# ⚙️ Лабораторія initcall: виміряти таблицю, витягти її з образу й вимкнути один рядок

Чотири питання про конкретну машину, що стоїть перед вами: які виклики ініціалізації на ній справді виконалися й скільки тривали, у якому порядку вони лежать у зібраному образі, куди потрапляє власний код і що станеться, якщо один виклик прибрати. На кожне є відповідь, яку можна побачити очима — рядок у журналі ядра або запис у таблиці символів, а не міркування про те, як воно мало б бути.

## Задача

Роботу зручно робити на власноруч зібраному ядрі — не тому, що на дистрибутивному щось не вийде, а тому, що третій крок вимагає додати файл у дерево ядра, а перший і другий тоді дістають готові `vmlinux` і `System.map` просто з теки збірки. Знадобляться [конфігурація й збірка ядра](book:unix-linux/kernel-config-and-build), уміння дописати параметр у [командний рядок ядра](book:unix-linux/bootloader-and-cmdline) і `binutils` (`nm`, `objdump`, `objcopy`). Усе, що ми читатимемо, лежить у [журналі ядра](book:unix-linux/kernel-log-printk), тож `dmesg` — головний прилад.

## Крок 1. Розкладка з журналу

Додаємо в командний рядок два параметри:

```
initcall_debug log_buf_len=4M
```

Перший умикає друк навколо кожного виклику, другий розширює кільцевий буфер журналу: без нього тисячі нових рядків витіснять із буфера саме той початок завантаження, заради якого все й затівалося.

Після завантаження в журналі на кожен виклик стоїть пара рядків, а перед кожним рівнем — заголовок:

```
entering initcall level: subsys
calling  pci_subsys_init+0x0/0x60 @ 1
initcall pci_subsys_init+0x0/0x60 returned 0 after 7622 usecs
```

Тривалість — це різниця двох позначок часу навколо самого виклику функції, тому вимірюється рівно синхронне тіло. Виклик, який лише замовив асинхронну роботу, виглядатиме дешевим, хоча система чекатиме на його наслідки далі.

Найдовші виклики дістаємо звичайним конвеєром. Позначки часу заважають розбирати рядок на поля, тож знімаємо їх ключем `-t`:

```sh
$ sudo dmesg -t | awk '$1 == "initcall" && $NF == "usecs" {
        name = $2; sub(/\+.*/, "", name); print $(NF-1), name
     }' | sort -rn | head -12
```

Та сама пара рядків називає винуватця зависання. «`calling`» друкується перед викликом, «`initcall ... returned`» — після, тож функція, яка не повернулася, лишає непарний рядок і більше нічого. Журнал зависання беруть, звісно, не з `dmesg` — системи, яка б його показала, уже немає, — а з послідовної консолі або з `pstore` після скидання; правило пошуку від цього не міняється:

```sh
$ awk '
     $1 == "calling"  { pending = $2 }
     $1 == "initcall" && $NF == "usecs" { pending = "" }
     END { print pending ? "не повернувся: " pending : "усі повернулися" }' boot.log
```

Другий погляд на ті самі дані — не хто найдовший, а куди пішов час за рівнями:

```sh
$ sudo dmesg -t | awk '
     /^entering initcall level:/ { lvl = $4
         if (!(lvl in total)) { order[++k] = lvl; total[lvl] = 0 }
         next }
     $1 == "initcall" && $NF == "usecs" { n[lvl]++; total[lvl] += $(NF-1) }
     END { for (i = 1; i <= k; i++) { l = order[i]
             printf "%-9s %4d викликів %9.1f мс\n", l, n[l], total[l] / 1000 } }'
early        14 викликів       3.1 мс
core         96 викликів      41.7 мс
...
device      612 викликів    1284.9 мс
late         88 викликів     102.4 мс
```

Розподіл майже завжди однаковий за формою: рівні до `device` коштують десятки мілісекунд, а майже весь час завантаження ядра сидить у кількох викликах рівня `device`, які чекають на залізо.

## Крок 2. Та сама таблиця, витягнута з образу

Журнал показує, що **виконалося**. Він не показує, що в таблиці **лежить**: вимкнений виклик рядка не залишає, а до викликів після зависання справа не дійшла зовсім. Тому другий погляд — прямо в зібраний образ.

Межі рівнів — звичайні символи, і `System.map` їх має:

```sh
$ grep -E '__initcall(_start|_end|[0-7]_start|rootfs_start)$' System.map
ffffffff82d5c1a0 D __initcall_start
ffffffff82d5c1d8 D __initcall0_start
...
ffffffff82d5eb60 D __initcallrootfs_start
ffffffff82d5eb68 D __initcall6_start
```

Видно й те, про що інакше довелося б вірити на слово: `__initcallrootfs_start` стоїть **перед** межею шостого рівня, тобто ці записи фізично живуть у діапазоні рівня `fs`.

Далі — вміст. На архітектурах, які вміють 32-бітні відносні переміщення, у секції лежить не адреса, а знаковий зсув від місця самого запису, тож ім'я функції треба відновити арифметикою. Вона нехитра, і варта одного проходу вручну, щоб потім довіряти скриптові.

**Умова: перший запис рівня `late` в ядрі x86-64.**

```
адреса самого запису   0xffffffff82d5ec80
чотири байти за нею    a8 14 df ff        (молодшим уперед)
як 32-бітне знакове    0xffdf14a8  →  −2157400
адреса функції         0xffffffff82d5ec80 − 2157400 = 0xffffffff82b50128
```

Зсув від'ємний, бо код ініціалізації лежить в образі раніше за таблицю покажчиків на нього. Знайдена адреса мусить збігтися з початком символу в `System.map` точно; якби вона сіла всередину функції, це означало б, що ширина запису вгадана неправильно.

Скрипт робить те саме масово: витягує секцію `.init.data` окремим файлом, розбирає її, а імена бере з тієї самої `System.map`:

```python
#!/usr/bin/env python3
"""Таблиця initcall зібраного ядра: рівень, номер у рівні, ім'я функції.
   ./initcalls.py vmlinux System.map [ширина-запису: 4 (зсув) або 8 (покажчик)]"""
import bisect, os, subprocess, sys, tempfile

LEVELS = ["pure", "core", "postcore", "arch", "subsys", "fs", "device", "late"]


def symbols(path):
    """System.map → адреси й імена, відсортовані для пошуку «хто тут живе»."""
    rows = []
    with open(path, encoding="utf-8", errors="replace") as f:
        for line in f:
            parts = line.split(None, 2)
            if len(parts) == 3:
                rows.append((int(parts[0], 16), parts[2].strip()))
    rows.sort()
    return [a for a, _ in rows], [n for _, n in rows]


def section_vma(vmlinux, name):
    """Початкова адреса секції — щоб перевести адресу запису в зсув у файлі."""
    out = subprocess.run(["objdump", "-h", vmlinux],
                         capture_output=True, text=True, check=True).stdout
    for line in out.splitlines():
        f = line.split()
        if len(f) >= 4 and f[1] == name:
            return int(f[3], 16)
    raise SystemExit("у файлі немає секції " + name)


def main(vmlinux, sysmap, width):
    addrs, names = symbols(sysmap)
    mark = dict(zip(names, addrs))          # межі мають унікальні імена
    vma = section_vma(vmlinux, ".init.data")

    tmp = tempfile.NamedTemporaryFile(suffix=".bin", delete=False)
    tmp.close()
    subprocess.run(["objcopy", "-O", "binary", "--only-section=.init.data",
                    vmlinux, tmp.name], check=True)
    with open(tmp.name, "rb") as f:
        blob = f.read()
    os.unlink(tmp.name)

    ranges = [("early", mark["__initcall_start"], mark["__initcall0_start"])]
    for i, level in enumerate(LEVELS):
        stop = "__initcall_end" if i == 7 else "__initcall%d_start" % (i + 1)
        ranges.append((level, mark["__initcall%d_start" % i], mark[stop]))
    rootfs = mark.get("__initcallrootfs_start")

    for level, start, stop in ranges:
        for k, at in enumerate(range(start, stop, width)):
            raw = blob[at - vma: at - vma + width]
            target = (at + int.from_bytes(raw, "little", signed=True)
                      if width == 4 else int.from_bytes(raw, "little"))
            i = bisect.bisect_right(addrs, target) - 1
            # Запис мусить указувати РІВНО на початок функції; інакше ширина не та.
            note = "" if addrs[i] == target else "   ← не на межі символу"
            tag = level + ("/rootfs" if rootfs and level == "fs"
                           and at >= rootfs else "")
            print("%-12s %3d  %s%s" % (tag, k, names[i], note))


if __name__ == "__main__":
    main(sys.argv[1], sys.argv[2],
         int(sys.argv[3]) if len(sys.argv) > 3 else 4)
```

Позначка «не на межі символу» — це вбудована перевірка здорового глузду: якщо ширина запису вгадана неправильно, кожен рядок сяде посеред чужої функції, і помилку видно одразу, а не через годину.

Найцікавіше починається, коли звірити порядок усередині одного рівня з порядком у файлах збірки. Візьміть із виводу дві сусідні назви одного рівня й знайдіть їхні файли:

```sh
$ ./initcalls.py vmlinux System.map | awk '$1 == "subsys"' | sed -n '17,18p'
$ grep -rn 'subsys_initcall(ІМ_Я_ФУНКЦІЇ)' drivers/ kernel/ fs/
```

Лишається подивитися, у якому порядку відповідні об'єктні файли перелічені в `obj-y` свого Makefile — а якщо вони з різних тек, то в якому порядку перелічені самі теки. Порядок збігається завжди, бо іншого джерела в нього немає; за мить ми переконаємося в цьому власними двома рядками.

## Крок 3. Свої два виклики — і свій модуль

Тепер додамо код, за яким можна стежити. Файл `drivers/misc/initlab.c` (ця тека компілюється завжди — `drivers/Makefile` заходить у неї беззастережно):

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/errno.h>
#include <linux/init.h>
#include <linux/jiffies.h>
#include <linux/printk.h>

static int __init lab_core(void)
{
	pr_info("initlab: core, jiffies=%lu\n", jiffies);
	return 0;
}
core_initcall(lab_core);

static int __init lab_late(void)
{
	pr_info("initlab: late, jiffies=%lu\n", jiffies);
	return -EIO;   /* навмисна помилка — подивимося, чи вона щось спинить */
}
late_initcall(lab_late);
```

Один рядок у `drivers/misc/Makefile` — `obj-y += initlab.o` — і після збірки скрипт із кроку 2 покаже обидва записи: один у рівні `core`, другий у `late`, з тисячами чужих між ними. У журналі між двома нашими повідомленнями лежить майже все завантаження ядра — це і є та відстань, яку купує вибір макроса.

Порядок усередині рівня перевіряється так само дешево: додайте другий такий самий файл із `core_initcall`, а потім поміняйте місцями два рядки `obj-y`. Записи в таблиці поміняються місцями, і жодного попередження збірка не дасть — саме тому такі залежності в ядрі тримаються на коментарях у Makefile.

Тепер той самий код, зібраний модулем. Окрема тека, `lab.c`:

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/init.h>
#include <linux/module.h>

static int __init lab_init(void)
{
	pr_info("lab: модуль стартував\n");
	return 0;
}

static void __exit lab_exit(void)
{
	pr_info("lab: модуль пішов\n");
}

module_init(lab_init);
module_exit(lab_exit);
MODULE_LICENSE("GPL");
```

```makefile
obj-m += lab.o

all:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
```

Параметр `initcall_debug` доступний і під час роботи системи — тому побачити ті самі два рядки для [модуля](book:unix-linux/kernel-modules) можна без перезавантаження:

```sh
$ echo 1 | sudo tee /sys/module/kernel/parameters/initcall_debug
$ sudo insmod lab.ko
$ sudo dmesg -t | tail -3
calling  lab_init+0x0/0x18 [lab] @ 1423
lab: модуль стартував
initcall lab_init+0x0/0x18 [lab] returned 0 after 11 usecs
```

Порівняйте з рядком вбудованого виклику: там `@ 1`, тобто потік, який згодом стане першим процесом, тут — номер процесу, що виконав `insmod`, і додатковий суфікс із назвою модуля. Обидва рядки друкує та сама функція `do_one_initcall()`; дороги, якими виклик до неї дійшов, розрізняють саме ці дві дрібниці.

![Таблиця з двох стовпчиків під спільним заголовком «module_init(lab_init) — один рядок у джерелі». Ліворуч дорога вбудованого коду: розгортається в device_initcall, зсув до функції лягає в секцію .initcall6.init між __initcall6_start і __initcall7_start, викликає цикл do_initcall_level(6) у потоці pid 1, у журналі «calling lab_init+0x0/0x18 @ 1», тіло зникає при free_initmem наприкінці завантаження. Праворуч дорога модуля: той самий рядок стає псевдонімом init_module у lab.ko, функція лежить у .init.text модуля й у таблиці ядра її немає, викликає завантажувач модулів у мить insmod у контексті процесу, у журналі «calling lab_init+0x0/0x18 [lab] @ 1423», init-пам'ять модуля звільняється одразу після insmod](/reference/unix-linux/boot-init/kernel-initcalls/img/two-paths-of-module-init.svg)

*Спільна в обох доріг рівно одна функція — `do_one_initcall()`. Усе інше різне, включно з тим, коли код перестає існувати.*

## Крок 4. Вимкнути один рядок

Наш `lab_late()` повернув `-EIO`, і в журналі це видно чорним по білому:

```
initcall lab_late+0x0/0x28 returned -5 after 8 usecs
```

Далі — нічого. Ніхто не скасував ініціалізації, не зупинив завантаження, не написав жодного попередження. Система дійшла до простору користувача так, ніби нічого не сталося.

Тепер приберемо виклик зовсім — додамо в командний рядок:

```
initcall_blacklist=lab_late
```

Після завантаження в журналі немає ні рядка `calling  lab_late...`, ні нашого `pr_info`, ні рядка про повернене значення. Перевірка списку стоїть **перед** трасувальною точкою, тож вимкнений виклик не лишає взагалі жодного сліду — і система, звісно, завантажилася. Ім'я шукається за таблицею символів ядра ([kallsyms](book:unix-linux/kallsyms-and-system-map)) і має збігатися точно, без зсуву: `lab_late`, а не `lab_late+0x0/0x28`.

## Пастки

**Вимкнений виклик мовчить.** Помилку в імені видно тільки за наслідком — виклик спокійно виконався. Повідомлення про занесення в список і про пропуск ідуть через `pr_debug`, тобто за умовчанням їх немає; щоб побачити, потрібне динамічне налагодження (`dyndbg="file init/main.c +p"`). І сам параметр працює лише тоді, коли ядро зібране з `CONFIG_KALLSYMS`: інакше все, що ви отримаєте, — попередження в журналі.

**Значення, що повернув initcall, не веде нікуди.** Крок 4 показує це прямо: `-EIO` не друкується без `initcall_debug`, не зупиняє завантаження й не скасовує нічого. Практичний наслідок для того, хто шукає причину: «підсистеми немає» і «підсистема не змогла стартувати» ззовні виглядають однаково, і розрізнити їх можна саме тим прогоном з `initcall_debug`.

**Тіло `__init`-функції після завантаження не існує.** Це не метафора: сторінки повернено розподільнику, і `free_initmem()` друкує, скільки саме. Спроба зберегти покажчик на таку функцію в звичайних даних — готовий стрибок у чужу пам'ять, і збірка ловить її сама:

```
WARNING: modpost: vmlinux: section mismatch in reference:
lab_ptr+0x0 (section: .data) -> lab_core (section: .init.text)
```

Попередження про невідповідність секцій означає рівно одне: щось із довгим життям посилається на щось, що от-от зникне.

**Межові символи є не всюди, де їх шукають.** У `System.map` вони є завжди, бо цей файл робиться з таблиці символів образу. У `/proc/kallsyms` символів-даних може не бути зовсім (їх дає окрема опція збірки), а звичайному користувачеві всі адреси там показані нулями — так працює обмеження на друк адрес ядра. Для цієї роботи джерело правди — `System.map` поруч із тим самим `vmlinux`, а не будь-який файл із такою назвою в `/boot`.

**Ширина запису залежить від архітектури.** Скрипт за умовчанням читає 32-бітні зсуви. Там, де ядро зібране без цієї можливості, у секції лежать повні покажчики — тоді третім аргументом треба дати `8`. Перевірка «не на межі символу» скаже про це першим же рядком.
