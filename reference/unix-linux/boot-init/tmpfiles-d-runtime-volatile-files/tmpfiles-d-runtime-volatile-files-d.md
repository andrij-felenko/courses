Запуск веб-сервера Nginx чи СУБД PostgreSQL після перезавантаження операційної системи аварійно завершується з помилкою `ENOENT` (англ. *No such file or directory*), якщо ці служби намагаються відкрити доменний сокет Unix за шляхом `/run/nginx/nginx.sock` або створити файл ідентифікатора процесу у `/run/postgresql/5432.pid`, а відповідних каталогів на файловій системі не існує. Оскільки каталог `/run` монтується у пам'яті як волотильна файлова система `tmpfs`, будь-яке вимкнення або перезавантаження вузла повністю знищує його вміст разом із усією створеною структурою підкаталогів. 

Спроби створювати ці каталоги безпосередньо у коді самих служб призводять до збоїв прав доступу: якщо служба запускається від імені некореневого системного користувача `postgres` чи `nginx`, у неї відсутні привілеї для створення підкаталогів у корінному каталозі `/run`, що належить `root`. Завдання створення, налаштування прав доступу, підготовки волотильних каталогів та ротації застарілих файлів вимагає системного механізму, який виконується до запуску основних прикладних процесів і діє у суворо визначеному декларативному форматі.

## 1. Декларативна модель systemd-tmpfiles

Інструмент `systemd-tmpfiles` (англ. *systemd temporary files manager*, від лат. *temporarius* — тимчасовий) забезпечує централізоване, декларативне управління волотильними та тимчасовими файлами, каталогами, символьними посиланнями, іменованими каналами (FIFO) та вузлами пристроїв. Замість виконання імперативних сценаріїв оболонки з викликами `mkdir`, `chmod` та `chown` під час кожного старту системи, системний менеджер зчитує конфігураційні файли з описом бажаного стану файлової системи та наводить диск у відповідність до цих специфікацій.

Декларативна модель дає три суттєві переваги над традиційними скриптами оболонки:
- **Атомарність та прогнозованість**: стан файлової системи описується як кінцева ціль. Якщо каталог існує з правильними правами, додаткові дії не виконуються; якщо атрибути відхилилися, утиліта коригує лише відмінності.
- **Централізована безпека**: створення та модифікація об'єктів відбувається з використанням безпечних системних викликів POSIX, які захищають від атак через символьні посилання та підміну шляхів у списку каталогів.
- **Уніфікований життєвий цикл**: створення рантайм-структур під час старту та ротація тимчасових файлів за часом описуються в межах єдиного формату конфігурації.

Історично операційні системи Linux покладалися на фрагментовані рішення: скрипти ініціалізації SysV вручну створювали рантайм-каталоги, а нічні завдання `cron` запускали утиліти очищення `tmpwatch` або `tmpreaper`. Такий підхід породжував критичні вразливості безпеки через гонитву за символьними посиланнями у відкритих каталогах та створював важкі піки навантаження на диски. Повний огляд історичного розвитку цих механізмів висвітлено у [нарисі про еволюцію волотильного сховища](book:unix-linux/tmpfiles-d-runtime-volatile-files/hist-volatile-storage-evolution.md).

Кожен рядок конфігураційного файла `tmpfiles.d` описує один файловий об'єкт у вигляді табличного формату із семи полів:

```text
# Тип  Шлях                  Режим  Власник    Група      Вік  Аргумент
d      /run/postgresql       0755   postgres   postgres   -    -
f      /run/postgresql/live  0644   postgres   postgres   -    -
L+     /run/postgres.sock    -      -          -          -    /run/postgresql/.s.PGSQL.5432
```

Повний довідник усіх підтримуваних типів директив, модифікаторів та часових форматів наведено у [специфікації форматів та типів директив tmpfiles.d](book:unix-linux/tmpfiles-d-runtime-volatile-files/api-tmpfiles-spec.md).

### Три режими виконання утиліти

Утиліта `systemd-tmpfiles` працює у трьох взаємодоповнюючих режимах, кожен із яких відповідає за свою фазу життєвого циклу тимчасових даних:

1. **Режим створення (`systemd-tmpfiles --create`)**:
   Виконується на ранньому етапі завантаження системи системними сервісами `systemd-tmpfiles-setup.service` та `systemd-tmpfiles-setup-dev.service`. Парсер аналізує конфігурації, створює відсутні каталоги, файли, символьні посилання та каналу FIFO, виставляє вісімкові права доступу POSIX, змінює власника (UID/GID), виставляє розширені атрибути файлової системи (`xattr`), списки контролю доступу (POSIX ACL) та відновлює контексти безпеки SELinux.
2. **Режим очищення (`systemd-tmpfiles --clean`)**:
   Виконується періодично за розкладом за допомогою системного таймера `systemd-tmpfiles-clean.timer` (за замовчуванням — щогодини). У цьому режимі утиліта сканує каталоги з тимчасовими файлами (`/tmp`, `/var/tmp`, `/run`), аналізує часові позначки об'єктів та видаляє ті файли й порожні каталоги, вік яких перевищує поріг, заданий у полі `Age`.
3. **Режим видалення (`systemd-tmpfiles --remove`)**:
   Виконується під час вимкнення системи або за явним викликом адміністратора. Утиліта видаляє файли та каталоги, які позначені спеціальними типами `r` (видалення конкретного об'єкта) або `R` (рекурсивне видалення вмісту).

## 2. Ієрархія конфігурації та затінення файлів (Shadowing)

Для забезпечення чіткого розподілу відповідальності між дистрибутивом Linux, динамічним генератором рантайм-станцій та системним адміністратором, файли налаштувань `tmpfiles.d` шукаються та зчитуються у трьох каталогах із суворо визначеним пріоритетом.

Конфігурації обробляються у порядку спадання пріоритету:

1. **`/etc/tmpfiles.d/*.conf` (Найвищий пріоритет)**:
   Призначений для локальних налаштувань системного адміністратора вузла. Конфігурації у цьому каталозі мають абсолютне перевагу над постачальниками пакетів.
2. **`/run/tmpfiles.d/*.conf` (Середній пріоритет)**:
   Призначений для тимчасових конфігурацій, які генеруються автоматично під час завантаження системи (наприклад, генераторами systemd, середовищем initramfs або контейнерними демонами).
3. **`/usr/lib/tmpfiles.d/*.conf` (Найнижчий пріоритет)**:
   Призначений для базованих конфігурацій, які поставляються пакетами дистрибутива (RPM, DEB) та самим службовим менеджером systemd. Переписувати файли у цьому каталозі вручну заборонено, оскільки вони перезаписуються при оновленні пакунків.

### Механізм лексикографічного сортування та маскування

Усі конфігураційні файли з усіх трьох каталогів об'єднуються в єдиний список і сортуються у лексикографічному (алфавітно-цифровому) порядку за їхнім базовим іменем (без урахування шляху до каталогу). Наприклад, файл `10-local.conf` буде оброблено раніше за файл `50-nginx.conf`.

Якщо файли з **однаковим іменем** присутні у кількох каталогах (наприклад, `/etc/tmpfiles.d/nginx.conf` та `/usr/lib/tmpfiles.d/nginx.conf`), файл із вищим пріоритетом повністю затіняє (англ. *shadows*) файл із нижчим пріоритетом. Файл у `/usr/lib` ігнорується повністю.

Якщо адміністратор бажає повністю вимкнути конфігураційний файл, поставляємий дистрибутивом, застосовується техніка **маскування**: у каталозі `/etc/tmpfiles.d/` створюється символьне посилання з таким самим іменем, яке вказує на `/dev/null`:

```bash
# Маскування поставляємого дистрибутивом файлу конфігурації
ln -s /dev/null /etc/tmpfiles.d/legacy-service.conf
```

Під час парсингу `systemd-tmpfiles` виявляє символьне посилання на `/dev/null` і повністю пропускає обробку даного набору правил.

### Системні специфікатори та динамічна підстановка

У полях `Path` та `Argument` дозволяється використовувати розширювані специфікатори systemd. Це дає змогу будувати універсальні конфігураційні файли, які адаптуються до оточення:

- `%t` підставляє системний рантайм-каталог `/run`.
- `%S` підставляє каталог стану `/var/lib`.
- `%C` підставляє каталог кешу `/var/cache`.
- `%L` підставляє каталог журналів `/var/log`.
- `%m` підставляє машини ідентифікатор Machine ID з `/etc/machine-id`.
- `%b` підставляє ідентифікатор сеансу завантаження Boot ID.
- `%H` підставляє мережеве ім'я вузла (hostname).

Завдяки специфікаторам рядок `d %t/mydaemon 0755 root root -` автоматично розгортається у `/run/mydaemon` на звичайній системі або у `/run/user/1000/mydaemon` при виконанні у сеансі користувача.

## 3. Топологія волотильних каталогів та безпека системних викликів

Файлова система Linux надає три ключові каталоги для розміщення нестійких даних. Кожен каталог має власну семантику збереження, швидкодію та регламент очищення:

1. **Каталог `/run` (tmpfs)**:
   Зберігає волотильний рантайм-стан служб (доменні сокети UNIX, PID-файли, FIFOs, файли блокувань у `/run/lock`). Фізично живе у пам'яті RAM. Вміст повністю зникає при перезавантаженні. Автоматичне очищення за віком (`Age`) для `/run` за замовчуванням вимкнене.
2. **Каталог `/tmp` (tmpfs або диск)**:
   Призначений для короткоживучих тимчасових файлів додатків і користувачів. Очищується під час завантаження системи та періодично процедурою `systemd-tmpfiles --clean`. Стандартний поріг очищення становить 10 днів.
3. **Каталог `/var/tmp` (Диск)**:
   Призначений для великих тимчасових файлів (наприклад, образів дисків чи великих архівів), які повинні зберігатися між перезавантаженнями системи. Розміщується на фізичному диску. Стандартний поріг очищення процедурою `--clean` становить 30 днів.

### Захист від атак TOCTOU та безпечний обхід каталогів

Оскільки каталоги `/tmp` та `/var/tmp` мають режим доступу `1777` (з виставленим sticky-бітом), створювати файли у них може будь-який непривілейований користувач системи. Це робить процедуру прибирання сміття з боку процесів із привілеями `root` потенційно вразливою до атак типу TOCTOU (англ. *Time-of-Check to Time-of-Use*).

Для запобігання атакам через символьні посилання `systemd-tmpfiles` реалізує суворі безпекові механізми на рівні системних викликів ядра Linux:

- **Атомарна робота через дескриптори каталогів**: замість передачі текстових шляхів у класичні системні виклики (`unlink`, `chmod`), утиліта відкриває каталог за допомогою `openat()` із прапорцями `O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC` і працює виключно з отриманим файловим дескриптором.
- **Заборона слідування за символьними посиланнями**: при перевірці та вилученні об'єктів використовуються системні виклики `fstatat()`, `unlinkat()` та `mkdirat()` із прапорцем `AT_SYMLINK_NOFOLLOW`. Якщо користувач створює символьне посилання, видаляється саме посилання, а не цільовий файл, на який воно вказує.
- **Перевірка власника та режимів доступу**: перед рекурсивним входженням у підкаталог утиліта перевіряє, чи належить цей каталог користувачеві, який є власником батьківського каталогу, або чи виставлено на ньому захисні прапорці.
- **Точний розрахунок віку через `statx()`**: для обчислення часу життя файлу `systemd-tmpfiles` задіяє сучасний системний виклик `statx()`, витягуючи не лише час модифікації (`mtime`) та доступу (`atime`), але й час зміни метаданих (`ctime`) та час створення файлу (`btime`). Файл вилучається лише тоді, коли **усі** доступні часові позначки є старішими за поріг `Age`.

Така низькорівнева інженерія гарантує, що локальний зловмисник не зможе змусити утиліту очищення видалити системний файл `/etc/passwd` або пошкодити баз даних, розмістивши хитрий симлінк у спільному каталозі `/tmp`.

## 4. Спеціалізовані типи директив та робота з розширеними атрибутами

Специфікація `tmpfiles.d` надає можливість працювати не лише зі звичайними файлами та каталогами, але й зі складними підсистемами ядра та файлових систем.

### 1. Підтримка файлової системи Btrfs та квот

Для файлової системи Btrfs `systemd-tmpfiles` надає спеціалізовані типи `v`, `q` та `Q`:
- Тип `v` створює новий подтом Btrfs (англ. *subvolume*). Якщо файлова система під вказаним шляхом є класичною (Ext4, XFS), утиліта прозоро створює звичайний каталог.
- Типи `q` та `Q` дозволяють прив'язувати створений подтом до ієрархічних груп квот дискового простору, обмежуючи максимальний обсяг даних, який може зайняти волотильний чи тимчасовий каталог.

### 2. Управління розширеними атрибутами (xattr) та POSIX ACL

У сучасних дистрибутивах Linux файли та каталоги часто потребують додаткових метаданих безпеки, які виходять за межі класичної трибітової маски POSIX (User/Group/Others):
- Типи `t` та `T` виставляють розширені атрибути файлової системи (`xattr`), такі як `user.comment` або атрибути підсистеми журналювання.
- Типи `a` та `A` (а також їхні модифікації `a+` та `A+`) виставляють списки контролю доступу POSIX ACL. Це дозволяє надати права на читання або запис у волотильний каталог одразу кільком різним системним користувачам або групам без їх об'єднання у спільну групу OS.

### 3. Рекурсивне оновлення прав доступу та SELinux (Типи z та Z)

Типи `z` та `Z` призначені для виправлення власників, вісімкових режимів доступу та відновлення контекстів безпеки SELinux на вже наявних файлових об'єктах:
- Тип `z` застосовує коригування лише до самого вказаного шляху (без занурення у підкаталоги).
- Тип `Z` рекурсивно обходить увесь вміст каталогу і перенацілює права доступу та маркування SELinux (`restorecon`) для всіх знайдених файлів.

### 4. Робота з пристроями та шиною devtmpfs

Служба `systemd-tmpfiles-setup-dev.service` виконується на найранніших стадіях завантаження системи для створення вузлів пристроїв (типи `c` та `b`), які необхідні до моменту ініціалізації демона `udevd`. Наприклад, створення статичних вузлів пристроїв `/dev/null`, `/dev/zero`, `/dev/console` та `/dev/loop-control` за допомогою `mknod()` описується саме через файли конфігурації `tmpfiles.d` у каталозі `/usr/lib/tmpfiles.d/static-nodes-permissions.conf`.

## 5. Інтеграція з службами та системним програмуванням

При розробці системних служб постає вибір між двома підходами до створення волотильних каталогів: використання вбудованих директив системного юніта systemd (таких як `RuntimeDirectory=`) або створення окремого конфігураційного файла у `tmpfiles.d`.

### Порівняння RuntimeDirectory та tmpfiles.d

Службові юніти systemd підтримують параметри `RuntimeDirectory=`, `StateDirectory=`, `CacheDirectory=`, `LogsDirectory=` та `ConfigurationDirectory=`. Коли у файлі `.service` вказано `RuntimeDirectory=myapp`, системний менеджер автоматично створює каталог `/run/myapp` при старті служби та видаляє його при зупинці.

Вибір між цими механізмами здійснюється за наступними критеріями:

- **Використовуйте `RuntimeDirectory=`**, якщо волотильний каталог потрібен **виключно одній конкретній службі**, має жити лише під час її роботи та не вимагає складних правил ротації файлів чи спеціальних розширених атрибутів xattr/ACL.
- **Використовуйте `tmpfiles.d`**, якщо каталог повинен **існувати завжди** (незалежно від того, чи за запущена служба у дану секунду), якщо до каталогу звертаються **декілька різних служб**, або якщо потрібні складні правила ротації за віком, створення іменованих каналів FIFO, дзеркалювання каталогів чи гнучка підтримка POSIX ACL.

Практичний проект із реалізацією системного демона мовами C та C++, який працює із підготовленим волотильним каталогом та захищеними доменними сокетами UNIX, наведено у [демонстраційній розробці сервісу з волотильним каталогом](book:unix-linux/tmpfiles-d-runtime-volatile-files/proj-custom-tmpfiles-service.md).

## 6. Контейнеризація та функціонування у легковагових середовищах

У сучасних контейнерних архітектурах (системні контейнери `systemd-nspawn`, LXC, Docker чи Podman) сервіс `systemd-tmpfiles` відіграє ключову роль при моментуванні порожніх волотильних каталогів всередині ізольованого rootfs:

- **Спільні каталоги `tmpfs` у контейнері**: при заповненні контейнерного середовища каталог `/run` монтується як новий екземпляр `tmpfs`, у якому відсутній будь-який рантайм-стан хоста. При старті PID 1 всередині контейнера служба `systemd-tmpfiles-setup.service` зчитує пакункові файли конфігурацій та за кілька мілісекунд розгортає повну структуру рантайм-каталогів.
- **Ізоляція просторів імен користувачів (User Namespaces)**: коли контейнер працює в ізольованому UID namespace (де UID 0 всередині контейнера відображається на непривілейовану UID 100000 на хості), `systemd-tmpfiles` автоматично транслює імена користувачів через NSS у контексті поточного простору імен, створюючи файли з правильним внутрішнім UID.

## 7. Інструменти діагностики, інспекції та ручного налагодження

Утиліта `systemd-tmpfiles` надає системному адміністраторові багатий набір прапорців для безпечного тестування та інспектування підсистеми:

- **Інспекція зведеного дерева конфігурацій (`--cat-config`)**:
  Відображає результуючий зведений конфігураційний файл із урахуванням усього дерева затінення каталогів `/etc`, `/run` та `/usr/lib`.
  ```bash
  systemd-tmpfiles --cat-config
  ```
- **Тестовий режим без застосування змін (`--dry-run`)**:
  Виводить у стандартний вивід усі системні виклики та файлові операції (`mkdir`, `unlink`, `chmod`, `chown`), які утиліта планує виконати при фазах `--create` або `--clean`.
  ```bash
  systemd-tmpfiles --create --dry-run /etc/tmpfiles.d/custom.conf
  ```
- **Виконання у контексті користувача (`--user`)**:
  Запускає утиліти від імені поточного непривілейованого користувача, застосовуючи конфігураційні правила з каталогу `~/.config/user-tmpfiles.d/*.conf` до волотильного каталогу сеансу `/run/user/$UID/`.

## 8. Практичний вимір, пастки та граничні випадки

> 🔧 **Навіщо це.** Знання внутрішніх механізмів `systemd-tmpfiles` рятує від раптових нічних падінь серверів через зниклі сокети, незрозумілих збоїв прав доступу після оновлення пакунків та дозволяє будувати суворо ізольовані середовища для високонавантажених служб.

### Типові помилки та граничні випадки

Під час експлуатації та адміністрування `tmpfiles.d` найчастіше виникають такі проблемні ситуації:

1. **Блокування оновлення часу доступу при монтуванні `noatime`**:
   Якщо файлова система підмонтована з прапорцем `noatime` (що приховано вимикає оновлення позначки `atime` при читанні файлів для підвищення швидкодії диска), очищення за віком `systemd-tmpfiles --clean` не спирається на `atime`. Завдяки використанню `statx()` утиліта перевіряє також `mtime` та `ctime`, що запобігає передчасному видаленню активних файлів.
2. **Конфлікти з динамічними користувачами (`DynamicUser=yes`)**:
   Якщо сервіс використовує тимчасових ефемерних користувачів, їхні UID/GID змінюються при кожному старті. Використання статичних імен у `tmpfiles.d` для таких служб є помилковим; замість цього слід застосовувати `RuntimeDirectory=` у файлі юніта, який автоматично прив'язує права до поточного динамічного UID.
3. **Рекурсивне відновлення SELinux та прав доступу (Тип `Z`)**:
   Використання типу `Z` для великих каталогів із мільйонами файлів (наприклад, у `/var/spool` чи `/var/log`) спричиняє важке тривале сканування диска при кожному завантаженні системи, викличучи затримки старту. Для великих каталогів слід використовувати нерекурсивний тип `z` або коригувати права лише для верхнього рівня.
4. **Користувацькі екземпляри (`--user`)**:
   Звичайні користувачі можуть створювати власні правила у `~/.config/user-tmpfiles.d/*.conf`. Екземпляр `systemd-tmpfiles --user` створює об'єкти всередині користувацького рантайм-каталогу `/run/user/$UID/` без використання привілеїв `root`.
