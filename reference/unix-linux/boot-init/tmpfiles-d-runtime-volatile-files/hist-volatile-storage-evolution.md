# 📜 Еволюція волотильного сховища: від cron-скриптів до декларативного tmpfiles.d

Історія управління волотильним та тимчасовим станом у системах Unix й Linux демонструє тривалий шлях від імперативних фрагментованих сценаріїв оболонки до єдиного атомарного декларативного підходу. Із перших днів існування Unix виникла потреба розділяти дані за часом їхнього життя: одні файли мали жити місяцями на магнітних дисках, інші потрібні були на кілька секунд для міжпроцесної взаємодії або зберігання проміжних обчислень. Однак механізми, якими операційні системи задовольняли цю потребу, еволюціонували разом із підвищенням вимог до безпеки, швидкодії та стабільності завантаження.

### Епоха тришарової структури FHS та первісний розрив

У ранніх стандартах ієрархії файлових систем (англ. *Filesystem Hierarchy Standard*, FHS версій 2.0–2.3) склалася традиційна тришарова схема розподілу тимчасових даних:

1. Каталог `/tmp` призначався для короткоживучих файлів системних процесів та користувачів. Згідно з угодою, дані в `/tmp` могли очищатися під час кожного перезавантаження системи або за періодичним розкладом.
2. Каталог `/var/tmp` слугував для тимчасових файлів, які мали переживати перезавантаження системи (наприклад, великі масиви даних компіляції, відновлювальні сесії текстових редакторів або великі файли друку).
3. Каталог `/var/run` вміщував рантайм-стан працюючих служб: ідентифікатори процесів (`.pid`-файли), доменні сокети Unix (`.sock`) та замок-файли (`.lock`).

Головна проблема цієї класичної схеми полягала у природі виклику файлових систем на етапі ініціалізації. Каталог `/var/run` фізично знаходився всередині ієрархії `/var`. На серверах 1990-х та ранніх 2000-х років каталог `/var` часто виносили на окремий дисковий розділ або навіть на мережеву файлову систему NFS. 

Коли система завантажувалася, сценарії ініціалізації SysV init намагалися запустити системні демони (такі як `syslogd`, `named` або `sshd`) до того, як ядро та утиліти монтування приєднували розділ `/var`. Виникало замкнене коло: служба не могла запуститися, бо не мала доступу до `/var/run` для створення сокета чи PID-файла, а змонтувати `/var` не вдавалося через відсутність піднятих мережевих чи системних служб.

Спроби змонтувати `/var/run` як окрему файлову систему в оперативній пам'яті (`tmpfs`) на ранніх етапах завантаження створювали додаткову плутанину, адже каталог `/var` міг бути ще відсутнім у дереві монтувань.

### Сценарії оболонки та проблема гонитви за файлом (TOCTOU)

Паралельно з проблемами монтування існувала проблема прибирання сміття у `/tmp` та `/var/tmp`. Протягом десятиліть стандартним рішенням були періодичні завдання фонового планувальника `cron`, які запускали утиліти `tmpwatch` або `tmpreaper` (або просто сценарії на командній оболонці `find /tmp -atime +7 -exec rm -f {} \;`).

Цей підхід мав три фундаментальні дефекти:

Перший дефект — **вразливість до атак типу TOCTOU** (англ. *Time-of-Check to Time-of-Use* — час перевірки проти часу використання). Оскільки утиліти `find` або `tmpwatch` виконувалися з привілеями суперкористувача (`root`), вони рекурсивно обходили каталоги, доступні для запису будь-якому користувачеві (з виставленим sticky-бітом `1777`). Зловмисник міг створити у `/tmp` звичайний файл, дочекатися, поки `tmpwatch` перевірить його вік, а у мікросекундний інтервал між перевіркою та видаленням замінити цей файл символьним посиланням на критичний системний файл (наприклад, `/etc/shadow` або `/lib64/libc.so.6`). Коли утиліта з привілеями `root` виконувала `unlink` або `open`, вона слідувала за символьним посиланням і знищувала системні дані.

Другий дефект — **фрагментація та імперативність**. Кожен пакунок у системі (Nginx, PostgreSQL, Redis) приносив у власному ініціалізаційному скрипті `/etc/init.d/service` унікальний шматок коду на Bash:

```sh
# Типовий імперативний фрагмент у SysV init
if [ ! -d /var/run/mydaemon ]; then
    mkdir -p /var/run/mydaemon
    chown daemon:daemon /var/run/mydaemon
    chmod 0755 /var/run/mydaemon
fi
```

Кожна служба вирішувала задачу створення свого волотильного середовища наново. Права доступу, маски `umask` та прапорці розставлялися неузгоджено, а помилка в одному скрипті могла зупинити увесь ланцюг старту системи.

Третій дефект — **сплески дискового введення-виведення**. Запуск `find` по мільйонах дрібних тимчасових файлів раз на добу викликав важкі піки навантаження на накопичувачі, блокуючи роботу корисних навантажень.

### Велика міграція 2011 року: виникнення `/run`

У березні 2011 року розробники системного дистрибутива Fedora разом із командою розробників systemd (зокрема Леннартом Пьоттерінгом та Каєм Зіверсом) опублікували пропозицію щодо уніфікації рантайм-сховища. Ідея полягала у створенні нового каталогу першого рівня `/run`, який монтується як `tmpfs` на найранніших етапах завантаження — безпосередньо з `initramfs` або першим процесом (PID 1) до монтування дискових файлових систем.

Згідно з цією реформою:
- `/run` став єдиним стандартизованим місцем для волотильного стану системних служб.
- Старі каталоги `/var/run` та `/var/lock` були перетворені на символьні посилання: `/var/run -> /run` та `/var/lock -> /run/lock`.
- У 2015 році каталог `/run` офіційно включили до специфікації Filesystem Hierarchy Standard 3.0.

Завдяки тому, що `/run` завжди лежить в оперативній пам'яті, перезавантаження системи гарантовано й повністю очищує рантайм-стан усіх служб, унеможливлюючи ситуації, коли застарілий PID-файл після аварійного вимкнення блокував повторний запуск демона.

### Народження systemd-tmpfiles та декларативного стандарту

Разом із каталогом `/run` виникла потреба в механізмі, який би централізовано й безпечно готував структуру файлів у цьому порожньому після кожного перезавантаження середовищі. На зміну розсипаним Bash-скриптам прийшов сервіс `systemd-tmpfiles` та формат декларативних конфігурацій `tmpfiles.d`.

Замість виконання імперативного коду розробники служб почали поставляти декларативні текстові специфікації:

```text
# Декларативний запис у tmpfiles.d замінює купу кодів у shell
d /run/mydaemon 0755 daemon daemon -
```

Утиліта `systemd-tmpfiles` була написана на C з вичерпним дотриманням вимог системної безпеки POSIX:
1. Замість нестабільних функцій роботи зі шляхами розробники задіяли сімейство системних викликів `openat()`, `mkdirat()`, `unlinkat()` із обов'язковими прапорцями `O_NOFOLLOW` та `O_CLOEXEC`, що унеможливило атаки через символьні посилання.
2. Періодична очистка тимчасових файлів перейшла від зовнішніх cron-скриптів до системних таймерів systemd (`systemd-tmpfiles-clean.timer`), які аналізують метрики часу `mtime`, `atime` та `ctime` атомарними викликами `statx()`.
3. Вперше з'явилася нативна підтримка розширених атрибутів (`xattr`), системних списків контролю доступу (POSIX ACL) та контекстів безпеки SELinux безпосередньо у мить створення файлового об'єкта.

Таким чином, еволюція від імперативних сценаріїв до `tmpfiles.d` перетворила управління тимчасовими файлами з джерела постійних збоїв та безпекових вразливостей на передбачувану, ізольовану й декларативну частину ядра системного адміністрування Linux.
