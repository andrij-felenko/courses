# Вимірюване завантаження: TPM, регістри PCR і вимірювання ланцюжка довіри

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У сучасних комп'ютерних системах безпека завантаження відіграє критичну роль. Замість того, щоб просто довіряти кожному компоненту, який бере участь у процесі завантаження, концепція "Вимірюваного завантаження" (Measured Boot) пропонує математично строгий метод фіксації стану системи на кожному етапі. Цей механізм базується на апаратному модулі Trusted Platform Module (TPM), який забезпечує надійне зберігання криптографічних гешів у своїх регістрах Platform Configuration Registers (PCR). У цій статті ми детально розглянемо архітектуру вимірюваного завантаження, стандарти TPM 2.0, структуру і призначення PCR, процес розширення (TPM2_Extend), журнал подій (Event Log), а також технологію Integrity Measurement Architecture (IMA) та атестацію ключів.

## Роль Trusted Platform Module (TPM 2.0)

TPM (Trusted Platform Module) — це спеціалізований мікроконтролер, призначений для забезпечення апаратних функцій безпеки. Специфікація TPM 2.0, розроблена Trusted Computing Group (TCG), значно розширює можливості свого попередника (TPM 1.2), пропонуючи алгоритмічну гнучкість (підтримку алгоритмів SHA-256, SHA-384, ECC та ін.), покращену авторизацію та гнучку політику доступу.

TPM не може самостійно зупинити процес завантаження, якщо виявляє модифікацію (на відміну від Secure Boot). Його головна задача — працювати як "чорний ящик" для зберігання вимірювань (гешів), які пізніше можна перевірити. Це створює "Ланцюжок довіри" (Chain of Trust).

## Регістри PCR (Platform Configuration Registers)

В основі механізму вимірюваного завантаження лежать регістри PCR. Вони знаходяться всередині TPM і використовуються для зберігання криптографічних гешів. Особливість цих регістрів у тому, що їх неможливо перезаписати безпосередньо. Замість цього використовується операція `Extend`.

### Стандартний розподіл PCR (0-15) у середовищі PC Client

Специфікація TCG визначає використання як мінімум 24 регістрів PCR. Перші 16 регістрів (PCR 0-15) використовуються прошивкою (BIOS/UEFI) та завантажувачем:

- **PCR 0**: Вимірювання базової прошивки (CRTM, Core Root of Trust for Measurement), BIOS/UEFI коду та мікрокоду процесора. Це незмінна частина, від якої починається ланцюг довіри.
- **PCR 1**: Конфігурація прошивки та дані (наприклад, налаштування SMBIOS).
- **PCR 2**: Option ROM коди, які додаються адаптерами (наприклад, відеокартами, мережевими картами).
- **PCR 3**: Конфігурація Option ROM.
- **PCR 4**: MBR (Master Boot Record) або код завантажувача UEFI (наприклад, `bootx64.efi`, `grubx64.efi`). Це перше вимірювання, що стосується ОС.
- **PCR 5**: Конфігурація завантажувача та GPT (GUID Partition Table).
- **PCR 6**: Події зміни стану або пробудження системи (State Transition/Wake Events).
- **PCR 7**: Стан Secure Boot (змінні PK, KEK, db, dbx). Це один з найважливіших регістрів для прив'язки ключів шифрування диска (наприклад, BitLocker, LUKS) до стану безпечного завантаження.
- **PCR 8-15**: Використовуються операційною системою та завантажувачем (наприклад, GRUB вимірює командний рядок ядра та `initrd` в PCR 8 і 9).

## Операція TPM2_Extend та Event Log

Як згадувалося, PCR не можна записати безпосередньо. Щоб додати нове вимірювання, використовується операція `Extend`. Математично це виглядає так:

`PCR_new = HASH(PCR_old || Data_Hash)`

де `||` означає конкатенацію (злиття), а `HASH` — алгоритм гешування (наприклад, SHA-256).

### Чому це безпечно?
Ця операція є односторонньою (one-way). Навіть якщо зловмисник знає початкове значення і всі дані, він не може скасувати операцію `Extend` або підробити дані так, щоб отримати те саме кінцеве значення (через стійкість криптографічних геш-функцій до колізій).

### Event Log (Журнал подій)
Оскільки значення PCR — це лише фінальний геш, сама по собі ця інформація не дає розуміння того, *які саме* компоненти були виміряні. Для цього система веде Журнал подій (Event Log) у пам'яті (TCG Event Log). Кожен раз, коли компонент робить `Extend` у PCR, він також додає запис у Event Log: "я виміряв файл X, його геш Y, і розширив його в PCR Z".

Для перевірки стану системи ОС читає Event Log, бере початкові нульові значення PCR і відтворює всі операції `Extend`. Якщо фінальний результат збігається з апаратними значеннями PCR з TPM, це означає, що Event Log справжній і система завантажилася так, як очікувалося.

## Integrity Measurement Architecture (IMA)

У Linux ланцюг довіри не закінчується на ядрі. Підсистема Integrity Measurement Architecture (IMA) продовжує його, вимірюючи файли, які операційна система відкриває для виконання (бінарні файли, бібліотеки, скрипти).

IMA має власний механізм журналу та розширює регістр **PCR 10** у TPM. Це дозволяє здійснювати атестацію не тільки процесу завантаження, але й середовища виконання ОС. Коли програма запускається, IMA хешує її вміст і робить `Extend` у PCR 10, перш ніж дозволити виконання.

## Key Attestation (Атестація ключів та розблокування дисків)

Одним із головних застосувань вимірюваного завантаження є *Sealing* (запечатування) даних або ключів. Ви можете змусити TPM зашифрувати ключ шифрування диска (наприклад, для LUKS) таким чином, щоб TPM розшифрував його *тільки* в тому випадку, якщо певні регістри PCR мають визначені значення.

Наприклад:
`tpm2_createpolicy --policy-pcr -l sha256:0,2,4,7 ...`
Це створює політику, за якою TPM віддасть ключ, лише якщо BIOS, Option ROMs, UEFI-завантажувач і стан Secure Boot залишилися незмінними. Якщо зловмисник спробує завантажитися з флешки (змінивши PCR 4), TPM відмовиться розшифровувати ключ диска.

Віддалена атестація (Remote Attestation) дозволяє серверу довести віддаленій системі, що він завантажився у безпечному стані. TPM підписує значення PCR і Event Log своїм унікальним апаратним ключем (Attestation Identity Key, AIK), дозволяючи сторонньому серверу перевірити стан інфраструктури.

## Висновок

Вимірюване завантаження формує криптографічний доказ цілісності системи з моменту подачі живлення до запуску простору користувача. Спираючись на TPM 2.0 і його регістри PCR, системні адміністратори можуть будувати потужні механізми захисту від руткітів, буткітів та фізичних атак, гарантуючи, що ключі шифрування стають доступними лише у довіреному середовищі.
