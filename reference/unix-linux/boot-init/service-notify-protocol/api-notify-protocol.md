# 📋 Специфікація ключів та параметрів NOTIFY_SOCKET

Ця довідкова вставка визначає повний інтерфейсний контракт, формальні описи текстових ключів, параметрів оточення та матрицю авторизації доступу для протоколу сповіщення системного менеджера `systemd` (`sd_notify`). Вона слугує канонічним орієнтиром для розробників системного ПЗ, бібліотек та демонів, які інтегруються з автоматом станів системи.

## 1. Динамічні змінні оточення запуску

При виклику системного виклику `execve()` для запуску процесу служби, конфігурованої параметром `Type=notify` або з увімкненим моніторингом `WatchdogSec=`, системний менеджер `systemd` автоматично формує та передає у простір процесів юніта трійку спеціалізованих змінних оточення.

Першою та найважливішою є змінна `NOTIFY_SOCKET`. Вона містить текстовий шлях до створеного сокета локального міжпроцесного сполучення сімейства `AF_UNIX`. Цей шлях може бути двох фізичних типів. Перший тип — стандартний абсолютний шлях у системній файловій системі `tmpfs`, розташованій за адресою `/run/systemd/notify` або у спеціальному підкаталозі юніта. Другий тип — шлях в абстрактному просторі імен сокетів ядра Linux, який позначається префіксним символом `@` (наприклад, `@/org/freedesktop/systemd/notify/control`). При відкритті абстрактного сокета програма повинна замінити префіксний символ `@` на null-байт `\0` у першому елементі масиву `sun_path` структури `sockaddr_un`.

Другою змінною є `WATCHDOG_USEC`. Вона з'являється лише у випадку, якщо у конфігураційному файлі юніта визначено параметр `WatchdogSec=`. Змінна містить позитивне 64-бітне ціле число, яке задає часовий інтервал моніторингу сторожового таймера у мікросекундах (де 1 секунда дорівнює 1 000 000 мікросекунд). Служба зобов'язана зчитати це значення при старті, перетворити його у внутрішні одиниці часу свого циклу подій та встановити внутрішній таймер надсилання повідомлень `WATCHDOG=1` на інтервал, що не перевищує половину від `WATCHDOG_USEC`.

Третьою змінною є `WATCHDOG_PID`. Вона містить числовий ідентифікатор процесу (PID), від якого системний менеджер очікує надходження пакетів сторожового таймера. Якщо при отриманні датаграми з текстом `WATCHDOG=1` ідентифікатор відправника не збігається зі значенням `WATCHDOG_PID`, системний менеджер ігнорує таке повідомлення. Це запобігає ситуаціям, коли дочірні форкнуті процеси перехоплюють обов'язки сторожового моніторингу у головного демона.

Рекомендованим правилом для розробників є очищення цих змінних оточення за допомогою системних функцій `unsetenv()` одразу після створення та налаштування локального сокета. Це унеможливлює випадкове успадкування змінних `NOTIFY_SOCKET` та `WATCHDOG_USEC` дочірніми процесами, які запускає служба.

## 2. Сигнали готовності та життєвого циклу

Повідомлення у сокет `NOTIFY_SOCKET` передаються у вигляді простих текстових датаграм у кодуванні UTF-8. Кожен параметр складається з пари `КЛЮЧ=значення`, після якої обов'язково йде символ нового рядка `\n`. Один пакет `sendto()` або `sendmsg()` може містити один або декілька ключів, об'єднаних у єдиний текстовий блок.

Ключ `READY=1` є головним тригером автомата станів `systemd`. Його надсилання інформує менеджер про те, що процес повністю завершив власну внутрішню ініціалізацію: прочитав конфігураційні файли, виділив необхідні обсяги оперативної пам'яті, підключився до зовнішніх залежностей та прив'язав мережеві сокети. Отримавши `READY=1`, `systemd` переводить стан юніта з `activating` у `active` і знімає блокування із запуску інших служб, які мають залежність `After=` від даного юніта.

Ключ `RELOADING=1` використовується для сигналізації про початок гарячого перезавантаження конфігурації (наприклад, при отриманні сигналу `SIGHUP` або виклику `systemctl reload`). Отримавши цей ключ, `systemd` змінює стан юніта на `reloading`. Під час цього стану служба може додатково надсилати ключ `MONOTONIC_USEC=...`, передаючи значення монотонного годинника ядра `CLOCK_MONOTONIC` у мікросекундах. Це дозволяє менеджеру точніше синхронізувати часові рамки перезавантаження й уникати гонки станів при частих повторних викликах. Після завершення оновлення конфігурації служба зобов'язана знову надіслати `READY=1` для повернення в активний стан.

Ключ `STOPPING=1` надсилається службою на самому початку процедури планового зупинення процесу (Graceful Shutdown). Це дозволяє системному менеджеру негайно перевести юніт у стан `deactivating` і розпочати зупинку залежних юнітів, не чекаючи фізичного завершення основного процесу та виходу з виклику `exit()`.

## 3. Сигнали діагностики, моніторингу та розширення тайм-аутів

Для підвищення прозорості роботи демонів для системних адміністраторів протокол підтримує передачу динамічних метаданих стану через ключ `STATUS=...`. Значенням цього ключа є довільний текстовий рядок UTF-8 (наприклад, `STATUS=Processing 42 requests/sec, memory usage: 115MB`). Отримавши такий пакет, `systemd` оновлює текстову властивість `StatusText` об'єкта D-Bus юніта і виводить її при виконанні команд `systemctl status` або `systemctl list-units`. Рядок статусу можна оновлювати без обмежень у будь-який момент часу життя процесу.

У разі виникнення фатальних помилок під час ініціалізації або виконання служба може повідомити менеджеру точні коди аварійного завершення до того, як процес виконає вихід. Для цього використовуються ключі `ERRNO=...` та `BUSERROR=...`. Ключ `ERRNO=` приймає ціле число системної помилки POSIX (наприклад, `ERRNO=2` для `ENOENT` або `ERRNO=111` для `ECONNREFUSED`). Ключ `BUSERROR=` приймає канонічний текстовий рядок помилки з підсистеми D-Bus (наприклад, `BUSERROR=org.freedesktop.DBus.Error.AccessDenied`). Ці дані фіксуються в системному журналі `journald` та полегшують діагностику причин відмови без необхідності аналізу довгих лог-файлів.

Окремим критичним інструментом для тривалих процедур є ключ `EXTEND_TIMEOUT_USEC=...`. Якщо служба під час стартів чи перезавантажень виконує тривалу миграцію бази даних або перевірку цілісності файлів, вона ризикує перевищити стандартний тайм-аут `TimeoutStartSec=` (за замовчуванням 90 секунд). Надсилаючи `EXTEND_TIMEOUT_USEC=10000000`, служба запитує у `systemd` продовження очікування ще на 10 секунд від поточного моменту часу. Служба може надсилати цей ключ періодично в процесі виконання важкої операції, гарантуючи, що системний менеджер не вб'є процес через вичерпання ліміту часу.

## 4. Механізм моніторингу надійності Watchdog

Механізм сторожового моніторингу спирається на регулярне надсилання ключа `WATCHDOG=1`. Це повідомлення слугує сигналом серцебиття (heartbeat). Отримавши його, `systemd` скидає внутрішній таймер зворотного відліку `WatchdogSec`.

Якщо служба зазнала взаємного блокування (deadlock) або безкінечного циклу, вона припиняє надсилати `WATCHDOG=1`. Після вичерпання інтервалу `WatchdogSec` системний менеджер фіксує відмову і надсилає процесу сигнал `SIGABRT`. Обробка `SIGABRT` за замовчуванням примушує ядро згенерувати аварійний дамп оперативної пам'яті (coredump), який зберігається у `systemd-coredumpd` для подальшого аналізу у налагоджувачі `gdb`.

У спеціальних випадках, коли служба сама виявляє внутрішнє непереборне пошкодження даних або порушення цілісності структур, вона може примусово ініціювати процедуру аварійного відновлення, надіславши ключ `WATCHDOG=trigger`. Це змушує `systemd` негайно активувати сценарій аварійної зупинки та перезапуску за правилом `Restart=`.

## 5. Протокол сховища файлових дескрипторів FDSTORE

Для реалізації перезапуску служб із нульовим часом простою (Zero Downtime Restarts) протокол `sd_notify` надає можливість передавати відкриті файлові дескриптори на збереження системному менеджеру.

Для передачі дескриптора служба формує датаграму `AF_UNIX` з текстовим ключем `FDSTORE=1`. Одночасно за допомогою системного виклику `sendmsg()` у допоміжне поле структури `msghdr` (поле `msg_control`) вкладається управляюче повідомлення з типом `SCM_RIGHTS`, яке містить один або декілька відкритих файлових дескрипторів. Ядро Linux здійснює дублювання посилань на файлові таблиці в простір процесів `systemd` (PID 1).

Служба може супроводжувати передачу додатковими ключами:
- `FDNAME=...`: Задає текстове ім'я файлового дескриптора (наприклад, `FDNAME=http-socket` або `FDNAME=db-connection`). Це дозволяє новій версії процесу ідентифікувати дескриптори за призначенням при їх зчитуванні.
- `FDPOLL=1`: Вказує `systemd` здійснювати моніторинг подієвих запитів (I/O events) на збережених сокетах за допомогою `epoll` під час відсутності процесу служби.
- `FDSTOREREMOVE=1`: Інформує системний менеджер про необхідність видалити зі сховища раніше збережені файлові дескриптори, що відповідають імені, вказаному в `FDNAME=`.

Додатковим елементом синхронізації є ключ `BARRIER=1`. Оскільки датаграмні сокети є асинхронними, процес може надіслати `BARRIER=1` для створення бар'єра послідовності. Отримавши `BARRIER=1`, системний менеджер гарантує, що всі попередні датаграми повністю опрацьовані, й надсилає у відповідний сокет підтвердження.

## 6. Політики доступу NotifyAccess

Конфігураційний параметр `NotifyAccess=` у секції `[Service]` задає правила фільтрації пакетів на основі ядерних облікових даних `ucred` та ієрархії контрольних груп cgroups v2:

- `main`: Системний менеджер приймає датаграми виключно від основного процесу служби, чий PID збігається з значенням `MAINPID` або первинним процесом, запущеним через `ExecStart=`. Датаграми від дочірніх процесів та інших членів cgroup відкидаються.
- `exec`: Приймаються повідомлення від будь-якого процесу, породженого `systemd` у межах даного юніта. Це дозволяє використовувати `sd_notify` у підготовчих скриптах `ExecStartPre=` та завершальних скриптах `ExecStartPost=`.
- `all`: Приймаються датаграми від абсолютно будь-якого процесу, який фізично знаходиться всередині cgroup цього юніта. Цей режим є необхідним для багатопроцесних архітектур з демонами-майстрами та воркерами.
- `none`: Усі датаграми, що надходять у `NOTIFY_SOCKET`, повністю ігноруються системним менеджером.
