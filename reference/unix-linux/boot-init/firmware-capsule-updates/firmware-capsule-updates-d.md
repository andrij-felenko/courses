Уявіть ситуацію: ви керуєте парком із сотень серверів або тисяч корпоративних лептопів, і раптом виробник випускає критичне оновлення прошивки, яке виправляє серйозну вразливість на рівні SMM (System Management Mode) або мікрокоду процесора. Традиційний підхід вимагав би від системного адміністратора завантажувати спеціальні ISO-образи, створювати завантажувальні USB-накопичувачі на базі DOS або Windows PE, і фізично обходити кожну машину, вручну запускаючи пропрієтарні утиліти прошивки, часто сподіваючись, що випадкове вимкнення електроенергії не перетворить материнську плату на «цеглу». Це не просто довго — це фундаментально несумісно з сучасними вимогами до автоматизації, CI/CD для інфраструктури та управління конфігураціями. Саме цю прірву між апаратним забезпеченням та сучасним управлінням парком пристроїв покликаний подолати стандарт UEFI Capsule Updates у симбіозі з інфраструктурою Linux (fwupd).

Сучасний підхід дозволяє встановлювати оновлення BIOS/UEFI, прошивки NVMe-накопичувачів, контролерів Thunderbolt та навіть периферійних пристроїв так само просто, як ви оновлюєте звичайні програмні пакети через `apt` чи `dnf`. Проте під капотом цієї «магії» лежить складна архітектура взаємодії між сервісами простору користувача, драйверами ядра Linux, специфікаціями ACPI/UEFI та самим обладнанням.

## Анатомія UEFI Capsule Update

Перш ніж заглиблюватися в інструментарій рівня ОС, важливо зрозуміти, що таке «капсула» (capsule) в контексті UEFI. UEFI Capsule — це стандартизований формат контейнера для передачі даних від операційної системи до firmware. Вона розроблена не лише для оновлень прошивки, але й для передачі будь-якої інформації, яку ОС хоче передати UEFI для обробки під час наступного перезавантаження або навіть під час виконання (runtime).

### Механізм передачі

Специфікація UEFI визначає сервіс часу виконання (Runtime Service) під назвою `UpdateCapsule()`. ОС може викликати цю функцію, передаючи їй масив вказівників на капсули. Проте, виклик `UpdateCapsule()` сам по собі рідко виконує саме прошивання флеш-пам'яті (SPI flash) миттєво під час роботи повноцінної ОС. Причина криється в безпеці та стабільності: прошивання часто вимагає доступу до регістрів апаратного забезпечення, які можуть конфліктувати з драйверами ОС, або вимагає переведення системи в специфічний режим (наприклад, SMM), що може спричинити значні затримки і порушити роботу ядра реального часу або переривань.

Тому стандартний пайплайн оновлення через капсулу виглядає так:

1. **Доставка в пам'ять**: ОС завантажує файл капсули в оперативну пам'ять.
2. **Виклик UpdateCapsule()**: Ядро Linux викликає UEFI Runtime Service `UpdateCapsule()`. UEFI перевіряє базову цілісність капсули і фіксує її розташування в пам'яті (часто використовуючи NVRAM змінні `CapsuleUpdateData`).
3. **Перезавантаження**: ОС ініціює перезавантаження системи (Warm Reset). Важливо, що під час перезавантаження вміст оперативної пам'яті, де лежить капсула, не повинен бути очищений.
4. **Обробка в PEI/DXE фазах**: Після ребуту, на дуже ранніх етапах завантаження (PEI - Pre-EFI Initialization або DXE - Driver Execution Environment), прошивка виявляє наявність очікуючої капсули.
5. **Автентифікація та прошивання**: UEFI перевіряє цифровий підпис капсули. Якщо підпис валідний і належить довіреному розробнику (зазвичай використовується публічний ключ виробника, вшитий у сам BIOS), спеціальний драйвер UEFI виконує фактичне стирання та запис SPI flash-пам'яті.
6. **Очищення та нормальне завантаження**: Після успішного (або неуспішного) оновлення, змінні стираються, і система продовжує звичайне завантаження.

### ESRT (EFI System Resource Table)

Для того, щоб ОС могла взаємодіяти з прошивкою, їй потрібно знати, які саме пристрої підтримують оновлення через капсули, їхні поточні версії та ідентифікатори. Для цього UEFI надає таблицю ESRT. 

ESRT публікується прошивкою під час завантаження і містить масив записів (entries), кожен з яких описує один ресурс прошивки (System Resource).
Кожен запис ESRT містить ключові поля:
- **FwClassId**: Унікальний ідентифікатор GUID (Globally Unique Identifier), що представляє клас пристрою (наприклад, системний BIOS конкретної моделі материнської плати).
- **FwType**: Тип ресурсу (системна прошивка, прошивка пристрою, тощо).
- **FwVersion**: Поточна версія прошивки (зазвичай 32-бітне ціле число).
- **LowestSupportedFwVersion**: Мінімальна версія прошивки, до якої дозволено відкат (для запобігання downgrade-атакам на вразливі старі версії).
- **CapsuleFlags**: Прапорці, що вказують на особливості застосування капсули (наприклад, чи вимагається перезавантаження).
- **LastAttemptVersion** та **LastAttemptStatus**: Дозволяють ОС дізнатися, чи було попереднє оновлення успішним, і якщо ні — який код помилки повернула прошивка (наприклад, помилка валідації підпису).

В Linux ядро читає ESRT і експортує її вміст у простір користувача через `sysfs`. Ви можете дослідити це самостійно:

```bash
ls /sys/firmware/efi/esrt/entries/
```

Кожна підтека відповідає одному `FwClassId` (GUID). Всередині теки ви знайдете файли `fw_version`, `last_attempt_status`, `lowest_supported_fw_version` тощо. Саме звідси користувацькі інструменти на кшталт `fwupd` дізнаються про поточний стан системи.

## Інфраструктура Linux: fwupd та LVFS

У той час як UEFI надає низькорівневий механізм (`UpdateCapsule` + `ESRT`), у просторі користувача потрібен потужний рушій для управління процесом. Раніше виробники надавали власні скрипти або бінарні файли (часто закриті), які спілкувалися з драйверами ядра. Це призводило до хаосу. Рішенням став проект **fwupd**.

`fwupd` — це системний демон (зазвичай працює як `fwupd.service` під управлінням systemd), який надає універсальний D-Bus інтерфейс для управління прошивками. Його головна філософія — створити єдиний абстрактний шар над безліччю різноманітних протоколів оновлення.

### Роль LVFS (Linux Vendor Firmware Service)

Звідки `fwupd` бере самі файли прошивок? Вони завантажуються з LVFS (fwupd.org) — безпечного хмарного порталу, куди виробники обладнання (Dell, Lenovo, HP, Logitech тощо) завантажують свої прошивки у форматі `.cab` (Cabinet).
Кожен `.cab` архів містить:
1. Сам файл прошивки (наприклад, бінарник `firmware.cap`).
2. Файл метаданих `firmware.metainfo.xml` у форматі AppStream, який описує прошивку: версію, ченджлог, рівень критичності та списки підтримуваних пристроїв (за їх `FwClassId` GUID або іншими апаратними ідентифікаторами: Vendor ID/Device ID).

Процес оновлення з точки зору користувача виглядає елегантно просто. Команда `fwupdmgr refresh` завантажує глобальний підписаний каталог метаданих з LVFS. Команда `fwupdmgr get-updates` порівнює локальні ідентифікатори пристроїв (зчитані демоном через `sysfs`, `udev`, USB/PCI шини) з каталогом LVFS. Якщо є збіг — пропонується оновлення. Команда `fwupdmgr update` завантажує потрібні `.cab` файли, розпаковує їх і передає до ядра.

### Плагінна архітектура fwupd

Важливо розуміти, що UEFI Capsule — це лише один (хоч і найважливіший для материнських плат) з багатьох методів оновлення, які підтримує `fwupd`. Архітектура демона побудована на плагінах. Під час старту `fwupd` завантажує десятки плагінів (у `/usr/lib/fwupd-plugins/`). 

Серед ключових плагінів:
- **uefi_capsule**: Працює з `/sys/firmware/efi/esrt/` та драйвером ядра `efi_capsule_loader`. Використовується для системного BIOS.
- **nvme**: Спілкується безпосередньо з NVMe контролерами через NVMe MI (Management Interface) команди за допомогою `ioctl()` до пристроїв `/dev/nvmeX`.
- **thunderbolt**: Оновлює прошивки контролерів Intel Thunderbolt, використовуючи специфічні інтерфейси `/sys/bus/thunderbolt/`.
- **synaptics_mst**, **logitech_hidpp**, **colorhug**, **wacom_usb** тощо: Плагіни для периферії, що реалізують пропрієтарні протоколи по USB.

Ось чому `fwupd` став індустріальним стандартом: розробнику ОС не потрібно писати окремі інструменти для мишки, SSD та BIOS — усе покривається єдиним демоном.

### Шлях капсули через ядро: efi_capsule_loader

Як саме `fwupd` (точніше, плагін `uefi_capsule`) передає капсулу до UEFI? У ядрі Linux існує спеціальний драйвер `efi_capsule_loader`, який створює character device вузол `/dev/efi_capsule_loader`.

1. `fwupd` розпаковує капсулу з `.cab` архіву.
2. Він відкриває `/dev/efi_capsule_loader` на запис.
3. `fwupd` записує байти капсули у цей пристрій пакетами.
4. Ядро, отримуючи ці дані, виділяє буфери пам'яті, гарантуючи, що вони відповідають вимогам UEFI (наприклад, безперервність фізичної пам'яті, якщо це вимагається, хоча сучасні реалізації підтримують scatter-gather списки).
5. Після завершення запису (файл закривається), ядро встановлює необхідні прапорці і змінні EFI (наприклад `OsIndications`, щоб сказати прошивці про необхідність обробити капсулу після перезавантаження).
6. ОС перезавантажується.

Завдяки цьому механізму простору користувача не потрібно безпосередньо маніпулювати сирою фізичною пам'яттю чи викликати складні ассемблерні переривання.

## Особливості та підводні камені

### Secure Boot та оновлення dbx

Однією з критичних функцій `fwupd` є доставка оновлень для бази відкликаних сертифікатів Secure Boot — **dbx** (Forbidden Signature Database). Якщо виявляється вразливість у певному завантажувачі (наприклад, гучні вразливості GRUB "BootHole" або "BlackLotus"), Microsoft (яка де-факто є довіреним коренем для більшості ПК) випускає оновлення списку відкликаних хешів/сертифікатів.

`fwupd` має окремий плагін `uefi_dbx`. Цікаво, що оновлення змінних Secure Boot (таких як `db` та `dbx`) в UEFI також може здійснюватися за допомогою механізму, дуже схожого на Capsule Update, або через аутентифіковані змінні (Authenticated Variables). `fwupd` формує спеціальний payload, підписаний KEK (Key Exchange Key, зазвичай належить Microsoft), і передає його прошивці. UEFI перевіряє підпис KEK, і якщо він збігається, додає нові записи до `dbx`. Це критичний механізм захисту від завантаження компрометованих старих ядер або завантажувачів.

### Оновлення NVMe без перезавантаження

На відміну від UEFI BIOS, де перезавантаження обов'язкове, багато сучасних NVMe SSD підтримують оновлення прошивки "на льоту". Специфікація NVMe визначає команди "Firmware Image Download" та "Firmware Commit". 

Плагін `nvme` у `fwupd`:
1. Розбиває прошивку на шматки (chunks) по кілька кілобайт (залежить від параметра MDTS контролера).
2. Відправляє кожен шматок через `NVME_IOCTL_ADMIN_CMD` з опкодом `0x10` (Download). SSD записує їх у свій тимчасовий буфер.
3. Після завантаження відправляється команда Commit (`0x11`). Контролер SSD верифікує підпис (криптографічний підпис самої прошивки накопичувача) та записує образ у flash-пам'ять пристрою (Firmware Slot).

Багато enterprise-накопичувачів дозволяють активувати новий Firmware Slot без перезавантаження системи (Firmware Activation without Reset). Однак, на споживчих десктопних системах, часто все одно потрібен power-cycle (повне вимкнення та увімкнення), щоб контролер перевантажився з нової мікросхеми ROM. `fwupd` коректно зчитує ці можливості пристрою з ідентифікаційних структур NVMe і повідомляє користувачеві, чи потрібне перезавантаження.

### Утиліти командного рядка: fwupdmgr vs fwupdtool

Важливо розрізняти два інструменти CLI, які постачаються з пакетом fwupd:
- **`fwupdmgr`**: Це клієнт високого рівня. Він **не** спілкується з обладнанням напряму. Замість цього він підключається до системного демона `fwupd.service` через D-Bus. Це правильний і найбезпечніший шлях, який гарантує, що не буде конфліктів конкурентного доступу (race conditions), якщо інший процес спробує отримати доступ до того ж обладнання.
- **`fwupdtool`**: Це інструмент розробника та відлагодження. Він ігнорує демона (ба більше, вимагає зупинити `fwupd.service` перед запуском) і самостійно завантажує плагіни у свій процес, взаємодіючи з обладнанням "безпосередньо". Його використовують розробники для тестування нових пристроїв (наприклад `fwupdtool firmware-read` для зчитування існуючої прошивки, якщо пристрій це дозволяє) або системні адміністратори для жорсткого відновлення (recovery).

## Діагностика збоїв оновлення

Незважаючи на високу надійність стандарту, капсульні оновлення можуть давати збої. Типовий сценарій: користувач запускає `fwupdmgr update`, погоджується на перезавантаження, система перезавантажується... і нічого не відбувається. Версія BIOS залишається старою.

Де шукати проблему?

1. **Журнали UEFI/ESRT**: Одразу після невдалого завантаження перевірте `sysfs`.
   ```bash
   cat /sys/firmware/efi/esrt/entries/<GUID>/last_attempt_status
   ```
   Якщо значення `0` — прошивка вважає, що все успішно. Значення `1` означає відсутність помилок, `2` - "Unsuccessful", `3` - "Insufficient Resources" (не вистачило пам'яті для розгортання капсули в SMM), `4` - "Incorrect Version" (спроба даунгрейду заблокована LowestSupportedFwVersion), `5` - "Invalid Format", `6` - "Auth Error" (проблема з цифровим підписом капсули). Важливий також стан `7` - "Power Event, AC not connected" — багато BIOS-ів жорстко вимагають підключення до електромережі, навіть якщо батарея заряджена на 100%.

2. **Dmesg та EFIVAR**: Перевірте логи ядра.
   ```bash
   dmesg | grep -i efi
   ```
   Можливо, `efi_capsule_loader` не зміг виділити безперервний блок пам'яті. Це іноді трапляється на системах, які довго працювали без перезавантаження (висока фрагментація пам'яті). Тимчасове рішення — перезавантажити систему і спробувати застосувати оновлення відразу після свіжого старту.

3. **Secure Boot / Підписи**: Якщо `last_attempt_status` вказує на помилку аутентифікації (`6`), проблема може бути в тому, що виробник змінив ключі підпису для нових версій BIOS, але стара версія BIOS про ці ключі не знає. Іноді вимагається проміжне оновлення до певної версії (bridge update), перш ніж стрибати на останню.

4. **Логи fwupd демона**:
   Демон веде детальний журнал. Запуск його в режимі відлагодження може дати багато інформації:
   ```bash
   systemctl stop fwupd
   /usr/libexec/fwupd/fwupd --verbose
   ```
   Або через `journalctl -u fwupd --priority=debug`.

## Підсумок та еволюція

Впровадження UEFI Capsule Updates та екосистеми fwupd здійснило тиху, але монументальну революцію в адмініструванні Linux. Те, що колись вважалося ризикованим "чорним мистецтвом" (прошивання BIOS), тепер інтегровано в звичайний цикл управління патчами. У корпоративному світі це дозволяє інтегрувати оновлення прошивок у системи на кшталт Ansible, Puppet або Fleet Management платформи. Більше того, це стимулює виробників апаратного забезпечення (IHVs) дотримуватися відкритих стандартів (ESRT) замість винаходу власних милиць для Windows.

Еволюція триває. Сучасні напрямки розвитку включають Redfish Host Interface для Out-of-Band оновлень на серверах, більшу гранулярність оновлень (окреме оновлення Intel ME/CSME, мікрокодів, EC - Embedded Controllers) та глибшу інтеграцію з TPM 2.0 для вимірювання (Measurement) цілісності самої капсули перед її виконанням (Measured Boot). Розуміння цих механізмів є обов'язковим для системних інженерів, які прагнуть будувати надійну та безпечну інфраструктуру.
