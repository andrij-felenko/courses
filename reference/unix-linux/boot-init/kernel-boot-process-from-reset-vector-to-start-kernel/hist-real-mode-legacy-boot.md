# 📜 Історія x86: від вектора 8086 і лінії A20 до EFI Stub

Ця історія описує, як сорокарічна спадщина 16-бітного процесора Intel 8086 сформувала протокол завантаження ядра Linux та чому сучасне ядро досі несе в собі сліди боротьби з вентилем A20, обмеженнями real mode і спадковими перериваннями BIOS.

Коли 1978 року компанія Intel випустила 16-бітний процесор 8086, він мав лише 20-бітну шину адреси. Це означало, що процесор міг адресувати максимум `2²⁰ = 1 048 576` байтів (рівно 1 Мегабайт) фізичної пам'яті. Щоб звернутися до всієї цієї пам'яті через 16-бітні регістярі, інженери створили систему **сегментації**: фізична адреса обчислювалася як `(Сегмент << 4) + Зсув`.

Під час подачі живлення процесор 8086 починав виконання з фіксованої адреси, відомої як **вектор скидання** (Reset Vector). У процесорі 8086 у сегментний регістр CS заносилося значення `0xFFFF`, а у вказівник інструкцій IP — `0x0000`. Згідно з формулою сегментації, адреса першої інструкції становила `(0xFFFF << 4) + 0x0000 = 0xFFFF0`, що лежить рівно за 16 байтів до межі 1 Мегабайта. Творці системних плат розміщували мікросхему ПЗП (ROM BIOS) у найвищій області пам'яті, і за адресою `0xFFFF0` завжди стояла перша інструкція безумовного фар-джампу (`jmp far`) на початок процедур перевірки обладнання (POST — Power-On Self-Test).

## Парадокс лінії A20 та зациклення пам'яті

Найбільша адреса, яку можна було сформувати в реальному режимі (Real Mode) на 8086, виникала при `CS = 0xFFFF` та `IP = 0xFFFF`:

```
(0xFFFF << 4) + 0xFFFF = 0x10FFEF (1 114 095 байтів)
```

Ця адреса виходила за межі 1 МБ (тобто за `0xFFFFF`). Оскільки процесор 8086 мав лише 20 фізичних ліній адреси (від `A0` до `A19`), 21-й біт (лінія `A20`) був відсутній у кремнії. Переповнення старшого біта просто відкидалося, і адреса `0x10FFEF` перетворювалася на `0x00FFEF` — тобто виконання "зациклювалося" назад на початок першої 64-кілобайтної сторінки RAM (High Memory Area / HMA).

Багато програмістів того часу (зокрема розробники DOS-програм) використали це апаратне зациклення як особливість і будували на ньому логіку адресації своїх програм, розраховуючи, що звернення вище 1 МБ автоматично потрапляє на перші кілобайти оперативної пам'яті.

У 1982 році з'явився процесор Intel 80286 із 24-бітною шиною адреси. На ньому адреса `0x10FFEF` уже не зациклювалася, а чесно зверталася до 65 520 байтів вище межі 1 МБ. Це раптово зламало сумісність із численними програмами MS-DOS.

Щоб зберегти зворотну сумісність, інженери IBM під час розробки персонального комп'ютера IBM PC/AT вбудували на материнську плату спеціальний вентиль (Gate A20), підключений до вільного піна мікроконтролера клавіатури Intel 8042. Якщо вентиль був закритий, лінія `A20` примусово заземлювалася (логічний 0), і процесор поводився як 8086, відсікаючи 21-й біт. Для доступу до пам'яті вище 1 МБ програма мусила надіслати повільну послідовність команд контролеру клавіатуричерез порти `0x60` та `0x64`, щоб той відкрив вентиль A20.

На пізніших чипсетах з'явився так званий FAST A20 Gate через системний порт `0x92`, який дозволяв перемикати лінію A20 без очікування повільного контролера клавіатури, проте затримка все одно залишалася відчутною для раннього коду завантажувачів.

## Перші дні Linux: bootsect.S та setup.S

Коли Лінус Торвальдс створював Linux у 1991 році для процесорів Intel 80386, ядро завантажувалося безпосередньо з дискети 1.44 МБ. Образ ядра складався з трьох окремих частин:

1. `bootsect.S` — 512-байтний завантажувальний сектор (Sector 0), який зчитував решту ядра за допомогою BIOS-переривання `int 0x13`.
2. `setup.S` — 16-бітний real mode код, який опитував BIOS про обсяг RAM, відеорежими, відкривав вентиль A20 і перемикав процесор у 32-бітний захищений режим (Protected Mode).
3. `head.S` — 32-бітний код, який ініціалізував таблиці сторінок і викликав `start_kernel()`.

Коли ядра збільшилися й перестали вміщатися в 512 кілобайтів "низької" пам'яті (Conventional Memory нижче 1 МБ), було створено формат **bzImage** (Big zImage). У ньому стиснуте ядро розміщувалося вище межі 1 МБ (High Memory), а 16-бітний `setup.S` виконував складну маніпуляцію: зчитував дані через реальний режим, вмикав A20, переходив у Protected Mode, переносив дані у верхню пам'ять і знову повертався в Real Mode для виклику інших переривань BIOS.

Еволюція завантажувачів Linux проходила крізь кілька поколінь:
- **LILO (Linux Loader)**: зчитував ядро за списком точних секторів диска. Якщо файл ядра дефрагментувався чи пересувався, машина зупинялася з помилкою `LI`.
- **LOADLIN**: утиліта DOS, яка дозволяла запускати ядро Linux прямо з командного рядка MS-DOS.
- **SYSLINUX / ISOLINUX / PXELINUX**: родина завантажувачів Х. Пітера Анвіна для завантаження з FAT, ISO-дисків та мережі PXE.
- **GRUB (Grand Unified Bootloader)**: ввів повноцінне розуміння файлових систем (ext2/3/4, btrfs, xfs), дозволивши вибирати образи через графічне меню.

## Відміна Real Mode: народження EFI Stub

З появою 64-бітних систем x86_64 та специфікації UEFI старий 16-бітний режим завантаження перетворився на важкий архаїзм. UEFI виконує свій код одразу у 64-бітному режимі з увімкненим MMU і таблицями сторінок.

Щоб не повертати 64-бітний процесор назад у 16-бітний real mode лише для виконання `setup.S`, розробники ядра створили **Linux EFI Boot Stub**. Це спеціальний заголовок усередині образу `vmlinuz`, який містить PE/COFF-структуру. UEFI сприймає файл ядра як звичайний 64-бітний виконуваний файл EFI.

Коли UEFI завантажує ядро через EFI Stub, точка входу `efi_pe_entry` приймає керування одразу в 64-бітному режимі. Спадковий код `setup.S` взагалі не виконується, вентиль A20 відсутній у сучасних чипсетах, а передача параметрів відбувається через структури EFI Boot Services. Проте внутрішній заголовок `boot_params` досі зберігає поля, сформовані ще за часів MS-DOS та 8086, забезпечуючи зворотну сумісність усіх завантажувачів Linux.
