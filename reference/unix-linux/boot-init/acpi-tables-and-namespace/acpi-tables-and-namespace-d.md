Коли ядро Linux завантажується на сучасній материнській платі з процесором x86_64 або ARM64, у бінарному файлі ядра немає жодної жорстко зашитої інформації про фізичні адреси регістрів контролера живлення, термальних датчиків, кнопок вимкнення чи ліній переривань даної конкретної платформи. Спроба ядра прочитати чи записати дані за стабільно зафіксованими адресами (на кшталт портів вводу-виводу legacy-архітектури) призвела б до негайного зависання або аварійної паніки ядра (kernel panic) на будь-якій платі іншої ревізії чи іншого виробника. Для того щоб операційна система могла динамічно виявити конфігурацію материнської плати та керувати її енергоспоживанням без компіляції окремого ядра під кожну модель ноутбука чи сервера, прошивка UEFI передає операційній системі набір структурованих таблиць ACPI та машино-незалежний байт-код AML.

Стандарт ACPI (Advanced Configuration and Power Interface) розв'язує цю проблему шляхом чіткого розподілу відповідальності між прошивкою та ядром. Прошивка завантажує в оперативну пам'ять статичні структури даних (статичні таблиці), які описують фізичну топологію заліза, та динамічний байт-код AML (ACPI Machine Language), що визначає процедури ініціалізації та зміну станів живлення. Ядро операційної системи містить вбудовану віртуальну машину (інтерпретатор ACPICA), яка парсить ці структури, будує в пам'яті ієрархічне дерево об'єктів (ACPI Namespace) і виконує AML-методи для взаємодії з апаратурою.

## 1. Концепція OSPM та усунення залежності від прошивки

До появи ACPI управління живленням та конфігурацією заліза базувалося на застарілих стандартах APM (Advanced Power Management) та PnP BIOS. У цій архітектурі вся логіка керування перебувала всередині прошивки BIOS. Коли операційна система простоювала, вона викликала переривання BIOS (`INT 15h`), і прошивка самостійно вирішувала, коли перевести процесор або жорсткий диск у режим сну.

Такий підхід створював фундаментальний конфлікт: прошивка BIOS не мала жодної уяви про фонові задачі ядра, підключені мережеві сокети, відкриті файлові дескриптори чи стан системного планувальника, що призводило до помилкових присиплянь пристроїв під час активних обчислень або незворотних зависань під час пробудження. Окрім цього, виклики BIOS виконувалися у 16-бітному реальному режимі з блокуванням переривань, що унеможливлювало їхнє безпечне використання у багатопроцесорних (SMP) системах, де кілька ядер могли одночасно спробувати виконати виклик BIOS.

З появою специфікації ACPI у 1996 році відбувся архітектурний перехід до концепції **OSPM (OS-directed Configuration and Power Management)**. Головним принципом OSPM є те, що прошивка комп'ютера перестає бути активним контролером заліза після завершення етапу boot. Вона лише надає пасивний опис платформи у формі таблиць та байт-коду, а ядро ОС стає єдиним центральним органом, який приймає рішення про перехід пристроїв у стани енергозбереження (D0–D3) та всієї системи у системні стани сну (S0–S5).

Завдяки концепції OSPM системний планувальник ядра Linux (`sched`), підсистеми керування частотою процесора (`cpufreq`), простою процесора (`cpuidle`) та загальний каркас управління живленням пристроїв (`dev_pm_ops`) узгоджено приймають рішення про вимкнення неактивних блоків платформи.

Детальний аналіз конфліктів між BIOS та ядром ОС, а також еволюційний шлях від 16-бітних викликів APM до стандарту ACPI 6.x викладено в матеріалі [📜 Від APM до ACPI: як операційна система забрала контроль над залізом у прошивки](book:unix-linux/acpi-tables-and-namespace/hist-apm-to-acpi.md).

## 2. Ієрархія таблиць ACPI: від RSDP до DSDT та SSDT

Під час ранньої фази завантаження (рання ініціалізація ядра) підсистема ACPI повинна знайти початкову точну структуру в оперативній пам'яті та побудувати повний граф системних таблиць.

![Ієрархія статичних та динамічних таблиць ACPI](/reference/unix-linux/boot-init/acpi-tables-and-namespace/img/acpi-tables.svg)
*_Рис. 1. Деревоподібна зв'язаність статичних таблиць та DSDT/SSDT з AML-кодом_*

### Пошук точки входу: RSDP (Root System Description Pointer)

Знаходження ACPI починається з пошуку структури **RSDP**. 

1. **В умовах UEFI:** Завантажувач передає ядру адресу RSDP через таблицю конфігурацій UEFI (`EFI_ACPI_20_TABLE_GUID` або `EFI_ACPI_TABLE_GUID`).
2. **В умовах Legacy BIOS:** Ядро сканує перші 1 Кілобайт області EBDA (Extended BIOS Data Area) або діапазон пам'яті фізичних адрес від `0x000E0000` до `0x000FFFFF` у пошуках 8-байтової сигнатури `"RSD PTR "`.

RSDP містить ревізію стандарту, 8-бітну контрольну суму та фізичну адресу головної описової таблиці. У версії ACPI 1.0 це 32-бітна адреса таблиці RSDT, а починаючи з ACPI 2.0 додається 64-бітна адреса таблиці XSDT.

### Таблиці RSDT та XSDT

Таблиця **RSDT (Root System Description Table)** містить масив 32-бітних фізичних адрес, кожна з яких вказує на окрему системну таблицю опису заліза. Оскільки на сучасних 64-бітних платформах адреси таблиць у пам'яті можуть розташовуватися вище межі 4 Гігабайтів, специфікація ACPI 2.0 ввела таблицю **XSDT (Extended System Description Table)**, яка виконує аналогічну роль, але містить масив 64-бітних pointer'ів. Якщо ядро виявляє валідну таблицю XSDT, воно повністю ігнорує 32-бітну RSDT.

Кожна системна таблиця, на яку вказує XSDT, починається зі стандартного 36-байтового заголовка `ACPI_TABLE_HEADER`. Цей заголовок містить 4-символьну сигнатуру ASCII (наприклад, `"FACP"`, `"APIC"`, `"MCFG"`), довжину всієї структури у байтах, ревізію, OEM-ідентифікатори та 8-бітну контрольну суму (checksum). Сума всіх байтів валідної таблиці за модулем 256 повинна давати точний нуль.

### Ключові статичні таблиці платформи

Отримавши масив адрес із XSDT, ядро послідовно читає та перевіряє сигнатури ключових статичних таблиць:

* **FADT (Fixed ACPI Description Table / FACP):** Найважливіша статична таблиця системи. Вона містить фізичні адреси блоків регістрів управління живленням (`PM1a_EVT_BLK`, `PM1a_CNT_BLK`, `PM_TMR_BLK`), порти команд SMI, інформацію про прапорці архітектури (Hardware Reduced ACPI, 8042 PS/2 controller presence), а також вказівники на структури `FACS` (Firmware ACPI Control Structure) та динамічну таблицю `DSDT`.
* **MADT (Multiple APIC Description Table / APIC):** Описує апаратну конфігурацію контролерів переривань у багатопроцесорних системах. Вона містить перелік усіх фізичних та логічних процесорних ядер (Local APIC ID), контролерів переривань вводу-виводу (I/O APIC), а також перерозподіл ліній переривань (Interrupt Source Overrides). Ядро Linux використовує MADT для ініціалізації симетричної багатопроцесорності (SMP) та налаштування маршрутизації IRQ.
* **MCFG (Memory Mapped Configuration Space Access Table):** Передає ядру базові фізичні адреси для доступу до розширеного конфігураційного простору PCI Express через механізм ECAM (Enhanced Configuration Access Mechanism), дозволяючи читати регістри PCI без використання застарілих I/O портів `0xCF8`/`0xCFC`.
* **SRAT (System Resource Affinity Table) та SLIT (System Locality Distance Information Table):** Описують фізичну топологію NUMA-систем — зв'язок між процесорними ядрами, модулями оперативної пам'яті та пристроями вводу-виводу, а також відносні затримки доступу між NUMA-вузлами.

### Динамічні таблиці: DSDT та SSDT

На відміну від статичних таблиць, які містять лише структури даних та адреси, **DSDT (Differentiated System Description Table)** та **SSDT (Secondary System Description Table)** містять виконуваний байт-код AML.

* **DSDT:** Серце динамічної підсистеми ACPI. Ця таблиця створюється розробником материнської плати і містить опис базового обладнання, системних шин (PCI, I2C, SPI), топології живлення та методів ініціалізації.
* **SSDT:** Модульні доповнення до DSDT. Вони використовуються для розбиття коду опису заліза на окремі блоки (наприклад, один SSDT описує параметри процесорного гнізда, інший — дискретну відеокарту). Крім того, SSDT можуть динамічно завантажуватися ядром під час роботи системи при підключенні гарячих пристроїв Thunderbolt, USB4 або PCI Express Hot-Plug.

Детальні двійкові опис-структури C/C++ для RSDP, FADT, MADT та універсальної адресної структури GAS зведено у довідникові [📋 Двійкові структури та заголовки таблиць ACPI](book:unix-linux/acpi-tables-and-namespace/api-acpi-table-structures.md).

## 3. Простір імен ACPI (ACPI Namespace)

Коли інтерпретатор ACPICA у ядрі Linux зчитує та розбирає бінарний AML-код з таблиць DSDT та SSDT, він не просто послідовно виконує інструкції. Замість цього він створює в оперативній пам'яті ядра динамічне дерево об'єктів — **ACPI Namespace**.

![Ієрархія простору імен ACPI (ACPI Namespace Tree)](/reference/unix-linux/boot-init/acpi-tables-and-namespace/img/acpi-namespace.svg)
*_Рис. 2. Структура деревного простору імен ACPI Namespace з пристроями та методами_*

Простір імен ACPI організовано за аналогією з ієрархічною файловою системою, де корінь позначається символом обратного слішу `\`. Кожен вузол у цьому дереві має ім'я, яке складається рівно з 4 символів ASCII (якщо ім'я коротше, воно доповнюється символами підкреслення `_`).

### Зарезервовані кореневі гілки

Специфікація ACPI фіксує кілька обов'язкових системних гілок на верхньому рівні простору імен:

* **`\_SB` (System Bus):** Головна гілка системних шин та пристроїв. Тут розташовуються об'єкти контролерів PCI Express (`PCI0`), шин I2C/SPI, вбудованих контролерів EC, системних кнопок та підключеної периферії. Більшість драйверів ядра Linux шукають свої пристрої саме всередині `\_SB`.
* **`\_PR` (Processors):** Історична гілка для розміщення об'єктів процесорних ядер (`CPU0`, `CPU1`). У новітніх версіях ACPI об'єкти процесорів також дозволено розміщувати всередині `\_SB`.
* **`\_TZ` (Thermal Zones):** Гілка термальних зон (`TZ00`, `TZ01`). Вона містить об'єкти моніторингу температури, пороги спрацювання критичного вимкнення та керування активним (вентилятори) і пасивним (тротлінг CPU) охолодженням.
* **`\_GPE` (General Purpose Events):** Гілка обробників загальних апаратних подій. Вона містить AML-методи для реакції на натискання кнопки живлення, закриття кришки ноутбука або підключення зарядного пристрою.
* **`\_SI` (System Indicators):** Гілка керування системними індикаторами та світлодіодами стану.

### Ідентифікація пристроїв: _HID, _CID та _ADR

Щоб ядро Linux могло зіставити вузол у просторі імен ACPI з відповідним драйвером ядра, кожен об'єкт пристрою (`Device`) надає спеціальні ідентифікаційні методи або змінні:

1. **`_HID` (Hardware ID):** Головний ідентифікатор пристрою. Це рядок із 7 або 8 символів. Наприклад, `PNP0A08` означає PCI Express Root Bridge, `PNP0C0C` — кнопку живлення Power Button, а `INT33A1` — Intel Power Engine.
2. **`_CID` (Compatible ID):** Список сумісних ідентифікаторів. Якщо ядро не має драйвера під конкретний `_HID`, воно використовує `_CID` для підбору універсального fallback-драйвера.
3. **`_ADR` (Address):** Фізична адреса пристрою на шині, яка не вимагає `_HID` (наприклад, номер пристрою та функції PCI у форматі `(Device << 16) | Function`).

Під час сканування шини ACPI ядро Linux створює екземпляри `struct acpi_device` для кожного знайденого вузла й реєструє їх у системній шині `acpi_bus_type`. Драйвери ядра оголошують масив сумісності `struct acpi_device_id`, що дозволяє ядру автоматично завантажувати потрібний модуль драйвера при виявленні відповідного `_HID`.

### Стандартні керуючі методи (Control Methods)

Об'єкти у просторі імен можуть містити викликувані методи (функції), написані мовою ASL/AML. Специфікація ACPI визначає набір стандартних методів, які починаються із символу підкреслення:

* **`_STA` (Status):** Повертає 8-бітну маску стану пристрою:
  * Біт 0 (0x01): Пристрій присутній фізично.
  * Біт 1 (0x02): Пристрій увімкнено та функціонує.
  * Біт 2 (0x04): Пристрій відображається в UI.
  * Біт 3 (0x08): Пристрій функціонує нормально.
  Якщо метод `_STA` повертає `0x0F`, це означає, що пристрій повністю активний. Ядро постійно викликає `_STA` під час енумерації пристроїв.
* **`_INI` (Initialize):** Викликається ядром один раз при завантаженні для виконання початкової конфігурації апаратури.
* **`_PS0` – `_PS3` (Power States):** Методи керування живленням. Викликом `_PS0` ядро переводить пристрій у стан повного живлення D0, а викликом `_PS3` — у стан глибокого вимкнення D3hot/D3cold.
* **`_DSM` (Device Specific Method):** Універсальний розширюваний метод, який приймає UUID функції, номер функції та аргументи. Використовується виробниками для реалізації специфічних процедур (наприклад, перемикання графічних адаптерів у ноутбуках з гібридною графікою).

## 4. Виконання AML-байткоду та віртуальна машина ACPICA

Використання компільованого байт-коду AML (ACPI Machine Language) замість нативного коду процесора є принциповим рішенням стандарту ACPI.

### Чому обрано інтерпретований байт-код?

Якби виробники материнських плат записували процедури керування залізом у формі скомпільованого виклику під архітектуру x86, операційна система не змогла б виконувати цей код на процесорах ARM64 чи RISC-V. Крім того, нативний код прошивки мав би прямий доступ до будь-яких фізичних адрес пам'яті ядра, що створювало б критичні загрози для безпеки й стабільності всієї системи.

Байт-код AML компілюється з вихідного коду ASL (ACPI Source Language) за допомогою компілятора `iasl` від Intel. Він є машинно-незалежним, стековим байт-кодом, який виконується всередині безпечного пісочничного середовища (sandbox) — інтерпретатора ACPICA.

### Архітектура підсистеми ACPICA у ядрі Linux

**ACPICA (Advanced Configuration and Power Interface Component Architecture)** — це референсна реалізація підсистеми ACPI, яка розробляється консорціумом Intel та інтегрована у вихідний код ядра Linux (каталог `drivers/acpi/acpica/`).

ACPICA виконує три ключові функції:

1. **Парсинг та побудова дерева:** Зчитування бінарних блоків DSDT/SSDT та створення вузлів простору імен у пам'яті.
2. **Виконання AML-інструкцій:** Стекова віртуальна машина зчитує опкоди AML (наприклад, `Opcode 0x14` для оголошення методу, `Opcode 0x70` для операції Store) і обчислює вирази.
3. **Абстракція доступу до регістрів через Operation Regions:** AML-код не має права безпосередньо виконувати інструкції `in`/`out` або повертати вказівники на фізичну пам'ять. Замість цього в ASL оголошуються об'єкти **`OperationRegion`**.

```asl
/* Приклад оголошення OperationRegion в ASL */
OperationRegion (SystemIO, 0x60, 0x04)  /* Регіон у просторі I/O портів */
Field (SystemIO, ByteAcc, NoLock, Preserve)
{
    CMD, 8,   /* Порт 0x60, довжина 8 біт */
    DAT, 8    /* Порт 0x61, довжина 8 біт */
}
```

Коли AML-код виконує операцію запису у поле `CMD`, інтерпретатор ACPICA перехоплює це звернення і перевіряє тип `OperationRegion`:

* **`SystemMemory`:** ACPICA викликає ядерний мапінг `ioremap()` і виконує безпечний запис у фізичну RAM.
* **`SystemIO`:** ACPICA викликає функцію ядра `outb()` / `outw()` для доступу до I/O порту.
* **`PCI_Config`:** Звернення перенаправляється до підсистеми ядра PCI ECAM.
* **`EmbeddedControl`:** ACPICA надсилає байти через драйвер вбудованого мікроконтролера EC (Embedded Controller) ноутбука.

Такий підхід гарантує, що операційна система повністю контролює кожен крок виконання коду прошивки і захищає ядро від несанкціонованого доступу до пам'яті.

### Апаратні події: GPE та системне переривання SCI

Окрім прямого виклику методів ядром, ACPI підтримує асинхронну обробку подій заліза за допомогою механізму **GPE (General Purpose Events)**.

Коли в системі відбувається апаратна подія (наприклад, підключення кабелю живлення, натискання гарячої клавіші чи зміна температури), материнська плата генерує системне переривання **SCI (System Control Interrupt)**. Це переривання є спільним для підсистеми ACPI і обробляється ядром Linux за наступним алгоритмом:

1. Ядро отримує переривання SCI і передає його обробнику ACPICA.
2. ACPICA зчитує регістри статусу `GPE0_STS` та `GPE1_STS`, адреси яких вказані у таблиці FADT, і знаходить номер активного біта події (наприклад, подію `0x1F`).
3. ACPICA шукає у просторі імен `\_GPE` метод з іменем `_L1F` (level-triggered) або `_E1F` (edge-triggered).
4. Інтерпретатор виконує знайдений AML-метод `_L1F`. Цей метод може прочитати регістри EC та викликати оператор `Notify(\_SB.BAT0, 0x80)`.
5. Драйвер батареї Linux, який підписався на нотифікації об'єкта `\_SB.BAT0`, отримує сигнал `0x80` і оновлює відображення відсотка заряду акумулятора у користувацькому просторі.

## 5. Практичний аналіз, декомпіляція та оверрайд у Linux

Для розробників та системних адміністраторів Linux надає повний спектр інструментів для дослідження та відлагодження ACPI на живій системі.

* **/sys/firmware/acpi/tables:** Простір sysfs, де ядро експортує сирі таблиці у бінарному вигляді.
* **acpidump / acpixtract:** Утиліти для створення повного бінарного дампа ACPI з системної пам'яті та витягування окремих таблиць `DSDT.dat` чи `SSDT.dat`.
* **iasl -d:** Декомпілятор Intel iASL, який перетворює бінарні `AML` файли у читабельні вихідні файли `ASL`.
* **ACPI Table Override (initramfs):** Механізм заміни помилкової DSDT-таблиці BIOS на модифікований `DSDT.aml` шляхом підкладання несжиманого CPIO-архіву в initramfs на старті завантажувача.
* **acpiexec:** Інструмент із пакету ACPICA, який дозволяє запустити інтерпретатор AML у користувацькому просторі та покроково виконувати AML-методи без ризику зависання живої системи.

Покроковий практикум з декомпіляції DSDT, виправлення ASL-коду, пакування CPIO-оверрайду та створення бінарного читача таблиць наведено у матеріалі [⚙️ Практикум: аналіз таблиць, декомпіляція ASL та оверрайд DSDT у Linux](book:unix-linux/acpi-tables-and-namespace/proj-aml-parser-and-override.md).

/* C Implementation: Reading and Parsing FADT Table Header from sysfs */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>

#pragma pack(push, 1)
struct acpi_table_header {
    char     signature[4];
    uint32_t length;
    uint8_t  revision;
    uint8_t  checksum;
    char     oem_id[6];
    char     oem_table_id[8];
    uint32_t oem_revision;
    char     asl_compiler_id[4];
    uint32_t asl_compiler_revision;
};
#pragma pack(pop)

int check_acpi_checksum(const uint8_t *buffer, size_t length) {
    uint8_t sum = 0;
    for (size_t i = 0; i < length; ++i) {
        sum += buffer[i];
    }
    return sum == 0;
}

int inspect_fadt_table(const char *sysfs_path) {
    FILE *f = fopen(sysfs_path, "rb");
    if (!f) {
        perror("Failed to open ACPI table file");
        return -1;
    }

    struct acpi_table_header header;
    if (fread(&header, 1, sizeof(header), f) != sizeof(header)) {
        fprintf(stderr, "Truncated ACPI header read\n");
        fclose(f);
        return -1;
    }

    uint8_t *full_table = (uint8_t *)malloc(header.length);
    if (!full_table) {
        fclose(f);
        return -1;
    }

    fseek(f, 0, SEEK_SET);
    if (fread(full_table, 1, header.length, f) != header.length) {
        fprintf(stderr, "Failed to read complete table body\n");
        free(full_table);
        fclose(f);
        return -1;
    }
    fclose(f);

    printf("ACPI Table Signature: %.4s\n", header.signature);
    printf("Total Size:           %u bytes\n", header.length);
    printf("OEM Identity:         %.6s\n", header.oem_id);
    printf("Checksum Status:      %s\n", 
           check_acpi_checksum(full_table, header.length) ? "VALID" : "CORRUPTED");

    free(full_table);
    return 0;
}

// C++ Implementation: RAII ACPI Sysfs Inspector using C++20
#include <iostream>
#include <fstream>
#include <vector>
#include <array>
#include <string_view>
#include <numeric>
#include <cstdint>
#include <expected>

#pragma pack(push, 1)
struct alignas(1) AcpiTableHeader {
    std::array<char, 4> signature;
    std::uint32_t       length;
    std::uint8_t        revision;
    std::uint8_t        checksum;
    std::array<char, 6> oem_id;
    std::array<char, 8> oem_table_id;
    std::uint32_t       oem_revision;
    std::array<char, 4> asl_compiler_id;
    std::uint32_t       asl_compiler_revision;
};
#pragma pack(pop)

enum class AcpiParseError {
    FileNotFound,
    HeaderTruncated,
    ReadFailure,
    ChecksumMismatch
};

class AcpiSysfsParser {
public:
    static std::expected<AcpiTableHeader, AcpiParseError>
    inspectTable(std::string_view sysfsPath) {
        std::ifstream file(sysfsPath.data(), std::ios::binary | std::ios::ate);
        if (!file.is_open()) {
            return std::unexpected(AcpiParseError::FileNotFound);
        }

        const auto fileSize = static_cast<std::size_t>(file.tellg());
        file.seekg(0, std::ios::beg);

        if (fileSize < sizeof(AcpiTableHeader)) {
            return std::unexpected(AcpiParseError::HeaderTruncated);
        }

        std::vector<std::uint8_t> buffer(fileSize);
        if (!file.read(reinterpret_cast<char*>(buffer.data()), fileSize)) {
            return std::unexpected(AcpiParseError::ReadFailure);
        }

        const auto sum = std::accumulate(buffer.begin(), buffer.end(), static_cast<std::uint8_t>(0));
        if (sum != 0) {
            return std::unexpected(AcpiParseError::ChecksumMismatch);
        }

        AcpiTableHeader header{};
        std::copy_n(buffer.data(), sizeof(AcpiTableHeader), reinterpret_cast<std::uint8_t*>(&header));
        return header;
    }
};

int main() {
    constexpr std::string_view path = "/sys/firmware/acpi/tables/FADT";
    auto result = AcpiSysfsParser::inspectTable(path);

    if (result) {
        const auto& hdr = *result;
        std::cout << "Signature:  " << std::string_view(hdr.signature.data(), 4) << '\n';
        std::cout << "Table Size: " << hdr.length << " bytes\n";
        std::cout << "OEM ID:     " << std::string_view(hdr.oem_id.data(), 6) << '\n';
        std::cout << "Status:     Checksum verified successfully.\n";
    } else {
        std::cerr << "Failed to parse ACPI table from sysfs.\n";
    }
    return 0;
}

## 7. Підсумок архітектурного синтезу

Архітектура ACPI об'єднує статичну топологію заліза та динамічну поведінку платформи в єдину цілісну систему. Завдяки статичним таблицям (RSDT/XSDT, FADT, MADT, MCFG) ядро Linux на найранніших стадіях завантаження дізнається про розміщення системних шин, кількість процесорних ядер та параметри контролерів переривань. 

Завдяки динамічним таблицям DSDT/SSDT та інтерпретатору ACPICA ядро будує в пам'яті ієрархічне дерево об'єктів ACPI Namespace і безпечно виконує AML-код у ізольованому пісочничному середовищі, обробляючи апаратні події GPE та SCI. Це перетворює ядро Linux на повновладного контролера енергоспоживання та конфігурації (OSPM), гарантуючи стабільну роботу операційної системи на будь-якому сучасному обладнанні.
