На сервері з увімкненим режимом UEFI Secure Boot системний диск потрапив до рук зловмисника. Оскільки образ ядра `vmlinuz` підписано цифровим підписом дистрибутива, модифікувати його вміст непомітно неможливо: будь-яка зміна бінарного коду миттєво зробить підпис недійсним, і прошивка відмовиться його запускати. Однак поруч із ядром на розділі EFI System Partition (ESP) лежать два інші файли: `initramfs.img` та текстова конфігурація завантажувача з командним рядком. Замінивши `initramfs` на власний архів із відкритим мережевим портом або додавши у командний рядок параметр `init=/bin/sh`, `rd.break` чи `systemd.debug_shell=1`, зловмисник отримує повний root-доступ до системи при наступному ввімкненні. Прошивка Secure Boot слухняно перевіряє підпис ядра, рапортує про його цілісність і запускає компрометовану систему.

Ця проблема виникає через фундаментальний розрив довіри в класичній схемі завантаження Linux. Прошивка UEFI перевіряє лише той виконуваний файл, який вона запускає безпосередньо. Початкова файлова система initramfs і командний рядок передаються завантажувачем у пам'яті як сирі блоки даних, позбавлені криптографічного підпису.

Розв'язанням цієї кризи стало поєднання двох технологій: мінімалістичного завантажувача `systemd-boot` та концепції Unified Kernel Image (UKI), яка об'єднує ядро, initramfs, командний рядок та метадані в єдиний атомарний файл із спільним цифровим підписом.

## Чому складному завантажувачу не місце в UEFI

Класичні завантажувачі епохи BIOS (зокрема GRUB 2) створювалися для роботи у середовищі, де прошивка плати вміла виконувати лише 512 байтів із першого сектора диска. Щоб прочитати ядро з диска, завантажувачу доводилося самостійно ініціалізувати дисковий контролер, розуміти таблиці розділів GPT/MBR і містити в собі драйвери файлових систем (ext4, xfs, btrfs), програмних масивів RAID та томів LVM. У результаті GRUB 2 перетворився на величезну операційну систему в мініатюрі, розмір коду якої вимірюється сотнями тисяч рядків.

Середовище UEFI кардинально змінило розподіл обов'язків між прошивкою та завантажувачем:
1. Прошивка плати містить власний драйвер файлової системи VFAT та розуміє таблиці партицій GPT.
2. Прошивка вміє шукати розділ EFI System Partition (ESP), зчитувати з нього файли за допомогою протоколів `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` та `EFI_FILE_PROTOCOL` і виконувати їх, якщо вони відповідають формату PE/COFF (стандартні бінарники `.efi`).
3. Прошивка надає таблиці службових викликів (UEFI Boot Services та Runtime Services) для мапування оперативної пам'яті, зчитування клавіатури, виведення на екран та збереження змінних у незмінній пам'яті NVRAM.

Якщо прошивка вже вміє читати файлову систему VFAT на розділі ESP, додавання в завантажувач власних драйверів дискових структур стає недоцільним дублюванням функцій. Що складніша програма завантажувача, то більше в ній потенційних вад безпеки (наприклад, помилок переповнення буфера в парсерах конфігів). Виправлення вразливості у завантажувачі вимагає оновлення списків відкликання `dbx` у пам'яті NVRAM материнських плат по всьому світу.

Звідси виріс підхід завантажувача `systemd-boot`: він не містить жодного драйвера файлових систем. `systemd-boot` — це крихітна EFI-програма (обсягом близько 30–50 КБ), яка працює виключно поверх файлової системи ESP, наданої прошивкою. Вона вирішує одну-єдину задачу: показує меню вибору операційної системи та запускає обраний PE/COFF бінарник за допомогою системного виклику прошивки `BS->StartImage()`.

Хронологію створення цього мінімалістичного підходу, розробку специфікації Boot Loader Specification та перехід від проектів `gummiboot` до `systemd-boot` висвітлено окремо: [від gummiboot до UKI: еволюція завантаження в UEFI](book:unix-linux/systemd-boot-and-systemd-stub-uki/hist-uki-evolution.md).

## Специфікація Boot Loader Specification (BLS)

Щоб завантажувач міг відобразити список доступних систем, йому потрібен механізм опису пунктів меню. У старих завантажувачах конфігурація збиралася в один монолітний файл (наприклад, `grub.cfg`). Під час інсталяції нового ядра спеціальні скрипти перегенеровували весь файл від початку до кінця. Найменша помилка в генераторі призводила до того, що система ставала незавантажуваною.

Стандарт Boot Loader Specification (BLS) розділив конфігурацію на два класи записів:

### Записи Type #1 (Роздільні конфігураційні файли)
Усі пункти меню описуються окремими файлами в директорії `/loader/entries/*.conf` на розділі ESP або XBOOTLDR. Кожен файл відповідає одному ядру й містить текстові ключі:

```text
title      Fedora Linux 40 (6.10.3)
version    6.10.3-200.fc40.x86_64
linux      /vmlinuz-6.10.3-200.fc40.x86_64
initrd     /initramfs-6.10.3-200.fc40.x86_64.img
options    root=UUID=5f2b8a1c-9d0e-4f3a-8b2c-1e0f9a8b7c6d ro quiet
```

Оновлення ядра зводиться до запису нового файла `.conf` і копіювання парних `vmlinuz` та `initramfs` на ESP. Старі записи вилучаються простим видаленням одного файла без ризику пошкодити конфігурацію інших ядер.

### Записи Type #2 (Unified Kernel Images — UKI)
Записи Type #2 взагалі відмовляються від конфігураційних файлів у `/loader/entries/`. Завантажувач `systemd-boot` сканує директорію `/EFI/Linux/` на розділі ESP та автоматично додає кожен знайдений файл з розширенням `.efi` до меню завантаження. Назва операційної системи, версія ядра та параметри витягуються безпосередньо з метаданих усередині самого бінарника.

## Концепція та будова Unified Kernel Image (UKI)

Ядро Linux містить модуль `EFISTUB` — код, який дозволяє файлу `vmlinuz` прикидатися виконуваним файлом PE/COFF і запускатися прошивкою UEFI напряму. Проте `vmlinuz` сам по собі не вирішує проблему безпеки: прошивка підтвердить підпис `vmlinuz`, але `initramfs` та командний рядок все одно доведеться завантажувати як незахищені зовнішні файли.

Unified Kernel Image (UKI) вирішує цю проблему шляхом пакування всіх складників завантаження в **єдиний контейнер PE/COFF**.

![Анатомія Unified Kernel Image](/reference/unix-linux/boot-init/systemd-boot-and-systemd-stub-uki/img/uki-structure.svg)

*Структура секцій PE/COFF контейнера UKI: заглушка systemd-stub об'єднує ядро, initramfs, командний рядок та метадані в атомарний виконуваний файл під єдиним підписом Authenticode.*

Основою UKI є використання специфічних секцій PE/COFF бінарника:

1. **`systemd-stub` (точка входу):** невелика EFI-заглушка з дистрибутива systemd. Прошивка UEFI передає керування на точку входу цієї заглушки.
2. **Секція `.linux`:** двійковий образ ядра Linux (`vmlinuz`), який містить у собі власний `EFISTUB`.
3. **Секція `.initrd`:** упакований CPIO-архів початкової файлової системи initramfs, включаючи мікрокод процесора (Intel/AMD).
4. **Секція `.cmdline`:** рядок аргументів ядра (наприклад, `root=UUID=... ro quiet`), зашитий статично під час збірки образу.
5. **Секція `.osrel`:** вміст файла `/etc/os-release` з текстовими метаданими (назва ОС, версія, ID).
6. **Секція `.uname`:** рядок версії ядра (`uname -r`).
7. **Секції `.pcrpkey` та `.pcrsig`:** публічний ключ та підпис для перевірки відповідності станів TPM2 PCR.
8. **Секція `.sbat`:** метадані Secure Boot Advanced Targeting, які дозволяють відкликати вразливі версії завантажувачів без зміни ключів у прошивці.
9. **Секція `.splash`:** графічний логотип у форматі BMP, який виводиться на екран під час раннього старту.

Оскільки всі ці секції лежать усередині **одного файла `.efi`**, на весь образ накладається **один підпис Secure Boot Authenticode**. Якщо зловмисник спробує змінити хоча б один символ у секції `.cmdline` або підмінити файл всередині `.initrd`, криптографічний підпис файла PE/COFF стане недійсним, і прошивка UEFI відмовиться його виконувати.

Детальний список секцій, їхні прапорці в PE-заголовку (`IMAGE_SCN_CNT_INITIALIZED_DATA`, `IMAGE_SCN_MEM_READ`), вирівнювання у файлі та налаштування `loader.conf` зібрано окремо: [специфікація секцій UKI та конфігурації systemd-boot](book:unix-linux/systemd-boot-and-systemd-stub-uki/api-uki-sections.md).

## Послідовність виконання systemd-stub та Measured Boot

Щоб зрозуміти, як UKI захищає систему після перевірки підпису прошивкою, простежимо закроковий шлях виконання коду від моменту вибору образу в меню до передачі керування ядру.

![Межа безпеки: Класичне завантаження проти UKI](/reference/unix-linux/boot-init/systemd-boot-and-systemd-stub-uki/img/boot-sequence.svg)

*Порівняння ланцюга завантаження: класична схема залишає initramfs та cmdline поза Secure Boot, тоді як UKI створює єдиний криптографічний блок із вимірюванням секцій у TPM2 PCR 11.*

Послідовність дій відбувається за таким каскадом:

1. **Перевірка прошивкою:** Прошивка UEFI завантажує образ `.efi` з розділу ESP, звіряє його цифровий підпис із базою `db` і, якщо підпис чинний, передає керування на точку входу `systemd-stub`.
2. **Аналіз власних секцій:** `systemd-stub` за допомогою протоколу `EFI_LOADED_IMAGE_PROTOCOL` отримує власну адресу в оперативній пам'яті, знаходить таблицю PE-секцій та визначає зміщення `.linux`, `.initrd`, `.cmdline` й `.osrel`.
3. **Виділення пам'яті та вирівнювання:** Заглушка викликає службу `BS->AllocatePages()` для виділення неперервних сторінок пам'яті під розпаковану секцію `.initrd` та структуру `boot_params` (zero-page ядра x86_64).
4. **Вимірювання в TPM2 (Measured Boot):**
   `systemd-stub` через протокол прошивки `EFI_TCG2_PROTOCOL` (метод `HashLogExtendEvent`) розраховує криптографічні хеші (SHA-256) кожної окремої секції та записує їх у спеціальний регістр апаратного модуля безпеки — **TPM2 PCR 11** (значення PCR за замовчуванням для `systemd-stub`).
   - Хеш секції `.cmdline` розширює PCR 11.
   - Хеш секції `.initrd` розширює PCR 11.
   - Хеші секцій `.linux` та `.osrel` розширюють PCR 11.
5. **Перевірка підпису політики TPM (опціонально):** За наявності секцій `.pcrsig` та `.pcrpkey`, заглушка перевіряє, чи відповідає поточний стан регістрів PCR підписаній политиці безпеки.
6. **Збирання командного рядка:** `systemd-stub` зчитує рядок із секції `.cmdline`. Якщо в конфігурації завантажувача дозволено передачу додаткових параметрів користувача і функція `editor` не вимкнена, вони додаються в кінець рядка. Якщо передачу параметрів заборонено (режим максимального захисту), передані ззовні аргументи ігноруються.
7. **Формування заголовка завантаження:** `systemd-stub` заповнює вказівники у структурі ядра: `hdr.ramdisk_image` вказує на виділену адресу `.initrd`, `hdr.ramdisk_size` — на його розмір, `hdr.cmd_line_ptr` — на підсумковий рядок, а `hdr.type_of_loader` записує ідентифікатор `0x44` (systemd-boot).
8. **Передача керування ядру:** `systemd-stub` викликає вхідну точку ядра `.linux` через `EFISTUB` (`efi_pe_entry`).
9. **Старт ядра:** Ядро Linux починає виконання, отримує з готової пам'яті вже перевірений `initramfs`, виходить із Boot Services прошивки (`ExitBootServices`), монтує початкову файлову систему та запускає `systemd`.

Завдяки тому, що хеші всіх складників зафіксовані в TPM2 PCR 11, модуль шифрування дисків `systemd-cryptsetup` може безпечно запечатати ключ розшифрування тома LUKS2 в чипі TPM2. Ключ буде видано лише тоді, коли PCR 11 містить хеші точно того UKI, який пройшов перевірку.

## Інтеграція з LUKS2 та автоматичне запечатування ключів шифрування

Використання UKI спільно з виміряним завантаженням TPM2 вирішує проблему автоматичного розшифрування системних дисків без введення пароля користувачем, не знижуючи рівень безпеки.

У класичній схемі автоматичного розшифрування диска ключі запечатувалися в TPM2 під регістри PCR 0–7 (налаштування прошивки та завантажувача). Однак при оновленні версії ядра або initramfs значення PCR 0–7 не змінювалися, що дозволяло зловмиснику підкинути власне модифіковане ядро й отримати запечатаний ключ із TPM2.

З появою UKI та заповненням регістру **TPM2 PCR 11** схема захисту стає абсолютно надійною:

1. Під час генерації UKI утиліта `systemd-measure` розраховує майбутній хеш PCR 11, який буде отримано після вимірювання секцій `.linux`, `.initrd` та `.cmdline`.
2. Модуль `systemd-cryptsetup` зв'язує мастер-ключ тома LUKS2 з політикою TPM2, яка вимагає точного збігу значення в PCR 11.
3. При ввімкненні ПК `systemd-stub` послідовно передає хеші секцій UKI в TPM2.
4. Коли система досягає стадії моунта диска в initramfs, `systemd-cryptsetup` запитує ключ у TPM2. Якщо хоча б один байт у initramfs чи командному рядку було змінено, підсумковий хеш у PCR 11 виявиться іншим, і TPM2 відмовить видати ключ розшифрування.

Для підтримки оновлень ядер без перепідпису дисків використовується інструмент `systemd-pcrlock`, який веде облік довірених підписів політик у секції `.pcrsig`.

## Практична збірка та розбір UKI в системі

Для генерації UKI у сучасних дистрибутивах використовується офіційний інструмент `systemd-ukify` або інтегровані генератори initramfs (`dracut --uefi`, `mkinitcpio`).

Під капотом утиліта збірки бере файл заглушки `linuxx64.efi.stub`, додає до нього потрібні секції за допомогою `objcopy` та вирівнює межі даних:

```bash
# Генерація UKI за допомогою утиліти systemd-ukify
systemd-ukify build \
    --linux=/boot/vmlinuz-6.10.3-200.fc40.x86_64 \
    --initrd=/boot/initramfs-6.10.3-200.fc40.x86_64.img \
    --cmdline="root=UUID=8f3c1a2b-3c4d-5e6f-7a8b-9c0d1e2f3a4b ro quiet" \
    --os-release=@/etc/os-release \
    --output=/boot/efi/EFI/Linux/fedora-6.10.3.efi
```

Отриманий файл `/boot/efi/EFI/Linux/fedora-6.10.3.efi` є повністю самодостатнім: його можна скопіювати на будь-яку іншу сумісну машину або завантажити напряму з UEFI NVRAM без використання додаткових меню.

Практичні консольні команди збірки, ручне застосування `objcopy`, підписання за допомогою `sbctl`, а також готовий код аналізатора PE-секцій мовами C та C++ подано у [практикумі складання та аналізу UKI](book:unix-linux/systemd-boot-and-systemd-stub-uki/proj-build-uki.md).

## Конфігурація та налаштування systemd-boot

Завантажувач `systemd-boot` встановлюється на розділ ESP однією командою:

```bash
# Встановлення бінарників systemd-boot у розділ ESP та створення записів в NVRAM
bootctl install
```

Ця команда копіює виконуваний файл `systemd-bootx64.efi` у директорії `/EFI/systemd/` та `/EFI/BOOT/BOOTX64.EFI` на розділі ESP і реєструє відповідний пункт у змінних прошивки NVRAM за допомогою системного виклику.

Головний файл конфігурації лежить за шляхом `/loader/loader.conf`:

```ini
# /loader/loader.conf
default  fedora*
timeout  3
console-mode max
editor   no
```

Ключові параметри конфігурації:
- **`default`**: шаблон назви пункту за замовчуванням. Для UKI це значення може збігатися з іменем файлу в `/EFI/Linux/` або змістом поля `PRETTY_NAME` у `.osrel`.
- **`timeout`**: час очікування вибору у меню (в секундах). Значення `0` вимикає меню й завантажує за замовчуванням негайно.
- **`editor no`**: вимикає можливість редагування командного рядка клавішею `e` у графічному меню завантажувача. Це критичний параметр безпеки: якщо командний рядок зашито у секцію `.cmdline` всередині підписаного UKI, дозволяти користувачеві змінювати його з клавіатури означало б відкрити можливість обходу Secure Boot.

## Порівняльний аналіз та межі застосування

Щоб узагальнити відмінності між підходами, порівняємо класичну схему завантаження на основі GRUB 2 та сучасну схему на основі `systemd-boot` і UKI:

| Характеристика | Класична схема (GRUB 2) | Схема systemd-boot + UKI |
| :--- | :--- | :--- |
| **Драйвери файлових систем** | Вбудовані у завантажувач (ext4, xfs, btrfs, LUKS) | Відсутні (використовується лише VFAT прошивки UEFI) |
| **Захист initramfs у Secure Boot** | Відсутній (initramfs не підписується прошивкою) | Повний (initramfs входить до підписаного PE/COFF образу) |
| **Захист командного рядка** | Відсутній (конфіг `grub.cfg` лежить у сирому вигляді) | Повний (cmdline зашито у підписану секцію `.cmdline`) |
| **Виміряне завантаження (TPM2)** | Складне, вимірює окремі файли у PCR 8/9 | Автоматичне, вимірює секції UKI в PCR 11 |
| **Конфігураційні файли** | Один громіздкий файл `grub.cfg` | Відсутні для UKI (автовиявлення файлів у `/EFI/Linux/`) |
| **Складність оновлення ядер** | Перегенерація всього `grub.cfg` | Додавання чи видалення одного файла `.efi` |
| **Вимоги до розміру ESP** | Маленький ESP (100–200 МБ), ядро на `/boot` | Більший ESP або XBOOTLDR (1–2 ГБ), оскільки UKI лежить на ESP |

Головний компроміс схеми UKI полягає у розмірі розділу ESP. Оскільки образ UKI містить ядро та розпаковані модулі initramfs, розмір одного `.efi` файла становить від 30 до 90 Мегабайтів. Для збереження кількох версій ядер розмір розділу ESP (або окремого розділу XBOOTLDR) рекомендується обирати від 1 до 2 Гігабайтів.

Завдяки відмові від зайвих шарів абстракції та об'єднанню завантажувальних елементів у єдиний криптографічний блок, поєднання `systemd-boot` та UKI забезпечує мінімальний час старту й нерозривний ланцюг довіри від першого такту процесора до запуску першого процесу користувача.
