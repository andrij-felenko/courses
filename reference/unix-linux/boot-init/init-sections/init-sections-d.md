# Секції ініціалізації ядра: __init, __initdata та їхнє звільнення з пам'яті

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Linux — це надзвичайно гнучка та адаптивна операційна система, яка з перших днів свого існування проектувалася та оптимізувалася для роботи в умовах суворо обмежених апаратних ресурсів. Одним із найбільш елегантних та цікавих архітектурних рішень ядра Linux є його унікальний підхід до управління пам'яттю під час завантаження системи. Оскільки величезна кількість функцій, драйверів, масивів та структур даних потрібні виключно на етапі початкової ініціалізації системи (наприклад, для розпізнавання обладнання, налаштування сторінкової пам'яті, парсингу параметрів командного рядка, розпакування структур, встановлення початкових таймерів), тримати їх у дорогій та обмеженій оперативній пам'яті під час звичайної роботи системи було б вкрай недоцільно та марнотратно.

Щоб вирішити цю архітектурну проблему, розробники ядра Linux створили набір спеціальних макросів мови C, найвідомішими з яких є `__init` та `__initdata`. Вони дозволяють компілятору розміщувати код та дані ініціалізації в окремих спеціалізованих секціях пам'яті, таких як `.init.text` та `.init.data`. Після того, як ядро успішно завершує етап завантаження і готується передати управління простору користувача (user space), викликається спеціальна архітектурно-залежна функція `free_initmem()`. Її завдання — назавжди звільнити ці секції, повертаючи сторінки пам'яті до загального сторінкового алокатора (Page Allocator), щоб вони стали повністю доступними для звичайних процесів користувача. 

Ця стаття глибоко та детально розглядає механізми, що стоять за цими секціями, їхній вплив на життєвий цикл ядра, взаємодію з лінкером та те, як фізично відбувається звільнення пам'яті на рівні архітектури.

## 1. Проблема: Чому звільнення пам'яті ініціалізації настільки важливе?

Під час процесу завантаження ядро Linux виконує колосальний обсяг роботи. Воно має перевірити наявну оперативну пам'ять, ініціалізувати складні контролери переривань (наприклад, APIC на архітектурі x86), налаштувати системні таймери, просканувати всі доступні шини передачі даних (PCI, USB, I2C, SPI), ініціалізувати віртуальну файлову систему (VFS), змонтувати кореневий розділ і, нарешті, запустити процес `init` (або `systemd`), який переводить систему в робочий режим.

Більшість коду, який відповідає за ці початкові налаштування, щойно він виконав свою роботу, більше ніколи не буде викликаний до наступного холодного перезавантаження системи. У ранніх версіях монолітних ядер операційних систем (або в менш оптимізованих архітектурах) весь цей код ініціалізації залишався б у пам'яті назавжди. Це означало б, що сотні кілобайтів або навіть кілька мегабайтів оперативної пам'яті (RAM) були б просто змарновані, оскільки вони зберігали б інструкції процесора, які ніколи не будуть виконані знову.

Для сучасних високопродуктивних серверів із сотнями гігабайтів оперативної пам'яті втрата кількох мегабайтів може здаватися абсолютно незначною і такою, що не варта уваги. Проте Linux працює не лише на серверах. Ця операційна система домінує на ринку вбудованих систем (embedded systems), пристроїв Інтернету речей (IoT), домашніх маршрутизаторів (роутерів), смартфонів та навіть смарт-годинників. У багатьох з цих пристроїв загальний обсяг оперативної пам'яті може становити лише 16 МБ, 32 МБ або 64 МБ. У таких екстремально обмежених умовах кожен кілобайт збереженої пам'яті є критичним. Звільнення 2 МБ ініціалізаційного коду на роутері з 16 МБ RAM означає звільнення понад 12% всієї доступної пам'яті системи! Це дозволяє запустити додаткові мережеві служби, збільшити розмір буферів TCP/IP або уникнути виклику Out-Of-Memory (OOM) Killer.

Щоб максимізувати обсяг вільної пам'яті для користувацького простору, Linux використовує концепцію "одноразових" секцій ініціалізації. Замість того, щоб змішувати код завантаження зі звичайним кодом ядра, компілятору дається сувора вказівка згрупувати весь ініціалізаційний код та тимчасові дані разом в один великий неперервний блок. Після того, як система завантажилася, ядро просто позначає всі сторінки пам'яті, які належать до цього блоку, як вільні. Після цього ця пам'ять стає частиною загального пулу вільної пам'яті системи.

## 2. Анатомія макросів `__init` та `__initdata`

Для того, щоб явно вказати компілятору (зазвичай це GCC або Clang), що певна функція, масив або змінна належить до коду ініціалізації і не буде потрібна згодом, в ядрі Linux визначені спеціальні макроси. Вони оголошені в головному заголовному файлі ініціалізації ядра — `include/linux/init.h`. Ці макроси активно використовують нестандартні розширення мови C, які підтримуються сучасними компіляторами.

### 2.1. Макрос `__init` для функцій

Макрос `__init` використовується виключно для позначення функцій. У препроцесорі C він розгортається в атрибут компілятора `__attribute__((__section__(".init.text")))`. 

Цей атрибут є директивою для компілятора: він змушує компілятор розмістити згенерований машинний код цієї конкретної функції не у стандартній секції коду `.text` (де лежить більшість коду ядра), а у спеціально виділеній користувацькій секції `.init.text`.

Розглянемо типовий приклад використання макроса в коді драйвера:

```c
#include <linux/init.h>
#include <linux/module.h>

/* Функція налаштування, яка потрібна лише раз */
static int __init my_custom_hardware_init(void)
{
    printk(KERN_INFO "Початок ініціалізації мого апаратного забезпечення...\n");
    
    // Тут іде складний код налаштування портів вводу/виводу,
    // реєстрація переривань, виділення початкових буферів тощо.
    
    return 0;
}
```

У цьому класичному прикладі машинний код функції `my_custom_hardware_init` буде розміщений у секції `.init.text`. Після того, як пристрій буде ініціалізовано на етапі завантаження, пам'ять, яку займає цей код, буде безповоротно звільнена. 

Важливо усвідомлювати критичне правило: **після завершення ініціалізації системи, будь-який виклик функції, позначеної макросом `__init`, неминуче призведе до краху системи (kernel panic, page fault або oops)**. Це станеться тому, що фізична пам'ять, за адресою якої колись знаходилася ця функція, вже була передана іншому процесу або перезаписана іншими даними. Процесор спробує виконати випадковий сміттєвий код або натрапить на сторінку пам'яті, до якої він більше не має прав доступу на виконання. Тому розробники повинні бути вкрай обережними і не експортувати `__init` функції для використання в пізніших етапах роботи ядра.

### 2.2. Макрос `__initdata` для змінних

Аналогічно до функцій, макрос `__initdata` використовується для статичних змінних, масивів або структур даних, інформація в яких потрібна лише під час ініціалізації. Цей макрос розгортається в атрибут `__attribute__((__section__(".init.data")))`, що розміщує дані в секції `.init.data`.

Приклад використання для тимчасових структур:

```c
#include <linux/init.h>

/* Великий масив конфігурації, який потрібен лише при старті */
static int initial_port_configuration[1024] __initdata = { 
    [0 ... 1023] = -1 
};

static int __init my_network_driver_init(void)
{
    int i;
    for (i = 0; i < 1024; i++) {
        if (initial_port_configuration[i] != -1) {
            setup_port(i, initial_port_configuration[i]);
        }
    }
    return 0;
}
```

У цьому випадку масив `initial_port_configuration` займає 4 кілобайти пам'яті (1024 цілих числа по 4 байти). Оскільки він позначений як `__initdata`, він буде розміщений у секції `.init.data` і буде повністю знищений та звільнений з оперативної пам'яті разом із кодом ініціалізації.

### 2.3. Похідні макроси та специфічні випадки

Окрім базових `__init` та `__initdata`, ядро Linux визначає цілий спектр подібних макросів для більш специфічних потреб:

- `__initconst`: Використовується для константних даних (змінних типу `const`), які потрібні лише під час завантаження. Він розміщує дані в секції `.init.rodata`. Це особливо важливо для великих таблиць констант, які використовуються для парсингу, але пізніше стають непотрібними.
- `__exit`: Цей макрос є логічною протилежністю `__init`. Він використовується для функцій очищення та деініціалізації (наприклад, під час вивантаження модуля ядра). Цікавою особливістю `__exit` є те, що якщо драйвер вбудовано безпосередньо в монолітне ядро (тобто він не компілюється як окремий модуль `.ko`), функції з макросом `__exit` можуть бути взагалі відкинуті лінкером. Це відбувається тому, що вбудований драйвер ніколи не вивантажується з пам'яті працюючої системи, а отже, його функція очищення ніколи не буде викликана.
- `__exitdata`: Відповідно, використовується для даних, які необхідні виключно функціям, позначеним як `__exit`.
- `__ro_after_init`: Хоч цей макрос і не призводить до звільнення пам'яті, він тісно пов'язаний з ініціалізацією. Дані, позначені ним, є доступними для читання та запису (Read/Write) під час процесу ініціалізації. Але щойно функція `free_initmem()` завершує свою роботу, ядро змінює права доступу до сторінок пам'яті з цими даними на "Тільки для читання" (Read-Only). Це надзвичайно потужний механізм безпеки, який захищає критичні структури даних ядра від зміни зловмисниками (наприклад, через атаки типу buffer overflow або use-after-free).

## 3. Магія лінкера: Як секції збираються разом

Самі по собі атрибути компілятора GCC, такі як `__attribute__((__section__(".init.text")))`, лише вказують компілятору, у які іменовані секції об'єктного файлу (ELF файлу `.o`) помістити згенерований машинний код чи дані. Справжня інженерна магія відбувається пізніше, на етапі компонування (лінкування) сотень і тисяч об'єктних файлів в єдиний монолітний образ ядра.

Під час збирання фінального ядра системний лінкер (наприклад, GNU `ld` або LLVM `lld`) використовує спеціальний, ретельно написаний скрипт лінкера. Для ядра Linux цей скрипт зазвичай генерується з файлу `arch/<architecture>/kernel/vmlinux.lds.S`. Цей файл містить вичерпні інструкції для лінкера щодо того, як саме структурувати фінальний бінарний файл ядра (`vmlinux`), де саме в пам'яті повинна розташовуватися кожна секція і яке вирівнювання вона повинна мати.

У скрипті лінкера `vmlinux.lds.S` усі розрізнені секції ініціалізації з усіх об'єктних файлів ядра збираються і групуються разом в один великий неперервний блок. Ключовим моментом є те, що цей блок розміщується між двома спеціальними глобальними символами, які позначають початок і кінець області ініціалізації. Розглянемо спрощений, але показовий фрагмент такого скрипта:

```ld
    /* Вирівнювання поточної адреси лінкування до розміру фізичної сторінки пам'яті.
       PAGE_SIZE зазвичай дорівнює 4096 байт на архітектурах x86. */
    . = ALIGN(PAGE_SIZE);
    
    /* Створення глобального символу, який вказує на початок пам'яті ініціалізації */
    __init_begin = .; 

    /* Збираємо всі секції .init.text з усіх вхідних файлів */
    .init.text : {
        _sinittext = .;
        *(.init.text)
        _einittext = .;
    }

    /* Збираємо всі секції .init.data */
    .init.data : {
        *(.init.data)
    }
    
    /* Збираємо масиви вказіників для initcalls */
    .initcall.init : {
        __initcall_start = .;
        *(.initcall.init)
        __initcall_end = .;
    }

    /* Вирівнюємо кінець блоку до повної сторінки пам'яті */
    . = ALIGN(PAGE_SIZE);
    
    /* Створення глобального символу для кінця ініціалізаційної пам'яті */
    __init_end = .;   
```

Символи `__init_begin` та `__init_end` не є звичайними змінними в C. Вони є глобальними символами лінкера, які представляють собою адреси в пам'яті. З C-коду ядра до них можна звернутися, оголосивши їх як зовнішні змінні (extern):

```c
extern char __init_begin[], __init_end[];
```

Ці символи дозволяють коду ядра точно знати фізичні та віртуальні адреси, де починається і де закінчується масивний блок пам'яті ініціалізації. Вирівнювання початку і кінця цього блоку за розміром сторінки (`ALIGN(PAGE_SIZE)`) є абсолютно критичним і обов'язковим. Справа в тому, що менеджер пам'яті ядра Linux (відомий як сторінковий алокатор або Buddy Allocator) не вміє оперувати окремими байтами. Він керує пам'яттю блоками, розмір яких строго дорівнює одній сторінці (наприклад, 4 КБ). Якби секція ініціалізації закінчувалася посеред сторінки пам'яті, а одразу за нею починалася б секція постійного коду ядра `.text`, ядро не змогло б звільнити цю останню сторінку. Звільнення частини сторінки неможливе, а звільнення всієї сторінки призвело б до знищення частини постійного коду ядра. Тому суворе вирівнювання по сторінках гарантує, що між `__init_begin` та `__init_end` лежать лише цілі сторінки пам'яті, які цілком безпечно можна повернути системі.

## 4. Процес завантаження Linux: Від bootloader до `rest_init`

Щоб зрозуміти, у який саме момент часу відбувається грандіозне звільнення пам'яті, необхідно чітко уявляти хронологію завантаження ядра Linux. Цей процес є складним багатоетапним конвеєром:

1. **Завантажувач (Bootloader)**: Програми на кшталт GRUB, U-Boot, LILO або системне firmware (UEFI) завантажують стиснений образ ядра (наприклад, `bzImage` на x86) з диска у фізичну оперативну пам'ять.
2. **Розпакування образу**: Код декомпресора, вбудований на початку образу, виконується і розпаковує справжнє ядро в іншу область оперативної пам'яті.
3. **Рання архітектурна ініціалізація**: Виконується низькорівневий асемблерний код (наприклад, `arch/x86/boot/head_64.S` для 64-бітних систем). Він налаштовує найпростіші початкові сторінкові таблиці (page tables), ініціалізує глобальну таблицю дескрипторів (GDT), переводить процесор у захищений або довгий режим (protected/long mode) і, підготувавши середовище виконання C, робить перехід до першої C-функції — `start_kernel()`.
4. **Масивна ініціалізація у `start_kernel()`**: Розташована у файлі `init/main.c`, ця функція є справжнім серцем процесу ініціалізації ядра. Її код позначений макросом `__init`. Вона виконує сотні викликів інших `__init` функцій. Тут налаштовуються всі базові підсистеми: менеджер пам'яті (slab/slub allocators), планувальник завдань (scheduler), система обробки переривань, таймери високої роздільної здатності, віртуальна файлова система (VFS) та механізми міжпроцесної взаємодії (IPC). 
5. **Розгалуження в `rest_init()`**: Наприкінці свого життєвого шляху, функція `start_kernel()` викликає `rest_init()`. Ця функція є переломним моментом у процесі завантаження. Вона створює два критично важливих потоки ядра (kernel threads), використовуючи виклик `kernel_thread()`:
   - **Потік `kernel_init` (PID 1)**: Це потік, який завершить ініціалізацію на вищому рівні та згодом перетвориться на перший процес простору користувача (відомий як `/sbin/init` або `systemd`).
   - **Потік `kthreadd` (PID 2)**: Цей потік стає "батьком" і менеджером усіх майбутніх потоків ядра.
6. **Перехід у нескінченний простій**: Сама функція `rest_init()`, породивши ці два потоки, перетворюється на так званий idle thread (потік простою, відомий як PID 0 або swapper). Вона переходить у нескінченний цикл очікування, викликаючи інструкцію процесора `hlt` (на x86) і споживаючи мінімум енергії. Відтепер цей потік буде виконуватися лише тоді, коли жоден інший процес у системі не потребує часу процесора.

### 4.1. Робота потоку `kernel_init` і фінал ініціалізації

Новостворений потік `kernel_init` (який все ще працює в режимі ядра) бере на себе естафету. Його головним завданням є виконання так званих `initcalls` (викликів ініціалізації, які ми розглянемо детальніше нижче), ініціалізація мережевого стеку, монтування кореневої файлової системи (rootfs) та підготовка до запуску першого користувацького процесу.

Саме в цей момент, безпосередньо перед тим, як ядро виконає системний виклик `execve` для запуску `/sbin/init` і передасть управління в user space, ядро розуміє: етап початкового завантаження офіційно та остаточно завершено. Жодна підсистема більше ніколи не потребуватиме функцій чи даних, позначених атрибутом `__init`. 

Настає час прибирання. Потік `kernel_init` викликає функцію `free_initmem()`.

## 5. Механізм звільнення пам'яті: Розбір `free_initmem()`

Функція `free_initmem()` не є універсальною. Вона визначається для кожної апаратної архітектури окремо (зазвичай в архітектурних каталогах, наприклад `arch/x86/mm/init.c` або `arch/arm64/mm/init.c`). Це зумовлено тим, що процес налаштування прав доступу до сторінок пам'яті та керування сторінковими таблицями (TLB, page directories) глибоко залежить від архітектури процесора. Однак, логіка роботи та кінцева мета є спільною для всіх архітектур: звільнити пам'ять між символами `__init_begin` та `__init_end`.

### 5.1. Погляд на реалізацію для архітектури x86

Давайте розглянемо спрощений, але концептуально точний вигляд того, як реалізована `free_initmem` для сучасної архітектури x86_64:

```c
void free_initmem(void)
{
    /* Отримуємо числові значення фізичних адрес із глобальних символів лінкера */
    unsigned long start = (unsigned long)(&__init_begin);
    unsigned long end = (unsigned long)(&__init_end);

    /* 
     * Архітектурно-специфічний захист пам'яті: 
     * Перед звільненням ми повинні переконатися, що сторінки пам'яті, які ми 
     * збираємося віддати процесам користувача, доступні для запису та читання (RW).
     * Якщо секція .init.text була раніше позначена як Read-Only / Executable,
     * ми мусимо змінити атрибути сторінкових таблиць, інакше система впаде 
     * при першій спробі записати туди дані.
     */
    set_memory_rw(start, (end - start) >> PAGE_SHIFT);

    /* Викликаємо загальносистемну функцію звільнення зарезервованої пам'яті */
    free_initmem_default(POISON_FREE_INITMEM);

    /* Виводимо інформаційне повідомлення в лог ядра (dmesg) */
    printk(KERN_INFO "Freeing unused kernel image (initmem) memory: %luk freed\n",
           (end - start) >> 10);
}
```

У сучасних версіях ядра Linux розробники винесли загальну логіку у платформо-незалежну функцію `free_initmem_default()`, яка визначається в спільному коді управління пам'яттю. Вона, у свою чергу, викликає базову функцію `free_reserved_area()`.

```c
void free_initmem_default(int poison)
{
    /* Передаємо початкову і кінцеву адреси, прапорець отруєння та рядок опису */
    free_reserved_area((void *)(&__init_begin), (void *)(&__init_end),
                       poison, "unused kernel image (initmem) memory");
}
```

### 5.2. Анатомія функції `free_reserved_area()`

Функція `free_reserved_area()` (розташована в `mm/page_alloc.c`) є справжньою робочою конячкою процесу звільнення. Її завдання — перевести фізичні сторінки пам'яті зі стану "зарезервовано для ядра" в стан "вільна пам'ять". 

```c
unsigned long free_reserved_area(void *start, void *end, int poison, const char *s)
{
    void *pos;
    unsigned long pages = 0;

    /* Суворе вирівнювання адрес: 
       start вирівнюється ВГОРУ (PAGE_ALIGN) до найближчої межі сторінки.
       end вирівнюється ВНИЗ (через PAGE_MASK) до найближчої межі.
       Це гарантує, що ми ніколи не звільнимо часткову сторінку, яка 
       може містити критичні дані ядра з інших секцій. */
    start = (void *)PAGE_ALIGN((unsigned long)start);
    end = (void *)((unsigned long)end & PAGE_MASK);

    /* Цикл проходить по кожній фізичній сторінці в діапазоні */
    for (pos = start; pos < end; pos += PAGE_SIZE, pages++) {
        
        /* Крок 1: Отруєння пам'яті (якщо ввімкнено) */
        if (poison)
            memset(pos, POISON_FREE_INITMEM, PAGE_SIZE);

        /* Крок 2: Фізичне звільнення сторінки */
        free_reserved_page(virt_to_page(pos));
    }

    /* Якщо було звільнено хоча б одну сторінку, друкуємо звіт */
    if (pages && s)
        pr_info("Freeing %s: %ldK\n", s, pages << (PAGE_SHIFT - 10));

    return pages;
}
```

Розберемо ключові кроки цього алгоритму більш детально:

1. **Безпечне вирівнювання сторінок**: Оскільки менеджер пам'яті працює виключно цілими сторінками, адреси жорстко вирівнюються. Ядро радше пожертвує невеликим фрагментом (кілька байтів) на початку або в кінці секції і залишить їх не звільненими, аніж ризикне звільнити сторінку, яка частково перекривається з постійним кодом.
2. **Отруєння пам'яті (Memory Poisoning)**: Якщо під час компіляції ядра була активована опція зневадження (наприклад, `CONFIG_DEBUG_PAGEALLOC`), параметр `poison` буде істинним. У цьому випадку вміст сторінки перед звільненням примусово заповнюється спеціальним байтовим патерном (магічним числом `POISON_FREE_INITMEM`). На архітектурі x86 цей магічний байт часто дорівнює `0xcc`. Чому саме `0xcc`? В системі команд x86 байт `0xcc` — це машинна інструкція `INT3` (програмне переривання для дебагера). Якщо після звільнення якийсь помилковий драйвер спробує викликати функцію з видаленої секції `__init`, процесор почне виконувати інструкції з цієї сторінки і миттєво натрапить на `INT3`. Це викличе миттєву паніку ядра (Kernel Oops) і зупинить систему, чітко вказавши розробникам на помилку використання звільненої пам'яті (use-after-free). Це геніальний механізм для пошуку прихованих багів.
3. **Функція `free_reserved_page()`**: Для кожної віртуальної адреси `pos` викликається макрос `virt_to_page()`. Він перетворює віртуальну адресу на вказівник на структуру `struct page`, яка є внутрішнім представленням фізичної сторінки в ядрі Linux. Після цього функція `free_reserved_page()` знімає зі сторінки спеціальний прапорець резервування (`PG_reserved`). Наявність цього прапорця означає, що сторінка "належить самому ядру і не може бути заміщена (swapped out) або передана комусь іншому". Знявши цей прапорець, функція викликає базову функцію менеджера пам'яті `__free_page()`, яка нарешті передає сторінку до загального пулу вільної пам'яті.

## 6. Сторінковий алокатор та система Buddy

Щоб зрозуміти кінцевий результат цього процесу, треба згадати, як працює ядро після виклику `__free_page()`. Linux використовує алгоритм Buddy System для управління вільною фізичною пам'яттю. Він групує вільні сторінки в блоки розміром $2^0, 2^1, 2^2, \dots, 2^{10}$ сторінок (від 4 КБ до 4 МБ).

Коли сторінки секції `__init` масово звільняються у циклі `free_reserved_area()`, алгоритм Buddy об'єднує (coalesces) ці розрізнені сторінки у великі неперервні блоки вільної пам'яті (наприклад, по 2 МБ). Ці блоки потрапляють у відповідні зони пам'яті (зазвичай `ZONE_NORMAL`). 

Відтепер ці сторінки стають невідрізними від будь-якої іншої оперативної пам'яті в системі. Коли процес користувача (наприклад, веб-сервер Nginx або база даних PostgreSQL) викликає системний виклик `mmap` або `brk` для виділення пам'яті (через функцію `malloc()` в libc), ядро може з легкістю виділити йому сторінки пам'яті, де ще кілька секунд тому знаходився код ініціалізації контролера переривань!

## 7. Механізм `initcalls`: Динамічна ініціалізація без хардкоду

Опис секцій ініціалізації був би неповним без детального розгляду механізму `initcalls`. У класичних (застарілих) операційних системах функція `main()` (або `start_kernel()`) містила б гігантський список викликів ініціалізації для кожної підсистеми: `init_pci()`, `init_usb()`, `init_net()`, тощо. Такий підхід є негнучким, призводить до конфліктів у системі контролю версій (git) і унеможливлює легке додавання нових драйверів без модифікації ядра.

Linux вирішує цю проблему за допомогою об'єктно-орієнтованого підходу, реалізованого на рівні макросів та лінкера. Будь-який драйвер або підсистема може визначити свою функцію ініціалізації та зареєструвати її за допомогою спеціальних макросів рівнів, таких як `core_initcall()`, `postcore_initcall()`, `arch_initcall()`, `subsys_initcall()`, `fs_initcall()`, `device_initcall()`, або `late_initcall()`. Найпопулярнішим макросом для звичайних драйверів є `module_init()`, який у вбудованому режимі розгортається у `device_initcall()`.

```c
static int __init my_advanced_subsystem_init(void)
{
    // Ініціалізація підсистеми
    return 0;
}

/* Реєструємо функцію на рівні підсистем */
subsys_initcall(my_advanced_subsystem_init);
```

Як це працює під капотом? Макрос `subsys_initcall(fn)` розгортається у визначення вказівника на функцію `fn`. При цьому компілятору дається вказівка розмістити цей вказівник у спеціальній підсекції, наприклад `.initcall4.init` (де 4 — це рівень ініціалізації для підсистем).

Під час компіляції ядра лінкер збирає всі ці вказівники з усіх сотень об'єктних файлів, сортує їх за рівнем (завдяки іменам секцій `.initcall0.init` ... `.initcall7.init`) і складає їх у великий суцільний масив. У скрипті лінкера `vmlinux.lds.S` цей масив обмежується глобальними символами `__initcall_start` та `__initcall_end`.

Під час завантаження системи, функція `do_initcalls()` (яка викликається з потоку `kernel_init()`) виконує надзвичайно просту операцію: вона ітерує по цьому масиву від `start` до `end` і викликає кожну функцію за вказівником. Ядру не потрібно знати імена функцій наперед; воно просто виконує все, що лінкер поклав у цей масив.

Оскільки масив цих вказівників (вся секція `.initcall.init`) також потрібен виключно під час завантаження для виконання викликів, лінкер розміщує цю секцію **всередині** тієї самої великої області пам'яті між `__init_begin` та `__init_end`. Таким чином, і сам код ініціалізації драйверів, і масив вказівників на них автоматично знищуються і звільняються одним махом під час виклику `free_initmem()`.

## 8. Модулі ядра та `__init`: Динамічне завантаження

Увесь описаний вище процес стосується так званого "built-in" коду — функцій та драйверів, які жорстко вкомпільовані в монолітний образ ядра (`vmlinux`). Але архітектура Linux активно підтримує завантажувані модулі ядра (Loadable Kernel Modules, LKM), які компілюються в окремі файли з розширенням `.ko`.

Для модулів концепція `__init` залишається актуальною, але реалізується дещо інакше. Адже модулі можуть завантажуватися динамічно в будь-який час за допомогою утиліт `insmod` або `modprobe`, вже після того, як базове ядро завантажилося і `free_initmem()` була викликана.

Коли модуль компілюється, його функції, позначені макросом `__init`, також потрапляють у секцію `.init.text` всередині ELF-файлу модуля `.ko`.

Під час завантаження модуля в систему викликається системний виклик `finit_module` або `init_module`. Внутрішній менеджер модулів ядра (розташований у `kernel/module/main.c`) аналізує ELF-файл і виділяє оперативну пам'ять для модуля. При цьому він ділить пам'ять модуля на два окремі логічні блоки (allocations):
1. **Core section (Основна секція)**: Це блок пам'яті, який містить постійний код та дані модуля (секції `.text`, `.data`, `.bss`). Цей блок залишиться в пам'яті ядра аж до моменту вивантаження модуля командою `rmmod`.
2. **Init section (Секція ініціалізації)**: Це окремий блок пам'яті, до якого копіюються секції `.init.text` та `.init.data` з файлу модуля.

Менеджер модулів виконує функцію ініціалізації модуля (ту саму, що зареєстрована через `module_init()`). Якщо ця функція завершується успішно (повертає 0), ядро розуміє, що код ініціалізації цього конкретного модуля більше не потрібен. 

Після цього ядро планує асинхронну роботу (через механізм RCU або workqueues), яка викликає функцію `module_memfree()` (або `module_init_free()`). Ця функція повністю звільняє блок пам'яті "Init section" конкретного модуля, повертаючи сторінки до сторінкового алокатора. Таким чином, геніальна оптимізація пам'яті діє не лише під час масивного завантаження всієї системи, а й під час динамічного, точкового завантаження драйверів у режимі реального часу.

## 9. Безпека: Принцип W^X та `__ro_after_init`

Розглядаючи секції ініціалізації, неможливо оминути питання безпеки. Сучасні версії ядра Linux суворо дотримуються архітектурного принципу безпеки, який називається **W^X** (Write XOR Execute). Згідно з цим правилом, жодна сторінка пам'яті в системі не повинна бути одночасно доступною для запису (Writable) і доступною для виконання коду (Executable). Якщо сторінка є Writable і Executable, зловмисник може записати туди шкідливий код (shellcode) і миттєво його виконати.

Секція `.init.text` містить виконуваний машинний код, тому її сторінки повинні бути позначені в сторінкових таблицях (Page Table Entries, PTE) як Executable, але обов'язково Read-Only.
З іншого боку, секція `.init.data` містить змінні, які драйвери можуть змінювати під час ініціалізації, тому її сторінки повинні бути Writable, але обов'язково Non-Executable (NX-bit встановлено).

Саме тому в сучасних скриптах лінкера ці дві секції не змішуються, а вирівнюються окремо на межах сторінок, незважаючи на те, що обидві вони лежать всередині загального блоку `__init_begin` ... `__init_end`. Це дозволяє ядру встановити різні, строгі права доступу (permissions) для різних типів ініціалізаційної пам'яті, навіть якщо ця пам'ять існує лише кілька секунд під час завантаження.

Ще одним потужним інструментом безпеки є макрос `__ro_after_init`. Він використовується для структур даних, які ініціалізуються та заповнюються під час завантаження (наприклад, архітектурно-специфічні таблиці системних викликів, налаштування модулів безпеки LSM (Linux Security Modules), таблиці маршрутизації), але ніколи не повинні змінюватися після того, як система перейшла в повноцінний робочий режим. 

Змінні, позначені атрибутом `__ro_after_init`, розміщуються у спеціальній секції `.data..ro_after_init`. На етапі завантаження ця секція має права доступу Read-Write. Але одразу після завершення всіх `initcalls` і безпосередньо перед викликом `free_initmem()`, ядро викликає спеціальну функцію (наприклад, `mark_rodata_ro()`), яка змінює права доступу до сторінок цієї секції в PTE на Read-Only. На відміну від `__initdata`, ці дані не звільняються з оперативної пам'яті, а просто стають апаратними константами. Це робить ядро значно стійкішим до експлойтів, які намагаються модифікувати критичні структури управління, оскільки будь-яка спроба перезапису викличе апаратне виключення захисту пам'яті.

## 10. Наслідки помилок розробників

Розуміння того, як працюють секції ініціалізації, є обов'язковою і базовою навичкою для будь-якого розробника ядра Linux або драйверів. Неправильне використання цих макросів неминуче веде до нестабільності системи.

Найпоширеніша помилка новачків — це збереження вказівника на структуру, яка лежить в `__initdata`, у глобальну змінну, яка використовується після завантаження. Наприклад:

```c
static struct my_config initial_cfg __initdata = { .mode = 1 };
static struct my_config *active_cfg;

static int __init my_driver_init(void)
{
    /* КРИТИЧНА ПОМИЛКА: Зберігаємо вказівник на тимчасову пам'ять */
    active_cfg = &initial_cfg;
    return 0;
}
```

У цьому сценарії під час завантаження все буде працювати ідеально. Але коли пізніше, під час звичайної роботи системи, драйвер спробує звернутися до `active_cfg->mode`, він звернеться до адреси фізичної сторінки, яка вже була звільнена `free_initmem()` і, ймовірно, виділена для процесу користувача (наприклад, для тексту документа в текстовому редакторі).
Читання з цієї адреси поверне "сміття", що призведе до непередбачуваної поведінки. А запис за цією адресою спотворить дані користувацького процесу (Data Corruption) або викличе Kernel Panic, якщо сторінка більше не відображена в адресному просторі ядра.

Саме для боротьби з такими помилками ядро має спеціальні попередження компілятора (section mismatch warnings) у системі збирання Kbuild. Інструмент `modpost` під час компіляції ядра сканує всі об'єктні файли та шукає ситуації, коли функція зі звичайної секції `.text` намагається викликати функцію з секції `.init.text`, виводячи попередження `WARNING: vmlinux.o(.text+0x...): Section mismatch`. Ігнорування цих попереджень є шляхом до створення вкрай нестабільних драйверів.

## 11. Висновки

Секції ініціалізації (такі як `__init` та `__initdata`) є зразковим і неймовірно елегантним архітектурним механізмом, який дозволяє монолітному ядру Linux "прибирати за собою" після важкого та ресурсомісткого процесу завантаження системи. 

Шляхом хитромудрого групування тимчасового коду та структур даних за допомогою атрибутів компілятора та скриптів лінкера, розробники ядра створили систему, в якій гігабайти вихідного коду (ініціалізація тисяч різних підсистем та драйверів) збираються в єдиний монолітний блок пам'яті. Цей блок можна легко і швидко повернути системі однією простою операцією у функції `free_initmem()`.

Цей економний і раціональний механізм управління пам'яттю відіграє визначальну роль у тому, що Linux зберігає невеликий слід у пам'яті (memory footprint) і залишається універсальною, високоефективною операційною системою. Він дозволяє одному і тому ж ядру керувати як суперкомп'ютерами зі складними масивами накопичувачів, так і крихітними вбудованими пристроями, де кожен байт оперативної пам'яті на рахунку. Розуміння цієї архітектури демонструє не лише те, як працює конкретна ОС, але й загальні принципи оптимізації системного програмного забезпечення.
