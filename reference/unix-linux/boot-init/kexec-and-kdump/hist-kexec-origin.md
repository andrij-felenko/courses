# 📜 Історія kexec та kdump: від LKCD до швидкого перезавантаження Linux

Стандартизація механізмів гарячої заміни ядра та збереження дампу пам'яті в Linux пройшла тривалий шлях від перших пачків ядра для серверів майнфреймів до офіційної інтеграції в основне дерево ядра (mainline kernel). Необхідність у kexec та kdump виникла через критичні обмеження класичного підходу до обробки катастрофічних збоїв ядра (Kernel Panic) та вимоги до мінімізації часу простою (downtime) високодоступних корпоративних систем.

## Ера до kexec: проблеми LKCD та netdump

Наприкінці 1990-х та на початку 2000-х років, коли Linux почав масово впроваджуватися на серверах корпоративного рівня, основною утилітою збереження аварійного дампу був **LKCD** (Linux Kernel Crash Dump). LKCD працював за принципом перезапису Swap-розділу або виділеного дискового блоку безпосередньо з контексту ядра, яке щойно зазнало фатального збою.

Цей підхід мав декілька фундаментальних вад:

1. **Ненадійність контексту паніки**: Коли ядро Linux викликає `panic()`, внутрішній стан підсистем пам'яті, таблиць сторінок та драйверів блокових пристроїв вважається зіпсованим. Виклик коду запісу на диск з панікуючого ядра часто призводив до повторного падіння (double panic) або, що гірше, до затерення файлових систем на сусідніх розділах диска.
2. **Мережевий аварійний дамп (netdump)**: Альтернативне рішення, netdump, намагалося відправляти вміст оперативної пам'яті мережевими пакетами UDP на віддалений сервер. Однак для цього в ядрі доводилося тримати спрощений мережевий стек, що працював при вимкнених перериваннях. Будь-який збій драйвера мережевої карти повністю блокував процес.
3. **Тривалий POST-цикл при перезавантаженні**: Апаратне перезавантаження серверів з багатьма терабайтами пам'яті вимагало тривалого часу на тестування RAM і переініціалізацію шини PCI Express, що робило будь-яку перезавантаження катастрофою для інфраструктури.

## Задум Еріка Бідермана та поява kexec (2002–2005)

У 2002 році розробник Ерік Бідерман (Eric Biederman) запропонував радикально новий підхід: замість спроб змусити зламане ядро писати на диск або наново ініціалізувати апаратуру через BIOS/UEFI, потрібно завантажити нове, повністю працездатне ядро безпосередньо з пам'яті вже запущенної системи.

Ця ідея матеріалізувалася у вигляді системного виклику `kexec_load` та архітектури **kexec** (Kernel Execution). Головний принцип kexec полягав у тому, що нове ядро сприймається поточним ядром просто як набір сегментів даних у користувацькому просторі. Спеціальний ізольований код релокації (названий *purgatory*) копіює ці сегменти на їхні фінальні фізичні адреси і виконує прямий стрибок на точку входу нового ядра.

Офіційне включення `kexec` до основного дерева ядра Linux відбулося у версії **Linux 2.6.13** (серпень 2005 року).

## Народження kdump: переосмислення аварійного дампу

Після появи `kexec` Ерік Бідерман та розробники з Red Hat і IBM усвідомили, що kexec є ідеаленим фундаментом для створення надійного механізму краш-дампів. Так народилася технологія **kdump**.

Замість того щоб писати дамп зі збійного ядра, kdump пропонує заздалегідь (під час нормального старту системи) завантажити за допомогою kexec друге, так зване «аварійне ядро» (Crash Kernel) в окремо зарезервовану ділянку оперативної пам'яті (`crashkernel=`).

Коли в основному ядрі відбувається Kernel Panic, воно не намагається писати на диск. Воно виконує миттєвий kexec-стрибок у Crash Kernel. Оскільки Crash Kernel живе в зарезервованій пам'яті, його код і структури даних є на 100% чистими. Crash Kernel бачить усю решту фізичної пам'яті померлого ядра просто як байти даних і експортує її через псевдофайл `/proc/vmcore` для безпечного збереження.

## Еволюція під Secure Boot: від `kexec_load` до `kexec_file_load`

Із широким впровадженням UEFI Secure Boot у 2010-х роках виникла нова проблема безпеки. Класичний системний виклик `kexec_load()` приймав від утиліти користувача вже розпаковані сегменти ядра та довільний код purgatory. Це дозволяло утиліті з правами root завантажити в пам'ять непідписане або шкідливе ядро в обхід механізму UEFI Secure Boot, повністю нівелюючи ланцюг довіри.

Для вирішення цієї загрози у 2014 році розробник Вівек Ґоял (Vivek Goyal) з Red Hat створив новий системний виклик — **`kexec_file_load()`**, який був включений до ядра **Linux 3.17**.

На відміну від свого попередника, `kexec_file_load()` приймає від користувацького простору не розібрані сегменти, а відкритий файловий дескриптор підписаного образу ядра (vmlinuz/bzImage). Ядро Linux самостійно розпаковує образ у ядерному просторі, перевіряє криптографічний підпис образу за допомогою вбудованих ключів Secure Boot і формує сегменти завантаження. Якщо підпис недійсний, ядро відхиляє завантаження з помилкою `EKEYREJECTED`.

| Ера / Технологія | Основний механізм | Головні недоліки | Статус у сучасному Linux |
| :--- | :--- | :--- | :--- |
| **LKCD (1999)** | Запис з контексту паніки на Swap | Високий ризик double panic та пошкодження ФС | Застаріла, видалена |
| **netdump (2001)** | Передача дампу через спрощений UDP | Залежність від мережевого стеку у збійному ядрі | Застаріла, замінена kdump |
| **kexec_load (2005)** | Підготовка сегментів у userspace | Неможливість перевірки підписів Secure Boot | Підтримується для legacy |
| **kexec_file_load (2014)** | Перевірка підпису vmlinuz у ядрі | Вимагає підтримки архітектури в ядрі | Стандарт для Secure Boot |

Завдяки еволюції від LKCD до `kexec_file_load` сучасні операційні системи Linux отримали змогу виконувати миттєві гарячі оновлення ядра та зберігати 100% надійні аварійні дампи навіть у найсуворіших корпоративних середовищах із вимогами Secure Boot.
