Коли критичний сервер із сотнями гігабайтів оперативної пам'яті і складними масивами зберігання даних раптово падає (kernel panic), стандартне перезавантаження через апаратне скидання (hardware reset) стає справжнім жахом. Повний цикл POST (Power-On Self-Test), ініціалізація пам'яті контролерами, перевірка PCIe-пристроїв та розкручування дисків можуть займати від 5 до 15 хвилин. За цей час система недоступна, а що найгірше — стан пам'яті в момент падіння безповоротно втрачається, залишаючи інженерів наодинці з загадковими повідомленнями в логах (якщо вони взагалі встигли туди записатися). Проблема вимагає механізму, який би дозволяв миттєво запустити нове, свіже ядро, обминаючи апаратну ініціалізацію, і при цьому зберегти точний знімок пам'яті «мертвого» ядра для подальшого розслідування. Саме цю фундаментальну інженерну задачу вирішує пара технологій: **kexec** та **kdump**.

## Анатомія kexec: Перезавантаження без BIOS/UEFI

**kexec** (Kernel Execution) — це системний виклик і механізм у ядрі Linux, який дозволяє завантажити та запустити нове ядро безпосередньо з поточного, яке вже працює. Це обходить фазу апаратного завантаження (BIOS/UEFI та завантажувача), різко скорочуючи час простою при запланованих перезавантаженнях. 

### Як працює системний виклик `kexec_load`

Ядро Linux експортує два основних системних виклики для kexec: `kexec_load()` та `kexec_file_load()`.

```c
long kexec_load(unsigned long entry, unsigned long nr_segments,
                struct kexec_segment *segments, unsigned long flags);
```

Коли утиліта користувацького простору (наприклад, `/sbin/kexec`) готує нове ядро до запуску, вона розбирає файл ядра (vmlinuz), розпаковує його (якщо використовується `kexec_load`, а не `kexec_file_load`) та initramfs, після чого розміщує їх у пам'яті. 

Структура `kexec_segment` визначає, які шматки даних куди потрібно скопіювати у фізичній пам'яті:
```c
struct kexec_segment {
    const void *buf;     // Вказівник на буфер у користувацькому просторі
    size_t bufsz;        // Розмір буфера
    const void *mem;     // Цільова фізична адреса у пам'яті
    size_t memsz;        // Розмір у фізичній пам'яті
};
```

Ці сегменти (ядро, initramfs, командний рядок, DTB для ARM) завантажуються в поточну оперативну пам'ять. Однак, ядро не може просто перестрибнути на новий код. Старе ядро ще працює! Тому створюється спеціальний перехідний код (relocation code), який розміщується в безпечній сторінці пам'яті. Цей код має одну мету: після зупинки всіх процесів і процесорів остаточно скопіювати сегменти нового ядра на їхні цільові місця (перезаписуючи старе ядро) і передати управління на точку входу (`entry`) нового ядра.

### Процес переходу (kexec transition)

Коли викликається `kexec -e` (або система виконує `reboot` і kexec налаштовано), відбувається таке:
1. **Зупинка користувацького простору**: Система завершує процеси (через systemd).
2. **Device Shutdown**: Ядро викликає функції `shutdown` для кожного драйвера пристрою, щоб перевести апаратуру в спокійний стан. Це критично: якщо DMA (Direct Memory Access) мережевої карти продовжить писати в пам'ять, воно затре нове ядро!
3. **Disable Interrupts**: На локальному CPU вимикаються переривання (`cli` на x86).
4. **Halt Other CPUs**: Всі інші логічні ядра процесора зупиняються (переводяться в стан очікування через IPI — Inter-Processor Interrupts).
5. **Purgatory/Relocation**: Поточне ядро перемикається на виконання коду релокації. Цей код копіює підготовлені сегменти нового ядра поверх старого. 
6. **Jump**: Процесор стрибає на адресу старту нового ядра. Нове ядро починає ініціалізацію так, ніби його щойно завантажив GRUB.

## kdump: Збереження стану після Kernel Panic

Якщо `kexec` — це інструмент для швидкого перезавантаження, то **kdump** використовує механіку kexec для іншої, більш складної мети: захоплення дампу пам'яті (crash dump) при фатальному збої системи (Kernel Panic, OOPS, NMI watchdog timeout, апаратні помилки).

Проблема паніки ядра полягає в тому, що стан системи вже скомпрометовано. Вказівники можуть бути зіпсовані, структури даних зруйновані, планувальник задач не працює. Не можна просто взяти і записати вміст пам'яті на диск з поточного (панікуючого) ядра — файлова система або драйвер диска можуть записати сміття і знищити дані користувача.

Рішення: перемкнутися на абсолютно нове, ізольоване ядро (Crash Kernel), яке завантажується за допомогою kexec у спеціально зарезервовану ділянку пам'яті. Це нове ядро чисте, неушкоджене, і має власні драйвери та файлові системи для безпечного запису дампу.

### Зарезервована пам'ять: параметр `crashkernel=`

Щоб kdump працював, Crash Kernel має бути розміщено в пам'яті заздалегідь. Під час звичайного завантаження системи, первинне ядро резервує шматок фізичної пам'яті, який воно саме не буде використовувати. Це робиться через параметр завантаження ядра `crashkernel`.

Приклад у `/etc/default/grub`:
```text
crashkernel=512M
# або складніше
crashkernel=1G-4G:192M,4G-64G:256M,64G-:512M
```
Цей рядок означає: якщо система має від 64 ГБ RAM і більше, зарезервувати 512 МБ пам'яті під crash kernel.

Коли первинне ядро падає, функція `panic()` викликає `crash_kexec()`. Всі інші CPU зупиняються (через NMI, якщо вони не реагують). Контролер переривань (APIC) обнуляється. Процесор стрибає на код Crash Kernel, який розпаковується *виключно в межах цих зарезервованих 512 МБ*.



### Експорт пам'яті: `/proc/vmcore`

Коли Crash Kernel завантажується, він має доступ до своєї власної пам'яті (512 МБ), але йому також доступна вся інша фізична пам'ять системи, де лежить «труп» первинного ядра.

Щоб полегшити читання цієї пам'яті, ядро експортує її у вигляді файлу у форматі ELF core (Executable and Linkable Format) за шляхом `/proc/vmcore`. 

Як Crash Kernel знає, де лежить пам'ять старого ядра і як вона відображається? Під час завантаження kdump-ядра йому передається спеціальний параметр, наприклад `elfcorehdr=0x3f000000`. Цей параметр вказує на ELF-заголовок, який був попередньо сформований первинним ядром і зберігає таблицю сегментів (PT_LOAD), що описує всю фізичну пам'ять.

### Утиліта makedumpfile: Стиснення і фільтрація

Копіювати 256 ГБ оперативної пам'яті на диск при кожному збої — це довго і ресурсоємно. Більш того, більша частина цієї пам'яті не має цінності для розслідування паніки ядра (наприклад, сторінки кешу сторінок, вільна пам'ять або пам'ять користувацького простору).

Тут вступає в гру утиліта **makedumpfile**. Її запускають в оточенні initramfs kdump-ядра. Її задача:
1. Прочитати `/proc/vmcore`.
2. Відфільтрувати непотрібні сторінки. Для цього потрібні *налагоджувальні символи* або хоча б *VMCOREINFO* (маленький блок даних, що первинне ядро залишає в пам'яті, описуючи зміщення основних структур, таких як таблиці сторінок).
3. Стиснути дані (zlib, lzo, snappy).
4. Записати результат на диск (локальний диск, NFS, SSH).

```bash
# Приклад використання makedumpfile (виконується автоматично скриптами kdump)
makedumpfile -l --message-level 1 -d 31 /proc/vmcore /var/crash/127.0.0.1-2026-08-10-14:30:00/vmcore
```
Прапорець `-d 31` (0x1F) вказує маску фільтрації (виключити zero pages, cache pages, cache private, user pages, free pages). Завдяки цьому дамп системи з 256 ГБ RAM може займати лише кілька сотень мегабайтів і містити лише ядерні структури.

## Налаштування kdump на практиці (RHEL/Ubuntu)

Встановлення пакетів:
- **Ubuntu/Debian**: `sudo apt install kdump-tools crash kexec-tools`
- **RHEL/CentOS/Rocky**: `sudo dnf install kexec-tools`

Після встановлення та конфігурації `crashkernel=` в GRUB, сервіс `kdump.service` генерує спеціальний initramfs для kdump (у `/var/lib/kdump/` або `/boot/`), який містить драйвери для доступу до цільового сховища (наприклад, драйвери RAID або мережеві модулі для NFS).

Щоб перевірити, чи kdump налаштовано правильно і чекає на збій:
```bash
cat /sys/kernel/kexec_crash_loaded
# Має вивести 1
```

Щоб спровокувати тестовий збій (ОБЕРЕЖНО: це справді обвалить систему!):
```bash
echo c > /proc/sysrq-trigger
```
Ця команда імітує NULL pointer dereference. Система миттєво зависне на частку секунди, потім ви побачите завантаження нового ядра (на консолі). За хвилину дамп буде збережено в `/var/crash/`, і система автоматично перезавантажиться у звичайний режим.

## Аналіз дампу: утиліта crash

Маючи файл `vmcore`, інженери використовують утиліту **crash** — потужний інтерактивний інструмент, розроблений Red Hat, який поєднує можливості GDB з глибоким розумінням внутрішніх структур ядра Linux.

Для аналізу потрібен сам дамп і файл `vmlinux` з налагоджувальними символами (з пакетів `linux-image-debug` або `kernel-debuginfo`).

```bash
crash /usr/lib/debug/boot/vmlinux-6.8.0-100-generic /var/crash/202608101430/vmcore
```

У середовищі crash можна виконувати команди для дослідження стану «замороженого» ядра:
- `bt` (backtrace) — показати стек викликів процесу, що панікує.
- `ps` — список усіх процесів, які працювали на момент збою.
- `log` — вивести системний буфер повідомлень (dmesg).
- `kmem -i` — статистика використання пам'яті.
- `struct task_struct <addr>` — розібрати структуру завдання за вказівником.

kdump є незамінним інструментом у дата-центрах. Завдяки йому адміністратори можуть швидко відновити надання сервісів (через kexec-перезавантаження), а розробники ядра або інженери підтримки отримують вичерпні матеріали для розслідування інциденту в спокійній обстановці.
