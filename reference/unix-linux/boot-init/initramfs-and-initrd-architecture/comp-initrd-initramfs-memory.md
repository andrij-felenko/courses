# 📊 Порівняльний аналіз initrd та initramfs: пам'ять, VFS та мотив розробника

Ця порівняльна вставка деталізує глибокі архітектурні та системні відмінності між застарілою технологією **initrd** (Initial RAM Disk) та сучасною технологією **initramfs** (Initial RAM Filesystem). Порівняльний аналіз охоплює механізми використання системної пам'яті, шари абстракції у Virtual File System (VFS), вимоги до підсистеми драйверів ядра, а також логіку передачі керування на етапі переходу до справжнього кореня.

### Архітектурні причини відмови від блокового initrd

Технологія `initrd` створювалася в середині 1990-х років як швидке рішення для підтримки модульних ядер Linux. Вона спиралася на концепцію емуляції блокового дискового носія в оперативній пам'яті. Хоча це дозволило постачати універсальні дистрибутивні ядра, механізм містив фундаментальний неефективності, які стали критичними зі зростанням навантажень і обсягів пам'яті.

При використанні `initrd` ядро створювало віртуальний пристрій `/dev/ram0`. Цей пристрій оброблявся повноцінним блоковим драйвером `brd.c`, а дані всередині нього форматувалися у звичайну файлову систему ext2 або minix. Будь-яке звернення до файлу на такому «диску» викликало виконання повного стеку дискового введення-виведення: формувалася структура `struct bio`, запит проходив через планировщик I/O, розкодовувалися іноди ext2 і заповнювався буферний кеш блокового пристрою.

В результаті виникало потрійне дублювання даних (англ. *triple buffering*):
1. **RAM Disk Buffer:** Базові блоки пам'яті під пристроєм `/dev/ram0`.
2. **Buffer Cache:** Кеш блоків файлової системи ext2 у пам'яті ядра.
3. **VFS Page Cache:** Сторінковий кеш файлової системи при виконанні або читанні бінарних файлів програмами.

Читання файлу розміром 10 МБ вимагало виділення від 25 до 30 МБ оперативної пам'яті. Крім того, обсяг пам'яті задавався жорстко через параметр `ramdisk_size` під час завантаження. Якщо під `/dev/ram0` виділялося 32 МБ пам'яті, усі 32 МБ залишалися заблокованими в RAM до моменту перезавантаження, навіть якщо реальні файли займали лише 4 МБ.

### Порівняльна таблиця характеристик

| Архітектурний аспект | Застарілий initrd (RAM Disk) | Сучасний initramfs (rootfs / cpio) |
|---|---|---|
| **Представлення в пам'яті** | Емуляція блокового пристрою `/dev/ram0` | Файлова система `tmpfs` у сторінковому кеші (page cache) |
| **Формат образу** | Готовий образ ФС (ext2, ext3, minix) | Потоковий архів `cpio` (newc format, стиснений або сирий) |
| **Виділення пам'яті** | Фіксоване (`ramdisk_size`), виділяється на старті повністю | Динамічне (розмір зростає/зменшується з файлами) |
| **Дублювання кешу** | Потрійне (Buffer Cache + RAM Disk Cache + VFS Page Cache) | Нульове (дані файлів живуть прямо у VFS Page Cache) |
| **Вимоги до ядра** | Блоковий шар + драйвер `brd` + драйвер ФС `ext2` | Лише вбудований розпаковувач `init/initramfs.c` |
| **Початковий процес** | Запуск `/linuxrc` | Запуск `/init` (як PID 1) |
| **Механізм передачі кореня** | Виклики `pivot_root` та `umount /initrd` | Утиліта `switch_root` (`mount MS_MOVE` + `execve`) |
| **Звільнення пам'яті** | Вимагає виклику `freeramdisk` (часто блокується) | Миттєве повернення сторінок RAM при видаленні файлів (`unlink`) |
| **Можливість склеювання** | Ні (один цілісний образ диска) | Так (конкатенація кількох архіві cpio в один потік) |

### Глибинні відмінності в підсистемі VFS та виконання IOPS

Перехід до `initramfs` став можливим завдяки рефакторингу Virtual File System (VFS) в ядрах Linux 2.6. Введення уніфікованого сторінкового кешу (англ. *page cache*) дозволило створити файлову систему `ramfs` (та її розширену версію `tmpfs`), яка існує виключно у вигляді структур VFS у оперативній пам'яті без проміжного блокового рівня.

Основні технічні відмінності у шляху проходження даних:

1. **Монтування блокового пристрою проти створення вузлів VFS:**
   Під час завантаження `initrd` ядро повинне сформувати повноцінний масив блокових секторів у пам'яті, який імітує фізичний диск. Будь-яке читання з цього «диска» проходить повний шлях драйвера блокового пристрою: створення запитів `struct bio`, проходження крізь плановик I/O, розшифровку таблиць інод ext2 та заповнення буферного кешу. 
   
   Натомість `initramfs` повністю ігнорує блоковий шар. Розпаковувач `unpack_to_rootfs()` створює записи `struct dentry` та `struct inode` безпосередньо у внутрішній `tmpfs` пам'яті ядра під назвою `rootfs`. Файли не мають підкладених секторів; їхні сторінки знаходяться прямо в оперативній пам'яті, що забезпечує максимальну швидкість читання й запису.

2. **Динаміка очищення ресурсу OAM (Operational Memory):**
   При використанні `initrd`, після переходу в справжній корінь через `pivot_root`, RAM-диск залишався прикріпленим у структурі пристроїв ядра. Навіть якщо файли з нього більше не використовувалися, виділена пам'ять залишалася недоступною для інших процесів, доки драйвер не отримував спеціальний ioctl `BLKFLSBUF` або не здійснювалося вивантаження пристрою.
   
   В `initramfs` утиліта `switch_root` перед перенесенням кореня рекурсивно викликає `unlink()` для всіх файлів тимчасового середовища. Оскільки `tmpfs` спирається безпосередньо на розподільник сторінок пам'яті ядра (page allocator), видалення кожного файлу миттєво повертає його фізичні сторінки пам'яті у загальний пул вільних сторінок системи.

### Вплив на продуктивність завантаження

Використання `initramfs` значно скорочує час завантаження системи. Вхідний потік `cpio` розпаковується за один послідовний прохід пам'яті зі швидкістю, що обмежена лише продуктивністю декомпресора (`zstd` або `gzip`). Відсутність необхідності ініціалізувати дисковий планувальник I/O та драйвер ext2 економить сотні мілісекунд на ранньому етапі ініціалізації ядра.
