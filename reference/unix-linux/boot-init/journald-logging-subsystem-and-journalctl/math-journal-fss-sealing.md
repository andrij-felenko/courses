# 🧮 Математична модель Forward Secure Sealing (FSS) у journald

Математичне доведення цілісності та неможливості модифікації записів у системному журналі `systemd-journald` спирається на криптографічну схему генератора ключів із підтримкою прямої безпеки (англ. *Forward-Secure Key Generator*, FSKG) Белларе-Майнера (Bellare-Miner cryptographic model). Нижче розкрито алгоритмічну модель епох, рекурентне обчислення HMAC-ланцюгів, побудову хеш-дерев Меркла для записів та математичне доведення неможливості компрометації минулих логів у разі захоплення поточного секретного ключа.

## Постановка задачі та модель загроз

Припустимо, що у звичайному текстовому журналі зловмисник отримує привілеї суперкористувача `root` у момент часу `T_attack`. Йому відомо весь вміст накопичувача та оперативної пам'яті сервера. Зловмисник бажає відредагувати або вилучити запис події `E_i`, зроблений у минулий момент часу `T_past < T_attack`, таким чином, щоб утиліта перевірки цілісності вважала журнал автентичним.

Для унеможливлення таких дій часова вісь ділиться на рівні інтервали — **епохи** (англ. *epochs*) тривалістю `τ` (за замовчуванням `15 хвилин` або `900 секунд`):

```
t_epoch = floor((t_realtime - t_epoch_start) / τ)
```

Де `t_realtime` — поточна часова мітка реального часу UTC, `t_epoch_start` — час початкової ініціалізації журналу, `τ` — константа епохи.

## Генерація та рекурентне однонаправлене оновлення ключів

Схема FSS оперує трьома основними елементами:
1. **Майстер-ключ `K_master`**: 256-бітний криптографічний секрет, згенерований утилітою `journalctl --setup-keys`. Зберігається виключно офлайн (на роздрукованому QR-коді або зовнішньому фізичному носії) і ніколи не зберігається на самому сервері.
2. **Ланцюжок ключів підпису `K_t`**: секретний ключ, що перебуває в оперативній пам'яті демона journald протягом епохи `t`.
3. **Публічна запечатана мітка `F_t`**: записується у заголовок бінарного файлу логів для верифікації.

### Алгоритм ініціалізації та ітерації ключів (FSKG State Transitions)

На початку роботи системи з `K_master` обчислюється ключ нульової епохи `K_0`:

```
K_0 = HMAC-SHA256(K_master, "systemd-journald-fss-init" · 0)
```

Перехід від ключа поточного інтервалу `t` до ключа наступного інтервалу `t + 1` виконується за однонаправленою псевдовипадковою функцією на основі криптографічного хешування HMAC-SHA256:

```
K_{t+1}
= HMAC-SHA256(K_t, "systemd-journald-fss-advance")  [рекурентне однонаправлене оновлення]
```

**Критична умова безпеки:** Одразу після обчислення `K_{t+1}` ключ попередньої епохи `K_t` безповоротно вилучається з оперативної пам'яті викликом `explicit_bzero()`.

Загальне рівняння генерації ключа для довільної епохи `t` через функцію розгортання:

```
K_t
= HMAC-SHA256(K_{t-1}, "advance")
= HMAC-SHA256(HMAC-SHA256(K_{t-2}, "advance"), "advance")
= HMAC-SHA256^(t)(K_0, "advance")                   [t-кратна композиція однонаправленої функції]
```

## Запечатування об'єктів журналу та побудова дерев Меркла

Усі об'єкти записів `OBJECT_ENTRY`, створені всередині епохи `t`, об'єднуються у бінарне хеш-дерево Меркла (Merkle Tree). Це забезпечує можливість швидкої перевірки як окремого запису, так і всієї послідовності подій за епоху.

Нехай упродовж епохи `t` записано `n` подій з хешами `h_1, h_2, ..., h_n`, де кожен хеш обчислюється від бінарного вмісту об'єкта запису та його послідовного номера:

```
h_i = SHA256(OBJECT_ENTRY_i · i · t)
```

Листки дерева обчислюються як хеші пар сусідніх подій:

```
H_{1,2} = SHA256(h_1 · h_2)
H_{3,4} = SHA256(h_3 · h_4)
```

Корінь дерева Меркла `R_t` є агрегованим цифровим відбитком усіх подій епохи `t`.

Підсумковий підпис запечатування епохи `S_t` обчислюється як HMAC від кореня дерева Меркла `R_t` та номера епохи `t`:

```
S_t = HMAC-SHA256(K_t, R_t · t)
```

У заголовок бінарного файлу `.journal` для епохи `t` записується значення підпису `S_t` та контрольний публічний хеш `F_t`:

```
F_t = SHA256(K_t)
```

## Математичне доведення властивості Forward Security (Прямої безпеки)

Припустимо від супротивного, що зловмисник здобув повний контроль над сервером під час епохи `T_attack = 5`. В ОЗП демона знаходиться лише поточний ключ `K_5`.

Зловмисник бажає відредагувати запис епохи `t = 2` й обчислити новий дійсний підпис `S_2'`. Для обчислення `S_2'` зловмиснику необхідно мати секретний ключ `K_2`.

Спроба відновити `K_2` з відомого `K_5` вимагає знаходження прообразу композиції функцій HMAC-SHA256:

```
K_5 = HMAC(HMAC(HMAC(K_2, "advance"), "advance"), "advance")
```

Формальне твердження безпеки:
Якщо HMAC-SHA256 є криптографічно стійкою функцією проти знаходження прообразу (Preimage Resistance), то імовірність `ε` обчислення `K_2` за відомим `K_5` за поліноміальний час `T_poly` обмежена зверху:

```
Probability(Compute K_2 from K_5) <= 2⁻²⁵⁶ + epsilon_HMAC
```

Оскільки розрядність SHA256 становить 256 біт, математична складність обчислення `K_2` за відомим `K_5` становить:

```
Complexity(K_2 | K_5) = 2²⁵⁶ операцій
```

Це доводить, що зловмисник **математично нездатний** згенерувати дійсний підпис `S_2'` для модифікованого минулого запису.

## Алгоритм офлайн-верифікації цілісності

Адміністратор виконує перевірку цілісності логів за допомогою команди `journalctl --verify --verify-key=...` на довіреному ізольованому комп'ютері, куди вводиться офлайн-ключ `K_master`.

Покроковий алгоритм верифікації:

```
1. K_0' = HMAC-SHA256(K_master, "systemd-journald-fss-init" · 0)  [генерація K0]

2. Для кожної епохи t = 0, 1, 2, ..., N:
   a. F_t' = SHA256(K_t')                                          [обчислення контрольного хешу]
   b. Якщо F_t' != F_t (із заголовка файлу):
      ПОМИЛКА: Ключ епохи t підроблено або журнал обрізано!
   
   c. Обчислення кореня дерева Меркла R_t' із прочитаних об'єктів OBJECT_ENTRY.
   d. S_t' = HMAC-SHA256(K_t', R_t' · t)                           [обчислення підпису]
   e. Якщо S_t' != S_t (із заголовка файлу):
      ПОМИЛКА: Записи подій епохи t було модифіковано!
   
   f. K_{t+1}' = HMAC-SHA256(K_t', "systemd-journald-fss-advance") [перехід до наступного ключа]
```

Якщо всі епохи `t = 0 ... N` пройшли перевірку, цілісність журналу вважається повністю доведеною.

## Математичні крайні випадки та обмеження алгоритму

1. **Аномалія стрибка часу назад (Clock Backward Jump)**:
   Якщо системний годинник переведено назад (наприклад через синхронізацію NTP або помилку адміністрування), значення `t_epoch` може зменшитися. Демон journald виявляє це шляхом порівняння `t_epoch` з поточним значенням епохи у файлі. Демон відмовляється повертатися до попереднього ключа `K_{t-1}` (бо він знищений) і продовжує запис у поточну епоху `t`, занотовуючи прапорець аномалії у метадані.
2. **Атака на обрізання журналу (Log Truncation Attack)**:
   Зловмисник, що володіє привілеями `root`, не може підробити минулі записи, але теоретично може вилучити останні кілька епох логів разом із підписами `S_t`. Для захисту від цього `journald` підтримує збереження поточного номера епохи у запечатаній енергонезалежній пам'яті TPM (Trusted Platform Module) або надсилання регулярних хеш-станцій на віддалений сервер логування.
3. **Завершення терміну дії ключа (Max Epoch Boundary)**:
   Кількість епох зашифрована у структурі заголовка FSS як 32-бітне число (`2³² - 1 ≈ 4.29 · 10⁹` епох). При тривалості епохи 15 хвилин цього вистачає на `122000` років безперервної роботи без необхідності зміни майстер-ключа `K_master`.
