# 📜 Історія кешу маршрутів Linux: від O(1) оптимізації до DDoS-уразливості та видалення в Linux 3.6

Сьогодні кожен мережевий пакет у Linux проходить сухий, безфайловий та безадресний (stateless) пошук у префіксному дереві LC-Trie підсистеми FIB. Проте так було не завжди. Протягом майже двох десятиліть — з перших релізів ядра 1.x і аж до версії Linux 3.5 — мережевий стек спирався на динамічний **кеш маршрутів IPv4 (IPv4 Route Cache)**.

Історія виникнення, розквіту, катастрофічного падіння та остаточного видалення кешу маршрутів у 2012 році є одним із найпочальніших уроків в історії системного програмування: **оптимізація, розроблена для прискорення стандартного трафіку, може перетворитися на смертельну зброю в руках зловмисника**.

---

## 1. Ера Route Cache: Як і навіщо був створений кеш маршрутів

У 1990-х та на початку 2000-х років обчислювальна потужність процесорів була обмеженою, а алгоритми пошуку в таблицях маршрутизації ядра спиралися на лінійні масиви або прості хеш-таблиці `fn_hash`. 

Щоб не виконувати важкий пошук у FIB для кожного з мільйонів пакетів, розробники ядра Linux інтегрували підсистему кешування `rt_hash_table`:

1. Коли перший пакет мережевого потоку від IP `A` до IP `B` потрапляв у систему, ядро здійснювало повний і відносно повільний пошук у базі FIB (Forwarding Information Base).
2. Знайдений результат — вихідний інтерфейс, IP-адресу шлюзу, MTU та вказівник на таблицю сусідів (ARP) — ядро пакувало в структуру `struct rtable` (яка містила поле `struct dst_entry`).
3. Запис розміщувався у глобальній хеш-таблиці `rt_hash_table`. Ключем хешування слугува 4-кортеж: `(Source IP, Destination IP, ToS, Input Interface)`.
4. Усі наступні пакети того ж потоку знаходили готовий об'єкт `dst_entry` за одну операцію обчислення хешу `O(1)`, повністю минаючи складний пошук у FIB та базу правил RPDB.

```
Вхідний пакет -> Хеш (Src, Dst, ToS, iif) -> rt_hash_table -> dst_entry знайдено -> Швидка відправка
```

Ця архітектура бездоганно працювала у вебсерверах та корпоративних мережах тих часів. Переважна більшість мережевого трафіку складалася з довготривалих TCP-сесій (FTP, HTTP/1.0), де між двома IP-адресами передавалися тисячі пакетів поспіль. Коефіцієнт влучання в кеш (Cache Hit Ratio) перевищував 99%, а обробка влучання вимагала всього кількох інструкцій CPU.

## 2. Ахіллесова п'ята: Отримання BGP Full View та зростання Інтернету

Наприкінці 2000-х років мережевий ландшафт вибухоподібно змінився. З'явилися магістральні маршрутизатори на базі Linux, які отримували від BGP-провайдерів повні таблиці глобальної маршрутизації Інтернету (**BGP Full View**), що нараховували сотні тисяч префіксів.

Для підтримки кешу ядро Linux виділяло фіксовану частину оперативної пам'яті під `rt_hash_table`. Розмір цієї хеш-таблиці обчислювався під час завантаження системи і залежав від обсягу RAM:

:::tabs
```c
/* net/ipv4/route.c (Ядро Linux 2.6) */
int __init ip_rt_init(void) {
    ...
    rt_hash_table = alloc_large_system_hash("IPv4 route cache",
                                            sizeof(struct rt_hash_bucket),
                                            rt_hash_mask,
                                            ...);
    ...
}
```
```cpp
// Концептуальне моделювання кешу маршрутів у C++ через RAII-контейнери (std::vector / std::unique_ptr)
namespace net::kernel_sim {
    void ip_rt_init(std::size_t bucket_count) {
        // У C++ динамічні таблиці кешу моделюються через безпечні смарт-покажчики
        auto rt_hash_table = std::make_unique<rt_hash_bucket[]>(bucket_count);
        // Ініціалізація та захист кошиків кешу
    }
}
```
:::

Проблема полягала в тому, що кожна комірка `struct rt_hash_bucket` була захищена глобальним або по-кошиковим спинлоком `rt_hash_lock`. 

Коли мережеве навантаження зростало до мільйонів пакетів на секунду від різних джерел, багатоядерні сервери (8–16 CPU cores) починали витрачати до 80% обчислювального часу не на маршрутизацію трафіку, а на межпроцесорне узгодження кеш-ліній CPU (`cache line bouncing`) та очікування вивільнення спинлоків при модифікації `rt_hash_table`.

## 3. DDoS-катастрофа: Сценарій Random Source IP Spoofed Attack

Справжньою виразкою кешу маршрутів виявилася його вразливість до розподілених атак на відмову в обслуговуванні (DDoS).

У 2010–2011 роках зловмисники почали масово застосовувати атаки типу **Random Source IP Flooding** (генерація потоку UDP/SYN пакетів із випадковими, підробленими IP-адресами джерела).

Ось що відбувалося всередині ядра Linux 2.6 під час такої атаки:

1. **Суцільні промахи кешу:** Кожен вхідний пакет мав нову комбінацію `(Source IP, Destination IP)`. Відповідно, пошук у `rt_hash_table` щоразу завершувався промахом.
2. **Вибухове створення записів:** Для кожного пакета ядро запускало процес `rt_intern_hash()`, створюючи новий запис `struct rtable` і розміщуючи його в кеші.
3. **Переповнення хеш-кошиків:** Мільйони нових записів заповнювали осередки `rt_hash_table`, перетворюючи `O(1)` хеш-таблицю на довжелезні зв'язані списки.
4. **Вмикання Garbage Collector:** Коли кількість записів перевищувала ліміт `ip_rt_max_size`, ядро примусово запускало збирач сміття `rt_garbage_collect()`. Збирач сміття намагався в режимі реального часу обходити списки, шукати застарілі записи та звільняти пам'ять.
5. **Таймер скидання хешу:** При надмірному заповненні ядро викликало функцію `rt_secret_rebuild_timer()`, яка повністю очищала всю таблицю кешу та змінювала секретний сольовий ключ хешування, щоб захиститися від колізій.
6. **Каскадний колапс (Thrashing):** Очищення кешу призводило до того, що ВСІ подальші пакети (включаючи легітимний трафік) одночасно отримували промахи кешу. Сервер входив у нескінченний цикл «виділення пам'яті → переповнення → примусове очищення кешу → шторм блокувань». Навантаження на CPU досягало 100% у режимі ядра (`sys time`), а мережевий стек повністю припиняв пропускати трафік.

Атака зі сміттєвим трафіком всього в 50–100 тисяч пакетів на секунду (що становить мізерні десятки мегабіт) могла повністю паралізувати потужний сервер із 64 Гб RAM та 16 ядрами CPU!

## 4. Патчсет Девіда Міллера та видалення кешу в Linux 3.6

У 2012 році головний мейнтейнер мережевої підсистеми ядра Linux **Девід Міллер (David S. Miller)** зробив радикальний висновок: *будь-які спроби "полагодити" кеш маршрутів (додаванням нових замків, балансуванням хешу чи оптимізацією збирача сміття) є глухим кутом*.

У серії патчів для ядра Linux 3.6 (COMMIT: `ipv4: Delete routing cache`) IPv4 Route Cache було **повністю вилучено з ядра Linux**.

Девід Міллер вирізав тисячі рядків коду:
* Вилучено хеш-таблицю `rt_hash_table` та відповідні спинлоки.
* Вилучено збирач сміття `rt_garbage_collect()` та таймер `rt_secret_rebuild_timer`.
* Поле `skb->dst` перестало зберігати динамічно згенеровані записи кешу для транзитного трафіку.

Відмова від кешу маршрутів не призвела до падіння продуктивності системи. Навпаки, вхідний потік став значно швидшим і передбачуваним завдяки двом факторам:

1. **Зрілість алгоритму LC-Trie:** Завдяки оптимізаціям стиснення рівнів і шляхів, проходження префіксного дерева LC-Trie для IPv4 вимагає всього 2–4 звернень до пам'яті. Це значення є детермінованим і не залежить від того, чи спойфиться адреса джерела. Всі структури LC-Trie компактно вміщуються у швидкому L2/L3-кеші сучасних процесорів. Обчислювальна складність пошуку стала оцінюватися як передбачувана `O(log_{2^k} N)`, унеможливлюючи атак типу «найгірший випадок».
2. **Збереження локального кешування на рівні сокетів (Socket Route Caching):** Розробники розділили транзитний трафік і трафік локальних застосунків. Для транзитних пакетів кешування не потрібне і небезпечне. Проте для локальних TCP/UDP з'єднань ядро зберегло механізм локального кешування маршруту безпосередньо всередині структури сокета (`struct sock->sk_dst_cache`).

Завдяки Socket Route Caching та механізму Early Demux, коли локальний вебсервер або СУБД встановлює TCP-з'єднання, вказівник на об'єкт маршрутизації `dst_entry` кешується прямо в структурі сокета. Подальші мільйони пакетів у межах цього відкритого сокета не звертаються ані до кешу маршрутів, ані до LC-Trie — вони беруть готовий маршрут безпосередньо з сокета.

Видалення глобального кешу маршрутів зменшило накладні витрати оперативної пам'яті ядра на кілька мегабайтів і зробило Linux-маршрутизатори абсолютно імунними до атак класу Route Cache Thrashing.

## 5. Механізм Early Demux у сучасних ядрах Linux

Для того щоб компенсувати видалення глобального кешу для вхідного локального трафіку, Ерік Дюмазе (Eric Dumazet) розробив оптимізацію **TCP/UDP Early Demux** (виклики `tcp_v4_early_demux` та `udp_v4_early_demux`).

Суть механізму Early Demux:
1. Коли новий пакет з'являється у `netif_receive_skb()`, ядро на етапі L2/L3 перевіряє, чи активний параметр sysctl `net.ipv4.tcp_early_demux = 1`.
2. Ядро виконує швидкий хеш-пошук по таблиці відкритих локальних сокетів за 4-кортежем `(saddr, daddr, sport, dport)` ще ДО виклику підсистеми маршрутизації.
3. Якщо сокет знайдено, ядро копіює збережений у сокеті вказівник `sk->sk_dst_cache` у заголовок пакета `skb->_skb_refdst` і збільшує лічильник посилань через `dst_hold()`.
4. Вхідний пакет негайно спрямовується до локальної черги прийому сокета, повністю оминаючи виклики RPDB (`ip rule`) та пошук у префіксному дереві LC-Trie!

Якщо ж пакет виявляється транзитним (і сокет не знайдено), ядро здійснює чистий і безпечний пошук у FIB через LC-Trie, звільняючи ресурси пам'яті безпосередньо після відправки пакета у вихідний драйвер через `dst_release()`.

## 6. Архітектурні висновки для розробників системного ПЗ

Історія видалення IPv4 Route Cache є фундаментальним кейсом у системному дизайні:

* **Stateful-кеш — це вектор атаки у відкритих мережах:** Будь-яка структура даних, яка автоматично створює динамічний стан (state) на основі неперевіреного зовнішнього вводу (вхідного мережевого пакета), вразлива до атак на виснаження ресурсів.
* **Швидкий безадресний алгоритм кращий за кеш:** Використання оптимізованих безадресних (stateless) алгоритмів і структур даних (таких як LC-Trie або eBPF LPM-Trie) забезпечує стабільний час виконання `O(1)` або `O(log N)` без ризику колізій та затримок на збирання сміття.
* **Ізоляція системних шарів:** Кешування слід виносити на рівні, де контекст уже перевірено і авторизовано (наприклад, у сокет з'єднання `struct sock`), замість того щоб застосовувати глобальне кешування для сирого вхідного трафіку.
