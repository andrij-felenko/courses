# Прийняття рішення про маршрутизацію: FIB, локальні й глобальні маршрути

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Підсистема маршрутизації (routing subsystem) є однією з найбільш складних та критичних частин мережевого стека Linux. Від того, наскільки ефективно ядро приймає рішення про те, куди направити кожен вхідний або згенерований локально пакет, залежить загальна пропускна здатність та затримки в мережі. У цій статті ми детально розглянемо, як саме Linux приймає рішення про маршрутизацію, починаючи від політик маршрутизації (Policy Based Routing) і закінчуючи пошуком найдовшого префіксу у структурі FIB (Forwarding Information Base) за допомогою алгоритму LC-trie, а також обговоримо, чому розробники ядра відмовилися від кешу маршрутизації (routing cache).

## Огляд процесу маршрутизації в Linux

Коли пакет потрапляє в мережевий стек (або генерується локальним застосунком), ядро має знайти відповідь на одне просте запитання: **на який інтерфейс і якому наступному вузлу (next-hop) слід відправити цей пакет?**

Процес прийняття рішення (routing decision) можна концептуально розділити на кілька основних етапів:
1. **Ідентифікація параметрів пакета:** Ядро витягує з пакета ключову інформацію: IP-адресу джерела (Source IP), IP-адресу призначення (Destination IP), тип сервісу (ToS), вхідний інтерфейс (для транзитних пакетів) та можливі мітки брандмауера (fwmark).
2. **Policy Based Routing (PBR):** Використовуючи бази правил (`ip rule`), ядро визначає, в якій саме таблиці маршрутизації слід шукати маршрут.
3. **Пошук маршруту у FIB:** В обраній таблиці маршрутизації відбувається пошук найдовшого збігу префіксу (Longest Prefix Match, LPM).
4. **Визначення Next-Hop та ARP/NDP:** Після того, як знайдено маршрут, ядро дізнається вихідний інтерфейс і IP-адресу шлюзу, яку потім потрібно перетворити в MAC-адресу за допомогою протоколів розв'язання адрес (ARP для IPv4, Neighbor Discovery для IPv6).

До версії ядра 3.6 існував ще один важливий компонент — **Routing Cache** (кеш маршрутизації), який запам'ятовував прийняті рішення для конкретних пар (джерело, призначення). Проте, через проблеми безпеки та масштабованості, його було повністю вилучено.

## Policy Based Routing (PBR) та ip rule

Традиційна маршрутизація спирається виключно на **IP-адресу призначення**. Однак у складних мережах, де система має кілька інтернет-каналів (multi-homing) або коли потрібно розділяти трафік різних клієнтів (наприклад, у VPN-серверах), цього недостатньо. Тут на допомогу приходить Policy Based Routing, або PBR.

У Linux PBR реалізується за допомогою підсистеми правил маршрутизації, якою можна керувати через команду `ip rule`.

### Як працює ip rule

Коли ядро повинно знайти маршрут, воно не звертається одразу до головної таблиці. Замість цього воно по черзі, відповідно до пріоритетів, переглядає список правил бази маршрутизації (Routing Policy Database, RPDB).

Переглянути поточні правила можна командою:
```bash
$ ip rule show
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
```

За замовчуванням у Linux існують три правила з різними пріоритетами (чим менша цифра, тим вищий пріоритет):
1. **Пріоритет 0:** Пакет перевіряється в таблиці `local`. Ця таблиця містить маршрути до локальних IP-адрес самої машини та broadcast-адрес. Вона гарантує, що трафік до самої себе обробляється миттєво і не виходить на зовнішні інтерфейси.
2. **Пріоритет 32766:** Пакет перевіряється в таблиці `main`. Це основна таблиця маршрутизації, з якою працює більшість користувачів і де зберігаються всі звичайні маршрути.
3. **Пріоритет 32767:** Пакет перевіряється в таблиці `default`. Використовується рідко, зазвичай як резервна (fallback) таблиця.

Адміністратор може додавати власні правила. Наприклад, якщо ми хочемо, щоб увесь трафік від певного локального підмережі (10.0.1.0/24) йшов через іншого провайдера (таблицю 100):

```bash
# Додаємо правило: якщо джерело 10.0.1.0/24, шукати в таблиці 100
ip rule add from 10.0.1.0/24 table 100 priority 1000

# Додаємо маршрут за замовчуванням у таблицю 100
ip route add default via 192.168.2.1 table 100
```

Селектори (критерії), за якими `ip rule` може вибирати таблицю:
- `from` — IP-адреса або підмережа джерела.
- `to` — IP-адреса призначення.
- `iif` / `oif` — вхідний або вихідний інтерфейс.
- `fwmark` — мітка брандмауера (корисно для направлення трафіку за портами, використовуючи iptables/nftables для встановлення мітки).
- `tos` — Type of Service.

Важливо розуміти, що ядро переглядає правила послідовно. Якщо правило відповідає критеріям, ядро переходить до пошуку в зазначеній таблиці. Якщо маршрут у цій таблиці знайдено — пошук припиняється. Якщо ж у цій таблиці немає підходящого маршруту (навіть маршруту за замовчуванням `default`), ядро повертається до RPDB і перевіряє наступне за пріоритетом правило.

## Таблиці маршрутизації та типи маршрутів

Кожна таблиця маршрутизації, визначена в RPDB, містить записи, які вказують, куди відправляти пакети для різних префіксів призначення.

### Локальні та глобальні маршрути

Маршрути можна умовно поділити на локальні та глобальні (транзитні).

**Локальні маршрути** існують переважно в таблиці `local` (table 255). Коли ви призначаєте IP-адресу інтерфейсу, ядро автоматично додає запис типу `local` у цю таблицю. 
- Маршрути типу `local` кажуть ядру: «ця адреса належить цьому комп'ютеру, передай пакет локальному процесу (наприклад, TCP/UDP сокету)».
- Маршрути типу `broadcast` використовуються для обробки широкомовних пакетів.

Приклад виведення локальної таблиці:
```bash
$ ip route show table local
local 127.0.0.0/8 dev lo proto kernel scope host src 127.0.0.1
local 127.0.0.1 dev lo proto kernel scope host src 127.0.0.1
broadcast 192.168.1.0 dev eth0 proto kernel scope link src 192.168.1.100
local 192.168.1.100 dev eth0 proto kernel scope host src 192.168.1.100
```
Завдяки правилу `priority 0`, ці маршрути перевіряються в першу чергу. Це оптимізація: не потрібно шукати складні шляхи, якщо пакет призначений самому собі.

**Глобальні маршрути** (unicast, multicast, тощо) описують шляхи до зовнішніх мереж. Вони переважно знаходяться в таблиці `main` (table 254).
Типовий вміст таблиці `main`:
```bash
$ ip route show table main
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100
```
Тут ми бачимо маршрут у безпосередньо підключену мережу (link scope) та маршрут за замовчуванням (шлюз).

## Forwarding Information Base (FIB)

Термін **FIB** (Forwarding Information Base) прийшов зі світу апаратних маршрутизаторів. На відміну від RIB (Routing Information Base), яка є базою даних всіх можливих маршрутів (включно з неактивними), зібраних різними протоколами динамічної маршрутизації (BGP, OSPF), FIB оптимізована саме для надшвидкого пошуку та пересилання пакетів. У ядрі Linux таблиці маршрутизації є по суті реалізацією FIB.

Головне завдання FIB — здійснити **Longest Prefix Match (LPM)**. 
Суть LPM: якщо пакет призначений для IP-адреси, і ця адреса підпадає під кілька різних маршрутів (наприклад, `10.0.0.0/8` і `10.1.2.0/24`), маршрутизатор зобов'язаний обрати той маршрут, маска якого довша, тобто найбільш специфічний (`10.1.2.0/24`).

### Еволюція структур даних FIB: від хеш-таблиць до LC-Trie

У ранніх версіях ядра Linux для організації FIB використовувались хеш-таблиці. Для кожної можливої довжини маски (від /32 до /0) існувала окрема хеш-таблиця. При пошуку ядро починало з /32, обчислювало хеш і шукало маршрут. Якщо не знайдено — переходило до /31, і так далі, аж до /0 (default route). 

Такий підхід непогано працював для малих таблиць, але зі зростанням таблиць маршрутизації глобального інтернету (BGP Full View), де існують сотні тисяч маршрутів з різними масками, такий лінійний перебір десятків хеш-таблиць ставав надто дорогим для процесора.

Тому починаючи з ядра 2.6.13, розробник Robert Olsson інтегрував у мережевий стек нову структуру — **LC-Trie** (Level-Compressed Trie).

### Як працює LC-Trie

Trie (префіксне дерево) — це структура даних, де кожен вузол представляє певний префікс, а шлях від кореня до листка визначає повну IP-адресу або підмережу. Звичайне бінарне дерево для 32-бітних IPv4 адрес мало б глибину до 32 рівнів, що означає до 32 звернень до пам'яті для кожного пошуку.

**Level Compression (LC)** — це алгоритмічна оптимізація. Суть її полягає у тому, що якщо в певній частині дерева є щільне заповнення (наприклад, розгалуження для всіх 256 варіантів наступного байту повністю заповнені маршрутами), то ці рівні "схлопуються" (стискаються) в один великий вузол з масивом. 
Замість того, щоб спускатись на 8 рівнів вниз, роблячи бінарні порівняння, ядро бере 8 біт адреси як індекс і за одну операцію O(1) переходить до наступного піддерева.

Переваги LC-Trie в Linux:
1. **Швидкість:** Пошук (LPM) для будь-якої адреси в таблиці розміром 1 мільйон префіксів займає лічені мікросекунди і вимагає мінімальної кількості промахів кешу процесора (CPU cache misses).
2. **Економія пам'яті:** Спеціальні оптимізації стиснення дозволяють тримати навіть великі таблиці в L2/L3 кешах сучасних процесорів, що кардинально прискорює пошук маршрутів на швидкостях 10Gbps, 40Gbps і вище.

Ось спрощена візуалізація процесу (див. згенерований SVG файл), де після вибору політики `ip rule`, пакет направляється до структури LC-trie, яка здійснює миттєвий пошук next-hop за допомогою побітових операцій та індексації масивів.

## Routing Cache: Чому від нього відмовилися

Ще однією важливою темою в розумінні маршрутизації Linux є історія кешу маршрутизації.
До версії ядра 3.6 (2012 рік), мережевий стек використовував **Routing Cache**. Ідея виглядала геніально:
- LC-Trie пошук дуже швидкий, але він все ж вимагає кількох звернень до пам'яті.
- Чому б не запам'ятовувати результат маршрутизації для конкретного потоку?
- Якщо прийшов пакет від IP `A` до IP `B`, ядро здійснювало пошук у FIB, а потім зберігало результат (вихідний інтерфейс і next-hop MAC) у гігантській хеш-таблиці (Routing Cache) ключем `(Source IP, Destination IP, ToS)`.
- Наступні пакети цього ж з'єднання минали FIB і одразу брали готовий маршрут з кешу.

### Проблема DDoS-атак

На практиці кеш маршрутизації став Ахіллесовою п'ятою Linux-маршрутизаторів. 
Зловмисники могли запускати атаки типу Random Source IP DDoS. Вони надсилали мільйони пакетів із підробленими, абсолютно випадковими IP-адресами джерела, звертаючись до випадкових IP-адрес призначення.

Для кожного такого пакета ядро змушене було:
1. Не знайти запис у кеші (бо IP нові).
2. Виконати пошук у FIB.
3. **Виділити пам'ять і створити новий запис у кеші**.

За лічені секунди хеш-таблиця кешу маршрутизації переповнювалася. Ядру доводилося запускати "збирача сміття" (Garbage Collector), щоб видаляти старі записи і звільняти пам'ять. Цей процес повністю навантажував процесор, призводячи до **spinlock contention**, і маршрутизатор просто "зависав", перестаючи обробляти корисний трафік. Це називалося "route cache thrashing".

### Видалення кешу (Routing Cache Removal)

Девід Міллер (David Miller), головний супровідник мережевої підсистеми ядра Linux, та інші розробники проаналізували ситуацію. З'ясувалося, що завдяки алгоритму LC-Trie, чистий пошук у FIB відбувається настільки швидко, що накладні витрати на підтримання та очищення кешу маршрутизації у сучасних мережах переважають користь від його використання.

У 2012 році в патчсеті "ipv4: routing cache removal" кеш було повністю видалено з ядра (для IPv4).
З того часу кожен вхідний або вихідний пакет (за деякими винятками оптимізацій на рівні сокетів TCP) завжди проходить через дерево LC-Trie (FIB) для визначення маршруту. Це зробило продуктивність маршрутизації в Linux абсолютно передбачуваною (O(1) або O(log N) в гіршому випадку) і стійкою до DDoS-атак зі спойфінгом адрес. Сучасні ядра Linux здатні маршрутизувати мільйони пакетів на секунду на ядро процесора без використання маршрутного кешу, покладаючись виключно на ефективність LC-trie.

## Наслідки для локального (Host) трафіку: Socket Route Caching

Якщо глобальний кеш маршрутів видалили, як ядро оптимізує локальний трафік, що генерується самим сервером?

Для транзитного трафіку маршрут шукається для кожного пакета. Але для трафіку, який генерується локальними застосунками (наприклад, вебсервером Nginx по TCP), ядро використовує **Socket Route Caching** (Early Demux).
- Коли сокет (TCP з'єднання) встановлюється, ядро виконує пошук у FIB і зберігає вказівник на маршрут (структура `dst_entry`) безпосередньо в структурі сокета (`struct sock`).
- Коли вебсервер відправляє наступний пакет через цей сокет, ядро бере вже готовий маршрут із пам'яті сокета, взагалі обминаючи пошук у FIB! 
Це дає величезний приріст продуктивності для локальних серверних застосунків, не створюючи при цьому глобальної вразливості до DDoS.

## Підсумок: Повний шлях пакета під час маршрутизації

Підсумуємо, як приймається рішення про маршрутизацію для вхідного транзитного пакета в сучасному ядрі Linux:
1. Пакет приймається мережевим драйвером і передається в IP-стек (наприклад, функція `ip_rcv`).
2. Після проходження базових перевірок (checksum) і `PREROUTING` ланцюгів Netfilter (iptables/nftables), викликається підсистема `ip_route_input_noref()`.
3. Ядро перевіряє таблицю політик `ip rule`.
4. Знайшовши перше правило, що підходить (зазвичай `rule 32766 main`), ядро заходить у відповідну таблицю FIB.
5. За допомогою алгоритму LC-trie виконується швидкий пошук префіксу з найдовшою маскою (LPM).
6. Знаходиться `fib_info`, який містить інформацію про next-hop.
7. Пакет передається на вихідний інтерфейс, після чого працює Neighbor Discovery (ARP), щоб переслати його на фізичний MAC-адресу шлюзу.

Розуміння цих механізмів, зокрема переваг LC-Trie та причин відмови від глобального кешу, є критичним для системних адміністраторів, які проектують високопродуктивні маршрутизатори (наприклад, з використанням FRRouting або BIRD) на базі операційної системи Linux.
