# eBPF у підсистемі Traffic Control (tc)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Технологія eBPF (Extended Berkeley Packet Filter) здійснила революцію в обробці мережевих пакетів у ядрі Linux. Однією з найпотужніших точок підключення (hook points) для програм eBPF є підсистема Traffic Control (tc). На відміну від XDP (eXpress Data Path), яка працює на найнижчому рівні драйвера пристрою ще до виділення структури `sk_buff`, eBPF у підсистемі tc має доступ до повністю сформованої структури `sk_buff`. Це дає змогу програмам tc eBPF виконувати складну модифікацію пакетів на рівнях L2-L4, маршрутизацію, класифікацію та керування трафіком.

У цій статті ми детально розглянемо архітектуру eBPF у Traffic Control, дисципліну черги (qdisc) `clsact`, типи програм `BPF_PROG_TYPE_SCHED_CLS` та `BPF_PROG_TYPE_SCHED_ACT`, а також ключові допоміжні функції, такі як `bpf_skb_store_bytes()` та `bpf_redirect()`.

## Архітектура Traffic Control та eBPF

Підсистема Traffic Control (tc) в Linux призначена для керування передачею та прийомом пакетів. Її основні компоненти:
- **Qdisc (Queueing Discipline):** Дисципліна черги, яка визначає порядок відправки або обробки пакетів.
- **Class (Клас):** Внутрішні структури класових qdisc для організації ієрархій.
- **Filter (Фільтр):** Класифікатор пакетів, який визначає, до якого класу або дії слід направити пакет.
- **Action (Дія):** Операція, яка виконується над пакетом (наприклад, скидання (drop), перенаправлення, модифікація).

Традиційно tc використовувалася для обмеження швидкості (rate limiting) та пріоритезації. Проте з додаванням підтримки eBPF, tc перетворилася на потужний інструмент програмованої обробки пакетів.

eBPF програми можуть бути прикріплені до tc як класифікатори (фільтри) або дії. Найчастіше використовується комбінація класифікатора і дії в одній eBPF програмі (direct action).

## Дисципліна черги `clsact`

Для полегшення використання eBPF у підсистемі tc було введено спеціальну дисципліну черги під назвою `clsact`. 
На відміну від традиційного `ingress` qdisc, `clsact` надає точки підключення як для вхідного (ingress), так і для вихідного (egress) трафіку без необхідності створення складних ієрархій.

Особливості `clsact`:
1. **Пряме прикріплення:** `clsact` прикріплюється до мережевого інтерфейсу і не вимагає дочірніх класів.
2. **Ingress та Egress:** Дозволяє прикріплювати eBPF програми до обох напрямків трафіку. Для `ingress` програми виконуються після XDP та після обробки драйвером, але до того, як пакет потрапить у мережевий стек (netfilter, IP routing). Для `egress` програми виконуються після проходження мережевого стеку, безпосередньо перед передачею пакета в драйвер пристрою.
3. **Lockless:** Робота на `clsact` оптимізована і часто не потребує глобальних блокувань, що забезпечує високу продуктивність.

Для створення `clsact` qdisc на інтерфейсі `eth0` використовується команда:
```bash
tc qdisc add dev eth0 clsact
```

Після цього можна прикріплювати eBPF програми до `ingress` або `egress` хуків.

## Типи програм eBPF для tc

Існує два основні типи eBPF програм для підсистеми Traffic Control:

### `BPF_PROG_TYPE_SCHED_CLS`
Це програми-класифікатори. Їхнє основне завдання — проаналізувати пакет (через структуру `__sk_buff`) і повернути код результату (classid або action code). У сучасних ядрах (з підтримкою прапорця `direct-action` або `da`), програма `SCHED_CLS` може не лише класифікувати пакет, а й самостійно виконувати дії (наприклад, скидати, перенаправляти або модифікувати) і повертати код дії tc (наприклад, `TC_ACT_OK`, `TC_ACT_SHOT`).

Коди повернення (tc actions):
- `TC_ACT_UNSPEC` (0): Продовжити обробку (передати наступному фільтру).
- `TC_ACT_OK` (0): Пропустити пакет.
- `TC_ACT_SHOT` (2): Відкинути пакет.
- `TC_ACT_STOLEN` (4): Пакет перехоплено (звільнення пам'яті пакета відповідальність eBPF/допоміжних функцій).
- `TC_ACT_REDIRECT` (7): Пакет перенаправлено на інший інтерфейс.

### `BPF_PROG_TYPE_SCHED_ACT`
Це програми-дії. Вони виконуються після того, як інший класифікатор вибрав цю дію. На практиці `SCHED_ACT` використовується рідше, оскільки режим `direct-action` у `SCHED_CLS` (де програма сама класифікує і виконує дію) є більш ефективним і поширеним підходом, що уникає додаткових накладних витрат на розділення логіки класифікації та дії.

## Доступ до пакета: структура `sk_buff`

У tc eBPF програми отримують як контекст вказівник на структуру `struct __sk_buff`. Це eBPF-еквівалент структури ядра `sk_buff` (socket buffer), яка представляє мережевий пакет.
Вона містить метадані про пакет і вказівники на самі дані:
- `data`: Вказівник на початок корисного навантаження (L2 заголовок).
- `data_end`: Вказівник на кінець даних пакета.
- `len`: Загальна довжина пакета.
- Поля метаданих: `mark`, `priority`, `vlan_tci`, `ifindex` тощо.

На відміну від XDP, де програма працює із сирими даними пам'яті, структура `sk_buff` вже розпарсена ядром (хоча б частково, на рівні L2), але eBPF програма має право читати і модифікувати як метадані, так і самі байти пакета.

## Модифікація пакетів L2-L4: `bpf_skb_store_bytes()`

Для зміни вмісту пакета (наприклад, зміни IP-адрес, MAC-адрес або портів TCP/UDP) tc eBPF програми використовують допоміжну функцію (helper) `bpf_skb_store_bytes()`.

```c
long bpf_skb_store_bytes(struct sk_buff *skb, u32 offset,
                         const void *from, u32 len, u64 flags);
```

- `skb`: Вказівник на пакет.
- `offset`: Зміщення у байтах від початку пакета (`data`), куди потрібно записати дані.
- `from`: Вказівник на буфер з новими даними.
- `len`: Довжина нових даних.
- `flags`: Прапорці (наприклад, `BPF_F_INVALIDATE_HASH`, щоб змусити ядро перерахувати хеш пакета).

Ця функція є життєво важливою, оскільки вона забезпечує безпечний запис у `sk_buff`. Пакет може бути фрагментованим (non-linear data) або клонованим, і ядро за допомогою цієї функції автоматично виконає розширення пакета (skb_pull/skb_push) або розклонування (unshare) при необхідності, гарантуючи, що модифікація пам'яті не призведе до kernel panic.

### Оновлення контрольних сум
При зміні заголовків IP або TCP/UDP, контрольні суми пакета стають недійсними. Щоб уникнути відкидання пакета мережевим стеком отримувача, tc eBPF програми повинні також оновити контрольні суми за допомогою:
- `bpf_l3_csum_replace()` (для IPv4/IPv6).
- `bpf_l4_csum_replace()` (для TCP/UDP/ICMP).

## Маршрутизація та перенаправлення: `bpf_redirect()`

Одним із найпотужніших механізмів tc eBPF є можливість перенаправлення пакетів в обхід стандартного мережевого стеку ядра. Для цього використовується функція `bpf_redirect()`.

```c
long bpf_redirect(u32 ifindex, u64 flags);
```

- `ifindex`: Індекс мережевого інтерфейсу, на який слід перенаправити пакет.
- `flags`: Напрямок перенаправлення: `0` для `egress` (на вихід інтерфейсу) або `BPF_F_INGRESS` (на вхід інтерфейсу, ніби пакет щойно прибув на нього).

Функція `bpf_redirect()` повертає `TC_ACT_REDIRECT`. Коли eBPF програма повертає цей код, ядро перехоплює пакет і направляє його безпосередньо на вказаний інтерфейс. Це дозволяє створювати високопродуктивні віртуальні маршрутизатори, балансувальники навантаження (L4 load balancers, як-от Cilium) та системи Service Mesh, обходячи складності та затримки маршрутизації IP-рівня ядра.

Існує також більш ефективна версія для перенаправлення до сусідів — `bpf_redirect_neigh()`, яка автоматично вирішує MAC-адреси через таблицю ARP/ND.

## Приклад eBPF програми tc

Нижче наведено концептуальний приклад tc `clsact` eBPF програми, яка перенаправляє пакети з портом призначення 8080 на інший інтерфейс:

```c
#include <linux/bpf.h>
#include <linux/pkt_cls.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include <bpf/bpf_helpers.h>

SEC("classifier")
int tc_redirect_prog(struct __sk_buff *skb) {
    void *data = (void *)(long)skb->data;
    void *data_end = (void *)(long)skb->data_end;

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return TC_ACT_OK;

    if (eth->h_proto != __constant_htons(ETH_P_IP))
        return TC_ACT_OK;

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return TC_ACT_OK;

    if (ip->protocol == IPPROTO_TCP) {
        struct tcphdr *tcp = (void *)(ip + 1);
        if ((void *)(tcp + 1) > data_end)
            return TC_ACT_OK;

        // Перевіряємо порт призначення 8080
        if (tcp->dest == __constant_htons(8080)) {
            // Перенаправляємо пакет на інтерфейс з індексом 2 (наприклад, eth1)
            return bpf_redirect(2, 0); 
        }
    }

    return TC_ACT_OK;
}

char _license[] SEC("license") = "GPL";
```

Ця програма компілюється в об'єктний файл ELF і може бути завантажена за допомогою `tc`:
```bash
tc qdisc add dev eth0 clsact
tc filter add dev eth0 ingress bpf da obj my_prog.o sec classifier
```
Прапорець `da` вказує на `direct-action`, що дозволяє програмі безпосередньо повертати `TC_ACT_*` коди.

## Переваги eBPF у Traffic Control

1. **Доступ до метаданих:** tc eBPF має доступ до інформації, яка генерується ядром (наприклад, cgroup ID, socket lookup), що дозволяє приймати рішення на основі контексту процесу або сокета.
2. **Безпека:** Як і всі eBPF програми, код перевіряється (verifier) перед завантаженням у ядро, що гарантує відсутність нескінченних циклів або некоректного доступу до пам'яті.
3. **Гнучкість:** Можливість поєднання маршрутизації, балансування, фільтрації та зміни пакетів в одному високопродуктивному проході.

Використання eBPF у `tc clsact` стало стандартом де-факто для сучасної мережевої інфраструктури хмарних середовищ і контейнерних платформ, де потрібна гнучка політика безпеки та висока продуктивність, що перевершує можливості традиційного iptables/netfilter.
