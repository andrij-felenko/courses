# Netfilter, iptables та nftables

Netfilter — це підсистема ядра Linux, яка забезпечує перехоплення та модифікацію мережевих пакетів. Вона формує каркас для фаєрволів, NAT (Network Address Translation) та логування мережевого трафіку.

## Хуки Netfilter (Netfilter Hooks)

Серцевиною Netfilter є п'ять хуків (hooks), розміщених у ключових точках мережевого стеку ядра. Коли пакет проходить через ядро, він перетинає ці точки, дозволяючи зареєстрованим модулям інспектувати, змінювати або відкидати його.

1. **`PREROUTING`** (До маршрутизації): Точка входу. Пакет щойно прийнято мережевою картою (NIC). Тут зазвичай виконується DNAT (Destination NAT), тобто зміна IP-адреси призначення до того, як ядро вирішить, куди відправити пакет.
2. **`INPUT`** (Вхід): Пакет призначений для локальної системи. Якщо локальний процес (наприклад, веб-сервер) очікує дані, пакет проходить цей хук перед тим, як потрапити в сокет.
3. **`FORWARD`** (Транзит): Пакет призначений не нам, а іншій машині. Ядро працює як маршрутизатор.
4. **`OUTPUT`** (Вихід): Пакет згенеровано локальним процесом і він щойно покинув сокет.
5. **`POSTROUTING`** (Після маршрутизації): Точка виходу. Пакет готовий до відправки на NIC. Тут зазвичай виконується SNAT (Source NAT) або Masquerading.

## Conntrack: відстеження з'єднань

Самих лише хуків недостатньо для побудови розумного фаєрволу. Більшість правил базуються на стані з'єднання: фаєрвол має розуміти, що вхідний пакет є відповіддю на наш вихідний запит. Це завдання виконує **conntrack** (Connection Tracking).

Conntrack — це незалежна від фаєрвола таблиця станів у ядрі, яка відстежує всі логічні з'єднання. Вона аналізує TCP-сесії (SYN, ACK, FIN), UDP-потоки (за IP та портами) і навіть складні протоколи типу FTP (за допомогою модулів-хелперів).

Стани `conntrack`:
- `NEW`: Пакет розпочинає нове з'єднання (наприклад, TCP SYN).
- `ESTABLISHED`: З'єднання вже встановлено, пакети йдуть в обох напрямках.
- `RELATED`: Пакет розпочинає нове з'єднання, але воно логічно пов'язане з уже наявним (наприклад, канал даних FTP або помилка ICMP щодо наявного TCP-з'єднання).
- `INVALID`: Пакет не належить жодному відомому з'єднанню і має некоректний стан.

## iptables проти nftables: еволюція архітектури

Щоб використовувати хуки Netfilter, адміністраторам потрібен інструмент. Історично це був `iptables`.

### iptables
В архітектурі `iptables` логіка протоколів (IPv4, IPv6, ARP, Bridge) була жорстко зашита в ядро. Ядро містило окремі модулі для порівняння IP-адрес, портів, TCP-прапорців тощо.
Коли ви писали правило `iptables`, користувацька утиліта просто передавала ядру структуру даних (бінарний блоб) з правилами. Ядро мало лінійно перебирати правила, що було дуже повільно для великих списків (десятки тисяч правил).

### nftables (віртуальна машина байт-коду)
`nftables` — це сучасна заміна, яка змінила парадигму. Замість жорстко вшитої в ядро логіки протоколів `nftables` реалізує в ядрі **просту віртуальну машину (VM)**.

Користувацька утиліта `nft` отримує зручний для людини синтаксис, компілює його у **байт-код** (подібно до BPF) і відправляє в ядро. Віртуальна машина в ядрі (регістрова VM) просто виконує цей байт-код.

**Переваги nftables:**
1. **Швидкість:** сам ланцюжок ядро й далі проходить правило за правилом, але великі переліки адрес і портів згортаються у словники (sets і maps) з пошуком за хешем — сотні правил стають одним записом у ланцюжку й одним пошуком.
2. **Універсальність:** Одна утиліта `nft` замінює `iptables`, `ip6tables`, `arptables` та `ebtables`.
3. **Атомарність:** Зміни правил застосовуються транзакційно. В `iptables` додавання одного правила означало, що утиліта вичитувала з ядра весь блоб таблиці, змінювала його в себе й віддавала назад цілком, щоб ядро підмінило старий блоб новим; звідси затримки на великих наборах і перегони (race condition) між двома одночасними викликами `iptables`.

## Приклади налаштування фаєрвола

Розглянемо базовий набір правил: дозволити вхідний SSH-трафік і вже встановлені з'єднання, а решту вхідного трафіку відкинути.

**nftables (сучасний підхід)**
```nft
# nftables.conf
table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;

        # Дозволити loopback
        iifname "lo" accept

        # Дозволити встановлені та пов'язані з'єднання (conntrack)
        ct state established,related accept

        # Дозволити SSH
        tcp dport 22 accept
    }
}
```

**iptables (успадкований підхід)**
```bash
# Дозволити loopback
iptables -A INPUT -i lo -j ACCEPT

# Дозволити встановлені та пов'язані з'єднання
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Дозволити SSH
iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Відкинути все інше
iptables -P INPUT DROP
```

Різниця видна вже на цих трьох правилах: `table inet` покриває IPv4 і IPv6 одним набором, тоді як показані команди `iptables` стосуються самого лише IPv4 — для IPv6 їх довелося б продублювати через `ip6tables`. Політику ланцюжка `nft` оголошує там само, де й сам ланцюжок (`policy drop`), а `iptables` ставить її окремою командою `-P`.

Межі цього механізму задають дві сусідні підсистеми. Знизу він упирається у [вибір маршруту](book:unix-linux/routing-decision): між `PREROUTING` і `INPUT`/`FORWARD` стоїть саме рішення про маршрут, тому DNAT у `PREROUTING` міняє не лише адресу призначення, а й подальшу долю пакета. З боку ізоляції весь набір таблиць і сама таблиця conntrack живуть у межах [мережевого простору імен](book:unix-linux/network-namespaces) — кожен контейнер має власний фаєрвол і власні записи про з'єднання. А там, де навіть байт-код nftables задорогий, фільтр переносять ще раніше за `PREROUTING` — у [eBPF на рівні clsact](book:unix-linux/ebpf-traffic-control-clsact), одразу за драйвером мережевої карти.
