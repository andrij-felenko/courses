# Менеджери шляхів у MPTCP (mptcpd та in-kernel path manager)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Технологія Multipath TCP (MPTCP), стандартизована у RFC 8684, є значним еволюційним кроком у розвитку класичного протоколу TCP. Вона дозволяє одному транспортному з'єднанню використовувати кілька мережевих шляхів (наприклад, Wi-Fi та стільниковий зв'язок 5G одночасно) для передачі даних. Це забезпечує підвищену надійність, стійкість до збоїв на окремих каналах та збільшення загальної пропускної здатності.

Однак, щоб ефективно використовувати кілька шляхів, MPTCP потребує механізму керування цими шляхами: виявлення нових IP-адрес, встановлення нових підпотоків (subflows), закриття неактивних та керування пріоритетами. За це відповідає компонент, відомий як **Path Manager** (менеджер шляхів). У сучасній реалізації MPTCP у ядрі Linux (починаючи з версії 5.6) передбачено два типи менеджерів шляхів: вбудований у ядро (**in-kernel path manager**) та менеджер у просторі користувача (**userspace path manager**), найвідомішою реалізацією якого є демон **mptcpd**.

У цій статті ми детально розглянемо архітектуру керування шляхами в MPTCP, відмінності між `pm_type=0` (in-kernel) та `pm_type=1` (userspace), а також практичні аспекти їх налаштування та використання через утиліту `ip mptcp` та Netlink API.

## Роль Path Manager в архітектурі MPTCP

Класичне TCP-з'єднання ідентифікується кортежем із чотирьох параметрів (Source IP, Source Port, Destination IP, Destination Port). MPTCP розширює цю концепцію, вводячи поняття MPTCP-з'єднання (MPTCP connection), яке складається з одного або кількох TCP-підпотоків (subflows). Кожен підпотік — це звичайне TCP-з'єднання зі своїм 4-tuple, але на рівні MPTCP дані розподіляються між ними та збираються на стороні приймача з дотриманням правильного порядку.

Основними завданнями Path Manager є:
1. **Моніторинг локальних мережевих інтерфейсів**: виявлення появи нових IP-адрес або їх зникнення.
2. **Оголошення адрес (Address Advertisement)**: відправка MPTCP-опції `ADD_ADDR` віддаленому вузлу, щоб повідомити йому про наявність альтернативного шляху, або `REMOVE_ADDR`, коли адреса стає недоступною.
3. **Створення підпотоків (Subflow Establishment)**: ініціалізація нових TCP-з'єднань (з опцією `MP_JOIN`) з локальної адреси на віддалену адресу.
4. **Керування пріоритетами**: встановлення прапорця `BACKUP` для підпотоків, які мають використовуватися лише у разі збою основного каналу.

Рішення про те, коли створювати підпотік і яку адресу оголошувати, є політикою (policy), яка може суттєво відрізнятися залежно від сценарію використання (наприклад, смартфон, що економить батарею, або сервер дата-центру, що максимізує пропускну здатність). Саме тому архітектура Linux MPTCP розділяє механізм керування шляхами на два типи, що дозволяє делегувати складну логіку в простір користувача.

## In-Kernel Path Manager (pm_type=0)

Вбудований у ядро менеджер шляхів є менеджером за замовчуванням (управляється через `sysctl net.mptcp.pm_type=0`). Він реалізує базову, але достатню для багатьох сценаріїв логіку керування шляхами.

### Принцип роботи

In-kernel Path Manager покладається на статичні правила, які адміністратор налаштовує через утиліту `ip mptcp`. Коли ядро виявляє нове MPTCP-з'єднання (або появу нової IP-адреси, яка підпадає під налаштовані правила), воно автоматично, без залучення простору користувача, генерує пакети з опціями `ADD_ADDR` або ініціює `MP_JOIN`.

Це забезпечує мінімальні затримки та відсутність накладних витрат на перемикання контексту, що є критично важливим для високопродуктивних мережевих вузлів.

### Налаштування через ip mptcp endpoint

Управління in-kernel менеджером здійснюється за допомогою команди `ip mptcp endpoint`. За допомогою цієї команди адміністратор може додати локальні IP-адреси до бази даних (policy database) ядра, вказавши, як саме вони мають використовуватися.

#### Додавання адрес та прапорці

Основні прапорці (flags), які можна призначити локальній кінцевій точці:
- **`signal`**: вказує ядру, що цю адресу потрібно оголосити віддаленому вузлу за допомогою опції `ADD_ADDR`. Віддалений вузол, отримавши цю адресу, може сам ініціювати підпотік (MP_JOIN) до неї.
- **`subflow`**: вказує ядру, що воно має активно створювати нові підпотоки з цієї локальної адреси до відомих адрес віддаленого вузла.
- **`backup`**: позначає підпотік як резервний (передається відповідний прапорець `BACKUP` у пакетах `MP_JOIN` або `ADD_ADDR`).
- **`fullmesh`**: (додано в новіших версіях ядра) вказує, що з цієї адреси потрібно створити підпотоки до всіх відомих віддалених адрес, утворюючи повнозв'язну топологію.

**Приклад:**
Припустимо, у нас є сервер з двома інтерфейсами: `eth0` (192.168.1.10) та `eth1` (10.0.0.10). Ми хочемо, щоб сервер оголошував адресу `10.0.0.10` усім клієнтам, що підключаються.
```bash
ip mptcp endpoint add 10.0.0.10 dev eth1 signal
```
Якщо ми налаштовуємо клієнта (який ініціює з'єднання), і хочемо, щоб він активно створював другий підпотік з інтерфейсу `wlan0`:
```bash
ip mptcp endpoint add 192.168.2.20 dev wlan0 subflow
```

#### Сигнали ADD_ADDR та REMOVE_ADDR

Коли додається адреса з прапорцем `signal`, ядро автоматично надсилає опцію `ADD_ADDR` у межах існуючого MPTCP-з'єднання. Це повідомлення містить саму IP-адресу, порт (опціонально) та HMAC для автентифікації. 

Якщо мережевий інтерфейс падає або адресу видаляють з конфігурації:
```bash
ip mptcp endpoint delete id 1
```
ядро згенерує та відправить `REMOVE_ADDR` з відповідним ідентифікатором адреси (Address ID), повідомляючи віддаленій стороні, що шлях більше не доступний і всі підпотоки, прив'язані до цієї адреси, мають бути закриті.

### Обмеження (Limits)

Навіть якщо конфігурація `ip mptcp endpoint` дозволяє створення багатьох підпотоків, ядро накладає глобальні обмеження (limits) для захисту від зловживань та вичерпання ресурсів. Вони налаштовуються за допомогою `ip mptcp limits`:

```bash
# Дозволити прийняти до 2 ADD_ADDR від віддаленого вузла
ip mptcp limits set add_addr_accepted 2

# Дозволити створення до 2 додаткових підпотоків (крім початкового)
ip mptcp limits set subflows 2
```

In-kernel Path Manager є чудовим вибором для статичних середовищ, де мережеві інтерфейси відомі заздалегідь, або їх поведінка проста. Однак, він стає недостатнім, коли політика маршрутизації вимагає складнішої логіки (наприклад, "використовувати Wi-Fi лише тоді, коли рівень сигналу вищий за пороговий", або "використовувати 5G лише для певних типів трафіку").

## Userspace Path Manager (pm_type=1) та mptcpd

Для реалізації складної, динамічної логіки, яка спирається на метрики з простору користувача (стан батареї, рівень сигналу, тарифні плани, геолокація), ядро Linux надає Userspace Path Manager.

Щоб його увімкнути, необхідно змінити параметр sysctl:
```bash
sysctl -w net.mptcp.pm_type=1
```

При `pm_type=1`, ядро більше не створює підпотоки автоматично і не відправляє `ADD_ADDR`. Замість цього воно делегує ці рішення додатку у просторі користувача, спілкуючись із ним через MPTCP Generic Netlink API. Найбільш зрілою та офіційно підтримуваною реалізацією такого додатку є демон `mptcpd`.

### Архітектура mptcpd

`mptcpd` — це системний демон, розроблений компанією Intel (та відкритою спільнотою), який слухає події від ядра через Netlink та реагує на них відповідно до налаштованих плагінів.

Архітектура `mptcpd` є модульною. Основний процес демона відповідає за взаємодію з ядром (парсинг Netlink-повідомлень та відправку команд), тоді як логіка прийняття рішень інкапсульована у плагіни (plugins), що завантажуються як динамічні бібліотеки (`.so`).

Основні події, які ядро генерує через Netlink multicast групу `MPTCP_PM_EVENTS`:
1. `MPTCP_EVENT_CREATED`: Створено нове MPTCP-з'єднання.
2. `MPTCP_EVENT_ESTABLISHED`: З'єднання успішно встановлено (завершено 3-way handshake).
3. `MPTCP_EVENT_ANNOUNCED`: Отримано `ADD_ADDR` від віддаленого вузла.
4. `MPTCP_EVENT_REMOVED`: Отримано `REMOVE_ADDR`.
5. `MPTCP_EVENT_SUB_ESTABLISHED`: Успішно встановлено новий підпотік.
6. `MPTCP_EVENT_SUB_CLOSED`: Підпотік закрито.

Демон `mptcpd` отримує ці події і викликає відповідні callback-функції у завантаженому плагіні. Плагін аналізує стан і може дати демону команду (яка транслюється в Netlink команду до ядра):
- Відправити `ADD_ADDR` (`mptcpd_kpm_add_addr`).
- Відправити `REMOVE_ADDR` (`mptcpd_kpm_remove_addr`).
- Створити новий підпотік (`mptcpd_kpm_add_subflow`).
- Змінити пріоритет (встановити `BACKUP` прапорець).

### Взаємодія userspace з ядром (Generic Netlink)

MPTCP Netlink API реалізовано як сімейство Generic Netlink (`GENL_NAME_MPTCP`). 
Команди, які userspace Path Manager може надсилати до ядра, включають (з префіксом `MPTCP_PM_CMD_`):
- `ADD_ADDR`: наказ ядру надіслати `ADD_ADDR` на конкретному з'єднанні (ідентифікується за token).
- `DEL_ADDR`: наказ ядру надіслати `REMOVE_ADDR`.
- `SUBFLOW_CREATE`: наказ ядру ініціювати TCP-з'єднання (MP_JOIN) з визначеної локальної адреси/порту до віддаленої адреси/порту для конкретного MPTCP-з'єднання.
- `SUBFLOW_DESTROY`: наказ ядру закрити підпотік.
- `SET_FLAGS`: зміна прапорців (наприклад, BACKUP) для існуючого підпотоку.

Це забезпечує абсолютний гранулярний контроль. На відміну від `pm_type=0`, де правила діють глобально або на рівні простору імен (network namespace), userspace Path Manager може приймати рішення індивідуально для *кожного* MPTCP-з'єднання.

### Розробка плагінів для mptcpd

Плагіни mptcpd пишуться мовою C (або будь-якою мовою, здатною експортувати C ABI). Плагін повинен реалізувати структуру `mptcpd_plugin_ops`, яка містить вказівники на функції-обробники подій:

```c
struct mptcpd_plugin_ops {
    void (*new_connection)(struct mptcpd_pm *pm, uint32_t token, ...);
    void (*connection_established)(struct mptcpd_pm *pm, uint32_t token, ...);
    void (*new_address)(struct mptcpd_pm *pm, uint32_t token, ...);
    // ... інші callback-функції
};
```

Прикладом простого плагіна є `sspi` (Single Subflow Per Interface), який постачається разом з mptcpd. Коли приходить подія `new_address` (віддалений вузол надіслав `ADD_ADDR`), плагін перевіряє свої локальні інтерфейси і наказує ядру створити новий підпотік (через `mptcpd_kpm_add_subflow`) для кожної пари локальна-віддалена адреса.

Більш складні плагіни можуть підключатися до D-Bus для отримання інформації від NetworkManager про рівень заряду батареї або вартість підключення (metered connection), щоб динамічно закривати стільникові підпотоки при низькому заряді.

## Порівняння pm_type=0 та pm_type=1

| Характеристика | In-Kernel (pm_type=0) | Userspace (pm_type=1, mptcpd) |
| :--- | :--- | :--- |
| **Місце виконання** | Ядро Linux (Network Stack) | Простір користувача (Daemon) |
| **Конфігурація** | `ip mptcp endpoint` та `limits` | Плагіни mptcpd, конфігураційні файли |
| **Гнучкість** | Низька (глобальні статичні правила) | Дуже висока (програмна логіка, зовнішні метрики) |
| **Гранулярність** | Per-namespace | Per-connection |
| **Затримка (Latency)**| Мінімальна (без context switch) | Трохи вища (Netlink IPC) |
| **Сценарії використання**| Сервери, статичні маршрутизатори | Мобільні пристрої, складні політики SD-WAN |

## Висновок

Система керування шляхами (Path Management) у Linux MPTCP демонструє класичний архітектурний підхід операційних систем: розділення механізму та політики. Ядро надає надійний та швидкий механізм інкапсуляції опцій `ADD_ADDR` та створення TCP-підпотоків. Завдяки наявності двох типів менеджерів шляхів, користувачі можуть обирати між простотою та продуктивністю in-kernel менеджера (`pm_type=0`) та безмежною гнучкістю userspace демонів на кшталт `mptcpd` (`pm_type=1`), які дозволяють інтегрувати MPTCP з сучасними динамічними мережевими середовищами.

Оволодіння інструментами `ip mptcp` та розуміння архітектури `mptcpd` є критично важливими для мережевих інженерів та системних адміністраторів, які розгортають рішення на базі Multipath TCP.
