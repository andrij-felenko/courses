# Підсистема відстеження зʼєднань Conntrack (nf_conntrack) та conntrack tables

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Підсистема **conntrack** (nf_conntrack) у ядрі Linux є ключовим компонентом архітектури Netfilter. Її головна мета — відстежувати стан мережевих зʼєднань. Завдяки conntrack фаєрволи можуть бути stateful (збереження стану), а механізми Network Address Translation (NAT) отримують змогу працювати коректно. Без nf_conntrack фаєрвол міг би приймати рішення лише на основі окремих пакетів (stateless), що робить неможливим створення безпечних і гнучких правил.

У цій статті ми детально розглянемо архітектуру nf_conntrack, структури даних у ядрі (такі як `struct nf_conn`), механізми хешування, роботу з таблицею conntrack (conntrack tables), а також практичні аспекти: налаштування, ліміти, переповнення таблиці (conntrack table overflow) і використання в iptables/nftables.

## Роль і місце nf_conntrack в архітектурі ядра

У стеку TCP/IP кожен пакет обробляється ізольовано на рівні IP. Але для додатків (HTTP, SSH) комунікація має вигляд сесії, тобто потоку даних. Підсистема nf_conntrack відновлює це бачення сесії на мережевому рівні, аналізуючи заголовки пакетів (L3 і L4).

Conntrack "бачить" пакети на дуже ранніх етапах (у хуках `PREROUTING` та `OUTPUT` перед маршрутизацією), створює або оновлює відповідний запис і надає цю інформацію іншим підсистемам.

### Як працює Connection Tracking

1. **Перехоплення пакету.** Пакет потрапляє в мережевий стек і перехоплюється через Netfilter hooks.
2. **Побудова кортежу (Tuple).** З пакета витягуються ключові дані для ідентифікації з'єднання:
   - Source IP, Destination IP (рівень L3)
   - Source Port, Destination Port, або ICMP ID/Type (рівень L4)
   - Протокол (TCP, UDP, ICMP, тощо)
3. **Хешування.** Кортеж хешується для швидкого пошуку в таблиці conntrack.
4. **Пошук.** Система перевіряє, чи існує вже такий запис.
5. **Оновлення або Створення.** Якщо запис існує, його стан оновлюється (наприклад, з `NEW` на `ESTABLISHED`). Якщо ні — створюється новий запис (спочатку він `NEW`).
6. **Прив'язка до пакета.** Пакет отримує вказівник на знайдений/створений `nf_conn` запис через поле `skb->nfct` (структура `sk_buff`).

Завдяки вказівнику в `sk_buff`, будь-які подальші правила iptables, nftables чи механізми NAT можуть дізнатися, до якого з'єднання належить пакет і який стан цього з'єднання.

## Тупли (Tuples) і мапінг напрямків

В основі nf_conntrack лежить поняття **Tuple** (кортеж). Кортеж однозначно ідентифікує потік пакетів у одному напрямку. 
Для кожного з'єднання conntrack зберігає два кортежі:
- **ORIGINAL:** напрямок, у якому був ініційований зв'язок (пакет, що створив запис).
- **REPLY:** очікуваний напрямок для пакетів у відповідь (перевернуті IP-адреси та порти).

Наприклад, якщо клієнт (192.168.1.100, порт 50000) підключається до сервера (8.8.8.8, порт 80, TCP), кортежі будуть такими:
- **ORIGINAL:** `SRC=192.168.1.100 DST=8.8.8.8 SPORT=50000 DPORT=80 PROTO=TCP`
- **REPLY:** `SRC=8.8.8.8 DST=192.168.1.100 SPORT=80 DPORT=50000 PROTO=TCP`

Завдяки `REPLY` кортежу, коли сервер відправляє відповідь, nf_conntrack одразу розуміє, що цей пакет є частиною вже існуючого (відомого) з'єднання.

### NAT і Tuples

Якщо з'єднання піддається NAT (наприклад, SNAT на маршрутизаторі), `REPLY` кортеж відповідно модифікується, щоб відображати нові адреси/порти, за якими клієнт очікуватиме відповідь.
Наприклад, якщо SNAT змінює 192.168.1.100 на зовнішній IP маршрутизатора 203.0.113.1, кортеж `REPLY` стає:
- `SRC=8.8.8.8 DST=203.0.113.1 SPORT=80 DPORT=50000 PROTO=TCP`

Таким чином conntrack автоматично виконує "де-NAT" для пакетів-відповідей, порівнюючи їх з `REPLY` кортежем і модифікуючи `sk_buff` перед відправкою клієнту.

## Структури даних ядра: `struct nf_conn` та таблиці

### struct nf_conn

Кожне відстежуване з'єднання представлено у ядрі структурою `struct nf_conn` (оголошена в `include/net/netfilter/nf_conntrack.h`).
Ця структура є досить складною, оскільки повинна обслуговувати різні протоколи і розширення. Вона містить:
- Масив `tuplehash[IP_CT_DIR_MAX]` — два хеш-вузли (для ORIGINAL та REPLY), через які запис додається до глобальної хеш-таблиці. Кожен вузол містить сам кортеж.
- Статус з'єднання (бітова маска, що вказує на стан: `IPS_SEEN_REPLY_BIT`, `IPS_ASSURED_BIT`, `IPS_SRC_NAT_BIT`, тощо).
- Таймер або час життя (timeout), який визначає, коли запис слід видалити, якщо нові пакети не надходять.
- Розширення (extensions) — для зберігання додаткових даних, таких як NAT-інформація, helper'и (наприклад, FTP або SIP), мітки (conntrack marks).

### Хеш-таблиця і conntrack tables

Усі записи `nf_conn` зберігаються в пам'яті у вигляді хеш-таблиці (conntrack table). 
Таблиця складається з масиву "кошиків" (buckets), або слотів. Коли приходить пакет, його кортеж хешується (використовується алгоритм Jenkins або SipHash), і за залишком від ділення на кількість кошиків (`HASH % HASHSIZE`) знаходиться потрібний слот. Слот є початком двобічно зв'язного списку (chain).

Чим більше розмір хеш-таблиці (кількість кошиків), тим коротші списки, і тим швидше відбувається пошук.

## Стани з'єднання у conntrack

Хоча conntrack працює на основі специфіки протоколу, він абстрагує стани до універсальних категорій:

1. **NEW:** Пакет створює нове з'єднання. Для TCP це пакет із прапорцем SYN, для UDP або ICMP — перший пакет потоку.
2. **ESTABLISHED:** Conntrack побачив пакети в обох напрямках (тобто `REPLY` пакет надійшов на `ORIGINAL` запит). Запис отримує прапорець `IPS_SEEN_REPLY`.
3. **RELATED:** Пакет не належить до існуючого з'єднання, але безпосередньо пов'язаний з ним (наприклад, ICMP помилка `Destination Unreachable` щодо вже існуючого TCP/UDP з'єднання, або FTP data-канал, пов'язаний з FTP control-каналом, якщо підключено nf_conntrack_ftp).
4. **INVALID:** Пакет не може бути ідентифікований або порушує специфікацію (наприклад, TCP ACK пакет без попереднього SYN і без існуючого запису в таблиці, або пакет з неправильними контрольними сумами).
5. **UNTRACKED:** Пакет спеціально виключено з відстеження (зазвичай за допомогою таблиці `raw` і target `CT --notrack` або правила `notrack` у nftables).

Крім цього, є ще один важливий прапорець — **ASSURED** (`IPS_ASSURED`). Запис стає `ASSURED`, коли з'єднання вважається стабільним. Для TCP це відбувається після завершення 3-way handshake, для UDP — після певної кількості успішних відповідей. `ASSURED` з'єднання не видаляються, коли таблиця conntrack заповнюється на 100% (early drop скидає лише не-assured з'єднання).

## Налаштування, ліміти та переповнення (Table Overflow)

Кількість з'єднань, які сервер може відстежувати, безпосередньо обмежена конфігурацією ядра. Це критичний фактор для високонавантажених серверів, балансувальників або маршрутизаторів.

### Основні параметри sysctl

1. `net.netfilter.nf_conntrack_max` — максимальна загальна кількість відстежуваних з'єднань у системі (максимальна кількість структур `nf_conn`).
2. `net.netfilter.nf_conntrack_buckets` — розмір хеш-таблиці (кількість кошиків/buckets). Змінити цей параметр можна лише через `/sys/module/nf_conntrack/parameters/hashsize` (у старих ядрах) або sysctl.
3. Тайм-аути, наприклад `net.netfilter.nf_conntrack_tcp_timeout_established` (за замовчуванням може бути до 5 днів (432000 секунд), зазвичай зменшують до 1 години або менше для економії пам'яті).

Ідеальне співвідношення: `nf_conntrack_max = nf_conntrack_buckets * 4` (або `* 8`). Це гарантує, що у кожному кошику в середньому буде не більше 4-8 записів (довжина ланцюжка), що забезпечує швидкий пошук `O(1)`.

### Conntrack table overflow

Якщо кількість активних з'єднань досягає `nf_conntrack_max`, ядро не може виділити нову структуру `nf_conn` для нових пакетів (стан `NEW`). Це призводить до критичної помилки:
`nf_conntrack: table full, dropping packet` (з'являється у `dmesg`).

**Симптоми переповнення:**
- Випадкові втрати пакетів і розриви нових з'єднань (таймаути при спробі відкрити сайт, підключитися по SSH).
- Мережа здається "мертвою", хоча ресурси CPU та пам'яті в нормі.

**Рішення проблеми переповнення:**
1. **Збільшити розмір таблиці та хешу.**
   ```bash
   sysctl -w net.netfilter.nf_conntrack_max=1048576
   echo 262144 > /sys/module/nf_conntrack/parameters/hashsize
   ```
   Слід пам'ятати, що кожен запис займає ~300-400 байт ядерної пам'яті (slab allocations). Записів 1 млн = ~300-400 МБ оперативної пам'яті. Це безпечно для сучасних серверів, але потребує усвідомлення.
2. **Зменшити тайм-аути.** Особливо корисно зменшити час утримання закритих з'єднань або з'єднань, що очікують:
   ```bash
   sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=3600
   sysctl -w net.netfilter.nf_conntrack_tcp_timeout_time_wait=60
   ```
3. **Вимкнути відстеження (NOTRACK).** Якщо сервер обробляє величезний обсяг трафіку (наприклад, DDoS-атака, DNS-сервер або мемкеш), для якого stateful-фільтрація і NAT не потрібні, пакети можна пропускати повз conntrack:
   - iptables: `iptables -t raw -A PREROUTING -p udp --dport 53 -j CT --notrack`
   - nftables: `nft add rule ip raw prerouting udp dport 53 notrack`

## Інструменти та діагностика: `/proc/net/nf_conntrack` та `conntrack`

Дізнатися, які з'єднання зараз відстежуються, можна кількома способами.

1. **Читання з `/proc` (або `/proc/net/ip_conntrack` у старих ядрах):**
   ```text
   cat /proc/net/nf_conntrack
   ipv4     2 tcp      6 431987 ESTABLISHED src=192.168.1.2 dst=10.0.0.1 sport=45322 dport=443 src=10.0.0.1 dst=192.168.1.2 sport=443 dport=45322 [ASSURED] mark=0 zone=0 use=2
   ```
   Тут ми бачимо протокол мережевого рівня (ipv4/2), протокол транспортного рівня (tcp/6), тайм-аут (431987 сек), стан TCP (ESTABLISHED), кортеж ORIGINAL (src=... sport=...), кортеж REPLY (src=... sport=...), статус [ASSURED], марку (mark=0) та інші дані.

2. **Утиліта `conntrack` (з пакету `conntrack-tools`):**
   Сучасний інструмент, що взаємодіє з ядром через Netlink (NFNETLINK). На відміну від `cat /proc/net/nf_conntrack`, він значно швидший і дозволяє не лише переглядати, а й видаляти або модифікувати записи в реальному часі.
   - Показати всі з'єднання: `conntrack -L`
   - Показати статистику (заповненість хешу, early drops, помилки): `conntrack -S`
   - Видалити всі записи до певного IP: `conntrack -D -d 10.0.0.1`
   - Слідкувати за змінами (real-time events): `conntrack -E`

## Conntrack target (CT) та зони (Zones)

У складних мережах, де використовуються VRF або перекриття IP-адрес (коли дві мережі мають однакові приватні IP 192.168.x.x), conntrack повинен мати можливість розділяти відстеження з'єднань, щоб не переплутати пакети.
Для цього існують **Conntrack Zones**.

Зони розділяють загальну хеш-таблицю на логічні частини. За замовчуванням усі пакети потрапляють у зону 0.
У iptables можна призначити зону за допомогою цілі `CT` у таблиці `raw`:
```bash
iptables -t raw -A PREROUTING -i eth1 -j CT --zone 1
```
У nftables:
```nft
nft add rule ip raw prerouting iif "eth1" ct zone set 1
```

Корисно також згадати про можливість прив'язки **Connection Marks (connmark)** до з'єднання. На відміну від маркера пакета (packet mark), який існує лише під час проходження конкретного пакета через стек, connmark зберігається в структурі `nf_conn` і "живе" до кінця з'єднання. Будь-який наступний пакет цього потоку може відновити packet mark із connmark (дія `Restore mark`), що дозволяє, наприклад, маршрутизувати весь потік через потрібний інтерфейс (Policy Routing).

## Висновки

Підсистема nf_conntrack — це потужний та критично важливий інструмент Linux, який перетворює фаєрвол з простого набору stateless-правил на розумну машину контролю сесій.
Вона створює місток між окремими L3-пакетами та логічними L4-потоками даних за допомогою ORIGINAL і REPLY кортежів.
Але за функціональність доводиться платити споживанням пам'яті та процесорного часу. Розуміння параметрів тюнінгу, таких як `nf_conntrack_max` та тайм-аути, є обов'язковою навичкою для будь-якого системного або мережевого адміністратора Linux, щоб ефективно протистояти table overflow і забезпечувати безперебійну роботу високонавантажених серверів.
