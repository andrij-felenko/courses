# 📜 Еволюція відстеження зʼєднань у Linux: від ipchains до nf_conntrack

Коли в середині 1990-х років корпоративні мережі почали масово підключатися до інтернету через ядра Linux 1.2 та 2.0, системні адміністратори зіткнулися з фундаментальною вразливістю stateless-фільтрації пакетів. Перші інструменти фільтрації в Linux — утиліта `ipfwadm` (написана Джосом Восом (Jos Vos) на основі кода Alan Cox і портована з BSD `ipfw`) у ядрі Linux 2.0 та її наступник `ipchains` у ядрі Linux 2.2 (створений Полом «Расті» Расселом) — вміли перевіряти лише заголовок кожного окремого пакета (IP-адреси, типи протоколів та TCP-прапорці) без збереження найменшої пам'яті про минулі події у мережі. 

Для закриття внутрішньої мережі від зовнішніх атак адміністратори мусили залишати відкритими всі TCP-порти вище 1024 із встановленим прапорцем `ACK`, оскільки інакше пакети-відповіді від зовнішніх вебсерверів або FTP-серверів просто не могли повернутися до внутрішніх клієнтів. Зловмиснику достатньо було згенерувати TCP-пакет із довільним портом джерела і прапорцем `ACK`, щоб безперешкодно обійти фаєрвол `ipchains` і доставити шкідливе корисне навантаження прямо на внутрішній хост.

## Криза безпам'ятних фільтрів та народження Netfilter

Проблема загострилася з поширенням складних протоколів транспортного та прикладного рівнів. Класичний протокол передачі файлів FTP для передачі даних створює окреме динамічне TCP-з'єднання (пасивний режим `PASV`), де порт вибирається випадковим чином у діапазоні невідомих заздалегідь високих номерів. У stateless-системах `ipfwadm` та `ipchains` дозволити пасивний FTP означало повністю відкрити весь діапазон високих портів для будь-якого вхідного трафіку з інтернету, що робило фаєрвол практично марним і залишало мережу беззахисною.

На саміті розробників ядра Linux (Linux Kernel Developers Summit) у 1999 році австралійський розробник Пол «Расті» Рассел (Paul "Rusty" Russell) запропонував фундаментальну переробку всієї мережевої підсистеми фільтрації Linux. Замість хаотичних точкових латок над кодом socket buffers (`sk_buff`) у файлах `net/ipv4/ip_input.c` та `dev.c`, він створив узагальнену підсистему **Netfilter** та підсистему відстеження з'єднань **`ip_conntrack`**, які вперше з'явилися у стабільній гілці ядра Linux 2.4.0 (січень 2001 року).

Основна ідея Рассела полягала у створенні відносно невеликої, але надзвичайно швидкої вбудованої таблиці станів прямо в просторі ядра. Замість перевірки правил фільтрації для кожного пакета з нуля, ядро Linux навчилося:

1. Зіставляти кожен вхідний або вихідний пакет із двома кортежами адресації (напрямок запиту `ORIGINAL` та очікуваний напрямок відповіді `REPLY`).
2. Призначати кожному пакету один із чотирьох фундаментальних станів: `NEW`, `ESTABLISHED`, `RELATED` або `INVALID`.
3. Надавати модульній підсистемі `iptables` змогу відкидати весь трафік у стані `INVALID` та дозволяти пакети-відповіді за єдиним узагальненим правилом:
   ```bash
   iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
   ```

Це рішення знизило складність конфігурації фаєрволів на порядки і підняло рівень безпеки Linux-маршрутизаторів до рівня спеціалізованих апаратних світчбордів Cisco, CheckPoint та Juniper.

## Обмеження `ip_conntrack` та зростання IPv6

Підсистема `ip_conntrack` у ядрах Linux 2.4 та ранніх 2.6 демонструвала високу продуктивність, але мала серйозні архітектурні вади, пов'язані з прив'язкою до конкретного протоколу:

- **Жорстка прив'язка до IPv4:** Код `ip_conntrack` розроблявся виключно для 32-бітних IP-адрес. Коли виникла потреба підтримки IPv6, розробникам довелося створити фактичний клон підсистеми — `ip6_conntrack`, що призвело до дублювання коду хешування, таймерів, алгоритмів блокування та лічильників станів.
- **Проблеми з модульністю:** Підтримка нових протоколів L4 (наприклад, SCTP, DCCP або GRE) вимагала глибокого втручання в ядро та розширення монолітних структур даних `struct ip_conntrack`.
- **Масштабованість на багатоядерних SMP-системах:** Перші версії `ip_conntrack` використовували єдине глобальне локування (spin-lock `ip_conntrack_lock`) для всієї хеш-таблиці з'єднань. На 4- або 8-ядерних серверах паралельна обробка пакетів різними мережевими картами впиралася у жорстку межпроцесорну синхронізацію, викликаючи катастрофічний спад пропускної здатності (spin-lock lock contention).

## Модульний рефакторинг: вихід `nf_conntrack` у Linux 2.6.20

Для подолання цих обмежень у 2006 році команда ядрових розробників Netfilter — Гаральд Вельте (Harald Welte), Патрік Мак-Гарді (Patrick McHardy) та Ясуюкі Козакаї (Yasuyuki Kozakai) — розпочала масштабну переробку підсистеми. Результатом їхньої праці стала поява уніфікованого модуля **`nf_conntrack`**, який офіційно замінив застарілий `ip_conntrack` у релізі ядра Linux 2.6.20 (лютий 2007 року), а в Linux 2.6.22 застарілий модуль `ip_conntrack` було повністю видалено з сирцевих текстів ядра.

Ключові архітектурні інновації `nf_conntrack` включали:

1. **Абстрагування L3 і L4 протоколів:** Структури даних були розділені на універсальну серцевину та протокольно-специфічні модулі `nf_conntrack_l3proto` (IPv4, IPv6) і `nf_conntrack_l4proto` (TCP, UDP, ICMP, ICMPv6, SCTP, GRE). Завдяки цьому з'єднання IPv4 та IPv6 відтепер оброблялися єдиним алгоритмом хешування та зберігалися у спільній хеш-таблиці.
2. **Дрібнозернисте локування (Lock Buckets):** Глобальний spin-lock було замінено на масив незалежних локів для окремих кошиків хеш-таблиці (`nf_conntrack_locks`). Це дозволило різним ядрам CPU паралельно шукати та оновлювати з'єднання у різних слотах таблиці без взаємного блокування.
3. **Використання RCU (Read-Copy-Update):** Пошук існуючого з'єднання під час проходження пакета став повністю безблокувальним для читання завдяки механізму RCU в ядрі Linux. Читач взагалі не захоплює spin-lock при виконанні lookup у хеш-таблиці.
4. **Підсистема розширень (Extensions):** З'явилася можливість динамічно підключати додаткові блоки пам'яті до структури з'єднання (`struct nf_conn`) лише тоді, коли вони дійсно потрібні (наприклад, розширення NAT, connmark, timestamping або helpers). Це зберегло оперативну пам'ять для звичайних з'єднань, які не потребують NAT.

## Сучасний стан, nftables та ера eBPF / XDP

З появою в Linux 3.13 нової підсистеми фільтрації **nftables** (яка заступила класичний `iptables`), `nf_conntrack` залишився фундаментальною основою для відстеження станів. Nftables відмовився від багатьох застарілих механізмів імпорту станів, але використовує ту саму ядерну структуру `struct nf_conn` та Netlink-інтерфейс `ctnetlink`.

У сучасних хмарних середовищах Kubernetes та високошвидкісних мережах (100+ Gbps) розробники мережевих плагінів (таких як Cilium або Calico) іноді реалізують відстеження з'єднань безпосередньо в екосистемі eBPF / XDP за допомогою BPF-карт `BPF_MAP_TYPE_LRU_HASH` (модуль `bpf_ct`), bypass-ячи стандартний стек Netfilter задля досягнення максимальної продуктивності та низької затримки (latency). Проте для переважної більшості серверів Linux підсистема `nf_conntrack` залишається еталонним, високооптимізованим і надійним ядром stateful-мережі.
