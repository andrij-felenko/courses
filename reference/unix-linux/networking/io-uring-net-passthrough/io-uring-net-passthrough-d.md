Передача мережевого трафіку зі швидкістю 100 Гбіт/с вимагає прокачування 12.5 гігабайта даних щосекунди через системну шину та оперативну пам'ять сервера. Якщо мережевий сервер використовує класичні системні виклики `send()` або `recv()`, процесор змушений копіювати кожен байт із пам'яті користувача в структури ядра `sk_buff` за допомогою функції `memcpy()`. При повній дуплексній утилізації 100-гігабітного каналу це створює навантаження у 50 гігабайт на секунду чистого трафіку читання-запису через кеші процесора. В результаті процесорні кеші рівнів L1, L2 та L3 повністю забиваються транзитними мережевими байтами, витісняючи структури даних вебсервера, баз даних або балансувальників навантаження, а системна шина RAM стає головним вузьким місцем продуктивності.

Підсистема `io_uring` вирішує цю проблему за допомогою операцій відправки та отримання даних без копіювання — `IORING_OP_SEND_ZC` (Send Zero-Copy) та `IORING_OP_RECV_ZC` (Recv Zero-Copy). Поєднуючи асинхронну кільцеву модель без системних викликів із механізмами прямого доступу до пам'яті (DMA), `io_uring` дозволяє мережевим картам читати й писати дані безпосередньо в буфери застосунку, повністю звільняючи центральний процесор від операцій `memcpy()`.

## Фізика копіювання даних та ціна системних викликів

Щоб зрозуміти, чому традиційний ввід-вивід вичерпує можливості сучасного апаратного забезпечення, розглянемо шлях пакета при класичному виклику `send(fd, buffer, length, 0)`:

1. **Переключення контексту (Context Switch):** Процесор виконує інструкцію `syscall`, здійснюючи перехід із простору користувача (Ring 3) у простір ядра (Ring 0). Це призводить до скидання конвеєра інструкцій та таблиць TLB (Translation Lookaside Buffer).
2. **Виділення пам'яті в ядрі:** Підсистема сокетів виділяє керуючу структуру `sk_buff` (Socket Buffer) та сторінки пам'яті у системному слайб-аллокаторі `kmalloc` / `kmem_cache`.
3. **Операція memcpy():** Процесор зчитує байти з віртуальної адреси буфера користувача `buffer`, завантажує їх у свої регістри та кеш L1/L2, після чого записує у виділені сторінки `sk_buff`.
4. **Формування DMA-описувачів:** Мережевий драйвер переводить віртуальні адреси ядра у фізичні адреси шини PCIe (Physical Frame Number, PFN) і записує їх у кільце передачі мережевої карти (TX Ring).
5. **Апаратний DMA-трансфер:** Контролер мережевої карти (NIC) через шину PCIe зчитує байти з RAM за фізичними адресами та відправляє їх у фізичний кабель.

![Архітектура мережевого вводу-виводу: memcpy проти SendZC](/reference/unix-linux/networking/io-uring-net-passthrough/img/io-uring-zc-arch.svg)
*Архітектура мережевого вводу-виводу: порівняння проміжного копіювання memcpy та прямого DMA-доступу за допомогою io_uring SendZC.*

Головний недолік цієї схеми — процесор виконує роботу «вантажника». При розмірі пакета 64 кілобайти процесор робить 16 384 ітерації читання-запису 32-бітних слів лише для того, щоб перекласти байти з однієї комірки RAM в іншу комірку того самого модуля RAM. 

Історія боротьби з цим обмеженням — від виклику `sendfile()` 1999 року до прапорця `MSG_ZEROCOPY` 2017 року — детально розібрана у вставці [Історія Zero-Copy в Linux: від sendfile до io_uring SendZC](book:unix-linux/io-uring-net-passthrough/hist-zerocopy-evolution.md). Проте всі попередні механізми вимагали складного опитування черги помилок сокета `MSG_ERRQUEUE`, що зводило нанівець економію CPU при роботі з малими й середніми пакетами.

## Глибокий аналіз пам'яті ядра: підсистема sk_buff та запікання сторінок

У ядрі Linux мережевий пакет описується фундаментальною структурою `struct sk_buff`. Коли застосунок надсилає дані традиційним способом, ядро виділяє пам'ять під керуючий заголовок `sk_buff` із системного кешу `skbuff_head_cache` та копіює дані в лінійну частину буфера.

При використанні Zero-Copy лінійна частина пакета залишається порожньою (містить лише заголовок протоколів L2/L3/L4), а корисне навантаження описується у векторах неподільних фрагментів `skb_shared_info(skb)->frags`. Кожен елемент `skb_frag_t` містить:
- Вказівник на сторінку ОЗП `struct page *page`.
- Зміщення від початку сторінки `__u32 page_offset`.
- Довжину фрагмента у байтах `__u32 size`.

```
Структура sk_buff при Zero-Copy:
┌───────────────────────────────────────────────────────────┐
│ struct sk_buff                                            │
│   head ────────► [Заголовки: Ethernet / IP / TCP]         │
│   end                                                     │
│   shinfo ──────► struct skb_shared_info                   │
│                    nr_frags = 2                           │
│                    frags[0] ──► Page PFN #1042 (User Buf) │
│                    frags[1] ──► Page PFN #1043 (User Buf) │
└───────────────────────────────────────────────────────────┘
```

### Механізм запікання сторінок (Page Pinning) та IOMMU

Щоб мережева карта могла зчитати дані безпосередньо з фізичних сторінок пам'яті користувача, ядро повинно гарантувати дві умови:
1. **Незмінність фізичної адреси:** Сторінка не може бути вивантажена підсистемою swap або переміщена у рамках NUMA-балансування.
2. **Безпека IOMMU:** Мапування віртуальних адрес у фізичні адреси DMA (Device Bus Address) повинно залишатися дійсним до моменту підтвердження відправлення контролером PCIe.

Для виконання цих умов функція ядра `pin_user_pages_fast()` виконує обхід таблиць сторінок процесу та збільшує спеціальний лічильник `page->_refcount` сторінки. Отримані фізичні адреси переходять під управління DMA-драйвера мережевої карти за допомогою функції `dma_map_page()`.

Якщо мережева карта підтримує контролер IOMMU (Input-Output Memory Management Unit), ядро створює віртуальні відображення у таблицях IOMMU (`iommu_map`). Це захищає решту оперативної пам'яті сервера від несанкціонованого читання або запису апаратною мережевою картою, обмежуючи доступ пристрою виключно зареєстрованими буферами.

## Взаємодія з механізмами розвантаження TSO та GSO

Сучасні високопродуктивні мережеві карти використовують технологію **TCP Segmentation Offload (TSO)** та **Generic Segmentation Offload (GSO)**. При використанні TSO застосунок через `io_uring` передає ядру один великий блок даних (наприклад, 64 КБ). Мережевий стек ядра створює один гігантський `sk_buff` (Super SKB), додає вказівники на фізичні сторінки у `skb_shared_info` і відправляє його на мережеву карту.

Апаратний контролер NIC самостійно нарізає цей 64-кілобайтний блок на стандартні кадрові сегменти Ethernet згідно з розміром MTU (наприклад, по 1500 байт), генеруючи потрібні заголовки TCP і IP для кожного сегмента на рівні кремнієвого кристала:

```
Потік TSO у поєднанні з SendZC:
SQE SendZC (64 KB) ──► Super SKB (без memcpy) ──► NIC TSO Engine ──► 44x Ethernet Frames (MTU 1500)
```

Завдяки поєднанню TSO та `IORING_OP_SEND_ZC` центральний процесор виконує лише одну асинхронну операцію підготовки на 44 мережеві пакети. Це забезпечує радикальне зниження кількості переривань та циклів обробки на один відправлений байт.

## Архітектура Send Zero-Copy (IORING_OP_SEND_ZC)

Операція `IORING_OP_SEND_ZC`, додана у ядро Linux 6.0, об'єднує відсутність копіювання з асинхронним кільцевим інтерфейсом `io_uring`. 

Замість передачі даних через `memcpy()`, ядро бере віртуальні сторінки пам'яті користувача, збільшує їхній лічильник посилань (`struct page->_refcount`) або закріплює їх через `pin_user_pages()`, після чого прикріплює вказівники на ці сторінки прямо у вектор неподільних фрагментів `skb_shared_info(skb)->frags`.

### Роль зареєстрованих буферів (IORING_REGISTER_BUFFERS)

Найбільш витратною частиною звичайного Zero-Copy є виклик `pin_user_pages()`. Щоб мережева карта могла безпечно виконати DMA за фізичною адресою, ядро повинно:
- Пройтися по таблицях сторінок процесу (Page Table Walk: PGD → P4D → PUD → PMD → PTE).
- Перевірити права доступу VMA (Virtual Memory Area).
- Заблокувати сторінки у пам'яті, унеможливлюючи їх вивантаження у swap або переміщення механізмом Compaction/NUMA balancing.

Якщо застосунок робить це на кожен пакет, накладні витрати на трансляцію та запікання сторінок перевищують вартість копіювання `memcpy()` для будь-яких обсягів даних, менших за 10–16 КБ.

Для подолання цього бар'єра `IORING_OP_SEND_ZC` інтегрується з механізмом **Fixed Buffers**. Під час ініціалізації сервер за допомогою системного виклику `io_uring_register` з прапорцем `IORING_REGISTER_BUFFERS` передає ядру масив векторів `iovec`. Ядро одноразово виконує `pin_user_pages()` для всіх буферів програми та будує внутрішню таблицю фізичних сторінок.

При наступних відправленнях через `IORING_OP_SEND_ZC` з прапорцем `IORING_RECVSEND_FIXED_BUF` у полі `ioprio` застосунок передає лише індекс буфера `buf_index` та зміщення в ньому. Ядро знаходить підготовлені фізичні сторінки за `O(1)` без жодних обходів таблиць сторінок та перевірок VMA.

## Двофазне завершення (Two-Phase Completion)

Фундаментальна відмінність Zero-Copy від копіювального відправлення полягає в управлінні життєвим циклом пам'яті. 

При копіювальному `send()` після повернення системного виклику ядро вже скопіювало байти у свій буфер `sk_buff`. Застосунок має право негайно перезаписати буфер `buf` у своєму просторі. У Zero-Copy пам'ять користувача використовується мережевою картою безпосередньо. Якщо програма змінить вміст буфера до того, як NIC вичитає його через DMA, у мережу підуть пошкоджені дані. Якщо програма звільнить пам'ять (`free()` або `munmap()`), станеться сторінкова помилка ядра або апаратний збій PCIe (Bus Fault).

Щоб запобігти цьому, `IORING_OP_SEND_ZC` використовує **двофазну модель сповіщень** через кільце Completion Queue (CQ):

![Життєвий цикл двофазного завершення SendZC](/reference/unix-linux/networking/io-uring-net-passthrough/img/io-uring-sendzc-two-phase.svg)
*Послідовність подій та двофазна синхронізація буферів між застосунком, підсистемою io_uring та мережевим контролером.*

### Фаза 1: CQE успішної передачі в мережевий стек

Коли ядро обробляє SQE з опкодом `IORING_OP_SEND_ZC`, воно викликає внутрішню функцію `io_send_zc()`. Вона формує мережевий пакет `sk_buff`, прикріплює до нього сторінки користувача та передає пакет у чергу відправки мережевого інтерфейсу `dev_queue_xmit()`.

Після цього ядро негайно поміщає у CQ кільце перший об'єкт `io_uring_cqe`:
- Поле `cqe->res` містить кількість переданих байт (наприклад, `65536`). Якщо виникла помилка на рівні сокета, повертається від'ємний код (наприклад, `-EPIPE`).
- Поле `cqe->flags` містить встановлений біт `IORING_CQE_F_MORE`.

Встановлений прапорець `IORING_CQE_F_MORE` сигналізує застосунку: *«Операція прийнята, байти передані в мережевий стек, але буфер усе ще заблоковано. Очікуйте наступного сповіщення для цієї ж операції»*.

### Фаза 2: Notification CQE (IORING_CQE_F_NOTIF) та батчинг

Після того, як мережева карта фізично передає байти через DMA і отримує апаратне переривання завершення передачі (TX Interrupt), або після того, як протокол TCP отримує підтвердження ACK від віддаленої сторони, функція ядра `skb_zcopy_ack()` знищує відповідний `sk_buff` і викликом `io_notif_complete()` генерує сповіщення.

У цей момент ядро поміщає у CQ кільце другий об'єкт `io_uring_cqe`:
- Поле `cqe->res` дорівнює `0`.
- Поле `cqe->flags` містить встановлений біт `IORING_CQE_F_NOTIF`.
- Поле `cqe->user_data` збігається з ідентифікатором першого CQE.

Отримання CQE з прапорцем `IORING_CQE_F_NOTIF` є остаточним підтвердженням того, що апаратне забезпечення та ядро повністю припинили доступ до пам'яті. Тільки після цієї події застосунок має право перезаписувати або звільняти відповідний буфер.

Для запобігання переповненню кільця CQE підсистема `io_uring` використовує механізм **батчингу нотифікацій**. Якщо застосунок відправляє серію пакетів з одного й того самого зареєстрованого буфера, ядро може об'єднати кілька нотифікацій у один CQE `IORING_CQE_F_NOTIF`, що істотно зменшує навантаження на кільце завершень.

Повний опис структур даних, полів SQE/CQE та прапорців наведено у довідникові [Інтерфейси та структури мережевого io_uring](book:unix-linux/io-uring-net-passthrough/api-io-uring-net.md).

## Багаторазовий accept та recv у режимі Multishot

У класичній моделі асинхронного вводу-виводу для прийому кожного нового з'єднання або нового пакета даних застосунок повинен сформувати новий запит у SQ-кільці. Якщо на сервер надходить тисяча підключень за секунду, програма змушена зробити 1000 ітерацій запису в SQE.

`io_uring` оптимізує цей процес через механізм **Multishot**:

1. **Multishot Accept (`IORING_ACCEPT_MULTISHOT`):** Застосунок подає **один** SQE з опкодом `IORING_OP_ACCEPT` та прапорцем `IORING_ACCEPT_MULTISHOT`. Ядро залишає цей запит активним у черзі слухаючого сокета. Кожного разу, коли додається нове TCP-з'єднання, ядро генерує CQE із прапорцем `IORING_CQE_F_MORE` та новим файловим дескриптором у `cqe->res`. Застосунок отримує безперервний потік подій про нові з'єднання без жодної повторної подачі SQE.
2. **Multishot Recv (`IORING_RECV_MULTISHOT`):** Застосунок подає один SQE на прийом даних, комбінуючи його із кільцем буферів `PBUF_RING`. Ядро повертає нові CQE по мірі надходження пакетів із мережі, автоматично вибираючи вільні буфери з кільця.

## Отримання даних без копіювання (Recv Zero-Copy)

Забезпечення Zero-Copy при відправці (`TX`) є відносно простою задачею, оскільки застосунок заздалегідь знає адреси й розміри буферів, які передаються в ядро. Натомість прийом даних (`RX`) є суттєво складнішим: мережевий пакет надходить із кабелю асинхронно, коли ядро ще не знає, якому сокету й буферу користувача він призначений.

У традиційному стеку мережева карта записує вхідний пакет через DMA у попередньо виділений ядром буфер `page_pool`, після чого ядро розбирає заголовки IP/TCP і під час виклику `recv()` копіює корисне навантаження (payload) у буфер користувача.

Для реалізації Receive Zero-Copy підсистема `io_uring` поєднує дві технології: **Provided Buffer Rings** та **Header-Data Split**.

### Надані буфери (Provided Buffer Ring — PBUF_RING)

Щоб ядро могло записати вхідні байти безпосередньо у простір користувача без копіювання, застосунок повинен надати ядру пул доступних буферів ще до того, як пакети прибудуть із мережі.

У `io_uring` це реалізовано через системний виклик `io_uring_register` з опцією `IORING_REGISTER_PBUF_RING`. Застосунок створює у спільній пам'яті кільцевий буфер `struct io_uring_buf_ring`, що складається з елементів `io_uring_buf`:

![Механізм Provided Buffers та Multishot Receive в io_uring](/reference/unix-linux/networking/io-uring-net-passthrough/img/io-uring-recvzc-pbuf.svg)
*Управління пулом буферів у спільній пам'яті через PBUF_RING для безнеперервного прийому даних у режимі Multishot.*

Схема роботи `PBUF_RING` під час прийому:
1. Застосунок заповнює кільце адресами вільних буферів у пам'яті та їхніми унікальними ідентифікаторами `buf_id`.
2. Застосунок подає **один** SQE з опкодом `IORING_OP_RECV` та прапорцем `IORING_RECV_MULTISHOT`.
3. Коли з мережі надходить пакет, ядро атомарно забирає перший вільний буфер із `PBUF_RING`, записує туди байти й генерує CQE.
4. У полі `cqe->flags` ядро повертає `IORING_CQE_F_BUFFER` та запечений у старших бітах `buf_id`.
5. Застосунок дізнається, у який саме буфер з його пулу ядро помістило дані, обробляє їх, після чого повертає `buf_id` назад у `PBUF_RING`.

### Header-Data Split та Devmem TCP (IORING_OP_RECV_ZC)

Навіть із `PBUF_RING` звичайний TCP-пакет містить 54 байти заголовків (Ethernet + IP + TCP) на початку кожного фрагмента. Якщо записати весь пакет у буфер користувача, застосунку доведеться постійно враховувати зміщення заголовків, що ламає вирівнювання сторінок пам'яті.

Сучасні мережеві карти (наприклад, 100GbE SmartNIC) підтримують функцію **Header-Data Split (HDS)**. Апаратний кард-контролер аналізує вхідний Ethernet-кадр на льоту:
- Заголовки L2/L3/L4 (54 байти) NIC відправляє через DMA у звичайний буфер ядра для обробки мережевим стеком.
- Корисне навантаження TCP (Payload, наприклад, 4096 байт) NIC відправляє через DMA безпосередньо у сторінки пам'яті, надані застосунком через `io_uring` та підсистему Devmem TCP (`DMABUF`).

Операція `IORING_OP_RECV_ZC` (додана в Linux 6.7+) спирається на цей апаратний розділювач: ядро обробляє протокол TCP у звичайному режимі, але самі байти даних опиняються у буферах користувача без жодного виклику `memcpy()`.

## Паснаскрізні команди сокетів (Passthrough & IORING_OP_URING_CMD)

Окрім класичних мережевих операцій read/write, підсистема `io_uring` підтримує механізм паснаскрізного виконання команд — `IORING_OP_URING_CMD` (Uring Command Passthrough).

Традиційно розширені мережеві конфігурації (налаштування фільтрів апаратного розвантаження, керування сокетами AF_XDP або керування підсистемою Kernel TLS) вимагали системного виклику `ioctl()`. Виклик `ioctl()` створює серйозні накладні витрати, оскільки вимагає повного блокування файлового дескриптора у VFS (Virtual File System) та перевірок атрибутів `file_operations`.

Операція `IORING_OP_URING_CMD` дозволяє мережевим драйверам та підсистемам ядра визначати власні 80-байтові асинхронні команди. Застосунок подає `IORING_OP_URING_CMD` у кільце SQ, і ядро передає команду безпосередньо у драйвер сокета чи мережевої карти, оминаючи шар VFS. Це дозволяє виконувати апаратні переналаштування сокета та прямий допуск до RX/TX кілець без системних викликів.

## Вплив топології NUMA та кешу процесора

При побудові 100-гігабітних систем із Zero-Copy критично важливу роль відіграє архітектурна топологія NUMA (Non-Uniform Memory Access).

У сучасних багатосокетних серверах кожна група ядер процесора має власний локальний контролер пам'яті RAM та власні слоти шини PCIe. Якщо мережева карта підключена до шини PCIe процесора NUMA Node 0, а зареєстрований буфер пам'яті `IORING_REGISTER_BUFFERS` виділено з модулів ОЗП, підключених до NUMA Node 1, кожен DMA-трансфер змушений проходити через міжпроцесорну шину UPI (Ultra Path Interconnect) / QPI:

```
Топологія NUMA при Zero-Copy:

[CPU Core Node 0] ◄─── PCIe Bus ───► [100GbE NIC]
       │                                   ▲
  Local RAM Node 0                        │ (Повільний DMA через міжпроцесорний UPI)
       │                                   │
       └─── Interconnect (UPI/QPI) ────────┘
       │
  Remote RAM Node 1 (Виділений буфер з помилкою)
```

Передавання даних через міжпроцесорну шину збільшує затримку DMA-читання на 120–180 наносекунд та зменшує граничну пропускну здатність каналу на 25–40%.

Для досягнення максимальної продуктивності застосунок повинен:
1. Прив'язувати робочі потоки `io_uring` до процесорних ядер відповідного NUMA-вузла за допомогою `sched_setaffinity()`.
2. Виділяти фіксовані буфери пам'яті через `numa_alloc_onnode()` на тому ж NUMA-вузлі, до якого приєднано мережевий адаптер.
3. Прив'язувати обробку апаратних переривань NIC (IRQ Affinity) до відповідних ядер процесора.

## Порівняльний аналіз та межі ефективності Zero-Copy

Zero-Copy не є універсальною оптимізацією, яка прискорює будь-який мережевий код. Використання `IORING_OP_SEND_ZC` супроводжується фіксованими накладними витратами ядра:
- Створення та обробка двох об'єктів CQE на кожен запит (підвоєння навантаження на CQ-кільце).
- Атомарні операції з масивом сторінок `skb_shared_info`.
- Синхронізація переривань мережевої карти для формування нотифікацій `IORING_CQE_F_NOTIF`.

Вирішальним фактором вибору між копіювальним `SEND` та `SEND_ZC` є **розмір мережевого навантаження (payload size)**.

```
Вартість обробки відправлення (CPU cycles):

  Цикли CPU
     ▲
     │       /  Класичний send() (зростає лінійно через memcpy)
     │      /
     │     /
     │    /     io_uring SendZC (фіксовані витрати на 2 CQE)
     │   / ───────────────
     │  /
     │ /
     └─┴───────────────► Розмір пакета (Bytes)
       4KB           64KB
```

1. **Малі пакети (< 4 КБ):** Вартість виконання `memcpy()` для 512 або 1024 байтів становить менше 100 наносекунд і повністю вміщується у квік-кеш L1 процесора. Накладні витрати на двофазне завершення SendZC у цьому разі **вищі** за вартість копіювання. Застосування Zero-Copy для малих HTTP-заголовків або RPC-пакетів призводить до падіння продуктивності на 10–15%.
2. **Середні пакети (4 КБ – 16 КБ):** Точка паритету. Продуктивність обидвох підходів приблизно однакова.
3. **Великі пакети (> 32 КБ – 64 КБ і більше):** `memcpy()` виходить за межі L1/L2 кешу і починає витісняти дані з L3 кешу, впираючись у пропускну здатність шини RAM. `IORING_OP_SEND_ZC` демонструє суттєву перевагу: завантаження CPU знижується на 50–70%, а пропускна здатність мережевого сокета досягає лінійного ліміту фізичного каналу 100 Gbps.

Практична реалізація повноцінного TCP ехо-сервера на C та C++ з використанням SendZC та fixed-буферів представлена у вставці [Практична реалізація SendZC/RecvZC сервера в io_uring](book:unix-linux/io-uring-net-passthrough/proj-zerocopy-tcp-server.md).

## Діагностика та трасування мережевого io_uring

Налагодження високопродуктивних мережевих систем із Zero-Copy вимагає інструментів моніторингу внутрішнього стану ядра. Linux надає для цього спеціалізовані трасувальні точки (tracepoints) та параметри sysctl.

### Моніторинг системних лімітів пам'яті

Кожна двофазна нотифікація SendZC вимагає виділення системної пам'яті ядра під буфер сповіщень. Ці ресурси обмежуються параметром `optmem_max`:

```bash
# Перевірка поточного ліміту пам'яті для мережевих нотифікацій
sysctl net.core.optmem_max

# Збільшення ліміту до 4 МБ для високонавантаженого 100GbE сервера
sysctl -w net.core.optmem_max=4194304
```

Якщо застосунок генерує тисячі паралельних `SEND_ZC` операцій при малому `optmem_max`, ядро не зможе виділити нотифікаційний контекст, і операція завершиться з помилкою `-ENOBUFS`.

### Трасування за допомогою eBPF та bpftrace

Для аналізу того, чи реально ядро використовує Zero-Copy, чи скидає виконання у копіювальний фолбек, застосовують трасувальні точки підсистеми `io_uring`:

```bash
# Відстеження завершення двофазних нотифікацій SendZC
bpftrace -e 'tracepoint:io_uring:io_uring_complete { 
    if (args->flags & 8) { // 8 == IORING_CQE_F_NOTIF
        @notifs[args->res]++; 
    } 
}'
```

Також корисно моніторити події виділення та звільнення сторінок у мережевому стеку через tracepoint `skb:kfree_skb`, щоб переконатися у відсутності витоків пам'яті при роботі з `PBUF_RING`.

> 🔧 **Навіщо це.** Мережевий ввід-вивід `io_uring` із SendZC та RecvZC є архітектурним фундаментом для розробки високонавантажених мережевих систем нового покоління: медіа-стрімерів, in-memory баз даних (Redis, KeyDB), орієнтованих на NVMe-over-Fabrics сховищ та проксі-серверів (Envoy, HAProxy). Розуміння різниці між копіюванням `memcpy()` та прямим DMA-доступом дозволяє будувати сервери, які утилізують 100-гігабітні та 400-гігабітні мережеві канали при мінімальних витратах процесорного часу.
