# 📜 Історія Zero-Copy в Linux: від sendfile до io_uring SendZC

Передавання даних між дисковими накопичувачами, оперативною пам’яттю та мережевими інтерфейсами за допомогою класичних системних викликів створює критичні накладні витрати на копіювання байтів через процесорні кеші та системну шину. Борючись із цими втратами продуктивності у високонавантажених серверах, розробники ядра Linux послідовно пройшли шлях від локальних оптимізацій роздачі статичного контенту до повноцінної архітектури Zero-Copy у підсистемі `io_uring`. Еволюція охоплює системні виклики `sendfile` та `splice`, прапорець `MSG_ZEROCOPY` і сучасні механізми `io_uring` SendZC/RecvZC, кожен із яких розв'язував специфічні проблеми свого часу.

## Ера вебсерверів та статичного контенту: sendfile(2)

Наприкінці 1990-х років із вибуховим зростанням мережі Інтернет та популяризацією вебсерверів (таких як Apache HTTP Server 1.3 та NGINX) основними операціями вводу-виводу стала масова роздача статичних файлів (зображень, вебсторінок, медіафайлів) із дискових накопичувачів у мережу. Традиційна схема обробки таких запитів полягала у послідовному використанні двох системних викликів: `read()` для зчитування даних із файлу у пам'ять користувача та `write()` (або `send()`) для запису цих даних у сокет.

Цей класичний підхід створював колосальні накладні витрати:

1. **Перший системний виклик `read(file_fd, buffer, length)`:** Процесор переключається у режим ядра. Дисковий контролер за допомогою DMA завантажує байти з диска в сторінковий кеш ядра (Page Cache). Потім ядро виконує операцію `memcpy()`, копіюючи дані зі сторінкового кешу у буфер простору користувача `buffer`.
2. **Другий системний виклик `write(socket_fd, buffer, length)`:** Процесор знову переключається у режим ядра. Ядро виконує другу операцію `memcpy()`, копіюючи дані з буфера користувача у структури `sk_buff` (Socket Buffer) мережевого сокета. Мережева карта (NIC) за допомогою DMA передає ці байти з системної пам'яті в фізичне середовище.

У результаті кожен байт файлу двічі проганявся через процесорні кеші L1, L2 та L3 і створював подвійне навантаження на системну шину пам'яті. При обслуговуванні тисяч паралельних HTTP-клієнтів це призводило до швидкої деградації продуктивності процесора та утворення вузького місця у контролері RAM.

У ядрі Linux 2.2, випущеному у січні 1999 року, розробники реалізували спеціалізований системний виклик `sendfile()`. Основна ідея `sendfile()` полягала у передачі даних безпосередньо від файлового дескриптора до мережевого сокета в межах ядра Linux, минаючи простір користувача. У першій версії `sendfile()` це позбавляло застосунок від необхідності виділяти власні буфери й переключати контекст між прочитанням і записом, але всередині ядра все одно виконувалася проміжна операція `memcpy()` зі сторінкового кешу у мережевий буфер сокета.

Справжній Zero-Copy для `sendfile()` було досягнуто під час перебудови мережевого стека у ядрі Linux 2.4 Днем Міллером (David S. Miller). Він додав підтримку апаратного механізму **Scatter-Gather DMA**. Якщо мережева карта підтримувала збір даних із різних фізичних сторінок, ядро переставало копіювати байти. Замість цього ядро формувало структури `sk_buff` так, щоб вони містили лише список фізичних вказівників (`skb_frag_t`) на сторінки сторінкового кешу ядра. Контролер мережевої карти зчитував байти безпосередньо зі сторінок `Page Cache` через шину PCIe.

```
Класичний підхід (read + write):
Disk DMA -> Page Cache -> [memcpy] -> User Buffer -> [memcpy] -> Socket Buffer -> NIC DMA

sendfile() із Scatter-Gather DMA (Linux 2.4+):
Disk DMA -> Page Cache ---------------------------------------> NIC DMA
                            (ядро передає лише pfn/offset)
```

Головним обмеженням `sendfile()` була його жорстка прив'язка до джерела даних: він працював виключно за схемою «файловий дескриптор на диску → мережевий сокет». Застосунок не мав можливості модифікувати байти на льоту — наприклад, застосувати шифрування TLS/SSL, стиснення Gzip або модифікувати заголовки протоколу, оскільки дані не потрапляли у простір пам'яті користувача.

## Універсалізація каналів: splice(2) та tee(2)

Прагнучи усунути обмеження `sendfile()` і надати розробникам універсальний інструмент передачі даних між довільними файловими дескрипторами, у ядрі Linux 2.6.17 (випущеному в червні 2006 року) Лінус Торвальдс запропонував системні виклики `splice()` та `tee()`.

Замість жорсткого зв'язку «диск → сокет», `splice()` спирався на концепцію кільцевого буфера анонімного каналу (pipe buffer). Буфер каналу в ядрі описувався як масив структури `struct pipe_buffer`, який містив не самі байти, а покажчики на сторінки пам'яті (`struct page*`).

Системний виклик `splice()` дозволяв перенаправляти дані між будь-яким джерелом та приймачем, якщо хоча б один із них був анонімним каналом (`pipe`). Наприклад, для перенаправлення трафіку з одного сокета в інший (у високопродуктивних проксі-серверах, таких як HAProxy):

1. `splice(sock_in, NULL, pipe_fd, NULL, len, SPLICE_F_MOVE)` — ядро захоплює сторінки вхідних мережевих пакетів і записує їхні вказівники у буфер пайпа без копіювання.
2. `splice(pipe_fd, NULL, sock_out, NULL, len, SPLICE_F_MOVE)` — ядро передає ці ж сторінки у вихідний сокет, де мережева карта зчитує їх через DMA.

Однак виклик `splice()` мав суттєві архітектурні недоліки:
- **Накладні витрати на файлові дескриптори:** Необхідність створення та підтримки системних каналів `pipe` для кожного мережевого з'єднання створювала додаткове навантаження на таблицю дескрипторів процесу.
- **Неможливість роботи з буферами ОЗП користувача:** `splice()` не дозволяв відправляти довільні масиви пам'яті, згенеровані безпосередньо у просторі користувача (наприклад, динамічно згенеровані списки об'єктів у базах даних).

## Довільні буфери користувача: MSG_ZEROCOPY

Для сучасних високопродуктивних застосунків (in-memory баз даних Redis, Memcached, серверів потокового відео, розподілених сховищ Ceph) більшість даних формується безпосередньо в ОЗП простору користувача. Оскільки цих даних немає у дисковому сторінковому кеші, `sendfile()` для них виявився непридатним.

У 2017 році Віллем де Брюйн (Willem de Bruijn) із компанії Google розробив і впровадив у ядро Linux 4.14 прапорець `MSG_ZEROCOPY` для системних викликів `send()`, `sendto()` та `sendmsg()`.

Механізм `MSG_ZEROCOPY` дозволив надсилати довільні буфери пам'яті користувача без копіювання у ядро за наступним алгоритмом:

1. Застосунок викликає `send(fd, buffer, length, MSG_ZEROCOPY)`.
2. Ядро викликає внутрішню функцію `pin_user_pages()`, яка проходить по таблицях сторінок процесу і закріплює віртуальні сторінки `buffer` у фізичній пам'яті ОЗП. Це гарантує, що сторінки не будуть переміщені підсистемою управління пам'яттю або вивантажені у swap під час виконання DMA.
3. Мережевий стек формує пакет `sk_buff`, додаючи вказівники на запечені сторінки користувача у масив `skb_shared_info`. Мережева карта передає байти через DMA.
4. Оскільки ядро не копіює буфер у власній пам'яті, воно забороняє застосунку перезаписувати `buffer` до тих пір, поки NIC не завершить передачу й не отримає підтвердження TCP ACK.
5. Для сповіщення застосунку про звільнення буфера ядро використовує чергу помилок сокета (`MSG_ERRQUEUE`). Застосунок змушений регулярно викликати `recvmsg(fd, ..., MSG_ERRQUEUE)` і розбирати спеціальні структури `sock_extended_err`.

### Чому MSG_ZEROCOPY не став абсолютним стандартом

Незважаючи на усунення операції `memcpy()`, прапорець `MSG_ZEROCOPY` мав серйозні обмеження продуктивності:
- **Накладні витрати на чергу помилок:** Опитування черги `MSG_ERRQUEUE` вимагало додаткових системних викликів `recvmsg()`. Накладні витрати на переключення контексту процесора та запікання сторінок `pin_user_pages()` при кожному виклику виявлялися більшими за вартість `memcpy()` для пакетів розміром менше 10–64 КБ.
- **Складність контролю стану:** Програміст повинен був реалізовувати складний апарат стану для відстеження унікальних ідентифікаторів пакетів (sequence numbers) у черзі помилок, що ускладнювало архітектуру мережевих бібліотек.

## Революція io_uring: SendZC та RecvZC

У 2019 році Йенс Аксбо (Jens Axboe) представив підсистему `io_uring`, яка змінила парадигму взаємодії із ядром Linux за рахунок двох кільцевих буферів у спільній пам'яті: Submission Queue (SQ) для подачі запитів та Completion Queue (CQ) для отримання результатів.

У ядрі Linux 6.0 (осінь 2022 року) Павло Бегунков (Pavel Begunkov) реалізував операцію `IORING_OP_SEND_ZC`. Вона об'єднала переваги `MSG_ZEROCOPY` із фундаментальними ідеями `io_uring`:

1. **Відсутність системних викликів на сповіщення:** Сповіщення про завершення передачі та звільнення пам'яті потрапляють прямо у загальне кільце CQЕ як специфічні елементи з прапорцем `IORING_CQE_F_NOTIF`. Додаткові системні виклики `recvmsg()` більше не потрібні.
2. **Інтеграція з Fixed Buffers:** При використанні `IORING_REGISTER_BUFFERS` сторінки пам'яті закріплюються ядром одноразово при старті програми. Це повністю усуває витрати на `pin_user_pages()` при кожній операції відправки.
3. **Двофазне завершення без черги помилок:** Програма отримує результат відправки у першому CQE, а потім сповіщення про безпечність повторного використання буфера у другому CQE.

Далі, у ядрах 6.7–6.10, спільнота Linux розробила механізми `IORING_OP_RECV_ZC` та підтримку Devmem TCP (Zero-Copy Receive за допомогою `page_pool` та DMABUF). Це завершило еволюційний шлях, надавши Linux повний двосторонній симетричний Zero-Copy мережевий стек для асинхронних застосунків.

| Ера / Механізм | Версія ядра | Джерело даних | Куди передає | Спосіб сповіщення | Основне обмеження |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **sendfile** | Linux 2.2 / 2.4 | Файл (Page Cache) | Мережевий сокет | Синхронний повернення | Лише для читання з файлів |
| **splice** | Linux 2.6.17 | Будь-який fd | Будь-який fd (через pipe) | Синхронне повернення | Потребує екземплярів pipe |
| **MSG_ZEROCOPY** | Linux 4.14 | Буфер користувача | Мережевий сокет | `MSG_ERRQUEUE` (recvmsg) | Накладні витрати на context switch та error queue |
| **io_uring SendZC** | Linux 6.0+ | Буфер користувача / Fixed Buf | Мережевий сокет | CQE (`IORING_CQE_F_NOTIF`) | Потребує відстеження 2-х CQE на запит |
