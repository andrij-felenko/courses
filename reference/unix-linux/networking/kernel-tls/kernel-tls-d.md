# TLS усередині ядра: шар записів на сокеті (kTLS)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Технологія Kernel TLS (kTLS) стала одним із найбільш значущих нововведень у мережевому стеку Linux за останні роки. Вона дозволяє перенести виконання криптографічних операцій (шифрування та розшифрування) з простору користувача (user-space) безпосередньо у простір ядра (kernel-space), що відкриває можливості для значного підвищення продуктивності та апаратного прискорення.

## 1. Архітектура та мотивація kTLS

Традиційно протокол Transport Layer Security (TLS) реалізовувався виключно у просторі користувача за допомогою бібліотек, таких як OpenSSL, GnuTLS або BoringSSL. Процес відправки даних виглядав наступним чином: додаток формував відкритий текст, передавав його у бібліотеку TLS, яка виконувала шифрування, формувала TLS-запис (record) і передавала цей зашифрований блок у ядро через системний виклик `send()` або `write()`.

Такий підхід має кілька суттєвих недоліків:

1. **Зайве копіювання даних**: При використанні традиційного простору користувача дані повинні бути скопійовані з ядра (якщо вони, наприклад, читаються з диска) у простір користувача, зашифровані, а потім знову скопійовані у ядро для відправки через мережу.
2. **Неможливість використання sendfile(2)**: Системний виклик `sendfile()` дозволяє ядру передавати дані безпосередньо з файлового кешу у мережевий буфер без копіювання у простір користувача. У традиційній моделі TLS це було неможливо, оскільки дані мали пройти через простір користувача для шифрування.
3. **Обмеження апаратного розвантаження (Hardware Offload)**: Сучасні мережеві інтерфейси (NIC) здатні самостійно шифрувати дані "на льоту". Але для цього ядро повинно розуміти формат TLS і передавати ключі мережевій карті. Якщо TLS обробляється повністю в user-space, ядро бачить лише непрозорий потік байтів, що унеможливлює апаратне прискорення.

kTLS вирішує ці проблеми, реалізуючи шар записів TLS (TLS Record Layer) безпосередньо як частину мережевого стеку ядра.

### Шар записів (Record Layer)

kTLS не реалізує весь протокол TLS. Процедура "рукостискання" (TLS Handshake), яка є надзвичайно складною і вимагає обробки сертифікатів, X.509, узгодження шифрів та генерації ключів, продовжує виконуватися у просторі користувача за допомогою стандартних бібліотек.

У ядро переноситься лише симетричне шифрування/розшифрування (шар записів). Після того як бібліотека в user-space успішно завершує handshake і отримує ключі сесії, вона передає ці ключі в ядро. З цього моменту ядро самостійно формує TLS-записи і шифрує корисне навантаження.

## 2. Налаштування kTLS: TCP_ULP

Інтерфейс взаємодії з kTLS реалізовано за допомогою стандартних сокетних опцій. Ключовою концепцією тут є ULP (Upper Layer Protocol) — інфраструктура у ядрі Linux, яка дозволяє "нашаровувати" додаткову логіку поверх існуючого TCP-з'єднання.

Щоб увімкнути kTLS для певного TCP-сокету, додаток використовує системний виклик `setsockopt` з рівнем `IPPROTO_TCP` та опцією `TCP_ULP`, передаючи рядок `"tls"`.

```c
#include <netinet/tcp.h>
#include <string.h>

int enable_ktls(int sockfd) {
    const char *ulp = "tls";
    return setsockopt(sockfd, IPPROTO_TCP, TCP_ULP, ulp, strlen(ulp));
}
```

Цей виклик переводить сокет у режим TLS. Проте на цьому етапі ядро ще не знає, як саме шифрувати дані, оскільки воно не має криптографічних ключів.

## 3. Передача ключів: setsockopt(SOL_TLS)

Після активації ULP додатку необхідно передати ядру симетричні ключі, вектори ініціалізації (IV) та інформацію про обраний алгоритм шифрування (наприклад, AES-128-GCM або AES-256-GCM).

Це робиться окремо для напрямку передачі (TX) та прийому (RX) за допомогою опцій `TLS_TX` та `TLS_RX` на рівні `SOL_TLS`.

```c
#include <linux/tls.h>

struct tls_crypto_info_keys {
    struct tls12_crypto_info_aes_gcm_128 gcm128;
    // ...
};

int set_tls_keys(int sockfd, struct tls12_crypto_info_aes_gcm_128 *crypto_info, int direction) {
    int optname = (direction == 1) ? TLS_TX : TLS_RX;
    return setsockopt(sockfd, SOL_TLS, optname, crypto_info, sizeof(*crypto_info));
}
```

Структура `tls12_crypto_info_aes_gcm_128` містить версію TLS, тип шифру, ключ, IV та сіль (salt). Після цього виклику будь-які дані, записані в сокет за допомогою `send()` або `write()`, будуть автоматично зашифровані ядром і відправлені як TLS-записи типу `Application Data`. Відповідно, дані, отримані через `recv()` або `read()`, будуть автоматично розшифровані, і додаток отримає чистий відкритий текст.

## 4. Інтеграція із sendfile(2) та zero-copy

Однією з найпотужніших переваг kTLS є можливість використання системного виклику `sendfile(2)` для передачі зашифрованих даних без їх копіювання у простір користувача.

Традиційна роздача файлів через HTTPS вимагає:
1. `read()` (диск -> ядро -> user-space).
2. Шифрування (в user-space).
3. `send()` (user-space -> ядро -> мережа).

З увімкненим kTLS вебсервер (наприклад, Nginx) може просто викликати `sendfile(sockfd, filefd, &offset, count)`.
Ядро бере сторінки з файлового кешу (page cache), розбиває їх на частини, що відповідають максимальному розміру TLS-запису (16 КБ), шифрує їх у пам'яті ядра та відправляє у мережевий стек. Це не тільки заощаджує цикли CPU на копіюванні пам'яті, але й зменшує кількість перемикань контексту.

Крім того, kTLS підтримує `MSG_ZEROCOPY`, що дозволяє відправляти дані, згенеровані безпосередньо у просторі користувача (наприклад, динамічний контент), без копіювання у буфери ядра, створюючи повністю безкопійний конвеєр (zero-copy pipeline) для TLS.

## 5. Апаратне розвантаження (NIC TLS Offload)

Якщо економія на копіюванні даних (завдяки `sendfile`) вже забезпечує значний приріст продуктивності, то апаратне розвантаження kTLS піднімає ефективність на якісно новий рівень.

Сучасні мережеві інтерфейсні карти (NIC), такі як Mellanox (NVIDIA) ConnectX-6 та інші, мають вбудовані криптографічні рушії, здатні шифрувати потоки даних зі швидкістю 100 Гбіт/с і вище.

Коли додаток налаштовує ключі kTLS через `setsockopt(TLS_TX)`, ядро Linux перевіряє, чи підтримує поточна мережева карта апаратне розвантаження для обраного алгоритму (наприклад, AES-GCM). Якщо так, ядро не шифрує дані самостійно, а натомість програмує мережеву карту, передаючи їй ключі та інформацію про стан TLS.

Процес відправки з Hardware Offload виглядає так:
1. Ядро бере відкритий текст.
2. Ядро формує заголовок TLS-запису та TCP/IP заголовки.
3. Ядро передає вказівник на дані мережевій карті.
4. Мережева карта "на льоту" (in-line) шифрує дані, обчислює GCM-тег, формує кінцевий пакет і відправляє його у кабель.

Це повністю звільняє центральний процесор (CPU) від складних криптографічних обчислень. Для хостинг-провайдерів та CDN це означає можливість обробляти вдвічі чи втричі більше HTTPS-з'єднань на одному сервері.

## 6. Типи записів та керуючі повідомлення (Control Messages)

TLS — це не лише дані додатку (`Application Data`). Існують також інші типи записів: `Handshake`, `Alert`, `ChangeCipherSpec`. Оскільки handshake залишається у просторі користувача, бібліотека TLS (наприклад, OpenSSL) повинна мати можливість відправляти та отримувати не тільки `Application Data`, але й керуючі повідомлення через той самий kTLS-сокет.

Для цього використовується допоміжне повідомлення (ancillary data) у системному виклику `sendmsg()`. Додаток може вказати тип TLS-запису (наприклад, `TLS_RECORD_TYPE_ALERT`) у структурі `cmsghdr`.

```c
// Псевдокод відправки TLS Alert через kTLS
struct msghdr msg = {0};
struct cmsghdr *cmsg;
char buf[CMSG_SPACE(sizeof(uint8_t))];

msg.msg_control = buf;
msg.msg_controllen = sizeof(buf);
cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_TLS;
cmsg->cmsg_type = TLS_SET_RECORD_TYPE;
cmsg->cmsg_len = CMSG_LEN(sizeof(uint8_t));
*((uint8_t *)CMSG_DATA(cmsg)) = 21; // Alert
```

При отриманні даних (RX) kTLS також використовує допоміжні повідомлення (cmsg) у `recvmsg()`, щоб повідомити додатку, що отриманий блок даних є не звичайними даними, а керуючим записом, який потрібно передати у криптографічну бібліотеку для обробки.

## 7. Обмеження та міркування щодо безпеки

Попри всі переваги, використання kTLS має свої особливості та обмеження:
- **Перезапуск з'єднання (Renegotiation) / Key Update**: У TLS 1.3 оновлення ключів (Key Update) вимагає пересинхронізації між ядром та user-space. Додаток повинен перехопити запит на оновлення ключів і знову викликати `setsockopt` з новими ключами.
- **Відкриті ключі в ядрі**: Ключі сесії зберігаються у пам'яті ядра. У разі вразливості ядра (наприклад, витоку пам'яті через експлойт) зловмисник може отримати доступ до ключів активних сесій. Втім, оскільки ці ключі вже існують в пам'яті процесу в user-space, ризик вважається прийнятним для більшості систем.
- **Підтримка шифрів**: kTLS у Linux підтримує обмежений набір алгоритмів. Станом на поточний момент це переважно сімейства AES-GCM (128 і 256 біт), ChaCha20-Poly1305, та AES-CCM. Якщо клієнт домовляється про використання застарілого шифру (наприклад, AES-CBC), з'єднання буде змушене працювати у класичному user-space режимі.

## Висновки

Kernel TLS — це потужний інструмент оптимізації, який докорінно змінює спосіб обробки захищених з'єднань на Linux. Відокремлення складного handshake, що залишається у user-space, від високопродуктивного Record Layer у ядрі, є прикладом елегантного архітектурного компромісу. У поєднанні з `sendfile` та апаратним розвантаженням (NIC offload), kTLS дозволяє серверам досягати пропускної здатності шифрованого трафіку, яка раніше була доступна лише для незашифрованого TCP.
