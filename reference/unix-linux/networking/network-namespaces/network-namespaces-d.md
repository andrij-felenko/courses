# Мережеві простори імен: ізоляція стеків, veth-пари й маршрутизація між ними

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Мережеві простори імен (Network Namespaces, netns) є фундаментальним механізмом ядра Linux, який забезпечує ізоляцію мережевого стека. Уявіть, що ви можете розділити один фізичний сервер на десятки або сотні віртуальних машин, але без накладних витрат на емуляцію апаратного забезпечення. Замість повноцінної віртуалізації, ядро Linux просто розділяє бачення ресурсів між процесами. Коли процес працює у власному мережевому просторі імен, він "бачить" абсолютно ізольоване середовище: власні мережеві інтерфейси (включно зі своїм `lo`), свої таблиці маршрутизації, власні правила фаєрвола (iptables/nftables) і навіть власний набір відкритих портів.

Ця стаття пропонує глибоке занурення в архітектуру мережевих просторів імен, використання `veth`-інтерфейсів для зв'язку між ними та побудову комплексних маршрутизованих топологій.

## 1. Архітектура та структура `netns` у ядрі

### 1.1. Історичний контекст та еволюція

Історично ядро Linux розроблялося з монолітним баченням мережі. Була глобальна змінна, яка представляла весь мережевий стек. З появою потреби в контейнеризації (проекти на кшталт OpenVZ, пізніше LXC), виникла необхідність ізолювати мережеву активність різних груп процесів. Для цього розробники ядра провели колосальну роботу з рефакторингу, замінивши глобальні змінні мережевого стека на вказівники на структуру `net`. 

### 1.2. Структура `struct net`

У вихідному коді ядра Linux (переважно в `include/net/net_namespace.h`) мережевий простір імен представлений структурою `struct net`. Ця структура містить вказівники на всі компоненти, що становлять ізольований мережевий стек:

*   **Список пристроїв (`struct list_head dev_base_head`)**: Кожен мережевий пристрій (`struct net_device`) належить рівно одному екземпляру `struct net`. Тому, якщо інтерфейс `eth0` знаходиться в просторі `netns1`, він фізично невидимий для процесів у глобальному просторі (або `netns2`).
*   **Таблиці маршрутизації FIB (Forwarding Information Base)**: Ядро підтримує окремі FIB для кожного простору.
*   **Таблиці сусідів (ARP/NDP caches)**: Кеші роздільні, тому процеси в різних просторах можуть мати однакові IP-адреси без конфліктів.
*   **Правила Netfilter (iptables, nftables)**: Правила фільтрації трафіку та трансляції адрес (NAT) ізольовані.
*   **Сокети**: Відкриті порти (наприклад, TCP 80) прив'язані до конкретного простору. Два веб-сервери можуть слухати порт 80, якщо вони працюють у різних мережевих просторах.
*   **Sysctl-параметри**: Більшість мережевих налаштувань у `/proc/sys/net/` (наприклад, `net.ipv4.ip_forward`) застосовуються per-namespace.

### 1.3. Створення простору: системний виклик `clone()` та `CLONE_NEWNET`

Створення нового простору імен відбувається за допомогою системного виклику `clone(2)` (або `unshare(2)`). Прапорець, що відповідає за мережевий простір, називається `CLONE_NEWNET`.

Коли процес викликає `unshare(CLONE_NEWNET)`, ядро виділяє нову структуру `struct net`, ініціалізує її значеннями за замовчуванням (створює новий loopback інтерфейс `lo`, порожню таблицю маршрутизації тощо) і асоціює поточний процес з цією новою структурою. Важливо розуміти, що при створенні простору новий `lo` інтерфейс вимкнений (`DOWN`), і його необхідно явно підняти (`ip link set lo up`), щоб мережа функціонувала коректно навіть усередині простору (інакше не працюватиме адресація `127.0.0.1`).

Мережевий простір існує доти, доки в ньому працює хоча б один процес (його reference counter > 0), або якщо на нього існує явне посилання у файловій системі (так званий *bind mount*). Утиліта `ip netns` створює саме такі постійні посилання в каталозі `/var/run/netns/`.

## 2. Управління через утиліту `ip netns`

Інструментарій `iproute2` надає зручний інтерфейс для управління мережевими просторами імен через підкоманду `ip netns`. Вона дозволяє створювати, видаляти та виконувати команди в ізольованому середовищі.

### 2.1. Створення та видалення

Створення нового мережевого простору `red` виконується командою:
```bash
ip netns add red
```
Під капотом, ця команда:
1. Викликає `unshare(CLONE_NEWNET)`, створюючи новий простір.
2. Створює файл `/var/run/netns/red`.
3. Робить bind mount поточного простору (який є новим завдяки `unshare`) на цей файл. Це збільшує лічильник посилань `struct net`, не дозволяючи простору зникнути після завершення процесу створення.

Видалення простору:
```bash
ip netns del red
```
Ця команда лише демонтує (unmount) файл `/var/run/netns/red` та видаляє його. Якщо всередині цього простору все ще працюють процеси (наприклад, ви запустили там shell або веб-сервер), ядро не знищить простір, поки ці процеси не завершаться. Простір просто стане "невидимим" для утиліти `ip netns` (бо файл видалено).

### 2.2. Виконання команд: `ip netns exec`

Щоб процес працював усередині створеного простору, його треба туди помістити. Це робиться командою:
```bash
ip netns exec red command
```
Наприклад, щоб побачити інтерфейси в просторі `red`:
```bash
ip netns exec red ip link show
```
Як це працює:
Утиліта `ip netns exec` відкриває файл `/var/run/netns/red`, отримує файловий дескриптор, і використовує системний виклик `setns(fd, CLONE_NEWNET)`. Після цього ядро перемикає поточний процес у простір імен `red`. Далі процес виконує `execvp`, замінюючи себе на цільову команду (наприклад, `bash` або `ip link`).

## 3. З'єднання просторів: `veth` пари (Virtual Ethernet)

Якщо ви створите новий мережевий простір, він буде абсолютно ізольований. У нього буде лише інтерфейс `lo`. Він не зможе спілкуватися ані з хостовою системою (глобальним простором), ані з іншими просторами, ані з інтернетом.

Для встановлення зв'язку між різними мережевими просторами використовуються `veth`-пари. `veth` (Virtual Ethernet) — це локальний Ethernet-тунель. Пристрої `veth` завжди створюються парами. Пакет, переданий (Tx) на одному кінці пари, миттєво з'являється як прийнятий (Rx) на іншому кінці пари. Це як віртуальний патч-корд.

### 3.1. Створення `veth`-пари

Команда для створення пари:
```bash
ip link add veth0 type veth peer name veth1
```
Ця команда створює два інтерфейси: `veth0` та `veth1`. Спочатку обидва вони з'являються в глобальному мережевому просторі (тому, де була виконана команда). 

### 3.2. Переміщення інтерфейсу в інший простір

Ключова особливість мережевих інтерфейсів Linux полягає в тому, що їх можна переміщувати (assign) між просторами імен. Перемістимо `veth1` до простору `red`:
```bash
ip link set veth1 netns red
```
Після виконання цієї команди `veth1` зникне з глобального простору і з'явиться в просторі `red`. `veth0` залишиться в глобальному просторі. Тепер ми маємо віртуальний кабель, один кінець якого лежить на хості, а інший — всередині ізольованої "кімнати" `red`.

### 3.3. Налаштування IP-адрес та тестування

Щоб по цьому віртуальному кабелю можна було передавати IP-пакети, обом кінцям потрібні IP-адреси з однієї підмережі.
На хості:
```bash
ip addr add 10.0.0.1/24 dev veth0
ip link set veth0 up
```
Всередині простору `red`:
```bash
ip netns exec red ip addr add 10.0.0.2/24 dev veth1
ip netns exec red ip link set veth1 up
ip netns exec red ip link set lo up
```
Тепер ми можемо пінгіти хост зсередини простору:
```bash
ip netns exec red ping 10.0.0.1
```
І навпаки, з хоста пінгіти простір:
```bash
ping 10.0.0.2
```

## 4. Складні топології: Маршрутизація та Bridges

Пряме з'єднання veth-парою добре працює для двох вузлів. Що робити, коли ми маємо багато контейнерів (просторів), і всім їм потрібен доступ до мережі та один до одного? Це саме те завдання, яке вирішує Docker (або Podman). Існує два основні підходи: маршрутизація та комутація (bridge).

### 4.1. Використання Linux Bridge (Комутатор)

Мережевий міст (Bridge) працює як віртуальний L2-світч. Замість того, щоб з'єднувати простори напряму (point-to-point), ми підключаємо їх усіх до одного віртуального свитча.

Сценарій: маємо два простори, `red` та `blue`.
1. Створюємо bridge на хості:
```bash
ip link add br0 type bridge
ip link set br0 up
```
2. Призначаємо IP-адресу на міст. Вона буде шлюзом за замовчуванням для наших контейнерів:
```bash
ip addr add 10.0.0.254/24 dev br0
```
3. Створюємо простори та veth-пари:
```bash
ip netns add red
ip netns add blue
ip link add veth-red type veth peer name veth-red-br
ip link add veth-blue type veth peer name veth-blue-br
```
4. Підключаємо "хостові" кінці veth-пар до моста (підключаємо патч-корд у порт свитча):
```bash
ip link set veth-red-br master br0
ip link set veth-blue-br master br0
ip link set veth-red-br up
ip link set veth-blue-br up
```
5. Переміщуємо інші кінці у простори та налаштовуємо:
```bash
ip link set veth-red netns red
ip netns exec red ip addr add 10.0.0.1/24 dev veth-red
ip netns exec red ip link set veth-red up
ip netns exec red ip link set lo up

ip link set veth-blue netns blue
ip netns exec blue ip addr add 10.0.0.2/24 dev veth-blue
ip netns exec blue ip link set veth-blue up
ip netns exec blue ip link set lo up
```
Тепер `red` (`10.0.0.1`) може напряму пінгувати `blue` (`10.0.0.2`), оскільки вони знаходяться в одному L2-домені (підключені до одного світча). Це класична топологія Docker-мережі типу `bridge`.

### 4.2. Налаштування маршрутизації в інтернет (NAT)

Простори мають локальні IP-адреси (10.0.0.x). Щоб вийти в інтернет (наприклад, через фізичний інтерфейс хоста `eth0`), необхідно налаштувати маршрутизацію (L3).

Спочатку вказуємо мосту як дефолтний шлюз для контейнерів:
```bash
ip netns exec red ip route add default via 10.0.0.254
ip netns exec blue ip route add default via 10.0.0.254
```
Але пакети, що дійдуть до моста, мають бути перенаправлені в інтернет.
По-перше, на хості має бути ввімкнений IP forwarding:
```bash
sysctl -w net.ipv4.ip_forward=1
```
По-друге, приватні адреси `10.0.0.x` не маршрутизуються в інтернеті. Необхідно налаштувати NAT (Source NAT, або MASQUERADE) за допомогою iptables на хості, щоб вихідний трафік маскувався під IP-адресу зовнішнього інтерфейсу хоста (`eth0`):
```bash
iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o eth0 -j MASQUERADE
```
Після цього процес із простору `red` зможе пінгувати `8.8.8.8` та звертатися до інтернет-ресурсів. Зворотні пакети демаскуватимуться ядром хоста і передаватимуться на міст `br0`, а звідти до відповідного veth-інтерфейсу і в простір `red`.

### 4.3. Маршрутизована топологія (без Bridge)

В якості альтернативи L2-мостам можна створити повністю L3-маршрутизовану мережу, де хост виступає маршрутизатором для безлічі point-to-point з'єднань (така модель активно використовується в Calico та інших CNI для Kubernetes).

Замість `br0`, ми залишаємо "хостові" кінці veth-пар у глобальному просторі і на кожен з них вішаємо окрему IP-адресу, або ж налаштовуємо маршрутизацію з вказівкою вихідного інтерфейсу:
```bash
ip link add veth0 type veth peer name veth-guest
ip link set veth-guest netns guest
# Налаштовуємо адресу в контейнері
ip netns exec guest ip addr add 10.1.1.2/32 dev veth-guest
ip netns exec guest ip link set veth-guest up
# Вказуємо специфічний маршрут на хост: "будь-яка адреса доступна через veth-guest"
ip netns exec guest ip route add 169.254.1.1 dev veth-guest
ip netns exec guest ip route add default via 169.254.1.1

# На хості інтерфейсу veth0 можна навіть не давати IP-адресу, якщо використовувати ip unnumbered, 
# але для простоти задамо хосту адресу:
ip addr add 10.1.1.1/32 dev veth0
ip link set veth0 up
# Вказуємо хосту, як знайти контейнер
ip route add 10.1.1.2 dev veth0
```
Цей підхід економить IP-адреси (немає втрат на адресу мережі, широкомовну адресу та шлюз, як у /24 підмережах) і змушує всі пакети проходити через L3-маршрутизацію хоста, що спрощує накладення фаєрволів та BGP-роутинг (як це робить Calico).

## 5. Вплив на продуктивність та Troubleshooting

Мережеві простори є вкрай легковими. Створення `struct net` займає мікросекунди і споживає кілобайти пам'яті. Однак `veth`-пари мають певні накладні витрати на продуктивність. Коли пакет проходить через veth-пару, він мусить додатково "перетнути" стек обробки ядра: пакет переходить з черги передачі (qdisc) одного інтерфейсу в чергу прийому (rx_ring) іншого. Це ініціює програмне переривання (`NET_RX_SOFTIRQ`). У високонавантажених системах (мільйони пакетів за секунду) це може стати вузьким місцем, що змушує переходити на технології типу `macvlan`, `ipvlan` або обхід ядра через `DPDK` (хоча останні суттєво ускладнюють інфраструктуру).

Для відлагодження проблем із netns найважливішим інструментом є здатність "увійти" в простір. Якщо контейнер не має мережі:
1. Використайте `ip netns exec <id> ip a`, щоб перевірити наявність інтерфейсів.
2. Перевірте таблицю маршрутів: `ip netns exec <id> ip route`.
3. Використайте `tcpdump`: ви можете запустити `ip netns exec <id> tcpdump -i veth1` всередині простору, або перехоплювати трафік на хостовому боці (на інтерфейсі `veth0` або `br0`). Другий варіант зручніший, оскільки не вимагає встановленого `tcpdump` всередині контейнера (якщо простір прив'язаний до ізольованої файлової системи).

## Висновок

Мережеві простори імен є одним із найбільш елегантних та критичних компонентів ядра Linux, що уможливили революцію контейнеризації. Надаючи повну ізоляцію L2-L4 рівнів мережевого стека при нульових витратах на віртуалізацію обладнання, `netns` дозволяють будувати складні, програмно-визначені мережі (SDN), запускати тисячі веб-сервісів на одному хості без конфліктів портів і гарантувати надійне розмежування мережевого трафіку. Розуміння принципів роботи `veth`-пар та мостів — це ключ до майстерності у сучасному DevOps та інфраструктурній інженерії.
