# Ядерне прискорення TLS (kTLS / TLS_HW / TLS_SW)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Коли мережевий трафік дедалі більше шифрується, навантаження на сервери зростає. Традиційна модель обробки Transport Layer Security (TLS) вимагає, щоб усі операції шифрування та дешифрування відбувалися у просторі користувача (userspace). Це створює вузьке місце для високопродуктивних додатків, таких як мережі доставки контенту (CDN), стримінгові платформи (Netflix, YouTube) та високошвидкісні балансувальники навантаження (NGINX, HAProxy).

Для подолання цих обмежень у ядрі Linux було реалізовано технологію **Kernel TLS (kTLS)**. kTLS дозволяє перенести симетричне шифрування та дешифрування даних безпосередньо в ядро операційної системи. Це відкриває двері для оптимізації передачі даних (наприклад, використання системного виклику `sendfile()`) та навіть повного апаратного розвантаження (Hardware Offload) на сучасні мережеві карти (SmartNIC).

У цій статті ми детально розглянемо архітектуру kTLS, його режими роботи (TLS_SW та TLS_HW), програмні інтерфейси (socket API, SOL_TLS) та синергію з `sendfile()`.

---

## 1. Проблема традиційного TLS

У класичній моделі (до появи kTLS) процес передачі зашифрованого файлу клієнту виглядає так:

1. Додаток (наприклад, вебсервер) викликає `read()` для читання блоку даних з файлу на диску в буфер користувацького простору.
2. Ядро копіює дані з дискового кешу (page cache) у буфер програми.
3. Бібліотека TLS (наприклад, OpenSSL, GnuTLS або BoringSSL) шифрує цей блок даних у користувацькому просторі.
4. Додаток викликає `write()` (або `send()`), щоб передати зашифровані дані в мережевий сокет.
5. Ядро копіює зашифровані дані з користувацького простору в буфери TCP/IP стека (socket buffers, skb).
6. Дані відправляються на мережеву карту.

### Чому це неефективно?

- **Копіювання пам'яті (Memory Copying):** Дані копіюються кілька разів між ядром і userspace.
- **Перемикання контексту (Context Switches):** Кожен виклик `read()` та `write()` вимагає переходу з користувацького режиму в режим ядра і назад.
- **Неможливість використання Zero-Copy:** Оскільки дані потрібно модифікувати (зашифрувати) у userspace, ми не можемо використовувати ефективний системний виклик `sendfile()`, який передає дані безпосередньо з файлового дескриптора в сокет без копіювання в userspace.

## 2. Що таке Kernel TLS (kTLS)?

**kTLS** — це інфраструктура в ядрі Linux (представлена в версії 4.13 для передачі і 4.17 для прийому), яка дозволяє делегувати ядру обробку TLS-записів (TLS records). 

**Важливо розуміти:** kTLS *не* замінює OpenSSL для етапу встановлення з'єднання (Handshake). Рукостискання (обмін сертифікатами, перевірка ключів, алгоритмів тощо) залишається складним асиметричним криптографічним процесом, який краще обробляти в користувацькому просторі. kTLS бере на себе лише етап **Data Plane** — симетричне шифрування та дешифрування самих даних після того, як ключі вже погоджені.

![Архітектура kTLS](/reference/unix-linux/networking/tls-ktls-kernel-offload/img/fig-tls-arch.svg)
*Рис. 1. Порівняння Userspace TLS та Kernel TLS*

Коли handshake завершено, програма (через OpenSSL) витягує симетричні ключі, IV (Initialization Vector), номери послідовностей та передає їх у ядро для конкретного TCP-сокета. Після цього сокет стає "TLS-обізнаним".

## 3. Режими роботи kTLS

kTLS може працювати у двох основних режимах розвантаження: **TLS_SW** (Software) та **TLS_HW** (Hardware).

### 3.1. TLS_SW: Програмне прискорення в ядрі

У цьому режимі шифрування (наприклад, AES-GCM) виконується центральним процесором (CPU), але всередині ядра Linux, з використанням **Linux Kernel Crypto API**.

Хоча шифрування все ще лягає на CPU, цей режим дає колосальну перевагу: **можливість використання `sendfile()`**.
Замість циклу `read()` + `encrypt()` + `write()`, вебсервер просто викликає:

```c
sendfile(socket_fd, file_fd, &offset, count);
```

Ядро бере дані з page cache, автоматично розбиває їх на TLS-записи, шифрує за допомогою Kernel Crypto API і передає в TCP-стек. Все це відбувається без жодного виходу в userspace. Це усуває зайве копіювання і значно знижує споживання CPU.

### 3.2. TLS_HW: Апаратне розвантаження (Full Offload)

Якщо мережева карта (SmartNIC, наприклад, від Mellanox/Nvidia або Chelsio) підтримує апаратне розвантаження TLS, ядро може піти ще далі. Замість шифрування на CPU, ядро передає ключі та стан TLS безпосередньо в мережеву карту.

![Апаратне прискорення](/reference/unix-linux/networking/tls-ktls-kernel-offload/img/fig-tls-hw.svg)
*Рис. 2. Апаратне прискорення TLS_HW*

У режимі **TLS_HW** (Inline TLS):
1. Додаток викликає `sendfile()`.
2. Ядро формує TCP-пакети з *незашифрованими* (plaintext) даними і відправляє їх у мережеву карту, позначаючи, що ці пакети потребують шифрування.
3. Мережева карта "на льоту" (inline) шифрує корисне навантаження TCP-пакета, генерує MAC (Message Authentication Code) і відправляє в мережу.

Це **абсолютний Zero-Copy** + **Zero-CPU Crypto**. Навантаження на центральний процесор стає таким самим, як при передачі звичайного, незашифрованого HTTP-трафіку. Це дозволяє серверам CDN віддавати десятки й сотні гігабіт зашифрованого трафіку на секунду з мінімальним використанням CPU.

## 4. Програмування kTLS (API рівня ядра та користувача)

Щоб використовувати kTLS, програміст або бібліотека повинні налаштувати сокет. Це робиться за допомогою опцій сокета `setsockopt()`.

### 4.1. Увімкнення kTLS на сокеті (SOL_TLS)

Спочатку ми повинні сказати ядру, що цей TCP-сокет буде використовувати TLS. Використовується рівень `SOL_TCP` та опція `TCP_ULP` (Upper Layer Protocol).

```c
#include <netinet/tcp.h>

int val = 1;
/* Прив'язуємо ULP 'tls' до відкритого TCP сокета */
setsockopt(sock_fd, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));
```

### 4.2. Передача ключів (TLS_TX / TLS_RX)

Після ініціалізації ULP "tls", ми використовуємо рівень `SOL_TLS` для налаштування ключів для передачі (`TLS_TX`) та/або прийому (`TLS_RX`).

Структури для передачі криптографічних параметрів визначені в `<linux/tls.h>`.
Для алгоритму AES-GCM 128 біт використовується структура `tls12_crypto_info_aes_gcm_128`:

```c
#include <linux/tls.h>

struct tls12_crypto_info_aes_gcm_128 crypto_info;
memset(&crypto_info, 0, sizeof(crypto_info));

crypto_info.info.version = TLS_1_2_VERSION; /* Або TLS_1_3_VERSION */
crypto_info.info.cipher_type = TLS_CIPHER_AES_GCM_128;

/* Копіюємо ключі, отримані від бібліотеки (наприклад, OpenSSL) */
memcpy(crypto_info.iv, init_vector, TLS_CIPHER_AES_GCM_128_IV_SIZE);
memcpy(crypto_info.key, symmetric_key, TLS_CIPHER_AES_GCM_128_KEY_SIZE);
memcpy(crypto_info.salt, salt, TLS_CIPHER_AES_GCM_128_SALT_SIZE);
memcpy(crypto_info.rec_seq, sequence_number, TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE);

/* Налаштовуємо шифрування для вихідного трафіку (TX) */
setsockopt(sock_fd, SOL_TLS, TLS_TX, &crypto_info, sizeof(crypto_info));

/* Аналогічно для вхідного трафіку (RX), якщо потрібно */
setsockopt(sock_fd, SOL_TLS, TLS_RX, &crypto_info, sizeof(crypto_info));
```

Після успішного виконання `setsockopt(TLS_TX)`, будь-які дані, записані в `sock_fd` за допомогою `write()`, `sendmsg()` або `sendfile()`, будуть автоматично загорнуті в TLS-записи і зашифровані ядром.

### 4.3. Керуючі повідомлення (Control Messages) та cmsg

У TLS дані передаються у вигляді записів (records). Записи можуть містити не лише дані (`TLS_RECORD_TYPE_DATA`), але й керуючу інформацію, наприклад, `Alert` або `Handshake` повідомлення. 

Оскільки kTLS обробляє лише симетричне шифрування, як відправити TLS Alert через kTLS сокет? Для цього використовується механізм `cmsg` (Control Messages) у системному виклику `sendmsg()`.

Програма формує `sendmsg()` з контрольним блоком `TLS_SET_RECORD_TYPE`:

```c
char buf[1];
buf[0] = 1; /* Close notify alert */

struct iovec iov = { .iov_base = buf, .iov_len = 1 };
struct msghdr msg = {0};
msg.msg_iov = &iov;
msg.msg_iovlen = 1;

char cmsgbuf[CMSG_SPACE(sizeof(unsigned char))];
msg.msg_control = cmsgbuf;
msg.msg_controllen = sizeof(cmsgbuf);

struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_TLS;
cmsg->cmsg_type = TLS_SET_RECORD_TYPE;
cmsg->cmsg_len = CMSG_LEN(sizeof(unsigned char));
*((unsigned char *)CMSG_DATA(cmsg)) = 21; /* Тип Alert */

sendmsg(sock_fd, &msg, 0);
```

Цей код змусить kTLS створити TLS-запис типу `21` (Alert), зашифрувати його поточним ключем і відправити.

## 5. Синергія: kTLS + sendfile()

Найважливіша фіча kTLS для CDN — це підтримка `sendfile()`. 
Без kTLS, щоб відправити файл по HTTPS, вебсервер NGINX робить таке:
1. `read()` з диска в userspace (тут NGINX часто використовує AIO або thread pools).
2. `SSL_write()` для шифрування.
3. `write()` зашифрованого буфера в сокет.

З kTLS, як тільки Handshake завершено, NGINX передає ключі в ядро і перемикається в режим `sendfile`:
1. `sendfile(socket, file)`.

**Внутрішня робота ядра:**
- Ядро знаходить сторінки файлу в Page Cache.
- Воно формує Scatter-Gather список (SG-list) з вказівниками на ці сторінки.
- Цей список передається до підсистеми Crypto API (для TLS_SW).
- Crypto API шифрує дані "на місці" або копіює зашифрований результат у нові сторінки ядра.
- Якщо використовується **TLS_HW** (SmartNIC), ядро просто передає SG-list вказівників на оригінальні сторінки файлу (plaintext) до драйвера NIC. Мережева карта через DMA (Direct Memory Access) зчитує ці сторінки з оперативної пам'яті і шифрує їх під час формування Ethernet-фрейму. Це справжній Zero-Copy!

Netflix використовував цей механізм для досягнення пропускної здатності **понад 200 Гбіт/с** на одному сервері (для відеостримінгу). Завдяки `sendfile()` + `kTLS_HW`, процесор майже не бере участі в пересиланні відеоданих.

## 6. Інтеграція з OpenSSL та іншими бібліотеками

Щоб використовувати kTLS, вам не обов'язково писати код із `setsockopt()` вручну. Сучасні криптографічні бібліотеки та сервери вже підтримують його.

### OpenSSL
Починаючи з версії 3.0 (і в деяких патчах до 1.1.1), OpenSSL має вбудовану підтримку kTLS. Вона активується автоматично (якщо ядро підтримує), або через конфігурацію:
```c
SSL_CTX_set_options(ctx, SSL_OP_ENABLE_KTLS);
```
Коли kTLS увімкнено, OpenSSL самостійно налаштує `TCP_ULP` і передасть ключі після успішного handshake. Наступні виклики `SSL_write()` будуть оптимізовані, а сервер (як-от NGINX) зможе перевірити стан сокета і застосувати `sendfile()`.

### NGINX
В NGINX підтримка kTLS додана у версії 1.21.4 (для Linux).
Щоб увімкнути:
1. Зберіть NGINX з підтримкою OpenSSL 3.0+.
2. У конфігураційному файлі `nginx.conf` додайте:
```nginx
sendfile on;
ssl_conf_command Options KTLS; # Або просто `ssl_protocols` + `sendfile` залежно від версії.
```
Це автоматично об'єднає ефективність `sendfile` з шифруванням TLS.

## 7. Моніторинг та Діагностика

Щоб перевірити, чи працює kTLS на вашому сервері, можна використовувати `ethtool` та статистику ядра:

**Перевірка підтримки апаратного розвантаження (TLS_HW):**
```bash
ethtool -k eth0 | grep tls
# tls-hw-tx-offload: on
# tls-hw-rx-offload: on
```

**Статистика kTLS:**
Ядро експортує метрики TLS через `/proc/net/tls_stat` або за допомогою утиліти `ss` (Socket Statistics):
```bash
# Показати TCP сокети з інформацією про TLS
ss -ti | grep -i tls
```

Статистика показує, скільки байтів було зашифровано програмно (TLS_SW) та апаратно (TLS_HW).

---

## Висновки

**Kernel TLS (kTLS)** — це критично важлива оптимізація для сучасних мережевих архітектур, орієнтованих на шифрування всього трафіку. Розділяючи складне рукостискання (userspace) і масову обробку даних (kernel space), kTLS повертає нам ефективність `sendfile()` у світі HTTPS. А завдяки режиму **TLS_HW** (SmartNIC Offload), шифрування стає майже "безкоштовним" для центрального процесора, дозволяючи будувати гіпермасштабовані відео- та CDN-сервери.
