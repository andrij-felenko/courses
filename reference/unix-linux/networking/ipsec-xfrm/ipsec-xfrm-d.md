## 1. Вступ
IPsec (Internet Protocol Security) — це набір протоколів для забезпечення захисту даних на мережевому рівні моделі OSI. На відміну від TLS, який працює на транспортному рівні (або рівні додатків) та захищає конкретні з'єднання, IPsec працює на рівні IP, шифруючи та автентифікуючи всі пакети між двома вузлами або мережами. У Linux підтримка IPsec реалізована безпосередньо в ядрі за допомогою підсистеми **XFRM** (від слова "transform"). У цій статті ми детально розглянемо архітектуру XFRM, її ключові концепції, такі як SA (Security Association) та SP (Security Policy), протоколи AH і ESP, а також навчимося керувати ними за допомогою утиліти `ip xfrm`.

## 2. Архітектура IPsec
Основою IPsec є два головні протоколи:
- **AH (Authentication Header)**: Забезпечує автентифікацію джерела даних та цілісність, захищаючи від підміни (spoofing) та атак повторного відтворення (replay). AH не шифрує дані.
- **ESP (Encapsulating Security Payload)**: Забезпечує не тільки автентифікацію і цілісність, але й конфіденційність (шифрування). ESP є найбільш поширеним протоколом у сучасних розгортаннях IPsec.

Існує два режими роботи:
- **Транспортний режим (Transport Mode)**: Захищає лише корисне навантаження (payload) IP-пакета. Використовується для з'єднань хост-хост.
- **Тунельний режим (Tunnel Mode)**: Захищає весь IP-пакет, інкапсулюючи його в новий IP-пакет. Використовується для з'єднань мережа-мережа (VPN-шлюзи) або хост-мережа.

## 3. Ядро Linux і каркас xfrm
XFRM (від слова "transform" — перетворення) — це інфраструктура ядра Linux для застосування перетворень до пакетів. Вона була впроваджена в ядрі серії 2.6 як заміна старішому проекту FreeS/WAN (і пізнішому модулю KLIPS). 

Коли пакет проходить через мережевий стек ядра Linux, він перевіряється на наявність політик безпеки (XFRM Policies). Якщо політика вказує, що пакет має бути захищений (або він був отриманий зашифрованим), пакет передається через ланцюжок перетворень XFRM.

## 4. Security Association (SA)
**Security Association (SA)** — це набір параметрів, що визначають, як саме трафік буде захищений. SA є односпрямованим: для двостороннього зв'язку потрібно щонайменше два SA (по одному в кожному напрямку).

Кожен SA унікально ідентифікується за допомогою трійки:
1. SPI (Security Parameter Index) — 32-бітне число, що передається в заголовку AH або ESP.
2. Протокол безпеки (AH або ESP).
3. IP-адреса призначення (Destination IP).

SA містить:
- Алгоритми шифрування та автентифікації.
- Ключі для цих алгоритмів.
- Режим роботи (транспортний або тунельний).
- Лічильники послідовності (Sequence Numbers) для захисту від повторного відтворення (Anti-Replay).

## 5. Security Policy (SP)
**Security Policy (SP)** визначає, до якого трафіку слід застосовувати захист. Політики зберігаються в базі даних політик безпеки (SPD — Security Policy Database).

SP містить:
- Селектори трафіку: джерело та призначення (IP-адреси, підмережі), протокол (TCP/UDP/ICMP), порти.
- Дію: `protect` (захистити за допомогою IPsec), `bypass` (пропустити без захисту), `drop` (відкинути).
- Шаблон (Template): вказівка на те, який саме SA (або ланцюжок SA) застосувати до цього трафіку.

## 6. Утиліта ip xfrm
Для керування xfrm у Linux використовується утиліта `ip xfrm` (з пакета `iproute2`).

### 6.1. Керування SA
Перегляд бази даних SA:
```bash
ip xfrm state ls
```

Додавання SA вручну:
```bash
ip xfrm state add src 192.168.1.1 dst 192.168.2.1 \
    proto esp spi 0x00001000 reqid 1 mode tunnel \
    auth sha256 0x0123456789abcdef... \
    enc aes 0x0123456789abcdef...
```

### 6.2. Керування SP
Перегляд політик:
```bash
ip xfrm policy ls
```

Додавання політики:
```bash
ip xfrm policy add src 10.0.1.0/24 dst 10.0.2.0/24 dir out \
    tmpl src 192.168.1.1 dst 192.168.2.1 proto esp reqid 1 mode tunnel
```

## 7. Практичний приклад налаштування тунелю
Розглянемо створення статичного тунелю між Site A (192.168.1.1) та Site B (192.168.2.1).

На Site A:
```bash
# Додавання SA для вихідного трафіку
ip xfrm state add src 192.168.1.1 dst 192.168.2.1 \
    proto esp spi 1001 reqid 1 mode tunnel \
    auth "hmac(sha256)" 0x... enc "cbc(aes)" 0x...

# Додавання SA для вхідного трафіку
ip xfrm state add src 192.168.2.1 dst 192.168.1.1 \
    proto esp spi 1002 reqid 2 mode tunnel \
    auth "hmac(sha256)" 0x... enc "cbc(aes)" 0x...

# Додавання політики для вихідного трафіку
ip xfrm policy add src 10.0.1.0/24 dst 10.0.2.0/24 dir out \
    tmpl src 192.168.1.1 dst 192.168.2.1 proto esp reqid 1 mode tunnel

# Додавання політики для вхідного трафіку
ip xfrm policy add src 10.0.2.0/24 dst 10.0.1.0/24 dir in \
    tmpl src 192.168.2.1 dst 192.168.1.1 proto esp reqid 2 mode tunnel
```

На Site B виконуються дзеркальні налаштування.

## 8. Висновки
Підсистема XFRM у Linux надає потужний, вбудований у ядро механізм для обробки IPsec трафіку. Розділення на SA (стан/ключі) та SP (правила/політики) дозволяє гнучко налаштовувати безпечні комунікації. Хоча ручне керування за допомогою `ip xfrm` корисне для навчання та налагодження, у продакшн середовищах зазвичай використовуються демони IKE, такі як strongSwan або LibreSwan, які автоматично встановлюють та оновлюють ключі й стани XFRM.
