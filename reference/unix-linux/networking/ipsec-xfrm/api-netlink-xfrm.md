# 📋 Інтерфейс сокетів Netlink XFRM

Підсистема XFRM у ядрі Linux використовує родинний сокет `NETLINK_XFRM` для взаємодії між простором користувача та ядра. Цей бінарний IPC-інтерфейс дозволяє зчитувати, додавати, модифікувати та видаляти об'єкти Security Association (SA) та Security Policy (SP) у базах даних SAD і SPD. Він становить основу роботи всіх сучасних демонів обміну ключами (IKEv2), таких як strongSwan та LibreSwan, а також системної утиліти `ip xfrm` з пакета `iproute2`.

## Створення сокету та формати повідомлень

Для відкриття каналу керування XFRM створюється сокет Netlink з типом протоколу `NETLINK_XFRM`. Процес повинен мати привілеї адміністратора мережі (`CAP_NET_ADMIN`), інакше виклик сокету повертає помилку доступу:

```c
int fd = socket(AF_NETLINK, SOCK_RAW, NETLINK_XFRM);
```

Спілкування через сокет Netlink є потоковим та пакетизованим. Кожен пакет даних складається з одного або кількох бінарних повідомлень, вирівняних за межею 4 байтів (`NLMSG_ALIGN`). Повідомлення починається зі стандартного заголовка `struct nlmsghdr`, за яким зберігається специфічна структура даних XFRM (наприклад, `struct xfrm_usersa_info` або `struct xfrm_userpolicy_info`), а в кінці додається послідовність змінних атрибутів Netlink у форматі Type-Length-Value (TLV) `struct rtattr`.

### Головні типи повідомлень (`nlmsg_type`)

Взаємодія керується константами типів повідомлень, визначеними у заголовку `<linux/xfrm.h>`:

| Константа `nlmsg_type` | Базова структура даних | Призначення та поведінка ядра |
| :--- | :--- | :--- |
| `XFRM_MSG_NEWSA` | `struct xfrm_usersa_info` | Створення нового або оновлення наявного запису SA у базі SAD |
| `XFRM_MSG_DELSA` | `struct xfrm_usersa_id` | Видалення конкретного запису SA за SPI, адресою призначення та протоколом |
| `XFRM_MSG_GETSA` | `struct xfrm_usersa_id` | Отримання деталей конкретного SA або дамп усієї бази SAD (`NLM_F_DUMP`) |
| `XFRM_MSG_NEWPOLICY` | `struct xfrm_userpolicy_info` | Створення нової або модифікація наявної політики безпеки у базі SPD |
| `XFRM_MSG_DELPOLICY` | `struct xfrm_userpolicy_id` | Видалення політики за селектором, напрямком та пріоритетом |
| `XFRM_MSG_GETPOLICY` | `struct xfrm_userpolicy_id` | Запит інформації про конкретну політику або запит дампа бази SPD |
| `XFRM_MSG_FLUSHSA` | `struct xfrm_usersa_flush` | Очищення всієї бази станів SAD (або станів для конкретного протоколу) |
| `XFRM_MSG_FLUSHPOLICY` | (порожній або `__u8 proto`) | Очищення всієї бази політик SPD у поточному мережевому просторі імен |
| `XFRM_MSG_NEWAE` | `struct xfrm_aevent_id` | Оновлення лічильників Anti-Replay та надсилання асинхронних сповіщень про події |
| `XFRM_MSG_MIGRATE` | `struct xfrm_user_migrate` | Динамічна міграція IP-адрес тунелю без розриву поточних з'єднань (MOBIKE) |
| `XFRM_MSG_POLEVENT` | `struct xfrm_userpolicy_info` | Асинхронне повідомлення ядра про закінчення терміну дії або зміну політики |

## Детальний розбір структур даних ядра (`<linux/xfrm.h>`)

### 1. Структура стану `struct xfrm_usersa_info`

Структура `struct xfrm_usersa_info` передається як основний шар даних у повідомленнях `XFRM_MSG_NEWSA` та повертається ядром при запитах `XFRM_MSG_GETSA`. Вона містить усі параметри, необхідні для шифрування та автентифікації трафіку:

```c
struct xfrm_usersa_info {
    struct xfrm_selector sel;           /* Селектор трафіку для прив'язки SA */
    struct xfrm_id       id;            /* Ідентифікатор SA: daddr, spi, proto */
    xfrm_address_t       saddr;         /* IP-адреса джерела тунелю */
    struct xfrm_lifetime_cfg lft;       /* Межі часу життя (байтів, пакетів, секунд) */
    struct xfrm_lifetime_cur curlft;    /* Поточна статистика використання */
    __u64                stats_packets; /* Лічильник успішно оброблених пакетів */
    __u64                stats_bytes;   /* Лічильник успішно оброблених байтів */
    __u32                seq;           /* Поточний серійний номер пакета */
    __u32                reqid;         /* Ідентифікатор запиту (зв'язок із політикам SPD) */
    __u16                family;        /* Родина адрес: AF_INET (IPv4) або AF_INET6 (IPv6) */
    __u8                 mode;          /* Режим: XFRM_MODE_TRANSPORT або XFRM_MODE_TUNNEL */
    __u8                 replay_window; /* Розмір вікна захисту від повторів (Anti-Replay) */
    __u8                 flags;         /* Бітові прапорці конфігурації стану */
};
```

Деталізація внутрішніх полів `struct xfrm_usersa_info`:
- **Поле `id` (`struct xfrm_id`)**: Потрійний ключ ідентифікації SA в ядрі. Містить `daddr` (IP-адресу призначення), `spi` (Security Parameter Index у мережевому порядку байтів big-endian) та `proto` (`IPPROTO_ESP` = 50 або `IPPROTO_AH` = 51).
- **Поле `saddr` (`xfrm_address_t`)**: IP-адреса джерела тунелю. Вміщує 32-бітну адресу IPv4 або 128-бітну структуру IPv6.
- **Поле `reqid` (`__u32`)**: Числовий ідентифікатор, який пов'язує конкретну політику SPD із відповідним станом SAD. Якщо демон IKE створює декілька SA для одного тунелю, `reqid` гарантує, що політика застосує саме призначений стан.
- **Поле `mode` (`__u8`)**: Визначає режим обробки IP-кадрів:
  - `XFRM_MODE_TRANSPORT` (0): Транспортний режим (шифрується лише payload).
  - `XFRM_MODE_TUNNEL` (1): Тунельний режим (пакет зашифровується повністю й інкапсулюється в новий зовнішній IP-заголовок).
  - `XFRM_MODE_BEET` (4): Режим Bound End-to-End Tunnel (гібридний режим для підтримки мобільності).
- **Поле `flags` (`__u8`)**: Бітові маски керування поведінкою стану:
  - `XFRM_STATE_NOECN` (1): Вимкнути перенос сигналів ECN (*Explicit Congestion Notification*) між внутрішнім та зовнішнім IP-заголовками.
  - `XFRM_STATE_DECAP_DSCP` (2): Копіювати байт DSCP з внутрішнього IP-заголовка у зовнішній при інкапсуляції.
  - `XFRM_STATE_NOPMTUDISC` (4): Ігнорувати Path MTU Discovery для цього SA.
  - `XFRM_STATE_WILDRECV` (8): Дозволити прийом вхідних пакетів із довільною адресою джерела (для мобільних клієнтів).

### 2. Структура політики `struct xfrm_userpolicy_info`

Структура `struct xfrm_userpolicy_info` визначає правило фільтрації та дії у базі SPD:

```c
struct xfrm_userpolicy_info {
    struct xfrm_selector sel;        /* Селектор трафіку (IP, порти, протокол) */
    struct xfrm_lifetime_cfg lft;    /* Обмеження часу життя політики */
    struct xfrm_lifetime_cur curlft; /* Поточний стан використання політики */
    __u32                priority;   /* Пріоритет (менше значення = вища перевага) */
    __u32                index;      /* Унікальний системний індекс політики */
    __u8                 dir;        /* Напрямок: XFRM_POLICY_IN, OUT, FWD */
    __u8                 action;     /* Дія: XFRM_POLICY_ALLOW або XFRM_POLICY_BLOCK */
    __u8                 flags;      /* Додаткові прапорці політики */
    __u8                 share;      /* Рівень спільного використання (XFRM_SHARE_ANY) */
};
```

Значення напрямку `dir`:
- `XFRM_POLICY_IN` (0): Вхідний трафік. Перевіряє, щоб вхідні зашифровані пакети після дешифрації відповідали дозволеним селекторам.
- `XFRM_POLICY_OUT` (1): Вихідний трафік. Застосовує XFRM-перетворення до пакетів, що генеруються локальними сокетами.
- `XFRM_POLICY_FWD` (2): Транзитний трафік. Застосовується до пакетів, які маршрутизуються крізь хост між різними мережевими інтерфейсами.

Значення дії `action`:
- `XFRM_POLICY_ALLOW` (0): Захистити трафік за допомогою IPsec або пропустити, якщо шаблони відсутні.
- `XFRM_POLICY_BLOCK` (1): Мовчки відкинути пакет (*drop*).

### 3. Селектор трафіку `struct xfrm_selector`

Визначає точні межі трафіку, до якого застосовується SA або SP:

```c
struct xfrm_selector {
    xfrm_address_t daddr;       /* IP-адреса призначення */
    xfrm_address_t saddr;       /* IP-адреса джерела */
    __be16         dport;       /* Порт призначення у network byte order */
    __be16         dport_mask;  /* Бітова маска порту призначення */
    __be16         sport;       /* Порт джерела у network byte order */
    __be16         sport_mask;  /* Бітова маска порту джерела */
    __u16          family;      /* AF_INET / AF_INET6 */
    __u8           prefixlen_d; /* Довжина маски призначення (CIDR, наприклад 24) */
    __u8           prefixlen_s; /* Довжина маски джерела (CIDR, наприклад 24) */
    __u8           proto;       /* Протокол транспортного рівня (IPPROTO_TCP, UDP, ICMP або 0) */
    int            ifindex;     /* Індекс причіпленого мережевого інтерфейсу */
    __kernel_uid32_t user;      /* UID процесу-власника сокету */
};
```

### 4. Час життя та ліміти `struct xfrm_lifetime_cfg`

Структура `struct xfrm_lifetime_cfg` дозволяє встановити жорсткі (*hard*) та м'які (*soft*) ліміти використання ключів:

```c
struct xfrm_lifetime_cfg {
    __u64 soft_byte_limit;   /* М'який ліміт оброблених байтів */
    __u64 hard_byte_limit;   /* Жорсткий ліміт оброблених байтів */
    __u64 soft_packet_limit; /* М'який ліміт оброблених пакетів */
    __u64 hard_packet_limit; /* Жорсткий ліміт оброблених пакетів */
    __u64 soft_add_expires_seconds;  /* М'який ліміт часу від моменту створення */
    __u64 hard_add_expires_seconds;  /* Жорсткий ліміт часу від моменту створення */
    __u64 soft_use_expires_seconds;  /* М'який ліміт часу від першого використання */
    __u64 hard_use_expires_seconds;  /* Жорсткий ліміт часу від першого використання */
};
```

Коли досягається **м'який ліміт** (*soft limit*), ядро не перериває шифрування трафіку, але генерує асинхронне Netlink-повідомлення `XFRM_MSG_POLEVENT` або `XFRM_MSG_NEWAE` до демона IKE. Це дає демону час узгодити нові ключі у фоновому режимі без втрати жодного пакета. Якщо ж досягається **жорсткий ліміт** (*hard limit*), ядро негайно знищує запис SA/SP, і весь наступний трафік блокується до встановлення нових ключів.

## Атрибути Netlink (`struct rtattr`) та криптографічні конфігурації

Після основної структури у повідомленні Netlink додаються вкладені атрибути `struct rtattr`. Кожен атрибут складається з заголовка `rta_type` (2 байти) та `rta_len` (2 байти), за якими розміщуються самі бінарні дані:

```c
struct rtattr {
    unsigned short rta_len;  /* Загальна довжина атрибута (заголовок + вміст) */
    unsigned short rta_type; /* Тип атрибута (XFRMA_*) */
};
```

### Реєстр типів атрибутів XFRM (`XFRMA_*`)

| Тип атрибута `rta_type` | Структура даних вмісту | Докладний опис |
| :--- | :--- | :--- |
| `XFRMA_ALG_CRYPT` | `struct xfrm_algo` | Назва алгоритму блочного шифрування (наприклад, `"cbc(aes)"`) та симетричний ключ |
| `XFRMA_ALG_AUTH` | `struct xfrm_algo` | Назва алгоритму цілісності (наприклад, `"hmac(sha256)"`) та ключ аутентифікації |
| `XFRMA_ALG_AUTH_TRUNC` | `struct xfrm_algo_auth` | Назва, ключ та усічена довжина дайджесту в бітах для HMAC |
| `XFRMA_ALG_AEAD` | `struct xfrm_algo_aead` | Суміщений алгоритм автентифікованого шифрування (наприклад, `"gcm(aes)"`) та ключ + tag len |
| `XFRMA_TMPL` | `struct xfrm_user_tmpl[]` | Масив шаблонів SA, що прив'язуються до політики в `XFRM_MSG_NEWPOLICY` |
| `XFRMA_ENCAP` | `struct xfrm_encap_tmpl` | Конфігурація UDP-інкапсуляції для проходження крізь NAT (NAT-Traversal, порт 4500) |
| `XFRMA_REPLAY_VAL` | `struct xfrm_replay_state` | Стан лічильника послідовності та бітова маска вікна Anti-Replay |
| `XFRMA_REPLAY_ESN_VAL` | `struct xfrm_replay_state_esn` | Розширений лічильник послідовності ESN (64-бітні Sequence Numbers) |
| `XFRMA_MARK` | `struct xfrm_mark` | Маркер пакета (`value`, `mask`) для інваріантного зв'язку з `iptables`/`nftables` |
| `XFRMA_IF_ID` | `__u32` | Унікальний ідентифікатор XFRM-інтерфейсу (`if_id` для пристроїв `xfrm0`) |

### 1. Атрибути шифрування та автентифікації

Структура `struct xfrm_algo` передає назви алгоритмів у форматі, який сприймається ядерною підсистемою Crypto API:

```c
struct xfrm_algo {
    char  alg_name[64]; /* Строкова назва в Crypto API (наприклад "cbc(aes)") */
    __u32 alg_key_len;  /* Довжина ключа у БІТАХ (наприклад 128, 192, 256) */
    char  alg_key[0];   /* Гнучкий масив байтів ключа */
};
```

Для суміщеного режиму AEAD (наприклад, AES-GCM) використовується структура `struct xfrm_algo_aead`:

```c
struct xfrm_algo_aead {
    char  alg_name[64];    /* Назва алгоритму (наприклад "gcm(aes)") */
    __u32 alg_key_len;     /* Довжина ключа шифрування у БІТАХ */
    __u32 alg_icv_len;     /* Довжина тегу цілісності ICV у БІТАХ (наприклад 128) */
    char  alg_key[0];      /* Ключ шифрування + соль (salt) */
};
```

### 2. Шаблони політик `struct xfrm_user_tmpl`

Під час додавання політики `XFRM_MSG_NEWPOLICY` до атрибута `XFRMA_TMPL` додається масив шаблонів `struct xfrm_user_tmpl`. Шаблон вказує ядра, які саме стані SA мають бути знайдені у SAD під час обробки трафіку:

```c
struct xfrm_user_tmpl {
    struct xfrm_id id;        /* Dst IP, SPI та протокол (IPPROTO_ESP/AH) */
    __u16          family;    /* AF_INET / AF_INET6 */
    xfrm_address_t saddr;     /* IP-адреса джерела тунелю */
    __u32          reqid;     /* reqid для зв'язування з SA */
    __u8           mode;      /* XFRM_MODE_TRANSPORT або XFRM_MODE_TUNNEL */
    __u8           share;     /* Спосіб поділу (XFRM_SHARE_ANY) */
    __u8           optional;  /* 0 = суворе використання IPsec, 1 = необов'язкове */
    __u32          aalgos;    /* Бітова маска дозволених алгоритмів аутентифікації */
    __u32          ealgos;    /* Бітова маска дозволених шифрів */
    __u32          calgos;    /* Бітова маска алгоритмів компресії */
};
```

### 3. UDP-інкапсуляція для обходу NAT (`XFRMA_ENCAP`)

Якщо між двома IPsec-шлюзами міститься маршрутизатор із NAT, стандартні ESP-пакети (IPproto 50) блокуються, оскільки NAT не може модифікувати порти у заголовку ESP (порти відсутні). Для обходу цієї проблеми трафік інкапсулюється у звичайні UDP-пакети на порт 4500 (RFC 3948). 

Параметри інкапсуляції передаються ядру атрибутом `XFRMA_ENCAP`:

```c
struct xfrm_encap_tmpl {
    __u16 encap_type; /* Тип: UDP_ENCAP_ESPINUDP (1) або UDP_ENCAP_ESPINUDP_NON_IKE (2) */
    __be16 encap_sport; /* Порт джерела UDP (зазвичай 4500) */
    __be16 encap_dport; /* Порт призначення UDP (зазвичай 4500) */
    xfrm_address_t encap_oa; /* Оригінальна адреса за NAT */
};
```

## Обробка відповідей та коди помилок Netlink

Після надсилання бінарного повідомлення до сокету `NETLINK_XFRM` ядро повертає підтвердження у вигляді повідомлення `NLMSG_ERROR`. Якщо в заголовку `nlmsghdr` встановлено прапорець `NLM_F_ACK`, ядро обов'язково надішле відповідь.

Структура вмісту відповіді `NLMSG_ERROR`:

```c
struct nlmsgerr {
    int error;                /* Від'ємний код помилки POSIX (0 = успіх) */
    struct nlmsghdr msg;      /* Копія заголовка вихідного запиту */
};
```

### Поширені коди помилок ядра XFRM

- **`0`**: Запит успішно виконано (SA або SP створено/модифіковано/видалено).
- **`-EEXIST` (-17)**: Спроба додати SA або SP, яка вже існує у базі даних SAD або SPD з тотожним SPI, селектором або пріоритетом.
- **`-ENOENT` (-2)**: Запит на видалення або отримання інформації про стан чи політику, які відсутні у базах ядра.
- **`-EINVAL` (-22)**: Некоректні параметри запиту. Найчастіші причини:
  - Довжина ключа не відповідає вимогам обраного криптографічного алгоритму.
  - Назва алгоритму в `alg_name` відсутня у реєстрі Crypto API ядра (не завантажено відповідний модуль ядра).
  - Некоректна довжина префікса CIDR або непідтримуваний режим `mode`.
- **`-ENOMEM` (-12)**: Нестача оперативної пам'яті ядра для виділення внутрішніх структур `struct xfrm_state` або `struct xfrm_policy`.
- **`-EAFNOSUPPORT` (-97)**: Родина адрес (`AF_INET6`) не підтримується ядром або вимкнена у налаштуваннях sysctl.
- **`-EPERM` (-1)** / **`-EACCES` (-13)**: Процес не має необхідних привілеїв `CAP_NET_ADMIN` для керування мережевим стеком ядра.
