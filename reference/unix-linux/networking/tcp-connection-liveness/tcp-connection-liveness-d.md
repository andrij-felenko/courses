# Виявлення мертвого TCP-з'єднання: keepalive, TCP_USER_TIMEOUT і прикладна перевірка

- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Під час розробки мережевих застосунків на базі TCP/IP однією з найпоширеніших і найскладніших проблем є виявлення втрати з'єднання. Оскільки протокол TCP розроблений таким чином, щоб бути стійким до тимчасових перебоїв у мережі, він за замовчуванням може підтримувати сесію в стані "встановлено" (ESTABLISHED) нескінченно довго, навіть якщо інша сторона раптово зникла через збій живлення або фізичний обрив кабелю (так звані "напіввідкриті" або "мертві" з'єднання). 

У цій статті ми детально розглянемо механізми, які дозволяють операційним системам сімейства Unix/Linux та самим прикладним програмам виявляти мертві з'єднання, своєчасно звільняти ресурси та швидко реагувати на збої в мережі.

## 1. Проблема мертвих з'єднань

TCP — це протокол з встановленням з'єднання та підтвердженням доставки (ACK). Коли відправляються дані, TCP очікує підтвердження. Якщо воно не приходить, TCP повторює відправку даних з експоненційним збільшенням затримки між спробами. Цей процес регулюється параметрами ОС (наприклад, `tcp_retries2` у Linux). 

Проте що відбувається, коли з'єднання "простоює" — тобто жодна зі сторін не надсилає жодних даних? У цьому випадку на рівні TCP не передаються жодні пакети. Якщо в цей час маршрутизатор між клієнтом і сервером вийде з ладу, або кабель буде перерізано, жодна зі сторін про це не дізнається. Обидві сторони будуть вважати, що з'єднання все ще живе. Це призводить до витоку ресурсів (файлових дескрипторів, пам'яті), оскільки сервер може тримати тисячі таких мертвих з'єднань.

## 2. Механізм TCP Keepalive

Для вирішення цієї проблеми у протокол TCP було додано механізм Keepalive. Його суть полягає в періодичному надсиланні спеціальних зондувальних пакетів (keepalive probes).

### Як увімкнути TCP Keepalive

Щоб операційна система почала надсилати keepalive-пакети, застосунок повинен явно ввімкнути цю опцію для конкретного сокета за допомогою `setsockopt` з параметром `SO_KEEPALIVE`.

```c
int optval = 1;
setsockopt(sockfd, SOL_SOCKET, SO_KEEPALIVE, &optval, sizeof(optval));
```

### Налаштування параметрів Keepalive в Linux

У Linux механізм Keepalive керується трьома основними параметрами, які можна налаштувати глобально для всієї системи або для конкретного сокета:

1.  **`TCP_KEEPIDLE`** (в секундах) — час простою з'єднання, після якого ОС почне надсилати keepalive-зонди.
2.  **`TCP_KEEPINTVL`** (в секундах) — інтервал між надсиланням повторних зондів, якщо на попередній не було отримано відповіді.
3.  **`TCP_KEEPCNT`** (кількість) — максимальна кількість зондів без відповіді, після якої з'єднання буде вважатися розірваним (відбудеться скидання, клієнт отримає `ETIMEDOUT` або `ECONNRESET`).

Ці параметри можна налаштувати на рівні конкретного сокета:

```c
int keepidle = 60; // Почати перевірку через 60 секунд простою
int keepintvl = 10; // Повторювати зондування кожні 10 секунд
int keepcnt = 5; // Зробити 5 спроб

setsockopt(sockfd, IPPROTO_TCP, TCP_KEEPIDLE, &keepidle, sizeof(keepidle));
setsockopt(sockfd, IPPROTO_TCP, TCP_KEEPINTVL, &keepintvl, sizeof(keepintvl));
setsockopt(sockfd, IPPROTO_TCP, TCP_KEEPCNT, &keepcnt, sizeof(keepcnt));
```

У даному прикладі виявлення мертвого з'єднання займе: `60 + (10 * 5) = 110` секунд.

## 3. TCP_USER_TIMEOUT

Починаючи з ядра Linux 2.6.37, було додано нову, надзвичайно корисну опцію для сокетів — `TCP_USER_TIMEOUT`. Її значення вказується в мілісекундах.

Ця опція встановлює максимальний час, протягом якого дані, що не були підтверджені (неотримані ACK), можуть залишатися в буфері передачі до того, як TCP примусово закриє з'єднання і поверне помилку застосунку. Вона також впливає на те, скільки часу TCP чекатиме відповіді на keepalive-зонди.

```c
unsigned int timeout = 10000; // 10 секунд
setsockopt(sockfd, IPPROTO_TCP, TCP_USER_TIMEOUT, &timeout, sizeof(timeout));
```

### Взаємодія TCP_USER_TIMEOUT з Keepalive

Особливість `TCP_USER_TIMEOUT` полягає в тому, що цей таймаут діє як жорстке обмеження часу на будь-які операції, що вимагають очікування від мережі. Якщо ви використовуєте і keepalive, і `TCP_USER_TIMEOUT`, з'єднання буде розірвано, коли час з моменту останнього підтвердження перевищить `TCP_USER_TIMEOUT`, незалежно від того, скільки ще keepalive-зондів залишилося надіслати. Це дає розробнику точний контроль над часом виявлення збою.

## 4. Прикладна перевірка (Application-level Heartbeats / Ping-Pong)

Хоча TCP Keepalive є зручним інструментом, він має певні обмеження:
- Він перевіряє життєздатність лише на рівні ОС і мережевого стеку. Серверна програма може зависнути (deadlock), але ядро операційної системи все одно відповідатиме на keepalive-зонди.
- Пакети TCP Keepalive можуть фільтруватися проміжними брандмауерами або NAT-маршрутизаторами.

Через це в критичних системах застосовується прикладна перевірка життєздатності з'єднання — так звані "heartbeats" (серцебиття) або протокол "ping-pong".

### Принцип роботи Ping-Pong

1.  **Таймер простою**: Одна або обидві сторони підтримують таймер, який скидається під час отримання будь-якого повідомлення.
2.  **Надсилання Ping**: Якщо повідомлень не було протягом певного часу (наприклад, 15 секунд), сторона надсилає спеціальне прикладне повідомлення (Ping).
3.  **Очікування Pong**: Сторона, що отримала Ping, повинна негайно відповісти повідомленням Pong.
4.  **Розірвання**: Якщо після надсилання Ping відповідь Pong не надходить протягом встановленого тайм-ауту, застосунок вважає з'єднання мертвим, самостійно закриває сокет і починає процедуру перепідключення.

### Переваги прикладного Heartbeat

- **Перевірка всього стеку**: Heartbeat обробляється самою програмою. Якщо програма зависла в нескінченному циклі або заблокувалася на м'ютексі, вона не відповість на Ping. Таким чином, ви виявляєте не лише обрив мережі, але й зависання застосунку на іншій стороні.
- **Контроль формату і логіки**: Ви можете передавати в повідомленнях Ping додаткову діагностичну інформацію (наприклад, поточне навантаження на сервер).

## Висновки

Виявлення мертвих TCP-з'єднань — це багаторівневий процес. 

- Для базового контролю ресурсів сервера та виявлення від'єднаних клієнтів (коли сервер переважно слухає) підходить **TCP Keepalive**.
- Коли вам потрібен жорсткий, передбачуваний тайм-аут на надсилання даних (особливо при використанні неблокуючих сокетів або систем високої доступності), найкращим вибором у Linux є використання опції **`TCP_USER_TIMEOUT`**.
- Для гарантії життєздатності не лише мережевого каналу, але й логіки самого застосунку на іншому кінці з'єднання, необхідно реалізовувати **прикладні heartbeats**.

Найбільш надійні розподілені системи часто комбінують ці підходи, використовуючи прикладний heartbeat для миттєвого виявлення збоїв між вузлами та TCP Keepalive як запасний механізм для очищення ресурсів від клієнтів-привидів.
