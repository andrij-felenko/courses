# 📋 Специфікація виразів, регістрів та Netlink-інтерфейсу nftables

Ця довідкова вставка містить детальний специфікований опис бінарних структур даних ядра Linux, констант переліків (enums), типів виразів, механізмів обробки вердиктів та атрибутів бінарного протоколу Netlink, які утворюють публічний та внутрішньоядерний інтерфейс підсистеми `nftables`.

## 1. Архітектура регістрової пам'яті та керування вердиктами

Віртуальна машина `nftables` використовує масив регістрів пам'яті, що виділяється безпосередньо на стеку ядра під час виконання головної функції обробки правил `nft_do_chain()`. Використання фіксованого регістрового масиву замість динамічного стек-поінтера дозволяє досягти нульових накладних витрат на виділення пам'яті у викликах нових функцій та забезпечує прямий індексований доступ до обчислених даних за допомогою фіксованих зсувів у масиві.

```c
struct nft_regs {
	union {
		u32		data[20];
		struct nft_verdict	verdict;
	};
};
```

Регістрова пам'ять представлена об'єднанням `union`, в якому перші 32 біти (елемент `data[0]`) відведено під структуру вердикту `struct nft_verdict`, а наступні елементи використовуються як робочі операнди обчислень.

### 1.1. Перелік регістрів та адресація (enum nft_registers)

Заголовочний файл `include/uapi/linux/netfilter/nf_tables.h` визначає публічну адресувальну схему регістрів віртуальної машини, що використовується при серіалізації правил у простір користувача:

```c
enum nft_registers {
	NFT_REG_VERDICT		= 0,
	NFT_REG_1		= 1,
	NFT_REG_2		= 2,
	NFT_REG_3		= 3,
	NFT_REG_4		= 4,
	__NFT_REG_MAX,

	/* 32-бітні регістри (впроваджені у ядрі 4.9) */
	NFT_REG32_00		= 8,
	NFT_REG32_01		= 9,
	NFT_REG32_02		= 10,
	NFT_REG32_03		= 11,
	NFT_REG32_04		= 12,
	NFT_REG32_05		= 13,
	NFT_REG32_06		= 14,
	NFT_REG32_07		= 15,
	NFT_REG32_08		= 16,
	NFT_REG32_09		= 17,
	NFT_REG32_10		= 18,
	NFT_REG32_11		= 19,
	NFT_REG32_12		= 20,
	NFT_REG32_13		= 21,
	NFT_REG32_14		= 22,
	NFT_REG32_15		= 23,
};
```

Детальний функціональний розподіл регістрів пам'яті виглядає наступним чином:

Перший регістр із номером 0 (`NFT_REG_VERDICT`) є зарезервованим під керування потоком виконання правил і збереження підсумкового вердикту обробки пакета. Будь-який вираз у ланцюжку може прочитати стан цього регістра або записати у нього новий код дії.

Історичні регістри від 1 до 4 (`NFT_REG_1` .. `NFT_REG_4`) були розраховані на 128-бітні блоки даних у найперших версіях підсистеми `nftables`. Вони збережені у специфікації інтерфейсу ABI для забезпечення повної сумісності зі старими версіями утиліти `nft` та зовнішніх бібліотек.

Сучасні 32-бітні регістри (`NFT_REG32_00` .. `NFT_REG32_15`) надають 16 окремих операндів. Для збереження простих полів (8-бітний протокол L4, 16-бітний порт TCP або UDP) використовується один регістр. Якщо ж необхідно оперувати 128-бітними значеннями (наприклад, IPv6-адресами чи бітовими мітками conntrack), чотири послідовні 32-бітні регістри об'єднуються у єдиний неперервний блок пам'яті (наприклад, від `NFT_REG32_00` до `NFT_REG32_03`).

### 1.2. Коди вердиктів та керування потоком (struct nft_verdict)

Структура `struct nft_verdict` зберігає результат обробки правила та параметри керування виконанням користувацьких ланцюжків:

```c
struct nft_verdict {
	u32			code;
	struct nft_chain	*chain;
};
```

Поле `code` містить числовий ідентифікатор вердикту, а поле `chain` використовується як вказівник на цільовий ланцюжок при виконанні інструкцій переходу `JUMP` або `GOTO`.

Повний перелік системних кодових значень `code`:

Вердикт `NFT_CONTINUE` (числове значення `-1`) вказує віртуальній машині, що умова поточного виразу успішно виконана, і необхідно перейти до виконання наступного виразу всередині того самого правила.

Вердикт `NFT_BREAK` (числове значення `-2`) сигналізує про те, що умова виразу не виконалася (наприклад, порт пакета не дорівнює вказаному у правилі). Отримавши `NFT_BREAK`, ВМ негайно припиняє обробку поточного правила, скидає вердикт у стан `NFT_CONTINUE` і переходить до першого виразу наступного правила у ланцюжку.

Вердикт `NFT_JUMP` (числове значення `-3`) здійснює перехід до виконання вказаного користувацького ланцюжка (`verdict.chain`). При цьому адреса поточного ланцюжка та правила зберігається у стеку викликів для подальшого повернення.

Вердикт `NFT_GOTO` (числове значення `-4`) здійснює безумовний перехід до вказаного ланцюжка без збереження адреси повернення.

Вердикт `NFT_RETURN` (числове значення `-5`) здійснює повернення з викликаного ланцюжка до батьківського ланцюжка, продовжуючи виконання з наступного правила після виклику `JUMP`.

Вердикт `NF_ACCEPT` (числове значення `0`) є кінцевою дією Netfilter. Він наказує ядру прийняти пакет і передати його наступним підсистемам мережевого стеку Linux.

Вердикт `NF_DROP` (числове значення `1`) є кінцевою дією Netfilter. Він наказує ядру мовчки відкинути пакет і негайно звільнити пов'язану з ним оперативну пам'ять буфера `sk_buff`.

Вердикт `NF_STOLEN` (числове значення `2`) вказує, що пакет було захоплено стороннім модулем ядра (наприклад, підсистемою IPsec чи розширенними шифрувальними обробниками), тому Netfilter повинен припинити його подальшу обробку.

Вердикт `NF_QUEUE` (числове значення `3`) передає пакет у простір користувача через підсистему `nfnetlink_queue` для виконання поглибленого аналізу вмісту (DPI) у зовнішніх додатках.

## 2. Ядерні структури даних (net/netfilter/nf_tables.h)

### 2.1. Опис виразу (struct nft_expr та struct nft_expr_ops)

Внутрішньоядерне представлення кожного виразу визначається структурою `struct nft_expr`:

```c
struct nft_expr {
	const struct nft_expr_ops	*ops;
	unsigned char			data[] __attribute__((aligned(__alignof__(u64))));
};
```

Поле `ops` містить вказівник на таблицю методів обробки, а масив `data[]` виділяється динамічно під приватні параметри виразу (наприклад, зсув заголовка, маску або значення порівняння) з обов'язковим вирівнюванням по 8-байтовій межі (`aligned(__alignof__(u64))`).

Властивості та логіка виконання виразу задаються через таблицю вказівників на функції `struct nft_expr_ops`:

```c
struct nft_expr_ops {
	void				(*eval)(const struct nft_expr *expr,
						struct nft_regs *regs,
						const struct nft_pktinfo *pkt);
	int				(*size);
	int				(*init)(const struct nft_ctx *ctx,
						const struct nft_expr *expr,
						const struct nlattr * const tb[]);
	void				(*activate)(const struct nft_ctx *ctx,
						   const struct nft_expr *expr);
	void				(*deactivate)(const struct nft_ctx *ctx,
						     const struct nft_expr *expr,
						     enum nft_trans_phase phase);
	void				(*destroy)(const struct nft_ctx *ctx,
						  const struct nft_expr *expr);
	int				(*dump)(struct sk_buff *skb,
						const struct nft_expr *expr,
						bool reset);
	int				(*validate)(const struct nft_ctx *ctx,
						   const struct nft_expr *expr,
						   const struct nft_data **data);
	const struct nft_expr_type	*type;
};
```

Покроковий аналіз ключових функціональних методів:

Метод `eval` є головною функцією виконання обчислень. Він викликається для кожного пакета, що проходить крізь дане правило. Функція приймає вказівник на екземпляр виразу `expr`, масив регістрів `regs` та метадані пакета `pkt`.

Метод `init` виконує розбір та валідацію бінарних атрибутів Netlink під час створення правила у просторі користувача. Він перевіряє межі пам'яті, валідує типи операндів та ініціалізує приватний блок `data`.

Метод `destroy` викликається при видаленні правила з пам'яті ядра. Він відповідає за звільнення динамічних ресурсів (наприклад, зменшення лічильників посилань на пов'язані набори або карти).

Метод `dump` серіалізує поточний внутрішній стан виразу назад у бінарний формат Netlink. Це необхідно для відображення правил користувачеві при виконанні команди `nft list ruleset`.

### 2.2. Контекст та метадані пакета (struct nft_pktinfo)

Для уникнення повторного розбору мережевих заголовків пакета на кожному виразі ядро передає у функцію `eval()` структуру `struct nft_pktinfo`:

```c
struct nft_pktinfo {
	struct sk_buff			*skb;
	const struct nf_hook_state	*state;
	u8				thoff;    /* Зсув транспортного заголовка L4 від початку пакета */
	u8				tprot;    /* Протокол L4 (IPPROTO_TCP, IPPROTO_UDP тощо) */
	bool				tprot_set;
};
```

Поле `skb` містить вказівник на бінарний буфер пакета Linux. Поле `state` вказує на стан хука Netfilter (включаючи мережевий простір імен `net`, вхідний та вихідний пристрої). Поле `thoff` вказує на точне зміщення заголовка транспортного рівня в байтах, що дозволяє виразам `nft_payload` миттєво зчитувати номери портів TCP/UDP без додаткових обчислень.

## 3. Специфікація основних типів виразів (Core Expressions Specification)

### 3.1. nft_payload (Зчитування даних із заголовків)

Вираз `nft_payload` копіює N байтів з L2 (Link), L3 (Network) або L4 (Transport) заголовків у вказаний регістр призначення.

Бінарні Netlink-атрибути (`enum nft_payload_attributes`):
- `NFTA_PAYLOAD_BASE`: Базовий заголовок (`NFT_PAYLOAD_LL_HEADER`, `NFT_PAYLOAD_NETWORK_HEADER`, `NFT_PAYLOAD_TRANSPORT_HEADER`).
- `NFTA_PAYLOAD_OFFSET`: Зсув від початку базового заголовка в байтах (u32).
- `NFTA_PAYLOAD_LEN`: Довжина даних для зчитування в байтах (u32).
- `NFTA_PAYLOAD_DREG`: Цільовий регістр призначення (`enum nft_registers`).

### 3.2. nft_cmp (Операції порівняння)

Вираз `nft_cmp` здійснює логічне порівняння вмісту вихідного регістра `sreg` з еталонною константою. Якщо умова порівняння хибна, вираз записує `NFT_BREAK` у регістр вердикту.

Бінарні Netlink-атрибути (`enum nft_cmp_attributes`):
- `NFTA_CMP_SREG`: Вихідний регістр для зчитування значення.
- `NFTA_CMP_OP`: Операція порівняння (`enum nft_cmp_ops`):
  - `NFT_CMP_EQ` — дорівнює (`==`);
  - `NFT_CMP_NEQ` — не дорівнює (`!=`);
  - `NFT_CMP_LT` — менше (`<`);
  - `NFT_CMP_LTE` — менше або дорівнює (`<=`);
  - `NFT_CMP_GT` — більше (`>`);
  - `NFT_CMP_GTE` — більше або дорівнює (`>=`).
- `NFTA_CMP_DATA`: Вкладений атрибут Netlink (`NFTA_DATA_VALUE`), що містить еталонні байти для порівняння.

### 3.3. nft_bitwise (Побітові маски та трансформації)

Вираз `nft_bitwise` виконує маскування та побітові зсуви за формулою: `dreg = (sreg & mask) ^ xor`.

Бінарні Netlink-атрибути (`enum nft_bitwise_attributes`):
- `NFTA_BITWISE_SREG`: Вихідний регістр джерела.
- `NFTA_BITWISE_DREG`: Цільовий регістр призначення.
- `NFTA_BITWISE_LEN`: Довжина операндів у байтах (4 для IPv4, 16 для IPv6).
- `NFTA_BITWISE_MASK`: Бітова маска для операції І (AND).
- `NFTA_BITWISE_XOR`: Значення для операції виключного АБО (XOR).

### 3.4. nft_lookup (Шукач у наборах та картах)

Вираз `nft_lookup` здійснює швидкий пошук значення з регістра `sreg` у вказаному наборі або карті.

Бінарні Netlink-атрибути (`enum nft_lookup_attributes`):
- `NFTA_LOOKUP_SET`: Текстова назва набору.
- `NFTA_LOOKUP_SET_ID`: Внутрішній системний ідентифікатор set handle.
- `NFTA_LOOKUP_SREG`: Регістр з ключем пошуку.
- `NFTA_LOOKUP_DREG`: Регістр для запису результату (для карт/maps) або вердикту (для vmaps).
- `NFTA_LOOKUP_FLAGS`: Прапорці пошуку (`NFT_LOOKUP_F_INV` — інвертувати результат пошуку).

### 3.5. nft_immediate (Завантаження констант та вердиктів)

Вираз `nft_immediate` записує константу або дію вердикту безпосередньо у цільовий регістр без зчитання даних із пакета.

Бінарні Netlink-атрибути (`enum nft_immediate_attributes`):
- `NFTA_IMMEDIATE_DREG`: Цільовий регістр (наприклад, `NFT_REG_VERDICT`).
- `NFTA_IMMEDIATE_DATA`: Значення константи або вкладена структура вердикту.

### 3.6. nft_meta (Системні та пакетні метадані)

Вираз `nft_meta` дозволяє зчитувати або записувати системні метадані операційної системи та сокета.

Перелік ключів метаданих (`enum nft_meta_keys`):
- `NFT_META_LEN`: Довжина пакета в байтах.
- `NFT_META_PROTOCOL`: Мережевий протокол рівня L2 (EtherType, наприклад ETH_P_IP).
- `NFT_META_PRIORITY`: Пріоритет сокета або пакета (`skb->priority`).
- `NFT_META_MARK`: Системна мітка пакета (`skb->mark`).
- `NFT_META_IIF`: Індекс вхідного мережевого інтерфейсу (`ifindex`).
- `NFT_META_OIF`: Індекс вихідного мережевого інтерфейсу.
- `NFT_META_IIFNAME`: Текстова назва вхідного мережевого інтерфейсу.
- `NFT_META_OIFNAME`: Текстова назва вихідного мережевого інтерфейсу.
- `NFT_META_L4PROTO`: Код протоколу транспортного рівня L4 (IPPROTO_TCP, IPPROTO_UDP).
- `NFT_META_SKUID`: Ідентифікатор користувача (UID) процесу, якому належить сокет.
- `NFT_META_SKGID`: Ідентифікатор групи (GID) процесу, якому належить сокет.
- `NFT_META_CGROUP`: Ідентифікатор контрольної групи cgroup v2.

## 4. Специфікація бекендів наборів (Set Backends Spec)

Ядро Linux підтримує кілька бекендів збереження наборів, що оптимізовані під різні типи даних:

```c
struct nft_set_type {
	int				(*ops)(const struct nft_set_desc *desc,
						u32 flags);
	struct list_head		list;
	enum nft_set_policies		policy;
	u32				klen;
	u32				alen;
};
```

Детальна характеристика бекендів:

Бекенд `nft_set_rhash` реалізований на основі динамічної хеш-таблиці `rhashtable`. Він забезпечує середню алгоритмічну складність пошуку `O(1)`. Використовується для підтримки великих точних списків IP-адрес, MAC-адрес або портів.

Бекенд `nft_set_rbtree` спирається на Red-Black Tree (червоно-чорне дерево) і забезпечує алгоритмічну складність пошуку `O(log N)`. Він оптимально підходить для обробки інтервалів та діапазонів (наприклад, CIDR підмереж `192.168.0.0/16` або діапазонів портів `1024-2048`).

Бекенд `nft_set_bitmap` реалізує бітову матрицю в пам'яті ядра із прямим індексуванням за `O(1)`. Застосовується для масивів цілих чисел з невеликим розкидом (наприклад, номери привілейованих портів від 1 до 1024).

Бекенд `nft_set_pipapo` (Packets In Packet Out trie) спеціально розроблений для підтримки складних мульти-конкатенацій (туплесів з кількома полями). Він оптимізований під використання векторних інструкцій процесора (AVX2/SSE) для паралельного порівняння бітових масок.

## 5. Формат повідомлень бінарного протоколу Netlink (nfnetlink)

Обмін правилами між простором користувача та ядром виконується через сокети `AF_NETLINK` підсистеми `NFNL_SUBSYS_NFTABLES` (`10`).

### 5.1. Заголовок повідомлення Netlink

Коже повідомлення містить стандартний заголовок `struct nlmsghdr` та заголовок підсистеми Netfilter `struct nfgenmsg`:

```c
struct nlmsghdr {
	u32	nlmsg_len;   /* Загальна довжина повідомлення у байтах */
	u16	nlmsg_type;  /* Тип повідомлення (наприклад, NFT_MSG_NEWRULE) */
	u16	nlmsg_flags; /* Прапорці (NLM_F_REQUEST | NLM_F_ACK | NLM_F_CREATE) */
	u32	nlmsg_seq;   /* Порядковий номер транзакції */
	u32	nlmsg_pid;   /* Порт/PID відправника */
};

struct nfgenmsg {
	u8	nfgen_family; /* Сімейство протоколів (AF_INET, AF_INET6, NFPROTO_UNSPEC) */
	u8	version;      /* Версія підсистеми (NFNETLINK_V0) */
	be16	res_id;       /* Зарезервовано */
};
```

### 5.2. Структура пакетного повідомлення транзакції (Netlink Batch Transaction)

Усі операції створення, модифікації або видалення правил загортаються у пакетну транзакцію Netlink, обмежену командами `NFNL_MSG_BATCH_BEGIN` та `NFNL_MSG_BATCH_END`:

```
+-------------------------------------------------------+
| nlmsghdr (NFNL_MSG_BATCH_BEGIN)                       |
+-------------------------------------------------------+
| nlmsghdr (NFT_MSG_NEWRULE) + nfgenmsg + Attributes   |
|   ├── NFTA_RULE_TABLE   = "filter"                    |
|   ├── NFTA_RULE_CHAIN   = "input"                     |
|   └── NFTA_RULE_EXPRESSIONS (nested array)            |
|         ├── NFTA_EXPR_NAME = "payload"                |
|         ├── NFTA_EXPR_DATA = { BASE, OFFSET, LEN... } |
|         ├── NFTA_EXPR_NAME = "cmp"                    |
|         └── NFTA_EXPR_DATA = { SREG, OP, DATA... }    |
+-------------------------------------------------------+
| nlmsghdr (NFT_MSG_NEWRULE) + ...                      |
+-------------------------------------------------------+
| nlmsghdr (NFNL_MSG_BATCH_END)                         |
+-------------------------------------------------------+
```

Ядро обробляє транзакцію атомарно: якщо бодай один атрибут виразу не проходить перевірку `ops->init()`, ядро скасовує виконання усієї пакетної транзакції та повертає помилку `NLMSG_ERROR`.
