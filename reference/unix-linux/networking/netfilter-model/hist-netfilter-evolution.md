# 📜 Еволюція пакетної фільтрації у Linux: від ipfwadm до nftables

Розуміння розвитку підсистеми фільтрації трафіку в Linux пояснює, чому сучасне ядро влаштовано саме так: від простих портованих BSD-механізмів до байткод-машини nftables. Історія Netfilter — це історія боротьби між продуктивністю мережевого стека, універсальністю правил та архітектурною чистотою коду ядра.

## 1. Перші кроки: ipfw та народження ipfwadm (1994–1997)

На початку 1990-х років ядро Linux взагалі не мало вбудованих засобів для фільтрації IP-пакетів. Першою спробою додати функції брандмауера став порт коду `ipfw` з операційної системи FreeBSD, виконаний Аланом Коксом (Alan Cox) для серії ядер 1.1. Це була статична реалізація, де перевірка пакетів виконувалася безпосередньо всередині функції обробки вхідних IP-пакетів.

З виходом ядра Linux 2.0 у 1996 році нідерландський розробник Йос Вос (Jos Vos) переробив цю систему, створивши утиліту користувача `ipfwadm` та відповідний ядерний модуль. Система `ipfwadm` дозволяла розмежовувати фільтрацію вхідних (Accounting), вихідних (Outbound) та транзитних (Forwarding) пакетів, а також підтримувала перші базові форми маскарадингу (IP Masquerading) — раннього аналога Source NAT для приховування локальних мереж за єдиною зовнішньою IP-адресою.

Проте `ipfwadm` мав серйозні обмеження:
- Правила зберігалися у вигляді монолітного лінійного масиву ядра.
- Робота з таблицями вимагала почергового лінійного перебору всіх записів для кожного пакету (`O(N)` складності).
- Не існувало механізму створення користувацьких ланцюжків правил, що ускладнювало структурування складної політики безпеки.

## 2. Ера ipchains та поява концепції ланцюжків (1998–1999)

У 1998 році австралійський розробник Расті Расселл (Rusty Russell) запропонував кардинально новий підхід, реалізований у серії ядер Linux 2.2 під назвою `ipchains`.

Головним нововведенням `ipchains` стала відмова від трьох фіксованих списків на користь деревоподібної структури **ланцюжків (chains)**. Користувачі отримали можливість створювати власні ланцюжки та робити переходи (jump) між ними. Це дозволило розбивати великі списки правил на логічні модулі (наприклад, окремий ланцюжок для обробки Web-трафіку, окремий для SSH).

Також `ipchains` уперше чітко розізвав обробку вхідного трафіку:
1. Вхідний пакет перевірявся ланцюжком `input`.
2. Якщо пакет призначався іншій машині, він проходив через `forward`.
3. На виході з мережевого інтерфейсу пакет аналізувався ланцюжком `output`.

Попри величезний крок уперед, `ipchains` все ще залишався брандмауером **без відстеження станів (stateless)**. Перевірка прапорців TCP SYN/ACK проводилася на основі окремих бітів у заголовку, а для UDP-трафіку взагалі не існувало поняття «відповіді на запит». Крім того, код фільтрації був жорстко прив'язаний до IPv4, що унеможливлювало просте додавання підтримки IPv6 або мережевих мостів (Bridge).

## 3. Революція Netfilter та еру створення iptables (1999–2013)

Для розв'язання фундаментальних проблем `ipchains` у 1999 році Расті Расселл разом із Гаральдом Вельте (Harald Welte), Марком Буше (Marc Boucher) та Джеймсом Моррісом (James Morris) започаткував проєкт **Netfilter**. 

Основною ідеєю Netfilter стала повна декомпозиція:
- **Ядро**: надає лише 5 статичних точок розширення (хуків) у мережевому стеку IPv4/IPv6, де інші модулі можуть реєструвати свої callback-функції.
- **Відстеження станів (`nf_conntrack`)**: відокремлений модуль ядра, який аналізує пакети до фільтрації та підтримує таблицю з'єднань у пам'яті.
- **Користувацька утиліта (`iptables`)**: передає структури правил через системні виклики `getsockopt`/`setsockopt` або сокети Netlink.

Вихід ядра Linux 2.4 у 2001 році з підтримкою Netfilter/iptables став стандартом на понад десятиліття. Систему було розділено на спеціалізовані таблиці (`filter`, `nat`, `mangle`, `raw`, `security`), що усунуло плутанину між фільтрацією та трансляцією адрес.

Проте за роки експлуатації з'ясувалися глибокі системні вади `iptables`:
1. **Дублювання коду під кожен протокол**: для IPv4 використовувався `iptables`, для IPv6 — `ip6tables`, для ARP — `arptables`, для L2-містків — `ebtables`. Кожен інструмент мав власну ядерну кодову базу зі схожою, але трохи відмінною логікою.
2. **Атомарність оновлень через заміну всього правилсету**: при додаванні одного правила утиліта `iptables` вивантажувала з ядра весь двоічний масив правил, модифікувала його в просторі користувача і завантажувала назад повністю. На серверах із десятками тисяч правил це викликало суттєві затримки та блокування пам'яті ядра.
3. **Лінійний перебір правил `O(N)`**: перевірка адрес або портів вимагала послідовного порівняння кожного правила у списку, що призводило до деградації швидкодії при великих обсягах трафіку.

## 4. Сучасна ера: nftables та байткод віртуальної машини ядра (з 2014)

Для подолання глухого кута `iptables` у 2008 році Патрик МакГарді (Patrick McHardy) розпочав розробку **nftables**, а пізніше роботу очолив Пабло Нейра Аюсо (Pablo Neira Ayuso). У ядрі Linux 3.13 (січень 2014 року) підсистему `nftables` було офіційно включено до основного дерева ядра.

`nftables` кардинально змінює парадигму:
- **Віртуальна машина ядра (Kernel VM)**: ядро більше не містить жорстко запрограмованої логіки для сотень окремих модулів порівняння (matchers) та дій (targets). Замість цього ядро виконує компактний псевдокод (байткод) у маленькій та безпечній віртуальній машині `nft_expr`.
- **Єдина родина `inet`**: один правиласет може одночасно обробляти IPv4 та IPv6 трафік без дублювання правил.
- **Динамічні набори (Sets) та мапи (Maps)**: замість перебору 1000 правил `DROP IP` nftables використовує хеш-таблиці та червоно-чорні дерева (`O(1)` або `O(log N)`), дозволяючи перевіряти належність адреси до мільйонного списку за один крок execution engine.
- **Атомарні транзакційні оновлення через Netlink**: зміни до правилсету передаються як транзакційні батчі (commit/abort), усуваючи необхідність перезавантажувати весь правилсет.

Завдяки цьому `nftables` повністю замінив застарілі `iptables`, `ip6tables` та `ebtables`, зберігши при цьому сумісність із тими самими 5 класичними хуками ядра Netfilter.
