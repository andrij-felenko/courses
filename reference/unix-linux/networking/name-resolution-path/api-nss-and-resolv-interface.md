# 📋 Довідник інтерфейсів NSS, resolv.conf та systemd-resolved D-Bus

Цей довідник містить повну технічну специфікацію інтерфейсів програмування додатків (API), двійкових структур даних, конфігураційних параметрів та міжпроцесних сигнатур (IPC) підсистеми розв'язання імен у Linux. Інформацію впорядковано за системними рівнями: від прикладного C-API POSIX до низькорівневих ABI модулів NSS, синтаксису конфігураційних файлів та методів системної шини D-Bus.

## 1. Системний API C-бібліотеки (POSIX getaddrinfo та glibc)

Прикладні додатки в операційних системах Linux взаємодіють із підсистемою розв'язання імен за допомогою системного стандарту POSIX.1-2001, головним вхідним компонентом якого є функція `getaddrinfo()`. Ця функція замінила застарілу `gethostbyname()`, надаючи потокобезпечний та універсальний спосіб отримання мережевих адрес для протоколів IPv4 та IPv6.

### Структури даних POSIX

Головні структури даних, константи та коди помилок визначено у системному заголовному файлі `<netdb.h>`.

#### `struct addrinfo`

Структура `addrinfo` слугує як для передачі вхідних підказок (hints) про бажаний тип сокета й сімейство протоколів, так і для повернення результатів у вигляді динамічного однозв'язаного списку знайдених мережевих адрес.

```c
struct addrinfo {
    int              ai_flags;      /* Прапорці поведінки (AI_PASSIVE, AI_CANONNAME тощо) */
    int              ai_family;     /* Сімейство адрес: AF_INET, AF_INET6, AF_UNSPEC */
    int              ai_socktype;   /* Тип сокета: SOCK_STREAM, SOCK_DGRAM */
    int              ai_protocol;   /* Протокол: IPPROTO_TCP, IPPROTO_UDP, 0 */
    socklen_t        ai_addrlen;    /* Довжина сокетної адреси у байтах */
    struct sockaddr *ai_addr;       /* Вказівник на структуру sockaddr_in або sockaddr_in6 */
    char            *ai_canonname;  /* Канонічне ім'я хоста (якщо вказано AI_CANONNAME) */
    struct addrinfo *ai_next;       /* Вказівник на наступний елемент зв'язаного списку */
};
```

Кожне поле структури відповідає за конкретний аспект мережевого з'єднання:

* **Поле `ai_flags`**: Бітова маска, яка модифікує внутрішні алгоритми пошуку, вибір сокетів та форматування результату.
* **Поле `ai_family`**: Задає протокольний простір адрес. Значення `AF_INET` обмежує пошук виключно IPv4-адресами, `AF_INET6` — виключно IPv6-адресами, а `AF_UNSPEC` вказує резолверу повертати абсолютно всі доступні адреси для обох протоколів.
* **Поле `ai_socktype`**: Вказує бажаний тип транспортного сокета. Значення `SOCK_STREAM` використовується для потокових TCP-з'єднань, а `SOCK_DGRAM` — для датаграмних UDP-сокетів.
* **Поле `ai_protocol`**: Задає конкретний транспортний протокол (наприклад, `IPPROTO_TCP` або `IPPROTO_UDP`). Зазвичай залишається `0`, що дозволяє системі вибрати відповідний протокол за замовчуванням.
* **Поле `ai_addrlen`**: Містить точний розмір у байтах двійкової структури сокетної адреси, на яку вказує поле `ai_addr`.
* **Поле `ai_addr`**: Універсальний вказівник на заповнену двійкову структуру сокетної адреси (`sockaddr_in` для IPv4 або `sockaddr_in6` для IPv6), яку додаток може безпосередньо передавати у системні виклики `connect()`, `bind()` або `sendto()`.
* **Поле `ai_canonname`**: Вказівник на текстовий нуль-термінований рядок, що містить офіційне канонічне ім'я вузла (наприклад, реальне ім'я сервера після розкриття всіх CNAME-записів у DNS).
* **Поле `ai_next`**: Вказівник на наступний вузол зв'язаного списку `addrinfo`. Додаток повинен послідовно обходити цей список у циклі, пробуючи під'єднатися до кожної адреси, доки не досягне `NULL`.

#### Детальний розбір бітових прапорців `ai_flags`

Прапорці дозволяють точково керувати поведінкою виклику `getaddrinfo()`.

* **Прапорець `AI_PASSIVE`**: Призначений для підготовки сокетної адреси, яка буде використовуватися у системному виклику `bind()` для відкриття слухаючого сервера. Якщо при цьому аргумент `node` дорівнює `NULL`, функція повертає wildcard-адресу (`INADDR_ANY` для IPv4 або `in6addr_any` для IPv6), що дозволяє серверу приймати вхідні з'єднання на всіх мережевих інтерфейсах системи. Якщо прапорець не встановлено, повертається адреса `127.0.0.1` або `::1` для локального під'єднання.
* **Прапорець `AI_CANONNAME`**: Вказує резолверу заповнити поле `ai_canonname` першого елемента повернутого списку офіційним канонічним іменем хоста, отриманим з бази даних DNS або файлу `/etc/hosts`.
* **Прапорець `AI_NUMERICHOST`**: Примусово вимикає будь-які мережеві запити та перевірки файлів конфігурації. Аргумент `node` повинен бути числовим текстовим IP-рядком (наприклад, `"192.168.1.1"` або `"2001:db8::1"`). Якщо замість числової адреси передано символьне ім'я домену, функція негайно повертає помилку `EAI_NONAME`.
* **Прапорець `AI_NUMERICSERV`**: Вимикає пошук текстових назв сервісів у файлі `/etc/services`. Аргумент `service` повинен бути числовою назвою порту (наприклад, `"80"` або `"443"`).
* **Прапорець `AI_V4MAPPED`**: Застосовується при виклику з `ai_family == AF_INET6`. Якщо у базі даних відсутні нативні AAAA-записи IPv6 для вказаного хоста, функція автоматично згенерує та поверне IPv4-відображені IPv6-адреси у форматі `::ffff:192.168.1.1`.
* **Прапорець `AI_ALL`**: Використовується виключно разом із `AI_V4MAPPED`. Примушує функцію повертати як нативні IPv6-адреси, так і IPv4-відображені адреси в єдиному списку.
* **Прапорець `AI_ADDRCONFIG`**: Повертає IPv4-адреси лише тоді, коли у системі присутній щонайменше один активний мережевий IPv4-інтерфейс з адресою, відмінною від loopback (аналогічно для IPv6). Це запобігає марній генерації IPv6 DNS-запитів на системах, які не мають IPv6-зв'язності.

### Сигнатури функцій POSIX API

Стандартний комплект функцій для розв'язання та звільнення адрес має такий вигляд:

```c
int getaddrinfo(
    const char *node,
    const char *service,
    const struct addrinfo *hints,
    struct addrinfo **res
);

void freeaddrinfo(struct addrinfo *res);

const char *gai_strerror(int errcode);

int getnameinfo(
    const struct sockaddr *sa,
    socklen_t salen,
    char *host,
    size_t hostlen,
    char *serv,
    size_t servlen,
    int flags
);
```

Функція `getaddrinfo()` повертає `0` у разі успішного виконання або один із від'ємних кодів помилок `EAI_*`:
* **`EAI_AGAIN`**: Тимчасова помилка розв'язання імені, рекомендується повторити запит пізніше.
* **`EAI_BADFLAGS`**: Некоректне або несумісне поєднання бітових прапорців у `hints->ai_flags`.
* **`EAI_FAIL`**: Невідновлювана системна помилка сервера імен.
* **`EAI_FAMILY`**: Запитане сімейство адрес `ai_family` не підтримується системою.
* **`EAI_MEMORY`**: Недостатньо оперативної пам'яті для виділення структур результату.
* **`EAI_NONAME`**: Запитане ім'я домену або сервісу не існує або не може бути розв'язане.
* **`EAI_SYSTEM`**: Системна помилка, детальний код якої збережено у глобальній змінній `errno`.

Для перетворення числового коду помилки `EAI_*` на текстовий рядок використовується функція `gai_strerror()`. Динамічно виділена пам'ять під повернутий зв'язаний список `res` зобов'язана звільнятися обов'язковим викликом `freeaddrinfo()`.

## 2. Двійковий ABI модулів Name Service Switch (NSS)

Підсистема NSS у бібліотеці `glibc` опитує динамічні shared-бібліотеки вида `libnss_<назва>.so.2`. Кожен плагін експортує суворо визначені C-функції.

### Перелічуваний тип статусу `enum nss_status`

Модуль повертає один із чотирьох стандартних кодів стану, на основі яких диспетчер `glibc` приймає рішення щодо продовження або припинення конвеєра в `/etc/nsswitch.conf`:

```c
enum nss_status {
    NSS_STATUS_TRYAGAIN = -2, /* Тимчасова помилка або недостатній розмір буфера (errno = ERANGE) */
    NSS_STATUS_UNAVAIL  = -1, /* Модуль недоступний або конфігурація зламана */
    NSS_STATUS_NOTFOUND =  0, /* Запис не знайдено в даному модулі */
    NSS_STATUS_SUCCESS  =  1  /* Запис успішно знайдено та заповнено у результаті */
};
```

Детальна поведінка кодів статусу:
* **`NSS_STATUS_SUCCESS`**: Запит оброблено успішно, структура `result` заповнена даними. `glibc` припиняє подальший перебір модулів і повертає результат додатку.
* **`NSS_STATUS_NOTFOUND`**: Запитане ім'я хоста відсутнє у даній базі даних (або не належить до домену відповідальності модуля). `glibc` передає запит наступному модулю в списку.
* **`NSS_STATUS_UNAVAIL`**: Модуль не може бути використаний (наприклад, зламано файл конфігурації або відсутній мережевий демон). За замовчуванням `glibc` переходить до наступного модуля, якщо в `/etc/nsswitch.conf` не вказано специфічних дій `[UNAVAIL=return]`.
* **`NSS_STATUS_TRYAGAIN`**: Тимчасова помилка ресурсу. Якщо в `*errnop` збережено `ERANGE`, це означає, що наданий `glibc` буфер `buffer` замалий. `glibc` автоматично збільшить буфер і повторить виклик.

### Сигнатури експортованих C-функцій NSS

```c
/* Опитування за іменем хоста та сімейством адрес (IPv4/IPv6) */
enum nss_status _nss_<module>_gethostbyname2_r(
    const char *name,
    int af,
    struct hostent *result,
    char *buffer,
    size_t buflen,
    int *errnop,
    int *h_errnop
);

/* Зворотне опитування за двійковою IP-адресою (Reverse DNS) */
enum nss_status _nss_<module>_gethostbyaddr_r(
    const char *addr,
    int len,
    int type,
    struct hostent *result,
    char *buffer,
    size_t buflen,
    int *errnop,
    int *h_errnop
);
```

Параметри `errnop` та `h_errnop` призначені для повернення детальних системних помилок (наприклад, `ERANGE`, `HOST_NOT_FOUND`, `NO_DATA`, `TRY_AGAIN`).

## 3. Конфігураційний формат та синтаксис `/etc/nsswitch.conf`

Конфігураційний файл `/etc/nsswitch.conf` визначє порядок опитування модулів для кожної системної бази даних (паролі, групи, хости).

### Формат запису рядка

Синтаксис запису складається з назви бази даних, двокрапки та списку модулів:

```text
<база_даних>: <модуль1> [<умова1>] <модуль2> [<умова2>] ...
```

Для підсистеми розв'язання імен хостів використовується ключ `hosts:`.

### Умови реагування `[STATUS=ACTION]`

Між назвами модулів дозволяється вставляти специфікатори реакцій у квадратних дужках. Вони змінюють стандартний потік перебору модулів:
* **Можливі значення `STATUS`**: `SUCCESS`, `NOTFOUND`, `UNAVAIL`, `TRYAGAIN`.
* **Можливі значення `ACTION`**:
  * `return`: Негайно припинити обробку даної бази даних і повернути поточний результат прикладному додатку.
  * `continue`: Ігнорувати даний статус і обов'язково перейти до опитування наступного модуля в списку.
* **Оператор заперечення `!`**: Використовується для інвертування умови. Наприклад, `[!UNAVAIL=return]` означає: «якщо статус модуля відмінний від UNAVAIL (тобто модуль доступний і повернув SUCCESS або NOTFOUND), припинити пошук і повернути результат».

```text
# Типовий виробничий рядок конфігурації hosts у сучасних дистрибутивах:
hosts: files resolve [!UNAVAIL=return] dns myhostname
```

## 4. Специфікація конфігураційного файла `/etc/resolv.conf`

Файл `/etc/resolv.conf` керує параметрами низькорівневого розв'язувача `glibc` (`libnss_dns.so.2`).

### Основні директиви конфігурації

* **Директива `nameserver`**: Вказує IPv4 або IPv6 адресу DNS-сервера, до якого надсилаються запити. У файлі можна вказати до 3 серверів (обмеження константою `MAXNS`). Сервери опитуються послідовно у порядку оголошення. Якщо перший сервер не відповідає протягом таймауту, розв'язувач переходить до другого.
* **Директива `search`**: Задає список доменних суфіксів (до 6 доменів, загальною довжиною до 256 байт) для автоматичного дописування до неповних (відносних) імен хостів. Наприклад, при `search corp.example.com` запит імені `db` перетвориться на `db.corp.example.com`.
* **Директива `domain`**: Застаріла директива для вказання єдиного локального домену. Повністю взаємовиключна з `search`. Якщо у файлі присутні обидві директиви, використовується та, яка розташована нижче.
* **Директива `sortlist`**: Дозволяє сортувати отримані від DNS адреси залежно від належності до вказаних IP-підмереж (до 10 записів).

### Параметри тонкого тюнінгу `options`

Параметри задаються у рядку `options <опція1> <опція2>...`:

* **`ndots:n`**: Визначає поріг кількості крапок у імені хоста. Якщо кількість крапок у імені `>= n`, ім'я спочатку пробується як абсолютне FQDN. За замовчуванням `ndots:1`. В Kubernetes значення `ndots:5` спричиняє до 4 послідовних невдалих DNS-запитів для кожного короткого імені.
* **`timeout:n`**: Час очікування відповіді від DNS-сервера у секундах перед перемиканням на наступний `nameserver` (за замовчуванням 5 секунд).
* **`attempts:n`**: Кількість спроб повторного надсилання запиту до кожного DNS-сервера перед поверненням помилки (за замовчуванням 2 спроби).
* **`rotate`**: Вмикає круговий перебір (round-robin) між серверами `nameserver` для рівномірного розподілу навантаження.
* **`single-request`**: Виконує паралельні A (IPv4) та AAAA (IPv6) запити через один сокет послідовно один за одним.
* **`single-request-reopen`**: Примусово закриває та відкриває UDP-сокет заново між відправкою A та AAAA запитів. Допомагає уникнути втрати пакетів на старих фаєрволах.
* **`use-vc`**: Примусово виконує абсолютно всі DNS-запити через TCP-з'єднання замість UDP.
* **`edns0`**: Вмикає розширення EDNS0 (RFC 6891), що дозволяє збільшити розмір UDP-пакета з 512 до 4096 байт.

## 5. D-Bus та Varlink API сервісу `systemd-resolved`

Демон `systemd-resolved` надає високопродуктивний міжпроцесний інтерфейс (IPC) через системну шину D-Bus.

* **Назва D-Bus сервісу:** `org.freedesktop.resolve1`
* **Шлях до об'єкта:** `/org/freedesktop/resolve1`
* **Головний інтерфейс:** `org.freedesktop.resolve1.Manager`

### Ключові методи D-Bus API

#### Метод `ResolveHostname`

Забезпечує пряме розв'язання імені в IP-адресу через D-Bus без відкриття сокетів UDP/53.

```text
ResolveHostname(
    in  i ifindex,          # Індекс мережевого інтерфейсу (0 — будь-який)
    in  s name,             # Доменне ім'я для розв'язання ("example.com")
    in  i family,           # AF_INET (2), AF_INET6 (10), AF_UNSPEC (0)
    in  t flags,            # Прапорці обробки (SD_RESOLVE_NO_SYNTHESIZE тощо)
    out a(iiay) addresses,  # Масив результатів: (ifindex, family, ip_bytes)
    out s canonical,        # Канонічне ім'я
    out t flags_out         # Прапорці джерела (SD_RESOLVE_DNS, SD_RESOLVE_LLMNR)
)
```

Аргумент `ifindex` дозволяє обмежити розв'язання конкретним мережевим адаптером. Масив `addresses` повертає двійкові байтові масиви IP-адрес разом із сімейством та індексом інтерфейсу.

#### Метод `SetLinkDNS`

Дозволяє мережевим демонам (NetworkManager, systemd-networkd) динамічно призначати DNS-сервери для конкретного інтерфейсу.

```text
SetLinkDNS(
    in  i ifindex,          # Системний індекс інтерфейсу (наприклад, 2 для eth0)
    in  a(iay) addresses    # Масив структур: (family, binary_ip_bytes)
)
```

#### Метод `SetLinkDomains`

Налаштовує домени маршрутизації (Split-DNS) для інтерфейсу.

```text
SetLinkDomains(
    in  i ifindex,          # Індекс інтерфейсу
    in  a(sb) domains       # Масив пар: (domain_name_string, is_routing_only_boolean)
)
```

Якщо прапорець `is_routing_only_boolean` дорівнює `true` (префікс `~` у CLI), інтерфейс використовується виключно для маршрутизації запитів до вказаного домену, але не додає його до списку пошуку.

## 6. Довідник команд утиліти `resolvectl`

Утиліта `resolvectl` є основним інструментом командного рядка для керування та діагностики `systemd-resolved`.

```bash
# Перегляд поточного стану DNS-серверів та доменів маршрутизації для всіх інтерфейсів:
resolvectl status

# Запит розв'язання імені через D-Bus API systemd-resolved:
resolvectl query example.com

# Зворотне розв'язання IP-адреси (Reverse DNS Lookup):
resolvectl query 1.1.1.1

# Очищення системного кaшу DNS-відповідей systemd-resolved:
resolvectl flush-caches

# Перегляд статистики влучань у кеш та перевірок DNSSEC:
resolvectl statistics

# Примусове призначення DNS-серверів для конкретного інтерфейсу eth0:
sudo resolvectl dns eth0 1.1.1.1 8.8.8.8

# Налаштування домену маршрутизації (Split-DNS) для VPN-інтерфейсу wg0:
sudo resolvectl domain wg0 "~corp.example.com"
```

Команда `resolvectl status` відображає підключені DNS-сервери, режим перевірки DNSSEC, протоколи mDNS/LLMNR та суфікси маршрутизації окремо для кожного мережевого інтерфейсу системи.
