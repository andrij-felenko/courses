При спробі перехопити мережевий трафік на швидкості 10 Gbit/s із розміром пакетів 64 байти (що становить 14.88 мільйона пакетів на секунду у повному дуплексі) стандартний підхід із регулярним викликом системної функції `recvfrom()` призводить до 100% завантаження центрального процесора лише на перемикання контексту та копіювання пам'яті. Система витрачає мільярди тактів CPU на марну системну рутину, внаслідок чого черги мережевої карти переповнюються, і ядро скидає понад 80% вхідного трафіку (packet drops).

Для подолання цього бар'єра продуктивності в ядрі Linux було розроблено механізм **PACKET_MMAP**, який у своїй найсучаснішій версії **TPACKET_V3** забезпечує високопродуктивне перехоплення та надсилання мережевих пакетів через спільну пам'ять без додаткового копіювання.

## 1. Проблема вузького місця класичних сокетів

Щоб зрозуміти, чому виник механізм PACKET_MMAP, розглянемо послідовність дій та розподіл ресурсів системи при використанні класичного сокета `AF_PACKET` у режимі `SOCK_RAW`:

:::tabs
```c
int fd = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
```
```cpp
int fd = ::socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
```
:::

Коли мережева карта (NIC) отримує фізичний кадр з мережі, у системі спрацьовує складний ланцюжок операцій:

1. **DMA та апаратне переривання:** NIC записує кадр через прямої доступ до пам'яті (DMA) у кільцевий буфер прийому (RX ring) драйвера і генерує апаратне переривання (IRQ) процесора.
2. **Обробка в SoftIRQ / NAPI:** Переривання змушує ядро переключитися у режим обробки софт-переривань (NAPI poll loop). Драйвер мережевої карти виділяє системну структуру `struct sk_buff` (SKB) у оперативній пам'яті ядра через ядерний аллокатор `kmem_cache` та копіює туди дані з апаратного RX-буфера.
3. **Постановка у чергу сокета:** Оскільки сокет відкритий у режимі `AF_PACKET`, ядро клонує структуру `sk_buff` і ставить її в чергу прийому конкретного сокета (`sk_receive_queue`), що вимагає захоплення локів сокета (`spin_lock`).
4. **Системний виклик `recvfrom()`:** Програма у користувацькому просторі викликає `recvfrom()` для отримання чергового пакета.
5. **Перемикання контексту (Context Switch):** Процесор виконує інструкцію `syscall` (`sysenter`), перемикаючись із привілеїв User Mode (Ring 3) у Kernel Mode (Ring 0). При цьому зберігаються регістри процесора, змінюються таблиці сторінок та перевіряються права доступу.
6. **Копіювання пам'яті (`copy_to_user`):** Ядро копіює вміст `sk_buff` із системної пам'яті ядра у буфер користувацького процесу через операцію `memcpy()`.
7. **Повернення контексту та звільнення пам'яті:** Процесор повертається у користувацький режим, а ядро деаллокує структуру `sk_buff`.

```
[ NIC RX DMA Ring ] ──> [ SoftIRQ: sk_buff Alloc ] ──> [ Socket Queue (sk_receive_queue) ]
                                                                     │
                                                          (copy_to_user + syscall)
                                                                     ▼
                                                          [ User Space Buffer ]
```

### Причини деградації продуктивності

При обробці мільйонів пакетів на секунду ця схема ламається через чотири фундаментальні обмеження:

- **Накладні витрати системних викликів:** Кожен виклик `recvfrom()` вимагає збереження та відновлення контексту процесів. Для 10 мільйонів пакетів на секунду це означає виконання 10 мільйонів системних викликів щосекунди, що повністю поглинає ресурси CPU.
- **Інвалідація кеш-пам'яті (Cache Line Flushing):** Операція `copy_to_user()` вимиває з L1/L2 кешів процесора корисні інструкції та дані програми, замінюючи їх сирими байтами вхідних пакетів.
- **Накладні витрати аллокатора `sk_buff`:** Виділення та звільнення пам'яті під структури `sk_buff` у ядерному аллокаторі SLUB вимагає значної кількості тактів процесора на кожен пакет.
- **Блокування черг (Lock Contention):** Постійні операції `spin_lock` при постановці пакетів у чергу сокета викликають затримки ядер CPU.

## 2. Архітектура PACKET_MMAP: Спільне кільце пам'яті

Механізм **PACKET_MMAP** фундаментально змінює модель взаємодії між ядром та користувацьким застосунком. Замість копіювання даних через межу системного виклику ядро та процес використовують **спільний кільцевий буфер** (shared memory ring buffer).

При створенні сокета програма за допомогою виклику `setsockopt()` замовляє у ядра буфер певного розміру, а потім відображає його у свій адресний простір за допомогою виклику `mmap()`:

![Порівняння традиційного захоплення пакетів та механізму PACKET_MMAP](/reference/unix-linux/networking/packet-mmap-ring-buffers/img/packet-mmap-arch.svg)
*Архітектура PACKET_MMAP у порівнянні з традиційними сокетами SOCK_RAW: усунення перемикання контексту та копіювання даних.*

Головні переваги цієї архітектури:

1. **Zero-Copy read:** Ядро записує вхідний мережевий кадр безпосередньо у сторінки пам'яті, які одночасно видимі користувацькому процесу. Програма читає дані прямо з пам'яті без операції `memcpy()`.
2. **Паралельна робота без системних викликів:** Програма перевіряє прапорці статусу в буфері без виконання системних викликів. Системний виклик `poll()` або `epoll()` виконується лише тоді, коли всі блоки буфера порожні і треба заснути в очікуванні нових даних.
3. **Амортизація сплесків трафіку:** Великий кільцевий буфер дозволяє накопичувати пакети під час тимчасових піків завантаження процесора.

## 3. Еволюція TPACKET: від V1/V2 до V3

Механізм PACKET_MMAP проходив еволюцію через три версії API (TPACKET), які детально описані у документальному екскурсі [Історія еволюції PACKET_MMAP](book:unix-linux/packet-mmap-ring-buffers/hist-tpacket-evolution.md).

### Порівняльний аналіз версій TPACKET

| Параметр | TPACKET_V1 | TPACKET_V2 | TPACKET_V3 |
| :--- | :--- | :--- | :--- |
| **Елемент буфера** | Слот (Frame) | Слот (Frame) | Блок (Block) |
| **Пакування пакетів** | 1 пакет = 1 фрейм | 1 пакет = 1 фрейм | Багато пакетів у блоці |
| **Точність точок часу** | Мікросекунди (`timeval`) | Наносекунди (`timespec`) | Наносекунди (`timespec`) |
| **Підтримка VLAN Offload** | Відсутня | Присутня (`tp_vlan_tci`) | Присутня (`tp_vlan_tci`) |
| **Ефективність пам'яті** | Низька (фрагментація) | Низька (фрагментація) | Висока (змінна довжина) |
| **Одиниця атомарної синхронізації** | Кожен пакет | Кожен пакет | Цілий блок (Batch) |
| **Таймер віддачі пам'яті** | Відсутній | Відсутній | Присутній (`retire_blk_tov`) |

### Революція TPACKET_V3: Пакувальні блоки (Block-Based Architecture)

Представлена в ядрі Linux 3.2 версія **TPACKET_V3** відмовилася від фіксованих фреймів на користь **блокової пачкової обробки**.

У TPACKET_V3 буфер складається з масиву великих безперервних блоків (наприклад, по 1 MB кожен). Пакети довільної довжини пакуються в блок послідовно один за одним:

![Структура блоку та вирівнювання фреймів у TPACKET_V3](/reference/unix-linux/networking/packet-mmap-ring-buffers/img/tpacket-v3-block.svg)
*Внутрішнє влаштування блоку TPACKET_V3: заголовок block_desc керує статусом усього блоку, а кадри tpacket3_hdr з'єднані офсетами tp_next_offset.*

Основні особливості TPACKET_V3:
1. **Змінна довжина кадрів:** Пакети пакуються щільно без втрати пам'яті.
2. **Блоковий статус:** Передача прав володіння пам'яттю здійснюється для цілого блоку (десятки/сотні пакетів) однією атомарною операцією.
3. **Таймер віддачі блоку (`retire_blk_tov`):** Якщо трафік низький, частково заповнений блок віддається користувачу за тайм-аутом, запобігаючи затримкам.

## 4. Конфігурація та внутрішня структура TPACKET_V3

Для створення кільцевого буфера TPACKET_V3 використовується структура `tpacket_req3`. Повний опис її полів наведено у довіднику [Довідник структур даних та API TPACKET_V3](book:unix-linux/packet-mmap-ring-buffers/api-tpacket-v3.md).

### Налаштування параметрів буфера у коді

:::tabs
```c
/* Конфігурація TPACKET_V3 на мові C */
struct tpacket_req3 req;
memset(&req, 0, sizeof(req));

req.tp_block_size = 1024 * 1024;    /* 1 MB на блок (мусить бути кратним PAGE_SIZE) */
req.tp_block_nr = 64;               /* 64 блоки (загалом 64 MB пам'яті) */
req.tp_frame_size = 2048;           /* Верхня межа розміру кадру */
req.tp_frame_nr = (req.tp_block_size * req.tp_block_nr) / req.tp_frame_size;
req.tp_retire_blk_tov = 10;         /* Таймаут віддачі часткового блоку: 10 мс */
req.tp_feature_req_word = TP_FT_REQ_FILL_RXHASH;

if (setsockopt(fd, SOL_PACKET, PACKET_RX_RING, &req, sizeof(req)) < 0) {
    perror("setsockopt PACKET_RX_RING");
}
```
```cpp
// Конфігурація TPACKET_V3 на мові C++ з використанням типів C++20
#include <linux/if_packet.h>
#include <sys/socket.h>
#include <system_error>
#include <cstdint>

void setup_tpacket_v3_ring(int socket_fd) {
    tpacket_req3 req{};
    req.tp_block_size = 1024 * 1024; // 1 MB
    req.tp_block_nr = 64;            // 64 MB
    req.tp_frame_size = 2048;
    req.tp_frame_nr = (req.tp_block_size * req.tp_block_nr) / req.tp_frame_size;
    req.tp_retire_blk_tov = 10;      // 10 ms timeout
    req.tp_feature_req_word = TP_FT_REQ_FILL_RXHASH;

    if (::setsockopt(socket_fd, SOL_PACKET, PACKET_RX_RING, &req, sizeof(req)) < 0) {
        throw std::system_error(errno, std::generic_category(), "Не вдалося налаштувати PACKET_RX_RING");
    }
}
```
:::

### Вимоги до пам'яті та вирівнювання

Під час виконання `setsockopt(PACKET_RX_RING)` ядро виділяє пам'ять через ядерний аллокатор сторінок (`alloc_pages`). Оскільки кожен блок є фізично безперервною ділянкою пам'яті, значення `tp_block_size` має відповідати умовам:
- Довжина блоку мусить бути кратною розміру системної сторінки (`PAGE_SIZE`, що на х86_64 становить 4096 байтів).
- Значення `tp_block_size` має ділитися на `tp_frame_size`.

Після цього програма відображає буфер у свій адресний простір:

:::tabs
```c
size_t total_size = (size_t)req.tp_block_size * req.tp_block_nr;
void *ring = mmap(NULL, total_size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_LOCKED, fd, 0);
if (ring == MAP_FAILED) {
    perror("mmap");
}
```
```cpp
size_t total_size = static_cast<size_t>(req.tp_block_size) * req.tp_block_nr;
void* ring = ::mmap(nullptr, total_size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_LOCKED, socket_fd, 0);
if (ring == MAP_FAILED) {
    throw std::system_error(errno, std::generic_category(), "mmap ring failed");
}
```
:::

Прапорець `MAP_LOCKED` гарантує, що сторінки пам'яті буде зафіксовано в RAM (`mlock`), запобігаючи їх вивантаженню у swap, що є принциповим для безпеки DMA-операцій ядра.

## 5. Автомат станів та синхронізація кільцевого буфера

Управління блоками у TPACKET_V3 базується на безблокувальній синхронізації (lockless ring buffer) за допомогою атомарного поля `block_status` у заголовку блоку `struct tpacket_hdr_v1`.

### Схема передачі прав (State Machine)

1. **Ініціалізація:** При створенні буфера всі блоки мають статус `TP_STATUS_KERNEL` (0). Це означає, що ядро має виключне право записувати дані в ці блоки.
2. **Заповнення ядром:** Драйвер мережевої карти записує кадри в поточний активний блок.
3. **Закриття блоку (Block Retirement):** Коли блок заповнюється або минає таймер `tp_retire_blk_tov`, ядро виставляє атомарний прапорець:
   `pbd->h1.block_status |= TP_STATUS_USER;`
4. **Обробка в User Space:** Користувацький процес опитує статус блоку. Побачивши прапорець `TP_STATUS_USER`, програма вичитає всі пакети блоку через зміщення `tp_next_offset`.
5. **Повернення ядру:** Завершивши обробку, процес повертає блок ядру:
   `pbd->h1.block_status = TP_STATUS_KERNEL;`

```
   +--------------------+
   |  TP_STATUS_KERNEL  | ◄──────────────────────┐
   +---------┬----------+                        │
             │                                   │
  (Ядро записує кадри)              (Процес повертає блок)
             │                                   │
             ▼                                   │
   +--------------------+                        │
   |   TP_STATUS_USER   | ───────────────────────┘
   +--------------------+
```

### Бар'єри пам'яті (Memory Barriers)

Оскільки ядро та користувацький процес працюють на різних ядрах CPU, для запобігання перевпорядкуванню операцій читання/запису процесором використовуються бар'єри пам'яті:
- В ядрі перед зміною статусу виконується `smp_wmb()` (Write Memory Barrier).
- У користувацькому коді перед зчитуванням полів пакета виконується `smp_rmb()` (Read Memory Barrier) або використовуватимуться атомарні операції `std::atomic_thread_fence(std::memory_order_acquire)`.

## 6. Шлях пакета всередині ядра Linux (`net/packet/af_packet.c`)

Розглянемо послідовність викликів функцій у ядрі Linux при надходженні пакета в буфер TPACKET_V3:

1. **`netif_receive_skb()`:** Драйвер мережевої карти передає `sk_buff` у мережевий стек.
2. **`packet_rcv()`:** Головна обробна функція сокета `AF_PACKET`. Вона перевіряє наявність BPF-фільтра. Якщо пакет відповідає критеріям, виклики перенаправляються у `tpacket_rcv()`.
3. **`tpacket_rcv()`:**
   - Обчислює необхідний обсяг пам'яті для кадру з урахуванням заголовка `tpacket3_hdr` та вирівнювання.
   - Викликає `prb_dispatch_next_hop()` для пошуку поточного активного блоку в кільці.
   - Якщо поточний блок заповнений, викликається `prb_close_block()`, який виставляє `TP_STATUS_USER` і перемикає активне кільце на наступний блок (`prb_open_block()`).
   - Записує метадані (timestamp, snaplen, len, hash) та виконує `skb_copy_bits()` для копіювання payload кадру в блок.
   - Перезапускає таймер блоку `prb_retire_rx_blk_timer_expire()`.

## 7. Передача даних через `PACKET_TX_RING`

Окрім прийому трафіку (RX), механізм PACKET_MMAP підтримує високопродуктивне надсилання пакетів через кільцевий буфер передачі **`PACKET_TX_RING`**.

### Принцип роботи TX_RING

1. Програма замовляє буфер передачі через `setsockopt(SOL_PACKET, PACKET_TX_RING, &req)`.
2. Користувацький процес записує кадри безпосередньо у слоти змонтованої пам'яті.
3. Процес виставляє статус фрейму в `TP_STATUS_SEND`.
4. Програма виконує один системний виклик `send(fd, NULL, 0, 0)`.
5. Ядро за один виклик проходиться по всьому кільцю, передає всі кадри зі статусом `TP_STATUS_SEND` у чергу драйвера NIC (`dev_queue_xmit`), і виставляє статус назад у `TP_STATUS_AVAILABLE`.

Це дозволяє відправляти десятки тисяч пакетів за один системний виклик `send()`.

## 8. Масштабування обробки через `PACKET_FANOUT`

На швидкостях 10-40 Gbps один потік у користувацькому просторі не встигає аналізувати трафік. Для розпаралелювання обробки між кількома ядрами CPU ядро Linux надає механізм **PACKET_FANOUT**.

### Принцип дії Fanout

Програма створює `N` сокетів `AF_PACKET` (по одному на кожен потік обробки), для кожного з яких налаштовується власний TPACKET_V3 ring buffer. Після цього всі сокети об'єднуються в одну **Fanout-групу**:

:::tabs
```c
/* Приєднання сокета до Fanout групи у C */
uint16_t group_id = 42;
uint32_t option = (group_id & 0xffff) | (PACKET_FANOUT_HASH << 16);
if (setsockopt(fd, SOL_PACKET, PACKET_FANOUT, &option, sizeof(option)) < 0) {
    perror("setsockopt PACKET_FANOUT");
}
```
```cpp
// Приєднання сокета до Fanout групи у C++
uint16_t group_id = 42;
uint32_t option = (group_id & 0xffff) | (PACKET_FANOUT_HASH << 16);
if (::setsockopt(socket_fd, SOL_PACKET, PACKET_FANOUT, &option, sizeof(option)) < 0) {
    throw std::system_error(errno, std::generic_category(), "Не вдалося налаштувати PACKET_FANOUT");
}
```
:::

### Алгоритми балансування Fanout

| Режим Fanout | Опис роботи | Сфера застосування |
| :--- | :--- | :--- |
| `PACKET_FANOUT_HASH` | Хешує 4-tuple кадру (SRC IP, DST IP, SRC Port, DST Port). Усі пакети одного сеансу потрапляють в один сокет. | Stateful IDS/IPS (Suricata, Snort), аналізатори сесій. |
| `PACKET_FANOUT_LB` | Просте циклічне розподілення пакетів (Round-Robin). | Простий рівномірний підрахунок обсягу трафіку. |
| `PACKET_FANOUT_CPU` | Відправляє пакет у сокет, прив'язаний до ядра CPU, де спрацював SoftIRQ. | Забезпечує ідеальну локальність L1/L2 кешу процесора. |
| `PACKET_FANOUT_ROLLOVER` | Направляє весь трафік в один сокет, а при його переповненні переливає в наступний. | Резервування потужностей обробки. |
| `PACKET_FANOUT_EBPF` | Вибір сокета-отримувача здійснюється власною eBPF програмою користувача. | Складне динамічне маршрутизування трафіку. |

## 9. Фільтрація трафіку через BPF / eBPF

Щоб не засмічувати кільцевий буфер непотрібними пакетами, до сокета `AF_PACKET` можна приєднати класичний BPF або eBPF фільтр за допомогою виклику `setsockopt(SOL_SOCKET, SO_ATTACH_FILTER)` або `SO_ATTACH_BPF`.

Ядро виконує BPF-фільтр у софт-перериванні **до** того, як пакет буде записано у блок TPACKET_V3. Якщо фільтр відхиляє пакет, він миттєво відкинується без витрати пам'яті кільцевого буфера.

## 11. Моніторинг та діагностика

Для спостереження за станом кільцевих буферів PACKET_MMAP у ядрі Linux використовуються такі інструменти:

### 1. Зчитування статистики через `getsockopt`

:::tabs
```c
struct tpacket_stats_v3 stats;
socklen_t len = sizeof(stats);
if (getsockopt(fd, SOL_PACKET, PACKET_STATISTICS, &stats, &len) == 0) {
    printf("Прийнято пакетів: %u, Скинуто (drops): %u\n", 
           stats.tp_packets, stats.tp_drops);
}
```
```cpp
tpacket_stats_v3 stats{};
socklen_t len = sizeof(stats);
if (::getsockopt(fd, SOL_PACKET, PACKET_STATISTICS, &stats, &len) == 0) {
    std::cout << "Прийнято пакетів: " << stats.tp_packets 
              << ", Скинуто (drops): " << stats.tp_drops << '\n';
}
```
:::

### 2. Псевдофайлова система `/proc/net/packet`

Файл `/proc/net/packet` надає інформацію про всі відкриті сокети `AF_PACKET` у системі:

```bash
cat /proc/net/packet
```

Вивід містить ідентифікатори сокетів, типи (`SOCK_RAW`), версії TPACKET (3), індекси приєднаних пристроїв та розміри виділених буферів.

## 12. Порівняльний аналіз: TPACKET_V3 vs AF_XDP vs DPDK

У сучасних високонавантажених системах використовуються три технології швидкого перехоплення трафіку:

| Критерій | PACKET_MMAP (TPACKET_V3) | AF_XDP (eXpress Data Path) | DPDK (Kernel Bypass) |
| :--- | :--- | :--- | :--- |
| **Швидкість (14.88 Mpps)** | До ~5-8 Mpps на ядро | Лінійна швидкість (14.88 Mpps) | Лінійна швидкість (14.88 Mpps) |
| **Проходження через SKB** | Часткове (створюється SKB) | Ні (обхід SKB на рівні driver) | Ні (повний обхід ядра) |
| **Сумісність із стек ядра** | Повна сумісність | Повна сумісність через BPF | Повна ізоляція NIC від ядра |
| **Необхідність спецільних драйверів** | Ні (будь-який NIC) | Потрібна підтримка XDP у драйвері | Потрібні спеціальні PMD драйвери |
| **Складність розробки** | Низька (стандартні сокети) | Середня | Дуже висока |

> 🔧 **Навіщо це.** TPACKET_V3 є золотим стандартом для більшості аналізаторів трафіку, IDS/IPS (Suricata, Snort) та утиліт моніторингу, оскільки він надає високу продуктивність без втрати сумісності зі стандартною мережевою інфраструктурою Linux. AF_XDP та DPDK застосовуються лише тоді, коли вимоги до швидкості перевищують 10 мільйонів пакетів на секунду на один потік.
