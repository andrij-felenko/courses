# API сокетів: socket, bind, listen, accept, connect та їхній зв'язок із TCP

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У цій статті ми детально розглядаємо архітектуру Socket API у Linux, зосереджуючись на тому, як кожен виклик (socket, bind, listen, accept, connect) відображається на стани протоколу TCP, зокрема під час триетапного рукостискання (3-way handshake).

## 1. Вступ до Socket API та архітектури Linux

Мережева підсистема Linux розділена на кілька рівнів абстракції. На верхньому рівні знаходиться BSD Socket API, який взаємодіє з процесами користувача. Під ним — транспортні протоколи (TCP/UDP), а ще нижче — протоколи мережевого рівня (IPv4/IPv6).

### `struct socket` проти `struct sock`

У ядрі Linux існує чіткий поділ між інтерфейсом сокета VFS (Virtual File System) та мережевим рівнем:
- **`struct socket`**: Представляє сокет на рівні BSD Socket API. Він містить інформацію, необхідну для VFS, і вказівник на `struct sock`.
- **`struct sock`**: Це нижчий рівень, який зберігає специфічну для мережевого протоколу інформацію (TCP, UDP). Для TCP ця структура розширюється до `struct tcp_sock`, яка містить таймери, вікна перевантаження, черги тощо.

## 2. Створення сокета: виклик `socket()`

Коли програма викликає `socket(AF_INET, SOCK_STREAM, 0)`, відбувається наступне:
1. Ядро виділяє новий файловий дескриптор.
2. Створюється `struct socket`.
3. Залежно від параметрів, ядро створює відповідний `struct sock` (у нашому випадку для TCP) і пов'язує його зі `struct socket`.
На цьому етапі сокет існує, але він не прив'язаний до жодного порту і не має встановленого з'єднання (стан TCP: `CLOSED`).

## 3. Прив'язка адреси: `bind()`

Виклик `bind(fd, sockaddr, len)` прив'язує `struct sock` до конкретної локальної IP-адреси та порту. Ядро перевіряє:
- Чи не зайнятий порт іншим процесом (якщо не встановлено SO_REUSEADDR/SO_REUSEPORT).
- Чи має процес права на використання порту (порти < 1024 потребують root).

## 4. Перехід у пасивний режим: `listen()`

Виклик `listen(fd, backlog)` переводить сокет у пасивний режим очікування з'єднань (TCP стан: `LISTEN`).
Тут починається магія керування чергами з'єднань. У Linux для `SOCK_STREAM` сокетів існують дві черги:
1. **SYN Backlog (черга неповних з'єднань)**: Зберігає запити, для яких отримано SYN, і ядро відповіло SYN-ACK, але фінальний ACK ще не надійшов.
2. **Accept Queue (черга повних з'єднань)**: Зберігає повністю встановлені з'єднання (отримано ACK), які очікують, поки процес викличе `accept()`.

Розмір цих черг регулюється параметром `backlog` у `listen()`, а також системними налаштуваннями (`net.ipv4.tcp_max_syn_backlog`, `net.core.somaxconn`).

## 5. Триетапне рукостискання (3-Way Handshake) та `connect()`

Клієнт ініціює з'єднання викликом `connect(fd, server_addr, len)`.

### Етап 1: Клієнт надсилає SYN
- Клієнтський `connect()` збирає пакет SYN, генерує початковий номер послідовності (ISN).
- Стан клієнта: `SYN_SENT`.
- Виклик `connect()` зазвичай блокується.

### Етап 2: Сервер отримує SYN, надсилає SYN-ACK
- Сервер отримує SYN. Якщо черга SYN Backlog не переповнена, він створює новий `request_sock` (мінімальну структуру) і додає його до SYN Backlog.
- Сервер надсилає SYN-ACK клієнту.
- Стан на сервері для цього з'єднання: `SYN_RECV`.

### Етап 3: Клієнт отримує SYN-ACK, надсилає ACK
- Клієнт отримує SYN-ACK, надсилає ACK.
- Стан клієнта: `ESTABLISHED`. Виклик `connect()` успішно повертається.

### Етап 4: Сервер отримує ACK
- Сервер отримує ACK. Ядро знаходить `request_sock` у SYN Backlog.
- Створюється повноцінний новий `struct sock` (і `struct tcp_sock`).
- З'єднання переміщується з SYN Backlog до Accept Queue.
- Стан на сервері: `ESTABLISHED`.

## 6. Прийняття з'єднання: `accept()`

Виклик `accept(fd, client_addr, len)` не бере участі в рукостисканні протоколу TCP безпосередньо. Його єдине завдання — витягти перше готове з'єднання з Accept Queue.
- Якщо Accept Queue порожня, `accept()` блокується (або повертає EAGAIN для неблокувальних сокетів).
- Якщо з'єднання є, `accept()` створює для нього новий файловий дескриптор і новий `struct socket` (який вказує на вже створений `struct sock`).
- Оригінальний сокет продовжує перебувати у стані `LISTEN`.

## Висновки

Socket API надає зручну абстракцію над складними механізмами TCP. Розуміння зв'язку між викликами `listen`, `connect`, `accept` та внутрішніми чергами ядра (SYN Backlog, Accept Queue), а також структурою `struct socket`/`struct sock`, є критично важливим для написання високопродуктивних мережевих серверів і налаштування ядра Linux для високих навантажень.
