# 📜 Від BSD Sockets 4.2BSD до мережевого стеку Linux

Перехід від локального файлового введення-виведення Unix до динамічних мережевих з'єднань вимагав кардинального перегляду фундаментальної концепції файлового дескриптора. У той час як класичні файли, дискові пристрої та безадресні канали (pipes) обслуговувалися єдиним лінійним потоком байтів на основі імен у файловій системі, мережевий зв'язок вимагав динамічного встановлення кінцевих точок, керування складними автоматами станів з'єднання, вибору транспортних протоколів та обробки позасмугових даних. Мережевий шар сокетів (BSD Socket API), розроблений у 1983 році для системи 4.2BSD, став універсальним стандартом, що поєднав таблицю дескрипторів процесу з мережевим стеком, а його наступна адаптація та глибока переробка у ядрі Linux створила один із найшвидших та найпродуктивніших мережевих стеків у сучасній індустрії.

## Виклики UNIX-парадигми та народження BSD Sockets

На початку 1980-х років Агентство передових оборонних дослідницьких проєктів США (DARPA) уклало контракт із Центром дослідження комп'ютерних систем (CSRG) у Каліфорнійському університеті в Берклі для інтеграції стеків ARPANET та TCP/IP у систему UNIX. Розробники на чолі з Біллом Джоєм (Bill Joy), Семом Леффлером (Sam Leffler) та Робом Гурвіцем (Rob Gurwitz) зіткнулися з фундаментальним обмеженням архітектури.

Засадничий принцип Unix — «усе є файлом» (Everything is a file) — ідеально працював для статичних носіїв та послідовних пристроїв. Для відкриття файлу програма викликала системний виклик `open("/var/log/messages", O_RDONLY)`, передаючи шлях у дереві каталогів. Однак для мережевого з'єднання на момент створення дескриптора жодного шляху у файловій системі не існує і бути не може. Для зв'язку потрібно було вказати цілу масу параметрів: локальну IP-адресу, віддалену IP-адресу, локальний порт, віддалений порт, сімейство адрес (IPv4 або Unix Domain) та конкретний транспортний протокол (гарантований потік TCP або датаграми UDP).

Крім того, мережеве з'єднання на відміну від файлу на диску має динамічний життєвий цикл. Звичайний файл відкривається миттєво, його вміст лежить на диску й чекає на зсув `f_pos`. Мережеве з'єднання TCP вимагає проходження триетапного рукостискання (3-way handshake), переходу через серію внутрішньоядерних станів (`LISTEN`, `SYN_SENT`, `SYN_RECV`, `ESTABLISHED`), обробки втрат пакетів та відстеження вікон перевантаження.

Група розробників з Берклі ухвалила рішення створити нову високорівневу абстракцію — **сокет** (BSD Socket). Замість перевантаження синтаксису системного виклику `open()` додатковими складними аргументами або створення штучних псевдофайлів для кожної IP-адреси, вони вплекли новий системний виклик `socket()`, який повертав стандартний файловий дескриптор. Для налаштування параметрів мережевої адресації, прив'язки портів та слухання підключень було розроблено окрему групу мережевих дієслів: `bind()`, `listen()`, `accept()`, `connect()`, `getsockname()`, `getpeername()`. Це дозволило зберегти єдині базові інструменти для читання та запису даних (`read()`, `write()`, `select()`), відокремивши фазу встановлення з'єднання та налаштування протоколу у спеціалізоване підсистему API.

## Еволюція мережі в Linux: від перших латок NET-1 до стабільності NET-3

Коли Лінус Торвальдс у 1991 році опублікував перші версії ядра Linux, у ньому повністю був відсутній мережевий стек. Першу базову реалізацію TCP/IP для Linux, відому як **NET-1**, створив Росс Біро (Ross Biro) у 1992–1993 роках. Вона була написана практично з нуля на основі специфікацій RFC та опису BSD API. Однак ця первинна версія була нестабільною, не мала належного кешування маршрутів і часто спричиняла взаємні блокування ядра (deadlocks) під час високого навантаження.

Для виправлення ситуації Фред ван Кемпен (Fred van Kempen) розпочав масштабну переробку під назвою **NET-2**, але справжній архітектурний прорив відбувся у 1994–1996 роках, коли провідним архітектором мережевої підсистеми став Алан Кокс (Alan Cox). У версіях ядра Linux 1.2 та 2.0 Алан Кокс переписав мережевий стек у підсистему **NET-3**.

Саме під час розробки NET-3 було закладено фундаментальне розділення об'єкта сокета в ядрі Linux на два чіткі шари:

1. **`struct socket` (VFS Socket Interface)**: Легковаговий шар, який безпосередньо зв'язаний із VFS та таблицею файлових дескрипторів процесу. Він зберігає прапорці стану сокета, вказівник на таблицю високорівневих операцій `proto_ops` та черги очікування `socket_wq` для системних викликів `poll()`, `select()` та `epoll()`.
2. **`struct sock` (Protocol Engine)**: Нижній мережевий шар ядра, повністю ізольований від VFS. Він містить черги мережевих буферів кадрів (`sk_buff`), таймери повторної відправки пакетів, лічильники вікон перевантаження, параметри алгоритмів TCP та стан автомата станів.

Це архітектурне розділення дозволило ядру Linux відокремити файлові операції користувацького простору від складних обчислень транспортного та мережевого рівнів, забезпечивши високу модульність та можливість підключення нових сімейств протоколів (`AF_INET6`, `AF_PACKET`, `AF_BLUETOOTH`, `AF_XDP`) без зміни коду VFS.

## Революція Олексія Кузнєцова та боротьба із мережевими атаками

З випуском ядер Linux 2.2 та 2.4 (1999–2001 роки) мережевий стек зазнав повторної глибокої реорганізації під керівництвом Олексія Кузнєцова. Його внесок перетворив Linux із любительської операційної системи на потужну платформу для високопродуктивних мережевих серверів та маршрутизаторів. Олексій Кузнєцов повністю переписав підсистему маршрутизації, створив підсистему керування трафіком (Traffic Control / `tc`), впровадив таблиці балансування та оптимізував внутрішньоядерні черги пакетів.

Важливим випробуванням для мережевого стеку стала поява нової масової загрози в Інтернеті у вересні 1996 року. У хакерському журналі Phrack 48 було опубліковано статтю із детальним описом атаки **SYN Flood** (затоплення серверами запитами на з'єднання). Класична модель BSD Sockets мала єдину чергу `backlog` для сокета у стані `LISTEN`. Коли нападник надсилав тисячі фейкових пакетів SYN із підробленими IP-адресами відправника, ця черга за декілька мілісекунд заповнювалася з'єднаннями у стані `SYN_RECV`. Сервер чекав на фінальні пакети ACK від адрес, яких не існувало, і легітимні користувачі не могли встановити жодного нового з'єднання.

Розробники ядра Linux відповіли на цю загрозу двома фундаментальними реформами:

- **Розділення черг на двочергову модель**: У Linux 2.2 було впроваджено окремі черги для слухаючого сокета. Замість єдиного списку з'явилися **SYN Backlog** (черга неповних з'єднань у стані `SYN_RECV` на основі компактних об'єктів `request_sock`) та **Accept Queue** (черга повністю готових з'єднань у стані `ESTABLISHED`). Заповнення черги незавершених рукостискань більше не перешкоджало викликам `accept()` для вже готових з'єднань.
- **Винахід та впровадження SYN Cookies**: Ден Бернштейн (Dan Bernstein) та Ерік Шенк (Eric Schenk) розробили механізм `tcp_syncookies`. При повній переповненості черги SYN Backlog ядро взагалі припиняє виділяти пам'ять під `request_sock`. Замість цього ядро обчислює криптографічний масив (Cookie) на основі IP-адрес, портів, таємного ключа ядра та лічильника часу, і записує його у початковий номер послідовності (ISN) у пакеті SYN-ACK. Коли від легітимного клієнта повертається підтвердження ACK, ядро вираховує зворотний хеш і створює повноцінне з'єднання «на льоту» без зберігання стану між кроками.

## Сучасний стан та спадковість BSD API

У сучасних версіях Linux мережевий стек продовжує постійно вдосконалюватися. Впровадження підсистеми NAPI (New API) дозволило об'єднати переривання від мережевих карт із періодичним опитуванням (polling), знижуючи навантаження на процесор при мільйонах пакетів на секунду. Інструменти eBPF (Extended Berkeley Packet Filter), `XDP` (eXpress Data Path) та асинхронне введення-виведення `io_uring` дозволяють обробляти пакети ще до їх потрапляння у класичний стек сокетів.

Попри ці вражаючі технологічні зміни, фундаментальні принципи розмежування шарів `struct socket` та `struct sock`, а також семантика викликів BSD Socket API (`socket`, `bind`, `listen`, `accept`, `connect`), розроблена в Каліфорнійському університеті Берклі понад 40 років тому, залишається незмінною поверхнею взаємодії між програмами користувача та ядром Linux.
