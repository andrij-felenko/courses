Уявіть ситуацію: вам потрібно миттєво дізнатися про підключення нового мережевого кабелю або зміну таблиці маршрутизації в Linux. Старі методи, такі як ioctl() для налаштування пристроїв або читання файлів з /proc, є повільними, незграбними та працюють за принципом "опитування" (polling). Вони не масштабуються і не можуть забезпечити асинхронні сповіщення від ядра до застосунку. Тут на сцену виходить **Netlink** – потужний механізм міжпроцесної взаємодії (IPC), створений спеціально для зв'язку між ядром Linux та програмами у просторі користувача.

## Що таке Netlink?

Netlink – це сімейство сокетів (`AF_NETLINK`), яке надає двонаправлений канал зв'язку на основі дейтаграм. На відміну від системних викликів, які є суворо синхронними (процес користувача викликає ядро і чекає), Netlink дозволяє ядру ініціювати відправку повідомлень у простір користувача. Це робить його ідеальним для асинхронних подій, таких як зміни в конфігурації мережі, оновлення правил брандмауера (netfilter) або події гарячого підключення пристроїв (uevent).

Спочатку Netlink створювався для заміни незручних `ioctl` для налаштування мережі, звідки й походить його назва (Network Link). Але з часом він став стандартом де-факто для багатьох інших підсистем ядра (наприклад, аудиту, SELinux, квотування, тощо).

### Основні переваги Netlink:
1. **Двонаправленість**: Як користувацький простір може запитувати ядро, так і ядро може надсилати повідомлення (мультикаст або юнікаст) користувачеві.
2. **Асинхронність**: Ядро може повідомляти процеси про події в міру їх виникнення, без необхідності періодичного опитування (polling).
3. **Стандартний API сокетів**: Розробникам не потрібно вчити нові парадигми; вони використовують знайомі функції `socket()`, `bind()`, `sendmsg()`, `recvmsg()`, `poll()`, та `select()`.
4. **Підтримка мультикасту**: Ядро може транслювати повідомлення (наприклад, "інтерфейс eth0 піднято") одночасно багатьом зацікавленим слухачам.

## Створення сокета Netlink

Як і для будь-якого мережевого програмування, все починається з виклику `socket()`:

```c
#include <asm/types.h>
#include <sys/socket.h>
#include <linux/netlink.h>

int sock_fd = socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE);
```

- **Домен (`domain`)**: `AF_NETLINK` (або `PF_NETLINK`), що вказує на сімейство сокетів Netlink.
- **Тип (`type`)**: `SOCK_RAW` (або `SOCK_DGRAM`). Netlink базується на дейтаграмах. Повідомлення не фрагментуються і доставляються як цілісні пакети.
- **Протокол (`protocol`)**: Вказує на конкретну підсистему ядра, з якою ви хочете спілкуватися. `NETLINK_ROUTE` використовується для мережевої конфігурації (маршрутизація, інтерфейси, IP-адреси). Інші популярні протоколи включають:
  - `NETLINK_GENERIC`: Сучасний "загальний" механізм для створення власних каналів без необхідності додавати нові константи `NETLINK_*` у ядро.
  - `NETLINK_KOBJECT_UEVENT`: Для сповіщень про зміни в обладнанні (використовується udev).
  - `NETLINK_AUDIT`: Для підсистеми аудиту ядра.
  - `NETLINK_NETFILTER`: Для взаємодії з iptables/nftables.

## Формат повідомлень: nlmsghdr

Усі повідомлення Netlink (як до ядра, так і від ядра) повинні починатися зі стандартного заголовка `struct nlmsghdr`, який визначено в `<linux/netlink.h>`:

```c
struct nlmsghdr {
    __u32 nlmsg_len;   /* Довжина повідомлення включаючи заголовок */
    __u16 nlmsg_type;  /* Тип вмісту повідомлення */
    __u16 nlmsg_flags; /* Додаткові прапорці */
    __u32 nlmsg_seq;   /* Номер послідовності (Sequence number) */
    __u32 nlmsg_pid;   /* ID порту відправника (зазвичай PID процесу) */
};
```

Після цього заголовка йде безпосереднє "корисне навантаження" (payload). Оскільки Netlink повідомлення можуть об'єднуватися в один пакет (для ефективності), існують спеціальні макроси для безпечного і правильного обходу цих повідомлень (вирівнювання тощо):
- `NLMSG_ALIGN(len)`: Вирівнює довжину до наступної межі `NLMSG_ALIGNTO` (зазвичай 4 байти).
- `NLMSG_LENGTH(len)`: Розраховує загальну довжину повідомлення, включаючи заголовок, на основі довжини корисного навантаження.
- `NLMSG_SPACE(len)`: Те ж саме, що й вище, але з вирівнюванням.
- `NLMSG_DATA(nlh)`: Повертає вказівник на корисне навантаження повідомлення.
- `NLMSG_NEXT(nlh, len)`: Переходить до наступного повідомлення в буфері.

### Типи повідомлень (`nlmsg_type`)
Netlink визначає кілька стандартних типів повідомлень для керування:
- `NLMSG_NOOP`: Повідомлення не несе корисного навантаження, його слід проігнорувати.
- `NLMSG_ERROR`: Вказує на помилку. Навантаження містить `struct nlmsgerr`.
- `NLMSG_DONE`: Завершує послідовність повідомлень, що складається з кількох частин (multipart message).
- `NLMSG_OVERRUN`: Сповіщення про втрату даних (буфер переповнено).

Інші типи специфічні для обраного протоколу (наприклад, `RTM_NEWLINK` для `NETLINK_ROUTE`).

### Прапорці (`nlmsg_flags`)
Найважливіші прапорці для запитів (Request flags):
- `NLM_F_REQUEST`: Вказує, що це повідомлення є запитом.
- `NLM_F_MULTI`: Вказує, що відповідь буде складатися з кількох повідомлень (multipart), останнє з яких буде `NLMSG_DONE`.
- `NLM_F_ACK`: Просить ядро надіслати повідомлення підтвердження (ACK).
- `NLM_F_ECHO`: Просить ядро повернути цей самий запит усім слухачам.
- `NLM_F_ROOT` та `NLM_F_MATCH` (зазвичай комбінуються як `NLM_F_DUMP`): Просять ядро вивантажити (dump) всю таблицю (наприклад, усі інтерфейси).

## Прив'язка (Binding) сокета

Щоб отримувати мультикаст-повідомлення (наприклад, сповіщення про зміну стану лінку), сокет потрібно "прив'язати" до певної адреси. У світі Netlink адресою є `struct sockaddr_nl`:

```c
struct sockaddr_nl src_addr;
memset(&src_addr, 0, sizeof(src_addr));
src_addr.nl_family = AF_NETLINK;
src_addr.nl_pid = getpid(); /* Або 0, тоді ядро призначить автоматично */
src_addr.nl_groups = RTMGRP_LINK | RTMGRP_IPV4_IFADDR; /* Мультикаст групи */

bind(sock_fd, (struct sockaddr*)&src_addr, sizeof(src_addr));
```

- `nl_pid`: Унікальний ідентифікатор порту для цього сокета. Часто використовують PID процесу, але в багатопотокових програмах він має бути унікальним для кожного потоку. Сучасна рекомендація – залишати 0 при виклику `bind()`, дозволяючи ядру самому вибрати унікальний ID.
- `nl_groups`: Бітова маска (або масив для сучасних ядер), що вказує, на які мультикаст-повідомлення підписується процес. Наприклад, `RTMGRP_LINK` для подій про мережеві інтерфейси (up/down/додавання).

## Приклад: Отримання списку мережевих інтерфейсів (rtnetlink)

rtnetlink (`NETLINK_ROUTE`) – це сімейство повідомлень для конфігурації мережевого стеку. Воно замінило старі ioctl.

Щоб отримати список інтерфейсів, нам потрібно надіслати запит `RTM_GETLINK` з прапорцем `NLM_F_DUMP`.

### Формування та відправка запиту

Корисне навантаження для `RTM_GETLINK` – це структура `ifinfomsg`.

```c
struct {
    struct nlmsghdr nlh;
    struct ifinfomsg ifi;
} req;

memset(&req, 0, sizeof(req));
req.nlh.nlmsg_len = NLMSG_LENGTH(sizeof(struct ifinfomsg));
req.nlh.nlmsg_type = RTM_GETLINK;
req.nlh.nlmsg_flags = NLM_F_REQUEST | NLM_F_DUMP;
req.nlh.nlmsg_seq = 1;
req.nlh.nlmsg_pid = getpid();

req.ifi.ifi_family = AF_UNSPEC; /* Усі сімейства */

struct sockaddr_nl dest_addr;
memset(&dest_addr, 0, sizeof(dest_addr));
dest_addr.nl_family = AF_NETLINK;
dest_addr.nl_pid = 0; /* 0 означає ядро */
dest_addr.nl_groups = 0; /* Юнікаст до ядра */

struct iovec iov = { (void *)&req, req.nlh.nlmsg_len };
struct msghdr msg = {
    .msg_name = (void *)&dest_addr,
    .msg_namelen = sizeof(dest_addr),
    .msg_iov = &iov,
    .msg_iovlen = 1,
};

sendmsg(sock_fd, &msg, 0);
```

### Обробка відповіді (TLVs / Attributes)

Відповідь ядра на `NLM_F_DUMP` зазвичай складається з кількох дейтаграм, кожна з яких може містити кілька структур `nlmsghdr`. Дані зазвичай структуровані у форматі Type-Length-Value (TLV), які в Netlink називаються "атрибутами" (`struct rtattr` або `struct nlattr`).

Макроси для роботи з атрибутами:
- `RTA_ALIGN`, `RTA_LENGTH`, `RTA_PAYLOAD`, `RTA_DATA`, `RTA_NEXT`. Вони працюють аналогічно до `NLMSG_*`, але для `struct rtattr`.

Цикл читання виглядатиме приблизно так:

```c
char buf[8192];
struct iovec iov = { buf, sizeof(buf) };
struct msghdr msg = { .msg_iov = &iov, .msg_iovlen = 1 };

while (1) {
    int len = recvmsg(sock_fd, &msg, 0);
    if (len < 0) break; // Помилка

    struct nlmsghdr *nlh = (struct nlmsghdr *)buf;
    for (; NLMSG_OK(nlh, len); nlh = NLMSG_NEXT(nlh, len)) {
        if (nlh->nlmsg_type == NLMSG_DONE) {
            return; /* Усі дані отримано */
        }
        if (nlh->nlmsg_type == NLMSG_ERROR) {
            /* Обробка помилки */
            return;
        }
        
        if (nlh->nlmsg_type == RTM_NEWLINK) {
            struct ifinfomsg *ifi = NLMSG_DATA(nlh);
            /* Атрибути знаходяться одразу після ifinfomsg */
            struct rtattr *rta = IFLA_RTA(ifi);
            int rta_len = IFLA_PAYLOAD(nlh);

            for (; RTA_OK(rta, rta_len); rta = RTA_NEXT(rta, rta_len)) {
                if (rta->rta_type == IFLA_IFNAME) {
                    printf("Found interface: %s\n", (char *)RTA_DATA(rta));
                }
            }
        }
    }
}
```

Цей "сирий" код виглядає досить громіздко, багатослівним і схильним до помилок. Треба пам'ятати про макроси вирівнювання, перевіряти розміри, щоб не вийти за межі буфера тощо.

## Бібліотеки вищого рівня: libnl

Оскільки робота з сирими сокетами Netlink вимагає написання великої кількості стереотипного (boilerplate) коду, для спрощення розробки були створені бібліотеки. Найпопулярнішою в середовищі C/C++ є сімейство бібліотек `libnl` (libnl-3, libnl-genl, libnl-route).

Бібліотека `libnl` бере на себе:
- Управління сокетами (`nl_socket_alloc()`, `nl_connect()`).
- Формування заголовків та управління Sequence Numbers.
- Форматування атрибутів TLV (вкладені атрибути, типи даних).
- Реєстрацію callback-функцій для обробки вхідних повідомлень.

### Приклад з libnl (Generic Netlink)

Generic Netlink (`NETLINK_GENERIC`) дозволяє розробникам ядра створювати нові API для Netlink без виділення нового номера `AF_NETLINK` (яких обмежена кількість, лише 32). Замість цього вони реєструють "сімейство" (family) за його ім'ям (рядок), а користувацький простір запитує ідентифікатор цього сімейства за ім'ям (через контролер Generic Netlink `nlctrl`).

Ось базовий каркас з використанням `libnl`:

```c
#include <netlink/netlink.h>
#include <netlink/genl/genl.h>
#include <netlink/genl/ctrl.h>

int main() {
    struct nl_sock *sock;
    int family_id;

    // 1. Алокація сокета
    sock = nl_socket_alloc();
    if (!sock) return -1;

    // 2. Підключення до Generic Netlink
    if (genl_connect(sock) < 0) {
        nl_socket_free(sock);
        return -1;
    }

    // 3. Пошук ID сімейства за його назвою (наприклад, "nl80211" для Wi-Fi)
    family_id = genl_ctrl_resolve(sock, "nl80211");
    if (family_id < 0) {
        printf("Family not found\n");
        nl_close(sock);
        nl_socket_free(sock);
        return -1;
    }

    printf("Resolved generic family ID: %d\n", family_id);

    // Далі йде формування повідомлень за допомогою nlmsg_alloc(), 
    // genlmsg_put(), nla_put_*(), nl_send_auto() та встановлення callbacks.

    nl_close(sock);
    nl_socket_free(sock);
    return 0;
}
```

Використання `libnl` є стандартом для сучасних програм у Linux (наприклад, `iproute2` здебільшого перейшов на libnl або аналогічні власні обгортки, NetworkManager, wpa_supplicant активно використовують libnl).

## Розширені можливості та підводні камені

- **Strict Checking (Сувора перевірка)**: У сучасних ядрах додано `NETLINK_GET_STRICT_CHK` (і відповідні прапорці). Якщо раніше ядро ігнорувало невідомі атрибути в запитах просто повертаючи всі дані (dump), то тепер можна просити ядро суворо фільтрувати вивід ще на етапі запиту, що різко зменшує обсяг даних, які пересилаються в простір користувача.
- **Розмір буфера приймання (SO_RCVBUF)**: При отриманні DUMP-відповідей або швидкого потоку подій, дефолтний розмір буфера сокета може бути замалим, що призведе до помилок `ENOBUFS`. Часто доводиться викликати `setsockopt` з `SO_RCVBUF`, збільшуючи його до кількох мегабайт.
- **Багатопоточність**: Не використовуйте один і той же сокет Netlink у кількох потоках одночасно без м'ютексів. sequence numbers і PID можуть заплутатися, і `recvmsg()` може прочитати відповідь, призначену для іншого потоку. Краще відкривати окремий сокет (з унікальним `nl_pid`!) для кожного потоку.

## Підсумок

Netlink — це кровоносна система конфігурації Linux, яка витіснила застарілі `ioctl` та файли в `/proc`. Хоча сирий API на мові C вимагає уважного ставлення до вирівнювання пам'яті та роботи з макросами, він забезпечує потужну, ефективну та асинхронну взаємодію з ядром. Знання Netlink є обов'язковим для будь-якого розробника системного рівня, який створює мережеві інструменти, демони моніторингу або конфігуратори в Linux.
