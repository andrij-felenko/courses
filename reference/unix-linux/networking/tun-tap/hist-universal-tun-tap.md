# 📜 Історія універсального драйвера TUN/TAP: від VTun до ядра Linux

Універсальний драйвер TUN/TAP з'явився в ядрі Linux як відповідь на хаос і фрагментацію віртуальних мережевих інтерфейсів наприкінці 1990-х років. До появи єдиного символьного пристрою `/dev/net/tun` розробники VPN, тунелів та емуляторів мережі були змушені підтримувати окремі несумісні драйвери для кожної операційної системи або писати власний код ядра.

## Передумови та фрагментація у 1990-х роках

Наприкінці 1990-х років корпоративні та приватні мережі зіткнулися з потребою захищеного з'єднання через публічний Інтернет. BSD-системні операційні середовища (FreeBSD, OpenBSD) мали пристрій `tun` (наприклад, `/dev/tun0`, `/dev/tun1`), який працював на мережевому рівні L3. У Solaris був доступний пристрій `ip.tun`.

У ядрах Linux серії 2.2 існував драйвер `ethertap` (`/dev/tap0`, `/dev/tap1`), який емулював Ethernet-пристрій L2. Проте кожен такий пристрій вимагав власного статичного вузла в системі файлів `/dev` та окремого запиту `open()` на конкретний пристрій (`tap0`, `tap1` і далі). Якщо додаток бажав створити віртуальний інтерфейс, він повинен був послідовно опитувати `/dev/tap0`, `/dev/tap1`, доки не знайде невідкритий файловий дескриптор.

Це створювало кілька проблем:
1. **Обмежена масштабованість:** кількість віртуальних інтерфейсів жорстко обмежувалася кількістю попередньо створених вузлів `/dev`.
2. **Розділення L2 та L3:** розробники мусили використовувати різні API для мережевих пакетів IP та Ethernet-кадрів.
3. **Відсутність єдиної системи прав:** керування доступом до кожного вузла пристрою вимагало окремих прав на рівні файлової системи POSIX.

## Проєкт VTun та розробка Максима Краснянського

У 1999–2000 роках Максим Краснянський (Maxim Krasnyansky) разом із колегами розробляв проєкт **VTun** (Virtual Tunnels) — один із перших відкритих програмних комплексів для організації шифрованих тунелів у Linux. Під час роботи над VTun Краснянський усвідомив, що наявний у Linux 2.2 драйвер `ethertap` має суттєві вади продуктивності й архітектури.

Замість створення окремих вузлів для кожного інтерфейсу Краснянський запропонував концепцію **універсального мультиплексора TUN/TAP** (Universal TUN/TAP driver). Основна ідея полягала у введенні єдиної точки входу — символьного пристрою `/dev/net/tun`.

Процес користувача відкриває цей пристрій один раз і через виклики `ioctl` із структурою `ifreq` динамічно запитує в ядра створення інтерфейсу потрібного типу (L3 `IFF_TUN` або L2 `IFF_TAP`) з довільним ім'ям.

## Інтеграція в ядро Linux 2.4

У 2000 році Максим Краснянський випустив першу версію універсального драйвера TUN/TAP для серії ядер Linux 2.4. Драйвер вирізнявся кількома засадничими нововведеннями:

- **Динамічний розподіл:** ядро автоматично створювало мережевий об'єкт `struct net_device` під час виклику `ioctl(fd, TUNSETIFF, ...)`, усуваючи потребу у статичних вузлах `/dev/tunX`.
- **Єдине API:** для L3 і L2 використовувався однаковий механізм системних викликів `read()` та `write()`.
- **Своєрідність володіння (Persistence):** можливість за допомогою `TUNSETPERSIST` залишати віртуальний інтерфейс у системі навіть після закриття файлового дескриптора користувацького процесу.

Універсальний драйвер було прийнято до основного дерева ядра Linux (mainline kernel) у версії 2.4.0 (січень 2001 року). Відтоді архітектура `/dev/net/tun` стала стандартом де-факто для створення користувацьких мережевих інтерфейсів у Linux та була згодом портована або імітована в інших Unix-подібних ОС (включаючи macOS через `tuntaposx` та FreeBSD через модуль `if_tuntap`).

## Прийняття екосистемою: OpenVPN, QEMU та KVM

Поява узагальненого пристрою `/dev/net/tun` у ядрі Linux 2.4 створила міцний фундамент для швидкого розвитку мережевого програмного забезпечення з відкритим кодом у 2000-х роках:

- **OpenVPN (2001):** Джеймс Йонан (James Yonan) побудував OpenVPN навколо архітектури TUN/TAP. Завдяки режиму `dev tun` OpenVPN забезпечив створення гнучких маршрутизованих VPN-мереж поверх UDP та TCP, а режим `dev tap` дозволив прозоро об'єднувати віддалені офіси у спільні L2-сегменти.
- **QEMU та KVM (2003–2007):** Фабріс Беллар (Fabrice Bellard) включив підтримку TAP-пристроїв у гіпервізор QEMU. З появою KVM (Kernel-based Virtual Machine) під проводом Аві Ківіті (Avi Kivity) пристрої TAP стали стандартним інструментом з'єднання віртуальних машин з мережевими мостами хоста.
- **User-Mode Linux (UML):** Один із перших проєктів віртуалізації в ядрі Linux активно застосовував TUN/TAP для надання мережевого доступу віртуалізованим процесам ядра.

## Еволюція: мультичерги та розвантаження

З ростом швидкостей мережевих каналів до 10G+ та появою багатоядерних систем класичний драйвер TUN/TAP зіткнувся з пляшковим горлом: один файловий дескриптор обслуговувався одним потоком, що спричиняло блокування замок (locks) у ядрі.

У 2012–2013 роках у ядрах Linux 3.8+ розробники з Red Hat (зокрема Jason Wang) запровадили підтримку **Multi-Queue TUN/TAP** (`IFF_MULTI_QUEUE`). Це дозволило прив'язувати кілька файлових дескрипторів до одного віртуального мережевого пристрою `tun0` чи `tap0`, паралелізуючи прийом та відправку пакетів між різними ядрами ЦП.

Сьогодні універсальний драйвер TUN/TAP є фундаментальною цеглиною технологій OpenVPN, QEMU/KVM, User-Mode Linux, Android VPN API та контейнерних мережевих плагінів (CNI).

## Від TUN/TAP до вбудованих ядерних тунелів та eBPF

Незважаючи на тривалу домінуючу роль TUN/TAP, перехід програмного забезпечення в просторі користувача змушував кожний пакет долати бар'єр системних викликів, викликаючи перемикання контексту ЦП (context switch) та копіювання даних у пам'яті.

Наприкінці 2010-х років це стимулювало створення нових підходів:
- **Вбудовані тунелі в ядрі (WireGuard):** Джейсон Доненфельд (Jason A. Donenfeld) створив протокол WireGuard, реалізувавши його безпосередньо у просторі ядра як модуль Linux 5.6 (2020 рік). Це усунуло накладні витрати `/dev/net/tun` для міжвузлових VPN.
- **eBPF та Express Data Path (XDP):** Використання AF_XDP та програм eBPF дозволяє обробляти та впорскувати пакети на рівні мережевої карти без копіювання буферів у простір користувача.

Тим не менш, завдяки своїй універсальності, простоті POSIX-інтерфейсу та відсутності потреби правити ядро, драйвер `/dev/net/tun` залишається золотим стандартом для розробки нових мережевих протоколів та систем віртуалізації.
