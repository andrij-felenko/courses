# 📜 Еволюція Linux Bridge: від brctl до VLAN-filtering та Switchdev

Розуміння історичного шляху підсистеми мостів у Linux пояснює, чому в сучасному ядрі співіснують інтерфейси ioctl, sysfs та Netlink, а також чому архітектура пройшла шлях від простого емулятора апаратного хабу до повноцінного Control Plane для комутаторів центрів обробки даних.

## Поява програмного комутатора: епоха Linux 2.2 та 2.4

Наприкінці 1990-х років об'єднання декількох фізичних сегментів Ethernet в один колізійний або широкомовний домен на базі ПК вимагало використання спеціалізованих апаратних комутаторів або пропрієтарних платформ. У 1999–2000 роках розробники Алан Кокс (Alan Cox) та Леннерт Буйтенгек (Lennert Buytenhek) інтегрували в ядро Linux першу повноцінну реалізацію стандарту IEEE 802.1D.

Початкова реалізація моста (модуль `bridge.o` у ядрі 2.2/2.4) створювала віртуальний мережевий пристрій, який переводив підпорядковані фізичні інтерфейси в нерозбірливий режим (promiscuous mode) і перехоплював кожен вхідний пакет на канальному рівні (L2). Управління цим пристроєм здійснювалося через набір системних викликів `ioctl()` із сімейства `SIOCGIFBR` та `SIOCSIFBR`, а користувацьким інструментом став пакет `bridge-utils` із його центральною утилітою `brctl`.

```
+-------------------------------------------------------------+
|  User Space: brctl (SIOCBRADDBR, SIOCBRADDIF via ioctl)     |
+-------------------------------------------------------------+
                              | ioctl
+-------------------------------------------------------------+
|  Kernel 2.4: net/bridge/br.c (promisc mode, global lock)    |
|  Вбудований STP 802.1D (ядро самостійно надсилає BPDU)     |
+-------------------------------------------------------------+
```

Така конструкція мала дві фундаментальні проблеми:
1. **Синхронний повільний інтерфейс ioctl**: передача складних структур конфігурації (наприклад, дампу всієї таблиці комутації FDB) через сокетні виклики `ioctl` призводила до блокування пам'яті ядра та неефективного копіювання буферів.
2. **STP у просторі ядра**: алгоритм Spanning Tree Protocol (IEEE 802.1D) було закодовано безпосередньо в коді ядра. Ядро самостійно генерувало та парсило кадри BPDU (Bridge Protocol Data Units). Це унеможливлювало швидке впровадження нових стандартів, таких як RSTP (Rapid STP, 802.1w) чи MSTP (Multiple STP, 802.1s), оскільки будь-яка модифікація таймерів вимагала перекомпіляції ядра.

## Перехід до sysfs та криза багатьох мостів

З виходом ядра Linux 2.6 мережевий стек зазнав масштабної перебудови. Інтерфейс `ioctl` для налаштування мостів було заморожено, а параметри комутатора експортовано у віртуальну файлову систему `sysfs` за шляхом `/sys/class/net/<brname>/bridge/` та `/sys/class/net/<brname>/brif/<portname>/`.

У цей же період відбувся бурхливий розвиток серверної віртуалізації (Xen, KVM/QEMU) та контейнеризації (OpenVZ, LXC). Кожна віртуальна машина потребувала ізоляції у власному сегменті VLAN (IEEE 802.1Q). Оскільки ядровий міст на той час не вміти фільтрувати VLAN всередині одного екземпляра `net_bridge`, інженерам доводилося будувати багаторівневі каскадні конструкції:

```
[ eth0 ] -> eth0.10 (VLAN sub-interface) -> [ br10 ] -> tap0 (VM1)
         -> eth0.20 (VLAN sub-interface) -> [ br20 ] -> tap1 (VM2)
         -> eth0.30 (VLAN sub-interface) -> [ br30 ] -> tap2 (VM3)
```

Для системи з сотнями віртуальних машин і десятками VLAN це створювало катастрофічні наслідки:
- Ядро витрачало терабайти пам'яті на підтримку тисяч віртуальних `struct net_device`;
- Шлях пакета через вкладені мости багаторазово перетинав черги `netif_receive_skb()`, викликаючи кеш-промахи процесора (CPU cache trashing);
- Масштабованість комутації деградувала в геометричній прогресії через блокування спільних локів підсистеми моста.

## Революція VLAN Filtering (Linux 3.8+)

У 2013 році інженери компанії Cumulus Networks (зокрема Рупа Прабху — Roopa Prabhu) та Стівен Хеммінгер (Stephen Hemminger) реалізували фундаментальний патч, що додав у ядро механізм **VLAN Filtering** (`CONFIG_BRIDGE_VLAN_FILTERING`).

Замість створення окремого моста під кожен VLAN ядро Linux навчилося обробляти теги IEEE 802.1Q всередині єдиного моста так само, як це роблять апаратні комутатори (Enterprise Switches). Кожен порт отримав поняття:
- **PVID (Port VLAN ID)**: тег за замовчуванням для нетегованих вхідних кадрів (Access port);
- **Egress Untagged / Tagged**: правила модифікації заголовка 802.1Q при виході кадру з порту.

Таблиця FDB стала двовимірною: адресація здійснюється за парою `{MAC-адреса, VLAN ID}`. Це усунуло тисячі проміжних віртуальних інтерфейсів `brX` та `eth0.X`, скоротивши накладні витрати CPU у віртуалізованих середовищах на 40–60%.

Одночасно відбувся остаточний перехід від пакета `bridge-utils` до сучасного інструменту `bridge` з пакета `iproute2`, що взаємодіє з ядром виключно через високоефективний протокол `rtnetlink` (повідомлення `RTM_NEWLINK`, `RTM_NEWNEIGH`, `RTM_GETNEIGH`).

## Простір користувача для STP/RSTP: поява mstpd

Для вирішення проблеми застарілого ядрового STP у ядрі 2.6.28 було впроваджено механізм перехоплення BPDU простором користувача (`/sys/class/net/<br>/bridge/stp_state 2`). Це дозволило перенести складну логіку обчислення топології дерева (RSTP 802.1w, MSTP 802.1s) у простір користувача — зокрема в демон `mstpd`.

Ядро зберегло за собою лише виконання базових інструкцій: швидку зміну станів портів (`BLOCKING`, `LEARNING`, `FORWARDING`) та керування апаратними прапорцями фільтрації.

## Ера Switchdev та апаратне розвантаження (Linux 4.x+)

З появою концепції Open Networking (відкриті комутатори на базі Whitebox ASIC від Mellanox/Nvidia, Broadcom, Marvell) виникла потреба використовувати стандартні інтерфейси Linux для керування комутаційними чіпами з продуктивністю в десятки терабіт на секунду.

У 2015 році розробники ядра (Іржі Пірко — Jiri Pirko, Ідо Шіммель — Ido Schimmel та інші) створили підсистему **Switchdev**. Linux Bridge став офіційним програмним Control Plane для апаратних комутаторів.

```
+-------------------------------------------------------------+
|   Control Plane: Linux Bridge (FDB, VLAN Filtering, STP)    |
+-------------------------------------------------------------+
                              | Switchdev driver API
                              v
+-------------------------------------------------------------+
|   Data Plane: Апаратний ASIC (Mellanox Spectrum / Broadcom) |
|   Комутація 100G/400G на швидкості дроту (Line Rate)        |
+-------------------------------------------------------------+
```

Коли адміністратор виконує команду додавання VLAN або порт вивчає новий MAC, Linux Bridge надсилає подію `SWITCHDEV_FDB_ADD_TO_DEVICE` до драйвера ASIC. Кадри комутуються апаратно всередині заліза без участі центрального процесора хоста, а ядро залучається лише як резервний шлях (Slow Path) для невідомих службових протоколів.
