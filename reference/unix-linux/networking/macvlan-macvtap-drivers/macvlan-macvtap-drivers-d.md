## Вступ до віртуалізації мереж у Linux

Сучасні інфраструктури, що базуються на контейнерах та віртуальних машинах, вимагають ефективних, швидких та гнучких механізмів мережевої комунікації. Історично для з'єднання віртуальних середовищ (таких як віртуальні машини QEMU/KVM або контейнери Docker/LXC) з фізичною мережею використовувався Linux Bridge. Хоча Linux Bridge є потужним інструментом, який фактично реалізує програмний комутатор рівня L2 (Data Link Layer) всередині ядра операційної системи, його використання супроводжується певними накладними витратами. Кожен пакет, що проходить через Linux Bridge, піддається додатковій обробці: перевірці MAC-адрес, вивченню таблиці комутації (FDB - Forwarding Database), проходженню через ланцюжки iptables/nftables (якщо завантажено модуль `br_netfilter`), а також блокуванням під час багатопотокової обробки.

Для вирішення проблеми продуктивності та спрощення топології мережі були розроблені спеціалізовані драйвери віртуальних інтерфейсів: **Macvlan** та **Macvtap**. Ці драйвери дозволяють уникнути використання традиційного Linux Bridge, забезпечуючи більш прямий та швидкий шлях для мережевого трафіку між віртуальним середовищем та фізичним мережевим адаптером (NIC). 

У цьому розділі ми детально розглянемо архітектуру драйверів Macvlan та Macvtap, їх режими роботи (Bridge, VEPA, Private, Passthrough), випадки використання, а також відмінності між ними та їхні переваги над традиційними мостовими з'єднаннями.

## Архітектура та принципи роботи Macvlan

Драйвер **Macvlan** — це механізм ядра Linux, який дозволяє створити кілька віртуальних мережевих інтерфейсів (sub-interfaces) поверх одного фізичного (або логічного) батьківського інтерфейсу (parent interface, наприклад, `eth0`). Кожен з цих віртуальних інтерфейсів має власну, унікальну MAC-адресу, а також може мати власну IP-адресу.

### Чому Macvlan?

З точки зору зовнішньої мережі (фізичного комутатора, до якого підключений хост), усі ці різні MAC-адреси виглядають так, ніби вони підключені до одного фізичного порту комутатора. Це дуже схоже на те, як працює звичайний некерований комутатор (hub/switch). Проте на стороні хоста, ядро Linux бере на себе завдання демультиплексування вхідного трафіку: коли пакет приходить на фізичний інтерфейс, драйвер Macvlan перевіряє MAC-адресу призначення (Destination MAC). Якщо вона збігається з MAC-адресою одного з інтерфейсів Macvlan, пакет безпосередньо передається цьому віртуальному інтерфейсу і, відповідно, в мережевий простір імен (network namespace), де цей інтерфейс знаходиться (наприклад, у контейнер).

Це усуває потребу в навчанні MAC-адрес (MAC learning) та підтримці таблиці FDB, як це робить Linux Bridge. Оскільки маршрутизація L2 виконується на основі простого порівняння MAC-адрес без додаткової логіки моста, Macvlan забезпечує значно вищу пропускну здатність та нижчу затримку (latency). Крім того, Macvlan обходить правила `iptables` на хості, що є і плюсом (продуктивність), і мінусом (неможливість фільтрації трафіку хостом) залежно від потреб безпеки.

### Важливе обмеження Macvlan

Одна з найважливіших особливостей Macvlan (і Macvtap), яку часто не розуміють користувачі-початківці, полягає в тому, що **хост-система (батьківський інтерфейс) та віртуальні інтерфейси Macvlan не можуть взаємодіяти один з одним безпосередньо**. 

Тобто, якщо ви створили інтерфейс Macvlan (наприклад, `macvlan0`) поверх `eth0` і помістили `macvlan0` у контейнер, контейнер зможе безперешкодно спілкуватися з іншими пристроями у фізичній мережі. Однак контейнер *не зможе* пропінгувати IP-адресу самого `eth0` на хості, а хост не зможе звернутися до контейнера. Це пов'язано з тим, що драйвер Macvlan фільтрує пакети, відправлені з віртуального інтерфейсу на батьківський MAC, і навпаки. Трафік просто скидається на рівні ядра, оскільки пакет, відправлений через фізичний інтерфейс, ніколи не повертається назад (петля, hairpin).

Щоб вирішити цю проблему (якщо зв'язок між хостом і гостем є обов'язковим), зазвичай створюють *ще один* інтерфейс Macvlan на самому хості і переносять IP-адресу з фізичного інтерфейсу `eth0` на цей новий хостовий інтерфейс Macvlan. Тоді і хост, і гості знаходяться на віртуальних інтерфейсах, і зв'язок між ними можливий (за умови використання режиму Bridge).

## Режими роботи Macvlan

Гнучкість Macvlan зумовлена наявністю чотирьох різних режимів роботи. Кожен режим визначає, як віртуальні інтерфейси (endpoints), створені поверх одного батьківського інтерфейсу, взаємодіють між собою та із зовнішнім світом.

![Режими Macvlan](macvlan_modes.svg)
*Рис. 2. Режими роботи Macvlan: Bridge, VEPA, Private, Passthrough.*

### 1. Режим Bridge (macvlan mode bridge)

Це найпопулярніший і найчастіше використовуваний режим. У режимі **Bridge** інтерфейси Macvlan, прив'язані до одного фізичного інтерфейсу, можуть спілкуватися один з одним безпосередньо. Драйвер Macvlan бере на себе роль простого віртуального комутатора L2 між цими інтерфейсами.

- **Як працює:** Якщо контейнер A (`macvlanA`) відправляє пакет контейнеру B (`macvlanB`), драйвер перехоплює пакет і направляє його безпосередньо інтерфейсу `macvlanB`, не випускаючи пакет на фізичний мережевий адаптер і у фізичну мережу.
- **Використання:** За замовчуванням у Docker (при використанні драйвера `macvlan`) використовується саме цей режим. Він ідеально підходить, коли вам потрібно, щоб контейнери на одному хості взаємодіяли між собою з максимальною швидкістю, а також мали прямий доступ до зовнішньої мережі.

### 2. Режим VEPA (Virtual Ethernet Port Aggregator)

Режим **VEPA** (Virtual Ethernet Port Aggregator, описаний у стандарті IEEE 802.1Qbg) є режимом за замовчуванням під час створення інтерфейсу Macvlan через утиліту `ip link`.

- **Як працює:** У цьому режимі інтерфейси Macvlan на одному хості **не можуть** спілкуватися один з одним безпосередньо всередині хоста. Увесь трафік від інтерфейсу Macvlan, незалежно від його призначення, виштовхується на фізичний комутатор. Якщо контейнер A хоче передати дані контейнеру B на тому ж самому хості, пакет спочатку йде на зовнішній апаратний комутатор, і той комутатор має відправити його назад (hairpin/reflective relay) на той самий порт.
- **Вимоги:** Для того, щоб цей режим працював коректно при взаємодії локальних контейнерів, фізичний комутатор (Switch) повинен підтримувати функцію **Hairpin Mode** (або "Reflective Relay" / 802.1Qbg). Багато стандартних комутаторів за замовчуванням відкидають пакети, які надходять на порт і мають бути відправлені назад з того самого порту (задля запобігання мережевим петлям).
- **Переваги:** Головна перевага режиму VEPA полягає в тому, що всі політики безпеки, ACL (Access Control Lists), моніторинг трафіку (port mirroring), та QoS застосовуються на фізичному апаратному комутаторі. Це дозволяє адміністраторам мережі керувати трафіком віртуальних машин та контейнерів за допомогою існуючого мережевого обладнання корпоративного класу, замість налаштування складних правил всередині Linux-хоста.

### 3. Режим Private

Режим **Private** є найбільш ізольованим режимом.

- **Як працює:** У цьому режимі інтерфейси Macvlan на одному хості повністю ізольовані один від одного. Навіть якщо зовнішній комутатор підтримує і налаштований на Hairpin Mode і відправляє пакет назад, драйвер Macvlan на рівні хоста розпізнає такий пакет і відкине (drop) його.
- **Використання:** Використовується у випадках, коли віртуальні машини або контейнери ніколи не повинні обмінюватися трафіком безпосередньо. Вони можуть спілкуватися лише із зовнішнім світом. Це ідеально підходить для хостингових платформ, де кожен контейнер належить різним клієнтам (multi-tenancy), і будь-яка можливість прямого L2-зв'язку між ними має бути апаратно та програмно виключена задля безпеки.

### 4. Режим Passthrough

Режим **Passthrough** надає ексклюзивний доступ до фізичного інтерфейсу одному (і лише одному) віртуальному інтерфейсу.

- **Як працює:** У цьому режимі не створюються додаткові MAC-адреси. Замість цього MAC-адреса віртуального інтерфейсу збігається з MAC-адресою фізичного батьківського інтерфейсу. Батьківський інтерфейс переводиться в спеціальний режим, при якому він передає весь трафік (навіть з чужими MAC-адресами, працюючи в promisc mode, якщо необхідно) безпосередньо до дочірнього інтерфейсу.
- **Обмеження:** Оскільки батьківський інтерфейс повністю захоплюється, ви можете створити лише **один** інтерфейс Macvlan (або Macvtap) у режимі passthrough поверх фізичного NIC.
- **Використання:** Цей режим активно використовується з Macvtap для передачі керування фізичним мережевим адаптером безпосередньо у віртуальну машину (через SR-IOV VFs - Virtual Functions або просто для повного відключення обробки на хості), дозволяючи гостьовій системі самостійно керувати MAC-адресами та обробкою мережевих протоколів (наприклад, для запуску всередині віртуальної машини власного програмного комутатора, такого як Open vSwitch).

## Створення та конфігурація Macvlan

Розглянемо практичні аспекти використання Macvlan з використанням утиліти `ip` з пакета `iproute2`.

### Створення Macvlan інтерфейсу

Для створення Macvlan інтерфейсу `macvlan1` поверх батьківського інтерфейсу `eth0` у режимі `bridge`, використовується наступна команда:

```bash
sudo ip link add macvlan1 link eth0 type macvlan mode bridge
```

Після виконання цієї команди з'явиться новий інтерфейс `macvlan1`. Ви можете переконатися в цьому:

```bash
ip link show macvlan1
```

Вивід буде приблизно таким:
```text
5: macvlan1@eth0: <BROADCAST,MULTICAST> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 12:34:56:78:9a:bc brd ff:ff:ff:ff:ff:ff
```
Зверніть увагу на нотацію `macvlan1@eth0`, яка явно вказує на батьківський інтерфейс. MAC-адреса генерується випадковим чином (зазвичай, починається з префікса локального адміністрування), але ви також можете задати її вручну під час створення.

### Переміщення в Network Namespace

Головна цінність Macvlan полягає у використанні його з мережевими просторами імен (Network Namespaces). Давайте створимо namespace і перемістимо туди наш інтерфейс:

```bash
# Створюємо namespace 'netns1'
sudo ip netns add netns1

# Переміщуємо macvlan1 до netns1
sudo ip link set macvlan1 netns netns1

# Вмикаємо інтерфейс і призначаємо IP-адресу всередині namespace
sudo ip netns exec netns1 ip link set macvlan1 up
sudo ip netns exec netns1 ip addr add 192.168.1.100/24 dev macvlan1

# Додаємо маршрут за замовчуванням
sudo ip netns exec netns1 ip route add default via 192.168.1.1
```

Тепер процеси, запущені всередині `netns1`, можуть безпосередньо використовувати `macvlan1` для зв'язку з мережею 192.168.1.0/24. Їхній трафік буде виходити через фізичний `eth0` хоста, не проходячи через жодні Linux-мости.

## Драйвер Macvtap: З'єднання Macvlan з віртуальними машинами (QEMU/KVM)

Драйвер **Macvlan** ідеально підходить для контейнерів (Docker, LXC), оскільки контейнери є просто процесами, ізольованими за допомогою просторів імен (namespaces), і вони безпосередньо працюють з мережевим стеком ядра Linux (хоча і в ізольованому екземплярі).

Однак **віртуальні машини** (наприклад, ті, що працюють під управлінням QEMU/KVM) працюють інакше. Віртуальна машина має власне ядро (Guest OS), і гіпервізор (QEMU, процес у просторі користувача хоста - userspace) повинен емулювати апаратний мережевий адаптер (наприклад, virtio-net) для цієї гостьової ОС. 

Для передачі пакетів між процесом QEMU (userspace) та мережевим стеком хоста (kernel space) використовується механізм файлових дескрипторів символьних пристроїв (character devices). Традиційно для цього використовувався драйвер **TUN/TAP**, який створював інтерфейс `/dev/net/tun`. Але при використанні TAP, адміністратору все одно доводилося підключати цей TAP-інтерфейс до Linux Bridge, щоб з'єднати його з фізичною мережею.

Тут на допомогу приходить **Macvtap**.

![Macvtap Архітектура](macvtap_arch.svg)
*Рис. 3. Взаємодія Macvtap та QEMU/KVM через символьний пристрій.*

### Що таке Macvtap?

**Macvtap** — це комбінація властивостей драйвера Macvlan та драйвера TAP.
1. З точки зору мережевого стека, Macvtap поводиться **точнісінько як Macvlan**: він створює віртуальний L2 інтерфейс з власною MAC-адресою поверх батьківського інтерфейсу і підтримує ті ж самі режими (Bridge, VEPA, Private, Passthrough).
2. На відміну від Macvlan, Macvtap створює **символьний пристрій (character device)** у файловій системі `/dev/tapX` (де X — індекс інтерфейсу, який відповідає `ifindex` в ядрі).

Процес QEMU може відкрити цей пристрій `/dev/tapX` і читати/писати в нього безпосередньо. Коли QEMU (і, відповідно, Guest OS) відправляє пакет, він записує його у `/dev/tapX`. Драйвер Macvtap в ядрі приймає цей пакет і негайно передає його на фізичний мережевий адаптер (минаючи весь мережевий стек маршрутизації хоста, netfilter та iptables). Аналогічно, коли вхідний пакет приходить на фізичний інтерфейс і MAC-адреса призначення збігається з MAC-адресою Macvtap, драйвер поміщає цей пакет у буфер символьного пристрою `/dev/tapX`, звідки його вичитує QEMU і передає у гостьову ОС.

Цей механізм надзвичайно ефективний. Він зменшує кількість перемикань контексту та копіювання пам'яті порівняно зі зв'язкою `QEMU -> TAP -> Linux Bridge -> eth0`.

### Створення Macvtap

Синтаксис створення Macvtap майже ідентичний Macvlan, лише тип вказується як `macvtap`:

```bash
# Створення інтерфейсу macvtap0 поверх eth0
sudo ip link add link eth0 name macvtap0 type macvtap mode bridge

# Ввімкнення інтерфейсу
sudo ip link set macvtap0 up
```

Після створення інтерфейсу, в системі з'явиться символьний пристрій. Дізнатися його номер можна, подивившись `ifindex`:

```bash
cat /sys/class/net/macvtap0/ifindex
```
Припустимо, вивід `6`. Це означає, що відповідний символьний пристрій знаходиться за адресою `/dev/tap6`. Саме цей шлях вказується гіпервізору QEMU або libvirt.

### Інтеграція Macvtap з Libvirt

Libvirt (високорівнева система управління віртуалізацією, яка використовується, наприклад, у virt-manager) має вбудовану підтримку Macvtap. У конфігураційному файлі (XML) віртуальної машини це визначається за допомогою `<interface type='direct'>`:

```xml
<interface type='direct'>
  <mac address='52:54:00:11:22:33'/>
  <source dev='eth0' mode='bridge'/>
  <model type='virtio'/>
</interface>
```

При запуску такої віртуальної машини, Libvirt автоматично створить інтерфейс Macvtap (зазвичай з іменем `macvtapN`), прив'яже його до `eth0` у режимі `bridge`, відкриє відповідний `/dev/tapX` і передасть файловий дескриптор безпосередньо процесу QEMU. Після вимкнення ВМ інтерфейс буде автоматично видалено.

Цей метод налаштування мережі часто називають "Macvtap/Macvlan direct attachment" у документації Libvirt.

## Продуктивність та оптимізація: Macvlan vs Linux Bridge

Вибір між Linux Bridge та Macvlan/Macvtap часто зводиться до балансу між продуктивністю та функціональністю.

### Переваги продуктивності Macvlan/Macvtap

1. **Скорочений шлях пакета (Shorter Data Path):** Пакети обходять складний стек мостової маршрутизації Linux.
2. **Відсутність MAC Learning:** Оскільки всі MAC-адреси заздалегідь відомі драйверу, ядро не витрачає час на аналіз заголовків кожного пакета для оновлення таблиці FDB, як це відбувається у Bridge. Це значно прискорює обробку, особливо під час флуду або multicast-трафіку.
3. **Обхід Netfilter/iptables:** У Linux Bridge пакети проходять через спеціальні хуки (hooks) netfilter (якщо параметр `net.bridge.bridge-nf-call-iptables` встановлений у 1), що дозволяє фільтрувати трафік моста. Це додає суттєві затримки. Macvlan/Macvtap не використовують ці хуки; пакети обробляються виключно на рівні L2 і швидко передаються в драйвер мережевої карти. Затримка (latency) зменшується на десятки мікросекунд на кожен пакет, що критично для високонавантажених баз даних або NFV (Network Function Virtualization).
4. **Масштабованість:** Macvlan набагато краще масштабується на системах з десятками або сотнями віртуальних машин/контейнерів завдяки паралельній обробці.

### Недоліки та обмеження Macvlan/Macvtap

1. **Обмеження кількості MAC-адрес:** Більшість сучасних мережевих адаптерів (NIC) підтримують апаратну фільтрацію кількох MAC-адрес. Однак ця кількість не є нескінченною (зазвичай кілька десятків або сотень). Якщо ви створюєте забагато інтерфейсів Macvlan, мережевий адаптер перейде у **promiscuous mode** (режим прослуховування всіх пакетів). Це означає, що NIC почне передавати всі пакети (навіть призначені для інших машин у мережі) до центрального процесора хоста, покладаючи на CPU завдання програмної фільтрації. Це може призвести до значного стрибка завантаження процесора (CPU Interrupts) і звести нанівець усі переваги продуктивності.
2. **Проблеми зі зв'язком Host-to-Guest:** Як зазначалося раніше, через особливості архітектури Macvlan, хост не може безпосередньо звертатися до віртуальних машин/контейнерів через той самий фізичний інтерфейс. Це вимагає створення додаткових віртуальних інтерфейсів на хості та складної маршрутизації.
3. **Відсутність гнучкої маршрутизації та NAT:** На відміну від Bridge, який можна налаштувати з NAT (через iptables) і використовувати як маршрутизатор для приватних підмереж (як це робить дефолтний міст Docker `docker0` або `virbr0` у libvirt), Macvlan вимагає, щоб віртуальні машини знаходилися в тій самій L2-мережі, що й хост. Їм потрібні IP-адреси з тієї ж підмережі. Це означає, що ви не можете приховати 100 контейнерів за однією публічною IP-адресою хоста за допомогою звичайного Macvlan (без використання зовнішніх маршрутизаторів).
4. **Складності з DHCP/ARP в деяких мережах:** У хмарних провайдерів (AWS, GCP, Azure) або на хостингах зі строгими правилами безпеки на комутаторах (Port Security), використання Macvlan часто призводить до того, що пакети просто блокуються. Процесори комутаторів бачать, що з одного порту (до якого підключений ваш сервер) надходять пакети з несанкціонованими MAC-адресами, і відкидають їх. У таких випадках використання Macvlan неможливе (потрібно використовувати IPvLAN або Bridge з NAT).

## Детальний аналіз режиму Passthrough (SR-IOV)

Режим Passthrough у драйверах Macvtap заслуговує на окрему увагу, оскільки він часто використовується у зв'язці з технологією **SR-IOV** (Single Root I/O Virtualization).

SR-IOV дозволяє розділити одну фізичну PCIe мережеву карту на кілька віртуальних пристроїв, які називаються **Virtual Functions (VF)**. Кожна VF виглядає для операційної системи як окрема, повноцінна мережева карта з власною MAC-адресою, власними чергами переривань (RX/TX queues) та незалежним DMA (Direct Memory Access).

Для надання віртуальній машині доступу до VF з максимальною продуктивністю можна використовувати два методи:
1. **PCI Passthrough (VFIO):** Віртуальна функція повністю передається в гостьову ОС як PCIe пристрій. Це дає найбільшу продуктивність, але унеможливлює живу міграцію (Live Migration) віртуальної машини в QEMU, оскільки апаратний стан PCIe-пристрою прив'язаний до конкретного фізичного хоста.
2. **Macvtap Passthrough:** Інтерфейс Macvtap створюється поверх VF (наприклад, `eth0_vf1`) у режимі `passthrough`. QEMU емулює стандартний інтерфейс (наприклад, virtio-net) для гостя, але всі пакети передаються через Macvtap прямо у VF. Хоча це трохи повільніше, ніж чистий PCI Passthrough, це дозволяє зберегти можливість живої міграції віртуальної машини! (Під час міграції QEMU може тимчасово перемкнутися на програмний міст, а на цільовому хості знову приєднатися до іншої VF).

Коли Macvtap працює в режимі passthrough поверх VF, він автоматично переводить VF у потрібний стан, дозволяючи гостьовій ОС змінювати MAC-адреси, налаштовувати VLAN-тегування та отримувати всі апаратні офлоадинги (Hardware Offloading - TSO, GSO, Checksum calculation) безпосередньо з мережевої карти.

## Використання Macvlan у Docker

Docker має вбудовану підтримку мереж Macvlan. Це особливо корисно, коли ви переносите legacy-додатки в контейнери (наприклад, старі сервери баз даних або VoIP системи), які вимагають, щоб вони виглядали як фізичні пристрої в корпоративній мережі, без жодного NAT.

Для створення мережі Macvlan у Docker використовується команда:

```bash
docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 pub_net
```

У цьому прикладі:
- `-d macvlan` — вказує драйвер.
- `--subnet` та `--gateway` повинні збігатися з параметрами фізичної мережі, до якої підключений `eth0`.
- `-o parent=eth0` — вказує батьківський інтерфейс.

Після цього контейнер можна запустити в цій мережі:

```bash
docker run -it --rm --network pub_net --ip 192.168.1.150 alpine /bin/sh
```

Тепер контейнер матиме IP-адресу `192.168.1.150` і безпосередньо взаємодіятиме з фізичним маршрутизатором мережі. Режим за замовчуванням — **bridge**, що дозволяє контейнерам у цій мережі `pub_net` спілкуватися один з одним.

### Вирішення проблеми зв'язку Host-to-Container у Docker

Як згадувалося, хост не зможе пінгувати адресу `192.168.1.150`. Щоб виправити це у середовищі Docker, адміністратори часто використовують наступний трюк. Вони не призначають IP-адресу безпосередньо на `eth0`. Замість цього:

1. Створюється додатковий Macvlan-інтерфейс на самому хості.
2. Вся маршрутизація хоста переноситься на цей новий Macvlan.
3. Таким чином, хост і контейнери стають "братами" на одному фізичному інтерфейсі, спілкуючись через вбудований комутатор Macvlan (mode bridge).

Конфігурація (приблизно):
```bash
# 1. Забираємо IP з фізичного інтерфейсу (може призвести до втрати зв'язку по SSH!)
sudo ip addr del 192.168.1.50/24 dev eth0

# 2. Створюємо macvlan для хоста
sudo ip link add host-macvlan link eth0 type macvlan mode bridge

# 3. Призначаємо IP і вмикаємо
sudo ip addr add 192.168.1.50/24 dev host-macvlan
sudo ip link set host-macvlan up

# 4. Додаємо маршрути
sudo ip route add default via 192.168.1.1 dev host-macvlan
```
Після цієї складної операції зв'язок між хостом (тепер через `host-macvlan`) та контейнерами (в мережі Docker `pub_net`) буде повністю відновлено.

## Підсумок: Коли що використовувати?

Вибір мережевої архітектури завжди залежить від конкретних вимог:

- **Linux Bridge:** Використовуйте як універсальне рішення за замовчуванням. Він простий у налаштуванні, ідеально працює з NAT, легко дозволяє фільтрувати трафік (через `iptables`) і не має проблем зі зв'язком між хостом та гостями. Якщо у вас немає критичних вимог до мікросекундних затримок або гігабітних швидкостей всередині хоста — Bridge є найкращим вибором.
- **Macvlan:** Використовуйте для контейнерів (Docker/LXC), коли їм потрібна власна IP-адреса з фізичної підмережі, висока пропускна здатність і коли фільтрація/NAT на рівні хоста не потрібні. Macvlan вимагає уважного планування мережі та розуміння обмежень зв'язку з хостом.
- **Macvtap:** Абсолютний стандарт для підключення віртуальних машин QEMU/KVM до мережі, коли потрібна максимальна продуктивність і коли віртуальній машині виділяється окрема IP-адреса у фізичній мережі. Macvtap повністю витіснив зв'язку `TAP + Bridge` у сучасних високопродуктивних віртуалізованих середовищах.

Розуміння внутрішньої роботи драйверів **Macvlan** та **Macvtap** дозволяє системним адміністраторам та мережевим інженерам створювати гнучкі, оптимізовані та потужні віртуальні мережі, уникаючи непотрібних накладних витрат традиційних програмних комутаторів.
