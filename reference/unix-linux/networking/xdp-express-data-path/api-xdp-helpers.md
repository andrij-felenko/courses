# 📋 Інтерфейс та хелпери eXpress Data Path (XDP)

Вставка є системним довідником з програмного інтерфейсу eXpress Data Path (XDP) у ядрі Linux. Вона містить опис структур даних `struct xdp_md` та `struct xdp_buff`, усіх кодів дій (Action Codes), допоміжних BPF-функцій (helpers), прапорців прив'язки програм через Netlink/libbpf та спеціалізованих типів BPF-карт.

---

## 1. Контекстні структури даних XDP

Під час виклику XDP-програми ядро передає їй контекстний вказівник. Усередині eBPF-програми цей контекст представлений як `struct xdp_md *`, тоді як у коді драйвера ядра використовується внутрішня структура `struct xdp_buff`.

### 1.1. Користувацький контекст uapi: `struct xdp_md`

Визначена у заголовочному файлі `<linux/bpf.h>`. Поля цієї структури доступні для читання (а деякі для запису) усередині eBPF-програми:

```c
struct xdp_md {
    __u32 data;           /* Вказівник на початок даних мережевого пакета */
    __u32 data_end;       /* Вказівник на кінець даних мережевого пакета */
    __u32 data_meta;      /* Вказівник на початок области метаданих перед пакетом */
    __u32 ingress_ifindex;/* Системний індекс вхідного мережевого інтерфейсу */
    __u32 rx_queue_index; /* Індекс RX-черги мережевого адаптера */
    __u32 egress_ifindex; /* Індекс вихідного інтерфейсу (для XDP_REDIRECT) */
};
```

#### Детальний опис полів `struct xdp_md`

| Поле | Тип у BPF | Опис та застосування |
| :--- | :--- | :--- |
| `data` | `void *` (після зсуву) | Вказівник на перший байт Ethernet-заголовка пакета у DMA-сторінці. Зсувається при виклику `bpf_xdp_adjust_head()`. |
| `data_end` | `void *` (після зсуву) | Вказівник на перший байт ПІСЛЯ кінця пакета. Використовується верифікатором для bounds check: `(data + len) <= data_end`. |
| `data_meta` | `void *` (після зсуву) | Вказівник на початок власної зони метаданих, що розміщена безпосередньо перед `data`. Початково дорівнює `data`. |
| `ingress_ifindex` | `__u32` | Унікальний числовий ідентифікатор мережевого інтерфейсу (`ifindex`), на який прибув пакет у ядрі. |
| `rx_queue_index` | `__u32` | Номер апаратної RX-черги (Hardware RX Queue Index) мережевої карти, яка зчитала цей пакет через DMA. |
| `egress_ifindex` | `__u32` | Індекс вихідного інтерфейсу. Заповнюється ядром або BPF-хелпером при використанні дії `XDP_REDIRECT`. |

> ⚠️ **Зверніть увагу:** Усі адреси пам'яті (`data`, `data_end`, `data_meta`) передаються у контексті як 32-бітні цілі числа для сумісності 32/64-бітних архітектур BPF. Усередині коду їх необхідно явно зводити до 64-бітних вказівників: `void *data = (void *)(long)ctx->data;`.

### 1.2. Внутрішня структура ядра: `struct xdp_buff`

Визначена у заголовочному файлі ядра `<linux/filter.h>`. Використовується драйверами мережевих карт для ініціалізації контексту XDP до створення `sk_buff`:

```c
struct xdp_buff {
    void *data;             /* Початок пакету */
    void *data_end;         /* Кінець пакету */
    void *data_meta;        /* Початок метаданих */
    void *data_hard_start;  /* Фізичний початок allocated сторінки пам'яті */
    struct xdp_rxq_info *rxq;/* Метадані про RX-чергу та драйвер */
    struct xdp_mem_info mem;/* Інформація про модель управління пам'яттю (PAGE_POOL) */
    enum xdp_mem_type type; /* Тип пам'яті (MEM_TYPE_PAGE_POOL, MEM_TYPE_PAGE_SHARED) */
    u32 flags;              /* Прапорці (наприклад, XDP_FLAGS_MB для multi-buffer) */
};
```

Поле `data_hard_start` указує на абсолютний початок сторінки пам'яті в RAM, виділеної драйвером під DMA. Відстань між `data_hard_start` та `data` називається Headroom. Початково ядро резервує там не менше 256 байт для забезпечення можливості додавання заголовків без перевиділення пам'яті.

Поле `rxq` містить вказівник на структуру `struct xdp_rxq_info`, яка зберігає метадані про мережевий пристрій, розмір сторінки та конфігурацію RX-черги:

```c
struct xdp_rxq_info {
    struct net_device *dev;
    u32 queue_index;
    u32 reg_state;
    struct xdp_mem_info mem;
} ____cacheline_aligned;
```

## 2. Коди дій (Action Codes / Return Values)

XDP-програма повертає 32-бітне ціле число, яке вказує драйверу NIC подальшу долю пакета. Усі коди визначені в переліку `enum xdp_action` у `<uapi/linux/bpf.h>`:

```c
enum xdp_action {
    XDP_ABORTED = 0,
    XDP_DROP    = 1,
    XDP_PASS    = 2,
    XDP_TX      = 3,
    XDP_REDIRECT= 4,
};
```

### Специфікація кожного коду дії

#### `XDP_ABORTED` (0)
- **Зміст:** Повідомляє про виключну ситуацію або внутрішній збій у логіці BPF-програми (некоректний формат заголовка, помилка в BPF map тощо).
- **Поведінка ядра:** Пакет негайно відкидається (аналогічно до `XDP_DROP`), але ядро додатково генерує подію tracepoint `xdp:xdp_exception`.
- **Продуктивність:** Драйвер повертає сторінку у RX ring recycling pool.

#### `XDP_DROP` (1)
- **Зміст:** Наказує негайно відкинути пакет на найнижчому рівні.
- **Поведінка ядра:** Драйвер не виділяє `sk_buff`, не викликає Netfilter чи routing. Буфер сторінки повторно використовується (recycling) для наступних вхідних пакетів.
- **Продуктивність:** Максимальна пропускна здатність системи (до 40+ млн пакетів/сек на ядро). Основний use case: Anti-DDoS фільтрація.

#### `XDP_PASS` (2)
- **Зміст:** Пропустити пакет далі у класичний мережевий стек Linux.
- **Поведінка ядра:** Драйвер викликає `napi_build_skb()` або `netdev_alloc_skb()`, конструює структуру `sk_buff`, копіює туди модифіковані XDP дані/метадані та передає пакет у функцію `netif_receive_skb()`.
- **Застосування:** Дозволений трафік після перевірки XDP-файрволом.

#### `XDP_TX` (3)
- **Зміст:** Hairpinning (повернення бумерангом). Відправити пакет назад через той самий мережевий інтерфейс, з якого він надійшов.
- **Поведінка ядра:** Пакет переміщується з RX-черги безпосередньо в апаратну TX-чергу того самого NIC. Зміна MAC/IP адрес покладається на eBPF програму.
- **Застосування:** Високошвидкісні ICMP Echo (ping) респондери, ARP proxy, Direct Server Return (DSR) балансувальники.

#### `XDP_REDIRECT` (4)
- **Зміст:** Перенаправити пакет в інше місце умиснувши класичну маршрутизацію Linux.
- **Поведінка ядра:** Працює у зв'язці з хелперами `bpf_redirect()` або `bpf_redirect_map()`. Пакет може бути перенаправлений на:
  1. Інший мережевий пристрій (`DEVMAP` / `DEVMAP_HASH`).
  2. Інше ядро CPU для паралельної обробки (`CPUMAP`).
  3. Сокет додатку у User Space (`XSKMAP` / AF_XDP).

## 3. Довідник допоміжних BPF-функцій (XDP Helpers)

Нижче наведено основні функції ядра (визначені в `bpf_helper_defs.h`), доступні для виклику з XDP-програм.

### 3.1. `bpf_xdp_adjust_head`

```c
long bpf_xdp_adjust_head(struct xdp_md *ctx, int delta);
```

- **Опис:** Змінює положення вказівника `ctx->data` на величину `delta` байт у межах доступного Headroom сторінки DMA.
- **Параметри:**
  - `ctx`: Вказівник на контекст XDP.
  - `delta`: Число байт. Якщо `delta > 0`, вказівник `data` зміщується вперед (видалення заголовків/деінкапсуляція). Якщо `delta < 0`, `data` зміщується назад у headroom (додавання заголовків/інкапсуляція).
- **Повертає:** `0` у разі успіху, або від'ємне значення помилки (наприклад, `-EINVAL` при виході за межі headroom).
- **⚠️ ВАЖЛИВА УМОВА:** Після виклику цього хелпера усі раніше обчислені вказівники на пам'ять (`data`, `data_end`, `data_meta`) стають **недійсними**! Розробник зобов'язаний заново перечитати `ctx->data` та `ctx->data_end`.

---

### 3.2. `bpf_xdp_adjust_tail`

```c
long bpf_xdp_adjust_tail(struct xdp_md *ctx, int delta);
```

- **Опис:** Змінює положення вказівника `ctx->data_end` на величину `delta` байт (зміна довжини пакета з кінця).
- **Параметри:**
  - `delta`: Якщо `delta < 0`, обрізає довжину пакета (truncation). Якщо `delta > 0`, розширює пакет в область tailroom.
- **Повертає:** `0` у разі успіху, або від'ємний код помилки. Інвалідує всі вказівники пакета.

---

### 3.3. `bpf_xdp_adjust_meta`

```c
long bpf_xdp_adjust_meta(struct xdp_md *ctx, int delta);
```

- **Опис:** Змінює положення вказівника `ctx->data_meta` для виділення користувацьких метаданих перед Ethernet-заголовком.
- **Параметри:**
  - `delta`: Якщо `delta < 0`, збільшує розмір зони метаданих на `abs(delta)` байт.
- **Повертає:** `0` у разі успіху. Дозволяє передавати спеціальні мітки (наприклад, vlan_id чи timestamp) з XDP у `sk_buff` чи `tc` eBPF програм.

---

### 3.4. `bpf_redirect`

```c
long bpf_redirect(u32 ifindex, u64 flags);
```

- **Опис:** Перенаправляє пакет безпосередньо на вихідний мережевий інтерфейс `ifindex`.
- **Параметри:**
  - `ifindex`: Системний індекс вихідного мережевого адаптера (наприклад, інтерфейсу `eth1`).
  - `flags`: Прапорці напрямку (зазвичай `0` для egress, або `BPF_F_INGRESS`).
- **Повертає:** `XDP_REDIRECT`.

---

### 3.5. `bpf_redirect_map`

```c
long bpf_redirect_map(void *map, u32 key, u64 flags);
```

- **Опис:** Високопродуктивне перенаправлення пакета за допомогою BPF-карти (`DEVMAP`, `CPUMAP` або `XSKMAP`).
- **Параметри:**
  - `map`: Вказівник на BPF-карту відповідного типу.
  - `key`: Ключ у карті (наприклад, індекс вихідного інтерфейсу, індекс CPU ядра або номер сокета).
  - `flags`: Прапорці дії (наприклад, `XDP_PASS` як fallback при відсутності елемента у карті).
- **Повертає:** `XDP_REDIRECT`.

---

### 3.6. `bpf_xdp_get_buff_len`

```c
u32 bpf_xdp_get_buff_len(struct xdp_md *ctx);
```

- **Опис:** Обчислює повну довжину пакета у байтах (корисна для Multi-Buffer XDP, де пакет складається з кількох фрагментів).

## 4. Прапорці завантаження та прив'язки XDP (Attach Flags)

При завантаженні XDP-програми на мережевий інтерфейс за допомогою Netlink або бібліотеки `libbpf` вказуються прапорці режиму виконання (визначені в `<linux/if_link.h>`):

| Прапорець | Значення | Режим виконання XDP |
| :--- | :--- | :--- |
| `XDP_FLAGS_UPDATE_IF_NOEXIST` | `(1U << 0)` | Забороняє перезапис існуючої XDP-програми на інтерфейсі, якщо вона там вже завантажена. |
| `XDP_FLAGS_SKB_MODE` | `(1U << 1)` | **Generic XDP / XDP_SKB:** Програма виконується після виділення `sk_buff`. Працює на БУДЬ-ЯКОМУ драйвері, але повільно. |
| `XDP_FLAGS_DRV_MODE` | `(1U << 2)` | **Native XDP / XDP_DRV:** Програма виконується безпосередньо в драйвері NIC до `sk_buff`. Вимагає підтримки з боку драйвера. |
| `XDP_FLAGS_HW_MODE` | `(1U << 3)` | **Offloaded XDP / XDP_HW:** Програма завантажується та виконується безпосередньо на процесорі мережевої карти (SmartNIC). |
| `XDP_FLAGS_REPLACE` | `(1U << 4)` | Дозволяє атомарну заміну існуючої XDP-програми з перевіркою її попереднього файлового дескриптора (fd). |

## 5. Спеціалізовані BPF Maps для XDP

XDP підтримує чотири типи високопродуктивних карт (BPF Maps), оптимізованих під обробку пакетів без lock-конфліктів:

1. **`BPF_MAP_TYPE_DEVMAP`:** Масив вихідних мережевих пристроїв. Дозволяє миттєво переправляти пакет на інший NIC за індексом масиву. Ядро оптимізує передачу за допомогою пакетного редіректу (bulk transmit).
2. **`BPF_MAP_TYPE_DEVMAP_HASH`:** Хеш-таблиця вихідних мережевих пристроїв (дозволяє довільні ключі замість суцільного індексу, зручна для динамічної маршрутизації).
3. **`BPF_MAP_TYPE_CPUMAP`:** Таблиця ядер CPU. Перенаправлення пакета на вибране ядро змушує ядро Linux сформувати `sk_buff` саме на цільовому CPU (Receive Packet Steering у коді eBPF), що дозволяє масштабувати обробку на багатоядерних системах.
4. **`BPF_MAP_TYPE_XSKMAP`:** Таблиця сокетів AF_XDP. Дозволяє спрямувати пакет безпосередньо у буфери пам'яті (UMEM) конкретного сокета користувацького додатку без створення `sk_buff`.

## 6. Системні tracepoints ядра для XDP

Підсистема ядра підтримує спеціальні події трасування, які дозволяють діагностувати збої та вимірювати продуктивність:

- `xdp:xdp_exception`: Генерується, коли XDP-програма повертає код `XDP_ABORTED` або виникає помилка при виклику `bpf_redirect()`.
- `xdp:xdp_bulk_tx`: Генерується при груповій відправці пакетів у TX-чергу при використанні дій `XDP_TX` або `XDP_REDIRECT`.
- `xdp:xdp_cpumap_kthread`: Фіксує обробку пакетів у виділеному ядерному потоці при використанні карт `CPUMAP`.
- `xdp:xdp_devmap_xmit`: Фіксує передачу пакетів через карту `DEVMAP` на вихідний пристрій.
