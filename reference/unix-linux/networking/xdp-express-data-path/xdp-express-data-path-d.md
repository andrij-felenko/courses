# eXpress Data Path (XDP): обробка пакетів на NIC

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Технологія **eXpress Data Path (XDP)** — це революційний підхід до обробки мережевих пакетів у ядрі Linux, що дозволяє виконувати користувацький код eBPF безпосередньо в драйвері мережевого інтерфейсу (NIC), ще до того, як для пакета буде створено структуру `sk_buff` (socket buffer). Ця архітектурна особливість забезпечує надзвичайно високу продуктивність (понад 20-30 мільйонів пакетів на секунду на одне ядро процесора) і робить XDP ідеальним інструментом для створення захисту від DDoS-атак, балансувальників навантаження (наприклад, Facebook Katran), високошвидкісних маршрутизаторів та систем моніторингу.

У цій статті ми глибоко зануримося в архітектуру XDP, життєвий цикл пакетів, основні типи повернення (`XDP_DROP`, `XDP_TX`, `XDP_REDIRECT`, `XDP_PASS`), механізми модифікації заголовків (`bpf_xdp_adjust_head()`), а також розглянемо високопродуктивний механізм передачі пакетів у user space — AF_XDP.

## 1. Архітектура та місце XDP у мережевому стеку

Традиційний мережевий стек Linux оптимізований для універсальності, надійності та сумісності, але не для максимальної продуктивності. Коли мережева карта отримує пакет, драйвер алокує структуру `sk_buff` (metadata пакета), копіює дані (або налаштовує DMA), після чого пакет проходить через складні підсистеми: Netfilter, маршрутизацію (routing), QoS (qdisc) і, нарешті, потрапляє у сокет додатку. Алокація `sk_buff` та контекстні перемикання додають значні затримки та навантаження на CPU (overhead).

XDP кардинально змінює цей процес, пропонуючи "fast path" — швидкий шлях на найнижчому рівні.

### 1.1. Хук до виділення sk_buff

Головна перевага XDP полягає в тому, що BPF-програма виконується на етапі **RX (Receive) ring buffer** драйвера, тобто відразу після того, як пакет потрапив у пам'ять через DMA (Direct Memory Access), але до будь-якої обробки стеком Linux. 

1. **Без `sk_buff`:** На момент роботи XDP-програми структури `sk_buff` не існує. Пакет представлений у вигляді структури `xdp_md`, яка містить лише вказівники на початок і кінець сирих даних пакета. Відсутність `sk_buff` означає відсутність overhead на виділення пам'яті (slab allocator) та ініціалізацію полів.
2. **Нульове копіювання (Zero-copy):** XDP читає дані безпосередньо з DMA-буфера мережевої карти. 
3. **Виконання у контексті NAPI (New API):** XDP-програма викликається у контексті NAPI poll, що означає роботу в режимі м'яких переривань (SoftIRQ) з вимкненими перериваннями (interrupts disabled) для даної черги RX.

### 1.2. Режими роботи XDP

XDP підтримує три режими виконання, які залежать від підтримки драйвером та мережевою картою:

1. **XDP_DRV (Native XDP):** BPF-програма інтегрована безпосередньо в код драйвера мережевої карти. Це забезпечує максимальну продуктивність. Більшість сучасних драйверів (ixgbe, i40e, mlx5, veth, virtio_net) підтримують цей режим.
2. **XDP_SKB (Generic XDP):** Це fallback-режим, у якому XDP-програма виконується після виділення `sk_buff` (на рівні `netif_receive_skb`). Цей режим не дає виграшу у продуктивності (навпаки, він повільніший), але є корисним для тестування та відлагодження на інтерфейсах, драйвери яких не підтримують Native XDP.
3. **XDP_HW (Offloaded XDP):** BPF-програма компілюється (JIT) та завантажується безпосередньо на апаратне забезпечення мережевої карти (SmartNIC, наприклад Netronome Agilio). У цьому режимі CPU хоста взагалі не бере участі в обробці пакетів (якщо пакет відкидається або пересилається на рівні карти).

## 2. Анатомія XDP-програми

XDP-програма — це функція мовою C (компільована за допомогою Clang/LLVM у байт-код eBPF), яка приймає один аргумент `struct xdp_md *ctx` і повертає ціле число (код дії).

### 2.1. Контекст: `struct xdp_md`

Структура `xdp_md` — це "metadata" пакета, доступна BPF-програмі:

```c
struct xdp_md {
    __u32 data;           // Вказівник на початок пакета
    __u32 data_end;       // Вказівник на кінець пакета
    __u32 data_meta;      // Вказівник на метадані перед пакетом
    __u32 ingress_ifindex;// Індекс вхідного інтерфейсу
    __u32 rx_queue_index; // Індекс RX-черги
    __u32 egress_ifindex; // Індекс вихідного інтерфейсу (для XDP_TX/REDIRECT)
};
```

Зверніть увагу, що `data`, `data_end` та `data_meta` представлені як цілі числа, але BPF verifier перетворює їх на вказівники у пам'яті. Щоб прочитати дані, програма приводить ці типи до вказівників (наприклад, `void *data = (void *)(long)ctx->data`). 

**Важливе правило BPF-верифікатора:** Будь-яке звернення до пам'яті пакета повинно супроводжуватися перевіркою меж (bounds checking). Верифікатор відхилить програму, якщо ви спробуєте прочитати, скажімо, IP-заголовок, не перевіривши попередньо, чи не перевищує вказівник значення `data_end`.

### 2.2. XDP Return Codes (Коди повернення)

Обробка пакета в XDP завершується поверненням одного з п'яти кодів дій (action codes), які вказують драйверу, що робити з пакетом.

#### 2.2.1. `XDP_DROP`
Найпростіша, але найпотужніша дія. Якщо XDP-програма повертає `XDP_DROP`, драйвер миттєво відкидає пакет, повертаючи DMA-буфер назад у RX-чергу (recycling) без жодної алокації `sk_buff`.
**Застосування:** Захист від DDoS, файрволи, фільтрація трафіку (наприклад, блокування певних IP чи портів), BGP blackholing. Продуктивність `XDP_DROP` досягає теоретичного максимуму мережевої шини.

#### 2.2.2. `XDP_PASS`
Повернення `XDP_PASS` означає, що пакет є "безпечним" або "потрібним". Драйвер передає пакет далі у мережевий стек Linux: виділяється `sk_buff`, пакет проходить Netfilter, маршрутизацію і врешті-решт досягає сокета.
**Застосування:** Дозволений трафік у файрволах. Пакет може бути модифікований перед поверненням `XDP_PASS`.

#### 2.2.3. `XDP_TX`
Цей код змушує драйвер **відправити пакет назад (bounce)** через той самий мережевий інтерфейс, з якого він надійшов. Зазвичай перед поверненням `XDP_TX` програма змінює MAC та/або IP-адреси (наприклад, міняє місцями Source та Destination).
**Застосування:** Реалізація "Hairpinning", DSR (Direct Server Return) балансувальників навантаження (коли відповідь не повинна йти через балансувальник), проксі-сервери, відповіді на ARP-запити чи ICMP Echo Request прямо з NIC.

#### 2.2.4. `XDP_REDIRECT`
Найскладніша і найважливіша дія для маршрутизації. `XDP_REDIRECT` дозволяє переспрямувати пакет на:
1. **Інший мережевий інтерфейс (NIC):** Пакет, отриманий на `eth0`, може бути миттєво перенаправлений на `eth1`, минаючи маршрутизацію Linux (`bpf_redirect`).
2. **Групу CPU (CPUMAP):** Перерозподіл обробки пакетів між іншими ядрами CPU (аналог Receive Packet Steering, але програмований).
3. **AF_XDP Сокет (XSKMAP):** Пакет перенаправляється в пам'ять користувацького простору (user space) без копіювання, що дозволяє додаткам на кшталт DPDK або Snort працювати з неймовірною швидкістю.

#### 2.2.5. `XDP_ABORTED`
Аналог винятку (exception). Вказує, що в BPF-програмі сталася помилка під час обробки. Пакет відкидається (як у `XDP_DROP`), але генерується tracepoint (`xdp:xdp_exception`), що дозволяє інструментам моніторингу зафіксувати збій. Зазвичай програміст не повинен навмисно повертати `XDP_ABORTED`.

## 3. Модифікація пакетів: `bpf_xdp_adjust_head()`

XDP дозволяє не лише читати, але й змінювати вміст пакета (header parsing and rewriting). Найбільш потужною функцією для цього є `bpf_xdp_adjust_head()`.

### 3.1. Зміна розміру заголовків

Функція `bpf_xdp_adjust_head(struct xdp_md *ctx, int delta)` змінює положення вказівника `data` пакета, фактично зменшуючи або збільшуючи розмір доступної області (headroom) пакета (в межах DMA-буфера сторінки).

- **`delta > 0` (Позитивне зміщення):** Вказівник `data` зміщується вперед, ближче до `data_end`. Це **видаляє** заголовки з пакета.
  *Приклад:* Видалення заголовка VLAN (`delta = 4`) або деіндекапсуляція тунелів (наприклад, видалення заголовків VXLAN чи IPIP).

- **`delta < 0` (Негативне зміщення):** Вказівник `data` зміщується назад у headroom. Це **додає** місце для нових заголовків.
  *Приклад:* Інкапсуляція пакета в тунель (додавання зовнішнього IP/UDP/VXLAN заголовка).

Після виклику `bpf_xdp_adjust_head()`, усі вказівники (`data`, `data_end`) у структурі `ctx` стають недійсними (invalidated). BPF-програма **зобов'язана** заново прочитати їх із `ctx` і повторно перевірити межі пакета, інакше верифікатор не пропустить код.

### 3.2. Приклад: Зменшення TTL

Хоча `bpf_xdp_adjust_head` змінює розмір пакета, часто необхідно модифікувати існуючі дані "на місці". Наприклад, створення найпростішого XDP-маршрутизатора вимагає зменшення Time To Live (TTL) в IP-заголовку та перерахунку контрольної суми (checksum).

Оскільки XDP працює з "сирими" даними, ви безпосередньо змінюєте байти в пам'яті. BPF надає helper-функції, такі як `bpf_csum_diff()`, для інкрементального оновлення контрольної суми без необхідності її повного перерахунку.

## 4. AF_XDP: Bypass стеку в User Space (XSK)

Однією з найпотужніших можливостей `XDP_REDIRECT` є взаємодія з сімейством сокетів **AF_XDP (Address Family eXpress Data Path)**, також відомим як **XSK**.

AF_XDP — це механізм, який дозволяє "перекидати" (bypass) мережеві пакети прямо в пам'ять програми в просторі користувача (user space), оминаючи повністю мережевий стек Linux (не створюється `sk_buff`, пакет не бачить Netfilter/TCP/IP). Це відкритий стандарт, який сьогодні активно використовується як альтернатива або бекенд для DPDK (Data Plane Development Kit).

### 4.1. Архітектура AF_XDP (UMEM)

Фундаментом AF_XDP є концепція **UMEM** (User Memory) — області пам'яті (зазвичай на основі HugePages), яка виділяється у user space і відображається (memory-mapped) у kernel space (драйвер NIC).

Модель взаємодії використовує 4 кільцеві буфери (Ring Buffers), що забезпечують безблокувальний обмін даними (lockless communication):

1. **Fill Ring (Rx allocation):** Простір користувача передає драйверу (ядру) "дескриптори" (адреси вільних чанків у UMEM), куди драйвер може записувати нові пакети.
2. **RX Ring (Rx receipt):** Драйвер передає користувачу дескриптори чанків, які вже заповнені отриманими пакетами з мережі.
3. **TX Ring (Tx transmit):** Користувач передає драйверу дескриптори чанків з готовими пакетами для відправки у мережу.
4. **Completion Ring (Tx cleanup):** Драйвер повертає користувачу дескриптори, пакети з яких уже успішно відправлені (DMA Tx завершено), і чанки знову вільні для використання.

### 4.2. Механізм перенаправлення (XSKMAP)

Щоб пакет потрапив у сокет AF_XDP, XDP-програма повинна використати BPF-карту (map) типу `BPF_MAP_TYPE_XSKMAP` та хелпер `bpf_redirect_map()`. 

1. Користувацький додаток створює AF_XDP сокет.
2. Сокет реєструється у XSKMAP.
3. Коли пакет прибуває, XDP-програма виконує парсинг (наприклад, перевіряє, чи це UDP пакет для певного порту).
4. Якщо пакет має бути оброблений у user space, XDP повертає `bpf_redirect_map(&xskmap, rx_queue, 0)`.
5. Драйвер переміщує пакет у RX Ring відповідного AF_XDP сокета.

### 4.3. Zero-Copy (ZCA)

Якщо драйвер підтримує функцію Zero-Copy (ZC), AF_XDP здатний записувати пакети з апаратного буфера безпосередньо у UMEM користувача без жодного копіювання пам'яті (CPU copy). У режимі Zero-Copy (встановлюється флагом `XDP_ZEROCOPY`), продуктивність AF_XDP може досягати 30-40+ млн пакетів на секунду, що робить його повноцінним конкурентом DPDK, але зі значною перевагою: AF_XDP працює в рамках інфраструктури ядра Linux, підтримується стандартними драйверами та дозволяє частково передавати трафік у ядро (за допомогою `XDP_PASS`), тоді як DPDK повністю відчужує мережеву карту.

## 5. Порівняння: XDP проти Netfilter (iptables / nftables)

| Характеристика | XDP | Netfilter (iptables, nftables) |
| :--- | :--- | :--- |
| **Етап обробки** | До створення `sk_buff` (на рівні драйвера) | Після створення `sk_buff`, маршрутизації, фрагментації |
| **Продуктивність (DDoS drop)** | 20–30+ Mpps / ядро | 2–3 Mpps / ядро |
| **Складність розробки** | Висока (написання C коду, верифікатор BPF) | Низька/Середня (правила, синтаксис iptables/nftables) |
| **Доступ до метаданих** | Немає (сирі байти пакета) | Повний доступ до `sk_buff` (conntrack, routing, sockets) |
| **Типові Use Cases** | Anti-DDoS, Load Balancing (L4), XDP Router, AF_XDP | Stateful Firewalls (L7), NAT, Policy Routing, Connection Tracking |

XDP не замінює Netfilter. Вони чудово працюють у тандемі: XDP служить "щитом", який відкидає явне сміття (DDoS, malformed packets) на гігабітних швидкостях (`XDP_DROP`), а легітимний трафік передається у ядро (`XDP_PASS`), де Netfilter виконує складний stateful-аналіз з використанням `conntrack` та маршрутизації.

## 6. Життєвий цикл розробки та виклики

Написання XDP-програм є нетривіальною задачею через жорсткі обмеження BPF-верифікатора ядра.

### 6.1. BPF Verifier: Ваш суворий друг

Верифікатор гарантує, що програма XDP ніколи не викличе panic ядра, не ввійде у нескінченний цикл і не матиме доступу до несанкціонованої пам'яті (Out-Of-Bounds read/write). Для XDP це означає:
- Немає циклів без гарантованого завершення (Bounded loops).
- **Обов'язкова перевірка меж (Bounds Check):** Перед доступом до полів заголовка (наприклад, `iph->protocol`), ви повинні переконатися, що весь заголовок вміщується між `ctx->data` та `ctx->data_end`. Якщо перевірку пропущено, компіляція (точніше, завантаження у ядро) зазнає невдачі з помилкою верифікатора.

### 6.2. Робота зі складними заголовками (VLAN, IPv6 Extension Headers)

Оскільки XDP працює з сирими байтами, парсинг заголовків лягає на плечі розробника. Наприклад, якщо пакет містить 802.1Q (VLAN), структура Ethernet-заголовка змінюється (з'являється поле типу `0x8100`), і зміщення (offset) IP-заголовка зсувається на 4 байти. XDP-програма повинна вручну перевірити `eth_proto`, розпізнати VLAN і динамічно зсунути вказівник розбору.

Аналогічно, IPv6 може містити ланцюжок Extension Headers. Програма повинна "йти" (walk) по цих заголовках у циклі з перевірками меж, щоб знайти потрібний транспортний заголовок (TCP/UDP), що вимагає ретельного написання C-коду.

## Висновки

eXpress Data Path (XDP) — це фундаментальний зсув парадигми в мережевій архітектурі Linux. Він дає розробникам інструмент для програмованої обробки пакетів на швидкості апаратного забезпечення, не відмовляючись від безпеки та екосистеми ядра Linux.
Завдяки комбінації BPF, `XDP_DROP`, модифікації через `bpf_xdp_adjust_head` та передачі трафіку в User Space через AF_XDP (XSK), XDP став галузевим стандартом для побудови надвисокопродуктивних хмарних і мережевих інфраструктур, поступово витісняючи традиційні bypass-рішення (такі як чистий DPDK) у багатьох нішах.
