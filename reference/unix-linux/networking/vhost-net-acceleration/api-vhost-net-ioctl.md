# 📋 Інтерфейс системних викликів ioctl та структури ядра /dev/vhost-net

Символьний пристрій `/dev/vhost-net` надає спеціалізований інтерфейс системних викликів `ioctl()` для передачі управління площиною даних (Data Plane) мережевих кільцевих буферів `virtio` від гіпервізора простору користувача (QEMU, kvmtool чи власного монітора віртуальних машин) до ядра Linux. Інтерфейс та відповідні структури даних визначено у заголовочних файлах ядра `<linux/vhost.h>` та `<linux/vhost_types.h>`.

Усі операції з налаштування та управління модулем ядра виконуються через один відкритий файловий дескриптор пристрою `/dev/vhost-net`. Завдяки використанню класичного механізму системних викликів `ioctl()`, розробники гіпервізорів отримали можливість прозоро конфігурувати пам'ять, кільцеві буфери, файлові дескриптори сповіщень `eventfd` та мережеві бекенди без створення додаткових файлових систем чи складних сокетних протоколів.

## Принцип роботи та порядок ініціалізації викликів ioctl

Процес ініціалізації прискорювача `vhost-net` вимагає суворого дотримання послідовності системних викликів `ioctl()`. Порушення порядку (наприклад, спроба налаштувати адреси кільця до передачі мапування пам'яті) призводить до повернення помилок `EINVAL` або `EFAULT`.

Управління пристроєм складається з кількох послідовних фаз:

1. **Фаза ініціалізації власності (Ownership Assignment):** Гіпервізор відкриває символьний файл `/dev/vhost-net` за допомогою виклику `open("/dev/vhost-net", O_RDWR)` і негайно виконує команду `VHOST_SET_OWNER`. Ця операція прив'язує відкритий дескриптор до поточного процесу (структури `struct task_struct`) та його таблиці сторінок пам'яті (структури `struct mm_struct`).
2. **Фаза узгодження можливостей (Feature Negotiation):** Гіпервізор зчитує бітову маску підтримуваних ядром розширень за допомогою `VHOST_GET_FEATURES`, порівнює їх із можливостями гостьового драйвера `virtio-net` і відправляє підтверджений набір назад ядру через `VHOST_SET_FEATURES`.
3. **Фаза передачі карти пам'яті (Memory Mapping):** За допомогою виклику `VHOST_SET_MEM_TABLE` гіпервізор передає ядру структуру `struct vhost_memory`, яка описує мапування фізичної пам'яті віртуальної машини (GPA) у віртуальний адресний простір процесу гіпервізора (HVA).
4. **Фаза конфігурації кільцевих буферів (Virtqueue Configuration):** Для кожної черги `virtqueue` (RX = 0, TX = 1) гіпервізор передає розмір кільця (`VHOST_SET_VRING_NUM`), віртуальні адреси трикутника буферів (`VHOST_SET_VRING_ADDR`) та початкові індекси читання/запису (`VHOST_SET_VRING_BASE`).
5. **Фаза прив'язки каналів сигналізації (Notification Setup):** Гіпервізор передає ядру файлові дескриптори `eventfd` для обробки сигналів «kick» від гостя (`VHOST_SET_VRING_KICK`) та для виклику MSI-X переривань у гості (`VHOST_SET_VRING_CALL`).
6. **Фаза прив'язки мережевого бекенду (Backend Binding):** Гіпервізор передає відкритий дескриптор TAP-пристрою за допомогою виклику `VHOST_NET_SET_BACKEND`. З цього моменту ядро Linux запускає потік `vhost-$PID` і розпочинає прискорену обробку кадерів.

## Докладна таблиця управляючих команд ioctl

У наступній таблиці зібрано всі ключові команди `ioctl`, які використовуються для ініціалізації, налаштування пам'яті, конфігурації черг та прив'язки мережевих бекендів.

| Управляюча команда (ioctl opcode) | Тип аргументу | Опис та призначення |
| :--- | :--- | :--- |
| `VHOST_SET_OWNER` | `void` (без аргументів) | Прив'язує дескриптор `/dev/vhost-net` до поточного процесу. Ініціалізує контекст безпеки та структуру `struct vhost_dev`. Викликається першою. |
| `VHOST_RESET_OWNER` | `void` (без аргументів) | Скидає стан бекенду, звільняє таблиці пам'яті, зупиняє потоки ядра `vhost-$PID` та повертає пристрій у початковий стан. |
| `VHOST_GET_FEATURES` | `uint64_t*` (out) | Зчитує бітову маску можливостей (features), які підтримуються модулем ядра `vhost-net` (наприклад, `VHOST_F_LOG_ALL`, `VHOST_NET_F_VIRTIO_NET_HDR`). |
| `VHOST_SET_FEATURES` | `uint64_t*` (in) | Узгоджує та встановлює бітову маску можливостей між гіпервізором та ядром. |
| `VHOST_SET_MEM_TABLE` | `struct vhost_memory*` | Передає ядру повну карту мапування фізичної пам'яті гостя (GPA) у віртуальний адресний простір хоста (HVA). |
| `VHOST_SET_VRING_NUM` | `struct vhost_vring_state*` | Встановлює розмір кільцевого буфера `virtqueue` (кількість дескрипторів у кільці, наприклад 256, 512, 1024). |
| `VHOST_SET_VRING_ADDR` | `struct vhost_vring_addr*` | Надає ядру віртуальні адреси хоста (HVA) для Descriptor Table, Available Ring та Used Ring. |
| `VHOST_SET_VRING_BASE` | `struct vhost_vring_state*` | Встановлює початкові індекси читання/запису у черзі `virtqueue` (використовується при міграції ВМ). |
| `VHOST_GET_VRING_BASE` | `struct vhost_vring_state*` (in/out) | Зчитує поточні індекси черги для збереження стану віртуальної машини перед міграцією. |
| `VHOST_SET_VRING_KICK` | `struct vhost_vring_file*` | Передає файловий дескриптор `eventfd` (`ioeventfd`), який KVM сигналізує при записі гостя у регістр `kick`. |
| `VHOST_SET_VRING_CALL` | `struct vhost_vring_file*` | Передає файловий дескриптор `eventfd` (`irqfd`), через який `vhost-net` викликає MSI-X переривання в гості. |
| `VHOST_SET_VRING_ERR` | `struct vhost_vring_file*` | Передає `eventfd` для сповіщення про помилки обробки черги (необов'язково). |
| `VHOST_NET_SET_BACKEND` | `struct vhost_vring_file*` | Специфічна команда `vhost-net`: прив'язує відкритий файловий дескриптор TAP-пристрою (`/dev/net/tun`) до конкретної черги `virtqueue`. |

## Основні структури даних ядра та алгоритми їх обробки

### 1. Карта пам'яті: struct vhost_memory та struct vhost_memory_region

Потік ядра `vhost-net` повинен мати можливість читати та записувати дані в буфери пам'яті гостя. Оскільки гіпервізор виділяє пам'ять гостя через системний виклик `mmap()`, ядро оперує зсувами між фізичною адресою гостя (GPA — Guest Physical Address) та віртуальною адресою в процесі гіпервізора (HVA — Host Virtual Address).

Структура `struct vhost_memory` описує повний набір фізичних регіонів пам'яті віртуальної машини:

```c
struct vhost_memory_region {
    uint64_t guest_phys_addr; /* Початкова фізична адреса у гості (GPA) */
    uint64_t memory_size;     /* Розмір сегмента пам'яті в байтах */
    uint64_t userspace_addr;  /* Початкова віртуальна адреса в гіпервізорі (HVA) */
    uint64_t flags_padding;   /* Допоміжні прапори та вирівнювання */
};

struct vhost_memory {
    uint32_t nregions;        /* Кількість сегментів пам'яті */
    uint32_t padding;         /* Вирівнювання структури */
    struct vhost_memory_region regions[0]; /* Гнучкий масив сегментів */
};
```

#### Детальний механізм трансляції GPA в HVA

Коли потік `vhost-net` зчитує з дескриптора `vring_desc` фізичну адресу кадру `gpa_addr`, він шукає відповідний регіон у масиві `regions` структури `vhost_memory`:

1. Процес обходить масив регіонів від `0` до `nregions - 1`.
2. Для кожного регіону перевіряється умова входження адреси:
   `guest_phys_addr <= gpa_addr < guest_phys_addr + memory_size`
3. Якщо умову виконано, обчислюється віртуальна адреса хоста:
   `hva_addr = userspace_addr + (gpa_addr - guest_phys_addr)`
4. Отримана адреса `hva_addr` перевіряється на право доступу за допомогою функцій `copy_from_user()` / `copy_to_user()`, або закріплюється у системі пейджингу ядра за допомогою `get_user_pages_fast()`.

Якщо адреса `gpa_addr` не потрапляє у жоден з описаних регіонів пам'яті, ядро припиняє обробку черги, генерує системну помилку та надсилає сигнал сповіщення про помилку (якщо було налаштовано `VHOST_SET_VRING_ERR`).

### 2. Конфігурація адресації кільцевих буферів: struct vhost_vring_addr

Структура `struct vhost_vring_addr` передає ядру віртуальні адреси трикутника буферів `virtqueue` (Descriptor Table, Available Ring, Used Ring) для конкретної черги (індекс `index`):

```c
struct vhost_vring_addr {
    uint32_t index;           /* Номер черги (0 = RX queue, 1 = TX queue) */
    uint32_t flags;           /* Прапори (наприклад, VHOST_VRING_F_LOG) */
    uint64_t desc_user_addr;  /* HVA адреса таблиці дескрипторів (vring_desc) */
    uint64_t used_user_addr;  /* HVA адреса кільця оброблених буферів (vring_used) */
    uint64_t avail_user_addr; /* HVA адреса кільця доступних буферів (vring_avail) */
    uint64_t log_guest_addr;  /* Адреса для логування брудних сторінок при Live Migration */
};
```

Слід звернути увагу, що всі адреси (`desc_user_addr`, `used_user_addr`, `avail_user_addr`) передаються у форматі віртуальних адрес хоста HVA. Ядро Linux самостійно транслює їх у фізичні сторінки оперативної пам'яті host за допомогою внутрішньої підсистеми MMU.

### 3. Структури стану та прив'язки файлових дескрипторів

Для встановлення кількості елементів у кільці та початкових індексів використовується структура `struct vhost_vring_state`:

```c
struct vhost_vring_state {
    uint32_t index;  /* Номер черги virtqueue */
    uint32_t num;    /* Кількість елементів / початковий індекс (idx) */
};
```

Для прив'язки дескрипторів `eventfd` (`ioeventfd`, `irqfd`) та мережевого бекенду (TAP fd) використовується структура `struct vhost_vring_file`:

```c
struct vhost_vring_file {
    uint32_t index;  /* Номер черги virtqueue */
    int fd;          /* Файловий дескриптор (eventfd або TAP fd; -1 розриває прив'язку) */
};
```

Передача значення `fd = -1` у викликах `VHOST_SET_VRING_KICK`, `VHOST_SET_VRING_CALL` або `VHOST_NET_SET_BACKEND` використовується для безпечного тимчасового відключення сповіщень або розриву зв'язку з бекендом без повного знищення контексту `vhost`.

## Структури кільцевих буферів virtqueue у спільній пам'яті

Модуль ядра `vhost-net` інтерпретує пам'ять за адресами `desc_user_addr`, `avail_user_addr` та `used_user_addr` відповідно до стандарту Virtio Specification v1.1.

### Таблиця дескрипторів: struct vring_desc

Таблиця дескрипторів містить масив елементів, кожен з яких описує один неперервний фрагмент пам'яті:

```c
struct vring_desc {
    uint64_t addr;  /* Фізична адреса буфера у гості (GPA) */
    uint32_t len;   /* Довжина буфера в байтах */
    uint16_t flags; /* Прапори: VRING_DESC_F_NEXT (1), VRING_DESC_F_WRITE (2), VRING_DESC_F_INDIRECT (4) */
    uint16_t next;  /* Індекс наступного дескриптора в ланцюжку (якщо встановлено VRING_DESC_F_NEXT) */
};
```

Прапори дескриптора визначають його поведінку:
- `VRING_DESC_F_NEXT (1)` — вказує, що дане кадрове повідомлення не вмістилося в один буфер, і наступний дескриптор ланцюжка знаходиться за індексом `next`.
- `VRING_DESC_F_WRITE (2)` — вказує, що буфер призначений для запису пристроєм (буфер прийому RX). Якщо прапор не встановлено, буфер є лише для читання (буфер передачі TX).
- `VRING_DESC_F_INDIRECT (4)` — вказує, що поле `addr` містить фізичну адресу не самого кадру, а додаткової непрямої таблиці дескрипторів. Це дозволяє упаковувати великі ланцюжки дескрипторів в один елемент головного кільця.

### Кільце доступних буферів: struct vring_avail

```c
struct vring_avail {
    uint16_t flags;     /* VRING_AVAIL_F_NO_INTERRUPT (1 = пригнічення переривань) */
    uint16_t idx;       /* Індекс наступного елемента, який запише гість */
    uint16_t ring[N];   /* Масив індексів головних дескрипторів з Descriptor Table */
    uint16_t used_event;/* Вказувач порогу сповіщення (при розширенні VIRTIO_F_EVENT_IDX) */
};
```

### Кільце оброблених буферів: struct vring_used

```c
struct vring_used_elem {
    uint32_t id;   /* Індекс головного дескриптора ланцюжка з Descriptor Table */
    uint32_t len;  /* Кількість записаних у буфер байтів */
};

struct vring_used {
    uint16_t flags;                /* VRING_USED_F_NO_NOTIFY (1 = пригнічення kick) */
    uint16_t idx;                  /* Індекс наступного елемента, який запише vhost */
    struct vring_used_elem ring[N];/* Масив результатів обробки */
    uint16_t avail_event;          /* Вказувач порогу сповіщення */
};
```

## Механізм логування брудних сторінок для Live Migration

Під час живої міграції віртуальної машини (Live Migration) процес гіпервізора QEMU повинен відстежувати всі зміни в оперативній пам'яті гостя, які здійснюються пристроєм `vhost-net` у ядрі.

Для цього використовується виклик `VHOST_SET_LOG_BASE`. Гіпервізор виділяє бітову карту (bitmap), де кожен біт відповідає одній сторінці пам'яті (4 КБ). Адреса цієї бітової карти передається ядру.

Коли потік `vhost-net` записує вхідний пакет у пам'ять гостя (RX queue), він викликає внутрішню функцію ядра `vhost_log_write()`. Ця функція встановлює відповідні біти у бітовій карті брудних сторінок (dirty bitmap). Гіпервізор QEMU періодично зчитує цю карту і повторно відправляв змінені сторінки пам'яті на цільовий хост міграції.

## Детальний аналіз кодів помилок системного виклику ioctl

При виконанні системного виклику `ioctl()` на `/dev/vhost-net` ядро повертає `0` у разі успіху або `-1` при помилці, встановлюючи глобальну змінну `errno`.

Нижче наведено вичерпний розбір причин виникнення системних помилок:

- `EBADF` — передано недійсний файловий дескриптор. Помилка виникає, якщо `fd` не відкритий, закритий у сусідньому потоці, або якщо дескриптор у `VHOST_NET_SET_BACKEND` не є дійсним TAP-сокетом.
- `EINVAL` — передано недійсні аргументи. Основні причини:
  1. Кількість елементів у `VHOST_SET_VRING_NUM` перевищує допустимий ліміт ядра (32768) або не є ступенем двійки.
  2. Переданий номер черги `index` перевищує кількість черг, підтримуваних даним бекендом.
  3. Невирівняні адреси у `VHOST_VRING_ADDR` (таблиця дескрипторів вимагає вирівнювання на 16 байтів).
- `EFAULT` — помилка адресації пам'яті. Ядро Linux не змогло прочитати або записати дані за вказаною віртуальною адресою простору користувача (помилка у внутрішніх функціях `copy_from_user()` або `get_user_pages_fast()`). Помилка часто виникає, якщо адреса HVA в `vhost_memory` вказує на вивільнену або невідображену область пам'яті (`SIGSEGV`).
- `EEXIST` / `EBUSY` — пристрій або черга вже мають призначеного власника або бекенд. Спроба повторно викликати `VHOST_SET_OWNER` без попереднього `VHOST_RESET_OWNER`, або спроба прив'язати TAP-дескриптор, який вже використовується іншим потоком `vhost`.
- `ENOMEM` — недостатньо оперативної пам'яті ядра для виділення внутрішніх структур `struct vhost_net`, створення таблиць мапування або створення dedicated потоку ядра `vhost-$PID`.
- `EPERM` / `EACCES` — процес не має належних привілеїв. Для відкриття `/dev/vhost-net` та створення мережевих бекендів вимагаються права користувача `root` або наявність системної правової категорії `CAP_NET_ADMIN`.
- `EOPNOTSUPP` — обрана функціональність не підтримується поточним модулем ядра або мережевим драйвером. Наприклад, спроба увімкнути Zero-Copy режим на пристрої, драйвер якого не підтримує закріплення сторінок з лічильником посилань.
