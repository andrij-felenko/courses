# Маршрутизація XDP: BPF_MAP_TYPE_CPUMAP та BPF_MAP_TYPE_DEVMAP

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

eBPF та XDP (eXpress Data Path) надають потужні механізми для високопродуктивної обробки мережевих пакетів безпосередньо в ядрі Linux. Найбільша перевага XDP полягає в тому, що пакети обробляються ще до створення мережевим стеком ядра структури `sk_buff` (skb), що суттєво зменшує накладні витрати на аллокацію пам'яті та копіювання даних.

У цій статті ми детально розглянемо два ключові типи BPF-карт (eBPF maps), які використовуються для маршрутизації та перенаправлення трафіку в XDP: `BPF_MAP_TYPE_CPUMAP` та `BPF_MAP_TYPE_DEVMAP`. Ці структури даних дозволяють ефективно балансувати навантаження між ядрами процесора (CPU) та перенаправляти пакети на інші мережеві інтерфейси (NIC) на ранніх етапах обробки, досягаючи пропускної здатності в мільйони пакетів за секунду (Mpps).

## 1. Концепція XDP Redirect

У базовому варіанті XDP-програма може повернути один із кількох кодів дії (action codes):
- `XDP_DROP` — відкинути пакет.
- `XDP_PASS` — передати пакет далі в мережевий стек Linux (створюється skb).
- `XDP_TX` — відправити пакет назад через той самий інтерфейс, з якого він надійшов.
- `XDP_ABORTED` — помилка обробки.
- `XDP_REDIRECT` — перенаправити пакет.

Дія `XDP_REDIRECT` є найцікавішою з точки зору маршрутизації. Вона вказує ядру, що пакет потрібно відправити не в стандартний мережевий стек, а в інше місце призначення. Місце призначення задається за допомогою BPF-карти та спеціальної допоміжної функції (helper function) `bpf_redirect_map()`.

Функція `bpf_redirect_map()` записує намір перенаправлення в локальні структури даних поточного CPU (per-CPU дані), а фактичне перенаправлення відбувається вже після завершення виконання XDP-програми, коли ядро опрацьовує код повернення `XDP_REDIRECT`.

## 2. BPF_MAP_TYPE_CPUMAP: Перенаправлення на інші CPU

Тип карти `BPF_MAP_TYPE_CPUMAP` використовується для масштабування обробки пакетів на багатоядерних системах. Вона дозволяє XDP-програмі, яка виконується на одному CPU (CPU прийому пакетів - RX), перенаправити пакет для подальшої обробки в мережевий стек ядра на інший CPU.

### Проблема, яку вирішує CPUMAP

Зазвичай переривання від мережевого інтерфейсу (NIC) прив'язані до певних CPU (за допомогою механізму SMP IRQ affinity). Якщо один CPU перевантажений обробкою пакетів з однієї черги (RX queue), загальна пропускна здатність системи обмежується продуктивністю цього єдиного ядра. Механізми на кшталт Receive Packet Steering (RPS) намагаються вирішити цю проблему, розподіляючи skb між різними CPU. Однак RPS працює *після* того, як пакет перетворився на `sk_buff`, що означає, що початковий CPU все одно витрачає значні ресурси на аллокацію пам'яті.

CPUMAP вирішує це на рівні XDP — *до* створення skb. XDP-програма приймає сирий пакет і за допомогою CPUMAP кладе його в lockless-чергу, пов'язану з іншим CPU. Той, інший CPU, потім "забирає" пакет з черги, самостійно створює `sk_buff` і передає його в TCP/IP стек. Таким чином, дорогі операції зі створення skb розпаралелюються.

### Як працює CPUMAP

1. **Створення карти**: У просторі користувача створюється карта типу `BPF_MAP_TYPE_CPUMAP`. Ключем є індекс (ID) цільового процесора (наприклад, 0, 1, 2...), а значенням — розмір черги (queue size), який визначає кількість пакетів, що можуть очікувати на обробку цим процесором.

2. **Заповнення карти**: Користувацька програма записує значення (розмір черги) у слоти карти, відповідні CPU, на які дозволено перенаправляти трафік.

3. **Виконання XDP (RX CPU)**: 
   - XDP-програма отримує пакет.
   - Виконує певний алгоритм балансування (наприклад, обчислює хеш від IP-адрес і портів).
   - Визначає цільовий `cpu_id`.
   - Викликає `bpf_redirect_map(&cpu_map, cpu_id, 0)`.
   - Повертає `XDP_REDIRECT`.

4. **Асинхронна обробка (Target CPU)**:
   - Цільовий процесор отримує сигнал (Inter-Processor Interrupt, IPI) або обробляє чергу в своєму циклі NAPI.
   - Бере пакети з черги, створює для них `sk_buff`.
   - Передає пакети в стандартний мережевий стек ядра.

### Приклад коду (XDP C програма)

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_CPUMAP);
    __uint(max_entries, 128); /* Максимум 128 CPU */
    __type(key, __u32);
    __type(value, __u32);
} cpu_map SEC(".maps");

SEC("xdp")
int xdp_redirect_cpu(struct xdp_md *ctx)
{
    __u32 cpu_id = 4; /* Спрощений приклад: завжди скеровуємо на CPU 4 */
    
    /* bpf_redirect_map повертає XDP_REDIRECT, якщо запис існує, 
     * або XDP_ABORTED, якщо перенаправлення неможливе */
    return bpf_redirect_map(&cpu_map, cpu_id, 0);
}

char _license[] SEC("license") = "GPL";
```

## 3. BPF_MAP_TYPE_DEVMAP: Перенаправлення на інші інтерфейси

Тип карти `BPF_MAP_TYPE_DEVMAP` дозволяє перенаправити пакет на інший мережевий інтерфейс без проходження через мережевий стек ядра. Це ключовий компонент для створення високопродуктивних програмних маршрутизаторів (software routers), балансувальників навантаження (load balancers) та віртуальних комутаторів.

### Проблема, яку вирішує DEVMAP

Традиційна маршрутизація (L3) або комутація (L2) в Linux вимагає, щоб пакет перетворився на `sk_buff`, пройшов через `netfilter` (iptables/nftables), таблиці маршрутизації ядра, підсистему черг (qdisc), і нарешті потрапив до драйвера передавального (TX) інтерфейсу. Це створює затримки та знижує пропускну здатність.

DEVMAP дозволяє драйверу RX-інтерфейсу (після виконання XDP) безпосередньо передати сторінку пам'яті з пакетом у драйвер TX-інтерфейсу, обходячи весь проміжний стек Linux.

### Як працює DEVMAP

1. **Створення карти**: Створюється карта `BPF_MAP_TYPE_DEVMAP` (або її оптимізований варіант `BPF_MAP_TYPE_DEVMAP_HASH`).
2. **Заповнення карти (userspace)**: Ключем є умовний індекс інтерфейсу (часто це `ifindex` мережевого пристрою в ОС Linux), а значенням є конфігураційна структура або просто індекс (залежить від конкретного використання, але зазвичай використовується для ідентифікації порту). В карту додаються інтерфейси (ifindex), куди може йти трафік.
3. **Обробка в XDP**:
   - XDP-програма аналізує MAC або IP адреси пакета.
   - Заглядає у власні таблиці маршрутизації (інші BPF карти).
   - Визначає `ifindex` вихідного інтерфейсу.
   - Модифікує заголовки пакета (наприклад, замінює MAC-адреси, зменшує TTL).
   - Викликає `bpf_redirect_map(&dev_map, ifindex, 0)`.
   - Повертає `XDP_REDIRECT`.

### Оптимізація Bulk Transmit (Пакетна передача)

Особливість `DEVMAP` полягає в тому, що пакети не відправляються відразу по одному (це було б неефективно через накладні витрати доступу до регістрів NIC). Натомість ядро використовує прихований буфер (bulk queue). Пакет спочатку поміщається у цей буфер. Коли буфер заповнюється (або коли завершується цикл NAPI), функція `xdp_do_flush()` відправляє весь пакет (batch) пакетів драйверу TX інтерфейсу одним викликом, що різко підвищує продуктивність.

### Приклад коду (XDP C програма)

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_DEVMAP);
    __uint(max_entries, 64);
    __type(key, __u32);   /* ifindex */
    __type(value, __u32); /* ifindex */
} tx_port SEC(".maps");

SEC("xdp")
int xdp_router(struct xdp_md *ctx)
{
    __u32 tx_ifindex = 2; /* Припустимо, eth1 має ifindex = 2 */
    
    /* Тут зазвичай відбувається зміна MAC-адрес (L2 rewrite) */

    return bpf_redirect_map(&tx_port, tx_ifindex, 0);
}

char _license[] SEC("license") = "GPL";
```

## 4. Висновок

Карти `CPUMAP` та `DEVMAP` розкривають справжню міць XDP для маршрутизації та балансування навантаження. `CPUMAP` розв'язує проблему процесорного "вузького горла" (bottleneck) при створенні `sk_buff`, розподіляючи обробку між багатьма CPU. `DEVMAP` дозволяє будувати високопродуктивні dataplane-додатки (роутери, свічі), які можуть пересилати пакети між мережевими картками без найменшої участі мережевого стеку ядра Linux, досягаючи wire-speed продуктивності. Поєднання цих технологій з логікою, реалізованою в eBPF, створює гнучкий, програмований і неймовірно швидкий фундамент для сучасних мережевих рішень.
