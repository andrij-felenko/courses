# Сучасний інтерфейс налаштування мережі ethtool Netlink

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Управління мережевими адаптерами в Linux історично здійснювалося через системний виклик `ioctl` та команду `ethtool`. Однак, з розвитком мережевих технологій та збільшенням складності мережевих пристроїв, старий інтерфейс `ioctl(SIOCETHTOOL)` виявився недостатньо гнучким, масштабованим та безпечним для сучасних потреб. Для вирішення цих проблем у ядрі Linux було розроблено новий інтерфейс на основі **Generic Netlink**, який прийшов на заміну традиційному `ioctl`. 

Ця стаття детально розглядає архітектуру ethtool Netlink інтерфейсу, його переваги, внутрішню будову, типи повідомлень та способи його використання в сучасних Linux системах.

## 1. Проблеми застарілого `ioctl(SIOCETHTOOL)`

Інтерфейс `ioctl` для налаштування мережевих карт існує в Linux з 1990-х років. Він використовує системний виклик `ioctl()` на сокеті з командою `SIOCETHTOOL`. Дані передаються через структуру `ethtool_cmd` або інші подібні структури, що передаються в ядро. Незважаючи на свою простоту і довголіття, цей підхід має низку фундаментальних недоліків.

### 1.1. Фіксований розмір структур

Команди `ioctl` зазвичай використовують структури фіксованого розміру для обміну даними між простором користувача та ядром. Коли з'являються нові технології (наприклад, нові швидкості передачі даних, понад 100Gbps, нові типи лінків), старі структури стають замалими. Щоб додати підтримку нових швидкостей, розробникам доводилося створювати нові `ioctl` команди та нові структури (наприклад, `ethtool_cmd` замінено на `ethtool_link_settings`), що призводило до дублювання коду та плутанини.

### 1.2. Відсутність механізму сповіщень (Notifications)

`ioctl` є синхронним викликом типу "запит-відповідь". Якщо стан мережевого інтерфейсу змінюється (наприклад, кабель відключено, швидкість змінилася), простір користувача не може дізнатися про це автоматично, окрім як періодично опитувати інтерфейс (polling), що є неефективним з точки зору використання ресурсів процесора.

### 1.3. Безпека і Привілеї

Для виконання більшості операцій `ethtool` через `ioctl` вимагаються привілеї `CAP_NET_ADMIN`. Неможливо було тонко налаштувати права доступу: наприклад, дозволити певному користувачеві лише читати певну статистику, не маючи повних прав адміністратора мережі.

### 1.4. Проблеми з розширенням

Кожен новий функціонал, що додається до мережевих карт (наприклад, енергозбереження EEE, Forward Error Correction, налаштування кільцевих буферів), вимагав створення нового макросу команди та структури, що ускладнювало підтримку сумісності (ABI) і збільшувало розмір коду в ядрі.

## 2. Архітектура Ethtool Netlink

Для подолання вищезазначених обмежень, починаючи з версії ядра Linux 5.6 (2020 рік), було інтегровано новий інтерфейс на базі **Generic Netlink**.

![Архітектура ethtool: ioctl vs netlink](/reference/unix-linux/networking/ethtool-netlink-interface/img/ethtool-arch.svg)
*Рис. 1. Еволюція API налаштування мережі: ioctl vs Netlink*

Netlink — це сімейство сокетів (`AF_NETLINK`), розроблене спеціально для зв'язку між простором користувача і ядром. Він використовує парадигму повідомлень з гнучким форматуванням даних (TLV - Type-Length-Value), що дозволяє легко додавати нові поля без порушення зворотної сумісності. 

**Generic Netlink** — це надбудова над Netlink, що дозволяє створювати власні "сімейства" протоколів без необхідності виділення постійних констант в ядрі.

### 2.1. Переваги Netlink інтерфейсу

1. **Гнучкість та Розширюваність**: Завдяки атрибутам Netlink (Netlink Attributes, NLA), повідомлення можуть містити лише необхідні поля. Ядро та утиліта `ethtool` можуть обмінюватися лише тими даними, які їм відомі, ігноруючи невідомі атрибути.
2. **Асинхронні сповіщення (Multicast Groups)**: Простір користувача може підписатися на Multicast групу Netlink (зокрема, групу `monitor`) і миттєво отримувати повідомлення від ядра при зміні стану лінку, зміні налаштувань тощо, без необхідності polling.
3. **Обробка багатьох пристроїв одночасно**: Netlink дозволяє передавати масив повідомлень для отримання стану багатьох інтерфейсів за один виклик, що значно пришвидшує роботу на системах з великою кількістю віртуальних або фізичних інтерфейсів.
4. **Контекстні помилки**: Netlink дозволяє повертати точні текстові повідомлення про помилки з простору ядра (через механізм `extack`), що значно полегшує зневадження ("Чому не можна встановити цю швидкість?").

## 3. Внутрішня будова в ядрі Linux

Сімейство ethtool netlink реєструється в ядрі з назвою `ethtool`. Ви можете переглянути його наявність за допомогою утиліти `genl`:
```bash
$ genl ctrl get name ethtool
Name: ethtool
ID: 0x1f
Version: 1
Commands: 39
```

### 3.1. Структури даних та повідомлення

Усі повідомлення Generic Netlink для ethtool визначені у заголовковому файлі `<linux/ethtool_netlink.h>`.
Повідомлення розділені на запити (від користувача до ядра) і відповіді (від ядра до користувача).

Типові префікси для ідентифікаторів повідомлень:
* `ETHTOOL_MSG_*_GET` — запит на читання інформації.
* `ETHTOOL_MSG_*_SET` — запит на зміну інформації.
* `ETHTOOL_MSG_*_NTF` — повідомлення (notification) про зміну (розіслане ядром у multicast).

Наприклад, базове налаштування лінку (link settings):
* `ETHTOOL_MSG_LINKINFO_GET`
* `ETHTOOL_MSG_LINKINFO_SET`
* `ETHTOOL_MSG_LINKINFO_NTF`

### 3.2. Формат заголовка Netlink (Ethtool Header)

Кожен запит ethtool netlink містить стандартний заголовок (`ethtool_header`), який вказує на те, до якого інтерфейсу застосовується запит. Це робиться за допомогою атрибутів, які можуть ідентифікувати пристрій:

* `ETHTOOL_A_HEADER_DEV_INDEX`: Ifindex (цілочисельний індекс інтерфейсу, наприклад 2).
* `ETHTOOL_A_HEADER_DEV_NAME`: Ім'я інтерфейсу (наприклад, "eth0").

### 3.3. Взаємодія з драйверами (`ethtool_ops`)

Хоча інтерфейс користувача змінився з `ioctl` на `Netlink`, драйвери мережевих карт в ядрі все ще здебільшого використовують структуру `struct ethtool_ops`, яка зареєстрована для пристрою (`netdev->ethtool_ops`). 

Ядро автоматично транслює Netlink запити у відповідні виклики функцій з `ethtool_ops`.
Наприклад, при отриманні `ETHTOOL_MSG_LINKINFO_GET` через Netlink, ядро знаходить мережевий пристрій, отримує блокування, і викликає `netdev->ethtool_ops->get_link_ksettings()`. Далі ядро пакує отримані дані у Netlink атрибути і надсилає назад користувачу.

## 4. Класифікація повідомлень Netlink API

Ethtool Netlink API розділене на логічні блоки, які відповідають різним аспектам налаштування інтерфейсу. Нижче розглянуті найважливіші групи.

### 4.1. Link Info & Link Modes (Стан лінку та швидкості)

* **LINKINFO**: Дані про фізичний порт, налаштування MDI/MDI-X, трансівер.
* **LINKMODES**: Підтримувані, анонсовані (advertised) швидкості та режим автоузгодження (Autonegotiation). За допомогою атрибутів (наприклад, `ETHTOOL_A_LINKMODES_OURS`), ядро передає бітові карти (bitmaps) доступних режимів (1000baseT/Full, 10GbaseT/Full тощо).
* **LINKSTATE**: Поточний стан лінку (Up/Down) та детальна інформація про причину відсутності лінку (Extended Link State).

### 4.2. Wake-on-LAN (WoL)

* **WOL**: Отримання та налаштування параметрів Wake-on-LAN (наприклад, "g" для Magic Packet, "p" для PHY activity) та SecureOn паролів.

### 4.3. Офлоадинг (Features Offload)

* **FEATURES**: Керування апаратним прискоренням (RX/TX Checksum, TSO, LRO, GRO, Scatter-Gather тощо). Утиліта `ethtool -k` / `ethtool -K` використовує ці повідомлення.

### 4.4. Кільцеві буфери (Rings) та Канали (Channels)

* **RINGS**: Кількість дескрипторів у буферах прийому (RX) та передачі (TX). Команди: `ethtool -g` та `ethtool -G`.
* **CHANNELS**: Кількість апаратних черг (каналів), що використовуються мережевою картою, зазвичай відповідає кількості переривань MSI-X або кількості CPU ядер (RSS). 

### 4.5. Статистика (Stats)

Звичайний `ioctl` мав великі проблеми з масштабуванням статистики (команда `ethtool -S`), оскільки драйвер передавав один великий блок неструктурованих рядкових назв і значень, що було повільним і незручним.
Netlink впровадив стандартизовану статистику (RMON, PHY, MAC). Група **STATS** дозволяє ядра групувати стандартну IEEE 802.3 статистику, що дозволяє різним утилітам (не тільки `ethtool`) програмно парсити показники помилок (FCS errors, collisions, pause frames).

### 4.6. EEE, FEC, Pause (Управління потоком)

* **EEE (Energy Efficient Ethernet)**: Налаштування режиму збереження енергії.
* **FEC (Forward Error Correction)**: Налаштування корекції помилок для швидкісних лінків (25G, 50G, 100G).
* **PAUSE**: Налаштування IEEE 802.3x PAUSE фреймів (Автоматичне, RX, TX).

## 5. Практичне застосування та відлагодження (Debugging)

### 5.1. Утиліта ethtool та підтримка Netlink

Сучасні версії утиліти `ethtool` (починаючи з версії 5.6) автоматично використовують Netlink, якщо ядро його підтримує. Якщо інтерфейс недоступний, або відбувається помилка, `ethtool` здійснює плавний "fallback" до старого `ioctl` інтерфейсу.

Користувач може примусово наказати `ethtool` не використовувати Netlink для відлагодження, використовуючи змінну оточення `ETHTOOL_NETLINK`:

```bash
# Примусово використовувати Netlink (за замовчуванням, якщо підтримується)
$ ethtool eth0

# Примусово використовувати застарілий ioctl
$ ETHTOOL_NETLINK=0 ethtool eth0
```

### 5.2. Моніторинг мережевих подій

Одна з найкорисніших функцій Netlink API — це можливість моніторити події в реальному часі. Ви можете виконати команду:

```bash
$ ethtool --monitor eth0
```

Якщо після цього ви підключите або відключите мережевий кабель, ви побачите сповіщення (Notification) безпосередньо в консолі, згенероване `ETHTOOL_MSG_LINKSTATE_NTF`. Це ідеально для написання мережевих демонів, які реагують на зміни топології.

### 5.3. Розширена діагностика повідомлень про помилки (Extack)

Якщо ви спробуєте налаштувати параметр, який мережева карта не підтримує (через Netlink), ядро поверне детальну текстову помилку, прикріплену до Netlink повідомлення (механізм Extended ACK).

Наприклад:
```bash
$ ethtool -s eth0 speed 10000 duplex full
netlink error: Operation not supported
netlink error: speed 10000 is not advertised or supported by device
```
З `ioctl` ви б отримали лише стандартну безлику помилку `EINVAL` (Invalid argument).

## 6. Виклики та перспективи розвитку

Поточне завдання розробників ядра — поступово перевести всі драйвери та всі складні опції налаштування суто на Netlink. Деякі екзотичні опції або специфічні для певних вендорів команди (наприклад, прошивка EEPROM, деякі аспекти перевірки самодіагностики `ethtool -t`) все ще сильно покладаються на старі механізми.

Проте, для розробників вбудованих систем (embedded systems) і сучасних мережевих ОС (як Cumulus Linux, SONiC), ethtool netlink надає надійний, програмований і швидкий спосіб масового конфігурування тисяч інтерфейсів у дата-центрах без накладних витрат на синхронні системні виклики.

## Висновки

Інтерфейс **ethtool Netlink** є величезним кроком вперед для мережевої підсистеми Linux. Він вирішує хронічні проблеми масштабованості, безпеки, та відсутності механізму підписок (notifications), які були притаманні старому `ioctl(SIOCETHTOOL)`. Розробникам і системним адміністраторам він надає більш багаті можливості діагностики та гнучкість, відкриваючи шлях до кращої програмної автоматизації управління мережею (SDN) на рівні операційної системи.
