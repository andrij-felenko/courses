# Мережевий стек ядра Linux: архітектура та шлях пакета

<preknowlist>
- [Системні виклики та VFS](topic:unix-linux/kernel-and-userspace) — як працюють файлові дескриптори.
- [Пам'ять ядра](topic:unix-linux/kernel-memory-slab) — що таке DMA та кільцеві буфери.
</preknowlist>

Мережевий стек ядра Linux — це складна багатошарова підсистема, що передає дані між користувацькими програмами (сокетами) та фізичним мережевим адаптером (NIC). Щоб забезпечити високу пропускну здатність (десятки й сотні Гбіт/с), ядро мінімізує копіювання даних, використовує розумне переривання (NAPI) та механізми обходу (XDP, DPDK).

У цій статті ми розберемо архітектуру стека: від базової структури `sk_buff` до повного шляху відправлення (TX) та отримання (RX) пакетів.

## 1. Фундамент стека: структура `sk_buff`

Усі мережеві пакети в ядрі Linux представлені структурою `sk_buff` (socket buffer). Щоб уникнути дорогого копіювання даних при проходженні через різні рівні (додавання заголовків TCP, IP, Ethernet), `sk_buff` маніпулює вказівниками.

`sk_buff` складається з метаданих та самого буфера. Замість копіювання, ядро зсуває вказівники:

**C (sk_buff pointers)**
```c
struct sk_buff {
    /* ... метадані ... */
    struct net_device *dev; // Пристрій, до якого належить пакет
    
    /* Вказівники на буфер даних */
    unsigned char *head;  // Початок виділеної пам'яті
    unsigned char *data;  // Початок поточних корисних даних (напр. TCP-заголовок)
    unsigned char *tail;  // Кінець поточних корисних даних
    unsigned char *end;   // Кінець виділеної пам'яті
};

// При відправленні: додаємо заголовок (зсуваємо data назад)
skb_push(skb, sizeof(struct iphdr)); 

// При отриманні: знімаємо заголовок (зсуваємо data вперед)
skb_pull(skb, sizeof(struct ethhdr));
```

**BPF (__sk_buff)**
```c
/* У eBPF програмах доступна спрощена версія __sk_buff */
struct __sk_buff {
    __u32 len;
    __u32 protocol;
    __u32 ingress_ifindex;
    __u32 ifindex;
    /* ... */
};
```

Цей механізм (Zero-Copy Data Manipulation) є основою продуктивності мережевого стека.

## 2. Шлях відправлення (Transmit Path - TX)

Шлях відправлення йде згори донизу: від сокета до драйвера мережевої карти.

### 2.1. Рівень сокетів та L4
Коли програма викликає `send()`, дані проходять через VFS у мережевий рівень. Тут відбувається **єдине неминуче копіювання**: дані з user-space копіюються в новостворений `sk_buff` у kernel-space. (Виняток — механізми `sendfile` або `MSG_ZEROCOPY`).

Для TCP ядро розбиває потік на сегменти (MSS), формує заголовки, рахує контрольні суми та керує вікном перевантаження. Пакет додається до черги сокета (`sk_write_queue`).

### 2.2. Мережевий рівень (L3)
На рівні IPv4/IPv6 ядро звертається до підсистеми маршрутизації (FIB), щоб визначити наступний вузол (next hop) та вихідний інтерфейс (`net_device`).
Тут пакет проходить через хуки **Netfilter** (iptables/nftables), де може бути модифікований (NAT) або відкинутий. Далі визначається MAC-адреса через ARP/NDP, додається Ethernet-заголовок.

### 2.3. Traffic Control (qdisc) та Драйвер
Перед передачею драйверу пакет потрапляє у підсистему Traffic Control (tc). Вона містить черги (qdisc), які реалізують пріоритезацію та шейпінг (наприклад, `fq_codel`).

Функція драйвера `ndo_start_xmit()` безпосередньо працює з обладнанням:
1. Виконує мапінг DMA (Direct Memory Access), щоб NIC міг читати пам'ять.
2. Додає вказівник на дані у TX Ring (кільцевий буфер дескрипторів).
3. Повідомляє NIC через MMIO-регістр про нові дані.
NIC асинхронно зчитує пакет через DMA і відправляє його у кабель, після чого генерує переривання, щоб ядро звільнило `sk_buff`.

## 3. Шлях отримання (Receive Path - RX) та NAPI

Отримання пакетів є критичним етапом. Висока швидкість (мільйони пакетів на секунду) може спричинити "шторм переривань" (Interrupt Storm), який паралізує CPU. Тому Linux використовує механізм **NAPI** (New API).

### 3.1. Переривання та поллінг
Коли пакет прибуває, NIC пише його через DMA у RX Ring і генерує апаратне переривання (HardIRQ). 
Замість того, щоб обробляти кожен пакет, обробник HardIRQ **вимикає переривання** від цієї карти і планує програмне переривання (`NET_RX_SOFTIRQ`).

Далі ядро переходить у режим поллінгу (polling): `ksoftirqd` викликає функцію драйвера, яка пакет за пакетом вичитує RX Ring. Переривання увімкнуться знову лише тоді, коли черга спорожніє.

### 3.2. Обробка у стеку
Кожен пакет упаковується у `sk_buff`. Якщо мережева карта підтримує GRO (Generic Receive Offload), драйвер одразу об'єднує багато дрібних пакетів в один великий `sk_buff`, що радикально економить час процесора.

Далі `netif_receive_skb()` направляє пакет на L3:
- Механізм **RPS (Receive Packet Steering)** розподіляє пакети різних з'єднань між різними ядрами CPU за допомогою хешу від IP/портів, щоб не перевантажувати одне ядро.
- Пакет проходить `ip_rcv()`, перевіряється Netfilter, і nếu призначений цьому хосту, IP-заголовок знімається.
- На рівні L4 `tcp_v4_rcv()` знаходить сокет призначення, перевіряє Sequence Numbers і додає дані в `sk_receive_queue`.

У кінці ядро пробуджує користувацький процес (який спав на `epoll()` або `recv()`), і дані копіюються назад у user-space.

## 4. Обхід стека (Bypass): XDP та DPDK

На швидкостях понад 10 Гбіт/с проходження повного стека стає занадто дорогим.

- **eBPF/XDP (eXpress Data Path):** Дозволяє запускати eBPF-програми безпосередньо в драйвері NIC, ще *до* створення `sk_buff`. Це дозволяє відкидати DDoS-трафік (`XDP_DROP`) або маршрутизувати пакети з мінімальними накладними витратами.
- **DPDK (Data Plane Development Kit):** Повністю обходить ядро (Kernel Bypass). Драйвер NIC у user-space безпосередньо читає RX Ring через DMA. Системні виклики і переривання відсутні, але програма мусить сама реалізовувати TCP/IP стек.

Мережевий стек Linux ідеально збалансований: він пропонує універсальність і багатство функцій (Netfilter, Traffic Control) для більшості задач, водночас надаючи інструменти (XDP, DPDK) для екстремальних навантажень.
