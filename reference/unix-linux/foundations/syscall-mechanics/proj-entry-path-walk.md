# ⚙️ Знайти виклик у сирцях ядра: від інструкції `syscall` до тіла `write`

<preknowlist>
- [Стадії компілятора](book:programming/compiler-stages) — препроцесор працює з текстом ще до компілятора: підставляє макроси й уміє склеювати з кількох шматків одне ім'я. Саме тому імена, які ми шукатимемо, у сирцях не написані.
- [Трасування системних викликів](book:unix-linux/syscall-tracing) — `strace` показує, який виклик і з якими аргументами зробила програма; звідси починається пошук.
- [Шар VFS](book:unix-linux/vfs-layer) — спільний рівень над усіма файловими системами: `read` і `write` спершу потрапляють у нього, а вже він кличе конкретну ФС.
</preknowlist>

`strace` показав рядок `write(1, "привіт\n", 13) = 13`, і виникає природне питання: **де код, який це виконав?** Дерево ядра розпаковане, `git grep` під рукою — а перша ж спроба знайти тіло дає нуль. Причина не в тому, що ви погано шукаєте: потрібного імені в сирцях справді немає, його складає препроцесор під час збірки. Розберімо, як влаштована ця склейка, і зробімо з цього рецепт, який за півхвилини веде від номера виклику до рядків, що роблять роботу, — для будь-якого з чотирьох з половиною сотень викликів.

## Перша спроба, яка нічого не дає

```bash
git grep -n -w sys_write
```

Влучань буде чимало, і всі трьох сортів. Перший — рядки таблиць викликів різних архітектур (`arch/*/…/syscall*.tbl`). Другий — оголошення в `include/linux/syscalls.h`:

```c
asmlinkage long sys_write(unsigned int fd, const char __user *buf, size_t count);
```

Третій — згадки в коментарях і в списках. Тіла немає в жодному. Оголошення каже, що функція з такою сигнатурою існує, таблиця каже, під яким номером вона живе, — а де вона написана, не каже ніхто.

Відповідь «воно десь у макросах» правильна, але марна. Треба знати, **як саме** складається ім'я, бо з цього знання прямо випливає запит, який шукає те, що шукається.

## Ім'я, якого ніхто не писав

Реалізація починається з макроса. У `include/linux/syscalls.h`:

```c
#define SYSCALL_DEFINE3(name, ...) SYSCALL_DEFINEx(3, _##name, __VA_ARGS__)

#define SYSCALL_DEFINEx(x, sname, ...)          \
        SYSCALL_METADATA(sname, x, __VA_ARGS__) \
        __SYSCALL_DEFINEx(x, sname, __VA_ARGS__)
```

Ключове тут — оператор `##`, який склеює два токени в один. З аргументу `write` перший же рядок робить `_write`, і далі це вже не слово `write`, а заготовка для склеювання. Кожне справжнє ім'я народжується так: `sys` + `_write` дає `sys_write`, `__do_sys` + `_write` дає `__do_sys_write`. Жодного з цих імен у файлі, де лежить реалізація, немає — там написано тільки `write`.

Далі архітектура додає свій шар. На x86 (`arch/x86/include/asm/syscall_wrapper.h`) макрос розкривається в чотири різні функції:

```c
#define __SYSCALL_DEFINEx(x, name, ...)                                   \
        static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__));       \
        static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));\
        __X64_SYS_STUBx(x, name, __VA_ARGS__)                             \
        __IA32_SYS_STUBx(x, name, __VA_ARGS__)
```

Кожна має свою роботу. `__x64_sys_write` приймає єдиний аргумент — вказівник на `pt_regs` — і витягає звідти реєстри як типізовані аргументи. `__ia32_sys_write` робить те саме для тридцятидвобітної програми, що працює на цьому ж ядрі. `__se_sys_write` розширює знак там, де вузький тип приїхав у широкому реєстрі. І тільки `__do_sys_write` — тіло, тобто рівно те, що автор написав у фігурних дужках після макроса.

![З одного рядка SYSCALL_DEFINE3(write, …) препроцесор робить чотири функції з різними іменами, і жодне з них не написане в сирцях літерами](/reference/unix-linux/foundations/syscall-mechanics/img/macro-names.svg)

*Пошук за складеним іменем приречений: у тексті, який читає `grep`, цього імені ще не існує.*

> 🔧 **Навіщо це.** З механізму склеювання випливає готовий пошуковий запит: шукати треба **аргумент макроса**, а не ім'я функції. Тобто не `sys_write`, а `write` — але не саме собою, а в товаристві макроса, інакше влучань будуть тисячі.

```bash
git grep -n 'SYSCALL_DEFINE[0-9](write[,)]'
# fs/read_write.c:SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf,
```

Квадратні дужки замість конкретної цифри — щоб не гадати про кількість аргументів, а `[,)]` наприкінці — щоб не зловити заразом `writev` і `write_iter`.

## Рецепт: від номера до тіла

Тепер повний шлях, крок за кроком.

**Крок 1. Номер → точка входу.** Джерело правди для x86-64 — `arch/x86/entry/syscalls/syscall_64.tbl`. Формат оголошено в шапці самого файлу: `<номер> <abi> <назва> <точка входу> [<compat-точка> [noreturn]]`.

```bash
awk '$1 == 1' arch/x86/entry/syscalls/syscall_64.tbl
# 1    common    write    sys_write
```

Якщо сирців під рукою немає, той самий номер дістається з системи: `ausyscall x86_64 1` із пакета аудиту друкує назву, а `grep -w __NR_write /usr/include/asm/unistd_64.h` — навпаки, номер за назвою. Сам номер `strace` покаже, якщо запустити його з `-n` (ця опція з'явилася у версії 5.9, восени 2020-го). А для процесу, що вже висить у ядрі, номер поточного виклику разом із шістьма аргументами, вказівником стека й лічильником команд лежить у [файлі `syscall` всередині теки процесу в `/proc`](book:unix-linux/proc-filesystem).

**Крок 2. Точка входу → аргумент макроса.** Відкиньте префікс `sys_`: те, що лишилося, і є перший аргумент `SYSCALL_DEFINE`. Для `sys_write` це `write`, і пошук із попереднього блоку веде просто в `fs/read_write.c`.

Правило треба брати саме з таблиці, а не з назви виклику, бо вони збігаються не завжди. Рядок `4 common stat sys_newstat` означає, що виклик називається `stat`, а шукати треба `SYSCALL_DEFINE2(newstat` — і знайдеться воно в `fs/stat.c`. Історія тут проста: структуру `stat` колись розширили, стару реалізацію лишили заради старих бінарників, а нову назвали «new». Хто піде шукати `SYSCALL_DEFINE2(stat`, знайде не те або нічого.

**Крок 3. Униз по шарах.** Тіло виявляється дуже коротким:

```c
/* fs/read_write.c */
SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf,
                size_t, count)
{
        return ksys_write(fd, buf, count);
}
```

Уся робота — у `ksys_write`, яка теж живе поруч. Вона перетворює дескриптор на структуру `struct file`, дістає з неї поточну позицію в файлі, кличе `vfs_write` і за успіху посуває позицію. А `vfs_write` — це вже [спільний шар над усіма файловими системами](book:unix-linux/vfs-layer): він перевіряє, що файл відкрито на запис, що діапазон адрес користувача взагалі адресовний, обмежує розмір, питає дозволу в модуля безпеки — і аж тоді викликає метод конкретної файлової системи через вказівник у `f_op`.

Отже, три імені — три різні рівні, і плутати їх дорого. `__do_sys_write` — тіло самого виклику, тут завдовжки в один рядок. `ksys_write` — та сама робота у вигляді звичайної функції C, яку може покликати код усередині самого ядра. `vfs_write` — власне логіка запису, спільна для `write`, `pwrite` і всього іншого, що пише у файл.

Ці `ksys_`-помічники існували не завжди. Їх додав Домінік Бродовський навесні 2018 року — у березні того року він розсилав серію, яка прибирала виклики `sys_*()` зсередини ядра. Причина — у тих самих обгортках: щойно точка входу почала приймати `pt_regs`, покликати її з ядра стало неможливо, бо в ядра немає користувацького `pt_regs`, який треба розібрати. Довелося виділити чисту функцію C, а обгортці лишити тільки розпаковування реєстрів.

## Угору: як керування дійшло до цієї функції

Зворотний бік шляху шукається легше, бо там імена написані буквально. Вхід — `SYM_CODE_START(entry_SYSCALL_64)` у `arch/x86/entry/entry_64.S`: `swapgs`, перемикання на стек ядра, збирання `pt_regs` із регістрів, а далі `movq %rsp, %rdi`, `movslq %eax, %rsi` і `call do_syscall_64`. Тобто на вхід C-коду йде вказівник на щойно складену структуру і номер виклику.

Далі — найцікавіше місце, бо воно змінилося:

```c
/* arch/x86/entry/syscall_64.c */
#define __SYSCALL(nr, sym) case nr: return __x64_##sym(regs);

long x64_sys_call(const struct pt_regs *regs, unsigned int nr)
{
        switch (nr) {
        #include <asm/syscalls_64.h>
        default: return __x64_sys_ni_syscall(regs);
        }
}
```

Це той самий трюк, що й з іменами, тільки навиворіт: `#include` стоїть **усередині** `switch`, а підключений файл — довгий список рядків виду `__SYSCALL(1, sys_write)`. Кожен такий рядок макрос перетворює на `case 1: return __x64_sys_write(regs);`. Самого файлу в дереві сирців немає — його породжує під час збірки скрипт `scripts/syscalltbl.sh` із тієї ж `.tbl`, і лежить він у `arch/x86/include/generated/asm/syscalls_64.h`.

До ядра 6.9 тут була не гілка, а індексація масиву `sys_call_table`. Замінив її патч Лінуса Торвальдса з простим міркуванням: непрямий перехід за вказівником із таблиці спекулятивно веде куди завгодно, а низка умовних переходів у гіршому разі спекулятивно виконає **чужий системний виклик** — річ сама собою нешкідливу. Масив `sys_call_table` лишився в дереві, але тепер він потрібен лише підсистемі трасування; про це просто сказано в коментарі над ним. Практичний наслідок неочевидний і болючий: старі поради «підмінити елемент у `sys_call_table`» на свіжому ядрі не роблять нічого — диспетчер їх не читає.

![Карта шляху від рядка strace через таблицю номерів, вхідний асемблер і диспетчер до тіла виклику й методу файлової системи](/reference/unix-linux/foundations/syscall-mechanics/img/source-map.svg)

*Тільки дві зупинки потребують не самих сирців: перша — живої системи, п'ята — зібраного дерева.*

## Перевірити, а не повірити

Усе описане легко звірити власноруч, і це варто зробити один раз. Препроцесований файл kbuild уміє зробити окремою ціллю:

```bash
make defconfig
make fs/read_write.i
grep -n '__x64_sys_write\|__do_sys_write' fs/read_write.i
```

У `.i`-файлі імена вже склеєні, тіло `__do_sys_write` видно цілком, і видно навіть те, чого в сирцях узагалі не було: метадані для точок трасування, які згенерував `SYSCALL_METADATA`.

На живій системі перевірка ще коротша:

```bash
grep -w __x64_sys_write /proc/kallsyms
grep -x __x64_sys_write /sys/kernel/tracing/available_filter_functions
```

Перша команда покаже, що символ із таким іменем справді є в завантаженому ядрі, друга — що на нього можна поставити зонд (на старших системах файлова система трасування монтується не в `/sys/kernel/tracing`, а в `/sys/kernel/debug/tracing`). Спробуйте так само пошукати `sys_write` чи `__do_sys_write`: першого не буде взагалі, другого — майже напевно теж, бо він оголошений `static inline` і компілятор вбудовує його в обгортку.

## Індексатори: хто бачить склеєні імена, а хто ні

Межа проходить рівно по препроцесору. Усе, що індексує **текст**, — `ctags`, `cscope`, більшість простих переходів у редакторах — про склеєні імена не знає в принципі, бо в тексті їх немає. Це не вада інструмента, а наслідок того, коли він працює:

```bash
make cscope              # база для поточної архітектури
make ARCH=arm64 tags     # теги для чужої архітектури, коли читаєш її шлях
```

Індексатори на базі Clang працюють після препроцесора й тому знають `__x64_sys_write` як звичайну функцію. Щоб їм було з чого починати, ядро дає генератор бази компіляції:

```bash
make defconfig && make -j"$(nproc)"
python3 scripts/clang-tools/gen_compile_commands.py
```

Після цього `clangd` переходить за складеними іменами так само спокійно, як за будь-якими іншими. Окремо стоїть `elixir.bootlin.com` — зручний, коли треба подивитися, як те саме місце виглядало саме у **вашій** версії ядра, а не в поточному майстрі.

## Пастки

**Обгортка залежить від архітектури.** Одне й те саме `SYSCALL_DEFINE3` дає `__x64_sys_write` на x86-64 і `__arm64_sys_write` на arm64. Скрипт із `kprobe`, написаний на робочому ноутбуці, на платі з іншим процесором мовчатиме — не тому, що виклику немає, а тому, що функції з таким іменем там немає.

**Тридцятидвобітна програма йде іншим тілом.** Дивіться на п'яту колонку таблиці:

```
5     i386    open     sys_open     compat_sys_open
54    i386    ioctl    sys_ioctl    compat_sys_ioctl
```

Якщо compat-точка вказана, для тридцятидвобітного процесу виконається **інша функція**, і написана вона іншим макросом — `COMPAT_SYSCALL_DEFINE3(ioctl, unsigned int, fd, unsigned int, cmd, compat_ulong_t, arg)` у `fs/ioctl.c`. Різниця не косметична: `compat_ulong_t` — це тридцять два біти, вказівники доводиться розширювати, структури мають інший розклад полів. Шукати причину дивної поведінки старого бінарника в нативному тілі — витрачений день.

**Номер без архітектури не означає нічого.** `write` — це 1 на x86-64, 4 на i386 і 64 на arm64. Новіші архітектури беруть номери зі спільного `scripts/syscall.tbl`, x86 тримає свої окремо. Тому перше питання до будь-якого номера з чужого логу: а чия це таблиця?

**Виклик без аргументів пишеться інакше.** `SYSCALL_DEFINE0(getpid)` — без коми, бо аргументів немає, і шаблон із `(getpid,` його не знайде. Тому в запиті й стоїть `[,)]`.

**Шар визначає, що ви ловите.** Зонд на `__x64_sys_write` спрацює лише на виклики з програм; зонд на `vfs_write` — ще й на записи, які робить саме ядро, зате пропустить шляхи, що йдуть у `write_iter` повз нього, як це робить [io_uring](book:unix-linux/io-uring). А точка трасування `syscalls:sys_enter_write`, яку згенерував той самий `SYSCALL_METADATA`, взагалі не залежить від архітектурних імен — приємна іронія, бо саме цей макрос і сховав від вас ім'я функції.

![Порівняння трьох рівнів одного write: що видно зондом на архітектурній обгортці, на шарі VFS і на точці трасування](/reference/unix-linux/foundations/syscall-mechanics/img/probe-layers.svg)

*Одна й та сама подія з трьох різних висот виглядає по-різному — і різне з неї видно.*

**Шляхи файлів переїжджають.** Функція `do_syscall_64` довго жила в `arch/x86/entry/common.c` — так вона виглядала ще в ядрі 6.9. У 6.15 вона вже в `arch/x86/entry/syscall_64.c`, поруч із диспетчером. Мораль практична: запам'ятовувати варто **імена**, а не шляхи, бо ім'я шукається за секунду в будь-якій версії, а завчений шлях одного дня просто збреше.

## Що чого коштує

Кроки цього шляху різні за ціною входу, і корисно тримати це в голові, коли обираєш, з чого почати.

| Що робимо | Що для цього треба | Скільки чекати |
|---|---|---|
| знайти тіло за назвою (`git grep 'SYSCALL_DEFINE…'`) | тільки розпаковані сирці | секунди |
| пройти шлях угору по `entry_64.S` і диспетчеру | тільки сирці | читання, не пошук |
| побачити склеєні імена в `.i`-файлі | сконфігуроване дерево, збірка одного файлу | десятки секунд |
| переходи за складеними іменами в редакторі | повна збірка + база компіляції | хвилини—десятки хвилин |
| звірити символ і поставити зонд | працююче ядро й права | секунди |

Перевірити рецепт легко на будь-якому іншому виклику. У таблиці `437 common openat2 sys_openat2`; відкидаємо префікс, шукаємо `SYSCALL_DEFINE[0-9](openat2[,)]` — і потрапляємо в `fs/open.c`, де стоїть `SYSCALL_DEFINE4(openat2, int, dfd, const char __user *, filename, struct open_how __user *, how, size_t, usize)`. Той самий четвертий аргумент `usize` — розмір структури, за яким ядро розуміє, з якою версією програми говорить, — тепер видно не переказом, а на місці, у контексті решти коду.
