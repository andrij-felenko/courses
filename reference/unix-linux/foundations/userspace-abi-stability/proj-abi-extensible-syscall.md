# ⚙️ Розширюваний двійковий контракт на практиці

Спроєктуймо один інтерфейс «ядро ↔ програма» так, щоб він пережив десяток версій **в обидва боки**: програма, зібрана 2016 року, працює на ядрі 2026-го, а програма 2026 року працює на ядрі 2016-го — і в жодному з випадків жодна зі сторін не робить мовчки чогось іншого, ніж її просили. Знадобиться чотири правила й приблизно сотня рядків коду; головна ж складність у тому, що кожне з цих правил мусить стояти на місці з **найпершої** версії — жодне з них не можна доточити згодом.

<preknowlist>
- [Системний виклик](book:unix-linux/syscall-mechanics) — програма кладе номер послуги й аргументи в регістри й переходить у ядро; помилка повертається числом.
- [Керуючий канал до драйвера](book:unix-linux/ioctl-interface) — `ioctl(fd, cmd, arg)`: єдина команда-число й один вказівник на структуру, якою драйвер обмінюється з програмою.
- [Вирівнювання даних у пам'яті](book:programming/memory-alignment) — компілятор ставить кожне поле на адресу, кратну його розміру, а проміжки заповнює байтами-заповнювачами.
</preknowlist>

## Задача, поставлена точно

Нехай ми пишемо драйвер `/dev/pacer` — він обмежує темп, з яким процес виконує певну операцію. Драйвер приймає від програми **політику**: скільки операцій за секунду дозволено, який допустимий сплеск, чи карати за перевищення жорстко. З роками політика обростає: 2019-го додається дедлайн у наносекундах, 2022-го — прив'язка до контрольної групи, 2025-го — перелік шляхів-винятків, довжина якого наперед невідома.

Ворогів у цій задачі троє, і вони різні.

**Тихе зміщення.** Програма 2016 року читає поле за зміщенням 24, драйвер 2022-го поставив туди інше поле. Ніхто не помиляється, ніхто не скаржиться, число просто інше.

**Тихе ігнорування.** Програма 2025 року просить дедлайн у 5 мс, драйвер 2016-го про дедлайни не чув і поле пропускає. Виклик повертає нуль. Програма впевнена, що дедлайн діє, і будує на цьому свою поведінку — це гірше за будь-яку помилку, бо помилку видно.

**Примус до синхронного оновлення.** Драйвер відмовляє всім, чия структура не збігається з його власною до байта. Формально безпечно, практично — заборона оновлювати ядро й програми окремо, тобто відмова від сумісності взагалі.

Мета — інтерфейс, у якому перші двоє неможливі за побудовою, а третього немає, бо оновлювати ядро й програми окремо мусить лишатися звичайною справою. І ще одна вимога, яку легко проґавити: **невдача мусить бути розрізненною**. Програма має вміти відповісти не на питання «спрацювало?», а на питання «чи вміє це ядро те, що мені потрібно» — до того, як почне працювати.

## Чотири правила

**Довжина йде першою й іде разом із даними.** Одержувач мусить дізнатися розмір структури раніше, ніж торкнеться будь-якого поля, — отже, поле `size` стоїть на зміщенні 0. Тримати довжину окремим аргументом теж можна (так зроблено в `clone3` і `openat2`), але тоді структуру не можна ні вкласти в іншу, ні записати у файл, ні передати через `ioctl`, у якого вільного аргумента просто немає. Довжина всередині робить структуру самоописовою, тобто придатною скрізь; `sched_setattr` і `perf_event_open` побудовані саме так.

**Рости лише в хвіст, і нуль означає «як було».** Нові поля дописуються після старих, і значення 0 у новому полі мусить давати рівно ту поведінку, яка була до появи поля. Це не побажання, а обов'язкова умова: коли стара програма надсилає коротшу структуру, ядро добиває решту нулями — і якщо нуль у полі щось означає, стара програма мовчки просить те, чого не просила.

**Невідоме в проханні — відмова.** Піднятий біт прапорця, якого ми не знаємо; ненульовий хвіст за межею відомих нам полів; атрибут незнайомого типу — усе це прохання, якого ми не вміємо виконати. Виконати не можемо, промовчати не маємо права, лишається відмовити. Документація ядра для авторів нових викликів вимагає саме цього: перевірити прапорці на невідомі біти й відхилити виклик з `EINVAL`, якщо такі є.

**Розкладка задана явно, а не виведена компілятором.** Жодних `long`, `time_t`, вказівників, бітових полів і перелічуваних типів: лише типи фіксованої ширини, лише явні поля-заповнювачі замість неявних дірок, лише `__u64` замість вказівника. Правила ядра для інтерфейсів `ioctl` формулюють це прямо: `long` має ширину регістра, тож у переносних структурах непридатний, а вказівник треба передавати як `__u64` і повертати назад через `u64_to_user_ptr()`.

## Заголовок інтерфейсу

```c
/* uapi/linux/pacer.h — цей файл більше ніколи не можна змінювати,
   можна тільки дописувати в кінець структур і в кінець списку бітів */

#include <linux/types.h>

struct pacer_policy {
        __u32          size;         /*  0.. 3  довжина структури від відправника */
        __u32          __reserved0;  /*  4.. 7  мусить бути 0 */
        __aligned_u64  flags;        /*  8..15 */
        __aligned_u64  rate;         /* 16..23  операцій за секунду; 0 = без межі */
        __u32          burst;        /* 24..27  дозволений сплеск; 0 = без сплеску */
        __u32          __reserved1;  /* 28..31  мусить бути 0 */
        /* ─────────── PACER_POLICY_SIZE_VER0 == 32 ─────────── */
        __aligned_u64  deadline_ns;  /* 32..39  0 = без дедлайну */
        /* ─────────── PACER_POLICY_SIZE_VER1 == 40 ─────────── */
        __s32          cgroup_fd;    /* 40..43  чинне лише з PACER_CGROUP */
        __u32          __reserved2;  /* 44..47  мусить бути 0 */
        /* ─────────── PACER_POLICY_SIZE_VER2 == 48 ─────────── */
        __aligned_u64  attrs;        /* 48..55  (uintptr_t) на хвіст атрибутів */
        __u32          attrs_len;    /* 56..59  0 = хвоста немає */
        __u32          __reserved3;  /* 60..63  мусить бути 0 */
        /* ─────────── PACER_POLICY_SIZE_VER3 == 64 ─────────── */
};

#define PACER_POLICY_SIZE_VER0  32
#define PACER_POLICY_SIZE_VER1  40
#define PACER_POLICY_SIZE_VER2  48
#define PACER_POLICY_SIZE_VER3  64

#define PACER_STRICT  (1ULL << 0)   /* з версії 0 */
#define PACER_NOTIFY  (1ULL << 1)   /* з версії 1 */
#define PACER_CGROUP  (1ULL << 2)   /* з версії 2: поле cgroup_fd має сенс */

#define PACER_ARM   _IO('P', 1)     /* поставити політику */
#define PACER_INFO  _IO('P', 0)     /* спитати, що це ядро вміє */
```

У цьому заголовку кожен рядок — рішення, за яким стоїть конкретна поломка.

`__aligned_u64` — це `__u64` з примусовим вирівнюванням на 8. Без нього тридцятидвобітна програма розклала б структуру інакше, ніж шістдесятичотирибітне ядро: на i386 восьмибайтові величини вирівнюються по чотири, на x86-64 — по вісім, і зміщення поїхали б. Примусове вирівнювання робить обидві розкладки однаковими — а це означає, що для тридцятидвобітних програм не потрібен окремий обробник-перекладач: ядро читає ту саму структуру.

`cgroup_fd` — приклад поля, для якого правило «нуль означає як було» **не працює само собою**: нуль — цілком законний [дескриптор](book:unix-linux/file-descriptor). Тому поле супроводжує біт `PACER_CGROUP`, і без цього біта вміст поля не розглядають. Так само влаштований `clone3`: поле `cgroup` беруть до уваги лише тоді, коли у прапорцях стоїть `CLONE_INTO_CGROUP`. А от `attrs_len` біта не потребує: нуль там природно означає «хвоста немає», і жодного іншого сенсу мати не може.

Команди оголошено через `_IO`, а не `_IOW('P', 1, struct pacer_policy)`, — і це не недбалість. Макрос `_IOW` зашиває `sizeof` структури в саме число команди; додайте поле — і число зміниться, а зібрана раніше програма надішле старе, якого драйвер уже не впізнає. Наш контракт уже несе власну довжину, тож друга, суперечлива довжина в номері команди тільки заважає. Правила ядра пропонують інший вихід — заводити для розширеної операції **новий номер**, лишаючи старий як обгортку; це теж працює, але ціна — окреме число й окремий обробник на кожну версію замість одного.

Нарешті, самі числа-межі варто закріпити перевірками під час збірки — на боці ядра, де доступний `offsetofend`:

```c
static_assert(offsetofend(struct pacer_policy, __reserved1) == PACER_POLICY_SIZE_VER0);
static_assert(offsetofend(struct pacer_policy, deadline_ns) == PACER_POLICY_SIZE_VER1);
static_assert(offsetofend(struct pacer_policy, __reserved2) == PACER_POLICY_SIZE_VER2);
static_assert(sizeof(struct pacer_policy)                   == PACER_POLICY_SIZE_VER3);
```

Тепер випадкове вставляння поля в середину, зміна типу чи поява неявного заповнювача ламають **збірку**, а не чужу програму через три роки.

## Бік ядра: узгодити довжину

```c
static int pacer_fetch_policy(struct pacer_policy *dst, const void __user *uarg)
{
        u32 usize;
        int err;

        /* довжина лежить першою — читаємо її, ще нічого не знаючи про решту */
        if (get_user(usize, (const u32 __user *)uarg))
                return -EFAULT;

        if (usize < PACER_POLICY_SIZE_VER0)
                return -EINVAL;   /* коротше за найпершу версію — це не наша структура */
        if (usize > PAGE_SIZE)
                return -E2BIG;    /* стеля проти безглуздих чисел */

        /* три випадки одним викликом: збіг, добивання нулями, перевірка хвоста */
        err = copy_struct_from_user(dst, sizeof(*dst), uarg, usize);
        if (err)
                return err;       /* -E2BIG, якщо в хвості не самі нулі */

        if (dst->flags & ~(PACER_STRICT | PACER_NOTIFY | PACER_CGROUP))
                return -EINVAL;   /* біт, якого ми не знаємо */
        if (dst->__reserved0 | dst->__reserved1 | dst->__reserved2 | dst->__reserved3)
                return -EINVAL;   /* заповнювач мусить бути чистим */
        if (!(dst->flags & PACER_CGROUP) && dst->cgroup_fd)
                return -EINVAL;   /* поле без свого біта — теж прохання, якого ми не розуміємо */

        return 0;
}
```

Уся розширюваність тримається на одному помічнику. `copy_struct_from_user(dst, ksize, src, usize)` з'явився в ядрі 5.4 (осінь 2019, автор — Алекса Сарай, Aleksa Sarai) саме тому, що цей шматок логіки в кожному виклику писали трохи по-різному й трохи неповно. Він робить три речі залежно від співвідношення довжин: за рівних копіює як є; коли довжина від програми менша — копіює скільки є й добиває решту нулями; коли більша — перевіряє зайвий хвіст і повертає `-E2BIG`, якщо там знайшовся хоч один ненульовий байт. Ті самі три випадки описує й довідка `openat2`: за нульового хвоста ядро спокійно ігнорує невідомі йому поля, за ненульового відмовляє.

Після копіювання `dst->size` тримає довжину **від програми**, а не нашу власну, — і це корисне число: воно каже, з якою версією заголовка зібрано співрозмовника.

І одна дрібниця, яка виглядає надмірною обережністю, а насправді закриває цілий клас поломок: перевірка полів-заповнювачів на нуль. Заповнювач має сенс лише доти, доки його можна колись пустити під нове поле. А пустити його під нове поле можна тільки тоді, коли **з першого дня** ненульовий заповнювач був помилкою. Якщо драйвер версії 0 його не перевіряв, у полі роками могло лежати сміття зі стека випадкових програм — і в день, коли ви оголосите там нове поле, ці програми почнуть просити казна-що. Неперевірений заповнювач мертвий назавжди.

## Бік програми: спитати один раз, а не гадати за errno

Найпростіше було б зробити так: надіслати повну структуру, а якщо повернеться помилка — вважати, що ядро старе, і спробувати простіше. Не вийде, бо коди помилок тут перевантажені. `E2BIG` справді означає «поле, якого я не знаю». А от `EINVAL` означає і «біт, якого я не знаю», і «твоя частота — дурниця», і «твій дескриптор не веде в контрольну групу». Розрізнити «ядро старе» й «я передав нісенітницю» за одним `errno` неможливо, і кожна спроба це зробити перетворюється на здогади.

Тому в контракт із самого початку закладається команда-запит, яка нічого не робить, а лише розповідає про можливості:

```c
struct pacer_info {
        __u32          size;             /* вхід: sizeof у програми; вихід: sizeof у ядра */
        __u32          __reserved0;
        __aligned_u64  flags_supported;  /* які біти прапорців розуміє це ядро */
        __aligned_u64  attrs_supported;  /* бітова мапа відомих типів атрибутів */
        __u32          policy_size;      /* sizeof(struct pacer_policy) у ядрі */
        __u32          __reserved1;
};

#define PACER_INFO_SIZE_VER0  32
```

Тут напрям зворотний, і в ньому є своя тонкість: ядро мусить не лише обрізати відповідь до довжини, яку програма спроможна прийняти, а й **сказати їй, що обрізало**. Тому в поле `size` ядро вписує власний `sizeof`: побачивши там число, більше за своє, програма знає, що на цьому ядрі є можливості, про які їй нема як спитати. Той самий прийом уже живе в ядрі: коли `perf_event_open` відмовляє з `E2BIG`, він перед тим переписує поле `size` у структурі програми на розмір, якого чекав сам, — помилка заразом стає відповіддю.

```c
static void pacer_fill_info(struct pacer_info *ki)
{
        memset(ki, 0, sizeof(*ki));
        ki->size            = sizeof(*ki);
        ki->flags_supported = PACER_STRICT | PACER_NOTIFY | PACER_CGROUP;
        ki->attrs_supported = PACER_ATTRS_KNOWN;  /* мапа типів, які ми розбираємо */
        ki->policy_size     = sizeof(struct pacer_policy);
}

static int pacer_put_info(void __user *uarg)
{
        struct pacer_info ki;
        u32 usize;

        if (get_user(usize, (const u32 __user *)uarg))
                return -EFAULT;
        if (usize < PACER_INFO_SIZE_VER0)
                return -EINVAL;

        pacer_fill_info(&ki);

        /* віддаємо стільки, скільки програма здатна прийняти, але size — наш */
        if (copy_to_user(uarg, &ki, min_t(u32, usize, sizeof(ki))))
                return -EFAULT;
        if (usize > sizeof(ki) &&
            clear_user((char __user *)uarg + sizeof(ki), usize - sizeof(ki)))
                return -EFAULT;   /* хвіст, якого ми не заповнили, мусить бути чистим */

        return 0;
}
```

На боці програми з цього виходить одноразове узгодження на старті:

```c
struct pacer_caps {
        __u32 policy_size;
        __u64 flags;
        __u64 attrs;
};

/* чи є в ядрі поле з такою назвою — питання про довжину, а не про версію */
#define PACER_HAS(caps, field)                                          \
        ((caps)->policy_size >= offsetof(struct pacer_policy, field) +  \
                                sizeof(((struct pacer_policy *)0)->field))

static int pacer_caps_get(int fd, struct pacer_caps *out)
{
        struct pacer_info info = { .size = sizeof(info) };

        if (ioctl(fd, PACER_INFO, &info) == 0) {
                out->policy_size = info.policy_size;
                out->flags       = info.flags_supported;
                out->attrs       = info.attrs_supported;
                return 0;
        }

        /* драйвер не знає навіть самої команди-запиту — отже, він
           давніший за неї, а такою була рівно одна версія */
        if (errno == ENOTTY) {
                out->policy_size = PACER_POLICY_SIZE_VER0;
                out->flags       = PACER_STRICT;
                out->attrs       = 0;
                return 0;
        }
        return -1;
}
```

Далі виклик стає нудним, а це і є ознака вдалого інтерфейсу: усе, чого це ядро не вміє, відсіяно **до** нього, у власній логіці програми, а не в розборі `errno`.

```c
int pacer_arm(int fd, const struct pacer_caps *caps,
              __u64 rate, __u32 burst, __u64 deadline_ns, int cgroup_fd)
{
        struct pacer_policy p = { 0 };   /* обнулити ВСЮ структуру — обов'язково */

        if (deadline_ns && !PACER_HAS(caps, deadline_ns))
                return -1;               /* дедлайну тут не буде — вирішує програма */
        if (cgroup_fd >= 0 && !(caps->flags & PACER_CGROUP))
                return -1;

        p.size  = sizeof(p);
        p.flags = PACER_STRICT;
        p.rate  = rate;
        p.burst = burst;
        p.deadline_ns = deadline_ns;
        if (cgroup_fd >= 0) {
                p.flags     |= PACER_CGROUP;
                p.cgroup_fd  = cgroup_fd;
        }

        /* сюди ми входимо, лише знаючи, що ядро це вміє; E2BIG чи EINVAL
           звідси — не «старе ядро», а помилка в нашому власному коді */
        return ioctl(fd, PACER_ARM, &p);
}
```

Рядок `struct pacer_policy p = { 0 }` — не косметика. Ми надсилаємо повний `sizeof(p)`, навіть коли ядро старе; це безпечно рівно доти, доки хвіст справді нульовий. Одне невитерте поле — і замість роботи ми дістанемо `E2BIG` там, де нічого зайвого не просили.

> 🔧 **Навіщо це.** Три коди помилок тут кажуть три різні речі, і плутати їх не можна. `ENOTTY` (для системного виклику — `ENOSYS`) означає «такої команди немає взагалі» — найстаріше ядро. `E2BIG` означає «команда є, але ти просиш поле, якого я не знаю». `EINVAL` означає «команда є, а прохання неправильне» — і саме через його багатозначність усе узгодження й винесене в окремий запит. Обгортка, проксі чи фільтр, що підмінює один із цих кодів іншим, ламає механізм відступу, заради якого все й будувалося.

## Коли скалярів не вистачає: хвіст з атрибутів

Структура з довжиною добре описує **сталий набір параметрів**. Вона безпорадна там, де потрібен перелік невідомої довжини, рядок, розріджений набір рідковживаних налаштувань. Дописати в структуру масив на тисячу шляхів не можна: його довелося б нести в кожному виклику.

Тут працює інша форма того самого принципу «невідоме можна пропустити, якщо воно позначене довжиною»: ланцюг записів «довжина–тип–дані». Кожен запис починається з власної довжини, тож одержувач уміє переступити через нього, навіть не здогадуючись, що всередині. Саме так побудовані атрибути [netlink](book:unix-linux/netlink-protocol), і саме звідти варто брати деталі — включно з вирівнюванням, про яке легко забути.

```c
struct pacer_attr {
        __u16 len;    /* довжина РАЗОМ із цим заголовком, без заповнювача */
        __u16 type;
};

#define PACER_ATTR_ALIGNTO   4
#define PACER_ATTR_ALIGN(n)  (((n) + PACER_ATTR_ALIGNTO - 1) & ~(PACER_ATTR_ALIGNTO - 1))
#define PACER_ATTR_HDRLEN    PACER_ATTR_ALIGN(sizeof(struct pacer_attr))

enum {
        PACER_A_UNSPEC = 0,
        PACER_A_EXEMPT_PATH,   /* рядок */
        PACER_A_EXEMPT_INO,    /* __u64 */
        __PACER_A_MAX,
};
#define PACER_ATTR_MAX      (__PACER_A_MAX - 1)
#define PACER_ATTRS_KNOWN   (BIT_ULL(PACER_A_EXEMPT_PATH) | BIT_ULL(PACER_A_EXEMPT_INO))
#define PACER_ATTRS_MAX_LEN 4096   /* стеля на весь хвіст */
```

Довжина в заголовку не враховує заповнювача, а крок до наступного запису — враховує. Різниця між `len` і `ALIGN(len)` і є той самий заповнювач, який відправник **зобов'язаний обнулити**: інакше в хвості кожного повідомлення поїде сміття зі стека, і одного дня, коли комусь знадобиться ще один прапорець у цих байтах, виявиться, що вони давно зайняті випадковими даними.

![Ланцюг записів «довжина–тип–дані»: крок до наступного атрибута рахується за вирівняною довжиною, тому пропустити незнайомий запис можна, не знаючи про нього нічого](/reference/unix-linux/foundations/userspace-abi-stability/img/tlv-walk.svg)

*Той самий незнайомий тип у проханні й у звіті вимагає протилежних дій — і це найважливіше рішення в усьому розборі.*

Хвіст лежить не в структурі, а за вказівником `attrs`, і ядро забирає його окремо — уже знаючи довжину, тож стеля перевіряється до будь-якого виділення пам'яті:

```c
        const struct pacer_attr *tab[PACER_ATTR_MAX + 1];
        void *tail = NULL;

        if (pol.attrs_len) {
                if (pol.attrs_len > PACER_ATTRS_MAX_LEN)
                        return -E2BIG;
                tail = memdup_user(u64_to_user_ptr(pol.attrs), pol.attrs_len);
                if (IS_ERR(tail))
                        return PTR_ERR(tail);
                err = pacer_parse(tail, pol.attrs_len, tab, PACER_ATTR_MAX);
        }
```

```c
/* Розбір хвоста. Повертає 0 або від'ємний код помилки; заповнює
   таблицю вказівників на знайдені атрибути. */
static int pacer_parse(const void *buf, size_t len,
                       const struct pacer_attr *tab[], u16 maxtype)
{
        size_t off = 0;

        memset(tab, 0, (maxtype + 1) * sizeof(tab[0]));

        while (off < len) {
                const struct pacer_attr *a;
                size_t alen, step;

                if (len - off < PACER_ATTR_HDRLEN)
                        return -EINVAL;        /* обрізаний заголовок */

                a    = (const struct pacer_attr *)((const char *)buf + off);
                alen = a->len;
                step = PACER_ATTR_ALIGN(alen);

                if (alen < PACER_ATTR_HDRLEN || step > len - off)
                        return -EINVAL;        /* довжині не можна вірити */
                if (a->type > maxtype)
                        return -EOPNOTSUPP;    /* прохання, якого ми не розуміємо */
                if (tab[a->type])
                        return -EINVAL;        /* той самий атрибут двічі */

                tab[a->type] = a;
                off += step;
        }
        return 0;
}
```

Чотири перевірки в тілі циклу закривають чотири різні способи зіпсувати розбір, і жодну не можна прибрати.

Порівняння `step > len - off` виглядає дивно — здавалося б, природніше написати `off + step > len`. Але `off + step` може переповнитися, а `len - off` не може: у циклі ми вже знаємо, що `off < len`. Це стандартна обережність будь-якого коду, що розбирає дані з чужого боку межі.

Вимога `alen >= PACER_ATTR_HDRLEN` рятує від нескінченного циклу: атрибут із заявленою довжиною 0 дав би крок 0, і розбір крутився б вічно на одному місці, тримаючи ядро.

Заборона повторів — рішення, якого в netlink якраз немає: там при однаковому типі перемагає останній запис. Виглядає дрібницею, доки два боки не розійдуться в тому, який саме запис вважати чинним; краще відмовити.

І, нарешті, головне: `a->type > maxtype` — відмова, а не пропуск.

## Пропустити чи відмовити — залежить від напряму

Спокусливо зробити розбір «поблажливим»: чого не знаю, те переступаю. Для потоку **звітів** з ядра в програму це правильно — новіше ядро додає в подію ще одне поле, старіша програма його не бачить і працює далі; зайвий факт нікому не шкодить. Для **прохання** це та сама тиха згода, з якої ми починали: програма попросила виняток для шляху, ядро атрибут пропустило, виклик повернув нуль — і обмеження тихо діє на файл, який мав бути винятком.

Різниця в коді — один рядок: `continue` замість `return -EOPNOTSUPP`. Різниця в наслідках — між «сумісно» й «зламано мовчки».

Ядро цей урок засвоїло дорогою ціною. Розбір атрибутів netlink від початку був поблажливим: невідомі типи мовчки пропускалися, зайве сміття в хвості теж. 2019 року Йоганнес Берг (Johannes Berg) провів через дерево ядра серію «stricter netlink validation»: з'явився режим `NL_VALIDATE_STRICT`, який відхиляє типи понад `maxtype`, відкидає хвіст-сміття й перевіряє атрибути за політикою, а всі наявні місця виклику перейменували на `nla_parse_deprecated()`. Саме перейменування й показує суть: старим командам суворість увімкнути **не можна** — програми роками надсилали їм сміття й отримували у відповідь нуль, тож суворість зламала б їх. Суворим інтерфейс буває тільки змолоду.

## Що це коштує

Обчислювальна ціна мізерна. Узгодження довжини — це читання чотирьох байтів, копіювання кількох десятків і, у рідкісному випадку задовгої структури, сканування хвоста на нулі. Розбір атрибутів — один прохід, `O(n)` за довжиною хвоста, без жодного виділення пам'яті понад копію самого хвоста.

Справжня ціна — проєктна, і платиться вона один раз, наперед. У день, коли перша версія драйвера потрапляє до людей, назавжди фіксуються: розкладка структури до байта, значення кожного біта прапорців, номери типів атрибутів, а разом із ними — навіть коди помилок, які ви віддаєте в кожній ситуації. Зі списку прибрати не можна нічого. На відміну від [версіонування API](book:programming/api-versioning), де досить оголосити версію 2 й лишити першу на рік-два, тут «версії 2» не буває: є одна структура, яка вміє бути будь-якої довжини.

Звідси кілька пасток, які коштували ядру найбільше.

**Розмір — не номер версії.** Не пишіть `if (usize == PACER_POLICY_SIZE_VER1)`. Програму могли зібрати з проміжним заголовком, довжина буває якою завгодно між найпершою й теперішньою, і питання, на яке ви насправді відповідаєте, звучить інакше: «чи дотягується довжина до кінця ось цього поля». Саме це й рахує `PACER_HAS`.

**Час — це `__s64` секунд і `__u32` наносекунд, і ніколи `time_t`.** Ширина `time_t` різна на різних архітектурах і змінювалася; 2038 року тридцятидвобітний лічильник секунд переповниться. Приклад для наслідування — `struct statx_timestamp` із `__s64 tv_sec` і `__u32 tv_nsec`, де решта до вирівнювання відведена під явне резервне поле.

**Часткова відповідь потребує власного механізму.** Прохання, виконане наполовину, — брехня; звіт, зібраний наполовину, — часто єдине, що можливо. Коли ядро може віддати не все, воно мусить сказати, що саме віддало. Так працює `statx`: програма просить набір полів маскою, а ядро вписує у `stx_mask` те, що справді заповнило, і біт запитаного, але недоступного поля лишається скинутим. Без такого дзеркала програма не має способу відрізнити «поля немає» від «поле дорівнює нулю».

**Суворість не додається згодом.** Це та сама думка, що стоїть за `nla_parse_deprecated`, і порушують її частіше за все: перевірка заповнювачів на нуль, перевірка невідомих бітів, відмова на невідомий атрибут — усе це працює лише як частина найпершої версії. Кожна з них, доточена пізніше, ламає простір користувача рівно так само, як зміщене поле.

## Перевірка: надіслати структуру з майбутнього

Останнє, що відрізняє задум від працездатного контракту, — можливість переконатися, що ви не помилилися, **не чекаючи десять років**. Майбутнє тут імітується тривіально: беремо буфер, більший за нашу структуру, і надсилаємо його.

```c
static void test_forward_compat(int fd)
{
        /* об'єднання, а не масив char: інакше буфер може виявитися
           невирівняним, і структура ляже не на ту адресу */
        union {
                struct pacer_policy p;
                char                raw[sizeof(struct pacer_policy) + 16];
        } u = { 0 };
        const size_t tail = sizeof(struct pacer_policy);   /* перший байт «майбутнього» */

        u.p.size = sizeof(u.raw);   /* «я з майбутнього, у мене структура довша» */
        u.p.rate = 1000;

        /* хвіст нульовий — драйвер мусить спокійно спрацювати */
        assert(ioctl(fd, PACER_ARM, &u.p) == 0);

        /* у хвості щось є — драйвер мусить відмовити, і саме з E2BIG */
        u.raw[tail] = 1;
        assert(ioctl(fd, PACER_ARM, &u.p) == -1 && errno == E2BIG);

        /* біт, якого не існує, — EINVAL, а не тиха згода */
        u.raw[tail] = 0;
        u.p.flags   = 1ULL << 63;
        assert(ioctl(fd, PACER_ARM, &u.p) == -1 && errno == EINVAL);
}
```

Ці двадцять рядків — єдиний спосіб дізнатися сьогодні, чи витримає інтерфейс завтрашню версію. Вони перевіряють не поведінку драйвера, а його **здатність постаріти**: що він пропустить чужий нульовий хвіст, що не змовчить у відповідь на прохання, якого не розуміє, і що скаже про це кодом, який програма зуміє розрізнити. Драйвер, який усі три перевірки проходить із першого дня, можна розширювати десятиліттями. Драйвер, який хоч одну провалює, доведеться дублювати цілком — і ця копія теж лишиться назавжди.
