# ⚙️ Аудит 2038: перевірити систему, не чекаючи 2038 року

Питання «чи переживе ця машина ніч на 19 січня 2038 року» здається таким, на яке чесно відповідає лише сам той рік. Насправді відповідь уже лежить у величинах, які знімаються сьогодні за пів години: у ширині типу, з яким зібрано програму, у наборі системних викликів ядра, у розмірі поля в структурі на диску. Нижче — саме такий дослід: чотири проби на C, кожна з власним «так» або «ні», а далі — спроба справді перевести годинник за межу й розбір поломок, які при цьому проступають.

Цінність тут не в тому, щоб пересвідчитися в написаному. Цінність у тому, що кожне число друкує сама програма або віддає системний інструмент, — тож хибне припущення видно одразу, і видно, у якому саме місці воно сидить.

## Не одне питання, а чотири

Позначка часу від миті, коли її взяли з годинника, до миті, коли її записали на диск, проходить крізь чотири різні вмістища, і кожне має власну ширину.

**Змінна `time_t` у програмі.** Її ширину зафіксували заголовки бібліотеки C тоді, коли цю програму збирали, — і відтоді ширина є властивістю двійкового файлу, а не системи. Оновлення дистрибутива не змінює її в уже зібраному файлі.

**Структура на межі з ядром** — `struct timespec`, `struct stat`, `struct itimerspec`. Її розкладку визначає те, який із двох наборів системних викликів бібліотека вирішила кликати.

**Внутрішнє представлення в ядрі.** Тут 64 біти на всіх архітектурах — але лише якщо ядро взагалі має `_time64`-виклики, якими це представлення можна дістати й покласти назад.

**Поле в структурі на носії.** Його ширину зафіксували в момент створення файлової системи, і після цього вона не змінюється ані від оновлення ядра, ані від перезбирання чого завгодно.

Ці чотири величини незалежні одна від одної, і звідси головне практичне: **три «так» не рятують**. Значення підріже або перекрутить найвужче з чотирьох вмістищ, а решта три спрацюють бездоганно й нічого не помітять.

![Чотири вмістища, крізь які проходить одна позначка часу: змінна в програмі, структура на межі з ядром, внутрішній час ядра й поле в inode; перші три 64-бітні, останнє 32-бітне і підрізає значення](/reference/unix-linux/foundations/time-representation-y2038/img/audit-four-fields.svg)

*Кожне вмістище питають окремо, бо ламається воно теж окремо.*

Тому аудит — це чотири окремі проби, і йдуть вони саме в такому порядку: кожна наступна має сенс лише після «так» на попередню. Питати файлову систему, чи витримає вона 2039 рік, безглуздо, якщо програма, яка питає, не вміє це число навіть вимовити.

## Стенд

На 64-бітній машині проблеми немає — там `time_t` має 64 біти від самої появи LP64. Щоб відтворити умови 32-бітної системи, не шукаючи 32-бітного заліза, вистачає ключа `-m32` і другого комплекту бібліотек ([як його поставити й чому одного ядра для цього замало](book:unix-linux/compat-32-on-64)):

```
Debian / Ubuntu:  sudo apt install gcc-multilib libc6-dev-i386
Fedora:           sudo dnf install glibc-devel.i686 libgcc.i686
```

Комплект i386 у більшості дистрибутивів навмисно лишили зі старим 32-бітним `time_t` — його тримають, щоб запускати давні двійкові файли, а не щоб на ньому будувати нове. Для нашого досліду це якраз ідеальний піддослідний. Усі команди нижче припускають `-m32`; на справжній 32-бітній машині цей ключ просто прибирають.

## Проба перша: що думає про час сама програма

Задача — дізнатися ширину типу й межу шкали, не покладаючись на жодне припущення про архітектуру. Ідея — обчислити максимум типу арифметично (з самого `sizeof`, а не з константи в заголовку) і перекласти його в дату.

Тут одразу трапляється перша пастка, і вона показова. Максимум **не можна** шукати через `max + 1` або через зсув у самому `time_t`: знакове переповнення в C — це [невизначена поведінка](book:programming/undefined-behavior), і компілятор має повне право побудувати код у припущенні, що його не буває. Усі граничні обчислення робимо в беззнаковому типі.

```c
/* y2038-probe.c — ширина типу часу й межа його шкали */
#define _GNU_SOURCE
#include <limits.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <time.h>

/* Максимум time_t, обчислений без жодного переповнення. */
static time_t time_t_max(void)
{
    if ((time_t)-1 > 0)                 /* тип виявився беззнаковим */
        return (time_t)-1;

    const unsigned bits = (unsigned)sizeof(time_t) * CHAR_BIT;
    return (time_t)(((uintmax_t)1 << (bits - 1)) - 1);
}

static void show(const char *what, time_t t)
{
    struct tm tm;
    char buf[64];

    /* gmtime_r віддає NULL, коли рік не влазить у int tm_year. */
    if (gmtime_r(&t, &tm) == NULL) {
        printf("%-14s %21jd   (у struct tm не вміщається)\n",
               what, (intmax_t)t);
        return;
    }
    strftime(buf, sizeof buf, "%Y-%m-%d %H:%M:%S UTC", &tm);
    printf("%-14s %21jd   %s\n", what, (intmax_t)t, buf);
}

int main(void)
{
    struct timespec now;
    time_t tmax = time_t_max();

    printf("sizeof(time_t)           = %zu\n", sizeof(time_t));
    printf("sizeof(struct timespec)  = %zu\n", sizeof(struct timespec));
    printf("sizeof(off_t)            = %zu\n", sizeof(off_t));
    printf("sizeof(st_mtim.tv_sec)   = %zu\n",
           sizeof(((struct stat *)0)->st_mtim.tv_sec));
    printf("sizeof(long)             = %zu\n", sizeof(long));
#ifdef __TIMESIZE
    printf("__TIMESIZE               = %d\n", __TIMESIZE);
#endif
#ifdef __USE_TIME_BITS64
    printf("64-бітний час            = увімкнено\n");
#endif
    putchar('\n');

    clock_gettime(CLOCK_REALTIME, &now);
    show("зараз", now.tv_sec);
    show("максимум", tmax);
    /* Перетворення завеликого беззнакового значення в знаковий тип стандарт
       лишає на розсуд реалізації — і GCC з Clang визначають його як
       загортання. Саме тому цей рядок писати можна, а «tmax + 1» — ні. */
    show("максимум + 1", (time_t)((uintmax_t)tmax + 1));
    return 0;
}
```

Той самий файл збираємо двічі — і саме порівняння двох стовпчиків є результатом проби:

```
$ gcc -m32 -O2 -Wall -o probe32 y2038-probe.c
$ gcc -m32 -O2 -Wall -D_FILE_OFFSET_BITS=64 -D_TIME_BITS=64 -o probe64 y2038-probe.c
```

```
        ./probe32                                ./probe64
sizeof(time_t)           = 4             sizeof(time_t)           = 8
sizeof(struct timespec)  = 8             sizeof(struct timespec)  = 16
sizeof(off_t)            = 4             sizeof(off_t)            = 8
sizeof(st_mtim.tv_sec)   = 4             sizeof(st_mtim.tv_sec)   = 8
sizeof(long)             = 4             sizeof(long)             = 4
__TIMESIZE               = 32            __TIMESIZE               = 32
                                         64-бітний час            = увімкнено

зараз          1786060800  2026-08-07…   зараз          1786060800  2026-08-07…
максимум       2147483647  2038-01-19…   максимум  9223372036854775807  (не вміщається)
максимум + 1  -2147483648  1901-12-13…   максимум + 1 -9223372036854775808  (не вміщається)
```

Три рядки з цієї таблиці варті окремої уваги.

`sizeof(off_t)` теж змінився — і це не побічний ефект, а вимога. Час і розмір файлу сидять в одній структурі `stat`, тож розширювати їх нарізно нема сенсу; glibc це просто забороняє. Спроба задати `-D_TIME_BITS=64` без `-D_FILE_OFFSET_BITS=64` обривається на компіляції рядком `_TIME_BITS=64 is allowed only with _FILE_OFFSET_BITS=64` — рідкісний випадок, коли помилка ловиться найдешевшим способом.

`__TIMESIZE` лишився `32` в обох стовпчиках. Це не помилка: макрос описує **природну** для платформи ширину, і ключ її не змінює. Ознака того, що ключ спрацював, — інша, `__USE_TIME_BITS64`, і саме її варто перевіряти в коді.

`sizeof(long)` не змінився ніде. На 32-бітній машині `long` має чотири байти незалежно від того, що робиться з часом, — і на цьому побудована одна з найтихіших поломок переходу, до якої ми ще дійдемо.

Останній рядок правого стовпчика показує, що [ширина типу й ширина календаря — різні речі](book:programming/integer-types-c): `time_t` тепер тримає момент за 292 мільярди років, а `struct tm` його не приймає, бо `tm_year` лишився звичайним `int`. `gmtime_r` чесно віддає `NULL`; програма, яка цього не перевіряє, розіменує його й упаде.

Чи справді ключ дійшов до бібліотеки, а не лише до заголовків, видно з самого двійкового файлу:

```
$ nm -D --undefined-only ./probe64 | grep 64
                 U __clock_gettime64@GLIBC_2.34
                 U __gmtime64_r@GLIBC_2.34
```

Це найнадійніша перевірка з усіх, бо вона питає не збірку, а вже готовий артефакт: імена з суфіксом `64` у glibc з'явилися разом із самою можливістю й ведуть до 64-бітних варіантів. Той самий `nm` варто прогнати по кожній спільній бібліотеці, з якою програма компонується, — про це нижче.

## Проба друга: чи вміє ядро

Тепер запитання до другого боку межі. Бібліотека може скільки завгодно вважати, що `time_t` має 64 біти, — якщо ядро не має `_time64`-викликів, ці біти нікуди не поїдуть.

Найпрямішу відповідь дає [системний виклик, зроблений в обхід бібліотеки](book:unix-linux/syscall-mechanics), із розкладкою, яку ядро чекає незалежно від того, що думає libc:

```c
/* y2038-kernel.c — чи є в ядра 64-бітна пара до clock_gettime */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

/* Саме так виглядає struct __kernel_timespec: секунди — рівно 64 біти,
   що б про time_t не думала бібліотека C. */
struct kernel_timespec64 {
    long long tv_sec;
    long long tv_nsec;
};

int main(void)
{
#ifdef __NR_clock_gettime64
    struct kernel_timespec64 ts = { 0, 0 };

    if (syscall(__NR_clock_gettime64, CLOCK_REALTIME, &ts) == 0) {
        printf("clock_gettime64 (№%ld) працює, tv_sec = %lld\n",
               (long)__NR_clock_gettime64, ts.tv_sec);
        return 0;
    }
    if (errno == ENOSYS) {
        puts("clock_gettime64 відсутній: ядро старше за 5.1 (травень 2019)");
        return 1;
    }
    printf("clock_gettime64 повернув помилку: %s\n", strerror(errno));
    return 1;
#else
    puts("номера clock_gettime64 немає в заголовках: або архітектура 64-бітна "
         "(там звичайний clock_gettime уже 64-бітний), або заголовки застарілі");
    return 0;
#endif
}
```

Два «ні» тут означають зовсім різне, і плутати їх не варто. Умова `#ifdef` не спрацювала — заголовки ядра, з якими зібрано систему, старіші за появу цих номерів; це проблема складання, а не машини. `ENOSYS` — виклик є в заголовках, але немає в ядрі, яке зараз працює; це вже проблема машини, і лікується вона тільки оновленням ядра.

На 32-бітній програмі, що працює під 64-бітним ядром, відповідь буде «так» — але вона стосується [шару сумісности](book:unix-linux/compat-32-on-64), а не тієї 32-бітної системи, заради якої дослід затівався. Остаточну відповідь про ядро дає лише запуск на цільовому пристрої.

## Проба третя: що витримує носій

Дві попередні проби перевіряли ті вмістища, які можна перезібрати. Тепер — те, яке перезібрати не можна: поле часу в [inode](book:unix-linux/inode-model). Тут аудит стає найважливішим, бо «ні» на цій пробі коштує не перезбирання, а перенесення даних.

Ідея проби спирається на дуже вдалу властивість ядра. Коли позначку часу неможливо записати точно, ядро **не повертає помилки** — воно, за формулюванням стандарту, кладе найбільше значення, яке файлова система здатна вмістити й яке не перевищує заданого. Тобто підрізає. А підрізане значення можна прочитати назад і порівняти:

```c
/* y2038-fs.c — чи витримує ця файлова система дату за 2038 роком.
   Збирати ОБОВ'ЯЗКОВО з -D_FILE_OFFSET_BITS=64 -D_TIME_BITS=64.  */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

#define BEYOND 2177452800LL          /* 2039-01-01 00:00:00 UTC */
#define WALL   2147483647LL          /* 2038-01-19 03:14:07 UTC */

int main(int argc, char **argv)
{
    const char *dir = (argc > 1) ? argv[1] : ".";
    char path[4096];
    struct timespec times[2];
    struct stat st;
    long long got;
    int fd;

    if (sizeof(times[0].tv_sec) < 8) {
        fprintf(stderr, "tv_sec тут має %zu байти — перезберіть програму\n",
                sizeof(times[0].tv_sec));
        return 2;
    }

    snprintf(path, sizeof path, "%s/y2038probe.XXXXXX", dir);
    if ((fd = mkstemp(path)) < 0) { perror("mkstemp"); return 1; }

    times[0].tv_sec  = (time_t)BEYOND;    /* atime */
    times[0].tv_nsec = 123456789;
    times[1] = times[0];                  /* mtime */

    if (utimensat(AT_FDCWD, path, times, 0) != 0) { perror("utimensat"); goto out; }
    if (stat(path, &st) != 0)                     { perror("stat");      goto out; }

    got = (long long)st.st_mtim.tv_sec;
    printf("записано : %lld.%09ld\n", BEYOND, 123456789L);
    printf("прочитано: %lld.%09ld\n", got, (long)st.st_mtim.tv_nsec);

    if (got == BEYOND)
        puts("вердикт  : поле часу тут ширше за 32 біти");
    else if (got == WALL)
        puts("вердикт  : значення підрізано рівно до межі — поле 32-бітне");
    else
        printf("вердикт  : значення змінилося на %lld — розберіться окремо\n", got);

out:
    close(fd);
    unlink(path);
    return 0;
}
```

Наносекунди в цій пробі несуть окрему звістку. Класичний inode [ext4](book:unix-linux/filesystem-families) на 128 байтів не має ані додаткових бітів секунд, ані частки секунди взагалі — і прочитані `tv_nsec` виявляться нулем, ще до того, як щось скажуть секунди. Нуль у наносекундах на нібито сучасній файловій системі — сам собою привід перевірити розмір inode.

Ту саму відповідь дають системні інструменти, і зіставити їх з програмою корисно:

```
$ sudo dumpe2fs -h /dev/sda2 | grep -i 'inode size'
Inode size:               256          ← 128 означає смерть у 2038-му

$ xfs_info /srv | grep -o 'bigtime=[01]'
bigtime=1                              ← 0 означає межу в січні 2038-го
```

За цими двома рядками стоїть ось що. Inode ext4 на 256 байтів має додаткове поле, у якому два молодші біти розширюють секунди з 32 до 34, а решта тридцять віддані наносекундам; це відсуває межу до 10 травня 2446 року. Inode на 128 байтів такого поля не має взагалі, і єдиний спосіб полагодити таку файлову систему — створити нову й перенести дані. XFS має властивість `bigtime`: беззнаковий 64-бітний лічильник наносекунд від грудня 1901-го, шкала до липня 2486-го. Сучасний `mkfs.xfs` вмикає її на нових файлових системах типово (крім `-m crc=0`), а вже створену можна оновити на **відмонтованій** і перевіреній `xfs_repair -n` системі:

```
$ sudo xfs_admin -O bigtime=1 /dev/sdb1
```

Це рух в один бік: після нього старі ядра таку файлову систему не змонтують.

> 🔧 **Навіщо це.** Дві дати варто просто запам'ятати як діагностичні відбитки. **2038-01-19 03:14:07** означає, що значення десь **підрізали** — таке роблять ядро й розбірники тексту, тобто винен вузький приймач. **1901-12-13 20:45:52** означає, що значення **загорнулося** — а це вже арифметика в 32-бітному знаковому типі, тобто винен код, який рахував. За симптомом одразу видно, у якому з двох світів шукати.

## Проба четверта: перевести годинник

Три перші проби відповідають на питання про ширину полів. Вони не відповідають на питання, чи не викинув компілятор ваші перевірки й чи не розкладено десь у програмі неявне припущення про майбутнє. На це відповідає лише переведений годинник — і ставити такий дослід треба обережно, бо він шкодить машині більше, ніж здається.

Перше, що спадає на думку, не працює. [Простір імен часу](book:unix-linux/namespaces) навмисно **не віртуалізує** `CLOCK_REALTIME` — він зсуває лише монотонний годинник і годинник від завантаження, а від віртуалізації настінного відмовилися через складність і накладні витрати всередині ядра. Тому `unshare --time` для аудиту 2038-го марний: настінний час у такому оточенні лишається загальносистемним.

Друга спокуса — `libfaketime`, що [перекриває символи бібліотеки C](book:unix-linux/symbol-resolution) через `LD_PRELOAD`. Цим справді зручно перевіряти прикладну логіку, але межі інструмента треба знати чітко: він не бачить статично зібраних програм, не бачить прямих системних викликів і не впливає на те, які позначки часу ставить **ядро** — а поломки у файлових системах і таймерах живуть саме там.

Чесний дослід — окрема віртуальна машина або пристрій, який не шкода, зі знімком стану перед початком:

```
# зупинити синхронізацію, інакше вона поверне годинник за кілька секунд
$ sudo systemctl stop systemd-timesyncd    # або chronyd / ntpd
$ sudo date -s '2038-01-19 03:14:00 UTC'
```

Права на це дає `CAP_SYS_TIME`, а не звання власника машини, — [окрема можливість, яку носить процес](book:unix-linux/capabilities). І одразу після переведення система починає розсипатися передбачуваним чином, тож варто знати, що з цього є симптомом досліду, а що — власне поломкою.

**Сертифікати перестають бути дійсними.** Перевірка строку `notAfter` — це порівняння двох чисел, і TLS-з'єднання просто перестають установлюватися. Апарат, який тягне оновлення з мережі, після переходу межі втрачає цей шлях назавжди — і полагодити його можна тільки руками на місці.

**Таймери спрацьовують усі одразу.** Служба, налаштована «раз на добу», бачить, що від минулого запуску минуло дванадцять років, і кидається наздоганяти пропущене.

**Позначки часу з майбутнього лишаються на диску.** Файли, записані, поки годинник стояв попереду, зберігають ту дату й після повернення годинника назад. Системи збірки, які порівнюють час джерела й результату, після цього вважають результат вічно свіжим; `find -newer` та резервне копіювання за часом теж перестають бачити зміни. Цю поломку **не можна відкотити** переведенням годинника назад — тільки перезаписом файлів. Саме через неї дослід ставлять на знімку, а не «швиденько на робочій машині».

## Пастки, і чому кожна з них тиха

### Перевірка, якої не існує

Найпоширеніший спосіб захиститися від межі виглядає так:

```c
time_t deadline = now + timeout;

if (deadline < now)          /* «а раптом переповнилося?» */
    return -EOVERFLOW;
```

Цієї перевірки в зібраному коді немає. Компілятор міркує законно: при додатному `timeout` вираз `now + timeout` більший за `now`, бо інакше сталося б знакове переповнення, а його за правилами мови не буває. Отже, умова тотожно хибна, отже, гілку можна викинути. Викидається вона мовчки — і зазвичай тільки на `-O2`, бо це наслідок поширення діапазонів значень, а на `-O0` цей прохід не працює. Помилка, яка є лише у випусковій збірці, — найгірший різновид помилки.

Перевіряти треба **до** дії й у межах, які напевно існують:

```c
/* Межі типу, обчислені так само беззнаково, як у першій пробі. */
#define TIME_T_MAX ((time_t)(((uintmax_t)1 << (sizeof(time_t) * CHAR_BIT - 1)) - 1))
#define TIME_T_MIN ((time_t)(-TIME_T_MAX - 1))

if (timeout > 0 && now > TIME_T_MAX - timeout) return -EOVERFLOW;
if (timeout < 0 && now < TIME_T_MIN - timeout) return -EOVERFLOW;

time_t deadline = now + timeout;   /* тепер безпечно */
```

Різниця не косметична: `TIME_T_MAX - timeout` при додатному `timeout` не може вийти за межі типу, тож ця перевірка залишиться в коді за будь-якої оптимізації.

Побачити викинуті гілки в чужому коді допомагають два ключі, і роль у них різна. `-fsanitize=signed-integer-overflow` додає перевірку в час виконання й друкує місце — але лише якщо тестовий прогін справді пройде тим шляхом. `-fwrapv` робить загортання визначеним, і після цього перевірка `deadline < now` перестає зникати й починає спрацьовувати; значення при цьому все одно неправильне, зате поломка стає видимою. Саме тому ядро Linux збирають із `-fno-strict-overflow`: у коді такого віку не можна ручатися, що жодна перевірка не написана «після дії».

### Мінус одиниця як помилка і як дата

Календарні функції несуть у собі домовленості, старші за самий `time_t`, і всі вони перевантажують один канал відповіді.

```c
struct tm tm = { .tm_year = 2039 - 1900, .tm_mon = 0, .tm_mday = 1,
                 .tm_isdst = -1 };      /* −1 = «літній час невідомий» */

errno = 0;                              /* обов'язково: інакше не розрізнити */
time_t t = mktime(&tm);
if (t == (time_t)-1 && errno != 0)
    return -EOVERFLOW;
```

`mktime` повідомляє про невдачу значенням `(time_t)-1` і кодом `EOVERFLOW` — але `-1` є цілком законною позначкою, вона означає 31 грудня 1969 року, 23:59:59 UTC. Відрізнити помилку від дати можна тільки через `errno`, і тільки якщо його обнулили перед викликом. Далі помиляються в обидва боки: код, який перевіряє лише `t == -1`, відкидає одну справжню секунду історії; код, який не перевіряє нічого, тихо кладе в базу 31 грудня 1969 року замість дати, яку не зміг перетворити.

Другий бік тієї самої монети — `gmtime` і `localtime`, які повертають `NULL` з тим самим `EOVERFLOW`, коли рік не влазить у `int tm_year`. Класичний рядок `strftime(buf, n, "%Y-%m-%d", gmtime(&t))` після переходу на 64-бітний `time_t` дістає шанс упасти на розіменуванні `NULL` — там, де на 32 бітах він не міг упасти ніколи, бо у вужчий тип просто не вміщалося значення, якого календар не приймає.

Нарешті, `strftime` повертає нуль і тоді, коли результат не вліз у буфер, і тоді, коли форматований рядок законно порожній. А `%Y` для року, більшого за 9999, дає **більше** чотирьох цифр — і будь-який розбирач, що чекає рівно `YYYY-MM-DD`, ламається на позиції. Розширення `time_t` не розширює календарний шлях; воно лише дозволяє в нього потрапити значенням, яких раніше там не бувало.

Окремо варто пам'ятати, що `mktime` тлумачить `struct tm` у **місцевому** поясі й нормалізує структуру просто на місці. Для UTC є `timegm`, і в аудиті слід уживати саме його, інакше межу перетинатимуть у різні моменти на різних машинах.

### Тип поїхав, а формат лишився

Це наслідок того `sizeof(long) = 4`, який не змінився в правому стовпчику першої проби.

```c
printf("%ld\n", t);            /* попередження: %ld чекає long, дано __time64_t */
printf("%ld\n", (long)t);      /* попередження зникло — разом зі старшою половиною */
printf("%jd\n", (intmax_t)t);  /* єдина форма, яка не бреше */
```

Механізм тут перевернутий, і саме тому пастка спрацьовує: `-Wformat` цю помилку **знаходить** — а людина «виправляє» її саме тим приведенням, яке її створює. Для `time_t` у C немає власного специфікатора, тож єдиний правильний хід — `(intmax_t)` з `%jd` або `(long long)` з `%lld`.

Те саме на вході. `strtol` на 32-бітній машині віддає `long`, тобто впирається в `LONG_MAX` і виставляє `ERANGE`; позначка «2177452800», прочитана з тексту, мовчки стає `2147483647`. Кожна дата з-за межі перетворюється на **ту саму** секунду 19 січня 2038 року — за цим відбитком поломку впізнають з першого погляду. Правильно — `strtoll` чи `strtoimax`. Той самий закон діє для стовпця `INTEGER` у базі, для 32-бітного поля в протоколі й для числа в JSON, розібраного в 32-бітний тип: розширення `time_t` не сягає за межі процесу.

### Два об'єктні файли, що не домовилися

Найтихіша поломка переходу не має ані попередження компілятора, ані помилки компонування.

Ключ `-D_TIME_BITS=64` діє на **заголовки**, тобто на кожен файл окремо. Усередині glibc це безпечно: заголовок перенаправляє `stat` на `__stat64_time64`, і два різні імені не можуть зіткнутися. Але ваша власна функція `void note(struct stat *st)` в C має одне й те саме ім'я в обох збірках. Компонувальник радо з'єднає файл, який передає структуру нової форми, з файлом, який читає її за старою розкладкою.

![Ті самі шістнадцять байтів struct timespec: бібліотека розклала їх як 8 байтів секунд плюс 4 наносекунд плюс набивка, а об'єктний файл без прапорця читає перші 4 байти як секунди, а другі 4 — як наносекунди](/reference/unix-linux/foundations/time-representation-y2038/img/mixed-object-layout.svg)

*Обидва прочитання самодостатні й несуперечливі — просто вони про різні структури.*

Придивіться до наслідків, бо саме вони пояснюють, чому помилку не знаходять роками. Старий читач бере молодшу половину секунд і тлумачить її як усі секунди — доки значення менше за 2³¹, воно **збігається**. Наносекунди він бере зі старшої половини, де сьогодні самі нулі, — і завжди отримує нуль замість частки секунди. Тобто ознака поломки на сучасних даних одна-єдина: наносекунди раптом стали нульовими. Решта симптомів чекає 2038 року — рівно того року, заради якого це все й затівалося.

Захист будується у два шари, бо загроз теж дві.

Свій код прикриває умова часу компіляції в спільному заголовку, який підключений звідусіль:

```c
/* time-abi.h — підключати першим у кожному файлі проєкту */
#include <time.h>

_Static_assert(sizeof(time_t) == 8,
    "файл зібрано без -D_TIME_BITS=64 -D_FILE_OFFSET_BITS=64");
```

Вона перетворює тиху розбіжність ABI на зрозумілу помилку збірки — але тільки для тих файлів, які цей заголовок підключили. Звідси й практичне правило: ці два ключі мають жити в **одному** місці на все дерево збірки, поруч із рештою [прапорців компіляції](book:build-systems/build-flags), і ніколи не задаватися пофайлово.

Чужий код прикриває перевірка готових артефактів, бо на них умови компіляції вже не діють:

```
$ nm -D --undefined-only ./myapp | grep time64
$ for so in $(ldd ./myapp | awk '/=>/ {print $3}'); do
      printf '%-44s %s\n' "$so" "$(nm -D "$so" 2>/dev/null | grep -c time64)"
  done
```

Читати цей стовпчик треба з розбором. Нуль у бібліотеки, яка часу взагалі не торкається, не означає нічого. Нуль у тієї, що приймає або віддає `time_t` у своєму відкритому інтерфейсі, означає, що вона зі старого світу, — а така бібліотека змінює [ABI при переході](book:unix-linux/library-abi-compat) і має бути перезібрана разом із усім, що нею користується. Дистрибутиви вирішують це найгрубішим і найнадійнішим способом: Debian під час своєї 64-бітної перебудови додав до імен таких пакунків суфікс `t64`, щоб дві форми фізично не могли опинитися в одній системі.

Відповідь аудиту, до речі, має строк придатности. Вона стосується цього двійкового файлу, цього ядра й цієї файлової системи — а не машини взагалі. Оновлення пакунка, підкладена стороння бібліотека або розділ, розмічений інсталятором зі старими типовими значеннями, повертають будь-яку з чотирьох проб у стан «не питали».
