# 📋 Поверхня 64-бітного часу: типи, структури, пари викликів, ключі складання

Це перелік усіх місць, де ширина `time_t` є не внутрішньою справою програми, а домовленістю між незалежно зібраними частинами системи: типи, розкладки структур, пари системних викликів, опції сокета, номери `ioctl` і ключі компілятора. Потрібен він тоді, коли 32-бітну систему переводять через межу 2038 року або коли пишуть код, що має однаково працювати по обидва боки переходу, — бо кожен рядок нижче є місцем, де дві сторони можуть розійтися **мовчки**, без помилки складання й без попередження.

Одразу межа застосовности: на 64-бітних архітектурах більшість цього не має сенсу — там `long` уже широкий, тож і `time_t` теж, і жодного роздвоєння системних викликів не існує. Усе, що тут написано, стосується 32-бітних архітектур і [шару сумісности](book:unix-linux/compat-32-on-64), яким 64-бітне ядро обслуговує 32-бітні програми.

## Словник типів

| Ім'я | Де живе | Ширина на 32-бітній архітектурі | Що означає |
| --- | --- | --- | --- |
| `time_t` | `<time.h>`, простір користувача | 32 **або** 64 — залежить від ключів складання | те, що бачить програма |
| `__kernel_old_time_t` | uapi-заголовки | 32 (`long`) | стара вузька форма на межі ядра |
| `__kernel_time64_t` | uapi-заголовки | 64 (`long long`) | широка форма на межі ядра |
| `old_time32_t` | `linux/time32.h`, код ядра | 32 (`s32`) | те саме, що `__kernel_old_time_t`, з боку ядра |
| `time64_t` | `linux/time64.h`, код ядра | 64 (`s64`) | час усередині ядра — завжди широкий |
| `ktime_t` | код ядра | 64 (`s64`), наносекунди | одне число замість пари; має власну стелю |
| `__kernel_suseconds_t` | uapi-заголовки | як `long` | мікросекунди в `timeval` |

Найважливіший рядок — перший. `time_t` є **єдиним типом у цьому переліку, ширина якого не визначена наперед**: її обирає бібліотека C за ключами, з якими зібрано програму. Решта імен існує саме тому, що ядро мусить називати обидві ширини різними словами, аби компілятор не дав їх переплутати.

Базові структури живуть в одному файлі:

```c
/* include/uapi/linux/time_types.h — форми, у яких час перетинає межу */

struct __kernel_timespec {
	__kernel_time64_t	tv_sec;		/* секунди — завжди 64 біти */
	long long		tv_nsec;
};

struct __kernel_itimerspec {
	struct __kernel_timespec it_interval;
	struct __kernel_timespec it_value;
};

struct __kernel_old_timespec {
	__kernel_old_time_t	tv_sec;		/* вузька форма */
	long			tv_nsec;
};

struct __kernel_old_timeval {
	__kernel_long_t		tv_sec;		/* лишили лише там, де це ТРИВАЛІСТЬ;
						   нових користувачів не заводять */
	__kernel_long_t		tv_usec;
};

struct __kernel_old_itimerval {
	struct __kernel_old_timeval it_interval;
	struct __kernel_old_timeval it_value;
};

struct __kernel_sock_timeval {
	__s64 tv_sec;				/* окрема широка форма для сокетів */
	__s64 tv_usec;
};
```

Зверніть увагу на `__kernel_old_timeval`: він не є помилкою, яку забули виправити. Його свідомо лишили вузьким там, де поле несе **проміжок**, а не позначку на осі часу, — і в самому заголовку стоїть застереження не заводити нових користувачів.

## Де саме сидить `time_t`

| Структура | Часові поля | Через які інтерфейси перетинає межу | Стан на 32-бітній архітектурі |
| --- | --- | --- | --- |
| `struct timespec` | `tv_sec` | `clock_*`, `nanosleep`, `timerfd_*`, `timer_*`, `futex`, `pselect`, `ppoll`, `sem_timedwait`, `stat` | замінена на `__kernel_timespec` у `_time64`-викликах |
| `struct timeval` | `tv_sec` | `gettimeofday`, `select`, `adjtimex`, всередині `rusage` й `itimerval`, опції сокета | розщеплена: `__kernel_old_timeval` для тривалостей, `__kernel_sock_timeval` для сокетів |
| `struct stat` | `st_atim`, `st_mtim`, `st_ctim` | `stat`, `fstat`, `lstat`, `fstatat` | окремого `stat_time64` **немає**: широкі позначки віддає [statx](book:unix-linux/statx-extended-stat) |
| `struct utimbuf` | `actime`, `modtime` | `utime` | libc перекладає виклик в `utimensat_time64` |
| `struct itimerspec` | два `timespec` | `timer_settime`, `timer_gettime`, `timerfd_*` | `__kernel_itimerspec` у `_time64`-викликах |
| `struct itimerval` | два `timeval` | `getitimer`, `setitimer` | ядро **не міняло**: це тривалості (`__kernel_old_itimerval`) |
| `struct rusage` | `ru_utime`, `ru_stime` | `getrusage`, `wait3`, `wait4` | ядро **не міняло**: спожитий процесорний час — тривалість |
| `struct semid_ds` | `sem_otime`, `sem_ctime` | `semctl(IPC_STAT)` | розширена **на місці** полями `_high` |
| `struct msqid_ds` | `msg_stime`, `msg_rtime`, `msg_ctime` | `msgctl(IPC_STAT)` | те саме |
| `struct shmid_ds` | `shm_atime`, `shm_dtime`, `shm_ctime` | `shmctl(IPC_STAT)` | те саме |
| `struct timex` | поле `time` типу `timeval` | `adjtimex`, `ntp_adjtime`, `clock_adjtime` | замінена на `struct __kernel_timex`, виклик `clock_adjtime64` |
| `struct sysinfo` | `uptime` | `sysinfo()` | **не стосується 2038-го**: це час від старту машини, а не позначка на осі |
| cmsg `SCM_TIMESTAMP` | `struct timeval` у тілі повідомлення | `recvmsg` | нова опція `SO_TIMESTAMP_NEW` віддає `__kernel_sock_timeval` |
| `struct input_event` | `time` | читання з `/dev/input/eventN` | **не розширено**: розкладку лише захищено від хибного прочитання |

Рядок `sysinfo` варто прочитати уважно, бо він показує, як відрізняти справжню біду від уявної. Поле `uptime` має тип `__kernel_long_t`, тобто на 32-бітній машині — тридцять два біти. Але лічить воно секунди **від увімкнення**, а не від 1970 року, і переповниться аж після 68 років безперервної роботи. Дата 2038 тут ні до чого: у полі, яке несе тривалість, епохи немає взагалі.

## Три способи, якими це полагодили

Ядро не мало одного універсального прийому. Вибір щоразу диктувала природа поля.

**Спосіб перший — виклик-близнюк.** Якщо структура несе позначку на осі часу й перетинає межу, поруч зі старим викликом ставили новий із суфіксом `_time64`. Старий лишався бітом у біт таким, як був, і всередині ядра діставав ім'я з суфіксом `_time32`.

**Спосіб другий — розширення на місці.** Структури керування [міжпроцесовими об'єктами](book:unix-linux/ipc-landscape) мали в собі невживані поля-набивки, і саме туди поклали старші половини:

```c
/* include/uapi/asm-generic/sembuf.h */

struct semid64_ds {
	struct ipc64_perm sem_perm;
#if __BITS_PER_LONG == 64
	long		sem_otime;	/* last semop time */
	long		sem_ctime;	/* last change time */
#else
	unsigned long	sem_otime;	/* молодші 32 біти */
	unsigned long	sem_otime_high;	/* колишнє __unused1 */
	unsigned long	sem_ctime;
	unsigned long	sem_ctime_high;	/* колишнє __unused2 */
#endif
	unsigned long	sem_nsems;
	unsigned long	__unused3;
	unsigned long	__unused4;
};
```

![Чотири поля struct semid64_ds у пам'яті: sem_otime і sem_otime_high тримають молодші й старші половини однієї 64-бітної позначки, так само sem_ctime і sem_ctime_high](/reference/unix-linux/foundations/time-representation-y2038/img/ipc-time-split.svg)

*Розмір структури не змінився, номер виклику не змінився — змінилося лише значення двох полів, які раніше нічого не означали.*

Наслідків із цього три, і кожен практичний.

- Складання половин — робота **програми**, не ядра: `sem_otime + ((long long)sem_otime_high << 32)`.
- Молодша половина оголошена **беззнаковою** (`unsigned long`) не випадково: знакове поле прочитало б значення понад 2³¹ як від'ємне, і в сумі воно б відняло замість додати.
- Порядок полів у пам'яті сталий і не залежить від порядку байтів у машині: молодша половина завжди перша. Саме тому на архітектурі зі старшим байтом уперед не можна просто накласти на цю пару вісім байтів і прочитати їх як одне число.

**Спосіб третій — не міняти нічого.** Там, де поле несе тривалість, ядро лишило вузьку форму: `getitimer`/`setitimer` і `getrusage`/`wait4` близнюків не отримали. Але це не звільняє [бібліотеку C](book:unix-linux/libc-as-gateway) від роботи: у програмі, зібраній із широким `time_t`, `struct itimerval` та `struct rusage` **уже інші**, і libc мусить перекласти їх у вузьку ядрову форму й назад — цілком у просторі користувача, без жодного нового виклику. Отже, «ядро не міняло» ще не означає «нічого не змінилося для мене».

## Пари `*_time32` / `*_time64`

Набір увійшов у ядро 5.1 (травень 2019). Номери однакові на всіх 32-бітних архітектурах і оголошені лише там: заголовок обгортає весь блок умовою `#if defined(__SYSCALL_COMPAT) || __BITS_PER_LONG == 32`, тож на 64-бітній машині цих номерів просто не існує.

| № | Виклик `_time64` | Що дублює | Що несе |
| --- | --- | --- | --- |
| 403 | `clock_gettime64` | `clock_gettime` | `timespec` на виході |
| 404 | `clock_settime64` | `clock_settime` | `timespec` на вході |
| 405 | `clock_adjtime64` | `clock_adjtime` | `struct __kernel_timex` |
| 406 | `clock_getres_time64` | `clock_getres` | `timespec` на виході |
| 407 | `clock_nanosleep_time64` | `clock_nanosleep` | `timespec` туди й назад; сюди ж libc відводить `nanosleep` і `sleep` |
| 408 | `timer_gettime64` | `timer_gettime` | `itimerspec` |
| 409 | `timer_settime64` | `timer_settime` | `itimerspec` |
| 410 | `timerfd_gettime64` | `timerfd_gettime` | `itimerspec` |
| 411 | `timerfd_settime64` | `timerfd_settime` | `itimerspec` |
| 412 | `utimensat_time64` | `utimensat` | два `timespec`; сюди ж libc відводить `utime`, `utimes`, `futimes`, `futimesat` |
| 413 | `pselect6_time64` | `pselect6` | `timespec`-таймаут; сюди ж `select` |
| 414 | `ppoll_time64` | `ppoll` | `timespec`-таймаут; сюди ж `poll` |
| 415 | — | — | номер лишили порожнім |
| 416 | `io_pgetevents_time64` | `io_pgetevents` | `timespec`-таймаут |
| 417 | `recvmmsg_time64` | `recvmmsg` | `timespec`-таймаут |
| 418 | `mq_timedsend_time64` | `mq_timedsend` | абсолютний `timespec` |
| 419 | `mq_timedreceive_time64` | `mq_timedreceive` | абсолютний `timespec` |
| 420 | `semtimedop_time64` | `semtimedop` | `timespec`-таймаут |
| 421 | `rt_sigtimedwait_time64` | `rt_sigtimedwait` | `timespec`-таймаут |
| 422 | `futex_time64` | `futex` | `timespec`, абсолютний або відносний |
| 423 | `sched_rr_get_interval_time64` | `sched_rr_get_interval` | `timespec` на виході |

Кілька зауваг до таблиці, без яких вона вводить в оману.

Стовпчик «що дублює» називає **системний виклик**, а не функцію бібліотеки. Багато звичних імен — `time`, `gettimeofday`, `select`, `poll`, `nanosleep`, `utime` — власного номера не мають узагалі: бібліотека давно зводить їх до кількох базових [системних викликів](book:unix-linux/syscall-mechanics), і після переходу вона зводить їх до широких близнюків.

`stat` у цьому переліку немає. Виклику `stat_time64` не існує: широкі позначки файлів віддає `statx`, який з'явився раніше (ядро 4.11) з іншої причини й одразу мав 64-бітне поле секунд. Отже, для файлових позначок відповідь на питання «чи широкий тут час» залежить не від версії 5.1, а від того, чи вміє ваша libc ходити через `statx`.

Годинник читають не лише викликом. На 32-бітних архітектурах поряд із `__vdso_clock_gettime` з'явився [`__vdso_clock_gettime64`](book:unix-linux/vdso) — і програма, зібрана з широким часом, бере саме його, не заходячи в ядро взагалі.

Арнд Берґман, який вів цю роботу разом із Діпою Дінамані, назвав першою придатною основою для 32-бітної системи, розрахованої на життя після 2038 року, не 5.1, а **5.6** (березень 2020): у 5.1 з'явилися виклики, а решта проміжку пішла на дрібніші інтерфейси й драйвери.

## Сокети: опції з суфіксом `_NEW`

П'ять опцій рівня `SOL_SOCKET` несуть час у своєму значенні або у відповіді, і всі п'ять отримали другий номер.

| Опція | Старий номер | Новий номер | Тип значення: старий → новий |
| --- | --- | --- | --- |
| `SO_RCVTIMEO` | 20 (`_OLD`) | 66 (`_NEW`) | `struct __kernel_old_timeval` → `struct __kernel_sock_timeval` |
| `SO_SNDTIMEO` | 21 | 67 | те саме |
| `SO_TIMESTAMP` | 29 | 63 | cmsg `SCM_TIMESTAMP`: `timeval` → `__kernel_sock_timeval` |
| `SO_TIMESTAMPNS` | 35 | 64 | cmsg `SCM_TIMESTAMPNS`: `timespec` → `__kernel_timespec` |
| `SO_TIMESTAMPING` | 37 | 65 | cmsg: три `timespec` → три `__kernel_timespec` |

Вибір між номерами робить сам заголовок, і робить його за шириною типу:

```c
/* include/uapi/asm-generic/socket.h */

#if __BITS_PER_LONG == 64 || (defined(__x86_64__) && defined(__ILP32__))
/* на 64-бітних і на x32 обходимося без ?: */
#define SO_TIMESTAMP		SO_TIMESTAMP_OLD
#define SO_RCVTIMEO		SO_RCVTIMEO_OLD
#else
#define SO_TIMESTAMP	(sizeof(time_t) == sizeof(__kernel_long_t) ? \
			 SO_TIMESTAMP_OLD : SO_TIMESTAMP_NEW)
#define SO_RCVTIMEO	(sizeof(time_t) == sizeof(__kernel_long_t) ? \
			 SO_RCVTIMEO_OLD : SO_RCVTIMEO_NEW)
#endif
```

Правило для програми з цього випливає одне: **писати `SO_TIMESTAMP`, ніколи не `SO_TIMESTAMP_NEW` і тим паче не число 29**. Ім'я без суфікса саме перетвориться на потрібний номер; ім'я з суфіксом жорстко прив'язує вас до однієї ширини й розійдеться з тим, що очікує ваша libc.

Найтихіша пастка тут не в номері, а в розборі відповіді. Тіло [допоміжного повідомлення](book:programming/ancillary-data-cmsg) `SCM_TIMESTAMP` при старій опції має вісім байтів (`struct timeval` із двома 32-бітними полями), при новій — шістнадцять (`struct __kernel_sock_timeval` із двома `__s64`). Програма, що приводить `CMSG_DATA(cmsg)` до типу «як завжди» й не дивиться на `cmsg_len`, читає не ті байти й навіть не помічає цього: мікросекунди завжди менші за мільйон, тож зайві старші байти виявляються нулями, і число виглядає цілком правдоподібно. Правило звідси подвійне: тип у приведенні мусить відповідати саме тій опції, яку ви ввімкнули, а довжину брати з `cmsg->cmsg_len`, а не з `sizeof` свого типу.

Тим самим переходом ідуть два `ioctl` для читання позначки останнього пакета:

```c
/* include/uapi/asm-generic/sockios.h — старі, лишилися незмінними */
#define SIOCGSTAMP_OLD		0x8906		/* struct timeval  */
#define SIOCGSTAMPNS_OLD	0x8907		/* struct timespec */

/* include/uapi/linux/sockios.h — нові */
#define SIOCGSTAMP_NEW		_IOR(SOCK_IOC_TYPE, 0x06, long long[2])
#define SIOCGSTAMPNS_NEW	_IOR(SOCK_IOC_TYPE, 0x07, long long[2])

#if __BITS_PER_LONG == 64 || (defined(__x86_64__) && defined(__ILP32__))
#define SIOCGSTAMP	SIOCGSTAMP_OLD
#else
#define SIOCGSTAMP	((sizeof(struct timeval)) == 8 ? \
			 SIOCGSTAMP_OLD : SIOCGSTAMP_NEW)
#endif
```

## `ioctl`: чому номер команди міняється сам

У [керуючому каналі до драйвера](book:unix-linux/ioctl-interface) розмір аргументу закодовано в самому номері команди: макрос `_IOR(тип, номер, T)` вкладає в число `sizeof(T)`. Звідси випливає властивість, якої немає в жодного іншого інтерфейсу цього переліку: **розширити структуру команди й лишити той самий номер неможливо** — номер зміниться сам собою.

Це радше подарунок, ніж завада. Стара програма, надіславши старий номер новому драйверові, дістане `ENOTTY` — чесну відмову замість тихо неправильної дати. Саме тому `SIOCGSTAMP_NEW` не є «тією самою командою з іншою структурою»: це інше число.

| Інтерфейс | Що з часом | Стан |
| --- | --- | --- |
| `SIOCGSTAMP`, `SIOCGSTAMPNS` | `timeval` / `timespec` | пара `_OLD` / `_NEW` з ядра 5.1 |
| `RTC_RD_TIME`, `RTC_SET_TIME` | `struct rtc_time`: `int tm_year`, `tm_mon`, `tm_mday`… | межі 2038 немає: це розкладений календар, а не скаляр (власна межа буває в самої мікросхеми — часто двоцифровий рік) |
| читання `struct input_event` | `time` типу `timeval` | розкладку лише захищено, широкої форми немає |

Останній рядок вартий коду, бо він показує третій, найскромніший різновид виправлення — коли інтерфейс не полагодили, а лише **не дали прочитати його неправильно**:

```c
/* include/uapi/linux/input.h, спрощено (окрему гілку для sparc64 прибрано).
 * __USE_TIME_BITS64 визначає libc, коли програма попросила широкий час.
 */
struct input_event {
#if (__BITS_PER_LONG != 32 || !defined(__USE_TIME_BITS64)) && !defined(__KERNEL__)
	struct timeval time;
#define input_event_sec  time.tv_sec
#define input_event_usec time.tv_usec
#else
	__kernel_ulong_t __sec;
	__kernel_ulong_t __usec;
#define input_event_sec  __sec
#define input_event_usec __usec
#endif
	__u16 type;
	__u16 code;
	__s32 value;
};
```

Умова стежить рівно за одним: щоб програма з широким `time_t` не наклала на потік подій свою `struct timeval`, яка тепер має інший розмір. Самі поля лишаються по 32 біти — 32-бітне ядро й далі пише туди вузьку позначку. Практичний вихід для драйверів вводу інший: увімкнути `EVIOCSCLOCKID` із `CLOCK_MONOTONIC` і не мати справи з настінною датою взагалі.

Звідси правило для автора нового драйвера: у структурі команди не має бути ані `time_t`, ані `struct timeval`, ані `struct timespec` — лише `__s64` або `struct __kernel_timespec`. Ті самі міркування, що й для решти полів змінної ширини, зібрано в [контракті шару сумісности](book:unix-linux/compat-32-on-64/api-compat-contract.md).

## Контракт складання в просторі користувача

| Питання | glibc 2.34 і новіші | musl 1.2 і новіші |
| --- | --- | --- |
| Типова ширина `time_t` на 32-бітній архітектурі | 32 біти | **64 біти** |
| Як увімкнути широкий час | `-D_TIME_BITS=64` **разом із** `-D_FILE_OFFSET_BITS=64` | вмикати нема чого |
| Що з уже зібраними програмами | працюють: обидва набори символів лишилися в бібліотеці | працюють через окремі обгортки зі старими іменами |
| Як звуться символи | звичайне ім'я — вузький, `__clock_gettime64` / `__stat64_time64` / `__gettimeofday64` — широкий | так само роздвоєні (`__gmtime64_r`, суфікс `64` або `_time64`) |
| На що перенаправляє заголовок | на широкий — лише за `_TIME_BITS=64` | на широкий — **завжди**; вузькі імена лишилися суто для вже зібраних програм |
| Мінімальне ядро | 5.1 для `_time64`-викликів; на старішому — `ENOSYS` і відкат | так само |
| Заголовки ядра для складання програми | не старіші за 5.1 (номери й опції `_NEW`) | не старіші за 4.19 |

Чому glibc вимагає обох макросів разом — видно зі `struct stat`: розмір файлу й час лежать в одній структурі, тож розширювати їх поодинці немає сенсу. Тому `_TIME_BITS=64` без [`_FILE_OFFSET_BITS=64`](book:unix-linux/large-file-support) не збереться взагалі — заголовок сам зупинить складання.

Три пастки, кожна з яких мовчазна.

**Макрос має бути визначений до першого `#include`.** Заголовок читає його один раз; `#define _TIME_BITS 64` після якогось `<stdio.h>` не зробить нічого. Тому надійніше ставити `-D` у ключах компілятора, а не в тексті одного файлу з багатьох.

**На glibc, старішій за 2.34, макрос нічого не означає.** Невідоме ім'я в командному рядку не є помилкою: складання пройде, `sizeof(time_t)` лишиться чотирма, і про це ніхто не скаже. Єдиний захист — перевірити ширину на етапі складання.

**Ключі мають бути однакові для всього дерева.** Кожна спільна бібліотека, у чиєму інтерфейсі є `time_t`, змінює [ABI](book:unix-linux/library-abi-compat), тож зібрати одну частину програми з широким часом, а другу з вузьким — це та сама помилка, що й з'єднати два різні визначення однієї структури. Debian саме тому перейменував бібліотечні пакети, додавши суфікс `t64`, і виконав перебірку одним ривком у 2024 році для `armhf` та `armel`; `i386` із неї свідомо вилучили, лишивши там вузький час заради вже зібраних програм.

Найкоротша перевірка, яка ловить усі три пастки одразу:

```c
/* width.c — макроси СТОЯТЬ ПЕРЕД усіма заголовками */
#define _FILE_OFFSET_BITS 64
#define _TIME_BITS 64

#include <stdio.h>
#include <time.h>

int main(void)
{
	struct timespec ts;

	printf("sizeof(time_t) = %zu\n", sizeof(time_t));
	printf("за межею 2038:   %lld\n", (long long)(time_t)2147483648LL);

	if (clock_gettime(CLOCK_REALTIME, &ts) != 0) {
		perror("clock_gettime");
		return 1;
	}
	printf("зараз:           %lld\n", (long long)ts.tv_sec);
	return 0;
}
```

```
cc -D_FILE_OFFSET_BITS=64 -D_TIME_BITS=64 width.c -o width && ./width
```

Правильний вивід — `8` і додатне `2147483648`. Четвірка в першому рядку означає, що макроси не дійшли до заголовків або libc застара; від'ємне число в другому — те саме, побачене з іншого боку. У бойовому коді цю перевірку варто зафіксувати назавжди, поставивши поруч `static_assert(sizeof(time_t) == 8, "…")` з `<assert.h>`: тоді розбіжність зупинить складання, а не дочекається 2038 року.

## Помилки на межі

| Помилка | Хто повертає | Коли |
| --- | --- | --- |
| `EOVERFLOW` | glibc, у вузькій обгортці над широким викликом | ядро віддало значення, що не влазить у 32-бітний `time_t`: так після 2038 року поводитимуться `clock_gettime`, `gettimeofday`, `stat`, `fstat` у програмі, зібраній без `_TIME_BITS=64` |
| `ENOSYS` | ядро | виклик `*_time64` на ядрі, старішому за 5.1; libc після цього відкочується на вузький і перевіряє діапазон сама |
| `EINVAL` | ядро | `clock_settime`/`settimeofday` зі значенням поза дозволеним; `tv_nsec` поза `[0, 10⁹)`; від'ємний `tv_sec` |
| `ENOPROTOOPT` | ядро | будь-яка опція `SO_*_NEW` на ядрі, старішому за 5.1 |
| `ENOTTY` | ядро | `SIOCGSTAMP_NEW` на ядрі, старішому за 5.1 |
| `EFAULT` | ядро | структуру не вдалося скопіювати через межу |

Ось як виглядає перший рядок у джерелі — вузька обгортка glibc над широким викликом:

```c
/* sysdeps/unix/sysv/linux/clock_gettime.c, спрощено */
int
__clock_gettime (clockid_t clock_id, struct timespec *tp)
{
  struct __timespec64 tp64;
  int ret = __clock_gettime64 (clock_id, &tp64);

  if (ret == 0)
    {
      if (! in_time_t_range (tp64.tv_sec))
        {
          __set_errno (EOVERFLOW);
          return -1;
        }
      *tp = valid_timespec64_to_timespec (tp64);
    }
  return ret;
}
```

> 🔧 **Навіщо це.** `EOVERFLOW` тут не є вадою — це найкраще з того, що можна зробити. Бібліотека вже має правильне число з ядра й бачить, що воно не влазить у тип, який просить програма. Вибір у неї рівно два: віддати обрізане значення, тобто дату 1901 року з виглядом справжньої, або відмовитися. Відмова гучна: `clock_gettime` повертає `−1`, і код, який хоч якось перевіряє результат, спиниться на місці помилки, а не через три шари вище, коли неправильна дата вже потрапила в базу. Тому програма, що ігнорує код повернення `clock_gettime` як «цей виклик не падає», сама себе позбавляє єдиного сигналу, який отримає в 2038 році.

Окремо — дві стелі, які ставить сам Linux і які **не зникають** із широким `time_t`. Усередині ядра час живе в `ktime_t`, тобто наносекундами в знакових 64 бітах:

```
KTIME_SEC_MAX = (2⁶³ − 1) / 10⁹
              = 9223372036854775807 / 1000000000
              = 9223372036 с            →  2262-04-11 23:47:16 UTC

TIME_UPTIME_SEC_MAX = 30·365·24·3600
                    = 946080000 с       (запас на 30 років роботи)

TIME_SETTOD_SEC_MAX = 9223372036 − 946080000
                    = 8277292036 с      →  2232-04-18 23:47:16 UTC
```

Перше число — межа арифметики `CLOCK_REALTIME`. Друге — межа того, що ядро дозволить **встановити**: `clock_settime` і `settimeofday` відмовляють із `EINVAL` уже за тридцять років до першої стелі, щоб машина, яку ввімкнули на самій межі, могла пропрацювати ці тридцять років і не переповнити внутрішній лічильник посеред роботи.

Різниця між «тип тримає 292 мільярди років» і «ядро дозволить поставити дату до 2232-го» — не педантичність. Це два різні числа для двох різних питань, і плутати їх у своїх перевірках так само шкідливо, як плутати ширину поля з діапазоном значень. Наносекундна шкала [всередині ядра](book:unix-linux/kernel-timekeeping) має власну межу, і ширина `time_t` на неї не впливає взагалі.

## Швидка перевірка чинної системи

```
# чи вміє бібліотека широкий час
getconf GNU_LIBC_VERSION                                    # потрібно ≥ 2.34
nm -D "$(ldd /bin/true | awk '/libc\.so/ {print $3}')" \
    | grep -c __clock_gettime64                             # >0 — символ на місці

# чи знають заголовки ядра номери _time64
grep -rq clock_gettime64 /usr/include/asm/ && echo "заголовки ≥ 5.1"

# чи є ці виклики в самому ядрі
uname -r                                                    # ≥ 5.1, бажано ≥ 5.6
```

Три перевірки навмисно окремі, бо ламаються вони незалежно: бібліотека може вміти широкий час на ядрі, яке ще не вміє, — і навпаки. Перша каже, чи є кому перекладати; друга — чи знає компілятор номери; третя — чи є що викликати.
