# Практичний приклад: v9fs та WSL2 у Windows

Коли Microsoft створювала Windows Subsystem for Linux (WSL2), перед інженерами постала класична проблема інтероперабельності: як дозволити Linux-ядру (яке працює у віртуальній машині Hyper-V) швидко і прозоро читати та писати файли на NTFS-диску хостової операційної системи Windows (наприклад, файли на `C:\`).

І навпаки: як дозволити Провіднику Windows (Windows Explorer) бачити файли, що лежать на віртуальному диску ext4 всередині Linux?

Рішенням став протокол **9P**. 

### Як Windows бачить файли Linux
Коли ви відкриваєте шлях `\\wsl$\Ubuntu\home\user` у Провіднику Windows:
1. Windows запускає вбудований клієнт 9P — драйвер-переспрямовувач `p9rdr.sys`, який і реєструє в системі імена `\\wsl$` та `\\wsl.localhost`.
2. Всередині Linux-віртуальної машини сервер 9P запускає `init` дистрибутива (офіційна документація WSL: «Plan9 is a Linux process that hosts a plan9 filesystem server»).
3. Windows надсилає 9P-повідомлення (`Twalk`, `Tread`) до Linux-сервера **сокетом Hyper-V** (`hvsocket`): у гостьовому Linux це сокет родини `AF_VSOCK`, на боці Windows — `AF_HYPERV`, а їде він поверх шини VMBus. Один канал, три імені — далі звемо його просто сокетом Hyper-V.
4. Linux транслює ці запити до локальної файлової системи ext4 і повертає дані Windows через R-повідомлення.

### Як Linux бачить файли Windows
Коли ви заходите в `/mnt/c/Users` у терміналі WSL:
1. Ядро Linux використовує вбудований драйвер **v9fs** (Plan 9 Resource Sharing Support).
2. На стороні хоста (Windows) сервер 9P піднімає служба `wslservice.exe` — саме вона, за документацією WSL, «starts a plan9 file server», до якого приєднується віртуальна машина, щоб змонтувати диски Windows. (Процес `wslhost.exe` до цього не причетний: він показує сповіщення й тримає фонові Linux-процеси.)
3. Linux монтує диск через `mount -t drvfs C: /mnt/c`; помічник `mount.drvfs` (насправді символьне посилання на `/init`) обирає реалізацію, і за типовою конфігурацією виходить звичайне монтування 9P — `mount` показує його як `type 9p (…aname=drvfs;path=C:\…,trans=fd,rfd=N,wfd=N)`.
4. Всі команди (наприклад, `ls /mnt/c`) Linux-ядро перетворює на повідомлення 9P і пише їх у той самий сокет Hyper-V — це і є `trans=fd`, транспорт «поверх уже відкритого дескриптора» з `Documentation/filesystems/9p.rst` (у v9fs узагалі немає окремого транспорту «vmbus»). Сервер на боці Windows виконує справжні NTFS-виклики.

Вибір 9P замість SMB/CIFS (рідного для Windows протоколу) був зроблений через те, що 9P значно легший, ідеально підходить для віртуалізації (мінімум round-trips для локальних сокетів) та має чудову вбудовану підтримку (v9fs) у ванільному ядрі Linux. Це блискучий приклад того, як технологія 1990-х років вирішила сучасну проблему віртуалізації 2020-х. (Пізніші випуски WSL дають для дисків Windows ще й `virtio-plan9` та `virtiofs` — що саме буде змонтовано, вирішує `.wslconfig`; 9P лишається типовим варіантом.)
