# ⚙️ Власний параметр у /proc/sys: модуль, що заводить свою крутилку

Механізм `/proc/sys` розумієш по-справжньому не тоді, коли крутиш чужі параметри, а тоді, коли заводиш свій — бо з цього боку доводиться самому вирішити, де лежить змінна, хто перевіряє межі й що робити, коли значення прийшло. Нижче — робочий модуль ядра мовою C, який створює каталог `/proc/sys/kernel/knobdemo` із трьома записами: перший — звичайне число з межами, другий після кожного запису перебудовує внутрішній стан модуля, а третій не має за собою змінної взагалі й рахує відповідь у мить читання. Складається все це в сімдесят рядків, збирається поза деревом ядра однією командою — і кожна з чотирьох класичних пасток тут теж видна руками, а не на словах.

## Задача

Уявімо підсистему, яка рахує події по комірках гістограми: щоразу, коли щось стається, вона збільшує один із лічильників. Двоє чисел у ній обирає не автор коду, а той, хто експлуатує машину: як часто знімати відлік і скільки комірок тримати. Обидва треба міняти на живій системі, обидва мусять мати межі, і ще хочеться бачити поточну суму лічильників, не зупиняючи нічого.

Це рівно той випадок, для якого існує `/proc/sys`: числа стосуються підсистеми загалом, а не окремого об'єкта чи процесу, і право їх крутити має той, хто відповідає за машину.

## Задум: три записи, і кожен з іншої причини

**`interval_ms` — просто змінна.** Період між відліками ні на що не впливає, доки хтось його не прочитає. Тому нову величину достатньо покласти в змінну: код, який планує наступний відлік, візьме її сам, коли до неї дійде. Такому запису не потрібен власний код узагалі — вистачає готового обробника `proc_dointvec_minmax`, якому досить сказати, де змінна й у яких межах вона осмислена.

**`slots` — змінна плюс дія.** А от кількість комірок так не працює. Записати `64` в змінну — це ще не мати шістдесяти чотирьох лічильників: масив треба виділити наново. Причому доки нового масиву немає, число `64` — брехня, і коли хтось на нього покладеться, звертання піде за межі старого масиву. Ось тут і потрібен власний обробник: він викликає ту саму стандартну машинерію (розбір тексту, звірка з межами, присвоєння), а потім робить те, чого змінна зробити не вміє.

**`hits` — жодної змінної.** Сума лічильників ніде не зберігається: тримати її окремо означало б підтримувати ще одне число в узгодженому стані. Простіше порахувати її під час читання. Запис у `/proc/sys` для цього й пристосований: за іменем стоїть функція, і ніхто не зобов'язує її брати відповідь із пам'яті.

## Стан модуля

Далі йде повний текст `knobdemo.c`, шматками — у тому самому порядку, у якому вони лежать у файлі.

```c
// knobdemo.c — власний вузол у /proc/sys/kernel/knobdemo
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include <linux/module.h>
#include <linux/sysctl.h>
#include <linux/slab.h>
#include <linux/mutex.h>
#include <linux/rcupdate.h>
#include <linux/workqueue.h>
#include <linux/random.h>
#include <linux/overflow.h>

/* Крутилка 1: період відліку. Звичайна змінна — свого коду не треба. */
static int interval_ms = 200;
static int interval_min = 10;
static int interval_max = 60000;

/* Крутилка 2: скільки комірок. Самого числа замало — треба масив. */
static int slots = 16;
static int slots_min = 1;
static int slots_max = 4096;

/* Скільки разів гістограму перебудовували — видно в журналі ядра. */
static int rebuilds;

/* Довжина живе всередині знімка, а не поруч із ним. */
struct bins {
	struct rcu_head rcu;
	int n;
	atomic_t hit[];
};

static struct bins __rcu *cur_bins;
static DEFINE_MUTEX(bins_lock);		/* серіалізує перебудову */
static struct delayed_work tick_work;

static struct bins *bins_alloc(int n)
{
	struct bins *b = kvzalloc(struct_size(b, hit, n), GFP_KERNEL);

	if (b)
		b->n = n;
	return b;
}
```

Найважливіше рішення прийнято тут, у структурі. Довжина `n` лежить *усередині* тієї самої структури, що й масив, — не окремим глобальним числом поруч. Причина проста: два глобали неможливо змінити одним рухом, а от підмінити один вказівник — можна.

`extra1` і `extra2` в описі параметра — вказівники, тому межі мусять бути змінними, а не сталими в тексті програми. Для найчастіших випадків ядро тримає готові спільні сталі — `SYSCTL_ZERO`, `SYSCTL_ONE`, `SYSCTL_INT_MAX` та кілька сусідніх, — щоб кожен модуль не заводив власну нульову змінну.

## Відлік — той, хто читає обидва числа

```c
static void tick_fn(struct work_struct *w)
{
	struct bins *b;

	rcu_read_lock();
	b = rcu_dereference(cur_bins);
	atomic_inc(&b->hit[get_random_u32() % b->n]);
	rcu_read_unlock();

	schedule_delayed_work(&tick_work,
			      msecs_to_jiffies(READ_ONCE(interval_ms)));
}
```

Це той код, задля якого крутилки взагалі існують, — і одразу видно, як він поводиться з кожною з них. Довжину `b->n` і масив `b->hit` він бере з одного знімка, тож вони не можуть розійтися, навіть якщо перебудова станеться просто зараз: старий знімок лишиться цілим доти, доки цей `rcu_read_lock()` не закриється. Механіка «читати без замків, а звільняти відкладено» — окрема тема: [RCU: читання без замків і відкладене звільнення](book:unix-linux/rcu-mechanism), тут досить знати, що всередині такої дужки знімок, який ви взяли, ніхто не звільнить.

`interval_ms` він читає інакше — через `READ_ONCE`, бо це просте число, яке в цю ж мить може міняти чужий процес. Пара `READ_ONCE`/`WRITE_ONCE` не робить читання узгодженим із чимось іще; вона лише забороняє компіляторові розкласти доступ на кілька звертань і тим самим показати вам напів-старе-напів-нове значення. Присвоєння з боку sysctl теж робиться через `WRITE_ONCE` — стандартні обробники цілих чисел саме так і пишуть у змінну.

І ще одне видно просто з форми запису: нове значення `interval_ms` подіє лише на *наступному* відліку, бо поточне очікування вже заплановане зі старим числом. Це не хиба, а межа того, що вміє «просто змінна».

Планувати роботу з відкладенням тут можна, бо `tick_fn` виконується в робочій черзі, тобто в контексті, де дозволено спати; звідки такий контекст береться — [Переривання, softirq і робочі черги](book:unix-linux/interrupts-bottom-halves).

## Обробник, що робить більше, ніж присвоєння

```c
static int slots_handler(const struct ctl_table *table, int write,
			 void *buffer, size_t *lenp, loff_t *ppos)
{
	struct bins *old, *new;
	int prev, ret;

	mutex_lock(&bins_lock);

	prev = slots;
	ret = proc_dointvec_minmax(table, write, buffer, lenp, ppos);
	if (ret || !write || slots == prev)
		goto out;			/* читання або те саме число */

	new = bins_alloc(slots);
	if (!new) {
		WRITE_ONCE(slots, prev);	/* не показувати того, чого не зробили */
		ret = -ENOMEM;
		goto out;
	}

	old = rcu_dereference_protected(cur_bins, lockdep_is_held(&bins_lock));
	rcu_assign_pointer(cur_bins, new);
	WRITE_ONCE(rebuilds, rebuilds + 1);
	kvfree_rcu(old, rcu);

	pr_info("slots %d -> %d (rebuild %d)\n", prev, new->n, rebuilds);
out:
	mutex_unlock(&bins_lock);
	return ret;
}
```

Обробник не робить розбору тексту сам: перший же рядок передає роботу `proc_dointvec_minmax`, який прочитає число, звірить його з `extra1`…`extra2` і, якщо все гаразд, покладе в `slots`. Цей прийом — «викликати стандартний обробник, а тоді дописати своє» — і є звичайним способом заводити побічну дію; писати розбір тексту вручну немає ані потреби, ані сенсу.

Далі три дрібниці, кожна з яких у чужому коді зазвичай відсутня.

По-перше, `if (ret || !write ...)`. Обробника кличуть і на читання теж — той самий обробник, тим самим викликом, лише з `write == 0`. Код, який цього не перевіряє, перебудовує гістограму щоразу, коли хтось зробив `cat`.

По-друге, `slots == prev`. Записати те саме число — законна дія, яку роблять постійно: файли `sysctl.d` програють при кожному завантаженні, а служби переписують свої значення «про всяк випадок». Перебудовувати стан на такий запис означає влаштувати собі сплеск роботи на рівному місці.

По-третє, `WRITE_ONCE(slots, prev)` на невдачі. На момент, коли ми дізналися, що пам'яті немає, `proc_dointvec_minmax` уже записав нове число в змінну. Якщо його там лишити, `write` поверне помилку, а наступне читання `slots` покаже значення, якого насправді не сталося, — параметр почне брехати. Порядок «спершу присвоїли, потім спробували виконати» тут неминучий, тож відкат — обов'язок обробника.

Підміна знімка — три рядки: узяти старий вказівник (під замком, тому `rcu_dereference_protected`), поставити новий і віддати старий на відкладене звільнення. Читач, що зараз усередині `rcu_read_lock()`, добігає зі старим масивом до кінця, і лише потім той звільниться.

![Ліворуч — довжина й масив окремими глобалями, читач бере нову довжину зі старим масивом; праворуч — знімок, у якому обоє їдуть разом](/reference/unix-linux/foundations/sysctl-tunables/img/snapshot-swap.svg)

*Крутилка змінює одне число за раз, тож узгодженість двох пов'язаних величин мусить забезпечити структура, а не порядок записів.*

> 🔧 **Навіщо це.** Питання «змінна чи обробник» вирішується не смаком, а одним критерієм: чи існує проміжок часу, у якому нове значення вже видно, а поведінка ще стара, і чи шкідливий цей проміжок. Для періоду відліку він нешкідливий — максимум одне запізніле спрацювання. Для довжини масиву він смертельний, бо в ньому число описує те, чого немає. Саме тому в ядрі трапляються параметри без побічної дії, з побічною дією й навіть без змінної — форма щоразу випливає з того, наскільки далеко значення розходиться з реальністю.

## Обробник, що рахує відповідь на місці

```c
static int hits_handler(const struct ctl_table *table, int write,
			void *buffer, size_t *lenp, loff_t *ppos)
{
	struct ctl_table tmp = *table;
	struct bins *b;
	int sum = 0, i;

	if (write)
		return -EACCES;

	rcu_read_lock();
	b = rcu_dereference(cur_bins);
	for (i = 0; i < b->n; i++)
		sum += atomic_read(&b->hit[i]);
	rcu_read_unlock();

	tmp.data = &sum;
	return proc_dointvec(&tmp, 0, buffer, lenp, ppos);
}
```

Тут видно, що опис параметра — не постійна прив'язка імені до адреси, а просто аргумент виклику. Ми копіюємо опис у локальну змінну, наводимо його `data` на щойно обчислене число й віддаємо стандартному обробникові форматувати. Цей прийом уживають скрізь у ядрі, де значення треба перерахувати або перевести в інші одиниці перед показом.

Наслідок для того, хто читає: `cat` цього запису — не копіювання пам'яті, а виконання циклу по всіх комірках просто зараз. Два послідовні читання дадуть різні числа, і жодного кешування між ними немає — значення не «оновлюється», воно щоразу народжується заново.

## Опис і реєстрація

```c
static struct ctl_table knobdemo_table[] = {
	{
		.procname	= "interval_ms",
		.data		= &interval_ms,
		.maxlen		= sizeof(int),
		.mode		= 0644,
		.proc_handler	= proc_dointvec_minmax,
		.extra1		= &interval_min,
		.extra2		= &interval_max,
	},
	{
		.procname	= "slots",
		.data		= &slots,
		.maxlen		= sizeof(int),
		.mode		= 0644,
		.proc_handler	= slots_handler,
		.extra1		= &slots_min,
		.extra2		= &slots_max,
	},
	{
		.procname	= "hits",
		.maxlen		= sizeof(int),
		.mode		= 0444,
		.proc_handler	= hits_handler,
	},
};

static struct ctl_table_header *knobdemo_hdr;

static int __init knobdemo_init(void)
{
	struct bins *b = bins_alloc(slots);

	if (!b)
		return -ENOMEM;
	rcu_assign_pointer(cur_bins, b);

	knobdemo_hdr = register_sysctl("kernel/knobdemo", knobdemo_table);
	if (!knobdemo_hdr) {
		kvfree(b);
		return -ENOMEM;
	}

	INIT_DELAYED_WORK(&tick_work, tick_fn);
	schedule_delayed_work(&tick_work, msecs_to_jiffies(interval_ms));
	return 0;
}

static void __exit knobdemo_exit(void)
{
	unregister_sysctl_table(knobdemo_hdr);	/* чекає на обробники в роботі */
	cancel_delayed_work_sync(&tick_work);	/* і на відлік у роботі теж */
	kvfree(rcu_dereference_protected(cur_bins, true));
}

module_init(knobdemo_init);
module_exit(knobdemo_exit);
MODULE_DESCRIPTION("Демонстраційні параметри в /proc/sys/kernel/knobdemo");
MODULE_LICENSE("GPL");
```

Кілька речей у цьому шматку варті окремого погляду.

Шлях у `register_sysctl` — це шлях *каталогу*, без ведучої скісної риски й без імен самих параметрів: імена беруться з `procname` кожного елемента. Проміжні каталоги ядро створить само, тож `kernel/knobdemo` з'явиться цілком.

У запису `hits` немає `data` — і це нормально, бо його обробник підставляє власне. Але `maxlen` там потрібен: стандартний обробник за ним вирішує, скільки чисел форматувати.

`mode` — звичайні [біти прав](book:unix-linux/permission-bits), які перевіряє ядро *до* виклику обробника. Для `hits` виставлено `0444`, тому спроба запису обірветься ще на перевірці прав; перевірка `if (write)` всередині обробника — страховка на випадок, коли хтось згодом послабить `mode` й забуде, що обробник до запису не готовий.

Порядок у вивантаженні не випадковий. `unregister_sysctl_table()` не просто прибирає імена з дерева: якщо якийсь обробник саме зараз працює, вона чекає, доки він повернеться, і лише тоді знімає запис. Тому після її повернення жоден обробник не виконується й жоден не почнеться. Далі `cancel_delayed_work_sync()` так само дочекається відліку, що вже почався, і не дасть йому перепланувати себе ще раз. І тільки коли обидві дороги до `cur_bins` закриті, знімок можна звільнити напряму — читачів більше не існує.

## Збірка

Модуль збирається поза деревом ядра, проти заголовків уже зібраного ядра — потрібен пакунок із заголовками для вашої поточної версії (`linux-headers-$(uname -r)` у похідних Debian, `kernel-devel` у похідних Fedora).

```makefile
obj-m := knobdemo.o
KDIR  ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
```

Дві крапки, на яких спотикаються. Відступи в `Makefile` мусять бути табуляціями, а не пробілами. І модуль зі своїм `MODULE_LICENSE("GPL")` збереться проти будь-якого ядра, але завантажиться лише в те, для якого зібраний: [модуль звіряє версію та контрольну суму інтерфейсів](book:unix-linux/kernel-modules), і невідповідність дає `Invalid module format`.

## Сеанс

```
$ sudo insmod knobdemo.ko
$ ls /proc/sys/kernel/knobdemo/
hits  interval_ms  slots

$ ls -l /proc/sys/kernel/knobdemo/hits
-r--r--r-- 1 root root 0 сер  7 14:02 /proc/sys/kernel/knobdemo/hits

$ cat /proc/sys/kernel/knobdemo/interval_ms
200
$ cat /proc/sys/kernel/knobdemo/hits
41
$ sleep 2; cat /proc/sys/kernel/knobdemo/hits
51
```

Розмір `hits` — нуль, бо тексту, поки його не попросили, не існує. Два читання з проміжком у дві секунди відрізняються рівно на десять — стільки відліків уміщається у дві секунди при періоді 200 мс.

```
$ echo 5 | sudo tee /proc/sys/kernel/knobdemo/interval_ms
5
tee: /proc/sys/kernel/knobdemo/interval_ms: Invalid argument
$ cat /proc/sys/kernel/knobdemo/interval_ms
200
```

П'ять мілісекунд менші за оголошений мінімум, тому `proc_dointvec_minmax` не підганяє значення до межі, а відхиляє запис із `EINVAL` — і змінна лишається старою. Число `5`, яке надрукував `tee`, — це його власне відлуння на стандартний вивід, а не відповідь ядра.

```
$ sudo sysctl -w kernel.knobdemo.slots=64
kernel.knobdemo.slots = 64
$ sudo dmesg | tail -1
[  412.883014] knobdemo: slots 16 -> 64 (rebuild 1)
$ cat /proc/sys/kernel/knobdemo/hits
2
```

Побічна дія спрацювала: у журналі ядра є запис, а `hits` показує двійку — новий масив виділено чистим, і в ньому встигло накопичитися лише два відліки. Втрата попередніх лічильників тут навмисна, але це якраз те місце, де в справжній підсистемі довелося б вирішувати, чи переносити старі значення в новий масив.

```
$ sudo sysctl -w kernel.knobdemo.slots=0
sysctl: setting key "kernel.knobdemo.slots": Invalid argument

$ sudo rmmod knobdemo
$ cat /proc/sys/kernel/knobdemo/hits
cat: /proc/sys/kernel/knobdemo/hits: No such file or directory
```

## Пастки

**Опис не копіюють — на нього посилаються.** `register_sysctl` запам'ятовує вказівник на ваш масив, а не його вміст. Отже, масив мусить пережити реєстрацію: файловий `static` — годиться, локальна змінна функції — гарантований крах, позначка `__initdata` — теж крах, бо таку пам'ять звільняють після завантаження. Те саме стосується всього, на що масив показує: `data`, `extra1`, `extra2` мусять лишатися чинними доти, доки запис висить у дереві. Це, до речі, і причина, чому межі доводиться заводити окремими змінними.

**Забутий `unregister` — не витік, а вибух.** Реєстрація не бере посилання на модуль: ніщо не заважає вивантажити його з активним записом у `/proc/sys`. Пам'ять модуля звільниться, а `proc_handler` у дереві й далі показуватиме на місце, де колись був ваш код. Наступний `cat` цим шляхом виконає те, що там опинилося, — і це буде [Oops](book:unix-linux/kernel-oops-panic) не в момент вивантаження, а через довільний час, у зовсім іншій програмі. Сюди ж належить і напівініціалізований модуль: якщо `register_sysctl` повернув `NULL`, а ви це проґавили й повернули нуль, модуль завантажиться без жодного свого параметра. Падіння не буде — `unregister_sysctl_table(NULL)` мовчки повернеться, — і саме тому поломку помічають не одразу, а тоді, коли хтось не знаходить свого каталогу в `/proc/sys`.

**Обробник — не одинак.** Ядро не серіалізує звертання до одного запису: два процеси можуть виконувати ваш обробник одночасно на різних ядрах, а третій у цю ж мить читати змінну зі свого коду. Стандартні обробники цілих чисел рятують лише від найгрубішого — присвоєння вони роблять через `WRITE_ONCE`, тож напів-старого-напів-нового числа ви не побачите ніколи. Усе інше — ваше: якщо запис тягне за собою більше, ніж присвоєння одного числа, потрібен власний замок, а якщо стан читає гарячий шлях, який замка собі дозволити не може, — знімок під RCU, як тут. Обирати замок під контекст — окрема наука: [Замки в ядрі й атомарний контекст: де спати не можна](book:unix-linux/kernel-locking).

**Довго спати в обробнику не можна — і причина не та, що зазвичай думають.** Спати там *дозволено*: обробник виконується в контексті процесу, що зробив `write`, і навіть буфер для нього ядро виділяє з `GFP_KERNEL`. Заборонена саме тривалість, і одразу з трьох причин. Поки обробник не повернувся, запис у дереві вважається вживаним, а `unregister_sysctl_table()` чекає — тобто обробник, який стукає в пристрій із таймаутом на десять секунд, перетворює `rmmod` на десятисекундне зависання, і це в кращому разі. Далі, при старті системи файли `sysctl.d` програються один за одним, послідовно: сотня записів по пів секунди — це хвилина завантаження, витрачена в нікуди. І нарешті, той, хто написав `sysctl -w`, чекає на повернення `write` і має всі підстави вважати цю дію миттєвою. Правило звідси просте: у обробнику — присвоєння й коротка перебудова, усе довге — запланувати роботу й повернутися.

**Ім'я — це вже обіцянка.** Каталог `kernel/knobdemo` у прикладі взято заради впізнаваності; справжній модуль не селиться в `kernel/`, бо це простір імен самого ядра. Але важливіше інше: щойно ім'я з'явилося, на нього почнуть посилатися чужі файли налаштувань і чужі скрипти, і перейменування зламає їх усі. Наскільки жорстко ядро тримається за такі обіцянки й де межа — [«Не ламати простір користувача»](book:unix-linux/kernel-abi-stability).

## Що змінити для іншої версії ядра

Внутрішні інтерфейси ядра нікому нічого не обіцяють, і саме цей за останні роки міняли кілька разів — тож приклади з мережі часто не збираються. Точні межі такі:

```
6.14  register_sysctl_sz() бере таблицю як const — масив можна
      оголосити static const, і він ляже в .rodata
6.11  обробник дістає const struct ctl_table * — до цієї версії
      аргумент був без const, і код вище не збереться
 6.6  з'явився register_sysctl_sz(), а register_sysctl() став
      макросом із ARRAY_SIZE; завершальний порожній елемент масиву
      більше не потрібен — до 6.6 він обов'язковий
 6.5  прибрано register_sysctl_table() і поле child: старі приклади
      з вкладеними таблицями не збираються взагалі
 5.8  buffer став вказівником на пам'ять ядра (void *); раніше був
      void __user * і обробник копіював дані сам
```

Код вище написано під 6.11 і новіші. Щоб зібрати його для 6.6…6.10, досить прибрати `const` в оголошеннях обох обробників — усе решта лишається як є.
