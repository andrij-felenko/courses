# 📋 Поверхня taint: біти, файли, параметри

Це довідка про механізм плям з боку інтерфейсу: повний перелік бітів маски `tainted_mask` — номер, літера, десяткове значення, константа й подія, що біт ставить, — а далі всі місця, звідки цю маску читають, і два важелі, якими на неї впливають. Потрібна вона тоді, коли перед очима чуже число або чужий заголовок аварії: щоб прочитати `Tainted: P        W  OE`, треба знати позиції, а щоб перетворити `12801` на слова — числа.

Усе нижче звірено з `Documentation/admin-guide/tainted-kernels.rst`, `kernel/panic.c` і `kernel/module/main.c` чинного дерева ядра. Бітів рівно двадцять (`TAINT_FLAGS_COUNT`), маска живе в одному `unsigned long`, найбільше можливе значення — `TAINT_FLAGS_MAX = (1UL << 20) - 1 = 1048575`.

## Усі двадцять бітів

| Біт | Літера | Десяткове | Константа `TAINT_*` | Подія, що ставить біт |
|---:|:---:|---:|---|---|
| 0 | `P` (чисто — `G`) | 1 | `PROPRIETARY_MODULE` | завантажено модуль із ліцензією, несумісною з GPL |
| 1 | `F` | 2 | `FORCED_MODULE` | модуль завантажено силою (`insmod --force`) |
| 2 | `S` | 4 | `CPU_OUT_OF_SPEC` | процесор або система працюють поза специфікацією |
| 3 | `R` | 8 | `FORCED_RMMOD` | модуль вивантажено силою (`rmmod -f`) |
| 4 | `M` | 16 | `MACHINE_CHECK` | процесор повідомив про апаратну помилку машинною перевіркою |
| 5 | `B` | 32 | `BAD_PAGE` | звернення до зіпсованої сторінки або несподівані прапорці сторінки |
| 6 | `U` | 64 | `USER` | пляму замовив простір користувача записом у sysctl |
| 7 | `D` | 128 | `DIE` | ядро вже вмирало: стався oops або спрацював `BUG()` |
| 8 | `A` | 256 | `OVERRIDDEN_ACPI_TABLE` | таблицю ACPI підмінено користувачем |
| 9 | `W` | 512 | `WARN` | спрацював `WARN()` |
| 10 | `C` | 1024 | `CRAP` | завантажено драйвер із `drivers/staging` |
| 11 | `I` | 2048 | `FIRMWARE_WORKAROUND` | застосовано обхід відомої вади прошивки платформи |
| 12 | `O` | 4096 | `OOT_MODULE` | завантажено модуль, зібраний поза деревом ядра |
| 13 | `E` | 8192 | `UNSIGNED_MODULE` | завантажено модуль без дійсного підпису |
| 14 | `L` | 16384 | `SOFTLOCKUP` | зафіксовано мʼяке зависання процесора чи задачі |
| 15 | `K` | 32768 | `LIVEPATCH` | застосовано живу латку |
| 16 | `X` | 65536 | `AUX` | допоміжна пляма, зміст якої визначає дистрибутив |
| 17 | `T` | 131072 | `RANDSTRUCT` | ядро зібрано з перемішуванням полів структур |
| 18 | `N` | 262144 | `TEST` | завантажено тестовий модуль або запущено тест усередині ядра |
| 19 | `J` | 524288 | `FWCTL` | простір користувача виконав змінювальну налагоджувальну операцію через `fwctl` |

Чотири зауваги до таблиці, без яких вона читається неправильно.

**Порожній стан — пробіл, і лише в біта 0 — літера.** Пара `G`/`P` дісталася від найпершого прапорця, коли ядро хотіло видимо казати «усе тут вільне». Решта дев'ятнадцять позицій у чистому стані просто порожні.

**Біт `T` ставить не подія, а збірка.** Маска ініціалізується ще до першого рядка журналу:

```c
static unsigned long tainted_mask =
	IS_ENABLED(CONFIG_RANDSTRUCT) ? (1 << TAINT_RANDSTRUCT) : 0;
```

Тож на ядрі з перемішуванням структур `/proc/sys/kernel/tainted` ніколи не поверне нуль, і це нормально.

**Двадцятий біт молодий.** `J` зʼявився в 6.15 разом із підсистемою `fwctl`; на старіших ядрах бітів дев'ятнадцять, і `TAINT_FLAGS_MAX` там менший. Число з чужої машини завжди читайте таблицею її версії.

**Сім бітів мають персонального носія.** `P`, `F`, `C`, `O`, `E`, `K`, `N` ставлять через `add_taint_module()`, тож вони лягають не лише в спільну маску, а й у поле `taints` конкретного модуля. Решта — суто глобальні: за ними видно, що сталося, але не видно хто.

## Читати маску: `/proc/sys/kernel/tainted`

Звичайний [параметр sysctl](book:unix-linux/sysctl-tunables) з режимом `0644`, який віддає ту саму маску десятковим числом одним рядком:

```
$ cat /proc/sys/kernel/tainted
12801
```

Запис у цей файл поводиться не так, як очікує рука, звикла до `/proc`. Обробник `proc_taint()` бере записане число й **домішує** його біти до наявних:

```c
if (write && !capable(CAP_SYS_ADMIN))
	return -EPERM;
...
for (i = 0; i < TAINT_FLAGS_COUNT; i++)
	if ((1UL << i) & tmptaint)
		add_taint(i, LOCKDEP_STILL_OK);
```

Звідси три наслідки. Записане число не замінює маску, а лише додає біти — `echo 0 > /proc/sys/kernel/tainted` виконається без помилки й не змінить нічого. Записати можна будь-який із двадцяти бітів, а не тільки `U`, хоч за домовленістю простір користувача ставить саме його. І потрібне [право `CAP_SYS_ADMIN`](book:unix-linux/capabilities), яке перевіряється у початковому просторі імен користувачів: root усередині контейнера з власним user namespace дістане `EPERM`.

> 🔧 **Навіщо це.** Односторонність тут не примха, а те, що робить маску придатною для доказу. Якби біт можна було зняти записом у файл, будь-який звіт про аварію із заплямованого ядра можна було б «почистити» одним рядком перед надсиланням — і жоден розробник не мав би підстав вірити рядку `Not tainted`.

## Розкласти число словами: `kernel-chktaint`

Службовий сценарій лежить у дереві ядра як `tools/debugging/kernel-chktaint` і приїздить у пакетах `linux-tools` чи `kernel-tools`. Без аргументів він читає `/proc/sys/kernel/tainted` цієї машини, з аргументом — розкладає будь-яке число, зокрема привезене з чужого вузла:

```
$ sh kernel-chktaint 12801
Kernel is "tainted" for the following reasons:
 * proprietary module was loaded (#0)
 * kernel issued warning (#9)
 * externally-built ('out-of-tree') module was loaded  (#12)
 * unsigned module was loaded (#13)
```

На чистому ядрі він друкує `Kernel not Tainted`.

## Хто приніс пляму: `/sys/module/` і `/proc/modules`

Персональна маска модуля видна двома шляхами. Перший — файл у [дереві пристроїв sysfs](book:unix-linux/sysfs-device-model), режим `0444`: суцільний рядок літер без роздільників і переведення рядка наприкінці. Файл є лише в справді завантажених модулів; у вбудованих у ядро теки `/sys/module/<name>/` є, а файла `taint` у них немає.

```
$ cat /sys/module/nvidia/taint
POE
```

Другий — останнє поле рядка в `/proc/modules`, ті самі літери в дужках:

```
$ grep ^nvidia /proc/modules
nvidia 62365696 76 nvidia_uvm,nvidia_modeset, Live 0x0000000000000000 (POE)
```

Звична `lsmod` із пакета `kmod` цього поля не показує: вона друкує рівно три колонки (`Module`, `Size`, `Used by`) і решту рядка відкидає. Тож літери шукайте в `/proc/modules` або обійдіть sysfs:

```sh
for f in /sys/module/*/taint; do
	t=$(cat "$f") || continue
	[ -n "$t" ] && printf '%-24s %s\n' "$(basename "$(dirname "$f")")" "$t"
done
```

## Рядок у заголовку аварії

Маску в [звіті про oops](book:unix-linux/kernel-oops-panic) друкує `print_tainted()` — той самий `%s` у форматі заголовка:

```c
"%sCPU: %d UID: %u PID: %d Comm: %.20s %s%s %s %.*s %s " BUILD_ID_FMT "\n"
```

Якщо маска нульова, функція повертає `Not tainted`. Інакше — `Tainted: ` і **рівно двадцять символів**: цикл проходить усі біти по порядку й для кожного друкує або його літеру, або порожній стан.

![Двадцять клітинок поля Tainted: позиція відповідає номеру біта, порожня позиція друкується пробілом](/reference/unix-linux/foundations/kernel-taint/img/taint-header-positions.svg)

*Групи пробілів усередині рядка — не збите форматування, а порожні позиції; тому літери завжди стоять на своїх місцях, а рядок має сталу довжину, включно з пробілами наприкінці.*

Новіші ядра поруч друкують ще й розшифровку виду `[P]=PROPRIETARY_MODULE, [W]=WARN` — назви беруться з поля `desc`, яке макрос `TAINT_FLAG` робить прямо з імені константи.

## Зупинити машину на плямі: `panic_on_taint`

[Завантажувальний параметр](book:unix-linux/bootloader-and-cmdline) перетворює появу вказаних бітів на негайну паніку:

```
panic_on_taint=<шістнадцяткова маска>[,nousertaint]
```

Розбирається він рано (`early_param`), тож діє від початку завантаження. Число читається за основою 16 — з префіксом `0x` чи без; зайві біти відтинаються (`panic_on_taint &= TAINT_FLAGS_MAX`), нульова маска вважається помилкою запису. Перевірка стоїть усередині `add_taint()` одразу після `set_bit()`, а перед самою панікою маска обнуляється — пастка одноразова й не спрацьовує рекурсивно на плямах самої паніки. Модифікатор `nousertaint` закриває шлях через sysctl: запис числа, що перетинається з маскою, повертає `EINVAL` замість того, щоб покласти машину. При завантаженні ядро підтверджує налаштування рядком `panic_on_taint: bitmask=0x30 nousertaint_mode=enabled`.

**Умова:** зупинити вузол у мить, коли зʼявиться зіпсована сторінка (`B`) або машинна перевірка (`M`), і не дати нікому відтворити це записом у `/proc`.

```
біт 4 (M) → 2⁴ = 16 = 0x10
біт 5 (B) → 2⁵ = 32 = 0x20
маска     = 0x10 | 0x20 = 0x30

panic_on_taint=0x30,nousertaint
```

Дамп, який після цього зніме [kdump](book:unix-linux/kexec-and-kdump), містить причину, а не наслідок, що виплив за півгодини.

## Ставити пляму зсередини: `add_taint()`

```c
void add_taint(unsigned flag, enum lockdep_ok lockdep_ok);
int  test_taint(unsigned flag);   /* 1, якщо біт стоїть */
unsigned long get_taint(void);    /* уся маска */
```

`flag` — це **номер біта** (`TAINT_WARN`, `TAINT_OOT_MODULE`, …), а не десяткове значення з таблиці; сплутати легко, бо обидва — цілі числа.

Другий аргумент — перелічення з двох значень, і воно каже про долю [перевірки порядку взяття замків](book:unix-linux/kernel-locking):

- `LOCKDEP_STILL_OK` — подія не руйнує припущень lockdep, перевірка працює далі;
- `LOCKDEP_NOW_UNRELIABLE` — руйнує, і lockdep вимикається до перезавантаження з рядком `Disabling lock debugging due to kernel taint`.

Вибір видно на прикладах із дерева. Завантаження силою (`try_to_force_load()`) і несумісна ліцензія дають `LOCKDEP_NOW_UNRELIABLE`: у ядрі опинився код, чиї замки перевірці невідомі. Зовнішня збірка (`O`) дає `LOCKDEP_STILL_OK` — походження модуля само по собі порядку замків не міняє.

`add_taint()` експортовано (`EXPORT_SYMBOL`), тож нею користуються й модулі; парної функції, що біт знімає, у ядрі немає взагалі. Модулям же відповідає внутрішня `add_taint_module(mod, flag, lockdep_ok)`: вона ставить біт і в спільній масці, і в `mod->taints` — саме звідти беруться літери в sysfs та `/proc/modules`.
