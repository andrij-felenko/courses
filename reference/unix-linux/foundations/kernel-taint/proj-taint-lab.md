# ⚙️ Лабораторія плям: шість бітів за один сеанс у віртуальній машині

Прапорці taint легко прочитати в чужому звіті — і саме тому вони довго лишаються абстракцією: літери, які хтось колись поставив за нез'ясованих обставин. Найкоротший шлях зробити їх відчутними — поставити їх власною рукою: зібрати модуль на два десятки рядків і по черзі витягти з нього `O`, `E`, `P`, `N`, `W`, а тоді дописати `U` звичайним записом числа у файл.

## Задача і чому тільки віртуальна машина

Пройти шлях від `Not tainted` до маски з шести бітів, щоразу знаючи, який саме рядок її змінив, і на кожному кроці подивитися на неї трьома способами: числом у `/proc`, літерами модуля в `/sys` і реакцією на `panic_on_taint`.

Усе це робиться **тільки** в одноразовій віртуальній машині зі знімком стану, і не з обережності заради обережності. По-перше, маска не знімається: заплямувавши робочу машину, ви лишите цей слід у кожному наступному звіті аж до перезавантаження. По-друге, останній крок навмисно спричиняє паніку — машина зупиниться посеред роботи. По-третє, `insmod` — це виконання довільного коду в найпривілейованішому режимі процесора, і помилка в модулі не «падає», а руйнує систему.

Знадобиться Linux зі встановленими заголовками поточного ядра (пакет `linux-headers-$(uname -r)` у деб-системах, `kernel-devel` у рпм-системах), компілятор і вимкнений [Secure Boot](book:unix-linux/secure-boot) — при ввімкненому ядро переходить у режим примусу підписів, і непідписаний модуль не завантажиться взагалі, замість того щоб дати біт `E`.

## Нульова точка

```sh
cat /proc/sys/kernel/tainted     # 0 — інакше починати нема сенсу
dmesg | grep -i taint            # порожньо
uname -r
```

Нуль тут не формальність. Готові образи часто вже мають щось у масці: гостьові доповнення гіпервізора дадуть `O E` ще до вашого втручання, обхід вади прошивки — `I`. Якщо число ненульове, розкладіть його сценарієм `tools/debugging/kernel-chktaint` (у дистрибутивах він їде в пакеті `linux-tools` або `kernel-tools`) і візьміть чистіший образ — інакше всі подальші числа не зійдуться.

## Піддослідний

Ідея конструкції проста: один файл, у якому кожна пляма вмикається окремо — ключем збірки або параметром завантаження. Так між двома сусідніми вимірами міняється рівно одна річ, і біт, що з'явився, ні з чим не сплутаєш. Тут це важить більше, ніж здається: маска накопичувальна, і якби модулів було кілька й вони різнилися одразу кількома властивостями, приріст числа довелося б угадувати.

Обв'язка збірки модуля поза деревом ядра — `obj-m`, `M=`, заголовки, `insmod`/`rmmod` — розібрана в [окремій вправі](book:unix-linux/monolithic-with-modules/proj-hello-module.md); тут лишається тільки те, що стосується плям.

```c
/* taintlab.c — піддослідний модуль: кожна пляма вмикається окремо */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include <linux/init.h>
#include <linux/module.h>
#include <linux/panic.h>	/* add_taint(), TAINT_*; у старих ядрах — linux/kernel.h */
#ifdef LAB_GPL_SYMBOL
#include <linux/rcupdate.h>	/* synchronize_rcu() експортовано лише для GPL */
#endif

static int step;
module_param(step, int, 0444);
MODULE_PARM_DESC(step, "2 — WARN_ON(), 3 — add_taint(TAINT_USER), 9 — відмовити в init");

static int __init taintlab_init(void)
{
	pr_info("завантажуюся, step=%d\n", step);

	if (step == 2)
		WARN_ON_ONCE(1);				/* біт W */
	if (step == 3)
		add_taint(TAINT_USER, LOCKDEP_STILL_OK);	/* біт U */
	if (step == 9)
		return -EINVAL;					/* init провалився */

#ifdef LAB_GPL_SYMBOL
	synchronize_rcu();
#endif
	return 0;
}

static void __exit taintlab_exit(void)
{
	pr_info("вивантажуюся\n");
}

module_init(taintlab_init);
module_exit(taintlab_exit);

#ifdef LAB_PROPRIETARY
MODULE_LICENSE("Proprietary");
#else
MODULE_LICENSE("GPL");
#endif
#ifdef LAB_TEST
MODULE_INFO(test, "Y");		/* біт N; працює на ядрах від 6.0 */
#endif
MODULE_DESCRIPTION("Піддослідний модуль для спостереження за плямами");
```

```make
# Makefile
obj-m += taintlab.o
ccflags-y += $(LAB)

KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules
clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
```

Ключі передаються в командному рядку (`make LAB=-DLAB_PROPRIETARY`) і самі доходять до вкладеного `make`: змінні, задані в командному рядку, успадковуються вкладеними викликами.

Ще до першого `insmod` варто переконатися, що `add_taint()` узагалі доступний модулям вашого ядра, — і заразом побачити, чим GPL-only символ відрізняється від звичайного:

```sh
grep -wE 'add_taint|synchronize_rcu' /lib/modules/$(uname -r)/build/Module.symvers
# 0x00000000	add_taint	vmlinux	EXPORT_SYMBOL
# 0x00000000	synchronize_rcu	vmlinux	EXPORT_SYMBOL_GPL
```

`add_taint` експортовано звичайним `EXPORT_SYMBOL`, без обмеження на GPL, — тобто поставити будь-який біт може навіть пропрієтарний модуль. Якщо рядка немає взагалі, ваше ядро зібране без цього експорту, і крок із `TAINT_USER` доведеться замінити записом у sysctl.

## Сходинки

**`O` і `E` — походження й перевірка.**

```sh
make && sudo insmod taintlab.ko
cat /proc/sys/kernel/tainted        # 12288
dmesg | tail -3
```

```
taintlab: loading out-of-tree module taints kernel.
taintlab: module verification failed: signature and/or required key missing - tainting kernel
```

12288 = 4096 + 8192. Ліцензія бездоганно GPL, код ваш власний — а плям уже дві, і жодна з них не про якість коду. `O` каже лише те, що модуль зібрано не в дереві ядра, `E` — що [підпису](book:unix-linux/module-signing) ніхто не перевіряв. Бачите тільки 4096 — ваше ядро зібране без `CONFIG_MODULE_SIG`; `insmod` відмовив із «Key was rejected by service» — примус підписів усе-таки ввімкнено, перевірте `/sys/module/module/parameters/sig_enforce`.

**`P` — ліцензія.** Перезавантажте машину (маска інакше не очиститься) і зберіть той самий код з іншим рядком ліцензії:

```sh
make clean && make LAB=-DLAB_PROPRIETARY
sudo insmod taintlab.ko
cat /proc/sys/kernel/tainted        # 12289
dmesg | grep license
# taintlab: module license 'Proprietary' taints kernel.
```

Змінився один рядок метаданих — і `P` став поруч із `O E`. Ядро не дивилося в код: воно звірило рядок зі списком сумісних із GPL і не знайшло збігу. Друга половина цієї плями видно в збірці — додайте до неї виклик `synchronize_rcu()`:

```sh
make clean && make LAB="-DLAB_PROPRIETARY -DLAB_GPL_SYMBOL"
# ERROR: modpost: GPL-incompatible module taintlab.ko uses GPL-only symbol 'synchronize_rcu'
```

Файла `.ko` не буде взагалі: відмова настає ще на `modpost`, до будь-якої спроби завантаження. Зберіть те саме без `-DLAB_PROPRIETARY` — і збірка мовчки пройде. Той самий код, та сама машина; уся різниця — рядок у `MODULE_LICENSE`.

**`N` — тестовий модуль.** Після перезавантаження: `make clean && make LAB=-DLAB_TEST`, далі `insmod` — і маска стане 274432, тобто 12288 + 262144. Один рядок метаданих, знову без жодного стосунку до того, що модуль робить. Біт `N` з'явився в ядрі 6.0; на старіших ядрах маска не зміниться, і це правильна відповідь, а не поламаний крок.

**`W` — ядро спіткнулося.** `sudo insmod taintlab.ko step=2` друкує в журнал повний слід стека від `WARN_ON_ONCE` і додає до маски 512. Це та сама пляма, яка в чужому звіті означає «аварія не перша», — і тут видно, яка вона дешева: один макрос усередині вашого коду, і кожен наступний oops у цій системі читатиметься як другий. Якщо в ядрі ввімкнено `panic_on_warn`, цей крок одразу зупинить машину.

Заразом слід стека дає найдешевший спосіб побачити маску такою, якою її бачить розбір аварії. Зберіть пропрієтарний варіант, завантажте з `step=2` — і в шапці сліду буде рядок:

```
CPU: 0 PID: 1874 Comm: insmod Tainted: P        W  OE     6.6.32 #1
```

1 + 512 + 4096 + 8192 = 12801 — те саме число, лише записане літерами. Кожен прапорець має закріплену позицію, а незайняті лишаються пробілами: вісім прогалин між `P` і `W` — це не форматування, а вісім невиставлених бітів. Отже, порядок у рядку — це порядок у таблиці прапорців, а не порядок подій, і з заголовка не видно, що сталося раніше.

**`U` — пляма руками.**

```sh
echo 64 | sudo tee /proc/sys/kernel/tainted   # додає біт 6
echo 0  | sudo tee /proc/sys/kernel/tainted   # не знімає нічого
```

Запис у цей [параметр sysctl](book:unix-linux/sysctl-tunables) вимагає `CAP_SYS_ADMIN` і працює як побітове «або»: число накладається на наявну маску, тож нулем ви не повертаєте нічого. Той самий біт ставиться і зсередини — `insmod taintlab.ko step=3` викликає `add_taint(TAINT_USER, …)` напряму.

## Дві маски, які легко сплутати

![Джерела плям сходяться в add_taint(), а осідають у двох різних масках: глобальній і модульній](/reference/unix-linux/foundations/kernel-taint/img/taint-two-masks.svg)

*Модульна маска зникає разом із модулем, глобальна — ні; звідси й слід у звіті від того, кого в системі вже немає.*

```sh
cat /sys/module/taintlab/taint     # OE
grep taintlab /proc/modules        # taintlab 16384 0 - Live 0x… (OE)
sudo rmmod taintlab
cat /proc/sys/kernel/tainted       # число не змінилося
```

Літери в дужках у `/proc/modules` і файл `taint` у sysfs показують плями **цього модуля**. `lsmod` — обгортка над тими самими даними, і залежно від версії інструмента колонки з літерами може не бути взагалі, тож звіряйтеся з першоджерелом. Після `rmmod` обидва показники зникають разом із текою модуля, а число в `/proc/sys/kernel/tainted` лишається тим самим.

## `panic_on_taint` і пастка систем числення

Останній крок показує єдиний наслідок плями, помітний неозброєним оком. Допишіть до [командного рядка ядра](book:unix-linux/bootloader-and-cmdline) параметр `panic_on_taint=240 panic=10` і перезавантажтеся.

**Умова:** які біти закриває маска 240 у цьому параметрі?

```
рядок ядра читається як ШІСТНАДЦЯТКОВЕ число
0x240 = 0x200 + 0x40
0x200 = 2⁹  →  біт 9  →  W
0x040 = 2⁶  →  біт 6  →  U
```

Ядро підтвердить прочитане в журналі: `panic_on_taint: bitmask=0x240 nousertaint_mode=disabled`. Далі кожен із двох рядків нижче зупинить машину, тож між ними доведеться перезавантажитися:

```sh
sudo insmod taintlab.ko step=2                # WARN → біт W → паніка
echo 64 | sudo tee /proc/sys/kernel/tainted   # біт U → паніка
```

`Kernel panic - not syncing: panic_on_taint set ...` — цей рядок і є метою. Перевірка сидить усередині `add_taint()`, одразу після того, як біт лягає в маску, тому паніка настає в момент появи плями, а не колись потім. Саме цим параметр і цінний: на біті зіпсованої сторінки він зупиняє машину, поки дамп пам'яті ще показує причину.

Звідси й пастка. Число в командному рядку шістнадцяткове, а число в sysctl десяткове: `panic_on_taint=64` означає не `U`, а `0x64` — тобто біти `S`, `B` і `U` разом. Вказавши там біт, який ваш дистрибутив ставить під час завантаження (наприклад `I` — обхід вади прошивки), ви дістанете машину, що панікує при кожній спробі стартувати. Другий бік того ж параметра — суфікс `nousertaint`: із `panic_on_taint=240,nousertaint` запис числа 64 у sysctl поверне `EINVAL` замість паніки, а модуль із `WARN` панікуватиме, як і раніше.

## Що ще ламається

Числа складаються, а не замінюються, тож читайте маску після **кожного** кроку: без перезавантаження між сходинками ви побачите суму, а не результат останньої дії. Заголовки мусять збігатися з поточним ядром — після оновлення ядра модуль треба перезбирати. І найкорисніше наостанок:

```sh
sudo insmod taintlab.ko step=9
# insmod: ERROR: could not insert module taintlab.ko: Invalid parameters
cat /proc/sys/kernel/tainted        # біти O і E однаково з'явилися
```

Плями ставить завантажувач, розбираючи метадані, — задовго до того, як `init` модуля дістав слово. Модуля в системі немає, він не виконав жодного власного рядка, у `/sys/module` порожньо — а маска вже змінена назавжди. Читаючи чужий заголовок аварії, варто пам'ятати: біт не означає, що щось із цього справді працювало.
