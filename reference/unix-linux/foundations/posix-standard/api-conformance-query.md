# 📋 Опитування відповідності: макроси, sysconf, pathconf, confstr, getconf

Заявка й фактична відповідність — різні величини, і в тому весь механізм: програма макросом називає редакцію контракту, на яку розраховує, а система окремо звітує, що з обіцяного в неї насправді є. Тому й засобів чотири рівні: макроси перевірки можливостей і чотири стани макроса опції — на компіляції; `sysconf`, `pathconf` і `confstr` — на виконанні; `getconf` — те саме з оболонки. Нижче — таблиці сталих `_SC_`/`_PC_`/`_CS_`, сигнатури, коди помилок і те, як усе це поєднується з ключем `-std` компілятора.

## Заявка програми: макроси перевірки можливостей

Заголовки бібліотеки C оголошують не все підряд. Вони дивляться на макроси перевірки можливостей (feature test macros), які програма визначила **до** підключення першого заголовка, і відкривають рівно той набір імен, який відповідає замовленому рівню. Причина строга: імена, яких стандарт не вимагає, належать програмі, і бібліотека не має права їх зайняти без дозволу.

Носій цього механізму — не ядро, а [бібліотека C](book:unix-linux/libc-as-gateway): саме її заголовки й таблиця умовних гардів у `<features.h>` вирішують, що ви побачите.

![Чотири шари оголошень — ISO C, POSIX, XSI, GNU — і макрос, який відмикає кожен з них](/reference/unix-linux/foundations/posix-standard/img/ftm-layers.svg)

*Набори вкладені один в одний: кожен наступний макрос дає все з попередніх плюс своє.*

### Головне правило: раніше за все

Макрос мусить бути визначений **до першого `#include`** будь-якого системного заголовка. Умовні гарди обчислюються один раз, коли заголовок читається; пізніший `#define` уже нічого не змінить — механіку цього моменту розбирає [препроцесор і заголовки](guide:embedded/c-preprocessor-headers).

```c
#define _POSIX_C_SOURCE 200809L   /* ПЕРШИЙ рядок, до будь-якого #include */
#include <unistd.h>
```

Надійніший спосіб — узагалі не тримати цей `#define` у коді, а віддати його командному рядку: `-D_POSIX_C_SOURCE=200809L`. Тоді макрос гарантовано існує ще до того, як компілятор прочитав перший символ файлу, і жоден `#include "config.h"`, що сам тягне `<stdio.h>`, вас не випередить.

### `_POSIX_C_SOURCE` — рівень базового POSIX

| Значення | Що відмикає |
|---|---|
| `1` | POSIX.1-1990 та ISO C (1990) |
| `2` | + POSIX.2-1992: `<regex.h>`, `<glob.h>`, `<fnmatch.h>`, `<wordexp.h>` |
| `199309L` | + POSIX.1b-1993, реальночасові розширення: `nanosleep`, `clock_gettime`, `timer_create`, `sigqueue` |
| `199506L` | + POSIX.1c-1995: потоки, увесь набір `pthread_*` |
| `200112L` | POSIX.1-2001 (Issue 6) без XSI, плюс можливості C95 і C99 |
| `200809L` | POSIX.1-2008 (Issue 7) без XSI: `openat`, `getline`, `strdup`, `fexecve`, `psignal` |
| `202405L` | POSIX.1-2024 (Issue 8) без XSI: `strlcpy`, `getentropy`, `ppoll`, `pipe2`, `accept4`, `qsort_r`, `memmem` |

Значення читаються як «не менше ніж»: `200809L` дає все з попередніх рядків теж. Таблиця описує, що додала кожна **редакція стандарту**, а не що вміє конкретна машина: бібліотека, яка Issue 8 ще не реалізувала, прийме число `202405L` мовчки й нічого нового не покаже. Тому заявка й фактична відповідність — різні величини, і другу перевіряють окремо.

### `_XOPEN_SOURCE` — той самий POSIX плюс набір XSI

| Значення | Що відмикає |
|---|---|
| будь-яке визначене | POSIX.1, POSIX.2 і XPG4 |
| `500` | + SUSv2 (UNIX 98) |
| `600` | + SUSv3 = POSIX.1-2001 з розширенням XSI, і C99 |
| `700` | + SUSv4 = POSIX.1-2008 з XSI |
| `800` | + POSIX.1-2024 з XSI |

XSI — надмножина базового POSIX, тож `_XOPEN_SOURCE` сам підтягує відповідний рівень `_POSIX_C_SOURCE`, і визначати обидва не треба. Саме XSI відкриває System V IPC (`shmget`, `msgget`, `semop`), `crypt()`, `strptime()` і низку інших історичних імен, яких у базовому наборі немає.

### Решта макросів

| Макрос | Дія |
|---|---|
| `_POSIX_SOURCE` | застарілий; те саме, що `_POSIX_C_SOURCE` зі значенням `1` |
| `_DEFAULT_SOURCE` | (glibc ≥ 2.19) типовий набір: POSIX.1-2008 + ISO C99 + звичні розширення BSD і System V |
| `_BSD_SOURCE`, `_SVID_SOURCE` | застарілі з glibc 2.20, замінені на `_DEFAULT_SOURCE` |
| `_GNU_SOURCE` | усе одразу: ISO C, POSIX.1, POSIX.2, BSD, SVID, X/Open, LFS і власні розширення GNU |
| `_ISOC99_SOURCE`, `_ISOC11_SOURCE`, `_ISOC23_SOURCE` | рівні ISO C; те саме дають ключі `-std=c99`, `-std=c11`, `-std=c23` |
| `_FILE_OFFSET_BITS 64` | на 32-бітних системах перемикає `off_t` і файлові виклики на 64-бітні варіанти |
| `_TIME_BITS 64` | (glibc ≥ 2.34) 64-бітний `time_t` на 32-бітних системах — життя після 2038 року; вимагає `_FILE_OFFSET_BITS 64` |
| `_LARGEFILE64_SOURCE` | паралельні імена з суфіксом `64` (`lseek64`, `off64_t`); витіснений попереднім |
| `_REENTRANT`, `_THREAD_SAFE` | історичні; нині їх ставить ключ `-pthread` |
| `_FORTIFY_SOURCE 1..3` | нічого не відмикає: додає перевірки переповнення в `str*` і `mem*` |

### Стан за замовчуванням і як його втратити

Якщо не визначено **жодного** зі стандартних макросів, glibc діє так, ніби визначено `_DEFAULT_SOURCE`: видно ISO C, увесь POSIX.1-2008 і звичні розширення BSD та System V. Це і є причина, чому «просто скомпілювати» зазвичай працює.

Але щойно ви визначили будь-який стандартний макрос — типовий набір **вимикається**. `-D_POSIX_C_SOURCE=200809L` не додає POSIX до типового набору, а замінює набір на строго POSIX-ний, і разом із замовленим ви втрачаєте BSD-шні дрібниці, які раніше йшли задарма. Потрібні обидва — просіть обидва:

```
-D_POSIX_C_SOURCE=200809L -D_DEFAULT_SOURCE
```

## `-std=c17` проти `-std=gnu17`

| Командний рядок | `__STRICT_ANSI__` | Що оголошено |
|---|---|---|
| `cc a.c` | ні | ISO C типового діалекту + POSIX.1-2008 + BSD/SysV |
| `cc -std=gnu17 a.c` | ні | те саме, лише діалект зафіксовано явно |
| `cc -std=c17 a.c` | **так** | лише ISO C17 — жодного `open`, `fork`, `strdup` |
| `cc -std=c17 -D_POSIX_C_SOURCE=200809L a.c` | так | ISO C17 + POSIX.1-2008, без BSD і GNU |
| `cc -std=c17 -D_XOPEN_SOURCE=700 a.c` | так | те саме плюс XSI |
| `cc -std=c17 -D_GNU_SOURCE a.c` | так | усе |
| `cc -ansi a.c` | так | лише ISO C90 |

Ланцюжок тут не такий прямий, як здається. Ключ `-std=c17` нічого не забороняє сам: він лише визначає макрос `__STRICT_ANSI__`. А вже `<features.h>` бібліотеки, побачивши цей макрос, не вмикає типового набору. Тобто обмеження накладає **бібліотека**, а не компілятор, — і зняти його можна тільки макросом, ключем компілятора не вийде.

Варіант із префіксом `gnu` (`-std=gnu17`, `-std=gnu23`) означає рівно те саме видання мови, тільки без `__STRICT_ANSI__`, тож типовий набір лишається на місці. Який діалект береться, коли `-std` не вказано, залежить від версії компілятора — у GCC 11–14 це `gnu17`, у GCC 15 — `gnu23`, — тому покладатися на замовчування в збірці, яку хтось колись перезбере іншим компілятором, не варто.

Подивитися, що діє насправді, можна не гадаючи:

```sh
$ cc -std=c17   -dM -E -x c /dev/null | grep -c __STRICT_ANSI__
1
$ cc -std=gnu17 -dM -E -x c /dev/null | grep -c __STRICT_ANSI__
0
```

## Звідки береться «implicit declaration of function»

До C99 виклик функції без оголошення був законним: компілятор мовчки припускав `int f()`. C99 це прибрав, але компілятори ще два десятиліття лише попереджали — аж поки GCC 14 і Clang 16 не зробили таке попередження помилкою за замовчуванням, а C23 не оголосив конструкцію порушенням обмежень мови.

Строгість тут не формальна. Припущений тип повернення — `int`. Візьміть `strdup()`, яка насправді повертає `char *`. На типовій 64-бітній моделі `int` займає 32 біти, а вказівник — 64, і за [угодою про виклик](book:programming/calling-convention) результат приїжджає в 64-бітному регістрі. Без оголошення компілятор бере з нього лише молодші 32 біти й розширює їх знаком:

```
справжня адреса   0x00007f3a91c04260
взято як int      0x91c04260  →  розширення знаком
отримано          0xffffffff91c04260   ← нікуди не веде
```

Програма падає не там, де помилка, а там, де вперше торкнеться цієї пам'яті, — і зв'язок між двома місцями не видно взагалі. Саме тому діагностику підняли до помилки.

Три причини, чому оголошення не знайшлося:

1. **Забутий макрос.** `strdup`, `getline`, `openat` вимагають `_POSIX_C_SOURCE ≥ 200809L`. Найчастіший випадок.
2. **`-std=c17` замість `-std=gnu17`.** Макрос ніхто не забув — його виключив `__STRICT_ANSI__`.
3. **Функції немає в POSIX узагалі.** `asprintf`, `strcasestr`, `secure_getenv` — розширення GNU, і без `_GNU_SOURCE` їх не буде за жодного рівня POSIX.

Окремий випадок, який плутає найдужче: `strdup` і `strndup` увійшли до ISO C23. Тому той самий файл, який не збирається під `-std=c17`, спокійно збирається під `-std=c23` без жодного POSIX-макроса.

> 🔧 **Навіщо це.** Помилка «implicit declaration» майже ніколи не про відсутню бібліотеку. Лінкер знайде `strdup` у `libc` і без оголошення — зламається саме тип результату. Тому шукати треба не пакунок для встановлення, а рядок із макросом.

## Відповідь системи (1): макрос опції в `unistd.h`

Кожній необов'язковій підсистемі стандарту відповідає символьна стала в `<unistd.h>`. У неї чотири можливі стани, і вони дають три різні відповіді.

![Чотири стани макроса опції: не визначено, -1, 0 і додатне число — і що робить програма в кожному випадку](/reference/unix-linux/foundations/posix-standard/img/option-decision.svg)

*Тільки нуль зобов'язує питати під час виконання; решта станів відповідають остаточно ще на компіляції.*

| Стан макроса | Що це означає | Дія програми |
|---|---|---|
| не визначено | опції немає | обхід або відмова |
| `-1` | опції немає, сказано явно | обхід або відмова |
| `0` | на компіляції невідомо — залежить від машини, де запустять | спитати `sysconf()` під час виконання |
| `> 0` (`202405L`) | опція є завжди | вживати прямо |

Додатне число — це не «істина», а **редакція**, за якою опцію реалізовано: `202405L` для Issue 8, `200809L` для Issue 7.

У редакції 2024 року частина колишніх опцій стала обов'язковою — стандарт про них каже «цей символ завжди має значення `202405L`»:

`_POSIX_THREADS` · `_POSIX_TIMERS` · `_POSIX_ASYNCHRONOUS_IO` · `_POSIX_BARRIERS` · `_POSIX_MONOTONIC_CLOCK`

Справді необов'язкові — ті, про які стандарт каже «якщо визначено, то `-1`, `0` або `202405L`»:

`_POSIX_PRIORITY_SCHEDULING` · `_POSIX_SHARED_MEMORY_OBJECTS` · `_POSIX_MESSAGE_PASSING` · `_POSIX_SPAWN` · `_POSIX_MEMLOCK` · `_POSIX_MEMLOCK_RANGE` · `_POSIX_RAW_SOCKETS` · `_POSIX_IPV6` · `_POSIX_SPORADIC_SERVER`

Рух буває і в третій бік: сталі `_POSIX_TRACE*` редакція 2024 року позначила як відмерлі — опцію трасування з тексту виводять, і реалізацій у неї майже не було.

Окремо стоять `_POSIX_VERSION`, `_POSIX2_VERSION` і `_XOPEN_VERSION` — це не опції, а номер редакції, за якою система себе оголошує; `_XOPEN_UNIX` каже, чи є розширення XSI, і тоді `_XOPEN_VERSION` дорівнює `800`.

Канонічний шаблон коду охоплює всі чотири стани:

```c
#include <unistd.h>

static int have_spawn(void) {
#if !defined(_POSIX_SPAWN) || _POSIX_SPAWN == -1
    return 0;                          /* немає й не буде */
#elif _POSIX_SPAWN == 0
    return sysconf(_SC_SPAWN) > 0;     /* вирішиться на місці */
#else
    return 1;                          /* є завжди */
#endif
}
```

`#if !defined(X) || X == -1` — не надмірність: у препроцесорі невизначене ім'я перетворюється на `0`, тож без `defined` стан «не визначено» неможливо відрізнити від стану «нуль».

## Відповідь системи (2): `sysconf`

```c
#include <unistd.h>

long sysconf(int name);
```

| Результат | `errno` | Значення |
|---|---|---|
| `≥ 0` | не чіпається | це і є відповідь |
| `-1` | `EINVAL` | реалізація не знає такої назви |
| `-1` | не змінився | межі не існує, або опцію не підтримано |

Два різні `-1` розрізняються **тільки** станом `errno`, а сама функція його при успіху не чіпає. Звідси єдиний правильний виклик: обнулити `errno` перед ним і подивитися після. Загальні правила роботи з цією змінною розібрано в [errno та POSIX-коди помилок](book:programming/errno).

```c
errno = 0;
long v = sysconf(_SC_OPEN_MAX);
if (v == -1 && errno != 0) { /* назва невідома */ }
```

Відповідь `sysconf` не змінюється протягом життя процесу — з двома винятками: `_SC_NPROCESSORS_ONLN` (ядра вмикають і вимикають на ходу) і `_SC_OPEN_MAX` після `setrlimit()`, що змінив м'яку межу `RLIMIT_NOFILE`.

**Версії контракту**

| Стала | Що повертає |
|---|---|
| `_SC_VERSION` | редакція POSIX під час виконання (значення `_POSIX_VERSION`) |
| `_SC_2_VERSION` | те саме для тому «Оболонка й утиліти» |
| `_SC_XOPEN_VERSION` | рівень XSI |

**Межі системи**

| Стала | Що повертає |
|---|---|
| `_SC_ARG_MAX` | скільки байтів займуть аргументи й оточення одного `execve` |
| `_SC_CHILD_MAX` | скільки одночасних процесів дозволено одному користувачеві |
| `_SC_OPEN_MAX` | скільки дескрипторів може тримати процес |
| `_SC_STREAM_MAX` | скільки потоків `FILE *` можна відкрити одночасно |
| `_SC_NGROUPS_MAX` | скільки додаткових груп має процес |
| `_SC_HOST_NAME_MAX` | довжина імені вузла, без завершального нуля |
| `_SC_LOGIN_NAME_MAX` | довжина імені користувача, разом із нулем |
| `_SC_SYMLOOP_MAX` | скільки символьних посилань пройде розбір шляху до `ELOOP` |
| `_SC_LINE_MAX` | найдовший рядок, який зобов'язані переварити текстові утиліти |
| `_SC_RE_DUP_MAX` | межа повторювача `{n,m}` у регулярних виразах |
| `_SC_ATEXIT_MAX` | скільки функцій приймає `atexit()` |
| `_SC_TZNAME_MAX` | довжина назви часового поясу |
| `_SC_GETPW_R_SIZE_MAX`, `_SC_GETGR_R_SIZE_MAX` | скільки пам'яті просити під буфер для `getpwnam_r()` і `getgrnam_r()` |

**Машина**

| Стала | Що повертає |
|---|---|
| `_SC_PAGESIZE` (він же `_SC_PAGE_SIZE`) | розмір сторінки пам'яті в байтах |
| `_SC_CLK_TCK` | скільки тиків на секунду в одиницях `times()` — не частота планувальника |
| `_SC_NPROCESSORS_CONF` | скільки процесорів система знає |
| `_SC_NPROCESSORS_ONLN` | скільки з них увімкнено просто зараз |
| `_SC_NSIG` | скільки взагалі номерів сигналів |
| `_SC_PHYS_PAGES`, `_SC_AVPHYS_PAGES` | фізична й вільна пам'ять у сторінках — **розширення glibc**, не POSIX |

Три сталі з цієї таблиці — `_SC_NPROCESSORS_CONF`, `_SC_NPROCESSORS_ONLN` і `_SC_NSIG` — увійшли до стандарту аж у редакції 2024 року, доти проживши десятиліття як розширення; писати код, що спирається на них, і водночас вимагати старішої редакції — суперечність, яку компілятор не спіймає.

**Потоки**

| Стала | Що повертає |
|---|---|
| `_SC_THREAD_STACK_MIN` | найменший припустимий розмір стека потоку |
| `_SC_THREAD_THREADS_MAX` | межа кількості потоків у процесі |
| `_SC_THREAD_KEYS_MAX` | скільки ключів локальних для потоку даних |
| `_SC_THREAD_DESTRUCTOR_ITERATIONS` | скільки разів прогнати деструктори цих даних |

**Опції.** Окремої таблиці не треба: назва виходить із назви макроса відкиданням префікса `_POSIX`. `_POSIX_SPAWN` → `_SC_SPAWN`, `_POSIX_THREADS` → `_SC_THREADS`, `_POSIX_TIMERS` → `_SC_TIMERS`, `_POSIX_PRIORITY_SCHEDULING` → `_SC_PRIORITY_SCHEDULING`, `_XOPEN_UNIX` → `_SC_XOPEN_UNIX`. Виняток форми — сталі тому про утиліти: `_POSIX2_C_BIND` → `_SC_2_C_BIND`.

## Відповідь системи (3): `pathconf` і `fpathconf`

```c
#include <unistd.h>

long pathconf(const char *path, int name);
long fpathconf(int fildes, int name);
```

Правило трьох результатів тут те саме, що в `sysconf`. Різниця в тому, що ці функції справді ходять до файлової системи, тож до `EINVAL` додаються `EACCES`, `ELOOP`, `ENAMETOOLONG`, `ENOENT`, `ENOTDIR` для `pathconf` і `EBADF` для `fpathconf`. Крім того, `EINVAL` тут означає ще й «назва відома, але до цього файлу не стосується» — питати `_PC_MAX_CANON` про звичайний файл замість термінала законно, але безглуздо, і система має право відмовити.

| Стала | Що повертає |
|---|---|
| `_PC_NAME_MAX` | найдовше ім'я файлу в цьому каталозі |
| `_PC_PATH_MAX` | найдовший відносний шлях від цього каталогу |
| `_PC_LINK_MAX` | скільки жорстких посилань витримає файл |
| `_PC_PIPE_BUF` | скільки байтів запис у канал лишається неподільним |
| `_PC_MAX_CANON` | довжина рядка в канонічному режимі термінала |
| `_PC_MAX_INPUT` | розмір вхідної черги термінала |
| `_PC_VDISABLE` | символ, яким вимикають спецфункцію термінала |
| `_PC_CHOWN_RESTRICTED` | чи заборонено звичайному користувачеві віддавати свій файл іншому |
| `_PC_NO_TRUNC` | чи задовге ім'я дає помилку, а не мовчазне обрізання |
| `_PC_FILESIZEBITS` | скільки бітів треба, щоб виразити найбільший файл цієї ФС |
| `_PC_SYMLINK_MAX` | найдовший вміст символьного посилання |
| `_PC_2_SYMLINKS` | чи ця ФС узагалі знає символьні посилання |
| `_PC_ALLOC_SIZE_MIN` | найменша одиниця виділення місця |
| `_PC_REC_MIN_XFER_SIZE`, `_PC_REC_MAX_XFER_SIZE`, `_PC_REC_INCR_XFER_SIZE`, `_PC_REC_XFER_ALIGN` | рекомендований розмір і вирівнювання блоку читання та запису |
| `_PC_ASYNC_IO`, `_PC_SYNC_IO`, `_PC_PRIO_IO` | чи працює на цьому файлі асинхронний, синхронний і пріоритетний ввід-вивід |
| `_PC_TIMESTAMP_RESOLUTION` | роздільність часових позначок у наносекундах (нове в Issue 8) |
| `_PC_FALLOC` | чи підтримує ця ФС `posix_fallocate()` (нове в Issue 8) |
| `_PC_TEXTDOMAIN_MAX` | межа довжини імені текстового домену |

Окрема функція для шляху існує саме тому, що ці межі належать не системі, а точці монтування: у [різних родин файлових систем](book:unix-linux/filesystem-families) розходяться і `_PC_NAME_MAX`, і `_PC_LINK_MAX`, і `_PC_FILESIZEBITS`, і той самий процес одночасно бачить кілька різних відповідей.

`_PC_PIPE_BUF` вартий окремої уваги: це не розмір буфера, а межа **неподільності** — запис до цієї кількості байтів у канал не переплететься із записом іншого процесу, а більший переплететься (докладніше — [канали й іменовані канали](book:unix-linux/pipe-and-fifo)).

Найпоширеніша пастка тут — `PATH_MAX`. Ця стала з `<limits.h>` може бути не визначена взагалі, бо межі може не існувати; тоді й `pathconf(dir, _PC_PATH_MAX)` поверне `-1` із незміненим `errno`. На Linux `PATH_MAX` дорівнює 4096, але це межа одного звернення до ядра, а не межа глибини дерева: [розбір шляху](book:unix-linux/path-resolution) відносними кроками спокійно заходить далі. Тому `char buf[PATH_MAX]` — не гарантія, а припущення.

```c
errno = 0;
long nm = pathconf(dir, _PC_NAME_MAX);
if (nm == -1 && errno == 0) nm = 255;    /* межі немає — беремо власну */
```

## Відповідь системи (4): `confstr`

```c
#include <unistd.h>

size_t confstr(int name, char *buf, size_t len);
```

Функція повертає **потрібний розмір буфера разом із завершальним нулем**, а не довжину того, що записала. Якщо потрібний розмір більший за `len`, рядок мовчки обрізається до `len - 1` байтів і завершується нулем — жодного сигналу про це не буде, крім самого поверненого числа. Нуль означає одне з двох: назва невідома (`errno` стає `EINVAL`) або для цієї назви значення не визначено (`errno` не змінюється).

Звідси шаблон із двох викликів:

```c
size_t n = confstr(_CS_PATH, NULL, 0);       /* скільки треба */
if (n == 0) { /* немає значення або невідома назва — дивитись errno */ }
char *buf = malloc(n);
confstr(_CS_PATH, buf, n);                   /* тепер напевно влізе */
```

| Стала | Що повертає |
|---|---|
| `_CS_PATH` | шлях пошуку, у якому гарантовано лежать стандартні утиліти |
| `_CS_V8_ENV` | змінні оточення для середовища збірки Issue 8 (`_CS_V7_ENV` — для Issue 7) |
| `_CS_POSIX_V8_ILP32_OFF32_CFLAGS` / `_LDFLAGS` / `_LIBS` | ключі для моделі з 32-бітними `int`, `long`, вказівником і 32-бітним `off_t` |
| `_CS_POSIX_V8_ILP32_OFFBIG_CFLAGS` / `_LDFLAGS` / `_LIBS` | те саме, але `off_t` не менший за 64 біти |
| `_CS_POSIX_V8_LP64_OFF64_CFLAGS` / `_LDFLAGS` / `_LIBS` | 64-бітні `long`, вказівник і `off_t` |
| `_CS_POSIX_V8_LPBIG_OFFBIG_CFLAGS` / `_LDFLAGS` / `_LIBS` | `long`, вказівник і `off_t` не менші за 64 біти |
| `_CS_POSIX_V8_THREADS_CFLAGS` / `_LDFLAGS` | що додати до збірки програми з потоками |
| `_CS_POSIX_V8_WIDTH_RESTRICTED_ENVS` | перелік середовищ збірки, доступних на цій системі |
| `_CS_GNU_LIBC_VERSION`, `_CS_GNU_LIBPTHREAD_VERSION` | версія бібліотеки рядком — **розширення glibc** |

Група `_CS_POSIX_V8_*` — не декорація. Це офіційна відповідь системи на питання «якими ключами мене компілювати, щоб дістати таку модель даних», і скрипт складання може спитати їх замість того, щоб вгадувати. Остання пара — найпростіший спосіб дізнатися версію самої glibc під час виконання (переносним він, звісно, не є: на іншій бібліотеці цих назв просто немає), що важливо, коли [сумісність ABI](book:unix-linux/library-abi-compat) стоїть під питанням: заголовки обіцяють одне, а бібліотека на машині запуску може бути старша.

## `getconf`: те саме з оболонки

```
getconf [-v специфікація] системна_змінна
getconf [-v специфікація] шляхова_змінна шлях
getconf -a                              # розширення glibc, у стандарті немає
```

- Без `-v` відповідь стосується типового середовища збірки цієї системи; з `-v` — конкретного (`POSIX_V8_LP64_OFF64`, `POSIX_V7_ILP32_OFFBIG`).
- Імена меж пишуться **без** префікса: `getconf ARG_MAX`, а не `_SC_ARG_MAX`; `getconf NAME_MAX /home`, а не `_PC_NAME_MAX`; `getconf PATH`, а не `_CS_PATH`. Імена опцій, навпаки, беруться як є: `getconf _POSIX_VERSION`.
- Код виходу: `0` — назву впізнано й значення виведено; більше нуля — помилка.
- Якщо змінної на цій системі немає, `getconf` друкує слово `undefined`. Це відповідь, а не збій.

**Умова: Debian 12, glibc 2.36, x86-64.**

```sh
$ getconf _POSIX_VERSION
200809
$ getconf PATH
/bin:/usr/bin
$ getconf ARG_MAX
2097152
$ getconf PAGESIZE
4096
$ getconf NAME_MAX /home
255
$ getconf PATH_MAX /home
4096
$ getconf _POSIX_TRACE
undefined
$ getconf LFS_CFLAGS

$ echo $?
0
```

Порожній рядок після `LFS_CFLAGS` — правильна відповідь: на 64-бітній системі великі файли працюють без жодних додаткових ключів, тож додавати нема чого. На 32-бітній та сама команда видала б `-D_FILE_OFFSET_BITS=64`. Ключ `-a` виводить усі відомі системі змінні одразу — зручно, щоб побачити повний перелік конкретної машини, але покладатися на нього в переносному скрипті не можна: стандарт такої форми не має.

## Мінімальна робоча програма

```c
/* conf.c — усі чотири способи спитати систему.
   збірка: cc -std=c17 -D_POSIX_C_SOURCE=200809L -o conf conf.c */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* 1. Час компіляції: що обіцяли заголовки */
static void compile_time(void) {
#ifdef _POSIX_VERSION
    printf("_POSIX_VERSION  = %ldL\n", (long)_POSIX_VERSION);
#else
    printf("_POSIX_VERSION  не визначено\n");
#endif
#if !defined(_POSIX_SPAWN) || _POSIX_SPAWN == -1
    printf("posix_spawn     : немає\n");
#elif _POSIX_SPAWN == 0
    printf("posix_spawn     : питати на виконанні\n");
#else
    printf("posix_spawn     : є завжди (%ldL)\n", (long)_POSIX_SPAWN);
#endif
}

/* 2. Час виконання: система */
static void ask_sys(int name, const char *label) {
    errno = 0;
    long v = sysconf(name);
    if (v != -1)          printf("%-16s: %ld\n", label, v);
    else if (errno == 0)  printf("%-16s: межі немає\n", label);
    else                  printf("%-16s: %s\n", label, strerror(errno));
}

/* 3. Час виконання: конкретний шлях */
static void ask_path(const char *path, int name, const char *label) {
    errno = 0;
    long v = pathconf(path, name);
    if (v != -1)          printf("%-16s(%s): %ld\n", label, path, v);
    else if (errno == 0)  printf("%-16s(%s): межі немає\n", label, path);
    else                  printf("%-16s(%s): %s\n", label, path, strerror(errno));
}

/* 4. Час виконання: рядкові значення */
static void ask_str(int name, const char *label) {
    errno = 0;
    size_t n = confstr(name, NULL, 0);
    if (n == 0) {
        printf("%-16s: %s\n", label, errno ? "невідома назва" : "значення немає");
        return;
    }
    char *buf = malloc(n);
    if (buf == NULL) { perror("malloc"); return; }
    confstr(name, buf, n);
    printf("%-16s: %s\n", label, buf);
    free(buf);
}

int main(void) {
    compile_time();
    ask_sys(_SC_VERSION,  "_SC_VERSION");
    ask_sys(_SC_PAGESIZE, "_SC_PAGESIZE");
    ask_sys(_SC_OPEN_MAX, "_SC_OPEN_MAX");
    ask_sys(_SC_THREADS,  "_SC_THREADS");
    ask_path("/", _PC_NAME_MAX, "_PC_NAME_MAX");
    ask_path("/", _PC_PIPE_BUF, "_PC_PIPE_BUF");
    ask_str(_CS_PATH, "_CS_PATH");
    return 0;
}
```

**Умова: та сама машина — Debian 12, glibc 2.36, x86-64.**

```
_POSIX_VERSION  = 200809L
posix_spawn     : є завжди (200809L)
_SC_VERSION     : 200809
_SC_PAGESIZE    : 4096
_SC_OPEN_MAX    : 1024
_SC_THREADS     : 200809
_PC_NAME_MAX    (/): 255
_PC_PIPE_BUF    (/): 4096
_CS_PATH        : /bin:/usr/bin
```

Зверніть увагу на першу пару рядків: заголовок пообіцяв `200809L`, і `sysconf` це підтвердив. Розбіжність між ними цілком можлива — програму збирають на одній машині, а запускають на іншій, — і саме заради такої розбіжності обидва питання ставлять окремо.

## Шпаргалка: симптом → діагноз → дія

| Симптом | Причина | Дія |
|---|---|---|
| `implicit declaration of function 'strdup'` | немає `_POSIX_C_SOURCE`, або діє `-std=c17` | `-D_POSIX_C_SOURCE=200809L`, або `-std=gnu17`, або `-std=c23` |
| `implicit declaration of function 'asprintf'` | функція не з POSIX, а з GNU | `-D_GNU_SOURCE`; для переносності — переписати на `snprintf()` у два проходи |
| макрос визначено, а помилка лишилася | `#define` стоїть після першого `#include` | перенести до командного рядка, `-D…` |
| з'явилися помилки на функціях, які раніше збиралися | явний стандартний макрос вимкнув типовий набір | додати `-D_DEFAULT_SOURCE` |
| `sysconf` повернув `-1` | невідома назва або межі не існує | обнулити `errno` перед викликом, перевірити після |
| код працює в розробника й падає у клієнта | макрос опції дорівнює `0`, перевірки на виконанні немає | додати `sysconf(_SC_…) > 0` |
| `char buf[PATH_MAX]` не збирається | на цій системі `PATH_MAX` не визначено | `pathconf(dir, _PC_PATH_MAX)`, а на `-1` — власна розумна межа |
| програма псує файли, більші за 2 ГіБ | 32-бітна система без великих зміщень | `-D_FILE_OFFSET_BITS=64`, а для дат після 2038 року ще й `-D_TIME_BITS=64` |
| `confstr` записав обрізаний рядок | буфер узято «з голови», без першого виклику | спершу `confstr(name, NULL, 0)`, потім виділити стільки |
| `getconf` каже `undefined` | опції на цій системі немає | обхід у програмі; це не збій утиліти |
