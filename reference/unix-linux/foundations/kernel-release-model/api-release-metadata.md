# 📋 Анатомія версії ядра: поля Makefile, теги й службові рядки комітів

Ця довідка збирає точні форми, у яких модель випусків виходить назовні рядками: з яких полів складається номер версії, що саме друкують `uname` і `/proc/version`, як звуться теги й гілки в дереві, що засвідчує кожен службовий рядок під комітом і як читати таблицю випусків на kernel.org. Потрібна вона в мить, коли треба не зрозуміти модель, а прочитати конкретний рядок і сказати, звідки він узявся й кому адресований.

Приклади взято зі стану дерева на 2 серпня 2026 року: у mainline — `7.2-rc6`, свіжий стабільний — `7.1.5`.

## Поля Makefile: чотири рядки, з яких росте номер

Номер версії не зашито в код — він живе в перших рядках кореневого `Makefile` і міняється звичайним комітом.

```make
VERSION = 7
PATCHLEVEL = 2
SUBLEVEL = 0
EXTRAVERSION = -rc6
NAME = Baby Opossum Posse
```

| поле | приклад | що означає | коли міняється |
|---|---|---|---|
| `VERSION` | `7` | головний номер | коли `PATCHLEVEL` доростає до 19–20 і велике число починає плутати |
| `PATCHLEVEL` | `2` | номер циклу mainline | у першому коміті кожного вікна злиття |
| `SUBLEVEL` | `0` | лічильник випусків стабільної гілки | лише в гілці `linux-7.1.y`; у mainline завжди `0` |
| `EXTRAVERSION` | `-rc6` | мітка кандидата | щотижня протягом стабілізації; у день випуску стає порожнім |
| `NAME` | `Baby Opossum Posse` | жартівлива назва дерева | зрідка, за настроєм; **у жоден номер версії не потрапляє** |

З перших чотирьох полів `Makefile` складає `KERNELVERSION`:

```make
KERNELVERSION = $(VERSION)$(if $(PATCHLEVEL),.$(PATCHLEVEL)$(if $(SUBLEVEL),.$(SUBLEVEL)))$(EXTRAVERSION)
```

Звідси випливає розбіжність, на якій спотикаються постійно: **тег і рядок версії того самого ядра не збігаються**.

| що це | тег у дереві | `KERNELVERSION` |
|---|---|---|
| тижневий кандидат | `v7.2-rc6` | `7.2.0-rc6` |
| випуск mainline | `v7.1` | `7.1.0` |
| п'ятий стабільний | `v7.1.5` | `7.1.5` |

Тег `v7.1` третьої цифри не має, бо називає подію — випуск. Рядок `7.1.0` її має, бо `SUBLEVEL` стоїть у формулі завжди. Тому `uname -r` на щойно випущеному mainline показує `7.1.0`, хоча ядро всюди зветься «7.1». Тега `v7.1.0` не існує взагалі: стабільна лінія починається з `v7.1.1`.

## Що дописується після Makefile

`KERNELVERSION` — це ще не той рядок, який побачить користувач. Остаточний друкує скрипт `scripts/setlocalversion`, зчіплюючи п'ять шматків у сталому порядку:

```sh
${KERNELVERSION}${file_localversion}${config_localversion}${LOCALVERSION}${scm_version}
```

| шматок | звідки береться | приклад |
|---|---|---|
| `file_localversion` | вміст усіх файлів на ім'я `localversion*` — спершу з теки збірки, потім з теки дерева | `-myfix` |
| `config_localversion` | рядок `CONFIG_LOCALVERSION` із `.config`; довжина обмежена 64 знаками | `-custom` |
| `LOCALVERSION` | змінна в самій команді: `make LOCALVERSION=-test` | `-test` |
| `scm_version` | те, що скрипт дізнався з git | `-00042-g4a1b2c3d4e5f-dirty` |

Останній шматок поводиться по-різному залежно від того, як зібрано ядро:

| умова | що додається |
|---|---|
| `CONFIG_LOCALVERSION_AUTO=y`, `HEAD` стоїть рівно на тезі | нічого |
| `CONFIG_LOCALVERSION_AUTO=y`, `HEAD` пішов далі від тега | `-00042-g4a1b2c3d4e5f` — п'ятизначна кількість комітів від тега і 12 знаків хеша `HEAD` |
| до того ж у дереві є незбережені зміни | ще й `-dirty` |
| `CONFIG_LOCALVERSION_AUTO=n`, `LOCALVERSION` не задано | сама лише `+`, і то лише як ознака «це не рівно тег»; на брудне дерево скорочений режим уже не дивиться |
| `CONFIG_LOCALVERSION_AUTO=n`, `LOCALVERSION` задано | нічого |

![Рядок версії, розкладений на сім суміжних ділянок: три числа й мітка кандидата приходять із Makefile, дві наступні — з файлів localversion і з CONFIG_LOCALVERSION, остання — з git; складений рядок лягає у файл kernel.release, звідти в UTS_RELEASE і далі в uname -r, /proc/sys/kernel/osrelease і початок /proc/version](/reference/unix-linux/foundations/kernel-release-model/img/version-string.svg)

*Кожна ділянка рядка має свого господаря: перші чотири правлять комітом у дерево, дві середні — налаштуванням збірки, останню дописує git і не питає нікого.*

Складений рядок лягає у файл `include/config/kernel.release`, звідти потрапляє в макрос `UTS_RELEASE` (`include/generated/utsrelease.h`) і вже звідти — у все, що ядро друкує про себе.

## Що показують uname і /proc

Виклик `uname(2)` заповнює структуру `utsname`, і кожен ключ команди `uname` віддає одне її поле.

| ключ | поле `utsname` | приклад | звідки |
|---|---|---|---|
| `-s` | `sysname` | `Linux` | стала: у цієї системи воно завжди одне |
| `-n` | `nodename` | `build-01` | ім'я вузла, ставить `sethostname()` — до версії ядра стосунку не має |
| `-r` | `release` | `6.8.0-52-generic` | `UTS_RELEASE`, тобто весь щойно складений рядок |
| `-v` | `version` | `#53-Ubuntu SMP PREEMPT_DYNAMIC Sat Jan 11 00:06:25 UTC 2025` | `UTS_VERSION` — про **складання**, не про версію |
| `-m` | `machine` | `x86_64` | `UTS_MACHINE`, архітектура збірки |
| `-o` | — | `GNU/Linux` | ядро цього не віддає взагалі: рядок дописують `coreutils` |

Плутанина між `-r` і `-v` трапляється постійно, бо англійською обидва ключі виглядають як «версія». Насправді номер ядра несе `-r`, а `-v` розповідає лише про конкретний акт складання:

```
#53-Ubuntu SMP PREEMPT_DYNAMIC Sat Jan 11 00:06:25 UTC 2025
│          │   │               └── час складання; перебивається KBUILD_BUILD_TIMESTAMP
│          │   └── CONFIG_PREEMPT_DYNAMIC (буває PREEMPT або PREEMPT_RT)
│          └── CONFIG_SMP
└── лічильник складань із файлу .version; перебивається KBUILD_BUILD_VERSION —
    саме сюди дистрибутиви вставляють номер свого пакета
```

Увесь цей рядок обрізається до 64 байтів на етапі складання, тож довгі власні мітки в ньому просто зникнуть.

Файл `/proc/version` склеює ті самі три поля разом із тим, хто і чим збирав ядро:

```
Linux version 6.8.0-52-generic (buildd@lcy02-amd64-091) (x86_64-linux-gnu-gcc-13 …, GNU ld …) #53-Ubuntu SMP PREEMPT_DYNAMIC Sat Jan 11 00:06:25 UTC 2025
```

| ділянка | що це |
|---|---|
| `Linux` | `/proc/sys/kernel/ostype` |
| `version` | стале слово самого формату, ні з чого не береться |
| `6.8.0-52-generic` | `/proc/sys/kernel/osrelease` |
| `(buildd@lcy02-amd64-091)` | хто і на якій машині збирав: `LINUX_COMPILE_BY` та `LINUX_COMPILE_HOST` |
| `(x86_64-linux-gnu-gcc-13 …, GNU ld …)` | `LINUX_COMPILER` — компілятор і компонувальник із версіями |
| `#53-Ubuntu SMP PREEMPT_DYNAMIC Sat Jan 11 …` | `/proc/sys/kernel/version` |

Пару `хто@де` беруть із `whoami` і `uname -n` машини-збирача, але дистрибутиви замінюють її сталими значеннями через `KBUILD_BUILD_USER` і `KBUILD_BUILD_HOST`. Без цього збірка не була б відтворюваною: те саме дерево, зібране на двох машинах, давало б різні двійкові файли — і звірити їх ніхто б не зміг.

Ті самі три поля лежать окремими файлами в `/proc/sys/kernel/`, і читати їх зручніше, ніж розбирати вивід команди. [Псевдофайлова система `/proc` — це не файли на диску, а поточний стан ядра, який читається звичайним `read()`](book:unix-linux/proc-filesystem):

| файл | дорівнює | приклад |
|---|---|---|
| `/proc/sys/kernel/ostype` | `uname -s` | `Linux` |
| `/proc/sys/kernel/osrelease` | `uname -r` | `6.8.0-52-generic` |
| `/proc/sys/kernel/version` | `uname -v` | `#53-Ubuntu SMP PREEMPT_DYNAMIC …` |

Є ще одне місце, де той самий рядок працює не як напис, а як замок. [Модуль ядра — це окремо зібраний шматок коду, який завантажують у вже запущене ядро](book:unix-linux/kernel-modules); у кожному модулі зашито рядок `vermagic`, і ядро відмовиться завантажити модуль, якщо цей рядок не збігається з його власним:

```sh
modinfo -F vermagic /lib/modules/$(uname -r)/kernel/fs/xfs/xfs.ko
# 6.8.0-52-generic SMP preempt mod_unload modversions
```

Саме тому модуль, зібраний під `6.8.0-52-generic`, не стане в `6.8.0-53-generic`: збіг перших трьох чисел тут нічого не важить, звіряється весь рядок цілком разом із прапорцями збірки.

## Теги й гілки в дереві

Дерев два, і назви в них не перетинаються. Головне (`torvalds/linux`) містить теги mainline; стабільне (`stable/linux`) містить гілки й теги виправлень.

| форма | приклад | дерево | що це |
|---|---|---|---|
| `v<X>.<Y>-rc<N>` | `v7.2-rc6` | mainline | тижневий кандидат; `N` рахує з одиниці |
| `v<X>.<Y>` | `v7.1` | mainline | випуск; тег заморожено назавжди |
| `v<X>.<Y>.<Z>` | `v7.1.5` | stable | п'ятий випуск стабільної гілки |
| `linux-<X>.<Y>.y` | `linux-6.12.y` | stable | сама гілка; `y` — не число, а буквально буква |
| `next-<РРРРММДД>` | `next-20260731` | linux-next | щоденний зріз майбутнього вікна |

Гілки з іменами `linux-2.6.11.y` і донині лежать у тому самому дереві поруч із `linux-6.18.y` — стабільне дерево нічого не викидає, воно лише перестає в мертві гілки писати.

Кілька команд, якими це дерево питають. Кожна відповідає на одне питання й нічого не змінює:

```sh
git describe --tags                        # де ми стоїмо: найближчий тег і відстань до нього
git tag --contains 4a1b2c3d4e5f            # у які випуски вже потрапив цей коміт
git log --oneline v7.1..v7.1.1             # що саме додав перший стабільний випуск
git log --oneline --grep='^Fixes: 4a1b2c'  # чи полагоджено вже цей коміт
```

[Що таке тег, гілка й діапазон `A..B` у git](book:programming/git-branching-and-history) — механіка, спільна для всіх проєктів; ядро лише користується нею в незвично великому масштабі.

Веб-дзеркало дерева розуміє короткі посилання, і вони трапляються в оголошеннях про вразливості частіше за самі хеші:

```
https://git.kernel.org/stable/c/4a1b2c3d4e5f    # коміт за хешем
https://git.kernel.org/stable/h/v7.1.5          # стан дерева на тезі
```

## Службові рядки під комітом

Наприкінці кожного повідомлення про коміт, після порожнього рядка, стоїть блок рядків виду `Ключ: значення`. Це не оздоба й не журнал ввічливості: кожен рядок має свого читача — людину або програму, — і саме з них зроблено весь облік поруки в ядрі. Ідея перетворити повідомлення коміту на структуровані дані сьогодні звична багатьом проєктам, [хоч домовленості про ключі скрізь свої](book:programming/commit-message-conventions); ядро дійшло до неї раніше за всіх і застосовує найсуворіше.

| рядок | що засвідчує | хто його читає |
|---|---|---|
| `Signed-off-by:` | «я маю право передати цей код далі під ліцензією проєкту» — підпис під Свідоцтвом про походження коду | `checkpatch.pl` (без підпису латку не візьмуть), супровідники, юристи компаній |
| `Co-developed-by:` | код писали кілька людей; **обов'язково** супроводжується власним `Signed-off-by:` названого одразу наступним рядком | супровідник, який звіряє повноту ланцюжка |
| `Reported-by:` | хто знайшов ваду | автор наступного схожого виправлення; статистика внесків |
| `Closes:` | адреса самого звіту, зазвичай у `lore.kernel.org` | трекер, що автоматично закриє звіт; приватні трекери й неробочі адреси заборонені |
| `Suggested-by:` | чия була ідея | облік авторства |
| `Tested-by:` | названа людина перевірила латку на живому залізі | супровідник, зважуючи ризик |
| `Reviewed-by:` | проведено технічну рецензію за писаною формулою відповідальності рецензента | супровідник вище по ланцюжку — це головний доказ, що латку хтось справді читав |
| `Acked-by:` | згода того, хто відповідає за зачеплений код, але сам його не писав; слабша за `Reviewed-by:` | супровідник суміжної підсистеми |
| `Fixes:` | який саме коміт зламав те, що ми лагодимо | **команда стабільних гілок**: із нього виводять, у які гілки виправлення взагалі потрібне |
| `Link:` | де обговорювали; для списків розсилки — `lore.kernel.org` із `Message-ID` без кутових дужок | той, хто за п'ять років спитає «навіщо це зробили» |
| `Cc:` | кого залучали до розмови | ті, кому воно може боліти |
| `Cc: stable@vger.kernel.org` | «це виправлення треба й у стабільні гілки» | робот, що після злиття в mainline забирає латку в чергу стабільних |

Порядок рядків формально не приписано, але на практиці він читається як хронологія: спершу те, що знав автор, далі підписи тих, крізь кого латка проходила, а підпис супровідника — останній.

Обов'язковий серед них лише перший, і важить він не технічно, а юридично. [Текст, під яким розписується автор, зветься Свідоцтвом про походження коду (Developer Certificate of Origin) — це кілька рядків, у яких він стверджує рівно одне: він має право віддати цей код під ліцензією проєкту; ніяких прав нікому при цьому не передають](book:programming/developer-certificate-of-origin). Саме тому `Signed-off-by:` не можна проставити за когось: підпис — це заява, а не позначка про участь.

**Форма блоку в цілому.** Коміт нижче вигаданий; справжня в ньому — форма кожного рядка.

```
net: dsa: fix use-after-free on port teardown

Знімаючи порт, драйвер звільняв структуру порту раніше, ніж знімав
із неї таймер. Спрацювавши після kfree(), таймер писав у вже повернуту
пам'ять: на стенді це давало падіння за кілька секунд після
«ip link set swp0 down».

Переставляємо порядок: спершу del_timer_sync(), потім kfree().

Fixes: a1b2c3d4e5f6 ("net: dsa: add per-port teardown")
Reported-by: Ольга Ткаченко <olha@example.org>
Closes: https://lore.kernel.org/all/20260612093015.1842-1-olha@example.org/
Tested-by: Ольга Ткаченко <olha@example.org>
Reviewed-by: Богдан Кравець <bohdan@example.org>
Cc: stable@vger.kernel.org # 6.12+
Signed-off-by: Марта Гнатюк <marta@example.org>
Signed-off-by: Ярема Заяць <yarema@example.org>
```

Перший підпис — автора, другий — супровідника, який узяв латку до свого дерева. Рядка `Link:` тут немає лише тому, що обговорення звелося до самого звіту, на який уже вказує `Closes:`.

**`Fixes:` — єдиний рядок із жорсткою формою.** Хеш — щонайменше 12 знаків, заголовок зламаного коміту — у круглих дужках і подвійних лапках, увесь рядок в один рядок, без переносу. Ось приклад із самої документації ядра, з реальним комітом:

```
Fixes: 54a4f0239f2e ("KVM: MMU: make kvm_mmu_zap_page() return the number of pages it actually freed")
```

Складати його вручну не треба — git уміє сам, якщо один раз навчити:

```ini
# ~/.gitconfig
[core]
    abbrev = 12
[pretty]
    fixes = Fixes: %h (\"%s\")
```

```sh
git log -1 --pretty=fixes 54a4f0239f2e
# Fixes: 54a4f0239f2e ("KVM: MMU: make kvm_mmu_zap_page() return the number of pages it actually freed")
```

## Різновиди рядка `Cc: stable`

Просте `Cc: stable@vger.kernel.org` означає «беріть у всі живі гілки, де ця вада є». Коли потрібно точніше, після адреси ставлять коментар `#`, і команда стабільних гілок читає його як вказівку.

| форма | що каже |
|---|---|
| `Cc: stable@vger.kernel.org` | звичайне позначення |
| `Cc: stable@kernel.org` | вразливість ще не оприлюднено: адреса без `vger` веде в закритий список |
| `Cc: <stable@vger.kernel.org> # 3.3.x` | нижня межа: у 3.3 і новіші, у старіші не носити |
| `Cc: <stable@vger.kernel.org> # 3.3.x: a1f84a3: sched: Check for idle` | передумова: у 3.3 спершу візьміть отой коміт, інакше ця латка не стане |
| `Cc: <stable@vger.kernel.org> # after -rc3` | не забирати одразу, дати відлежатися в mainline |
| `Cc: <stable@vger.kernel.org> # see patch description, needs adjustments for <= 6.3` | у старі гілки просто так не стане, потрібна ручна переробка |
| `Cc: <stable+noautosel@kernel.org> # причина` | не чіпати автовідбором; причину писати обов'язково |

Форма `# 6.12+` із плюсом у документації як приклад не наведена — там показано `# 3.3.x`, — але в комітах вона трапляється часто й читається так само: «від цієї гілки й далі». Документація ж наголошує на іншому: коли є `Fixes:`, обмеження зазвичай зайве, бо потрібні гілки з нього виводяться самі.

Умови прийому у стабільну гілку записані короткими рядками й перевіряються дослівно:

| вимога | межа |
|---|---|
| виправлення вже в mainline | без винятків; на переробку під стару гілку — окремий шлях |
| розмір | не більше 100 рядків **разом із контекстом** |
| характер вади | падіння, зависання, псування даних, вразливість, поламка збірки, вада конкретного заліза або новий ідентифікатор пристрою |
| що не беруть | теоретичні проблеми без опису, як їх використати; правки стилю; «зроблено краще» |
| час на заперечення | після розсилки добірки — 48 годин на «за» або «проти» |

Коли латка лягає у стабільну гілку, її повідомлення дописують рядком-посиланням на першоджерело. Це найпростіший спосіб відрізнити стабільний коміт від mainline-коміту, і форм тут дві:

```
[ Upstream commit 4a1b2c3d4e5f6789abcdef0123456789abcdef01 ]

commit 4a1b2c3d4e5f6789abcdef0123456789abcdef01 upstream.
```

Перша з'являється сама, коли команда стабільних гілок бере коміт із mainline без змін. Другу пише людина, яка вручну переробила латку під стару гілку й надіслала окремо, — і в такому разі рядок обов'язковий, бо код у коміті вже не той, що вгорі.

## Категорії на kernel.org

Головна сторінка kernel.org — це таблиця з трьох колонок: позначка лінії, версія, дата. Позначок чотири.

| позначка | приклад на 2 серпня 2026 | що це |
|---|---|---|
| `mainline` | `7.2-rc6` (2026-08-02) | поточний стан головного дерева: або кандидат, або щойно виданий випуск |
| `stable` | `7.1.5` (2026-07-24) | гілка виправлень найсвіжішого випуску; нові виходять приблизно раз на тиждень |
| `longterm` | `6.18.41`, `6.12.100`, `6.6.147`, `6.1.180`, `5.15.213`, `5.10.262` (усі 2026-07-30) | довгострокові гілки: лише важливі виправлення, зате роками |
| `linux-next` | `next-20260731` | учорашній зріз інтеграційного дерева, а не випуск |

`EOL` у цьому переліку немає: це не п'ята позначка, а мітка, яку дописують збоку до рядка гілки, коли її закривають. Гілка з нею ще кілька тижнів висить у таблиці, щоб її встигли помітити ті, хто на ній сидить, а потім зникає.

Третя цифра `longterm`-гілок наочно показує, що таке «роки»: `6.1.180` означає сто вісімдесят добірок виправлень, зроблених від грудня 2022-го.

Окрема таблиця нижче на сторінці перелічує довгострокові гілки з датою кінця підтримки. Усі шість веде та сама пара — Ґреґ Кроа-Гартман і Саша Левін:

| версія | випущено | очікуваний кінець |
|---|---|---|
| 6.18 | 2025-11-30 | груд. 2028 |
| 6.12 | 2024-11-17 | груд. 2028 |
| 6.6 | 2023-10-29 | груд. 2027 |
| 6.1 | 2022-12-11 | груд. 2027 |
| 5.15 | 2021-10-31 | груд. 2026 |
| 5.10 | 2020-12-13 | груд. 2026 |

Слово *projected* у назві колонки — не ввічливість. Сам сайт пояснює, що ці дати не висічені в камені: нова довгострокова гілка починає життя з обіцянкою десь на два роки, а далі строк продовжують, якщо знайшлися ті, кому це потрібно достатньо, щоб платити за супровід. Планувати на дату з цієї колонки як на зобов'язання не можна; планувати на неї як на найгірший випадок — можна цілком.

## Ті самі дані машиною

Усе, що є в таблиці, kernel.org віддає й у машинному вигляді за адресою `https://www.kernel.org/releases.json`. Верхніх ключів два: `releases` — масив, і `latest_stable` — об'єкт з єдиним полем `version`. Один запис виглядає так:

```json
{
  "moniker": "stable",
  "version": "7.1.5",
  "iseol": false,
  "released": { "timestamp": 1784903251, "isodate": "2026-07-24" },
  "source":    "https://cdn.kernel.org/pub/linux/kernel/v7.x/linux-7.1.5.tar.xz",
  "pgp":       "https://cdn.kernel.org/pub/linux/kernel/v7.x/linux-7.1.5.tar.sign",
  "patch": {
    "full":        "https://cdn.kernel.org/pub/linux/kernel/v7.x/patch-7.1.5.xz",
    "incremental": "https://cdn.kernel.org/pub/linux/kernel/v7.x/incr/patch-7.1.4-5.xz"
  },
  "changelog": "https://cdn.kernel.org/pub/linux/kernel/v7.x/ChangeLog-7.1.5",
  "gitweb":    "https://git.kernel.org/stable/h/v7.1.5",
  "diffview":  "https://git.kernel.org/stable/ds/v7.1.5/v7.1.4"
}
```

Поле `moniker` повторює позначку з таблиці, `iseol` каже, чи лінію вже закрито, а `patch.incremental` дає різницю саме між двома сусідніми стабільними випусками — найдешевший спосіб побачити, що змінилося за тиждень.

Мінімальний виклик, який відповідає на питання «які довгострокові гілки живі просто зараз»:

```sh
curl -s https://www.kernel.org/releases.json |
  jq -r '.releases[]
         | select(.moniker == "longterm" and .iseol == false)
         | "\(.version)\t\(.released.isodate)"'
```

## Чотири розбіжності, на яких спотикаються

| здається | насправді |
|---|---|
| `uname -r` показує версію з kernel.org | показує рядок дистрибутивної збірки; базовий випуск усередині може бути зовсім іншим, а сотні перенесених виправлень номер ніяк не відбиває |
| `uname -v` — це версія ядра | це відомості про **складання**: лічильник, прапорці й дата |
| випуск 7.1 має рядок `7.1` | має рядок `7.1.0`; сам тег при цьому зветься `v7.1` |
| у стабільних гілках теж бувають `-rc` | ні: мітка `-rc` існує лише в mainline. Кандидати стабільних випусків живуть в окремому дереві `linux-stable-rc`, тегів на kernel.org не мають і за кілька днів зникають, ставши звичайним `7.1.6` |

Остання розбіжність варта того, щоб її запам'ятати окремо. Мітка `-rc` у номері однозначно каже: це mainline посеред циклу. Її відсутність не каже нічого — випуск це чи стабільний, видно тільки з третьої цифри та з того, у якому дереві лежить тег.
