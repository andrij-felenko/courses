# 🧮 Такти в наносекунди: звідки беруться mult і shift

Перетворення `нс = (такти · mult) >> shift` виглядає як звичайний трюк, аби не ділити. Насправді пара цілих чисел `mult` і `shift` — це розв'язок однієї нерівности, у якій сходяться три речі, на позір незалежні: точність коефіцієнта, розрядність лічильника і те, як довго ядру дозволено взагалі не дивитися на годинник. Порахуймо цю нерівність і підставмо в неї числа двох справжніх джерел часу — архітектурного таймера ARM на 24 МГц із 32-бітним лічильником і TSC на 3 ГГц із 64-бітним.

## Коефіцієнт, який довелося зробити цілим

Точна відповідь очевидна:

```
нс = такти · 10⁹ / f
```

де `f` — частота лічильника в герцах. Множник `10⁹/f` дробовий: для 24 МГц це 41.666… наносекунди на такт, для 3 ГГц — 0.333… . Тримати його в плаваючій комі ядро не може — час читають і з обробників переривань, де регістрами плаваючої коми користуватися заборонено, — а ділити на кожному запиті часу задорого.

Лишається [фіксована кома](book:programming/fixed-point): дробовий коефіцієнт множать на `2^shift`, округлюють до цілого, а зайві розряди відрізають зсувом уже після множення.

```
mult = round(10⁹ · 2^shift / f)
нс   = (такти · mult) >> shift
```

`shift` тут — просто кількість двійкових розрядів, які лишили дробовій частині коефіцієнта. Здавалося б, бери `shift` побільше — коефіцієнт буде точніший. Але придивімося, що саме лежить у проміжному добутку.

## Одна тотожність, з якої випливає все

Підставмо `mult` у добуток і на мить забудьмо про округлення:

```
такти · mult = такти · 10⁹ · 2^shift / f
             = (такти · 10⁹ / f) · 2^shift
             = нс · 2^shift
```

Проміжний добуток — це **та сама відповідь у наносекундах, помножена на 2^shift**. Зсув наприкінці нічого не виправляє; він лише повертає число з дрібніших одиниць у наносекунди. Тобто регістр, у якому лежить добуток, тримає не якусь службову величину, а шукану тривалість — просто в одиницях `2⁻ˢʰⁱᶠᵗ` наносекунди.

Звідси й береться головне обмеження. Добуток обчислюється в 64-бітному регістрі, отже

```
нс_max · 2^shift < 2⁶⁴
```

Частота скоротилася. У нерівності її немає взагалі — швидкий лічильник і повільний тут рівні. Лишилися рівно дві величини: скільки наносекунд треба вміти виразити й скільки розрядів віддано дробовій частині коефіцієнта. Разом вони мусять уміститися в 64:

```
2^shift < 2⁶⁴ / (T_max · 10⁹)
```

де `T_max` — найдовший проміжок у секундах, який дозволено перетворити за одну дію. Ось як ця межа виглядає в числах:

```
T_max      нс_max = T_max·10⁹    розрядів на нс    лишається на shift
──────────────────────────────────────────────────────────────────────
    1 с         1.0 · 10⁹              30                  34
   10 с         1.0 · 10¹⁰             34                  30
   60 с         6.0 · 10¹⁰             36                  28
  178 с         1.78 · 10¹¹            38                  26
  600 с         6.0 · 10¹¹             40                  24
 3600 с         3.6 · 10¹²             42                  22
```

Кожне подвоєння дозволеної паузи забирає рівно один розряд у коефіцієнта. Іншого важеля немає: 64 біти поділено між двома потребами, і додати одній можна тільки відібравши в другої.

![Проміжний добуток такти·mult — це наносекунди, зсунуті на shift розрядів; 64 біти регістра діляться між розрядами наносекунд і розрядами коефіцієнта](/reference/unix-linux/foundations/kernel-timekeeping/img/mult-shift-budget.svg)

*Що довшу паузу треба вміти перетворити, то менше розрядів лишається коефіцієнтові — і третій рядок показує, що буває, коли межу не поставити зовсім.*

> 🔧 **Навіщо це.** Той самий поділ 64 бітів доводиться робити щоразу, коли перетворення з фіксованою комою стоїть на гарячому шляху: у драйвері, що переводить відліки АЦП у вольти, у кодеку, що переводить семпли в мілісекунди. Питання завжди одне й те саме — який найбільший вхід ви зобов'язані перетворити правильно, — і саме воно, а не бажана точність, задає `shift`.

## Скільки коштує округлення

`mult` цілий, а точне значення `10⁹·2^shift/f` — ні. Промах не більший за пів одиниці:

```
|Δmult| ≤ 0.5
відносна похибка = |Δmult| / mult ≤ 0.5 / mult = f / (2 · 10⁹ · 2^shift)
```

Знову виходить залежність лише від двох величин — від частоти й від `shift`. І за однакового `shift` **швидший лічильник дістає гірший коефіцієнт**: його `mult` менший, а отже одна одиниця важить у ньому більше.

Тепер два справжні випадки.

**Архітектурний таймер 24 МГц, 32-бітний лічильник**

```
оберт лічильника = 2³² / 24·10⁶ = 178.96 с        →  T_max = 178 с
2^shift < 2⁶⁴ / (178 · 10⁹) = 1.036·10⁸           →  shift = 26   (2²⁶ = 67108864)

точний коефіцієнт = 10⁹ · 2²⁶ / 24·10⁶ = 2796202666.667
mult              = 2796202667                     (округлення вгору на 0.333)

відносна похибка = +0.333 / 2796202666.667 = 1.19·10⁻¹⁰ = +0.12 ppb
                 = 0.12 нс за секунду = 10.3 мкс за добу
теоретична межа  = 0.5 / mult = 0.18 ppb
```

**TSC 3 ГГц, 64-бітний лічильник**

Спершу візьмімо `T_max` буквально з обороту лічильника й подивімося, що вийде:

```
оберт = (2⁶⁴ − 1) / 3·10⁹ = 6.15·10⁹ с ≈ 195 років
2^shift < 2⁶⁴ / (6.15·10⁹ · 10⁹) = 3.0            →  shift ≤ 1
mult    = round(10⁹ · 2 / 3·10⁹) = round(0.667)   =  1
```

Уже на `shift = 1` коефіцієнт вироджений: замість точних 0.667 у ньому стоїть 1, тобто такт оцінено в пів наносекунди замість 0.333, і годинник побіг би на половину швидше. Та й цього `shift` добір не візьме — він вимагає, щоб `mult` умістився у відведені йому розряди, а тут їх не лишилося зовсім, тож цикл добігає до `shift = 0` із тим самим `mult = 1`. Такт зараховано як цілу наносекунду; годинник утричі швидший за справжній.

Саме тому джерелам з маскою, ширшою за 32 біти, ядро згори кладе `T_max = 600 с`: коментар у `__clocksource_update_freq_scale` називає десять хвилин усе ще розумною величиною. З цією межею числа стають такі:

```
T_max = 600 с
2^shift < 2⁶⁴ / (600 · 10⁹) = 3.07·10⁷            →  shift = 24   (2²⁴ = 16777216)

точний коефіцієнт = 10⁹ · 2²⁴ / 3·10⁹ = 5592405.333
mult              = 5592405                        (округлення вниз на 0.333)

відносна похибка = −0.333 / 5592405.333 = −5.96·10⁻⁸ = −60 ppb
                 = −60 нс за секунду = −5.1 мс за добу
теоретична межа  = 0.5 / mult = 89 ppb
```

Порівняння двох рядків показове: дешевий 24-мегагерцовий лічильник дістає коефіцієнт із похибкою 0.12 ppb, а «кращий» тригігагерцовий TSC — у п'ятсот разів гірший, 60 ppb. Причина не в апаратурі: ширша маска змусила поставити стелю на `T_max`, стеля забрала розряди в `shift`, і коефіцієнт огрубішав.

Чи це багато? [Кварц звичайної машини](book:electronics/frequency-accuracy-ppm) відхиляється від номіналу на десятки мільйонних часток, тобто типові 30 ppm — це в п'ятсот разів більше за наші 0.06 ppm. Служба синхронізації однаково мусить виправляти набагато більше, тож у виправлених годинниках цієї похибки просто не видно. Видно її там, де поправок нема: невиправлений монотонний годинник (`CLOCK_MONOTONIC_RAW`) рахується з номінальним `mult` і несе цей зсув постійно.

І ще одне: похибка — властивість дільби, а не частоти. TSC на рівно 4 ГГц дістає `shift = 23` і `mult = 10⁹·2²³/4·10⁹ = 2097152 = 2²¹` — точно, без залишку, з нульовим округленням. Один процесор швидший за інший на третину, а коефіцієнт у нього ідеальний просто тому, що 4·10⁹ ділить 10⁹·2²³ націло.

## Скільки одиниць mult коштує одна мільйонна частка

Тепер про поправки. Служба синхронізації не переставляє годинника — вона каже, що той поспішає чи відстає на стільки-то мільйонних часток, і ядро відповідає зміною `mult`. Переклад тривіальний, але його наслідки — ні.

```
поправка p (у частках одиниці)  ⟹  mult′ = mult · (1 + p)
Δmult = mult · p

для p = 10⁻⁶ (одна ppm):   Δmult = mult · 10⁻⁶
одна одиниця mult          =      10⁶ / mult   ppm
```

Підставмо обидва наші джерела:

```
                     mult          1 ppm коштує       1 одиниця важить
──────────────────────────────────────────────────────────────────────
24 МГц       2 796 202 667       2796.20 одиниць     0.00036 ppm = 0.36 ppb
3 ГГц TSC        5 592 405          5.59 одиниць     0.179 ppm   = 179 ppb
```

Різниця в п'ятсот разів — це та сама різниця в `shift`, побачена з іншого боку. І вона вже не косметична, бо на TSC поправка мусить лягти на цілу кількість одиниць:

```
запит         24 МГц: Δmult → віддано ppm      3 ГГц: Δmult → віддано ppm
──────────────────────────────────────────────────────────────────────────
  0.1 ppm         279.6 → 280   → 0.10014         0.56 →    1 →   0.1788
  1.0 ppm        2796.2 → 2796  → 0.99993         5.59 →    6 →   1.0729
 12.0 ppm       33554.4 → 33554 → 11.99985       67.11 →   67 →  11.9805
500.0 ppm     1398101.3 → 1398101 → 499.99988   2796.2 → 2796 → 499.9638
```

На 24 МГц округлення поправки не варте згадки. На TSC запит у десяту частку ppm перетворюється на 0.179 ppm — промах у вісімдесят відсотків від того, що просили.

Останній рядок таблиці не випадковий: 500 ppm — це стеля швидкісної поправки, зашита в ядро константою `MAXFREQ` зі значенням 500000 наносекунд на секунду. В одиницях `mult` вона займає 1 398 101 одиницю на 24 МГц і лише 2796 на TSC.

## Як добирають те, чого нема в одиниці mult

Крок у 0.179 ppm завеликий, щоб просто округлити до нього поправку й забути. Тому ядро й не округлює один раз назавжди. Воно тримає накопичену розбіжність між власним часом і тим, якого хоче синхронізація, і на кожному оновленні додає до множника нуль або одиницю:

```c
tk->ntp_err_mult = tk->ntp_error > 0 ? 1 : 0;
mult += tk->ntp_err_mult;
```

Середня швидкість годинника при цьому виходить дробовою, хоч кожне окреме значення множника ціле. Якщо на частці `q` оновлень до множника додано одиницю, а на решті нічого, то середня за часом швидкість дорівнює `mult + q` — тобто ефективна поправка лягає між сусідніми цілими значеннями. Щоб дістати на TSC потрібні 0.05 ppm при кроці 0.179 ppm, досить піднімати множник на одиницю приблизно на 28 % оновлень:

```
q = 0.05 / 0.179 = 0.28
середня поправка = 0.28 · 0.179 = 0.050 ppm
```

Це та сама ідея, що в [сигма-дельта-модуляції](book:electronics/sigma-delta-pwm): величину, дрібнішу за крок квантування, віддають частотою перемикань, а не амплітудою, і накопичувач похибки сам стежить, щоб середнє збіглося. Миттєва швидкість годинника при цьому стрибає між двома сусідніми значеннями, зате інтеграл — тобто саме показ часу — виходить правильний.

Того самого підходу ядро тримається й нижче, на рівні порції накопичення. Проміжок між згортаннями задано в наносекундах (`10⁹/HZ`), а накопичувати треба такти, тож переклад знову дає залишок — і залишок не викидають, а записують:

```c
tmp = NTP_INTERVAL_LENGTH;          /* 10⁹/HZ наносекунд */
tmp <<= clock->shift;
ntpinterval = tmp;
tmp += clock->mult / 2;
do_div(tmp, clock->mult);
interval = tmp;

tk->cycle_interval   = interval;
tk->xtime_interval   = interval * clock->mult;
tk->xtime_remainder  = ntpinterval - tk->xtime_interval;
```

Для TSC на 3 ГГц при `HZ = 250` це дає ось що:

```
NTP_INTERVAL_LENGTH = 10⁹/250 = 4·10⁶ нс
ntpinterval    = 4·10⁶ << 24              = 67108864000000  (зсунуті нс)
cycle_interval = (ntpinterval + mult/2) / mult = 12000001 тактів
xtime_interval = 12000001 · 5592405        = 67108865592405
xtime_remainder = 67108864000000 − 67108865592405 = −1592405
```

Порція накопичення — 12 000 001 такт, а не рівно дванадцять мільйонів; надлишок у 1 592 405 зсунутих наносекунд (менше десятої частки наносекунди) записано в `xtime_remainder` зі знаком мінус, і звідти його забирає наступне обчислення множника. Жодне округлення в цьому ланцюжку не губиться — кожне десь записане.

## Чому зміна mult не зрушує стрілку

Читання часу з бази виглядає так:

```
нс = (offset · mult + xtime_nsec) >> shift
```

де `offset` — такти, що набігли від останнього оновлення, а `xtime_nsec` — збережений час, що лежить у **зсунутих** наносекундах, тобто вже помножений на `2^shift`.

Тепер поставмо вимогу, без якої вся конструкція розсиплеться: у мить зміни множника показ часу не сміє змінитися ані на наносекунду. Інакше кожна поправка синхронізації давала б мікроскопічний стрибок, а монотонний годинник обіцяв не стрибати. Запишімо цю вимогу як рівність і розв'яжімо її:

```
offset · mult + xtime_nsec = offset · (mult + Δ) + xtime_nsec′
xtime_nsec′ = xtime_nsec − offset · Δ
```

Два рядки алгебри — і ось звідки в ядрі береться пара рядків, що завжди стоять поруч:

```c
tk->tkr_mono.mult += mult_adj;
tk->tkr_mono.xtime_nsec -= offset;   /* offset уже помножено на mult_adj */
```

Нова швидкість починає діяти від поточної миті, а все, що встигло набігти по старій, лишається зарахованим саме по старій. Годинник міняє хід, не міняючи показу.

Тут же видно, навіщо базу тримають у зсунутих наносекундах, а не в цілих. По-перше, компенсація `offset · Δ` майже ніколи не кратна `2^shift`, і в цілих наносекундах вона просто не виразилася б. По-друге — і це важливіше — при `HZ = 250` база оновлюється 250 разів на секунду, і якби кожне оновлення відкидало дробову частину наносекунди, набігало б до 250 нс щосекунди, тобто до 0.25 ppm. Це вчетверо більше за округлення коефіцієнта на тому самому TSC — за ту похибку, яку ми досі так старанно рахували.

## Маска: віднімання, якому оберт не заважає

Лічильник рано чи пізно обернеться, а різницю треба брати правильну. Ядро робить це однією операцією:

```c
static inline u64 clocksource_delta(u64 now, u64 last, u64 mask)
{
	u64 ret = (now - last) & mask;

	/* Prevent time going backwards by checking the MSB of mask in
	 * the result. If set, return 0. */
	return ret & ~(mask >> 1) ? 0 : ret;
}
```

Перший рядок — це [модульна арифметика](book:math/modular-arithmetic) у чистому вигляді. Лічильник завширшки `k` бітів живе не на числовій прямій, а в кільці лишків за модулем `2^k`; [беззнакове віднімання](book:programming/unsigned-overflow) у цьому кільці визначене завжди й ніколи не переповнюється. Якщо від моменту `last` минуло `d` тактів, то

```
now ≡ last + d      (mod 2^k)
(now − last) mod 2^k = d,   якщо 0 ≤ d < 2^k
```

Умова тут одна: справжня різниця мусить бути меншою за повний оберт. Тоді відповідь точна — не наближена, не «майже правильна», а точна, і сам оберт узагалі не є подією.

```
маска = 0xFFFFFFFF  (k = 32),  f = 24 МГц
last  = 0xF0000000
now   = 0x10000000                   лічильник уже обернувся

(now − last) & 0xFFFFFFFF = 0x20000000 = 536870912 тактів
у наносекундах: (536870912 · 2796202667) >> 26 = 22369621336 нс ≈ 22.37 с
точне значення: 536870912 / 24·10⁶ · 10⁹      = 22369621333.3 нс
розбіжність:    +2.7 нс на 22.4 с             = +0.12 ppb
```

Останній рядок варто прочитати уважно: розбіжність збіглася з похибкою округлення `mult`, порахованою на початку. Так і має бути — інших джерел похибки в цьому обчисленні немає.

Другий рядок функції додає обмеження, суворіше за модульне. `~(mask >> 1)` — це старший біт маски; якщо він у різниці стоїть, різницю визнають кроком назад і повертають нуль. Тобто корисним лишається не весь оберт, а його половина:

```
2³¹ тактів / 24·10⁶ Гц = 89.478 с        замість 178.96 с
```

*Половина кільця — це не запас про всяк випадок, а межа, за якою «вперед на багато» і «назад на трохи» стають нерозрізненними.*

## Скільки насправді можна мовчати

Тепер зберімо всі межі докупи. Їх три, і жодна з них не є повним обертом лічильника.

Перша — маска: більше ніж `mask` тактів різниця виразити не може. Друга — той самий 64-бітний добуток `такти · mult`, тільки цього разу з погляду тактів, а не наносекунд. Третя — запас: ядро бере половину від того, що вийшло, щоб лишити собі змогу помітити безглузді значення, і закладає одинадцять відсотків множника в обидва боки, бо поправка синхронізації може діяти в будь-який бік.

```c
max_cycles = ULLONG_MAX;
do_div(max_cycles, mult + maxadj);
max_cycles = min(max_cycles, mask);
max_nsecs = clocksource_cyc2ns(max_cycles, mult - maxadj, shift);
max_nsecs >>= 1;
```

**24 МГц, 32 біти**

```
maxadj = 11 % · 2796202667 = 307582293
(2⁶⁴−1) / (mult + maxadj) = 1.8447·10¹⁹ / 3103784960 = 5943306096 тактів
min(5943306096, 2³²−1)    = 4294967295              ← в'яже маска
(4294967295 · 2488620374) >> 26 = 159271703898 нс
>> 1                            =  79635851949 нс   = 79.6 с
```

**3 ГГц TSC, 64 біти**

```
maxadj = 11 % · 5592405 = 615164
(2⁶⁴−1) / (mult + maxadj) = 1.8447·10¹⁹ / 6207569 = 2971653488460 тактів  (≈ 990 с)
min(2971653488460, 2⁶⁴−1) = 2971653488460          ← в'яже 64-бітний добуток
(2971653488460 · 4977241) >> 24 = 881590579781 нс
>> 1                            = 440795289890 нс  = 440.8 с
```

Два випадки, дві різні причини. На вузькому лічильнику в'яже оберт, і замість наївних 179 секунд лишається 79.6. На широкому лічильнику оберт не в'яже взагалі — його 195 років не мають жодного значення, бо перетворення захлинається на 64-бітному добутку задовго до того. Ядро мусить оновити базу принаймні раз на сім хвилин навіть на тому TSC, якого номінально вистачило б на два сторіччя.

## Прочитати конструкцію назад із журналу завантаження

Наприкінці реєстрації джерела часу ядро друкує рядок, у якому лежать саме ті два числа, що ми щойно рахували:

```
tsc: mask: 0xffffffffffffffff max_cycles: 0x2b3e459bf4c, max_idle_ns: 440795289890 ns
```

`mult` і `shift` тут не надруковано, але їх можна відновити — уся арифметика оборотна:

```
max_cycles = 0x2b3e459bf4c = 2971653488460

2⁶⁴ / max_cycles = 18446744073709551616 / 2971653488460 = 6207569 = mult + maxadj
mult + 0.11·mult = 1.11 · mult = 6207569
mult   = 6207569 / 1.11 = 5592404.5   →  5592405
maxadj = 11 % · 5592405 = 615164

2^shift = max_cycles · (mult − maxadj) / (2 · max_idle_ns)
        = 2971653488460 · 4977241 / 881590579780
        = 16777216 = 2²⁴                     →  shift = 24

f = 10⁹ · 2^shift / mult = 10⁹ · 16777216 / 5592405 = 3.0000002·10⁹ Гц
```

Із двох чисел у журналі відновилися і коефіцієнт, і зсув, і частота лічильника. Причому відновлена частота відрізняється від справжніх 3 ГГц рівно на 60 ppb — на ту саму похибку округлення `mult`, що народилася разом із вибором `shift`. Точнішого числа з `mult` дістати неможливо в принципі: у ньому просто немає стільки розрядів, і саме через це ядро ніколи не покладається на номінальний множник як на еталон, а тримає поруч живу поправку.
