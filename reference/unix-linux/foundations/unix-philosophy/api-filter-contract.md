# 📋 Контракт програми-фільтра: що стирчить назовні

Це сторінка-контракт: усе, що чужий конвеєр бачить у вашій програмі — три дескриптори, форма операндів, код виходу, реакція на `SIGPIPE`, перевірка терміналу, режим буферизації й вплив локалі — зведено в таблиці з мінімальними прикладами, щоб можна було звірити свою програму рядок за рядком, а не пригадувати. Кожне з цих правил має ту саму причину: наступну ланку конвеєра писала інша людина, вона вашого коду не читала й читати не буде.

## Уся поверхня на одній таблиці

Незалежно від того, що програма робить усередині, назовні стирчить рівно сім речей. Усе решта — приватна справа реалізації.

| Що | Напрямок | Хто це підклав | Що туди можна класти |
| --- | --- | --- | --- |
| **fd 0** (stdin) | вхід, потоком | той, хто запустив | — (читаєте ви) |
| **fd 1** (stdout) | вихід, потоком | той, хто запустив | **лише результат** — те, що має розбирати наступна ланка |
| **fd 2** (stderr) | вихід, потоком | той, хто запустив | помилки, попередження, прогрес, розмова з людиною |
| **argv** | вхід, одноразово | оболонка після [розкриття й лапок](book:unix-linux/expansion-and-quoting) | ключі й операнди |
| **оточення** | вхід, одноразово | успадковано від батька | типові значення: `LC_*`, `TMPDIR`, `NO_COLOR` |
| **код виходу** | вихід, наприкінці | — | одне число: вийшло / штатне «ні» / зламалося |
| **сигнали** | вхід, будь-коли | ядро, сусід по конвеєру, людина | `SIGPIPE`, `SIGINT`, `SIGTERM` |

Правило, яке пояснює половину решти сторінки: **у fd 1 не можна класти нічого, крім даних**. Ані «Обробляю файл 3 з 12…», ані порожній рядок «для краси», ані шапку таблиці, якщо її не просили. Усе це стане входом наступної програми, і вона сумлінно його обробить.

## Три дескриптори: хто що несе

| Дескриптор | Куди типово дивиться | Чи входить у конвеєр | Що з ним може статися |
| --- | --- | --- | --- |
| 0 | термінал або попередня ланка | так — це вихід попередньої ланки | може бути порожнім, закритим, непридатним для перемотування |
| 1 | термінал, файл або наступна ланка | так — це вхід наступної ланки | читач може піти раніше → `SIGPIPE`/`EPIPE` |
| 2 | термінал | **ні** — іде повз | може бути перенаправлений у файл або в той самий файл, що й fd 1 |

Три висновки, які ламають програми найчастіше:

- **fd 2 — не обов'язково термінал.** `prog 2>log` цілком законне. Тому не можна припускати, що діагностику читає людина: `\r`-перемальовування прогрес-бару у файлі дає нечитабельне місиво.
- **fd 1 і fd 2 можуть бути одним і тим самим файлом.** `prog >out 2>&1` дає обом дескрипторам спільний [опис відкритого файлу](book:unix-linux/open-file-description) — тобто одну позицію запису на двох. Порядок рядків у результаті тоді визначає **буферизація**, а не порядок ваших викликів — типова причина «чому помилка в лозі стоїть раніше за рядок, який її спричинив».
- **fd 1 може бути закритим.** `prog >&-` — і перший же `write(1, …)` повертає `EBADF`. Правильна реакція — не мовчати, а завершитися ненульовим кодом.

## Операнди: файли, «`-`» і «`--`»

Форму аргументів [POSIX](book:unix-linux/posix-standard) описує не як вимогу, а як настанови (Utility Syntax Guidelines). Для фільтра вагомі дві з них — десята й тринадцята.

| Форма виклику | Що мусить статися |
| --- | --- |
| `prog` (без операндів) | читати **стандартний ввід** — не питати, не падати, не друкувати довідку |
| `prog f1 f2` | обробити файли по черзі, наче це один потік |
| `prog -` | у цьому місці послідовності — стандартний ввід (Guideline 13) |
| `prog a - b` | файл `a`, потім стандартний ввід, потім файл `b` |
| `prog -- -x` | усе після `--` — операнди, навіть якщо починається з дефіса (Guideline 10) |
| `prog ./-` | справжній файл на ім'я `-`; іншого способу до нього дістатися немає |

Точне формулювання десятої настанови: перший аргумент `--`, який сам не є значенням ключа, слід приймати як межу кінця ключів. Тринадцята стосується `-`: для утиліт, чиї операнди — імена файлів, `-` слід уживати для позначення стандартного вводу (або стандартного виводу, коли з контексту ясно, що йдеться про вихідний файл).

**Чому `--` — питання безпеки, а не охайності.**

```sh
f='-rf'                 # ім'я файлу, що прийшло ззовні
rm "$f"                 # rm бачить ключ -rf, а не ім'я
rm -- "$f"              # rm бачить операнд

grep "$pattern" file    # зразок «-v» перетворюється на ключ
grep -- "$pattern" file # зразок лишається зразком
```

Обробник ключів у самій програмі мусить це підтримувати, тому розбір argv має рівно три правила зупинки: аргумент `--` (з'їсти й вийти з циклу), аргумент, що не починається з `-`, і аргумент рівно `-` (це операнд, а не ключ).

Дві межі, за які виходити не варто. `-` як «стандартний ввід» доречний **лише** там, де операнд і так означає файл: `tar -f -`, `curl -o -`, `diff a -`. Якщо ваша програма файлів не приймає, вигадувати їй `-` не треба — угода не універсальна, і `cd -` (попередній каталог) чи `git checkout -` живуть за іншим правилом. І друге: розбирайте ключі стандартним `getopt(3)`/`getopt_long(3)`, а не власним циклом — самописний розбір майже завжди мовчки провалює `--`, злиті короткі ключі (`-abc`) і від'ємні числа як значення.

## Коди виходу

Код виходу — це не «число, яке я захотів повернути», а **відповідь на одне питання**: чи можна покластися на те, що лежить у fd 1. Тому шкала в добре поведених програм трирівнева, і її канонічні зразки — `grep` і `diff`.

| Код | Значення | `grep` | `diff` / `cmp` |
| --- | --- | --- | --- |
| **0** | так, усе гаразд | рядок знайдено | файли однакові |
| **1** | **штатне «ні»** — не помилка | збігів немає | файли різні |
| **2** | помилка виконання | немає файлу, поганий ключ, збій читання | не зміг прочитати вхід |

Розрізнення «1 = ні» і «2 = зламалося» — те, заради чого варто писати цю таблицю в документації своєї програми. Без нього скрипт не може відрізнити «нічого не знайшлося» від «пошук не відбувся», і обидва випадки тихо зливаються в один.

Поверх цієї шкали оболонка додає свої значення — вони не належать вашій програмі, але з'являються там, де на неї чекають:

| Код | Хто його ставить | Що означає |
| --- | --- | --- |
| **126** | оболонка | файл знайдено, але він не виконуваний |
| **127** | оболонка | команду не знайдено в `PATH` |
| **128 + n** | оболонка | процес **убито сигналом** `n`; сам процес коду не повертав |
| **130** | оболонка | 128 + 2 — `SIGINT`, тобто Ctrl-C |
| **141** | оболонка | 128 + 13 — `SIGPIPE` |
| **143** | оболонка | 128 + 15 — `SIGTERM` |

Три пастки навколо цього числа:

- **Виживають лише молодші 8 бітів.** `exit(256)` система віддасть як 0, `exit(-1)` — як 255. Тому не можна повертати кодом виходу кількість чогось: тисяча знайдених рядків стане кодом 232, а рівно 256 знайдених — успіхом.
- **Код конвеєра — це код останньої ланки.** У `grep шаблон файл | head -3` падіння `grep` невидиме. Латка — `set -o pipefail` (у POSIX його додали аж у виданні 2024 року, тож у старих `dash` його немає) або масив `PIPESTATUS` у bash.
- **`grep -q` навмисно порушує власну шкалу**: якщо збіг знайдено, він виходить із 0, навіть якщо дорогою сталася помилка. Це задокументована відмінність, а не хиба, і саме тому `grep -q` не годиться там, де треба відрізнити «немає» від «не зміг».

Окремим світом живе `sysexits.h` із BSD (`EX_USAGE` 64, `EX_DATAERR` 65, `EX_NOINPUT` 66, …, `EX_CONFIG` 78). Ця схема виросла з потреб `sendmail`, за межами поштових інструментів майже не вживається, і GNU-утиліти її не дотримуються — покладатися на конкретні числа з неї не варто.

## SIGPIPE і EPIPE: коли наступна ланка пішла раніше

Коли читач каналу закриває свій кінець, а ви пишете далі, ядро мусить якось вас зупинити. Що саме станеться — залежить від [диспозиції](book:unix-linux/signal-disposition) сигналу `SIGPIPE` у вашому процесі.

![Запис у канал без читача розгалужується за диспозицією SIGPIPE: типова дія вбиває процес, ігнорування перетворює це на помилку EPIPE](/reference/unix-linux/foundations/unix-philosophy/img/filter-sigpipe-branch.svg)

*Обидві гілки правильні — але друга вимагає від вас коду, а перша ні.*

| Диспозиція `SIGPIPE` | Що робить `write()` | Що бачить оболонка |
| --- | --- | --- |
| типова дія (`SIG_DFL`) | не повертається — процес гине | 141 |
| `SIG_IGN` або власний обробник | повертає −1, `errno = EPIPE` (на Linux 32) | те, що ви самі повернете |

**Найтихіша пастка тут — успадкування.** Диспозиція `SIG_IGN` переживає `exec()`. Якщо ваш фільтр запустили з-під програми, яка десь раніше зробила `signal(SIGPIPE, SIG_IGN)` — а так роблять майже всі мережеві демони, оркестратори й раннери CI, — то `SIGPIPE` вас не вб'є: `write()` просто поверне −1 з `EPIPE`. Наївний цикл, який результату `write()` не перевіряє, у такому оточенні не завершиться взагалі — читач давно пішов, а програма крутиться вічно й палить процесор. Тому фільтр, що поважає себе, або явно повертає типову диспозицію, або чесно перевіряє `EPIPE`.

```c
signal(SIGPIPE, SIG_DFL);          /* хай конвеєр згортає нас типово */

/* якщо ж SIGPIPE все-таки заблоковано — помилку треба впіймати */
if (write(1, buf, n) < 0) {
    if (errno == EPIPE) return 0;  /* читач пішов; це не наша невдача */
    perror("write");
    return 2;
}
```

Дві дрібниці, без яких перевірка неповна. `write()` має право повернути **менше** байтів, ніж просили, — цикл обов'язковий. І `write()` має право перерватися сигналом, повернувши [`EINTR`](book:unix-linux/eintr-and-restart) — тоді запис треба повторити, а не зарахувати як помилку.

Якщо ви пишете не `write()`, а `printf()`, помилка спливе пізніше: `stdio` могло просто скласти байти в буфер. Тому фільтр закінчується не `return`, а перевіркою:

```c
if (fclose(stdout) != 0 && errno != EPIPE) {
    fprintf(stderr, "prog: не вдалося дописати вивід: %s\n", strerror(errno));
    return 2;
}
```

Саме тут виявляється і `EPIPE`, і `ENOSPC` — «диск повний» на останньому, ще не скинутому буфері. Програма, яка цього не перевіряє, тихо повертає 0, віддавши обрізаний результат.

## isatty: що можна робити лише в термінал

`isatty(fd)` відповідає на одне питання: чи за цим дескриптором стоїть [термінал](book:unix-linux/tty-and-termios). В оболонці те саме питання ставить `test -t`.

| Перевірка | Питання | На що впливає |
| --- | --- | --- |
| `isatty(1)` / `[ -t 1 ]` | результат читає людина? | колір, вирівнювання колонок, заголовки таблиць |
| `isatty(2)` / `[ -t 2 ]` | діагностику читає людина? | прогрес-бар, перемальовування через `\r` |
| `isatty(0)` / `[ -t 0 ]` | вхід інтерактивний? | чи питати підтвердження, чи чекати введення |

Порядок рішень про колір усталився такий і має саме такий пріоритет:

| Умова | Результат |
| --- | --- |
| `--color=never` | без кольору — завжди |
| `--color=always` (або `CLICOLOR_FORCE`) | з кольором — навіть у канал |
| `NO_COLOR` присутня й непорожня | без кольору (неформальна угода, запропонована 2017 року; `no-color.org`) |
| `TERM=dumb` або `TERM` не задано | без керівних послідовностей |
| `--color=auto` (типово) | колір ⟺ `isatty(1)` |

Точне формулювання угоди `NO_COLOR`: програма, яка типово додає ANSI-колір, має перевіряти змінну `NO_COLOR` і, коли та присутня й не порожня — **незалежно від значення** — кольору не додавати.

**Головне обмеження.** За `isatty` можна міняти **оформлення**, але не **формат даних**. Класичний контрприклад — `ls`: у термінал він виводить кілька колонок, у канал — по одному імені на рядок. Це зручно людині й саме тому робить `ls | …` ненадійним у скриптах: конвеєр отримує не те, що бачив автор, коли перевіряв команду руками. Якщо вивід треба розбирати, беруть `find`, а не `ls`.

## Буферизація stdio: чому вивід «зависає»

Між вашим `printf()` і системним викликом стоїть буфер бібліотеки: вона накопичує байти й віддає їх пачкою, щоб не бігати до ядра на кожен рядок ([як улаштована буферизація stdio](book:unix-linux/stdio-buffering)). Для контракту фільтра важить один-єдиний наслідок — **режим бібліотека вибирає сама**, подивившись, куди вказує fd 1. Звідси й найчастіша скарга на власну програму: у терміналі все з'являлося вчасно, а в конвеєрі «зависло».

![Одна й та сама програма: у термінал рядки з'являються по одному, у канал — усі разом наприкінці](/reference/unix-linux/foundations/unix-philosophy/img/filter-buffering-modes.svg)

*Різниця не в коді й не в даних: перед першим виводом `stdio` спитала в системи, чи fd 1 — термінал, і мовчки вибрала режим.*

Стандарт C ставить типові режими так:

| Потік | Куди дивиться | Режим | Байти йдуть далі, коли |
| --- | --- | --- | --- |
| `stdout` | термінал | порядковий (`_IOLBF`) | трапився `\n` |
| `stdout` | канал, файл, сокет | **поблоковий** (`_IOFBF`, зазвичай 4 КіБ) | буфер повний, `fflush()` або `exit()` |
| `stderr` | будь-куди | не повнобуферний (на практиці — без буфера) | одразу |
| `stdin` | те саме правило, що в `stdout` | порядковий із термінала, поблоковий з файлу чи каналу | — |

Звідси всі симптоми: `prog | grep щось` мовчить хвилину, а тоді вивалює все разом; `prog >log 2>&1` дає перемішаний порядок рядків; `prog | tee log` не показує нічого в реальному часі. Жодного збою немає — просто ніхто не наказував скидати буфер.

| Кого треба переконати | Як |
| --- | --- |
| власний код | `setvbuf(stdout, NULL, _IOLBF, 0)` **до першого виводу**, або `fflush(stdout)` після рядка |
| чужу програму на C | `stdbuf -oL prog` (порядково) чи `stdbuf -o0 prog` (без буфера) |
| `grep` | `--line-buffered` |
| `sed` | `-u` |
| `awk` | виклик `fflush()` у коді |
| Python | `python -u` або `PYTHONUNBUFFERED=1` |
| програму, що не піддається | `script -qec 'prog' /dev/null` або `unbuffer prog` — дати їй псевдотермінал |

Межі `stdbuf` варто знати наперед: він працює через `LD_PRELOAD`, тобто не діє на статично злінковані та setuid-програми, на середовища без C-`stdio` (Go, Rust, Java) і на програми, які самі викликають `setvbuf`. Про останнє в документації самого `stdbuf` є окреме застереження, і за приклад такої програми там узято `tee`.

Ще дві пастки того самого буфера. По-перше, `fork()` **копіює** незлитий буфер: якщо перед розгалуженням не зробити `fflush()`, ті самі рядки вийдуть двічі. По-друге, `_exit()`, `abort()` і смерть від сигналу буфер **не** скидають — тому програма, вбита `SIGPIPE`, губить те, що встигла накопичити, і це нормально, а програма, яка сама викликала `_exit()` замість `exit()`, губить результат мовчки.

> 🔧 **Навіщо це.** Ваш фільтр перевіряють у терміналі, а живе він у конвеєрі — тобто в **іншому** режимі буферизації, ніж той, у якому ви його бачили. Тому будь-яку програму, що виводить дані поступово (лог, монітор, довгий обхід), тестуйте не так `prog`, а так: `prog | cat`. Якщо в другому випадку рядки перестали з'являтися вчасно — ви щойно знайшли те, на що поскаржиться перший же користувач.

## Локаль: одна змінна, що змінює порядок

Локаль — це набір змінних оточення, які кажуть бібліотеці, за якими правилами порівнювати рядки, що вважати літерою й де ставити десятковий роздільник ([локаль і порядок зіставлення](book:unix-linux/locale-and-collation)). Для фільтра з цього випливає одна незручна річ: **однаковий вхід може дати різний вихід на різних машинах**, і жодного повідомлення про це не буде.

| Змінна | Що визначає | Пріоритет |
| --- | --- | --- |
| `LC_ALL` | усе; перекриває решту | найвищий |
| `LC_COLLATE` | порядок порівняння рядків: `sort`, діапазони в зразках | ↓ |
| `LC_CTYPE` | що є літерою, як байти складаються в символи | ↓ |
| `LC_NUMERIC` | десятковий роздільник у `printf`, `awk` | ↓ |
| `LC_MESSAGES` | мова діагностики | ↓ |
| `LANG` | типове значення для всіх `LC_*`, які не задані окремо | найнижчий |

Різниця видима на трьох рядках:

```sh
$ printf 'Banana\napple\nCherry\n' | LC_ALL=C sort
Banana
Cherry
apple            # байтовий порядок: усі великі літери йдуть перед малими

$ printf 'Banana\napple\nCherry\n' | LC_ALL=en_US.UTF-8 sort
apple
Banana
Cherry           # регістр на першому рівні порівняння не враховується
```

Правила, які з цього випливають:

- **Скрипт, що порівнює або зіставляє, прибиває `LC_ALL=C`.** Порядок стає байтовим — стабільним між машинами й помітно швидшим, бо не треба будувати ключі зіставлення.
- **`sort`, `join`, `comm` і `uniq` мусять бути в одній локалі.** `join` і `comm` вимагають, щоб вхід був відсортований **їхнім** порядком; локаль, що змінилася між кроками конвеєра, дає мовчки неповний результат без жодного повідомлення.
- **Діапазони `[a-z]` поза локаллю C — невизначені.** POSIX прямо лишає їхню поведінку неозначеною за межами локалі C, і в деяких локалях `[a-z]` захоплює й великі літери. Безпечна форма — класи символів: `[[:lower:]]`, `[[:digit:]]`, `[[:space:]]`.
- **`LC_CTYPE` вирішує, чи ваш вхід — [UTF-8](book:programming/ascii-utf8) чи послідовність байтів.** У локалі C `wc -m` порахує байти, а `grep '.'` зіставить один байт замість символу.
- **Числа для машини друкують у локалі C.** `printf '%.2f'` у німецькій локалі дає `3,14`, і наступна ланка конвеєра цього не прочитає.
- **Вивід для людини лишається в локалі користувача.** Тому `setlocale(LC_ALL, "")` на початку програми потрібен: без нього ваша програма ігнорує налаштування системи взагалі.

## Нульовий роздільник: коли ім'я містить пробіл або перенос

Універсальний текстовий формат не має способу екранувати власний роздільник, а в іменах файлів Unix дозволено все, крім `/` і нульового байта. Саме тому нульовий байт узяли за роздільник там, де двозначність неприпустима: він єдиний **не може** трапитися в даних.

| Інструмент | Ключ | Що змінює |
| --- | --- | --- |
| `find` | `-print0` | імена розділені `\0`, а не `\n` |
| `xargs` | `-0`, `--null` | читає аргументи, розділені `\0` |
| `xargs` | `-r`, `--no-run-if-empty` | не запускати команду, коли вхід порожній |
| `sort` | `-z`, `--zero-terminated` | і вхід, і вихід — `\0`-термінований |
| `grep` | `-z`, `--null-data` | «рядок» — це все до `\0` |
| `grep` | `-Z`, `--null` | `\0` після імені файлу (разом із `-l`, `-H`) |
| `sed` | `-z`, `--null-data` | те саме, що в `grep -z` |
| `uniq`, `cut`, `head`, `tail` | `-z` | `\0` замість `\n` |
| `du` | `-0`, `--null` | `\0` після кожного запису |
| `read` (bash) | `-d ''` | читати до `\0` |
| `mapfile` (bash ≥ 4.4) | `-d ''` | заповнити масив `\0`-розділеними значеннями |

Дві канонічні безпечні форми:

```sh
# найкоротша: усе на xargs
find . -type f -name '*.log' -print0 | xargs -0 -r gzip --

# коли для кожного імені потрібна логіка
find . -type f -print0 |
  while IFS= read -r -d '' f; do
      printf '%s\n' "$f"
  done
```

Тут працюють одразу три правила цієї сторінки: `-print0`/`-0` прибирають двозначність роздільника, `--` захищає імена, що починаються з дефіса, а `IFS=` разом із `-r` не дає оболонці порізати ім'я по пробілах і поламати зворотні похилі.

Варто пам'ятати, що `-print0`, `-0` і `-z` — розширення GNU й BSD, а не [POSIX](book:unix-linux/posix-standard). Переносний спосіб обійтися без них — вбудований запуск, який передає імена як окремі аргументи, оминаючи текстовий потік узагалі:

```sh
find . -type f -name '*.log' -exec gzip -- {} +
```

## Мінімальний фільтр, що тримає весь контракт

Програма друкує рядки, довші за поріг. Вона нічого особливого не робить — вона лише **виконує все, про що йшлося вище**, і саме тому її можна поставити в чужий конвеєр не соромлячись.

```c
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <locale.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static size_t limit  = 80;   /* поріг довжини рядка */
static int    color  = 0;    /* чи фарбувати результат */
static int    found  = 0;    /* чи спрацювало хоч раз  */
static int    failed = 0;    /* чи була помилка        */

static void run(FILE *in, const char *name)
{
    char   *line = NULL;
    size_t  cap  = 0;
    ssize_t n;

    while ((n = getline(&line, &cap, in)) > 0) {
        if (line[n - 1] == '\n') line[--n] = '\0';
        if ((size_t)n <= limit) continue;
        found = 1;
        if (color) printf("\033[1m%s\033[0m\n", line);
        else       printf("%s\n", line);
    }
    if (ferror(in)) {                       /* збій читання — це код 2 */
        fprintf(stderr, "long: %s: %s\n", name, strerror(errno));
        failed = 1;
    }
    free(line);
}

int main(int argc, char **argv)
{
    const char *STDIN_NAME = "(стандартний ввід)";
    int i = 1;

    setlocale(LC_ALL, "");                  /* поважати локаль користувача */
    signal(SIGPIPE, SIG_DFL);               /* не покладатися на успадковану */
    color = isatty(1) && !getenv("NO_COLOR");

    for (; i < argc; i++) {                 /* ключі — до першого операнда */
        if (strcmp(argv[i], "--") == 0) { i++; break; }
        if (argv[i][0] != '-' || argv[i][1] == '\0') break;   /* «-» — операнд */
        if (argv[i][1] == 'n' && argv[i][2])
            limit = strtoul(argv[i] + 2, NULL, 10);
        else {
            fprintf(stderr, "вжиток: long [-nЧИСЛО] [--] [файл...]\n");
            return 2;                       /* 2 — помилка вжитку */
        }
    }

    if (i == argc)                          /* операндів немає → stdin */
        run(stdin, STDIN_NAME);

    for (; i < argc; i++) {
        if (strcmp(argv[i], "-") == 0) { run(stdin, STDIN_NAME); continue; }
        FILE *f = fopen(argv[i], "r");
        if (!f) {
            fprintf(stderr, "long: %s: %s\n", argv[i], strerror(errno));
            failed = 1;                     /* один поганий файл ≠ кінець роботи */
            continue;
        }
        run(f, argv[i]);
        fclose(f);
    }

    if (fclose(stdout) != 0 && errno != EPIPE) {   /* тут спливає ENOSPC */
        fprintf(stderr, "long: не вдалося дописати вивід: %s\n", strerror(errno));
        failed = 1;
    }
    return failed ? 2 : (found ? 0 : 1);    /* шкала grep */
}
```

Що саме тут виконано з контракту: читання зі stdin без операндів, `-` як стандартний ввід, `--` як кінець ключів, діагностика в fd 2 і тільки туди, колір лише за `isatty(1)` і за відсутності `NO_COLOR`, явна типова диспозиція `SIGPIPE`, перевірка `ferror` і `fclose(stdout)`, повага до локалі, трирівнева шкала виходу. Розбір ключів тут навмисно спрощений — у справжній програмі його місце займає `getopt_long()`.

## Той самий контракт у різних середовищах

Правила однакові для всіх, а от типова поведінка бібліотеки під ними — різна, і саме на цьому спотикаються, переписуючи фільтр іншою мовою.

| | C (`stdio`) | Python | Go | Rust |
| --- | --- | --- | --- | --- |
| **`SIGPIPE` типово** | типова дія: процес гине | рантайм ставить `SIG_IGN` → `BrokenPipeError` | fd 1 і 2 — гине з `SIGPIPE`; решта fd — `write` дає `EPIPE` | рантайм ставить `SIG_IGN` ще до `main` (так із 2014 р.) |
| **симптом, коли читач пішов** | тихе завершення, код 141 | виняток `BrokenPipeError: [Errno 32]` | тихе завершення | паніка на друку |
| **буферизація stdout** | порядкова в термінал, поблокова інакше | те саме | буфера немає: кожен `Write` — системний виклик | завжди порядкова (`LineWriter`) |
| **як вимкнути буфер** | `setvbuf` | `-u`, `PYTHONUNBUFFERED=1` | не потрібно (буфер додають самі, `bufio`) | не потрібно |
| **необроблена помилка → код** | той, що ви повернули | `1` | паніка → `2` | паніка → `101` |

Практичний висновок звідси один: **перевіряйте свій фільтр саме командою `prog | head -1`**, якою б мовою його не написали. Вона за секунду показує і поведінку при обриві, і те, чи не забули ви про буфер.

## Контрольний список

| Питання | Правильна відповідь |
| --- | --- |
| Операндів немає — що робить програма? | читає stdin |
| Що йде у fd 1? | лише дані; жодного прогресу й привітань |
| Що йде у fd 2? | усе, що адресоване людині |
| `-` серед операндів? | стандартний ввід |
| `--`? | кінець ключів |
| Знайшлося / не знайшлося / зламалося? | 0 / 1 / 2, і це записано в документації |
| Читач конвеєра пішов? | тихо завершитися, не лаятися |
| Колір і прогрес? | лише за `isatty` і без `NO_COLOR` |
| Вивід у канал з'являється вчасно? | перевірено запуском у конвеєр із `cat` |
| Сортування й зіставлення? | під `LC_ALL=C`, класи замість діапазонів |
| Імена файлів у потоці? | `-print0` / `-0`, або `-exec … {} +` |
| Останній `fclose(stdout)` перевірено? | так — інакше «диск повний» пройде як успіх |
