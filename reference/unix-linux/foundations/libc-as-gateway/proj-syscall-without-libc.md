# ⚙️ Системний виклик власноруч: три рівні без обгортки

Вивести рядок у дескриптор 1 і завершитися — і жодного `printf`, `write` чи іншої функції бібліотеки на шляху до ядра. Задача навмисно дрібна, бо цікаве не в ній: на кожному з трьох рівнів ми забираємо ще один шар libc й записуємо, що довелося дописати натомість. Наприкінці рахуємо переходи в ядро — і виявляється, що шлюз коштує майже нічого, а дорога зовсім інша річ.

Усе нижче — x86-64 Linux, і це не випадковість. Перший і третій рівні прив'язані до архітектури за самою своєю природою; саме тому їх руками зазвичай і не пишуть.

## Рівень 1: пастка просто в тілі функції на C

Компілятор мови C не вміє видавати інструкцію `syscall` сам, зате вміє вставити в потік свого коду чужий текст асемблера й погодити його з рештою — через [вбудований асемблер](book:programming/inline-assembly). Домовитися треба про три речі: у яких регістрах будуть входи, у якому регістрі забирати вихід і що інструкція псує.

```c
#include <stddef.h>

static long raw_syscall3(long n, long a1, long a2, long a3)
{
    long ret;
    __asm__ volatile (
        "syscall"
        : "=a" (ret)                                   /* вихід — rax */
        : "a" (n), "D" (a1), "S" (a2), "d" (a3)        /* rax, rdi, rsi, rdx */
        : "rcx", "r11", "memory");                     /* що псує інструкція */
    return ret;
}
```

Літери в обмеженнях — це імена регістрів, а не абревіатури слів: `a` — `rax`, `D` — `rdi`, `S` — `rsi`, `d` — `rdx`. Ядро чекає номер виклику в `rax`, а перші три аргументи там само, де їх лишає звичайний виклик функції.

Два записи в останньому рядку варті окремої уваги, бо без них програма зламається не одразу й не завжди.

`"rcx", "r11"` — інструкція `syscall` не кладе адресу повернення на стек: вона кладе її в `rcx`, а прапорці процесора в `r11`. Обидва регістри після пастки містять сміття. Компілятор про це не здогадається — якщо йому не сказати, він спокійно триматиме там свою змінну через увесь виклик.

`"memory"` — обіцянка компіляторові, що вставка може читати й писати будь-яку пам'ять. Без неї він має право вважати, що рядок, адресу якого ми передали в `rsi`, ніхто не читає, і не виштовхнути його значення з регістра в пам'ять до пастки. Ядро прочитає з тієї адреси те, що там лежало раніше.

Слово `volatile` тримає вставку на місці, коли її результат нікому не потрібен: без нього оптимізатор має повне право викинути виклик, від якого «нічого не залежить».

Тепер сам вивід:

```c
static const char msg[] = "Привіт із пастки\n";

long r = raw_syscall3(1, 1, (long)msg, sizeof msg - 1);   /* 1 — номер write */
```

Перша одиниця — номер системного виклику `write` на x86-64; друга — дескриптор. Довжину беремо як `sizeof msg - 1`, щоб не рахувати байти багатобайтових літер руками.

А тепер спитаймо ядро про завідомо неможливе:

```c
long bad = raw_syscall3(1, -1, (long)msg, sizeof msg - 1);
/* bad == -9, і більше нічого: 9 — це EBADF, «поганий дескриптор» */
```

Ядро повернуло **одне** число, у якому змішані результат і причина невдачі. Перетворити його на звичну для мови C форму — робота, яку ми щойно забрали в бібліотеки, тож робимо її самі:

```c
#include <errno.h>

static long finish(long r)
{
    if ((unsigned long)r >= (unsigned long)-4095) {   /* тобто −4095 … −1 */
        errno = (int)(-r);
        return -1;
    }
    return r;
}
```

Порівняння тут **беззнакове**, і це не примха. Ядро вважає помилкою рівно 4095 найбільших значень беззнакового діапазону — саме так записана перевірка `IS_ERR_VALUE` у самому ядрі, де межа задана як `MAX_ERRNO`, рівна 4095. Знакова перевірка `r < 0` дала б той самий результат для `write`, але зламалася б на `mmap`: адресу, у якої стоїть старший біт, вона оголосила б помилкою, хоча це цілком законна пам'ять.

Четвертий аргумент вимагає ще одного трюку, бо `rcx` уже зайнято під адресу повернення й ядро чекає його в `r10` — регістрі, для якого в GCC немає окремої літери-обмеження. Виручає прив'язка змінної до конкретного регістра:

```c
static long raw_syscall4(long n, long a1, long a2, long a3, long a4)
{
    long ret;
    register long r10 __asm__("r10") = a4;
    __asm__ volatile ("syscall"
        : "=a" (ret)
        : "a" (n), "D" (a1), "S" (a2), "d" (a3), "r" (r10)
        : "rcx", "r11", "memory");
    return ret;
}
```

Це той самий текст, що лежить у musl в `arch/x86_64/syscall_arch.h`, — приємно бачити, що «власноруч» тут збігається зі «як у справжній бібліотеці».

Але програма досі цілком libc-ова. У неї є `main`, є `errno` з окремою коміркою на кожен потік, є нормальне завершення з поверненням коду. Ми обійшли лише одну функцію-обгортку — найтоншу з усього, що бібліотека робить.

## Рівень 2: `syscall()` — універсальні двері, які теж належать libc

Той самий виклик можна зробити, не пишучи ані рядка асемблера. У libc є функція, яка приймає номер і аргументи й сама розкладає їх за правилами поточної архітектури:

```c
#include <unistd.h>
#include <sys/syscall.h>
#include <errno.h>
#include <stdio.h>

int main(void)
{
    static const char msg[] = "Привіт із загальних дверей\n";

    long r = syscall(SYS_write, 1, msg, sizeof msg - 1);
    if (r == -1)
        fprintf(stderr, "не вийшло: errno=%d\n", errno);
    return 0;
}
```

Прототип у неї нехитрий — `long syscall(long number, ...)`, — а от що вона робить, варто прочитати уважно: зберігає регістри, робить виклик, відновлює регістри й **записує помилку в `errno`**. Тобто це не «виклик в обхід libc». Це libc, просто загальні двері замість іменних: замість `write()` ви кажете `syscall(SYS_write, …)`, а весь клопіт із регістрами й `errno` бібліотека бере на себе. Той самий код зібрався б і працював би на AArch64, де номер `write` — 64, а пастка зветься `svc #0`.

За цю зручність платять двома різними монетами.

**Перша — типи.** Функція змінного числа аргументів не знає, чого чекає ядро, тож не перетворює нічого. На x86-64 це майже завжди минається, а на 32-бітових архітектурах — ні: там 64-бітове значення передають парою регістрів, і документація прямо попереджає, що на ARM EABI така пара мусить починатися з парного регістра. Іменна обгортка `pwrite64()` про це знає, `syscall()` — ні.

**Друга дорожча, і про неї згадують запізно.** Обгортка в libc не завжди лише перекладає — деякі несуть власну політику, і, гукнувши номер напряму, ви ту політику викидаєте.

Найкоротший приклад — завершення програми. Системний виклик `exit` має номер 60 і вбиває **лише той потік, який його зробив**. Процес цілком убиває інший виклик — `exit_group`, номер 231; саме його з версії glibc 2.3 і робить функція `_exit()`. У однопотоковій програмі різниці не видно взагалі, у багатопотоковій `syscall(SYS_exit, 0)` тихо лишає процес живим і без одного [потоку](book:unix-linux/threads-as-tasks).

Так само поводяться інші: `syscall(SYS_clone, …)` створить задачу, про яку бібліотека нічого не знатиме, — без стека потоку, без пам'яті потоку, без `errno`, і перша ж бібліотечна функція в новій задачі впаде.

> 🔧 **Навіщо це.** Практичне правило: `syscall()` доречний рівно там, де іменної обгортки **немає** — новий виклик ядра, якого ще не підхопила ваша версія glibc (`memfd_secret`, свіжі прапорці `openat2`), або навмисна перевірка поведінки ядра в тестах. Скрізь, де обгортка є, вона є не просто так — і найдорожчі помилки трапляються не в регістрах, а в тому шматку політики, який обгортка робила мовчки.

## Рівень 3: `-nostdlib` — не лишилося нікого

Тепер забираємо бібліотеку зовсім. Прапорець `-nostdlib` каже компонувальнику не брати ані libc, ані стартові об'єктні файли, — і одразу з'ясовується, що `main` більше нема кому викликати.

Ядро про `main` ніколи й не знало: виконуючи `execve`, воно відображає в пам'ять сегменти файлу [ELF](book:unix-linux/elf-structure) і стрибає на адресу, записану в заголовку як точка входу. Типово компонувальник шукає під цю адресу символ `_start`. Що він там побачить — наша справа.

А побачить він ось таке:

![Стовпчик восьмибайтових слів на вершині стека: argc, вказівники argv до NULL, вказівники оточення до NULL, пари допоміжного вектора; збоку — як із них дістати argv і envp](/reference/unix-linux/foundations/libc-as-gateway/img/entry-stack.svg)

*Ядро лишає на стеку рівно сирі дані: кількість аргументів, два NULL-завершені масиви вказівників і допоміжний вектор. Ніхто їх не розібрав і не збирається.*

Звідси видно, чому `_start` не може бути звичайною функцією мовою C. Адреси повернення на стеку немає — ядро не викликало програму, а стрибнуло в неї, — тож пролог і `ret`, які компілятор поставить будь-якій функції, тут або зіпсують розкладку стека, або відправлять керування за випадковою адресою. У деяких компіляторів для цього є атрибут `naked`, який просить не ставити нічого зайвого, але серед атрибутів функцій, які GCC документує для x86, `naked` немає — його підтримують інші архітектури, не ця.

Робочий спосіб — написати точку входу асемблером на верхньому рівні файлу й одразу передати керування у звичайну функцію мовою C:

```c
/* nolibc.c — програма без бібліотеки: своя точка входу, свій вихід */

#define SYS_write       1
#define SYS_exit_group  231

static long syscall3(long n, long a1, long a2, long a3)
{
    long ret;
    __asm__ volatile ("syscall"
        : "=a" (ret)
        : "a" (n), "D" (a1), "S" (a2), "d" (a3)
        : "rcx", "r11", "memory");
    return ret;
}

/* strlen теж нема кому надати */
static unsigned long slen(const char *s)
{
    const char *p = s;
    while (*p) p++;
    return (unsigned long)(p - s);
}

static void put(const char *s)
{
    syscall3(SYS_write, 1, (long)s, (long)slen(s));
}

/* ані printf, ані snprintf: десяткове число теж наша робота */
static void put_ulong(unsigned long v)
{
    char buf[21];                       /* 20 цифр максимум плюс перевід рядка */
    char *p = buf + sizeof buf;
    *--p = '\n';
    if (v == 0) *--p = '0';
    while (v) { *--p = (char)('0' + v % 10); v /= 10; }
    syscall3(SYS_write, 1, (long)p, (long)(buf + sizeof buf - p));
}

/* Сюди _start передає вершину стека такою, якою її лишило ядро */
void c_start(long *sp)
{
    long argc   = sp[0];
    char **argv = (char **)(sp + 1);
    char **envp = argv + argc + 1;      /* одразу за NULL-завершувачем argv */

    put("аргументів: ");
    put_ulong((unsigned long)argc);
    for (long i = 0; i < argc; i++) {
        put("  ");
        put(argv[i]);
        put("\n");
    }
    put("перша змінна оточення: ");
    put(envp[0] ? envp[0] : "(немає)");
    put("\n");

    syscall3(SYS_exit_group, 0, 0, 0);
    __builtin_unreachable();            /* повертатися нікуди */
}

__asm__(
    ".globl _start           \n"
    "_start:                 \n"
    "    xor  %ebp, %ebp     \n"   /* найзовнішній кадр: розкрутка стека спиниться тут */
    "    mov  %rsp, %rdi     \n"   /* перший аргумент c_start — сам покажчик стека */
    "    and  $-16, %rsp     \n"   /* угода про виклик вимагає вирівняного стека */
    "    call c_start        \n"
);
```

Три рядки асемблера роблять рівно те, що потрібно, і нічого понад. `xor %ebp, %ebp` позначає найзовнішній кадр — так налагоджувач знає, де спинити розкрутку. `mov %rsp, %rdi` віддає вершину стека першим аргументом, поки її ніхто не зачепив. `and $-16, %rsp` вирівнює стек: [угода про виклик](book:programming/calling-convention) на x86-64 вимагає, щоб перед `call` покажчик був кратний шістнадцяти, інакше перша ж інструкція SSE, яку вставить оптимізатор, впаде на невирівняному доступі.

Збирається це так:

```
$ gcc -static -nostdlib -ffreestanding -fno-stack-protector \
      -fno-asynchronous-unwind-tables -O2 -o nolibc nolibc.c
$ ./nolibc один два
аргументів: 3
  ./nolibc
  один
  два
перша змінна оточення: SHELL=/bin/bash
```

Кожен прапорець тут не випадковий. `-static` потрібен не заради libc — її вже прибрав `-nostdlib`, — а щоб компонувальник не вписав у файл шлях до динамічного компонувальника: без нього типова збірка PIE отримала б `PT_INTERP` і тягла б `ld.so` — «без libc», зате з [динамічним компонувальником](book:unix-linux/static-and-dynamic-linking). `-fno-stack-protector` обов'язковий: захист стека вставляє в кожну функцію з масивом виклик `__stack_chk_fail`, а він живе в libc. `-ffreestanding` каже компіляторові не вважати, що стандартні функції поводяться стандартно. `-fno-asynchronous-unwind-tables` прибирає таблиці розкрутки, які нікому обробляти.

## Що довелося відтворити своїми руками

Список виходить показовий — і в ньому майже нічого від ядра.

**Точку входу.** Три рядки асемблера, які ядро не надасть ніколи, бо не знає нічого про мову C.

**Розбір `argv` і `envp`.** Ядро поклало на стек сирі вказівники; перетворити їх на два зручні масиви — робота бібліотеки, і робить її `__libc_start_main` ще до `main`.

**Вихід.** Повернення з `c_start` — це стрибок за адресою, якої на стеку немає, тобто негайний `SIGSEGV`. Завершує програму лише явний `exit_group`.

**`errno`.** Її нема взагалі: комірка на кожен потік живе в пам'яті потоку, а пам'ять потоку налагоджує та сама бібліотека. Без неї лишається сире від'ємне число з `rax`.

**`strlen` і друк числа.** Дрібниця, доки не згадаєш, що те саме стосується `memcpy`, `strcmp`, `qsort`, форматування, локалей і роботи з часом.

**Буферизований вивід.** Кожен `put()` вище — окремий перехід у ядро. Буфер, який складає їх докупи, ніхто не поставив.

**`atexit`, конструктори глобальних об'єктів, скидання буферів на виході.** Нічого з цього не існує.

Спільне в цьому переліку одне: жодного пункту ядро не надає й надавати не збирається. Це все — середовище виконання мови, яке історично лежить у тому самому файлі, що й шлюз, і забирається разом із ним.

## Скільки разів програма заходить у ядро

Тепер вимірюємо. Інструмент — [трасування системних викликів](book:unix-linux/syscall-tracing) з підсумковою таблицею: `strace -c` рахує виклики й друкує звіт у стандартний потік помилок, тож вивід самої програми можна спокійно відводити у файл.

Перший дослід — про тіло програми. Три однакові цикли, тисяча рядків рівно по 20 байтів, вивід у файл:

```c
static const char line[] = "0123456789abcdefghi\n";   /* рівно 20 байтів */

for (int i = 0; i < 1000; i++) printf("%s", line);              /* stdio */
for (int i = 0; i < 1000; i++) write(1, line, sizeof line - 1); /* обгортка */
for (int i = 0; i < 1000; i++)                                  /* сира пастка */
    raw_syscall3(1, 1, (long)line, sizeof line - 1);
```

```
$ strace -c ./loop-stdio > out.txt     # у таблиці цікавий лише рядок write
      5  write
$ strace -c ./loop-write > out.txt
   1000  write
$ strace -c ./loop-raw   > out.txt
   1000  write
```

Другий дослід — про програму цілком. Той самий вивід одного рядка, зібраний трьома способами, і дивимося підсумковий рядок `total`.

![Дві панелі смуг: у циклі printf дає 5 переходів проти 1000 у write і сирої пастки; уся програма — близько 30 викликів у динамічної збірки, близько 12 у статичної та рівно 3 без libc](/reference/unix-linux/foundations/libc-as-gateway/img/syscall-counts.svg)

*Обгортка не додає до межі нічого; двісті разів різниці дає буфер, а два порядки різниці в короткій програмі — розгортання середовища виконання.*

Читаються ці числа так.

**Обгортка `write()` і сира пастка дають рівно однакову кількість переходів — тисячу.** Шлюз не коштує **жодного** зайвого входу в ядро; уся його ціна — кілька інструкцій пересилання регістрів, які губляться на тлі самого переходу. Отже, писати пастки руками заради швидкості немає сенсу: економити нема на чому.

**`printf` дає п'ять.** Двадцять тисяч байтів, буфер у 4 КіБ — чотири повні скидання й залишок на виході. Це не властивість ядра й не властивість шлюзу: це політика бібліотеки, яку ми на третьому рівні викинули разом із нею.

**Уся програма без libc робить рівно три системні виклики** — `execve`, `write`, `exit_group`, — тоді як звичайна динамічна збірка того самого «привіт» робить їх десятки. Точні числа різняться між дистрибутивами й версіями бібліотеки, порядок — ні. І майже все, що там понад три, зроблено до першої інструкції `main`: пошук та відображення бібліотек, перші сторінки купи, налаштування пам'яті потоку.

Обидва спостереження кажуть те саме різними словами. Шлюз у ядро дешевий і легко відтворний — ми відтворили його одним рядком асемблера. Дорогі й невідтворні за вечір ті шари, що з ядром не пов'язані взагалі.

## Пастки, на які натикаєшся

**Без libc не завжди швидше.** Ядро відображає в кожен процес маленьку бібліотеку vDSO, і `clock_gettime()` через libc здебільшого читає час прямо зі спільної сторінки, не входячи в ядро зовсім. Ваша власна пастка з номером `SYS_clock_gettime` увійде туди завжди — тобто буде повільнішою за обгортку в рази.

**Компілятор кличе функції, яких ви не писали.** Присвоєння структури або ініціалізований масив на стеку перетворюються на виклик `memcpy` чи `memset`, і `-ffreestanding` цього не скасовує — навпаки, GCC прямо вимагає, щоб середовище без бібліотеки надало чотири функції: `memcpy`, `memmove`, `memset` і `memcmp`. У збірці без libc їх треба написати самому.

**Оптимізація на етапі компонування може викинути `c_start`.** На неї посилається лише текст асемблера, який GCC не аналізує; з `-flto` функція виглядає невикористаною. Порятунок — `__attribute__((used))` або відмова від LTO.

**Синтаксис асемблера не універсальний.** Текст вище — AT&T, типовий для GCC на Linux. Збірка з `-masm=intel` його не прийме.

**Номери викликів прив'язані до архітектури.** `write` — це 1 на x86-64 і 64 на AArch64, а `open` на AArch64 не існує взагалі: там є лише загальніший `openat`. Рівень 1 і рівень 3 доведеться переписувати під кожну архітектуру; рівень 2 переноситься сам.

**`exit` і `exit_group` — різні речі.** Помилка непомітна рівно доти, доки в програмі один потік.

Останнє варте того, щоб сказати прямо. Уся ця вправа не про те, як обійтися без бібліотеки — так у продакшн майже ніхто й не робить. Вона про те, **де саме проходить межа**: усе, що вдалося відтворити трьома рядками асемблера, було шлюзом; усе, чого відтворити не вдалося, шлюзом ніколи й не було.
