# 🧭 Межа libc: що стоїть за функцією і як це подивитися

Довідник на три питання: у яку з трьох категорій потрапляє конкретна функція libc, якою командою побачити межу в живій системі та як прочитати повідомлення про брак версії символу.

## Критерій, за яким розкладено таблиці

Критерій один і суто механічний: **скільки пасток у ядро робить один виклик функції**.

- **A — жодної.** Функція працює в пам'яті процесу від початку до кінця.
- **B — рівно одна.** Функція перекладає аргументи в іншу угоду, б'є пасткою й переводить одне повернене число в пару «результат + `errno`». Більше нічого.
- **C — скільки libc вважатиме за потрібне.** Нуль, один або десятки — і зовсім інших на ім'я. Тут у libc є власна політика, і саме її наслідки помітні ззовні.

Категорія — властивість не мови C, а конкретної пари «libc + ядро»: та сама `fopen` на іншій системі може лягти в інший рядок. Номери нижче взято з таблиць Linux 6.6 — `arch/x86/entry/syscalls/syscall_64.tbl` для x86-64 і `include/uapi/asm-generic/unistd.h` для aarch64 та інших пізніх архітектур, що взяли спільну таблицю.

## Категорія A: за межу процесу не виходить

| Функції | Що робить libc | Пасток у ядро |
|---|---|---|
| `strlen`, `memcpy`, `memset`, `strcmp` | читає й пише вашу-таки пам'ять | 0 |
| `qsort`, `bsearch` | переставляє елементи вашого масиву | 0 |
| `snprintf`, `sscanf`, `strtod`, `atoi` | форматує й розбирає в буфері, який дали ви | 0 |
| `sin`, `pow`, `sqrt`, `fma` | рахує; це окрема бібліотека libm | 0 |
| `setjmp`, `longjmp` | зберігає й відновлює регістри | 0 |
| `errno` | макрос, що читає пам'ять цього потоку | 0 |
| `pthread_self`, `pthread_equal` | читає той самий блок пам'яті потоку | 0 |
| `abs`, `div`, `rand`, `srand` | арифметика | 0 |

Один виняток варто знати окремо. Функції, що залежать від локалі — `strcoll`, `strftime`, `towupper`, розбір десяткової коми в `strtod`, — самі пасток не роблять, але спираються на таблиці, які колись хтось прочитав із файлу. Читає їх `setlocale()`, і саме вона (а не вони) з'являється у трасі як `openat` + `mmap`. Тому «`strftime` ходить у ядро» — хибний висновок із правильного спостереження: ходила `setlocale`, одного разу, і зазвичай на старті.

## Категорія B: рівно одна пастка, часто під іншим ім'ям

| Функція C | Системний виклик насправді | № x86-64 | № aarch64 |
|---|---|---|---|
| `read` | `read` | 0 | 63 |
| `write` | `write` | 1 | 64 |
| `close` | `close` | 3 | 57 |
| `getpid` | `getpid` | 39 | 172 |
| `mprotect` | `mprotect` | 10 | 226 |
| `munmap` | `munmap` | 11 | 215 |
| `open(шлях, …)` | **`openat(AT_FDCWD, шлях, …)`** | 257 | 56 |
| `unlink` | **`unlinkat`** | 263 | 35 |
| `mkdir` | **`mkdirat`** | 258 | 34 |
| `chmod` | **`fchmodat`** | 268 | 53 |
| `rename` | **`renameat`** | 264 | 38 |
| `stat`, `lstat` | **`newfstatat`** (де потрібен 64-бітний час — `statx`) | 262 / 332 | 79 / 291 |
| `dup2(o, n)` | **`dup3(o, n, 0)`** там, де `dup2` немає | 33 / 292 | 24 |
| `pipe(fd)` | **`pipe2(fd, 0)`** | 22 / 293 | 59 |
| `poll` | **`ppoll`** | 7 / 271 | 73 |
| `select` | **`pselect6`** | 23 / 270 | 72 |
| `epoll_create(n)` | **`epoll_create1(0)`** — застаріле `n` просто відкидають | 213 / 291 | 20 |
| `fork()` | **`clone(… SIGCHLD)`** | 56 | 220 |

Ліва половина таблиці — імена, які не змінювалися десятиліттями; права — те, що справді сталося. Перейменування не випадкові й не косметичні. Спільну таблицю викликів, яку взяли aarch64, riscv та інші пізні архітектури, свідомо позбавили старих форм: там немає ані `open`, ані `fork`, `poll`, `pipe`, `select`, `dup2`, `stat`, `unlink`, `rename`, `mkdir`, `chmod`, `getdents`, `epoll_create`. Лишили тільки узагальнені: з дескриптором каталогу (`*at`), з окремим полем прапорців (`*2`, `*3`) або з точнішим часом і маскою сигналів (`p*`).

Наслідок для читання трас: на aarch64 у колонці «системний виклик» стоїть єдина можливість, а на x86-64 стара форма ще існує в ядрі — просто glibc її не кличе. Коли `strace` показує `openat` там, де в коді написано `open`, це не заміна на льоту й не оптимізація: обгортка `open()` у glibc буквально складається з одного рядка, що підставляє `AT_FDCWD` і кличе `openat`.

Через це ж «рівно одна пастка» не означає «нуль роботи». Обгортка ще й перекладає угоду про виклик, ловить діапазон помилок і кладе код у `errno` — а `errno` живе в пам'яті потоку, яку хтось мав створити раніше.

## Категорія C: власна політика

| Функція | Типові виклики за нею | Що вирішує libc сама |
|---|---|---|
| `printf`, `fputs`, `putchar` | 0 або 1 `write` | коли віддати буфер: на `\n`, на заповненні чи на `exit` |
| `fopen` | `openat`, `fstat` | розмір буфера бере з `st_blksize`; сам буфер виділяє при першому вжитку |
| `fclose`, `fflush` | 0 або 1 `write`, `close` | чи є що скидати |
| `malloc` | у більшості викликів 0; інакше `brk` або `mmap` | коли й скільки просити в ядра гуртом; від ~128 КіБ одразу `mmap` |
| `free` | зазвичай 0; іноді `madvise`, `munmap` | чи повертати сторінки системі |
| `pthread_create` | `mmap` (стек), `mprotect` (сторінка-пастка), `clone3` з відкатом на `clone`, `rt_sigprocmask` | розмір стека, пам'ять потоку, прибирання по завершенні |
| `pthread_mutex_lock` | 0, якщо замок вільний; `futex` при суперечці | чи взагалі турбувати ядро |
| `sem_wait`, `pthread_cond_wait` | `futex` | те саме |
| `clock_gettime`, `gettimeofday`, `time` | 0 через vDSO або 1 пастка | чи годиться поточне джерело часу для читання без переходу |
| `sched_getcpu` | 0 через ділянку rseq; інакше vDSO, інакше пастка | яким із трьох шляхів дізнатися номер |
| `getaddrinfo`, `getpwnam` | десятки: `openat` файлів налаштувань, `mmap` модулів, `socket`, `sendto`, `recvfrom`, `poll` | де й у якому порядку шукати ім'я |
| `dlopen` | `openat`, `read`, `mmap` × N, `mprotect` | розкладка сегментів і правки зв'язків |
| `readdir` | `getdents64` раз на кілька сотень записів | розмір власного буфера каталогу |
| `system`, `popen` | `clone`, `execve`, `wait4` | запуск оболонки й очікування |
| `getentropy` | `getrandom` | — |
| `abort` | `rt_sigprocmask`, `gettid`, `tgkill` | розблокувати SIGABRT і послати його собі |
| провалений `assert` | `write` у дескриптор 2, далі те саме, що `abort` | зібрати повідомлення з файлу, рядка й виразу |
| `exit` | `write` × скільки буферів, потім `exit_group` | обробники `atexit`, деструктори, скидання stdio |
| `_exit` | рівно `exit_group` | нічого — і саме тому губить недописане |

Три рядки тут заслуговують на окреме слово, бо саме вони найчастіше збивають з пантелику при читанні трас.

`clock_gettime` може не дійти до ядра зовсім. Ядро відображає в кожен процес крихітну спільну бібліотеку [vDSO](book:unix-linux/vdso), де лежить код, що читає час просто зі сторінки, яку ядро й так оновлює. На x86-64 цей символ зветься `__vdso_clock_gettime`, на aarch64 — `__kernel_clock_gettime`. Порожня колонка `clock_gettime` у `strace -c` означає не «програма не питала часу», а «питала й отримала без пастки».

`pthread_mutex_lock` у неконкурентному випадку теж не бачить ядра: захоплення вільного замка — це атомарна операція над словом у пам'яті. До ядра доходить лише той, кому довелося чекати, і робить це через [futex](book:unix-linux/eventfd-and-futex). Тому кількість `futex` у трасі — міра суперечки за замки, а не кількість блокувань.

`malloc` за визначенням не є системним викликом: ядро видає пам'ять сторінками й лише через `brk` або `mmap`, тож просити в нього 24 байти безглуздо. [Розподільник](book:unix-linux/allocator-and-kernel) бере гуртом і нарізає сам.

## Інструменти: подивитися на межу

![Стек «ваш код — libc — ядро»; ltrace вимірює верхній край межі, strace нижній, а статичні інструменти дивляться на сам файл](/reference/unix-linux/foundations/libc-as-gateway/img/boundary-tools.svg)

*Ті самі байти проходять через два зрізи, і кожен зріз має свій інструмент: різниця між показаннями і є те, що libc зробила власною політикою.*

### Що файлові потрібно — ще до запуску

```
$ ldd ./myapp
        linux-vdso.so.1 (0x00007ffd4b3fe000)
        libssl.so.3 => /lib/x86_64-linux-gnu/libssl.so.3 (0x00007f2c7e800000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f2c7e400000)
        /lib64/ld-linux-x86-64.so.2 (0x00007f2c7eb00000)
```

Чотири рядки — чотири різні за природою речі:

- `linux-vdso.so.1` без шляху — це не файл на диску, а сторінка, яку відобразило ядро;
- `libssl.so.3 => /lib/…` — ім'я SONAME ліворуч, знайдений [порядком пошуку](book:unix-linux/library-search-order) шлях праворуч; якщо праворуч `not found`, проблема не у версіях, а в пошуку;
- `libc.so.6` — та сама libc, і її шлях каже, з якої вона системи;
- `/lib64/ld-linux-x86-64.so.2` без стрілки — не залежність, а [динамічний завантажувач](book:unix-linux/dynamic-loader), ім'я якого зашите в самому файлі.

`ldd` за певних умов запускає файл, щоб дістати ці дані, — тож для чужого файлу беруть інші дві команди, які лише читають:

```
$ objdump -p ./myapp | grep NEEDED
  NEEDED               libssl.so.3
  NEEDED               libc.so.6

$ readelf -p .interp ./myapp
String dump of section '.interp':
  [     0]  /lib64/ld-linux-x86-64.so.2
```

Другий вивід відповідає заразом і на питання «яка це взагалі libc»: `ld-linux-*.so.2` — glibc, `ld-musl-*.so.1` — musl.

### Яка libc у цій системі

```
$ getconf GNU_LIBC_VERSION
glibc 2.39
```

Змінна `GNU_LIBC_VERSION` є лише в glibc (з версії 2.3.2) — сам факт, що команда відпрацювала, вже відповідь. Ще два способи, корисні, коли `getconf` немає:

```
$ ldd --version | head -1
ldd (Ubuntu GLIBC 2.39-0ubuntu8.4) 2.39

$ /lib/x86_64-linux-gnu/libc.so.6
GNU C Library (Ubuntu GLIBC 2.39-0ubuntu8.4) stable release version 2.39.
```

Останній рядок не помилка набору: у `libc.so.6` є власна точка входу, і бібліотеку можна запустити як програму — вона надрукує, ким є.

### Які символи й мітки версій потрібні файлові

```
$ objdump -T ./myapp | grep UND
0000000000000000      DF *UND*  0000000000000000  GLIBC_2.34  __libc_start_main
0000000000000000      DF *UND*  0000000000000000  GLIBC_2.2.5 printf
```

Колонки: адреса (для невизначеного символу — нулі), ознаки, секція (`*UND*` — «тут його немає»), розмір, **мітка версії**, ім'я. Те саме компактніше й з міткою просто в імені після `@`:

```
$ nm -D --with-symbol-versions --undefined-only ./myapp
                 U __libc_start_main@GLIBC_2.34
                 U printf@GLIBC_2.2.5
```

Стеля вимог одним рядком:

```
$ objdump -T ./myapp | grep -o 'GLIBC_[0-9.]*' | sort -uV | tail -1
GLIBC_2.34
```

Ключ `-V` тут обов'язковий: без нього `sort` вважає `2.9` більшим за `2.34`.

З боку бібліотеки дивляться тим самим `nm`, помінявши напрямок відбору. Подвійна `@@` означає версію за замовчуванням — ту, яку візьме нова збірка:

```
$ nm -D --with-symbol-versions --defined-only /lib/x86_64-linux-gnu/libc.so.6 \
      | grep __libc_start_main
0000000000029d10 T __libc_start_main@GLIBC_2.2.5
000000000002a180 T __libc_start_main@@GLIBC_2.34
```

Два записи на одне ім'я — це [версіонування символів](book:unix-linux/soname-versioning) у чистому вигляді. У glibc 2.34 змінили умову виклику `__libc_start_main`: параметр `init` віднині завжди `NULL`, а старіші libc до такого не готові. Стару реалізацію не прибрали — додали нову під новою міткою.

> 🔧 **Навіщо це.** Ця пара команд і є перевірка «чи піде воно на цільовій системі», яку варто робити у збірці, а не в користувача: `objdump -T` по артефакту дає стелю вимог, `getconf` на найстарішій підтримуваній машині — підлогу. Якщо стеля вища, файл не запуститься, і жоден прапорець компілятора цього не змінить: мітка потрапляє у файл на етапі [лінкування](book:unix-linux/static-and-dynamic-linking).

### Скільки разів воно ходило в ядро

Найкоротший спосіб побачити всі три категорії одразу — програма, яка робить рівно одне:

```c
#include <stdio.h>

int main(void)
{
    for (int i = 0; i < 1000; i++)
        printf("%d\n", i);
    return 0;
}
```

Тисяча рядків — це 3890 байтів (десять по два, дев'яносто по три, дев'ятсот по чотири). Менше за типовий буфер у 4096, тож у файл усе піде одним записом:

```
$ gcc t.c -o t
$ strace -c ./t > out.txt
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 22.1    0.000104          13         8           mmap
 17.4    0.000082          16         5           openat
 …
  4.2    0.000020          20         1           write
------ ----------- ----------- --------- --------- ----------------
100.00   0.000471                    31         2 total
```

Той самий двійковий файл без перенаправлення (тобто у термінал) дасть у рядку `write` тисячу. Змінився не код і не ядро — змінився режим буфера, бо `fstat` на дескрипторі 1 показав інший тип призначення.

Із колонок надійні дві: `calls` і `errors`. `seconds` і `usecs/call` виміряні під [ptrace](book:unix-linux/ptrace-model), який зупиняє процес двічі на кожен виклик, — це годиться порівнювати між прогонами `strace`, але не з реальним часом. Корисні добірки: `-f` — стежити за нащадками, `-e trace=%file`, `%memory`, `%network`, `%process` — цілі родини викликів замість переліку імен.

Тепер той самий прогін з іншого боку межі:

```
$ ltrace -c ./t > /dev/null
% time     seconds  usecs/call     calls      function
------ ----------- ----------- --------- --------------------
 99.30    0.036511          36      1000 printf
  0.70    0.000257         257         1 __libc_start_main
```

Тисяча згори, один знизу — і між ними немає нічого, крім буфера stdio. `ltrace` перехоплює виклики, що йдуть через [таблицю зв'язку процедур](book:unix-linux/plt-and-got), тож він сліпий там, де PLT немає: у статично злінкованому файлі, при збірці з `-fno-plt`, а також для внутрішніх викликів бібліотеки, зібраної з `-Bsymbolic`. Ключ `-S` додає до тієї самої стрічки ще й системні виклики — тоді обидва краї межі видно в одному впорядкованому списку.

> 🔧 **Навіщо це.** Питання «чому програма робить стільки записів» відповіді з одного інструмента не має — тільки з порівняння. Тисяча `printf` і один `write` — працює буфер. Тисяча й тисяча — буфер вимкнено або вивід іде в термінал. Жодного `printf` і тисяча `write` — байти пише не stdio, а щось інше, і шукати треба не там. Постійне ж вимірювання кількості викликів у робочому навантаженні роблять не цими двома: [трасування без зупинки процесу](book:unix-linux/syscall-tracing) коштує на порядки менше.

## Читання «version GLIBC_x.y not found»

```
./myapp: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.34' not found (required by ./myapp)
```

Повідомлення складене з чотирьох незалежних відомостей:

| Фрагмент | Що каже |
|---|---|
| `./myapp:` | хто не запустився |
| `/lib/x86_64-linux-gnu/libc.so.6:` | у якому саме файлі шукали мітку — не «в libc узагалі», а в цьому |
| `` version `GLIBC_2.34' not found `` | якої мітки в ньому немає |
| `(required by ./myapp)` | хто її вимагає |

Останній фрагмент читають найрідше, а він найважливіший: якщо в дужках стоїть не програма, а `libfoo.so.5`, то перезбирати треба бібліотеку, і жодні дії з програмою не допоможуть.

![Дві панелі: збірка на glibc 2.17 запускається на 2.39, збірка на 2.39 не запускається на 2.28 — бо мітки версій лише додаються](/reference/unix-linux/foundations/libc-as-gateway/img/version-direction.svg)

*Мітки версій до бібліотеки лише додаються й ніколи не зникають, тому напрямок сумісності один: старе на новому працює, нове на старому — ні.*

Діагностика вкладається у три команди:

| Питання | Команда |
|---|---|
| що дає ця система | `getconf GNU_LIBC_VERSION` |
| чого хоче файл (стеля) | `objdump -T ./myapp \| grep -o 'GLIBC_[0-9.]*' \| sort -uV \| tail -1` |
| який саме символ винен | `nm -D --with-symbol-versions ./myapp \| grep GLIBC_2.34` |

Якщо треба побачити порядок, у якому завантажувач звіряв версії, до цього додають `LD_DEBUG=versions ./myapp` (повний перелік розділів дає `LD_DEBUG=help /bin/true`).

Відповідь третьої команди й визначає, що робити:

| Що показав `nm` | Причина | Дія |
|---|---|---|
| лише `__libc_start_main@GLIBC_2.34` | зібрано на glibc ≥ 2.34; стосується будь-якої програми, навіть порожньої | перезібрати на найстарішій цільовій системі |
| конкретні функції: `fcntl64@GLIBC_2.28`, `pthread_*@GLIBC_2.34` | ужито функцію, чия реалізація дістала нову мітку | те саме; зрідка вигідніше обійтися без цієї функції |
| у дужках повідомлення стоїть `.so`, а не програма | вимагає не ваш код, а залежність | перезібрати або замінити саме її |
| мітка `GLIBCXX_3.4.x` чи `CXXABI_1.3.x` | це взагалі не glibc | питання до версії GCC і файлу `libstdc++.so.6` |

Перший рядок пояснює найпоширенішу несподіванку: програма, у якій немає нічого, крім порожнього `main`, вимагає `GLIBC_2.34`, бо `__libc_start_main` є в кожній програмі, а її мітку підняли всім одночасно.

Три способи, які виглядають розв'язанням і ним не є:

- **Скопіювати новий `libc.so.6` у стару систему.** `libc.so.6` і `ld-linux-*.so.2` — нерозлучна пара однієї версії; підміна одного файлу ламає всю систему, а не лагодить одну програму. Для разової перевірки на місці правильна форма інша: `/шлях/до/ld-linux-x86-64.so.2 --library-path /шлях/до/lib ./myapp` — так запускається весь набір цілком, не чіпаючи системного. Це діагностика, не постачання.
- **Виставити `LD_LIBRARY_PATH`.** Він впливає на пошук бібліотек, але не на вибір завантажувача: того обирає рядок `PT_INTERP`, зашитий у сам файл. Змінити його можна (`patchelf --set-interpreter`) — і тоді все одно доведеться тягнути повний комплект.
- **Злінкувати glibc статично.** Мітки версій справді зникнуть, натомість з'явиться інша біда: модулі розв'язання імен glibc підвантажує під час роботи, тож [`getaddrinfo` і `getpwnam`](book:unix-linux/name-resolution-path) у статичному файлі поводяться залежно від машини, на якій його запустили. Компонувальник про це попереджає. Саме тому справді статичні збірки роблять на musl.

Працює одне: збирати там, де glibc найстарша з тих, які треба підтримати, — у контейнері з потрібним дистрибутивом або в SDK з окремим sysroot. Зворотний напрямок безкоштовний і саме тому непомітний: файл, зібраний на glibc 2.17, піде й на 2.39, бо жодну стару мітку звідти не прибрали.
