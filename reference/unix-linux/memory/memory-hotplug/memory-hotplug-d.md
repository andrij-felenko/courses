# Гаряче додавання й вилучення пам'яті (Memory Hotplug)

<preknowlist>
<details>
<summary>Що треба знати перед читанням</summary>

- **Фізична пам'ять (RAM):** базове розуміння організації оперативної пам'яті комп'ютера.
- **Таблиці сторінок (Page Tables):** як ядро ОС відображає віртуальні адреси на фізичні.
- **sysfs:** віртуальна файлова система Linux, що експортує інформацію про пристрої та дозволяє керувати ними (монтується в `/sys`).
- **NUMA (Non-Uniform Memory Access):** архітектура багатопроцесорних систем, де час доступу до пам'яті залежить від її розташування відносно процесора.
</details>
</preknowlist>

Уявіть сучасний дата-центр або хмарну інфраструктуру: віртуальним машинам постійно потрібно змінювати обсяг виділеної оперативної пам'яті залежно від навантаження. Або ж фізичний сервер класу enterprise, де адміністратор має можливість додати нову планку RAM безпосередньо під час роботи системи, без перезавантаження ОС. Щоб зробити це можливим, ядро Linux реалізує механізм **Memory Hotplug** (гаряче додавання та вилучення пам'яті). Ця нетривіальна проблема вимагає від ядра вміння динамічно оновлювати свої внутрішні структури, таблиці сторінок та перерозподіляти дані "на льоту".

## Модель пам'яті SPARSEMEM

Для того щоб ядро могло динамічно додавати та видаляти пам'ять, воно повинно вміти працювати з фрагментованим адресним простором фізичної пам'яті. Саме для цього була створена модель **SPARSEMEM**.

Замість того, щоб утримувати один гігантський масив структур `struct page` для всієї пам'яті (що було б дуже неефективно, якби в пам'яті були "діри"), SPARSEMEM ділить фізичний адресний простір на секції (`mem_section`). Кожна секція представляє безперервний блок фізичної пам'яті фіксованого розміру (зазвичай 128 МБ на x86_64, хоча розмір залежить від архітектури).

Коли нова пам'ять додається в систему (наприклад, через ACPI події при встановленні нового DIMM модуля або гіпервізором), ядро ініціалізує нові структури `mem_section` та відповідні масиви `struct page` для цієї пам'яті.

![Структура SPARSEMEM](/reference/unix-linux/memory/memory-hotplug/img/sparsemem-struct.svg)

*Секція `mem_section` описує безперервний шматок фізичної пам'яті; над нею sysfs показує блок `memoryX`, а керування зводиться до запису стану `online`/`offline` у файл цього блоку.*

## Системні блоки пам'яті та sysfs

З погляду користувацького простору (user-space) керування пам'яттю здійснюється через абстракцію **системних блоків пам'яті**. Ці блоки експортуються через `sysfs` у каталозі `/sys/devices/system/memory/`.

Кожен блок має своє ім'я у форматі `memoryX`, де X — це індекс блоку. Наприклад:
```bash
$ ls /sys/devices/system/memory/
memory0  memory1  memory2  ...
```

Розмір одного такого блоку зазвичай відповідає розміру однієї або кількох секцій SPARSEMEM. Дізнатися розмір блоку у вашій системі можна так:
```bash
$ cat /sys/devices/system/memory/block_size_bytes
8000000
```
*(У цьому прикладі розмір подано у шістнадцятковому форматі: `8000000`₁₆ = 134 217 728 байтів = 128 МБ.)*

## Перехід в онлайн та офлайн

Самого факту виявлення пам'яті ядром недостатньо, щоб процеси могли її використовувати. Пам'ять необхідно перевести в стан **online**.
Стан блоку пам'яті визначається файлом `state` у відповідній теці sysfs.

Можливі стани:
- `offline` — пам'ять фізично присутня (або була виявлена), але не використовується ядром для виділення сторінок.
- `online` — пам'ять додана до загального пулу і може використовуватись.

### Додавання пам'яті (online)

Перевести блок в онлайн можна простою командою:
```bash
# echo online > /sys/devices/system/memory/memory32/state
```

Коли пам'ять переводиться в онлайн, ядро додає її в одну з зон — і яка це буде зона, залежить від написаного слова. Файл `state` приймає три «онлайнові» рядки, а зону за ними обирає `zone_for_pfn_range()` у `mm/memory_hotplug.c`:
- `online_kernel`: блок іде в типову зону ядра для свого діапазону (зазвичай `ZONE_NORMAL`). Така пам'ять придатна на будь-які потреби ядра, зокрема на непереміщувані структури даних.
- `online_movable`: блок іде в зону `ZONE_MOVABLE`. В ній розміщуються лише ті сторінки, які ядро здатне мігрувати (перемістити в інше місце фізичної пам'яті). Це критично важливо для подальшого вилучення цього блоку.
- `online` без суфікса — **не синонім `online_kernel`**. Тут ядро обирає зону саме, за чинною політикою `memory_hotplug.online_policy`. Типова політика `contig-zones` тримає зони суцільними: блок успадковує ту зону, з якою межує, а коли діапазон не належить жодній зоні або перетинає одразу дві — рішення залежить від параметра ядра `movable_node` (заданий → `ZONE_MOVABLE`, не заданий → зона ядра). Політика `auto-movable`, навпаки, свідомо кладе блок у `ZONE_MOVABLE`, коли це дозволяє співвідношення переміщуваної й непереміщуваної пам'яті, — щоб потім його можна було надійно вилучити.

Вибір політики з'явився у ядрі 5.15: у ядрах до 5.15 функція `zone_for_pfn_range()` не знала про `online_policy` взагалі, тож простий `online` завжди йшов гілкою «суцільних зон». Отже, безумовно рівним `online_kernel` запис `online` не був ніколи — збігтися з ним він може лише як наслідок політики й розташування сусідніх зон. (Ті самі рядки приймає й файл `/sys/devices/system/memory/auto_online_blocks`, який задає, у якому стані ядро вмикає щойно додану пам'ять само; його початкове значення дає параметр командного рядка `memhp_default_state=`.)

![Перехід станів](/reference/unix-linux/memory/memory-hotplug/img/hotplug-transition.svg)

*Перехід в обидва боки робить той самий запис у файл `state`, але шлях назад, в `offline`, спершу вимагає міграції зайнятих сторінок — саме тому він може й не вдатися.*

### Чому вилучення (offline) значно складніше?

Якщо додати пам'ять відносно просто — ядро просто оновлює свої пули вільних сторінок, то **вилучення** пам'яті є надзвичайно складним процесом.

Коли ви намагаєтесь перевести блок в `offline`:
```bash
# echo offline > /sys/devices/system/memory/memory32/state
```

Ядро повинно:
1. Ізолювати сторінки у цьому блоці, щоб запобігти виділенню нових сторінок з нього.
2. Знайти всі сторінки, які вже зайняті даними, і мігрувати їх. Ядро повинно виділити нові сторінки в іншій частині пам'яті, скопіювати туди дані і оновити таблиці сторінок (Page Tables) всіх процесів, які посилались на старі адреси.
3. Дочекатися звільнення тих сторінок, які мігрувати не можна (наприклад, сторінки, заблоковані через `mlock`, або деякі структури ядра).

Якщо в блоці опинилась хоча б одна **непереміщувана (unmovable)** сторінка (наприклад, критична внутрішня структура ядра), операція `offline` завершиться помилкою. Саме тому для гарячого вилучення важливо додавати пам'ять як `online_movable`.

## Виклики для ядра та таблиць сторінок

Процес гарячої заміни пам'яті глибоко зачіпає підсистему управління пам'яттю (Memory Management, MM).
Під час міграції сторінок ядро використовує механізм, подібний до ущільнення пам'яті (memory compaction). Воно тимчасово блокує доступ до сторінки (виклик сторінкового переривання, page fault), копіює дані, оновлює запис PTE (Page Table Entry) і скидає відповідний запис у TLB (Translation Lookaside Buffer) на всіх процесорах. Це ресурсомістка операція, що може викликати короткочасні затримки (latency spikes) у роботі системи.

Крім того, гіпервізори часто використовують механізм **ballooning** разом з hotplug для динамічного балансування пам'яті між віртуальними машинами, проте hotplug дозволяє змінювати загальний доступний фізичний ліміт, що робить його більш фундаментальним інструментом.
