# 📋 Регулятори фізичного розподільника: файли, сисктли, прапорці

Це повний перелік того, що розподільник фізичних кадрів виставляє назовні: файли, у яких видно його стан, сисктли й параметри завантаження, якими його поведінку змінюють, і прапорці, якими код усередині ядра формулює свій запит. Довідка потрібна тому, що майже всі ці імена нічого не важать поодинці: `min_free_kbytes` не має сенсу без `watermark_scale_factor`, стовпці `buddyinfo` — без `pagetypeinfo`, а число з `extfrag_index` — без порога, з яким його порівнюють.

Числа звірено з деревом Linux 7.1 (`mm/page_alloc.c`, `mm/compaction.c`, `mm/vmstat.c`, `mm/cma_sysfs.c`, `Documentation/admin-guide/sysctl/vm.rst`). Розмір сторінки скрізь 4 КіБ, як на x86-64; на іншій архітектурі всі перерахунки «сторінки → байти» треба множити на своє `getconf PAGESIZE`.

## Права й одиниці

**Одиниця — сторінка**, якщо в таблиці не сказано інше. Виняток один і він єдиний важливий: `min_free_kbytes` — у кібібайтах, а всі похідні від нього числа в `/proc/zoneinfo` — у сторінках.

**Хто може читати й писати.**

| Шлях | Режим | Хто |
| --- | --- | --- |
| `/proc/buddyinfo` · `/proc/zoneinfo` · `/proc/vmstat` | `0444` | читає будь-хто |
| `/proc/pagetypeinfo` | `0400` | **лише root**; звичайний користувач дістане `EACCES`, а не порожній файл |
| `/proc/sys/vm/*` | `0644` | читає будь-хто, пише root |
| `/proc/sys/vm/compact_memory` · `/proc/sys/vm/drop_caches` | `0200` | **лише запис**; `cat` цих файлів завершиться помилкою — це не збій |
| `/sys/kernel/mm/hugepages/**` | `0644` | пише root |
| `/sys/kernel/mm/cma/**` | `0444` | лише читання |
| `/sys/kernel/debug/**` | тека `0700` | root, і лише коли [псевдофайлову систему](book:unix-linux/pseudo-filesystems) `debugfs` змонтовано: `mount -t debugfs none /sys/kernel/debug` |

**Змінюване й незмінне.** Сисктли діють одразу після запису й переживають лише до перезавантаження (постійність дає `/etc/sysctl.d/`). Параметри завантаження — навпаки: діють із моменту старту ядра й не змінюються ніяк, бо описують поділ пам'яті, який стається до того, як з'явиться перший процес.

## /proc/buddyinfo — форма вільної пам'яті

```
Node 0, zone      DMA      1      1      1      0      2      1      1      0      1      1      3
Node 0, zone    DMA32   1893    952    431    186     67     22      9      3      1      0      0
Node 0, zone   Normal   3542   1201    486    154     37      8      2      0      0      0      0
```

| Елемент | Що це |
| --- | --- |
| `Node N` | вузол пам'яті — на машині без NUMA завжди `Node 0` |
| `zone <ім'я>` | зона: `DMA`, `DMA32`, `Normal`, `HighMem` (лише 32-бітні), `Movable`, `Device` |
| стовпці | кількість **вільних блоків** кожного порядку, зліва порядок 0 |
| скільки стовпців | `NR_PAGE_ORDERS` = `MAX_PAGE_ORDER` + 1, типово **11** (порядки 0…10) |

Число в стовпці — це кількість **блоків**, не кадрів. Щоб дістати байти, кожен стовпець треба помножити на `2ᵏ · PAGE_SIZE`:

```
awk '/zone +Normal/ {
       s = 0; m = -1
       for (i = 5; i <= NF; i++) { s += $i * 2^(i-5); if ($i > 0) m = i-5 }
       printf "%s: вільно %.1f МіБ, найбільший блок — порядок %d (%d КіБ)\n",
              $4, s*4/1024, m, 2^m*4
     }' /proc/buddyinfo
```

Три пастки цього файла.

**Сума рядка — не вся вільна пам'ять машини.** Вона сходиться з `nr_free_pages` тієї самої зони, а після складання зон — із `MemFree`: усі три рахують те саме, кадри в списках приятелів. Але кадри, які осіли в **посторінкових запасах процесорів**, не потрапляють у жоден із трьох — тобто вільної пам'яті на машині більше, ніж каже будь-який із цих лічильників. Побачити її можна лише в `/proc/zoneinfo`, у блоці `pagesets`, окремо на кожен процесор.

**Рядок нічого не каже про рухомість.** Дванадцять вільних блоків порядку 9 у стовпці — це ще не дванадцять доступних великих сторінок: частина з них може лежати в нерухомих блоках сторінок, куди запит на рухому пам'ять не пустять. Відповідь дає наступний файл.

**Читання дороге.** Ядро проходить списки вільних блоків під замком зони; на великій машині це помітна пауза. Опитувати `buddyinfo` раз на секунду — нормально, раз на 10 мс — ні.

## /proc/pagetypeinfo — та сама форма, розрізана за рухомістю

Файл читає лише root і складається з трьох частин.

**Шапка** — розмір блоку сторінок:

```
Page block order: 9
Pages per block:  512
```

Порядок блоку сторінок дорівнює порядку великої сторінки, тобто на x86-64 це 9 (512 кадрів, 2 МіБ). Це та одиниця, якою ядро роздає рухомість: позначку носить цілий блок, не окремий кадр.

**Вільні блоки за парою «порядок × рухомість»** — рядок на кожен тип у кожній зоні:

```
Free pages count per migrate type at order       0      1      2 ...
Node    0, zone   Normal, type    Unmovable    412     93     18 ...
Node    0, zone   Normal, type      Movable   2871    998    441 ...
Node    0, zone   Normal, type  Reclaimable    259    110     27 ...
Node    0, zone   Normal, type   HighAtomic      0      0      0 ...
Node    0, zone   Normal, type          CMA      0      0      0 ...
Node    0, zone   Normal, type      Isolate      0      0      0 ...
```

| Тип | Кому належить |
| --- | --- |
| `Unmovable` | структури ядра, закріплені буфери — зрушити не можна ніяк |
| `Movable` | сторінки процесів і кеша файлів — можна перенести, переписавши записи таблиць |
| `Reclaimable` | те, що не переносять, а викидають і за потреби перечитують (кеші, що мають зменшувачі) |
| `HighAtomic` | резерв під атомарні запити високого порядку — ядро тримає його осторонь |
| `CMA` | блоки області суцільної пам'яті: доки її власник мовчить, туди пускають рухоме |
| `Isolate` | тимчасовий стан під час ущільнення чи гарячого вимкнення — з таких блоків не виділяють |

Порядок рядків фіксований і саме такий; `CMA` є лише при `CONFIG_CMA`, `Isolate` — при `CONFIG_MEMORY_ISOLATION`.

Лічильник у кожній клітинці **обрізаний на 100 000**: ядро перебирає список під замком і зупиняється, поставивши перед числом `>`. Значення `>100000` означає «щонайменше стільки», а не точну кількість.

**Кількість блоків кожного типу** — остання частина, і саме вона відповідає на питання «скільки великих сторінок узагалі можливо»:

```
Number of blocks type     Unmovable      Movable  Reclaimable   HighAtomic          CMA      Isolate
Node 0, zone      Normal        184         6912          201            0            0            0
```

Одного живого нерухомого кадру досить, щоб великої сторінки з блоку не склалося: перенести його нема як, а ущільнення нерухомого не чіпає. Тому 184 у стовпці `Unmovable` — це 184 блоки, 368 МіБ, які з боротьби за великі сторінки випадають, доки те, що в них живе, не звільниться само. Сума `Movable` і `Reclaimable` — навпаки, верхня оцінка того, скільки великих сторінок машина здатна дати після ущільнення.

## /proc/zoneinfo — стан кожної зони повністю

Найдетальніший із трьох файлів. Формат — блок на зону; порядок полів фіксований.

| Поле | Одиниця | Що це |
| --- | --- | --- |
| `per-node stats` | сторінки | блок, що друкується **один раз на вузол**, при першій населеній зоні: черги сторінок, брудні, у записі, прив'язані — усе, що ядро рахує по вузлу, а не по зоні |
| `pages free` | сторінки | `nr_free_pages` цієї зони — те, що лежить у списках приятелів |
| `boost` | сторінки | тимчасова добавка до всіх трьох позначок, накинута через подію фрагментації |
| `min` · `low` · `high` | сторінки | позначки рівня: нижче `min` виділяють лише привілейованим, на `low` будять `kswapd`, до `high` він працює |
| `promo` | сторінки | четверта позначка, вище `high`: поріг, за яким сторінку підвищують із повільної пам'яті у швидку при багаторівневій пам'яті (з ядра 6.12) |
| `spanned` | сторінки | скільки кадрів накриває діапазон зони, разом із дірками |
| `present` | сторінки | скільки з них фізично існує |
| `managed` | сторінки | скільки з них справді віддано розподільникові — саме від цього числа рахують позначки |
| `cma` | сторінки | скільки кадрів зони належить областям CMA |
| `protection: (a, b, c, …)` | сторінки | масив `lowmem_reserve`: скільки цієї зони не віддадуть запитові, який міг би обійтися зоною з індексом `j` |
| `nr_*` | сторінки | зонні лічильники: `nr_free_pages`, `nr_free_cma`, `nr_free_pages_blocks` (з 6.15 — скільки вільного лежить цілими блоками сторінок), `nr_zone_*_anon/file`, `nr_mlock` |
| `numa_hit` · `numa_miss` · `numa_foreign` · `numa_local` · `numa_other` | події | чи дістав запит пам'ять із бажаного вузла ([нерівномірний доступ до пам'яті](book:programming/numa)) |
| `pagesets → cpu: N` | — | посторінковий запас цього процесора в цій зоні |
| ↳ `count` | сторінки | скільки кадрів зараз у запасі — **єдине місце, де їх видно** |
| ↳ `high` · `batch` | сторінки | стеля запасу й розмір пачки, якою його поповнюють і зливають |
| ↳ `high_min` · `high_max` | сторінки | межі, у яких ядро саме підбирає `high` під навантаження (з 6.12) |
| `vm stats threshold` | сторінки | наскільки локальний лічильник може розійтися з глобальним, доки його не зіллють — джерело дрібних розбіжностей між файлами |
| `node_unreclaimable` | 0/1 | вузол визнано безнадійним: відбір більше нічого не дає |
| `start_pfn` | номер кадру | з якого кадру починається зона |
| `reserved_highatomic` | сторінки | скільки відкладено під атомарні запити високого порядку |
| `free_highatomic` | сторінки | скільки з відкладеного зараз вільно (з 6.19) |

Масив `protection[]` читається так: для зони `i` елемент `j` — це кількість сторінок, які запитові, дозволеному аж до зони `j`, заборонено з'їдати в зоні `i`. Рахують його з розміру **верхніх** зон:

**Умова.** Вузол з `ZONE_DMA32` на 3.5 ГіБ і `ZONE_NORMAL` на 12 ГіБ, типове `lowmem_reserve_ratio = 256 256 32 0 0`.

```
managed(Normal) = 12 · 1024 · 1024 / 4 = 3 145 728 сторінок
ratio(DMA32)    = 256

protection[Normal] у рядку DMA32 = 3145728 / 256 = 12 288 сторінок = 48 МіБ
```

Тобто звичайне виділення, яке чудово вміститься в `Normal`, зможе взяти з `DMA32` лише те, що лишається понад `min` **плюс** ці 48 МіБ. Так низька зона лишається живою для тих, у кого вибору немає — для 32-бітних пристроїв.

## /proc/vmstat — лічильники розподільника

Усе тут, крім полів `nr_*`, — накопичувальні лічильники від завантаження: сенс має різниця двох читань, поділена на час. Повну мапу того, які поля рівень, а які потік, дано в [довіднику лічильників витіснення](book:unix-linux/swap-and-reclaim/api-reclaim-counters.md); нижче — та частина, що належить саме розподільникові.

| Поле | Одиниця | Що рахує |
| --- | --- | --- |
| `pgalloc_dma` · `pgalloc_dma32` · `pgalloc_normal` · `pgalloc_movable` · `pgalloc_device` | сторінки | скільки кадрів видано з кожної зони |
| `pgfree` | сторінки | скільки повернуто |
| `pgskip_dma` · `pgskip_dma32` · `pgskip_normal` · `pgskip_movable` | сторінки | скільки сторінок сканер відбору пропустив, бо вони не в тій зоні |
| `allocstall_dma` · `allocstall_dma32` · `allocstall_normal` · `allocstall_movable` | **рази** | скільки разів виділення завернуло в прямий відбір; розріз — за зоною, з якої просили |
| `compact_stall` | **рази** | скільки разів виділенню довелося ущільнювати самому, у своєму потоці |
| `compact_success` · `compact_fail` | рази | чим ці спроби завершилися |
| `compact_migrate_scanned` · `compact_free_scanned` | сторінки | скільки переглянули два зустрічні сканери |
| `compact_isolated` | сторінки | скільки сторінок вилучили для перенесення |
| `compact_daemon_wake` | рази | скільки разів будили `kcompactd` |
| `compact_daemon_migrate_scanned` · `compact_daemon_free_scanned` | сторінки | та сама робота, зроблена фоновою ниткою |
| `pgmigrate_success` · `pgmigrate_fail` | сторінки | перенесення сторінок — **уся** міграція, не лише ущільнення (сюди ж іде вирівнювання за вузлами й гаряче вимкнення пам'яті) |
| `thp_migration_success` · `thp_migration_fail` · `thp_migration_split` | великі сторінки | те саме для прозорих великих сторінок; `split` — коли перенести цілою не вийшло й довелося розбити |
| `htlb_buddy_alloc_success` · `htlb_buddy_alloc_fail` | великі сторінки | спроби дістати наперед-виділену велику сторінку прямо з розподільника |
| `drop_pagecache` · `drop_slab` | рази | скільки разів у `drop_caches` писали 1 і 2 |
| `nr_free_pages` · `nr_free_cma` · `nr_free_pages_blocks` | сторінки | рівні, підсумовані по всіх зонах |

Три відношення, заради яких ці лічильники читають:

```
компактність роботи = compact_isolated / compact_migrate_scanned
      мала частка → сканер міграції перемелює зайняте нерухомим, ущільнення марне

ціна для програм   = compact_stall  (за секунду)
      будь-яке ненульове значення означає, що хтось чекав у своєму потоці

успішність          = compact_success / (compact_success + compact_fail)
      стійко низька → у зоні є нерухомі кадри, які ущільнення обійти не може
```

## Два показники фрагментації в debugfs

```
/sys/kernel/debug/extfrag/unusable_index
/sys/kernel/debug/extfrag/extfrag_index
```

Обидва файли влаштовані однаково: рядок на зону, число на кожен порядок від 0 до `MAX_PAGE_ORDER`, з трьома знаками після коми.

`unusable_index` відповідає на питання «яка частка вільної пам'яті непридатна під блок цього порядку». `0.000` — уся вільна пам'ять лежить блоками щонайменше такого розміру; `1.000` — жодного такого блоку немає.

`extfrag_index` відповідає на інше питання — **чому** запит цього порядку провалиться:

| У файлі | Зміст |
| --- | --- |
| `-1.000` | запит не провалиться взагалі, доки дотримано позначок рівня — придатний блок є |
| близько до `0.000` | пам'яті просто мало; переставляти нема чого, потрібне витіснення |
| близько до `1.000` | пам'яті вдосталь, біда у формі; ущільнення допоможе |

Тут ховається розбіжність шкал, на якій легко спіткнутися. Усередині ядро тримає це число цілим, від `-1000` до `1000`, і саме з цілим порівнює `vm.extfrag_threshold`. Тобто типовий поріг `500` — це `0.500` у файлі: якщо показник у зоні не перевищує половини, ущільнення не запускають, бо провал списують на брак пам'яті, а не на її форму.

Обидва файли **не рахуються постійно**, а обчислюються в мить читання — з тих самих списків вільних блоків і під тим самим замком зони, тож коштують стільки ж, скільки `buddyinfo`.

## CMA: скільки зарезервовано й скільки з того вдалося

Область суцільної пам'яті має два комплекти файлів. Постійний облік — у sysfs, лише читання:

| Файл під `/sys/kernel/mm/cma/<ім'я>/` | Що це | З ядра |
| --- | --- | --- |
| `total_pages` | розмір області в сторінках | 6.15 |
| `available_pages` | скільки з них зараз можна віддати під запит CMA | 6.15 |
| `alloc_pages_success` · `alloc_pages_fail` | накопичено: скільки сторінок вдалося й не вдалося виділити | 5.13 |
| `release_pages_success` | скільки повернуто | 6.9 |

Імена областей не довільні: глобальна область, оголошена параметром `cma=`, зветься **`reserved`**; області на вузол — `pernuma<N>` або `numa<N>`; області з дерева пристроїв беруть ім'я вузла.

Другий комплект — debugfs, і там є не лише спостереження, а й дії:

| Файл під `/sys/kernel/debug/cma/<ім'я>/` | Режим | Що це |
| --- | --- | --- |
| `count` | `0444` | розмір області в сторінках |
| `used` | `0444` | скільки зайнято |
| `maxchunk` | `0444` | **найбільший суцільний вільний шматок** — головне число, бо саме воно, а не `used`, каже, чи пройде наступний великий запит |
| `order_per_bit` | `0444` | скільки сторінок описує один біт мапи зайнятості |
| `ranges/N/base_pfn` · `ranges/N/bitmap` | `0444` | початок діапазону й сира мапа зайнятості |
| `alloc` · `free` | `0200` | записом числа сторінок можна виділити чи звільнити з області вручну — інструмент перевірки, не робочий інтерфейс |

Стійке `alloc_pages_fail` при чималому `available_pages` означає рівно одне: в області осіли сторінки, яких ущільнення не виселяє, і `maxchunk` це підтвердить. Як драйвер користується цією областю з боку коду — у темі про [прямий доступ до пам'яті й буфери](book:unix-linux/dma-and-buffers).

## Великі сторінки

Наперед-виділені великі сторінки живуть у `/sys/kernel/mm/hugepages/hugepages-<розмір>kB/` (`nr_hugepages`, `free_hugepages`, `resv_hugepages`, `surplus_hugepages`, `nr_overcommit_hugepages`, `nr_hugepages_mempolicy`, `demote`, `demote_size`), з дзеркалом на кожен вузол у `/sys/devices/system/node/node<N>/hugepages/`. Для розподільника важливий лише один бік цього: **запис у `nr_hugepages` на працюючій машині — це прямий запит блоків до системи приятелів**, і його результат негайно видно в `htlb_buddy_alloc_success` та `htlb_buddy_alloc_fail`. Повний розбір самих інтерфейсів — у [довіднику інтерфейсів великих сторінок](book:unix-linux/huge-pages/api-huge-page-interfaces.md).

## Сисктли: що можна змінити на живій машині

| `/proc/sys/vm/…` | Тип і межі | Типове | Режим | З ядра |
| --- | --- | --- | --- | --- |
| `min_free_kbytes` | ціле ≥ 0, кібібайти | обчислюване (див. нижче) | `0644` | давно |
| `watermark_scale_factor` | ціле 1…3000, частки з 10 000 | `10` (0.1 %) | `0644` | 4.6 |
| `watermark_boost_factor` | ціле ≥ 0, частки з 10 000 | `15000` (150 % від `high`) | `0644` | 5.0 |
| `defrag_mode` | `0` або `1` | `0` | `0644` | 6.15 |
| `lowmem_reserve_ratio` | масив цілих, по одному на зону | `256 256 32 0 0` | `0644` | давно |
| `percpu_pagelist_high_fraction` | `0` або ціле ≥ 8 | `0` (ядро добирає само) | `0644` | 5.14 |
| `extfrag_threshold` | ціле 0…1000 | `500` | `0644` | з появою ущільнення |
| `compaction_proactiveness` | ціле 0…100 | `20` | `0644` | 5.9 |
| `compact_unevictable_allowed` | `0` або `1` | `1` (`0` на `PREEMPT_RT`) | `0644` | 4.1 |
| `compact_memory` | запис `1` | — | `0200` | з появою ущільнення |
| `drop_caches` | запис 1…4 | — | `0200` | давно |

Що варто знати про кожен понад таблицю.

**`min_free_kbytes`** задає найнижчу позначку, `min`, для всіх зон разом, а ядро розподіляє її між зонами пропорційно до `managed`. Типове значення не стале, а обчислюване з розміру пам'яті — і не лінійно:

```
min_free_kbytes = int_sqrt(lowmem_kbytes · 16), обрізане до [128, 262144]

  1 ГіБ  →   4 096 кБ
  4 ГіБ  →   8 192 кБ
 16 ГіБ  →  16 384 кБ
256 ГіБ  →  65 536 кБ
```

Корінь тут не примха: попит на аварійний запас росте зі швидкістю мережі й дисків, а вона не подвоюється разом із планками пам'яті. Стеля 256 МіБ означає, що на дуже великій машині запас доведеться піднімати руками. Запис у цей файл перераховує всі позначки негайно; поставлене руками значення ядро запам'ятовує окремо й більше не перебиває власним розрахунком при гарячому додаванні пам'яті.

**`watermark_scale_factor`** задає **відстані** між позначками — те, чого `min_free_kbytes` не задає взагалі. Проміжок `low − min` і проміжок `high − low` дорівнюють `managed · scale / 10000`, але не менше за чверть `min`.

**Умова.** Одна зона `Normal` на 16 ГіБ (`managed` = 4 194 304 сторінки), типові значення.

```
min_free_kbytes = int_sqrt(16777216 · 16) = 16384 кБ
min (уся машина) = 16384 >> (12 − 10)     = 4096 сторінок = 16.0 МіБ

Δ = max(min/4, managed · 10 / 10000)
  = max(1024, 4194) = 4194 сторінки

min   = 4 096  = 16.0 МіБ
low   = 8 290  = 32.4 МіБ
high  = 12 484 = 48.8 МіБ
promo = 16 678 = 65.1 МіБ
```

`kswapd` прокидається, коли вільного стає менше за `low`, і працює, доки не дотягне до `high`. Отже, весь його робочий хід — це `high − min`, у цьому прикладі 32.8 МіБ на шістнадцятигігабайтній машині. Піднімемо `watermark_scale_factor` до 100, тобто до одного відсотка:

```
Δ = max(1024, 4194304 · 100 / 10000) = 41 943 сторінки

min  =  4 096  =  16.0 МіБ   (не змінилося)
low  = 46 039  = 179.8 МіБ
high = 87 982  = 343.7 МіБ

робочий хід kswapd = high − min = 83 886 сторінок = 327.7 МіБ
```

Запас на найгіршу мить лишився той самий, а простір, у якому працюють фоновий відбір і ущільнення, виріс удесятеро. Саме тому дві ручки не взаємозамінні: одна відповідає за глибину аварійного запасу, друга — за розмах фонової роботи.

![Позначки рівня на осі вільних сторінок: що відбувається в кожній смузі й звідки беруться відстані](/reference/unix-linux/memory/physical-page-allocator/img/watermark-bands.svg)

*Дві ручки керують різними речами: `min_free_kbytes` рухає всю драбину вгору-вниз, `watermark_scale_factor` розтягує проміжки між щаблями.*

> 🔧 **Навіщо це.** Коли ущільнення провалюється, найдешевший важіль — не `compaction_proactiveness`, а саме ці дві ручки. Причина проста: сканеру вільних кадрів **нема куди переносити**, якщо вільного в зоні рівно стільки, скільки вимагають позначки. Ширший проміжок `high − min` дає ущільненню робочий простір, і робить це за рахунок фонової нитки, а не за рахунок того, хто просив пам'ять.

**`watermark_boost_factor`** — реакція на подію, а не постійна настройка. Щоразу, коли розподільник змушений позичити блок сторінок чужого типу рухомості, він накидає до `watermark_boost` цієї зони ще один блок сторінок, аж доки не впреться в стелю `high · boost_factor / 10000` — при типових 15000 це півтори `high`. Піднята позначка змушує `kswapd` попрацювати більше, ніж він робив би за звичайних обставин, — і саме цей надлишок вільного стає простором, у якому ущільнення переставляє сторінки. Коли події позичання припиняються, добавка сходить нанівець. Нуль вимикає механізм повністю. На зонах, менших за чотири блоки сторінок, ядро не піднімає позначку взагалі — на крихітній зоні це миттєво дало б брак пам'яті.

**`defrag_mode`** — найновіша й найгрубіша ручка: одиниця каже розподільникові старатися сильніше берегти цілі блоки сторінок навіть коштом того, що звичайні виділення частіше йтимуть довшим шляхом. Довідка ядра радить вмикати її **одразу після завантаження**: фрагментація, яка вже сталася, буває довговічною або й невиправною, тож пізнє вмикання лікує менше, ніж раннє запобігає.

**`percpu_pagelist_high_fraction`** обмежує посторінкові запаси процесорів: значення `N` означає, що в усі запаси однієї зони разом не потрапить більше за `1/N` її сторінок. Нуль — типовий стан — віддає вибір ядру, яке рахує стелю з позначки `low` і кількості процесорів. Менші за 8 значення відкидаються з `EINVAL`. Ручка потрібна там, де важлива не швидкість виділення, а те, щоб пам'ять не зникала в непомітних запасах.

**`extfrag_threshold`** — поріг, із яким порівнюють `extfrag_index`: якщо показник **не перевищує** порога, ущільнення в цій зоні не запускають. Менше значення — ущільнюють охочіше.

**`compaction_proactiveness`** керує випереджальним ущільненням у фоні. Нуль вимикає. Запис ненульового значення не просто змінює настройку — він **негайно запускає** випереджальний прохід. Значення понад 80 роблять ядро чутливішим до зростання фрагментації: ущільнення спрацьовує частіше, але кожен раз виправляє менше; 100 дає надмірну фонову активність.

**`compact_unevictable_allowed`** дозволяє ущільненню чіпати сторінки, які не підлягають витісненню, — насамперед прибиті `mlock`. Перенести їх можна (адреса ж віртуальна), але процес на час перенесення стане на сторінковому збої, а це для системи реального часу неприйнятно — звідси й нуль за замовчуванням на `PREEMPT_RT`. Запис у цей файл на такому ядрі лишає попередження в журналі.

**`compact_memory`** — разова дія: запис `1` ущільнює всі зони всіх вузлів синхронно, у контексті того, хто пише. Будь-яке інше значення відкидається з `EINVAL`. Той самий важіль на один вузол — `/sys/devices/system/node/node<N>/compact`, теж лише на запис.

**`drop_caches`** до розподільника прямого стосунку не має, але потрапляє в ту саму послідовність дій, тож варто знати точну семантику. Це **бітова маска**, і межа запису — від 1 до 4:

| Значення | Дія |
| --- | --- |
| `1` | викинути чистий кеш сторінок |
| `2` | викинути чисті об'єкти [slab: зубці, індексні вузли, кеші зі зменшувачами](book:unix-linux/kernel-memory-slab) |
| `3` | і те, і те |
| `4` | окремий біт: більше не писати в журнал повідомлення про скидання (діє до перезавантаження) |

Брудні сторінки не викидаються ніколи — спершу потрібен `sync`. Форма вільної пам'яті від цього покращується мало: звільнені кадри лишаються там само, де були, тож правий хвіст `buddyinfo` після `drop_caches` зазвичай майже не міняється. Довідка ядра прямо застерігає: поза випробуваннями й налагодженням цього краще не робити.

## Параметри завантаження

Ці рішення ухвалюються до появи першого процесу й не переграються. Передають їх у [рядку команди ядра](book:unix-linux/bootloader-and-cmdline).

| Параметр | Формат | Що робить |
| --- | --- | --- |
| `cma=` | `nn[MG]@[start[MG][-end[MG]]]` | розмір глобальної області суцільної пам'яті, за бажанням із прив'язкою до фізичного діапазону; `0` вимикає CMA зовсім |
| `cma_pernuma=` | `nn[MG]` | окрема область такого розміру **на кожен** вузол; типово 0 |
| `numa_cma=` | `<вузол>:nn[MG][,…]` | область на конкретні вузли; має перевагу над `cma_pernuma=` |
| `hugetlb_cma=` | `nn[KMGTPE]` або `<вузол>:nn[…]` | область, з якої гігантські сторінки (1 ГіБ) беруть **через CMA**, а не при завантаженні: доки їх не просять, пам'ять працює під рухомі виділення |
| `hugepagesz=` | `size[KMG]` | розмір великих сторінок для наступного `hugepages=` |
| `hugepages=` | `N` | скільки сторінок цього розміру виділити при завантаженні |
| `default_hugepagesz=` | `size[KMG]` | який розмір вважати типовим для старих інтерфейсів і `shmget`/`mmap` |
| `kernelcore=` | `nn[KMGTPE]` · `nn%` · `mirror` | скільки пам'яті лишити під **нерухомі** виділення (`ZONE_NORMAL`); решта стає `ZONE_MOVABLE` |
| `movablecore=` | `nn[KMGTPE]` · `nn%` | доповнення до попереднього: скільки віддати під рухомі. Разом із `kernelcore=` перший має перевагу — нерухомої буде **щонайменше** стільки |
| `movable_node` | без значення | вузли, які можна вимкнути гарячим способом, робити повністю рухомими; ядерні виділення туди майже не пускають |
| `page_alloc.shuffle=` | `0`/`1` | перемішувати списки вільних блоків при заповненні (стан читається з `/sys/module/page_alloc/parameters/shuffle`) |

Пара `kernelcore=` / `movablecore=` — це та сама вимога, з якої почалася вся боротьба за форму, тільки поставлена наперед і жорстко: замість сортувати за рухомістю всередині зон, ми проводимо між ними межу до першого виділення. Ціна — те, що віддали під `ZONE_MOVABLE`, для ядра не існує зовсім: якщо ядерних структур виявиться більше, ніж уміщує `kernelcore`, машина дійде до нестачі пам'яті, маючи гігабайти вільного в `Movable`.

## Прапорці запиту: контракт усередині ядра

Назовні цих імен не видно ніде, але саме вони визначають, що́ саме побачить розподільник у кожному запиті. Кожен виклик `alloc_pages()` чи `kmalloc()` несе набір прапорців `gfp_t`, і той набір відповідає на чотири окремі питання: **звідки** брати, **якої рухомості** пам'ять, **що дозволено робити**, щоб її знайти, і **як глибоко** дозволено черпати із запасу.

**Звідки й якої рухомості.**

| Прапорець | Що каже розподільникові |
| --- | --- |
| `__GFP_DMA32` | лише кадри під межею 4 ГіБ — для пристрою з 32-бітною адресацією |
| `__GFP_DMA` | лише найнижча зона; уживати лише там, де це справді потрібно |
| `__GFP_HIGHMEM` | дозволено й пам'ять поза прямим відображенням ядра (має сенс тільки на 32-бітних) |
| `__GFP_MOVABLE` | цю сторінку **можна перенести** ущільненням або забрати відбором — клади її в рухомий блок |
| `__GFP_RECLAIMABLE` | переносити не можна, але можна викинути через зменшувач кеша — окремий блок, третій тип |
| `__GFP_THISNODE` | лише цей вузол, без відступу на сусідні: краще відмова, ніж далека пам'ять |
| `__GFP_HARDWALL` | дотримуватися обмежень набору процесорів, до якого прив'язано завдання |
| `__GFP_COMP` | зібрати видані кадри в **складену сторінку** — блок із власними метаданими, який далі поводиться як одне ціле |

**Що дозволено робити заради пам'яті.** Ці чотири прапорці працюють як дозволи: кожен доданий розширює те, що розподільникові вільно зробити заради відповіді, — і рівно так само розширює перелік місць, де виклик може застрягти надовго:

| Прапорець | Дозволяє |
| --- | --- |
| `__GFP_KSWAPD_RECLAIM` | розбудити `kswapd`, але самому не чекати |
| `__GFP_DIRECT_RECLAIM` | самому піти забирати пам'ять і **заснути** на цьому |
| `__GFP_IO` | під час відбору запускати справжній ввід-вивід |
| `__GFP_FS` | заходити у файлову систему — те, чого не можна робити коду, який сам зараз усередині файлової системи |

Пару `__GFP_DIRECT_RECLAIM | __GFP_KSWAPD_RECLAIM` записують скорочено як `__GFP_RECLAIM` — саме воно стоїть у більшості готових наборів нижче.

**Наскільки наполягати.** Перші три рядки — головна причина, з якої однакові на вигляд виділення поводяться геть по-різному; четвертий стоїть окремо, бо міняє не наполегливість, а глибину, до якої дозволено черпати:

| Прапорець | Поведінка при невдачі |
| --- | --- |
| `__GFP_NORETRY` | найлегший відбір, здатися одразу; різких дій на кшталт виклику вбивці через брак пам'яті не буде |
| `__GFP_RETRY_MAYFAIL` | повторювати довше за попередній, чекати на ущільнення й запис сторінок, але межа спроб усе одно є; невдача — надійна ознака, що вбивця скоро знадобиться |
| `__GFP_NOFAIL` | не здаватися **ніколи**; вимагає, щоб виклик міг спати |
| `__GFP_HIGH` | запит привілейований: дозволено черпати нижче позначки `min`, бо без цієї пам'яті система не рушить далі |

**Готові набори**, з яких складається майже весь код ядра:

| Набір | Розкривається в | Коли вживають |
| --- | --- | --- |
| `GFP_KERNEL` | `__GFP_RECLAIM \| __GFP_IO \| __GFP_FS` | типове виділення; **може заснути** |
| `GFP_NOFS` | `__GFP_RECLAIM \| __GFP_IO` | код усередині файлової системи: відбір дозволено, повертатися у файлову систему — ні |
| `GFP_NOIO` | `__GFP_RECLAIM` | код усередині шляху вводу-виводу: можна лише викидати чисте |
| `GFP_NOWAIT` | `__GFP_KSWAPD_RECLAIM \| __GFP_NOWARN` | не можна спати, але й аварійного запасу не чіпаємо: розбудити `kswapd` і взяти те, що є |
| `GFP_ATOMIC` | `__GFP_HIGH \| __GFP_KSWAPD_RECLAIM` | обробник переривання: спати не можна, а пам'ять потрібна — **дозволено брати нижче `min`** |
| `GFP_USER` | `GFP_KERNEL \| __GFP_HARDWALL` | пам'ять для користувача, до якої ядро теж має прямий доступ |
| `GFP_HIGHUSER_MOVABLE` | `GFP_USER \| __GFP_HIGHMEM \| __GFP_MOVABLE` | звичайна сторінка процесу: рухома, ядру прямий доступ не потрібен |
| `GFP_TRANSHUGE_LIGHT` | `GFP_HIGHUSER_MOVABLE \| __GFP_COMP \| __GFP_NOMEMALLOC \| __GFP_NOWARN`, **без** відбору | спроба дістати велику сторінку задарма: не вийшло — і не треба |
| `GFP_TRANSHUGE` | те саме **плюс** `__GFP_DIRECT_RECLAIM` | те саме, але з правом ущільнювати й чекати |

Найповчальніша пара тут — `GFP_ATOMIC` і `GFP_NOWAIT`. Обидва означають «не можна спати», і на вигляд вони взаємозамінні. Але `GFP_ATOMIC` несе `__GFP_HIGH`, тобто дозвіл черпати з того самого аварійного запасу, який тримає `min_free_kbytes`, а `GFP_NOWAIT` — ні. Драйвер, що з обережності написав `GFP_ATOMIC` там, де вистачило б `GFP_NOWAIT`, тихо їсть запас, за яким система тримається в найгіршу мить.

Так замикається все, що є в цьому переліку. `min_free_kbytes` визначає, який запас лежить під позначкою `min`; `GFP_ATOMIC` визначає, кому дозволено в нього заходити; `/proc/zoneinfo` показує, що з того вийшло. І коли `pages free` тримається нижче за `min` і не піднімається, `kswapd` крутиться безперервно, а вбивця через брак пам'яті ще не спрацював — це не збій обліку. Це видимий результат того, що запас під позначкою виїдають рівно з тією швидкістю, з якою його поповнюють.
