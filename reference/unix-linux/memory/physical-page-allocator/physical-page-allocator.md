Коли звичайній прикладній програмі потрібен мегабайт пам'яті, ядро просто знаходить 256 розрізнених вільних фізичних кадрів (по 4 КіБ) і за допомогою таблиць сторінок зшиває їх так, що програма бачить один суцільний мегабайт віртуальних адрес. Завдяки цій ілюзії програма ніколи не дізнається, що її дані насправді розкидані по всій оперативній пам'яті машини дрібними шматками.

Але існують ситуації, коли віртуальна ілюзія не працює, і ядру або апаратурі потрібні фізичні кадри, що йдуть строго підряд у фізичній оперативній пам'яті. Головні замовники суцільної пам'яті — це:
1. **Апаратні пристрої (DMA)**: Багато контролерів шин або мережевих карт читають і пишуть пам'ять напряму, виставляючи адреси на шину в обхід процесорного MMU. Їм потрібен суцільний буфер, інакше вони почнуть писати не туди.
2. **Структури самого ядра**: Ядро тримає всю фізичну пам'ять машини у так званому прямому відображенні. Якщо великій ядерній структурі треба 16 КіБ, це мають бути 4 фізичні кадри поспіль.
3. **Великі сторінки (Huge Pages)**: Щоб одна велика сторінка на 2 МіБ працювала на рівні апаратури, під нею мають лежати рівно 512 фізичних кадрів поспіль, причому вирівняних за правильною базовою адресою.

Для обслуговування таких запитів ядро має найнижчий рівень управління пам'яттю — розподільник фізичних сторінок, який розуміє форму вільного простору.

## Система приятелів (Buddy Allocator)

Щоб швидко видавати суцільні блоки й, що найважливіше, миттєво зливати їх назад у великі шматки при звільненні, Linux використовує алгоритм "приятелів". 

Вся пам'ять ділиться на блоки розмірами, кратними ступеням двійки. Розподільник не приймає запити у байтах, він оперує **порядками** (order). Блок порядку 0 — це 1 кадр, порядку 1 — 2 кадри, порядку 2 — 4 кадри і так далі до обмеження `MAX_PAGE_ORDER` (зазвичай це порядок 10, тобто 1024 кадри або 4 МіБ на типовій архітектурі x86-64).

Коли великий блок розділяється навпіл для задоволення меншого запиту, утворюються два "приятелі". Їхня головна властивість — індекс приятеля обчислюється однією швидкою побітовою операцією виключного "або" (XOR). Коли блок звільняється, ядро не мусить сканувати списки: воно одразу дивиться на стан його приятеля. Якщо той теж вільний, вони зливаються в один блок вищого порядку. Жодного довгого пошуку суміжних вільних шматків по всій пам'яті не відбувається.

Кожен фізичний кадр у системі має свій описувач — структуру `struct page`. Коли ядро виділяє пам'ять через базовий API `alloc_pages()`, воно повертає покажчик саме на першу `struct page` виділеного суцільного блоку.

```c
#include <linux/gfp.h>
#include <linux/mm.h>

/* Просимо 4 кадри (порядок 2) звичайної пам'яті */
struct page *pages = alloc_pages(GFP_KERNEL, 2);
if (!pages) {
    /* Немає суцільного блоку потрібного розміру */
    return -ENOMEM;
}

/* Отримуємо віртуальну адресу з прямого відображення */
void *buffer = page_address(pages);

/* Звільняємо ці 4 кадри назад системі приятелів */
__free_pages(pages, 2);
```

## Зони пам'яті

Не всі кадри однаково доступні для всіх споживачів. Наприклад, деякі старі ISA-пристрої можуть звертатися апаратно лише до перших 16 МіБ фізичної пам'яті, а багато 32-бітних пристроїв бачать лише перші 4 ГіБ.

Через це ядро заздалегідь групує кадри в **зони** (`ZONE_DMA`, `ZONE_DMA32`, `ZONE_NORMAL`). Розподільник системи приятелів працює суворо всередині кожної зони окремо й ніколи не зливає кадри з різних зон докупи в один блок, адже в такого гібридного блоку були б несумісні правила доступу.

## Зовнішня фрагментація та ущільнення

З часом, коли процеси активно запускаються й завершуються, а кеші файлів постійно ростуть і стискаються, великі блоки неминуче дробляться на дрібні. Якщо посеред 1024 вільних кадрів "застрягне" хоча б один нерухомий зайнятий кадр (наприклад, закріплена структура ядра або DMA-буфер), великого 4-мегабайтного блоку там більше ніколи не збереться, навіть якщо все довкола звільниться. Це називається **зовнішньою фрагментацією** — вільної пам'яті сумарно багато, але потрібної суцільної форми серед неї немає.

У цьому стані запит драйвера на суцільний буфер просто провалиться з помилкою `ENOMEM`, навіть якщо звичайна утиліта `free` показує кілька вільних гігабайтів. Точний стан системи приятелів і кількість вільних блоків за порядками завжди можна подивитися у спеціальному системному файлі `/proc/buddyinfo`.

Щоб лікувати й попереджати фрагментацію, ядро застосовує два інструменти:
1. **Сортування за рухомістю**: Пам'ять заздалегідь ділиться на великі "блоки сторінок". Сторінки користувацьких програм, які можна непомітно для програми перенести на інше місце, кладуться в одні блоки, а нерухомі структури ядра — суворо в інші. Це зменшує шанси того, що один нерухомий кадр зіпсує цілий рухомий блок.
2. **Ущільнення (Compaction)**: Якщо великого блоку все одно немає, ядро може запустити два зустрічні сканери. Один іде знизу зони і збирає зайняті рухомі сторінки, інший іде згори і збирає вільні кадри. Сторінки переносяться у вільні кадри на один край, вивільняючи на іншому краї суцільний масив вільного місця, з якого успішно склеюються великі блоки вищих порядків.
