# 📋 Інтерфейси великих сторінок: пул HugeTLB, THP і те, чим вони міряються

Керування великими сторінками розкидане по шести різних місцях: рядок завантаження ядра, `sysctl`, дві гілки `sysfs`, опції монтування, прапорці системних викликів і чотири різні файли в `/proc`. Тут вони зібрані в одному місці — з тим, що саме кожне значення міняє, і з типовим значенням, від якого варто відштовхуватися.

Кілька домовленостей, без яких таблиці нижче читаються криво.

У шляхах `sysfs` розмір записаний у кілобайтах: `hugepages-2048kB` — це 2 МіБ, `hugepages-1048576kB` — 1 ГіБ. Розміри, доступні на цій машині, ядро саме заводить окремими підтеками, і перелік цих підтек — найшвидша відповідь на питання «а що взагалі вміє це залізо».

`HPAGE_PMD_NR` — скільки звичайних сторінок уміщається у велику сторінку, що описується кінцевим записом на рівні PMD. На x86-64 зі звичайною сторінкою 4 КіБ це 512, і майже всі типові значення нижче — похідні саме від цього числа.

Розмір за домовленістю (`Hugepagesize` у `/proc/meminfo`) — той, що дістається викликам, які розміру не назвали, і монтуванню без `pagesize=`. На x86-64 це 2 МіБ, якщо не сказано інакше в рядку ядра.

## Частина перша: пул HugeTLB

### Рядок завантаження ядра

Пул зазвичай задають саме тут, бо на щойно завантаженій машині пам'ять іще не роздроблена й суцільні блоки знаходяться без бою. Параметри передаються завантажувачем — [як рядок ядра складається й де його правити](book:unix-linux/bootloader-and-cmdline): це один текстовий рядок, який завантажувач кладе поряд з образом ядра, а ядро розбирає ще до того, як з'явиться перший процес.

| параметр | що робить | приклад |
|---|---|---|
| `hugepagesz=<розмір>` | обирає розмір, до якого стосується **наступний** `hugepages=`; може повторюватися для кількох розмірів | `hugepagesz=1G` |
| `hugepages=<N>` | скільки сторінок щойно названого розміру виділити при завантаженні; форма по вузлах — `<вузол>:<N>` через кому | `hugepages=8`, `hugepages=0:512,1:512` |
| `default_hugepagesz=<розмір>` | розмір за домовленістю для викликів і монтувань, які його не назвали; **дозволений у рядку лише один раз** | `default_hugepagesz=2M` |
| `hugepage_alloc_threads=<N>` | скільки потоків виділяють пул при завантаженні; діє лише на не-гігантські розміри, помітно на пулах у сотні гігабайтів | `hugepage_alloc_threads=16` |
| `hugetlb_cma=<розмір>` | зарезервувати область CMA, з якої гігантські сторінки можна брати **в роботі**, а не тільки на завантаженні; форма `nn[GTPE]`, `nn%` або по вузлах | `hugetlb_cma=32G`, `hugetlb_cma=0:16G,1:16G` |
| `hugetlb_free_vmemmap=on\|off` | вмикає HVO — злиття однакових описувачів `struct page` усередині великої сторінки | `hugetlb_free_vmemmap=on` |
| `transparent_hugepage=always\|madvise\|never` | стартове значення вимикача THP, доки хтось не перезапише його в `sysfs` | `transparent_hugepage=madvise` |

Порядок у рядку значущий, і це найчастіша помилка. `hugepages=` завжди стосується того `hugepagesz=`, який стоїть **перед** ним; `hugepages=` без попереднього `hugepagesz=` дістається розміру за домовленістю. Робочий рядок для машини з базою даних і кількома віртуалками виглядає так:

```
default_hugepagesz=1G hugepagesz=1G hugepages=16 hugepagesz=2M hugepages=4096
```

Шістнадцять гігантських сторінок і чотири тисячі двомегабайтових — разом 24 ГіБ, вилучених із системи назавжди.

`hugetlb_cma` вартий окремої уваги, бо він знімає головне обмеження гігантських сторінок. Гігабайт перевищує найбільший блок, який розподільник фізичних кадрів уміє скласти в роботі, тому без CMA сторінки на 1 ГіБ беруться тільки при завантаженні. Область CMA — це смуга пам'яті, у якій ядро дозволяє собі лише **рухомий** вміст, тобто такий, який завжди можна виселити; коли знадобиться гігантська сторінка, смуга звільняється й віддає суцільний блок. Ціна — та пам'ять не годиться для нерухомого: [як ядро веде фізичні кадри, блоки за порядками й ущільнення](book:unix-linux/physical-page-allocator) пояснює, чому одна закріплена сторінка посеред гігабайта робить його неможливим.

HVO варта уваги на великих пулах. Описувач `struct page` займає 64 байти на кожні 4 КіБ пам'яті, тобто одну шістдесят четверту всього обсягу — на пул у 1 ТіБ це близько 16 ГіБ самих лише описувачів. Усередині великої сторінки ці описувачі однакові, тому їх можна не тримати: з восьми сторінок `vmemmap`, що описують 2 МіБ, лишається одна, а з 4096 на гігабайт — теж одна. Вмикається це й у роботі, через `sysctl vm.hugetlb_optimize_vmemmap=1`, але подіє тільки на сторінки, виділені після ввімкнення.

### sysctl

| ключ | тип | що робить | типове |
|---|---|---|---|
| `vm.nr_hugepages` | ч/з | розмір пулу сторінок **розміру за домовленістю**; запис більшого числа просить ядро добрати, меншого — повернути вільні в систему | `0` |
| `vm.nr_hugepages_mempolicy` | ч/з | те саме, але добір розкладається по вузлах NUMA за поточною політикою пам'яті процесу, що пише | `0` |
| `vm.nr_overcommit_hugepages` | ч/з | стеля, наскільки пул може **тимчасово** вирости понад `nr_hugepages` за рахунок суцільних блоків, узятих на льоту; такі сторінки звільняються назад, щойно стають не потрібні | `0` |
| `vm.hugetlb_shm_group` | ч/з | числовий GID групи, членам якої дозволено `shmget(SHM_HUGETLB)` і `memfd_create(MFD_HUGETLB)` без привілеїв | `0` |
| `vm.hugetlb_optimize_vmemmap` | ч/з | вмикає HVO для сторінок, що виділятимуться далі | `0` |

Головне про `vm.nr_hugepages`: запис у нього — це **прохання, а не наказ**. Ядро візьме стільки суцільних блоків, скільки знайде, і мовчки зупиниться. Перевіряти результат обов'язково, і перевіряти читанням того самого файлу:

```sh
$ sysctl -w vm.nr_hugepages=4096
vm.nr_hugepages = 4096
$ cat /proc/sys/vm/nr_hugepages
2317
```

Дві тисячі триста сімнадцять замість чотирьох тисяч дев'яноста шести — це не помилка й не затримка, це остаточна відповідь: більше суцільних блоків у системі немає. Скрипт розгортання, який не читає це число назад, тихо залишить базу даних на дрібних сторінках.

`nr_overcommit_hugepages` вмикає інший режим — пул, що дихає. Сторінки понад `nr_hugepages` називаються надлишковими (`Surp`), беруться в момент запиту з тієї самої фрагментованої пам'яті й повертаються, коли останній охочий їх відпустив. Це компроміс: гарантії пулу зникають (блоку може й не знайтися), зате гігабайти не лежать мертвим вантажем між запусками.

### Гілка `/sys/kernel/mm/hugepages/hugepages-<size>kB/`c

Та сама панель, але окремо на кожен розмір, який уміє машина. Для розміру за домовленістю ці файли дублюють `sysctl`; для всіх інших розмірів це **єдиний** спосіб до них дістатися.

| файл | тип | що показує або міняє |
|---|---|---|
| `nr_hugepages` | ч/з | розмір пулу цього розміру |
| `nr_hugepages_mempolicy` | ч/з | те саме з урахуванням політики NUMA того, хто пише |
| `nr_overcommit_hugepages` | ч/з | стеля надлишкових сторінок цього розміру |
| `free_hugepages` | ч | скільки в пулі ще не роздано |
| `resv_hugepages` | ч | скільки з вільних уже комусь обіцяно |
| `surplus_hugepages` | ч | скільки взято понад `nr_hugepages` |
| `demote` | з | подрібнити задане число сторінок цього розміру на сторінки розміру `demote_size` |
| `demote_size` | ч/з | на який розмір дробити; має бути меншим за розмір цієї теки |

Пара `demote`/`demote_size` — відповідь на цілком реальну біду. Гігантські сторінки набираються тільки при завантаженні, а через тиждень виявляється, що з шістнадцяти гігабайтів потрібні вісім, і решту хочеться повернути в обіг — але не в звичайну пам'ять, а в пул двомегабайтових, бо вони теж потрібні й теж не набираються. Запис у `demote` розрізає гігантські сторінки на 512 двомегабайтових без перезавантаження:

```sh
$ cd /sys/kernel/mm/hugepages/hugepages-1048576kB
$ cat demote_size
2048kB
$ echo 8 > demote          # вісім гігантських → 4096 двомегабайтових
```

Зворотного ходу немає: скласти двомегабайтові назад у гігантську ядро не вміє.

### Роздача по вузлах NUMA

На багатопроцесорній машині має значення не тільки скільки сторінок у пулі, а й **біля якого процесора** вони лежать: доступ до пам'яті чужого вузла коштує помітно дорожче. [Що таке вузол NUMA й чому відстань до пам'яті різна](book:programming/numa) — окрема тема; тут важить лише те, що пул можна набирати вузол за вузлом.

```
/sys/devices/system/node/node<N>/hugepages/hugepages-<size>kB/
    nr_hugepages        ч/з   розмір пулу на цьому вузлі
    free_hugepages      ч     скільки на ньому вільних
    surplus_hugepages   ч     скільки на ньому надлишкових
```

Різниця між глобальним і вузловим записом суттєва. Запис у глобальний `nr_hugepages` розкладає різницю по всіх дозволених вузлах приблизно порівну, і скільки саме дісталося кожному — питання удачі й фрагментації. Запис у вузловий файл задає число на цьому вузлі точно. Тому пул під віртуальну машину, прив'язану до вузла 1, набирають так:

```sh
$ echo 8192 > /sys/devices/system/node/node1/hugepages/hugepages-2048kB/nr_hugepages
$ cat /sys/devices/system/node/node1/hugepages/hugepages-2048kB/free_hugepages
8192
```

### Монтування hugetlbfs

`hugetlbfs` — псевдофайлова система: файли в ній не мають нічого спільного з диском і зникають разом з монтуванням, а слугують лише іменами для шматків пулу ([інші такі системи в Linux і що між ними спільного](book:unix-linux/pseudo-filesystems)). Її монтують тоді, коли великі сторінки треба **розділити між кількома процесами** або дати їх програмі, яка вміє відображати файл, але не вміє `MAP_HUGETLB`.

| опція | що робить | приклад |
|---|---|---|
| `pagesize=<розмір>` | з якого пулу брати сторінки; без неї — розмір за домовленістю | `pagesize=1G` |
| `size=<обсяг або %>` | стеля пам'яті для цього монтування: скільки сторінок звідси можна забрати щонайбільше | `size=8G`, `size=25%` |
| `min_size=<обсяг або %>` | скільки сторінок зарезервувати за цим монтуванням одразу, щоб їх не перехопили інші | `min_size=4G` |
| `nr_inodes=<N>` | стеля кількості файлів у цій системі | `nr_inodes=1024` |
| `uid=`, `gid=` | власник і група кореня системи | `uid=26,gid=26` |
| `mode=<вісімкове>` | права кореня (накладаються маскою `& 01777`) | `mode=0770` |

```sh
$ mkdir -p /dev/hugepages1G
$ mount -t hugetlbfs -o pagesize=1G,size=8G,min_size=4G,uid=26,gid=26,mode=0770 \
        none /dev/hugepages1G
```

Пара `size`/`min_size` описує коридор: `min_size` — скільки цьому монтуванню гарантовано (ядро резервує їх одразу й нікому іншому не віддасть), `size` — далі якої межі воно не виросте, навіть якщо в пулі вільно. Обидві приймають і відсоток від пулу відповідного розміру, і це зручніше, ніж перераховувати абсолютні числа щоразу, коли пул змінився.

Права доступу тут — звичайні файлові: хто має право створити файл у каталозі монтування, той дістає великі сторінки без жодних привілеїв. Саме так їх зазвичай і роздають службам — `mode=0770` плюс потрібна група, і жодних додаткових можливостей роздавати не доводиться.

### Прапорці системних викликів

У пул ведуть четверо дверей, і всі вони зрештою заводять інод у `hugetlbfs`.

| двері | як просити | привілей |
|---|---|---|
| `mmap` | `MAP_HUGETLB` разом з `MAP_ANONYMOUS` | не потрібен |
| `shmget` | `SHM_HUGETLB` у полі `shmflg` | `CAP_IPC_LOCK` **або** членство в `vm.hugetlb_shm_group` |
| `memfd_create` | `MFD_HUGETLB` у полі `flags` | так само |
| відкритий файл | `open` у змонтованій `hugetlbfs`, далі звичайний `mmap` | звичайні права каталогу |

Різниця в привілеях не випадкова: анонімне відображення видно лише самому процесові, тоді як сегмент `shmget` і дескриптор `memfd` можна передати іншим, тобто ними можна поділитися пулом — а це вже питання розподілу спільного ресурсу. [Що таке можливості процесу й чим вони кращі за прапорець «root»](book:unix-linux/capabilities): права суперкористувача розбито на десятки окремих дозволів, і `CAP_IPC_LOCK` — один з них.

Розмір сторінки, якщо він не той, що за домовленістю, кодується прямо в слові прапорців — тими самими шістьма бітами в усіх трьох викликах:

```c
#define MAP_HUGE_SHIFT  26
#define MAP_HUGE_MASK   0x3f
#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)
```

![Слово прапорців: шість старших бітів тримають двійковий логарифм розміру сторінки, решта — звичайні прапорці виклику](/reference/unix-linux/memory/huge-pages/img/huge-flag-bits.svg)

*У шести бітах, починаючи з двадцять шостого, лежить не сам розмір, а його двійковий логарифм. Нуль означає «розмір за домовленістю». `SHM_HUGE_SHIFT` і `MFD_HUGE_SHIFT` — те саме число 26.*

Шість бітів вистачає на логарифми до 63, тобто на будь-який мислимий розмір, і саме тому інтерфейс не довелося переробляти, коли з'явилися архітектури зі своїми розмірами. Довільний розмір рахується так:

```
розмір 512 МіБ = 2²⁹  →  log₂ = 29
flags = MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB | (29 << 26)
```

Мінімальний робочий виклик — з перевіркою, якої зазвичай і бракує:

```c
#define _GNU_SOURCE
#include <sys/mman.h>
#include <stdio.h>
#include <string.h>
#include <errno.h>

/* Узяти len байтів із пулу сторінок розміру 2^lg2. lg2 == 0 — розмір за домовленістю. */
static void *huge_alloc(size_t len, unsigned lg2)
{
        int flags = MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB
                  | (int)((lg2 & MAP_HUGE_MASK) << MAP_HUGE_SHIFT);

        void *p = mmap(NULL, len, PROT_READ | PROT_WRITE, flags, -1, 0);
        if (p == MAP_FAILED) {
                fprintf(stderr, "MAP_HUGETLB %zu Б: %s\n", len, strerror(errno));
                return NULL;
        }
        /* Резервування вже зроблено, але торкнутися варто тут, а не в гарячому шляху. */
        memset(p, 0, len);
        return p;
}

int main(void)
{
        void *p = huge_alloc(4ull << 30, 30);   /* чотири сторінки по 1 ГіБ */
        if (!p)
                return 1;
        printf("%p\n", p);
        return 0;
}
```

Довжина `len` мусить бути кратна обраному розміру сторінки — інакше `EINVAL`. Виклик [`mmap` просить у ядра ділянку адресного простору, а не пам'ять](book:unix-linux/mmap-model), і сторінки під нею з'являються пізніше, на збоях; з `MAP_HUGETLB` різниця в тому, що потрібна кількість сторінок **резервується** вже в момент виклику, тож пізніший збій не може провалитися через чужий апетит.

| помилка | коли | що робити |
|---|---|---|
| `ENOMEM` | у пулі потрібного розміру немає стільки вільних сторінок | набрати пул або зменшити запит |
| `EINVAL` | довжина не кратна розміру сторінки; названо розмір, якого машина не вміє | звірити з переліком тек у `/sys/kernel/mm/hugepages/` |
| `EPERM` | `SHM_HUGETLB` або `MFD_HUGETLB` без `CAP_IPC_LOCK` і без членства в групі | внести GID у `vm.hugetlb_shm_group` |
| `SIGBUS` | збій на ділянці, під яку сторінки не зарезервовані (пул зменшили після `mmap`, або відображення робилося з `MAP_NORESERVE`) | не зменшувати пул під живими процесами |

`SIGBUS` тут — не збій програми, а спосіб, у який брак великих сторінок доповідають саме тому процесові, що на них розраховував. Ні OOM-убивця, ні повільна робота не втручаються: адреса законна, а кадру під нею немає.

### Обмеження через cgroup

Пул — спільний ресурс, тому його ділять тим самим механізмом, яким ділять решту ([що таке контрольні групи й як вони вкладаються одна в одну](book:unix-linux/cgroups)). У другій версії ієрархії контролер `hugetlb` дає на кожен розмір такі файли:

| файл | що робить |
|---|---|
| `hugetlb.<розмір>.max` | стеля великих сторінок цього розміру для групи (в байтах або `max`) |
| `hugetlb.<розмір>.current` | скільки група вже займає |
| `hugetlb.<розмір>.events` | лічильник `max` — скільки разів запит уперся в стелю |
| `hugetlb.<розмір>.events.local` | те саме, але без урахування нащадків |
| `hugetlb.<розмір>.rsvd.max` | стеля на **резервування**, а не на фактично зайняте |
| `hugetlb.<розмір>.rsvd.current` | скільки група зарезервувала |
| `hugetlb.<розмір>.numa_stat` | розклад зайнятого по вузлах |

Пара `rsvd` існує тому, що момент резервування (`mmap`) і момент фактичного зайняття (перший запис) розведені в часі. Обмежувати варто саме резервування: група, яка успішно зробила `mmap` і впала на `SIGBUS` при першому записі, — значно гірший результат, ніж група, яка чесно дістала `ENOMEM` одразу.

## Частина друга: прозорі великі сторінки

### Гілка `/sys/kernel/mm/transparent_hugepage/`c

| файл | значення | що робить | типове |
|---|---|---|---|
| `enabled` | `always` · `madvise` · `never` | де пробувати великі сторінки: скрізь, лише за проханням через `madvise`, ніде | `always` у типовій збірці ядра, `madvise` у більшості дистрибутивів |
| `defrag` | `always` · `defer` · `defer+madvise` · `madvise` · `never` | чи вільно змусити прикладний потік чекати на ущільнення | `madvise` в ядрі, `defer+madvise` у дистрибутивах |
| `use_zero_page` | `0` · `1` | чи віддавати на читання ще не записаної пам'яті одну спільну нульову велику сторінку замість того, щоб виділяти справжню | `1` |
| `shrink_underused` | `0` · `1` | під тиском на пам'ять розбивати назад великі сторінки, у яких більшість дрібних порожні (з версії 6.12) | `0` |
| `hpage_pmd_size` | лише читання | розмір великої сторінки рівня PMD у байтах — 2097152 на x86-64 | — |
| `shmem_enabled` | `always` · `within_size` · `advise` · `never` · `deny` · `force` | те саме, що `enabled`, але для `tmpfs` і спільної пам'яті | `never` |

Значення `defrag` — це відповідь на одне питання: чи можна змусити потік, що спіткнувся об збій, стояти, поки ядро переносить чужі сторінки.

| значення | що станеться на збої, коли суцільного блоку немає |
|---|---|
| `always` | потік стоїть і чекає на ущільнення — завжди |
| `defer` | потік одразу бере дрібні сторінки, а ущільнення доручається фоновим потокам ядра |
| `defer+madvise` | чекає лише той, хто просив великих сторінок через `madvise`; решта беруть дрібні й ідуть далі |
| `madvise` | чекає лише той, хто просив; решті ущільнення навіть не замовляється |
| `never` | не чекає ніхто й ніколи |

Два значення `shmem_enabled` не мають відповідників у звичайному `enabled` і варті окремого слова. `within_size` дає велику сторінку лише тоді, коли вона повністю вміщається в оголошений розмір файлу — інакше `tmpfs` роздувався б до кратного двом мегабайтам на кожному дрібному файлі. `force` і `deny` — грубі важелі для налагодження: перший вимагає великих сторінок скрізь, незалежно від прохань, другий забороняє їх усюди.

### Проміжні розміри

Двомегабайтовий крок для багатьох задач завеликий: суцільних блоків на 2 МіБ бракує, а зібрати шістнадцять суцільних кадрів можна майже завжди. Тому кожен степінь двійки нижче за повний блок дістав власну підтеку:

```
/sys/kernel/mm/transparent_hugepage/hugepages-<size>kB/
    enabled         always · inherit · madvise · never
    shmem_enabled   always · inherit · within_size · advise · never
    stats/          лічильники саме цього розміру
```

Значення `inherit` означає «як у глобальному `enabled`» — саме воно стоїть на розмірі рівня PMD, тоді як усі менші розміри за домовленістю **вимкнені** (`never`). Тобто проміжні розміри не вмикаються самі: їх треба назвати поіменно.

У теці `stats/` лежать ті самі поняття, що й у `/proc/vmstat`, але окремо на розмір: `anon_fault_alloc`, `anon_fault_fallback`, `collapse_alloc`, `collapse_alloc_failed`, `split`, `split_deferred`, `nr_anon`, `nr_anon_partially_mapped`, `swpout`, `shmem_alloc`. Це єдиний спосіб побачити, який саме розмір справді працює: глобальні лічильники змішують усе докупи.

### khugepaged

Фоновий потік, що згортає вже роздані дрібні сторінки у великі. Керується підтекою `khugepaged/`; типові значення нижче — з початкового коду ядра, а не з якогось дистрибутива.

| файл | що робить | типове |
|---|---|---|
| `pages_to_scan` | скільки сторінок оглянути за один прохід | `4096` (`HPAGE_PMD_NR · 8`) |
| `scan_sleep_millisecs` | пауза між проходами | `10000` |
| `alloc_sleep_millisecs` | пауза після невдалої спроби взяти велику сторінку — щоб не гатити по порожньому | `60000` |
| `max_ptes_none` | скільком сторінкам у вікні дозволено бути **порожніми**, щоб вікно все одно згорнули | `511` (`HPAGE_PMD_NR − 1`) |
| `max_ptes_swap` | скільки сторінок вікна дозволено підняти з підкачки заради згортання | `64` (`HPAGE_PMD_NR / 8`) |
| `max_ptes_shared` | скільком сторінкам вікна дозволено бути спільними (після `fork`) | `256` (`HPAGE_PMD_NR / 2`) |
| `defrag` | чи вільно самому `khugepaged` запускати ущільнення | `1` |
| `pages_collapsed` | лише читання: скільки вікон згорнуто від завантаження | — |
| `full_scans` | лише читання: скільки разів пройдено всі ділянки | — |

`max_ptes_none` зі значенням 511 із 512 — саме той важіль, за яким тягнеться репутація THP як «пожирача пам'яті». За домовленістю ядро згортає вікно, у якому зайнята **одна-єдина** сторінка з п'ятисот дванадцяти, роздуваючи чотири кілобайти корисного до двох мегабайтів зайнятого. Для рідкої купи з розкиданими живими об'єктами це видно в `RSS` як цілком реальні гігабайти. Лікується не вимкненням THP, а меншим значенням — або новим `shrink_underused`, який розбирає роздуте назад під тиском.

Швидкість обходу рахується прямо з двох чисел, і рахунок вартий того, щоб зробити його один раз:

```
сторінок за секунду = pages_to_scan · 1000 / scan_sleep_millisecs
                    = 4096 · 1000 / 10000 = 409.6

повний обхід 24 ГіБ дрібними сторінками:
    24 ГіБ / 4 КіБ = 6291456 сторінок
    6291456 / 409.6 ≈ 15360 с ≈ 4.3 години
```

Чотири з половиною години — саме тому на щойно завантаженому індексі в двадцять чотири гігабайти `AnonHugePages` довго лишається майже нульовим, хоч усе начебто ввімкнено. Хто не хоче чекати, той не крутить `pages_to_scan`, а просить згортання синхронно.

### madvise і prctl

```c
#include <sys/mman.h>
int madvise(void *addr, size_t length, int advice);
```

| порада | значення | з версії | що робить |
|---|---|---|---|
| `MADV_HUGEPAGE` | 14 | 2.6.38 | позначити ділянку як бажану для великих сторінок; діє і на майбутні збої, і на `khugepaged` |
| `MADV_NOHUGEPAGE` | 15 | 2.6.38 | заборонити великі сторінки на ділянці; згортання її не чіпатиме |
| `MADV_COLLAPSE` | 25 | 6.1 | згорнути **негайно й синхронно**: виклик не повернеться, доки згортання не закінчиться або не провалиться |

`addr` мусить бути вирівняний на звичайну сторінку, інакше `EINVAL`. Але для `MADV_HUGEPAGE` цього замало: ділянка дістане велику сторінку лише там, де в неї вміщається цілий вирівняний блок на 2 МіБ, тож буфер, узятий за довільною адресою, майже напевно не дістане нічого.

`MADV_COLLAPSE` вирізняється тим, що це не порада на майбутнє, а робота тут і зараз, і тому в нього власні помилки:

| помилка | причина |
|---|---|
| `EINVAL` | адреса не вирівняна на сторінку, або ділянка не годиться для великих сторінок узагалі |
| `ENOMEM` | не вдалося взяти велику сторінку — суцільного блоку немає |
| `EBUSY` | велика сторінка не влізла в стелю пам'яті контрольної групи |
| `EAGAIN` | тимчасова перешкода (блокування, гонка) — спробувати ще раз |

Цінність цього виклику в тому, що він дає програмі обрати **момент** оплати: згорнути індекс одразу після завантаження, поки ніхто не чекає на відповідь, а не посеред обслуговування запиту й не за чотири години фонового обходу.

Останній важіль — на весь процес, а не на ділянку:

```c
#include <sys/prctl.h>
prctl(PR_SET_THP_DISABLE, 1, 0, 0, 0);                             /* геть усе */
prctl(PR_SET_THP_DISABLE, 1, PR_THP_DISABLE_EXCEPT_ADVISED, 0, 0); /* лише за madvise */
prctl(PR_GET_THP_DISABLE, 0, 0, 0, 0);
```

`PR_SET_THP_DISABLE` існує з версії 3.15 і вимикає прозорі сторінки для всього процесу, не питаючи глобальних вимикачів. Прапорець успадковується через `fork` і **переживає `exec`** — а отже, обгортка, яка виставила його й запустила службу, вимкнула THP саме цій службі, не чіпаючи решту машини. Це найакуратніший спосіб вимкнути THP там, де це справді потрібно: не `never` на всю систему, а на один процес.

## Частина третя: чим це все міряється

### `/proc/meminfo` — стан системи

| рядок | що показує |
|---|---|
| `HugePages_Total` | розмір пулу розміру за домовленістю, у сторінках |
| `HugePages_Free` | скільки з них іще не роздано; **включає обіцяні** |
| `HugePages_Rsvd` | скільки з вільних уже комусь обіцяно через `mmap` |
| `HugePages_Surp` | скільки взято понад `nr_hugepages` (стеля — `nr_overcommit_hugepages`) |
| `Hugepagesize` | розмір за домовленістю, у кБ |
| `Hugetlb` | сумарно по **всіх** розмірах, у кБ — скільки пам'яті вилучено із системи |
| `AnonHugePages` | скільки анонімної пам'яті лежить під прозорими сторінками рівня PMD |
| `ShmemHugePages` | те саме для `tmpfs` і спільної пам'яті |
| `FileHugePages` | те саме для кешу сторінок звичайних файлів |
| `ShmemPmdMapped` | скільки зі `ShmemHugePages` справді відображено одним записом PMD, а не 512 дрібними |

![Смуга пулу, розділена на роздане, обіцяне й вільне: HugePages_Free охоплює й обіцяне теж](/reference/unix-linux/memory/huge-pages/img/pool-accounting.svg)

*Найчастіша помилка читання — вважати `Free` за наявне. Обіцяне лежить незайнятим, але вже нічиє.*

```
справді доступно новому охочому = HugePages_Free − HugePages_Rsvd
```

Різниця між `ShmemHugePages` і `ShmemPmdMapped` теж варта уваги: перше — скільки великих сторінок узято, друге — скільки з них справді дають виграш у TLB. Велика сторінка, яку довелося відобразити дрібними записами (бо ділянка не вирівняна або її частину перекрито), потрапляє тільки в перший рядок, і різниця між цими двома числами — це пам'ять, витрачена без жодної користі.

### `/proc/<pid>/smaps` — стан однієї ділянки

Кожна ділянка простору має власний блок рядків, і це єдине місце, де видно, чи стала великою саме та пам'ять, заради якої все робилося.

| поле | що показує |
|---|---|
| `AnonHugePages` | скільки анонімної пам'яті цієї ділянки під великими сторінками |
| `ShmemPmdMapped` | те саме для спільної пам'яті |
| `FilePmdMapped` | те саме для відображеного файлу |
| `Shared_Hugetlb` | сторінки з `hugetlbfs`, спільні з іншими; **у `RSS` і `PSS` не входять** |
| `Private_Hugetlb` | сторінки з `hugetlbfs`, приватні; так само не входять у `RSS` |
| `THPeligible` | `1`, якщо ділянка взагалі придатна для великих сторінок; `0`, якщо ні |
| `VmFlags` | серед літер: `ht` — ділянка з `hugetlbfs`, `hg` — стоїть `MADV_HUGEPAGE`, `nh` — стоїть `MADV_NOHUGEPAGE` |

Те, що пам'ять з `hugetlbfs` не входить у `RSS`, — історична незручність, але про неї треба знати: процес із восьмигігабайтовим пулом виглядатиме в `top` як такий, що займає сотні мегабайтів. Шукати ці гігабайти треба в `Hugetlb` у `/proc/meminfo` і в `Private_Hugetlb` у `smaps`.

`THPeligible` — найшвидша відповідь на питання «чому нічого не згортається». Нуль тут означає, що далі крутити вимикачі марно: ділянка не годиться в принципі — замала, не вирівняна, або на ній стоїть `MADV_NOHUGEPAGE`.

### `/proc/vmstat` — чи вдаються спроби

| лічильник | що рахує |
|---|---|
| `thp_fault_alloc` | вдалих великих сторінок, узятих просто на збої |
| `thp_fault_fallback` | збоїв, де великої сторінки не знайшлося і взяли дрібні |
| `thp_fault_fallback_charge` | те саме, але причина — стеля контрольної групи, а не брак пам'яті |
| `thp_collapse_alloc` | вікон, згорнутих `khugepaged` або `MADV_COLLAPSE` |
| `thp_collapse_alloc_failed` | невдалих спроб згортання |
| `thp_file_alloc` / `thp_file_fallback` | те саме для кешу сторінок файлів |
| `thp_split_pmd` | розбиттів великої сторінки на 512 звичайних записів |
| `thp_split_page` / `thp_split_page_failed` | розбиттів самої сторінки (а не лише запису) |
| `thp_deferred_split_page` | розбиттів, відкладених до тиску на пам'ять |
| `thp_underused_split_page` | розбиттів, зроблених `shrink_underused` через порожнечу всередині |
| `thp_zero_page_alloc` | виділень спільної нульової великої сторінки |
| `thp_swpout` / `thp_swpout_fallback` | великих сторінок, вивантажених цілком / розбитих задля вивантаження |
| `compact_stall` | скільки разів прикладний потік **стояв** на ущільненні |
| `compact_fail` / `compact_success` | невдалих і вдалих ущільнень |

Читати їх варто парами, і найважливіша пара — перша:

```sh
$ grep -E 'thp_fault_(alloc|fallback)$|thp_collapse_alloc$|compact_stall' /proc/vmstat
thp_fault_alloc 18422
thp_fault_fallback 96431
thp_collapse_alloc 311
compact_stall 4127
```

Тут `fallback` уп'ятеро більший за `alloc`: суцільних блоків бракує, програма здебільшого працює на дрібних сторінках і при цьому регулярно платить за марні спроби. А чотири тисячі `compact_stall` кажуть, що частину цих спроб оплачено прикладними потоками — тобто гістограма затримок уже зіпсована.

Усі ці числа — накопичувальні від завантаження, тому дивитися треба **різницю** за проміжок, а не абсолютне значення:

```sh
$ grep -E 'thp_|compact_' /proc/vmstat > /tmp/a; sleep 60
$ grep -E 'thp_|compact_' /proc/vmstat > /tmp/b
$ join /tmp/a /tmp/b | awk '$3 != $2 { print $1, $3 - $2 }'
```

### Знімок стану однією командою

Останнє, що варто мати під рукою, — коротка вибірка, яка відповідає на все одразу: що є в системі, що дісталося процесові й чи вдаються спроби.

```sh
#!/bin/sh
echo "── розміри, які вміє машина ──"
ls -1 /sys/kernel/mm/hugepages/

echo "── пул ──"
grep -E 'HugePages_|Hugepagesize|^Hugetlb' /proc/meminfo

echo "── THP: вимикачі ──"
for f in enabled defrag shrink_underused hpage_pmd_size; do
        printf '%-18s %s\n' "$f" "$(cat /sys/kernel/mm/transparent_hugepage/$f)"
done

echo "── THP: скільки вже лежить під великими сторінками ──"
grep -E 'AnonHugePages|ShmemHugePages|FileHugePages|ShmemPmdMapped' /proc/meminfo

echo "── чи вдаються спроби ──"
grep -E 'thp_fault_(alloc|fallback)$|thp_collapse_alloc$|compact_stall' /proc/vmstat

echo "── що дісталося процесові $1 ──"
awk '/^[0-9a-f]+-/ { rng=$0 }
     /^AnonHugePages:/ && $2 > 0 { print rng; print "  " $0 }' "/proc/$1/smaps"
```

Останній шматок вартий окремої згадки: він друкує лише ті ділянки, де `AnonHugePages` більший за нуль. У процесі із сотнями відображень це рятує від гортання й одразу показує, чи стала великою саме та ділянка, заради якої все затівалося.
