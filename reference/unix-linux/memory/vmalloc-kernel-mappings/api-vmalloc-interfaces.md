# 📋 Двері в область vmalloc: сигнатури, контексти, /proc/vmallocinfo

Це перелік усього, чим у Linux заходять в область vmalloc: якою функцією просять адреси, яким прапорцем описують ділянку, чим її звільняють і що потім читають у `/proc`. Два питання тут важать більше за самі сигнатури — **звідки виклик дозволено** і **хто після нього володіє сторінками**; саме на них ламається код, який компілюється без жодного попередження.

Описано ядро приблизно від 6.17; там, де інтерфейс змінювався недавно, версію названо — приклади зі старіших джерел дослівно не зберуться.

**Одна деталь про імена.** Від 6.10 усі ці функції — макроси-обгортки: `vmalloc(size)` розкривається у `vmalloc_noprof(size)` під обліковою міткою того місця, звідки покликали. У заголовках ви побачите прототипи із суфіксом `_noprof`, у `/proc/kallsyms` — символи з ним же, а в коді пишете звичайне ім'я. Побічний зиск приємний: файл `/proc/allocinfo` показує, скільки байтів висить на кожному рядку коду.

## Виділити

```c
/* базові */
void *vmalloc(unsigned long size);
void *vzalloc(unsigned long size);                      /* + занулення */
void *vmalloc_node(unsigned long size, int node);
void *vzalloc_node(unsigned long size, int node);

/* масиви — з перевіркою переповнення добутку n · size */
void *vmalloc_array(size_t n, size_t size);
void *vcalloc(size_t n, size_t size);                   /* те саме + занулення */

/* особливі призначення */
void *vmalloc_user(unsigned long size);                 /* під віддачу в простір користувача */
void *vmalloc_32(unsigned long size);                   /* кадри, адресовані 32 бітами */
void *vmalloc_32_user(unsigned long size);

/* зі своїми прапорцями й параметрами */
void *__vmalloc(unsigned long size, gfp_t gfp_mask);
void *vmalloc_huge_node(unsigned long size, gfp_t gfp_mask, int node);  /* від 6.16 */
void *__vmalloc_node_range(unsigned long size, unsigned long align,
                           unsigned long start, unsigned long end,
                           gfp_t gfp_mask, pgprot_t prot,
                           unsigned long vm_flags, int node, const void *caller);

/* змінити розмір, зберігши вміст (від 6.12) */
void *vrealloc(const void *p, size_t size, gfp_t flags);

void vfree(const void *addr);
```

| Виклик | Що додає понад `vmalloc` | Позначка ділянки |
| --- | --- | --- |
| `vmalloc` | нічого: `GFP_KERNEL`, права `PAGE_KERNEL` (читання-запис, без виконання), будь-який вузол | `VM_ALLOC` |
| `vzalloc` · `vzalloc_node` | `__GFP_ZERO` | `VM_ALLOC` |
| `vmalloc_node` | перевагу названому вузлу пам'яті; це побажання, а не вимога | `VM_ALLOC` |
| `vmalloc_array` · `vcalloc` | множення `n · size` з перевіркою переповнення — при переповненні `NULL`, а не буфер, коротший за потрібний | `VM_ALLOC` |
| `vmalloc_user` | занулення, вирівнювання під `SHMLBA` і дозвіл віддати ділянку в простір користувача | `VM_ALLOC \| VM_USERMAP` |
| `vmalloc_32` | кадри, чия фізична адреса вміщається в 32 біти (`GFP_VMALLOC32`) — для старих пристроїв | `VM_ALLOC` |
| `vmalloc_huge_node` | дозвіл лягти великими сторінками, якщо розмір не менший за `PMD_SIZE` | `VM_ALLOC \| VM_ALLOW_HUGE_VMAP` |
| `__vmalloc_node_range` | усе одразу: діапазон адрес, вирівнювання, права сторінок, прапорці `VM_*`, вузол, підмінений «викликач» для звіту | яку задасте |

Спільне для всієї родини: розмір округлюється вгору до сторінки, при невдачі повертається `NULL`, а **кожен із цих викликів може заснути**. Він бере кадри по одному й будує проміжні рівні таблиць сторінок — обидві дії чекають. Тому з обробника переривання чи з-під [спін-замка](book:unix-linux/kernel-locking) виділяти звідси не можна, і компілятор про це не скаже.

> 🔧 **Навіщо це.** Найпоширеніше хибне твердження про цю область — «`vmalloc` кладе великі сторінки». Клав, і то лише один рік. У 5.13 механізм увімкнули для всіх виділень від `PMD_SIZE`, а вже в 5.19 прапорець `VM_NO_HUGE_VMAP` замінили на протилежний за змістом `VM_ALLOW_HUGE_VMAP`: великі сторінки стали **дозволом, а не типовою поведінкою**. Причина проста — той, хто отримав покажчик від `vmalloc`, має право поміняти права окремій сторінці всередині ділянки, а велику сторінку так не розділити. Сьогодні великі сторінки дістаються лише тим, хто попросив явно: `vmalloc_huge_node`, `kvmalloc` і прямі викликачі `__vmalloc_node_range` із цим прапорцем. Звичайний `vmalloc` кладе ділянку сторінками по чотири кілобайти, і жодна кількість вільної пам'яті цього не змінить.

Великі сторінки взагалі можливі лише там, де архітектура оголосила `CONFIG_HAVE_ARCH_HUGE_VMALLOC` (він, своєю чергою, вимагає `HAVE_ARCH_HUGE_VMAP`) — це x86-64, arm64 і powerpc з radix-MMU. Механізм увів Nicholas Piggin у 5.13, спершу для powerpc; решта архітектур підхопили пізніше.

## Відобразити вже готові сторінки

Родина `vmalloc` бере кадри сама. Ця — не бере: ви приносите готовий масив сторінок, а ядро лише зшиває їх у суцільний діапазон адрес.

```c
void *vmap(struct page **pages, unsigned int count,
           unsigned long flags, pgprot_t prot);
void  vunmap(const void *addr);

void *vmap_pfn(unsigned long *pfns, unsigned int count, pgprot_t prot);

void *vm_map_ram(struct page **pages, unsigned int count, int node);
void  vm_unmap_ram(const void *mem, unsigned int count);
void  vm_unmap_aliases(void);
```

Головне в цій трійці — не сигнатури, а те, хто після виклику відповідає за самі кадри.

![Три контракти на кадри: хто їх узяв, хто поверне і що саме знімає парний виклик](/reference/unix-linux/memory/vmalloc-kernel-mappings/img/vmap-ownership.svg)

*Помилка тут не падає одразу: відображення знято, покажчик недійсний, а кадри тихо висять зайнятими до перезавантаження.*

| Виклик | Хто дав кадри | Чим знімати | Що станеться з кадрами |
| --- | --- | --- | --- |
| `vmalloc` і вся його родина | ядро | `vfree` | ядро їх і поверне |
| `vmap` без особливих прапорців | ви | `vunmap` | **лишаться вашими** — знято лише відображення |
| `vmap` із `VM_MAP_PUT_PAGES` | ви, але володіння передано | `vfree` (**не** `vunmap`) | ядро зніме по посиланню з кожної сторінки й звільнить сам масив `pages` |
| `vmap_pfn` | ніхто: за цими номерами може взагалі не бути `struct page` | `vunmap` | нічого — там пам'ять пристрою |
| `vm_map_ram` | ви | `vm_unmap_ram` | лишаться вашими |

`VM_MAP_PUT_PAGES` — єдиний спосіб перекласти прибирання на ядро, і в нього є умова: масив `pages` мусить бути виділений через `kmalloc` або `vmalloc`, бо `vfree` його потім звільнить. Масив на стеку чи статичний тут дає пошкодження купи.

`vm_map_ram` — це швидкий шлях для **короткочасних дрібних** відображень. Поки `count` менший за `VMAP_MAX_ALLOC` (він дорівнює `BITS_PER_LONG`, тобто 64 сторінкам, або 256 КіБ при сторінці 4 КіБ), запит обслуговує запас адрес, викроєний [на кожному ядрі процесора окремо](book:unix-linux/per-cpu-data), без походу в спільне дерево. Ціна за швидкість написана в самому коментарі ядра: змішайте тут довгоживучі й короткоживучі об'єкти — і область роздрібниться так, що великі запити перестануть влазити. У `vm_unmap_ram` доведеться передати **той самий** `count`: часткового зняття інтерфейс не має.

`vm_unmap_aliases()` стоїть окремо. Він примусово доганяє всі відкладені зняття відображень і чекає розсилки. Потрібен він тому, хто збирається змінити права сторінок у прямому відображенні: доки в області vmalloc висить хай і знятий, але ще не вичищений із [TLB](book:programming/tlb) псевдонім тієї самої сторінки, процесор може ходити до неї старим шляхом зі старими правами.

## Звільнити — і звідки саме

Тут ховається найтонше місце всього переліку.

```c
void vfree(const void *addr);          /* сам вирішує, звільняти зараз чи відкласти */
void vfree_atomic(const void *addr);   /* завжди відкладає */
void vunmap(const void *addr);
void vm_unmap_ram(const void *mem, unsigned int count);
void kvfree(const void *addr);
void kvfree_sensitive(const void *addr, size_t len);   /* затерти нулями, тоді звільнити */
void iounmap(volatile void __iomem *addr);
```

| Виклик | Контекст задачі | Під спін-замком | Обробник переривання | NMI |
| --- | --- | --- | --- | --- |
| `vfree` | **може заснути** | ✖ — засне | ✔ відкладе роботу в чергу | ✖ |
| `vfree_atomic` | ✔ | ✔ | ✔ | ✖ |
| `vunmap` | **може заснути** | ✖ | ✖ | ✖ |
| `vm_unmap_ram` | **може заснути** | ✖ | ✖ | ✖ |
| `kvfree` | **може заснути** | ✖ | ✔ | ✖ |
| `kvfree_atomic` (у свіжих ядрах) | ✔ | ✔ | ✔ | ✖ |
| `iounmap` | **може заснути** | ✖ | ✖ | ✖ |

`vfree(NULL)` дозволений і нічого не робить — окремої перевірки перед ним не пишуть.

> 🔧 **Навіщо це.** Рядок, з якого все випливає, у ядрі виглядає так: `if (unlikely(in_interrupt())) { vfree_atomic(addr); return; }`. Умова питає **не** «чи ми в атомарному контексті», а «чи ми в перериванні». Спін-замок, узятий у контексті задачі, забороняє спати, але `in_interrupt()` при ньому дає нуль — і `vfree` спокійно піде довгим шляхом, який чекає. Отримаєте ви не тихе псування, а гучне «BUG: sleeping function called from invalid context», і то лише на ядрі, зібраному з відповідними перевірками. Правило просте: **у перериванні `vfree` безпечний, під замком — ні**. Скрізь, де спати не можна, а в перериванні ви не перебуваєте, кличте `vfree_atomic` явно. У немаскованому перериванні не можна нічого: там стоїть `BUG_ON(in_nmi())`.

Ще дві умови, які легко проґавити:

- Ділянку з прапорцем `VM_FLUSH_RESET_PERMS` **не можна** звільняти з атомарного контексту взагалі: при знятті вона мусить відновити права сторінок у прямому відображенні й дочекатися розсилки.
- `vunmap` не звільняє кадрів. Якщо ви їх колись брали в розподільника, після `vunmap` треба віддати їх самому — інакше маєте витік, який `/proc/vmallocinfo` уже не покаже, бо ділянки там більше немає.

## kvmalloc: компроміс і його правила

```c
void *kvmalloc(size_t size, gfp_t flags);
void *kvzalloc(size_t size, gfp_t flags);
void *kvmalloc_node(size_t size, gfp_t flags, int node);
void *kvmalloc_array(size_t n, size_t size, gfp_t flags);
void *kvcalloc(size_t n, size_t size, gfp_t flags);
void *kvrealloc(const void *p, size_t size, gfp_t flags);
void  kvfree(const void *addr);
```

Спершу пробує [суцільний блок кадрів](book:unix-linux/kernel-memory-slab), при невдачі відкочується сюди. Правила, які з цього випливають, стосуються прапорців:

| Прапорець | Чи можна | Чому |
| --- | --- | --- |
| `GFP_KERNEL` і надмножини | ✔ | звичайний випадок |
| `__GFP_RETRY_MAYFAIL` | ✔ | «старайся суцільним довше»; беруть, коли розсипана пам'ять справді гірша |
| `__GFP_NORETRY` | ✖ | суперечить самій ідеї: перша спроба тут **уже** одноразова |
| `GFP_NOWAIT` · `GFP_ATOMIC` | ✖ у ядрах по 6.18 | побудова таблиць вимагала чекання, і виклик просто повертав `NULL` |
| `GFP_NOWAIT` · `GFP_ATOMIC` | ✔ у свіжих | серія Uladzislau Rezki (у мейнлайні від кінця 2025 року) навчила відкат працювати без чекання; великі сторінки при цьому вимикаються, бо той шлях досі спить |

Дві поведінки, які виклик робить мовчки й про які варто знати. Для запитів **більших за сторінку** він сам додає до першої спроби `__GFP_NOWARN` і, якщо ви не просили `__GFP_RETRY_MAYFAIL`, ще й `__GFP_NORETRY` — щоб гонитва за суцільним блоком не будила [вбивцю за браком пам'яті](book:unix-linux/overcommit-and-oom), коли є куди відкотитися. І він знімає `__GFP_NOFAIL` із першої спроби: обіцянку «не мати права відмовити» виконує відкат, а не `kmalloc`. Нульовий розмір повертає `ZERO_SIZE_PTR` — не `NULL`, і `kvfree` його розуміє.

Звільняти результат треба саме через `kvfree`: він дивиться на адресу й сам вибирає `kfree` чи `vfree`. І головне обмеження, яке жоден прапорець не знімає: **результат може виявитися фізично розсипаним**, тож пристроєві з [прямим доступом до пам'яті](book:unix-linux/dma-and-buffers) його віддавати не можна.

## Спитати про адресу

```c
static inline bool is_vmalloc_addr(const void *x);     /* просте порівняння меж */
int   is_vmalloc_or_module_addr(const void *x);
struct page   *vmalloc_to_page(const void *addr);      /* обхід таблиць */
unsigned long  vmalloc_to_pfn(const void *addr);

struct vm_struct *get_vm_area(unsigned long size, unsigned long flags);
struct vm_struct *find_vm_area(const void *addr);
struct vm_struct *remove_vm_area(const void *addr);

/* лише для ділянок із VM_SPARSE, від 6.9 */
int  vm_area_map_pages(struct vm_struct *area, unsigned long start,
                       unsigned long end, struct page **pages);
void vm_area_unmap_pages(struct vm_struct *area, unsigned long start,
                         unsigned long end);
```

`is_vmalloc_addr` — це буквально `addr >= VMALLOC_START && addr < VMALLOC_END`. Звідси три речі, яких він **не** каже: чи адреса взагалі відображена, чи ділянка прийшла з `vmalloc`, а не з `ioremap` або з-під стека задачі, і чи вона ще жива. Він відповідає лише на питання «чи можна тут застосовувати арифметику прямого відображення» — і відповідь завжди «ні».

`vmalloc_to_page` дає справжній кадр, але коштує повного обходу [таблиць сторінок](book:unix-linux/paging-and-mmu) на кожен виклик — на гарячому шляху це помітно. Для ділянки `ioremap` він поверне `NULL`: за тими адресами кадрів немає, там сидить пристрій.

Що лежить у `struct vm_struct`, яку віддає `find_vm_area`:

| Поле | Зміст |
| --- | --- |
| `addr` · `size` | початок ділянки й **її розмір разом зі сторожовою сторінкою** |
| `requested_size` | скільки байтів попросили насправді (з'явилося заради точної роботи `vrealloc` і санітайзерів) |
| `flags` | набір `VM_*` із таблиці нижче |
| `pages` · `nr_pages` | масив сторінок і їхня кількість; для `ioremap` порожні |
| `page_order` | порядок сторінок, якими лягла ділянка: `0` — звичайні, більше — великі |
| `phys_addr` | фізична адреса, якщо ділянка описує область пристрою |
| `caller` | адреса коду, який ділянку попросив; саме її друкує `/proc/vmallocinfo` |

Заборона, яку варто написати окремим рядком: `virt_to_phys`, `__pa` й `virt_to_page` на адресі з цієї області дають **сміття**, а не помилку. Вони роблять арифметику зі сталим зсувом, якої тут немає. Ядро, зібране з `CONFIG_DEBUG_VIRTUAL`, на таке лається; звичайне — мовчить і повертає число.

## Віддати в простір користувача

```c
void *vmalloc_user(unsigned long size);
int   remap_vmalloc_range(struct vm_area_struct *vma, void *addr,
                          unsigned long pgoff);
int   remap_vmalloc_range_partial(struct vm_area_struct *vma, unsigned long uaddr,
                                  void *kaddr, unsigned long pgoff,
                                  unsigned long size);
```

Це шлях для драйвера, який хоче віддати свій буфер процесові через [`mmap`](book:unix-linux/mmap-model). Дві умови зв'язані між собою: `remap_vmalloc_range` вимагає, щоб на ділянці стояв `VM_USERMAP`, а ставить його саме `vmalloc_user`. Ділянка з-під звичайного `vmalloc` дасть `-EINVAL`. Друга послуга `vmalloc_user` — занулення: без нього процес прочитав би те, що лежало в кадрах до нього.

```c
static int demo_mmap(struct file *f, struct vm_area_struct *vma)
{
    struct demo *d = f->private_data;    /* d->buf узято через vmalloc_user() */

    if (vma->vm_pgoff)                   /* зсув усередині буфера не підтримуємо */
        return -EINVAL;
    if (vma->vm_end - vma->vm_start > d->size)
        return -EINVAL;

    return remap_vmalloc_range(vma, d->buf, 0);
}
```

## Прапорці ділянки: VM_*

Задати їх можна лише там, де інтерфейс приймає `vm_flags`: у `__vmalloc_node_range`, у `vmap` і в `get_vm_area`. Решту проставляє саме ядро.

| Прапорець | Значення | Що означає |
| --- | --- | --- |
| `VM_IOREMAP` | `0x0001` | ділянка описує область пристрою, а не пам'ять |
| `VM_ALLOC` | `0x0002` | сторінки взяв сам `vmalloc` |
| `VM_MAP` | `0x0004` | сторінки принесли ззовні через `vmap` |
| `VM_USERMAP` | `0x0008` | ділянку дозволено віддати в простір користувача |
| `VM_DMA_COHERENT` | `0x0010` | ділянка з-під `dma_alloc_coherent` |
| `VM_UNINITIALIZED` | `0x0020` | опис ще не добудований; службовий, у чужому коді не ставлять |
| `VM_NO_GUARD` | `0x0040` | **не** класти сторожову сторінку в кінці; у заголовку позначено як небезпечний, бо саме сторожова сторінка й тримає ділянки нарізно |
| `VM_KASAN` | `0x0080` | під ділянку виділено тіньову пам'ять санітайзера |
| `VM_FLUSH_RESET_PERMS` | `0x0100` | при знятті відновити права сторінок у прямому відображенні й дочекатися розсилки; таку ділянку не звільнити з атомарного контексту |
| `VM_MAP_PUT_PAGES` | `0x0200` | володіння сторінками й масивом `pages` переходить до ядра; звільняти через `vfree` |
| `VM_ALLOW_HUGE_VMAP` | `0x0400` | дозволити великі сторінки там, де архітектура це вміє |
| `VM_DEFER_KMEMLEAK` | `0x0800` | відкласти реєстрацію об'єкта в шукачеві витоків |
| `VM_SPARSE` | `0x1000` | розріджена ділянка: відображені не всі сторінки, решта заповнюється потім через `vm_area_map_pages` |

Три з них у сумісності одне з одним обмежені: розріджена ділянка не може мати ні `VM_FLUSH_RESET_PERMS`, ні `VM_NO_GUARD` — ядро це перевіряє явно.

## Регістри пристроїв: ioremap

Ці виклики теж кладуть записи в область vmalloc, але за ними немає жодного кадра — там [самі регістри контролера](book:programming/memory-mapped-io).

```c
void __iomem *ioremap(phys_addr_t offset, size_t size);
void __iomem *ioremap_wc(phys_addr_t offset, size_t size);
void __iomem *ioremap_wt(phys_addr_t offset, size_t size);
void __iomem *ioremap_np(phys_addr_t offset, size_t size);
void __iomem *ioremap_uc(phys_addr_t offset, size_t size);
void          iounmap(volatile void __iomem *addr);

void *memremap(resource_size_t offset, size_t size, unsigned long flags);
void  memunmap(void *addr);

/* з прив'язкою до життя пристрою — знімаються самі */
void __iomem *devm_ioremap(struct device *dev, resource_size_t offset,
                           resource_size_t size);
void __iomem *devm_ioremap_resource(struct device *dev, const struct resource *res);
void __iomem *devm_platform_ioremap_resource(struct platform_device *pdev,
                                             unsigned int index);
```

| Виклик | Як процесор поводиться з цією областю |
| --- | --- |
| `ioremap` | без кеша, без випереджального читання, без переставляння й склеювання записів — типовий вибір для керуючих регістрів |
| `ioremap_wc` | звичайна пам'ять зі склеюванням записів: процесор може передбачати, переставляти й зливати сусідні записи в один пакет; беруть для кадрових буферів, де важить пропускна здатність |
| `ioremap_wt` | наскрізний запис — читання кешуються; сьогодні майже не потрібен |
| `ioremap_np` | запис без відкладання (non-posted): інструкція не завершиться, поки пристрій не прийме дані; потрібен окремим платформам, для PCI не рекомендований |
| `ioremap_uc` | має сенс лише на давньому x86-32 і ia64; переносний код бере просто `ioremap` |
| `memremap` | для **справжньої пам'яті**, а не регістрів: `MEMREMAP_WB`, `MEMREMAP_WT`, `MEMREMAP_WC` — і повертає звичайний покажчик, не `__iomem` |

Правила поводження з результатом строгі. Покажчик `__iomem` **не розіменовують**: усе читання й запис ідуть через `readb`/`readw`/`readl`/`readq` і `writeb`/…/`writeq`, блоки — через `memcpy_fromio`, `memcpy_toio`, `memset_io`. Причина не в стилі, а в тому, що на різних архітектурах ці функції розкриваються в різні інструкції з різними бар'єрами; звичайне присвоєння там просто не працює. Виклик `iounmap` обов'язковий: адреси в області скінченні, і драйвер, який їх не повертає, вичерпує її на всю систему. Найпростіше цього не забути з `devm_`-варіантами — вони знімають відображення разом із від'єднанням пристрою.

`ioremap` на діапазон, який ядро вважає звичайною пам'яттю, свідомо відмовляє: для пам'яті є `memremap`.

## Межі області, конфіги, параметри завантаження

| Позначення | Що це |
| --- | --- |
| `VMALLOC_START` · `VMALLOC_END` | межі області; задає архітектура, читати як константи не можна — при `CONFIG_RANDOMIZE_MEMORY` основу зсуває [випадковість розкладки](book:unix-linux/address-space-randomization) |
| `VMALLOC_TOTAL` | `VMALLOC_END − VMALLOC_START`; те саме число видно як `VmallocTotal` |
| `PMD_SIZE` | поріг, від якого має сенс просити великі сторінки (на x86-64 — 2 МіБ) |
| `VMAP_MAX_ALLOC` | `BITS_PER_LONG` — стеля `count` для швидкого шляху `vm_map_ram` |

На x86-64 із чотирма рівнями таблиць область займає `ffffc90000000000`–`ffffe8ffffffffff`, тобто 32 ТіБ; із п'ятьма — `ffa0000000000000`–`ffd1ffffffffffff`, 12.5 ПіБ. На arm64 й на 32-бітних архітектурах числа зовсім інші, і питати їх треба в системи, а не в пам'яті.

| Параметр завантаження | Дія |
| --- | --- |
| `vmalloc=<nn>[KMG]` | задати області **точний** розмір; має сенс на 32 бітах (x86-32, arm), де типово виходить близько 128 МіБ; додане тут рівно стільки ж віднімається в прямого відображення. Ставиться в [командному рядку ядра](book:unix-linux/bootloader-and-cmdline) |
| `nohugevmalloc` | заборонити великі сторінки для виділень vmalloc |
| `nohugeiomap` | заборонити великі сторінки для відображень `ioremap` |

| Конфіг | Що вмикає |
| --- | --- |
| `CONFIG_HAVE_ARCH_HUGE_VMAP` | архітектура вміє великі сторінки в цій області взагалі |
| `CONFIG_HAVE_ARCH_HUGE_VMALLOC` | те саме дозволено й виділенням vmalloc, а не лише `ioremap`; вимагає попереднього |
| `CONFIG_HAVE_ARCH_VMAP_STACK` | архітектура вміє тримати стеки задач у цій області |
| `CONFIG_VMAP_STACK` | власне вмикає такі стеки: за кожним — сторожова сторінка, тож переповнення дає збій одразу, а не тихе псування сусіда. Наслідок для драйверів: **на дані зі стека не можна ставити прямий доступ пристрою** |
| `CONFIG_KASAN_VMALLOC` | тіньова пам'ять санітайзера для цієї області |
| `CONFIG_DEBUG_VIRTUAL` | лається на `virt_to_phys` від адреси, для якої той не діє |

Стеки в цій області вміють arm64, powerpc, riscv, s390, um і x86.

## /proc/vmallocinfo по полях

Файл дає по рядку на кожну **зайняту** ділянку області. Читає його лише суперкористувач (права `0400`), а адреси друкуються через `%pK`, тож на них ще й впливає `kptr_restrict`.

```
0xffffc90000000000-0xffffc90000201000  2101248 alloc_large_system_hash+0x204/0x2c0 pages=512 vmalloc N0=256 N1=256
0xffffc90000302000-0xffffc90000304000     8192 acpi_tb_verify_table+0x21/0x4f phys=7fee8000 ioremap
0xffffc90000a10000-0xffffc90000a15000    20480 vm_map_ram
```

Обов'язкові тут лише перші два поля; усе інше з'являється залежно від того, звідки ділянка взялася.

| Поле | Коли з'являється | Зміст |
| --- | --- | --- |
| `0x<початок>-0x<кінець>` | завжди | межі ділянки; різниця точно дорівнює наступному полю |
| `<розмір>` | завжди | байтів, **разом зі сторожовою сторінкою** |
| `<викликач>` | майже завжди | символ і зсув того, хто ділянку попросив; для коду [модуля](book:unix-linux/kernel-modules) — з іменем модуля у квадратних дужках |
| `pages=<n>` | коли за ділянкою є сторінки | скільки їх; для `ioremap` поля немає |
| `phys=<адреса>` | коли записано фізичну адресу | ділянки `ioremap` і `dma-coherent` |
| `ioremap` | `VM_IOREMAP` | область пристрою |
| `vmalloc` | `VM_ALLOC` | сторінки взяв сам `vmalloc` |
| `vmap` | `VM_MAP` | сторінки принесені ззовні |
| `user` | `VM_USERMAP` | ділянку можна віддати в простір користувача |
| `sparse` | `VM_SPARSE` | відображені не всі сторінки діапазону |
| `dma-coherent` | `VM_DMA_COHERENT` | з-під `dma_alloc_coherent` |
| `vpages` | автоматично | сам масив покажчиків на сторінки довелося виділяти через `vmalloc` — ознака великої ділянки |
| `N<вузол>=<n>` | на машинах із [нерівномірним доступом](book:programming/numa) | скільки сторінок узято на кожному вузлі; сума дорівнює `pages=` |

Ділянки з-під `vm_map_ram` мають коротку форму: діапазон, розмір і слово `vm_map_ram` — ні викликача, ні лічильника сторінок там немає.

**Умова: `vmalloc(1 << 20)` на машині з чотирикілобайтною сторінкою.**

```
попросили                  = 1048576 Б  = 256 сторінок
сторожова сторінка         =    4096 Б  =   1 сторінка
у файлі буде <розмір>      = 1052672 Б  = 257 сторінок
кінець − початок           = 1052672 Б            ✔ збігається
pages=                     =     256              ← сторожової тут немає
```

Тобто `pages=` рахує **корисні** сторінки, а `<розмір>` — зайняті адреси. Різниця завжди рівно одна сторінка, доки на ділянці не стоїть `VM_NO_GUARD`. Панель моніторингу, яка підсумовує `<розмір>`, на десятках тисяч дрібних ділянок накрутить зайвого рівно на їхню кількість сторінок.

Поріг для позначки `vpages` рахується так само однозначно:

**Умова: 64-бітна машина, сторінка 4 КіБ, покажчик 8 Б.**

```
масив покажчиків = nr_pages · 8 Б
у kmalloc іде, поки масив ≤ 4096 Б  →  nr_pages ≤ 512
512 сторінок · 4 КіБ = 2 МіБ

⇒ vpages з'являється на ділянках, більших за 2 МіБ
```

Три пастки читання цього файлу, кожна з яких уже коштувала комусь вечора:

- **Тут немає відкладених ділянок.** Звільнене, але ще не вичищене з дерева тут не показується, а адреси його ще не вільні. Тому найбільший проміжок, порахований за цим файлом, — оцінка **згори**: наступному запитові може не влізти й те, що ви побачили вільним.
- **Порядок рядків.** Від 6.9, коли дерева зайнятих ділянок розкололи по вузлах, файл збирає рядки з усіх дерев і сортує їх за адресою перед друком. Старіші ядра друкували їх у порядку єдиного списку — теж за адресою. Але покладатися на це в скриптах без перевірки не варто.
- **Викликач — це той, хто попросив, а не той, хто тримає.** Тисяча рядків з `alloc_large_system_hash` — це одна підсистема; тисяча рядків з `kvmalloc_node` не каже нічого, бо `kvmalloc` кличуть звідусіль. У таких випадках допомагає `/proc/allocinfo`, який рахує за рядком коду.

Дві команди, з яких зазвичай починають розбір. Підсумки за функціями, з відкиданням зсуву в символі:

```sh
sudo awk '{ sub(/\+0x.*/, "", $3);
            if ($3 ~ /^[a-zA-Z_]/) s[$3] += $2 }
          END { for (k in s) printf "%12d  %s\n", s[k], k }' /proc/vmallocinfo |
  sort -rn | head -15
```

Найбільший проміжок між сусідніми ділянками (потрібен `gawk` — через `strtonum`):

```sh
sudo gawk '{ split($1, a, "-");
             s = strtonum(a[1]); e = strtonum(a[2]);
             if (prev && s - prev > max) { max = s - prev; at = prev }
             prev = e }
           END { printf "найбільший проміжок: %.1f МіБ від 0x%x\n", max/1048576, at }' \
  /proc/vmallocinfo
```

Перша команда відповідає на питання «хто росте», друга — на «чому не влазить». Обидві варто знімати двічі з проміжком у годину: у цій області важить не значення, а похідна.

## /proc/meminfo: три рядки Vmalloc

```
VmallocTotal:   34359738367 kB
VmallocUsed:      312108 kB
VmallocChunk:          0 kB
```

| Рядок | Зміст |
| --- | --- |
| `VmallocTotal` | розмір **адресного простору** області, `VMALLOC_END − VMALLOC_START`; до зайнятої пам'яті стосунку не має |
| `VmallocUsed` | фізичні сторінки, узяті саме викликами `vmalloc` |
| `VmallocChunk` | жорсткий нуль від 4.4; поле лишили заради сумісності |

Середній рядок довго був нулем — його оживив Roman Gushchin у 5.3, коли частка цієї області в пам'яті машини помітно виросла (стеки задач, BPF, ділянки на кожен процесор). Але рахує він рівно те, що написано: **лише сторінки, узяті самим `vmalloc`**. Ділянки `vmap`, `ioremap` і `vm_map_ram` у це число не входять — за ними або чужі сторінки, або взагалі не пам'ять. Тож зведення `VmallocUsed` і суми розмірів із `/proc/vmallocinfo` не збігаються ніколи, і це не помилка. Решта способів рахувати ту саму пам'ять — [як міряти пам'ять](book:unix-linux/memory-accounting).

## Питання → де відповідь

| Питання | Джерело |
| --- | --- |
| скільки адрес в області взагалі | `/proc/meminfo`: `VmallocTotal` |
| скільки фізичних сторінок тримає `vmalloc` | `/proc/meminfo`: `VmallocUsed` |
| хто саме тримає область | `/proc/vmallocinfo`, підсумки за третім полем |
| скільки з того — регістри пристроїв | рядки з позначкою `ioremap` |
| чому великий запит не влазить | найбільший проміжок між сусідніми рядками |
| який рядок коду виділив байти | `/proc/allocinfo` (`CONFIG_MEM_ALLOC_PROFILING`) |
| чи ділянка лягла великими сторінками | `page_order` у `struct vm_struct` (з-під налагоджувача) |
| чи можна цю адресу дати пристрою | `is_vmalloc_addr` — якщо «так», то не можна |
| з якого контексту звільняти | таблиця контекстів вище: у перериванні `vfree`, під замком `vfree_atomic` |
