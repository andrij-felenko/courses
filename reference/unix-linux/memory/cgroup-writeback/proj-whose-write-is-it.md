# ⚙️ Чий це запис: доводимо лічильниками, кому виписали рахунок

Зберемо на живій машині стенд із двох груп [cgroup v2](book:unix-linux/cgroups) і власного генератора брудних сторінок — і замість того, щоб вірити документації на слово, подивимося чотирма приладами, кому ядро справді записує байти буферизованого запису й у яких трьох випадках рахунок приходить не тому.

## Три твердження, які дослід має підтвердити або спростувати

Дослід вартий заходу лише тоді, коли наперед відомо, який результат його завалить.

1. **Підтримана файлова система.** На ext4 з увімкненими контролерами `memory` та `io` буферизований запис групи потрапляє в **її** `io.stat`, а [`io.max`](book:unix-linux/io-cgroup-control) цієї групи його стримує — хоча програма жодного разу не викликала `fsync()` і взагалі нічого не знає про ліміт.
2. **Непідтримана файлова система.** Ті самі байти мовчки йдуть у кореневу групу. Помилки не буде, ліміт просто не побачить трафіку.
3. **Спільний файл.** Коли в один файл пишуть дві групи, увесь рахунок дістається одній із них — і в другої групи власні лічильники починають суперечити одне одному.

Останнє й буде найцікавішим виміром: суперечність між двома файлами однієї групи — не хиба стенда, а прямий відбиток того, що облік пам'яті ведеться посторінково, а зворотний запис — поінодно.

*Ліворуч від пунктиру питання «чия сторінка» має точну відповідь, праворуч — уже ні.*

## Стенд

Перше, що варто перевірити, — чи ієрархія взагалі друга:

```sh
stat -fc %T /sys/fs/cgroup      # cgroup2fs — інакше нижче немає сенсу читати
grep -o 'memory\|io' /sys/fs/cgroup/cgroup.controllers
```

Далі — окремий носій, який не шкода стерти, і дві групи-листки під спільним батьком:

```sh
DEV=/dev/nvme0n1                        # ⚠️ цілий пристрій; наступний рядок стирає вміст
MAJMIN=$(lsblk -ndo MAJ:MIN "$DEV")     # 259:0
MNT=/mnt/wblab
mkfs.ext4 -qF "$DEV"; mkdir -p "$MNT"; mount "$DEV" "$MNT"

ROOT=/sys/fs/cgroup; CG=$ROOT/wblab
echo "+memory +io" > "$ROOT/cgroup.subtree_control"
mkdir -p "$CG"/{a,b}
echo "+memory +io" > "$CG/cgroup.subtree_control"

in_cg() { ( echo $BASHPID > "$CG/$1/cgroup.procs"; shift; exec "$@" ); }
```

Контролер видно в групі лише тоді, коли його ввімкнув **батько**, — тому два `echo`, а не один. Тонкощі з [номером пристрою](book:unix-linux/major-minor-numbers) — чому не `stat -c '%t:%T'` і чому не розділ — розібрано в [сусідній лабораторній](book:unix-linux/io-cgroup-control/proj-two-groups-lab.md); тут вони ті самі.

## Генератор бруду

Готові інструменти сюди не годяться: потрібно однією ручкою перемикати буферизований запис на [прямий](book:unix-linux/buffered-and-direct-io), другою задавати темп `fsync()`, а третьою — початковий зсув, щоб два процеси писали в один файл, але в різні мегабайти й ніколи не ділили сторінку.

```c
/* dirtier.c — керований генератор брудних сторінок; cc -O2 -o dirtier dirtier.c */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define BLK (1u << 20)                  /* 1 МіБ: кратний будь-якому логічному блоку */

int main(int argc, char **argv)
{
    if (argc < 4) {
        fprintf(stderr, "usage: %s <файл> <МіБ> buffered|direct"
                        " [fsync_кожні_МіБ] [зсув_МіБ]\n", argv[0]);
        return 2;
    }
    const char *path   = argv[1];
    long        mib    = atol(argv[2]);
    int         direct = strcmp(argv[3], "direct") == 0;
    long        every  = argc > 4 ? atol(argv[4]) : 0;
    long        start  = argc > 5 ? atol(argv[5]) : 0;

    int flags = O_WRONLY | O_CREAT | (direct ? O_DIRECT : 0);
    int fd = open(path, flags, 0644);
    if (fd < 0) { perror("open"); return 1; }
    if (lseek(fd, (off_t)start * BLK, SEEK_SET) < 0) { perror("lseek"); return 1; }

    void *buf;                          /* O_DIRECT вимагає вирівняного буфера */
    int rc = posix_memalign(&buf, 4096, BLK);          /* повертає код, а не ставить errno */
    if (rc) { fprintf(stderr, "posix_memalign: %s\n", strerror(rc)); return 1; }
    memset(buf, 0xA5, BLK);

    for (long i = 0; i < mib; i++) {
        for (size_t done = 0; done < BLK; ) {
            ssize_t n = write(fd, (char *)buf + done, BLK - done);
            if (n < 0) { perror("write"); return 1; }
            done += (size_t)n;
        }
        if (every && (i + 1) % every == 0 && fsync(fd) < 0) { perror("fsync"); return 1; }
    }
    if (close(fd) < 0) { perror("close"); return 1; }   /* тут спливають відкладені помилки */
    return 0;
}
```

Дві дрібниці в коді не косметичні. `posix_memalign()` замість `malloc()` — бо `O_DIRECT` відкидає невирівняний буфер помилкою `EINVAL`, і саме на цьому спотикається кожен перший дослід. Перевірка `close()` — бо при буферизованому записі помилка пристрою спливає не у `write()`, а пізніше, у `fsync()` або в `close()`.

## Прилади

```sh
snap() {                                 # snap <шлях-до-групи>
  local io mem
  io=$(grep "^$MAJMIN " "$1/io.stat" | tr ' ' '\n' | grep -E '^w(bytes|ios)=' | tr '\n' ' ')
  mem=$(grep -E '^file_(dirty|writeback) ' "$1/memory.stat" 2>/dev/null | tr '\n' ' ')
  printf '%-16s %-34s| %s\n' "${1#$ROOT/}" "${io:-—}" "${mem:-—}"
}
all() { for d in "$CG/a" "$CG/b" "$ROOT"; do snap "$d"; done; }
```

Прочерк у стовпчику пам'яті на корені не помилка: `io.stat` у кореневій групі є, а `memory.stat` там немає за побудовою — його заводять лише на некореневих групах.

Четвертий прилад — [debugfs](book:unix-linux/debugfs), і він єдиний показує розкладку по wb напряму:

```sh
grep -E 'WbCgIno|WbWritten|WbWriteBandwidth' /sys/kernel/debug/bdi/$MAJMIN/wb_stats
stat -c %i "$CG/a"     # цей номер і стоїть у WbCgIno рядка групи A; корінь — 1
```

Файл `wb_stats` з'явився в ядрі 6.10 (робота Ши Кемена); на старіших є лише зведений `stats` на весь пристрій, і третій прилад доведеться замінити на арифметику з `io.stat`.

## Дослід 1: рахунок приходить за адресою

```sh
rm -f "$MNT"/*.dat
time in_cg a ./dirtier "$MNT/a.dat" 512 buffered
sync                                     # доганяємо хвіст, який не встиг злитися
all
```

```
wblab/a          wbytes=536887296 wios=4131        | file_dirty 0 file_writeback 0
wblab/b          wbytes=0 wios=0                   | file_dirty 0 file_writeback 0
/sys/fs/cgroup   wbytes=1806336 wios=74            | —
```

Півгігабайта опинилися там, де їх писали. Неповних два мегабайти на корені — це не похибка, а метадані й журнал ext4: їх скидає спільна задача файлової системи, і вона нічия.

Тепер найважливіше — ліміт:

```sh
echo "$MAJMIN wbps=10485760" > "$CG/a/io.max"      # 10 МіБ/с
time in_cg a ./dirtier "$MNT/a.dat" 512 buffered   # real ≈ 0m52s
```

Програма й далі не викликає `fsync()`, `write()` нічого не знає про `io.max` — а виконується вона рівно стільки, скільки дозволяє стеля. Побачити механізм можна просто під час прогону: у `wb_stats` цієї групи `WbWriteBandwidth` осідає до тих самих десяти мегабайтів, а `WbDirtyThresh` стискається слідом — і поріг брудних сторінок присипляє писаря просто в системному виклику.

Контрольний прогін тим самим кодом, але повз кеш:

```sh
time in_cg a ./dirtier "$MNT/a.dat" 512 direct     # real ≈ 0m51s
```

Час той самий, шлях зовсім інший, і розрізняє їх `memory.stat`: при буферизованому записі `file_dirty` групи росте до сотень мегабайтів, при `O_DIRECT` він увесь прогін стоїть на нулі. Прямий запит подають у контексті того, хто його викликав, тож він обліковувався правильно завжди.

## Дослід 2: файлова система, яка про це не знає

```sh
umount "$MNT"; mkfs.vfat -F 32 "$DEV" >/dev/null; mount "$DEV" "$MNT"
in_cg a ./dirtier "$MNT/a.dat" 512 buffered; sync; all
```

```
wblab/a          wbytes=0 wios=0                   | file_dirty 0 file_writeback 0
wblab/b          wbytes=0 wios=0                   | file_dirty 0 file_writeback 0
/sys/fs/cgroup   wbytes=537526272 wios=4238        | —
```

`io.max` на групі A лишився на місці — і прогін тривав дві секунди замість п'ятдесяти. Ліміт виставлено правильно, він існує в ядрі, повз нього просто пройшов увесь трафік: серед файлових систем, які вміють відносити фоновий запис до групи-власника, лише ext2, ext4, btrfs, f2fs та XFS; vfat туди не входить.

Ознака, за якою це видно без здогадів, доступна ще під час прогону: `file_dirty` групи A росте (облік пам'яті працює на будь-якій ФС), а `io.stat` тієї самої групи не рухається взагалі. У `wb_stats` при цьому єдиний рядок — `WbCgIno: 1`, тобто кореневий wb.

[tmpfs](book:unix-linux/pseudo-filesystems) — випадок іншої природи, і плутати його з цим не варто: її сторінки не пишуться на блоковий пристрій узагалі, тож `io.stat` нульовий і в групи, і в кореня, а в `memory.stat` вони рахуються полем `shmem`, а не `file_dirty`. Тут нема чого відносити не тому — тут просто нема запису.

## Дослід 3: один файл на дві групи

```sh
umount "$MNT"; mkfs.ext4 -qF "$DEV"; mount "$DEV" "$MNT"
echo "$MAJMIN wbps=max" > "$CG/a/io.max"
in_cg a ./dirtier "$MNT/shared.dat" 1024 buffered 0 0    &
in_cg b ./dirtier "$MNT/shared.dat" 1024 buffered 0 1024 &
sleep 5; all                                             # знімок у польоті
wait; sync; all
```

Обидва пишуть у той самий файл, але в різні мегабайти — так жодна сторінка не належить обом, і облік пам'яті лишається однозначним. Знімок посеред прогону і є той доказ, заради якого все будувалося:

```
wblab/a          wbytes=71303168 wios=548          | file_dirty 132132864 file_writeback 8388608
wblab/b          wbytes=0 wios=0                   | file_dirty 139460608 file_writeback 4194304
/sys/fs/cgroup   wbytes=917504 wios=38             | —
```

У групи B сто тридцять три мегабайти **власних** брудних сторінок, чотири мегабайти з них просто зараз пишуться на диск — і нуль записаних байтів. Її сторінки справді зливають, тільки за рахунок групи A: [inode](book:unix-linux/inode-model) у файла один, власник у нього один, і весь запит іде з wb переможця. Підсумковий знімок лише закріплює: `wbytes` групи B так і лишається біля нуля.

Переможцем стає не той, хто перший відкрив файл, а той, чиїх сторінок виявилося більше за час обходу. Тому фора в п'ять секунд для групи B міняє результат **повністю**, а не пропорційно: числа просто переїжджають з рядка в рядок.

Спокуслива гіпотеза «якщо я сам покличу `fsync()`, то принаймні свої байти запишу на себе» перевіряється одним рядком:

```sh
in_cg b ./dirtier "$MNT/shared.dat" 1024 buffered 16 1024 &
```

`wbytes` групи B не зрушить. Синхронний скид теж бере `writeback_control` від **inode-а**, а не від того, хто його викликав, тож `fsync()` із групи B подає запити з wb групи A.

## Пастки, на яких дослід тихо бреше

**Забутий контролер на гілці.** Відсутній `+io` помітний одразу — файла `io.max` просто немає. Відсутній `+memory` не помітний ніяк: файли на місці, ліміт ставиться, а сторінки не пам'ятають своєї групи, і все йде на корінь — рівно як у другому досліді. Дешева перевірка: `grep memory "$CG/a/cgroup.controllers"`.

**Перша версія cgroup.** Якщо `stat -fc %T /sys/fs/cgroup` каже `tmpfs`, або система гібридна й `memory` живе у v1, механізм вимкнено цілком — незалежно від файлової системи.

**Кеш, який ще не злився.** Одразу після виходу програми в `io.stat` буде лише частина: решту заберуть таймери — пробудження раз на п'ять секунд і вік сторінки в тридцять ([`dirty_writeback_centisecs` і `dirty_expire_centisecs`](book:unix-linux/sysctl-tunables)). Або чекайте, або `sync`. Дзеркальна помилка не менш підступна: якщо зняти базовий відлік **після** `sync`, ви втратите весь запис, що вже стався під час прогону. Знімайте до і після й віднімайте.

**Теплий файл.** Другий прогін поверх того самого файлу переписує сторінки, які ще лежать у кеші брудними з першого, і байти не збігаються з очікуваними. Між дослідами — `rm -f` файлу й `echo 3 > /proc/sys/vm/drop_caches`.

**Прибирання.** Групу видаляють лише порожньою й лише `rmdir` — `rm -rf` тут не працює:

```sh
pkill dirtier; sleep 1
rmdir "$CG/a" "$CG/b" "$CG"; umount "$MNT"
```

Забудете прибрати — і група з десятимегабайтною стелею дочекається наступного досліду, а ви шукатимете, чому числа не збігаються з учорашніми.
