# 📋 Поля обліку пам'яті в /proc: що означає кожне число

Ядро віддає облік пам'яті процесу через чотири файли — `statm`, `status`, `smaps` і `smaps_rollup`, — і кожне число в них має точну одиницю, точний лічильник за собою й точну версію ядра, з якої воно взагалі існує. Тут зібрано всі ці поля разом із тим, які саме стовпчики `ps` і `top` з них ростуть, — щоб не доводилося вгадувати, чому два «однакові» показники розходяться.

Числа й формули нижче звірені з деревом ядра (`fs/proc/task_mmu.c`, `fs/proc/array.c`) станом на 6.12 і з джерелами procps-ng (`src/ps/output.c`, `src/top/top.c`, `library/pids.c`). Одиниця `kB` у виводі ядра означає 1024 байти. Прочерк у стовпчику «з ядра» означає, що поле є в усіх ядрах, які ще підтримуються.

## Чотири файли: права, одиниця, ціна

| Файл | Одиниця | Звідки бере число | Права на чужий процес | Що дає унікального |
| --- | --- | --- | --- | --- |
| `/proc/<pid>/statm` | сторінки | лічильники в `mm_struct` | вільно | нічого унікального; найдешевше з усього |
| `/proc/<pid>/status` | kB | ті самі лічильники | вільно | імена полів, піки `VmPeak`/`VmHWM`, розклад RSS на три частини |
| `/proc/<pid>/smaps` | kB | обхід таблиць сторінок кожної ділянки | рівень `ptrace` | `Pss`, приватне проти спільного, прапорці ділянки |
| `/proc/<pid>/smaps_rollup` | kB | той самий обхід, один підсумок | рівень `ptrace` | `Pss` без друку тисяч блоків, `Pss_Anon`/`Pss_File`/`Pss_Shmem` |

Обидва файли зі `smaps` відкриваються через `proc_mem_open(inode, PTRACE_MODE_READ)` — тобто читати чужий процес можна рівно тоді, коли його можна трасувати. Механіка перевірки — у темі про [ptrace](book:unix-linux/ptrace-model). `statm` і `status` такої перевірки не мають і доступні всім, поки `/proc` не змонтовано з `hidepid`.

![Кожне видиме число веде до конкретного лічильника в ядрі](/reference/unix-linux/memory/memory-accounting/img/field-routing.svg)

*Ліворуч — те, що ядро тримає в `mm_struct`; посередині — файли, які це друкують; праворуч — стовпчики, які показують люди. PSS і USS не мають шляху до `ps` чи `top` узагалі.*

## `/proc/<pid>/statm` — сім чисел в один рядок

```
$ cat /proc/self/statm
1174 285 236 6 0 173 0
```

| № поля (`$N` в awk) | Ім'я | Що це в ядрі | Одиниця | Зауваги |
| --- | --- | --- | --- | --- |
| 1 | `size` | `mm->total_vm` | сторінки | те саме число, що `VmSize` |
| 2 | `resident` | `MM_ANONPAGES + MM_FILEPAGES + MM_SHMEMPAGES` | сторінки | те саме число, що `VmRSS` |
| 3 | `shared` | `MM_FILEPAGES + MM_SHMEMPAGES` | сторінки | `RssFile + RssShmem` |
| 4 | `text` (`trs`) | `PAGE_ALIGN(end_code) − (start_code & PAGE_MASK)` | сторінки | розмах адрес коду, а не заселені сторінки |
| 5 | `lib` (`lrs`) | стала | — | у ядрі друкується літеральним нулем |
| 6 | `data` (`drs`) | `mm->data_vm + mm->stack_vm` | сторінки | віртуальний розмір, а не заселений |
| 7 | `dt` | стала | — | так само літеральний нуль |

Три пастки тут варті окремої уваги.

**Одиниця — сторінки, не кілобайти.** Множити треба на `sysconf(_SC_PAGESIZE)`, а не на 4096: на aarch64 сторінка буває 16 або 64 КіБ, на ppc64le — 64 КіБ.

**`shared` не означає «ділю з кимось».** Це просто сума файлових і shmem-сторінок. Один процес, що відобразив свій виконуваний файл і більше нікого поруч не має, покаже в цьому полі всі свої мегабайти коду. Саме це число `top` друкує як `SHR`.

**Поля 4 і 6 віртуальні, попри назви `trs` і `drs`.** Документація ядра прямо позначає обидва як `broken`: четверте включає сегмент даних, шосте — код бібліотек. Обчислюються вони не з лічильників RSS, а з меж сегментів і з `data_vm`/`stack_vm`, тобто з розміру відображень.

## `/proc/<pid>/status` — те саме, але з іменами

```
$ grep -E '^(Vm|Rss|Hugetlb)' /proc/self/status
VmPeak:      1210348 kB
VmSize:      1204120 kB
VmLck:             0 kB
VmPin:             0 kB
VmHWM:        312244 kB
VmRSS:        298120 kB
RssAnon:      186432 kB
RssFile:      103512 kB
RssShmem:       8176 kB
VmData:       512040 kB
VmStk:           132 kB
VmExe:           712 kB
VmLib:         14208 kB
VmPTE:          1160 kB
VmSwap:        40960 kB
HugetlbPages:      0 kB
```

| Поле | З ядра | Що саме це | Заувага |
| --- | --- | --- | --- |
| `VmPeak` | — | `max(mm->total_vm, mm->hiwater_vm)` | пік VSZ за все життя процесу |
| `VmSize` | — | `mm->total_vm` | довжина карти, не пам'ять |
| `VmLck` | — | `mm->locked_vm` | сторінки, замкнені `mlock` |
| `VmPin` | 3.2 | `mm->pinned_vm` | сторінки, які не можна пересунути: DMA, `io_uring`, RDMA |
| `VmHWM` | — | `max(поточний RSS, mm->hiwater_rss)` | пік RSS за все життя |
| `VmRSS` | — | `RssAnon + RssFile + RssShmem` | заселені кадри |
| `RssAnon` | 4.5 | `MM_ANONPAGES` | купа, стеки, `MAP_ANONYMOUS` |
| `RssFile` | 4.5 | `MM_FILEPAGES` | код, дані, відображені файли |
| `RssShmem` | 4.5 | `MM_SHMEMPAGES` | tmpfs, SysV shm, `MAP_SHARED\|MAP_ANONYMOUS` |
| `VmData` | — | `mm->data_vm` | **віртуальний** розмір приватних записуваних відображень, крім стека |
| `VmStk` | — | `mm->stack_vm` | **віртуальний** розмір стека |
| `VmExe` | — | `min(розмах коду, mm->exec_vm)` | **віртуальний** розмір тексту програми |
| `VmLib` | — | `mm->exec_vm − VmExe` | **віртуальний** розмір коду бібліотек |
| `VmPTE` | — | `mm_pgtables_bytes(mm)` | з 4.15 — усі рівні таблиць сторінок; до 4.15 лише PTE |
| `VmPMD` | 4.0–4.14 | другий рівень таблиць | вилучено в 4.15, коли рівні звели в один лічильник |
| `VmSwap` | — | `MM_SWAPENTS` | лише анонімні приватні; своп shmem сюди **не** входить |
| `HugetlbPages` | 4.4 | сторінки hugetlbfs | у `VmRSS` не входить, рахується окремо |

Піки `VmPeak` і `VmHWM` мають тонкість, закладену в самому ядрі: `hiwater_vm` і `hiwater_rss` оновлюються тільки перед тим, як відповідне значення мають **знизити**. Тому ядро друкує максимум із запам'ятованого піка й поточного стану, — інакше щойно зрослий RSS не потрапив би у звіт.

Чотири «віртуальні» рядки посеред таблиці — найчастіше джерело хибних висновків. `VmData` у 512 МіБ не означає, що програма має півгігабайта даних у пам'яті: це сума довжин її приватних записуваних ділянок, з яких заселена може бути десята частина.

Тотожності, які мусять сходитися завжди:

```
VmRSS                = RssAnon + RssFile + RssShmem
statm size           = VmSize / розмір_сторінки
statm resident       = VmRSS  / розмір_сторінки
statm shared         = (RssFile + RssShmem) / розмір_сторінки
statm data           = (VmData + VmStk)     / розмір_сторінки
```

## `/proc/<pid>/smaps` — блок на кожну ділянку

Кожен блок починається рядком того самого формату, що й у `/proc/<pid>/maps`:

```
7f2a4c000000-7f2a4c022000 r-xp 00000000 08:02 1181241  /usr/lib/libc.so.6
└──── діапазон адрес ───┘ │    │        │     │        └ шлях або псевдоім'я
                          │    │        │     └ inode (0 для анонімних)
                          │    │        └ major:minor пристрою
                          │    └ зміщення у файлі
                          └ права: rwx та p (приватне) або s (спільне)
```

Замість шляху бувають псевдоімена `[heap]`, `[stack]`, `[vdso]`, `[vvar]`, а з ядра 5.17 — ще й `[anon:ім'я]` для анонімних ділянок, яким програма сама дала назву через `prctl(PR_SET_VMA, PR_SET_VMA_ANON_NAME, …)`. Сучасна glibc цим користується, тож арени алокатора підписані самі собою: `[anon:glibc: malloc arena]`.

Далі — поля, у порядку друку:

| Поле | З ядра | Що саме це |
| --- | --- | --- |
| `Size` | — | `vm_end − vm_start`: довжина ділянки, від заселеності не залежить |
| `KernelPageSize` | 2.6.29 | найменша сторінка, якою ядро підпирає цю ділянку |
| `MMUPageSize` | 2.6.29 | найменша сторінка, якою для неї може оперувати MMU |
| `Rss` | — | заселено, пораховано обходом таблиць сторінок |
| `Pss` | 2.6.25 | сума `розмір / mapcount` по всіх заселених сторінках ділянки |
| `Pss_Dirty` | 6.0 | та частина `Pss`, що припадає на брудні сторінки |
| `Shared_Clean` | — | сторінки з `mapcount ≥ 2`, чисті |
| `Shared_Dirty` | — | сторінки з `mapcount ≥ 2`, брудні |
| `Private_Clean` | — | сторінки з `mapcount = 1`, чисті |
| `Private_Dirty` | — | сторінки з `mapcount = 1`, брудні |
| `Referenced` | — | сторінки з ознакою недавнього звернення |
| `Anonymous` | — | сторінки, що не належать жодному файлу |
| `KSM` | 6.6 | скільки сторінок ділянки злито механізмом [KSM](book:unix-linux/ksm-page-merging) |
| `LazyFree` | 4.12 | сторінки, позначені `madvise(MADV_FREE)`: ядро може викинути їх без свопу |
| `AnonHugePages` | — | анонімні [великі сторінки](book:unix-linux/huge-pages), відображені на рівні PMD |
| `ShmemPmdMapped` | 4.8 | те саме для shmem |
| `FilePmdMapped` | 5.4 | те саме для файлових відображень, крім shmem |
| `Shared_Hugetlb` | 4.4 | пам'ять hugetlbfs; **не** входить ні в `Rss`, ні в `Pss` |
| `Private_Hugetlb` | 4.4 | те саме, приватна частина |
| `Swap` | — | витіснене з цієї ділянки |
| `SwapPss` | 4.3 | те саме, поділене на `swp_swapcount` — скільки процесів чекають на цю сторінку свопу |
| `Locked` | — | не прапорець, а `Pss` замкнених сторінок ділянки |
| `THPeligible` | 5.0 | `1`, якщо ділянці взагалі можуть дати THP, інакше `0` |
| `ProtectionKey` | 4.9 | номер [ключа захисту пам'яті](book:unix-linux/memory-protection-keys); рядка немає, якщо архітектура ключів не має |
| `VmFlags` | 3.8 | прапорці ділянки двобуквеними кодами |

Чотири речі тут читають неправильно частіше за решту.

**`Locked` — це число, а не «так/ні».** Ядро друкує туди `pss_locked`, тобто пропорційну частку саме замкнених сторінок. Порожня ділянка з прапорцем `VM_LOCKED` дасть `Locked: 0 kB`, і це не суперечність.

**`Swap` у `smaps` і `VmSwap` у `status` рахують різне.** Для shmem-ділянок обхід `smaps` додатково питає в tmpfs, скільки її сторінок пішло у своп, і додає це до `Swap`; `VmSwap` бере лічильник `MM_SWAPENTS`, у якому shmem немає взагалі. Тому сума `Swap` по блоках буває більшою за `VmSwap` — і жодне з чисел не помилкове.

**`Pss` друкується цілими кілобайтами.** Усередині ядро тримає його з точністю 1/4096 байта (звідси й стала `PSS_SHIFT = 12`), а на друк віддає з відкиданням дробової частини. На ділянці в кілька сторінок, розділених між сотнею процесів, це округлення з'їдає весь внесок; у сумі по великому процесу воно неістотне.

**Порядок рядків фіксований, але набір — ні.** Розбирач має шукати поля за іменем і мовчки пропускати незнайомі: між 4.3 і 6.6 у блок додали дев'ять нових рядків, і жорстко зашитий порядок ламається на кожному новому ядрі.

### `VmFlags`: двобуквені коди

Рядок `VmFlags` — єдине місце, де видно внутрішні прапорці ділянки: те, що програма запросила через `mmap` і `madvise`, і те, що ядро вирішило саме.

**Права зараз і права максимально можливі:**

| Код | Значення |
| --- | --- |
| `rd` · `wr` · `ex` | читання · запис · виконання дозволено **зараз** |
| `mr` · `mw` · `me` | читання · запис · виконання дозволити **можна** |
| `sh` | ділянка спільна |
| `ms` | зробити спільною можна |

Пара «зараз/можна» — це різниця між поточними правами й стелею, за яку `mprotect` уже не пустить.

**Природа ділянки:**

| Код | Значення |
| --- | --- |
| `gd` | стек, росте вниз |
| `pf` | чистий діапазон PFN: пам'ять пристрою без структур `struct page` |
| `io` | відображений ввід-вивід |
| `ht` | ділянка на сторінках hugetlb |
| `mm` | змішана ділянка |
| `ac` | ділянка враховується в overcommit |
| `nr` | місце у свопі під неї не зарезервовано |
| `ar` | архітектурний прапорець |

**Поради, які дала програма (`madvise`, прапорці `mmap`):**

| Код | Звідки |
| --- | --- |
| `sr` · `rr` | `MADV_SEQUENTIAL` · `MADV_RANDOM` |
| `hg` · `nh` | `MADV_HUGEPAGE` · `MADV_NOHUGEPAGE` |
| `mg` | `MADV_MERGEABLE` — ділянку віддано механізму KSM |
| `dc` · `de` | `MADV_DONTFORK` · `MADV_DONTEXPAND` |
| `dd` · `wf` | `MADV_DONTDUMP` · `MADV_WIPEONFORK` |
| `dp` | ділянка завжди ліниво звільнювана |
| `lo` · `lf` | сторінки замкнено (`mlock`) · замикати при першому дотику (`MLOCK_ONFAULT`) |

**Особливі режими:**

| Код | Значення |
| --- | --- |
| `sf` | синхронний сторінковий збій (`MAP_SYNC`, постійна пам'ять) |
| `sd` | стежити за брудними сторінками (`soft-dirty`) |
| `um` · `uw` · `ui` | `userfaultfd` стежить за пропусками · за записом · за дрібними збоями |
| `bt` · `mt` | arm64: сторінка під захистом BTI · увімкнено теги MTE |
| `ss` | тіньовий стек викликів |
| `sl` | ділянку запечатано, змінити її вже не можна |
| `gu` | у ділянці можуть бути сторожові проміжки |

Набір кодів росте разом із ядром: `mt`, `ss`, `sl`, `gu` на старших ядрах просто не з'являться. Читати цей рядок треба як множину, а не як позиційний формат.

## `/proc/<pid>/smaps_rollup` — підсумок замість тисяч блоків

Файл з'явився в ядрі 4.14. Ядро робить той самий обхід таблиць сторінок, але друкує один блок, і саме друк, а не обхід, коштував найдорожче.

Заголовний рядок склеєний зі старту першої ділянки й кінця останньої; права в ньому завжди `---p`, а зміщення, пристрій та inode — заглушкові нулі:

```
$ head -4 /proc/self/smaps_rollup
55d3f0e00000-7ffd8c3f2000 ---p 00000000 00:00 0    [rollup]
Rss:              12480 kB
Pss:               4131 kB
Pss_Dirty:         2856 kB
```

**Є тільки тут:** `Pss_Anon`, `Pss_File`, `Pss_Shmem` (з ядра 5.3) — розклад `Pss` за походженням сторінок. У поблочному `smaps` вони позбавлені сенсу: там ділянка завжди одного типу, тож два з трьох чисел були б нулями, а третє дорівнювало б `Pss`.

**Немає тут:** `Size`, `KernelPageSize`, `MMUPageSize`, `THPeligible`, `ProtectionKey`, `VmFlags` — усе, що описує окрему ділянку, а не суму. Тобто `VmSize` із `smaps_rollup` не дістати; для нього лишається `status`.

Ще одна відмінність важлива для того, хто збирає точну статистику: `smaps_rollup` обходить усі ділянки під замком карти пам'яті, тож у нормі його вивід описує один стан. Але якщо замок комусь потрібен на запис, ядро свідомо відпускає його посеред обходу й підхоплює наступну ділянку вже після тієї межі, на якій спинилося. Тож і цей файл на процесі, що активно робить `mmap`, дає лише *майже* злагоджений знімок.

## Точність: які числа наближені й наскільки

Документація ядра й довідкові сторінки позначають `VmRSS`, `VmHWM`, `RssAnon`, `RssFile`, `VmData`, `VmStk`, `VmExe` і `VmSwap` як неточні, і причина в усіх одна. Лічильники RSS оновлюються в гарячому шляху обробки [сторінкових збоїв](book:unix-linux/page-fault), тому їх зробили пакетними: зміни накопичуються локально й зливаються у спільний лічильник не щоразу. Похибка виходить порядку сотень кілобайтів на потік — шум для питання «скільки воно їсть» і катастрофа для тотожності «сума PSS дорівнює зайнятій пам'яті».

`smaps` і `smaps_rollup` такої похибки не мають: вони рахують проходом по таблицях сторінок, сторінка за сторінкою. Плата — час, лінійний за кількістю відображених сторінок, і замок карти пам'яті на весь час обходу.

| Потрібно | Брати з | Чому не інакше |
| --- | --- | --- |
| опитувати процеси щосекунди | `statm` або `status` | таблиць сторінок не чіпають |
| `Pss`, USS, `SwapPss` | `smaps_rollup` | більше їх ніде немає |
| знайти винну ділянку | `smaps` | лише він дає розклад по ділянках |
| точний RSS | `smaps_rollup`, поле `Rss` | без пакетної похибки |

## Стовпчики `ps`: куди веде кожен

`ps` із procps-ng бере ці числа з `status` і `stat`, а не зі `statm`.

| Стовпчик | Специфікатор | Джерело | Одиниця |
| --- | --- | --- | --- |
| `VSZ` | `vsz`, `vsize` | `status: VmSize` | KiB |
| `RSS` | `rss`, `rssize` | `status: VmRSS` | KiB |
| `RSZ` | `rsz` | `status: VmRSS` | KiB |
| `SZ` | `sz` | `VmSize / розмір_сторінки` | сторінки |
| `SIZE` | `size` | `status: VmData + VmStk` | KiB |
| `%MEM` | `pmem` | `VmRSS ÷ MemTotal` | відсотки |
| `TRS` | `trs` | `stat`: `end_code − start_code` | KiB |
| `DRS` | `drs` | `stat`: `vsize − (end_code − start_code)` | KiB |

Специфікатори `rss`, `rsz` і `rssize` дають те саме число й різняться лише заголовком стовпчика — спадок трьох історичних діалектів `ps`.

`SIZE` варто прочитати уважно: це не розмір процесу, а `VmData + VmStk` — оцінка, скільки місця знадобиться у свопі, якщо процес забруднить усі свої записувані сторінки. Обидва доданки віртуальні, тож `SIZE` спокійно перевищує весь наявний своп — і нічого поганого це не означає.

`TRS` і `DRS` — окрема пастка. Обчислюються вони з меж сегмента коду в `/proc/<pid>/stat`, а ці межі ядро віддає лише читачеві з правом трасувати процес; решті друкує на їхньому місці одиниці. Тому на чужому процесі `TRS` виходить нулем, а `DRS` — усім віртуальним розміром. Самі джерела procps-ng це визнають: над цими функціями стоїть коментар, що поля успадковані від ранніх BSD і, найпевніше, зламані.

## Поля `top`: куди веде кожне

`top` бере `VIRT`, `RES`, `SHR`, `CODE` і `DATA` зі `statm`, а решту — зі `status`.

| Поле | Джерело | Що це насправді |
| --- | --- | --- |
| `VIRT` | `statm`: `size` | `VmSize` у KiB |
| `RES` | `statm`: `resident` | `VmRSS` у KiB |
| `SHR` | `statm`: `shared` | `RssFile + RssShmem`, а не «спільне з кимось» |
| `%MEM` | `statm`: `resident` ÷ `MemTotal` | частка фізичної пам'яті |
| `SWAP` | `status: VmSwap` | лише анонімний приватний своп |
| `USED` | `VmRSS + VmSwap` | оцінка потреби процесу в пам'яті |
| `CODE` | `statm`: `text` | розмах адрес коду в KiB |
| `DATA` | `statm`: `data` | `VmData + VmStk` у KiB — те саме число, що `ps -o size` |
| `RSan` | `status: RssAnon` | анонімна частина RES |
| `RSfd` | `status: RssFile` | файлова частина RES |
| `RSsh` | `status: RssShmem` | shmem-частина RES |
| `RSlk` | `status: VmLck` | замкнена частина RES |

Найчастіше плутають саме `SHR`. Людина читає «shared» і робить висновок про спільну пам'ять із сусідніми процесами, а бачить кількість файлових сторінок — навіть якщо процес у системі один. Питання «скільки я справді ділю» вимагає `Shared_Clean + Shared_Dirty` зі `smaps_rollup`, і в жодному стовпчику `top` відповіді на нього немає.

Пара `CODE`/`DATA` показує ті самі величини, що `ps -o trs,drs`, але бере їх з іншого файлу — зі `statm`, а не зі `stat`. Наслідок несподіваний: на чужому процесі `top` покаже розмах коду чесно, а `ps -o trs` — нуль, бо в `stat` межі сегментів ховаються від читача без права трасувати, а в `statm` ті самі межі віддаються всім.

Так само варто помітити, чого в цій таблиці немає взагалі: `Pss`. Ані `ps`, ані `top` його не показують — сортувати процеси за справедливою часткою штатними інструментами не вийде.

## Мінімальний виклик

П'ять чисел, які найчастіше потрібні, дістаються так:

```sh
# VSZ і RSS у KiB, без запуску ps
awk '/^VmSize:/ {vsz=$2} /^VmRSS:/ {rss=$2} END {print vsz, rss}' /proc/$$/status

# PSS у KiB
awk '/^Pss:/ {print $2}' /proc/$$/smaps_rollup

# USS: те, що звільниться негайно після смерті процесу
awk '/^Private_(Clean|Dirty):/ {s+=$2} END {print s}' /proc/$$/smaps_rollup

# реальна потреба в пам'яті: заселене плюс витіснене
awk '/^VmRSS:/ {r=$2} /^VmSwap:/ {s=$2} END {print r+s}' /proc/$$/status

# найдорожчі ділянки за PSS, з іменами
awk '/^[0-9a-f]+-/ {name = (NF >= 6) ? $6 : "[анонімне]"}
     /^Pss:/       {p[name] += $2}
     END           {for (n in p) print p[n], n}' /proc/$$/smaps | sort -rn | head
```

Перевірка `NF >= 6` в останньому прикладі не косметична: у заголовку анонімної ділянки шостого поля просто немає, і без цієї перевірки всі анонімні ділянки — купа, стеки потоків, арени алокатора — злилися б у єдиний рядок із порожнім іменем.

## Помилки й межові випадки

| Ситуація | Що станеться |
| --- | --- |
| процес зник до `open` | `open` → `ENOENT` |
| процес зник посеред читання | `read` → `ESRCH` |
| немає права трасувати процес | `open("smaps")` → `EPERM`; `statm`/`status` читаються далі |
| ядро без `CONFIG_PROC_PAGE_MONITOR` | `smaps` і `smaps_rollup` не існують: `ENOENT` |
| потік замість процесу | `/proc/<pid>/task/<tid>/…` дає ті самі числа: карта в потоків спільна |
| процес без карти пам'яті (потік ядра, зомбі) | `statm` → `0 0 0 0 0 0 0`; у `status` рядків `Vm*` немає зовсім; `smaps_rollup` → `ESRCH` |
| `/proc` змонтовано з `hidepid=2` | чужий каталог не видно взагалі |

Ще один випадок не дає помилки, і тим небезпечніший: `smaps` того самого процесу, прочитаний двічі поспіль, дасть різні числа, якщо процес живий. Ядро тримає замок карти лише в межах кожного окремого читання, тож довгий `smaps` активного процесу — це послідовність знімків, а не один. Для сум, які мусять сходитися, беруть `smaps_rollup`; для порівняння «до й після» процес на час вимірювання зупиняють сигналом `SIGSTOP`.
