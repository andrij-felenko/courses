# Міграція сторінок: перенести вміст в інший кадр, не зламавши посилань

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

<details>
<summary>Що треба знати перед читанням</summary>

- **Віртуальна пам'ять (Virtual Memory)**: відображення віртуальних адрес на фізичні.
- **Таблиці сторінок (Page Tables)**: структури даних, що містять Page Table Entries (PTE), які вказують на фізичні кадри.
- **NUMA (Non-Uniform Memory Access)**: архітектура багатопроцесорних систем, де час доступу до пам'яті залежить від відстані між процесором та модулем пам'яті.
- **RMAP (Reverse Mapping)**: механізм ядра, що дозволяє знайти всі PTE, які посилаються на даний фізичний кадр.
</details>

Міграція сторінок (page migration) — це механізм ядра операційної системи, який дозволяє перемістити вміст фізичної сторінки (кадру) з одного місця в пам'яті в інше, при цьому прозоро для працюючого процесу. Це надзвичайно нетривіальна задача: як витягнути фізичний кадр з-під ніг процесу, який постійно з ним працює, скопіювати дані в інший кадр і оновити всі посилання, не викликавши краху системи або пошкодження даних?

Ця можливість є критичною для кількох важливих підсистем ядра:
1. **NUMA-балансування**: переміщення сторінок ближче до вузла (node), де виконується потік, який з ними працює, для зменшення затримок (latency).
2. **Дефрагментація пам'яті (Memory Compaction)**: збирання розкиданих вільних сторінок у великі безперервні блоки для виділення Huge Pages (величезних сторінок) або для потреб Contiguous Memory Allocator (CMA), який забезпечує великі блоки пам'яті для пристроїв.
3. **Гаряче вилучення пам'яті (Memory Hot-remove)**: міграція всіх даних з фізичного модуля пам'яті перед його фізичним вилученням з сервера.
4. **Управління живленням**: переміщення даних для можливості повного вимкнення певних банків пам'яті.

## Логіка процесу міграції

Щоб безпечно перенести сторінку, ядро Linux виконує складну хореографію, яка включає блокування, використання спеціальних маркерів та оновлення зворотного відображення (rmap). Процес міграції складається з наступних ключових етапів.

### 1. Ізоляція сторінки та виділення нового кадру

Спочатку ядро знаходить сторінку, яку потрібно перемістити (джерело), і виділяє новий фізичний кадр (ціль), куди будуть скопійовані дані. Сторінка-джерело блокується (встановлюється прапорець `PG_locked`), щоб запобігти змінам її стану іншими частинами ядра під час міграції. Також сторінка ізолюється зі списків LRU (Least Recently Used), щоб механізм вивантаження (page reclaim) не намагався її звільнити.

### 2. Атомарне зняття PTE (Unmap) та Migration Entry

Найнебезпечніший момент — це коли процес намагається звернутися до сторінки, яка саме переміщується. Щоб запобігти цьому, ядро знаходить усі таблиці сторінок усіх процесів, які відображають цей кадр. Для цього використовується механізм зворотного відображення (**rmap**).

Ядро атомарно видаляє дійсні Page Table Entries (PTE), які вказують на стару сторінку. Замість того, щоб просто очистити PTE (що призвело б до помилки page fault типу "сторінка не існує"), ядро записує туди спеціальний маркер — **migration entry**. 

Migration entry виглядає як запис про вивантажену сторінку (swap entry), але має спеціальний тип. Якщо будь-який потік спробує звернутися до пам'яті за цією віртуальною адресою, процесор згенерує page fault. Обробник page fault у ядрі побачить, що це migration entry, і зрозуміє: "Ага, ця сторінка зараз мігрує". Потік буде заблоковано і він чекатиме, доки міграція не завершиться.

### 3. Копіювання вмісту кадру

Після того, як усі доступи з боку процесорів перехоплені через migration entries, ядро копіює вміст старої сторінки в нову. Окрім самих даних, копіюються також метадані сторінки (наприклад, прапорці стану, інформація про доступ (`PG_referenced`), стан модифікації (`PG_dirty`)).

### 4. Оновлення Rmap та відновлення PTE (Remap)

Після успішного копіювання ядро знову використовує rmap, щоб обійти всі місця, де були встановлені migration entries. Кожен migration entry замінюється на новий, дійсний PTE, який тепер вказує на *новий* фізичний кадр. 

Тепер сторінка розблоковується. Усі потоки, які чекали на завершення міграції в обробнику page fault, прокидаються, прозоро повторюють інструкцію доступу до пам'яті і продовжують роботу вже з новим фізичним кадром. Процес навіть не здогадується, що його пам'ять фізично переїхала в інше місце.

### 5. Звільнення старого кадру

Старий фізичний кадр тепер повністю вільний від посилань. Його можна повернути в загальний пул вільних сторінок (buddy allocator) або вимкнути, якщо це було гаряче вилучення пам'яті.

## Проблема заблокованих (Pinned) сторінок

Описаний вище механізм ідеально працює для звичайного доступу з боку процесора. Але що робити, якщо сторінка використовується пристроями введення/виведення (Direct I/O, DMA)? 

Коли пристрій (наприклад, мережева карта або дисковий контролер) читає або пише безпосередньо в пам'ять (DMA), він обходить процесор і таблиці сторінок. Якщо ядро спробує перемістити сторінку під час DMA-транзакції, пристрій запише дані в старий кадр, який може вже належати іншому процесу, що призведе до катастрофічного пошкодження даних.

Тому перед виконанням DMA сторінки "пришпилюються" (pinned). У Linux це робиться за допомогою механізму **GUP (Get User Pages)**. GUP збільшує лічильник посилань на сторінку (`page->_refcount`). 

Під час міграції, після заміни PTE на migration entries, ядро перевіряє лічильник посилань. Якщо лічильник більший, ніж очікувана кількість посилань з таблиць сторінок (і кешу сторінок), це означає, що сторінка "pinned" кимось іншим (наприклад, для DMA). 

У такому випадку міграція цієї конкретної сторінки **скасовується** (fails). Ядро повертає старі PTE на місце і залишає сторінку в спокої. Мігрувати pinned сторінки неможливо, доки драйвер не завершить I/O і не відпустить їх. Саме тому довготривалі pinned сторінки є головним ворогом дефрагментації пам'яті та CMA.

## Системні виклики міграції

Користувацькі програми можуть керувати міграцією сторінок або запитувати їхнє переміщення (зазвичай для оптимізації NUMA) за допомогою спеціальних системних викликів.

Основні з них:
- `mbind()`: встановлює політику пам'яті для діапазону адрес (наприклад, вимагає виділення пам'яті лише на певному NUMA-вузлі). Може запускати міграцію існуючих сторінок, якщо вони не відповідають новій політиці.
- `move_pages()`: дозволяє перемістити масив конкретних сторінок процесу на вказані NUMA-вузли.
- `migrate_pages()`: переміщує всі сторінки процесу з одного набору NUMA-вузлів на інший набір.

Ці виклики є частиною API для High-Performance Computing (HPC) додатків, які ретельно оптимізують розташування даних у пам'яті для досягнення максимальної пропускної здатності та мінімальних затримок. Точні сигнатури двох головних із них, призначення кожного аргумента й різниця між «насипним» і поштучним переміщенням зібрані окремо: [move_pages та migrate_pages](book:unix-linux/page-migration/api-move-pages.md).
