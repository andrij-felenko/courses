# 🔬 Дослід над власною купою: програма, що сама себе міряє

Це одна програма на C, яка влаштовує собі п'ять дослідів поспіль і після кожного заглядає у власні лічильники — брейк, `VmRSS`, `VmSize`, рядки `/proc/self/maps`. На живому процесі стає видно те, що інакше лишається словами: брейк рухається стрибками, не пов'язаними з розміром запиту; великий блок відлітає за десятки терабайтів від купи; поріг сам піднімається після першого ж звільнення; півгігабайта не повертається системі, доки живий один-єдиний блок; `calloc` буває в тисячі разів швидший за `malloc` із `memset`.

Числа у виводі нижче — очікувані для glibc 2.39 на x86-64 з вимкненою рандомізацією адрес. Головні тут не самі числа, а арифметика, з якої кожне з них виходить: маючи її, ви впізнаєте своє число навіть тоді, коли воно інше.

Усі шматки коду йдуть підряд в один файл `heapprobe.c`; збірка й запуск — наприкінці.

## Правило приладу: не чіпати те, що міряєш

Вимірювати купу зсередини процесу — це як зважувати терези, стоячи на них. Перш ніж писати досліди, треба прибрати з приладів усе, що саме виділяє пам'ять, інакше прилад покаже власний слід.

Пасток рівно три, і всі три коштували б нам першого й найцікавішого числа.

**`printf` виділяє буфер.** Перший запис у `stdout` змушує stdio попросити в `malloc` буфер (зазвичай 4 КіБ) — і цей запит підніме брейк одразу на понад сто кілобайтів, ще до того, як почнеться дослід. Ліки прості: віддати stdio власний статичний буфер через `setvbuf` до першого виводу. Тоді stdio не звертається до купи взагалі.

**`fopen` теж виділяє буфер.** Читати `/proc/self/status` через `fopen`/`fgets` не можна з тієї самої причини. Читаємо голими `open`/`read`/`close` у статичний масив.

**Самі лічильники мають бути дешеві.** `sbrk(0)` — це навіть не системний виклик у сучасній glibc для читання: бібліотека тримає поточне значення межі в себе. А `/proc/self/status` — це [файл, якого немає на диску](book:unix-linux/proc-filesystem): ядро складає його текст у момент читання, тож кожен наш замір коштує одного `read` і розбору кількох сотень байтів.

```c
/* heapprobe.c — дослід над власною купою */
#define _GNU_SOURCE
#include <fcntl.h>
#include <malloc.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

#define KiB 1024UL
#define MiB (1024UL * KiB)

static char out_buf[8 * 1024];        /* власний буфер stdout: щоб stdio не кликав malloc */

static long proc_status_kib(const char *key)
{
    static char buf[4096];
    ssize_t n;
    char *p;
    int fd = open("/proc/self/status", O_RDONLY);

    if (fd < 0) return -1;
    n = read(fd, buf, sizeof buf - 1);
    close(fd);
    if (n <= 0) return -1;
    buf[n] = '\0';
    p = strstr(buf, key);
    return p ? strtol(p + strlen(key), NULL, 10) : -1;
}

static long rss_kib(void)   { return proc_status_kib("VmRSS:"); }
static long vsize_kib(void) { return proc_status_kib("VmSize:"); }

static void *brk_now(void) { return sbrk(0); }

/* надрукувати рядок /proc/self/maps, що містить задану адресу */
static void show_map_of(const void *addr)
{
    static char buf[128 * 1024];
    unsigned long want = (unsigned long) addr;
    size_t len = 0;
    ssize_t n;
    char *line;
    int fd = open("/proc/self/maps", O_RDONLY);

    if (fd < 0) return;
    while (len + 1 < sizeof buf && (n = read(fd, buf + len, sizeof buf - 1 - len)) > 0)
        len += (size_t) n;
    close(fd);
    buf[len] = '\0';

    for (line = buf; line && *line; ) {
        char *end = strchr(line, '\n');
        unsigned long lo = 0, hi = 0;

        if (end) *end = '\0';
        if (sscanf(line, "%lx-%lx", &lo, &hi) == 2 && want >= lo && want < hi)
            printf("        %s   (%lu КіБ)\n", line, (hi - lo) / KiB);
        line = end ? end + 1 : NULL;
    }
}

static void *xmalloc(size_t n)
{
    void *p = malloc(n);
    if (!p) { fprintf(stderr, "malloc(%zu) не вдався\n", n); exit(1); }
    return p;
}

/* сховати покажчик від оптимізатора (навіщо — у пастках наприкінці) */
static void *opaque(void *p)
{
    __asm__ volatile ("" : "+r"(p) : : "memory");
    return p;
}

static double now_s(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double) t.tv_sec + (double) t.tv_nsec / 1e9;
}
```

`CLOCK_MONOTONIC`, а не `CLOCK_REALTIME`, — бо нас цікавить тривалість, а настінний годинник має право стрибнути назад посеред заміру ([монотонний час проти настінного](book:programming/monotonic-vs-wall-time)).

## Дослід 1: драбинка брейка

Сім виділень підряд — одне крихітне й шість по 100 КіБ, усі під порогом `mmap`. Після кожного читаємо межу.

```c
static void probe_ladder(void)
{
    static const size_t sizes[7] = { 32, 102400, 102400, 102400, 102400, 102400, 102400 };
    void *keep[7];
    void *prev = brk_now();
    int i;

    printf("[1] драбинка брейка\n");
    printf("      старт: брейк = %p\n", prev);

    for (i = 0; i < 7; i++) {
        void *b;
        keep[i] = xmalloc(sizes[i]);
        memset(keep[i], 0, sizes[i]);
        b = brk_now();
        printf("      malloc(%6zu) = %p   брейк = %p  %+5ld КіБ\n",
               sizes[i], keep[i], b, ((char *) b - (char *) prev) / (long) KiB);
        prev = b;
    }
    for (i = 0; i < 7; i++)
        free(keep[i]);
    printf("      після free() усіх сімох: брейк = %p\n", brk_now());
}
```

```
[1] драбинка брейка
      старт: брейк = 0x555555559000
      malloc(    32) = 0x555555559010   брейк = 0x55555557a000   +132 КіБ
      malloc(102400) = 0x555555559040   брейк = 0x55555557a000     +0 КіБ
      malloc(102400) = 0x555555572050   брейк = 0x5555555ac000   +200 КіБ
      malloc(102400) = 0x55555558b060   брейк = 0x5555555ac000     +0 КіБ
      malloc(102400) = 0x5555555a4070   брейк = 0x5555555de000   +200 КіБ
      malloc(102400) = 0x5555555bd080   брейк = 0x5555555de000     +0 КіБ
      malloc(102400) = 0x5555555d6090   брейк = 0x555555610000   +200 КіБ
      після free() усіх сімох: брейк = 0x55555557a000
```

Жоден крок драбинки не дорівнює запитові — і в цьому вся суть. Алокатор рухає межу не тоді, коли його просять, а тоді, коли в нього скінчився запас, і рухає одразу з подушкою.

Розмір першого стрибка виводиться з трьох доданків. Запит на 32 байти перетворюється на блок 48 байтів (8 на заголовок, вирівнювання на 16). До нього glibc додає `M_TOP_PAD` — 128 КіБ подушки на майбутнє — і `MINSIZE`, найменший можливий блок, щоб залишок зверху був придатний до вжитку. Сума округлюється вгору до цілої сторінки:

```
запит                  = 32 байтів
блок                   = (32 + 8) вирівняне на 16     = 48
подушка M_TOP_PAD      = 131072
запас на верхній блок  = MINSIZE                      = 32
сума                   = 48 + 131072 + 32             = 131152
округлення до сторінки = 33 × 4096                    = 135168 = 132 КіБ
```

Далі верхній вільний блок має 135168 − 48 = 135120 байтів. Перший запит на 100 КіБ (блок 102416 байтів) у нього влазить — брейк не рухається. Другий уже ні: лишилося 32704, і алокатор просить у ядра різницю, знову з подушкою:

```
верхній блок           = 32704
потрібно на блок       = 102416
просимо в ядра         = 102416 + 131072 + 32 − 32704 = 200816
округлення до сторінки = 50 × 4096                    = 204800 = 200 КіБ
```

Звідси й ритм: кожне друге виділення підіймає межу на 200 КіБ, кожне непарне обходиться запасом. А остання адреса в кожній парі рівно на 102416 байтів вища за попередню — блоки лягають упритул один до одного, без жодної дірки.

Останній рядок пояснює, чому купа таки вміє зменшуватися. Коли звільнено все, вільний хвіст під брейком виріс до 732 КіБ і переріс `M_TRIM_THRESHOLD` (128 КіБ) — і `free` покликав `brk` униз, лишивши зверху ту саму подушку в 128 КіБ:

```
хвіст під брейком      = 732 КіБ = 749568
віддаємо               = (749568 − 131072 − 32 − 1) округлене вниз до сторінки
                       = 150 × 4096 = 614400 = 600 КіБ
брейк повертається на  = 749568 − 614400 = 135168 = 132 КіБ від старту
```

Це той самий випадок, коли все склалося вдало: живих блоків не лишилося жодного. Дослід 4 покаже, що буває, коли лишається один.

## Дослід 2: під порогом і над порогом

Два виділення — 64 КіБ і 1 МіБ — і рядки `/proc/self/maps`, у яких вони опинилися.

```c
static void probe_two_doors(void)
{
    void *small, *big, *b;

    printf("[2] під порогом і над порогом\n");
    small = xmalloc(64 * KiB);
    big   = xmalloc(1 * MiB);
    memset(small, 0, 64 * KiB);
    memset(big, 0, 1 * MiB);
    b = brk_now();

    printf("      64 КіБ → %p   (брейк = %p)\n", small, b);
    show_map_of(small);
    printf("      1 МіБ  → %p   вище за брейк на %ld ГіБ\n",
           big, ((char *) big - (char *) b) / (long) (1024 * MiB));
    show_map_of(big);

    free(small);
    free(big);
}
```

```
[2] під порогом і над порогом
      64 КіБ → 0x555555559010   (брейк = 0x55555558a000)
        555555559000-55555558a000 rw-p 00000000 00:00 0     [heap]   (196 КіБ)
      1 МіБ  → 0x7ffff7cad010   вище за брейк на 43690 ГіБ
        7ffff7cad000-7ffff7dae000 rw-p 00000000 00:00 0              (1028 КіБ)
```

Дві адреси різняться не розміром і не правами, а місцем у карті процесу. Купа росте одразу за даними програми, тому її адреси починаються з тих самих старших розрядів, що й сам виконуваний файл. Анонімні відображення ядро кладе в зовсім іншу частину простору — під бібліотеками, за десятки терабайтів звідти. Проміжок між ними — не витрачена пам'ять, а порожні числа: адрес у 64-бітовому просторі стільки, що розкидати ділянки на терабайти дешевше, ніж стерегти їх упритул.

Розмір ділянки в 1028 КіБ теж не випадковий. Блокові з `mmap` потрібен заголовок, і, на відміну від блоків у купі, за ним не йде сусід, чиє поле можна позичити, — тож накладних витрат тут на 8 байтів більше. Сума округлюється вгору до сторінки:

```
запит                  = 1048576
блок                   = (1048576 + 8) вирівняне на 16   = 1048592
заголовок без сусіда   = + 8                             = 1048600
округлення до сторінки = 257 × 4096                      = 1052672 = 1028 КіБ
```

Брейк при цьому не зрушив: до купи великий блок стосунку не має.

Обидва рядки взято з `/proc/self/maps`, і дивитися на них варто разом із сусіднім `smaps`: саме він скаже, скільки з цих 196 і 1028 КіБ справді лежить у пам'яті, а не лише записано за процесом ([VSZ, RSS і PSS](book:unix-linux/memory-accounting)).

## Дослід 3: поріг, який навчається

Чотири ітерації по 200 КіБ із негайним звільненням — той самий візерунок, на якому сталий поріг ламався б.

```c
static void probe_moving_threshold(void)
{
    int i;

    printf("[3] поріг, який навчається\n");
    for (i = 0; i < 4; i++) {
        void *b0 = brk_now();
        void *p = xmalloc(200 * KiB);
        void *b1;

        memset(p, 0, 200 * KiB);
        b1 = brk_now();
        printf("      ітерація %d: %p   брейк %+5ld КіБ   %s\n",
               i, p, ((char *) b1 - (char *) b0) / (long) KiB,
               (char *) p < (char *) b1 ? "з купи" : "окремий mmap");
        free(p);
    }
}
```

```
[3] поріг, який навчається
      ітерація 0: 0x7ffff7f7a010   брейк    +0 КіБ   окремий mmap
      ітерація 1: 0x555555559010   брейк +332 КіБ   з купи
      ітерація 2: 0x555555559010   брейк    +0 КіБ   з купи
      ітерація 3: 0x555555559010   брейк    +0 КіБ   з купи
```

Нульова ітерація йде через `mmap`: 204816 байтів — це більше за початковий поріг у 128 КіБ. А от `free` того самого блоку робить дещо непомітне: бачачи, що звільняють ділянку, видану через `mmap`, і що її розмір не перевищує стелі в 32 МіБ, glibc піднімає поріг до розміру цього блоку — і заразом ставить поріг обрізання вдвічі більшим.

```
поріг mmap  спочатку   = 131072            (128 КіБ)
ділянка блоку          = 51 × 4096 = 208896  (204 КіБ)
free() ділянки         → поріг mmap  = 208896
                       → поріг trim  = 2 × 208896 = 417792
наступний запит 204816 < 208896       → з купи
```

Наступні три ітерації беруть блок із купи — і всі три віддають **ту саму адресу**. Це найкоротший доказ того, навіщо взагалі потрібен цей механізм: там, де раніше на кожну ітерацію припадали `mmap`, п'ятдесят сторінкових збоїв, обнулення сторінок ядром і `munmap` зі скиданням кешу перекладів, тепер не відбувається жодного системного виклику взагалі.

Стрибок брейка в ітерації 1 рахується вже знайомою формулою: 204816 + 131072 + 32 = 335920, округлене вгору до 83 сторінок, тобто 339968 байтів = 332 КіБ. А вниз межа далі не йде, бо вільний хвіст (332 КіБ) не дотягує до нового порогу обрізання (408 КіБ), — механізм, піднявши один поріг, заразом зробив купу «липкішою».

> 🔧 **Навіщо це.** Дослід 3 — це діагностичний шаблон, який варто вміти повторити на своєму коді. Якщо в `strace` видно рівні пари `mmap`/`munmap` того самого розміру, що йдуть чергою ([трасування системних викликів](book:unix-linux/syscall-tracing)), — механізм підняття порогу вимкнено. А вимикається він лише в один спосіб: хтось явно задав бодай один із [чотирьох параметрів межі](book:unix-linux/allocator-and-kernel/api-mallopt-tunables.md) — через `mallopt`, змінну середовища чи тюнабл. Спершу перевіряйте оточення процесу, а не свій код.

## Дослід 4: півмільйона блоків і один живий

Головний дослід. Виділяємо 512000 блоків по 1 КіБ, торкаємося кожного, звільняємо всі, крім останнього — того, що лежить найвище, під самим брейком.

```c
#define BLOCKS 512000

static void snapshot(const char *tag)
{
    printf("      VmRSS = %8ld КіБ   VmSize = %8ld КіБ   брейк = %p   %s\n",
           rss_kib(), vsize_kib(), brk_now(), tag);
}

static void probe_trapped(void)
{
    void **v;
    size_t i;

    printf("[4] півмільйона блоків, звільнено всі, крім верхнього\n");
    snapshot("старт");

    v = xmalloc(BLOCKS * sizeof *v);
    for (i = 0; i < BLOCKS; i++) {
        v[i] = xmalloc(1 * KiB);
        memset(v[i], 0x5a, 1 * KiB);      /* доторкнутися: без цього сторінок не буде */
    }
    snapshot("512000 блоків по 1 КіБ виділено й заповнено");

    for (i = 0; i + 1 < BLOCKS; i++)
        free(v[i]);
    snapshot("free() усіх, крім верхнього");

    malloc_trim(0);
    snapshot("після malloc_trim(0)");

    free(v[BLOCKS - 1]);
    snapshot("після free() верхнього");

    free(v);
}
```

```

      VmRSS =     1808 КіБ   VmSize =     3908 КіБ   брейк = 0x555555559000   старт
      VmRSS =   525812 КіБ   VmSize =   528040 КіБ   брейк = 0x555575149000   512000 блоків по 1 КіБ виділено й заповнено
      VmRSS =   525812 КіБ   VmSize =   528040 КіБ   брейк = 0x555575149000   free() усіх, крім верхнього
      VmRSS =     5812 КіБ   VmSize =   527916 КіБ   брейк = 0x55557512a000   після malloc_trim(0)
      VmRSS =     5808 КіБ   VmSize =     8044 КіБ   брейк = 0x55555557a000   після free() верхнього
```

*Два лічильники розходяться саме там, де починається непорозуміння: `malloc_trim` віддає ядру сторінки, а адреси лишає за процесом.*

Другий рядок сходиться з арифметики блоків:

```
запит                  = 1024
блок                   = (1024 + 8) вирівняне на 16   = 1040
блоків                 = 512000
зайнято в купі         = 512000 × 1040 = 532480000    = 520000 КіБ
масив покажчиків       = 512000 × 8 = 4096000, окремим mmap ≈ 4004 КіБ
разом до старту        = 1808 + 520000 + 4004         ≈ 525812 КіБ
```

Надбавка в шістнадцять байтів на кожен блок — це не марнотратство алокатора, а ціна того, щоб блок можна було звільнити наосліп, знаючи саму лише адресу: перед даними мусить лежати розмір.

**Третій рядок — це і є та сама скарга «у нас витік».** Звільнено 511999 блоків, півгігабайта в купі вільні — і жоден лічильник не зрушив. Причина видна в самому виводі: брейк не змінився. Опустити його можна лише доти, доки під ним усе вільне, а під ним лежить один живий блок — той, який ми навмисне залишили найвищим. Усе, що нижче, для ядра невіддільне від живого: межа одна, і вона мусить бути вище за живий блок.

**Четвертий рядок — найцікавіший.** `malloc_trim(0)` віддає 520 000 КіБ — майже 508 МіБ — фізичної пам'яті, і `VmRSS` падає в дев'яносто разів. А `VmSize` майже не змінюється. Бо `malloc_trim` не рухає межу там, де не може: вільні сторінки посеред купи він віддає ядру через `madvise(MADV_DONTNEED)` — адреси лишаються записаними за процесом, а фізичні кадри йдуть у вільний список системи. Наступний дотик до тих адрес дасть свіжу нульову сторінку через [сторінковий збій](book:unix-linux/page-fault). Ті 124 КіБ, на які `VmSize` таки зменшився, — це вже робота `brk`: хвіст над живим блоком `malloc_trim` зрізає по-старому.

Так `malloc_trim` поводиться від glibc 2.8; до того він умів обрізати тільки хвіст головної арени й на цьому досліді не дав би нічого.

**П'ятий рядок** знімає останню перешкоду. Живий блок звільнено, вільний хвіст під брейком став завбільшки з усю купу й перевищив поріг обрізання — і `free` сам покликав `brk` униз. `VmSize` повертається до стартового плюс масив покажчиків плюс та сама подушка в 132 КіБ, яку алокатор лишає над брейком.

Мораль досліду в одному реченні: `VmRSS` каже, скільки сторінок ядро зараз тримає за процесом, `VmSize` — скільки адрес за ним записано, і жоден із двох не відповідає на питання «скільки пам'яті програма справді використовує». Саме тому [облік cgroup](book:unix-linux/cgroups) і OOM-killer, які дивляться на перше число, вбивають процеси, у яких немає жодного забутого об'єкта.

## Дослід 5: calloc проти malloc із memset

Два способи дістати гігабайт нулів. Різниця — у тисячі разів.

```c
static void probe_calloc(void)
{
    const size_t SZ = 1024 * MiB;
    volatile unsigned long sink = 0;
    unsigned char *a, *b;
    long r0, r1, r2, r3;
    double t0, t1, t2, t3, t4, t5;
    size_t i;

    printf("[5] calloc проти malloc+memset на 1 ГіБ\n");
    r0 = rss_kib();

    t0 = now_s();
    a = calloc(1, SZ);
    t1 = now_s();
    r1 = rss_kib();
    if (!a) { printf("      calloc не вдався\n"); return; }
    printf("      calloc(1, 1 ГіБ)          %9.3f мс   VmRSS %+8ld КіБ\n",
           (t1 - t0) * 1e3, r1 - r0);

    t2 = now_s();
    for (i = 0; i < SZ; i += 4096)
        sink += a[i];
    t3 = now_s();
    r2 = rss_kib();
    printf("      прочитати всі сторінки    %9.3f мс   VmRSS %+8ld КіБ   (сума = %lu)\n",
           (t3 - t2) * 1e3, r2 - r1, sink);

    t4 = now_s();
    b = opaque(malloc(SZ));
    if (!b) { printf("      malloc не вдався\n"); free(a); return; }
    memset(b, 0, SZ);
    t5 = now_s();
    r3 = rss_kib();
    printf("      malloc + memset(1 ГіБ)    %9.3f мс   VmRSS %+8ld КіБ\n",
           (t5 - t4) * 1e3, r3 - r2);

    free(a);
    free(b);
}
```

```
[5] calloc проти malloc+memset на 1 ГіБ
      calloc(1, 1 ГіБ)              0.012 мс   VmRSS       +0 КіБ
      прочитати всі сторінки      148.633 мс   VmRSS       +0 КіБ   (сума = 0)
      malloc + memset(1 ГіБ)      312.408 мс   VmRSS +1048576 КіБ
```

Перший рядок: `calloc` на гігабайт коштує дванадцять мікросекунд і не додає жодного кілобайта до `VmRSS`. Обидва числа з одного джерела. Блок такого розміру завжди йде окремим `mmap`, а ділянка з `mmap` приходить порожньою: сторінок під нею ще немає, а коли вони прийдуть — ядро зобов'язане віддати їх обнуленими, бо інакше в них потрапив би вміст чужого процесу. Отже, обіцянку «пам'ять буде нульова» вже дало ядро, і `calloc` про це знає: у glibc є явна перевірка, чи блок прийшов із `mmap`, і якщо так, `memset` просто не викликається. Уся робота `calloc` тут — один системний виклик.

Другий рядок — те, у що мало хто вірить із першого разу: **прочитати весь гігабайт можна, не займаючи жодної сторінки.** Кожен із 262144 дотиків спричиняє збій, але збій на **читання** анонімної ділянки ядро задовольняє спільною нульовою сторінкою — однією на всю систему, доступною лише для читання. Ця сторінка навмисне не рахується в `VmRSS`, тож лічильник стоїть. Записати в неї не можна: перший запис спричинить ще один збій, і аж тоді процес отримає власну сторінку.

Третій рядок показує, скільки коштує ця чесність. `memset` пише в кожну сторінку, тож кожна з 262144 сторінок мусить бути справжньою: ядро бере вільний кадр, обнуляє його, вставляє в таблицю сторінок, а потім `memset` пише туди нулі ще раз. Гігабайт запису ядром, гігабайт запису програмою, чверть мільйона переходів у режим ядра — і рівно гігабайт у `VmRSS`.

```
сторінок у 1 ГіБ       = 1073741824 / 4096   = 262144
calloc                 = 1 системний виклик, 0 збоїв, 0 записаних байтів
читання всіх сторінок  = 262144 збоїв, 0 кадрів  (спільна нульова сторінка)
malloc + memset        = 262144 збоїв, 262144 кадрів, ≈ 2 ГіБ запису
```

Тому `calloc(n, size)` — не «зручна обгортка над `malloc` і `memset`», а окремий інструмент, який знає те, чого не знає код зовні: звідки прийшла пам'ять.

## Складання й запуск

```c
int main(int argc, char **argv)
{
    int only = (argc > 1) ? atoi(argv[1]) : 0;

    setvbuf(stdout, out_buf, _IOFBF, sizeof out_buf);

    if (!only || only == 1) probe_ladder();
    if (!only || only == 2) probe_two_doors();
    if (!only || only == 3) probe_moving_threshold();
    if (!only || only == 4) probe_trapped();
    if (!only || only == 5) probe_calloc();
    return 0;
}
```

```
$ gcc -O2 -Wall -o heapprobe heapprobe.c
$ setarch -R ./heapprobe 1          # один дослід, без рандомізації адрес
$ setarch -R ./heapprobe            # усі п'ять підряд
$ strace -e trace=brk,mmap,munmap,madvise ./heapprobe 3
$ GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072 ./heapprobe 3
```

Ключ `-R` (він же `--addr-no-randomize`) у `setarch` знімає рандомізацію адресного простору для одного запуску — без нього адреси в кожному запуску інші. Останній рядок — контрольний дослід: явно задавши поріг, ми вимикаємо його динамічне підняття, і дослід 3 покаже чотири `mmap` замість одного.

**Запускайте досліди по одному.** Кожен лишає по собі стан: дослід 1 роздуває купу, дослід 3 назавжди піднімає поріг `mmap`. Числа з повного прогону сходяться з тією ж арифметикою, але початкові умови в них уже не порожні, і пояснювати їх утричі довше.

## Пастки

**Рандомізація адрес.** [ASLR](book:unix-linux/address-space-randomization) зсуває і базу програми, і початок купи (у Linux — на випадкову величину до 32 МіБ вище за кінець даних), і область відображень. Адреси в кожному запуску інші, а от **різниці** між ними — сталі, тож усі стрибки брейка й розміри ділянок відтворюються точно. Порівнювати абсолютні адреси має сенс лише під `setarch -R`.

**Кеш потоку (tcache).** З glibc 2.26 кожен потік має власний кеш звільнених блоків — до семи штук на кожен розмір, без жодних замків. Ці сім блоків вважаються зайнятими: сусіди з ними не зливаються, і `malloc_trim` їх не бачить. У досліді 4 це сім дірок на півмільйона блоків — непомітно. А от у мікродосліді на десяток блоків tcache змінює все: звільнений блок повертається тією ж адресою й не потрапляє ні в яку статистику. Про самі списки й біни — [внутрішня будова алокатора](book:programming/memory-allocator-internals).

**Версія glibc.** Числа тут — не константи мови C, а рішення конкретної реалізації, і вони мінялися: `malloc_trim` навчився віддавати сторінки посеред купи в 2.8, tcache з'явився в 2.26, тюнабли `glibc.malloc.*` — у 2.25, а в 2.43 з алокатора прибрано шар fastbin і типовий розмір кеша потоку зріс із семи блоків до шістнадцяти. Перше, що варто надрукувати поруч із результатами, — `gnu_get_libc_version()`.

**Компілятор може підмінити дослід.** Сучасні компілятори вміють склеювати `malloc` із наступним `memset(…, 0, …)` в один `calloc` — і тоді дослід 5 порівнював би `calloc` із `calloc`. Саме тому покажчик проходить через `opaque()`: порожня асемблерна вставка з `"memory"` у списку зіпсованого змушує компілятор вважати, що покажчик кудись подівся, і склеювання не відбувається. Той самий прийом рятує будь-який [мікробенчмарк](book:programming/microbenchmarking) від оптимізатора, який викидає роботу, чий результат нікому не потрібен.

**Прозорі великі сторінки.** Якщо в системі `/sys/kernel/mm/transparent_hugepage/enabled` стоїть у `always`, ядро підкладає під великі анонімні ділянки сторінки по 2 МіБ ([великі сторінки](book:unix-linux/huge-pages)). Тоді збоїв у досліді 5 буде не 262144, а 512, час зміниться в рази, а `VmRSS` стрибатиме поділками по 2 МіБ. Це не помилка вимірювання, але про режим треба знати, перш ніж пояснювати числа.

**Overcommit.** `calloc` на гігабайт удається на машині, де вільно значно менше, бо ядро роздає обіцянки, а не сторінки. Якщо ж `/proc/sys/vm/overcommit_memory` виставлено в 2, обіцянки рахують суворо і виклик може повернути `NULL` — тому перевірка на `NULL` у коді не формальність ([overcommit і OOM-killer](book:unix-linux/overcommit-and-oom)).

**Інший алокатор.** Запустіть програму з `LD_PRELOAD=/usr/lib/libjemalloc.so` — і досліди 1, 3 і 4 покажуть щось зовсім інше: ці алокатори `brk` не використовують узагалі, тож брейк не зрушить ані разу, а пам'ять повертатиметься системі там, де glibc її замикає. Дослід міряє не «Linux», а конкретну бібліотеку C.

**Контейнер.** Усередині cgroup `VmRSS` процесу й `memory.current` контрольної групи — різні числа: друге враховує ще й кеш сторінок і пам'ять ядра, витрачену на цей процес. Діагностувати «витік» у контейнері за одним лише `VmRSS` — певний шлях до хибного висновку.
