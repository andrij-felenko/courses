# userfaultfd: сторінкові збої в руках програми

<preknowlist>
- [Сторінковий збій](book:unix-linux/page-fault) — коли чинного запису в таблиці сторінок немає, апаратура спиняє інструкцію на півдорозі й віддає керування ядру.
- [Віртуальний адресний простір процесу](book:unix-linux/virtual-address-space) — простір складається з ділянок (VMA), у кожної свій діапазон адрес і походження вмісту.
- [Файловий дескриптор](book:unix-linux/file-descriptor) — маленьке число, за яким ядро знаходить об'єкт; його можна читати й чекати на ньому подій.
</preknowlist>

Коли програма звертається до віртуальної адреси, якої ще немає у фізичній пам'яті, апаратура генерує сторінковий збій. Зазвичай ядро самостійно вирішує цю проблему: виділяє нову нульову сторінку або читає дані з диска. Але існують задачі, де джерело даних відоме лише самій програмі, а не ядру. 

Типовий приклад — жива міграція віртуальної машини методом «після копіювання» ([post-copy](book:programming/live-migration)). Віртуальну машину запускають на новому сервері з порожньою пам'яттю, а її сторінки підкачують через мережу зі старого сервера саме тоді, коли гість намагається до них звернутися. Ядро не знає мережевого протоколу міграції, а програма-переносник не має доступу до таблиць сторінок. 

## Збій як повідомлення

Механізм `userfaultfd` зшиває ці дві половини. Він дозволяє програмі перехоплювати сторінкові збої у визначених діапазонах пам'яті й обробляти їх у звичайному потоці.

Спроба зробити це через сигнал `SIGSEGV` та `mprotect` розбивається об низку проблем: обробник сигналу виконується в перерваному потоці (що обмежує доступні функції), заповнення сторінки не є неподільним (інші потоки можуть побачити нулі між зміною прав і записом даних), а обслужити чужий процес так узагалі неможливо.

`userfaultfd` розв'язує це, перетворюючи збій на подію у [файловому дескрипторі](book:unix-linux/everything-is-a-file):

1. **Створення та реєстрація**: Програма створює об'єкт викликом `userfaultfd()` і реєструє діапазон адрес (`UFFDIO_REGISTER`).
2. **Перехоплення**: Коли будь-який потік (винуватець) звертається до відсутньої сторінки в цьому діапазоні, ядро не підставляє сторінку самостійно. Воно призупиняє винуватця і кладе повідомлення про збій у чергу дескриптора.
3. **Обслуговування**: Інший потік (наглядач) чекає подій на дескрипторі через `poll()`, читає повідомлення, дізнається адресу і приносить необхідні байти (наприклад, з мережі).
4. **Заповнення**: Наглядач викликає `UFFDIO_COPY`, передаючи ядру буфер з даними. Ядро **неподільно** копіює дані у вільний кадр, оновлює таблицю сторінок і будить винуватця. Інструкція продовжує виконання, ніби нічого не сталося.

```c
/* 1. Реєстрація ділянки */
struct uffdio_register reg = {
    .range = { .start = (unsigned long)area, .len = length },
    .mode  = UFFDIO_REGISTER_MODE_MISSING,
};
ioctl(uffd, UFFDIO_REGISTER, &reg);

/* 2. Обслуговування збою */
struct uffd_msg msg;
read(uffd, &msg, sizeof msg); 
unsigned long page = msg.arg.pagefault.address & ~(pagesize - 1);
fetch_page(page, buf); /* Отримання даних програмою */

/* 3. Неподільне заповнення */
struct uffdio_copy copy = {
    .dst = page, .src = (unsigned long)buf, .len = pagesize, .mode = 0,
};
ioctl(uffd, UFFDIO_COPY, &copy);
```

## Три режими роботи

Механізм підтримує різні питання до сторінки:

1. **`MISSING` (Тут нічого нема)**: Сторінка відсутня. Використовується для лінивої міграції та породження пам'яті на вимогу. Працює лише для анонімної пам'яті та `tmpfs`/`memfd` (бо для файлів ядро саме знає, звідки брати дані).
2. **`WP` (Тут щойно написали)**: Режим Write Protect. Спроба запису генерує подію. Дозволяє наглядачу точно фіксувати зміни для створення поступових контрольних точок (знімків) без розгалуження процесу.
3. **`MINOR` (Сторінка є, відображення нема)**: Дані вже лежать у кеші сторінок (наприклад, прибули з мережі в інше відображення того ж об'єкта), бракує лише запису в таблиці. Дозволяє уникнути зайвого копіювання пам'яті під час обслуговування збою для [великих сторінок](book:unix-linux/huge-pages).

Дескриптор `userfaultfd` також можна передавати іншому процесу через сокет домену Unix. Тоді наглядач зчитує збої та події зміни адресного простору (`fork`, `mremap`, `munmap`) **чужого** процесу. Саме так інструмент [CRIU](book:unix-linux/userfaultfd/hist-userfaultfd.md) відновлює процеси з контрольних точок.

## Безпека та обмеження

Можливість зупиняти потік у довільний момент зробила `userfaultfd` потужною зброєю для експлуатації вразливостей ядра через перегони ([TOCTOU](book:programming/toctou-race)). Зловмисник міг передати ядру буфер, зареєстрований у `userfaultfd`, і змусити ядро "зависнути" посеред копіювання.

Тому сучасні ядра обмежують цей механізм: за замовчуванням непривілейовані користувачі можуть перехоплювати лише ті збої, що сталися **у просторі користувача** (прапорець `UFFD_USER_MODE_ONLY`). Для повноцінної роботи (наприклад, для віртуальних машин, чию пам'ять читає ядро) потрібен доступ до спеціального файлу пристрою `/dev/userfaultfd`.
