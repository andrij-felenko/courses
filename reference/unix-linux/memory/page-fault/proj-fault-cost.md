# ⚙️ Вимірюємо сторінкові збої власноруч

Одна програма на C, яка на вашій машині показує кожен різновид сторінкового збою нарізно й ціну кожного важеля проти нього — щоб чужі числа стали числами, які ви бачили самі й умієте пояснити.

Ціна збою — не стала величина. Вона залежить від того, чи сторінка анонімна, чи за нею стоїть файл, чи цей файл лежить у пам'яті, чи ядро вгадало ваш намір наперед. Прочитати про це можна. Але поки не побачиш на своєму залізі, що обхід одного й того самого файлу коштує то 14 мілісекунд, то п'ять секунд — і різниця в одному виклику `madvise`, — не віриться.

## Прилад: звідки беруться числа

Ядро рахує збої точно. Не вибірково, не за таймером — щоразу, коли обробник збою дороблює свою роботу, він додає одиницю до лічильника задачі: `min_flt` або `maj_flt`, залежно від того, чи довелося йти на носій. Ці два числа видно з двох боків: зсередини процесу через `getrusage`, ззовні — у [файлі `/proc/<pid>/stat`](book:unix-linux/proc-filesystem), де ядро віддає стан процесу як текстовий рядок із десятками полів (мінорні збої — десяте поле, мажорні — дванадцяте).

Обидва джерела дають ту саму пару, і брати варто обидва: `getrusage` дешевший і не потребує розбору тексту, а `/proc` — єдиний спосіб подивитися на ЧУЖИЙ процес, який нічого про вимір не знає.

```c
/* faultlab.c — вимірювання сторінкових збоїв.
   Збірка:  cc -O2 -std=gnu11 -o faultlab faultlab.c            */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/stat.h>

#ifndef MADV_POPULATE_WRITE           /* з'явилося в Linux 5.14 */
#define MADV_POPULATE_WRITE 23
#endif

#define PGSZ   4096UL
#define ANON   (1024UL * 1024 * 1024)      /* 1 ГіБ анонімної пам'яті */
#define FSIZE  (256UL  * 1024 * 1024)      /* 256 МіБ файлу           */

/* Куди зливати прочитане, щоб компілятор не викинув самі читання. */
volatile unsigned long sink;

struct mark { double t; unsigned long minf, majf; };

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec * 1e-9;
}

static void counters(unsigned long *minf, unsigned long *majf)
{
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);        /* RUSAGE_THREAD — якщо потоків кілька */
    *minf = ru.ru_minflt;
    *majf = ru.ru_majflt;
}

static void mark_begin(struct mark *m)  /* час беремо ОСТАННІМ  */
{
    counters(&m->minf, &m->majf);
    m->t = now();
}

static void mark_end(const struct mark *m, const char *what)
{
    double dt = now() - m->t;           /* час беремо ПЕРШИМ    */
    unsigned long minf, majf;
    counters(&minf, &majf);
    printf("  %-32s %9.3f мс   minflt +%-8lu majflt +%lu\n",
           what, dt * 1e3, minf - m->minf, majf - m->majf);
}
```

Порядок усередині `mark_begin` і `mark_end` не випадковий: `getrusage` — це справжній системний виклик, десь дві-три сотні наносекунд. Якщо взяти час першим на початку і останнім у кінці, ці сотні наносекунд опиняться всередині виміряного відтинку. На двохсотмілісекундному досліді байдуже, на однопрохідному — ні.

Другий бік лічильників — з `/proc`. Розбір там має одну підступність: ім'я програми стоїть у круглих дужках і само може містити пробіли й дужки, тож рахувати поля зліва напрямець не можна.

```c
/* Ті самі два числа, але видимі ззовні: поля 10 і 12 у /proc/self/stat.
   Починаємо від ОСТАННЬОЇ ')' — усе, що лівіше, це pid та ім'я. */
static void proc_faults(unsigned long *minf, unsigned long *majf)
{
    char buf[1024];
    int fd = open("/proc/self/stat", O_RDONLY);
    if (fd < 0) { *minf = *majf = 0; return; }
    ssize_t n = read(fd, buf, sizeof buf - 1);
    close(fd);
    buf[n > 0 ? n : 0] = '\0';

    char *p = strrchr(buf, ')');
    if (!p) { *minf = *majf = 0; return; }
    /*     state ppid pgrp session tty tpgid flags minflt cminflt majflt */
    sscanf(p + 2, "%*c %*d %*d %*d %*d %*d %*u %lu %*lu %lu", minf, majf);
}
```

Лишається третій прилад, без якого решта — самообман. Треба вміти спитати систему, чи сторінка справді лежить у пам'яті. Для цього є `mincore`: він заповнює масив байтів, по одному на сторінку діапазону, і молодший біт кожного каже «резидентна». Для файлового відображення це прямий погляд у [кеш сторінок](book:unix-linux/page-cache-durability) — той шар, де ядро тримає прочитані шматки файлів, щоб не ходити на носій двічі.

```c
/* Скільки сторінок діапазону справді в пам'яті. Саме цим перевіряють,
   що «холодний» кеш таки холодний, а не здається таким. */
static unsigned long resident(void *addr, size_t len)
{
    size_t n = len / PGSZ;
    unsigned char *vec = malloc(n);
    unsigned long r = 0;
    if (mincore(addr, len, vec) == 0)
        for (size_t i = 0; i < n; i++) r += vec[i] & 1u;
    free(vec);
    return r;
}
```

І сам обхід. Тут єдина, зате найпоширеніша пастка всього досліду: цикл, який читає байти й нічого з ними не робить, [оптимізатор](book:programming/compiler-optimizations) має повне право викинути цілком — читання з пам'яті без побічного ефекту не змінює нічого спостережуваного, а отже, за правилами мови його наче й не було. Накопичувач `acc`, злитий у `volatile`-змінну, робить результат спостережуваним, і читання лишаються.

```c
static void touch_seq(char *p, size_t len, int write)
{
    unsigned long acc = 0;
    for (size_t i = 0; i < len; i += PGSZ)
        if (write) p[i] = 1;
        else       acc += (unsigned char)p[i];
    sink += acc;                        /* без цього рядка циклу не буде */
}

/* Випадковий порядок готуємо ЗАЗДАЛЕГІДЬ: генератор випадкових чисел
   у виміряному циклі — це вимір генератора, а не пам'яті. */
static size_t *permutation(size_t n)
{
    size_t *idx = malloc(n * sizeof *idx);
    for (size_t i = 0; i < n; i++) idx[i] = i;
    for (size_t i = n - 1; i > 0; i--) {
        size_t j = (size_t)(random() % (long)(i + 1));
        size_t t = idx[i]; idx[i] = idx[j]; idx[j] = t;
    }
    return idx;
}

static void touch_perm(char *p, const size_t *idx, size_t n)
{
    unsigned long acc = 0;
    for (size_t k = 0; k < n; k++) acc += (unsigned char)p[idx[k] * PGSZ];
    sink += acc;
}
```

## Дослід А: анонімна пам'ять і три способи за неї заплатити

Перший дослід найпростіший: узяти гігабайт, торкнутися кожної сторінки, пройти вдруге. Потім те саме, але попросивши систему зробити всю роботу наперед.

```c
static void exp_anon(void)
{
    struct mark m;
    char *p;

    puts("A. анонімна пам'ять, 1 ГіБ = 262144 сторінок по 4 КіБ");

    mark_begin(&m);
    p = mmap(NULL, ANON, PROT_READ | PROT_WRITE,
             MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    mark_end(&m, "mmap (ліниво)");

    /* Прибиваємо великі сторінки: інакше збоїв буде 512, а не 262144,
       і дослід міряв би налаштування машини, а не сторінковий збій. */
    madvise(p, ANON, MADV_NOHUGEPAGE);

    mark_begin(&m); touch_seq(p, ANON, 1); mark_end(&m, "перший дотик");
    mark_begin(&m); touch_seq(p, ANON, 1); mark_end(&m, "другий прохід");
    munmap(p, ANON);

    mark_begin(&m);
    p = mmap(NULL, ANON, PROT_READ | PROT_WRITE,
             MAP_PRIVATE | MAP_ANONYMOUS | MAP_POPULATE, -1, 0);
    mark_end(&m, "mmap + MAP_POPULATE");
    mark_begin(&m); touch_seq(p, ANON, 1); mark_end(&m, "перший дотик по ній");
    munmap(p, ANON);

    p = mmap(NULL, ANON, PROT_READ | PROT_WRITE,
             MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    madvise(p, ANON, MADV_NOHUGEPAGE);
    mark_begin(&m);
    madvise(p, ANON, MADV_POPULATE_WRITE);
    mark_end(&m, "madvise(MADV_POPULATE_WRITE)");
    munmap(p, ANON);
}
```

Вивід на звичайній машині з NVMe і DDR4:

```

  mmap (ліниво)                       0.011 мс   minflt +0        majflt +0

  другий прохід                       0.617 мс   minflt +0        majflt +0
  mmap + MAP_POPULATE               191.004 мс   minflt +262144   majflt +0
  перший дотик по ній                 0.621 мс   minflt +0        majflt +0
  madvise(MADV_POPULATE_WRITE)      190.233 мс   minflt +262144   majflt +0
```

Розберімо кожне число, бо кожне щось стверджує.

**262144 збої й жодного зайвого** — це 1 ГіБ ÷ 4 КіБ рівно. Не «приблизно стільки», а точно один збій на сторінку: сторінки народжуються поштучно, у мить доторку, і ніхто не робить нічого наперед.

**749 наносекунд на збій** (196.412 мс ÷ 262144). Уся робота ядра — знайти область, узяти вільну сторінку, обнулити її, вписати запис у таблицю — вкладається в три чверті мікросекунди. Причому обнулення тут головне: 4096 байтів на швидкості пам'яті близько 5.5 ГіБ/с — це якраз сотні наносекунд. Ядро не має права віддати вам сторінку зі старим вмістом, тож обнулення оплатити доведеться завжди.

**Другий прохід — 0.617 мс і нуль збоїв.** Ті самі 262144 доторки, у триста разів швидше. Це і є повна ціна ліні: 196 мілісекунд, які лінива система розсипала по 262144 непередбачуваних моментах у майбутньому.

**MAP_POPULATE не зменшив кількості збоїв.** Ось найцікавіше число досліду. Було б природно чекати, що населення наперед — це якийсь оптовий шлях в обхід збоїв. Ні: лічильник показує ті самі 262144 дрібні збої, тільки тепер вони всі сталися **всередині виклику `mmap`**. Ядро населює область не якимось особливим кодом, а просто проходить діапазон і бере кожен збій свідомо, тим самим обробником. Змінилося не «скільки», а «коли» — і саме це варте грошей: 191 мілісекунда в одному відомому місці замість 196 мілісекунд, розкиданих де завгодно.

Побічний наслідок, який колись зіб'є вас із пантелику: `perf stat -e page-faults` цих збоїв **не** покаже. Perf рахує події, що прийшли від процесора зі збереженим станом регістрів, а населення йде зсередини ядра, без апаратного винятку; лічильник задачі при цьому росте, подія perf — ні. Два «однакові» лічильники розійдуться в півмільйона.

`MADV_POPULATE_WRITE` (Linux 5.14) робить те саме, але його можна прикласти до вже наявного відображення й він не ховає помилок — на відміну від `MAP_POPULATE`, який мовчки поверне успіх, якщо населити не вдалося.

*Важіль проти ліні майже ніколи не зменшує роботи. Він переносить її туди, де на неї ніхто не дивиться, і робить передбачуваною.*

## Дослід Б: файл, холодний і теплий

Тепер найголовніше — різниця між дрібним і великим збоєм. Для цього потрібен файл, [відображений у пам'ять](book:unix-linux/mmap-model), і вміння вигнати його з кеша.

Вигнати можна без прав адміністратора: `posix_fadvise` з порадою `POSIX_FADV_DONTNEED` викидає сторінки конкретного файлу. Але тільки **чисті** — брудні (щойно записані й ще не збережені) ядро не викине, бо тоді б воно втратило дані. Тому `fsync` перед цим не формальність, а умова.

```c
static int make_file(const char *path)
{
    int fd = open(path, O_RDWR | O_CREAT, 0644);
    struct stat st;
    fstat(fd, &st);
    if ((size_t)st.st_size < FSIZE) {
        char *chunk = malloc(1 << 20);
        memset(chunk, 0xA5, 1 << 20);
        for (size_t off = 0; off < FSIZE; off += (1 << 20))
            write(fd, chunk, 1 << 20);
        free(chunk);
    }
    fsync(fd);
    return fd;
}

/* Викинути сторінки файлу з кеша. Викидаються ЛИШЕ чисті — звідси fsync. */
static void chill(int fd)
{
    fsync(fd);
    posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED);   /* 0 = до кінця файлу */
}

static void exp_file(int fd, const char *label, int cold, int advice, int randomly)
{
    struct mark m;
    size_t n = FSIZE / PGSZ;
    if (cold) chill(fd);

    /* Відображення ЩОРАЗУ нове: інакше таблиця сторінок лишиться від
       минулого проходу й збоїв не буде взагалі, хоч кеш і холодний. */
    char *p = mmap(NULL, FSIZE, PROT_READ, MAP_PRIVATE, fd, 0);
    if (advice) madvise(p, FSIZE, advice);
    printf("  %-32s резидентних до обходу: %lu з %zu\n",
           label, resident(p, FSIZE), n);

    size_t *idx = randomly ? permutation(n) : NULL;
    mark_begin(&m);
    if (idx) touch_perm(p, idx, n);
    else     touch_seq(p, FSIZE, 0);
    mark_end(&m, "  обхід");
    free(idx);
    munmap(p, FSIZE);
}
```

Зверніть увагу на `mmap` усередині: кожен прохід отримує **свіже відображення**. Це не охайність, це необхідність. Теплим може бути і кеш сторінок, і таблиця сторінок процесу — це різні речі. Якщо пройти двічі по одному відображенню, другий прохід не дасть збоїв узагалі, і ви поміряєте ніщо. Свіже відображення обнуляє таблицю, лишаючи стан кеша таким, яким ви його зробили.

Четвертий дослід — окремою функцією, бо `MADV_WILLNEED` має власну пастку.

```c
static void exp_willneed(int fd)
{
    struct mark m;
    size_t n = FSIZE / PGSZ;
    chill(fd);
    char *p = mmap(NULL, FSIZE, PROT_READ, MAP_PRIVATE, fd, 0);

    mark_begin(&m);
    madvise(p, FSIZE, MADV_WILLNEED);
    mark_end(&m, "madvise(MADV_WILLNEED)");

    /* WILLNEED лише ЗАПУСКАЄ читання й одразу вертається. Якщо піти в обхід
       негайно, великі збої нікуди не подінуться — чекаємо резидентності. */
    double t0 = now();
    while (resident(p, FSIZE) < n && now() - t0 < 5.0)
        nanosleep(&(struct timespec){0, 1000000}, NULL);
    printf("  прогрівання: %.1f мс, резидентних %lu з %zu\n",
           (now() - t0) * 1e3, resident(p, FSIZE), n);

    mark_begin(&m); touch_seq(p, FSIZE, 0); mark_end(&m, "  обхід");
    munmap(p, FSIZE);
}
```

Порядок викликів у `main` теж значущий: теплий прохід іде **одразу після** холодного, бо саме холодний прохід і нагріває кеш.

```c
    int fd = make_file("faultlab.dat");
    puts("\nB. файл 256 МіБ = 65536 сторінок");
    exp_file(fd, "холодний кеш, послідовно",        1, 0,           0);
    exp_file(fd, "теплий кеш, послідовно",          0, 0,           0);
    exp_file(fd, "холодний, MADV_RANDOM, вроздріб", 1, MADV_RANDOM, 1);
    exp_willneed(fd);
    close(fd);
```

*Одні й ті самі 65536 сторінок одного й того самого файлу. Різниця в чотирьохсот разах за часом береться не з коду обходу, а з того, чи ядро вгадало намір наперед.*

Тут кожне число виводиться з двох налаштувань системи, які можна прочитати просто зараз.

**4096 дрібних збоїв на 65536 теплих сторінок** — це рівно 65536 ÷ 16. Шістнадцять сторінок за один збій: коли збій стався на читанні файлової сторінки, ядро одразу відображає всіх сусідів, які вже лежать у кеші, — дорога частина (вхід у ядро, пошук області) вже оплачена, вписати ще п'ятнадцять записів у таблицю майже безкоштовно. Механізм зветься fault-around, а розмір вікна відкритий у debugfs:

```
$ cat /sys/kernel/debug/fault_around_bytes
65536
```

65536 ÷ 4096 = 16. Поставте туди 4096 — і теплий прохід дасть рівно 65536 збоїв замість 4096.

**2048 великих збоїв на холодному проході** — це 65536 ÷ 32. Тридцять дві сторінки за одне звернення до носія, бо таке типове вікно [випереджального читання](book:unix-linux/readahead), тобто механізму, яким ядро вгадує послідовний обхід і тягне наступний шматок файлу до того, як по нього прийдуть:

```
$ cat /sys/block/nvme0n1/queue/read_ahead_kb
128
```

128 КіБ ÷ 4 КіБ = 32. Разом обидва механізми дають на холодному проході 4096 збоїв, з яких кожен другий — великий: вікно читання вдвічі ширше за вікно відображення.

**59214 великих збоїв на випадковому обході** — і ось вирок. `MADV_RANDOM` каже ядру: послідовності не буде, вгадувати нема чого. Перевірка стоїть просто в коді випереджального читання — побачивши на області прапорець «випадковий доступ», ядро виходить, не почавши читати наперед. Кожна сторінка тепер їде на носій окремим запитом, і 65536 запитів по вісімдесят із гаком мікросекунд дають ті п'ять секунд.

Чому не рівно 65536, а 59214? Бо fault-around — механізм інший, він живе не в читанні, а у відображенні, і `MADV_RANDOM` його не вимикає. Ближче до кінця обходу дедалі більше сусідів уже лежать у кеші від попередніх читань, і черговий збій чіпляє їх задарма. Звідси й 2170 дрібних збоїв, що набігли самі. Числа не круглі саме тому, що механізмів два й вони незалежні.

**`MADV_WILLNEED` повернувся за 0.312 мс.** Не тому, що він швидкий, а тому, що він **асинхронний**: порада лише ставить читання в чергу. Якби програма пішла в обхід одразу, великі збої були б на місці, просто трохи менші числом. Саме тому в коді стоїть цикл чекання на резидентність — і саме тому в житті `MADV_WILLNEED` корисний тільки тоді, коли між порадою і доступом є чим зайнятися. Прогрівання зайняло 218 мс — рівно стільки ж, скільки й холодний послідовний обхід, бо робота та сама, просто виконана заздалегідь.

> 🔧 **Навіщо це.** Коли служба «повільно стартує» й профіль показує розмазане очікування, ці два числа розрізняють діагнози. `majflt` у тисячах — дані йдуть із носія, і рятує прогрівання наперед або більший кеш. `majflt` близько нуля при великому `minflt` — дані вже в пам'яті, а програма платить за саме́ відображення; тут допоможе менше відображень, більші сторінки або населення наперед.

## Дослід В: mlockall і найгірший дотик

Досі ми міряли суму. Але програмі керування рухом байдужа сума — їй важить найгірший один випадок. Порахуймо не середнє, а розподіл: час кожного окремого дотику до сторінки.

Такий вимір можливий лише тому, що `clock_gettime` не заходить у ядро: він виконується з [vDSO](book:unix-linux/vdso) — шматка коду, який ядро відображає в кожен процес, — і коштує десятки наносекунд. Інакше прилад був би дорожчий за те, що він міряє.

```c
static int cmp_d(const void *a, const void *b)
{
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}

static void exp_latency(int lock)
{
    size_t n = 64UL * 1024 * 1024 / PGSZ;        /* 16384 сторінки */
    size_t len = n * PGSZ;
    double *lat = malloc(n * sizeof *lat);

    char *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    madvise(p, len, MADV_NOHUGEPAGE);
    if (lock) {
        mlockall(MCL_CURRENT | MCL_FUTURE);      /* див. ulimit -l */
        touch_seq(p, len, 1);                    /* усі збої — тут, на старті */
    }

    for (size_t i = 0; i < n; i++) {
        double t0 = now();
        p[i * PGSZ] = 1;
        lat[i] = (now() - t0) * 1e6;             /* мкс */
    }
    qsort(lat, n, sizeof *lat, cmp_d);
    printf("  %-24s медіана %6.2f   99.9%% %7.2f   максимум %8.2f мкс\n",
           lock ? "mlockall + прогрів" : "без mlock, перший дотик",
           lat[n / 2], lat[(size_t)(n * 0.999)], lat[n - 1]);
    free(lat);
    if (lock) munlockall();
    munmap(p, len);
}
```

```
C. найгірший час одного дотику, 64 МіБ анонімної
  без mlock, перший дотик   медіана   0.61   99.9%    2.43   максимум  1832.10 мкс
  mlockall + прогрів        медіана   0.02   99.9%    0.04   максимум    11.36 мкс
```

Медіана в лівому рядку — знайомі 0.61 мкс, звичайний дрібний збій. А максимум — 1832 мікросекунди, у три тисячі разів більше за медіану. Це не збій із походом на носій: свопу тут нема. Це мить, коли вільних сторінок не лишилося й ядро мусило [добути їх витісненням](book:unix-linux/swap-and-reclaim) просто в обробнику збою — знайти холодні сторінки, звільнити, а може, ще й ущільнити пам'ять. Ціна такої миті не обмежена нічим і не з'являється в жодному середньому.

`mlockall(MCL_CURRENT | MCL_FUTURE)` прибиває всі теперішні й майбутні сторінки до фізичної пам'яті; прохід записом одразу після нього забирає всі збої на старт. Медіана падає до 0.02 мкс — це вже просто запис у пам'ять, збою нема взагалі.

Але максимум лишився 11.36 мкс, і це важливо чесно назвати. Збоїв там нема — є переривання таймера й планувальник, що на мить забрав процесор. `mlock` знімає одну причину затримки, не всі; за решту відповідають [реальночасові класи планування](book:unix-linux/priority-nice-realtime), які визначають, коли задачу взагалі можна витіснити. Якщо `mlockall` повернув `ENOMEM`, дивіться `ulimit -l`: непривілейованому процесу дозволено прибити обмежений обсяг.

## Пастки, через які числа брешуть

Кожна з них дає правдоподібний вивід — і саме тому небезпечна. Загальне правило [чесного мікробенчмарку](book:programming/microbenchmarking) тут набуває конкретної форми: перевіряйте не час, а **кількість збоїв**, бо вона мусить збігатися з арифметикою.

**Компілятор з'їв читання.** Симптом упізнаваний з першого погляду:

```
  обхід                             0.004 мс   minflt +0        majflt +0
```

Нуль збоїв там, де їх мусили бути тисячі. Циклу просто нема в машинному коді. Ліки — накопичувач, злитий у `volatile`, як у `touch_seq`. Перевірка одна: очікуване число збоїв рахується наперед, і якщо вивід із ним не сходиться, вимір недійсний.

**Кеш лишився теплим.** `posix_fadvise` — це порада, а не наказ. Він не викине сторінку, яку не збережено на носій, і не викине ту, яку тримає інший процес. Тому в програмі й стоїть `resident()` перед кожним обходом: рядок «резидентних до обходу: 0 з 65536» — це не прикраса виводу, це доказ, що дослід узагалі відбувся. Побачивши там 65536 замість нуля, не пояснюйте час — виправляйте вимір.

Окремий випадок — файл на `tmpfs` (типово це `/tmp` і `/dev/shm`). У [цієї файлової системи](book:unix-linux/pseudo-filesystems) нема носія: її сторінки і є сховищем. Викидати їх нема куди, великих збоїв не буде ніколи, і холодний прохід нічим не відрізнятиметься від теплого. Кладіть тестовий файл на звичайну файлову систему.

**Прозорі великі сторінки тихо змінили масштаб.** Прибрати `MADV_NOHUGEPAGE` — і той самий дослід А на машині з увімкненими [великими сторінками](book:unix-linux/huge-pages) дає:

```
$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never
  перший дотик                    178.902 мс   minflt +512      majflt +0
```

512 замість 262144 — бо 1 ГіБ ÷ 2 МіБ = 512. Час майже не змінився: обнулити доводиться ті самі гігабайт, тільки тепер один збій коштує 349 мікросекунд замість 749 наносекунд. Числа виглядають цілком правдоподібно, доки не поділити одне на одне. Якщо ваш «дрібний збій» коштує сотні мікросекунд — ви поміряли не дрібний збій.

**Пам'ять забрали посеред досліду.** Якщо машина під тиском, ваш гігабайт можуть частково витіснити між першим і другим проходом — і «другий прохід без збоїв» раптом покаже великі збої. Дивіться `/proc/meminfo` і не міряйте на машині, де щось іще працює.

**Лічильники не ваші.** `getrusage(RUSAGE_SELF)` підсумовує **всі** потоки процесу. Одна бібліотека, що завела фоновий потік, — і дельти попливуть без жодної видимої причини. Для однопотокового виміру беріть `RUSAGE_THREAD`.

**Другий запуск — не той самий дослід.** Після першого запуску файл лежить у кеші, а виконуваний файл програми — і поготів. Різниця між першим і другим запуском може бути більшою за все, що ви хотіли поміряти. Тому кожен режим у програмі сам приводить систему до потрібного стану й сам це перевіряє — покладатися на «щойно завантажену машину» не варто ніколи.

Найкоротший підсумок усього приладу такий: сторінковий збій — єдина подія в системі, кількість якої можна передбачити арифметично **до** виміру. Гігабайт анонімної — 262144. Теплий файл на 256 МіБ — 65536 ÷ 16. Холодний послідовний — ще ÷ 2 великих. Коли вивід сходиться з цим рахунком, ви міряєте пам'ять. Коли не сходиться — ви міряєте щось інше, і треба спершу зрозуміти що.
