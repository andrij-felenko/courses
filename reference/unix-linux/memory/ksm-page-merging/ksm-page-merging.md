# KSM: злиття однакових сторінок

<preknowlist>
- [Копіювання при записі](book:unix-linux/copy-on-write) — спільний кадр тримають під забороною запису; перший, хто пише, дістає в обробнику збою власну копію.
- [Свопінг і витіснення сторінок](book:unix-linux/swap-and-reclaim) — щоб забрати фізичний кадр, ядро має знайти всіх, хто на нього вказує, через зворотні відображення.
- [Сторінковий збій](book:unix-linux/page-fault) — апаратна зупинка інструкції при порушенні прав доступу до сторінки з подальшою обробкою в ядрі.
</preknowlist>

Коли на одній фізичній машині працюють десятки однакових віртуальних машин або контейнерів, їхня оперативна пам'ять наповнена ідентичними даними: той самий системний код `libc`, однакові глобальні таблиці, базові образи систем та розпаковані інтерпретатори. Якщо процеси прочитали той самий файл або створені через `fork`, ядро тримає один фізичний кадр задарма, бо ця спорідненість зафіксована в його внутрішніх структурах. Але коли процеси дійшли до однакового вмісту незалежно, для Linux це різні анонімні сторінки, які дублюють дані й без потреби витрачають оперативну пам'ять.

**KSM (Kernel Samepage Merging)** — це механізм дедуплікації пам'яті в ядрі Linux, який періодично та фоново сканує анонімну пам'ять процесів, знаходить сторінки з однаковим вмістом і зливає їх у єдиний фізичний кадр, вивільняючи дублікати й повертаючи оперативну пам'ять у вільний пул системи.

## Як працюють дві структури пошуку

Порівнювати кожну сторінку з кожною неможливо — для 16 ГіБ пам'яті це вимагало б понад вісім трильйонів порівнянь. Замість цього фоновий потік ядра `ksmd` впорядковує вміст сторінок лексикографічно й шукає близнюків за допомогою двох червоно-чорних дерев:

1. **Стабільне дерево (`stable tree`)** — містить сторінки, які вже були злиті. Вони захищені від запису (read-only). Оскільки процес не може змінити їхній вміст без відома ядра, ключі в цьому дереві стабільні.
2. **Нестабільне дерево (`unstable tree`)** — містить звичайні анонімні сторінки-кандидати. Оскільки процес може в будь-який момент змінити їхній вміст інструкцією процесора, це дерево регулярно скидається й будується наново між проходами сканування.

Щоб не витрачати ресурси на «летючі» сторінки, які постійно змінюються, KSM запам'ятовує контрольну суму вмісту (хеш). Якщо між двома проходами сканування хеш сторінки змінився, вона вважається нестабільною й у дерево кандидатів не потрапляє.

Коли `ksmd` знаходить дві сторінки з однаковим вмістом, ядро перенаправляє записи в таблицях сторінок обох процесів на один фізичний кадр і позначає його як «лише для читання». Звільнений другий кадр повертається системі.

Далі спільна сторінка живе за правилами [копіювання при записі](book:unix-linux/copy-on-write). Якщо один із процесів вирішить змінити свої дані, апаратура згенерує сторінковий збій. Ядро виділить для нього новий кадр, скопіює туди 4 КіБ і поновить право запису. Програма не помітить зміни семантики, окрім невеликої затримки на час обробки збою.

## Наслідки та обмеження дедуплікації

Економія пам'яті через KSM супроводжується ціною та системними ризиками:

1. **Витрати CPU.** Сканування, порівняння та обчислення контрольних сум потребують процесорного часу. Параметри `/sys/kernel/mm/ksm/pages_to_scan` (скільки сторінок оглядати за захід) та `sleep_millisecs` (затримка) задають швидкість ходу потоку `ksmd`. У сучасних ядрах Linux 6.7+ з'явився режим `smart_scan` (пропуск «стійких» самотніх сторінок) та порадник `advisor_mode = scan-time` (Linux 6.8+), який автоматично підбирає кількість сторінок під задану часову ціль та ліміт навантаження CPU.
2. **Глибина зворотних відображень.** Коли один фізичний кадр використовують сотні процесів, ядру стає складно витіснити або перенести цей кадр, бо треба оновити сотні записів у таблицях сторінок. Щоб уникнути довгих блокувань, параметр `max_page_sharing` обмежує кількість користувачів одного кадру (типово до 256), створюючи ланцюжки кадрів-двійників.
3. **Локальність NUMA.** За замовчуванням (`merge_across_nodes = 1`) KSM зливає однакові сторінки незалежно від того, на яких [вузлах NUMA](book:programming/numa) вони лежать. Це забезпечує максимальну економію пам'яті, але звернення процесів з інших вузлів до спільного кадру стають віддаленими й повільнішими. Запис `0` у цей параметр вимагає від ядра тримати окрему копію кадру для кожного вузла.
4. **Ризик масового розколу.** Зекономлена пам'ять — це відкладене зобов'язання. Якщо десятки віртуальних машин одночасно почнуть запис у злиті сторінки (наприклад, під час оновлення), станеться сплеск сторінкових збоїв і масове виділення нових кадрів, що може спричинити вичерпання пам'яті (OOM).

## Як увімкнути злиття в коді

KSM обробляє лише **анонімну приватну пам'ять** і тільки тоді, коли програма або адміністратор надали явний дозвіл. Системний вимикач `/sys/kernel/mm/ksm/run` мусить дорівнювати `1`.

Для окремих ділянок пам'яті програма викликає `madvise` з прапорцем `MADV_MERGEABLE`. Для чужих програм у контейнерах, починаючи з ядра Linux 6.4, злиття можна ввімкнути на весь процес викликом `prctl(PR_SET_MEMORY_MERGE, 1, ...)`.

:::tabs
```c
#include <sys/mman.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    size_t size = 100 * 1024 * 1024; // 100 МіБ

    void *addr = mmap(NULL, size, PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (addr == MAP_FAILED) return 1;

    // Дозволяємо KSM сканувати та зливати цю ділянку
    if (madvise(addr, size, MADV_MERGEABLE) == 0) {
        printf("KSM дозволено для ділянки %p\n", addr);
    }
    return 0;
}
```
```cpp
#include <sys/mman.h>
#include <iostream>
#include <memory>
#include <unistd.h>

int main() {
    constexpr size_t size = 100 * 1024 * 1024; // 100 МіБ

    struct MmapDeleter {
        size_t len;
        void operator()(void* p) const {
            if (p && p != MAP_FAILED) munmap(p, len);
        }
    };

    void* raw = mmap(nullptr, size, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (raw == MAP_FAILED) return 1;

    std::unique_ptr<void, MmapDeleter> area(raw, MmapDeleter{size});

    if (madvise(area.get(), size, MADV_MERGEABLE) == 0) {
        std::cout << "KSM дозволено для ділянки " << area.get() << "\n";
    }
    return 0;
}
```

## Моніторинг та безпека

Результат злиття видно у `/sys/kernel/mm/ksm/`: `pages_shared` показує кількість зайнятих спільних кадрів, а `pages_sharing` — кількість зекономлених сторінок. З боку процесу в `/proc/<pid>/smaps` рядок `KSM` відображає обсяг злитої пам'яті. При цьому показник `RSS` (Resident Set Size) не зменшується, оскільки він рахує кількість відображених сторінок, а не унікальних кадрів; реальне зниження споживання показує `PSS` (Proportional Set Size).

Для точної оцінки чистої вигоди ядро надає лічильники `general_profit` у sysfs та `ksm_process_profit` у `/proc/<pid>/ksm_stat` (додані в Linux 6.4+). Ці показники дають прибуток у байтах за відрахуванням службових структур `struct ksm_rmap_item`, які заводяться на кожну оглянуту сторінку-кандидат. Якщо злиття дає мало, а оглянутих сторінок багато, чистий прибуток може стати від'ємним — і це прямий сигнал, що механізм працює вхолосту.

Запис у злиту сторінку триває на 2–3 мікросекунди довше через обробку сторінкового збою та копіювання. Ця затримка створює побічний канал часу (timing oracle): зловмисник заповнює свою сторінку **здогадом** і за часом запису дізнається, чи є десь у пам'яті машини сторінка з точно таким вмістом. Через ці ризики (атака Dedup Est Machina) KSM рекомендують використовувати виключно в межах єдиного кола довіри (один власник ВМ чи контейнерів).
