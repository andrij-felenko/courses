# ⚙️ Модуль ядра з власною областю CMA: буфер беруть раз і чесно кажуть «немає»

Зберемо невеликий драйвер, який оголошує в дереві пристроїв власну область CMA, бере з неї суцільний буфер на відкритті пристрою й віддає його в простір користувача без копіювання, — а потім пройдемо тими самими рядками вдруге й подивимося на п'ять місць, де такий код зазвичай ламається. Спільна риса всіх п'яти: на машині розробника вони мовчать.

## Задача

Апаратний відеодекодер на системі-на-кристалі без [IOMMU](book:programming/iommu). Він ходить по кадру лінійно й виставляє фізичні адреси напряму, тому кільце кадрів мусить лежати суцільно:

```
кадр 1920×1088, NV12 (1.5 байта на піксель) = 3 133 440 Б ≈ 2.99 МіБ
кільце з 8 кадрів                           ≈ 23.9 МіБ → беремо 24 МіБ
сторінок по 4 КіБ у такому буфері           = 6144
```

Програвач хоче бачити ці кадри у своїй пам'яті. Умов три: область своя, щоб декодер не змагався за смуги з камерою; буфер беруть один раз на відкритті `/dev/vdec` і тримають до закриття; коли суцільного шматка немає — драйвер повертає помилку відкриття, а не псує відтворення мовчки.

## Ідея: чотири рішення, кожне з причини

**Область оголошують у [дереві пристроїв](book:unix-linux/device-tree), і ключове слово там — `reusable`.** Опис цієї властивості у стандарті прив'язок каже прямо: система «може користуватися пам'яттю цієї області з тим обмеженням, що драйвери-власники мусять уміти забрати її назад». Без цієї властивості вузол `reserved-memory` описує глухий резерв, який нікому не позичають. Решта властивостей вузла — про фізику: `alignment` ставить початок області на межу, з якою вміє працювати позначка рухомості, а `alloc-ranges` заганяє область у діапазон, куди пристрій дотягується, — той самий, який драйвер потім оголосить маскою в `dma_set_mask_and_coherent()`. Розійдуться ці два описи — і виділення падатиме при цілком вільній області.

**Прив'язку області до пристрою робить драйвер, а не ядро.** Властивість `memory-region` у вузлі пристрою ядро самотужки не обробляє: ні створення платформного пристрою, ні налаштування DMA до `reserved-memory` не заглядають. Поки драйвер не покличе `of_reserved_mem_device_init()`, поле `dev->cma_area` порожнє, а `dma_alloc_contiguous()` мовчки піде в загальну область — саме туди, де живуть усі інші.

**Суцільність просять явно.** За домовленістю [підсистема DMA](book:unix-linux/dma-and-buffers) «має право зібрати буфер із окремих сторінок, якщо зуміє відобразити його суцільним шматком в адресний простір DMA пристрою». Прапорець `DMA_ATTR_FORCE_CONTIGUOUS` — не оптимізація, а відмова від цієї послуги: «мені мало суцільності для пристрою, мені потрібна суцільність у фізичній пам'яті».

**Виділення стоїть у `open()`, і не лише через ціну.** Функція `dma_alloc_contiguous()` починається з перевірки `if (!gfpflags_allow_blocking(gfp)) return NULL;`. Виселення мешканців області може заснути на будь-якому кроці — тож у контексті без права спати CMA не пробують узагалі.

## Код

Спершу дерево. Область відрізають до старту системи, тому іншого місця для цього опису немає:

```dts
reserved-memory {
        #address-cells = <2>;
        #size-cells = <2>;
        ranges;

        vdec_pool: vdec-pool {
                compatible = "shared-dma-pool";
                reusable;                      /* саме це робить область CMA, а не глухим резервом */
                size = <0x0 0x1800000>;        /* 24 МіБ */
                alignment = <0x0 0x400000>;
                alloc-ranges = <0x0 0x40000000 0x0 0x40000000>;
        };
};

vdec: video-decoder@ff900000 {
        compatible = "acme,vdec";
        reg = <0x0 0xff900000 0x0 0x1000>;
        memory-region = <&vdec_pool>;          /* прочитає драйвер, не ядро */
};
```

Тепер [модуль](book:unix-linux/kernel-modules). Стан драйвера маленький, бо буфер у ньому рівно один:

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/dma-mapping.h>
#include <linux/miscdevice.h>
#include <linux/mm.h>
#include <linux/module.h>
#include <linux/mutex.h>
#include <linux/of.h>
#include <linux/of_reserved_mem.h>
#include <linux/platform_device.h>

#define VDEC_BUF_SIZE  (24u << 20)             /* 8 кадрів 1920×1088 NV12 */
#define VDEC_ATTRS     DMA_ATTR_FORCE_CONTIGUOUS

struct vdec {
        struct device     *dev;
        struct miscdevice  misc;

        struct mutex       lock;                /* захищає все нижче */
        unsigned int       refs;                /* відкриття + живі відображення */
        void              *cpu;                 /* адреса буфера в ядрі */
        dma_addr_t         dma;                 /* та сама пам'ять очима пристрою */
};

static const struct file_operations vdec_fops;  /* тіло — наприкінці файла */
```

Під'єднання пристрою — це два рядки, які легко проґавити, і жоден із них не про буфер:

```c
static int vdec_probe(struct platform_device *pdev)
{
        struct device *dev = &pdev->dev;
        struct vdec *v;
        int ret;

        v = devm_kzalloc(dev, sizeof(*v), GFP_KERNEL);
        if (!v)
                return -ENOMEM;
        v->dev = dev;
        mutex_init(&v->lock);

        /* Без цього рядка dev->cma_area лишиться порожнім, і виділення
           піде в загальну область — тихо й успішно, доки не почне падати. */
        ret = of_reserved_mem_device_init(dev);
        if (ret && ret != -ENODEV)              /* -ENODEV: memory-region у дереві немає */
                return dev_err_probe(dev, ret, "не вдалося взяти memory-region\n");

        /* Досяжність оголошують до першого виділення: розподільник
           мусить знати, у які фізичні адреси пристрій уміє дотягтися. */
        ret = dma_set_mask_and_coherent(dev, DMA_BIT_MASK(32));
        if (ret)
                return ret;

        v->misc.minor  = MISC_DYNAMIC_MINOR;
        v->misc.name   = "vdec";
        v->misc.fops   = &vdec_fops;
        v->misc.parent = dev;
        platform_set_drvdata(pdev, v);
        return misc_register(&v->misc);
}
```

Серце прикладу — відкриття. Це єдине місце в драйвері, де взагалі згадано виділення:

```c
static int vdec_open(struct inode *ino, struct file *f)
{
        /* Ядро вже поклало сюди вказівник на miscdevice — від нього
           дістаємося свого стану, а далі підмінюємо на нього ж. */
        struct vdec *v = container_of(f->private_data, struct vdec, misc);
        int ret = 0;

        mutex_lock(&v->lock);
        if (!v->refs) {
                /* GFP_KERNEL тут обов'язковий: перенос мешканців області
                   спить, і без права спати CMA навіть не пробують.       */
                v->cpu = dma_alloc_attrs(v->dev, VDEC_BUF_SIZE, &v->dma,
                                         GFP_KERNEL, VDEC_ATTRS);
                if (!v->cpu) {
                        dev_warn(v->dev,
                                 "немає суцільних %u КіБ; подивіться maxchunk у /sys/kernel/debug/cma/\n",
                                 VDEC_BUF_SIZE >> 10);
                        ret = -ENOMEM;
                        goto out;
                }
        }
        v->refs++;
        f->private_data = v;
out:
        mutex_unlock(&v->lock);
        return ret;
}

static void vdec_put(struct vdec *v)
{
        mutex_lock(&v->lock);
        if (!--v->refs) {
                dma_free_attrs(v->dev, VDEC_BUF_SIZE, v->cpu, v->dma, VDEC_ATTRS);
                v->cpu = NULL;
        }
        mutex_unlock(&v->lock);
}
```

Віддача буфера в процес — один виклик, але з умовою: `dma_mmap_attrs()` треба годувати рівно тим, чим годували `dma_alloc_attrs()`, включно з набором ознак. Межі він звірить сам і поверне `-ENXIO`, якщо процес просить більше, ніж виділено:

```c
static void vdec_vm_open(struct vm_area_struct *vma)
{
        struct vdec *v = vma->vm_private_data;

        mutex_lock(&v->lock);
        v->refs++;                              /* відображення пережило fork */
        mutex_unlock(&v->lock);
}

static void vdec_vm_close(struct vm_area_struct *vma) { vdec_put(vma->vm_private_data); }

static const struct vm_operations_struct vdec_vm_ops = {
        .open  = vdec_vm_open,
        .close = vdec_vm_close,
};

static int vdec_mmap(struct file *f, struct vm_area_struct *vma)
{
        struct vdec *v = f->private_data;
        int ret;

        mutex_lock(&v->lock);
        ret = dma_mmap_attrs(v->dev, vma, v->cpu, v->dma, VDEC_BUF_SIZE, VDEC_ATTRS);
        if (!ret) {
                v->refs++;                      /* відображення тримає буфер нарівні з fd */
                vma->vm_private_data = v;
                vma->vm_ops = &vdec_vm_ops;
        }
        mutex_unlock(&v->lock);
        return ret;
}

static int vdec_release(struct inode *ino, struct file *f)
{
        vdec_put(f->private_data);
        return 0;
}

static const struct file_operations vdec_fops = {
        .owner   = THIS_MODULE,
        .open    = vdec_open,
        .release = vdec_release,
        .mmap    = vdec_mmap,
};

static void vdec_remove(struct platform_device *pdev)
{
        struct vdec *v = platform_get_drvdata(pdev);

        misc_deregister(&v->misc);
        of_reserved_mem_device_release(&pdev->dev);
}

static const struct of_device_id vdec_of_match[] = {
        { .compatible = "acme,vdec" },
        { }
};
MODULE_DEVICE_TABLE(of, vdec_of_match);

static struct platform_driver vdec_driver = {
        .driver = { .name = "vdec", .of_match_table = vdec_of_match },
        .probe  = vdec_probe,
        .remove = vdec_remove,
};
module_platform_driver(vdec_driver);
MODULE_LICENSE("GPL");
```

## Пастки

**Суцільність, якої не треба.** `DMA_ATTR_FORCE_CONTIGUOUS` виглядає як безпечна перестраховка — і саме тому потрапляє в драйвери, яким він не потрібен. Якщо між пристроєм і пам'яттю стоїть IOMMU, прапорець нічого не додає пристроєві й забирає в системи: без нього ядро зібрало б буфер зі звичайних розкиданих сторінок і зшило б їх таблицею. Якщо контролер уміє [йти списком шматків](book:algorithms/scatter-gather), суцільність не потрібна й поготів. Перевірка займає секунду: якщо `/sys/class/iommu/` не порожня, а пристрій має там свою групу, — прапорець зайвий. І навпаки: на системі **без** IOMMU він майже нічого не міняє, бо великі виділення й так ідуть через CMA. Уся вага цього прапорця — рівно там, де IOMMU є; там же він найчастіше й зайвий.

**Виділення на кожен кадр.** Спокуса природна: брати буфер під кадр і віддавати після показу — тоді пам'ять не лежить дарма. Ціна цього рішення двоскладова, і перша половина навіть не про швидкість. У гарячому шляху драйвери часто виділяють із `GFP_ATOMIC` — і тоді `dma_alloc_contiguous()` віддає `NULL` одразу, при цілком порожній області: у контексті без права спати переносити нікого не можна. Помилка виглядає як брак пам'яті, хоча пам'ять є.

Друга половина — про швидкість, і арифметика тут невблаганна:

```
сторінок у буфері                = 6144
переносів за секунду при 60 к/с  = 6144 · 60 = 368 640
бюджет одного кадру              = 1 / 60 с  = 16.7 мс
навіть по 1 мкс на перенос       = 6144 мкс  = 6.1 мс з тих 16.7
```

А мікросекунда — оптимістична оцінка: у переносі сидить не тільки копіювання чотирьох кілобайтів, а й правка таблиць сторінок з [розсиланням скидань TLB](book:unix-linux/tlb-shootdown) по всіх ядрах і очікуванням підтверджень.

Унизу: пунктирна сітка з дев'яти бюджетів по 16.7 мс, а поверх неї лише п'ять широких пар «виділення плюс кадр», які виходять за межі сіток](/reference/unix-linux/memory/cma-contiguous-allocator/img/cma-where-alloc.svg)

*Той самий буфер і те саме залізо; різниця лише в тому, у якій функції драйвера стоїть `dma_alloc_attrs()`.*

**Звільнення, поки відображення живе.** Найтихіша помилка цього коду ховається не в CMA, а в тривалості життя. Закриття дескриптора не знімає `mmap`: процес може відобразити буфер, закрити `/dev/vdec` і далі спокійно читати з нього кадри. Драйвер, який звільняє буфер у `release()`, повертає в область пам'ять, яку в цю саму мить читає процес, — а CMA чесно поселить туди рухомі сторінки, і в кадрі проступлять шматки чийогось файлового кеша. Тому лічильник у прикладі рахує не відкриття, а **всіх, хто тримає буфер**: `vdec_mmap()` додає одиницю, `.close` знімає, а `fork()` подвоює її через `.open` — інакше вихід дитини звільнив би буфер батькові.

**Когерентність, за яку платять швидкістю читання.** `dma_alloc_attrs()` віддає узгоджену пам'ять: процесор і пристрій бачать однакові байти без жодного явного скидання [кеша](book:programming/cache). На платформі без апаратної [когерентності](book:programming/cache-coherency-dma) ядро домагається цього єдиним доступним способом — робить відображення **некешованим**, і `dma_mmap_attrs()` переносить ті самі права в процес. Наслідок видно не в коді, а в профілі: кожне читання байта з такої пам'яті — окрема транзакція до контролера, рядок кеша не працює, попереднє підвантаження не працює. Процес, який хоче лише **покласти** туди кадр, рятує ознака `DMA_ATTR_WRITE_COMBINE` — записи «можуть буферизуватися задля швидкості», і послідовний запис іде майже на швидкості пам'яті. Процесові, який хоче кадр **читати й обробляти**, узгоджена пам'ять не підходить взагалі: йому потрібен кешований буфер з явною синхронізацією, а це вже [dma-buf](book:unix-linux/dma-buf) із його ioctl синхронізації, а не власний `mmap`. На x86 і на когерентній системі-на-кристалі різниці немає жодної — помилка терпляче чекає на переїзд.

**Висновок про причину відмови без погляду в debugfs.** Коли `dma_alloc_attrs()` повернув `NULL`, у цього є кілька різних причин, і найгрубіший важіль — збільшити область — лікує лише одну з них. Розрізняє їх один каталог:

```sh
# усі три числа — у сторінках
cat /sys/kernel/debug/cma/*/count      # розмір області
cat /sys/kernel/debug/cma/*/used       # скільки роздано пристроям
cat /sys/kernel/debug/cma/*/maxchunk   # найбільша вільна смуга поспіль

grep Cma /proc/meminfo                 # те саме по всій системі, у кілобайтах
```

Читати їх треба парою. `used` малий, а `maxchunk` теж малий — це фрагментація області: кілька дрібних довговічних буферів порізали її на клапті, і лікується це не розміром, а укрупненням буферів. `maxchunk` більший за запит, а виділення все одно падає — місце є, але смугу не вдалося очистити: хтось тримає в ній [закріплену сторінку](book:unix-linux/page-pinning-gup). А порожній каталог `/sys/kernel/debug/cma/` означає, що області CMA не створено взагалі: найімовірніше, у дереві забули `reusable`, і вузол став глухим резервом. Каталог є, але `used` уперто нуль при робочому декодері — забули `of_reserved_mem_device_init()`, і буфер увесь цей час приходив із загальної області.

> 🔧 **Навіщо це.** Чотири з п'яти пасток вище об'єднує те, що неправильний драйвер працює. Зайвий `DMA_ATTR_FORCE_CONTIGUOUS` дає робочий буфер, виділення на кадр дає правильне відео на порожній системі, зарано звільнений буфер псує кадр раз на тисячу запусків, некешоване відображення дає точні пікселі. Компілятор мовчить, тести проходять, і різниця вилазить лише під навантаженням або на іншій платі. Єдине, що працює проти цього, — ставити собі три питання ще до першого рядка коду: чи справді потрібна фізична суцільність, скільки разів за час роботи ми її просимо і хто читатиме ці байти процесором.
