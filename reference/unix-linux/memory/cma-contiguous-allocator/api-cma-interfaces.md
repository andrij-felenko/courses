# 📋 Інтерфейси CMA: параметри, вузол дерева пристроїв, виклики, лічильники

Це повний перелік того, що розподільник суцільної пам'яті виставляє назовні: чим область оголошують, якими викликами з неї беруть буфер і в яких файлах видно її стан. Довідка потрібна тому, що важелі лежать у трьох різних шарах — конфігурація збірки, завантаження, драйвер, — і кожен шар говорить про ту саму область власними одиницями: один рахує мегабайти, другий байти, третій сторінки, четвертий порядки двійки.

Усе звірено з деревом ядра 6.x: `mm/Kconfig`, `kernel/dma/Kconfig`, `kernel/dma/contiguous.c`, `mm/cma.c`, `mm/cma_debug.c`, `mm/cma_sysfs.c`.

## Опції збірки

| Опція | Типове значення | Що визначає |
| --- | --- | --- |
| `CONFIG_CMA` | — | сам розподільник; тягне за собою `MIGRATION` і `MEMORY_ISOLATION`, бо без переносу й ізоляції він не працює |
| `CONFIG_DMA_CMA` | — | міст від DMA API до CMA. Без нього область існує, але `dma_alloc_coherent` у неї не заходить |
| `CONFIG_CMA_AREAS` | `20` при `NUMA`, інакше `8` | стеля числа областей у системі (`MAX_CMA_AREAS`) |
| `CONFIG_CMA_SIZE_MBYTES` | `0` на x86, інакше `16` | розмір типової області в МіБ |
| `CONFIG_CMA_SIZE_PERCENTAGE` | `0` на x86, інакше `10` | той самий розмір у відсотках усієї пам'яті |
| `CONFIG_CMA_SIZE_SEL_{MBYTES,PERCENTAGE,MIN,MAX}` | — | котре з двох попередніх чисел узяти (або менше, або більше з них) |
| `CONFIG_CMA_ALIGNMENT` | `8`, діапазон 2…12 | стеля вирівнювання, яку DMA-шлях просить у `cma_alloc`, у порядках сторінок |
| `CONFIG_DMA_NUMA_CMA` | — | окремі області на [вузол NUMA](book:programming/numa), щоб пристрій брав місцеву пам'ять |
| `CONFIG_CMA_DEBUGFS` | — | файли в `/sys/kernel/debug/cma/` |
| `CONFIG_CMA_SYSFS` | — | лічильники в `/sys/kernel/mm/cma/` |

`CONFIG_CMA_AREAS` — тверда стеля, а не підказка: оголошення понад цю кількість просто провалюється при завантаженні. На системі-на-кристалі з десятком підсистем, кожна зі своєю областю, типова вісімка вичерпується легко, і симптом виглядає як «одна з областей чомусь не з'явилася».

## Командний рядок

У кожного з трьох параметрів власний ранній розбирач; місце, звідки вони беруться, — [рядок ядра від завантажувача](book:unix-linux/bootloader-and-cmdline).

```
cma=nn[MG]@[start[MG][-end[MG]]]
cma_pernuma=nn[MG]
numa_cma=<node>:nn[MG][,<node>:nn[KMG]]
```

| Запис | Що виходить |
| --- | --- |
| `cma=64M` | 64 МіБ будь-де в межах, куди дотягується маска адресації |
| `cma=64M@0x40000000` | **рівно** за цією адресою: розбір ставить межу в `base + size`, а збіг `base + size == limit` вмикає ознаку `fixed` — «або тут, або ніде» |
| `cma=64M@0x40000000-0x80000000` | 64 МіБ будь-де всередині вікна; `fixed` не вмикається |
| `cma=0` | типової області немає зовсім |
| `cma_pernuma=32M` | по 32 МіБ на кожен вузол NUMA; типово `0` |
| `numa_cma=0:64M,1:32M` | різні розміри названим вузлам; для них б'є `cma_pernuma=` |

Числа проходять через `memparse` — звідси суфікси K/M/G і шістнадцяткові адреси з `0x`. Різниця між `@start` і `@start-end` коштує дорого й у документації не впадає в око: одна адреса після равлика — це вимога стати рівно там (потрібна, коли на цю адресу заточене залізо), а пара адрес — лише вікно, всередині якого ядро вибирає місце саме.

Пріоритет між джерелами один і жорсткий: `cma=` перебиває вузол з `linux,cma-default` у дереві пристроїв. Ядро не мовчить — воно друкує в журнал, що пропускає вузол на користь параметра.

## Опис області в дереві пристроїв

На системі-на-кристалі область описують у [дереві пристроїв](book:unix-linux/device-tree) — під вузлом `reserved-memory`.

```dts
reserved-memory {
        #address-cells = <2>;
        #size-cells = <2>;
        ranges;

        video_cma: video-pool {
                compatible = "shared-dma-pool";
                reusable;                            /* саме це слово робить резерв областю CMA */
                size = <0x0 0x08000000>;             /* 128 МіБ */
                alignment = <0x0 0x00400000>;        /* 4 МіБ */
                alloc-ranges = <0x0 0x40000000 0x0 0x40000000>;
        };
};

vpu@ff9a0000 {
        memory-region = <&video_cma>;
        memory-region-names = "video";
};
```

| Властивість | Обов'язкова | Значення |
| --- | --- | --- |
| `compatible = "shared-dma-pool"` | так | спільний запас буферів DMA для набору пристроїв |
| `reusable` | **так** | система має право вживати пам'ять, поки власник її не забрав. Без цього слова вузол — глухий резерв, і CMA його не візьме (`-ENODEV`) |
| `no-map` | **не можна** | заборона відображати ділянку; взаємно виключна з `reusable` — разом вони не мають сенсу й відкидаються |
| `size` | так, якщо немає `reg` | розмір у байтах, число комірок — за `#size-cells` батька |
| `reg` | альтернатива до `size` | конкретний діапазон замість пошуку |
| `alignment` | ні | межа, на яку кластуть початок області |
| `alloc-ranges` | ні | пари «адреса, довжина» — вікна, з яких дозволено брати |
| `linux,cma-default` | ні | ця область стає типовою для всіх, хто не назвав свою |
| `linux,dma-default` | ні | те саме для розподільника узгодженої пам'яті |

`size` і `reg` — це два різні способи, а не два записи одного. `reg` називає конкретний діапазон, який хтось уже вибрав за вас: так описують пам'ять, прив'язану до заліза. `size` разом із `alignment` і `alloc-ranges` описує не місце, а **вимоги** до нього, і місце шукає ядро. Друга форма переносна між платами тієї самої родини, перша — ні, тож без потреби в конкретній адресі беруть саме `size`.

З боку пристрою прив'язка — одна властивість `memory-region` із посиланням на вузол. Драйвер підбирає її викликом `of_reserved_mem_device_init_by_idx(dev, np, idx)` або `..._by_name(dev, np, "video")`, який шукає індекс у `memory-region-names`; успіх означає, що `dev->cma_area` тепер указує на цю область, і всі наступні виділення для пристрою підуть саме звідти. Поки цього виклику не було, властивість у дереві не робить нічого — вона лише посилання, яке хтось має пройти.

## Виклики ядра

```c
/* оголошення області — лише на етапі завантаження, звідси __init */
int cma_declare_contiguous_nid(phys_addr_t base, phys_addr_t size,
                               phys_addr_t limit, phys_addr_t alignment,
                               unsigned int order_per_bit, bool fixed,
                               const char *name, struct cma **res_cma, int nid);
int cma_init_reserved_mem(phys_addr_t base, phys_addr_t size,
                          unsigned int order_per_bit, const char *name,
                          struct cma **res_cma);

/* робота з готовою областю */
struct page *cma_alloc(struct cma *cma, unsigned long count,
                       unsigned int align, bool no_warn);
bool         cma_release(struct cma *cma, const struct page *pages,
                         unsigned long count);
```

| Аргумент `cma_declare_contiguous_nid` | Одиниця | Значення |
| --- | --- | --- |
| `base` | байти | `0` — шукати будь-де; ненульове разом із `fixed = true` — вимога до конкретної адреси |
| `size` | байти | розмір області |
| `limit` | байти | верхня межа фізичних адрес (`0` — без межі) |
| `alignment` | байти | піднімається до `CMA_MIN_ALIGNMENT_BYTES` = `PAGE_SIZE * pageblock_nr_pages`; нижче цієї межі позначку рухомості на область просто не поставити |
| `order_per_bit` | порядок | скільки сторінок відповідає одному бітові мапи, як степінь двійки |
| `name` | — | до `CMA_MAX_NAME` = 64 байтів; це ж ім'я стає назвою теки в debugfs і sysfs |
| `nid` | — | вузол NUMA, з якого брати |

Два оголошення різняться тим, хто відкроює пам'ять. `cma_declare_contiguous_nid` робить обидві дії: сам просить у раннього завантажувального розподільника діапазон за наведеними вимогами й уже потім робить із нього область. `cma_init_reserved_mem` бере діапазон, **уже** відкроєний кимось іншим, і лише надбудовує над ним облік — цим шляхом ідуть вузли дерева пристроїв, бо там пам'ять відклали ще на розборі `reserved-memory`, до того, як хтось знав, що це буде CMA.

`order_per_bit` варто прочитати уважно, бо число тут не абстрактне. Шлях DMA передає **нуль** — один біт на одну сторінку, тобто мапа найдрібнішого зерна. Області під [великі сторінки](book:unix-linux/huge-pages) передають порядок великої сторінки, і тоді один біт відповідає за кілька мегабайтів одразу. Від цього числа залежить, у якій кратності область узагалі вміє видавати шматки.

`cma_alloc` бере `count` у **сторінках**, а `align` — у **порядках**, не в байтах: `align = 4` означає межу 16 сторінок. Повертає перший `struct page` смуги або `NULL` — без коду помилки, тож розрізнити «немає місця» й «мешканця не вдалося виселити» звідси неможливо, і саме тому діагностика живе в лічильниках, а не в поверненому значенні. `no_warn` гасить попередження в журналі, коли невдача — очікуваний робочий випадок. `cma_release` повертає `false`, якщо сторінки не належать цій області.

## Шлях, яким туди потрапляє драйвер

Драйвер майже ніколи не кличе `cma_alloc` сам — він просить буфер звичайним [інтерфейсом DMA](book:unix-linux/dma-and-buffers/api-dma-mapping.md), а той сам вирішує, звідки взяти.

```c
buf = dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL);
buf = dma_alloc_attrs(dev, size, &dma_handle, GFP_KERNEL, DMA_ATTR_FORCE_CONTIGUOUS);
ret = dma_mmap_attrs(dev, vma, buf, dma_handle, size, DMA_ATTR_FORCE_CONTIGUOUS);
```

Порядок вибору області в `dma_alloc_contiguous` такий:

| Умова | Звідки беруть |
| --- | --- |
| у пристрою є `dev->cma_area` (з `memory-region`) | тільки з неї, за будь-якого розміру |
| `size <= PAGE_SIZE` і власної області немає | CMA не чіпають узагалі — одну сторінку дасть звичайний [розподільник кадрів](book:unix-linux/physical-page-allocator) |
| запит із `GFP_DMA` / `GFP_DMA32` | вузлові області пропускають — вони не дають гарантії щодо зони |
| увімкнено `CONFIG_DMA_NUMA_CMA` | область свого вузла NUMA, з відкотом на типову |
| решта | типова область (`dma_contiguous_default_area`) |

Відсіювання запитів на одну сторінку — не оптимізація, а межа застосовності. Одна сторінка ніколи не буває несуцільною, тож брати її з CMA означає заплатити виселенням мешканців за те, що звичайний розподільник дає задарма.

Вирівнювання шлях обчислює сам: `min(get_order(size), CONFIG_CMA_ALIGNMENT)` — природне вирівнювання за розміром, але не вище стелі з конфігурації. Стеля тут не про дрібниці: без неї запит на 64 МіБ вимагав би початку, кратного 64 МіБ, а це вимога **важча** за саму суцільність — область на 128 МіБ мала б у такому разі рівно дві придатні позиції. Типові вісім порядків обмежують вимогу 256 сторінками, і цього досить будь-якому контролерові, який справді має обмеження на межу.

`DMA_ATTR_FORCE_CONTIGUOUS` (`1UL << 6`) важить рівно там, де між пристроєм і пам'яттю стоїть [IOMMU](book:programming/iommu): без атрибута цей шлях зшив би розкидані кадри таблицею перекладу й до CMA не звернувся, з атрибутом — вимагає фізично суцільного буфера попри IOMMU. Атрибут мусить збігатися при виділенні і при [відображенні в простір користувача](book:unix-linux/mmap-model), інакше програма дістане ділянку з іншими властивостями кешування, ніж ядро.

## Точки спостереження

`/proc/meminfo`, дві сумарні по системі:

| Поле | Джерело | Що показує |
| --- | --- | --- |
| `CmaTotal` | `totalcma_pages` | сума розмірів усіх областей, у кБ |
| `CmaFree` | `NR_FREE_CMA_PAGES` | скільки сторінок в областях **зараз вільні з погляду розподільника кадрів** |

`/sys/kernel/debug/cma/<name>/` при `CONFIG_CMA_DEBUGFS`:

| Файл | Режим | Значення |
| --- | --- | --- |
| `count` | читання | розмір області в сторінках |
| `used` | читання | скільки сторінок роздано через бітову мапу |
| `maxchunk` | читання | **найбільша вільна смуга** — єдине число, що передбачає долю наступного запиту |
| `order_per_bit` | читання | сторінок на біт, як степінь двійки |
| `alloc` | запис | записане число сторінок виділяють з області |
| `free` | запис | стільки ж повертають назад |
| `ranges/<r>/base_pfn`, `ranges/<r>/bitmap` | читання | початок діапазону й сира мапа |

Тека `ranges/` існує тому, що область не зобов'язана бути одним шматком: оголошення через `cma_declare_contiguous_multi` збирає її з кількох діапазонів, і кожен веде власну бітову мапу. Для сумісності зі старими сценаріями поруч лежать посилання `base_pfn` і `bitmap`, що вказують на нульовий діапазон.

`/sys/kernel/mm/cma/<name>/` при `CONFIG_CMA_SYSFS` — п'ять лічильників: `total_pages`, `available_pages`, `alloc_pages_success`, `alloc_pages_fail`, `release_pages_success`. Три останні накопичуються від завантаження й міряють **сторінки, а не запити**. Різниця не косметична: `alloc_pages_fail` зі значенням 8192 — це, найпевніше, одна невдала спроба взяти 32 МіБ, а не вісім тисяч невдач. Ділити це число на типовий розмір буфера драйвера — єдиний спосіб дізнатися, скільки разів насправді відмовили.

Тут криється розбіжність, через яку читають не те число. `CmaFree` і `available_pages` відповідають на різні питання й у робочій системі **не збігаються**. `CmaFree` — це скільки сторінок області порожні просто зараз, тобто в які ще не заселилися рухомі мешканці. `available_pages` — скільки область не роздала пристроям, тобто скільки вона в принципі може спробувати звільнити. Заселена кешем файлів область показує малий `CmaFree` і великий `available_pages`, і це ознака здоров'я: пам'ять працює. Рівність `used + available_pages == total_pages` тримається завжди, `CmaFree` плаває незалежно від обох.

> 🔧 **Навіщо це.** Коли виділення падає, дивитися треба на `maxchunk`, а не на `CmaFree`. Мале `maxchunk` при великому `available_pages` — область роздроблена зсередини, і збільшувати її марно. Велике `maxchunk` при відмові означає протилежне: місце було, а смугу не вдалося очистити від мешканця. `alloc_pages_fail` сам по собі обидва роди відмов не розрізняє — він рахує будь-яку, тож розводить їх саме `maxchunk`. `CmaFree` у цій діагностиці не значить майже нічого: він падає до нуля на цілком здоровій системі.

## Перевірка без жодного рядка драйвера

Файли `alloc` і `free` існують саме для того, щоб з'ясувати, чи здатна область видати потрібну смугу, ще до того, як писати код.

```
$ grep Cma /proc/meminfo
CmaTotal:         131072 kB
CmaFree:            4096 kB

$ cd /sys/kernel/debug/cma/video-pool
$ cat count order_per_bit maxchunk
32768
0
32768

$ echo 8192 > alloc          # 8192 сторінок = 32 МіБ
$ cat used maxchunk
8192
24576
$ echo 8192 > free
```

Запис у `alloc` проходить рівно тим шляхом, що й запит драйвера — з ізоляцією, спорожненням локальних запасів і переносом мешканців. Невдача повертається оболонці помилкою запису, а `alloc_pages_fail` у sysfs підростає. Отже, машину, на якій буфер не виділяється раз на годину, можна допитати простим циклом із двох рядків, не чіпаючи ані ядра, ані пристрою.
