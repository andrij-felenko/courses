# Статус завершення: 0, помилки й мапування сигналів у код 128+N

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У світі Unix та Linux статус завершення (exit status) є фундаментальним механізмом взаємодії між процесами. Він дозволяє операційній системі та програмам-оболонкам (таким як bash, zsh, sh) дізнаватися, чи успішно завершила свою роботу викликана програма, чи сталася помилка, і якого роду ця помилка.

У цій статті ми детально розглянемо, як формується статус завершення на рівні ядра за допомогою системних викликів `exit()` та `waitpid()`, як обробляються макроси `WIFEXITED`, `WEXITSTATUS`, `WTERMSIG`, а також розберемо специфіку роботи оболонки зі спеціальною змінною `$?` та мапуванням сигналів (наприклад, SIGKILL, SIGSEGV) у коди 128+N.

## 1. Системний виклик `exit()` та завершення процесу

Коли процес у Unix завершує свою роботу, він викликає системний виклик `_exit(status)` або бібліотечну функцію `exit(status)` (яка додатково виконує очищення буферів вводу-виводу стандартної бібліотеки C перед викликом `_exit()`). 

Аргумент `status` — це ціле число (`int`). Незважаючи на те, що C дозволяє передавати ціле число розміром 32 або 64 біти, операційна система (конкретно, ядро Linux) використовує лише молодші 8 бітів цього значення. Таким чином, фактичний статус завершення, доступний батьківському процесу, лежить у діапазоні від 0 до 255.

* **0** — традиційно означає **успішне завершення** без помилок.
* **1-255** — означає помилку, причому різні коди можуть нести різний семантичний зміст залежно від програми.

## 2. Як батьківський процес отримує статус: `waitpid()`

Щоб зчитати статус завершення дочірнього процесу, батьківський процес використовує системний виклик `wait()` або `waitpid()`.

```c
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

pid_t waitpid(pid_t pid, int *wstatus, int options);
```

Аргумент `wstatus` вказує на цілочисельну змінну, в яку ядро запише інформацію про те, як завершився процес.
Важливо розуміти, що значення `wstatus` не дорівнює значенню, переданому в `exit(status)`. `wstatus` — це 16-бітне (або більше) значення, яке містить **декілька частин інформації**:
1. Чи завершився процес нормально (через `exit`) чи був вбитий сигналом?
2. Який саме був код завершення (якщо нормально) або який сигнал його вбив (якщо ненормально)?
3. Чи був створений core dump?

## 3. Макроси `WIFEXITED`, `WEXITSTATUS`, `WTERMSIG`

Для правильної інтерпретації `wstatus` стандарт POSIX визначає набір макросів у заголовковому файлі `<sys/wait.h>`. Безпосередньо розбирати біти не рекомендується.

### 3.1 `WIFEXITED` та `WEXITSTATUS`
Ці макроси використовуються, якщо процес завершився добровільно.
* `WIFEXITED(wstatus)` повертає істину (true), якщо дочірній процес завершився нормально, тобто викликав `exit(3)` або `_exit(2)`, або повернув значення з функції `main()`.
* `WEXITSTATUS(wstatus)` витягує власне код завершення (молодші 8 біт аргументу, переданого в `exit()`). Цей макрос має сенс викликати **тільки** якщо `WIFEXITED` повернув істину.

### 3.2 Завершення за сигналом: `WIFSIGNALED` та `WTERMSIG`
Якщо процес не завершився сам, а був перерваний сигналом (наприклад, SIGKILL, SIGTERM або SIGSEGV (Segmentation Fault)), ситуація змінюється.
* `WIFSIGNALED(wstatus)` повертає істину, якщо дочірній процес був примусово завершений неперехопленим сигналом.
* `WTERMSIG(wstatus)` витягує номер сигналу, який спричинив завершення. Викликати тільки якщо `WIFSIGNALED` істинне.

## 4. Статус `$?` у командній оболонці (Shell)

У bash (та інших POSIX-сумісних оболонках) змінна `$?` містить статус завершення останньої виконаної команди. Shell приховує складність `waitpid()` та макросів, видаючи користувачеві одне ціле число від 0 до 255.

Але як shell об'єднує два можливих сценарії (нормальне завершення і завершення від сигналу) в одне число від 0 до 255?

### 4.1 Нормальне завершення
Якщо процес завершується через `exit(N)`, то `$?` дорівнює `N & 255`.

### 4.2 Мапування сигналів у код 128 + N
Коли процес вбивається сигналом (тобто `WIFSIGNALED` є істинним), у нього немає власного "коду завершення", адже він не встиг (чи не зміг) викликати `exit()`. Щоб повідомити користувачеві, що програма впала від сигналу, bash використовує конвенцію: **він додає 128 до номера сигналу.**

$$ \text{Exit Status} = 128 + \text{Signal Number} $$

Наприклад:
* **SIGINT (Ctrl+C)**: Номер сигналу зазвичай 2. Якщо ви перериваєте програму через Ctrl+C, `$?` буде дорівнювати `128 + 2 = 130`.
* **SIGKILL (kill -9)**: Номер сигналу 9. Статус `$?` буде `128 + 9 = 137`.
* **SIGSEGV (Segmentation Fault)**: Номер 11. Статус `$?` буде `128 + 11 = 139`.
* **SIGTERM**: Номер 15. Статус `$?` буде `128 + 15 = 143`.

Це елегантне, хоч і дещо заплутане рішення. Воно дозволяє використовувати діапазон 0-127 для власних кодів помилок програми, а діапазон 128-255 — для індикації того, що процес був убитий сигналом.

## 5. Проблеми та колізії

Конвенція 128+N працює добре доти, доки програма сама не вирішить повернути код завершення більше ніж 127.

Якщо програма робить `exit(139)`, то оболонка побачить `$? = 139`. Вона не зможе однозначно сказати, чи програма просто повернула 139, чи вона впала з Segmentation Fault (SIGSEGV).
Саме тому стандарти (зокрема, Advanced Bash-Scripting Guide) наполегливо рекомендують:
**Ніколи не використовуйте коди завершення більше 127 у своїх власних програмах.**
Діапазон 1-127 безпечний і призначений для ваших специфічних помилок.

## 6. Висновок
Статус завершення в Unix — це багатошарова конструкція. Ядро зберігає детальну інформацію про причину смерті процесу, використовуючи складені поля у 16-бітному значенні. Бібліотека C надає макроси `WIFEXITED`, `WEXITSTATUS`, `WTERMSIG` для розбору цієї структури. А командна оболонка транслює цю інформацію в плоский простір чисел 0-255, застосовуючи правило 128+N для сигналів. 
Розуміння цього механізму є критичним для системного програмування на C та написання надійних shell-скриптів.
