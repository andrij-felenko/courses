# 📋 Інтерфейс коду виходу: макроси waitpid, sysexits.h та POSIX-коди

Низькорівнева специфікація макросів розбору статусу `wstatus`, системного виклику `waitid()`, стандартизованих кодів помилок `<sysexits.h>` та зарезервованих значень POSIX визначає точний двосторонній контракт між дочірнім процесом, системними викликами ядра та командною оболонкою.

Цей довідник детально описує структуру системних констант, бітовий розклад масок ядра Linux, розширені структури `siginfo_t` та стандартизовані таблиці системних кодів помилок.

## 1. Макроси аналізу статусу у `<sys/wait.h>`

Під час виклику системних функцій `wait()` або `waitpid(pid, &wstatus, options)` ядро повертає ціле значення `wstatus`, у якому упаковуються причини зупинки, аварійного завершення чи звичайного виходу процесу. Стандарт POSIX визначив вісім обов'язкових макросів для розпакування цієї структури без прямого використання бітових зсувів:

| Макрос | Вхідна умова | Що витягує / означає |
| :--- | :--- | :--- |
| `WIFEXITED(w)` | Завжди | Повертає `1` (true), якщо процес завершився добровільно через виклик `exit()`, `_exit()` або повернув значення з функції `main()`. |
| `WEXITSTATUS(w)` | `WIFEXITED(w) != 0` | Повертає молодші 8 бітів (`0..255`) значення, яке було передано в `exit(code)`. Виклик неліцензований, якщо процес вбито сигналом. |
| `WIFSIGNALED(w)` | Завжди | Повертає `1`, якщо процес був примусово анульований неперехопленим сигналом операційної системи. |
| `WTERMSIG(w)` | `WIFSIGNALED(w) != 0` | Повертає числовий номер сигналу (`1..64`), який призвів до примусового виходу процесу з життя. |
| `WCOREDUMP(w)` | `WIFSIGNALED(w) != 0` | Повертає `1`, якщо ядро згенерувало образ пам'яті (core dump) при загибелі процесу (залежить від біта 7 у `wstatus`). |
| `WIFSTOPPED(w)` | Завжди | Повертає `1`, якщо процес не загинув, а був зупинений сигналом підсистеми Job Control (наприклад, `SIGSTOP` або `SIGTSTP`). |
| `WSTOPSIG(w)` | `WIFSTOPPED(w) != 0` | Повертає номер сигналу, який спричинив тимчасову зупинку процесу. |
| `WIFCONTINUED(w)`| Завжди | Повертає `1`, якщо процес відновлено після зупинки за допомогою сигналу `SIGCONT`. |

### Докладний розбір бітової декомпозиції в ядрі Linux

На архітектурах Linux x86 та ARM значення `wstatus` розпаковується ядерними макросами за допомогою бітових масок та правосторонніх зсувів. Розуміння цієї логіки необхідне при написанні власного системного коду або аналізі даних у відлагоджувачах:

* **Звичайний вихід (`exit(code)`)**:
  * Молодші 7 бітів `wstatus & 0x7F` дорівнюють `0`.
  * Старший байт `(wstatus >> 8) & 0xFF` зберігає код виходу `0..255`.
  * Перевірка `WIFEXITED`: макрос перевіряє, чи дорівнює молодший 7-бітний блок нулю.
* **Загибель від сигналу (`SIGKILL`, `SIGSEGV`)**:
  * Молодші 7 бітів `wstatus & 0x7F` містять номер сигналу `1..127`.
  * Біт 7 (`0x80`) позначає наявність згенерованого core dump.
  * Перевірка `WIFSIGNALED`: макрос перевіряє, чи молодший блок не є нулем і не дорівнює `0x7F` (яке позначає зупинку).
* **Тимчасова зупинка (`SIGSTOP`, `SIGTSTP`)**:
  * Молодший байт `wstatus & 0xFF` дорівнює `0x7F`.
  * Старший байт `(wstatus >> 8) & 0xFF` містить номер сигналу зупинки.

Завдяки цьому пакуванню за один системний виклик `waitpid()` батьківський процес отримує повний вектор стану дочірнього завдання без виділення додаткової пам'яті чи складних структур.

## 2. Сучасний системний виклик `waitid()` та структура `siginfo_t`

Стандарт POSIX.1-2001 запровадив гнучкіший системний виклик `int waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options)` із заголовка `<sys/wait.h>`, який замість упаковки бітів у `int` повертає детальну структуру `siginfo_t`.

### Поля структури `siginfo_t`, пов'язані з виходом

При успішному виклику `waitid()` ядро Linux заповнює наступні поля в `siginfo_t`:

1. `si_pid`: Ідентифікатор процесу (PID) дочірнього завдання, яке змінило стан.
2. `si_uid`: Реальний ідентифікатор користувача (UID) дочірнього процесу.
3. `si_signo`: Завжди встановлюється у `SIGCHLD`.
4. `si_status`: Містить числовий код виходу (якщо `si_code == CLD_EXITED`) або номер сигналу, який убив чи зупинив процес.
5. `si_code`: Причина зміни стану процесу. Приймає одне зі стандартизованих системних значень:
   * `CLD_EXITED`: Дочірній процес завершився добровільно через `exit()`. Поле `si_status` містить код виходу.
   * `CLD_KILLED`: Дочірній процес вбито неперехопленим сигналом. Поле `si_status` містить номер сигналу.
   * `CLD_DUMPED`: Дочірній процес вбито сигналом зі створенням дампу пам'яті (core dump).
   * `CLD_TRAPPED`: Дочірній процес потрапив під точку зупинки відлагоджувача (trapped by ptrace).
   * `CLD_STOPPED`: Дочірній процес зупинено сигналом Job Control.
   * `CLD_CONTINUED`: Дочірній процес відновлено сигналом `SIGCONT`.

Виклик `waitid()` є набагато прозорішим для розробників системного ПЗ, оскільки він полностью розділяє номер сигналу та код виходу, прибираючи необхідність маскування бітів.

## 3. Зарезервовані коди виходу POSIX та Bash

Командна оболонка POSIX інтерпретує 8-бітні коди завершення у діапазоні `0..255`. Частина цього діапазону зарезервована для службових потреб оболонки та стандартних системних утиліт:

| Код виходу | Значення за POSIX / Bash | Сценарій виникнення та контекст |
| :--- | :--- | :--- |
| `0` | Успішне завершення (`EXIT_SUCCESS`) | Команда виконана без жодної помилки. Оболонка інтерпретує як Успіх (true). |
| `1` | Загальна помилка (`EXIT_FAILURE`) | Загальний збій (неправильні аргументи, відсутність ресурсу, помилка виконання у програмі). |
| `2` | Неправильне використання команд оболонки | Помилка синтаксису built-in команд bash або помилка прав доступу до самого скрипту. |
| `126` | Команду знайдено, але вона не є виконуваною | Файл існує, але відсутні права на виконання (`chmod +x`) або права доступу VFS. |
| `127` | Команду не знайдено | Вказаний бинарник або скрипт відсутній у каталогах змінної оточення `PATH`. |
| `128` | Недійсний аргумент виходу | Некоректний виклик `exit N`, де N не є цілим числом або виходить за межі. |
| `128 + N` | Загибель від сигналу N | Вбито сигналом N (наприклад, `130` = SIGINT, `137` = SIGKILL, `139` = SIGSEGV). |
| `255` | Код виходу поза діапазоном | Виникає при спробі виконати `exit -1` або `exit 255`. |

## 4. Повна специфікація стандартних кодів `<sysexits.h>`

Специфікація BSD розробила заголовочний файл `<sysexits.h>`, який став стандартом для мережевих демонів, поштових серверів (Sendmail, Postfix), утиліт OpenSSH та системних CLI-інструментів у Unix та Linux. Ці коди займають діапазон `64..78` і запобігають перетину з сигналами оболонки:

### `EX_OK` (Код 0)
Успішне завершення програми. Символізує повне виконання задачі без відхилень.

### `EX_USAGE` (Код 64)
Користувач припустився помилки у синтаксисі командного рядка: передано невідомий прапорець, відсутні обов'язкові аргументи або порушено формат виклику.

### `EX_DATAERR` (Код 65)
Вхідні дані мають неправильний формат. Використовується, коли сам файл існує і прочитаний, але його вміст не відповідає граматиці або специфікації (наприклад, пошкоджений JSON чи синтаксична помилка конфігурації).

### `EX_NOINPUT` (Код 66)
Вхідний файл відсутній або недоступний для читання. Застосовується, коли програма не може відкрити вказаний користувачем шлях.

### `EX_NOUSER` (Код 67)
Зазначений користувач або обліковий запис не існує в системі. Зазвичай повертається поштовими серверами або демонами авторизації SSH.

### `EX_NOHOST` (Код 68)
Зазначений мережевий вузол (host) недоступний або його ім'я не вдалося розпізнати через підсистему DNS.

### `EX_UNAVAILABLE` (Код 69)
Необхідна служба, сервіс або зовнішнє середовище недоступні у системі.

### `EX_SOFTWARE` (Код 70)
Внутрішній програмний збій. Повертається при виявленні непоправної логічної помилки у самому коді програми (наприклад, порушення внутрішнього інваріанту).

### `EX_OSERR` (Код 71)
Системна помилка операційної системи. Виникає при відмові системних викликів ядра (неможливість роздвоєння `fork`, вичерпання ліміту файлових дескрипторів FD або PIDs).

### `EX_OSFILE` (Код 72)
Критичний системний файл відсутній або пошкоджений. На відміну від `EX_NOINPUT`, стосується системних файлів (наприклад, `/etc/passwd` або `/etc/hosts`).

### `EX_CANTCREAT` (Код 73)
Неможливо створити вихідний файл. Виникає при відсутності прав на запис у каталог або при повному заповненні дискового простору.

### `EX_IOERR` (Код 74)
Апаратна або фізична помилка введення-виведення (I/O error) при роботі з диском, файловою системою чи мережевим пристроєм.

### `EX_TEMPFAIL` (Код 75)
Тимчасовий збій ресурсу. Повідомляє клієнту або оркестратору, що збій має тимчасовий характер і повторна спроба виконання (retry) через деякий час може бути успішною.

### `EX_PROTOCOL` (Код 76)
Помилка мережевого або міжпроцесного протоколу (некоректний handshake, відсутній відповідний заголовок або несумісна версія протоколу).

### `EX_NOPERM` (Код 77)
Відсутність потрібних прав доступу або привілеїв суперкористувача Root (`EPERM` / `EACCES`).

### `EX_CONFIG` (Код 78)
Помилка у конфігураційних файлах підсистеми або невірна конфігурація середовища виконання.

## 5. Витяг статусу завершення з C та C++

Наведений нижче код показує стандартний спосіб розбору `wstatus` мовою C та її ідіоматичний еквівалент у C++ з використанням типів `std::variant`, строгих структурованих зв'язувань та безпечного розпакування:

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <sysexits.h>
#include <unistd.h>

void analyze_process_status(int wstatus) {
    if (WIFEXITED(wstatus)) {
        int code = WEXITSTATUS(wstatus);
        printf("[C] Процес завершився нормально. Код виходу: %d\n", code);
        switch (code) {
            case EX_OK:
                printf("  Результат: Успіх (EX_OK).\n");
                break;
            case EX_USAGE:
                printf("  Причина: Некоректні параметри командного рядка (EX_USAGE).\n");
                break;
            case EX_NOINPUT:
                printf("  Причина: Вхідний файл відсутній або недоступний (EX_NOINPUT).\n");
                break;
            case EX_UNAVAILABLE:
                printf("  Причина: Необхідний сервіс недоступний (EX_UNAVAILABLE).\n");
                break;
            default:
                printf("  Причина: Специфічний код програми (%d).\n", code);
                break;
        }
    } else if (WIFSIGNALED(wstatus)) {
        int sig = WTERMSIG(wstatus);
        printf("[C] Процес вбито сигналом: %d\n", sig);
        if (WCOREDUMP(wstatus)) {
            printf("  Увага: Ядро згенерувало образ пам'яті (core dump).\n");
        }
        printf("  Еквівалентний код для оболонки ($?): %d\n", 128 + sig);
    } else if (WIFSTOPPED(wstatus)) {
        printf("[C] Процес зупинено сигналом Job Control: %d\n", WSTOPSIG(wstatus));
    }
}
```
```cpp
#include <iostream>
#include <variant>
#include <string_view>
#include <sys/wait.h>
#include <sysexits.h>

struct NormalExit {
    int code;
};

struct SignalExit {
    int signal_number;
    bool core_dumped;
};

struct StoppedExit {
    int stop_signal;
};

using ExitResult = std::variant<NormalExit, SignalExit, StoppedExit>;

class StatusDecoder {
public:
    static ExitResult parse(int wstatus) {
        if (WIFEXITED(wstatus)) {
            return NormalExit{WEXITSTATUS(wstatus)};
        }
        if (WIFSIGNALED(wstatus)) {
            return SignalExit{
                WTERMSIG(wstatus), 
                static_cast<bool>(WCOREDUMP(wstatus))
            };
        }
        return StoppedExit{WSTOPSIG(wstatus)};
    }

    static void print(const ExitResult& result) {
        std::visit([](auto&& res) {
            using T = std::decay_t<decltype(res)>;
            if constexpr (std::is_same_v<T, NormalExit>) {
                std::cout << "[C++] Нормальне завершення з кодом: " << res.code << "\n";
                if (res.code == EX_USAGE) {
                    std::cout << "  Деталі: Некоректний синтаксис (EX_USAGE)\n";
                } else if (res.code == EX_CONFIG) {
                    std::cout << "  Деталі: Помилка конфігурації (EX_CONFIG)\n";
                }
            } else if constexpr (std::is_same_v<T, SignalExit>) {
                std::cout << "[C++] Вбито сигналом " << res.signal_number 
                          << " (код оболонки: " << (128 + res.signal_number) << ")\n";
                if (res.core_dumped) {
                    std::cout << "  Деталі: Дамп пам'яті (core dump) записано.\n";
                }
            } else if constexpr (std::is_same_v<T, StoppedExit>) {
                std::cout << "[C++] Процес зупинено сигналом: " << res.stop_signal << "\n";
            }
        }, result);
    }
};
```

## 6. Діагностичні інтерфейси procfs та підсистеми ядра

Операційна система Linux надає декілька вікон для контролю статусів завершення процесів без прямого виклику `waitpid`:

1. **/proc/[pid]/stat**: 52-ге поле файлу містить код виходу процесу `exit_code`, записаний після його смерті (у стані Zombie).
2. **/proc/sys/kernel/core_pattern**: Визначає шаблон шляху та ім'я генератора core dump при загибелі процесів від сигналів (наприклад, SIGSEGV чи SIGABRT).
3. **Точки трасування `tracepoint:sched:sched_process_exit`**: Дозволяють інструментам eBPF (BCC, bpftrace) та `ftrace` перехоплювати точний код завершення та PID процесу в момент виконання системного виклику ядра `do_exit()`.
