# 📜 Історія та еволюція статусу завершення в Unix

Історичний процес формування 8-бітного коду виходу, поява конвенції `128+N` та еволюція правил обробки конвеєрів від V6 Unix до POSIX.1 пояснюють походження сучасних обмежень оболонки.

Технічні обмеження апаратури PDP-11 у 1970-х роках сформували фундаментальні архітектурні рішення, якими ми користуємося у сучасних операційних системах Linux та macOS.

---

## 1. Апаратні обмеження PDP-11 та 6th Edition Unix (1975)

У перших версіях операційної системи AT&T Unix, розроблених Кеном Томпсоном (Ken Thompson) та Деннісом Рітчі (Dennis Ritchie) для 16-бітного мінікомп'ютера PDP-11, розмір машинного слова становив 16 бітів. Системний виклик `sys exit` приймав ціле значення у регістрі `r0`.

Проте у Sixth Edition Unix (V6, 1975 рік) перед архітекторами операційної системи постала гостра проблема міжпроцесної комунікації. Коли дочірній процес завершувався, батьківському процесу треба було одночасно дізнатися дві кардинально відмінні речі:
1. Чи завершився процес добровільно, і яке числове значення він повернув через функцію `exit(status)`?
2. Чи був процес примусово анульований через апаратний збій, апаратну трапу (trap) або зовнішній сигнал (signal)?

Оскільки оперативно-запам'ятовувальний пристрій (ОЗП) комп'ютерів PDP-11 обмежувався 64 кілобайтами для всього простору користувача, створення повноцінного об'єкта структури або передача повідомлення через оперативну пам'ять при кожному завершенні процесу вважалися неприпустимо дорогою розкішшю.

Розробники Unix знайшли компромісне рішення: вони спакували обидві причини смерті процесу в єдине 16-бітне ціле число статусу `wstatus`:

```text
+------------------------+---+-----------------------+
|  Exit Code (0..255)    | C | Signal Number (0..127)|
+------------------------+---+-----------------------+
 15                    8   7  6                     0
```

Молодші 7 бітів віддавалися під номер сигналу ядра, 7-й біт (`0x80`) позначав створення дампу пам'яті (Core Dump), а старші 8 бітів (`8..15`) зберігали код завершення, переданий у виклик `exit(code)`.

Саме це апаратне рішення 1975 року назавжди зафіксувало розмірність власного коду виходу програм рівною **8 бітам** (максимальне значення `255`). Усі наступні операційні системи (BSD, System V, Linux, macOS) зберегли цей 8-бітний діапазон заради бінарної сумісності.

## 2. Bourne Shell та поява конвенції 128 + N (1979)

У Seventh Edition Unix (V7, 1979 рік) Стів Борн (Stephen Bourne) випустив нову командну оболонку Bourne shell (`/bin/sh`), яка прийшла на зміну первинній оболонці Томпсона.

Борн зіштовхнувся з логічною суперечністю при розробці мови скриптів оболонки:
* З одного боку, у командній мові стан завершення останньої виконаної програми зберігався в єдиній змінній оболонки `$?`.
* З іншого боку, усі керуючі конструкції розгалуження (`if cmd; then ...`, `while cmd; do ...`) та логічні зв'язки (`&&`, `||`) мали оцінювати `$?` як єдине числове значення, де `0` позначав істину (успіх), а будь-яке ненульове значення — хибність (помилку).

Якщо процес завершувався нормально через `exit(1)`, оболонка записувала у змінну `$? = 1`. Проте якщо процес був примусово вбитий неперехопленим сигналом ядра `SIGINT` (Ctrl+C, номер 2), системний виклик `wait()` повертав номер сигналу 2, а власний код виходу `WEXITSTATUS` був відсутній.

Для того щоб об'єднати два різні простори значень (нормальні коди виходу програм `0..127` та сигнали ядра) в єдиній змінній `$?`, Стів Борн запропонував витончене правило зсуву:

```text
Якщо процес загинув від сигналу N, оболонка записує у змінну $? значення: 128 + N
```

Вибір базового масиву `128` (встановлений 8-й біт) був зумовлений тим, що утиліти Unix традиційно повертали власні коди помилок у діапазоні від `0` до `127`. Діапазон `128..255` був повністю відданий для індикації того, що процес був знищений сигналом ядра.

Це правило швидко стало універсальною конвенцією для всіх оболонкових інтерпретаторів Unix.

## 3. Стандартизація POSIX.1 та поява BSD sysexits.h (1988)

Наприкінці 1980-х років фрагментація Unix-систем (війна між AT&T System V та BSD) призвела до необхідності створення єдиного стандарту. У 1988 році був випущений стандарт POSIX.1 (IEEE Std 1003.1), який закріпив 8-бітний код виходу, макроси `WIFEXITED`, `WEXITSTATUS`, `WTERMSIG` та мапування `128+N` як юридичну норму.

Одночасно у лабораторіях Університету Каліфорнії у Берклі (UC Berkeley) Ерік Оллман (Eric Allman) при розробці поштового сервера Sendmail зіштовхнувся з відсутністю стандартизації кодів виходу для мережевих сервісів. Якщо поштовий демон повертав випадкове число при відмові доставки листу, поштовий клієнт не міг зрозуміти: це тимчасовий збій мережі (потрібно зробити retry пізніше) чи неіснуюча адреса скриньки (потрібно відправити bounce).

Для вирішення цієї проблеми Оллман розробив заголовочний файл `<sysexits.h>`, який зафіксував 15 системних кодів у діапазоні `64..78`. Цей заголовок увійшов до складу 4.3BSD, а згодом став стандартом де-факто для всього системного ПЗ у Linux.

## 4. Проблема конвеєрів та поява pipefail у ksh93 та Bash (1990–2004)

Первинний стандарт POSIX.1 зафіксував правило обчислення коду виходу для вертикального конвеєра процесів:

```bash
cmd1 | cmd2 | cmd3
```

Згідно з POSIX, кодом виходу всього конвеєра завжди вважається **статус завершення останньої команди** (`cmd3`).

Протягом 1990-х років із розширенням використання Unix у фінансових та корпоративних системах з'ясувалося, що це правило створює небезпечну прогалину в безпеці та надійності скриптів. Помилки перших елементів ланцюга (наприклад, збій резервного копіювання `tar` чи `gzip`) повністю маскувалися успішним завершенням фінальної утиліти фільтрації (`head` чи `wc`).

Для усунення цього недоліку Девід Корн (David Korn) у командній оболонці KornShell (ksh93g, 1998 рік) розробив опцію `set -o pipefail`. У 2004 році ця опція була адаптована у Bash 3.0 разом із масивом `${PIPESTATUS[@]}`.

Еволюція статусів виходу пройшла шлях від 16-бітного регістра PDP-11 до сучасної багаторівневої підсистеми, яка поєднує низькорівневі макроси ядра, конвенцію `128+N` та гнучкий контроль конвеєрів у сучасних командних оболонках.
