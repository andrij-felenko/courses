## 1. Вступ: Контекст народження процесу

Кожного разу, коли ви запускаєте команду в терміналі Linux, відбувається складна послідовність подій, що забезпечує передачу даних від вашої оболонки до програми, яка починає виконуватися. Цей механізм є фундаментальним для філософії Unix: програми мають бути невеликими, виконувати одну функцію добре, і їхня поведінка повинна гнучко налаштовуватися через аргументи командного рядка та змінні середовища. 

Але як саме ці дані потрапляють до вашої функції `main(int argc, char *argv[])`? Як ядро операційної системи передає інформацію, таку як розташування динамічного лінкера або апаратні можливості процесора, новоствореному процесу? У цьому розділі ми здійснимо глибоке занурення в анатомію адресного простору процесу на самому початку його життя. Ми дослідимо системний виклик `execve()`, структуру стека під час запуску, масиви `argv` та `environ`, а також менш відомий, але критично важливий допоміжний вектор `auxv`.

## 2. Системний виклик execve(): Точка відліку

У світі Unix створення процесу і запуск програми — це дві окремі дії, які виконуються системними викликами `fork()` (або `clone()` у Linux) та `execve()`. Виклик `fork()` створює точну копію поточного процесу. Але щоб запустити іншу програму, поточний процес повинен бути "перезаписаний" новою програмою. Це завдання виконує `execve()`.

Сигнатура `execve()` виглядає так:
```c
int execve(const char *pathname, char *const argv[], char *const envp[]);
```

Коли оболонка (наприклад, `bash`) збирається запустити команду `ls -l /tmp`, вона викликає `fork()`, а потім дитячий процес викликає `execve()` з такими параметрами:
- `pathname`: Шлях до виконуваного файлу (наприклад, `"/bin/ls"`).
- `argv`: Масив рядків, що представляють аргументи (наприклад, `["ls", "-l", "/tmp", NULL]`).
- `envp`: Масив рядків середовища (наприклад, `["PATH=/bin:/usr/bin", "USER=john", ..., NULL]`).

Ядро Linux отримує цей системний виклик і починає складний процес заміни поточного образу пам'яті новим. Спочатку ядро перевіряє права доступу до файлу, а потім намагається розпізнати формат виконуваного файлу (зазвичай це формат ELF — Executable and Linkable Format, або скрипт, що починається з `#!`).

Якщо файл є коректним ELF-файлом, ядро очищує старий адресний простір дитячого процесу, налаштовує нову таблицю сторінок і завантажує сегменти ELF-файлу в пам'ять (код, дані, bss). Після цього настає критичний етап: ядро повинно розмістити масиви `argv` та `envp` в адресний простір нового процесу, щоб програма могла їх прочитати. 

Ядро розміщує цю інформацію не деінде, а на самому верху стека користувача.

## 3. Анатомія стека на старті процесу

Коли ядро передає керування програмі користувача (тобто переходить у просторі користувача до адреси входу, зазвичай до `_start`), стек знаходиться у специфічному стані. Дані на стеку розташовані в строго визначеному порядку. Архітектури можуть мати незначні відмінності у вирівнюванні, але для найпоширенішої архітектури x86_64 стандарт System V ABI визначає такий макет стека (починаючи від вищих адрес і спускаючись до нижчих, оскільки стек росте вниз):

```text
[Високі адреси]
---------------------------------------------------------
| Інформаційні блоки (Information Block)                  |
| Тут фізично зберігаються самі рядки (символи)           |
| - Рядки середовища (наприклад, "USER=john\0")           |
| - Рядки аргументів (наприклад, "ls\0", "-l\0")          |
| - Ім'я програми (з execve)                              |
| - Padding для вирівнювання (зазвичай до 16 байт)        |
---------------------------------------------------------
| Допоміжний вектор (Auxiliary Vector, auxv)              |
| - Elf64_auxv_t масив, закінчується AT_NULL              |
---------------------------------------------------------
| Масив покажчиків середовища (envp)                      |
| - char *envp[0]                                         |
| - ...                                                   |
| - NULL (0x0000000000000000)                             |
---------------------------------------------------------
| Масив покажчиків аргументів (argv)                      |
| - char *argv[0]                                         |
| - ...                                                   |
| - char *argv[argc-1]                                    |
| - NULL (0x0000000000000000)                             |
---------------------------------------------------------
| Кількість аргументів (argc)                             |
| - 8 байт на x86_64, містить ціле число                  |
---------------------------------------------------------  <--- Вказівник стека (%rsp) на старті
[Низькі адреси]
```

Цей блок пам'яті формується безпосередньо кодом ядра Linux (`fs/binfmt_elf.c` та `fs/exec.c`). Процес копіювання відбувається так: ядро копіює рядки з простору батьківського процесу (які були передані в `execve`) у спеціальні сторінки пам'яті ядра, потім відображає ці сторінки на вершині стека нового процесу і, нарешті, будує масиви покажчиків, які вказують на ці рядки.

## 4. Аргументи командного рядка: argv та argc

На самому дні цієї структури (за адресою, на яку вказує регістр покажчика стека `%rsp` під час старту) лежить `argc` — кількість аргументів. Одразу над `argc` розташований масив покажчиків `argv`. Цей масив закінчується NULL-покажчиком, що є обов'язковою вимогою POSIX. Це дозволяє перебирати масив двома способами: за допомогою `argc` або ітеруючи до зустрічі з `NULL`.

Кожен елемент `argv` — це адреса в пам'яті, де лежить конкретний рядок. Рядки зберігаються вище у стеку (в Інформаційному блоці). Варто звернути увагу, що ці рядки йдуть підряд у пам'яті. 

Стандарт C вимагає, щоб `argv[argc]` був `NULL`. Крім того, традиційно `argv[0]` містить ім'я програми, як воно було викликане. Важливо розуміти, що це ім'я не обов'язково відповідає справжньому імені виконуваного файлу на диску. Якщо ви створите символічне посилання на програму, `argv[0]` зазвичай міститиме ім'я посилання. Більше того, батьківський процес, який викликає `execve()`, може передати абсолютно будь-який рядок як `argv[0]`.

## 5. Середовище: environ

Одразу після NULL-покажчика, що завершує масив `argv`, починається масив `envp` (середовище). У стандарті C глобальна змінна `extern char **environ;` є стандартним способом доступу до цього масиву в POSIX-системах (хоча функція `main()` також може приймати третій аргумент: `int main(int argc, char *argv[], char *envp[])`).

Масив середовища концептуально дуже схожий на `argv`: це також масив покажчиків на рядки, який завершується `NULL`. Рядки середовища мають формат `KEY=VALUE`.

Змінні середовища є критичним механізмом передачі контексту. Вони використовуються для:
- Налаштування поведінки стандартних бібліотек (наприклад, `LD_LIBRARY_PATH` для динамічного лінкера, `LANG` і `LC_ALL` для локалізації).
- Передачі автентифікаційних даних або конфігураційних шляхів програмам користувача (наприклад, `HOME`, `USER`).

Ядро лише копіює ці рядки; воно не розуміє формату `KEY=VALUE` і не надає API для їх пошуку — це завдання реалізується в просторі користувача бібліотекою C (наприклад, функцією `getenv()`). Бібліотека glibc просто перебирає масив `environ`, шукаючи рядок, що починається з потрібного ключа.

## 6. Допоміжний вектор (auxv)

Після масиву `envp` лежить, мабуть, найцікавіша частина — Auxiliary Vector, або допоміжний вектор. На відміну від `argv` та `envp`, це не масив покажчиків на рядки, а масив структур. На 64-бітних системах він складається з пар 8-байтових значень:

```c
typedef struct {
    uint64_t a_type;              /* Тип запису */
    union {
        uint64_t a_val;           /* Цілочисельне значення */
        void *a_ptr;              /* Або покажчик */
    } a_un;
} Elf64_auxv_t;
```

Масив `auxv` завершується елементом, тип якого дорівнює `AT_NULL` (0). 

Навіщо потрібен допоміжний вектор? Коли ядро завантажує ELF-файл, воно дізнається багато речей про програму та апаратне забезпечення. Програмі в просторі користувача, особливо динамічному лінкеру (наприклад, `ld-linux.so`), ця інформація вкрай необхідна для правильної ініціалізації процесу. Щоб не примушувати лінкер робити зайві системні виклики (що повільно), ядро просто кладе ці дані прямо в стек.

Деякі важливі типи (типи `AT_*` визначені в `<elf.h>`):
- `AT_PHDR` (3): Адреса таблиці програмних заголовків ELF (Program Headers). Лінкер використовує це для розуміння структури завантаженої програми.
- `AT_PHENT` (4): Розмір одного програмного заголовка.
- `AT_PHNUM` (5): Кількість програмних заголовків.
- `AT_PAGESZ` (6): Розмір сторінки системи (зазвичай 4096 байт). Завдяки цьому libc не має викликати `sys_getpagesize()`.
- `AT_BASE` (7): Базова адреса, за якою ядро завантажило інтерпретатор програми (динамічний лінкер).
- `AT_FLAGS` (8): Флаги (поки що не використовуються широко).
- `AT_ENTRY` (9): Точка входу в саму програму. Це критично: коли ядро завантажує динамічно скомпоновану програму, воно передає керування динамічному лінкеру (його адреса стає адресою старту). Лінкер налаштовує бібліотеки, а потім має стрибнути до коду користувача. Він дізнається, де знаходиться код користувача, саме з `AT_ENTRY`.
- `AT_UID` (11), `AT_EUID` (12), `AT_GID` (13), `AT_EGID` (14): Реальні та ефективні ідентифікатори користувача/групи. Дозволяє libc відразу знати права доступу.
- `AT_HWCAP` (16): Бітова маска можливостей процесора (наприклад, підтримка AVX2, SSE4). Glibc перевіряє це поле для вибору оптимізованих версій функцій, як-от `memcpy()` або `strlen()`.
- `AT_SECURE` (23): Дорівнює 1, якщо програма запущена в безпечному режимі (наприклад, через setuid або setgid). Якщо це 1, динамічний лінкер ігнорує змінні на кшталт `LD_PRELOAD` з міркувань безпеки.
- `AT_RANDOM` (25): Покажчик на 16 випадкових байтів, які ядро надає програмі. Використовується, зокрема, для генерації "canary" (захист від переповнення буфера) та ініціалізації генератора випадкових чисел.

Переглянути auxv будь-якого процесу можна командою:
```bash
LD_SHOW_AUXV=1 /bin/true
```
Або прочитавши `/proc/[pid]/auxv` за допомогою `hexdump` або `od`.

## 7. Від ядра до main(): Довга дорога C Runtime (CRT)

Як регістр стека та всі ці дані перетворюються на виклик `main(argc, argv)`?

Точкою входу ELF-файлу зазвичай є символ `_start`, який створюється не вашим компілятором, а додається компонувальником (і береться з файлів, таких як `crt1.o`, що постачаються з glibc).
Код `_start` написаний мовою асемблера, оскільки він повинен безпосередньо читати зі стека в тому стані, в якому його залишило ядро.

У типовому `_start` на x86_64 відбувається наступне:
1. Виймає зі стека `argc` у регістр `%rdi` (перший аргумент для функції).
2. Обчислює адресу `argv` (поточний `%rsp`) і кладе її в `%rsi` (другий аргумент).
3. Вирівнює стек по межі 16 байт, що є вимогою System V ABI (інакше інструкції SSE можуть викликати помилку сегментації).
4. Викликає функцію `__libc_start_main()`.

`__libc_start_main` виконує всю складну ініціалізацію:
- Знаходить `envp` та `auxv`. Зберігає глобальні покажчики, такі як `environ` та `__environ`.
- Використовує `auxv` (`AT_HWCAP` тощо) для налаштування системи (особливо IFUNC — вибір функцій на основі можливостей CPU).
- Ініціалізує захист стека (stack canary).
- Викликає функції ініціалізації (конструктори, секція `.init` або масив `.init_array`, такі як глобальні об'єкти в C++).
- Нарешті викликає вашу функцію `main(argc, argv, envp)`.
- Отримує код повернення з `main` і передає його у `exit()`, який, у свою чергу, викликає деструктори (з `.fini_array`) і робить системний виклик `exit_group()`.

## 8. Модифікація та ліміти: ARG_MAX і зміна імені процесу

### Перезапис імені процесу (ps)

Цікавий побічний ефект того, як організовані ці дані: інструменти на кшталт `ps` або `top` читають ім'я процесу та аргументи, заглядаючи в файл `/proc/[pid]/cmdline`. Це ядро формує з пам'яті процесу, безпосередньо зчитуючи рядки в Інформаційному блоці, на які вказує `argv`.

Якщо програма змінить вміст рядка, на який вказує `argv[0]`, команда `ps` покаже нове ім'я процесу! Це техніка, яку часто використовують сервери (наприклад, PostgreSQL або Nginx), щоб показати свій поточний стан: `nginx: worker process`.

Але оскільки рядки лежать підряд, якщо нове ім'я довше за старе, ви можете перезаписати наступні аргументи або змінні середовища! Тому правильний спосіб зміни імені процесу — це або використовувати `prctl(PR_SET_NAME, ...)` (змінює ім'я потоку, обмежене 15 символами), або ретельно скопіювати весь `environ` в нову пам'ять, а потім безпечно перезаписати весь інформаційний блок.

### Ліміти: ARG_MAX

Існує обмеження на загальний обсяг даних, які можна передати через `execve()`. Цей ліміт стосується суми довжин усіх рядків в `argv` та `envp` разом з покажчиками. Традиційно цей ліміт називався `ARG_MAX` і становив 128 КБ або 2 МБ.

Якщо ви коли-небудь намагалися виконати `rm *` у директорії з сотнями тисяч файлів, ви, ймовірно, бачили помилку оболонки:
```text
bash: /bin/rm: Argument list too long
```
Це означає, що системний виклик `execve` повернув помилку `E2BIG`.

У сучасних ядрах Linux ліміт набагато вищий (як правило, чверть розміру стека процесу, що зазвичай дорівнює 2 МБ, тобто розмір стека 8 МБ / 4), що робить такі помилки менш поширеними, але вони все ще можливі. Проблема вирішується за допомогою утиліт типу `find ... -exec` або `xargs`.

## 9. Висновок

Процес старту програми в Unix і Linux — це елегантний і перевірений часом механізм. Те, що для програміста виглядає як прості параметри `main`, насправді є результатом ретельно організованої співпраці між ядром ОС, динамічним лінкером та середовищем виконання C. Розуміння структури стека на старті, ролі `auxv` та управління середовищем дозволяє краще розуміти життєвий цикл процесів і глибше інтегруватися з операційною системою.
