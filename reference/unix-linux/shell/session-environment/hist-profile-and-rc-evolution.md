# 📜 Історія та еволюція конфігураційних файлів сеансу

Конфігураційні файли командної оболонки Unix (такі як `.profile`, `.bashrc` чи `.zshrc`) сьогодні сприймаються як даність. Проте їхнє розділення на «профілі сеансу» (login profile) та «файли конфігурації екземпляра» (runtime configuration / rc) не було закладено у початкову архітектуру системи. Воно сформувалося внаслідок еволюції багатьох процесів, появі інтерактивних терміналів та виникненню концепції розмежування сесій користувача від виконання окремих програм.

## Перші дні Unix: Bourne Shell та єдиний ~/.profile

У перших версіях Unix (від V1 до V6) оболонка `sh` під авторством Кена Томпсона (Ken Thompson) була надзвичайно простою. Вона не мала вбудованих мовних засобів програмування і не читала жодних конфігураційних файлів при запускі: середовище формувалося виключно системним процесом `init` та програмою `login`.

Ситуація докорінно змінилася у 1979 році з виходом Seventh Edition Unix (V7), у якій Стів Борн (Stephen Bourne) презентував нову командну оболонку Bourne shell (`/bin/sh`). Борн запровадив концепцію сценарію ініціалізації сеансу:
1. Системний файл `/etc/profile`, який налаштовував глобальні змінні (такі як `PATH`, `PS1`, `MAIL`) для всіх користувачів машини.
2. Персональний файл `~/.profile` у домашньому каталозі користувача, який виконувався одразу після успішної автентифікації в системі.

На цьому етапі модель була монолітною. Unix-системи 1970-х років працювали за схемою «один термінал — один сеанс». Користувач підключався через послідовний порт (teletype / TTY), вводив логін і пароль, після чого програма `login` запускала один екземпляр `/bin/sh`. Цей єдиний процес зчитував `/etc/profile` та `~/.profile`, виставляв змінні середовища та очікував на команди. Будь-які додаткові скрипти виконувалися як дочірні процеси без створення нових інтерактивних оболонок.

## Поява C-Shell та розколення на profile і rc

У 1978 році у Берклі Білл Джой (Bill Joy) створив C Shell (`csh`) для BSD Unix. Джой прагнув зробити оболонку зручною для щоденної інтерактивної роботи, додавши історію команд, автодоповнення та псевдоніми (aliases).

Проте виникла архітектурна проблема: псевдоніми та внутрішні налаштування оболонки (наприклад, `set history = 100`) не зберігалися у масиві змінних середовища `envp` ядра OS і не передавалися дочірнім процесам при системному виклику `execve()`. Якщо користувач запускав скрипт або під-оболонку, всі інтерактивні псевдоніми зникали.

Щоб вирішити цю проблему, Білл Джой розділив ініціалізацію на дві фази та створив два файли:
- `~/.login` — виконувався **один раз** під час входу користувача у систему. Тут встановлювалися глобальні змінні середовища (`setenv PATH ...`, `setenv TERM ...`) та важкі команди виводу (вітання, перевірка пошти, статус системи).
- `~/.cshrc` — виконувався **при кожному запускі** нового екземпляра `csh` (будь то інтерактивний термінал або неінтерактивний сценарій). Тут визначалися псевдоніми (`alias`), інтерактивні функції та змінні самої оболонки.

Абревіатура **rc** походить від історичної конвенції *runcom* (run commands), що з'явилася ще в операційній системі CTSS (Compatible Time-Sharing System) у 1965 році в MIT, де файли з інструкціями для запуску програм називалися `runcom`.

## Поява KornShell та стандартизація в Bash

У 1983 році Девід Корн (David Korn) випустив KornShell (`ksh`), яка поєднала синтаксичну сумісність із Bourne shell та зручність C Shell. Корн вирішив проблему неінтерактивних запусків за допомогою спеціальної змінної середовища `ENV`. Якщо `ENV` містила шлях до файла (наприклад, `ENV=$HOME/.kshrc`), оболонка виконувала його при кожному інтерактивному старті.

Коли у 1989 році Брайан Фокс (Brian Fox) в межах проекту GNU створив Bash (Bourne-Again Shell), перед ним постало завдання зберегти сумісність із двома світами:
1. Сумісність із класичним POSIX Bourne shell (`/etc/profile` та `~/.profile`).
2. Підтримка зручної роздільної моделі `rc`-файлів для інтерактивних сеансів (`~/.bashrc`).

Фокс сформував правила завантаження Bash, які діють і сьогодні:
- Для **Login Shell** читаються `/etc/profile`, а потім перший знайдений з `~/.bash_profile`, `~/.bash_login` чи `~/.profile`.
- Для **Interactive Non-Login Shell** (наприклад, новий віконний термінал у X11 чи GUI) читається `/etc/bash.bashrc` та `~/.bashrc`.

## Еволюція в Zsh та сучасних розподілах

З появою Zsh (Paul Falstad, 1990) граф конфігурації став ще гнучкішим і отримав чітку ієрархію з п'яти файлів:
1. `.zshenv` — виконується завжди (навіть для неінтерактивних скриптів).
2. `.zprofile` — виконується для login shells до `.zshrc`.
3. `.zshrc` — виконується для інтерактивних оболонок.
4. `.zlogin` — виконується для login shells після `.zshrc`.
5. `.zlogout` — виконується при виході з login shell.

Сучасні графічні оточення (GNOME, KDE, macOS Terminal) додатково ускладнили цю картину. Наприклад, macOS Terminal за замовчуванням відкриває кожне нове вікно як login shell, що змушує дублювати сорсинг `~/.bashrc` у `~/.bash_profile`. Розуміння цієї історичної траєкторії дає можливість чітко проектувати конфігурацію: змінні середовища належать профілю сеансу, а псевдоніми та налаштування інтерактивності — rc-файлу.
