# Успадкування й експорт змінних: export, успадкування процесів і залишкові змінні

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У світі операційних систем сімейства Unix та Linux середовище (environment) процесу є одним із найважливіших механізмів передачі конфігурації, стану та метаданих між програмами. Командна оболонка (shell) діє як головний інтерфейс користувача для управління цим середовищем. Розуміння того, як змінні створюються, як вони експортуються, та яким чином вони передаються від батьківського процесу до дочірнього через системні виклики `fork()` та `exec()`, є критично важливим для будь-якого системного адміністратора, розробника чи power user'а. У цій статті ми глибоко зануримося у внутрішню архітектуру управління змінними в оболонці bash (та інших POSIX-сумісних оболонках), дослідимо механізми успадкування на рівні ядра, навчимося інспектувати середовище живих процесів через `/proc/PID/environ`, а також розберемо проблему "залишкових" (residual) змінних.

## 1. Локальні змінні оболонки проти змінних середовища (Environment Variables)

Коли ви працюєте в оболонці (наприклад, Bash, Zsh, Dash), ви можете створювати змінні для зберігання рядкових даних. Проте не всі змінні є рівнозначними. Оболонка поділяє всі змінні на дві основні категорії: **локальні змінні оболонки (shell variables)** та **змінні середовища (environment variables)**.

### 1.1. Локальні змінні оболонки

Локальна змінна існує виключно в пам'яті поточного процесу оболонки. Вона доступна для використання у скриптах, циклах чи умовному виконанні в межах цієї ж сесії, але вона **абсолютно невидима** для будь-яких зовнішніх команд або дочірніх процесів, які запускає ця оболонка.

Створення локальної змінної відбувається за допомогою простого присвоєння (без пробілів навколо знака дорівнює):

```bash
# Створюємо локальну змінну
MY_LOCAL_VAR="Hello, local world"

# Вона доступна для внутрішньої команди echo (яка є shell builtin)
echo $MY_LOCAL_VAR
```

Якщо ми тепер спробуємо запустити новий дочірній процес — наприклад, новий екземпляр `bash` або скрипт на Python — ця змінна не буде передана:

```bash
bash -c 'echo "Inside child: $MY_LOCAL_VAR"'
# Вивід буде: Inside child: 
```

Дочірній процес нічого не знає про `MY_LOCAL_VAR`, оскільки оболонка не помістила її в блок середовища, що передається системному виклику при створенні нового процесу.

### 1.2. Змінні середовища (Exported Variables)

Змінні середовища — це змінні, які були спеціально позначені для передачі дочірнім процесам. В оболонці процес такого позначення називається **експортуванням** (exporting). Коли ви експортуєте змінну, оболонка гарантує, що при запуску будь-якої зовнішньої програми ця змінна буде включена до масиву `envp`, який ядро передає новій програмі.

Використовується команда `export`:

```bash
# Створюємо і експортуємо змінну одночасно
export MY_ENV_VAR="Hello, global world"

# Або експортуємо раніше створену локальну змінну
ANOTHER_VAR="This was local"
export ANOTHER_VAR
```

Тепер, якщо ми запустимо дочірній процес, він отримає копію цих змінних:

```bash
bash -c 'echo "Inside child: $MY_ENV_VAR"'
# Вивід: Inside child: Hello, global world
```


*Рис. 1. Локальні змінні залишаються у батьківському процесі, тоді як експортовані копіюються в середовище дочірнього процесу під час fork/exec.*

### 1.3. Одноразовий експорт (Per-Command Environment)

Часто виникає потреба передати змінну середовища лише одній конкретній програмі, не забруднюючи глобальне середовище поточної оболонки. POSIX-оболонки підтримують синтаксис префіксного присвоєння:

```bash
# Змінна TZ (Time Zone) встановлюється лише для команди date
TZ='Asia/Tokyo' date

# В поточній оболонці TZ залишається незмінною або порожньою
echo $TZ
```

Це дуже зручний і безпечний патерн, який варто використовувати при запуску скриптів, що вимагають специфічної конфігурації (наприклад, `LD_LIBRARY_PATH=/opt/mylib ./myprog`).

## 2. Механізм успадкування процесів: fork() та exec()

Щоб по-справжньому зрозуміти, чому `export` працює саме так, необхідно зазирнути на рівень ядра операційної системи та розглянути два ключових системних виклики (syscalls), які відповідають за запуск програм в Linux/Unix: `fork()` та `execve()`.

### 2.1. Системний виклик fork()

Коли оболонка хоче запустити нову команду (наприклад, `ls`), вона спочатку робить копію самої себе за допомогою системного виклику `fork()` (або його сучасних оптимізованих варіантів типу `clone()` в Linux чи `vfork()`). 

Після `fork()` ми маємо два ідентичних процеси:
1. **Батьківський процес (Parent)** — оригінальна оболонка.
2. **Дочірній процес (Child)** — точна копія оболонки.

Оскільки дочірній процес є повною копією пам'яті батьківського на момент виклику, він містить **всі** змінні — як експортовані, так і локальні. На цьому етапі дочірній процес ще є "башем", просто він виконується в іншому просторі адрес (з використанням Copy-On-Write).

### 2.2. Системний виклик execve()

Справжня магія `export` відбувається на другому кроці. Дочірній процес оболонки негайно викликає системний виклик `execve()`, щоб замінити свою програму (bash) на нову (наприклад, `/bin/ls`).

Сигнатура `execve` на мові C виглядає так:

```c
int execve(const char *pathname, char *const argv[], char *const envp[]);
```

Зверніть увагу на третій аргумент: `char *const envp[]`. Це масив вказівників на рядки формату `"KEY=VALUE"`, який закінчується `NULL`. 

Перед викликом `execve`, дочірня оболонка переглядає свій внутрішній список змінних. Вона формує масив `envp`, включаючи туди **тільки ті змінні, які були позначені атрибутом export**. Локальні змінні оболонки в цей масив не потрапляють.

Коли ядро обробляє `execve()`, воно:
1. Очищає пам'ять процесу (знищуючи старий bash та всі його внутрішні змінні).
2. Завантажує код нової програми (`/bin/ls`).
3. Виділяє на вершині стека (stack) пам'ять і записує туди аргументи (`argv`) та масив середовища (`envp`).
4. Передає управління функції `main(int argc, char **argv, char **envp)` нової програми.

Отже, нова програма знаходить своє середовище вже готовим у пам'яті. З цього моменту середовище дочірнього процесу повністю **відв'язане** від батьківського. Зміна змінної середовища всередині дочірнього процесу ніяк не вплине на батьківський процес (оскільки пам'ять вже розмежована).

## 3. Внутрішня реалізація середовища в C (libc)

Будь-яка програма, написана мовами високого рівня (C, Python, Go, Node.js), отримує доступ до цих змінних через бібліотеку C (`libc`).

У мові C глобальна змінна `extern char **environ;` вказує на масив середовища. Для роботи з ним існують стандартні функції POSIX:

- `char *getenv(const char *name);` — отримати значення змінної.
- `int setenv(const char *name, const char *value, int overwrite);` — встановити або змінити змінну.
- `int unsetenv(const char *name);` — видалити змінну.
- `int putenv(char *string);` — додати змінну (вимагає передачі рядка `KEY=VALUE`).

Приклад простої програми на C, що читає змінну:

```c
#include <stdio.h>
#include <stdlib.h>

int main() {
    char *user = getenv("USER");
    if (user != NULL) {
        printf("Hello, %s!\n", user);
    } else {
        printf("USER variable is not set.\n");
    }
    return 0;
}
```

Мови програмування надають власні обгортки над цими функціями:
- **Python**: `os.environ['USER']`
- **Node.js**: `process.env.USER`
- **Go**: `os.Getenv("USER")`
- **Ruby**: `ENV['USER']`

Усі ці обгортки під капотом читають той самий масив рядків, який ядро поклало на стек під час `execve()`.

## 4. Інспектування середовища: /proc/PID/environ

У Linux ядро експонує багато інформації про запущені процеси через віртуальну файлову систему `/proc` (procfs). Для кожного процесу з ідентифікатором `PID` існує директорія `/proc/PID/`.

Один із найкорисніших файлів у цій директорії — `/proc/PID/environ`. Він містить початкове середовище процесу (те саме, що було передано ядром через `envp` під час `execve`).

### 4.1. Особливості формату

Файл `environ` містить дані в "сирому" вигляді — це рядки формату `KEY=VALUE`, розділені нуль-байтом (`\0` або NUL-символ), а не символом нового рядка (`\n`). Це зроблено для того, щоб підтримувати змінні середовища, значення яких містять символи перенесення рядка (що цілком легально в Unix).

Якщо ви спробуєте прочитати цей файл за допомогою звичайного `cat`, вивід зіллється в один суцільний нечитабельний рядок (в кращому випадку), або термінал може зійти з глузду від спецсимволів.

### 4.2. Правильні способи читання /proc/PID/environ

Існує кілька ідіоматичних способів перегляду цього файлу у зручному форматі.

**Спосіб 1: Використання tr (перетворення NUL у newline)**
```bash
# Знаходимо PID нашого SSH-демона, наприклад, 1234
tr '\0' '\n' < /proc/1234/environ
```
Ця команда замінює всі нуль-байти на символ нового рядка, роблячи вивід легким для читання. Проте, якщо якесь значення змінної само по собі містить `\n`, воно буде розбито на два рядки.

**Спосіб 2: Використання xargs**
```bash
xargs -0 -L1 -a /proc/1234/environ
```
Прапорець `-0` вказує `xargs`, що вхідні дані розділені NUL-байтами. `-L1` змушує виводити кожен аргумент з нового рядка, а `-a` зчитує з файлу.

**Спосіб 3: Використання jq (для серіалізації в JSON)**
```bash
# Перетворюємо env у JSON-об'єкт (потребує bash і jq)
cat /proc/1234/environ | xargs -0 -I{} bash -c 'printf "%s\n" "$1"' _ {} | jq -R -s -c 'split("\n") | map(select(length > 0)) | map(split("=") | {key: .[0], value: .[1:] | join("=")}) | from_entries'
```

### 4.3. Обмеження /proc/PID/environ

Важливо розуміти одне суттєве обмеження цього файлу: **він відображає лише те середовище, з яким процес був запущений (викликав `execve`)**. Якщо процес під час свого виконання викликає `setenv()` або модифікує масив `environ` (як це постійно робить сам `bash` або сервери додатків), ці зміни **не будуть** відображені у `/proc/PID/environ`. 

Файл вказує на початковий регіон пам'яті (над стеком), і якщо процес виділяє нову пам'ять для зміненого середовища (що зазвичай робить libc при додаванні нових змінних), ядро не оновлює вказівник для procfs. Тому `/proc/PID/environ` — це зліпок "на момент народження", а не живий стан.

Для інспектування "живого" середовища процесу необхідно використовувати відлагоджувач на кшталт `gdb`:
```bash
gdb -p 1234 -batch -ex 'call (void)printenv()'
```
Або читати пам'ять, якщо ви знаєте адресу глобальної змінної `environ`.

## 5. Проблема "залишкових" (Residual) змінних

Однією з найпідступніших проблем при адмініструванні Linux або розробці бекенд-додатків є концепція "залишкових" (residual) або "випадково успадкованих" змінних середовища.

Оскільки середовище успадковується від батька до дитини за замовчуванням глобально і повністю (весь масив `envp`), будь-яка змінна, яку експортував батько, потрапляє до всіх його нащадків.

### 5.1. Джерела залишкових змінних

1. **Профілі користувачів (`/etc/profile`, `~/.bash_profile`, `~/.bashrc`)**: Коли користувач заходить по SSH, запускається login shell. Вона виконує скрипти ініціалізації, які експортують купу змінних (`PATH`, `LANG`, `XDG_SESSION_ID`, `DBUS_SESSION_BUS_ADDRESS`). Всі процеси, запущені цим користувачем у цій сесії, успадковують цей "багаж".

2. **Systemd (system manager)**: Systemd має глобальне середовище, яке передається всім сервісам. Якщо ви глобально налаштуєте проксі (`http_proxy` в `/etc/environment` або через `systemctl set-environment`), ВСІ демони отримають його, що може зламати їхню локальну комунікацію.

3. **Скрипти-обгортки (Wrapper scripts)**: Скрипт, який експортує `LD_LIBRARY_PATH` для одного бінарника, а потім запускає інший, випадково отруює середовище для другого бінарника.

### 5.2. Проблеми безпеки та ізоляції

Залишкові змінні створюють реальні ризики:
- **Витік секретів**: Якщо CI/CD пайплайн експортує `AWS_ACCESS_KEY_ID`, а потім запускає сторонній скрипт збору метрик або лінтер, лінтер отримує повний доступ до ваших ключів AWS (оскільки він успадковує середовище).
- **Недетермінованість**: Програма може працювати ідеально у вашому терміналі (бо у вас встановлена якась специфічна змінна, напр. `PYTHONPATH`), але падати при запуску через systemd чи cron, де середовище "чисте" або інше.
- **Вразливості бібліотек**: Відома вразливість Shellshock базувалася саме на залишкових/експортованих змінних середовища, які bash інтерпретував як визначення функцій під час запуску CGI-скриптів.

### 5.3. Очищення середовища: команда env

Для вирішення проблеми залишкових змінних стандартною практикою є використання утиліти `env` (з coreutils). Її прапорець `-i` (ignore environment) дозволяє запустити команду в **абсолютно порожньому** середовищі, передаючи лише ті змінні, які ви явно вкажете.

```bash
# Запуск make з чистим середовищем, додавши лише PATH та CC
env -i PATH="/usr/bin:/bin" CC="gcc" make
```

Це гарантує 100% відтворюваність поведінки процесу, незалежно від того, хто і де його запускає (з cron, systemd чи інтерактивної консолі). 

У середовищі systemd для ізоляції використовують директиви типу `PassEnvironment=` (лише вказані змінні проходять) або явне задання через `Environment=`.

## 6. Висновок

Середовище процесу — це елегантний, але архаїчний механізм IPC (Inter-Process Communication), що прийшов до нас з перших версій Unix. 

Розуміння різниці між локальними змінними оболонки та експортованими (змінними середовища) знімає більшість питань про те, чому скрипти поводяться непередбачувано. Зв'язка `fork` -> `exec` пояснює односпрямовану природу цього зв'язку: батько передає середовище дитині, але дитина не може змінити середовище батька (без спеціальних хаків з `ptrace`).

Уміння працювати з `/proc/PID/environ` дає потужний інструмент для дебагу "в польових умовах", а розуміння проблеми залишкових змінних та використання `env -i` є ознакою зрілого інженера, який дбає про безпеку та відтворюваність своїх систем.

Пориньте глибше, експериментуйте з `export` і завжди пам'ятайте: те, що ви бачите в `printenv`, — це лише те, що ваш bash вирішив передати вам у спадок.
