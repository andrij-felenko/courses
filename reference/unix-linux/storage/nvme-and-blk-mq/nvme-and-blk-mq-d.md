До появи NVMe традиційні накопичувачі (SATA/SAS) мали єдину апаратну чергу запитів. У Linux за це відповідав класичний єдиний блочний шар (Single-Queue Block Layer), який використовував одне глобальне блокування для всіх I/O операцій. Це створювало вузьке місце при роботі з надшвидкими флеш-накопичувачами на багатоядерних системах.

NVMe вирішує цю проблему на апаратному рівні, надаючи до 64 тисяч черг (Hardware Submission/Completion Queues), кожна з яких може містити до 64 тисяч команд. Щоб розкрити цей потенціал у ядрі Linux, було створено архітектуру багаточергового блочного шару — **blk-mq** (Block Multi-Queue).

## Архітектура blk-mq та NVMe

Архітектура blk-mq у контексті NVMe складається з двох основних рівнів черг: програмних (Software Staging Queues) та апаратних (Hardware Dispatch Queues).

### Програмні черги (Software Staging Queues)
Ядро створює одну програмну чергу на кожне логічне ядро процесора (CPU). Коли процес ініціює операцію введення-виведення, запит спочатку потрапляє до програмної черги того процесора, на якому виконується процес. Це дозволяє уникнути конкуренції за блокування між процесорами (lock contention), оскільки кожне ядро працює зі своєю локальною чергою.

### Апаратні черги (Hardware Submission/Completion Queues)
NVMe контролер надає апаратні черги подачі (Submission Queues, SQ) та черги завершення (Completion Queues, CQ). Драйвер NVMe у Linux відображає ці апаратні черги на абстракцію Hardware Dispatch Queues у blk-mq. 
Кількість апаратних черг зазвичай дорівнює кількості CPU, що дозволяє організувати пряме відображення (1:1) між програмними чергами та апаратними чергами NVMe.

### NUMA Affinity
Для досягнення максимальної продуктивності blk-mq враховує топологію NUMA. Драйвер NVMe створює апаратні черги таким чином, щоб переривання від черги завершення (CQ) оброблялися на тому самому вузлі NUMA, де знаходиться CPU, що подав запит. Це мінімізує затримки на доступ до пам'яті (PCIe DMA та структури даних ядра).

## Взаємодія драйвера NVMe та blk-mq

Драйвер NVMe (`drivers/nvme/host/pci.c`) є тонким прошарком, який реалізує інтерфейс `blk_mq_ops`. 

Коли запит готовий до відправки на пристрій, blk-mq викликає функцію драйвера `queue_rq`. Драйвер бере запит, формує команду NVMe (64 байти) і записує її в Submission Queue у пам'яті хоста. Після цього драйвер записує нове значення у регістр SQ Tail Doorbell контролера NVMe через MMIO.

```c
== C (Драйвер NVMe)
/* Спрощений приклад реалізації queue_rq у драйвері NVMe */
static blk_status_t nvme_queue_rq(struct blk_mq_hw_ctx *hctx,
                                  const struct blk_mq_queue_data *bd)
{
    struct nvme_queue *nvmeq = hctx->driver_data;
    struct request *req = bd->rq;
    struct nvme_command cmnd;
    
    // Формування команди NVMe
    nvme_setup_cmd(req, &cmnd);
    
    // Копіювання команди в Submission Queue
    nvme_sq_copy_cmd(nvmeq, &cmnd);
    
    // Дзвінок у Doorbell
    nvme_write_sq_db(nvmeq);
    
    blk_mq_start_request(req);
    return BLK_STS_OK;
}
== Shell (Перегляд черг)
# Перегляд кількості апаратних черг для пристрою nvme0n1
ls -d /sys/block/nvme0n1/mq/* | wc -l
# Перегляд відображення CPU на апаратну чергу 0
cat /sys/block/nvme0n1/mq/0/cpu_list
```

Після виконання команди контролер записує результат у Completion Queue і генерує переривання (MSI-X). Обробник переривання викликає `blk_mq_complete_request`, що сигналізує blk-mq про завершення операції.

## Оптимізації введення-виведення

### Polling (Опитування) замість переривань
Для надшвидких NVMe накопичувачів обробка переривань може займати більше часу, ніж саме виконання I/O. blk-mq підтримує механізм **io polling**, де ядро активно опитує CQ замість очікування переривання. Це вимагає виділення окремих апаратних черг спеціально для поллінгу (poll queues).

[book:unix-linux:io:blk-iopoll-and-io-polling] детальніше розглядає цей механізм.

### Злиття запитів (Request Merging)
На рівні програмних черг blk-mq все ще може виконувати злиття суміжних запитів у більші транзакції, що зменшує накладні витрати на рівні PCIe. Однак планувальники вводу-виводу (IO Schedulers), такі як `mq-deadline`, зазвичай вимикаються для NVMe (використовується режим `none`), оскільки апаратні черги самі ефективно керують порядком виконання.
