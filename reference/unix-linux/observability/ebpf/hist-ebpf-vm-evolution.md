# 📜 Еволюція BPF: від пакетного фільтра BSD до універсальної віртуальної машини ядра

У 1992 році інженери Стівен Маккейн (*Steven McCanne*) та Ван Джейкобсон (*Van Jacobson*) у Лабораторії Лоуренса в Берклі (*Lawrence Berkeley Laboratory*, LBL) зіткнулися з фундаментальним обмеженням мережевого стеку Unix: інструменти моніторингу трафіку, зокрема `tcpdump`, не встигали за зростанням пропускної здатності мереж 10 Мбіт/с Ethernet. Кожен мережевий пакет ядро операційної системи було змушене копіювати з кільцевого буфера мережевої карти у простір ядра, а звідти через системний виклик передавати у простір користувача, де користувацька програма перевіряла, чи належить пакет потрібному TCP-порту. Якщо фільтр відкидав 99% пакетів, процесор витрачав майже весь час на непотрібне копіювання пам'яті між контекстами та перемикання режимів процесора (*context switches*).

Рішенням дослідників стала концепція виконання коду фільтра безпосередньо всередині ядра — технологія, що отримала назву **BSD Packet Filter (BPF)**.

## 1. Архітектура Classic BPF (cBPF, 1992)

Маккейн і Джейкобсон запропонували перенести логіку фільтрації в ядро, використовуючи спеціально спроєктовану інтерпретовану віртуальну машину. Замість копіювання сирого пакета у простір користувача ядро спочатку запускало маленький байт-код фільтра над заголовками пакета, що лежали у буфері пам'яті ядра (`sk_buff` або `mbuf`). Якщо фільтр повертав `0`, пакет негайно видалявся без жодного звернення до простору користувача; якщо фільтр повертав число `N > 0`, ядро копіювало лише перші `N` байтів пакета, необхідні для аналізу.

Віртуальна машина cBPF спиралася на просту акумуляторну модель обчислень:
* **Акумулятор (регістр `A`, 32 біти)**: використовувався для завантаження даних із пакета, виконання арифметичних операцій та збереження проміжних результатів.
* **Індексний регістр (`X`, 32 біти)**: застосовувався для адресації зі зміщенням (наприклад, читання довжини заголовка IP для подальшого зміщення до порту TCP).
* **Пам'ять тимчасового зберігання (Scratch Memory)**: масив із 16 комірок по 4 байти (`M[0]`–`M[15]`), що відігравав роль примітивного стеку.
* **Набір інструкцій**: приблизно 30 фіксованих інструкцій довжиною 64 біти (структура `struct sock_filter`), що містили код операції (`code`), прапорці переходу (`jt`, `jf`) та зміщення або константу (`k`).

```
+-------------------------------------------------------------+
|  Classic BPF (cBPF): Акумуляторна 32-бітна архітектура      |
|                                                             |
|  [ Регістр A (32 bit) ] <---> [ ALU (Арифметика та логіка)] |
|  [ Регістр X (32 bit) ]                                     |
|  [ Scratch Memory M[0..15] (16 x 4B) ]                      |
|                                                             |
|  Інструкції: ld/ldx/st/alu/jmp/ret (фіксований розмір 64b)  |
+-------------------------------------------------------------+
```

Такий підхід забезпечив прискорення фільтрації пакетів у 10–100 разів порівняно з тогочасними аналогами (як-от CMU/Stanford Packet Filter, CSPF), оскільки мінімізував простій шини пам'яті.

## 2. Поява BPF у Linux та перші обмеження

У 1997 році розробник Джей Шуманн (*Jay Schulist*) портував cBPF до ядра Linux версії 2.1.75 через опцію сокета `SO_ATTACH_FILTER`. Утиліти `tcpdump` та `libpcap` отримали можливість компілювати високорівневі вирази фільтрації (наприклад, `tcp and port 80`) у байт-код cBPF і завантажувати їх через `setsockopt()`.

Згодом cBPF знайшов застосування у сфері безпеки: у 2012 році в ядрі Linux 3.5 з'явився підсистема **seccomp-bpf** (*Secure Computing Mode*), яка використовувала віртуальну машину cBPF для перевірки аргументів системних викликів процесів і блокування небезпечних викликів.

У 2011 році Ерік Дюмазе (*Eric Dumazet*) написав перший JIT-компілятор (*Just-In-Time Compiler*) для cBPF в архітектурі x86_64 (Linux 3.0), що транслював інструкції cBPF безпосередньо в нативні машинні коди CPU під час завантаження сокетного фільтра.

Однак до 2013 року класичний BPF досяг своєї архітектурної межі:
1. **Невідповідність апаратному забезпеченню**: 32-розрядні регістри `A` та `X` погано відображалися на 64-розрядні регістри сучасних процесорів (x86_64, ARM64), вимагаючи додаткових операцій розширення знаків та маскування.
2. **Брак регістрів для викликів функцій**: Наявність лише двох регістрів унеможливлювала прямий виклик функцій ядра з передачею стандартних 4–6 аргументів за конвенцією System V AMD64 ABI.
3. **Повна відсутність стану (Stateless)**: Програма cBPF не мала механізму збереження даних між викликами. Вона не могла рахувати накопичувальні лічильники, створювати гістограми або пам'ятати стан TCP-з'єднань.
4. **Ізольованість від підсистем ядра**: cBPF міг працювати лише з мережевими сокетами та фільтрацією seccomp, але не мав доступу до точок динамічного трасування ядра (`kprobes`), статичних точок трасування (`tracepoints`) чи файлової системи.

## 3. Народження Extended BPF (eBPF, 2014)

У 2014 році інженери Олексій Старовойтов (*Alexey Starovoitov*) та Даніель Боркманн (*Daniel Borkmann*) запропонували радикальний перегляд архітектури віртуальної машини, перетворивши її на повноцінне середовище виконання коду загального призначення. Нова підсистема отримала назву **Extended BPF (eBPF)** (в офіційній термінології ядра Linux стара підсистема стала називатися cBPF, а нова — просто BPF).

Патчі eBPF увійшли в ядро Linux 3.18 наприкінці 2014 року. Архітектура віртуальної машини була переписана з нуля під сучасні процесори:
* **64-розрядні регістри**: Кількість регістрів зросла з 2 до 11 (`R0`–`R10`). Призначення регістрів було жорстко стандартизовано для збігу з апаратними регістрами x86_64 та ARM64 (`R1`–`R5` для аргументів, `R0` для повернення значення, `R10` для кадру стеку).
* **Стек на 512 байтів**: Програми отримали власний локальний стек фіксованого розміру для збереження локальних змінних і структур.
* **Структури збереження стану — BPF Maps**: З'явився механізм виділення універсальних структур даних у пам'яті ядра (хеш-таблиці, масиви, кільцеві буфери), до яких програми eBPF можуть звертатися під час обробки подій, а програми простору користувача — читати й змінювати через файлові дескриптори.
* **Математичний верифікатор (In-Kernel Verifier)**: Замість простого статичного аналізу безпеки cBPF було створено верифікатор, що здійснює абстрактну інтерпретацію коду, відстежує типи та числові межі кожного регістру, контролює розіменування вказівників і гарантує завершення програми.
* **Універсальний системний виклик `bpf()`**: Було запроваджено окремий системний виклик `sys_bpf`, який став єдиним інтерфейсом завантаження програм, створення карт і зв'язування з подіями.

```
+-------------------------------------------------------------------+
|  Extended BPF (eBPF): 64-бітна RISC-архітектура                   |
|                                                                   |
|  [ R0: Код повернення / Результат ]                               |
|  [ R1..R5: Аргументи функцій / Контекст виконання ]               |
|  [ R6..R9: Збережені регістри (Callee-saved) ]                    |
|  [ R10: Вказівник стеку (Read-Only Frame Pointer) ]               |
|  [ Локальний стек: 512 байтів ]                                   |
|                                                                   |
|  BPF Maps (Хеш-таблиці, масиви) <---> BPF Helper Functions        |
+-------------------------------------------------------------------+
```

## 4. Еволюція сфер застосування: від мережі до спостережуваності та безпеки

Після виходу ядра 3.18 екосистема eBPF почала стрімко охоплювати всі ключові підсистеми ядра Linux:

| Рік / Версія ядра | Ключова інновація eBPF | Вплив на системне програмування |
|---|---|---|
| **2014 (Linux 3.18)** | Системний виклик `bpf()`, BPF Maps | Початок універсальної розширюваності ядра |
| **2015 (Linux 4.1–4.4)** | Підтримка `kprobes`, `uprobes`, `tracepoints`, `perf_events` | Поява сучасного динамічного трасування без оверхеду модулів |
| **2016 (Linux 4.8)** | Підсистема **XDP** (*eXpress Data Path*) | Обробка пакетів на рівні мережевого драйвера (до 24 млн пакетів/с на ядро) |
| **2017 (Linux 4.10)** | Підтримка контрольних груп **cgroup-bpf** | Фільтрація трафіку та сокетів на рівні контейнерів |
| **2018 (Linux 4.18)** | **BTF** (*BPF Type Format*) | Компактний опис структур даних ядра для переносимості програм |
| **2019 (Linux 5.2–5.3)** | Дозвіл обмежених циклів (*Bounded Loops*), **CO-RE** (*Compile Once – Run Everywhere*) | Компіляція eBPF без необхідності мати заголовочні файли ядра на цільовій системі |
| **2020 (Linux 5.7–5.8)** | **BPF LSM** (*Linux Security Modules*), **BPF Ring Buffer** | Створення власних безпекових політик у ядрі та високошвидкісна передача подій |
| **2023 (Linux 6.6+)** | **Sched-ext** (*Extensible Scheduler Class*) | Можливість реалізації користувацьких планувальників завдань CPU на eBPF |

Завдяки підтримці компілятора LLVM/Clang програмісти отримали можливість писати програми eBPF мовою C або Rust, які компілюються у двійковий об'єктний ELF-файл з BPF-інструкціями. Інструменти на зразок `BCC` (*BPF Compiler Collection*) та сучасної бібліотеки `libbpf` з моделлю CO-RE перетворили eBPF на промисловий стандарт системної діагностики, моніторингу безпеки (наприклад, Falco, Tetragon) та високопродуктивних мережевих проксі (Cilium, Katran).
