Коли програма, незалежно від того, чи це складна база даних у просторі користувача, чи підсистема віртуальної пам'яті в ядрі Linux, починає поводитися непередбачувано на працюючому виробничому (production) сервері, розробники постають перед серйозною проблемою. Традиційне налагодження (debugging) передбачає використання інтерактивних інструментів на кшталт GDB або розстановку статичних повідомлень через `printf` чи `printk`. Перший підхід неможливий, оскільки він призупиняє роботу системи, що неприпустимо для сервера під навантаженням. Другий підхід вимагає редагування сирцевого коду, перекомпіляції програми або ядра та їхнього перезапуску, що руйнує сам стан, який спричинив проблему (так званий ефект "гейзенбагу"). Крім того, статичні точки трасування (tracepoints) вимагають передбачення: розробник мусить заздалегідь знати, яке місце в коді коли-небудь знадобиться інспектувати.

Щоб вирішити цю фундаментальну проблему, інженери створили механізми динамічного трасування, здатні вставляти "зонди" (probes) у працюючий двійковий код "на льоту". У системі Linux цими механізмами є **kprobes** (Kernel Probes), які дозволяють зондувати код самого ядра, та **uprobes** (User Probes), що поширюють ті ж самі принципи на програми простору користувача. Разом вони формують основу для сучасних систем аналітики та спостережуваності (observability), дозволяючи інженерам зазирати всередину будь-якої інструкції, не змінюючи виконуваних файлів на диску та не вимагаючи перезавантажень.

## 1. Фундамент динамічної інструментації: апаратні переривання та INT3

Секрет здатності kprobes та uprobes зупиняти виконання на довільній інструкції полягає не в магії компілятора, а у використанні низькорівневих апаратних можливостей процесора. Для архітектури x86_64, яка сьогодні є найпоширенішою на серверах, головним інструментом є інструкція програмного переривання (software breakpoint), відома як `INT3`.

В асемблері x86 інструкція `INT3` унікальна тим, що її машинний код складається лише з одного байта: `0xCC`. Ця однобайтовість є критичною. На архітектурах зі змінною довжиною інструкцій, таких як x86, заміна кількох байтів працюючого коду не є атомарною з точки зору інших ядер процесора. Якби зонд вимагав запису багатобайтової інструкції, інший потік виконання міг би натрапити на "наполовину переписаний" машинний код, що неминуче призвело б до падіння (crash). Байт `0xCC` записується атомарно, що робить цей процес безпечним у багатопроцесорних (SMP) системах.

Коли ви просите ядро встановити зонд (неважливо, kprobe чи uprobe) на певну адресу, відбувається такий ланцюг подій:

1. **Ідентифікація та копіювання:** Ядро перевіряє, чи є вибрана адреса допустимою інструкцією. Далі воно копіює оригінальну інструкцію з цієї адреси в спеціально виділений, безпечний буфер пам'яті (out-of-line buffer), щоб зберегти її для майбутнього виконання.
2. **Атомарна заміна (Вставка зонду):** Ядро замінює перший байт оригінальної інструкції в робочому коді на байт `0xCC` (`INT3`).
3. **Генерація виключення:** Процесор, виконуючи код програми або ядра, доходить до нашого модифікованого місця і намагається виконати байт `0xCC`. Це негайно призводить до генерації апаратного виключення `#BP` (Breakpoint Exception).
4. **Перемикання контексту:** Нормальний потік виконання інструкцій переривається. Апаратне забезпечення процесора безумовно передає керування обробнику переривань (trap handler) у ядрі ОС. При цьому стан усіх регістрів процесора (значення лічильника інструкцій, вказівники стека, регістри загального призначення) зберігається в пам'яті у вигляді структури `pt_regs`.

Саме на цьому етапі "магія" трасування передає ініціативу в руки розробника. Ядро дивиться на адресу, звідки надійшло переривання `INT3`, шукає її у своїй внутрішній хеш-таблиці активних зондів і, знайшовши збіг, викликає пов'язану функцію-обробник (handler). Цей обробник тепер має повний доступ до структури `pt_regs`. Інспектуючи регістри (наприклад, `RDI`, `RSI`, `RDX` за стандартом викликів x86_64), обробник може зчитати значення аргументів, з якими була викликана оригінальна функція, або перевірити стан стека.

### Single-stepping: повернення до нормального життя

Після того, як наш обробник зібрав потрібні дані, програма повинна продовжити свою роботу так, ніби нічого не сталося. Для цього потрібно якось виконати ту саму оригінальну інструкцію, чий перший байт ми затерли на `0xCC`. 

У ранніх версіях kprobes використовувався метод "in-line single-stepping". Ядро тимчасово знімало байт `0xCC`, повертаючи оригінальну інструкцію на місце. Далі воно встановлювало спеціальний прапорець Trap Flag (TF) у регістрі стану процесора (EFLAGS) і повертало керування. Trap Flag змушував процесор виконати рівно одну інструкцію і одразу згенерувати інше виключення — `#DB` (Debug Exception). Перехопивши `#DB`, ядро знову вставляло `0xCC` на місце і знімало Trap Flag. Цей метод мав катастрофічну ваду в SMP-системах: у те коротке вікно, коли `0xCC` було знято, інший процесор міг проскочити це місце, взагалі "не помітивши" зонду. Це вимагало складної і повільної зупинки інших ядер процесора.

Сучасний і безпечніший підхід називається **Out-Of-Line (OOL) single-stepping**. Пам'ятаєте буфер, у який ми скопіювали оригінальну інструкцію? Ядро модифікує збережений стан регістрів (вказівник інструкцій, RIP) так, щоб він вказував не на оригінальний код, а на цей OOL-буфер. Процесору дозволяється виконати інструкцію безпосередньо з цього буфера. Після виконання інструкції генерується переривання, і ядро вручну коригує RIP так, щоб він вказував на *наступну* інструкцію в оригінальному коді (одразу після зонда). Оскільки байт `0xCC` ніколи не видаляється з оригінального коду, зонд залишається надійно активним для всіх потоків одночасно.

## 2. Kprobes: анатомія ядерного зондування

Механізм kprobes діє у привілейованому просторі ядра (Ring 0) і дозволяє інспектувати як базовий код ядра Linux, так і завантажені модулі. Він пропонує два основні інструменти:

1. **Kprobe:** Базовий зонд, який можна встановити практично на будь-яку інструкцію, але найчастіше він розміщується на найпершій інструкції функції (вхід у функцію). Це дозволяє надійно перехоплювати вхідні аргументи (наприклад, який файловий дескриптор передали у виклик `sys_read`).
2. **Kretprobe (Kernel Return Probe):** Спеціалізований зонд, що спрацьовує в момент *повернення* з функції. Це критично важливо для інспектування результату роботи функції (наприклад, чи повернув системний виклик помилку `-ENOENT`) та для вимірювання точного часу виконання (зафіксувати час на kprobe при вході і відняти його від часу на kretprobe при виході).

### Влаштування Kretprobe: магія підміни стека

Перехопити момент входу у функцію легко: ми знаємо її адресу. Перехопити вихід значно складніше. Функція може бути великою, мати десятки інструкцій `RET` (повернення), розкиданих по всьому коду, або завершуватися нетипово через оптимізації компілятора. Пошук усіх цих точок виходу і встановлення на них окремих kprobes є неефективним і крихким підходом.

Kretprobe вирішує цю проблему елегантно, динамічно підміняючи інформацію на стеку викликів (call stack). 

Коли розробник реєструє kretprobe для певної функції, ядро насправді встановлює звичайний зонд (kprobe) на її вхідну інструкцію. Коли викликається цільова функція, спрацьовує цей початковий зонд. Спеціальний внутрішній обробник kretprobe аналізує стан поточного стека. Там, на вершині стека, лежить **справжня адреса повернення** — адреса тієї інструкції, до якої має повернутися процесор після завершення функції.

Що робить kretprobe? Він запам'ятовує цю справжню адресу у своїй внутрішній структурі даних (пов'язаній з поточним завданням, `task_struct`), а на стеку **замінює її на адресу своєї власної функції-трампліна** (kretprobe trampoline).

Функція продовжує своє виконання, абсолютно не підозрюючи про маніпуляції зі стеком. Коли вона нарешті доходить до будь-якої інструкції `RET`, процесор слухняно зчитує зі стека підмінену адресу і виконує стрибок на функцію-трамплін ядра. Трамплін отримує керування, знаходить збережену справжню адресу повернення, викликає ваш користувацький обробник kretprobe (який тепер може інспектувати регістр результату, наприклад `RAX`), а потім відновлює справжню адресу повернення і передає керування на неї. Цей механізм гарантує перехоплення незалежно від того, яким шляхом функція дійшла до кінця.

## 3. Uprobes: міграція динамічного трасування у простір користувача

Те, що kprobes робить для операційної системи, **uprobes** робить для програм у просторі користувача. Уявіть, що ви можете поставити зонд на виклик `malloc` у стандартній бібліотеці `libc`, на обробку HTTP-запиту всередині інтерпретатора Node.js або на запит SQL у PostgreSQL. 

Концептуально uprobes працюють за тими ж принципами, що й kprobes: вони покладаються на вставку байта `0xCC` та генерацію виключення `#BP`. Однак, оскільки мова йде про простір користувача, механізм реалізації стикається з додатковими складнощами, пов'язаними з віртуальною пам'яттю.

### Механіка Uprobes через віртуальну пам'ять

Процеси в просторі користувача не мають доступу до фізичної пам'яті напряму; вони існують у своїх ізольованих віртуальних адресних просторах. Крім того, виконувані файли та спільні бібліотеки зазвичай мапляться в пам'ять багатьох процесів одночасно (наприклад, бібліотека `libc.so` завантажена один раз у фізичну пам'ять, але використовується сотнями процесів).

Процес встановлення uprobe виглядає так:
1. Замість адреси в пам'яті, ви ідентифікуєте uprobe за шляхом до файлу (наприклад, `/lib/x86_64-linux-gnu/libc.so.6`) та зміщенням (offset) необхідної інструкції від початку цього файлу.
2. Ядро знаходить фізичну сторінку пам'яті, що відповідає цьому місцю у файлі. Оскільки пам'ять спільних бібліотек зазвичай захищена від запису, ядро ініціює механізм **Copy-on-Write (CoW)** — воно створює приватну копію цієї сторінки.
3. У цю скопійовану сторінку ядро записує байт `0xCC`.
4. Ядро змінює таблиці сторінок (page tables) для процесів так, щоб вони бачили цю модифіковану сторінку замість оригінальної. За замовчуванням, якщо ви не вказали конкретний PID процесу, ця модифікована сторінка стає видимою для всіх процесів, які використовують цей файл.

Коли програма користувача досягає байта `0xCC`, генерується виключення. Це спричиняє обов'язкове **перемикання контексту (context switch)** — процесор переходить з режиму користувача (Ring 3) в режим ядра (Ring 0), оскільки обробники апаратних переривань завжди живуть у ядрі. Ядро ідентифікує подію як uprobe, викликає пов'язаний код (наприклад, програму eBPF), а потім повинно виконати out-of-line single-stepping. OOL буфер для uprobes створюється у спеціальному прихованому регіоні пам'яті в адресному просторі самого процесу. Після виконання інструкції, ядро повертає процесор назад у режим користувача.

Для перехоплення виходу з функцій користувача існує **uretprobe**. Його механізм підміни стека є дзеркальним відображенням kretprobe, але працює з користувацьким стеком. Ядро замінює адресу на користувацькому стеку на адресу маленького шматка коду (трампліна), який ядро примусово інжектує в адресний простір процесу при його створенні (у так звану сторінку `[uprobes]`).

## 4. Ціна питання: Overhead, Branch Predictor та Optprobes

Найбільшою перешкодою для масового використання динамічного трасування є його накладні витрати (overhead). Хоча `INT3` забезпечує 100% безпечне впровадження зонду, його виконання обходиться системі дуже дорого. 

Кожне спрацьовування зонду означає генерацію апаратного виключення. Для kprobes це зупинка конвеєра процесора, збереження гігантської структури `pt_regs` та виклик складної інфраструктури обробників. Для uprobes ситуація ще гірша: окрім переривання, відбувається повноцінне перемикання контексту з режиму користувача в ядро і назад. Якщо ви розмістите зонд на функції, яка викликається мільйони разів на секунду (наприклад, на дрібному алокаторі пам'яті чи функції розбору рядків), ваша система, швидше за все, деградує до стану повної непридатності.

### Оптимізація через JMP: Optprobes

Щоб радикально знизити накладні витрати в ядрі, був розроблений механізм **Optprobes** (Оптимізовані kprobes). Основна ідея полягає у відмові від повільного переривання `INT3` на користь звичайної інструкції безумовного переходу (`JMP`).

Замість того, щоб вставляти однобайтовий `0xCC`, Optprobe замінює одразу 5 байтів оригінального коду (саме стільки на x86 потребує відносний `JMP` на 32-бітне зміщення). Оскільки інструкції x86 мають змінну довжину, ця операція дуже делікатна: ядро фоновим процесом (kprobe-optimizer) ретельно аналізує машинний код навколо місця вставки. Воно має переконатися, що заміна не "розріже" іншу інструкцію навпіл і що немає інших інструкцій `JMP` чи `CALL`, які могли б несподівано передати керування прямо всередину цих 5 байтів. Якщо перевірка успішна, ядро замінює інструкції на `JMP`, що вказує на спеціальний буфер (detour buffer). У цьому буфері зберігається стан, викликається ваш обробник, виконуються оригінальні 5 байт інструкцій, і відбувається стрибок назад у ядро.

Оскільки `JMP` не генерує жодних переривань, оптимізований kprobe виконується на порядок швидше, ніж класичний `INT3`-зонд.

### Покарання за uretprobes: Branch Predictor

Якщо kprobes можна оптимізувати, то **uretprobes** несуть у собі ще одну, приховану ціну, пов'язану з архітектурою сучасних процесорів. Усі сучасні CPU мають механізм передбачення розгалужень (Branch Predictor), важливою частиною якого є Return Stack Buffer (RSB). RSB — це апаратний кеш, який відстежує виклики `CALL` і запам'ятовує, куди має статися відповідний `RET`. Завдяки RSB процесор спекулятивно виконує інструкції після повернення ще до того, як сам `RET` завершить зчитування стека.

Коли uretprobe маніпулює стеком, підміняючи адресу повернення на свій трамплін, він грубо порушує обіцянки, дані RSB. Процесор очікує повернення в оригінальне місце, а замість цього стрибає на трамплін. Це спричиняє 100% "хибне передбачення розгалуження" (branch misprediction). Увесь конвеєр спекулятивного виконання (pipeline) доводиться скидати і заповнювати наново, що коштує десятки тактів на кожне повернення. Тому використання uretprobes на "гарячих" (тих, що часто викликаються) функціях вимагає особливої обережності. 

## 5. Синергія: чому BPF — ідеальний компаньйон

Самі по собі kprobes та uprobes — це лише механізм сповіщення ядра про те, що певна подія (виконання інструкції) сталася. Але що з цим робити? 

Раніше розробникам доводилося писати власні модулі ядра на мові C (kernel modules), які реєстрували функції-обробники. Це несло величезні ризики: помилка у вказівнику або нескінченний цикл у такому модулі миттєво призводили до паніки ядра (Kernel Panic) і падіння всього сервера. Крім того, передача кожного одиничного спрацьовування зонду у простір користувача для аналізу була б катастрофічно повільною через перемикання контексту.

Саме тому сучасне використання зондів немислиме без **eBPF (Extended Berkeley Packet Filter)**. eBPF — це віртуальна машина в ядрі Linux. Ви пишете невеликі програми (на C або спеціальних мовах), які компілюються у безпечний байткод. Перед завантаженням у ядро, суворий верифікатор перевіряє цей байткод, гарантуючи, що він ніколи не призведе до падіння і завжди завершиться за визначений час. 

Головна перевага eBPF полягає в **локальності**. Коли спрацьовує kprobe або uprobe, програма eBPF виконується *одразу на місці*, в контексті ядра. Вона не передає сирі дані в userspace. Натомість вона може відфільтрувати подію (наприклад, ігнорувати системні виклики `open` для системних процесів), витягнути з пам'яті лише необхідні аргументи, або агрегувати статистику. Замість мільйонів подій, eBPF-програма може формувати BPF-карту (гістограму або лічильник) безпосередньо в пам'яті ядра, а програма у просторі користувача зчитуватиме цю статистику раз на кілька секунд.

### Інструментарій: BPFtrace та C (libbpf)

Сьогодні ніхто не працює з kprobes чи uprobes через сирі системні виклики. Розробники використовують високорівневі інструменти, такі як `bpftrace` (схожий на awk для ядра) або програми на C з використанням `libbpf`. 

Розглянемо практичний приклад. Ми хочемо проаналізувати роботу командної оболонки `bash`. Ми встановимо uprobe на функцію `readline` (щоб бачити, коли користувач готується ввести команду), uretprobe, щоб захопити саму введену команду, і kprobe на системний виклик `openat2`, щоб побачити, які файли bash відкриває при її виконанні.

:::tabs
== bpftrace
```bash
# bpftrace дозволяє створювати зонди в стилі однорядкових скриптів.
# Він сам транслює цей скрипт у BPF-байткод, валідує і прикріплює до зондів.

# 1. Kprobe: відстежуємо вхід у функцію ядра do_sys_openat2
# (ця функція відповідає за більшість системних викликів відкриття файлів)
bpftrace -e 'kprobe:do_sys_openat2 { 
    // arg1 містить адресу рядка імені файлу. str() читає рядок з пам'яті.
    printf("PID %d (comm: %s) відкриває файл: %s\n", pid, comm, str(arg1)); 
}'

# 2. Uprobe: відстежуємо виклик функції readline всередині процесу bash
# Синтаксис: uprobe:шлях_до_бінарника:назва_функції
bpftrace -e 'uprobe:/bin/bash:readline { 
    printf("Bash (PID %d) вивів запрошення і чекає на ввід...\n", pid); 
}'

# 3. Uretprobe: відстежуємо повернення з функції readline
# В момент повернення, в регістрі результату (retval) буде лежати вказівник
# на рядок, який користувач щойно ввів.
bpftrace -e 'uretprobe:/bin/bash:readline { 
    printf("Користувач (PID %d) ввів: %s\n", pid, str(retval)); 
}'
```

== C (libbpf)
```c
// Написання BPF-програм мовою C з використанням сучасної бібліотеки libbpf.
// Макроси SEC() вказують завантажувачу (наприклад, bpftool або вашому userspace-коду),
// до яких зондів прикріпити ці функції.
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

// 1. Kprobe: перехоплення відкриття файлу
SEC("kprobe/do_sys_openat2")
int BPF_KPROBE(trace_open, int dfd, const char *filename) {
    char buf[256];
    // Для читання з адресного простору користувача в BPF потрібна функція bpf_probe_read
    bpf_probe_read_user_str(buf, sizeof(buf), filename);
    bpf_printk("Файл відкривається: %s\n", buf);
    return 0;
}

// 2. Uprobe: вхід у функцію користувача. 
// Зауважте: libbpf не містить жорсткого шляху до /bin/bash у байткоді.
// Шлях та зміщення (offset) налаштовуються динамічно вашою програмою 
// у просторі користувача під час прикріплення (attach).
SEC("uprobe/bash_readline")
int BPF_UPROBE(trace_bash_readline) {
    bpf_printk("Bash готується до вводу\n");
    return 0;
}

// 3. Uretprobe: отримання результату функції
SEC("uretprobe/bash_readline")
int BPF_URETPROBE(trace_bash_readline_ret, const char *ret_string) {
    char buf[256];
    bpf_probe_read_user_str(buf, sizeof(buf), ret_string);
    bpf_printk("Введено команду: %s\n", buf);
    return 0;
}

char _license[] SEC("license") = "GPL";
```
:::

Як демонструють приклади, використання BPF ізолює розробника від небезпек прямої роботи з `INT3` та маніпуляціями зі стеком. Складна низькорівнева робота повністю делегується інфраструктурі ядра.

## Висновки

Динамічне трасування перетворює Linux із "чорної скриньки" на прозору систему, де поведінку будь-якого компонента можна виміряти в реальному часі. Базуючись на простому, але надійному апаратному механізмі програмного переривання (`INT3`), kprobes та uprobes здатні перехоплювати виконання будь-якої інструкції як у ядрі, так і в користувацьких процесах, не залишаючи слідів на диску і не вимагаючи зупинок. Попри неминучі накладні витрати на перемикання контексту та маніпуляції зі стеком (як у випадку uretprobes), поєднання цих інструментів із віртуальною машиною eBPF робить їх безпечними та неймовірно швидкими, забезпечуючи фундамент для сучасних рішень спостережуваності та профілювання.
