# 📋 C/C++ API для Syslog: openlog, syslog, closelog та setlogmask

Стандартна бібліотека мови C (libc) надає програмний інтерфейс для відправки повідомлень у системний демон логування. Цей інтерфейс визначено в заголовочному файлі `<syslog.h>` і він є частиною офіційної специфікації POSIX.1-2001. Завдяки цьому будь-яка програма, написана мовами C або C++, може здійснювати запис у системний журнал без необхідності писати власний код для роботи з мережевими чи міжпроцесними сокетами.

## Основні функції системного API

Інтерфейс логування C-бібліотеки складається з п'яти основних функцій (включаючи варіант із масивом аргументів `vsyslog`):

```text
#include <syslog.h>
#include <stdarg.h>

void openlog(const char *ident, int option, int facility);
void syslog(int priority, const char *format, ...);
void vsyslog(int priority, const char *format, va_list ap);
void closelog(void);
int setlogmask(int maskpri);
```

### 1. Функція ініціалізації: `openlog()`

Функція `openlog()` готує та налаштовує з'єднання з демоном логування. Викликати її не обов'язково: якщо програма одразу викликає `syslog()`, сокет відкриється автоматично із дефолтними значеннями. Проте явний виклик `openlog()` є гарною практикою, оскільки він дозволяє встановити власне ім'я програми (ідентифікатор), налаштувати прапорці відкриття сокета та задати дефольтний засіб логування (Facility).

Детальний опис параметрів `openlog()`:
- `ident`: Рядок-префікс, який автоматично додається до початку кожного лог-повідомлення. Зазвичай сюди передають ім'я програми або фонового демона, наприклад `"my_service"`. Особливістю реалізації в libc є те, що переданий вказівник копіюється як чиста адреса, а не як новий рядок. Тому рядок `ident` мусить перебувати у статичній пам'яті програми протягом усього часу роботи логера. Якщо пам'ять під `ident` буде звільнено (наприклад, якщо це був локальний масив у функції), подальші виклики `syslog()` призведуть до читання «висячого» вказівника (dangling pointer) і краху програми (Segmentation Fault).
- `option`: Бітова маска прапорців, що змінюють поведінку підсилення логування при відправці та відкритті сокета.
- `facility`: Категорія за замовчуванням (Facility), яка буде застосована до всіх наступних викликів `syslog()`, якщо в них не вказано іншу категорію.

**Основні прапорці опцій (`option`):**

- `LOG_PID`: Додавати ідентифікатор процесу (PID) у квадратних дужках одразу після ідентифікатора програми (наприклад, `my_service[4512]`). Це корисно для розрізнення записів, якщо запуск відбувся в кількох екземплярах або при використанні пул-процесів.
- `LOG_CONS`: Якщо при спробі відправки повідомлення в сокет syslog сталася помилка (наприклад, демон логування зупинено або сокет `/dev/log` недоступний), вивести це повідомлення безпосередньо на системну консоль `/dev/console`.
- `LOG_NDELAY`: Відкрити сокет до демона логування негайно під час виконання виклику `openlog()`. За замовчуванням відкриття сокета є «лінивим» і відбувається лише під час першого реального виклику `syslog()`. Прапорець `LOG_NDELAY` часто використовують у демон-процесах перед викликом `chroot()`, щоб зберегти дескриптор сокета відкритим до зміни кореневого каталогу.
- `LOG_ODELAY`: Протилежність `LOG_NDELAY`: відкласти відкриття сокета до першої реальної спроби логування (типова дефолтна поведінка).
- `LOG_PERROR`: Паралельно із відправкою у системний журнал друкувати копію кожного повідомлення у стандартний потік помилок `stderr`.
- `LOG_NOWAIT`: Не чекати дочірніх процесів, які могли бути створені під час відправки. У сучасній реалізації GNU C Library (glibc) цей прапорець не має ефекту, оскільки сокети відправляються без створення дочірніх процесів через `fork()`.

### 2. Основна функція запису: `syslog()` та `vsyslog()`

Функція `syslog()` безпосередньо формує лог-запис та надсилає його в сокет. Вона працює за аналогією до стандартної функції `printf()`, підтримуючи довільну кількість аргументів форматування.

Варіант `vsyslog()` приймає список аргументів змінної довжини у вигляді `va_list`. Це дозволяє створювати власні обгортки логування у C-програмах, які приймають варікативні параметри та передають їх далі у системний журнал.

- `priority`: Числове значення пріоритету, яке об'єднує категорію (**Facility**) та важливість (**Severity**) через операцію бітового «АБО» (`|`). Якщо категорію передано як 0, функція автоматично використовує значення `facility`, вказане при виклику `openlog()`.
- `format`: Рядок форматування. Він підтримує всі стандартні специфікатори `printf()`, а також специфічний для syslog специфікатор `%m`. Специфікатор `%m` не вимагає відповідного аргументу в списку — при обробці рядок `%m` автоматично замінюється на системний текстовий опис поточної помилки `strerror(errno)`.

```text
// Запис помилки автентифікації з автоматичною підстановкою опису errno (%m)
syslog(LOG_AUTHPRIV | LOG_ERR, "Не вдалося автентифікувати користувача %s: %m", username);
```

### 3. Функція закриття: `closelog()`

Функція `closelog()` закриває файловий дескриптор сокета, який використовувався для зв'язку з демоном логування. Такий виклик є корисним при вигрузці динамічних бібліотек, перезапуску служб або перед виконанням системного виклику `execve()`.

### 4. Клієнтська фільтрація: `setlogmask()`

Функція `setlogmask()` надає можливість відфільтровувати повідомлення за рівнем важливості безпосередньо в процесі користувача. Якщо рівень важливості повідомлення не відповідає встановленій масці, функція `syslog()` миттєво повертає керування, не витрачаючи ресурси на форматування рядка та системні виклики запису в сокет.

- `setlogmask(maskpri)` приймає бітову маску дозволених пріоритетів і повертає попередньо встановлене значення маски.
- Якщо передати аргумент `0`, поточна маска не змінюється, а функція лише повертає поточний стан фільтра.

Для побудови бітових масок у заголовочному файлі `<syslog.h>` визначено наступні макроси:
- `LOG_MASK(pri)` — створює маску для одного конкретного рівня важливості (наприклад, `LOG_MASK(LOG_ERR)`).
- `LOG_UPTO(pri)` — створює маску для всіх рівнів від найвищого `LOG_EMERG` до вказаного `pri` включно.

```text
// Дозволити проходження лише повідомлень рівня Warning, Error, Crit, Alert та Emerg:
setlogmask(LOG_UPTO(LOG_WARNING));
```

## Допоміжні макроси та розбирання пріоритету

Заголовочний файл `<syslog.h>` містить макроси для конструювання та зворотного витягнення полів із комбінованого пріоритету:

- `LOG_MAKEPRI(fac, pri)` — конструює значення пріоритету із заданої категорії `fac` та важливості `pri`.
- `LOG_FAC(pri)` — витягує код категорії (Facility) із пріоритету (виконує операцію `(pri >> 3) & 0x1f`).
- `LOG_PRI(pri)` — витягує код важливості (Severity) із пріоритету (виконує операцію `pri & 0x07`).

## Багатопотоковість, Сигнальна Безпека та Внутрішній Механізм glibc

Під час розробки системного програмного забезпечення важливе значення мають особливості поведінки `syslog()` у багатопотокових середовищах та обробниках сигналів POSIX.

### 1. Багатопотокова безпека (Thread Safety)

Виклик `syslog()` у сучасній GNU C Library (glibc) є **потокобезпечним (thread-safe)**. Всередині C-бібліотека захищає внутрішні змінні (файловий дескриптор сокета та параметри) за допомогою внутрішнього м'ютекса. Кілька паралельних потоків виконання можуть одночасно викликати `syslog()`, і libc послідовно відправить усі повідомлення у сокет без псування даних.

Проте виклик `openlog()` та `setlogmask()` змінює глобальний стан логера для всього процесу. Зміна ідентифікатора `ident` під час роботи інших потоків може призвести до стану гонитви (race condition). Тому ініціалізацію `openlog()` слід виконувати в головному потоці програми до створення додаткових робочих thread'ів.

### 2. Сигнальна безпека (Async-Signal Safety)

Функція `syslog()` **НЕ є асинхронно сигнально-безпечною (async-signal-safe)**. Це означає, що її категорично заборонено викликати всередині обробників сигналів Linux (Signal Handlers, наприклад для `SIGSEGV`, `SIGTERM`, `SIGINT`).

Причини відсутності сигнальної безпеки:
1. `syslog()` використовує внутрішні блокування (mutexes). Якщо сигнал перерве потік у момент, коли той утримував м'ютекс логера, і обробник сигналу спробує викликати `syslog()`, виникне взаємне блокування (Deadlock).
2. `syslog()` може виконувати динамічне виділення пам'яті (`malloc`) під час форматування великих рядків, що також заборонено в обробниках сигналів.

Для безпечного логування з обробників сигналів слід використовувати прямий системний виклик `write()` у заздалегідь відкритий файловий дескриптор або записувати дані в атомарний кільцевий буфер (lock-free ring buffer), який зчитується основним потоком програми.

### 3. Внутрішній механізм роботи libc під капотом

Коли програма викликає `syslog(LOG_ERR, "Message")`, білотека виконує наступні кроки:
1. Перевіряє маску `setlogmask`. Якщо пріоритет відфільтровано, функція відразу повертає керування.
2. Захоплює внутрішній м'ютекс логера.
3. Якщо сокет не відкритий, виконує системний виклик `socket(AF_UNIX, SOCK_DGRAM, 0)` та підключається до сокета `/dev/log` за допомогою `connect()`.
4. Форматує підсумковий рядок, додаючи пріоритет у кутових дужках `<PRIVAL>`, мітку часу, ідентифікатор програми та PID.
5. Записує рядок у сокет за допомогою системного виклику `send()` або `write()`.
6. Звільняє м'ютекс та повертає керування.

## Таблиця числових констант

У заголовочному файлі `<syslog.h>` визначено наступні числові константи для категорій та рівнів важливості:

### Категорії (Facility):
- `LOG_KERN` (0): Повідомлення ядра ОС.
- `LOG_USER` (1): Загальні користувацькі програми (дефолт).
- `LOG_MAIL` (2): Поштова підсистема.
- `LOG_DAEMON` (3): Системні фонові демони.
- `LOG_AUTH` (4): Служби автентифікації.
- `LOG_SYSLOG` (5): Внутрішній вивід syslogd.
- `LOG_LPR` (6): Підсистема друку.
- `LOG_NEWS` (7): Служби USENET.
- `LOG_UUCP` (8): Підсистема UUCP.
- `LOG_CRON` (9): Планувальник cron.
- `LOG_AUTHPRIV` (10): Захищена автентифікація з чутливими даними.
- `LOG_FTP` (11): FTP-служба.
- `LOG_LOCAL0` .. `LOG_LOCAL7` (16..23): Зарезервовані локальні категорії.

### Важливість (Severity):
- `LOG_EMERG` (0): Фатальна аварія системи.
- `LOG_ALERT` (1): Потрібна негайна дія.
- `LOG_CRIT` (2): Критичний стан.
- `LOG_ERR` (3): Помилка виконання.
- `LOG_WARNING` (4): Попередження.
- `LOG_NOTICE` (5): Важлива нормальна подія.
- `LOG_INFO` (6): Інформаційне повідомлення.
- `LOG_DEBUG` (7): Налагоджувальний вивід.

```c
/* Приклад використання Syslog C API */
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <syslog.h>

int main(void) {
    /* Ініціалізуємо підключення: додаємо PID та виводимо на stderr у разі потреби */
    openlog("demo_service", LOG_PID | LOG_PERROR, LOG_DAEMON);

    /* Налаштовуємо маску: ігноруємо LOG_DEBUG */
    setlogmask(LOG_UPTO(LOG_INFO));

    syslog(LOG_INFO, "Службу успішно запущено.");

    FILE *f = fopen("/nonexistent/file.txt", "r");
    if (!f) {
        /* %m автоматично підставить опис errno (strerror) */
        syslog(LOG_ERR, "Не вдалося відкрити конфігураційний файл: %m");
    }

    /* Це повідомлення буде відфільтровано на боці клієнта функцією setlogmask */
    syslog(LOG_DEBUG, "Це налагоджувальне повідомлення не потрапить у лог.");

    closelog();
    return 0;
}
```

```cpp
// Приклад ідіоматичної C++ обгортки (RAII Logger) над Syslog API
#include <syslog.h>
#include <string_view>
#include <string>
#include <format>
#include <utility>

class SyslogLogger {
public:
    enum class Facility : int {
        User     = LOG_USER,
        Daemon   = LOG_DAEMON,
        AuthPriv = LOG_AUTHPRIV,
        Local0   = LOG_LOCAL0
    };

    enum class Level : int {
        Emerg   = LOG_EMERG,
        Alert   = LOG_ALERT,
        Crit    = LOG_CRIT,
        Error   = LOG_ERR,
        Warning = LOG_WARNING,
        Notice  = LOG_NOTICE,
        Info    = LOG_INFO,
        Debug   = LOG_DEBUG
    };

    explicit SyslogLogger(std::string ident, 
                         Facility facility = Facility::Daemon, 
                         int options = LOG_PID)
        : m_ident(std::move(ident)) 
    {
        // openlog очікує вказівник на статичну пам'ять або об'єкт, який живе до closelog.
        // Зберігаємо рядок у полі класу m_ident.
        ::openlog(m_ident.c_str(), options, static_cast<int>(facility));
    }

    ~SyslogLogger() {
        ::closelog();
    }

    // Забороняємо копіювання, щоб уникнути подвійного closelog
    SyslogLogger(const SyslogLogger&) = delete;
    SyslogLogger& operator=(const SyslogLogger&) = delete;

    SyslogLogger(SyslogLogger&&) noexcept = default;
    SyslogLogger& operator=(SyslogLogger&&) noexcept = default;

    void set_max_level(Level max_level) noexcept {
        ::setlogmask(LOG_UPTO(static_cast<int>(max_level)));
    }

    template <typename... Args>
    void log(Level level, std::string_view fmt_str, Args&&... args) const {
        std::string message = std::vformat(fmt_str, std::make_format_args(args...));
        ::syslog(static_cast<int>(level), "%s", message.c_str());
    }

    template <typename... Args>
    void info(std::string_view fmt_str, Args&&... args) const {
        log(Level::Info, fmt_str, std::forward<Args>(args)...);
    }

    template <typename... Args>
    void error(std::string_view fmt_str, Args&&... args) const {
        log(Level::Error, fmt_str, std::forward<Args>(args)...);
    }

private:
    std::string m_ident;
};

int main() {
    SyslogLogger logger("cpp_service", SyslogLogger::Facility::Daemon, LOG_PID | LOG_PERROR);
    logger.set_max_level(SyslogLogger::Level::Info);

    logger.info("Службу C++ запущено. Порт: {}", 8080);
    logger.error("Виникла помилка з'єднання з ВБ: {}", "Connection refused");

    return 0;
}
```
