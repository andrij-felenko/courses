# Трасування системних викликів: ptrace, seccomp й перехоплення входів/виходів

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Трасування системних викликів — це один із найважливіших механізмів в операційних системах сімейства Unix та Linux, який дозволяє зовнішньому процесу (tracer) спостерігати та контролювати виконання іншого процесу (tracee). Завдяки трасуванню можна аналізувати поведінку програм, створювати інструменти налагодження (наприклад, gdb та strace), перехоплювати системні виклики та навіть змінювати їхню поведінку.

У цій статті ми детально розглянемо механізми `ptrace`, точки перехоплення `sys_enter` та `sys_exit`, можливості модифікації викликів через `PTRACE_SET_SYSCALL`, продуктивність такого трасування, а також сучасні альтернативи, такі як `seccomp user notification` (`SECCOMP_RET_USER_NOTIF`).

## Механізм ptrace

`ptrace` (process trace) — це системний виклик у Unix-подібних системах, який надає процесу-трасувальнику можливість спостерігати та керувати виконанням іншого процесу. Трасувальник може читати та записувати пам'ять і регістри трасованого процесу, а також перехоплювати сигнали та системні виклики.

### Основи роботи з ptrace

Для початку трасування процес може використовувати команду `PTRACE_TRACEME`, щоб дозволити своєму батьківському процесу трасувати його, або ж батьківський процес може приєднатися до вже існуючого процесу за допомогою `PTRACE_ATTACH`.

```c
#include <sys/ptrace.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    pid_t pid = fork();

    if (pid == 0) {
        // Дочірній процес: дозволяємо трасування
        ptrace(PTRACE_TRACEME, 0, NULL, NULL);
        execl("/bin/ls", "ls", NULL);
    } else {
        // Батьківський процес: чекаємо зупинки дочірнього
        wait(NULL);
        // ... подальше трасування ...
    }
    return 0;
}
```

### PTRACE_SYSCALL та перехоплення викликів

Коли процес трасується, трасувальник може використовувати команду `PTRACE_SYSCALL`, щоб відновити виконання трасованого процесу, але змусити його зупинитися при наступному вході до системного виклику або виході з нього. Це є основою роботи таких утиліт, як `strace`.

При кожному системному виклику генеруються дві зупинки:
1. **`sys_enter`**: Процес зупиняється безпосередньо перед виконанням системного виклику. На цьому етапі трасувальник може прочитати аргументи виклику, які знаходяться в регістрах процесора, та навіть змінити їх або номер виклику.
2. **`sys_exit`**: Процес зупиняється після завершення системного виклику, але перед поверненням у простір користувача. Трасувальник може перевірити результат виконання (код повернення) і за потреби змінити його.

Коли трасований процес зупиняється, ядро надсилає йому сигнал `SIGTRAP`. Трасувальник отримує сповіщення через системний виклик `waitpid` і може проаналізувати стан процесу, використовуючи команди `PTRACE_GETREGS` (для читання регістрів) та `PTRACE_PEEKDATA` (для читання пам'яті).

### Модифікація викликів: PTRACE_SET_SYSCALL

Однією з потужних можливостей `ptrace` є здатність змінювати номер системного виклику, який має виконатися, використовуючи команду `PTRACE_SET_SYSCALL_INFO` (або просто записуючи нове значення в регістр, що містить номер виклику, через `PTRACE_SETREGS`). Це дозволяє, наприклад, замінити виклик `open` на `openat` або взагалі скасувати виконання виклику, замінивши його на неіснуючий номер (наприклад, -1).

Щоб скасувати системний виклик і повернути власний результат, трасувальник може:
1. Зупинити процес на `sys_enter`.
2. Змінити номер системного виклику на неіснуючий (щоб ядро нічого не робило).
3. Продовжити виконання до `sys_exit`.
4. На `sys_exit` записати власний код повернення в регістр результату.

### Продуктивність ptrace

Хоча `ptrace` є потужним інструментом, його головним недоліком є **продуктивність**. Трасування системних викликів через `ptrace` вносить значні накладні витрати:
- Кожен системний виклик призводить до двох додаткових перемикань контексту (context switches) на `sys_enter` та ще двох на `sys_exit`.
- Трасувальник повинен постійно викликати `waitpid` та `ptrace` для читання регістрів/пам'яті та продовження виконання.
- Для багатониткових програм `ptrace` може стати серйозним "вузьким місцем", оскільки кожен потік зупинятиметься і чекатиме на обробку трасувальником.

Через ці накладні витрати `ptrace` зазвичай не використовується в production-середовищах для постійного моніторингу або перехоплення I/O, а застосовується переважно для налагодження та розробки інструментів.

## Seccomp User Notification

Для вирішення проблем із продуктивністю та безпекою, пов'язаних із `ptrace`, у ядрі Linux з'явився новий механізм: **Seccomp User Notification** (`SECCOMP_RET_USER_NOTIF`).

`seccomp` (secure computing mode) — це механізм ізоляції, який дозволяє процесу обмежити набір системних викликів, які він може виконувати. Використовуючи BPF (Berkeley Packet Filter), можна створювати складні правила фільтрації системних викликів.

Традиційно `seccomp` міг лише дозволити (`SECCOMP_RET_ALLOW`), заборонити з помилкою (`SECCOMP_RET_ERRNO`) або вбити процес (`SECCOMP_RET_KILL`) при спробі виконати виклик. З додаванням `SECCOMP_RET_USER_NOTIF` з'явилася можливість перенаправляти обробку системного виклику до іншого процесу (супервізора) у просторі користувача.

### Як працює SECCOMP_RET_USER_NOTIF

1. Процес встановлює фільтр `seccomp`, який повертає `SECCOMP_RET_USER_NOTIF` для певних системних викликів.
2. При встановленні фільтра ядро повертає файловий дескриптор (notification fd).
3. Супервізор читає з цього дескриптора. Коли процес виконує системний виклик, що підпадає під правило `USER_NOTIF`, він блокується, а ядро надсилає повідомлення супервізору.
4. Супервізор обробляє запит, виконує необхідні дії (наприклад, віртуалізує доступ до файлу або перехоплює мережевий запит) і надсилає відповідь (результат системного виклику) назад через той самий файловий дескриптор.
5. Заблокований процес розблоковується та отримує результат, ніби системний виклик був виконаний ядром.

### Переваги над ptrace

Механізм `seccomp user notification` має значні переваги порівняно з `ptrace`:
- **Продуктивність**: Зупиняються лише ті системні виклики, які дійсно потрібно перехопити, відповідно до BPF-фільтра. Інші виклики виконуються з нульовими накладними витратами.
- **Безпека**: Не потрібно надавати трасувальнику повний контроль над процесом, як це робить `ptrace`. Супервізор може лише обробляти конкретні системні виклики.
- **Гнучкість**: Це ідеальний механізм для побудови пісочниць (sandboxes), контейнерних середовищ та віртуалізації системних викликів на рівні користувача (наприклад, перехоплення звернень до `/sys` або `/proc` всередині контейнера без привілеїв root).

### Перехоплення входів/виходів (I/O Interception)

І `ptrace`, і `seccomp user notification` можуть використовуватися для перехоплення операцій вводу/виводу. Однак для високонавантажених I/O операцій обидва підходи можуть виявитися занадто повільними через постійні переходи між ядром та простором користувача (user-space).

Для ефективного перехоплення I/O в сучасних системах Linux частіше використовують технології, засновані на **eBPF** (extended BPF), які дозволяють виконувати логіку перехоплення безпосередньо в ядрі без перемикання контексту, або інструменти на кшталт `io_uring` для асинхронного та високоефективного I/O, де перехоплення може здійснюватися на рівні кільцевих буферів (ring buffers). Тим не менш, для задач емуляції, віртуалізації та побудови пісочниць `seccomp user notif` залишається найкращим вибором.

## Висновок

Трасування системних викликів пройшло довгий шлях від універсального, але повільного `ptrace` до гнучкого та цілеспрямованого `seccomp user notification`. Розуміння цих механізмів, їхніх точок входу (`sys_enter`, `sys_exit`) та можливостей модифікації (`PTRACE_SET_SYSCALL`) є критично важливим для розробки інструментів аналізу, налагодження та безпеки в операційних системах Linux. Вибір між цими інструментами залежить від конкретної задачі: `ptrace` для глибокого налагодження, а `seccomp` для безпечної віртуалізації та створення пісочниць.
