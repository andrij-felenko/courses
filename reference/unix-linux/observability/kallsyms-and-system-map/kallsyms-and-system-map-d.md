# kallsyms: імена символів усередині ядра, System.map і %pS

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У світі розробки та зневадження ядра Linux розробник постійно має справу з адресами пам'яті. Коли ядро стикається з критичною помилкою (Oops або Panic), воно виводить дамп регістрів та стек викликів (call trace), де функції представлені у вигляді шістнадцяткових адрес, таких як `0xffffffff81123456`. Самостійно шукати ці адреси у вихідному коді вкрай незручно, тому ядро Linux має спеціальну підсистему **kallsyms**, яка дозволяє відображати адреси на імена функцій та змінних.

Цей розділ довідника детально розглядає архітектуру та використання `kallsyms`, статичний файл `System.map`, функцію програмного пошуку `kallsyms_lookup_name()`, а також форматування виводу за допомогою `printk` специфікаторів `%pS` та `%B`.

## 1. System.map: Статичне відображення символів

Файл `System.map` — це статичний текстовий файл, який містить таблицю символів ядра Linux. Він генерується під час збірки ядра утилітою `nm` (частина GNU binutils), яка аналізує скомпільований файл `vmlinux` і витягує з нього адреси всіх глобальних та локальних символів.

### Формат System.map
Кожен рядок у файлі `System.map` має такий формат:
```
<адреса> <тип_символу> <ім'я_символу>
```
Наприклад:
```
ffffffff81000000 T _stext
ffffffff81000100 t startup_64
ffffffff81001500 T do_one_initcall
ffffffff82c00000 B _end
```
Де тип символу кодується однією літерою:
- **T/t**: Текст (код). Великі літери — глобальні символи, малі — локальні (static).
- **D/d**: Ініціалізовані дані.
- **B/b**: Неініціалізовані дані (BSS).
- **R/r**: Дані лише для читання (Read-only data).
- **A**: Абсолютне значення (не змінюється при завантаженні).

### Для чого потрібен System.map?
Історично, `System.map` використовувався утилітою `klogd` для перекладу адрес, що виводилися ядром у `dmesg`, в імена функцій перед записом у системний журнал. Коли ставався Oops, ядро просто друкувало адреси (бо не мало kallsyms всередині), а користувацький простір брав на себе задачу резолвінгу за допомогою `System.map`.
Сьогодні ядро (якщо сконфігуровано з `CONFIG_KALLSYMS=y`) самостійно виконує резолвінг під час друку повідомлень, тому `System.map` втратив своє ключове значення для користувача, але досі використовується деякими системними інструментами, такими як `perf`, `crash` та `systemtap`, якщо `/proc/kallsyms` недоступний або потрібно працювати з дампами (vmcore).

## 2. /proc/kallsyms: Динамічна таблиця символів

Опція конфігурації ядра `CONFIG_KALLSYMS=y` (зазвичай увімкнена в усіх сучасних дистрибутивах) вбудовує таблицю символів безпосередньо у бінарний файл ядра. Це дозволяє ядру самостійно розпізнавати, до якої функції належить певна адреса, без доступу до зовнішнього файлу `System.map`.

Інтерфейс простору користувача до цієї вбудованої таблиці експортується через віртуальний файл `/proc/kallsyms`.

### Відмінності між System.map та /proc/kallsyms
1. **Динамічність**: `/proc/kallsyms` містить не лише символи з основного образу ядра (vmlinux), але й символи з динамічно завантажених модулів ядра (наприклад, `ext4.ko`). `System.map` модулів не містить.
2. **Формат**: У `/proc/kallsyms` навпроти символів, що належать модулям, у квадратних дужках вказується ім'я модуля. Наприклад:
   ```
   ffffffffc0201000 t ext4_mkdir [ext4]
   ```
3. **Обмеження доступу**: Заради безпеки, щоб ускладнити атаки з поверненням на ядро (ROP) та обійти KASLR (Kernel Address Space Layout Randomization), значення адрес у `/proc/kallsyms` часто приховуються для звичайних користувачів. Якщо параметр sysctl `kernel.kptr_restrict` дорівнює `1` (або `2`), усі адреси будуть виводитися як нулі:
   ```
   0000000000000000 T sys_open
   ```
   Лише root (користувач з `CAP_SYSLOG`) може бачити справжні адреси (при `kptr_restrict=1`).

### Опція CONFIG_KALLSYMS_ALL
За замовчуванням `kallsyms` включає лише функції (текст) та, можливо, деякі важливі змінні. Якщо ядро зібране з опцією `CONFIG_KALLSYMS_ALL=y`, таблиця буде містити абсолютно всі символи, включаючи всі глобальні та статичні змінні. Це значно збільшує розмір ядра (приблизно на кілька мегабайтів), але дає повну інформацію при зневадженні.

## 3. Програмний інтерфейс: kallsyms_lookup_name()

Коли розробник пише модуль ядра і йому потрібно отримати адресу неекспортованої функції (функції, яка не має макроса `EXPORT_SYMBOL`), він може спробувати знайти її динамічно за іменем. Для цього слугує функція `kallsyms_lookup_name()`.

```c
#include <linux/kallsyms.h>

unsigned long addr;
addr = kallsyms_lookup_name("sys_call_table");
if (addr) {
    pr_info("Found sys_call_table at 0x%lx\n", addr);
}
```

### Зміни в ядрі 5.7+
Важливо зазначити, що у версії ядра Linux 5.7 функція `kallsyms_lookup_name()` була **деекспортована** (видалено `EXPORT_SYMBOL_GPL`). Це означає, що модулі ядра більше не можуть безпосередньо викликати її для пошуку довільних функцій. Цей крок був зроблений з метою безпеки, щоб перешкодити руткітам (rootkits) і шкідливим модулям ядра легко знаходити внутрішні структури, такі як `sys_call_table`, та хукати їх.

Сучасні легітимні модулі (наприклад, `kprobes`, `ftrace`, або `bpf`) мають власні, контрольовані ядром API для підключення до неекспортованих функцій.

### Функція kallsyms_lookup()
Існує також зворотна функція, яка дозволяє отримати ім'я за адресою (хоча вона використовується переважно самим ядром для форматування логів):

```c
const char *kallsyms_lookup(unsigned long addr,
                            unsigned long *symbolsize,
                            unsigned long *offset,
                            char **modname, char *namebuf);
```

## 4. Специфікатори printk: %pS, %pB та інші

При написанні повідомлень у лог ядра через `printk` або `pr_info`, ядро надає спеціальні розширення специфікатора формату `%p` (pointer), які автоматично використовують підсистему kallsyms для перетворення адреси на зрозумілий рядок. Це значно полегшує зневадження, оскільки замість "магічних" чисел ми бачимо імена функцій.

Найбільш використовувані специфікатори для символів:

- **`%pS`** (Symbol): Виводить ім'я символу, а також зміщення (offset) всередині функції та її загальний розмір. Якщо символ належить модулю, також виводить ім'я модуля.
  *Приклад виводу:* `vfs_read+0x43/0x140`
  *Використання:* `pr_info("Called from %pS\n", __builtin_return_address(0));`

- **`%ps`** (symbol): Те ж саме, що й `%pS`, але виводить лише ім'я символу, без зміщення та розміру.
  *Приклад виводу:* `vfs_read`

- **`%pF` / `%pf`** (Function descriptor): Використовується на архітектурах, де покажчик на функцію є не прямою адресою коду, а покажчиком на дескриптор функції (наприклад, IA64, PPC64). На архітектурах x86 та ARM він поводиться ідентично до `%pS` / `%ps`. У сучасних ядрах використання `%pF` здебільшого замінено на `%pS`.

- **`%pB`** (Backtrace): Використовується спеціально для виводу елементів стека викликів (stack trace). Забезпечує форматування, оптимізоване для читабельності стеків.
  *Приклад:* `printk("%pB\n", (void *)address);`

- **`%pSR`** (Symbol Raw): Виводить "сире" (raw) ім'я символу, без жодних префіксів модуля чи зміщень, корисне для машинної обробки.

### Як це працює з KASLR?
При використанні `%pS` ядро самостійно компенсує зсув адрес, викликаний KASLR. Навіть якщо базову адресу ядра було рандомізовано при завантаженні, `printk("%pS", addr)` все одно правильно відобразить `function_name+offset`, оскільки `kallsyms` знає рандомізовану розкладку в пам'яті.

## 5. Декодування зміщень інструкцій при Oops (Oops decoding)

Коли стається збій у ядрі, на екран (і в логи) виводиться Oops або Kernel Panic. Ключовою частиною цього дампу є Call Trace. Рядки в Call Trace виглядають так:

```
Call Trace:
 <TASK>
 ? __die+0x23/0x70
 ? page_fault_oops+0x171/0x4e0
 ? do_user_addr_fault+0x63/0x6b0
 ...
 vfs_read+0x43/0x140
 ksys_read+0x5f/0xe0
 do_syscall_64+0x3b/0x90
 entry_SYSCALL_64_after_hwframe+0x63/0xcd
 </TASK>
```

Розберемо рядок `vfs_read+0x43/0x140`:
- **`vfs_read`**: Ім'я функції (символ), де сталась помилка або звідки був зроблений виклик.
- **`0x43`**: Зміщення (offset) в байтах від початку функції до конкретної машинної інструкції, яка виконувалася.
- **`0x140`**: Загальний розмір функції `vfs_read` у байтах.

### Чому зміщення (0x43) настільки важливе?
Знати, в якій функції сталась помилка, часто недостатньо, адже функція може бути довгою (наприклад, 1000 байт), і в ній може бути десяток місць, де відбувається розіменування покажчика. Щоб знайти точний рядок у вихідному коді (C), потрібно декодувати це зміщення.

### Як декодувати зміщення в рядок коду (C)

Існує кілька способів перетворити вивід `%pS` на точний рядок коду, за умови, що у вас є файл `vmlinux` із відладочною інформацією (збудований з `CONFIG_DEBUG_INFO=y`).

#### 1. Утиліта addr2line
Ви не можете передати `addr2line` безпосередньо адресу з логів, якщо ввімкнено KASLR, оскільки адреса в логах є рандомізованою, а `vmlinux` на диску не рандомізований. Але ви можете вирахувати статичну адресу!

Ви знаєте, що помилка сталася на зміщенні `0x43` у функції `vfs_read`.
Знайдіть базову адресу `vfs_read` у вашому локальному (не рандомізованому) `vmlinux`:
```bash
$ nm vmlinux | grep vfs_read
ffffffff81234000 T vfs_read
```
Додайте зміщення до базової адреси: `0xffffffff81234000 + 0x43 = 0xffffffff81234043`.
Викличте `addr2line`:
```bash
$ addr2line -e vmlinux ffffffff81234043
fs/read_write.c:450
```

#### 2. gdb (GNU Debugger)
Можна використовувати `gdb` для дисасемблювання функції і пошуку потрібного місця.

```bash
$ gdb vmlinux
(gdb) list *(vfs_read+0x43)
0xffffffff81234043 is in vfs_read (fs/read_write.c:450).
445     }
446
447     ret = rw_verify_area(READ, file, pos, count);
448     if (ret >= 0) {
449         count = ret;
450         if (file->f_op->read)
451             ret = file->f_op->read(file, buf, count, pos);
452         else
```

#### 3. faddr2line та scripts/decode_stacktrace.sh
В дереві вихідних кодів ядра є готові скрипти для автоматизації цього процесу:
- `scripts/faddr2line`: Дозволяє передати йому символ і зміщення у форматі з Oops:
  ```bash
  $ ./scripts/faddr2line vmlinux vfs_read+0x43/0x140
  vfs_read+0x43/0x140:
  vfs_read at fs/read_write.c:450
  ```
- `scripts/decode_stacktrace.sh`: Цей скрипт може розпарсити весь лог `dmesg` з Oops-ом і автоматично декодувати всі рядки Call Trace.
  ```bash
  $ ./scripts/decode_stacktrace.sh vmlinux < oops.log
  ```

## Висновки

1. **System.map** є застарілим механізмом для сучасного розробника (через KASLR та вбудовані засоби ядра), але корисний для інструментарію поза живим ядром (vmcore).
2. **/proc/kallsyms** та `CONFIG_KALLSYMS=y` роблять ядро самодостатнім у відображенні власних адрес та адрес модулів.
3. Функції на зразок `kallsyms_lookup_name()` корисні для динамічного зв'язування, але їх використання суворо обмежене в останніх версіях ядра з міркувань безпеки.
4. Специфікатор формату **`%pS`** є незамінним для виводу зрозумілих логів та Call Trace.
5. Запис вигляду `func+offset/size` легко перетворюється на точний рядок у вихідному файлі C за допомогою утиліт `addr2line` або `gdb`, що робить зневадження збоїв ядра значно швидшим.
