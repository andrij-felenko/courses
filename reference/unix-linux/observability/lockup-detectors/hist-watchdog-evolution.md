# 📜 Еволюція сторожових механізмів у ядрі Linux

Сьогодні інженери сприймають автоматичне виявлення завислих ядер, виведення трасування викликів `Call Trace` у `dmesg` та аварійне перезавантаження через `kdump` як належне. Проте на ранніх етапах розвитку ядра Linux будь-яка помилка синхронізації — зациклення у спинлоку, некоректне вимкнення переривань чи нескінченне очікування відповіді від периферійного пристрою — призводила до раптового й повністю безмовного паралічу комп'ютера. Екран застигав, клавіатура переставала реагувати на `CapsLock`, а мережевий стек припиняв відповідати на пакети `ping`. Жодного журналу, коду помилки чи стека не залишалося, перетворюючи пошук несправності на багатогодинне читання коду навпомацки.

Цей історичний екскурс розкриває шлях від примітивних апаратних плат розширення ISA до сучасної багаторівневої системи сторожових наглядачів на основі немаскованих переривань та підсистеми `perf`.

---

## 1. Ера апаратних карт і наївних таймерів (1990-ті роки)

Першим підходом до боротьби із зависаннями серйозних серверів на базі Linux було використання зовнішніх апаратних плат із власними кварцовими генераторами та цифровими таймерами зворотного відліку (Watchdog Timer Cards). Такі плати встановлювалися в шину ISA або PCI та підключалися безпосередньо до лінії апаратного скидання материнської плати (`RESET#`).

Ядро Linux отримало інтерфейс `/dev/watchdog` (драйвери типу `wdt.c`, `pcwd.c`, а згодом `iTCO_wdt` для південних мостів Intel). Процес простору користувача або ядерний таймер мусив періодично записувати довільний байт у файл пристрою (`"pinging the dog"`):

:::tabs
```c
/* Типовий код "годування собаки" у просторі користувача 1990-х (C/POSIX) */
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("/dev/watchdog", O_WRONLY);
    if (fd < 0) return 1;
    while (1) {
        write(fd, "\0", 1);
        sleep(10);
    }
    close(fd);
    return 0;
}
```
```cpp
// Періодичне надсилання сигналу активності у сторожовий таймер (C++20)
#include <fstream>
#include <thread>
#include <chrono>

using namespace std::chrono_literals;

int main() {
    std::ofstream watchdog("/dev/watchdog");
    if (!watchdog.is_open()) return 1;

    while (true) {
        watchdog.put('\0');
        watchdog.flush();
        std::this_thread::sleep_for(10s);
    }
    return 0;
}
```
:::

Якщо протягом заданого інтервалу (наприклад, 60 секунд) запис не відбувався, апаратний таймер доходив до нуля і замикав контакти апаратного перезавантаження.

### Фундаментальна вада на SMP-системах
Із появою багатопроцесорних систем (SMP) у кінці 1990-х років ця схема виявилася безпорадною:
- Якщо ядро CPU#1 намертво застрягало у взаємному блокуванні в драйвері SCSI-контролера з вимкненими перериваннями, ядро CPU#0 продовжувало виконувати планувальник та успішно оновлювало таймер у `/dev/watchdog`.
- Зовнішній апаратний таймер «бачив», що операційна система нібито жива, тоді як половина системних служб переставала функціонувати через завислі черги запитів до диска.

Стало очевидно: нагляд за станом окремих ядер CPU має відбуватися зсередини самого ядра та на рівні кожного логічного процесора окремо.

## 2. Поява NMI Watchdog для x86 (Linux 2.4 – 2.6)

У ядрі Linux 2.4 розробники звернулися до внутрішніх блоків процесорів Intel Pentium Pro та AMD Athlon — контролерів переривань **Local APIC** (Advanced Programmable Interrupt Controller) та таймерів **IO-APIC**.

Головною проблемою діагностики апаратних зависань була інструкція `cli` (`local_irq_disable()`): коли код ядра маскував звичайні масковані переривання (INTR), процесор ігнорував будь-які регулярні таймери. Єдиним апаратним механізмом, який процесор x86 зобов'язаний виконати навіть за наявності `cli`, було **немасковане переривання (NMI — Non-Maskable Interrupt)**.

Розробники запрограмували таймер Local APIC або лічильник циклів CPU так, щоб він періодично (100–1000 разів на секунду) генерував вектор NMI (Vector 2 в IDT):
- Під час кожного NMI процесор примусово переривав виконання будь-якого потоку (навіть усередині мертвого циклу зі `spin_lock_irqsave()`) і переходив на обробник ядра.
- Обробник перевіряв, чи зростає лічильник звичайних переривань ядра (`irq_stat[cpu].irq_count`).
- Якщо за певний проміжок часу лічильник звичайних переривань не змінився, ядро робило висновок: переривання заблоковані занадто довго, фіксувало Hard Lockup та друкувало повний дамп регістрів на послідовну консоль.

### Проблеми ранньої реалізації:
1. **Боротьба за ресурси APIC:** NMI Watchdog ділив апаратні канали з профайлерами того часу (такими як OProfile). Увімкнення профілювання вимикало захист від зависань.
2. **Архітектурна фрагментація:** Код був жорстко прив'язаний до x86. На інших архітектурах (SPARC, PowerPC, ARM) механізм взагалі не працював або вимагав написання власного складного апаратного коду з нуля.

## 3. Детектор Soft Lockup Інґо Молнара (Linux 2.6.12+)

Хоча NMI Watchdog відмінно виявляв зависання з вимкненими IRQ, незабаром з'явився інший клас збоїв: **Soft Lockup**.
У цьому сценарії апаратні переривання залишалися увімкненими, таймери ядра регулярно цокали, проте код у режимі ядра захоплював `spinlock` або входив у довгий обчислювальний цикл, повністю вимикаючи витіснення (preemption) і не викликаючи функцію `schedule()`. Звичайні процеси користувача повністю голодували.

У 2005 році провідний архітектор ядра **Інґо Молнар (Ingo Molnar)** розробив концепцію програмного наглядача Soft Lockup:
- На кожному логічному ядрі процесора було створено окремий ядерний потік `[watchdog/K]` із найвищим пріоритетом реального часу `SCHED_FIFO 99`.
- Єдиним завданням цього потоку було періодичне оновлення позначки часу (`watchdog_touch_ts`).
- Високоточний таймер ядра (`hrtimer`) перевіряв, скільки часу минуло від останнього запуску потоку.
- Якщо потік не отримував управління протягом 10–20 секунд, це однозначно свідчило про те, що якийсь низькорівневий код монополізував ядро без віддачі CPU.

Цей механізм став справжнім проривом для стабільності дистрибутивів Enterprise Linux (RHEL, SLES, Debian), оскільки вперше дозволив локалізувати баги драйверів мережі та пам'яті, які раніше списували на "загадкові зависання заліза".

## 4. Велика уніфікація через `perf_event` (Linux 2.6.38 – 3.x)

До початку 2010-х років ядро Linux мало два абсолютно різних, не узгоджених між собою кодових дерева для сторожових таймерів: Soft Lockup на основі kthreads та хаотичний x86-специфічний NMI Watchdog.

У релізі **Linux 2.6.38** Дон Зікус (Don Zickus) за активної підтримки Інґо Молнара та Петера Зійлстри (Peter Zijlstra) здійснив повне переписування підсистеми (`kernel/watchdog.c`):
- Замість прямих низькорівневих маніпуляцій з регістрами MSR та Local APIC, Hard Lockup Detector було переведено на стандартну підсистему лічильників продуктивності процесора — **`perf_event`**.
- Ядро створювало внутрішній ядерний лічильник `PERF_COUNT_HW_CPU_CYCLES` через виклик `perf_event_create_kernel_counter()`, налаштований на генерацію апаратного сигналу переповнення.
- Це дозволило автоматично поширити підтримку Hard Lockup на будь-яку архітектуру, що має підтримку підсистеми `perf` (включно з ARM64 та PowerPC), та об'єднати Soft Lockup і Hard Lockup під єдиним інтерфейсом параметрів `/proc/sys/kernel/watchdog_*`.

## 5. Поява детектора завислих процесів `khungtaskd`

Останнім важливим елементом мозаїки стало створення детектора завислих задач — **Hung Task Detector**.
Адміністратори баз даних стикалися з ситуацією, коли процесори сервера були завантажені лише на 1%, апаратні переривання працювали, Soft/Hard Lockup детектори мовчали, проте СУБД MySQL чи PostgreSQL раптово припиняла відповідати.

Причиною було зависання процесів у стані `TASK_UNINTERRUPTIBLE` (D-state) під час очікування відповіді від мертвого сервера NFS або несправного SSD-диска. Оскільки потік у D-state не споживає такти CPU, таймери watchdog не фіксували проблеми.

Для вирішення цього завдання було впроваджено окремий демон ядра **`khungtaskd`**, який періодично сканував таблицю задач і порівнював лічильники перемикань контексту (`nvcsw + nivcsw`), виводячи повідомлення про задачі, заблоковані довше 120 секунд.

## 6. Сучасний стан: віртуалізація та хмарні виклики

У сучасних ядрах Linux 5.x – 6.x детектори зависань зіткнулися з новою реальністю: **хмарними середовищами та контейнеризацією**.
- **Проблема vCPU Steal Time:** Коли фізичний сервер перевантажений, гіпервізор (KVM або ESXi) може забрати фізичний процесор у віртуальної машини на 15–30 секунд. Гостьове ядро після повернення процесора вважало, що сталося Hard Lockup, і помилково викидало паніку.
- Для вирішення цього було впроваджено інтеграцію з інтерфейсом пара-віртуалізації `pvclock` та механізм `kvm_check_and_clear_guest_paused()`, який автоматично скидає лічильники сторожових таймерів після виходу з паузи гіпервізора.
- На сучасних архітектурах ARM64 впроваджено підтримку **Buddy Watchdog**, де сусідні процесорні ядра періодично перевіряють стан одне одного за допомогою регулярних міжпроцесорних переривань IPI, забезпечуючи надійне виявлення зависань навіть без складного конфігурування апаратного PMU.
