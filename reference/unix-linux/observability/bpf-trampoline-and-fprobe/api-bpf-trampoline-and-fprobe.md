# 📋 Довідник системних інтерфейсів та макросів BPF Trampoline і fprobe

Цей довідник містить детальну технічну специфікацію системних програмних інтерфейсів (API), внутрішніх структур даних ядра Linux, прапорців секцій libbpf, системних макросів розгортання аргументів та віртуальних файлових систем інспектування. Інформація призначена для системних інженерів, розробників BPF-утиліт та фахівців із безпеки, які розробляють високопродуктивні інструменти моніторингу на основі BPF Trampoline та фреймворку `fprobe`.

При розробці сучасних систем спостережуваності на базі eBPF інженер повинен чітко розуміти контракт взаємодії між кодом простору користувача, бібліотекою `libbpf`, BPF-верифікатором та JIT-компілятором ядра. Цей документ детально розбирає кожен елемент цієї взаємодії — від назв ELF-секцій до кодів помилок системного виклику `bpf()`.

## 1. Специфікація типів BPF-програм та секцій libbpf

Для використання BPF Trampoline або фреймворку `fprobe` кожна BPF-програма повинна мати відповідний тип у BPF-верифікаторі й бути розміщена у правильній ELF-секції за допомогою макросів `SEC()`. Під час завантаження об'єктного файла бібліотека `libbpf` аналізує назву секції, визначає тип приєднання (attach type) і готує відповідний системний виклик `bpf(BPF_LINK_CREATE)`.

Тип програми визначає, які самі перевірки проводитиме верифікатор ядра Linux при аналізі інструкцій байт-коду. Програми типу `BPF_PROG_TYPE_TRACING` проходять перевірку на відповідність типізації BTF, що дозволяє безпечно зчитувати вказівники на структури ядра без використання проміжних функцій-копіювальників.

Нижче наведено зведену матрицю доступних конфігурацій секцій libbpf, типів програм та їхніх можливостей:

| Секція libbpf (`SEC`) | Внутрішній тип BPF-програми | Прапорець attach_type | Доступний контекст і аргументи | Можливість модифікації |
| :--- | :--- | :--- | :--- | :--- |
| `SEC("fentry/func")` | `BPF_PROG_TYPE_TRACING` | `BPF_TRACE_FENTRY` | Вхідні аргументи функції ядра (`u64 args[0..5]`) з BTF-типами. | Ні (спостереження) |
| `SEC("fexit/func")` | `BPF_PROG_TYPE_TRACING` | `BPF_TRACE_FEXIT` | Вхідні аргументи `args[0..n]` + результат виконання `args[n]` (`retval`). | Ні (спостереження) |
| `SEC("fmod_ret/func")` | `BPF_PROG_TYPE_TRACING` | `BPF_TRACE_FMOD_RET` | Вхідні аргументи функції. | **Так** (перевизначення коду повернення) |
| `SEC("kprobe.multi")` | `BPF_PROG_TYPE_KPROBE` | `BPF_TRACE_KPROBE_MULTI` | Масив регістрів `struct pt_regs` + `bpf_get_func_ip()`. | Ні (масове зондування) |
| `SEC("kretprobe.multi")` | `BPF_PROG_TYPE_KPROBE` | `BPF_TRACE_KPROBE_MULTI` | `struct pt_regs` + `bpf_get_func_ip()` на виході з функції. | Ні (масове зондування) |

Програми типів `fentry`, `fexit` та `fmod_ret` вимагають від ядра обов'язкової наявності метаданих BTF. Якщо цільова функція не знайдена у `/sys/kernel/btf/vmlinux`, завантаження скасовується з помилкою `-ENOENT`. Натомість секції `kprobe.multi` використовують фреймворк `fprobe` і можуть працювати навіть за відсутності типізації аргументів у BTF, спираючись виключно на таблицю символів ядра `/proc/kallsyms` або `available_filter_functions`.

## 2. Системні макроси розгортання аргументів у BPF-коді (`bpf_tracing.h`)

Під час виконання BPF Trampoline передає у BPF-програму єдиний системний аргумент — вказівник на масив `u64 ctx[]`, у якому послідовно упаковані значення регістрів аргументів процесора. Щоб розробникові не доводилося вручну зчитати `ctx[0]`, `ctx[1]` і приводити типи через явні вказівники, бібліотека `libbpf` надає заголовочний файл `<bpf/bpf_tracing.h>` із макросом `BPF_PROG`.

Макрос `BPF_PROG` під час компіляції створює спеціальну функцію-обгортку, яка розпаковує масив `ctx[]` у звичайний список типізованих параметрів C-функції.

Внутрішня механіка макросу `BPF_PROG` базується на компіляторних розширеннях `typeof` та варіативних аргументах препроцесора. Це дозволяє генерувати статичні вбудовані (always_inline) функції, які розпаковують масив `ctx` без додаткових накладних витрат під час виконання:

```c
/* Внутрішня реалізація макросу BPF_PROG у заголовочному файлі bpf_tracing.h */
#define BPF_PROG(name, args...) \
name(unsigned long long *ctx); \
static __attribute__((always_inline)) typeof(name(0)) \
____##name(unsigned long long *ctx, ##args); \
typeof(name(0)) name(unsigned long long *ctx) \
{ \
    return ____##name(ctx, ##args_unpack); \
} \
static __attribute__((always_inline)) typeof(name(0)) \
____##name(unsigned long long *ctx, ##args)
```

Завдяки цьому макросу BPF-програма виглядає як звичайна функція ядра C, де всі типи аргументів контролюються верифікатором ядра під час збірки та завантаження.

### Приклади синтаксису розгортання для різних типів зондів:

Нижче наведено практичні приклади застосування макросів розгортання для зондів входу, виходу та модифікації поведінки ядра.

```c
/* 
 * 1. fentry: Назва функції у SEC та макросі має точно відповідати BTF vmlinux.h.
 * Аргументи (dfd, filename, flags, mode) розпаковуються автоматично з ctx[0..3].
 */
SEC("fentry/do_sys_open")
int BPF_PROG(trace_do_sys_open, int dfd, const char *filename, int flags, umode_t mode)
{
    /* Аргументи доступні безпосередньо як C-змінні */
    return 0;
}

/* 
 * 2. fexit: Останнім аргументом у списку BPF_PROG ОБОВ'ЯЗКОВО додається ret / retval.
 * Він розпаковується з елемента ctx[n], де n — кількість вхідних аргументів.
 */
SEC("fexit/do_sys_open")
int BPF_PROG(trace_do_sys_open_exit, int dfd, const char *filename, int flags, umode_t mode, int ret)
{
    if (ret < 0) {
        /* Обробка помилки системного виклику (код повернення ret < 0) */
    }
    return 0;
}

/* 
 * 3. fmod_ret: Дозволяє змінити результат повернення функції ядра.
 * Якщо BPF-програма повертає ненульове значення (наприклад, -EPERM), 
 * BPF Trampoline пропускає виконання оригінальної функції ядра і повертає це значення.
 */
SEC("fmod_ret/security_file_open")
int BPF_PROG(prevent_file_open, struct file *file, int ret)
{
    /* Заборона відкриття файла: повертаємо -EPERM (-13) */
    return -13; 
}
```

## 3. Структури ядра Linux (`include/linux/bpf.h` та `include/linux/fprobe.h`)

Підсистема трасування ядра оперує кількома фундаментальними C-структурами даних, які забезпечують кешування об'єктів JIT, лічильники посилань, реєстрацію в ftrace та керування беклогом викликів.

### 3.1. Структура BPF Trampoline (`struct bpf_trampoline`)

Ядро Linux використовує структуру `struct bpf_trampoline` для кешування та керування життєвим циклом згенерованого машинного коду. Якщо кілька BPF-програм приєднуються до однієї й тієї самої функції ядра, ядро не створює дублікати, а об'єднує їх у єдиний трамплін.

Поле `image` містить вказівник на сторінку виділеної виконуваної пам'яті JIT (`bpf_jit_alloc_exec`), у яку записуються асемблерні інструкції мосту. Поле `fops` містить структуру конфігурації для реєстрації трампліна у глобальному списку підсистеми ftrace.

```c
struct bpf_trampoline {
    /* Хеш-вузол для швидкого пошуку в глобальній таблиці tramp_table */
    struct hlist_node hlist;
    
    /* Ключ хешування (комбінація ID модуля ядра та адреси IP цільової функції) */
    u64 key;
    
    /* Лічильник активних посилань приєднаних BPF програм */
    int refcnt;
    
    /* Списки приєднаних програм за типами (fentry, fexit, fmod_ret) */
    struct hlist_head progs_hlist[BPF_TRAMP_MAX];
    
    /* Згенерований машинний код трампліна у виконуваній пам'яті JIT */
    void *image;
    u32 image_size;
    
    /* Прапорці стану (наприклад, BPF_TRAMP_F_ORIG_STACK) */
    u32 flags;
    
    /* Структура реєстрації в підсистемі ftrace */
    struct ftrace_ops fops;
};
```

### 3.2. Структура fprobe (`struct fprobe`) та колбеки

Ядерний інтерфейс `struct fprobe` використовується підсистемою `bpf_kprobe_multi` для реєстрації єдиної точки трасування на масивах адрес функцій ядра.

Він містить масив назв символів `syms`, лічильник пропущених подій `nmissed` та вказівник на об'єкт `rethook`, який відповідає за безпечне перехоплення виходу з функцій без використання важких спінлоків.

```c
struct fprobe {
    /* Вказівник на масив назв символів або адрес у пам'яті ядра */
    const char **syms;
    size_t nsyms;
    
    /* Колбеки ядра, що викликаються на вході та виході з функції */
    fprobe_entry_cb entry_handler;
    fprobe_exit_cb  exit_handler;
    
    /* Інтеграція з підсистемами ftrace та rethook */
    struct ftrace_ops ops;
    struct rethook   *rethook;
    
    /* Лічильник пропущених подій через вичерпання ресурсів */
    unsigned long nmissed;
};

/* Сигнатури колбеків fprobe у ядрі */
typedef int (*fprobe_entry_cb)(struct fprobe *fp, unsigned long entry_ip,
                               struct pt_regs *regs, void *entry_data);

typedef void (*fprobe_exit_cb)(struct fprobe *fp, unsigned long entry_ip,
                               unsigned long ret_ip, struct pt_regs *regs,
                               void *entry_data);
```

## 4. Системний API приєднання `kprobe.multi` в libbpf

Для приєднання однієї BPF-програми до багатьох функцій через `fprobe` бібліотека `libbpf` надає функцію `bpf_program__attach_kprobe_multi_opts()`.

Параметр `opts` дозволяє передавати масиви назв символів (`syms`), масиви точних адрес пам'яті (`addrs`) або спеціальні 64-бітні ідентифікатори `cookies`. Значення `cookie` передається у BPF-програму під час її виконання через хелпер `bpf_get_attach_cookie()`, що дозволяє одній BPF-програмі розрізняти, яка саме з 10 000 функцій її викликала.

```c
struct bpf_kprobe_multi_opts {
    /* Розмір структури для гарантії зворотної сумісності ABI */
    size_t sz;
    /* Масив назв символів (наприклад, ["vfs_read", "vfs_write"]) */
    const char **syms;
    /* Масив абсолютних адрес функцій у пам'яті ядра */
    const unsigned long long *addrs;
    /* Опціональний масив 64-бітних cookies для ідентифікації подій у BPF */
    const unsigned long long *cookies;
    /* Кількість елементів у масивах */
    size_t cnt;
    /* Прапорці: BPF_TRACE_MULTI_RETPROBE для виходу з функції */
    u32 flags;
};

/* Головна функція приєднання в libbpf */
struct bpf_link *
bpf_program__attach_kprobe_multi_opts(const struct bpf_program *prog,
                                       const char *pattern,
                                       const struct bpf_kprobe_multi_opts *opts);
```

## 5. Інтерфейси інспекції в псевдофайлових системах

Для налагодження, перевірки сумісності та моніторингу активних трамплінів підсистема трасування Linux надає набір інтерфейсів у віртуальних файлових системах `sysfs`, `tracefs` та `procfs`:

| Шлях до файлу / системний інтерфейс | Призначення та спосіб використання |
| :--- | :--- |
| `/sys/kernel/btf/vmlinux` | Бінарний файл метаданих BTF ядра. Якщо файл відсутній, BPF Trampoline (`fentry`/`fexit`) **не працюватиме**. |
| `/sys/kernel/tracing/available_filter_functions` | Перелік усіх C-функцій ядра, до яких можна приєднатися через ftrace / `fentry` / `fprobe`. |
| `/sys/kernel/tracing/enabled_functions` | Перелік функцій ядра, які наразі інструментовані (до яких приєднано ftrace, fentry або fprobe). |
| `/sys/kernel/debug/bpf` | Розширене інспектування мап та програм BPF (за наявності монтування debugfs). |
| `bpftool feature probe` | CLI-команда для перевірки підтримки `bpf_trampoline` та `kprobe_multi` поточним ядром. |

### Приклади CLI-команд для терміналу:

Для діагностики проблем із приєднанням зондів у реальній системі рекомендується застосовувати такі консольні команди:

```bash
# 1. Перевірка наявності метаданих BTF у поточному ядрі
ls -lh /sys/kernel/btf/vmlinux

# 2. Пошук функції ядра у списку доступних поверхонь інструментування
grep "do_sys_open" /sys/kernel/tracing/available_filter_functions

# 3. Перегляд списку активних BPF-трамплінів за допомогою bpftool
bpftool link list type tracing
```

## 6. Детальна розшифровка кодів помилок BPF Trampoline

При спробі завантаження та приєднання BPF-програми через системний виклик `bpf(BPF_LINK_CREATE)` ядро може повернути один із таких від'ємних кодів помилок:

- **`-ENOENT` (-2):** Вказану функцію не знайдено в метаданих BTF (`vmlinux`) або у таблиці символів ядра. Перевірте правильність написання назви функції.
- **`-EINVAL` (-22):** Сигнатура BPF-програми не відповідає метаданим BTF (наприклад, кількість аргументів у `BPF_PROG` перевищує кількість аргументів функції ядра).
- **`-EOPNOTSUPP` / `-NOPROTO` (-95):** Поточна архітектура CPU або ядро Linux не підтримує BPF Trampoline (відсутня опція `CONFIG_DYNAMIC_FTRACE_WITH_REGS` або JIT-компілятор BPF).
- **`-E2BIG` (-7):** Кількість аргументів функції перевищує максимум, що підтримується трампліном (понад 6 аргументів у регістрах для x86_64).
- **`-EBUSY` (-16):** Конфлікт безпеки: спроба приєднати програму `fmod_ret` до функції ядра, яка не позначена в сирцевому коді макросом `ALLOW_ERROR_INJECTION`.
