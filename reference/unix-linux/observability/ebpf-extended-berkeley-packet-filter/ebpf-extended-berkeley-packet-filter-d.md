У сучасному світі системного програмування під Linux мало які технології здійснили такий самий революційний вплив, як eBPF (Extended Berkeley Packet Filter). Спочатку розроблений для фільтрації мережевих пакетів (звідки й назва), BPF еволюціонував у повноцінну віртуальну машину всередині ядра Linux. Він дозволяє безпечно виконувати користувацький код у привілейованому режимі без необхідності писати й компілювати модулі ядра, забезпечуючи при цьому нативну швидкодію.

## Що таке eBPF та для чого він потрібен?

Ядро Linux є монолітним: воно має повний контроль над апаратним забезпеченням і процесами. Традиційно, щоб змінити поведінку ядра або зібрати глибокі метрики, системний інженер мав лише два шляхи:
1. Змінити вихідний код ядра та перезібрати його. Це довго, складно, і вимагає постійного перенесення патчів на нові версії.
2. Написати модуль ядра (Kernel Module) і завантажити його. Цей підхід популярніший, але має суттєві недоліки: помилка в модулі ядра (наприклад, розіменування нульового вказівника або нескінченний цикл) призводить до "паніки ядра" (Kernel Panic) та повного краху системи. Крім того, модулі часто залежать від внутрішніх структур ядра, які не гарантують стабільності ABI (див. [«Не ламати простір користувача»: сталість ABI ядра](book:unix-linux/kernel-abi-stability)).

eBPF пропонує третій шлях. Розробник пише програму (переважно мовою C), компілює її у спеціальний **BPF bytecode**, і цей байт-код завантажується в ядро. Головна перевага: перед виконанням ядро перевіряє цей код за допомогою **Верифікатора** (Verifier). Тільки якщо код гарантовано безпечний (не завалить систему, не прочитає заборонену пам'ять, не зависне), ядро транслює його у машинні інструкції та дозволяє виконуватись як реакцію на певні події (трасувальні точки, мережеві пакети тощо).

## Архітектура та Віртуальна Машина eBPF

eBPF — це, по суті, RISC-подібна віртуальна машина всередині ядра Linux. Її архітектура створена такою, щоб JIT-компілятор міг миттєво й ефективно перекласти її інструкції в нативний код процесора.

### 11 64-бітних регістрів та BPF Bytecode

ВМ eBPF має 11 64-бітних регістрів. Це число не випадкове: архітектура x86_64 та ARM64 мають достатню кількість апаратних регістрів, щоб усі 11 регістрів eBPF могли бути "спроектовані" (mapped) напряму на апаратні регістри (наприклад, `R0` стає `RAX` на x86). Це забезпечує нульові накладні витрати на збереження стану ВМ.

* `R0`: Регістр повернення (Return value) з допоміжних функцій ядра або самої eBPF-програми.
* `R1` – `R5`: Регістри для передачі аргументів у функції. eBPF-функції можуть приймати максимум 5 аргументів.
* `R6` – `R9`: Регістри, що зберігаються між викликами функцій (Callee saved). Якщо функція їх змінює, вона мусить зберегти та відновити їхнє значення.
* `R10`: Регістр вказівника на стек (Frame Pointer). Він єдиний доступний лише для читання.

BPF bytecode складається з інструкцій фіксованого розміру (64 біти кожна). Кожна інструкція містить код операції, номери регістрів-джерел/призначень, зміщення та безпосереднє значення (immediate). Розмір стеку програми обмежений лише 512 байтами, що змушує писати вкрай компактний код, який не розкидається великими масивами локальних змінних.

### In-kernel Verifier (Верифікатор)

Це "серце" безпеки eBPF. Завантажити код в ядро легко, але переконатись, що він не зашкодить — надзвичайно складна комп'ютерна задача (згадайте проблему зупинки Тьюринга). Верифікатор перевіряє кожну інструкцію програми перед її прийняттям:

1. **Відсутність нескінченних циклів (Граф виконання):** Верифікатор будує граф потоку керування (Control Flow Graph). Раніше цикли були повністю заборонені. Зараз дозволені обмежені цикли (bounded loops), але верифікатор повинен проаналізувати їх і довести, що програма завершиться за скінченний (і малий) час.
2. **Безпека доступу до пам'яті:** Програма не може просто так взяти й прочитати довільну адресу пам'яті ядра. Кожен вказівник супроводжується метаданими про те, куди він вказує (стек, пакет, BPF мапа). Доступи перевіряються на вихід за межі масивів.
3. **Обмежений розмір:** Існує ліміт на кількість виконаних інструкцій (наприклад, 1 мільйон для сучасних ядер), що запобігає зависанням.
4. **Ініціалізація пам'яті:** Верифікатор відстежує стан кожного регістра та байта на стеку. Не можна прочитати неініціалізовану змінну.

Якщо хоча б одне правило порушене, верифікатор відхиляє програму і повертає `EINVAL`, а в лог (який можна вичитати з простору користувача) записується детальна причина відмови.

### JIT (Just-In-Time) Компілятор

Як тільки верифікатор каже "ОК", байт-код eBPF не інтерпретується інструкція за інструкцією (хоча історично інтерпретатор існував). Вмикається JIT-компілятор, який на льоту генерує нативний машинний код для поточного процесора (x86, ARM, RISC-V). Оскільки регістри ВМ співпадають з апаратними, компіляція є лінійною і надзвичайно швидкою. Отриманий машинний код підключається до трасувальної точки або мережевого хука і виконується зі швидкістю звичайного коду ядра.

## Системний виклик bpf(2)

Простір користувача взаємодіє з підсистемою eBPF через єдиний системний виклик — `bpf(2)`.

```c
int bpf(int cmd, union bpf_attr *attr, unsigned int size);
```

Це мультиплексований виклик: його поведінка залежить від параметра `cmd`. Найважливіші команди:
* `BPF_PROG_LOAD`: Завантаження байт-коду програми в ядро (передається масив інструкцій).
* `BPF_MAP_CREATE`: Створення сховища даних (BPF Map).
* `BPF_MAP_LOOKUP_ELEM`, `BPF_MAP_UPDATE_ELEM`, `BPF_MAP_DELETE_ELEM`: Робота з мапами з боку користувацького процесу.

Для завантаження програми, користувацький процес готує структуру `bpf_attr`, передає її вказівник, і ядро або повертає файловий дескриптор, що представляє завантажену програму/мапу, або помилку від верифікатора. Після завантаження програма повинна бути прикріплена (attached) до певної події (hook) — наприклад, до системного виклику, Kprobe або мережевого інтерфейсу (XDP/TC).

## BPF Maps: Сховища даних та зв'язок

Програми eBPF ізольовані. Вони не можуть викликати стандартні функції `malloc` або використовувати глобальні змінні вільно, і не можуть безпосередньо відправляти дані на екран. Щоб зберігати стан між різними викликами однієї програми (наприклад, лічити кількість викликів `open`) та передавати дані у простір користувача, існують **BPF Maps** — ефективні структури даних типу "ключ-значення", реалізовані всередині ядра.

Найпопулярніші типи мап:
1. **Hash Table (`BPF_MAP_TYPE_HASH`):** Класична хеш-таблиця. Дозволяє використовувати ключі та значення довільного розміру. Ідеально підходить для лічильників, згрупованих за IP-адресами або PID процесів.
2. **Array (`BPF_MAP_TYPE_ARRAY`):** Масив фіксованого розміру з цілочисельним ключем (індексом). Значно швидший за хеш-таблицю.
3. **Perf Event Array / Ring Buffer (`BPF_MAP_TYPE_RINGBUF`):** Кільцевий буфер для високопродуктивної асинхронної передачі потоку подій з ядра у простір користувача. eBPF-програма записує подію в буфер, а програма користувача читає її. Це витіснило старіший Perf Buffer завдяки кращій продуктивності при кількох процесорах.
4. **LRU Hash (`BPF_MAP_TYPE_LRU_HASH`):** Хеш-таблиця, яка при переповненні автоматично видаляє найменш використовувані елементи (Least Recently Used).
5. **LPM Trie (`BPF_MAP_TYPE_LPM_TRIE`):** Дерево для пошуку найдовшого префікса (Longest Prefix Match). Спеціалізована мапа для маршрутизації та перевірки належності IP-адрес до підмереж.

## CO-RE (Compile Once – Run Everywhere)

Протягом багатьох років розгортання eBPF було болісним. Ядро Linux часто змінює розміщення полів у своїх структурах. Якщо ви написали програму, яка читає поле `pid` зі структури `task_struct`, зміщення цього поля може бути `0x400` у ядрі 5.4, і `0x410` у ядрі 5.8.

Щоб вирішити це, ранні інструменти (як BCC) перекомпілювали програму *нальоту* прямо на цільовому сервері. Це означало, що на кожен production-сервер треба було тягнути величезні заголовні файли ядра (kernel headers) та важкий компілятор LLVM, що витрачало пам'ять і процесорний час.

**CO-RE** розв'язав цю проблему елегантно, об'єднавши три елементи:
1. **BTF (BPF Type Format):** Компактний бінарний формат, що описує точний вигляд усіх структур ядра. Він тепер вбудовується прямо в образ самого ядра і доступний у файлі `/sys/kernel/btf/vmlinux`.
2. **LLVM BPF Backend (Релокації):** Коли LLVM компілює C-код у байт-код eBPF, він не "зашиває" жорстко зміщення полів, а замість цього генерує спеціальні метадані (релокації), що позначають: "Ось тут читається поле X зі структури Y".
3. **libbpf (Loader):** При запуску готової програми на цільовому сервері, бібліотека завантажувача (`libbpf`) читає поточний BTF ядра, знаходить, де насправді розташоване поле X у поточній версії `task_struct`, і переписує відповідні інструкції eBPF-програми ще до того, як віддати їх верифікатору.

Завдяки CO-RE розробник може скомпілювати свою eBPF-утиліту один раз у себе на ноутбуці, запакувати її в єдиний маленький бінарний файл і запускати на мільйонах серверів з різними ядрами — без перекомпіляції і без kernel headers. Це зробило дистрибуцію eBPF-інструментів простою і масовою.

## Інструментарій: bcc, bpftrace та libbpf

Екосистема eBPF пропонує різні рівні абстракції для створення інструментів:

1. **BCC (BPF Compiler Collection):** Історично перший великий фреймворк для розробки. Дозволяє писати C-код програми ядра прямо як рядок у Python-скрипті. Скрипт компілює C-код на льоту, завантажує його і читає дані. BCC включає понад 100 готових скриптів (так звані bcc-tools, наприклад `execsnoop`, `opensnoop`, `biolatency`). Головний недолік: він повільний при запуску і потребує LLVM на сервері. Сьогодні його використання для нових інструментів не рекомендується.
2. **bpftrace:** Це високорівнева спеціалізована мова трасування (синтаксисом нагадує awk або DTrace). Вона дозволяє писати короткі, потужні скрипти-однорядковики для живого аналізу системи. `bpftrace` ідеально підходить для швидкого розслідування інцидентів (troubleshooting), коли немає часу писати C-код.
3. **libbpf:** Це сучасний стандарт. Офіційна C-бібліотека, яка реалізує завантажувач програм і підтримку CO-RE. Підтримується різними мовами через обгортки (Go, Rust, Python). Інструменти, написані за допомогою `libbpf`, швидкі, компактні й не потребують залежностей на цільовій машині. Більшість нових агентів observability та безпеки (Cilium, Falco) використовують саме цей підхід.

## Приклади коду

Нижче наведено два приклади простого інструмента, який відстежує кожен виклик `execve` (запуск нової програми) у системі.

:::tabs

=== bpftrace

```bpftrace
// Простий bpftrace скрипт для відстеження запуску програм.
// Він прикріплюється до трасувальної точки входу в системний виклик execve.
tracepoint:syscalls:sys_enter_execve
{
    // comm - це вбудована змінна bpftrace, що містить назву поточного процесу.
    // pid  - ідентифікатор поточного процесу.
    printf("Процес %s (PID %d) викликав execve\n", comm, pid);
}
```

=== C (libbpf)

```c
// Код для ядра, що компілюється в BPF bytecode.
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>

// Макрос SEC вказує завантажувачу libbpf, до якої події прикріпити функцію
SEC("tracepoint/syscalls/sys_enter_execve")
int handle_execve(void *ctx)
{
    char comm[16];
    
    // eBPF не може напряму читати пам'ять, тому використовуються спеціальні helper-функції
    bpf_get_current_comm(&comm, sizeof(comm));
    
    // Отримуємо 64-бітне значення: верхні 32 біти - це TGID (PID в просторі користувача),
    // нижні 32 біти - це PID потоку. Тому робимо зсув.
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    
    // bpf_printk виводить повідомлення у /sys/kernel/tracing/trace_pipe
    bpf_printk("Процес %s (PID %d) викликав execve", comm, pid);
    
    return 0; // 0 означає успішне виконання
}

// Усі програми BPF повинні мати ліцензію, сумісну з GPL, щоб мати доступ до функцій ядра
char _license[] SEC("license") = "GPL";
```

:::

## Висновок

eBPF здійснив революцію в ядрі Linux. Дозволивши безпечно виконувати користувацькі програми безпосередньо в контексті ядра з нативною швидкістю, ця технологія дала початок цілій індустрії. Завдяки верифікатору та JIT-компілятору, система залишається стабільною. Концепція BPF мап дозволила гнучко обробляти та експортувати метрики. А поява CO-RE перетворила eBPF-інструменти з нішевих хакерських утиліт на надійні, поширювані бінарні застосунки. Сьогодні eBPF лежить в основі найкращих інструментів спостережуваності (observability), мережевого керування (Cilium) та безпеки (Tetragon).
