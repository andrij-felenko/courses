# 📋 Інтерфейс системного виклику bpf(2) та BPF-мапи

Двійковий контракт системного виклику `bpf(2)` у поєднанні з конфігураційним об'єднанням `union bpf_attr`, ключовими типами BPF-мап та допоміжними функціями (Helper Functions) формує низькорівневу інтерфейсну поверхню взаємодії між простором користувача та підсистемою eBPF всередині ядра Linux.

---

## 1. Сигнатура та параметри системного виклику

Простір користувача взаємодіє з підсистемою eBPF у ядрі через єдиний мультиплексований системний виклик `bpf(2)`.

```c
#include <linux/bpf.h>

int bpf(int cmd, union bpf_attr *attr, unsigned int size);
```

### Деталізація параметрів виклику:

1. **`cmd` (Command Identifier)**: Цілочисельний кодовий макрос (enum `bpf_cmd`), який визначає конкретну дію, яку ядро має виконати. Поведінка виклику повністю залежить від цього параметра: завантаження байт-коду, створення мапи, маніпуляція елементами або отримання метаданих.
2. **`attr` (Attribute Pointer)**: Вказівник на універсальне конфігураційне об'єднання `union bpf_attr`. Воно містить вкладені анонімні структури, розраховані під відповідну команду `cmd`.
3. **`size` (Attribute Size)**: Розмір структури у байтах, на яку вказує `attr` (зазвичай передається `sizeof(union bpf_attr)`).

### Механізм гарантії сумісності за допомогою параметра `size`
Використання аргументу `size` є ключовим архітектурним рішенням ядра Linux для забезпечення ABI-сумісності між різними версіями ядер та інструментів простору користувача:

- **Старий користувацький бінарник на новому ядрі**: Якщо програма користувача скомпільована зі старішим `sizeof(union bpf_attr)`, ніж поточне ядро, ядро зчитує лише вказану кількість байтів, а решту нових полів структури автоматично заповнює нулями (`0`).
- **Новий користувацький бінарник на старому ядрі**: Якщо програма передає `size`, який перевищує розмір структури `bpf_attr` поточного ядра, ядро перевіряє, чи заповнені нові поля ненульовими значеннями. Якщо всі невідомі ядру поля дорівнюють нулю, ядро успішно виконує запит. Якщо ж програма передала ненульові значення у поля, які поточне ядро ще не підтримує, виклик повертає помилку `-1` та встановлює `errno = E2BIG`.

### Повернювані значення:
- При успішному виконанні команди створення об'єктів (`BPF_MAP_CREATE`, `BPF_PROG_LOAD`, `BPF_LINK_CREATE`): Повертається анонімний файловий дескриптор (значення `>= 0`). Цей дескриптор підтримує стандартне закриття через `close(fd)` та дублювання через `dup()`. Коли всі файлові дескриптори об'єкта закриваються, ядро автоматично звільняє пам'ять мапи чи програми (якщо об'єкт не був прикріплений до хука або не закріплений у bpffs).
- При успішному виконанні маніпуляцій з елементами (`BPF_MAP_UPDATE_ELEM`, `BPF_MAP_DELETE_ELEM`): Повертається `0`.
- При помилці: Повертається `-1`, а системна змінна `errno` містить код помилки.

## 2. Повний специфікат команд системного виклику (`cmd`)

Нижче наведено повний перелік команд мультиплексора `bpf(2)` з описом їхнього призначення та повернюваних типів:

| Команда `cmd` | Опис операції у ядрі | Повертає |
|---|---|---|
| `BPF_MAP_CREATE` | Виділяє пам'ять у ядрі та створює BPF-мапу заданого типу | Файловий дескриптор `map_fd` (>= 0) |
| `BPF_MAP_LOOKUP_ELEM` | Шукає значення за вказаним вказівником на ключ у BPF-мапі | `0` при успіху, `-1` якщо ключ відсутній |
| `BPF_MAP_UPDATE_ELEM` | Додає нову або оновлює наявну пару ключ-значення у мапі | `0` при успіху, `-1` при помилці |
| `BPF_MAP_DELETE_ELEM` | Видаляє елемент за вказаним ключем із мапи | `0` при успіху, `-1` якщо ключ відсутній |
| `BPF_MAP_GET_NEXT_KEY` | Шукає наступний ключ у мапі після переданого поточного ключа | `0` при успіху, `-1` при досягненні кінця |
| `BPF_PROG_LOAD` | Передає байт-код eBPF верифікатору та JIT-компілятору | Файловий дескриптор `prog_fd` (>= 0) |
| `BPF_OBJ_PIN` | Прикріплює мапу або програму до віртуальної файлової системи `/sys/fs/bpf` | `0` при успіху |
| `BPF_OBJ_GET` | Відкриває новий файловий дескриптор об'єкта, закріпленого у `/sys/fs/bpf` | Файловий дескриптор об'єкта `fd` |
| `BPF_PROG_ATTACH` | Приєднує eBPF-програму до події (cgroup, socket тощо) | `0` при успіху |
| `BPF_PROG_DETACH` | Від'єднує eBPF-програму від події | `0` при успіху |
| `BPF_LINK_CREATE` | Створює зв'язувальний об'єкт `bpf_link` для надійного прив'язування | Файловий дескриптор `link_fd` |
| `BPF_LINK_UPDATE` | Замінює eBPF-програму всередині наявного `bpf_link` на льоту | `0` при успіху |
| `BPF_BTF_LOAD` | Завантажує метадані BTF (BPF Type Format) у ядро | Файловий дескриптор `btf_fd` |

## 3. Розбір полів об'єднання union bpf_attr

Об'єднання `union bpf_attr` складається з багатьох анонімних структур. Нижче наведено розбір найбільш уживаних конфігураційних полів.

### 3.1. Структура для команди BPF_MAP_CREATE

При команді `BPF_MAP_CREATE` ядро інтерпретує першу структуру об'єднання:

```c
union bpf_attr {
    struct {
        __u32   map_type;        // Тип мапи (enum bpf_map_type)
        __u32   key_size;        // Розмір ключа у байтах (наприклад, sizeof(u32))
        __u32   value_size;      // Розмір значення у байтах (наприклад, sizeof(struct event))
        __u32   max_entries;     // Максимальна кількість елементів мапи
        __u32   map_flags;       // Прапорці створення (BPF_F_NO_PREALLOC, BPF_F_NUMA_NODE)
        __u32   inner_map_fd;    // fd шаблону внутрішньої мапи (для BPF_MAP_TYPE_ARRAY_OF_MAPS)
        __u32   numa_node;       // Ідентифікатор NUMA-вузла при BPF_F_NUMA_NODE
        char    map_name[16];    // Символьна назва мапи для ідентифікації у bpftool
        __u32   btf_fd;          // fd метаданих BTF
        __u32   btf_key_type_id; // BTF type ID для типу ключа
        __u32   btf_value_type_id;// BTF type ID для типу значення
    };
};
```

Деталізація прапорців `map_flags`:
- `BPF_F_NO_PREALLOC`: Забороняє попереднє виділення всієї пам'яті мапи при створенні. Пам'ять для нових елементів буде виділятися динамічно через `kmalloc()`. Це економить оперативну пам'ять, але додає затримки при перших вставках.
- `BPF_F_NUMA_NODE`: Примусово виділяє пам'ять мапи на конкретному фізичному NUMA-вузлі процесора для мінімізації міжсокетних затримок шини DRAM.
- `BPF_F_RDONLY` / `BPF_F_WRONLY`: Обмежує доступ до мапи лише для читання або лише для запису з боку eBPF-програми.
- `BPF_F_RDONLY_PROG` / `BPF_F_WRONLY_PROG`: Обмежує доступ до мапи з боку користувацького простору.

### 3.2. Структура для команди BPF_PROG_LOAD

При команді `BPF_PROG_LOAD` задіяне таке розташування полів:

```c
union bpf_attr {
    struct {
        __u32   prog_type;       // Тип програми (BPF_PROG_TYPE_KPROBE, BPF_PROG_TYPE_SCHED_CLS тощо)
        __u32   insn_cnt;        // Кількість 64-бітних інструкцій у байт-коді
        __aligned_u64 insns;     // Вказівник у просторі користувача (const struct bpf_insn *)
        __aligned_u64 license;   // Вказівник на рядок ліцензії (const char *), наприклад "GPL"
        __u32   log_level;       // Рівень деталей верифікатора: 0 (вимкнено), 1 (лог), 2 (детальний log)
        __u32   log_size;        // Розмір буфера для логу у байтах
        __aligned_u64 log_buf;   // Вказівник на буфер пам'яті (char *), куди ядро запише текстовий лог
        __u32   kern_version;    // Версія ядра (потрібна для старих kprobe у ядрах < 4.18)
        __u32   prog_flags;      // Прапорці (наприклад, BPF_F_STRICT_ALIGNMENT)
        char    prog_name[16];   // Символьна назва функції eBPF
        __u32   prog_btf_fd;     // fd завантаженого об'єкта BTF
        __u32   expected_attach_type; // Очікуваний тип прикріплення для Tracing/LSM
    };
};
```

## 4. Детальний специфікат типів BPF-мап

Нижче наведено порівняльний аналіз усіх основних типів мап ядра Linux:

| Тип BPF-мапи | Формат даних | Пам'ять та локальність | Застосування |
|---|---|---|---|
| `BPF_MAP_TYPE_HASH` | Хеш-таблиця | Динамічна або попередньо виділена пам'ять | Збереження довільних пар ключ-значення (наприклад, лічильники по IP-адресах чи PID). |
| `BPF_MAP_TYPE_ARRAY` | Безперервний масив | Неперервний блок пам'яті у ядрі | Найшвидший доступ за індексом `0..max_entries-1`. Глобальні конфігурації. |
| `BPF_MAP_TYPE_PROG_ARRAY` | Масив `prog_fd` | Масив посилань на eBPF-програми | Використовується для механізму tail calls (`bpf_tail_call`) — переходу виконання в іншу програму. |
| `BPF_MAP_TYPE_PERF_EVENT_ARRAY` | Масив `perf_fd` | Таблиця буферів `perf_event` за CPU | Передача подій у простір користувача через підсистему `perf`. |
| `BPF_MAP_TYPE_PERCPU_HASH` | Хеш-таблиця per-CPU | Окрема хеш-таблиця на кожне ядро CPU | Високочастотні лічильники без міжядерного колізійного блокування. |
| `BPF_MAP_TYPE_PERCPU_ARRAY` | Масив per-CPU | Окремий масив на кожне ядро CPU | Накопичення статистики та профілювання з нульовими витратами на атомарні інструкції. |
| `BPF_MAP_TYPE_STACK_TRACE` | Таблиця стеків | Масив масивів адрес пам'яті | Збереження унікальних ідентифікаторів та адрес стеків викликів (Callstacks). |
| `BPF_MAP_TYPE_LRU_HASH` | LRU Хеш-таблиця | Фіксована хеш-таблиця з кільцевим списком | Автоматично видаляє найменш використовувані елементи при досягненні `max_entries`. |
| `BPF_MAP_TYPE_LPM_TRIE` | Дерево префіксів | Двійкове префіксне дерево (Trie) | Пошук найдовшого збігу префікса (Longest Prefix Match). Маршрутизація IP/CIDR. |
| `BPF_MAP_TYPE_RINGBUF` | Кільцевий буфер | Lock-free спільна пам'ять для всіх CPU | Асинхронна високопродуктивна передача потоку подій у користувацький простір (`mmap`). |

## 5. Допоміжні функції eBPF (Helper Functions)

eBPF-програми всередині ядра не можуть прямо викликати довільні C-функції ядра. Замість цього вони звертаються до фіксованого набору **BPF Helpers** — внутрішніх API ядра з гарантованим ABI.

Усередині байт-коду виклик хелпера генерується як інструкція `BPF_CALL` з аргументом-імплементацією ID функції.

### Детальний довідник BPF Helpers:

| ID | Назва функції | Сигнатура | Детальний опис поведінки |
|---|---|---|---|
| 1 | `bpf_map_lookup_elem` | `void *bpf_map_lookup_elem(void *map, const void *key)` | Шукає елемент у мапі за ключем. Повертає вказівник на значення у пам'яті мапи або `NULL`. Повернений вказівник вимагає обов'язкової перевірки на `NULL` перед розіменуванням. |
| 2 | `bpf_map_update_elem` | `long bpf_map_update_elem(void *map, const void *key, const void *value, u64 flags)` | Вставляє або оновлює елемент. Прапорці `BPF_ANY` (створити або оновити), `BPF_NOEXIST` (створити лише якщо не існує), `BPF_EXIST` (оновити лише наявний). |
| 3 | `bpf_map_delete_elem` | `long bpf_map_delete_elem(void *map, const void *key)` | Видаляє елемент з мапи за ключем. Повертає `0` при успіху або від'ємний код помилки. |
| 5 | `bpf_ktime_get_ns` | `u64 bpf_ktime_get_ns(void)` | Повертає поточний монотонний час системи у наносекундах (від моменту завантаження ОС, без урахування часу сну). |
| 6 | `bpf_trace_printk` | `long bpf_trace_printk(const char *fmt, u32 fmt_size, ...)` | Записує форматований рядок у відлагоджувальний буфер `/sys/kernel/tracing/trace_pipe`. Використовується виключно для відлагодження, оскільки має глобальне блокування. |
| 14 | `bpf_get_current_pid_tgid` | `u64 bpf_get_current_pid_tgid(void)` | Повертає 64-бітне значення: верхні 32 біти містять TGID (Process ID у просторі користувача), а нижні 32 біти — PID потоку (Thread ID). |
| 15 | `bpf_get_current_uid_gid` | `u64 bpf_get_current_uid_gid(void)` | Повертає 64-бітне значення: верхні 32 біти містять GID, нижні 32 біти — UID користувача, від імені якого виконується поточний процес. |
| 16 | `bpf_get_current_comm` | `long bpf_get_current_comm(void *buf, u32 size_of_buf)` | Записує у буфер `buf` назву виконуваного файла поточного процесу (поле `comm` з `task_struct`, розміром до 16 байтів). |
| 113 | `bpf_probe_read_kernel` | `long bpf_probe_read_kernel(void *dst, u32 size, const void *unsafe_ptr)` | Безпечно копіює `size` байтів із довільної адреси пам'яті ядра у локальний стек чи буфер eBPF. Запобігає краху ядра при недійсних адресах. |
| 114 | `bpf_probe_read_user_str` | `long bpf_probe_read_user_str(void *dst, u32 size, const void *unsafe_ptr)` | Безпечно копіює null-terminated рядок з простору користувача у буфер eBPF. Повертає довжину скопійованого рядка або від'ємний код помилки. |
| 130 | `bpf_ringbuf_reserve` | `void *bpf_ringbuf_reserve(void *ringbuf, u64 size, u64 flags)` | Резервує неперервний шматок пам'яті у Ring Buffer під нову подію. Повертає вказівник на пам'ять або `NULL` при переповненні буфера. |
| 131 | `bpf_ringbuf_submit` | `void bpf_ringbuf_submit(void *data, u64 flags)` | Фіксує зарезервовану подію у Ring Buffer, роблячи її негайно доступною для зчитування користувацьким процесом. |

## 6. Детальний розбір кодів помилок системного виклику bpf(2)

Якщо виклик `bpf(2)` повертає `-1`, причина відмови фіксується у змінній `errno`. Нижче наведено детальний опис кожного коду помилки та сценаріїв його виникнення у ядрі:

### `EINVAL` (Invalid Argument, 22)
- **Причина 1**: Верифікатор відхилив завантажувану програму eBPF через порушення правил безпеки (неініціалізована пам'ять, недосяжний код, вихід за межі масиву).
- **Причина 2**: Передано невідоме значення `cmd` або невалідні прапорці у `map_flags`.
- **Причина 3**: Спроба створити мапу з розмірами `key_size = 0` або `value_size = 0`.

### `E2BIG` (Argument list too long, 7)
- **Причина**: Значення параметра `size` у виклику `bpf(int cmd, union bpf_attr *attr, unsigned int size)` більше за розмір структури `bpf_attr`, відомий даному ядру, і при цьому в невідомих ядру полях передано ненульові значення.

### `EACCES` (Permission denied, 13)
- **Причина 1**: Програмі користувача бракує необхідних привілеїв POSIX Capabilities (`CAP_BPF`, `CAP_PERFMON` чи `CAP_NET_ADMIN`).
- **Причина 2**: Верифікатор виявив спробу виконання невідомих інструкцій або запису у вказівники, доступні лише для читання (наприклад, спроба змінити регістр `R10`).

### `EPERM` (Operation not permitted, 1)
- **Причина**: Завантаження eBPF-програм заборонено на рівні системи через параметр sysctl `kernel.unprivileged_bpf_disabled = 1` або `2`.

### `ENOMEM` (Out of memory, 12)
- **Причина**: Ядро не змогло виділити необхідний обсяг неперервної оперативної пам'яті (kmalloc/vmalloc) під створення BPF-мапи великого розміру або під виділення сторінки пам'яті для JIT-скомпільованого коду.

### `ENOENT` (No such file or directory, 2)
- **Причина**: Спроба отримати файловий дескриптор закріпленого об'єкта (`BPF_OBJ_GET`) за шляхом у `/sys/fs/bpf`, який не існує, або видалити ключ із мапи (`BPF_MAP_DELETE_ELEM`), який відсутній у хеш-таблиці.

### `EBUSY` (Device or resource busy, 16)
- **Причина**: Спроба приєднати eBPF-програму до трасувальної точки або сокета, який вже зайнятий іншою програмою у монопольному режимі.
