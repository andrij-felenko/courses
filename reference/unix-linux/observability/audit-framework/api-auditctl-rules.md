# 📜 Синтаксис правил auditctl

Ця довідка необхідна для правильного конструювання правил аудиту за допомогою `auditctl`, щоб ефективно перехоплювати критичні системні виклики та зміни у файловій системі, не створюючи надмірного навантаження на ядро. Оскільки неправильно сформульовані правила можуть призвести до падіння продуктивності або втрати важливих подій, важливо розуміти анатомію фільтрів та дій, які підтримує підсистема аудиту ядра Linux.

## Файлові правила (Watches)

Файлові правила (watches) є абстракцією, яка дозволяє відстежувати доступ до файлів та директорій. Під капотом вони транслюються у правила системних викликів, таких як `open`, `openat`, `execve`, `chmod`, `chown` тощо. Використання файлових правил значно спрощує синтаксис для типових задач моніторингу конфігураційних файлів або бінарників.

Приклад робочого Bash-скрипта, який додає правило для моніторингу доступу до `/etc/passwd`:

```bash
#!/bin/bash
# Додаємо правило аудиту для файлу /etc/passwd
# Відстежуємо запис (w) та зміну атрибутів (a)
# Прив'язуємо унікальний ключ "passwd_changes" для зручного пошуку
sudo auditctl -w /etc/passwd -p wa -k passwd_changes

# Перевіряємо, чи правило успішно додано
sudo auditctl -l | grep passwd_changes
```

**Доступні дозволи для параметра `-p`:**
- `r` (read): Читання файлу або лістинг директорії.
- `w` (write): Запис у файл, створення нових файлів у директорії, видалення.
- `x` (execute): Виконання файлу як програми.
- `a` (attribute): Зміна атрибутів (наприклад, зміна прав доступу або власника).

**Порада щодо використання ключів (`-k`):**
Завжди використовуйте параметр `-k`, щоб маркувати ваші правила. Мітка ключа може містити до 31 символу. Це дозволить пізніше шукати події в логах за допомогою команди `ausearch -k passwd_changes`, значно прискорюючи розслідування інцидентів.

## Правила системних викликів

Правила системних викликів забезпечують найвищий рівень контролю, дозволяючи фільтрувати події на основі специфічних системних викликів, їх аргументів, результату виконання та ідентифікаторів користувача. Вони вимагають точного вказування архітектури, оскільки номери системних викликів відрізняються між 32-бітними та 64-бітними системами.

Приклад Bash-скрипта для відстеження невдалих спроб відкриття файлів через помилку доступу:

```bash
#!/bin/bash
# Відстежуємо невдалі системні виклики open, openat та openat2 на 64-бітній архітектурі
# Подія генерується на виході (exit) із системного виклику
# Фільтруємо лише події, які завершилися помилкою EACCES (Permission denied)
sudo auditctl -a always,exit -F arch=b64 -S open -S openat -S openat2 -F exit=-EACCES -k access_denied
```

**Обов'язкові компоненти правила:**
1. **Дія (Action):** `always` (створювати запис у логах) або `never` (проігнорувати подію). Правила `never` корисні для пригнічення шуму від довірених процесів.
2. **Список (List):** Визначає, на якому етапі життєвого циклу системного виклику застосовується правило:
   - `exit`: Застосовується після завершення системного виклику. Це найпоширеніший список, оскільки лише на цьому етапі доступний код повернення та результат операції.
   - `task`: Застосовується при створенні нового процесу (через `fork` або `clone`). Використовується рідко, переважно для фільтрації на рівні процесів.
   - `user`: Фільтрує події, згенеровані простором користувача, а не ядром (наприклад, логи від `sudo` або `sshd`).
   - `exclude`: Дозволяє виключати певні типи подій глобально.

### Поля фільтрації (-F)

Фільтри дозволяють звузити потік подій, перевіряючи різні атрибути процесу та контексту виклику. Можна об'єднувати кілька фільтрів у одному правилі (усі вони працюватимуть як логічне `AND`).

Основні поля для фільтрації:
- `arch`: Архітектура процесора (`b64` для x86_64, `b32` для x86). Це критично важливо, якщо ваша система може виконувати як 32-бітні, так і 64-бітні бінарні файли (наприклад, через Multilib).
- `auid` (Audit User ID): Оригінальний ідентифікатор користувача, який увійшов у систему (Login UID). На відміну від поточного `uid`, `auid` не змінюється після виконання `sudo` або `su`, дозволяючи відстежити дійсного ініціатора дій. Пошук за `auid>=1000` дозволяє відкинути системних демонів.
- `uid`, `euid`, `suid`, `fsuid`: Поточні, ефективні, збережені та файлові ідентифікатори користувача. Вони змінюються залежно від стану процесу та прав `setuid`.
- `pid`: Фільтрація за ідентифікатором певного процесу (наприклад, виключення моніторингу власне аудитора).
- `success`: Приймає `1` (якщо системний виклик успішний) або `0` (якщо він повернув помилку).
- `exit`: Фільтрація за специфічним кодом помилки, таким як `-EPERM` (Operation not permitted) або `-EACCES` (Permission denied).
- `dir`: Дозволяє вказати каталог, для якого буде застосовуватись фільтр (рекурсивно). Це зручно для моніторингу цілої гілки файлової системи, не використовуючи watch-правила для кожного окремого файлу.

Приклад правила, яке ігнорує події читання від певного довіреного процесу, щоб зменшити обсяг логів:

```bash
#!/bin/bash
# Не записувати події системного виклику read для процесу з PID 1234
sudo auditctl -a never,exit -S read -F pid=1234
```

Правильна комбінація дій, фільтрів та ключів дозволяє створити цілеспрямовану систему моніторингу, яка фіксуватиме лише дійсно важливі події безпеки, залишаючи системні ресурси вільними для виконання основних завдань сервера.
