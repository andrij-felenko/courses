# 📋 Довідник sysctl-параметрів, прапорців Taint та формату Oops

Даний довідник містить вичерпний опис інтерфейсів керування реакцією ядра Linux на аварійні ситуації, розшифровку бітових прапорців забруднення ядра (Kernel Taint) та детальний анатомічний аналіз усіх полів текстового блоку Kernel Oops.

---

## 1. Конфігураційні параметри sysctl та аргументи завантаження ядра

Підсистема аварійної обробки ядра Linux надає системним адміністраторам та інженерам зв'язок із внутрішніми алгоритмами через файлову систему `/proc/sys/kernel/` та параметри командного рядка завантажувача (`bootloader command line`). Оскільки поведінка ядра при збоях вимагає балансу між доступністю сервісів (High Availability) та збереженням цілісності даних (Data Integrity), конфігураційні перемикачі дозволяють гнучко налаштовувати реакцію від ізольованого знищення одного потоку до миттєвого перезавантаження чи виклику аварійного ядра.

### Таблиця глобальних параметрів аварійного реагування

| Параметр sysctl | Файл у procfs | Аргумент cmdline | Значення за замовчуванням | Опис та поведінка ядра |
| :--- | :--- | :--- | :--- | :--- |
| `kernel.panic` | `/proc/sys/kernel/panic` | `panic=N` | `0` | Кількість секунд затримки перед автоматичним перезавантаженням системи після виклику `panic()`. Якщо значення дорівнює `0`, автоматичне перезавантаження вимкнено — ядро залишається в бескінечному циклі зупинки. Якщо `N > 0`, ядро чекає `N` секунд і виконує перезавантаження через апаратний контролер. Якщо `N < 0`, перезавантаження виконується миттєво без затримки. |
| `kernel.panic_on_oops` | `/proc/sys/kernel/panic_on_oops` | `oops=panic` | `0` | Визначає поведінку підсистеми `die()`. При `0` ядро знищує лише той потік (`task_struct`), який спричинив помилку, і намагається продовжити виконання. При `1` будь-який Kernel Oops негайно трансформується у фатальний виклик `panic()`. |
| `kernel.panic_on_warn` | `/proc/sys/kernel/panic_on_warn` | `panic_on_warn` | `0` | При значення `1` будь-яке "м'яке" попередження ядра, сформоване макросами `WARN()` або `WARN_ON()`, перетворюється на Kernel Panic. Режим використовується для автоматизованого стрес-тестування (fuzzing). |
| `kernel.panic_on_rcu_stall` | `/proc/sys/kernel/panic_on_rcu_stall` | `rcupdate.panic_on_rcu_stall=1` | `0` | При значення `1` виявлення затримки підсистеми Read-Copy Update (RCU stall тривалістю понад 21 секунду) ініціює виклик `panic()`. |
| `kernel.panic_on_stackoverflow` | `/proc/sys/kernel/panic_on_stackoverflow` | - | `0` | При значення `1` переповнення стека ядра (kernel stack overflow) викликає негайний `panic()` замість спроби обробити виняток у пошкодженому стеку. |
| `kernel.panic_on_io_nmi` | `/proc/sys/kernel/panic_on_io_nmi` | - | `0` | При значення `1` отримання немаскованого переривання NMI від I/O шини (апаратна помилка RAM або PCIe) викликає паніку ядра. |
| `kernel.unknown_nmi_panic` | `/proc/sys/kernel/unknown_nmi_panic` | - | `0` | При значення `1` отримання неідентифікованого NMI-переривання викликає `panic()`. |
| `kernel.hung_task_panic` | `/proc/sys/kernel/hung_task_panic` | `hung_task_panic=1` | `0` | При значення `1` виявлення потоку, який перебуває у стані безперервного очікування `TASK_UNINTERRUPTIBLE` (D-state) понад встановлений таймаут `hung_task_timeout_secs`, призводить до `panic()`. |
| `kernel.softlockup_panic` | `/proc/sys/kernel/softlockup_panic` | `softlockup_panic=1` | `0` | При значення `1` виявлення зависання ядра на одному з CPU з увімкненими перериваннями (Soft Lockup) викликає `panic()`. |
| `kernel.hardlockup_panic` | `/proc/sys/kernel/hardlockup_panic` | `nmi_watchdog=1` | `1` (на більшості систем) | При значення `1` NMI Watchdog при виявленні повністю заблокованого ядра CPU з вимкненими перериваннями (Hard Lockup) ініціює `panic()`. |

### Механізми застосування та особливості обробки параметрів

Налаштування параметрів аварійного реагування здійснюється як динамічно під час роботи системи, так і статично на етапі ініціалізації ядра завантажувачем:

1. **Динамічна зміна через sysctl:**
   Запис нових значень у файли `/proc/sys/kernel/` негайно змінює глобальні змінні C-коду ядра (розташовані у файлі `kernel/sysctl.c`). Наприклад, команда `sysctl -w kernel.panic_on_oops=1` модифікує внутрішню змінну `panic_on_oops`. Коли функція `die()` заходить у розгалуження перевірки умов, вона читає значення цієї атомарної змінної і передає керування на `panic()`.

2. **Передавання параметрів через завантажувач (Boot Parameters):**
   При завантаженні системи через GRUB, systemd-boot або UKI параметри командного рядка аналізуються ранньою функцією `parse_args()` під час виконання `start_kernel()`. Значення на кшталт `oops=panic` або `crashkernel=512M` закріплюються у пам'яті до моменту створення перших процесів простору користувача, що забезпечує захист системи від аварій навіть під час ініціалізації драйверів раннього стажу (`initramfs`).

3. **Взаємодія panic_timeout з апаратними таймерами (Watchdog Timer):**
   Якщо параметр `kernel.panic` встановлено у значення `N > 0`, функція `panic()` запускає зворотний відлік. Проте якщо апаратне забезпечення системи повністю заморожено і переривання таймера ядра не обробляються, затримка може зависнути. Для вирішення цього використовується зовнішній апаратний таймер вартівника (Hardware Watchdog Device, наприклад `/dev/watchdog`), який скидає систему апаратним сигналом `RESET`, якщо ядро припиняє регулярно надсилати йому сигнал живлення (`ping`).

## 2. Бітові прапорці забруднення ядра (Kernel Taint Flags)

Вміст файлу `/proc/sys/kernel/tainted` репрезентує десяткове число, яке утворюється шляхом побітового АБО (`OR`) прапорців у масці `taint_mask`. Якщо число дорівнює `0`, це означає, що ядро перебуває у повністю "чистому" стані (`untainted`) — усі завантажені модулі є відкритими, апаратне забезпечення працює у межах штатної специфікації, і в системі не фіксувалося жодних збоїв.

Поява навіть одного біта в масці `tainted` свідчить про те, що гарантії стабільності ядра порушено. Під час аналізу баг-репортів розробники Linux у першу чергу перевіряють статус Taint. Якщо ядро позначено прапорцем пропрієтарного модуля (`P`) або стороннього драйвера (`O`), розробники можуть відмовитися від розслідування, оскільки закритий код міг пошкодити внутрішні структури пам'яті ядра ще до виникнення аварії.

| Біт | Десяткове значення | Буквений код | Внутрішня константа ядра | Детальний опис та умови встановлення прапорця |
| :---: | :---: | :---: | :--- | :--- |
| `0` | `1` | `P` | `TAINT_PROPRIETARY_MODULE` | Завантажено модуль, що не має ліцензії, сумісної з GPL (Proprietary module). Встановлюється при виклику `init_module()` для модулів без макросу `MODULE_LICENSE("GPL")`. |
| `1` | `2` | `F` | `TAINT_FORCED_MODULE` | Модуль завантажено примусово за допомогою прапорця `--force` (`insmod -f`), ігноруючи невідповідність версії ядра або символів. |
| `2` | `4` | `S` | `TAINT_CPU_OUT_OF_SPEC` | Процесор працює поза специфікацією виробника (оверклокінг, некоректна частота або некоректна симетрія ядер у багатопроцесорній системі SMP). |
| `3` | `8` | `R` | `TAINT_FORCED_RMODULE` | Модуль було видалено з ядра примусово (`rmmod -f`). Це залишає ризик існування "висячих" вказівників (dangling pointers) на код модуля. |
| `4` | `16` | `M` | `TAINT_MACHINE_CHECK` | Системою зафіксовано апаратну помилку перевірки машини (Machine Check Exception, MCE), таку як невідновлювана помилка парності ECC-пам'яті або шини CPU. |
| `5` | `32` | `B` | `TAINT_BAD_PAGE` | Виявлено пошкодження структури сторінки пам'яті (`struct page`) або виявлено невалідні прапорці в таблиці сторінок (Page Table Entry corruption). |
| `6` | `64` | `U` | `TAINT_USER` | Прапорець забруднення було встановлено вручну з простору користувача шляхом запису значення у `/proc/sys/kernel/tainted`. |
| `7` | `128` | `D` | `TAINT_DIE` | У ядрі стався збій типу Kernel Oops або спрацював обробник `die()`. Вказує на те, що хоча система вижила, один із потоків ядра впав. |

| `9` | `512` | `W` | `TAINT_WARN` | У ядрі спрацювало "м'яке" попередження `WARN()` або `WARN_ON()`. Свідчить про виявлення нетипового стану коду, який ще не призвів до падіння. |
| `10` | `1024` | `C` | `TAINT_CRAP` | Завантажено модуль із підсистеми `staging` (експериментальний або застарілий драйвер низької якості, що перебуває на стадії розробки). |
| `11` | `2048` | `I` | `TAINT_FIRMWARE_WORKAROUND` | Задіяно спеціальний компенсаційний хак ядра для обходу бага в прошивці системної плати (BIOS/UEFI firmware bug workaround). |
| `12` | `4096` | `O` | `TAINT_OOT_MODULE` | Завантажено модуль, зібраний поза офіційним джерельним деревом ядра Linux (Out-of-tree module, наприклад DKMS-драйвер). |
| `13` | `8192` | `E` | `TAINT_UNSIGNED_MODULE` | Завантажено модуль без валідного цифрового підпису на ядрі з увімкненою перевіркою підписів (`CONFIG_MODULE_SIG_FORCE`). |
| `14` | `16384` | `L` | `TAINT_SOFTLOCKUP` | У системі зафіксовано випадок Soft Lockup (зависання одного з ядер CPU в режимі ядра при збереженні обробки переривань). |
| `15` | `32768` | `K` | `TAINT_LIVEPATCH` | До ядра було застосовано оперативну заплатку під час виконання без перезавантаження за допомогою підсистеми Kernel Livepatching (`klp`). |
| `16` | `65536` | `X` | `TAINT_AUX` | Допоміжний прапорець, зарезервований під специфічні потреби адаптації ядра комерційними дистрибутивами (Auxiliary taint). |
| `17` | `131072`| `T` | `TAINT_TEST` | Модуль ядра було зібрано з використанням інструментів рандомізації структур `randstruct` або тестувальних плагінів GCC/Clang. |

### Алгоритм обчислення та інтерпретації прапорців Taint

Для розшифрування десяткового значення з `/proc/sys/kernel/tainted` виконується бітова перевірка. Наприклад, якщо файл повертає значення `4609`:

```
4609 у двійковій системі = 1000100000001_2
Біт 0 (1)     -> TAINT_PROPRIETARY_MODULE (P)
Біт 9 (512)   -> TAINT_WARN (W)
Біт 12 (4096) -> TAINT_OOT_MODULE (O)
Сума: 1 + 512 + 4096 = 4609
```

Текстове представлення цього стану в логах Oops буде виглядати як `Tainted: P        W  O`. Порядок букв у дамп-рядку є суворо зафіксованим у масиві `taint_flags` у файлі `kernel/panic.c`. Якщо прапорець відсутній, на його місці виводиться пробіл.

## 3. Детальний анатомічний аналіз формату блоку Kernel Oops

Коли ядро формує звіт про збій у системному журналі `dmesg`, воно використовує стандартну структуру виводу. Нижче наведено повний реальний приклад Kernel Oops із покроковим текстовим аналізом кожного фрагмента.

### Покроковий розбір блоків журналу:

1. **Ідентифікатор винятку (Рядки 1–4):**
   - `[ 42.108492]` — штамп часу (uptime у секундах від завантаження ядра).
   - `BUG: unable to handle page fault for address: 0000000000000008` — загальний тип апаратної помилки та адреса пам'яті, спроба доступу до якої згенерувала виняток MMU.
   - `#PF: supervisor write access in kernel mode` — деталі Page Fault: виняток стався при операції запису у привілейованому режимі ядра.
   - `#PF: error_code(0x0002) - not-present page` — апаратний код помилки процесора x86: біт 1 дорівнює `1` (Write), біт 0 дорівнює `0` (Page not present).
   - `PGD 0 P4D 0` — стан глобального каталогу сторінок пам'яті (Page Global Directory). Значення `0` вказує, що для цієї віртуальної адреси не існує жодного мапування у таблиці сторінок.

2. **Заголовок Oops та метадані виконання (Рядки 5–7):**
   - `Oops: 0002 [#1]` — другий код помилки та порядковий номер Oops від моменту старта системи.
   - `PREEMPT SMP NOPTI` — параметри компіляції ядра: увімкнено витискання коду ядра (`PREEMPT`), підтримка багатопроцесорності (`SMP`), вимкнено ізоляцію сторінок ядра (`NOPTI`).
   - `CPU: 3` — логічний номер ядра процесора, на якому виконувався збійний потік.
   - `PID: 1422 Comm: my_app` — ідентифікатор та ім'я процесу простору користувача, у контексті системного виклику якого стався збій.
   - `Tainted: G W O 6.1.0-21-amd64 #1` — рядок статусу Taint та точна версія збірки ядра Linux.
   - `Hardware name:...` — ідентифікатор материнської плати або віртуальної машини (з ACPI/DMI таблиць).

3. **Вказівник інструкцій RIP та машиний код (Рядки 8–9):**
   - `RIP: 0010:my_driver_write+0x35/0x90 [my_driver]` — адреса збійної інструкції. Зміщення `+0x35` від початку функції `my_driver_write` у модулі `my_driver`.
   - `Code: ... <48> 89 50 08 ...` — шістнадцятковий дамп інструкцій машинного коду навколо точки падіння. Інструкція в кутових дужках `<48> 89 50 08` відповідає ассемблерній команді `mov %rdx, 0x8(%rax)`.

4. **Регістри процесора та стек (Рядки 10–16):**
   - `RSP: 0018:ffffa93201463d80` — вказівник на вершину стека ядра даного потоку.
   - `RAX: 0000000000000000` — вміст регістра `RAX`. Оскільки інструкція намагалася виконати `mov %rdx, 0x8(%rax)`, а `RAX` дорівнював `0`, це викликало делікатне розіменування нульового вказівника зі зміщенням `+0x8`.
   - `CR2: 0000000000000008` — лінійна адреса MMU, що збігається з адресою розіменування `RAX + 0x8`.

5. **Стек викликів Call Trace (Рядки 17–24):**
   - Блок `<TASK>` містить послідовність викликів функцій від системного виклику `entry_SYSCALL_64` через підсистему VFS (`vfs_write`) до функції модуля `my_driver_write`.
   - `RIP: 0033:0x7f9c2d2179b7` — адреса інструкції у просторі користувача (Ring 3, селектор `0x33`), яка ініціювала системний виклик `write()`.
