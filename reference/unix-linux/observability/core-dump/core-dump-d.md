Уявіть ситуацію: ви розробляєте складний мережевий сервіс на С++, який ідеально працює на вашому комп'ютері та в тестовому середовищі. Ви розгортаєте його на production-сервері, і через три дні, о 3-й годині ночі, він раптово падає з помилкою `Segmentation fault`. Жодних зрозумілих логів немає, клієнти скаржаться, а перезапуск сервісу лише відтерміновує наступне падіння. Ви не можете просто підключити зневаджувач (GDB) до production-сервісу й чекати кілька днів, доки він знову впаде. Як зрозуміти, що саме сталося в пам'яті програми в момент краху? Відповідь одна — аварійний дамп (core dump).

Аварійний дамп — це "посмертний" зліпок пам'яті процесу, збережений у файл у той самий момент, коли процес зазнав критичної помилки. Це немов фотографія місця злочину, на якій зафіксовано стан усіх потоків, регістрів процесора, стеків викликів і змінних. Маючи цей зліпок, ви можете спокійно аналізувати причини падіння на своїй робочій машині, не впливаючи на роботу production-системи.

У цій статті ми детально розглянемо, що таке core dump, як його налаштувати за допомогою `RLIMIT_CORE` та `core_pattern`, як сучасні системи Linux керують дампами через `systemd-coredump` (та утиліту `coredumpctl`), а також як ефективно використовувати GDB для аналізу таких дампів (команди `bt`, `info registers`, `thread apply all backtrace`). Ми також зазирнемо під капот і дізнаємося, яку роль відіграє сегмент `PT_NOTE` у форматі ELF при створенні дампів.

## Що таке Core Dump і коли він створюється

Термін "core dump" має глибоке історичне коріння. У 1950–1970-х роках оперативна пам'ять комп'ютерів виготовлялася з магнітних осердь (magnetic cores). Коли програма зазнавала краху, вміст цієї пам'яті буквально "скидався" (dumped) на папір або магнітну стрічку для подальшого аналізу. Сьогодні магнітні осердя давно пішли в минуле, але термін зберігся. 

В ОС Linux аварійний дамп генерується ядром, коли процес отримує певний сигнал, дія якого за замовчуванням полягає у завершенні процесу зі створенням дампа (terminate and dump core). До таких сигналів належать:
- `SIGSEGV` (11): Порушення сегментації (Segmentation fault). Найчастіша причина — звернення до неіснуючої або захищеної пам'яті (наприклад, розіменування null-вказівника).
- `SIGABRT` (6): Сигнал переривання (Abort). Зазвичай генерується самою програмою через виклик функції `abort()`, коли спрацьовує `assert()` або виникає критична помилка в стандартній бібліотеці (наприклад, "double free or corruption").
- `SIGFPE` (8): Помилка арифметики з рухомою комою (Floating-point exception). Також виникає при діленні на нуль для цілих чисел.
- `SIGILL` (4): Недопустима інструкція (Illegal instruction). Процесор зустрів код операції, який він не підтримує (часто буває при запуску скомпільованої під новіші процесори програми на старому обладнанні).
- `SIGBUS` (7): Помилка шини (Bus error). Зазвичай пов'язана з неправильним вирівнюванням пам'яті (misaligned memory access) або доступом до файлу, відображеного в пам'ять (mmap), розмір якого був змінений.
- `SIGQUIT` (3): Сигнал виходу. Генерується, коли користувач натискає `Ctrl+\` у терміналі.

Ось приклади коду, що гарантовано викликають генерацію дампів різними мовами:

:::tabs
== C++
```cpp
#include <iostream>

void crash_function(char* ptr) {
    // Розіменування нульового вказівника
    std::cout << *ptr << std::endl; 
}

int main() {
    char* data = nullptr;
    crash_function(data); // Згенерує SIGSEGV
    return 0;
}
```
== Python
```python
import ctypes

def crash_function():
    # Штучний виклик Segmentation fault через ctypes
    ctypes.string_at(0)

if __name__ == "__main__":
    crash_function() # Згенерує SIGSEGV
```
:::

Коли ядро обробляє один із цих сигналів (за умови, що процес не встановив власний обробник сигналу), воно призупиняє процес, збирає всю інформацію про його стан (пам'ять, регістри, інформацію про потоки) і записує її у файл. Після цього процес остаточно завершується.

## Налаштування генерації дампів: RLIMIT_CORE

Часто розробники стикаються з тим, що їхня програма падає з написом `Segmentation fault`, але жодного файлу `core` не з'являється. Чому так відбувається?

Справа в тому, що аварійні дампи можуть займати багато місця на диску (від десятків мегабайтів до сотень гігабайтів, залежно від того, скільки пам'яті споживав процес). Щоб запобігти вичерпанню дискового простору, у багатьох дистрибутивах Linux створення дампів за замовчуванням вимкнено або суворо обмежено на рівні операційної системи.

Управління ресурсами в Linux здійснюється через механізм *limits* (лімітів). Ліміт, що відповідає за максимальний розмір файлу дампа, називається `RLIMIT_CORE`. Він має два значення: "м'яке" (soft limit) і "жорстке" (hard limit). М'який ліміт користувач може змінювати самостійно в межах жорсткого, а жорсткий ліміт може збільшити лише суперкористувач (root).

Щоб перевірити поточний ліміт у командному рядку, використовується команда `ulimit`:

```bash
# Перевірити м'який ліміт на розмір core dump (в блоках по 512 байт, або 'unlimited')
$ ulimit -c
0
```

Значення `0` означає, що створення аварійних дампів повністю заборонено. Ядро навіть не буде намагатися створити дамп, якщо процес отримає SIGSEGV.

Щоб увімкнути генерацію дампів для поточної сесії термінала, потрібно встановити ліміт у значення `unlimited` (або конкретний розмір у кілобайтах):

```bash
# Зняти обмеження на розмір core dump
$ ulimit -c unlimited
```

Це налаштування діє лише для поточного оболонки (shell) та всіх процесів, які будуть запущені з неї. Якщо ви хочете зробити це налаштування постійним для всіх користувачів, необхідно відредагувати конфігураційний файл, зазвичай `/etc/security/limits.conf`:

```text
# /etc/security/limits.conf
# Дозволяємо створення core dumps необмеженого розміру для всіх користувачів
*               soft    core            unlimited
*               hard    core            unlimited
```

Для системних сервісів (systemd units) ліміт налаштовується в їхньому конфігураційному файлі `.service`:

```ini
[Service]
# Дозволити дампи для цього сервісу
LimitCORE=infinity
```

Важливий нюанс: якщо програма використовує `setuid` або `setgid` (тобто виконується з правами іншого користувача, зазвичай root), ядро з міркувань безпеки за замовчуванням не створює дампи для неї, щоб уникнути витоку конфіденційної інформації. Це поведінкою керує параметр `/proc/sys/fs/suid_dumpable`. Його можна встановити в `1` (debug) або `2` (suidsafe) для дозволу дампів.

## Куди ядро пише дампи: core_pattern

Добре, ми дозволили створення дампів за допомогою `ulimit -c unlimited`. Програма впала. Де шукати файл дампа?

Історично склалося так, що ядро записувало файл із назвою `core` безпосередньо в поточну робочу директорію (Current Working Directory) процесу, що впав. Однак це було не дуже зручно: файли розкидалися по всій файловій системі, їх було важко відстежувати, а при кількох падіннях поспіль новий дамп просто перезаписував старий.

У сучасному Linux шлях і ім'я файлу дампа гнучко налаштовуються через параметр ядра `kernel.core_pattern`, який можна прочитати або змінити у файлі `/proc/sys/kernel/core_pattern` або через `sysctl`.

```bash
# Перевірка поточного шаблону
$ cat /proc/sys/kernel/core_pattern
```

Шаблон підтримує спеціальні макроси (специфікатори), що починаються зі знака `%`, які ядро автоматично замінює на інформацію про процес, що впав:
- `%e` — ім'я виконуваного файлу (executable).
- `%p` — ідентифікатор процесу (PID).
- `%s` — номер сигналу, що спричинив падіння.
- `%t` — час падіння в секундах з початку епохи (UNIX timestamp).
- `%u` та `%g` — UID та GID користувача, від імені якого працював процес.
- `%h` — ім'я хоста (hostname).

Наприклад, якщо ми встановимо такий шаблон:
```bash
$ sudo sysctl -w kernel.core_pattern=/var/crash/core-%e-pid%p-sig%s-ts%t
```
Тоді при падінні процесу `my_server` (PID 1234) від сигналу 11 (SIGSEGV) у час 1678880000, ядро створить файл `/var/crash/core-my_server-pid1234-sig11-ts1678880000`. Це дуже зручно, адже всі дампи збираються в одній папці й ніколи не перезаписують одне одного.

### Pipes (|) у core_pattern: магія перенаправлення

Найцікавіша можливість `core_pattern` з'явилася у версії ядра 2.6.19. Якщо перший символ у шаблоні — це вертикальна риска (`|`), ядро сприймає все, що написано після неї, не як шлях до файлу, а як команду!

Ядро запускає зазначену програму, передає їй аргументи (зазвичай сформовані за допомогою тих самих макросів `%e`, `%p` тощо) і "вливає" вміст аварійного дампа їй на стандартний ввід (stdin) (через pipe).

Це дозволяє передати роботу зі збереження, стиснення, аналізу чи відправлення дампа спеціалізованій програмі в користувацькому просторі (userspace), замість того щоб ядро самотужки писало гігабайти на диск.

Наприклад:
```text
|/usr/local/bin/core_handler.sh %p %e %s
```

Сучасні дистрибутиви (Ubuntu, Fedora, Arch Linux) активно використовують цю можливість, перенаправляючи дампи в спеціальні системи, такі як `apport` (в Ubuntu), `ABRT` (у RHEL/CentOS) або `systemd-coredump` (майже скрізь, де є systemd).

## systemd-coredump: сучасний збір дампів

Якщо ви використовуєте сучасний дистрибутив Linux із systemd, найімовірніше, ваш `core_pattern` виглядає приблизно так:

```bash
$ cat /proc/sys/kernel/core_pattern
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h
```

Це означає, що при падінні програми ядро передає дамп програмі `systemd-coredump`. Що робить ця утиліта?
1. Вона збирає метадані про процес (час, ім'я, аргументи командного рядка, змінні оточення, cgroup тощо).
2. Вона стискає дамп (наприклад, за допомогою алгоритму zstd або lz4). Це критично важливо, оскільки стиснутий дамп зазвичай у 10-20 разів менший за оригінальний об'єм пам'яті (пам'ять часто містить багато нулів або текстових даних).
3. Вона зберігає стиснутий файл на диск, зазвичай у директорію `/var/lib/systemd/coredump/`.
4. Найголовніше: вона записує подію в **системний журнал (Journald)**.

Це геніальне рішення, оскільки тепер дампи прив'язані до загальносистемних логів, а їхнє зберігання автоматично очищується (ротується), коли місце на диску закінчується, згідно з конфігурацією `/etc/systemd/coredump.conf`.

### Використання coredumpctl

Оскільки дампи тепер стиснуті й заховані глибоко у `/var/lib/systemd/coredump/`, для роботи з ними systemd надає спеціальну утиліту `coredumpctl`.

Щоб переглянути всі дампи, збережені в системі:
```bash
$ coredumpctl list
TIME                            PID  UID  GID SIG     COREFILE EXE               SIZE
Tue 2026-08-10 14:15:00 EEST   5432 1000 1000 SIGSEGV present  /usr/bin/my_server 15M
Tue 2026-08-10 14:20:15 EEST   5678 1000 1000 SIGABRT present  /usr/bin/python3   2.1M
```

Щоб отримати детальну інформацію про конкретне падіння (за PID):
```bash
$ coredumpctl info 5432
           PID: 5432 (my_server)
           UID: 1000 (user)
           GID: 1000 (user)
        Signal: 11 (SEGV)
     Timestamp: Tue 2026-08-10 14:15:00 EEST (25 min ago)
  Command Line: ./my_server --port 8080
    Executable: /usr/bin/my_server
       Storage: /var/lib/systemd/coredump/core.my_server.1000.1a2b3c...zst (present)
```

Цікаво, що `coredumpctl` одразу записує в журнал "мікро-backtrace" — спробу розібрати стек викликів, щоб ви могли хоча б приблизно зрозуміти, де відбулося падіння, навіть без ручного запуску GDB.

Але якщо вам потрібен повноцінний аналіз, ви можете запустити GDB прямо з `coredumpctl`:
```bash
$ coredumpctl gdb 5432
```
`coredumpctl` автоматично розпакує дамп, знайде відповідний виконуваний файл і передасть їх у GDB. Це неймовірно економить час. Якщо ж ви хочете експортувати дамп, щоб передати його іншому розробнику (або проаналізувати на іншій машині), використовуйте команду:
```bash
$ coredumpctl dump 5432 -o my_server.core
```

## Анатомія дампа: формат ELF і PT_NOTE

Перш ніж переходити до практичного аналізу в GDB, давайте трохи зазирнемо "під капот". Що насправді являє собою файл дампа на диску?

Можливо, ви здивуєтеся, але аварійний дамп у Linux — це звичайнісінький файл у форматі **ELF** (Executable and Linkable Format). Тобто той самий формат, що й у звичайних виконуваних програм (на кшталт `/bin/ls`) або динамічних бібліотек (`.so`).

Якщо ми натравимо утиліту `file` або `readelf` на файл дампа, ми побачимо це:
```bash
$ file my_server.core
my_server.core: ELF 64-bit LSB core file, x86-64, version 1 (SYSV), SVR4-style
```
Зверніть увагу на тип файлу: `core file` (в заголовку ELF це тип `ET_CORE`).

На відміну від звичайного виконуваного файлу (`ET_EXEC` або `ET_DYN`), у якому секції (sections) та сегменти (segments) містять інструкції коду (текст) і статичні дані, файл дампа містить зліпки віртуальної пам'яті (VMA — Virtual Memory Areas), що були виділені процесу на момент падіння.

Кожна ділянка пам'яті (наприклад, купа/heap, стеки потоків, mmap-регіони) записується у файл як окремий сегмент `PT_LOAD`. Тому дамп може бути величезним.

Але найцікавіший сегмент у файлі дампа має тип **`PT_NOTE`**. Саме тут ядро Linux зберігає специфічні метадані про процес, без яких зневаджувач не зміг би нічого зрозуміти. Сегмент `PT_NOTE` складається з масиву структур (notes), кожна з яких має тип і дані. Серед найважливіших "нотаток" (notes) можна виділити:

1. `NT_PRSTATUS` (Process Status): Найважливіший запис. Він містить структуру, що зберігає інформацію про конкретний потік виконання (thread), включно зі значеннями **всіх регістрів процесора** на момент падіння (Instruction Pointer, Stack Pointer, регістри загального призначення). Якщо в програмі було 10 потоків, у файлі буде 10 записів `NT_PRSTATUS`.
2. `NT_PRPSINFO` (Process ps-info): Загальна інформація про процес, аналогічна тій, яку показує утиліта `ps` (ім'я програми, PID, аргументи командного рядка, UID).
3. `NT_SIGINFO`: Детальна інформація про сигнал, що вбив процес (номер сигналу, код помилки, адреса пам'яті, що спричинила page fault, якщо це був SIGSEGV).
4. `NT_FILE`: Список файлів, які були відображені в пам'ять (mmap). Це дозволяє GDB знайти динамічні бібліотеки (`.so`), що використовувалися процесом.

Тобто, коли GDB аналізує дамп, він спочатку читає `PT_NOTE`. Звідти він дістає стан регістрів (наприклад, регістр `RIP` на x86-64 — де зупинився код, і `RSP` — де знаходиться вершина стеку). Потім GDB дивиться в сегменти `PT_LOAD`, щоб знайти пам'ять стеку. Маючи `RSP` і пам'ять стеку, GDB може "розкрутити" ланцюжок викликів назад і показати вам `backtrace`.

## Практика: аналіз дампа в GDB

Отже, у нас є виконуваний файл (`my_server`) і файл дампа (`my_server.core`). Щоб почати аналіз, запускаємо GNU Debugger (GDB), передаючи йому обидва файли:

```bash
$ gdb ./my_server ./my_server.core
```

Важливе зауваження: щоб аналіз був ефективним, ваш виконуваний файл повинен містити **відлагоджувальні символи** (debug symbols). Вони генеруються під час компіляції з прапорцем `-g` (наприклад, `gcc -g main.c`). Без символів GDB зможе показати лише шістнадцяткові адреси пам'яті, і вам буде дуже складно зрозуміти, на якому саме рядку вихідного коду сталася помилка. У production-середовищі часто використовують "розділені символи" (split debuginfo): символи вирізаються з бінарного файлу за допомогою `objcopy` (щоб зменшити розмір), а потім завантажуються в GDB окремо (наприклад, через команду `symbol-file`).

Після завантаження GDB одразу прочитає `PT_NOTE`, знайде потік, який спричинив падіння, і покаже вам точну інструкцію та рядок коду.

### Команда bt (backtrace)

Перше, що ви завжди робите при аналізі дампа, — вводите команду `bt` (скорочення від `backtrace`). Вона виводить "стек викликів" — послідовність функцій, які викликали одна одну і привели до поточного стану.

```gdb
(gdb) bt
#0  0x00005555555551c9 in crash_function (ptr=0x0) at main.cpp:15
#1  0x00005555555551f3 in process_data (data=0x7fffffffe010) at main.cpp:25
#2  0x000055555555521b in worker_thread (arg=0x0) at main.cpp:32
#3  0x00007ffff7fa3b43 in start_thread (arg=<optimized out>) at ./nptl/pthread_create.c:442
#4  0x00007ffff7f41a00 in clone3 () at ../sysdeps/unix/sysv/linux/x86_64/clone3.S:81
```

Цей вивід читається знизу вгору. Потік почав своє життя у функції `clone3` (системний виклик створення потоку), потім викликав обгортку `start_thread` з бібліотеки `pthread`, яка викликала нашу функцію `worker_thread`. Вона, своєю чергою, викликала `process_data`, і нарешті `crash_function`, де на рядку 15 файлу `main.cpp` програма впала.

Ми бачимо, що аргумент `ptr` має значення `0x0` (тобто це null-вказівник). Якщо на рядку 15 ми намагаємося звернутися до `ptr->value`, це неминуче призведе до SIGSEGV (доступу до нульової сторінки пам'яті).

Якщо ви хочете побачити не лише імена функцій, а й локальні змінні в кожному фреймі стеку, використовуйте `bt full`:
```gdb
(gdb) bt full
```

### Навігація фреймами та змінні

Ви можете переміщатися між "фреймами" (кадрами) стеку за допомогою команд `up` (вгору по стеку викликів, тобто до функції, що викликала) і `down` (вниз). Або вибрати конкретний фрейм командою `frame <номер>`.

Наприклад, перейдемо у фрейм 1 (`process_data`), щоб подивитися, чому він передав null-вказівник у `crash_function`:

```gdb
(gdb) frame 1
#1  0x00005555555551f3 in process_data (data=0x7fffffffe010) at main.cpp:25
25          crash_function(data->buffer);
(gdb) print data
$1 = (Data *) 0x7fffffffe010
(gdb) print data->buffer
$2 = (char *) 0x0
```
За допомогою команди `print` (або `p`) ми можемо інспектувати значення будь-яких змінних, які були в пам'яті на той момент. Ми бачимо, що об'єкт `data` існує, але його поле `buffer` дорівнює нулю.

### Аналіз багатопотокових програм: thread apply all backtrace

Сучасні програми (особливо веб-сервери та бази даних) зазвичай мають десятки або сотні потоків. Коли програма падає, ядро записує в дамп стан **усіх** потоків, а не лише того, у якому виникла помилка. Це надзвичайно корисно, оскільки причиною падіння одного потоку часто є дії іншого (наприклад, deadlock, або інший потік звільнив пам'ять (free), до якої ми зараз намагаємося звернутися — use-after-free).

Щоб переглянути список усіх потоків, використовуйте команду:
```gdb
(gdb) info threads
  Id   Target Id                                          Frame 
* 1    Thread 0x7ffff7a00640 (LWP 5432) "my_server"       crash_function (ptr=0x0) at main.cpp:15
  2    Thread 0x7ffff71ff640 (LWP 5433) "my_server_w1"    0x00007ffff7f340bf in __GI___poll (...)
  3    Thread 0x7ffff69fe640 (LWP 5434) "my_server_w2"    __futex_abstimed_wait_common (...)
```
(Зірочка вказує на поточний потік, який GDB аналізує в даний момент).

Але найбільш потужна команда для отримання "зрізу" всієї програми — це `thread apply all backtrace` (або `thread apply all bt`). Ця команда пройдеться по всіх потоках і виведе backtrace для кожного з них:

```gdb
(gdb) thread apply all bt
```
Якщо виведення дуже велике, ви можете зберегти його у файл для подальшого вивчення:
```gdb
(gdb) set logging file coredump_analysis.txt
(gdb) set logging on
(gdb) thread apply all bt
(gdb) set logging off
```

Аналізуючи цей файл, ви можете побачити, що, наприклад, потік 3 чекає на м'ютекс (futex_wait), а потік 2 завис у системному виклику читання з мережі (`poll`).

### Апаратний рівень: info registers

Іноді падіння стається в місці, де у вас немає вихідного коду (наприклад, всередині пропрієтарної динамічної бібліотеки або збірки стандартної бібліотеки C без символів відлагодження). Тоді вам доводиться опускатися на рівень асемблера та процесорних регістрів.

Як ми пам'ятаємо, сегмент `PT_NOTE` містить стан усіх регістрів на момент падіння. Щоб їх переглянути, використовуйте команду `info registers` (або `i r`):

```gdb
(gdb) info registers
rax            0x0                 0
rbx            0x7fffffffe010      140737488347152
rcx            0x5555555551c9      93824992235977
rdx            0x0                 0
rsi            0x0                 0
rdi            0x0                 0
rbp            0x7fffffffdfe0      0x7fffffffdfe0
rsp            0x7fffffffdfc0      0x7fffffffdfc0
rip            0x5555555551c9      0x5555555551c9 <crash_function(char*)+4>
eflags         0x10202             [ IF RF ]
...
```

Тут ми чітко бачимо, що `RIP` (Instruction Pointer, вказівник інструкції) вказує на адресу `0x5555555551c9`. А перший аргумент функції (`rdi` у конвенції викликів x86-64 для Linux) дорівнює нулю (`0x0`). Це пояснює падіння.

Щоб побачити самі асемблерні інструкції навколо місця падіння, використовуйте команду `disassemble` (або `disas`):

```gdb
(gdb) disassemble
Dump of assembler code for function crash_function(char*):
   0x00005555555551c5 <+0>:     push   %rbp
   0x00005555555551c6 <+1>:     mov    %rsp,%rbp
   0x00005555555551c9 <+4>:     mov    %rdi,-0x8(%rbp)
=> 0x00005555555551cd <+8>:     mov    -0x8(%rbp),%rax
   0x00005555555551d1 <+12>:    movzbl (%rax),%eax       # <--- ТУТ СТАЛАСЯ ПОМИЛКА
   0x00005555555551d4 <+15>:    movsbl %al,%eax
...
```
Стрілочка `=>` показує наступну інструкцію, яку мав виконати процесор. Тобто падіння сталося на інструкції `movzbl (%rax),%eax`. Ця інструкція означає: "прочитай 1 байт за адресою, збереженою в регістрі `rax`, розшир його до 32 біт і поклади в `eax`". Якщо ми подивимося на вивід `info registers`, то побачимо, що в регістрі `rax` лежав нуль. Розіменування нульової адреси (`(%rax)`) на рівні процесора викликало апаратне переривання Page Fault, яке ядро Linux конвертувало в сигнал `SIGSEGV` і відправило процесу, що врешті призвело до створення цього самого core dump.

## Загальні поради щодо роботи з дампами

1. **Зберігайте бінарники та символи**: Якщо ви компілюєте програму і розгортаєте її на серверах, обов'язково зберігайте не лише самі виконувані файли, а й `.debug` файли з символами (наприклад, на сервері збірки або в архіві артефактів). Без точної копії бінарного файлу і символів, які збігаються з дампами, аналіз буде вкрай складним. GDB використовує ідентифікатори збірки (Build ID) у форматі ELF, щоб переконатися, що бінарний файл і дамп належать до однієї і тієї ж компіляції.
2. **Безпека**: Пам'ятайте, що аварійний дамп містить **усю** пам'яті процесу. Це означає, що там у відкритому вигляді лежать паролі користувачів, які вводилися в цей момент, приватні ключі TLS/SSL, вміст зашифрованих баз даних тощо. Зберігайте файли дампів у захищених директоріях з обмеженими правами доступу і будьте обережні при передачі їх через інтернет.
3. **Обмеження за часом і ресурсами**: Генерація дампа для процесу, що споживає десятки гігабайтів оперативної пам'яті (наприклад, бази даних), може зайняти багато часу і спричинити високе навантаження на диск (I/O). У критичних системах це може призвести до "зависання" інших процесів, які чекають на диск. У таких випадках іноді доцільніше вимкнути дампи або обмежити їхній розмір.
4. **ASLR**: Address Space Layout Randomization — це механізм безпеки, який при кожному запуску програми розміщує її в пам'яті за різними адресами. На щастя, інформація в `PT_NOTE` та секціях дампа містить усі необхідні зсуви (offsets), тому GDB автоматично враховує ASLR при аналізі дампа, і вам не потрібно вручну вираховувати реальні адреси функцій.

Аварійні дампи — це найпотужніший інструмент у вашому арсеналі для вирішення найскладніших проблем типу "воно падає лише іноді й тільки в production". Навчившись правильно налаштовувати їх збір та майстерно орудувати GDB, ви зможете "розплутати" навіть найскладніший клубок помилок у C/C++ програмах.
