# /proc: процеси як файли

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Однією з найвизначніших ідей, закладених в основу Unix, є концепція **«усе є файлом»** (everything is a file). Це означає, що доступ до більшості ресурсів системи (апаратних пристроїв, сокетів, каналів, і навіть конфігураційних параметрів ядра) здійснюється через стандартні інтерфейси роботи з файлами: `open()`, `read()`, `write()`, `close()`.

Файлова система `/proc` (procfs) є одним з найяскравіших і найпотужніших втілень цієї філософії. Вона являє собою **псевдофайлову систему**, яка існує виключно в оперативній пам'яті (RAM) і не займає місця на фізичному накопичувачі. Ядро операційної системи динамічно створює вміст цих файлів і каталогів у момент, коли користувач або програма до них звертається.

В операційній системі Linux `/proc` відіграє роль головного інформаційного та керувального вікна у внутрішній світ ядра та запущених процесів. Спочатку, як видно з назви (від "processes"), procfs була розроблена виключно для надання інформації про запущені процеси. Проте з розвитком Linux її роль суттєво розширилася: сьогодні `/proc` містить величезний обсяг інформації про апаратне забезпечення, статистику роботи системи, конфігурацію мережі, підсистему віртуальної пам'яті та багато іншого.

У цій статті ми детально розглянемо внутрішню архітектуру `/proc`, її найважливіші компоненти та механізми взаємодії з нею як з боку користувацького простору, так і з боку ядра.

## 1. Архітектура procfs у ядрі Linux

Оскільки `procfs` є віртуальною файловою системою, вона підпорядковується архітектурі **VFS (Virtual File System)** ядра Linux. VFS надає абстрактний шар, який дозволяє користувацьким програмам використовувати стандартні системні виклики для доступу до різних типів файлових систем, не знаючи їхніх внутрішніх деталей.

Коли ви монтуєте `procfs` (зазвичай це робиться автоматично під час завантаження системи за допомогою команди на кшталт `mount -t proc proc /proc`), VFS реєструє її обробники операцій. 

### Як формується вміст?

Вміст файлів у `/proc` не зберігається на диску, він генерується **«на льоту»**. Коли ви читаєте файл, наприклад, `cat /proc/meminfo`, ядро викликає спеціально зареєстровану функцію для цього «файлу». Ця функція збирає актуальні дані з внутрішніх структур ядра (в даному випадку — зі структур підсистеми управління пам'яттю), форматує їх у текстовий вигляд і повертає як результат читання.

Більшість файлів у `/proc` використовують механізм **seq_file**. `seq_file` — це API ядра, створений спеціально для того, щоб полегшити виведення послідовних текстових даних, обсяг яких може перевищувати розмір однієї сторінки пам'яті (зазвичай 4 КБ). До впровадження `seq_file` створення великих віртуальних файлів у `/proc` було складною та часто схильною до помилок задачею через необхідність ручного керування буферами та зміщеннями.

### Структури даних ядра

Кожен елемент (каталог, файл, символічне посилання) в межах `procfs` представлений у ядрі структурою `proc_dir_entry`. Ця структура містить ім'я вузла, його права доступу, вказівники на функції, які оброблятимуть читання та запис, а також вказівники на дочірні та батьківські елементи дерева.

```c
// Спрощене подання структури з ядра Linux (fs/proc/internal.h)
struct proc_dir_entry {
    atomic_t in_use;
    refcount_t refcnt;
    struct list_head pde_openers;
    spinlock_t pde_unload_lock;
    struct completion *pde_unload_completion;
    const struct inode_operations *proc_iops;
    const struct file_operations *proc_fops; // Операції файлу (read, write)
    union {
        const struct seq_operations *seq_ops; // Операції seq_file
        int (*single_show)(struct seq_file *, void *);
    };
    void *data;
    unsigned int low_ino;
    nlink_t nlink;
    kuid_t uid;
    kgid_t gid;
    loff_t size;
    struct proc_dir_entry *parent; // Батьківський каталог
    struct rb_root subdir;         // Дерево нащадків
    // ... інші поля ...
    char name[];                   // Ім'я файлу/каталогу
};
```

Коли відбувається звернення до файлу, ядро за допомогою VFS перетворює шлях на конкретний об'єкт `inode`. Для файлів `procfs` цей `inode` пов'язується з відповідним `proc_dir_entry`, з якого потім витягуються операції файлу (`proc_fops`).

## 2. Анатомія процесу: каталог /proc/PID

Первісна і найголовніша функція `/proc` — надання детальної інформації про кожен запущений процес у системі. Для кожного процесу створюється каталог, ім'я якого відповідає числовому ідентифікатору процесу (**PID**).

Наприклад, якщо процес має `PID 1234`, вся інформація про нього міститиметься в каталозі `/proc/1234/`. Якщо ви подивитеся в корінь `/proc`, ви побачите безліч каталогів із числами — це і є каталоги процесів. (Особливий каталог `/proc/self/` є символічним посиланням на каталог процесу, який здійснює до нього звернення).

Рис. 1 показує структуру файлової системи /proc, яку генерує `figs.py`.

![Структура procfs](proc-structure.svg)

Розглянемо найважливіші файли та каталоги, що знаходяться всередині `/proc/PID/`.

### 2.1. cmdline та environ

- **/proc/PID/cmdline**
  Цей файл містить повний командний рядок, за допомогою якого було запущено процес, включаючи всі аргументи. Особливістю цього файлу є те, що аргументи розділяються не пробілами, а нуль-символом (`\0`). Якщо процес змінив свій командний рядок (що можливо шляхом перезапису масиву `argv`), тут буде відображено нове значення.
  
  Щоб зручно переглянути цей файл, можна використати команду `tr` або `cat -v`:
  ```bash
  $ tr '\0' ' ' < /proc/1234/cmdline
  /usr/sbin/nginx -g daemon off;
  ```

- **/proc/PID/environ**
  Містить змінні оточення (environment variables), які були передані процесу під час його запуску. Як і в `cmdline`, змінні розділені нуль-символом. Формат запису: `KEY=value\0KEY2=value2\0`.
  
  Цей файл є надзвичайно корисним для налагодження. Наприклад, якщо програма не може знайти певну конфігурацію, ви можете перевірити, які саме змінні оточення (наприклад, `PATH` або `HOME`) вона бачить.
  ```bash
  $ tr '\0' '\n' < /proc/1234/environ | grep PATH
  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
  ```

### 2.2. stat, statm та status

Ця трійка файлів надає вичерпну інформацію про стан процесу, споживання пам'яті та інші метрики.

- **/proc/PID/stat**
  Містить інформацію про стан процесу у форматі, зручному для машинного розбору (один довгий рядок значень, розділених пробілами). Саме цей файл читають утиліти на кшталт `ps` або `top`.
  
  Тут містяться десятки полів, серед яких:
  - PID процесу.
  - Ім'я виконуваного файлу (в круглих дужках).
  - Стан процесу (`R` - running, `S` - sleeping, `D` - disk sleep, `Z` - zombie, `T` - stopped).
  - PPID (ідентифікатор батьківського процесу).
  - ID групи процесів, ID сесії.
  - Час, проведений у просторі користувача (`utime`) та просторі ядра (`stime`) у "тіках" годинника.
  - Пріоритет планувальника (nice value).
  - Обсяг віртуальної пам'яті (`vsize`) та Resident Set Size (`rss`).

- **/proc/PID/statm**
  Надає інформацію про використання пам'яті процесом. Дані подані в кількості сторінок пам'яті (зазвичай розмір сторінки — 4 КБ). Складається з 7 колонок:
  1. `size` (загальний розмір віртуальної пам'яті).
  2. `resident` (кількість сторінок, фізично присутніх у RAM).
  3. `shared` (розділяється з іншими процесами, наприклад, спільні бібліотеки).
  4. `text` (код програми).
  5. `lib` (бібліотеки — починаючи з ядра 2.6, зазвичай 0).
  6. `data` (дані та стек).
  7. `dt` (брудні сторінки — з ядра 2.6 зазвичай 0).

- **/proc/PID/status**
  Це файл, створений спеціально для читання людиною. Він містить більшу частину інформації з `stat` та `statm`, але у зручному форматі "Ключ: Значення".
  
  ```bash
  $ cat /proc/1234/status | head -n 10
  Name:   bash
  Umask:  0022
  State:  S (sleeping)
  Tgid:   1234
  Ngid:   0
  Pid:    1234
  PPid:   1233
  TracerPid:      0
  Uid:    1000    1000    1000    1000
  Gid:    1000    1000    1000    1000
  ```
  Тут можна побачити не лише загальний стан, але й реальні, ефективні, збережені та файлові UID/GID, маски сигналів, інформацію про використання пам'яті (`VmPeak`, `VmSize`, `VmRSS`, `VmData`, `VmStk`, `VmExe`, `VmLib`) та потоки.

### 2.3. Пам'ять: maps, smaps та mem

Розуміння того, як процес використовує адресний простір, є критичним для розробників, хакерів та фахівців з безпеки.

- **/proc/PID/maps**
  Показує розкладку віртуальної пам'яті (memory layout) процесу. Кожен рядок описує один безперервний регіон віртуальної пам'яті (Virtual Memory Area - VMA).
  
  Формат рядка:
  `address           perms offset  dev   inode      pathname`
  `7f8a1b2c0000-7f8a1b2c2000 r-xp 00000000 08:01 123456 /lib/x86_64-linux-gnu/libc.so.6`
  
  - **address**: початкова і кінцева віртуальні адреси регіону.
  - **perms**: права доступу. `r` (читання), `w` (запис), `x` (виконання), `p` (private, копіювання при записі - Copy-On-Write), `s` (shared).
  - **offset**: зміщення у файлі (якщо регіон спроектований на файл).
  - **dev**: major:minor номери пристрою, де лежить файл.
  - **inode**: номер inode файлу на пристрої.
  - **pathname**: шлях до файлу (або псевдо-шляхи на кшталт `[heap]`, `[stack]`, `[vdso]`).

- **/proc/PID/smaps** (і **smaps_rollup**)
  Є розширеною версією `maps`. Для кожного регіону пам'яті, крім базової інформації, `smaps` виводить деталізовану статистику його використання: скільки пам'яті є Rss (Resident Set Size), Pss (Proportional Set Size - з урахуванням розділення пам'яті між процесами), Shared_Clean, Shared_Dirty, Private_Clean, Private_Dirty тощо. Це ключовий файл для виявлення витоків пам'яті.
  
  `smaps_rollup` надає ті самі дані, але підсумовані для всього процесу.

- **/proc/PID/mem**
  Цей файл репрезентує фізичну пам'ять процесу. За допомогою `mem` можна безпосередньо читати або писати в адресний простір процесу. Проте для того, щоб читання було успішним, ви повинні використати `lseek()` або `pread()` для переходу на коректну віртуальну адресу (яку можна дізнатися з `maps`). Крім того, доступ до `mem` жорстко контролюється механізмами безпеки (наприклад, через обмеження `ptrace`).

### 2.4. Файлові дескриптори: fd/ та fdinfo/

Процеси в Unix постійно працюють з файлами, сокетами та каналами, використовуючи файлові дескриптори.

- **/proc/PID/fd/**
  Цей каталог містить символічні посилання на всі файли, відкриті процесом. Ім'я кожного посилання — це число, що дорівнює номеру файлового дескриптора.
  
  ```bash
  $ ls -l /proc/1234/fd/
  total 0
  lrwx------ 1 user user 64 Jan  1 12:00 0 -> /dev/pts/0
  lrwx------ 1 user user 64 Jan  1 12:00 1 -> /dev/pts/0
  lrwx------ 1 user user 64 Jan  1 12:00 2 -> /dev/pts/0
  lr-x------ 1 user user 64 Jan  1 12:00 3 -> /var/log/syslog
  lrwx------ 1 user user 64 Jan  1 12:00 4 -> socket:[1234567]
  ```
  Тут `0`, `1`, `2` — це стандартний ввід, вивід та помилки (stdin, stdout, stderr). Дескриптор `3` відкрив файл логів, а `4` — це мережевий або локальний сокет. Це неймовірно зручно: якщо ви випадково видалили файл, який все ще відкритий якоюсь програмою, ви можете відновити його вміст, скопіювавши відповідний дескриптор з `/proc/PID/fd/`!

- **/proc/PID/fdinfo/**
  Тут лежать звичайні файли, імена яких відповідають номерам дескрипторів. Вони містять метаінформацію про відкритий файловий дескриптор: поточну позицію у файлі (`pos`), прапорці доступу (`flags`, наприклад `O_RDONLY`), і (для деяких типів) інформацію про блокування.

### 2.5. Простори імен і Cgroups

Сучасний Linux неможливо уявити без контейнерів. Технології контейнеризації (Docker, LXC, Kubernetes) спираються на два фундаментальних механізми ядра: namespaces (простори імен, що забезпечують ізоляцію) та cgroups (контрольні групи, що забезпечують лімітування ресурсів).

- **/proc/PID/ns/**
  Цей каталог містить файли (магічні символічні посилання), що представляють простори імен, до яких належить процес: `cgroup`, `ipc`, `mnt`, `net`, `pid`, `user`, `uts`.
  Якщо два процеси мають однаковий inode для `ns/net`, вони знаходяться в одному мережевому просторі імен і мають спільні мережеві інтерфейси та таблиці маршрутизації. За допомогою системного виклику `setns()` процес може "приєднатися" до простору імен іншого процесу, відкривши відповідний файл з цього каталогу.

- **/proc/PID/cgroup**
  Описує належність процесу до контрольних груп. Кожен рядок визначає ієрархію, підсистему (наприклад, `cpu`, `memory`, `blkio`) та шлях до cgroup в рамках цієї ієрархії. У cgroups v2 (уніфікованій ієрархії) цей файл зазвичай містить один рядок із записом типу `0::/user.slice/user-1000.slice/...`.

## 3. Керування ядром: /proc/sys (sysctl)

Якщо каталог `/proc/PID/` призначений для моніторингу процесів, то каталог `/proc/sys/` — це центр керування всією операційною системою.

Це інтерфейс до механізму **sysctl**, який дозволяє читати та динамічно змінювати параметри ядра під час його роботи, без необхідності перекомпіляції або перезавантаження.

Файли в `/proc/sys/` не є звичайними. Більшість з них містять лише одне число, рядок або масив чисел. Ви можете змінити поведінку системи, просто записавши нове значення в ці файли (якщо у вас є права `root`).

Структура `/proc/sys/` поділяється за підсистемами ядра:

### 3.1. /proc/sys/kernel/
Керує основними функціями ядра.
- `kernel/pid_max`: Максимальний PID, який може бути виданий процесу. За замовчуванням часто 32768, але на великих серверах його збільшують (до 4194304).
- `kernel/panic`: Кількість секунд, після яких ядро автоматично перезавантажить систему в разі виникнення kernel panic. Значення 0 означає, що система буде нескінченно чекати на втручання адміністратора.
- `kernel/hostname` та `kernel/domainname`: Зберігають ім'я вузла та домену. Їх можна редагувати безпосередньо.
- `kernel/randomize_va_space`: Керує механізмом ASLR (Address Space Layout Randomization). `0` — вимкнено, `1` — часткова рандомізація, `2` — повна рандомізація.

### 3.2. /proc/sys/net/
Найбільший та найскладніший каталог, який налаштовує мережевий стек.
- `net/ipv4/ip_forward`: Якщо містить `1`, система працюватиме як маршрутизатор (роутер) і пересилатиме IP-пакети між мережевими інтерфейсами.
- `net/ipv4/tcp_syncookies`: Вмикає або вимикає механізм захисту від SYN-flood атак.
- `net/ipv4/conf/all/rp_filter`: Вмикає сувору перевірку зворотного шляху (Reverse Path Filtering) для запобігання IP-спуфінгу.
- `net/core/somaxconn`: Максимальна кількість з'єднань, що можуть перебувати в черзі на прослуховування (listen backlog) для сокетів. Навантажені веб-сервери вимагають збільшення цього параметра.

### 3.3. /proc/sys/vm/
Керує підсистемою віртуальної пам'яті (Virtual Memory).
- `vm/swappiness`: Значення від 0 до 100, яке визначає нахил ядра до використання файлу/розділу підкачки (swap). Значення 100 означає агресивний свопінг, 0 — використання свопу лише за крайньої необхідності (Out Of Memory).
- `vm/overcommit_memory`: Визначає політику виділення пам'яті, коли процес просить більше пам'яті, ніж є фізично доступною. `0` — евристичний підхід, `1` — завжди дозволяти (небезпечно, може викликати OOM Killer), `2` — жорстке лімітування (ніколи не виділяти більше встановленого ліміту).
- `vm/drop_caches`: Запис у цей файл дозволяє звільнити дискові кеші. Наприклад, `echo 3 > /proc/sys/vm/drop_caches` очистить pagecache, dentry та inode caches. Це корисний інструмент під час проведення бенчмарків.

Зміна параметрів через `echo` або `cat` безпосередньо в `/proc/sys/` застосовується миттєво, але ці зміни зникнуть після перезавантаження системи. Для збереження налаштувань використовується конфігураційний файл `/etc/sysctl.conf` (або файли в `/etc/sysctl.d/`) та утиліта `sysctl` (`sysctl -p` для застосування).

## 4. Глобальна інформація про систему

Окрім інформації про окремі процеси та конфігурації ядра, `/proc` містить безліч файлів з глобальною статистикою та даними про апаратне забезпечення.

- **/proc/cpuinfo**
  Виводить детальну інформацію про всі логічні процесори в системі: модель, тактова частота (поточна), розмір кешу, кількість ядер та, що найважливіше, список прапорців (flags). Прапорці повідомляють, які додаткові набори інструкцій підтримує процесор (наприклад, `avx`, `sse4_2`, `aes`, `vmx` / `svm` для апаратної віртуалізації).
  
- **/proc/meminfo**
  Глобальна статистика використання пам'яті. Саме цей файл парсять утиліти `free` і `top`. Він показує загальний обсяг пам'яті (`MemTotal`), доступну пам'ять (`MemAvailable`), скільки пам'яті використано під дискові кеші (`Buffers` і `Cached`), обсяг Swap тощо. Розділення пам'яті на `Active` та `Inactive` сторінки допомагає зрозуміти, скільки пам'яті активно використовується, а яку ядро може легко відібрати та перепризначити.

- **/proc/uptime**
  Містить два числа: час роботи системи в секундах (uptime) та кількість секунд, які система провела в стані простою (idle time) сумарно для всіх процесорних ядер. Якщо idle time більше, ніж uptime, це означає, що багатоядерна система більшу частину часу простоювала.

- **/proc/loadavg**
  Містить показники середнього навантаження (load average) за 1, 5 та 15 хвилин, кількість активних сутностей планувальника (запущені процеси / загальна кількість процесів) та PID останнього створеного процесу. Цей файл формує вивід утиліти `uptime`.

- **/proc/mounts**
  Це символічне посилання на `/proc/self/mounts`, яке містить список усіх змонтованих у поточному просторі імен (mount namespace) файлових систем. Файл динамічно оновлюється ядром і завжди є актуальним, на відміну від `/etc/mtab`, який може містити застарілі дані.

- **/proc/net/**
  Цей каталог (який технічно є символічним посиланням на `/proc/self/net`) містить масивну кількість інформації про мережевий стек. 
  - `dev`: Статистика по кожному мережевому інтерфейсу (кількість переданих і отриманих байт, пакетів, помилок). Її використовує утиліта `ifconfig` або `ip -s link`.
  - `tcp`, `udp`: Список усіх активних мережевих сокетів, їхній стан, локальні та віддалені адреси і порти. Утиліти `netstat` та `ss` (частково) базуються на парсингу цих файлів.
  - `route`, `arp`: Таблиці маршрутизації та ARP-кеш.

## 5. Як створити власний файл у /proc: proc_create()

Якщо ви розробляєте модуль ядра (kernel module), вам часто буває потрібно вивести якусь внутрішню інформацію для користувача або отримати від нього параметри. Створення файлу в `/proc` — один з найпростіших способів це зробити (хоча сучасні рекомендації ядра для конфігурації апаратних пристроїв та драйверів радять використовувати `sysfs` — `/sys`).

Для створення файлу в `/proc` використовується функція **`proc_create()`** (або її варіації `proc_create_data`, `proc_mkdir`). 

Щоб створити файл, що підтримує читання через механізм `seq_file` (найзручніший шлях), необхідно реалізувати функцію, яка буде виводити дані, і зв'язати її з файловими операціями.

### Приклад коду (модуль ядра):

```c
#include <linux/module.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>

// Функція, яка генерує вміст файлу
static int my_proc_show(struct seq_file *m, void *v)
{
    seq_printf(m, "Привіт з ядра Linux!\n");
    seq_printf(m, "Цей файл згенеровано модулем: %s\n", KBUILD_MODNAME);
    return 0;
}

// Функція, яка викликається при відкритті файлу (open)
// Вона ініціалізує seq_file і прив'язує до нього нашу функцію show
static int my_proc_open(struct inode *inode, struct file *file)
{
    return single_open(file, my_proc_show, NULL);
}

// Структура, що описує операції над нашим файлом у /proc
// Використовуємо стандартні функції seq_read, seq_lseek, single_release
static const struct proc_ops my_proc_fops = {
    .proc_open    = my_proc_open,
    .proc_read    = seq_read,
    .proc_lseek   = seq_lseek,
    .proc_release = single_release,
};

static struct proc_dir_entry *my_proc_entry;

static int __init my_module_init(void)
{
    // Створюємо файл /proc/my_hello
    // 0444 - права (тільки для читання)
    // NULL - файл створюється в корені /proc
    my_proc_entry = proc_create("my_hello", 0444, NULL, &my_proc_fops);
    if (!my_proc_entry) {
        printk(KERN_ERR "Не вдалося створити /proc/my_hello\n");
        return -ENOMEM;
    }
    
    printk(KERN_INFO "Модуль my_hello завантажено\n");
    return 0;
}

static void __exit my_module_exit(void)
{
    // Видаляємо файл при вивантаженні модуля
    if (my_proc_entry) {
        remove_proc_entry("my_hello", NULL);
    }
    printk(KERN_INFO "Модуль my_hello вивантажено\n");
}

module_init(my_module_init);
module_exit(my_module_exit);
MODULE_LICENSE("GPL");
```

Після компіляції та завантаження цього модуля за допомогою `insmod`, користувач зможе виконати команду `cat /proc/my_hello` і побачити рядок "Привіт з ядра Linux!".

Важливо розуміти, що при використанні `proc_create` ядро не виділяє пам'ять під сам рядок "Привіт...". Текст генерується функцією `my_proc_show()` безпосередньо у буфер, наданий користувацьким викликом `read()`, що робить цей механізм надзвичайно швидким і економічним щодо пам'яті.

## Підсумок

Файлова система `/proc` є геніальним архітектурним рішенням. Перетворивши складні структури даних ядра на звичайні текстові файли та каталоги, розробники Linux дозволили будь-якому користувачеві чи скрипту взаємодіяти з операційною системою за допомогою стандартних, знайомих інструментів: `cat`, `grep`, `awk`, `echo`.

Без `procfs` нам довелося б мати десятки спеціалізованих системних викликів і бінарних утиліт для моніторингу кожного окремого аспекту системи (як це часто буває в інших ОС). Завдяки `/proc`, ми можемо писати прості shell-скрипти, які аналізують мережевий трафік, знаходять процеси з витоком пам'яті або адаптують системні параметри під навантаження. 

Незважаючи на те, що для інформації про апаратні пристрої ядро Linux зараз активно використовує `/sys` (sysfs), `/proc` залишається незамінним інструментом для моніторингу процесів, системних метрик та управління налаштуваннями `sysctl`. Розуміння того, як влаштована `procfs` і яка інформація там прихована, є обов'язковою навичкою для будь-якого системного адміністратора, девопс-інженера чи розробника в екосистемі Linux.
