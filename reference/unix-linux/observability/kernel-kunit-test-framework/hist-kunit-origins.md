# 📜 Історія появи KUnit та еволюція тестування ядра Linux

Історичний шлях розвитку методів перевірки коректності ядра Linux відображає трансформацію підходів до забезпечення надійності складних програмних систем — від ручного розбору системних журналувань до герметичного автотестування у мілісекундному часовому вікні.

## Епоха ручної верифікації та примітивів printk (1991–2012)

У перші два десятиліття існування ядра Linux основними інструментами перевірки коду слугували візуальний аналіз виводу функції `printk()` та обережне випробування нових драйверів або підсистем безпосередньо на фізичному обладнанні. Розробник, створивши новий алгоритм розподілу пам'яті або нову файлову систему, комбінував його у вигляді модуля ядра, завантажував командою `insmod` і вручну виконував сценарії використання у просторі користувача.

Цей підхід мав критичні недоліки, які ускладнювали масштабування розробки:

1. **Ціна помилки (Fatal Cost)**: Помилка виходу за межі масиву або розіменування нульового вказівника (Null Pointer Dereference) у просторі ядра призводила до негайного краху усієї операційної системи (Kernel Panic або OOPS). Розробник втрачав відлагоджувальний стан і мусив перезавантажувати фізичну або віртуальну машину.
2. **Неможливість ізоляції внутрішніх функцій**: Більшість ключових алгоритмів ядра реалізовано у вигляді приватних статичних функцій (`static`), які свідомо не експортуються у глобальну таблицю символів ядра через `EXPORT_SYMBOL()`. Перевірка таких функцій вимагала створення штучних зовнішніх інтерфейсів `sysfs`, `procfs` або `ioctl`, що забруднювало виробничий код тимчасовими милицями.
3. **Високі часові затримки циклу розробки (Edit-Compile-Test cycle)**: Збірка повного образу ядра, перезапуск віртуальної машини QEMU, завантаження ініціалізаційного рамдиска (initramfs) та запуск тестів займали від кількох хвилин до десятків хвилин.

## Поява kselftest: перша спроба системної стандартизації (2012)

Щоб подолати хаос розрізнених тестових скриптів, у ядрі Linux 3.14 (під керівництвом Шуа Хан / Shuah Khan) було зареєстровано фреймворк `kselftest` (Kernel Self-Tests), розміщений у дереві вихідного коду за шляхом `tools/testing/selftests/`.

`kselftest` пропонував концепцію тестування ядра «ззовні всередину» (outside-in). Тести реалізовувалися як звичайні програми простору користувача мовою C або скриптами Shell. Вони взаємодіяли з ядром через стандартні системні виклики (syscalls), інтерфейси `/dev`, `/sys` та `/proc`, перевіряючи поведінку підсистем із точки зору користувацького середовища.

Попри значний крок уперед для функціонального та інтеграційного тестування, `kselftest` не міг виконати роль справжнього фреймворку юніт-тестування:

- **Потреба у повноцінному середовищі**: Для виконання тестів вимагалося повністю завантажене ядро Linux із змонтованою кореневою файловою системою та ініціалізованим середовищем простору користувача.
- **Низька швидкість у CI/CD**: Автоматизовані системи безперервної інтеграції мусили запускати важкі віртуальні машини, що робило перевірку кожного кожної зміни у коді занадто дорогою за ресурсами та часом.
- **Втрата контексту помилки**: Якщо системний виклик повертав помилку `EINVAL`, користувацький тест `kselftest` часто не міг точно визначити, на якому саме внутрішньому кроці ядра стався збій.

## Революція KUnit: Брендан Гіггінс та концепція UML (2018–2020)

У 2018 році розробник компанії Google Брендан Гіггінс (Brendan Higgins) запропонував фундаментально новий для ядра Linux підхід. Натхненний популярними фреймворками юніт-тестування із світу простору користувача (такими як JUnit для Java або GoogleTest для C++), він розпочав розробку KUnit (Kernel Unit Testing Framework).

Головною ідеєю KUnit стала внутрішньоядерна герметичність: тести мусять виконуватися безпосередньо у просторі ядра, мати прямий доступ до внутрішніх структур даних та статичних функцій підсистем, але при цьому запускатися ізольовано від фізичного обладнання.

Для досягнення цієї мети Брендан використав архітектуру User Mode Linux (UML) — спеціальний порт ядра Linux, який компілюється як звичайний виконуваний файл архітектури POSIX/x86_64, що запускається як користувацький процес у будь-якій Linux-системі.

Ключові переваги архітектури KUnit:

- **Швидкість**: Виконання сотень тестів у середовищі UML займає менше секунди, оскільки відсутній етап ініціалізації фізичних пристроїв та драйверів контролерів.
- **Прямий доступ**: Тести компілюються разом із вихідним кодом модуля ядра і мають доступ до всіх його внутрішніх функцій.
- **Безпека**: Збій у тесті не викликає перезавантаження хост-машини.

Злиття KUnit у головну гілку ядра (mainline Linux kernel) відбулося у релізі Linux 5.5 у січні 2020 року.

## Сучасна еволюція та інтеграція із санітайзерами (2020–дотепер)

Після офіційного включення до складу ядра KUnit пройшов шлях від експериментального інструменту до загальносистемного стандарту якості.

Важливими віхами розвитку KUnit стали:

- **Параметризовані тести (KUNIT_CASE_PARAM)**: Додано можливість запускати один і той самий тестовий сценарій із різними наборами вхідних даних (table-driven testing).
- **Динамічна підміна функцій (Static Stubbing)**: Додано інфраструктуру `kunit_activate_static_stub()`, що дозволяє на льоту замінювати виклики апаратних драйверів на тестові заглушки без використання важких C++ фреймворків макетування.
- **Альянс із санітайзерами пам'яті та конфліктів**: Інтеграція KUnit із детекторами KASAN, KCSAN та KFENCE дозволила виявляти не лише логічні помилки в `KUNIT_EXPECT_EQ()`, але й приховані стану гонитви (race conditions) та виходи за межі виділених блоків пам'яті безпосередньо під час виконання юніт-тестів.

Сьогодні KUnit є обов'язковим елементом автоматизованого тестування для ключових підсистем ядра, включаючи графічний стек DRM, файлові системи ext4, Btrfs та XFS, мережеву підсистему socket buffer (sk_buff) та криптографічні модулі.
