# Kernel Concurrency Sanitizer (KCSAN)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Дані, що розділяються між кількома потоками або процесорами в ядрі операційної системи, завжди є джерелом потенційних проблем. Найпоширенішим класом таких проблем є стан перегонів (data race). Стан перегонів виникає, коли два або більше потоків виконання звертаються до однієї і тієї ж ділянки пам'яті одночасно, принаймні одне зі звернень є операцією запису, і ці звернення не синхронізовані належним чином.

В ядрі Linux стани перегонів можуть призводити до непередбачуваної поведінки, пошкодження даних, краху системи (kernel panic) та вразливостей безпеки. Виявлення таких помилок традиційними методами (тестування, статичний аналіз) є надзвичайно складним завданням, оскільки вони залежать від специфічного таймінгу та планування потоків.

Для вирішення цієї проблеми розробники ядра Linux інтегрували **Kernel Concurrency Sanitizer (KCSAN)** — динамічний аналізатор станів перегонів, заснований на семплюванні та точках спостереження (watchpoints).

## Принципи роботи KCSAN

KCSAN базується на інструментуванні коду під час компіляції та використанні програмних watchpoint-ів під час виконання. На відміну від інших інструментів, таких як KASAN (Kernel Address Sanitizer), KCSAN спеціалізується виключно на проблемах паралельного доступу до даних.

### Інструментування компілятором

Для роботи KCSAN необхідна підтримка з боку компілятора (GCC або Clang). При увімкненні KCSAN (через конфігурацію `CONFIG_KCSAN`), компілятор вставляє виклики спеціальних функцій KCSAN перед кожним доступом до пам'яті (читанням або записом).

Ці функції зазвичай виглядають як `__tsan_read*` та `__tsan_write*` (де `*` позначає розмір доступу в байтах: 1, 2, 4, 8, 16). Префікс `__tsan` використовується тому, що KCSAN частково використовує ABI (Application Binary Interface), сумісний із ThreadSanitizer (TSAN) простору користувача.

```c
// Початковий код ядра
void update_counter(int *ptr) {
    *ptr = *ptr + 1;
}
```

Після інструментування компілятором цей код концептуально виглядає так:

```c
// Після інструментування KCSAN
void update_counter(int *ptr) {
    int temp;
    
    // Інструментування читання
    __tsan_read4(ptr);
    temp = *ptr;
    
    temp = temp + 1;
    
    // Інструментування запису
    __tsan_write4(ptr);
    *ptr = temp;
}
```

### Механізм Watchpoint-ів (точок спостереження)

На відміну від ThreadSanitizer, який відстежує всі доступи до пам'яті та будує граф відносин "happens-before", KCSAN використовує ймовірнісний підхід на основі точок спостереження (watchpoints). Цей підхід є набагато легшим для ядра, вимагає менше пам'яті та має менші накладні витрати на продуктивність.

Алгоритм роботи KCSAN наступний:

1. **Встановлення Watchpoint-а**: Під час доступу до пам'яті (у функції `__tsan_read` або `__tsan_write`), KCSAN з певною ймовірністю вирішує встановити watchpoint на цю адресу пам'яті.
2. **Затримка (Delay)**: Після встановлення watchpoint-а, потік тимчасово призупиняється (на кілька мікросекунд). Ця затримка штучно розширює "вікно вразливості", збільшуючи шанси того, що інший потік звернеться до цієї ж адреси в цей самий час.
3. **Виявлення конфлікту**: Якщо протягом цієї затримки інший потік на іншому процесорі звертається до тієї ж адреси пам'яті (і хоча б один з доступів є записом), його інструментований виклик (`__tsan_read`/`__tsan_write`) перевірить список активних watchpoint-ів.
4. **Реєстрація стану перегонів**: Знайшовши збіг, другий потік розуміє, що стався стан перегонів. KCSAN генерує звіт, що містить стек викликів обох потоків: того, який встановив watchpoint, і того, який його "спрацював" (hit).
5. **Зняття Watchpoint-а та продовження**: Після закінчення затримки, перший потік знімає watchpoint і продовжує нормальне виконання.

## Типи станів перегонів у KCSAN

KCSAN розпізнає та повідомляє про різні типи станів перегонів. Важливо розуміти, що не всі "перегони", виявлені KCSAN, є обов'язково помилками. Ядро Linux іноді навмисно використовує несинхронізований доступ для оптимізації (так звані "benign data races").

### Справжні стани перегонів (True Data Races)

Це ситуації, коли одночасний доступ може призвести до некоректної поведінки. Приклади:
- **Tearing (розрив)**: Зчитування половини старого значення і половини нового (часто буває з 64-бітними змінними на 32-бітних архітектурах).
- **Втрата оновлень**: Два потоки читають значення, інкрементують його і записують назад. Одне з оновлень може бути перезаписане.
- **Оптимізації компілятора**: Компілятор може перевпорядкувати інструкції або кешувати значення в регістрах, припускаючи, що доступу з інших потоків немає.

### Data Races vs. Data Race Candidates

KCSAN розділяє виявлені перегони на справжні помилки та "можливі" або такі, що вимагають уваги. Розробники можуть розмічати свій код, щоб вказати KCSAN, що певний несинхронізований доступ є навмисним.

## Використання KCSAN та розмітка коду

Для того, щоб уникнути хибних спрацьовувань на навмисних станах перегонів, розробники ядра використовують спеціальні макроси, які вказують компілятору (і KCSAN), як обробляти певні доступи.

### READ_ONCE() та WRITE_ONCE()

Якщо змінна може бути прочитана іншим потоком під час її зміни (або навпаки), доступ до неї повинен здійснюватися через макроси `READ_ONCE()` та `WRITE_ONCE()`.

```c
// Замість:
// count = new_count;

// Потрібно використовувати:
WRITE_ONCE(count, new_count);

// Замість:
// int current_count = count;

// Потрібно використовувати:
int current_count = READ_ONCE(count);
```

Ці макроси роблять дві речі:
1. Забороняють компілятору оптимізувати доступ (наприклад, не можна кешувати значення в регістрі).
2. Повідомляють KCSAN, що цей доступ є "безпечним" з точки зору перегонів, тому KCSAN не буде повідомляти про стан перегонів, якщо обидва доступи (читання і запис) марковані відповідним чином.

### data_race()

Якщо стан перегонів вважається абсолютно безпечним (наприклад, збір статистики, де втрата одного інкременту не має значення), код можна обгорнути в макрос `data_race()`. Це явно вказує KCSAN ігнорувати стан перегонів для цього виразу.

```c
// Дозволяємо стан перегонів для збору статистики
data_race(stats->packets_dropped++);
```

## Конфігурація KCSAN (CONFIG_KCSAN)

KCSAN налаштовується через систему Kconfig під час компіляції ядра. Основні параметри:

- `CONFIG_KCSAN=y`: Увімкнути KCSAN.
- `CONFIG_KCSAN_REPORT_ONCE_IN_MS`: Інтервал між звітами (запобігає флуду в dmesg).
- `CONFIG_KCSAN_UDELAY_TASK`: Затримка у мікросекундах для потоків контексту задачі (task context) після встановлення watchpoint.
- `CONFIG_KCSAN_UDELAY_INTERRUPT`: Затримка у мікросекундах для контексту переривань. Чим більша затримка, тим вища ймовірність виявлення стану перегонів, але тим сильніше падає продуктивність системи.

### Переваги KCSAN

1. **Точність**: Оскільки KCSAN базується на спостереженні за реальними доступами в пам'ять під час виконання, він рідко дає хибні спрацьовування (якщо не враховувати benign races, які ще не розмічені).
2. **Контекст**: KCSAN надає повні стеки викликів для обох потоків, що беруть участь у стані перегонів.
3. **Низьке споживання пам'яті**: На відміну від KASAN, KCSAN не потребує значної тіньової пам'яті (shadow memory) для стеження за станом кожного байта.

## Висновок

Kernel Concurrency Sanitizer (KCSAN) став потужним інструментом в арсеналі розробників ядра Linux для боротьби зі складними помилками конкурентного доступу. Завдяки ймовірнісному підходу з використанням точок спостереження та інтеграції з компілятором, KCSAN забезпечує прийнятний баланс між продуктивністю системи під час тестування та здатністю виявляти приховані стани перегонів, роблячи ядро Linux надійнішим та безпечнішим.
