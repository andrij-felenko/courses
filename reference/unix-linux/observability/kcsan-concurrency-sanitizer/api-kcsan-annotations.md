# 📋 Довідник анотацій, конфігурацій та інтерфейсів KCSAN

Kernel Concurrency Sanitizer (KCSAN) надає розробникам ядра широкий спектр інструментів для налаштування частоти вибірки, фільтрації очікуваних паралельних доступів, затвердження виключних прав на змінні та аналізу звітів про стани перегонів. У цьому довіднику зібрано всі конфігураційні прапорці Kconfig, публічні макроси анотування коду ядра, системні параметри `sysfs` та специфікація форматів повідомлень `dmesg`.

---

## 1. Параметри конфігурації ядра (Kconfig)

Налаштування KCSAN здійснюється під час компіляції ядра в меню конфігурації `Kernel hacking -> Memory Debugging -> KCSAN: dynamic data-race detector`. Кожен параметр відповідає за окремий аспект інструментування коду або поведінки підсистеми моніторингу під час виконання.

Головний прапорець `CONFIG_KCSAN` слугує основними воротами підсистеми. При його увімкненні збірник Kbuild додає до прапорців компіляції GCC або Clang опцію `-fsanitize=kernel-concurrency`. Це активує компіляторний плагін, який автоматично вставляє виклики `__tsan_read*` та `__tsan_write*` перед кожною інструкцією доступу до пам'яті. Якщо прапорець вимкнено, всі розширення KCSAN повністю виключаються з ядра, а виклики анотацій згортаються у звичайні доступи без жодних накладних витрат.

Параметр `CONFIG_KCSAN_STRICT` перемикає аналізатор у режим суворого виявлення. За замовчуванням KCSAN застосовує евристику фільтрації за зміною значення (value-change filtering): якщо один потік записує у змінну те саме значення, яке там уже перебувало, KCSAN не вважає це критичною помилкою. Однак у суворому режимі ця фільтрація вимикається, і будь-який паралельний запис без маркування породжує звіт у системному журналі. Це корисно під час глибокого аудиту нових підсистем ядра.

Прапорець `CONFIG_KCSAN_WEAK_MEMORY` активує перевірку слабкого впорядкування пам'яті. Сучасні процесорні архітектури (такі як ARM64, POWER або RISC-V) мають слабку модель пам'яті, де процесор може довільно змінювати порядок виконання інструкцій читання та запису, якщо між ними немає явного бар'єра пам'яті (`smp_rmb`, `smp_wmb`, `smp_store_release`). Дана конфігурація дозволяє KCSAN штучно симулювати ефекти перевпорядкування, виявляючи відсутність необхідних бар'єрів навіть під час тестування на архітектурі x86-64.

Часові затримки налаштовуються за допомогою `CONFIG_KCSAN_UDELAY_TASK` та `CONFIG_KCSAN_UDELAY_INTERRUPT`. Перший параметр визначає тривалість штучної затримки у мікросекундах для звичайних потоків виконання (контекст задач). За замовчуванням це значення становить 80 мікросекунд, що є оптимальним компромісом між імовірністю спіймати перегони та загальним сповільненням ядра. Другий параметр регулює затримку у контексті переривань (hardirq та softirq) і за замовчуванням дорівнює 10 мікросекундам. Менше значення необхідне для того, щоб запобігти тайм-аутам апаратних пристроїв та завісанню обробників переривань.

Інтервал вибірки задається через `CONFIG_KCSAN_SKIP_WATCH`. Це число визначає пересічну кількість доступів, які KCSAN пропускає між встановленнями нових точок спостереження (watchpoints). Значення за замовчуванням (47) забезпечує чудове покриття без створення високого навантаження на систему. Для обмеження флуду в системному журналі застосовується `CONFIG_KCSAN_REPORT_ONCE_IN_MS` (за замовчуванням 3000 мс), що гарантує пригнічення дубльованих звітів про одну й ту саму лінію коду.

Параметр `CONFIG_KCSAN_VERBOSE` включає розширене логування. При його активації звіт KCSAN містить додаткові відомості про регістри процесора, стан прапорців та контекст виконання. Прапорець `CONFIG_KCSAN_TEST` включає модуль автоматичних самотестів `lib/kcsan/kcsan-test.c`, який інтегрується з фреймворком KUnit для перевірки коректності роботи макросів анотування.

## 2. Детальний розбір макросів анотування коду ядра

Для запобігання хибним спрацьовуванням та виявлення прихованих логічних помилок KCSAN спирається на набір макросів, що вставляються безпосередньо в сирцевий C-код ядра.

### 2.1. Макроси маркування явного паралельного доступу

Макрос `READ_ONCE(x)` призначений для атомарного зчитування скалярної змінної з пам'яті. На рівні C-компілятора він перетворює доступ у читання через `volatile`-вказівник, що забороняє компіляторні оптимізації дублювання, злиття або розриву доступів. З точки зору KCSAN, використання `READ_ONCE()` сигналізує, що розробник знає про можливість паралельного оновлення цієї змінної і свідомо здійснює читання без блокувань.

Макрос `WRITE_ONCE(x, val)` реалізує атомарний запис значення у змінну. Він гарантує, що компілятор не виконуватиме створюваних записів (invented stores) та не розриватиме операцію збереження. Якщо один потік використовує `WRITE_ONCE()`, а інший — `READ_ONCE()`, KCSAN вважає такий доступ узгодженим і не видає сповіщень про стани перегонів.

Макроси `READ_ONCE_NOCHECK(x)` та `WRITE_ONCE_NOCHECK(x, val)` діють аналогічно до основних макросів, але повністю вимикають будь-яке інструментування KCSAN для конкретної інструкції. Вони застосовуються у найнижчих шарах самого санітайзера та планера задач.

Макрос `data_race(expr)` дозволяє загорнути цілий вираз C, для якого допускаються будь-які стани перегонів. Це корисно при зборі статистичних даних (наприклад, лічильників оброблених байтів чи скинутих пакетів), де втрата одного інкременту під час паралельного доступу не впливає на стабільність системи. Всередині виразу `data_race()` KCSAN повністю ігнорує будь-які конфлікти.

```c
// Приклад використання data_race() для некритичної статистики
void net_drop_packet(struct net_device *dev) {
    /* Навіть якщо кілька ядер одночасно інкрементують цей лічильник без замка,
     * KCSAN не видаватиме попередження в dmesg. */
    data_race(dev->stats.rx_dropped++);
}
```

### 2.2. Твердження виключного доступу (Exclusive Access Assertions)

Твердження виключності дозволяють розробнику явно сформулювати контракт синхронізації для критичних ділянок коду.

Макрос `ASSERT_EXCLUSIVE_WRITER(var)` стверджує, що в поточний момент часу поточний контекст є єдиним дозволеним письменником у змінну `var`. Якщо KCSAN виявить, що інший потік паралельно виконує запис або читання цієї змінної (навіть марковане через `READ_ONCE`), це вважається порушенням контракту блокування і KCSAN згенерує звіт про помилку.

Макрос `ASSERT_EXCLUSIVE_ACCESS(var)` встановлює ще суворішу вимогу: він стверджує повну виключність доступу до змінної `var`. Будь-яке паралельне звернення з боку інших ядер процесора (як на читання, так і на запис) викликає негайне спрацьовування санітайзера.

Макрос `ASSERT_EXCLUSIVE_BITS(var, mask)` захищає окремі біти у прапорцевому масиві `var`, задані маскою `mask`. Це дозволяє перевірити, що поки один потік змінює конкретний прапорець пристрою, жоден інший потік не намагається паралельно модифікувати ті самі біти.

```c
// Приклад захисту стану об'єкта під час утримання spinlock
void update_device_flags(struct my_device *dev, unsigned long new_flags) {
    spin_lock(&dev->lock);
    
    /* Перевіряємо, що поки ми під замком, ніхто не намагається писати в dev->flags */
    ASSERT_EXCLUSIVE_WRITER(dev->flags);
    dev->flags = new_flags;
    
    spin_unlock(&dev->lock);
}
```

### 2.3. Функції явного перевірки доступів та пригнічення

Розробники підсистем ядра можуть вручну керувати моніторингом KCSAN за допомогою безпосередніх викликів C-функцій API:

```c
#include <linux/kcsan-checks.h>

/* Явна перевірка діапазону пам'яті на читання або запис */
void kcsan_check_read(const volatile void *ptr, size_t size);
void kcsan_check_write(const volatile void *ptr, size_t size);

/* Тимчасово вимикає перевірки KCSAN для поточного потоку/контексту */
void kcsan_disable_current(void);

/* Відновлює перевірки KCSAN для поточного потоку/контексту */
void kcsan_enable_current(void);

/* Початок та кінець атомарної зони для вкладених операцій */
void kcsan_nestable_atomic_begin(void);
void kcsan_nestable_atomic_end(void);
```

Функції `kcsan_disable_current()` та `kcsan_enable_current()` є критично важливими при розробці низькорівневих обробників переривань NMI або зон перемикання контексту MMU. Якщо потік входить у зону, де виконання інструментованих викликів `__tsan_read*` може спричинити рекурсивне завісання або порушення стек-фрейму, викликають `kcsan_disable_current()`. Лічильник вимкнення зберігається у контексті поточного CPU (`kcsan_ctx.disable_count`), що підтримує безпечну вкладеність викликів.

## 3. Системний інтерфейс sysfs та параметри ядра

KCSAN експортує свої динамічні налаштування через стандартну файлову систему `sysfs` за шляхом `/sys/module/kcsan/parameters/`. Робота з цими файлами вимагає прав суперкористувача (root).

За допомогою системних параметрів інженери можуть змінювати поведінку аналізатора безпосередньо під час тестування системи:

1. `enabled`: Приймає значення `1` або `0`. Дозволяє оперативно увімкнути або повністю призупинити роботу KCSAN без перезавантаження ядра (наприклад, для проведення бенчмарків продуктивності).
2. `udelay_task`: Налаштовує тривалість штучної затримки у мікросекундах для контексту задач. Збільшення цього значення розширює вікно виявлення перегонів, але підвищує сповільнення системи.
3. `udelay_interrupt`: Регулює тривалість затримки у контексті переривань.
4. `skip_watchpoints`: Задає частоту вибірки семплювання. Зменшення значення збільшує кількість перевірок.
5. `report_once_in_ms`: Встановлює ліміт часу для пригнічення повторних повідомлень про один і той самий випадок перегонів.
6. `verbose`: Увімкнення розширеного логування з виводом стану регістрів процесора.
7. `interrupt_watcher`: Дозволяє або забороняє встановлення точок спостереження безпосередньо всередині обробників переривань.

```bash
# Збільшення тривалості затримки для розширення вікна виявлення перегонів
echo 150 | sudo tee /sys/module/kcsan/parameters/udelay_task

# Тимчасове зупинення моніторингу KCSAN
echo 0 | sudo tee /sys/module/kcsan/parameters/enabled

# Перевірка поточних налаштувань
cat /sys/module/kcsan/parameters/skip_watchpoints
```

## 4. Специфікація та аналіз звіту KCSAN (dmesg)

Коли KCSAN фіксує стан перегонів, він друкує структурований звіт у системний журнал `dmesg`. Звіт складається з декількох чітко розмежованих секцій.

```text
==================================================================
BUG: KCSAN: data-race in update_counter / read_counter

write to 0xffffffff82a04840 of 4 bytes by task 1421 on cpu 0:
 update_counter+0x28/0x60 [kcsan_demo_mod]
 worker_thread+0x1d4/0x3d0
 kthread+0x10b/0x130
 ret_from_fork+0x1f/0x30

read to 0xffffffff82a04840 of 4 bytes by task 1422 on cpu 1:
 read_counter+0x14/0x40 [kcsan_demo_mod]
 worker_thread+0x1d4/0x3d0
 kthread+0x10b/0x130
 ret_from_fork+0x1f/0x30

value changed: 0x00000005 -> 0x00000006

Reported by Kernel Concurrency Sanitizer on:
CPU: 1 PID: 1422 Comm: kworker/1:2 Tainted: G        W         5.15.0-kcsan #1
Hardware name: QEMU Standard PC (Q35 + ICH9, 2009), BIOS 1.15.0-1 04/01/2014
==================================================================
```

### Покрокова розшифровка всіх полів звіту:

1. **Заголовок `BUG: KCSAN: data-race in ...`**: Вказує тип виявленої проблеми (`data-race`, `race in ASSERT_EXCLUSIVE_WRITER` або `race in ASSERT_EXCLUSIVE_ACCESS`) та назви C-функцій, у яких зафіксовано конфліктний доступ.
2. **Секція першого потоку (Access 1)**:
   - `write to 0xffffffff82a04840 of 4 bytes by task 1421 on cpu 0`: Вказує операцію (запис), віртуальну адресу пам'яті ядра (`0xffffffff82a04840`), розмір доступних даних (4 байти), PID задачі (1421) та номер ядра CPU (0).
   - `update_counter+0x28/0x60 [kcsan_demo_mod]`: Символьний стек викликів (Call Trace) з вказанням зсуву інструкції та імені модуля ядра.
3. **Секція другого потоку (Access 2)**:
   - `read to 0xffffffff82a04840 of 4 bytes by task 1422 on cpu 1`: Наводить деталі конфліктного доступу з боку другого процесорного ядра (читання 4 байтів на CPU 1) та його повний стек викликів.
4. **Секція порівняння значень `value changed: 0x00000005 -> 0x00000006`**:
   - Показує значення комірки пам'яті до та після виконання штучної затримки `udelay()`. Зміна значення підтверджує реальний перезапис даних під час несинхронізованого доступу.
5. **Системний контекст та прапорці заплямованості (Taint Flags)**:
   - `CPU: 1 PID: 1422 Comm: kworker/1:2`: Показує, яке саме ядро згенерувало фінальне повідомлення.
   - `Tainted: G W`: Прапорці стану ядра (`G` — GPL модуль, `W` — у ядрі вже було згенеровано попередження/Warning).
