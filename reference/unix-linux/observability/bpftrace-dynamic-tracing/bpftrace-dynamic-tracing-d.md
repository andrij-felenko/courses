# Високорівневе трасування через bpftrace

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Трасування та спостережність (observability) у сучасних Linux-системах досягли нового рівня завдяки технології eBPF. Серед численних інструментів, що використовують eBPF, **bpftrace** виділяється як потужна, але водночас проста у використанні високорівнева мова трасування, яка дозволяє адміністраторам, розробникам та інженерам з продуктивності глибоко аналізувати роботу ядра та користувацьких програм без необхідності писати складний код на C чи завантажувати модулі ядра.

У цій статті ми детально розглянемо утиліту та мову bpftrace, типи доступних проб (kprobe, tracepoint, uprobe, usdt), використання мап агрегацій (count, hist, lhist) та порівняємо bpftrace з легендарним DTrace, з якого він черпав натхнення.

## 1. Що таке bpftrace?

**bpftrace** — це високорівнева мова трасування для Linux eBPF, яка була створена Бренданом Греггом (Brendan Gregg), Аластєром Робертсоном (Alastair Robertson) та іншими розробниками спільноти. Вона компілює скрипти, написані простою мовою (подібною до AWK, C та DTrace), у байткод eBPF за допомогою LLVM та завантажує їх у ядро Linux через `bpf()` системний виклик. 

Цей інструмент призначений для написання коротких, швидких скриптів (так званих one-liners) та більш складних інструментів спостереження. Він є частиною ширшої екосистеми BCC (BPF Compiler Collection), але якщо BCC призначений для розробки складних інструментів за допомогою Python та C, то bpftrace ідеальний для швидкого, інтерактивного аналізу.

### 1.1. Архітектура та принцип роботи

bpftrace використовує архітектуру, що поєднує кілька компонентів:
1. **Парсер (Parser) та Семантичний аналізатор**: розбирають код скрипта.
2. **LLVM/Clang**: генерують eBPF байткод з абстрактного синтаксичного дерева.
3. **libbpf та BPF syscall**: завантажують байткод у ядро, де він перевіряється In-kernel Verifier (верифікатором ядра), щоб гарантувати безпеку виконання (відсутність нескінченних циклів, доступу до недійсної пам'яті тощо).
4. **BPF Maps**: використовуються для передачі даних (агрегацій, статистик) між ядром (де виконується скрипт) та користувацьким простором (де bpftrace виводить результати).

## 2. Синтаксис мови bpftrace

Мова bpftrace базується на парадигмі подій (event-driven). Основна структура скрипта виглядає так:

```awk
probe_type:probe_name /filter/ {
    action;
}
```

- **probe_type**: тип події, яку ми перехоплюємо (наприклад, `kprobe`, `tracepoint`, `uprobe`).
- **probe_name**: назва події або функції.
- **filter**: (опціонально) логічний вираз; дія виконується лише якщо він істинний.
- **action**: блок коду з інструкціями для виконання.

### 2.1. Змінні

У bpftrace існують три типи змінних:
1. **Вбудовані (Built-ins)**: системні змінні, такі як `pid`, `tid`, `comm` (ім'я процесу), `cpu`, `nsecs` (наносекунди).
2. **Локальні (Scratch variables)**: починаються з `$`, живуть лише в межах поточного блоку `action`. Наприклад, `$start_time = nsecs;`.
3. **Глобальні / Асоціативні масиви (Maps)**: починаються з `@`. Вони зберігаються в BPF maps і доступні між різними подіями. Наприклад, `@counts[comm] = count();`.

## 3. Типи проб (Probes)

Потужність bpftrace полягає в можливості прикріплюватися до різних точок виконання системи. Розглянемо основні типи проб.

### 3.1. kprobe та kretprobe: Трасування ядра

**kprobes** дозволяють динамічно встановлювати точки перехоплення на вході в будь-яку функцію ядра. Відповідно, **kretprobes** спрацьовують під час виходу з функції.

- **Синтаксис**: `kprobe:function_name`
- **Приклад**: відстеження використання системного виклику `clone` (створення процесів).

```bash
bpftrace -e 'kprobe:sys_clone { printf("Process %s (PID %d) is calling clone()\n", comm, pid); }'
```

kprobes є динамічними. Вони не вимагають попередньої підготовки ядра, але вони не гарантують стабільності між різними версіями ядра, оскільки внутрішні функції ядра можуть змінювати свої імена чи аргументи.

Для отримання аргументів функції в kprobe використовуються вбудовані змінні `arg0`, `arg1`, ..., `arg5` (які відповідають регістрам процесора). Для доступу до значень, що повертаються з `kretprobe`, використовується змінна `retval`.

```bash
bpftrace -e 'kretprobe:vfs_read { @bytes_read[comm] = sum(retval); }'
```

### 3.2. Tracepoints: Стабільні події ядра

На відміну від kprobes, **tracepoints** — це статично визначені точки трасування в ядрі Linux. Вони спеціально створені розробниками ядра для забезпечення стабільного API (Application Programming Interface) для інструментів спостереження. Вони не змінюються між версіями ядра.

- **Синтаксис**: `tracepoint:category:event_name` (або `t:category:event_name`)
- **Приклад**: трасування відкриття файлів.

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s is opening a file\n", comm); }'
```

Аргументи tracepoint доступні через структуру `args`, яка автоматично генерується bpftrace на основі інформації з `/sys/kernel/debug/tracing/events/`.

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s opened %s\n", comm, str(args->filename)); }'
```

### 3.3. uprobe та uretprobe: Трасування користувацьких програм

Трасування не обмежується ядром. За допомогою **uprobes** можна динамічно впроваджувати точки перехоплення у функції простору користувача (бібліотеки або виконувані файли).

- **Синтаксис**: `uprobe:binary_path:function_name`
- **Приклад**: відстеження викликів функції `malloc` у стандартній бібліотеці C (libc).

```bash
bpftrace -e 'uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc { printf("malloc called by %s\n", comm); }'
```

Як і з `kprobes`, тут доступні `arg0`-`arg5` та `retval` (для `uretprobe`). Це неймовірно корисний інструмент для дебагінгу скомпільованих програм (C/C++, Go, Rust) на льоту, без їх перезапуску чи перекомпіляції.

### 3.4. USDT: User-Level Statically Defined Tracing

Якщо розробник програми хоче надати стабільний інтерфейс для трасування своєї програми, він додає статичні маркери в код — **USDT** (User Statically Defined Tracing). Це аналог tracepoints, але для простору користувача. Багато СУБД (PostgreSQL, MySQL), рантаймів (Node.js, Ruby, Python) та веб-серверів підтримують USDT.

- **Синтаксис**: `usdt:binary_path:probe_name`
- **Приклад**: трасування подій збирання сміття (GC) в Node.js.

```bash
bpftrace -e 'usdt:/usr/bin/node:gc__start { printf("GC started in Node.js\n"); }'
```

## 4. Мапи агрегацій та гістограми

Однією з найсильніших сторін bpftrace є здатність агрегувати дані безпосередньо в ядрі. Це радикально знижує накладні витрати на копіювання даних у простір користувача. У bpftrace є кілька потужних функцій агрегації, результати яких зберігаються в глобальних мапах (глобальних змінних, що починаються з `@`).

### 4.1. count() — підрахунок подій

Найпростіша агрегація. Підраховує кількість разів, коли спрацювала проба.

```bash
# Скільки системних викликів виконує кожен процес?
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
```
На виході після переривання (Ctrl-C) bpftrace автоматично виведе вміст мапи `@[comm]`.

### 4.2. hist() — гістограми (логарифмічні, степінь 2)

Дуже часто потрібно оцінити розподіл значень, наприклад, затримку (latency) вводу-виводу. Функція `hist()` будує гістограму зі ступенем основи 2 (power-of-2).

```bash
# Розподіл розмірів зчитаних даних для системного виклику read()
bpftrace -e 'kretprobe:vfs_read { @bytes = hist(retval); }'
```
Вивід виглядатиме як класична текстова гістограма:
```
@bytes:
[0]                   12 |                                                    |
[1]                    0 |                                                    |
[2, 4)                 4 |                                                    |
[4, 8)                42 |@                                                   |
[8, 16)             1024 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@                     |
[16, 32)            1500 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[32, 64)             200 |@@@@@                                               |
```

### 4.3. lhist() — лінійні гістограми

Якщо вам потрібен лінійний розподіл (де інтервали між "кошиками" однакові), використовується `lhist(value, min, max, step)`.

```bash
# Лінійна гістограма розмірів (від 0 до 100 з кроком 10)
bpftrace -e 'kretprobe:vfs_read /retval > 0/ { @bytes = lhist(retval, 0, 100, 10); }'
```

### Інші агрегації
- `sum(value)` — сума всіх значень.
- `avg(value)` — середнє значення.
- `min(value)` / `max(value)` — мінімум / максимум.

Усі ці агрегації виконуються *всередині ядра* в ефективних хеш-таблицях (eBPF map), що робить їх використання безпечним навіть на високонавантажених серверах (overhead зазвичай складає частки відсотка).

## 5. Порівняння bpftrace та DTrace

Історія динамічного трасування нерозривно пов'язана з **DTrace**. Розроблений компанією Sun Microsystems для операційної системи Solaris у 2005 році, DTrace став еталоном того, як повинна виглядати безпечна та потужна система спостереження. Він представив мову D та концепцію "Zero Overhead" для неактивних проб.

Коли eBPF почав бурхливо розвиватися в Linux, виникла потреба в аналогу DTrace. Хоча були спроби портувати сам DTrace на Linux, спільнота вибрала шлях розбудови нативних інструментів на базі eBPF. Так виник bpftrace, який Брендан Грегг назвав "духовним спадкоємцем DTrace".

### 5.1. Подібності
1. **Синтаксис**: мова bpftrace (яку іноді неофіційно називають "D-подібною") дуже нагадує DTrace. Блоки `probe /filter/ { action }`, використання мап, вбудованих функцій (наприклад, `count()`, `quantize()` в DTrace і `hist()` в bpftrace) — концептуально ідентичні.
2. **Безпека**: обидві системи гарантують безпеку. DTrace має свій верифікатор і віртуальну машину (DIF), bpftrace покладається на In-kernel BPF Verifier. Обидва інструменти не дозволять завантажити код, який спричинить kernel panic.
3. **Мета**: і DTrace, і bpftrace створені для вирішення складних проблем продуктивності у виробничому середовищі без переривання сервісів.

### 5.2. Відмінності
1. **Екосистема**: DTrace монолітний. Компілятор, віртуальна машина і користувацька утиліта тісно інтегровані в ядро Solaris (або FreeBSD). bpftrace є компонованим: він використовує LLVM для генерації коду та абстракції BPF ядра Linux, будучи модулем поверх загального ядра eBPF, яке також використовується для маршрутизації мережі (XDP), безпеки (Cilium) тощо.
2. **Доступність**: DTrace є стандартом для illumos, Solaris, FreeBSD і macOS. bpftrace розроблений виключно для Linux-систем.
3. **Типи даних і стабільність**: DTrace був глибоко інтегрований із форматом відладки CTF (Compact C Type Format), що робило навігацію по структурах ядра дуже зручною. bpftrace використовує BTF (BPF Type Format), що є аналогом у світі Linux, і завдяки технології CO-RE (Compile Once – Run Everywhere) сучасний bpftrace стає настільки ж зручним, дозволяючи звертатися до полів структур (наприклад, `task->pid`) без наявності повних заголовних файлів ядра на цільовій системі.

## Висновок

`bpftrace` здійснив справжню революцію у способі діагностики продуктивності Linux. Якщо раніше аналіз затримок вводу-виводу або пошук причин "гальмування" програми вимагав складних маніпуляцій з SystemTap або написання модулів ядра, то сьогодні це можна зробити одним рядком коду, використовуючи `kprobe` або `tracepoint`. Завдяки підтримці мап агрегацій, bpftrace дозволяє збирати статистику (лінійні та логарифмічні гістограми) прямо в ядрі, гарантуючи мінімальне навантаження на систему. 

Як надійний спадкоємець ідей DTrace, адаптований під сучасні реалії архітектури eBPF, bpftrace є незамінним інструментом в арсеналі будь-якого системного адміністратора чи інженера надійності (SRE).
