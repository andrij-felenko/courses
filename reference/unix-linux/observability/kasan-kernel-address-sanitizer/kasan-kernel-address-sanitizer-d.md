# Kernel Address Sanitizer (KASAN)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Kernel Address Sanitizer (KASAN) — це потужний інструмент динамічного аналізу пам'яті, вбудований у ядро Linux, який дозволяє виявляти різноманітні помилки роботи з пам'яттю під час виконання (runtime). Основною метою KASAN є швидке та точне знаходження таких вразливостей, як Use-After-Free (використання після звільнення) та Out-of-Bounds (вихід за межі виділеного буфера) з мінімальними накладними витратами (overhead). 

Ця стаття детально розглядає архітектуру KASAN, концепцію Shadow Memory, відмінності між режимами Generic, Software Tag-Based та Hardware Tag-Based (ARM MTE), а також практичні аспекти використання та розшифровки звітів KASAN.

## 1. Концепція Shadow Memory

Основою роботи Generic KASAN є концепція «тіньової пам'яті» (Shadow Memory). Для кожного байта основної пам'яті ядра підтримується відповідний стан (наприклад, доступний він для читання/запису чи ні). Оскільки зберігати стан кожного окремого байта неефективно, KASAN використовує оптимізацію: 1 байт тіньової пам'яті відображає стан 8 байтів (одного 64-бітного слова) основної пам'яті.

### 1.1 Відображення адрес

Відображення адреси `A` основної пам'яті в адресу `S` тіньової пам'яті відбувається за простою формулою:
```c
S = (A >> 3) + KASAN_SHADOW_OFFSET
```
де `KASAN_SHADOW_OFFSET` — це базова адреса регіону тіньової пам'яті, яка розраховується під час завантаження ядра таким чином, щоб весь простір віртуальної пам'яті ядра міг бути відображений у тіньову пам'ять.

### 1.2 Кодування стану

1 байт тіньової пам'яті описує 8 байт основної. Значення цього байта має такий зміст:
- `0`: Усі 8 байтів доступні для звернення.
- `1..7`: Тільки перші N байтів доступні. Це трапляється, коли виділяється структура даних, розмір якої не кратний 8.
- Від'ємні значення (старший біт встановлено, наприклад `0xFF`, `0xFE`): Усі 8 байтів недоступні (poisoned). Різні значення (redzones) вказують на причину недоступності:
  - `0xFA`: Slab-allocator left redzone.
  - `0xFB`: Slab-allocator right redzone.
  - `0xFC`: Slab-allocator freed pointer (використовується для виявлення Use-After-Free).

## 2. Типи KASAN

У ядрі Linux реалізовано три різні режими роботи KASAN: Generic, Software Tag-Based (SW_TAGS) та Hardware Tag-Based (HW_TAGS).

### 2.1 Generic KASAN
Це початковий і найбільш універсальний режим. Він спирається на інструментування коду компілятором (GCC або Clang). Під час компіляції ядра компілятор вставляє перевірки перед кожним зверненням до пам'яті. Generic KASAN виявляє як Out-of-Bounds, так і Use-After-Free, але має значні накладні витрати на продуктивність (приблизно в 2-3 рази повільніше) і вимагає багато додаткової пам'яті (1/8 від усієї пам'яті ядра йде на Shadow Memory).

### 2.2 Software Tag-Based KASAN
Цей режим розроблений переважно для архітектури ARM64, яка підтримує Top-Byte Ignore (TBI). Суть полягає в тому, що старший байт (8 біт) 64-бітного вказівника ігнорується процесором при зверненні до пам'яті, що дозволяє зберігати в ньому «тег». KASAN призначає унікальний тег кожному виділеному блоку пам'яті (slab object) і зберігає цей тег як у вказівнику, так і в тіньовій пам'яті (де кожен тег займає пам'ять, що відображає блок). Під час доступу перевіряється, чи збігається тег у вказівнику з тегом у тіньовій пам'яті. Це значно знижує використання пам'яті.

### 2.3 Hardware Tag-Based KASAN
Заснований на апаратному розширенні ARM Memory Tagging Extension (MTE). Апаратне забезпечення бере на себе задачу перевірки тегів при кожному доступі до пам'яті. Немає необхідності в інструментуванні коду компілятором або використанні класичної програмної тіньової пам'яті, оскільки MTE підтримує свої власні теги пам'яті. Це дає змогу використовувати KASAN у production-середовищах завдяки дуже низьким накладним витратам (менше 5% падіння продуктивності).

## 3. Виявлення помилок

### 3.1 Out-of-Bounds (OOB)
При виділенні буфера алокатор (наприклад, SLUB) додає «червоні зони» (redzones) перед і після буфера. Ці зони позначаються в тіньовій пам'яті як недоступні. Якщо код виходить за межі буфера, відбувається звернення до червоної зони. Інструментований код KASAN перевіряє тіньову пам'ять, бачить недоступний байт і генерує KASAN-звіт (Bug report).

### 3.2 Use-After-Free (UAF)
Після звільнення пам'яті функцією `kfree()`, KASAN не повертає її одразу до алокатора. Замість цього він розміщує її у спеціальний карантин (quarantine), а тіньову пам'ять для цього блоку позначає як звільнену (`0xFC`). Якщо інший код спробує звернутися до цього блоку за старим вказівником, KASAN помітить звернення до недоступної пам'яті. Карантин затримує перевикористання блоку (reallocation), що збільшує вірогідність виявлення UAF, перш ніж блок буде перезаписаний іншим об'єктом.

## 4. Звіт KASAN: Читання та аналіз

Типовий звіт KASAN у `dmesg` виглядає подібно до kernel oops, але містить додаткову специфічну інформацію.

```
==================================================================
BUG: KASAN: use-after-free in foo_function+0x42/0x100
Read of size 8 at addr ffff888100234000 by task my_process/1234
...
```

Основні секції звіту:
1. **Тип помилки:** (use-after-free, slab-out-of-bounds, тощо).
2. **Місце:** (IP, інструкція, яка виконала некоректний доступ), стек викликів (Call Trace) на момент доступу.
3. **Історія алокації/звільнення:** Якщо включено `CONFIG_STACKTRACE`, KASAN зберігає стек викликів під час виділення та звільнення проблемного об'єкта. Це критично важливо для налагодження UAF.
4. **Дамп тіньової пам'яті:** (Memory state around the buggy address). Показує байти навколо адреси; проблемний байт виділено дужками, наприклад `[fc]`. Це дозволяє зрозуміти, чи це червона зона, чи звільнена пам'ять.

## Висновок
KASAN є невід'ємною частиною сучасного циклу розробки ядра Linux (зокрема, використовується фазером syzkaller). Його ефективність у виявленні складних багів, таких як UAF, врятувала ядро від безлічі критичних вразливостей.
