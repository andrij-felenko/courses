# Користувацькі події у ftrace: User Events підсистема

<preknowlist>
- [Контроль і трасування: ftrace та tracefs](book:unix-linux/ftrace-kernel-tracing) — підсистема ftrace, віртуальна ФС tracefs, кільцевий буфер та трасувальні точки ядра.
- [Системні виклики та інтерфейс ядра](book:unix-linux/syscall-tracing) — механізм переходу між простором користувача та ядром через системні виклики та файлові дескриптори.
</preknowlist>

Високонавантажені сервіси простору користувача — такі як мережеві проксі, бази даних чи вебсервери, що обробляють сотні тисяч запитів за секунду — стикаються з фундаментальною суперечністю під час налаштування спостережуваності (observability). З одного боку, розробникам необхідно мати можливість підключитися до працюючого процесу в будь-який момент і отримати деталізовану структуровану телеметрію (латентність, ідентифікатори транзакцій, URL-адреси). З іншого боку, коли трасування вимкнено, інструментарій спостереження не повинен створювати жодного помітного навантаження на процесор — його ціна має дорівнювати нулю.

Історичні інструменти Linux розривали цей баланс: текстовий запис у `/sys/kernel/tracing/trace_marker` марнував процесорні цикли на форматування рядків навіть у вимкненому стані, а точки динамічного трасування USDT (User Statically-Defined Tracing) на базі `uprobes` провокували сотні тисяч апаратних переривань `int 3`, що призводило до перемикання контексту ядра та падіння продуктивності сервісу на десятки відсотків. Детальніше про еволюційну боротьбу між швидкістю та гнучкістю трасування викладено у матеріалі [📜 Історія трасування з простору користувача: від trace_marker та uprobes до User Events](book:unix-linux/user-events-ftrace-subsystem/hist-user-events.md).

Інтегрована у ядро Linux починаючи з версії 5.18 підсистема **User Events** розв'язує цю суперечність. Вона дозволяє програмам простору користувача динамічно реєструвати власні підсистеми подій у ядра, які виглядають і поводяться як стандартні точки трасування ядра (`tracepoints`). Перевірка стану події виконується у користувацькому просторі за 1–2 такти процесора через спільну сторінку пам'яті (`mmap`), а відправка увімкненої події здійснюється як швидкий бінарний векторний запис (`writev`) безпосередньо у кільцевий буфер ftrace чи обробники eBPF.

## 1. Архітектурна модель та принципи побудови

Підсистема User Events мостує простір користувача та внутрішні механізми ядра Linux через абстракцію віртуальної файлової системи `tracefs`. Замість створення власних приватних каналів передачі даних (як це роблять позаядерні системи трасування), User Events інтегрує події користувача безпосередньо у загальну модель `tracepoint` ядра.

![Архітектура підсистеми User Events](/reference/unix-linux/observability/user-events-ftrace-subsystem/img/architecture.svg)
*Рис. 1. Архітектурна схема взаємодії прикладної програми з ядром Linux через підсистему User Events, спільну пам'ять mmap та трасувальні інструменти ftrace, perf і eBPF.*

Архітектура підсистеми спирається на три ключових елементи:

1. **Керівний та транспортний вузол `user_events_data`:** Псевдофайл `/sys/kernel/tracing/user_events_data` є єдиною точкою входу для програм користувача. Через нього за допомогою викликів `ioctl()` реєструються нові події, через нього через виклик `mmap()` отримується доступ до масиву статусу, і в нього ж через виклики `write()`/`writev()` надсилаються бінарні пакунки подій.
2. **Динамічні tracepoint-дерева у tracefs:** Під час реєстрації події ядро автоматично створює відповідний каталог у файловій системі `tracefs` за шляхом `/sys/kernel/tracing/events/user_events/<назва_події>/`. У цьому каталозі з'являються стандартні управляючі файли: `enable` (увімкнення/вимкнення), `filter` (фільтрація полів), `format` (текстовий опис бінарного формату) та `id` (унікальний числовий ідентифікатор події в ядрі).
3. **Єдиний шинопровід споживачів (Consumer Bus):** З точки зору ядра, подія користувача нічим не відрізняється від системного tracepoint (таких як `sched_switch` чи `sys_enter`). Це означає, що як тільки подія згенерована користувацьким застосунком, вона може бути одночасно перехоплена будь-яким наявним інструментом Linux: записана у кільцевий буфер `ftrace`, згрупована підсистемою `perf`, або оброблена eBPF-програмою, прив'язаною до відповідного tracepoint.

## 2. Zero-Overhead перевірка стану через спільну пам'ять

Найважливішим досягненням User Events є реалізація механізму **Zero-Overhead** (нульових витрат) у ситуації, коли трасування вимкнено.

Традиційні системні виклики вимагають перемикання контексту процесора з режиму користувача (`Ring 3`) у режим ядра (`Ring 0`), збереження регістрів, перевірки прав та повернення назад. Такий виклик займає від 50 до 100 наносекунд. Якщо програма намагатиметься запитати ядро через системний виклик «чи увімкнено зараз логування?», вона втратить продуктивність ще до того, як сформує сам лог.

User Events обходить цю перешкоду за допомогою механізму розділюваної пам'яті (`shared memory`):

```
             ПРОСТІР КОРИСТУВАЧА                    ЯДРО LINUX
     +----------------------------------+   +------------------------+
     |  Прикладний процес               |   | ftrace / sysfs control |
     |                                  |   |                        |
     |  status_ptr = mmap(fd)           |   |                        |
     |                                  |   |  echo 1 > enable       |
     |  if (status_ptr[status_index])   |   |        |               |
     |       [ Виконати writev() ]      |   |        v               |
     |  else                            |   |  Ядро пише 0x01        |
     |       [ Пропустити 1-2 такти ]   |   |  у сторінку статусу    |
     |                                  |   |        |               |
     +----------------------------------+   +--------|---------------+
                       ^                             |
                       |===== Пряме читання RAM =====|
```

Під час відкриття файла `user_events_data` ядро виділяє для процесу (або групи процесів) сторінку статусу. Коли програма реєструє подію через `ioctl(DIAG_IOCSREG)`, ядро закріплює за цією подією конкретний байт у цій сторінці й повертає його номер — `status_index`.

Після виконання `mmap()` програма отримує прямий вказівник у пам'яті на цю сторінку. Оскільки сторінка змонтована лише для читання (`PROT_READ`), процес не може її пошкодити.

### Алгоритм виконання у користувацькому коді та бар'єри пам'яті

Коли застосунок доходить до точки в коді, де сформовано подію, він не викликає системних функцій, а виконує одну процесорну інструкцію читання з пам'яті:

:::tabs
```c
/* status_map - вказівник на mmap-сторінку, status_index - отриманий ID */
if (__builtin_expect(status_map[status_index] != 0, 0)) {
    /* Трасування увімкнено адміністратором!
     * Тільки зараз виконуємо пакування полів та системний виклик writev().
     */
    trace_user_event_payload(...);
}
```
```cpp
// status_map - вказівник на mmap-сторінку, status_index - отриманий ID
if (status_map[status_index] != 0) [[unlikely]] {
    // Трасування увімкнено адміністратором!
    // Тільки зараз виконуємо пакування полів та системний виклик writev().
    trace_user_event_payload(...);
}
```
:::

У 99.9% часу, коли трасування у продакшн-середовищі вимкнено, цей байт дорівнює `0`. Процесор зчитує значення `0` безпосередньо з кешу L1 (або за 1–2 такти процесора), предиктор розгалужень (branch predictor) бачить виражений умовою пропуск, і програма миттєво продовжує виконання основної бізнес-логіки.

З точки зору синхронізації між ядрами процесора, коли системний адміністратор виконує команду `echo 1 > .../enable`, ядро Linux оновлює відповідний прапор у внутрішній структурі `struct user_event` та виконує виклик бар'єра запису пам'яті `smp_wmb()`, після чого записує значення `0x01` у сторінку статусу. У користувацькому просторі процесор зчитує це значення через звичайну інструкцію зчитування. Завдяки когерентності кешів процесора (протоколи MESI/MOESI), зміна прапорця стає помітною усім потокам виконання протягом кількох наносекунд.

## 3. Внутрішня реалізація ядра: від ioctl до tracepoint_probe

Для повного розуміння механізму простежимо шлях виконання події всередині вихідного коду ядра Linux (підсистема `kernel/trace/trace_events_user.c`).

### Етап 1. Реєстрація через user_events_ioctl

Коли процес викликає `ioctl(fd, DIAG_IOCSREG, &reg)`, ядро переходить у обробник `user_events_ioctl()`:

1. **Парсинг специфікації:** Ядро копіює C-рядок із `reg.name_args` з пам'яті користувача у свій внутрішній буфер (`user_event_parse`). Воно розбиває рядок на назву події та токени полів.
2. **Перевірка наявних об'єктів:** Ядро шукає у глобальній хеш-таблиці, чи не була ця подія вже зареєстрована іншим процесом. Якщо подія з таким ім'ям та **абсолютно ідентичною бінарною сигнатурою** вже існує, ядро просто повертає наявні індекси `status_index` та `write_index`. Якщо сигнатура полів різниться, виклик повертає помилку `-EBUSY`.
3. **Створення внутрішніх структур:** Якщо подія нова, ядро виділяє пам'ять під структуру `struct user_event`, створює об'єкт `struct trace_event_call` та реєструє новий динамічний tracepoint у підсистемі ftrace через `trace_add_event_call()`.
4. **Створення файлів у tracefs:** Ядро створює відповідний каталог у `/sys/kernel/tracing/events/user_events/` і генерує вміст файла `format`.

```text
  ioctl(DIAG_IOCSREG)
          |
          v
user_events_ioctl() ---> user_event_parse() (валідація рядка)
          |
          v
user_event_create() ---> trace_add_event_call() (реєстрація в ftrace)
          |
          v
Призначення status_index і write_index ---> повернення у Userspace
```

### Етап 2. Запис даних через user_events_write_core

Коли увімкнена програма виконує `writev(fd, iov, count)`, ядро викликає обробник `user_events_write_core()`:

1. **Зчитування ідентифікатора:** Ядро читає перші 4 байти з `iov[0]`, отримуючи `write_index`.
2. **Пошук об'єкта події:** За значенням `write_index` у контексті відкритого файла `user_events_data` ядро знаходить вказівник на структуру `struct user_event`.
3. **Виділення буфера у кільці ftrace:** Ядро викликає `trace_event_buffer_lock_reserve()`, виділяючи необхідний обсяг байтів у кільцевому буфері ftrace для поточного процесора (per-CPU ring buffer).
4. **Копіювання payload:** Ядро копіює решту вектора `iov` безпосередньо з пам'яті користувача у виділений буфер ядра за допомогою `copy_from_iter()`.
5. **Фіксація та виклик BPF:** Викликом `trace_event_buffer_commit()` ядро фіксує запис у буфері і послідовно викликає усі прив'язані до цього tracepoint обробники eBPF або perf.

```text
  writev(fd, iov, 3)
          |
          v
user_events_write_core() ---> Зчитування write_index (iov[0])
          |
          v
trace_event_buffer_lock_reserve() (виділення пам'яті у per-CPU ring buffer)
          |
          v
copy_from_iter() (копіювання iov[1] та iov[2] з Userspace у Kernel ring buffer)
          |
          v
trace_event_buffer_commit() ---> виклик BPF-програм / perf-слухачів
```

## 4. Реєстрація подій та ABI підсистеми

Реєстрація події — це процес узгодження типізованого контракту між застосунком та ядром. Програма повинна повідомити ядру назву події та список її полів разом із їхніми типами.

Процес реєстрації здійснюється за допомогою виклику `ioctl` з командою `DIAG_IOCSREG`. Програма передає в ядро структуру `struct user_reg`. Повний довідник двійкових структур, полів та кодів помилок наведено у матеріалі [📋 Інтерфейс ABI підсистеми User Events: ioctl, mmap та формат даних](book:unix-linux/user-events-ftrace-subsystem/api-user-events.md).

### Опис схеми полів (Event Format String)

Схема події задається C-рядком, який схожий на оголошення полів у мові C. Наприклад:

```text
app_http_request u32 status_code; u64 latency_ns; char url[128]
```

Цей рядок повідомляє ядру, що треба створити подію з трьома полями:
- `status_code` — 32-бітне беззнакове ціле число;
- `latency_ns` — 64-бітне беззнакове ціле число;
- `url` — статичний масив з 128 символів.

Після обробки цього рядка ядро валідує синтаксис і створює файл `format` у `tracefs`. Файл `format` є офіційним контрактом для зовнішніх аналізаторів (таких як `perf` чи `gdb`), що описує зміщення полів у байтах від початку бінарного payload.

```text
name: app_http_request
ID: 1042
format:
	field:unsigned int status_code;	offset:8;	size:4;	signed:0;
	field:unsigned long long latency_ns;	offset:12;	size:8;	signed:0;
	field:char url[128];	offset:20;	size:128;	signed:1;
```

Зверніть увагу: перші 8 байтів у структурі ftrace зарезервовані під системний заголовок ядра (загальний заголовок події `common_type`, `common_flags` тощо). Ядро автоматично враховує ці зміщення під час формування відображення.

## 5. Динамічні типи даних та специфікатор `__data_loc`

Статичні масиви (наприклад, `char url[128]`) прості в обробці, але вони некоректно витрачають пам'ять і смугу пропускання буфера ядра: якщо рядок URL містить всього 10 символів, програма все одно змушена передавати і копіювати решту 118 байтів порожнечі.

Для розв'язання цієї проблеми у User Events інтегровано підтримку динамічних масивів ядра через специфікатор `__data_loc`.

Специфікація події з динамічним рядком виглядає так:

```text
app_http_request u32 status_code; u64 latency_ns; __data_loc char[] url
```

![Бінарна структура пакунка події у writev()](/reference/unix-linux/observability/user-events-ftrace-subsystem/img/payload-structure.svg)
*Рис. 2. Двійкове кодування вектора writev(): розділення ідентифікатора write_index, фіксованих полів та дескриптора __data_loc для динамічних рядків.*

### Механізм кодування `__data_loc`

Коли у схемі оголошено `__data_loc`, фіксована частина payload не містить самого рядка. Замість цього на місці полів виділяється **4 байти** під так званий **локатор** (`u32 loc`).

Локатор пакує два 16-бітних значення:
1. **Низькі 16 біт (`offset`):** Зсув у байтах від початку фіксованого заголовка події до місця у пам'яті, де реально починаються динамічні дані.
2. **Високі 16 біт (`len`):** Фактична довжина динамічного рядка в байтах (включаючи нуль-термінатор).

```
 31                            16 15                             0
+--------------------------------+--------------------------------+
|  Довжина рядка (len, 16 біт)   | Зсув від початку (off, 16 біт) |
+--------------------------------+--------------------------------+
```

Самі динамічні дані (символи рядка або байтовий масив) розміщуються у векторі `writev()` одразу за фіксованою структурою. Ядро читає 32-бітний `loc`, зчитує `offset` і `len`, перевіряє, що межі не виходять за загальний розмір отриманого пакета, і копіює у кільцевий буфер лише реально передані байти.

Це забезпечує максимальну щільність пакування даних у кільцевому буфері ftrace без зайвого оверхеду копіювання пам'яті.

## 6. Запис подій у ядро через системний виклик writev()

Коли перевірка `status_map[status_index] != 0` показує, що подію увімкнено, програма повинна передати сформовані байти в ядро.

Рекомендованим способом передачі є системний виклик `writev()`. Перевага `writev()` полягає у можливості зібрати пакунок з кількох розрізнених буферів пам'яті без попереднього копіювання їх в один суцільний масив простору користувача (Zero-Copy у користувацькому просторі).

### Формат вектора `iovec`

Вектор `iovec` складається з двох або трьох елементів:

1. **`iov[0]` (Ідентифікатор `write_index`):** Перші 4 байти обов'язково повинні містити 32-бітний ідентифікатор `write_index`, отриманий програмою від ядра під час реєстрації `DIAG_IOCSREG`. Це необхідно для того, щоб ядро миттєво визначило, якій саме зареєстрованій події належить цей пакет.
2. **`iov[1]` (Фіксована частина payload):** Структура мови C/C++, що містить скалярні поля та локатори `__data_loc`.
3. **`iov[2]` (Динамічні payload-дані):** Буфер, що містить самі динамічні рядки чи масиви байтів.

:::tabs
```c
#include <sys/uio.h>

/* Перший елемент - ID події (4 байти) */
struct iovec iov[3];
iov[0].iov_base = &reg.write_index;
iov[0].iov_len  = sizeof(reg.write_index);

/* Другий елемент - фіксовані поля структури */
iov[1].iov_base = &payload_header;
iov[1].iov_len  = sizeof(payload_header);

/* Третій елемент - динамічний рядок */
iov[2].iov_base = (void *)dynamic_url_string;
iov[2].iov_len  = dynamic_url_length;

/* Відправка в ядро за один системний виклик */
ssize_t bytes_written = writev(fd, iov, 3);
```
```cpp
#include <sys/uio.h>
#include <array>
#include <string_view>

std::uint32_t write_id = reg.write_index;
std::string_view url = "/api/v1/resource";

std::array<::iovec, 3> iov{};
iov[0].iov_base = &write_id;
iov[0].iov_len  = sizeof(write_id);

iov[1].iov_base = &payload_header;
iov[1].iov_len  = sizeof(payload_header);

iov[2].iov_base = const_cast<char*>(url.data());
iov[2].iov_len  = url.size() + 1;

ssize_t bytes_written = ::writev(fd, iov.data(), iov.size());
```
:::

Повний працюючий приклад програми з обробкою сигналів завершення, вирівнюванням полів та практичним керівництвом з тестування наведено у матеріалі [⚙️ Практикум: створення та відправка користувацьких подій у ftrace мовами C та C++](book:unix-linux/user-events-ftrace-subsystem/proj-user-events-demo.md).

## 7. Інтеграція з екосистемою трасування Linux

Головною перевагою User Events над специфічними фреймворками є те, що після реєстрації подія автоматично стає доступною для всіх стандартних інструментів Linux.

### Вбудована фільтрація ftrace

Завдяки тому, що ядро знає бінарну схему полів з опису реєстрації, адміністратор може налаштувати фільтрацію подій прямо в ядрі.

Наприклад, якщо ми хочемо логувати у кільцевий буфер ftrace лише ті HTTP-запити, час виконання яких перевищує 5 мілісекунд (5 000 000 наносекунд), виконуємо команду:

```bash
echo "latency_ns > 5000000" > /sys/kernel/tracing/events/user_events/app_http_request/filter
```

Після цього ядро Linux буде самостійно перевіряти умову `latency_ns > 5000000` під час кожного виклику `writev()`. Якщо умова хибна, байти відкидаються на вході в ядро без запису в кільцевий буфер ftrace. Програма користувача продовжує виконувати `writev()`, але витрати на збереження логів зникають.

### Запис через інструмент perf

Інструмент `perf` може записувати події користувача разом із апаратними лічильниками процесора (CPU cycles, cache misses) або контекстними перемиканнями ядра:

```bash
sudo perf record -e user_events:app_http_request -a sleep 10
sudo perf script
```

### Аналіз та аналітика через eBPF (bpftrace)

Оскільки подія є стандартним tracepoint, до неї можна підключити BPF-програму. Інструмент `bpftrace` дозволяє на ходу будувати гістограми або агрегувати метрики без запису окремих рядків на диск:

```bash
sudo bpftrace -e '
tracepoint:user_events:app_http_request {
    @latency_hist = hist(args->latency_ns / 1000); // Гістограма у мікросекундах
    if (args->status_code >= 500) {
        @error_count[args->status_code]++;
    }
}'
```

BPF-програма виконується у контексті ядра при виконанні `writev()`, зчитує аргументи безпосередньо з буфера й оновлює BPF-карти (maps) у пам'яті з мінімальними витратами.

## 8. Модель безпеки, обмеження та ізоляція

Дозволяти користувацьким програмам створювати об'єкти у контексті ядра вимагає суворих механізмів обмеження доступу та захисту від атак типу «відмова у обслуговуванні» (DoS).

### Права доступу до tracefs

За замовчуванням файли у `/sys/kernel/tracing/` належать користувачу `root`. Застосунок без привілеїв не зможе відкрити `/sys/kernel/tracing/user_events_data`.

Для надання прав звичайним сервісам системний адміністратор у сучасних дистрибутивах Linux може скористатися двома механізмами:
1. **POSIX Capability:** Надати виконуваному файлу сервісу капсулу `CAP_PERFMON` або `CAP_SYS_ADMIN` за допомогою команди `setcap cap_perfmon=+ep ./my_service`.
2. **Спеціальна група:** Змінити групу власника файла `/sys/kernel/tracing/user_events_data` на групу `tracing` і надати їй права читання/запису (`chmod 0660`).

### Системні обмеження ядра

Для запобігання вичерпанню пам'яті ядра підсистема User Events реалізує декілька рівнів лімітів:

- **Лимит кількості подій (`user_events_max`):** Ядро обмежує загальну кількість унікальних подій, які можуть бути зареєстровані у системі (за замовчуванням 32 768). Значення регулюється через `sysctl kernel.user_events_max`.
- **Максимальний розмір пакунка:** Розмір одного payload у виклику `writev()` обмежений 64 кілобайтами. Якщо програма намагається передати більший обсяг даних, `writev()` повертає помилку `-EINVAL`.
- **Валідація імен та полів:** Імена подій перевіряються на відсутність спецсимволів і не можуть перекривати імена вбудованих подій ядра (наприклад, не можна створити користувацьку подію з назвою `sched_switch`).

### Ізоляція у контейнерах (Namespaces)

У початковій версії (Linux 5.18) події `user_events` реєструвалися у глобальному просторі імен ядра. Це означало, що два різних Docker-контейнери, що запускали однакові застосунки, могли конфліктувати за назви подій.

Починаючи з ядра **Linux 6.4**, підсистему було розширено підтримкою пространств імен трасування (user tracing namespaces). Це дозволяє ізолювати реєстрацію подій всередині контейнера: подія, зареєстрована у контейнері A, не бачна у контейнері B і не конфліктує з її збігається ім'ям.

## 9. Практичний порівняльний аналіз та заміри швидкодії

Для обґрунтованого вибору інструментарію спостережуваності порівняємо витрати на обробку однієї події різними підходами Linux:

| Характеристика | trace_marker | uprobes / USDT | LTTng-UST | **User Events (Linux 5.18+)** |
| :--- | :--- | :--- | :--- | :--- |
| **Витрати у вимкненому стані** | Високі (snprintf) | 1 такт NOP | 1 такт (RAM check) | **1 такт (mmap RAM check)** |
| **Витрати увімкненої події** | ~500–1000 нс | ~1500–3000 нс | ~20–50 нс | **~100–250 нс** |
| **Структурованість даних** | Немає (текст) | Так (ELF metadata) | Так (CTF format) | **Так (ABI binary format)** |
| **Вбудована фільтрація в ядрі**| Немає | Так (eBPF) | Ні (user-space) | **Так (ftrace / eBPF filter)** |
| **Необхідність сторонніх демонів**| Ні | Ні | Так (lttng-sessiond)| **Ні (нативно в ядрі)** |
| **Інтеграція з ftrace/perf/eBPF**| Часткова (текст)| Нативна | Немає | **Повна нативна** |

> 🔧 **Навіщо це у розробці.**
> Підсистема **User Events** є ідеальним вибором для розробки високонавантажених C/C++, Rust або Go систем (вебсервери, проксі-сервери на зразок Envoy або Nginx, СУБД), де звичайне логування у текстовий файл або `stdout` створює неприпустимий оверхед дискового вводу-виводу чи блокує потоки виконання. Використання User Events дозволяє залишити сотні точок трасування прямо у гарячих циклах обробки коду, знаючи, що у вимкненому стані вони виконуються за 1 такт процесора, а при виникненні інциденту у продакшн-середовищі — миттєво увімкнути їх через `tracefs` і отримати повний двійковий профілограф системи без перезапуску сервісу.
