# 📜 Історія трасування з простору користувача: від trace_marker та uprobes до User Events

Вставка пояснює еволюційний шлях механізмів спостережуваності (observability) у системі Linux для програм простору користувача. Вона розкриває проблеми продуктивності, компроміси безпеки та архітектурні обмеження попередніх підходів (`/dev/kmsg`, `trace_marker`, uprobes/USDT, LTTng-UST), які зрештою призвели до розробки та інтеграції підсистеми User Events у ядро Linux 5.18.

## 1. Рання епоха: логування через kmsg та виклики printk

На зорі розвитку операційної системи Linux основним інструментом отримання діагностичної інформації від ядра був буфер `printk`, доступний через системний виклик `syslog` або псевдопристрій `/dev/kmsg`. Ранні розробники системного програмного забезпечення інколи використовували цей пристрій для відправки логів із користувацького простору у загальний системний журнал.

Однак цей підхід мав серйозні обмеження і не призначався для високонавантаженого трасування. Буфер `printk` мав фіксований розмір, і масове виведення повідомлень від прикладних програм швидко призводило до «затоплення» (log flooding) важливих системних повідомлень ядра, таких як сповіщення про помилки дискового вводу-виводу або паніку ядра (kernel panic). Крім того, виклики запису у `/dev/kmsg` вимагали значних ресурсів на форматування рядків у режимі ядра та роботу з символьними пристроями VFS.

з появою у ядрі Linux 2.6.27 підсистеми трасування **ftrace** (Function Tracer) виникла потреба створити спеціалізований, високошвидкісний канал зв'язку між користувацькими процесами та кільцевими буферами ядра.

## 2. Текстовий протік через trace_marker та trace_marker_raw

Першою спробою інтегрувати користувацькі події безпосередньо у підсистему ftrace стала поява віртуального файла `/sys/kernel/tracing/trace_marker` (та його пізнішої модифікації `trace_marker_raw`).

Ідея `trace_marker` полягала у повній простоті використання: будь-яка програма простору користувача могла відкрити цей файл як звичайний файловий дескриптор і виконувати у нього системний виклик `write()` з будь-яким текстовим вмістом:

:::tabs
```c
int trace_fd = open("/sys/kernel/tracing/trace_marker", O_WRONLY);
write(trace_fd, "User event: Processing request #1042", 36);
```
```cpp
int trace_fd = ::open("/sys/kernel/tracing/trace_marker", O_WRONLY);
std::string_view msg = "User event: Processing request #1042";
::write(trace_fd, msg.data(), msg.size());
```
:::

Ядро Linux перехоплювало цей виклик і негайно вставляло надісланий текстовий рядок у загальний кільцевий буфер ftrace (`ring buffer`), автоматично додаючи до нього системну часову позначку високої точності (timestamp), номер процесора (CPU ID) та ідентифікатор поточного процесу (PID).

```text
[Прикладний процес] -- write("User event") --> /sys/kernel/tracing/trace_marker --> [ftrace ring buffer]
```

Попри надзвичайну простоту впровадження, цей підхід виявився абсолютно непридатним для високопродуктивних продакшн-систем через чотири фундаментальні архітектурні вади:

1. **Відсутність структури даних:** Усі події надходили в ядро як неструктурований текст. Для подальшої аналітики або побудови графіків системному адміністратору або утилітам моніторингу доводилося вичитувати велетенські текстові логи та парсити їх регулярними виразами. Це створювало величезне навантаження на процесор у користувацькому просторі.
2. **Неможливість вбудованої фільтрації у ядрі:** Оскільки ядро бачило лише неструктурований потік символів, воно не могло застосувати внутрішній механізм фільтрів ftrace (наприклад, відфільтрувати події за числовою умовою `latency > 100` або `error_code == 500`). Усі надіслані рядки безумовно потрапляли у кільцевий буфер, миттєво переповнюючи його та витісняючи важливі траси ядра.
3. **Високий overhead форматування рядків:** Навіть у ситуації, коли буфер ftrace ніхто не читав, прикладний застосунок змушений був на кожному кроці виконувати виклики `snprintf()` для збірки текстового рядка й здійснювати системний виклик `write()`. Це марнувало дорогоцінні процесорні цикли.
4. **Проблема trace_marker_raw:** Пізніше доданий файл `trace_marker_raw` дозволяв надсилати бинарні байти замість тексту, але ядро все одно розглядало їх як неструктуровану пляму (blob) і не вміло надавати схему полів для інструментів `perf` чи eBPF.

## 3. Революція статичного трасування: USDT та механізм Uprobes

Для вирішення проблеми структурованості даних у середині 2000-х років із операційної системи Sun Solaris у світ Linux було портовано концепцію **USDT** (User Statically-Defined Tracing). У Linux цей механізм було реалізовано поверх підсистеми **uprobes** (User Space Probes).

Основна ідея USDT полягала у тому, щоб вставляти точки трасування безпосередньо у бінарний код програми на етапі компіляції (за допомогою макросів DTrace `DTRACE_PROBE()` або SystemTap `STAP_PROBE()`).

### Внутрішня будова USDT-точки

На етапі компіляції компилятор (GCC або Clang) виконує дві дії:
1. У місці розміщення точки трасування в машиний код вставляється однобайтова інструкція **`NOP`** (No Operation). У звичайному режимі роботи ця інструкція виконується за один такт процесора й не робить нічого.
2. У спеціальну ELF-секцію `.note.stapsdt` записано метадані: назва події, її аргументи та точні операнди (які саме регістри процесора або комірки стека містять значення змінних у цю мить).

```text
Вимкнено (Enabled = False):
[ Інструкція A ] -> [ NOP (1 такт CPU) ] -> [ Інструкція B ]

Увімкнено (Enabled = True):
[ Інструкція A ] -> [ INT 3 (Trap 0xCC) ] -> Ядро: Перехоплення -> Перемикання контексту -> BPF/Perf -> [ Інструкція B ]
```

Коли інструмент трасування (наприклад, `bpftrace` чи `perf`) активує USDT-точку, ядро Linux через підсистему `uprobes` динамічно модифікує машинну пам'ять працюючого процесу: воно перезаписує інструкцію `NOP` на інструкцію апаратного переривання (на архітектурі x86_64 це `int 3`, опкод `0xCC`).

### Драматичний overhead uprobes та переривань

Хоча USDT розв'язав проблему структурованості та дозволив eBPF-програмам зчитувати значення з регістрів процесу, ціна виконання увімкненої точки виявилася катастрофічною.

Щоразу, коли потік процесу досягає інструкції `int 3`, виникає апаратне виключення процесора (trap):
- Процесор зупиняє виконання коду простору користувача і перемикається на таблицю векторів переривань ядра (IDT);
- Ядро виконує збереження усіх регістрів загального призначення процесу на стек ядра;
- Відбувається перемикання таблиць сторінок пам'яті (згідно з механізмом захисту від уразливостей KPTI);
- Підсистема `uprobes` знаходить прив'язаний обробник, копіює пам'ять користувача і виконує BPF-програму;
- Виконується зворотне відновлення контексту й повернення у простір користувача через інструкцію `iret`.

Замери продуктивності показують, що одне спрацьовування uprobe займає від **1500 до 3000 наносекунд** (1.5–3.0 мікросекунди). Якщо високонавантажений вебсервер обробляє 100 000 запитів за секунду і на кожен запит викликається 5 USDT-точок, процес виконуватиме півмільйона апаратних переривань на секунду. Це призводить до падіння продуктивності сервісу на 30–80%, що робить USDT непридатним для постійно увімкненого моніторингу гарячих циклів у продакшн.

## 4. Спроби створення користувацьких кільцевих буферів: LTTng-UST

Бачачи обмеження uprobes, розробники канадського проекту **LTTng-UST** (Linux Trace Toolkit Next Generation — User Space Tracing) розробили принципово іншу архітектуру.

Вони вирішили взагалі не звертатися до ядра під час трасування. Замість цього LTTng-UST виділяє кільцеві буфери у спільній пам'яті (`shm`) між прикладною програмою та фоновим демоном моніторингу.

Перевірка стану події в LTTng-UST здійснюється перевіркою прапорця в пам'яті за 1 такт, а запис події виконується за допомогою безблокових атомарних інструкцій (lockless ring buffer) прямо у користувацькому просторі. Це дозволило досягти вражаючої швидкодії: відправка події займає всього **20–50 наносекунд**.

Проте LTTng-UST не став загальноприйнятим стандартом Linux через складність екосистеми:
- Він вимагає встановлення сторонніх бібліотек та запуску спеціальних фонових демонів (`lttng-sessiond`);
- Події LTTng не видно у стандартній інфраструктурі ядра Linux (`tracefs`, `ftrace`, `perf`);
- Відсутня пряма взаємодія з eBPF-програмами ядра без застосування складних костилів та трансляторів.

## 5. Зародження та народження підсистеми User Events (Linux 5.18+)

У 2021 році інженер Бо Белгрейв (Beau Belgrave) з компанії Microsoft у співпраці з ключовими архітекторами підсистеми трасування ядра Linux (Стівеном Ростемпом/Steven Rostedt, Масамі Хірамацу/Masami Hiramatsu та іншими) висунув ініціативу створення нового нативного механізму ядра.

Метою проекту було створення підсистеми, яка поєднає у собі найкращі риси попередників:

1. **Швидкість LTTng-UST:** Перевірка активності події має виконуватися у користувацькому просторі через спільну сторінку пам'яті `mmap` без виконання системних викликів або переривань (Zero-Overhead у вимкненому стані).
2. **Нативність та структурованість ftrace:** Зареєстрована подія повинна ставати повноцінним `tracepoint` ядра у файловій системі `tracefs` зі чітко оголошеною бінарною схемою полів.
3. **Пряма сумісність з eBPF та perf:** Інструменти `bpftrace`, `perf` та довільні eBPF-програми повинні мати можливість підключатися до користувацьких подій точно так само, як до системних подій ядра.

Після серії інтенсивних обговорень у поштовій розсилці Linux Kernel Mailing List (LKML) та внесення численних покращень щодо безпеки та пам'яті, патчі підсистеми **User Events** були офіційно прийняті Лінусом Торвальдсом до основного ядра Linux у версії **5.18** у травні 2022 року.

У наступних випусках ядра підсистему було суттєво розширено: у ядрі 6.4 додано підтримку просторів імен (namespaces) для ізоляції подій у контейнерах Docker/Kubernetes, а також впроваджено мульти-байтне відстеження статусу для складнокомплексних систем моніторингу.
