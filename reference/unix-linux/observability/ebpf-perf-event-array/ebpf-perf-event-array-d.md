# Канали подій eBPF Perf Event Array

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У світі eBPF та системного програмування на базі Linux одним із найголовніших завдань є передача зібраних даних з простору ядра (kernel space) до простору користувача (user space). Під час трасування, моніторингу або профілювання ядра системи, eBPF програми часто генерують тисячі чи навіть мільйони подій на секунду. Збереження цих подій у ядрі або їх пряма передача у повільний userspace вимагає надійної, високопродуктивної та низькозатримної архітектури. 

Довгий час золотим стандартом для такого завдання був тип мапи (map type) **`BPF_MAP_TYPE_PERF_EVENT_ARRAY`**. Незважаючи на появу новіших механізмів, таких як BPF Ring Buffer, `PERF_EVENT_ARRAY` залишається надзвичайно поширеним, добре перевіреним у бойових умовах і підтримується майже всіма версіями ядер, що мають базову підтримку eBPF.

У цій статті ми глибоко зануримося в архітектуру `BPF_MAP_TYPE_PERF_EVENT_ARRAY`, розберемо механіку використання допоміжної функції `bpf_perf_event_output()`, дослідимо переваги та недоліки per-CPU ring buffer підходу, розглянемо способи оптимізації для високонавантажених систем та зробимо детальне порівняння з новішим `BPF_MAP_TYPE_RINGBUF`.

---

## 1. Проблема передачі подій з ядра у Userspace

Коли ви пишете програму eBPF для трасування (наприклад, за допомогою `kprobe` або `tracepoint`), ця програма виконується в контексті ядра кожного разу, коли відбувається відповідна подія. Завдання програми — зібрати необхідні дані (регістри, значення аргументів функції, ідентифікатори процесів, часові мітки тощо). 

Виникає фундаментальна проблема: як передати ці зібрані структури даних до демона в userspace (наприклад, вашого моніторингового агента), який буде їх аналізувати, агрегувати та відправляти на бекенд?

- **Системні виклики** для кожної події — занадто повільно і порушує принципи роботи eBPF.
- **Звичайні eBPF Maps (Hash, Array)** чудово підходять для ведення статистики та агрегації прямо в ядрі. Проте вони погано підходять для потокового передавання кожної окремої події (streaming), оскільки userspace має постійно опитувати карту (polling), що створює велике навантаження на CPU і призводить до пропущених подій, якщо userspace не встигає.

Для вирішення цієї проблеми розробники ядра Linux адаптували вже існуючу підсистему **perf**, яка традиційно використовувалася для профілювання (`perf record`). Було введено спеціальний тип карти `BPF_MAP_TYPE_PERF_EVENT_ARRAY`, який дозволяє eBPF програмам надсилати дані у кільцеві буфери підсистеми perf.

## 2. Архітектура BPF_MAP_TYPE_PERF_EVENT_ARRAY

`BPF_MAP_TYPE_PERF_EVENT_ARRAY` — це спеціалізований тип карти eBPF, який представляє собою масив файлових дескрипторів подій `perf`. Під капотом цей механізм реалізований як набір **кільцевих буферів (ring buffers)**. 

Найважливіша архітектурна особливість `PERF_EVENT_ARRAY` полягає в тому, що він використовує **per-CPU** (один на кожен логічний процесор) кільцеві буфери.

### 2.1 Як це працює?

1. **Ініціалізація в Userspace:** Userspace програма створює `PERF_EVENT_ARRAY` карту. Для кожного процесора (CPU core) у системі, вона відкриває `perf_event` за допомогою системного виклику `perf_event_open()`.
2. **Пам'ять (mmap):** Для кожного файлового дескриптора `perf_event` програма викликає `mmap()`, щоб створити спільну область пам'яті (shared memory) між ядром та userspace. Ця область виступає в ролі кільцевого буфера для конкретного процесора.
3. **Запис у ядрі:** Коли спрацьовує eBPF програма, вона використовує функцію `bpf_perf_event_output()` для запису структури даних (події) у буфер, що належить поточному процесору (на якому виконується код).
4. **Читання в Userspace:** Userspace програма використовує механізми асинхронного вводу/виводу, такі як `epoll`, для очікування даних (подій) на всіх дескрипторах `perf_event`. Коли дані з'являються, userspace читає їх з `mmap` області відповідного CPU.

### 2.2 Чому per-CPU?

Підхід з буфером на кожен процесор (per-CPU) вирішує головну проблему багатопроцесорних систем — **конкурентний доступ (concurrency) та блокування (locking)**.

Якби всі процесори писали в один спільний буфер, ядру довелося б використовувати спінлоки (spinlocks) для синхронізації доступу, що призвело б до катастрофічного падіння продуктивності (cache line bouncing, lock contention) при високому навантаженні. Оскільки кожен процесор має власний незалежний буфер, запис з ядра відбувається без жодних блокувань. eBPF програма просто розміщує дані у "своєму" буфері, оновлює вказівник і продовжує роботу.

## 3. API ядра: bpf_perf_event_output()

У просторі ядра, eBPF програма використовує спеціальну функцію-помічник (BPF helper) для надсилання даних у `PERF_EVENT_ARRAY`.

```c
long bpf_perf_event_output(void *ctx, struct bpf_map *map, u64 flags, void *data, u64 size)
```

**Параметри:**
- `ctx`: Контекст eBPF програми (наприклад, `struct pt_regs *` для kprobes).
- `map`: Вказівник на карту типу `BPF_MAP_TYPE_PERF_EVENT_ARRAY`.
- `flags`: Використовується для вказівки, в який саме буфер CPU потрібно записати дані. Зазвичай використовується константа `BPF_F_CURRENT_CPU`, яка вказує ядру використати буфер процесора, на якому наразі виконується цей код. 
  - *Зауваження: Старші 32 біти `flags` також можна використовувати для передачі розміру "сирих" даних (raw sample size).*
- `data`: Вказівник на структуру даних, яку ми хочемо надіслати.
- `size`: Розмір даних у байтах.

**Приклад використання в eBPF коді (C):**

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

/* Визначення структури події */
struct my_event_t {
    __u32 pid;
    __u64 timestamp;
    char comm[16];
};

/* Оголошення PERF_EVENT_ARRAY карти */
struct {
    __uint(type, BPF_MAP_TYPE_PERF_EVENT_ARRAY);
    __uint(key_size, sizeof(__u32));
    __uint(value_size, sizeof(__u32));
} my_perf_map SEC(".maps");

SEC("kprobe/sys_execve")
int bpf_prog1(struct pt_regs *ctx)
{
    struct my_event_t event = {};

    event.pid = bpf_get_current_pid_tgid() >> 32;
    event.timestamp = bpf_ktime_get_ns();
    bpf_get_current_comm(&event.comm, sizeof(event.comm));

    /* Відправка події у userspace */
    bpf_perf_event_output(ctx, &my_perf_map, BPF_F_CURRENT_CPU, &event, sizeof(event));

    return 0;
}

char _license[] SEC("license") = "GPL";
```

### 3.1 Обмеження при записі
Важливо пам'ятати про обмеження стеку в eBPF (лише 512 байт). Якщо ваша структура події дуже велика, ви не зможете виділити її на стеку. У таких випадках використовують **Per-CPU Array Maps** як тимчасовий "scratch buffer" (буфер-чернетку) для зберігання події перед її відправкою через `bpf_perf_event_output`.

## 4. Обробка подій у Userspace

На стороні користувача використання `PERF_EVENT_ARRAY` традиційно вимагало багато шаблонного (boilerplate) коду. Необхідно було викликати `perf_event_open()` для кожного CPU, налаштувати `mmap`, налаштувати механізм опитування за допомогою `epoll` та правильно розбирати заголовки повідомлень підсистеми perf.

На щастя, сучасна бібліотека **`libbpf`** надає високорівневе API, яке приховує всі ці деталі реалізації: структуру `perf_buffer` та функції для роботи з нею.

**Приклад обробки в userspace (C + libbpf):**

```c
#include <stdio.h>
#include <bpf/libbpf.h>
#include <bpf/bpf.h>

/* Callback, який викликається при отриманні кожної події */
void handle_event(void *ctx, int cpu, void *data, __u32 data_sz)
{
    struct my_event_t *e = data;
    printf("CPU %d: PID %d, Comm: %s, Time: %llu\n", 
           cpu, e->pid, e->comm, e->timestamp);
}

/* Callback для обробки втрачених подій (dropped events) */
void handle_lost_events(void *ctx, int cpu, __u64 lost_cnt)
{
    fprintf(stderr, "Попередження: Втрачено %llu подій на CPU %d\n", lost_cnt, cpu);
}

int main(int argc, char **argv)
{
    struct bpf_object *obj;
    struct perf_buffer *pb = NULL;
    int map_fd, err;

    /* ... Завантаження об'єкта bpf (bpf_object__open, bpf_object__load) ... */
    
    map_fd = bpf_object__find_map_fd_by_name(obj, "my_perf_map");

    /* Налаштування perf buffer через libbpf */
    pb = perf_buffer__new(map_fd, 8, /* 8 сторінок пам'яті на кожен CPU буфер */
                          handle_event, handle_lost_events, NULL, NULL);
    if (libbpf_get_error(pb)) {
        fprintf(stderr, "Помилка ініціалізації perf buffer\n");
        return 1;
    }

    printf("Початок трасування... Натисніть Ctrl-C для зупинки.\n");

    /* Безкінечний цикл читання подій */
    while (1) {
        err = perf_buffer__poll(pb, 100 /* таймаут у мілісекундах */);
        if (err < 0 && err != -EINTR) {
            fprintf(stderr, "Помилка опитування perf buffer: %d\n", err);
            break;
        }
    }

    perf_buffer__free(pb);
    /* ... Звільнення ресурсів ... */
    return 0;
}
```

У цьому прикладі `perf_buffer__new()` автоматично створює всі необхідні кільцеві буфери для кожного доступного процесора в системі і налаштовує `epoll`. Метод `perf_buffer__poll()` блокується (чекає), доки в буферах не з'являться нові події, і автоматично викликає ваш callback (`handle_event`).

## 5. Переваги BPF_MAP_TYPE_PERF_EVENT_ARRAY

1. **Висока продуктивність завдяки Lock-less дизайну:** Запис у буфер у просторі ядра не вимагає блокувань, оскільки кожен CPU пише у свій власний буфер. Це робить `PERF_EVENT_ARRAY` надзвичайно швидким.
2. **Широка підтримка (Зворотна сумісність):** Цей тип карти підтримується у Linux починаючи з версії 4.4. Якщо вам потрібно, щоб ваша eBPF програма працювала на старих ядрах (наприклад, CentOS 7 / RHEL 7 з бекпортованим eBPF), ви зобов'язані використовувати `PERF_EVENT_ARRAY`.
3. **Обробка втрачених подій:** Підсистема `perf` автоматично відстежує ситуації, коли userspace не встигає читати події і буфер переповнюється. Вона надає точну інформацію про те, скільки саме подій було втрачено на кожному конкретному CPU.

## 6. Недоліки та архітектурні проблеми

Незважаючи на ефективність, `PERF_EVENT_ARRAY` має декілька фундаментальних недоліків, які роблять його не ідеальним для всіх сценаріїв, і саме ці недоліки призвели до створення нового `BPF_MAP_TYPE_RINGBUF`.

### 6.1 Неефективне використання пам'яті (Memory Overhead)

Оскільки `PERF_EVENT_ARRAY` створює окремий кільцевий буфер фіксованого розміру для **кожного логічного процесора** у системі, загальний обсяг задіяної оперативної пам'яті залежить від кількості ядер. 
- Наприклад, якщо ви виділяєте по 8 сторінок (32 КБ) на кожен CPU, на звичайному ноутбуці з 8 ядрами це займе лише 256 КБ.
- Однак на сучасному сервері з 128 або 256 ядрами, навіть скромні розміри буфера для одного CPU призведуть до виділення кількох мегабайтів. А якщо у вас складна система моніторингу з буферами по кілька мегабайтів на кожен CPU, загальне споживання пам'яті може сягати сотень мегабайт або навіть гігабайт лише для кільцевих буферів, більшість з яких можуть залишатися порожніми більшу частину часу. 
Проблема полягає в тому, що пам'ять не розподіляється між процесорами. Якщо один процесор сильно навантажений подіями (overloaded), його буфер може переповнитися, що призведе до втрати даних, тоді як буфери інших 127 процесорів можуть бути абсолютно порожніми, але їх пам'ять не може бути використана.

### 6.2 Глобальне впорядкування подій (Cross-CPU Event Ordering)

Оскільки кожна подія зберігається у буфері того CPU, який її згенерував, userspace отримує події розкиданими по різних буферах. `perf_buffer__poll()` в `libbpf` використовує `epoll` для пробудження при наявності даних у будь-якому з буферів. Але `epoll` не гарантує строгий хронологічний порядок читання між різними файловими дескрипторами.

В результаті, якщо подія A відбулася на CPU 0 о 10:00:00.001, а подія B відбулася на CPU 1 о 10:00:00.002, ваш userspace застосунок може спочатку зчитати подію B, а потім подію A.
Якщо вашому застосунку критично важливо аналізувати події у строгому глобальному хронологічному порядку, вам доведеться буферизувати та сортувати (впорядковувати) ці події у просторі користувача, спираючись на часові мітки (наприклад, `bpf_ktime_get_ns()`). Ця операція сортування у userspace часто стає серйозним "вузьким місцем" продуктивності (bottleneck).

### 6.3 Непотрібне копіювання даних
Виклик `bpf_perf_event_output()` спочатку змушує вас створити повну копію події (на стеку або в scratch-мапі), а потім ця функція копіює дані ще раз у сам кільцевий буфер. Це подвійне копіювання збільшує затримку.

## 7. Тюнінг та Оптимізація Perf Event Array

При побудові високонавантажених систем на основі `PERF_EVENT_ARRAY`, необхідно враховувати два критичних параметри при налаштуванні в userspace: **розмір буфера** та **wakeup events (поріг пробудження)**.

1. **Розмір буфера:** При ініціалізації `perf_buffer__new` ви задаєте розмір буфера у сторінках пам'яті (page_cnt). Значення обов'язково має бути ступенем двійки (power of two), наприклад: 8, 16, 64. Чим більший буфер, тим рідше userspace може прокидатися без втрати подій (dropped events). Але варто зважати на проблему неефективного використання пам'яті (множення на кількість CPU), описану вище.
2. **Wakeup Threshold (watermark):** За замовчуванням підсистема `perf` надсилає сигнал пробудження (wakeup / POLLIN) до `epoll` кожного разу, коли у буфер надходить нова подія. Це створює величезну кількість контекстних перемикань (context switches). 
Функція `perf_buffer__new` в `libbpf` дозволяє налаштувати це через `perf_buffer_opts` (або `perf_buffer_raw_opts`), використовуючи параметр `wakeup_events`. Встановивши його, наприклад, у значення `64`, ви скажете ядру: "Не пробуджуй мій userspace процес, поки в буфер не накопичиться хоча б 64 події" (або не буде заповнено певну кількість байтів, якщо використовується `wakeup_watermark`). Це суттєво зменшує використання CPU простором користувача і підвищує загальну пропускну здатність.

## 8. BPF_MAP_TYPE_RINGBUF: Сучасна альтернатива

У ядрі Linux 5.8 (випущеному у 2020 році) розробники ввели новий тип карти — **`BPF_MAP_TYPE_RINGBUF`** (BPF Ring Buffer). Його було створено спеціально для вирішення фундаментальних проблем `PERF_EVENT_ARRAY`.

### 8.1 Ключові відмінності BPF Ringbuf

- **Спільний буфер (Multi-Producer, Single-Consumer):** Ringbuf створює один загальний гігантський кільцевий буфер, спільний для всіх CPU. Розмір буфера більше не множиться на кількість процесорів.
- **Ефективне використання пам'яті:** Пам'ять розподіляється динамічно. Навіть якщо всі події відбуваються на одному CPU, цей CPU може використати всю доступну ємність буфера.
- **Вбудоване глобальне впорядкування:** Оскільки всі CPU пишуть у той самий буфер, події автоматично розміщуються у строгому хронологічному порядку. Userspace читає їх у тій самій послідовності. Немає необхідності в дорогому сортуванні на стороні користувача.
- **API Резервування/Підтвердження (Reserve/Commit):** BPF Ringbuf надає нові хелпери: `bpf_ringbuf_reserve()` та `bpf_ringbuf_submit()`. Ви можете напряму зарезервувати місце в буфері і записувати дані прямо туди (zero-copy), що уникає додаткового копіювання, характерного для `bpf_perf_event_output`.

### 8.2 Чому не всі одразу перейшли на Ringbuf?
1. **Сумісність:** Як згадувалося раніше, Ringbuf з'явився лише у Linux 5.8. Багато корпоративних серверів працюють на старих ядрах (наприклад, Ubuntu 18.04, старі версії RHEL). Якщо вам потрібна підтримка старих систем, `PERF_EVENT_ARRAY` залишається єдиним варіантом.
2. **Продуктивність (Специфічний випадок):** Хоча Ringbuf має глобальний дизайн і використовує дуже легковажний спінлок (spinlock) з коротким часом утримання (short hold time), у вкрай специфічних сценаріях з шаленим навантаженням (мільйони подій на секунду *одночасно на всіх CPU*) глобальний лок може призвести до contention (боротьби за ресурс), і per-CPU `PERF_EVENT_ARRAY` може продемонструвати дещо вищу пропускну здатність. Проте для переважної більшості реальних випадків Ringbuf є швидшим і ефективнішим.

---

## 9. Підсумок

`BPF_MAP_TYPE_PERF_EVENT_ARRAY` та `bpf_perf_event_output()` зробили революцію у можливостях системного моніторингу, надавши інструментам на зразок **BCC** та **bpftrace** здатність ефективно потоково передавати високочастотні дані телеметрії з простору ядра до userspace.

Архітектура на базі **per-CPU кільцевих буферів** забезпечує роботу без блокувань і надзвичайно високу продуктивність під час запису. Водночас, вона страждає від неефективного використання пам'яті на багатоядерних серверах і створює складнощі з глобальним впорядкуванням подій.

Сьогодні, якщо ви розробляєте нову eBPF-аплікацію для сучасних ядер (Linux 5.8+), настійно рекомендується використовувати новіший **BPF Ring Buffer**. Однак глибоке розуміння того, як працює `PERF_EVENT_ARRAY`, залишається обов'язковим для будь-якого eBPF-інженера, оскільки цей механізм ще багато років буде зустрічатися у legacy коді, сумісних агентах та у продакшен-середовищах з консервативними вимогами до оновлення ядра.
