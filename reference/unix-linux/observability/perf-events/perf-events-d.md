# Підсистема perf: лічильники й вибірковий профіль

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття простору ядра й системних викликів.
- [Системний виклик](book:unix-linux/syscall-mechanics) — як користувацька програма звертається до ядра.
</preknowlist>

Коли програма працює повільно, інстинктивне бажання — додати таймери навколо підозрілих функцій. Але цей підхід має фатальну ваду: сам процес вимірювання спотворює результат. Таймери вимагають системних викликів, які зупиняють виконання, скидають конвеєр процесора й витісняють корисні дані з кешу. Щоб зрозуміти реальну продуктивність, потрібен інструмент, який спостерігає за системою, не змінюючи її поведінки.

Підсистема `perf` у Linux розв'язує цю проблему, поєднуючи апаратні можливості процесора з механізмами ядра. Вона дає змогу зазирнути всередину мікроархітектури (рахувати промахи кешу чи такти) та програмних подій (відмови сторінок, перемикання контексту) з майже нульовими накладними витратами.

## Апаратні лічильники продуктивності (PMU)

Щоб вимірювати без втручання, вимірювання має відбуватися апаратно. Сучасні процесори містять спеціальний блок — Performance Monitoring Unit (PMU). Це набір регістрів, які кремній автоматично збільшує, коли стається певна подія. 

Процесор виконує інструкції, а PMU паралельно фіксує:
- **cycles (такти)** — скільки пульсів генератора частоти минуло.
- **instructions (інструкції)** — скільки інструкцій успішно завершилося (retired).
- **cache-misses (промахи кешу)** — скільки разів процесору довелося чекати на дані з оперативної пам'яті через відсутність їх у L1/L2/L3.
- **branch-misses (хибні передбачення розгалужень)** — скільки разів конвеєр був скинутий через те, що процесор не вгадав, куди піде умовний перехід.

Ці лічильники працюють асинхронно. Програма виконується на повній швидкості, а кремній просто оновлює числа збоку. Поділивши `instructions` на `cycles`, отримують **IPC (Instructions Per Cycle)** — ключову метрику того, наскільки щільно завантажений конвеєр процесора. Якщо IPC низький, процесор більшість часу простоює (наприклад, чекаючи на пам'ять).

## Універсальний інтерфейс: perf_event_open

Довгий час кожен архітектурний інструмент мав власні драйвери для доступу до PMU. Linux об'єднав їх навколо єдиного системного виклику — `perf_event_open`. Ця функція є шлюзом не лише до апаратних лічильників, але й до програмних подій ядра.

Виклик `perf_event_open` не просто вмикає лічильник, він створює файловий дескриптор. Це глибоко в дусі Unix («усе є файлом»). Ви налаштовуєте подію (наприклад, «рахувати промахи кешу L1»), передаєте конфігурацію в ядро і отримуєте дескриптор.

Є два фундаментально різні режими використання цього дескриптора: підрахунок (counting) і вибірка (sampling).

### Режим підрахунку (Counting)

У режимі підрахунку `perf` використовується як секундомір. Ядро програмує PMU перед тим, як віддати процесор вашому потоку, і зчитує лічильники, коли потік витісняється. Значення сумуються лише для вашого процесу (або всієї системи, якщо це вказано). 

Користувацька програма просто робить `read()` з дескриптора, щоб отримати 64-бітне ціле число — кількість подій. Це ідеально для відповідей на запитання «скільки всього промахів кешу сталося за час роботи?». Утиліта `perf stat` працює саме так.

```bash
# Рахує такти, інструкції та промахи кешу до завершення програми
perf stat -e cycles,instructions,cache-misses ./my_program
```

### Режим вибірки (Sampling) і переповнення

Підрахунок каже *скільки*, але не каже *де*. Щоб знайти повільну функцію, потрібен режим вибірки (sampling). 

Як зупинити програму саме тоді, коли вона багато працює, не сповільнюючи її постійними перевірками? PMU налаштовують на переривання по переповненню. Замість того, щоб рахувати від 0 вгору, лічильник ініціалізують від'ємним значенням (або числом, близьким до максимуму) — наприклад, налаштовують переповнення кожні 10 000 промахів кешу або кожний мільйон тактів.

Коли лічильник переповнюється, PMU генерує немасковане переривання (NMI). Процесор миттєво зупиняє користувацький код і стрибає в обробник ядра. Ядро дивиться, де саме зупинився процесор (значення регістра Instruction Pointer, `RIP` на x86), записує цю адресу, скидає лічильник і повертає керування програмі. 

Зібравши тисячі таких вибірок, можна побачити статистичний розподіл: функції, де процесор зупинявся найчастіше, і є найгарячішими.

## Кільцевий буфер і доставка подій

Якщо ядро зупиняє програму тисячі разів на секунду, воно не може писати кожну вибірку на диск або робити контекстне перемикання до інструменту моніторингу — це знищило б продуктивність. 

Тому `perf_event_open` використовує спільну пам'ять. Програма, що викликала системний виклик, робить `mmap()` на отриманому файловому дескрипторі. Це створює кільцевий буфер (ring buffer) безпосередньо між ядром і користувацьким простором. Ядро під час NMI швидко записує вибірку в цей буфер і йде. Користувацький процес (наприклад, `perf record`) може асинхронно зчитувати ці дані й зберігати у файл (`perf.data`), не блокуючи ядро.

## Відновлення стеку (Stack Unwinding)

Знати адресу однієї інструкції, де сталося переривання, недостатньо. Проблема може бути не в самій функції `memcpy`, а в функції `parse_json`, яка викликає її мільйон разів. Тому ядро під час вибірки записує весь стек викликів (call graph). 

Є три основні способи відновлення стеку:
1. **Frame Pointers (Вказівники кадрів)**: Компілятор зберігає адресу початку стекового кадру в регістрі `RBP`. Ядро може просто пройтися ланцюжком вказівників. Це швидко, але компілятори часто вимикають цю опцію (`-fomit-frame-pointer`) для оптимізації.
2. **DWARF**: Ядро копіює шматок сирого стеку у вибірку (в кільцевий буфер), а утиліта `perf report` пізніше розбирає його, використовуючи налагоджувальну інформацію DWARF. Це працює завжди, але створює гігантські файли `perf.data` і має великі накладні витрати.
3. **LBR (Last Branch Record)**: Апаратна функція процесорів Intel, яка постійно запам'ятовує останні 16-32 умовні переходи. Це дає змогу відновити стек апаратно і без накладних витрат.

Утиліта `perf record` (з опцією `-g` для стеку викликів) збирає ці дані, а `perf report` їх агрегує.

## Візуалізація: Flamegraphs

Виведення `perf report` у терміналі важко сприймати для глибоких стеків викликів. Цю проблему розв'язав Брендан Грегг (Brendan Gregg), створивши Flamegraphs (полум'яні графи). 

Flamegraph — це візуалізація, де:
- Вісь X представляє частку часу (відсоток вибірок), а не плин часу. Чим ширший прямокутник, тим частіше функція була на стеку під час переривань.
- Вісь Y показує глибину стеку (хто кого викликав). Корінь завжди внизу.
- Кольори зазвичай випадкові (теплі тони), лише щоб візуально відокремити функції.

Щоб знайти «вузьке місце», достатньо подивитися на найширші «плато» на графіку. Якщо широка смуга розпадається на безліч дрібних «зубців» зверху, час витрачається у самій функції (в циклі); якщо ж вона переходить у таку саму широку смугу вище — час витрачається у нащадку.

## Використання perf_event_open у коді

Хоча найчастіше використовують утиліту `perf`, API ядра є відкритим. Можна самостійно викликати `perf_event_open` для точного профілювання критичних ділянок коду (наприклад, у циклах рендерингу або фінансовому трейдингу), щоб читати кількість циклів безпосередньо з процесора.

:::tabs
== C
```c
#include <linux/perf_event.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <stdio.h>
#include <string.h>

long perf_event_open(struct perf_event_attr *hw_event, pid_t pid,
                     int cpu, int group_fd, unsigned long flags) {
    return syscall(__NR_perf_event_open, hw_event, pid, cpu, group_fd, flags);
}

int main() {
    struct perf_event_attr pe;
    memset(&pe, 0, sizeof(struct perf_event_attr));
    pe.type = PERF_TYPE_HARDWARE;
    pe.size = sizeof(struct perf_event_attr);
    pe.config = PERF_COUNT_HW_INSTRUCTIONS;
    pe.disabled = 1;
    pe.exclude_kernel = 1; // Рахувати лише користувацький код
    pe.exclude_hv = 1;

    int fd = perf_event_open(&pe, 0, -1, -1, 0);
    if (fd == -1) return 1;

    ioctl(fd, PERF_EVENT_IOC_RESET, 0);
    ioctl(fd, PERF_EVENT_IOC_ENABLE, 0);

    // Код для профілювання
    for (int i = 0; i < 1000000; i++) { __asm__(""); }

    ioctl(fd, PERF_EVENT_IOC_DISABLE, 0);
    long long count;
    read(fd, &count, sizeof(long long));

    printf("Виконано інструкцій: %lld\n", count);
    close(fd);
    return 0;
}
```
== Rust
```rust
use libc::{ioctl, read, syscall, SYS_perf_event_open};
use std::mem;
use std::os::raw::c_long;

// Конфігураційні константи з linux/perf_event.h
const PERF_TYPE_HARDWARE: u32 = 0;
const PERF_COUNT_HW_INSTRUCTIONS: u64 = 1;
const PERF_EVENT_IOC_ENABLE: c_long = 0x2400;
const PERF_EVENT_IOC_DISABLE: c_long = 0x2401;
const PERF_EVENT_IOC_RESET: c_long = 0x2403;

#[repr(C)]
#[derive(Default)]
struct PerfEventAttr {
    type_: u32,
    size: u32,
    config: u64,
    flags: u64,
    // ... інші поля опущено для стислості (повна структура має бути ~120 байтів)
}

fn main() {
    // В реальному коді використовуйте крейт `perf-event` замість сирих викликів
    println!("Використання perf_event_open через FFI.");
}
```
:::

Підсистема `perf` — це не просто утиліта, а фундаментальний міст між поведінкою апаратури та розумінням ядра. Вона доводить принцип відсутності накладних витрат до межі, дозволяючи бачити продуктивність такою, якою вона є насправді.
