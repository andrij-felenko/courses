# Виявлення витоків пам'яті ядра (Kmemleak)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів, межа між режимами процесора та відмінності виділення пам'яті.
- [Псевдо-ФС: procfs, sysfs, debugfs](book:unix-linux/debugfs) — монтаж та взаємодія з віртуальними файловими системами ядра.
- [KASAN: Kernel Address Sanitizer](book:unix-linux/kasan-kernel-address-sanitizer) — динамічний аналіз помилок адресації та виходу за межі буферів у ядрі.
</preknowlist>

Коли програма у просторі користувача (user space) припускається помилки у керуванні динамічною пам'яттю і втрачає останній вказівник на виділений буфер, наслідки цієї втрати залишаються ізольованими у межах її власного віртуального адресного простору. Як тільки процес завершує своє виконання або примусово ліквідується операційною системою за допомогою сигналу `SIGKILL`, ядро Linux повністю знищує відповідну структуру таблиць сторінок (`struct mm_struct`) і гарантовано повертає абсолютно всі фізичні сторінки пам'яті у загальний пул вільної пам'яті.

У просторі ядра (kernel space) така захисна сітка відсутня за визначенням. Ядро Linux являє собою єдиний монолітний виконавець, який працює безперервно з моменту завершення початкової ініціалізації процесора при включенні живлення плати і до моменту повного знеструмлення або перезавантаження системи. Будь-який блок динамічної пам'яті, виділений функціями `kmalloc()`, `kmem_cache_alloc()`, `vmalloc()` або `alloc_pages()`, на який код ядра або драйвера пристрою втрачає посилання, залишається заблокованим у системній пам'яті назавжди.

Накопичення таких недосяжних блоків призводить до поступової фрагментації SLUB-кешів, виснаження доступного пулу фізичних сторінок та неминуче завершується аварійною зупинкою системи через спрацювання OOM Killer (Out-Of-Memory) чи критичну паніку ядра (`kernel panic`). Для вирішення цієї проблеми у ядро Linux інтегровано спеціалізований механізм динамічної діагностики — **Kmemleak** (Kernel Memory Leak Detector).

## 1. Архітектурний принцип: Консервативний Mark-and-Sweep

У високорівневих мовах програмування з автоматичним збиранням сміття (Garbage Collection) спеціалізований потік середовища виконання аналізує граф посилань і самостійно вивільняє недосяжну пам'ять. У ядрі операційної системи автоматична деалокація є принципово неприпустимою. Об'єкти у ядрі часто прив'язані до фізичного апаратного забезпечення, володіють зареєстрованими обробниками переривань (IRQ handlers), знаходяться у списку чекання таймерів чи утримують внутрішні блокування `spinlock`. Неконтрольований виклик `kfree()` для недосяжного об'єкта ядра призвів би до катастрофічного пошкодження стану системи (Use-After-Free).

З цієї причини Kmemleak запозичує з традиційних алгоритмів збирання сміття лише фазу виявлення досяжності об'єктів — алгоритм **Mark-and-Sweep (Познач і Змети)**, але повністю відмовляється від автоматичного вилучення пам'яті. 

Замість деалокації пам'яті Kmemleak працює як пасивний відстежувач:
1. Він будує граф посилань між усіма виділеними блоками пам'яті ядра.
2. Періодично виконує обхід графу, позначаючи недосяжні блоки як "білі" (потенційні витоки).
3. Формує текстовий звіт із фіксацією повного стеку викликів (stack backtrace) на момент створення витоку та надає його розробнику через віртуальну файлову систему `debugfs`.

Історичні передумови розробки Kmemleak, чому класичний консервативний збирач Бема-Вайзера не зміг працювати у kernel space безпосередньо та як Каталін Марінас реалізував пасивне сканування для ядра Linux, детально викладено у матеріалі [📜 Еволюція виявлення витоків пам'яті: від збирачів сміття до Kmemleak](book:unix-linux/kmemleak-leak-detector/hist-mark-and-sweep-in-kernel.md).

![Алгоритм Mark-and-Sweep у Kmemleak](/reference/unix-linux/observability/kmemleak-leak-detector/img/kmemleak-scan.svg)
*Алгоритм сканування пам'яті за графом вказівників у Kmemleak. Кореневі регіони містять посилання на досяжні об'єкти (сірі та чорні), тоді як блоки без вхідних посилань (білі) класифікуються як витоки.*

## 2. Відстеження алокацій та метадані (`struct kmemleak_object`)

Для того щоб знати про існування кожного блоку пам'яті у ядрі, Kmemleak інтегрується в усі підсистеми динамічного виділення пам'яті через спеціалізовані хуки (hooks). Детектор перехоплює виклики наступних алокаторів:
- **Slab-алокатори (SLUB / SLAB / SLOB):** функції `kmalloc()`, `kmem_cache_alloc()`, `kfree()`, `kmem_cache_free()`.
- **Алокатор віртуально-неперервної пам'яті:** функції `vmalloc()`, `vfree()`, `vmap()`, `vunmap()`.
- **Сторінковий алокатор (Page Allocator):** функції `alloc_pages()`, `free_pages()`.
- **Per-CPU алокатор:** функції `alloc_percpu()`, `free_percpu()`.
- **Ранній алокатор завантаження:** підсистема `memblock`.

При кожній алокації Kmemleak створює внутрішню структуру метаданих `struct kmemleak_object`. Вона описує межі блоку та стан його досяжності:

```c
struct kmemleak_object {
    raw_spinlock_t lock;
    unsigned int flags;        /* Прапорці стану: KMEMLEAK_GREY, KMEMLEAK_NO_SCAN */
    struct rb_node rb_node;    /* Вузол для включення у червоно-чорне дерево */
    unsigned long pointer;     /* Початкова віртуальна адреса виділеної пам'яті */
    size_t size;               /* Розмір виділеного блоку у байтах */
    int min_count;             /* Поріг досяжності (за замовчуванням 1) */
    int count;                 /* Поточний лічильник знайдених посилань */
    unsigned long trace[16];   /* Стек викликів на момент алокації */
};
```

### Пошукова індексна структура (`object_tree`)

У працюючому ядрі Linux кількість одночасно виділених об'єктів пам'яті може сягати кількох мільйонів. Під час сканування пам'яті Kmemleak мусить для кожного знайденого 64-бітного значення миттєво відповісти на питання: чи є це значення віртуальною адресою, яка потрапляє всередину будь-якого з відстежуваних блоків?

Для забезпечення високої швидкості пошуку всі структури `struct kmemleak_object` зберігаються у глобальному самобалансованому **червоно-чорному дереві (Red-Black Tree)** під назвою `object_tree`.

Пошук у `object_tree` здійснюється за адресою з часовою складністю `O(log n)`. Кожен вузол дерева індексується за діапазоном `[pointer, pointer + size]`. Це дозволяє сканеру визначати належність вказівника до об'єкта, навіть якщо вказівник вказує не на початок блоку, а зі зміщенням всередину структури.

## 3. Фази сканування та граф досяжності

Процес сканування пам'яті виконується фоновим потоком ядра `kmemleak-scan` періодично (за замовчуванням кожні 10 хвилин) або примусово за викликом користувача через `debugfs`.

Сканування є чотиристадійним алгоритмом обходу графу:

### 1. Ініціалізація (White Marking)
Сканер отримує глобальне блокування метаданих і скидає лічильник посилань `count` для всіх об'єктів у `object_tree` у значення `0`. Усі об'єкти позначаються як **"білі"** (недосяжні кандидатні витоки).

### 2. Сканування кореневих регіонів (Root Sets)
Kmemleak аналізує ділянки пам'яті ядра, які вважаються апріорі досяжними і з яких можуть починатися ланцюжки вказівників. До кореневих регіонів належать:
- **Сегменти `.data` та `.bss` ядра та завантажених модулів:** містять глобальні та статичні змінні мови C.
- **Стеки завдань (Task Stacks):** стеки всіх потоків ядра та системних викликів процесів (структури `struct thread_info` та `struct task_struct`).
- **Per-CPU пам'ять:** спеціалізовані регіони пам'яті, закріплені за кожним логічним ядром процесора.

Сканер обходить ці регіони як масив вирівняних машиних слів (64-бітних значень на x86_64). Кожне слово перевіряється через пошук у `object_tree`. Якщо слово чисельно потрапляє у діапазон адреси відомого об'єкта, лічильник `count` цього об'єкта збільшується. Об'єкти, які отримали `count >= min_count`, позначаються як **"сірі"** (досяжні, але вміст їхнього власного тіла ще не проскановано) та додаються до списку обходу.

### 3. Транзитивне замикання (Transitive Closure)
Kmemleak послідовно бере об'єкти зі списку "сірих" і сканує їхній власний вміст як масив потенційних вказівників. Якщо у тілі "сірого" об'єкта знайдено вказівник на інший "білий" об'єкт, останній збільшує свій `count`, стає "сірим" і додається до списку обходу. Після завершення сканування тіла об'єкт змінює свій колір на **"чорний"** (повністю досяжний і просканований).

### 4. Виявлення витоків (Sweeping phase)
Коли список "сірих" об'єктів стає порожнім, транзитивне замикання завершується. Усі об'єкти у `object_tree`, які залишилися у стані **"білий"** (на них не знайдено жодного посилання з коренів або інших чорних об'єктів), класифікуються як **витоки пам'яті**.

### Синхронізація та RCU
Щоб не заблокувати ядро під час тривалого сканування, Kmemleak застосовує механізм RCU (Read-Copy-Update) та спин-блокування `kmemleak_lock`. Потік сканування періодично робить паузи (`cond_resched()`), дозволяючи процесору обробляти переривання та інші плани виконання.

## 4. Конфігурація ядра та параметри завантаження

Оскільки Kmemleak створює відчутні накладні витрати пам'яті та процесорного часу, його компіляція керується опціями меню `make menuconfig` у розділі *Kernel Hacking -> Kernel Debugging*:

```kconfig
CONFIG_DEBUG_KERNEL=y
CONFIG_DEBUG_KMEMLEAK=y
CONFIG_DEBUG_KMEMLEAK_EARLY_LOG_SIZE=40000
CONFIG_DEBUG_KMEMLEAK_AUTO_SCAN=y
```

- **`CONFIG_DEBUG_KMEMLEAK_EARLY_LOG_SIZE`:** Розмір стаціонарного масиву для запису алокацій, які відбуваються на самому початку завантаження ядра (до того, як Kmemleak виділить власні динамічні структури). Якщо при старті виникає помилка *Kmemleak: Early log buffer exceeded*, це значення збільшують до `100000`.
- **`CONFIG_DEBUG_KMEMLEAK_DEFAULT_OFF`:** Якщо параметр активовано (`y`), ядро буде скомпільовано з Kmemleak, але сам детектор залишиться вимкненим до запуску з параметром командного рядка.

### Параметри командного рядка ядра (`cmdline`)

Поведінкою Kmemleak можна керувати безпосередньо при завантаженні ядра через параметр `kmemleak=`:
- `kmemleak=on` — примусово вмикає детектор.
- `kmemleak=off` — повністю вимикає Kmemleak. Усі хуки алокаторів перетворюються на порожні інструкції, а пам'ять метаданих звільняється.

## 5. Інтерфейс управління через Debugfs

Після завантаження системи взаємодія з Kmemleak здійснюється через віртуальний файл у `debugfs`:

```bash
/sys/kernel/debug/kmemleak
```

### Основні команди запису

Розробник відправляє команди у Kmemleak за допомогою звичайного запису рядків у файл:

```bash
# Примусово запустити синхронне сканування пам'яті
echo scan > /sys/kernel/debug/kmemleak

# Очистити список поточних знайдених витоків (скинути базлайн)
echo clear > /sys/kernel/debug/kmemleak

# Змінити інтервал фонового сканування на 300 секунд
echo scan=300 > /sys/kernel/debug/kmemleak

# Вимкнути фонове автоматичне сканування
echo scan=off > /sys/kernel/debug/kmemleak

# Повністю вимкнути Kmemleak у працюючій системі
echo off > /sys/kernel/debug/kmemleak
```

Повний довідник програмного C API (`<linux/kmemleak.h>`), внутрішніх прапорців об'єктів та всіх команд керування `debugfs` наведено у матеріалі [📋 Інтерфейс та API детектора Kmemleak](book:unix-linux/kmemleak-leak-detector/api-kmemleak-interface.md).

## 6. Аналіз звітів Kmemleak та декодування адрес

Читання звітів здійснюється стандартною командою читання з файлу `debugfs`:

```bash
cat /sys/kernel/debug/kmemleak
```

Якщо Kmemleak виявляє недосяжні об'єкти, він формує детальний текстовий блок:

```text
unreferenced object 0xffff8881023b6000 (size 1024):
  comm "modprobe", pid 1234, jiffies 4294967295 (age 123.456s)
  hex dump (first 32 bytes):
    00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  ................
    00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  ................
  backtrace:
    [<00000000b46327b8>] kmem_cache_alloc_trace+0x16b/0x2f0
    [<000000001c23a54b>] my_driver_init+0x34/0x100 [my_buggy_driver]
    [<00000000f40d6c54>] do_one_initcall+0x46/0x200
```

### Розшифровка полів звіту:
1. **`unreferenced object 0xffff8881023b6000 (size 1024)`:** Віртуальна адреса втраченого блоку та його розмір у байтах.
2. **`comm` та `pid`:** Назва процесу та його PID, який здійснив алокацію.
3. **`hex dump`:** Вміст перших 32 байтів блоку пам'яті (допомагає ідентифікувати дані за магічними числами або ASCII-рядками).
4. **`backtrace`:** Стек викликів моментів створення алокації. Зсув `my_driver_init+0x34` вказує на точне місце **виділення** пам'яті.

Покроковий практикум з написання тестових драйверів, автоматизації аудіювання та декодування адрес за допомогою утиліти `decode_stacktrace.sh` наведено у матеріалі [⚙️ Практикум: Автоматизований аудит та локалізація витоків пам'яті у драйверах](book:unix-linux/kmemleak-leak-detector/proj-kmemleak-driver-audit.md).

## 7. Проблема хибних спрацювань (False Positives & Negatives)

Оскільки Kmemleak інтерпретує пам'ять евристично, аналізуючи кожне слово як потенційний вказівник, він піддається двом типам помилок.

### 7.1. Хибні спрацювання (False Positives)
Ситуація, коли об'єкт насправді використовується кодом ядра, але Kmemleak вважає його витоком:
1. **Out-of-bounds вказівники:** Вказівник зберігається зі зміщенням, яке вказує за межі блоку пам'яті.
2. **Побітове пакування (Bitwise Tagging):** Розробники драйвера виконують побітові операції XOR або зберігають прапорці у нижніх бітах адреси.
3. **Спеціальні алокатори:** Пам'ять виділяється сторінками, але використовується власним внутрішнім пулом без інформування Kmemleak.

Для усунення хибних спрацювань у коді ядра застосовуються функції C API `kmemleak_not_leak()`, `kmemleak_ignore()` або `kmemleak_no_scan()`.

### 7.2. Пропущені витоки (False Negatives)
Ситуація, коли витік пам'яті дійсно стався, але Kmemleak його пропустив. Це виникає, коли випадкове ціле число у пам'яті (наприклад, лічильник пакета або залишок старого стеку) чисельно збігається з віртуальною адресою виділеного блоку. Сканер вважає цей блок досяжним і позначає його сірим. У 64-бітних системах ймовірність такого збігу є низькою через величезний адресний простір, але у 32-бітних архітектурах це є суттєвим обмеженням.

## 8. Продуктивність та порівняння з KASAN

Kmemleak створює високі накладні витрати на ресурси системи:

| Метрика | Вплив Kmemleak | Причина накладних витрат |
| :--- | :--- | :--- |
| **Обсяг RAM** | Зростання на 30–80% | Для кожного `kmalloc` створюється об'єкт `struct kmemleak_object` зі стеком викликів. |
| **Продуктивність CPU** | Падіння на 20–50% | Синхронізація `spinlock` при кожному виділенні та звільненні пам'яті у `object_tree`. |
| **Кеш CPU (L2/L3)** | Вимивання кешу | Повний обхід пам'яті під час сканування витісняє корисні дані процесів користувача з кеш-ліній. |

Через ці накладні витрати Kmemleak **категорично заборонено використовувати у робочих (production) системах**.

### Kmemleak проти KASAN

Kmemleak і KASAN (Kernel Address Sanitizer) доповнюють один одного у процесі тестування ядра:
- **KASAN** ([KASAN: Kernel Address Sanitizer](book:unix-linux/kasan-kernel-address-sanitizer)) перехоплює помилки **некоректного доступу** (Out-of-bounds, Use-After-Free) в момент виконання інструкції читання або запису.
- **Kmemleak** виявляє **пасивні витоки** — пам'ять, до якої більше немає посилань, але яка залишається виділеною.

Спільне використання KASAN та Kmemleak на автоматизованих стендах CI/CD забезпечує максимальне покриття аналізу пам'яті ядра Linux.
