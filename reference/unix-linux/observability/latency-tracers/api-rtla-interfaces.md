# 📋 Інтерфейси керування трасувальниками затримок: sysfs, ftrace та CLI-утиліта rtla

Цей довідник містить повну специфікацію файлових інтерфейсів `tracefs`, параметрів конфігурації ядра, структури подій кільцевого буфера ftrace та прапорців командного рядка користувацької утиліти `rtla` для вимірювання затримок `osnoise` і `timerlat`.

## 1. Структура файлової системи tracefs для osnoise

Трасувальник `osnoise` керується через спеціальні файли у віртуальній файловій системі `tracefs` (зазвичай змонтованій у `/sys/kernel/tracing/osnoise/`). Цей інтерфейс надає повний контроль над поведінкою вимірювальних потоків ядра, періодичністю вимірювань, порогами автоматичного зупинення трасування та логуванням додаткової налагоджувальної інформації.

Нижче наведено детальний опис усіх керуючих параметрів файлової системи з поясненням їхнього семантичного впливу на вимірювальну підсистему:

- **`cpus`** (тип `ASCII String`, значення за замовчуванням — усі доступні CPU).
  Задає маску або інтервальний список процесорних ядер (наприклад, `1-3,5`), на яких підсистема ядра створює та запускає тестові вимірювальні потоки. Запис порожнього значення або списку відновлює трасування на всіх активних ядрах. У високопродуктивних конфігураціях реального часу сюди записують суворо ізольовані ядра (що не обробляють загальні переривання системи), щоб оцінити чистий рівень апаратного та системного шуму.

- **`period_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `1000000` мкс / 1 секунда).
  Визначає загальну тривалість одного вимірювального циклу `osnoise`. Інтервальне вікно повторюється циклічно протягом усього часу роботи трасувальника. Зміна цього параметра дозволяє налаштувати частоту агрегації статистичних даних та виводу звітних подій у буфер ftrace.

- **`runtime_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `1000000` мкс / 1 секунда).
  Визначає активну частину вимірювального періоду (`period_us`), протягом якої тестовий потік ядра крутиться у безперервному нескінченному циклі читання лічильника TSC з відключеним витісненням (`preempt_disable()`). Якщо значення `runtime_us` менше за `period_us`, потік після завершення `runtime_us` добровільно засинає на решту часу періоду, віддаючи процесор для виконання інших системних завдань. Це дозволяє здійснювати моніторинг шуму без 100% завантаження CPU.

- **`stop_tracing_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `0`, вимкнено).
  Критично важливий параметр для автоматичної фіксації та збереження траси затримок. Задає поріг затримки на одному процесорному ядрі. Якщо тривалість окремого епізоду шуму (наприклад, обробка довгого IRQ чи апаратний SMI) перевищує вказане значення у мікросекундах, трасувальник `osnoise` негайно надсилає сигнал зупинки у підсистему ftrace (`tracing_off()`). Це дозволяє "заморозити" кільцевий буфер ftrace точно у момент виникнення затримки й зберегти повний стек викликів функцій ядра для подальшого аналізу.

- **`stop_tracing_total_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `0`, вимкнено).
  Задає поріг сумарного (агрегованого) шуму на всіх вимірювальних ядрах за один період `period_us`. Якщо сума всіх епізодів затримки на виділених ядрах перевищує цей поріг, підсистема ftrace зупиняє трасування. Параметр використовується для виявлення каскадних затримок, коли шум виникає одночасно на кількох ядрах під час системних збоїв чи високого навантаження на шину пам'яті.

- **`tracing_thresh`** (тип `Integer`, мікросекунди, значення за замовчуванням — `0`).
  Посилається на глобальний поріг фільтрації подій ftrace (`/sys/kernel/tracing/tracing_thresh`). Події із тривалістю затримки, меншою за вказане значення, ігноруються й не записуються у кільцевий буфер `trace_pipe`, що дозволяє фільтрувати дрібне незначне тремтіння й економити пропускну здатність буфера.

- **`print_stack`** (тип `Integer`, значення `0` або `1`, за замовчуванням — `0`).
  При записі `1` у цей файл підсистема `osnoise` автоматично робить знімок ядерного стеку викликів (`kernel stack trace`) кожного разу, коли виявлений шум перевищує поріг `stop_tracing_us`. У трасу додається повний стек із назвами функцій ядра, що дозволяє точно ідентифікувати конкретну функцію чи обробник, який заблокував виконання.

Для активації трасувальника необхідно записати ім'я `osnoise` у файл `current_tracer`:

```bash
echo osnoise > /sys/kernel/tracing/current_tracer
```

## 2. Структура файлової системи tracefs для timerlat

Трасувальник затримок періодичних таймерів `timerlat` використовує каталог конфігурації `/sys/kernel/tracing/timerlat/`. На відміну від `osnoise`, цей трасувальник зосереджений на вимірюванні точного часу реагування періодичного таймера високої роздільної здатності (hrtimer) та швидкості пробудження відповідного потоку реального часу.

Нижче наведено повну специфікацію керуючих параметрів:

- **`cpus`** (тип `ASCII String`, значення за замовчуванням — усі доступні CPU).
  Визначає список процесорних ядер, на яких створюються періодичні таймери `hrtimer` та відповідні вимірювальні потоки. Записом у цей файл регулюється зоноване вимірювання затримок на ізольованих ядрах або загальних ядрах системи.

- **`period_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `1000` мкс / 1 мілісекунда).
  Визначає період спрацьовування таймера `hrtimer`. За замовчуванням таймер спрацьовує з частотою 1000 Гц (щосекунди здійснюється 1000 вимірювань затримки на кожному ядрі). Зменшення періоду (наприклад, до `100` мкс) підвищує роздільну здатність моніторингу затримок, але збільшує процесорне навантаження на систему.

- **`stop_tracing_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `0`, вимкнено).
  Задає критичний поріг затримки таймера (сумарної або окремо IRQ/Thread). При перевищенні цього значення трасування у ftrace негайно зупиняється. Це ключовий параметр для виявлення рідкісних аномальних затримок пробудження (outliers): як тільки затримка таймера перевищує, наприклад, 15 мкс, кільцевий буфер заморожується, зберігаючи контекст подій, що передували аномалії.

- **`stop_tracing_total_us`** (тип `Integer`, мікросекунди, значення за замовчуванням — `0`, вимкнено).
  Поріг сумарної затримки таймера по всіх ядрах за один інтервал спостереження. Використовується для фіксації глобальних системних затримок, що впливають на всі процесори одночасно (наприклад, тривалі затримки шини PCI Express або паузи у роботі контролера пам'яті).

- **`print_stack`** (тип `Integer`, значення від `0` до `N`, за замовчуванням — `0`).
  Вказує кількість кадрів ядерного стеку викликів, які будуть збережені в трасу ftrace при виникненні затримки таймера, більшої за `stop_tracing_us`. На відміну від `osnoise`, тут можна задавати глибину стеку (наприклад, `10`), щоб обмежити розмір траси лише найважливішими функціями ядра.

Активація трасувальника здійснюється командою:

```bash
echo timerlat > /sys/kernel/tracing/current_tracer
```

## 3. Формат подій tracepoint у кільцевому буфері (trace_pipe)

Трасувальники `osnoise` та `timerlat` інтегровані з підсистемою ftrace tracepoints і виводять структуровані текстові події у файл `/sys/kernel/tracing/trace_pipe`. Кожен рядок містить точний часовий штамп, номер процесора, ідентифікатор події та набір специфічних метрик.

### 3.1 Подія osnoise:sample_threshold

Ця подія ґенерується трасувальником `osnoise` кожного разу, коли виявлений шум перевищує заданий поріг фільтрації або при закінченні чергового періоду вимірювання.

Формат текстового рядка у `trace_pipe`:

```text
osnoise/sample_threshold: sample_threshold: CPU 1 start 1234567890 duration 12.350 us interference 15.100 us hw: 1 NMI: 0 IRQ: 2 SoftIRQ: 1 Thread: 0
```

Детальний розбір усіх полів події:

1. `CPU 1`: Номер процесорного ядра, на якому зафіксовано епізод шуму.
2. `start 1234567890`: Часова мітка початку вимірювального вікна у наносекундах від моменту завантаження системи.
3. `duration 12.350 us`: Фактичний корисний час, протягом якого вимірювальний потік крутився в циклі читання TSC без переривань.
4. `interference 15.100 us`: Сумарна тривалість усіх перешкод (шуму), які "вкрали" процесорний час у потоку за вказаний період.
5. `hw: 1`: Кількість апаратних подій, які не супроводжувалися реєстрацією ядерних обробників IRQ або NMI (найчастіше це свідчить про викрадення часу мікропрограмою BIOS/UEFI під час обробки System Management Interrupts — SMI).
6. `NMI: 0`: Кількість обробників немаскованих переривань (Non-Maskable Interrupts), які виконувалися під час вимірювального вікна (наприклад, таймер NMI watchdog або події профілювальника perf).
7. `IRQ: 2`: Кількість апаратних переривань від пристроїв (мережевих адаптерів, накопичувачів, таймерів), які перервали вимірювальний потік.
8. `SoftIRQ: 1`: Кількість програмних переривань (SoftIRQ), що виконувалися у контексті відкладеної обробки після апаратних переривань або у фоновому потоці `ksoftirqd`.
9. `Thread: 0`: Кількість сторонніх потоків ядра або звичайних процесів користувача, на які був витіснений вимірювальний потік через відсутність повної ізоляції ядра.

### 3.2 Подія timerlat:timerlat_sample

Ця подія ґенерується трасувальником `timerlat` при кожному спрацьовуванні періодичного таймера.

Формат текстового рядка у `trace_pipe`:

```text
timerlat:timerlat_sample: seq: 1042 context: thread irq_latency: 2.150 us thread_latency: 5.420 us total_latency: 7.570 us
```

Детальний розбір полів події:

1. `seq: 1042`: Монотонно зростаючий порядковий номер вимірювального сніпету на даному CPU.
2. `context: thread`: Контекст вимірювання. Може набувати значень `irq` (вимірювання виконано безпосередньо в обробнику апаратного переривання hrtimer) або `thread` (вимірювання виконано у контексті вимірювального потоку реального часу).
3. `irq_latency: 2.150 us`: Затримка обробника переривання. Це час між запланованим часом спрацьовування таймера (`T_target`) та моментом, коли процесор фактично увійшов у першу інструкцію обробника IRQ. Залежить від того, чи були в системі вимкнені переривання (`local_irq_disable()`), чи виконувалися NMI/SMI.
4. `thread_latency: 5.420 us`: Затримка потоку. Це час від моменту, коли обробник IRQ розблокував вимірювальний потік, до моменту, коли цей потік почав фізично виконуватися на CPU. На цю затримку впливає черга планувальника завдань (`scheduler`), пріоритети інших процесів та стан витіснення (`preemption`).
5. `total_latency: 7.570 us`: Загальна затримка реагування системи, яка обчислюється як пряма сума `irq_latency + thread_latency`.

## 4. Консольна утиліта rtla (Real-Time Linux Analysis)

Утиліта `rtla` (Real-Time Linux Analysis) надає високорівневий інтерфейс командного рядка для автоматизації роботи з `osnoise` та `timerlat`. Вона позбавляє потреби вручну маніпулювати файлами `tracefs` та парсити сирий текстовий трейс.

Утиліта підтримує три основні команди: `rtla osnoise`, `rtla timerlat` та `rtla hnoise`.

### 4.1 Команда rtla osnoise

Синтаксис виклику:

```bash
rtla osnoise [top|hist] [опції]
```

Підкоманда `top` відображає таблицю зведеної статистики у реальному часі (з оновленням щосекунди), а підкоманда `hist` будує гістограму розподілу затримок за інтервалами.

Детальний довідник прапорців запуску `rtla osnoise`:

- **`-c`, `--cpus CPU_LIST`**
  Задає список або діапазон процесорних ядер для вимірювання (наприклад, `-c 1-3` або `-c 0,2,4`). Утиліта автоматично конфігурує файл `osnoise/cpus` у `tracefs`.

- **`-d`, `--duration TIME[s|m|h]`**
  Задає загальну тривалість вимірювального експерименту. Наприклад, `-d 30s` виконує трасування протягом 30 секунд, після чого утиліта зупиняє трасувальник, збирає підсумкову статистику й завершує роботу.

- **`-p`, `--period US`**
  Задає період вимірювального циклу `period_us` у мікросекундах.

- **`-r`, `--runtime US`**
  Задає час активного виконання циклу `runtime_us` у мікросекундах.

- **`-S`, `--stop US`**
  Встановлює поріг автоматичного зупинення трасування `stop_tracing_us`. Якщо зафіксований шум перевищує `US` мікросекунд, утиліта заморожує трасування і виводить детальну трасу ftrace.

- **`-T`, `--threshold US`**
  Встановлює мінімальний поріг шуму `tracing_thresh` у мікросекундах. Значення, менші за `US`, не враховуються у підсумкових гістограмах.

- **`-P`, `--priority PRIO`**
  Задає політику та пріоритет планувальника для тестових потоків `osnoise`. Формат: `POLICY:PRIORITY`, де `POLICY` — це `f` (SCHED_FIFO), `r` (SCHED_RR), `b` (SCHED_BATCH) або `d` (SCHED_DEADLINE). Наприклад, `-P f:95` запустить потоки з пріоритетом SCHED_FIFO 95.

- **`--user-threads`**
  Замість заповнення ядра потоками `kthread`, утиліта створює вимірювальні потоки у просторі користувача. Це дозволяє оцінити вплив системних викликів та переключень контексту між ядром і юзерспейсом.

Приклад запуску режиму табличного моніторингу на ядрах 1-3 протягом 10 секунд:

```bash
rtla osnoise top -c 1-3 -d 10s -P f:95
```

Приклад побудови гістограми затримок шуму з зупинкою при перевищенні 20 мікросекунд:

```bash
rtla osnoise hist -c 1-3 -d 1m -S 20 -T 1
```

### 4.2 Команда rtla timerlat

Синтаксис виклику:

```bash
rtla timerlat [top|hist] [опції]
```

Призначена для вимірювання затримок періодичних таймерів реального часу.

Специфічні прапорці команди `rtla timerlat`:

- **`-u`, `--user-threads`**
  Створює періодичний тестовий потік у просторі користувача, який засинає через системний виклик `clock_nanosleep()` і вимірює повну затримку пробудження на рівні юзерспейсу. Якщо прапорець не вказано, вимірювання проводиться у ядрі.

- **`-U`, `--user-load`**
  Автоматично запускає фонове стрес-навантаження у просторі користувача на виділених ядрах для перевірки стійкості затримок під навантаженням.

- **`-s`, `--stack INT`**
  Вмикає збереження ядерного стеку викликів завглибшки `INT` кадрів при виникненні затримки таймера, більшої за заданий поріг `-S`.

- **`--trace [FILE]`**
  При виникненні аномальної затримки автоматично зберігає весь сирий вміст буфера ftrace у вказаний файл для подальшого аналізу через `trace-cmd` або `kernelshark`.

- **`-AA`, `--auto-analysis US`**
  Вмикає модуль автоматичного аналізу затримок (Auto-Analysis). Якщо затримка таймера перевищує `US` мікросекунд, `rtla` детально аналізує трасу і видає зрозумілий текстовий висновок із зазначенням конкретної причини затримки (наприклад: "IRQ від мережевої карти eth0 заблокував ядро на 18.2 мкс").

Приклад побудови гістограми затримок з вимірюванням у просторі користувача:

```bash
rtla timerlat hist -c 2 -u -d 30s -P f:98 -AA 10
```

### 4.3 Команда rtla hnoise

Спеціалізований модуль утиліти `rtla`, призначений для ізольованого виявлення апаратного шуму (Hardware Noise), такого як System Management Interrupts (SMI) чи немасковані переривання (NMI), без запуску інтенсивних обчислювальних потоків.

```bash
rtla hnoise top -c 1-3 -d 20s -S 10
```

Ця команда дозволяє системному адміністратору швидко перевірити, чи є апаратна платформа (материнська плата, BIOS/UEFI) придатною для використання у системах жорсткого реального часу, ще до розгортання прикладного програмного забезпечення.

## 5. Параметри ядра (Kernel Command-Line Parameters) для ізоляції затримок

Щоб вимірювання затримок за допомогою `osnoise`, `timerlat` та `rtla` відображали чисту картину без спотворень, зумовлених фоновими завданнями операційної системи, ядро Linux необхідно правильно зконфігурувати при завантаженні через параметри командного рядка (у конфігурації GRUB або systemd-boot).

Нижче наведено детальний опис ключових параметрів ізоляції ядра:

- **`isolcpus=nohz,domain,1-7`**
  Повністю виключає вказані процесорні ядра (у даному прикладі ядра 1-7) із загальносистемного планувальника задач. Параметр `nohz` вимикає регулярні тики системного таймера на цих ядрах, якщо на них виконується лише один потік. Параметр `domain` вилучає ядра з балансування навантаження, унеможливлюючи автоматичне перенесення звичайних процесів на ізольовані ядра.

- **`nohz_full=1-7`**
  Переводить вказані ядра у режим безперервного безтикового виконання (tickless mode / Full Dynticks). Якщо на ізольованому ядрі виконується один потік реального часу, ядро повністю вимикає періодичні переривання системного таймера (`scheduler tick`), прибираючи одне з головних джерел OS Noise.

- **`rcu_nocbs=1-7`**
  Перенаправляє виконання зворотних викликів підсистеми Read-Copy Update (RCU callbacks) з вказаних ізольованих ядер на спеціальні фонові потоки ядра (`rcuog`), прив'язані до неізольованих ядер (наприклад, CPU 0). Це усуває затримки, пов'язані із викликом RCU-обробників під час звільнення пам'яті в ядрі.

- **`skew_tick=1`**
  Зсуває у часі моменти спрацьовування системних таймерів між різними процесорними ядрами. Запобігає ситуації, коли переривання таймера спрацьовують одночасно на всіх ядрах, що створює пікові сплески навантаження на шину пам'яті та міжпроцесорні з'єднання (QPI/UPI).

- **`processor.max_cstate=1`**
  Обмежує максимальний рівень енергозбереження процесора станом C1. Запобігає переходу ядер у глибокі стани сну (C2, C3, C6, C7), вихід з яких вимагає від десятків до сотень мікросекунд і є одним із найпоширеніших джерел гігантських затримок (latency spikes) при спрацьовуванні таймерів.

- **`intel_idle.max_cstate=0`**
  Повністю вимикає спеціалізований драйвер енергозбереження Intel idle, змушуючи ядро використовувати стандартний обробник `acpi_idle` або утримувати процесор у постійній готовності C0. Забезпечує максимальну детермінованість часу відгуку ціною підвищеного енергоспоживання.

- **`mce=off`**
  Вимикає періодичний опитувальний таймер підсистеми Machine Check Exception (MCE), який за замовчуванням кожні кілька секунд генерує переривання для перевірки апаратних регістрів помилок процесора та пам'яті.
