# 🧮 Скільки коштує більший шматок

Ця вставка пояснює 🧮 скільки коштує більший шматок та дозволяє зрозуміти її детальніше. Розмір одиниці стиснення тягнуть у різні боки дві криві — щільність образу й надлишкове читання, — і майже все у виборі між ними вирішує те, що перша логарифмічна, а друга лінійна. Порахуймо обидві до чисел.

## Модель: скільки важить стиснений шматок

Стискач родини [LZ77](book:algorithms/lz77) описує дані токенами «відступи назад на стільки-то, візьми стільки-то», і кожен токен посилається кудись у вже розтиснений словник. Якщо словник обмежений шматком у B байтів, поле відступу мусить адресувати B позицій, тобто коштує близько log₂B бітів.

А скільки байтів такий токен накриває? Стільки, скільки завдовжки знайдений збіг. Його довжину можна оцінити з першого принципу. Хай джерело має [ентропійну швидкість](book:algorithms/entropy) h бітів на байт — тобто правдоподібних рядків завдовжки L існує приблизно 2^(hL). У словнику лежить B позицій, з яких збіг може початися. Збіг завдовжки L там знайдеться доти, доки позицій вистачає накрити всі варіанти, тобто доки B ≳ 2^(hL):

```
L ≈ log₂B / h
```

Саме на цій оцінці Аарон Вайнер і Яаков Зів 1994 року побудували доведення, що LZ77 з достатньо великим вікном виходить на ентропію джерела.

Тепер поділімо ціну токена на його покриття:

```
бітів на байт ≈ (log₂B + λ)/L = h·(log₂B + λ)/log₂B = h·(1 + λ/log₂B)
```

де λ — решта токена в бітах: код довжини, прапорець «літерал чи збіг», недобір ентропійного кодера.

Тут і схована вся пласкість. Подвоєння B додає до log₂B **одиницю**, а не множник, тож надлишок над ентропією спадає як 1/log₂B — повільніше за будь-який степінь.

До цього додається другий внесок, зовсім іншої природи. Кожен шматок стартує з порожнім словником: перші сотні байтів нема на що вказувати, вони йдуть літералами, а зверху лягає заголовок контейнера з таблицями кодів. Це стала величина c байтів на шматок, байдужа до B, — але на байт даних вона важить c/B.

Разом:

```
r(B) = h₈ + m/log₂B + c/B        байтів образу на байт даних
коефіцієнт = 1/r(B)              h₈ = h/8,  m = h₈·λ
```

Три невідомі — три рівняння. Візьмімо три виміряні точки:

```
r(2¹⁴) = 1/2.6 = 0.38462
r(2¹⁷) = 1/3.0 = 0.33333
r(2²⁰) = 1/3.2 = 0.31250
      ↓
h₈ = 0.2125     m = 1.990     c = 491 байт
```

Модель варта довіри не тому, що проходить через власні три точки — це вміє будь-яка трипараметрична крива, — а тому, що її коефіцієнти означають саме те, чим мають бути. h₈ = 0.2125 байта на байт — це 1.70 біта на байт, правдоподібна ентропійна швидкість дерева з бінарників, текстів і конфігів. Звідси середня довжина збігу при B = 128 КіБ: L ≈ 17/1.70 = 10.0 байта — рівно той порядок, який дають реальні стискачі. А λ = m/h₈ ≈ 9.4 біта на токен теж на місці: код довжини у deflate важить сім-дев'ять бітів. Три параметри підганялися під розміри образів, а вийшли з них довжина збігу й ціна токена.

Ось що модель каже про всю шкалу:

```
B          коеф.    надлишок на випадкове читання 4 КіБ
4 КіБ      2.01×    ×1
16 КіБ     2.60×    ×4
64 КіБ     2.90×    ×16
128 КіБ    3.00×    ×32
1 МіБ      3.20×    ×256
16 МіБ     3.38×    ×4096
```

## Очікуваний надлишок: точна формула

Тепер друга крива. Читання S байтів із відступу X зачіпає шматки з номерами від ⌊X/B⌋ до ⌊(X+S−1)/B⌋, тобто

```
N = ⌊(X + S − 1)/B⌋ − ⌊X/B⌋ + 1
```

а розтиснути доведеться B·N байтів. Ядро працює сторінками, тож і X, і S кратні P = 4 КіБ. Перейдімо до сторінок: b = B/P — шматок, s = S/P — читання, j = (X/P) mod b — з якої сторінки всередині шматка читання починається.

```
N(j) = ⌊(j + s − 1)/b⌋ + 1
```

Усереднимо по j. Коли j пробігає повну систему лишків 0…b−1, вираз m = j+s−1 пробігає b **послідовних** цілих. А серед будь-яких b послідовних цілих дробові частки {m/b} набувають кожного зі значень 0, 1/b, …, (b−1)/b рівно по разу. Тому

```
Σ ⌊m/b⌋ = Σ m/b − Σ {m/b} = [(s−1) + (b−1)/2] − (b−1)/2 = s − 1
E[N]    = 1 + (s − 1)/b
```

Показово, що (b−1)/2 скоротилося начисто: від розміру шматка лишилося одне ділення й жодного залишкового члена. У байтах це читається так:

```
E[розтиснених байтів] = B·E[N] = B + S − P
A(S) = (B + S − P)/S = 1 + (B − P)/S
```

Уся арифметика надлишку — в цих двох рядках, і надбавка B − P **не залежить від S**. Зайвої роботи рівно один шматок мінус сторінка на кожне читання, скільки б те читання не просило.

![Смуга з п'яти однакових шматків і три положення того самого читання: одне цілком усередині шматка, одне на межі двох, одне рівно від початку шматка](/reference/unix-linux/files/read-only-image-filesystems/img/read-window-chunks.svg)

*Читання, коротше за шматок, зачіпає один шматок або два — а в середньому забирає рівно на один шматок більше, ніж просило.*

Три випадки читаються прямо з формули:

- **Одна сторінка навмання** (S = P): A = B/P. При 128 КіБ це рівно ×32.
- **Читання завдовжки в цілий шматок** (S = B): A = 2 − P/B ≈ 2. Навіть ідеально «одношматкове» читання в середньому зачіпає майже два, бо межі не збігаються.
- **Послідовний прохід** файлу на F байтів: A = 1 + (B−P)/F → 1. Кожен шматок тут розтискається один раз і обслуговує всі читання, що в нього влучать, а [випереджувальне читання](book:unix-linux/readahead) підвозить наступний заздалегідь.

Формула припускає, що відступи рівномірні за модулем B. Але сама межа тримається без жодних припущень: N ніколи не перевищує ⌈S/B⌉ + 1, тож розтиснених байтів завжди менше за S + B. Розподіл відступів вирішує лише те, де саме в проміжку [S, S+B) осяде середнє.

## Чому одна крива пласка, а друга пряма

Порівняймо тепер, що дає **одне подвоєння** B. Позначимо x = log₂B.

Видаток росте як A = 2^(x−12) — рівно вдвічі, на кожному кроці, без згасання.

Виграш дає похідна щільності

```
−dr/dx = m/x² + c·ln2·2⁻ˣ
```

а поділивши її на саму r, дістаємо відсоток від розміру образу за одне подвоєння:

```
x = 14 (16 КіБ):   8.0 %     словник 2.6 %   вступний внесок 5.4 %
x = 17 (128 КіБ):  2.8 %     словник 2.1 %   вступний внесок 0.8 %
x = 20 (1 МіБ):    1.7 %     словник 1.6 %   вступний внесок 0.1 %
```

Розклад на стовпчики показує, що «пласка крива» — насправді дві різні криві, які міняються місцями. Доданок словника спадає як 1/x², тобто вкрай повільно. Доданок вступного внеску спадає як 2⁻ˣ, тобто вдвічі на кожне подвоєння — точно в такт із тим, як росте видаток. Рівні вони там, де

```
c·ln2/2ˣ = m/x²    →    B ≈ 39 КіБ
```

Нижче цієї межі за дрібний шматок платять повну ціну, і платять не за короткий словник, а за те, що заголовок і холодний старт не встигли розмазатися по даних. Вище лишається сам словник, і кожне наступне подвоєння купує ті самі два відсотки за ту саму двійку. Замовчування `mksquashfs` у 128 КіБ стоїть якраз за перегином: щільність уже майже вибрана, а надлишок ще вимірюється десятками, не сотнями.

![Дві криві від розміру шматка на логарифмічній осі: надлишкове читання росте прямою від ×1 до ×256, а розмір образу спадає майже горизонтальною лінією від ×1 до ×0.63](/reference/unix-linux/files/read-only-image-filesystems/img/size-vs-cost-curves.svg)

*Обидві криві нормовані на варіант із 4 КіБ, вісь ординат логарифмічна: за вісім подвоєнь надлишок виріс у 256 разів, а образ схуд на 37 відсотків.*

Криві не перетинаються, і внутрішнього оптимуму в задачі немає — його й не існує доти, доки ви самі не призначите курс обміну між байтом образу й мілісекундою затримки.

## Що міняється, коли прибити вихід

EROFS фіксує не вхід, а вихід: одиниця стиснення важить рівно P = 4 КіБ. Тоді розмір входу вже не вибирають — він розв'язує неявне рівняння

```
B·r(B) = P
```

Для нашої моделі корінь такий:

```
B* ≈ 9.7 КіБ      r(B*) ≈ 0.412      коефіцієнт 2.43×
```

Отже «кластер на чотири кілобайти» насправді бачить близько десяти кілобайтів даних. Словник менший, ніж у SquashFS зі 128 КіБ, але не в тридцять два рази, а приблизно в тринадцять.

І тут проступає тотожність, заради якої варто було рахувати. Надлишок розтискання — це B*/P байтів на одну сторінку. Але B* = P/r(B*), тому

```
A = B*/P = 1/r(B*) = коефіцієнт стиснення
```

Надлишок конструкції з фіксованим виходом **дорівнює її ж коефіцієнтові стиснення** — тотожно, за побудовою, і без жодного параметра, який можна було б підкрутити. Він самообмежений: чим краще стискаються дані, тим більше їх розгортається на кожну сторінку, але рівно настільки ж меншає й образ.

Порівняйте з фіксованим входом, де A = B/P не залежить від даних узагалі: 128 КіБ дають ×32 і на тексті, і на вже стисненому jpeg, з якого не вичавилося нічого.

## Індекс: третя крива

Лишилося порахувати те, про що згадують останнім, — таблицю, за якою шматок узагалі знаходять.

**Фіксований вхід.** Довжини різні, тож позицію k-го шматка наперед не обчислити. SquashFS тримає в inode список довжин: 32 біти на шматок, з них молодші 24 — довжина, а біт 24 означає «цей ліг нестисненим». На байт даних це

```
4/B = 4/131072 ≈ 0.0031 %        файл 1 ГіБ → 32 КіБ списку
```

Мізер. Але ціна цього списку не в байтах: це список **довжин**, а не адрес, і відступ k-го шматка — сума перших k. Дістатися середини великого файлу означає підсумувати пів списку, тобто прочитати його весь. Пошук коштує O(k) і дорожчає разом із файлом.

**Фіксований вихід.** Довжина тут відома завжди — вона стала. Зате зникає зворотне знання: скільки вхідних байтів улізло в кожен кластер, наперед не скажеш, і відповідність «логічний кластер → фізичний блок» доводиться зберігати поштучно на кожні 4 КіБ логічного простору. Повний запис EROFS — 8 байтів:

```
8/4096 ≈ 0.195 %                 файл 1 ГіБ → 2 МіБ індексу
```

Це в **шістдесят чотири рази** більше, ніж у SquashFS зі 128-кілобайтним шматком. Ось справжня ціна фіксованого виходу: не гірший коефіцієнт, а розпухлий індекс — і саме тому з повними записами EROFS лишитися не могла.

Рятує те саме, що створило проблему. Коли вихід сталий, сусідні кластери лягають у сусідні блоки, відповідність стає майже арифметичною, а майже арифметична послідовність стискається до кількох бітів на член. EROFS так і робить: пакує підряд кілька кластерів, кладе на весь пакет одну абсолютну адресу блока, а на кожен кластер лишає тип і зсув. Виходить амортизовано чотири байти на кластер або два:

```
compacted 4B:  4/4096 ≈ 0.098 %   1 ГіБ → 1 МіБ      у 32 рази більше за SquashFS
compacted 2B:  2/4096 ≈ 0.049 %   1 ГіБ → 512 КіБ    у 16 разів
```

Пакети при цьому вирівнюють по 8 і 32 байти відповідно, щоб жоден не перетинав межі сторінки.

І головне, чого список довжин дати не може: такий індекс адресується прямо. Пакети однакові й вирівняні, тож номер потрібного запису переводиться в позицію арифметично — O(1) замість O(k). Шістнадцятикратно більший індекс купує сталий час пошуку, і на дереві з мільйоном дрібних файлів це саме той обмін, що окупається.

Три криві залежать від одного числа, і показники в них різні: щільність поліпшується як 1/log₂B, індекс дешевшає як 1/B, надлишок росте як B. Лінійний серед трьох лише останній — тому щойно читання перестають бути послідовними, вирішує саме він.
