Блокове шифрування на рівні блокового пристрою (таке як LUKS чи `dm-crypt`) працює нижче шару файлової системи: воно перетворює весь фізичний диск або розділ на монолітний зашифрований масив секторів. Для операційної системи це забезпечує повну прозорість, проте платою за це є жорстка негнучкість. Підсистема шифрування блокового рівня не уявляє внутрішньої структури файлової системи, не знає про існування окремих каталогів чи томів, не здатна розрізнити вільний дисковий простір від зайнятого й не може застосовувати різні політики безпеки до різних даних. Як наслідок, шифрувати окремий каталог або датасет із власним паролем доводиться шляхом створення вкладених файлових образів чи складних схем монтування. Крім того, під час реплікування даних через мережу систему змушують або розшифровувати блоки перед відправкою, або передавати увесь сирий том посекторно разом із незайнятими блоками.

З іншого боку, шифрування на рівні VFS (таке як `fscrypt` у файлових системах ext4 чи f2fs) працює на рівні окремих файлів та каталогів, але позбавлене цілісного криптографічного захисту метаданих і не захищає від пошкодження дискових секторів на рівні виділення тома.

Традиційна дедуплікація даних ставить протилежне завдання: знайти в сховищі однаковий за змістом вміст і зберегти його в єдиному фізичному блоці на диску, замінивши дублікати посиланнями. Однак суворі криптографічні вимоги до шифрування вимагають, щоб повторювані відкриті блоки (наприклад, нульові блоки бази даних або стандартні заголовки системних файлів) кожного разу перетворювалися на абсолютно унікальний, нерозрізнюваний від білого шуму шифротекст. Якщо використати класичні схеми блокового шифрування з унікальними векторами ініціалізації (IV) або різними ключами для кожного датасету, дві точні копії одного й того самого файла на диску будуть виглядати як два абсолютно різні набори випадкових байтів, що унеможливлює їх виявлення алгоритмами дедуплікації.

Файлова система ZFS розв'язує цю суперечність шляхом перенесення криптографічних операцій та алгоритмів дедуплікації безпосередньо у внутрішні шари власної об'єктної архітектури — **DMU** (англ. *Data Management Unit*) та **SPA** (англ. *Storage Pool Allocator*). Замість накладання шифрування зверху або знизу файлової системи, ZFS робить кожен блоковий вказівник (*Block Pointer*) носієм власного автентифікаційного тегу, а ключі шифрування прив'язує до дерев метаданих датасетів. Це дозволяє поєднати безпечне ізольоване шифрування окремих томів, прозору передачу зашифрованих потоків на віддалені бекап-сервери без розкриття ключів та дедуплікацію дубльованих блоків у межах спільного криптографічного кореня.

## Ієрархія ключів та криптографічні механізми (AES-GCM)

Криптографічна архітектура ZFS базується на розділенні ключів на два рівні: **Майстер-ключі датасету** (англ. *Master Key*) та **Ключі обгортання** (англ. *Wrapping Key*). Така двошарова схема відокремлює фізичне шифрування блоків даних від способу аутентифікації користувача (парольної фрази чи бінарного файла ключа).

![Ієрархія коренів шифрування та успадкування ключів у ZFS](/reference/unix-linux/files/zfs-native-encryption/img/zfs-encryption-tree.svg)

*Кореневий пул може містити як незашифровані датасети, так і незалежні корені шифрування (Encryption Root). Дочірні датасети за замовчуванням успадковують Майстер-ключ від батьківського кореня, але можуть створювати власний криптографічний корінь із новим ключем.*

Під час створення зашифрованого датасету (наприклад, `zfs create -o encryption=on pool/data`) ядро ZFS генерує за допомогою криптографічно стійкого генератора псевдовипадкових чисел (CSPRNG) 256-бітний симетричний **Майстер-ключ** (Master Key). Саме цим ключем шифруються всі блоки даних і метаданих, що належать цьому датасету та його дочірнім об'єктам.

Майстер-ключ ніколи не зберігається на диску у відкритому вигляді. Замість цього система запитує у користувача парольну фразу або зчитує 256-бітний файл ключа, з якого формується **Wrapping Key**:
1. Якщо обрано авторизацію за парольною фразою (`keyformat=passphrase`), ядро застосовує алгоритм виведення ключа **PBKDF2** (англ. *Password-Based Key Derivation Function 2*) з використанням HMAC-SHA256, 350 000 ітерацій (за замовчуванням) та унікальної для кожного датасету криптографічної солі (*salt*).
2. Якщо обрано сирий ключ (`keyformat=raw` або `hex`), поданий 256-бітний масив байтів використовується безпосередньо як Wrapping Key.

Далі Майстер-ключ шифрується за допомогою Wrapping Key за стандартом **AES Key Wrap** (RFC 3394) або алгоритмом **AES-256-GCM**. Отриманий зашифрований блок (англ. *Wrapped Key*) разом із сіллю PBKDF2 та криптографічним тегом автентифікації зберігається у внутрішніх метаданих датасету — об'єкті DSL (англ. *Dataset and Snapshot Layer*), структурі `dsl_crypto_key_phys_t`.

```
[ Парольна фраза користувача ] + [ Криптографічна сіль (Salt 64-bit) ]
                │
                ▼ (PBKDF2 HMAC-SHA256, 350k+ ітерацій)
        [ Wrapping Key (256-bit) ]
                │
                ▼ (AES Key Wrap RFC 3394 / AES-256-GCM)
   Зашифрований Master Key  ──► Збережено у DSL об'єкті метаданих
```

Ця двошарова архітектура дає важливу практичну перевагу: операція зміни пароля або файла ключа (команда `zfs change-key`) виконується миттєво і не вимагає перешифрування терабайтів даних на диску. Змінюється лише Wrapping Key, яким заново перегортається той самий 256-бітний Майстер-ключ у метаданих DSL.

Датасет, на якому було вперше ініціалізовано Майстер-ключ, називається **коренем шифрування** (англ. *Encryption Root*). Усі дочірні датасети та файлові знімки (snapshots), створені всередині цього кореня, за замовчуванням успадковують цей самий Майстер-ключ і входять до єдиного криптографічного дерева. Проте ZFS дозволяє розірвати успадкування: при створенні дочірнього датасету можна вказати прапор `-o encryption=on`, що згенерує новий Encryption Root зі власним незалежним Майстер-ключем.

Докладну довідку щодо параметрів CLI, форматів ключів та команд моніторингу стану шифрування наведено в матеріалі [Параметри, CLI-інтерфейс та керування зашифрованими датасетами ZFS](book:unix-linux/zfs-native-encryption/api-zfs-crypto-cli.md).

> 🔧 **Навіщо це.** Двохрівневе шифрування ZFS вирішує проблему безпечного вимкнення серверів у дата-центрах. При перезавантаженні системи або її вимкненні Майстер-ключі витираються з оперативної пам'яті (операція `zfs unload-key`). Навіть якщо зловмисник отримає фізичний доступ до вилучених NVMe-дисків чи серверної стійки, зчитати дані буде неможливо без введення парольної фрази, оскільки самі Майстер-ключі замкнені всередині метаданих за допомогою PBKDF2 та AES Key Wrap.

## Анатомія зашифрованого блоку у шарах SPA та DMU

У ZFS шифрування працює на рівні окремих блоків даних (від 4 КБ до 16 МіБ). Коли транзакційна група (TXG) скидає накопичені в пам'яті блоки на диск, шар SPA (Storage Pool Allocator) обробляє кожен блок через конвеєр перетворень: стискання (LZ4, ZSTD), шифрування та обчислення контрольних сум.

Основним криптографічним режимом у ZFS є **AES-256-GCM** (англ. *Galois/Counter Mode*), також підтримується **AES-128-GCM** та **AES-256-CCM**. Обраний режим AES-GCM є алгоритмом автентифікованого шифрування з приєднаними даними (AEAD — *Authenticated Encryption with Associated Data*). Це означає, що алгоритм не лише забезпечує конфіденційність (шифрує відкритий текст у шифротекст), але й одночасно обчислює 128-бітний автентифікаційний тег MAC (англ. *Message Authentication Code*), який гарантує цілісність даних і захист від навмисного підроблення чи пошкодження секторів.

Усі метадані адресації блоків у ZFS зберігаються у структурі **Block Pointer** (`struct blockptr_t` розміром 128 байтів). Анатомія блокового вказівника при увімкненому шифруванні трансформується таким чином:

```
+-----------------------------------------------------------------------+
|                       struct blockptr_t (128 bytes)                   |
+-----------------------------------------------------------------------+
| DVA[0] (Data Virtual Address 1: vdev, offset, size)                   |
| DVA[1] (Data Virtual Address 2: mirror/RAID-Z copy)                   |
| DVA[2] (Data Virtual Address 3: spare copy)                           |
+-----------------------------------------------------------------------+
| Props: Comp=LZ4, Crypt=AES-256-GCM, Endian=LE, Type=DATA, Lsize/Psize |
+-----------------------------------------------------------------------+
| Logical Byte Offset (LOFFSET)  | Birth Transaction Group (TXG)        |
+-----------------------------------------------------------------------+
| Cryptographic IV / Nonce (96 bits) & Encryption Salt/Tag Metadata     |
+-----------------------------------------------------------------------+
| Checksum / MAC Tag Field (128 bits):                                  |
| [ MAC Tag (128 bit) замінює звичайну контрольну суму Fletcher4/SHA256] |
+-----------------------------------------------------------------------+
```

Для роботи режиму AES-GCM потрібен унікальний ініціалізаційний вектор **IV (Nonce)** розміром 96 біт. Повторне використання одного й того самого IV із тим самим ключем шифрування в режимі GCM є фатальним дефектом безпеки, що дозволяє зловмиснику відновити відкритий текст. Щоб уникнути збереження мільйонів додаткових IV на диску, ZFS конструює 96-бітний IV детерміновано з внутрішніх атрибутів блоку:
- 64 біти — номер об'єкта dnode (`object number`), якому належить цей блок;
- 32 біти — логічний зсув блоку всередині файла (`logical byte offset`), поділений на розмір блоку.

Оскільки кожен об'єкт у ZFS має унікальний ID, а блоки всередині об'єкта впорядковані за зсувом, отримана комбінація гарантує абсолютну унікальність IV для кожного блоку в межах одного датасету.

Окрім перевірки цілісності вмісту блоку, AES-GCM у ZFS захищає від атак класу **Block Swapping** (підміна одного зашифрованого блоку іншим валідним зашифрованим блоком із цього ж або сусіднього файла). Для цього в розрахунок автентифікаційного тегу MAC як приєднані дані (AAD — *Additional Authenticated Data*) включаються:
- GUID пулу ZFS;
- Номер об'єкта dnode та логічний зсув блоку;
- Генераційна транзакційна група (Birth TXG).

Якщо зловмисник або скомпрометований фізичний накопичувач скопіює зашифрований блок з однієї позиції диска в іншу, розрахований при читанні тег MAC не збігається з тегом у `blockptr_t`, і ядро миттєво відхилить пошкоджений блок.

Під час зчитування блоку з диска ядро виконує зворотний процес:
1. З розшифрованого в пам'яті дерева метаданих DSL дістається 256-бітний `Master Key`.
2. Зі структури `blockptr_t` зчитуються DVA-адреси, розмір, прапори алгоритму та 128-бітний автентифікаційний тег MAC.
3. З атрибутів `blockptr_t` реконструюється 96-бітний IV.
4. Апаратні інструкції процесора (AES-NI) виконують розшифрування блоку та одночасну перевірку MAC-тегу.

Якщо MAC-тег у `blockptr_t` не збігається з обчисленим під час розшифрування тегом, ZFS фіксує криптографічну помилку цілісності (`EIO` або `ECKSUM`). У цей момент спрацьовує механізм самовідновлення ZFS: система звертається до дзеркальної копії диска (другого DVA у `blockptr_t`) або обчислює пошкоджений блок за допомогою парності RAID-Z, виправляє збійний блок на першому диску й повертає процесу коректні дані.

Взаємодія зашифрованого датасету з журналом синхронного запису ZIL (ZFS Intent Log) підпорядкована тим же правилам: записи журналу (ZIL intent log records) шифруються Майстер-ключем датасету перед записом на фізичний носій SLOG. Це забезпечує повний захист цілісності синхронних операцій `fsync()`.

В оперативній пам'яті кеш **ARC** (Adaptive Replacement Cache) зберігає зашифровані блоки у розшифрованому вигляді після першої успішної перевірки MAC-тегу. Це виключає потребу повторно виконувати обчислення AES-NI при частих операціях читання гарячих даних користувача.

## Прозоре сире реплікування (Raw Send / Receive)

Традиційні файлові системи для передачі бекапів вимагають розмонтування тома чи створення знімка з подальшим зчитуванням відкритих файлів користувацьким процесом (`rsync`, `tar`), що вимагає наявності ключів розшифрування на відправнику та відкриває дані в пам'яті. 

Вбудоване шифрування ZFS змінює цей процес завдяки механізму **Raw Send / Receive** (команда `zfs send -w` або `zfs send --raw`).

```
[ Джерело: Local Zpool ]                          [ Приймач: Remote Backup Server ]
(Ключ завантажено в RAM)                           (КЛЮЧІ ВІДСУТНІ / UNTRUSTED)
        │                                                     │
        ▼                                                     ▼
zfs send -w pool/data@snap                            zfs receive backup/data
        │                                                     │
        ├─────────► [ Потік зашифрованих блоків ] ────────────┤
        │           (AES-GCM шифротекст + MAC)                │
        │           (Ключі НЕ передаються через мережу)       │
        ▼                                                     ▼
Зашифровані блоки зчитуються                         Зашифровані блоки записуються
з диска без розшифрування                            на диск у сирому вигляді
```

Під час виконання `zfs send -w` шар DMU не звертається до Майстер-ключа і не виконує розшифрування даних у пам'яті ядра. ZFS зчитує блоки з диска в їхньому **сирому зашифрованому вигляді** — саме так, як вони були записані в структуру `blockptr_t` (включно зі збереженими MAC-тегами та IV).

Цей потік даних спрямовується через мережу (наприклад, через SSH-тунель або навіть незахищений канал) на віддалений сервер резервного копіювання. На приймаючому сервері команда `zfs receive` створює зашифрований датасет і записує отримані блоки безпосередньо у власний Zpool. 

Ключова перевага полягає в тому, що на приймаючому сервері **взагалі не потрібно мати Майстер-ключ або парольну фразу**. Віддалений сервер зберігає точну зашифровану копію датасету й усіх його знімків, не маючи жодної фізичної можливості зчитати вміст файлів. Навіть якщо резервний сервер буде повністю скомпрометовано або викрадено, зловмисники отримають лише зашифровані блоки із захистом AES-256-GCM.

При цьому віддалений сервер зберігає можливість виконувати всі службові операції ZFS: перевірку цілісності секторів (`zfs scrub`), створення додаткових локальних знімків, видалення старих снапшотів та моніторинг використання дискового простору.

## Механізм та архітектура дедуплікації (DDT)

На відміну від шифрування, яке захищає дані від сторонніх очей, **дедуплікація** (англ. *Deduplication*) покликана оптимізувати використання дискового простору шляхом усунення однакових блоків даних у режимі реального часу (In-band Deduplication).

Коли на датасеті активовано дедуплікацію (`zfs set dedup=on pool/data`), шар SPA змінює алгоритм обробки кожного блоку, що готується до запису:
1. Замість звичайного швидкого хешу (LZ4 або Fletcher4) для блоку обчислюється криптографічно стійкий 256-бітний або 512-бітний контрольний хеш (за замовчуванням **SHA-256**, або **SKEIN** / **SHA-512**).
2. ZFS звертається до глобальної індексної структури пулу — **Таблиці дедуплікації DDT** (англ. *Deduplication Table*).
3. Якщо обчислений хеш блоку відсутній у DDT, створюється новий запис із цим хешем, лічильником посилань `RefCount = 1` та фізичною адресою DVA на диску. Блок записується на носій.
4. Якщо хеш блоку вже існує в DDT, фізичний запис нових даних на диск скасовується. ZFS лише збільшує лічильник `RefCount` у таблиці DDT та конструює новий `Block Pointer`, який вказує на вже існуючу фізичну адресу DVA.

![Структура таблиці дедуплікації (DDT) та адресація у ZFS](/reference/unix-linux/files/zfs-native-encryption/img/zfs-ddt-structure.svg)

*Таблиця дедуплікації (DDT) зберігає зв'язок між 256-бітним хешем блоку, лічильником посилань (RefCount) та фізичними координатами на диску (DVA). Два різних файли можуть посилатися на один фізичний блок.*

Один запис у таблиці DDT являє собою структуру даних, яка описує зв'язок між криптографічним хешем та фізичним блоком:

```
+-----------------------------------------------------------------------+
|                    DDT Entry Structure (~320 bytes)                   |
+-----------------------------------------------------------------------+
| Block Checksum (SHA-256 / SHA-512 / SKEIN digest: 256..512 bits)      |
+-----------------------------------------------------------------------+
| Reference Count (RefCount: 32-bit uint) -> Кількість посилань         |
+-----------------------------------------------------------------------+
| Physical DVA (Data Virtual Addresses: 1..3 physical disk locations)   |
+-----------------------------------------------------------------------+
| Physical Size (Psize)  | Logical Size (Lsize) | Compression Type      |
+-----------------------------------------------------------------------+
```

Для швидкого пошуку дублікатів під час запису таблиця DDT повинна повністю розміщуватися в оперативній пам'яті (у кеші ARC).

## Криптографічний конфлікт: шифрування проти дедуплікації

Сумісне використання вбудованого шифрування та дедуплікації в ZFS стикається з базовим математичним конфліктом криптографії та пошуку дублікатів.

Автентифіковане шифрування AES-256-GCM гарантує, що навіть однакові вхідні блоки даних у результаті шифрування дають абсолютно різний шифротекст, якщо вони шифруються:
- з використанням різних Майстер-ключів (у двох різних коренях шифрування Encryption Root);
- з використанням різних ініціалізаційних векторів IV (наприклад, для двох різних об'єктів або різного зсуву всередині файла).

Якщо б ZFS виконувала дедуплікацію *після* шифрування на рівні SPA, хеші SHA-256 від зашифрованих блоків ніколи б не збіглися, і коефіцієнт дедуплікації дорівнював би 1.0x (нульова ефективність).

Для вирішення цієї проблеми ZFS виконує дедуплікацію **до шифрування, але всередині межі безпеки одного кореня шифрування**:

```
[ Відкритий блок даних ] ──► Обчислення SHA-256 від відкритих даних
                                         │
                                         ▼
                             Пошук у DDT (Encryption Root)
                                   ┌─────┴─────┐
                             Знайдено        Не знайдено
                                  │               │
                                  ▼               ▼
                       Збільшення RefCount   Шифрування AES-256-GCM
                       у вже існуючому DVA   і фізичний запис на диск
```

Це накладає жорстке обмеження: **дедуплікація в ZFS можлива лише в межах одного кореня шифрування (Encryption Root)**. Якщо два датасети рознесені по різних коренях шифрування (мають різні Майстер-ключі), ZFS принципово не здатна дедуплікувати блоки між ними, оскільки для цього довелося б або зберігати відкриті хеші даних у незахищеному загальному індексі, або розшифровувати блоки іншого датасету.

Окрім криптографічних обмежень, дедуплікація ZFS несе колосальне навантаження на оперативну пам'ять (RAM):
- Кожен запис у таблиці DDT займає приблизно 320 байтів оперативної пам'яті (з урахуванням службових обгородок структури AVL-дерева або B-дерева в ARC).
- При стандартному розмірі блоку 128 КБ для збереження 1 ТБ унікальних даних потрібно `1 TiB / 128 KiB = 8 388 608` блоків.
- Таблиця DDT для 1 ТБ унікальних даних вимагатиме: `8 388 608 × 320 байт ≈ 2.68 ГБ RAM`.
- Для сховища обсягом 100 ТБ розмір DDT в ARC перевищить **268 ГБ оперативної пам'яті** лише під індекс дедуплікації!

Якщо обсяг RAM на сервері недостатній для утримання всієї DDT, ZFS змушена витісняти частини таблиці на диск. При кожній операції запису нового блоку ядро має зчитати відповідний блок DDT з диска, перевірити хеш і записати оновлений `RefCount` назад. Це викликає так званий **DDT Thrashing**: швидкість запису на пул падає від сотень мегабайтів на секунду до кількох кілобайтів, роблячи файлову систему практично непридатною для використання.

## Порівняльний аналіз архітектур шифрування

Порівняння трьох підходів до шифрування дискових даних у системах Linux наведено в таблиці:

| Критерій | LUKS / dm-crypt | fscrypt (ext4/f2fs) | ZFS Native Encryption |
| :--- | :--- | :--- | :--- |
| **Рівень реалізації** | Блоковий пристрій | Вздовж шару VFS | Об'єктний шар DMU/SPA |
| **Захист метаданих** | Повний (всередині тома) | Частковий (лише ім'я) | Повний у межах датасету |
| **Ключі за датасетами** | Ні (один на весь том) | Так (каталоги) | Так (дерева датасетів) |
| **Реплікація без ключів** | Ні (посекторний том) | Ні | Так (`zfs send -w`) |
| **Захист від підміни блоків** | Ні | Ні | Так (MAC у Block Pointer) |
| **Підтримка дедуплікації** | Ні | Ні | Так (у межах EncRoot) |

> 🔧 **Навіщо це.** У реальному системному адмініструванні ввімкнення `dedup=on` без попереднього розрахунку RAM є однією з найпоширеніших причин катастрофічної втрати продуктивності пулів ZFS. У 95% практичних завдань замість дедуплікації доцільно використовувати легке алгоритмічне стискання **LZ4** або **ZSTD** (`zfs set compress=zstd pool/data`). Воно не потребує оперативної пам'яті під індекси, працює зі швидкістю кількох гігабайтів на секунду за рахунок векторних інструкцій CPU і зменшує обсяг даних на 30–60% без ризику падіння пулу. Для випадків, де дедуплікація дійсно необхідна, сучасні версії OpenZFS дозволяють виділяти спеціалізовані VDEV диски класу `dedup` або `special` на базі надшвидких NVMe SSD, що запобігає падінню I/O при витісненні DDT із оперативної пам'яті.

Практичні методи програмного керування зашифрованими датасетами, завантаження ключів та перевірки стану через C та C++ API детально розібрано в матеріалі [Програмне керування ключами та перевірка стану шифрування ZFS мовами C та C++](book:unix-linux/zfs-native-encryption/proj-zfs-key-manager.md).
