# ⚙️ Файловий замок у робочому коді: один лічильник, три замки, п'ять пасток

Далі — програма мовою C, яку можна зібрати й запустити просто зараз: вісім процесів одночасно збільшують число у спільному файлі й дописують рядок у спільний журнал, не загубивши жодної події. Уся робота із замком у ній зведена до двох функцій, тому та сама програма збирається з `flock`, з POSIX-замком записів і з замком на опис відкритого файлу — заміною одного файлу на двадцять рядків. Це й дає змогу побачити різницю між трьома механізмами не на словах, а на бігу. Наприкінці — захист служби від другого запуску, п'ять пасток, кожна з демонстрацією, що її показує, і скрипт, який доводить: без замка результат справді неправильний.

## Що вважати правильним результатом

Перш ніж писати рядок коду, треба вміти відрізнити правильний результат від правдоподібного — інакше програма «працює», доки хтось не подивиться уважно.

Домовмося так: `P` процесів по `N` разів кожен збільшують лічильник на одиницю. Правильна робота означає три речі одразу. **У файлі лічильника наприкінці стоїть рівно `P × N`** — жодного загубленого й жодного зайвого приросту. **У журналі рівно `P × N` рядків**, і кожен цілий, без перемішаних половинок. **Числа в журналі — це вся послідовність від 1 до `P × N` без повторів і без дірок**: якщо два процеси записали в журнал те саме число, значить, обидва бачили однаковий старий стан, і один приріст зник.

Третя умова найцінніша, бо ловить те, чого не ловлять перші дві. Файл із правильним підсумком і журнал із повторами означають, що програма помиляється в обидва боки й просто вдало обнулила помилки.

## Кістяк, спільний для всіх трьох версій

Почнемо з того, що не залежить від виду замка. Два дрібні помічники — і в кожному захована пастка, на яку регулярно наступають.

```c
/* counter.c — кілька процесів безпечно збільшують лічильник у файлі. */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* Реалізацію цих двох функцій дає окремий файл — саме нею
   й різняться три версії програми.                                 */
int lock_take(int fd);
int lock_drop(int fd);

/* pread має право повернути МЕНШЕ, ніж просили, і має право
   повернутися ні з чим, бо його перервав сигнал. Ні те, ні те
   не є помилкою — тому одного виклику ніколи не досить.            */
static ssize_t pread_all(int fd, void *buf, size_t len, off_t off)
{
    size_t got = 0;
    while (got < len) {
        ssize_t n = pread(fd, (char *) buf + got, len - got,
                          off + (off_t) got);
        if (n < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (n == 0) break;             /* кінець файлу: він просто коротший */
        got += (size_t) n;
    }
    return (ssize_t) got;
}

static int pwrite_all(int fd, const void *buf, size_t len, off_t off)
{
    size_t done = 0;
    while (done < len) {
        ssize_t n = pwrite(fd, (const char *) buf + done, len - done,
                           off + (off_t) done);
        if (n < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (n == 0) { errno = EIO; return -1; }
        done += (size_t) n;
    }
    return 0;
}

static int write_all(int fd, const void *buf, size_t len)
{
    size_t done = 0;
    while (done < len) {
        ssize_t n = write(fd, (const char *) buf + done, len - done);
        if (n < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        done += (size_t) n;
    }
    return 0;
}
```

Читаємо й пишемо навмисне через `pread`/`pwrite`, а не через `lseek` плюс `read`. Причин дві. По-перше, `lseek` і `read` — це два виклики, а `pread` один: зайвого проміжку між ними просто не існує. По-друге, звичайні `read` і `write` рухають поточну позицію, яка лежить не в дескрипторі, а в [описі відкритого файлу](book:unix-linux/open-file-description) — а його дитина після `fork` ділить із батьком. Дві гілки, що «кожна собі» читають з початку файлу, насправді штовхають одну спільну позицію й отримують шматки впереміш. `pread` бере зміщення аргументом і спільної позиції не чіпає взагалі.

Тепер серце програми — одна безпечна одиниця роботи.

```c
/* Прочитати число, збільшити, записати назад і лишити слід
   у журналі. Усе між lock_take і lock_drop — критична ділянка.     */
static int bump_once(int fd, int logfd)
{
    char buf[32], line[64];
    unsigned long long value = 0;
    ssize_t got;
    char *end;
    int n, m, saved;

    if (lock_take(fd) != 0) return -1;

    got = pread_all(fd, buf, sizeof buf - 1, 0);
    if (got < 0) goto fail;
    buf[got] = '\0';

    if (got > 0) {                     /* порожній файл — це чесний нуль */
        errno = 0;
        value = strtoull(buf, &end, 10);
        if (errno != 0 || end == buf) { errno = EINVAL; goto fail; }
    }

    value += 1;
    n = snprintf(buf, sizeof buf, "%llu\n", value);
    if (pwrite_all(fd, buf, (size_t) n, 0) != 0) goto fail;

    /* Число могло вкоротшати (1000 → 999), і без обрізання від
       старого запису лишився б хвіст: «9990».                       */
    if (ftruncate(fd, n) != 0) goto fail;

    m = snprintf(line, sizeof line, "pid %ld -> %llu\n",
                 (long) getpid(), value);
    if (write_all(logfd, line, (size_t) m) != 0) goto fail;

    return lock_drop(fd);

fail:
    saved = errno;                     /* lock_drop має право зіпсувати errno */
    lock_drop(fd);
    errno = saved;
    return -1;
}

int main(int argc, char **argv)
{
    long times, i;
    int fd, logfd;

    if (argc != 4) {
        fprintf(stderr, "вжиток: %s <файл-лічильника> <журнал> <разів>\n",
                argv[0]);
        return 2;
    }
    times = strtol(argv[3], NULL, 10);

    /* Файл відкриваємо ОДИН раз — поза циклом і поза замком.
       Відкриття не є частиною критичної ділянки, а от дескриптор
       мусить бути тим самим від початку до кінця роботи.            */
    fd = open(argv[1], O_RDWR | O_CREAT | O_CLOEXEC, 0644);
    if (fd < 0) { perror("open counter"); return 1; }

    logfd = open(argv[2], O_WRONLY | O_CREAT | O_APPEND | O_CLOEXEC, 0644);
    if (logfd < 0) { perror("open log"); return 1; }

    for (i = 0; i < times; i++)
        if (bump_once(fd, logfd) != 0) { perror("bump"); return 1; }

    close(logfd);
    close(fd);
    return 0;
}
```

Три рішення в цьому коді варті пояснення, бо кожне зроблено проти першого пориву.

**Журнал відкрито з `O_APPEND` і пишеться звичайним `write`.** З цим прапорцем ядро саме визначає кінець файлу й пише під внутрішнім замком inode, тож рядки різних процесів не перемішуються навіть без жодного нашого замка. Тобто журнал захисту не потребує — але ми все одно пишемо його під замком, бо потрібне інше: щоб число в журналі збігалося з числом, яке цієї миті лежить у файлі. Замок тут захищає не запис, а **відповідність двох файлів одне одному**.

**`pwrite` до журналу не годиться.** На Linux запис у дескриптор, відкритий з `O_APPEND`, іде в кінець файлу незалежно від зміщення, переданого в `pwrite`; POSIX вимагає протилежного. Змішувати два прапорці, поведінка яких різниться між системами, — зайвий спосіб нажити помилку, що не відтворюється.

**Номер помилки забирається в локальну змінну першої ж миті.** На шляху виходу ми викликаємо `lock_drop`, той успішно спрацьовує й ставить свій `errno` — і викликач отримує номер, який уже нічого не означає. Це найчастіша помилка в коді з прибиранням за собою.

Довговічності тут навмисне немає: після `pwrite` дані лежать у сторінковому кеші, і раптове зникнення живлення їх забере. Якщо лічильник має пережити й це, перед `lock_drop` треба поставити `fsync(fd)` — і заплатити за кожен приріст обертом диска ([довговічність запису](book:unix-linux/page-cache-durability)). Замок і довговічність — дві незалежні властивості, і плутати їх не варто: замок не рятує від відмови живлення, `fsync` не рятує від перегонів.

## Три замки, дві функції

Тепер те, чим версії різняться. Кожен файл нижче — повна реалізація обох функцій.

```c
/* lock-flock.c — замок на весь файл; власник — опис відкритого файлу. */
#include <errno.h>
#include <sys/file.h>

int lock_take(int fd)
{
    while (flock(fd, LOCK_EX) != 0)
        if (errno != EINTR) return -1;
    return 0;
}

int lock_drop(int fd) { return flock(fd, LOCK_UN); }
```

```c
/* lock-posix.c — POSIX-замок записів; власник — процес плюс файл. */
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>

static int lock_op(int fd, short type, int cmd)
{
    struct flock fl = { .l_type   = type,
                        .l_whence = SEEK_SET,
                        .l_start  = 0,
                        .l_len    = 0 };   /* 0 — до кінця файлу,
                                              хоч би куди той доріс */
    while (fcntl(fd, cmd, &fl) != 0) {
        if (errno != EINTR) return -1;     /* EDEADLK приходить сюди ж —
                                              і повторювати його не можна */
    }
    return 0;
}

int lock_take(int fd) { return lock_op(fd, F_WRLCK, F_SETLKW); }
int lock_drop(int fd) { return lock_op(fd, F_UNLCK, F_SETLK); }
```

```c
/* lock-ofd.c — замок на опис відкритого файлу.
   _GNU_SOURCE обов'язковий: без нього F_OFD_SETLKW не оголошено.    */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>

static int lock_op(int fd, short type, int cmd)
{
    struct flock fl = { .l_type   = type,
                        .l_whence = SEEK_SET,
                        .l_start  = 0,
                        .l_len    = 0,
                        .l_pid    = 0 };   /* саме нуль у l_pid і каже ядру,
                                              що заявка на OFD-замок */
    while (fcntl(fd, cmd, &fl) != 0) {
        if (errno != EINTR) return -1;
    }
    return 0;
}

int lock_take(int fd) { return lock_op(fd, F_WRLCK, F_OFD_SETLKW); }
int lock_drop(int fd) { return lock_op(fd, F_UNLCK, F_OFD_SETLK); }
```

Плюс четвертий файл для порівняння — той самий інтерфейс, що не робить нічого:

```c
/* lock-none.c — навмисно зламана версія, потрібна для перевірки. */
int lock_take(int fd) { (void) fd; return 0; }
int lock_drop(int fd) { (void) fd; return 0; }
```

Збирається все чотирма рядками:

```sh
cc -O2 -Wall -Wextra -o counter-flock counter.c lock-flock.c
cc -O2 -Wall -Wextra -o counter-posix counter.c lock-posix.c
cc -O2 -Wall -Wextra -o counter-ofd   counter.c lock-ofd.c
cc -O2 -Wall -Wextra -o counter-none  counter.c lock-none.c
```

Ключа `-D_GNU_SOURCE` у цих рядках навмисне немає: файли, яким макрос потрібен, оголошують його самі, а визначений двічі — з командного рядка й у тексті — він дав би лише попередження про перевизначення.

Цикл `while (… != 0) if (errno != EINTR) return -1;` стоїть у всіх трьох не для краси. Очікування на замок може перервати сигнал, і виклик поверне `EINTR` — не «не вийшло», а «мене збудили». Ядро вміє перезапускати такі виклики саме, якщо обробник сигналу встановлено з прапорцем `SA_RESTART`; але прапорець ставить не ваша функція, а той, хто встановлював обробник, і в бібліотечному коді ви про його вибір не знаєте ([EINTR і перезапуск](book:unix-linux/eintr-and-restart)). Цикл коштує рядок і працює в обох випадках.

Зверніть увагу й на те, чого в цих файлах немає: перевірки «а чи вільно», окремого таймаута, лічильника спроб. Заявка на замок — це вже вся операція цілком.

## Що змінюється, коли підмінити рівно ці двадцять рядків

Решта програми — байт у байт та сама. Ось усе, що при цьому міняється в поведінці.

**Робітники, народжені `fork` після `open`, перестають виключати одне одного** — у версіях `flock` і OFD. Обидві прив'язують замок до опису відкритого файлу, а дитина ділить із батьком **той самий** опис; для ядра це один власник. Батько тримає виключний замок, дитина просить його ж — і дістає негайно, бо він у неї вже є. Ніякого взаємного виключення. Версія `posix` тут, навпаки, працює: власник — процес, а процеси різні.

```c
/* ✗ так робити не можна з flock і з OFD-замками */
fd = open(path, O_RDWR);
for (i = 0; i < 8; i++)
    if (fork() == 0) { work(fd); _exit(0); }   /* один опис на всіх */

/* ✓ кожен робітник відкриває файл сам — і має власний опис */
for (i = 0; i < 8; i++)
    if (fork() == 0) { fd = open(path, O_RDWR); work(fd); _exit(0); }
```

> 🔧 **Навіщо це.** Помилка з лівого стовпця не падає й не гальмує — вона мовчки прискорює програму, бо очікування на замок зникає разом із самим виключенням. Пул робітників починає працювати рівно так, як версія `counter-none`: швидко й неправильно. Тому в коді, що народжує процеси, порядок `open` і `fork` — не стилістика, а частина логіки замка; правило коротке — **спершу розмножитися, потім відкривати**.

**Потоки не виключаються ніколи** — у версії `posix`. Власник там процес, а всі потоки процесу для замка — одна особа: другий потік просто перевизначить замок першого й піде працювати. З OFD-замками багатопотокова робота можлива, якщо кожен потік робить власний `open`.

**Замок може мовчки зникнути** — знову у версії `posix`. Досить будь-де в програмі відкрити цей самий файл і закрити, і ядро зніме **всі** ваші замки на нього. Демонстрація — нижче.

**Можна замкнути не весь файл, а лише байти лічильника** — у версіях `posix` і `ofd`: замінити `l_len = 0` на `l_len = 32`. Для нашої задачі це нічого не дає, а для файлу бази з тисячами записів — усе. `flock` такого не вміє в принципі.

**Ядро попереджає про взаємне блокування** — лише у версії `posix`. Побудуйте цикл очікування (перший тримає файл A й чекає на B, другий — навпаки), і `F_SETLKW` поверне `EDEADLK` замість того, щоб зависнути назавжди. `F_OFD_SETLKW` у поточній реалізації зависне мовчки: пошуку взаємного блокування для OFD-замків немає. Правда, і в POSIX-версії це рятівна сітка, а не гарантія — глибина пошуку обмежена.

**На NFS `flock` перестає бути `flock`.** З Linux 2.6.12 клієнт емулює його POSIX-замком на весь файл. Локально ці два види між собою не взаємодіють зовсім, а на NFS — взаємодіють, бо вони там одне й те саме ([мережеві файлові системи](book:unix-linux/network-filesystems)).

## Служба, яку не можна запустити двічі

Друга класична задача розв'язується тим самим `flock`, але зовсім інакше: замок береться один раз і не знімається ніколи.

```c
/* Повертає дескриптор, який треба тримати відкритим до самої смерті:
   саме він і є заявою «примірник працює».
   Помилка EWOULDBLOCK означає «вже працює», решта — справжні збої.  */
static int claim_single_instance(const char *path)
{
    int fd, n, saved;
    char line[32];

    fd = open(path, O_RDWR | O_CREAT, 0644);   /* без O_CLOEXEC — див. нижче */
    if (fd < 0) return -1;

    if (flock(fd, LOCK_EX | LOCK_NB) != 0) {
        saved = errno;
        close(fd);
        errno = saved;
        return -1;
    }

    /* Номер процесу пишемо ПІСЛЯ взяття замка й винятково для людини:
       правду про зайнятість каже замок, а не вміст файлу.            */
    if (ftruncate(fd, 0) != 0) goto fail;
    n = snprintf(line, sizeof line, "%ld\n", (long) getpid());
    if (write_all(fd, line, (size_t) n) != 0) goto fail;

    return fd;
fail:
    saved = errno;
    close(fd);
    errno = saved;
    return -1;
}
```

Знімати замок наприкінці не треба й не можна забути: ядро зніме його само, коли закриється останній дескриптор на цей опис, а при смерті процесу — хоч би від `SIGKILL`, хоч би від зникнення живлення — воно закриває дескриптори саме. Застарілого стану, який довелося б розбирати наступного запуску, тут не виникає в принципі ([демонізація](book:unix-linux/daemonize)).

Два місця, де ця схема все-таки ламається, варті окремої уваги.

**Дескриптор і `exec`.** `O_CLOEXEC` тут навмисне не поставлено: якщо служба вміє оновлюватися перезапуском самої себе через `exec`, замок мусить пережити цей перезапуск, інакше в проміжку між зняттям і взяттям устигне влізти другий примірник. Ціна цього рішення — будь-яка запущена вами програма успадкує дескриптор і триматиме замок, доки жива; забутий у довгому нащадку дескриптор означає, що замок переживе вашу смерть, і наступний запуск не зможе стартувати. Тому правило таке: `O_CLOEXEC` ставимо завжди, **крім** випадку, коли служба перезапускає себе через `exec` ([exec і що переживає заміну образу](book:unix-linux/exec-semantics)).

**Вміст файлу — не джерело правди.** Спокуса «прочитати номер процесу й перевірити, чи він живий» повертає нас рівно до тієї схеми з файлом-прапорцем, від якої `flock` і рятує: номери перевикористовуються, а перевірка й дія — знову два кроки з проміжком ([гонка між перевіркою й використанням](book:programming/toctou-race)). Номер усередині корисний людині, що дивиться на файл руками, і більше нікому.

## Пастка перша: чужий `open` і `close` роззброюють POSIX-замок

Найнебезпечніша з усіх, бо не дає жодного знаку. Двадцять рядків, які її показують:

```c
/* posix-lock-lost.c — cc -Wall -o posix-lock-lost posix-lock-lost.c */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

/* Чи може ЧУЖИЙ процес узяти замок на цей файл прямо зараз?
   Так — означає, що наш замок більше не існує.                      */
static int file_is_free(const char *path)
{
    struct flock fl = { .l_type = F_WRLCK, .l_whence = SEEK_SET,
                        .l_start = 0, .l_len = 0 };
    int st;
    pid_t pid = fork();

    if (pid == 0) {
        int fd = open(path, O_RDWR);
        _exit(fd >= 0 && fcntl(fd, F_SETLK, &fl) == 0 ? 0 : 1);
    }
    waitpid(pid, &st, 0);
    return WEXITSTATUS(st) == 0;
}

int main(void)
{
    const char *path = "/var/tmp/demo.db";
    struct flock fl = { .l_type = F_WRLCK, .l_whence = SEEK_SET,
                        .l_start = 0, .l_len = 0 };
    int fd = open(path, O_RDWR | O_CREAT, 0644);
    int other;

    if (fcntl(fd, F_SETLK, &fl) != 0) { perror("F_SETLK"); return 1; }
    printf("замок узято:          файл вільний? %s\n",
           file_is_free(path) ? "так" : "ні");

    other = open(path, O_RDONLY);   /* «стороння бібліотека дивиться розмір» */
    close(other);                   /* саме цей рядок і знімає ваш замок */

    printf("після чужого close:   файл вільний? %s\n",
           file_is_free(path) ? "так" : "ні");
    return 0;
}
```

```
замок узято:          файл вільний? ні
після чужого close:   файл вільний? так
```

Дескриптор `fd` при цьому живий і робочий, помилки не повернув ніхто, наступний `write` пройде — програма просто далі працює з переконанням, що захищена. Замініть `F_SETLK` на `F_OFD_SETLK` (і не забудьте `.l_pid = 0`) — обидва рядки скажуть «ні».

Найгірше тут те, що «стороння бібліотека» — не вигадка для прикладу. Її роль виконує будь-що: журналювання, що глянуло на розмір файлу; перевірка прав перед відкриттям; чужий код, який ви навіть не викликали навмисно. Саме через цю поведінку бібліотеки, що серйозно працюють із файловими замками, окремим розділом документації просять не показувати їхні файли стороннім.

## Пастка друга: перехід зі спільного замка на виключний не атомарний

`flock` не вміє міняти тип замка одним рухом: ядро спершу знімає старий, потім бере новий. Вікно між ними невелике, але воно є, і саме в нього залазить конкурент.

```c
/* upgrade-window.c — вікно робимо видимим навмисне.
   Уривок із main; fd уже відкрито, read_counter — це pread_all
   плюс strtoull, write_counter — snprintf плюс pwrite_all.
   Запустіть два примірники одночасно.                              */
    flock(fd, LOCK_SH);                       /* читаємо стан */
    a = read_counter(fd);

    sleep(1);                                 /* даємо другому дійти сюди ж */

    flock(fd, LOCK_EX);                       /* ← ядро зняло SH і аж потім дало EX */
    b = read_counter(fd);                     /* саме в тому проміжку стан і міняється */
    write_counter(fd, b + 1);                 /* пишемо вже під виключним замком */

    printf("до переходу %llu, після переходу %llu%s\n", a, b,
           a == b ? "" : "   ← стан змінився під час переходу");
```

Обидва примірники беруть спільний замок одночасно — він для того й спільний. Далі обидва просять виключний; один дістає його першим, збільшує лічильник і відпускає, і лише тоді до переходу доходить другий:

```
$ ./upgrade-window & ./upgrade-window
до переходу 41, після переходу 41
до переходу 41, після переходу 42   ← стан змінився під час переходу
```

Висновок практичний і короткий: **після переходу стан треба перечитати**, а не покладатися на прочитане до нього. А ще краще — не переходити взагалі: якщо ви наперед знаєте, що будете писати, беріть `LOCK_EX` одразу. Спільний замок має сенс там, де читачів справді багато й вони справді лише читають.

У версіях `posix` і `ofd` цієї пастки немає: заявка описує бажаний **кінцевий стан** діапазону, а не дію над наявним замком, тому зміна типу робиться одним викликом і без проміжку. Натомість там з'являється сусідня біда: якщо два процеси одночасно тримають спільний замок і обидва хочуть перейти на виключний, кожен чекає на іншого. `F_SETLKW` дасть `EDEADLK`, `F_OFD_SETLKW` — зависне ([дедлок](book:programming/deadlock)).

## Пастка третя: розрізання діапазонів множить записи в ядрі

Заявка на діапазон виглядає як безкоштовна дрібниця, але кожен окремий шматок — це окрема структура в пам'яті ядра. Зняття замка посередині замкненої ділянки не зменшує їх кількість, а **збільшує**: один запис стає двома.

```c
/* split-locks.c — скільки записів у ядрі коштує наша дисципліна замків. */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static long kernel_locks(void)            /* усі замки системи, грубо */
{
    FILE *f = fopen("/proc/locks", "r");
    char line[256];
    long n = 0;
    while (fgets(line, sizeof line, f)) n++;
    fclose(f);
    return n;
}

int main(void)
{
    struct flock fl = { .l_type = F_WRLCK, .l_whence = SEEK_SET,
                        .l_start = 0, .l_len = 0 };
    int fd = open("/var/tmp/split.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
    off_t i;

    ftruncate(fd, 1 << 20);
    fcntl(fd, F_SETLK, &fl);              /* ОДНА заявка на весь файл */
    printf("одна заявка:        %ld записів у /proc/locks\n", kernel_locks());

    for (i = 1; i < 2000; i += 2) {       /* знімаємо кожен другий байт */
        struct flock hole = { .l_type = F_UNLCK, .l_whence = SEEK_SET,
                              .l_start = i, .l_len = 1 };
        if (fcntl(fd, F_SETLK, &hole) != 0) {
            printf("зупинилися на зміщенні %lld: %s\n",
                   (long long) i, strerror(errno));
            break;
        }
    }
    printf("після розрізання:   %ld записів у /proc/locks\n", kernel_locks());
    return 0;
}
```

```
одна заявка:        7 записів у /proc/locks
після розрізання:   1007 записів у /proc/locks
```

Тисяча дірок — тисяча записів, і жоден із них програма не просила явно. Сама ця арифметика й стоїть за помилкою `ENOLCK`: на локальній файловій системі Linux немає окремого налаштовуваного ліміту на кількість замків, і `ENOLCK` означає, що ядру не вистачило пам'яті на чергову структуру; на NFS той самий код повертається ще й тоді, коли не спрацював мережевий протокол блокування. Тобто спіймати `ENOLCK` на порожній машині важко — а на завантаженій, у контейнері з жорсткою межею пам'яті й із кодом, що дрібно ріже діапазони, цілком реально.

Практичний висновок простий: **`ENOLCK` мусить бути в переліку помилок, які ваш код обробляє**, і дисципліна діапазонів має бути грубою. Замикати запис бази — так; замикати кожне поле кожного запису — спосіб перетворити акуратність на відмову.

## Пастка четверта: замикають дескриптор, а не ім'я

Замок живе на об'єкті файлової системи, а ім'я в каталозі — лише вказівник на нього ([inode: файл без імені](book:unix-linux/inode-model)). Якщо ім'я між справами видалили й створили наново, два процеси спокійно «виграють» замок — кожен на своєму об'єкті:

```
A: fd = open("app.lock", O_CREAT) → inode 77
A: flock(fd, LOCK_EX) → 0                    A тримає 77
B: fd = open("app.lock")          → inode 77 (той самий)
A: unlink("app.lock"); close(fd)             імені немає, 77 вільний
B: flock(fd, LOCK_EX) → 0                    B тримає 77
A: запуск наново: open("app.lock", O_CREAT) → inode 91
A: flock(fd, LOCK_EX) → 0                    A тримає 91, B тримає 77
```

Обидва мають рацію: замків справді два, на двох різних файлах. Помилки не повернув ніхто.

Найдешевший розв'язок — **ніколи не видаляти файл замка**. Порожній файл не коштує нічого, і те, що він лишається лежати після зупинки служби, не є засміченням: він і є точкою, до якої всі домовилися чіплятися. Якщо ж прибирання неминуче (файл лежить у теці, яку чистить чужий код), доводиться після взяття замка перевіряти, чи ім'я досі веде туди ж:

```c
/* Замок узято на об'єкті, а перевіряємо ми ім'я — тому звіряти
   треба після взяття, а не до нього.                                */
static int lock_by_path(const char *path)
{
    struct stat by_fd, by_name;
    int attempt, fd, saved;

    for (attempt = 0; attempt < 8; attempt++) {
        fd = open(path, O_RDWR | O_CREAT | O_CLOEXEC, 0644);
        if (fd < 0) return -1;

        if (flock(fd, LOCK_EX) != 0) goto give_up;
        if (fstat(fd, &by_fd) != 0)  goto give_up;

        if (stat(path, &by_name) == 0
            && by_name.st_dev == by_fd.st_dev
            && by_name.st_ino == by_fd.st_ino)
            return fd;                 /* ім'я веде сюди — замок справжній */

        close(fd);                     /* нас замкнули на викинутому файлі */
    }
    errno = ESTALE;
    return -1;

give_up:
    saved = errno;
    close(fd);
    errno = saved;
    return -1;
}
```

Пара `st_dev` плюс `st_ino` — єдиний надійний спосіб сказати «це той самий файл»: номер inode унікальний лише в межах файлової системи, тож без номера пристрою порівняння бреше. Той самий принцип працює і в зворотний бік: якщо служба має відкрити файл у каталозі, який хтось може підмінити, надійніше один раз відкрити каталог і далі ходити через його дескриптор ([родина викликів із каталожним дескриптором](book:unix-linux/at-family-syscalls)).

## Чому `F_GETLK` перед `F_SETLK` — зайвий крок

Виглядає обачно: спитати, чи вільно, і лише потім брати. Насправді це рівно та сама помилка, від якої рятує замок, — рознесені в часі перевірка й дія. Довідка `F_GETLK` описує стан **на момент виклику**; поки відповідь дійшла до вашого коду, конфліктний замок могли зняти, а вільний діапазон — зайняти. Довідкова сторінка каже про це прямо: повернуті відомості можуть застаріти ще до того, як викликач їх прочитає.

Взяття замка — вже атомарна перевірка з дією в одному виклику. Тому правильна форма коротша й швидша:

```c
/* ✗ два кроки з проміжком — і жодної гарантії від першого */
fcntl(fd, F_GETLK, &probe);
if (probe.l_type == F_UNLCK) fcntl(fd, F_SETLK, &fl);

/* ✓ один крок; EAGAIN або EACCES означає «зайнято» */
if (fcntl(fd, F_SETLK, &fl) != 0) {
    if (errno == EAGAIN || errno == EACCES) return BUSY;
    return -1;
}
```

Перевіряти обидва номери помилки треба тому, що POSIX дозволяє реалізації повернути будь-який із них; Linux повертає `EAGAIN`, але код, який поїде на іншу систему, має бути готовий до `EACCES`.

Один законний ужиток у `F_GETLK` усе-таки є — **пояснити людині, чому програма чекає**. Дістати номер процесу, що заважає, і написати його в повідомленні про помилку корисно; ухвалювати за цією відповіддю рішення — ні. Для того самого діагностичного завдання зазвичай зручніше глянути `/proc/locks` або `lslocks` ([procfs](book:unix-linux/proc-filesystem)).

## Перевірка на бігу

Останнє, що лишається, — переконатися, що все це не дарма. Скрипт запускає вісім примірників паралельно й порівнює три числа: що у файлі, скільки рядків у журналі й скільки різних чисел у ньому.

```sh
#!/bin/sh
# check.sh — чи справді замок щось міняє.
set -eu
DIR=$(mktemp -d)
N=200          # скільки разів кожен примірник додає одиницю
P=8            # скільки примірників одночасно

run() {
    prog=$1
    : > "$DIR/ctr"; : > "$DIR/log"
    i=0
    while [ "$i" -lt "$P" ]; do
        "./$prog" "$DIR/ctr" "$DIR/log" "$N" &
        i=$((i + 1))
    done
    wait
    printf '%-14s у файлі %-7s рядків %-7s різних чисел %-7s треба %s\n' \
        "$prog" "$(cat "$DIR/ctr")" "$(wc -l < "$DIR/log")" \
        "$(awk '{print $4}' "$DIR/log" | sort -u | wc -l)" "$((P * N))"
}

run counter-flock
run counter-posix
run counter-ofd
run counter-none
rm -rf "$DIR"
```

```
counter-flock  у файлі 1600    рядків 1600    різних чисел 1600    треба 1600
counter-posix  у файлі 1600    рядків 1600    різних чисел 1600    треба 1600
counter-ofd    у файлі 1600    рядків 1600    різних чисел 1600    треба 1600
counter-none   у файлі 429     рядків 1600    різних чисел 429     треба 1600
```

Останній рядок вартий того, щоб на нього подивитися уважно. Рядків у журналі рівно стільки, скільки треба, — про це подбав `O_APPEND`, і жоден із них не покалічено. А от **різних чисел лише 429**: майже три чверті приростів прочитали те саме значення, що й хтось інший, і зникли. Програма без замка не «іноді помиляється» — вона стабільно втрачає більшість роботи, і єдине, що приховує це від очей, — правдоподібний вигляд журналу.

Ті самі перегони видно й без жодного рядка C. Класичний однорядковий лічильник на оболонці ламається так само:

```sh
# ✗ читання й запис — дві команди, між ними проміжок
n=$(cat "$F"); echo $((n + 1)) > "$F"

# ✓ критична ділянка — цілий запуск, замок бере сама утиліта flock
flock "$F" sh -c 'n=$(cat "$1"); echo $((n + 1)) > "$1"' _ "$F"
```

Тут варто помітити дрібницю. Утиліта `flock` із util-linux відкриває файл сама й тримає свій дескриптор, доки не завершиться запущена команда, — а команда всередині відкриває той самий файл ще раз, обрізає його через `> "$1"` і закриває. Замкові це не шкодить: усталено `flock(1)` породжує дитину, тож оболонка — окремий процес, і її закриття до чужих замків не дотягується взагалі.

Але додайте `-F` — команда заміщує собою `flock`, замість того щоб бути її дитиною, — і процес стане одним на двох. Ось тоді вибір механізму вирішує все: POSIX-замок власний же `> "$1"` і зняв би, бо це вже той самий процес, а `flock(2)`, чий власник — опис відкритого файлу, переживає будь-яку кількість відкриттів і закриттів того самого файлу.

Для перевірки «чи не працює вже попередній запуск» тій самій утиліті потрібен лише прапорець `-n`:

```sh
flock -n /var/lock/backup.lock -c ./backup.sh \
    || echo "попереднє копіювання ще не завершилося"
```

Якщо замок вдалося взяти, `flock` повертає код виходу самої `./backup.sh`; якщо замок зайнято — виходить із кодом 1, не запустивши нічого (інше число задається прапорцем `-E`). Цих двох рядків досить, щоб щогодинне завдання перестало накладатися саме на себе, — і в них немає нічого, крім тієї самої механіки, заради якої ми написали чотири файли на C.
