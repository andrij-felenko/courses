# 📋 Контракт дескриптора й опису: поля, виклики, помилки

Довідка про точну межу між трьома поверхами відкритого файлу: що саме лежить в елементі таблиці дескрипторів, що — в описі відкритого файлу, що — в inode, і який виклик до якого поверху дотягується. Потрібна щоразу, коли треба відповісти не «приблизно так», а «ось це поле, ось цей виклик, ось хто побачить зміну».

Правило читання всієї довідки одне: **чим нижчий поверх, тим ширше коло тих, хто побачить зміну**. Зміна на першому поверсі стосується одного номера в одному процесі. Зміна на другому — усіх дескрипторів у всіх процесах, що посилаються на цей опис. Зміна на третьому — усіх, хто взагалі має справу з файлом.

---

## Поверх 1. Елемент таблиці дескрипторів

Належить процесові (точніше — `struct files_struct`, спільній для потоків одного процесу). У Linux це не окрема структура на кожен номер, а масив покажчиків плюс бітові мапи паралельно до нього.

| Що зберігається | Де в ядрі (6.13) | Читають | Пишуть |
|---|---|---|---|
| покажчик на опис | `fdt->fd[N]`, масив `struct file *` у `struct fdtable` | будь-який виклик, що бере `fd` | `open`, `dup*`, `fcntl(F_DUPFD*)`, `close` |
| прапорець «закрити при exec» | біт `N` у бітовій мапі `fdt->close_on_exec` | `fcntl(F_GETFD)` | `fcntl(F_SETFD)`, `O_CLOEXEC` в `open`, `dup3`, `F_DUPFD_CLOEXEC` |
| зайнятість номера | біт `N` у `fdt->open_fds` | — | лише ядро |

Прапорців дескриптора рівно один — `FD_CLOEXEC`; інших у Linux не визначено. Саме тому `F_GETFD` повертає число, у якому цікавий один біт, і саме тому `F_SETFD` не має проблеми «читай-зміни-запиши», яка є в його сусіда поверхом нижче.

Що з цього випливає практично: `FD_CLOEXEC`, поставлений на дескрипторі 3, нічого не каже про дескриптор 4, навіть якщо обидва ведуть в один опис. Один можна лишити [заміні образу](topic:unix-linux/exec-semantics), другий — закрити.

## Поверх 2. Опис відкритого файлу — `struct file`

Належить актові відкриття. Нижче — поля, з якими має справу простір користувача (внутрішні кеші й списки опущено).

| Поле | Тип | Що це | Змінне після `open` |
|---|---|---|---|
| `f_pos` | `loff_t` | поточна позиція читання-запису | так — `read`, `write`, `lseek` |
| `f_flags` | `unsigned int` | режим доступу + прапорці стану | частково — `fcntl(F_SETFL)` |
| `f_mode` | `fmode_t` | внутрішнє право (`FMODE_READ`, `FMODE_WRITE`), виведене з режиму доступу | **ні** |
| `f_ref` (до 6.13 — `f_count`) | `file_ref_t` | лічильник посилань | так — ядро |
| `f_cred` | `const struct cred *` | знімок повноважень того, хто відкривав | **ні** |
| `f_path` | `struct path` | елемент каталогу + точка монтування | ні |
| `f_inode` | `struct inode *` | сам файл | ні |
| `f_op` | `const struct file_operations *` | набір операцій цієї ФС або драйвера | ні |
| `f_pos_lock` | `struct mutex` | замок позиції (в об'єднанні з `f_pipe`) | — |
| `f_owner` | `struct fown_struct *` | кому слати `SIGIO`/`SIGURG` | так — `F_SETOWN` |
| `private_data` | `void *` | стан конкретного типу об'єкта | залежить від типу |

Два поля тут пояснюють більше, ніж решта разом. **`f_cred`** — це знімок облікового запису й можливостей, зроблений у момент відкриття; він і є доказом дозволу, тому режим доступу після `open` не змінюється жодним викликом. **`f_pos_lock`** — м'ютекс, який `read`, `write` і `lseek` беруть, коли на опис посилається більш ніж один дескриптор; він робить оновлення позиції неподільним, але не робить неподільним сам обмін даними.

Одна тонкість `f_flags`, про яку майже не пишуть: одразу після успішного відкриття ядро вичищає з нього створювальні прапорці —

```c
/* fs/open.c, do_dentry_open() */
f->f_flags &= ~(O_CREAT | O_EXCL | O_NOCTTY | O_TRUNC);
```

— тому `fcntl(F_GETFL)` їх **ніколи** не покаже, скільки б їх не передали в `open`. Це не втрата інформації: вони описували саму операцію відкриття, а не стан, який має жити далі.

## Поверх 3. inode

Належить файловій системі. Тут лежить усе, що є в файлі незалежно від того, чи його хтось відкривав ([Inode: файл без імені](topic:unix-linux/inode-model)).

| Поле | Що це | Читають |
|---|---|---|
| `i_ino` | номер inode у межах файлової системи | `stat`, `fstat`, поле `ino` у `fdinfo` |
| `i_nlink` | скільки імен веде на цей inode | `stat` → `st_nlink` |
| `i_size` | розмір вмісту | `stat` → `st_size` |
| `i_mode`, `i_uid`, `i_gid` | тип і права | `stat`, `chmod`, `chown` |
| `i_atime`, `i_mtime`, `i_ctime` | часи | `stat`, `utimensat` |

## Прапорці `open`: створювальні проти станових

Сторінка `open(2)` ділить прапорці на дві групи буквально: *file creation flags* — `O_CLOEXEC`, `O_CREAT`, `O_DIRECTORY`, `O_EXCL`, `O_NOCTTY`, `O_NOFOLLOW`, `O_TMPFILE`, `O_TRUNC`; *file status flags* — усі решта. Різниця не косметична: перші діють один раз, під час самого відкриття, і потім не існують; другі стають полем опису й живуть, доки живе опис.

| Прапорець | Група | Змінює `F_SETFL` | Примітка |
|---|---|---|---|
| `O_CREAT`, `O_EXCL`, `O_TRUNC`, `O_NOCTTY` | створювальний | — | ядро вичищає з `f_flags` після відкриття |
| `O_DIRECTORY`, `O_NOFOLLOW`, `O_TMPFILE` | створювальний | — | умови на сам розбір шляху |
| `O_CLOEXEC` | створювальний | — | **діє на поверх 1**: вмикає біт у `close_on_exec` |
| `O_APPEND` | становий | **так** | позиція в кінець неподільно із записом |
| `O_ASYNC` | становий | **так** | сигнал за готовністю; адресат — `F_SETOWN` ([сигнали](topic:unix-linux/signal-model)) |
| `O_DIRECT` | становий | **так** | повз кеш сторінок ([буферований і прямий ввід-вивід](topic:unix-linux/buffered-and-direct-io)) |
| `O_NOATIME` | становий | **так** | не оновлювати час доступу |
| `O_NONBLOCK` | становий | **так** | ([блокуючий і неблокуючий режим](topic:unix-linux/blocking-and-nonblocking)) |
| `O_SYNC`, `O_DSYNC` | становий | **ні** — мовчки ігнорує | ставиться лише при відкритті |
| `O_LARGEFILE` | становий | ні | 64-бітні зсуви; на 64-бітних платформах стоїть завжди |
| `O_PATH` | становий | ні | `read`/`write` на такому описі → `EBADF` |
| `O_RDONLY`, `O_WRONLY`, `O_RDWR` | режим доступу | **ні** — мовчки ігнорує | виділяють маскою `O_ACCMODE` |

Три речі з цієї таблиці варто тримати в голові окремо.

**`F_SETFL` не помиляється, коли не може.** Передані йому режим доступу й створювальні прапорці не викликають `EINVAL` — вони просто ігноруються. Тобто виклик, який «мав би» перевести дескриптор із читання в запис, поверне 0 і не зробить нічого; помилка виявиться пізніше, на `write` із `EBADF`.

**`O_CLOEXEC` — єдиний прапорець, чия група й поверх не збігаються.** У класифікації він створювальний, бо стосується самого відкриття; діє ж на елемент таблиці дескрипторів. Наслідок: `dup` копії його не успадковує, а `F_SETFD` може зняти або поставити його потім.

**Режим доступу виділяють маскою, а не порівнянням.** `O_RDONLY` дорівнює нулю, тому перевірка `if (fl & O_RDONLY)` завжди хибна. Правильно — `(fl & O_ACCMODE) == O_RDONLY`.

## Дублювання: п'ять способів дістати друге ім'я одного опису

Усі п'ять роблять одне: кладуть у вільний елемент таблиці той самий покажчик і збільшують лічильник посилань. Новий опис не створює жоден із них.

```c
int dup(int oldfd);
int dup2(int oldfd, int newfd);
int dup3(int oldfd, int newfd, int flags);          /* Linux 2.6.27, glibc 2.9 */
int fcntl(int fd, F_DUPFD, int arg);                /* arg = мінімальний номер */
int fcntl(int fd, F_DUPFD_CLOEXEC, int arg);        /* Linux 2.6.24, POSIX.1-2008 */
```

| Виклик | Який номер дає | `FD_CLOEXEC` нового | Коли `oldfd == newfd` |
|---|---|---|---|
| `dup` | найменший вільний | **знято** | — |
| `dup2` | рівно `newfd`, попереднє відкриття тихо закривши | **знято** | нічого не робить, повертає `newfd` |
| `dup3` | рівно `newfd` | за `flags`: `O_CLOEXEC` або нічого | **`EINVAL`** |
| `F_DUPFD` | найменший вільний ≥ `arg` | **знято** | — |
| `F_DUPFD_CLOEXEC` | найменший вільний ≥ `arg` | **поставлено** | — |

Розбіжність `dup2` і `dup3` на однакових аргументах — не недогляд, а свідомий вибір: у `dup3` є `flags`, і «нічого не робити» лишило б незрозумілим, чи застосовано `O_CLOEXEC`. Тому там, де `dup2` мовчки погоджується, `dup3` відмовляє.

Дві пастки `dup2`. Перша: він закриває `newfd` **мовчки**, і помилка того закриття губиться — якщо на дескрипторі лишалися незаписані дані файлової системи, дізнатися про це вже нема як. Друга: `dup2(oldfd, newfd)` при неправильному `oldfd` дає `EBADF` **навіть якщо** `newfd` дорівнює `oldfd`; перевірка первинна.

## `fcntl`: дві пари команд, два поверхи

| Команда | Поверх | `arg` | Повертає | Хто побачить зміну |
|---|---|---|---|---|
| `F_GETFD` | 1 | ігнорується | прапорці дескриптора | — |
| `F_SETFD` | 1 | `int` (0 або `FD_CLOEXEC`) | 0 | лише цей дескриптор у цьому процесі |
| `F_GETFL` | 2 | ігнорується | режим доступу + прапорці стану | — |
| `F_SETFL` | 2 | `int` — **увесь набір**, а не додаток | 0 | **усі** дескриптори на цей опис, у всіх процесах |
| `F_GETOWN` / `F_SETOWN` | 2 | `pid_t` | адресат `SIGIO` | усі, хто ділить опис |
| `F_OFD_SETLK` та рідня | 2 | `struct flock *` | 0 | опис ([блокування файлів](topic:unix-linux/file-locking)) |

`F_SETFL` — єдина з цих команд, яку не можна викликати «в лоб»: вона **замінює** увесь набір прапорців, тож перед нею обов'язковий `F_GETFL`.

```c
int fl = fcntl(fd, F_GETFL);
if (fl == -1) { /* EBADF */ }
if (fcntl(fd, F_SETFL, fl | O_NONBLOCK) == -1) { /* EPERM для O_NOATIME */ }
```

Проміжок між цими двома викликами — справжня гонитва: інший потік або інший процес, що ділить опис, може встигнути змінити прапорці, і його зміна буде затерта прочитаним раніше значенням. Атомарного «додай один біт» у `fcntl` немає.

`EPERM` у цій парі виникає рівно в одному випадку — спроба поставити `O_NOATIME` на файл, чий власник не збігається з чинним обліковим записом і в кого немає `CAP_FOWNER` ([можливості](topic:unix-linux/capabilities)).

## Явний зсув: `pread`, `pwrite` і родина

Ці виклики беруть позицію аргументом і **не чіпають** `f_pos` опису — тому вони єдиний правильний спосіб працювати з різними частинами файлу через один спільний дескриптор.

```c
ssize_t pread (int fd,       void *buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void *buf, size_t count, off_t offset);

ssize_t preadv (int fd, const struct iovec *iov, int iovcnt, off_t offset);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt, off_t offset);

/* Linux 4.6, glibc 2.26 */
ssize_t preadv2 (int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
```

| Прапорець `preadv2`/`pwritev2` | Ядро | Дія |
|---|---|---|
| `RWF_HIPRI` | 4.6 | пріоритетний запит із опитуванням пристрою |
| `RWF_DSYNC` | 4.7 | як `O_DSYNC`, лише для цього виклику (запис) |
| `RWF_SYNC` | 4.7 | як `O_SYNC`, лише для цього виклику (запис) |
| `RWF_NOWAIT` | 4.14 | не чекати; немає в кеші — `EAGAIN` (читання) |
| `RWF_APPEND` | 4.16 | як `O_APPEND`, лише для цього виклику (запис) |
| `RWF_NOAPPEND` | 6.9 | зневажити `O_APPEND` опису й ужити переданий зсув |
| `RWF_ATOMIC` | 6.11 | запис без розриву на межі |
| `RWF_DONTCACHE` | 6.14 | звільнити сторінки кешу після операції |

Три контракти, які тут ламають найчастіше.

**Дескриптор мусить бути придатний до перемотування.** Канал, сокет, `FIFO` дадуть `ESPIPE` — позиції в них немає взагалі.

**`pwrite` на описі з `O_APPEND` у Linux ігнорує переданий зсув.** POSIX вимагає протилежного, і Linux позначає це як власне відхилення. Тому дескриптор, з яким працюють через `pwrite`, не відкривають з `O_APPEND`; починаючи з ядра 6.9 явним виходом є `pwritev2(..., RWF_NOAPPEND)`.

**`preadv2` та `pwritev2` зі зсувом `-1` поводяться як звичайні `readv`/`writev`** — беруть і посувають позицію опису. Це єдиний спосіб додати `RWF_*`-прапорець до послідовного читання, і водночас легкий спосіб випадково зачепити спільну позицію.

## `kcmp`: чи це один опис

Однакові `pos` і `flags` у двох дескрипторів нічого не доводять: два свіжі відкриття щойно створеного файлу дадуть ті самі числа. Точну відповідь дає лише ядро.

```c
#include <linux/kcmp.h>
#include <sys/syscall.h>
#include <unistd.h>

long syscall(SYS_kcmp, pid_t pid1, pid_t pid2, int type,
             unsigned long idx1, unsigned long idx2);
```

| Що | Значення |
|---|---|
| `type` | `KCMP_FILE` (0) — «чи `idx1` у `pid1` і `idx2` у `pid2` ведуть на той самий опис» |
| Повертає `0` | так, це **один** опис |
| Повертає `1`, `2` | різні; число задає порядок адрес (щоб можна було сортувати) |
| Повертає `3` | різні, порядок недоступний |
| З'явився | ядро 3.5 |
| Умова збірки | `CONFIG_CHECKPOINT_RESTORE`; з ядра 5.12 — також `CONFIG_KCMP` |
| Обгортка в glibc | **немає**, лише через `syscall(2)` |

Помилки: `EBADF` — переданий номер не є відкритим дескриптором; `EINVAL` — невідомий `type`; `ESRCH` — процесу немає; `EPERM` — бракує права оглядати чужий процес (для не своїх процесів потрібна `CAP_SYS_PTRACE`); `ENOSYS` — ядро зібране без потрібної опції.

Порядкові значення `1` і `2` існують не для краси: вони дають повний порядок, тож набір дескрипторів можна відсортувати й за один прохід згрупувати ті, що ведуть на спільні описи, замість `n²` порівнянь. Це і був первісний ужиток виклику — у відновленні збережених контейнерів.

## `/proc/PID/fdinfo/N`

Показує вміст опису з погляду конкретного дескриптора ([/proc: процеси як файли](topic:unix-linux/proc-filesystem)).

```sh
$ cat /proc/self/fdinfo/3
pos:    1024
flags:  0100002
mnt_id: 28
ino:    3548712
```

| Рядок | Поверх | Значення |
|---|---|---|
| `pos` | 2 | `f_pos`, десятковим |
| `flags` | 1 + 2 | режим доступу й прапорці стану опису, **вісімковим**; біт `O_CLOEXEC` ядро домальовує з бітової мапи `close_on_exec` |
| `mnt_id` | 2 | точка монтування з `f_path` (з ядра 3.15) |
| `ino` | 3 | номер inode (з ядра 5.13) |

Рядок `flags` — єдине місце в системі, де поверхи 1 і 2 подано одним числом, і це варто пам'ятати під час розбору. Приклад вище: `0100002` = `O_RDWR` (2) `| O_LARGEFILE` (0100000), тобто звичайне читання-запис без жодного особливого режиму.

Для окремих типів об'єктів ядро додає власні рядки з `private_data`: `eventfd-count` для `eventfd` (з 3.8), рядки `tfd:`/`events:`/`data:` на кожен стежений дескриптор для `epoll`, `inotify wd:` для `inotify`, `clockid:`/`ticks:` для `timerfd` (з 3.17).

## Зведення: виклик → поверх → коло видимости

| Виклик | Поверх | Зміну побачать |
|---|---|---|
| `fcntl(F_SETFD)`, `close` | 1 | лише цей номер у цьому процесі |
| `dup`, `dup2`, `dup3`, `F_DUPFD*` | 1 | новий номер у цьому процесі; опис той самий |
| `lseek`, `read`, `write` | 2 | усі дескриптори на цей опис, у всіх процесах |
| `fcntl(F_SETFL)`, `F_SETOWN` | 2 | те саме |
| `pread`, `pwrite`, `preadv2` зі зсувом ≥ 0 | 2 (лише вміст) | позиції не чіпає взагалі |
| `flock`, `F_OFD_SETLK` | 2 | усі, хто ділить опис |
| `fcntl(F_SETLK)` | 3 (пара «процес + inode») | знімається будь-яким `close` цього файлу в процесі |
| `chmod`, `truncate`, `unlink` | 3 | усіх, хто має справу з файлом |
| `open` того самого шляху | новий опис | нікого — власна позиція, власні прапорці |

## Типові коди помилок

| Код | Де виникає найчастіше | Причина |
|---|---|---|
| `EBADF` | скрізь, де є `fd` | номер не відкритий, або `newfd` поза межами, або `O_PATH`-дескриптор у `read`/`write` |
| `EMFILE` | `open`, `dup*`, `F_DUPFD` | вичерпано `RLIMIT_NOFILE` процесу ([ліміти ресурсів](topic:unix-linux/resource-limits)) |
| `ENFILE` | `open`, `socket`, `pipe` | вичерпано загальносистемну стелю описів, `fs.file-max` |
| `EINVAL` | `dup3`, `fcntl`, `preadv2` | `oldfd == newfd` у `dup3`; від'ємний `arg` у `F_DUPFD`; невідомий `RWF_`-прапорець |
| `EBUSY` | `dup2`, `dup3` | гонитва з паралельним `open`/`dup` (лише Linux) |
| `EINTR` | `dup2`, `dup3`, `F_OFD_SETLKW` | сигнал під час виклику ([EINTR і перезапуск](topic:unix-linux/eintr-and-restart)) |
| `EPERM` | `F_SETFL`, `kcmp` | `O_NOATIME` на чужому файлі; огляд чужого процесу без `CAP_SYS_PTRACE` |
| `ESPIPE` | `pread`, `pwrite` | об'єкт не має позиції (канал, сокет) |
| `EAGAIN` | `preadv2` з `RWF_NOWAIT` | даних немає в кеші, а чекати заборонено |
| `EOPNOTSUPP` | `preadv2`, `pwritev2` | файлова система не вміє цього `RWF_`-прапорця |
| `ENOSYS` | `kcmp` | ядро зібране без `CONFIG_KCMP`/`CONFIG_CHECKPOINT_RESTORE` |

## Мінімальний робочий виклик

Програма перевіряє весь контракт за один прохід: прапорець першого поверху виявляється особистим, прапорець другого — спільним, а питання «один це опис чи два» ставиться ядру, а не вгадується з чисел.

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <linux/kcmp.h>
#include <stdio.h>
#include <sys/syscall.h>
#include <unistd.h>

static int same_ofd(int a, int b) {
    pid_t me = getpid();
    return syscall(SYS_kcmp, me, me, KCMP_FILE,
                   (unsigned long)a, (unsigned long)b) == 0;
}

int main(void) {
    int fd  = open("probe.txt", O_RDWR | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    int cp  = dup(fd);                    /* той самий опис, новий номер */
    int own = open("probe.txt", O_RDWR);  /* власний опис */
    if (fd < 0 || cp < 0 || own < 0) { perror("open"); return 1; }

    /* поверх 1: у кожного дескриптора свій прапорець */
    printf("FD_CLOEXEC: fd=%d cp=%d\n",
           (fcntl(fd, F_GETFD) & FD_CLOEXEC) != 0,
           (fcntl(cp, F_GETFD) & FD_CLOEXEC) != 0);

    /* поверх 2: прапорці стану спільні — читай-зміни-запиши */
    int fl = fcntl(fd, F_GETFL);
    printf("режим доступу = %d, O_APPEND до = %d\n",
           fl & O_ACCMODE, (fl & O_APPEND) != 0);
    fcntl(fd, F_SETFL, fl | O_APPEND);
    printf("O_APPEND після: через cp = %d, через own = %d\n",
           (fcntl(cp,  F_GETFL) & O_APPEND) != 0,
           (fcntl(own, F_GETFL) & O_APPEND) != 0);

    /* спільність опису — питання до ядра */
    printf("fd~cp = %d, fd~own = %d\n", same_ofd(fd, cp), same_ofd(fd, own));
    return 0;
}
```

**Збірка й очікуваний вивід на Linux із увімкненим `kcmp`:**

```
$ cc -o probe probe.c && ./probe
FD_CLOEXEC: fd=1 cp=0
режим доступу = 2, O_APPEND до = 0
O_APPEND після: через cp = 1, через own = 0
fd~cp = 1, fd~own = 0
```

Перший рядок — межа першого поверху: `dup` дав друге ім'я тому самому описові, але прапорець `FD_CLOEXEC` не скопіював. Третій — межа другого: `O_APPEND`, поставлений через `fd`, видно через `cp` і не видно через `own`. Четвертий підтверджує обидва висновки незалежно від чисел у `fdinfo`. Якщо `kcmp` віддає `-1` з `ENOSYS`, ядро зібране без потрібної опції — решта перевірок від цього не залежить.
