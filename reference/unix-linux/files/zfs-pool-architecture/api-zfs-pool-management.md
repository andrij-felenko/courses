# 🔌 Довідник системних команд zpool/zfs та низькорівневих властивостей

Ця вставка містить структурований довідник CLI-команд управління пулами та датасетами ZFS, опис топологічних специфікацій VDEV, детальний аналіз системних властивостей ZPOOL і ZFS, а також опис контракту системного виклику `/dev/zfs` (ioctl) у просторі ядра.

## 1. Специфікація топології та правил zpool create / add

Команда `zpool create` ініціалізує новий пул шляхом запису заголовків `vdev_label_t` на кожен вказаний пристрій, а команда `zpool add` розширює наявний пул новими Top-Level VDEV або спеціалізованими пристроями.

### Таблиця специфікації груп VDEV

| Тип VDEV / Клас | Синтаксис специфікації | Опис та правила надмірності |
| :--- | :--- | :--- |
| **Mirror** | `mirror <dev1> <dev2> [... <devN>]` | N-стороннє дзеркало. Витримує відмову `N - 1` дисків у групі. |
| **RAIDZ1** | `raidz1 <dev1> ... <devN>` | Одиночна парність (аналог RAID-5). Мінімально 3 диски. Витримує відмову 1 диска. |
| **RAIDZ2** | `raidz2 <dev1> ... <devN>` | Подвійна парність (аналог RAID-6). Мінімально 4 диски. Витримує відмову 2 дисків. |
| **RAIDZ3** | `raidz3 <dev1> ... <devN>` | Потрійна парність. Мінімально 5 дисків. Витримує відмову 3 дисків. |
| **dRAID** | `draid[:parity][:<data>d][:<spares>s]` | Розподілений RAIDZ (OpenZFS 2.1+). Прискорює resilvering через розподілені spares. |
| **Log (SLOG)** | `log [mirror] <dev1> [<dev2>]` | Окремий пристрій ZIL. Для захисту синхронних записів рекомендується дзеркало. |
| **Cache (L2ARC)**| `cache <dev1> [... <devN>]` | Кеш читання другого рівня на SSD/NVMe. Не потребує надмірності (безризиковий). |
| **Special** | `special [mirror] <dev1> <dev2>` | Allocation class для метаданих (`dnode`) та малих блоків. Втрата нищить пул! |
| **Dedup** | `dedup [mirror] <dev1> <dev2>` | Allocation class для таблиці дедуплікації (DDT). Потребує високої надійності. |
| **Spare** | `spare <dev1> [... <devN>]` | Hot spare диски для автоматичної заміни збійних пристроїв. |

### Правила та застереження при конфігурації топології

При формуванні топології ZPOOL необхідно дотримуватися кількох жорстких системних правил:

1. **Однорідність Top-Level VDEV:** Всі Top-Level VDEV у пулі повинні мати однакову продуктивність та рівень надмірності. Не можна змішувати в одному пулі VDEV типу Mirror і VDEV типу RAIDZ2, оскільки виділювач SPA буде записувати дані на обидва пристрої, і загальна відмовостійкість пулу знизиться до рівня найменш захищеного VDEV.
2. **Незворотність додавання Top-Level VDEV:** У старих версіях ZFS видалити доданий Top-Level VDEV було неможливо. В OpenZFS реалізовано механізм `zpool remove` для одиночних дисків та дзеркал, проте він створює шар непрямої адресації (Indirection Layer) в пам'яті. Для VDEV типу RAIDZ видалення досі не підтримується.
3. **Захист Special VDEV:** Оскільки Special Allocation Class зберігає всі метадані датасетів (`dnode`, ZAP-каталоги), вихід з ладу Special VDEV призводить до повної нечитабельності всього пулу. Тому Special VDEV обов'язково повинен формуватися з дзеркал (Mirror) із рівнем надмірності, не меншим за основні VDEV пулу.

```bash
# Приклад створення високопродуктивного enterprise-пулу:
zpool create -f -o ashift=12 -O compression=lz4 -O acltype=posixacl -O xattr=sa datapool \
    mirror /dev/disk/by-id/nvme-CT1000_A /dev/disk/by-id/nvme-CT1000_B \
    special mirror /dev/disk/by-id/nvme-FAST_A /dev/disk/by-id/nvme-FAST_B \
    log mirror /dev/disk/by-id/nvme-OPTANE_A /dev/disk/by-id/nvme-OPTANE_B \
    cache /dev/disk/by-id/nvme-READCACHE_A
```

## 2. Системні властивості пулу (zpool properties)

Властивості пулу керують поведінкою виділювача SPA, апаратними параметрами пристроїв та інтеграцією з ядром операційної системи.

### Детальний розбір властивостей ZPOOL

- `ashift` (за замовчуванням `0` — автовизначення, допустимо `9`..`16`): Задає розмір фізичного сектора носія у вигляді ступеня двійки (`2^ashift`). Значення `9` відповідає сектору 512 байтів (`2^9 = 512`), `12` — сектору 4096 байтів (4 КБ), `13` — 8192 байти (8 КБ). Це найважливіша властивість пулу: вона задається **одноразово під час створення VDEV і ніколи не може бути змінена**. Помилка в `ashift=9` на дисках 4Kn спричиняє падіння швидкості запису в 10–20 разів через феномен Read-Modify-Write.
- `autoexpand` (`off` \| `on`): Визначає, чи повинен пул автоматично збільшувати свій корисний обсяг після заміни всіх дисків у складі VDEV на диски більшої ємності. Якщо встановлено `off`, для розширення простору потрібно виконати команду `zpool online -e`.
- `autotrim` (`off` \| `on`): Вмикає фонову передачу команд TRIM (для NVMe) або DISCARD (для SATA SSD) при звільненні блоків у результаті видалення файлів або снапшотів. Дозволяє SSD-контролерам ефективно виконувати збір сміття (Garbage Collection).
- `failmode` (`wait` \| `continue` \| `panic`): Визначає поведінку системи при втраті доступу до всіх копій VDEV (наприклад, при відключенні зовнішньої дискової стійки). Режим `wait` блокує операції I/O до відновлення зв'язку; `continue` повертає помилку `EIO` для нових запитів; `panic` викликає паніку ядра Linux/FreeBSD для запобігання пошкодженню стану додатків.
- `delegation` (`on` \| `off`): Керує можливістю делегування прав адміністрування ZFS непривілейованим користувачам через команду `zfs allow`.

## 3. Властивості датасетів (zfs properties)

Управління параметрами запису, стиснення, кешування та виділення простору на рівні ZPL і DMU виконується окремо для кожного датасету або тома ZVOL.

### Детальний розбір властивостей датасетів

- `compression` (`off` \| `on` \| `lz4` \| `zstd` \| `gzip`): Алгоритм прозорого стиснення блоків. Стиснення відбувається в RAM перед передачею блоку до SPA. `lz4` є стандартом за замовчуванням: він має високу швидкість розпакування (>2 ГБ/с на ядро) та миттєво відхиляє нестисливі блоки. `zstd` (Zstandard) надає ступені стиснення від 1 до 19 і рекомендований для резервних копій та систем зберігання логів.
- `recordsize` (`512`..`16M`, за замовчуванням `128k`): Максимальний розмір блоку для файлів у датасеті. Зміна `recordsize` впливає тільки на нові або модифіковані файли. Для систем управління базами даних (PostgreSQL, MySQL InnoDB) `recordsize` обов'язково встановлюють рівним розміру сторінки СУБД (16 КБ або 8 КБ), щоб уникнути ампліфікації запису. Для зберігання медіафайлів та відео вибирають `1M` або `4M`.
- `sync` (`standard` \| `always` \| `disabled`): Керує обробкою синхронних викликів `fsync()` та `O_SYNC`. У режимі `standard` ZFS записує синхронні дані в ZIL/SLOG. У режимі `disabled` ZFS ігнорує вимоги додатків про синхронізацію й записує всі дані асинхронно через TXG. Це підвищує швидкість, але створює ризик втрати останніх 5 секунд даних при збої живлення.
- `atime` (`on` \| `off` \| `relatime`): Оновлення мітки часу останнього доступу до файла. Встановлення `atime=off` повністю усуває генерування CoW-транзакцій запису при простих операціях читання файлів.
- `special_small_blocks` (`0`..`1M`): Пороговий розмір файлів. Якщо розмір файла менший за це значення, його блоки даних записуються безпосередньо на Special VDEV разом із метаданими.
- `dnodesize` (`legacy` \| `auto` \| `1k`..`16k`): Розмір структури `dnode`. Режим `auto` дозволяє розширювати `dnode` до 1 КБ або 2 КБ, що дозволяє вмістити всі розширені атрибути файлу (xattr) всередині самого `dnode`, усуваючи необхідність створення окремих об'єктів ZAP.
- `quota` та `reservation` (`none` \| `<size>`): `quota` встановлює жорстку верхню межу простору для датасету. `reservation` гарантує, що вказаний обсяг простору пулу буде зарезервований виключно для даного датасету й не зможе бути зайнятий іншими датасетами.

## 4. Контракт інтерфейсу `/dev/zfs` (ioctl interface)

Утиліти простору користувача (`zpool`, `zfs`, демон подій `zed`, службові бібліотеки `libzfs` та `libzfs_core`) взаємодіють з модулем ядра ZFS через символьний пристрій `/dev/zfs` за допомогою системного виклику `ioctl()`.

### Структура керуючого пакета `zfs_cmd_t`

Усі команди передаються в ядро через єдину базову структуру `zfs_cmd_t`, вирівняну по 8-байтовій межі:

```c
struct zfs_cmd {
    char         zc_name[MAXPATHLEN];     /* Ім'я пулу або датасету */
    uint64_t     zc_nvlist_src;           /* Вказівник на NVList конфігурації (input) */
    uint64_t     zc_nvlist_src_size;      /* Розмір вхідного NVList буфера */
    uint64_t     zc_nvlist_dst;           /* Вказівник на NVList результату (output) */
    uint64_t     zc_nvlist_dst_size;      /* Розмір вихідного NVList буфера */
    uint64_t     zc_history;              /* Вказівник на журнал історії */
    uint64_t     zc_cookie;               /* Спеціальний ідентифікатор транзакції */
    uint64_t     zc_objset_type;          /* Тип об'єкта (DMU_OST_ZFS, DMU_OST_ZVOL) */
    uint64_t     zc_perm_action;          /* Права доступу та операція */
};
```

Поля `zc_nvlist_src` та `zc_nvlist_dst` містять упаковані бінарні структури **NVList (Name-Value List)** у форматі XDR. Через NVList ядро та простір користувача обмінюються складними деревами конфігурацій (списками VDEV, дисковими ідентифікаторами, наборами властивостей).

### Основні коди `ioctl` для підсистеми ZFS

Коди перелічення `zfs_ioc` призначаються послідовно від `('Z' << 8)` = `0x5a00` у порядку оголошення в `zfs_ioctl.h`, тож конкретне число залежить від версії модуля — покладатися слід на ім'я, а не на константу.

- `ZFS_IOC_POOL_CREATE`: Створення нового пулу. Упакований NVList містить повне дерево VDEV (Top-Level VDEVs, Mirroring, RAIDZ, SLOG, Cache) та первинні властивості пулу.
- `ZFS_IOC_POOL_IMPORT`: Зчитування заголовків `vdev_label_t` з указаних секторів носіїв, перевірка відповідності GUID пулу та імпорт топології в ядро.
- `ZFS_IOC_POOL_CONFIGS`: Отримання повного списку завантажених конфігурацій усіх імпортованих пулів для відображення в `zpool status`.
- `ZFS_IOC_CLEAR`: Скидання лічильників помилок читання, запису та контрольних сум на пристроях VDEV, а також переведення пулу зі стану `DEGRADED` або `FAULTED` у нормальний стан після заміни дисків.
- `ZFS_IOC_POOL_SCAN`: Ініціалізація, призупинення або скасування операцій сканування пулу — скрабування (`scrub`) або ресілверингу (`resilver`).

Взаємодія через `/dev/zfs` вимагає привілеїв суперкористувача (`root`) або наявності відповідних прав `CAP_SYS_ADMIN` у просторі імен користувачів (user namespaces).
