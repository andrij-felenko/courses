# 📋 Контракт дескриптора: виклики, прапорці, коди помилок

Це довідник інтерфейсу, з яким має справу будь-яка програма, що відкриває файл, приймає з'єднання чи заводить таймер: точні сигнатури викликів, які номер видають, переставляють і забирають; таблиця прапорців із відповіддю на головне питання — на якому саме поверсі кожен із них живе; і перелік кодів помилок із поясненням, що кожен каже про таблицю дескрипторів. Виклики подано так, як їх бачить програма на C: контракт визначено на цьому рівні, а обгортки решти мов його лише переказують.

## Виклики, що видають номер

Спільне для всіх — правило номера: **найменший вільний у цьому процесі**. Виняток один, і він явний: `dup2` та `dup3` беруть потрібний номер аргументом.

Друга спільна риса новіша. Кожен сучасний виклик цієї родини вміє поставити `FD_CLOEXEC` **у мить створення**, без окремого кроку:

| Виклик | Що видає | CLOEXEC при створенні | Доступно з |
|---|---|---|---|
| `open`, `openat`, `creat` | файл, каталог, пристрій, FIFO | `O_CLOEXEC` у прапорцях | `openat` — Linux 2.6.16; `O_CLOEXEC` — 2.6.23 |
| `openat2` | те саме плюс строгі правила розбору шляху | `O_CLOEXEC` у `how.flags` | Linux 5.6 |
| `socket`, `socketpair` | сокет | `SOCK_CLOEXEC` в аргументі типу | Linux 2.6.27 |
| `accept4` | номер прийнятого з'єднання | `SOCK_CLOEXEC` | Linux 2.6.28 |
| `pipe2` | два номери каналу: `[0]` читання, `[1]` запис | `O_CLOEXEC` | Linux 2.6.27 |
| `epoll_create1` | набір очікування | `EPOLL_CLOEXEC` | Linux 2.6.27 |
| `eventfd`, `signalfd`, `timerfd_create`, `inotify_init1` | лічильник-сповіщення, сигнали, таймер, стеження за ФС | `EFD_` / `SFD_` / `TFD_` / `IN_CLOEXEC` | Linux 2.6.27 |
| `memfd_create` | безіменна ділянка пам'яті | `MFD_CLOEXEC` | Linux 3.17 |
| `dup3` | копія наявного номера | `O_CLOEXEC` у `flags` | Linux 2.6.27 |
| `fcntl(fd, F_DUPFD_CLOEXEC, n)` | копія з номером ≥ `n` | вбудовано в саму команду | Linux 2.6.24 |
| `recvmsg` з `SCM_RIGHTS` | опис, надісланий чужим процесом | `MSG_CMSG_CLOEXEC` | здавна |
| `pidfd_getfd` | копія номера з чужого процесу | ставиться завжди | Linux 5.6, glibc 2.36 |

Старі форми — `open` без `O_CLOEXEC`, `pipe`, `accept`, `dup`, `epoll_create`, `socket` без `SOCK_CLOEXEC` — видають номер успадковуваним, і позначити його можна лише другим викликом. Саме проміжок між цими двома викликами й закривали всі нові форми: у програмі з кількома потоками виконання ([потоки в Linux — це задачі зі спільною таблицею дескрипторів](book:unix-linux/threads-as-tasks)) між `open` і `fcntl` сусідній потік устигає зробити `fork` з `exec` і забрати із собою ще не позначений номер.

## Мінімальний правильний виклик

Найкоротший код, у якому вже враховано всі чотири щоденні вимоги контракту:

```c
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <stdio.h>

int main(void)
{
    int fd = openat(AT_FDCWD, "/etc/hostname", O_RDONLY | O_CLOEXEC);
    if (fd < 0) {
        fprintf(stderr, "open: %s\n", strerror(errno));
        return 1;
    }

    char buf[64];
    ssize_t n;
    do {
        n = read(fd, buf, sizeof buf);
    } while (n < 0 && errno == EINTR);   /* read повторювати можна */

    if (n < 0)
        fprintf(stderr, "read: %s\n", strerror(errno));
    else
        fwrite(buf, 1, (size_t) n, stdout);

    if (close(fd) < 0)                   /* рівно один раз, без повтору */
        fprintf(stderr, "close: %s\n", strerror(errno));
    fd = -1;

    return n < 0;
}
```

Чотири рішення тут навмисні. `O_CLOEXEC` стоїть одразу, а не додається згодом. Перевірка `fd < 0` іде до будь-якого використання номера — бо в разі невдачі в змінній лежить `−1`, і саме це число потім дасть `EBADF` у найнесподіванішому місці. Повтор після `EINTR` зроблено для `read` і **не зроблено** для `close`. І змінна занулена одразу після закривання, у тому самому блоці.

## `open`, `openat`, `openat2`

```c
int open(const char *path, int flags, ... /* mode_t mode */);
int openat(int dirfd, const char *path, int flags, ... /* mode_t mode */);
int openat2(int dirfd, const char *path, struct open_how *how, size_t size);
```

- **`flags`** — рівно один режим доступу (`O_RDONLY`, `O_WRONLY`, `O_RDWR`) плюс будь-яка кількість решти прапорців через `|`.
- **`mode`** — обов'язковий і осмислений лише за наявності `O_CREAT` або `O_TMPFILE`; фактичні права новоствореного файлу виходять `mode & ~umask` ([umask — маска, що вирізає біти з бажаних прав](book:unix-linux/umask-and-defaults)). Пропустити `mode` там, де він потрібен, — не помилка компіляції, а зчитування випадкового сміття зі стека.
- **`dirfd`** — номер уже відкритого каталогу, від якого відлічується відносний шлях; стала `AT_FDCWD` означає «від поточного робочого каталогу», тобто поведінку старого `open`. Уся суть цього аргументу в тому, що каталог названо не рядком, а дескриптором, і підмінити його між викликами вже не можна ([родина `*at`: шлях, відлічений від дескриптора](book:unix-linux/at-family-syscalls)).
- **`how`** в `openat2` — структура `{ __u64 flags; __u64 mode; __u64 resolve; }`, де поле `resolve` дозволяє обмежити сам розбір шляху: `RESOLVE_BENEATH` забороняє вийти за межі `dirfd`, `RESOLVE_NO_SYMLINKS` — піти за символьним посиланням, `RESOLVE_NO_XDEV` — перетнути точку монтування. На відміну від `open`, невідомі біти тут не ігноруються, а дають `EINVAL`: програма дізнається, що ядро її обмежень не зрозуміло, замість того щоб мовчки лишитися без захисту.

Повертають найменший вільний номер або `−1`. Ключові коди помилок, крім спільних для всієї родини: `EACCES` (немає прав на сам файл або на прохід через котрийсь каталог шляху), `EEXIST` (`O_CREAT|O_EXCL` на наявному об'єкті), `EISDIR` (каталог відкрито на запис), `ELOOP` (забагато символьних посилань або `O_NOFOLLOW` спрацював), `ENOENT`, `ENOTDIR`, `ENXIO` (файл пристрою є, самого пристрою немає), `EROFS`, `ETXTBSY` (запис у файл, який зараз виконується), `EOPNOTSUPP` (файлова система не вміє `O_TMPFILE`).

Окремий випадок — `O_PATH` (Linux 2.6.39). Такий номер називає об'єкт, але **не відкриває** його: читати й писати ним не можна, зате можна `fstat`, `fchdir`, `close`, `fcntl` з `F_GETFD`/`F_SETFD` і — головне — передати його як `dirfd` у виклики родини `*at`. Це дешевий спосіб узяти каталог «у руки», не питаючи права на читання його вмісту.

## Дублювання: п'ять форм і одна пастка

| Форма | Який номер дає | `FD_CLOEXEC` на новому | Якщо `oldfd == newfd` |
|---|---|---|---|
| `dup(oldfd)` | найменший вільний | скинуто | — |
| `dup2(oldfd, newfd)` | точно `newfd`, закривши те, що там було | скинуто | нічого не робить, повертає `newfd` |
| `dup3(oldfd, newfd, flags)` | точно `newfd` | за `O_CLOEXEC` у `flags` | `EINVAL` |
| `fcntl(oldfd, F_DUPFD, n)` | найменший вільний ≥ `n` | скинуто | — |
| `fcntl(oldfd, F_DUPFD_CLOEXEC, n)` | найменший вільний ≥ `n` | встановлено | — |

Усі п'ять дають новий номер на **той самий опис**: позиція читання-запису, режим доступу й прапорці стану в них спільні, і зсув, зроблений через один номер, миттєво видно через другий ([опис відкритого файлу — рівень, де живе позиція](book:unix-linux/open-file-description)). Незалежним лишається рівно одне — `FD_CLOEXEC`, бо він належить номерові, а не описові.

Далі — те, на чому спотикаються:

- `dup2` закриває те, що було відкрито під номером `newfd`, **мовчки**. Код помилки того закривання не повертається нікуди; якщо там лежали незаписані дані, це остання нагода їх утратити.
- Якщо `oldfd` недійсний, `dup2` падає з `EBADF`, і `newfd` при цьому **не закривається**. Невдалий `dup2` нічого не руйнує.
- `dup2(fd, fd)` — законна операція, що не робить нічого; `dup3(fd, fd, 0)` на тих самих аргументах дає `EINVAL`. Механічна заміна одного на друге ламає код, який на цю поблажливість покладався.
- `dup2` і `dup3` виконують закривання й підстановку **неподільно**. Ручна пара `close(newfd); dup(oldfd);` цієї властивості не має: у щілину між викликами інший потік устигає забрати щойно звільнений номер, і `dup` поверне вже не те, що просили.
- На Linux `dup2` і `dup3` можуть повернути `EBUSY` — це слід внутрішніх перегонів із паралельним `open` у тому самому процесі. Правильна реакція — повторити виклик.

## Два поверхи прапорців

Інтерфейс `fcntl` здається непослідовним, поки не помітиш, що команд там не одна четвірка, а **дві пари на двох різних рівнях**. `F_GETFD`/`F_SETFD` працюють із номером, `F_GETFL`/`F_SETFL` — з описом.

| Прапорець | Де живе | Читати | Міняти | Спільний для копій номера | Після `fork` | Після `exec` |
|---|---|---|---|---|---|---|
| `FD_CLOEXEC` | на дескрипторі | `F_GETFD` | `F_SETFD` | ні: `dup` його скидає | копіюється | номер закривається |
| режим доступу `O_RDONLY` / `O_WRONLY` / `O_RDWR` | в описі | `F_GETFL & O_ACCMODE` | не змінюється взагалі | так | спільний | лишається |
| `O_APPEND`, `O_NONBLOCK`, `O_ASYNC`, `O_DIRECT`, `O_NOATIME` | в описі | `F_GETFL` | `F_SETFL` | так | спільні | лишаються |
| `O_SYNC`, `O_DSYNC` | в описі | `F_GETFL` | `F_SETFL` їх **не змінює** | так | спільні | лишаються |
| `O_CREAT`, `O_EXCL`, `O_TRUNC`, `O_NOCTTY`, `O_DIRECTORY`, `O_NOFOLLOW`, `O_TMPFILE` | ніде не зберігаються | — | — | діють лише в мить `open` | — | — |
| `O_CLOEXEC` | перетворюється на `FD_CLOEXEC` | `F_GETFD`, не `F_GETFL` | `F_SETFD` | ні | копіюється | номер закривається |

Останній рядок — найчастіше джерело здивування. `O_CLOEXEC` виглядає як решта `O_*`, передається в тому самому аргументі `open`, але прапорцем опису він не є ні секунди: це коротка форма прохання «постав на новому номері `FD_CLOEXEC`». Шукати його через `F_GETFL` марно.

`F_SETFL` замінює **весь** набір прапорців стану, а не додає до наявного. Тому єдина правильна форма — читання, правка, запис:

```c
int fl = fcntl(fd, F_GETFL);
if (fl < 0) { /* EBADF */ }
if (fcntl(fd, F_SETFL, fl | O_NONBLOCK) < 0) { /* EBADF, EINVAL, EPERM */ }
```

Поширена помилка `fcntl(fd, F_SETFL, O_NONBLOCK)` без попереднього `F_GETFL` мовчки скидає `O_APPEND`, який хтось поставив при відкритті, — і два процеси, що дописували в один журнал, починають затирати одне одного. `F_SETFL` не міняє ні режим доступу, ні прапорці створення: передані в ньому `O_RDWR` чи `O_CREAT` просто ігноруються.

І окремо про режим доступу. `O_RDONLY` дорівнює нулю, тому перевірка `fl & O_RDONLY` **завжди хибна**, а `fl & O_WRONLY` дає істину і для `O_RDWR`. Єдина правильна форма — маска `O_ACCMODE`:

```c
switch (fcntl(fd, F_GETFL) & O_ACCMODE) {
case O_RDONLY: /* лише читання */ break;
case O_WRONLY: /* лише запис   */ break;
case O_RDWR:   /* і те, і те   */ break;
}
```

> 🔧 **Навіщо це.** Розрізнення двох поверхів — не формальність, а спосіб передбачити наслідок, не заглядаючи в документацію. Поставили `O_NONBLOCK` на успадкованому номері 0 — і його побачила батьківська оболонка разом з усіма іншими програмами конвеєра, бо опис у них спільний ([блокуючий і неблокуючий режим](book:unix-linux/blocking-and-nonblocking)). Поставили `FD_CLOEXEC` — не побачив ніхто, бо прапорець лежить у вашій комірці таблиці й далі неї не виходить.

POSIX.1-2024 додав до цієї пари ще й `FD_CLOFORK` з `F_DUPFD_CLOFORK` — «закрий цей номер при `fork`». Linux їх не підтримує, і переносний код мусить це враховувати ([POSIX: що саме стандартизовано](book:unix-linux/posix-standard)).

## Закривання

```c
int close(int fd);
int close_range(unsigned int first, unsigned int last, unsigned int flags);
```

`close` повертає `0` або `−1`. Уся тонкість — у порядку кроків усередині виклику:

![Чотири кроки всередині close: спершу номер вилучається з таблиці процесу, далі зменшується лічильник посилань на опис, далі — якщо лічильник став нулем — дані скидаються й опис звільняється, і лише наприкінці повертається код. Смуга над кроками показує, що номер вільний уже з першого кроку; знизу підписано, що EBADF походить із першого кроку, а EIO, ENOSPC і EINTR — із третього, коли номера вже немає](/reference/unix-linux/files/file-descriptor/img/close-order.svg)

*Номер звільняється на першому кроці, а помилки народжуються на третьому. Тому код помилки від `close` — це повідомлення про подію, якій уже нічим не зарадити.*

Звідси два правила, яких зі здорового глузду не вивести, — їх доводиться просто запам'ятати.

**Не повторювати `close` після `EINTR`.** Ядро Linux звільняє номер на початку операції — отже після `EINTR` номер уже вільний, і повтор закриє те, що інший потік устиг під цим номером відкрити. Документація Linux каже це прямо. POSIX.1-2024 при цьому узаконив протилежну поведінку HP-UX, де номер після `EINTR` лишається відкритим і повтор обов'язковий, — тож переносний код мусить знати, під якою системою працює, а міняти поведінку Linux ніхто не планує ([EINTR: перервані виклики й правила перезапуску](book:unix-linux/eintr-and-restart)).

**Викликати `fsync` до `close`, якщо дані важливі.** Помилка запису на пристрій виявляється на третьому кроці — коли номера вже немає, буфери вже віддано, а повторити запис уже нема через що: сам номер, через який його робили, зник на кроці першому ([кеш сторінок, `fsync` і довговічність](book:unix-linux/page-cache-durability)).

`close_range(first, last, flags)` закриває цілий діапазон номерів включно з обома кінцями. Незайняті номери всередині діапазону просто пропускаються — `EBADF` цей виклик не повертає взагалі. Ідіома «закрити все зайве перед `exec`» скорочується до одного рядка:

```c
close_range(3, ~0U, 0);          /* лишити тільки 0, 1, 2 */
```

| Прапорець | Що робить | Доступно з |
|---|---|---|
| `0` | закрити діапазон | Linux 5.9, glibc 2.34 |
| `CLOSE_RANGE_CLOEXEC` | не закривати, а розставити `FD_CLOEXEC` — номери доживуть до `exec` і зникнуть там | Linux 5.11 |
| `CLOSE_RANGE_UNSHARE` | спершу відщепити таблицю від процесів, з якими вона спільна, і аж тоді закривати | Linux 5.9 |

Помилки `close_range`: `EINVAL` (невідомий прапорець або `first > last`), а з `CLOSE_RANGE_UNSHARE` ще й `EMFILE` та `ENOMEM` — бо відщеплення таблиці означає її копіювання.

## Коди помилок: що кожен каже про таблицю

| Код | Про що він насправді | Куди дивитися |
|---|---|---|
| `EBADF` | про **таблицю**: такого номера в ній немає або комірка порожня | номер закрито раніше часу, узято з неініціалізованої змінної або це `−1` після невдалого `open` |
| `EMFILE` | про **межу процесу**: `RLIMIT_NOFILE` вичерпано | витік у цій програмі або замалий ліміт |
| `ENFILE` | про **межу системи**: вичерпано `fs.file-max`, тобто описи для всіх процесів разом | винуватець може бути де завгодно; свій процес часто ні до чого |
| `EINTR` | про **сигнал**, не про номер: виклик перервано до завершення | обробник сигналу без `SA_RESTART` |
| `EAGAIN` (він же `EWOULDBLOCK`) | про **опис**: на ньому стоїть `O_NONBLOCK`, і зараз даних чи місця немає | це не поломка, а нормальний робочий стан неблокуючого режиму |
| `EINVAL` | про **аргументи**: `dup3` з однаковими номерами, невідомий біт у `openat2`, недозволена команда `fcntl` | найчастіше — прапорець, якого ядро цієї версії ще не знає |
| `EBUSY` | про **внутрішні перегони** `dup2`/`dup3` з паралельним `open` | просто повторити виклик |
| `EPERM` | про **права**: підняття жорсткого `RLIMIT_NOFILE` вище `fs.nr_open` або `pidfd_getfd` без права трасувати | |
| `ENOMEM` | ядру забракло пам'яті на розширення таблиці | |
| `ESRCH` | процесу, на який указує `pidfd`, уже немає | |

Найкорисніше розрізнення тут — між `EMFILE` і `ENFILE`, і воно робиться ще до читання коду. `EMFILE` означає «винен я», `ENFILE` — «винен хтось у системі». Друге, попри майже однакову назву, веде діагностику зовсім в інший бік.

`EAGAIN` варто читати уважно з протилежної причини: попри вигляд коду помилки, він нічого не каже ні про номер, ні про таблицю. Це відповідь опису: «зараз нічого немає, спитай пізніше». Програма, що трактує його як збій і закриває дескриптор, руйнує цілком справне з'єднання.

## Межі

| Що обмежено | Де подивитися | Що трапляється на межі |
|---|---|---|
| м'яка межа процесу | `getrlimit(RLIMIT_NOFILE, …)`, `ulimit -n`, `/proc/<pid>/limits` | `EMFILE`; програма може підняти сама, аж до жорсткої |
| жорстка межа процесу | те саме | підняти може лише той, хто має `CAP_SYS_RESOURCE` ([можливості замість всесильного root](book:unix-linux/capabilities)) |
| стеля жорсткої межі | `/proc/sys/fs/nr_open`, типово 1048576 | спроба перевищити дає `EPERM` |
| межа системи | `/proc/sys/fs/file-max`; лічильник — `/proc/sys/fs/file-nr` | `ENFILE` |

`RLIMIT_NOFILE` рахується не так, як здається: це значення **на одиницю більше** за найбільший дозволений номер. Якщо межа дорівнює 1024, найбільший номер, який видасть `open`, — 1023.

Підняти м'яку межу до жорсткої може будь-яка програма, прав на це не треба ([ліміти ресурсів: м'яка й жорстка межа](book:unix-linux/resource-limits)):

```c
struct rlimit rl;
if (getrlimit(RLIMIT_NOFILE, &rl) == 0) {
    rl.rlim_cur = rl.rlim_max;
    setrlimit(RLIMIT_NOFILE, &rl);
}
```

І тут варто знати, звідки беруться конкретні числа на типовій сучасній системі. `systemd` починаючи з версії 240 (кінець 2018) роздає службам пару `1024:524288` — м'яка межа 1024, жорстка понад півмільйона. Розрив зроблено навмисно: жорстку межу підняли, а м'яку лишили на старому значенні, бо `select` уміє працювати лише з номерами, меншими за `FD_SETSIZE`, а це якраз 1024, і запис у `fd_set` більшого номера псує пам'ять поруч. Програма, готова до великих номерів, піднімає межу сама й тим заявляє, що `select` вона не вживає ([select, poll, epoll: чекати на багато джерел](book:unix-linux/select-poll-epoll)).

Є в цієї межі й друга, менш очевидна роль: з Linux 4.5 `RLIMIT_NOFILE` обмежує ще й кількість дескрипторів, які непривілейований процес може тримати «в польоті» — надісланих через сокет домену Unix, але ще не прийнятих одержувачем.

## Забрати номер, якого ти не відкривав

Способів рівно два, і обидва потребують згоди — або власника, або системи.

**Через сокет домену Unix.** Відправник кладе опис у допоміжне повідомлення `SCM_RIGHTS`, приймач дістає його з `recvmsg` і отримує **свій власний** номер — найменший вільний у себе, ніяк не пов'язаний з номером відправника. Прапорець `MSG_CMSG_CLOEXEC` у `recvmsg` ставить на отриманому номері `FD_CLOEXEC` одразу ([сокети домену Unix і передача дескрипторів](book:unix-linux/unix-domain-sockets)).

**Через `pidfd_getfd`.** Це вже не згода власника, а дозвіл системи:

```c
#include <sys/syscall.h>
#include <unistd.h>

int fd = syscall(SYS_pidfd_getfd, pidfd, targetfd, 0u);
```

| Аргумент | Значення |
|---|---|
| `pidfd` | дескриптор процесу-цілі, узятий із `pidfd_open` або `clone` з `CLONE_PIDFD` ([PID і дерево процесів](book:unix-linux/pid-and-hierarchy)) |
| `targetfd` | номер **у таблиці цілі**, не у своїй |
| `flags` | зарезервовано, мусить бути `0`, інакше `EINVAL` |

Право на цю дію перевіряється так само, як право під'єднатися налагоджувачем: `PTRACE_MODE_ATTACH_REALCREDS` ([ptrace: на чому тримається трасування](book:unix-linux/ptrace-model)). Інакше — `EPERM`. Повертає новий номер уже у власній таблиці, і `FD_CLOEXEC` на ньому стоїть завжди. Доступно з Linux 5.6; обгортку в glibc додано у версії 2.36 (серпень 2022), тож на старіших системах доводиться й далі кликати через `syscall`.

## Що видно ззовні

| Шлях | Що показує |
|---|---|
| `/proc/<pid>/fd/` | символьне посилання на кожен відкритий номер; ціль посилання називає об'єкт: шлях, `socket:[12345]`, `pipe:[…]`, `anon_inode:[eventfd]` |
| `/proc/<pid>/fdinfo/<n>` | стан **опису** за цим номером: `pos` — позиція, `flags` — прапорці вісімковим числом, `mnt_id`, `ino` |
| `/proc/<pid>/limits` | чинні м'яка й жорстка межі, зокрема «Max open files» |

Файл `fdinfo` — найпряміший спосіб відповісти на питання «а чи справді на цьому номері стоїть `O_APPEND`», не змінюючи в процесі нічого ([/proc: процеси як файли](book:unix-linux/proc-filesystem)). Ось він для файлу, відкритого як `O_RDONLY | O_CLOEXEC`:

```
$ cat /proc/self/fdinfo/3
pos:    4096
flags:  02100000
mnt_id: 27
ino:    1180023
```

Число `flags` вісімкове й складається так: `0` — режим `O_RDONLY`, `0100000` — `O_LARGEFILE` (на 64-бітних системах ядро ставить його завжди), `02000000` — `O_CLOEXEC`.

Останній доданок тут особливий, і на ньому варто спинитися. Усе решта в цьому числі — прапорці **опису**; `O_CLOEXEC` в описі не зберігається ніде, і ядро домальовує цей біт на льоту, дивлячись на `FD_CLOEXEC` у комірці таблиці в мить читання. Тобто `fdinfo` — єдине місце, де обидва поверхи показані одним числом. До Linux 3.1 воно натомість показувало значення `O_CLOEXEC` на час відкриття — і після кожного `fcntl(fd, F_SETFD, …)` починало брехати. А от `O_CREAT`, `O_EXCL` і `O_TRUNC` не з'являться тут ніколи: їх справді ніде не збережено.
