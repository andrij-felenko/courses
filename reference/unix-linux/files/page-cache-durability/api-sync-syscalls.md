# 📋 Довговічність на замовлення: виклики, прапорці й важелі ядра

Це контракт усього, чим програма в Linux просить довговічності, і всього, чим система цю довговічність послаблює: повні підписи `fsync`, `fdatasync`, `sync`, `syncfs`, `msync`, `sync_file_range`, прапорці відкриття `O_SYNC`/`O_DSYNC`/`O_DIRECT`, форми «синхронно на один запис» у `pwritev2` та `io_uring`, таблиця кодів помилок із причиною кожного — а далі параметри `/proc/sys/vm`, вміст `/sys/block/<пристрій>/queue/write_cache` і варіанти монтування, які скидання кешу вимикають. Потрібне тоді, коли треба точно знати, докуди дотягується конкретний виклик і яким кодом він відмовиться.

## Спільні правила

Усі виклики цієї родини повертають `0` при успіху й `−1` при відмові, поклавши причину в `errno`; винятки — `sync()`, що не повертає нічого й не може відмовити, і форми `io_uring`, які кладуть **від'ємний** код помилки просто в поле `res` завершення й `errno` не чіпають узагалі. Про те, як цей код доходить до програми, — [механіка системного виклику](book:unix-linux/syscall-mechanics): значення `errno` визначене лише після явної ознаки відмови.

Два формулювання зі стандарту трапляються далі постійно, тож варто закріпити їх один раз.

| термін POSIX | що мусить опинитися на носії |
|---|---|
| завершення з цілісністю **даних** (*synchronized I/O data integrity completion*) | самі дані плюс ті метадані, без яких дані неможливо прочитати назад: новий розмір файлу, карта виділених блоків |
| завершення з цілісністю **файлу** (*synchronized I/O file integrity completion*) | те саме плюс решта полів inode: часи доступу й зміни, лічильники, права |

Жодна форма з цього довідника не поширюється на **ім'я** файлу: запис у каталозі — вміст іншого об'єкта, і його довговічності просять окремо — `fsync` над дескриптором самого каталогу ([каталог як відображення імен](book:unix-linux/directory-as-mapping) — каталог є файлом, у якому лежить таблиця «ім'я → номер inode»). Довідник `fsync(2)` каже це прямим текстом: виклик не забезпечує, що запис у каталозі теж дійшов до диска.

## Явне прохання: fsync і fdatasync

```c
#include <unistd.h>

int fsync(int fd);
int fdatasync(int fd);
```

`fsync()` від glibc 2.16 не потребує макросів; давнішій потрібен `_BSD_SOURCE`, `_XOPEN_SOURCE` або `_POSIX_C_SOURCE >= 200112L`. `fdatasync()` вимагає `_POSIX_C_SOURCE >= 199309L` чи `_XOPEN_SOURCE >= 500`.

| дія | `fsync` | `fdatasync` |
|---|---|---|
| виносить брудні сторінки даних цього inode | так | так |
| виносить розмір файлу й карту блоків | так | лише якщо вони змінилися |
| виносить `st_atime`, `st_mtime`, `st_ctime` | так | ні |
| надсилає пристроєві команду скидання кешу | так | так |
| чекає підтвердження до останнього блоку | так | так |
| стосується інших файлів у тій самій ФС | ні | ні |

Практичний наслідок один: дописування в кінець файлу змінює розмір, тому `fdatasync` після нього все одно оновить inode; перезапис уже наявних блоків розміру не змінює, тому `fdatasync` обмежиться даними й заощадить окрему поїздку до зовсім іншої ділянки носія. У Linux 2.2 й давніших `fdatasync` був простим синонімом `fsync` і жодної переваги не давав.

## Ширше за один файл: sync і syncfs

```c
#include <unistd.h>
void sync(void);        /* _XOPEN_SOURCE >= 500 або _DEFAULT_SOURCE */
int  syncfs(int fd);    /* _GNU_SOURCE; Linux 2.6.39, glibc 2.14 */
```

`sync()` виносить усі відкладені зміни всіх змонтованих файлових систем; `syncfs()` — лише тієї, якій належить файл за дескриптором `fd` (сам дескриптор при цьому потрібен тільки як вказівка на файлову систему, його права й режим ролі не грають).

Розходження зі стандартом варто знати: POSIX дозволяє `sync()` лише **запланувати** записи й повернутися ще до їх завершення, а Linux від версії 1.3.20 чекає завершення вводу-виводу. Тому в Linux `sync()` дає ту саму гарантію, що й `fsync()`, викликаний для кожного файлу системи, а `syncfs()` — що й `fsync()` для кожного файлу свого тому.

Повідомлення про помилки в `syncfs()` довго було фіктивним: до ядра 5.8 виклик міг відмовити лише з `EBADF`, тобто програма не мала способу дізнатися про невдалий зворотний запис. Від 5.8 виклик повертає помилку, якщо від попереднього `syncfs()` на цьому дескрипторі хоч один inode не вдалося записати. У `sync()` коду повернення немає взагалі, тож переконатися через нього, що все справді лягло на носій, неможливо.

## Відображена пам'ять: msync

```c
#include <sys/mman.h>
int msync(void *addr, size_t length, int flags);
```

Потрібен там, де файл змінюють не викликом `write`, а записом у пам'ять ([mmap: файл і пам'ять як одне](book:unix-linux/mmap-model) — відображення файлу в адресний простір, після якого зміна вмісту стає звичайною інструкцією процесора). `addr` мусить бути кратний розміру сторінки.

| прапорець | значення |
|---|---|
| `MS_SYNC` | запустити винесення діапазону й **чекати** його завершення — єдина форма, що дає гарантію |
| `MS_ASYNC` | лише запланувати винесення й повернутися негайно; від Linux 2.6.19 це фактично порожня дія, бо ядро й без того стежить за брудними сторінками й виносить їх |
| `MS_INVALIDATE` | скасувати чинність інших відображень того самого файлу, щоб вони перечитали свіжі значення |

`MS_SYNC` і `MS_ASYNC` взаємовиключні; вказати обидва — `EINVAL`. Стандарт вимагає вказати рівно один із двох, Linux дозволяє не вказати жодного — і тоді поводиться як за `MS_ASYNC`. Помилки: `EBUSY` (`MS_INVALIDATE` над діапазоном із замкненими в пам'яті сторінками), `EINVAL` (адреса не кратна сторінці або хибне поєднання прапорців), `ENOMEM` (діапазон не відображено).

## sync_file_range: керування, а не гарантія

```c
#define _GNU_SOURCE
#include <fcntl.h>

int sync_file_range(int fd, off_t offset, off_t nbytes, unsigned int flags);
```

Доданий у Linux 2.6.17. На архітектурах, де 64-бітний аргумент вимагає вирівнювання в регістрах (ARM, PowerPC), ядро надає інший порядок аргументів — `sync_file_range2(int fd, unsigned int flags, off_t offset, off_t nbytes)`; glibc ховає цю різницю за тим самим ім'ям.

| прапорець | значення |
|---|---|
| `SYNC_FILE_RANGE_WAIT_BEFORE` | дочекатися завершення тих сторінок діапазону, які вже віддано драйверові, **перш ніж** щось подавати |
| `SYNC_FILE_RANGE_WRITE` | подати на запис усі брудні сторінки діапазону, які ще не подано; не чекати |
| `SYNC_FILE_RANGE_WAIT_AFTER` | дочекатися завершення всіх сторінок діапазону **після** подання |

Звідси два корисні поєднання: сам `SYNC_FILE_RANGE_WRITE` — «почни писати цей шматок, я потім по нього повернуся» (спосіб розмазати зворотний запис у часі замість одного пікового злиття), а всі три разом — «винеси цей діапазон і дочекайся».

⚠️ **Це не заміна `fsync`.** Довідник Linux формулює прямо: виклик надзвичайно небезпечний і не годиться для переносних програм; жодна з операцій не виносить метаданих файлу, тому — якщо програма не робить строго перезапис уже виділених на диску блоків — гарантії, що дані будуть доступні після збою, немає. Скидання кешу самого накопичувача він теж не замовляє. Помилки: `EBADF`, `EINVAL` (хибні прапорці, від'ємний `offset` чи `nbytes`), `EIO`, `ENOMEM`, `ENOSPC`, `ESPIPE` (дескриптор не звичайного файлу, не блокового пристрою й не каталогу).

## Прапорці відкриття: O_SYNC, O_DSYNC, O_DIRECT

```c
#include <fcntl.h>
int fd = open(path, O_WRONLY | O_CREAT | O_DSYNC, 0644);
```

| прапорець | що обіцяє кожному `write` | чого не робить |
|---|---|---|
| `O_DSYNC` | виклик повертається лише після завершення з цілісністю **даних** — еквівалент `fdatasync` після кожного запису | не виносить часів; не стосується імені |
| `O_SYNC` | виклик повертається лише після завершення з цілісністю **файлу** — еквівалент `fsync` після кожного запису | не стосується імені |
| `O_RSYNC` | у Linux **не реалізований**; glibc помилково прирівнює його до `O_SYNC` | — |
| `O_DIRECT` | обходить кеш сторінок: дані йдуть із буфера програми в пристрій напряму | **нічого не гарантує про носій** — довідник каже, що прапорець намагається передати дані синхронно, але гарантій `O_SYNC` не дає; кеш пристрою лишається незайманим |

Історична дрібниця, від якої залежить поведінка на старому ядрі: до Linux 2.6.33 існував лише `O_SYNC`, і більшість файлових систем реалізовували під цим ім'ям семантику цілісності **даних**. Із 2.6.33 з'явилася чесна пара — старе числове значення дісталося `O_DSYNC`, а `O_SYNC` став новим прапорцем, що вбирає поведінку `O_DSYNC` і додає метадані.

**Чим прапорець гірший за явний виклик.** Прапорець прив'язує синхронізацію до кожного окремого `write`, тож десять записів по 4 КіБ означають десять повних обертів до носія. Явний `fsync`/`fdatasync` дозволяє зробити десять записів і **один** оберт — а оскільки ціна довговічності майже вся сидить у кількості обертів, а не в обсязі даних, різниця виходить у рази. Прапорець виграє в іншому: він не дає забути, і його не можна пропустити в гілці обробки помилок.

**Чим прапорець гірший, ніж здається.** `O_DIRECT` регулярно беруть за «запис одразу на диск» — це неправда: він лише прибирає проміжну копію в кеші сторінок, а кеш накопичувача, тобто останній енергозалежний поверх, лишається на місці. Довговічність із `O_DIRECT` усе одно замовляють через `fdatasync` або `O_DSYNC`. Обмеження вирівнювання (адреса буфера, зсув у файлі й довжина) залежать від файлової системи й ядра; від Linux 6.1 їх питають у самої системи через [statx](book:unix-linux/statx-extended-stat) із `STATX_DIOALIGN` замість того, щоб вгадувати. Подробиці самої моделі — [буферизований і прямий ввід-вивід](book:unix-linux/buffered-and-direct-io).

## Синхронність на один запис: pwritev2 та io_uring

```c
#define _GNU_SOURCE
#include <sys/uio.h>

ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
```

`pwritev2` дозволяє те, чого не дає ні прапорець відкриття, ні окремий виклик: зробити синхронним **один конкретний запис**, не змінюючи режиму дескриптора й не роблячи другого системного виклику. Зсув `−1` означає «від поточної позиції, і посунути її».

| прапорець | дія | з якого ядра |
|---|---|---|
| `RWF_DSYNC` | цей запис поводиться так, ніби файл відкрито з `O_DSYNC` | 4.7 |
| `RWF_SYNC` | цей запис поводиться так, ніби файл відкрито з `O_SYNC` | 4.7 |
| `RWF_APPEND` | цей запис іде в кінець файлу, як за `O_APPEND` | 4.16 |
| `RWF_ATOMIC` | запис у звичайний файл виконується із захистом від розриву на частини | 6.11 |
| `RWF_DONTCACHE` | після завершення прибрати з кешу сторінки, які цей запис створив | 6.14 |

Невідомий прапорець дає `EOPNOTSUPP`, а не мовчазне ігнорування, — це навмисно, щоб програма не думала, ніби попросила синхронності й отримала її.

У кільцях `io_uring` ту саму дію подають як окрему операцію ([io_uring: кільця подань і завершень](book:unix-linux/io-uring) — черга подань і черга завершень у пам'яті, спільній із ядром):

```c
#include <liburing.h>
void io_uring_prep_fsync(struct io_uring_sqe *sqe, int fd, unsigned flags);
```

| що подають | значення |
|---|---|
| `IORING_OP_FSYNC`, `flags = 0` | те саме, що `fsync(fd)` |
| `IORING_OP_FSYNC`, `flags = IORING_FSYNC_DATASYNC` | те саме, що `fdatasync(fd)` |
| `IORING_OP_SYNC_FILE_RANGE` | те саме, що `sync_file_range()`, з тими самими застереженнями |

Результат приходить у полі `res` завершення: `0` при успіху, **від'ємний** код помилки при відмові (`-EIO`, `-ENOSPC`) — кільце ніколи не користується `errno`. І головне: кільце **не впорядковує** незалежні подання між собою, тож `IORING_OP_FSYNC`, подана разом із записами, цілком може виконатися раніше за них. Порядок вимагають явно — прапорцем `IOSQE_IO_LINK` на попередньому поданні, який зв'язує його з наступним.

## Коди помилок

| код | де трапляється | що означає й що з ним робити |
|---|---|---|
| `EIO` | `fsync`, `fdatasync`, `syncfs`, `sync_file_range` | зворотний запис не вдався. Помилку бачить кожен дескриптор, який міг записати ці дані, — але **рівно один раз**: повторний виклик поверне `0`, і цей нуль не означає, що дані на диску. Повторювати не можна; коректна реакція — вважати вміст після останньої вдалої синхронізації втраченим |
| `ENOSPC` | `fsync`, `fdatasync`, `syncfs`, `sync_file_range` | місце на пристрої скінчилося саме під час винесення. Типовий наслідок відкладеного виділення блоків: `write` пройшов успішно, бо блоки на той момент ще не вибиралися |
| `EDQUOT` | `fsync`, `fdatasync`, `syncfs` | те саме, але через квоту користувача або брак місця на віддаленій файловій системі (NFS) |
| `EINVAL`, `EROFS` | `fsync`, `fdatasync` | дескриптор указує на об'єкт, що синхронізації не підтримує взагалі: канал, FIFO, сокет, деякі спеціальні файли. Це не збій, а відповідь «тут нема чого виносити» — і саме цей код бачать програми, що механічно роблять `fsync` над кожним відкритим дескриптором |
| `EBADF` | усі | число не є відкритим дескриптором |
| `EINTR` | `fsync`, `fdatasync` | виклик перервано сигналом, і це єдина відмова з цього списку, після якої виклик правильно повторити ([EINTR: перервані виклики й перезапуск](book:unix-linux/eintr-and-restart)) |
| `ENOMEM` | `sync_file_range` | ядру забракло пам'яті на службові структури запиту |
| `ESPIPE` | `sync_file_range` | дескриптор не звичайного файлу, не блокового пристрою й не каталогу |
| `EBUSY` | `msync` | `MS_INVALIDATE` над діапазоном, у якому є замкнені в пам'яті сторінки |

Одна деталь про `EIO` варта окремого рядка, бо від неї залежить, чи взагалі помилку буде видно. До Linux 4.13 позначку про невдалий зворотний запис знімав перший, хто її прочитав, — включно з чужим процесом, що просто зробив `sync`. Від 4.13 лічильник помилок ведеться так, що кожен [опис відкритого файлу](book:unix-linux/open-file-description) бачить кожну помилку рівно один раз незалежно від інших.

## Мінімальний робочий виклик

Дописування запису в журнал так, щоб після повернення функції він гарантовано був на носії, і без спроби «повторити `fsync`»:

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>

/* Дописати len байтів у кінець журналу і зробити їх довговічними.
   Повертає 0 при успіху; −1 означає, що вміст журналу після останнього
   вдалого виклику вважається втраченим — повторювати НЕ можна. */
int wal_append(int fd, const void *buf, size_t len)
{
    const char *p = buf;
    size_t left = len;

    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0) {
            if (errno == EINTR) continue;   /* сигнал — це не відмова */
            return -1;
        }
        p += n;
        left -= (size_t)n;
    }

    /* Файл росте, тож fdatasync усе одно винесе новий розмір,
       але не чіпатиме часів — саме цього ми й хочемо. */
    while (fdatasync(fd) < 0) {
        if (errno == EINTR) continue;
        return -1;                          /* EIO/ENOSPC — відновлюємося, не повторюємо */
    }
    return 0;
}
```

Ті самі дві дії в кільці `io_uring` виглядають як два подання, зв'язані `IOSQE_IO_LINK`: без прапорця ядро має право виконати `IORING_OP_FSYNC` до того, як `IORING_OP_WRITE` донесе байти.

## Важелі системи: коли зворотний запис починається

Параметри живуть у `/proc/sys/vm/` ([псевдо-ФС](book:unix-linux/pseudo-filesystems) — файли, за якими немає носія: читання й запис у них є викликом коду ядра). Читати їх можна `cat`, міняти — `sysctl -w` або записом у файл; постійні значення кладуть у `/etc/sysctl.d/`.

| параметр | одиниця | типове | що робить |
|---|---|---|---|
| `dirty_background_ratio` | % доступної пам'яті | 10 | частка брудного, з якої фонові потоки зворотного запису беруться до роботи, не чекаючи на вік |
| `dirty_background_bytes` | байти | 0 | те саме в абсолютних числах |
| `dirty_ratio` | % доступної пам'яті | 20 | частка, з якої процес, що пише, **сам** починає гальмувати всередині `write` |
| `dirty_bytes` | байти | 0 | те саме в абсолютних числах; мінімум — дві сторінки, менше ігнорується |
| `dirty_expire_centisecs` | 1/100 с | 3000 | вік, з якого брудна сторінка підлягає плановому винесенню |
| `dirty_writeback_centisecs` | 1/100 с | 500 | як часто прокидаються потоки, що виносять старе; `0` вимикає планове винесення взагалі |
| `dirtytime_expire_seconds` | с | 43200 | поріг віку для inode, у яких застаріли самі лише часи (режим монтування `lazytime`); ним же задано інтервал пробудження відповідного потоку |

Дві пари взаємовиключні: запис у `dirty_bytes` негайно скасовує `dirty_ratio`, і той при читанні показує `0`; так само для фонової пари. Тому налаштовують **одну** форму з двох, а не обидві.

«Доступна пам'ять» тут — не вся оперативна: документація ядра каже, що це вільні сторінки плюс ті, які можна вивільнити, і що ця величина не дорівнює обсягу пам'яті системи. Тому відсоток, порахований від повного обсягу оперативної пам'яті, вийде завищеним.

![Три зони поведінки зворотного запису і важіль, що рухає кожну межу](/reference/unix-linux/files/page-cache-durability/img/dirty-thresholds.svg)

*Два пороги ділять шкалу на три режими; третій режим — це і є те сповільнення копіювання великого файлу, яке видно неозброєним оком.*

**Умова.** Сервер, 64 ГіБ пам'яті, з них доступними ядро вважає 48 ГіБ. Типові пороги. Скільки даних може висіти в пам'яті й скільки часу займе їх злити на пристрої, що стало приймає 800 МБ/с?

```
доступна пам'ять                    = 48 ГіБ  = 51540 МБ
фоновий поріг    (10 % від 48 ГіБ)  = 4.8 ГіБ =  5154 МБ
поріг гальмування (20 % від 48 ГіБ) = 9.6 ГіБ = 10308 МБ

злити 10308 МБ на 800 МБ/с          ≈ 12.9 с
```

Той самий поріг, заданий абсолютним числом — `dirty_bytes = 268435456`, тобто 256 МіБ, — дав би вікно втрати ≈ 0.34 с; платою за це є те, що в гальмування впирається кожен сплеск запису, навіть короткий.

Поточний стан читають не з цих файлів, а з `/proc/meminfo`: рядок `Dirty:` — скільки зараз чекає на винесення, `Writeback:` — скільки саме зараз пишеться на пристрій ([як міряти пам'ять](book:unix-linux/memory-accounting) — які саме лічильники ядро веде й що кожен рахує).

### drop_caches

```sh
sync                                  # спершу зробити брудне чистим
echo 3 > /proc/sys/vm/drop_caches
```

| значення | що звільняє |
|---|---|
| `1` | чисті сторінки кешу сторінок |
| `2` | кеші dentry та inode |
| `3` | і те, і те |

Операція неруйнівна саме тому, що звільняє **лише чисті** об'єкти: брудне вона не викидає й не виносить, тож без попереднього `sync` більша частина кешу лишиться на місці. Документація ядра прямо застерігає від використання цього поза тестуванням і налагодженням: відкинуті об'єкти доведеться створювати наново, а це коштує і вводу-виводу, і процесора. Для одного файлу замість цього молотка є скальпель — `posix_fadvise(fd, offset, len, POSIX_FADV_DONTNEED)`, який теж не чіпає брудних сторінок і теж вимагає `fsync` перед собою ([випереджувальне читання](book:unix-linux/readahead) — уся родина підказок `posix_fadvise` і як ядро їх ураховує).

## Важелі пристрою: кеш накопичувача

Стан останнього енергозалежного поверху видно в черзі блокового пристрою ([блоковий пристрій](book:unix-linux/block-device-model) — сектори, черга запитів і те, як ядро з ними працює):

```sh
cat /sys/block/nvme0n1/queue/write_cache   # write back | write through
cat /sys/block/nvme0n1/queue/fua           # 1, якщо драйвер уміє FUA
cat /sys/block/nvme0n1/queue/rotational    # 1 — обертовий, 0 — ні
```

| файл | значення | наслідок |
|---|---|---|
| `write_cache` = `write back` | пристрій має власний енергозалежний кеш | ядро надсилає команди скидання; довговічність працює |
| `write_cache` = `write through` | ядро **вважає**, що пристрій підтверджує запис лише після носія | скидання не надсилаються зовсім |
| `fua` = `1` | драйвер уміє позначку «підтверди лише з носія» | окремий запит можна зробити довговічним без загального скидання |

Пастка тут у слові «вважає». Запис у `write_cache` змінює **погляд ядра**, а не стан самого пристрою: перевести значення з `write back` на `write through` означає просто перестати надсилати скидання, тимчасом як кеш на платі нікуди не подівся. З протилежного боку той самий ефект дають `hdparm -W 0 /dev/sda` для ATA й `sdparm --clear=WCE /dev/sdb` для SCSI — але ці вимикають кеш **у пристрої**, тож із ними довговічність зберігається, а падає швидкість.

## Важелі файлової системи: варіанти монтування

| варіант | ФС | дія |
|---|---|---|
| `barrier=0` (він же `nobarrier`) | ext4 | вимикає бар'єри в журналі, тобто скидання кешу пристрою. Типове значення — `barrier=1` |
| `barrier` / `nobarrier` | XFS | **прибрані** з ядра 4.19; на новому ядрі просто не існують, скидання завжди ввімкнені |
| `data=ordered` | ext4 | типове: дані виносяться на місце **до** того, як їхні метадані потраплять у журнал |
| `data=writeback` | ext4 | порядок не зберігається: після збою метадані можуть указувати на блоки зі старим або чужим умістом |
| `data=journal` | ext4 | дані теж ідуть через журнал (вимикає відкладене виділення й `O_DIRECT`) |
| `commit=N` | ext4 | максимальний вік поточної транзакції журналу, типово 5 с |
| `auto_da_alloc` | ext4 | типово ввімкнений: розпізнає підміну через `rename` чи `truncate` й проштовхує дані нового файлу перед фіксацією перейменування |
| `wsync` | XFS | усі операції над іменами виконуються синхронно: після повернення `create`/`unlink` зміна вже на стабільному носії |
| `sync` | будь-яка | кожен запис у кожен файл поводиться так, ніби файл відкрито з `O_SYNC` |
| `dirsync` | будь-яка | синхронними стають лише зміни каталогів |

`auto_da_alloc` варто читати уважно: це евристика, а не гарантія. Вона рятує саме той випадок, у якому програма зробила `rename` поверх наявного імені, не проштовхнувши даних, — але вона живе в конкретній файловій системі, вмикається конкретним варіантом монтування й нічого не обіцяє на іншій. Що саме журнал гарантує сам по собі, а що ні, — [журналювання й узгодженість після збою](book:unix-linux/journaling-consistency).

Ці варіанти вказують при монтуванні (`mount -o barrier=0 …`) або в `/etc/fstab`; чинний набір для змонтованого тому видно в `/proc/mounts` ([монтування й дерево монтувань](book:unix-linux/mount-model) — де саме живе цей набір і чому він належить монтуванню, а не файловій системі).

## Переносність за межі Linux

Формально `fsync` є всюди, але глибина його дії різна. На macOS `fsync()` доводить дані лише до пристрою й **не** замовляє скидання його кешу; для повної гарантії там потрібен `fcntl(fd, F_FULLFSYNC)`. Це не дрібниця для програм, які покладаються на однакову семантику на всіх системах, — і саме тому сховища зазвичай тримають окрему реалізацію «зробити довговічним» на кожну платформу, а не один виклик на всі.
