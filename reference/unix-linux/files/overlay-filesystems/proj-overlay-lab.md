# ⚙️ Лабораторія накладеного дерева: зібрати шари руками

Це заняття на пару годин: ми складемо накладення з двох звичайних образів ext4 і по черзі змусимо його показати кожен свій механізм — злиття імен, білило, непрозорий каталог, копіювання вгору, розрив жорсткого посилання, відмову `EXDEV` — не на слово, а числами, які надрукує написана тут же програма на C.

Побачити `c---------` у виводі `ls` легко — складніше зрозуміти, чому нічим іншим воно бути не могло; тому в кожному кроці за командою йде не лише результат, а й те, **що саме він доводить**.

Усе далі виконується від `root` у машині, яку не шкода: віртуалці, контейнері з повними правами, будь-якому тимчасовому Linux. Причина не в обережності — без [можливості](book:unix-linux/capabilities) `CAP_SYS_ADMIN` не змонтувати накладення в звичайному просторі імен і не прочитати службові атрибути в просторі `trusted`. Наприкінці є варіант для непривілейованого користувача, з якого частина спостережень усе-таки видима.

## Стенд, який не шкода

Спокуса зробити стенд із чотирьох каталогів у домівці велика, і саме вона псує половину результатів. Ми натомість візьмемо **два окремі образи файлових систем**, і на те є чотири причини, кожна з яких потім спрацює в конкретному кроці.

Нижній шар має бути справді доступним лише для читання — інакше нема чого доводити. `workdir` мусить лежати на тій самій файловій системі, що й `upperdir`: окремий образ це гарантує, а сусідня tmpfs дає нам чужу файлову систему для навмисної відмови. Шари на **різних** файлових системах — це нормальний випадок (образ контейнера внизу, диск вузла вгорі), і саме в ньому видно, що накладення робить із парою `st_dev`/`st_ino`. І нарешті, окремий образ можна розмонтувати — а з ним із кешу вилітають рівно його сторінки, не чіпаючи решту машини.

```sh
# нижній шар — свій образ, змонтований лише для читання
truncate -s 1G /var/tmp/ovl-lower.img
mkfs.ext4 -q /var/tmp/ovl-lower.img
mkdir -p /mnt/lower
mount -o loop /var/tmp/ovl-lower.img /mnt/lower

# верхній шар, робочий каталог і точка збірки — другий образ
truncate -s 2G /var/tmp/ovl-upper.img
mkfs.ext4 -q /var/tmp/ovl-upper.img
mkdir -p /mnt/lab
mount -o loop /var/tmp/ovl-upper.img /mnt/lab
mkdir /mnt/lab/upper /mnt/lab/work /mnt/lab/merged
```

Обидва образи стають файловими системами через петльовий пристрій — файл, який ядро подає нагору як [блоковий пристрій](book:unix-linux/block-device-model). Для накладення ця подробиця байдужа: воно однаково не знає, звідки взялися його каталоги.

Тепер наповнюємо нижній шар. Робимо це **до** монтування накладення й більше туди не лізтимемо:

```sh
cd /mnt/lower
printf 'нижній a\n' > a.txt
printf 'нижній b\n' > b.txt
printf 'нижній c\n' > c.txt
mkdir d && touch d/one d/two d/three
printf 'оригінал\n' > h1 && ln h1 h2          # одне тіло, два імені
mkdir moveme && touch moveme/f
head -c 512M /dev/urandom > big.bin           # для виміру ціни копіювання
cd / && mount -o remount,ro /mnt/lower
```

Випадкові байти в `big.bin` замість нулів — не примха: на файловій системі зі стисненням або дедуплікацією півгігабайта нулів коштували б підозріло дешево, і вимір збрехав би на порядок.

Один файл кладемо одразу у верхній шар, теж до монтування — він знадобиться, щоб побачити, як розв'язується збіг імен:

```sh
printf 'верхній b\n' > /mnt/lab/upper/b.txt
```

Далі — короткі імена й помічник, який ставить накладення заново з потрібними опціями. Кожен експеримент починатиметься з чистого верхнього шару, тож попередній не впливатиме на наступний:

```sh
L=/mnt/lower  U=/mnt/lab/upper  W=/mnt/lab/work  M=/mnt/lab/merged

fresh() {
  umount "$M" 2>/dev/null
  rm -rf "$U" "$W" && mkdir "$U" "$W"
  printf 'верхній b\n' > "$U/b.txt"
  mount -t overlay ovl-lab -o "lowerdir=$L,upperdir=$U,workdir=$W,$1" "$M"
}
```

Перший аргумент `mount` — `ovl-lab` — тут довільний рядок: блокового пристрою в накладення немає, і в поле, де в інших [монтувань](book:unix-linux/mount-model) стоїть розділ диска, можна написати будь-що. Воно з'явиться в `/proc/mounts`, тож давати експериментам різні імена зручно.

## Відмова, яку варто отримати навмисно

Перш ніж змонтувати як слід, зламаємо монтування свідомо — це найдешевший спосіб довести, що вимога до робочого каталогу не з примхи:

```sh
mkdir -p /dev/shm/w
mount -t overlay ovl-bad -o "lowerdir=$L,upperdir=$U,workdir=/dev/shm/w" "$M"
```

```
mount: /mnt/lab/merged: wrong fs type, bad option, bad superblock on ovl-bad,
       missing codepage or helper program, or other error.
```

Повідомлення не каже нічого — воно однакове для двадцяти різних причин. Справжня причина в журналі ядра:

```sh
dmesg | tail -3
```

```
overlayfs: workdir and upperdir must reside under the same mount
```

`/dev/shm` — це [tmpfs](book:unix-linux/pseudo-filesystems), тобто інша файлова система, ніж наш образ. Ядро перевіряє це першим ділом і відмовляється монтувати взагалі: копію файлу воно збирає в робочому каталозі й вставляє у верхній одним `rename`, а `rename` між файловими системами неможливий за визначенням. Перевірка на вході дешевша за помилку на першому ж копіюванні.

Запам'ятайте цю пару кроків: **`mount` мовчить, `dmesg` каже**. Далі половина ваших власних помилок розгадуватиметься саме так. (Новіші версії `util-linux` монтують через новий інтерфейс ядра й іноді друкують справжнє повідомлення одразу — але покладатися на це не варто.)

Тепер монтуємо по-справжньому, і всі три спірні опції задаємо явно:

```sh
fresh index=off,redirect_dir=off,metacopy=off
grep ovl-lab /proc/mounts
```

Явні `off` — не педантизм. Типові значення цих трьох опцій різні в різних збірках ядра, і саме звідси беруться «дивні» результати в чужих лабораторіях: у сусіда `rename` каталогу працює, у вас — ні. Подивіться на свої типові значення:

```sh
grep . /sys/module/overlay/parameters/*
```

Це параметри [модуля ядра](book:unix-linux/kernel-modules): вони задають, що станеться, коли опцію не вказано. Побачити їх один раз корисніше, ніж потім годину дивуватися.

## Один інструмент на весь день

Майже кожне твердження далі впирається в одну й ту саму пару чисел: **номер файлової системи й номер inode**. Це і є справжня тотожність файлу — те, чим користуються `rsync`, `make`, збирачі сміття й системи резервного копіювання, коли питають «це той самий файл?».

Напишемо помічник. Він міг би стояти на `stat`, але [`statx`](book:unix-linux/statx-extended-stat) зручніший саме тут: він одразу віддає старший і молодший номери окремими полями — і для файлової системи, і для файлу пристрою, а нам далі знадобиться саме друге.

```c
/* ovlstat.c — тотожність файлу: чия файлова система, який inode, скільки імен */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>

static const char *kind(unsigned mode)
{
    switch (mode & S_IFMT) {
    case S_IFREG: return "файл";
    case S_IFDIR: return "каталог";
    case S_IFCHR: return "симв.пристрій";
    case S_IFBLK: return "блок.пристрій";
    case S_IFLNK: return "символьне посилання";
    default:      return "інше";
    }
}

int main(int argc, char **argv)
{
    for (int i = 1; i < argc; i++) {
        struct statx sx;

        if (statx(AT_FDCWD, argv[i],
                  AT_SYMLINK_NOFOLLOW | AT_STATX_SYNC_AS_STAT,
                  STATX_TYPE | STATX_MODE | STATX_NLINK |
                  STATX_INO | STATX_SIZE, &sx) < 0) {
            printf("%-22s — %s\n", argv[i], strerror(errno));
            continue;
        }

        printf("%-22s fs=%u:%-3u ino=%-9llu nlink=%-2u %s",
               argv[i], sx.stx_dev_major, sx.stx_dev_minor,
               (unsigned long long)sx.stx_ino, sx.stx_nlink,
               kind(sx.stx_mode));

        if (S_ISCHR(sx.stx_mode) || S_ISBLK(sx.stx_mode))
            printf(" %u/%u", sx.stx_rdev_major, sx.stx_rdev_minor);
        else if (S_ISREG(sx.stx_mode))
            printf(" %llu Б", (unsigned long long)sx.stx_size);

        printf("\n");
    }
    return 0;
}
```

```sh
cc -O2 -o ovlstat ovlstat.c
```

Прапорець `AT_SYMLINK_NOFOLLOW` тут обов'язковий: нас цікавить сам об'єкт під іменем, а не те, куди він показує. Якщо в системі стара бібліотека C без обгортки `statx`, замініть виклик на звичайний `stat` і розберіть `st_dev` макросами `major()`/`minor()` з `<sys/sysmacros.h>` — сенс не зміниться.

## Імена зливаються, байти — ні

```sh
ls $M
cat $M/a.txt $M/b.txt
./ovlstat $M/a.txt $L/a.txt $M/b.txt $U/b.txt
```

```
a.txt  b.txt  big.bin  c.txt  d  h1  h2  moveme

нижній a
верхній b

/mnt/lab/merged/a.txt  fs=7:0   ino=13    nlink=1  файл 15 Б
/mnt/lower/a.txt       fs=7:0   ino=13    nlink=1  файл 15 Б
/mnt/lab/merged/b.txt  fs=7:1   ino=12    nlink=1  файл 17 Б
/mnt/lab/upper/b.txt   fs=7:1   ino=12    nlink=1  файл 17 Б
```

Спершу очевидне: `b.txt` існує в обох шарах, і крізь накладення видно верхній. Це не «злиття вмісту» — два набори байтів не поєднати нічим осмисленим, тож ядро просто обирає один. Зливаються **списки імен** каталогу, а не файли: у виводі `ls` є і те, що лежить унизу, і те, що лежить угорі.

А тепер те, заради чого ми писали `ovlstat`. Накладення не вигадує тотожності: воно віддає номери **того справжнього файлу, який зараз обслуговує ім'я**. Нижній `a.txt` звітує номерами нижнього образу (`7:0`), верхній `b.txt` — номерами верхнього (`7:1`). Тобто два файли в одному каталозі одного «носія» повідомляють різні файлові системи.

Тепер спитайте самі себе, що покаже каталог, у якому вони лежать:

```sh
./ovlstat $M $M/a.txt
```

```
/mnt/lab/merged        fs=0:47  ino=256   nlink=4  каталог
/mnt/lab/merged/a.txt  fs=7:0   ino=13    nlink=1  файл 15 Б
```

Каталог не може віддати номер жодного справжнього об'єкта — він зліплений з двох, — тому звітує **власним** номером накладення (`0:47`, безіменний пристрій). Виходить те, чого у звичайній файловій системі не буває ніколи: файл усередині каталогу лежить «на іншій файловій системі», ніж сам каталог. Утиліти, які саме за цією ознакою вирішують, чи перетнули межу монтування (`du -x`, `find -xdev`), у такому дереві поводяться несподівано. Полагодити це й покликаний режим `xino`: він домішує в номер inode ознаку шару й видає всім об'єктам один спільний `st_dev`. Змонтуйте з `fresh index=off,redirect_dir=off,xino=on` і повторіть обидві команди — числа зійдуться.

## Видалити те, чого не можна видалити

```sh
rm $L/c.txt
```

```
rm: cannot remove '/mnt/lower/c.txt': Read-only file system
```

Нижній шар справді недоторканий — це не домовленість, це файлова система, змонтована для читання. А тепер те саме крізь накладення:

```sh
rm $M/c.txt
cat $M/c.txt
ls -l $U/c.txt
./ovlstat $U/c.txt $L/c.txt
```

```
cat: /mnt/lab/merged/c.txt: No such file or directory
c--------- 1 root root 0, 0 серп  7 12:41 /mnt/lab/upper/c.txt

/mnt/lab/upper/c.txt   fs=7:1   ino=14  nlink=1  симв.пристрій 0/0
/mnt/lower/c.txt       fs=7:0   ino=15  nlink=1  файл 15 Б
```

Файл унизу цілий. Угорі під тим самим іменем з'явився **символьний пристрій із номерами 0/0** — і саме він змушує пошук імені зупинитися й відповісти «немає». Це білило.

Чому саме файл пристрою, видно з вимог. Позначку треба записати у звичайну ext4, яка не має поняття «відсутній запис»: у таблиці імен запис або є, або його немає. Отже, відсутність доводиться закодувати присутністю — а для цього потрібен об'єкт, яким **не буває жоден справжній файл**. Пристрою з [номерами](book:unix-linux/major-minor-numbers) 0/0 не існує й не може існувати, тож переплутати білило зі змістовним вмістом неможливо; при цьому воно не займає жодного блоку даних і переживає копіювання чи архівування шару.

Зверніть увагу: `ls -l` показує тип і пару `0, 0` на місці розміру, але саме `ovlstat` доводить це полем `stx_rdev` — тим, задля якого ми й брали `statx`. У новіших ядрах дозволена й друга форма білила — порожній звичайний файл з атрибутом `trusted.overlay.whiteout`; якщо ви побачите її, суть та сама.

## Каталог зникає інакше

Спершу приберемо з нижнього каталогу одне ім'я:

```sh
rm $M/d/one
ls $M/d
ls -l $U/d
getfattr -n trusted.overlay.opaque $U/d
```

```
two  three

total 0
c--------- 1 root root 0, 0 серп  7 12:44 one

/mnt/lab/upper/d: trusted.overlay.opaque: No such attribute
```

У верхньому шарі з'явився каталог `d` — порожній, якщо не рахувати білила для `one`. Він **зливається** з нижнім `d`: `two` і `three` далі видно знизу. Одне ім'я сховано, гілка ціла.

Тепер приберемо каталог цілком і створимо заново з тим самим іменем:

```sh
rm -r $M/d
./ovlstat $U/d                 # ← подивіться, чим став $U/d
mkdir $M/d && touch $M/d/новий
ls $M/d
ls $L/d
getfattr -n trusted.overlay.opaque $U/d
```

```
/mnt/lab/upper/d       fs=7:1   ino=16  nlink=1  симв.пристрій 0/0

новий
one  two  three
trusted.overlay.opaque="y"
```

Проміжний рядок вартий уваги окремо: після `rm -r` верхній `d` — таке саме білило, як для звичайного файлу. А от `mkdir` перетворює його на каталог із атрибутом `trusted.overlay.opaque="y"`, і атрибут означає «під мене не заглядай». Без нього крізь новий, майже порожній каталог просвічували б три чужі імені з нижнього шару — очевидна дурниця з погляду програми, яка щойно створила каталог з нуля.

Отже, інструменти різні й не взаємозамінні: **білило ховає одне ім'я, непрозорість обриває злиття цілої гілки**.

Дві пастки на цьому кроці. По-перше, `getfattr` без `-n` показує лише простір `user` — типовий шаблон імен у нього саме такий, тож `getfattr -d $U/d` чесно надрукує порожнечу. Або називайте атрибут повністю, або беріть `getfattr -d -m - $U/d`. По-друге, простір [`trusted`](book:unix-linux/acl-and-xattr) доступний лише процесу з `CAP_SYS_ADMIN`: під звичайним користувачем ви отримаєте не «немає атрибута», а «немає прав». Це навмисно — інакше будь-хто, маючи доступ до верхнього каталогу, підробив би службові позначки й змусив накладення показувати не те, що є.

## Копіювання вгору й підмінена тотожність

Найтонше спостереження всієї лабораторії робить коротка програма, яка нічого не пише. Вона лише **відкриває файл на запис** і засікає, скільки це коштувало:

```c
/* firstwrite.c — скільки коштує намір писати у файл нижнього шару */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

static double now(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv)
{
    if (argc < 2) { fprintf(stderr, "вжиток: firstwrite <шлях> [trunc]\n"); return 2; }

    int flags = O_WRONLY;
    if (argc > 2 && strcmp(argv[2], "trunc") == 0) flags |= O_TRUNC;

    struct stat st;
    if (stat(argv[1], &st) < 0) { perror("stat"); return 1; }

    double t0 = now();
    int fd = open(argv[1], flags);       /* жодного байта не записано */
    double t1 = now();
    if (fd < 0) { perror("open"); return 1; }
    close(fd);

    double mib = st.st_size / 1048576.0, dt = t1 - t0;
    printf("open(%s%s): %.6f с при розмірі %.1f МіБ",
           argv[1], (flags & O_TRUNC) ? ", O_TRUNC" : "", dt, mib);
    /* швидкість має сенс лише там, де копіювання справді сталося */
    if (mib >= 1.0 && dt > 0.01) printf("  (%.0f МіБ/с)", mib / dt);
    printf("\n");
    return 0;
}
```

`CLOCK_MONOTONIC` тут не випадковий: це [годинник](book:unix-linux/kernel-timekeeping), який ніхто не переводить назад, тож різниця двох його відліків завжди має сенс.

Спершу — про тотожність, на маленькому файлі:

```sh
fresh index=off,redirect_dir=off,metacopy=off
./ovlstat $M/a.txt
./firstwrite $M/a.txt
./ovlstat $M/a.txt $U/a.txt $L/a.txt
```

```
/mnt/lab/merged/a.txt  fs=7:0   ino=13    nlink=1  файл 15 Б
open(/mnt/lab/merged/a.txt): 0.000312 с при розмірі 0.0 МіБ

/mnt/lab/merged/a.txt  fs=7:1   ino=17    nlink=1  файл 15 Б
/mnt/lab/upper/a.txt   fs=7:1   ino=17    nlink=1  файл 15 Б
/mnt/lower/a.txt       fs=7:0   ino=13    nlink=1  файл 15 Б
```

Вміст не змінився ні на байт, ім'я те саме — а пара «файлова система + inode» уже інша. Копіювання вгору **підмінило файл іншим файлом, лишивши ім'я на місці**. Для програми, яка працює з іменами, підміна непомітна; для програми, яка звіряє тотожність числами, файл щойно замінили — і вона матиме рацію, бо об'єкт справді інший.

І сталося це від самого лише `open` із прапорцем на запис. Ядро не знає, скільки й куди програма писатиме, тож зобов'язане мати верхню копію ще до першого `write`.

## Скільки коштує перший запис

Тепер те саме на півгігабайті. Перед виміром треба скинути кеш сторінок — інакше ми виміряємо швидкість пам'яті, а не носія:

```sh
fresh index=off,redirect_dir=off,metacopy=off
sync; echo 3 > /proc/sys/vm/drop_caches
./firstwrite $M/big.bin
./firstwrite $M/big.bin
```

```
open(/mnt/lab/merged/big.bin): 4.812331 с при розмірі 512.0 МіБ  (106 МіБ/с)
open(/mnt/lab/merged/big.bin): 0.000041 с при розмірі 512.0 МіБ
```

**Умова: файл 512 МіБ у нижньому шарі, обидва образи на одному SSD, кеш скинуто.**

```
розмір файлу          = 512 МіБ = 5.369·10⁸ Б
перший open(O_WRONLY) = 4.812 с
дійсна швидкість      = 5.369·10⁸ / 4.812 ≈ 1.12·10⁸ Б/с ≈ 106 МіБ/с
другий open(O_WRONLY) = 0.000041 с
записано програмою    = 0 байтів
```

Виклик, який зазвичай коштує мікросекунди, коштував майже п'ять секунд, і за цей час не записано жодного корисного байта. Це не патологія, а точний наслідок конструкції: щоб мати право змінити файл, треба спершу мати його копію. Другий рядок показує другу половину правди — ціна платиться **один раз**, далі файл уже вгорі.

Число включає не лише читання й запис, а й скидання копії на носій: ядро робить `fsync` перед тим, як вставити готову копію у верхній шар, інакше після збою там лишилося б ім'я без вмісту ([кеш сторінок, fsync і довговічність](book:unix-linux/page-cache-durability)). Тому виміряне — справді про диск.

Запис `echo 3 > /proc/sys/vm/drop_caches` — груба сокира: він скидає кеш усієї машини. Значення `1` обмежується кешем сторінок, а хірургічний спосіб — розмонтувати нижній образ і змонтувати знову: сторінки файлової системи викидаються разом із нею. Обидва шляхи ведуть до одного: **вимір без скинутого кешу вимірює пам'ять** ([буферований і прямий ввід-вивід](book:unix-linux/buffered-and-direct-io), [керування ядром через sysctl](book:unix-linux/sysctl-tunables)).

Тепер перевірмо здогад. Якщо файл відкривають із `O_TRUNC`, його вміст однаково зникає — виходить, копіювати нема чого:

```sh
fresh index=off,redirect_dir=off,metacopy=off
sync; echo 3 > /proc/sys/vm/drop_caches
./firstwrite $M/big.bin trunc
```

```
open(/mnt/lab/merged/big.bin, O_TRUNC): 0.000229 с при розмірі 512.0 МіБ
```

Ядро цю можливість справді використовує: копію створює порожньою, бо розмір заздалегідь відомий і дорівнює нулю. П'ять секунд перетворилися на чверть мілісекунди — і це практична порада, а не курйоз: програма, що перезаписує файл цілком, має відкривати його з `O_TRUNC`, а не дописувати в кінець після ручного очищення.

Той самий рід економії дає режим `metacopy=on` (змінюємо лише права чи власника — угорі створюється порожня оболонка, дані лишаються внизу) і [копії з поділом блоків](book:unix-linux/reflink-copies), коли обидва шари на одній файловій системі, що це вміє.

## Жорстке посилання, яке рветься

У нижньому шарі є `h1` і `h2` — [два імені одного тіла](book:unix-linux/hard-and-symbolic-links). Лічильник імен живе в самому inode, тож обидва звітують `nlink=2`.

```sh
fresh index=off,redirect_dir=off,metacopy=off
./ovlstat $M/h1 $M/h2
printf 'змінено\n' >> $M/h1
./ovlstat $M/h1 $M/h2
cat $M/h2
```

```
/mnt/lab/merged/h1     fs=7:0   ino=18    nlink=2  файл 17 Б
/mnt/lab/merged/h2     fs=7:0   ino=18    nlink=2  файл 17 Б

/mnt/lab/merged/h1     fs=7:1   ino=19    nlink=1  файл 32 Б
/mnt/lab/merged/h2     fs=7:0   ino=18    nlink=2  файл 17 Б
оригінал
```

Копіювання вгору забрало нагору **ім'я**, а не тіло. Друге ім'я лишилося на старому inode, і два імені, які були одним файлом, стали двома різними файлами. Саме те, чого жорстке посилання обіцяло не допускати.

Тепер увімкнемо покажчик:

```sh
fresh index=on,redirect_dir=off,metacopy=off
dmesg | tail -2                     # чи не відмовився index мовчки
printf 'змінено\n' >> $M/h1
./ovlstat $M/h1 $M/h2
cat $M/h2
ls $W/index/
```

```
/mnt/lab/merged/h1     fs=7:1   ino=20    nlink=2  файл 32 Б
/mnt/lab/merged/h2     fs=7:1   ino=20    nlink=2  файл 32 Б
оригінал
змінено
00000000f8010000cb...
```

Обидва імені знову ведуть на один об'єкт — цього разу на верхню копію. Механізм видно в останньому рядку: при копіюванні вгору ядро завело в робочому каталозі запис, названий за **дескриптором нижнього файлу**, і цей запис сам є жорстким посиланням на верхню копію. Коли пошук доходить до `h2`, він знаходить унизу той самий нижній inode, обчислює той самий дескриптор, знаходить за ним запис у покажчику — і бере вже готову копію замість того, щоб робити другу.

![Три стани: одне нижнє тіло на два імені; після копіювання без покажчика тіла роз'їхалися; з покажчиком обидва імені ведуть на ту саму верхню копію](/reference/unix-linux/files/overlay-filesystems/img/hardlink-index.svg)

*Запис у покажчику названий за дескриптором нижнього файлу й сам є жорстким посиланням на копію — тому друге ім'я знаходить її, а не робить свою.*

Порахуйте посилання з двох боків — і ви побачите, чого ця латка коштує зсередини:

```sh
./ovlstat $M/h1 $U/h1
getfattr -n trusted.overlay.nlink $U/h1
```

Число `nlink` у справжнього верхнього inode може бути **більшим**, ніж те, що накладення показує програмам: сам запис у покажчику — теж ім'я, і ext4 його чесно рахує. Програмі ж треба знати кількість імен, які вона може побачити. Різницю overlayfs зберігає окремим атрибутом `trusted.overlay.nlink` — короткий рядок на кшталт `U-1`: літера каже, від чийого лічильника відштовхуватися, число — поправка.

Звідси й головна ціна режиму: у робочому каталозі накопичується стан, прив'язаний саме до цих нижніх шарів. Поміняли нижній шар — дескриптори в покажчику показують у порожнечу.

> 🔧 **Навіщо це.** Розрив жорстких посилань виглядає академічною дрібницею, доки під накладенням не опиниться сховище пакунків, що економить місце саме ними: у Nix і pnpm однакові файли різних версій — це одне тіло під багатьма іменами. Без `index=on` перший же запис у такий файл тихо роздвоює його, і замість економії ви отримуєте копію на кожне ім'я.

## Каталог, якому нема куди перейменуватися

Остання відмова — найчесніша з усіх. Її теж треба побачити на рівні виклику, а не команди, бо `mv` її від вас сховає:

```c
/* tryrename.c — що саме повертає rename(), а не що з цього робить mv */
#include <errno.h>
#include <stdio.h>
#include <string.h>

int main(int argc, char **argv)
{
    if (argc != 3) { fprintf(stderr, "вжиток: tryrename <з> <на>\n"); return 2; }

    if (rename(argv[1], argv[2]) == 0) { puts("rename() успішний"); return 0; }

    printf("rename() відмовив: %s (errno=%d)\n", strerror(errno), errno);
    return 1;
}
```

```sh
cc -O2 -o tryrename tryrename.c
fresh index=off,redirect_dir=off,metacopy=off
./tryrename $M/moveme $M/moved
mv $M/moveme $M/moved && ls $M/moved
```

```
rename() відмовив: Invalid cross-device link (errno=18)
f
```

Виклик відмовив, а команда спрацювала. Це не суперечність, а вся суть відповіді: `EXDEV` означає «це різні файлові системи, перенеси сам», і кожна пристойна утиліта вміє на нього відповісти копіюванням із наступним видаленням. Переконайтеся власними очима:

```sh
fresh index=off,redirect_dir=off,metacopy=off
strace -f -e trace=rename,renameat,renameat2 mv $M/moveme $M/moved 2>&1 | head -3
```

У [трасуванні](book:unix-linux/syscall-tracing) видно ту саму відмову, після якої `mv` мовчки переходить на обхідний шлях.

Чому ядро взагалі відмовляється? Каталог `moveme` фізично лежить унизу, і чесне перейменування означало б скопіювати нагору весь його вміст — для каталогу з тисячею файлів `mv` перетворилася б на багатохвилинне копіювання, сховане за операцією, яку всі вважають миттєвою. Ядро радше скаже правду.

Другий вихід — знову позначка:

```sh
fresh index=off,redirect_dir=on,metacopy=off
./tryrename $M/moveme $M/moved
getfattr -n trusted.overlay.redirect $U/moved
ls $M/moved
```

```
rename() успішний
trusted.overlay.redirect="moveme"
f
```

Угорі створено новий порожній каталог із атрибутом, що каже: «шукаючи в мені, дивись унизу за старою назвою». Тисяча файлів лишилася на місці, перейменування коштувало один запис. Значення атрибута — старе ім'я, якщо каталог лишився в тому самому батьківському каталозі, або повний шлях від кореня накладення, якщо він переїхав. І ціна та сама, що в покажчика: верхній шар більше не самодостатній, бо тримає посилання на конкретні шляхи в конкретних нижніх шарах.

## Пастки, на яких лабораторія ламається

**`mount` мовчить — читайте `dmesg`.** Одне безлике повідомлення накриває двадцять різних причин; справжня — у журналі ядра.

**Робочий каталог — на тій самій файловій системі, що й верхній.** І не всередині верхнього, і верхній не всередині нижнього. Усі ці випадки ядро відкидає на вході.

**Типові значення `index`, `redirect_dir`, `metacopy` різні в різних збірках.** Задавайте явно все, що впливає на експеримент, і звіряйтеся з `/sys/module/overlay/parameters/`. Половина «нездійсненних» результатів — саме звідси.

**`trusted.*` не видно без `-n` і без прав.** `getfattr -d` показує лише простір `user`; читати `trusted` може лише `CAP_SYS_ADMIN`.

**Не чіпайте шари, поки накладення змонтоване — жодні.** Наш нижній шар змонтований лише для читання й від спокуси захищений сам, а от створити файл прямо в `$U` при змонтованому `$M` не заважає ніщо. Спробуйте — і не робіть висновку з того, що побачите в `$M`: ядро кешує зведені списки імен і не стежить за чужими змінами під собою, тож результат тут не визначений, а не «працює». І окремо: якщо ввімкнено `index`, `redirect_dir`, `metacopy` чи `xino`, то навіть зміни нижнього шару в розмонтованому стані ламають накопичені посилання.

**Вимір без скинутого кешу — вимір пам'яті.** І навпаки: скидати кеш перед кожним із десятка вимірів на робочій машині — надійний спосіб зіпсувати всім день.

**Нижній шар на tmpfs погано дружить з `index=on`.** Покажчик спирається на дескриптори файлів і сталий ідентифікатор файлової системи; там, де їх нема, ядро може мовчки повернутися до `index=off` — з попередженням у `dmesg` і без жодної ознаки в `/proc/mounts`. Для лабораторії беріть звичайну дискову файлову систему, як ми й зробили.

## Те саме без прав root

Якщо доступу до `root` немає, більшу частину спостережень усе одно можна відтворити — у [просторі імен користувача](book:unix-linux/namespaces), де ядро дозволяє монтувати накладення з версії 5.11:

```sh
mkdir -p ~/ovl/{lower,upper,work,merged}
printf 'нижній a\n' > ~/ovl/lower/a.txt
unshare --user --map-root-user --mount        # далі — вже в новому просторі імен

cd ~/ovl
mount -t overlay ovl-lab \
      -o lowerdir=lower,upperdir=upper,workdir=work,userxattr merged
```

Ключ тут — `userxattr`: службові позначки переїжджають із `trusted.overlay.*` у `user.overlay.*`, доступний власникові файлу. Отже, і дивитися треба інакше: `getfattr -n user.overlay.opaque`. Петльові образи в такому просторі не змонтувати, тож шари доведеться класти в одну файлову систему — а з нею зникнуть спостереження, що спираються на різні `st_dev`. Усе інше — білило, непрозорість, копіювання вгору, `EXDEV` — лишається на місці.

## Прибирання

```sh
umount /mnt/lab/merged
umount /mnt/lower
umount /mnt/lab
rm -f /var/tmp/ovl-lower.img /var/tmp/ovl-upper.img
```

Порядок має значення: накладення тримає обидва шари, тож знімати треба згори вниз. Якщо `umount` каже «device is busy», хтось із ваших терміналів стоїть каталогом усередині — `lsof +D /mnt/lab` покаже, хто саме.
