# 📋 Інтерфейс та структура даних подій дозволу fanotify

Ця вставка є вичерпним довідником зі системних викликів, констант, бітових масок і структур даних, які використовуються при розробці систем перехоплення подій дозволу у ядрі Linux за допомогою підсистеми fanotify. Вона систематизує прапорці ініціалізації, формати метаданих подій і відповідей, детально пояснює правила взаємодії між ядром та користувацьким простором, висвітлює нюанси вирівнювання пам'яті, а також описує коди помилок, які повертає ядро під час міжпроцесного обміну.

## Системні виклики підсистеми та порядок їхнього застосування

Основна взаємодія з підсистемою fanotify здійснюється через два спеціалізовані системні виклики та стандартні інструменти файлового введення-виведення (`read()`, `write()`, `close()`, `poll()`, `epoll`). 

Процес реєстрації демона моніторингу починається зі створення групи fanotify за допомогою системного виклику `fanotify_init()`. Після отримання файлового дескриптора демон налаштовує мітки на потрібних точках монтування або конкретних каталогах за допомогою виклику `fanotify_mark()`. Наліплені мітки вказують VFS, які саме операції над файлами слід зупиняти та передавати у чергу подій.

### 1. `fanotify_init()`

Створює новий файловий дескриптор fanotify та налаштовує чергу подій для поточного процесу.

:::tabs
```c
#include <sys/fanotify.h>

int fanotify_init(unsigned int flags, unsigned int event_f_flags);
```
```cpp
#include <sys/fanotify.h>
#include <cstdint>

extern "C" int fanotify_init(unsigned int flags, unsigned int event_f_flags);
```
:::

Аргумент `flags` визначає клас підписника та поведінку самого дескриптора. Для роботи з подіями дозволу вкрай важливо правильно обрати клас підписки, оскільки ядро Linux обробляє класи у суворо визначеному порядку пріоритету. Якщо у системі зареєстровано кілька демонів різного класу, ядро спочатку викликає демони класу `FAN_CLASS_PRE_CONTENT`, а після отримання їхнього вердикту `FAN_ALLOW` передає подію демонам класу `FAN_CLASS_CONTENT`.

Аргумент `event_f_flags` задає прапорці стану файлу, з якими ядро створюватиме анонімні файлові дескриптори для демона у момент виникнення події. Наприклад, передача прапорців `O_RDONLY | O_CLOEXEC` гарантує, що демон зможе читати вміст заблокованого файлу для сканування, а сам дескриптор не успадкується дочірніми процесами при виклику `execve()`.

#### Детальний розбір прапорців `flags` для `fanotify_init()`

- **`FAN_CLASS_CONTENT`**: Реєструє підписника класу перевірки вмісту. Дозволяє отримати та обробляти синхронні події `FAN_OPEN_PERM`, `FAN_ACCESS_PERM`, `FAN_OPEN_EXEC_PERM`. Призначений для антивірусних сканерів та систем DLP.
- **`FAN_CLASS_PRE_CONTENT`**: Реєструє підписника найвищого пріоритету для HSM (Hierarchical Storage Management) та завантаження файлів на вимогу. Отримує події дозволу раніше за клас `FAN_CLASS_CONTENT`.
- **`FAN_CLASS_NOTIF`**: Стандартний клас суто асинхронних сповіщень (за замовчуванням). Не підтримує перехоплення та синхронне блокування подій дозволу.
- **`FAN_CLOEXEC`**: Встановлює прапорець `FD_CLOEXEC` на створеному дескрипторі fanotify для автоматичного закриття дескриптора моніторингу при виклику `execve()`.
- **`FAN_NONBLOCK`**: Встановлює неблокуючий режим читання з файлового дескриптора fanotify (`O_NONBLOCK`). Рекомендовано для асинхронних циклів подій на основі `epoll`.
- **`FAN_UNIFORM_PIDS`**: Примушує ядро завжди повідомляти справжні PID процесів у глобальному просторі імен ідентифікаторів, що є критичним при моніторингу всередині ізольованих контейнерів Docker або Kubernetes.
- **`FAN_REPORT_FID`**: Вмикає звітування ідентифікаторів `file_handle` замість відкритих файлових дескрипторів (потребує Linux 5.1+). Використовується для моніторингу файлових систем без відкриття зайвих файлових дескрипторів.
- **`FAN_REPORT_DIR_FID`**: Модифікатор для `FAN_REPORT_FID`, який примушує ядро передавати ідентифікатор батьківського каталогу для подій, що відбуваються над елементами каталогу.
- **`FAN_REPORT_NAME`**: Прапорець, який примушує ядро передавати ім'я файлу у хвості метаданих події разом із ідентифікатором батьківського каталогу `file_handle`.

### 2. `fanotify_mark()`

Додає, видаляє або змінює мітки моніторингу на об'єктах файлової системи.

:::tabs
```c
#include <sys/fanotify.h>

int fanotify_mark(int fanotify_fd, unsigned int flags,
                  uint64_t mask, int dirfd, const char *pathname);
```
```cpp
#include <sys/fanotify.h>
#include <cstdint>

extern "C" int fanotify_mark(int fanotify_fd, unsigned int flags,
                             std::uint64_t mask, int dirfd, const char *pathname);
```
:::

Системний виклик `fanotify_mark()` пов'язує створену fanotify-групу з конкретною точкою монтування або окремим файловим inode. Аргумент `dirfd` та `pathname` задають цільовий об'єкт. Якщо `pathname` є відносним шляхом, він розраховується відносно каталогу `dirfd` (або поточної робочої директорії при `AT_FDCWD`).

#### Детальний розбір прапорців дій `flags` для `fanotify_mark()`

- **`FAN_MARK_ADD`**: Додати нові події з маски `mask` до існуючої мітки об'єкта.
- **`FAN_MARK_REMOVE`**: Видалити вказані події з маски `mask` з мітки об'єкта.
- **`FAN_MARK_FLUSH`**: Очистити та видалити абсолютно всі мітки з даної fanotify-групи. Аргументи `dirfd` та `pathname` при цьому ігноруються.
- **`FAN_MARK_INODE`**: Поставити мітку безпосередньо на конкретний `inode` (окремий файл або каталог). Події відслідковуються лише для цього конкретного об'єкта.
- **`FAN_MARK_MOUNT`**: Поставити мітку на весь точковий монт (`mount point`). Перехоплюються події з усіх файлів та підкаталогів даного монтування, навіть якщо нові файли додаються динамічно.
- **`FAN_MARK_FILESYSTEM`**: Поставити мітку на усю файлову систему (навіть якщо вона змонтована у кількох різних точках дерева імен, додано у Linux 4.20).
- **`FAN_MARK_IGNORED_MASK`**: Додати маску ігнорованих подій для даного об'єкта. Використовується для виключення операцій самого демона безпеки з загального потоку перехоплення.
- **`FAN_MARK_IGNORED_SURV_MODIFY`**: Вказує ядру, що маска ігнорування повинна зберігатися навіть після того, як об'єкт моніторингу буде модифікований операцією запису.

## Маски подій дозволу (`mask`)

При налаштуванні перехоплення синхронних подій у виклику `fanotify_mark()` використовуються такі бітові маски:

- **`FAN_OPEN_PERM`**: Синхронний запит на відкриття файлу. Викликається всередині `do_dentry_open()` під час системних викликів `open()`, `openat()`, `creat()`. Потік процесу блокується до отримання відповіді.
- **`FAN_ACCESS_PERM`**: Синхронний запит на читання вмісту. Викликається всередині `rw_verify_area()` при системних викликах `read()`, `readv()`, `pread()`. Дозволяє перехоплювати операції читання вже відкритого файлу.
- **`FAN_OPEN_EXEC_PERM`**: Синхронний запит на відкриття бінарного виконуваного файлу або динамічної бібліотеки для виконання (додано у Linux 5.0). Викликається при викликах `execve()`, `execveat()`, `uselib()`. Дозволяє перевіряти підписи виконуваного коду до його завантаження в оперативну пам'ять.

## Структури даних міжпроцесного обміну

### 1. Метадані події (`struct fanotify_event_metadata`)

При виклику `read()` з файлового дескриптора fanotify ядро повертає один або кілька послідовних бінарних блоків такої структури. Буфер у користувацькому просторі повинен бути вирівняний по межі `struct fanotify_event_metadata`:

:::tabs
```c
#include <sys/fanotify.h>

struct fanotify_event_metadata {
    uint32_t event_len;      /* Загальна довжина даного запису в байтах */
    uint8_t  vers;           /* Версія структури (поточна FANOTIFY_METADATA_VERSION) */
    uint8_t  reserved;       /* Зарезервовано ядрами Linux */
    uint16_t metadata_len;   /* Довжина фіксованої частини метаданих */
    uint64_t mask;           /* Бітова маска події (наприклад, FAN_OPEN_PERM) */
    int32_t  fd;             /* Відкритий анонімний дескриптор файлу АБО FAN_NOFD */
    int32_t  pid;            /* PID процесу, який викликав операцію VFS */
};
```
```cpp
#include <sys/fanotify.h>
#include <cstdint>

struct fanotify_event_metadata {
    std::uint32_t event_len;      // Загальна довжина запису в байтах
    std::uint8_t  vers;           // Версія структури
    std::uint8_t  reserved;       // Зарезервовано ядром
    std::uint16_t metadata_len;   // Довжина фіксованої частини метаданих
    std::uint64_t mask;           // Бітова маска події (FAN_OPEN_PERM)
    std::int32_t  fd;             // Відкритий анонімний дескриптор файлу або FAN_NOFD
    std::int32_t  pid;            // PID процесу, який викликав операцію VFS
};
```
:::

Кожна подія дозволу повертає відкритий файловий дескриптор `fd`. Цей дескриптор надає демону доступ до сканування вмісту заблокованого файлу. Демон безпеки зобов'язаний закрити цей `fd` за допомогою виклику `close()` одразу після надсилання відповіді ядру, інакше у системі виникне витік файлових дескрипторів.

Для ітерації по буферу подій розробник повинен використовувати макроси ядра:
- **`FAN_EVENT_OK(meta, len)`**: Перевіряє, чи залишилося достатньо байтів у буфері для читання наступної структури метаданих.
- **`FAN_EVENT_NEXT(meta, len)`**: Переходить до наступного запису у буфері, зменшуючи залишок довжини `len` на розмір прочитаного запису `meta->event_len`.

### 2. Структура відповіді (`struct fanotify_response`)

Для передачі рішення ядру демон безпеки записує у файловий дескриптор fanotify за допомогою виклику `write()` таку структуру:

:::tabs
```c
#include <sys/fanotify.h>

struct fanotify_response {
    int32_t  fd;         /* Дескриптор файлу з fanotify_event_metadata.fd */
    uint32_t response;   /* Значення вердикту: FAN_ALLOW або FAN_DENY */
};
```
```cpp
#include <sys/fanotify.h>
#include <cstdint>

struct fanotify_response {
    std::int32_t  fd;         // Дескриптор файлу з fanotify_event_metadata.fd
    std::uint32_t response;   // Значення вердикту: FAN_ALLOW або FAN_DENY
};
```
:::

#### Значення поля `response` та їхній вплив на системні виклики

- **`FAN_ALLOW`**: Надати дозвіл. Ядро розблоковує прикладний потік, VFS успішно завершує системний виклик `open()` і повертає створившийся файловий дескриптор програмі.
- **`FAN_DENY`**: Заборонити дозвіл. Ядро розблоковує потік, негайно скасовує операцію VFS і повертає прикладній програмі помилку **`-EPERM`** (Operation not permitted).
- **`FAN_AUDIT`**: Додаткова бітова маска, яка сполучається з `FAN_DENY` або `FAN_ALLOW` для генерації системного запису в журналі аудіосистеми Linux Audit (`auditd`).

## Коди помилок системних викликів (`errno`)

При роботі з подійним моніторингом fanotify розробник може зіштовхнутися з такими кодами помилок у системній змінній `errno`:

- **`EPERM`**: 1) Виклик `fanotify_init()` виконано без привілеїв `CAP_SYS_ADMIN`. 2) Операція прикладного процесу заблокована демоном через відповідь `FAN_DENY`.
- **`EINVAL`**: Передано недійсну бітову маску подій, непідтримуваний клас чи недійсний прапорець у `fanotify_init()` або `fanotify_mark()`.
- **`EMFILE`**: Досягнуто ліміту відкритості файлових дескрипторів у процесі або в загальній системній таблиці файлів.
- **`ENOMEM`**: Недостатньо оперативної пам'яті ядра для виділення внутрішньої черги подій fanotify.
- **`EBUSY`**: Спроба зняти мітку з об'єкта, який наразі заблокований або використовується іншою внутрішньою операцією ядра.
- **`ETXTBSY`**: Спроба відкрити для запису бінарний виконуваний файл, який прямо зараз виконується іншим процесом у системі.
- **`ENOTDIR`**: Передано прапорець `FAN_MARK_ONLYDIR`, але вказаний шлях не є каталогом.
- **`ENOENT`**: Переданий шлях до файлу або каталогу не існує у файловій системі.
