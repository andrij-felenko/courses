# 📋 Контракт `stat` і `statx`: усе, що система каже про файл

Ця вставка пояснює 📋 контракт `stat` і `statx`: усе, що система каже про файл та дозволяє зрозуміти її детальніше. Це довідник по єдиному вікну, крізь яке простір користувача бачить inode: `struct stat` поле за полем — що з цього справді лежить на носії, а що ядро вигадує на льоту; чотири виклики, які цю структуру заповнюють; і `statx`, у якому ядро вперше почало відповідати чесно — «ось що я насправді знаю про цей файл».

## `struct stat`: поля

```c
struct stat {
    dev_t     st_dev;      /* пристрій, на якому лежить файл */
    ino_t     st_ino;      /* номер inode */
    mode_t    st_mode;     /* тип файлу + біти прав */
    nlink_t   st_nlink;    /* скільки жорстких посилань */
    uid_t     st_uid;      /* власник */
    gid_t     st_gid;      /* група */
    dev_t     st_rdev;     /* номер пристрою — якщо сам файл є пристроєм */
    off_t     st_size;     /* розмір у байтах */
    blksize_t st_blksize;  /* бажаний розмір порції вводу-виводу */
    blkcnt_t  st_blocks;   /* зайнято 512-байтових блоків */

    struct timespec st_atim;  /* останнє читання вмісту */
    struct timespec st_mtim;  /* остання зміна вмісту */
    struct timespec st_ctim;  /* остання зміна самого inode */
};
```

`st_atime`, `st_mtime` й `st_ctime` — не окремі поля, а макроси, розкриті в `st_atim.tv_sec`. Наносекунди доступні лише через довгу форму (`st_mtim.tv_nsec`), і не всяка файлова система їх тримає: ext2 та ext3 округляли до секунди, ext4, XFS, Btrfs і JFS — ні. Порядок і кількість полів у структурі не є частиною контракту: між платформами вони різні, між версіями libc міняються, тому звертатися можна тільки за іменами, а ініціалізувати за позиціями — ніколи.

Тепер по кожному полю окремо: звідки береться значення і де в ньому пастка.

| поле | звідки береться | що варто знати |
|---|---|---|
| `st_dev` | **не з inode**: ядро видає номер змонтованому екземпляру файлової системи | у пари з `st_ino` це тотожність файлу; для псевдо- й мережевих ФС номер анонімний (старший = 0), бо носія немає |
| `st_ino` | з inode — для ext-родини це буквально індекс у таблиці | для FAT драйвер його **вигадує** з місця запису каталогу; на NFS клієнт дістає його з відповіді сервера |
| `st_mode` | з inode | тип і права в одному числі, розкладка нижче |
| `st_nlink` | з inode | для каталогу це `2 + кількість підкаталогів` (він сам, ім'я в батька і `..` кожного нащадка); Btrfs завжди пише туди `1`, ext4 — коли підкаталогів понад 65000, і `1` тут означає «не рахую» |
| `st_uid`, `st_gid` | з inode | числа, а не імена; у просторі імен користувачів і на idmapped-монтуваннях ядро **перекладає** їх на льоту, тож із різних контекстів той самий файл має різних власників |
| `st_rdev` | з inode, замість карти блоків | має сенс лише для `S_IFCHR` і `S_IFBLK`, для решти в ньому сміття або нуль |
| `st_size` | з inode | для звичайного файлу — байти; для символьного посилання — довжина цільового шляху; для каталогу — число без корисного змісту |
| `st_blksize` | **не з inode**: підказка драйвера | не розмір блока ФС, а «якими порціями зі мною зручно працювати» |
| `st_blocks` | з inode | завжди в одиницях по 512 байтів, незалежно ні від чого |
| часи | з inode | їх три, і жоден із них не є часом створення |

Ще одна річ, яку контракт каже мовчанням: **`stat` не вимагає права читати файл**. Достатньо права проходу (`x`) на кожному каталозі шляху — і ви дізнаєтеся розмір, власника й часи файлу, вміст якого вам недоступний. Це навмисно й це давня властивість [бітів прав](book:unix-linux/permission-bits): права стосуються вмісту, метадані відкриті всім, хто дійшов до імені.

## `st_mode`: тип і права в одному числі

![Смуга з шістнадцяти пронумерованих бітів st_mode. Перші чотири біти згори підписано як тип файлу, наступні три як особливі біти, останні дев'ять як права доступу. Під кожною групою рамка з поясненням: маска S_IFMT дорівнює 0170000 і перевірка лише макросами S_ISREG, S_ISDIR, S_ISLNK; вісімкові значення S_ISUID 04000, S_ISGID 02000, S_ISVTX 01000; три трійки rwx для власника, групи й решти з маскою 00777. Унизу приклад: значення 0100644 — звичайний файл із правами rw-r--r--](/reference/unix-linux/files/inode-model/img/stat-mode-bits.svg)

*Одне ціле число несе три різні речі. Верхні чотири біти — тип, він з'ясовується один раз і потім не міняється ніколи; далі три особливі біти; далі дев'ять бітів прав, і саме ці дванадцять молодших ставить `chmod`.*

| макрос типу | вісімково | що це |
|---|---|---|
| `S_IFSOCK` | `0140000` | сокет |
| `S_IFLNK` | `0120000` | символьне посилання |
| `S_IFREG` | `0100000` | звичайний файл |
| `S_IFBLK` | `0060000` | блоковий пристрій |
| `S_IFDIR` | `0040000` | каталог |
| `S_IFCHR` | `0020000` | символьний пристрій |
| `S_IFIFO` | `0010000` | іменований канал |

**Тип — не набір прапорців, а число в чотирьох бітах**, і це найчастіша помилка новачка в цьому інтерфейсі. Перевірка `st_mode & S_IFDIR` виглядає природно й дає правду для каталогу — але так само дає правду для блокового пристрою (`0060000`) і для сокета (`0140000`), бо їхні комбінації бітів містять біт каталогу. Єдина правильна форма — рівність із виділеною маскою або відповідний макрос:

```c
if ((st.st_mode & S_IFMT) == S_IFREG)  /* правильно */
if (S_ISREG(st.st_mode))               /* те саме, коротше */
if (st.st_mode & S_IFREG)              /* ПОМИЛКА: спрацює й на сокеті */
```

Молодші дванадцять бітів — те, що ставить `chmod`: `S_ISUID` (`04000`), `S_ISGID` (`02000`), `S_ISVTX` (`01000`), далі три трійки `rwx` — `S_IRWXU` (`00700`), `S_IRWXG` (`00070`), `S_IRWXO` (`00007`). Значення особливих бітів залежить від типу файлу: на виконуваному файлі `S_ISUID` [піднімає запущений процес до власника файлу](book:unix-linux/setuid-and-privilege), на каталозі `S_ISGID` задає групу для новостворених у ньому файлів, а `S_ISVTX` на каталозі — це «липкий біт» `/tmp`, який дозволяє прибирати звідти лише власні файли.

## Розмір і зайняте — два незалежні числа

`st_blocks` **завжди** рахує блоки по 512 байтів, хоч би яким був розмір блока файлової системи. Це не логіка, а історія, вмерзла в двійковий інтерфейс: поле прийшло з BSD, де стала `DEV_BSIZE` дорівнювала 512, а супровідного поля «а в яких я одиницях» до структури не додали. POSIX цю одиницю взагалі не визначає й лишає її на реалізацію — Linux фіксує 512, і покладатися на це можна. Обчислення завжди одне:

```
зайнято байтів = st_blocks × 512
```

GNU `stat` показує обидві половини роздільно: `%b` друкує лічильник, а `%B` — розмір одиниці, і на Linux це незмінно `512`, навіть коли ФС оперує блоками по 4096.

Розходитися з `st_size` це число може в обидва боки, і обидва — законні.

| співвідношення | причина |
|---|---|
| `st_blocks × 512` **менше** за `st_size` | [розріджений файл](book:unix-linux/sparse-files): в областей-дір блоків просто не виділено; або дрібний файл, чиї байти ФС уклала прямо в inode |
| `st_blocks × 512` **більше** за `st_size` | службові блоки самої карти адрес також зараховано; попереднє резервування через `fallocate`; хвостовий блок, зайнятий цілком заради кількох байтів |

`st_blksize` до цієї арифметики стосунку не має. Це не розмір блока носія й не одиниця обліку, а підказка «якими порціями зі мною вигідно розмовляти»: `stdio` у glibc бере саме її, коли відводить свій буфер під потік, а на NFS вона дорівнює узгодженим `rsize`/`wsize`, тобто розміру мережевої порції, а не розміру блока на сервері.

Окремо про розмір символьного посилання: `st_size` дорівнює довжині шляху-цілі **без** завершального нуля, і це спокуса відвести під `readlink` рівно стільки байтів. Спокуса небезпечна двічі: посилання могли підмінити між викликами, а на псевдофайлових системах на кшталт `/proc` розмір узагалі повідомляється нульовим. Робочий спосіб — буфер, що подвоюється, доки `readlink` повертає рівно стільки, скільки в нього влізло.

## Часи: їх три, і жоден не «створено»

| поле | що позначає | що його рухає |
|---|---|---|
| `st_atim` | останній доступ до **вмісту** | `read`, `execve`, читання через `mmap`, `readlink` |
| `st_mtim` | остання зміна **вмісту** | `write`, `truncate`, `fallocate`; для каталогу — створення й видалення записів у ньому |
| `st_ctim` | остання зміна **самого inode** | усе з рядка вище, плюс `chmod`, `chown`, `rename`, `link`, `unlink`, зміна розширених атрибутів |

Літера «c» — від *change*, а не *creation*. Плутанина коштує дорого саме тому, що поле завжди заповнене правдоподібним значенням: у щойно створеного файлу `ctime` справді дорівнює часу створення, і хибна здогадка підтверджується — доки хтось не змінить права.

З цієї трійці `ctime` — єдиний, який неможливо підробити зі звичайного коду. `utimensat` дозволяє поставити `atime` й `mtime` будь-якими, хоч торішніми, але сам цей виклик змінює inode, а отже, ставить `ctime` на «зараз». Тому інструменти резервного копіювання, яким важливо не пропустити зміну, дивляться саме на `ctime`: збрехати йому можна лише через сирий доступ до носія.

`atime` варто читати з поправкою на те, як його насправді оновлюють. Чесне оновлення при кожному читанні означало б запис на носій під час читання — тому з ядра 2.6.30 типовим став режим `relatime`: позначку оновлюють лише тоді, коли стара `atime` старіша за `mtime` чи `ctime` або старіша за добу. Монтування з `noatime` вимикає оновлення взагалі. Отже, `atime` відповідає не на питання «коли востаннє читали», а на слабше «чи читали після останньої зміни й чи читали сьогодні».

Часу створення в `struct stat` немає взагалі — ні під якою назвою. Він з'явився пізніше й тільки в `statx`.

## Чотири способи спитати

```c
int stat (const char *path, struct stat *buf);
int lstat(const char *path, struct stat *buf);
int fstat(int fd,           struct stat *buf);
int fstatat(int dirfd, const char *path, struct stat *buf, int flags);
```

| виклик | що описує | коли потрібен |
|---|---|---|
| `stat` | об'єкт, до якого шлях **приводить** — символьні посилання пройдено наскрізь | коли цікавить ціль, а не дорога до неї |
| `lstat` | останній елемент шляху **як він є** — посилання описано саме себе | будь-який обхід дерева, будь-яка перевірка «а це не посилання?» |
| `fstat` | уже відкритий об'єкт за дескриптором | єдина форма без гонки: описано рівно те, що ви тримаєте |
| `fstatat` | шлях відносно каталогу `dirfd` плюс прапорці | обхід дерева без склеювання рядків-шляхів |

`fstatat` покриває всі три попередні: `AT_FDCWD` як `dirfd` дає звичайний відносний шлях, `AT_SYMLINK_NOFOLLOW` перетворює виклик на `lstat`, а порожній шлях із `AT_EMPTY_PATH` — на `fstat`. Решта родини влаштована так само й розібрана в [`*at`-викликах](book:unix-linux/at-family-syscalls).

| прапорець `fstatat` | з якого ядра | дія |
|---|---|---|
| `AT_SYMLINK_NOFOLLOW` | від початку | не йти за останнім символьним посиланням |
| `AT_EMPTY_PATH` | 2.6.39 | порожній шлях означає сам `dirfd`, у тому числі відкритий із `O_PATH` |
| `AT_NO_AUTOMOUNT` | 2.6.38 | не запускати автомонтування дорогою |

> 🔧 **Навіщо це.** Відповідь `stat` застаріває тієї ж миті, коли повертається: між нею й наступною дією ім'я може вказати на інший об'єкт, і жодна перевірка «спершу спитаю, потім відкрию» від цього не рятує. Тому перевірки за шляхом ненадійні за побудовою, а надійний порядок зворотний: спершу `open` (за потреби з `O_PATH`, який не читає й не пише, а лише тримає об'єкт), далі `fstat` на отриманому дескрипторі — і всі рішення вже про той самий inode, який ви тримаєте.

Обхід дерева має ще одну обов'язкову умову. Якщо на кожному кроці кликати `stat`, а не `lstat`, то символьне посилання на каталог виглядатиме каталогом — і обхід або порахує ту саму гілку двічі, або зациклиться назавжди на посиланні, що вказує вгору. Різницю двох видів посилань розібрано в [жорстких і символьних посиланнях](book:unix-linux/hard-and-symbolic-links).

## `statx`: маска як частина контракту

```c
int statx(int dirfd, const char *pathname, int flags,
          unsigned int mask, struct statx *statxbuf);
```

З'явився в Linux 4.11 (2017); обгортку в glibc додано у версії 2.28, до неї виклик робили через `syscall()` напряму.

Причина появи — вичерпаність старої структури. `struct stat` не має вільного місця, розширювати її не можна, не ламаючи двійкової сумісності, а різні файлові системи знають про файл дуже різне: одна тримає час створення, друга ні; одна знає, що файл стиснуто, друга не має такого поняття. Старий інтерфейс мусив на це відповідати нулями, невідрізнюваними від справжніх значень.

`statx` змінив саму форму розмови. Той, хто питає, називає в масці, що йому потрібно; ядро повертає в `stx_mask` те, що **справді заповнило**.

![Три блоки зліва направо. Перший: mask, який передали — STATX_BASIC_STATS, STATX_BTIME, STATX_MNT_ID. Стрілка до другого блоку: ядро питає драйвер файлової системи й заповнює те, що той уміє, а зайве, що дісталося задарма, теж кладе й теж позначає. Стрілка до третього блоку: stx_mask, який повернули — є BASIC_STATS і MNT_ID, немає BTIME, бо ext4 зі 128-байтовим inode її просто не зберігає. Унизу на всю ширину червона рамка з правилом: поле, чийого біта немає в stx_mask, читати не можна, бо там нуль, а нуль у stx_btime — це 1 січня 1970 року, цілком правдоподібна дата, якої ніщо не позначить помилкою](/reference/unix-linux/files/inode-model/img/statx-mask.svg)

*Маска працює в обидва боки: назад може прийти менше, ніж просили, — і більше, коли поле дісталося ядру задарма. Тому єдиний коректний спосіб прочитати поле — спершу перевірити його біт.*

Ось чому це не формальність. Час створення на ext4 живе в додаткових полях inode, а вони існують лише тоді, коли inode більший за 128 байтів. На томі, створеному зі старим розміром inode, поля просто немає — і драйвер чесно не виставить `STATX_BTIME`. Програма, яка прочитає `stx_btime` без перевірки, отримає нуль і надрукує «створено 1 січня 1970 року»: дата виглядає дурною, але не помилковою, і ніщо в системі про підміну не попередить.

| біт маски | поле | з якого ядра |
|---|---|---|
| `STATX_TYPE`, `STATX_MODE` | `stx_mode` | 4.11 |
| `STATX_NLINK`, `STATX_UID`, `STATX_GID` | відповідні поля | 4.11 |
| `STATX_ATIME`, `STATX_MTIME`, `STATX_CTIME` | `stx_atime`, `stx_mtime`, `stx_ctime` | 4.11 |
| `STATX_INO`, `STATX_SIZE`, `STATX_BLOCKS` | `stx_ino`, `stx_size`, `stx_blocks` | 4.11 |
| `STATX_BASIC_STATS` | усе перелічене разом — рівно те, що дає `stat` | 4.11 |
| `STATX_BTIME` | `stx_btime` — час створення | 4.11 |
| `STATX_MNT_ID` | `stx_mnt_id` | 5.8 |
| `STATX_DIOALIGN` | `stx_dio_mem_align`, `stx_dio_offset_align` | 6.1 |
| `STATX_MNT_ID_UNIQUE` | `stx_mnt_id`, але неповторний ідентифікатор | 6.8 |
| `STATX_SUBVOL` | `stx_subvol` — підтом на ФС, що їх має | 6.10 |
| `STATX_WRITE_ATOMIC` | `stx_atomic_write_*` | 6.11 |

Два поля маскою не покриті взагалі й повертаються завжди: `stx_dev_major` з `stx_dev_minor` (аналог `st_dev`) і `stx_blksize`. Стару зведену константу `STATX_ALL` оголошено застарілою — просити треба саме те, що потрібно, або `STATX_BASIC_STATS | STATX_BTIME`.

**`stx_attributes` і `stx_attributes_mask`** — та сама двоярусна логіка, тільки для прапорців стану файлу. Перше поле каже, які властивості ввімкнено; друге — які з них ця файлова система взагалі здатна повідомити. Нуль у `stx_attributes` означає «ні» лише тоді, коли відповідний біт стоїть у `stx_attributes_mask`; інакше він означає «не знаю».

| прапорець | значення | з якого ядра |
|---|---|---|
| `STATX_ATTR_COMPRESSED` | вміст зберігається стисненим | 4.11 |
| `STATX_ATTR_IMMUTABLE` | файл не можна змінити, перейменувати чи видалити | 4.11 |
| `STATX_ATTR_APPEND` | відкрити на запис можна лише в режимі дописування | 4.11 |
| `STATX_ATTR_NODUMP` | позначено як такий, що не потребує резервної копії | 4.11 |
| `STATX_ATTR_ENCRYPTED` | для доступу потрібен ключ | 4.11 |
| `STATX_ATTR_VERITY` | увімкнено `fs-verity`: запис заборонено, читане звіряють із хешем | 5.5 |
| `STATX_ATTR_DAX` | доступ до вмісту йде повз сторінковий кеш, прямо процесором | 5.8 |
| `STATX_ATTR_MOUNT_ROOT` | цей файл є коренем монтування | 5.8 |
| `STATX_ATTR_WRITE_ATOMIC` | ФС гарантує запис без розриву | 6.11 |

**`stx_mnt_id`** закриває давню діру в тотожності. Пара «пристрій плюс номер» розрізняє файли, але не розрізняє **монтувань**: те саме сховище, підмонтоване двічі, і будь-яке `bind`-монтування дадуть однаковий `st_dev`, тож питання «через яке саме монтування я дивлюся на цей файл» старий інтерфейс поставити не дозволяв. `stx_mnt_id` (ядро 5.8) на нього відповідає. Проте звичайний ідентифікатор монтування ядро після відмонтування пускає в обіг наново — тому з ядра 6.8 просять `STATX_MNT_ID_UNIQUE`, який не повторюється; саме це число видає `listmount(2)` і саме за ним `statmount(2)` розкаже про монтування решту. Про самі монтування — у [моделі монтування](book:unix-linux/mount-model).

Прапорці синхронізації в аргументі `flags` мають вагу лише там, де правда про файл лежить не тут. На локальному носії різниці немає; на [мережевій файловій системі](book:unix-linux/network-filesystems) вибір між ними — це вибір між свіжістю й мережевим обміном.

| прапорець | поведінка |
|---|---|
| `AT_STATX_SYNC_AS_STAT` | як робив `stat`; поведінку визначає сама ФС — типове значення |
| `AT_STATX_FORCE_SYNC` | звірити з сервером обов'язково, хай навіть коштом обміну |
| `AT_STATX_DONT_SYNC` | віддати кешоване, не питаючи нікого; найдешевше й найменш свіже |

## Помилки

| код | коли |
|---|---|
| `EACCES` | немає права проходу (`x`) на якомусь каталозі шляху |
| `EBADF` | `dirfd` не є ані `AT_FDCWD`, ані чинним дескриптором |
| `EFAULT` | шлях або буфер лежать поза доступним простором пам'яті |
| `EINVAL` | у `flags` невідомий прапорець або в масці зарезервований біт (`statx`) |
| `ELOOP` | забагато символьних посилань дорогою |
| `ENAMETOOLONG` | шлях довший за дозволене |
| `ENOENT` | якогось складника шляху немає, або шлях порожній без `AT_EMPTY_PATH` |
| `ENOMEM` | ядру забракло пам'яті |
| `ENOTDIR` | складник шляху не є каталогом, або `dirfd` указує не на каталог |
| `EOVERFLOW` | значення не влазить у поле структури |

`EOVERFLOW` заслуговує окремого рядка, бо він не про файл, а про вашу збірку. Виникає він тоді, коли розмір, номер inode чи лічильник блоків не вміщається в 32-бітове поле: класично — на 32-бітовій збірці без `_FILE_OFFSET_BITS=64`, коли файл переріс 2 ГіБ, а також на XFS, змонтованій із `inode64`, де номери легко виходять за межу 2³². Лікується це прапорцями компіляції, а не обробкою помилки.

І окреме правило дисципліни: `ENOENT` та `EACCES` — різні відповіді, і зливати їх в одне «файлу немає» не можна. Перше означає, що файлу справді немає; друге — що ви не маєте права це перевірити, і файл цілком може бути на місці.

## Мінімальний робочий виклик

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>

static void print_ts(const char *label, long long sec, unsigned nsec)
{
    char buf[64];
    time_t t = (time_t)sec;
    struct tm tm;
    localtime_r(&t, &tm);
    strftime(buf, sizeof buf, "%Y-%m-%d %H:%M:%S", &tm);
    printf("%-12s %s.%09u\n", label, buf, nsec);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "вжиток: %s ШЛЯХ\n", argv[0]);
        return 2;
    }

    struct statx sx;
    unsigned mask = STATX_BASIC_STATS | STATX_BTIME | STATX_MNT_ID;

    if (statx(AT_FDCWD, argv[1], AT_SYMLINK_NOFOLLOW, mask, &sx) != 0) {
        if (errno != ENOSYS) {                 /* справжня помилка, не старе ядро */
            fprintf(stderr, "statx(%s): %s\n", argv[1], strerror(errno));
            return 1;
        }
        struct stat st;                        /* ядро до 4.11 — падаємо назад */
        if (fstatat(AT_FDCWD, argv[1], &st, AT_SYMLINK_NOFOLLOW) != 0) {
            fprintf(stderr, "fstatat(%s): %s\n", argv[1], strerror(errno));
            return 1;
        }
        printf("%-12s %u:%u\n", "пристрій", major(st.st_dev), minor(st.st_dev));
        printf("%-12s %llu\n", "inode", (unsigned long long)st.st_ino);
        printf("%-12s %llu\n", "імен", (unsigned long long)st.st_nlink);
        printf("%-12s %lld\n", "розмір", (long long)st.st_size);
        printf("%-12s %lld\n", "зайнято", (long long)st.st_blocks * 512);
        return 0;
    }

    /* stx_dev_* і stx_blksize маскою не покриті — вони є завжди */
    printf("%-12s %u:%u\n", "пристрій", sx.stx_dev_major, sx.stx_dev_minor);

    if (sx.stx_mask & STATX_INO)
        printf("%-12s %llu\n", "inode", (unsigned long long)sx.stx_ino);
    if (sx.stx_mask & STATX_NLINK)
        printf("%-12s %u\n", "імен", sx.stx_nlink);
    if (sx.stx_mask & STATX_TYPE)
        printf("%-12s %s\n", "тип",
               S_ISREG(sx.stx_mode) ? "звичайний файл" :
               S_ISDIR(sx.stx_mode) ? "каталог" :
               S_ISLNK(sx.stx_mode) ? "символьне посилання" : "інший");
    if (sx.stx_mask & STATX_MODE)
        printf("%-12s %04o\n", "права", sx.stx_mode & 07777);
    if (sx.stx_mask & STATX_SIZE)
        printf("%-12s %llu\n", "розмір", (unsigned long long)sx.stx_size);
    if (sx.stx_mask & STATX_BLOCKS)
        printf("%-12s %llu (%llu × 512)\n", "зайнято",
               (unsigned long long)sx.stx_blocks * 512,
               (unsigned long long)sx.stx_blocks);
    if (sx.stx_mask & STATX_MTIME)
        print_ts("змінено", sx.stx_mtime.tv_sec, sx.stx_mtime.tv_nsec);

    if (sx.stx_mask & STATX_BTIME)
        print_ts("створено", sx.stx_btime.tv_sec, sx.stx_btime.tv_nsec);
    else
        printf("%-12s ця файлова система часу створення не тримає\n", "створено");

    if (sx.stx_mask & STATX_MNT_ID)
        printf("%-12s %llu\n", "монтування", (unsigned long long)sx.stx_mnt_id);
    return 0;
}
```

Збирається як `cc -O2 -o statshow statshow.c` на glibc від 2.28 (там з'явилася обгортка `statx`) і 2.32 (там у структурі з'явилося поле `stx_mnt_id`). Кожне читання тут накрито перевіркою свого біта — і саме це, а не набір полів, є головним у контракті `statx`. Виклик `statx` не переривається сигналом і не потребує повторів; помилки, які приходять із мережевої ФС, приходять як звичайні коди — `ESTALE`, `EIO` — і їх треба обробляти нарівні з рештою.

## З командного рядка

`stat(1)` із GNU coreutils віддає ті самі поля, тільки текстом. За замовчуванням команда описує **саме символьне посилання**, а не його ціль — тобто працює як `lstat`; піти за посиланням просить `-L`.

| формат | поле |
|---|---|
| `%i` | `st_ino` |
| `%d` / `%D` | `st_dev` десятково / шістнадцятково |
| `%h` | `st_nlink` |
| `%f` | `st_mode` цілком, шістнадцятково |
| `%a` / `%A` | права вісімково / рядком `-rw-r--r--` |
| `%F` | тип словами |
| `%u` / `%U`, `%g` / `%G` | `st_uid` / ім'я, `st_gid` / назва групи |
| `%s` | `st_size` |
| `%b` / `%B` | `st_blocks` / розмір одиниці, тобто завжди `512` |
| `%o` | `st_blksize` |
| `%t` / `%T` | старший / молодший номер пристрою, шістнадцятково |
| `%x` / `%X`, `%y` / `%Y`, `%z` / `%Z` | `atime`, `mtime`, `ctime` — текстом / у секундах від епохи |
| `%w` / `%W` | час створення текстом / у секундах; `-` і `0`, коли невідомий |
| `%m` | точка монтування |

```sh
$ stat -c '%i %h %s %b×%B %F' /var/log/syslog
1443127 1 8412 24×512 regular file

$ stat -c '%w' /etc/hostname          # на ФС без цього часу тут буде «-»
2024-03-11 09:14:02.117445301 +0200

$ stat --printf '%n %s\n' *.log       # без обов'язкового переводу рядка
```

Числа старшого й молодшого номерів (`%t`, `%T`) варто читати через макроси `major()`/`minor()` з `<sys/sysmacros.h>`, а не розбирати `dev_t` бітами вручну: розкладка цього типу — внутрішня справа ядра й libc, вона вже мінялася й нічого нікому не обіцяє. Що ці числа означають — у [старших і молодших номерах](book:unix-linux/major-minor-numbers).

Дві сусідні можливості легко переплутати. `stat -f` описує не файл, а **файлову систему** під ним — це вже інший виклик (`statfs`) і зовсім інша структура, з вільними блоками й вільними inode. А час створення на ext4 можна дістати й без `statx`, читанням поля `crtime` через `debugfs -R 'stat <1443127>' /dev/sda1`, — саме так робили до 2017 року, коли з простору користувача цей час був недосяжний узагалі.
