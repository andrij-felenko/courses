# 📜 Історія виникнення Copy-on-Write та субтомів

У класичних файлових системах Unix (таких як UFS, Ext2, Ext3 та Ext4) управління блоками даних базувалося на принципі модифікації «на місці» (in-place modification). Коли процес змінює вже наявний блок файлу, ядро операційної системи знаходить відповідний сектор на дисковому накопичувачі та перезаписує його новим вмістом. Такий підхід був простим та ефективним для повільних накопичувачів минулого, але створював фундаментальну проблему: якщо під час запису ставався збій живлення або апаратна відмова, файлова система залишалася у неузгодженому (corrupted) стані.

Для вирішення цієї проблеми у 1990-х роках було створено журналювання (journaling). Файлові системи Ext3 та Ext4 додали журнал транзакцій (JBD2), у який заздалегідь записувалися метадані перед їх фіксацією на основному диску. Проте журнал лише захищав цілісність метаданих, накладаючи подвійні накладні витрати на дисковий ввід/вивід (double write overhead). Справжня технологічна революція відбулася з появою парадигми **Copy-on-Write (CoW)** — запису при копіюванні.

## Еволюційний шлях: від WAFL до ZFS

Першою комерційно успішною файловою системою з підтримкою CoW стала **WAFL (Write Anywhere File Layout)**, розроблена компанією Network Appliance (NetApp) у 1992 році під керівництвом Дейва Хітца (Dave Hitz) для спеціалізованих мережевих сховищ (NAS). WAFL повністю відмовилася від перезапису блоків на їхніх старих місцях. Замість цього будь-яка модифікація записувалася у нові, раніше вільні блоки на диску, а посилання в дереві метаданих перенаправлялися на нові адреси. Додатково WAFL використовувала батарейну оперативну пам'ять (NVRAM) для накопичення транзакцій. Це дозволило реалізувати миттєві знімки файлової системи (snapshots) шляхом простого збереження старого кореня дерева метаданих.

У 2004 році інженери Sun Microsystems під керівництвом Джеффа Бонвіка (Jeff Bonwick) та Метта Аренса (Matt Ahrens) представили **ZFS (Zettabyte File System)** для операційної системи Solaris. ZFS поєднала в собі менеджер томів (volume manager) та CoW-файлову систему, ввівши поняття пулів дисків (zpools), дерева Меркла (Merkle trees) для захисту від тихого пошкодження даних (bit rot) та легковагових файлових систем (datasets). ZFS довела, що файлова система може гарантувати 100% цілісність даних завдяки контрольним сумам для кожного блоку та транзакційній моделі CoW.

## Виклики в екосистемі Linux та створення Btrfs

Хоча ZFS була видатним технологічним досягненням, її ліцензія (Sun CDDL — Common Development and Distribution License) була юридично несумісною з ліцензією ядра Linux (GNU GPLv2). Використання ZFS безпосередньо в основній гілці ядра Linux виявилося неможливим без виникнення ліцензійних ризиків для дистрибутивів.

До появи Btrfs єдиним способом створення знімків у Linux залишався механізм LVM (Logical Volume Manager) на основі модуля ядра `device-mapper`. Проте LVM-знімки мали суттєві вади:
1. Вони працювали на блоковому рівні під файловою системою, не знаючи семантики метаданих.
2. При модифікації кожного блоку LVM виконував фізичне читання старого блоку з основного тома, запис його у том знімка і лише потім перезапис основного тома (Read-Copy-Write). Це призводило до трикратного падіння продуктивності дискового вводу/виводу.
3. Розмір знімка LVM мав бути заздалегідь фіксованим, і при його переповненні знімок повністю руйнувався.

У 2007 році Кріс Мейсон (Chris Mason), який раніше працював над журнальованою файловою системою ReiserFS та підсистемою VFS у SUSE, а пізніше перейшов до Oracle, розпочав розробку абсолютно нової файлової системи для Linux. Метою проєкту було створення нативної, сумісної з GPL файлової системи наступного покоління, яка мала б гнучкість ZFS, але базувалася на універсальному B-дереві. Так народилася **Btrfs (B-tree File System)**, яку у спільноті називають «ButterFS» або «B-tree FS».

```
Хронологія еволюції CoW-файлових систем:

1992: NetApp WAFL  ──────► Перша CoW-архітектура та знімки метаданих
2004: Sun ZFS      ──────► Поєднання менеджера томів, csum та CoW (CDDL)
2007: Oracle Btrfs ──────► Нативна CoW-файлова система для Linux (GPL)
2013: Stable Btrfs ──────► Дисковий формат оголошено стабільним (ядро Linux 3.12)
```

Розробка Btrfs швидко об'єднала інженерів провідних технологічних компаній — Oracle, Red Hat, SUSE, Intel, а пізніше Meta (Facebook). Інженери Meta під керівництвом Йозефа Бачіка (Josef Bacik) провели глибоку оптимізацію підсистеми виділення екстентів та блокування дерев, завдяки чому Btrfs стала стандартною файловою системою для мільйонів серверів інфраструктури Meta.

## Концептуальний зсув: Субтоми проти Партицій

До появи Btrfs розбиття дискового простору в Linux здійснювалося жорсткими межами: таблицями розділів MBR/GPT або логічними томами LVM. Кожен розділ мав фіксований розмір, власну файлову систему Ext4/XFS та власні таблиці інодів. Зміна розміру розділу вимагала зупинки сервісів, розмонтування та небезпечних операцій зміни розміру файлової системи через `resize2fs`.

Кріс Мейсон запропонував концепцію **субтомів (subvolumes)**. Субтом у Btrfs — це не дисковий розділ і не блоковий пристрій. Це ізольоване B-дерево метаданих файлів, яке існує в межах єдиного спільного пулу екстентів (`chunk_tree`).

### Головні переваги субтомів порівняно з партиціями:

- **Динамічний розподіл простору:** Усі субтоми використовують спільний вільний простір диска. Якщо ви створюєте субтоми `/`, `/home` та `/var`, їм не потрібно заздалегідь виділяти 50 ГБ чи 200 ГБ — кожен субтом бере стільки байтів, скільки йому потрібно прямо зараз із загального пулу.
- **Низькі накладні витрати:** Створення субтому вимагає лише запису одного вузла `btrfs_root_item` розміром у кілька кілобайтів у системне корінне дерево `ROOT_TREE`.
- **Атомарні знімки (Snapshots):** Оскільки субтом визначається коренем свого B-дерева, створення знімка (snapshot) полягає у дублюванні цього кореневого запису. Це операція зі складністю `O(1)`, яка виконується за частки мілісекунди незалежно від того, скільки терабайтів даних містить субтом.

Цей історичний та архітектурний зсув перетворив Btrfs на основу сучасних дистрибутивів Linux (таких як openSUSE, Fedora та Arch Linux), уможлививши системи автоматичного відкоту оновлень (утиліти `Snapper` та `Timeshift`), атомарні операційні системи (Fedora Silverblue, SteamOS для Valve Steam Deck) та інкрементальне мережеве резервне копіювання через `btrfs send/receive`.
