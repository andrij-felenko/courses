# 📋 Контракт заморожування: FIFREEZE, FITHAW і сусідні важелі

Заморожування просять одним `ioctl` — і майже все важливе в цій домовленості лежить поза підписом виклику: аргумент у ньому є, але ядро його не читає; дескриптор потрібен, але заморожування до нього не прив'язане; `EINVAL` приходить і тоді, коли виклик зробив свою роботу. Нижче — точний контракт: номери команд, потрібне повноваження, повний перелік кодів помилок з умовами, важелі командного рядка й ядерні точки входу, крізь які в те саме заморожування заходять device mapper і підсистема живлення.

## Дві команди й один ігнорований аргумент

```c
/* include/uapi/linux/fs.h */
#define FIFREEZE   _IOWR('X', 119, int)   /* Freeze */
#define FITHAW     _IOWR('X', 120, int)   /* Thaw   */
```

Літера `X` — від XFS, звідки цю пару взяли в спільний інтерфейс; номери лишили старі, щоб не ламати вже написані інструменти.

[Кодування номера](topic:unix-linux/ioctl-interface) обіцяє тут більше, ніж є насправді. `_IOWR(…, int)` каже, що по вказівнику ходить `int` в обидва боки, — а обробник у ядрі оголошений як `ioctl_fsfreeze(struct file *filp)` і третього аргументу не отримує взагалі. Передавайте `0` і не сподівайтеся ні задати параметр, ні прочитати щось назад.

Суперблок ядро бере з inode дескриптора — `file_inode(filp)->i_sb`, — тож формально спрацює будь-який відкритий файл потрібної файлової системи. Домовленість, однак, інша: дескриптор відкривають на каталозі [точки монтування](topic:unix-linux/mount-model), і саме цього очікують інструменти й довідники.

```c
#include <fcntl.h>
#include <sys/ioctl.h>
#include <linux/fs.h>

int fd = open("/srv/data", O_RDONLY | O_DIRECTORY);
if (fd < 0)
        return -1;

if (ioctl(fd, FIFREEZE, 0) < 0)   /* аргумент є в підписі, але не читається */
        return -1;                /* errno — за таблицею нижче */

/* ... вікно: тут той, хто знімає копію, робить свою справу ... */

if (ioctl(fd, FITHAW, 0) < 0)
        return -1;

close(fd);                        /* close НЕ відтає — див. «Пастки» */
```

Повноваження потрібне одне — `CAP_SYS_ADMIN`, — і перевіряють його не абстрактно, а виразом `ns_capable(sb->s_user_ns, CAP_SYS_ADMIN)`. [Повноваження](topic:unix-linux/capabilities) мусить бути дійсним у тому [просторі імен користувачів](topic:unix-linux/namespaces), якому належить суперблок: root у контейнері заморозить те, що змонтовано його власним простором, і не дістанеться файлових систем хазяїна.

## Коди помилок

| код | коли повертається |
|---|---|
| `EPERM` | немає `CAP_SYS_ADMIN` у просторі імен користувачів, якому належить суперблок |
| `EOPNOTSUPP` | у файлової системи немає ні `->freeze_fs`, ні `->freeze_super` (tmpfs, squashfs, більшість мережевих) |
| `EBUSY` | `FIFREEZE` на файловій системі, уже замороженій із простору користувача |
| `EINVAL` | `FITHAW` на незамороженій; `FITHAW`, коли заморожування тримає хтось інший; суперблок демонтується |
| `ENOTTY` | номер команди невідомий тому, хто його отримав |

`EBUSY` читається буквально: вкладеності для простору користувача немає. Другий `FIFREEZE` не збільшує жодного лічильника — він просто відмовляє, і перший `FITHAW` після нього відтає файлову систему повністю.

`EINVAL` при відтаванні покриває три різні події, і третя з них — не помилка виклику. Коли ваше відтавання зменшило лічильник, але заморожування ще тримає інший власник, ядро теж повертає `EINVAL`: зменшення відбулося, а файлова система лишилася замороженою.

> 🔧 **Навіщо це.** Повернене число тут описує **стан файлової системи**, а не успіх вашої дії. `0` означає «після цього виклику вона розморожена», будь-що інше — «ні». Через це скрипт не може судити з коду помилки, чи спрацював саме його `FITHAW`, і не має права трактувати `EINVAL` як «нема чого відтавати» й тихо йти далі. Єдине надійне прочитання: `0` — вікно закрите; не `0` — вікно, можливо, ще відкрите, і треба дивитися, хто його тримає.

`ENOTTY` на цій парі в сучасному ядрі не трапляється: обидва номери перехоплює `do_vfs_ioctl()` ще до того, як запит дійде до `->unlocked_ioctl` файлової системи чи драйвера. Побачити його можна на ядрі, старішому за появу цієї пари, або крізь прошарок, що підміняє `ioctl` своєю реалізацією.

## Пастки

**Монтування лише для читання заморожується успішно й не робить нічого.** Побачивши `sb_rdonly()`, `freeze_super()` збільшує лічильник, ставить стан `SB_FREEZE_COMPLETE` і повертає `0` — жодного бар'єра, жодного `->freeze_fs()`. Тобто `fsfreeze -f` на змонтованому з `-o ro` томі відпрацює «успішно», хоч зупиняти там нічого. Файлова система, яка лише для читання за своєю природою (squashfs, iso9660), поводиться інакше — вона взагалі не має методу заморожування й дає `EOPNOTSUPP`. Отже, `0` тут читається як «нема чого зупиняти», а не як «зупинено».

**Заморожування не належить ні дескриптору, ні процесу.** Воно живе на суперблоці. `close(fd)` його не знімає, завершення процесу не знімає, `kill -9` не знімає. Зняти може лише `FITHAW` (від того самого класу власника), ядерне відтавання або перезавантаження.

**Читання у вікні дозволені.** Бар'єри стоять на шляхах зміни, тож `open` для читання, `read`, `stat`, обхід каталогів працюють як завжди. Засинає — [непереривно](topic:unix-linux/process-states) — лише той, хто прийшов писати.

## Командний рядок

| команда | що робить |
|---|---|
| `fsfreeze -f <точка>` | `FIFREEZE` на точці монтування |
| `fsfreeze -u <точка>` | `FITHAW` на ній же |
| `dmsetup suspend <пристрій>` | призупиняє пристрій і дорогою заморожує файлову систему на ньому |
| `dmsetup resume <пристрій>` | знімає призупинення й відтає |
| `dmsetup suspend --nolockfs` | те саме призупинення, але **без** заморожування файлової системи |
| `dmsetup suspend --noflush` | не скидати незавершений ввід-вивід; має перевагу над заморожуванням |

`fsfreeze` — з `util-linux`; у його довіднику перелічені файлові системи, які цю дію вміють: btrfs, ext2/3/4, f2fs, jfs, nilfs2, reiserfs, xfs. Там же сказано, що для пристроїв device mapper команда зайва — [створення знімка LVM](topic:unix-linux/lvm-and-snapshots) уже проходить крізь те саме ядерне заморожування.

`--nolockfs` вимикає не «синхронізацію взагалі», як можна прочитати з опису, а конкретну дію: [device mapper](topic:unix-linux/device-mapper) пропускає свій `lock_fs()`, тобто не заходить у заморожування зовсім. Пристрій зупиняється, файлова система про це не дізнається, і знімок виходить рівня «після збою». Прапорець потрібен там, де заморожувати нема кого (на пристрої немає змонтованої файлової системи) або де спроба заморозити зациклилася б сама на собі.

## Ядерні точки входу

```c
int freeze_super(struct super_block *sb, enum freeze_holder who,
                 const void *freeze_owner);
int thaw_super  (struct super_block *sb, enum freeze_holder who,
                 const void *freeze_owner);
```

| функція | хто заходить крізь неї | з якими прапорцями |
|---|---|---|
| `freeze_super()` / `thaw_super()` | спільна кінцева точка всіх шляхів | тими, що передали |
| `bdev_freeze()` / `bdev_thaw()` | device mapper, програмні масиви | `FREEZE_MAY_NEST \| FREEZE_HOLDER_USERSPACE` |
| `filesystems_freeze()` / `filesystems_thaw()` | призупинення й сон системи | `FREEZE_EXCL \| FREEZE_HOLDER_KERNEL` плюс вказівник-власник |

До ядра 6.8 блокові обгортки звалися `freeze_bdev()` і `thaw_bdev()`; слова в назвах помінялися місцями, зміст лишився. У `struct block_device` є власний лічильник `bd_fsfreeze_count`: повторний `bdev_freeze()` того самого пристрою дозволений, а справжнє відтавання робить лише останній `bdev_thaw()`.

Прапорці власника — це `enum freeze_holder`:

| прапорець | що задає |
|---|---|
| `FREEZE_HOLDER_USERSPACE` | рахувати в `sb->s_writers.freeze_ucount` |
| `FREEZE_HOLDER_KERNEL` | рахувати в `sb->s_writers.freeze_kcount` |
| `FREEZE_MAY_NEST` | дозволити повторне заморожування у своєму класі |
| `FREEZE_EXCL` | ексклюзив із власником: адреса лягає в `s_writers.freeze_owner`, і зняти заморожування може лише той самий вказівник |

Правило відтавання одне на всіх: зменшивши свій лічильник, ядро дивиться на **суму обох**, і бар'єри знімає разом із викликом `->unfreeze_fs()` тільки тоді, коли ця сума стала нулем. Тому зняти чуже заморожування не виходить ні згори, ні знизу.

Назви класів варто читати обережно: клас — це не «хто фізично викликав», а «в який лічильник записати». Шлях device mapper рахується в лічильнику простору користувача, хоч і заходить із ядра, — зате з дозволом на вкладеність, якого простому `FIFREEZE` не дали. А `FREEZE_HOLDER_KERNEL` лишили тим, кому потрібен ексклюзив із власником.

Звідси два передбачувані наслідки для скриптів. Поки знімок LVM тримає файлову систему замороженою, ваш `fsfreeze -f` отримає `EBUSY`. А якщо ви заморозили першими й поверх пройшов `dmsetup suspend`, ваш `fsfreeze -u` поверне `EINVAL` — ваш лічильник обнулився, файлова система лишилася замороженою чужим.

## Перемикач для призупинення

```
/sys/power/freeze_filesystems     0 | 1
```

З'явився в ядрі 6.16 — у 6.15 його ще немає. Одиниця вмикає заморожування змонтованих файлових систем перед [призупиненням і сном](topic:unix-linux/suspend-and-resume), нуль лишає стару поведінку; значення поза цією парою відкидається з `EINVAL`. Шлях живлення заходить у `freeze_super()` з `FREEZE_EXCL | FREEZE_HOLDER_KERNEL` і власним вказівником — отже, поставлене ним заморожування не зніме ні `fsfreeze -u`, ні будь-який інший сторонній виклик.
