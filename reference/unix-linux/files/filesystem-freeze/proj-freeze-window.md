# ⚙️ Вікно з таймером безпеки: програма, яка заморожує ФС і називає ціну вікна

Ця вставка пояснює ⚙️ вікно з таймером безпеки: програма, яка заморожує фс і називає ціну вікна та дозволяє зрозуміти її детальніше. Ця програма робить чотири речі поспіль — відкриває точку монтування, зводить сторожа, заморожує файлову систему, утримує її й відтає, — а насамкінець друкує, скільки мілісекунд усе це коштувало тим, хто в цей час писав. Писати її варто не заради самого `ioctl`: там один рядок. Варто заради двох речей, яких у коротких прикладах зазвичай немає, — виходу з вікна, що не залежить від долі основного процесу, і числа, яке показує справжню ціну вікна для навантаження.

Мова тут безальтернативна. Заморожування просять [через `ioctl`](book:unix-linux/ioctl-interface) на відкритому дескрипторі, і потрібне повноваження [`CAP_SYS_ADMIN`](book:unix-linux/capabilities) — тобто зазвичай запуск від root. Пишемо на C, бо саме там системний виклик видно таким, як він є.

## Ідея: три ролі, три окремі задачі

Заморожування живе на суперблоці — не на процесі й не на дескрипторі. Звідси випливає асиметрія, яка й визначає всю будову програми: поставити заморожування — одна дія, а зняти його може вже не бути кому. Процес убили ззовні, він упав на своєму ж сегментному порушенні, обірвалася сесія ssh, з якої його запустили, — файлова система лишається зупиненою, і повернути її здатен тільки хтось живий із дескриптором у руках.

Тому програма розкладається на три задачі, які не залежать одна від одної.

**Основна** тримає вікно: заморожує, чекає, поки зроблять знімок, відтає. **Сторож** — окремий процес, який відтає за таймером, хай там що сталося з основною. **Писар** пише в циклі й міряє, скільки найдовше простояв один запис: це і є ціна вікна, виражена в мілісекундах для того, хто працює.

![Три доріжки в часі: основний процес, сторож і писар навколо одного вікна](/reference/unix-linux/files/filesystem-freeze/img/watchdog-timeline.svg)

*Таймер зводять до бар'єра, а не після; писар у вікні не «повільний», а зупинений.*

## Сторож: чому таймер зводять першим

Спокуса зробити навпаки сильна — спершу заморозити, а вже потім, «маючи вікно», подбати про вихід. Проти цього є три окремі причини, і кожної досить.

Перша: сам `FIFREEZE` не миттєвий. Він чекає на писарів, які вже всередині, і кілька разів скидає брудні сторінки на носій. На томі з великим [кешем брудних сторінок](book:unix-linux/page-cache-durability) це не мілісекунди, а секунди. Таймер, зведений після виклику, цієї ділянки не покриває — а вона вже частина вікна, за яку платить навантаження.

Друга: саме на цій ділянці процес найлегше втратити. Поки `ioctl` не повернувся, ви не маєте куди вставити рядок із таймером, а файлова система вже може бути замороженою.

Третя, найпростіша: бюджет треба ставити на те, що ви обіцяли, — на повну довжину зупинки, а не на її хвіст.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <limits.h>
#include <fcntl.h>
#include <unistd.h>
#include <time.h>
#include <signal.h>
#include <sys/ioctl.h>
#include <sys/wait.h>
#include <linux/fs.h>          /* FIFREEZE, FITHAW */

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);      /* монотонний час: не стрибне від NTP */
    return ts.tv_sec * 1000.0 + ts.tv_nsec / 1e6;
}

/* Сторож. Власний дескриптор відкрито ДО fork і ДО заморожування. */
static pid_t spawn_watchdog(const char *mountpoint, unsigned deadline_ms)
{
    int wfd = open(mountpoint, O_RDONLY | O_DIRECTORY);
    if (wfd < 0) { perror("сторож: open"); return -1; }

    pid_t pid = fork();
    if (pid < 0)  { perror("fork"); close(wfd); return -1; }
    if (pid > 0)  { close(wfd); return pid; }   /* батько сторожевим fd не користується */

    /* --- далі код сторожа: жодного відкриття файлів, жодного stdio --- */
    struct timespec req = { deadline_ms / 1000,
                            (long)(deadline_ms % 1000) * 1000000L }, rem;
    while (nanosleep(&req, &rem) == -1 && errno == EINTR)
        req = rem;                              /* добираємо залишок сну */

    ioctl(wfd, FITHAW, 0);                      /* СПЕРШУ відтаємо… */
    static const char m[] = "СТОРОЖ: дедлайн — файлову систему відтанули\n";
    (void)!write(2, m, sizeof m - 1);           /* …і лише потім говоримо */
    _exit(0);
}
```

Порядок двох останніх дій у сторожа не косметичний. Якщо повідомлення піде першим, а стандартний потік помилок перенаправлено у файл на тій самій файловій системі, сторож застрягне на власному звіті — усередині вікна, яке він мав закрити. Такий сторож гірший за жодного: він створює враження, що вихід є.

## Чому сторожеві не можна нічого писати

У замороженій файловій системі проходять читання й не проходить **жоден** запис. Не проходить `write()` у відкритий файл, не проходить створення файла, не проходить `mkdir`, не проходить дописування в журнал застосунку. Причому програма не отримує помилки: вона засинає [непереривним сном](book:unix-linux/process-states) — станом D, з якого задачу не витягти ні сигналом, ні `kill -9`, бо вона тримає внутрішні структури ядра посеред операції.

Звідси набір заборон, надмірний тільки на перший погляд. Сторож не пише лог. Не відкриває файлів. Не викликає `system("fsfreeze -u …")`, бо оболонка на першому ж кроці захоче кудись щось записати. Не покладається на буфери `stdio`, які можуть злитися саме в невдалу мить. Усе, що йому потрібно, — дескриптор, відкритий заздалегідь, і один системний виклик на ньому.

> 🔧 **Навіщо це.** Таймер усередині того самого процесу — через `alarm()` або [POSIX-таймер](book:unix-linux/process-timers) — теж дасть відтавання за розкладом, і на перший погляд це простіше за окремий процес. Але він тримається на процесі: `SIGKILL` в основну програму забирає з собою й таймер, а разом із ним — єдиний шлях назад. До того ж `ioctl` немає в переліку [безпечних для обробника сигналу](book:unix-linux/async-signal-safety) функцій, тож формально відтавання прямо з обробника — за межами гарантій стандарту. Окремий процес знімає обидва заперечення одним рухом: він переживає смерть батька й робить свій виклик у звичайному потоці керування.

## Писар: скільки коштує вікно тому, хто працює

Друга половина програми — вимірювальна. Писар пише в циклі невеликими порціями й тримає найдовшу тривалість одного запису. Поза вікном це десяті частки мілісекунди, у вікні — уся його довжина.

```c
static volatile sig_atomic_t stop_writer = 0;
static void on_term(int sig) { (void)sig; stop_writer = 1; }

/* Писар. Файл створено ДО заморожування: O_CREAT усередині вікна застряг би. */
static pid_t spawn_writer(const char *path)
{
    int wr = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (wr < 0) { perror("писар: open"); return -1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); close(wr); return -1; }
    if (pid > 0) { close(wr); return pid; }

    struct sigaction sa = { .sa_handler = on_term };   /* без SA_RESTART */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGTERM, &sa, NULL);

    char buf[4096];
    memset(buf, 'x', sizeof buf);
    double worst = 0.0;
    unsigned long long ops = 0;

    while (!stop_writer) {
        off_t off = (off_t)(ops % 256) * sizeof buf;   /* файл лишається ~1 МіБ */
        double a = now_ms();
        ssize_t n = pwrite(wr, buf, sizeof buf, off);  /* тут і буде стан D */
        double d = now_ms() - a;
        if (n < 0 && errno != EINTR) break;
        if (d > worst) worst = d;
        ops++;
        struct timespec pause = { 0, 1000000L };       /* 1 мс між записами */
        nanosleep(&pause, NULL);
    }
    fprintf(stderr, "ПИСАР: записів %llu, найдовший pwrite() = %.1f мс\n", ops, worst);
    _exit(0);
}
```

Звіт друкується не в обробнику сигналу, а в основному циклі: обробник лише ставить прапорець. Це та сама дисципліна, що й у сторожа, тільки з іншої причини — `fprintf` у переліку безпечних для обробника функцій теж немає.

## Головна частина

```c
int main(int argc, char **argv)
{
    if (argc < 3) {
        fprintf(stderr, "вжиток: %s <точка-монтування> <вікно-мс> [--sync]\n", argv[0]);
        return 2;
    }
    const char *mp = argv[1];
    unsigned window_ms = (unsigned)strtoul(argv[2], NULL, 10);
    int presync = (argc > 3 && strcmp(argv[3], "--sync") == 0);

    char probe[PATH_MAX];
    snprintf(probe, sizeof probe, "%s/freeze-probe.tmp", mp);

    int fd = open(mp, O_RDONLY | O_DIRECTORY);   /* дескриптор ТОЧКИ МОНТУВАННЯ */
    if (fd < 0) { perror("open точки монтування"); return 1; }

    pid_t writer = spawn_writer(probe);
    if (writer < 0) return 1;
    pid_t dog = spawn_watchdog(mp, window_ms + 5000);   /* СТОРОЖ — ДО заморожування */
    if (dog < 0) { kill(writer, SIGKILL); waitpid(writer, NULL, 0); return 1; }

    struct timespec warmup = { 0, 200000000L };
    nanosleep(&warmup, NULL);                    /* дати писареві розігнатися */

    if (presync) syncfs(fd);                     /* виносимо масу брудних сторінок ЗА вікно */

    double t0 = now_ms();
    if (ioctl(fd, FIFREEZE, 0) < 0) {
        fprintf(stderr, "FIFREEZE: %s\n", strerror(errno));
        kill(dog, SIGKILL); kill(writer, SIGKILL);
        return 1;
    }
    double t1 = now_ms();

    /* ═══ ВІКНО. Сюди підставляють знімок. Писати в цю ФС не можна нічого. ═══ */
    struct timespec hold = { window_ms / 1000,
                             (long)(window_ms % 1000) * 1000000L };
    nanosleep(&hold, NULL);

    double t2 = now_ms();
    int thawed = (ioctl(fd, FITHAW, 0) == 0);
    double t3 = now_ms();
    if (!thawed) fprintf(stderr, "FITHAW: %s\n", strerror(errno));

    if (thawed) kill(dog, SIGKILL);   /* сторожа знімаємо ЛИШЕ після успішного відтавання */

    fprintf(stderr, "FIFREEZE %.1f мс | утримання %.1f мс | FITHAW %.1f мс | вікно %.1f мс\n",
            t1 - t0, t2 - t1, t3 - t2, t3 - t0);

    kill(writer, SIGTERM);
    waitpid(writer, NULL, 0);
    waitpid(dog, NULL, 0);
    unlink(probe);
    close(fd);
    return 0;
}
```

Збирається без ключів: `cc -O2 -o freezewin freezewin.c`. Запускається від root на **окремому** томі — `./freezewin /mnt/test 1000`.

Рядок `if (thawed) kill(dog, …)` варто прочитати двічі. Сторожа знімають тільки тоді, коли відтавання справді вдалося; якщо `FITHAW` повернув помилку, сторож лишається жити й спробує ще раз за таймером. Зворотний порядок — убити сторожа, а потім відтавати — повертає програму рівно в те становище, від якого сторожа й заводили.

## Що видно в прогоні

Абсолютні числа залежать від носія, обсягу брудних сторінок і навантаження; важить не їхня величина, а співвідношення двох прогонів.

Без попереднього скидання:

```
FIFREEZE 2841.6 мс | утримання 1000.2 мс | FITHAW 1.9 мс | вікно 3843.7 мс
ПИСАР: записів 178, найдовший pwrite() = 3842.4 мс
```

З ключем `--sync`:

```
FIFREEZE 41.3 мс | утримання 1000.1 мс | FITHAW 1.4 мс | вікно 1042.8 мс
ПИСАР: записів 2604, найдовший pwrite() = 1041.6 мс
```

Просили вікно на секунду — у першому прогоні дістали майже чотири. Різницю з'їв сам `FIFREEZE`, якому довелося вивозити на носій усе накопичене. `syncfs()` не зменшив цієї роботи ні на байт: він виконав її **до** бар'єрів, поки писарі ще працювали нормально. Усередині вікна лишився тільки дрібний залишок — те, що набігло за проміжок між скиданням і заморожуванням.

Різниця в кількості записів каже те саме з іншого боку. Писар у другому прогоні зробив їх у чотирнадцять разів більше не тому, що став швидшим: ті самі три секунди скидання він провів працюючи, а не в стані D.

І останнє, що видно з обох прогонів: найдовший `pwrite()` писаря майже дорівнює всій довжині вікна. Ціна для навантаження — не «трохи повільніше», а рівно стільки, скільки триває зупинка.

## Пастки

**Писаря у вікні не вбити.** Спроба прибрати завислий процес під час вікна нічого не дає: `ps -o pid,stat,cmd -p …` показує `D`, а `kill -9` лягає в чергу й спрацює тільки після відтавання. Це не аварія, а нормальна поведінка непереривного сну — і саме тому вікном керує таймер, а не людина з клавіатурою. Побічний наслідок: задачі в стані D враховуються в [середньому навантаженні](book:unix-linux/load-and-pressure) нарівні з тими, що рахують, — тож моніторинг покаже стрибок рівно на довжину вікна, хоча процесор у цей час нічим не зайнятий.

**Повторне заморожування — `EBUSY`.** Вкладеності немає: другий `FIFREEZE` на вже замороженій файловій системі чесно відмовляє.

```c
if (ioctl(fd2, FIFREEZE, 0) < 0)
    fprintf(stderr, "FIFREEZE: %s\n", strerror(errno));   /* → Device or resource busy */
```

Прочитати цю відмову як «уже й так заморожено, отже, можна робити знімок» — груба помилка. `EBUSY` означає, що вікно тримає **хтось інший**, і ваше `FITHAW` обірве йому копіювання посеред роботи. Дзеркальний випадок: `FITHAW` на незамороженій системі повертає `EINVAL` — саме тому сторож не дивиться на код помилки, для нього «уже відтануло» є нормальним результатом.

**Сторож, що пережив своє вікно.** Якщо основну програму вбито після успішного відтавання, але до `kill(dog, …)`, сторож доживе до дедлайну й відтане те, що на той час встиг заморозити хтось інший. Тому запас беруть невеликий — секунди понад очікуване вікно, а не хвилини.

**Корінь без сторожа — це зупинена машина.** Заморожена коренева файлова система лишає систему в оманливо живому стані: читання йдуть, наявна оболонка відповідає, уже запущені програми не падають. Але перший же запис будь-де тихо стає в чергу — журнал системи, історія оболонки, `utmp` при новому вході. Практично це означає, що по ssh ви більше не зайдете, а `fsfreeze -u` набрати нема звідки. Лишаються тільки ті виходи, які не торкаються замороженого тому: команда з уже відкритої оболонки — або запис у `/proc/sysrq-trigger`, що спрацює, бо [procfs](book:unix-linux/pseudo-filesystems) є окремою псевдофайловою системою в пам'яті й до заморожування не має стосунку. Утиліта `fsfreeze` з `util-linux` власного таймера не має — сторожа треба приносити з собою.

**Знімок теж не повинен писати в заморожене.** Код, що стоїть у вікні замість `nanosleep`, підпадає під ті самі заборони, що й сторож. Знімок [через device mapper](book:unix-linux/device-mapper) їх не порушує — він працює з метаданими тому, а не з файлами на ньому. А скрипт, який дорогою запише рядок у `/var/log` тієї самої файлової системи, повисне в стані D і не вийде звідти, доки його не звільнить сторож.
