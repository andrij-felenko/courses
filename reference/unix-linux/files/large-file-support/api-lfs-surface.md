# 📋 Великі файли: макроси, типи, символи, виклики, помилки

Ця вставка пояснює 📋 великі файли: макроси, типи, символи, виклики, помилки та дозволяє зрозуміти її детальніше. Довідка за клавіатурою: усе, що в Linux і glibc становить поверхню великих файлів — які макроси що вмикають і як залежать один від одного, якої ширини кожен тип у кожному режимі, у який символ перетвориться ім'я, який системний виклик по той бік libc, що означає `O_LARGEFILE` і за яких **точно** умов повертається `EOVERFLOW` чи `EFBIG`. Головні питання, на які ця довідка відповідає: чи широкий зараз мій `off_t`, у що скомпілювався мій `lseek` — і чого з цього переліку взагалі не існує на 64-бітній цілі.

Усе, крім розділу про musl, стосується glibc на Linux. Розміри в таблицях подано для двох крайніх випадків: **ILP32** (32-бітні вказівники й `long` — `i386`, `armv7`, `mips32`, 32-бітний `riscv`) і **LP64** (`x86-64`, `aarch64`, `riscv64`, 64-бітний `powerpc`).

## 1. Макроси перевірки можливостей

Два правила перед таблицею, бо без них таблиця вводить в оману.

**Макрос мусить бути визначений до першого `#include`.** Він працює через `<features.h>`, який заголовки підтягують першим рядком; визначення після хоч одного включення застає систему типів уже зібраною й не робить нічого — мовчки. Тому місце макроса — прапорець `-D` у системі збирання, а не `#define` у тілі файлу.

**Макрос діє рівно на одну одиницю трансляції.** Компонувальник розбіжності не помічає, бо імена ваших власних функцій від макроса не міняються.

| Макрос | Значення | Що вмикає |
|---|---|---|
| `_FILE_OFFSET_BITS` | `64` | `off_t`, `ino_t`, `blkcnt_t`, `rlim_t`, `fpos_t` і поля `struct stat` стають широкими; звичайні імена перенаправляються на реалізації з суфіксом `64` |
| `_FILE_OFFSET_BITS` | `32` або не задано | вузький режим; glibc документує 32 як **чинне** типове значення й попереджає, що воно колись зміниться |
| `_LARGEFILE_SOURCE` | визначений | історичний: відкриває `fseeko` і `ftello` — версії `fseek`/`ftell` із типом `off_t` замість `long`. Визначається неявно, коли задано `_XOPEN_SOURCE ≥ 500`, тож окремо його вже не пишуть |
| `_LARGEFILE64_SOURCE` | визначений | відкриває `off64_t`, `struct stat64`, `struct dirent64` і **весь** набір імен із суфіксом `64` — паралельний, «перехідний» інтерфейс LFS |
| `_TIME_BITS` | `64` | 64-бітний `time_t` і всі похідні від нього типи; доступний від glibc 2.34 |
| `_GNU_SOURCE` | визначений | серед іншого — `loff_t`, `readahead`, `sync_file_range`, `fallocate` |

Два макроси ширини пов'язані жорстко: `_TIME_BITS=64` дозволено **лише** разом із `_FILE_OFFSET_BITS=64`. Причина проста — обидва міняють розкладку тих самих структур. Комбінації, які збираються, вичерпуються трьома:

```
_FILE_OFFSET_BITS   _TIME_BITS   результат на 32-бітній цілі, glibc ≥ 2.34
──────────────────────────────────────────────────────────────────────────
не задано / 32      не задано    вузький зсув, вузький час (стеля 2 ГіБ і 2038 рік)
64                  не задано    широкий зсув, вузький час
64                  64           широкий зсув, широкий час
не задано / 32      64           #error — препроцесор зупиняє збірку
```

> 🔧 **Навіщо це.** Наслідок останнього рядка неочевидний і б'є на практиці: проєкт, який лагодить у себе [межу 2038 року](book:unix-linux/time-representation-y2038) на 32-бітній платі, тим самим зобов'язаний перейти й на широкі зсуви — а отже перебрати всі бібліотеки, чиї заголовки виносять `off_t` або `time_t`. Одне не вмикається без другого.

Усередині заголовків режим позначено внутрішнім макросом `__USE_FILE_OFFSET64` — його виставляє `<features.h>`, коли `_FILE_OFFSET_BITS` дорівнює 64. **Самому його визначати не можна** (заголовки тоді розійдуться з тим, що насправді зібрано), але перевіряти у власному заголовку — цілком доречно, якщо ваш API виносить `off_t` назовні.

Найнадійніша перевірка не потребує ані макросів, ані `getconf` — вона питає сам тип:

```c
#include <sys/types.h>
_Static_assert(sizeof(off_t) == 8, "зібрано без широких зсувів");
```

## 2. Типи

Ширина в таблиці — та, яку тип має **після** препроцесора, тобто вже з урахуванням макросів.

| Тип | Заголовок | ILP32 без макроса | ILP32 з `_FILE_OFFSET_BITS=64` | LP64 |
|---|---|---|---|---|
| `off_t` | `<sys/types.h>` | 32 біти зі знаком | 64 зі знаком | 64 зі знаком |
| `off64_t` | те саме, під `_LARGEFILE64_SOURCE` | 64 зі знаком | 64 | 64 |
| `loff_t` | те саме, під `_GNU_SOURCE` | 64 зі знаком | 64 | 64 |
| `ino_t` | `<sys/types.h>` | 32 без знака | 64 без знака | 64 без знака |
| `ino64_t` | те саме, під `_LARGEFILE64_SOURCE` | 64 | 64 | 64 |
| `blkcnt_t` (`st_blocks`) | `<sys/types.h>` | 32 зі знаком | 64 | 64 |
| `blksize_t` (`st_blksize`) | `<sys/types.h>` | 32 **завжди** | 32 | 64 |
| `fsblkcnt_t`, `fsfilcnt_t` | `<sys/statvfs.h>` | 32 | 64 | 64 |
| `rlim_t` | `<sys/resource.h>` | 32 | 64 | 64 |
| `fpos_t` | `<stdio.h>` | структура з вузьким `__pos` | структура з широким | широкий |
| `time_t` | `<time.h>` | 32 — міняє **інший** макрос | 32 (доки нема `_TIME_BITS`) | 64 |
| `size_t`, `ssize_t` | `<stddef.h>` | 32 — не міняється ніколи | 32 | 64 |

Чотири рядки з цієї таблиці варті окремого слова.

**`loff_t` — тип ядра, а не програми.** Він 64-бітний завжди й ніколи не залежить від макросів, бо всередині ядра зсув у файлі іншим і не буває. Саме тому його видно в підписах, що дивляться прямо в ядро: `_llseek` віддає результат через `loff_t *`.

**`blksize_t` не росте разом із рештою.** Це не зсув і не розмір файлу, а порада щодо зручного кроку читання; чотирьох мільярдів для неї вистачає з запасом, тож у вузькому ABI вона лишається 32-бітною навіть під макросом.

**`size_t` і `ssize_t` не мають до великих файлів жодного стосунку.** Вони описують шматок **пам'яті**, а не позицію у файлі: `read` за один виклик і не може попросити більше байтів, ніж уміщає адресний простір. Плутанина тут поширена й дорога — спроба «розширити» лічильник байтів замість зсуву не лікує нічого.

**`fpos_t` — непрозора структура, а не число.** У glibc це

```c
typedef struct _G_fpos_t {
  __off_t     __pos;    /* власне позиція */
  __mbstate_t __state;  /* стан розбору багатобайтових символів */
} __fpos_t;
```

тож значення, здобуте `fgetpos`, годиться лише на те, щоб віддати його назад у `fsetpos`. Арифметика над ним — помилка: у потоці з багатобайтовим кодуванням позиція без стану неповна. Коли потрібне саме **число**, беруть `ftello`, а не `fgetpos`. Ширина в цій структурі теж плаває: під `_FILE_OFFSET_BITS=64` `fpos_t` стає `__fpos64_t` із широким `__pos`, і структура міняє розмір — ще одна причина не класти її у власні формати чи в публічні заголовки.

## 3. Перехідні імена з суфіксом `64`

Ключове правило, яке пояснює всю таблицю: **під `_FILE_OFFSET_BITS=64` звичайне ім'я і його `*64`-двійник — це один і той самий символ**. Без макроса — два різні. Тобто суфікс `64` не дає нічого понад те, що дає макрос; він лише дозволяє вжити широкий інтерфейс точково, не міняючи типів усього файлу.

```c
/* <fcntl.h> */
int      open64(const char *path, int flags, ... /* mode_t mode */);
int      openat64(int dirfd, const char *path, int flags, ... /* mode_t mode */);
int      creat64(const char *path, mode_t mode);
int      fcntl64(int fd, int cmd, ...);
int      posix_fadvise64(int fd, off64_t offset, off64_t len, int advice);
int      posix_fallocate64(int fd, off64_t offset, off64_t len);

/* <unistd.h> */
off64_t  lseek64(int fd, off64_t offset, int whence);
ssize_t  pread64(int fd, void *buf, size_t n, off64_t offset);
ssize_t  pwrite64(int fd, const void *buf, size_t n, off64_t offset);
int      truncate64(const char *path, off64_t length);
int      ftruncate64(int fd, off64_t length);
int      lockf64(int fd, int cmd, off64_t len);

/* <sys/stat.h> */
int      stat64(const char *path, struct stat64 *buf);
int      fstat64(int fd, struct stat64 *buf);
int      lstat64(const char *path, struct stat64 *buf);
int      fstatat64(int dirfd, const char *path, struct stat64 *buf, int flags);

/* <stdio.h> */
FILE    *fopen64(const char *path, const char *mode);
FILE    *freopen64(const char *path, const char *mode, FILE *stream);
FILE    *tmpfile64(void);
int      fseeko64(FILE *stream, off64_t off, int whence);
off64_t  ftello64(FILE *stream);
int      fgetpos64(FILE *stream, fpos64_t *pos);
int      fsetpos64(FILE *stream, const fpos64_t *pos);

/* <dirent.h> */
struct dirent64 *readdir64(DIR *dirp);
int      scandir64(const char *dir, struct dirent64 ***namelist,
                   int (*sel)(const struct dirent64 *),
                   int (*cmp)(const struct dirent64 **, const struct dirent64 **));
int      scandirat64(int dfd, const char *dir, struct dirent64 ***namelist,
                     int (*sel)(const struct dirent64 *),
                     int (*cmp)(const struct dirent64 **, const struct dirent64 **));
int      alphasort64(const struct dirent64 **a, const struct dirent64 **b);
int      versionsort64(const struct dirent64 **a, const struct dirent64 **b);
ssize_t  getdirentries64(int fd, char *buf, size_t nbytes, off64_t *basep);
```

Решта родин — тим самим правилом, без окремих підписів: `<sys/mman.h>` — `mmap64`; `<sys/sendfile.h>` — `sendfile64`; `<sys/resource.h>` — `getrlimit64`, `setrlimit64`; `<sys/statvfs.h>` — `statvfs64`, `fstatvfs64`; `<sys/statfs.h>` — `statfs64`, `fstatfs64`; `<ftw.h>` — `ftw64`, `nftw64`; `<glob.h>` — `glob64`, `globfree64`; `<stdlib.h>` — `mkstemp64`, `mkostemp64`, `mkstemps64`, `mkostemps64`; `<aio.h>` — `aio_read64`, `aio_write64`, `lio_listio64` і решта родини на `struct aiocb64`.

**Ім'я без двійника.** Кілька інтерфейсів пізнішого походження оголошено відразу з широким типом і `*64`-варіанту не мають узагалі: `readahead`, `sync_file_range`, `fallocate`, `copy_file_range`. Саме так і варто було робити від початку; так само влаштовано [`statx`](book:unix-linux/statx-extended-stat) — з явно широкими полями замість полів плаваючої ширини.

### Як саме відбувається підміна

Заголовок не перевизначає ім'я макросом (це зламало б `struct` із полем такої назви й будь-яку вашу локальну змінну). Він оголошує ту саму функцію з **іншим асемблерним іменем** — розширенням GCC:

```c
/* так це виглядає в <unistd.h> під __USE_FILE_OFFSET64 */
extern off64_t lseek (int __fd, off64_t __offset, int __whence)
     __asm__ ("lseek64");
```

У тексті програми лишається `lseek`, у об'єктному файлі з'являється звертання до `lseek64`. Звідси й найдешевша перевірка, що саме зібралося — подивитися на невизначені символи об'єктного файлу (у `.o` вони ще без версійних міток, тому читаються чисто):

```sh
$ cc -m32 -c checksum.c -o narrow.o
$ nm -u narrow.o
                 U lseek
                 U open
                 U stat

$ cc -m32 -D_FILE_OFFSET_BITS=64 -c checksum.c -o wide.o
$ nm -u wide.o
                 U lseek64
                 U open64
                 U stat64

$ cc -m32 -D_FILE_OFFSET_BITS=64 -D_TIME_BITS=64 -c checksum.c -o wide64.o
$ nm -u wide64.o
                 U lseek64
                 U open64
                 U __stat64_time64
```

Третя збірка показує, що `_TIME_BITS=64` кладе **свій** шар перейменування поверх першого — і робить це лише там, де структура несе час. Ще одне попередження щодо читання цього виводу: у старіших випусках glibc `stat` узагалі не був окремим символом, бо заголовок розгортав його у виклик `__xstat` із номером версії структури. Там у переліку невизначених треба шукати `__xstat64`, а `stat64` не з'явиться взагалі.

## 4. Системні виклики 32-бітних ABI

Нижче — таблиця для `i386`; номери взято з таблиці викликів ядра. На інших 32-бітних архітектурах номери свої, імена ті самі.

| № | Виклик | Що робить окремим |
|---|---|---|
| 140 | `_llseek` | зсув на вході розбито надвоє, результат — через покажчик |
| 180 | `pread64` | зсув двома словами |
| 181 | `pwrite64` | зсув двома словами |
| 192 | `mmap2` | зсув **в одиницях по 4096 байтів** |
| 193 | `truncate64` | довжина двома словами |
| 194 | `ftruncate64` | довжина двома словами |
| 195 | `stat64` | широка `struct stat64` замість вузької |
| 196 | `lstat64` | те саме |
| 197 | `fstat64` | те саме |
| 220 | `getdents64` | широкі `d_ino`/`d_off` плюс поле `d_type` |
| 221 | `fcntl64` | широка `struct flock64` для блокувань |
| 239 | `sendfile64` | зсув через покажчик на `loff_t` |
| 268 | `statfs64` | широкі лічильники блоків |
| 269 | `fstatfs64` | те саме |
| 272 | `fadvise64_64` | і зсув, і довжина широкі |
| 300 | `fstatat64` | широка структура для форми з якірним дескриптором |

Підпис `_llseek` — найпоказовіший, бо в ньому видно обидва боки тісноти:

```c
int syscall(SYS__llseek, unsigned int fd,
            unsigned long offset_high,   /* старші 32 біти зсуву */
            unsigned long offset_low,    /* молодші 32 біти */
            loff_t *result,              /* сюди ляже новий зсув */
            unsigned int whence);
```

Ядро складає зсув як `(offset_high << 32) | offset_low`. Повертає воно `0` або `−1`, а сам новий зсув пише за покажчиком — регістра повернення для 64-бітного числа не вистачило б. Обгортки в glibc для `_llseek` немає: його викликають лише через `syscall(2)`, а прикладний код звертається до `lseek`/`lseek64`, які цей виклик і роблять.

`mmap2` розв'язує ту саму задачу інакше — не розбиттям, а зміною одиниці:

```c
void *syscall(SYS_mmap2, unsigned long addr, unsigned long length,
              unsigned long prot, unsigned long flags,
              unsigned long fd, unsigned long pgoffset);
```

Зсув `pgoffset` міряють у 4096-байтових одиницях (на `ia64` — у справжніх сторінках системи), тож в одне 32-бітне слово влазить

```
2³² · 4096 = 2⁴⁴ = 16 ТіБ
```

Це стеля [відображення файлу в пам'ять](book:unix-linux/mmap-model) на 32-бітному ABI — і вона нижча за стелю самого `off_t`, тобто вузьким місцем тут лишається виклик, а не тип.

### Узагальнений набір викликів

Архітектури, що беруть спільну (generic) таблицю викликів — `arm64`, `riscv` обох розрядностей, `loongarch`, `csky` — узагалі не називають вузьку й широку форму окремими іменами. Вони визначають **одне** число, а вибір реалізації роблять за шириною машинного слова:

```c
#define __NR3264_lseek     62   /* 32 біти → sys_llseek,     64 біти → sys_lseek     */
#define __NR3264_fstat     80   /* 32 біти → sys_fstat64,    64 біти → sys_newfstat  */
#define __NR3264_fstatat   79   /* 32 біти → sys_fstatat64,  64 біти → sys_newfstatat */
#define __NR3264_truncate  45   /* 32 біти → sys_truncate64, 64 біти → sys_truncate  */
#define __NR3264_mmap     222   /* 32 біти → sys_mmap2,      64 біти → sys_mmap      */
#define __NR3264_fcntl     25   /* 32 біти → sys_fcntl64,    64 біти → sys_fcntl     */
#define __NR3264_statfs    43   /* 32 біти → sys_statfs64,   64 біти → sys_statfs    */
#define __NR3264_sendfile  71   /* завжди sys_sendfile64                             */
```

На 32-бітній цілі ті самі номери потім видно під звичними іменами: `__NR_llseek`, `__NR_fstat64`, `__NR_mmap2`, `__NR_fcntl64`. Зверніть увагу на дрібницю в іменуванні: на `i386` виклик зветься `_llseek` (з підкресленням спереду), в узагальненому наборі — `llseek`.

### Вирівнювання пар регістрів

На 32-бітних `arm`, `mips` і `powerpc` [двійкова угода](book:programming/abi-calling-convention) вимагає, щоб 64-бітний аргумент лягав у пару регістрів, яка починається з **парного** номера. Через це один регістр між аргументами часом пропадає намарне — і ядро додає варіанти виклику з переставленими аргументами, поведінка яких та сама:

```c
/* звичайна форма */
int sync_file_range(int fd, off_t offset, off_t nbytes, unsigned int flags);
/* форма для arm/powerpc — прапорці переїхали на друге місце */
int sync_file_range2(int fd, unsigned int flags, off_t offset, off_t nbytes);

/* на arm, від Linux 2.6.14 — advice переставлено вперед */
long arm_fadvise64_64(int fd, int advice, loff_t offset, loff_t size);
```

Обгортка glibc ховає цю різницю: ви пишете `posix_fadvise` і `sync_file_range`, вона підбирає потрібний виклик для архітектури.

## 5. `O_LARGEFILE`

| Питання | Відповідь |
|---|---|
| Значення | `(1 << 15)` = `0100000` вісімкове в узагальненому наборі; окремі архітектури визначають своє |
| На LP64 | glibc визначає прапорець нулем — він не робить нічого; ядро й так відкриває без обмеження |
| Хто ставить | libc **сама**, коли заголовки зібрано з `_FILE_OFFSET_BITS=64`; `open64`/`openat64`/`creat64` ставлять його завжди |
| Що означає для ядра | «ця програма вміє числа, ширші за 31 біт» |
| Без нього | відкриття звичайного файлу, розмір якого перевищує 2³¹ − 1, дає `EOVERFLOW` |
| Видимість | повертається в наборі бітів від `fcntl(fd, F_GETFL)` |

Прапорець стосується **тільки** відкриття. Дескриптор, отриманий від когось іншого (успадкований через `exec`, переданий сокетом, узятий із `/proc`), уже несе рішення того, хто відкривав, — і ваш макрос на нього не впливає.

## 6. Коди помилок і точні умови

Різниця між двома головними кодами проста, і тримати її в голові варто: **`EOVERFLOW` — число не подати вашими типами** (біда програми), **`EFBIG` — стільки не можна записати** (біда сховища або ліміту).

| Код | Виклик | Точна умова |
|---|---|---|
| `EOVERFLOW` | `open`, `openat`, `creat` | звичайний файл, чий розмір більший за 2³¹ − 1, відкривають без `O_LARGEFILE` на 32-бітній цілі |
| `EOVERFLOW` | `stat`, `fstat`, `lstat`, `fstatat` | хоч одне з полів — `st_size`, `st_ino`, `st_blocks` — не влазить у свій вузький тип |
| `EOVERFLOW` | `readdir` | `d_ino` або `d_off` запису каталогу не подати у вузькому типі; POSIX формулює це як «одне зі значень структури неможливо подати правильно» |
| `EOVERFLOW` | `lseek` | підсумковий зсув не подати в `off_t` — наприклад `SEEK_END` на файлі 3 ГіБ при вузькому типі |
| `EOVERFLOW` | `fcntl(F_GETLK)` | поля [блокування](book:unix-linux/file-locking) не влазять у вузьку `struct flock` |
| `EOVERFLOW` | `statvfs`, `statfs` | лічильники блоків файлової системи ширші за поля структури |
| `EFBIG` | `write`, `pwrite` | запис за максимальний розмір файлу, дозволений реалізацією, або за [`RLIMIT_FSIZE`](book:unix-linux/resource-limits) — у другому випадку процес ще й дістає сигнал `SIGXFSZ` |
| `EFBIG` | `truncate`, `ftruncate` | довжина понад максимум файлової системи |
| `EFBIG` | `open` | **історичне**: до Linux 2.6.24 тут повертали `EFBIG` там, де тепер `EOVERFLOW`. POSIX вимагає саме `EOVERFLOW` |
| `EINVAL` | `lseek` | підсумковий зсув від'ємний, або `whence` не з набору `SEEK_*` |
| `EINVAL` | `mmap` | зсув не кратний розміру сторінки |

Повідомлення, яке glibc виводить для `EOVERFLOW`, звучить як «Value too large for defined data type», і в перекладах воно часто ще менш зрозуміле. Читати його треба буквально: значення завелике для типу — **у вашій програмі**, не на диску.

## 7. `getconf`: прапорці й середовища збирання

POSIX описує ширину зсуву не макросами, а поняттям **середовища збирання**, і дає спосіб дізнатися прапорці для кожного з них у самої системи. Це те, чим користуються скрипти `configure`, коли не хочуть зашивати `-D_FILE_OFFSET_BITS=64` наосліп.

Коротка, специфічна для LFS форма — чотири змінні (за ними стоять сталі `_CS_LFS_*` для `confstr(3)`):

| Змінна | На 32-бітній системі | На 64-бітній |
|---|---|---|
| `LFS_CFLAGS` | `-D_FILE_OFFSET_BITS=64` | порожньо |
| `LFS_LDFLAGS` | порожньо | порожньо |
| `LFS_LIBS` | порожньо | порожньо |
| `LFS_LINTFLAGS` | `-D_FILE_OFFSET_BITS=64` | порожньо |

Ті самі чотири суфікси є й у наборі `LFS64_*` — вони дають прапорці для **перехідного** інтерфейсу (тобто `-D_LARGEFILE64_SOURCE`), а не для підміни типів.

Довга, загальна форма — чотири середовища, чиї назви самі описують ширини: `I` — `int`, `L` — `long`, `P` — вказівник, `OFF` — `off_t`.

| Середовище | вказівник | `long` | `off_t` |
|---|---|---|---|
| `POSIX_V7_ILP32_OFF32` | 32 | 32 | 32 |
| `POSIX_V7_ILP32_OFFBIG` | 32 | 32 | щонайменше 64 |
| `POSIX_V7_LP64_OFF64` | 64 | 64 | 64 |
| `POSIX_V7_LPBIG_OFFBIG` | щонайменше 64 | щонайменше 64 | щонайменше 64 |

Питати систему можна двома способами: чи середовище взагалі підтримується — через `sysconf` зі сталими `_SC_V7_ILP32_OFF32`, `_SC_V7_ILP32_OFFBIG`, `_SC_V7_LP64_OFF64`, `_SC_V7_LPBIG_OFFBIG`; і які саме прапорці — через `confstr` зі сталими виду `_CS_POSIX_V7_ILP32_OFFBIG_CFLAGS`. З командного рядка обидва — через `getconf`:

```sh
# коротка форма: що додати до CFLAGS, щоб зсуви стали широкими
$ getconf LFS_CFLAGS
-D_FILE_OFFSET_BITS=64

# чи підтримується середовище з широким зсувом при 32-бітних вказівниках
$ getconf _POSIX_V7_ILP32_OFFBIG
1

# прапорці конкретного середовища — прапорець -v обирає середовище
$ getconf -v POSIX_V7_ILP32_OFFBIG POSIX_V7_ILP32_OFFBIG_CFLAGS
-D_FILE_OFFSET_BITS=64
```

На 64-бітній системі `getconf LFS_CFLAGS` не виводить нічого, а `getconf _POSIX_V7_ILP32_OFF32` зазвичай дає `undefined` або `-1`: вузького середовища там просто немає.

## 8. Чого немає на 64-бітних ABI

| Немає взагалі | Лишається, попри назву |
|---|---|
| виклики `_llseek`, `mmap2`, `stat64`, `lstat64`, `fstat64`, `fstatat64`, `truncate64`, `ftruncate64`, `fcntl64`, `statfs64`, `fstatfs64`, `sendfile64`, `fadvise64_64`, `sync_file_range2` | виклики `pread64` і `pwrite64` — назви історичні, зсув у них звичайний широкий `off_t` |
| дії макроса `_FILE_OFFSET_BITS` — тип уже широкий | виклик `getdents64`: він відрізняється від `getdents` не лише шириною `d_ino`/`d_off`, а й наявністю `d_type`, тому потрібен і тут |
| ненульового `O_LARGEFILE` — glibc визначає його нулем | символи `lseek64`, `open64`, `stat64` у самій glibc — вони є, але це просто псевдоніми звичайних |
| потреби в `_TIME_BITS` — `time_t` там широкий від початку | `sendfile` реалізовано ядерною функцією `sys_sendfile64` — під одним, звичайним номером |

На `aarch64` картина ще чистіша: там немає навіть `open`, `stat` і `lstat` — лише `openat`, `fstatat` і `statx`. Набір викликів цієї архітектури склали тоді, коли питання ширини вже не стояло.

Одне важливе застереження: усе сказане стосується **рідного** 64-бітного коду. 32-бітна програма, [запущена на 64-бітному ядрі](book:unix-linux/compat-32-on-64), звертається до свого 32-бітного набору викликів через шар сумісності — у таблиці викликів це третя колонка, `compat_sys_*`. Для неї `stat64`, `mmap2` і `_llseek` існують і працюють точно так само.

## 9. Чим glibc відрізняється від musl

| Питання | glibc | musl |
|---|---|---|
| Ширина `off_t` | залежить від `_FILE_OFFSET_BITS` на 32-бітних цілях | **завжди** 64 біти, вузького варіанту немає |
| `_FILE_OFFSET_BITS=64` | вмикає широкий режим | приймається й нічого не міняє — ширшати вже нема куди |
| Ширина `time_t` | залежить від `_TIME_BITS` (від 2.34) | завжди 64 біти, від випуску 1.2.0 |
| Імена `open64`, `lseek64`… | справжні символи в бібліотеці | від випуску 1.2.4 — **лише макроси** й лише під `_LARGEFILE64_SOURCE` |
| Старі двійкові файли, зібрані під `lseek64` | працюють — символ на місці | працюють — динамічний завантажувач перенаправляє їх на звичайне ім'я |
| `getconf` | входить до glibc | окрема програма дистрибутива; ключі `confstr` musl доповнив у 1.2.4 |

Практичний висновок із цієї таблиці один — і він же головна порада всієї довідки. **Пишіть звичайні імена.** `lseek`, `open`, `stat`, `fseeko` працюють скрізь: на glibc під макросом вони стають широкими, на musl вони широкі завжди. Перехідні імена з суфіксом `64`, написані «про всяк випадок», нічого не додають і при цьому ламають збірку на musl без `_LARGEFILE64_SOURCE`.

## 10. Мінімальна перевірка

Програма нижче за одне виконання показує все, що з цієї довідки треба знати про конкретну збірку: справжню ширину типу, реальний розмір файлу й точний код помилки, якщо ширини забракло.

```c
#include <stdio.h>
#include <inttypes.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(int argc, char **argv)
{
    printf("sizeof(off_t) = %zu\n", sizeof(off_t));

    if (argc < 2)
        return 0;

    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        fprintf(stderr, "open: %s (errno %d)\n", strerror(errno), errno);
        return 1;                     /* тут і буде EOVERFLOW = 75 */
    }

    off_t end = lseek(fd, 0, SEEK_END);
    if (end == (off_t)-1) {
        fprintf(stderr, "lseek: %s (errno %d)\n", strerror(errno), errno);
        close(fd);
        return 1;
    }

    /* у власний вивід — явна ширина, а не off_t */
    printf("розмір у байтах = %" PRId64 "\n", (int64_t)end);
    close(fd);
    return 0;
}
```

Зберіть її двічі й проженіть на файлі, більшому за два гігабайти:

```sh
$ cc -m32 probe.c -o narrow
$ cc -m32 $(getconf LFS_CFLAGS) probe.c -o wide

$ ./narrow big.iso
sizeof(off_t) = 4
open: Value too large for defined data type (errno 75)

$ ./wide big.iso
sizeof(off_t) = 8
розмір у байтах = 4700372992
```

Зверніть увагу на рядок виводу розміру. Назовні — у повідомлення, у власний формат файлу, у мережевий пакет — зсув їде як `int64_t` із `<inttypes.h>`, а не як `off_t`. Ширина `off_t` є властивістю збірки, і покласти її в щось довговічне означає зробити довговічну річ залежною від чужого прапорця.
