# 🧮 Ціна роздробленості в числах: поріг суцільності й податок на хвіст

Роздробленість б'є двічі — по часу читання й по зайнятому місцю, — і обидві ціни виводяться в закритому вигляді з кількох рядків арифметики. З першого підрахунку випаде довжина екстента, нижче за яку суцільність ще варта боротьби, а вище — вже ні; з другого — розмір блока під конкретний профіль навантаження. Числа вийдуть разюче асиметричні, і саме ця асиметрія тут головна.

## Час читання як функція кількості екстентів

Послідовне читання файлу розміром `S`, розкладеного в `n` суцільних смуг, розпадається на два доданки, і вони одне одному не заважають.

Перший — передавання самих байтів. Пристрій віддає їх зі швидкістю `B`, і хоч як розкидані шматки, байтів однаково `S`. Цей доданок дорівнює `S/B` і про розкладку не знає нічого.

Другий — плата за початок кожного запиту. Блоковий шар зшиває сусідні блоки в один запит до пристрою, але через розрив зшити не може: за розривом інша адреса, отже, треба починати новий запит. Тож запитів рівно стільки, скільки суцільних смуг, і кожен коштує `t_req`.

```
T = S/B + n·t_req
```

Обидва параметри пристрою не вигадані — вони розкладаються на складники. На обертовому диску 7200 об/хв `t_req` — це переміщення головки плюс очікування, поки потрібний сектор під'їде під головку: повний оберт триває 60/7200 ≈ 8.33 мс, у середньому чекаємо половину, тобто 4.17 мс. Переміщення на сусідню ділянку носія — того самого порядку, близько 4 мс; повністю випадковий доступ по всій пластині коштує помітно більше. Разом близько 8 мс. На NVMe головки немає, і `t_req` — це вартість команди: постановка в чергу, запис у регістр-дзвінок (doorbell) контролера, читання сторінки флешу, повернення відповіді. На черзі глибиною один це десятки мікросекунд; візьмімо 80.

Тепер заміна змінної, після якої формула починає щось казати. Середня довжина екстента `L = S/n`, тобто `n = S/L`:

```
T = S/B + (S/L)·t_req
  = (S/B)·(1 + B·t_req/L)
```

У дужках виникла єдина комбінація параметрів пристрою, яка в цій задачі взагалі можлива, — добуток `B·t_req`. Він має розмірність байтів і пряме прочитання: це стільки даних, скільки пристрій устиг би передати за той час, який коштує один-єдиний запит. Позначмо його `L₀` — власна довжина пристрою.

```
L₀ = B · t_req

T₀ = S/B                          — час ідеального, односмугового читання
k  = T/T₀ = 1 + L₀/L              — у скільки разів довше за ідеал
α  = n·t_req/T = 1/(1 + L/L₀)     — частка часу, з'їдена накладними
```

Уся задача згорнулася в безрозмірне відношення `L/L₀`. Пристрій з іншою швидкістю й іншою затримкою дає ту саму криву, лише зсунуту по осі. Звідси ж і зв'язок двох мір: `k = 1/(1 − α)`.

## Поріг суцільності

Питання «якої довжини екстент уже достатньо довгий» саме собою відповіді не має: `α` спадає плавно, зламу в кривій немає, і жодне значення `L` не є природною межею. Питання набуває сенсу лише тоді, коли названо частку `α`, яку ми згодні платити. Тоді формула розвертається:

```
α = 1/(1 + L/L₀)
1 + L/L₀ = 1/α
    L/L₀ = (1 − α)/α

    L = B·t_req·(1 − α)/α
```

Підставмо числа.

**Власна довжина двох носіїв**

```
диск:  L₀ = 150·10⁶ Б/с · 8·10⁻³ с   = 1.2·10⁶ Б = 1.2 МБ
NVMe:  L₀ = 3·10⁹ Б/с  · 80·10⁻⁶ с   = 2.4·10⁵ Б = 240 кБ

порогова довжина L = L₀·(1−α)/α:

              α = ½     α = 20 %   α = 10 %   α = 5 %
множник        1          4          9         19
диск        1.2 МБ     4.8 МБ    10.8 МБ    22.8 МБ
NVMe        240 кБ     960 кБ     2.16 МБ    4.56 МБ
```

Ось звідки беруться числа, що їх зазвичай подають як досвідні: якщо погодитися віддавати накладним половину часу — а це рівно двократне сповільнення, — то екстент має бути завдовжки з `L₀`, тобто близько мегабайта на диску й близько чверті мегабайта на NVMe. Захочете обмежити втрату десятою часткою — вимоги множаться на дев'ять.

![Дві спадні криві частки накладних α залежно від середньої довжини екстента на шкалі подвоєнь від 4 КіБ до 64 МіБ: верхня для обертового диска з власною довжиною 1.2 МБ, нижня для NVMe з власною довжиною 240 кБ. Горизонтальна пунктирна лінія на рівні α = ½ перетинає кожну криву в точці, де довжина екстента дорівнює власній довжині пристрою](img/fragmentation-threshold.svg)

*Крива та сама для будь-якого носія — міняється лише те, де вона стоїть на осі. Швидший пристрій із меншою затримкою зсуває її ліворуч, але не робить пологішою: форма задана відношенням `L/L₀`, а не самими швидкостями.*

**Перевірка на файлі 4 ГіБ у 41 000 екстентів**

```
L = S/n = 4294967296 / 41000 = 104755 Б ≈ 102 КіБ

диск:  k = 1 + 1.2·10⁶/104755 = 1 + 11.46 = 12.5
       T = 28.6 с + 41000·8 мс = 28.6 + 328 = 357 с      (α = 92 %)

NVMe:  k = 1 + 2.4·10⁵/104755 = 1 + 2.29  = 3.3
       T = 1.43 с + 41000·80 мкс = 1.43 + 3.28 = 4.7 с   (α = 70 %)
```

Один і той самий файл читається в дванадцять з половиною разів довше на диску й у три з третиною — на NVMe. Швидкий носій не рятує, а лише зменшує показник, бо разом зі швидкістю впала й затримка, а важить їхній добуток.

## Де ця модель ламається

Доданок `n·t_req` припускає, що запити йдуть один за одним. Якщо їх подавати по кілька одночасно — черга глибиною `Q`, — накладні перекриваються, і оцінка стає ближчою до `max(S/B, n·t_req/Q)`, а порогова довжина падає в `Q` разів. Для NVMe при `Q = 32` це `240 кБ / 32 ≈ 7.3 КіБ`: роздробленість майже перестає впливати на пропускну здатність.

Слово «майже» тут не ввічливість, а межа застосовності в обидва боки. Перекриття справді працює на твердотільному носії, бо запити розходяться по різних кристалах — [шар трансляції флешу](book:algorithms/ftl-flash-translation) (проміжний рівень усередині SSD, що сам вирішує, у яку фізичну сторінку лягає логічний блок) розкладає їх паралельно. На обертовому диску глибока черга дає лише переупорядкування, яке скорочує середнє переміщення головки, але перекрити його нічим: головка одна. І сама глибина `Q` береться не з повітря — послідовне читання наповнює чергу через [випереджувальне читання](book:unix-linux/readahead) (здогад ядра про наступні блоки, що подає їх наперед), а той здогад ламається якраз на межі екстента. Одинокий читач із `read()` по 4 КіБ і `O_DIRECT` живе рівно при `Q = 1`.

## Податок на хвіст: половина блока

Друга ціна платиться місцем і не має нічого спільного з першою. Файл займає ціле число блоків, а закінчується де завгодно, тож останній блок майже завжди недозаповнений:

```
W(S) = b·⌈S/b⌉ − S
```

Нехай `r = S mod b` — залишок. Тоді `W = 0` при `r = 0` і `W = b − r` в усіх інших випадках. Якщо розміри файлів «випадкові», тобто `r` рівномірно пробігає значення `0 … b−1`, середня втрата рахується одним рядком:

```
E[W] = (1/b)·(0 + (b−1) + (b−2) + … + 1)
     = (1/b)·(b(b−1)/2)
     = (b − 1)/2  ≈  b/2
```

Половина блока на файл — звідси й звичне «на кожному файлі гине півблока». На `N` файлів очікувана втрата `N·b/2`, і зростає вона з кількістю файлів, а не з їхнім обсягом.

Дві застороги, і кожна вирішальна. Перша: рівномірність залишку припускає, що файли значно більші за блок. Файл, менший за блок, втрачає не половину, а всю незайняту решту блока — `b − S`, і при `S ≪ b` це майже цілий блок. Друга: справжні розміри часто не випадкові. GNU tar пише записами по 512 байтів і добиває архів до цілого блока з двадцяти таких записів, тобто до 10240 байтів (документовано в посібнику GNU tar); база даних пише сторінками по 8 або 16 КіБ. Де розміри кратні `b`, хвостова втрата дорівнює нулю, а не половині блока. Тож `b/2` — оцінка для довільних розмірів, а не закон.

## Вибір розміру блока: два профілі

Відносна втрата `η = E[W]/S̄` залежить лише від відношення `b` до середнього розміру файлу — ні кількість файлів, ні обсяг сховища на неї не впливають. Тому відповідь для двох профілів виходить протилежна.

**Мільйон дрібних файлів проти сотні великих**

```
профіль A: N = 10⁶ файлів по 6 КіБ  →  корисних даних 5.72 ГіБ

  b = 4 КіБ:   6 КіБ > b, хвіст ≈ b/2 = 2 КіБ
               втрата = 10⁶ · 2 КіБ = 1.91 ГіБ    → +33 % обсягу
  b = 64 КіБ:  6 КіБ < b, кожен файл бере цілий блок
               втрата = 10⁶ · (64−6) КіБ = 55.3 ГіБ
               зайнято 61.0 ГіБ на 5.72 ГіБ даних  → ×10.7

профіль B: N = 100 файлів по 20 ГіБ →  корисних даних 1.95 ТіБ

  b = 4 КіБ:   втрата = 100 · 2 КіБ  = 200 КіБ    → ≈ 10⁻⁷ обсягу
  b = 64 КіБ:  втрата = 100 · 32 КіБ = 3.1 МіБ    → ≈ 1.5·10⁻⁶ обсягу
```

Що великий блок купує натомість — видно, якщо повернутися до першої формули. Екстент не може бути коротшим за один блок, тому `n ≤ S/b`, а отже, `L ≥ b`: розмір блока ставить підлогу під довжину екстента й тим самим стелю над втратою часу.

```
k ≤ 1 + L₀/b

              b = 4 КіБ    b = 64 КіБ
диск            ×294         ×19.3
NVMe            ×59.6        ×4.7
```

Ця стеля однакова для обох профілів — вона про пристрій, не про файли. Уся різниця між профілями сидить у другому доданку, і саме він вирішує.

Великий блок укорочує ще й саму карту, причому навіть за ідеальної розкладки. Один запис екстента в ext4 покриває щонайбільше 32768 блоків (документація ядра), тож стеля довжини одного запису — це `32768·b`:

```
b = 4 КіБ:   один запис покриває 128 МіБ
             файл 20 ГіБ → щонайменше 160 записів, карта 1920 Б
b = 64 КіБ:  один запис покриває 2 ГіБ
             файл 20 ГіБ → щонайменше 10 записів, карта 120 Б
```

Виграш реальний, але скромний: в inode вміщаються перші чотири записи, а далі карта однаково йде в дерево — і 160, і 10 записів осідають в одному його блоці. Тому вирішує все-таки місце під хвости.

![Таблиця з двох рядків. Перший рядок: мільйон файлів по 6 КіБ, 5.7 ГіБ корисних даних, хвости при блоці 4 КіБ 1.91 ГіБ або плюс 33 відсотки, при блоці 64 КіБ 55.3 ГіБ або в 10.7 раза більше за дані, стеля втрати часу падає з 59 до 4.7, висновок брати 4 КіБ і дрібніше. Другий рядок: сто файлів по 20 ГіБ, 1.95 ТіБ даних, хвости 195 КіБ і 3.1 МіБ, тобто мільйонні частки обсягу, та сама стеля з 59 до 4.7, висновок брати найбільший блок, який дозволяє файлова система](img/block-size-tradeoff.svg)

*Функція ціни однобока: збільшення блока завжди трохи допомагає часу й завжди шкодить місцю — питання лише в тому, чи помітна шкода на цьому профілі.*

Звідси й правило вибору. Задамо припустиму відносну втрату, скажімо один відсоток: з `b/(2·S̄) ≤ 0.01` виходить `b ≤ 0.02·S̄`. Для профілю B це `b ≤ 410 МіБ` — обмеження не діє взагалі, і брати треба найбільший блок, який дозволяє файлова система. Для профілю A це `b ≤ 123 байти` — величина, менша за будь-який блок, тобто на дрібних файлах відсотком не обійтися жодним вибором `b`. Зменшення блока лише пом'якшує втрату (при 512 байтах вона падає до 4.2 %), а прибирає її вже інший механізм: дані найдрібніших файлів кладуть у сам [inode](book:unix-linux/inode-model) (запис із властивостями файлу), не витрачаючи блока взагалі. В ext4 це `inline_data`: 60 байтів у полі `i_block` і ще трохи в просторі розширених атрибутів — близько 160 байтів у 256-байтовому inode (документація ядра).

Наостанок — обмеження, яке довго робило колонку «64 КіБ» умоглядною. Блок файлової системи традиційно не міг перевищувати сторінку пам'яті, тож на x86 зі сторінкою 4 КіБ великих блоків просто не існувало. Розв'язали це нещодавно: підтримка блоків, більших за сторінку, увійшла в ядро 6.12 для XFS — щоб зробити такий том на x86, потрібні і свіже ядро, і свіжі `xfsprogs`; згодом те саме дістав btrfs, для ext4 патчі ще готують. Обхідний шлях, який працював і раніше, — ext4 `bigalloc`: блок лишається дрібним, але одиницею виділення стає кластер із кількох блоків. Для арифметики вище це те саме: у формулах `b` — не «розмір блока» як такий, а мінімальна одиниця, якою розподільник узагалі вміє оперувати.
