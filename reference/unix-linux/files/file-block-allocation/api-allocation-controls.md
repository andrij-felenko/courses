# 📋 Керування виділенням блоків: виклики, прапорці монтування й ручки

Це довідка по важелях, якими програма й адміністратор впливають на те, де саме файлова система розкладе блоки файлу: один системний виклик, один `ioctl`, кілька прапорців монтування, кілька файлів у `/sys` і `/proc` — і жменя утиліт, які показують результат і виправляють його заднім числом. Тут сигнатури, точні назви, усталені значення й обмовки, через які важіль не спрацьовує.

Важелі стоять на трьох різних рівнях, і плутати їх дорого. **Програма** знає найбільше — вона одна може назвати точний розмір, — але вміє це лише через `fallocate` і підказку довжини екстента. **Створення файлової системи** закладає геометрію носія: розмір смуги масиву запікається в суперблок і далі мовчки керує кожним виділенням. **Монтування й `/sys`** правлять евристики, коли перші два рівні не спрацювали або збрехали. Що нижче рівень, то ширша дія й то менше в ній знання про конкретний файл.

Найкоротший орієнтир, з якого починається вибір:

| задача | чим | ключова обмовка |
|---|---|---|
| розмір відомий наперед | `fallocate(fd, 0, …)` | резервує ще й ті блоки, які лишаться порожніми — місце зайняте одразу |
| розмір відомий, але `st_size` міняти не можна | `fallocate` + `FALLOC_FL_KEEP_SIZE` | `du` покаже більше, ніж `ls` |
| файл росте порціями, розмір невідомий | XFS: підказка `extsize`; ext4: `stripe=` | підказка про **довжину порції**, а не про кінцевий розмір |
| потік дрібних файлів має лягти купно | ext4 `mb_stream_req`, `mb_group_prealloc` | ручки скидаються на розмонтуванні |
| файл переписують випадково на місці | Btrfs: `chattr +C` | лише на **порожньому** файлі; знімає й контрольні суми |
| дізнатися, що вийшло | `filefrag -e -s` | без `-s` міряєте намір, а не носій |
| виправити вже написане | `e4defrag`, `xfs_fsr`, `btrfs fi defragment` | коштує повного читання й запису; на Btrfs розриває поділ блоків |

## Сказати розмір наперед

```c
#define _GNU_SOURCE
#include <fcntl.h>

int fallocate(int fd, int mode, off_t offset, off_t len);
```

Для керування розміщенням цікаві рівно два значення `mode`.

| `mode` | що робить із блоками | що робить із `st_size` |
|---|---|---|
| `0` | закріплює блоки під увесь діапазон, позначає їх незаписаними | росте до `offset + len` |
| `FALLOC_FL_KEEP_SIZE` (`0x01`) | те саме | не міняється |

Різниця лише в обліку довжини, і саме через неї `KEEP_SIZE` доречний там, де формат файлу сам знає свій кінець: журнал, кільцевий буфер, сегмент бази. Решта режимів (`PUNCH_HOLE`, `ZERO_RANGE`, `COLLAPSE_RANGE`, `INSERT_RANGE`, `UNSHARE_RANGE`) до виділення стосунку не мають — їхні значення, вимоги до вирівнювання, таблиця підтримки по файлових системах і повний перелік `errno` зібрані в [контракті розріджених операцій](topic:unix-linux/sparse-files/api-sparse-syscalls.md).

Три обмовки, які вирішують, спрацює важіль чи ні.

**`EOPNOTSUPP` — звичайна відповідь.** Виклик підтримують ext4, XFS, Btrfs, tmpfs; не підтримують багато мережевих і саморобних файлових систем. Запасна гілка потрібна завжди.

**Резервування не робить карту суцільною.** Один стогігабайтний незаписаний екстент, заповнений випадковими записами по 8 КіБ, розпадеться на тисячі записів у карті — просто сусідніх. Місце суцільне, карта — ні.

**`posix_fallocate(3)` — не синонім.**

```c
#include <fcntl.h>
int posix_fallocate(int fd, off_t offset, off_t len);
```

Він повертає код помилки **як значення** й не чіпає `errno`. Головне ж: коли системний виклик відмовляє з `EOPNOTSUPP`, glibc не здається, а **дописує весь діапазон нулями вручну**. Резервування терабайта перетворюється на запис терабайта — і на мережевій файловій системі це помітно негайно. Ту саму поведінку утиліта `fallocate(1)` вмикає прапорцем `-x`, і робить це навмисно: «завершиться завжди, хай і довго».

Звідси й правило вибору: `fallocate` тоді, коли повільний запасний шлях **неприйнятний** і краще дізнатися про відмову одразу; `posix_fallocate` тоді, коли місце потрібне за будь-яку ціну й затримка терпима.

### Мінімальний виклик

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <errno.h>

enum reserve_result { RESERVE_OK, RESERVE_UNSUPPORTED, RESERVE_FAILED };

/* Закріпити місце під файл наперед — без тихого запису нулів. */
enum reserve_result reserve_space(int fd, off_t bytes)
{
    if (fallocate(fd, 0, 0, bytes) == 0)
        return RESERVE_OK;

    if (errno == EOPNOTSUPP || errno == ENOSYS)
        return RESERVE_UNSUPPORTED;  /* ФС або ядро не вміють */

    return RESERVE_FAILED;           /* ENOSPC, EFBIG, EIO — справжня відмова */
}
```

Розрізняти «не вміє» і «не змогло» тут обов'язково, і саме тому відповідей три, а не дві: `RESERVE_UNSUPPORTED` означає, що гарантії немає й `ENOSPC` прилетить пізніше, під час запису; `RESERVE_FAILED` — що місця немає вже зараз і писати нема куди.

## Геометрія масиву: закладається на створенні

Якщо носій — RAID або логічний том зі смугами, найдієвіший важіль спрацьовує ще до першого файлу. Розподільник, який знає ширину смуги, вирівнює по ній свої запити, і одне велике записування лягає на всі диски рівно; розподільник, який її не знає, регулярно кладе запис через межу смуги й змушує масив читати-перераховувати-писати парність.

| ФС | де задається | одиниця |
|---|---|---|
| ext4 | `mke2fs -E stride=<n>,stripe_width=<n>` | блоки ФС: `stride` — шматок, що лягає на один диск; `stripe_width` = `stride × кількість дисків з даними` (для RAID5 — усі диски мінус один) |
| XFS | `mkfs.xfs -d su=<байти>,sw=<кратність>` або `-d sunit=,swidth=` | `su`/`sw` — байти й кратність до `su`; `sunit`/`swidth` — блоки по 512 Б |

Обидві родини вміють підхопити геометрію самі, коли пристрій про неї повідомляє (програмний RAID, `dm`, багато апаратних контролерів). Перевіряти варто завжди: `xfs_info` для XFS, `dumpe2fs -h` для ext4 — числа `sunit`/`swidth` і `RAID stride`/`RAID stripe width` у виводі не мають бути нулями там, де смуги є. Прапорці монтування (`stripe=` в ext4, `sunit=`/`swidth=` у XFS, у блоках по 512 Б) ці значення лише перекривають — на вже створеній ФС це єдиний шлях виправити помилку `mkfs`.

## XFS: підказка довжини й спекулятивний запас

XFS дозволяє прямо сказати розподільнику, якими порціями різати файл, — це **підказка розміру екстента** (extent size hint). Ставиться вона тим самим `ioctl`, що й прапорці inode; назва історична й оманлива — до розширених атрибутів із `getfattr` це не має стосунку.

```c
#include <linux/fs.h>

struct fsxattr {
    __u32         fsx_xflags;      /* прапорці FS_XFLAG_* */
    __u32         fsx_extsize;     /* підказка довжини, БАЙТИ */
    __u32         fsx_nextents;    /* лише читання: скільки екстентів зараз */
    __u32         fsx_projid;
    __u32         fsx_cowextsize;  /* те саме для копіювання під час запису */
    unsigned char fsx_pad[8];
};

ioctl(fd, FS_IOC_FSGETXATTR, &fsx);   /* прочитати */
ioctl(fd, FS_IOC_FSSETXATTR, &fsx);   /* записати */
```

| прапорець у `fsx_xflags` | значення |
|---|---|
| `FS_XFLAG_EXTSIZE` | розподільник виділяє кратно `fsx_extsize`; **можна поставити лише на файл без жодного виділеного екстента** |
| `FS_XFLAG_EXTSZINHERIT` | ставиться на **каталог**: нові файли й підкаталоги успадковують і прапорець, і значення |
| `FS_XFLAG_COWEXTSIZE` | те саме для екстентів, у які лягає копіювання під час запису |

Значення в байтах і має бути кратне розміру блока файлової системи. Нуль у `fsx_extsize` разом із виставленим `FS_XFLAG_EXTSIZE` знімає й сам прапорець.

З оболонки те саме робить `xfs_io` — і саме через каталог, бо на непорожній файл підказку вже не почепиш:

```sh
$ xfs_io -c "extsize 16m" /srv/vm          # каталог: успадкують усі нові файли
$ qemu-img create -f raw /srv/vm/disk.img 100G
$ xfs_io -c extsize /srv/vm/disk.img       # прочитати успадковане
[16777216] /srv/vm/disk.img
```

Два інші важелі XFS не вимагають нічого від програми.

| важіль | де | усталення | що робить |
|---|---|---|---|
| `allocsize=<розмір>` | [прапорець монтування](topic:unix-linux/mount-model) | динамічний | фіксує спекулятивний запас за кінцем файлу; від розміру сторінки до 1 ГіБ, лише степені двійки. **Явне значення вимикає динамічну поведінку** — саме в цьому й сенс, коли евристика хибить |
| `/proc/sys/fs/xfs/speculative_prealloc_lifetime` | [sysctl](topic:unix-linux/sysctl-tunables) | `300` (с) | як часто фоновий обхідник підрізає невитрачений запас у файлів, у які перестали писати; межі 1…86400 |

Запас повертається й сам — на закритті файлу та на вивільненні inode; обхідник потрібен для тих, що лежать відкриті й мовчать. Це й пояснює звичне здивування: `du` одразу після запису показує більше, ніж у файлі байтів, а за кілька хвилин число саме падає.

Різниця між двома важелями XFS принципова, і плутають їх постійно. `extsize` — це **мінімальна порція виділення**: файл ростиме кроками по 16 МіБ, і кожен крок буде суцільним. `allocsize` — це **запас за кінцем файлу**, який тримають про запас і зрештою підріжуть. Перший потрібен, коли ви знаєте характер файлу (образ ВМ, сегмент бази); другий — коли евристика XFS помиляється щодо всієї файлової системи одразу, наприклад роздає гігабайтні запаси тисячі дрібних файлів, які ніколи не виростуть.

## ext4: відкладення, смуга масиву й запаси розподільника

В ext4 окремої підказки довжини на файл немає — усе керування зосереджене в багатоблоковому розподільнику (mballoc), і крутять його прапорцями монтування та файлами в `/sys`.

| прапорець монтування | усталення | що робить |
|---|---|---|
| `delalloc` | увімкнено | виділення відкладається до виштовхування з [кешу сторінок](topic:unix-linux/page-cache-durability) |
| `nodelalloc` | — | блоки обираються ще на `write`; потрібен лише для діагностики й для дуже старих програм |
| `stripe=<n>` | з суперблока | скільки блоків ФС розподільник бере за одиницю розміру й вирівнювання. Для RAID5/6 — «кількість дисків з даними × шматок масиву, у блоках ФС» |
| `mb_optimize_scan=0\|1` | за розміром ФС | інший порядок обходу груп блоків, який рятує на сильно роздробленій ФС |

Останній варто розписати. Замість лінійного обходу груп розподільник тримає їх упорядкованими за найбільшою вільною ділянкою й одразу йде туди, де смуга потрібної довжини справді є, — на роздробленій системі це скорочує пошук у рази. Усталення ядро обирає само за кількістю груп блоків: увімкнено, коли їх щонайменше 16 (`MB_DEFAULT_LINEAR_SCAN_THRESHOLD`), вимкнено на менших ФС; прапорець потрібен лише щоб перекрити цей вибір, і приймає він рівно `0` або `1`. З'явився важіль у ядрі 5.13 (коміт `196e402adf2e`, «ext4: improve cr 0 / cr 1 group scanning»), а після переходу ext4 на новий інтерфейс монтування розібране значення затиралося усталенням — працювати як слід він знову став із 5.17. На обертових дисках і дешевій флеші після нього траплялися просідання швидкості, тому важіль двобічний: він міняє те, який блок ви дістанете, а не лише те, як довго його шукали.

Тонше налаштування живе в `/sys/fs/ext4/<пристрій>/` (`<пристрій>` — ім'я блокового пристрою, наприклад `dm-0`). Ручки живуть лише доти, доки файлова система змонтована: розмонтували — усе повернулося до усталень, тож постійне значення ставлять правилом udev або файлом `tmpfiles.d`.

| файл | усталення | що означає |
|---|---|---|
| `mb_stream_req` | `16` блоків | запити, менші за це, обслуговуються зі **спільного запасу групи локальності** (щоб дрібні файли лягли купно); більші отримують власний запас на inode |
| `mb_group_prealloc` | `512` блоків | до кратного цьому числу округляються запити — **але лише коли `stripe` у суперблоці не заданий**; заданий `stripe` цю ручку перекриває |
| `mb_max_to_scan` | `200` | скільки екстентів розподільник щонайбільше передивиться, шукаючи найкращий |
| `mb_min_to_scan` | `10` | скільки він передивиться щонайменше |
| `mb_order2_req` | `2` | від якого степеня двійки вмикається пошук по buddy-картах вільних блоків |
| `delayed_allocation_blocks` | лише читання | скільки блоків зараз чекає на адресу — пряме вимірювання глибини відкладення |

## Btrfs: вимкнути копіювання під час запису

Тут корінь роздробленості інший — [копіювання під час запису](topic:unix-linux/copy-on-write) переносить кожен змінений блок у нове місце, — тож і важелі інші.

| важіль | як | обмовка |
|---|---|---|
| `chattr +C файл` | знімає копіювання під час запису для цього файлу | **лише на порожньому файлі**; знімає й контрольні суми, і стиснення |
| `chattr +C каталог` | нові файли в ньому успадкують ознаку | наявні файли не змінюються — правильний спосіб «зробити +C» для образу ВМ: створити порожній, позначити, тоді наповнити |
| `-o nodatacow` | те саме для всієї ФС | тягне за собою `nodatasum` і вимикає стиснення; усі створені файли дістають ознаку NOCOW |
| `-o autodefrag` | дрібні випадкові записи (нині — у межах 64 КіБ) виявляються й ставляться в чергу на ущільнення | працює на записі, а не разово; для великих файлів баз даних дорожчий за `+C` |

Ознака `+C` не абсолютна: якщо файл потрапив у знімок, наступний запис у спільний блок усе одно зробить копію — інакше знімок перестав би бути знімком.

## Виміряти й полагодити

Жоден із важелів вище не дає квитанції: `fallocate` повертає нуль, а чи лягли блоки суцільно — питання окреме. Відповідь дає одна утиліта.

```sh
$ filefrag -e -s /srv/vm/disk.img
```

| ключ `filefrag` | що дає |
|---|---|
| `-e` | вивід у форматі екстентів навіть для ФС без екстентів |
| `-s` | синхронізувати файл **перед** запитом карти — без цього на ext4 видно наміри відкладеного виділення, а не носій |
| `-v` | повна таблиця замість підсумкового рядка |
| `-b<розмір>`, `-k` | одиниця, у якій друкувати зсуви (типово 1024 Б) |
| `-X` | номери блоків шістнадцятково |

Ущільнення на живій, змонтованій системі:

| утиліта | як працює | що варто знати |
|---|---|---|
| `e4defrag файл` | створює тимчасовий файл-донор, резервує йому суцільну смугу й викликає `EXT4_IOC_MOVE_EXT`, який міняє екстенти місцями між двома inode | inode, ім'я та вміст оригіналу лишаються ті самі; дані йдуть через кеш навмисно — щоб не змагатися з тими, хто відобразив файл у пам'ять |
| `xfs_fsr` | копіює файл у тимчасовий (`.fsr*` у тому ж каталозі) і атомарно міняє екстенти місцями | без аргументів обходить **усі** змонтовані XFS; `-t` обмежує час, усталено 7200 с; місце зупинки запам'ятовує у `/var/tmp/.fsrlast_xfs` |
| `btrfs filesystem defragment -r -t 32M шлях` | переписує екстенти, менші за `-t` (усталено 32 МіБ) | `-r` не заходить у вкладені підтоми — їх треба перелічувати окремо |

⚠️ **Ущільнення на Btrfs розриває поділ блоків.** Якщо файл ділив екстенти зі знімком, із дедуплікованим двійником або з [копією через reflink](topic:unix-linux/reflink-copies), після дефрагментації він дістане власні — і зайняте місце зросте рівно на розмір того, що доти було спільним. Поведінка стосується ядер `< 3.9` і `≥ 3.14-rc2`, а зі стабільних гілок — `≥ 3.10.31`, `≥ 3.12.12`, `≥ 3.13.4`, тобто практично всіх, які сьогодні можна зустріти. Тому на носії зі знімками дефрагментацію планують за вільним місцем, а не за роздробленістю: перевіряти треба не «наскільки погано лежить файл», а «чи переживе носій те, що спільне стане окремим».

## Межа всіх цих важелів

Спільна обмовка одна, і вона над усіма таблицями: **розподільник не може видати суцільну смугу, якої на носії немає.** `fallocate` на файлову систему, де вільне місце розсипане дірками по 64 КіБ, чесно поверне нуль — і дасть тисячі екстентів замість одного. Підказка `extsize` у тих самих умовах стане побажанням, яке нікому виконати. Тому перш ніж крутити ручки, дивляться на розподіл вільного простору — гістограму вільних ділянок за довжиною:

```sh
$ e2freefrag /dev/mapper/data              # ext4
$ xfs_db -r -c "freesp -s" /dev/mapper/data   # XFS, читання на змонтованій
```

Якщо найдовша вільна смуга коротша за те, що ви просите, жоден важіль із цієї довідки не спрацює — лікувати треба заповненість і сусідство навантажень, а не виклики.
