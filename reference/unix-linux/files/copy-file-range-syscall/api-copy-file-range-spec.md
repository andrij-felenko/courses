# 📋 Повна специфікація та семантика системного виклику copy_file_range

Ця довідкова вставка містить вичерпну технічну специфікацію системного виклику `copy_file_range(2)`, деталізуючи його C/C++ сигнатуру, семантику параметрів, правила обробки вказівників зміщення, розширену матрицю кодів помилок `errno`, системні перевірки прав доступу, а також хронологію розвитку поведінки у ядрах Linux та системній бібліотеці `glibc`.

## Сигнатура та заголовні файли

Системний виклик `copy_file_range(2)` оголошено у заголовному файлі `<unistd.h>`. Для роботи з типом `loff_t` на 32-бітних та 64-бітних архітектурах Linux додатково підключається `<sys/types.h>`. Початкове визначення системного виклику у ядрі реалізовано у файлі `fs/read_write.c`.

:::tabs
```c
#define _GNU_SOURCE
#include <unistd.h>
#include <sys/types.h>

ssize_t copy_file_range(int fd_in, loff_t *off_in,
                        int fd_out, loff_t *off_out,
                        size_t len, unsigned int flags);
```
```cpp
#include <unistd.h>
#include <sys/types.h>
#include <cstddef>

// У C++ системний виклик доступний у глобальному просторі імен або через ::copy_file_range
extern "C" {
    ssize_t copy_file_range(int fd_in, loff_t *off_in,
                            int fd_out, loff_t *off_out,
                            size_t len, unsigned int flags);
}
```
:::

## Внутрішній контракт VFS та структура file_operations

Усередині ядра Linux системний виклик `copy_file_range` транслюється у виклик внутрішнього вказівника структури `struct file_operations` відповідного драйвера файлової системи:

```c
struct file_operations {
    /* ... інші вказівники на операції VFS ... */
    ssize_t (*copy_file_range)(struct file *file_in, loff_t pos_in,
                               struct file *file_out, loff_t pos_out,
                               size_t len, unsigned int flags);
    /* ... */
};
```

Якщо конкретна файлова система реалізує свій специфічний хук (наприклад, `btrfs_copy_file_range` у Btrfs або `xfs_file_copy_file_range` у XFS), VFS передає управління безпосередньо коду ФС. Якщо вказівник у структурі `file_operations` дорівнює `NULL`, VFS застосовує стандартний універсальний алгоритм `generic_copy_file_range()`.

## Семантика аргументів та функціональний контракт

Параметри системного виклику визначають операнди джерела, цілі та геометрію передачі даних у межах файлового простору:

- `fd_in` (вхідний файловий дескриптор): файловий дескриптор, з якого зчитуються дані. Об'єкт опису відкритого файлу повинен бути відкритий у режимі, що дозволяє читання (`O_RDONLY` або `O_RDWR`). Повинен вказувати на звичайний дисковий файл (`S_ISREG`).
- `off_in` (вказівник на зміщення джерела):
  - Якщо `off_in == NULL`, копіювання починається з поточної позиції каретки (file offset) опису відкритого файлу `fd_in`. Після завершення виклику позиція каретки `fd_in` зміщується вперед на кількість реально скопійованих байтів.
  - Якщо `off_in != NULL`, він вказує на змінну типу `loff_t`, яка задає початкову байтову позицію в `fd_in`. Після повернення з виклику значення за вказівником `off_in` атомарно збільшується на кількість скопійованих байтів, а каретка дескриптора `fd_in` залишається незмінною.
- `fd_out` (вихідний файловий дескриптор): файловий дескриптор, у який записуються дані. Об'єкт повинен бути відкритий у режимі, що дозволяє запис (`O_WRONLY` або `O_RDWR`). `fd_out` не може вказувати на файл, відкритий з прапорцем `O_APPEND`.
- `off_out` (вказівник на зміщення цілі):
  - Якщо `off_out == NULL`, запис виконується з поточного зміщення каретки `fd_out`, і позиція каретки зміщується на обсяг скопійованих даних.
  - Якщо `off_out != NULL`, запис починається із позиції `*off_out`, значення `*off_out` оновлюється наприкінці виклику, а каретка `fd_out` не змінюється.
- `len` (бажана довжина): максимальна кількість байтів для копіювання за один системний виклик.
- `flags` (прапорці): зарезервоване ядром Linux поле. Наразі повинно дорівнювати `0`.

## Типи даних зміщення та сумісність з Large File Support (LFS)

Тип `loff_t` є signed 64-бітним цілим числом у ядрі Linux (`long long`), що дозволяє адресувати позиції у файлах розміром до `9223372036854775807` байтів (8 ЕіБ, ексбібайт).

На 32-бітних архітектурах Linux (наприклад, x86 або ARM32) для забезпечення коректної роботи з 64-бітними зміщеннями застосунок повинен компілюватися з макросом `#define _FILE_OFFSET_BITS 64` або використовувати типізовані виклики LFS. Системна бібліотека `glibc` автоматично транслює виклик у номер системного виклику `__NR_copy_file_range`. На архітектурі x86_64 цей системний виклик має номер `326` у таблиці `arch/x86/entry/syscalls/syscall_64.tbl`.

## Обмеження дескрипторів у режимі O_PATH

Спроба передати файловий дескриптор, відкритий із прапорцем `O_PATH` (дескриптор, призначений виключно для маніпуляцій з інодом та шляхом у файловій системі без надання прав читання/запису вмісту), відхиляється VFS на етапі валідації. Системний виклик `copy_file_range` повертає помилку `EBADF`, оскільки прапор `O_PATH` унеможливлює виконання операцій зчитування або перезапису блоків файлу.

## Значення, що повертаються

- `> 0`: кількість успішно скопійованих байтів. Це число може бути меншим за запрошений параметр `len` (коротке копіювання, short copy).
- `0`: досягнуто кінця вихідного файлу (`EOF`) або аргумент `len` дорівнює `0`.
- `-1`: виникла помилка. Глобальна змінна `errno` встановлюється у відповідний системний код.

## Матриця кодів помилок (errno)

При виникненні збою `copy_file_range` повертає `-1` і виставляє один із наступних кодів у змінній `errno`:

- `EBADF`: дескриптор `fd_in` не відкритий на читання, або `fd_out` не відкритий на запис, або один із дескрипторів є недійсним файловим дескриптором процесу чи відкритий з `O_PATH`.
- `EINVAL`: зафіксовано недійсний аргумент або порушення семантики:
  - Передано прапорці `flags != 0`.
  - Файловий дескриптор `fd_out` відкритий з прапорцем `O_APPEND`.
  - Дескриптори `fd_in` та `fd_out` посилаються на один і той самий файл (`inode`), і діапазони копіювання перекриваються без підтримки CoW reflink.
  - Вказівник `off_in` або `off_out` містить негативне зміщення (`< 0`).
- `EISDIR`: один із дескрипторів `fd_in` або `fd_out` посилається на каталог (directory), а не на звичайний файл.
- `ENOSYS`: системний виклик `copy_file_range` не реалізовано у поточному ядрі Linux (ядро старше за 4.5 або архітектура не має табличного номера виклику).
- `EXDEV`: файлові системи `fd_in` та `fd_out` розташовані на різних змонтованих пристроях чи суперблоках, і ядро у даній версії не підтримує міжфайловосистемний offload чи VFS-фолбек.
- `EOVERFLOW`: запрошений діапазон копіювання перевищує максимально допустиме зміщення у файлі (`MAX_LFS_FILESIZE`) для даної 32/64-бітної архітектури або файлової системи.
- `ETXTBSY`: цільовий файл є виконуваним файлом бінарної програми, який наразі виконується ядром і заблокований для запису.
- `EOPNOTSUPP`: файлова система під описом `fd_in` чи `fd_out` не реалізує внутрішню операцію копіювання та забороняє базовий VFS-фолбек.
- `EIO`: виникла апаратна помилка введення-виведення при зчитуванні з дискового носія або записі на нього.
- `ENOSPC`: на цільовій файловій системі недостатньо вільного дискового простору для розміщення скопійованих блоків.
- `EPERM` / `EACCES`: операцію блоковано модулем безпеки Linux (SELinux, AppArmor) або відсутні необхідні права доступу до файлу.

## Перевірки прав доступу та безпеки

Власної перевірки прав у `copy_file_range` немає: усе вирішено раніше, на етапі `open(2)`, а виклик лише звіряє режими вже відкритих описів файлів:

1. **Режими відкриття файлів**: `fd_in` має бути відкритий на читання, `fd_out` — на запис. Права на самі файли (у тому числі обхід перевірок через `CAP_DAC_OVERRIDE` для чужих файлів) перевірено ще при відкритті.
2. **Модулі безпеки (LSM)**: SELinux та AppArmor судять ті самі дозволи на читання й запис, що й для звичайних `read`/`write` над цими описами файлів.

## Особливості обробки сигналів та прапорець SA_RESTART

При отриманні асинхронного сигналу під час виконання тривалого копіювання у ядрі (наприклад, при generic-копіюванні великого блоку) системний виклик `copy_file_range` поводиться згідно зі стандартами POSIX:

- Якщо частину даних уже передано, виклик повертає саме цю кількість байтів, а не `-1`: прозоро «дорахувати» решту ядро не може, тож поновлення з нового зміщення лишається обов'язком застосунку, і `SA_RESTART` тут нічого не змінює.
- Якщо сигнал перервав виклик до передачі першого байта, повертається `-1` з `errno = EINTR`, і цикл копіювання просто повторює спробу з тим самим зміщенням.

## Реалізації у системних бібліотеках musl та Bionic

Окрім системної бібліотеки `glibc`, виклик `copy_file_range` підтримується іншими стандартними бібліотеками C у світі Linux:

- **musl libc**: Застосовується у дистрибутивах Alpine Linux. Бібліотека `musl` надає пряму обгортку над системним викликом ядра `__NR_copy_file_range` без жодної внутрішньої емуляції у користувацькому просторі. Якщо ядро не підтримує виклик, повертається `ENOSYS`.
- **Bionic (Android libc)**: обгортка з'явилася порівняно пізно, тож на старших рівнях Android API виклик доступний лише напряму через `syscall(__NR_copy_file_range, …)`. Емуляції у користувацькому просторі Bionic, як і musl, не робить.

## Реалізації у суміжних операційних системах

Концепція offload-копіювання на боці сховища присутня і у інших сучасних операційних системах:

- **FreeBSD**: З версії FreeBSD 13.0 додано системний виклик `copy_file_range(2)` із точно такою самою сигнатурою та семантикою операндів, як і в Linux.
- **macOS / Darwin**: У файловій системі APFS реалізовано системний виклик `clonefile(2)`, який виконує Copy-on-Write клонування іноду на рівні метаданих.
- **Windows / Win32 API**: Використовуються керуючі коди файлових систем `FSCTL_DUPLICATE_EXTENTS_TO_FILE` (для ReFS) та `FSCTL_SRV_COPYCHUNK` (для SMB серверів).

## Еволюція поведінки у ядрах Linux

Механізм `copy_file_range` проходив кілька ключових етапів розвитку у ядрі Linux:

- **Linux 4.5**: Перша поява системного виклику. Операція працювала виключно в межах однієї файлової системи (однаковий `struct super_block`). Копіювання між різними файловими системами завершувалося помилкою `EXDEV`.
- **Linux 5.3**: Впроваджено базовий VFS-фолбек `generic_copy_file_range()`. Якщо файлові системи `fd_in` та `fd_out` відрізнялися, ядро більше не повертало `EXDEV`, а автоматично виконувало передачу даних у ядрі через `pagecache` та `splice`.
- **Linux 5.19**: Прихований міжфайловосистемний фолбек скасовано. Копіювання через межу файлових систем лишилося дозволеним лише тоді, коли обидві ФС одного типу й самі реалізують таке перенесення; в решті випадків знову повертається `EXDEV`. Причиною були псевдо- та мережеві ФС (CIFS/SMB, OverlayFS, FUSE, tracefs), де generic-фолбек міг мовчки дати неправильний результат.

## Зміна поведінки у бібліотеці glibc

Обгортка `copy_file_range()` з'явилася у системній бібліотеці `glibc 2.27`.

- **Glibc 2.27 – 2.30**: Бібліотека мала вбудовану емуляцію у користувацькому просторі. Якщо ядро повертало `ENOSYS` або `EXDEV`, `glibc` приховано виконувала звичайний цикл зчитування-запису через внутрішній буфер у User Space.
- **Glibc 2.31**: Приховану емуляцію було повністю вилучено. Причина полягала у тому, що емуляція створювала ілюзію успішного hardware/CoW-offloading, спричиняла непомітні падіння продуктивності, не гарантувала атомарності та заважала застосункам коректно обробляти помилки `EXDEV`/`ENOSYS`. З версії 2.31 `glibc` повертає точний результат системного виклику ядра.

Розробники системного програмного забезпечення повинні враховувати цю еволюцію при підтримці старих ядер Linux.
