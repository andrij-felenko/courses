# 📜 Історія shared-disk кластерних файлових систем: від VAXclusters до GFS2 та OCFS2

Кластерні файлові системи з прямим доступом до спільного диска (*shared-disk cluster filesystems*) виникли як відповідь на апаратну революцію початку 1980-х років: появу мереж зберігання даних (*Storage Area Network*, SAN) та дискових масивів із декількома портами вводу-виводу. Можливість під'єднати десяток незалежних комп'ютерів до одного фізичного дискового накопичувача обіцяла колосальну швидкість паралельної обробки, проте одразу вперлася в фундаментальну перешкоду — відсутність апаратної координації між незалежними операційними системами. Історія розвитку GFS2 та OCFS2 — це чотири десятиліття еволюції розподіленого узгодження кешів, менеджерів блокувань та архітектур аварійного відновлення.

## Народження розподіленого блокування: DEC VAXclusters та VMS DLM (1983)

Першу комерційно успішну архітектуру зі спільним дисковим простором представила корпорація Digital Equipment Corporation (DEC) у 1983 році для операційної системи VAX/VMS під назвою VAXcluster. Інженери DEC з'єднали комп'ютери VAX високошвидкісною шиною CI (*Computer Interconnect*) та під'єднали їх до спільних дискових контролерів HSC50. Кожен процесор виконував власну копію операційної системи й міг напряму надсилати дискові команди до накопичувачів, оминаючи посередників.

Щоб запобігти взаємному знищенню файлової структури Files-11 On-Disk Structure Level 2 (ODS-2), інженери DEC створили Distributed Lock Manager (DLM) — розподілений менеджер блокувань. Саме в VMS DLM було сформульовано класичну модель із шістьма режимами блокування (від `Null` до `Exclusive`), концепцію просторів імен ресурсів (*lockspaces*) та механізм асинхронних пасток:

* **CAST (*Completion Asynchronous System Trap*)** — сповіщення процесу про те, що запитане блокування або конверсія режиму успішно завершилися;
* **BAST (*Blocking Asynchronous System Trap*)** — сповіщення вузла-власника блокування про те, що інший вузол вимагає конфліктного доступу, тому локальний кеш слід скинути на диск, а режим блокування — добровільно понизити.

Модель VMS DLM виявилася настільки вивіреною та математично повною, що всі наступні кластерні розробки наступних десятиліть — включно з ядром Linux — запозичили її базову термінологію та протокол узгодження практично без змін.

## Епоха Unix-мейнфреймів та спеціалізованих SAN-систем (1990-ті)

Упродовж 1990-х років концепція shared-disk розвивалася переважно в середовищі високопродуктивних комерційних Unix-систем для суперкомп'ютерів та великих баз даних:

1. **DEC Tru64 UNIX (AdvFS та Memory Channel)** — розвиток спадщини VMS на 64-бітній архітектурі Alpha, де координація кластера досягала мікросекундних затримок завдяки спеціалізованому апаратному інтерконнекту Memory Channel;
2. **SGI CXFS (*Clustered XFS*)** — розробка Silicon Graphics для IRIX (а згодом і Linux), яка поєднала файлову систему XFS із моделлю асиметричних метаданих: один виділений сервер керував метаданими, тоді як усі клієнти читали й писали дані блоків напряму через Fibre Channel;
3. **IBM GPFS (*General Parallel File System*, нині IBM Storage Scale)** — створена в 1998 році для суперкомп'ютерів RS/6000 SP, де було впроваджено токен-менеджер блокувань метаданих і розподілений розподіл простору.

Усі ці рішення були пропрієтарними, прив'язаними до дорогого фірмового обладнання і недоступними для масового ринку відкритих операційних систем.

## Проєкт GFS: від лабораторії Міннесоти до ядра Linux (1996–2006)

Історія GFS (*Global File System*) розпочалася в 1996 році в лабораторії досліджень систем зберігання даних Університету Міннесоти під керівництвом професора Метью О'Кіфа (*Matthew O'Keefe*). Метою проєкту було створення повністю симетричної кластерної файлової системи для операційної системи Linux на базі Fibre Channel SAN, де кожен комп'ютер мав би однаковий статус і жоден сервер не ставав би вузьким місцем для метаданих.

Для комерціалізації розробки в 1999 році було засновано компанію Sistina Software. Sistina розробила два взаємопов'язані фундаментальні компоненти:
* **GFS** — файлову систему, структуровану на незалежні групи ресурсів (*Resource Groups*), кожна з яких містила власні бітові карти виділення блоків;
* **DLM та Pool / Device Mapper** — систему розподілених блокувань та агрегації дисків.

У 2001 році Sistina Software спробувала змінити ліцензію GFS із відкритої GPL на комерційну пропрієтарну ліцензію, що спричинило розкол у спільноті та появу відкритого форку OpenGFS. Проте в грудні 2003 року компанія Red Hat придбала Sistina Software і негайно повернула весь початковий код GFS, DLM та CLVM (*Cluster Logical Volume Manager*) під ліцензію GPL, зробивши їх ядром Red Hat Cluster Suite.

Зі збільшенням кількості ядер і масштабуванням сховищ перша версія GFS виявила серйозні архітектурні обмеження: неефективне відновлення журналів при збоях, високу латентність блокувань через часті звернення до простору користувача та надмірну фрагментацію метаданих. Це призвело до повного переписування кодової бази, і в 2006 році в ядрі Linux 2.6.19 з'явилася GFS2 (*Global File System 2*). У GFS2 менеджер блокувань перенесли безпосередньо в адресний простір ядра Linux (модуль `dlm.ko`), утиліти виділення блоків перевели на b-tree екстенти, а модель глобальних блокувань `glock` оптимізували під мінімізацію мережевого трафіку.

## Шлях Oracle: від OCFS до OCFS2 (2002–2006)

Паралельно з розвитком GFS корпорація Oracle зіткнулася з гострою потребою у високопродуктивному спільному сховищі для своєї кластерної бази даних Oracle Real Application Clusters (RAC) на платформі Linux. На початку 2000-х років єдиним способом запуску Oracle RAC під Linux було використання так званих «сирих» блокових пристроїв (*raw devices*), що надзвичайно ускладнювало адміністрування: кожен файл бази даних вимагав окремого дискового розділу.

У 2002 році Oracle випустила OCFS (*Oracle Cluster File System v1*). Вона не була повноцінною POSIX-сумісною файловою системою: OCFS1 підтримувала лише базовий набір операцій запису для великих попередньо виділених файлів баз даних (`.dbf`), не підтримувала символьні посилання, квоти чи стандартний набір прав доступу, а при спробі використати її як загальний системний диск демонструвала катастрофічно низьку продуктивність.

Усвідомивши тупиковість вузькоспеціалізованого підходу, команда розробників Oracle під керівництвом Марка Фаше (*Mark Fasheh*) та Курта Хаккеля (*Kurt Hackel*) переписала систему з нуля. У 2005 році було представлено OCFS2 (*Oracle Cluster File System Release 2*), яку в лютому 2006 року офіційно включили до основного дерева ядра Linux 2.6.16.

OCFS2 отримала повноцінну сумісність із POSIX, розвинену систему динамічного виділення простору на основі бітових карт екстентів, вбудований кластерний стек `o2cb` із власним менеджером блокувань `o2dlm`, а також віртуальну файлову систему `dlmfs`, яка дозволила користувацьким процесам (зокрема серверу СКБД Oracle) напряму використовувати кластерні блокування ядра через звичайні файлові дескриптори.

## Сучасне місце shared-disk систем у ландшафті зберігання

У 2010–2020-х роках інфраструктурний ландшафт суттєво змінився під впливом розподілених об'єктних сховищ (Ceph, GlusterFS) та хмарних файлових систем. Проте GFS2 і OCFS2 зберегли своє незамінне місце у критичних корпоративних сегментах:

* **Кластери віртуалізації (KVM, Proxmox, oVirt, Oracle VM)** — спільне використання високошвидкісних LUN (NVMe-over-Fabrics, 32G Fibre Channel) для дисків віртуальних машин із підтримкою миттєвої міграції без копіювання даних;
* **Кластери високої доступності (High Availability Active-Active)** — спільний доступ веб-серверів або поштових вузлів (Dovecot, Apache) до єдиного дискового пулу з низькими накладними витратами;
* **Бази даних спільного доступу (Oracle RAC, SAP HANA)** — симетричний прямий ввід-вивід на рівні контролера сховища.

GFS2 і OCFS2 залишаються класичними зразками системної інженерії ядра Linux, які демонструють, як завдяки математично вивіреній моделі розподілених блокувань можна перетворити звичайний дисковий масив на цілісний багатовузловий простір зберігання.
