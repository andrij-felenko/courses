# 📋 Контракт викликів рукоятки: поля, прапорці, коди помилок

Довідка за клавіатурою: точні підписи `name_to_handle_at` і `open_by_handle_at`, будова `struct file_handle`, правило узгодження розміру, повний перелік прапорців із версіями ядра, у яких вони з'явилися, і коди помилок обох викликів. Три питання, заради яких до неї приходять: скільки пам'яті виділити під рукоятку, які прапорці вільно поєднуються між собою і що саме означає кожна відмова.

## Підписи й умови складання

```c
#define _GNU_SOURCE          /* обов'язково, і перед першим #include */
#include <fcntl.h>

int name_to_handle_at(int dirfd, const char *path,
                      struct file_handle *handle,
                      int *mount_id, int flags);

int open_by_handle_at(int mount_fd, struct file_handle *handle,
                      int flags);
```

Обидва виклики з'явилися в Linux 2.6.39, обгортки glibc — від версії 2.14; у POSIX їх немає й не передбачається. Без `_GNU_SOURCE` заголовок не покаже ані прототипів, ані `struct file_handle`, ані сталої `MAX_HANDLE_SZ`. Ядро має бути зібране з параметром `CONFIG_FHANDLE`, інакше обидва відповідають `ENOSYS`; у звичайних [збірках](book:unix-linux/kernel-config-and-build) він увімкнений, бо його вимагає systemd.

`dirfd` у першому виклику поводиться точно так, як у решти [родини `*at`](book:unix-linux/at-family-syscalls): абсолютний шлях робить його неістотним, відносний відлічується від нього, `AT_FDCWD` означає поточний каталог процесу.

## `struct file_handle`

```c
struct file_handle {
    unsigned int  handle_bytes;   /* [in-out] розмір f_handle у байтах */
    int           handle_type;    /* [out]    як саме ФС закодувала     */
    unsigned char f_handle[];     /* [out]    самі байти рукоятки       */
};
```

![Ліворуч — три поля структури з позначками in та out і зауваження, що гнучкий хвіст f_handle у sizeof не входить, тож виділяти треба sizeof(struct file_handle) плюс MAX_HANDLE_SZ, тобто 8 + 128 = 136 байтів, а handle_bytes понад стелю дає EINVAL. Праворуч — послідовність із чотирьох кроків: виклик із handle_bytes = 0, відмова EOVERFLOW із проставленим потрібним розміром, виділення пам'яті під нього, успішний другий виклик; унизу застереження, що EOVERFLOW без зростання handle_bytes означає відсутність рукоятки для цього імені](/reference/unix-linux/files/file-handles/img/handle-struct.svg)

*Структура складається з двох окремих речей: заголовка сталого розміру, який виклик читає й переписує, і хвоста змінної довжини, під який пам'ять виділяє сама програма.*

Хвіст **гнучкий**: `sizeof(struct file_handle)` дорівнює восьми байтам і жодного байта рукоятки в собі не має. Отже, коли в структуру мають лягти самі байти, її не оголошують змінною — пам'ять виділяють із запасом:

```c
struct file_handle *fh = malloc(sizeof *fh + MAX_HANDLE_SZ);
fh->handle_bytes = MAX_HANDLE_SZ;
```

`MAX_HANDLE_SZ` дорівнює 128. Число не кругле й не випадкове: у заголовку ядра при ньому стоїть пояснення, що стелю взято з розміру рукоятки NFSv4 — тієї самої, заради якої [мережева файлова система](book:unix-linux/network-filesystems) весь механізм і породила. Разом із заголовком це 136 байтів, які завжди можна виділити на стеку одним махом.

Дві тонкощі, яких у підписі не видно.

**Довжина завжди кратна чотирьом.** Ядро ділить `handle_bytes` на 4 і далі рахує 32-бітними словами, тож 10 байтів означають 8, а поверненим розміром завжди буде число, кратне чотирьом.

**`handle_bytes` понад `MAX_HANDLE_SZ` — це `EINVAL`**, а не «візьми, скільки влізе». Нуль допустимий лише в `name_to_handle_at`, де він є питанням про розмір; для `open_by_handle_at` нуль — теж `EINVAL`.

## Узгодження розміру у два виклики

Скільки байтів займе рукоятка, наперед не знає ніхто: це справа файлової системи, і в межах однієї ФС розмір може різнитися для різних файлів. Тому виклик збудовано на перепитуванні: програма ставить `handle_bytes = 0`, отримує відмову `EOVERFLOW` з проставленим потрібним числом, виділяє стільки й кличе вдруге.

```c
/* рукоятка у свіжовиділеній пам'яті, або NULL із причиною в errno */
static struct file_handle *fh_get(int dirfd, const char *path,
                                  int *mount_id, int flags)
{
    struct file_handle probe, *fh;

    probe.handle_bytes = 0;                  /* перший виклик — питання про розмір */
    if (name_to_handle_at(dirfd, path, &probe, mount_id, flags) == 0) {
        errno = EIO;                         /* нуль байтів — такого не буває */
        return NULL;
    }
    if (errno != EOVERFLOW)
        return NULL;                         /* EOPNOTSUPP, ENOENT, EFAULT… */
    if (probe.handle_bytes == 0) {
        errno = EOPNOTSUPP;                  /* розмір не проставлено, див. нижче */
        return NULL;
    }

    fh = malloc(sizeof *fh + probe.handle_bytes);
    if (fh == NULL)
        return NULL;
    fh->handle_bytes = probe.handle_bytes;

    if (name_to_handle_at(dirfd, path, fh, mount_id, flags) < 0) {
        int saved = errno;
        free(fh);
        errno = saved;
        return NULL;
    }
    return fh;
}
```

Перевірка `probe.handle_bytes == 0` не зайва, і це найтонше місце всього контракту. `EOVERFLOW` має два різні значення. Зазвичай воно каже «замало місця, ось скільки треба» — і поле зростає. Але та сама помилка приходить і тоді, коли файлова система взагалі не може закодувати **саме цей** файл, хоча рукоятки видавати вміє; тоді поле лишається таким, яким його подали. Розрізняє випадки лише те, чи змінилося `handle_bytes`. Якщо не змінилося, повторювати з більшим буфером марно — місця вистачало й першого разу.

Поле `mount_id` ядро заповнює навіть тоді, коли відповідає `EOVERFLOW`, — воно не залежить від того, чи вмістилася рукоятка.

## Прапорці `name_to_handle_at`

| прапорець | біт | ядро | дія |
|---|---|---|---|
| `AT_SYMLINK_FOLLOW` | `0x400` | 2.6.39 | останній складник шляху — символьне посилання: кодувати ціль, а не саме посилання; типово кодується посилання |
| `AT_EMPTY_PATH` | `0x1000` | 2.6.39 | шлях — порожній рядок: кодувати сам об'єкт, який відкриває `dirfd` (файл, каталог, будь-що) |
| `AT_HANDLE_FID` | `0x200` | 6.5 | рукоятка потрібна лише для порівняння тотожності; ФС може видати таку, якою потім не відкриєш |
| `AT_HANDLE_MNT_ID_UNIQUE` | `0x001` | 6.12 | четвертий аргумент указує на `u64`, і туди йде неповторюваний номер монтування |
| `AT_HANDLE_CONNECTABLE` | `0x002` | 6.13 | закодувати ще й батьківський каталог, щоб відкритий файл мав чинний шлях |

Три правила поверх таблиці.

**Невідомий біт — це `EINVAL`.** Ядро звіряє `flags` з переліком дозволених і відмовляє на будь-якому зайвому. Мовчазного ігнорування, як в `open`, тут немає, і це добре: спроба вжити `AT_HANDLE_CONNECTABLE` на ядрі 6.12 не вдасть успіху, а чесно відмовить.

**`AT_HANDLE_CONNECTABLE` несумісний з `AT_HANDLE_FID` і з `AT_EMPTY_PATH`** — обидві пари дають `EINVAL`. Причина в першому випадку логічна: `AT_HANDLE_FID` каже «відкривати не збираюся», `AT_HANDLE_CONNECTABLE` — «збираюся, і з правильним шляхом». У другому — технічна: `AT_EMPTY_PATH` дозволяє назвати дескриптором відв'язаний від дерева об'єкт, у якого батьківського каталогу просто немає. Решта прапорців поєднуються вільно.

**`open_by_handle_at` прапорців `AT_*` не бере взагалі.** Його третій аргумент — це прапорці `open(2)`: `O_RDONLY`, `O_WRONLY`, `O_CLOEXEC`, `O_PATH` і решта.

## Що в полі `handle_type`

Поле розділене надвоє. Молодші вісім бітів заповнює файлова система, і вони кажуть, за яким саме форматом закодовано байти:

| значення | формат |
|---|---|
| `0x01` `FILEID_INO32_GEN` | 32-бітний номер inode і 32-бітне покоління |
| `0x02` `FILEID_INO32_GEN_PARENT` | те саме плюс номер батьківського каталогу |
| `0x81` `FILEID_INO64_GEN` | 64-бітний номер inode і 32-бітне покоління |
| `0x4d`, `0x4e`, `0x4f` | власні формати Btrfs — з коренем підтому, з батьком, з коренем батька |
| `0xff` `FILEID_INVALID` | зарезервовано: ФС не має права видавати це значення |

Старші шістнадцять бітів до файлової системи не потрапляють — це позначки самого ядра: `0x10000` означає «рукоятка зв'язна», `0x20000` — «за нею каталог». Ядро проставляє їх на кодуванні з `AT_HANDLE_CONNECTABLE`, читає при розкодуванні (щоб вимагати той самий рівень зв'язності) і зрізає перед тим, як віддати байти драйверові.

Звідси єдине практичне правило: **`handle_type` зберігають разом із байтами й разом із `handle_bytes`**, а порівнюють усю трійцю дослівно. Розбирати вміст `f_handle` не можна — формат є внутрішньою справою ФС і міняється між версіями; але побайтове порівняння двох рукояток з однаковим типом є цілком законним способом спитати «це той самий файл?».

## `mount_id`

Число, яке віддає четвертий аргумент, — це номер монтування, той самий, що стоїть **першим полем** у рядках `/proc/self/mountinfo` (сама точка монтування — п'яте поле того ж рядка). Його ж повертає [`statx`](book:unix-linux/statx-extended-stat) з маскою `STATX_MNT_ID` (ядро 5.8).

Ширина аргумента залежить від прапорця, і це найлегший спосіб зіпсувати собі стек. Без `AT_HANDLE_MNT_ID_UNIQUE` ядро пише туди `int` — чотири байти. З цим прапорцем (ядро 6.12) воно пише `u64` — вісім. Прототип у заголовку в обох випадках однаковий, `int *`, тож приведення типу доводиться писати руками, і компілятор помилки не помітить:

```c
uint64_t mnt_id;
name_to_handle_at(dirfd, path, fh, (int *)&mnt_id,
                  AT_HANDLE_MNT_ID_UNIQUE);
```

Різниця між двома номерами не косметична. Звичайний номер монтування **перевикористовується**: відмонтували одну [файлову систему](book:unix-linux/mount-model), змонтували іншу — і номер дістався новій. Неповторюваний номер (той самий, що його показують `listmount` і `statmount`, і той, що його віддає `statx` з `STATX_MNT_ID_UNIQUE` від ядра 6.8) гарантовано не повторюється, доки система працює.

Жоден із двох не переживає перезавантаження. Тому в довговічному покажчику зберігають не номер, а UUID файлової системи — через `/dev/disk/by-uuid` або `libblkid` — і вже перед відкриттям знаходять чинне монтування.

## `open_by_handle_at`: перший аргумент і повноваження

`mount_fd` — дескриптор **будь-чого** на потрібній файловій системі: файла, каталогу, дескриптора, відкритого з `O_PATH`. Він не є точкою відліку шляху й потрібен лише для того, щоб указати, у якій ФС розкодовувати байти. Значення `AT_FDCWD` теж приймається й означає поточний каталог.

Якщо рукоятка веде на символьне посилання, у `flags` обов'язковий `O_PATH`: посилання не розкривається, а `O_NOFOLLOW` мовчки ігнорується. Без `O_PATH` виклик відмовляє `ELOOP`.

Повноваження — окрема історія з двома поверхами. Носієві [`CAP_DAC_READ_SEARCH`](book:unix-linux/capabilities) дозволено все й одразу. Для решти від ядра 6.11 діє послаблення, зроблене заради [контейнерів](book:unix-linux/namespaces): відкривати можна **лише каталоги** (обов'язковий `O_DIRECTORY`), і лише за умови, що процес має `CAP_DAC_READ_SEARCH` у власному просторі імен користувачів **і** або `CAP_SYS_ADMIN` над цією файловою системою, або право створити прив'язане монтування піддерева, з якого подано `mount_fd`, — за відсутності всередині нього замкнених монтувань. Обмеження на каталоги навмисне: воно робить поведінку передбачуваною й закриває найнеприємніший випадок — відв'язані від дерева файли. Саме цього послаблення потребують cgroupfs і [`fanotify`](book:unix-linux/inotify-and-fanotify), які без нього в контейнері віддавали рукоятки, непридатні до вжитку.

## Коди помилок

| код | виклик | коли |
|---|---|---|
| `EOVERFLOW` | `name_to_handle_at` | буфера замало, `handle_bytes` проставлено потрібним числом; **або** рукоятки для цього імені немає — тоді поле не змінилося |
| `EOPNOTSUPP` | `name_to_handle_at` | ФС не вміє того, що просять: без `AT_HANDLE_FID` — не має таблиці `export_operations` або не вміє розкодовувати; з `AT_HANDLE_CONNECTABLE` — не вміє кодувати батька; з `AT_HANDLE_FID` — прямо відмовилася від видачі посвідчень |
| `ENOENT` | `name_to_handle_at` | шляху не існує; або шлях порожній, а `AT_EMPTY_PATH` не заданий |
| `ENOTDIR` | `name_to_handle_at` | шлях відносний, `dirfd` дійсний, але відкриває не каталог |
| `EBADF` | обидва | `dirfd` або `mount_fd` не є дійсним дескриптором і не є `AT_FDCWD` |
| `EFAULT` | обидва | `path`, `handle` чи `mount_id` указують за межі доступної пам'яті |
| `EINVAL` | обидва | недозволений біт у `flags` чи заборонена їх пара; `handle_bytes` понад `MAX_HANDLE_SZ`; для `open_by_handle_at` ще й `handle_bytes = 0` |
| `EPERM` | `open_by_handle_at` | немає `CAP_DAC_READ_SEARCH` (або не виконано умов послаблення 6.11) |
| `ELOOP` | `open_by_handle_at` | рукоятка веде на символьне посилання, а `O_PATH` не заданий |
| `ESTALE` | `open_by_handle_at` | рукоятка непридатна до відкриття |

Дві пари з цієї таблиці плутають найчастіше.

**`EOPNOTSUPP` проти `ESTALE`.** Перше — це відмова на боці кодування: файлова система не вміє видати рукоятку потрібного ґатунку, і дізнається програма про це ще на `name_to_handle_at`, до всякого зберігання. Друге — відмова на боці розкодування, і причин у неї три: файлу справді немає (номер inode перезаселено, покоління не збіглося); рукоятку взято з `AT_HANDLE_FID` на ФС, яка кодувати вміє, а знаходити назад — ні; рукоятку взято з `AT_HANDLE_CONNECTABLE`, а файл відтоді перемістили, і зв'язного шляху до нього більше немає. Показово, що остання пара випадків повертає саме `ESTALE`, а не `EOPNOTSUPP`: на боці розкодування ядро не розрізняє «не вмію» і «вже не той».

**`EPERM` проти `ESTALE`.** Права перевіряються **до** розкодування. Отже, програма без повноважень отримає `EPERM` і на живій, і на мертвій рукоятці — відрізнити вилучений файл від чинного вона не може взагалі. Порядок важливий і в зворотний бік: `EPERM` нічого не каже про долю файлу, тож вважати його ознакою «файл на місці» не можна.

> 🔧 **Навіщо це.** Наявність сталої в `<fcntl.h>` нічого не доводить про ядро, на якому програма зараз біжить: `AT_HANDLE_CONNECTABLE` потрапляє в заголовок разом із пакетом заголовків, а бере його ядро чи ні — окреме питання, і відповідь залежить від машини. Єдина надійна перевірка — спробувати виклик із прапорцем на завідомо доступному каталозі й глянути на `errno`: `EINVAL` означає, що ядро прапорця не знає, `EOPNOTSUPP` — що не знає його ця файлова система. Різниця між двома відмовами визначає, що робити далі: у першому випадку запасний варіант потрібен для всієї машини, у другому — лише для цього монтування.
