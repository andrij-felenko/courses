# 📋 Контракт клонування й копіювання діапазонів

Ця вставка пояснює 📋 контракт клонування й копіювання діапазонів та дозволяє зрозуміти її детальніше. Це довідка по трьох інтерфейсах, якими програма просить ядро зробити копію, не переносячи байтів крізь простір користувача: `FICLONE`/`FICLONERANGE` («поділи блоки або відмов»), `FIDEDUPERANGE` («злий однакове, але спершу звір») і `copy_file_range` («скопіюй якнайдешевше»). Тут структури поле за полем, значення параметрів, правило вирівнювання, повний перелік помилок із причиною кожної, таблиця підтримки по файлових системах і межі, що рухалися від версії до версії. Саме те, що доводиться звіряти щоразу, коли код має спрацювати не тільки на машині, де його написали.

Найкоротший орієнтир, з якого починається вибір:

| що потрібно | чим | на чому спотикаються |
|---|---|---|
| спільні блоки для цілого файлу або чесна відмова | `ioctl(dest_fd, FICLONE, src_fd)` | третій аргумент — число, а не покажчик |
| спільні блоки для частини файлу | `ioctl(dest_fd, FICLONERANGE, &arg)` | зсуви й довжина кратні розміру блока |
| злити вже наявні однакові ділянки | `ioctl(src_fd, FIDEDUPERANGE, &arg)` | виклик роблять на **джерелі**, а нуль на поверненні не означає, що щось злито |
| копія найдешевшим доступним способом | `copy_file_range(…)` | копіює менше, ніж просили, — обов'язковий цикл |

## Звідки беруться константи

Обгорток у libc для клонування немає: `reflink(2)` як системний виклик так і не з'явився, тому всі три операції над картою файлу — це [ioctl](book:unix-linux/ioctl-interface), керуючий канал, куди складають усе, що не вкладається в загальний набір дієслів. Оголошення живуть у заголовку ядра:

```c
#include <linux/fs.h>        /* FICLONE, FICLONERANGE, FIDEDUPERANGE, FILE_DEDUPE_* */
#include <sys/ioctl.h>
```

Самі номери мають промовисту форму:

```c
#define FICLONE        _IOW(0x94,  9, int)
#define FICLONERANGE   _IOW(0x94, 13, struct file_clone_range)
#define FIDEDUPERANGE  _IOWR(0x94, 54, struct file_dedupe_range)
```

`0x94` — це `BTRFS_IOCTL_MAGIC`, власна літера Btrfs. Коли операції піднімали з однієї файлової системи на спільний рівень, номери лишили байт-у-байт тими самими, бо змінити їх означало б поламати всі готові програми. Тому загальний, ніяк не пов'язаний із Btrfs інтерфейс і досі носить її магічне число — це слід у ABI, а не помилка заголовка.

Практичний наслідок: збірка проти старих заголовків (до Linux 4.5) імен `FICLONE` не знайде, хоч ядро на машині цілком може їх розуміти. Тому в переносному коді константи або оголошують самі під `#ifndef`, або зупиняються на `BTRFS_IOC_CLONE` — це той самий номер під старою назвою.

## `FICLONE` і `FICLONERANGE`: поділити або відмовитися

```c
int ioctl(int dest_fd, FICLONE, int src_fd);
int ioctl(int dest_fd, FICLONERANGE, struct file_clone_range *arg);
```

Обидві форми викликають **на дескрипторі призначення**: саме той файл змінюють, а джерело передають усередину — числом у `FICLONE` і полем структури у `FICLONERANGE`. У `FICLONE` третій аргумент `ioctl` — це не покажчик, а сам дескриптор за значенням; передати туди `&src_fd` — типова помилка, яка компілюється без жодного слова.

```c
struct file_clone_range {
    __s64 src_fd;
    __u64 src_offset;
    __u64 src_length;
    __u64 dest_offset;
};
```

| поле | що означає |
|---|---|
| `src_fd` | дескриптор джерела, відкритий принаймні на читання |
| `src_offset` | зсув у джерелі, звідки брати |
| `src_length` | скільки байтів; **нуль означає «до кінця файлу-джерела»** |
| `dest_offset` | зсув у призначенні, куди класти |

`FICLONE` — це та сама операція з нулями в трьох полях: усе джерело від початку в призначення від початку. Тому `cp --reflink` спершу створює порожній файл, а потім клонує в нього.

Три властивості контракту, які варто знати наперед.

**Це заміна, а не злиття.** Діапазон призначення перезаписується цілком; що там лежало раніше, зникає. Ядру не треба нічого звіряти, бо програма й так наказала перезаписати саме ці байти.

**Клон узгоджений щодо паралельних записів.** Клонування атомарне стосовно конкурентних записів — так це й записано в контракті, тож брати замки́ заради цілісного знімка не треба. Не буде такого, що перша половина діапазону взята до чужого запису, а друга після.

**Відмова чесна.** `FICLONE` ніколи не відкочується на копіювання байтів мовчки. Якщо файлова система не вміє ділити блоки — буде помилка, і жодного зайвого місця не витрачено. Саме тому цей виклик придатний там, де потрібна не швидкість, а сам факт спільности блоків.

### Мінімальний виклик

```c
#include <sys/ioctl.h>
#include <linux/fs.h>
#include <errno.h>

/* 1 — блоки поділено, 0 — тут так не вміють, -1 — справжня помилка. */
int try_clone(int dest_fd, int src_fd)
{
    if (ioctl(dest_fd, FICLONE, src_fd) == 0)
        return 1;
    if (errno == EOPNOTSUPP || errno == EINVAL || errno == EXDEV)
        return 0;
    return -1;
}
```

Три помилки в другій умові — не перестрахування. Яку саме з них поверне ядро, коли файлова система не вміє поділу, залежить від того, на якій перевірці все спинилося, і ця межа між версіями зсувалася. Переносний код мусить приймати всі три як одну відповідь «тут не вийде».

## Правило вирівнювання

Спільним може бути тільки цілий блок: облік власників ведуть поблоково, і половину блока двом файлам не віддати. Звідси вимога до всіх трьох чисел у `struct file_clone_range` (і так само в запиті дедуплікації):

```
src_offset  % розмір_блока == 0
dest_offset % розмір_блока == 0
src_length  % розмір_блока == 0     ← крім єдиного випадку нижче
```

Виняток один і він природний: якщо діапазон упирається в кінець файлу-джерела, довжину вирівнювати не треба. За кінцем файлу однаково немає нічого, з чим спільність могла б зіпсувати сусіда.

![Три однакові смуги файлу-джерела, поділені на блоки по 4096 байтів; п'ятий блок неповний, бо розмір файлу 20000 байтів. Над кожною смугою зелена або червона планка запитаного діапазону, під смугою підписані межі блоків 0, 4096, 8192, 12288, 16384 і 20000 з позначкою EOF. Перший рядок: зсув 8192 і довжина 8192 — обидва кінці лягли на межу блока, планка зелена. Другий рядок: зсув 8192 і довжина 6000 — кінець на 14192 упав усередину блока, показано червоною штриховою лінією, планка червона, вердикт EINVAL. Третій рядок: зсув 16384 і довжина 3616 — кінець збігся з EOF, планка зелена, хвіст вирівнювати не треба. Унизу рамка з підсумком правила](/reference/unix-linux/files/reflink-copies/img/alignment-rule.svg)

*Вирівняні мають бути три числа, а не одне: зсув у джерелі, зсув у призначенні й довжина. Хвіст, що доходить до кінця джерела, — єдиний дозволений «неповний» шматок.*

**Розмір блока ядро окремим запитом не повідомляє.** Найближче до потрібного числа — `f_bsize` зі `statvfs`, і на локальних [файлових системах з екстентами](book:unix-linux/filesystem-families) — XFS, Btrfs, ext4 — воно збігається з розміром блока, зазвичай 4096. А от `st_blksize` зі `stat` для цього не годиться: це рекомендований розмір порції для читання й запису, і на мережевих файлових системах він дорівнює розміру запиту протоколу — мегабайту й більше. Код, який вважає `st_blksize` межею вирівнювання, на NFS отримає `EINVAL` там, де все могло б спрацювати.

Через це найнадійніший спосіб — не гадати: `FICLONE` цілого файлу вирівнювання не потребує взагалі, а для часткових діапазонів `EINVAL` треба вміти пережити й відступити на звичайне копіювання.

Друга межа з того самого правила: перекривні діапазони в межах **одного** файлу ні XFS, ні Btrfs не приймають — теж `EINVAL`. Копіювати частину файлу поверх іншої його частини поділом блоків не вийде.

## `FIDEDUPERANGE`: злити те, що вже однакове

```c
int ioctl(int src_fd, FIDEDUPERANGE, struct file_dedupe_range *arg);
```

Тут напрямок виклику **обернений**: `ioctl` роблять на джерелі, а всі призначення перелічують усередині структури. Одним викликом можна злити ту саму ділянку джерела одразу з багатьма файлами, тому аргумент має змінну довжину — заголовок і масив записів за ним.

```c
struct file_dedupe_range {
    __u64 src_offset;
    __u64 src_length;
    __u16 dest_count;
    __u16 reserved1;
    __u32 reserved2;
    struct file_dedupe_range_info info[];
};

struct file_dedupe_range_info {
    __s64 dest_fd;
    __u64 dest_offset;
    __u64 bytes_deduped;
    __s32 status;
    __u32 reserved;
};
```

![Ліворуч розкладка запиту в пам'яті згори вниз: заголовок struct file_dedupe_range на 24 байти з полями src_offset вісім байтів, src_length вісім байтів, dest_count два байти і шість байтів зарезервованого; далі запис info нуль на 32 байти з полями dest_fd вісім байтів, dest_offset вісім байтів, bytes_deduped вісім байтів, status і reserved разом вісім байтів; нижче рамка, що позначає решту записів масиву по 32 байти кожен. Поля пофарбовано за тим, хто їх заповнює: сині заповнює програма перед викликом, зелені заповнює ядро на поверненні, сірі мають бути нулями. Праворуч чотири рамки: виклик роблять на дескрипторі джерела; арифметика стелі — 24 плюс 32 помножити на dest_count не більше за 4096, звідки dest_count не більше за 127; примітка про мовчазне обрізання src_length до 16 мебібайтів; попередження, що ioctl повертає нуль навіть коли жодного байта не злито; перелік двох значень status](/reference/unix-linux/files/reflink-copies/img/dedupe-layout.svg)

*Заголовок і масив лежать одним шматком пам'яті — тому стелю на кількість призначень задає не окрема константа, а розмір сторінки.*

| поле | хто заповнює | що означає |
|---|---|---|
| `src_offset`, `src_length` | програма | ділянка джерела, яку пропонують злити |
| `dest_count` | програма | скільки записів у масиві `info` |
| `reserved1`, `reserved2`, `info[i].reserved` | програма | **мусять бути нулями** |
| `info[i].dest_fd` | програма | дескриптор призначення, відкритий на запис |
| `info[i].dest_offset` | програма | зсув у цьому призначенні |
| `info[i].bytes_deduped` | ядро | скільки байтів справді злито |
| `info[i].status` | ядро | `FILE_DEDUPE_RANGE_SAME` (0) або `FILE_DEDUPE_RANGE_DIFFERS` (1) |

Три обмеження, яких немає ні в клонуванні, ні в копіюванні.

**Стелю на `dest_count` задає розмір сторінки.** Заголовок і масив мусять уміститися в одну сторінку пам'яті, а це проста арифметика:

```
sizeof(struct file_dedupe_range)      = 8 + 8 + 2 + 2 + 4 = 24 Б
sizeof(struct file_dedupe_range_info) = 8 + 8 + 8 + 4 + 4 = 32 Б

24 + 32 · dest_count ≤ 4096
     32 · dest_count ≤ 4072
          dest_count ≤ 127
```

Більше — `ENOMEM`, і це та рідкісна помилка, яку легко отримати, маючи вдосталь пам'яті.

**`src_length` ядро обрізає мовчки.** Стеля залежить від файлової системи й типово становить 16 МіБ на виклик. Попросити більше можна, помилки не буде — просто в `bytes_deduped` повернеться менше, ніж просили. Програма, яка не дивиться на це число, вважатиме злитим те, що лишилося окремим.

**Успіх виклику не означає, що щось злито.** `ioctl` повертає нуль і тоді, коли ядро порівняло всі діапазони й **жоден** не збігся. Нуль тут означає лише «порівняння відбулося»; справжня відповідь лежить у `status` кожного запису окремо. Досить одного розбіжного байта, щоб запис отримав `FILE_DEDUPE_RANGE_DIFFERS`, а його `bytes_deduped` лишився нулем.

Саме звіряння — не перестрахування ядра, а єдине, що робить операцію безпечною. Між тим, як програма прочитала два діапазони й побачила збіг, і тим, як вона попросила їх злити, минає час, і за цей час хтось міг записати в один із файлів. Тому ядро бере діапазони під замок і порівнює їх само.

### Права на дедуплікацію

Правило змінилося в Linux 4.19 і стало м'якшим. До того злити ділянку в чужий файл дозволяли лише тому, хто мав його відкритим на запис, або суперкористувачеві, — і власник не міг дедуплікувати власні файли, відкриті на читання. Тепер дозволено, якщо виконано хоч одне: дескриптор відкрито на запис, файл належить тому, хто просить, або процес має [можливість](book:unix-linux/capabilities) `CAP_SYS_ADMIN` — окремий дозвіл із набору, на які розібрали всесилля root. Тією ж зміною відмову перевели з `EINVAL` на `EPERM`, щоб її можна було відрізнити від «файлова система не вміє».

### Мінімальний виклик

```c
#include <stdint.h>
#include <stdlib.h>
#include <sys/ioctl.h>
#include <linux/fs.h>

/* Скільки призначень справді збіглося й дістало спільні блоки; -1 — помилка. */
int dedupe_range(int src_fd, uint64_t off, uint64_t len,
                 const int *dst_fd, const uint64_t *dst_off, unsigned n)
{
    size_t sz = sizeof(struct file_dedupe_range)
              + (size_t)n * sizeof(struct file_dedupe_range_info);

    /* calloc, а не malloc: усі reserved мусять бути нулями. */
    struct file_dedupe_range *arg = calloc(1, sz);
    if (!arg)
        return -1;

    arg->src_offset = off;
    arg->src_length = len;
    arg->dest_count = n;
    for (unsigned i = 0; i < n; i++) {
        arg->info[i].dest_fd = dst_fd[i];
        arg->info[i].dest_offset = dst_off[i];
    }

    int same = -1;
    if (ioctl(src_fd, FIDEDUPERANGE, arg) == 0) {
        same = 0;
        for (unsigned i = 0; i < n; i++)
            if (arg->info[i].status == FILE_DEDUPE_RANGE_SAME
                && arg->info[i].bytes_deduped > 0)
                same++;
    }
    free(arg);
    return same;
}
```

## `copy_file_range`: скопіювати якнайдешевше

```c
#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <unistd.h>

ssize_t copy_file_range(int fd_in, off_t *off_in,
                        int fd_out, off_t *off_out,
                        size_t size, unsigned int flags);
```

`_FILE_OFFSET_BITS 64` тут не косметика. Коли зсуви передають покажчиками, розмір `off_t` стає частиною виклику, і на 32-бітних платформах без цього визначення програма розмовляє з ядром іншою структурою, ніж думає, — та сама межа, що й у [решті інтерфейсів із великими файлами](book:unix-linux/large-file-support).

Обидва покажчики зсуву незалежні, і кожен має два режими:

| `off_in` / `off_out` | звідки береться зсув | що змінюється |
|---|---|---|
| `NULL` | поточна позиція дескриптора | позицію в [описі відкритого файлу](book:unix-linux/open-file-description) посунуто на скопійоване — саме ту спільну структуру, від якої відлічують `read` і `write` |
| покажчик на `off_t` | значення за покажчиком | позиція дескриптора не змінюється, посунуто саму змінну |

Комбінувати режими можна вільно: читати з поточної позиції й класти за заданим зсувом — припустимо.

`flags` існує лише заради майбутніх розширень і **мусить бути нулем**; будь-що інше — `EINVAL`.

**Повернене число — це не «зробив чи ні».** Виклик повертає кількість скопійованих байтів, і вона законно буває меншою за замовлену: ядро вільне спинитися на межі екстента, на межі того, що вміє файлова система, на межі внутрішнього буфера. Нуль означає, що джерело скінчилося. Тому єдина правильна форма вживання — цикл:

```c
#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <unistd.h>
#include <errno.h>

/* Копіює len байтів від початку fd_in у початок fd_out. 0 або -1 з errno. */
int copy_all(int fd_in, int fd_out, off_t len)
{
    off_t in_off = 0, out_off = 0;

    while (len > 0) {
        ssize_t n = copy_file_range(fd_in, &in_off, fd_out, &out_off,
                                    (size_t)len, 0);
        if (n < 0)
            return -1;              /* errno вже виставлено */
        if (n == 0) {               /* джерело скінчилося раніше, ніж чекали */
            errno = EIO;
            return -1;
        }
        len -= n;                   /* in_off і out_off ядро посунуло само */
    }
    return 0;
}
```

Дві обмовки про те, чого виклик **не** обіцяє. Він не обіцяє поділу блоків: поділ — лише найдешевший із варіантів, які ядро перебирає, а не частина контракту. І він не обіцяє зберегти [діри розрідженого файлу](book:unix-linux/sparse-files): порожнечу дозволено розкрити в справжні нулі, витративши місце там, де його витрачено не було. Кому потрібна саме карта дір, той обходить файл через `SEEK_DATA`/`SEEK_HOLE` і копіює шматками.

## Помилки: повний перелік

| помилка | де буває | причина |
|---|---|---|
| `EXDEV` | усі три | джерело й призначення на різних змонтованих файлових системах. Для `copy_file_range` — до Linux 5.3 завжди, а з 5.19 знову, коли типи файлових систем різні |
| `EOPNOTSUPP` | `FICLONE*`, `FIDEDUPERANGE`, `copy_file_range` (з 5.19) | файлова система не підтримує операції для одного з дескрипторів або дескриптор веде на особливий inode |
| `EINVAL` | `FICLONE*`, `FIDEDUPERANGE` | файлова система не вміє операції для цих діапазонів; дескриптор представляє пристрій, FIFO чи сокет; зсуви або довжина не вирівняні на розмір блока; діапазони перекриваються в межах одного файлу |
| `EINVAL` | `copy_file_range` | `flags` не дорівнює нулю; діапазони перекриваються, коли це той самий файл; один із дескрипторів не є звичайним файлом |
| `EBADF` | усі три | дескриптор недійсний; джерело не відкрито на читання; призначення не відкрито на запис або відкрито тільки на дозапис (`O_APPEND`) |
| `EBADF` | `FICLONE*`, `FIDEDUPERANGE` | **окремо: файлова система, на якій лежить джерело, не підтримує поділу блоків** — помилка з назвою про дескриптор, але з причиною про файлову систему |
| `EISDIR` | усі три | один із дескрипторів веде на каталог. Для двох `ioctl` — коли файлова система ще й не підтримує спільних ділянок у каталогах |
| `EPERM` | усі три | призначення — незмінний файл (атрибут, що його ставлять `chattr +i`); для `FIDEDUPERANGE` — ще й відмова в правах на дедуплікацію, з Linux 4.19 |
| `ETXTBSY` | усі три | один із файлів є [файлом підкачки](book:unix-linux/swap-and-reclaim). Такий файл ділити блоками не можна взагалі: підсистема підкачки звертається до нього безпосередньо за фізичними блоками, обминаючи файлову систему, і копіювання при записі там просто не спрацює |
| `ENOMEM` | `FIDEDUPERANGE`, `copy_file_range` | бракує пам'яті ядра; для дедуплікації — ще й `dest_count` такий великий, що опис аргументу не вміщається в одну сторінку |
| `ENOSPC` | `copy_file_range` | на файловій системі призначення бракує місця |
| `EFBIG` | `copy_file_range` | запис виходить за найбільший припустимий зсув, за граничний розмір файлу або за обмеження ресурсу на розмір файлу для цього процесу |
| `EOVERFLOW` | `copy_file_range` | запитаний діапазон не вміщається в ужиті типи |
| `EIO` | `copy_file_range` | збій вводу-виводу під час копіювання |
| `ENOSYS` | `copy_file_range` | ядро не має цього виклику. Побачити цю помилку почали лише від glibc 2.30 — раніше обгортка ховала її за власною емуляцією |

Найпідступніша пара — `EINVAL` і `EOPNOTSUPP`. Обидві означають «тут так не можна», але яку саме віддадуть, залежить від того, на якому шарі спинилася перевірка, і між версіями ядра ця межа рухалася. Код, що вирішує «чи вміє ця пара файлів поділ блоків», мусить сприймати `EINVAL`, `EOPNOTSUPP` і `EXDEV` як одну відповідь, а не розрізняти їх.

## Хто це вміє

| файлова система | `FICLONE*` | `FIDEDUPERANGE` | `copy_file_range` | обмовка |
|---|---|---|---|---|
| Btrfs | так | так | так, поділом блоків | лічильник посилань на екстенти був у форматі від початку |
| XFS | так, **лише з `reflink=1`** | так | так, поділом блоків | прапорець задають на `mkfs.xfs` і назавжди; типовим став із `xfsprogs` 5.1 (липень 2019) |
| OCFS2 | так | так | так, поділом блоків | дерево лічильників від Linux 2.6.32 (грудень 2009) |
| bcachefs | так | так | так, поділом блоків | у дереві ядра був із 6.7; з 6.18 живе поза ним, як модуль DKMS |
| NFS 4.2 | так — операція `CLONE` | ні | так — операція `COPY` на боці сервера | мусить уміти і клієнт, і сервер; операції описано в RFC 7862 |
| SMB 3.1.1 (`cifs`) | так — `FSCTL_DUPLICATE_EXTENTS_TO_FILE` | ні | так — копіювання на боці сервера | у клієнті ядра від Linux 4.2 (серпень 2015) |
| ext4, ext3, ext2 | **ні** | **ні** | так, циклом усередині ядра | вільне місце обліковує бітова карта — місця під лічильник власників у форматі немає |
| решта локальних (tmpfs, F2FS, …) | ні | ні | так, циклом усередині ядра | загальний відкат ядра, тому виклик не відмовляє, але й не економить нічого |

У стовпці `copy_file_range` немає жодного «ні», і це не випадковість: виклик має право звестися до звичайного циклу читання й запису всередині ядра. Він завжди «спрацьовує» — і саме тому питати в нього про факт спільности блоків марно.

Окремо варто пам'ятати, що [мережеві файлові системи](book:unix-linux/network-filesystems) підтримують клонування, але не дедуплікацію: операції, яка звіряла б вміст під замком на боці сервера, ні в NFS 4.2, ні в SMB 3 немає.

## Межі за версіями

| версія | що змінилося |
|---|---|
| Linux 2.6.29 (березень 2009) | Btrfs і її власні `BTRFS_IOC_CLONE`, `BTRFS_IOC_CLONE_RANGE` |
| Linux 4.2 (серпень 2015) | клієнт SMB 3.1.1 навчився клонувати через `FSCTL_DUPLICATE_EXTENTS_TO_FILE` |
| Linux 4.5 (березень 2016) | `FICLONE`, `FICLONERANGE`, `FIDEDUPERANGE` на рівні VFS зі старими btrfs-івськими номерами; поява `copy_file_range` |
| Linux 4.9 (грудень 2016) | XFS із деревом лічильників посилань (формат v5, `reflink=1`) |
| Linux 4.19 (жовтень 2018) | дедуплікацію дозволено власникові файлу, відкритого лише на читання; відмову в правах переведено з `EINVAL` на `EPERM` |
| Linux 5.3 (вересень 2019) | велика переробка `copy_file_range`: суворіші перевірки меж і загальний відкат, який зняв безумовний `EXDEV` |
| Linux 5.19 (липень 2022) | різні файлові системи для `copy_file_range` дозволено, лише коли вони одного типу й самі це вміють; інакше `EOPNOTSUPP`. Ці умови перенесено й у старіші стабільні гілки — саме на них слід орієнтуватися |
| Linux 6.7 (січень 2024) | bcachefs у головному дереві ядра |
| Linux 6.18 (грудень 2025) | bcachefs прибрано з головного дерева, розповсюджується як модуль DKMS |

Окрема вісь — [libc як шлюз до ядра](book:unix-linux/libc-as-gateway), і тут вона поводиться нетипово. Обгортка `copy_file_range` з'явилася в glibc 2.27 (лютий 2018), і від 2.27 до 2.29 включно вона **сама емулювала виклик** у просторі користувача, коли ядро його не мало. З glibc 2.30 (серпень 2019) емуляцію прибрано, і виклик чесно віддає `ENOSYS`.

Наслідок для проб на можливості дражливий: на glibc 2.27–2.29 спроба «а чи є в системи `copy_file_range`» відповідала «є» навіть на ядрі, яке про виклик не чуло, — і байти летіли через простір користувача так само, як у звичайному циклі, тільки непомітно. Проба, що міряє ядро, а не обгортку, ходить повз libc: `syscall(__NR_copy_file_range, …)`. Як будувати такі перевірки взагалі — [розібрано окремо](book:unix-linux/kernel-abi-stability/proj-feature-probe.md).
