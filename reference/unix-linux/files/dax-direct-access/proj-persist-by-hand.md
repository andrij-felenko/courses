# ⚙️ Зберегти байт власноруч: кільцевий журнал на постійній пам'яті

Нижче — робоча програма мовою C, яка дописує записи в кільцевий журнал на файлі з прямим звертанням і після аварійного перезапуску перевіряє, що з них уціліло. Мову тут диктує задача, а не смак: усе складається з `mmap` із прапорцями ядра, інструкцій виштовхування кешу й точного порядку сторів, а це має пряме вираження лише в C.

## Задача

Журнал приймає записи змінної довжини й тримає останню тисячу, витісняючи найдавніші. Вимога одна й жорстка: живлення можна зняти будь-якої миті, і після ввімкнення читач мусить побачити або повний запис, або жодного його сліду — ніколи половину. При цьому в гарячому шляху не повинно бути жодного системного виклику: заради цього DAX і брали.

Складність не в структурі даних — кільце з фіксованих слотів пишеться за десять хвилин. Складність у тому, що звичайна інструкція запису у відображення не зберігає нічого: вона змінює рядок кешу процесора, а кеш процесора — летюча пам'ять. Отже, порядком, у якому байти перетинають межу довговічності, доведеться керувати самій програмі.

## Ідея

Слот — рівно одна сторінка. Перші вісім байтів слота — **ознака фіксації**: нуль означає «запису тут немає», ненуль — порядковий номер запису. Далі довжина, контрольна сума й тіло.

Ознака мусить бути саме восьмибайтовою й вирівняною, і це не естетика. На x86-64 вирівняний запис розміром до восьми байтів атомарний щодо зникнення живлення: після перезапуску в комірках буде або старе слово, або нове, ніколи мішанина; усе, що більше за вісім байтів, такої гарантії не має. Тому в одне слово стискається вся відповідь на питання «чи існує цей запис», а тіло, довжина й сума мусять дійти до носія **раніше**, ніж це слово стане ненульовим.

Звідси й увесь порядок дій, і те, що втрачається під час аварії в кожній його точці.

![Шість дій, з яких складається фіксація запису, і наслідок аварії на кожній із них](/reference/unix-linux/files/dax-direct-access/img/commit-order.svg)

*Читати варто справа наліво: спершу перелічити всі стани, які має витримати відновлення, і вже з них вивести обов'язковий порядок дій.*

## Код

Спершу формат і контрольна сума. Сума потрібна не задля надійності носія, а щоб ловити наслідки власних помилок у порядку записів — обірваний запис має розпізнаватися, а не братися на віру ([Контрольна сума CRC](book:programming/crc) — коротке число, пораховане з блоку так, що зміна будь-якого біта майже напевно змінить і його).

```c
/* pmlog.c — кільцевий журнал на файлі з прямим звертанням.
   збірка:  cc -O2 -mclwb -o pmlog pmlog.c                          */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <immintrin.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

#define LINE   64u          /* рядок кешу */
#define SLOT   4096u        /* слот = сторінка */
#define SLOTS  1024u        /* 4 МіБ журналу */

struct slot {
    uint64_t commit;        /* 0 — порожньо; інакше номер запису + 1 */
    uint32_t len;
    uint32_t crc;
    uint8_t  body[SLOT - 16];
};
_Static_assert(sizeof(struct slot) == SLOT, "слот мусить дорівнювати сторінці");
_Static_assert(offsetof(struct slot, commit) % 8 == 0, "ознака мусить бути вирівняна");

static uint32_t crc32_bitwise(const void *buf, uint32_t n)
{
    const uint8_t *b = buf;
    uint32_t c = 0xffffffffu;
    for (uint32_t i = 0; i < n; i++) {
        c ^= b[i];
        for (int k = 0; k < 8; k++)
            c = (c >> 1) ^ (0xedb88320u & (uint32_t)-(int32_t)(c & 1));
    }
    return ~c;
}
```

Тепер відображення. Прапорець `MAP_SYNC` вимагає нового типу відображення `MAP_SHARED_VALIDATE`, і саме на цій парі програма дізнається правду про файл: невдача — єдиний надійний спосіб виявити, що DAX під нею немає. Два коди помилки розрізняються за змістом: `EOPNOTSUPP` каже «ядро прапорці зрозуміло, але цей файл їх не тягне», `EINVAL` — «ядро не знає такого типу відображення взагалі», бо `MAP_SHARED_VALIDATE` і `MAP_SYNC` з'явилися разом у ядрі 4.15.

```c
static struct slot *map_log(const char *path, int *fd_out)
{
    int fd = open(path, O_RDWR);
    if (fd < 0) { perror("open"); return NULL; }

    void *base = mmap(NULL, (size_t)SLOT * SLOTS, PROT_READ | PROT_WRITE,
                      MAP_SHARED_VALIDATE | MAP_SYNC, fd, 0);
    if (base != MAP_FAILED) { *fd_out = fd; return base; }

    switch (errno) {
    case EOPNOTSUPP:
        fprintf(stderr, "файл не тягне MAP_SYNC: прямого звертання для нього немає\n");
        break;
    case EINVAL:
        fprintf(stderr, "ядро не знає MAP_SHARED_VALIDATE — старіше за 4.15\n");
        break;
    default:
        perror("mmap");
    }
    close(fd);
    return NULL;              /* продовжити без гарантій — гірше, ніж не запуститися */
}
```

Далі — дві дії, з яких складається довговічність. `CLWB` відсилає копію рядка кешу вниз, лишаючи сам рядок на місці (`CLFLUSHOPT` робить те саме, але рядок викидає — на даних, які зараз-таки читатимуть, це зайва втрата). Обидві інструкції асинхронні, тому потрібен `SFENCE`. І потрібен ще один бар'єр, невидимий: компілятор має право переставити звичайні стори між собою, тож заборону треба видати і йому ([Упорядкованість пам'яті та бар'єри](book:programming/memory-ordering) — правила, за якими процесор і компілятор можуть міняти порядок звертань до пам'яті, і засоби, що цей порядок відновлюють).

```c
static void flush(const void *addr, size_t len)
{
    const char *p   = (const char *)((uintptr_t)addr & ~(uintptr_t)(LINE - 1));
    const char *end = (const char *)addr + len;
    for (; p < end; p += LINE)
        _mm_clwb((void *)p);
}

static void fence(void)
{
    __atomic_signal_fence(__ATOMIC_SEQ_CST);   /* компіляторові: нічого не переставляй */
    _mm_sfence();                              /* процесорові: дочекайся виштовхувань */
}
```

Саме додавання запису повторює шість кроків із фігури — плюс нульовий, потрібний лише на другому колі кільця.

```c
static uint64_t seq;                /* номер наступного запису; ставить recover() */

static int append(struct slot *ring, const void *rec, uint32_t n)
{
    struct slot *s = &ring[seq % SLOTS];
    if (n > sizeof s->body) { errno = EMSGSIZE; return -1; }

    if (s->commit != 0) {                       /* слот іде на друге коло: */
        __atomic_store_n(&s->commit, (uint64_t)0, __ATOMIC_RELAXED);
        flush(&s->commit, 8); fence();          /* спершу зняти стару ознаку */
    }

    memcpy(s->body, rec, n);                    /* 1 */
    s->len = n;
    s->crc = crc32_bitwise(rec, n);
    flush(&s->len, 8 + n);                      /* 2 */
    fence();                                    /* 3 */

    __atomic_store_n(&s->commit, seq + 1, __ATOMIC_RELAXED);   /* 4 */
    flush(&s->commit, 8);                       /* 5 */
    fence();                                    /* 6 */

    seq++;
    return 0;
}
```

Нульовий крок легко проґавити. Слот на другому колі приходить із ненульовою ознакою від давнього запису; якщо просто почати писати нове тіло, то аварія посеред копіювання лишить чинну на вигляд ознаку над сумішшю старих і нових байтів. Знімаємо ознаку — і вікно зникає.

Дрібниця, що працює на нас: перше виштовхування починається з рядка, у якому лежить і `commit`, бо `flush` зсуває початок до межі рядка. Ознака в цю мить нульова, тож зайвий рядок несе вниз саме те, що треба.

Відновлення — повний обхід кільця з переліком того, що прийнято й що відкинуто. Це і є перевірка цілісності після аварійного перезапуску; вона ж повертає номер, з якого писати далі.

```c
static uint64_t recover(struct slot *ring)
{
    uint64_t newest = 0, good = 0, broken = 0;

    for (uint32_t i = 0; i < SLOTS; i++) {
        struct slot *s = &ring[i];
        uint64_t c = s->commit;
        if (c == 0) continue;                       /* слот ніколи не фіксували */
        if ((c - 1) % SLOTS != i || s->len > sizeof s->body ||
            crc32_bitwise(s->body, s->len) != s->crc) {
            broken++;                               /* сюди падає обірваний запис */
            continue;
        }
        good++;
        if (c > newest) newest = c;
    }
    printf("цілих: %llu, відкинутих: %llu, наступний номер: %llu\n",
           (unsigned long long)good, (unsigned long long)broken,
           (unsigned long long)newest);
    return newest;
}

int main(int argc, char **argv)
{
    int fd;
    struct slot *ring = map_log(argc > 1 ? argv[1] : "/mnt/pmem/log", &fd);
    if (!ring) return 1;

    seq = recover(ring);

    char line[256];
    while (fgets(line, sizeof line, stdin))
        if (append(ring, line, (uint32_t)strlen(line)) < 0)
            perror("append");

    munmap(ring, (size_t)SLOT * SLOTS);
    close(fd);
    return 0;
}
```

Файл готується один раз і назавжди — після цього гарячий шлях метаданих не торкається:

```
# mount -o dax=always /dev/pmem0 /mnt/pmem
# dd if=/dev/zero of=/mnt/pmem/log bs=4096 count=1024 && sync
```

## Той самий журнал через libpmem

Бібліотека `libpmem` із набору PMDK робить те саме, але не зашиває вибір інструкцій:

```c
#include <libpmem.h>

size_t mapped; int is_pmem;
void *base = pmem_map_file(path, 0, 0, 0, &mapped, &is_pmem);  /* сама спробує MAP_SYNC */
if (!base) { perror("pmem_map_file"); return 1; }
if (!is_pmem) { fprintf(stderr, "це не постійна пам'ять\n"); return 1; }

pmem_memcpy_persist(s->body, rec, n);      /* копіювання + доведення до довговічності */
s->len = n; s->crc = crc32_bitwise(rec, n);
pmem_persist(&s->len, 8);                  /* виштовхування + очікування */

__atomic_store_n(&s->commit, seq + 1, __ATOMIC_RELAXED);
pmem_persist(&s->commit, 8);
```

`pmem_persist` — це рівно наші `flush` і `fence`, злиті в одну назву: бібліотека сама вирішує, чи вживати `CLWB`, `CLFLUSHOPT` чи старий `CLFLUSH`, і чи взагалі щось виштовхувати. Останнє й пояснює, навіщо потрібна ця обгортка. Окрема функція `pmem_has_auto_flush()` питає платформу, чи кожен модуль у системі накритий механізмом, який доведе вміст кешів до комірок після зникнення живлення. Якщо накритий, межа довговічності проходить вище за кеші — і будь-яке виштовхування стає марною роботою. Зашитий у програму `CLWB` на такій машині просто палить такти; його відсутність на машині без цього механізму мовчки втрачає дані. Одне джерело правди тут — платформа, а не автор коду.

`pmem_memcpy_persist` вибирає ще й спосіб копіювання: короткі шматки — звичайними сторами з наступним виштовхуванням, довгі — нетемпоральними, які йдуть повз кеш і виштовхувати їх нічим не треба. Межу вмикають змінною середовища `PMEM_MOVNT_THRESHOLD`. Власноруч нетемпоральний запис виглядає так — і `SFENCE` тут обов'язковий не менше, ніж після `CLWB`, бо такі стори слабко впорядковані навіть на x86:

```c
_mm_stream_si64((long long *)dst, val);
_mm_sfence();
```

## Пастки

**Без бар'єра ознака може випередити тіло.** Спокуслива думка: на x86 стори не переставляються, отже, запис ознаки й так буде після запису тіла. Пастка в тому, що впорядкованість стосується того, що бачать інші ядра, а тут важить інша подія — перетин межі довговічності. `CLWB` асинхронний: команду видано, а коли рядок доїде до контролера пам'яті, невідомо. Рядок з ознакою тим часом може виїхати вниз сам, звичайним витісненням із кешу. Тоді на носії опиниться ознака над недописаним тілом — рівно та єдина ситуація, яку журнал не переживе. `SFENCE` не прискорює нічого; він лише не пускає програму до кроку 4, доки виштовхування з кроку 2 не завершилися.

**Ознака ширша за вісім байтів — це прихована помилка.** Якщо покласти в неї, скажімо, номер і довжину разом, вийде шістнадцять байтів, і аварія має право лишити на носії половину. Так само ламається невирівняне поле, що перетинає межу рядка кешу. Обидві перевірки варті `_Static_assert`. Компілятор — теж учасник домовленості: звичайне присвоєння він має право розбити або пересунути, тому ознака пишеться через `__atomic_store_n` навіть із найслабшою моделлю — вона нічого не коштує, але забороняє саме це.

**`fsync` не рятує метадані заднім числом.** Файл без `MAP_SYNC` виглядає робочим: помилка сторінки над ділянкою, під яку блок ще не виділено, змушує файлову систему цей блок виділити, а запис про виділення лягає в журнал у пам'яті. Програма повертається з помилки сторінки, старанно виштовхує рядки — байти справді на носії. Аварія в цю мить лишає бездоганні байти в блоці, який не належить жодному файлу. `fsync` після запису вікна не закриває, бо вікно вже було. Закриває його лише `MAP_SYNC`, який доводить метадані до носія ще всередині обробника помилки сторінки. Попереднє `fallocate` теж не рятує: воно створює екстенти «незаписані», і перше справжнє звертання переводить їх у звичайні — знову зміна метаданих. Тому вище й стоїть `dd`, який виділяє блоки по-справжньому.

**На файлі без DAX той самий код мовчки стає некоректним.** `CLWB` виштовхує рядок кешу процесора в сторінку — але це сторінка кешу сторінок у звичайній оперативній пам'яті, і носія вміст не досягає, доки не станеться зворотний запис або `msync` ([Кеш сторінок, fsync і довговічність запису](book:unix-linux/page-cache-durability) — між записом програми й носієм стоїть копія в оперативній пам'яті, і виносить її на пристрій окремий механізм). Помилки не буде: програма працює, тести проходять, журнал читається — рівно до першого зникнення живлення. Саме тому невдалий `mmap` мусить зупиняти запуск, а не переводити програму в «режим без гарантій».

**`pmem_is_pmem` бреше на чужих відображеннях.** Функція знає лише про діапазони, відображені самою бібліотекою через `pmem_map_file`; для будь-чого, відображеного власним викликом `mmap`, вона повертає «ні» незалежно від того, що там насправді. Змішувати два стилі в одній програмі — найкоротший шлях до хибного висновку про власний носій.

**`kill -9` не відтворює аварію.** Смерть процесу не чіпає ні кеш процесора, ні кеш сторінок: усе записане лишається читабельним, і хибний порядок сторів такою перевіркою не ловиться. Ловлять його або справжнім зняттям живлення, або `pmemcheck` — надбудовою Valgrind від того самого проєкту PMDK, яка стежить за кожним записом у відображення й повідомляє про стори, що ніколи не були виштовхані, і про виштовхування без бар'єра. Проєкт заархівовано наприкінці 2024 року, але як навчальний інструмент він робочий.

## Ціна

Додавання запису коштує `O(n)` на копіювання й підрахунок суми плюс **стала** кількість бар'єрів — два в звичайному випадку, три на другому колі кільця. Ця сталість і є головним здобутком: запис на десять байтів і на десять кілобайтів чекають однаково довго, а чекають вони стільки, скільки триває найповільніше з виданих виштовхувань, тобто десятки-сотні наносекунд замість десятків мікросекунд системного виклику.

Відновлення — `O(SLOTS)`: повний обхід із перерахунком сум, лінійний за розміром журналу, а не за кількістю записів. Якщо кільце велике, обхід зводиться до `O(log SLOTS)`: номери в ознаках зростають уздовж кільця й мають рівно один розрив — місце, де найновіший запис межує з найдавнішим, — а таке шукається двійковим пошуком. Повний перерахунок сум тоді лишається тільки для кількох слотів навколо розриву.
