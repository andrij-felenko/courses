Сервер бази даних під управлінням класичної файлової системи ext4 зчитує з жорсткого диска сектор розміром 4096 байтів. Через фізичну деградацію флеш-пам'яті SSD або дефект магнітної пластини накопичувача 12 бітів усередині сектора змінили свої значення. Дисковий контролер не виявив апаратної помилки й успішно віддав спотворені байти файловій системі. ОС повертає ці дані додатку без жодного попередження, що призводить до непомітного псування записів бази даних або виникнення важкодіагностованих збоїв у виконанні програм.

Файлова система Btrfs усуває цю фундаментальну незахищеність завдяки впровадженню трьох взаємопов'язаних технологій: скрізного обчислення контрольних сум (End-to-End Checksumming) для всіх даних та метаданих, фонового сканування цілісності (Scrubbing) та внутрішньої підсистеми об'єднання накопичувачів RAID на рівні логічних чанків.

## Фундамент скрізного контролю: Хешування та CSUM Tree

У традиційних файлових системах (ext4, XFS) перевірка цілісності обмежена лише метаданими або покладається на апаратний секторний код корекції помилок (ECC) самого диска. Btrfs працює за принципом скрізного контролю, де кожен сектор даних та кожен вузол метаданих захищені власним хешем, що обчислюється центральним процесором. Детальніше про появу цієї парадигми та дослідження деградації носіїв висвітлено у [історії боротьби з тихим пошкодженням даних](book:unix-linux/btrfs-checksums-scrubbing-raid/hist-silent-data-corruption.md).

Збереження контрольних сум у Btrfs чітко розділене між метаданими та файловими даними:

1. **Контрольні суми метаданих:** Зберігаються безпосередньо у заголовку кожного вузла B-дерева у полі `csum` структури `struct btrfs_header`. Саме поле `csum` займає перші 32 байти вузла (увесь заголовок довший — близько сотні байтів), а обчислення хешу охоплює все, що лежить у вузлі після цього поля (стандартний розмір вузла метаданих — 16 КіБ). Під час кожного зчитування вузла метаданих із диска ядро негайно перевіряє хеш у заголовку, перш ніж розбирати записи (items). Якщо хеш не збігається, вузол відхиляється, запобігаючи руйнуванню усієї ієрархії дерев.
2. **Контрольні суми файлових даних:** Зберігаються в окремому спеціалізованому B-дереві — **CSUM Tree (`BTRFS_CSUM_TREE_OBJECTID`)**.

![Організація зберігання контрольних сум у Btrfs](/reference/unix-linux/files/btrfs-checksums-scrubbing-raid/img/btrfs-csum-tree-structure.svg)
*_Організація зберігання контрольних сум метаданих безпосередньо у заголовку вузла та файлових даних у глобальному B-дереві CSUM Tree._*

### Структурний устрій CSUM Tree

Для кожного файлового екстента Btrfs розбиває послідовність байтів на сектори розміром `sector_size` (зазвичай 4096 байтів). У дереві `CSUM Tree` контрольні суми групуються у записи `struct btrfs_csum_item`.

Ключ пошуку `struct btrfs_key` для запису хешів у `CSUM Tree` має такий вигляд:
- `key.objectid = BTRFS_EXTENT_CSUM_OBJECTID` (константа `-10ULL`);
- `key.type = BTRFS_EXTENT_CSUM_KEY` (тип запису `128`);
- `key.offset = logical_bytenr` (початкова логічна дискова адреса першого сектора екстента).

:::tabs
```c
// Запис у листі CSUM Tree ядра Linux (fs/btrfs/ctree.h)
struct btrfs_csum_item {
    u8 csum[]; // Масив хешів для безперервної послідовності секторів
} __attribute__ ((packed));
```
```cpp
// C++ аналог структури запису у CSUM Tree
#include <cstdint>
#include <vector>

struct btrfs_csum_item {
    std::uint8_t csum[]; // Масив хешів для безперервної послідовності секторів
} __attribute__ ((packed));
```
:::

Якщо файл займає безперервну дискову область у 100 секторів (400 КіБ), Btrfs створює один запис у `CSUM Tree` з ключем, рівним логічній адресі першого сектора, де масив `csum[]` містить 100 послідовних 32-бітних хешів (разом 400 байтів даних у листі дерева). Така упакована структура мінімізує кількість окремих записів у B-дереві та прискорює пошук через `btrfs_search_slot()`.

### Підтримувані алгоритми та накладні витрати

Під час форматування файлової системи за допомогою `mkfs.btrfs --csum <algorithm>` адміністратор може обрати один із чотирьох хеш-алгоритмів:

- **CRC32c (Castagnoli):** Стандарт за замовчуванням. Обчислює 32-бітну контрольну суму. На сучасних процесорах x86_64 та ARMv8 він апаратно прискорюється спеціалізованими інструкціями процесора. Практичну реалізацію обчислення та бенчмарки наведено у [проектній статті обчислення CRC32c](book:unix-linux/btrfs-checksums-scrubbing-raid/proj-crc32c-btrfs.md).
- **xxHash64:** 64-бітний надшвидкий алгоритм. Навіть проти апаратно прискореного CRC32c він виграє приблизно у півтора раза, а вдвічі ширший хеш різко зменшує ймовірність випадкових колізій на масивах петабайтного розміру.
- **SHA256:** 256-бітний криптографічний хеш. Захищає від навмисного підроблення вмісту блоків, але потребує в 8 разів більше пам'яті для зберігання `CSUM Tree` (32 байти на кожен сектор 4 КіБ) та створює помітне навантаження на CPU.
- **BLAKE2b:** 256-бітний криптографічний хеш із високою швидкістю виконання на 64-бітних процесорах.

Розрахунок накладних витрат дискової пам'яті для зберігання хешів за умов використання алгоритму CRC32c (4 байти хешу на 4096 байтів даних):

```
Витрати = 4 байти / 4096 байтів = 0.0976% ≈ 1 ГБ на кожні 1 ТБ даних
```

Цей гігабайт дискового простору упакований у вузли `CSUM Tree`, що кешуються в оперативній пам'яті ядра під час інтенсивних операцій читання та запису.

### Відключення контрольних сум (`nodatasum` та `nodatacow`)

У деяких спеціалізованих сценаріях (наприклад, файли дискових образів віртуальних машин або бази даних із випадковим записом) постійний CoW-перезапис створює високу фрагментацію. Для таких файлів Btrfs дозволяє встановити прапор `nodatacow` (або замонтувати файлову систему з опцією `nodatasum`).

Слід враховувати важливий наслідок: установка прапора `nodatacow` або `nodatasum` повністю вимикає генерацію та перевірку контрольних сум для файлових даних. Метадані Btrfs при цьому продовжують хешуватися й захищатися у будь-якому режимі.

## Траєкторія виконання запитів: Write Path та Read Path

Перевірка цілісності у Btrfs є невід'ємною частиною конвеєра введення-виведення ядра Linux і виконується прозоро для користувацьких додатків.

### Траєкторія запису (Write Path)

Коли процес викликає системний виклик `write()`, дані спочатку потрапляють до сторінкового кешу ядра (Page Cache). Під час скидання брудних сторінок на диск (операції `fsync`, `sync` або планове скидання кожні 30 секунд) підсистема Btrfs виконує послідовність кроків:

1. **Формування блочного запиту:** Підсистема I/O формує структуру `struct bio`, яка описує групу секторів для запису на дисковий накопичувач.
2. **Асинхронне обчислення хешів:** До відправки блочного запиту на дисковий контролер ядро викликає функцію `btrfs_csum_one_bio()`. Вона розбиває буфер на сектори по 4096 байтів та обчислює контрольні суми у робочих чергах ядра (workqueue `btrfs-endio-write`). Це дозволяє розпаралелити обчислення CRC32c за наявності багатьох ядер CPU.
3. **Запис хешів у транзакцію:** Обчислені хеші додаються до списку затриманих елементів (Delayed Items) поточної транзакції файлової системи (`fs_info->delayed_root`).
4. **Запис на диск:** Блок даних відправляється на накопичувач. Після успішного запису даних відповідний запис `btrfs_csum_item` додається до `CSUM Tree`.

Завдяки архітектурі Copy-on-Write (CoW) Btrfs спочатку записує нові дані та нові контрольні суми у вільні блоки диска, і лише після цього атомарно оновлює корінь дерева у суперблоці через `btrfs_commit_transaction()`. Це унеможливлює розсинхронізацію між даними та їхніми хешами при збої живлення.

### Траєкторія читання (Read Path) та виявлення збоїв

Під час виклику `read()` процедура перевірки гарантує, що додаток не отримає спотворених бітів:

1. Btrfs зчитує блок даних із логічної адреси `bytenr` накопичувача.
2. Одночасно з `CSUM Tree` зчитується відповідний еталонний хеш для цієї адреси (шляхом бінарного пошуку у B-дереві через функцію `btrfs_lookup_csum()`).
3. Процесор обчислює поточний хеш зчитаного з диска буфера даних.
4. Порівняння хешів:
   - **Якщо хеші збігаються:** Дані повертаються у буфер користувача.
   - **Якщо хеші не збігаються:** Btrfs блокує повернення даних додатку, генерує системне попередження в журналі ядра (`dmesg`) (`btrfs: checksum error on dev ... bytenr ...`) та ініціює алгоритм **самовідновлення (Self-Healing)**.

Якщо у системі немає дубльованих копій даних (наприклад, профіль Single на одному диску), Btrfs повертає системному виклику помилку введення-виведення `-EIO` (Input/Output Error). Це не дозволяє пошкодженим байтам забруднити пам'ять додатка.

## Підсистема самовідновлення (Self-Healing) та фоновий Scrubbing

Найбільша потужність контрольних сум виявляється у поєднанні з дубльованим або паритетним сховищем Btrfs.

:::tabs
```c
// Спрощена контурна логіка самовідновлення в ядрі Linux (fs/btrfs/extent_io.c)
int btrfs_read_repair_system(struct inode *inode, struct bio *failed_bio, int mirror_num)
{
    // 1. Формуємо запит читання з наступного альтернативного дзеркала RAID
    struct bio *repair_bio = btrfs_alloc_mirror_bio(failed_bio, mirror_num + 1);
    
    if (btrfs_submit_bio_wait(repair_bio) == 0) {
        // 2. Зчитуємо альтернативний блок та перевіряємо його хеш із CSUM Tree
        if (btrfs_verify_checksum(repair_bio) == 0) {
            // 3. Копіюємо валідні дані користувачеві
            btrfs_copy_bio_pages(failed_bio, repair_bio);
            
            // 4. АСИНХРОННО перезаписуємо пошкоджений сектор на першому диску правильними даними!
            btrfs_repair_io_failure(inode, failed_bio->bi_iter.bi_sector, repair_bio);
            return 0; // Успішно відновлено!
        }
    }
    return -EIO; // Усі дзеркала пошкоджені
}
```
```cpp
// Концептуальний C++ RAII-аналог алгоритму Self-Healing для емулятора Btrfs
#include <vector>
#include <cstdint>
#include <span>
#include <optional>
#include <iostream>
#include <cstring>

struct DiskMirror {
    std::uint32_t device_id;
    std::vector<std::uint8_t> data;
};

class SelfHealingEngine {
public:
    template <typename CsumCalcFunc>
    static std::optional<std::vector<std::uint8_t>> 
    readAndRepair(std::span<const DiskMirror> mirrors, 
                  std::uint32_t expected_csum,
                  CsumCalcFunc csum_calculator) 
    {
        int failed_mirror_index = -1;

        // 1. Пробуємо зчитати з першого накопичувача
        for (std::size_t i = 0; i < mirrors.size(); ++i) {
            std::uint32_t actual_csum = csum_calculator(mirrors[i].data);
            if (actual_csum == expected_csum) {
                // Якщо перше дзеркало було пошкоджене, але ми знайшли валідне друге - ремонтуємо перше!
                if (failed_mirror_index >= 0) {
                    std::cout << "[Self-Healing] Відновлення пошкодженого сектора на devid=" 
                              << mirrors[failed_mirror_index].device_id << "...\n";
                }
                return mirrors[i].data;
            }
            
            if (failed_mirror_index == -1) {
                failed_mirror_index = static_cast<int>(i);
                std::cout << "[WARN] Помилка хешу на devid=" << mirrors[i].device_id << "!\n";
            }
        }
        return std::nullopt; // Усі дзеркала деградували
    }
};
```
:::

Послідовність самовідновлення під час читання зображено на схемі:

![Механізм перевірки контрольних сум та самоновлення](/reference/unix-linux/files/btrfs-checksums-scrubbing-raid/img/btrfs-scrub-repair-flow.svg)
*_Послідовність дій ядра під час виявлення помилки контрольної суми та автоматичне відновлення блоку з дзеркальної копії RAID._*

1. При виявленні незбігу хешу на Дзеркалі 1 ядро збільшує лічильник `mirror_num` і подає запит читання до Дзеркала 2.
2. Прочитаний з Дзеркала 2 блок звіряється з оригінальним хешем із `CSUM Tree`.
3. Якщо Дзеркало 2 містить правильний блок, ядро віддає його користувачеві (користувацький процес навіть не дізнається про збій на першому диску).
4. Ядро створює фонове завдання запису і **автоматично перезаписує** пошкоджений сектор на Дзеркалі 1 заново обчисленим правильним блоком з Дзеркала 2.

### Фоновий Scrubbing (`btrfs scrub`)

Якщо файли записані на диск і до них немає активних звернень протягом місяців або років, вони можуть тихо деградувати (Bit Rot) без викликів `read()`. Якщо згодом один із дисків RAID1 повністю вийде з ладу, деградований сектор на другому диску виявиться єдиним і втраченим.

Для запобігання цьому Btrfs надає механізм **Scrubbing** — фонове сканування цілісності дискового масиву.

```bash
# Запуск фонової перевірки та відновлення цілісності файлової системи
btrfs scrub start /mnt/storage

# Отримання поточного статусу та статистики виправлених помилок
btrfs scrub status /mnt/storage
```

На відміну від звичайного обходу файлової системи (наприклад, через `find`), `btrfs scrub`:
- Вичитує накопичувачі послідовно за їхніми фізичними дисковими адресами, мінімізуючи позиціонування головок HDD.
- Оминає сторінковий кеш ядра, зменшуючи навантаження на оперативну пам'ять.
- Перевіряє як вузли B-дерев метаданих, так і всі екстенти даних.
- Автоматично виправляє виявлені помилки із дзеркальних копій.

Для моніторингу роботи scrub підсистема ядра розсилає події трасування tracepoints: `btrfs:btrfs_scrub_start`, `btrfs:btrfs_scrub_read_error` та `btrfs:btrfs_scrub_fixup_error`.

Для програмного керування скануванням розробники системного ПЗ можуть використовувати низку викликів `ioctl`, детально описаних у [довіднику ioctl підсистеми Btrfs Scrub](book:unix-linux/btrfs-checksums-scrubbing-raid/api-btrfs-scrub-ioctl.md).

## Внутрішній RAID у Btrfs: Чанки та Профілі

Традиційні програмні технології RAID (наприклад, `mdadm`) працюють на блочному рівні під файловою системою. Вони не знають, де на диску розташовані корисні файли, а де вільний простір, тому вимушені дзеркалювати чи обчислювати паритет для всього обсягу накопичувачів.

Btrfs використовує **об'єктний RAID на рівні логічних чанків (Chunk Allocation)**.

### Логічний простір та Chunk Tree

Btrfs об'єднує всі фізичні диски у єдиний логічний адресний простір. Цей простір ділиться на великі безперервні блоки — **Чанки (Chunks)**:
- **Data Chunk:** Зазвичай має розмір 1 ГіБ і призначений для зберігання файлових даних.
- **Metadata Chunk:** Має розмір 256 МіБ або 1 ГіБ і призначений для зберігання вузлів B-дерев.

Мапування логічних адрес чанків на фізичні диски та їхні профілі зберігання здійснюється за допомогою системного B-дерева **Chunk Tree (`BTRFS_CHUNK_TREE_OBJECTID`)**.

![Мапування логічного простору чанків на фізичні накопичувачі](/reference/unix-linux/files/btrfs-checksums-scrubbing-raid/img/btrfs-raid-stripe-chunk-mapping.svg)
*_Ієрархія трансляції логічних дискових адрес у фізичні страйпи накопичувачів через Chunk Tree у профілях Single, RAID1 та RAID5._*

Ключ у `Chunk Tree` містить логічну адресу початку чанка:
- `key.objectid = BTRFS_FIRST_CHUNK_TREE_OBJECTID` (константа `256ULL`);
- `key.type = BTRFS_CHUNK_ITEM_KEY` (тип `228`);
- `key.offset = logical_stripe_bytenr`.

:::tabs
```c
// Запис у Chunk Tree ядра Linux (fs/btrfs/volumes.h)
struct btrfs_chunk {
    u64 length;            // Розмір чанка у байтах (1073741824 = 1 ГіБ)
    u64 owner;             // Ідентифікатор дерева-власника
    u64 stripe_len;        // Розмір страйпа (64 КіБ)
    u64 type;              // Профіль: BTRFS_BLOCK_GROUP_RAID1, RAID5, DUP тощо
    u16 num_stripes;       // Кількість фізичних страйпів (дисків) у цьому чанку
    u16 sub_stripes;
    struct btrfs_stripe stripes[]; // Масив посилань (devid, physical_offset)
} __attribute__ ((packed));
```

Завдяки такій архітектурі кожен чанк у Btrfs може мати власний профіль RAID незалежно від інших чанків. Наприклад, метадані можуть зберігатися у профілі `RAID1c3` (3 копії), а звичайні дані — у профілі `RAID1` (2 копії). 

Трансляція логічного блоку `logical_bytenr` у фізичний сектор накопичувача виконується функцією ядра `btrfs_map_block()`. Вона шукає відповідний чанк у `Chunk Tree`, обчислює номер страйпа `stripe_nr = offset / stripe_len`, за ним — індекс диска `stripe_index = stripe_nr % num_stripes`, і врешті фізичний сектор `physical = stripes[stripe_index].offset + (stripe_nr / num_stripes) × stripe_len + (offset % stripe_len)`.

### Профілі відмовостійкості Btrfs

Btrfs підтримує гнучкий набір профілів розміщення даних:

1. **Single:** Дані записуються в один чанк без дублювання.
2. **DUP (Duplication):** Створюються дві незалежні копії чанка на **одному і тому самому** фізичному накопичувачі, але з максимально можливим фізичним віддаленням секторів один від одного. За замовчуванням `mkfs.btrfs` обирає профіль `DUP` для метаданих на поодиноких накопичувачах HDD та SSD, щоб захистити структуру B-дерев від локальних пошкоджень секторів.
3. **RAID1:** Забезпечує зберігання двох копій даних на двох **різних** фізичних накопичувачах. На відміну від `mdadm`, Btrfs RAID1 не вимагає однакового розміру дисків. Якщо у масиві встановлено диски розміром 4 ТБ, 4 ТБ та 8 ТБ, Btrfs об'єднає їх у корисну ємність 8 ТБ дзеркального простору, виділяючи чанки на двох дисках із найбільшим вільним обсягом.
4. **RAID1c3 / RAID1c4:** Зберігають відповідно 3 або 4 незалежні копії кожного чанка на різних фізичних дисках. Використовуються для критичних метаданих у масивах із великою кількістю накопичувачів.
5. **RAID10:** Стріппінг (Striping) поверх дзеркальних пар. Вимагає щонайменше 4 диски і забезпечує найвищу швидкість паралельного читання та запису.
6. **RAID5 / RAID6:** Чітність (Parity). Розподіляють дані та блоки паритету між накопичувачами.

### Проблема RAID5/6 Write Hole у Btrfs

Під час роботи з профілями RAID5 та RAID6 у Btrfs існує фундаментальна проблема, відома як **Write Hole (діра запису)**.

Причина виникнення Write Hole розкривається у логіці оновлення страйпа. Коли Btrfs виконує частковий запис у сектор 4 КіБ усередині 64-кілобайтного страйпа RAID5, вона повинна:
1. Прочитати старі дані та старий паритет.
2. Обчислити новий паритет.
3. Записати новий сектор даних на Диск 1 та новий паритет на Диск 3.

Якщо у момент між записом сектора даних на Диск 1 та записом паритету на Диск 3 відбувається раптове відключення живлення або паніка ядра, стан масиву стає неузгодженим: нові дані записані, але паритет відповідає старим даним.

У традиційних апаратних RAID-контролерах ця проблема вирішується за допомогою NVRAM-кешу з батарейним живленням або журналу запису (Journaling). У Btrfs через відсутність окремого транзакційного журналу паритетних чанків виникає ризик того, що наступний фоновий `scrub` чи процедура відновлення після збою диска використає застарілий паритет і зіпсує сусідні цілісні файли у страйпі.

> ⚠️ **Застереження:** Профілі RAID5 та RAID6 у Btrfs вважаються нестабільними для критичних продуктивних середовищ. Профілі `RAID1`, `RAID1c3` та `RAID10` позбавлені цієї проблеми за побудовою: у них немає паритету, а отже й другого запису, який міг би розсинхронізуватися з даними. Саме вони і є практичним стандартом відмовостійкості Btrfs.

## Взаємодія з мережевим реплікуванням (Send/Receive)

Завдяки збереженню контрольних сум безпосередньо в ієрархії дерев Btrfs забезпечує високу надійність під час використання механізму інкрементального мережевого передавання субтомів — `btrfs send` та `btrfs receive`.

Під час формування потоку `send` ядро зчитує екстенти й звіряє їхні контрольні суми з `CSUM Tree`. Якщо диск містить тихо пошкоджений сектор, Btrfs не відправляє цей зіпсований сектор по мережі на резервний сервер, а генерує помилку `EIO`, захищаючи віддалену резервну копію від забруднення спотвореними даними. При отриманні потоку `btrfs receive` пише дані звичайною траєкторією запису, тож приймальна файлова система заново обчислює контрольні суми своїм власним алгоритмом і будує нове `CSUM Tree` — воно не переноситься з джерела.

## Динамічне розширення масиву та гаряча заміна дисків

Важливою перевагою архітектури чанків Btrfs є можливість динамічної зміни фізичного складу дискового масиву без зупинки системи:

1. **Додавання нового диска (`btrfs device add`):**
   ```bash
   btrfs device add /dev/sdc1 /mnt/storage
   ```
   Новий диск негайно включається до пулу вільної ємності. Btrfs починає виділяти нові чанки на доданому пристрої.
2. **Видалення диска (`btrfs device remove`):**
   ```bash
   btrfs device remove /dev/sdb1 /mnt/storage
   ```
   Ядро прозоро переносить усі чанки з диска, який вилучають, на інші накопичувачі масиву й відключає його.
3. **Гаряча заміна збійного накопичувача (`btrfs device replace`):**
   ```bash
   btrfs device replace start 2 /dev/sdd1 /mnt/storage
   ```
   Замість повільної процедури видалення та додавання команда `device replace` зчитує дані з `devid 2` (а де він збоїть — із дзеркал) і копіює їх напряму на новий накопичувач `/dev/sdd1`, мінімізуючи тривалість відновлення масиву.

## Практична діагностика, відновлення та керування масивом

Для моніторингу стану цілісності дискового масиву ядро Linux веде апаратні лічильники помилок для кожного пристрою.

```bash
# Перевірка наявності апаратних помилок та збоїв CRC32c
btrfs device stats /mnt/storage
```

Приклад виводу команди `btrfs device stats`:

```
[/dev/sda1].write_io_errs    0
[/dev/sda1].read_io_errs     0
[/dev/sda1].flush_io_errs    0
[/dev/sda1].corruption_errs  2   <-- Виявлено 2 тихі пошкодження бітів!
[/dev/sda1].generation_errs  0
```

Якщо `corruption_errs` > 0, це свідчить про те, що Btrfs успішно виявила незбіг контрольної суми CRC32c. У разі використання RAID1 або DUP ці помилки були автоматично виправлені.

### Динамічна конфігурація та ребалансування (`btrfs balance`)

Btrfs дозволяє змінювати профілі RAID на льоту без зупинки файлової системи та без відмонтування диска за допомогою виклику `btrfs balance`:

```bash
# Конвертація масиву з Single у RAID1 для даних та метаданих на живому масиві
btrfs balance start -dconvert=raid1 -mconvert=raid1 /mnt/storage

# Перевірка прогресу ребалансування чанків
btrfs balance status /mnt/storage
```

Під час виконання `btrfs balance` ядро послідовно зчитує кожен чанк, перерозподіляє його блоки відповідно до нового профілю відмовостійкості, оновлює записи у `Chunk Tree` та видаляє старі чанки.

### Аварійне реагування та відновлення даних

Якщо у разі використання профілю Single або подвійного збою дисків у RAID1 виникають невідновлювані помилки контрольних сум (`uncorrectable_errors`), ядро забороняє читання пошкодженого екстента. Для збереження вцілілих файлів застосовують інструменти:

1. **Монтування в режимі відновлення (Mount Options):**
   - `mount -o ro,usebackuproot,clear_cache /dev/sda1 /mnt/rescue` — вмикає пошук резервних коренів B-дерев попередніх транзакцій (tree roots). До ядра 4.6 ця опція звалася `recovery`; стару назву ядро ще приймає як синонім.
2. **Аварійне витягування файлів (`btrfs restore`):**
   - `btrfs restore -v /dev/sda1 /mnt/backup_disk` — витягує вцілілі файли на інший носій без монтування пошкодженої файлової системи, обходячи блокуючі перевірки хешів.
3. **Автономна перевірка дерев (`btrfs check`):**
   - `btrfs check --readonly /dev/sda1` — виконує глибоку автономну перевірку цілісності системних дерев. Застосування прапора `--repair` рекомендується лише як крайній захід, оскільки у разі важких пошкоджень воно може змінити структуру дерев.

> 🔧 **Навіщо це.** Поєднання скрізного обчислення контрольних сум, автоматичного самовідновлення та динамічного об'єднання дисків у чанках робить Btrfs захищеною від тихої деградації носіїв (Bit Rot). Моніторинг за допомогою `btrfs device stats` та фоновий `btrfs scrub` дають змогу виявляти фізичні відмови накопичувачів задовго до незворотної втрати даних.
