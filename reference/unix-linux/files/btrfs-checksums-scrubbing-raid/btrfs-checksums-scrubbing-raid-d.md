# Контрольні суми, Scrubbing та внутрішній RAID у Btrfs

- [Файлова система Btrfs: Copy-on-Write та субтоми](book:unix-linux/btrfs-copy-on-write-and-subvolumes) — базові механізми захисту даних.
</preknowlist>

У традиційних файлових системах (ext4, XFS) захист від тихого пошкодження даних (silent data corruption або bit rot) практично відсутній: якщо магнітний диск чи накопичувач SSD через деградацію осередків пам'яті спотворить декілька біт у секторі, контролер пристрою та ОС прочитають ці пошкоджені дані і без жодних попереджень віддадуть їх користувачу.

Btrfs розв'язує цю проблему на фундаментальному рівні завдяки обчисленню контрольних сум (checksumming) для всіх даних та метаданих, фоновому процесу перевірки та відновлення (scrubbing) і вбудованому підсистему програмного RAID.

## Механізм контрольних сум: Checksum Tree

У Btrfs кожному блоку даних (Data Extent) та кожному вузлу метаданих призначається своя контрольна сума. 

Контрольні суми метаданих зберігаються безпосередньо у заголовку кожного вузла (`struct btrfs_header.csum`), а контрольні суми звичайних файлових даних зберігаються в окремому глобальному B-дереві — **CSUM Tree (`BTRFS_CSUM_TREE_OBJECTID`)**.

```c
// Запис контрольної суми даних у CSUM Tree
struct btrfs_csum_item {
    u8 csum[]; // Масив контрольних сум для блоків розміром sector_size (4096 байт)
} __attribute__ ((packed));
```

Під час створення файлової системи можна обрати алгоритм хешування (`mkfs.btrfs -c <algorithm>`):
- **CRC32c (за замовчуванням):** Високошвидкісний алгоритм з апаратною підтримкою на інструкціях SSE4.2 / ARMv8 CRC.
- **xxHash64:** Надшвидкий сучасний хеш із дуже низьким відсотком колізій.
- **SHA256:** Криптографічний хеш для високих вимог до цілісності (зі збільшеними витратами CPU).
- **BLAKE2b:** Криптографічний хеш з високою швидкодією.

### Ланцюжок перевірки під час читання (Read Path)

```
[ Користувач: read() ]
          │
          ▼
[ VFS / Btrfs Engine ] ──> Зчитує блок з диску
          │
          ├─> Зчитує відповідний хеш з CSUM Tree
          ├─> Обчислює CRC32c/xxHash від отриманого блоку
          │
     ┌────┴──────────────────────────┐
     │ Хеші збігаються?             │
     ├──────────────┬────────────────┤
     │ ТАК          │ НІ             │
     ▼              ▼                │
 [Повертає      [ Помилка EIO або   │
   дані]          Self-Healing ] ◄───┘
```

1. Процес звертається до файлу через виклик `read()`.
2. Btrfs зчитує блок даних із диска і паралельно дістає його еталонний хеш із `CSUM Tree`.
3. Btrfs обчислює контрольне значення прочитаного блоку на CPU.
4. Якщо хеші **не збігаються**, Btrfs **не повертає** пошкоджені дані користувачу. Вона генерує системне попередження в `dmesg` (`btrfs: checksum error on dev ...`) і намагається виконати **Self-Healing (Самоновлення)**.

## Самоновлення (Self-Healing) та фоновий Scrubbing

Якщо файлова система Btrfs розгорнута поверх дубльованого сховища (RAID1, RAID10, RAID5/6 або з профілем метаданих `DUP`), під час виявлення помилки контрольної суми запускається алгоритм самоновлення:

```c
// Логіка самоновлення Btrfs при помилці хешу
if (btrfs_check_repairable(inode, bio, mirror_num)) {
    // 1. Зчитуємо альтернативну копію блоку з іншого дзеркала RAID (mirror_num + 1)
    read_correct_mirror();
    
    // 2. Якщо альтернативна копія валідна — повертаємо її додатку
    // 3. Автоматично перезаписуємо пошкоджений дзеркальний диск правильним блоком!
    btrfs_repair_io_failure(dev, bad_sector, good_data);
}
```

### Фоновий Scrubbing (`btrfs scrub`)

Оскільки файли, до яких тривалий час немає звернень, можуть тихо деградувати на диску без викликів `read()`, Btrfs надає фоновий механізм сканування — **Scrubbing**:

```bash
# Запуск фонової перевірки та відновлення цілісності файлової системи
btrfs scrub start /mnt/data

# Перевірка статусу виконання
btrfs scrub status /mnt/data
```

Під час виконання `btrfs scrub`:
1. Ядро послідовно вичитує **всі** екстенти та вузли метаданих із накопичувачів.
2. Обчислює їхні поточні контрольні суми та звіряє з `CSUM Tree`.
3. При виявленні спотворених блоків автоматично відновлює їх із дзеркальних копій RAID і виводить вичерпний звіт про кількість виправлених бітових помилок.

## Внутрішній RAID у Btrfs: Чанки та Профілі

На відміну от традиційного `mdadm`, який діє як сліпий блочний шар нижчого рівня, RAID у Btrfs інтегрований безпосередньо у файлову систему і оперує логічними чанками (Chunk Allocation).

Файлова система ділить накопичувачі на логічні блоки розміром 1 ГБ (для даних) або 256 МБ (для метаданих) — **Чанки (Chunks)**. Кожен чанк може мати власний профіль відмовостійкості:

- **Single:** Без дублювання (дані записуються на один диск).
- **DUP:** Дві копії записуються на **один і той самий** фізичний диск (у різні його зони). Використовується за замовчуванням для метаданих на поодиноких SSD/HDD.
- **RAID1:** Зберігає дві копії даних на двох **різних** фізичних накопичувачах.
- **RAID1c3 / RAID1c4:** Зберігає 3 або 4 незалежні копії даних на різних дисках.
- **RAID10:** Стрічка (Striping) поверх дзеркальних пар.
- **RAID5 / RAID6:** Чітність (Parity). *Зауваження:* Профілі RAID5/6 у Btrfs вважаються неостаточними для критичних продуктивних середовищ через історичні проблеми з колізіями Write Hole під час відключення живлення, тому RAID1/RAID1c3 є золотим стандартом для Btrfs.

> 🔧 **Навіщо це.** Поєднання контрольних сум та апаратного самоновлення в Btrfs гарантує 100% захист від деградації носіїв (bit rot), а фоновий `btrfs scrub` дає змогу виявляти відмови накопичувачів до того, як вони призведуть до незворотної втрати файлів.
