У 2017 році виробники мобільних пристроїв на базі операційної системи Android зіткнулися з жорстким апаратним обмеженням: розмір оперативної пам'яті смартфонів масового сегмента лишався в межах 2–4 ГБ, тоді як обсяг системного образу ОС (розділи `/system`, `/vendor`, `/product`, `/odm`) зростав з кожним випуском і досяг багатьох гігабайтів. Традиційні стиснені файлові системи для читання — SquashFS та cramfs — забезпечували компактність на диску, але робили це ціною катастрофічного підвищення затримок читання та виснаження оперативної пам'яті.

## Проблема SquashFS та аналіз Huawei (2017)

Конфлікт загострився із впровадженням ініціативи Google **Project Treble** в Android 8.0, яка розбила монолітну систему на десяток окремих Read-Only розділів. Інженер компанії Huawei Гао Сян (Gao Xiang) та його колега Чао Юй (Chao Yu), працюючи над оптимізацією фірмової графічної оболонки EMUI для смартфонів на базі процесорів HiSilicon Kirin, провели серію вимірювань за допомогою tracepoints ядра Linux та фреймворка `ftrace`.

Дослідження виявило фундаментальний архітектурний тупик SquashFS. Ця файлова система розроблялася у 2002 році Філліпом Локером для компактних дистрибутивів Linux на LiveCD та DVD-дисках. Вона використовувала принцип стиснення з фіксованим входом (Fixed-Input): оригінальний потік даних розбивався на однакові блоки розміром 128 КБ або 256 КБ, кожен з яких стискався в кусок довільної дискової довжини.

Коли процесор смартфона під час запуску застосунку намагався зчитати лише одну сторінку пам'яті (4 КБ) з динамічної бібліотеки `.so`, підсистема VFS викликала процедуру підкачки сторінки. Оскільки стиснений блок SquashFS був невирівняний і містив 128 КБ даних, ядро Linux змушене було:
1. Зчитати з повільної флеш-пам'яті eMMC/UFS весь 128-кілобайтний стиснений блок.
2. Виділити в RAM через `kmalloc()` тимчасовий буфер (англ. *bounce buffer*).
3. Розпакувати у цей буфер 128 КБ розпакованих даних.
4. Скопіювати потрібні 4 КБ у цільову сторінку Page Cache процесу.
5. Звільнити тимчасовий буфер.

Вимірювання показали, що 85% часу введення-виведення витрачалося на зчитування та декомпресію сусідніх 124 КБ даних, які взагалі не були потрібні для запуску програми. Це спричиняло кратне підвищення обсягу зчитування (Read Amplification) до 32 разів, мікрозависання інтерфейсу та постійний дециклічний виклики механізму витіснення сторінок (OOM killer) через фрагментацію оперативної пам'яті.

```
SquashFS: 128 КБ (несм.) → [ Compressor ] → 37 КБ (диск) → [ RAM Bounce Buffer ] → 4 КБ (Page Cache)
EROFS:    12 КБ (несм.)  → [ Compressor ] → 4 КБ (диск)  → [ In-place Direct ]    → 4 КБ (Page Cache)
```

## Створення парадигми Fixed-Output та підтримка ядра Linux

Наприкінці 2017 року Гао Сян запропонував принципово нову концепцію — файлову систему **EROFS** (Enhanced Read-Only File System). Замість стиснення з фіксованим входом EROFS впровадила **стиснення з фіксованим виходом** (Fixed-Output). На дисковому носії фізичні блоки стиснених даних мають строго визначений розмір 4 КБ, що збігається з розміром сторінки пам'яті архітектури ARM64 та x86_64 (`PAGE_SIZE`). 

Це дозволило реалізувати декомпресію за місцем (In-place decompression): ядро зчитує 4 КБ фізичного блоку безпосередньо у виділені сторінки Page Cache і виконує декодування прямо у цільові буфери без жодного тимчасового копіювання чи виділення додаткової RAM.

У травні 2018 року перша серія патчів EROFS була опублікована у поштовій розсилці Linux Kernel Mailing List (LKML). Разом із суворим рецензуванням Грега Кроа-Гартмана (Greg Kroah-Hartman) та розробників VFS-шару, драйвер спочатку увійшов до експериментальної гілки `drivers/staging/erofs` ядра Linux 4.19.

Протягом 2018–2019 років EROFS пройшла суворе випробування на більш ніж 100 мільйонах смартфонів Huawei та Honor. Після очищення коду від експериментальних залишків, додавання підтримки компресорів Zstd, LZMA та розширення безпеки, у листопаді 2019 року ядро Linux 5.4 офіційно прийняло EROFS до основного складу підсистеми файлових систем (`fs/erofs/`).

## Стандарт AOSP та розширення на мобільну індустрію

У 2022 році компанія Google опублікувала результати власного незалежного аудиту файлових систем для Android. Впровадження EROFS у випуску **Android 13 (AOSP)** як стандартної файлової системи за замовчуванням для системних Read-Only розділів (`/system`, `/vendor`, `/product`) показало вражаючі результати:
- Загальний обсяг системного образу скоротився на 600–800 МБ порівняно з нестисненим ext4.
- Споживання оперативної пам'яті ядра під час активного I/O зменшилося на 800 МБ за рахунок відмови від проміжних буферів.
- Час холодного запуску важких застосунків та ігор скоротився на 20–30%.

Після цього EROFS була адаптована більшістю провідних виробників мобільних пристроїв, включаючи Xiaomi, OPPO, vivo та Samsung.

## Контейнерна революція: Composefs, Nydus та FS-Cache (2021–2026)

Вихід EROFS за межі мобільних систем відбувся у 2021 році, коли спільнота хмарних обчислень зіткнулася із затримками під час розгортання великих контейнерних образів. Класичний підхід шаррування контейнерів через OverlayFS вимагає розпакування `tar.gz` архіву кожного шару на дискову файлову систему ноди. Це призводить до виникнення мільйонів дрібних файлів, виснаження кешу каталогів ядра (dentry cache) та тривалого часу розгортання образів.

Відомий розробник Red Hat Александр Ларссон (Alexander Larsson, автор Flatpak та OSTree) у співпраці з Джузеппе Скрівано (Giuseppe Scrivano) створив проєкт **Composefs**. Вони використали EROFS як підкладку для компактного, бінарно-захищеного дискового образу контейнера, який спирається на блокову дедуплікацію файлів (chunk-based deduplication).

Одночасно консорціум CNCF та компанія Alibaba розробили проєкт **Nydus Image Service**, який перевів контейнерні образи OCI на дисковий формат EROFS. Завдяки впровадженню підсистеми **FS-Cache** (`erofs over fscache`) у ядро Linux 5.19 розробники досягли безпрецедентної швидкості:
- Контейнерний образ монтується і починає виконання за **2–5 мілісекунд** без попереднього завантаження всіх гігабайтів шарів.
- Блоки EROFS підтягуються з мережевого реєстру за вимогою (on-demand streaming) в міру того, як процеси у контейнері запитують відповідні сторінки пам'яті.
- Система інтегрується з механізмом `fs-verity` для гарантії криптографічної незмінності кожного блоку контейнера.
