# 🔌 Архітектурне порівняння SquashFS та EROFS

<preknowlist>
- [Сторінковий кеш ядра](topic:unix-linux/page-cache-durability) — посторінкова підкачка та робота декомпресора у RAM.
- [Модель inode](topic:unix-linux/inode-model) — індексні вузли, метадані та відокремлення імен від вмісту.
</preknowlist>

Під час вибору стисненої файлової системи для незмінних системних образів операційних систем, мікро-VM rootfs або контейнерів інженери найчастіше обирають між двома системами: класичною **SquashFS** (створеною Філіпом Лоером, Phillip Lougher, у 2002 році) та сучасною **EROFS** (розробленою Гао Сяном у 2017 році). Попри спільне практичне призначення — забезпечення максимальної щільності збереження даних у формі Read-Only — внутрішня архітектура цих систем базується на протилежних фундаментальних принципах роботи з диском та оперативною пам'яттю.

| Архітектурний параметр | SquashFS | EROFS |
| :--- | :--- | :--- |
| **Парадигма стиснення** | Fixed-Input (фіксований вхідний блок 128–1024 КБ) | Fixed-Output (фіксований дисковий блок 4 КБ) |
| **Декомпресія в RAM** | Через тимчасовий проміжний буфер (Bounce Buffer) | Безпосередньо за місцем (In-place Decompression) |
| **Вирівнювання блоків** | Дискові блоки не мають апаратного вирівнювання | Строге фізичне вирівнювання по 4 КБ (`PAGE_SIZE`) |
| **Розмір індексного вузла** | Змінний / складений формат метаданих | Фіксований: Compact (32 B) або Extended (64 B) |
| **Упаковка хвостів файлів** | Збір хвостів файлів у окремі узагальнені блоки | Inline Tail-Packing безпосередньо в блок метаданих |
| **Дедуплікація xattr** | Загальний словник розширених атрибутів | Індексована таблиця спільних атрибутів (Shared xattr) |
| **Подвійне кешування** | Потребує кешування стисненого та розпакованого блоку | Кешуються лише підсумкові сторінки Page Cache |
| **Натиск на кеш каталогів** | Стандартні сутності VFS для кожного файла | Оптимізоване плоске картування дрібних файлів |
| **Інтеграція з FS-Cache** | Обмежена (вимагає проміжних шарів) | Нативна підтримка `erofs over fscache` для контейнерів |

## Парадигма стиснення: Fixed-Input проти Fixed-Output

Фундаментальна відмінність виявляється на рівні дискового планування стиснених даних. 

У **SquashFS** вхідний потік оригінального файла розбивається на однакові блоки великого розміру (зазвичай 128 КБ, 256 КБ або 1024 КБ). Кожен блок стискається алгоритмом zlib, XZ або Zstd у вихідний кусок довільної дискової довжини. Це забезпечує дуже високий коефіцієнт стиснення на статичних даних, але створює важку залежність між сусідніми байтами усередині 128-кілобайтного блоку.

У **EROFS** застосовується принцип стиснення з фіксованим виходом (Fixed-Output). Компресор бере логічні екстентні блоки нестиснених даних різного обсягу (наприклад, 8 КБ, 12 КБ чи 16 КБ) і упаковує їх так, щоб підсумковий результат заповнював строго один або декілька фізичних блоків розміром точно 4096 байтів (`PAGE_SIZE`). Усі дискові блоки EROFS починаються за зсувами, кратними 4 КБ, що збігається з апаратною архітектурою сторінкової пам'яті x86_64 та ARM64.

```
SquashFS: [ Вхід: 128 КБ ] → [ Compressor ] → [ Диск: 37 412 B (невирівняно) ]
EROFS:    [ Вхід: 12 КБ  ] → [ Compressor ] → [ Диск: 4096 B (строго PAGE_SIZE) ]
```

## Декомпресія та копіювання в оперативній пам'яті

Найважливіша різниця у продуктивності виникає під час обробки промаху кешу сторінки (англ. *page fault*). Коли програма звертається до 4 КБ даних з файла у SquashFS, драйвер системи змушений виконати громіздкий ланцюжок дій:
1. Зчитати з фізичного накопичувача увесь стиснений 128-кілобайтний блок.
2. Динамічно виділити в оперативній пам'яті ядра через `kmalloc()` тимчасовий буфер (англ. *bounce buffer*).
3. Розпакувати у цей буфер 128 КБ нестиснених даних.
4. Скопіювати потрібні 4 КБ у цільову сторінку Page Cache процесу.
5. Звільнити тимчасовий буфер.

Цей процес спричиняє **кратне підвищення обсягу зчитування** (англ. *read amplification*): ядро розпаковує до 32 разів більше даних, ніж запитувала програма. Виділення та звільнення пам'яті під навантаженням провокує фрагментацію ядра та сплески затримок (англ. *latency spikes*).

В EROFS кожен дисковий блок стиснених даних має строго визначений розмір 4 КБ. При виконанні запиту читання декомпресор ядра розпаковує логічний екстент даних безпосередньо у виділені сторінки Page Cache. Драйвер EROFS декодує LZ4 у ковзному (rolling) режимі: стиснений блок лежить у хвості цільового масиву сторінок, а розпакований вихід росте від його початку, тож ані проміжний буфер, ані `memcpy()` не потрібні.

```
Витрати RAM на декомпресію однієї 4 КБ сторінки:
SquashFS = [ ~37 КБ стиснений блок з диска ] + [ 128 КБ розпакований буфер ] + [ 4 КБ Page Cache ] ≈ 170 КБ RAM
EROFS    = [ 4 КБ фізичний диск ] → In-Place Decompress → [ 4 КБ Page Cache ] = 4 КБ RAM
```

## Упаковка хвостів файлів (Tail-packing)

У файлових системах із фіксованим розміром блоку 4 КБ кожний файл, чий розмір не кратний 4096 байтам, лишає невикористаний хвіст у своєму останньому блоці. Наприклад, файл розміром 4097 байт займає два повних блоки (8192 байти), марнуючи 4095 байт.

- **SquashFS** вирішує це шляхом об'єднання останніх фрагментів тисяч різних файлів у так звані «хвостові блоки» (англ. *fragment blocks*). Однак це ускладнює обхід файлів: для читання останнього байта файла потрібно зчитати спільний хвостовий блок, що руйнує послідовність читання та спричиняє додаткові затримки I/O.
- **EROFS** застосовує механізм **Inline Tail-packing** (`EROFS_INODE_FLAT_INLINE`). Якщо залишок файла не перевищує розміру вільного місця у блоці метаданих (одразу за структурою `erofs_inode`), цей залишок записується безпосередньо в той самий 4-кілобайтний блок, де лежить сам індексний вузол. Отримання метаданих файла (`stat`) та його кінцевих байтів відбувається за одну операцію читання з диска.

## Спільна таблиця розширених атрибутів (Shared xattributes)

У мобільній ОС Android та сучасних контейнерах Linux кожен файл захищається мітками безпеки SELinux або анотаціями контейнера (наприклад, `security.selinux="u:object_r:system_file:s0"`). У системному образі з 100 000 файлів ці текстові рядки дублюються 100 000 разів, марнуючи мегабайти дискового простору.

- **SquashFS** тримає атрибути в окремих стиснених метаблоках: щоб прочитати атрибути файла, драйвер мусить розпакувати відповідний метаблок таблиці.
- **EROFS** впроваджує індексовану таблицю спільних розширених атрибутів (`shared xattr table`). Під час збирання образу інструмент `mkfs.erofs` виявляє однакові атрибути та зберігає їх в єдиному глобальному масиві. В індексних вузлах файлів зберігаються лише 32-бітні індекси-посилання на елементи цієї таблиці.

## Онлайн-завантаження та контейнерні стеки

Для сучасних хмарних навантажень критичною є можливість інтеграції з підсистемами мережевої підкачки даних:

- **SquashFS** розроблялася для локальних носіїв (CD-ROM, флеш-карти, розділи жорстких дисків). Запуск SquashFS-образу з мережі вимагає попереднього завантаження всього монолітного файлу образу або використання складних обгорток FUSE.
- **EROFS** підтримує нативний шар **FS-Cache** (`erofs over fscache`), доданий у ядро Linux 5.19. Це дозволяє проєктам на кшталт Nydus запускати контейнери з мережевих реєстрів, не чекаючи на повне завантаження образу: блоки EROFS підтягуються за вимогою (on-demand) лише тоді, коли процес у контейнері звертається до відповідних сторінок пам'яті.
