# Архітектура B-дерев файлової системи Btrfs

<preknowlist>
- [Файлова система Btrfs: Copy-on-Write та субтоми](book:unix-linux/btrfs-copy-on-write-and-subvolumes) — концепція CoW та поверхневе уявлення про Btrfs.
- [Модель Inode та VFS](book:unix-linux/inode-model) — принципи репрезентації метаданих файлів у Linux.
</preknowlist>

Більшість класичних файлових систем Linux (таких як Ext4) використовують фіксовані таблиці інодів (inode tables), масиви блоків та окремі структури для зберігання директорій і атрибутів. На противагу їм, **Btrfs (B-tree File System)** побудована навколо єдиної універсальної концепції: **все всередині файлової системи є B-деревом**. 

Усі атрибути файлів, дані, вміст директорій, списки прав доступу (ACL), карти екстентів і навіть параметри субтомів зберігаються у вигляді записів (items) у підсистемі з кількох зв'язаних між собою дерев `B-tree` з підтримкою механізму **Copy-on-Write (CoW)**.

## Апаратна та структурна анатомія B-дерева Btrfs

Кожен вузол (node) та листок (leaf) B-дерева в Btrfs має фіксований розмір метаданих (за замовчуванням 16 КБ або `nodesize`) і представляється в ядрі структурою `btrfs_header`.

```c
// Заголовок кожного вузла та листка B-дерева Btrfs (fs/btrfs/ctree.h)
struct btrfs_header {
    u8 csum[BTRFS_CSUM_SIZE]; // Контрольна сума всього вузла (CRC32c / xxHash)
    u8 fsid[BTRFS_FSID_SIZE]; // UUID файлової системи
    __le64 bytenr;            // Логічна адреса цього вузла на диску
    __le64 flags;             // Прапорці вузла
    u8 chunk_tree_uuid[BTRFS_UUID_SIZE];
    __le64 generation;        // Номер транзакції (Transaction ID), коли написано вузол
    __le64 owner;             // ID дерева-власника (наприклад, ROOT_TREE_OBJECTID)
    __le32 nritems;           // Кількість елементів у вузлі/листку
    u8 level;                 // Рівень у дереві (0 = листок, >0 = внутрішній вузол)
} __attribute__ ((packed));
```

### Структура Листка (Leaf): Ключ, Елемент та Дані

Усі реальні корисні дані зберігаються виключно на **рівні 0 (Leaf)**. Листок ділиться на дві зони, що ростуть назустріч одна одній:
- **Заголовки елементів (`struct btrfs_item`):** ростуть від початку листка вперед.
- **Тіла даних (Data payloads):** ростуть від кінця листка назад.

```c
// Заголовок елемента всередині листка
struct btrfs_item {
    struct btrfs_key key;     // Унікальний 3-компонентний ключ Btrfs
    __le32 offset;            // Зсув до даних усередині листка
    __le32 size;              // Розмір даних у байтах
} __attribute__ ((packed));

// Фундаментальний ключ пошуку в Btrfs
struct btrfs_key {
    __le64 objectid;          // ID об'єкта (наприклад, номер іноди або ID субтому)
    u8 type;                  // Тип запису (INODE_ITEM, EXTENT_DATA, DIR_ITEM)
    __le64 offset;            // Допоміжний зсув (зсув у файлі, хеш імені тощо)
} __attribute__ ((packed));
```

## Триплет Ключа `(objectid, type, offset)`

Будь-який факт у Btrfs шукається за впорядкованим триплетом `key = (objectid, type, offset)`:

1. **`objectid` (64-біт):** Ідентифікатор об'єкта. Для файлу або директорії це номер його іноди (наприклад, `256`).
2. **`type` (8-біт):** Семантичний тип даних:
   - `BTRFS_INODE_ITEM_KEY` (1): Основні метадані файлу (розмір, UID, GID, mtime).
   - `BTRFS_INODE_REF_KEY` (12): Зворотне посилання на ім'я та батьківську директорію.
   - `BTRFS_DIR_ITEM_KEY` (84): Запис у директорії (ім'я файлу ➔ target objectid).
   - `BTRFS_EXTENT_DATA_KEY` (108): Вказівник на дані файлу (inline дані або диск-екстент).
3. **`offset` (64-біт):** Допоміжне значення. Для `EXTENT_DATA` це байтовий зсув усередині файлу (наприклад, `0`, `4096`, `8192`); для `DIR_ITEM` — хеш імені файлу.

> Завдяки тому, що ключі в листку впорядковані спочатку за `objectid`, потім за `type`, а потім за `offset`, **усі метадані одного файлу розміщуються поруч у листку**, що забезпечує колосальну локальність читання!

## Архітектура Дерев у Btrfs: Ліс Дерев (Forest of Trees)

Btrfs складається з кількох спеціалізованих дерев, які посилаються одне на одне:

```
                  [ Root Tree ]
                 /      |      \
                /       |       \
     [ FS Tree ]  [ Chunk Tree ]  [ Extent Tree ]
    (Субтом 1)    (Логічні ➔      (Облік вільних
                   Фізичні блоки)  блоків та refcount)
```

1. **Root Tree (Дерево коренів):** Головне дерево метаданих. Його листки містять записи `BTRFS_ROOT_ITEM_KEY`, які вказують на коріння всіх інших дерев (включно із субтомами та снапшотами).
2. **FS Tree (Дерево файлової системи):** Зберігає іноди, директорії та дані конкретного субтому. Кожен новий субтом або CoW-снапшот — це просто нове FS Tree.
3. **Chunk Tree (Дерево чанків):** Транслює логічні віртуальні адреси Btrfs у фізичні адреси на блочних пристроях. Саме Chunk Tree реалізує всередині Btrfs програмний RAID (RAID0, RAID1, RAID10, RAID5/6).
4. **Extent Tree (Дерево екстентів):** Веде облік використання кожного фізичного блоку на диску, лічильники посилань (reference count) для підтримки CoW-дедуплікації та де-алокації.

## Механізм Copy-on-Write (CoW) на B-деревах

Коли у файл вносяться зміни:
1. Btrfs не перезаписує існуючий листок. Вона алокує новий листок на диску і записує модифіковані дані туди.
2. Батьківський вузол (Node рівень 1) оновлює вказівник на новий листок. Оскільки батьківський вузол теж змінився, він також записується в нове місце (CoW propagation).
3. Шлях модифікації піднімається до самого Root Tree.
4. Оновлений корінь Root Tree фіксується у Superblock під час транзакції `btrfs_commit_transaction()`.

> 🔧 **Навіщо це.** Завдяки CoW на рівнях B-дерева, створення мгновенного снапшота субтому Btrfs виконується за O(1) часу: ядро просто створює новий `BTRFS_ROOT_ITEM` у Root Tree, який вказує на той самий корінь FS Tree, і збільшує лічильники посилань вузлів у Extent Tree.
