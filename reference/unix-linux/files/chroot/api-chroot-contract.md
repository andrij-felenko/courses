# 📋 Контракт chroot і сусідніх засобів

Тут зібрано те, що треба мати перед очима, коли пишеш код або конфіг: точні підписи `chroot(2)`, `pivot_root(2)` і `openat2(2)`, повні переліки кодів помилок і вимог, а також те, як ці три виклики виставлені назовні — командою `chroot(1)`, директивами sshd і systemd, опціями монтування.

## chroot(2)

```c
#include <unistd.h>

int chroot(const char *path);
```

Повертає `0` при успіху, `-1` і виставлений `errno` при помилці. Аргумент один, прапорців немає, режимів немає.

Дія теж одна: поле кореня в описі файлової частини процесу починає вказувати на каталог `path`. Після цього кожен розбір шляху, що починається з «/», стартує звідти, і компонент `..` у самому корені веде сам у себе.

Потрібна можливість — **`CAP_SYS_CHROOT`**, і саме в тому просторі імен користувачів, якому належить процес ([можливості](book:unix-linux/capabilities), [простори імен](book:unix-linux/namespaces)). Це важлива дрібниця: у власному просторі користувачів звичайний користувач має повний набір можливостей, тож `chroot` там доступний і без прав root у системі.

### Коди помилок

| `errno` | Коли |
|---|---|
| `EPERM` | у процесу немає `CAP_SYS_CHROOT` у своєму просторі імен користувачів |
| `EACCES` | немає права пошуку на якомусь компоненті шляху (біт `x` на каталозі) |
| `ENOENT` | такого файлу немає |
| `ENOTDIR` | компонент шляху — не каталог (зокрема й сам `path`) |
| `ELOOP` | забагато символьних посилань під час розбору `path` |
| `ENAMETOOLONG` | шлях задовгий |
| `EFAULT` | `path` указує поза доступний процесові адресний простір |
| `ENOMEM` | ядру забракло пам'яті |
| `EIO` | помилка вводу-виводу |

Окремої помилки «каталог не порожній», «у дереві немає shell» чи «дерево не самодостатнє» не існує — ядро таких питань не ставить. Усе, що бракує всередині, вилізе пізніше й під іншими іменами: найчастіше як `ENOENT` від динамічного завантажувача, який не знайшов `ld.so` або бібліотек.

### Чого виклик не робить

Перелік важить не менше за перелік помилок, бо саме з нього ростуть усі відомі втечі.

| Не змінюється | Наслідок |
|---|---|
| поточний каталог | може лишитися **поза** новим деревом — і тоді `..` не впирається ні в що |
| вже відкриті дескриптори | лишаються дійсними; дескриптор каталогу плюс `fchdir` виводить із дерева без жодних привілеїв |
| `umask` | успадковується як був |
| таблиця монтувань | спільна з усією системою; старе дерево лишається змонтованим |
| uid, gid, набір можливостей | процес-root лишається root ([uid і gid](book:unix-linux/uid-gid-model)) |
| простір PID-ів, сокети, засоби IPC | поза дією виклику цілком |

### Успадкування: fork, execve, потоки

| Подія | Що з коренем процесу |
|---|---|
| `fork(2)` | дитина отримує той самий корінь |
| `execve(2)` | не змінюється — тому `chroot /srv/ftp /bin/sh` узагалі можливий |
| `clone(2)` **без** `CLONE_FS` | дитина працює з **копією** — подальші `chroot`, `chdir`, `umask` в одного не зачіпають іншого |
| `clone(2)` **з** `CLONE_FS` | структура **спільна**: `chroot`, `chdir` або `umask` в одного негайно діють і на іншого |
| `pthread_create(3)` | створює задачу з `CLONE_FS` → **корінь спільний для всіх потоків процесу** |

Останній рядок — головна пастка багатопотокових програм. `chroot` в одному потоці міняє корінь **усій** програмі, і не колись потім, а тієї ж миті; сусідній потік, який саме зараз відкриває файл за абсолютним шляхом, отримає інший файл або `ENOENT`. Тому корінь міняють до створення потоків — або в дитині одразу після `fork`, поки вона однопотокова ([потоки як задачі](book:unix-linux/threads-as-tasks)).

Відв'язати спільну структуру можна викликом `unshare(CLONE_FS)` — після нього корінь, поточний каталог і `umask` у цієї задачі стають власними. Дві заборони ядра варто знати наперед: `CLONE_FS` не поєднується ні з `CLONE_NEWNS` (новий простір монтувань), ні з `CLONE_NEWUSER` — тобто задача, що заводить собі окремий простір монтувань, автоматично перестає ділити корінь із рештою.

### Погляд ззовні: `/proc/<pid>/root`

```
/proc/<pid>/root        магічне посилання на корінь процесу <pid>
/proc/<pid>/cwd         магічне посилання на його поточний каталог
```

Магічне — бо це не текстове посилання, яке ядро розкриває в рядок, а покажчик просто на об'єкт у дереві. Звідси два різні вживання:

- `readlink("/proc/1234/root", …)` — дізнатися, де корінь чужого процесу;
- `open("/proc/1234/root/etc/passwd", …)` — **зайти** в чуже дерево, не змінюючи власного кореня.

Друге вживання й робить `procfs` дірою в обороні: процес із `CAP_SYS_ADMIN`, що змонтував `proc` усередині свого дерева, читає `/proc/1/root` і отримує справжній корінь системи. Доступ до цих посилань регулюють ті самі правила, що й доступ через `ptrace`: чужий процес пустить лише того, хто мав би право до нього приєднатися ([procfs](book:unix-linux/proc-filesystem)).

### Мінімальний правильний виклик

Порядок рядків тут не стилістичний — кожен закриває конкретну дорогу назовні, і жоден не можна переставити.

```c
if (chdir("/srv/jail") < 0) err(1, "chdir");
if (chroot("/srv/jail") < 0) err(1, "chroot");  /* потребує CAP_SYS_CHROOT */
if (chdir("/") < 0) err(1, "chdir");            /* інакше cwd лишиться поза деревом */

if (setgroups(0, NULL) < 0) err(1, "setgroups"); /* додаткові групи — геть */
if (setgid(gid) < 0) err(1, "setgid");           /* група ДО користувача */
if (setuid(uid) < 0) err(1, "setuid");           /* після цього прав уже немає */

closefrom(3);                                    /* успадковані дескриптори — геть */
```

Три обов'язкові умови порядку: `chroot` іде до втрати привілею; `chdir("/")` — поки поточний каталог іще можна поставити на місце; `setgid` — до `setuid`, бо після скидання uid змінити групу вже не вийде. `closefrom(3)` є в glibc з версії 2.34; де його немає, пробігають `/proc/self/fd` або ставлять `FD_CLOEXEC` заздалегідь ([файловий дескриптор](book:unix-linux/file-descriptor)).

### Статус у стандартах

`chroot` **не входить** до POSIX.1-2001 і пізніших. Він є в SVr4 і 4.4BSD, а в ранніх редакціях Single UNIX Specification був позначений як застарілий і згодом вилучений. Практично це означає: виклик присутній скрізь, де є Unix, але його точна поведінка — справа конкретного ядра, і переносних гарантій щодо неї немає.

## chroot(1) з coreutils

```
chroot [OPTION]... NEWROOT [COMMAND [ARG]...]
```

Команда — тонка обгортка: змінити корінь, перейти в новий «/», за потреби скинути особу, запустити програму. У ядрі з цього є лише перший крок.

| Опція | Дія |
|---|---|
| `--userspec=USER:GROUP` | запустити програму від цього користувача й групи (ім'я або число) |
| `--groups=G_LIST` | задати додаткові групи списком через кому: `g1,g2,…` |
| `--skip-chdir` | **не** переходити в «/» після зміни кореня |

Без `COMMAND` запускається `"$SHELL" -i`, а якщо `SHELL` не заданий — `/bin/sh -i`.

Три деталі, на яких спотикаються.

**`--skip-chdir` дозволений, тільки якщо `NEWROOT` — це «/».** Інакше команда відмовляється працювати з повідомленням `option --skip-chdir only permitted if NEWROOT is old /`. Заборона навмисна: пропустити перехід у новий корінь для справжнього дерева означало б лишити поточний каталог поза ним — тобто зібрати описану вище втечу власними руками. Єдине осмислене вживання опції — коли корінь не міняється, а команда потрібна лише заради `--userspec`.

**Порядок скидання прав — той самий, що й у коді вище:** `setgroups()`, потім `setgid()`, потім `setuid()`.

**Імена користувача й груп розв'язуються двічі — зовні та всередині дерева.** Якщо в `--userspec` подано ім'я, а не число, воно шукається в базі системи, а додаткові групи — ще й у базі всередині нового кореня, бо `/etc/passwd` і `/etc/group` там можуть бути іншими. Коли обидва пошуки провалилися, команда падає з `failed to get supplemental groups`. Тому в скриптах надійніше подавати числа: `--userspec=1000:1000`.

Коди виходу відрізняють поламану обгортку від поламаної програми:

| Код | Значення |
|---|---|
| `125` | не вдалася сама команда `chroot` (немає прав, немає каталогу) |
| `126` | `COMMAND` знайдено, але не вдалося запустити |
| `127` | `COMMAND` не знайдено (найчастіше — бракує бібліотек у дереві) |
| решта | код виходу самої `COMMAND` |

## pivot_root(2)

```c
#include <sys/syscall.h>
#include <unistd.h>

int syscall(SYS_pivot_root, const char *new_root, const char *put_old);
```

Обгортки в glibc немає — викликають через `syscall()`. Дія: кореневе монтування простору монтувань замінюється на те, що під `new_root`, а старе переїжджає під `put_old`, звідки його можна відмонтувати ([pivot_root](book:unix-linux/pivot-root)).

Потрібна можливість — **`CAP_SYS_ADMIN`** у просторі імен користувачів, що володіє простором монтувань викликача.

### Вимоги, які треба виконати заздалегідь

Виклик прискіпливий, і майже кожне `EINVAL` від нього — це порушення одного з цих пунктів:

- обидва аргументи вказують на **каталоги**;
- ні `new_root`, ні `put_old` не лежать на тому самому монтуванні, що й нинішній корінь;
- `put_old` розташований **у самому `new_root` або нижче** (тобто дописування кількох «/..» до `put_old` дає той самий каталог, що й `new_root`);
- `new_root` **є точкою монтування** — і не «/». Звичайний каталог годиться лише після прив'язки самого до себе: `mount(new_root, new_root, NULL, MS_BIND, NULL)`;
- нинішній корінь теж є точкою монтування;
- тип поширення не `MS_SHARED` — ні в батьківського монтування `new_root`, ні в батьківського монтування нинішнього кореня, ні в самого `put_old`, якщо той уже є точкою монтування;
- нинішній корінь **не на `rootfs`** — початковій ramfs. Саме тому початковий образ користується `switch_root`, а не голим `pivot_root`.

| `errno` | Причина |
|---|---|
| `EBUSY` | `new_root` або `put_old` лежить на монтуванні нинішнього кореня |
| `EINVAL` | `new_root` не є точкою монтування |
| `EINVAL` | `put_old` не всередині `new_root` |
| `EINVAL` | нинішній корінь не є точкою монтування |
| `EINVAL` | нинішній корінь на `rootfs` |
| `EINVAL` | тип поширення котрогось монтування — `MS_SHARED` |
| `ENOTDIR` | котрийсь аргумент не каталог |
| `EPERM` | немає `CAP_SYS_ADMIN` |

### Ідіома без тимчасового каталогу

Класичний рецепт вимагав створити всередині нового дерева порожню теку під старий корінь. Але оскільки `pivot_root` кладе старе кореневе монтування **поверх** нового кореня, обидва аргументи можна подати як «.»:

```c
chdir(new_root);
syscall(SYS_pivot_root, ".", ".");   /* старий корінь лягає стосом поверх нового */
umount2(".", MNT_DETACH);            /* знімаємо верхній шар — лишається новий корінь */
```

Ніякої теки заводити не треба, і в дереві не лишається сліду. Це той варіант, яким користуються сучасні середовища запуску контейнерів.

## openat2(2): корінь на час одного розбору

Ядро 5.6 (`RESOLVE_CACHED` — з 5.12). Розв'язує симетричну задачу: програма живе **зовні** й мусить розібрати шлях, що стосується чужого дерева, — не замикаючи себе й не маючи жодних привілеїв ([сімейство *at](book:unix-linux/at-family-syscalls)).

```c
#include <linux/openat2.h>
#include <sys/syscall.h>
#include <unistd.h>

struct open_how {
    __u64 flags;      /* ті самі O_*, що в openat(2) */
    __u64 mode;       /* лише біти 07777 */
    __u64 resolve;    /* маска RESOLVE_* */
};

long syscall(SYS_openat2, int dirfd, const char *pathname,
             struct open_how *how, size_t size);
```

Останній аргумент — `sizeof(struct open_how)`: структура розширювана, і розмір каже ядру, яку саме її редакцію знає програма. Ще одна відмінність від `openat`: невідомі або суперечливі біти тут **не ігноруються мовчки**, а дають помилку — тож перевірити підтримку прапорця можна просто спробувавши його.

| Прапорець `resolve` | Дія |
|---|---|
| `RESOLVE_BENEATH` | жоден компонент розбору не сміє вийти за піддерево `dirfd`; абсолютні `pathname` і абсолютні символьні посилання **відхиляються** |
| `RESOLVE_IN_ROOT` | `dirfd` вважається коренем: `..` у ньому веде сам у себе, абсолютні шляхи й абсолютні посилання розбираються **від нього** |
| `RESOLVE_NO_SYMLINKS` | символьні посилання не розбираються взагалі (вмикає й `RESOLVE_NO_MAGICLINKS`) |
| `RESOLVE_NO_MAGICLINKS` | заборонити магічні посилання — `/proc/<pid>/root`, `/proc/<pid>/fd/N` |
| `RESOLVE_NO_XDEV` | не переходити точки монтування, зокрема прив'язані |
| `RESOLVE_CACHED` (5.12) | відмовити, якщо не всі компоненти вже є в кеші пошуку — швидкий шлях для `io_uring` |

Різниця між двома першими прапорцями практична, а не смакова. `RESOLVE_BENEATH` **відхиляє** вихід за межі — годиться, коли шлях мали дати свій код або довірений конфіг, і вихід за межі означає помилку. `RESOLVE_IN_ROOT` **загортає** вихід усередину — годиться, коли шлях прийшов ззовні: з архіву, від клієнта, з чужої файлової системи, — і `../../etc/passwd` має просто впертися в корінь дерева, а не завалити операцію.

| `errno` | Причина |
|---|---|
| `EXDEV` | виявлено спробу вийти за межі (`BENEATH`/`IN_ROOT`) або перетнути монтування (`NO_XDEV`) |
| `ELOOP` | трапилося символьне або магічне посилання, коли воно заборонене |
| `EAGAIN` | дерево під час розбору перебудували, і ядро не змогло поручитися за захист від `..`; виклик слід повторити. Також — промах кеша при `RESOLVE_CACHED` |
| `EINVAL` | невідомий або суперечливий прапорець |
| `E2BIG` | у структурі є ненульові поля з розширення, якого ядро не знає |

`EAGAIN` варто виділити: це не відмова, а прохання повторити. Ядро розбирає шлях без глобального замка́, і якщо посеред розбору хтось перемістив каталог, воно чесно зізнається замість того, щоб віддати сумнівний результат.

```c
struct open_how how = {
    .flags   = O_RDONLY | O_CLOEXEC,
    .resolve = RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS,
};
int root = open("/srv/www", O_PATH | O_DIRECTORY | O_CLOEXEC);
int fd;
do {
    fd = syscall(SYS_openat2, root, req_path, &how, sizeof how);
} while (fd < 0 && errno == EAGAIN);
```

Тут `req_path` — рядок просто від клієнта, без жодної фільтрації: усі `..`, усі провідні «/» і всі посилання розбере ядро в межах `/srv/www`.

## Як це виставлено в інструментах

### sshd: ChrootDirectory

```
# у sshd_config або в блоці Match
Match Group sftponly
    ChrootDirectory /srv/sftp/%u
    ForceCommand internal-sftp
```

| Пункт контракту | Що саме |
|---|---|
| Коли спрацьовує | після автентифікації |
| Куди стає cwd | у домашній каталог користувача (вже всередині дерева) |
| Підстановки | `%%`, `%h` (домашній каталог), `%u` (ім'я користувача), `%U` (uid) |
| **Вимога до власника** | **усі** компоненти шляху — каталоги, що належать root і не доступні на запис ні групі, ні решті. Перевіряє сам `sshd` і відмовляє в сесії |
| Що треба всередині для оболонки | власне оболонка та вузли `/dev`: `null`, `zero`, `stdin`, `stdout`, `stderr`, `tty` |
| Що треба для SFTP | нічого, якщо вжито `internal-sftp` — сервер працює в самому процесі; для журналювання подекуди потрібен `/dev/log` |

Вимога «власник root, чужого запису немає» — не прискіпливість. Якщо користувач може писати в корінь свого дерева або в будь-який каталог на шляху до нього, він підкладає туди власну `libc.so` чи власний `/etc/nsswitch.conf` — і будь-яка програма, що стартує в цьому дереві з підвищеними правами, завантажить **його** код. Звужений простір імен перетворюється на важіль підвищення привілеїв ([setuid і підвищення прав](book:unix-linux/setuid-and-privilege)).

Через це саме `ForceCommand internal-sftp` є типовою відповіддю: у дереві не треба ні оболонки, ні бібліотек, ні вузлів пристроїв — а отже, немає й чого підмінювати.

### systemd: RootDirectory= і RootImage=

```ini
[Service]
RootDirectory=/srv/app
MountAPIVFS=yes
PrivateUsers=yes
```

| Директива | Дія |
|---|---|
| `RootDirectory=` | корінь для процесів служби; systemd бере `pivot_root(2)` **або** `chroot(2)` — залежно від того, що виходить у цьому оточенні |
| `RootImage=` | те саме, але дерево береться з блокового пристрою чи файлу-образу: гола файлова система, єдиний Linux-розділ у MBR/GPT або образ за Discoverable Partitions Specification |
| `RootImageOptions=` | опції монтування образу; можна на розділ — `root:ro,usr:nodev` |
| `RootEphemeral=` | працювати з одноразовою копією дерева в `/var/lib/systemd/ephemeral-trees/`, яку прибирають при зупинці |
| `MountAPIVFS=` | завести окремий простір монтувань і змонтувати всередині `/proc`, `/sys`, `/dev` і порожній `tmpfs` на `/run`. Саме по собі не діє — лише разом із `RootDirectory=`/`RootImage=` |

Дві межі, які економлять годину налагодження. Перша: служба у власному корені **не бачить журналу вузла**, поки сокет журналу не змонтований усередину; натомість `os-release` вузла systemd кладе сам — у `/run/host/os-release`. Друга: у службах користувача ці директиви працюють, лише коли ввімкнено `PrivateUsers=` (для `RootImage=`, `RootEphemeral=` і `MountAPIVFS=` — неявно), а це вимагає підтримки непривілейованих просторів імен користувачів у ядрі ([модель systemd](book:unix-linux/systemd-model)).

### Опції монтування під деревом

| Опція | Дія |
|---|---|
| `nosuid` | не зважати на біти set-user-ID і set-group-ID **та на можливості, записані у файлі** |
| `nodev` | не тлумачити символьні й блокові файли пристроїв — вузол лишається просто записом у каталозі |
| `noexec` | не виконувати з цієї файлової системи двійкові файли безпосередньо |
| `ro` | тільки читання |

Мінімум для дерева, куди пускають користувача, — `nosuid,nodev` ([модель монтування](book:unix-linux/mount-model)). Перша опція закриває підміну бібліотек під програму з підвищеними правами, друга — читання диска повз файлову систему через власноруч створений вузол. Варто помітити, що `nosuid` знімає **і** файлові можливості: без цього програма з `CAP_DAC_OVERRIDE` у розширених атрибутах дала б рівно те саме, що й програма з бітом setuid, тільки тихіше.

`noexec` і `ro` до цього мінімуму не належать, бо часто просто несумісні з задачею: у дереві для збірки треба і виконувати, і писати.

## Що коли брати

| Задача | Засіб |
|---|---|
| зібрати чи полагодити систему в окремому дереві | `chroot(1)` |
| служба скидає права й далі не має назв для решти файлів | `chroot(2)` + `setgid`/`setuid` + закриття дескрипторів |
| контейнер: старого дерева не має бути навіть у таблиці монтувань | власний простір монтувань + `pivot_root(2)` |
| розібрати недовірений шлях, лишаючись зовні | `openat2(2)` з `RESOLVE_IN_ROOT` |
| перевірити, що свій же шлях не вийшов за межі теки | `openat2(2)` з `RESOLVE_BENEATH` |
| віддати файл, не наступивши на символьне посилання | `openat2(2)` з `RESOLVE_NO_SYMLINKS` |
