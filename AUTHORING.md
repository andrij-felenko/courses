# Канон письма (єдиний для всіх книг)

Правила письма — **тут**. План/черга/статуси — у маніфесті книги/курсу (схема — §2). Скрипти — у `scripts/`.

## §1 Структура — три теки

**`book/` — предметні книги.** Стаття лежить у **галузі предмета** (поле `sections` маніфесту; напр. «Аналогова», «Механіка»), **без нумерації**. **Стаття = тема** (стаття пишеться навколо однієї теми). Кожна стаття **самодостатня й не залежить від інших**: може посилатися на іншу, але **не вживає фраз послідовності** («попередній/наступний розділ», «як ми бачили», «далі побачимо», «пригадаймо», «ми це проходили») — порядку в книзі немає.

8 книг: `electronics` (Електроніка), `physics` (Фізика), `math` (Математика), `programming` (Програмування), `algorithms` (Алгоритми), `communications` (Зв'язок), `chemistry` (Хімія), `philosophy` (Філософія).

**`guide/` — навчальні книги (курси).** Теми йдуть **послідовно** — впорядкована програма (нумерується). Крок курсу:
- **`ref`** — пряме посилання на готову статтю з `book/` (коли тема цілісна й належить предметній книзі);
- **власна тема guide** — коли вона **поєднує** кілька book-статей у синтез; **не дублює** їхній зміст, лише сплітає; спиратися може **лише назад** (на пройдене в курсі), без забігань уперед.

Наративна нитка курсу живе **у власних темах guide і структурі його модулів**, не всередині book-статей. book-стаття, навіть кроком курсу, лишається самодостатньою. Фрази послідовності — **лише** у власних темах guide. 2 курси: `embedded`, `basic-chemistry`.

**`catalog/` — книги-каталоги.** Згруповані **описи конкретних об'єктів** (деталей; згодом і ширше). Запис **описує конкретну річ**, а не будує наукову ідею. Поводиться **як `book/`** (без порядку, базова+детальна версії, вставки `hist-`/`math-`/`proj-` — але **не** `comp-`, бо каталог і є компонентом). Поки: `pcb-board`, `sensor-board`.

**`comp-` (вставка) ↔ `catalog/`:** у `comp-`-вставках лишаємо **лише компоненти, прямо потрібні в науці теми** (прилад, що ілюструє фізику теми); усе, що **не прив'язане один-до-одного** (плати, модулі, вузли) — у `catalog/`.

## §2 Нейминг, нумерація, маніфест

**Нейминг — slug-only** (ASCII, **без номерів**): `book/<book>/<галузь>/<slug>/<slug>.md`; так само `catalog/…`, `guide/…`. Детальна — `<slug>-d.md`; вставки — `<type>-<name>.md`. Колізії slug — мінімальним кваліфікатором.

**Нумерація:** `book/` і `catalog/` — **без номерів** (ні в теках, ні в тексті, ні в підписах фігур). `guide/` **нумерується** — Модуль · Розділ · Крок (поля `n` маніфесту курсу), нумерація **в маніфесті**, не в slug.

**Маніфест — єдине джерело** навігації, плану, черги, статусів. **Один маніфест на книгу/курс**; нові поля поза схемою не вигадуємо.

**book** — `book/<book>/manifest.js`, реєструє `window.__BOOKS__.push({…})`:
```js
{ type:"book", slug, title,
  sections:[ { slug, title, scope,              // section = галузь предмета
    topics:[ { slug, title,
               status,                          // done | empty | update | deeper | recheck (§9)
               levels:["basic","detailed"],     // наявні версії статті
               hist:[ {file:"hist-<name>.md", status} ],   // вставки 📜 — масив на тип
               comp:[ {file:"comp-<name>.md", status} ],   // вставки 🔌
               math:[ {file:"math-<name>.md", status} ],   // вставки 🧮
               proj:[ {file:"proj-<name>.md", status} ] } ] } ] }   // вставки ⚙️
```
**catalog** — `catalog/<book>/manifest.js`, **та сама схема** з `type:"catalog"` (без масиву `comp`).

**guide** — `guide/<course>/manifest.js`, реєструє `window.__GUIDES__.push({…})`:
```js
{ type:"guide", slug, title,
  modules:[ { n, slug, title,
    chapters:[ { title,
      steps:[ { ref:"<книга>/<галузь>/<slug>", title }   // крок-посилання на book-статтю (3 сегменти)
            | { bridge, slug, title } ] } ] } ]          // власна тема курсу (синтез)
}
```
Поля: `scope` — межа галузі; `status` — enum §9, є **в кожної статті й кожної вставки**; `levels` — наявні версії (§3); масиви `hist`/`comp`/`math`/`proj` — вставки за типом, елемент = `{file, status}`. Увага: `ref` у guide має **галузь** (3 сегменти) — на відміну від `book:`-лінка §6, де галузь не потрібна. *(`origin` у мігрованих темах — лише слід старого розташування, для нових тем не потрібен.)*

## §3 Версії та вставки

**Дві версії повноти** (повнота — у назві файлу):
- **`<slug>.md` — базова.** Проста, щоб **швидко засвоїти тему й іти далі**; суть без надмірних деталей. **1000–3500 слів.**
- **`<slug>-d.md` — детальна.** Глибоко, **щоб зрозуміти максимально, без дір** — але так само просто подане. **2500–13000 слів.**

Різниця — у **глибині думки й обсязі**; кількість слів — від складності теми. **Яка версія існує — диктує `guide`** (потреба курсу): лише базова, лише детальна або обидві. Маніфест: `levels:["basic"]` / `["detailed"]` / `["basic","detailed"]`.

**Вставки — підтеми, окремі `.md` у теці теми**, чотири типи за префіксом `<type>-<name>.md` (у `catalog/` — без `comp`):
- 📜 `hist-` — **історія**: як народилося поняття (що бентежило, хто, суперечки); завжди справжня.
- 🔌 `comp-` — **компонент**: клас пристрою/мікросхеми — розпіновка, підключення, граблі.
- 🧮 `math-` — **математика**: апарат за темою (означення → інтуїція → формули), ЧОМУ від першопричини.
- ⚙️ `proj-` — **алгоритм/код**: задача → ідея → робочий C/C++ → пастки.

**Обсяг вставки — 1000–10000 слів** за насиченістю; матеріалу дуже багато — **розділити на кілька**. Реєстр у маніфесті — **окремо за типом**. Кожна вставка **несе вагу** (переказ чи банальність не вставляємо).

**Структура вставки для парсера:** файл починається із **заголовка H1** (`# Назва`, можна з емодзі `# 📜 Назва`) — рушій бере його як заголовок попапу. Вставка **зареєстрована в маніфесті** (масив свого типу, §2) і **згадана в тексті** ref-вставкою (§6). Вставка **не містить зворотних навігаційних карток** («🔗 Тема, до якої…», «▶️ До теми» тощо) — її відкривають попапом із теми, тож зворотне посилання зайве; інлайн-лінки на інші теми в тілі тексту — можна. Якщо повернення справді несе зміст — оформлюй його як **звичайну вставку**, не як картку-навігацію.

## §4 Ядро письма

**Метод (Фейнман — глибоко, від першопричин).**
- Спершу **інтуїція й «ЧОМУ»**, тоді деталі. Мотивацію даємо, **якщо є бодай легка потреба**; пропускаємо лише там, де її **точно немає**.
- Мета мотивації (й історії, якщо є): **коротко й цікаво показати реальну причину**, чому це почали робити — щоб читач побачив справжню суть.
- Висновок **будуємо на очах у читача**, не оголошуємо готовим.
- Аналогії **точні** — і показуємо, **де вони ламаються**.
- Виклад — **причинно-наслідкові ланцюжки** «A → тому B → звідси C», не списки; пастки й граничні випадки — з механізмом.
- Жодних переказів і зведень — кожна одиниця несе **нову думку**.

**Плавність (одразу, не окремим проходом).**
- Кожен абзац — **місток від попереднього** («з'ясували X — постає Y»).
- Наскрізна нитка: **навіщо → інтуїція → деталі → приклад**.
- Перед завершенням файлу **перечитати суцільно** і згладити стики.
- Тест нитки: переставив абзаци й нічого не зламалося — це купа, переписати.

**Жива українська (доступність + першоджерело).**
- Доступно, **як добрий лектор**: зрозуміло, але **без зверхності** — не «як малюкам». Поважаємо інтелект читача (без пафосу «відчуй це!»).
- Лише **справжні слова** — без вигаданих/перекручених/калькованих; без русизмів, канцеляриту, недоречних англіцизмів, випадкової синонімії. **Один термін на поняття** в межах файла.
- **Першоджерело назви:** уводячи нове поняття, у дужках дати мову-джерело й корінь — латину/грецьку (або англ., якщо звідти): «атом (гр. *átomos* — неподільний)», «напруга (лат. *tensio*)». Для **всіх** книг.
- Тест речення: прочитай подумки вголос — **якщо жива людина так не скаже, переформулюй**.

## §5 Формули, приклади, фігури

**Формули.** **БЕЗ LaTeX** (рендер не показує) — Unicode в тексті: `10⁻⁹, ε, ≈, ×, ·, ², ₀, Δ, σ, ω, →, ⇄`. Покрокові обчислення й ключові формули — у **моноширинних код-блоках**, вирівняних по `=`. Роздільник — **крапка** (`3.3`). Формул рівно скільки треба; є формула — нею **користуються**.

**Worked-приклад.** **Жирний підпис-умова** → код-блок із **покроковим обчисленням** → висновок. Код у прикладі — реальний **C/C++** (прошивка), короткий і коректний, **не псевдокод**.

**Фігури.**
- Тільки **SVG**, **чистий Python без залежностей** (без matplotlib); генератор `figs.py` **у теці теми**, вивід у `./img/`.
- `svgkit` зі `scripts/` **імпортувати, не переписувати**; рамку з текстом — **лише** через `textbox()/fitbox()`.
- **Кожна фігура несе вагу** (нетривіальна ідея, яку важко передати словами); банальних прикрас — краще жодної.
- Посилання на фігуру — **шлях від кореня репо** (з `/`): `![опис](/book/<книга>/<галузь>/<slug>/img/<file>.svg)`. **Імені файлу й номерів у тексті немає.**
- **Підпис — звичайний опис** (що показано і висновок), **без номера й без «Рис.»**, курсивом наступним рядком.
- Після генерації — `scripts/svgcheck.py`; виправляти позначене, доки «із зауваженнями: 0».

**Практичність.** Біля важливого поняття — рамка `> 🔧 **Навіщо це.**`: для чого воно в реальній розробці, **на матеріалі цієї теми**.

## §6 Крос-посилання й попапи

**Лінкуємо лише справжні залежності** — не кожну згадку (інакше ліс гіперпосилань). Тільки там, де стаття **точно потребує**, щоб читач знав іншу.

Оформлення — **ref-вставка**: короткий конспект **1–7 речень** «що саме треба знати» (лише те, без чого стаття не зрозуміла) + ref-лінк, що відкриває **попап**. Усю ціль **не переписуй**. Ціль ref-вставки:
- **інша стаття** — `book:<книга>/<slug>` (базова) / `book:<книга>/<slug>/<slug>-d.md` (детальна);
- **вставка цієї теми** — `book:<книга>/<slug>/<type>-<name>.md`.

Галузь у шляху не потрібна. Посилання — на **конкретну версію**; підстановку наявної й примітку «бракує/очікується» робить **рендер**, не автор. **Якщо ref вимагає детальну версію (`<slug>-d.md`), а в цілі існує лише базова — цільову тему познач у маніфесті `deeper`** (треба написати детальну); сам лінк лишається на детальну версію.

**Цілі ще нема — створюємо й ref-имо заздалегідь** (стаття чи вставка):
1. Визнач **правильне місце** (стаття — книга+галузь; вставка — тека теми).
2. Створи **порожній файл** (md або `<type>-<name>.md`).
3. Зареєструй у маніфесті зі статусом **`empty`**.
4. Постав ref — попап покаже стаб, **підтягне текст** по заповненні.

Де є справжня залежність — **жодних висячих згадок без ref**.

## §7 Історичні факти й атрибуція

- Будь-яке історичне/фактичне твердження (дата, ім'я, «хто перший», винахід, патент, походження) — **лише за перевіреними даними** (веб-перевірка). Історія завжди **справжня**; легенди позначати легендами.
- **Розрізняти виміри ідентичності**: етнічність / громадянство / місце народження / мова / інституція / імперська приналежність. Не клеїти «російське», коли джерела дають точніше (українець, поляк, серб, єврей, грузин, вірменин, балт…); змішане чи непевне — **сказати прямо**.
- Пильнувати **імперське поглинання** (рос.-радянські наративи; фабрикації кампанії першості 1948–53 — куля Крякутного, велосипед Артамонова).
- Винаходи **колективні**: розрізняти ідею / теорію / робочу реалізацію / систему / патент; не приймати «ми перші подумали» без доказів (радіо — Тесла, Марконі, Попов, Герц, Лодж, Бозе).
- Завжди **позначати статус доказовості**: усталено · спірно · імперсько-національне обрамлення · правдоподібно-але-недоведено · міф.

## §8 Технічний голос і каталог

**Межа `book` ↔ `guide` ↔ `catalog`.**
- `book/`-статті — **узагальнені**: конкретну деталь/номер можна дати **лише як приклад-згадку з посиланням** (на `catalog/`/`comp-`), але **не будувати статтю на ній**.
- `guide/`-статті — **можуть базуватися на конкретних деталях/компонентах** (курс прикладний).
- Платформи, що є самим предметом вивчення (ESP32, ArduPilot), називати можна й у `book/`.

**Каталог.** Пишемо **вільно, без нав'язаного переліку секцій**. Орієнтир — **загальна модель**: опиши об'єкт так, щоб читач **упізнав його, зрозумів що він робить і як влаштований, як його використати/підключити й чого стерегтися**. Конкретні секції добираєш **сам під природу пристрою**; детальна версія **покриває все, потрібне, щоб реально з ним працювати**. Обсяг: базова — як §3; **детальна каталогу — до 25000 слів** (вища за стелю §3, бо буває треба); більше — **розбити на кілька частин**.

Спецправил за предметом/аудиторією в каноні немає — **як писати конкретну книгу диктує той, хто ставить задачу**.

## §9 Статуси, процес, гігієна

**Статуси (enum у маніфесті):** `done` · `empty` (не почато) · `update` (переписати) · `deeper` (поглибити; зокрема — на тему посилаються як на детальну `-d.md`, а є лише базова, §6) · `recheck` (передивитися за чинними правилами й привести у відповідність). Міняємо **прямо в маніфесті** одразу після правки.

**Процес.** Беремо **найперший** запис `empty`/`update`/`deeper`/`recheck`. **Одна тема = один хід** (текст + фігури + статус→`done`). Великий крок **делегуємо сабагенту** з повними шляхами; у головну loop-сесію — лише короткий звіт.

**Паралельність.** Маніфест **один на книгу/курс/каталог** → ізоляція **по книзі**: кілька `/loop` працюють паралельно, лише якщо кожен — у **своїй** книзі/курсі. Двох `/loop` на одну книгу **не запускати** (спільний маніфест → конфлікт). Працюй лише в маніфесті своєї книги.

**Гігієна.** **НЕ комітити** без прохання. Перейменування — **`git mv`**. Скрипти — універсальні, у `scripts/`. Перед бампом версій — `node --check` зміненого JS.
