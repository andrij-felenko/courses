# ⚙️ Лічильник у прошивці: рахуємо події й ділимо частоту без таймера

> 🔧 **Навіщо це.** Не на кожен лічильник потрібен апаратний блок. Коли подій небагато (натиски, оберти, імпульси давача), той самий [лічильник](topic:hw-digital/counters) живе як **звичайна змінна** в C: нарощуємо її на одиницю на кожній події, а при досягненні межі — скидаємо й діємо. Це і є toggle-тригер та mod-N, перекладені на код. Розберімо робочу реалізацію й пастки, на яких такий лічильник тихо ламається.

### Задача: порахувати оберти й поділити їх

Уявімо колесо з магнітом і давачем Голла: на кожен оберт давач дає один імпульс. Треба дві речі — **полічити всі оберти** (одометрія) і **раз на десять обертів** видати імпульс на світлодіод (поділ частоти подій). Перша задача — чистий лічильник подій, друга — лічильник за модулем 10. Обидві розв'язуються однією змінною.

Чому це взагалі лічильник, а не «просто код»? Бо структура та сама, що в залізі. Апаратний лічильник має три частини: розряди, що зберігають число, вхід, що його нарощує, і детектор, що ловить досягнення межі. У прошивці цим частинам відповідають змінна, інкремент і умова `if`. Зрозумівши цю відповідність, ви читатимете будь-який лічильник — апаратний чи програмний — як одну й ту саму машину, і легше помічатимете, де реалізація розходиться з ідеєю.

Імпульс від давача приходить як перехід рівня на вході (фронт), тож зручно повісити на нього **переривання** — функцію, яку процесор викликає сам, щойно фронт стався, не відриваючи головну програму. Уся «логіка лічильника» в ній — лише інкремент і перевірка межі; решта коду навіть не знає, що оберти лічаться. Саме ця непомітність робить програмний лічильник таким зручним: він працює «у фоні», як апаратний.

### Перша реалізація: інкремент і поділ за модулем

```c
#include <stdint.h>

#define DIV 10u                       // поділ: дія раз на DIV подій

volatile uint32_t revolutions = 0;    // усього обертів (лічильник подій)
volatile uint8_t  mod_cnt    = 0;     // лічильник за модулем (0..DIV-1)

// Викликається з переривання на фронті від давача Голла
void on_hall_pulse(void) {
    revolutions++;                    // лічильник подій: просто +1

    if (++mod_cnt >= DIV) {           // дорахували до межі —
        mod_cnt = 0;                  // скидаємось у 0 (mod-N по колу)
        LED_PIN ^= 1u;               // дія: перемкнути світлодіод (toggle у коді)
    }
}
```

Тут `revolutions` — N-розрядний лічильник, лише не з тригерів, а 32-бітний у пам'яті: рахує до 2³² і аж тоді переповнюється. `mod_cnt` — точний аналог апаратного mod-10: дорахував до 10, скинувся в 0. А `LED_PIN ^= 1u` робить рівно те, що toggle-тригер: перевертає біт, тож світлодіод міняє стан раз на 10 обертів, тобто блимає вдвічі повільніше — поділ частоти подій на 2·DIV.

### Перша пастка: дребезг контакту лічить «зайве»

Якщо імпульс дає не давач Голла, а **механічний** контакт (геркон, кнопка), реалізація вище порахує забагато. Механічний контакт при замиканні **дребезжить**: дві металеві пластинки, торкаючись, кілька разів відскакують, перш ніж ляжуть щільно. Для електрики це не один чистий фронт, а пачка з кількох швидких — за частки мілісекунди. Лічильник, що реагує на кожен фронт, побачить не один оберт, а п'ять-десять. Це класична пастка: число накручується «з повітря», і помітити її важко, бо інколи контакт лягає чисто й рахунок збігається, а інколи — ні.

Лікують це ще одним лічильником, тільки **часу**: щойно зарахували фронт, ми на короткий «глухий» проміжок (кілька мілісекунд) перестаємо приймати нові. Дребезг весь уміщається в цей проміжок і тому ігнорується, а наступний справжній оберт прийде набагато пізніше й буде зарахований. Відлік цього проміжку веде системний лічильник мілісекунд — той самий апаратний таймер, лише прочитаний з коду.

```c
#include <stdint.h>

#define DIV         10u
#define DEBOUNCE_MS 5u                // глухий проміжок після фронту

volatile uint32_t revolutions = 0;
volatile uint8_t  mod_cnt     = 0;

extern volatile uint32_t millis;      // системний лічильник мілісекунд

void on_hall_pulse(void) {
    static uint32_t last_ms = 0;
    uint32_t now = millis;

    if ((uint32_t)(now - last_ms) < DEBOUNCE_MS)
        return;                       // ще в «глухому» проміжку — це дребезг, ігноруємо
    last_ms = now;

    revolutions++;
    if (++mod_cnt >= DIV) {
        mod_cnt = 0;
        LED_PIN ^= 1u;
    }
}
```

Зверніть увагу на `(uint32_t)(now - last_ms)`: віднімання беззнакових **само** дає правильний результат навіть коли `millis` переповнився й «перескочив» через нуль — різниця лишається коректною завдяки арифметиці за модулем 2³². Це той самий принцип, що й у лічильника: переповнення не ламає різницю, бо все рахується по колу.

### Друга пастка: читання багатобайтного лічильника «розривається»

Головна змінна `revolutions` — 32-бітна, а переривання може оновити її **посеред** того, як головний код її читає. Корінь біди в тому, що для процесора «прочитати 32 біти» — не одна неподільна дія. На 8- чи 16-розрядному ядрі це кілька машинних інструкцій: спершу взяти молодші байти, тоді старші. Якщо переривання вклинилося якраз між ними й змінило число, головний код збере молодшу половину від нового значення й старшу — від попереднього. Вийде число, якого ніколи не існувало (так званий розрив, *tearing*). Прикро тут те, що збій рідкісний і випадковий: він трапляється, лише коли переривання влучає в крихітне вікно між інструкціями, тож у тестах усе працює, а в полі раз на тисячу читань вискакує дикий стрибок.

Тому довгий лічильник, що його пише переривання, читають **атомарно** — так, щоб переривання гарантовано не вклинилося. Найпростіший спосіб — на час самого читання коротко вимкнути переривання:

```c
uint32_t read_revolutions(void) {
    uint32_t v;
    uint32_t saved = irq_save();      // запам'ятати стан і вимкнути переривання
    v = revolutions;                  // атомарне читання: переривання не вклиниться
    irq_restore(saved);               // повернути як було
    return v;
}
```

`volatile` тут **обов'язковий**, але сам по собі **не рятує** від розриву. Його роль вужча, ніж часто думають: він лише забороняє компілятору тримати змінну в регістрі й змушує щоразу читати її з пам'яті — інакше оптимізатор, не бачачи, що змінну міняє переривання, міг би взагалі «запам'ятати» старе значення й не перечитувати. Та `volatile` нічого не каже про **неподільність** доступу: 32-бітне читання як було двома інструкціями, так і лишається. Атомарність дає саме коротке вимкнення переривань (або апаратна підтримка атомарного доступу, якщо ядро її має). Плутати ці дві речі — `volatile` проти атомарності — поширена й підступна помилка, бо код із `volatile` виглядає «правильним» і здебільшого працює, аж поки розрив не вистрелить.

### Третя пастка: переповнення лічильника подій

`uint32_t` переповнюється після 2³² ≈ 4.3 млрд подій. Для колеса це роки, та для швидкого імпульсного давача — лічені години. Коли лічильник дійшов до краю й «обнулився», наївне віднімання двох знятих значень дасть від'ємний стрибок — якщо тримати різницю в **знаковому** типі. Як і з `millis`, рятує беззнакова арифметика: `(uint32_t)(now_count - prev_count)` дає правильний приріст навіть через переповнення, бо рахунок іде по колу 2³². Це знову та сама ідея mod-N — лічильник завжди циклічний, головне читати його різницями, а не абсолютом.

### Коли програмного лічильника замало

Програмний лічильник добрий, поки події **нечасті**. Кожна з них коштує входу в переривання — процесор мусить зберегти, чим був зайнятий, виконати обробник і відновитися; це десятки тактів. Поки імпульси йдуть з частотою сотень чи тисяч за секунду, ця ціна непомітна. Та якщо вони сиплються сотнями тисяч чи мільйонами за секунду, процесор почне витрачати на самі переривання більше часу, ніж має, — і на корисну роботу його вже не лишиться, аж до повного захлинання.

Тоді лічбу віддають **апаратному** лічильнику-таймеру. Він рахує фронти сам, у залізі, на повній швидкості входу, без жодного переривання на кожен імпульс, а процесор лише зрідка — скажімо, раз на мілісекунду — зчитує накопичене число. Виходить розподіл праці: швидку, монотонну лічбу робить залізо, а рідке читання й розумні рішення — код. Межа проста й варта запам'ятовування: рідкі події рахуй змінною в коді; густий потік віддавай апаратному лічильнику, бо саме для цього він і існує. А всередині — що там, що там — той самий ланцюг розрядів, що нарощує число на одиницю.
