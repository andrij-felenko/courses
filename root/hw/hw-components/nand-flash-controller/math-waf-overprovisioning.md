# 🧮 Математична модель WAF та баланс резервної ємності

Коефіцієнт посилення запису (англ. *Write Amplification Factor*, WAF) — це ключова математична метрика ефективності функціонування твердотільного накопичувача. Вона визначає відношення між повним фізичним обсягом даних, записаних мікроконтролером у масив комірок кремнію NAND Flash, та корисним обсягом даних, відправлених операційною системою хоста:

```
WAF = W_flash ÷ W_host
```

В ідеальній системі без внутрішніх накладних витрат `WAF = 1.0`: кожен кілобайт даних від хоста записується у флеш-пам'ять рівно один раз. Проте через фізичну неможливість перезапису комірок на місці (Out-of-Place updates) та необхідність фонового збирання сміття (Garbage Collection, GC) реальне значення `WAF` завжди строго більше одиниці. 

У несприятливих умовах безперервного випадкового запису на переповнений накопичувач WAF може зростати до 10–20. Це означає, що накопичувач зношується у 10–20 разів швидше, а його реальна пропускна здатність падає пропорційно.

Розглянемо суворе аналітичне виведення WAF для стаціонарного стану та покажемо його залежність від коефіцієнта надлишкового резервування (англ. *Over-Provisioning*, OP), структури навантаження, евристик вибору блоків і команди TRIM.

---

### 1. Параметри базової моделі простору NAND

Введемо такі позначення для фізичних та логічних параметрів накопичувача:
* `T` — повна фізична ємність встановленого масиву NAND Flash (англ. *Total raw capacity*), виміряна в байтах або сторінках.
* `C` — доступна користувачеві корисна ємність накопичувача, яку бачить операційна система (англ. *User-visible capacity*).
* `OP` — коефіцієнт надлишкового резервування, що показує частку прихованого резерву відносно доступного простору:

```
OP = (T − C) ÷ C
   = T ÷ C − 1                     [поділили почленно чисельник на C]
```

Звідси повна фізична ємність виражається через користувацьку:

```
T = C · (1 + OP)
```

* `u` — середня частка дійсних (англ. *valid*) даних у всьому фізичному масиві NAND за умови 100% заповнення логічного простору `C`:

```
u = C ÷ T
```

Підставимо формулу повної ємності `T` у вираз для частки дійсних даних `u`:

```
u = C ÷ T
  = C ÷ (C · (1 + OP))             [підставили T = C · (1 + OP)]
  = 1 ÷ (1 + OP)                   [скоротили дріб на C]
```

Таким чином, частка недійсних сторінок («сміття» або застарілих даних, інвалідованих наступними перезаписами) у всьому масиві становить:

```
1 − u = 1 − 1 ÷ (1 + OP)
      = ((1 + OP) − 1) ÷ (1 + OP)  [звели до спільного знаменника]
      = OP ÷ (1 + OP)              [спростили чисельник]
```

### 2. Виведення WAF для рівномірного випадкового навантаження

Розглянемо накопичувач, що перебуває в стаціонарному стані (англ. *steady state*) під дією рівномірного потоку випадкових записів (Uniform Random Writes). Усі логічні адреси LBA оновлюються хостом з однаковою ймовірністю.

Нехай кожен фізичний блок NAND складається з `N` сторінок. У стаціонарному стані при виборі блоку для очищення за жадібним алгоритмом збирання сміття (Greedy GC):
1. Блок-жертва містить у середньому `u · N` дійсних сторінок і `(1 − u) · N` застарілих недійсних сторінок.
2. Контролер зчитує `u · N` дійсних сторінок і **копіює їх у новий активний відкритий блок**.
3. Блок-жертва повністю стирається.
4. У результаті очищення блоку розміром `N` сторінок контролер отримує можливість записати **лише `(1 − u) · N` нових сторінок від хоста**, оскільки решту місця `u · N` вже зайняли перенесені старі сторінки.

Підрахуємо сумарний фізичний запис у пам'ять `W_flash`, виконаний контролером для прийому `W_host = (1 − u) · N` сторінок від хоста:

```
W_flash = W_gc + W_host
        = (u · N) + ((1 − u) · N)   [додали перенесення GC та запис хоста]
        = N                         [розкрили дужки: u·N + N − u·N = N]
```

Тепер обчислимо коефіцієнт посилення запису WAF:

```
WAF = W_flash ÷ W_host
    = N ÷ ((1 − u) · N)            [підставили значення W_flash та W_host]
    = 1 ÷ (1 − u)                  [скоротили дріб на розмір блоку N]
```

Підставимо у знайдений вираз частку `u = 1 ÷ (1 + OP)`:

```
WAF = 1 ÷ (1 − u)
    = 1 ÷ (1 − 1 ÷ (1 + OP))       [підставили u = 1 / (1 + OP)]
    = 1 ÷ (((1 + OP) − 1) ÷ (1 + OP))  [привели знаменник до спільного дробу]
    = 1 ÷ (OP ÷ (1 + OP))          [відняли одиниці в чисельнику знаменника]
    = (1 + OP) ÷ OP                [перевернули триповерховий дріб]
    = 1 + 1 ÷ OP                   [поділили чисельник почленно на OP]
```

Формула `WAF = 1 + 1 ÷ OP` є класичним аналітичним рівнянням посилення запису для рівномірного випадкового доступу. Вона показує фундаментальну гіперболічну залежність: **при зменшенні резервування `OP` посилення запису стрімко зростає до нескінченності**.

### 3. Числовий розрахунок: порівняння промислових конфігурацій

Порівняємо поведінку трьох реальних накопичувачів, побудованих на однакових масивах сирої пам'яті `T = 1024 ГБ` (1 ТБ Flash).

**Випадок 1: Споживчий SSD початкового рівня (OP ≈ 7%)**
* Користувацька ємність: `C = 960 ГБ` (двійковий перерахунок $1024 / 960 - 1 \approx 0.067$).
* Обчислення коефіцієнта посилення:

```
WAF = 1 + 1 ÷ 0.067
    = 1 + 14.925                   [розділили 1 на 0.067]
    = 15.93                        [додали одиницю]
```

При безперервному випадковому перезаписі на повністю заповнений диск контролер виконує майже 16 фізичних записів на кожен 1 логічний запис хоста. Якщо ресурс TLC-комірок становить 3000 циклів P/E, реальний життєвий ресурс накопичувача впаде з теоретичних 2880 ТБ до всього 180 ТБ записаних даних (TBW).

**Випадок 2: Корпоративний SSD стандартної витривалості (OP = 28%)**
* Користувацька ємність: `C = 800 ГБ` (`OP = (1024 − 800) ÷ 800 = 0.28`).
* Обчислення коефіцієнта посилення:

```
WAF = 1 + 1 ÷ 0.28
    = 1 + 3.571                    [розділили 1 на 0.28]
    = 4.57                         [додали одиницю]
```

Збільшення резервування з 7% до 28% знижує WAF з 15.93 до 4.57 (падіння у 3.5 раза). Ресурс і стійка швидкість запису зростають у 3.5 раза.

**Випадок 3: Серверний SSD для екстремальних навантажень (OP = 100%)**
* Користувацька ємність: `C = 512 ГБ` (`OP = (1024 − 512) ÷ 512 = 1.0`).
* Обчислення коефіцієнта посилення:

```
WAF = 1 + 1 ÷ 1.0
    = 1 + 1.0                      [розділили 1 на 1]
    = 2.0                          [додали одиницю]
```

При 100% резервуванні WAF падає до 2.0. Контролер переносить лише одну сторінку фонових даних на одну нову сторінку користувача.

### 4. Марковська модель накопичення сміття (Модель Деснуайє)

У реальному накопичувачі частка дійсних сторінок не є абсолютно однаковою в кожному блоці: вона розподілена статистично. Згідно з марковською моделлю Пітера Деснуайє (англ. *Peter Desnoyers*), процес інвалідації сторінок у блоці описується дискретним ланцюгом Маркова.

Нехай у системі є `B` фізичних блоків. Ймовірність того, що черговий випадковий запис хоста потрапить у конкретний блок `i`, дорівнює:

```
p_hit = 1 ÷ B
```

Якщо блок містить `k` дійсних сторінок, ймовірність того, що наступний запис інвалідує одну з його сторінок, пропорційна числу живих даних у ньому:

```
P(k → k − 1) = k ÷ (C_pages)
```

де `C_pages` — загальна кількість логічних сторінок у системі.

Ця диференційна залежність показує важливий фізичний ефект: **чим більше дійсних сторінок містить блок, тим вища ймовірність, що наступний запис потрапить саме в нього й створить сміття**. Навпаки, коли в блоці залишається мало дійсних сторінок, швидкість накопичення сміття в ньому сповільнюється.

Жадібний алгоритм GC вибирає для очищення блок у нижньому хвості цього статистичного розподілу (з мінімальним `k`), де частка дійсних сторінок `u_victim` суттєво менша за середню по диску `u_avg`. Для великої кількості блоків емпірична апроксимація Деснуайє дає скориговану формулу WAF:

```
WAF_greedy ≈ 1 ÷ (2 · OP) + 0.5
```

Для `OP = 0.28` (28%) це дає:

```
WAF_greedy ≈ 1 ÷ (2 · 0.28) + 0.5
           = 1 ÷ 0.56 + 0.5        [перемножили знаменник]
           = 1.785 + 0.5           [розділили 1 на 0.56]
           = 2.29                  [додали 0.5]
```

Це пояснює, чому реальні контролери з ефективними евристиками GC демонструють WAF відчутно кращий, ніж дає найпростіша рівномірна модель.

### 5. Послідовне навантаження проти випадкового (Модель злиття потоків)

Абсолютно інша математична картина спостерігається при послідовному записі великих файлів (Sequential Writes). 

Коли операційна система записує неперервний потік даних (наприклад, відеофайл розміром 10 ГБ), контролер FTL послідовно заповнює фізичні блоки один за одним від нульової до останньої сторінки:
* Усі сторінки в блоці належать суміжним LBA одного файлу.
* Якщо користувач згодом видаляє цей файл або повністю переписує його новим вмістом, **всі сторінки фізичного блоку інвалідуються одночасно**.
* Частка дійсних даних у такому блоці падає до нуля: `u_seq = 0`.

Підставимо `u = 0` у базову формулу посилення:

```
WAF_seq = 1 ÷ (1 − u_seq)
        = 1 ÷ (1 − 0)              [підставили u = 0]
        = 1.0                      [розділили 1 на 1]
```

При чисто послідовному записі стирання блоку не вимагає перенесення жодної сторінки (нульові накладні витрати міграції), тому `WAF = 1.0` незалежно від встановленого коефіцієнта Over-Provisioning.

### 6. Вплив буферизації та злиття записів у DRAM (Write Coalescing)

Важливим апаратним фактором зниження WAF на практиці є кешування записів у внутрішній оперативній пам'яті DRAM/SRAM контролера.

Коли операційна система надсилає багаторазові дрібні оновлення одного й того самого 4-кілобайтного сектора (наприклад, лічильник транзакцій у заголовку журналу СУБД):
* Якщо запис одразу скидається у флеш-пам'ять, кожна модифікація витрачає одну фізичну сторінку NAND, створюючи лавину сміття.
* За наявності буфера **Write Coalescing** контролер акумулює зміни в DRAM. Якщо той самий логічний сектор оновлюється `M` разів підряд, контролер скидає у флеш лише фінальну версію даних після заповнення буфера.

Математичне зменшення WAF завдяки злиттю `M` оновлень виражається множником:

```
WAF_buffered = WAF_raw ÷ M
```

Якщо гарячий сектор бази даних перезаписується в кеші 10 разів перед збереженням у NAND (`M = 10`), ефективний WAF для цього потоку падає в 10 разів, істотно розвантажуючи збирання сміття.

### 7. Модель неоднорідного навантаження (Hot / Cold Data Separation)

У реальних операційних системах звернення до накопичувача майже ніколи не бувають рівномірними. Відповідно до емпіричної моделі розподілу звернень (правило Парето або біпартитна модель Деснуайє):
* Частка `α` (наприклад, 80% = 0.8) усіх операцій запису спрямовується у вузький діапазон «гарячих» даних (англ. *Hot Data*: логи, тимчасові файли, індекси баз даних).
* Гарячі дані займають лише частку `β` (наприклад, 20% = 0.2) від усього логічного простору `C`.
* Решта `1 − α` (20%) записів припадає на великий масив «холодних» даних (англ. *Cold Data*: бінарні файли програм, медіа, архіви), що займають `1 − β` (80%) простору.

Якщо контролер FTL здатний динамічно класифікувати потоки й записувати гарячі та холодні дані в **різні фізичні блоки**:

1. **Блоки гарячих даних:** оскільки невеликий обсяг адрес постійно перезаписується з високою частотою, сторінки в цих блоках інвалідуються лавиноподібно. На момент запуску GC блок-жертва містить понад 90–95% недійсних сторінок (`u_hot ≈ 0.05..0.10`). Посилення запису для гарячої зони становить:

```
WAF_hot = 1 ÷ (1 − u_hot)
        = 1 ÷ (1 − 0.05)           [підставили u_hot = 0.05]
        = 1 ÷ 0.95                 [відняли частку дійсних сторінок]
        = 1.05                     [розділили 1 на 0.95]
```

2. **Блоки холодних даних:** ці блоки заповнені майже на 100% дійсними сторінками, які ніколи не перезаписуються хостом. Контролер взагалі не бере їх на збирання сміття, уникаючи безглуздого переписування незмінних файлів.

Сумарний зважений коефіцієнт посилення для системи з розділенням даних:

```
WAF_total = α · WAF_hot + (1 − α) · WAF_cold
          = 0.8 · 1.05 + 0.2 · 1.00 [підставили вагові коефіцієнти]
          = 0.84 + 0.20             [перемножили доданки]
          = 1.04                    [додали результати]
```

Розділення гарячих і холодних потоків у поєднанні зі статистичним аналізом адрес знижує WAF із теоретичних 15.9 до вражаючих 1.05–1.2 навіть на споживчих SSD.

### 8. Порівняння евристик GC: Greedy проти Cost-Benefit

Вибір блоку-жертви є оптимізаційною задачею. Класичний жадібний підхід (Greedy) оцінює виключно миттєву вигоду (кількість вільного місця, що звільниться після стирання). Проте при змішаному навантаженні жадібний алгоритм припускається помилки: він може вибрати «холодний» блок, де випадково утворилося трохи сміття, перенести його дорогі дані, а потім цей блок знову роками не буде модифікуватися.

Алгоритм Розенблюма-Оустерхаута **Cost-Benefit** враховує вік блоку (англ. *age* — час, що минув з моменту останньої модифікації будь-якої сторінки в блоці):

```
Функція корисності U = (Користь) ÷ (Витрати)
                    = ((1 − u) · age) ÷ (1 + u)
```

де:
* `1 − u` — обсяг простору, який звільниться (вигода);
* `1 + u` — сумарні витрати на зчитування та переписування дійсних сторінок (1 читання блоку + `u` записів сторінок);
* `age` — час спокою блоку.

Множник `age` надає перевагу старим блокам: якщо «холодний» блок пролежав тривалий час і в ньому накопичилося навіть небагато сміття, його вигідно очистити зараз, оскільки дані в ньому стабільні. Навпаки, для «молодого» гарячого блоку алгоритм відкладає очищення, даючи хосту час самостійно інвалідувати решту його сторінок без зайвих перенесень.

### 9. Вплив команди TRIM на ефективне резервування

Коли файлова система видаляє файл, на звичайному накопичувачі без підтримки TRIM контролер продовжує вважати ці сектори зайнятими (оскільки вони не були перезаписані).

Команда **TRIM** (в NVMe — *Dataset Management / Deallocate*) повідомляє FTL, що певні діапазони LBA стали вільними. Нехай частка вільного місця у файловій системі становить `f` (наприклад, диск заповнений лише наполовину, `f = 0.5`).

Ефективна користувацька ємність дійсних даних падає до:

```
C_eff = C · (1 − f)
```

Відповідно, ефективне надлишкове резервування `OP_eff` зростає:

```
OP_eff = (T − C_eff) ÷ C_eff
       = (T − C · (1 − f)) ÷ (C · (1 − f))
```

Підставимо `T = C · (1 + OP)` у формулу ефективного резерву:

```
OP_eff = (C · (1 + OP) − C · (1 − f)) ÷ (C · (1 − f))
       = (C · ((1 + OP) − (1 − f))) ÷ (C · (1 − f))   [винесли C за дужки]
       = ((1 + OP) − 1 + f) ÷ (1 − f)                 [скоротили дріб на C]
       = (OP + f) ÷ (1 − f)                           [спростили чисельник]
```

**Приклад розрахунку з TRIM для споживчого SSD (OP = 0.07, диск заповнений на 50%, тобто f = 0.5):**

```
OP_eff = (0.07 + 0.5) ÷ (1 − 0.5)
       = 0.57 ÷ 0.5                 [додали доданки в чисельнику]
       = 1.14                       [розділили 0.57 на 0.5]
```

Розрахуємо новий ефективний WAF для випадкового запису:

```
WAF_eff = 1 + 1 ÷ OP_eff
        = 1 + 1 ÷ 1.14              [підставили OP_eff = 1.14]
        = 1 + 0.877                 [розділили 1 на 1.14]
        = 1.88                      [додали одиницю]
```

Команда TRIM, своєчасно звільняючи невикористаний простір, знижує WAF із 15.93 до 1.88 навіть при найжорсткішому випадковому навантаженні.

### 10. Розрахунок життєвого ресурсу накопичувача (TBW)

Значення WAF має прямий лінійний вплив на показник гарантованого обсягу запису (англ. *Total Bytes Written*, TBW), який виробники зазначають у гарантійних зобов'язаннях:

```
TBW = (C · PE_Cycles) ÷ WAF
```

де:
* `C` — корисна ємність накопичувача;
* `PE_Cycles` — паспортний ресурс комірок флеш-пам'яті (наприклад, 3000 циклів для 3D TLC).

**Порівняльний приклад для накопичувача ємністю 1 ТБ з TLC NAND (3000 циклів P/E):**
* При несприятливому навантаженні без TRIM (`WAF = 10.0`):

```
TBW = (1 ТБ · 3000) ÷ 10.0
    = 3000 ТБ ÷ 10.0               [перемножили ємність на ресурс]
    = 300 ТБ                       [розділили на WAF]
```

* При оптимізованому навантаженні з розділенням даних та TRIM (`WAF = 1.2`):

```
TBW = (1 ТБ · 3000) ÷ 1.2
    = 3000 ТБ ÷ 1.2                [перемножили ємність на ресурс]
    = 2500 ТБ                      [розділили на WAF]
```

### 11. Економічна оптимізація вартості володіння (TCO)

У корпоративних центрах обробки даних вибір коефіцієнта Over-Provisioning є прямою економічною оптимізацією сукупної вартості володіння (англ. *Total Cost of Ownership*, TCO).

Собівартість одного терабайта гарантованого запису (англ. *Cost per TBW*) обчислюється як:

```
Cost_per_TBW = (Ціна_накопичувача) ÷ TBW
             = (Cost_raw · (1 + OP)) ÷ ((C · PE_Cycles) ÷ WAF)  [підставили вирази для ціни та TBW]
             = (Cost_raw · (1 + OP) · WAF) ÷ (C · PE_Cycles)    [перенесли WAF у чисельник]
```

де `Cost_raw` — собівартість встановленого кремнію NAND.

Оскільки множник `1 + OP` лінійно зростає зі збільшенням апаратного резерву, а коефіцієнт `WAF(OP) = 1 + 1/OP` гіперболічно спадає, функція `Cost_per_TBW(OP)` має чітко виражений глобальний мінімум. Для змішаних баз даних OLTP (з відношенням читання/запис 70/30) мінімум питомої вартості запису припадає на діапазон `OP = 28%..33%`, що пояснює домінування саме таких конфігурацій (наприклад, накопичувачі на 3.2 ТБ та 6.4 ТБ замість споживчих 4.0 ТБ та 8.0 ТБ) у корпоративному серверному сегменті.
