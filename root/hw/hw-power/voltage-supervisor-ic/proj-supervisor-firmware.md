# ⚙️ Програмне обслуговування супервізора напруги та віконного сторожового таймера

Апаратний супервізор напруги та зовнішній сторожовий таймер забезпечують фізичний захист мікроконтролера, проте повноцінна відмовостійкість системи досягається лише за умови правильної програмної інтеграції. Прошивка повинна вирішувати дві взаємопов'язані задачі: коректно обробляти сигнал раннього попередження про зникнення живлення (Power-Fail Interrupt) для збереження критичних даних в енергонезалежну пам'ять, а також своєчасно обслуговувати віконний сторож (Windowed Watchdog), підтверджуючи працездатність усіх критичних потоків виконання без ризику хибного апаратного перезавантаження.

### Анатомія програмних збоїв та пастки обслуговування сторожа

У складних вбудованих системах під керуванням операційних систем реального часу (FreeRTOS, Zephyr, RT-Thread) або багаторівневих суперциклів збої програмного забезпечення рідко виглядають як повна апаратна зупинка процесора. На практиці найнебезпечнішими є часткові зависання, коли процесор продовжує тактуватися, але ключові алгоритми керування втрачають працездатність:

1. **Взаємне блокування потоків (Deadlock):**
   Дві або більше задач блокують спільні м'ютекси або семафори у взаємно протилежному порядку. Потоки керування приводами чи сенсорами назавжди зависають у чергах очікування, хоча переривання системного таймера (SysTick) продовжують справно викликатися на кожному такті.
2. **Інверсія та голодування пріоритетів (Priority Inversion & Starvation):**
   Низькопріоритетна задача захоплює ресурс і витісняється задачею середнього пріоритету, блокуючи критичну високопріоритетну задачу безпеки на час, що перевищує допустимі межі реального часу.
3. **Виродження циклу в порожній стан (Infinite Loop):**
   Вказівник інструкцій через пошкодження адреси повернення в стеку (Stack Overflow / Buffer Overflow) потрапляє в цикл опитування апаратного прапорця периферії, яка зависла через апаратний збій на шині I2C або SPI.
4. **Зациклення швидких переривань (ISR Storm):**
   Джерело зовнішнього переривання (наприклад, оптичний енкодер або мережевий контролер) через заваду переходить у стан неперервної генерації імпульсів. Обробник переривання займає 100% часу ядра, не даючи жодного кванту часу фоновим задачам.

Якщо інженер реалізує обслуговування сторожового таймера наївно — наприклад, скидає вивід `WDI` всередині системного переривання `SysTick_Handler()` або у фоновій задачі `Idle Task`, — сторожовий таймер стає абсолютно марним. Переривання `SysTick` буде успішно скидати апаратний таймер навіть тоді, коли вся система керування перебуває у стані мертвого блокування, а аварійний двигун продовжує некеровано обертатися.

### Архітектура детектора зникнення живлення (PFI/PFO)

Багатоканальні супервізори містять додатковий нескомпенсований компаратор раннього попередження (Power-Fail Comparator). Його вхід `PFI` підключають до вхідної нестабілізованої шини (наприклад, 12 В або 5 В до LDO), а вихід `PFO` підтягують до лінії зовнішнього переривання процесора (EXTI).

```
   Вхідна напруга 12 В
          │
      ┌───┴───┐
      │ Діод  │
      └───┬───┘
          ├───────────────┬────────────────────────┐
          │               │                        │
       [R_div1]     [C_резервний]            ┌─────┴─────┐
          │            2200 мкФ              │    LDO    │
         PFI                                 └─────┬─────┘
          │                                        │ 3.3 В
       [R_div2]                                    ├───────────► MCU VDD
          │                                        │
         GND                                ┌──────┴──────┐
                                            │ Супервізор  │
                                            └──────┬──────┘
                                                  PFO (Переривання EXTI) ──► MCU
```

#### Розрахунок часу утримання енергії (Hold-up Time)
Коли зовнішня мережа вимикається, напруга до діода падає до нуля. Розділовий діод блокує зворотний струм, тому вся енергія, накопичена в резервному конденсаторі `C_резервний`, живить виключно внутрішній стабілізатор мікроконтролера.

Час, протягом якого напруга на конденсаторі спадає від порогу спрацьовування компаратора `V_pfi` (наприклад, 9.0 В) до мінімальної робочої напруги стабілізатора `V_reg_drop` (наприклад, 4.5 В для отримання 3.3 В), визначається зарядом конденсатора та споживаним струмом:

```
t_holdup = C_резервний · (V_pfi − V_reg_drop) / I_load
```

Якщо `C_резервний = 1000 мкФ`, а активний струм навантаження плати під час повної роботи становить `I_load = 200 мА`, час утримання становитиме лише:

```
t_holdup = 1000·10⁻⁶ · (9.0 − 4.5) / 0.200 = 4.5·10⁻³ / 0.200 = 0.0225 с = 22.5 мс
```

Якщо ж у перші мікросекунди переривання прошивка апаратно вимикає потужні навантажувачі (дисплей, радіоканал, реле), знижуючи струм до `I_sleep = 10 мА`, час утримання зростає до сотень мілісекунд, що дає гарантований запас часу на збереження сотень кілобайт журналу.

#### Послідовність дій усередині обробника переривання PFI
1. **Апаратне знеструмлення навантаження:** негайно перевести вивід `Power-Gate GPIO` у низький рівень, відсікаючи живлення підсвічування, драйверів двигунів та бездротових трансиверів.
2. **Блокування планувальника та звичайних переривань:** заборонити виконання непривілейованих задач, які можуть спробувати виконати довгі транзакції запису до повільної Flash-пам'яті.
3. **Розрахунок контрольної суми:** обчислити CRC-32 поточного стану критичних змінних (лічильники мотогодин, позиції приводів, калібрувальні коефіцієнти, журнали помилок).
4. **Енергонезалежний запис:** виконати пакетний запис у швидку енергонезалежну пам'ять FRAM (час запису одного байта менше 100 нс без затримок стирання) або виділену сторінку EEPROM.
5. **Фіксація безпечного стану:** записати сигнатурне магічне число `0xDEADBEEF`, що підтверджує коректність завершення аварійного збереження, і перевести мікроконтролер у режим `Sleep / WFI`, очікуючи остаточного падіння напруги та апаратного скидання від супервізора.

### Шаблон контрольних точок (Task Checkpoint Pattern) для WWDT

Для усунення проблеми «сліпого скидання сторожа» застосовують шаблон контрольних точок із бітовою маскою працездатності:

1. **Реєстрація задач:** кожній критичній задачі системи присвоюється унікальний бітовий прапорець у 32-бітному атомарному реєстрі `s_health_flags`:
   - Задача опитування сенсорів: `TASK_SENSOR_BIT = (1 << 0)`.
   - Задача контуру цифрового регулювання: `TASK_CONTROL_BIT = (1 << 1)`.
   - Задача мережевого протоколу: `TASK_COMMS_BIT = (1 << 2)`.
2. **Звітування про проходження циклу:** у кінці кожної успішної ітерації основного циклу задача виставляє свій бітовий прапорець у реєстрі. Якщо задача заблокована на м'ютексі або зависла у внутрішньому циклі, вона не доходить до кінця ітерації, і її біт залишається нульовим.
3. **Диспетчеризація сторожа:** окрема високопріоритетна задача-наглядач або функція в таймерному циклі прокидається з фіксованим періодом, що відповідає центру дозволеного вікна супервізора.
4. **Перевірка маски та генерація імпульсу:**
   - Наглядач перевіряє, чи всі обов'язкові біти встановлені в `1`.
   - Якщо всі біти на місці, наглядач атомарно скидає весь регістр прапорців у `0` і формує перепад на виводі `WDI`.
   - Якщо хоча б один біт відсутній (наприклад, задача зв'язку зависла), наглядач **навмисно припиняє обслуговування сторожа**. Протягом наступних кількох десятків мілісекунд супервізор зафіксує таймаут відсутності імпульсу `WDI` і виконає чисте апаратне перезавантаження всієї мікросхеми.

### Енергонезалежний «чорний ящик» збоїв (Crash Telemetry Recorder)

Коли задача-наглядач фіксує пропуск контрольної точки іншим потоком, вона виконує екстрений знімок діагностичних параметрів системи безпосередньо перед зупинкою обслуговування сторожа:

```
[ Виявлено зависання задачі ]
             │
   [ Збір діагностики ]
   ├─ Вказівник стека (SP) та адреса збою (PC / LR)
   ├─ Залишок стека задач (FreeRTOS High Water Mark)
   ├─ Маска прапорців здоров'я (s_health_flags)
   └─ Лічильник системного часу (SysTick)
             │
   [ Запис у RTC Backup RAM або SPI FRAM ]
             │
   [ Заборона WDI ] ──► Очікування апаратного рестарту від супервізора
```

Структура даних знімка зберігається у спеціальному енергонезалежному домені живлення (RTC Backup Domain), який живиться від батарейки й не стирається при апаратному скиданні лінії `/RESET`. Під час наступного завантаження діагностичний модуль зчитує ці дані та передає повний звіт розробникам через телеметричний канал зв'язку (CAN / LTE).

### Багатоядерна синхронізація та бар'єри пам'яті

У сучасних багатоядерних системах (наприклад, ESP32 із двома ядрами Xtensa або STM32H7 із ядрами Cortex-M7 та Cortex-M4) обслуговування єдиного зовнішнього виводу `WDI` вимагає суворої між'ядерної синхронізації (Inter-Core Synchronization):

1. **Міжпроцесорні бар'єри (Memory Barriers):**
   При оновленні прапорців працездатності між різними ядрами необхідно використовувати апаратні бар'єри пам'яті (`__DMB()`, `__DSB()` в архітектурі ARM або `std::atomic_thread_fence(std::memory_order_seq_cst)` у С++). Це запобігає перевпорядкуванню інструкцій оптимізуючим компілятором та кеш-пам'яттю процесора.
2. **Розподілена маска підтвердження:**
   Ядро 0 (відповідальне за бездротовий зв'язок та інтерфейси) формує молодші 16 бітів маски працездатності, а Ядро 1 (відповідальне за критичні математичні розрахунки контуру керування) — старші 16 бітів. Лише тоді, коли обидва ядра виставили всі 32 біти, генерується імпульс на вивід `WDI`. Якщо одне з ядер зависає у стані HardFault, уся система безпечно йде на перезавантаження.

### Управління сторожем у режимах глибокого сну (Deep Sleep / Tickless Idle)

В автономних батарейних пристроях мікроконтролер 99% часу проводить у режимі глибокого сну з вимкненим тактуванням ядра. Якщо зовнішній сторожовий таймер активний, звичайний сон тривалістю понад 1.6 с викличе фальшиве апаратне перезавантаження.

Для вирішення цієї суперечності застосовують одну з трьох інженерних стратегій:

1. **Апаратне стробування сторожа (WDT Enable Gating):**
   Використання супервізорів із входом дозволу `/ENABLE` або `WDT_DIS`. Перед переходом у глибокий сон мікроконтролер виставляє сигнал блокування сторожа через спеціальний вивід GPIO, який утримує свій стан під час сну (Hold Latched Pin).
2. **Періодичні пробудження за таймером RTC (Tickless Periodic Kick):**
   Низькоспоживаючий внутрішній таймер реального часу RTC налаштовують на пробудження мікроконтролера кожні 800 мс (за таймауту сторожа 1.6 с). Ядро прокидається на 50 мкс, генерує імпульс `WDI` і негайно засинає знову, що зберігає середній струм споживання на рівні менше 10 мкА.
3. **Динамічне перемикання часозадавального конденсатора:**
   Підключення додаткового конденсатора паралельно виводу `CT` через малий польовий транзистор перед сном, що збільшує таймаут сторожа з 1 секунди до кількох годин.

### Обслуговування сторожа під час оновлення прошивки «по повітрю» (FOTA / IAP)

Оновлення програмного забезпечення в польових умовах (Firmware Over-The-Air, FOTA) або через завантажувач (In-Application Programming, IAP) створює критичний конфлікт таймінгів:

1. **Тривале блокування ядра при стиранні Flash-пам'яті:**
   Апаратне стирання одного сектора або банку Flash-пам'яті (Flash Sector Erase) триває від 20 до 200 мс, а повне стирання масиву (Mass Erase) — до 2–5 секунд. Під час операцій стирання ядро мікроконтролера повністю блокується на шині Flash (Stall state) або виконує цикл очікування з вимкненими перериваннями.
2. **Уникнення фальшивого рестарту:**
   Якщо таймаут зовнішнього сторожа становить 100 мс, стирання блоку призведе до апаратного скидання в момент відкритого запису. В результаті пам'ять пошкоджується, а прилад перетворюється на невідновлювану «цеглину».
3. **Алгоритм гранулярного стирання та чергування імпульсів:**
   - Завантажувач виконує стирання Flash строго малими порціями (посторінково або посекторно).
   - Між стираннями кожного сектора завантажувач примусово генерує імпульс `WDI` всередині дозволеного часового вікна супервізора.
   - Якщо супервізор має апаратний вивід відключення сторожа (`WDT_DIS`), завантажувач блокує сторож лише на час верифікації контрольної суми повного образу нової прошивки.

### Повний часовий цикл обробки аварійного скидання та відновлення

Для наочності розглянемо повний наскрізний ланцюг подій під час реального аварійного просідання живлення та подальшого холодного пуску системи:

```
[ Подія 0: Зникнення мережі ]
         │ (Напруга на вході 12 В падає нижче 9.0 В)
         ▼
[ Подія 1: Переривання PFO ] ──► MCU знеструмлює навантаження, пише FRAM (Hold-up time 20 мс)
         │ (Напруга на VDD процесора падає нижче 2.93 В)
         ▼
[ Подія 2: Спрацьовування супервізора ] ──► Вихід /RESET примусово падає в 0 В (MCU зупинено)
         │ (Шина VDD сповзає до 0.5 В і повертається після відновлення мережі)
         ▼
[ Подія 3: Перетин порогу V_IT+ ] ──► Живлення перевищує 3.0 В, супервізор запускає таймер t_rst
         │ (Пауза t_rst = 150 мс: стабілізація живлення та кварцу 16 МГц)
         ▼
[ Подія 4: Відпускання /RESET ] ──► Лінія переходить у "1", процесор починає виконання Reset Handler
         │
         ▼
[ Подія 5: Аналіз прапорців ] ──► Прошивка читає RCC_CSR, відновлює робочий стан із FRAM
```

### Аналіз причин перезавантаження (Boot-Up Reset Reason Analysis)

Після кожного старту прошивка зобов'язана з'ясувати фізичну причину скидання ядра шляхом зчитування апаратних прапорців у системних контролерах мікроконтролера (наприклад, `RCC_CSR` в STM32 або функція `esp_reset_reason()` в ESP-IDF):

```
       Старт процесора (Reset Handler)
                     │
         [ Читання регістру прапорців ]
                     │
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
  POR / PDR      BOR / SVS     WDT Timeout
(Холодний старт) (Просідання)   (Зависання)
      │              │              │
  Ініціалізація   Аварійне      Інкремент
  за замовчуванням відновлення   лічильника збоїв
```

- **Холодний старт (Power-On Reset, POR):** система вмикається вперше; виконується повна ініціалізація периферії, очищення оперативної пам'яті (BSS) та завантаження налаштувань за замовчуванням.
- **Аварійне просідання живлення (Brown-out / SVS):** система відновлює роботу після короткочасного зникнення мережі. Прошивка перевіряє цілісність контрольної суми аварійного журналу в FRAM; якщо сигнатура `0xDEADBEEF` валідна, робочі змінні відновлюються з пам'яті без скидання накопичених даних.
- **Спрацьовування сторожа (Watchdog Reset, WDR):** відбулося зависання коду. Прошивка інкрементує лічильник циклічних збоїв (Boot-Loop Counter) у спеціальній енергонезалежній ділянці пам'яті (RTC Backup RAM). Якщо кількість послідовних збоїв перевищує поріг (наприклад, 3 перезавантаження поспіль), мікроконтролер переходить у безпечний режим (Safe Mode / Recovery Mode), блокуючи активацію силових приводів та сповіщаючи оператора аварійним сигналом.

---

### Захист лінії WDI від високочастотних індуктивних завад

При комутації потужних індуктивних навантажувачів (соленоїдів, контакторів, крокових двигунів) через зворотний струм комутації в загальній земляній шині виникає сплеск потенціалу (Ground Bounce). Цей імпульс може навестися на довгу сигнальну лінію `WDI`, створивши паразитний спадний фронт:

1. Якщо супервізор сприйме цей наведений сплеск за імпульс скидання сторожа в середині зачиненого вікна (Closed Window), відбудеться раптове хибне апаратне скидання процесора.
2. Для запобігання цьому лінію `WDI` трасують максимально короткою доріжкою з підтяжкою до землі через резистор 47 кОм та встановленням малого RC-фільтра (100 Ом + 100 пФ), частота зрізу якого відфільтровує наносекундні завади комутації без спотворення робочих мікросекундних стробів процесора.

---

### Апаратне тестування та інжекція несправностей (HIL Fault Injection)

Верифікація коду обслуговування супервізора та сторожа вимагає автоматизованого тестування на апаратно-програмному стенді (Hardware-in-the-Loop, HIL):

1. **Тестування реакції на короткочасні викиди (Glitch Immunity):**
   Програмоване джерело живлення генерує калібровані прямокутні просідання напруги шини 3.3 В до 2.0 В тривалістю від 100 нс до 100 мкс. Тест підтверджує, що імпульси коротші 5 мкс ігноруються вхідним фільтром супервізора, а імпульси довші 20 мкс надійно ініціюють повний цикл перезавантаження.
2. **Інжекція програмних збоїв у зачинене вікно (Early Kick Injection):**
   Спеціальний зневаджувальний тестовий потік навмисно формує імпульс `WDI` через 10 мс після попереднього (всередині забороненого вікна). Стенд фіксує спадний перепад на лінії `/RESET` як доказ коректного спрацьовування захисту від зациклення.
3. **Тестування аварійного збереження (Hold-up Verification):**
   Керований ключ миттєво відсікає вхідну напругу 12 В. Осцилограф вимірює часовий інтервал між спадним фронтом переривання `PFO` та моментом, коли напруга на шині 3.3 В опускається нижче 2.7 В. Тест вважається успішним, якщо час збереження журналу в FRAM займає менше 40% виміряного часу утримання `t_holdup`.
4. **Інтеграція в конвеєр неперервного тестування (CI/CD Regression):**
   Усі наведені HIL-тести запускаються автоматично під час кожного коміту в репозиторій прошивки. Стенд із платою підключається через кероване реле живлення та логічний аналізатор, генеруючи сотні циклів аварійного вимкнення та аналізуючи телеметрію аварійних прапорців після перезапуску.

/* stm32_supervisor.c — C-реалізація */
#include "main.h"
#include <stdint.h>
#include <stdbool.h>

#define TASK_SENSOR_BIT   (1U << 0)
#define TASK_CONTROL_BIT  (1U << 1)
#define TASK_COMMS_BIT    (1U << 2)
#define TASKS_ALL_MASK    (TASK_SENSOR_BIT | TASK_CONTROL_BIT | TASK_COMMS_BIT)

static volatile uint32_t s_health_flags = 0;
static volatile bool s_power_fail_active = false;
static uint32_t s_last_wdt_kick_ms = 0;

void Task_ReportHealth(uint32_t task_bit) {
    __disable_irq();
    s_health_flags |= task_bit;
    __enable_irq();
}

/* Обробник раннього переривання зникнення живлення PFI (EXTI Line) */
void EXTI0_IRQHandler(void) {
    if (__HAL_GPIO_EXTI_GET_IT(PFO_PIN_Pin) != RESET) {
        __HAL_GPIO_EXTI_CLEAR_IT(PFO_PIN_Pin);
        s_power_fail_active = true;

        /* 1. Негайне відключення потужних периферійних модулів */
        HAL_GPIO_WritePin(PERIPH_PWR_EN_GPIO_Port, PERIPH_PWR_EN_Pin, GPIO_PIN_RESET);
        
        /* 2. Аварійне збереження стану в енергонезалежну FRAM через SPI */
        Save_Critical_State_Emergency();
    }
}

/* Періодична функція обслуговування віконного сторожа */
void WDT_Service_Routine(void) {
    if (s_power_fail_active) {
        return; /* Не обслуговуємо сторож, дозволяємо чисте апаратне скидання */
    }

    uint32_t now = HAL_GetTick();
    uint32_t delta = now - s_last_wdt_kick_ms;

    /* Вікно супервізора: min 35 мс, max 85 мс */
    if (delta >= 45 && delta <= 75) {
        if ((s_health_flags & TASKS_ALL_MASK) == TASKS_ALL_MASK) {
            /* Усі задачі відзвітували — смикаємо вивід WDI */
            HAL_GPIO_TogglePin(WDI_GPIO_Port, WDI_Pin);
            s_health_flags = 0;
            s_last_wdt_kick_ms = now;
        }
    }
}

/* stm32_supervisor.hpp — Ідіоматична C++ реалізація */
#pragma once
#include "main.h"
#include <cstdint>
#include <atomic>
#include <concepts>

namespace SystemSafety {

enum class TaskId : uint32_t {
    Sensor  = (1U << 0),
    Control = (1U << 1),
    Comms   = (1U << 2)
};

class SupervisorController {
public:
    static constexpr uint32_t RequiredMask = 
        static_cast<uint32_t>(TaskId::Sensor) |
        static_cast<uint32_t>(TaskId::Control) |
        static_cast<uint32_t>(TaskId::Comms);

    static constexpr uint32_t MinWindowMs = 45;
    static constexpr uint32_t MaxWindowMs = 75;

    static void reportTask(TaskId id) noexcept {
        healthFlags_.fetch_or(static_cast<uint32_t>(id), std::memory_order_relaxed);
    }

    static void handlePowerFailIsr() noexcept {
        powerFailState_.store(true, std::memory_order_seq_cst);
        HAL_GPIO_WritePin(PERIPH_PWR_EN_GPIO_Port, PERIPH_PWR_EN_Pin, GPIO_PIN_RESET);
        saveEmergencyState();
    }

    static void serviceWatchdog(uint32_t currentTickMs) noexcept {
        if (powerFailState_.load(std::memory_order_relaxed)) {
            return;
        }

        const uint32_t delta = currentTickMs - lastKickMs_;
        if (delta >= MinWindowMs && delta <= MaxWindowMs) {
            uint32_t expected = RequiredMask;
            if (healthFlags_.compare_exchange_strong(expected, 0, std::memory_order_acq_rel)) {
                HAL_GPIO_TogglePin(WDI_GPIO_Port, WDI_Pin);
                lastKickMs_ = currentTickMs;
            }
        }
    }

private:
    static inline std::atomic<uint32_t> healthFlags_{0};
    static inline std::atomic<bool> powerFailState_{false};
    static inline uint32_t lastKickMs_{0};

    static void saveEmergencyState() noexcept;
};

} // namespace SystemSafety

#include "esp_log.h"

#define PFO_INTR_PIN        GPIO_NUM_19
#define TASK_SENSOR_BIT     BIT0
#define TASK_COMM_BIT       BIT1
#define ALL_TASKS_BITS      (TASK_SENSOR_BIT | TASK_COMM_BIT)

static EventGroupHandle_t s_watchdog_event_group;
static const char *TAG = "SUPERVISOR";

static void IRAM_ATTR pfo_isr_handler(void* arg) {
    /* Раннє вимкнення радіотракту Wi-Fi/BLE при падінні живлення */
    gpio_set_level(GPIO_NUM_21, 0);
}

void app_supervisor_task(void *pvParameters) {
    s_watchdog_event_group = xEventGroupCreate();
    gpio_set_direction(WDI_GPIO_PIN, GPIO_MODE_OUTPUT);
    
    int pin_level = 0;
    TickType_t last_wake_time = xTaskGetTickCount();
    const TickType_t service_period = pdMS_TO_TICKS(50); /* 50 мс — центр вікна */

    while (1) {
        vTaskDelayUntil(&last_wake_time, service_period);

        EventBits_t bits = xEventGroupWaitBits(
            s_watchdog_event_group,
            ALL_TASKS_BITS,
            pdTRUE,  /* Очистити прапорці після читання */
            pdTRUE,  /* Чекати ВСІ прапорці */
            0        /* Без блокування */
        );

        if ((bits & ALL_TASKS_BITS) == ALL_TASKS_BITS) {
            pin_level = !pin_level;
            gpio_set_level(WDI_GPIO_PIN, pin_level);
        } else {
            ESP_LOGE(TAG, "Watchdog: окремі задачі пропустили ітерацію!");
        }
    }
}

#pragma once
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "freertos/event_groups.h"
#include "driver/gpio.h"

class EspWindowWatchdog {
public:
    explicit EspWindowWatchdog(gpio_num_t wdiPin, gpio_num_t pfoPin)
        : wdiPin_(wdiPin), pfoPin_(pfoPin), eventGroup_(xEventGroupCreate()) {
        
        gpio_config_t out_conf = {
            .pin_bit_mask = (1ULL << wdiPin_),
            .mode = GPIO_MODE_OUTPUT,
            .pull_up_en = GPIO_PULLUP_DISABLE,
            .pull_down_en = GPIO_PULLDOWN_DISABLE,
            .intr_type = GPIO_INTR_DISABLE
        };
        gpio_config(&out_conf);
    }

    void reportTaskHealth(EventBits_t taskBit) noexcept {
        xEventGroupSetBits(eventGroup_, taskBit);
    }

    void runSupervisorLoop(EventBits_t expectedTasksMask, uint32_t periodMs) noexcept {
        TickType_t lastWake = xTaskGetTickCount();
        const TickType_t period = pdMS_TO_TICKS(periodMs);
        int state = 0;

        while (true) {
            vTaskDelayUntil(&lastWake, period);

            EventBits_t bits = xEventGroupWaitBits(
                eventGroup_, expectedTasksMask, pdTRUE, pdTRUE, 0
            );

            if ((bits & expectedTasksMask) == expectedTasksMask) {
                state = !state;
                gpio_set_level(wdiPin_, state);
            }
        }
    }

private:
    gpio_num_t wdiPin_;
    gpio_num_t pfoPin_;
    EventGroupHandle_t eventGroup_;
};

/* arduino_supervisor.ino */
const int PIN_WDI = 7;
const int PIN_PFO_INTERRUPT = 2;
const int PIN_PERIPH_POWER = 8;

volatile bool powerLost = false;
unsigned long lastKickTime = 0;
const unsigned long MIN_WINDOW_MS = 35;
const unsigned long MAX_WINDOW_MS = 80;

void onPowerFail() {
  powerLost = true;
  digitalWrite(PIN_PERIPH_POWER, LOW); // Миттєво знеструмити навантаження
}

void setup() {
  pinMode(PIN_WDI, OUTPUT);
  pinMode(PIN_PERIPH_POWER, OUTPUT);
  digitalWrite(PIN_PERIPH_POWER, HIGH);

  pinMode(PIN_PFO_INTERRUPT, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(PIN_PFO_INTERRUPT), onPowerFail, FALLING);
  lastKickTime = millis();
}

void loop() {
  if (powerLost) {
    // Зупиняємося і не чіпаємо сторож — чекаємо апаратного скидання
    while (1) {}
  }

  // Виконання корисного алгоритму
  executeMainTasks();

  unsigned long now = millis();
  unsigned long elapsed = now - lastKickTime;

  // Скидання строго всередині відкритого вікна
  if (elapsed >= 50 && elapsed <= MAX_WINDOW_MS) {
    digitalWrite(PIN_WDI, !digitalRead(PIN_WDI));
    lastKickTime = now;
  }
}

void executeMainTasks() {
  delay(10); // Симуляція корисної роботи
}

class ArduinoWatchdogGuard {
public:
    ArduinoWatchdogGuard(uint8_t wdiPin, uint8_t pfoPin, uint8_t pwrPin)
        : wdiPin_(wdiPin), pfoPin_(pfoPin), pwrPin_(pwrPin) {}

        pinMode(wdiPin_, OUTPUT);
        pinMode(pwrPin_, OUTPUT);
        digitalWrite(pwrPin_, HIGH);

            state_ = !state_;
            digitalWrite(wdiPin_, state_ ? HIGH : LOW);
            lastKick_ = millis();
        }
    }

    uint8_t pfoPin_;
    uint8_t pwrPin_;
    uint32_t lastKick_{0};
