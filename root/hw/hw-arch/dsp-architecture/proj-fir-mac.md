# ⚙️ FIR-фільтр на C: MAC-цикл, кільцевий буфер, широкий акумулятор і насичення

Уся розмова про архітектуру DSP лишається абстрактною, доки не побачиш, як п'ять розрізнених рис — Гарвардський поділ пам'яті, однотактний MAC, широкий накопичувач, кільцева адресація, насичення — збираються в одну коротку функцію на C, що фільтрує реальний звук. Тут ми пройдемо саме цей шлях: від задачі до робочої прошивки, і в кожному рядку буде видно, чому DSP влаштований так, а не інакше. Код тут справжній — його можна вставити в проєкт для Cortex-M4 чи будь-якого чипа з MAC-командою, і він рахуватиме фільтр.

Домовимося про фільтр наперед, щоб було на чому стояти: **FIR** (англ. *finite impulse response*, фільтр зі скінченною імпульсною відповіддю) — це той, де новий вихідний відлік є зваженою сумою кількох останніх вхідних. Ніякого зворотного зв'язку, ніякої пам'яті про власні виходи — лише вхід, помножений на сталі коефіцієнти. Саме через цю простоту FIR стабільний завжди й лягає на MAC-цикл без жодної підступності, тому з нього й починають.

## Задача: відфільтрувати потік, не прогавивши жодного відліку

Уявімо конкретику. Acp (аналого-цифровий перетворювач) дає нам 48 000 відліків звуку за секунду, кожен — 16-бітне ціле зі знаком. Нам треба прибрати з сигналу високочастотний шум — застосувати згладжувальний низькочастотний фільтр на, скажімо, 64 коефіцієнти. Це означає, що на **кожен** із 48 тисяч відліків ми повинні порахувати суму з 64 множень і встигнути до приходу наступного відліку, тобто за 1/48000 секунди ≈ 20.8 мікросекунди.

Порахуймо навантаження чесно:

```
48000 відліків/с × 64 MAC/відлік = 3 072 000 MAC/с ≈ 3.1 млн MAC щосекунди
```

Три мільйони множень-додавань за секунду — і це лише один канал одного скромного фільтра. Якщо кожен MAC на звичайному ядрі коштує п'ять-сім команд, набігає 15–20 мільйонів команд щосекунди тільки на фільтр, і в реальному часі це вже відчутно. На DSP-подібному ядрі, де MAC — одна команда за такт, ті самі 3.1 мільйона MAC з'їдають лише 3.1 мільйона тактів — на 200-мегагерцовому чипі це кілька відсотків його часу. Ось де народжується вся вигода, і код нижче має цю вигоду не змарнувати.

> 🔧 **Навіщо це.** Різниця «п'ять команд на MAC чи одна» вирішує, влізе фільтр у бюджет реального часу чи ні. Той самий алгоритм, написаний недбало (з `%` у циклі, вузьким акумулятором, гілками на насичення), може виявитися вп'ятеро повільнішим і почати губити відліки — а в звуці згублений відлік чути як клац, у керуванні двигуном — як ривок. Тому в гарячому циклі кожна зайва команда на вагу золота.

## Ідея: згортка як ковзне вікно

Математично ми рахуємо **згортку** сигналу з коефіцієнтами фільтра. Вихідний відлік `y[n]` — це сума добутків останніх N вхідних відліків на N коефіцієнтів:

```
y[n] = h₀·x[n] + h₁·x[n−1] + h₂·x[n−2] + … + h_{N−1}·x[n−N+1]
```

Придивімося до структури, бо в ній — уся підказка для коду. По-перше, це просто N разів «помнож і додай», тобто N MAC-ів поспіль — рівно те, під що заточений DSP. По-друге, коли приходить наступний відлік `x[n+1]`, вікно з N значень **зсувається на один**: найновіший заходить, найдавніший випадає, а всі інші лишаються тими самими. Нам не треба нічого копіювати чи рухати в пам'яті — треба лише **правильно завести новий відлік і правильно пройтися по вікну**.

Наївний спосіб зсунути вікно — фізично переписати весь масив на одну комірку (`x[i] = x[i-1]` у циклі). Це N операцій копіювання на кожен відлік — стільки ж, скільки й самих множень, тобто ми подвоїли роботу дарма. Розумний спосіб — не рухати дані взагалі, а рухати **місце запису**: тримати масив-кільце й щоразу класти новий відлік туди, де лежав найдавніший, затираючи його. Дані стоять на місці, «їде» лише покажчик. Це і є **кільцевий буфер**, і саме він робить згортку дешевою.

## Перша, чесна версія: лінійний буфер і зсув

Почнемо з найпростішого коду, щоб він працював і був очевидним, а тоді розганятимемо. Коефіцієнти й відліки — 16-бітні цілі зі знаком; акумулятор — 32-бітний (поки що), бо добуток двох 16-бітних чисел не влазить у 16 біт.

```c
#include <stdint.h>

#define N 64                 /* кількість коефіцієнтів (порядок фільтра) */

static int16_t coef[N];      /* коефіцієнти h₀…h_{N-1}, задані наперед */
static int16_t hist[N];      /* останні N відліків, hist[0] — найновіший */

/* Наївно: зсунути історію й порахувати згортку в лоба. */
int16_t fir_naive(int16_t sample)
{
    /* зсув вікна: усе на комірку вправо, найдавніший випадає */
    for (int i = N - 1; i > 0; --i)
        hist[i] = hist[i - 1];
    hist[0] = sample;                 /* новий відлік — на початок */

    int32_t acc = 0;
    for (int i = 0; i < N; ++i)
        acc += (int32_t)hist[i] * coef[i];

    return (int16_t)(acc >> 15);      /* масштаб Q15 → Q0, про це нижче */
}
```

Цей код правильний і зрозумілий, і саме тому з нього корисно почати — видно кожну дію. Але в ньому дві біди. Перша — цикл зсуву: 63 присвоєння на кожен відлік, чиста витрата, яка нічого не рахує. Друга — приведення `(int32_t)hist[i]`: воно **обов'язкове**. Якби ми написали `hist[i] * coef[i]` без нього, C помножив би два `int16_t`, підвищивши їх до `int` (це [цілочислове підвищення](root:sf-lang/integer-types-c) — дрібні типи в арифметиці C автоматично стають щонайменше `int`), і на платформі, де `int` — 32-бітний, обійшлося б. Але покладатися на це не можна: суть у тому, що добуток мусить рахуватися в ширшому типі, ніж операнди, і це треба зробити явно. Найгірша ж біда захована в `acc` — до неї дійдемо, коли розберемося з масштабом.

## Друга версія: кільцевий буфер замість зсуву

Тепер приберемо марний зсув. Замість рухати дані, тримаємо покажчик `pos` на комірку, куди ляже **наступний** новий відлік (вона ж — місце найдавнішого). Дані стоять, рухається індекс.

```c
#include <stdint.h>

#define N 64

static int16_t coef[N];
static int16_t hist[N];
static int      pos = 0;          /* куди покласти наступний відлік */

int16_t fir_ring(int16_t sample)
{
    hist[pos] = sample;           /* новий відлік затер найдавніший */

    int32_t acc = 0;
    int     idx = pos;            /* ідемо від найновішого назад у часі */
    for (int i = 0; i < N; ++i) {
        acc += (int32_t)hist[idx] * coef[i];
        idx = (idx == 0) ? (N - 1) : (idx - 1);   /* крок назад по кільцю */
    }

    pos = (pos == N - 1) ? 0 : (pos + 1);         /* просунути місце запису */
    return (int16_t)(acc >> 15);
}
```

Зсув зник — це вже великий виграш. Але вигулькнула нова тонкість, і вона повчальна. Найновіший відлік лежить у `hist[pos]`, а попередні за часом — у комірках з меншими індексами, завертаючись через край масиву. Тому в циклі ми йдемо **назад** по буферу (`idx` зменшується, завертаючись з 0 на N−1) і множимо на коефіцієнти **вперед** (`coef[0]`, `coef[1]`, …). Це відповідає формулі: `coef[0]` = `h₀` множиться на найновіший `x[n]`, `coef[1]` = `h₁` — на попередній `x[n−1]`, і так далі. Наплутати напрямок легко, а для несиметричного фільтра це тихо зіпсує результат — фільтр працюватиме «навпаки в часі». Для симетричного (як багато згладжувальних FIR) помилка сховається, і ви впіймаєте її аж на іншому фільтрі.

Зверніть увагу на рядок завертання індексу:

```c
idx = (idx == 0) ? (N - 1) : (idx - 1);
```

Це і є **та сама модульна адресація, яку DSP робить залізом** — тільки написана вручну. На звичайному ядрі вона коштує порівняння й гілку на кожній ітерації гарячого циклу. Далі ми побачимо, чому це важливо і як `%` тут — пастка, а не рятунок.

## Масштаб: чому саме `>> 15` і що таке Q-формат

Тепер розберемо `acc >> 15`, бо без розуміння масштабу фільтр видасть тишу або хрип. Річ у тім, що коефіцієнти фільтра — це дробові числа, зазвичай менші за одиницю (сума 64 коефіцієнтів згладжувального фільтра дорівнює приблизно 1, тож кожен — десь 0.01–0.05). Але наші `coef[]` — цілі. Як покласти дробове число в ціле?

Домовляємося про **спільний масштаб**. У [фіксованій комі](root:hw-arch/fixed-point) число зображають цілим, домовившись, де подумки стоїть кома. Найпоширеніша домовленість для 16-бітного звуку — **Q15**: усі 15 біт після коми, один біт (знаковий) — до. Тобто ціле ділять подумки на 2¹⁵ = 32768, і діапазон значень стає від −1.0 до майже +1.0. Коефіцієнт 0.5 у Q15 — це ціле 16384; коефіцієнт 0.03 — це `round(0.03 × 32768)` = 983.

> 🔧 **Навіщо це.** Q-формат — це той місток, який дозволяє дешевому цілочисловому DSP рахувати дробову математику без апаратної плаваючої коми. Уся ціна — програміст мусить сам пам'ятати масштаб на кожному кроці й сам його вирівнювати. Забув зсув — і сигнал або зникне (недомасштабував), або перетвориться на хрип від переповнення (перемасштабував). Тому масштаб треба тримати в голові так само чітко, як розмірність у фізиці.

Тепер порахуймо масштаб добутку. Відлік `x` — це Q0 (звичайне ціле, кома в кінці), коефіцієнт `h` — Q15. Множимо:

```
Q0 × Q15 = Q15
```

Кожен доданок `x·h` виходить у Q15, і їхня сума `acc` — теж Q15, тобто вона в 32768 разів більша за справжнє значення. Щоб повернути результат у звичайне ціле (Q0), треба поділити на 32768 — а ділення на степінь двійки для цілого це просто зсув управо на 15:

```
y = acc / 32768 = acc >> 15
```

Ось звідки `>> 15`. Якби відліки теж були в Q15 (нормовані до діапазону −1…+1, як часто роблять), то добуток був би Q30, і зсунути довелося б на 15, щоб повернутись у Q15 — деталь та сама, змінюється лише інтерпретація. Пастка тут одна, але серйозна: **зсув мусить відповідати сумі Q-форматів операндів**. Помилка на один біт у зсуві — і сигнал стане вдвічі тихішим або вдвічі гучнішим, а на кілька біт — зникне чи розлетиться.

**Приклад: масштаб коефіцієнта в Q15.** Хай треба коефіцієнт h = 0.75.

```
Q15-подання:  round(0.75 × 32768) = round(24576.0) = 24576
перевірка:    24576 / 32768 = 0.75   ✓ точно
```

А тепер підступний коефіцієнт h = 0.1:

```
Q15-подання:  round(0.1 × 32768) = round(3276.8) = 3277
перевірка:    3277 / 32768 = 0.100006…   ← не рівно 0.1!
```

Десяткові дроби на кшталт 0.1 у двійковій фіксованій комі **точно не подаються** — так само, як 1/3 не подається скінченним десятковим дробом. Похибка тут крихітна (шоста значуща цифра), але вона є завжди, і в довгих ланцюгах обчислень такі похибки накопичуються. Це не вада коду — це природа фіксованої коми, і про неї треба знати, а не боротися з нею наосліп.

## Головна пастка: переповнення акумулятора

Тепер найважливіше — той рядок `int32_t acc`, який я двічі назвав бідою. Розберемо, чому 32 біт може не вистачити, хоч на перший погляд вистачає з запасом.

Один добуток `int16_t × int16_t` лежить у діапазоні до 32767 × 32767 ≈ 1.07 × 10⁹, а це майже впритул до стелі 32-бітного знакового числа (2³¹ − 1 ≈ 2.15 × 10⁹). Тобто **один** добуток ще влазить у int32 — але ледь-ледь. А ми складаємо **64** таких добутки. Якщо всі вони випадково однакового знаку й близькі до максимуму, сума полізе далеко за 2³¹, станеться [переповнення зі знаком](root:sf-lang/overflow-wraparound), і — увага — у C переповнення знакового цілого це взагалі **невизначена поведінка**: компілятор має право видати будь-що, і сучасні оптимізатори цим користуються. Практично ж сума «загорнеться»: щойно вона перескочить 2³¹, велике додатне число раптом стане великим від'ємним, і у звуці це буде різкий тріск на найгучнішому місці — рівно там, де фільтр найпотрібніший.

Чи трапиться це насправді? Для згладжувального фільтра, де сума коефіцієнтів ≈ 1, вихід не перевищує входу, і переповнення малоймовірне. Але для фільтра з підсиленням (сума коефіцієнтів > 1) або з великими коефіцієнтами воно цілком реальне, і покладатися на «зазвичай не переповнюється» в гарячому коді реального часу — це закладати міну.

Ось чому DSP роблять **накопичувач ширшим за добуток**. Класичний хід — 40-бітний акумулятор: 32 біти для суми плюс 8 додаткових «сторожових» бітів (англ. *guard bits*), які приймають переповнення проміжної суми на себе. Це не вигадка з підручника — саме так влаштований, наприклад, TI TMS320C55x: кожен його акумулятор має рівно 40 біт = 8 сторожових + 16 старших + 16 молодших, а MAC-блок має суматор із 32-/40-бітною логікою насичення (усталено, за офіційним CPU Reference Guide від Texas Instruments, SPRU371). Вісім сторожових бітів означають, що сума може «вилізти» за 32 біти аж у 2⁸ = 256 разів і не зіпсуватися — тобто можна безпечно скласти сотні добутків, а масштаб повернути наприкінці.

У чистому C 40-бітного типу нема, тож на ядрі загального призначення накопичуємо в **64-бітному** цілому — це навіть із запасом, зате гарантія без жодних роздумів про межу:

```c
#include <stdint.h>

#define N 64

static int16_t coef[N];
static int16_t hist[N];
static int      pos = 0;

int16_t fir_wide(int16_t sample)
{
    hist[pos] = sample;

    int64_t acc = 0;                          /* широкий акумулятор */
    int     idx = pos;
    for (int i = 0; i < N; ++i) {
        acc += (int64_t)hist[idx] * coef[i];  /* добуток одразу в 64 біт */
        idx = (idx == 0) ? (N - 1) : (idx - 1);
    }

    acc >>= 15;                               /* Q15 → Q0 */

    pos = (pos == N - 1) ? 0 : (pos + 1);
    return sat16(acc);                        /* насичення на виході — далі */
}
```

Зверніть увагу: `(int64_t)hist[idx] * coef[i]` — приведення знову стоїть на **лівому** операнді перед множенням, щоб добуток рахувався одразу в 64 бітах. Якби ми написали `acc += (int64_t)(hist[idx] * coef[i])`, то множення відбулося б у 32 бітах (де один добуток ще влазить, але це вже хиткий ґрунт), і лише потім результат розширився б — приведення запізнилося б. Дрібниця в дужках, а керує тим, у якій розрядності живе арифметика.

На DSP з апаратним 40-бітним акумулятором компілятор зробить те саме безкоштовно: MAC-команда сама накопичує у широкий регістр, і жодного `int64_t` писати не треба — ви пишете простий цикл множень-додавань, а залізо тримає ширину. Наш `int64_t` — це спосіб отримати ту саму безпеку на ядрі, де широкого акумулятора нема в залізі.

## Друга пастка: насичення на виході

Ми розширили акумулятор — усередині суми переповнення більше не буде. Але лишається **вихід**: після зсуву `acc >> 15` результат треба покласти назад у 16-бітний відлік, а він може не влізти. Якщо фільтр підсилює або сигнал сам близький до стелі, `acc >> 15` вийде за межі int16 (−32768…+32767).

Що робити на межі? Наївне `(int16_t)acc` знову **загорне** значення: 32768 стане −32768, і у звуці — той самий руйнівний тріск. Правильна для сигналу поведінка — **насичення** (англ. *saturation*): вилізло за стелю — залипни на стелі, за підлогу — на підлозі. Гучний звук тоді лише впирається в межу й дає м'яке обрізання, яке слух пробачає, замість перескоку з максимуму в мінімум. Різницю між загортанням і насиченням та її наслідки докладно розібрано в темі [насичувальної арифметики](root:sf-lang/saturating-arithmetic) — там видно, коли яка реакція доречна; тут же нам потрібен сам робочий clamp:

```c
/* Насичення 64-бітної суми до 16-бітного відліку зі знаком. */
static inline int16_t sat16(int64_t v)
{
    if (v >  32767) return  32767;   /* впертися у стелю */
    if (v < -32768) return -32768;   /* впертися у підлогу */
    return (int16_t)v;
}
```

Три рядки — і сигнал захищено. На DSP ці три рядки не потрібні зовсім: там насичення — це **режим самого MAC-блока**, і при записі акумулятора у вужчий регістр залізо саме притискає значення до межі. Тобто те, що на звичайному ядрі коштує дві гілки на кожен вихідний відлік, на DSP коштує нуль — це вбудовано в апаратну логіку суматора. Наша функція `sat16` — програмна заміна апаратного режиму, і в гарячому циклі саме ці приховані гілки з'їдають такти, яких DSP не витрачає.

## Третя пастка: `%` — це не апаратна модульна адресація

Повернімося до завертання індексу, бо тут криється поширена й дорога помилка. Природно ж написати гарно:

```c
idx = (idx - 1 + N) % N;    /* виглядає елегантно... */
```

Це працює **правильно**, але на багатьох ядрах — **повільно**, і причина глибша, ніж здається. Операція `%` для загального `N` — це апаратне ділення, а ділення на більшості вбудованих ядер (особливо без апаратного дільника) коштує десятки тактів. Поставити ділення в тіло циклу, який має бути голим MAC-ом за такт, — значить розтягнути кожну ітерацію в десятки разів. Ви написали елегантний рядок і зробили фільтр удесятеро повільнішим, не помітивши.

Компілятор рятує лише в одному випадку: якщо `N` — **степінь двійки** й тип **беззнаковий**, `x % N` оптимізується в дешеве побітове `x & (N-1)`. Тому DSP-код часто навмисне беруть довжину буфера рівною степеню двійки:

```c
#define N 64            /* степінь двійки — маска замість ділення */
unsigned idx = ...;
idx = (idx - 1) & (N - 1);   /* дешева заміна % для степеня двійки */
```

Але й це — компроміс, а не те, що робить справжній DSP. **Апаратна модульна адресація** DSP — це зовсім інший механізм: ви один раз задаєте регістру адресу початку буфера й його довжину, а далі кожне звичайне звертання «наступний елемент» апаратно тримає адресу в межах кільця, **не витрачаючи в циклі жодної окремої команди** — ні ділення, ні маски, ні порівняння. Завертання відбувається «на льоту» в самому блоці генерації адрес, паралельно з MAC-ом. Ось у чому прірва: наше `& (N-1)` — це все ще **окрема команда** на кожній ітерації; апаратна модульна адресація — це **нуль команд**, бо завертання вбудоване в саме звертання до пам'яті. І довжина буфера при цьому не мусить бути степенем двійки — залізо тримає будь-яку межу.

Підсумуємо ці три способи завертання, бо вибір між ними — це і є практична різниця між «код на CPU» і «код на DSP»:

```
(i - 1 + N) % N        загальний %  → апаратне ділення, десятки тактів
(i - 1) & (N - 1)      маска         → одна дешева команда, лише для N = 2ᵏ
апаратна модульна      DSP           → нуль команд у циклі, будь-яке N
```

## Тонкість вирівнювання: де насправді стоїть найновіший відлік

Ще одна пастка, на якій легко втратити годину на відлагодженні, — **узгодженість індексів буфера й коефіцієнтів**. Ми домовилися: після запису найновіший відлік у `hist[pos]`, а йти треба назад. Але дуже спокусливо просунути `pos` **до** обчислення, а не після, або переплутати, з якого індексу стартувати цикл. Кожен такий зсув на одиницю означає, що коефіцієнт `h₀` множиться не на той відлік — фільтр «з'їжджає» на один відлік у часі. Для згладжувального фільтра результат майже не зміниться (ви й не помітите), а для точного фазового фільтра зіпсується форма сигналу.

Правило, якого варто триматися залізно: **запиши новий відлік → порахуй, стартуючи саме з місця запису → лише потім просунь покажчик**. Порядок цих трьох дій — не косметика, а частина коректності. У коді `fir_wide` вище він саме такий: спершу `hist[pos] = sample`, тоді цикл від `idx = pos`, і аж наприкінці `pos = …`. Переставите — отримаєте тихий зсув на відлік.

Є й дослівно фізичне вирівнювання — **у пам'яті**. Апаратна кільцева адресація багатьох DSP вимагає, щоб буфер починався з адреси, кратної його розміру (вирівняної межі), інакше «завертання» піде не туди. У чистому C на звичайному ядрі це нас не стосується (ми завертаємо вручну), але щойно ви покладаєтеся на апаратне кільце, вирівнювання буфера стає обов'язковим — це те, про що компілятор для DSP подбає директивою, а ви маєте про це знати, щоб не дивуватися, чому «правильний» код дає сміття. Ширша тема того, чому взагалі дані люблять лягати на кратні адреси, — це [вирівнювання даних у пам'яті](root:sf-apps/memory-alignment).

![Три способи завернути індекс кільцевого буфера, від найдорожчого до безкоштовного: загальний оператор % розкладається в апаратне ділення на десятки тактів; побітова маска працює лише для довжини-степеня-двійки й коштує одну команду; апаратна модульна адресація DSP тримає адресу в межах кільця взагалі без окремих команд у циклі](img/wrap-cost.svg)
*Ціна завертання індексу. Той самий крок «назад по кільцю» коштує зовсім різне залежно від того, як його написати. Оператор `%` для довільного N — це ділення, десятки тактів у найгарячішому місці. Маска `& (N−1)` дешева, але вимагає, щоб довжина була степенем двійки. Апаратна модульна адресація DSP не витрачає в циклі жодної команди — завертання вбудоване в саме звертання до пам'яті, тому DSP і тримає темп «один MAC за такт».*

## Складаємо все разом: фільтр, готовий до прошивки

Тепер зберемо остаточну версію, у якій ураховано всі чотири уроки: кільцевий буфер без зсуву, широкий акумулятор проти переповнення, правильний масштаб Q15 і насичення на виході. Це код, який реально можна класти в обробник переривання acp.

```c
#include <stdint.h>

#define N 64                         /* степінь двійки: дешева маска */

static int16_t coef[N];              /* коефіцієнти в Q15, задані наперед */
static int16_t hist[N];              /* кільцевий буфер відліків */
static unsigned pos = 0;             /* беззнаковий → маска замість % */

/* Насичення широкої суми до 16-бітного відліку зі знаком. */
static inline int16_t sat16(int64_t v)
{
    if (v >  32767) return  32767;
    if (v < -32768) return -32768;
    return (int16_t)v;
}

/* Один відлік усередину — один відфільтрований назовні. */
int16_t fir_step(int16_t sample)
{
    hist[pos] = sample;              /* новий відлік затирає найдавніший */

    int64_t acc = 0;                 /* широкий акумулятор (замінює 40 біт DSP) */
    unsigned idx = pos;
    for (int i = 0; i < N; ++i) {
        acc += (int64_t)hist[idx] * coef[i];   /* MAC: множ і накопич */
        idx = (idx - 1) & (N - 1);             /* крок назад по кільцю */
    }

    pos = (pos + 1) & (N - 1);       /* просунути місце запису */
    return sat16(acc >> 15);         /* масштаб Q15 → Q0 + насичення */
}
```

Двадцять рядків, а в них — уся архітектура DSP, перекладена на C. Тіло циклу — це **чистий MAC** плюс завертання індексу: рівно те, що DSP робить однією командою з апаратною модульною адресацією й нульовими накладними на цикл. Широкий `int64_t` — це наш програмний замінник 40-бітного акумулятора з його сторожовими бітами. `sat16` — замінник апаратного режиму насичення. А маска замість `%` — найдешевше, що можна зробити на звичайному ядрі, коли справжньої модульної адресації нема.

Тепер видно головне: **чим ближче ядро до DSP, тим більше з цього коду зникає в залізо**. На ядрі з розширенням DSP (наприклад, Cortex-M4 з командами SIMD і насиченням) компілятор згорне тіло циклу в MAC-команди з апаратним насиченням, і `int64_t` та `sat16` перестануть коштувати зайвих тактів — вони або зникнуть, або стануть однією апаратною дією. На справжньому DSP зникне ще й маска, бо адресу тримає окремий блок. Той самий вихідний код, та сама коректність — але на кожному кроці до DSP гарячий цикл худне, доки не лишиться голий потік «один MAC за такт». Саме заради цього худнення й придумали всю ту архітектуру: Гарвардські шини, щоб годувати цикл; широкий акумулятор, щоб не боятися суми; кільцеву адресацію, щоб не платити за завертання; насичення, щоб не платити за захист виходу.

**Приклад: перевіримо масштаб на живих числах.** Хай фільтр із двох коефіцієнтів h₀ = 0.5, h₁ = 0.5 (просте усереднення двох сусідів), а на вхід прийшли відліки 20000 і 10000.

```
коефіцієнти в Q15:   0.5 → 16384
добутки:             20000 × 16384 = 327 680 000
                     10000 × 16384 = 163 840 000
сума acc:            327 680 000 + 163 840 000 = 491 520 000
зсув Q15 → Q0:       491 520 000 >> 15 = 491 520 000 / 32768 = 15000
насичення:           15000 у межах ±32767 → лишається 15000
результат:           15000  ← рівно середнє (20000+10000)/2  ✓
```

Числа сходяться: усереднення двох відліків дало їхнє середнє, масштаб повернувся правильно, насичення не знадобилося. А тепер видно й межу int32: проміжна сума 491 мільйон уже займає 29 біт — для двох доданків ще безпечно, але помножте кількість доданків на 32, як у реальному фільтрі, і стане зрозуміло, чому акумулятор мусить бути ширшим за 32 біти. Одне це число робить весь аргумент про сторожові біти відчутним на дотик.

## Що з цього забрати

FIR-фільтр — це найчистіший приклад того, як абстрактна архітектура стає конкретним кодом, і навпаки: як кожне архітектурне рішення DSP має точну відповідність у рядку C, який без цього заліза коштував би зайвих тактів.

Кільцевий буфер прибирає марний зсув даних — рухається покажчик, не масив. Широкий акумулятор ловить переповнення проміжної суми, якого 32 біт не гарантують: один добуток ще влазить, але їхня сума — ні, тому DSP тримає 40 біт зі сторожовими, а ми на звичайному ядрі беремо int64. Масштаб Q-формату — це домовленість, де стоїть кома; зсув наприкінці мусить дорівнювати сумі Q-форматів операндів, інакше сигнал зникне чи розлетиться. Насичення на виході рятує від руйнівного загортання — на DSP це режим заліза, на CPU три рядки clamp. І модульна адресація: `%` — це підступне ділення, маска рятує лише для степеня двійки, а справжня апаратна кільцева адресація не коштує в циклі жодної команди зовсім.

Напишіть цей фільтр раз своїми руками, крок за кроком — і будова будь-якого DSP перестане бути списком абревіатур: ви впізнаєте в ній відповіді на ті самі пастки, які щойно самі й обходили.
