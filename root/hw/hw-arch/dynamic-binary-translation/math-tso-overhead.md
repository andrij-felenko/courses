# 🧮 Математика та мікроархітектура TSO: ціна бар'єрів пам'яті

Під час двійкової трансляції багатопотокових програм x86 на процесори з архітектурою ARM64 або RISC-V головним бар'єром для продуктивності стає не трансляція арифметичних інструкцій чи декодування регістрів, а фундаментальна різниця в апаратних моделях узгодженості пам'яті (*Memory Consistency Models*).

Архітектура x86 жорстко гарантує строгий порядок збереження даних у пам'ять — модель **Total Store Order (TSO)**. Натомість архітектури ARM64 та RISC-V спроєктовані за моделлю **слабкого впорядкування пам'яті (Weak Memory Ordering, WMO)**. Щоб програма, скомпільована для x86, працювала коректно на процесорі ARM без апаратної підтримки TSO, транслятор змушений програмно вставляти дорогі інструкції синхронізації шини — бар'єри пам'яті (*Memory Fences / Barriers*).

Розглянемо мікроархітектурну будову процесорного конвеєра, виведемо аналітичну математичну модель накладних витрат на бар'єри пам'яті та порівняємо програмну емуляцію з апаратним перемиканням режиму TSO в чипах Apple Silicon та розширенні RISC-V Ztso.

## Аксіоматична модель: матриця перевпорядкувань

У сучасних суперскалярних процесорах з позачерговим виконанням (*Out-of-Order Execution*) конвеєр намагається виконати якомога більше інструкцій паралельно. Якщо дві інструкції звернення до пам'яті не мають залежності за адресою, процесор може змінити порядок їхньої фізичної відправки на шину кешу першого рівня L1D.

Нехай `L` позначає операцію читання з пам'яті (*Load*), а `S` — операцію запису в пам'ять (*Store*). Можливі чотири комбінації послідовних звернень до різних адрес пам'яті:

```
1. L -> L  (Читання після Читання)
2. L -> S  (Запис після Читання)
3. S -> S  (Запис після Запису)
4. S -> L  (Читання після Запису)
```

Матриця дозволених апаратних перевпорядкувань (*Reordering Matrix*) для різних процесорних архітектур виглядає так:

| Перестановка | x86 TSO | SPARC TSO | ARM64 (v8-A / v9-A) | RISC-V (RVWMO) |
| :--- | :--- | :--- | :--- | :--- |
| `L -> L` (Load обганяє Load) | ❌ Заборонено | ❌ Заборонено | ✅ Дозволено | ✅ Дозволено |
| `L -> S` (Store обганяє Load) | ❌ Заборонено | ❌ Заборонено | ✅ Дозволено | ✅ Дозволено |
| `S -> S` (Store обганяє Store) | ❌ Заборонено | ❌ Заборонено | ✅ Дозволено | ✅ Дозволено |
| `S -> L` (Load обганяє Store) | ✅ **Дозволено** | ✅ **Дозволено** | ✅ Дозволено | ✅ Дозволено |

### Чому x86 забороняє перестановки `S -> S` та `L -> L`
В архітектурі x86 кожен процесорний кристал містить апаратний буфер запису FIFO — **Store Buffer**. Записи потрапляють у Store Buffer строго в порядку програми й так само строго по черзі скидаються в кеш L1D. Завдяки цьому жоден інший процесор у системі не може побачити новий запис раніше за старий.

Єдина оптимізація, яку дозволяє x86 TSO — це перевпорядкування `S -> L`: процесор може прочитати значення з кешу для операції `Load`, поки його власні попередні записи `Store` ще перебувають у локальному Store Buffer і не скинуті в загальну пам'ять.

### Чому ARM та RISC-V дозволяють усі перестановки
У процесорах зі слабкою моделлю (WMO) апаратура має право:
1. Виконувати операції `Load` спекулятивно в довільному порядку, якщо лінії кешу вже доступні в L1D.
2. Об'єднувати та переставляти записи у Store Buffer для максимізації пропускної здатності шини (*Store Merging / Write Combining*).

Якщо гостьовий код x86 використовує класичний патерн публікації даних без блокувань (*Lock-Free Message Passing*):

```
// Потік 1 (Письменник):
data = 42;        // Store 1
flag = 1;         // Store 2

// Потік 2 (Читач):
while (flag == 0); // Load 1
r1 = data;        // Load 2
```

На процесорі x86 цей код гарантовано працює: Потік 2 ніколи не прочитає `data == 0`, якщо він побачив `flag == 1`. 

Проте на звичайному процесорі ARM64:
* Потік 1 може скинути `flag = 1` у кеш раніше, ніж `data = 42` (перестановка `S -> S`).
* Потік 2 може спекулятивно прочитати `data` до того, як перевірить `flag` (перестановка `L -> L`).

У результаті Потік 2 отримає неініціалізовані сміттєві дані `r1 == 0`. Щоб запобігти цій помилці, транслятор повинен встановити апаратні бар'єри пам'яті.

## Мікроархітектурна анатомія бар'єра пам'яті

Розглянемо, що відбувається всередині фізичного конвеєра ядра ARM64 під час виконання повної інструкції бар'єра пам'яті `DMB ISH` (*Data Memory Barrier, Inner Shareable*) або інструкції `FENCE rw, rw` в архітектурі RISC-V.

Ядро позачергового процесора містить такі ключові структури:
1. **ROB (Reorder Buffer):** буфер перевпорядкування інструкцій (типовий розмір від 192 до 352 записів), що гарантує стан точних виключень при завершенні інструкцій у порядку програми (*In-Order Commit*).
2. **SB (Store Buffer):** черга відкладених записів у пам'ять (від 48 до 72 записів).
3. **LQ (Load Queue):** черга активних операцій читання, що відстежує спекулятивні зчитування та конфлікти когерентності (від 64 до 128 записів).
4. **RS (Reservation Stations / Execution Queues):** черги планувальника операцій перед передачею у функціональні блоки ALU/FPU/LSU.

Коли декодер конвеєра зустрічає інструкцію `DMB ISH`, процесор запускає таку послідовність апаратних дій:

```
1. Зупинка диспетчеризації (Fetch / Decode Stall):
   Нові інструкції більше не передаються в черги Reservation Stations.

2. Спустошення Store Buffer (Drain SB):
   Конвеєр очікує, поки ВСІ записи, що перебувають у Store Buffer, 
   будуть фізично зафіксовані в лініях кешу L1D та підтверджені 
   протоколом когерентності шини (MESI / MOESI).

3. Інвалідація спекулятивних Load Queue (Flush Speculative Loads):
   Усі операції Load, розташовані після бар'єра, що встигли виконатися 
   спекулятивно з випередженням, скасовуються. Їхні результати 
   викидаються з регістра перейменування (RAT).

4. Відновлення конвеєра (Pipeline Resume):
   Після повного підтвердження скидання шини блокування знімається, 
   і вибірка інструкцій відновлюється.
```

Ці чотири кроки повністю зупиняють паралелізм конвеєра. Позачерговий процесор фактично перетворюється на повільний послідовний процесор на десятки тактів.

## Аналітична математична модель накладних витрат

Сформуємо аналітичну модель для розрахунку падіння темпу виконання інструкцій за такт (англ. *Instructions Per Cycle*, IPC) при програмній емуляції TSO.

### 1. Параметри гостьового навантаження
Нехай програма виконує потік інструкцій із такими статистичними частками:
* `f_L` — частка операцій читання (*Loads*) від загальної кількості інструкцій програми (для типового коду x86 `f_L ≈ 0.20 – 0.25`);
* `f_S` — частка операцій запису (*Stores*) від загальної кількості інструкцій (`f_S ≈ 0.10 – 0.15`);
* `f_mem = f_L + f_S` — загальна частка операцій з пам'яттю (`f_mem ≈ 0.30 – 0.40`);
* `f_other = 1 - f_mem` — частка арифметичних інструкцій, розгалужень та регістрових операцій;
* `IPC_native` — базовий темп виконання коду нативним конвеєром без бар'єрів пам'яті;
* `CPI_native = 1 / IPC_native` — середня кількість тактів на інструкцію (*Cycles Per Instruction*).

### 2. Затримка одного бар'єра пам'яті
Штраф за виконання одного апаратного бар'єра `C_fence` (у тактах процесора) складається з трьох складових:

```
C_fence = T_drain_sb + T_flush_lq + T_restart
```

де:
* `T_drain_sb` — час очікування скидання черги записів Store Buffer у кеш L1D. Якщо середня кількість записів у буфері становить `N_sb`, а середня латентність фіксації одного запису через шину кешу дорівнює `L_write`:

```
T_drain_sb
= N_sb · L_write    [скидання всіх записів у Store Buffer]
```

* `T_flush_lq` — час анулювання спекулятивних читань та оновлення таблиць перейменування регістрів.
* `T_restart` — затримка заповнення конвеєра вибірки (глибина конвеєра `D_pipe`, зазвичай від 12 до 18 тактів).

Для сучасних ядер ARM Cortex-A78 / Neoverse-N1 середня вартість виконання повного бар'єра пам'яті `DMB ISH` при гарячому кеші L1 становить:

```
C_fence ≈ 18 – 35 тактів
```

Якщо ж один із записів у Store Buffer спричинив промах кешу L1/L2 і вимагає звернення до кешу L3 або оперативної пам'яті DRAM, вартість бар'єра стрибає до:

```
C_fence_miss ≈ 80 – 200 тактів
```

### 3. Розрахунок деградації CPI та IPC

Розглянемо дві стратегії трансляції:

#### Стратегія А: Бар'єр після кожного запису (Store-Only Fencing)
Найпростіший коректний транслятор перетворює кожну інструкцію запису `mov [mem], reg` у пару: `str` + `dmb ish`.

Кількість тактів на інструкцію для транслятора `CPI_dbt` розраховується як:

```
CPI_dbt
= CPI_native + f_S · C_fence    [додавання затримки бар'єра на кожен запис]
```

Звідси реальний темп виконання:

```
IPC_dbt
= 1 / CPI_dbt                   [визначення темпу IPC через CPI]
= 1 / (CPI_native + f_S · C_fence) [підстановка формули CPI_dbt]
```

Коефіцієнт уповільнення програми `S` (у скільки разів нативний код швидший за трансльований):

```
S
= IPC_native / IPC_dbt          [відношення темпів виконання]
= IPC_native · (1 / IPC_native + f_S · C_fence) [розкриття виразу для IPC_dbt]
= 1 + IPC_native · f_S · C_fence [спрощення: скорочення базового темпу]
```

#### Стратегія Б: Повна емуляція TSO через Acquire/Release
Архітектура ARMv8.1-A надає інструкції одностороннього бар'єра: `LDAR` (*Load-Acquire*) та `STLR` (*Store-Release*).
`STLR` гарантує, що всі попередні операції запису й читання завершаться до виконання цього запису (забороняє `Store -> Store` та `Load -> Store`).
`LDAR` гарантує, що жодна наступна операція читання чи запису не почнеться раніше цього читання (забороняє `Load -> Load` та `Load -> Store`).

Хоча `LDAR`/`STLR` не скидають конвеєр повністю як `DMB ISH`, вони утримують відповідні записи в черзі Load/Store Unit, блокуючи випереджальне спекулятивне виконання. Штраф за кожну таку інструкцію становить:
* `C_stlr ≈ 4 – 8` тактів на кожен запис;
* `C_ldar ≈ 2 – 5` тактів на кожне читання.

Тоді розрахунок деградації для стратегії Acquire/Release:

```
CPI_dbt_ar
= CPI_native + f_S · C_stlr + f_L · C_ldar    [штрафи односторонніх бар'єрів]
```

## Покроковий числовий приклад розрахунку

Розглянемо реальні параметри сучасного високопродуктивного процесора:

```
Параметри системи:
IPC_native = 2.50 інструкцій/такт  (потужне 4-way суперскалярне ядро)
CPI_native = 1 / 2.50 = 0.40 такти/інструкцію
f_L = 0.22  (22% операцій читання)
f_S = 0.12  (12% операцій запису)
C_fence = 22 такти  (середня ціна повного бар'єра DMB ISH)
C_stlr = 6 тактів   (ціна інструкції Store-Release)
C_ldar = 3 такти    (ціна інструкції Load-Acquire)
```

### 1. Розрахунок для Стратегії А (Повний бар'єр `DMB ISH` після кожного Store):

Розрахуємо середній час виконання інструкції `CPI_dbt`:

```
CPI_dbt
= CPI_native + f_S · C_fence    [формула повного бар'єра]
= 0.40 + 0.12 · 22              [підстановка числових параметрів]
= 0.40 + 2.64                   [обчислення штрафу записів]
= 3.04 такти/інструкцію         [підсумок CPI]
```

Розрахуємо новий темп виконання `IPC_dbt`:

```
IPC_dbt
= 1 / CPI_dbt                   [визначення темпу через CPI]
= 1 / 3.04                      [ділення на отриманий CPI]
= 0.329 інструкцій/такт         [підсумковий темп IPC]
```

Коефіцієнт уповільнення `S`:

```
S
= IPC_native / IPC_dbt          [відношення темпів]
= 2.50 / 0.329                  [підстановка значень]
= 7.60                          [уповільнення у 7.6 раза]
```

У наївному варіанті з повними бар'єрами продуктивність процесора падає на **86.8%**! Процесор витрачає 87% усього часу на очікування скидання шини Store Buffer.

### 2. Розрахунок для Стратегії Б (Оптимізований транслятор з `LDAR` / `STLR`):

Розрахуємо `CPI_dbt_ar`:

```
CPI_dbt_ar
= CPI_native + f_S · C_stlr + f_L · C_ldar [формула з Acquire/Release]
= 0.40 + 0.12 · 6 + 0.22 · 3    [підстановка параметрів]
= 0.40 + 0.72 + 0.66            [проміжні штрафи]
= 1.78 такти/інструкцію         [підсумок CPI]
```

Розрахуємо `IPC_dbt_ar`:

```
IPC_dbt_ar
= 1 / CPI_dbt_ar                [визначення темпу через CPI]
= 1 / 1.78                      [ділення на отриманий CPI]
= 0.562 інструкцій/такт         [підсумковий темп IPC]
```

Коефіцієнт уповільнення `S_ar`:

```
S_ar
= IPC_native / IPC_dbt_ar       [відношення темпів]
= 2.50 / 0.562                  [підстановка значень]
= 4.45                          [уповільнення у 4.45 раза]
```

Навіть при використанні спеціалізованих інструкцій `LDAR/STLR` втрата продуктивності становить **77.5%**. Це математично доводить, чому чисто програмні емулятори x86 на базі стандартного ARM64 не здатні подолати бар'єр у 20–30% нативної швидкості на багатопотокових навантаженнях.

## Аналіз конкретних структур даних без блокувань

Розглянемо вплив бар'єрів пам'яті на дві фундаментальні багатопотокові структури даних:

### 1. Черга Майкла-Скотта (Michael-Scott Lock-Free Queue)
У неблокуючій черзі Майкла-Скотта операція додавання вузла (`enqueue`) складається з чотирьох послідовних кроків:
1. `Load tail` (читання вказівника на хвіст);
2. `Load tail->next` (перевірка кінця черги);
3. `Atomic CAS(tail->next, null, new_node)` (атомарне приєднання вузла);
4. `Atomic CAS(tail, old_tail, new_node)` (просування покажчика хвоста).

В архітектурі x86 звичайні операції `Load` не вимагають бар'єрів, а `lock cmpxchg` автоматично виконує повну синхронізацію шини.

Під час програмної емуляції на ARM64 кожне читання перетворюється на `LDAR`, а кожен запис — на `STLR`. Додатково перед `CAS` вставляється повний бар'єр `DMB ISH`. 

Розрахуємо накладні витрати на одну операцію `enqueue` при частоті процесора `f = 3.2 ГГц`:

```
T_enqueue_x86
= 2 · L_load + 2 · L_cas        [формула затримки для x86]
= 2 · 4 + 2 · 18                [тактові затримки в x86 TSO]
= 44 такти                      [13.75 наносекунд при частоті 3.2 ГГц]
```

```
T_enqueue_arm_dbt
= 2 · (L_load + C_ldar) + 2 · (L_cas + C_fence) [формула з бар'єрами для ARM]
= 2 · (4 + 4) + 2 · (18 + 22)   [тактові затримки в емуляції DBT]
= 16 + 80                       [проміжний розрахунок]
= 96 тактів                     [30.00 наносекунд при частоті 3.2 ГГц]
```

Пропускна здатність черги під DBT падає у `96 / 44 = 2.18` раза (більш ніж удвічі) виключно через простій шини синхронізації пам'яті.

### 2. Кільцевий буфер SPSC (Single-Producer Single-Consumer)
У кільцевому буфері передачі повідомлень виробник оновлює покажчик запису `write_idx`, а споживач — покажчик читання `read_idx`.
В x86 звичайний запис `mov [write_idx], val` негайно публікує дані.
В емуляторі на ARM64 цей запис вимагає інструкції `STLR` або `DMB ISH`, що збільшує затримку передачі повідомлення від виробника до споживача (*End-to-End Latency*) з 15–20 наносекунд до 65–90 наносекунд.

## Апаратне рішення: Apple Silicon TSO та RISC-V Ztso

Розуміючи фатальні обмеження програмної емуляції, розробники кремнію впровадили апаратне перемикання моделей пам'яті.

### 1. Apple Silicon Hardware TSO Mode
Корпорація Apple при розробці мікроархітектур Firestorm (чипи M1) та Avalanche (M2) реалізувала апаратну підтримку режиму x86 TSO безпосередньо в кремнії процесора через службовий біт регістра `ACTLR_EL1`.

Коли для потоку Rosetta 2 вмикається біт TSO:
* **FIFO Store Buffer:** блок черги записів автоматично забороняє перевпорядкування `Store -> Store` та `Load -> Store` на апаратному рівні без програмних бар'єрів.
* **Спекулятивне читання з перевіркою когерентності (Snooping on Speculative Loads):** операції `Load` продовжують виконуватися позачергово й спекулятивно на максимальній швидкості конвеєра. Проте черга Load Queue починає апаратно відстежувати вхідні сигнали інвалідації ліній кешу від інших ядер (*Snoop Invalidation*).
* **Вибірковий відкіт замість тотальної зупинки:** якщо інше ядро записало дані за адресою, яку поточне ядро вже встигло прочитати спекулятивно з випередженням, апаратура генерує внутрішній сигнал *Memory Order Violation*. Лише в цей рідкісний момент конвеєр скидає спекулятивні інструкції та перечитує лінію пам'яті.

У реальних багатопотокових програмах ситуація, коли два ядра одночасно звертаються до однієї й тієї самої комірки пам'яті в конфліктному порядку (*True Data Race*), трапляється вкрай рідко.

Нехай `P_conflict` — ймовірність того, що спекулятивна операція `Load` зазнає конфлікту когерентності з записом іншого ядра під час перебування в черзі Load Queue:

```
P_conflict ≈ 0.00005 – 0.0002 (0.005% – 0.02%)
```

Затримка відновлення конвеєра при виявленні конфлікту `T_recovery` дорівнює вартості звичайного промаху передбачення переходу:

```
T_recovery ≈ 14 – 20 тактів
```

Додатковий штраф до `CPI` при апаратному TSO становить:

```
ΔCPI_hw_tso
= f_L · P_conflict · T_recovery [математичне сподівання штрафу]
= 0.22 · 0.0001 · 16            [підстановка середніх значень]
= 0.000352 такти/інструкцію     [мізерна затримка]
```

Розрахуємо підсумковий `CPI_apple_tso`:

```
CPI_apple_tso
= CPI_native + ΔCPI_hw_tso      [додавання затримки конфліктів]
= 0.40 + 0.000352               [підстановка значень]
= 0.400352 такти/інструкцію     [підсумок CPI]
```

Розрахуємо підсумковий `IPC_apple_tso`:

```
IPC_apple_tso
= 1 / 0.400352                  [ділення на підсумковий CPI]
= 2.4978 інструкцій/такт        [майже ідентично нативним 2.50]
```

Втрата продуктивності в апаратному режимі TSO становить:

```
Втрата
= (1 - IPC_apple_tso / IPC_native) · 100% [відносна втрата швидкодії]
= (1 - 2.4978 / 2.50) · 100%    [розрахунок відсотка]
= 0.088%                        [менше однієї десятої відсотка!]
```

### 2. Архітектурне розширення RISC-V Ztso
Організація RISC-V International стандартизувала аналогічне розширення — **Ztso (Total Store Ordering Extension)**, включене до профілів серверних процесорів RVA22/RVA23.

Розширення Ztso визначає:
* Модифікацію правил когерентності пам'яті для команд `LW`, `SW`, `LD`, `SD`, перетворюючи модель RVWMO на строгий TSO.
* Можливість динамічного перемикання моделі пам'яті для окремих процесів операційної системи Linux через системний виклик `prctl(PR_SET_MEMORY_ORDER)`.
* Завдяки цьому серверні процесори RISC-V (наприклад, ядра SpacemiT K1 та Alibaba T-Head XuanTie C910/C920) можуть транслювати хмарні сервери x86 без катастрофічних втрат на бар'єрах пам'яті.

## Енергетичні витрати: Джоулі на інструкцію (EPI)

Зупинка конвеєра бар'єрами пам'яті руйнує не лише швидкодію, а й енергоефективність процесора.

Енергія `E`, витрачена на виконання програми з `N` інструкцій, визначається середньою споживаною потужністю процесора `P_core` та часом виконання `t_exec`:

```
t_exec
= (N · CPI) / f_clk             [час через кількість тактів і частоту]
```

```
E
= P_core · t_exec               [визначення енергії через потужність і час]
= P_core · (N · CPI) / f_clk    [підстановка формули часу t_exec]
```

Енергія на одну інструкцію (англ. *Energy Per Instruction*, EPI):

```
EPI
= E / N                         [енергія на одну інструкцію]
= (P_core · CPI) / f_clk        [підстановка формули загальної енергії E]
```

Коли конвеєр зупиняється бар'єром `DMB ISH`, динамічна потужність логіки ALU дещо знижується, проте статична потужність витоків (*Static Leakage Power*) та потужність тактового дерева (*Clock Tree Power*) продовжують споживатися на повній частоті.

Порівняємо відносні енерговитрати:

```
EPI_dbt / EPI_native
= (P_dbt · CPI_dbt) / (P_native · CPI_native) [відношення витрат енергії]
```

Навіть якщо споживана потужність під час простою зменшується на 20% (`P_dbt ≈ 0.80 · P_native`), зростання `CPI` з `0.40` до `1.78` (у 4.45 раза) призводить до стрибка енерговитрат:

```
EPI_dbt / EPI_native
= 0.80 · 4.45                   [підстановка відносної потужності та CPI]
= 3.56                          [зростання витрат енергії у 3.56 раза]
```

Акумулятор ноутбука розряджається в 3.5 раза швидше виключно через програмну синхронізацію пам'яті! Апаратний TSO-біт Apple Silicon та розширення RISC-V Ztso повністю усувають ці зайві енерговитрати, забезпечуючи рекордну енергоефективність.
