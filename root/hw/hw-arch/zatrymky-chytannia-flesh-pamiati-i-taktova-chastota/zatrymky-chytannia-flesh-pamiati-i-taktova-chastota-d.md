- [Конвеєр](root:hw-arch/pipeline) — стадії вибірки, декодування та виконання інструкцій, простої конвеєра (pipeline stalls).
- [Кеш](root:hw-arch/cache) — принцип локальності, лінії кешу, промахи й попадання (hit/miss).

Коли мікроконтролер із тактовою частотою ядра 168 МГц або 480 МГц прокидається після апаратного скидання, він стартує від повільного внутрішнього RC-генератора на частоті близько 16 МГц. На цій швидкості період одного такту становить 62.5 нс, і ядро безперешкодно вичитує інструкції зі вбудованої Flash-пам'яті за один такт. Але щойно розробник ініціалізує блок фазового автопідстроювання частоти (PLL) на максимальні 168 МГц, де період такту стискається до 5.95 нс, і перемикає системний мультиплексор тактування без попереднього налаштування контролера Flash, процесор миттєво падає у помилку шини (`BusFault`) або зависає в нескінченному циклі `HardFault`. Причина полягає не в помилці обчислювального ядра: кремнієва логіка самого процесора здатна виконувати арифметичні операції за 5.95 нс, але масив комірок енергонезалежної пам'яті фізично не здатний віддати збережені дані швидше ніж за 20–30 нс.

Цей фундаментальний розрив між високою тактовою частотою процесорного ядра та відносно повільною матрицею Flash-пам'яті визначає архітектуру всієї підсистеми пам'яті сучасного мікроконтролера. Подолання цього бар'єра вимагає апаратного конфігурування тактів очікування (лат. *latentia* — прихованість, затримка, Wait States), використання надшироких шин вибірки, буферів випереджального читання, апаратних кеш-прискорювачів та перенесення найбільш критичних ділянок коду в оперативну пам'ять.

## Фізичні обмеження швидкості доступу до Flash-матриці

Щоб зрозуміти походження затримки читання, необхідно порівняти фізичну будову комірки швидкої оперативної пам'яті (SRAM) та комірки енергонезалежної пам'яті (NOR Flash).

Комірка статичної оперативної пам'яті SRAM будується на базі шести польових транзисторів (схема 6T). Вона являє собою симетричний тригер із двох взаємно інверсних логічних елементів, який підтримує свій стан за рахунок прямого живлення. Коли процесор звертається до комірки SRAM, транзистори керування відкриваються, і вихідні транзистори тригера активно перезаряджають паразитну ємність короткої внутрішньої лінії зчитування. Час наростання фронту сигналу становить частки наносекунди, що дозволяє отримувати дані за 1 такт навіть на частотах 200–500 МГц.

![Часові діаграми доступу до Flash](/root/hw/hw-arch/zatrymky-chytannia-flesh-pamiati-i-taktova-chastota/img/flash-access-timing.svg)
*Часові діаграми доступу до вбудованої Flash-пам'яті: при 16 МГц період такту 62.5 нс перекриває 30 нс матриці (0WS); при 168 МГц період такту 5.95 нс вимагає 5 тактів очікування (разом 6 тактів = 35.7 нс).*

Будова комірки NOR Flash кардинально інша. Вона використовує транзистор із плаваючим затвором (англ. *floating gate*) або нітридною пасткою заряду (англ. *charge trap*, технологія SONOS/MONOS). Інформація зберігається у вигляді електронів, ізольованих шаром діелектрика з діоксиду кремнію завтовшки лише кілька нанометрів. Наявність або відсутність зв'язаного заряду змінює порогову напругу відкриття транзистора:

1. **Стертий стан (логічна 1):** На плаваючому затворі немає надлишкового заряду. При подачі на затвор керування номінальної напруги зчитування транзистор відкривається і проводить електричний струм (типово 15–40 мкА).
2. **Запрограмований стан (логічний 0):** На плаваючий затвор інжектовані електрони. Створене ними електричне поле зміщує порогову напругу вгору. При тій самій напрузі зчитування транзистор залишається закритим, і струм через канал практично дорівнює нулю.

Процес зчитування одного біта з масиву Flash складається з чотирьох послідовних апаратних фаз, кожна з яких додає свій внесок у підсумкову часову затримку:

1. **Декодування адреси та активація словарної лінії (Word Line):** Адресний дешифратор повинен підняти напругу на провіднику словарної лінії. У масиві об'ємом 1–2 Мбайти словарна лінія проходить через тисячі комірок. Вона має відчутний розподілений опір та значну паразитну ємність відносно підкладки. Поширення фронту напруги по словарній лінії є класичним перехідним процесом в RC-ланцюжку, що забирає від 4 до 8 нс (`t_WL`).
2. **Попереднє заряджання бітової лінії (Precharge):** Перед початком вимірювання лінія зчитування стовпчика (Bit Line) заряджається спеціальним ключем до проміжного потенціалу (наприклад, 1.2 В).
3. **Розряджання ємності бітової лінії струмом комірки:** Коли словарна лінія відкрита, вибраний транзистор комірки (якщо він містить логічну одиницю) починає стікати струм на «землю». Але струм однієї мініатюрної комірки становить лише десятки мікроампер, тоді як довга металева лінія стовпчика, до якої підключені стоки тисяч сусідніх комірок масиву, володіє сумарною паразитною ємністю від 1 до 5 пФ. Час, необхідний для того, щоб слабкий струм `I_cell` знизив напругу на ємності `C_BL` на порогову дельту `ΔV` (близько 100–200 мВ), визначається рівнянням:
   ```
   Δt_discharge = (C_BL · ΔV) / I_cell
   ```
   Для `C_BL = 2 пФ`, `ΔV = 150 мВ` та `I_cell = 20 мкА`:
   ```
   Δt_discharge = (2·10⁻¹² · 0.15) / (20·10⁻⁶) = 15 нс
   ```
4. **Спрацьовування сенсорного підсилювача (Sense Amplifier):** Оскільки спад напруги на бітовій лінії становить лише десятки або сотні мілівольтів, до кожного стовпчика підключено аналоговий диференційний підсилювач. Він порівнює спад напруги або струм робочої бітової лінії зі зразковою еталонною коміркою (англ. *reference cell*) і перетворює слабку аналогову різницю в повноцінний цифровий логічний сигнал CMOS-рівня (0 або 3.3 В). Час перемикання компаратора становить 5–8 нс.

Сумарний фізичний час доступу до масиву вбудованої Flash-пам'яті складається з суми цих затримок:

```
T_access = t_WL + t_discharge + t_sense + t_mux ≈ 20...32 нс
```

Жодна сучасна технологія вбудованої кремнієвої пам'яті NOR Flash (від техпроцесів 90 нм до 28 нм) не здатна зменшити цей час нижче 15–20 нс без катастрофічного збільшення площі кристала та енергоспоживання.

## Співвідношення тактової частоти ядра та затримок

Швидкість роботи обчислювального ядра визначається періодом тактового сигналу шини AHB/HCLK:

```
T_clk = 1 / f_cpu
```

Розглянемо, як співвідноситься період такту з часом доступу матриці Flash (`T_access ≈ 30 нс`) на різних частотах роботи мікроконтролера:

* **При `f_cpu = 16 МГц`:** Період такту `T_clk = 62.5 нс`. Оскільки `62.5 нс > 30 нс`, матриця Flash встигає повністю завершити розряджання бітових ліній та спрацьовування підсилювачів задовго до завершення поточного такту. Дані фіксуються ядром за **1 такт шини**. Такий режим називається доступом із нульовими тактами очікування — **0 Wait States (0WS)**.
* **При `f_cpu = 84 МГц`:** Період такту `T_clk = 11.9 нс`. За один такт матриця встигає виконати лише третину циклу зчитування. Щоб отримати валідні дані, шинний інтерфейс повинен подовжити транзакцію на 3 повні такти (`3 · 11.9 нс = 35.7 нс`). Це означає 1 початковий такт запиту плюс **2 такти очікування (2WS)**.
* **При `f_cpu = 168 МГц`:** Період такту `T_clk = 5.95 нс`. За один такт сигнал навіть не встигне поширитися по словарній лінії. Щоб набрати необхідні 30 нс, потрібно витратити `ceil(30 / 5.95) = 6` тактів шини (`6 · 5.95 нс = 35.7 нс`). Це вимагає конфігурації **5 тактів очікування (5WS)**.
* **При `f_cpu = 480 МГц` (Cortex-M7 / Cortex-M85):** Період такту `T_clk = 2.08 нс`. Час доступу матриці Flash вимагає конфігурації від **8 до 10 тактів очікування (8–10WS)**.

Узагальнена формула для розрахунку необхідної кількості тактів очікування:

```
Загальна тривалість вибірки N_cycles = ceil(T_access / T_clk)
Wait States (WS / Latency)           = N_cycles - 1
```

Кількість тактів очікування програмується у спеціальному регістрі керування контролера Flash — `FLASH_ACR` (Flash Access Control Register) або його апаратних аналогах в інших родинах процесорів. Детальний опис бітових полів, адрес та регістрової карти наведено у вставці [Регістри затримок Flash та конфігурація живлення](root:hw-arch/zatrymky-chytannia-flesh-pamiati-i-taktova-chastota/api-flash-latency-registers.md).

> 🔧 **Навіщо це.** Якщо процесор зчитує шину безпосередньо без вставки необхідної кількості `Wait States`, ядро захоплює значення бітових ліній у момент, коли сенсорний підсилювач ще знаходиться в невизначеному стані або перехідному процесі. Вхідний декодер інструкцій отримує псевдовипадкову комбінацію бітів. Якщо ця комбінація не відповідає жодній інструкції Thumb-2, ядро генерує `Undefined Instruction UsageFault`; якщо спотворена адреса переходу чи операнда пам'яті — `BusFault` через неіснуючу або невирівняну адресу.

## Вплив напруги живлення на затримки Flash

Час доступу до Flash-матриці не є абсолютною константою для конкретного кристала: він безпосередньо залежить від робочої напруги живлення ядра (Vdd).

Коли напруга живлення знижується (наприклад, при живленні від батареї, що розряджається), затримки зростають з двох фундаментальних фізичних причин:
1. **Зниження струму насичення транзисторів:** Струм стоку польового транзистора комірки `I_cell` пропорційний квадрату різниці між напругою на затворі та пороговою напругою `(V_gs - V_th)²`. При зниженні живлення з 3.3 В до 1.8 В струм комірки зменшується більш ніж утричі, і час розряджання ємності бітової лінії `t_discharge` зростає з 15 нс до 35–45 нс.
2. **Зниження крутизни характеристики сенсорного підсилювача:** Диференційні каскади компараторів працюють повільніше при низькій напрузі живлення, додаючи ще кілька наносекунд до `t_sense`.

Як наслідок, один і той самий мікроконтролер на одній і тій самій частоті вимагає різної кількості тактів очікування залежно від діапазону напруги живлення:

```
Частота f_cpu = 120 МГц (T_clk = 8.33 нс):
При Vdd = 2.7 В – 3.6 В (T_access ≈ 30 нс): ceil(30 / 8.33) - 1 = 3 WS
При Vdd = 1.8 В – 2.1 В (T_access ≈ 55 нс): ceil(55 / 8.33) - 1 = 6 WS
```

Саме тому в мікроконтролерах із вбудованим регулятором напруги (Voltage Scaling) зміна рівня внутрішнього живлення ядра (регістр `PWR_CR`, поле `VOS`) завжди повинна узгоджуватися з перерахунком затримок у `FLASH_ACR`.

## Безпечний порядок перемикання тактової частоти

Під час переналаштування системи тактування мікроконтролера (наприклад, під час старту або динамічної зміни продуктивності) зміна тактової частоти та затримок Flash підпорядковується залізному правилу пріоритету: **затримка Flash завжди повинна бути достатньою для найвищої частоти, яка діє на даному етапі**.

Порушення цього порядку є однією з найпоширеніших критичних помилок низькорівневого програмування.

![Порядок конфігурації частоти й затримок](/root/hw/hw-arch/zatrymky-chytannia-flesh-pamiati-i-taktova-chastota/img/frequency-scaling-order.svg)
*Безпечна послідовність зміни тактової частоти: при розгоні спершу збільшується затримка Flash, а потім вмикається PLL; при гальмуванні спершу знижується частота, а потім зменшується затримка Flash.*

### Сценарій 1: Підвищення тактової частоти (Розгін системи)

При переході від низької частоти (16 МГц, 0WS) до високої частоти (168 МГц, 5WS):

1. **Крок 1: Збільшення затримки Flash Latency.** У регістр `FLASH_ACR` записується значення `5WS`. Оскільки ядро все ще працює на повільній частоті 16 МГц, кожне зчитування тепер триватиме 6 повільних тактів (`6 · 62.5 нс = 375 нс`). Процесор тимчасово сповільнюється, але продовжує коректно і стабільно виконувати інструкції.
2. **Крок 2: Обов'язкова перевірка фіксації бітів (Read-back polling).** Контролер Flash має внутрішній шинний конвеєр. Команда запису у `FLASH_ACR` може перебувати в буфері запису AHB. Необхідно в циклі зчитувати `FLASH_ACR`, доки біти `LATENCY` не повернуть нове значення `0b0101`.
3. **Крок 3: Конфігурація та запуск PLL.** Налаштовуються коефіцієнти множення та ділення генератора PLL. Вмикається біт `RCC_CR.PLLON`, і програма очікує підняття апаратного прапорця стабілізації `RCC_CR.PLLRDY`.
4. **Крок 4: Перемикання системного тактування.** Регістр вибору джерела такту `RCC_CFGR.SW` перемикається на вихід PLL. Ядро миттєво починає цокати на частоті 168 МГц, і оскільки контролер Flash уже налаштований на 5WS, вибірка інструкцій продовжується без жодного збою.

### Сценарій 2: Зниження тактової частоти (Гальмування / Енергозбереження)

При поверненні з 168 МГц (5WS) на 16 МГц (0WS) послідовність дій дзеркально розвертається:

1. **Крок 1: Перемикання джерела тактування на низьку частоту.** Мультиплексор `RCC_CFGR.SW` перемикається на джерело HSI/HSE. Програма очікує, поки статусний біт `RCC_CFGR.SWS` підтвердить успішне перемикання. Ядро вже працює на 16 МГц, тоді як Flash все ще має конфігурацію 5WS.
2. **Крок 2: Вимкнення або переналаштування PLL.** За потреби вимикається біт `PLLON` для збереження енергії.
3. **Крок 3: Зменшення затримки Flash Latency.** Лише тепер, коли частота вже гарантовано низька, у `FLASH_ACR` записується значення `0WS`, що повертає систему до однотактового доступу.
4. **Крок 4: Підтвердження фіксації 0WS через зчитування `FLASH_ACR`.**

> ⚠️ **Що станеться при порушенні порядку:** Якщо розробник спробує спочатку перемкнути такт на 168 МГц, а рядок `FLASH_ACR->LATENCY = 5` поставити наступним, процесор зависне під час виконання самої інструкції перемикання частоти. Наступною інструкцією конвеєра ядра є вибірка адреси регістра Flash, але на частоті 168 МГц за 0WS Flash поверне сміття, і ядро впаде в апаратний збій, так і не дійшовши до команди зміни затримки.

## Анатомія падіння швидкодії: чому затримки Flash руйнують конвеєр

Розглянемо процесорне ядро Cortex-M4 із 3-стадійним конвеєром: вибірка інструкції (Fetch), декодування (Decode), виконання (Execute).

В ідеальних умовах (виконання з нульовими затримками пам'яті, 0WS) на кожному такті завершується одна інструкція. Показник темпу виконання інструкцій за такт — IPC (англ. *Instructions Per Cycle*) — наближається до `1.0`.

![Виконання інструкцій у конвеєрі](/root/hw/hw-arch/zatrymky-chytannia-flesh-pamiati-i-taktova-chastota/img/flash-vs-ram-execution.svg)
*Порівняння конвеєра: Flash 5WS без кешу спричиняє бульбашки простою (Stall Bubbles); Flash з прискорювачем ART виконує лінійний код та цикли за 1 такт (0WS Equivalent); RAM забезпечує детермінований 1 такт без джиттеру.*

Що відбувається, коли ядро змушене читати кожну 32-бітну інструкцію безпосередньо з Flash-пам'яті із затримкою 5WS:

1. Стадія вибірки виставляє адресу на шину I-Code і завмирає на **6 тактів** (1 такт запиту + 5 тактів очікування).
2. Стадії декодування та виконання залишаються без вхідних даних і простоюють. У конвеєрі утворюється 5 тактів порожніх «бульбашок простою» (англ. *pipeline stall bubbles*).
3. Після отримання інструкції ядро декодує та виконує її за 1 такт.
4. Для наступної інструкції цикл повторюється: знову 5 тактів очікування.

Розрахуємо ефективний темп виконання інструкцій:

```
Час на одну інструкцію = 1 (виконання) + 5 (затримка Flash) = 6 тактів
IPC                    = 1 / 6 ≈ 0.167
Ефективна швидкодія    = 168 МГц · 0.167 = 28 MIPS
```

Виникає парадоксальна ситуація: розробник підняв тактову частоту кристала з 16 МГц до 168 МГц (більш ніж удесятеро), енергоспоживання цифрової логіки зросло пропорційно частоті, але реальна обчислювальна потужність процесора залишилася на рівні 28 МГц. Дорогий високочастотний процесор витрачає понад 83% свого часу на очікування відповіді повільної матриці Flash.

## Розширення шини матриці та буфер попередньої вибірки (Prefetch)

Для вирішення проблеми простою конвеєра розробники мікроконтролерів застосовують перший рівень апаратної оптимізації — розширення внутрішньої шини Flash-матриці та буферизацію вибірки.

Шина інструкцій ядра Cortex-M (шина I-Code) є 32-бітною: за одне звертання вона здатна прийняти одне 32-бітне слово (дві 16-бітні інструкції Thumb або одну 32-бітну інструкцію Thumb-2). Проте фізичний масив вбудованої Flash-пам'яті роблять значно ширшим — **128 біт або 256 біт** на одне звертання (плюс додаткові біти для апаратного коду корекції помилок ECC).

![Блок-схема апаратного прискорювача ART Accelerator](/root/hw/hw-arch/zatrymky-chytannia-flesh-pamiati-i-taktova-chastota/img/art-accelerator-block.svg)
*Архітектура прискорювача Flash: 128-бітна внутрішня шина масиву, буфер випереджального читання (Prefetch), 64-рядковий кеш інструкцій та 8-рядковий кеш даних.*

Коли контролер Flash виконує одне повільне звертання тривалістю 6 тактів, він вичитує з матриці не 32 біти, а відразу **128 біт** (4 повних 32-бітних слова або до восьми 16-бітних інструкцій).

Ці 128 біт завантажуються в **буфер попередньої вибірки (Instruction Prefetch Buffer)**:

1. **Такт 1–6:** Контролер Flash вичитує блок із 128 біт. Ядро отримує перші 32 біти коду і починає їх виконання.
2. **Такт 7:** Ядро запитує наступні 32 біти. Оскільки вони вже знаходяться у 128-бітному буфері Prefetch, вони передаються ядру **миттєво за 1 такт (0WS)**.
3. **Такт 8–9:** Наступні слова вичитуються з буфера також за 1 такт.
4. **Паралельна вибірка у фоні:** Поки ядро послідовно виконує інструкції з поточного буфера, контролер Flash у фоновому режимі (англ. *pipelined background read*) заздалегідь запускає зчитування наступного 128-бітного блоку матриці. Коли ядро дійде до кінця поточного рядка, наступний блок уже готовий у буфері.

Для строго лінійного коду буфер Prefetch згладжує затримки майже до нуля: один раз сплативши 5 тактів очікування на старті, процесор далі виконує послідовні інструкції з темпом, близьким до 1 інструкції за такт.

### Межа ефективності буфера Prefetch: штраф за перехід (Branch Penalty)

Буфер випереджального читання ідеально працює лише доти, доки потік виконання команд є неперервним і лінійним. Проте реальний програмний код містить велику кількість розгалужень:
* Умовні переходи (`if / else`, команди `BNE`, `BEQ`);
* Цикли (`for`, `while`, команди `B`, `CBZ`);
* Виклики функцій та повернення (`BL`, `BLX`, `BX LR`);
* Обробники переривань.

Щойно процесор виконує інструкцію переходу, програмний лічильник (PC) змінює свою адресу на довільне значення. Дані, які буфер Prefetch старанно вичитував із наступних послідовних адрес, стають абсолютно непотрібними.

Конвеєр ядра та буфер вибірки повністю скидаються (англ. *pipeline flush*), і процесор зазнає повного апаратного штрафу: шина зупиняється на 6 тактів для нового звертання до Flash за новою цільовою адресою переходу. Якщо в тісному циклі виконується всього 3–4 інструкції з переходом на початку та в кінці, ефективність Prefetch падає до базового рівня без оптимізацій.

## Апаратний кеш інструкцій та даних: прискорювач ART та еквівалент 0WS

Щоб усунути штрафи за переходи у повторюваних ділянках коду, виробники мікроконтролерів інтегрують у контролер Flash повноцінні апаратні кеш-пам'яті. Найвідомішим прикладом такої архітектури є прискорювач **ART Accelerator (Adaptive Real-Time Accelerator)** у мікроконтролерах STM32 родини Cortex-M4/M7, а також аналогічні кеш-модулі в чіпах NXP LPC, Microchip SAM та TI MSPM0.

Прискорювач ART містить два спеціалізованих кеш-масиви:
1. **Кеш інструкцій (Instruction Cache, I-Cache):** Масив швидкої статичної пам'яті SRAM об'ємом 1 Кбайт, організований у вигляді 64 рядків по 128 біт кожен. Кожен рядок забезпечений апаратною схемою порівняння тегів (англ. *tag comparator*). Кеш є повністю асоціативним.
2. **Кеш даних та констант (Data Cache, D-Cache):** Масив об'ємом 128 байтів (8 рядків по 128 біт), підключений до шини D-Code. Він кешує незмінні літеральні пули, константи та таблиці переходів, розміщені компілятором у секції `.rodata` у Flash-пам'яті.

### Механізм роботи кешу ART

Коли ядро запитує адресу інструкції через шину I-Code:

1. Контролер порівнює старші біти адреси з тегами всіх 64 рядків кешу за 1 такт.
2. **Влучання в кеш (Cache Hit):** Якщо рядок із цією адресою вже завантажувався раніше (наприклад, це тіло циклу, функція фільтрації або обробник переривання), 128-бітне слово видається з кеш-пам'яті SRAM за **1 такт (0WS)**. Ніякого звертання до повільної матриці Flash не відбувається взагалі.
3. **Промах кешу (Cache Miss):** Якщо адреси в кеші немає, контролер за 6 тактів вичитує 128-бітний блок із Flash-матриці, передає запитане слово ядру, а весь 128-бітний рядок разом із тегом зберігає в одній із вільних ліній кешу за алгоритмом заміщення (зазвичай псевдо-LRU — Least Recently Used).

Оскільки більшість алгоритмів обробки сигналів, керування та обчислень проводять понад 90% часу у відносно компактних циклах, коефіцієнт влучань у кеш (англ. *Cache Hit Ratio*) у реальних прошивках перевищує **95–98%**.

Завдяки цьому процесор досягає показника швидкодії **0WS Equivalent**: реальна продуктивність ядра на частоті 168 МГц сягає 210 CoreMark / 1.25 DMIPS/МГц — рівно стільки ж, скільки ядро видавало б при роботі з ідеальної беззатримкової пам'яті.

## Інвалідація кешів та узгодженість при самомодифікації

Апаратний кеш Flash оптимізований виключно для операцій швидкого читання. Контролер Flash апаратно не відстежує операції запису у Flash, які виконуються через спеціальний контролер програмування (`FLASH_CR`).

Це породжує критичну проблему кеш-когерентності (узгодженості даних) у системах із самопрограмуванням:
* Внутрішньосхемне оновлення прошивки (In-Application Programming, IAP);
* Робота завантажувача (Bootloader);
* Збереження калібрувальних коефіцієнтів або налаштувань у спеціальний сектор Flash під час роботи пристрою.

Якщо мікроконтролер перезаписав сторінку Flash-пам'яті новими даними або новим машинним кодом, фізичний вміст матриці змінився, але у 64 рядках кешу ART та в буфері Prefetch залишаються старі копії 128-бітних слів. Якщо ядро спробує виконати новий код або прочитати оновлені константи без попереднього очищення кешу, прискорювач віддасть застарілі інструкції з ліній кешу (`Hit`), що призведе до виконання непередбачуваного коду або спотворення даних.

Для вирішення цієї проблеми інтерфейс Flash надає механізм примусової програмної інвалідації (скидання) кешів:

:::tabs
```c
/* Безпечна інвалідація кешу інструкцій та даних у C */
void flash_cache_flush(void) {
    /* 1. Тимчасово вимикаємо кеші (біти ICEN та DCEN скидаються в 0) */
    FLASH_ACR_REG &= ~(FLASH_ACR_ICEN_BIT | FLASH_ACR_DCEN_BIT);

    /* 2. Подаємо команду скидання тегів (запис 1 у біти ICRST та DCRST) */
    FLASH_ACR_REG |= (FLASH_ACR_ICRST_BIT | FLASH_ACR_DCRST_BIT);

    /* 3. Очищаємо біти скидання */
    FLASH_ACR_REG &= ~(FLASH_ACR_ICRST_BIT | FLASH_ACR_DCRST_BIT);

    /* 4. Вмикаємо кеші назад для нових звертань */
    FLASH_ACR_REG |= (FLASH_ACR_ICEN_BIT | FLASH_ACR_DCEN_BIT);
}
```
```cpp
/* Безпечна інвалідація кешу інструкцій та даних у C++ */
namespace mcu::flash {

inline void cache_flush() noexcept {
    auto& acr = *reinterpret_cast<volatile uint32_t*>(0x40023C00U);
    constexpr uint32_t IcenBit  = 1U << 9;
    constexpr uint32_t DcenBit  = 1U << 10;
    constexpr uint32_t IcrstBit = 1U << 11;
    constexpr uint32_t DcrstBit = 1U << 12;

    /* Вимикаємо кеші перед скиданням тегів */
    acr &= ~(IcenBit | DcenBit);
    acr |= (IcrstBit | DcrstBit);
    acr &= ~(IcrstBit | DcrstBit);
    acr |= (IcenBit | DcenBit);
}

} // namespace mcu::flash
```
:::

Інвалідація кешів є обов'язковою процедурою перед передачею керування новому завантаженому образу прошивки у будь-якому завантажувачі.

## Виконання критичного коду з RAM: детермінізм проти стохастики кешу

Незважаючи на високу середню ефективність прискорювача ART, робота кешу має фундаментальну особливість: вона є **стохастичною (ймовірнісною)**.

Час виконання інструкції з Flash з увімкненим кешем залежить від передісторії:
* Якщо рядок знаходиться в кеші (`Hit`) — час вибірки становить **1 такт**.
* Якщо рядок був витіснений іншим кодом або перериванням (`Miss`) — час вибірки становить **6 тактів**.

Ця різниця в 5 тактів на першій інструкції створює **часовий джиттер (англ. *jitter* — тремтіння затримки)**. Для звичайних прикладних задач цей джиттер непомітний. Але в системах жорсткого реального часу він є неприпустимим:
* **Векторне керування електродвигунами (FOC — Field Oriented Control):** Обробник переривання АЦП вимірює струми фаз і повинен за фіксовану кількість наносекунд розрахувати ШІМ-кути. Промах кешу призводить до нерівномірності дискретизації контуру струму та акустичного шуму двигуна.
* **Переривання захоплення швидких сигналів:** Обробка сигналів енкодерів або аварійного захисту силових ключів (Short Circuit Protection).
* **Програмування самої Flash-пам'яті:** Під час виконання операції стирання або запису сектору Flash вся внутрішня матриця блокується контролером на читання (прапорець `FLASH_SR.BSY = 1`). Якщо в цей момент ядро спробує виконати хоча б одну інструкцію з Flash, шина заблокується, і процесор зависне намертво. Тому код запису Flash **зобов'язаний** виконуватися з оперативної пам'яті SRAM.

Оперативна пам'ять SRAM позбавлена кеш-промахів: вона відповідає за чесний **1 такт шини (0WS)** абсолютно завжди, забезпечуючи 100% математичний детермінізм часу виконання алгоритму.

## Організація релокації функцій у RAM

Для розміщення критичних функцій в оперативній пам'яті використовується механізм релокації компілятора та компонувальника (Linker).

### Крок 1: Маркування функції в коді C/C++

Функція позначається атрибутом розміщення в спеціальній секції (зазвичай `.ramfunc`):

:::tabs
```c
/* Оголошення функції для виконання з RAM у C */
__attribute__((noinline, section(".ramfunc")))
void Critical_Motor_ISR(void) {
    /* Алгоритм швидкого регулятора струму */
    GPIO_PORT->BSRR = GPIO_PIN_0; // 1 такт, детерміновано
}
```
```cpp
/* Оголошення функції для виконання з RAM у C++ */
namespace control {

[[gnu::noinline, gnu::section(".ramfunc")]]
void critical_motor_isr() noexcept {
    /* Алгоритм швидкого регулятора струму */
    // Детерміноване виконання без затримок Flash
}

} // namespace control
```
:::

### Крок 2: Налаштування скрипта компонувальника (Linker Script)

Компонувальнику необхідно повідомити дві різні адреси для секції `.ramfunc`:
* **LMA (Load Memory Address):** Фізична адреса зберігання байтів машинної програми всередині Flash-пам'яті (щоб прошивка не зникала при вимкненні живлення).
* **VMA (Virtual/Execution Memory Address):** Адреса в оперативній пам'яті SRAM або CCMRAM, за якою функція буде виконуватися, і до якої прив'язуються всі абсолютні та відносні переходи.

```ld
/* Фрагмент Linker Script (.ld) */
SECTIONS
{
  .ramfunc :
  {
    . = ALIGN(4);
    _sramfunc = .;          /* Символ початку секції в RAM (VMA) */
    *(.ramfunc)
    *(.ramfunc*)
    . = ALIGN(4);
    _eramfunc = .;          /* Символ кінця секції в RAM (VMA) */
  } >CCMRAM AT>FLASH        /* Виконання в CCMRAM, зберігання у FLASH */

  _si_ramfunc = LOADADDR(.ramfunc); /* LMA адреса у Flash */
}
```

### Крок 3: Копіювання коду під час стартапу програми

Перед тим як функція буде викликана вперше, її машинний код має бути скопійований із адреси LMA у Flash за адресою VMA у RAM. Це виконується у функції системного скидання (`Reset_Handler`) або на початку `main()`:

:::tabs
```c
/* Копіювання секції .ramfunc у C */
extern uint32_t _si_ramfunc; /* Початок у Flash */
extern uint32_t _sramfunc;    /* Початок у RAM */
extern uint32_t _eramfunc;    /* Кінець у RAM */

void copy_ramfunc_to_ram(void) {
    uint32_t *src = &_si_ramfunc;
    uint32_t *dst = &_sramfunc;
    while (dst < &_eramfunc) {
        *dst++ = *src++;
    }
    __DSB();
    __ISB();
}
```
```cpp
/* Копіювання секції .ramfunc у C++ */
#include <cstdint>

extern "C" {
    extern uint32_t _si_ramfunc;
    extern uint32_t _sramfunc;
    extern uint32_t _eramfunc;
}

namespace mcu::startup {

inline void copy_ramfunc() noexcept {
    const uint32_t* src = &_si_ramfunc;
    uint32_t* dst = &_sramfunc;
    while (dst < &_eramfunc) {
        *dst++ = *src++;
    }
    asm volatile("dsb 0xF" ::: "memory");
    asm volatile("isb 0xF" ::: "memory");
}

} // namespace mcu::startup
```
:::

Після виконання цього копіювання будь-який виклик функції `Critical_Motor_ISR()` виконується безпосередньо з високошвидкісної пам'яті SRAM/CCMRAM із нульовою затримкою.

## Повний драйвер конфігурації Flash та практичні вимірювання швидкодії

Нижче наведено практичну реалізацію модуля безпечного налаштування Flash Latency, ініціалізації прискорювачів та перемикання системи тактування на мовах C та C++.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

#define FLASH_ACR_REG     (*(volatile uint32_t *)0x40023C00U)
#define RCC_CR_REG        (*(volatile uint32_t *)0x40023800U)
#define RCC_CFGR_REG      (*(volatile uint32_t *)0x40023808U)

#define FLASH_ACR_LATENCY_5WS (5U)
#define FLASH_ACR_PRFTEN      (1U << 8)
#define FLASH_ACR_ICEN        (1U << 9)
#define FLASH_ACR_DCEN        (1U << 10)

#define RCC_CR_PLLON          (1U << 24)
#define RCC_CR_PLLRDY         (1U << 25)
#define RCC_CFGR_SW_PLL       (2U)
#define RCC_CFGR_SWS_MASK     (0x0CU)
#define RCC_CFGR_SWS_PLL      (0x08U)

/* Безпечний перехід на високу частоту 168 МГц */
bool system_clock_scale_up_168mhz(void) {
    /* 1. СПЕРШУ збільшуємо затримку Flash до 5WS та вмикаємо кеші */
    FLASH_ACR_REG = FLASH_ACR_LATENCY_5WS | FLASH_ACR_PRFTEN | 
                    FLASH_ACR_ICEN | FLASH_ACR_DCEN;

    /* 2. Очікуємо фіксації затримки 5WS */
    uint32_t timeout = 5000U;
    while ((FLASH_ACR_REG & 0x0FU) != FLASH_ACR_LATENCY_5WS) {
        if (--timeout == 0U) return false;
    }

    /* 3. Запускаємо PLL (передбачається, що дільники PLLM/PLLN/PLLP вже налаштовані) */
    RCC_CR_REG |= RCC_CR_PLLON;
    timeout = 10000U;
    while (!(RCC_CR_REG & RCC_CR_PLLRDY)) {
        if (--timeout == 0U) return false;
    }

    /* 4. Перемикаємо системний такт на вихід PLL */
    uint32_t cfgr = RCC_CFGR_REG;
    cfgr &= ~0x03U;
    cfgr |= RCC_CFGR_SW_PLL;
    RCC_CFGR_REG = cfgr;

    /* 5. Очікуємо підтвердження перемикання джерела тактування */
    timeout = 5000U;
    while ((RCC_CFGR_REG & RCC_CFGR_SWS_MASK) != RCC_CFGR_SWS_PLL) {
        if (--timeout == 0U) return false;
    }

    return true;
}
```

```cpp
#include <cstdint>

namespace mcu::system {

class ClockManager {
private:
    static constexpr uintptr_t FlashAcrAddr = 0x40023C00U;
    static constexpr uintptr_t RccCrAddr    = 0x40023800U;
    static constexpr uintptr_t RccCfgrAddr  = 0x40023808U;

    static constexpr uint32_t Latency5Ws = 5U;
    static constexpr uint32_t Prften     = 1U << 8;
    static constexpr uint32_t Icen       = 1U << 9;
    static constexpr uint32_t Dcen       = 1U << 10;

    static constexpr uint32_t PllOn      = 1U << 24;
    static constexpr uint32_t PllRdy     = 1U << 25;
    static constexpr uint32_t SwPll      = 2U;
    static constexpr uint32_t SwsMask    = 0x0CU;
    static constexpr uint32_t SwsPll     = 0x08U;

    static auto& flash_acr() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(FlashAcrAddr);
    }
    static auto& rcc_cr() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(RccCrAddr);
    }
    static auto& rcc_cfgr() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(RccCfgrAddr);
    }

public:
    [[nodiscard]] static bool scale_up_to_168mhz() noexcept {
        /* 1. Спершу збільшуємо затримку Flash */
        flash_acr() = Latency5Ws | Prften | Icen | Dcen;

        uint32_t timeout = 5000U;
        while ((flash_acr() & 0x0FU) != Latency5Ws) {
            if (--timeout == 0U) return false;
        }

        /* 2. Запуск PLL */
        rcc_cr() |= PllOn;
        timeout = 10000U;
        while (!(rcc_cr() & PllRdy)) {
            if (--timeout == 0U) return false;
        }

        /* 3. Перемикання системного такту */
        auto cfgr = rcc_cfgr();
        cfgr &= ~0x03U;
        cfgr |= SwPll;
        rcc_cfgr() = cfgr;

        timeout = 5000U;
        while ((rcc_cfgr() & SwsMask) != SwsPll) {
            if (--timeout == 0U) return false;
        }

        return true;
    }
};

} // namespace mcu::system
```

## Архітектурна піраміда пам'яті мікроконтролера

Сучасний високопродуктивний мікроконтролер являє собою збалансований компроміс між вартістю кристала, щільністю збереження даних та швидкодією:

1. **Вершина піраміди — регістри ядра та пам'ять TCM/CCMRAM (0WS, 1 такт):** Мінімальний об'єм (від 16 до 128 Кбайт), максимальна ціна за біт, нульові затримки, повний детермінізм. Призначена для стека, таблиці векторів переривань та критичних функцій жорсткого реального часу.
2. **Середній рівень — буфери Prefetch та кеш ART / L1 Cache (0WS Equivalent):** Кілька кілобайтів надшвидкої пам'яті тегів і ліній кешу, які закривають 95% звертань до інструкцій під час виконання циклів.
3. **Основа піраміди — матриця вбудованої Flash-пам'яті (5–8WS, 20–30 нс):** Великий об'єм (від 512 Кбайт до 4 Мбайт), висока щільність, енергонезалежність. Завдяки широкій внутрішній шині (128–256 біт) та кешуванню вона забезпечує зберігання всього монолітного коду програми без катастрофічної втрати швидкодії ядра.
