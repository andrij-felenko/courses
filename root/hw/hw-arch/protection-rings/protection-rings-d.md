Якщо процесор завантажує з пам'яті команду вимкнення переривань або наказ перепрограмувати контролер прямого доступу до пам'яті (DMA), кристал виконує операцію за лічені наносекунди. Для арифметико-логічного пристрою та конвеєра інструкцій немає різниці між додаванням двох чисел у регістрах і записом у керівний регістр живлення системи: вхідний опкод декодується у керуючі сигнали на шинах. Проте якщо випадковий браузерний скрипт або помилковий потік користувацької програми виконає команду зупинки ядра `hlt` чи зітре кореневу таблицю сторінок пам'яті, вся обчислювальна система негайно втратить працездатність. У чистому фон-нейманівському процесорі без додаткових апаратних вузлів захистити систему неможливо: будь-який код, що потрапив на конвеєр, володіє машиною беззастережно.

Апаратна безпека починається з одного кремнієвого фіксатора всередині блоку декодування та керування процесора — апаратного регістра поточного рівня привілеїв. Цей стан ділить простір виконання на ізольовані домени. Кожна інструкція та кожне звернення до пам'яті проходять крізь комбінаційну схему перевірки прав: якщо код без належного привілею намагається виконати системну дію, апаратура блокує наказ на конвеєрі й викликає внутрішній апаратний виняток (пастку). Програмний код неспроможний обійти цю перевірку, оскільки вона впаяна у схему вибірки та виконання команд.

Потреба в такому розмежуванні виникла ще на світанку багатокористувацьких систем: [історичний розвиток від 64 програмних кілець Multics до апаратних рівнів](root:hw-arch/protection-rings/hist-rings-multics.md) показує, як інженери шукали баланс між кількістю рівнів захисту та складністю кремнієвої логіки. Переконатися у непохитності цієї апаратної межі можна експериментально: [практичний експеримент зі зчитування власного рівня та обробки процесорних відмов](root:hw-arch/protection-rings/proj-privileged-trap.md) демонструє, як ядро операційної системи ловить відхилені процесором інструкції.

## 1. Ієрархія кілець захисту x86

В архітектурі x86 класична модель захисту реалізована у вигляді чотирьох концентричних кілець — від Ring 0 (найвищий привілей) до Ring 3 (найнижчий привілей). Хоча мікропроцесор Intel 80286 заклав у кремній усі чотири рівні, сучасні операційні системи загального призначення (Linux, Windows, macOS) використовують переважно дворівневу плоску модель: Ring 0 для ядра ОС і драйверів апаратури (Kernel space) та Ring 3 для користувацьких процесів і бібліотек (User space). Кільця Ring 1 та Ring 2, первинно призначені для проміжних системних служб та драйверів файлових систем, практично не використовуються через несумісність із моделями сторінкового захисту пам'яті інших процесорних архітектур (ARM, MIPS, RISC-V), де апаратно доступні лише два рівні привілеїв виконання коду користувача та ядра.

![Апаратна перевірка привілеїв x86](/root/hw/hw-arch/protection-rings/img/x86-privilege-check.svg)
*Апаратна перевірка привілеїв в архітектурі x86: взаємодія поточного рівня CPL у селекторі коду CS, запитаного рівня RPL та дескрипторного рівня DPL у таблицях GDT/IDT під час звернення до даних і переходу між кільцями.*

### Поля CPL, DPL та RPL у сегментній логіці

Поточний рівень виконання коду не зберігається в окремому реєстрі загального призначення. В архітектурі x86 діє система трьох взаємопов'язаних числових міток:

1. **CPL (Current Privilege Level)** — поточний рівень привілеїв процесора. Він фізично розміщений у двох молодших бітах (біти 0–1) регістрів селекторів сегментів коду `CS` та стека `SS`. Значення `00b` відповідає Ring 0, а `11b` — Ring 3. Процесор гарантує, що `CPL` завжди дорівнює привілею дескриптора кодового сегмента, з якого вибираються інструкції.
2. **DPL (Descriptor Privilege Level)** — рівень привілеїв дескриптора. Записаний у бітах 13–14 дескриптора сегмента в глобальній (GDT) чи локальній (LDT) таблиці дескрипторів, а також у дескрипторах шлюзів виклику (Call Gates) і переривань (IDT). DPL визначає мінімальний привілей, необхідний для доступу до сегмента.
3. **RPL (Requested Privilege Level)** — запитаний рівень привілеїв. Міститься в бітах 0–1 будь-якого 16-бітного селектора сегмента, що завантажується в регістри `DS`, `ES`, `FS`, `GS` або передається як параметр виклику. RPL дозволяє привілейованому коду ядра знизити власний ефективний привілей до рівня того, хто звернувся із запитом, щоб уникнути атак класу «заплутаний заступник».

Апаратна схема перевірки доступу до сегмента даних виконує суворе логічне порівняння:

```text
Ефективний рівень = max(CPL, RPL)
Умова доступу:     Ефективний рівень <= DPL сегмента даних
```

Оскільки менше числове значення відповідає вищому привілею (0 > 1 > 2 > 3), код користувача з `CPL = 3` неспроможний завантажити в сегментний регістр селектор із `DPL = 0`, `1` або `2`. Будь-яка спроба такого завантаження негайно спричиняє апаратне виключення загального захисту `#GP` (General Protection Fault, вектор 13).

Для виконання коду в іншому сегменті правила ще суворіші. Прямий стрибок (`jmp` або звичайний `call`) у непідпорядкований (non-conforming) кодовий сегмент вимагає точної рівності: `CPL == DPL` та `RPL <= DPL`. Підвищити привілей за допомогою звичайної інструкції стрибка чи виклику неможливо: кремнієва логіка забороняє зміну `CS` на кодовий дескриптор із вищим привілеєм.

### Механізм перемикання стеків і TSS

Привілейований код ядра ніколи не може виконуватися на стеку, який надала непривілейована програма: якщо стек користувача переповнений, пошкоджений або розташований у спільній пам'яті, збереження регістрів ядра призведе до порушення безпеки або зависання процесора. Тому перехід між кільцями завжди супроводжується апаратним перемиканням покажчика стека.

Для цього процесор використовує сегмент стану задачі — **TSS (Task State Segment)**. В 64-бітному режимі (x86-64 / Long Mode) структура TSS містить обов'язкові 64-бітні поля `RSP0`, `RSP1`, `RSP2`, а також таблицю покажчиків стеків для переривань — IST (Interrupt Stack Table).

Коли процесор переходить із Ring 3 у Ring 0:
1. Апаратура автоматично зчитує безпечну адресу верхівки стека ядра з поля `RSP0` поточного TSS.
2. Процесор зберігає на цей новий стек ядра контекст попереднього рівня: старий селектор стека `SS`, старий покажчик стека `RSP`, прапорці `RFLAGS`, селектор коду `CS` та лічильник команд `RIP`.
3. У регістр `CS` завантажується селектор коду ядра з `CPL = 0`, у `SS` — селектор стека ядра.
4. Керування передається на точку входу системного обробника.
5. Зворотний перехід у Ring 3 виконується інструкцією `iretq`, яка витягує збережений кадр зі стека ядра, відновлює старі `RSP` і `SS`, атомарно знижуючи `CPL` до 3.

### Еволюція системних переходів: від `int 0x80` до `syscall`

Історично перехід із Ring 3 у Ring 0 здійснювався через програмне переривання `int 0x80` (у Linux) або `int 0x2e` (у Windows NT). Цей шлях вимагав повного циклу обробки через таблицю дескрипторів переривань (IDT): процесор зчитував дескриптор шлюзу з пам'яті, перевіряв права шлюзу (`DPL_шлюзу == 3`), зчитував TSS, змінював сегменти та зберігав на стек щонайменше 5 регістрів. Такий перехід займав сотні тактів процесора.

Для усунення цих накладних витрат було впроваджено інструкції швидкого системного виклику, які оминають таблиці IDT та TSS:

- **SYSENTER / SYSEXIT** (введено Intel у Pentium II): налаштовуються через модельні регістри процесора (MSR): `IA32_SYSENTER_CS` (0x174), `IA32_SYSENTER_ESP` (0x175) та `IA32_SYSENTER_EIP` (0x176). При виклику `sysenter` процесор миттєво встановлює `CPL = 0`, завантажує заздалегідь відомий `ESP` і `EIP` без збереження зворотного контексту на стек (збереження адреси повернення покладається на програмний код у регістрах).
- **SYSCALL / SYSRET** (стандарт x86-64, розроблений AMD): використовує спеціалізовані MSR-регістри:
  - `MSR_STAR` (0xC0000081) — містить селектори коду й стека для переходів у Ring 0 та Ring 3.
  - `MSR_LSTAR` (0xC0000082, Long Mode Target Address) — містить абсолютну 64-бітну адресу входу в ядро ОС.
  - `MSR_SFMASK` (0xC0000084, System Call Flag Mask) — бітова маска прапорців, які апаратно скидаються в `RFLAGS` під час виклику (зокрема біт `IF` для тимчасового вимкнення апаратних переривань).

Інструкція `syscall` виконує перехід за 10–15 тактів: вона зберігає поточний `RIP` у регістр `RCX`, `RFLAGS` у `R11`, атомарно завантажує `RIP` із `MSR_LSTAR`, накладає маску на `RFLAGS` і перемикає `CPL` на 0.

## 2. Модель привілеїв ARM Cortex-M

Мікроконтролери сімейства ARM Cortex-M (Cortex-M0+/M3/M4/M7/M23/M33/M55) реалізують принципово іншу модель привілеїв, оптимізовану для детермінізму систем реального часу та мінімізації площі кристала. Тут відсутні сегментні регістри x86 чи складні таблиці дескрипторів. Архітектура будується на перетині двох незалежних осей: **режимів роботи** (Operating Modes) та **рівнів привілеїв** (Privilege Levels).

![Модель привілеїв ARM Cortex-M](/root/hw/hw-arch/protection-rings/img/cortex-m-modes.svg)
*Матриця режимів та рівнів привілеїв ARM Cortex-M: розмежування Handler Mode та Thread Mode, вплив бітів nPRIV та SPSEL регістра CONTROL, використання стеків MSP/PSP та механізм виклику SVC.*

### Режими та рівні привілеїв

Архітектура ARMv7-M / ARMv8-M визначає два взаємодоповнюючі режими роботи:

1. **Handler Mode (режим обробника):**
   - Процесор автоматично переходить у цей режим під час виникнення будь-якого винятку чи апаратного переривання (Reset, NMI, HardFault, SysTick, SVC, зовнішні IRQ).
   - **Завжди привілейований.** Непривілейованого режиму Handler в архітектурі не існує фізично.
   - Завжди використовує основний покажчик стека — **MSP (Main Stack Pointer)**.
   - Має повний доступ до системного адресного простору (System Control Space, SCS за адресою `0xE000E000`), включно з регістрами NVIC, SCB, SysTick та MPU.

2. **Thread Mode (режим потоку):**
   - Основний режим, у якому процесор перебуває після скидання та виконує прикладний код або задачі операційної системи реального часу (RTOS).
   - Може виконуватися на одному з двох рівнів привілеїв:
     - **Privileged Thread Mode:** має повний доступ до всіх інструкцій і пам'яті. Може використовувати як стек MSP, так і процесний стек **PSP (Process Stack Pointer)**.
     - **Unprivileged Thread Mode (користувацький режим):** має обмежений доступ до спеціальних інструкцій (`CPSID`, `CPSIE`, `MSR` системних регістрів, `WFI`, `WFE` у деяких конфігураціях) і не має права запису в системні регістри ядра. Зазвичай працює виключно на стеку PSP.

### Системний регістр CONTROL

Поточний стан процесора в Thread Mode визначається системним регістром `CONTROL` (доступним через спеціальні інструкції `MRS` та `MSR`):

| Біт | Назва | Призначення та значення |
| :--- | :--- | :--- |
| **0** | `nPRIV` | **Рівень привілеїв у Thread Mode:**<br>`0` = Privileged (привілейований)<br>`1` = Unprivileged (непривілейований) |
| **1** | `SPSEL` | **Вибір активного стека в Thread Mode:**<br>`0` = Використовувати MSP (Main Stack Pointer)<br>`1` = Використовувати PSP (Process Stack Pointer) |
| **2** | `FPCA` | **Активність контексту FPU:**<br>`1` = Розширений плаваючий контекст активний (автостекування s0–s15, FPSCR) |

Головне апаратне правило безпеки Cortex-M: **непривілейований код неспроможний змінити біт `nPRIV` назад на `0`**. Якщо програма в Unprivileged Thread Mode виконає інструкцію `MSR CONTROL, R0` зі спробою скинути біт `nPRIV`, апаратура ядра просто проігнорує цей запис без зупинки конвеєра. Програмне підвищення привілеїв напряму заблоковано в кремнії.

Єдиний шлях підвищення привілеїв для непривілейованої задачі — викликати інструкцію системної пастки `SVC #imm` (Supervisor Call). Інструкція `SVC` породжує синхронний виняток, що перемикає процесор у **Handler Mode** (привілейований стан), де обробник `SVC_Handler` ядра RTOS перевіряє запит і виконує системну дію від імені системи.

### Апаратне автостекування та значення `EXC_RETURN`

На відміну від архітектури x86, де ядро операційної системи самостійно зберігає регістри у пролозі обробника за допомогою інструкцій `push`, мікроконтролери Cortex-M мають апаратний автомат збереження та відновлення контексту (Hardware Stacking Engine).

Коли процесор бере виняток, апаратура паралельно з вибіркою вектора переривання автоматично зберігає 8 слів (32 байти) на поточний активний стек (якщо переривання сталося в задачі — на стек `PSP`):

```text
               Верхівка стека (після входу у виняток)
             +-----------------------+
   SP + 0x00 | R0                    |  <- Аргумент 0 функції / виклику
   SP + 0x04 | R1                    |  <- Аргумент 1
   SP + 0x08 | R2                    |  <- Аргумент 2
   SP + 0x0C | R3                    |  <- Аргумент 3
   SP + 0x10 | R12                   |  <- Внутрішньопроцедурний регістр
   SP + 0x14 | LR (R14)              |  <- Адреса повернення викликача
   SP + 0x18 | PC (R15)              |  <- Адреса команди, що викликала виняток
   SP + 0x1C | xPSR                  |  <- Регістр стану програми (прапорці, IPSR)
             +-----------------------+
```

Якщо використовується блок плаваючої коми (FPU) і біт `CONTROL.FPCA == 1`, апаратура автоматично додає ще 18 слів (регістри `S0`–`S15`, `FPSCR` та слово вирівнювання).

Під час входу в обробник регістр `LR` (Link Register) завантажується спеціальним магічним значенням — **`EXC_RETURN`**. Це значення служить інструкцією для апаратного автомата виходу:

- `0xFFFFFFF9` — повернення в Privileged Thread Mode з використанням стека **MSP** (базовий кадр цілих регістрів).
- `0xFFFFFFFD` — повернення в Thread Mode (привілейований або непривілейований, згідно з `CONTROL.nPRIV`) з використанням стека **PSP**.
- `0xFFFFFFF1` — повернення в Handler Mode (при вкладених перериваннях) з використанням **MSP**.
- `0xFFFFFFED` / `0xFFFFFFE9` — аналогічні повернення з відновленням розширеного кадру плаваючих регістрів FPU.

Коли обробник переривання виконує команду виходу `BX LR` або `POP {PC}`, апаратура розпізнає шаблон `0xFFFFFFFx` у лічильнику команд, автоматично витягує зі стека збережені 8 слів (Unstacking) і повертає процесор у відповідний режим і рівень привілеїв за 12 тактів.

## 3. Рівні винятків ARMv8-A (Exception Levels EL0–EL3)

У 64-бітній архітектурі ARMv8-A (серія Cortex-A: від Cortex-A53/A72 до Neoverse та сучасних ядер Apple Silicon) ієрархія захисту формалізована як система дискретних **рівнів винятків (Exception Levels)** від EL0 до EL3. Чим вищий номер рівня, тим вищий рівень привілеїв виконання коду та ширший доступ до апаратних ресурсів.

![Рівні винятків ARMv8-A та домени TrustZone](/root/hw/hw-arch/protection-rings/img/armv8-el-trustzone.svg)
*Ієрархія рівнів винятків ARMv8-A EL0–EL3, розподіл між звичайним світом (Non-Secure), захищеним світом (Secure World / TrustZone) та Realm Management Extension (RME), із зазначенням інструкцій системних переходів SVC, HVC, SMC та повернення ERET.*

### Призначення рівнів EL0–EL3

1. **EL0 (Application / Користувацький рівень):**
   - Призначений для виконання звичайних прикладних процесів і користувацьких бібліотек.
   - Непривілейований доступ: заборонено конфігурувати таблиці трансляції віртуальної пам'яті, переривання та системні таймери.
   - Спроба читання системних регістрів рівня EL1 (наприклад, `SCTLR_EL1` або `TTBR0_EL1`) породжує виняток невизначеної інструкції.
2. **EL1 (OS Kernel / Ядро операційної системи):**
   - Рівень виконання ядра багатозадачної ОС (Linux, Windows on ARM, macOS XNU, FreeBSD) та його драйверів.
   - Керує віртуальною пам'яттю першого ступеня (Stage 1 Translation: віртуальна адреса процесу → проміжна фізична адреса IPA або фізична адреса PA).
   - Обробляє системні виклики та апаратні переривання рівня ОС.
3. **EL2 (Hypervisor / Гіпервізор):**
   - Забезпечує апаратну віртуалізацію та ізоляцію гостьових операційних систем (KVM, Xen, Hyper-V, Apple Hypervisor).
   - Керує трансляцією пам'яті другого ступеня (Stage 2 Translation: IPA → реальна фізична адреса PA), унеможливлюючи вихід гостьової ОС за межі виділеної їй фізичної оперативної пам'яті.
   - Дозволяє перехоплювати (trap) доступ гостьового ядра до чутливих регістрів керування процесором безпосередньо у гіпервізор.
4. **EL3 (Secure Monitor & Firmware / Безпечний монітор):**
   - Найвищий привілейований рівень процесора, корінь довіри апаратної безпеки (Hardware Root of Trust).
   - Виконує початковий завантажувач мікрокоду, компоненти TF-A (Trusted Firmware-A) та диспетчер безпечного монітора.
   - Володіє керівним регістром безпеки `SCR_EL3` (Secure Configuration Register).
   - Забезпечує перемикання контекстів між звичайним світом (Non-Secure World), безпечним світом (Secure World / ARM TrustZone) та ізольованими анклавами (Realm World в архітектурі ARMv9 CCA).

### Механізми переходів між рівнями

Перехід між рівнями винятків регулюється трьома залізними законами архітектури ARMv8-A:

1. **Підвищення рівня привілею можливе виключно внаслідок взяття винятку.** Код рівня EL0 не може виконати інструкцію, що перевела б його в EL1 на наступному кроці. Для підвищення рівня використовуються виділені команди генерації синхронних винятків:
   - `SVC #imm` (Supervisor Call): перехід EL0 → EL1.
   - `HVC #imm` (Hypervisor Call): перехід EL1 → EL2. Команда `HVC` заблокована на рівні EL0.
   - `SMC #imm` (Secure Monitor Call): перехід EL1/EL2 → EL3. Заблокована на рівні EL0; на рівні EL1 може бути перехоплена гіпервізором EL2 залежно від біта `HCR_EL2.TSC`.
2. **Зниження рівня привілею виконується виключно інструкцією `ERET` (Exception Return).** При виконанні `ERET` на рівні ELx:
   - Процесор копіює збережене значення стану з регістра `SPSR_ELx` (Saved Program Status Register) у робочий регістр стану `PSTATE`.
   - Процесор завантажує адресу відновлення з регістра `ELR_ELx` (Exception Link Register) у лічильник команд `PC`.
   - Обидва оновлення відбуваються атомарно, запобігаючи виконанню коду нижчого рівня з правами вищого рівня.
3. **Рівень винятку не може бути змінений у межах однієї інструкції без виклику або повернення.** Не існує команд, які дозволили б «тимчасово» підняти привілеї поточного виконання.

### Таблиця векторів винятків ARMv8-A

Кожен рівень винятків від EL1 до EL3 має власну таблицю векторів винятків, базову адресу якої визначає регістр `VBAR_ELx` (Vector Base Address Register). Таблиця має фіксований розмір у 2048 байтів (вирівняна на межу 2 КБ) і містить рівно 16 записів.

Таблиця розбита на 4 групи по 4 типи винятків залежно від контексту джерела виклику:

```text
VBAR_ELx + 0x000 : Виняток із поточного EL з використанням SP_EL0
VBAR_ELx + 0x200 : Виняток із поточного EL з використанням SP_ELx
VBAR_ELx + 0x400 : Виняток із нижчого EL, що виконується в AArch64
VBAR_ELx + 0x600 : Виняток із нижчого EL, що виконується в AArch32
```

Усередині кожної з 4 груп розташовані 4 слоти по 128 байтів (32 інструкції) для кожного класу винятків:
1. **Synchronous** (SVC, звернення до пам'яті без прав, помилки вибірки інструкцій).
2. **IRQ** (звичайні асинхронні переривання).
3. **FIQ** (швидкі переривання / безпечні переривання TrustZone).
4. **SError** (System Error — асинхронні апаратні помилки шин та пам'яті).

Завдяки тому, що кожен слот займає 128 байтів, простий обробник винятку можна розмістити безпосередньо у слоті таблиці векторів, оминаючи додаткові інструкції непрямого переходу.

## 4. Апаратне розмежування пам'яті через MPU та MMU

Кільця захисту та рівні привілеїв не захищають систему самі по собі: заборона виконувати команду `hlt` не завадить непривілейованому коду переписати дані ядра в оперативній пам'яті, якщо шина пам'яті відкрита для запису. Ізоляція стає повною лише тоді, коли апаратний рівень привілеїв зв'язується з блоком захисту пам'яті — **MPU** у мікроконтролерах або **MMU** у процесорах загального призначення.

![Апаратне розмежування пам'яті через MPU в RTOS](/root/hw/hw-arch/protection-rings/img/mpu-task-isolation.svg)
*Організація пам'яті під керуванням MPU в операційній системі реального часу: поділ фізичного простору на ізольовані регіони завдань, захист системного простору SCS та фіксація порушень через прапорці CFSR.*

### MPU (Memory Protection Unit) проти MMU (Memory Management Unit)

Головна відмінність між MPU та MMU полягає у трансляції адрес:

- **MPU (мікроконтролери / вбудовані системи):**
  - **Не змінює адресу.** Фізична адреса з конвеєра ядра безпосередньо потрапляє на шину пам'яті (`Addr_virt == Addr_phys`).
  - Перевіряє права доступу для фіксованої кількості прямокутних вікон (регіонів) пам'яті (зазвичай 8, 16 або 24 регіони в ARMv7-M / ARMv8-M).
  - Нульові накладні витрати на трансляцію адрес: перевірка виконується паралельно з декодуванням адреси за 1 такт процесора, що гарантує детермінізм часу відгуку в RTOS.
- **MMU (сервери, ПК, смартфони):**
  - **Транслює віртуальні адреси у фізичні** за допомогою багаторівневих таблиць сторінок (Page Tables) фіксованого розміру (зазвичай 4 КБ, 2 МБ, 1 ГБ).
  - Дозволяє кожному процесу мати власний ізольований адресний простір однакового діапазону (наприклад, кожен процес бачить власну пам'ять починаючи з `0x00400000`).
  - Використовує апаратний кеш трансляції — **TLB (Translation Lookaside Buffer)**. Промах TLB тягне за собою апаратний обхід таблиць сторінок (Page Table Walk), що може займати десятки наносекунд.

### Біти прав доступу в дескрипторах

Кожен запис таблиці сторінок (MMU) або регістр конфігурації регіону (MPU) містить набір бітів контролю доступу:

#### В архітектурі x86 (дескриптори сторінок PTE/PDE):
- **U/S (User / Supervisor, біт 2):** якщо біт дорівнює `0`, сторінка є системною (доступна лише для Ring 0, 1, 2). Якщо біт дорівнює `1`, сторінка доступна для коду з Ring 3.
- **R/W (Read / Write, біт 1):** якщо `0`, сторінка доступна лише для читання; якщо `1`, дозволено читання та запис.
- **NX / XD (No-Execute / Execute-Disable, біт 63):** забороняє вибірку інструкцій зі сторінки пам'яті, блокуючи виконання шкідливого коду зі стека або купи.
- **SMEP / SMAP (Supervisor Mode Execution/Access Prevention):** апаратні розширення в регістрі `CR4`. `SMEP` генерує помилку, якщо ядро (Ring 0) намагається виконати код із користувацької сторінки (`U/S == 1`). `SMAP` блокує пряме читання та запис користувацьких даних із ядра без явного підняття прапорця `AC` інструкцією `stac`.

#### В архітектурі ARM Cortex-M (регістри MPU `RASR` / `RLAR`):
- **AP (Access Permission, біти AP[2:0]):**
  - `000` — доступ заборонено для всіх рівнів.
  - `001` — Privileged RW, Unprivileged No Access (пам'ять ядра ОС).
  - `010` — Privileged RW, Unprivileged Read-Only (спільні константи/буфери).
  - `011` — Privileged RW, Unprivileged RW (власна оперативна пам'ять та стек задачі).
  - `101` — Privileged RO, Unprivileged Read-Only.
  - `110` — Privileged RO, Unprivileged Read-Only.
- **XN (Execute-Never, біт 28):** заборона виконання коду з регіону даних (захист стека від переповнення буфера).

### Обробка порушень прав доступу

Коли непривілейований процес порушує правила доступу, апаратура генерує виняток і формує діагностичний код помилки:

- **На x86:** виникає виключення **Page Fault (#PF, вектор 14)**. Процесор поміщає адресу збою в регістр `CR2`, а на стек кладе апаратний код помилки (Error Code):
  - Біт 0 (`P`): `0` = звернення до невідображеної сторінки, `1` = порушення прав доступу.
  - Біт 1 (`W/R`): `0` = спроба читання, `1` = спроба запису.
  - Біт 2 (`U/S`): `0` = збій стався у привілейованому режимі, `1` = збій стався у Ring 3.
  - Біт 4 (`I/D`): `1` = спроба вибірки інструкції з NX-сторінки.
- **На ARM Cortex-M:** виникає виняток **MemManage Fault (вектор 4)**. Процесор встановлює біти в регістрі стану відмов `SCB->CFSR` (Configurable Fault Status Register, байти `MMFSR`):
  - `DACCVIOL` (біт 1) — порушення прав доступу під час читання/запису даних (Data Access Violation).
  - `IACCVIOL` (біт 0) — спроба вибірки коду із забороненої зони або регіону з `XN=1`.
  - `MMFARVALID` (біт 7) — вказує, що точна адреса пам'яті, де стався збій, зафіксована в регістрі `SCB->MMFAR` (MemManage Fault Address Register).

## 5. Перемикання задачі RTOS у непривілейований режим із налаштуванням MPU

Щоб побудувати надійну вбудовану систему на мікроконтролері Cortex-M, ядро RTOS повинно ізолювати кожну задачу:
1. Задачі виконуються в **Unprivileged Thread Mode** на окремих стеках **PSP**.
2. Планувальник RTOS виконується в **Handler Mode** (переривання `SysTick` або `PendSV`) на стеку **MSP**.
3. Під час кожного перемикання контексту планувальник переконфігурує MPU так, щоб поточна задача мала доступ лише до власного стека, своїх виділених буферів та відкритого коду Flash.

Нижче наведено робочий приклад ініціалізації та перемикання задачі в непривілейований режим з конфігурацією MPU згідно зі стандартом CMSIS (ARMv7-M).

/* rtos_mpu_task.c — налаштування MPU та перехід у Unprivileged Thread Mode
 * Платформа: ARM Cortex-M4 / Cortex-M7 (ARMv7-M, CMSIS-compliant)
 */
#include <stdint.h>
#include <stdbool.h>

/* Структури системних регістрів CMSIS */
#define MPU_BASE          (0xE000ED90UL)
#define SCB_BASE          (0xE000ED00UL)

typedef struct {
    volatile uint32_t TYPE;
    volatile uint32_t CTRL;
    volatile uint32_t RNR;
    volatile uint32_t RBAR;
    volatile uint32_t RASR;
} MPU_Type;

typedef struct {
    volatile uint32_t CPUID;
    volatile uint32_t ICSR;
    volatile uint32_t VTOR;
    volatile uint32_t AIRCR;
    volatile uint32_t SCR;
    volatile uint32_t CCR;
    volatile uint32_t SHPR[3];
    volatile uint32_t SHCSR;
    volatile uint32_t CFSR;
    volatile uint32_t HFSR;
    volatile uint32_t DFSR;
    volatile uint32_t MMFAR;
    volatile uint32_t BFAR;
} SCB_Type;

#define MPU               ((MPU_Type *)MPU_BASE)
#define SCB               ((SCB_Type *)SCB_BASE)

/* Бітові маски MPU RASR */
#define MPU_RASR_ENABLE_Msk     (1UL << 0)
#define MPU_RASR_SIZE_Pos       (1UL)
#define MPU_RASR_AP_Pos         (24UL)
#define MPU_RASR_XN_Pos         (28UL)

#define MPU_AP_PRIV_RW_USER_NO  (1UL << MPU_RASR_AP_Pos)
#define MPU_AP_PRIV_RW_USER_RO  (2UL << MPU_RASR_AP_Pos)
#define MPU_AP_PRIV_RW_USER_RW  (3UL << MPU_RASR_AP_Pos)
#define MPU_AP_PRIV_RO_USER_RO  (6UL << MPU_RASR_AP_Pos)

#define MPU_REGION_SIZE_32B     (4UL << MPU_RASR_SIZE_Pos)
#define MPU_REGION_SIZE_1KB     (9UL << MPU_RASR_SIZE_Pos)
#define MPU_REGION_SIZE_4KB     (11UL << MPU_RASR_SIZE_Pos)
#define MPU_REGION_SIZE_512KB   (18UL << MPU_RASR_SIZE_Pos)

/* Бар'єри пам'яті та синхронізації */
static inline void __dmb(void) { __asm__ volatile ("dmb 0xF" ::: "memory"); }
static inline void __dsb(void) { __asm__ volatile ("dsb 0xF" ::: "memory"); }
static inline void __isb(void) { __asm__ volatile ("isb 0xF" ::: "memory"); }

/* Конфігурація MPU регіонів для конкретної задачі */
void rtos_setup_task_mpu(uint32_t stack_base, uint32_t data_base) {
    __dsb();

    /* Вимикаємо MPU перед переконфігурацією */
    MPU->CTRL = 0;

    /* Регіон 0: Код Flash (0x08000000, 512 КБ) — Privileged RO/X, Unprivileged RO/X */
    MPU->RNR  = 0;
    MPU->RBAR = 0x08000000UL;
    MPU->RASR = MPU_RASR_ENABLE_Msk | MPU_REGION_SIZE_512KB | MPU_AP_PRIV_RO_USER_RO;

    /* Регіон 1: Стек задачі (stack_base, 1 КБ) — Privileged RW, Unprivileged RW, XN */
    MPU->RNR  = 1;
    MPU->RBAR = stack_base;
    MPU->RASR = MPU_RASR_ENABLE_Msk | MPU_REGION_SIZE_1KB | MPU_AP_PRIV_RW_USER_RW | (1UL << MPU_RASR_XN_Pos);

    /* Регіон 2: Дані задачі (data_base, 4 КБ) — Privileged RW, Unprivileged RW, XN */
    MPU->RNR  = 2;
    MPU->RBAR = data_base;
    MPU->RASR = MPU_RASR_ENABLE_Msk | MPU_REGION_SIZE_4KB | MPU_AP_PRIV_RW_USER_RW | (1UL << MPU_RASR_XN_Pos);

    /* Увімкнення обробника MemManage Fault у SCB */
    SCB->SHCSR |= (1UL << 16); /* MEMFAULTENA */

    /* Вмикаємо MPU: PRIVDEFENA (біт 2) = дозволити фонову пам'ять для привілейованого режиму */
    MPU->CTRL = (1UL << 0) | (1UL << 2);

    __dsb();
    __isb();
}

/* Запуск задачі в непривілейованому режимі */
void rtos_launch_unprivileged_task(void (*task_entry)(void), uint32_t task_psp_top) {
    /* 1. Завантажуємо адресу верхівки стека в PSP */
    __asm__ volatile ("msr psp, %0" :: "r"(task_psp_top) : "sp");

    /* 2. Перемикаємося на PSP (SPSEL = 1) та скидаємо привілеї (nPRIV = 1) */
    uint32_t control_val = (1UL << 1) | (1UL << 0); /* SPSEL=1, nPRIV=1 */
    __asm__ volatile (
        "msr control, %0 \n"
        "isb             \n"
        :: "r"(control_val) : "memory"
    );

    /* 3. Передаємо керування на точку входу непривілейованої задачі */
    task_entry();
}

public:
    static void init() noexcept {
        __asm__ volatile ("dsb 0xF" ::: "memory");
        SCB->SHCSR |= (1UL << 16); // Увімкнення MemManage Fault
        MPU->CTRL = 0;             // Скидання перед конфігурацією
    }

    static void configure_region(uint8_t region_num,
                                 uintptr_t base_address,
                                 RegionSize size,
                                 AccessPermission perm,
                                 bool execute_never = true) noexcept {
        MPU->RNR  = region_num;
        MPU->RBAR = base_address;
        
        uint32_t rasr = 1UL // Enable
                      | static_cast<uint32_t>(size)
                      | static_cast<uint32_t>(perm)
                      | (execute_never ? (1UL << 28) : 0UL);
        MPU->RASR = rasr;
    }

    static void enable() noexcept {
        // Біт 0 = ENABLE, біт 2 = PRIVDEFENA (фонова пам'ять для ядра)
        MPU->CTRL = (1UL << 0) | (1UL << 2);
        __asm__ volatile ("dsb 0xF \n isb 0xF" ::: "memory");
    }
};

class TaskLauncher {
public:
    template <typename TaskFn>
    requires std::invocable<TaskFn>
    [[noreturn]] static void launch_unprivileged(TaskFn&& task_entry, uintptr_t psp_stack_top) noexcept {
        __asm__ volatile ("msr psp, %0" :: "r"(psp_stack_top) : "sp");

        // Біт 1 = SPSEL (PSP), Біт 0 = nPRIV (Unprivileged)
        constexpr uint32_t unprivileged_control = 0b11UL;
        __asm__ volatile (
            "msr control, %0 \n"
            "isb             \n"
            :: "r"(unprivileged_control) : "memory"
        );

        task_entry();
        while (true) { /* У разі повернення — зупинка */ }
    }
};

} // namespace rtos::hal

## Підсумок: багаторівнева фортеця сучасного процесора

Розмежування рівнів привілеїв перетворює процесор із примітивного автомата обробки інструкцій на захищену багатозадачну платформу. Незалежно від того, як архітектура називає свої домени — кільцями x86 (0–3), рівнями винятків ARMv8-A (EL0–EL3) чи матрицею режимів Cortex-M (Thread/Handler), усі процесори підпорядковуються спільним принципам:

1. **Неподільність перевірки:** схема контролю прав вбудована безпосередньо в тракт вибірки та декодування інструкцій. Порушення прав відхиляється апаратурою до зміни стану процесора.
2. **Єдиний законний шлях підвищення прав:** непривілейований код не може підняти власний рівень жодним програмним записом у системні регістри. Єдиний шлях угору — апаратні шлюзи системних викликів (`syscall`, `SVC`, `int 0x80`), які водночас передають керування на фіксовані перевірені адреси ядра.
3. **Ізоляція стекових просторів:** кожен рівень привілеїв володіє виділеним стеком (TSS `RSP0` у x86, `MSP` у Cortex-M, `SP_ELx` у ARMv8-A), що унеможливлює атаку на пам'ять ядра через пошкоджений користувацький покажчик.
4. **Співпраця з блоками пам'яті:** рівні привілеїв знаходять фізичне вираження через блоки MPU та MMU, які пов'язують біти поточного статусу ядра з доступом до конкретних діапазонів оперативної пам'яті та шин периферійних пристроїв.
