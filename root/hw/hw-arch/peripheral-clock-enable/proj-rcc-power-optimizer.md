# ⚙️ Диспетчер динамічного тактування периферії з оптимізацією живлення

У складних вбудованих системах реального часу (RTOS) та автономних бездротових вузлах десятки драйверів одночасно конкурують за периферійні ресурси мікроконтролера. Якщо кожен драйвер намагається самостійно й несинхронізовано керувати регістрами контролера тактування (RCC), система стикається з трьома критичними проблемами: передчасним вимкненням спільно використовуваних шин (наприклад, шини I2C, до якої підключено кілька датчиків), невиправдано високим енергоспоживанням через постійно ввімкнені невикористовувані блоки та апаратними збоями `BusFault` через відсутність бар'єрів стабілізації тактування.

Для комплексного вирішення цих завдань створено архітектурний компонент — **диспетчер динамічного тактування периферії** (англ. *Dynamic Peripheral Clock & Power Manager*). Диспетчер інкапсулює апаратні особливості шинних доменів, веде атомарний підрахунок посилань на кожен периферійний вузол, автоматично керує залежностями (наприклад, тактуванням ліній GPIO та каналів DMA), забезпечує апаратні бар'єри синхронізації та переводить пасивні шинні мости в сплячий стан для максимального збереження заряду джерела живлення.

## Інженерна мотивація та постановка задачі

Розробка сучасного вбудованого програмного забезпечення вимагає балансування між двома протилежними вимогами: максимальною швидкодією при виконанні обчислень і мінімальним споживанням струму в періоди очікування. У класичному підході до програмування мікроконтролерів розробники часто налаштовують тактування всієї периферії одноразово під час старту системи у функції `main()`. Проте для пристроїв з автономним живленням від акумуляторів або збирачів енергії (англ. *energy harvesting*) такий підхід є неприпустимим: тактова мережа навіть пасивних периферійних модулів споживає від 30% до 50% загального динамічного струму кристала.

Розглянемо три реальні інженерні сценарії, які демонструють необхідність централізованого диспетчера:

### Сценарій 1: Конфлікт спільного володіння шиною I2C
На одній апаратній шині `I2C1` паралельно працюють два незалежні програмні драйвери: високопріоритетний драйвер цифрового акселерометра, що опитує датчик 100 разів на секунду, та фоновий драйвер мікросхеми енергонезалежної пам'яті EEPROM, що періодично зберігає журнал подій. Якщо драйвер EEPROM після завершення запису блоку даних безпосередньо виконає вимкнення тактування шини `RCC->APB1ENR &= ~RCC_APB1ENR_I2C1EN`, наступна транзакція акселерометра спричинить апаратне зависання або генерацію винятку `BusFault`, оскільки шинний міст виявиться знеструмленим за тактом. Пряме ручне керування регістрами RCC порушує принцип ізоляції модулів.

### Сценарій 2: Невидимий витік енергії пасивних мостів
Периферійна шина `APB1` об'єднує повільні модулі: таймери, інтерфейси CAN, UART, I2C. Якщо в системі активний лише один модуль UART на шині `APB2`, але тактування шини `APB1` залишається ввімкненим разом із дільником частоти та внутрішніми логічними мостами, пристрій марно розсіює енергію на холостому перемиканні буферів моста. Диспетчер повинен фіксувати стан повної пасивності шинного домену (англ. *Bus Domain Dormancy*) і автоматично переводити відповідний шинний міст у режим низького енергоспоживання або перекривати кореневий тактовий вентиль домену.

### Сценарій 3: Каскадні апаратні залежності
Робота високошвидкісного інтерфейсу `SPI1` у режимі передачі через прямий доступ до пам'яті (DMA) вимагає одночасної злагодженої роботи трьох незалежних апаратних вузлів:
1. Самого модуля `SPI1` (шина APB2);
2. Порту введення-виведення `GPIOA` (шина AHB1) для керування лініями SCK, MOSI, MISO;
3. Контролера `DMA2` (шина AHB1) для автоматичного перекачування слів із пам'яті SRAM.

Якщо прикладний код повинен вручну пам'ятати всю цю ієрархію й у правильному порядку вмикати та вимикати біти в трьох різних регістрах `RCC_AHB1ENR` та `RCC_APB2ENR`, виникає висока ймовірність помилок людського фактора. Диспетчер тактування бере на себе автоматичне рекурсивне розв'язання дерева залежностей (англ. *Dependency Graph Resolution*).

```
+─────────────────────────────────────────────────────────────────────────────+
|                              Додаток / RTOS                                |
|  Драйвер Датчика A       Драйвер Модема B         Завдання Обробки C        |
+────────────┬─────────────────────┬─────────────────────────┬────────────────+
             │                     │                         │
             │ acquire(I2C1)       │ acquire(USART1)         │ clock_guard    |
             ▼                     ▼                         ▼
+─────────────────────────────────────────────────────────────────────────────+
|                   Диспетчер динамічного тактування                          |
|  - Атомарний підрахунок посилань (ref_count)                                |
|  - Резолвер залежностей (USART1 -> GPIOA, DMA2)                             |
|  - Монітор активності шинних доменів (AHB1, APB1, APB2)                     |
|  - Бар'єри стабілізації (Dummy Read + DSB)                                  |
|  - Монітор енергетичного бюджету (Saved Energy Calculator)                  |
+──────────────────────────────────────┬──────────────────────────────────────+
                                       │
                                       ▼
+─────────────────────────────────────────────────────────────────────────────+
|                         Апаратні регістри RCC / SoC                         |
|  RCC_AHB1ENR     RCC_APB1ENR     RCC_APB2ENR     RCC_APBxLPENR  RCC_APBxRSTR|
+─────────────────────────────────────────────────────────────────────────────+
```

## Математична модель обліку збереженої енергії

Для оцінки ефективності динамічного керування тактуванням у диспетчер інтегровано математичну модель обліку збереженої електричної енергії.

Згідно з фізикою напівпровідникових КМОН-схем, динамічна потужність, що споживається цифровим вузлом, прямо пропорційна його еквівалентній ємності `C_eq`, напрузі живлення `V_DD` у квадраті та тактовій частоті `f`. Коли тактування модуля вимкнено, його динамічне споживання дорівнює нулю, а статичний струм витоку залишається незмінним.

Якщо відомий номінальний динамічний струм споживання `I_dyn,i` для кожного `i`-го периферійного модуля при робочій частоті шини, сумарний збережений електричний заряд `Q_saved` (у кулонах або мікроампер-секундах) за загальний час роботи системи `T_total` визначається інтегралом різниці часу пасивності:

```
Q_saved = ∑ [ I_dyn,i · (T_total - T_active,i) ] + ∑ [ I_bridge,j · T_dormant,j ]
```

де:
- `T_active,i` — сумарний час, протягом якого `i`-й периферійний модуль перебував у ввімкненому стані (`ref_count > 0`);
- `I_dyn,i` — додатковий струм споживання модуля при активному тактуванні;
- `T_dormant,j` — час, протягом якого весь `j`-й шинний домен (наприклад, шина APB1) був повністю вільний від активних модулів;
- `I_bridge,j` — власний струм споживання шинного моста та його внутрішніх буферів.

Сумарна збережена енергія `E_saved` у джоулях (або мікроджоулях) обчислюється як:

```
E_saved = Q_saved · V_DD
```

Диспетчер підтримує внутрішні лічильники часу активності кожного вузла, що дозволяє підсистемі телеметрії в режимі реального часу надавати операційній системі точні дані про поточний енергетичний баланс пристрою.

## Інженерний розрахунок енергетичного бюджету бездротового автономного трекера

Розглянемо практичний інженерний розрахунок енергоспоживання бездротового трекера активів (англ. *Asset Tracker*), що живиться від літій-полімерного акумулятора номінальною ємністю `E_bat = 500 мА·год` при середній напрузі `V_DD = 3.7 В`.

Пристрій працює за періодичним графіком із циклом `T_cycle = 60 с` (1 хвилина):
1. **Опитування IMU акселерометра (I2C1 на шині APB1 + GPIOB)**: тривалість `T_imu = 2 мс`, струм модуля `I_i2c = 450 мкА`, струм порту `I_gpio = 250 мкА`.
2. **Зчитування координат із GPS-модуля (USART1 на шині APB2 + DMA2 + GPIOA)**: тривалість `T_gps = 100 мс`, струм `I_usart = 850 мкА`, `I_dma = 1200 мкА`, `I_gpio = 250 мкА`.
3. **Запис у Flash-пам'ять журналів (SPI1 на шині APB2 + GPIOA)**: тривалість `T_flash = 5 мс`, струм `I_spi = 1100 мкА`, `I_gpio = 250 мкА`.
4. **Режим глибокого сну Stop Mode**: тривалість `T_sleep = 59.893 с`.

Порівняємо три архітектурні стратегії керування тактуванням:

### Профіль 1: Статичне тактування (усі периферійні блоки та мости ввімкнені постійно)
- Базовий струм тактування 30 периферійних модулів та шинних мостів: `I_static_clk = 3.2 мА`.
- Струм ядра в активному режимі (64 МГц): `I_core_active = 8.5 мА`.
- Струм у режимі сну (тактові дерева продовжують перемикатися): `I_sleep_1 = 3.2 мА`.

Середній струм споживання:

```
I_avg_1 = (8.5 мА · 0.107 с + 3.2 мА · 59.893 с) / 60 с  [визначення середнього струму за цикл 60 с]
        = (0.9095 + 191.657) / 60                         [сумарний електричний заряд у мА·с]
        = 3.209 мА                                        [середньозважений струм за 1 хвилину]
```

Час автономної роботи від акумулятора:

```
Life_1 = 500 мА·год / 3.209 мА                            [закон розряду хімічного акумулятора LiPo]
       = 155.8 годин                                      [приблизно 6.5 діб безперервної роботи]
```

### Профіль 2: Базове стробування (Clock Gating лише під час сну ядра via LPENR)
- В активній фазі всі блоки тактуються постійно: `I_active = 8.5 мА + 3.2 мА = 11.7 мА`.
- У фазі сну всі блоки знеструмлюються апаратурою за винятком RTC: `I_sleep_2 = 18 мкА` (0.018 мА).

Середній струм споживання:

```
I_avg_2 = (11.7 мА · 0.107 с + 0.018 мА · 59.893 с) / 60 с  [середній струм зі стробуванням у режимі сну]
        = (1.2519 + 1.078) / 60                             [сумарний заряд активної фази та фази сну]
        = 0.0388 мА                                         [еквівалентний постійний струм 38.8 мкА]
```

Час автономної роботи:

```
Life_2 = 500 мА·год / 0.0388 мА                             [час розряду від ємності 500 мА·год]
       = 12886 годин                                        [приблизно 1.47 року автономної роботи]
```

### Профіль 3: Динамічний диспетчер тактування (Reference Counting + Dormancy + Staggered Enable)
- В активній фазі тактуються **строго ті модулі, що виконують транзакцію в цей конкретний мікросекундний інтервал**:
  - Під час опитування I2C (2 мс): активні лише I2C1 + GPIOB (`I = 8.5 + 0.45 + 0.25 = 9.2 мА`);
  - Під час читання GPS (100 мс): активні лише USART1 + DMA2 + GPIOA (`I = 8.5 + 0.85 + 1.2 + 0.25 = 10.8 мА`);
  - Під час запису Flash (5 мс): активні лише SPI1 + GPIOA (`I = 8.5 + 1.1 + 0.25 = 9.85 мА`);
  - Мости APB1 та APB2 сплять у всі інші інтервали часу.
- У фазі сну: `I_sleep_3 = 4.2 мкА` (0.0042 мА).

Середній струм споживання:

```
I_avg_3 = (9.2 мА · 0.002 с + 10.8 мА · 0.100 с + 9.85 мА · 0.005 с + 0.0042 мА · 59.893 с) / 60 с  [сумарний струм за інтервалами]
        = (0.0184 + 1.080 + 0.04925 + 0.2515) / 60                                                   [заряд окремих транзакцій]
        = 1.39915 / 60                                                                               [підсумок у мА·с]
        = 0.0233 мА                                                                                  [середній струм 23.3 мкА]
```

Час автономної роботи від акумулятора:

```
Life_3 = 500 мА·год / 0.0233 мА                             [розрахунок повного терміну служби]
       = 21459 годин                                        [приблизно 2.45 року автономної роботи]
```

Використання централізованого динамічного диспетчера додатково подовжує час життя пристрою на **66% порівняно з базовим засинанням** і майже у **140 разів порівняно зі статичною ініціалізацією**!

## Архітектурні патерни проєктування драйверів із динамічним стробуванням

Використання диспетчера тактування змінює фундаментальні патерни розробки драйверів вбудованих систем:

### 1. Патерн «Лінива ініціалізація тактування» (Lazy Clock Initialization)
Традиційний драйвер вмикає тактування у функції конструктора `driver_init()`. У патерні лінивої ініціалізації функція `driver_init()` лише налаштовує дескриптори в пам'яті SRAM, але фізичне тактування в RCC залишається вимкненим.

Перше апаратне ввімкнення тактування через `clock_manager_acquire()` відбувається безпосередньо всередині функції `driver_transfer()` або `driver_read()`, перед передачею даних. Якщо пристрій взагалі не використовує цей інтерфейс у поточному режимі роботи, тактування ніколи не буде активовано.

### 2. Патерн «Агресивне засинання» (Eager Sleep Gating)
Щойно драйвер завершує останню операцію передачі даних (наприклад, надходить переривання про спорожнення буфера DMA або підтвердження прийому ACK), він не залишає модуль увімкненим «про всяк випадок», а негайно викликає `clock_manager_release()`.

Якщо наступний пакет надійде через 10 мілісекунд, шинний міст встигне заснути й заощадити значну кількість енергії.

### 3. Патерн «Адаптивне регулювання мостів» (Bridge Throttling)
Якщо диспетчер фіксує, що на шині APB1 активні лише низькошвидкісні періодичні таймери, він може програмно збільшити коефіцієнт дільника частоти шини APB1 (наприклад, встановити прескейлер /16 замість /2). Це знижує динамічну частоту перемикання ліній адреси та даних, додатково зменшуючи споживання струму без зупинки функціонування таймерів.

## Вплив динамічного стробування на електромагнітну сумісність (EMC & EMI)

Окрім прямого енергозбереження, динамічне стробування тактування має вирішальний вплив на електромагнітну сумісність (англ. *Electromagnetic Compatibility*, EMC) мікроконтролера та рівень паразитних випромінювань (англ. *Electromagnetic Interference*, EMI):

### 1. Зниження радіовипромінювання на гармоніках такту (Radiated Emissions)
Кожне розгалужене тактове дерево всередині кремнієвого кристала діє як мініатюрна дипольна антена. Коли тактовий сигнал із крутими фронтами наростання (менше 1 нс) безперервно прокачується по сотнях мікрон металевих шарів кристала, мікроконтролер випромінює потужні радіозавади на гармоніках тактової частоти `f_bus`, `2 · f_bus`, `3 · f_bus` тощо.

Вимкнення тактових дерев для пасивних модулів усуває паразитне випромінювання в діапазонах частот від 10 МГц до 1 ГГц, що дозволяє комерційним пристроям успішно проходити лабораторні випробування на відповідність європейським та американським стандартам CE/FCC (EN 55032 Class B).

### 2. Підвищення точності аналогових вимірювань (ADC Signal-to-Noise Ratio)
Цифрові шини APB/AHB, що перемикаються поруч із прецизійними аналоговими вузлами (АЦП, ЦАП, компараторами та підсилювачами з програмованим коефіцієнтом підсилення PGA), індукують ємнісні та індуктивні перехресні наведення (*Crosstalk*) на шинах аналогового живлення `VDDA`/`VSSA`.

Застосування патерну засинання шинних доменів під час перетворення АЦП:
- Диспетчер зупиняє всі комунікаційні модулі UART/SPI/I2C на час вибірки сигналу АЦП;
- Рівень шумів квантування падає на 6–12 дБ;
- Ефективна розрядність вбудованого 12-бітного АЦП (англ. *Effective Number of Bits*, ENOB) зростає з 9.8 біт до 11.4 біт!

## Методика фізичної верифікації профілю споживання на тестовому стенді

Для практичної перевірки ефективності роботи диспетчера та детектування прихованих витоків енергії використовується спеціалізований вимірювальний стенд:

```
+─────────────────────+             +────────────────────────────────────────+
```

2. **Синхронізація з осцилографом**: у код драйверів додаються строби перемикання налагоджувального піна GPIO (`DEBUG_PIN_HIGH()` перед `acquire()` та `DEBUG_PIN_LOW()` після `release()`).
3. **Зняття часової діаграми перехідних процесів**:
   - Фіксується затримка між підняттям сигналу GPIO та наростанням струму споживання (час включення ICG-вентиля та моста шини: 2–4 такти);

   - Перевіряється повернення базового струму до рівня режиму сну (< 5 мкА) протягом не більше 1 мкс після виклику `release()`.

## Інспекція стану диспетчера через GDB та OpenOCD

Під час налагодження складних RTOS-прошивок інженерам необхідно швидко перевіряти, які саме периферійні вузли утримують тактові шини в активному стані. Для автоматизації цієї задачі використовується допоміжний скрипт для відлагоджувача GDB:

```gdb
define clock_status
    set $idx = 0
    printf "=== Peripheral Clock Manager Status ===\n"
    while $idx < 11
        set $cnt = g_clk_state.ref_counts[$idx]
        if $cnt > 0
            printf " [ACTIVE] Module ID: %2d, RefCount: %d\n", $idx, $cnt
        end
        set $idx = $idx + 1
    end
    printf "--- Bus Domains Active Counts ---\n"
    printf " AHB1: %d, AHB2: %d, APB1: %d, APB2: %d\n", \
           g_clk_state.domain_active_count[0], \
           g_clk_state.domain_active_count[1], \
           g_clk_state.domain_active_count[2], \
           g_clk_state.domain_active_count[3]
end
```

Команда `clock_status` у командному рядку GDB миттєво візуалізує повну картину розподілу тактування кристала без необхідності зупинки виконання завдань планувальника.

Для вбудовування в автоматизовані пайплайни тестування енергоспоживання (CI/CD Hardware-in-the-Loop) скрипт легко трансформується у Python-розширення для GDB, яке формує детальний JSON-звіт із кількістю активних циклів кожного модуля та передає його серверу моніторингу регресій енергетичного бюджету.

## Архітектура матриці дескрипторів та дерева залежностей

Щоб мінімізувати накладні витрати на оперативну пам'ять (SRAM), яка в мікроконтролерах є вкрай обмеженим ресурсом (від кількох кілобайтів), уся статична конфігурація периферії винесена в незмінну таблицю дескрипторів `g_periph_meta[]`, розташовану у Flash-пам'яті програм (`.rodata`).

Кожен запис таблиці містить:
1. **Ідентифікатор шинного домену** (`domain`): належність до AHB1, AHB2, APB1 або APB2;
2. **Вказівники на фізичні регістри**: адреса регістра ввімкнення (`enr_register`), регістра роботи в режимі сну (`lpenr_register`) та регістра апаратного скидання (`rstr_register`);
3. **Бітову маску** (`mask`): позиція керуючого біта в 32-розрядному регістрі RCC;
4. **Список прямих залежностей** (`deps[]`): масив ідентифікаторів інших апаратних блоків, без яких цей модуль фізично не може функціонувати (наприклад, порти GPIO для сигнальних ліній або канали DMA);
5. **Параметр динамічного струму** (`dynamic_current_ua`): оціночне значення струму для енергетичного калькулятора.

Динамічний стан у SRAM займає лише кілька десятків байтів і складається з масиву 16-розрядних лічильників посилань `ref_counts[]`, лічильників активності шинних доменів `domain_active_count[]` та службових прапорців блокування критичних секцій.

Граф залежностей спроєктовано як спрямований ациклічний граф (англ. *Directed Acyclic Graph*, DAG). Рекурсивний алгоритм розв'язання гарантує відсутність нескінченних циклів та автоматично виконує ідемпотентний відкат при виникненні будь-якої апаратної помилки.

## Апаратні бар'єри синхронізації та потокобезпечність

Основним джерелом збоїв у багатопотокових RTOS-системах є стан перегонів (Race Condition) між задачами, що одночасно звертаються до одного регістра RCC. Оскільки операція встановлення біта в регістрі `RCC->APBxENR |= MASK` на рівні асемблера розгортається у три окремі інструкції:
1. `LDR` — читання поточного 32-бітного значення регістра в регістр процесора;
2. `ORR` — порозрядне логічне «АБО» з маскою нового модуля;
3. `STR` — запис модифікованого значення назад у пам'ять,

переривання або перемикання контексту RTOS між кроками 1 та 3 призведе до того, що налаштування, зроблені паралельним потоком, будуть безповоротно затерті старим значенням.

Для запобігання цьому диспетчер реалізує сувору потокобезпечність:
- Усі операції модифікації лічильників та регістрів захищені критичними секціями (`clock_enter_critical()` / `clock_exit_critical()`).
- Для платформ Cortex-M критична секція маскує переривання за допомогою інструкцій `CPSID i` / `CPSIE i` або через зміну порогу пріоритетів `BASEPRI`.
- Кожен запис у фізичний регістр супроводжується функцією `clock_hw_sync_barrier()`, яка виконує фіктивне читання (*dummy read*) значення назад на шину даних і накладає апаратний бар'єр пам'яті. Це гарантує, що коли функція `clock_manager_acquire()` поверне керування прикладному коду, тактовий сигнал усередині кремнію вже надійно стабілізується.

## Інтеграція з операційними системами реального часу (RTOS Integration)

Диспетчер динамічного тактування слугує фундаментом для підсистем енергозбереження сучасних RTOS:

### 1. Інтеграція з FreeRTOS Tickless Idle
У режимі безтікового сну (`configUSE_TICKLESS_IDLE = 1`) планувальник FreeRTOS зупиняє системний таймер `SysTick` і обчислює тривалість можливого глибокого сну `xExpectedIdleTime`.
Перед викликом інструкції `WFI` диспетчер тактування:
- Опитує стан шинних доменів через `clock_manager_get_bus_activity()`;
- Якщо всі шини перебувають у стані `DORMANT`, диспетчер перемикає головний стабілізатор напруги в режим низького енергоспоживання (Low-Power Regulator) та зупиняє основний помножувач PLL;
- Модулі, чиї біти в регістрах `RCC_xxxLPENR` вимкнені, автоматично знеструмлюються за тактом апаратурою чипа на весь час сну.

### 2. Інтеграція з Zephyr RTOS Power Management
У підсистемі керування живленням Zephyr PM диспетчер реєструється як базовий провайдер політик (`pm_policy`). Коли драйвер пристрою викликає `pm_device_action_run(dev, PM_DEVICE_ACTION_SUSPEND)`, Zephyr звертається до диспетчера для звільнення тактового ресурсу (`clock_manager_release()`). Якщо пристрій встановлює обмеження затримки пробудження (`PM_CONSTRAINT_CPU_DOZE`), диспетчер блокує вимкнення високошвидкісних генераторів HSE/PLL, зберігаючи швидкий вихід із переривання.

## Багатоядерні системи (Dual-Core Asymmetric Multiprocessing)

У гетерогенних мікроконтролерах із кількома ядрами (наприклад, STM32H747 з ядрами Cortex-M7 @ 480 МГц та Cortex-M4 @ 240 МГц або двоядерних чипах ESP32 / RP2350) блок RCC є єдиним апаратним ресурсом, спільним для обох процесорів.

Якщо обидва ядра одночасно спробують виконати модифікацію регістра `RCC_AHB1ENR`, звичайного маскування локальних переривань `__disable_irq()` недостатньо, оскільки воно діє лише всередині одного ядра.

Для таких архітектур диспетчер розширюється **апаратними між'ядерними семафорами** (Hardware Semaphore — `HSEM`):
1. Перед модифікацією будь-якого регістра RCC ядро зобов'язане захопити виділений апаратний канал семафора (наприклад, `HSEM_CHANNEL_RCC`):
:::tabs
```c
while (HSEM->R[HSEM_CHANNEL_RCC] != HSEM_CR_COREID_CURRENT) {
    // Очікування звільнення апаратного семафора іншим ядром
}
```
```cpp
while (hsem->r[hsem_channel_rcc] != hsem_cr_coreid_current) {
    // Очікування звільнення апаратного семафора іншим ядром
}
```
:::
2. Виконується безпечне читання, модифікація та запис у регістр RCC із фіктивним читанням.
3. Апаратний семафор негайно звільняється записом у регістр `HSEM->R[HSEM_CHANNEL_RCC] = 0`.
4. Між'ядерне сповіщення про зміну стану тактування шин передається через блок апаратних поштових скриньок (IPCC / Mailbox).

## Захист доступу до регістрів тактування через MPU та TrustZone

У системах підвищеної надійності та безпеки (наприклад, медичні прилади, промислова автоматика чи автомобільні блоки керування) прямий неконтрольований доступ прикладного коду до регістрів контролера тактування становить серйозну загрозу:
- Помилковий або шкідливий запис у регістр `RCC_AHB1ENR` може раптово вимкнути тактування порту керування аварійним клапаном чи гальмівним реле.
- Випадкова зміна дільників PLL може розігнати ядро вище допустимої частоти при поточній напрузі живлення, спричинивши незворотне зависання процесора.

Для запобігання цьому диспетчер тактування інтегрується з апаратними механізмами захисту:

### 1. Захист через блок захисту пам'яті MPU (Memory Protection Unit)
Область адрес регістрів RCC (наприклад, `0x40023800 - 0x40023BFF`) конфігурується в MPU як **виключно привілейована зона** (Privileged Access Only):
- Непривілейовані користувацькі завдання RTOS виконуються в режимі `Unprivileged Thread Mode` і не мають фізичного доступу до адресного простору RCC. Будь-яка спроба прямого запису негайно викликає виняток `MemManageFault`.
- Завдання зобов'язані викликати функції диспетчера `clock_manager_acquire()` через системний виклик `SVC` (Supervisor Call), який перемикає ядро у привілейований режим `Handler Mode`, де диспетчер перевіряє права доступу та безпечно виконує операцію.

### 2. Захист у середовищі ARM TrustZone (Cortex-M33 / Cortex-M55)
У мікроконтролерах з підтримкою TrustZone адресний простір RCC розділяється на захищену зону (`Secure RCC`) та відкриту зону (`Non-Secure RCC`). Критичні тактові генератори (головний PLL, джерела безпеки CSS, тактування криптографічних блоків) призначаються захищеному світу (`Secure World`). Відкритий світ (`Non-Secure World`) може керувати тактуванням лише дозволених базових інтерфейсів через шлюзи безпеки `Secure Gateway` (інструкція `SG`).

## Покроковий розбір алгоритмів роботи ядра диспетчера

Для глибокого розуміння архітектурних рішень розберемо покрокове виконання ключових операцій:

### 1. Алгоритм рекурсивного захоплення з гарантією відкату (`clock_manager_acquire`)
Коли викликається функція `clock_manager_acquire(PERIPH_SPI1)`:
1. Диспетчер входить у критичну секцію, блокуючи перемикання контексту RTOS.
2. Програма звертається до метаданих модуля `PERIPH_SPI1` у Flash-пам'яті та знаходить дві прямі залежності: `PERIPH_GPIOA` та `PERIPH_DMA2`.
3. Виконується рекурсивний виклик `clock_manager_acquire(PERIPH_GPIOA)`. Лічильник посилань `ref_counts[PERIPH_GPIOA]` збільшується з 0 до 1, встановлюється біт у регістрі `AHB1ENR`, виконується фіктивне читання, а лічильник активності домену `domain_active_count[BUS_DOMAIN_AHB1]` інкрементується.
4. Виконується рекурсивний виклик `clock_manager_acquire(PERIPH_DMA2)`. Аналогічно встановлюється біт DMA2 у `AHB1ENR`, а лічильник шини AHB1 збільшується до 2.
5. Якщо на будь-якому кроці виникає помилка (наприклад, переповнення лічильника або невалідний аргумент), диспетчер ініціює процедуру відкату (*rollback*), послідовно викликаючи `clock_manager_release()` для всіх успішно захоплених на попередніх кроках залежностей, після чого повертає код помилки без порушення цілісності системи.
6. Якщо всі залежності успішно підключені, збільшується лічильник самого модуля `PERIPH_SPI1`, встановлюється біт у регістрі `APB2ENR`, виконується апаратний бар'єр і лічильник активності домену `BUS_DOMAIN_APB2` стає рівним 1.

### 2. Алгоритм каскадного звільнення (`clock_manager_release`)
Коли драйвер завершує роботу й викликає `clock_manager_release(PERIPH_SPI1)`:
1. Диспетчер перевіряє, чи лічильник посилань не дорівнює нулю (захист від повторного або помилкового звільнення `CLOCK_STATUS_REF_UNDERFLOW`).
2. Лічильник `ref_counts[PERIPH_SPI1]` декрементується.
3. Якщо лічильник досяг нуля:
   - Скидається біт маски в регістрі `APB2ENR`.
   - Виконується фіктивне читання для фіксації вимкнення такту на шині.
   - Декрементується лічильник шини `BUS_DOMAIN_APB2`. Якщо він досягає нуля, шина APB2 вважається повністю сплячою (*Dormant*).
4. Виконуються рекурсивні виклики `clock_manager_release()` для всіх залежностей модуля (`PERIPH_GPIOA` та `PERIPH_DMA2`). Якщо порт `GPIOA` паралельно використовується іншим модулем (наприклад, `USART1`), його лічильник зменшиться з 2 до 1, і живлення порту фізично залишиться ввімкненим.

## Покрокове логування та трасування подій через ITM/SWO

У процесі діагностики складних періодичних збоїв або оптимізації профілю споживання заряду батареї важливо бачити точну хронологію вмикання та вимикання тактових доменів. Використання традиційних функцій форматованого виводу `printf` через послідовний порт UART є неприпустимим, оскільки передача рядка тексту займає сотні мікросекунд і сама вимагає активного тактування порту UART, що спотворює результати вимірювань.

Для неінвазивного трасування диспетчер інтегрує підтримку апаратного макротрасувальника **ARM ITM** (англ. *Instrumentation Trace Macrocell*):
- Запис 32-бітного слова в порт ITM займає рівно 1 такт процесорного ядра й виконується паралельно з роботою конвеєра через виділений апаратний контакт `SWO` (Serial Wire Output).
- Формат діагностичного пакета:
  - Біти `[31:16]`: нижні 16 біт системного таймера або лічильника циклів `DWT->CYCCNT`;
  - Біти `[15:8]`: ідентифікатор периферійного модуля `periph_id_t`;
  - Біти `[7:4]`: тип події (`0x1` — ACQUIRE, `0x2` — RELEASE, `0x3` — RESET, `0x4` — DOMAIN_SLEEP);
  - Біти `[3:0]`: поточне значення лічильника посилань `ref_count`.

## Інженерний аналіз крайових випадків та типових пасток

Під час проєктування диспетчерів тактування для висококритичних систем слід враховувати низку тонких апаратних нюансів:

### 1. Виклики з обробників переривань (ISR Context)
Якщо захоплення або звільнення тактування викликається всередині обробника апаратного переривання (ISR), стандартні м'ютекси RTOS або блокуючі функції очікування використовувати заборонено. Диспетчер повинен застосовувати виключно неблокуючі атомарні операції на базі інструкцій процесора `LDREX`/`STREX` (або `__atomic_*` у GCC/Clang) чи короткочасне маскування переривань через регістри `PRIMASK`/`BASEPRI`.

### 2. Динамічне перемикання джерел SYSCLK на льоту
Якщо системний планувальник змінює частоту ядра (наприклад, під час роботи алгоритмів динамічного регулювання напруги та частоти DVFS перемикається з PLL 168 МГц на HSI 16 МГц), коефіцієнти дільників шинних мостів можуть вимагати динамічного оновлення. Диспетчер повинен блокувати нові операції `acquire()` на час переконфігурації PLL та коректно перераховувати часові затримки.

### 3. Затримка завершення передачі периферійного модуля
Найпоширеніша помилка реалізації драйверів полягає у виклику `release()` одразу після запису останнього байта в регістр даних модуля (наприклад, `USART->DR = byte; clock_manager_release(USART1);`).

У цей момент байт лише потрапив у буфер передавача, але ще фізично не переданий по лінії зв'язку. Миттєве вимкнення тактування знеструмлює зсувний регістр передавача прямо посеред передачі біта, спотворюючи пакет. Диспетчер або драйвер зобов'язані дочекатися підняття прапорця повного завершення передачі (англ. *Transmission Complete*, прапорець `TC = 1`) перед викликом `release()`.

### 4. Апаратне скидання та запобігання шинним глітчам
При виконанні програмного апаратного скидання модуля через регістр `RCC_xxxRSTR` слід переконатися, що до модуля в цей момент не здійснюється активних транзакцій з боку процесора чи контролера DMA. Скидання модуля під час активного шинного циклу `ACCESS` призведе до миттєвого обриву сигналу `PREADY`, викликаючи збій шини або таймаут шинного моста. Диспетчер вимагає, щоб операція `clock_manager_reset_module()` викликалася строго у стані спокою або під час первинної ініціалізації.

### 5. Стрибки струму (Current Inrush) та ступеневе ввімкнення
Одночасне ввімкнення тактування кількох великих периферійних блоків (наприклад, графічного прискорювача DMA2D, контролера Ethernet MAC та інтерфейсу USB OTG) призводить до різкого стрибка споживання струму з крутим фронтом `di/dt`.

Через паразитну індуктивність доріжок живлення на друкованій платі та внутрішніх з'єднувальних провідників корпусу мікросхеми виникає імпульсне просідання напруги живлення ядра:

```
ΔV = L_trace · (di / dt)
```

Якщо величина `ΔV` перевищує запас стабільності внутрішнього LDO-регулятора, напруга живлення може короткочасно впасти нижче порогу скидання детектора `BOR` (Brownout Reset), спричиняючи раптове перезавантаження мікроконтролера.

Для запобігання цьому явищу диспетчер використовує алгоритм **ступеневого ввімкнення** (англ. *Staggered Enable*): при одночасному запиті групи потужних модулів диспетчер вставляє між їх активацією мікросекундні затримки (20–50 тактів NOP), дозволяючи локальним блокувальним керамічним конденсаторам плавно компенсувати заряд без просідання шини живлення.

### 6. Залипання лічильника посилань через пропущені виклики (Resource Leak)
Якщо драйвер у разі помилки зв'язку (наприклад, таймауту очікування I2C ACK або переповнення буфера UART) виходить із функції через аварійний `return`, оминаючи виклик `clock_manager_release()`, лічильник посилань залишається постійно більшим за нуль.

Модуль ніколи не вимкнеться, спричиняючи постійний витік енергії батареї. Для захисту від таких дефектів диспетчер підтримує сторожовий таймер активності тактування (Clock Activity Watchdog): якщо модуль утримує тактування неперервно понад заданий граничний таймаут (наприклад, більше 5 секунд без шинних транзакцій), диспетчер генерує діагностичне попередження у системний журнал або виконує примусове аварійне звільнення.

## Висновок

Впровадження централізованого диспетчера динамічного тактування перетворює розрізнене ручне керування регістрами RCC на надійну, детерміновану та енергоефективну підсистему. Завдяки атомарному підрахунку посилань, автоматичному керуванню залежностями та апаратним бар'єрам синхронізації вбудоване програмне забезпечення отримує надійний захист від апаратних збоїв `BusFault`, а батарейні пристрої демонструють максимальний час автономної роботи.
