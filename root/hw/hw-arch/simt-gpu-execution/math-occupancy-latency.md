# 🧮 Розрахунок окупансі та математика приховування латентності на GPU

Графічний процесор (GPU) спроєктовано не для мінімізації затримки однієї операції, а для максимізації сумарної пропускної здатності. Якщо центральний процесор (CPU) витрачає величезні площі кристала на кеші та позачергове виконання, щоб скоротити час виконання одного потоку, то GPU приймає високу латентність звернень до пам'яті (400–800 тактів) як неминучість і маскує її наявністю тисяч готових до виконання потоків.

Математична основа цієї моделі базується на теорії масового обслуговування, законі Літтла, теорії ймовірностей дивергенції, аналізі транзакційного підсилення пам'яті, теорії чисел у конфліктах банків, аналізі динамічного виділення спільної пам'яті та розрахунку апаратних обмежень мультипроцесора (Streaming Multiprocessor, SM).

### Закон Літтла в конвеєрах обчислювальних машин

Закон Літтла (англ. *Little's Law*), сформульований Джоном Літтлом 1961 року в теорії черг, стверджує: середня кількість заявок у стаціонарній системі дорівнює добутку середньої інтенсивності надходження заявок на середній час перебування заявки в системі.

Стосовно конвеєра графічного процесора закон набуває вигляду:

```
N = W · L
```

де:
* `N` (англ. *concurrency*) — мінімальна кількість незалежних операцій (або активних варпів), які одночасно перебувають у стані виконання або очікування на мультипроцесорі;
* `W` (англ. *throughput*) — темп видачі інструкцій мультипроцесором (кількість інструкцій варпів за один такт);
* `L` (англ. *latency*) — повна затримка виконання інструкції в тактах генератора частоти (від моменту запуску до моменту, коли результат стає доступним як операнд для наступної команди).

Якщо кількість незалежної роботи `N` менша за добуток `W · L`, конвеєри процесора неминуче простоюють, оскільки наступні інструкції не можуть стартувати через брак готових операндів.

### Приховування арифметичної латентності

Розглянемо виконання арифметичних інструкцій із плаваючою комою одинарної точності (FP32) на одному мультипроцесорі.

Нехай архітектура мультипроцесора має такі характеристики:
* Кількість планувальників варпів на SM: `W = 4` (SM може видавати до 4 інструкцій варпів за один такт);
* Апаратна затримка конвеєра FP32 FMA (Fused Multiply-Add): `L_alu = 4` такти.

Розрахуємо мінімальну кількість активних варпів `N_alu`, необхідну для 100% завантаження арифметичних блоків без простоїв між залежними командами:

```
N_alu
= W · L_alu                     [закон Літтла для арифметичного конвеєра]
= 4 · 4                         [підстановка значень: 4 планувальники, 4 такти затримки]
= 16                            [мінімальна кількість варпів без взаємних залежностей]
```

Висновок: щоб арифметичний конвеєр мультипроцесора працював із піковою продуктивністю за наявності залежностей «інструкція за інструкцією» всередині кожного потоку, планувальники SM повинні мати щонайменше 16 активних варпів.

### Приховування латентності глобальної пам'яті (VRAM)

На відміну від внутрішніх регістрів та арифметичних блоків, звернення до глобальної пам'яті GPU (GDDR6 або HBM3) проходить через шини пам'яті, контролери та кеші, що створює затримку від 400 до 800 тактів.

Нехай:
* Затримка читання з VRAM: `L_mem = 400` тактів;
* Кожен варп генерує одне звернення до пам'яті на кожні 4 арифметичні інструкції (тобто частка інструкцій пам'яті `f_mem = 0.25`);
* SM видає `W = 4` інструкції за такт.

Темп запитів до пам'яті, який видає SM:

```
W_mem
= W · f_mem                     [частка інструкцій пам'яті від загального темпу]
= 4 · 0.25                      [підстановка: 4 інструкції/такт, чверть звертається до пам'яті]
= 1                             [1 запит до пам'яті за 1 такт від SM]
```

Звідси мінімальна кількість паралельних транзакцій пам'яті в польоті (англ. *memory requests in flight*), необхідна для повного насичення шини:

```
N_mem
= W_mem · L_mem                 [закон Літтла для підсистеми глобальної пам'яті]
= 1 · 400                       [підстановка: 1 запит/такт, 400 тактів очікування]
= 400                           [незалежних транзакцій пам'яті має обслуговуватися паралельно]
```

Оскільки один варп за один раз зазвичай може мати обмежену кількість незавершених звернень до пам'яті (наприклад, від 2 до 4 через черги буферів очікування MSHR), для приховування 400 тактів затримки пам'яті графічний процесор мусить підтримувати максимальну кількість активних варпів на мультипроцесорі — аж до апаратної стелі в 32–64 варпи.

### Теоретична та реальна окупансі (Occupancy)

**Окупансі** (англ. *occupancy* — заселеність, коефіцієнт заповнення) — це відношення кількості активних варпів, виділених мультипроцесору, до максимально можливої кількості варпів, яку мультипроцесор підтримує апаратно.

```
Occupancy = N_active_warps / N_max_warps
```

Якщо мультипроцесор підтримує максимум 64 варпи (2048 потоків), а на ньому зараз активні 32 варпи (1024 потоки), окупансі становить:

```
Occupancy
= 32 / 64                       [відношення активних варпів до апаратного максимуму]
= 0.50                          [50% теоретичної окупансі]
```

Висока окупансі не гарантує максимальної швидкості автоматично, але низька окупансі (наприклад, менше 20%) робить приховування латентності пам'яті неможливим: конвеєри АЛП будуть глухо стояти в очікуванні даних із VRAM.

### Апаратні обмеження мультипроцесора: трикутник ресурсів

Кількість варпів, які можуть одночасно жити на SM, жорстко обмежується трьома апаратними пулами ресурсів:

1. **Регістровий файл (Register File):**
   Усі змінні потоків активних варпів зберігаються безпосередньо у фізичних 32-бітних регістрах SM. Загальний обсяг регістрового файлу на сучасному SM зазвичай становить `R_total = 65536` регістрів (256 КБ).
   Якщо один потік використовує `R_thread` регістрів, то один варп (32 потоки) потребує `32 · R_thread` регістрів.
   Апаратне виділення регістрів відбувається блоками з певною гранулярністю (наприклад, кратно 256 регістрам на варп).

2. **Спільна пам'ять (Shared Memory):**
   Обсяг надшвидкої локальної пам'яті на SM (наприклад, `S_total = 64` КБ або 100 КБ). Спільна пам'ять виділяється цілими блоками потоків (Thread Blocks). Якщо блок вимагає `S_block` байтів, кількість блоків на SM обмежується `S_total / S_block`.

3. **Ліміти блоків і варпів на SM:**
   * Максимальна кількість блоків на SM: `B_max` (зазвичай 16 або 32 блоки);
   * Максимальна кількість потоків на SM: `T_max` (зазвичай 1536 або 2048 потоків, тобто 48 або 64 варпи);
   * Максимальна кількість потоків на один блок: `T_block_max` (зазвичай 1024 потоки, тобто 32 варпи).

### Покроковий розрахунок окупансі на прикладі

Нехай маємо мультипроцесор із такими апаратними параметрами:
* `R_total = 65536` регістрів на SM;
* `S_total = 65536` байтів (64 КБ) Shared Memory на SM;
* `W_max = 64` варпи на SM (`T_max = 2048` потоків);
* `B_max = 32` блоки на SM;
* Гранулярність виділення регістрів: 256 регістрів на варп;
* Гранулярність виділення Shared Memory: 256 байтів на блок.

Порівняємо дві різні конфігурації функції-ядра (Kernel).

#### Конфігурація А: збалансоване ядро

Параметри ядра:
* Розмір блоку потоків: `T_block = 256` потоків (8 варпів на блок);
* Регістрів на потік: `R_thread = 32`;
* Shared Memory на блок: `S_block = 4096` байтів (4 КБ).

Розрахуємо обмеження по кожному ресурсу:

1. За лімітом блоків:
```
B_limit_blocks
= B_max                         [апаратна стеля кількості блоків на SM]
= 32                            [максимум 32 блоки]
```

2. За лімітом спільної пам'яті:
```
B_limit_smem
= ⌊S_total / S_block⌋           [ділення загального обсягу на потребу одного блоку]
= ⌊65536 / 4096⌋                [підстановка чисел]
= 16                            [максимум 16 блоків поміщається в Shared Memory]
```

3. За лімітом регістрового файлу:
```
R_per_warp_raw
= 32 · R_thread                 [регістри одного варпу: 32 потоки · 32 регістри]
= 1024                          [1024 регістри на варп]

R_per_warp
= ⌈1024 / 256⌉ · 256            [вирівнювання за гранулярністю 256]
= 1024                          [кратне 256, залишається 1024]

R_per_block
= 8 · R_per_warp                [8 варпів у блоці]
= 8 · 1024                      [підстановка]
= 8192                          [8192 регістри на один блок]

B_limit_regs
= ⌊R_total / R_per_block⌋       [ділення доступних регістрів на потребу блоку]
= ⌊65536 / 8192⌋                [підстановка чисел]
= 8                             [максимум 8 блоків поміщається в регістровий файл]
```

4. За лімітом максимальної кількості потоків (варпів):
```
B_limit_threads
= ⌊W_max / (T_block / 32)⌋      [ділення стелі варпів SM на кількість варпів у блоці]
= ⌊64 / 8⌋                      [підстановка: 64 / 8]
= 8                             [максимум 8 блоків]
```

Остаточна кількість активних блоків на SM:

```
B_active
= min(B_limit_blocks, B_limit_smem, B_limit_regs, B_limit_threads) [вузьке місце серед усіх ресурсів]
= min(32, 16, 8, 8)             [підстановка розрахованих лімітів]
= 8                             [активних блоків на SM]
```

Розрахунок активних варпів та окупансі:

```
W_active
= B_active · 8                  [8 блоків по 8 варпів]
= 8 · 8                         [підстановка]
= 64                            [64 активні варпи на SM]

Occupancy_A
= W_active / W_max              [відношення активних варпів до максимуму]
= 64 / 64                       [підстановка]
= 1.00                          [100% окупансі]
```

#### Конфігурація Б: роздування регістрів (Register Pressure)

Припустимо, що програміст розгорнув цикли (loop unrolling) і зберіг проміжні змінні, через що компілятор виділив `R_thread = 72` регістри на потік замість 32, а розмір блоку зменшив до `T_block = 128` потоків (4 варпи на блок). Shared Memory залишилася `S_block = 4096` байтів.

Розрахуємо обмеження регістрів:

```
R_per_warp_raw
= 32 · 72                       [32 потоки · 72 регістри]
= 2304                          [2304 регістри на варп]

R_per_warp
= ⌈2304 / 256⌉ · 256            [вирівнювання за гранулярністю 256]
= 2304                          [2304 ділиться на 256 без залишку: 9 · 256 = 2304]

R_per_block
= 4 · R_per_warp                [4 варпи в блоці з 128 потоків]
= 4 · 2304                      [підстановка]
= 9216                          [9216 регістрів на один блок]

B_limit_regs
= ⌊65536 / 9216⌋                [ділення загальних регістрів на потребу блоку]
= 7                             [максимум 7 блоків поміститься на SM]
```

Кількість активних варпів та окупансі:

```
W_active_B
= B_limit_regs · 4              [7 блоків по 4 варпи]
= 7 · 4                         [підстановка]
= 28                            [28 активних варпів]

Occupancy_B
= W_active_B / W_max            [відношення активних варпів до максимуму]
= 28 / 64                       [підстановка]
= 0.4375                        [43.75% окупансі]
```

Через збільшення кількості регістрів на потік у 2.25 раза (з 32 до 72) окупансі впала з 100% до 43.75%. На мультипроцесорі залишилося лише 28 варпів замість 64, що в умовах частих звернень до пам'яті призведе до простою АЛП і падіння сумарної швидкодії програми.

### Теорія ймовірностей дивергенції варпу

Нехай у тілі ядра міститься умовний оператор `if (condition) { path_A; } else { path_B; }`. Припустимо, що для кожного окремого потоку ймовірність виконання гілки `path_A` дорівнює `p`, а ймовірність вибору `path_B` дорівнює `1 - p`, причому вибір гілки різними потоками є взаємно незалежним.

Для варпу з 32 потоків:
* Ймовірність того, що **всі 32 потоки** виберуть гілку `path_A` (дивергенція відсутня):
  `P_all_A = p³²`;
* Ймовірність того, що **всі 32 потоки** виберуть гілку `path_B` (дивергенція відсутня):
  `P_all_B = (1 - p)³²`.

Ймовірність виникнення дивергенції всередині варпу (хоча б один потік вибрав `path_A` і хоча б один вибрав `path_B`):

```
P_diverge = 1 - p³² - (1 - p)³²
```

Розглянемо практичний випадок, коли алгоритм має сильну статистичну перевагу: 90% даних ідуть гілкою `path_A` (`p = 0.90`), і лише 10% вимагають виклику виняткової гілки `path_B` (`1 - p = 0.10`):

```
P_all_A
= 0.90³²                        [ймовірність, що всі 32 потоки пішли в A]
≈ 0.03433                       [лише 3.43% варпів пройдуть без розходження]

P_all_B
= 0.10³²                        [ймовірність, що всі 32 потоки пішли в B]
≈ 10⁻³²                         [практично 0]

P_diverge
= 1 - 0.03433 - 0               [підстановка значень]
= 0.96567                       [96.57% усіх варпів зазнають дивергенції!]
```

Цей результат є ключовим для архітектури SIMT: навіть якщо 90% чисел у масиві не потребують виконання гілки B, **понад 96% варпів будуть змушені послідовно виконати обидві гілки**, серіалізуючи обчислення.

Середня обчислювальна ефективність варпу (Warp Execution Efficiency) при однаковій тривалості гілок `T_A = T_B`:

```
E_warp
= 1 / (1 + P_diverge)           [відношення корисного часу до загального]
= 1 / (1 + 0.9657)              [підстановка]
≈ 0.5087                        [50.87% ефективності конвеєрів]
```

### Модель Roofline та точка балансу обчислень

Для визначення того, чи лімітується алгоритм пропускною здатністю пам'яті (Memory-Bound) чи швидкістю АЛП (Compute-Bound), застосовують модель **Roofline**.

Введемо поняття **арифметичної інтенсивності** (англ. *Arithmetic Intensity*, `AI`), яка вимірюється в кількості операцій із плаваючою комою на кожен вичитаний або записаний байт пам'яті:

```
AI = Total_FLOPs / Total_Bytes_transferred
```

Точка зламу даху (англ. *ridge point*) визначає граничну арифметичну інтенсивність заліза:

```
AI_ridge = Peak_GFLOPS / Peak_Bandwidth_GB_per_sec
```

Розглянемо чип Nvidia RTX 4090:
* Пікова теоретична продуктивність FP32: `Peak_FLOPS = 82.6` TFLOPS (82 600 GFLOPS);
* Пікова смуга пропускання VRAM GDDR6X: `Peak_BW = 1008` ГБ/с.

Розрахуємо точку зламу `AI_ridge`:

```
AI_ridge
= Peak_FLOPS / Peak_BW          [формула точки перегину моделі Roofline]
= 82600 / 1008                  [підстановка характеристик чипа]
≈ 81.94                         [FLOP на кожен переданий байт]
```

Висновки для оптимізації SIMT-програм:
* Якщо ядро виконує менше ніж `82 FLOP/байт` (наприклад, додавання двох векторів виконує 1 FLOP на 12 байтів пам'яті: `AI = 0.083 FLOP/байт`), швидкодія програми на 100% обмежена шиною VRAM. Будь-які оптимізації арифметики чи усунення дивергенції варпів не дадуть приросту швидкості без виправлення коалесцингу та використання спільної пам'яті.
* Якщо ядро має `AI > 82 FLOP/байт` (наприклад, множення матриць або згортка в нейромережах), програма виходить у зону насичення АЛП. Тут вирішальну роль відіграє висока окупансі, максимальна кількість активних варпів та усунення дивергенції.

### Математика коалесцингу та коефіцієнт підсилення транзакцій

Ефективність використання смуги пропускання глобальної пам'яті (VRAM) визначається співвідношенням між корисними даними, які запросили потоки, та обсягом байтів, який шина пам'яті була змушена фізично переслати.

Введемо коефіцієнт підсилення транзакцій (англ. *Transaction Amplification Factor*, `TAF`):

```
TAF = Bytes_transferred / Bytes_requested
```

Корисна ефективність шини пам'яті:

```
Bus_Efficiency = 1 / TAF = Bytes_requested / Bytes_transferred
```

Фізична транзакція пам'яті на GPU має фіксовану гранулярність сектора кеша (зазвичай `S_sector = 32` байти або лінія кеша `S_line = 128` байтів).

#### Випадок 1: Злитий доступ (Coalesced)

32 потоки варпу читають 32 сусідні числа float32 (`4` байти кожне) за адресами `Base + i · 4`:

```
Bytes_requested_coalesced
= 32 · 4                        [32 потоки по 4 байти]
= 128                           [128 байтів корисної інформації]

Bytes_transferred_coalesced
= 4 · S_sector                  [4 сектори по 32 байти накривають рівно 128 байтів]
= 4 · 32                        [підстановка]
= 128                           [128 байтів переслано шиною]

TAF_coalesced
= Bytes_transferred_coalesced / Bytes_requested_coalesced [розрахунок коефіцієнта підсилення]
= 128 / 128                     [підстановка]
= 1.0                           [ідеальне використання шини]

Bus_Efficiency_coalesced
= 1 / TAF_coalesced             [ефективність шини]
= 1 / 1.0                       [підстановка]
= 1.00                          [100% корисної пропускної здатності]
```

#### Випадок 2: Незлитий доступ із кроком (Strided Access)

Нехай 32 потоки читають елементи з кроком у 32 слова (`128` байтів), наприклад, при доступі до одного поля в масиві структур (AoS): `Base + i · 128`.

Кожен потік потрапляє у власну окрему кеш-лінію (або сектор). Контролер пам'яті змушений виконати 32 окремі 32-байтові транзакції:

```
Bytes_requested_strided
= 32 · 4                        [ті самі 32 корисні числа float32]
= 128                           [128 байтів корисних даних]

Bytes_transferred_strided
= 32 · S_sector                 [32 окремі сектори пам'яті]
= 32 · 32                       [підстановка: 32 · 32]
= 1024                          [1024 байти фізично вичитано з VRAM]

TAF_strided
= Bytes_transferred_strided / Bytes_requested_strided [розрахунок коефіцієнта підсилення]
= 1024 / 128                    [підстановка: 1024 / 128]
= 8.0                           [восьмикратне перевитрачання шини пам'яті]

Bus_Efficiency_strided
= 1 / TAF_strided               [ефективність шини]
= 1 / 8.0                       [підстановка]
= 0.125                         [лише 12.5% смуги шини несе корисні дані]
```

Пропускна здатність глобальної пам'яті падає у 8 разів (а на залізі зі 128-байтовими транзакціями — у 32 рази), навіть якщо всі обчислювальні конвеєри готові до роботи.

### Теорія чисел у конфліктах банків спільної пам'яті

Спільна пам'ять (Shared Memory) складається з 32 незалежних банків пам'яті шириною 4 байти (32 біти). Слово з індексом `k` (де адреса дорівнює `k · 4` байти) потрапляє в банк:

```
Bank_index = k mod 32
```

Якщо 32 потоки варпу звертаються до масиву з постійним кроком `stride` слів (`Address_thread_i = Base + i · stride`), то номер банку для потоку `i` дорівнює:

```
Bank_i = (i · stride) mod 32
```

За теоремою модульної арифметики, кількість різних банків, які будуть задіяні цим зверненням, визначається найбільшим спільним дільником (НСД, англ. *GCD*):

```
Distinct_Banks = 32 / gcd(32, stride)
```

Ступінь конфлікту банків `M` (кількість потоків, які б'ють в один і той самий банк):

```
M = 32 / Distinct_Banks = gcd(32, stride)
```

Розглянемо практичні значення кроку доступу `stride`:
* `stride = 1` (послідовний доступ): `gcd(32, 1) = 1` → `M = 1` (0 конфліктів, 1 такт);
* `stride = 2` (через одне слово): `gcd(32, 2) = 2` → `M = 2` (2-кратний конфлікт, 2 такти);
* `stride = 4`: `gcd(32, 4) = 4` → `M = 4` (4-кратний конфлікт, 4 такти);
* `stride = 32` (стовпчик матриці 32×32): `gcd(32, 32) = 32` → `M = 32` (32-кратний конфлікт, 32 такти).
* Будь-який непарний крок (`stride = 3, 5, 7, 9, ...`): `gcd(32, stride) = 1` → `M = 1` (0 конфліктів, 1 такт!).

Саме цей математичний факт пояснює, чому додавання фіктивного елемента (паддінг +1 до ширини рядка) перетворює крок з парного (32) на непарний (33) і миттєво зводить ступінь конфлікту з 32 до 1, усуваючи апаратні простої.

#### Приклад усунення конфлікту: транспонування матриці

Розглянемо запис блоку матриці розміром 32×32 числа float32 у спільну пам'ять:

1. **Без вирівнювання (розмір масиву `[32][32]`):**
   Елемент `A[row][col]` має лінійний індекс `k = row · 32 + col`.
   При читанні по стовпчиках (фіксований `col`, змінний `row = 0..31`):

```
Bank_index_raw
= (row · 32 + col) mod 32       [формула розподілу по банках]
= ((row · 32) mod 32 + col mod 32) mod 32 [властивість модульної арифметики]
= (0 + col mod 32) mod 32       [(row · 32) mod 32 = 0 для будь-якого цілого row]
= col mod 32                    [усі 32 потоки варпу б'ють у єдиний банк col!]
```

Отримуємо 32-кратний конфлікт банків (`M = 32`). Швидкість читання падає в 32 рази, а операція займає 32 такти замість одного.

2. **Із паддінгом (додавання фіктивного стовпця, розмір масиву `[32][33]`):**
   Елемент `A[row][col]` має індекс `k = row · 33 + col`:

```
Bank_index_padded
= (row · 33 + col) mod 32       [індекс із паддінгом +1 стовпець]
= (row · (32 + 1) + col) mod 32 [розклад 33 = 32 + 1]
= (row · 32 + row + col) mod 32 [розкриття дужок]
= (0 + row + col) mod 32        [(row · 32) mod 32 = 0]
= (row + col) mod 32            [циклічний зсув індексу банку для кожного рядка]
```

Для фіксованого стовпця `col` при зміні `row` від 0 до 31 значення `(row + col) mod 32` набуває всіх 32 різних значень від 0 до 31 без жодного повторення.
Ступінь конфлікту `M = 1` (конфліктів немає). Доступ виконується за 1 такт зі 100% піковою швидкістю.
