У сучасних розподілених базах даних на основі архітектури LSM-дерева (зокрема RocksDB, ClickHouse, Apache Cassandra та ScyllaDB), що опрацьовують десятки мільйонів операцій на секунду, переважна більшість запитів на точкове читання (до 85–95%) звертається до ключів, які взагалі відсутні в конкретному файлі незмінної таблиці (SSTable). Якщо кожен такий негативний запит змушує контролер сховища виконувати випадкове зчитування з твердотільного накопичувача NVMe через шину PCIe, затримка відповіді зростає з 50 наносекунд (час доступу до оперативної пам'яті) до 15–40 мікросекунд, що призводить до катастрофічного падіння пропускної здатності дискової підсистеми через паразитну ампліфікацію читання (Read Amplification).

Для миттєвого відсікання звернень до відсутніх даних кожен незмінний блок супроводжується компактним імовірнісним фільтром належності. Класичний [фільтр Блума](root:sf-algorithms/bloom-filter) десятиліттями слугував основним інструментом для цієї задачі, проте для забезпечення стандартного 1% хибних спрацьовувань він вимагає 9.6–10.0 бітів на ключ і здійснює 7 випадкових звернень до різних ділянок бітового масиву на кожен запит. На сучасних багатоядерних процесорах із глибокими конвеєрами це спричиняє до 7 послідовних промахів повз кеш-пам'ять другого та третього рівнів (L2/L3 cache misses), зупиняючи конвеєр інструкцій на сотні тактів.

Xor-фільтр (XOR Filter), розроблений Томасом Мюллером Графом та Даніелем Леміром у 2020 році, повністю змінює архітектурний баланс: він зводить перевірку належності до строго трьох звернень до пам'яті та однієї безрозгалуженої операції виключного АБО (`XOR`), скорочуючи витрати пам'яті до 8.15–8.30 бітів на ключ при тому самому 1% помилок (або до 9.84 бітів при значно нижчому рівні помилок 0.39%). Детальну хронологію виникнення структури та її еволюційний шлях від теоретичних праць із досконалого хешування до сучасних сховищ розкрито у вставці [📜 Історія та еволюція Xor-фільтра](root:sf-algorithms/xor-filter/hist-xor-filter.md).

## Інформаційна надлишковість та обмеження попередників

Ймовірнісні фільтри належності базуються на фундаментальному компромісі: вони виключають хибнонегативні відповіді (якщо елемент було збережено, фільтр гарантовано поверне «так»), але допускають контрольовану ймовірність хибнопозитивних спрацьовувань `ε` (для відсутнього елемента фільтр може з імовірністю `ε` помилково відповісти «так»).

З погляду теорії інформації Клода Шеннона, мінімальна кількість бітів, необхідна для збереження множини з `N` елементів із допустимою похибкою `ε`, визначається ентропією простору відповідей:

```
S_min = N · log₂(1/ε)     [теоретична межа Шеннона]
```

Для стандартного інженерного порогу хибних спрацьовувань 1% (`ε = 0.01`):

```
log₂(1 / 0.01)
= log₂(100)
≈ 6.6438 біта на ключ     [абсолютний теоретичний мінімум Шеннона]
```

Класичний фільтр Блума встановлює `k = ln 2 · (m / N)` незалежних бітів для кожного ключа у спільному масиві розміром `m`. Через стохастичні колізії та багаторазовий перезапис однакових комірок фактичні витрати пам'яті становлять:

```
m / N
= (1 / ln 2) · log₂(1/ε)
≈ 1.4427 · log₂(1/ε)     [витрати фільтра Блума: +44.27% надлишку]
```

Цей додатковий надлишок у 44.3% називають «податком Блума». Крім того, перевірка `k = 7` бітів у великому масиві, що не вміщується в L1/L2 кеш, породжує 7 незалежних транзакцій на шині пам'яті. Якщо масив фільтра Блума займає гігабайти оперативної пам'яті, майже кожен запит спричиняє затримку очікування даних із шини DDR (DRAM latency), яка становить від 40 до 80 наносекунд на одну транзакцію.

Створений у 2014 році [фільтр зозулі](root:sf-algorithms/cuckoo-filter) зменшив витрати до 8.4–9.0 бітів на ключ і скоротив кількість звернень до пам'яті до строго двох бакетів завдяки збереженню коротких числових відбитків (фінгерпринтів). Проте фільтр зозулі розроблявся для динамічних множин із підтримкою вставок і видалень. Для статичних незмінних наборів даних його механізм виявився надлишковим:
1. **Каскадні витіснення під час заповнення**: При коефіцієнті заповнення понад 90–95% вставка нових елементів спричиняє довгі рекурсивні ланцюжки витіснень комірок (cuckoo kicks), що різко сповільнює швидкість наповнення структури.
2. **Неможливість роботи з дублікатами**: Якщо один і той самий ключ випадково потрапляє у вхідний потік більше разів, ніж місткість бакета (`2 · b` копій), таблиця зазнає незворотного переповнення, що змушує виконувати повну перебудову структури.
3. **Обмеження для незмінних блоків**: У файлах SSTables таблиці створюються одноразово під час скидання буфера пам'яті на накопичувач. Підтримка динамічних видалень для таких файлів є абсолютно непотрібною, але за неї доводиться платити додатковими бітами пам'яті.

Xor-фільтр фокусується саме на незмінних (immutable) наборах даних, досягаючи вищої швидкості запитів, стабільної лінійної побудови `O(N)` та суттєвої економії оперативної пам'яті.

## Парадигма статичного відновлення та математична модель

Замість випадкового встановлення окремих бітів або переміщення записів між бакетами, Xor-фільтр формулює задачу перевірки належності як побудову статичного словника відновлення (англ. *static retrieval data structure*).

Нехай задано множину `S`, що містить `N` унікальних 64-бітних ключів:

```
S = {x₀, x₁, x₂, ..., x_{N-1}}
```

Фільтр створює масив `B`, що складається з `M` слотів, де кожен слот містить `r`-бітне число (зазвичай `r = 8` або `r = 16` бітів). Загальний розмір масиву обирається з невеликим надлишком відносно кількості ключів: `M = 1.23 · N`.

Масив `B` розбивається на три рівні неперетинні сегменти (блоки) `B₀, B₁, B₂` розміром `L = M / 3` кожен:
* `B₀` охоплює індекси `[0 .. L-1]`;
* `B₁` охоплює індекси `[L .. 2L-1]`;
* `B₂` охоплює індекси `[2L .. 3L-1]`.

Для кожного ключа `x` три незалежні псевдовипадкові хеш-функції `h₀(x), h₁(x), h₂(x)` обчислюють рівно по одному індексу у кожному з трьох блоків:

```
h₀(x) ∈ [0, L)
h₁(x) ∈ [L, 2L)
h₂(x) ∈ [2L, 3L)
```

Одночасно незалежна функція обчислює цільовий `r`-бітний відбиток (фінгерпринт) ключа:

```
f(x) ∈ {0, 1}^r \ {0}
```

Головний інваріант Xor-фільтра полягає в тому, що для кожного ключа `x ∈ S` значення комірок масиву `B` підбираються таким чином, щоб їхня побітова сума за модулем 2 (операція `XOR`, `⊕`) точно дорівнювала цільовому відбитку `f(x)`:

```
B[h₀(x)] ⊕ B[h₁(x)] ⊕ B[h₂(x)]
= f(x),    ∀ x ∈ S        [головний інваріант Xor-фільтра]
```

*Архітектура 3-блокового Xor-фільтра: відображення ключа запиту в три незалежні сегменти пам'яті B₀, B₁, B₂, побітове виключне АБО значень комірок та порівняння з цільовим відбитком f(x)*

### Етимологія та термінологічний апарат

В основі описаного механізму лежить кілька фундаментальних концепцій комп'ютерних наук:

* **Хешування** (англ. *hashing*, від давньофранцузького *hachier* — рубати, дрібно кришити) — перетворення довільного масиву вхідних даних фіксованої або змінної довжини у число фіксованої розрядності з псевдовипадковим та рівномірним розподілом значень.
* **Відбиток / фінгерпринт** (англ. *fingerprint* — відбиток пальця) — короткий бітовий підпис невеликої фіксованої довжини (наприклад, 8 або 16 бітів), що однозначно характеризує ключ у межах поточної функції хешування.
* **Гіперграф** (грец. *ὑπέρ* — понад, над + *γράφω* — пишу, зображую) — узагальнення математичного графа, в якому кожне ребро (звана гіперребром) може з'єднувати не дві, а довільну кількість вершин (у нашому випадку — строго 3 вершини).
* **Лущення** (англ. *peeling* — очищення від лушпиння, обдирання) — ітеративний алгоритм послідовного вилучення елементів графа, що мають найменший ступінь зв'язності (степінь 1), до повного вичерпання структури або виявлення нерозв'язного ядра.
* **Зворотна підстановка** (лат. *substitutio*, від *sub* — під + *statuere* — ставити, призначати) — класичний метод лінійної алгебри для знаходження невідомих у верхньотрикутній системі рівнянь шляхом послідовного руху від останньої змінної до першої.
* **Ациклічний** (грец. *ἀ-* — заперечна частка «не-», «без» + *κύκλος* — коло, оберт) — граф або гіперграф, що не містить замкнених циклічних залежностей та повністю зводиться до порожньої множини процедурою лущення.
* **Система лінійних рівнянь** (лат. *linea* — лінія, нитка) — математична сукупність алгебраїчних співвідношень першого степеня над заданим числовим або двійковим полем, у якій шукані змінні комбінуються виключно за допомогою операцій додавання та множення на скаляр.

## Алгоритм побудови: 3-гіперграфи та лущення 2-ядра

Побудова Xor-фільтра еквівалентна знаходженню розв'язку системи з `N` лінійних рівнянь з `M` невідомими над скінченним полем Галуа `GF(2)` (або над простором векторів відбитків `GF(2)^r`).

Пряме застосування класичного методу виключення Гаусса вимагало б кубічного часу `O(N³)`, що унеможливило б побудову фільтра для мільйонів ключів. Xor-фільтр розв'язує цю систему за строго лінійний час `O(N)` завдяки властивостям розріджених 3-однорідних гіперграфів.

### Фаза 1: Лущення гіперграфа (Peeling Phase)

Для відстеження зв'язності вершин алгоритм виділяє два компактні допоміжні масиви розміром `M` слотів:
1. `HCount[0 .. M-1]` — 8-бітний масив лічильників степенів (кількості ключів, що посилаються на даний слот).
2. `HXor[0 .. M-1]` — 64-бітний масив акумуляторів побітової суми `XOR` усіх інцидентних ключів.

Процес лущення виконується за такі кроки:

1. **Заповнення графів**:
   Для кожного ключа `k ∈ S` обчислюються його три позиції `(h₀(k), h₁(k), h₂(k))`. Для кожної з трьох позицій збільшується лічильник `HCount` та акумулюється значення ключа:
   ```
   HCount[h_j] += 1
   HXor[h_j] ^= k,    для j ∈ {0, 1, 2}
   ```

2. **Ініціалізація черги степеня 1**:
   Усі слоти `c`, для яких `HCount[c] == 1`, додаються до черги обходу FIFO. У таких комірках накопичувач `HXor[c]` містить єдиний незлущений ключ `k`, що претендує на цей слот.

3. **Ітеративне розмотування**:
   Поки черга не порожня, з неї витягується слот `pure_slot`:
   * Зчитується єдиний інцидентний йому ключ `k = HXor[pure_slot]`.
   * Пара `(k, pure_slot)` додається на вершину вихідного LIFO-стека (Last-In, First-Out).
   * Для всіх трьох позицій ключа `k` лічильники `HCount` декрементуються на 1, а значення `k` виключається з акумуляторів: `HXor[h_j] ^= k`.
   * Якщо в результаті декременту будь-який із сусідніх слотів отримує `HCount == 1`, він негайно додається до черги.

![Двоетапна побудова Xor-фільтра: лущення та зворотна підстановка](/root/eng/sf-algorithms/xor-filter/img/xor-filter-peeling.svg)
*Двоетапний процес побудови Xor-фільтра: (1) лущення 3-гіперграфа з виділенням комірок степеня 1 та записом у LIFO-стек; (2) зворотна підстановка значень у масив слотів*

### Фаза 2: Зворотна підстановка (Back-substitution)

Якщо після вичерпання черги всі `N` ключів опинилися у стеку, гіперграф є ациклічним (його 2-ядро порожнє).

Масив слотів `B` ініціалізується нулями. Далі пари `(k, pure_slot)` послідовно витягуються зі стека від вершини до дна (у зворотному порядку до моменту їхнього лущення):
1. Для ключа `k` обчислюються його три хеш-позиції `(h₀, h₁, h₂)`. Дві позиції, що відмінні від `pure_slot`, позначаються як `c_a` та `c_b`.
2. Обчислюється цільовий відбиток `fp = f(k)`.
3. Значення виділеного слота встановлюється як:
   ```
   B[pure_slot] = fp ⊕ B[c_a] ⊕ B[c_b]
   ```

Оскільки на момент лущення слот `pure_slot` був інцидентний виключно ключу `k` серед усіх ще не злущених ребер, при зворотному проході значення `B[pure_slot]` ще не використовувалося жодним іншим рівнянням. Ми отримуємо рівно один вільний ступінь свободи, що гарантує точне виконання рівності `B[h₀] ⊕ B[h₁] ⊕ B[h₂] == f(k)` без порушення будь-яких раніше зафіксованих значень.

Повне математичне доведення теореми про 2-ядра, розрахунок критичного порогу фазового переходу та аналіз трикутної структури матриці наведено у вставці [🧮 Математичний апарат Xor-фільтра: 3-гіперграфи та лущення](root:sf-algorithms/xor-filter/math-peeling-and-hypergraphs.md).

## Чому коефіцієнт розширення дорівнює c = 1.23

Ймовірність успішного завершення фази лущення без застрягання у циклічному 2-ядрі визначається відношенням кількості слотів до кількості ключів: `c = M / N`.

Теорія випадкових 3-однорідних гіперграфів показує існування різкого фазового переходу:
* При `c < 1.2217` ймовірність наявності непорожнього 2-ядра прямує до 1 при `N → ∞` (лущення майже напевно зупиниться передчасно).
* При `c > 1.2217` ймовірність повної ациклічності гіперграфа стрибкоподібно стає строго додатною величиною.

Для практичного коефіцієнта `c = 1.23`:
* Ймовірність успішної побудови з першої спроби перевищує `82%`.
* Якщо спроба виявилася невдалою (черга спорожніла до злущення всіх `N` ключів), алгоритм просто змінює 64-бітний псевдовипадковий seed хеш-функцій і повторює спробу.
* Ймовірність успішної побудови за не більше ніж 3 спроби становить:

```
P(успіх за ≤ 3 спроби)
= 1 - (1 - 0.82)³
= 1 - 0.18³
= 1 - 0.005832
≈ 99.42%        [надійність конструювання]
```

Середня кількість спроб становить `1 / 0.82 ≈ 1.22`, що гарантує детермінований лінійний час побудови `O(N)` у реальних застосунках.

## Безділильне хешування (Lemire FastRange) та рівномірність

Основою високої продуктивності Xor-фільтра є швидке відображення 64-бітного значення хешу на три неперетинні інтервали довжини `L`.

Звичайне взяття залишку від ділення `hash % L` транслюється компілятором в інструкцію `div`, що займає від 12 до 25 тактів CPU. Для усунення цієї затримки застосовується безділильне перетворення (Fast Alternative to Modulo), запропоноване Даніелем Леміром:

```
reduce(hash, L) = (uint32_t)(((uint64_t)hash * (uint64_t)L) >> 32)
```

Математично ця операція еквівалентна множенню дробової частини `hash / 2³²` на `L` і взяттю цілої частини. Оскільки вхідний хеш рівномірно розподілений на інтервалі `[0, 2³² - 1]`, результуючий індекс строго належить діапазону `[0, L - 1]` і генерується за одну процесорну інструкцію множення `mul` без жодних розгалужень чи ділень.

Для генерації трьох незалежних позицій із єдиного 64-бітного виклику хеш-функції застосовується 64-бітний генератор SplitMix64 / MurmurHash3:

:::tabs
```c
uint64_t hash = xor_hash64(key, seed);
uint32_t h0 = reduce((uint32_t)(hash >> 32), block_len);
uint32_t h1 = block_len + reduce((uint32_t)hash, block_len);
uint32_t h2 = 2 * block_len + reduce((uint32_t)(hash ^ (hash >> 16)), block_len);
```
```cpp
const uint64_t hash = hash64(key, seed);
const auto h0 = reduce(static_cast<uint32_t>(hash >> 32), block_len);
const auto h1 = block_len + reduce(static_cast<uint32_t>(hash), block_len);
const auto h2 = 2 * block_len + reduce(static_cast<uint32_t>(hash ^ (hash >> 16)), block_len);
```
:::

Розбиття масиву на 3 сегменти гарантує, що `h₀`, `h₁` та `h₂` завжди посилаються на різні фізичні адреси пам'яті, що унеможливлює виродження гіперребра у ребро з меншою кількістю вершин.

## Операція перевірки (Lookup) та апаратна ефективність

Операція перевірки належності ключа `x` у Xor-фільтрі вражає своєю лаконічністю:

:::tabs
```c
bool xor_contains(const xor_filter_t *filter, uint64_t key) {
    uint32_t h0 = reduce(hash_a(key, filter->seed), filter->block_len);
    uint32_t h1 = filter->block_len + reduce(hash_b(key, filter->seed), filter->block_len);
    uint32_t h2 = 2 * filter->block_len + reduce(hash_c(key, filter->seed), filter->block_len);

    uint8_t fp = compute_fingerprint(key, filter->seed);
    uint8_t combined = filter->B[h0] ^ filter->B[h1] ^ filter->B[h2];

    return (combined == fp);
}
```
```cpp
bool contains(uint64_t key) const noexcept {
    const auto [h0, h1, h2] = get_positions(key, seed_, block_length_);
    const uint8_t fp = compute_fingerprint(key, seed_);
    const uint8_t combined = B_[h0] ^ B_[h1] ^ B_[h2];
    return (combined == fp);
}
```
:::

### Чому Xor-фільтр швидший за аналоги на сучасних CPU

1. **Строго 3 звернення до пам'яті (Fixed Memory Accesses)**:
   Фільтр Блума з 1% помилок виконує `k = 7` або `k = 8` звернень до пам'яті. Xor-фільтр завжди виконує рівно 3 читання незалежно від бажаного рівня помилок `ε` (рівень помилок регулюється лише бітовою шириною відбитка `r`, а не кількістю хеш-функцій).
2. **Паралелізм на рівні інструкцій (Instruction-Level Parallelism, ILP)**:
   Оскільки адреси `h₀, h₁, h₂` належать трьом різним, наперед відомим сегментам `B₀, B₁, B₂`, суперскалярний процесор з кількома блоками завантаження (Load Ports) зчитує всі три значення з кеш-пам'яті L1/L2 абсолютно паралельно в межах одного тактового вікна.
3. **Повна відсутність розгалужень (Branchless Execution)**:
   Алгоритм не містить циклів `for`/`while` та розгалужень `if`/`else` під час вилучення даних. Машинний код транслюється у лінійну послідовність арифметичних та бітових інструкцій, повністю усуваючи простої процесора через хибне передбачення переходів (Branch Misprediction).

## Механізм хибнопозитивних спрацьовувань

Коли фільтр запитує ключ `y`, який ніколи не додавався до множини (`y ∉ S`), три хеш-функції `h₀(y), h₁(y), h₂(y)` обирають три довільні слоти в масиві `B`.

Оскільки значення слотів `B` конструювалися виключно на основі ключів із `S`, для невідомого ключа `y` вираз `V(y) = B[h₀(y)] ⊕ B[h₁(y)] ⊕ B[h₂(y)]` поводиться як незалежна псевдовипадкова величина, рівномірно розподілена на просторі всіх `2^r` бітових комбінацій.

Цільовий відбиток `f(y)` також генерується незалежною хеш-функцією. Ймовірність того, що випадковий результат `V(y)` випадково збіжиться зі значенням `f(y)`, становить:

```
P(Хибне спрацьовування)
= P(V(y) = f(y) | y ∉ S)
= 1 / (2^r)
= 2^(-r)        [теоретична точність Xor-фільтра]
```

Для 8-бітного відбитка (`r = 8`):
```
ε = 1 / 256 ≈ 0.00390625 (0.39%)
```

Для 16-бітного відбитка (`r = 16`):
```
ε = 1 / 65536 ≈ 0.00001525 (0.0015%)
```

На відміну від фільтра Блума, де ймовірність помилки плавно зростає при переповненні масиву, у Xor-фільтрі ймовірність помилки залишається строго постійною `2^(-r)` для будь-якого коректно збудованого фільтра.

Вибір між фільтром Блума, фільтром зозулі, Xor-фільтром та стрічковим фільтром визначається конкретними вимогами системи до пам'яті, швидкості та підтримки динамічних операцій.

*Порівняльна характеристика ймовірнісних фільтрів належності за просторовими витратами, кількістю звернень до пам'яті та підтримкою динамічних оновлень*

| Характеристика | Фільтр Блума (Bloom) | Фільтр зозулі (Cuckoo) | Xor-фільтр (XOR) | Стрічковий фільтр (Ribbon) |
|---|---|---|---|---|
| **Пам'ять при 1% FPR** | 9.6 – 10.0 біт/ключ | 8.4 – 9.0 біт/ключ | **8.15 – 8.30 біт/ключ** | 7.1 – 7.3 біт/ключ |

| **Швидкість запиту** | Помірна (багато хешів) | Висока (2 бакети) | **Максимальна (3 XOR)** | Висока (маска) |

| **Складність коду** | Мінімальна | Середня (витіснення) | **Низька (стек + черга)** | Висока (бітова лінійна алгебра) |

## Практична реалізація: C та C++

Наступний приклад демонструє лаконічне використання 8-бітного Xor-фільтра у користувацькому коді на мовах C та C++.

:::tabs
```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <stdlib.h>

/* Використання бібліотечного Xor-фільтра */
#include "xor_filter.h"

int main(void) {
    const size_t num_keys = 5;
    uint64_t dataset[5] = {
        0x1000ULL, 0x2000ULL, 0x3000ULL, 0x4000ULL, 0x5000ULL
    };

    xor_filter_8_t filter;
    if (!xor_filter_8_build(&filter, dataset, num_keys)) {
        fprintf(stderr, "Помилка конструювання Xor-фільтра\n");
        return 1;
    }

    /* Перевірка наявних ключів */
    for (size_t i = 0; i < num_keys; ++i) {
        bool exists = xor_filter_8_contains(&filter, dataset[i]);
        printf("Ключ 0x%llX: %s (очікується ТАК)\n",
               (unsigned long long)dataset[i], exists ? "ТАК" : "НІ");
    }

    /* Перевірка відсутнього ключа */
    uint64_t missing_key = 0x9999ULL;
    bool false_positive = xor_filter_8_contains(&filter, missing_key);
    printf("Відсутній ключ 0x%llX: %s\n",
           (unsigned long long)missing_key, false_positive ? "ХИБНИЙ СПАЛАХ" : "НІ (відсутній)");

    xor_filter_8_destroy(&filter);
    return 0;
}
```
```cpp
#include <iostream>
#include <vector>
#include <cstdint>
#include <span>

#include "xor_filter.hpp"

int main() {
    const std::vector<uint64_t> dataset = {
        0x1000ULL, 0x2000ULL, 0x3000ULL, 0x4000ULL, 0x5000ULL
    };

    auto filter_result = algorithms::XorFilter<uint8_t>::build(dataset);
    if (!filter_result.has_value()) {
        std::cerr << "Помилка конструювання Xor-фільтра\n";
        return 1;
    }

    const auto& filter = *filter_result;

    /* Перевірка збережених ключів */
    for (uint64_t key : dataset) {
        std::cout << "Ключ 0x" << std::hex << key << ": "
                  << (filter.contains(key) ? "ТАК" : "НІ") << " (очікується ТАК)\n";
    }

    /* Перевірка стороннього ключа */
    const uint64_t missing_key = 0x9999ULL;
    std::cout << "Відсутній ключ 0x" << std::hex << missing_key << ": "
              << (filter.contains(missing_key) ? "ХИБНИЙ СПАЛАХ" : "НІ (відсутній)\n");

    std::cout << std::dec << "Розмір структури в RAM: " << filter.size_in_bytes() << " байтів\n";
    return 0;
}
```

## Архітектурні варіації та подальший розвиток

Успіх концепції Xor-фільтра дав поштовх для розробки кількох спеціалізованих модифікацій:

1. **Fuse-фільтри (Fuse Filters)**:
   Замість строгого розбиття на 3 рівні неперетинні частини `B₀, B₁, B₂`, структура розбивається на більшу кількість сегментів (наприклад, 4 або 5), які частково перекриваються з фіксованим зсувом вікна. Це дозволяє зменшити коефіцієнт просторового розширення з `c = 1.23` до `c = 1.125`, скорочуючи розмір структури до 7.5–7.8 бітів на ключ для 1% помилок.
2. **Блоковані локальні Xor-фільтри (Blocked XOR Filters)**:
   Для великих масивів, що перевищують розмір кеш-пам'яті L3, дані розбиваються на незалежні блоки розміром 64 байти (розмір однієї лінії кешу процесора) або 4 КБ (розмір сторінки віртуальної пам'яті ОС). Головна хеш-функція спочатку обирає відповідний блок, а три внутрішні позиції обчислюються строго всередині цього блоку. Це скорочує кількість промахів кешу до строго **одного промаху** на запит ціною незначного збільшення теоретичного надлишку слотів.
3. **Стрічкові фільтри (Ribbon Filters)**:
   Інженери компанії Meta замінили випадкові 3-гіперграфи на стрічкові матриці над полем `GF(2)`. Замість трьох фіксованих позицій ключ генерує бітову маску ширини `w = 64` або `w = 128` бітів, яка розв'язується інкрементним стрічковим виключенням Гаусса. Стрічковий фільтр досягає 7.1–7.3 бітів на ключ і є найщільнішою відомою інженерною структурою перевірки належності.

## Практичні застосування та межі придатності

> 🔧 **Навіщо це в реальній інженерії.**
> Xor-фільтр є ідеальним вибором для будь-яких систем, де набори даних формуються пакетами і після створення залишаються незмінними. Він забезпечує на 20% менший розмір, ніж фільтр Блума, і на 25–35% вищу швидкість запитів порівняно з фільтрами зозулі.

### Сфери найвищої ефективності:
1. **LSM-дерева та незмінні файли SSTables**:
   У дискових рушіях таблиці SSTable записуються послідовно один раз під час скидання буфера пам'яті (MemTable flush) або ущільнення (Compaction) і більше ніколи не змінюються. Побудова Xor-фільтра під час фіналізації файлу дозволяє тримати всі індекси гарячих рівнів в оперативній пам'яті сервера зі значною економією RAM.
2. **Статичні індекси пошукових систем**:
   Словники термінів інвертованого індексу та статичні таблиці автодоповнення оновлюються фоновими пакетними процесами (Batch Jobs). Xor-фільтр дозволяє миттєво відсікати запити до слів, яких немає в словнику.
3. **Мережеві комутатори та маршрутизатори**:
   Таблиці фільтрації IP-пакетів та списки контролю доступу (ACL) завантажуються в пам'ять контролера блоками. Відсутність розгалужень у перевірці забезпечує стабільну затримку опрацювання пакетів без ризику джиттеру (Jitter).
4. **Вбудовані системи та ROM-образи (Embedded/IoT)**:
   Пристрої з обмеженим обсягом оперативної пам'яті можуть монтувати попередньо обчислений Xor-фільтр безпосередньо з енергонезалежної флеш-пам'яті NOR/NAND у режимі Zero-Copy через `mmap`.

### Коли Xor-фільтр не підходить:
* **Динамічні множини з частими вставками/видаленнями**: Якщо нові елементи повинні додаватися до фільтра в реальному часі без повної перебудови, слід використовувати [фільтр зозулі](root:sf-algorithms/cuckoo-filter) або [підрахунковий фільтр Блума](root:sf-algorithms/counting-bloom-filter).
* **Потокові дані без фіксованого розміру**: Якщо кількість вхідних ключів наперед невідома або надходить у нескінченному потоці, класичний фільтр Блума залишається більш гнучким інструментом.
