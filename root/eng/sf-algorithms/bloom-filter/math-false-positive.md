# 🧮 Математика фільтра Блума: виведення ймовірності та вибір оптимальних параметрів

Ця вставка містить повне строге математичне виведення ймовірності хибнопозитивного спрацьовування фільтра Блума, аналітичне обґрунтування оптимальної кількості хеш-функцій та мінімально необхідного обсягу пам'яті на один елемент. Вона пояснює фундаментальний зв'язок між ентропією бітового масиву, кількістю елементів, оптимізацією Кірша-Мітценмахера, деградацією при переповненні та порівняльним математичним аналізом із сучасними альтернативами (Cuckoo Filter, Counting Bloom Filter, Ribbon Filter).

## Припущення ймовірнісної моделі та теорія рівномірного розподілу

Розглянемо бітовий масив `B` розміром `m` бітів, у якому всі елементи початково ініціалізовані нулями (`0`). У масив послідовно додається `n` унікальних елементів із множини `S`. Для розміщення кожного елемента використовується `k` незалежних хеш-функцій:

```
h₁, h₂, ..., hₖ : S → {0, 1, 2, ..., m - 1}
```

Для побудови суворої математичної моделі приймається **припущення про просте рівномірне хешування** (Simple Uniform Hashing Assumption, SUHA). Воно полягає у двох фундаментальних вимогах:
1. Кожна хеш-функція відображає будь-який елемент у будь-який індекс масиву `[0, m - 1]` із абсолютно однаковою ймовірністю `1/m`, незалежно від значення самого елемента.
2. Значення, повернені різними хеш-функціями для одного й того самого елемента, є взаємно незалежними випадковими величинами.

На практиці ідеально незалежні хеш-функції є обчислювально дорогими, оскільки вимагають генерирування багатьох випадкових солей або обчислення окремих криптографічних залишків. Однак, як буде доведено нижче, для збереження ймовірнісних гарантій достатньо застосування високоякісних некриптографічних хеш-функцій із рівномірним розподілом (наприклад, MurmurHash3 або CityHash).

## Покрокове виведення ймовірності встановлення біта

Знайдемо ймовірність того, що конкретно обраний біт у масиві залишиться дорівнювати `0` після вставки всіх даних.

**Крок 1. Аналіз дії однієї хеш-функції.**
При вставці одного елемента та застосуванні однієї хеш-функції `hᵢ` ймовірність того, що конкретно обраний комірковий біт **не буде** вибраний цією функцією, дорівнює частці невибраних комірок від їхньої загальної кількості:

```
P(біт не вибрано 1 хешем) = 1 - 1/m
```

**Крок 2. Аналіз комплексу з k хеш-функцій.**
Оскільки один елемент обробляється `k` незалежними хеш-функціями, ймовірність того, що конкретний біт залишиться дорівнювати `0` після послідовного застосування всіх `k` функцій для цього елемента, дорівнює добутку ймовірностей незалежних подій:

```
P(біт не вибрано 1 елементом) = (1 - 1/m)ᵏ
```

**Крок 3. Накопичувальний ефект вставки n елементів.**
Після послідовного додавання всіх `n` елементів до фільтра було виконано загалом `n · k` незалежних операцій звернення до масиву. Отже, ймовірність того, що конкретний біт жодного разу не був обраний і зберіг значення `0`, становить:

```
P(біт дорівнює 0 після n елементів) = (1 - 1/m)ⁿᵏ
```

Для великих значень розміру масиву `m` (що завжди виконується у реальних системах, де `m` становить мільйони бітів) скористаємося другою чудовою границею математичного аналізу:

```
lim_{x → ∞} (1 - 1/x)ˣ = 1/e ≈ 0.367879441
```

Перетворимо вираз для ймовірності нульового біта шляхом виділення показника `m` у внутрішній степені:

```
(1 - 1/m)ⁿᵏ
= ((1 - 1/m)ᵐ)^(kn/m)      [перегрупування показника степеня]
≈ e^(-kn/m)                [граничний перехід при m → ∞]
```

Помилка цього наближення є надзвичайно малою і зменшується як `O(1/m)`, що робить експоненційну формулу біля границі точним інструментом для практичних інженерних розрахунків.

**Крок 4. Ймовірність одиничного біта.**
Ймовірність `p₁` того, що конкретний біт у масиві буде встановлений в одиницю (`1`) внаслідок перекриття хоч одним із викликів хеш-функцій, є протилежною подією до збереження нуля:

```
p₁ = P(біт дорівнює 1) = 1 - (1 - 1/m)ⁿᵏ ≈ 1 - e^(-kn/m)
```

## Ймовірність хибнопозитивного спрацьовування та кореляція бітів

Виконаємо запит перевірки належності для елемента `y`, який **гарантовано не додавався** до фільтра (`y ∉ S`). 

Фільтр Блума поверне ствердну відповідь (`true`), якщо всі `k` позицій `h₁(y), h₂(y), ..., hₖ(y)` у бітовому масиві виявляться встановленими в `1`. Це і є **хибнопозитивне спрацьовування** (false positive).

У найпростішому наближенні припускають, що події встановлення різних бітів є незалежними. За цього припущення ймовірність `p` хибного спрацьовування обчислюється як добуток ймовірностей знаходження `1` у кожній із `k` перевірюваних позицій:

```
p = (p₁)ᵏ
= (1 - (1 - 1/m)ⁿᵏ)ᵏ       [точна математична формула]
≈ (1 - e^(-kn/m))ᵏ          [асимптотична наближена формула]
```

### Суворіше доведення з урахуванням кореляції бітів

У дійсності біти масиву не є повністю незалежними: якщо ми знаємо, що багато інших бітів вже дорівнюють `1`, це трохи підвищує ймовірність того, що й поточний біт дорівнює `1` (оскільки загальна кількість встановлених бітів у масиві є випадковою величиною). 

Суворіший аналіз, виконаний за допомогою концентраційних нерівностей (нерівність Чернова або мартингали Дуба), показує, що точна ймовірність хибнопозитивного спрацьовування обмежується виразом:

```
P(хибне спрацьовування) ≤ (1 - e^(-kn/m))ᵏ · (1 + O(√(k / m)))
```

Оскільки у реальних фільтрах розмір масиву `m` перевищує кількість хеш-функцій `k` на 5–6 порядків, поправковий член `O(√(k / m))` є мізерно малим, і класична формула `p ≈ (1 - e^(-kn/m))ᵏ` є математично обґрунтованою та надійною.

З аналізу формули видно поведінку функції `p(k)` при зміні `k`:
- При малій кількості хеш-функцій (`k → 1`) кількість перевіряних бітів мала. Незважаючи на те, що сам масив залишається відносно порожнім, імовірність випадкового збігу одного біта залишається високою.
- При занадто великій кількості хеш-функцій (`k → ∞`) бітовий масив переповнюється одиницями (`p₁ → 1`). Перевірка великої кількості бітів майже напевно потрапить лише на одиниці, що знову призводить до `p → 1`.

Отже, існує точка глобального мінімуму функції `p(k)`, яка забезпечує найнижчу ймовірність помилки для заданого обсягу пам'яті.

## Виведення оптимальної кількості хеш-функцій k

Для знаходження точки мінімуму прологарифмуємо асимптотичний вираз для ймовірності `p`:

```
ln(p) = ln((1 - e^(-kn/m))ᵏ)
= k · ln(1 - e^(-kn/m))    [властивість логарифма степеня]
```

Введемо безрозмірну змінну `g = kn/m`, яка характеризує середню кількість хеш-звернень на одну комірку масиву. Звідси виразимо `k`:

```
k = g · (m / n)
```

Підставимо отримане значення `k` у вираз для логарифма ймовірності:

```
ln(p) = (m/n) · g · ln(1 - e^(-g))
```

Оскільки співвідношення `m/n` (виділена пам'ять на один елемент) є константою, мінімізація `ln(p)` по змінній `k` еквівалентна мінімізації скалярної функції `f(g) = g · ln(1 - e^(-g))` по змінній `g`.

Знайдемо першу похідну `f'(g)` за правилом диференціювання добутку:

```
f'(g) = d/dg [g · ln(1 - e^(-g))]
= 1 · ln(1 - e^(-g)) + g · (d/dg [ln(1 - e^(-g))])
= ln(1 - e^(-g)) + g · (e^(-g) / (1 - e^(-g)))
```

Прирівняємо похідну `f'(g)` до нуля для пошуку екстремуму:

```
ln(1 - e^(-g)) + (g · e^(-g)) / (1 - e^(-g)) = 0
```

Це рівняння має єдиний дійсний розв'язок, коли `e^(-g) = 1/2`, що легко перевіряється безпосередньою підстановкою:

```
ln(1 - 1/2) + (ln(2) · (1/2)) / (1 - 1/2)
= ln(1/2) + ln(2)                         [спрощення знаменника (1 - 1/2) = 1/2]
= -ln(2) + ln(2) = 0                      [за тотожністю ln(1/2) = -ln(2)]
```

Отже, оптимальне значення змінної становить `g = ln(2)`. Згадуючи визначення `g = kn/m`, отримуємо формулу **оптимальної кількості хеш-функцій**:

```
k_opt = (m/n) · ln(2) ≈ 0.693147 · (m/n)
```

### Фізичний та інформаційний зміст оптимуму

Фундаментальний висновок з отриманого розв'язку полягає в наступному. Якщо підставити `k_opt` у формулу ймовірності одиничного біта `p₁`, ми отримаємо:

```
p₁ = 1 - e^(-k_opt · n / m)
= 1 - e^(-(m/n · ln 2) · n / m)          [підстановка k_opt = (m/n) · ln 2]
= 1 - e^(-ln 2)                           [скорочення m/n та n/m]
= 1 - 1/2 = 0.5                           [за тотожністю e^(-ln 2) = 1/2]
```

Це означає, що **у найоптимальніше налаштованому фільтрі Блума рівно 50% бітів масиву дорівнюють 1, і 50% бітів дорівнюють 0**. 

З точки зору теорії інформації Шеннона, бітовий послідовний шар має максимальну ентропію (1 біт інформації на осередки) саме тоді, коли ймовірність поява нулів та одиниць є однаковою і дорівнює `0.5`. Якщо масив заповнений одиницями менше або більше ніж на половину, структура використовує виділений обсяг пам'яті не з максимально можливою інформаційною щільністю.

## Формула необхідної пам'яті m та бітів на елемент

Підставимо оптимальну кількість хеш-функцій `k_opt = (m/n) · ln(2)` безпосередньо у вираз для ймовірності хибнопозитивного спрацьовування:

```
p_opt = (1 - 1/2)^(k_opt)
= (1/2)^(k_opt) = 2^(-k_opt)
```

Прологарифмуємо обидві частини за основою 2:

```
log₂(p) = -k_opt
= - (m/n) · ln(2)
```

Виразимо необхідне співвідношення бітів на один елемент `m/n`:

```
m/n = - log₂(p) / ln(2)
= - ln(p) / (ln(2))²       [зміна основи логарифма]
≈ - 1.442695 · log₂(p)
```

Звідси отримуємо підсумкову формулу для **обчислення загального розміру бітового масиву m**:

```
m = - (n · ln(p)) / (ln(2))² ≈ - 1.442695 · n · log₂(p)
```

Цей виражений результат є ключовим теоретичним досягненням Бертона Блума: необхідна кількість бітів пам'яті на один збережений елемент є функцією **виключно** від заданого рівня точності `p`. Вона абсолютно не залежить ні від фізичного розміру самих ключів (чи це 4-байтове ціле число, чи 10-кілобайтовий документ), ні від сукупної кількості елементів `n`.

## Обґрунтування оптимізації Кірша-Мітценмахера

Класична модель фільтра Блума вимагає обчислення `k` повністю незалежних хеш-функцій. На практиці обчислення `k` окремих хешів для кожного елемента (наприклад, за допомогою `k` викликів хеш-алгоритму) створює високе навантаження на процесор і стає вузьким місцем продуктивності.

У 2006 році Адам Кірш (Adam Kirsch) та Майкл Мітценмахер (Michael Mitzenmacher) опублікували фундаментальну теорему, яка доводить, що замість `k` хеш-функцій достатньо обчислити **лише дві** 64-бітні хеш-функції `g(x)` та `h(x)`. Решта `k` індексів повторно згенеровуються за допомогою їхньої лінійної комбінації:

```
g_i(x) = (g(x) + i · h(x)) mod m,    де i ∈ {0, 1, ..., k - 1}
```

### Теоретичне обґрунтування

Математичне доведення Кірша-Мітценмахера спирається на аналіз розподілу пар хеш-значень. Вони довели, що асимптотична ймовірність хибнопозитивного спрацьовування при використанні лінійної комбінації двох хеш-функцій маскується під повну незалежність:

```
p_KM = (1 - e^(-kn/m))ᵏ + O(1/m)
```

Член відхилення `O(1/m)` прямує до нуля зі зростанням розміру масиву `m`. Для будь-яких практичних розмірів масивів (де `m > 1000`) різниця у ймовірності помилки між ідеально незалежними `k` хеш-функціями та лінійною генерацією Кірша-Мітценмахера не перевищує `0.0001%`. Це дозволяє зменшити обчислювальні витрати CPU при вставці та перевірці в `k/2` разів без втрати точності.

## Деградація фільтра при переповненні

Що відбувається з ймовірністю помилки `p`, якщо кількість доданих елементів перевищує розрахункове значення `n`? 

Позначимо коефіцієнт переповнення як `α = n_actual / n_design > 1`. Тоді фактична ймовірність помилки `p_actual` виражається формулою:

```
p_actual = (1 - e^(-k · α · n_design / m))ᵏ
= (1 - (1/2)α)ᵏ
```

Розглянемо приклад: фільтр розраховано на `p = 1%` (`m/n = 9.6`, `k = 7`). Якщо додати у фільтр вдвічі більше елементів (`α = 2`):

```
p_actual = (1 - (1/2)²)⁷
= (1 - 0.25)⁷                             [піднесення 1/2 до квадрата]
= (0.75)⁷ ≈ 0.133 (13.3%)                 [обчислення степеня]
```

Як видно з розрахунку, при подвоєнні кількості елементів ймовірність хибного спрацьовування зростає з `1%` до `13.3%`, а при потроєнні (`α = 3`) досягає `38.4%`. Фільтр Блума не втрачає коректності (хибнонегативні відповіді як і раніше неможливі), але його захисна ефективність стрімко падає.

## Недетерміновані запити та закон Зіпфа

У реальних мережевих системах та СУБД частота запитів до елементів не є рівномірною. Повторні запити відсутніх елементів зазвичай підпорядковуються **закону Зіпфа** (Zipfian distribution): невелика кількість відсутніх ключів запитується критично часто.

Якщо відсутній ключ `y_bad` потрапляє у категорію хибнопозитивних спрацьовувань фільтра Блума, то **кожен повторний запит цього самого ключа буде стійко викликати марне зчитування з диска**. 

У разі рівномірного розподілу запитів середньозважена частка помилок дорівнює `p`. Однак при розподілі Зіпфа із показником степеня `s > 1`, якщо найчастіше запитувані ключі виявляться хибнопозитивними, фактична частка марного I/O може зрости у кілька разів. Цей фактор необхідно враховувати під час вибору запасу точності `p` у веб-проксі та NoSQL базах даних.

## Математичне порівняння з сучасними ймовірнісними альтернативами

Класичний фільтр Блума є не єдиною ймовірнісною структурою даних для перевірки належності елемента. Порівняємо його математичні характеристики з трьома основними сучасними альтернативами.

### 1. Counting Bloom Filter (Лічильний фільтр Блума)

Для підтримки видалення елементів кожну 1-бітну комірку класичного фільтра Блума замінюють на `c`-бітний лічильник (зазвичай `c = 4` біти). При вставці елемента лічильники у `k` позиціях збільшуються на 1 (`increment`), а при видаленні — зменшуються на 1 (`decrement`).

Математична ймовірність переповнення 4-бітного лічильника (досягнення значення 15) описується розподілом Пуассона з параметром `λ = kn/m = ln(2) ≈ 0.693`:

```
P(переповнення лічильника) ≤ m · P(Poisson(λ) ≥ 15) ≈ m · 1.37 · 10^(-15)
```

Отже, 4-бітного лічильника абсолютно достатньо для практичних задач. Однак ціна операції видалення є математично високою: **витрати пам'яті зростають у 4 рази** (замість ~10 бітів на елемент потрібно 40 бітів).

### 2. Cuckoo Filter (Фільтр зозулі)

Фільтр зозулі зберігає не бітовий слід, а короткі підписи (fingerprints) розміром `f` бітів у таблиці з `b` слотами на відро (bucket). Індекси двох можливих відер для елемента `x` обчислюються за допомогою часткового хешування зозулі (Partial-key Cuckoo Hashing):

```
i₁ = hash(x) mod B
i₂ = (i₁ ⊕ hash(fingerprint(x))) mod B
```

Математична перевага фільтра зозулі полягає у теоретичній межі пам'яті: для досягнення ймовірності помилки `p` він вимагає `m/n = (log₂(1/p) + 2) / α` бітів, де `α ≈ 0.955` — коефіцієнт заповнення таблиці. При малій ймовірності помилки (`p < 3%`) фільтр зозулі потребує **менше пам'яті, ніж класичний фільтр Блума**, і при цьому природно підтримує операцію видалення ключів.

### 3. Ribbon Filter (Стрічковий фільтр)

Розроблений інженерами RocksDB у 2021 році, стрічковий фільтр моделює вставку елементів як систему лінійних рівнянь над двозначним полем Galois GF(2). Матриця коефіцієнтів має вузьку «стрічкову» діагональну структуру, що дозволяє вирішувати систему за допомогою швидкої елімінації Ґаусса з використанням векторних інструкцій AVX2/AVX-512.

Стрічковий фільтр досягає теоретичної межі Шеннона `m/n ≈ log₂(1/p) + 0.3` бітів на елемент. Це на **30% ефективніше за класичний фільтр Блума** (який вимагає `1.44 · log₂(1/p)` бітів), що дозволяє економити сотні гігабайтів оперативної пам'яті у надвеликих дата-центрах.

### Практичний розрахунок параметрів для бази даних

**Задача:** Необхідно спроєктувати фільтр Блума для таблиці RocksDB, яка містить `n = 50 000 000` (50 мільйонів) записів. Вимога системи: ймовірність марного звернення до диска не повинна перевищувати `p = 0.5%` (0.005).

**Крок 1. Розрахунок загального розміру масиву бітів m:**

```
m = - (50 000 000 · ln(0.005)) / (0.693147)²
= - (50 000 000 · (-5.298317)) / 0.480453 [обчислення ln(0.005) та квадрата ln(2)]
= 264 915 870 / 0.480453                 [множення у чисельнику]
≈ 549 306 480 бітів                       [ділення]
```

Переведемо біти у мегабайти:

```
Розмір у байтах = 549 306 480 / 8 = 68 663 310 байтів
Розмір у МБ = 68 663 310 / (1024 · 1024) ≈ 65.48 МБ
```

**Крок 2. Обчислення кількості бітів на елемент:**

```
m/n = 549 306 480 / 50 000 000 ≈ 10.99 бітів/елемент
```

**Крок 3. Обчислення оптимальної кількості хеш-функцій k:**

```
k = (m/n) · ln(2)
= 10.99 · 0.693147                        [підстановка m/n = 10.99 та ln(2)]
= 7.618 ≈ 8 хеш-функцій                   [округлення до найближчого цілого]
```

**Висновок:** Для збереження 50 мільйонів ключів із гарантією 99.5% відсутності хибних дискових зчитувань достатньо виділити **65.5 МБ** оперативної пам'яті та використовувати **8** хеш-функцій. Для порівняння: збереження самих ключів розміром по 32 байти у звичайній хеш-таблиці вимагало б щонайменше 1.6 ГБ пам'яті (у 24 рази більше).
