# 📋 Інтерфейс та контракт абстрактного типу даних «Граф»

Уніфікований контракт абстрактного типу даних графа: сигнатури функцій, поведінка ітераторів по сусідах, концептуальні вимоги до пам'яті, дескриптори вузлів і ребер та таблиця асимптотичних гарантій для C та C++.

Абстрактний тип даних (АТД) «Граф» інкапсулює топологічну структуру множини вершин `V` та ребер `E`, приховуючи внутрішнє фізичне розташування даних у пам'яті (матриця, динамічні списки, CSR або списки пар) за єдиним стабільним інтерфейсом.

У класичному системному програмуванні створення абстракції для графа є значно складнішим завданням, ніж проектування лінійних контейнерів на зразок динамічного масиву чи двозв'язного списку. Причина криється в багатовимірності топологічних відношень: один і той самий алгоритм у процесі роботи може вимагати швидкого перебору вихідних ребер вершини, ітерації за вхідними ребрами, послідовного сканування всіх ребер системи або миттєвої перевірки наявності зв'язку між довільною парою вузлів. 

Жодна фізична структура даних не здатна забезпечити однаково швидке виконання всіх цих операцій одночасно. Тому контракт АТД графа чітко специфікує категорії операцій, правила валідації дескрипторів, концептуальні вимоги до ітераторів та семантику інвалідації посилань під час динамічної модифікації топології.

## 1. Дескриптори вершин та ребер

Для забезпечення повної незалежності прикладних алгоритмів від внутрішньої структури графа контракт спирається на два базові типи дескрипторів:

1. **Дескриптор вершини (`vertex_descriptor`)**: Числовий ідентифікатор або непрозорий дескриптор, що однозначно визначає вузол у межах графа. У цілочисельній індексації це значення від `0` до `|V| - 1`. У розподілених чи динамічних графах дескриптор може бути 64-бітним глобальним ідентифікатором (GUID/UUID) або покажчиком на внутрішній вузол.
2. **Дескриптор ребра (`edge_descriptor`)**: Об'єкт, що однозначно визначає ребро між парою вершин `(u, v)`. Для незважених простих графів це пара індексів джерела та призначення. Для мультиграфів дескриптор містить додатковий унікальний ідентифікатор зв'язку, що дозволяє розрізняти паралельні дуги з однаковими кінцями.

## 2. Сигнатури інтерфейсу: C та C++

Розглянемо повний контракт операцій для маніпуляції топологією та доступу до суміжних елементів.

```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* Непрозорий тип графа */
typedef struct Graph Graph;

/* Створення графа з фіксованою або початковою кількістю вершин */
Graph* graph_create(uint32_t num_vertices, bool is_directed);
void   graph_destroy(Graph *g);

/* Топологічні запити розміру */
uint32_t graph_vertex_count(const Graph *g);
size_t   graph_edge_count(const Graph *g);
bool     graph_is_directed(const Graph *g);

/* Модифікація зв'язків */
bool graph_add_edge(Graph *g, uint32_t u, uint32_t v, double weight);
bool graph_remove_edge(Graph *g, uint32_t u, uint32_t v);
bool graph_add_vertex(Graph *g, uint32_t *out_vertex_id);
bool graph_remove_vertex(Graph *g, uint32_t u);

/* Запити суміжності */
bool   graph_has_edge(const Graph *g, uint32_t u, uint32_t v);
double graph_get_edge_weight(const Graph *g, uint32_t u, uint32_t v);
bool   graph_set_edge_weight(Graph *g, uint32_t u, uint32_t v, double weight);

/* Ступені вершин */
uint32_t graph_out_degree(const Graph *g, uint32_t u);
uint32_t graph_in_degree(const Graph *g, uint32_t u);

/* Ітератор по вихідних сусідах */
typedef struct {
    const Graph *graph;
    uint32_t vertex;
    size_t state_cursor;

GraphNeighborIter graph_neighbors_begin(const Graph *g, uint32_t u);
bool graph_neighbors_next(GraphNeighborIter *it, uint32_t *out_target, double *out_weight);
```

```cpp
#include <concepts>
#include <ranges>
#include <span>
#include <cstdint>
#include <optional>

/* C++20 Concept: вимоги до базового графа */
template <typename G>
concept GraphConcept = requires(const G& g, G& mut_g, uint32_t u, uint32_t v, double w) {
    // Топологічні розміри
    { g.vertex_count() } -> std::same_as<uint32_t>;
    { g.edge_count() }   -> std::same_as<std::size_t>;
    { g.is_directed() }  -> std::same_as<bool>;

    // Запити суміжності
    { g.has_edge(u, v) } -> std::same_as<bool>;
    { g.out_degree(u) }  -> std::same_as<uint32_t>;

    // Діапазон сусідів (forward range або span)
    { g.neighbors(u) }   -> std::ranges::forward_range;

    // Модифікація топології
    { mut_g.add_edge(u, v) } -> std::same_as<bool>;
    { mut_g.remove_edge(u, v) } -> std::same_as<bool>;
};

/* C++20 Concept: розширення для зваженого графа */
template <typename G>
concept WeightedGraphConcept = GraphConcept<G> && requires(const G& g, uint32_t u, uint32_t v) {
    { g.edge_weight(u, v) } -> std::same_as<std::optional<double>>;
};
```

## 3. Таблиця асимптотичних гарантій операцій

У таблиці наведено гарантії часової складності для кожного методу залежно від обраного типу внутрішньої структури даних (`V = |V|`, `E = |E|`, `deg(u)` — ступінь вершини `u`):

| Операція інтерфейсу | Матриця суміжності | Списки векторів | Зв'язані списки | Compressed Sparse Row (CSR) | Список ребер |
|---|---|---|---|---|---|
| `has_edge(u, v)` | `O(1)` | `O(deg(u))` | `O(deg(u))` | `O(log(deg(u)))` (сортований) | `O(E)` |
| `neighbors(u)` (перебір) | `Θ(V)` | `Θ(deg(u))` | `Θ(deg(u))` | `Θ(deg(u))` (найшвидший у кеші) | `Θ(E)` |
| `add_edge(u, v)` | `O(1)` | `O(1)` аморт. | `O(1)` | Не підтримується (`O(E)` перебудова) | `O(1)` |
| `remove_edge(u, v)` | `O(1)` | `O(deg(u))` | `O(deg(u))` | Не підтримується (`O(E)` перебудова) | `O(E)` |
| `out_degree(u)` | `Θ(V)` або `O(1)`* | `O(1)` | `O(deg(u))` або `O(1)`* | `O(1)` (`offsets[u+1] - offsets[u]`) | `Θ(E)` |
| `in_degree(u)` | `Θ(V)` | `Θ(V + E)` | `Θ(V + E)` | `Θ(V + E)` (або `O(1)` у CSC) | `Θ(E)` |
| `memory_footprint` | `Θ(V²)` | `Θ(V + E)` | `Θ(V + E)` | `Θ(V + E)` (мінімальна стала) | `Θ(E)` |

*\* За умови підтримки окремого масиву кешованих ступенів.*

## 4. Контракт інвалідації ітераторів та модифікації топології

Будь-яка зміна структури графа під час активного обходу накладає обмеження на дійсність покажчиків та ітераторів:

1. **Матриця суміжності**:
   * Додавання або видалення ребер (`add_edge` / `remove_edge`) змінює значення в наявних комірках `A[u][v]` і **ніколи не інвалідує** ітератори та покажчики.
   * Додавання нової вершини вимагає зміни розмірності сітки з `V × V` на `(V+1) × (V+1)`, що викликає повну релокацію неперервного буфера в купі та робить недійсними всі наявні покажчики на рядки.

2. **Списки векторів (`std::vector<std::vector>`)**:
   * Додавання ребра у вершину `u` може спричинити вичерпання ємності (`capacity`) внутрішнього вектора `adj_[u]` і його переалокацію. Це інвалідує ітератори та зрізи (`std::span`), що посилаються на список сусідів саме вершини `u`, але не впливає на інші вершини.
   * Додавання вершини інвалідує зовнішній вектор дескрипторів.

3. **Compressed Sparse Row (CSR)**:
   * Структура є **строго незмінною (immutable)**. Будь-яка спроба додавання чи видалення зв'язків вимагає створення нової копії масивів `offsets` та `edges`. Ітератори по зрізах дійсні протягом усього життєвого циклу об'єкта графа.

## 5. Властивості та карти атрибутів (Property Maps)

У багатьох алгоритмах (наприклад, фарбування графів, пошук компонент зв'язності або алгоритм Дейкстри) вершинам та ребрам присвоюються динамічні атрибути: статус відвідування `visited`, відстань `distance`, попередник `predecessor`.

Контракт проектування графів передбачає два підходи до збереження атрибутів:

* **Внутрішні властивості (Internal Properties)**: Властивості пакуються безпосередньо у вузол структури (наприклад, `struct Vertex { uint32_t id; Color color; double distance; };`). Цей підхід зручний для простих навчальних програм, проте робить структуру жорстко прив'язаною до конкретного алгоритму і сповільнює обходи, якщо поля атрибутів заповнюють кеш-лінії непотрібними даними.
* **Зовнішні властивості (External Property Maps)**: Граф зберігає виключно чисту топологію зв'язків (ідентифікатори `0 .. V-1`), а кожен алгоритм створює власні незалежні масиви розміром `|V|` у стеку або купі (наприклад, `std::vector<bool> visited(g.vertex_count(), false)`). Це забезпечує повторне використання графа багатьма паралельними потоками одночасно без конфліктів за спільні дані.

## 6. Багатопотоковість та контракти синхронізації

У високонавантажених сервісах граф часто є спільним ресурсом для багатьох робочих потоків. Контракт АТД графа розрізняє три рівні безпеки:

1. **Паралельне читання (Concurrent Read-Only)**: Усі структури (включно з CSR, матрицями та векторами) підтримують необмежене одночасне читання з довільної кількості потоків без м'ютексів чи атомарних операцій.
2. **Паралельна модифікація ваг ребер**: Якщо топологія фіксована, але ваги зв'язків оновлюються динамічно, комірки матриці або елементи масиву `weights` у CSR можуть оголошуватися як `std::atomic<double>`, що усуває потребу в блокуваннях.
3. **Паралельна модифікація топології**: Додавання та видалення ребер у реальному часі вимагає або поблокового блокування списків окремих вершин (Fine-Grained Locking), або використання спеціалізованих lock-free структур даних.

## 7. Патерн «Відвідувач» (Visitor Pattern) та неявні графи

Для максимального відокремлення логіки обходу від конкретної прикладної задачі бібліотеки рівня Boost Graph Library (BGL) використовують патерн «Відвідувач» (Visitor).

Замість написання окремого циклу обходу для кожного завдання, базовий рушій BFS або DFS викликає спеціальні функції зворотного виклику (події) у фіксовані моменти життєвого циклу вершини:
1. `discover_vertex(u)` — вершину вперше виявлено в черзі обходу;
2. `examine_edge(u, v)` — алгоритм розглядає ребро між `u` та `v`;
3. `tree_edge(u, v)` — ребро веде до ще не відвіданої вершини і стає частиною дерева пошуку;
4. `finish_vertex(u)` — усі сусіди вершини повністю опрацьовані.

Така концептуальна абстракція дозволяє запускати алгоритми пошуку шляхів навіть на **неявних графах** (Implicit Graphs), де вершини та ребра не зберігаються в пам'яті комп'ютера взагалі, а генеруються на льоту математичними правилами переходу (наприклад, простір станів кубика Рубіка або гра в шахи).
