# 📋 Довідник інтерфейсів та інваріантів сортування бульбашкою

Сортування бульбашкою (Bubble Sort) та його двонаправлена модифікація Cocktail Shaker Sort представляють клас простих обмінних алгоритмів in-place сортування. Вони характеризуються детермінованим використанням пам'яті, повною відсутністю динамічних алокацій, строгою стабільністю збереження порядку еквівалентних ключів та простотою апаратної верифікації. Цей довідник містить вичерпну специфікацію програмних інтерфейсів для системних мов програмування C та C++, детальний опис контрактних зобов'язань (преумови, постумови, інваріанти), підсумкові таблиці часової та просторової складності, а також інженерні рекомендації щодо розробки вбудованого програмного забезпечення (Embedded Systems) та систем жорсткого реального часу (Hard Real-Time).

## 3. Формальні контрактні зобов'язання (Design by Contract)

Коректність роботи функцій сортування спирається на суворе дотримання формального контракту між клієнтським кодом і алгоритмічною бібліотекою.

### 3.1. Преумови (Preconditions)

Клієнтський код перед викликом функції зобов'язаний забезпечити виконання наступних умов:
1. **Валідність вказівників та пам'яті:**
   - Для C API: покажчик `arr` (або `base`) повинен посилатися на дійсний, виділений блок пам'яті розміром щонайменше `n * sizeof(T)` (або `num * size`) байтів. Якщо `n == 0`, покажчик може бути довільним, але функція повинна негайно повернути керування без розіменування.
   - Для C++ API: об'єкт `std::span<T>` або діапазон `[first, last)` повинні утворювати валідний безперервний інтервал ітераторів.
2. **Властивості компаратора (Strict Weak Ordering):**
   Функція-компаратор `cmp(a, b)` або предикат `comp(a, b)` повинні задавати математичне відношення строгого слабкого порядку:
   - **Іррефлексивність:** `comp(a, a) == false` для будь-якого `a`.
   - **Асиметрія:** якщо `comp(a, b) == true`, то `comp(b, a) == false`.
   - **Транзитивність:** якщо `comp(a, b) == true` та `comp(b, c) == true`, то `comp(a, c) == true`.
   - **Транзитивність еквівалентності:** якщо два елементи незрівнянні (`!comp(a, b) && !comp(b, a)`), а також `!comp(b, c) && !comp(c, b)`, то вони незрівнянні між собою: `!comp(a, c) && !comp(c, a)`.
   *Порушення будь-якої з цих аксіом (наприклад, використання нестрогої нерівності `<=` у предикаті C++) призводить до невизначеної поведінки або руйнування стійкості сортування.*
3. **Вимоги до типів (C++):**
   Тип елементів `T` повинен задовольняти концепт `std::movable` (або `std::copyable`), тобто операція `std::swap(a, b)` повинна бути коректно визначеною і не призводити до витоку ресурсів.

### 3.2. Постумови (Postconditions)

Після успішного завершення роботи функції гарантується виконання наступних умов:
1. **Глобальна впорядкованість:**
   Для будь-яких двох індексів `i` та `j`, де `0 ≤ i < j < n`, виконується умова:
   ```
   !comp(arr[j], arr[i])
   ```
   Тобто елемент із меншим індексом не може бути строго більшим за елемент із більшим індексом за заданим компаратором.
2. **Збереження мультимножини елементів (Permutation Invariance):**
   Результуючий стан масиву є точною перестановкою початкового масиву. Жоден елемент не видаляється, не дублюється і не модифікується поза операціями обміну.
3. **Гарантія стійкості (Stability Preservation):**
   Якщо два елементи `X` та `Y` мають однакові ключі (`!comp(X, Y) && !comp(Y, X)`) і початково `X` передував `Y` у вхідному масиві (`pos_in(X) < pos_in(Y)`), то у відсортованому масиві їхній відносний порядок зберігається:
   ```
   pos_out(X) < pos_out(Y)
   ```

### 3.3. Гарантії безпеки винятків (Exception Safety)

- **C++ No-Throw Guarantee:** Якщо операція порівняння `comp(a, b)` та операція обміну `std::swap(a, b)` позначені як `noexcept`, уся функція сортування гарантовано є `noexcept`.
- **Basic Exception Guarantee:** Якщо операція порівняння або переміщення генерує виняток під час виконання внутрішнього циклу, масив залишається у валідному стані (жоден об'єкт не втрачається, ресурси не витікають), проте елементи можуть бути частково переставленими.

## 4. Специфіка використання у вбудованих системах та Hard Real-Time

Хоча для високонавантажених серверних систем сортування бульбашкою вважається застарілим через квадратичну складність `O(N²)`, у специфічних низькорівневих доменах воно володіє критично важливими інженерними перевагами.

### 4.1. Детермінізм та аналіз найгіршого часу виконання (WCET)

В операційних системах жорсткого реального часу (RTOS: FreeRTOS, Zephyr, VxWorks, PikeOS) центральною вимогою до коду авіоніки (DO-178C) та автомобільних систем (ISO 26262 ASIL-D) є можливість точного розрахунку верхньої межі часу виконання (**Worst-Case Execution Time, WCET**).

- **Наївний варіант (Bubble Naive):**
  Виконує строго фіксовану кількість ітерацій `N(N - 1) / 2` незалежно від значень вхідного масиву. Якщо внутрішній обмін реалізовано без умовних переходів (через умовні команди асемблера `cmov` або бітові маски), час виконання є абсолютно детермінованим. Це виключає часовий джитер (jitter) у циклічних задачах керування двигунами чи сенсорами.
- **Адаптивні варіанти (з прапорцем або last_swap):**
  Створюють значну часову невизначеність: час виконання коливається в діапазоні від `O(N)` до `O(N²)`. У системах із жорсткими дедлайнами планувальник задач повинен розраховувати час за найгіршим випадком `O(N²)`, через що переваги адаптивності нівелюються.

### 4.2. Обмеження стека в мікроконтролерах

У багатьох 8-бітних та 32-бітних мікроконтролерах (AVR ATmega, STM32 Cortex-M0+, PIC16/18) обсяг оперативної пам'яті (SRAM) вимірюється сотнями байтів або одиницями кілобайтів.

- Рекурсивні алгоритми швидкого сортування (Quicksort) створюють стек викликів глибиною `O(log N)` у середньому та `O(N)` у найгіршому випадку. На масиві з кількох сотень елементів це може спричинити переповнення стека (stack overflow), що перезавантажить мікроконтролер або непомітно зіпсує статичні змінні програми.
- Сортування бульбашкою є суто ітеративним алгоритмом. Воно зберігає стан у 2–3 регістрах процесора, має стековий кадр розміром менше 32 байтів і **гарантує повну безпеку щодо переповнення пам'яті**.

### 4.3. Багатопотоковість та потокобезпека (Thread Safety)

- **Паралельне читання:** Функції сортування модифікують пам'ять in-place. Одночасне читання масиву іншими потоками під час сортування без зовнішніх примітивів синхронізації (м'ютексів або `std::shared_mutex`) є станом гонитви (data race) та призводить до невизначеної поведінки.
- **Реентрабельність (Reentrancy):** Усі наведені функції є реентрабельними: вони не використовують глобальних або статичних змінних. Декілька незалежних потоків можуть одночасно сортувати власні неперетинні буфери даних без взаємних блокувань.

### 4.4. Безпека в обробниках переривань (ISR Safety)

Виклик алгоритмів сортування з часовою складністю `O(N²)` безпосередньо всередині функцій обробки переривань (Interrupt Service Routine, ISR) є грубим порушенням архітектури реального часу. Тривале блокування ядра в циклі сортування спричиняє затримку обробки інших апаратних переривань (Interrupt Latency Jitter) та втрату пакетів даних на послідовних інтерфейсах (UART, SPI, CAN). Рекомендований патерн — швидке копіювання сирих даних у чергу задач (`xQueueSendFromISR` у FreeRTOS або k_msgq_put у Zephyr) та виконання сортування у фоновому потоці з низьким пріоритетом.
