# 📋 Інтерфейси динамічного паралелізму: OpenMP Tasking, Cilk та Intel TBB

Для перетворення абстрактного обчислювального графа `G = (V, E)` у машинні інструкції сучасні компілятори та системні бібліотеки надають декларативні конструкції створення задач (породження вершин графа) та синхронізації (породження ребер залежності). Програміст описує логічну структуру графа без прямого зв'язування з потоками операційної системи, а середовище виконання автоматично транслює дерево задач на доступні ядра за моделлю крадіжки роботи.

---

## 1. Специфікація OpenMP Tasking (OpenMP 3.0+)

Стандарт OpenMP реалізує модель динамічного багатопотокового виконання через директиви створення та синхронізації задач. На відміну від класичних паралельних циклів (`#pragma omp parallel for`), задачі дозволяють будувати довільні ациклічні графи з нерегулярною деревоподібною структурою та асинхронним виконанням.

### Базове породження та очікування задач

:::tabs
```c
#include <stdio.h>
#include <omp.h>

void process_subtask(int id);

void parallel_tree_execution(void) {
    #pragma omp parallel
    {
        #pragma omp single
        {
            // Створення лівої вершини DAG
            #pragma omp task
            {
                process_subtask(1);
            }

            // Створення правої вершини DAG
            #pragma omp task
            {
                process_subtask(2);
            }

            // Точка синхронізації (join-ребро) для прямих дочірніх задач
            #pragma omp taskwait
        }
    }
}
```
```cpp
#include <iostream>
#include <omp.h>

void process_subtask(int id);

void parallel_tree_execution() {
    #pragma omp parallel
    {
        #pragma omp single
        {
            #pragma omp task
            {
                process_subtask(1);
            }

            #pragma omp task
            {
                process_subtask(2);
            }

            #pragma omp taskwait
        }
    }
}
```

### Таблиця директив OpenMP Tasking

| Конструкція | Семантика в обчислювальному графі DAG | Область дії |
|---|---|---|
| `#pragma omp task` | Створює нову асинхронну вершину графа (spawn-ребро). Поточний потік продовжує виконання наступної інструкції без блокування. | Блок коду або виклик функції |
| `#pragma omp taskwait` | Синхронізаційне join-ребро: блокує поточну задачу до повного завершення **всіх її прямих дочірніх задач**. Не очікує завершення задач наступних рівнів вкладеності. | Точка виклику у фреймі |
| `#pragma omp taskgroup` | Глибокий бар'єр синхронізації: блокує вихід із блоку до завершення **всіх нащадків будь-якого рівня вкладеності**, створених усередині структурованого регіону. | Огороджений блок коду |
| `#pragma omp taskloop` | Автоматично розбиває ітерації циклу на підзадачі за схемою збалансованого дерева з логарифмічною глибиною `T_∞ = O(log N)`. | Цикл `for` |
| `depend(in: ...)` / `depend(out: ...)` | Оголошує явні ребра залежності між задачами за адресами змінних у пам'яті без глобальних бар'єрів. | Клауза директиви `#pragma omp task` |

### Керування поведінкою та зв'язуванням задач

Директива `#pragma omp task` підтримує набір спеціалізованих клауз для тонкого налаштування поведінки планувальника:

1. **Клауза `untied`:**
   - За замовчуванням задачі в OpenMP є прив'язаними (англ. *tied*): якщо задача була призупинена в точці планування (наприклад, всередині `taskwait`), після відновлення її зобов'язаний продовжувати той самий фізичний потік.
   - Клауза `untied` дозволяє будь-якому вільному потоку пулу підхопити призупинену задачу. Це суттєво зменшує простої в глибоких рекурсивних деревах, але забороняє використання локальних змінних потоку (`threadprivate`).

2. **Клауза `final(condition)` та `mergeable`:**
   - Якщо умова `final` стає істинною (наприклад, розмір масиву впав нижче порогу відсікання), усі підзадачі, породжені всередині цієї задачі, створюються як фінальні (послідовні).
   - Клауза `mergeable` дозволяє компілятору не виділяти окремий контекст задачі, а виконати тіло безпосередньо у фреймі викликача, знижуючи накладні витрати до нуля.

3. **Клауза `priority(value)`:**
   - Задає цілочисельний пріоритет виконання задачі. Планувальник віддає перевагу задачам із вищим пріоритетом, що дозволяє програмісту вручну направляти ресурси на критичний шлях графа (`T_∞`).

### Побудова довільних DAG за допомогою клаузи `depend`

Клауза `depend` реалізує концепцію задач за потоком даних (англ. *dataflow tasks*), де ребра залежності формуються не через явні бар'єри синхронізації, а автоматично на основі адрес змінних:

:::tabs
```c
#include <stdio.h>
#include <omp.h>

int compute_step_a(void);
int compute_step_b(void);
int combine_results(int a, int b);

int execute_dag_pipeline(void) {
    int res_a = 0, res_b = 0, res_c = 0;

    #pragma omp parallel
    {
        #pragma omp single
        {
            // Вершина 1: генерує значення res_a
            #pragma omp task depend(out: res_a)
            {
                res_a = compute_step_a();
            }

            // Вершина 2: генерує значення res_b (виконується паралельно з вершиною 1)
            #pragma omp task depend(out: res_b)
            {
                res_b = compute_step_b();
            }

            // Вершина 3: залежить від завершення задач 1 і 2
            #pragma omp task depend(in: res_a, res_b) depend(out: res_c)
            {
                res_c = combine_results(res_a, res_b);
            }

            #pragma omp taskwait
        }
    }
    return res_c;
}
```
```cpp
#include <iostream>
#include <omp.h>

int compute_step_a();
int compute_step_b();
int combine_results(int a, int b);

int execute_dag_pipeline() {
    int res_a = 0;
    int res_b = 0;
    int res_c = 0;

    #pragma omp parallel
    {
        #pragma omp single
        {
            #pragma omp task depend(out: res_a)
            {
                res_a = compute_step_a();
            }

            #pragma omp task depend(out: res_b)
            {
                res_b = compute_step_b();
            }

            #pragma omp task depend(in: res_a, res_b) depend(out: res_c)
            {
                res_c = combine_results(res_a, res_b);
            }

            #pragma omp taskwait
        }
    }
    return res_c;
}
```

## 2. Мова Cilk та розширення Cilk Plus

Cilk інтегрує паралелізм безпосередньо в синтаксис мови через три ключові слова, що забезпечують мінімальні накладні витрати на рівні інструкцій компілятора.

### Ключові слова Cilk

| Ключове слово | Синтаксис | Семантика виконання |
|---|---|---|
| `cilk_spawn` | `cilk_spawn func(args);` | Породжує асинхронну гілку обчислень (spawn-ребро в DAG). Викликана функція виконується паралельно з наступним кодом поточного фрейму. |
| `cilk_sync` | `cilk_sync;` | Локальний бар'єр: виконання поточної функції призупиняється, доки всі підзадачі, породжені викликами `cilk_spawn` у **цьому ж фреймі**, не завершаться. |
| `cilk_for` | `cilk_for (int i = 0; i < N; ++i) { ... }` | Паралельний цикл, що компілюється в логарифмічне дерево бінарного розбиття діапазону зі спаном `T_∞ = O(log N)`. |

### Механізм трансляції компілятором (Compiler Lowering)

Компілятор транформує виклик `cilk_spawn` у послідовність низькорівневих дій:
1. **Збереження стану фрейму:** компілятор виділяє структуру стану (фрейм задачі) та зберігає поточні регістри через оптимізований аналог `setjmp`.
2. **Локальне виконання або передача:** потік-батько продовжує виконання наступного коду, а породжена функція залишається доступною для крадіжки іншими ядрами у дні локального дека.
3. **Обробка синхронізації:** на інструкції `cilk_sync` потік перевіряє лічильник активних дочірніх фреймів; якщо він ненульовий, потік переходить у режим очікування або починає крадіжку задач у сусідніх потоків.

### Правило серіалізації (Serial Elision)

Фундаментальний інваріант мови Cilk: якщо з програми видалити всі ключові слова `cilk_spawn`, `cilk_sync` і замінити `cilk_for` на звичайний `for`, отримана послідовна програма є синтаксично й семантично коректною. Це дозволяє здійснювати повне налагодження логіки стандартними послідовними налагоджувачами (GDB, Valgrind) без ризику недетермінованих міжпотокових блокувань.

## 3. Бібліотека Intel oneAPI Threading Building Blocks (oneTBB)

Бібліотека oneTBB надає об'єктно-орієнтований C++ інтерфейс для побудови динамічних графів задач, спираючись на RAII, концепції та лямбда-вирази.

### Клас `tbb::task_group`

```cpp
#include <iostream>
#include <tbb/task_group.h>

void parallel_recursive_fibonacci(int n, int &result) {
    if (n < 2) {
        result = n;
        return;
    }

    int left_res = 0;
    int right_res = 0;
    tbb::task_group tg;

    // Створення лівої підзадачі (spawn)
    tg.run([n, &left_res] {
        parallel_recursive_fibonacci(n - 1, left_res);
    });

    // Створення правої підзадачі (spawn)
    tg.run([n, &right_res] {
        parallel_recursive_fibonacci(n - 2, right_res);
    });

    // Синхронізація обох підзадач (sync)
    tg.wait();

    result = left_res + right_res;
}
```

### Модуль `tbb::flow::graph` для потокових DAG

Для задач із довільною топологією та конвеєрною обробкою даних oneTBB надає спеціалізований модуль потокових графів:

```cpp
#include <tbb/flow_graph.h>
#include <iostream>

void build_dataflow_dag() {
    tbb::flow::graph g;

    // Вузол джерела даних
    tbb::flow::broadcast_node<int> start_node(g);

    // Паралельні вузли обробки
    tbb::flow::function_node<int, int> node_a(g, tbb::flow::unlimited, [](int v) {
        return v * 2;
    });

    tbb::flow::function_node<int, int> node_b(g, tbb::flow::unlimited, [](int v) {
        return v + 10;
    });

    // Вузол об'єднання результатів
    tbb::flow::join_node<std::tuple<int, int>, tbb::flow::queueing> join(g);

    tbb::flow::function_node<std::tuple<int, int>, int> final_node(g, tbb::flow::serial, [](const std::tuple<int, int> &t) {
        return std::get<0>(t) + std::get<1>(t);
    });

    // Побудова ребер графа
    tbb::flow::make_edge(start_node, node_a);
    tbb::flow::make_edge(start_node, node_b);
    tbb::flow::make_edge(node_a, tbb::flow::input_port<0>(join));
    tbb::flow::make_edge(node_b, tbb::flow::input_port<1>(join));
    tbb::flow::make_edge(join, final_node);

    start_node.try_put(5);
    g.wait_for_all();
}
```

## Змінні середовища та афінність потоків

Для забезпечення стабільної продуктивності середовища виконання надають параметри конфігурації через змінні оточення:

1. **`OMP_NUM_THREADS=N`:** задає кількість робочих потоків у пулі. Для чисто обчислювальних задач встановлюється рівним кількості фізичних ядер процесора (без урахування віртуальних ядер SMT / Hyper-Threading, які можуть спричиняти конкуренцію за кеш L1).
2. **`OMP_PROC_BIND=close | spread | master`:** контролює розміщення потоків по ядрах та сокетах NUMA. Значення `close` розміщує сусідні потоки на суміжних ядрах, максимізуючи спільне використання кешу L3; значення `spread` рівномірно розподіляє потоки по всіх фізичних сокетах для досягнення максимальної сумарної пропускної здатності шини пам'яті.
3. **`OMP_PLACES=cores | sockets | threads`:** визначає апаратні одиниці для прив'язки потоків, запобігаючи спонтанній міграції задач між ядрами планувальником ОС.
4. **`OMP_WAIT_POLICY=ACTIVE | PASSIVE`:** визначає поведінку потоків під час очікування задач. Значення `ACTIVE` змушує потоки крутитися в активному спінлоці (Spinlock), мінімізуючи затримку пробудження ціною 100% навантаження CPU; значення `PASSIVE` переводить потоки в режим сну через системні виклики ядра (Futex).

## Порівняльна таблиця інтерфейсів динамічного паралелізму

| Характеристика | OpenMP 3.0+ Tasking | Cilk / Cilk Plus | Intel oneTBB (`task_group`) |
|---|---|---|---|
| **Мовна підтримка** | Директиви препроцесора C/C++/Fortran | Розширення компілятора | Чистий стандартний C++20 |
| **Синхронізація** | `#pragma omp taskwait` / `taskgroup` | `cilk_sync` | `tg.wait()` / деструктор `task_group` |
| **Довільні залежності DAG** | Так (через клаузу `depend`) | Ні (лише вкладений Fork-Join) | Так (через модуль `tbb::flow::graph`) |
| **Управління стеком** | Власний пул потоків ОС | Робочий стек із перехопленням кадрів | Локальні арени задач (`task_arena`) |
| **Поріг гранулярності** | Клауза `if(len > threshold)` | Ручний `if` перед `cilk_spawn` | `tbb::parallel_for(blocked_range, ...)` |

## Інженерні застереження та типові помилки

1. **Захоплення локальних змінних за посиланням у короткоживучих фреймах:**
   - Передача посилання на змінну зі стека функції, яка завершується раніше за породжену задачу, створює висяче посилання (англ. *dangling reference*). У C++ необхідно використовувати явне захоплення по копії `[=]` або `std::shared_ptr`, а в OpenMP — клаузу `firstprivate`.

2. **Забутий бар'єр синхронізації (`taskwait` / `wait`):**
   - Читання результатів підзадачі без попереднього очікування призводить до недетермінованого стану пам'яті (Data Race) та пошкодження результатів обчислень.

3. **Надмірна дрібнозернистість задач:**
   - Породження задач із тривалістю менше 1–2 мікросекунд створює накладні витрати на виділення дескрипторів та роботу планувальника, які багаторазово перевищують корисний час виконання інструкцій. Для компенсації слід використовувати адаптивний поріг відсікання рекурсії (Cutoff).
