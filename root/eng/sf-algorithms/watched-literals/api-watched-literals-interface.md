# 📋 Інтерфейс та структура даних 2WL у SAT-солвері

Цей довідник містить вичерпну специфікацію типів даних, сигнатур функцій, контрактів викликів та схем розташування у пам'яті для двигуна двох спостережуваних літералів (2WL).

## Архітектурний огляд та контракти типів

Двигун 2WL призначений для забезпечення надвисокої швидкості поширення булевих обмежень (Boolean Constraint Propagation, BCP) під час розв'язання КНФ-формул. Для досягнення максимальної швидкодії на сучасних процесорних архітектурах x86_64 та ARM64 інтерфейс спирається на трьохрівневу систему кодування:

1. **Компактність:** Усі об'єкти (літерали, ідентифікатори диз'юнктів, структури спостереження) мають фіксований розмір 32 або 64 біти для забезпечення мінімального кеш-футпринту та усунення нелокальних фрагментацій.
2. **Нульові нелокальні розіменування:** Списки спостереження зберігають дубльовану інформацію (блокуючий літерал), що дозволяє приймати рішення про істинність диз'юнкта без доступу до його головного масиву літералів у купі.
3. **Строгі контракти функцій:** Будь-яка операція передачі даних має чітко визначені предумови (preconditions) та постумови (postconditions), що унеможливлює стан невизначеної поведінки (undefined behavior) та виключення під час BCP.

### 1. Перелік статусів поширення (`PropStatus`)

Ступінь виконання поширення обмежень повертається за допомогою уніфікованого переліку статусів.

:::tabs
```c
/* c */
typedef enum {
    PROP_OK       = 0,  // BCP завершено успішно, конфліктів та нових одиничних поширень немає
    PROP_UNIT     = 1,  // Знайдено та успішно додано новий одиничний літерал до стеку trail
    PROP_CONFLICT = -1  // Виявлено суперечність (порожній диз'юнкт). BCP перервано
} PropStatus;
```
```cpp
// cpp
enum class PropStatus : int8_t {
    Ok       = 0,  // BCP завершено успішно, конфліктів немає
    Unit     = 1,  // Додано новий одиничний літерал
    Conflict = -1  // Виявлено суперечність у формулі
};
```
:::

- **Контракт використання та винятки:**
  - Якщо процедура `solver_propagate` повертає `PROP_OK`, стек `trail` містить усі логічно випливаючі літерали під поточним частковим присвоєнням, а база списків спостереження залишається в строго інваріантному стані.
  - Якщо повернуто `PROP_CONFLICT`, стек `trail` зберігає точний стан присвоєнь на момент виникнення конфлікту, а вихідне поле `conflict_clause_id` містить унікальний ідентифікатор диз'юнкта, усі літерали якого оцінені як False.

### 2. Упаковане представлення літерала (`Literal`)

Усі літерали у 2WL кодуються у вигляді 32-бітного беззнакового цілого числа `uint32_t`. Таке упакування забезпечує збереження змінної та полярності в одному інструкційному слові CPU.

**Схема кодування:**
```
 31                                         1       0
+-----------------------------------------+---+-----------+
|          Індекс змінної (var_id)        |   | Sign (0/1)|
+-----------------------------------------+---+-----------+
```
- `var_id`: Індекс змінної (1-based), від `1` до `N` (займає верхні 31 біт).
- `sign`: Біт полярності (займає 0-й біт): `0` для позитивного літерала `x`, `1` для заперечення `¬x`.

:::tabs
```c
/* c */
#include <stdint.h>
#include <stdbool.h>

typedef uint32_t Literal;
typedef uint32_t Var;

#define LIT_VAR(lit)      ((lit) >> 1)
#define LIT_SIGN(lit)     ((lit) & 1)
#define LIT_MAKE(v, s)    (((uint32_t)(v) << 1) | ((s) ? 1 : 0))
#define LIT_NEG(lit)      ((lit) ^ 1)
```
```cpp
// cpp
#include <cstdint>

class Literal {
    uint32_t code_{0};
public:
    constexpr Literal() noexcept = default;
    constexpr Literal(uint32_t var, bool is_neg) noexcept 
        : code_((var << 1) | (is_neg ? 1u : 0u)) {}
    
    [[nodiscard]] constexpr uint32_t var() const noexcept { return code_ >> 1; }
    [[nodiscard]] constexpr bool is_neg() const noexcept { return (code_ & 1u) != 0; }
    [[nodiscard]] constexpr Literal neg() const noexcept { return Literal(code_ ^ 1u); }
    [[nodiscard]] constexpr uint32_t code() const noexcept { return code_; }
    
    constexpr bool operator==(const Literal& o) const noexcept { return code_ == o.code_; }
    constexpr bool operator!=(const Literal& o) const noexcept { return code_ != o.code_; }
private:
    constexpr explicit Literal(uint32_t raw_code) noexcept : code_(raw_code) {}
};
```
:::

- **Математичний інваріант:** Для будь-якого літерала `l` виконується `neg(neg(l)) == l`.
- **Індексація масивів:** Літерал `l` безпосередньо слугує індексом у масиві списків спостереження `watches[l.code()]`. Загальна кількість елементів масиву `watches` дорівнює `2 * (N + 1)`.

### 3. Структура покажчика спостереження (`Watcher`)

Запис у списку спостереження представляє зв'язок між спостережуваним літералом та диз'юнктом.

:::tabs
```c
/* c */
typedef struct {
    uint32_t clause_id;  // 32-бітний індекс або зміщення диз'юнкта у масиві
    Literal  blocker;    // 32-бітний блокуючий літерал (копія w[2])
} Watcher;
```
```cpp
// cpp
struct Watcher {
    uint32_t clause_id;  // Ідентифікатор диз'юнкта
    Literal  blocker;    // Блокуючий літерал для швидкої перевірки кешу
};
```
:::

- **Вирівнювання та розмір:** Розмір `Watcher` складає строго 8 байтів (64 біти). Усі записи розташовуються у неперервному масиві. Одна кеш-лінія процесора розміром 64 байти вміщує строго 8 записів `Watcher`.
- **Семантика поля `blocker`:** Поле `blocker` зберігає копію другого спостережуваного літерала диз'юнкта `w[2]`. Якщо під час ітерації по списку `watches[¬p]` виявляється, що `value(blocker) == True`, диз'юнкт гарантовано задоволений. У цьому випадку алгоритм пропускає диз'юнкт без розіменування вказівника `clause_id`, що запобігає промаху кешу L1.

### 4. Внутрішня структура диз'юнкта (`ClauseHeader`)

У пам'яті кожен диз'юнкт представляється у вигляді заголовка із гнучким масивом літералів (Flexible Array Member у C або `std::vector` / `std::span` у C++).

:::tabs
```c
/* c */
typedef struct {
    uint32_t size;       // Кількість літералів у диз'юнкті (k >= 2)
    uint32_t flags;      // Бітові прапорці (IsLearned, LBD_score)
    Literal  lits[];     // Гнучкий масив літералів [w1, w2, l3, ..., lk]
} ClauseHeader;
```
```cpp
// cpp
#include <vector>
#include <span>

class Clause {
    uint32_t flags_{0};
    std::vector<Literal> lits_;
public:
    explicit Clause(std::span<const Literal> lits, bool is_learned = false)
        : flags_(is_learned ? 1u : 0u), lits_(lits.begin(), lits.end()) {}
    
    [[nodiscard]] size_t size() const noexcept { return lits_.size(); }
    [[nodiscard]] bool is_learned() const noexcept { return (flags_ & 1u) != 0; }
    [[nodiscard]] Literal& operator[](size_t idx) noexcept { return lits_[idx]; }
    [[nodiscard]] const Literal& operator[](size_t idx) const noexcept { return lits_[idx]; }
};
```
:::

- **Фізичний інваріант покажчиків:** Перші два елементи масиву `lits[0]` та `lits[1]` завжди є спостережуваними літералами `w[1]` та `w[2]`.
- При успішному пошуку нового не-хибного літерала на індексі `i` виконується `swap(lits[0], lits[i])`, що відновлює інваріант фізичного розташування.

## Сигнатури та специфікації функцій

Нижче наведено повний контракт функцій інтерфейсу двигуна 2WL.

### `solver_create` / Конструктор `WatchedLiteralsEngine`

Створення екземпляра солвера та ініціалізація структур даних для заданої кількості змінних.

:::tabs
```c
/* c */
Solver* solver_create(uint32_t num_vars);
```
```cpp
// cpp
explicit WatchedLiteralsEngine(uint32_t num_vars);
```
:::

- **Предумови:** `num_vars > 0`.
- **Постумови:**
  - Виділено пам'ять під масив значений змінних `values` розміром `num_vars + 1`, ініціалізований у `VAL_UNASSIGNED`.
  - Створено масив списків спостереження `watches` розміром `2 * (num_vars + 1)`.
  - Стек `trail` порожній, поточний рівень рішення `current_level = 0`.
- **Складність:** `O(num_vars)` за часом та пам'яттю.

### `solver_add_clause` / `add_clause`

Додавання нового диз'юнкта до бази даних формули з автоматичною реєстрацією у 2WL.

:::tabs
```c
/* c */
bool solver_add_clause(Solver* s, const Literal* lits, uint32_t size);
```
```cpp
// cpp
bool add_clause(std::span<const Literal> lits);
```
:::

- **Параметри:**
  - `s` / `this`: вказівник на двигун.
  - `lits`: масив літералів нового диз'юнкта.
  - `size`: кількість літералів (`k`).
- **Поведінка та крайові випадки:**
  - **`k == 0` (Порожній диз'юнкт):** Повертає `false`. Формула є нездійсненною.
  - **`k == 1` (Унарний диз'юнкт):** Не реєструється у 2WL. Літерал `lits[0]` негайно вміщується до `trail` на рівні 0. Якщо `value(lits[0]) == False`, повертає `false` (конфлікт).
  - **`k >= 2` (Загальний диз'юнкт):** Диз'юнкт додається до бази. Реєструються записи `Watcher` у списках `watches[lits[0]]` та `watches[lits[1]]`.
- **Повертає:** `true` при успішному додаванні, `false` при виявленні негайного конфлікту.

### `solver_propagate` / `propagate`

Основний цикл поширення обмежень BCP на базі списків спостереження 2WL.

:::tabs
```c
/* c */
PropStatus solver_propagate(Solver* s, uint32_t* conflict_clause_id);
```
```cpp
// cpp
std::expected<void, uint32_t> propagate();
```
:::

- **Алгоритм виконання:**
  1. Поки стек `trail` містить необроблені літерали (`trail_head < trail_size`):
     a. Витягти літерал `p = trail[trail_head++]`.
     b. Отримати список `wl = &watches[¬p]`.
     c. Проітеруватися по всіх запишах `w` у `wl`.
     d. Якщо `value(w.blocker) == True`, залишити запис і перейти до наступного.
     e. Відкрити диз'юнкт `C = clauses[w.clause_id]`. Якщо `c.lits[1] == ¬p`, виконати `swap(c.lits[0], c.lits[1])`.
     f. Якщо `value(c.lits[1]) == True`, оновити `w.blocker = c.lits[1]` і продовжити.
     g. Сканувати `c.lits[k]` від `k=2` до `size-1`. Якщо знайдено `c.lits[k] ∉ {False}`, виконати `swap(c.lits[0], c.lits[k])`, додати `Watcher` до `watches[c.lits[0]]` та вилучити з `wl`.
     h. Якщо заміну не знайдено: якщо `value(c.lits[1]) == Unassigned`, виконати `enqueue(c.lits[1])`. Якщо `value(c.lits[1]) == False`, повернути конфлікт.
- **Повертає:** `PROP_OK` (або порожній `std::expected`) при успішному поширенні; `PROP_CONFLICT` (або `std::unexpected(clause_id)`) при виявленні суперечності.

### `solver_backtrack` / `backtrack`

Скасування присвоєнь змінних вище заданого рівня рішення.

:::tabs
```c
/* c */
void solver_backtrack(Solver* s, uint32_t target_level);
```
```cpp
// cpp
void backtrack(uint32_t target_level);
```
:::

- **Контракт виконання:**
  - Скасовує значення всіх змінних у `trail`, які були присвоєні на рівнях рішення `level > target_level`.
  - Усі скасовані змінні повертаються у стан `VAL_UNASSIGNED`.
  - **Гарантія 2WL:** Функція **не виконує жодного запису** у масиви диз'юнктів `clauses` та списки спостереження `watches`.
- **Складність:** `O(N_unassigned)` за часом, `O(1)` додаткової пам'яті.

## Схема розташування у пам'яті та кеш-локальність

Для забезпечення високої продуктивності двигун 2WL організовує пам'ять у вигляді суцільних блоків (flat arrays):

```
Масив списків спостереження (watches array):
=============================================================================
Literal Code | Watcher Array (Contiguous Memory Vector)
-----------------------------------------------------------------------------
0x0002 (x1)  | [ {CID: 0, Blocker: ¬x2}, {CID: 4, Blocker: x3} ]
0x0003 (¬x1) | [ {CID: 1, Blocker: x4} ]
0x0004 (x2)  | [ {CID: 0, Blocker: x1},  {CID: 8, Blocker: ¬x3} ]
=============================================================================

Плоска база диз'юнктів (Flat Clause Database):
=============================================================================
Offset   | Header (Size, Flags) | Literals Array [w1, w2, l3, l4, ...]
-----------------------------------------------------------------------------
0x0000   | Size: 3, Flags: 0x0  | [ x1,  ¬x2,  x3 ]         <-- Clause 0
0x0014   | Size: 2, Flags: 0x1  | [ ¬x1,  x4 ]              <-- Clause 1
0x0024   | Size: 4, Flags: 0x0  | [ ¬x3,  x4,  x1, ¬x2 ]    <-- Clause 2
=============================================================================
```

### Переваги плоского розташування:
1. **Зменшення промахів кешу L1/L2:** Послідовний обхід вектора `Watcher` дозволяє префетчеру CPU завантажувати наступні 8 записів спостереження до виконання інструкцій перевірки.
2. **Нуль фрагментації купи (Heap Fragmentation):** База диз'юнктів виділяється великими блоками (pages) по 4 МБ, що усуває накладні витрати стандартного `malloc`.

## Повна таблиця контрактів та крайових випадків

Розглянемо вичерпний аналіз крайових ситуацій під час роботи публічних функцій двигуна 2WL.

| Функція / Метод | Предумови | Постумови | Поведінка при `k=1` | Поведінка при конфлікті |
| :--- | :--- | :--- | :--- | :--- |
| `solver_create` | `num_vars > 0` | Створено порожні списки 2WL | Н/Д | Н/Д |
| `solver_add_clause` | Вказівник на масив літералів | Диз'юнкт додано до бази 2WL | Одразу додається до `trail` | Повертає `false` |
| `solver_propagate` | `trail` ініціалізовано | Усі вимушені поширення виконані | Обробляється з `trail` | Переривається, повертає conflict ID |
| `solver_backtrack` | `target_level <= current_level` | Змінні скасовано | `trail` скорочується | **0 операцій з 2WL** |

У разі спроби додавання порожнього диз'юнкта (`k = 0`) функція `solver_add_clause` повертає `false`, сповіщаючи розробника про теоретичну нездійсненність сформованої формули ще до початку пошуку. При виникненні суперечності під час обробки унарного диз'юнкта на базовому рівні рішення 0 (Level 0) двигун 2WL фіксує глобальну тривіальну нездійсненність КНФ-формули.
