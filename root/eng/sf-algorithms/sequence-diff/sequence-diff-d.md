- [Хеш-таблиця](root:sf-algorithms/hash-table) — структура даних для асоціативного збереження та швидкого пошуку елементів за ключем.

Розробник вносить зміну у вихідний файл розміром 10 000 рядків: додає на початку один новий рядок із директивою підключення бібліотеки. Якщо текстовий редактор або система контролю версій спробує порівняти стару і нову версії наївним попозиційним скануванням (індекс `i` старого файлу проти індексу `i` нового), кожен наступний рядок старого файлу виявиться зміщеним рівно на одну позицію відносно нового. Позиційне порівняння зафіксує 9 999 розбіжностей у файлі на 10 000 рядків — стовідсотковий фальшивий незбіг, хоча 99.99% коду нижче залишилися абсолютно незмінними.

Аналогічна проблема виникає в системах синхронізації баз даних, біоінформатиці під час аналізу геномних ланцюгів ДНК та рушіях оновлення інтерфейсів (Virtual DOM): наївне покрокове порівняння елементів руйнується при першій же локальній вставці чи видаленні. Щоб виявити справжню структуру змін, системі потрібен алгоритм, інваріантний до глобальних зсувів — механізм, здатний знайти максимальний незмінний кістяк даних та виокремити мінімальний набір вставок і видалень, що трансформують одну послідовність в іншу.

Такий кістяк називають **підпослідовністю** (лат. *sub-* — під + *sequentia* — слідування) — набором елементів, який зберігає їхній первинний відносний порядок, але не вимагає, щоб вони стояли впритул один до одного. Задача пошуку найдовшої спільної підпослідовності (Longest Common Subsequence, LCS) є фундаментальною математичною основою для сімейства алгоритмів **diff** (лат. *differentia* — різниця, розбіжність).

## Спільна підпослідовність (LCS) та сценарій редагування (SES)

Нехай задано дві послідовності елементів `A = (a₁, a₂, ..., a_N)` довжиною `N` та `B = (b₁, b₂, ..., b_M)` довжиною `M`. Елементами можуть бути символи тексту, рядки вихідного файлу, токени абстрактного синтаксичного дерева або байти двійкового потоку.

Якщо з послідовності `A` вилучити нуль або більше елементів без зміни порядку решти, отримуємо підпослідовність `A'`. Якщо певна послідовність `C` є одночасно підпослідовністю для `A` і для `B`, вона є їхньою **спільною підпослідовністю**. Послідовність найбільшої можливої довжини називається **найдовшою спільною підпослідовністю** (LCS).

Розглянемо дві послідовності символів:
```
A = [A, B, C, D, G, H]
B = [A, E, D, F, H, R]
```
Спільними підпослідовностями тут є `[A]`, `[A, D]`, `[A, H]`, `[D, H]`, а також `[A, D, H]`. Остання має довжину 3 і є найдовшою спільною підпослідовністю `LCS(A, B) = [A, D, H]`.

Паралельно існує поняття **найкоротшого сценарію редагування** (Shortest Edit Script, SES) — мінімального за кількістю кроків списку елементарних операцій **видалення** (Delete) та **вставки** (Insert), що трансформує послідовність `A` в `B`.

Між LCS та SES існує фундаментальна математична еквівалентність (дуальність):
- Усі елементи `A`, що увійшли до LCS, зберігаються без змін.
- Усі елементи `A`, що не увійшли до LCS, мають бути видалені (рівно `N - |LCS|` операцій).
- Усі елементи `B`, що не увійшли до LCS, мають бути вставлені (рівно `M - |LCS|` операцій).

Сумарна кількість операцій редагування `D` виражається формулою:

```
D
= (N - |LCS|) + (M - |LCS|)    [сума кількості видалень та вставок]
= N + M - 2·|LCS|              [згруповано доданки]
```

З цієї рівності випливає ключовий висновок: **максимізація довжини спільної підпослідовності строго еквівалентна мінімізації кількості операцій редагування**.

Історію розвитку алгоритмів порівняння — від перших утиліт Bell Labs у 1970-х роках до сучасних розподілених систем контролю версій — описано у вставці [Історія розвитку алгоритмів diff](root:sf-algorithms/sequence-diff/hist-diff-evolution.md).

## Класичне динамічне програмування: матричний алгоритм

Для знаходження довжини LCS послідовностей `A` та `B` використовується метод динамічного програмування. Задача володіє властивістю оптимальної підструктури: оптимальне вирівнювання префіксів `A[1 .. i]` та `B[1 .. j]` складається з оптимальних вирівнювань їхніх коротших префіксів.

Введемо двовимірний масив `L[0 .. N, 0 .. M]`, де комірка `L[i, j]` зберігає довжину LCS між префіксом `A[1 .. i]` довжиною `i` та префіксом `B[1 .. j]` довжиною `j`.

Базові випадки відповідають зіставленню з порожньою послідовністю довжини 0:
```
L[i, 0] = 0    для всіх 0 ≤ i ≤ N    [LCS з порожньою послідовністю має нульову довжину]
L[0, j] = 0    для всіх 0 ≤ j ≤ M
```

Для довільних індексів `1 ≤ i ≤ N` та `1 ≤ j ≤ M` рекурентне правило має вигляд:

```
якщо A[i] == B[j]:
    L[i, j] = L[i - 1, j - 1] + 1
інакше:
    L[i, j] = max(L[i - 1, j], L[i, j - 1])
```

Логіка рекурентного переходу:
1. Якщо поточні елементи `A[i]` та `B[j]` збігаються, цей елемент гарантовано подовжує спільну підпослідовність на 1, спираючись на оптимальний розв'язок для менших префіксів `L[i-1, j-1]`.
2. Якщо елементи різні, вони не можуть одночасно входити в кінець спільної підпослідовності на цій позиції. Тому ми обираємо найкращий результат серед двох взаємно вичерпних варіантів: відкинути елемент `A[i]` (значення `L[i-1, j]`) або відкинути елемент `B[j]` (значення `L[i, j-1]`).

### Покроковий приклад заповнення таблиці DP

Розглянемо покрокове заповнення матриці для рядків `A = "ABCABBA"` (`N = 7`) та `B = "CBABAC"` (`M = 6`):

```
       ε   C   B   A   B   A   C
  ε    0   0   0   0   0   0   0
  A    0   0   0   1   1   1   1
  B    0   0   1   1   2   2   2
  C    0   1   1   1   2   2   3
  A    0   1   1   2   2   3   3
  B    0   1   2   2   3   3   3
  B    0   1   2   2   3   3   3
  A    0   1   2   3   3   4   4
```

1. **Рядок 1 (`A[1] = 'A'`):** Збіг виникає на позиції `j = 3` (`B[3] = 'A'`), де `L[1, 3] = L[0, 2] + 1 = 1`. Значення 1 поширюється праворуч.
2. **Рядок 2 (`A[2] = 'B'`):** Збіг на `j = 2` дає `L[2, 2] = 1`, а другий збіг на `j = 4` (`B[4] = 'B'`) бере `L[1, 3] + 1 = 2`.
3. **Фінальна комірка `L[7, 6] = 4`:** Довжина найдовшої спільної підпослідовності дорівнює 4.

Для відновлення самої підпослідовності виконується зворотний прохід (Backtracking) від комірки `(7, 6)` до `(0, 0)`:
- Починаємо в `(7, 6)`: `A[7] = 'A'`, `B[6] = 'C'` (різні). `L[6, 6] = 3 < L[7, 5] = 4`, тому рухаємося ліворуч у `(7, 5)` (вставка `'C'`).
- У `(7, 5)`: `A[7] = 'A'`, `B[5] = 'A'` (збіг!). Додаємо `'A'` до LCS і переходимо по діагоналі в `(6, 4)`.
- У `(6, 4)`: `A[6] = 'B'`, `B[4] = 'B'` (збіг!). Додаємо `'B'` до LCS, переходимо в `(5, 3)`.
- У `(5, 3)`: рухаємося вгору в `(4, 3)` (видалення `'B'`), де `A[4] = 'A'`, `B[3] = 'A'` (збіг!). Додаємо `'A'` до LCS, переходимо в `(3, 2)`.
- У `(3, 2)`: рухаємося вгору в `(2, 2)` (видалення `'C'`), де `A[2] = 'B'`, `B[2] = 'B'` (збіг!). Додаємо `'B'` до LCS, переходимо в `(1, 1)`.
- У `(1, 1)`: рухаємося в `(1, 0)` (вставка `'C'`) і нарешті в `(0, 0)` (видалення `'A'`).

Отримана найдовша спільна підпослідовність: `LCS = "BABA"`, а сценарій редагування містить `7 + 6 - 2·4 = 5` правок.

Часова складність алгоритму становить `O(N · M)`, а просторова складність вимагає збереження `(N + 1) × (M + 1)` чисел. Для файлів у 100 000 рядків матриця потребує `10^10` комірок (40 ГБ RAM) — алгоритм стає непридатним без спеціальних просторових оптимізацій.

## Лінійний простір: алгоритм Гіршберґа

Якщо нам потрібна лише довжина LCS, пам'ять легко скоротити до `O(min(N, M))`, оскільки для заповнення поточного рядка матриці потрібен лише попередній рядок. Проте постає питання: як відновити повну послідовність вирівнювання, не зберігаючи всю матрицю в пам'яті?

У 1975 році Ден Гіршберґ запропонував алгоритм, який поєднує метод «розділяй і володарюй» із прямим та зворотним проходом динамічного програмування, забезпечуючи відновлення LCS за лінійну пам'ять `O(N + M)` без погіршення часової складності `O(N · M)`.

![Розбиття Гіршберґа](/root/eng/sf-algorithms/sequence-diff/img/hirschberg-split.svg)
*Алгоритм Гіршберґа: прямий і зворотний DP-вектори зустрічаються на середньому рядку i = N/2, знаходять точку розрізу j* та рекурсивно ділять простір пошуку.*

### Механізм роботи алгоритму Гіршберґа

1. **Фіксація середини першої послідовності:** Знаходимо середину послідовності `A`: `mid = ⌊N / 2⌋`.
2. **Прямий прохід DP (вектор `L_fwd`):** Запускаємо алгоритм DP з оптимізацією пам'яті (лише два рядки) від початку `(0, 0)` до рядка `mid`. Вектор `L_fwd[j]` зберігає довжину LCS для `A[1 .. mid]` та `B[1 .. j]`.
3. **Зворотний прохід DP (вектор `L_bwd`):** Запускаємо такий самий дворядковий DP у зворотному напрямку: від кінця `(N, M)` назад до рядка `mid + 1`. Вектор `L_bwd[j]` зберігає довжину LCS для перевернутих суфіксів `A[mid+1 .. N]` та `B[j+1 .. M]`.
4. **Пошук оптимальної точки розрізу `j*`:** Шукаємо індекс `j*` у послідовності `B`, який максимізує суму:
   ```
   j* = argmax_{0 ≤ j ≤ M} (L_fwd[j] + L_bwd[M - j])
   ```
   Точка `(mid, j*)` гарантовано лежить на оптимальному шляху вирівнювання.
5. **Рекурсивне розбиття:** Задача розпадається на дві незалежні підзадачі меншого розміру:
   - Знайти LCS між `A[1 .. mid]` та `B[1 .. j*]`.
   - Знайти LCS між `A[mid+1 .. N]` та `B[j*+1 .. M]`.
   Підсумковий результат є конкатенацією результатів обох підзадач.

### Чому час залишається O(N · M)

На першому кроці ми обчислюємо DP для прямокутника площею `N · M`. На наступному рівні рекурсії дві підзадачі мають сумарну площу:

```
mid · j* + (N - mid) · (M - j*)
≈ (N / 2) · j* + (N / 2) · (M - j*)    [підстановка mid = N / 2]
= (N / 2) · (j* + M - j*)              [винесення N / 2 за дужки]
= (N · M) / 2                          [сумарна площа зменшилася вдвічі]
```

Загальний обсяг обчислень за всіма рівнями рекурсії утворює спадну геометричну прогресію:

```
T_total
= N·M · (1 + 1/2 + 1/4 + 1/8 + ...)
= N·M · 2
= 2 · N · M                            [сума нескінченної спадної прогресії дорівнює 2]
= O(N · M)
```

Таким чином, алгоритм Гіршберґа зменшує споживання пам'яті до лінійного `O(N + M)`, подвоюючи кількість операцій порівняно зі звичайним DP, але зберігаючи асимптотичний час `O(N · M)`.

Строгі математичні доведення складності та коректності розбиття Гіршберґа наведено у вставці [Математичні основи: граф редагування та інваріанти Маєрса](root:sf-algorithms/sequence-diff/math-lcs-myers.md).

## Алгоритм Маєрса: граф редагування та діагональний пошук

Незважаючи на лінійну пам'ять Гіршберґа, час `O(N · M)` залишається занадто великим для практичних систем контролю версій. Якщо у файлі на 50 000 рядків змінено лише 2 рядки, алгоритм все одно виконує `50 000 × 50 000 = 2.5 × 10^9` операцій.

У 1986 році Юджин Маєрс запропонував алгоритм, часова складність якого залежить не від добутку довжин `N · M`, а від кількості відмінностей `D` між файлами: `O((N + M) · D)`. Коли файли схожі (`D << N + M`), алгоритм Маєрса працює практично за лінійний час `O(N + M)`.

![Граф редагування та алгоритм Маєрса](/root/eng/sf-algorithms/sequence-diff/img/edit-graph-myers.svg)
*Граф редагування Маєрса: рух праворуч — видалення з A, рух вниз — вставка з B, діагональний рух (змія) — нульова вартість збігу символів.*

### Концепція графа редагування (Edit Graph)

Граф редагування будується на двовимірній сітці координат `(x, y)`, де `0 ≤ x ≤ N`, `0 ≤ y ≤ M`:
- Початок координат `(0, 0)` відповідає стану до початку порівняння.
- Цільова точка `(N, M)` відповідає повному завершенню зіставлення.
- **Горизонтальне ребро** `(x, y) → (x + 1, y)` означає **видалення** елемента `A[x+1]` (вартість 1).
- **Вертикальне ребро** `(x, y) → (x, y + 1)` означає **вставку** елемента `B[y+1]` (вартість 1).
- **Діагональне ребро** `(x, y) → (x + 1, y + 1)` існує лише якщо `A[x+1] == B[y+1]` і означає **збіг** (вартість 0).

Пошук найкоротшого сценарію редагування зводиться до пошуку шляху від `(0, 0)` до `(N, M)` із мінімальною кількістю недіагональних (горизонтальних та вертикальних) кроків.

### Діагоналі та інваріант парності

Ключова ідея Маєрса полягає у введенні координати діагоналі `k`:

```
k = x - y
```

- Головна діагональ, що проходить через `(0, 0)`, має номер `k = 0`.
- Горизонтальний крок збільшує `x` на 1 (перехід з діагоналі `k - 1` на `k`).
- Вертикальний крок збільшує `y` на 1 (перехід з діагоналі `k + 1` на `k`).
- Діагональний крок збільшує і `x`, і `y` на 1, тому номер діагоналі `k = x - y` не змінюється.

**Інваріант парності:** Після виконання `D` недіагональних кроків кінцева точка може лежати лише на діагоналях `k`, що мають таку саму парність, як і `D`:

```
k ∈ {-D, -D + 2, -D + 4, ..., D - 2, D}
k ≡ D (mod 2)
```

### Жадібний пошук та «змії» (Snakes)

Алгоритм Маєрса ітерується за кількістю правок `D = 0, 1, 2, ...`. На кожному кроці `D` ми шукаємо найдальшу точку `(x, y)`, якої можна досягти на кожній діагоналі `k`:

1. Зберігаємо в одновимірному масиві `V[k]` максимальну координату `x`, досягнуту на діагоналі `k`.
2. Для поточної діагоналі `k` обираємо найкращий попередній крок між діагоналями `k - 1` (рух вправо) та `k + 1` (рух вниз):
   ```
   якщо k == -D або (k != D і V[k - 1] < V[k + 1]):
       x = V[k + 1]        // рух вниз від діагоналі k+1 (вставка)
   інакше:
       x = V[k - 1] + 1    // рух вправо від діагоналі k-1 (видалення)
   y = x - k
   ```
3. **Протягування змії (Snake):** Опинившись у точці `(x, y)`, ми безкоштовно рухаємося по діагоналі вперед стільки, скільки елементи послідовностей збігаються:
   ```
   поки x < N і y < M і A[x + 1] == B[y + 1]:
       x = x + 1
       y = y + 1
   ```
4. Оновлюємо `V[k] = x`. Якщо `x == N` та `y == M`, найкоротший шлях знайдено.

### Покрокове трасування масиву V[k]

Простежимо роботу алгоритму Маєрса для рядків `A = "ABCABBA"` та `B = "CBABAC"`:

- **`D = 0`:** Діагональ `k = 0`. Починаємо в `(0, 0)`. Символи `A[1] = 'A'` та `B[1] = 'C'` різні, змія нульова. `V[0] = 0`.
- **`D = 1`:** Діагоналі `k ∈ {-1, 1}`:
  - `k = -1`: крок вниз від `k = 0` у `(0, 1)`. `A[1]='A'`, `B[2]='B'` (різні). `V[-1] = 0`.
  - `k = 1`: крок вправо від `k = 0` у `(1, 0)`. `A[2]='B'`, `B[1]='C'` (різні). `V[1] = 1`.
- **`D = 2`:** Діагоналі `k ∈ {-2, 0, 2}`:
  - `k = -2`: крок вниз від `k = -1` у `(0, 2)`. Змія: `A[1]='A'==B[3]='A'` → `(1, 3)`, далі `A[2]='B'==B[4]='B'` → `(2, 4)`. `V[-2] = 2`.
  - `k = 0`: вибираємо між `k = -1` (`x = 0+1 = 1`) та `k = 1` (`x = 1`). `x = 1`, `y = 1`. Змія: `A[2]='B'==B[2]='B'` → `(2, 2)`. `V[0] = 2`.
  - `k = 2`: крок вправо від `k = 1` у `(2, 0)`. Змія: `A[3]='C'==B[1]='C'` → `(3, 1)`. `V[2] = 3`.
- **`D = 3, 4, 5`:** На кроці `D = 5` діагональ `k = 1` (оскільки `7 - 6 = 1`) досягає координати `x = 7`, `y = 6`. Алгоритм завершує роботу, виконавши лише 5 ітерацій зовнішнього циклу.

Завдяки протягуванню змій алгоритм миттєво долає велетенські ділянки незміненого тексту. Складність алгоритму становить `O((N + M) · D)` за часом та `O(D^2)` за пам'яттю для збереження історії переходів.

Повну програмну реалізацію алгоритму Маєрса мовами C та C++ з відновленням сценарію редагування та генерацією уніфікованого diff наведено у вставці [Практична реалізація алгоритму Маєрса](root:sf-algorithms/sequence-diff/proj-myers-diff.md).

## Евристика Гекеля: лінійний час та переміщення блоків

Класичні алгоритми LCS розглядають переміщення блоку коду (наприклад, перенесення функції з кінця файлу на початок) як дві окремі масивні операції: повне видалення функції на старому місці та повну вставку на новому. Це створює громіздкий diff, у якому важко розгледіти справжній зміст рефакторингу.

У 1978 році Пол Гекель розробив принципово інший підхід, заснований на ізоляції унікальних рядків. Алгоритм Гекеля спирається на емпіричний факт: у будь-якому вихідному коді або тексті більшість ключових рядків (сигнатури функцій, заголовки, характерні вирази) зустрічаються рівно один раз.

Термін **евристика** (грец. *heurisko* — знаходити, шукати) означає практичний метод, який гарантує швидке знаходження якісного розв'язку за рахунок використання специфічних властивостей предметної області.

### П'ять проходів алгоритму Гекеля

Алгоритм Гекеля виконує послідовно п'ять лінійних проходів над масивами рядків `A` та `B`:

1. **Прохід 1 (Хешування файлу A):** Скануємо файл `A`, будуємо хеш-таблицю символів рядків та підраховуємо кількість входжень кожного рядка у файлі `A`.
2. **Прохід 2 (Хешування файлу B):** Скануємо файл `B`, оновлюємо таблицю символів, фіксуючи кількість входжень кожного рядка у файлі `B` та його позицію.
3. **Прохід 3 (Ізоляція унікальних якорів):** Знаходимо всі рядки, які зустрічаються **рівно один раз у файлі A і рівно один раз у файлі B**. Такі пари рядків однозначно відповідають один одному і стають непорушними опорними точками (якорями). Встановлюємо прямі зв'язки між їхніми індексами: `A[i] <-> B[j]`.
4. **Прохід 4 (Пряме розширення збігів):** Скануємо масив зліва направо. Якщо рядок `A[i]` пов'язаний із `B[j]`, і при цьому рядки `A[i+1]` та `B[j+1]` є ідентичними, ми пов'язуємо `A[i+1]` із `B[j+1]`, навіть якщо вони не були унікальними (наприклад, повторювані рядки всередині тіла переміщеної функції).
5. **Прохід 5 (Зворотне розширення):** Скануємо масив справа наліво. Якщо `A[i]` пов'язаний із `B[j]`, і попередні рядки `A[i-1]` та `B[j-1]` збігаються, пов'язуємо їх.

### Покроковий приклад проходів Гекеля на рефакторингу

Розглянемо вихідний файл `A`, у якому функція `parse_header()` розташована на початку, а допоміжна `log_error()` — наприкінці. У файлі `B` розробник переніс `log_error()` на початок файлу:

- **Файл A:** `[1: fn parse_header(), 2: validate(), 3: return;, 4: fn log_error(), 5: write_log(), 6: return;]`
- **Файл B:** `[1: fn log_error(), 2: write_log(), 3: return;, 4: fn parse_header(), 5: validate(), 6: return;]`

1. **Проходи 1 та 2 (Таблиця частот):** Рядки `fn parse_header()`, `validate()`, `fn log_error()` та `write_log()` мають частоту `count_A = 1` та `count_B = 1`. Рядок `return;` має `count_A = 2` та `count_B = 2`.
2. **Прохід 3 (Якорі):** Встановлюються однозначні зв'язки між унікальними рядками:
   - `A[1] ("fn parse_header") <-> B[4]`
   - `A[2] ("validate()") <-> B[5]`
   - `A[4] ("fn log_error()") <-> B[1]`
   - `A[5] ("write_log()") <-> B[2]`
3. **Прохід 4 (Пряме розширення):** Алгоритм дивиться на сусідів після якорів: після `A[2]` та `B[5]` стоїть `return;`. Оскільки вони збігаються, встановлюється зв'язок `A[3] <-> B[6]`. Аналогічно після `A[5]` та `B[2]` встановлюється зв'язок `A[6] <-> B[3]`.
4. **Результат:** Усі 6 рядків успішно спаровано. Алгоритм бачить два суцільні блоки: блок `A[1..3]` перемістився на позицію `B[4..6]`, а блок `A[4..6]` — на позицію `B[1..3]`. Жодного зайвого рядка не видалено і не додано.

Складність алгоритму Гекеля становить строго `O(N + M)` за часом та `O(N + M)` за пам'яттю завдяки використанню хеш-таблиці.

## Patience Diff та проблема закривальних дужок

Хоча алгоритм Маєрса гарантує мінімальну кількість правок `D`, на реальному вихідному коді він нерідко генерує diff, незручний для сприйняття людиною.

Причина полягає в наявності великої кількості однакових дрібних рядків: закривальних фігурних дужок `}`, порожніх рядків або операторів `break;`. Коли програміст додає нову функцію поруч зі старою, жадібний алгоритм Маєрса може зіставити закривальну дужку нової функції із закривальною дужкою старої, розірвавши логічні межі функцій.

![Patience Diff проти Myers](/root/eng/sf-algorithms/sequence-diff/img/patience-diff-anchors.svg)
*Patience Diff проти Myers: використання найдовшої зростаючої підпослідовності унікальних рядків як якорів запобігає руйнуванню меж функцій.*

Щоб розв'язати цю проблему, Брем Коен створив алгоритм **Patience Diff** (названий за аналогією з картярською грою «Пасьянс» / Patience Sorting):

1. **Фільтрація унікальних рядків:** Знаходимо лише ті рядки, які зустрічаються строго один раз у файлі `A` і строго один раз у файлі `B`.
2. **Пошук LIS (Longest Increasing Subsequence):** Будуємо послідовність індексів цих унікальних рядків у файлі `B` у порядку їхнього слідування у файлі `A`. Знаходимо найдовшу зростаючу підпослідовність індексів за допомогою двійкового пошуку (терпляче сортування) за час `O(K log K)`, де `K` — кількість унікальних рядків.
3. **Фіксація якорів:** Знайдена LIS визначає послідовність непорушних семантичних якорів (наприклад, унікальні заголовки функцій або оголошення класів).
4. **Рекурсивне порівняння проміжків:** Проміжки між сусідніми якорями порівнюються рекурсивно за тим самим алгоритмом (або алгоритмом Маєрса).

### Механіка Patience Sorting для пошуку LIS

Алгоритм терплячого сортування розкладає індекси у «стопки» за правилом: кожне наступне число кладеться на вершину першої зліва стопки, верхній елемент якої є строго більшим за поточне число. Якщо такої стопки немає, створюється нова стопка праворуч.

Розглянемо послідовність індексів унікальних рядків у файлі `B`: `[4, 1, 6, 2, 5, 7, 3]`.
1. `4`: Стопка 1 `[4]`.
2. `1`: Кладемо на Стопку 1 (`1 < 4`): `[1]`.
3. `6`: Створюємо Стопку 2: `[1]`, `[6]`.
4. `2`: Кладемо на Стопку 2 (`2 < 6`): `[1]`, `[2]`.
5. `5`: Створюємо Стопку 3: `[1]`, `[2]`, `[5]`.
6. `7`: Створюємо Стопку 4: `[1]`, `[2]`, `[5]`, `[7]`.
7. `3`: Кладемо на Стопку 3 (`3 < 5`): `[1]`, `[2]`, `[3]`, `[7]`.

Кількість утворених стопок (4) дорівнює довжині найдовшої зростаючої підпослідовності, а відновлена LIS `[1, 2, 5, 7]` (або `[1, 2, 3, 7]`) визначає глобальний скелет змін. Оскільки опорними точками стають лише семантично унікальні рядки, спільні для обох файлів, Patience Diff ніколи не плутає випадкові дужки `}` і формує природні, інтуїтивно зрозумілі для розробника блоки змін.

### Histogram Diff: оптимізація Patience в ядрі Git

Сучасні версії Git використовують алгоритм **Histogram Diff** — оптимізований варіант Patience Diff. Замість глобального пошуку унікальних рядків по всьому файлу, Histogram Diff будує локальні гістограми частот рядків у поточному проміжку і обирає як якір рядок із **найменшою ненульовою частотою входження**. Це усуває проблему, коли через наявність хоча б двох однакових сигнатур у файлі алгоритм Patience втрачав якірні точки.

## Тристороннє злиття (3-Way Merge) та виявлення конфліктів

У системах контролю версій (Git) алгоритми порівняння послідовностей слугують основою для операції автоматичного злиття гілок. Коли дві гілки розробки вносять зміни в один файл, злиття спирається на три версії:
1. **Base (`O`):** Спільний предок двох гілок (найближчий спільний коміт).
2. **Ours (`A`):** Поточна версія файлу в робочій гілці.
3. **Theirs (`B`):** Версія файлу у гілці, що вливається.

### Алгоритм побудови злиття

1. Обчислюються два незалежні сценарії редагування: `diff(O, A)` та `diff(O, B)`.
2. Файл розбивається на послідовні сегменти (чанкі). Якщо певний діапазон рядків предка `O`:
   - Змінено лише у гілці `A`, а у `B` залишено без змін — автоматично приймаються зміни з `A`.
   - Змінено лише у гілці `B`, а у `A` залишено без змін — автоматично приймаються зміни з `B`.
   - Одинаково змінено в обох гілках `A` та `B` — зміна застосовується без конфлікту.
   - Різним чином змінено в обох гілках — фіксується **конфлікт злиття** (Merge Conflict), який обрамляється маркерами `<<<<<<< HEAD`, `=======` та `>>>>>>>`.

Якість алгоритму diff безпосередньо визначає кількість конфліктів: якщо алгоритм зсуває межі змін через однакові закривальні дужки (як це трапляється у Маєрса), Git сигналізує про фальшивий конфлікт у суміжних функціях, тоді як Patience та Histogram diff ізолюють зміни всередині окремих тіл функцій і здійснюють чисте злиття.

## Гранулярність diff: рядки, символи та дерева AST

Залежно від задачі порівняння застосовують три різні рівні гранулярності:
1. **Порядковий diff (Line-level Diff):** Елементами послідовності є рядки тексту. Найшвидший підхід, що лежить в основі всіх утиліт контролю версій.
2. **Внутрішньорядковий посимвольний diff (Inline Word/Character Diff):** Після знаходження змінених рядків алгоритм Маєрса запускається вдруге на рівні окремих слів або символів усередині заміненого рядка (наприклад, `git diff --word-diff`). Це дозволяє візуально підсвітити точкове виправлення друкарської описки чи назви змінної.
3. **Синтаксичний структурний diff (AST Diff / GumTree):** Текст трансформується парсером (наприклад, Tree-sitter) в абстрактне синтаксичне дерево (AST). Замість лінійних послідовностей алгоритм порівнює вузли дерева (оператори, оголошення, цикли), виявляючи перейменування змінних або зміну порядку аргументів функції незалежно від переформатування пробілів чи розривів рядків.

## Інженерні оптимізації та рушії порівняння

Промислові бібліотеки diff застосовують багаторівневий конвеєр попередньої та постобробки даних перед запуском основного алгоритму:

1. **Відсікання спільного префікса та суфікса (Prefix/Suffix Trimming):**
   Перед побудовою графа редагування виконується лінійне покрокове зіставлення рядків з початку та з кінця обох файлів за час `O(min(N, M))`. Якщо у файлі на 100 000 рядків змінено 5 рядків посередині, префіксне і суфіксне відсікання зменшує розмір робочих послідовностей для Маєрса зі 100 000 до 5 рядків, перетворюючи час роботи на частки мікросекунди.
2. **Інтернування та 64-бітне хешування рядків:**
   Усі рядки вихідних текстів одноразово перетворюються на 64-бітні некриптографічні хеші (наприклад, FNV-1a або xxHash). Масив вказівників на рядки замінюється масивом чисел `uint64_t`. Посимвольне порівняння рядків під час протягування змій замінюється однією процесорною інструкцією порівняння цілих чисел.
3. **Генерація уніфікованого формату (Unified Diff):**
   Знайдений сценарій редагування розбивається на окремі змістові фрагменти (**Hunks**), які містять змінені рядки разом із кількома рядками незміненого контексту (типово 3 рядки до і після змін) та заголовком діапазону:
   ```
   @@ -старт_A,кількість_A +старт_B,кількість_B @@
   ```

Архітектуру структур даних, прапорці конфігурації та сигнатури функцій публічного API бібліотеки diff описано у вставці [Інтерфейс бібліотеки порівняння послідовностей](root:sf-algorithms/sequence-diff/api-diff-engine.md).

## Порівняння алгоритмів та сфери застосування

Кожен із розглянутих алгоритмів оптимізований під специфічні інженерні вимоги:

| Алгоритм | Часова складність | Просторова складність | Підтримка переміщень | Природність для коду | Типове застосування |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Класичний DP (Вагнер—Фішер)** | `O(N · M)` | `O(N · M)` | Ні | Низька | Навчальні задачі, короткі рядки |
| **Гіршберґ (Hirschberg)** | `O(N · M)` | `O(N + M)` | Ні | Середня | Біоінформатика (вирівнювання ДНК) |
| **Маєрс (Myers)** | `O((N + M) · D)` | `O(D² або N + M)` | Ні | Середня | Утиліта `diff`, Git (за замовчуванням) |
| **Гекель (Heckel)** | `O(N + M)` | `O(N + M)` | Так | Висока | `ncurses`, виявлення рефакторингу |
| **Patience Diff** | `O((N + M) · log N)` | `O(N + M)` | Частково | Дуже висока | Код-рев'ю, злиття складних гілок |
| **Histogram Diff** | `O((N + M) · log N)` | `O(N + M)` | Частково | Дуже висока | Сучасний рушій `git diff --histogram` |

> 🔧 **Навіщо це.** Порівняння послідовностей є критичним компонентом сучасного інженерного стеку. Вибір алгоритму безпосередньо впливає на продуктивність та якість інструментів: алгоритм Маєрса гарантує математично мінімальний розмір патчів для мережевої передачі, Histogram/Patience diff запобігає конфліктам злиття у версійному контролі вихідного коду, а алгоритм Гекеля дозволяє бібліотекам рендерингу (таким як `ncurses` або Virtual DOM) мінімізувати кількість перемальовувань екрана за рахунок розпізнавання переміщених віконних блоків.
