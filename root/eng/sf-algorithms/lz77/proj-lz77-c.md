# ⚙️ LZ77 на C: кодувальник і декодер від нуля

[Стаття](topic:sf-algorithms/lz77) пояснила ідею LZ77 словами й малюнками; тут зберемо **робочий** кодек на C — щоб побачити, як трійка, ковзне вікно й посимвольне копіювання живуть у коді. Зробимо найзрозумілішу форму: класичні трійки `(offset, length, next)`, жадібний пошук збігу. Це не найшвидша й не найщільніша реалізація (промислова взяла б хеш-ланцюги й [прапорці LZSS](topic:sf-algorithms/lz77/detail)), зате коротка й чесна — її легко прочитати рядок за рядком і запустити на будь-якому мікроконтролері.

### Задача й формат

Маємо буфер байтів на вході; хочемо потік **трійок** на виході, з якого декодер точно відновить оригінал. Зафіксуймо невелике вікно — щоб усе влізло в скромну пам'ять і щоб поля трійки були маленькі:

:::tabs
```c
#include <stdint.h>
#include <stddef.h>

#define WINDOW   4096   // буфер пошуку: як далеко назад дивимось (offset < 4096)
#define MAX_LEN   18     // буфер попереду: найдовший збіг, який кодуємо
#define MIN_LEN    3     // коротші збіги не кодуємо посиланням (невигідно)

// Один елемент виходу. offset/length задають збіг у вже бачених даних;
// next — свіжий символ, що йде відразу за збігом (як у класичному LZ77).
typedef struct {
    uint16_t offset;   // на скільки байтів назад (0, якщо збігу нема)
    uint16_t length;   // скільки байтів копіювати (0, якщо збігу нема)
    uint8_t  next;     // наступний свіжий байт
    uint8_t  has_next; // чи є цей свіжий байт (на самому кінці може не бути)
} Triple;
```
```python
WINDOW  = 4096   # буфер пошуку: як далеко назад дивимось (offset < 4096)
MAX_LEN = 18     # буфер попереду: найдовший збіг, який кодуємо
MIN_LEN = 3      # коротші збіги не кодуємо посиланням (невигідно)

# Один елемент виходу. offset/length задають збіг у вже бачених даних;
# next — свіжий символ за збігом (як у класичному LZ77) або None у самому кінці.
class Triple(NamedTuple):
    offset: int          # на скільки байтів назад (0, якщо збігу нема)
    length: int          # скільки байтів копіювати (0, якщо збігу нема)
    next: int | None     # наступний свіжий байт; None — свіжого байта нема
```
:::

`WINDOW 4096` означає, що зсув уміщається в 12 бітів; `MAX_LEN 18` — довжина в 4 біти (значення 3…18 кодують як 0…15). Це класичні числа з навчальних LZSS — невипадково: 12+4 біти на посилання гарно лягають у формат. `MIN_LEN 3` — поріг беззбитковості: збіг із двох байтів дешевше записати дослівно, ніж посиланням.

### Кодувальник: жадібний пошук найдовшого збігу

Серце кодувальника — на кожній позиції знайти **найдовший** збіг у буфері пошуку (останні `WINDOW` уже пройдених байтів). Робимо це в лоб: пробуємо кожен можливий старт у вікні й дивимось, як далеко тягнеться збіг.

```c
// Шукає найдовший збіг для src[pos..] у вікні src[pos-WINDOW .. pos-1].
// Повертає довжину; *best_off — зсув назад до знайденого збігу.
static size_t find_match(const uint8_t *src, size_t n, size_t pos, size_t *best_off) {
    size_t best_len = 0;
    *best_off = 0;

    // початок вікна пошуку: не далі ніж WINDOW назад і не лівіше за початок даних
    size_t start = (pos > WINDOW) ? pos - WINDOW : 0;

    for (size_t cand = start; cand < pos; cand++) {
        // тягнемо збіг від cand і від pos, поки байти однакові
        size_t len = 0;
        while (len < MAX_LEN &&
               pos + len < n &&
               src[cand + len] == src[pos + len]) {
            len++;
        }
        if (len > best_len) {            // знайшли довший — запам'ятовуємо
            best_len = len;
            *best_off = pos - cand;      // зсув назад
        }
    }
    return best_len;
}
```

Зверни увагу: у `while` ми перевіряємо `src[cand + len] == src[pos + len]`, де `cand < pos`. Коли збіг тягнеться так далеко, що `cand + len` доходить до самого `pos` і **переростає** його, ми починаємо порівнювати з ще не закодованими байтами — і це **правильно**: так природно виходять збіги, що накладаються самі на себе (зсув менший за довжину). Декодер їх теж відтворить, бо копіюватиме посимвольно (нижче).

Тепер головний цикл — він склеює пошук у потік трійок:

```c
// Кодує src[0..n) у масив трійок out (місткістю out_cap). Повертає кількість трійок.
size_t lz77_encode(const uint8_t *src, size_t n, Triple *out, size_t out_cap) {
    size_t pos = 0, count = 0;

    while (pos < n && count < out_cap) {
        size_t off;
        size_t len = find_match(src, n, pos, &off);

        if (len < MIN_LEN) {            // збігу нема (або закороткий) → лише свіжий байт
            out[count].offset   = 0;
            out[count].length   = 0;
            out[count].next     = src[pos];
            out[count].has_next = 1;
            pos += 1;
        } else {                        // є вигідний збіг → посилання + свіжий байт за ним
            out[count].offset = (uint16_t)off;
            out[count].length = (uint16_t)len;
            pos += len;                 // перестрибуємо весь збіг
            if (pos < n) {              // ...і дописуємо наступний свіжий байт
                out[count].next     = src[pos];
                out[count].has_next = 1;
                pos += 1;
            } else {
                out[count].has_next = 0; // збіг сягнув самого кінця — свіжого байта нема
            }
        }
        count++;
    }
    return count;
}
```

Логіка точно повторює статтю. Нема збігу (`len < MIN_LEN`) — пишемо трійку з порожнім посиланням і одним свіжим байтом, рухаємось на 1. Є збіг — пишемо посилання, перестрибуємо `len` байтів і додаємо один свіжий за ним. Єдина пастка тут — **кінець даних**: якщо збіг доїхав до самого хвоста, свіжого байта вже нема, тож ставимо `has_next = 0`. Забудеш цю перевірку — вилізеш за межі буфера на останній трійці.

### Декодер: чистий copy-paste назад

Декодер набагато простіший — він нічого не шукає, лише розгортає посилання. Уся хитрість — копіювати **по одному байту**, бо збіг може накладатися сам на себе.

```c
// Розгортає масив трійок назад у байти. out — вихідний буфер (він-таки словник).
// Повертає кількість відновлених байтів.
size_t lz77_decode(const Triple *in, size_t count, uint8_t *out) {
    size_t o = 0;
    for (size_t i = 0; i < count; i++) {
        size_t off = in[i].offset;
        size_t len = in[i].length;

        // КЛЮЧОВЕ: копіюємо по одному байту зліва направо.
        // Якщо off < len, ми дописуємо байти, на які тут-таки посилаємось —
        // так одна трійка відтворює довгу серію (накладний збіг).
        for (size_t k = 0; k < len; k++) {
            out[o] = out[o - off];
            o++;
        }
        if (in[i].has_next)
            out[o++] = in[i].next;
    }
    return o;
}
```

Спокуса «оптимізувати» цикл через `memcpy(out + o, out + o - off, len)` тут **зламає** декодер: `memcpy` не гарантує посимвольного порядку й не побачить байтів, що дописуються по ходу. На накладному збігу (скажімо, `(1, 10, …)` — розмножити останній байт удесятеро) `memcpy` дасть сміття, а наш простий цикл — правильну серію. Це той випадок, коли наївний цикл правильніший за «швидку» бібліотечну функцію.

### Прогін на рядку з повторами

Перевіримо на «ABRACADABRA». Кодувальник видасть приблизно таке (як у [розборі руками](topic:sf-algorithms/lz77)):

```
вхід:  A B R A C A D A B R A   (11 байтів)

трійки:
  (0,0,A)   нема збігу → свіжий A
  (0,0,B)   нема збігу → свіжий B
  (0,0,R)   нема збігу → свіжий R
  (3,1,C)   «A» на 3 назад, далі C
  (2,1,D)   «A» на 2 назад, далі D
  (7,4,—)   «ABRA» на 7 назад, до кінця

6 трійок замість 11 байтів; хвіст «ABRA» згорнувся в одне посилання.
```

На такому короткому рядку виграш скромний (трійки самі не безкоштовні), та видно сам механізм: що довші й частіші повтори, то сильніше посилання перемагають дослівний запис. На реальному тексті чи логах ця сама проста схема дає стиск у рази.

### Пастки, на яких спотикаються

- **Накладний збіг і `memcpy`.** Найчастіша помилка. Декодер мусить копіювати **посимвольно**; будь-яка блокова копія ламає збіги зі зсувом, меншим за довжину. Якщо твій декодер дає сміття на серіях однакового — майже напевно тут.
- **Кінець даних без свіжого байта.** Якщо збіг сягає самого хвоста, свіжого байта нема (`has_next = 0`). Не перевіриш — читання/запис за межами буфера на останній трійці.
- **Квадратична швидкість.** `find_match` перебирає все вікно на кожній позиції — для `WINDOW 4096` це ще терпимо, але на великому вікні кодувальник стане черепахою. Промислові кодеки замінюють цей перебір [хеш-ланцюгами](topic:sf-algorithms/lz77/detail); декодер же лишається таким самим швидким.
- **Маленький `MIN_LEN`.** Якщо кодувати збіги коротші за поріг беззбитковості, посилання дорожчатиме за самі байти — і «стиснення» роздуватиме дані. Поріг (тут 3) має відповідати тому, скільки бітів реально займає посилання у твоєму форматі.
- **Розмір вихідного буфера.** На даних без повторів кожен байт дає трійку — у найгіршому разі вихід у трійках довший за вхід. Місткість `out_cap` має це передбачати (або переходь на [LZSS із прапорцями](topic:sf-algorithms/lz77/detail), що не роздуває).

Цей кодек навмисно мінімальний — рівно стільки, щоб ідея LZ77 стала кодом, який можна прочитати й запустити. Додаси хеш-ланцюги для швидкості, прапорці LZSS проти роздування й [Гаффман](topic:math-information/huffman-coding) на дотиск — і дійдеш до [DEFLATE](topic:sf-algorithms/deflate), того самого, що в zip і PNG.
