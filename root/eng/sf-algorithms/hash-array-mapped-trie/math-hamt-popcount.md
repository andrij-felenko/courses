# 🧮 Математичні основи HAMT: побітова індексація, аналіз глибини та колізій

Функціонування та ефективність структури Hash Array Mapped Trie (HAMT) спираються на побітову алгебру над геш-кодами ключів, компресію розріджених масивів за допомогою індексувальної бітової мапи та імовірнісний аналіз розподілу префіксів у дереві.

---

## 1. Формалізація індексації через popcount та алгебраїчний доказ

Розглянемо математичну модель маскування та індексації в одному внутрішньому вузлі HAMT.

### Вхідні параметри та простори станів

Нехай `h` — геш-код ключа, збережений як ціле число без знаку розрядністю `W` бітів (де `W = 32` або `W = 64`):

```
h ∈ {0, 1, ..., 2ʷ - 1}
```

Фактор розгалуження дерева дорівнює `B = 2ʷ_c`, де `w_c` — кількість бітів на один рівень (стандартно `w_c = 5`, що дає `B = 32`).

Для рівня дерева `L ∈ {0, 1, ..., ⌈W / w_c⌉ - 1}` відповідний 5-бітний фрагмент (chunk) `c_L(h)` виділяється за формулою:

```
c_L(h) = ⌊ h / 2⁵ᴸ ⌋ mod 32 = (h >> (5 · L)) & 0x1F
```

Звідси значення фрагмента належить скінченній множині `c_L(h) ∈ {0, 1, 2, ..., 31}`.

### Бітова мапа та монотонне відображення індексів

У кожному внутрішньому вузлі стан дочірніх гілок описується 32-бітним вектором `bitmap ∈ {0, 1}³²`. Позначимо через `b_k ∈ {0, 1}` значення `k`-го біта у `bitmap` для `k ∈ {0, 1, ..., 31}`.

Множина встановлених бітів вузла:

```
S = { k ∈ {0, 1, ..., 31} | b_k = 1 }
```

Розмір компактного масиву вказівників дорівнює потужності цієї множини `m = |S| = popcount(bitmap)`.

Наша мета — побудувати строго монотонне бієктивне відображення `f: S → {0, 1, ..., m - 1}`, яке кожному наявному фрагменту `k ∈ S` ставить у відповідність індекс `i` у компактному масиві.

Математично індекс `i` для даного елемента `k ∈ S` визначається як кількість елементів множини `S`, строго менших за `k`:

```
i = f(k) = |{ j ∈ S | j < k }| = ∑_{j=0}^{k-1} b_j
```

### Алгебраїчне доведення еквівалентності операції popcount(bitmap & mask)

Застосуємо побітову арифметику. Розглянемо число `mask(k)`, у якому перші `k` бітів установлені в `1`, а решта бітів дорівнюють `0`:

```
mask(k) = (1 << k) - 1 = ∑_{j=0}^{k-1} 2ʲ
```

Виконаємо побітове множення `AND` між бітовою мапою вузла та маскою:

```
masked_bitmap = bitmap & mask(k)
```

Розглянемо `j`-й біт результату `(masked_bitmap)_j`:

```
(masked_bitmap)_j = b_j ∧ (mask(k))_j
```

Оскільки `(mask(k))_j = 1` при `j < k` та `(mask(k))_j = 0` при `j ≥ k`, отримуємо:

```
(masked_bitmap)_j = b_j ,  якщо j ∈ {0, 1, ..., k - 1}
(masked_bitmap)_j = 0   ,  якщо j ∈ {k, k + 1, ..., 31}
```

За визначенням операції `popcount(X)`, вона обчислює суму бітів числа `X`:

```
popcount(masked_bitmap) = ∑_{j=0}^{31} (masked_bitmap)_j = ∑_{j=0}^{k-1} b_j + ∑_{j=k}^{31} 0 = ∑_{j=0}^{k-1} b_j = i
```

Отже, операція `popcount(bitmap & ((1 << k) - 1))` алгебраїчно тотожна кількості встановлених бітів із індексами `j < k`. Це гарантує точний і монотонний доступ до елементів компактного масиву за час `O(1)`.

## 2. Числовий приклад обчислення popcount-індексації

Для остаточного засвоєння механізму розглянемо конкретне числове значення бітової мапи.

Нехай внутрішній вузол має бітову мапу:

```
bitmap = 0b 0010 0000 0000 0100 0000 0000 0010 0100₂ = 0x20040024
```

У цій масці біти встановлені в одиницю у позиціях:
- Біт №2 (`2² = 4`)
- Біт №5 (`2⁵ = 32`)
- Біт №14 (`2¹⁴ = 16384`)
- Біт №29 (`2²⁹ = 536870912`)

Загальна кількість дітей у вузлі `m = popcount(0x20040024) = 4`. Фізичний масив має розмір 4 елементи: `children[0..3]`.

### Обчислення індексу для шуканого фрагмента k = 14

1. **Обчислення маски:**
```
mask(14) = (1 << 14) - 1 = 16384 - 1 = 16383 = 0x00003FFF
```
Двійковий вигляд: `0000 0000 0000 0000 0011 1111 1111 1111₂` (14 одиниць).

2. **Застосування робітового AND:**
```
masked_bitmap = 0x20040024 & 0x00003FFF = 0x00000024
```
Двійковий вигляд `masked_bitmap`: `0000 0000 0000 0000 0000 0000 0010 0100₂`.

3. **Підрахунок popcount:**
Одиниці залишилися тільки в позиціях 2 і 5.
```
popcount(0x00000024) = 2
```

Висновок: шуканий вказівник для фрагмента `k = 14` знаходиться в масиві за індексом `2` (`children[2]`). Обчислення відбулося без жодного циклу за 3 побітові інструкції CPU.

## 3. Імовірнісний аналіз глибини дерева та кількості вузлів

Оцінимо математичне сподівання висоти дерева та обсяг пам'яті при зберіганні `N` ключів.

### Граничні значення глибини H

Оскільки 32-бітний геш ділиться на фрагменти по 5 бітів, максимальна глибина дерева `H_max` визначається кількістю фрагментів:

```
H_max = ⌈ 32 / 5 ⌉ = 7
```

Для 64-бітного геш-коду з `B = 32`:

```
H_max = ⌈ 64 / 5 ⌉ = 13
```

Це означає, що незалежно від кількості елементів `N` (навіть для 100 мільярдів записів), глибина дерева **не може перевищити 13 рівнів**.

### Математичне сподівання глибини E[H]

Припустимо, що геш-функція `h(k)` є ідеально рівномірною на проміжку `[0, 2ʷ - 1]`.

Ймовірність того, що два випадкові ключі мають однакові значення фрагментів на перших `L` рівнях:

```
P(збіг на рівні L) = (1 / B)^L = 2⁻⁵ᴸ
```

Розглянемо математичне сподівання кількості внутрішніх вузлів `E[I(N)]` у дереві з `N` елементами. За допомогою апроксимації Пуассона для префіксних дерев класичний результат Бертоле та Фложоле (Flajolet, 1986) дає:

```
E[I(N)] = ∑_{L=1}^{∞} Bᴸ · ( 1 - (1 - B⁻ᴸ)ᴺ - N · B⁻ᴸ · (1 - B⁻ᴸ)ᴺ⁻¹ )
```

При великих `N` ця сума асимптотично наближається до:

```
E[I(N)] ≈ N / ((B - 1) · ln B)
```

Для фактора розгалуження `B = 32`:

```
(B - 1) · ln B = 31 · ln(32) ≈ 31 · 3.4657 ≈ 107.43
E[I(N)] ≈ N / 107.43 ≈ 0.0093 · N
```

Це дивовижний результат: на кожні 100 ключів у HAMT створюється **менше ніж 1 внутрішній вузол**! Решта ключів знаходяться у компактних листових вузлах на верхніх рівнях.

Середня глибина пошуку `E[H]` обчислюється як:

```
E[H] = log_B N + O(1) = (ln N / ln 32) + C
```

Для `N = 1 000 000` елементів:

```
log₃₂ (10⁶) = ln(10⁶) / 3.4657 ≈ 13.8155 / 3.4657 ≈ 3.986
```

Середня глибина пошуку елемента у мільйонній базі становить **менше 4 переходів**.

## 4. Аналіз колізій геш-функції та Birthday Paradox

Якщо два різні ключі `K₁ ≠ K₂` мають абсолютно однакові значення геш-функції `h(K₁) = h(K₂)`, дерево не зможе розділити їх навіть на найнижчому рівні `H_max`.

Згідно з парадоксом днів народження (Birthday Paradox), ймовірність виникнення хоча б однієї колізії геш-кодів для `N` ключів та розрядності гешу `W` бітів становить:

```
P_collision(N, W) ≈ 1 - exp( - N² / (2 · 2ʷ) )
```

Проаналізуємо цю ймовірність для різних розрядностей гешу:

1. **Для 32-бітного гешу (`W = 32`, `2³² ≈ 4.29 · 10⁹`):**
   - При `N = 10 000`: `P_collision ≈ 1 - exp(- 10⁸ / 8.58·10⁹) ≈ 1.15%`
   - При `N = 100 000`: `P_collision ≈ 1 - exp(- 10¹⁰ / 8.58·10⁹) ≈ 68.3%`
   Отже, для 32-бітного гешу колізійні листи (Collision Leaves) є неминучими при великих обсягах даних.

2. **Для 64-бітного гешу (`W = 64`, `2⁶⁴ ≈ 1.84 · 10¹⁹`):**
   - При `N = 1 000 000`: `P_collision ≈ 1 - exp(- 10¹² / 3.68·10¹⁹) ≈ 2.7 · 10⁻⁸`
   - При `N = 100 000 000`: `P_collision ≈ 1 - exp(- 10¹⁶ / 3.68·10¹⁹) ≈ 0.027%`
   При використанні 64-бітного гешу ймовірність виникнення колізій є мізерно малою, а глибина дерева гарантовано обмежена 13 рівнями.

У разі колізії HAMT зберігає списки елементів із однаковим гешем у спеціальних колізійних вузлах. Використання якісних некриптографічних геш-функцій (наприклад, xxHash64 або MurmurHash3) забезпечує ідеально рівномірний розподіл і захищає HAMT від атак типу HashDoS (навмисного виклику колізій для уповільнення роботи дерева).
