# Підпис у конвеєрі без ключа в конвеєрі: архітектура віддаленого підписання та короткоживучої ідентичності

<preknowlist>
- [Цифровий підпис та хешування](root:sf-security/hash-and-digital-signature) — асиметрична криптографія, закритий та відкритий ключ, перевірка цілісності та автентичності артефактів.
- [Де живе приватний ключ](root:sf-security/de-zhyve-pryvatnyi-kliuch) — апаратні модулі безпеки (HSM), токени, ізоляція криптографічних операцій від середовища виконання.
- [OpenID Connect та федеративна ідентичність](root:sf-security/openid-connect) — механізм видачі та криптографічної перевірки токенів довіреними провайдерами (IdP).
- [Управління секретами та ротація](root:sf-security/secrets-management) — ризики статичних секретів, моделі розподілу доступу та часові обмеження токенів.
</preknowlist>

Автоматизований конвеєр неперервної інтеграції та доставки (CI/CD) за своєю природою є динамічним, розподіленим і вкрай вразливим середовищем виконання. Щодня типовий раннер збірки (англ. *build runner*) витягує сотні зовнішніх сторонніх бібліотек із публічних реєстрів (`npm`, `PyPI`, `crates.io`), запускає неперевірені скрипти збірки з pull request сторонніх розробників і компілює тисячі рядків коду у спільній або тимчасовій віртуальній машині. Якщо в таке середовище завантажити довгоживучий закритий ключ підпису релізів (наприклад, сертифікат підпису коду PKCS#12 або приватний ключ ECDSA/RSA виробника), будь-яка вразливість у системі збірки чи шкідливий код у залежностях призводить до миттєвого викрадення ключа. Зловмисник, заволодівши закритим ключем, отримує можливість необмежено підписувати шкідливі оновлення, бекдори та троянізовані прошивки від імені законного виробника, а відкликання скомпрометованого кореневого сертифіката паралізує всю екосистему вже встановленого клієнтського програмного забезпечення.

Для розв'язання цієї фундаментальної суперечності між потребою в повній автоматизації релізів і вимогою нульової довіри до середовища збірки було розроблено архітектуру **віддаленого підписання** (англ. *Remote Signing*) та **безключової криптографії** (англ. *Keyless Signing*). У цій парадигмі раннер конвеєра ніколи не отримує доступу до закритого ключа, не зберігає його в пам'яті й не виконує локальних криптографічних перетворень. Замість цього раннер обчислює лише криптографічний геш зібраного артефакту, підтверджує свою поточну контекстну ідентичність за допомогою короткоживучих токенів OpenID Connect (OIDC) і передає запит до ізольованої служби підпису, захищеної апаратним модулем безпеки (HSM) та рушієм суворих релізних політик.

### Фатальна дилема традиційного конвеєра та таксономія загроз

Традиційний підхід до підписання програмного забезпечення базувався на припущенні, що сервер збірки є довіреним периметром. Довгоживучий закритий ключ завантажувався в конвеєр як зашифрована змінна оточення (`ACTIONS_SECRET`, `GITLAB_SECRET` або сховище HashiCorp Vault), розпаковувався в пам'ять раннера або тимчасовий файл на диску, після чого утиліта на кшталт `openssl`, `sign tool` чи `gpg` накладала цифровий підпис на скомпільований бінарний файл.

```
+-----------------------------------------------------------------------------+
| Антипідхід: Довгоживучий приватний ключ усередині середовища збірки         |
|                                                                             |
|  [Pull Request / Git Push]                                                  |
|           ↓                                                                 |
|  [CI/CD Runner (GitHub/GitLab/Jenkins)]                                     |
|  ├── Завантаження 1000+ сторонніх пакетів (npm, pip, cargo)                 |
|  ├── Виконання компілятора та довільних скриптів збірки                     |
|  ├── Секрет у RAM/диску: PRIVATE_KEY.pem  <=== (ТОЧКА КАТАСТРОФІЧНОГО ВИХОДУ)|
|  └── Локальний виклик OpenSSL dgst -sign                                    |
|           ↓                                                                 |
|  [Викрадення ключа: зловмисник отримує вічний контроль над релізами]        |
+-----------------------------------------------------------------------------+
```

Така модель створює чотири критичні вектори компрометації, обумовлені самою структурою сучасного процесу розробки:

1. **Ексфільтрація через сторонні залежності (Supply Chain Poisoning):** Сучасні проекти використовують тисячі транзитивних бібліотек. Достатньо одному пакету містити шкідливий скрипт встановлення (`postinstall` в npm або `setup.py` в Python), щоб він прочитав змінні оточення, просканував файлову систему або підключився до адресного простору процесу збірки через системні виклики `ptrace` та надіслав викрадений приватний ключ на віддалений сервер управління (C2).
2. **Атаки через pull request (PwnRequest):** Якщо конвеєр налаштовано на автоматичний запуск збірки для зовнішніх форків або pull request, зловмисник може надіслати код із вбудованою інструкцією читання пам'яті раннера та викрасти секрети підпису.
3. **Витік у журнали та артефакти:** Помилка в налагоджувальних скриптах, аварійний скид пам'яті ядра під час збою компілятора (core dump) або неконтрольований вивід трасування утиліт призводить до того, що закритий ключ потрапляє у відкриті логи конвеєра, доступні всім розробникам організації.
4. **Неможливість гранулярного аудиту:** Коли ключ живе на раннері, неможливо довести, чи був підписаний конкретний офіційний релізний бінарник, чи хтось запустив тестову збірку в сторонній гілці й згенерував валідний підпис для шкідливого драйвера чи підробленої прошивки.

Детальний історичний огляд реальних катастрофічних компрометацій інфраструктури розробки викладено у вставці: [уроки зламу SolarWinds та еволюція безключового підпису](root:sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/hist-solarwinds-and-code-signing.md).

### Архітектурний принцип: розділення обчислення та криптографічного затвердження

Фундаментальне вирішення проблеми витоку ключів полягає у фізичному та логічному розриві між процесом створення артефакту та процесом накладання цифрового підпису.

Головне криптографічне спостереження полягає в тому, як саме працюють алгоритми цифрового підпису (ECDSA, RSA-PSS, Ed25519). Жоден сучасний алгоритм асиметричного підпису не оперує безпосередньо гігабайтним бінарним файлом або образом диска. Натомість математична операція підпису виконується винятково над криптографічним дайджестом фіксованої довжини:

```
M              = Бінарний артефакт довільного розміру (наприклад, 500 МБ)
H(M)           = SHA-256(M) -> Фіксований 32-байтовий дайджест
Signature      = Sign(PrivateKey, H(M))
Verification   = Verify(PublicKey, H(M), Signature)
```

З цього випливає прямий інженерний інваріант: **для створення юридично та криптографічно бездоганного цифрового підпису апаратному модулю безпеки не потрібен сам артефакт — йому потрібен лише його 32-байтовий геш**.

![Порівняння архітектури підпису: статичний ключ у раннері проти віддаленого HSM](/root/eng/sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/img/traditional-vs-remote-signing.svg)
*Порівняння архітектури підпису: небезпечне зберігання статичного ключа в середовищі збірки проти ізольованого віддаленого підписання через апаратний модуль безпеки HSM.*

Це дозволяє вибудувати архітектуру, де раннер виконує важку й ненадійну роботу (компіляцію, лінкування, оптимізацію) і самостійно рахує фінальний дайджест `SHA-256`, а потім надсилає цей короткий геш через мережу до захищеної, ізольованої служби підпису. Закритий ключ зберігається винятково всередині апаратного модуля безпеки (HSM), який фізично не підтримує операцію експорту ключа назовні (`CKA_EXTRACTABLE = FALSE` у термінах стандарту PKCS#11).

### Апаратні модулі безпеки (HSM) та інтерфейс PKCS#11

Апаратний модуль безпеки (англ. *Hardware Security Module*, HSM) є спеціалізованим фізичним обчислювальним пристроєм, спроєктованим для захисту криптографічних ключів упродовж усього їхнього життєвого циклу. На відміну від звичайного сервера, HSM сертифікується за суворими міжнародними стандартами безпеки, зокрема **FIPS 140-2 / FIPS 140-3 Рівень 3 або 4**.

Фізична архітектура HSM включає багатошарові апаратні бар'єри:
1. **Захисні кремнієві сітки (Active Shielding):** Поверхня кристала криптопроцесора покрита мікроскопічною провідною сіткою. Будь-яка спроба фізичного розкриття корпусу мікросхеми мікроголками для зчитування бітів пам'яті призводить до зміни електричного опору сітки.
2. **Датчики впливу навколишнього середовища:** Сенсори температури, іонізуючого випромінювання, лазерного опромінення та перепадів напруги живлення захищають пристрій від атак за сторонніми каналами (Side-Channel Attacks) та ін'єкцій збоїв (Fault Injection).
3. **Миттєве апаратне самознищення (Zeroization):** У разі фіксації спроби злому внутрішня енергонезалежна пам'ять ключа миттєво закорочується на землю і стирається за частки мікросекунди.

В інфраструктурній практиці застосовують два основні фізичні формфактори апаратних HSM:
* **Внутрішні карти розширення PCIe HSM:** Встановлюються безпосередньо в серверні шасі шлюзу підпису. Забезпечують найвищу швидкість обробки (до 10 000 криптографічних підписів ECDSA на секунду з мінімальними затримками шини PCIe), проте прив'язані до одного фізичного хоста.
* **Мережеві пристрої (Network-Attached HSM Appliances):** Автономні захищені сервери (наприклад, Thales Luna HSM або Entrust nShield), доступні через резервовані Ethernet-інтерфейси з автентифікацією TLS. Вони дозволяють створити відмовостійкий георозподілений пул криптографічних ресурсів для сотень незалежних шлюзів підпису.

Взаємодія шлюзу підпису з апаратним модулем стандартизована міжнародним інтерфейсом **PKCS#11 (Cryptoki)**. Інтерфейс визначає операції над непрозорими апаратними дескрипторами об'єктів (handles):

```
+-----------------------------------------------------------------------------+
| Взаємодія шлюзу підпису з HSM через інтерфейс PKCS#11                       |
|                                                                             |
|  [Signing Gateway Service]                                                  |
|           │                                                                 |
|  1. C_Initialize()                 (Ініціалізація криптографічного драйвера)|
|  2. C_OpenSession(slot_id)         (Відкриття сесії до захищеного слота)    |
|  3. C_Login(CKU_USER, pin)         (Автентифікація сервісу в HSM)           |
|  4. C_FindObjectsInit(key_label)   (Пошук дескриптора закритого ключа)      |
|  5. C_SignInit(CKM_ECDSA, hKey)    (Ініціалізація операції підпису)         |
|  6. C_Sign(pDigest, 32, pSignature)(Апаратне накладання підпису над гешем)  |
|           │                                                                 |
|           ▼                                                                 |
|  [Hardware HSM Enclave (Non-exportable Private Key)]                        |
+-----------------------------------------------------------------------------+
```

Ключова перевага функції `C_Sign` полягає в тому, що закритий ключ ніколи не залишає захищеного кремнієвого анклаву. Навіть якщо операційна система сервера, де запущено шлюз підпису, буде повністю скомпрометована зловмисником із правами `root`, нападник не зможе прочитати байти приватного ключа з пам'яті ядра.

### Криптографічні алгоритми цифрового підпису: ECDSA проти Ed25519 та RSA-PSS

Вибір криптографічного алгоритму цифрового підпису для релізного конвеєра визначає як рівень стійкості, так і швидкість верифікації на кінцевих пристроях (клієнтських комп'ютерах, серверах чи мікроконтролерах).

```
+-----------------------------------------------------------------------------+
| Порівняння алгоритмів підпису артефактів                                    |
|                                                                             |
| Алгоритм        Розмір ключа    Розмір підпису   Швидкість   Вразливість    |
| ─────────────────────────────────────────────────────────────────────────── |
| RSA-PSS         2048-4096 біт   256-512 байтів   Повільно    Складний паддінг|
| ECDSA (P-256)   256 біт         64 байти         Швидко      Витік через k  |
| Ed25519 (EdDSA) 256 біт         64 байти         Дуже швидко Стійкий детерм.|
+-----------------------------------------------------------------------------+
```

1. **ECDSA (Elliptic Curve Digital Signature Algorithm, NIST P-256 / P-384):**
   Широко підтримується в усіх сучасних апаратних HSM та операційних системах. Проте класичний алгоритм ECDSA має критичну вразливість: для кожного підпису вимагається генерація криптографічно стійкого випадкового одноразового числа `k` (nonce). Якщо генератор випадкових чисел HSM дасть збій або використає однакове значення `k` для двох різних повідомлень, приватний ключ обчислюється елементарною алгебраїчною операцією:
   
   ```
   s1 = k⁻¹ · (H(M1) + d · r)  mod n
   s2 = k⁻¹ · (H(M2) + d · r)  mod n
   d  = (s1·H(M2) - s2·H(M1)) · (s2·r - s1·r)⁻¹  mod n
   ```
   
   Для усунення цього ризику сучасні конвеєри використовують детермінований ECDSA за стандартом **RFC 6979**, де число `k` генерується шляхом криптографічного гешування приватного ключа та дайджесту повідомлення `k = HMAC(PrivateKey, H(M))`.

2. **Ed25519 (Edwards-curve Digital Signature Algorithm, EdDSA):**
   Сучасний криптографічний стандарт на базі скрученої кривої Едвардса Curve25519. Алгоритм є повністю детермінованим за дизайном, має постійний час виконання операцій (захист від атак за часом виконання), забезпечує компактний розмір відкритого ключа (32 байти) та підпису (64 байти) і демонструє найвищу швидкість перевірки на вбудованих мікроконтролерах.

3. **RSA-PSS (Probabilistic Signature Scheme):**
   Модернізована схема підпису RSA з імовірнісним доповненням PSS (PKCS#1 v2.1). Забезпечує найвищу швидкість перевірки на малопотужних клієнтах, проте створює великі бінарні підписи (256–512 байтів) та повільно генерується на стороні HSM.

### Хмарні сервіси підпису та брокери секретів (KMS і HashiCorp Vault)

Окрім фізичних апаратних модулів безпеки у власних серверних шафах, сучасні інженерні команди активно використовують керовані хмарні сервіси управління ключами:
* **Cloud KMS (AWS KMS, Google Cloud KMS, Azure Key Vault Managed HSM):** Хмарні провайдери надають REST та gRPC API для операції асиметричного підпису (`kms:Sign`, `asymmetricSign`). Приватний ключ генерується всередині FIPS 140-2 Level 3 HSM провайдера і ніколи не розкривається користувачу.
* **HashiCorp Vault Transit Secrets Engine:** Потужний проміжний криптографічний шлюз (Cryptography as a Service). Vault приймає OIDC-токени від раннерів збірки, перевіряє права доступу через власну систему ACL та виконує підпис `transit/sign/{key_name}` або на власних програмних ключах, або делегуючи операцію фізичному апаратному HSM через плагін PKCS#11.

Така багаторівнева схема дозволяє масштабувати службу підпису, ізолюючи прямий доступ до HSM від мережі раннерів і забезпечуючи централізований облік квот і транзакцій.

### Церемонії ключів (Key Ceremonies) та кворум розділення M-of-N

Безпека кореневого закритого ключа в HSM залежить не лише від фізичного захисту чіпа, а й від процедури його ініціалізації. Створення релізного ключа найвищого рівня довіри здійснюється через суворо регламентовану процедуру — **церемонію ключів** (англ. *Key Ceremony*).

Церемонія проводиться у фізично захищеному приміщенні (екранованій кімнаті Фарадея без камер і радіоелектронних пристроїв) у присутності кількох незалежних офіцерів безпеки:
1. **Схема розділення секрету Шаміра (Shamir's Secret Sharing Scheme):** Майстер-пароль активації HSM або корінь ініціалізації розбивається на `N` частин (наприклад, 5 смарт-карт). Для розблокування або відновлення слота вимагається одночасна присутність кворуму з `M` офіцерів (наприклад, 3 з 5).
2. **Апаратне загортання ключів (Key Wrapping / AES-KWP):** Створений приватний ключ релізу ніколи не зберігається у відкритому вигляді на зовнішніх носіях. Для резервного копіювання HSM шифрує його за стандартом NIST SP 800-38F ключем шифрування ключів (Key Encryption Key, KEK), що дозволяє переносити зашифровані образи між резервними кластерами HSM без загрози витоку.

### Автентифікація раннера без статичних секретів: ефемерні OIDC токени

Якщо раннер надсилає запит на віддалений підпис до ізольованого сервісу, виникає наступне критичне питання безпеки: **як служба підпису може переконатися, що запит надійшов від легітимного релізного конвеєра, а не від зламаного тестового раннера чи зловмисника, якщо ми принципово відмовляємося зберігати в раннері будь-які статичні паролі чи API-ключі?**

Використання статичного API-токена до сервісу підпису було б простою підміною понять: нападник викрав би API-токен замість закритого ключа і викликав сервіс підпису напряму. Справжня безпека вимагає повної відмови від статичних секретів на користь **ефемерної ідентичності робочих навантажень** (англ. *Workload Identity*) на базі стандарту **OpenID Connect (OIDC)**.

![Послідовність віддаленого підписання з OIDC-автентифікацією](/root/eng/sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/img/oidc-signing-flow.svg)
*Послідовність взаємодії між CI-раннером, провайдером ідентичності OIDC, шлюзом підпису та апаратним модулем HSM.*

Механізм ефемерної автентифікації працює за наступним криптографічним протоколом:
1. **Запит токену ідентичності:** Під час запуску кроку релізу клієнтська утиліта в раннері звертається до внутрішнього локального сокета CI-провайдера (GitHub Actions, GitLab CI тощо) із запитом на генерацію OIDC ID Token. У запиті обов'язково вказується цільова аудиторія (Audience, `aud`), наприклад `https://signing.internal.acme.net`.
2. **Криптографічна генерація JWT:** CI-провайдер динамічно формує JSON Web Token (JWT), де вказує точні метадані поточного запуску, і підписує цей токен власним асиметричним ключем (RS256/ES256).
3. **Короткий термін дії:** Токен видається з часом життя всього 5–15 хвилин (`exp = now + 600s`) і є одноразовим для конкретного кроку збірки.
4. **Передача на шлюз:** Раннер відправляє отриманий JWT разом із 32-байтовим гешем артефакту через взаємно автентифікований TLS-тунель (mTLS) до служби підпису.

```
+-----------------------------------------------------------------------------+
| Кроки протоколу безключового віддаленого підписання                         |
|                                                                             |
| 1. CI Runner ------(Запит OIDC JWT, aud: sig-service)-----> [CI Provider]   |
| 2. CI Runner <-----(Підписаний JWT з метаданими збірки)----+                 |
| 3. CI Runner: Local compute SHA-256(firmware.bin) -> Digest                 |
| 4. CI Runner ------(mTLS RPC: Sign(Digest, OIDC_JWT))-----> [Signing Gate]  |
| 5. Signing Gate: Verify JWT signature via JWKS                              |
| 6. Signing Gate: Policy Engine evaluates claims (Tag, Repo, Workflow)       |
| 7. Signing Gate ---(PKCS#11 C_Sign(Digest))---------------> [Hardware HSM]  |
| 8. Signing Gate <--(Raw Signature (r, s))-------------------+                |
| 9. Signing Gate ---> [Audit Log (Tamper-evident Merkle Log)]                |
| 10.CI Runner <-----(SignResponse: Signature + Cert Chain)--- [Signing Gate]  |
+-----------------------------------------------------------------------------+
```

### Анатомія OIDC клеймів та рушій перевірки політик

Служба віддаленого підписання ніколи не повинна діяти як «сліпий криптографічний оракул», що підписує будь-який надісланий геш лише за наявності валідного підпису провайдера ідентичності. Отримавши запит, шлюз підпису запускає **рушій виконання політик** (англ. *Policy Enforcement Engine*).

![Анатомія OIDC JWT токену та оцінка умов у рушії політик підпису](/root/eng/sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/img/jwt-claims-policy-evaluation.svg)
*Структура клеймів OIDC токену та багаторівнева перевірка умов допуску в рушії політик перед зверненням до HSM.*

Токен OIDC містить набір незмінних криптографічно засвідчених тверджень (клеймів), які описують повний контекст виконання коду:

```json
{
  "iss": "https://token.actions.githubusercontent.com",
  "sub": "repo:acme-corp/firmware-core:ref:refs/tags/v2.4.0",
  "aud": "https://signing.internal.acme.net",
  "repository": "acme-corp/firmware-core",
  "repository_owner": "acme-corp",
  "ref": "refs/tags/v2.4.0",
  "ref_type": "tag",
  "actor": "release-engineer-dmitro",
  "sha": "4a2f8b91c0e3d5a78216390fbc4e7d2198a56214",
  "job_workflow_ref": "acme-corp/firmware-core/.github/workflows/release.yml@refs/tags/v2.4.0",
  "event_name": "push",
  "exp": 1724810400
}
```

Рушій політик шлюзу перевіряє суворе виконання наступних інваріантів безпеки:

1. **Верифікація криптографічного ланцюжка провайдера:** Шлюз завантажує відкриті ключі провайдера (JWKS) через захищений канал і перевіряє цифровий підпис JWT-токена.
2. **Перевірка цільової аудиторії (`aud`):** Значення `aud` зобов'язане точно збігатися з унікальним ідентифікатором шлюзу підпису. Це виключає атаку підміни токенів, отриманих для інших хмарних сервісів (наприклад, AWS чи GCP).
3. **Сегрегація репозиторіїв (`repository`):** Кожному апаратному ключу в HSM зіставляється білий список дозволених вихідних репозиторіїв. Тестовий репозиторій не може використати виробничий ключ підпису прошивок.
4. **Політика захищених релізних тегів (`ref` та `ref_type`):** Шлюз категорично блокує запити, що надійшли з довільних гілок розробки (`refs/heads/feature-xyz`) чи подій `pull_request`. Підпис дозволяється винятково для захищених семантичних тегів релізів, які відповідають строгому регулярному виразу:
   
   ```
   ^refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$
   ```

5. **Контроль незмінності воркфлоу (`job_workflow_ref`):** Рушій перевіряє, що збірка виконувалася саме за канонічним файлом інструкцій релізу (`release.yml`), зафіксованим у захищеній гілці, а не через тимчасово модифікований тестовий пайплайн.
6. **Захист від спуфінгу облікових записів (`actor` та події):** Додаткові правила можуть вимагати, щоб запуск релізу ініціювався лише уповноваженими обліковими записами або сервісними ботами релізу з обов'язковим проходженням процедури двоетапного схвалення (Dual-Approval).

Повний контракт інтерфейсу, структуру protobuf-повідомлень та JSON-схему правил докладно описано у довіднику: [протокол та RPC-контракт служби віддаленого підписання артефактів](root:sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/api-signing-service-rpc.md).

### Анатомія захищеного конверта та взаємодія з апаратним HSM

Фізична ізоляція криптографічних ключів забезпечується розміщенням апаратного модуля безпеки (HSM) у внутрішній демілітаризованій зоні корпоративної мережі, недоступній з публічного інтернету.

![Архітектура захищеного конверта та межа довіри віддаленого підпису](/root/eng/sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/img/remote-signing-envelope.svg)
*Архітектура захищеного конверта та межі довіри між недовіреним раннером, шлюзом контролю доступу та апаратним анклавом HSM.*

Взаємодія між компонентами системи відбувається за принципом багаторівневого захищеного конверта (англ. *Security Envelope*):

1. **Клієнтський рівень (Раннер):**
   * Обчислює `H = SHA-256(Artifact)`.
   * Формує структуру запиту `SignRequest(digest: H, key_id: "firmware-v2", token: JWT)`.
   * Встановлює mTLS-з'єднання з TLS 1.3 та шифронаборами на основі ефемерних ключів Діффі-Геллмана (ECDHE), що гарантує пряму секретність передачі (Forward Secrecy).

2. **Рівень шлюзу підпису (Signing Gateway):**
   * Термінує mTLS, перевіряє клієнтський сертифікат раннера.
   * Декодує OIDC токен, валідує його в рушії політик.
   * У разі позитивного вердикту транслює запит у стандартизований виклик стандарту **PKCS#11** (Cryptoki API).

3. **Апаратний рівень (HSM Enclave):**
   * Шлюз ініціалізує криптографічну сесію `C_SignInit(hSession, &mechanism, hKey)`, де `mechanism = CKM_ECDSA` або `CKM_RSA_PKCS_PSS`.
   * Передає 32 байти дайджесту у функцію `C_Sign(hSession, pDigest, 32, pSignature, &ulSigLen)`.
   * Апаратний криптопроцесор HSM, використовуючи некопійований закритий ключ із захищеної кремнієвої пам'яті, обчислює компоненти підпису `(r, s)`.
   * Результат повертається шлюзу, який пакує його у формат IEEE P1363 або DER, додає ланцюжок відкритих сертифікатів X.509 і фіксує подію в журналі аудиту.

Повну програмну реалізацію клієнтської утиліти на C та C++ з використанням OpenSSL API наведено у практичній вставці: [клієнт віддаленого підпису з mTLS та верифікацією OIDC токенів](root:sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/proj-remote-signer-client.md).

### Парадигма короткоживучих сертифікатів: Sigstore, Fulcio та Rekor

Альтернативою традиційній моделі з централізованим корпоративним HSM є підхід **безключового підписання** (англ. *Keyless Signing*), розроблений консорціумом OpenSSF у рамках проєкту **Sigstore**.

Замість збереження постійного закритого ключа в HSM, Sigstore повністю ліквідує концепцію довгоживучих ключів релізу:
1. **Генерація одноразового ключа:** Під час запуску збірки утиліта `cosign` у пам'яті раннера генерує нову ефемерну пару ключів ECDSA (P-256).
2. **Обмін токену на сертифікат (Fulcio):** Раннер відправляє свій відкритий ключ та OIDC-токен до центру сертифікації **Fulcio**. Fulcio перевіряє OIDC-токен і випускає цифровий сертифікат X.509 із терміном дії всього **10 хвилин**. У сертифікат як ім'я суб'єкта (Subject Alternative Name, SAN) записується розширення OIDC (наприклад, `https://github.com/acme-corp/app/.github/workflows/release.yml@refs/tags/v1.0.0`).
3. **Публікація в журнал прозорості (Rekor):** Раннер підписує артефакт ефемерним приватним ключем, після чого відправляє підпис, відкритий ключ та геш артефакту до публічного незмінного журналу **Rekor** (побудованого на базі криптографічного дерева Меркла).
4. **Знищення ключа:** Раннер безповоротно стирає закритий ключ з пам'яті.

```
+-----------------------------------------------------------------------------+
| Механізм валідації безключового підпису в Sigstore                          |
|                                                                             |
| 1. Як перевірити підпис, якщо сертифікат X.509 діє лише 10 хвилин?          |
|                                                                             |
| Клієнт перевірки (Verify):                                                  |
| ├── 1. Зчитує сертифікат X.509 та перевіряє його підпис від Fulcio Root CA  |
| ├── 2. Отримує криптографічний штамп часу (RFC 3161) або запис із Rekor     |
| ├── 3. Перевіряє математичний доказ включення (Inclusion Proof) у Merkle Log|
| └── 4. Інваріант: Якщо час запису в Rekor лежить у межах [NotBefore, NotAfter]|
|        сертифіката — підпис є беззаперечно чинним НАЗАВЖДИ.                 |
+-----------------------------------------------------------------------------+
```

Така схема розв'язує проблему відкликання сертифікатів: оскільки сертифікат стає недійсним уже через 10 хвилин після збірки, його не потрібно відкликати через важкі списки CRL чи протоколи OCSP. Криптографічний штамп часу у поєднанні з незмінним журналом прозорості забезпечує математичну доказовість факту підписання в момент дійсності сертифіката на десятиліття вперед.

Порівняльний аналіз архітектур на основі віддаленого HSM та екосистеми Sigstore наведено у вставці: [порівняльний аналіз моделей захисту підпису в CI/CD: від секретів раннера до короткоживучих сертифікатів](root:sf-security/pidpys-u-konveieri-bez-kliucha-v-konveieri/comp-keyless-signing-models.md).

### Підпис контейнерних образів та артефактів OCI

У хмарних та мікросервісних інфраструктурах основним форматом артефакту виступає образ контейнера (OCI Image). Підписання образу має суттєві відмінності від підпису звичайного бінарного файлу на диску.

Образ контейнера складається з масиву стиснених шарів файлової системи (tar.gz blobs), файлу конфігурації та маніфесту (Manifest JSON). Підпис накладається не на окремі гігабайтні шари, а на канонічний криптографічний дайджест дескриптора маніфесту:

```
Manifest Digest = SHA-256(Canonical_JSON(Manifest))
```

Специфікація OCI 1.1 та утиліта `cosign` зберігають створений підпис прямо всередині того самого реєстру контейнерів (Docker Hub, Harbor, GitHub Container Registry) поруч із цільовим образом. Підпис записується як окремий OCI-артефакт зі спеціальним тегом виду `sha256-<manifest-hash>.sig` або через механізм OCI Referrers API.

```
+-----------------------------------------------------------------------------+
| Розміщення підписів у реєстрі контейнерів OCI 1.1                           |
|                                                                             |
|  [OCI Container Registry]                                                   |
|  ├── Image Manifest:   app:v2.4.0 (Digest: sha256:4a2f8b...)               |
|  ├── Signature Object: sha256-4a2f8b...sig                                  |
|  │   ├── Payload:      SimpleSigning JSON (Subject: sha256:4a2f8b...)       |
|  │   ├── Signature:    ECDSA P-256 Raw Bytes                                |
|  │   └── Certificate:  X.509 Fulcio Cert (SAN: repo:acme/app:tag:v2.4.0)    |
|  └── Attestation:      sha256-4a2f8b...att (in-toto SLSA Provenance)        |
+-----------------------------------------------------------------------------+
```

Під час розгортання в кластері Kubernetes вхідний контролер допуску (Admission Controller — наприклад, Kyverno, Gatekeeper або Sigstore Policy Controller) перехоплює запит на створення Pod, запитує підпис із реєстру, перевіряє криптографічну відповідність відкритому ключу або OIDC-суб'єкту і блокує запуск контейнерів, зібраних поза авторизованим релізним конвеєром.

### Відтворюване збирання (Reproducible Builds) та атестації SLSA

Навіть найдосконаліший апаратний HSM не захищає систему, якщо скомпільований бінарний файл містить недетермінований артефакт або впроваджений бекдор. Тому сучасні стандарти безпеки ланцюжків постачання (зокрема **SLSA Рівень 3 та 4**) вимагають інтеграції механізму відтворюваного збирання (англ. *Reproducible Builds*).

Відтворювана збірка гарантує, що компіляція одного й того самого вихідного коду з однаковими параметрами дає бінарно ідентичний результат до останнього біта:
1. **Усунення часових міток:** Компілятори (GCC, Clang) за замовчуванням записують дату й час компіляції (`__DATE__`, `__TIME__`) у заголовки секцій. Для усунення цього використовується стандартизована змінна оточення `SOURCE_DATE_EPOCH`, яка фіксує часову мітку на момент останнього git-коміту.
2. **Нормалізація шляхів файлової системи:** Прапорець `-ffile-prefix-map` замінює абсолютні шляхи налагоджувальних символів DWARF на уніфіковані відносні імена.
3. **Детерміноване архівування:** Під час формування контейнерів або tar/zip-архівів порядок файлів впорядковується за алфавітом, а біти прав доступу та ідентифікатори власників (`uid`/`gid`) скидаються до нульових значень.

```
+-----------------------------------------------------------------------------+
| Подвійна перевірка збірки перед викликом віддаленого підпису                |
|                                                                             |
|  [Source Code Commit @ git tag v2.0.0]                                      |
|       ├──> [Ізольований Раннер A] ---> Hash A = SHA-256(Binary_A)           |
|       └──> [Ізольований Раннер B] ---> Hash B = SHA-256(Binary_B)           |
|                                                                             |
|  [Rebuild Verification Gate]:                                               |
|  If Hash A == Hash B:                                                       |
|       -> Відправка Hash A до Signing Service + HSM                          |
|  Else:                                                                      |
|       -> Аварійна зупинка конвеєра: невідтворювана збірка (Build Anomaly)    |
+-----------------------------------------------------------------------------+
```

Перед відправкою запиту на підпис релізу конвеєр може запускати незалежне паралельне перезбирання двома різними раннерами. Тільки в разі повного бінарного збігу гешів `Hash_A == Hash_B` формується атестація походження **in-toto** (SLSA Provenance Envelope) і передається на підпис до HSM.

### Незмінний аудит, виявлення аномалій та блокування атак

Останнім критичним компонентом архітектури є система незмінного аудиту (англ. *Tamper-Evident Audit Logging*). 

Оскільки в парадигмі віддаленого підпису закритий ключ залишається недосяжним для нападника, єдиною доступною атакою для скомпрометованого раннера є спроба **несанкціонованого підписання підробленого гешу** під час легітимного релізного запуску.

Для виявлення та запобігання таким атакам служба підпису впроваджує три рубежі оборони:

1. **Аудиторський ланцюжок гешів:** Кожен запит на підпис фіксується у спеціальному журналі, де кожен запис містить геш попереднього запису:
   
   ```
   Record[N] = { Timestamp, OIDC_Context, Digest, Signature, Hash(Record[N-1]) }
   ```
   
   Це унеможливлює непомітне видалення чи редагування записів про проведені підписи навіть у разі отримання адміністративного доступу до сервера шлюзу.

2. **Миттєве відкликання довіри без зміни ключів:** Якщо виявлено компрометацію репозиторію або вихідного коду, офіцер безпеки змінює конфігурацію політики на шлюзі підпису (блокує конкретний репозиторій або тег). Спроби підписати нові артефакти миттєво блокуються, при цьому всі раніше випущені легітимні підписи та сертифікати на мільйонах клієнтських пристроїв залишаються чинними і не потребують екстреної ротації кореневих ключів.

3. **Детекція аномалій та ліміти частоти (Rate Limiting):** Рушій шлюзу контролює аномальні спалахи активності. Якщо конвеєр проекту замість звичних одного-двох релізів на день починає генерувати десятки запитів на підпис за хвилину, шлюз автоматично заморожує операції для цього ключа та генерує сповіщення підвищеного пріоритету в системі моніторингу безпеки (SIEM).

> 🔧 **Навіщо це.**
> Архітектура віддаленого підписання на базі ефемерної ідентичності OIDC та апаратних HSM перетворює процес випуску програмного забезпечення з зони постійного ризику на детерміновану систему з нульовою довірою. Вона ліквідує загрозу викрадення довгоживучих ключів релізу, забезпечує суворий криптографічний контроль за тим, який саме код потрапляє до кінцевих користувачів, та відповідає найвищому рівню безпеки ланцюжка постачання SLSA Level 3.
