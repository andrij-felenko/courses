# 🔌 Порівняльний аналіз моделей підпису артефактів: від локальних секретів до безключового Sigstore

Забезпечення автентичності та цілісності програмного забезпечення під час автоматизованого випуску вимагає балансування між двома взаємовиключними вимогами: швидкістю неперервної доставки (CI/CD) та суворою ізоляцією приватних криптографічних ключів. Залежно від вимог до безпеки, регуляторного середовища та відкритості проекту індустрія використовує чотири основні архітектурні парадигми. Цей порівняльний аналіз розглядає внутрішній устрій, поверхню атаки, експлуатаційну складність та криптографічні гарантії кожної з моделей.

---

### Огляд чотирьох парадигм підписання

```
+-----------------------------------------------------------------------------+
| 1. Секрети в раннері      2. Віддалений HSM      3. Безключовий Sigstore    |
|                                                                             |
|    [CI Runner]               [CI Runner]               [CI Runner]          |
|    | (Ключ у RAM)            | (Лише SHA-256)          | (Ефемерний ключ)   |
|    v                         v                         v                    |
|  [OpenSSL Sign]          [Signing Gateway]         [Fulcio CA]              |
|                              |                         | (X.509 на 10 хв)   |
|                              v                         v                    |
|                          [Hardware HSM]            [Rekor Log]              |
+-----------------------------------------------------------------------------+
```

#### Модель 1: Статичний закритий ключ у секретах конвеєра (Runner Secrets)
Традиційний підхід, за якого приватний ключ (у форматі PKCS#12, PEM або зашифрованого блоку) передається в раннер через механізм зашифрованих змінних оточення (наприклад, GitHub Actions Secrets чи GitLab CI Variables). Раннер розшифровує ключ у тимчасовий файл або оперативну пам'ять і викликає локальну утиліту (`openssl`, `codesign`, `gpg`) для накладання підпису.

* **Переваги:** Мінімальні витрати на впровадження; відсутність потреби у додатковій інфраструктурі; повна автономність збірки.
* **Недоліки:** Критична вразливість до ексфільтрації ключа через шкідливі залежності, витоки логів, скомпрометовані pull requests або RCE у раннері. Будь-який злам раннера веде до повної компрометації сертифіката компанії.

#### Модель 2: Віддалений ізольований шлюз підпису (Remote Signing Gateway + HSM)
Раннер не має доступу до закритого ключа. Після компіляції артефакту клієнт у раннері рахує локальний дайджест (SHA-256) і передає його разом із контекстом збірки (OIDC JWT) до ізольованого внутрішнього мікросервісу через захищений RPC/mTLS. Сервіс підпису перевіряє право репозиторію на підпис і звертається до апаратного модуля безпеки (HSM / Cloud KMS) через PKCS#11 API для генерації цифрового підпису.

* **Переваги:** Ключ апаратно неможливо витягти з HSM; повний контроль політик (підпис лише валідних релізних тегів); аудит кожної спроби підпису.
* **Недоліки:** Необхідність розгортання та підтримки власної відмовостійкої інфраструктури шлюзів та апаратних HSM; мережеві затримки під час збірки.

#### Модель 3: Безключовий підпис на короткоживучих сертифікатах (Sigstore / Fulcio / Rekor)
Повна відмова від постійних закритих ключів. Раннер генерує одноразову пару ключів безпосередньо в пам'яті процесу збірки, відправляє свій OIDC-токен до короткоживучого центру сертифікації Fulcio й отримує тимчасовий сертифікат X.509 (термін дії — 10–15 хвилин), де суб'єктом виступає URL репозиторію та тег. Після накладання підпису відкритий ключ, підпис і сертифікат публікуються в незмінний публічний журнал прозорості Rekor, а локальний закритий ключ негайно стирається.

* **Переваги:** Повна відсутність операційного навантаження з управління, захисту та ротації ключів; публічна доказовість походження артефакту (SLSA Level 3); висока масштабованість.
* **Недоліки:** Залежність від публічної інфраструктури або необхідність розгортання приватного стека Sigstore (Scaffold); обов'язкова фіксація метаданих у журналі прозорості.

#### Модель 4: Офлайн-контур з ручним підтвердженням (Air-gapped / Dual-Control Signing)
Раннер CI/CD лише публікує скомпільований артефакт та його контрольні суми в захищений буфер. Фінальний підпис виконується на фізично ізольованій робочій станції або спеціальному терміналі за присутності двох уповноважених офіцерів безпеки (Dual-Control Ceremony) з використанням смарт-карт або апаратних ключів YubiKey/HSM.

* **Переваги:** Абсолютний захист від автоматизованих атак; повна незалежність від вразливостей CI/CD конвеєра.
* **Недоліки:** Повна зупинка автоматизації (затримка випуску релізу від годин до днів); висока вартість людських ресурсів; неможливість застосування для щоденних збірок.

### Порівняльна матриця архітектурних характеристик

| Критерій оцінки | 1. Секрети в раннері | 2. Віддалений HSM | 3. Безключовий Sigstore | 4. Офлайн-контур |
|---|---|---|---|---|
| **Ризик викрадення закритого ключа** | Критичний (100% експорт) | Нульовий (Non-exportable) | Нульовий (Ключ зникає за 10 хв) | Практично нульовий |
| **Рівень автоматизації CI/CD** | Повний (секунди) | Повний (мілісекунди) | Повний (1-2 секунди) | Відсутній (Ручний крок) |
| **Складність інфраструктури** | Нульова | Висока (HSM + Proxy) | Середня (SaaS або CA-стек) | Висока (Фізична зона) |
| **Ротація та відкликання ключів** | Ручна, болісна | Централізована в HSM | Автоматична (Не потрібна) | Ручна, регламентна |
| **Контроль релізних політик** | Слабкий (скрипт раннера) | Жорсткий (Policy Engine) | Жорсткий (OIDC Subject) | Людський фактор |
| **Незмінний аудит дій** | Логи CI (можуть зтерти) | Власний SIEM / HSM Log | Merkle Tree (Rekor Log) | Паперовий журнал / Відео |
| **Відповідність стандарту SLSA** | Рівень 1 | Рівень 3 | Рівень 3 | Рівень 4 |
| **Підтримка приватного коду** | Повна | Повна | Вимагає Private Sigstore | Повна |

### Аналіз відмов та моделей поведінки в аварійних ситуаціях

Кожна архітектурна модель по-різному реагує на збої мережі, компрометацію окремих компонентів та аварійне відновлення:

#### Поведінка під час компрометації раннера (Runner Compromise)
* **У моделі секретів:** Зловмисник отримує закритий ключ і може необмежено підписувати будь-які сторонні програми на власних серверах без відома жертви.
* **У моделі віддаленого HSM:** Зловмисник не має ключа. Він може спробувати відправити підроблений геш до шлюзу, проте шлюз відхилить запит, якщо збірка запущена не на захищеному тезі чи виконується в неавторизованому pull request.
* **У моделі Sigstore:** Зловмисник може отримати короткоживучий підпис лише в межах поточного запуску. Будь-який створений підпис миттєво з'явиться в публічному журналі Rekor, що дозволить системі моніторингу зафіксувати аномалію.

#### Стратегія відмовостійкості: Fail-Open проти Fail-Close
Для систем підпису коду єдиною допустимою стратегією є **суворий Fail-Close**:
1. Якщо шлюз підпису або апаратний HSM недоступні через мережевий збій, конвеєр зобов'язаний зупинити випуск релізу з помилкою.
2. Спроба створити «резервний шлях» із локальним аварійним ключем у раннері повністю нівелює захист і повертає систему до найгіршого сценарію Моделі 1.

#### Вибір моделі під тип проекту
* **Для відкритих проектів (Open Source) та публічних контейнерів:** Оптимальним вибором є **Модель 3 (Sigstore)** — вона безкоштовна, повністю автоматизована та забезпечує публічну довіру через журнал Rekor.
* **Для комерційних корпоративних систем, вбудованого ПЗ (firmware) та OTA-оновлень:** Стандартом є **Модель 2 (Віддалений HSM + OIDC шлюз)** — вона гарантує повну конфіденційність метаданих, апаратний захист криптографії та суворе виконання корпоративних політик.
