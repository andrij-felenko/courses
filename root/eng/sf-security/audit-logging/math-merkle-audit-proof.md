# 🧮 Математика криптографічних доказів у деревах аудиту

Криптографічне дерево Меркла (англ. *Merkle Tree*, запропоноване Ральфом Мерклом у 1979 році) забезпечує доказову цілісність великих масивів даних. У журналах аудиту воно виконує роль математичного фундаменту незмінності, дозволяючи незалежному аудиторові виконати дві операції з мінімальними обчислювальними й мережевими витратами:
1. **Доказ включення (Inclusion Proof / Audit Path):** Довести, що конкретний запис `L_i` дійсно присутній у журналі, маючи лише опублікований корінь дерева `Root` та `⌈log₂ N⌉` проміжних гешів.
2. **Доказ узгодженості (Consistency Proof):** Довести, що стан журналу розміром `M` є точним незмінним префіксом нового стану розміром `N` (де `M < N`), тобто жоден старий запис не був змінений, видалений чи переставлений місцями.

Математична строгість цієї моделі спирається на три фундаментальні властивості криптографічної геш-функції: стійкість до пошуку першого прообразу (незворотність), стійкість до пошуку другого прообразу та стійкість до колізій.

## 1. Розділення доменів та захист від колізій другого прообразу

При наївній побудові бінарного геш-дерева геш листка `H(d)` та геш внутрішнього вузла `H(l || r)` обчислюються однією й тією самою функцією `H`. Така однорідність створює критичну вразливість — атаку змішування типів (англ. *Type Confusion / Second Preimage Attack*).

Припустимо, що дерево має внутрішній вузол з лівим нащадком `H_left` і правим нащадком `H_right`. Обчислений геш цього внутрішнього вузла дорівнює:

```
H_parent = H(H_left || H_right)
```

Зловмисник може сформувати фальшивий запис первинних даних, чий двійковий вміст є точною конкатенацією двох 32-байтових гешів: `d_fake = H_left || H_right` (загальний розмір 64 байти). Якщо система обчислює геш листка як `H(d_fake)`, вона отримає:

```
H_leaf(d_fake) = H(d_fake) = H(H_left || H_right) = H_parent
```

У результаті зловмисник може підставити фальшивий запис `d_fake` замість цілого піддерева, і математична перевірка кореня буде успішною, оскільки корінь піддерева збігається з гешем листка.

Для усунення цієї вразливості стандарт RFC 6962 впроваджує строге **розділення доменів** (англ. *Domain Separation*) через однобайтові префікси:

```
H_leaf(d)     = SHA-256(0x00 || d)
H_node(l, r)  = SHA-256(0x01 || l || r)
```

Де:
- `0x00` — однобайтовий маркер листового вузла первинних даних;
- `0x01` — однобайтовий маркер проміжного внутрішнього вузла;
- `||` — операція конкатенації двійкових масивів байтів.

Оскільки перший байт аргументу геш-функції завжди різний (`0x00 ≠ 0x01`), множини прообразів для листків і внутрішніх вузлів ніколи не перетинаються. Навіть якщо зловмисник знайде дані `d`, для яких `d = l || r`, виходи геш-функції будуть різними:

```
SHA-256(0x00 || d) ≠ SHA-256(0x01 || l || r)
```

Це математично гарантує неможливість підміни структурних шарів дерева.

## 2. Математичний доказ складності доказу включення

Нехай журнал містить `N` записів аудиту `L_0, L_1, ..., L_{N-1}`. Побудуємо збалансоване бінарне дерево, де листками є значення `H_i = H_leaf(L_i)`.

Висота бінарного дерева `h` для кількості елементів `N` визначається як:

```
h = ⌈log₂ N⌉
```

Для перевірки включення запису `L_k` на глибині `h` аудитору не потрібні всі `N` листків. Достатньо отримати кортеж сестринських гешів на кожному рівні дерева від листка до кореня:

```
AuditPath(L_k) = { (S_0, dir_0), (S_1, dir_1), ..., (S_{h-1}, dir_{h-1}) }
```

Де `dir_j ∈ {LEFT, RIGHT}` вказує на положення сестринського вузла відносно поточного шляху.

### Покрокове обчислення кореня

Алгоритм верифікації ініціалізує проміжний акумулятор `C_0 = H_leaf(L_k)` і послідовно піднімається вгору до кореня:

```
C_{j+1} = H_node(S_j, C_j)    якщо dir_j = LEFT
C_{j+1} = H_node(C_j, S_j)    якщо dir_j = RIGHT
```

У фіналі аудитор порівнює результат `C_h` з опублікованим коренем `Root`:

```
C_h = Root      [доказ включення математично підтверджено]
```

### Обчислювальна та комунікаційна складність

Порівняємо пряму верифікацію повного сканування та доказ Меркла для журналу з 1 000 000 000 записів (SHA-256, розмір гешу 32 байти):

```
Кількість елементів N = 10⁹

Повний скан:
  Обсяг передачі даних = 10⁹ · 32 байти ≈ 32 ГБ
  Кількість операцій гешування = 10⁹ - 1

Доказ Меркла (Audit Path):
  Висота дерева h = ⌈log₂ (10⁹)⌉ = 30
  Обсяг передачі даних = 30 · 32 байти = 960 байтів
  Кількість операцій гешування = 30
```

Економія мережевого трафіку та часу перевірки становить понад 33 000 000 разів при збереженні абсолютної криптографічної строгості. Завдяки логарифмічній складності навіть клієнт на мобільному пристрої або вбудованому мікроконтролері здатний перевірити наявність власного чека в глобальній банку за кілька мілісекунд.

## 3. Математика доказу узгодженості (Consistency Proof)

Доказ узгодженості розв'язує фундаментальну задачу довіри: як клієнтові переконатися, що лог-сервер не веде дві паралельні історії (*Split-View Attack*) і не видалив жодного старого запису, коли розмір журналу зріс від `M` до `N` подій (`M < N`)?

Нехай `Root_M` — зафіксований раніше корінь дерева розміром `M`, а `Root_N` — свіжий корінь дерева розміром `N`.

Дерево розміром `M` розбивається на мінімальну сукупність повних піддерев степенів двійки, що покривають діапазон індексів `[0, M-1]`.

Нехай двійковий розклад числа `M` має вигляд:

```
M = 2^{k_1} + 2^{k_2} + ... + 2^{k_p}
де k_1 > k_2 > ... > k_p ≥ 0
```

Доказ консистентності надає геші коренів цих піддерев `R_1, R_2, ..., R_p`, а також сестринські вузли, необхідні для завершення побудови як старого дерева `Root_M`, так і нового дерева `Root_N`.

### Формальний інваріант консистентності

Якщо множина вузлів `R_1..R_p` дозволяє за схемою Меркла одночасно відновити:

```
Root_M = Combine_M(R_1, R_2, ..., R_p)
Root_N = Combine_N(R_1, R_2, ..., R_p, Leaves_{M..N-1})
```

Тоді з колізійної стійкості SHA-256 випливає теорема: **перші `M` листків у дереві `N` ідентичні листкам дерева `M` у точно такому самому порядку**. Жоден історичний запис не був замінений, переставлений чи пропущений.

## 4. Числовий приклад обчислення та верифікації

Розглянемо журнал із 4 записів `L_0, L_1, L_2, L_3`. Потрібно довести включення запису `L_2` у дерево з відомим коренем `Root`.

```
Листки (prefixed):
H_0 = SHA-256(0x00 || L_0)
H_1 = SHA-256(0x00 || L_1)
H_2 = SHA-256(0x00 || L_2)
H_3 = SHA-256(0x00 || L_3)

Проміжні вузли:
H_01 = SHA-256(0x01 || H_0 || H_1)
H_23 = SHA-256(0x01 || H_2 || H_3)

Корінь дерева:
Root = SHA-256(0x01 || H_01 || H_23)
```

Аудитор отримує доказ включення для `L_2`: `AuditPath = { (H_3, RIGHT), (H_01, LEFT) }`.

Покрокова перевірка аудитора:

```
C_0 = SHA-256(0x00 || L_2)                     [обчислення гешу цільового запису]
C_1 = SHA-256(0x01 || C_0 || H_3)              [поєднання з сестрою праворуч, dir=RIGHT]
    = SHA-256(0x01 || H_2 || H_3)              [тотожність: C_0 дорівнює H_2]
    = H_23                                     [знайдено проміжний вузол H_23]
C_2 = SHA-256(0x01 || H_01 || C_1)             [поєднання з сестрою ліворуч, dir=LEFT]
    = SHA-256(0x01 || H_01 || H_23)            [тотожність: C_1 дорівнює H_23]
    = Root                                     [обчислений корінь точно збігся з Root]
```

Збіг `C_2 = Root` є математично неспростовним доказом того, що `L_2` перебуває на позиції з індексом 2 у зафіксованому стані аудиту. Будь-яка зміна хоча б одного байта в `L_2` змінить `C_0`, що лавиноподібно змінить `C_1` та `C_2`, унеможлививши збіг із `Root`.

## 5. Теоретико-складносний аналіз стійкості до колізій (Birthday Bound)

Безпека дерева Меркла повністю залежить від колізійної стійкості базової геш-функції. Відповідно до парадоксу днів народження (*Birthday Attack*), для геш-функції з довжиною виходу `n` бітів ймовірність знаходження колізії досягає 50% після обчислення приблизно `2^{n/2}` гешів.

Для стандарту SHA-256 (`n = 256`):
- Простір виходів становить `2^{256} ≈ 1.15 · 10^{77}` можливих значень.
- Складність пошуку колізії становить `2^{128} ≈ 3.4 · 10^{38}` операцій гешування.
- Навіть якби вся обчислювальна потужність людства обчислювала мільярд гешів на секунду, для знаходження колізії знадобилися б трильйони років.

Це доводить, що заміна будь-якого вузла в дереві Меркла без зміни кореня є обчислювально нездійсненною задачею для сучасних комп'ютерів.

## 6. Алгоритм декомпозиції для доказу консистентності (RFC 6962 §2.1.2)

Формальний алгоритм перевірки узгодженості двох станів дерева розміром `M` та `N` (`M < N`) виконується за таким рекурсивним правилом:

1. Нехай `k` — найбільший степінь двійки, строго менший за `M` (`k = 2^{\lfloor \log_2(M-1) floor}`).
2. Якщо `M = k`, ліве піддерево розміру `M` повністю заповнене і є лівим нащадком як у старому дереві, так і в новому дереві. Аудитор бере корінь цього піддерева як перший елемент доказу і рекурсивно доводить консистентність залишку `N - k` у правому піддереві.
3. Якщо `M < k`, старе дерево повністю міститься всередині лівого піддерева нового стану. Алгоритм рекурсивно спускається в ліве піддерево розміром `k` і продовжує перевірку.

Така бітова декомпозиція гарантує, що розмір доказу консистентності ніколи не перевищує `2 · ⌈log₂ N⌉` гешів, а час верифікації становить частки мілісекунди.
