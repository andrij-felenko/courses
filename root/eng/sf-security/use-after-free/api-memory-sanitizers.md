# 📋 Інтерфейси пам'яті: AddressSanitizer, HWASan та керування ARM MTE

Специфікація програмних інтерфейсів, компіляторних прапорців та системних викликів ядра для діагностики, моніторингу та апаратного придушення вразливостей використання після звільнення (Use-After-Free).

## 1. Програмний інтерфейс AddressSanitizer (C/C++ API)

Заголовний файл: `<sanitizer/asan_interface.h>`

Бібліотека часу виконання AddressSanitizer (`libclang_rt.asan` або `libasan`) надає розробникам низькорівневий інтерфейс для ручного керування станом тіньової пам'яті. Це критично необхідно під час створення власних розподільників пам'яті (пулів об'єктів, арена-алокаторів, кільцевих буферів або кастомних збирачів сміття), які виділяють великі системні блоки через `mmap()`, але самостійно управляють життєвим циклом дрібних об'єктів усередині них. Без явного виклику API санітайзера такі внутрішні UAF-помилки залишалися б непоміченими, оскільки для стандартного рантайму вся арена виглядає як один великий активний блок.

### Функції ручного керування отруєнням пам'яті

| Сигнатура | Призначення |
|---|---|
| `void __asan_poison_memory_region(void const volatile *addr, size_t size);` | Позначає регіон пам'яті як заборонений для читання та запису (записує червоні або отруєні байти в тіньову пам'ять). |
| `void __asan_unpoison_memory_region(void const volatile *addr, size_t size);` | Знімає заборону доступу, повертаючи тіньові байти у стан `0x00` (валідний доступ). |
| `int __asan_address_is_poisoned(void const volatile *addr);` | Повертає `1`, якщо адреса вказує на отруєну/звільнену ділянку, і `0`, якщо адреса доступна для звернення. |
| `int __asan_region_is_poisoned(void const volatile *addr, size_t size);` | Повертає адресу першого отруєного байта в межах діапазону або `NULL`, якщо весь діапазон безпечний. |
| `void __asan_describe_address(void *addr);` | Друкує в `stderr` повну діагностичну інформацію про адресу (належність до купи, стека, глобальних змінних, стек виділення та звільнення). |

#### Механіка роботи функцій отруєння

Функція `__asan_poison_memory_region` транслює переданий діапазон віртуальних адрес у відповідні байти тіньового масиву за формулою `(Addr >> 3) + Offset`. Якщо розмір `size` не є кратним 8 байтам, функція виконує побайтове маскування: для останнього неповного 8-байтного слова встановлюється значення від `0x01` до `0x07`, що дозволяє звертатися лише до перших `size % 8` байтів, блокуючи доступ до решти. Повне отруєння діапазону записує в тіньову пам'ять байт `0xFF` (для користувацьких зон) або `0xFD` (для звільненої купи).

Функція `__asan_unpoison_memory_region` скидає відповідні тіньові байти в нуль (`0x00`), сигналізуючи компіляторним перевіркам, що всі 8 байтів кожного слова знову легітимно доступні для читання та запису.

### Механізм перехоплення системних функцій (Interceptors)

Рантайм AddressSanitizer реалізує техніку динамічного перехоплення символів (*interposition / hooking*). Під час завантаження динамічного компонувальника (`ld.so`) бібліотека `libasan` підміняє стандартні функції керування пам'яттю бібліотеки `libc`:

- `malloc(size)`: перехоплювач виділяє запитаний розмір разом із додатковими червоними зонами ліворуч і праворуч (`kAsanHeapLeftRedzoneMagic`), записує стек виклику виділення у внутрішню таблицю дескрипторів та ініціалізує тіньову пам'ять значеннями `0x00`.
- `free(ptr)`: перехоплювач вилучає чанк, отруює всю пам'ять об'єкта байтом `0xFD`, зберігає поточний стек виклику звільнення та переміщує блок у локальний потік карантину.
- `realloc(ptr, new_size)`: перехоплювач виділяє новий блок, копіює дані, а старий блок негайно отруює та відправляє в карантин.
- Рядкові та буферні функції (`memcpy`, `memmove`, `strcpy`, `strlen`): перехоплювачі перевіряють стан тіньової пам'яті для кожного зчитуваного та записуваного байта, запобігаючи несанкціонованому копіюванню даних зі звільнених або чужих блоків.

### Конфігурація середовища виконання (`ASAN_OPTIONS`)

Рантайм AddressSanitizer зчитує змінну оточення `ASAN_OPTIONS` під час запуску процесу до виклику функції `main()`. Це дозволяє налаштовувати глибину перевірки, обсяг карантину та поведінку аварійного завершення без перекомпіляції коду.

Синтаксис рядка конфігурації: `ASAN_OPTIONS="параметр1=значення1:параметр2=значення2"`

| Параметр | За замовчуванням | Опис і вплив на виявлення UAF |
|---|---|---|
| `quarantine_size_mb` | `256` (64-біт) / `32` (32-біт) | Розмір глобального буфера карантину (у мегабайтах). Звільнені чанки пам'яті утримуються в карантині і не повертаються застосунку доти, доки сумарний обсяг звільненої пам'яті не перевищить цей ліміт. Збільшення значення до `1024` чи `2048` подовжує час життя отруєного стану і гарантує виявлення навіть дуже віддалених у часі UAF-помилок. |
| `max_quarantine_size_mb` | `1024` | Абсолютна верхня межа пам'яті карантину під час інтенсивних сплесків виділення та звільнення блоків. |
| `redzone` | `16` (байти) | Мінімальний розмір захисної червоної зони навколо кожного виділеного на купі чанка. Може динамічно збільшуватися рантаймом до `2048` байтів для великих об'єктів. |
| `max_redzone` | `2048` | Максимальний розмір червоної зони між суміжними об'єктами купи. |
| `detect_stack_use_after_return` | `0` | Увімкнення експериментального захисту від використання локальних змінних стека після повернення з функції (UAR). Рантайм замінює реальний стек віртуальними фейковими фреймами в купі. |
| `halt_on_error` | `1` | Якщо встановлено в `1`, процес негайно друкує звіт про помилку і завершує виконання через `exit(1)`. При значенні `0` рантайм намагається продовжити виконання (не рекомендується для виправлення вразливостей). |
| `malloc_context_size` | `30` | Кількість кадрів трасування стека (*stack frames*), які зберігаються для кожної операції `malloc()` та `free()`. Високе значення полегшує діагностику, але збільшує накладні витрати на пам'ять. |

#### Алгоритм витіснення з карантину

Карантин ASan організований як дворівнева структура: кожен потік має локальний карантинний буфер фіксованого розміру (зазвичай 1 МБ), що зменшує міжпотокову конкуренцію за глобальні м'ютекси. Коли локальний буфер заповнюється, потік під монопольним блокуванням переносить партію звільнених блоків у глобальний кільцевий FIFO-масив. Якщо сумарний обсяг глобального карантину перевищує `quarantine_size_mb`, найстаріші блоки витісняються: рантайм знімає отруєння з їхніх тіньових байтів і повертає пам'ять системному алокатору для повторного виділення.

## 2. Прапорці компіляторів Clang та GCC

Компілятори LLVM Clang та GCC інтегрують механізми перевірки пам'яті безпосередньо у проміжне представлення коду (LLVM IR / GIMPLE).

| Прапорець компіляції | Цільова архітектура | Механізм і накладні витрати |
|---|---|---|
| `-fsanitize=address` | x86, x86-64, ARM, AArch64 | Класичний AddressSanitizer. Компілятор інструментує кожне читання/запис інструкціями зсуву та перевірки тіньового байта в масиві `[App >> 3 + Base]`. Накладні витрати: споживання RAM зростає на 200–300%, уповільнення CPU складає 70–100%. |
| `-fsanitize=hwaddress` | AArch64 (ARM64) | HWAddressSanitizer (HWASan). Використовує апаратне ігнорування верхнього байта вказівника (TBI). Тіньова пам'ять організована у масштабі 1:16 (1 байт тіні зберігає 8-бітний тег для 16 байтів ОЗП). Накладні витрати: RAM +10–20%, CPU +20–40%. |
| `-fsanitize=memtag` | AArch64 (ARMv8.5-A+) | Апаратне тегування пам'яті ARM MTE. Компілятор генерує нативні асемблерні інструкції керування тегами (`IRG`, `STG`, `LDG`). Накладні витрати: RAM +3% (Tag RAM), CPU +1–3%. |
| `-fsanitize-address-outline-instrumentation` | Усі платформи | Замість інлайн-вставки перевірочних інструкцій перед кожним розіменуванням генерує виклики службових функцій `__asan_load8()` / `__asan_store8()`. Зменшує розмір бінарного файлу за рахунок додаткових накладних витрат на виклики функцій. |
| `-fno-omit-frame-pointer` | Усі платформи | Примушує компілятор зберігати покажчик кадру (`RBP` на x86-64 або `X29` на ARM64) у кожній функції. Обов'язковий прапорець для генерації точних стеків викликів у звітах про аварії UAF. |

### Асемблерні інструкції ARMv8.5-A MTE

Під час компіляції з прапорцем `-fsanitize=memtag` компілятор Clang використовує спеціальний набір інструкцій процесора для маніпуляції апаратними тегами:

- `IRG Xd, Xn` (*Insert Random Tag*): Генерує випадковий 4-бітний тег, що не входить до маски виключення, і записує його у біти `[59:56]` регістра `Xd`.
- `ADDG Xd, Xn, #imm1, #imm2` (*Add with Tag*): Додає числове зміщення та змінює значення тегу на константу.
- `STG Xt, [Xn]` (*Store Allocation Tag*): Записує 4-бітний тег із верхнього байта регістра `Xt` у фізичну Tag RAM для 16-байтної гранули за адресою `Xn`.
- `ST2G Xt, [Xn]` (*Store Allocation Tag for 2 granules*): Записує тег одночасно у дві послідовні гранули (32 байти пам'яті).
- `LDG Xt, [Xn]` (*Load Allocation Tag*): Зчитує фізичний тег гранули з Tag RAM і розміщує його у бітах `[59:56]` регістра `Xt`.

## 3. Системний інтерфейс ядра Linux для керування ARM MTE

Заголовні файли ядра Linux: `<sys/prctl.h>`, `<linux/prctl.h>`, `<sys/mman.h>`, `<signal.h>`, `<sys/ptrace.h>`

Ядро Linux (починаючи з версії 5.10) надає системний інтерфейс для конфігурації апаратного тегування адрес процесу користувача через системний виклик `prctl()`.

### Системний виклик `prctl()` для конфігурації тегування адрес

:::tabs
```c
#include <sys/prctl.h>

int prctl(int option, unsigned long arg2, unsigned long arg3, unsigned long arg4, unsigned long arg5);
```
```cpp
#include <sys/prctl.h>

extern "C" int prctl(int option, unsigned long arg2, unsigned long arg3, unsigned long arg4, unsigned long arg5);
```
:::

#### Керуючі опції та бітові маски

:::tabs
```c
#include <sys/prctl.h>
#include <stdio.h>

/* Увімкнення синхронного режиму MTE для поточного процесу */
unsigned long flags = PR_TAGGED_ADDR_ENABLE | PR_MTE_TCF_SYNC | (0 << PR_MTE_TAG_SHIFT);
if (prctl(PR_SET_TAGGED_ADDR_CTRL, flags, 0, 0, 0) != 0) {
    perror("Помилка активації ARM MTE");
}
```
```cpp
#include <sys/prctl.h>
#include <iostream>
#include <system_error>

// Увімкнення синхронного режиму MTE в ідіоматичному C++
const unsigned long flags = PR_TAGGED_ADDR_ENABLE | PR_MTE_TCF_SYNC | (0 << PR_MTE_TAG_SHIFT);
if (::prctl(PR_SET_TAGGED_ADDR_CTRL, flags, 0, 0, 0) != 0) {
    throw std::system_error(errno, std::generic_category(), "Помилка активації ARM MTE");
}
```
:::

| Константа прапорця | Числове значення | Призначення та поведінка |
|---|---|---|
| `PR_SET_TAGGED_ADDR_CTRL` | `55` | Команда `prctl()` для встановлення режиму керування тегованими адресами для поточного потоку/процесу. |
| `PR_GET_TAGGED_ADDR_CTRL` | `56` | Зчитування поточної конфігураційної маски MTE процесу. Повертає бітову маску активних прапорців. |
| `PR_TAGGED_ADDR_ENABLE` | `(1UL << 0)` | Дозволяє ядру операційної системи приймати вказівники з ненульовими верхніми байтами (TBI) у системних викликах (`read()`, `write()`, `ioctl()`). Без цього прапорця системні виклики з тегованими адресами повертають помилку `EFAULT`. |
| `PR_MTE_TCF_NONE` | `(0UL << 1)` | Перевірку апаратних тегів вимкнено (TBI дозволено, але невідповідність тегів ігнорується процесором). |
| `PR_MTE_TCF_SYNC` | `(1UL << 1)` | **Синхронний режим перевірки.** При розіменуванні вказівника з невідповідним тегом процесор негайно зупиняє виконання на поточній інструкції, викликаючи виняток синхронної помилки даних (*Data Abort*). Ядро формує сигнал `SIGSEGV` із кодом `SEGV_MTESERR`. |
| `PR_MTE_TCF_ASYNC` | `(2UL << 1)` | **Асинхронний режим перевірки.** При невідповідності тегу процесор встановлює внутрішній біт збою в системному регістрі `TFSRE0_EL1`, дозволяючи коду виконуватися далі. Сигнал `SIGSEGV` генерується ядром пізніше — під час виходу із системного виклику або перемикання контексту. Накладні витрати на швидкодію мінімальні (~1%). |
| `PR_MTE_TAG_MASK` | `(0xffffUL << 3)` | 16-бітна маска виключення тегів. Дозволяє заборонити інструкції `IRG` генерувати конкретні значення тегів (наприклад, нульовий тег для сумісності з нетегованим кодом). |

### Виділення тегованої пам'яті через `mmap()`

Щоб сторінки віртуальної пам'яті підтримували зберігання фізичних тегів у Tag RAM, процес повинен запросити їх із прапорцем захисту `PROT_MTE`:

:::tabs
```c
#include <sys/mman.h>
#include <stdio.h>

void *ptr = mmap(NULL, 65536, PROT_READ | PROT_WRITE | PROT_MTE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (ptr == MAP_FAILED) {
    perror("mmap з підтримкою PROT_MTE зазнав невдачі");
}
```
```cpp
#include <sys/mman.h>
#include <iostream>
#include <span>
#include <cstddef>
#include <system_error>

void* raw_ptr = ::mmap(nullptr, 65536, PROT_READ | PROT_WRITE | PROT_MTE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (raw_ptr == MAP_FAILED) {
    throw std::system_error(errno, std::generic_category(), "mmap з PROT_MTE зазнав невдачі");
}
std::span<std::byte> mte_buffer(static_cast<std::byte*>(raw_ptr), 65536);
```
:::

Якщо прапорець `PROT_MTE` не вказано, ядро виділяє звичайні сторінки без ініціалізації Tag RAM. Виконання інструкцій `STG` над такою пам'яттю призведе до генерації винятку відмови сторінки або апаратного збою шини. Під час обробки сторінкового переривання ядро Linux виділяє 128 байтів фізичної Tag RAM на кожні 4 КБ фізичного фрейму пам'яті, забезпечуючи рівно 4 біти тегу на кожні 16 байтів даних.

### Інтерфейс відлагодження ptrace для аналізу тегів

Налагоджувачі (GDB, LLDB) взаємодіють з тегами MTE за допомогою спеціальних команд `ptrace()`:
- `PTRACE_PEEKMTETAGS`: дозволяє зчитувати масив фізичних тегів пам'яті за вказаною адресою цільового процесу без виконання інструкцій `LDG`.
- `PTRACE_POKEMTETAGS`: записує нові теги у пам'ять процесу, що налагоджується, дозволяючи встановлювати точки спостереження за модифікацією тегів.

Під час генерації аварійного дампу пам'яті (*core dump*) ядро операційної системи Linux автоматично додає спеціальну секцію ELF-нотаток `NT_ARM_TAGGED_ADDR_CTRL` та `NT_ARM_MTE_TAGS`, що зберігає точний знімок усіх тегів гранул пам'яті на момент збою процесу.

### Обробка сигналів аварійного завершення (`siginfo_t`)

Коли ядро перехоплює порушення MTE, воно надсилає процесу сигнал `SIGSEGV`. Для отримання точної діагностики програма може зареєструвати розширений обробник через `sigaction()` з прапорцем `SA_SIGINFO`:

:::tabs
```c
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>

void mte_signal_handler(int sig, siginfo_t *info, void *ucontext) {
    if (sig == SIGSEGV) {
        if (info->si_code == SEGV_MTESERR) {
            printf("[!] MTE Synchronous Fault за адресою: %p\n", info->si_addr);
            printf("[!] Зафіксовано невідповідність тегу (Use-After-Free або Buffer Overflow)!\n");
        } else if (info->si_code == SEGV_MTEAERR) {
            printf("[!] MTE Asynchronous Fault: адреса недоступна в асинхронному режимі.\n");
        }
        exit(1);
    }
}
```
```cpp
#include <signal.h>
#include <iostream>
#include <cstdlib>

void mte_cpp_signal_handler(int sig, siginfo_t *info, void *ucontext) {
    if (sig == SIGSEGV) {
        if (info->si_code == SEGV_MTESERR) {
            std::cerr << "[!] MTE Synchronous Fault за адресою: " << info->si_addr << "\n"
                      << "[!] Зафіксовано невідповідність тегу (Use-After-Free або Buffer Overflow)!\n";
        } else if (info->si_code == SEGV_MTEAERR) {
            std::cerr << "[!] MTE Asynchronous Fault: адреса недоступна в асинхронному режимі.\n";
        }
        std::exit(1);
    }
}
```

#### Структура кодів `si_code` для MTE

| Код помилки | Числове значення | Семантика порушення пам'яті |
|---|---|---|
| `SEGV_MTESERR` | `8` | **Synchronous Tag Check Fault.** Точна адреса збою записана у полі `info->si_addr`. Верхні біти `si_addr` містять некоректний логічний тег вказівника, що дозволяє порівняти його з фізичним тегом у Tag RAM. |
| `SEGV_MTEAERR` | `9` | **Asynchronous Tag Check Fault.** Збій зафіксовано асинхронно. Поле `info->si_addr` містить `0` або невизначене значення, оскільки точна адреса інструкції, що виконала читання/запис, не зберігається в конвеєрі процесора. |
