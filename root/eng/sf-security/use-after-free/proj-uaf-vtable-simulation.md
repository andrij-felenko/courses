# ⚙️ Практикум: анатомія Use-After-Free, підміна vtable та виявлення через ASan

Коли динамічно виділений об'єкт звільняється за допомогою виклику `free()` або `delete`, а вказівник на нього продовжує зберігатися в пам'яті застосунку, виникає вразливість часової безпеки пам'яті — використання після звільнення (Use-After-Free). Якщо системний алокатор згодом перевикористовує цей самий блок пам'яті під новий об'єкт іншого типу, зловмисник отримує змогу маніпулювати внутрішніми даними первинного об'єкта через новий інтерфейс. Якщо цими даними є вказівник на функцію або покажчик на таблицю віртуальних методів (`vtable`), звернення через завислий вказівник призводить до несанкціонованого перехоплення потоку виконання програми (Control Flow Hijacking).

## 1. Концепція експерименту: від звільнення до перехоплення потоку керування

У цьому лабораторному практикумі моделюється класичний сценарій експлуатації вразливості типу «плутанина типів» (Type Confusion) на основі повторного використання пам'яті в купі.

### Архітектура модельованих структур

Розглянемо дві структури даних, що мають однаковий розмірний клас в алокаторі пам'яті (16 байтів на 64-бітній платформі):

1. **Цільовий об'єкт `AuthSession`:**
   - Поле 1 (зміщення +0, 8 байтів): вказівник на функцію валідації прав `int (*check_auth)(int)`.
   - Поле 2 (зміщення +8, 4 байти): числовий ідентифікатор користувача `user_id`.
   - Поле 3 (зміщення +12, 4 байти): прапорець активності сесії `is_active`.
2. **Об'єкт підміни `UserComment`:**
   - Поле 1 (зміщення +0, 8 байтів): довільне числове поле `raw_field1` (у реальній системі — дані повідомлення або завантажений бінарний буфер).
   - Поле 2 (зміщення +8, 8 байтів): додаткове корисне навантаження `raw_field2`.

### Послідовність фаз моделювання

1. **Фаза 1 (Легітимне виділення):** Застосунок створює об'єкт `AuthSession` через `malloc()` або `new`. Алокатор повертає адресу в купі `0x6000`. Поле `check_auth` ініціалізується адресою стандартної функції безпеки `normal_auth()`. Виклик через вказівник підтверджує нормальну роботу.
2. **Фаза 2 (Створення завислого вказівника):** Викликається функція звільнення пам'яті `free(session)` або `delete session`. Блок `0x6000` повертається у список вільних чанків алокатора (`tcache_entry`). Проте локальна змінна `session` навмисно не обнуляється, перетворюючись на завислий вказівник (*dangling pointer*).
3. **Фаза 3 (Детерміноване перевикористання ділянки):** Застосунок виділяє об'єкт `UserComment` того самого розміру (16 байтів). Завдяки стековій організації списків LIFO у сучасних алокаторах (`ptmalloc`), алокатор миттєво віддає ту саму адресу `0x6000` новому об'єкту `comment`.
4. **Фаза 4 (Впровадження корисного навантаження):** Застосунок записує в поле `comment->raw_field1` адресу привілейованої функції `root_escalation()`. Оскільки зміщення обох полів збігаються (+0 байтів), вміст пам'яті за адресою `0x6000` змінюється.
5. **Фаза 5 (Активація UAF):** Програма звертається до старого інтерфейсу через завислий вказівник: `session->check_auth(session->user_id)`. Процесор зчитує змінений перший 8-байтний покажчик і виконує непрямий перехід на функцію підвищення привілеїв `root_escalation()`.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

/* Нормальна функція перевірки прав */
static int normal_auth(int user_id) {
    printf("[+] Нормальна перевірка: доступ для UID %d обмежено стандартними правами.\n", user_id);
    return 0;
}

/* Привілейована функція (симуляція адміністративного доступу / ROP-гаджета) */
static int root_escalation(int user_id) {
    (void)user_id;
    printf("[!] КРИТИЧНО: Викликано root_escalation! Права підвищено до суперкористувача!\n");
    return 1;
}

/* Структура легітимної сесії (розмір 16 байтів на x86-64) */
typedef struct {
    int (*check_auth)(int);
    int user_id;
    int is_active;
} AuthSession;

/* Структура довільного контенту того самого розмірного класу */
typedef struct {
    uintptr_t raw_field1;
    uintptr_t raw_field2;
} UserComment;

int main(void) {
    printf("=== Симуляція Use-After-Free у мові C ===\n\n");

    /* 1. Виділення первинного об'єкта сесії */
    AuthSession *session = (AuthSession *)malloc(sizeof(AuthSession));
    if (!session) return 1;

    session->user_id = 1000;
    session->is_active = 1;
    session->check_auth = normal_auth;

    printf("[1] Створено сесію за адресою: %p (UID: %d)\n", (void *)session, session->user_id);
    session->check_auth(session->user_id);

    /* 2. Звільнення об'єкта, створення завислого вказівника (Dangling Pointer) */
    printf("\n[2] Виклик free(session) без обнулення вказівника...\n");
    free(session);
    /* session залишається незмінним і все ще вказує на звільнену ділянку пам'яті */

    /* 3. Виділення об'єкта коментаря того самого розміру */
    printf("\n[3] Виділення нового об'єкта UserComment...\n");
    UserComment *comment = (UserComment *)malloc(sizeof(UserComment));
    if (!comment) return 1;

    printf("[3] Новий об'єкт отримав адресу: %p\n", (void *)comment);

    /* Підміна поля check_auth адресою привілейованої функції */
    comment->raw_field1 = (uintptr_t)root_escalation;
    comment->raw_field2 = 0x1337;

    /* 4. Розіменування завислого вказівника (Use-After-Free) */
    printf("\n[4] Виклик session->check_auth() через завислий вказівник...\n");
    session->check_auth(session->user_id);

    free(comment);
    return 0;
}
```

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <cstdint>

/* Базовий поліморфний інтерфейс сервісу */
class IAuthHandler {
public:
    virtual ~IAuthHandler() = default;
    virtual void verify_token(int user_id) = 0;
};

class StandardAuth : public IAuthHandler {
public:
    void verify_token(int user_id) override {
        std::cout << "[+] Стандартна авторизація: користувача " << user_id << " підтверджено як гостя.\n";
    }
};

/* Клас імітації шкідливого навантаження з сумісною структурою vtable */
class ExploitPayload : public IAuthHandler {
public:
    void verify_token(int user_id) override {
        std::cout << "[!] ПЕРЕХОПЛЕННЯ VTABLE: Виконано привілейований метод для UID " << user_id << "!\n";
    }
};

/* Безпечна реалізація з використанням RAII та розумних вказівників */
void demonstrate_safe_cpp_lifecycle() {
    std::cout << "\n=== Безпечна C++ альтернатива (std::shared_ptr + std::weak_ptr) ===\n";

    std::weak_ptr<IAuthHandler> weak_session;

    {
        auto shared_session = std::make_shared<StandardAuth>();
        weak_session = shared_session;

        if (auto locked = weak_session.lock()) {
            locked->verify_token(1001);
        }
    } // shared_session знищується тут, пам'ять коректно вивільняється

    // Спроба використати ресурс після завершення його життєвого циклу
    if (auto locked = weak_session.lock()) {
        locked->verify_token(1001);
    } else {
        std::cout << "[+] weak_ptr успішно запобіг UAF: ресурс своєчасно вивільнено, доступ заблоковано.\n";
    }
}

int main() {
    std::cout << "=== Симуляція Use-After-Free у C++ із віртуальними таблицями ===\n\n";

    // 1. Створення об'єкта через сирий вказівник (небезпечний підхід)
    IAuthHandler* volatile dangling_ptr = new StandardAuth();
    std::cout << "[1] Створено StandardAuth за адресою: " << dangling_ptr << "\n";
    dangling_ptr->verify_token(42);

    // 2. Звільнення об'єкта
    delete dangling_ptr;
    std::cout << "[2] Об'єкт видалено через delete. Вказівник став завислим.\n";

    // 3. Перевикористання пам'яті новим об'єктом іншого підтипу
    IAuthHandler* payload = new ExploitPayload();
    std::cout << "[3] Створено ExploitPayload за адресою: " << payload << "\n";

    // 4. Розіменування старого вказівника (виклик віртуального методу через підмінену vtable)
    std::cout << "[4] Звернення через завислий вказівник dangling_ptr->verify_token():\n";
    dangling_ptr->verify_token(42);

    delete payload;

    // Демонстрація ідіоматичного безпечного керування ресурсами
    demonstrate_safe_cpp_lifecycle();

    return 0;
}
```

### Асемблерний аналіз непрямого виклику на x86-64

Розглянемо, як процесор транслює виклик `session->check_auth(session->user_id)` у машинний код:

```nasm
; RDI містить адресу session (0x6000)
mov rax, qword ptr [rdi]        ; RAX = зчитує перші 8 байтів пам'яті за адресою 0x6000
mov esi, dword ptr [rdi + 8]    ; ESI = перший аргумент функції (user_id зі зміщенням +8)
call rax                        ; Непрямий перехід за адресою в регістрі RAX
```

У нормальному стані за адресою `0x6000` записано адресу функції `normal_auth`. Проте після перевиділення об'єкта `comment` за тією ж адресою `0x6000` значення в комірці стає рівним адресі `root_escalation`. Процесор завантажує це число в регістр `RAX` і виконує перехід інструкцією `call rax`, не маючи змоги визначити, чи відповідає поточний вміст пам'яті початковому типу `AuthSession`.

## 2. Діагностика через AddressSanitizer: детальний аналіз дампу

Для динамічного виявлення часових порушень пам'яті компілюємо код із увімкненим інструментуванням санітайзера:

```bash
clang -fsanitize=address -g -O1 proj_uaf.c -o proj_uaf
./proj_uaf
```

### Покроковий розбір звіту ASan

1. **Тип помилки та місце розіменування (`heap-use-after-free`):**
   - Рядок `READ of size 8 at 0x602000000010` повідомляє, що процес спробував прочитати 8-байтне машинне слово за адресою `0x602000000010`.
   - Трасування стека вказує точний номер рядка коду, де відбулося розіменування (`proj_uaf.c:56:5`).
2. **Історія звільнення пам'яті (`freed by thread T0 here`):**
   - Рантайм ASan зберігає повний стек викликів операції `free()`, яка повернула блок у карантин. Це дозволяє миттєво побачити, де саме об'єкт було передчасно знищено (`proj_uaf.c:42:5`).
3. **Історія первинного виділення (`previously allocated by thread T0 here`):**
   - Звіт фіксує місце початкового виклику `malloc()` (`proj_uaf.c:30:33`), що усуває невизначеність щодо походження пошкодженого об'єкта.
4. **Стан тіньової пам'яті (`Shadow bytes around the buggy address`):**
   - Адреса `0x602000000010` транслюється у тіньову адресу `0x0c047fff8000`.
   - Маркер `[fd]fd` наочно демонструє, що два 8-байтні фрагменти (сумарно 16 байтів) позначені магічним значенням `kAsanHeapFreeMagic` (`0xFD`), а навколо них розташовані захисні червоні зони `fa` (`kAsanHeapLeftRedzoneMagic`).

## 3. Інженерні пастки та архітектурні висновки

1. **Маскування помилки під час звичайного запуску:** Без компіляторного санітайзера або апаратного тегування цей код виконується без жодних системних попереджень. Оскільки адреса `0x6000` належить дійсній сторінці пам'яті процесу, операційна система не фіксує помилки захисту сторінок `Page Fault`, і вразливість може роками залишатися непоміченою у релізному коді.
2. **Неефективність ручного обнулення вказівників при наявності псевдонімів:** Присвоєння `session = NULL` захищає лише одну конкретну змінну. Якщо посилання на цей об'єкт було скопійовано у масив обробників подій, чергу асинхронних завдань чи передано в інший потік, звернення через ці несинхронізовані псевдоніми все одно призведе до UAF.
3. **Вплив агресивних оптимізацій компілятора (`-O2`/`-O3`):** Компілятор під час агресивної оптимізації може вважати, що звернення через завислий вказівник є невизначеною поведінкою (Undefined Behavior). Якщо компілятор доведе, що перед викликом пам'ять було звільнено, він має право повністю видалити перевірку прав або викинути подальші гілки коду, що створює приховані дірки безпеки у релізних бінарниках.
4. **Перевага сучасних моделей володіння:** Використання `std::unique_ptr` та `std::shared_ptr` / `std::weak_ptr` у C++ або статичної перевірки часу життя (*borrow checker*) у Rust усуває кореневу причину часових порушень за рахунок строгої прив'язки життєвого циклу пам'яті до області видимості об'єкта-власника. У Rust спроба звернутися до ресурсу після виклику `drop()` призводить до зупинки збірки з помилкою `E0382: use of moved value`, унеможливлюючи появу UAF ще до етапу компіляції.
