Коли програма на мові C або C++ запитує динамічну пам'ять викликом `malloc()` або оператором `new`, системний розподільник виділяє неперервний блок адресного простору в купі (heap) і повертає вказівник на його початок. Після завершення обробки даних виклик `free()` або `delete` сповіщає алокатор, що ця ділянка більше не потрібна і її можна повторно використати під наступні виділення. Проте ні функція `free()`, ні оператор `delete` фізично не здатні модифікувати значення змінної-вказівника, що зберігається в регістрах процесора, у стековому кадрі функції чи всередині інших об'єктів пам'яті. Вказівник продовжує містити ту саму 64-бітну адресу, перетворюючись на **завислий вказівник** (англ. *dangling pointer*, від давньоскандинавського *dangle* — вільно гойдатися, звисати).

Якщо програма згодом здійснює читання, запис або виклик функції через такий вказівник, виникає фундаментальне порушення життєвого циклу ресурсів — **використання після звільнення** (англ. *use-after-free*, скор. *UAF*). На відміну від класичного переповнення буфера, яке є просторовим порушенням меж виділеної ділянки, UAF є вадою **часової безпеки пам'яті** (англ. *temporal memory safety*, від латинського *temporalis* — часовий, тимчасовий). Сама адреса пам'яті залишається повністю легітимною в межах віртуального простору процесу, проте логічний зв'язок між типом даних, на який розраховував код, та фізичним вмістом цієї комірки безповоротно втрачається.

![Життєвий цикл вразливості Use-After-Free](/root/eng/sf-security/use-after-free/img/uaf-lifecycle.svg)
*Чотири фази розвитку вразливості UAF: виділення пам'яті під об'єкт A, його звільнення з утворенням завислого вказівника, перевикористання ділянки новим об'єктом B та несанкціоноване розіменування через старий інтерфейс.*

## 1. Архітектура розподільників купи та детермінізм перевикористання пам'яті

Щоб зрозуміти, чому звільнення пам'яті не призводить до негайної системної аварії (*Segmentation fault*), необхідно розібрати внутрішню організацію сучасних системних алокаторів динамічної пам'яті (англ. *heap allocator*, від латинського *allocare* — призначати, виділяти частку). 

Операційна система взаємодіє з процесом на рівні сторінок віртуальної пам'яті (розміром 4 КБ або 2 МБ на архітектурах x86-64 та ARM64) через системні виклики `mmap()` або `brk()`. Викликати системне ядро на кожен запит виділення 32 чи 64 байтів було б катастрофічно повільно через накладні витрати на перемикання контексту процесора. Тому бібліотека часу виконання (наприклад, `ptmalloc3` у GNU C Library, `jemalloc` у FreeBSD або `PartitionAlloc` у рушії Chromium) бере на себе роль проміжного менеджера: вона запитує у ядра великі пули пам'яті (арени) і нарізає їх на невеликі фрагменти — **чанки** (*chunks*).

### Структура чанка та кеші швидкого виділення (tcache та fastbins)

У стандартному розподільнику `ptmalloc` бібліотеки `glibc` виділена ділянка має чітко визначену структуру метаданих. Перед адресою даних, яку отримує прикладний код, розміщується службовий заголовок:

```text
+--------------------------------+---------------------------------+
| Попередній розмір (prev_size)  | Розмір поточного чанка (size)   |
| (якщо попередній блок вільний) | + прапорці стану (A | M | P)    |
+--------------------------------+---------------------------------+ <-- Адреса повернення malloc()
|                                                                  |
|               Корисне навантаження користувача (payload)         |
|                                                                  |
+------------------------------------------------------------------+
```

Прапорець `PREV_INUSE` (`P`, біт 0) сигналізує, чи зайнятий попередній фізично суміжний блок. Це запобігає фрагментації: коли звільняються два сусідні блоки, алокатор миттєво об'єднує їх в один великий.

Для забезпечення максимальної швидкодії сучасні версії `glibc` (починаючи з версії 2.26) використовують потоковий кеш **tcache** (*thread-local caching*), а також пули швидких списків **fastbins**. 

Коли програма викликає `free(ptr)`:
1. Алокатор обчислює розмірний клас чанка (наприклад, 32, 48 чи 64 байти).
2. Замість того, щоб повертати сторінку операційній системі або витрачати процесорні такти на блокування глобальної арени, алокатор поміщає вільний блок у локальний однобічно зв'язаний список потоку `tcache_entry[size_index]`.
3. Організація списку є стековою — **LIFO** (*Last-In, First-Out*): щойно звільнений чанк стає новою вершиною (*head*) списку.
4. Адреса попередньої вершини записується безпосередньо у перші 8 байтів звільненої ділянки як вказівник переходу вперед `fd` (*forward pointer*).

![Механіка перевикористання блоків у tcache glibc](/root/eng/sf-security/use-after-free/img/heap-allocator-reuse-tcache.svg)
*Організація зв'язаного списку tcache: звільнені чанки одного розмірного класу об'єднуються в LIFO-ланцюжок через покажчик fd, розташований у корисній ділянці блоку.*

Оскільки алокатор прагне зберегти максимальну локальність даних у кеш-пам'яті процесора L1/L2, наступний виклик `malloc()` з тим самим розмірним запитом **негайно поверне ту саму адресу**, яка щойно була звільнена.

:::tabs
```c
void *a = malloc(32); // Виділено блок за адресою 0x55555555a020
free(a);               // Блок 0x55555555a020 поміщено на вершину tcache

void *b = malloc(32); // b отримує РІВНО адресу 0x55555555a020!
```
```cpp
#include <memory>
#include <array>
#include <cstddef>

// У C++ алокатор поводиться аналогічно при ручному керуванні
auto a = std::make_unique<std::array<std::byte, 32>>();
a.reset(); // Звільнення блоку

auto b = std::make_unique<std::array<std::byte, 32>>(); // Перевикористання ділянки
```
:::

Цей детермінізм поведінки алокатора є базовою передумовою для експлуатації вразливостей UAF. Якщо після звільнення вказівник `a` не було обнулено, а новий об'єкт `b` створено за тією ж адресою, операції читання й запису через `a` тепер оперують даними об'єкта `b`.

### Багатопотокові арени та міжпотокове вивільнення

У багатопотокових процесах системний алокатор створює пул незалежних арен (до `8 * кількість_ядер` на 64-бітних системах). Кожен потік прив'язується до конкретної арени, що виключає конкуренцію за пам'ять. Проте коли об'єкт виділяється Потоком 1, передається через чергу завдань і звільняється Потоком 2, алокатор `glibc` повертає звільнений чанк не в глобальну купу ядра, а в локальний `tcache` Потоку 2 або в список `unsorted bin` арени-власника. Це створює міжпотокові стани гонитви (Race Conditions), коли один потік вивільняє структуру в процесі її активного читання іншим потоком.

> 🔧 **Навіщо це.** Кешування вільних блоків за схемою LIFO скорочує час виконання `malloc()` і `free()` до лічених тактів процесора (без системних викликів і без міжпотокових блокувань м'ютексів). Проте саме ця оптимізація робить повторне виділення пам'яті абсолютно передбачуваним для атакуючого.

## 2. Анатомія часових збоїв: від читання до перезапису метаданих

Залежно від характеру дій, які програма здійснює над завислим вказівником, наслідки Use-After-Free поділяються на три рівні небезпеки.

### 1. Читання після звільнення (Read-UAF / Information Disclosure)

Якщо програма зчитує поля структури через завислий вказівник, вона отримує доступ або до залишкових даних старого об'єкта, або до вмісту нового об'єкта, або до внутрішніх службових вказівників самого алокатора.

Коли чанк потрапляє у список `tcache` або `fastbins`, алокатор записує в його тіло вказівник `fd` на наступний вільний блок. Якщо вільний блок потрапляє до списку більших чанків (`unsorted bin`), алокатор записує туди вказівники на саму структуру арени всередині бібліотеки `libc` (`main_arena`). 

Зчитування такого поля через завислий вказівник дозволяє атакуючому миттєво з'ясувати точну адресу завантаження стандартної бібліотеки або адреси сусідніх блоків купи у пам'яті процесу. Це надає готовий примітив витоку пам'яті (*Memory Leak / Info Leak*), що повністю нівелює захист [ASLR](root:sf-security/aslr), перетворюючи рандомізований адресний простір на детерміновану карту для подальшої атаки.

### 2. Запис після звільнення (Write-UAF / Memory Corruption)

Запис через завислий вказівник дозволяє модифікувати поля нового об'єкта, порушуючи його внутрішні інваріанти (наприклад, змінюючи прапорець `is_admin`, лічильник довжини рядка або дескриптор файлу).

Більш небезпечний сценарій виникає, коли запис здійснюється в блок, який **ще не був перевиділений**, а все ще перебуває у списку вільних блоків алокатора. Записавши значення в перші 8 байтів звільненого блоку, зловмисник перезаписує вказівник `fd` списку `tcache` (техніка *Tcache Poisoning*). Під час наступних викликів `malloc()` алокатор поверне атакуючому адресу довільної пам'яті (наприклад, стек або таблицю перенаправлення системних викликів), що дозволяє записати довільні байти у будь-яку ділянку процесу.

### 3. Перехоплення потоку виконання (Control Flow Hijacking)

Найвищий рівень критичності виникає тоді, коли звільнений об'єкт містив вказівники на функції або був поліморфним C++ об'єктом. Розіменування вказівника для виклику методу призводить до передачі керування на довільну адресу в пам'яті.

## 3. Плутанина типів (Type Confusion) та підміна таблиці віртуальних методів (vtable)

У мові C++ класи, що містять хоча б один віртуальний метод, реалізують поліморфізм динамічного зв'язування за допомогою **таблиці віртуальних методів** (англ. *virtual method table*, скор. *vtable*).

Для кожного поліморфного класу компілятор генерує в секції даних тільки для читання (`.rodata`) незмінний масив адрес функцій. Кожен екземпляр такого класу містить у своєму першому машинному слові (зміщення +0) неявний прихований вказівник — **`_vptr`** (*virtual table pointer*), який вказує на відповідну таблицю `vtable` класу.

```text
Об'єкт у купі (Heap Object):
+-----------------------+
| _vptr (8 байтів)      | -------> Таблиця vtable у пам'яті (.rodata):
+-----------------------+          +-----------------------------------+
| int user_id           |          | &UserSession::validate_session()  |
+-----------------------+          +-----------------------------------+
| int permissions       |          | &UserSession::process_request()   |
+-----------------------+          +-----------------------------------+
```

Коли програма виконує віртуальний виклик `obj->validate_session()`, процесор на рівні асемблерного коду виконує непрямий перехід через покажчик:

```nasm
mov rax, qword ptr [rdi]        ; RAX = obj->_vptr (адреса vtable)
mov rax, qword ptr [rax]        ; RAX = vtable[0] (адреса функції validate_session)
call rax                        ; Виклик цільового методу
```

### Механізм атаки Type Confusion через UAF

**Плутанина типів** (англ. *type confusion*, від латинського *confusio* — змішування, безлад) виникає, коли ділянка пам'яті, що належала об'єкту одного типу (`TypeA`), після звільнення заповнюється даними іншого типу (`TypeB`), але програма продовжує взаємодіяти з нею як з `TypeA`.

Сценарій експлуатації виглядає так:

1. **Фаза жертви:** Програма виділяє об'єкт `UserAccount` розміром 32 байти, що містить покажчик `_vptr`.
2. **Фаза звільнення:** Об'єкт знищується через `delete user;`, але вказівник `user` залишається активним. Пам'ять повертається до пулу `tcache`.
3. **Фаза підміни:** Атакуючий ініціює виділення структури даних такого ж розмірного класу (наприклад, рядка або масиву чисел `char raw_data[32]`), контролюючи кожний байт його вмісту.
4. **Конструювання фальшивої таблиці:** У перші 8 байтів буфера записується адреса `fake_vtable`, попередньо створеної атакуючим у купі (або адреса ROP-ланцюжка).
5. **Фаза запуску:** Програма здійснює виклик `user->do_work()`. 

Процесор зчитує підроблену адресу `fake_vtable`, вибирає з неї адресу шкідливого коду і передає на неї керування регістром `RIP`. Якщо у системі активовано заборону виконання коду на сторінках даних ([біт NX](root:sf-security/no-execute-memory)), виклик перенаправляється на підготовлений ланцюжок повторного використання коду ([ROP-ланцюжок](root:sf-security/code-reuse-attacks)), який відключає захисні механізми операційної системи.

Детальний покроковий аналіз цього сценарію на прикладі вихідного коду мовами C та C++ наведено у [практикумі з підміни vtable](root:sf-security/use-after-free/proj-uaf-vtable-simulation.md). Історію розвитку цієї техніки від ранніх Linux-алокаторів до масштабних експлойтів сучасних веб-браузерів викладено в [історичному нарисі еволюції атак на купу](root:sf-security/use-after-free/hist-uaf-exploitation-milestones.md).

## 4. Контроль розкладки купи: Heap Spraying та Heap Feng Shui

У реальних складних застосунках (веб-браузери Chromium чи WebKit, офісні пакети, ядра ОС) купа не є статичною. Між звільненням об'єкта та розіменуванням завислого вказівника інші потоки програми можуть виконати тисячі паралельних виділень, зайнявши потрібну комірку небажаними даними.

Для гарантованого контролю над вмістом звільненої пам'яті застосовуються спеціальні методики структурування купи.

### Розпилення купи (Heap Spraying)

**Розпилення купи** (англ. *heap spraying*, від латинського *aspergere* — кропити, розпилювати) — це техніка масованого заповнення адресного простору процесу мільйонами копій підготовлених об'єктів або NOP-слайдів із пейлоадом. 

Атакуючий через скриптову мову (наприклад, JavaScript у браузері) циклічно створює тисячі типізованих масивів (`Uint8Array`) або рядків однакового розміру. Купа розростається, займаючи сотні мегабайтів. Коли черговий блок звільняється, наступне виділення з вірогідністю понад 99.9% вибере саме один із блоків атакуючого, забезпечуючи точний вміст пам'яті за адресою завислого вказівника.

### Формування купи (Heap Feng Shui / Heap Grooming)

На відміну від сліпого розпилення, **формування купи** (англ. *heap grooming*) — це детерміноване розташування об'єктів у пам'яті через прецизійну послідовність викликів `malloc()` та `free()`.

```text
Крок 1: Виділення суцільного ланцюжка блоків однакового розміру:
[ Блок 1 ] [ Блок 2 ] [ Блок 3 ] [ Блок 4 ] [ Блок 5 ] ...

Крок 2: Звільнення кожного другого блоку (створення «отворів» у купі):
[ Блок 1 ] [ ВІЛЬНО ] [ Блок 3 ] [ ВІЛЬНО ] [ Блок 5 ] ...

Крок 3: Виділення вразливого цільового об'єкта (він гарантовано займає один із отворів):
[ Блок 1 ] [ ЦІЛЬ (A) ] [ Блок 3 ] [ ВІЛЬНО ] [ Блок 5 ] ...

Крок 4: Звільнення об'єкта A та негайне виділення підробленого буфера B:
[ Блок 1 ] [ ПІДМІНА (B) ] [ Блок 3 ] [ ВІЛЬНО ] [ Блок 5 ] ...
```

Такий підхід дозволяє повністю нейтралізувати випадковість розміщення даних у багатопотокових середовищах.

## 5. Багатопотокові гонки та часові вразливості (Concurrent UAF)

Значна частка сучасних UAF-вразливостей у ядрах операційних систем (зокрема Linux Kernel і Windows Kernel) виникає внаслідок станів гонитви (Race Conditions) між паралельними потоками виконання.

Коли два потоки спільно використовують структуру даних без належної синхронізації або з помилкою у порядку блокувань:

```text
Потік 1 (Обробник системного виклику A):     Потік 2 (Обробник системного виклику B):
1. Отримує покажчик: ptr = get_shared_obj();
2. Перевіряє права: if (ptr->valid) {
                                              3. Закриває дескриптор: free(ptr);
                                              4. Виділяє новий мережевий сокет на місці ptr;
5. Виконує дію: ptr->handle_event();  <-- UAF!
```

Цей різновид помилки є проявом вразливості **TOCTOU** (*Time-Of-Check to Time-Of-Use*) у керуванні пам'яттю: між моментом, коли Потік 1 перевірив дійсність об'єкта, і моментом, коли він звернувся до його полів, Потік 2 встиг звільнити цей об'єкт.

### Неатомарні лічильники посилань

Класичною інженерною пасткою є використання звичайних цілих чисел для підрахунку посилань на об'єкт (`refcount--`) замість атомарних інструкцій (`std::atomic` або `refcount_t` у ядрі Linux). Якщо два потоки одночасно декрементують неатомарний лічильник, стан гонитви призводить до того, що пам'ять звільняється тоді, коли один із потоків все ще володіє активним посиланням на об'єкт, створюючи завислий вказівник.

## 6. Програмні захисні механізми та безпечні алокатори

Захист від використання після звільнення вимагає комплексного поєднання безпечних патернів проектування, спеціалізованих алокаторів та інструментів компіляторного аналізу.

### 1. Обнулення вказівників (Pointer Nulling) та його межі

Найпростішим рекомендованим правилом у мові C є негайне присвоєння `NULL` після кожного звільнення:

:::tabs
```c
free(ptr);
ptr = NULL;
```
```cpp
// У C++ ідіома RAII обнуляє або скидає володіння автоматично
ptr.reset(); // std::unique_ptr звільняє ресурс і скидає вказівник у nullptr
```
:::

Якщо програма спробує розіменувати такий покажчик пізніше, процесор викличе апаратний збій читання нульової сторінки (`Page Fault`), і процес безпечно завершиться аварією без виконання коду атакуючого.

Проте у реальних системах цей метод вирішує проблему лише частково. Причиною є **псевдоніми вказівників** (англ. *pointer aliasing*): коли один і той самий об'єкт адресований з багатьох різних місць програми (наприклад, у списку підписників події, у кеші сесій та у черзі завдань). Обнулення одного локального вказівника залишає решту посилань у системі завислими.

### 2. Патерн RAII та розумні вказівники у C++

Сучасний стандарт C++ вирішує проблему часової безпеки за допомогою ідіоми **RAII** (*Resource Acquisition Is Initialization*) та розумних вказівників:

- **`std::unique_ptr`:** Реалізує концепцію монопольного володіння ресурсом. Пам'ять звільняється автоматично, коли вказівник виходить з області видимості. Його не можна скопіювати — лише перемістити (`std::move`), що виключає появу неконтрольованих копій.
- **`std::shared_ptr` та `std::weak_ptr`:** Реалізують спільне володіння на основі лічильника посилань. Пам'ять фізично звільняється лише тоді, коли лічильник активних власників стає рівним нулю. Для спостерігачів, які не повинні продовжувати час життя об'єкта, використовується `std::weak_ptr`. Перед зверненням до ресурсу він вимагає виклику `lock()`, який повертає валідний `shared_ptr` або сповіщає про завершення життя об'єкта, унеможливлюючи UAF.

:::tabs
```c
#include <stdlib.h>
#include <stdio.h>

/* Небезпечний підхід: вказівник залишається завислим */
void legacy_unsafe_flow(void) {
    int *data = (int *)malloc(sizeof(int) * 10);
    if (!data) return;

    data[0] = 42;
    free(data);

    /* Небезпека: вказівник не обнулено, можливе помилкове звернення */
    /* data[0] = 100; -- Use-After-Free! */
}

/* Захищений підхід: безпечне вивільнення з обнуленням */
void safe_c_free(void **ptr_ref) {
    if (ptr_ref && *ptr_ref) {
        free(*ptr_ref);
        *ptr_ref = NULL;
    }
}
```
```cpp
#include <memory>
#include <iostream>

class ResourceSession {
public:
    void perform_work() {
        std::cout << "[+] Безпечне виконання операції над сесією.\n";
    }
};

void modern_safe_flow() {
    // 1. Монопольне володіння: автоматичне детерміноване звільнення
    auto unique_res = std::make_unique<ResourceSession>();
    unique_res->perform_work();
    // unique_res автоматично та безпечно знищується при виході з функції

    // 2. Спільне володіння через слабкі посилання (weak_ptr)
    std::weak_ptr<ResourceSession> observer;
    {
        auto shared_res = std::make_shared<ResourceSession>();
        observer = shared_res; // Створення спостерігача

        if (auto active = observer.lock()) {
            active->perform_work();
        }
    } // shared_res знищується тут, лічильник власників = 0

    // Спроба доступу після знищення
    if (auto active = observer.lock()) {
        active->perform_work();
    } else {
        std::cout << "[+] Ресурс безпечно відсутній: спробу UAF повністю усунуто.\n";
    }
}
```
:::

### 3. Карантин звільнених блоків (Memory Quarantine)

**Карантин пам'яті** (від італійського *quarantena* — сорок днів) — це архітектурний механізм захищених алокаторів (таких як *DieHarder*, *Freeguard*, *hardened_malloc* та *PartitionAlloc*), покликаний зруйнувати передбачуваність повторного використання ділянок.

Коли застосунок викликає `free(p)`, блок не повертається у вільні списки негайно:
1. Його поміщають у циклічний буфер карантину фіксованого розміру (наприклад, 256 МБ).
2. Захист сторінки може перемикатися на `PROT_NONE` через `mprotect()`, роблячи будь-яку спробу доступу фатальною.
3. Блок повертається до повторного використання лише через тривалий час після витіснення з карантину новими звільненими об'єктами.

Це позбавляє зловмисника змоги передбачити, куди саме потрапить новий об'єкт під час атаки Heap Spraying.

### 4. Ізоляція типів та MiraclePtr у Chromium

У рушії Google Chromium розподільник **PartitionAlloc** розділяє адресний простір на ізольовані арени за категоріями об'єктів. DOM-вузли ніколи не розміщуються на тих самих сторінках пам'яті, що й рядкові масиви чи буфери зображень. Навіть за наявності завислого вказівника на DOM-елемент, перевиділення пам'яті може відбутися лише під об'єкт такого самого типу, що виключає експлуатацію Type Confusion для підміни vtable.

Для повного нейтралізації UAF команда Chromium впровадила технологію **MiraclePtr (`raw_ptr<T>`)**. Усі сирі вказівники в C++ коді замінюються розумною обгорткою `raw_ptr`. При кожному виділенні пам'яті PartitionAlloc виділяє 4 додаткових байти перед корисними даними під прихований лічильник `raw_ptr`. Коли об'єкт знищується через `delete`, деструктор викликається негайно, але сам чанк пам'яті **залишається заблокованим у карантині** і не повертається алокатору доти, доки останній `raw_ptr` у коді не буде скинуто. Спроба звернення через завислий `raw_ptr` призводить до безпечного виклику контрольованого аварійного завершення `CrashHandler` замість виконання коду зловмисника.

## 7. Динамічне виявлення: тіньова пам'ять AddressSanitizer (ASan)

**AddressSanitizer (ASan)** — це компіляторна технологія динамічного аналізу пам'яті, що забезпечує практично 100% виявлення UAF-вразливостей під час тестування програм.

Робота ASan базується на двох компонентах:
1. **Тіньова пам'ять (Shadow Memory):** Пряме відображення віртуального простору програми на спеціальний службовий масив пам'яті.
2. **Компіляторне інструментування:** Вставка перевірочного коду перед кожною операцією читання або запису.

### Формула адресації тіньової пам'яті

На 64-бітній архітектурі x86-64 кожні 8 байтів звичайної оперативної пам'яті процесу відображаються рівно на **1 байт тіньової пам'яті**.

Адреса тіньового байта обчислюється через бітовий зсув і константне зміщення:

```text
ShadowAddress = (AppAddress >> 3) + 0x7fff8000
```

Математично трансляція виконується за один такт:

```
AppAddress = 0x10008000
ShadowAddress
= (0x10008000 >> 3) + 0x7fff8000  [зсув на 3 біти: масштаб 1:8]
= 0x02001000 + 0x7fff8000        [додавання бази тіньового простору]
= 0x81ff9000                     [підсумкова адреса байта стану]
```

![Тіньова пам'ять AddressSanitizer](/root/eng/sf-security/use-after-free/img/asan-shadow-memory.svg)
*Відображення пам'яті застосунку на тіньовий простір у масштабі 1:8 та кодування стану блоків (валідні байти, червоні зони та звільнені чанки).*

### Кодування стану та процес отруєння (Poisoning)

Значення кожного тіньового байта визначає доступність відповідних 8 байтів пам'яті застосунку:

| Значення тіньового байта | Стан ділянки пам'яті | Пояснення |
|---|---|---|
| `0x00` | Повністю доступна | Усі 8 байтів виділені і готові до читання/запису. |
| `0x01` – `0x07` | Частково доступна | Перші `k` байтів доступні, решта `8 - k` — у червоній зоні. |
| `0xFA` / `0xFB` | Червона зона (Redzone) | Службовий захисний бар'єр навколо блоку для виявлення переповнення буфера. |
| `0xFD` | Звільнена купа (`kAsanHeapFreeMagic`) | Пам'ять звільнена через `free()`, блок знаходиться в карантині ASan. |

Коли програма викликає `free(ptr)`:
1. Рантайм ASan поміщає блок у глобальний карантин.
2. Уся відповідна ділянка тіньової пам'яті **отруюється** — заповнюється значенням `0xFD`.
3. Перед кожним розіменуванням компілятор генерує швидку перевірку:

```nasm
mov rax, rdi                    ; RDI = цільова адреса пам'яті
shr rax, 3                      ; Зсув на 3 біти
mov cl, byte ptr [rax + 0x7fff8000] ; Читання тіньового байта
test cl, cl                     ; Перевірка, чи значення дорівнює 0
jnz .__asan_report_error        ; Якщо != 0, виклик діагностики аварії
```

Якщо програма спробує прочитати пам'ять за завислим вказівником, тіньовий байт `0xFD` миттєво активує аварійний обробник із детальним дампом стеків створення та звільнення цього блоку. Повний опис функцій та прапорців запуску міститься у [довіднику інтерфейсів ASan та MTE](root:sf-security/use-after-free/api-memory-sanitizers.md).

## 8. Апаратний захист: тегування пам'яті ARM MTE

Головним недоліком програмних санітайзерів (ASan) є накладні витрати: споживання пам'яті зростає в 2–3 рази, а швидкодія падає на 70–100%, що унеможливлює їхнє використання у релізному середовищі на смартфонах чи серверах.

Для вирішення цієї проблеми процесорна архітектура ARMv8.5-A стандартизувала апаратне розширення **Memory Tagging Extension (MTE)**.

### Архітектура тегів та механіка Top-Byte Ignore (TBI)

MTE використовує вбудовану апаратну можливість процесорів ARM64 ігнорувати верхній байт віртуальної адреси при трансляції через сторінкові таблиці (англ. *Top-Byte Ignore*, TBI).

Адресний простір і вказівники організовані за двома рівнями:
1. **Логічний тег (Logical Tag):** 4 біти (значення від 0 до 15), розташовані у бітах `[59:56]` 64-бітного вказівника.
2. **Фізичний тег виділення (Allocation Tag):** 4 біти, збережені у спеціальній виділеній апаратній пам'яті (*Tag RAM*) для кожної фізичної 16-байтної **гранули пам'яті**.

![Апаратне тегування пам'яті ARM MTE](/root/eng/sf-security/use-after-free/img/arm-mte-tagging.svg)
*Схема роботи ARM MTE: порівняння 4-бітного логічного тегу вказівника з фізичним тегом 16-байтної гранули пам'яті. Зміна фізичного тегу при free() викликає апаратне переривання при зверненні через застарілий вказівник.*

### Життєвий цикл тегування при виділенні та звільненні

1. **Виділення (`malloc`):**
   - Алокатор обирає для блоку псевдовипадковий 4-бітний тег (наприклад, `0x9`).
   - За допомогою спеціальної процесорної інструкції `STG` (*Store Allocation Tag*) алокатор записує тег `0x9` у фізичну Tag RAM для всіх 16-байтних гранул цього блоку.
   - Алокатор вбудовує значення `0x9` у верхній байт вказівника і повертає його програмі.
2. **Легітимне використання:**
   - Під час кожного читання (`LDR`) або запису (`STR`) апаратний конвеєр процесора паралельно порівнює біти `[59:56]` вказівника з фізичним тегом гранули в Tag RAM.
   - Оскільки `0x9 == 0x9`, доступ відбувається без жодних затримок.
3. **Звільнення (`free`):**
   - Алокатор генерує **новий інший тег** (наприклад, `0x4`) і записує його в Tag RAM звільнених гранул через інструкцію `STG`.
4. **Спроба Use-After-Free:**
   - Завислий вказівник усе ще містить старий логічний тег `0x9`.
   - Програма намагається виконати запис за цією адресою.
   - Процесор порівнює теги: `0x9 != 0x4` (Tag Mismatch).
   - Апаратура негайно генерує виняток відмови пам'яті, перериваючи виконання шкідливого коду.

### Режими роботи MTE

MTE підтримує два режими апаратної реакції на порушення:
- **Синхронний режим (Synchronous, `PR_MTE_TCF_SYNC`):** Виняток генерується миттєво на тій самій інструкції процесора, що спричинила збій. Ядро надсилає процесу сигнал `SIGSEGV` із кодом `SEGV_MTESERR`. Ідеально підходить для налагодження та точної локалізації помилок.
- **Асинхронний режим (Asynchronous, `PR_MTE_TCF_ASYNC`):** Збій тегу фіксується у внутрішньому регістрі процесора, а переривання відкладається до наступного системного виклику чи перемикання контексту. Накладні витрати на швидкодію складають лише ~1–2%, що робить цей режим оптимальним для захисту серійних пристроїв на рівні операційної системи (зокрема у сучасних версіях Android).

## 9. Порівняльний аналіз захисних технологій

| Технологія захисту | Рівень реалізації | Накладні витрати RAM / CPU | Виявлення Read-UAF | Виявлення Write-UAF | Можливість використання у продакшені |
|---|---|---|---|---|---|
| **Pointer Nulling (`ptr = NULL`)** | Прикладний код | 0% / 0% | Тільки для самого вказівника (не діє на aliasing) | Тільки для самого вказівника | Так (базова дисципліна) |
| **Smart Pointers (RAII / `std::shared_ptr`)** | Компілятор C++ | Мінімальні (лічильник посилань) | Повне запобігання (запобігає dangling pointer) | Повне запобігання | Так (рекомендований стандарт) |
| **Allocator Quarantine (PartitionAlloc / MiraclePtr)** | Рантайм алокатора | +10–20% RAM / +2–5% CPU | Уповільнює перевикористання | Запобігає підміні типів у межах карантину | Так (Chrome, Edge, Hardened Linux) |
| **AddressSanitizer (ASan)** | Компілятор + Рантайм | +200–300% RAM / +70–100% CPU | Повне детерміноване перехоплення (тіньовий байт 0xFD) | Повне детерміноване перехоплення | Ні (лише тестування, CI/CD та фазинг) |
| **ARM MTE (Memory Tagging)** | Апаратний кремній (ARMv8.5-A) | +3% Tag RAM / +1–3% CPU | Апаратна зупинка (перевірка 4-бітних тегів) | Апаратна зупинка | Так (серійні релізи ОС, Android 13+) |

Use-After-Free залишається одним із найнебезпечніших класів вразливостей системного програмного забезпечення саме через свою часову природу. Еволюція захисних заходів довела: повної безпеки неможливо досягти виключно дисципліною ручного керування пам'яттю. Фундаментальним рішенням проблеми є поєднання сучасних апаратних бар'єрів тегування пам'яті в кремнії процесора з переходом на мови програмування із суворою статичною перевіркою часу життя ресурсів.
