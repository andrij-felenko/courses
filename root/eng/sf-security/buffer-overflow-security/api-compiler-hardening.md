# 📋 Прапорці компілятора та системні інтерфейси захисту від переповнення

Сучасний захист бінарних виконуваних файлів від переповнення буфера будується на поетапному комбінуванні прапорців компілятора (GCC, Clang, MSVC), опцій компонувальника (Linker) та системних налаштувань ядра операційної системи. Кожен рівень закриває специфічний клас загроз: компіляторні інструменти виявляють порушення меж під час виконання та захищають стекові кадри, компонувальник блокує перезапис службових таблиць динамічного зв'язування, а операційна система забезпечує ізоляцію та рандомізацію пам'яті.

## Прапорці компіляторів GCC та Clang

Компілятори сімейства GNU Compiler Collection (GCC) та LLVM Clang надають широкий набір опцій захисту пам'яті, які вбудовують перевірки безпосередньо у згенерований машинний код.

### 1. Захист стекового кадру (Stack Smashing Protector)

Сімейство прапорців `-fstack-protector` керує автоматичною генерацією канаркових вартових значень між локальними буферами та збереженими регістрами керування (`Saved RBP` та `Saved RIP`):

- **`-fno-stack-protector`**: Повне вимкнення генерації канарок. Використовується виключно в коді низькорівневих завантажувачів, ядрах операційних систем до ініціалізації регістрів сегментів або для навчальних демонстрацій класичних експлойтів.
- **`-fstack-protector`**: Базовий історичний режим. Компілятор вставляє канарку лише у функції, які виділяють масиви символів розміром 8 і більше байтів (`char buf[8]`), або функції, що містять виклики динамічного виділення пам'яті на стеку через `alloca()`. Масиви інших типів (наприклад, `int arr[10]`) або менші масиви цим прапорцем ігноруються.
- **`-fstack-protector-strong`**: Сучасний галузевий стандарт безпеки. Компілятор аналізує абстрактне синтаксичне дерево (AST) функції та вставляє канарку, якщо виконується хоча б одна з чотирьох умов:
  1. Функція містить масив будь-якого типу та будь-якого розміру (включно з `char`, `int`, покажчиками або структурами);
  2. Функція виділяє об'єкт на стеку через виклик `alloca()` або масив змінної довжини (VLA);
  3. Адреса будь-якої локальної змінної береться через оператор `&` і передається як покажчик за межі виразу;
  4. Функція містить структуру, яка має масив як одне зі своїх полів.
- **`-fstack-protector-all`**: Примусове встановлення канарки в абсолютно всі функції бінарного файлу, включно з найпростішими гетерами, математичними обчисленнями та функціями без локальних змінних. Створює навантаження на регістровий файл процесора та сповільнює виконання на 2–5%.

### 2. Захист від перестрибування сторожової сторінки (Stack Clash Protection)

- **`-fstack-clash-protection`**: Захищає програму від специфічного класу атак *Stack Clash*. Операційна система розміщує в кінці стекового простору спеціальну невідображену сторожову сторінку ([Guard Page](root:sf-os/virtual-address-space)) розміром 4 КБ із забороною доступу. Якщо стек росте поступово, дотик до цієї сторінки викликає сторінковий збій і ядро розширює стек або аварійно зупиняє процес. Проте якщо функція виділяє на стеку локальний буфер розміром понад 4096 байтів (`char big_buf[8192]`), покажчик стека `%rsp` може зменшитися одразу на 8 КБ, «перестрибнувши» сторожову сторінку в область сусідньої пам'яті (наприклад, кучі). Прапорець змушує компілятор генерувати циклічні зондувальні звернення (*probe instructions*) через кожні 4096 байтів при виділенні великих фреймів:
  ```nasm
  subq    $4096, %rsp
  orq     $0, (%rsp)          ; апаратний дотик до кожної сторінки
  subq    $4096, %rsp
  orq     $0, (%rsp)
  ```

### 3. Динамічна та статична фортифікація функцій (Fortify Source)

Макрос `_FORTIFY_SOURCE` замінює виклики стандартних функцій копіювання пам'яті та рядків на їхні захищені аналоги з бібліотеки Glibc:

- **`-O2 -D_FORTIFY_SOURCE=2`**: Активує вбудовані компіляторні перевірки розміру об'єктів `__builtin_object_size(ptr, type)`. Якщо компілятор на етапі збирання або під час виконання може обчислити точний розмір цільового буфера, виклик `strcpy(dest, src)` автоматично підміняється на виклик `__strcpy_chk(dest, src, dest_size)`. Якщо довжина джерела перевищує `dest_size`, бібліотека перериває процес викликом `__chk_fail()`.
- **`-O2 -D_FORTIFY_SOURCE=3`**: Розширений режим (GCC 12+, Glibc 2.33+). Спирається на розширений аналіз динамічного розміру `__builtin_dynamic_object_size()`. Це дозволяє обчислювати розміри об'єктів, виділених у динамічній пам'яті через `malloc(n)`, навіть якщо розмір залежить від аргументів часу виконання, перекриваючи понад 80% операцій копіювання.

### 4. Санітайзери та технології розділення стека

- **`-fsanitize=address`**: AddressSanitizer (ASan). Потужний інструмент динамічного аналізу. Перетворює кожен 8-байтний блок оперативної пам'яті на 1 байт у спеціальній тіньовій пам'яті (*Shadow Memory*). Перед кожним буфером і після нього вставляються заблоковані «червоні зони» (*Redzones*). Будь-яка спроба зчитати або записати байт за межами масиву миттєво викликає деталізований звіт про помилку пам'яті. Використовується під час тестування, фаззингу та CI/CD-конвеєрів через сповільнення швидкодії приблизно у 2 рази.
- **`-fsanitize=safe-stack`**: Технологія SafeStack у компіляторі Clang. Компілятор фізично розділяє єдиний стек потоку на два незалежні адресні простори:
  1. *Safe Stack*: Зберігає лише адреси повернення, збережені регістри кадру, регістрові скиди та локальні скалярні змінні, чия адреса ніколи не береться через покажчик. Цей стек повністю захищений від будь-якого виходу за межі;
  2. *Unsafe Stack*: Зберігає всі масиви, буфери та змінні, до яких звертаються через покажчики. Переповнення буфера на небезпечному стеку може зіпсувати сусідні змінні, але фізично не здатне дістатися до адрес повернення на безпечному стеку.
- **`-fcf-protection=full`**: Вмикає апаратну підтримку технологій захисту потоку керування Intel CET: апаратний Shadow Stack проти підміни адрес повернення (`-fcf-protection=return`) та Indirect Branch Tracking з перевіркою інструкцій `endbr64` на точках непрямих стрибків (`-fcf-protection=branch`).

| Прапорець компіляції | Призначення та механіка дії | Вплив на продуктивність |
|---|---|---|
| `-fstack-protector-strong` | Стандартний захист канарками функцій з масивами будь-якого типу та витоками покажчиків. | ~1% |
| `-fstack-clash-protection` | Зондування стека через кожні 4 КБ проти пропуску сторожової сторінки Guard Page. | < 0.2% |
| `-D_FORTIFY_SOURCE=3` | Динамічний контроль меж копіювання в функціях Glibc (`__memcpy_chk`, `__sprintf_chk`). | < 1% |
| `-fsanitize=address` | Повний контроль пам'яті через тіньові маски (ASan). Для розробки та фаззингу. | Сповільнення ~2× |
| `-fsanitize=safe-stack` | Апаратне розділення стека на безпечний (адреси повернення) та небезпечний (буфери). | < 0.5% |
| `-fcf-protection=full` | Апаратні інструкції Intel CET: Shadow Stack та IBT (`endbr64`). | < 1% |
| `-fPIE -pie` | Генерація позиційно-незалежного коду для повної рандомізації бінарника в ASLR. | 0% |
| `-Wl,-z,relro -Wl,-z,now` | Full RELRO: блокування таблиці GOT від перезапису покажчиків після старту. | Лише на старті |

## Прапорці компілятора MSVC (платформа Windows)

Середовище розробки Microsoft Visual C++ містить власний набір механізмів захисту бінарного коду:

- **`/GS`**: Вмикає генерацію безпекового кукі (*Security Cookie*), аналога стекової канарки. Компілятор розміщує 32- або 64-бітне псевдовипадкове число між локальними змінними та адресою повернення. Перевірка цілісності кукі виконується викликом `__security_check_cookie()` в епілозі функції. У разі виявлення пошкодження викликається обробник `__report_gsfailure`, який аварійно ліквідує процес.
- **`/GS-`**: Повне вимкнення захисту канаркою.
- **`/guard:cf`**: Вмикає Control Flow Guard (CFG) — технологію перевірки валідності адрес непрямих викликів функцій перед передачею керування на основі попередньо скомпільованої бітової карти дозволених точок входу.
- **`/guard:ehcont`**: Створює таблицю дозволених адрес блоків обробки винятків (`try/catch`) для коректної взаємодії з апаратною технологією Intel CET Shadow Stack.
- **`/DYNAMICBASE`**: Додає інформацію переміщення (*Relocations*) у заголовок PE-файлу, повідомляючи завантажувачу Windows про можливість довільної рандомізації адреси запуску через ASLR.
- **`/HIGHENTROPYVA`**: Дозволяє 64-бітним процесам використовувати повний 64-бітний діапазон адресного простору для рандомізації ASLR (понад 4 ГБ), значно підвищуючи ентропію розміщення модулів.
- **`/NXCOMPAT`**: Позначає бінарний файл як сумісний із технологією апаратної заборони виконання даних Data Execution Prevention (DEP / NX-біт).

## Системні інтерфейси та параметри ядра Linux

Окрім компілятора, фундаментальні параметри безпеки пам'яті конфігуруються на рівні операційної системи.

### 1. Керування ASLR через procfs

Глобальний стан рандомізації адресного простору в ядрі Linux контролюється віртуальним файлом `/proc/sys/kernel/randomize_va_space`:

```bash
# Перевірка поточного значення ASLR
cat /proc/sys/kernel/randomize_va_space

# Встановлення максимального рівня рандомізації через sysctl
sudo sysctl -w kernel.randomize_va_space=2
```

Параметр підтримує три режими:
- **`0` — Вимкнено**: Усі адресні простори (стек, куча, завантажені бібліотеки, виконуваний файл) мають фіксовані адреси при кожному запуску. Використовується виключно для налагодження низькорівневих проблем.
- **`1` — Часткова рандомізація**: Рандомізуються адреси верхівки стека, відображень динамічних бібліотек через `mmap()` та віртуальної динамічної бібліотеки `vdso`. Сегмент кучі `brk` розміщується безпосередньо за кінцем сегмента коду бінарника без зсуву.
- **`2` — Повна рандомізація (Рекомендовано)**: Додатково рандомізується розміщення сегмента кучі (`brk`), що унеможливлює передбачення адрес динамічно виділених блоків пам'яті.

### 2. Програмне керування Shadow Stack через `prctl` (Linux 6.6+)

У ядрі Linux 6.6 впроваджено спеціалізовані команди системного виклику `prctl()` для керування станом апаратного тіньового стека Intel CET безпосередньо з простору користувача:

:::tabs
```c
#include <sys/prctl.h>
#include <stdio.h>

#ifndef PR_SET_SHADOW_STACK_STATUS
#define PR_SET_SHADOW_STACK_STATUS 75
#define PR_GET_SHADOW_STACK_STATUS 74
#define PR_LOCK_SHADOW_STACK_STATUS 76
#define PR_SHADOW_STACK_ENABLE     (1UL << 0)
#define PR_SHADOW_STACK_WRITE      (1UL << 1)
#endif

int configure_shadow_stack(void) {
    // Примусова активація апаратного тіньового стека для поточного процесу
    if (prctl(PR_SET_SHADOW_STACK_STATUS, PR_SHADOW_STACK_ENABLE, 0, 0, 0) != 0) {
        perror("Помилка: процесор або ядро не підтримують Intel CET");
        return -1;
    }

    // Блокування подальшої зміни статусу для захисту від вимкнення зловмисником
    if (prctl(PR_LOCK_SHADOW_STACK_STATUS, PR_SHADOW_STACK_ENABLE, 0, 0, 0) != 0) {
        perror("Помилка блокування конфігурації Shadow Stack");
        return -1;
    }

    return 0;
}
```
```cpp
#include <sys/prctl.h>
#include <iostream>
#include <expected>
#include <system_error>

#ifndef PR_SET_SHADOW_STACK_STATUS
#define PR_SET_SHADOW_STACK_STATUS 75
#define PR_GET_SHADOW_STACK_STATUS 74
#define PR_LOCK_SHADOW_STACK_STATUS 76
#define PR_SHADOW_STACK_ENABLE     (1UL << 0)
#define PR_SHADOW_STACK_WRITE      (1UL << 1)
#endif

enum class ShadowStackError {
    NotSupported,
    LockFailed
};

// Ідіоматична обгортка C++23 з поверненням типізованого результату
std::expected<void, ShadowStackError> configure_shadow_stack() noexcept {
    if (prctl(PR_SET_SHADOW_STACK_STATUS, PR_SHADOW_STACK_ENABLE, 0, 0, 0) != 0) {
        return std::unexpected(ShadowStackError::NotSupported);
    }
    if (prctl(PR_LOCK_SHADOW_STACK_STATUS, PR_SHADOW_STACK_ENABLE, 0, 0, 0) != 0) {
        return std::unexpected(ShadowStackError::LockFailed);
    }
    return {};
}
```
:::

Цей інтерфейс дозволяє високонавантаженим службам та захищеним серверам гарантувати неможливість підміни адрес повернення, навіть якщо сам бінарний файл було скомпільовано без прапорця `-fcf-protection=full`.
