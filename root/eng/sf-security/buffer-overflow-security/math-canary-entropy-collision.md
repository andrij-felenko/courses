# 🧮 Імовірність вгадування канарки та ентропія захисту

Ефективність механізмів рандомізації у системній безпеці спирається на ентропію випадкових величин. У випадку стекової канарки (Stack Canary) та рандомізації адресного простору (ASLR) математична модель захисту визначає, скільки спроб потрібно здійснити зловмиснику для успішного вгадування секретного значення або цільової адреси в пам'яті. Розуміння цих імовірнісних меж дозволяє інженерам обирати правильну розрядність архітектури, налаштовувати системні параметри та уникати архітектурних помилок у мережевих сервісах.

## Ентропія випадкової 64-бітної канарки

У 64-бітних операційних системах (x86-64) канарочне значення займає повне машинне слово розміром 8 байтів (64 біти). Проте компілятор GCC та бібліотека Glibc навмисно фіксують молодший байт канарки нульовим значенням `0x00` (Null Byte). Це робиться для того, щоб рядкові функції на зразок `strcpy()` або `sprintf()` зупиняли копіювання при спробі витоку канарки через незакритий рядок.

Внаслідок фіксації першого байта випадковими залишаються рівно 7 байтів:

```
Ентропія канарки
= 7 байтів · 8 бітів / байт    [фіксація молодшого байта як 0x00]
= 56 бітів                    [чистий простір станів CSPRNG]
```

Загальна кількість можливих комбінацій значень випадкової канарки становить:

```
N_комбінацій
= 2⁵⁶                         [простір випадкових 56 бітів]
= 72 057 594 037 927 936      [понад 7.2 · 10¹⁶ можливих станів]
```

Якщо мережевий демон перезапускається заново після кожного аварійного завершення через виклик `execve()`, генеруючи абсолютно нову випадкову канарку за допомогою системного генератора ентропії ядра, ймовірність вгадати значення за одну незалежну спробу дорівнює:

```
P(успіх за 1 спробу)
= 1 / 2⁵⁶                     [один вибір із рівноймовірного простору]
≈ 1.3877 · 10⁻¹⁷             [абсолютно нездійсненний прямий перебір]
```

Для 32-бітних систем (x86) розмір канарки становить 4 байти (32 біти). З урахуванням нульового байта `0x00` для випадкового значення залишається лише 3 байти (24 біти ентропії), що відповідає `2²⁴ = 16 777 216` комбінаціям. Для повного перебору 32-бітної канарки потрібно в середньому близько 8.38 мільйона спроб, що є цілком реалістичним для автоматизованого мережевого бота в локальній мережі.

## Побайтове вгадування у форк-моделі (Byte-by-Byte Brute-Force)

Математична стійкість канарки миттєво руйнується, якщо мережевий сервер побудовано за багатопроцесною моделлю `fork()`, де головний процес приймає вхідні з'єднання на сокеті й породжує дочірній процес (`fork()`) на кожного клієнта без наступного виклику `execve()`.

При виклику `fork()` ядро операційної системи дублює віртуальний адресний простір батьківського процесу (механізм Copy-on-Write). Це означає, що **значення канарки в пам'яті дочірнього процесу є абсолютно ідентичним до канарки батька**. Якщо дочірній процес завершується аварійно через спрацювання захисту `__stack_chk_fail`, батьківський процес не падає і продовжує працювати, зберігаючи незмінне канарочне число для всіх наступних з'єднань.

Оскільки пам'ять розташована лінійно, зловмисник може перебирати канарку не цілком (усі 56 бітів одразу), а послідовно по одному байту зліва направо:

1. **Крок 1**: Надіслати довжину буфера, що переповнює його рівно на 1 байт у позицію першого невідомого байта канарки (старшого після нульового). Перебираються 256 можливих значень від `0x00` до `0xFF`.
2. Якщо надіслано неправильне значення, дочірній процес падає від `SIGABRT` і закриває з'єднання.
3. Якщо надіслано правильний байт, процес не падає і повертає коректну відповідь або продовжує тримати сокет відкритим.
4. **Крок 2**: Зловмисник фіксує знайдений байт, збільшує довжину вхідного навантаження на 1 байт і перебирає наступний байт канарки (знову від 0 до 255).
5. Процедура повторюється для всіх 7 невідомих байтів.

Математична модель перебору кожного окремого байта описується дискретним рівномірним розподілом з кількістю варіантів `M = 256`.

Розрахунок максимальної кількості спроб для повного розкриття 64-бітної канарки:

```
N_максимум
= 7 байтів · 256 варіантів    [лінійний перебір кожного байта окремо]
= 1 792 спроби               [замість 7.2 · 10¹⁶ комбінацій!]
```

Математичне сподівання загальної кількості спроб (середнє число з'єднань) обчислюється як сума середніх значень перебору для кожного з 7 байтів:

```
E[N_спроб]
= 7 · ((256 + 1) / 2)         [математичне сподівання дискретного розподілу]
= 7 · 128.5                  [середня кількість спроб на один байт]
= 899.5 спроб                [менше 900 запитів до сервера]
```

Зниження складності атаки від експоненційної `2⁵⁶` до лінійної `7 · 256` доводить, чому архітектура `fork()` без зміни адресного простору створює фатальну прогалину в безпеці систем з увімкненим SSP.

## Математична стійкість ASLR та парадокс днів народження

Рандомізація адресного простору (ASLR) додає випадковий зсув до базових адрес сторінок пам'яті. Оскільки мінімальною одиницею виділення пам'яті в архітектурі x86/x86-64 є сторінка розміром 4096 байтів (`2¹²` байтів), молодші 12 бітів будь-якої адреси (зміщення всередині сторінки) залишаються незмінними.

Доступна ентропія випадкового зсуву визначається кількістю бітів `k`:
- На 32-бітній архітектурі x86 із віртуальним простором 4 ГБ: від 32 бітів віднімаються 12 бітів сторінки та 1 біт межі ядра/користувача, що залишає лише `k = 19` бітів ентропії для стека (`2¹⁹ = 524 288` станів) та `k = 8`..`12` бітів для спільних бібліотек `mmap` (`256`..`4096` станів);
- На 64-бітній архітектурі x86-64 із канонічним простором 48 бітів: віднімання 12 бітів залишає `k = 28`..`33` біти ентропії для стека (до `8.5 · 10⁹` станів) та `k = 28`..`32` біти для динамічних бібліотек.

Якщо зловмисник намагається підібрати фіксовану адресу в пам'яті шляхом багаторазових спроб, або викликати колізію двох випадкових адрес, імовірність успіху описується наближенням парадоксу днів народження:

```
P(колізія)
= 1 - exp( - (n · (n - 1)) / (2 · 2ᵏ) )    [наближення розподілу ймовірностей]
≈ 1 - exp( - n² / (2 · 2ᵏ) )              [спрощення для великих значень n]
```

Для 32-бітної системи з `k = 19` бітами стека (`2¹⁹ = 524 288` можливих адрес) кількість запитів `n`, необхідна для досягнення 50% ймовірності колізії (`P = 0.5`), розраховується так:

```
0.5
= 1 - exp( - n² / (2 · 2¹⁹) )             [рівняння для 50% ймовірності]

exp( - n² / (2 · 2¹⁹) )
= 0.5                                     [перенесення компонентів]

- n² / (2 · 524 288)
= ln(0.5)                                 [логарифмування обох частин]
= - 0.693147                              [значення натурального логарифма]

n²
= 2 · 524 288 · 0.693147                  [множення на знаменник]
= 726 817.3                               [квадрат кількості спроб]

n
= √(726 817.3)                            [вилучення квадратного кореня]
≈ 853 спроби                              [достатньо менше 1000 запитів]
```

Для 64-бітної системи з `k = 32` бітами ентропії (`2³² = 4 294 967 296` станів) аналогічний розрахунок дає:

```
n²
= 2 · 2³² · 0.693147                      [розрахунок для 32 бітів]
= 5 953 826 406.8                         [квадрат кількості спроб]

n
= √(5 953 826 406.8)                      [вилучення кореня]
≈ 77 161 спроба                           [кількість спроб для колізії]
```

При цьому для прямого вгадування конкретної цільової адреси шеллкоду на 64-бітній системі потрібно в середньому `2³² / 2 ≈ 2.14 · 10⁹` спроб. Ці виведення доводять, що 32-бітна ASLR не здатна протистояти навіть найпростішому мережевому підбору, тоді як 64-бітна архітектура робить сліпі спроби експлуатації абсолютно неефективними.
