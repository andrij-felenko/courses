</preknowlist>

Коли центральний процесор архітектури x86-64 виконує машинну інструкцію виклику функції `call`, апаратний блок керування послідовно виконує дві неподільні операції: зменшує значення регістра покажчика стека `%rsp` на 8 байтів і записує за новою адресою верхівки стека адресу наступної машинної інструкції — **адресу повернення** (англ. *Return Address*, Saved RIP). Усередині викликаної підпрограми стандартний компіляторний пролог зберігає поточний базовий покажчик кадру (`push %rbp`), копіює значення покажчика стека в базовий регістр (`mov %rsp, %rbp`) та віднімає від `%rsp` необхідну кількість байтів для резервування пам'яті під локальні змінні й масиви.

У віртуальному адресному просторі процесу стек організовано асиметрично: **стек росте у бік менших адрес пам'яті** (вниз, від високих адрес до низьких), тоді як **запис байтів у будь-який послідовний масив пам'яті відбувається у бік більших адрес** (вгору, від молодших адрес до старших). Якщо програма починає копіювати вхідні байти у локальний буфер фіксованого розміру без суворої попередньої перевірки довжини, надлишкові дані безперешкодно перетинають верхню межу масиву. Вони послідовно перезаписують сусідні змінні, збережений покажчик кадру попередньої функції (Saved RBP) і, зрештою, саму адресу повернення (Saved RIP).

Коли функція завершує роботу й виконує інструкцію повернення `ret` (`pop %rip`), процесор вилучає 8 байтів з верхівки стека, безумовно завантажує їх у регістр лічильника команд `%rip` і починає вибірку наступної інструкції за цією адресою. Якщо зловмисник передав спеціально сформований байтовий масив, адреса повернення заміщується довільним значенням, що передає повне керування процесором на підконтрольний атакуючому машинний код або ланцюг системних викликів. **Переповнення буфера** (англ. *buffer overflow*, від старофранцузького *buffe* — «удар, поштовх», первісно механічний пристрій для пом'якшення зіткнення залізничних вагонів, у комп'ютерах — проміжне сховище даних) — це стан порушення безпеки пам'яті, за якого запис даних за межі виділеного блоку призводить до спотворення суміжних структур керування виконанням або метаданих алокатора.

## Анатомія стекового кадру x86-64 та механіка руйнування пам'яті

Щоб зрозуміти точну фізичну послідовність перезапису пам'яті, розглянемо організацію типового стекового кадру (англ. *stack frame*, від давньоанглійського *framian* — «рухатися вперед, бути корисним, обрамляти») для функції, що виділяє буфер під вхідні дані:

:::tabs
```c
void process_user_input(int connection_fd) {
    char username_buffer[64];
    read_socket_data(connection_fd, username_buffer);
}
```
```cpp
#include <array>
#include <span>

void process_user_input(int connection_fd) {
    std::array<char, 64> username_buffer{};
    read_socket_data(connection_fd, std::span{username_buffer});
}
```
:::

Згідно зі специфікацією викликів System V AMD64 ABI, перші 6 цілочисельних аргументів передаються через регістри загального призначення (`%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`), а верхівка стека перед інструкцією `call` повинна бути вирівняна по 16 байтах. Під час компіляції компілятор GCC транслює функцію `process_user_input` у наступну послідовність машинних інструкцій:

```nasm
process_user_input:
    pushq   %rbp                ; Збереження базового покажчика кадру caller (8 байтів)
    movq    %rsp, %rbp          ; Встановлення нового базового покажчика кадру
    subq    $80, %rsp           ; Виділення 80 байтів на стеку (64 буфер + 16 вирівнювання)
    movl    %edi, -68(%rbp)     ; Збереження аргументу connection_fd
    leaq    -64(%rbp), %rax     ; Обчислення адреси username_buffer
    movq    %rax, %rsi          ; Передача другого аргументу у read_socket_data
    movl    -68(%rbp), %edi     ; Передача першого аргументу у read_socket_data
    call    read_socket_data    ; Виклик підпрограми зчитування
    leave                       ; Еквівалент: movq %rbp, %rsp; popq %rbp
    ret                         ; Вилучення Saved RIP зі стека у регістр %rip
```

Фізичне розташування даних на стеку демонструє діаграма пам'яті:

![Анатомія стекового кадру x86-64 та перезапис адреси повернення](/root/eng/sf-security/buffer-overflow-security/img/stack-frame-anatomy-and-overflow.svg)
*Анатомія стекового кадру x86-64: послідовний запис даних у локальний буфер здійснюється знизу вгору (у бік старших адрес), що дозволяє надлишковому масиву байтів перетерти збережений регістр RBP та адресу повернення RIP.*

Розташування елементів у пам'яті кадру розгортається від молодших адрес до старших наступним чином:

```
[ Молодші адреси: 0x7fffffffd000 ]  <- %rsp (Верхівка стека)
  |
  +-- username_buffer[0..63]       : 64 байти (Локальний буфер даних)
  +-- Вирівнювання компілятора     : 0..8 байтів (Padding для 16-байтного вирівнювання стека)
  +-- Збережена канарка (SSP)      : 8 байтів (якщо ввімкнено захист)
  +-- Збережений RBP (Saved RBP)   : 8 байтів (Покажчик кадру викликаючої функції)
  +-- Адреса повернення (Saved RIP): 8 байтів (Адреса наступної інструкції в caller)
  |
[ Старші адреси:  0x7fffffffe000 ]  <- Кадр викликаючої функції (Caller Frame)
```

При нормальному виконанні функція `read_socket_data` записує не більше 63 корисних символів і завершальний нульовий байт `\0`. Після виходу з функції процесор виконує інструкцію епілогу `leave`, відновлюючи базовий покажчик кадру попередньої функції, після чого інструкція `ret` повертає керування в точку виклику.

Якщо ж функція зчитування записує 88 байтів вхідного масиву `0x41414141...` (символ 'A'), пам'ять кадру зазнає наступних змін:
1. Перші 64 байти заповнюють масив `username_buffer`.
2. Наступні 8 байтів (якщо захист канаркою відсутній) затирають байтове вирівнювання.
3. Наступні 8 байтів переписують збережений `Saved RBP` значенням `0x4141414141414141`.
4. Останні 8 байтів переписують комірку `Saved RIP` значенням `0x4141414141414141`.

Коли виконується `ret`, процесор зчитує зі стека значення `0x4141414141414141`, намагається звернутися за цією невалідною адресою віртуальної пам'яті для вибірки чергової інструкції, отримує апаратну помилку блоку MMU ([Page Fault](root:hw-arch/virtual-memory)) та генерує операційній системі сигнал аварійної зупинки `SIGSEGV` (Segmentation Fault). Якщо замість випадкового сміття зловмисник помістив точну адресу розміщення власного коду або адреси корисних бібліотечних фрагментів, виникає не падіння процесу, а захоплення контролю над ходом виконання (англ. *Control Flow Hijacking*).

### Переповнення на один байт (Off-by-One та Stack Pivoting)

Критична вразливість виникає навіть тоді, коли зловмисник може вийти за межі буфера лише на один-єдиний байт (*Off-by-One Overflow*). Класичний випадок — некоректне використання циклу з умовою `<=` замість `<` або помилка в розрахунку нуль-термінатора:

:::tabs
```c
char buffer[64];
for (int i = 0; i <= 64; ++i) {
    buffer[i] = read_byte();
}
```
```cpp
#include <array>

std::array<char, 64> buffer{};
for (size_t i = 0; i <= buffer.size(); ++i) {
    // Метод .at() генерує виняток std::out_of_range на 65-й ітерації
    buffer.at(i) = read_byte();
}
```
:::

65-й байт (`buffer[64]`) потрапляє безпосередньо у молодший байт збереженого покажчика кадру `Saved RBP`. Якщо цим байтом є нуль (`0x00`), молодший байт базового покажчика кадру обнуляється. 

Коли поточна функція виконує інструкцію `leave`, відновлений регістр `%rbp` починає вказувати не на справжній стек попередньої функції, а на зміщену адресу всередині нашого вхідного буфера. Коли вже викликаюча функція спробує завершитися і виконає власний `leave; ret`, верхівка стека `%rsp` буде перекинута на повністю контрольований зловмисником буфер. Ця техніка маніпуляції стеком відома як **перемикання стека** (англ. *Stack Pivoting*).

## Небезпечні бібліотечні функції як каталізатори вразливостей

Головним джерелом уразливостей переповнення буфера в мовах C та C++ є використання стандартних функцій вводу-виводу та маніпуляції рядками з бібліотеки `libc`, які не приймають параметр максимальної місткості цільового буфера:

1. **`gets(char *s)`**: Зчитує рядок зі стандартного вводу `stdin` до символу нового рядка `\n` або `EOF`. Функція фізично не має параметра розміру буфера, через що будь-який ввід користувача, довший за виділений масив, гарантовано призводить до переповнення. Функцію офіційно визнано застарілою у стандарті C99 та повністю вилучено зі стандартів C11 і C++14.
2. **`strcpy(char *dest, const char *src)`** та **`strcat(char *dest, const char *src)`**: Копіюють або конкатенують нуль-терміновані рядки, перевіряючи лише наявність байта `0x00` у вихідному рядку `src`. Якщо довжина `src` перевищує місткість `dest`, виникає лінійне переповнення суміжних комірок пам'яті.
3. **`sprintf(char *str, const char *format, ...)`**: Форматує рядок у вихідний буфер без обмеження довжини. Специфікатори на зразок `%s` або `%d` можуть генерувати довільно велику кількість байтів, що перевищує розмір `str`.
4. **`scanf("%s", char *buf)`**: Зчитує слово, розділене пробілами, без перевірки граничної місткості `buf`. Безпечним варіантом є обов'язкове вказання максимальної ширини поля, наприклад `scanf("%63s", buf)`.

Детальна хронологія появи перших експлойтів на базі функції `gets()`, атака на мережевий демон `fingerd` під час епідемії хробака Морріса 1988 року та історична публікація маніфесту Aleph One «Smashing The Stack For Fun And Profit» викладені в [історичному нарисі про еволюцію переповнення буфера від хробака Морріса до маніфесту Aleph One](root:sf-security/buffer-overflow-security/hist-morris-and-phrack.md).

## Захисний бар'єр 1: Канарейки стека (Stack Canaries / SSP)

Першим фундаментальним автоматизованим захистом від переповнення стекового буфера став механізм **Stack Smashing Protector** (SSP), реалізований у компіляторах GCC, Clang та MSVC (під назвою `/GS`). 

Назва технології походить від історичної практики шахтарів брати з собою в підземні забої клітку з канаркою (ісп. *canario*, від лат. *canis* — «собака», за назвою островів, пташка для виявлення отруйного чадного газу): канарки мають надзвичайно високу чутливість до метану та чадного газу, тому загибель пташки сигналізувала шахтарям про смертельну небезпеку ще до того, як отрута подіє на людей.

![Механізм захисту стека канаркою (SSP)](/root/eng/sf-security/buffer-overflow-security/img/stack-canary-protection-mechanism.svg)
*Механізм перевірки канарки стека (SSP): випадкове 64-бітне значення встановлюється в пролозі перед адресою повернення і перевіряється в епілозі перед виконанням інструкції RET.*

### Механізм роботи канарки на рівні процесора

1. **Генерація еталона**: Під час запуску процесу ядро операційної системи генерує криптографічно стійке випадкове 64-бітне число ([CSPRNG](root:sf-security/csprng)) і розміщує його в структурі локального сховища потоку (Thread Local Storage, TLS). На архітектурі x86-64 доступ до цього значення здійснюється через сегментний регістр `%fs` за фіксованим зміщенням `%fs:0x28` (на 32-бітній архітектурі x86 — через регістр `%gs:0x14`).
2. **Встановлення вартового у пролозі функції**: Компілятор вставляє інструкції, які зчитують еталонне значення з регістра `%fs` і записують його на стек між локальними буферами та збереженим базовим покажчиком `Saved RBP`:
   ```nasm
   movq    %fs:0x28, %rax      ; зчитування еталонної канарки з TLS
   movq    %rax, -8(%rbp)      ; збереження канарки на стек перед Saved RBP
   xorl    %eax, %eax          ; очищення тимчасового регістра RAX
   ```
3. **Контрольна перевірка в епілозі функції**: Безпосередньо перед відновленням регістрів та виконанням інструкції `ret` компілятор знову зчитує збережене на стеку значення і порівнює його з еталоном у `%fs:0x28`:
   ```nasm
   movq    -8(%rbp), %rax      ; зчитування значення канарки зі стека
   xorq    %fs:0x28, %rax      ; порівняння через порозрядне виключне АБО
   je      .L_clean_exit       ; якщо значення збігаються (XOR == 0) — виходимо
   call    __stack_chk_fail    ; якщо значення відрізняється — аварійне завершення!
   ```
4. **Аварійна реакція**: Якщо зловмисник переповнив локальний буфер, щоб досягти адреси повернення, він неминуче переписав проміжне значення канарки. Операція `xorq` повертає ненульовий результат, перехід `je` не спрацьовує, і програма викликає системну функцію `__stack_chk_fail()`. Ця функція миттєво друкує повідомлення `*** stack smashing detected ***: terminated` і завершує процес аварійним сигналом `SIGABRT`, не дозволяючи процесору виконати інструкцію `ret`.

### Структура та типи канарок

Сучасні компілятори використовують кілька типів канарочних значень:
- **Null-байтова канарка (Terminator Canary)**: Молодший байт 64-бітної канарки фіксується нульовим значенням `0x00` (наприклад, `0x0041a9b2c3d4e5f6`). Це зупиняє вразливі строкові функції (`strcpy`, `strcat`, `sprintf`), які сприймають перший же нульовий байт як кінець рядка і припиняють копіювання до того, як атакуючий дістанеться до покажчиків керування.
- **Випадкова канарка (Random Canary)**: 56 бітів канарки обираються абсолютно випадково з високою ентропією під час ініціалізації середовища виконання.
- **Random XOR Canary**: Випадкова канарка додатково комбінується операцією XOR з адресою повернення або покажчиком кадру. Це унеможливлює атаку, навіть якщо зловмисник зміг викрасти еталонне значення канарки з іншого потоку.

### Рівні захисту компілятора GCC та Clang

Компілятори надають кілька рівнів генерації канарок:
- `-fno-stack-protector`: Повне вимкнення захисту канаркою.
- `-fstack-protector`: Додає канарку лише у функції, де є масиви символів розміром від 8 байтів або виклики динамічного виділення пам'яті на стеку `alloca()`.
- `-fstack-protector-strong`: Оптимальний промисловий стандарт (активований за замовчуванням у сучасних дистрибутивах Linux). Вставляє канарку у функції, що містять масиви будь-якого типу та розміру, структури з масивами або якщо адреса будь-якої локальної змінної передається як покажчик за межі функції.
- `-fstack-protector-all`: Додає канарочну обв'язку в усі функції без винятку, що створює незначні накладні витрати на продуктивність у критичних циклах (2–5%).

Повний перелік параметрів компілятора, розширення `_FORTIFY_SOURCE` та системні виклики керування безпекою пам'яті задокументовані у [довіднику прапорців компілятора та системних налаштувань](root:sf-security/buffer-overflow-security/api-compiler-hardening.md).

### Межі стійкості канарки та методи обходу

Хоча канарка ефективно блокує сліпі атаки на стек, вона не є абсолютною панацеєю. Існують три сценарії обходу захисту SSP:
1. **Витік пам'яті (Information Disclosure)**: Якщо в програмі присутня окрема вразливість витоку інформації (наприклад, уразливість форматування рядка *Format String* через виклик `printf(user_buf)` або неконтрольоване читання за межами масиву), зловмисник може прочитати поточне значення канарки зі стека і вставити його у свій пейлоад на відповідну позицію, пройшовши перевірку `xorq`.
2. **Побайтовий перебір у форк-моделях (Byte-by-byte Brute-Force)**: Якщо мережевий сервер обслуговує запити через виклик `fork()` без зміни адресного простору (`execve`), дочірні процеси успадковують ідентичне значення канарки батька. Зловмисник може послідовно підбирати канарку байт за байтом (усього 7 байтів по 256 варіантів = максимум 1792 запити), не змінюючи стан головного процесу.
3. **Нелінійний перезапис (Arbitrary Write)**: Якщо вразливість дозволяє записати дані за довільним покажчиком без послідовного заповнення проміжних комірок пам'яті, зловмисник може безпосередньо змінити адресу повернення або покажчик функції, не зачіпаючи значення канарки.

Покрокове математичне виведення складності побайтового перебору канарки та розрахунок ентропії наведені у [математичному розрахунку ймовірності вгадування канарки та ентропії](root:sf-security/buffer-overflow-security/math-canary-entropy-collision.md).

## Захисний бар'єр 2: Рандомізація адресного простору (ASLR) та заборона виконання даних (NX)

Навіть якщо зловмисник зумів перезаписати адресу повернення, успішна експлуатація вимагає знання точної адреси пам'яті, на яку процесор повинен передати керування. Для блокування таких дій застосовується комплекс системних механізмів:

### 1. Рандомізація розташування адресного простору (ASLR)

Механізм [ASLR](root:sf-security/aslr) (англ. *Address Space Layout Randomization*) при кожному запуску програми випадковим чином зсуває базові адреси ключових сегментів віртуальної пам'яті процесу:
- Базову адресу сегмента стека користувача;
- Базову адресу динамічної пам'яті (кучі);
- Базові адреси завантаження спільних динамічних бібліотек (`libc.so`, `libssl.so`);
- Базову адресу самого виконуваного бінарного файлу (якщо його скомпільовано з прапорцем `-fPIE -pie` як Position Independent Executable).

В умовах повної ASLR адреса розміщення шеллкоду на стеку або адреса функції `system()` у бібліотеці Glibc змінюється при кожному старті процесу. Спроба передати керування за жорстко закодованою статичною адресою з ймовірністю понад 99.999% спричиняє звернення до неіснуючої сторінки віртуальної пам'яті та негайне аварійне завершення процесу.

### 2. Заборона виконання даних (NX / DEP / W^X)

Апаратний захист [пам'яті без права виконання](root:sf-security/no-execute-memory) (англ. *No-Execute bit*, NX-біт у процесорах AMD64 та XD-біт *Execute Disable* у процесорах Intel) спирається на 63-й біт у таблиці трансляції сторінок пам'яті процесора (PTE).

Операційна система позначає всі сторінки стека та купи з правами `PROT_READ | PROT_WRITE`, але без прапорця `PROT_EXEC` (принцип **W^X**: *Write XOR Execute* — сторінка пам'яті може бути або доступною для запису, або доступною для виконання, але ніколи обома одночасно). Якщо зловмисник переповнив буфер і розмістив на стеку власний бінарний шеллкод, при спробі процесора виконати першу ж інструкцію зі стекової сторінки апаратний блок MMU генерує виняток порушення прав доступу, унеможливлюючи пряме виконання коду.

### 3. Еволюція до атак з повторним використанням коду (Code Reuse / ROP)

Впровадження біта NX призвело до зміни фундаментальної парадигми експлуатації: зловмисники припинили спроби впроваджувати новий код у пам'ять і перейшли до [атак з повторним використанням коду: return-to-libc та ROP](root:sf-security/code-reuse-attacks) (Return-Oriented Programming). В атаці ROP стек переповнюється послідовністю адрес коротких фрагментів уже наявного в пам'яті дозволеного коду програми або бібліотеки libc (так званих *ROP-гаджетів*, що закінчуються інструкцією `ret`). Ланцюжок гаджетів послідовно конфігурує системні регістри й виконує довільні системні виклики (наприклад, `mprotect` для зняття захисту NX або `execve` для запуску оболонки), повністю нівелюючи захист W^X.

Для протидії таким ланцюгам розробляються механізми [цілісності потоку керування (CFI)](root:sf-security/control-flow-integrity), які контролюють валідність усіх непрямих переходів і викликів.

## Захисний бар'єр 3: Апаратний тіньовий стек (Intel CET Shadow Stack)

Остаточним апаратним бар'єром проти атак переповнення стека та ROP стала технологія апаратного захисту потоку керування **Intel CET** (Control-flow Enforcement Technology) та її еквіваленти в архітектурі ARM (ARMv8.3-A Pointer Authentication PAC та ARMv9 GCS — Guarded Control Stack).

![Апаратний тіньовий стек Intel CET](/root/eng/sf-security/buffer-overflow-security/img/intel-cet-shadow-stack.svg)
*Апаратний тіньовий стек Intel CET: процесор підтримує ізольований від користувача стек повернень (SSP), блокуючи спроби підміни адрес винятком #CP.*

### Архітектура та принцип подвійного стека

Intel CET реалізує концепцію **подвійного стека** безпосередньо в мікрокоді процесора:
1. **Звичайний стек даних (Data Stack)**: Адресується традиційним регістром `%rsp`. Містить локальні змінні, масиви та структури даних програми. Цей стек відкритий для читання й запису звичайними інструкціями процесора (`mov`, `push`, `pop`, `memcpy`), тому саме він стає жертвою переповнення буфера.
2. **Тіньовий стек (Shadow Stack)**: Адресується спеціальним внутрішнім регістром процесора `%ssp` (Shadow Stack Pointer). Тіньовий стек зберігає **виключно адреси повернення**. Сторінки пам'яті тіньового стека позначаються в таблицях сторінок спеціальним апаратним атрибутом, який повністю блокує будь-які спроби запису через стандартні інструкції `mov` простору користувача. Запис у тіньовий стек дозволено виконувати лише мікрокоду самого процесора.

### Апаратний контроль інструкцій CALL та RET

Коли процесор з увімкненим Intel CET виконує інструкцію виклику функції `call`:
- Мікрокод записує адресу повернення на звичайний стек даних (`[%rsp] = return_addr`);
- Одночасно мікрокод записує ту саму адресу повернення на тіньовий стек (`[%ssp] = return_addr`).

Коли функція завершується і виконує інструкцію повернення `ret`:
- Процесор вилучає адресу повернення зі звичайного стека даних (`data_rip = *rsp++`);
- Одночасно процесор вилучає еталонну адресу з тіньового стека (`shadow_rip = *ssp++`);
- Апаратний компаратор процесора порівнює значення `data_rip` та `shadow_rip`.

Якщо зловмисник переповнив локальний буфер на звичайному стеку і підмінив адресу повернення на ROP-гаджет, значення `data_rip` не збігатиметься з недосяжним для переповнення `shadow_rip`. 

Процесор миттєво зупиняє виконання програми та генерує спеціальний апаратний виняток захисту керування **`#CP` (Control Protection Exception, вектор переривання 21)**. Процес аварійно ліквідується ядром операційної системи до того, як хоча б одна інструкція зловмисника буде виконана.

Додатково технологія Intel CET включає механізм **Indirect Branch Tracking** (IBT). Кожна валідна функція, на яку можна передати керування через непрямий виклик (`call *%rax` або `jmp *%rax`), повинна починатися спеціальною машинною інструкцією `ENDBR64` (`0xF3 0x0F 0x1E 0xFA`). Якщо після непрямого переходу процесор не виявляє інструкції `ENDBR64`, генерується аналогічний виняток `#CP`, що блокує стрибки всередину функцій або на випадкові байти інструкцій.

## Переповнення буфера в динамічній пам'яті (Heap Buffer Overflow)

Переповнення буфера не обмежується стеком: аналогічне порушення меж виникає і в динамічній пам'яті процесу — **кучі** (англ. *heap*, від давньоанглійського *hēap* — «купа, нагромадження»).

На відміну від стека, де безпосередньо за буфером розташовані покажчики керування виконанням (RBP/RIP), динамічна пам'ять керується складним бібліотечним менеджером пам'яті — алокатором (наприклад, `ptmalloc2` у Glibc, `jemalloc` у FreeBSD/Android, або Windows Heap Manager).

### Анатомія чанка Glibc malloc

Алокатор розбиває виділену в операційної системи пам'ять на неперервні блоки — **чанки** (англ. *chunks*):

![Переповнення в кучі та захисне вилучення (Safe Unlinking)](/root/eng/sf-security/buffer-overflow-security/img/heap-chunk-corruption-and-unlink.svg)
*Анатомія чанка glibc malloc та механізм Safe Unlinking: перевірка кругової цілісності списку блокує примітив довільного запису через пошкоджені покажчики fd/bk.*

Кожен чанк містить службовий заголовок та область даних користувача:
1. `prev_size` (8 байтів на x86-64): розмір попереднього суміжного чанка в пам'яті (використовується для зворотного злиття вільних блоків).
2. `size` (8 байтів): розмір поточного чанка. Оскільки всі чанки вирівнюються по 16 байтів, молодші 3 біти поля `size` процесором не використовуються для адресації і слугують прапорцями стану:
   - Біт 0 (`PREV_INUSE`, `P`): 1 — попередній чанк зайнятий, 0 — вільний;
   - Біт 1 (`IS_MMAPPED`, `M`): 1 — виділено через прямий системний виклик `mmap`;
   - Біт 2 (`NON_MAIN_ARENA`, `A`): 1 — виділено з арени додаткового потоку.
3. **Область корисного навантаження (User Data)**: байти, що повертаються користувачеві викликом `malloc(size)`.
4. **Покажчики зв'язного списку (якщо чанк звільнено через `free()`)**:
   - `fd` (Forward Pointer, 8 байтів) — покажчик на наступний вільний чанк у біні;
   - `bk` (Backward Pointer, 8 байтів) — покажчик на попередній вільний чанк у двозв'язному списку.

### Механіка псування кучі та класична атака Unlink

Якщо програма виділяє два суміжних блоки пам'яті `char *a = malloc(64)` та `char *b = malloc(64)`, і під час запису в буфер `a` переповнює його на 80 байтів, надлишкові байти врізаються у службовий заголовок чанка `b`.

Зловмисник може навмисно підробити прапорець `PREV_INUSE = 0` та поля `fd`/`bk` у звільненому чанку. Коли програма викликає `free()`, алокатор намагається об'єднати сусідні вільні блоки у великий суцільний блок, вилучаючи чанк із двозв'язного списку за допомогою макроса `unlink()`:

:::tabs
```c
// Класичний вразливий алгоритм вилучення з двозв'язного списку Glibc:
#define unlink_vulnerable(P, BK, FD) { \
    FD = P->fd;                         \
    BK = P->bk;                         \
    FD->bk = BK;                        \
    BK->fd = FD;                        \
}
```
```cpp
// Концептуальна модель вилучення вузла в C++ з контролем цілісності покажчиків:
struct ChunkNode {
    ChunkNode* fd{nullptr};
    ChunkNode* bk{nullptr};
};

bool unlink_safe(ChunkNode* p) noexcept {
    if (!p || !p->fd || !p->bk) return false;
    // Перевірка цілісності: суміжний вузол повинен посилатися назад на поточний
    if (p->fd->bk != p || p->bk->fd != p) {
        return false; // Пошкодження зв'язного списку виявлено
    }
    p->fd->bk = p->bk;
    p->bk->fd = p->fd;
    return true;
}
```
:::

У старіших версіях Glibc (до 2.3.6) ця операція сліпо записувала адресу `BK` у комірку пам'яті за адресою `FD + offset`, і навпаки. Підробляючи поля `fd` та `bk`, зловмисник отримував найпотужніший примітив експлуатації — **довільний запис 8 байтів за довільною адресою** (англ. *Write-What-Where Primitive*), що дозволяло переписати таблицю GOT (Global Offset Table), покажчики обробників сигналів або таблиці віртуальних методів C++ ([Use-After-Free](root:sf-security/use-after-free)).

### Захисне вилучення (Safe Unlinking) та маскування покажчиків (Safe Linking)

Для ліквідації цього класу атак у сучасні алокатори впроваджено обов'язкову перевірку взаємної узгодженості двозв'язного списку — **Safe Unlinking**:

:::tabs
```c
// Сучасна перевірка Safe Unlinking у макросі unlink() бібліотеки Glibc:
if (__builtin_expect(P->fd->bk != P || P->bk->fd != P, 0)) {
    malloc_printerr("corrupted double-linked list");
}
```
```cpp
// Еквівалентна верифікація цілісності в C++ з використанням fail-fast семантики:
if (p->fd->bk != p || p->bk->fd != p) [[unlikely]] {
    std::terminate(); // Негайне аварійне завершення без розкручування стека
}
```
:::

Перед зміною будь-яких покажчиків алокатор перевіряє суворе математичне правило: якщо чанк `P` вказує вперед на чанк `FD` (`P->fd == FD`), то зворотний покажчик цього чанка обов'язково повинен посилатися назад на `P` (`FD->bk == P`). Аналогічна симетрична умова перевіряється і для покажчика `P->bk`. Якщо зловмисник змінив покажчики на довільні адреси пам'яті, кругова рівність порушується, і алокатор негайно аварійно завершує виконання процесу через виклик `abort()`, блокуючи довільний запис у пам'ять.

Для захисту швидких одновз'язних списків (tcache та fastbins) у Glibc 2.32 додано технологію **Safe Linking**: покажчик `next` на наступний вільний блок зберігається в пам'яті не у відкритому вигляді, а шифрується порозрядним XOR з випадковим зсувом адреси самого покажчика:

```
зашифрований_покажчик
= P->next ⊕ (Адреса_комірки >> 12)    [маскування покажчика випадковими бітами ASLR]
```

Оскільки зсув `>> 12` використовує випадкові старші біти сторінки, згенеровані ASLR, зловмисник не може переписати покажчик `next` на довільну адресу без попереднього повного розкриття розкладки пам'яті процесу.

## Діагностичні санітайзери: тіньова пам'ять AddressSanitizer (ASan)

Якщо компіляторні канарки перевіряють стан пам'яті лише перед поверненням із функції, то діагностичний інструмент **AddressSanitizer** (ASan, прапорець `-fsanitize=address`) виявляє несанкціонований доступ безпосередньо в момент виконання некоректної інструкції запису або читання.

Архітектура ASan базується на концепції **тіньової пам'яті** (англ. *Shadow Memory*): кожні 8 байтів віртуальної пам'яті процесу відображаються на 1 байт тіньового простору за фіксованою адресною формулою:

```
тіньова_адреса
= (пряма_адреса >> 3) + 0x7fff8000    [зсув адресного простору x86-64]
```

Значення байта в тіньовій пам'яті кодує статус відповідних 8 байтів: значення `0` означає, що всі 8 байтів доступні для читання й запису; значення від `1` до `7` вказує кількість валідних початкових байтів; від'ємні значення позначають заблоковані «отруєні» зони (*Poisoned Redzones*).

Під час виділення будь-якого буфера на стеку або в кучі компілятор та алокатор оточують масив червоними зонами розміром 16–32 байти. Перед кожною інструкцією доступу до пам'яті компілятор вставляє швидку перевірку тіньового байта:

```nasm
movq    %rax, %rdi
shrq    $3, %rdi            ; ділення адреси на 8
movb    0x7fff8000(%rdi), %cl ; зчитування тіньового байта
testb   %cl, %cl
jne     .L_asan_report_error ; якщо пам'ять отруєна — негайний звіт про помилку!
```

Це дозволяє ловити вихід за межі масивів навіть на 1 байт усередині тіла функції, не чекаючи виклику `ret`, що робить ASan незамінним інструментом для фаззинг-тестування та динамічного аналізу програм.

## Захищені патерни програмування та безпечні абстракції

Повна ліквідація переповнень буфера на етапі написання вихідного коду вимагає фундаментальної відмови від застарілих патернів прямого керування сирою пам'яттю.

Нижче наведено практичний приклад переходу від небезпечного C-стилю до сучасних захищених абстракцій C++20/C++23:

:::tabs
```c
#include <stdio.h>
#include <string.h>
#include <stdbool.h>

#define USERNAME_MAX_CAPACITY 64

// Захищена функція копіювання з контролем меж буфера
bool copy_username_bounded(char *dest, size_t dest_capacity, const char *src) {
    if (!dest || !src || dest_capacity == 0) {
        return false;
    }

    // Використання snprintf гарантує запис не більше dest_capacity байтів
    // і обов'язкову наявність завершального нуль-термінатора '\0'
    int written = snprintf(dest, dest_capacity, "%s", src);

    // Якщо довжина джерела перевищує або дорівнює місткості — відбулося обрізання
    if (written < 0 || (size_t)written >= dest_capacity) {
        // Очищаємо цільовий буфер для запобігання використанню обрізаних даних
        dest[0] = '\0';
        return false;
    }

    return true;
}
```
```cpp
#include <iostream>
#include <string_view>
#include <array>
#include <span>
#include <expected>
#include <algorithm>

constexpr size_t UsernameMaxCapacity = 64;

enum class CopyError {
    BufferOverflow,
    InvalidInput
};

// Ідіоматична функція C++23 з використанням std::span та std::expected
template <size_t N>
std::expected<void, CopyError> copy_username_safe(
    std::array<char, N>& destination, 
    std::string_view source
) noexcept {
    if (source.empty()) {
        return std::unexpected(CopyError::InvalidInput);
    }

    // std::string_view зберігає розмір, унеможливлюючи сканування довільної пам'яті
    if (source.size() >= N) {
        return std::unexpected(CopyError::BufferOverflow);
    }

    std::copy(source.begin(), source.end(), destination.begin());
    destination[source.size()] = '\0';
    return {};
}
```

> 🔧 **Навіщо це.** У промисловій розробці безпека пам'яті досягається ешелонованим захистом (*Defense-in-Depth*): захищені абстракції мови усувають помилки в коді, компіляторні канарки блокують помилки в залишках низькорівневих модулів, а апаратний Shadow Stack та ASLR ядра захищають систему в разі виявлення вразливостей нульового дня в сторонніх залежностях.

## Підсумок архітектури захисту від переповнення

Еволюція захисту від переповнення буфера пройшла шлях від повної вразливості систем кінця XX століття до трирівневої сучасної фортеці:

1. **Рівень мови та коду**: Використання мов з автоматичним контролем меж (Rust, modern C++, Go) або обмежених функцій (`snprintf`, `std::span`).
2. **Рівень компілятора**: Stack Canaries (`-fstack-protector-strong`), розширений аналіз меж об'єктів (`-D_FORTIFY_SOURCE=3`) та розділення стеків (*SafeStack*).
3. **Рівень ядра та апаратури**: Повна рандомізація адресного простору (ASLR / PIE), нездійсненність виконання стека (NX-біт W^X) та апаратний тіньовий стек адрес повернення (Intel CET / ARM GCS).

Поєднання цих рівнів перетворює класичну критичну атаку захоплення віддаленого контролю на контрольовану локальну аварійну зупинку процесу, забезпечуючи надійну стійкість критичної інфраструктури.
