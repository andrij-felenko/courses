# 🔌 Порівняльний інженерний аналіз: Файл на диску, USB-токен, Мережевий HSM та Хмарний KMS

Вибір місця зберігання та виконання операцій із приватним криптографічним ключем визначає не лише ступінь стійкості системи до зловмисників, але й її пропускну здатність, затримку (Latency), операційні витрати, складність аварійного відновлення (Disaster Recovery) та юридичну відповідність регуляторним стандартам (PCI-DSS, eIDAS, FIPS, ISO 27001).

У цій вставці наведено всебічний інженерний аналіз чотирьох основних архітектурних парадигм розміщення ключів:
1. **Локальний файл на хості («Ноутбук Петра» / Сервер ОС)**: Зберігання в файловій системі (`~/.ssh/`, `/etc/ssl/private/`, PEM/PKCS#8 на диску).
2. **Персональний апаратний токен / Смарт-картка (USB Token / Secure Element)**: YubiKey, Nitrokey, смарт-картки JavaCard із шиною CCID/APDU.
3. **Мережевий апаратний модуль безпеки (Dedicated Network HSM)**: Автономні стоєчні пристрої класу Thales Luna, Utimaco CryptoServer, Entrust nShield, YubiHSM.
4. **Хмарний KMS / Керований Cloud HSM (Cloud KMS / HSM-as-a-Service)**: AWS Key Management Service (KMS), Google Cloud KMS / Cloud HSM, Azure Key Vault Managed HSM.

## 2. Глибокий аналіз моделей загроз

### 2.1. Чому файловий ключ на диску — це «міна сповільненої дії»
Зберігання закритого ключа у вигляді файлу `private.pem` на диску є найпростішим для розробника, але катастрофічним з погляду безпеки:
- **Атака на пам'ять**: Коли процес запускає TLS-сервер або підписує бінарний файл, ключ завантажується в пам'ять процесу. Будь-яка вразливість переповнення буфера (Heartbleed), некоректна обробка винятків із генерацією core dump або зчитування `/proc/$PID/mem` суперкористувачем віддає зловмиснику повний контроль.
- **Безслідне клонування**: Якщо хакер викрав `id_ed25519` або `cakey.pem`, оригінальний власник навіть не знає про витік, доки від його імені не буде випущено фальшивий сертифікат чи підроблено підпис під прошивкою.

### 2.2. USB-токени: Ідеальний баланс для розробника, бар'єр для автоматизації
Апаратні токени (YubiKey, смарт-картки) вирішують проблему витоку завдяки фізичній неможливості зчитування ключа (`CKA_EXTRACTABLE=FALSE`):
- **Перевага**: Вимагають фізичної присутності людини (дотик до металевого контакту токена). Навіть якщо робоча станція розробника заражена складним трояном із правами адміністратора, шкідлива програма не зможе непомітно підписати шкідливий коміт без явного дотику користувача.
- **Обмеження**: Через низьку швидкість криптопроцесора (до 50 підписів/с) та вимогу фізичного підключення до USB-порту токен неможливо використати для високонавантаженого веб-сервера чи корпоративного шлюзу автентифікації.

### 2.3. Мережеві HSM: Корпоративна фортеця високої пропускної здатності
Мережевий HSM (Hardware Security Module) є спеціалізованим броньованим сервером для датацентрів:
- **Перевага**: Забезпечує десятки тисяч операцій підпису на секунду завдяки спеціалізованим ASIC/FPGA криптоакселераторам. Захищений корпус із мікропровідною сіткою миттєво знищує (нуліфікує) ключі при спробі свердління корпусу чи охолодження кристала рідким азотом. Доступ до кореневих операцій вимагає присутності кількох офіцерів безпеки за схемою m-з-n.
- **Обмеження**: Екстремальна вартість заліза (десятки тисяч доларів), складність оновлення прошивки та високі вимоги до інфраструктури (серверні стійки, резервне живлення, фізичний периметр).

### 2.4. Хмарні KMS: Еластичність та аудит ціною делегування межі довіри
Хмарні сервіси (AWS KMS, GCP KMS, Azure Key Vault) надають HSM у вигляді керованого сервісу (Hardware-as-a-Service):
- **Перевага**: Повна інтеграція з ролями та політиками IAM, що дозволяє надавати мікросервісам права на підпис без видачі самого ключа. Автоматичний детальний аудит кожного звернення в режимі реального часу.
- **Обмеження**: Залежність від політик доступності хмарного провайдера (Vendor Lock-in), юридичні обмеження на розміщення ключів за межами суверенної держави (Data Sovereignty) та плата за кожен мережевий виклик.

## 3. Резервне копіювання, міграція та аварійне відновлення (Disaster Recovery)

Одним із найскладніших інженерних викликів апаратної криптографії є парадокс надійності: як створити резервну копію ключа, якщо сам апаратний чип проектувався з категоричною забороною на вивантаження секретів?

### 3.1. Парадокс клонування USB-токенів
Оскільки персональні смарт-картки та токени YubiKey фізично не дозволяють експортувати згенерований приватний ключ, створити точну «резервну копію» токена після генерації пари ключів неможливо. Якщо інженер губить свій єдиний токен, доступ до систем втрачається назавжди.

Правильна інженерна практика для персональних токенів будується на принципі **паралельної реєстрації кількох незалежних ключів**:
1. Інженер купує два ідентичні фізичні токени: основний (Primary) та резервний (Backup).
2. На кожному токені генерується **власна унікальна пара ключів** зі своїми відкритими ключами `PubKey_Primary` та `PubKey_Backup`.
3. Усі цільові сервіси (сервери SSH у файлі `authorized_keys`, акаунти GitHub/GitLab, системи корпоративного VPN) налаштовуються на довіру **обом** відкритим ключам одночасно.
4. Резервний токен замикається у вогнестійкому сейфі. При втраті основного токена інженер активує резервний і негайно видаляє відкритий ключ втраченого токена з усіх систем доступу.

### 3.2. Домени безпеки та загорнуті бекапи мережевих HSM (Key Wrapping)
У корпоративних мережевих HSM втрата заліза без можливості відновлення означала б банкрутство банку або параліч національної системи електронних паспортів. Для безпечного резервного копіювання виробники HSM (Thales, Utimaco, Entrust) реалізують концепцію **доменів безпеки (Security Domains)**:

```
[ Джерельний HSM 1 ]                                [ Цільовий HSM 2 ]
┌────────────────────────┐                        ┌────────────────────────┐
│ Внутрішній ключ K      │                        │ Відновлений ключ K     │
│ (CKA_EXTRACTABLE=FALSE)│                        │ (CKA_EXTRACTABLE=FALSE)│
│           │            │                        │           ▲            │
│   Апаратне огортання   │                        │   Апаратне розгортання │
│   AES-KWP(K, MKEK)     │                        │   AES-KWP(C, MKEK)     │
│           ▼            │                        │           │            │
│ Зашифрований блоб C    │── Захищений бекап ────>│ Зашифрований блоб C    │
└────────────────────────┘  (на флешці чи диску)  └────────────────────────┘
            ▲                                                 ▲
            │           [ Спільний Master KEK ]               │
            └─────────── (Кворум смарт-карток m-of-n) ────────┘
```

1. Під час ініціалізації кластера HSM генерується спільний ключ шифрування домену — **Master Key Encryption Key (MKEK)** або *Ключ перенесення домену*.
2. Цей MKEK розділяється за схемою Шаміра на n часток і записується на смарт-картки офіцерів безпеки (Admin/PED Cards).
3. Коли адміністратор виконує резервне копіювання, внутрішній криптопроцесор HSM шифрує робочі приватні ключі за алгоритмом AES Key Wrap (NIST SP 800-38F / RFC 5649) за допомогою MKEK і вивантажує зашифрований бінарний блоб на зовнішній носій.
4. Отриманий файл бекапу є повністю криптографічно безпечним: зловмисник, що викрав файл, не може витягти з нього жодного ключа без фізичного доступу до іншого HSM того ж виробника та присутності кворуму m-з-n смарт-карток для введення MKEK.

### 3.3. Багаторегіональна реплікація у хмарних KMS
Хмарні провайдери вирішують проблему відмовостійкості на рівні архітектури датацентрів:
- Кожен мастер-ключ KEK усередині регіону (наприклад, `eu-central-1`) автоматично реплікується між трьома незалежними зонами доступності (Availability Zones), кожна з яких має власний фізичний пул HSM.
- Для захисту від катастрофічних збоїв цілих регіонів впроваджуються **багаторегіональні ключі (Multi-Region Keys)**: хмарний сервіс безпечно синхронізує криптографічний матеріал KEK між різними географічними датацентрами (наприклад, Франкфурт та Ірландія) через виділені апаратні тунелі без розкриття відкритого тексту ключів.

## 4. Фінансове та операційне моделювання (TCO)

Порівняння сукупної вартості володіння (Total Cost of Ownership, TCO) на горизонті 3–5 років демонструє чіткий інженерний вододіл між рішеннями:

1. **Файловий підхід (0$ CapEx / 0$ OpEx)**: Має нульову початкову вартість, але несе колосальні потенційні фінансові збитки у разі компрометації (штрафи GDPR, відкликання ліцензій платіжних систем, втрата репутації).
2. **Персональні токени ($50–$100 на розробника)**: Разова інвестиція з практично нульовими операційними витратами. Забезпечує максимальну окупність інвестицій у безпеку для захисту доступу до репозиторіїв та серверів інфраструктури.
3. **Фізичні мережеві HSM ($25 000 – $100 000+ CapEx + 20% щорічної підтримки)**: Вимагають значних капітальних витрат, спеціалізованого персоналу для обслуговування серверних стійок та фізичних церемоній. Окупаються лише у великих банках, телеком-операторах та урядових установах із мільйонами криптографічних транзакцій на добу.
4. **Хмарні KMS (0$ CapEx / $1–$500+ щомісяця OpEx)**: Оптимальний вибір для 90% сучасних цифрових бізнесів. Надають безпеку корпоративного рівня без початкових капіталовкладень, масштабуючись пропорційно реальному навантаженню застосунків.

## 5. Інженерний алгоритм вибору

```
Яке призначення приватного ключа?
│
├── Особиста ідентифікація людини (SSH, Git-коміти, доступ до адмінки)
│   └──> USB-токен (YubiKey / FIDO2 / PIV смарт-картка)
│
├── Автоматизована збірка та підпис артефактів у CI/CD
│   ├── Хмарна інфраструктура (AWS/GCP/Azure)
│   │   └──> Хмарний KMS з OIDC-автентифікацією збирача (Short-lived tokens)
│   └── Локальний On-Premises конвеєр
│       └──> Мережевий HSM / YubiHSM із викликом через PKCS#11
│
├── Високонавантажений TLS Edge / Банківський процесинг / Кореневий CA
│   ├── Вимоги FIPS 140-3 Level 3/4 та повний контроль над залізом
│   │   └──> Фізичний Мережевий HSM (Thales Luna / Utimaco) з кворумом m-of-n
│   └── Повністю хмарне розгортання
│       └──> Cloud KMS Dedicated HSM / Cloud HSM
│
└── Тимчасовий тестовий стенд розробника (Staging / Mock)
    └──> Локальний програмний емулятор HSM (SoftHSM2)
```
