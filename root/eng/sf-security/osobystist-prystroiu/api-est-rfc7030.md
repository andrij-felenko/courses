# 📋 Протокол EST (RFC 7030): Специфікація кінцевих точок та форматів запитів

Протокол EST (Enrollment over Secure Transport, RFC 7030) регламентує клієнт-серверний інтерфейс автоматизованого випуску, поновлення та управління життєвим циклом цифрових сертифікатів X.509 для вбудованих пристроїв та мережевого обладнання поверх захищеного з'єднання HTTPS (TLS з обов'язковою взаємною автентифікацією mTLS). 

На відміну від застарілих протоколів на кшталт SCEP (Simple Certificate Enrollment Protocol), де повідомлення шифрувалися поверх незахищеного HTTP за допомогою складних вкладених конвертів PKCS#7 і вимагали попередньо узгоджених статичних паролів (Challenge Passwords), протокол EST повністю делегує шифрування та автентифікацію транспортному рівню TLS. Це суттєво зменшує обсяг кодової бази мікроконтролерів, усуває надлишкове подвійне шифрування та забезпечує пряму й прозору інтеграцію з фабричними апаратними сертифікатами стандарту IEEE 802.1AR.

Усі операції протоколу EST виконуються через стандартизований префікс шляху уніфікованого ідентифікатора ресурсів:
`https://<est-server>[:<port>]/.well-known/est/<operation>`

---

## 1. Реєстр кінцевих точок EST та їхнє призначення

| Метод HTTP | Шлях операції | Призначення | Тіло запиту (MIME) | Тіло відповіді (MIME) |
|---|---|---|---|---|
| `GET` | `/.well-known/est/cacerts` | Отримання ланцюжка довірених кореневих та проміжних сертифікатів CA | Порожнє | `application/pkcs7-mime; smime-type=certs-only` |
| `POST` | `/.well-known/est/simpleenroll` | Первинний випуск сертифіката пристрою (LDevID) на основі фабричного IDevID | `application/pkcs10` (CSR у кодуванні Base64) | `application/pkcs7-mime; smime-type=certs-only` |
| `POST` | `/.well-known/est/simplereenroll` | Планове поновлення чинного сертифіката пристрою до закінчення терміну дії | `application/pkcs10` (CSR у кодуванні Base64) | `application/pkcs7-mime; smime-type=certs-only` |
| `POST` | `/.well-known/est/serverkeygen` | Випуск сертифіката з генерацією пари ключів на боці сервера (опціонально) | `application/pkcs10` | `multipart/mixed` (PKCS#7 сертифікат + PKCS#8 зашифрований ключ) |
| `GET` | `/.well-known/est/csrattrs` | Запит вимог сервера до змісту та розширень у запиті на сертифікат (CSR) | Порожнє | `application/csrattrs` (ASN.1 послідовність OID) |

## 2. Послідовність та детальний розбір операцій

Кожна операція протоколу виконує строго визначену фазу в життєвому циклі криптографічної ідентичності.

### 2.1. Отримання сертифікатів центру сертифікації (`/cacerts`)

Ця кінцева точка є першим кроком під час ініціалізації пристрою в новій мережі. Пристрій надсилає HTTP-запит `GET` без тіла для отримання повного сертифікатного ланцюжка довіреного CA:

```http
GET /.well-known/est/cacerts HTTP/1.1
Host: pki.internal.corp:8443
User-Agent: embedded-device-est/1.0
```

Сервер повертає структуру CMS / PKCS#7 у так званому виродженому форматі (`certs-only`), яка містить лише сертифікати X.509 без цифрових підписів чи зашифрованих даних:

```http
HTTP/1.1 200 OK
Content-Type: application/pkcs7-mime; smime-type=certs-only
Content-Transfer-Encoding: base64
Content-Length: 2156

MIAGCSqGSIb3DQEHAqCAMIACAQExADALBgkqhkiG9w0BBwGggDCCBGIwggNKoAMCAQICAQEw
DQYJKoZIhvcNAQELBQAwVzELMAkGA1UEBhMCVVMxFDASBgNVBAoMC0V4YW1wbGUgSW5jMSIw
... [Base64 закодований сертифікатний ланцюжок CA] ...
AAAA
```

Клієнт повинен перевірити цілісність отриманого ланцюжка. Якщо з'єднання TLS встановлювалося з перевіркою кореневого сертифіката (Implicit Trust Anchor), клієнт перевіряє, що кореневий CA у відповіді збігається з сертифікатом, який використовувався для автентифікації EST-сервера. Отриманий ланцюжок записується у Flash-пам'ять пристрою як новий перелік довірених коренів (Trust Store).

### 2.2. Запит атрибутів сертифіката (`/csrattrs`)

Перед генерацією локальної пари ключів та формуванням запиту CSR клієнт може запитати у сервера перелік обов'язкових полів. Це дозволяє серверу вказати, які криптографічні алгоритми, типи еліптичних кривих або розширення X.509 він вимагає.

Сервер повертає структуру ASN.1 `CsrAttrs`:

```asn1
CsrAttrs ::= SEQUENCE SIZE (0..MAX) OF AttrOrOID

AttrOrOID ::= CHOICE {
   oid        OBJECT IDENTIFIER,
   attribute  Attribute {{ CsrAttrSet }}
}
```

Типові обов'язкові об'єктні ідентифікатори (OID) включають:
- `1.2.840.10045.4.3.2` — вимога підпису алгоритмом `ecdsa-with-SHA256` (NIST P-256);
- `1.3.6.1.5.5.7.7.1` — розширення `id-pe-authorityInfoAccess` для підтримки протоколу перевірки статусу OCSP;
- `2.5.29.17` — обов'язкове заповнення поля `subjectAltName` (SAN) для прив'язки ідентифікатора пристрою.

---

### 2.3. Первинна реєстрація сертифіката (`/simpleenroll`)

Після генерації пари ключів `(LDevID_PrivKey, LDevID_PubKey)` всередині Secure Element пристрій створює запит PKCS#10 (CSR). CSR містить відкритий ключ `LDevID_PubKey` та підписується відповідним `LDevID_PrivKey` — це реалізує механізм доказу володіння (Proof-of-Possession, PoP).

Запит надсилається методом `POST` у захищеному каналі mTLS, де клієнт автентифікований своїм фабричним сертифікатом IDevID:

```http
POST /.well-known/est/simpleenroll HTTP/1.1
Host: pki.internal.corp:8443
Content-Type: application/pkcs10
Content-Transfer-Encoding: base64
Content-Length: 684

MIICijCCAXICAQAwTjELMAkGA1UEBhMCVUEyFDASBgNVBAoMC0RldmljZU5ldHcxKTAnBgNV
BAMMIGdhdGV3YXktZGUyZi00YjBhLTg4Y2YtNmY3YmFkMjAxM2YwWTATBgcqhkjOPQIBBggq
hkjOPQMBBwNCAASt37w8x1U8fH8+k2c6v+...
... [Base64 закодований DER PKCS#10 CSR] ...
```

На стороні EST-сервера (Registration Authority, RA) виконується комплексна перевірка:
1. Перевіряється валідність клієнтського сертифіката IDevID за ланцюжком сертифікатів виробника обладнання;
2. З сертифіката IDevID зчитується апаратний серійний номер (поле SAN `HardwareModuleName`) та звіряється зі списком дозволених до онбордингу пристроїв;
3. Перевіряється математичний підпис всередині CSR, щоб переконатися, що клієнт володіє приватним ключем для нового LDevID;
4. Якщо перевірки успішні, EST-сервер надсилає запит до внутрішнього CA на випуск сертифіката LDevID і повертає його у форматі PKCS#7.

---

### 2.4. Планове поновлення сертифіката (`/simplereenroll`)

Коли термін дії чинного сертифіката LDevID наближається до завершення (наприклад, залишилося менше 20% часу валідності), пристрій ініціює операцію поновлення через кінцеву точку `/simplereenroll`.

Семантично цей запит ідентичний `/simpleenroll`, але має ключову відмінність у процедурі автентифікації на транспортному рівні:
- Під час рукостискання mTLS пристрій пред'являє свій **чинний сертифікат LDevID**, а не фабричний IDevID;
- Пристрій може як згенерувати нову пару ключів у Secure Element (рекомендовано), так і сформувати CSR для наявного відкритого ключа;
- Сервер перевіряє, що запит надійшов від легітимного, ще не відкликаного вузла системи, та випускає оновлений сертифікат LDevID із продовженим терміном дії.

## 3. Коди стану HTTP та протокольні крайові випадки

| Код стану | Семантичне значення | Дія клієнтського автомата станів |
|---|---|---|
| `200 OK` | Операцію успішно виконано. Тіло містить сертифікати PKCS#7. | Зберегти сертифікат у захищену пам'ять (Secure Element). |
| `202 Accepted` | Запит прийнято в чергу, випуск потребує підтвердження оператора. | Зчитати заголовок `Retry-After: <секунди>`, встановити таймер і повторити `POST` запит із тим самим CSR. |
| `400 Bad Request` | Некоректний формат CSR, непідтримувана крива або помилка ASN.1. | Зафіксувати помилку конфігурації, перевірити параметри генерації ключів за `/csrattrs`. |
| `401 Unauthorized` | Відсутній сертифікат клієнта у mTLS або не пройдено авторизацію. | Перевірити працездатність Secure Element та наявність IDevID/LDevID. |
| `403 Forbidden` | Сертифікат клієнта відкликано (CRL/OCSP) або пристрій видалено з білого списку. | Заблокувати спроби зв'язку, перевести пристрій у стан аварійної ізоляції. |
| `503 Service Unavailable` | EST-сервер не може з'єднатися з внутрішнім HSM або бекенд-CA. | Запустити повторні спроби за алгоритмом експоненційного відступу (Exponential Backoff з рандомізованим джитером). |

У разі повернення коду `202 Accepted` клієнт повинен суворо дотримуватися вказаного інтервалу затримки. Занадто часті повторні опитування сервера будуть відхилені як надмірне навантаження або атака відмови в обслуговуванні.

## 4. Порівняння з іншими протоколами онбордингу

1. **SCEP (Simple Certificate Enrollment Protocol)**: застарілий протокол, створений спочатку для мережевого обладнання Cisco. Використовує складне вкладене шифрування PKCS#7 поверх звичайного незахищеного HTTP. Не підтримує еліптичні криві в базових версіях і вимагає попередньо узгодженого спільного секрету (Challenge Password).
2. **ACME (RFC 8555, Automatic Certificate Management Environment)**: домінує у публічній веб-інфраструктурі (Let's Encrypt). Вимагає проходження викликів HTTP-01 або DNS-01, що практично неможливо реалізувати для вбудованих IoT-пристроїв, які перебувають за трансляцією мережевих адрес (NAT) і не мають публічних доменних імен або статичних IP-адрес.
3. **BRSKI (RFC 8995, Bootstrapping Remote Secure Key Infrastructure)**: є потужною архітектурною надбудовою над EST. Додає протокол обміну криптографічними ваучерами (Voucher Artifacts) за стандартом RFC 8366 через хмарну службу координації виробника (MASA — Manufacturer Authorized Signing Authority). Це дозволяє повністю автоматизувати впровадження нового пристрою з нульовим дотиком (Zero-Touch Provisioning) у повністю недовірених локальних мережах без потреби ручного налаштування IP-адрес чи сертифікатів.
4. **EST-coaps (RFC 9148)**: спеціальна адаптація протоколу EST для мікроконтролерів із жорстким обмеженням обчислювальних ресурсів та оперативної пам'яті (RAM < 32 КБ). Працює поверх легкого транспортного протоколу CoAP та DTLS із використанням компактного бінарного кодування CBOR замість важких текстових заголовків HTTP.
