# ⚙️ Вхід: від реєстрації до сесії, з пасткою на кожному кроці

## Задача

Теорія входу вкладається в один рядок: доведи, ким ти є, і сервер видасть тобі жетон, який далі заступить пароль. Але між цим рядком і робочим кодом лежить шість кроків, і кожен виглядає дрібницею — «захешуй пароль», «згенеруй токен», «постав cookie» — доки не приглянешся. Бо за кожним стоїть конкретний напад, і майже кожен із цих нападів колись спрацював на справжньому сайті з мільйонами користувачів.

Збудуймо весь шлях від початку до кінця: людина реєструється, згодом входить, і далі лишається впізнаною, не пред'являючи пароль щоразу. Шість кроків — реєстрація, перевірка, видача жетона, його зберігання, cookie, термін і ротація. Для кожного — робочий код трьома мовами, якими справді пишуть бекенди (TypeScript на Node, Python, Go), і поряд та сама пастка, у яку легко впасти й дорого потім вибиратися.

## Ідея: два секрети, а не один

Крізь усі шість кроків проходить одна думка, і якщо тримати її в голові, кожне рішення стає майже очевидним. Пароль — це секрет із жалюгідно малою ентропією: його вигадала людина, а не машина. Тому пароль не можна ні зберігати як є, ні ганяти дротом частіше, ніж конче треба. Його пред'являють рівно один раз, звіряють обережно — так, щоб сама перевірка не проговорилася зайвого, — і негайно міняють на **інший** секрет: довгий, машинно-випадковий жетон, який уже не страшно возити туди-сюди в кожному запиті.

Уся решта роботи — оберігати цей жетон: тримати в базі його відбиток, а не його самого; віддавати браузеру так, щоб не вкрали й не підсунули; і не дати йому жити вічно. Ключ до всього — **розрізняти два секрети**, бо їх постійно плутають, і плутанина коштує. Пароль слабкий і довговічний; жетон сильний і тимчасовий. Звідси й різне поводження на кожному кроці — аж до того, що навіть хешують їх різними функціями з протилежних міркувань.

## Крок 1. Реєстрація: зробити з пароля те, що не страшно зберігати

Реєстрація — єдина мить, коли сервер бачить пароль і мусить вирішити, у якому вигляді його пам'ятати. Відповідь відома: не пам'ятати зовсім. Зберігають не пароль, а його однобічний хеш — відбиток, з якого пароль назад не витягнеш, але який щоразу той самий для того самого пароля.

Тільки хеш хешу не рівня, і тут криється перша розвилка. Швидка функція на кшталт SHA-256 — помилка, і саме тому, що вона швидка: сучасна відеокарта проганяє мільярди SHA-256 за секунду, а отже, перебирає короткий людський пароль за години. Проти цього беруть функцію, яку зробили повільною й ненажерливою до пам'яті **навмисно** — argon2id.

> 🔧 **Навіщо це.** Чому хеш пароля має бути повільним, звідки береться сіль, що ламає заздалегідь пораховані таблиці, і як параметри задають ціну однієї спроби — розбирає [зберігання паролів](root:sf-security/password-hashing): там сама механіка відбитка, від якої тут відштовхуємось.

argon2id — переможець відкритого конкурсу Password Hashing Competition (2015), розробка Алекса Бірюкова, Даніеля Діну й Дмитра Ховратовича з Люксембурзького університету. Літера «id» означає гібрид: перші проходи він адресує пам'ять незалежно від даних (щоб не текти через побічні канали), решту — залежно (щоб опиратися перебору на відеокартах). Старший, але досі придатний варіант — bcrypt (Нільс Провос і Девід Мазʼєр, 1999, на базі шифру Blowfish); він теж навмисно повільний, але навантажує лише процесор, тоді як argon2id ще й вимагає пам'яті, чим збиває з пантелику спеціалізоване залізо для перебору.

Параметри беремо за чинною рекомендацією OWASP і вшиваємо їх у сам хеш:

```
argon2id (рекомендація OWASP):
  m = 19456 KiB   19 МіБ памʼяті на один хеш
  t = 2           проходи (ітерації)
  p = 1           паралелізм
  сіль            16 випадкових байтів — генерує сама бібліотека

результат — рядок PHC, що несе в собі все потрібне для звірки:
  $argon2id$v=19$m=19456,t=2,p=1$<сіль>$<хеш>
```

Найважливіше в цьому рядку — він **самодостатній**: алгоритм, параметри й сіль лежать усередині. Тому за рік, піднявши параметри під швидше залізо, старі записи не доведеться чіпати — бібліотека прочитає їхні власні параметри з рядка й звірить правильно.

:::tabs
```ts
import argon2 from "argon2";

const ARGON: argon2.Options = {
  type: argon2.argon2id,
  memoryCost: 19456,   // КіБ → 19 МіБ
  timeCost: 2,         // проходи
  parallelism: 1,
};

async function register(email: string, password: string, db: Db): Promise<void> {
  const norm = email.trim().toLowerCase();
  // хеш уже містить і сіль, і параметри — зберігаємо рядок як є
  const pwHash = await argon2.hash(password, ARGON);
  await db.insertUser({ email: norm, pwHash });
}
```
```python
from argon2 import PasswordHasher

# памʼять у КіБ; сіль (16 Б) додається сама й лежить у рядку-хеші
ph = PasswordHasher(memory_cost=19456, time_cost=2, parallelism=1)

def register(email: str, password: str, db) -> None:
    norm = email.strip().lower()
    pw_hash = ph.hash(password)          # рядок $argon2id$v=19$m=19456,...
    db.insert_user(email=norm, pw_hash=pw_hash)
```
```go
import (
    "crypto/rand"
    "encoding/base64"
    "fmt"
    "strings"

    "golang.org/x/crypto/argon2"
)

const (
    argonMem  = 19 * 1024 // 19 МіБ у КіБ = 19456
    argonTime = 2
    argonPar  = 1
    keyLen    = 32
)

// збираємо PHC-рядок вручну: $argon2id$v=..$m=..,t=..,p=..$<сіль>$<хеш>
func hashPassword(password string) (string, error) {
    salt := make([]byte, 16)
    if _, err := rand.Read(salt); err != nil { // crypto/rand — CSPRNG
        return "", err
    }
    key := argon2.IDKey([]byte(password), salt, argonTime, argonMem, argonPar, keyLen)
    b64 := base64.RawStdEncoding
    return fmt.Sprintf("$argon2id$v=%d$m=%d,t=%d,p=%d$%s$%s",
        argon2.Version, argonMem, argonTime, argonPar,
        b64.EncodeToString(salt), b64.EncodeToString(key)), nil
}

func register(email, password string, db *DB) error {
    norm := strings.ToLower(strings.TrimSpace(email))
    h, err := hashPassword(password)
    if err != nil {
        return err
    }
    return db.InsertUser(norm, h)
}
```
:::

**Пастка кроку.** Тут три способи все зіпсувати. Перший — узяти швидкий хеш («він же теж хеш»): він захищає від випадкового підглядання в базу, але не від перебору, а саме перебору ми й боїмося. Другий — самому «підсолити й похешувати кілька разів у циклі»: сіль argon2id генерує сам і вшиває в результат, а саморобні схеми з циклом SHA стабільно виходять слабшими за перевірену функцію. Третій, специфічний для bcrypt: він мовчки відкидає все після 72-го байта вводу, тож дуже довгі паролі — або спроба «підсилити» bcrypt, згодувавши йому вже готовий SHA-хеш, — обертаються тим, що частина секрета просто не рахується.

## Крок 2. Вхід: звірити пароль, не виказавши зайвого

Вхід — та сама перевірка, але тепер сервер має два тонкі обов'язки одночасно: сказати «так» лише правильному паролю **і не проговоритися ні про що більше**. Наївний код звіряє й повертає результат — і непомітно зливає те, чого не мав.

Витікає не пароль, а сам факт, що акаунт існує. Зливають його два канали. Перший — різні повідомлення про помилку: «немає такого користувача» проти «невірний пароль» просто називає зловмиснику, які адреси зареєстровані. Другий, підступніший, — час. Уяви два запити на вхід з паролем навмання. Якщо акаунт існує, сервер чесно проганяє повільний argon2 і відповідає, скажімо, за п'яту частку секунди. Якщо акаунта немає, а наївний код, не знайшовши користувача, одразу вертає відмову, — відповідь прилітає за п'ять мілісекунд. Зловмиснику й не треба знати пароль: сама швидкість відповіді ділить усі адреси на «є в системі» і «немає».

![Дві панелі-хронометражі. Угорі, наївно: коли акаунт існує, сервер проганяє повільний argon2 і відповідає приблизно за 200 мс; коли акаунта немає, наївний код одразу вертає відмову — приблизно за 5 мс. Розрив у часі сам виказує, чи зареєстрований акаунт. Унизу, захищено: на неіснуючий акаунт сервер так само проганяє argon2, але проти заздалегідь порахованого фіктивного хешу — і час відповіді стає однаковим, тож існування акаунта не витікає](img/enum-timing.svg)
*Перелічення користувачів через час відповіді. Ліки — не пришвидшити наявний акаунт, а вповільнити відсутній: змарнувати рівно стільки ж часу на фіктивному хеші.*

Це й є перелічення користувачів (user enumeration) — витік не пароля, а списку зареєстрованих, з якого починають прицільний фішинг чи підстановку викрадених деінде паролів. Ліки не в тому, щоб зробити наявний акаунт швидшим, а в тому, щоб **зрівняти** відсутній із наявним: коли користувача не знайдено, сервер усе одно проганяє argon2 — проти заздалегідь порахованого фіктивного хешу з тими самими параметрами, — марнує стільки ж часу й повертає те саме повідомлення. Плюс сама звірка байтів іде за сталий час: перевірка не вискакує на першій розбіжності (інакше довжина спільного початку теж підтікала б у часі), і `argon2.verify` та `subtle.ConstantTimeCompare` роблять це за нас.

:::tabs
```ts
import argon2 from "argon2";

// ESM: рахуємо фіктивний хеш один раз під час старту, з ТИМИ САМИМИ параметрами
const DUMMY_HASH = await argon2.hash("dummy-password-never-matches", ARGON);

async function login(email: string, password: string, db: Db): Promise<User | null> {
  const norm = email.trim().toLowerCase();
  const user = await db.findUser(norm);
  // немає користувача → усе одно звіряємо проти фіктивного хешу:
  // стільки ж часу, те саме повідомлення — існування акаунта не витікає
  const hash = user?.pwHash ?? DUMMY_HASH;
  const ok = await argon2.verify(hash, password);   // звірка за сталий час
  return ok && user ? user : null;
}
```
```python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher(memory_cost=19456, time_cost=2, parallelism=1)
# фіктивний хеш із тими самими параметрами — рахуємо один раз під час старту
DUMMY_HASH = ph.hash("dummy-password-never-matches")

def login(email: str, password: str, db):
    norm = email.strip().lower()
    user = db.find_user(norm)                # None, якщо немає
    stored = user.pw_hash if user else DUMMY_HASH
    try:
        ph.verify(stored, password)          # кине VerifyMismatchError, якщо не збіглося
    except VerifyMismatchError:
        return None                          # те саме «ні» на обидва випадки
    return user                              # None → так само вхід не відбувся
```
```go
import (
    "crypto/subtle"
    "encoding/base64"
    "errors"
    "fmt"
    "strings"

    "golang.org/x/crypto/argon2"
)

type argonParams struct {
    mem, time uint32
    par       uint8
}

// розібрати PHC-рядок назад на параметри, сіль і хеш
func decodeHash(encoded string) (p argonParams, salt, key []byte, err error) {
    parts := strings.Split(encoded, "$") // ["", "argon2id", "v=19", "m=..,t=..,p=..", сіль, хеш]
    if len(parts) != 6 {
        return p, nil, nil, errors.New("поганий формат хешу")
    }
    if _, err = fmt.Sscanf(parts[3], "m=%d,t=%d,p=%d", &p.mem, &p.time, &p.par); err != nil {
        return p, nil, nil, err
    }
    b64 := base64.RawStdEncoding
    if salt, err = b64.DecodeString(parts[4]); err != nil {
        return p, nil, nil, err
    }
    if key, err = b64.DecodeString(parts[5]); err != nil {
        return p, nil, nil, err
    }
    return p, salt, key, nil
}

func verifyPassword(encoded, password string) bool {
    p, salt, key, err := decodeHash(encoded)
    if err != nil {
        return false
    }
    calc := argon2.IDKey([]byte(password), salt, p.time, p.mem, p.par, uint32(len(key)))
    return subtle.ConstantTimeCompare(key, calc) == 1 // звірка за сталий час
}

// заздалегідь порахований фіктивний хеш (ті самі параметри)
var dummyHash, _ = hashPassword("dummy-password-never-matches")

func login(email, password string, db *DB) *User {
    norm := strings.ToLower(strings.TrimSpace(email))
    user := db.FindUser(norm) // nil, якщо немає
    stored := dummyHash
    if user != nil {
        stored = user.PwHash
    }
    if verifyPassword(stored, password) && user != nil {
        return user
    }
    return nil
}
```
:::

Одну межу цієї гри треба назвати чесно: сталий час на сервері — не абсолют, а «досить рівно». Пошук у базі, мережа, збирач сміття додають свій шум у мілісекундах, і виміряти наносекунди звідси годі. Але дорога, керована операція тут одна — argon2, і вона на два-три порядки більша за той шум. Тому не ганяються за наносекундами: досить закрити **грубий** розрив — той, у якому наявний акаунт коштує чверть секунди, а відсутній п'ять мілісекунд.

> 🔧 **Навіщо це.** Рівна перевірка не спиняє того, хто просто пробує пароль за паролем. Друга заслона — [обмеження частоти спроб](root:sf-security/rate-limiting): після кількох невдач з однієї адреси чи по одному акаунту сервер уповільнюється або тимчасово замикається, і мільйон здогадів на секунду стискається до жменьки. Як улаштувати такий лічильник — там.

## Крок 3. Видати жетон: сто двадцять вісім випадкових бітів

Пароль звірено — тепер його відкладають і більше до нього не вертаються. Замість нього сервер видає жетон сесії: рядок, що заступає пароль на весь час, поки ти впізнаний. Вимога до нього одна, зате сувора — **його не можна вгадати**.

«Не вгадати» означає конкретну арифметику. Жетон роблять із випадкових байтів, а простір, у якому їх довелося б перебирати, — астрономічний:

```
токен = 16 випадкових байтів = 128 бітів ентропії
простір = 2¹²⁸ ≈ 3.4·10³⁸ можливих значень
```

Для порівняння: короткий людський пароль живе у просторі десь 2³⁸ — розрив у мільярди мільярдів разів. OWASP кладе за мінімум саме 128 бітів довжини й щонайменше 64 біти справжньої ентропії; за їхнім же підрахунком, навіть 64 біти означають, що при десяти тисячах здогадів на секунду й ста тисячах живих сесій нападник шукав би чинний жетон близько 585 років. Сто двадцять вісім бітів — далеко за межею будь-якого перебору.

Але вся ця арифметика тримається на слові **випадкових**. Байти має дати криптографічний генератор — непередбачуваний навіть для того, хто бачив мільйон попередніх жетонів.

> 🔧 **Навіщо це.** Різницю між «схоже на випадкове» і «непередбачуване» тримає [криптографічний генератор випадкових чисел (CSPRNG)](root:sf-security/csprng). Звичайний `Math.random` (чи `math/rand` у Go) чудовий, щоб перемішати колоду, але для жетона згубний: його внутрішній стан відновлюють за кількома видачами, і далі всі майбутні жетони передбачувані. Тут беруть лише крипто-джерело: `crypto.randomBytes`, `secrets`, `crypto/rand`.

Байти віддають у base64url — компактно й без символів, які довелося б екранувати в cookie:

:::tabs
```ts
import { randomBytes } from "node:crypto";

function newSessionToken(): string {
  // 16 байтів = 128 бітів ентропії з криптографічного джерела
  return randomBytes(16).toString("base64url");
}
```
```python
import secrets

def new_session_token() -> str:
    # token_urlsafe(16) = 16 байтів ентропії, base64url без набивки
    return secrets.token_urlsafe(16)
```
```go
import (
    "crypto/rand"
    "encoding/base64"
)

func newSessionToken() (string, error) {
    b := make([]byte, 16) // 128 бітів
    if _, err := rand.Read(b); err != nil { // crypto/rand, НЕ math/rand
        return "", err
    }
    return base64.RawURLEncoding.EncodeToString(b), nil
}
```
:::

**Пастка кроку.** Найпоширеніша — узяти зручний, але некрипто-генератор: `Math.random`, поточний час, лічильник чи послідовний числовий ідентифікатор рядка в базі. Усе це передбачуване: сусідні жетони відрізняються на крок, а бачивши кілька — вгадують решту. Друга пастка — заощадити на довжині: жетон на 32 чи 64 біти вже потрапляє в зону, де ферма машин перебирає його за розумний час, надто якщо живих сесій багато й досить влучити в **будь-яку**.

## Крок 4. Де жити жетону: серверне сховище чи підпис

Жетон готовий — куди його подіти на сервері? Найпростіший шлях — сховище сесій: рядок-жетон як ключ, а за ним — чий це вхід і коли він почався. Але тут повторюється урок кроку 1, з несподіваним поворотом. У базі знову тримають **не сам жетон, а його відбиток** — щоб викрадена база не роздала живих сесій так само, як не роздає паролів. А от хеш цього разу беруть **швидкий**, звичайний SHA-256, і це не недбалість, а точний розрахунок.

![Порівняння двох секретів у трьох рядках. Пароль: ентропія близько 38 бітів (вигадала людина), функція argon2id — навмисно повільна, сіль потрібна проти райдужних таблиць, хешуємо, щоб перебір коштував часу. Токен сесії: ентропія 128 бітів (CSPRNG), функція SHA-256 — швидка, сіль не потрібна бо секрет уже випадковий, хешуємо, щоб витік бази не віддав живих сесій. Дві протилежні задачі диктують дві різні хеш-функції](img/two-hashes.svg)
*Чому пароль хешують повільно, а жетон швидко. Повільність — щоб зробити перебір слабкого секрета болючим; жетон перебрати неможливо в принципі, тож повільний хеш на ньому лише марнував би CPU на кожному запиті.*

Ось де сходяться два секрети. Пароль слабкий, тому його хеш **навмисно повільний** — щоб кожна з мільярдів спроб перебору коштувала часу. Жетон уже несе 128 бітів повної ентропії, перебрати його неможливо в принципі — тож повільний хеш на ньому нічого не додав би до безпеки, зате важив би на **кожному** запиті, де сесію треба впізнати. Тому SHA-256: він миттєвий, солі не потребує (жетон і так рівномірно випадковий), а від витоку бази захищає незгірш — маючи лише відбиток, з нього не відновиш живий жетон.

:::tabs
```ts
import { createHash, randomBytes } from "node:crypto";

const sha256 = (s: string) => createHash("sha256").update(s).digest("hex");

interface Session { userId: string; createdAt: number; lastSeen: number; }

async function createSession(userId: string, db: Db): Promise<string> {
  const token = randomBytes(16).toString("base64url");
  const now = Date.now();
  // у базі — лише ВІДБИТОК жетона; сам жетон їде тільки в cookie до клієнта
  await db.putSession(sha256(token), { userId, createdAt: now, lastSeen: now });
  return token;
}

async function resolveSession(token: string, db: Db): Promise<Session | null> {
  return db.getSession(sha256(token));   // шукаємо за відбитком
}
```

Є й інший шлях — **не зберігати нічого**. Замість запису в базі жетон роблять самоописним: кладуть у нього, хто ти й доки він чинний, і підписують секретним ключем сервера (HMAC) — це родина [підписаних токенів (JWT)](root:sf-web/jwt-tokens). Тоді сервер не заглядає у сховище зовсім, лише перевіряє підпис. Ціна — відкликати такий жетон важко: він чинний, доки не сплив термін, бо викидати з бази нема чого. Тому підписані токени роблять короткоживучими, а серверні сесії легко гасять, стерши рядок. Що обрати — зважують у [керуванні сесіями](root:sf-web/session-management): серверне сховище дає миттєве відкликання ціною звірки з базою на кожному запиті, підпис дає без-баз-ний масштаб ціною млявого відкликання.

**Пастка кроку.** Три штрихи. Класти в базу сам жетон замість відбитка — означає, що витік бази миттєво роздає живі сесії. Хешувати жетон повільним argon2 «для надійності» — марна витрата CPU на кожному запиті, що нічого не додає (перебирати нема чого). І найгірше з підписаними токенами — довіритись **не**підписаному самоописному жетону: якщо всередині просто написано `user=42` без підпису, будь-хто перепише його на `user=1` і стане адміністратором; самоопис без криптографічного підпису — це не захист, а запрошення.

## Крок 5. Cookie: чотири прапорці — чотири щити

Жетон треба довезти до браузера так, щоб він повертався з кожним запитом сам, і щоб дорогою його не вкрали й не підмінили. Це робить cookie — пара «ім'я=значення», яку браузер запам'ятовує й сам чіпляє до кожного запиту на цей сайт. Уся безпека тут — у кількох прапорцях, які кажуть браузерові, як цю cookie берегти, і кожен прапорець закриває свій напад:

```
Set-Cookie: sid=<жетон>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1209600

  HttpOnly   JS сторінки не бачить cookie (document.cookie німий) → XSS не вкраде жетон
  Secure     cookie їде лише поверх HTTPS, ніколи відкритим HTTP → не прочитають дорогою
  SameSite   Lax: cookie не шлеться на чужих міжсайтових POST → щит від CSRF
  Path=/     на весь сайт
  Max-Age    час життя в секундах (тут 14 діб = 1209600)
```

Кожен прапорець — відповідь на конкретну загрозу. `HttpOnly` виймає жетон з-під дії скриптів: навіть якщо на сторінку просочився чужий JavaScript (напад XSS), він не прочитає cookie через `document.cookie` — а отже, не викраде сесію. `Secure` тримає cookie в шифрованому каналі й не дає їй вислизнути відкритим HTTP, де її прочитав би будь-хто на шляху. `SameSite=Lax` б'є по нападу підробки міжсайтового запиту (CSRF): це коли чужий сайт змушує твій браузер тихо надіслати запит на наш, а браузер слухняно чіпляє cookie; `Lax` обриває саме це — не пускає cookie на запити, породжені зовнішньою сторінкою (зокрема на міжсайтові POST). З лютого 2020 року (Chrome 80) браузери й самі вважають відсутній `SameSite` за `Lax`, але покладатися на замовчання не варто — прапорець ставлять явно.

> 🔧 **Навіщо це.** Прапорець `Secure` має сенс лише тому, що канал шифрований: cookie їде тільки поверх [TLS](root:sf-security/tls), інакше перший-ліпший на шляху прочитав би її відкритим текстом. Без TLS решта прапорців — замок на дверях із вибитим вікном.

:::tabs
```ts
function sessionCookie(token: string): string {
  const twoWeeks = 60 * 60 * 24 * 14; // секунд
  return [
    `sid=${token}`,
    "HttpOnly",       // недосяжна для document.cookie
    "Secure",         // лише поверх HTTPS
    "SameSite=Lax",   // не піде на чужий POST → щит від CSRF
    "Path=/",
    `Max-Age=${twoWeeks}`,
  ].join("; ");
}

// у обробнику входу:
res.setHeader("Set-Cookie", sessionCookie(token));
```

**Пастка кроку.** Забути `HttpOnly` — і будь-який XSS перетворюється на крадіжку сесії. Забути `Secure` — і жетон витікає на першому ж запиті, який чомусь пішов відкритим HTTP. Забути `SameSite` на старому браузері — і відкриваєшся CSRF. Ще дві пастки поза цим списком: занадто широкий `Domain` (наприклад `.example.com`) розсилає cookie всім піддоменам, зокрема чужим і ненадійним; а найгрубіша — взагалі не класти жетон у cookie, а тягати його в URL (де він осідає в логах і в заголовку Referer) чи в `localStorage` (звідки його дістає той-таки XSS, від якого рятує `HttpOnly`).

## Крок 6. Термін і ротація: жетон не живе вічно

Жетон, що живе вічно, — це вкрадений жетон, який працює вічно. Тому кожній сесії дають **два годинники**. Перший — вікно бездіяльності: не бачили тебе, скажімо, тиждень — сесія просрочена. Другий — жорстка стеля від моменту входу: навіть якщо ти активний щодня, через два тижні доведеться увійти наново. Вікно бездіяльності обмежує, скільки прослужить украдений жетон занедбаної сесії; абсолютна стеля не дає жодній сесії тягтися нескінченно, хоч би як часто нею користувались.

Обидва годинники мусять цокати **на сервері**. `Max-Age` у cookie — лише підказка браузеру, і її легко підробити чи знехтувати; істина — у серверному записі, з якого впізнавання й читає час. Тому перевірка терміну живе поряд зі звіркою відбитка:

:::tabs
```ts
const IDLE_MS = 1000 * 60 * 60 * 24 * 7;      // 7 діб без активності — просрочка
const ABSOLUTE_MS = 1000 * 60 * 60 * 24 * 14; // 14 діб від входу — жорстка стеля

async function authenticate(token: string, db: Db): Promise<Session | null> {
  const s = await db.getSession(sha256(token));
  if (!s) return null;
  const now = Date.now();
  if (now - s.lastSeen > IDLE_MS || now - s.createdAt > ABSOLUTE_MS) {
    await db.deleteSession(sha256(token));  // мертву — прибрати
    return null;
  }
  await db.touchSession(sha256(token), now); // ковзне вікно бездіяльності
  return s;
}

// РОТАЦІЯ під час входу — проти фіксації сесії:
async function loginAndStart(user: User, oldToken: string | null, db: Db): Promise<string> {
  if (oldToken) await db.deleteSession(sha256(oldToken)); // старий ідентифікатор — мертвий
  return createSession(user.id, db);                      // свіжий, невідомий нападнику
}
```

Ротація в момент входу — не забаганка, а ліки від окремого нападу. Уяви фіксацію сесії (session fixation): зловмисник заздалегідь підсовує жертві **відомий йому** жетон — через посилання чи через cookie, — жертва входить, і якщо жетон при вході не змінився, нападник тепер тримає в руках чинну, вже впізнану сесію. Розрив простий: щойно піднявся рівень довіри (стався вхід), старий жетон гасять і видають свіжий, якого нападник не знає. З тієї ж причини жетон обов'язково міняють при зміні пароля.

> 🔧 **Навіщо це.** Стара перехоплена копія жетона, надіслана повторно, — окрема морока: [захист від повтору](root:sf-security/replay-protection) додає одноразові позначки, прив'язку до сеансу й короткий термін, щоб копія, чинна вчора, сьогодні вже нічого не відмикала. Термін і ротація з цього кроку — перша, найдешевша його частина.

**Пастка кроку.** Найтихіша — вихід, який лише стирає cookie в браузері, а серверний запис лишає живим: жетон, який десь осів (у логах проксі, в історії), досі відмикає сесію. Гасити треба **серверний рядок**. Друга — покластися на `Max-Age` cookie як на термін дії: клієнт нею керує, тому єдиний авторитетний годинник — серверний. Третя — не ротувати жетон при вході, лишаючи відчиненими двері для фіксації.

## Складність і пастки: один кошторис і один принцип

Через усі шість кроків проходить один кошторис часу. Єдина навмисно дорога операція — argon2, і вона спрацьовує лише двічі за життя сесії: при реєстрації та при кожному вході. Її розмір підбирають так, щоб один хеш займав кількадесят-двісті мілісекунд на **твоєму** залізі: досить, щоб перебір став болючим, не досить, щоб чесний вхід гальмував. Решта шляху — швидка: SHA-256 відбитка жетона на кожному запиті коштує мікросекунди, тому саме впізнавання не навантажує сервер. Звідси, до речі, ще одна роль обмеження частоти — воно не лише проти вгадування, а й як стеля на дорогі argon2-виклики: без нього зловмисник завалить сервер лавиною спроб входу, кожна з яких з'їдає чверть секунди процесора.

А над кошторисом стоїть один принцип, і він пояснює геть кожне рішення вище: **будуй так, ніби база колись витече**. Варто прийняти це — і стає очевидним, чому в базі лежить хеш пароля, а не пароль; хеш жетона, а не жетон; чому підписаний токен коротко живе, а серверну сесію можна вбити стиранням рядка; чому cookie — `HttpOnly` й `Secure`. Витік майже ніколи не стається через одну велику дурницю. Він складається з кроків, кожен з яких здавався дрібницею, у якій «нічого не станеться»:

- **Реєстрація** — швидкий хеш або саморобна схема замість argon2id: перебір слабкого пароля стає посильним.
- **Вхід** — різне повідомлення чи різний час на неіснуючий акаунт: витікає список зареєстрованих (перелічення користувачів).
- **Жетон** — некрипто-генератор чи заощадження на бітах: жетони стають передбачуваними.
- **Зберігання** — сам жетон замість відбитка в базі, або довіра непідписаному самоопису: витік бази роздає живі сесії, підробка даху робить будь-кого адміністратором.
- **Cookie** — забутий `HttpOnly`/`Secure`/`SameSite` або жетон у URL чи `localStorage`: крадіжка через XSS, підслух, CSRF.
- **Термін** — сесія без стелі, вихід без гасіння серверного запису, відсутня ротація при вході: украдений жетон працює вічно, а фіксація відмикає чужий вхід.

Правильний вхід — не одна хитра штука, а шість дрібниць, зроблених без жодного «та нічого не станеться».
