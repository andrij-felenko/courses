# 📋 Інтерфейс та структура параметрів протоколу Шнорра

Цей довідник описує специфікацію параметрів, структур даних, граничних обмежень та інтерфейсних функцій протоколу Шнорра для доведення знання дискретного логарифма у мультиплікативних групах простих полів `ℤ_p^*` та групах еліптичних кривих.

Документ слугує розробникам і криптоаналітикам як довідникова специфікація контракту при створенні бібліотек автентифікації, цифрових підписів та криптографічних протоколів з нульовим розголошенням.

## 1. Специфікація математичних параметрів

Усі обчислення в рамках протоколу Шнорра виконуються над алгебраїчною структурою `(p, q, g)`. Вибір цієї трійки визначає рівень криптографічної стійкості всієї системи.

Великий модуль `p` задає основне скінченне поле `ℤ_p^*`. Для забезпечення стійкості проти дискретного логарифмування за допомогою загального методу решета числового поля (англ. *Number Field Sieve*, NFS) довжина `p` повинна становити не менше 2048 біт у сучасних системах, а для довгострокового захисту — 3072 або 4096 біт. Алгоритм генерації модулів `p` спирається на стандарти FIPS 186-4 або пошук безпечних простих чисел вида `p = 2q + 1` (прості числа Софі Жермен).

Порядок циклічної підгрупи `q` мусить бути простим числом, що ділить `p - 1`. Це гарантує існування підгрупи відповідного порядку у мультиплікативній групі поля. Довжина `q` обирається з розрахунку стійкості проти алгоритму ро-Поларда та алгоритму Шенкса (англ. *baby-step giant-step*). Мінімальний розмір `q` становить 256 біт, що забезпечує 128 біт еквівалентної криптографічної стійкості. Якщо `q` обрано занадто малим, зловмисник може легко обчислити дискретний логарифм у підгрупі малого порядку.

Твірний елемент `g` обирається так, щоб він породжував циклічну підгрупу порядку `q`. Це означає, що `g^q ≡ 1 (mod p)` та `g ≠ 1`. Для побудови `g` генератор обирає довільне число `h ∈ {2, ..., p-2}` та обчислює `g = h^{(p-1)/q} mod p`. Якщо отримане `g = 1`, процес повторюється з іншим `h`. Якщо обрати елемент поза цією підгрупою, протокол стає вразливим до атак малими підгрупами (англ. *Small Subgroup Attack*), під час яких перевіряльник або спостерігач може витягнути приватний ключ `x` за модулем факторів малого порядку.

| Параметр | Позначення | Тип / Обмеження | Криптографічна роль |
| :--- | :--- | :--- | :--- |
| **Великий модуль** | `p` | Непарне просте число, `\|p\| ≥ 2048` біт | Задає основне скінченне поле `ℤ_p^*` |
| **Порядок підгрупи** | `q` | Просте число, `\|q\| ≥ 256` біт, `q \| (p - 1)` | Задає порядок циклічної підгрупи |
| **Твірний елемент** | `g` | `g ∈ ℤ_p^*`, `g^q ≡ 1 (mod p)`, `g ≠ 1` | Генератор циклічної підгрупи порядку `q` |
| **Приватний ключ** | `x` | `x ∈ ℤ_q^*`, рівномірно випадковий | Секретний свідок (дискретний логарифм) |
| **Публічний ключ** | `y` | `y = g^x mod p`, `y ∈ ℤ_p^*`, `y ≠ 1` | Відкритий ідентифікатор доводжувача |
| **Тимчасовий nonce** | `k` | `k ∈ ℤ_q^*`, унікальний для кожного доказу | Випадкове зобов'язання доводжувача |
| **Зобов'язання** | `r` | `r = g^k mod p`, `r ∈ ℤ_p^*` | Перша фаза протоколу (Commitment) |
| **Випробовувальний виклик** | `c` | `c ∈ ℤ_q`, випадковий або `H(g, y, r)` | Друга фаза протоколу (Challenge) |
| **Відповідь** | `s` | `s = (k + c · x) mod q` | Третя фаза протоколу (Response) |

## 2. Структури даних та бінарне кодування

Для забезпечення повної сумісності між різними мовами програмування (C, C++, Rust, Python, Go) структури даних подаються у вигляді плоских байтових масивів у прямому порядку байтів (англ. *big-endian*). Усі числові значення доповнюються провідними нулями до максимального розміру відповідного параметра.

Кожен елемент групи `p` серіалізується у масив фіксованої довжини `p_len` (наприклад, 256 байтів для 2048-бітного модуля або 384 байти для 3072-бітного модуля). Елементи порядку підгрупи `q` та приватні ключі серіалізуються у масив довжини `q_len` (наприклад, 32 байти для 256-бітного порядку).

### Специфікація структур даних (C++ / C-compatible ABI)

Опис статусів операцій дозволяє чітко розрізняти криптографічні відхилення доказів від технічних помилок виділення пам'яті чи некоректних аргументів.

```cpp
#include <cstdint>
#include <cstddef>

// Перелік статусів виконання операцій та кодів помилок
enum class ZkpStatus : uint32_t {
    SUCCESS               = 0x00, // Операція виконана успішно
    ERR_INVALID_PARAMS    = 0x01, // Некоректні математичні параметри групи (p, q, g)
    ERR_OUT_OF_RANGE      = 0x02, // Вхідні дані виходять за дозволені межі полів
    ERR_ZERO_COMMITMENT   = 0x03, // Згенеровано тривіальне зобов'язання r = 0 або r = 1
    ERR_VERIFICATION_FAIL = 0x04, // Математична тотожність g^s ≡ r * y^c не справдилася
    ERR_NONCE_REUSE       = 0x05, // Виявлено повторне використання тимчасового nonce k
    ERR_NULL_POINTER      = 0x06, // Передано нульовий вказівник на буфер даних
    ERR_BUFFER_TOO_SMALL  = 0x07  // Розмір вихідного буфера є недостатнім
};

// Контейнер публічних параметрів групи
struct SchnorrGroupParams {
    const uint8_t* p_bytes;  // Буфер байтів модуля p (big-endian)
    size_t         p_len;    // Довжина p у байтах (наприклад, 256 або 384)
    const uint8_t* q_bytes;  // Буфер байтів порядку q (big-endian)
    size_t         q_len;    // Довжина q у байтах (наприклад, 32)
    const uint8_t* g_bytes;  // Буфер байтів генератора g (big-endian)
    size_t         g_len;    // Довжина g у байтах
};

// Контейнер пакетного неінтерактивного доказу π = (r, s)
struct SchnorrProof {
    uint8_t r_bytes[384];    // Зобов'язання r (розмір відповідає p_len)
    size_t  r_len;
    uint8_t s_bytes[32];     // Відповідь s (розмір відповідає q_len)
    size_t  s_len;
};

// Контейнер стану детермінованого генератора nonce за RFC 6979
struct SchnorrRfc6979State {
    uint8_t v_key[32];       // Внутрішній вектор V для HMAC-SHA256
    uint8_t k_key[32];       // Внутрішній ключ K для HMAC-SHA256
    size_t  hash_len;
};
```

## 3. Сигнатури та специфікація API

Інтерфейсна поверхня бібліотеки розділена на три фундаментальні фази: ініціалізація параметрів, виконання рольових функцій доводжувача та підсумкова верифікація на боці перевіряльника.

### 1. Перевірка цілісності параметрів групи

Перед використанням будь-яких параметрів `(p, q, g)` додаток повинен викликати функцію ініціалізації. Вона виконує перевірку того, що `p` та `q` є простими числами, `q` ділить `p - 1`, а `g^q ≡ 1 (mod p)`.

```cpp
/**
 * @brief Перевіряє математичну коректність та криптографічну стійкість параметрів групи.
 * 
 * @param params Указатель на структуру параметрів групи.
 * @return ZkpStatus SUCCESS якщо параметри коректні, інакше ERR_INVALID_PARAMS.
 */
ZkpStatus schnorr_validate_group_params(
    const SchnorrGroupParams* params
);
```

### 2. Функція генерації зобов'язання (Prover Phase 1)

Функція відповідає за генерацію випадкового одноразового значення `k` та обчислення публічного значення `r = g^k mod p`. Сгенерований nonce `k` є строго секретним і повинен зберігатися в захищеній пам'яті до завершення генерації доказу. Одразу після використання буфер пам'яті з `k` має бути надійно очищений функцією `explicit_bzero` або її захищеним аналогом, щоб унеможливити витік через знімки оперативної пам'яті чи дамп ядра.

```cpp
/**
 * @brief Генерує випадкове зобов'язання r = g^k mod p та зберігає секретний nonce k.
 * 
 * @param params Указатель на валідовані параметри групи.
 * @param out_k Вихідний буфер для збереження тимчасового secret nonce k (розмір q_len).
 * @param out_r Вихідний буфер для публічного зобов'язання r (розмір p_len).
 * @return ZkpStatus SUCCESS у разі успіху, інакше код помилки.
 */
ZkpStatus schnorr_commit(
    const SchnorrGroupParams* params,
    uint8_t*                  out_k,
    uint8_t*                  out_r
);
```

### 3. Функція обчислення відповіді (Prover Phase 2)

Ця функція приймає випробовувальний виклик `c` (отриманий від перевіряльника у випадку інтерактивного діалогу або обчислений через хеш-функцію Фіата — Шаміра для неінтерактивного режиму) і комбінує його з приватним ключем `x` та тимчасовим nonce `k`.

```cpp
/**
 * @brief Обчислює підтверджувальну відповідь s = (k + c * x) mod q.
 * 
 * @param params Указатель на параметри групи.
 * @param secret_x Приватний ключ доводжувача (розмір q_len).
 * @param k_nonce Тимчасовий secret nonce з фази 1 (розмір q_len).
 * @param challenge Випробовувальний виклик c (розмір q_len).
 * @param out_s Вихідний буфер для відповіді s (розмір q_len).
 * @return ZkpStatus SUCCESS у разі успіху.
 */
ZkpStatus schnorr_respond(
    const SchnorrGroupParams* params,
    const uint8_t*            secret_x,
    const uint8_t*            k_nonce,
    const uint8_t*            challenge,
    uint8_t*                  out_s
);
```

### 4. Функція неінтерактивного доведення NIZK (Prover Combined)

Функція об'єднує генерацію `k`, обчислення хеш-виклику `c = H(g, y, r)` та формування відповіді `s` у єдиний атомарний виклик. Вона гарантує правильний порядок обчислень і запобігає витоку тимчасових змінних за межі локального стека.

```cpp
/**
 * @brief Автономно будує неінтерактивний доказ π = (r, s) за допомогою хешування Фіата — Шаміра.
 * 
 * @param params Параметри групи.
 * @param secret_x Приватний ключ доводжувача.
 * @param public_y Публічний ключ доводжувача y = g^x mod p.
 * @param out_proof Вихідна структура доказу.
 * @return ZkpStatus SUCCESS у разі успіху.
 */
ZkpStatus schnorr_nizk_prove(
    const SchnorrGroupParams* params,
    const uint8_t*            secret_x,
    const uint8_t*            public_y,
    SchnorrProof*             out_proof
);
```

### 5. Функція верифікації (Verifier)

Верифікатор не має доступу до секретних змінних `x` чи `k`. Функція виконує обчислення `c = H(g, y, r)` та перевіряє фундаментальну тотожність `g^s ≡ r · y^c (mod p)`.

```cpp
/**
 * @brief Перевіряє тотожність g^s ≡ r * y^c (mod p).
 * 
 * @param params Параметри групи.
 * @param public_y Публічний ключ доводжувача y.
 * @param proof Структура доказу (r, s).
 * @return ZkpStatus SUCCESS якщо доказ дійсний, ERR_VERIFICATION_FAIL якщо некоректний.
 */
ZkpStatus schnorr_nizk_verify(
    const SchnorrGroupParams* params,
    const uint8_t*            public_y,
    const SchnorrProof*       proof
);
```

## 4. Карта перевірок та санітарна обробка вхідних даних

Під час верифікації перевіряльник **зобов'язаний** виконати послідовний ланцюжок санітарних перевірок. Пропуск хоча б однієї перевірки робить систему вразливою до фальсифікацій та атак зниження криптографічної стійкості.

Спочатку виконується санітарний контроль діапазонів чисел. Значення зобов'язання `r` має строго знаходитися в інтервалі від `1` до `p - 1`. Якщо `r = 0` або `r ≥ p`, обчислення негайно припиняються. Значення відповіді `s` повинно належати інтервалу `[0, q - 1]`.

Далі виконується перевірка належності елементів `y` та `r` до заданої підгрупи порядку `q`. Для цього перевіряльник здійснює піднесення до степеня: `y^q mod p` та `r^q mod p`. Обидва результати мають дорівнювати `1 mod p`. Це блокує атаки з використанням елементів з малих підгрупах.

Після проходження всіх санітарних перевірок обчислюється хеш-виклик `c = H(g, y, r) mod q` та виконується підсумкова перевірка тотожності.

```
[Вхідні дані: y, r, s, p, q, g]
       │
       ├─► 1. Перевірка вказівників на NULL ────────────────► [Так] ─► ERR_NULL_POINTER
       │
       ├─► 2. Перевірка діапазону r:  0 < r < p  ───────────► [Ні] ──► ERR_OUT_OF_RANGE
       │
       ├─► 3. Перевірка діапазону s:  0 ≤ s < q  ───────────► [Ні] ──► ERR_OUT_OF_RANGE
       │
       ├─► 4. Перевірка підгрупи y:   y^q ≡ 1 (mod p) ──────► [Ні] ──► ERR_INVALID_PARAMS
       │
       ├─► 5. Перевірка підгрупи r:   r^q ≡ 1 (mod p) ──────► [Ні] ──► ERR_INVALID_PARAMS
       │
       └─► 6. Обчислення c = H(g, y, r) mod q
               │
               └─► 7. Перевірка тотожності g^s ≡ r · y^c (mod p) ──► [Ні] ──► ERR_VERIFICATION_FAIL
                       │
                       └─► [Так] ──► ZkpStatus::SUCCESS
```

## 5. Таблиця помилок та вразливостей реалізації

Детальний аналіз можливих помилок розробки дозволяє передбачити захисні механізми на рівні коду.

Особливу небезпеку становить повторне використання значення `k` (nonce reuse). Якщо розробник згенерує однакові значення `k` для двох різних повідомлень або доказів, зловмисник зможе скласти систему з двох лінійних рівнянь і обчислити приватний ключ `x`. Для запобігання цьому рекомендується використовувати детерміновану генерацію nonce відповідно до специфікації RFC 6979, де `k` обчислюється як HMAC від приватного ключа та змісту повідомлення.

Атаки по бічних каналах (англ. *Side-Channel Attacks*) за часом виконання піднесення до степеня можуть розкрити значення `x` або `k`. Тому всі модульні операції повинні виконуватися за допомогою алгоритмів із постійним часом виконання (англ. *constant-time arithmetic*), без розгалужень та залежних від даних адресних звернень до пам'яті.

| Код помилки | Причина виникнення | Наслідки недотримання | Спосіб захисту |
| :--- | :--- | :--- | :--- |
| `ERR_INVALID_PARAMS` | Елемент `y` або `r` не належить циклічній підгрупі порядку `q` | Атака малими підгрупами (англ. *Small Subgroup Attack*), витік секрету | Перевіряти `y^q ≡ 1 mod p` та `r^q ≡ 1 mod p` |
| `ERR_OUT_OF_RANGE` | Значення `r ≥ p` або `s ≥ q` перевищують межі поля | Фальсифікація доведень за допомогою виходу за модуль | Строгий контроль `r ∈ [1, p-1]` та `s ∈ [0, q-1]` |
| `ERR_NONCE_REUSE` | Повторне використання `k` для двох різних доведень | Повне відкриття приватного ключа `x = (s₁ - s₂)/(c₁ - c₂)` | Використовувати детерміновану генерацію `k = RFC6979(x, msg)` |
| `ERR_ZERO_COMMITMENT` | Згенеровано `r = 0 mod p` або `g^k = 1 mod p` | Тривіальний доказ, вироджена математична система | Відхиляти `r = 0` та `r = 1` |
| `ERR_NULL_POINTER` | Передано нулевий буфер даних для вхідних або вихідних масивів | Падіння процесу (Segmentation Fault), аварійне завершення | Обов'язкова перевірка `if (ptr == nullptr)` на вході |
| `ERR_BUFFER_TOO_SMALL` | Буфер вихідного доказу має розмір менший за `p_len + q_len` | Переповнення буфера у стеку (Buffer Overflow) | Перевіряти розмір вихідної структури до запису |

## 6. Варіанти API для еліптичних кривих (secp256k1 / Ed25519)

У сучасних криптографічних бібліотеках (Libsecp256k1, Sodium) протокол Шнорра реалізують над групами точок еліптичних кривих. При цьому математичні об'єкти змінюють свою форму, проте алгебраїчний контракт залишається тотожним:

- Модульне піднесення до степеня `g^k mod p` замінюється на скалярне множення точки кривої: `R = k · G`.
- Публічний ключ обчислюється як `Y = x · G`.
- Хеш-виклик обчислюється над стиснутими координатами точок: `c = H(G, Y, R) mod q`.
- Підтверджувальна відповідь обчислюється точно так само у полі скалярів: `s = (k + c · x) mod q`.
- Верифікатор перевіряє геометричну тотожність точок на кривій: `s · G = R + c · Y`.

Використання еліптичних кривих дозволяє скоротити розмір доказу `π = (R, s)` до 64 байтів (32 байти для стиснутої координати `R` та 32 байти для скаляра `s`), що робить його ідеальним для використання в обмежених каналах зв'язку та блокчейн-транзакціях (стандарт BIP-340 Schnorr Signatures).
