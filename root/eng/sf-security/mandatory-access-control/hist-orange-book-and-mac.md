# 📜 Історія обов'язкового контролю доступу: від Multics та ADEPT-50 до «Помаранчевої книги» та SELinux

У 1960-х роках перехід від пакетної обробки перфокарт до багатокористувацьких систем із розподілом часу (time-sharing) виявив критичну проблему: різні термінали, підключені до однієї ЕОМ, належали операторам із кардинально різними рівнями допуску до державної та військової таємниці.

Перші спроби розмежування доступу в системах на кшталт ADEPT-50 (розробленої корпорацією SDC у 1967 році для військових командних центрів) та операційної системи Multics опиралися на класичні списки контролю доступу (ACL). Проте списки доступу залишали повний контроль над правами у руках користувача-власника. Якщо військовослужбовець із допуском до таємних документів запускав текстовий процесор чи калькулятор, написаний стороннім розробником, цей процес отримував усі права користувача. Програма могла без відома оператора створити загальнодоступну копію секретного звіту у відкритій теці.

Цей сценарій отримав назву «атака троянського коня» (англ. *Trojan Horse attack*). Вона довела, що дискреційний контроль доступу (DAC) неспроможний гарантувати збереження таємниці в умовах виконання стороннього або скомпрометованого коду.

### Звіт Андерсона та концепція монітора звернень (1972)

У жовтні 1972 року заступник директора з досліджень ВПС США Джеймс Андерсон опублікував фундаментальний технічний звіт *Computer Security Technology Planning Study* (відомий як Anderson Report). Андерсон вперше сформулював концепцію **монітора звернень** (англ. *Reference Monitor Concept*) — абстрактної машини в серці операційної системи, яка контролює кожен зв'язок між суб'єктами (процесами) та об'єктами (пам'яттю, файлами, пристроями).

Андерсон визначив три обов'язкові вимоги до монітора звернень:
1. **Повна невідхильність (Complete Mediation):** механізм перевірки викликається на кожній спробі доступу, і його неможливо обійти жодним апаратним чи програмним шляхом.
2. **Захищеність від модифікації (Tamperproof):** сам код монітора звернень та його структури даних захищені від несанкціонованої зміни будь-яким процесом простору користувача.
3. **Верифіковність (Verifiable):** реалізація має бути настільки компактною та простою, щоб її коректність можна було довести формальними математичними методами.

Сукупність монітора звернень, апаратних кілець захисту процесора та ядра операційної системи отримала назву **довірена обчислювальна база** (англ. *Trusted Computing Base*, TCB).

### Модель Белла — ЛаПадули (1973)

На замовлення ВПС США дослідники корпорації MITRE Девід Белл та Леонард ЛаПадула розробили математичну модель, яка перевела американські правила військового грифування в алгоритми операційної системи. 

У моделі Bell-LaPadula інформація отримала мітки двох типів: ієрархічні рівні таємності (Unclassified, Confidential, Secret, Top Secret) та неієрархічні категорії допуску (наприклад, Crypto, Nuclear). Щоб автоматично заблокувати витік даних через троянські програми, автори ввели два базові правила: «no read up» (заборона читати документи вищого рівня таємності) та «no write down» (заборона процесу з високим рівнем таємності записувати дані у відкриті файли).

### Стандарт TCSEC та «Помаранчева книга» (1983–1985)

У 1983 році Національний центр комп'ютерної безпеки США (NCSC) видав стандарт *DoD 5200.28-STD*, відомий як «Помаранчева книга» (англ. *Orange Book*) через характерний колір обкладинки. Це був перший у світі формальний норматив оцінки захищеності комп'ютерних систем.

Стандарт встановив чотири класи довіри (від найнижчого D до найвищого A):
- **Клас C (C1, C2):** Дискреційний захист (DAC), вимога автентифікації користувачів та ведення журналів аудиту (рівень комерційних Unix та Windows NT).
- **Клас B (B1, B2, B3):** Обов'язковий мандатний захист (MAC). Усі об'єкти системи обов'язково отримують мітки безпеки, а операційна система забезпечує дотримання моделі Белла — ЛаПадули незалежно від бажання користувача.
- **Клас A (A1):** Верифікований захист. Проєкт TCB має бути повністю верифікований формальними математичними доказами теорем безпеки.

Поява «Помаранчевої книги» стимулювала створення спеціалізованих безпечних ОС — Trusted IRIX, Trusted Solaris, PitBull та BAE Systems XTS-400. Проте ці системи були пропрієтарними, надзвичайно дорогими та складними в адмініструванні.

### Проєкт FLASK та народження SELinux (1990-ті — 2000)

На початку 1990-х років Агентство національної безпеки США (NSA) разом із дослідницькою лабораторією Університету Юти створили архітектуру **FLASK** (англ. *Flux Advanced Security Kernel*) у межах мікроядерної системи Fluke. FLASK ввела критичне розділення:
- **Точка застосування політики (Policy Enforcement Point, PEP):** код ядра, який перехоплює системні виклики та запитує дозвіл.
- **Сервер безпеки та ухвалення рішень (Policy Decision Point, PDP):** ізольований компонент, який зберігає правила та обчислює вердикт.

Для прискорення перевірок у FLASK було реалізовано кеш векторів доступу (AVC — Access Vector Cache), який усунув затримки повторних перевірок.

У грудні 2000 року NSA несподівано для індустрії відкрила вихідний код проєкту **Security-Enhanced Linux (SELinux)** як набір патчів до ядра Linux 2.4. Це стало переломним моментом: вперше повноцінна мандатна система захисту класу MLS/TE стала доступною в загальнодоступній відкритій операційній системі.

### Linux Security Modules (LSM) та сучасний етап

Коли розробники SELinux запропонували включити патчі безпосередньо в основну гілку ядра Linux, Лінус Торвальдс та спільнота розробників відхилили пряму інтеграцію однієї конкретної моделі. Торвальдс зазначив, що ядро не повинно бути жорстко прив'язане до конкретного формату міток NSA, а має надати узагальнений механізм підключення різних модулів безпеки.

У 2001 році на Linux Kernel Summit було започатковано проєкт **Linux Security Modules (LSM)**. Розробники (серед яких були представники NSA, WireX, IBM, Immunix) створили нейтральну інфраструктуру зворотних викликів (хуків), розташованих у точках ухвалення рішень VFS, мережевого стека та підсистеми процесів.

У 2003 році ядро Linux 2.6 офіційно вийшло з підтримкою LSM. Це відкрило шлях не лише для SELinux (який увійшов до Red Hat Enterprise Linux у 2004 році), але й для альтернативних підходів: шляхового захисту AppArmor (розробленого Immunix/SUSE), спрощеного SMACK (для вбудованих систем та мобільних платформ) і сучасних підсистем BPF-LSM та Landlock.
