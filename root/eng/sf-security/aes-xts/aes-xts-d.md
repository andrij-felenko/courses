# Режим AES-XTS: криптографічний захист блокових пристроїв та носіїв прямого доступу

<preknowlist>
- [Блоковий шифр](root:sf-security/block-cipher) — оборотна симетрична підстановка фіксованих блоків, алгоритм Rijndael (AES) та базові режими перетворення.
- [Шифрування даних у спокої](root:sf-security/encryption-at-rest) — модель загроз фізичного вилучення накопичувачів, рівні впровадження криптографії та ієрархія ключів.
- [Автентифіковане шифрування](root:sf-security/authenticated-encryption) — режими зі збереженням цілісності (AEAD), наслідки відсутності криптографічного контролю автентичності.
</preknowlist>

Фізичні накопичувачі прямого доступу — твердотільні диски NVMe, жорсткі диски HDD, карти пам'яті та вбудовані флешмодулі eMMC/UFS — оперують даними не як неперервним байтовим потоком, а як масивом незалежних апаратних секторів фіксованого розміру (зазвичай 512 або 4096 байтів). Операційна система повинна мати можливість у довільний момент часу зчитати або перезаписати будь-який окремий сектор посеред диска без необхідності розшифровувати чи перечитувати весь накопичувач. Це вимагає від криптографічного перетворення суворого виконання умови **нульового розширення даних** (англ. *in-place encryption*): зашифрований сектор на носії мусить мати точно таку саму довжину до останнього байта, що й вихідний відкритий сектор. Спроба застосувати класичні мережеві або потокові режими шифрування на рівні фізичних дисків призводить або до катастрофічного витоку внутрішньої структури файлових систем, або до руйнування апаратного інтерфейсу накопичувача. Для розв'язання цієї задачі було розроблено стандарт **IEEE Std 1619-2007** та **NIST SP 800-38E**, які закріпили для блокових пристроїв спеціалізований режим **XTS-AES** (*XEX-based Tweaked-codebook mode with Ciphertext Stealing*).

### Фізична геометрія накопичувачів та вимога нульового розширення

Архітектура систем збереження даних базується на понятті логічного блокового адресування (англ. *Logical Block Addressing*, LBA). Дисковий накопичувач представляє свій простір операційній системі як лінійний масив секторів, пронумерованих від `0` до `N-1`. Протягом десятиліть стандартом був сектор розміром 512 байтів (формат 512n). З появою сучасних жорстких дисків великої ємності та флешнакопичувачів індустрія перейшла на формат Advanced Format із фізичними секторами по 4096 байтів (4Kn або 512e з емуляцією).

Контролери накопичувачів та шини передачі даних (NVMe PCIe, SATA, SAS) оптимізовані під апаратну атомарність операцій: запис одного сектора є неподільною операцією, захищеною апаратними механізмами захисту від раптового знеструмлення (Power Loss Protection, PLP). Якщо операційна система надсилає запит на запис 4096 байтів за адресою LBA `1048576`, контролер записує рівно 4096 байтів у відповідні фізичні комірки флешпам'яті або магнітні доріжки.

```
+-----------------------------------------------------------------------+
| Фізичний сектор LBA k (4096 байтів)                                   |
| Відкритий текст: [ 4096 байтів даних файлової системи ]               |
|                               ↓ Шифрування in-place                   |
| Зашифрований сектор: [ 4096 байтів шифротексту на носії ]             |
+-----------------------------------------------------------------------+
```

Якщо криптографічний алгоритм спробує додати до сектора хоча б один байт метаданих (наприклад, вектор ініціалізації чи імітовставку автентифікації), розмір сектора зросте (наприклад, з 4096 до 4128 байтів). Це призводить до трьох нездоланних апаратних проблем:
1. **Зсув секторів (Sector Misalignment):** Розмір сектора перестає бути степенем двійки, що руйнує відповідність між дисковими блоками та сторінками оперативної пам'яті ядра ОС (4096 байтів). Будь-яка операція запису вимагатиме важких циклів читання-модифікації-запису (Read-Modify-Write), що знижує пропускну здатність вводу-виводу в десятки разів.
2. **Втрата апаратної атомарності:** Контролер більше не може гарантувати атомарний запис сектора разом із його метаданими під час збою живлення, що призводить до незворотного пошкодження структур файлової системи.
3. **Несумісність із протоколами накопичувачів:** Стандартні накопичувачі споживчого класу (NVMe/SATA) апаратно підтримують винятково геометрію 512 або 4096 байтів. Нестандартні розміри секторів (520, 528 або 4104 байти) підтримуються лише спеціалізованими корпоративними дисками SAS/SAN із захистом Data Integrity Field (DIF/DIX T10).

Криптографічний захист блокових пристроїв зобов'язаний працювати в жорстких рамках: **розмір шифротексту кожного сектора повинен строго дорівнювати розміру відкритого тексту**.

### Чому класичні режими шифрування непридатні для дисків

Шифрування блокових пристроїв принципово відрізняється від захисту мережевих каналів зв'язку (TLS чи IPsec). У мережевому пакеті можна легко виділити додаткові 16 або 32 байти під вектор ініціалізації (IV) та імітовставку (MAC). На дисковому накопичувачі кожен фізичний сектор має фіксовану геометрію на рівні контролера. Порівняймо поведінку стандартних криптографічних режимів в умовах дискового вводу-виводу.

![Порівняння режимів шифрування на секторах накопичувача](/root/eng/sf-security/aes-xts/img/block-device-modes-comparison.svg)
*Порівняння чотирьох підходів до шифрування секторів: від небезпечного витоку шаблонів в ECB до спеціалізованого стандарту XTS-AES.*

#### 1. Режим електронної кодової книги (ECB): витік шаблонів

Режим ECB (англ. *Electronic Codebook*) шифрує кожен 16-байтовий блок відкритого тексту абсолютно незалежно на одному й тому самому ключі. Якщо два блоки відкритого тексту ідентичні, їхні шифротексти збігаються байт-у-байт:

```
C[j] = AES_Enc(K, P[j])
```

У контексті файлових систем це призводить до повної компрометації структури сховища:
* **Нульові блоки:** Більшість файлових систем ініціалізують порожній дисковий простір довгими послідовностями нульових байтів. У режимі ECB нульові блоки `0x00...00` перетворюються на однаковий 16-байтний шифротекст. Зловмисник, спостерігаючи накопичувач, точно бачить карту заповненості диска, фрагментацію та розміщення файлів.
* **Таблиці розміщення та метадані:** Бітові карти зайнятого простору (ext4 block bitmaps), суперблоки, заголовки каталогів та системні структури містять фіксовані магічні числа та повторювані поля. Зловмисник без розшифрування визначає тип файлової системи, межі файлів і навіть версію операційної системи.
* **Структуровані файли:** У базах даних (SQLite, PostgreSQL, InnoDB) сторінки даних містять однакові системні префікси. Класична ілюстрація вразливості ECB — пінгвін Tux, контури якого залишаються чітко видимими після шифрування зображення через збереження локальних патернів однакових пікселів.

#### 2. Режим зчеплення блоків (CBC): проблема паралелізму та підміна бітів

Режим CBC (англ. *Cipher Block Chaining*) намагається усунути повторення однакових блоків за рахунок додавання шифротексту попереднього блока до відкритого тексту поточного:

```
C[j] = AES_Enc(K, P[j] ⊕ C[j-1])
```

Проте для блокових накопичувачів режим CBC створює дві нездоланні інженерні проблеми:
1. **Неможливість розпаралелювання шифрування:** Щоб зашифрувати блок `j`, процесор зобов'язаний дочекатися завершення шифрування блока `j-1`. На сучасних процесорах із багаторівневими конвеєрами та багатоядерними контролерами NVMe це знижує пропускну здатність запису у 4–8 разів, оскільки апаратні інструкції AES-NI не можуть виконуватися паралельно над кількома блоками одного сектора.
2. **Вразливість до передбачуваних векторів ініціалізації (IV):** Якщо як `IV` сектора береться його логічний номер (LBA), виникає можливість атаки Вотермаркінгу (англ. *watermarking attack*). Навіть ускладнений варіант CBC-ESSIV (*Encrypted Sector-Salt Initial Vector*), де `IV` шифрується окремим гешем від ключа, зберігає критичну вразливість **підміни бітів** (*bit-flipping*):
   
   ```
   P[j] ⊕ Δ = AES_Dec(K, C[j]) ⊕ (C[j-1] ⊕ Δ)
   ```
   
   Зловмисник, модифікуючи блок `C[j-1]`, передбачувано змінює відкритий текст наступного блока `P[j]` на маску `Δ`, ціною перетворення блока `P[j-1]` на псевдовипадкове сміття. У структурах файлових систем це дозволяє цілеспрямовано змінювати системні ідентифікатори користувачів (наприклад, скидати `UID` з 1000 на 0) або перемикати прапорці дозволів `chmod`.

#### 3. Лічильниковий режим (CTR) та режими AEAD: ризик повторного використання Nonce

Потокові та лічильникові режими — такі як CTR, а також сучасні стандарти автентифікованого шифрування AEAD (GCM, ChaCha20-Poly1305) — перетворюють блоковий шифр на генератор гами, яка накладається на відкритий текст операцією `XOR`:

```
C = P ⊕ AES_Enc(K, Nonce || Counter)
```

Застосування режиму CTR на рівні дискових секторів створює **катастрофу повторного використання одноразового коду** (англ. *nonce reuse catastrophe*). Якщо файлова система перезаписує один і той самий сектор `S` новими даними, а `Nonce` формується детерміновано з номера сектора `S`, гама шифрування залишається ідентичною. Зловмисник, зберігши два послідовні знімки одного сектора (`C1` та `C2`), миттєво отримує `XOR` двох відкритих текстів:

```
C1 ⊕ C2
= (P1 ⊕ Gamma) ⊕ (P2 ⊕ Gamma)    [підстановка визначення гамування в CTR]
= P1 ⊕ P2 ⊕ (Gamma ⊕ Gamma)      [комутативність та асоціативність XOR]
= P1 ⊕ P2                        [самоанулювання однакової гами: Gamma ⊕ Gamma = 0]
```

Знання `P1 ⊕ P2` дозволяє за допомогою методів частотного аналізу та атак із використанням передбачуваних відкритих текстів (Crib Dragging) повністю відновити відкритий вміст обох версій сектора.

Щоб запобігти цьому, режим вимагав би використання унікального випадкового або монотонного `Nonce` для кожного запису, а також збереження 128-бітного тегу автентифікації MAC (у режимі GCM). Проте збереження додаткових 28–32 байтів на кожен 512-байтний або 4096-байтний сектор фізично несумісне зі стандартними контролерами дисків і руйнує апаратну атомарність дискових операцій.

Детальний аналіз історичних дискусій та причин відхилення режимів CBC та LRW викладено в історичній довідці: [стандартизація IEEE 1619: еволюція криптографії сховищ від LRW до XTS](root:sf-security/aes-xts/hist-ieee1619-standardization.md).

### Архітектура та математичний апарат режиму XTS-AES

Режим XTS-AES побудований на базі криптографічної схеми **XEX** (*XOR-Encrypt-XOR*), запропонованої вченим Філіпом Роґавеєм. Ідея полягає у створенні **шифру з налаштуванням** (англ. *tweakable block cipher*), де кожне 16-байтове зміщення всередині диска отримує власну унікальну маску-твік `T`, яка залежить від номера сектора та позиції блока в секторі.

![Схема шифрування та дешифрування блоку в режимі XTS-AES](/root/eng/sf-security/aes-xts/img/xts-block-structure.svg)
*Внутрішня структура обробки блоку в режимі XTS-AES: генерація маски T через поліноміальне множення на альфа та подвійне відбілювання XOR-Encrypt-XOR.*

#### Структура подвійного ключа

Режим XTS вимагає подвоєного розміру ключа порівняно зі стандартним AES. Загальний ключ `K` розділяється на два рівні незалежні ключі однакової довжини:

```
K = Key1 || Key2
```

* **XTS-AES-128:** загальний ключ 256 бітів (`Key1` — 128 бітів, `Key2` — 128 бітів).
* **XTS-AES-256:** загальний ключ 512 бітів (`Key1` — 256 бітів, `Key2` — 256 бітів).

Призначення ключів:
* **`Key2` (Твік-ключ):** використовується винятково для первинного шифрування номера сектора та створення базового вектора налаштування `T[0]`.
* **`Key1` (Ключ даних):** використовується для безпосереднього шифрування та дешифрування маскованих блоків відкритого тексту.

> [!IMPORTANT]
> **Критична вимога безпеки:** Ключі `Key1` та `Key2` повинні бути криптографічно незалежними (`Key1 ≠ Key2`). Якщо `Key1 = Key2`, режим деградує, і зловмисник отримує можливість проводити атаку на виявлення відкритих текстів за допомогою підібраного твіка. Усі реалізації ядра Linux та вимоги FIPS 140-3 автоматично відхиляють ініціалізацію XTS, якщо обидві половини ключа збігаються.

#### Генерація базового твіка сектора

Нехай `i` — 128-бітне число, що представляє номер логічного сектора накопичувача (LBA, англ. *Logical Block Address*). У стандарті IEEE 1619 номер сектора кодується як 64-бітне беззнакове ціле у форматі Little-Endian, а решта 64 біти заповнюються нулями.

Базовий твік `T[0]` для нульового блоку сектора обчислюється шляхом одноразового шифрування номера сектора на ключі `Key2`:

```
T[0] = AES_Enc(Key2, i)
```

Завдяки цьому номер сектора `i` перетворюється на непередбачувану 128-бітну псевдовипадкову послідовність.

#### Множення на αʲ у скінченному полі GF(2¹²⁸)

Сектор накопичувача складається з послідовності 16-байтових блоків `P[0], P[1], ..., P[m-1]` (наприклад, для сектора 512 байтів `m = 32`; для сектора 4096 байтів `m = 256`).

Щоб не виконувати дороге шифрування AES для кожного окремого блоку всередині сектора, маска `j`-го блоку `T[j]` обчислюється за допомогою швидкої алгебраїчної операції в полі Галуа `GF(2¹²⁸)`:

```
T[j] = T[0] ⊗ αʲ   (у полі GF(2¹²⁸))
```

Послідовні маски обчислюються ітеративно:

```
T[j] = T[j-1] ⊗ α
```

Стандарт IEEE 1619-2007 визначає поле `GF(2¹²⁸)` за допомогою первісного редукційного полінома:

```
P(x) = x¹²⁸ + x⁷ + x² + x + 1
```

Примітивний елемент `α` відповідає поліному `x`, що у 16-байтовому представленні Little-Endian відповідає значенню `0x02` у нульовому байті.

Операція множення 128-бітного масиву `T` на `α` виконується за один прохід:
1. Усі байти масиву `T[0..15]` зсуваються вліво на 1 біт із переносом між сусідніми байтами (від молодших індексів до старших).
2. Якщо старший біт найстаршого байта `T[15]` (коефіцієнт при `x¹²⁷`) до зсуву дорівнював 1, виникає переповнення `x¹²⁸`, яке замінюється за модулем `P(x)` шляхом операції `XOR` із константою редукції `0x87` (`10000111₂`) у наймолодшому байті `T[0]`.

Повне математичне виведення властивостей поля, циклічної групи та прикладів обчислень розібрано у вставці: [алгебра поля GF(2^128) та множення твіка на альфа](root:sf-security/aes-xts/math-gf128-tweak-multiplication.md).

#### Пряме та зворотне перетворення блоку

Маючи обчислений твік `T[j]`, шифрування `j`-го блоку відкритого тексту `P[j]` виконується у три кроки (подвійне відбілювання, або *whitening*):

```
PP[j] = P[j] ⊕ T[j]                [вхідне відбілювання: маскування відкритого тексту]
CC[j] = AES_Enc(Key1, PP[j])       [основне шифрування на першому ключі]
C[j]  = CC[j] ⊕ T[j]               [вихідне відбілювання: формування шифротексту]
```

Дешифрування є дзеркальним перетворенням, яке використовує ту саму маску `T[j]` та процедуру розшифрування AES:

```
CC[j] = C[j] ⊕ T[j]                [зняття вихідної маски з шифротексту]
PP[j] = AES_Dec(Key1, CC[j])       [основне дешифрування блоку на першому ключі]
P[j]  = PP[j] ⊕ T[j]               [відновлення початкового відкритого тексту]
```

Оскільки операція `XOR` є абсолютно симетричною (`A ⊕ B ⊕ B = A`), перетворення є суворо оборотним. Якщо відкритий блок `P[j]` розташований у двох різних секторах `i1` та `i2`, їхні базові твіки `T[0](i1) ≠ T[0](i2)` будуть абсолютно різними, утворюючи повністю некорельовані шифротексти.

### Механізм викрадення шифротексту (Ciphertext Stealing)

У більшості випадків розмір сектора накопичувача є кратним 16 байтам (512, 1024, 2048, 4096 байтів). Проте стандарт IEEE 1619 та специфікація NIST SP 800-38E проектувалися як універсальний стандарт захисту будь-яких пристроїв збереження даних (зокрема стрічкових накопичувачів та нерівних мережевих блоків). Якщо довжина блоку даних `N` не кратна 16 байтам, виникає потреба шифрування без збільшення загального розміру.

Класичне доповнення (наприклад, PKCS#7) додає від 1 до 16 байтів, що заборонено на фізичних носіях. Для розв'язання цієї проблеми в XTS застосовується алгоритм **Ciphertext Stealing (CTS)**.

![Механізм викрадення шифротексту (Ciphertext Stealing)](/root/eng/sf-security/aes-xts/img/ciphertext-stealing-flow.svg)
*Порядок обробки неповного кінцевого сектора в режимі Ciphertext Stealing: запозичення байтів шифротексту з передостаннього блоку для формування повнорозмірного блоку.*

Нехай довжина даних становить `N` байтів (`N ≥ 16`). Дані розбиваються на `m` повних 16-байтних блоків `P[0], ..., P[m-1]` та неповний залишок `P[m]` довжиною `b` байтів (`1 ≤ b < 16`).

#### Процедура шифрування за схемою CTS

1. Блоки `P[0], ..., P[m-2]` шифруються за стандартною схемою XTS із твіками `T[0], ..., T[m-2]`.
2. Передостанній повний блок `P[m-1]` (16 байтів) шифрується з поточним твіком `T[m-1]`, утворюючи проміжний 16-байтний блок шифротексту `C'[m-1]`:
   
   ```
   C'[m-1] = AES_Enc(Key1, P[m-1] ⊕ T[m-1]) ⊕ T[m-1]
   ```
3. Перші `b` байтів блоку `C'[m-1]` відокремлюються і стають фінальним шифротекстом кінцевого неповного блоку `C[m]`:
   
   ```
   C[m] = head(C'[m-1], b)
   ```
4. Решта `16 - b` байтів блоку `C'[m-1]` (хвіст) «викрадаються» і конкатенуються з відкритим текстом `P[m]` (довжиною `b` байтів), утворюючи повнорозмірний 16-байтний блок `P'[m-1]`:
   
   ```
   P'[m-1] = P[m] || tail(C'[m-1], 16 - b)
   ```
5. Обчислюється наступний твік `T[m] = T[m-1] ⊗ α`.
6. Сконструйований блок `P'[m-1]` шифрується з новим твіком `T[m]`, утворюючи фінальний 16-байтний шифротекст `C[m-1]`:
   
   ```
   C[m-1] = AES_Enc(Key1, P'[m-1] ⊕ T[m]) ⊕ T[m]
   ```

У результаті сумарна довжина вихідного шифротексту `(m × 16 + b)` точно дорівнює вхідній довжині відкритого тексту.

#### Процедура дешифрування CTS

1. Блоки `C[0], ..., C[m-2]` дешифруються за стандартною схемою XTS.
2. Обчислюються обидва твіки: `T[m-1]` та `T[m] = T[m-1] ⊗ α`.
3. Блок `C[m-1]` дешифрується з твіком `T[m]`, утворюючи проміжний блок `P'[m-1]`:
   
   ```
   P'[m-1] = AES_Dec(Key1, C[m-1] ⊕ T[m]) ⊕ T[m]
   ```
4. Перші `b` байтів блоку `P'[m-1]` є відновленим відкритим текстом неповного кінцевого блоку: `P[m] = head(P'[m-1], b)`.
5. Хвіст блоку `P'[m-1]` (довжиною `16 - b` байтів) поєднується із шифротекстом `C[m]`, відновлюючи повний блок `C'[m-1]`:
   
   ```
   C'[m-1] = C[m] || tail(P'[m-1], 16 - b)
   ```
6. Блок `C'[m-1]` дешифрується з твіком `T[m-1]`, повертаючи відкритий текст `P[m-1]`:
   
   ```
   P[m-1] = AES_Dec(Key1, C'[m-1] ⊕ T[m-1]) ⊕ T[m-1]
   ```

### Криптографічні межі стійкості та модель загроз

Розуміння меж безпеки XTS-AES є критичним для проектування захищених систем зберігання. XTS гарантує винятково **конфіденційність** даних і не є алгоритмом автентифікованого шифрування (не містить імітовставки).

![Модель загроз та обмеження стійкості режиму AES-XTS](/root/eng/sf-security/aes-xts/img/xts-attack-surface.svg)
*Чотири головні вектори вразливостей режиму XTS-AES та інженерні механізми їх нейтралізації на рівні операційної системи.*

#### 1. Вразливість до маніпуляцій всередині сектора (Malleability)

Якщо зловмисник отримує фізичний доступ до носія і модифікує 16-байтовий зашифрований блок `C[j]`, операційна система під час зчитування цього сектора виконає стандартне дешифрування:

```
CC[j] = (C[j] ⊕ Δ) ⊕ T[j]
PP[j] = AES_Dec(Key1, CC[j])
P[j]  = PP[j] ⊕ T[j]
```

Оскільки вхідний блок блокового шифру спотворено маскою `Δ`, на виході алгоритму AES виникає лавинний ефект: увесь 16-байтовий блок `P[j]` перетворюється на псевдовипадкове статистичне сміття. Проте **жодної криптографічної помилки чи аварійної зупинки не виникає**. Усі сусідні блоки сектора (`P[j-1], P[j+1]`) розшифровуються абсолютно коректно.

Якщо файлова система або додаток не перевіряють контрольну суму структури даних, сміття у критичних полях (наприклад, у таблиці покажчиків файлової системи) може спричинити виконання шкідливого коду або пошкодження даних.

#### 2. Атака повторного відтворення секторів (Replay Attack)

Оскільки шифрування сектора залежить винятково від його логічної адреси (LBA) та статичного ключа, шифротекст сектора не прив'язаний до часу запису. Зловмисник, маючи можливість перезаписувати сирі сектори (наприклад, у віртуалізованому середовищі чи викравши резервну копію), може зберегти зашифрований стан сектора `S` у момент часу `t1` і перезаписати ним сектор `S` у момент часу `t2`. Під час зчитування драйвер розшифрує старі валідні дані без жодного попередження про підміну версії.

#### 3. Перестановка блоків усередині сектора

Якщо зловмисник поміняє місцями блоки `C[j]` та `C[k]` у межах одного сектора, під час розшифрування обидва блоки розшифруються у випадкове сміття, оскільки твіки `T[j] = T[0] ⊗ αʲ` та `T[k] = T[0] ⊗ αᵏ` є різними. Проте якщо відкритий текст блоків був заздалегідь відомий атакуючому, атакуючий може аналізувати відмінності масок.

#### 4. Обмеження обсягу зашифрованих даних на один ключ

Згідно зі спеціальною публікацією **NIST SP 800-38E**:
* Максимальний розмір одного блоку даних (сектора або data unit), що шифрується з одним базовим твіком, не повинен перевищувати `2²⁰` 16-байтних блоків (16 МіБ).
* Загальна кількість блоків, зашифрованих на одній парі ключів `(Key1, Key2)`, не повинна перевищувати `2⁶⁴` блоків AES.

Для сучасних дисків петабайтного обсягу це обмеження виконується з величезним запасом, проте ротація головних ключів томів залишається обов'язковою практикою безпеки.

> 🔧 **Навіщо це.** Якщо додаток або операційна система вимагають абсолютного захисту від підміни секторів і гарантії цілісності, у ядрі Linux використовується комбінація `dm-crypt` із підсистемою `dm-integrity`. Модуль `dm-integrity` виділяє приховану службову область на накопичувачі, де зберігає 32-байтний криптографічний тег HMAC-SHA256 для кожного сектора, перетворюючи дисковий стек на повноцінну систему автентифікованого зберігання даних.

Повний перелік параметрів ядра та конфігурацій підсистеми `dm-crypt` зібрано у довіднику: [інтерфейс AES-XTS у підсистемах dm-crypt та AF_ALG ядра Linux](root:sf-security/aes-xts/api-kernel-crypto-xts.md).

### Апаратна оптимізація та системна інтеграція

Сучасні процесори досягають швидкості шифрування XTS понад 5–10 ГБ/с на одне процесорне ядро завдяки векторним криптографічним розширенням:

1. **AES-NI та VAES (Vector AES):** Інструкції `_mm_aesenc_si128` (x86) та `vaesenc` (AVX-512) виконують один раунд перетворення AES над 128-бітними або 512-бітними регістрами. Конвеєр процесора дозволяє обробляти одночасно 4 або 8 блоків сектора паралельно, оскільки в режимі XTS блоки не мають взаємної залежності.
2. **Безпереносне множення (PCLMULQDQ / VPCLMULQDQ):** Генерація послідовності твіків `T[j] = T[0] ⊗ αʲ` виконується векторно без використання повільних таблиць пошуку (Lookup Tables), що повністю виключає витоки ключів через кеш-пам'ять (Cache-timing attacks).
3. **Підсистеми ОС:**
   * **Linux:** `dm-crypt` (LUKS2) використовує шифр `aes-xts-plain64` як стандарт за замовчуванням.
   * **Windows:** `BitLocker` починаючи з Windows 10 (Build 1511) перейшов з CBC-Elephant на `XTS-AES-128` та `XTS-AES-256`.
   * **macOS / iOS:** `FileVault 2` та шифрування файлової системи APFS використовують `XTS-AES-128` для шифрування метаданих і тіл файлів.

### Повна інженерна реалізація XTS-AES на C та C++

Нижче наведено самодостатню реалізацію криптографічного перетворення XTS-AES з константним часом множення в полі `GF(2¹²⁸)` та підтримкою Ciphertext Stealing для обох мов програмування.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <string.h>
#include <stdbool.h>

#define AES_BLOCK_LEN 16

/* Інтерфейс блокового шифрування AES-128 / AES-256 */
typedef struct {
    uint32_t round_keys_enc[60];
    uint32_t round_keys_dec[60];
    int rounds;
} aes_core_t;

void aes_core_init(aes_core_t *ctx, const uint8_t *key, size_t key_bytes);
void aes_core_encrypt(const aes_core_t *ctx, const uint8_t in[16], uint8_t out[16]);
void aes_core_decrypt(const aes_core_t *ctx, const uint8_t in[16], uint8_t out[16]);

/* Структура контексту XTS-AES */
typedef struct {
    aes_core_t cipher_data;   /* Key1: шифрування відбілених блоків даних */
    aes_core_t cipher_tweak;  /* Key2: шифрування початкового твіка LBA */
} xts_context_t;

/* Множення на alpha в полі GF(2^128) за стандартом IEEE 1619 у константному часі */
static void xts_mul_alpha(uint8_t t[16]) {
    uint8_t carry = 0;
    for (int i = 0; i < 16; ++i) {
        uint8_t next_carry = t[i] >> 7;
        t[i] = (uint8_t)((t[i] << 1) | carry);
        carry = next_carry;
    }
    /* Маска константного часу: 0x87, якщо carry != 0, інакше 0x00 */
    uint8_t mask = (uint8_t)(-(int8_t)carry) & 0x87;
    t[0] ^= mask;
}

/* Ініціалізація ключів: 32 байти для AES-128-XTS, 64 байти для AES-256-XTS */
bool xts_setup(xts_context_t *ctx, const uint8_t *key, size_t total_key_len) {
    if (!ctx || !key || (total_key_len != 32 && total_key_len != 64)) {
        return false;
    }
    size_t k_len = total_key_len / 2;
    /* Захист від однакових ключів K1 == K2 */
    if (memcmp(key, key + k_len, k_len) == 0) {
        return false;
    }
    aes_core_init(&ctx->cipher_data, key, k_len);
    aes_core_init(&ctx->cipher_tweak, key + k_len, k_len);
    return true;
}

/* Шифрування сектора з автоматичною обробкою неповного залишку через CTS */
bool xts_encrypt(const xts_context_t *ctx, const uint8_t tweak_lba[16],
                 const uint8_t *src, size_t len, uint8_t *dst) {
    if (!ctx || !tweak_lba || !src || !dst || len < AES_BLOCK_LEN) {
        return false;
    }

    uint8_t t[AES_BLOCK_LEN], pp[AES_BLOCK_LEN], cc[AES_BLOCK_LEN];

    /* 1. Базовий твік T0 = AES(Key2, LBA) */
    aes_core_encrypt(&ctx->cipher_tweak, tweak_lba, t);

    size_t full_blocks = len / AES_BLOCK_LEN;
    size_t rem = len % AES_BLOCK_LEN;
    size_t lim = (rem == 0) ? full_blocks : (full_blocks - 1);

    /* 2. Основний цикл повних блоків */
    for (size_t i = 0; i < lim; ++i) {
        const uint8_t *p_blk = src + i * AES_BLOCK_LEN;
        uint8_t *c_blk = dst + i * AES_BLOCK_LEN;

        for (int k = 0; k < AES_BLOCK_LEN; ++k) pp[k] = p_blk[k] ^ t[k];
        aes_core_encrypt(&ctx->cipher_data, pp, cc);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) c_blk[k] = cc[k] ^ t[k];

        xts_mul_alpha(t);
    }

    /* 3. Обробка CTS для залишку */
    if (rem > 0) {
        size_t m = full_blocks;
        const uint8_t *p_m_minus_1 = src + (m - 1) * AES_BLOCK_LEN;
        const uint8_t *p_m = src + m * AES_BLOCK_LEN;
        uint8_t *c_m_minus_1 = dst + (m - 1) * AES_BLOCK_LEN;
        uint8_t *c_m = dst + m * AES_BLOCK_LEN;

        uint8_t c_prime[AES_BLOCK_LEN];
        for (int k = 0; k < AES_BLOCK_LEN; ++k) pp[k] = p_m_minus_1[k] ^ t[k];
        aes_core_encrypt(&ctx->cipher_data, pp, cc);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) c_prime[k] = cc[k] ^ t[k];

        memcpy(c_m, c_prime, rem);

        uint8_t p_prime[AES_BLOCK_LEN];
        memcpy(p_prime, p_m, rem);
        memcpy(p_prime + rem, c_prime + rem, AES_BLOCK_LEN - rem);

        xts_mul_alpha(t);

        for (int k = 0; k < AES_BLOCK_LEN; ++k) pp[k] = p_prime[k] ^ t[k];
        aes_core_encrypt(&ctx->cipher_data, pp, cc);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) c_m_minus_1[k] = cc[k] ^ t[k];
    }

    return true;
}

/* Дешифрування сектора */
bool xts_decrypt(const xts_context_t *ctx, const uint8_t tweak_lba[16],
                 const uint8_t *src, size_t len, uint8_t *dst) {
    if (!ctx || !tweak_lba || !src || !dst || len < AES_BLOCK_LEN) {
        return false;
    }

    uint8_t t[AES_BLOCK_LEN], cc[AES_BLOCK_LEN], pp[AES_BLOCK_LEN];

    aes_core_encrypt(&ctx->cipher_tweak, tweak_lba, t);

    size_t full_blocks = len / AES_BLOCK_LEN;
    size_t rem = len % AES_BLOCK_LEN;
    size_t lim = (rem == 0) ? full_blocks : (full_blocks - 1);

    for (size_t i = 0; i < lim; ++i) {
        const uint8_t *c_blk = src + i * AES_BLOCK_LEN;
        uint8_t *p_blk = dst + i * AES_BLOCK_LEN;

        for (int k = 0; k < AES_BLOCK_LEN; ++k) cc[k] = c_blk[k] ^ t[k];
        aes_core_decrypt(&ctx->cipher_data, cc, pp);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) p_blk[k] = pp[k] ^ t[k];

        xts_mul_alpha(t);
    }

    if (rem > 0) {
        size_t m = full_blocks;
        const uint8_t *c_m_minus_1 = src + (m - 1) * AES_BLOCK_LEN;
        const uint8_t *c_m = src + m * AES_BLOCK_LEN;
        uint8_t *p_m_minus_1 = dst + (m - 1) * AES_BLOCK_LEN;
        uint8_t *p_m = dst + m * AES_BLOCK_LEN;

        uint8_t t_m_minus_1[AES_BLOCK_LEN];
        memcpy(t_m_minus_1, t, AES_BLOCK_LEN);
        xts_mul_alpha(t);

        uint8_t p_prime[AES_BLOCK_LEN];
        for (int k = 0; k < AES_BLOCK_LEN; ++k) cc[k] = c_m_minus_1[k] ^ t[k];
        aes_core_decrypt(&ctx->cipher_data, cc, pp);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) p_prime[k] = pp[k] ^ t[k];

        memcpy(p_m, p_prime, rem);

        uint8_t c_prime[AES_BLOCK_LEN];
        memcpy(c_prime, c_m, rem);
        memcpy(c_prime + rem, p_prime + rem, AES_BLOCK_LEN - rem);

        for (int k = 0; k < AES_BLOCK_LEN; ++k) cc[k] = c_prime[k] ^ t_m_minus_1[k];
        aes_core_decrypt(&ctx->cipher_data, cc, pp);
        for (int k = 0; k < AES_BLOCK_LEN; ++k) p_m_minus_1[k] = pp[k] ^ t_m_minus_1[k];
    }

    return true;
}
```

```cpp
namespace security {

constexpr std::size_t kBlockBytes = 16;

enum class CryptError {
    kInvalidKey,
    kBufferTooSmall,
    kEqualKeysRejected

class BlockCipher {
public:
    virtual ~BlockCipher() = default;
    virtual void Encrypt(const Block128& in, Block128& out) const noexcept = 0;
    virtual void Decrypt(const Block128& in, Block128& out) const noexcept = 0;

class XtsProcessor {
public:
    explicit XtsProcessor(std::unique_ptr<BlockCipher> data_cipher,
                          std::unique_ptr<BlockCipher> tweak_cipher) noexcept
        : data_cipher_(std::move(data_cipher)),
          tweak_cipher_(std::move(tweak_cipher)) {}

    static void GaloisMultiplyAlpha(Block128& t) noexcept {
        uint8_t carry = 0;
        for (std::size_t i = 0; i < kBlockBytes; ++i) {
            uint8_t next_carry = t[i] >> 7;
            t[i] = static_cast<uint8_t>((t[i] << 1) | carry);
            carry = next_carry;
        }
        const uint8_t mask = static_cast<uint8_t>(-(static_cast<int8_t>(carry))) & 0x87;
        t[0] ^= mask;
    }

    [[nodiscard]] std::expected<void, CryptError> EncryptSector(
        const Block128& lba_tweak,
        std::span<const uint8_t> plaintext,
        std::span<uint8_t> ciphertext) const noexcept {

        if (plaintext.size() < kBlockBytes || ciphertext.size() < plaintext.size()) {
            return std::unexpected(CryptError::kBufferTooSmall);
        }

        Block128 t{};
        tweak_cipher_->Encrypt(lba_tweak, t);

        const std::size_t len = plaintext.size();
        const std::size_t full_blocks = len / kBlockBytes;
        const std::size_t rem = len % kBlockBytes;
        const std::size_t lim = (rem == 0) ? full_blocks : (full_blocks - 1);

        Block128 pp{}, cc{};

        for (std::size_t i = 0; i < lim; ++i) {
            const auto offset = i * kBlockBytes;
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                pp[k] = plaintext[offset + k] ^ t[k];
            }
            data_cipher_->Encrypt(pp, cc);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                ciphertext[offset + k] = cc[k] ^ t[k];
            }
            GaloisMultiplyAlpha(t);
        }

        if (rem > 0) {
            const std::size_t m = full_blocks;
            const auto p_m_minus_1_idx = (m - 1) * kBlockBytes;
            const auto p_m_idx = m * kBlockBytes;

            Block128 c_prime{};
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                pp[k] = plaintext[p_m_minus_1_idx + k] ^ t[k];
            }
            data_cipher_->Encrypt(pp, cc);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                c_prime[k] = cc[k] ^ t[k];
            }

            std::memcpy(&ciphertext[p_m_idx], c_prime.data(), rem);

            Block128 p_prime{};
            std::memcpy(p_prime.data(), &plaintext[p_m_idx], rem);
            std::memcpy(p_prime.data() + rem, c_prime.data() + rem, kBlockBytes - rem);

            GaloisMultiplyAlpha(t);

            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                pp[k] = p_prime[k] ^ t[k];
            }
            data_cipher_->Encrypt(pp, cc);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                ciphertext[p_m_minus_1_idx + k] = cc[k] ^ t[k];
            }
        }

        return {};
    }

    [[nodiscard]] std::expected<void, CryptError> DecryptSector(
        const Block128& lba_tweak,
        std::span<const uint8_t> ciphertext,
        std::span<uint8_t> plaintext) const noexcept {

        if (ciphertext.size() < kBlockBytes || plaintext.size() < ciphertext.size()) {
            return std::unexpected(CryptError::kBufferTooSmall);
        }

        Block128 t{};
        tweak_cipher_->Encrypt(lba_tweak, t);

        const std::size_t len = ciphertext.size();
        const std::size_t full_blocks = len / kBlockBytes;
        const std::size_t rem = len % kBlockBytes;
        const std::size_t lim = (rem == 0) ? full_blocks : (full_blocks - 1);

        Block128 cc{}, pp{};

        for (std::size_t i = 0; i < lim; ++i) {
            const auto offset = i * kBlockBytes;
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                cc[k] = ciphertext[offset + k] ^ t[k];
            }
            data_cipher_->Decrypt(cc, pp);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                plaintext[offset + k] = pp[k] ^ t[k];
            }
            GaloisMultiplyAlpha(t);
        }

        if (rem > 0) {
            const std::size_t m = full_blocks;
            const auto c_m_minus_1_idx = (m - 1) * kBlockBytes;
            const auto c_m_idx = m * kBlockBytes;

            Block128 t_m_minus_1 = t;
            GaloisMultiplyAlpha(t);

            Block128 p_prime{};
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                cc[k] = ciphertext[c_m_minus_1_idx + k] ^ t[k];
            }
            data_cipher_->Decrypt(cc, pp);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                p_prime[k] = pp[k] ^ t[k];
            }

            std::memcpy(&plaintext[c_m_idx], p_prime.data(), rem);

            Block128 c_prime{};
            std::memcpy(c_prime.data(), &ciphertext[c_m_idx], rem);
            std::memcpy(c_prime.data() + rem, p_prime.data() + rem, kBlockBytes - rem);

            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                cc[k] = c_prime[k] ^ t_m_minus_1[k];
            }
            data_cipher_->Decrypt(cc, pp);
            for (std::size_t k = 0; k < kBlockBytes; ++k) {
                plaintext[c_m_minus_1_idx + k] = pp[k] ^ t_m_minus_1[k];
            }
        }

        return {};
    }

private:
    std::unique_ptr<BlockCipher> data_cipher_;
    std::unique_ptr<BlockCipher> tweak_cipher_;
};

} // namespace security
```

### Термінологічний покажчик

* **XTS-AES** (англ. *XEX Tweakable Block Cipher with Ciphertext Stealing*) — режим блокового шифрування з маскуванням адреси та викраденням шифротексту для накопичувачів прямого доступу.
* **Твік** (англ. *tweak* — налаштовувати, підкручувати) — відкритий допоміжний параметр блокового шифру, що створює незалежну перестановку блоків для кожного окремого сектора.
* **Відбілювання** (англ. *whitening* — робити білим / знеособлювати) — криптографічна техніка накладання маски операцією `XOR` на вхідні та вихідні блоки шифру для захисту від атак на внутрішні раунди.
* **Викрадення шифротексту** (англ. *ciphertext stealing*, від давньоангл. *stelan* — брати непомітно) — метод збереження вихідного розміру неповного блоку даних шляхом запозичення бітів із шифротексту сусіднього блоку.
* **Поле Галуа** `GF(2¹²⁸)` (на честь фр. математика *Évariste Galois*) — скінченне алгебраїчне поле з `2¹²⁸` елементами, у якому додавання відповідає `XOR`, а множення — операціям над поліномами за модулем незвідного многочлена.
* **Неподатливість** (англ. *non-malleability*, від лат. *malleus* — молот, піддатливість куванню) — криптографічна властивість, що унеможливлює модифікацію шифротексту так, щоб розшифрований текст мав передбачувану зміну.
