# 📜 Як народився OAuth: від парольного хаосу до стандарту вебу

На початку 2000-х років веб стрімко змінювався: статичні сайти поступилися місцем сервісам, де користувачі зберігали персональні дані. Люди завантажували фотографії на Flickr, вели розклади в Google Calendar, тримали контакти в Yahoo! та публікували короткі нотатки у Twitter. Майже одразу з'явилася потреба зв'язати ці сервіси між собою. Користувач хотів замовити друк своїх знімків у сервісі фотокниг, синхронізувати адресну книгу з поштовою скринькою або транслювати повідомлення з блогу в соціальну мережу.

Проте інженерного протоколу для такої взаємодії не існувало. Застосунки обирали найпростіший і водночас найнебезпечніший шлях: вони просто просили користувача ввести його логін і пароль від стороннього сайту.

```
+───────────────────────────────────────────────────────────────+
|               Вхід у сервіс друку PrintMyPhotos               |
|                                                               |
| Щоб надрукувати ваші фотографії, введіть облікові дані Flickr:|
| Логін:   [ user@example.com                                 ] |
| Пароль:  [ ****************                                 ] |
|                                                               |
|        [ Дозволити сервісу зберегти пароль і ввійти ]         |
+───────────────────────────────────────────────────────────────+
```

Ця практика отримала назву **антипатерн спільного пароля** (англ. *password anti-pattern*). Щоб надрукувати альбом, людина була змушена віддавати майстер-пароль сторонньому стартапу. Сервіс друку зберігав цей пароль у своїй базі у відкритому чи оборотно зашифрованому вигляді й заходив на Flickr так, ніби це сам користувач. 

Така схема несла в собі чотири непереборні вади:
1. **Надмірний доступ:** сервіс друку отримував повний контроль над усім акаунтом — міг читати особисті листи, змінювати платіжні реквізити чи видаляти чужі альбоми.
2. **Неможливість точкового відкликання:** єдиний спосіб заборонити доступ підозрілому сервісу полягав у зміні головного пароля, що ламало налаштування на всіх інших пристроях і програмах.
3. **Загроза витоку:** злам бази даних невеликого стороннього сайту миттєво розкривав паролі користувачів до великих поштових і фотосервісів.
4. **Легітимізація фішингу:** користувачів привчали вводити свої головні паролі у будь-які форми на чужих доменах.

### Ера пропрієтарних протоколів (2004–2006)

Великі технологічні компанії усвідомили небезпеку й почали створювати власні закриті механізми делегування доступу. 

У 2004 році Flickr представив власну систему аутентифікації Flickr API Auth. Користувач перенаправлявся на сторінку Flickr, підтверджував надання доступу, після чого застосунок отримував спеціальний шістнадцятковий рядок — «frob», який потім обмінював на постійний токен авторизації. 

Слідом за Flickr власні протоколи запустили інші гіганти:
* **Google** розробив систему **AuthSub** (а пізніше **ClientLogin**), яка дозволяла веб-сайтам отримувати обмежені токени для роботи з Google Calendar чи Picasa.
* **Yahoo!** впровадив систему **BBAuth** (Browser-Based Authentication).
* **AOL** представив **OpenAuth**.
* **Amazon** побудував власну схему авторизації запитів на основі підписів HMAC.

Хоча всі ці рішення базувалися на спільній ідеї — не показувати пароль сторонній програмі, а видавати їй обмежений токен, — вони були абсолютно несумісними між собою. Розробник, який створював настільний клієнт або веб-агрегатор, мав писати й підтримувати п'ять різних бібліотек авторизації з різними форматами запитів, підписів і схем оновлення ключів.

### Об'єднання зусиль і народження OAuth 1.0 (2007)

Переломний момент настав у квітні 2007 року. Блейн Кук (англ. *Blaine Cook*), головний архітектор молодого сервісу мікроблогів Twitter, працював над впровадженням протоколу [OpenID](topic:sf-security/openid-connect) для входу користувачів. Водночас Twitter потребував API, через який сторонні мобільні та настільні клієнти (наприклад, популярний тоді Tweetie) могли б публікувати твіти від імені користувачів, не знаючи їхніх паролів.

OpenID чудово розв'язував завдання ідентифікації («хто ти такий»), але взагалі не передбачав делегування повноважень до API («які дії програма може виконувати від твого імені»).

Кук зв'язався з Крісом Мессіною (англ. *Chris Messina*), відомим євангелістом відкритих веб-стандартів, та Ларрі Гелффом (англ. *Larry Halff*), творцем сервісу закладок Ma.gnolia, який у той самий час намагався створити аналогічний механізм авторизації для свого сайту. Вони дійшли висновку: замість винаходу чергового локального протоколу для Twitter необхідно створити єдиний відкритий стандарт для всього інтернету.

У квітні 2007 року було створено робочу групу з розробки відкритого протоколу делегування. Проект отримав назву **OAuth** (скорочення від *Open Authorization*). До обговорення швидко долучилися інженери з Google (Еран Гаммер-Лахав), Yahoo!, AOL та незалежні криптографи.

У грудні 2007 року було опубліковано чорновий проект специфікації OAuth Core 1.0. У квітні 2010 року Інженерна рада інтернету (IETF) стандартизувала його як **RFC 5849: The OAuth 1.0 Protocol**.

### Архітектура OAuth 1.0 і «танець на трьох ногах»

Протокол OAuth 1.0 базувався на витонченій, але складній моделі криптографічного захисту кожного HTTP-запиту. Вона отримала назву «триногий танець» (англ. *three-legged dance*), оскільки в процесі брали участь три сторони: користувач, клієнтський застосунок і сервер.

Потік складався з трьох обов'язкових кроків:
1. Клієнт звертався до сервера й отримував тимчасовий неавторизований токен запиту (англ. *Request Token*).
2. Клієнт перенаправляв браузер користувача на сервер, де користувач уводив логін/пароль і давав дозвіл. Сервер відзначав цей Request Token як авторизований і повертав користувача назад клієнту з кодом верифікації.
3. Клієнт знову звертався до сервера напряму, передаючи підтверджений Request Token і верифікатор, та обмінював їх на довготривалий токен доступу (англ. *Access Token*) і парний секрет токена (англ. *Token Secret*).

```
Клієнт                          Сервер авторизації               Користувач
  │                                     │                             │
  │ 1. Отримати Request Token           │                             │
  ├────────────────────────────────────►│                             │
  │◄────────────────────────────────────┤                             │
  │                                     │                             │
  │ 2. Перенаправити на авторизацію     │                             │
  ├──────────────────────────────────────────────────────────────────►│
  │                                     │ 3. Вхід і підтвердження     │
  │                                     │◄────────────────────────────┤
  │ 4. Редирект з verifier              │                             │
  │◄──────────────────────────────────────────────────────────────────┤
  │                                     │                             │
  │ 5. Обмін на Access Token            │                             │
  ├────────────────────────────────────►│                             │
  │◄────────────────────────────────────┤                             │
```

Головною особливістю OAuth 1.0 було те, що **протокол не покладався на HTTPS**. У 2007 році повсюдне шифрування веб-трафіку (TLS) було рідкістю: сертифікати коштували дорого, а навантаження на процесори серверів вважалося зависоким. 

Тому автори OAuth 1.0 заклали математичний захист на рівні додатків: кожен запит до API мав містити підпис **HMAC-SHA1** або **RSA-SHA1**. Щоб підписати запит, клієнт мав зібрати у суворо визначеному порядку «базовий рядок підпису» (англ. *Signature Base String*), куди входили HTTP-метод, нормалізований URL, відсортовані за алфавітом параметри запиту, мітка точного часу (англ. *timestamp*) та випадковий рядок для захисту від повторів (англ. *nonce*).

### Криза підписів і виклики мобільної революції

Невдовзі після стандартизації OAuth 1.0 індустрія зіткнулася з низкою проблем, які робили протокол нестерпним для розробників:

1. **Крихкість генерації базового рядка:** Найменша розбіжність у сортуванні URL-параметрів, кодуванні символів пробілу (`%20` чи `+`), роботі проксі-серверів чи балансувальників навантаження спотворювала базовий рядок. Підпис не збігався, сервер повертав помилку `401 Unauthorized`, а зрозуміти причину збою було надзвичайно складно. Розробники витрачали дні на налаштування одного виклику.
2. **Мобільний вибух:** Почалася ера смартфонів (iOS та Android). Обчислення складних криптографічних підписів для кожного фонового запиту мобільного додатку виснажувало батарею та уповільнювало інтерфейс.
3. **Монолітність сервера:** В OAuth 1.0 сервер, що видавав токени, і API-сервер, що обслуговував дані, мусили мати доступ до спільних секретів клієнта для перевірки HMAC-підписів. Це заважало будувати розподілені мікросервісні архітектури.
4. **Незручність для браузерних додатків:** Поява Single Page Applications (SPA) на JavaScript означала, що секрет клієнта взагалі не можна було зберегти в браузері: будь-який відвідувач міг відкрити код сторінки й викрасти його.

### Народження OAuth 2.0 та розкол (2010–2012)

У 2010 году IETF сформувала робочу групу для створення нової версії стандарту — **OAuth 2.0**. Головним редактором специфікації став Еран Гаммер-Лахав (англ. *Eran Hammer-Lahav*).

Учасники робочої групи ухвалили фундаментальне рішення: **відмовитися від підписування кожного запиту та повністю делегувати безпеку транспорту протоколу TLS (HTTPS)**. До 2010 року апаратне прискорення та поява доступних сертифікатів зробили HTTPS новим стандартом вебу.

Перехід на TLS дав змогу перейти до моделі **токена на пред'явника** (англ. *Bearer Token*). Замість складного підрахунку підписів клієнту стало достатньо додати заголовок:

```http
Authorization: Bearer s3cr3t-t0k3n-str1ng
```

Крім того, новий протокол розділив ролі клієнтів (конфіденційні для бекендів і публічні для мобільних додатків і SPA) та ввів різні **потоки авторизації** (англ. *Grant Types*):
* `authorization_code` — для класичних веб-сайтів із захищеним бекендом.
* `implicit` — оптимізований скорочений потік для JavaScript у браузері.
* `password` (Resource Owner Password Credentials) — перехідний потік для міграції застарілих систем.
* `client_credentials` — для взаємодії між серверами без участі людини.

Проте розробка стандарту перетворилася на запеклу війну компромісів між гігантами індустрії. Компанії Google, Facebook, Microsoft, Yahoo! та численні enterprise-вендори мали різні бізнес-інтереси й тягнули специфікацію у власні боки. Щоб задовольнити всіх, робоча група почала прибирати зі стандарту конкретні технічні вимоги, замінюючи їх необов'язковими рекомендаціями та залишаючи забагато деталей «на розсуд реалізації».

Це призвело до гучного конфлікту. У липні 2012 року, коли робота над документом добігала кінця, Еран Гаммер подав у відставку з посади головного редактора й відкликав своє ім'я зі списку авторів. Він опублікував резонансне есе під назвою *«OAuth 2.0 and the Road to Hell»*, у якому жорстко розкритикував результат:

> *«OAuth 2.0 за своєю суттю — це не протокол. Це рамкова основа (framework), яка настільки переповнена варіантами та розмитими місцями, що несумісність між реалізаціями гарантована. Ми витратили три роки, щоб перетворити просту й безпечну річ на складне полотно компромісів для гігантських корпорацій».*

Попри критику Гаммера, у жовтні 2012 року стандарт було офіційно затверджено у вигляді двох ключових документів:
* **RFC 6749:** *The OAuth 2.0 Authorization Framework*
* **RFC 6750:** *The OAuth 2.0 Authorization Framework: Bearer Token Usage*

### Тріумф і подальша еволюція до OAuth 2.1

Попри всі архітектурні суперечки, простота інтеграції через `Bearer`-токени та гнучкість потоків призвели до тріумфу OAuth 2.0. Він став негласним фундаментом для всього сучасного вебу, мобільних додатків та хмарних екосистем.

У подальші роки спільнота закрила прогалини базової специфікації серією важливих доповнень:
* **2013 (серпень):** **RFC 7009** стандартизував ендпоінт відкликання токенів (`/revoke`).
* **2014:** Поверх OAuth 2.0 створено [OpenID Connect (OIDC)](topic:sf-security/openid-connect), який стандартизував шар ідентифікації через підписані токени [JWT](topic:sf-web/jwt-tokens).
* **2015:** **RFC 7636 (PKCE)** розв'язав проблему перехоплення коду авторизації у мобільних і браузерних додатках, додавши динамічну криптографічну прив'язку без повернення до важких підписів OAuth 1.0.
* **2015:** **RFC 7662** стандартизував ендпоінт інтроспекції токенів (`/introspect`).
* **2019:** **RFC 8628 (Device Authorization Grant)** дав зручний потік для Smart TV, ігрових консолей та термінальних утиліт (CLI).
* **2020–2024:** Робоча група IETF розпочала підготовку **OAuth 2.1**. Ця нова редакція прибрала з історії застарілі й небезпечні компроміси 2012 року: повністю заборонила потоки `implicit` і `password`, зробила механізм `PKCE` обов'язковим для всіх клієнтів без винятку, посилила правила перевірки адрес перенаправлення та запропонувала захист від крадіжки токенів через механізм **DPoP (RFC 9449)**.

Історія OAuth демонструє еволюцію інженерної думки: від наївного введення паролів у чужі форми — через надскладну криптографію локальних підписів — до елегантної системи делегування повноважень, що тримає на собі безпеку мільярдів щоденних операцій у цифровому світі.
