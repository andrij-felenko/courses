# 📋 Інтерфейс та протокольні точки взаємодії OAuth 2.0

Протокол OAuth 2.0 (RFC 6749, RFC 6750, RFC 7636, RFC 7009, RFC 7662, RFC 7591, RFC 8414, RFC 8628, RFC 9449) визначає стандартизований набір HTTP-точок взаємодії (англ. *endpoints*) між клієнтом, сервером авторизації та сервером ресурсів. 

Цей довідник містить вичерпну специфікацію протокольних контрактів, параметрів запитів, схем відповідей, механізмів автентифікації клієнтів, метаданих автоконфігурації, інваріантів життєвого циклу токенів, правил обробки часових похибок та стандартних кодів помилок.

```
+─────────────────────────────────────────────────────────────────────────────+
|                    ТОПОЛОГІЯ ЕНДПОІНТІВ OAUTH 2.0                           |
|                                                                             |
|  [ Сервер авторизації (Authorization Server) ]                              |
|   ├── /.well-known/oauth-authorization-server — автоконфігурація (RFC 8414) |
|   ├── /register     — динамічна реєстрація клієнтів (RFC 7591)              |
|   ├── /authorize    — фронт-канал: взаємодія з власником ресурсу            |
|   ├── /token        — бек-канал: обмін кодів, облікових даних і оновлення   |
|   ├── /revoke       — бек-канал: примусове відкликання токенів (RFC 7009)   |
|   ├── /introspect   — бек-канал: інтроспекція opaque-токенів (RFC 7662)     |
|   └── /device/code  — бек-канал: ініціалізація Device Flow (RFC 8628)       |
|                                                                             |
|  [ Сервер ресурсів (Resource Server) ]                                      |
|   └── /api/*        — захищені бізнес-ендпоінти з Bearer/DPoP токенами      |
+─────────────────────────────────────────────────────────────────────────────+
```

## 1. Метадані сервера авторизації (`/.well-known/oauth-authorization-server`)

Стандарт RFC 8414 визначає протокол автоматичного виявлення конфігурації сервера авторизації (англ. *Authorization Server Metadata*). Клієнти використовують цей документ для динамічного налаштування URL-адрес ендпоінтів, підтримуваних криптографічних алгоритмів, способів автентифікації та доступних областей видимості без необхідності ручного прописування адрес у конфігураційних файлах.

Документ конфігурації публікується за стандартизованою адресою з префіксом `/.well-known/oauth-authorization-server` або `/.well-known/openid-configuration` (для систем, сумісних із OpenID Connect). Сервер зобов'язаний віддавати цей документ із типом вмісту `application/json` та дозволяти міжсайтові запити (заголовок `Access-Control-Allow-Origin: *`), щоб браузерні застосунки могли зчитувати налаштування.

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/oauth/authorize",
  "token_endpoint": "https://auth.example.com/oauth/token",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "registration_endpoint": "https://auth.example.com/oauth/register",
  "scopes_supported": ["openid", "profile", "email", "photos.read", "photos.write"],
  "response_types_supported": ["code"],
  "response_modes_supported": ["query", "fragment"],
  "grant_types_supported": [
    "authorization_code",
    "refresh_token",
    "client_credentials",
    "urn:ietf:params:oauth:grant-type:device_code"
  ],
  "token_endpoint_auth_methods_supported": [
    "client_secret_basic",
    "client_secret_post",
    "private_key_jwt"
  ],
  "revocation_endpoint": "https://auth.example.com/oauth/revoke",
  "revocation_endpoint_auth_methods_supported": ["client_secret_basic", "private_key_jwt"],
  "introspection_endpoint": "https://auth.example.com/oauth/introspect",
  "introspection_endpoint_auth_methods_supported": ["client_secret_basic", "private_key_jwt"],
  "code_challenge_methods_supported": ["S256"],
  "dpop_signing_alg_values_supported": ["ES256", "RS256"]
}
```

Головні поля схеми метаданих:
* `issuer` — унікальний канонічний ідентифікатор сервера авторизації (URL без завершального слеша та рядка параметрів). Цей рядок обов'язково звіряється клієнтом під час перевірки твердження `iss` у підписаних токенах.
* `jwks_uri` — адреса набору відкритих ключів у форматі JSON Web Key Set (JWKS), за допомогою яких сервери ресурсів перевіряють цифрові підписи токенів доступу.
* `code_challenge_methods_supported` — перелік підтримуваних методів трансформації PKCE; сучасні захищені сервери вказують лише `S256`.

## 2. Динамічна реєстрація клієнтів (`/register`, RFC 7591)

Для застосунків, які розгортаються на пристроях користувачів або створюються динамічно, протокол визначає ендпоінт реєстрації клієнтів. Замість ручного створення застосунку в адміністративній панелі клієнт надсилає POST-запит із метаданими про себе.

```http
POST /oauth/register HTTP/1.1
Host: auth.example.com
Content-Type: application/json
Accept: application/json

{
  "client_name": "My Mobile Photo Sync",
  "redirect_uris": ["org.example.photosync:/oauth/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none",
  "application_type": "native"
}
```

У відповідь сервер авторизації створює запис у базі даних і повертає зареєстрований `client_id`, а для конфіденційних клієнтів — також `client_secret` і строк його дії (`client_secret_expires_at`).

## 3. Ендпоінт авторизації (`/authorize`)

Ендпоінт авторизації взаємодіє з користувачем через браузер (фронт-канал). Він служить для автентифікації користувача на стороні сервера авторизації та отримання його явної згоди (англ. *consent*) на надання доступу клієнту.

* **HTTP-метод:** `GET` (рекомендовано) або `POST` (для передачі довгих наборів параметрів через форму).
* **Формат запиту:** URL-параметри рядка запиту (англ. *query parameters*).
* **Тип клієнта:** Усі клієнти, що використовують потік Authorization Code.

### Параметри запиту до `/authorize`

| Параметр | Обов'язковість | Специфікація та правила валідації |
| :--- | :--- | :--- |
| `response_type` | **Обов'язковий** | Тип відповіді, яку очікує клієнт. Для сучасного потоку Authorization Code значення строго фіксоване: `code`. Будь-які запити зі значенням `token` (застарілий Implicit flow) сучасний сервер зобов'язаний відхиляти. |
| `client_id` | **Обов'язковий** | Публічний унікальний ідентифікатор клієнта, виданий сервером авторизації під час реєстрації застосунку. |
| `redirect_uri` | Умовно обов'язковий | URL-адреса зворотного виклику, на яку браузер користувача повернеться після завершення авторизації. Якщо клієнт зареєстрував більше ніж одну адресу, цей параметр стає строго обов'язковим. Сервер застосовує суворе посимвольне порівняння без шаблонів. |
| `scope` | Опціональний | Список областей видимості (прав доступу), розділених пробілами (наприклад: `photos.read contacts.write`). Якщо не вказано, сервер застосовує стандартний набір за замовчуванням або повертає помилку `invalid_scope`. |
| `state` | **Критично обов'язковий** | Непрозорий криптографічно випадковий рядок високої ентропії (не менше 128 біт випадковості), що генерується клієнтом і зберігається в сесії користувача в браузері. Захищає від атак міжсайтової підробки запиту (CSRF). Сервер зобов'язаний повернути цей рядок клієнту у відповіді без жодних модифікацій. |
| `code_challenge` | **Обов'язковий (PKCE)** | Захешований рядок верифікатора коду для механізму PKCE (RFC 7636). Обчислюється як `BASE64URL(SHA256(code_verifier))`. |
| `code_challenge_method` | Опціональний (PKCE) | Метод перетворення верифікатора коду. Дозволені значення: `S256` (обов'язковий сучасний стандарт) або застарілий `plain` (відкритий текст без хешування, заборонений в OAuth 2.1). Клієнт зобов'язаний явно вказувати `S256`. |
| `prompt` | Опціональний | Керує відображенням користувацького інтерфейсу: `none` (тиха перевірка без показу UI; якщо потрібна дія — повертає помилку), `login` (примусова повторна автентифікація), `consent` (примусовий показ форми надання прав), `select_account` (вибір облікового запису). |
| `max_age` | Опціональний | Максимально допустимий час у секундах з моменту останньої активної автентифікації користувача. Якщо минуло більше часу, сервер вимагає повторного введення облікових даних. |

### Приклад запиту перенаправлення

```http
GET /oauth/authorize?response_type=code
    &client_id=analytics-dashboard-123
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Foauth%2Fcallback
    &scope=reports.read%20metrics.export
    &state=c29tZS1yYW5kb20tc3RhdGUtdmFsdWU
    &code_challenge=E9Melhoa2OwvFrGMTJguCH5rtx64fZqiJ405nmIjY0s
    &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com
```

### Успішна відповідь ендпоінта авторизації

Сервер авторизації не повертає тіло HTTP. Він надсилає заголовок перенаправлення `302 Found` або `303 See Other` на вказаний `redirect_uri` з параметрами в частині запиту:

```http
HTTP/1.1 302 Found
Location: https://app.example.com/oauth/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=c29tZS1yYW5kb20tc3RhdGUtdmFsdWU
```

Параметри відповіді:
* `code` — короткоживучий (строк дії 30–60 секунд), одноразовий код авторизації.
* `state` — точна копія значення `state`, отриманого у вхідному запиті. Клієнт зобов'язаний перевірити його збіг зі збереженим значенням у сесії користувача перед обробкою коду.

### Відповідь із помилкою через перенаправлення

Якщо користувач відхилив запит або передано невалідні параметри (за умови, що `redirect_uri` валідний і попередньо перевірений сервером):

```http
HTTP/1.1 302 Found
Location: https://app.example.com/oauth/callback?error=access_denied&error_description=User%20declined%20the%20request&state=c29tZS1yYW5kb20tc3RhdGUtdmFsdWU
```

Якщо ж сам `redirect_uri` є невалідним, не збігається з білим списком або відсутній, сервер **не має права виконувати редирект** (щоб не стати інструментом атаки Open Redirector). У такому разі сервер повертає пряму HTTP-відповідь із кодом `400 Bad Request` на власній сторінці помилки.

## 4. Ендпоінт видачі токенів (`/token`)

Ендпоінт токенів використовується клієнтом для прямого обміну коду авторизації або облікових даних на токени доступу та токени оновлення. Спілкування відбувається виключно через прямий захищений TLS-канал між бекендом клієнта та сервером авторизації (бек-канал).

* **HTTP-метод:** Строго `POST`.
* **Заголовок `Content-Type`:** Строго `application/x-www-form-urlencoded`.
* **Заголовок `Accept`:** `application/json`.
* **Кешування:** Відповіді містять обов'язкові заголовки `Cache-Control: no-store` та `Pragma: no-cache`.

### Способи автентифікації клієнта на ендпоінті `/token`

1. **`client_secret_basic` (HTTP Basic Auth, RFC 6749):**
   Клієнт передає заголовок `Authorization: Basic <credentials>`, де `<credentials>` — це кодований у Base64 рядок `client_id:client_secret`.
2. **`client_secret_post`:**
   Параметри `client_id` та `client_secret` передаються прямо у формі `application/x-www-form-urlencoded` у тілі POST-запиту.
3. **`private_key_jwt` (RFC 7523):**
   Клієнт підписує власним асиметричним приватним ключем одноразовий токен JWT із твердженнями `iss=client_id`, `sub=client_id`, `aud=token_endpoint`, `exp`, `jti` та надсилає його в параметрі `client_assertion` із типом `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`. Це найнадійніший спосіб для бекендів, оскільки секрет ніколи не передається мережею.
4. **Публічні клієнти (без секрету):**
   Мобільні та браузерні додатки не мають секрету й передають лише `client_id` разом із параметром PKCE `code_verifier`.

---

### Варіант А: Обмін коду авторизації (`grant_type=authorization_code`)

| Параметр тіла | Обов'язковість | Опис і вимоги |
| :--- | :--- | :--- |
| `grant_type` | **Обов'язковий** | Значення строго: `authorization_code`. |
| `code` | **Обов'язковий** | Код авторизації, отриманий з ендпоінта `/authorize`. |
| `redirect_uri` | **Обов'язковий** | Той самий `redirect_uri`, що використовувався в початковому запиті до `/authorize`. Сервер вимагає точного посимвольного збігу. |
| `client_id` | Умовно обов'язковий | Ідентифікатор клієнта (обов'язковий для публічних клієнтів або якщо автентифікація передається в тілі). |
| `code_verifier` | **Обов'язковий (PKCE)** | Початковий випадковий рядок високої ентропії (довжиною від 43 до 128 символів із набору `[A-Z, a-z, 0-9, "-", ".", "_", "~"]`), від якого раніше обчислювався `code_challenge`. |

#### Приклад запиту обміну коду:

```http
POST /oauth/token HTTP/1.1
Host: auth.example.com
Authorization: Basic YW5hbHl0aWNzLWRhc2hib2FyZC0xMjM6c3VwZXItc2VjcmV0LWtleQ==
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fapp.example.com%2Foauth%2Fcallback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

### Варіант Б: Оновлення токена доступу (`grant_type=refresh_token`)

| Параметр тіла | Обов'язковість | Опис і вимоги |
| :--- | :--- | :--- |
| `grant_type` | **Обов'язковий** | Значення строго: `refresh_token`. |
| `refresh_token` | **Обов'язковий** | Довготривалий токен оновлення, отриманий під час попередньої авторизації. |
| `scope` | Опціональний | Новий набір прав. Може бути лише **підмножиною** початково наданих прав (звуження прав). Запит на розширення прав заборонено. |

#### Приклад запиту оновлення токена:

```http
POST /oauth/token HTTP/1.1
Host: auth.example.com
Authorization: Basic YW5hbHl0aWNzLWRhc2hib2FyZC0xMjM6c3VwZXItc2VjcmV0LWtleQ==
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=kZ8yQ2vM5xT9jP7w
&scope=reports.read
```

### Варіант В: Облікові дані клієнта (`grant_type=client_credentials`)

Використовується для взаємодії сервіс-сервіс (Machine-to-Machine, M2M) без участі користувача.

| Параметр тіла | Обов'язковість | Опис і вимоги |
| :--- | :--- | :--- |
| `grant_type` | **Обов'язковий** | Значення строго: `client_credentials`. |
| `scope` | Опціональний | Бажаний рівень доступу сервісу до ресурсів. |

#### Приклад запиту Client Credentials:

```http
POST /oauth/token HTTP/1.1
Host: auth.example.com
Authorization: Basic c2VydmljZS13b3JrZXItY2xpZW50OnNlY3JldC1hcGkta2V5LTQ1Ng==
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=system.metrics%20system.logs
```

### Успішна відповідь ендпоінта `/token`

Сервер авторизації повертає HTTP-статус `200 OK` та тіло формату `application/json`.

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "rF83mN9xQ2pZ7vL5",
  "scope": "reports.read metrics.export"
}
```

#### Поля схеми відповіді `/token`:

* `access_token` *(рядок, обов'язковий)* — токен доступу (opaque-рядок або JWT), який пред'являється серверу ресурсів.
* `token_type` *(рядок, обов'язковий)* — тип токена. Зазвичай строго `"Bearer"` (без урахування регістру) або `"DPoP"` у разі використання криптографічної прив'язки.
* `expires_in` *(ціле число, рекомендований)* — час життя токена доступу в секундах від моменту видачі (наприклад, `3600` = 1 година).
* `refresh_token` *(рядок, опціональний)* — новий токен оновлення. При використанні ротації токенів старий `refresh_token` анулюється, а замість нього клієнт зобов'язаний зберегти цей новий.
* `scope` *(рядок, умовно обов'язковий)* — фактично наданий перелік прав, якщо він відрізняється від запитаного клієнтом.

---

### Відповідь із помилкою ендпоінта `/token`

У разі невдалої перевірки параметрів сервер авторизації повертає HTTP-статус `400 Bad Request` (або `401 Unauthorized`, якщо не вдалася автентифікація клієнта):

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "error": "invalid_grant",
  "error_description": "Authorization code has expired or was already redeemed",
  "error_uri": "https://auth.example.com/docs/errors#invalid_grant"
}
```

## 5. Інваріанти життєвого циклу коду та токенів

Специфікація OAuth 2.0 встановлює строгі правила обробки стану авторизаційних сутностей, які гарантують стійкість до атак перехоплення та підміни:

1. **Одноразовість коду авторизації (`Authorization Code Single-Use`):**
   Код авторизації може бути використаний на ендпоінті `/token` рівно один раз. Щойно код пред'явлено, сервер негайно позначає його як погашений. Якщо сервер авторизації фіксує повторну спробу обміну того самого коду (наприклад, коли зловмисник спробував використати перехоплений код або клієнт помилково надіслав дублікат), сервер **зобов'язаний негайно відкликати всі токени доступу та оновлення, видані за першим запитом із цим кодом**. Це локалізує атаку та сповіщає систему про компрометацію.
2. **Строк дії коду авторизації:**
   Код авторизації створюється з надзвичайно коротким строком придатності — не більше 10 хвилин за стандартом, а на практиці рекомендовано від 30 до 60 секунд. Це звужує часове вікно для будь-якого потенційного перехоплення.
3. **Ротація Refresh Token (Refresh Token Rotation):**
   При кожному зверненні до ендпоінта `/token` із параметром `grant_type=refresh_token` сервер авторизації інвалідує використаний `refresh_token` і повертає новий у парі зі свіжим `access_token`. Усі токени оновлення групуються в логічну «сім'ю» (англ. *token family*). Якщо до сервера надходить запит із уже погашеним старим токеном оновлення, це однозначний маркер того, що токен було вкрадено (зловмисник або легітимний клієнт скористався застарілою копією). У відповідь сервер негайно анулює всю сім'ю токенів цієї сесії, змушуючи користувача пройти повну повторну автентифікацію.

## 6. Ендпоінт відкликання токенів (`/revoke`, RFC 7009)

Дозволяє клієнту явно відкликати раніше виданий токен доступу або токен оновлення (наприклад, під час виходу користувача із системи — *Logout* або видалення підключеної інтеграції).

* **HTTP-метод:** Строго `POST`.
* **Заголовок `Content-Type`:** `application/x-www-form-urlencoded`.
* **Автентифікація:** Клієнт автентифікується тими самими методами, що й на ендпоінті `/token`.

### Параметри запиту до `/revoke`

| Параметр | Обов'язковість | Опис і вимоги |
| :--- | :--- | :--- |
| `token` | **Обов'язковий** | Рядок токена, який необхідно відкликати. |
| `token_type_hint` | Опціональний | Підказка типу токена: `access_token` або `refresh_token`. Допомагає серверу оптимізувати пошук токена у сховищі даних. Якщо тип указано невірно, сервер все одно зобов'язаний перевірити інші типи токенів. |

#### Приклад запиту відкликання:

```http
POST /oauth/revoke HTTP/1.1
Host: auth.example.com
Authorization: Basic YW5hbHl0aWNzLWRhc2hib2FyZC0xMjM6c3VwZXItc2VjcmV0LWtleQ==
Content-Type: application/x-www-form-urlencoded

token=rF83mN9xQ2pZ7vL5
&token_type_hint=refresh_token
```

### Відповідь ендпоінта `/revoke`

* **HTTP `200 OK`:** Токен успішно відкликано. 
* **Критичне правило безпеки:** Сервер **зобов'язаний повернути статус `200 OK` навіть тоді, коли переданий токен не існує, є недійсним чи вже був відкликаний раніше**. Це запобігає атакам зондування (англ. *token scanning oracle*), коли зловмисник перебирає рядки для з'ясування валідності чужих токенів.

Якщо відкликається `refresh_token`, сервер авторизації також зобов'язаний автоматично відкликати всі пов'язані з ним активні `access_token`. Якщо ж відкликається окремий `access_token`, пов'язаний `refresh_token` може залишатися активним (залежно від політики безпеки сервера).

## 7. Ендпоінт інтроспекції токенів (`/introspect`, RFC 7662)

Використовується сервером ресурсів для динамічної перевірки валідності непрозорих (англ. *opaque*) токенів доступу та отримання пов'язаних із ними метаданих безпосередньо від сервера авторизації.

* **HTTP-метод:** Строго `POST`.
* **Заголовок `Content-Type`:** `application/x-www-form-urlencoded`.
* **Автентифікація:** Сервер ресурсів автентифікується як довірений клієнт (наприклад, через Basic Auth або за допомогою `private_key_jwt`).

### Параметри запиту до `/introspect`

| Параметр | Обов'язковість | Опис |
| :--- | :--- | :--- |
| `token` | **Обов'язковий** | Рядок токена, стан якого перевіряється. |
| `token_type_hint` | Опціональний | `access_token` або `refresh_token`. |

#### Приклад запиту інтроспекції:

```http
POST /oauth/introspect HTTP/1.1
Host: auth.example.com
Authorization: Basic cmVzb3VyY2Utc2VydmVyLTE6c2hhcmVkLXNlY3JldC1wYXNz
Content-Type: application/x-www-form-urlencoded

token=2YotnFZFEjr1zCsicMWpAA
&token_type_hint=access_token
```

### Відповідь ендпоінта `/introspect`

#### Успішна активна відповідь (`active: true`):

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8

{
  "active": true,
  "scope": "reports.read metrics.export",
  "client_id": "analytics-dashboard-123",
  "username": "alice@example.com",
  "token_type": "Bearer",
  "exp": 1735736400,
  "iat": 1735732800,
  "nbf": 1735732800,
  "sub": "usr-98741",
  "aud": "https://api.example.com/reports",
  "iss": "https://auth.example.com"
}
```

Поля відповіді інтроспекції:
* `active` *(булеве, обов'язкове)* — показує, чи токен на цей момент є дійсним, не протермінованим і не відкликаним.
* `scope` — список прав, закодованих у токені.
* `sub` *(Subject)* — унікальний ідентифікатор користувача або сутності, яка надала дозвіл.
* `aud` *(Audience)* — цільова аудиторія токена (URL або ідентифікатор сервера ресурсів). Сервер ресурсів зобов'язаний перевірити, що його власний ідентифікатор присутній у списку `aud`.
* `exp` *(Expiration Time)* — час закінчення дії токена у форматі Unix Timestamp.

#### Відповідь для неактивного або недійсного токена (`active: false`):

Якщо токен недійсний, відкликаний або протермінований, сервер повертає `200 OK` з єдиним обов'язковим полем:

```json
{
  "active": false
}
```

Сервер ресурсів зазвичай кешує результат інтроспекції на невеликий проміжок часу (наприклад, 10–30 секунд), щоб уникнути надлишкового навантаження на сервер авторизації при високому потоці запитів.

## 8. Ендпоінт авторизації пристроїв (`/device/code`, RFC 8628)

Використовується для пристроїв із відсутнім браузером або обмеженим введенням тексту (Smart TV, IoT, консольні CLI-термінали).

* **HTTP-метод:** Строго `POST`.
* **Заголовок `Content-Type`:** `application/x-www-form-urlencoded`.

### Параметри запиту до `/device/code`

| Параметр | Обов'язковість | Опис |
| :--- | :--- | :--- |
| `client_id` | **Обов'язковий** | Публічний ідентифікатор пристрою/клієнта. |
| `scope` | Опціональний | Бажані області видимості. |

#### Приклад відповіді ендпоінта авторизації пристроїв:

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8

{
  "device_code": "GmRhmhcOxhqb1xNs-GmRhmhcOxhqb1xNs",
  "user_code": "WDJB-MJHT",
  "verification_uri": "https://auth.example.com/activate",
  "verification_uri_complete": "https://auth.example.com/activate?user_code=WDJB-MJHT",
  "expires_in": 900,
  "interval": 5
}
```

Пристрій виводить на екран `user_code` і `verification_uri` (часто у вигляді QR-коду) та починає періодично опитувати (англ. *polling*) ендпоінт `/token` із параметром `grant_type=urn:ietf:params:oauth:grant-type:device_code` з інтервалом не менше ніж `interval` секунд.

Якщо користувач ще не ввів код, ендпоінт `/token` повертає помилку `authorization_pending`. Якщо пристрій опитує сервер частіше ніж `interval`, сервер повертає `slow_down`, змушуючи клієнта збільшити інтервал на 5 секунд.

## 9. Обробка часових похибок (Clock Skew) та валідація строків дії

У розподілених системах годинники різних серверів ніколи не бувають синхронізовані абсолютно точно. Різниця в 1–3 секунди між сервером авторизації та сервером ресурсів є звичайною ситуацією навіть за умови використання протоколу NTP.

Якщо сервер ресурсів виконує сувору перевірку часових тверджень без урахування похибки, щойно випущений токен може бути помилково відхилений із вердиктом «токен ще не набув чинності» (якщо годинник сервера ресурсів відстає від `nbf`/`iat`), або відхилений передчасно на останніх секундах життя.

### Правила обробки похибки годинників

1. **Допуск похибки (Clock Skew Tolerance):**
   Сервер ресурсів та клієнт зобов'язані закладати допустимий буфер похибки під час перевірки часових полів (рекомендоване значення — **від 30 до 60 секунд**).
2. **Перевірка моменту початку дії (`nbf` та `iat`):**
   Токен визнається валідним за часом початку, якщо поточний час `current_time` задовольняє умову:
   ```
   current_time >= nbf - clock_skew
   ```
3. **Перевірка закінчення дії (`exp`):**
   Токен визнається не протермінованим, якщо поточний час задовольняє умову:
   ```
   current_time <= exp + clock_skew
   ```
4. **Випереджальне оновлення токенів клієнтом:**
   Клієнтські застосунки не чекають фізичного настання моменту `exp` для виклику ендпоінта `/token` із токеном оновлення. Клієнт ініціює оновлення за **60–120 секунд до закінчення строку дії** токена доступу. Це запобігає виникненню ситуацій, коли токен стає недійсним безпосередньо під час польоту HTTP-запиту мережею.

## 10. Порівняння архітектур токенів: Opaque проти JWT

При проєктуванні системи перед архітектором постає вибір внутрішньої структури токена доступу: непрозорий посилальний токен (англ. *by-reference / opaque*) чи самодостатній структурований токен (англ. *by-value / JWT*).

| Критерій порівняння | Opaque токен (за посиланням) | JWT токен (за значенням) |
| :--- | :--- | :--- |
| **Місце збереження стану** | Тільки в центральній базі сервера авторизації. | Усередині самого токена (підписаний JSON). |
| **Спосіб валідації API** | Запит до ендпоінта `/introspect` на кожен виклик API (або короткочасне кешування). | Локальна перевірка криптографічного підпису за допомогою відкритого ключа JWKS без звернення до мережі. |
| **Затримка (Latency) API** | Вища (додатковий мережевий запит до сервера авторизації). | Мінімальна (мікросекунди на перевірку підпису в пам'яті). |
| **Швидкість відкликання** | Миттєва: сервер авторизації видаляє запис із бази, і наступний запит інтроспекції повертає `active: false`. | Відкладена: токен залишається валідним до моменту настання `exp` (якщо не реалізовано чорні списки чи механізм Revocation List). |
| **Розмір заголовка HTTP** | Дуже малий (зазвичай 32–64 байти випадкових символів). | Значний (500–2000 байтів залежно від кількості тверджень і прав). |
| **Приватність даних** | Повна: клієнт і мережеві проксі не бачать жодних внутрішніх даних користувача. | Відкритість: вміст токена відкритий для читання будь-ким у форматі Base64url. |
| **Рекомендоване застосування** | Системи з високими вимогами до миттєвого відкликання та публічні клієнти. | Високонавантажені мікросервісні екосистеми з великою кількістю паралельних API-викликів. |

## 11. Зведена таблиця стандартних кодів помилок OAuth 2.0

| Код помилки (`error`) | HTTP статус | Де виникає | Причина збою та обов'язкові дії клієнта |
| :--- | :--- | :--- | :--- |
| `invalid_request` | `400 Bad Request` | `/authorize`, `/token` | Запит сформовано некоректно: відсутній обов'язковий параметр, передано дубльовані параметри, використано некоректний метод або заголовок `Content-Type`. Клієнт зобов'язаний виправити синтаксис запиту. |
| `invalid_client` | `401 Unauthorized` | `/token`, `/revoke`, `/introspect` | Автентифікація клієнта не вдалася: невірний `client_id`/`client_secret`, непідтримуваний спосіб передачі облікових даних або клієнт заблокований. |
| `invalid_grant` | `400 Bad Request` | `/token` | Наданий авторизаційний код або токен оновлення є недійсним, протермінованим, відкликаним або був створений для іншого `redirect_uri` чи `client_id`. Також виникає при незбігу PKCE `code_verifier`. Потрібен повний перезапуск потоку авторизації. |
| `unauthorized_client` | `400 Bad Request` | `/authorize`, `/token` | Клієнт зареєстрований, але не має прав використовувати цей конкретний `grant_type` або `response_type`. Необхідно налаштувати дозволи застосунку в кабінеті розробника. |
| `unsupported_grant_type` | `400 Bad Request` | `/token` | Сервер авторизації не підтримує значення параметра `grant_type`, надіслане клієнтом. |
| `invalid_scope` | `400 Bad Request` | `/authorize`, `/token` | Запитаний `scope` є синтаксично некоректним, перевищує дозволені ліміти клієнта або містить неіснуючі дозволи. |
| `access_denied` | `302 / 403` | `/authorize` | Користувач або адміністратор організації явно натиснув «Відхилити» на формі запиту прав. Клієнт повинен повідомити користувача про неможливість виконання дії без дозволу. |
| `unsupported_response_type` | `302 / 400` | `/authorize` | Сервер не підтримує запитаний `response_type` (наприклад, спроба використання `response_type=token` на захищеному сучасному сервері). |
| `server_error` | `500 Internal Error` | Усі ендпоінти | Непередбачений внутрішній збій на стороні сервера авторизації. Клієнт повинен повторити запит пізніше з використанням експоненційного відступу. |
| `temporarily_unavailable` | `503 Service Unavail` | Усі ендпоінти | Сервер тимчасово перевантажений або перебуває на технічному обслуговуванні. |
| `authorization_pending` | `400 Bad Request` | `/token` (Device Flow) | Користувач ще не ввів код на іншому пристрої. Клієнт продовжує фонове опитування із заданим інтервалом. |
| `slow_down` | `400 Bad Request` | `/token` (Device Flow) | Клієнт опитує сервер занадто часто. Пристрій зобов'язаний збільшити інтервал опитування на 5 секунд. |
| `expired_token` | `400 Bad Request` | `/token` (Device Flow) | Строк дії `device_code` вичерпано (зазвичай 15 хвилин). Користувач не завершив авторизацію вчасно. Необхідно згенерувати новий код. |

## 12. Захищений доступ до ресурсів (`Resource Access`)

Клієнт використовує отриманий `access_token` для викликів до захищеного API сервера ресурсів.

### Стандартний заголовок Bearer (RFC 6750)

За стандартом RFC 6750 токен на пред'явника передається в HTTP-заголовку `Authorization`:

```http
GET /api/v1/user/reports HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
```

Передача токенів у параметрах URL (`?access_token=...`) категорично заборонена в сучасних системах, оскільки токен неминуче осідає в логах веб-серверів, браузерній історії та заголовках `Referer`.

### Захищений заголовок DPoP (Demonstration of Proof-of-Possession, RFC 9449)

Для захисту від атак крадіжки та несанкціонованого повторного використання токенів використовується механізм DPoP: клієнт створює асиметричну ключову пару й додає підписаний приватним ключем короткоживучий JWT-доказ (англ. *DPoP proof*) до кожного HTTP-запиту:

```http
GET /api/v1/user/reports HTTP/1.1
Host: api.example.com
Authorization: DPoP eyJhbGciOiJSUzI1NiIs...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2Ii...
Accept: application/json
```

#### Структура DPoP Proof JWT:

```json
// Заголовок DPoP JWT:
{
  "typ": "dpop+jwt",
  "alg": "ES256",
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "f83OJ3D2xFmT4v_X4l... ",
    "y": "x_da7W45P128_6..."
  }
}

// Тіло DPoP JWT (твердження):
{
  "jti": "-BzA1TyTJIg",
  "htm": "GET",
  "htu": "https://api.example.com/api/v1/user/reports",
  "iat": 1735732800,
  "ath": "fUHyO2r2Z3DZ520SNSnU5ATHompVoDKFWvn95b4WJZQ"
}
```

* `htm` *(HTTP Method)* — метод поточного запиту (`GET`, `POST` тощо).
* `htu` *(HTTP URI)* — повний цільовий URL без рядка параметрів і фрагментів.
* `ath` *(Access Token Hash)* — хеш токена доступу: `BASE64URL(SHA256(access_token))`.
* `jti` — унікальний одноразовий ідентифікатор доказу для захисту від повторів (replay attacks).

Сервер ресурсів перевіряє криптографічний підпис DPoP-доказу за допомогою публічного ключа `jwk`, переконується, що `htm` і `htu` збігаються з фактичним викликом, і звіряє хеш `ath` із наданим токеном. Якщо зловмисник перехопить `access_token`, він не зможе виконати жодного запиту без приватного ключа клієнта.
