# 📋 Бінарні структури TPM 2.0 для атестації та виклики Credential Activation

Специфікація Trusted Computing Group (TCG) TPM 2.0 (зокрема частина 2 «Structures» та частина 3 «Commands») визначає суворий низькорівневий бінарний контракт для генерації атестаційних цитат та взаємного прив'язування криптографічних ключів. Усі структури даних передаються через шину мікроконтролера у двійковому форматі безпосереднього байтового кодування з порядком байтів від старшого до молодшого (Big-Endian) і використанням префіксів розміру `TPM2B_`.

Цей довідник містить детальний опис бінарного формату команди `TPM2_Quote`, внутрішньої структури сертифікаційного блоку `TPMS_ATTEST`, параметрів викликів активації облікових даних `TPM2_MakeCredential` та `TPM2_ActivateCredential`, а також зведену таблицю кодів помилок апаратного мікроконтролера.

## 1. Контракт команди TPM2_Quote

Команда `TPM2_Quote` (командний код `TPM_CC_Quote` = `0x00000158`) змушує апаратний модуль зняти криптографічний зліпок із вибраного набору регістрів PCR, упакувати його у фіксовану бінарну структуру разом з одноразовим викликом сервера та згенерувати цифровий підпис за допомогою ключа атестації.

Головна мета цієї команди — створити нерозривний криптографічний зв'язок між поточним станом конфігурації системи (зафіксованим у регістрах PCR), випадковим викликом віддаленого верифікатора (Nonce) та апаратним ключем атестації (AK). Оскільки формування дайджесту та накладання підпису відбуваються виключно всередині захищеного кристала чипа, операційна система хоста не може модифікувати зміст підписуваного повідомлення.

```
+---------------------------------------------------------------------------------+
| Команда TPM2_Quote (TPM_CC_Quote: 0x00000158)                                   |
+---------------------------------------------------------------------------------+
| Параметри виклику:                                                              |
| • signHandle (TPMI_DH_OBJECT)       : Дескриптор ключа атестації (AK)           |
| • qualifyingData (TPM2B_DATA)       : Одноразовий код виклику (Nonce, до 64 б)  |
| • inScheme (TPMT_SIG_SCHEME)        : Схема підпису (RSASSA, ECDSA, SM2)        |
| • PCRselect (TPML_PCR_SELECTION)    : Список банків та масок вибору регістрів   |
+---------------------------------------------------------------------------------+
| Повертані дані:                                                                 |
| • quoted (TPM2B_ATTEST)             : Серіалізована бінарна структура атестації |
| • signature (TPMT_SIGNATURE)        : Апаратний цифровий підпис над блоком      |
+---------------------------------------------------------------------------------+
```

### Вхідні параметри команди

Вхідний пакет команди складається з чотирьох основних компонентів, що передаються стеком TSS2 через дескриптори ресурсів:

1. **Дескриптор ключа (`signHandle`):** 32-бітний ідентифікатор `TPMI_DH_OBJECT`, який вказує на попередньо завантажений у пам'ять TPM об'єкт асиметричного ключа. Цей ключ обов'язково повинен мати прапорець `restricted` (що забороняє підпис довільних зовнішніх даних) та прапорець `sign` (дозвіл на операції підпису). Спроба передати дескриптор звичайного користувацького ключа призводить до повернення помилки `TPM_RC_ATTRIBUTES`.
2. **Дані кваліфікації (`qualifyingData`):** Двійковий буфер `TPM2B_DATA` розміром від 0 до 64 байтів. У сценаріях віддаленої атестації сюди записується криптографічний Nonce, згенерований верифікатором. Цей параметр гарантує свіжість цитати та захищає протокол від атак повторного відтворення (replay attacks).
3. **Криптографічна схема підпису (`inScheme`):** Структура `TPMT_SIG_SCHEME`, що визначає алгоритм підпису. Для ключів RSA зазвичай вказується `TPM_ALG_RSASSA` або `TPM_ALG_RSAPSS` із геш-функцією `TPM_ALG_SHA256`. Якщо схема була жорстко зафіксована при генерації ключа AK у структурі `TPMT_PUBLIC`, клієнт передає значення `TPM_ALG_NULL`, і чип автоматично використовує стандартну схему ключа.
4. **Вибірка регістрів (`PCRselect`):** Список `TPML_PCR_SELECTION`, який містить один або кілька записів `TPMS_PCR_SELECTION`. Кожен запис задає ідентифікатор алгоритму банку (наприклад, `TPM_ALG_SHA256`) та 3-байтний бітовий масив `pcrSelect[3]`, де кожен біт відповідає номеру регістра від 0 до 23.

### Вихідні структури та результати

Після успішного виконання чип повертає два двійкові блоки:
- `quoted`: структура `TPM2B_ATTEST`, що містить серіалізоване тіло атестаційного звіту `TPMS_ATTEST`. Довжина буфера залежить від розміру Nonce та кількості обраних регістрів, але не перевищує 1024 байтів.
- `signature`: складена структура `TPMT_SIGNATURE`, яка містить ідентифікатор використаного алгоритму підпису та масив байтів самого підпису (наприклад, 256 байтів для RSA-2048 або 64 байти для ECDSA P-256).

## 2. Бінарне розпланування структури TPMS_ATTEST

Структура `TPMS_ATTEST` формується виключно внутрішнім криптографічним ядром чипа TPM. Зовнішнє програмне забезпечення хоста не має технічної можливості підмінити або відредагувати жодне з її полів перед генерацією підпису. Кожне поле виконує конкретну функцію валідації в протоколі:

```
Поле                     Зсув (байти)  Розмір   Опис
┌───────────────────────┬────────────┬────────┬──────────────────────────────────────────┐
│ magic                 │ 0x00       │ 4      │ 0xFF544347 (TPM_GENERATED_VALUE)         │
│ type                  │ 0x04       │ 2      │ 0x8018 (TPM_ST_ATTEST_QUOTE)             │
│ qualifiedSigner.size  │ 0x06       │ 2      │ Довжина Qualified Name ключа AK          │
│ qualifiedSigner.name  │ 0x08       │ size   │ Унікальне криптографічне ім'я підписувача│
│ extraData.size        │ var        │ 2      │ Довжина переданого Nonce                 │
│ extraData.buffer      │ var        │ size   │ Байти Nonce від сервера                  │
│ clockInfo.clock       │ var        │ 8      │ Монотонний час роботи чипа (мс)          │
│ clockInfo.resetCount  │ var        │ 4      │ Кількість апаратних перезапусків TPM     │
│ clockInfo.restartCount│ var        │ 4      │ Кількість перезавантажень хоста          │
│ clockInfo.safe        │ var        │ 1      │ 1 = час не скидався аварійно             │
│ firmwareVersion       │ var        │ 8      │ Номер версії прошивки виробника чипа     │
│ attested.quote...     │ var        │ var    │ Специфічні дані цитати (TPMS_QUOTE_INFO) │
└───────────────────────┴────────────┴────────┴──────────────────────────────────────────┘
```

Поле `magic` завжди містить константу `0xFF544347` (у символьному представленні ASCII це байти `\xFF T C G`). Його наявність є апаратною гарантією того, що підписані дані згенеровані самим чипом, а не підсунуті зовнішньою програмою. Поле `type` вказує тип атестації — для команди Quote воно завжди дорівнює `0x8018` (`TPM_ST_ATTEST_QUOTE`).

Поле `qualifiedSigner` містить криптографічне ім'я підписувача (Qualified Name), яке враховує не лише відкритий ключ AK, а й усю ієрархію його батьківських ключів аж до первинного кореня `Owner Hierarchy` чи `Platform Hierarchy`.

Підструктура `clockInfo` надає захищену інформацію про час:
- `clock`: 64-бітний лічильник мілісекунд з моменту останнього скидання живлення чипа.
- `resetCount`: 32-бітний лічильник кількості повних циклів вимкнення та ввімкнення живлення мікроконтролера.
- `restartCount`: 32-бітний лічильник кількості перезапусків операційної системи без зняття напруги з чипа (soft reset).
- `safe`: 8-бітний прапорець, що підтверджує безперервність роботи внутрішнього генератора тактових імпульсів без аварійного збою живлення.

Поле `attested` для типу `TPM_ST_ATTEST_QUOTE` розгортається у структуру `TPMS_QUOTE_INFO`:

:::tabs
```c
typedef struct {
    TPML_PCR_SELECTION pcrSelect; /* Вибір банків та номерів регістрів */
    TPM2B_DIGEST       pcrDigest; /* SHA-256 дайджест композиту обраних PCR */
} TPMS_QUOTE_INFO;
```
```cpp
struct TPMS_QUOTE_INFO {
    TPML_PCR_SELECTION pcrSelect; // Вибір банків та номерів регістрів
    TPM2B_DIGEST       pcrDigest; // SHA-256 дайджест композиту обраних PCR
};
```
:::

Дайджест `pcrDigest` обчислюється чипом як результат послідовного гешування конкатенації поточних значень усіх зазначених у бітовій масці регістрів PCR:

```
pcrDigest = Hash( PCR[a] || PCR[b] || ... || PCR[k] )
```
де `Hash` — алгоритм гешування, зазначений у структурі банку `pcrSelect`.

## 3. Протокол активації облікових даних: MakeCredential та ActivateCredential

Процедура Credential Activation використовується для того, щоб віддалений верифікатор міг переконатися, що згенерований публічний ключ атестації `AK_pub` належить тому самому фізичному пристрою, автентичність якого підтверджена заводським сертифікатом `EK-Cert`.

Проблема, яку вирішує ця процедура, полягає в тому, що клієнт може згенерувати ключ AK самостійно і заявити, що він створений усередині TPM. Верифікатор не може перевірити це твердження безпосередньо, тому він створює криптографічну загадку, розв'язати яку може лише справжній апаратний чип, що володіє приватним ключем EK і одночасно завантажив саме цей об'єкт AK.

```
+-----------------------------------------------------------------------------------+
| Верифікатор (TPM2_MakeCredential)                                                 |
| 1. Отримує EK_pub (з EK-Cert) та AK_pub від клієнта                               |
| 2. Обчислює Name(AK) = HashAlg || Hash(AK_pub)                                    |
| 3. Генерує випадковий симетричний секрет S (наприклад, 256-бітний ключ)           |
| 4. Зашифровує S за допомогою симетричного алгоритму, прив'язаного до Name(AK)     |
|    → Отримує структуру TPM2B_ID_OBJECT credentialBlob                             |
| 5. Зашифровує симетричний ключ за допомогою EK_pub (RSA-OAEP / ECDH)              |
|    → Отримує структуру TPM2B_ENCRYPTED_SECRET secret                              |
+-----------------------------------------------------------------------------------+
                                          │
                                          │ Передача {credentialBlob, secret}
                                          ▼
+-----------------------------------------------------------------------------------+
| Клієнтський чип TPM (TPM2_ActivateCredential)                                     |
| 1. Приймає activateHandle (AK) та keyHandle (EK)                                  |
| 2. Розшифровує secret за допомогою апаратного приватного EK_priv                  |
| 3. Перевіряє, чи ім'я завантаженого об'єкта AK відповідає Name(AK)                |
| 4. Розшифровує credentialBlob та повертає відновлений секрет S у TPM2B_DIGEST     |
+-----------------------------------------------------------------------------------+
```

### Формат структур даних Credential Activation

Під час формування загадки через виклик `TPM2_MakeCredential` верифікатор створює два зв'язаних бінарних об'єкти:

1. **Ідентифікаційний об'єкт (`TPM2B_ID_OBJECT`):** Містить зашифрований симетричним алгоритмом секрет `credential` та код автентифікації повідомлення (HMAC integrity tag). Ключ для симетричного шифрування та обчислення HMAC виводиться за допомогою функції `KDFa` (Key Derivation Function in Counter Mode) з використанням випадкового зерна та криптографічного імені ключа `Name(AK)`.
2. **Зашифрований секрет (`TPM2B_ENCRYPTED_SECRET`):** Буфер, що містить асиметрично зашифроване зерно симетричного шифрування. Для ключів RSA використовується схема `RSAES-OAEP` із параметром розділення `NULL`. Для ключів ECC використовується протокол узгодження ключів `ECDH`.

Під час виклику `TPM2_ActivateCredential` клієнт передає чипу обидві структури разом із дескрипторами ключів `activateHandle` (дескриптор AK) та `keyHandle` (дескриптор EK). Мікроконтролер виконує такі операції:
- Застосовує свій внутрішній приватний ключ `EK_priv` для розшифрування вмісту `TPM2B_ENCRYPTED_SECRET`.
- Обчислює криптографічне ім'я завантаженого ключа `Name(AK)` і відновлює симетричні ключі шифрування через внутрішню функцію `KDFa`.
- Перевіряє HMAC-тег структури `TPM2B_ID_OBJECT`. Якщо ім'я завантаженого ключа відрізняється від того, для якого створювався пакет, чип повертає помилку цілісності `TPM_RC_INTEGRITY`.
- Якщо перевірка успішна, чип розшифровує початковий секрет і повертає його клієнту в структурі `TPM2B_DIGEST certInfo`.

Клієнт передає відновлений секрет верифікатору через мережеве з'єднання. Отримавши коректне значення, верифікатор отримує беззаперечний криптографічний доказ того, що ключ AK фізично розташований усередині саме того чипа TPM, чий сертифікат EK-Cert було перевірено на початку.

## 4. Коди повернення та обробка помилок (TPM Response Codes)

Усі виклики функцій TSS2 та повернення мікроконтролера TPM 2.0 повертають 32-бітний статус виконання `TPM_RC`. Якщо старші байти містять нуль (`TPM_RC_SUCCESS` = `0x00000000`), операція пройшла успішно. При виникненні помилок використовуються такі константи:

| Шістнадцятковий код | Мнемоніка константи | Причина виникнення та інженерна діагностика |
| :--- | :--- | :--- |
| `0x00000084` / `0x00000184` | `TPM_RC_VALUE` | Некоректне значення параметра. Передано недійсний номер регістра PCR або непідтримувану довжину Nonce (понад 64 байти). |
| `0x00000192` | `TPM_RC_SCHEME` | Схема підпису `inScheme` несумісна з параметрами створення ключа AK (наприклад, спроба використати RSAPSS для ключа ECDSA). |
| `0x0000008B` | `TPM_RC_HANDLE` | Вказаний дескриптор `signHandle` або `activateHandle` не існує в пам'яті чипа або був вивантажений менеджером ресурсів. |
| `0x0000009F` | `TPM_RC_INTEGRITY` | Помилка перевірки цілісності в `TPM2_ActivateCredential`. Ім'я переданого об'єкта AK не збіглося з `Name(AK)`, вказаним верифікатором. |
| `0x0000008E` | `TPM_RC_AUTH_FAIL` | Помилка авторизації сесії. Передано невірний пароль або недійсний HMAC-токен для доступу до приватного ключа. |
| `0x00000907` | `TPM_RC_MEMORY` | Вичерпано внутрішню оперативну пам'ять чипа (SRAM). Необхідно виконати контекстне збереження (`ContextSave`) для невикористовуваних ключів. |

## 5. Типовий сценарій виконання в консолі через tpm2-tools

Для практичної діагностики та налагодження систем атестації в середовищі Linux використовується набір утиліт `tpm2-tools`:

```bash
# 1. Генерація первинного ключа засвідчення EK під ієрархією Endorsement
tpm2_createprimary -C e -g sha256 -G rsa -c primary_ek.ctx

# 2. Створення та завантаження ключа атестації AK з фіксацією атрибутів
tpm2_create -C primary_ek.ctx -g sha256 -G rsa -u ak.pub -r ak.priv -a "restricted|sign|fixedtpm|fixedparent|sensitivedataorigin"
tpm2_load -C primary_ek.ctx -u ak.pub -r ak.priv -c ak.ctx

# 3. Формування атестаційної цитати для регістрів PCR 0, 1 та 7 з одноразовим Nonce
tpm2_quote -c ak.ctx -l sha256:0,1,7 -q "34a8f9c1b7e24d08" -m quote.msg -s quote.sig -o pcr.bin
```

Сформовані файли `quote.msg` (структура `TPM2B_ATTEST`), `quote.sig` (підпис `TPMT_SIGNATURE`) та `pcr.bin` передаються мережевому верифікатору для виконання автоматизованої перевірки.
