Коли віддалений сервер отримує мережевий запит на видачу конфіденційних ключів шифрування, розшифрування бази даних або підключення до закритого контуру інфраструктури, він стикається з фундаментальним парадоксом довіри. Якщо запитати в операційної системи хоста «чи ти скомпрометована?», відповідь завжди буде негативною: скомпрометоване ядро або перехоплений руткітом гіпервізор перехопить запит і поверне бездоганний фальшивий звіт. Програмне забезпечення не може достовірно свідчити про власний стан, оскільки інструменти контролю виконуються в тому самому середовищі, яке підлягає перевірці.

Щоб довести свою справжність і незмінність середовища віддаленому серверу, пристрій повинен мати фізично відокремлений апаратний якір довіри — кремнієвий модуль, який вимірює стан системи під час старту та формує криптографічний доказ, непідробний для самої операційної системи. Цей процес отримав назву віддаленої атестації (Remote Attestation).

## 1. Проблема семантичного розриву та неможливість програмного самозвіту

У класичній моделі мережевої автентифікації клієнт надає сертифікат X.509 (протокол mTLS) або підписаний сесійний токен. Цей механізм доводить лише одне: клієнтський процес володіє приватним ключем. Проте він нічого не повідомляє про те, яке саме програмне забезпечення зараз використовує цей ключ: легітимне мікросервісне ядро чи шкідливий інструмент, що перехопив пам'ять процесу через вразливість переповнення буфера або прямий доступ до пам'яті через шину PCI Express (DMA-атаки).

Зловмисник, отримавши найвищі привілеї адміністратора (`root` або `ring 0`), отримує повний контроль над системними викликами, таблицями сторінок пам'яті та файловою системою:

```
+─────────────────────────────────────────────────────────────+
| Скомпрометована операційна система (Host OS / Ring 0)       |
|                                                             |
|  [ Легітимний демон безпеки ] <── Перехоплено руткітом       |
|                │                  (DKOM / eBPF-хук)         |
|                ▼                                            |
|  Мережевий запит: "Стан ядра безпечний? SHA256 = ???"       |
|                │                                            |
|  Відповідь ОС: "Так, стан ідеальний (SHA256 = Golden_Val)"  |
+─────────────────────────────────────────────────────────────+
                               │  Фальшивий звіт
                               ▼
               [ Віддалений сервер-верифікатор ]
```

Якщо перевірка цілісності спирається виключно на програмні агенти всередині операційної системи, виникає семантичний розрив (Semantic Gap): віддалений верифікатор змушений вірити коду, який сам може перебувати під повним контролем атакуючого. Руткіти рівня ядра здатні маніпулювати структурами ядра безпосередньо в оперативній пам'яті (Direct Kernel Object Manipulation, DKOM), перехоплювати виклики підсистеми аудиту через eBPF або приховувати модифіковані модулі ядра від утиліти `lsmod`.

Крім того, атаки на базі гіпервізорів нульового рівня (Blue Pill або гіперруткіти) дозволяють перевести операційну систему у віртуалізований стан непомітно для самого ядра: гіпервізор перехоплює інструкції читання пам'яті та замінює скомпрометовані ділянки оригінальними бінарними кодами під час виконання перевірок безпеки.

Будь-які сканери файлової системи, контролери цілісності пакетів чи локальні антивірусні демони виявляються безсилими, оскільки їхній код, оперативна пам'ять і повертані значення API можуть бути підмінені на рівні ядра чи гіпервізора.

Єдиним способом подолання цієї проблеми є перенесення процесу вимірювання та збереження криптографічних доказів у фізично ізольований обчислювальний модуль — мікроконтролер Trusted Platform Module (TPM 2.0) або процесорний безпековий співпроцесор. Історичний шлях розвитку цієї концепції та драматичну боротьбу за стандарти конфіденційності описано в матеріалі [Еволюція віддаленої атестації: від суперечок довкола Privacy CA до конфіденційних обчислень](root:sf-security/remote-attestation/hist-remote-attestation-evolution.md).

## 2. Апаратні основи: первинні корені та ієрархія ідентичності чипа

Модуль TPM 2.0 є автономною системою на кристалі, що містить власне захищене процесорне ядро, апаратні криптографічні прискорювачі (RSA, ECC, AES, SHA-256/384), енергонезалежну пам'ять NVRAM та апаратний генератор справжніх випадкових чисел (TRNG).

Внутрішня архітектура TPM 2.0 організована навколо трьох незалежних первинних джерел ентропії (Primary Seeds), зашитих у кремній:
1. **Endorsement Primary Seed (EPS):** Джерело ідентичності виробника чипа. Використовується виключно для створення ієрархії засвідчення.
2. **Storage Primary Seed (SPS):** Джерело ієрархії власника платформи (Owner Hierarchy). Використовується для довготривалого шифрування дисків і збереження ключів користувача.
3. **Platform Primary Seed (PPS):** Джерело ієрархії прошивки платформи (Platform Hierarchy), доступне прошивці UEFI під час ініціалізації.

```
+-------------------------------------------------------------------+
| Апаратний мікроконтролер TPM 2.0                                  |
|                                                                   |
|  +--------------------+  +--------------------+  +-------------+  |
|  | Регістри PCR       |  | Первинні корені    |  | Крипторушій |  |
|  | PCR[0] .. PCR[23]  |  | EPS (Endorsement)  |  | RSA, ECC,   |  |
|  | (Банки SHA-256/384)|  | SPS (Storage)      |  | SHA-256     |  |
|  +--------------------+  +--------------------+  +-------------+  |
|            ▲                       │                              |
|            │                       ▼                              |
|   Операція Extend        +--------------------+                   |
|   (Лише додавання)       | Ключі атестації    |                   |
|                          | Endorsement (EK)   |                   |
|                          | Attestation (AK)   |                   |
|                          +--------------------+                   |
+-------------------------------------------------------------------+
```

### Ключ засвідчення (Endorsement Key, EK)

Endorsement Key є фундаментальним криптографічним якорем пристрою. Його приватна частина `EK_priv` виводиться всередині мікроконтролера на основі `EPS` та стандартного шаблону генерації (EK Template) за допомогою внутрішньої функції KDF.

- Приватний ключ `EK_priv` ніколи не експортується за межі захищеного кремнію мікросхеми у відкритому вигляді.
- Публічний ключ `EK_pub` засвідчується цифровим сертифікатом виробника (EK Certificate / EK-Cert), який записується у захищену область NVRAM чипа (за стандартом TCG — за фіксованою адресою `0x01c00002` для RSA або `0x01c0000a` для ECC).
- Сертифікат `EK-Cert` підписаний кореневим центром сертифікації виробника чипа (наприклад, Infineon TPM Root CA або STMicroelectronics TPM CA) і містить унікальний серійний номер мікросхеми та її криптографічні характеристики.

Проте використовувати ключ EK для прямого підпису атестаційних звітів суворо заборонено архітектурою безпеки TPM 2.0. Причини цієї заборони мають подвійну природу:
1. **Проблема нерозривного зв'язування (Linkability & Privacy Leak):** Якби EK підписував кожен мережевий запит, публічний ключ `EK_pub` перетворився б на глобальний незмінний ідентифікатор комп'ютера. Сервери в інтернеті могли б відстежувати активність користувача між різними доменами та сайтами, руйнуючи мережеву приватність.
2. **Криптографічне призначення:** Ключ EK генерується з атрибутами асиметричного шифрування (Decryption / Key Exchange), а не створення цифрового підпису, що унеможливлює його пряме використання для операцій `TPM2_Sign`.

### Ключ атестації (Attestation Key, AK)

Для забезпечення приватності та гнучкого управління операційна система генерує окремі вторинні пари ключів — Attestation Keys (AK). Адміністратор або програмний агент може створити окремий ключ AK для кожної незалежної системи верифікації (наприклад, один ключ для системи контролю доступу корпоративної мережі, інший — для хмарного сервісу моніторингу безпеки).

Ключ AK створюється всередині TPM під ієрархією Endorsement або Storage за допомогою команди `TPM2_Create` з жорстко зафіксованими апаратними атрибутами:
- `restricted`: Ключ не може використовуватися для підпису довільних користувацьких даних, переданих ззовні. Чип дозволяє використовувати AK виключно для підпису внутрішніх структур, сформованих самим криптопроцесором (наприклад, структури `TPMS_ATTEST`).
- `sign`: Ключ наділений правом виконувати операції генерації цифрового підпису (наприклад, алгоритмом RSASSA-SHA256 або ECDSA P-256).
- `fixedTPM` та `fixedParent`: Ключ криптографічно прив'язаний до цього конкретного екземпляра кремнію і не може бути дубльований або перенесений на іншу платформу.

Унікальне ім'я ключа `Name(AK)` обчислюється як конкатенація ідентифікатора алгоритму гешування та геша його публічної структури `TPMT_PUBLIC`. Крім того, TPM відстежує Qualified Name ключа (`QName`), який представляє собою геш усього ланцюга батьківських ключів від первинного кореня `EPS`/`SPS` до даного листка, що гарантує неможливість підміни контексту дерева об'єктів.

Порівняння різних кремнієвих реалізацій коренів довіри — від дискретних чипів до захищених процесорних анклавів Apple SEP та AMD SEV-SNP — наведено в огляді [Порівняння кремнієвих коренів довіри для атестації: TPM, Apple Secure Enclave, Titan та хмарні TEE](root:sf-security/remote-attestation/comp-secure-enclave-attestation.md).

## 3. Механізм виміряного завантаження (Measured Boot) та логіка Extend

Щоб сформувати доказ поточного стану системи, комп'ютер повинен зафіксувати кожен крок процесу завантаження, починаючи з найпершої інструкції центрального процесора. Тут виникає принципова різниця між двома спорідненими концепціями безпеки:

- **Secure Boot (Безпечне завантаження):** Локальний механізм примусового контролю. На кожному етапі завантажувальний компонент перевіряє цифровий підпис наступного бінарного образу перед передачею керування. Якщо підпис недійсний або відсутній у базі `db`, завантаження негайно переривається. Проте Secure Boot має суто бінарну логіку («дозволено» або «заборонено») і не зберігає деталей про те, які саме версії модулів, драйверів чи параметрів конфігурації було фактично активовано.
- **Measured Boot (Виміряне завантаження):** Механізм криптографічної фіксації фактів. Компонент перед передачею керування наступному модулю обчислює його криптографічний геш SHA-256 і записує отримане значення в апаратний регістр TPM. Процес завантаження продовжується за будь-яких умов, навіть якщо завантажено нестандартне чи скомпрометоване ядро, але факт запуску конкретного бінарного коду назавжди фіксується в апаратному кремнії до наступного перезавантаження.

```
       Secure Boot: Перевіряє підпис ──► Співпадає? ──► Запуск
                                              │
                                           Ні └──► Блокування завантаження

       Measured Boot: Обчислює SHA256 ──► TPM2_PCR_Extend ──► Запуск у будь-якому стані
                                                │
                                                └──► Стан зафіксовано для атестації
```

Початковою точкою вимірювань є статичний корінь вимірювань (Static Core Root of Trust for Measurement, S-CRTM) — невеликий блок коду в захищеній Flash-пам'яті материнської плати (BootBlock), який виконується відразу після зняття сигналу скидання процесора. S-CRTM вимірює основний образ прошивки UEFI, виконує перший `Extend` у регістр PCR[0] і лише потім передає керування основному мікрокоду.

### Математична операція PCR Extend

Регістри конфігурації платформи (Platform Configuration Registers, PCR) являють собою внутрішні енергозалежні комірки пам'яті TPM фіксованого розміру (32 байти для банку SHA-256, 48 байтів для банку SHA-384). Безпосередній довільний запис даних у регістри PCR заблоковано апаратною логікою мікроконтролера. Єдиним способом оновлення вмісту регістра є незворотна операція розширення (Extend):

```
PCR_new = SHA256( PCR_old || Event_Digest )
```

Ця операція має три ключові криптографічні властивості:
1. **Незворотність та стійкість до колізій:** Завдяки властивостям геш-функції SHA-256 зловмисник не може розрахувати такий вхідний дайджест `Event_Digest`, який би повернув регістр PCR до попереднього стану або встановив у ньому наперед задане значення.
2. **Чутливість до послідовності подій:** Оскільки конкатенація операндів під гешем залежить від порядку аргументів:
   ```
   SHA256( A || B ) ≠ SHA256( B || A )
   ```
   будь-яка зміна порядку ініціалізації драйверів або завантажувальних фаз призведе до кардинально іншого фінального дайджесту PCR.
3. **Захист від стирання:** Регістри 0–15 ініціалізуються нульовими байтами (`0x00...00`) виключно під час подачі живлення на платформу (Power-on Reset). Жоден програмний процес, включно з ядром операційної системи, не здатний скинути їх у нуль без повного апаратного перезавантаження всієї системи.

*Ланцюг розширення регістра PCR криптографічним хешем та повторне обчислення стану верифікатором за записом подій.*

### Стандартний розподіл регістрів PCR за специфікацією TCG

Специфікація TCG PC Client Platform Firmware Profile жорстко закріплює призначення перших 16 регістрів PCR за конкретними етапами завантаження комп'ютерної платформи:

| Номер PCR | Контрольований компонент платформи |
| :--- | :--- |
| **PCR[0]** | Код первинного завантажувача: Core Root of Trust for Measurement (CRTM), BIOS/UEFI ROM, системна прошивка материнської плати. |
| **PCR[1]** | Конфігурація хоста: налаштування BIOS Setup, таблиці конфігурації ACPI, SMBIOS, порядок завантажувальних пристроїв. |
| **PCR[2]** | Код плат розширення: Option ROM мережевих контролерів, RAID-адаптерів та графічних прискорювачів. |
| **PCR[3]** | Конфігурація та налаштування плат розширення (Option ROM Configuration). |
| **PCR[4]** | Код головного завантажувача: Master Boot Record (MBR), виконуваний файл завантажувача UEFI (`shim.efi`, `grubx64.efi`, `systemd-boot`). |
| **PCR[5]** | Дані та конфігурація завантажувача: файл конфігурації `grub.cfg`, змінні оточення EFI Boot Manager. |
| **PCR[7]** | Стан підсистеми Secure Boot: вміст сертифікаційних баз даних `PK`, `KEK`, дозволених підписів `db` та відкликаних хешів `dbx`. |
| **PCR[8]** | Командний рядок ядра Linux: повний вміст параметрів завантаження ядра з `/proc/cmdline`. |
| **PCR[9]** | Бінарні образи системи: виконуваний файл ядра Linux (`vmlinuz`) та початковий образ оперативної пам'яті (`initramfs`). |
| **PCR[10]** | Вимірювання простору користувача: журнал підсистеми цілісності Linux IMA (Integrity Measurement Architecture). |
| **PCR[11]** | Об'єднаний образ ядра (Unified Kernel Image, UKI): вимірювання комбінованого PE-бінарника, що об'єднує ядро, initrd та cmdline. |

### Проблема ламкості PCR та об'єднані образи ядер (UKI)

У традиційних дистрибутивах Linux вимірювання розбиті по декількох регістрах: конфігурація завантажувача потрапляє в PCR[5], параметри ядра — в PCR[8], а саме ядро та `initramfs` — в PCR[9]. Будь-яке оновлення мінорного пакета ядра чи генерація нового `initramfs` приводили до зміни значень PCR, ламаючи автоматичну атестацію та розблокування дисків LUKS.

Сучасні архітектури вирішують цю проблему через використання об'єднаних образів ядер (Unified Kernel Image, UKI): ядро, `initramfs`, завантажувальні параметри та сертифікати пакуються в єдиний виконуваний PE-бінарник, який вимірюється завантажувачем `systemd-boot` або `systemd-stub` безпосередньо в регістр PCR[11]. Для гнучкого управління оновленнями застосовується механізм підписаних політик `TPM2_PolicyAuthorize`: дистрибутив підписує відкритим ключем майбутні очікувані значення PCR[11], дозволяючи оновлювати ядро без скидання ключів безпеки.

Спеціальні утиліти `systemd-measure` дозволяють обчислити очікуваний підпис PCR ще до перезавантаження системи, а `systemd-pcrphase` автоматично розширює регістри спеціальними фазовими маркерами (`enter-initrd`, `leave-initrd`, `sysinit`, `ready`), що унеможливлює використання ключів розшифрування після завершення процесу старту.

### Журнал вимірювань TCG Event Log

Оскільки кінцеве значення регістра PCR являє собою згорнутий 32-байтний геш, отриманий у результаті десятків або сотень послідовних операцій розширення, віддалений сервер не може безпосередньо визначити з самого лише числа, який саме файл чи модуль спричинив зміну значення.

Для забезпечення прозорості прошивка UEFI та ядро Linux паралельно з кожною операцією `TPM2_PCR_Extend` записують детальну інформацію про подію у спеціальний журнал — TCG Event Log. У середовищі Linux цей двійковий файл експортується ядром через псевдофайлову систему SecurityFS за шляхом `/sys/kernel/security/tpm0/binary_bios_measurements`.

Кожен двійковий запис журналу містить такі поля:
- `pcrIndex`: Номер регістра PCR, для якого призначене вимірювання (0–23).
- `eventType`: Тип події (наприклад, `EV_EFI_BOOT_SERVICES_APPLICATION` для завантажувача або `EV_IPL` для ядра).
- `digests`: Масив криптографічних гешів компонента для всіх активних банків алгоритмів (SHA-256, SHA-384).
- `eventSize` та `event`: Детальний опис події у двійковому форматі (шлях до файлу на розділі ESP, назва модуля або рядок конфігурації).

Хоча сам файл журналу розташований у звичайній оперативній пам'яті хоста і може бути модифікований скомпрометованим ядром, будь-яка спроба фальсифікації логу миттєво виявляється: верифікатор бере записи журналу, послідовно повторює операцію `Extend` від початкового нульового стану і порівнює результат з апаратно підписаним дайджестом PCR від чипа TPM. Якщо зловмисник видалив запис про неавторизований драйвер із логу, розраховане сервером значення не збіжиться з апаратним зліпком чипа.

## 4. Протокол виклику-відповіді та генерація цитати TPM2_Quote

Процедура віддаленої атестації реалізується на основі криптографічного протоколу виклику-відповіді (Challenge-Response), який гарантує свіжість даних та захищає систему від атак повторного відтворення (Replay Attacks).

![Архітектура та протокол виклику-відповіді віддаленої атестації TPM 2.0](/root/eng/sf-security/remote-attestation/img/attestation-protocol-flow.svg)
*Взаємодія між клієнтським чипом TPM, сервісом атестації та верифікатором: виклик із nonce, генерація цитати TPM2_Quote та активація сертифіката AK.*

Повний цикл протоколу складається з п'яти послідовних фаз:

### Крок 1. Генерація виклику сервером (Challenge Nonce)

Сервер-верифікатор генерує криптографічно надійний псевдовипадковий масив байтів — `Nonce` розміром від 16 до 32 байтів. Верифікатор зберігає `Nonce` у тимчасовій сесійній базі даних і надсилає клієнтському вузлу мережевий запит на проходження атестації, вказуючи згенерований `Nonce` та список необхідних для перевірки регістрів PCR (наприклад, PCR 0, 7, 8, 9).

### Крок 2. Передача виклику до мікроконтролера TPM

Клієнтський агент безпеки отримує мережевий пакет і викликає функцію `Esys_Quote` або низькорівневу команду TSS2 `TPM2_Quote`. Агент передає чипу три параметри:
- Дескриптор попередньо завантаженого ключа атестації (`signHandle` = `Handle(AK)`).
- Отримане від сервера значення одноразового виклику (`qualifyingData` = `Nonce`).
- Структуру вибору банків та номерів регістрів (`PCRselect` = `TPML_PCR_SELECTION`).

### Крок 3. Внутрішня генерація сертифікаційного блоку TPMS_ATTEST

Мікроконтролер TPM виконує операції виключно всередині свого ізольованого кристала:
1. Зчитує поточні апаратні значення з указаних у бітовій масці регістрів PCR.
2. Обчислює композитний дайджест обраних регістрів шляхом їхньої конкатенації та гешування:
   ```
   pcrDigest = SHA256( PCR[0] || PCR[7] || PCR[8] || PCR[9] )
   ```
3. Формує стандартизовану внутрішню бінарну структуру `TPMS_ATTEST`, де:
   - поле `magic` заповнюється магічною константою `0xFF544347` (`TPM_GENERATED_VALUE`);
   - поле `type` набуває значення `0x8018` (`TPM_ST_ATTEST_QUOTE`);
   - поле `extraData` заповнюється переданим від сервера значенням `Nonce`;
   - поле `clockInfo` фіксує монотонний час роботи чипа та апаратні лічильники скидання живлення;
   - підструктура `attested.quote` містить маску запитаних регістрів та розрахований композитний дайджест `pcrDigest`.
4. Використовує приватний ключ `AK_priv` для створення асиметричного цифрового підпису над сформованим бінарним буфером `TPMS_ATTEST`.
5. Повертає серіалізований пакет `TPM2B_ATTEST` та структуру підпису `TPMT_SIGNATURE` клієнтському процесу.

Детальний двійковий розклад полів структури `TPMS_ATTEST` та специфікацію командних структур описано у довіднику [Бінарні структури TPM2_Quote та криптографічний протокол Credential Activation](root:sf-security/remote-attestation/api-tpm2-quote-structures.md).

### Крок 4. Відправка атестаційного пакета верифікатору

Клієнтський агент передає віддаленому серверу сформований підтверджувальний пакет, що містить:
- Серіалізований буфер цитати `TPM2B_ATTEST`.
- Криптографічний підпис `TPMT_SIGNATURE`.
- Повний дамп журналу завантаження `TCG Event Log`.

## 5. Двофазна активація облікових даних (Credential Activation)

Перед тим як приймати цитату, підписану ключем AK, сервер-верифікатор повинен вирішити критичне завдання перевірки походження ключа: *«Як переконатися, що відкритий ключ AK_pub дійсно створено всередині справжнього апаратного чипа TPM, чий сертифікат EK-Cert підписаний легітимним виробником, а не згенеровано програмним генератором на віртуальній машині зловмисника?»*.

Оскільки відкритий ключ AK не має заводського сертифіката, консорціум TCG запровадив двофазний протокол активації облікових даних на базі команд `TPM2_MakeCredential` та `TPM2_ActivateCredential`.

![Двофазна процедура прив'язки ключа AK до апаратного чипа через MakeCredential та ActivateCredential](/root/eng/sf-security/remote-attestation/img/tpm2-credential-activation.svg)
*Шифрування секрету на публічному EK та розшифрування всередині TPM лише за умови володіння прив'язаним AK.*

### Фаза 1: Створення криптографічної загадки (MakeCredential)

Верифікатор виконує операцію локально без безпосереднього звернення до клієнтського чипа:
1. Отримує від клієнта заводський сертифікат `EK-Cert` та перевіряє його дійсність за ланцюгом сертифікатів виробника мікросхеми. Якщо сертифікат валідний, верифікатор витягує з нього відкритий ключ `EK_pub`.
2. Отримує від клієнта публічну частину згенерованого ключа атестації `AK_pub` та обчислює його унікальне криптографічне ім'я:
   ```
   Name(AK) = SHA256_AlgID || SHA256( AK_pub_bytes )
   ```
3. Генерує випадковий 256-бітний симетричний секретний ключ `K`.
4. Створює подвійну зашифровану структуру:
   - Внутрішній блок `TPM2B_ID_OBJECT`: містить секрет `K` та HMAC-тег цілісності, розрахований за допомогою симетричного ключа, виведеного через внутрішню функцію `KDFa` від імені `Name(AK)`.
   - Зовнішній блок `TPM2B_ENCRYPTED_SECRET`: містить асиметрично зашифроване на публічному ключі `EK_pub` насіння для відновлення симетричного ключа за алгоритмом RSA-OAEP або ECDH.
5. Відправляє двійковий пакет `{ID_Object, Encrypted_Secret}` клієнту через мережу.

Математична функція `KDFa` працює в режимі лічильника (Counter Mode) над HMAC-SHA256, гарантуючи, що симетричні ключі шифрування та HMAC-теги строго детерміновані для даного імені об'єкта `Name(AK)`:

```
KDFa(Key, Label, ContextU, ContextV) = HMAC_SHA256(Key, Counter || Label || ContextU || ContextV)
```

### Фаза 2: Розв'язання загадки мікроконтролером (ActivateCredential)

Клієнт передає отримані структури до чипа через команду `TPM2_ActivateCredential`, вказуючи дескриптор завантаженого ключа `AK` та дескриптор первинного ключа `EK`:
1. TPM застосовує свій апаратний приватний ключ `EK_priv` для зняття зовнішнього асиметричного шару та відновлення вихідного насіння.
2. TPM розраховує криптографічне ім'я завантаженого на даний момент ключа AK і відновлює ключ HMAC через власну реалізацію `KDFa`. Якщо завантажений об'єкт AK не відповідає тому, для якого створювався пакет, HMAC-тег структури `ID_OBJECT` не зійдеться, і чип негайно заблокує операцію, повернувши статус помилки `TPM_RC_INTEGRITY`.
3. Якщо перевірка імені успішна, TPM розшифровує секретний ключ `K` і повертає його клієнтському процесу.
4. Клієнт передає розшифрований секрет `K` верифікатору.

Отримавши правильне значення `K`, сервер-верифікатор отримує математичний доказ: ключ `AK_pub` дійсно розташований усередині того самого фізичного чипа TPM, чий сертифікат `EK-Cert` було перевірено на початку. З цього моменту сервер реєструє `AK_pub` як довірений ключ атестації даного вузла.

## 6. Алгоритм верифікації на стороні сервера (Appraisal та Event Log Replay)

Отримавши атестаційний звіт, сервер-верифікатор виконує строгий багаторівневий алгоритм оцінки та відтворення (Appraisal Engine):

```
+─────────────────────────────────────────────────────────────+
| Вхідні дані: TPM2B_ATTEST, Signature, Event Log, Nonce      |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
| Етап 1: Перевірка цифрового підпису AK                      |
| • VerifySignature(AK_pub, TPM2B_ATTEST, Signature) == OK    |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
| Етап 2: Валідація метаданих структури TPMS_ATTEST           |
| • magic == 0xFF544347                                       |
| • extraData == Challenge_Nonce (Свіжість виклику)           |
| • clockInfo.resetCount відповідає очікуваному значенню      |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
| Етап 3: Відтворення журналу завантаження (Event Log Replay) |
| • Sim_PCR[i] = 0x00..00                                     |
| • Для кожного запису в лозі:                                |
|     Sim_PCR[i] = SHA256(Sim_PCR[i] || Event.Digest)         |
| • Expected_Composite = SHA256(Sim_PCR_0 || Sim_PCR_7 || ..) |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
| Етап 4: Порівняння композитних дайджестів                   |
| • Expected_Composite == TPMS_ATTEST.attested.quote.pcrDigest |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
| Етап 5: Оцінка семантики журналу за базою еталонів (RIM)    |
| • Чи входять геші завантажувача та ядра у whitelist?        |
| • Чи відповідають параметри командного рядка безпечній базі? |
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
            [ РІШЕННЯ ПРО ДОПУСК / БЛОКУВАННЯ ВУЗЛА ]
```

Повну програмну реалізацію логіки верифікатора з парсингом бінарних структур та математичним відтворенням логу мовами C та C++ наведено у проекті [Реалізація верифікатора цитати TPM2_Quote та відновлення стану PCR](root:sf-security/remote-attestation/proj-tpm2-quote-verifier.md).

### База еталонних вимірювань (Reference Integrity Measurements, RIM)

Збіг відтвореного геша з цитатою TPM доводить лише одне: журнал подій не сфальсифіковано, і він точно відтворює послідовність дій на пристрої. Проте він сам по собі не відповідає на питання, чи є завантажена конфігурація безпечною.

Для прийняття рішення про допуск вузла сервер зіставляє окремі записи журналу з базою еталонних вимірювань (Reference Integrity Measurements, RIM / Golden Values):
- Чи відповідає геш прошивки UEFI офіційному релізу вендора материнської плати?
- Чи відповідають підписи `shim.efi`, завантажувача GRUB та ядра `vmlinuz` офіційним релізам дистрибутива Linux?
- Чи не містить командний рядок ядра небезпечних параметрів налагодження (`init=/bin/sh`, `enforcing=0`, `nokaslr`)?
- Чи відповідає стан бази відкликаних підписів `dbx` у PCR[7] найсвіжішому бюлетеню безпеки UEFI Forum?

Якщо хоча б один дайджест не входить до білого списку (Whitelist), сервер блокує авторизацію вузла, ізолює його порт на комутаторі та сповіщає службу безпеки про компрометацію цілісності.

### Виявлення та локалізація збоїв атестації (Triage & Diagnostics)

У промислових середовищах інженери з експлуатації найчастіше стикаються з трьома типами відхилень атестації (Attestation Drift):
1. **Дрейф конфігурації NVRAM (PCR[1]):** Зміна порядку завантажувальних дисків у BIOS або підключення нового USB-носія під час технічного обслуговування змінює дайджест регістра PCR[1]. Для локалізації використовується утиліта `tpm2_eventlog`, яка порівнює дампи старого та нового журналів рядок за рядком.
2. **Оновлення мікрокоду CPU (PCR[0]):** Патчі безпеки процесора (Microcode Updates), застосовані прошивкою материнської плати, змінюють вихідний геш CRTM. Це вимагає попереднього оновлення маніфесту RIM до перезавантаження серверів кластера.
3. **Розсинхронізація лічильників часу (`TPMS_CLOCK_INFO`):** Якщо пристрій тривалий час перебував у стані глибокого сну або батарейка RTC вийшла з ладу, прапорець `safe` у структурі `clockInfo` скидається в 0, що слугує сигналом для додаткової перевірки цілісності платформи.

## 7. Інтеграція в архітектуру Zero Trust та вирішення проблеми TOCTOU

Віддалена атестація є наріжним каменем архітектури нульової довіри (Zero Trust Architecture). Замість надання статичного безстрокового доступу робочі вузли датацентру зобов'язані регулярно доводити свій стан для отримання короткоживучих криптографічних сертифікатів:

```
[ Робочий вузол ] ── 1. TPM2_Quote + Event Log ──► [ Сервіс атестації ]
                                                            │
                                                     2. Валідація за RIM
                                                            │
                                                            ▼
[ Доступ до mTLS мережі ] ◄── 3. Короткоживучий ──── [ Внутрішній CA ]
                                 X.509 сертифікат
                                 (Дійсний 1 год)
```

1. Під час завантаження сервер формує цитату TPM та передає її внутрішньому центру атестації (наприклад, фреймворку SPIFFE/SPIRE).
2. Сервіс атестації валідує цитату, відтворює Event Log та звіряє параметри з базою RIM.
3. У разі успішної перевірки внутрішній центр сертифікації видає вузлу короткоживучий сертифікат X.509 SVID (SPIFFE Verifiable Identity Document), дійсний протягом однієї години.
4. Усі міжсервісні з'єднання та мікросервісні запити в кластері вимагають взаємної mTLS-автентифікації на базі цього сертифіката.

> 🔧 **Навіщо це в реальній розробці:**
> У великих хмарних кластерах Kubernetes віддалена атестація запобігає підключенню скомпрометованих фізичних нод. Навіть якщо зловмисник скопіював диск віртуальної машини або викрав токени доступу сервісних акаунтів, він не зможе згенерувати дійсну атестаційну цитату без доступу до зареєстрованого апаратного чипа TPM з валідним заводським сертифікатом `EK-Cert`.

### Подолання розриву між перевіркою та використанням (TOCTOU)

Головною вразливістю класичної атестації завантаження є проблема Time-of-Check to Time-of-Use (TOCTOU): система успішно проходить атестацію в момент старту, але через дві години піддається експлуатації вразливості в користувацькому просторі та компрометується в пам'яті. Регістри PCR завантаження при цьому залишаються незмінними, і базова атестація продовжує вважати вузол безпечним.

Для подолання цієї загрози сучасні системи застосовують комплексний ешелонований підхід:
- **Підсистема Linux IMA (Integrity Measurement Architecture):** Ядро вимірює геш кожного виконуваного бінарного файлу, динамічної бібліотеки та конфігураційного скрипту безпосередньо перед завантаженням у пам'ять (`execve`, `mmap`) і розширює ними регістр PCR[10]. Журнал IMA транслюється серверу в режимі реального часу.
- **Динамічний корінь довіри для вимірювань (Dynamic Root of Trust for Measurement, DRTM):** Процесорні технології Intel TXT або AMD Secure Startup дозволяють скинути та повторно виміряти стан системи посеред виконання без повного перезавантаження за допомогою спеціальних інструкцій процесора `GETSEC[SENTER]` або `SKINIT`.
- **Періодична повторна атестація:** Агенти безпеки оновлюють атестаційні цитати кожні 10–15 хвилин з новими одноразовими значеннями Nonce, відстежуючи монотонний приріст системного часу `clockInfo.clock` та фіксуючи появу нових подій у журналі IMA.
- **Конфіденційні обчислення (Confidential Containers / CoCo):** У хмарах атестація хоста доповнюється атестацією ізольованого апаратного TEE (AMD SEV-SNP, Intel TDX). Атестаційний брокер Key Broker Service (KBS) розшифровує образ контейнера лише після перевірки процесорного атестаційного звіту, унеможливлюючи доступ до даних навіть для адміністратора гіпервізора.

Віддалена атестація перетворює абстрактне припущення про безпеку на строгий математичний ланцюг кремнієвих доказів, забезпечуючи захист інфраструктури навіть в умовах ворожого мережевого оточення.
