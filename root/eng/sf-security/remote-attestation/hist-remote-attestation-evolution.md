# 📜 Еволюція віддаленої атестації: від суперечок довкола Privacy CA до конфіденційних обчислень

Ідея змусити обчислювальний пристрій криптографічно доводити свій внутрішній стан віддаленому серверу виникла не як корпоративний інструмент хмарної безпеки, а як результат гострого конфлікту інтересів на зламі 1990-х та 2000-х років. Коли комерційне програмне забезпечення та цифрові медіаматеріали масово перейшли в цифрові мережі, правовласники зіткнулися з фундаментальною вразливістю архітектури ПК: локальний користувач, маючи привілеї адміністратора або фізичний доступ до шини пам'яті, міг перехопити будь-який розшифрований контент. Звичайні операційні системи не могли надати жодних гарантій віддаленій стороні, оскільки скомпрометоване ядро могло імітувати довільний стан безпеки.

## Альянс TCPA та суперечка довкола проекту Palladium

У 1999 році корпорації Compaq, HP, IBM, Intel та Microsoft створили консорціум Trusted Computing Platform Alliance (TCPA), пізніше реорганізований у Trusted Computing Group (TCG). Їхньою метою було створення апаратного якоря довіри, вбудованого в кожен комп'ютер, здатного гарантувати незмінність середовища виконання.

Паралельно Microsoft оголосила про розробку ініціативи під кодовою назвою Palladium (пізніше перейменованої на Next-Generation Secure Computing Base, NGSCB). За задумом інженерів, архітектура поєднувала спеціальні процесорні режими ізоляції пам'яті та апаратний криптографічний чип для криптографічного засвідчення того, яка саме програма обробляє захищені дані.

```
1999: Створення альянсу TCPA (IBM, Intel, Microsoft, HP)
      │
2002: Анонс Microsoft Palladium / NGSCB
      │  └─ Критика Річарда Сталлмана та Росса Андерсона (загроза DRM-локапу)
      │
2003: Реорганізація в Trusted Computing Group (TCG) та специфікація TPM 1.1b
      │  └─ Поява моделі Privacy CA для розділення EK та AIK
      │
2004: Розробка Direct Anonymous Attestation (DAA, Каменіш-Лисянська)
      │  └─ Доведення автентичності без розкриття унікального ID чипа
      │
2013: Затвердження стандарту TPM 2.0
      │  └─ Перехід до прямої активації облікових даних (MakeCredential / ActivateCredential)
      │
2018+: Епоха Confidential Computing (Intel SGX DCAP, AMD SEV-SNP, Intel TDX)
         └─ Атестація пам'яті та стану ізольованих віртуальних машин у хмарі
```

Оприлюднення планів TCPA викликало безпрецедентний спротив академічної спільноти та прихильників вільного програмного забезпечення. Британський криптограф Росс Андерсон опублікував маніфест «TCPA / Palladium FAQ», у якому аргументував, що віддалена атестація перетворить персональний комп'ютер на пристрій, де власник втрачає контроль над власним обладнанням. Річард Сталлман назвав цю концепцію «Treacherous Computing» (віроломні обчислення), вказуючи на ризик блокування відкритих форматів файлів і заборони сторонніх операційних систем через механізм запечатування даних під конкретну версію ядра Windows.

Ключовим технічним каменем спотикання стала проблема приватності: якщо кожен чип безпеки має унікальний заводський сертифікований ключ Endorsement Key (EK), то його використання для прямого цифрового підпису кожного мережевого запиту перетворює EK на глобальний глобальний ідентифікатор пристрою. Сервери в інтернеті могли б легко відстежувати переміщення користувача між вебсайтами та збирати цифровий профіль обладнання, що знищувало мережеву анонімність.

## Архітектура Privacy CA у специфікаціях TPM 1.1b та TPM 1.2

Для подолання дилеми ідентифікації консорціум TCG у специфікаціях TPM 1.1b (2003 рік) та TPM 1.2 (2005 рік) запровадив суворе архітектурне розділення:

1. **Ключ засвідчення (Endorsement Key, EK):** Апаратна асиметрична пара ключів (зазвичай RSA-2048), приватна частина якої зашита в кремній на заводі виробника і захищена від зчитування. Публічна частина засвідчена сертифікатом виробника (EK-Cert). За стандартом EK ніколи не використовується для створення цифрових підписів користувацьких даних або станів PCR.
2. **Ключі ідентичності атестації (Attestation Identity Key, AIK):** Тимчасові, необмежено створювані ключі, які підписують вимірювання регістрів PCR.

Оскільки віддалена сторона не могла безпосередньо знати, чи згенеровано ключ AIK на справжньому апаратному чипі TPM, чи він просто створений програмним емулятором, стандарт передбачав використання третьої довіреної сторони — центру сертифікації конфіденційності (Privacy CA).

```
Клієнт (TPM)                      Privacy CA                    Верифікатор
      │                               │                              │
      │── 1. AIK_pub + EK-Cert ──────>│                              │
      │   (Запит на сертифікацію)     │                              │
      │                               │ (Перевіряє EK-Cert           │
      │                               │  і шифрує симетричний        │
      │                               │  пароль на EK_pub)           │
      │<── 2. Зашифрований сертифікат─│                              │
      │                               │                              │
      │ (TPM розшифровує через EK_priv                               │
      │  та отримує AIK-сертифікат)                                  │
      │                                                              │
      │── 3. Quote(PCRs) + AIK-Cert + Nonce ────────────────────────>│
      │                                                              │ (Перевіряє AIK-Cert
      │                                                              │  без знання EK чипа)
```

Процедура працювала наступним чином: клієнт генерував новий ключ AIK і надсилав запит до Privacy CA, додаючи свій заводський сертифікат EK-Cert. Сервіс Privacy CA перевіряв справжність виробника чипа, генерував сертифікат для AIK і зашифровував його на публічному ключі EK. Лише справжній апаратний TPM міг розшифрувати цей пакет своїм приватним EK.

У результаті верифікатор отримував підпис AIK, завірений сертифікатом Privacy CA, але не дізнавався справжнього серійного номера чи ключа EK пристрою. Проте модель Privacy CA зазнала комерційного фіаско. Сервіс ставав єдиною точкою відмови, вимагав постійного підключення до мережі третьої сторони, створював ризик змови між Privacy CA та верифікатором, а також був занадто складним та дорогим для корпоративних мереж.

## Direct Anonymous Attestation (DAA) та Intel EPID

У 2004 році дослідники Ерні Брікелл (Ernie Brickell) з Intel, Ян Каменіш (Jan Camenisch) з IBM Research та Лікунь Чень (Liqun Chen) з HP Labs запропонували протокол прямої анонімної атестації (Direct Anonymous Attestation, DAA), заснований на доказах з нульовим розголошенням (Zero-Knowledge Proofs) над групами простих порядків і сигнатурних схемах Каменіша-Лисянської (CL-signatures).

DAA дозволяв чипу TPM довести віддаленій стороні наступне твердження: *«Я є автентичним TPM, сертифікованим легітимним емітентом, і мій поточний стан конфігурації PCR дорівнює X, проте я не розкриваю, який саме екземпляр чипа з пулу авторизованих пристроїв виконує цей підпис»*.

Корпорація Intel адаптувала принципи DAA у власній пропрієтарній схемі Intel Enhanced Privacy ID (EPID), яку було вбудовано в апаратні модулі Intel Management Engine (ME) та середовище захищених енклавів Intel SGX. Проте математична складність криптографічних перетворень на еліптичних кривих (pairing-friendly curves) та значний обсяг обчислень виявилися занадто ресурсомісткими для масових дешевих мікроконтролерів дискретних TPM.

## Зміна парадигми в TPM 2.0: Credential Activation

У 2013 році консорціум TCG випустив специфікацію TPM 2.0, яка кардинально переглянула модель атестації. Від ідеї обов'язкового стороннього Privacy CA та важких протоколів DAA відмовилися на користь прямої двофазної криптографічної активації облікових даних — протоколу Credential Activation (`TPM2_MakeCredential` / `TPM2_ActivateCredential`).

Замість глобального посередника будь-який віддалений сервер (верифікатор) отримав можливість самостійно виступити центром активації для конкретного пристрою. Сервер генерує криптографічний виклик, шифрує секрет на публічному ключі EK чипа із захистом за допомогою криптографічного геша імені нового ключа атестації (`Name(AK)`), а чип апаратно доводить володіння обома ключами одночасно. Це усунуло залежність від сторонніх хмарних служб і зробило віддалену атестацію стандартом для автентифікації парку корпоративних серверів, робочих станцій та пристроїв інтернету речей.

## Від материнської плати до конфіденційних хмар (Confidential Computing)

Починаючи з 2015 року вектор розвитку віддаленої атестації змістився з фізичних комп'ютерів у сферу хмарних обчислень. Якщо раніше атестація захищала контент від локального користувача, то у публічних хмарах (AWS, Azure, Google Cloud) виникла протилежна потреба: захистити робочі навантаження клієнта від адміністраторів хмарного провайдера та скомпрометованого гіпервізора.

З'явилися апаратні технології конфіденційних обчислень (Confidential Computing):
- **Intel SGX (Software Guard Extensions):** Ізольовані анклави користувацького простору. Початковий протокол EPID у версії SGX DCAP (Data Center Attestation Primitives) було замінено на стандартні сертифікати X.509 на еліптичних кривих ECDSA, що дозволило датацентрам розгортати локальні кешувальні сервіси перевірки (Provisioning Certificate Enclave).
- **AMD SEV-SNP (Secure Encrypted Virtualization-Secure Nested Paging):** Атестація повноцінних гостьових віртуальних машин. Апаратний співпроцесор безпеки AMD Secure Processor формує підписаний криптографічний звіт `ATTESTATION_REPORT` за допомогою кореневого ключа версії кристала (Versioned Chip Endorsement Key, VCEK), прив'язаного до конкретного рівня прошивки CPU.
- **Intel TDX (Trust Domain Extensions) та ARM CCA (Confidential Compute Architecture):** Сучасні апаратні розширення, що генерують атестаційні цитати для апаратно ізольованих доменів довіри.

Таким чином, технологія віддаленої атестації пройшла шлях від суперечливого механізму цифрових обмежень до фундаменту безпеки сучасного хмарного світу, де жоден компонент операційної системи не вважається довіреним без криптографічного доказу з кремнієвого джерела істини.
