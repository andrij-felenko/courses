# 📋 Інтерфейси узгодження ключів: OpenSSL 3.0 EVP_PKEY та libsodium crypto_kx

Узгодження ключів у сучасному системному та прикладному програмному забезпеченні спирається на стандартизовані бібліотечні інтерфейси. Найбільш поширеними у виробничому середовищі є універсальний провайдерний API бібліотеки **OpenSSL 3.0** (`EVP_PKEY`) та спеціалізований захищений API бібліотеки **libsodium** (`crypto_kx`).

## 1. OpenSSL 3.0 Provider API: Сімейство функцій EVP_PKEY_derive

Починаючи з версії 3.0, криптографічна бібліотека OpenSSL перейшла на модульну архітектуру провайдерів (англ. *Providers*). Усі операції з асиметричними ключами (як класичний обмін за модулем у скінченних полях `EVP_PKEY_DH`, так і обмін на еліптичних кривих `EVP_PKEY_EC`, `EVP_PKEY_X25519` та `EVP_PKEY_X448`) уніфіковано через єдиний контекст операцій виведення секрету `EVP_PKEY_derive`.

### Таблиця функцій життєвого циклу обміну

| Функція | Призначення та сигнатура | Повертане значення та обробка помилок |
|---|---|---|
| `EVP_PKEY_CTX_new_id` | `EVP_PKEY_CTX* EVP_PKEY_CTX_new_id(int id, ENGINE *e)` — Створює контекст для вказаного числового ідентифікатора алгоритму (`EVP_PKEY_X25519`, `EVP_PKEY_X448`, `EVP_PKEY_DH`). | Повертає вказівник на виділений контекст або `NULL` у разі нестачі оперативної пам'яті. |
| `EVP_PKEY_keygen_init` | `int EVP_PKEY_keygen_init(EVP_PKEY_CTX *ctx)` — Ініціалізує контекст для виконання операції генерації пари ключів. Перевіряє стан провайдера. | Повертає `1` при успіху, `0` або від'ємне значення при некоректному стані контексту. |
| `EVP_PKEY_keygen` | `int EVP_PKEY_keygen(EVP_PKEY_CTX *ctx, EVP_PKEY **ppkey)` — Генерує нову пару ключів за допомогою системного джерела ентропії провайдера. | Повертає `1` при успішній генерації; `0` або `<0` при відмові системного генератора випадкових чисел. |
| `EVP_PKEY_CTX_new` | `EVP_PKEY_CTX* EVP_PKEY_CTX_new(EVP_PKEY *pkey, ENGINE *e)` — Створює контекст операцій для вже наявного закритого ключа суб'єкта. | Повертає новий контекст операцій або `NULL`. |
| `EVP_PKEY_derive_init` | `int EVP_PKEY_derive_init(EVP_PKEY_CTX *ctx)` — Переводить внутрішній скінченний автомат контексту в режим виведення спільного секрету (`EVP_PKEY_OP_DERIVE`). | Повертає `1` при успіху; `0` якщо алгоритм ключа не підтримує узгодження. |
| `EVP_PKEY_derive_set_peer` | `int EVP_PKEY_derive_set_peer(EVP_PKEY_CTX *ctx, EVP_PKEY *peerkey)` — Прив'язує відкритий ключ віддаленої сторони до контексту узгодження. | Повертає `1` при успішній валідації параметрів; `0` якщо типи кривих чи модулі сторін не збігаються. |
| `EVP_PKEY_derive` | `int EVP_PKEY_derive(EVP_PKEY_CTX *ctx, unsigned char *key, size_t *keylen)` — Обчислює спільний симетричний секрет `K`. | Повертає `1` при успіху, `0` при математичній або апаратній помилці. |

### Поведінка параметрів та виділення пам'яті

Функція `EVP_PKEY_derive` реалізує ідіому двокрокового виклику для гарантії безпеки буферів:

1. **Запит розміру буфера:** Якщо параметр `key` передається як `NULL`, функція не виконує криптографічних обчислень, а лише записує необхідний розмір буфера у байтах за адресою `keylen`. Для X25519 це завжди 32 байти, для X448 — 56 байтів, а для класичного MODP DH розмір дорівнює довжині модуля `p` (256 байтів для 2048-бітної групи, 384 байти для 3072-бітної групи).
2. **Обчислення секрету:** Під час повторного виклику з виділеним буфером `key` вказівник `keylen` повинен містити фактичну місткість виділеного буфера. Функція обчислює скалярний добуток або модульний степінь, записує байти секрету в буфер і оновлює `keylen` фактичною кількістю записаних байтів.

:::tabs
```c
size_t secret_len = 0;
/* Крок 1: запит необхідного розміру буфера */
if (EVP_PKEY_derive(ctx, NULL, &secret_len) <= 0) {
    /* Обробка помилки: неможливо визначити довжину секрету */
}

uint8_t *secret = (uint8_t*)malloc(secret_len);
/* Крок 2: фактичне обчислення спільного секрету */
if (!secret || EVP_PKEY_derive(ctx, secret, &secret_len) <= 0) {
    /* Обробка помилки: збій під час скалярного множення */
}
```
```cpp
size_t secret_len = 0;
// Крок 1: запит необхідного розміру буфера
if (EVP_PKEY_derive(ctx, nullptr, &secret_len) <= 0) {
    // Обробка помилки: неможливо визначити довжину секрету
}

std::vector<uint8_t> secret(secret_len);
// Крок 2: фактичне обчислення спільного секрету
if (EVP_PKEY_derive(ctx, secret.data(), &secret_len) <= 0) {
    // Обробка помилки: збій під час скалярного множення
}
```
:::

### Налаштування параметрів класичного MODP DH через OSSL_PARAM

Під час використання класичного обміну за модулем у скінченних полях (FFDHE) OpenSSL 3.0 вимагає конфігурації параметрів групи (модуля `p` та генератора `g`) або вказівки стандартизованої іменованої групи (наприклад, RFC 7919 `ffdhe2048` чи `ffdhe3072`):

:::tabs
```c
EVP_PKEY_CTX *pctx = EVP_PKEY_CTX_new_from_name(NULL, "DH", NULL);
EVP_PKEY_paramgen_init(pctx);

char group_name[] = "ffdhe3072";
OSSL_PARAM params[2];
params[0] = OSSL_PARAM_construct_utf8_string("group", group_name, sizeof(group_name));
params[1] = OSSL_PARAM_construct_end();

EVP_PKEY_CTX_set_params(pctx, params);
EVP_PKEY *dh_params = NULL;
EVP_PKEY_paramgen(pctx, &dh_params);
EVP_PKEY_CTX_free(pctx);
```
```cpp
auto pctx = std::unique_ptr<EVP_PKEY_CTX, decltype(&EVP_PKEY_CTX_free)>(
    EVP_PKEY_CTX_new_from_name(nullptr, "DH", nullptr), &EVP_PKEY_CTX_free);
EVP_PKEY_paramgen_init(pctx.get());

char group_name[] = "ffdhe3072";
std::array<OSSL_PARAM, 2> params = {
    OSSL_PARAM_construct_utf8_string("group", group_name, sizeof(group_name)),
    OSSL_PARAM_construct_end()
};

EVP_PKEY_CTX_set_params(pctx.get(), params.data());
EVP_PKEY *raw_params = nullptr;
EVP_PKEY_paramgen(pctx.get(), &raw_params);
auto dh_params = std::unique_ptr<EVP_PKEY, decltype(&EVP_PKEY_free)>(raw_params, &EVP_PKEY_free);
```
:::

### Валідація віддаленого ключа піра

Під час виклику `EVP_PKEY_derive_set_peer(ctx, peerkey)` бібліотека OpenSSL автоматично виконує внутрішню верифікацію коректності відкритого ключа віддаленої сторони:

* Перевіряє, що обидва об'єкти `EVP_PKEY` належать до однакового сімейства алгоритмів (наприклад, обидва є ключами `EVP_PKEY_X25519` або `EVP_PKEY_EC`).
* Для еліптичних кривих NIST (P-256, P-384) перевіряє, що точка лежить на кривій (`y² ≡ x³ + ax + b mod p`), не є точкою на нескінченності та має правильний порядок підгрупи.
* Для класичного DH перевіряє спільність параметрів генератора `g` та простого модуля `p`.

Якщо валідація зазнає невдачі, виклик негайно повертає `0`, а код детальної помилки поміщається у чергу помилок поточного потоку, яку можна вилучити за допомогою `ERR_get_error()`.

### Багатопотоковість та керування життєвим циклом об'єктів

Об'єкти `EVP_PKEY` мають внутрішній атомарний лічильник посилань (`references`) і можуть безпечно читатися одночасно кількома робочими потоками (наприклад, довгостроковий відкритий ключ сервера). Натомість контекст операцій `EVP_PKEY_CTX` зберігає внутрішній змінний стан операції та буфери провайдера і **не є потокобезпечним**: кожен потік повинен створювати власний екземпляр `EVP_PKEY_CTX` для кожної окремої операції виведення секрету.

### FIPS 140-3 та самотестування алгоритмів (Known Answer Tests)

Під час роботи у регульованих корпоративних та банківських середовищах (стандарт FIPS 140-3) OpenSSL вимагає явного завантаження FIPS-провайдера:

:::tabs
```c
OSSL_PROVIDER *fips_prov = OSSL_PROVIDER_load(NULL, "fips");
OSSL_PROVIDER *base_prov = OSSL_PROVIDER_load(NULL, "base");
if (!fips_prov) {
    /* Обробка помилки: неможливо ініціалізувати сертифікований криптомодуль */
}
```
```cpp
auto fips_prov = std::unique_ptr<OSSL_PROVIDER, decltype(&OSSL_PROVIDER_unload)>(
    OSSL_PROVIDER_load(nullptr, "fips"), &OSSL_PROVIDER_unload);
auto base_prov = std::unique_ptr<OSSL_PROVIDER, decltype(&OSSL_PROVIDER_unload)>(
    OSSL_PROVIDER_load(nullptr, "base"), &OSSL_PROVIDER_unload);
if (!fips_prov) {
    // Обробка помилки: неможливо ініціалізувати сертифікований криптомодуль
}
```
:::

У режимі FIPS бібліотека автоматично виконує обов'язкові тести з відомою відповіддю (англ. *Known Answer Tests*, KAT) для операцій піднесення до степеня та скалярного множення під час завантаження модуля, а також блокує використання груп FFDHE розміром менше ніж 2048 бітів та небезпечних кривих.

### Діагностика та вилучення детальних кодів помилок

Усі функції сімейства `EVP_PKEY` та `EVP_KDF` сигналізують про помилку поверненням `0` або від'ємного значення. Для отримання вичерпної причини збою потік виконання вилучає помилки зі стека OpenSSL:

:::tabs
```c
unsigned long err_code = ERR_get_error();
char err_buf[256];
ERR_error_string_n(err_code, err_buf, sizeof(err_buf));
/* Формат виводу: error:[код]:[бібліотека]:[функція]:[причина] */
```
```cpp
const unsigned long err_code = ERR_get_error();
std::array<char, 256> err_buf{};
ERR_error_string_n(err_code, err_buf.data(), err_buf.size());
const std::string_view err_msg{err_buf.data()};
```
:::

Типові причини помилок під час узгодження ключів:
* `DH_R_NO_PRIVATE_VALUE` — спроба виклику derive на об'єкті ключа, що містить лише відкриті координати.
* `EC_R_PEER_KEY_ERROR` — відкрита точка віддаленої сторони не належить до зазначеної кривої або є нейтральним елементом.
* `PROV_R_INVALID_KEY_LENGTH` — запитаний розмір вихідного матеріалу в HKDF перевищує ліміт стандарту `255 · HashLen`.

## 2. Бібліотека libsodium: Інтерфейс crypto_kx

Бібліотека `libsodium` реалізує підхід «криптографії без небезпечних налаштувань» (англ. *misuse-resistant cryptography*). Замість надання доступу до сирих математичних операцій скалярного множення, інтерфейс `crypto_kx` інкапсулює повний цикл безпечного узгодження сесійних ключів на базі X25519 та геш-функції BLAKE2b.

### Контракт функцій libsodium crypto_kx

| Функція | Призначення та сигнатура | Гарантії безпеки |
|---|---|---|
| `crypto_kx_keypair` | `int crypto_kx_keypair(unsigned char pk[32], unsigned char sk[32])` | Генерує пару ключів X25519 з апаратного CSPRNG і автоматично накладає бітову маску (clamping) на закритий ключ `sk`. Повертає `0`. |
| `crypto_kx_client_session_keys` | `int crypto_kx_client_session_keys(unsigned char rx[32], unsigned char tx[32], const unsigned char client_pk[32], const unsigned char client_sk[32], const unsigned char server_pk[32])` | Обчислює два незалежні симетричні сесійні ключі на боці клієнта: `rx` для дешифрування вхідного трафіку, `tx` для шифрування вихідного. Повертає `0` при успіху, `-1` якщо `server_pk` неприпустимий. |
| `crypto_kx_server_session_keys` | `int crypto_kx_server_session_keys(unsigned char rx[32], unsigned char tx[32], const unsigned char server_pk[32], const unsigned char server_sk[32], const unsigned char client_pk[32])` | Обчислює два симетричні ключі на боці сервера. Гарантує дзеркальну відповідність: `server_rx == client_tx` та `server_tx == client_rx`. Повертає `0` або `-1`. |

### Захист від атак віддзеркалення та нульових точок

Інтерфейс `crypto_kx` проектувався з урахуванням типових вразливостей практичних мережевих протоколів:

1. **Розподіл напрямків передачі (Directional Key Separation):** У наївних реалізаціях обчислюється єдиний спільний ключ `K`, який використовується для шифрування обох напрямків зв'язку. Це дозволяє зловмиснику перехопити зашифрований пакет від клієнта і відправити його назад клієнту як відповідь сервера (атака віддзеркалення, англ. *Reflection Attack*). Функції `crypto_kx` хешують обчислений скалярний добуток `q = X25519(sk, pk)` разом із відкритими ключами обох сторін у фіксованому порядку:
   ```
   Клієнт: rx = BLAKE2b(q || client_pk || server_pk),  tx = BLAKE2b(q || server_pk || client_pk)
   Сервер: rx = BLAKE2b(q || server_pk || client_pk),  tx = BLAKE2b(q || client_pk || server_pk)
   ```
   У результаті ключ передачі клієнта завжди ідентичний ключу прийому сервера, але суворо відрізняється від ключа прийому клієнта.
2. **Виявлення слабких та нульових точок:** Якщо віддалена сторона надсилає публічний ключ, що складається з одних нулів або представляє точку малого порядку на кривій, обчислення скалярного добутку дає нейтральний елемент поля. Функції `crypto_kx_client_session_keys` та `crypto_kx_server_session_keys` виявляють цей стан за константний час і негайно повертають статус помилки `-1`, не генеруючи передбачуваних ключів.
3. **Гарантоване зачищення буферів:** Бібліотека вимагає очищення секретних буферів через виклик `sodium_memzero(sk, sizeof(sk))`, що запобігає оптимізації компілятора (Dead Store Elimination), яка зазвичай видаляє стандартні виклики `memset`.

### Порівняльний аналіз вибору API для нових розробок

Вибір між OpenSSL `EVP_PKEY` та libsodium `crypto_kx` визначається вимогами до взаємосумісності системи:
* Якщо система інтегрується в корпоративну інфраструктуру X.509, підтримує стандарти TLS 1.3 чи вимагає сертифікації FIPS 140-3, безальтернативним вибором є **OpenSSL 3.0**, який дозволяє налаштовувати криптографічні провайдери та апаратні модулі безпеки (HSM / PKCS#11).
* Якщо проект реалізує власний протокол прикладного рівня, наскрізне шифрування для мобільних додатків або IoT-пристроїв, рекомендується **libsodium**: її API унеможливлює передачу некоректних параметрів, має у кілька разів менший обсяг бінарного коду та виконує всі операції строго за константний час.
