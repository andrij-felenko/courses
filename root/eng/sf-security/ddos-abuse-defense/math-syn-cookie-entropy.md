# 🧮 Математичний аналіз ентропії та ймовірності колізій SYN Cookies

Безстанковий механізм TCP SYN Cookies вирішує проблему збереження стану сервера шляхом пакування метаданих з'єднання в 32-бітне поле початкового порядкового номера відповіді `SYN-ACK`. Проте жорстке обмеження довжини поля у 32 біти накладає математичні компроміси між точністю часового вікна, кількістю допустимих розмірів MSS та криптографічною стійкістю до сліпого підбору підтвердження.

У цій вставці наведено строгий ймовірнісний розрахунок ентропійного бюджету, оцінку ймовірності колізій, часових затримок та стійкості протоколу до високошвидкісного підбору підроблених ACK-пакетів.

---

## 1. Розподіл ентропії 32-бітного простору ISN

Загальний простір станів початкового порядкового номера в заголовку протоколу TCP обмежений розміром поля:

```
|ISN| = 2³² = 4 294 967 296 станів
```

У класичній схемі Бернштейна-Шенка (RFC 4987) бітовий бюджет розподіляється між трьома незалежними змінними:
- `t`: часовий індекс (3 біти, 8 дискретних станів).
- `m`: індекс розміру максимального сегмента MSS (3 біти, 8 дискретних станів).
- `s`: усічений криптографічний MAC (26 бітів, `2²⁶ = 67 108 864` стани).

```
32 біти = 3 біти (час) + 3 біти (MSS) + 26 бітів (MAC)
```

### Часовий простір та періодичність переповнення

Нехай часовий крок дискретизації становить `Δt = 64` секунди. Повний період лічильника часу `T_cycle` дорівнює:

```
T_cycle
= 2³ · Δt               [формула повного циклу для 3 бітів]
= 8 · 64                [підстановка констант: 8 вікон по 64 с]
= 512 с                 [період повного оберту лічильника]
```

Оскільки сервер приймає пакети лише з поточним часовим індексом `t_curr` або попереднім індексом `(t_curr - 1) mod 8`, максимальний допустимий час життя куки становить:

```
T_valid_max
= 2 · Δt                [допуск поточного та попереднього вікна]
= 2 · 64
= 128 с                 [максимальний часовий лаг легітимного клієнта]
```

Якщо мережева затримка або повторні спроби передачі легітимного клієнта перевищують 128 секунд, його підтвердження буде відхилено як застаріле. Проте для 99.99% з'єднань в інтернеті типовий час кругової затримки (RTT) становить від 10 до 300 мілісекунд, тому часове вікно у 64–128 секунд забезпечує величезний запас надійності.

## 2. Ймовірність успішного сліпого підбору ACK-пакета

Розглянемо атакувальника, який не має можливості прослуховувати трафік відповіді `SYN-ACK` від сервера (через спуфінг вихідної IP-адреси), але намагається навмання надіслати третій пакет `ACK`, щоб змусити операційну систему створити фіктивний сокет і виділити ресурси оперативної пам'яті.

Для фіксованого кортежу адрес та портів зловмисник намагається вгадати правильне 32-бітне число підтвердження:

```
ack_seq = Cookie + 1
```

Ймовірність `P_single` вгадати коректний 26-бітний криптографічний MAC у межах одного надісланого пакета становить:

```
P_single
= 1 / 2²⁶               [рівномірний розподіл криптографічного MAC]
= 1 / 67 108 864
≈ 1.490116 · 10⁻⁸       [ймовірність успіху одиночної спроби]
```

Якщо атакувальник генерує потік із `N` підроблених ACK-пакетів за одиницю часу з різними псевдовипадковими номерами підтвердження, ймовірність `P_success(N)` того, що **хоча б один** пакет буде визнано валідним, описується формулою біноміального розподілу:

```
P_success(N)
= 1 - (1 - P_single)ᴺ   [ймовірність протилежної події: жодного успіху]
≈ 1 - e^(-N / 2²⁶)      [наближення Пуассона для великих N та малого P]
```

### Математичний розрахунок для високошвидкісного флуду 10 Mpps

Нехай потужність атаки становить `N = 10 000 000` (10 мільйонів пакетів на секунду, що еквівалентно приблизно 6.4 Гбіт/с чистих 64-байтних Ethernet-кадрів).

Обчислимо математичне сподівання кількості успішно створених фіктивних сокетів за секунду `λ`:

```
λ
= N · P_single          [математичне сподівання біноміального розподілу]
= 10 000 000 / 67 108 864
≈ 0.14901 сокетів/с     [менше одного фантомного сокета за 6 секунд]
```

Обчислимо ймовірність успіху за 1 секунду атаки:

```
P_success(10⁷)
= 1 - e^(-10 000 000 / 67 108 864)  [підстановка інтенсивності флуду]
= 1 - e^(-0.14901)                  [обчислення показника експоненти]
= 1 - 0.86156
≈ 0.13844                           [13.84% ймовірності успіху за 1 с]
```

### Динаміка вичерпання пам'яті ядра під час атаки

Нехай кожен створений фіктивний сокет займає в пам'яті ядра близько 1 Кбайт (`struct tcp_sock`) і залишається в стані `ESTABLISHED` до спрацьовування таймауту відсутності активності `T_idle = 60` секунд.

Середня кількість одночасно відкритих фіктивних сокетів у системі `E[Sockets]` за законом Літтла становить:

```
E[Sockets]
= λ · T_idle            [закон Літтла для стаціонарної системи]
= 0.14901 · 60
≈ 8.94 сокетів          [менше дев'яти сокетів у будь-який момент часу]
```

Сумарний витік оперативної пам'яті дорівнює:

```
Memory_leak
= E[Sockets] · 1024 байт
≈ 8.94 · 1 Кбайт
≈ 9.15 Кбайт            [абсолютно нехтовне навантаження на систему]
```

**Висновки для безпеки:** Навіть за умов колосального флуду в 10 мільйонів пакетів на секунду сервер створює лише 1 фантомний сокет кожні 6.7 секунди. При типовому таймауті неактивного сокета в 60 секунд у системі одночасно перебуватиме не більше 9–10 фантомних з'єднань, що становить абсолютно нехтовне навантаження на оперативну пам'ять сучасного сервера.

## 3. Межа колізій парадоксу днів народження для внутрішніх потоків

Оскільки довжина MAC становить `k = 26` бітів, розглянемо ситуацію, коли сервер одночасно обробляє множину легітимних клієнтських з'єднань `M` у межах одного часового вікна `Δt`.

Згідно з класичним парадоксом днів народження, кількість з'єднань `M_collision`, необхідна для виникнення хоча б однієї випадкової колізії гешу з ймовірністю `P ≈ 0.5`, оцінюється асимптотичною формулою:

```
M_collision
≈ √(2 · 2²⁶ · ln(2))    [асимптотична формула парадоксу днів народження]
= √(2²⁷ · 0.69315)      [спрощення під коренем]
= √(134 217 728 · 0.69315)
= √93 032 870
≈ 9 645 з'єднань        [поріг появи першої випадкової колізії гешу]
```

### Чому внутрішня колізія не порушує безпеку та ізоляцію даних

На перший погляд, число в 9645 одночасних з'єднань здається невеликим для великого навантаженого кластера. Проте збіг 26-бітного значення `s_1 = s_2` для двох різних клієнтів не несе жодної загрози безпеці:

1. **Повна валідація 4-tuple:** Коли від клієнта А надходить завершальний пакет `ACK`, операційна система витягує адреси й порти джерела та призначення з IP/TCP-заголовків саме цього пакета.
2. **Детермінований перерахунок:** Сервер обчислює еталонний підпис `s_expected = Hash(src_A, dst_A, port_A, port_A, client_isn_A, t, secret)`.
3. Навіть якщо клієнт Б на іншому континенті випадково має такий самий молодший залишок 26 бітів, його пакет не пройде перевірку на сокеті клієнта А, оскільки їхні IP-адреси різняться.

Таким чином, колізія кук між різними клієнтами жодним чином не дозволяє одному користувачеві перехопити чи підмінити TCP-сесію іншого.

## 4. Порівняння конфігурацій розподілу бітів ISN

У процесі стандартизації та впровадження ядрами ОС розглядалися альтернативні варіанти розбиття 32-бітного поля:

| Конфігурація | Час `t` | MSS `m` | MAC `s` | Стійкість `P_single` | Оцінка практичності |
|---|---|---|---|---|---|
| **24-бітний MAC** | 4 біти (16 вікон по 64 с = 1024 с) | 4 біти (16 значень MSS) | 24 біти (`2²⁴ = 16.7M`) | `5.96 · 10⁻⁸` | Зручно для повільних мереж, але слабша стійкість до флуду. |
| **26-бітний MAC (Стандарт Linux)** | 3 біти (8 вікон по 64 с = 512 с) | 3 біти (8 значень MSS) | 26 бітів (`2²⁶ = 67.1M`) | `1.49 · 10⁻⁸` | Оптимальний баланс між стійкістю та діапазоном MSS. |
| **28-бітний MAC** | 2 біти (4 вікна по 64 с = 256 с) | 2 біти (4 значення MSS) | 28 бітів (`2²⁸ = 268.4M`) | `3.72 · 10⁻⁹` | Максимальна стійкість, але груба шкала MSS (втрата пропускної здатності). |

Математичний аналіз доводить, що 26-бітна схема ядра Linux забезпечує математично оптимальний компроміс: вона знижує ймовірність сліпого підбору до мікроскопічних величин, зберігаючи точний вибір розміру пакета Ethernet та стійкість до затримок у глобальних мережах.
