# 📋 Специфікація інтерфейсів конвеєра очищення трафіку та правил BGP Flowspec

Ефективний захист від розподілених атак на відмову в обслуговуванні базується на узгодженій роботі кількох рівнів інфраструктури: магістральних маршрутизаторів прикордонного шлюзу (BGP), високошвидкісних драйверних фільтрів ядра Linux (XDP eBPF), систем збору телеметрії (IPFIX) та прикладних вебфаєрволів (L7 WAF).

У цьому довіднику наведено точні структури даних, формати правил, коди повернення та протокольні контракти взаємодії між компонентами конвеєра фільтрації.

---

## 1. Специфікація правил BGP Flow Specification (RFC 8955 / RFC 5575)

BGP Flowspec дозволяє маршрутизаторам та контролерам безпеки динамічно поширювати детальні правила фільтрації трафіку через адресне сімейство AFI=1 (IPv4) або AFI=2 (IPv6) та SAFI=133 (Dissemination of Flow Specification Rules). Кожне правило передається у полі NLRI (англ. *Network Layer Reachability Information*) оновлення BGP `UPDATE` і містить набір послідовних байтових кортежів `[Type, Length, Value]`.

### Компоненти відповідності (Flowspec NLRI Match Types)

Правило фільтрації складається з послідовності байтових дескрипторів, що описують критерії відбору пакетів:

| Тип (Type) | Назва компонента | Опис та формат кодування | Приклад значення |
|---|---|---|---|
| `1` | **Destination Prefix** | Префікс призначення (довжина в бітах + байти адреси) | `198.51.100.0/24` |
| `2` | **Source Prefix** | Префікс джерела (довжина в бітах + байти адреси) | `203.0.113.0/24` |
| `3` | **IP Protocol** | Номер протоколу L3/L4 (оператор порівняння + 1 байт) | `== 17` (UDP), `== 6` (TCP) |
| `4` | **Port** | Будь-який порт (джерело або призначення) | `== 53` (DNS), `== 123` (NTP) |
| `5` | **Destination Port** | Порт призначення L4 | `== 80`, `== 443`, `== 389` |
| `6` | **Source Port** | Порт джерела L4 (ампліфікаційні атаки) | `== 11211` (Memcached), `== 1900` (SSDP) |
| `7` | **ICMP Type** | Тип повідомлення ICMP | `== 8` (Echo Request) |
| `8` | **ICMP Code** | Код повідомлення ICMP | `== 0` |
| `9` | **TCP Flags** | Маска бітів прапорців TCP (SYN, ACK, RST, FIN, PSH, URG) | `& SYN != 0 && ACK == 0` |
| `10` | **Packet Length** | Фізична довжина IP-пакета в байтах (включно із заголовком) | `> 1400`, `<= 64` |
| `11` | **DSCP** | Поле DiffServ Code Point у заголовку IP | `== 46` (Expedited Forwarding) |
| `12` | **Fragment** | Стан фрагментації (IsF, HasF, FirstF, LastF, NotF) | `IsF` (Is Fragment), `FirstF` |

### Правила валідації та безпеки BGP Flowspec (RFC 8955 §6)

Для запобігання атакам типу BGP Hijacking, коли зловмисний BGP-пір намагається заблокувати чужий трафік через фальшиві Flowspec-правила, маршрутизатор зобов'язаний виконувати сувору перевірку валідності перед застосуванням правила:

1. **Перевірка префікса призначення:** Автономна система (AS), що надсилає Flowspec-правило для префікса призначення `198.51.100.0/24`, повинна бути тією самою AS, яка є автором найкращого одноадресного маршруту (Unicast BGP Route) до цього префікса в таблиці маршрутизації (RIB).
2. **Перевірка відсутності циклів в AS_PATH:** У ланцюжку автономних систем не повинно бути пропущених транзитних вузлів.
3. Якщо правило порушує ці умови, маршрутизатор позначає NLRI статусом `Invalid` та відкидає правило без застосування до таблиць комутації (FIB).

### Розширені спільноти дій (BGP Flowspec Extended Communities)

Коли пакет відповідає критеріям NLRI, маршрутизатор виконує одну або кілька дій, закодованих у 8-байтних атрибутах розширених спільнот BGP:

| Розширена спільнота | Hex-код типу | Значення аргументу | Семантика дії |
|---|---|---|---|
| **Traffic-Rate** | `0x8006` | 4 байти float (байт/с) | Обмеження швидкості (Rate-limit) у форматі IEEE 754 single precision. Значення `0.0` (`0x00000000`) означає повне скидання (Drop). |
| **Traffic-Action** | `0x8007` | Бітова маска (2 байти) | Біт 0: `Terminal Action` (припинити перевірку подальших правил); Біт 1: `Sample` (надсилати дзеркальну копію пакета в аналізатор NetFlow). |
| **Redirect to VRF** | `0x8008` | 6 байтів Route Target | Перенаправлення потоку у віртуальний контекст маршрутизації (VRF) очищення для глибокого аналізу. |
| **Traffic-Marking** | `0x8009` | 1 байт значення DSCP | Перезапис бітів DSCP/TOS у заголовку IP для пріоритезації або апаратного полісингу на комутаторах ядра. |

Особливістю спільноти `Traffic-Rate` є використання 32-бітного числа з рухомою комою: значення `1250000.0` встановлює жорсткий ліміт пропускної здатності в 10 Мбіт/с (1.25 Мбайт/с). Маршрутизатор реалізує це обмеження через апаратний двошвидкісний триколірний маркер (Two-Rate Three-Color Marker, srTCM за RFC 2697) у кремнії комутаційної матриці без участі центрального процесора.

## 2. Коди повернення та контракт ядра XDP (eXpress Data Path)

На рівні мережевого драйвера ядра Linux програма eBPF, завантажена на хук XDP, обробляє сирий покажчик `struct xdp_md` і повертає одне зі стандартизованих цілочисельних значень.

:::tabs
```c
/* Заголовковий файл ядра: <uapi/linux/bpf.h> */
enum xdp_action {
    XDP_ABORTED = 0,  /* Помилка в коді eBPF: відкинути пакет і зафіксувати tracepoint */
    XDP_DROP    = 1,  /* Миттєве скидання пакета в кремнії/драйвері (нуль виділень пам'яті) */
    XDP_PASS    = 2,  /* Передати пакет вгору у стандартний мережевий стек ядра (sk_buff) */
    XDP_TX      = 3,  /* Відправити модифікований пакет назад у той самий інтерфейс (SYN-ACK) */
    XDP_REDIRECT= 4   /* Перенаправити пакет на іншу NIC, AF_XDP сокет або CPU-воркер */
};
```
```cpp
#include <cstdint>

enum class XdpAction : std::uint32_t {
    Aborted  = 0,  // Критична помилка в логіці: скинути та записати подію
    Drop     = 1,  // Відкинути на рівні драйвера без виділення sk_buff
    Pass     = 2,  // Пропустити до мережевого стека Linux
    Tx       = 3,  // Відправити модифікований кадр назад у той самий порт
    Redirect = 4   // Перенаправити на інший інтерфейс або в сокет AF_XDP
};
```
:::

### Контекстні поля структури `struct xdp_md`

Верифікатор eBPF жорстко контролює доступ до пам'яті кадру. Програма отримує структуру дескриптора з такими полями:

| Поле структури | Тип | Призначення |
|---|---|---|
| `data` | `__u32` | Віртуальна адреса початку сирих байтів Ethernet-кадру в оперативній пам'яті. |
| `data_end` | `__u32` | Віртуальна адреса кінця отриманого кадру (використовується eBPF-верифікатором для перевірки меж). |
| `data_meta` | `__u32` | Вказівник на додаткові метадані, збережені перед заголовком кадру. |
| `ingress_ifindex`| `__u32` | Системний числовий індекс вхідного мережевого інтерфейсу. |
| `rx_queue_index` | `__u32` | Номер апаратної черги прийому (RX Queue) контролера NIC. |

### Життєвий цикл та керування програмою XDP

Завантаження, підключення та вивантаження eBPF-програми фільтрації здійснюється засобами системної утиліти `iproute2` через протокол Netlink:

1. **Компіляція:** Байткод генерується компілятором Clang: `clang -O2 -target bpf -c xdp_scrubber.c -o xdp_scrubber.o`.
2. **Підключення до інтерфейсу:** `ip link set dev eth0 xdpgeneric obj xdp_scrubber.o sec xdp` (для тестування) або `ip link set dev eth0 xdpdrv obj xdp_scrubber.o sec xdp` (для максимальної продуктивності в нативному режимі драйвера).
3. **Моніторинг лічильників:** Програма веде облік скинутих і пропущених пакетів через спільну мапу `BPF_MAP_TYPE_PERCPU_ARRAY`, що унеможливлює блокування пам'яті (Lock Contention) між ядрами багатопроцесорного сервера.
4. **Вивантаження:** `ip link set dev eth0 xdp off`.

## 3. Шаблон експорту телеметрії аномалій IPFIX / NetFlow v9

Для автоматичного виявлення атак сервери та комутатори експортують агреговані потоки через протокол IPFIX (RFC 7011) або NetFlow v9 (RFC 3954). Протокол базується на концепції шаблонів (*Templates*), які маршрутизатор надсилає аналізатору перед передачею сирих записів трафіку.

### Стандартний набір полів запису (Template FlowSet) для детекції DDoS

```
┌───────────────────────────────────────────────┬───────────────────────────┐
│ Назва поля (Information Element)              │ Field ID │ Довжина (Byte) │
├───────────────────────────────────────────────┼──────────┼────────────────┤
│ IN_BYTES (Кількість переданих байтів)         │    1     │       8        │
│ IN_PKTS  (Кількість переданих пакетів)        │    2     │       8        │
│ PROTOCOL (Протокол IPv4/IPv6: TCP/UDP/ICMP)   │    4     │       1        │
│ IP_TOS   (Тип сервісу / DSCP)                 │    5     │       1        │
│ TCP_FLAGS (Бітова маска прапорців TCP)        │    6     │       1        │
│ L4_SRC_PORT (Порт джерела)                    │    7     │       2        │
│ IPV4_SRC_ADDR (IP-адреса джерела)             │    8     │       4        │
│ L4_DST_PORT (Порт призначення)                │    11    │       2        │
│ IPV4_DST_ADDR (IP-адреса призначення)         │    12    │       4        │
│ FLOW_START_MILLISECONDS (Час початку потоку)  │   152    │       8        │
│ FLOW_END_MILLISECONDS   (Час кінця потоку)    │   153    │       8        │
└───────────────────────────────────────────────┴──────────┴────────────────┘
```

### Алгоритмічні порогові тригери систем виявлення

Аналізатор безпеки обробляє потік записів IPFIX у реальному часі та ініціює захисні заходи при спрацьовуванні таких евристичних правил:

- **Сплеск пакетної щільності (Packet Rate Spike):** Перевищення порогу `500 000` пакетів/с на одну цільову IP-адресу протягом 3 послідовних інтервалів вимірювання (по 1 с).
- **Аномалія прапорців TCP (SYN/ACK Ratio):** Співвідношення кількості пакетів `SYN` до `ACK` перевищує `10:1` (ознака активної атаки SYN Flood).
- **Зниження ентропії портів джерела:** Концентрація понад 80% вхідного UDP-трафіку з фіксованих портів ампліфікації (`53`, `123`, `1900`, `11211`) з розміром пакетів понад 1000 байтів.

При виявленні аномалії оркестратор безпеки автоматично формує правило BGP Flowspec або команду оновлення BPF-мап на периферійних вузлах XDP.

## 4. Контракт HTTP-челенджів рівня L7 WAF

Під час детекції прикладного флуду (L7 Flood / Credential Stuffing) зворотний проксі-сервер (WAF) перехоплює підозрілий HTTP-запит і повертає відповідь зі статусом `429 Too Many Requests` або `403 Forbidden`, що містить криптографічну загадку доказу виконання роботи (Proof of Work, PoW).

### Заголовки відповіді сервера (WAF Challenge Headers)

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 5
X-Challenge-Algorithm: SHA256-PoW
X-Challenge-Target: 000000ffffffffffffffffffffffffffffffffffffffffffffffffffffffffff
X-Challenge-Nonce: 4f8a9b2c3d1e5f7a90b1c2d3e4f5a6b7
X-Challenge-Expires: 1718912400
```

### Формат JSON-корисного навантаження для клієнтських додатків

```json
{
  "status": "challenge_required",
  "error_code": "DDoS_L7_VERIFICATION",
  "challenge": {
    "algorithm": "sha256",
    "prefix": "4f8a9b2c3d1e5f7a90b1c2d3e4f5a6b7",
    "difficulty_bits": 20,
    "max_target": "0x00000fffffffffffffffffffffffffffffffffffffffffffffffffffffffffff",
    "expires_at": 1718912400
  },
  "submission_endpoint": "/api/v1/security/challenge/verify"
}
```

### Алгоритм виконання та верифікації клієнтського доказу

1. **Клієнтський пошук:** Клієнтська програма (у браузері через WebAssembly або в мобільному додатку) ітерує 64-бітне ціле число `solution` від `0` до `2⁶⁴ - 1` та обчислює криптографічний хеш: `H = SHA256(prefix || solution)`. Пошук зупиняється, коли числове значення `H` стає меншим за `max_target` (вимагає в середньому `2²⁰ ≈ 1 048 576` операцій хешування, що займає близько 100–300 мс на сучасному процесорі).
2. **Повторне надсилання запиту:** Клієнт надсилає розв'язок у заголовку оригінального запиту:
   `X-Challenge-Solution: 0x00000000003f4a1b`.
3. **Миттєва перевірка WAF:** Сервер виконує рівно **одну операцію обчислення SHA256** над наданим розв'язком. Якщо результат задовольняє умову і мітка часу в Nonce не застаріла, сервер встановлює підписаний сесійний токен (наприклад, криптографічний cookie з HMAC-підписом) на 30 хвилин і пропускає запити клієнта без повторних челенджів.
