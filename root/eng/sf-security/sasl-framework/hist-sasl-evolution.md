# 📜 Еволюція SASL: від хаосу прикладних паролів до універсального криптокаркаса

Цей історичний екскурс розкриває інженерні передумови виникнення універсального каркаса автентифікації SASL, хроніку боротьби з комбінаторним вибухом протокольних реалізацій, причини відмови від застарілих схем на кшталт DIGEST-MD5 та формування сучасної екосистеми безпеки розподілених систем.

## Ера протокольного хаосу: проблема комбінаторного вибуху

На початку 1990-х років розвиток Інтернету супроводжувався бурхливою появою нових прикладних протоколів. Кожна мережева служба розроблялася як ізольований моноліт: поштовий протокол POP3 (RFC 1939) запроваджував текстові команди `USER` та `PASS`, протокол доступу до поштових скриньок IMAP (RFC 1730) використовував команду `LOGIN`, протокол передавання файлів FTP (RFC 959) мав власний діалог ідентифікації, а протокол каталогів LDAP (RFC 1777) вимагав операції `bind` з відкритим паролем (*Simple Bind*).

Усі ці механізми об'єднувала спільна вразливість: облікові дані передавалися мережею у відкритому вигляді без будь-якого шифрування. Будь-який проміжний маршрутизатор або зловмисник із пасивним мережевим аналізатором перехоплював паролі користувачів. 

Коли у криптографічній спільноті з'явилися стійкі схеми автентифікації — протокол Kerberos v4 та v5 у Массачусетському технологічному інституті (MIT), одноразові паролі S/KEY (RFC 1760), схеми виклику-відповіді на базі хеш-функцій, — інженери зіткнулися з проблемою **комбінаторного вибуху `M × N`**.

Якщо в організації використовувалося `M` прикладних протоколів (SMTP, POP3, IMAP, LDAP, ACAP, NNTP, Telnet) і виникала потреба підтримати `N` криптографічних технологій автентифікації (Kerberos, S/KEY, GSS-API, SRP, відкритий пароль у захищеному тунелі), розробники мусили:

1. Переписувати специфікацію RFC для кожного з `M` протоколів окремо, додаючи нові граматичні конструкції.
2. Вносити зміни до кодової бази кожного клієнта і кожного сервера (наприклад, модифікувати Sendmail, Postfix, UW-IMAP, Cyrus IMAPd, OpenLDAP).
3. Дублювати складну логіку обробки криптографічних викликів, генерації випадкових чисел та форматування бінарних структур усередині кожного прикладного демона.

```
Без SASL (M × N зв'язків):
IMAP  ────┬─── Kerberos v5
SMTP  ────┼─── S/KEY
POP3  ────┼─── OTP / SRP
LDAP  ────┴─── Plaintext / Unix Shadow

З SASL (M + N адаптерів):
IMAP  ───┐                ┌─── Kerberos v5
SMTP  ───┼─── [ SASL ] ───┼─── SCRAM-SHA-256
POP3  ───┤    RFC 4422    ├─── GSSAPI / OAuth
LDAP  ───┘                └─── PLAIN / TLS
```

Поява будь-якого нового методу автентифікації вимагала перегляду стандартів усіх інтернет-служб. Якщо в алгоритмі виявляли вразливість, виправлення потрібно було впроваджувати в десятки незалежних програмних проєктів.

## Проєкт Cyrus та народження RFC 2222

Універсальне вирішення проблеми запропонував Джон Маєрс (John G. Myers) під час роботи над проєктом поштової системи **Cyrus** в Університеті Карнегі — Меллона (Carnegie Mellon University, CMU) у співпраці з консорціумом IETF.

Маєрс сформулював ідею чистого архітектурного розділення: прикладний протокол повинен відповідати лише за транспортування непрозорих блоків даних (*Opaque Octet Streams*), тоді як уся криптографічна логіка, перевірка доказів та узгодження ключів мають бути інкапсульовані в незалежні під'єднувані модулі автентифікації.

У жовтні 1997 року IETF опублікував стандарт **RFC 2222: Simple Authentication and Security Layer (SASL)**. Документ закріпив три базові інженерні принципи:

1. **Єдина команда запуску автентифікації:** Прикладний протокол визначає лише одну команду (наприклад, `AUTHENTICATE` в IMAP або `AUTH` в SMTP), яка приймає назву механізму (рядок від 1 до 20 символів, зареєстрований в IANA).
2. **Абстрактний цикл «виклик-відповідь»:** Протокол передає серверні виклики (*Challenges*) та клієнтські відповіді (*Responses*) як послідовності двійкових байтів, закодованих у безпечний текстовий формат Base64. Прикладний протокол нічого не знає про внутрішній зміст цих байтів.
3. **Рівень безпеки (Security Layer):** Після успішної автентифікації механізм має право передати прикладному рівню узгоджений симетричний ключ для захисту цілісності (*Integrity*) та конфіденційності (*Confidentiality*) всього подальшого потоку даних сесії.

Для широкого впровадження стандарту в Університеті Карнегі — Меллона було створено еталонну відкриту бібліотеку **Cyrus SASL** (`libsasl2`). Завдяки Cyrus SASL серверні демони (Sendmail, Postfix, Dovecot, OpenLDAP) та клієнтські поштові програми (Mutt, Thunderbird) отримали змогу підтримувати будь-які сучасні методи автентифікації через підключення динамічних бібліотек (`.so` / `.dll`) без зміни власного сирцевого коду.

## Переосмислення: RFC 4422 та усунення архітектурних вад

Майже десятиліття промислової експлуатації RFC 2222 виявило низку неточностей та прихованих проблем сумісності:

- **Неоднозначність передачі початкової відповіді (Initial Client Response):** Деякі механізми (наприклад, PLAIN або Kerberos AP-REQ) можуть передати перший доказ одразу разом із назвою механізму, заощаджуючи один повний мережевий оберт (*Round-Trip Time*, RTT). У RFC 2222 не було чітко специфіковано, чи зобов'язаний сервер приймати такі дані в тому самому пакеті, що призводило до розриву з'єднань між клієнтами та серверами різних вендорів.
- **Розділення ідентифікатора автентифікації та авторизації:** Виникла потреба чітко розрізняти користувача, чиї облікові дані перевіряються (*Authentication Identity*, `authcid`), та суб'єкта, чиї права доступу запитуються (*Authorization Identity*, `authzid`). Це критично для систем делегування та сервісних облікових записів (наприклад, адміністратор або шлюз входить за власним сертифікатом, але діє від імені поштової скриньки `user@example.com`).
- **Міжнародні рядки та кодування:** Відсутність єдиних правил нормалізації імен користувачів і паролів Unicode призводила до того, що символи в різних формах нормалізації (NFC проти NFD) відхилялися серверами.

У червні 2006 року Олексій Мельников (Alexey Melnikov, Isode) та Курт Зейленга (Kurt Zeilenga, OpenLDAP Foundation) завершили масштабну переробку стандарту, випустивши **RFC 4422: Simple Authentication and Security Layer (SASL)**, який офіційно скасував і замінив застарілий RFC 2222. 

Новий стандарт ввів алгоритм нормалізації рядків **SASLprep** (RFC 4013 на базі Stringprep), формалізував семантику передачі початкових даних клієнта, запровадив правила скасування діалогу автентифікації за ініціативою клієнта (через відправку символу `*`) та уточнив взаємодію із захисними рівнями транспорту.

## Злет і падіння DIGEST-MD5 (RFC 2831 → RFC 6331)

Найяскравішим уроком в історії SASL стала доля механізму **DIGEST-MD5** (RFC 2831, 1999 рік).

DIGEST-MD5 проєктувався як «золотий стандарт» автентифікації без передачі відкритого пароля. Він адаптував HTTP Digest Authentication (RFC 2617) для довільних прикладних протоколів, пропонуючи захист від атак повтору через випадкові виклики (`nonce`, `cnonce`), взаємну автентифікацію сервера перед клієнтом та вбудоване шифрування сесії (RC4, DES, 3DES). IETF навіть надав DIGEST-MD5 статус *Mandatory-to-Implement* (обов'язковий для реалізації) у низці протокольних стандартів (зокрема в XMPP RFC 3920 та LDAP RFC 4513).

Однак на практиці DIGEST-MD5 виявився надмірно складним і крихким:

1. **Надмірна складність ABNF-граматики:** Повідомлення являли собою списки пар `ключ=значення`, де значення могли бути в лапках або без, підтримували кілька альтернативних наборів шифрів та кодувань. Різні реалізації трактували пробіли й коми по-різному, що викликало постійні збої сумісності між клієнтами на Java, C та Python.
2. **Криптографічне старіння примітивів:** Механізм був жорстко прив'язаний до геш-функції MD5. Коли в середині 2000-х років було опубліковано практичні атаки на знаходження колізій MD5 (роботи професора Сяоюнь Ван), протокол не мав можливості просто замінити геш на SHA-256 через відсутність криптографічної гнучкості (*Hash Agility*).
3. **Уразливість узгодження шифрування:** Процедура узгодження якості захисту (`qop=auth-conf`) не накривала криптографічним підписом весь початковий діалог. Активний зловмисник посередині (*Man-in-the-Middle*, MITM) міг підмінити список підтримуваних шифрів і змусити сторони відкотитися до слабкого 40-бітного шифрування або відкритого тексту.

У липні 2011 року IETF випустив офіційний документ **RFC 6331: Moving DIGEST-MD5 to Historic**, який позбавив протокол статусу стандарту і перевів його в категорію застарілих історичних артефактів. 

## Сучасна епоха: GS2, SCRAM та хмарні архітектури

Провал DIGEST-MD5 змусив співтовариство розробити нове покоління механізмів SASL, побудованих на принципах мінімалізму, криптографічної строгості та гнучкості:

- **Каркас GS2 (RFC 5801):** Створено універсальний міст між стандартами SASL та Generic Security Services API (GSS-API). GS2 стандартизував легковаговий заголовок для узгодження прив'язки до каналу (*Channel Binding*) та передачі ідентифікатора авторизації.
- **Родина SCRAM (RFC 5802, RFC 7677):** Механізм Salted Challenge Response Authentication Mechanism (SCRAM-SHA-1, SCRAM-SHA-256) став повноцінною і безпечною заміною DIGEST-MD5. SCRAM базується на стійкій функції PBKDF2 та алгоритмі HMAC, забезпечує взаємну перевірку сторін і унеможливлює атаку за словником на базі вкрадених хешів із сервера.
- **OAUTHBEARER (RFC 7628):** З переходом корпоративних систем на мікросервіси та хмарні шлюзи автентифікацію за довготривалими паролями витіснили короткоживучі криптографічні токени JSON Web Token (JWT). Механізм OAUTHBEARER стандартизував передачу токенів доступу OAuth 2.0 через SASL.

Сьогодні SASL вийшов далеко за межі традиційних поштових протоколів. Каркас RFC 4422 став стандартом автентифікації за замовчуванням у розподіленому брокері повідомлень **Apache Kafka**, реляційній системі керування базами даних **PostgreSQL** (починаючи з версії 10), документній СКБД **MongoDB**, промисловому протоколі черг **AMQP 1.0** та корпоративних федераціях **Kerberos / Active Directory**. Завдяки чіткому архітектурному фундаменту протоколи XXI століття підключають найсучасніші криптографічні механізми без жодної зміни власних транспортних рівнів.
