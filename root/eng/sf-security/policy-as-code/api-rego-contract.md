# 📋 Інтерфейсний контракт OPA та синтаксична поверхня Rego

Open Policy Agent (OPA) взаємодіє із зовнішніми точками застосування політик (PEP), системами управління конфігураціями та сховищами даних через стандартизований набір програмних інтерфейсів. Цей контракт складається з трьох ключових частин: протоколу HTTP REST API для передачі запитів на оцінку, просторів імен глобальних ієрархічних документів `input` і `data`, а також специфікації криптографічно підписаних архівів (*bundles*) для автоматичного оновлення правил у пам'яті рушія.

Нижче наведено формальну специфікацію інтерфейсів, форматів запитів і відповідей, системних кодів помилок та стандартних детерміністичних функцій рушія Rego.

---

### 1. Специфікація REST API та протоколу обчислення

Точка ухвалення рішень OPA працює як мережевий демон і за замовчуванням очікує вхідні HTTP-з'єднання на TCP-порті `8181`. Всі операції використовують серіалізацію у форматі JSON і підтримують потокове стиснення `gzip`.

| HTTP-метод та Шлях | Призначення | Тіло запиту | Тіло відповіді |
| :--- | :--- | :--- | :--- |
| `POST /v1/data/{path}` | Оцінка конкретного правила або витяг віртуального документа за вказаним шляхом | JSON об'єкт `{"input": {...}}` | `{"result": <value>}` |
| `POST /v1/compile` | Запит часткового обчислення (*Partial Evaluation*) з визначенням невідомих змінних | JSON об'єкт з полями `query`, `input`, `unknowns` | `{"result": {"queries": [...]}}` |
| `GET /v1/data/{path}` | Читання статичного базового документа або зліпка гілки `data` з пам'яті | Порожнє | `{"result": <document>}` |
| `PUT /v1/data/{path}` | Запис, створення або повне перезаписування гілки базового документа `data` | Довільний валідний JSON | Порожній об'єкт `{}` |
| `PATCH /v1/data/{path}`| Атомарне оновлення гілки документа за специфікацією JSON Patch (RFC 6902) | Масив операцій JSON Patch | Порожній об'єкт `{}` |
| `DELETE /v1/data/{path}`| Повне видалення зазначеного шляху з пам'яті базових документів `data` | Порожнє | Порожній об'єкт `{}` |
| `PUT /v1/policies/{id}` | Динамічне завантаження та компіляція нового сирцевого модулю Rego | Текст політики у кодуванні UTF-8 | Порожній об'єкт `{}` |
| `GET /v1/policies/{id}` | Отримання вихідного тексту раніше завантаженого модулю за його ідентифікатором | Порожнє | `{"result": {"raw": "..."}}` |
| `GET /health` | Перевірка працездатності демона для балансувальників навантаження (*liveness/readiness*) | Порожнє | HTTP 200 OK |

#### Обробка системних статусів та кодів помилок

Мережевий інтерфейс OPA суворо типізує коди відповідей HTTP для спрощення діагностики в точці застосування (PEP):

1. **`200 OK`**: Запит успішно обчислено. Якщо правило або запитаний шлях не визначені у політиці (стан *undefined*), тіло відповіді містить порожній об'єкт `{}` або поле `result` взагалі відсутнє, що точка PEP повинна трактувати як відмову за правилом заборони за замовчуванням.
2. **`400 Bad Request`**: Синтаксично некоректний JSON у тілі запиту, передача невідомого параметра URL або помилка синтаксичного аналізу файлу Rego під час виконання `PUT /v1/policies`. Відповідь містить поле `code: "invalid_parameter"` та детальний опис позиції помилки (рядок і стовпчик).
3. **`404 Not Found`**: Спроба видалити або отримати модуль політики за неіснуючим ідентифікатором `id`.
4. **`408 Request Timeout`**: Перевищення ліміту часу обчислення політики, встановленого параметром `timeout` (за замовчуванням запити обчислюються без таймауту, якщо він не обмежений клієнтом).
5. **`500 Internal Server Error`**: Критична помилка обчислення вбудованої функції (наприклад, некоректний тип аргументу у функції, що не підтримує неявне приведення, чи паніка рушія).

#### Керуючі параметри запиту оцінки (`POST /v1/data/{path}`)

| Параметр URL | Тип | Опис та семантика поведінки |
| :--- | :--- | :--- |
| `pretty` | `boolean` | Вмикає відступи, нові рядки та форматування вихідного JSON (`true`/`false`). |
| `provenance` | `boolean` | Додає до відповіді повну інформацію про збірку OPA, версію компілятора та Git-ревізію завантаженого бандла. |
| `metrics` | `boolean` | Повертає блок наносекундних таймерів для кожної фази: синтаксичний розбір входу, компіляція AST, обчислення запиту. |
| `explain` | `string` | Вмикає покрокове трасування обчислення правил. Допустимі значення: `notes` (лише явні виклики `trace()`), `fails` (точки відхилення умов), `full` (повне дерево обчислення). |
| `instrument` | `boolean` | Активує детальний підрахунок кількості викликів кожного виразу правил для профілювання вузьких місць. |

#### Приклад запиту та повної відповіді сервера

Запит до точки ухвалення рішень для перевірки доступу користувача до фінансового звіту:

```http
POST /v1/data/authz/allow?metrics=true&provenance=true HTTP/1.1
Host: 127.0.0.1:8181
Content-Type: application/json

{
  "input": {
    "user": "alice",
    "groups": ["engineering", "security"],
    "action": "read",
    "resource": "/api/v2/reports/q3"
  }
}
```

Відповідь OPA з метриками продуктивності та метаданими ревізії:

```json
{
  "decision_id": "c1f7a2b9-6d84-4e12-b91c-99e5a1b32d0f",
  "provenance": {
    "version": "0.68.0",
    "build_commit": "7b825dc",
    "bundles": {
      "authz-bundle": {
        "revision": "git:4b825dc642cb6eb9a060e54bf8d69288fbee4904"
      }
    }
  },
  "result": true,
  "metrics": {
    "timer_rego_input_parse_ns": 3800,
    "timer_rego_query_eval_ns": 24200,
    "timer_server_handler_ns": 48100
  }
}
```

### 2. Ієрархія та ізоляція просторів імен `input` і `data`

Модель пам'яті OPA представляє всі доступні об'єкти як єдине глобальне дерево ієрархічних документів. Це дерево строго розділене на два неперетинні простори імен:

1. **Динамічний документ `input`**:
   - Являє собою контекст поточного оцінюваного запиту (HTTP-заголовки, метод, шлях, маніфест пода Kubernetes, план Terraform).
   - Передається клієнтом точки застосування (PEP) безпосередньо в тілі POST-запиту.
   - Є суворо незмінним (*read-only*) протягом усього часу виконання запиту.
   - Знищується з оперативної пам'яті одразу після формування відповіді клієнту, що виключає витік даних між послідовними запитами різних користувачів.

2. **Глобальний документ `data`**:
   - Зберігає довгоживучий стан системи: завантажені модулі правил Rego, статичні конфігурації, списки облікових записів та таблиці ролей.
   - Складається з двох типів документів: **базових** (*base documents*, завантажених як чистий JSON через API чи з файлу `data.json`) та **віртуальних** (*virtual documents*, що обчислюються на льоту правилами Rego).
   - Якщо шлях `data.authz.roles` визначений у базовому JSON-файлі, спроба оголосити правило Rego з пакетом `package authz.roles` спричинить помилку конфлікту просторів імен під час компіляції політики.

```rego
package authz.policy

import future.keywords.if

# Доступ до динамічного контексту запиту
is_valid_method if input.method == "GET"

# Доступ до статичного базового документа data
is_admin_user if input.user in data.acl.administrators
```

### 3. Специфікація вбудованих функцій (Built-in Functions)

Мова Rego надає багату стандартну бібліотеку детерміністичних функцій. Усі функції є чистими: при однакових аргументах вони завжди повертають ідентичний результат і не змінюють стан середовища.

#### Маніпуляція колекціями та перевірка типів

| Функція | Повна сигнатура | Поведінка та крайові випадки |
| :--- | :--- | :--- |
| `count` | `count(collection: any) : number` | Повертає кількість елементів у масиві, множині чи об'єкті. Для порожньої колекції повертає `0`. Для `null` генерує помилку типу. |
| `array.slice` | `array.slice(arr: array, start: number, stop: number) : array` | Повертає підмасив від індексу `start` (включно) до `stop` (виключно). Якщо індекси виходять за межі, автоматично обмежує діапазон розміром масиву. |
| `object.get` | `object.get(obj: object, key: string, default_val: any) : any` | Безпечно витягує значення за ключем. Якщо ключ відсутній, повертає `default_val` замість генерації невизначеного стану (*undefined*). |
| `json.is_valid` | `json.is_valid(raw: string) : boolean` | Повертає `true`, якщо текстовий рядок містить коректний синтаксис JSON; інакше `false`. |

#### Криптографія, сертифікати та перевірка токенів

| Функція | Повна сигнатура | Поведінка та крайові випадки |
| :--- | :--- | :--- |
| `io.jwt.decode` | `io.jwt.decode(string) : [header, payload, signature]` | Швидкий синтаксичний розбір токена JWT без перевірки криптографічного підпису. Зручно для попередньої маршрутизації за ідентифікатором ключа `kid`. |
| `io.jwt.verify_rs256` | `io.jwt.verify_rs256(string, cert: string) : boolean` | Повна валідація підпису RSA-SHA256 токена за відкритим ключем або сертифікатом у форматі PEM. |
| `crypto.sha256` | `crypto.sha256(data: string) : string` | Обчислює криптографічний геш SHA-256 та повертає результат у вигляді шістнадцяткового рядка довжиною 64 символи. |
| `crypto.x509.parse_certificates` | `crypto.x509.parse_certificates(pem: string) : array` | Розбирає ланцюжок сертифікатів X.509 і повертає масив структурованих об'єктів з полями `Subject`, `Issuer`, `SAN`, `NotAfter`. |

#### Мережеві перевірки та робота з часом

| Функція | Повна сигнатура | Поведінка та крайові випадки |
| :--- | :--- | :--- |
| `net.cidr_contains` | `net.cidr_contains(cidr: string, ip: string) : boolean` | Перевіряє належність адреси IPv4 або IPv6 вказаній підмережі CIDR (наприклад, `"10.0.0.0/8"` та `"10.2.3.4"` дає `true`). |
| `time.now_ns` | `time.now_ns() : number` | Повертає поточну мітку часу Unix у наносекундах. Фіксується один раз на старті оцінки запиту, що гарантує детермінізм всередині транзакції. |
| `time.parse_rfc3339_ns` | `time.parse_rfc3339_ns(ts: string) : number` | Перетворює строкову дату формату ISO 8601 / RFC 3339 (наприклад, `"2026-08-20T18:00:00Z"`) у наносекунди для числового порівняння. |
| `http.send` | `http.send(request: object) : object` | Виконує блокуючий синхронний HTTP-виклик до стороннього API під час оцінки. Вимагає явного дозволу в конфігурації безпеки OPA. |

### 4. Специфікація архітектури бандлів (Bundle Protocol)

Для централізованого управління політиками на сотнях вузлів OPA підтримує протокол бандлів. Бандл являє собою архів у форматі `tar.gz`, що містить вихідні тексти правил, статичні дані та службовий файл маніфесту.

#### Фізична структура архіву `.tar.gz`

```
security-bundle-v1.2.0.tar.gz
├── .manifest
├── data.json
├── org/
│   └── metadata.json
└── policies/
    ├── rbac.rego
    ├── admission.rego
    └── network.rego
```

#### Специфікація файлу `.manifest`

Файл `.manifest` обов'язково розміщується у корені архіву і визначає межі відповідальності бандла:

```json
{
  "revision": "git:4b825dc642cb6eb9a060e54bf8d69288fbee4904",
  "roots": ["authz", "kubernetes/admission", "org/metadata"],
  "wasm": [
    {
      "entrypoint": "authz/allow",
      "path": "policy.wasm"
    }
  ],
  "metadata": {
    "author": "Cloud Security Architecture Team",
    "built_at": "2026-08-20T18:00:00Z",
    "environment": "production-eu-west"
  }
}
```

1. **Поле `roots`**: Масив рядків, що визначає кореневі шляхи простору `data`, якими управляє цей бандл. Якщо бандл оголошує корінь `["authz"]`, OPA атомарно очистить старий вміст `data.authz` і замінить його новими файлами з архіву, не торкаючись гілок `data.system` чи `data.network`.
2. **Поле `revision`**: Довільний рядок (наприклад, Git SHA-1 комміту), що однозначно ідентифікує стан вихідного коду політик. Цей ідентифікатор автоматично записується у всі логи рішень (*decision logs*), гарантуючи повну простежуваність аудиту.
3. **Криптографічний підпис `.signatures.json`**: Забезпечує перевірку цілісності та автентичності бандла. Перед розпакуванням архіву OPA перевіряє цифровий підпис файлів за відкритим ключем RSA/ECDSA, запобігаючи атакам типу «людина посередині» (*Man-in-the-Middle*).

### 5. Специфікація логу ухвалення рішень (Decision Log Schema)

Для виконання вимог відповідності стандартам безпеки (SOC 2, ISO 27001, PCI-DSS) OPA автоматично протоколює кожну операцію оцінки правил у форматі [аудит-логу](root:sf-security/audit-logging).

```json
{
  "decision_id": "c1f7a2b9-6d84-4e12-b91c-99e5a1b32d0f",
  "labels": {
    "app": "api-gateway",
    "cluster": "k8s-prod-fra-01",
    "environment": "production",
    "region": "eu-central-1"
  },
  "bundles": {
    "security-bundle": {
      "revision": "git:4b825dc642cb6eb9a060e54bf8d69288fbee4904"
    }
  },
  "path": "authz/allow",
  "input": {
    "method": "POST",
    "path": "/api/v1/payments/transfer",
    "user": "service-account-checkout",
    "amount": 45000
  },
  "result": false,
  "errored": false,
  "requested_by": "10.244.3.42:51280",
  "timestamp": "2026-08-20T18:02:30.124892Z",
  "metrics": {
    "timer_rego_query_eval_ns": 21400,
    "timer_server_handler_ns": 39800
  }
}
```

Логи рішень накопичуються у локальному буфері оперативної пам'яті та асинхронно відправляються пачками (*batches*) за протоколом HTTP POST на віддалений сервер збору подій безпеки (наприклад, SIEM або Elasticsearch). Якщо сервер збору логів тимчасово недоступний, OPA зберігає буфер у кільцевій черзі, запобігаючи уповільненню основного шляху обробки призначених для користувача запитів.
