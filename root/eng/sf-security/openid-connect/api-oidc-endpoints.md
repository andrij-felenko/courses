# 📋 Довідник специфікацій OpenID Connect Core: кінцеві точки, параметри та схеми

Цей довідник містить вичерпний опис мережевих інтерфейсів, параметрів запитів, схем корисного навантаження JSON/JWT, механізмів автентифікації клієнтів та стандартизованих кодів помилок згідно зі специфікаціями OpenID Connect Core 1.0, OpenID Connect Discovery 1.0, RFC 7517 (JWK), RFC 7591 (Dynamic Client Registration) та специфікаціями федеративного виходу.

## 1. Документ виявлення конфігурації провайдера (Discovery)

Будь-який сумісний з OIDC сервер ідентифікації публікує свій маніфест за фіксованим шляхом `/.well-known/openid-configuration` відносно базового URL емітента (`issuer`). Клієнти (Relying Parties) використовують цей документ для автоматичного налаштування адрес ендпоінтів, підтримуваних криптографічних алгоритмів та доступних областей доступу (scopes).

**HTTP-метод:** `GET`  
**Заголовки запиту:** `Accept: application/json`  
**Формат відповіді:** `application/json`

### Порядок обробки та валідації Discovery

Під час завантаження документа клієнт зобов'язаний перевірити такі інваріанти:
1. **Збіг емітента:** Значення поля `issuer` у JSON-відповіді має символ-у-символ збігатися з URL-адресою, за якою запитувався документ (без урахування суфікса `/.well-known/openid-configuration`). Будь-яка розбіжність у протоколі (`http` замість `https`), порту чи кінцевому слеші свідчить про спробу підміни конфігурації (MitM) або помилку налаштування і вимагає негайного припинення роботи.
2. **Обов'язкова підтримка HTTPS:** Усі кінцеві точки (`authorization_endpoint`, `token_endpoint`, `jwks_uri` тощо) зобов'язані використовувати транспортний протокол `https://` (за винятком тестових середовищ на `localhost`).
3. **Кешування документа:** Клієнти повинні кешувати документ Discovery відповідно до стандартних HTTP-заголовків керування кешем (`Cache-Control`, `max-age`, `ETag`), уникаючи надмірних запитів на кожен цикл автентифікації.

### Стандартні поля метаданих провайдера

| Поле | Тип | Обов'язкове | Опис |
| :--- | :--- | :---: | :--- |
| `issuer` | `string` (URI) | **Так** | Офіційний унікальний ідентифікатор емітента (повинен точно збігатися зі схемою HTTPS, хостом і шляхом без кінцевого слеша). |
| `authorization_endpoint` | `string` (URL) | **Так** | URL кінцевої точки авторизації, куди клієнт спрямовує браузер користувача для проходження автентифікації. |
| `token_endpoint` | `string` (URL) | **Так**\* | URL точки обміну коду на токени (обов'язковий для Authorization Code Flow та Hybrid Flow). |
| `userinfo_endpoint` | `string` (URL) | Ні | URL точки отримання даних профілю користувача за допомогою Access Token. |
| `jwks_uri` | `string` (URL) | **Так** | URL документа з набором відкритих ключів провайдера у форматі JWKS (RFC 7517). |
| `registration_endpoint` | `string` (URL) | Ні | URL кінцевої точки динамічної реєстрації клієнтів згідно з RFC 7591. |
| `scopes_supported` | `string[]` | **Так** | Список підтримуваних областей доступу. Зобов'язаний містити рядок `"openid"`. |
| `response_types_supported` | `string[]` | **Так** | Список підтримуваних значень `response_type`, наприклад `["code", "code id_token", "id_token", "token id_token"]`. |
| `response_modes_supported` | `string[]` | Ні | Способи повернення параметрів: `["query", "fragment", "form_post"]`. За замовчуванням `["query", "fragment"]`. |
| `grant_types_supported` | `string[]` | Ні | Підтримувані типи надання доступу: `["authorization_code", "implicit", "refresh_token"]`. |
| `id_token_signing_alg_values_supported` | `string[]` | **Так** | Список алгоритмів підпису ID-токена JWS. Сервер зобов'язаний підтримувати `RS256`. Приклади: `["RS256", "ES256", "EdDSA"]`. |
| `subject_types_supported` | `string[]` | **Так** | Типи ідентифікаторів суб'єкта: `["public"]`, `["pairwise"]` або обидва `["public", "pairwise"]`. |
| `token_endpoint_auth_methods_supported` | `string[]` | Ні | Методи автентифікації клієнта на точці `/token`: `["client_secret_basic", "client_secret_post", "private_key_jwt", "none"]`. |
| `claims_supported` | `string[]` | Ні | Перелік підтримуваних тверджень користувача: `["sub", "iss", "name", "email", "email_verified", "locale"]`. |
| `code_challenge_methods_supported` | `string[]` | Ні | Список методів захисту коду PKCE (RFC 7636). Рекомендовано: `["S256"]`. |
| `end_session_endpoint` | `string` (URL) | Ні | URL кінцевої точки завершення сесії згідно з RP-Initiated Logout. |
| `check_session_iframe` | `string` (URL) | Ні | URL спеціального iframe провайдера для фонової перевірки стану сесії користувача. |

## 2. Кінцева точка авторизації (Authorization Endpoint)

Взаємодія ініціюється перенаправленням браузера користувача на адресу `authorization_endpoint`. Провайдер відображає інтерфейс входу, запитує пароль або біометрію, перевіряє фактори автентифікації та збирає згоду на надання доступу до персональних даних.

**HTTP-метод:** `GET` (або `POST` у разі надсилання довгих параметрів)  
**Формат передачі:** Query-параметри в URL або `application/x-www-form-urlencoded` у тілі POST.

### Детальний опис параметрів запиту авторизації

1. **`scope`** (`string`, обов'язковий). Рядок областей доступу, розділених пробілами. Наявність значення `"openid"` є маркером того, що запит обробляється за протоколом OpenID Connect, а не чистим OAuth 2.0. Додаткові стандартизовані скоупи:
   * `"profile"` — доступ до базових полів імені, прізвища, нікнейма, аватара;
   * `"email"` — доступ до адреси електронної пошти та статусу верифікації;
   * `"address"` — доступ до поштової адреси користувача;
   * `"phone"` — доступ до телефонного номера;
   * `"offline_access"` — запит на видачу довгоживучого Refresh Token для фонової роботи бекенду.
2. **`response_type`** (`string`, обов'язковий). Визначає обраний профіль протоколу:
   * `"code"` — класичний та найбільш захищений Authorization Code Flow. Повертає одноразовий код авторизації;
   * `"id_token"` або `"id_token token"` — Implicit Flow (застарілий, заборонений у нових системах через вразливість витоку токенів у URL);
   * `"code id_token"` або `"code token id_token"` — Hybrid Flow, де ID-токен повертається одразу фронтенду, а код обмінюється бекендом.
3. **`client_id`** (`string`, обов'язковий). Унікальний ідентифікатор зареєстрованого клієнтського додатку.
4. **`redirect_uri`** (`string`, обов'язковий). URL повернення. Сервер провайдера зобов'язаний виконати строгу посимвольну звірку `redirect_uri` з білим списком адрес, збереженим під час реєстрації клієнта. Використання підстановочних знаків (wildcards) заборонено стандартом безпеки OAuth 2.0 Security Best Current Practice.
5. **`state`** (`string`, суворо рекомендований). Непрозоре випадкове значення з ентропією щонайменше 128 біт. Захищає клієнтську точку зворотного виклику від CSRF-атак.
6. **`nonce`** (`string`, обов'язковий для Implicit/Hybrid, суворо рекомендований для Code Flow). Випадковий рядок, що пов'язує сесію клієнта з випущеним ID-токеном і запобігає атакам повторного відтворення.
7. **`prompt`** (`string`, опційний). Визначає інтерактивність процесу:
   * `"none"` — тиха перевірка (Silent Authentication). Провайдер не показує жодного інтерфейсу. Якщо сесія неактивна або потрібна згода, сервер негайно повертає помилку `login_required` або `interaction_required`;
   * `"login"` — вимагає примусового повторного вводу облікових даних, навіть якщо в користувача вже є активна сесія;
   * `"consent"` — примусовий показ діалогу надання дозволів на читання даних;
   * `"select_account"` — показ вікна вибору облікового запису, якщо в системі залоговано кілька користувачів.
8. **`max_age`** (`integer`, опційний). Допустимий вік сесії в секундах. Якщо з моменту останньої автентифікації користувача пройшло більше ніж `max_age`, провайдер зобов'язаний заново запитати пароль/фактори.
9. **`ui_locales`** (`string`, опційний). Перелік мов інтерфейсу за спаданням пріоритету згідно з BCP 47 (наприклад, `"uk-UA uk en"`).
10. **`id_token_hint`** (`string`, опційний). Раніше випущений ID-токен як підказка особи користувача.
11. **`login_hint`** (`string`, опційний). Підказка логіна користувача (наприклад, поштова адреса для автозаповнення).
12. **`acr_values`** (`string`, опційний). Запит на певний контекст автентифікації (наприклад, вимога апаратного ключа FIDO2 або обов'язкової двофакторної перевірки).
13. **`code_challenge`** та **`code_challenge_method`** (`string`, обов'язкові для PKCE). Захисний відбиток verifier. Метод зобов'язаний бути `"S256"`.

### Успішна відповідь (Redirect)

Провайдер перенаправляє браузер на `redirect_uri` з параметрами:
```http
HTTP/1.1 302 Found
Location: https://my-app.com/auth/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz123_csrf
```

### Відповідь із помилкою

Якщо користувач відхилив запит або передано некоректні параметри:
```http
HTTP/1.1 302 Found
Location: https://my-app.com/auth/callback?error=access_denied&error_description=User+declined+consent&state=xyz123_csrf
```

## 3. Кінцева точка токенів (Token Endpoint)

Точка обміну коду або оновлення сесії обслуговує виключно прямі бек-канал запити між бекендом клієнта та сервером провайдера. Токени передаються в захищеному TLS-тунелі, що унеможливлює їх витік через історію браузера або проксі-сервери.

**HTTP-метод:** `POST`  
**Заголовки запиту:** `Content-Type: application/x-www-form-urlencoded`, `Accept: application/json`

### Методи автентифікації клієнта (Client Authentication)

Клієнт повинен підтвердити свою автентичність одним із чотирьох методів:

1. **`client_secret_basic` (За замовчуванням):** Клієнт передає `client_id` та `client_secret` у стандартному HTTP-заголовку `Authorization: Basic <base64(client_id:client_secret)>`.
2. **`client_secret_post`:** Клієнт передає параметри `client_id` та `client_secret` безпосередньо в тілі POST-запиту у форматі `application/x-www-form-urlencoded`.
3. **`private_key_jwt` (Найбільш захищений):** Клієнт не має спільного секрету з сервером. Замість цього клієнт генерує одноразовий підписаний власним закритим ключем JWT (Client Assertion згідно з RFC 7523) і передає його в параметрі `client_assertion`.
4. **`none`:** Використовується для публічних клієнтів (SPA, мобільні додатки), які не можуть безпечно зберігати секрет. Автентичність гарантується виключно механізмом PKCE.

### Параметри тіла запиту на отримання токенів

| Параметр | Тип | Обов'язковий | Опис |
| :--- | :--- | :---: | :--- |
| `grant_type` | `string` | **Так** | Тип надання. Значення `"authorization_code"` для обміну коду, або `"refresh_token"` для поновлення. |
| `code` | `string` | **Так**\* | Одноразовий код авторизації, отриманий з кінцевої точки `/authorize`. |
| `redirect_uri` | `string` (URL) | **Так**\* | Адреса `redirect_uri`, яка передавалася у початковому запиті `/authorize` (значення мають символ-у-символ збігатися). |
| `code_verifier` | `string` | **Так**\* | Початковий випадковий рядок verifier для перевірки PKCE. |
| `refresh_token` | `string` | **Так**\* | Токен оновлення (якщо `grant_type == "refresh_token"`). |
| `client_id` | `string` | **Так**\* | Ідентифікатор клієнта (якщо автентифікація виконується через тіло запиту). |
| `client_secret` | `string` | Ні | Секрет клієнта (для конфіденційних клієнтів при методі `client_secret_post`). |

### Схема успішної відповіді Token Endpoint

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjFhMmIzYyIs...",
  "scope": "openid profile email"
}
```

## 4. Структура та стандартні твердження ID-токена (Claims)

ID-токен є підписаним структурованим документом [JSON Web Token (JWT)](root:sf-web/jwt-tokens). Він складається з заголовка (Header), корисного навантаження (Payload) та цифрового підпису (Signature).

### Структура заголовка (Header)

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "k-2026-prod-01"
}
```

* `alg` (`string`): алгоритм цифрового підпису (наприклад, `RS256`, `ES256`, `EdDSA`). Значення `none` суворо заборонене.
* `kid` (`string`): ідентифікатор відкритого ключа в JWKS провайдера, яким виконано підпис.
* `typ` (`string`): тип медіа, за стандартом `"JWT"`.

### Обов'язкові та базові твердження (Payload Claims)

| Claim | Тип | Обов'язковий | Опис |
| :--- | :--- | :---: | :--- |
| `iss` | `string` (URI) | **Так** | Емітент токена. Зобов'язаний точно відповідати значенню `issuer` з документа Discovery. |
| `sub` | `string` | **Так** | Унікальний, локально незмінний ідентифікатор користувача у провайдера (Subject Identifier). Довжина до 255 символів ASCII. |
| `aud` | `string` або `string[]` | **Так** | Аудиторія токена. Зобов'язана містити `client_id` клієнта, який робив запит. |
| `exp` | `integer` (Unix Time) | **Так** | Час закінчення дії токена (секунди з 1970-01-01 UTC). Після настання цього часу токен недійсний. |
| `iat` | `integer` (Unix Time) | **Так** | Час створення токена провайдером. |
| `auth_time` | `integer` (Unix Time) | Ні\* | Час, коли користувач безпосередньо пройшов автентифікацію (увів пароль або підтвердив біометрію). Обов'язковий, якщо передавався параметр `max_age`. |
| `nonce` | `string` | Ні\* | Сіль запиту клієнта. Обов'язковий, якщо параметр `nonce` був присутній у запиті авторизації. |
| `azp` | `string` | Ні\* | Authorized Party — ідентифікатор клієнта, якому видано токен. Обов'язковий, якщо масив `aud` містить більше одного значення. |
| `at_hash` | `string` | Ні\* | Хеш токена доступу. Забезпечує криптографічну прив'язку `access_token` до `id_token`. Обов'язковий для Implicit/Hybrid flows, коли токен доступу повертається разом із ID-токеном. |
| `c_hash` | `string` | Ні\* | Хеш коду авторизації. Обчислюється як Base64URL лівої половини SHA-хешу від рядка `code`. Обов'язковий при поверненні `code` через Hybrid Flow. |
| `acr` | `string` | Ні | Authentication Context Class Reference — клас надійності автентифікації (наприклад, рівень гарантії або прапорець пройденої двофакторної перевірки). |
| `amr` | `string[]` | Ні | Authentication Methods References — масив ідентифікаторів використаних факторів (наприклад, `["pwd", "mfa", "fido"]`). |

### Математичний розрахунок хешів прив'язки (`at_hash` та `c_hash`)

Для запобігання підміні токена доступу або коду авторизації у відповідях провайдер обчислює односторонній відбиток:
1. Застосовується алгоритм хешування, що відповідає алгоритму підпису ID-токена: для `RS256` або `ES256` береться `SHA-256`, для `RS384` — `SHA-384`, для `RS512` — `SHA-512`.
2. Обчислюється хеш від ASCII-байтів вхідного рядка:
```
digest = SHA-256( access_token )
```
3. Відрізається рівно перша половина (ліві 128 біт для SHA-256).
4. Отримані 16 байтів кодуються у формат Base64URL без знаків заповнення `=`.

### Стандартні твердження профілю користувача (Profile Claims)

Ці поля повертаються в ID-токені або через запит до кінцевої точки `/userinfo` залежно від запитаних скоупів:

| Claim | Скоуп | Тип | Опис |

| `given_name` | `profile` | `string` | Ім'я (First name). |
| `family_name` | `profile` | `string` | Прізвище (Last name). |
| `middle_name` | `profile` | `string` | По батькові або друге ім'я. |
| `nickname` | `profile` | `string` | Псевдонім користувача. |
| `preferred_username` | `profile` | `string` | Бажаний нікнейм або логін. |
| `profile` | `profile` | `string` (URL) | Посилання на веб-сторінку профілю користувача. |
| `picture` | `profile` | `string` (URL) | Посилання на аватар або фотографію профілю. |
| `website` | `profile` | `string` (URL) | Посилання на веб-сайт користувача. |
| `email` | `email` | `string` | Адреса електронної пошти. |
| `email_verified` | `email` | `boolean` | Прапорець, який підтверджує, що пошта пройшла перевірку володіння. |
| `gender` | `profile` | `string` | Стать користувача. |
| `birthdate` | `profile` | `string` | Дата народження у форматі `YYYY-MM-DD` або `0000-MM-DD`. |
| `zoneinfo` | `profile` | `string` | Назва часового поясу за базою IANA (наприклад, `"Europe/Kyiv"`). |
| `locale` | `profile` | `string` | Мовна локаль користувача згідно з BCP47 (наприклад, `"uk-UA"`). |

| `phone_number_verified`| `phone` | `boolean` | Прапорець підтвердження номера телефону через SMS/OTP. |
| `address` | `address` | `object` | Поштова адреса (містить поля `formatted`, `street_address`, `locality`, `region`, `postal_code`, `country`). |
| `updated_at` | `profile` | `integer` | Час останнього оновлення профілю у форматі Unix Epoch. |

## 5. Кінцева точка інформації про користувача (UserInfo Endpoint)

Захищений ресурс OAuth 2.0, який повертає актуальні твердження про автентифікованого користувача. Використання UserInfo дозволяє зменшити розмір ID-токена, залишаючи в ньому лише критичні системні поля, а важкі профілі (адреси, аватари) завантажувати за потреби.

**HTTP-метод:** `GET` або `POST`  
**Заголовки запиту:** `Authorization: Bearer <access_token>`

### Приклад відповіді UserInfo

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "sub": "usr-88319204",
  "name": "Андрій Мельник",
  "given_name": "Андрій",
  "family_name": "Мельник",
  "email": "andriy.melnyk@example.com",
  "email_verified": true,
  "locale": "uk-UA",
  "picture": "https://img.example.com/avatars/usr-88319204.png"
}
```

Якщо `access_token` недійсний або прострочений, точка повертає статус HTTP 401 із заголовком:
```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="The Access Token expired"
```

## 6. Схема набору відкритих ключів (JWKS Schema)

Формат JWKS (RFC 7517) визначає структуру публікації відкритих ключів для перевірки підписів JWS.

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "k-2026-prod-01",
      "n": "u1W_9QjZ12kM... (модуль RSA у форматі Base64URL)",
      "e": "AQAB"
    },
    {
      "kty": "EC",
      "use": "sig",
      "alg": "ES256",
      "crv": "P-256",
      "kid": "k-2026-ec-02",
      "x": "f83OJ3D2xF... (координата X еліптичної кривої Base64URL)",
      "y": "x_da7W8h8r... (координата Y еліптичної кривої Base64URL)"
    }
  ]
}
```

### Властивості елемента ключа (JWK)

* `kty` (Key Type): тип сімейства ключів (`"RSA"`, `"EC"`, `"OKP"`).
* `use` (Public Key Use): цільове призначення ключа (`"sig"` для цифрового підпису, `"enc"` для шифрування).
* `kid` (Key ID): унікальний маркер версії ключа для швидкого пошуку в масиві.
* `alg` (Algorithm): алгоритм, для якого призначений ключ (`"RS256"`, `"ES256"`).
* `n`, `e`: компоненти відкритого ключа RSA (модуль і публічна експонента).
* `crv`, `x`, `y`: компоненти відкритого ключа еліптичної кривої (назва кривої та афінні координати).

## 7. Стандартизовані коди помилок OpenID Connect

### Помилки авторизації (Authorization Endpoint Errors)

Передаються як параметр `error` у редиректі на `redirect_uri` клієнта:

| Код помилки | Опис згідно зі специфікацією OIDC Core |
| :--- | :--- |
| `invalid_request` | У запиті відсутній обов'язковий параметр, повторюється параметр або передано непідтримувані опції. |
| `unauthorized_client` | Клієнту заборонено використовувати запитаний `response_type` або даний метод авторизації. |
| `access_denied` | Користувач або адміністратор явно відхилив запит на автентифікацію або надання прав. |
| `unsupported_response_type` | Сервер авторизації не підтримує вказаний тип відповіді (наприклад, клієнт запросив `"id_token"`, а провайдер підтримує лише `"code"`). |
| `invalid_scope` | Запитаний скоуп невідомий або заборонений політикою безпеки для цього клієнта. |
| `server_error` | Внутрішня помилка на стороні сервера ідентифікації. |
| `temporarily_unavailable` | Сервер перевантажений або перебуває на технічному обслуговуванні. |
| `interaction_required` | Клієнт надіслав `prompt=none`, але запит вимагає взаємодії з користувачем (наприклад, показ діалогу згоди чи форми логіну). |
| `login_required` | Клієнт надіслав `prompt=none`, але у користувача немає активної сесії автентифікації. |
| `account_selection_required` | Клієнт надіслав `prompt=none`, але користувач має кілька облікових записів і сервер не може автоматично обрати потрібний. |
| `consent_required` | Клієнт надіслав `prompt=none`, але користувач ще не надав згоду на запитані скоупи. |

### Помилки обміну токенів (Token Endpoint Errors)

Повертаються як HTTP 400 Bad Request із тілом `application/json`:

| Код помилки | Опис причини |
| :--- | :--- |
| `invalid_request` | Відсутній обов'язковий параметр `grant_type`, `code` або `redirect_uri`. |
| `invalid_client` | Автентифікація клієнта провалилася (невірний `client_secret`, недійсний сертифікат або непідтримуваний спосіб автентифікації). |
| `invalid_grant` | Переданий авторизаційний код недійсний, прострочений, уже був використаний раніше, або передано невірний `code_verifier` PKCE. |
| `unauthorized_client` | Зареєстрований клієнт не має права використовувати вказаний `grant_type`. |
| `unsupported_grant_type` | Сервер не підтримує вказаний тип надання доступу. |
| `invalid_scope` | Запитаний скоуп при використанні Refresh Token перевищує початково наданий користувачем. |

## 8. Кінцеві точки федеративного виходу (Logout Specifications)

OpenID Connect визначає три окремі взаємодоповнюючі специфікації для завершення сесій користувача у федеративному середовищі.

### 8.1. RP-Initiated Logout 1.0 (`end_session_endpoint`)

Клієнт ініціює вихід, перенаправляючи браузер користувача на кінцеву точку `end_session_endpoint` провайдера.

**HTTP-метод:** `GET` або `POST`  
**Параметри запиту:**

| Параметр | Тип | Опис |
| :--- | :--- | :--- |
| `id_token_hint` | `string` (JWT) | Раніше виданий ID-токен користувача. Служить підтвердженням особи, чию сесію завершують. |
| `post_logout_redirect_uri` | `string` (URL) | Адреса клієнтського сайту, куди провайдер повинен повернути браузер після успішного виходу. Зобов'язана бути попередньо зареєстрована в конфігурації клієнта. |
| `state` | `string` | Непрозорий токен клієнта, який провайдер повертає на `post_logout_redirect_uri` без змін. |
| `client_id` | `string` | Ідентифікатор клієнта (використовується як альтернатива `id_token_hint` у деяких провайдерах). |

### 8.2. Front-Channel Logout 1.0

Провайдер завантажує сторінку виходу, яка містить приховані HTML-елементи `<iframe>`, спрямовані на зареєстровані адреси `frontchannel_logout_uri` всіх додатків, у які заходив користувач:
```http
GET https://rp-app.com/frontchannel-logout?iss=https://auth.example.com&sid=sess-88192 HTTP/1.1
```
Клієнт у контексті браузера очищає сесійні cookies для відповідного `sid` (Session ID).

### 8.3. Back-Channel Logout 1.0

Провайдер надсилає прямий серверний HTTP POST-запит на `backchannel_logout_uri` кожного зареєстрованого клієнта:

**HTTP-метод:** `POST`  
**Тіло запиту:** `application/x-www-form-urlencoded` з єдиним параметром `logout_token`.

`logout_token` є підписаним JWT, що містить такі твердження:
* `iss`: URL емітента провайдера;
* `aud`: ідентифікатор клієнта `client_id`;
* `iat`: час генерації;
* `jti`: унікальний ідентифікатор токена виходу;
* `events`: об'єкт `{"http://schemas.openid.net/event/backchannel-logout": {}}`;
* `sub` або `sid`: ідентифікатор користувача або конкретної сесії;
* **Заборонено:** твердження `nonce` не може бути присутнім.

## 9. Кінцеві точки відклику та інтроспекції токенів

### 9.1. Кінцева точка відклику токенів (Token Revocation, RFC 7009)

Дозволяє клієнту явно анулювати раніше отриманий `access_token` або `refresh_token` (наприклад, коли користувач натискає «Відкликати доступ» в налаштуваннях).

**HTTP-метод:** `POST`  
**Заголовки:** `Content-Type: application/x-www-form-urlencoded`, `Authorization: Basic ...`  
**Тіло запиту:**
* `token` (`string`, обов'язковий): рядок токена;
* `token_type_hint` (`string`, опційний): підказка типу (`"access_token"` або `"refresh_token"`).

У разі успіху сервер завжди повертає HTTP 200 OK з порожнім тілом (навіть якщо токен уже був недійсним, що запобігає витоку інформації про існування токенів).

### 9.2. Кінцева точка інтроспекції токенів (Token Introspection, RFC 7662)

Використовується захищеними серверами ресурсів (Resource Server / API Gateway) для перевірки дійсності непрозорих (opaque) токенів доступу та отримання пов'язаних із ними метаданих без необхідності локального збереження сесій.

**HTTP-метод:** `POST`  
**Заголовки:** `Content-Type: application/x-www-form-urlencoded`, `Authorization: Basic ...`  
**Тіло запиту:** `token=<access_token>&token_type_hint=access_token`  

#### Стандартні поля відповіді інтроспекції

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `active` | `boolean` | **Обов'язкове.** `true`, якщо токен дійсний, не прострочений і не відкликаний. Якщо `false`, інші поля опускаються. |
| `scope` | `string` | Перелік наданих дозволів, розділених пробілами (наприклад, `"openid profile email"`). |
| `client_id` | `string` | Ідентифікатор клієнта, якому видано токен. |
| `username` | `string` | Логін або облікове ім'я суб'єкта, що надав авторизацію. |
| `token_type` | `string` | Тип токена (наприклад, `"Bearer"`). |
| `exp` | `integer` | Час закінчення дії токена (Unix Epoch). |
| `iat` | `integer` | Час створення токена. |
| `nbf` | `integer` | Час, до настання якого токен не є дійсним (Not Before). |
| `sub` | `string` | Ідентифікатор суб'єкта (користувача). |
| `aud` | `string` / `string[]` | Цільові аудиторії або сервіси, для яких призначено токен. |
| `iss` | `string` | URL емітента провайдера авторизації. |
| `jti` | `string` | Унікальний ідентифікатор токена (JWT ID). |

**Приклад відповіді (HTTP 200):**

```json
{
  "active": true,
  "scope": "openid profile email",
  "client_id": "my-saas-client-id",
  "username": "andriy.melnyk@example.com",
  "token_type": "Bearer",
  "exp": 1735736400,
  "iat": 1735732800,
  "sub": "usr-88319204",
  "iss": "https://auth.example.com"
}
```

## 10. Керівництво з діагностики типових помилок інтеграції

1. **Помилка `redirect_uri_mismatch`:**
   * *Причина:* Адреса `redirect_uri`, передана у запиті, не збігається символ-у-символ з адресою в кабінеті провайдера.
   * *Вирішення:* Перевірте наявність завершального слеша (`/`), збіг протоколу (`http` vs `https`), номер порту та регістр символів.
2. **Помилка `invalid_grant` при обміні коду:**
   * *Причина:* Авторизаційний код уже був використаний (коди одноразові), минув час його життя (зазвичай 30–60 секунд), або передано невірний `code_verifier` PKCE.
   * *Вирішення:* Переконайтеся, що обмін коду не дублюється повторними запитами React StrictMode на фронтенді, та перевірте правильність розрахунку хешу `code_challenge`.
3. **Помилка верифікації підпису ID-токена:**
   * *Причина:* Провайдер провів ротацію ключів підпису, а клієнт використовує застарілий кеш JWKS.
   * *Вирішення:* Реалізуйте автоматичне оновлення кешу JWKS на вимогу при появі невідомого `kid`.

## 11. Динамічна реєстрація клієнтів (Dynamic Client Registration, RFC 7591)

Кінцева точка `registration_endpoint` дозволяє автоматизувати процес реєстрації нових клієнтських додатків без необхідності ручного налаштування в панелі адміністратора провайдера.

**HTTP-метод:** `POST`  
**Заголовки:** `Content-Type: application/json`, `Accept: application/json`

### Приклад тіла запиту реєстрації

```json
{
  "client_name": "My SaaS Client",
  "redirect_uris": [
    "https://my-app.com/auth/callback"
  ],
  "response_types": [
    "code"
  ],
  "grant_types": [
    "authorization_code",
    "refresh_token"
  ],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://my-app.com/.well-known/jwks.json",
  "id_token_signed_response_alg": "RS256"
}
```

### Схема відповіді реєстрації (HTTP 201 Created)

```json
{
  "client_id": "c-981240182",
  "client_secret": "sec-b091823901...",
  "client_id_issued_at": 1735732800,
  "client_secret_expires_at": 0,
  "registration_access_token": "reg-token-881920...",
  "registration_client_uri": "https://auth.example.com/oauth2/v1/register/c-981240182"
}
```

Поле `registration_access_token` використовується клієнтом для автентифікації наступних запитів на управління власною конфігурацією згідно зі специфікацією RFC 7592:
* `GET /register/{client_id}` — отримання поточних параметрів реєстрації клієнта;
* `PUT /register/{client_id}` — оновлення налаштувань (списку `redirect_uris`, ключів або методів автентифікації);
* `DELETE /register/{client_id}` — відкликання реєстрації та повне видалення клієнтського облікового запису.

## 12. Специфікація перевірки стану сесії (Session Management 1.0)

Специфікація описує механізм перевірки активності сесії користувача у провайдера за допомогою HTML5 `postMessage` без надсилання регулярних HTTP-запитів.

1. **Завантаження iframe:** Клієнт завантажує у власному браузерному вікні прихований iframe провайдера, вказаний у параметрі discovery `check_session_iframe`.
2. **Формат запиту клієнта:** Клієнтський скрипт періодично надсилає повідомлення у вікно iframe через `window.postMessage`:
```javascript
const message = `${clientId} ${sessionState}`;
opIframe.contentWindow.postMessage(message, opOrigin);
```
3. **Обробка та відповідь провайдера:** Провайдер перевіряє сесійні кукі в домені IdP, порівнює їх із переданим значенням `sessionState` і повертає одне з трьох повідомлень:
   * `"unchanged"` — сесія користувача активна і не змінювалася;
   * `"changed"` — користувач вийшов або змінив обліковий запис у провайдері (клієнт повинен ініціювати тихий повторний вхід або вихід);
   * `"error"` — некоректний формат повідомлення або невідомий `clientId`.

#### Розрахунок значення `session_state`

Провайдер обчислює значення `session_state`, що повертається клієнту після авторизації, за односторонньою функцією хешування:
```
session_state = SHA-256( client_id + " " + origin + " " + op_browser_state + " " + salt ) + "." + salt
```
де `op_browser_state` — внутрішній стан сесійної cookie у провайдера, а `salt` — випадкова сіль. Це дозволяє браузеру перевіряти дійсність сесії без розкриття внутрішніх ідентифікаторів провайдера стороннім скриптам.
