# 📋 Інтерфейси керування спекуляцією ядра та процесора

Захист від апаратних атак на базі спекулятивного виконання вимагає узгодженої та багаторівневої взаємодії всіх шарів обчислювальної системи: кремнієвих регістрів процесора (MSR), системних викликів ядра операційної системи (`prctl`), діагностичного інтерфейсу віртуальної файлової системи (`sysfs`), механізмів очищення внутрішніх буферів ядра та бар'єрних інструкцій компілятора. Якщо надати розробникам лише апаратні біти без програмної обгортки, кожна програма змушена була б виконувати привілейовані команди або нести максимальні накладні витрати на повне вимкнення спекуляції. З іншого боку, програмні латки без апаратної підтримки є надто повільними. Нижче детально описано специфікацію контрактів, структурні біти, сімейства уразливостей буферів (MDS/L1TF), правила успадкування привілеїв та програмні інтерфейси взаємодії між цими шарами.

### Апаратні регістри моделі (MSR) архітектури x86-64

Архітектура x86-64 надає механізм конфігурації мікроархітектурних функцій через специфічні для моделі регістри (англ. *Model-Specific Registers*, MSR). Ці регістри не входять до стандартного набору регістрів загального призначення й доступні виключно на рівні найвищих привілеїв — у нульовому кільці (Ring 0) або в режимі кореня віртуалізації (VMX Root Mode / Hypervisor).

Доступ до простору MSR здійснюється парою парних асемблерних команд:
- `RDMSR` (Read from Model-Specific Register): зчитує 64-бітне значення регістру, номер якого передається в регістрі `ECX`. Старші 32 біти результату повертаються в `EDX`, а молодші 32 біти — в `EAX`.
- `WRMSR` (Write to Model-Specific Register): записує 64-бітне значення з пари `EDX:EAX` у MSR-регістр із номером з `ECX`.

Обидві команди є суворо привілейованими: спроба виконати їх у просторі користувача (Ring 3) негайно викликає переривання General Protection Fault (`#GP(0)`).

| MSR-регістр | Адреса | Призначення та бітовий розклад |
|---|---|---|
| `IA32_SPEC_CTRL` | `0x48` | **Біт 0 (IBRS):** Indirect Branch Restricted Speculation — блокує вплив менш привілейованого коду на передбачення непрямих переходів у ядрі.<br>**Біт 1 (STIBP):** Single Thread Indirect Branch Predictor — ізолює провісники розгалужень між двома SMT-потоками одного ядра.<br>**Біт 2 (SSBD):** Speculative Store Bypass Disable — вимикає випереджальне читання пам'яті до фіксації попередніх збережень (Spectre v4).<br>**Біт 10 (BHI_DIS_S):** Branch History Injection Disable — забороняє використання глобальної історії користувача під час виконання коду в просторі супервізора. |
| `IA32_PRED_CMD` | `0x49` | Командний регістр одноразової дії (тільки запис):<br>**Біт 0 (IBPB):** Indirect Branch Prediction Barrier — апаратна команда, що миттєво очищає всю історію буфера цілей переходів (BTB) під час перемикання задач. |
| `IA32_ARCH_CAPABILITIES` | `0x10A` | Регістр апаратних властивостей тільки для читання (наявний у нових CPU):<br>**Біт 0 (RDCL_NO):** Процесор апаратно не вразливий до Meltdown.<br>**Біт 1 (IBRS_ALL / eIBRS):** Постійний Enhanced IBRS із нульовими накладними витратами.<br>**Біт 2 (RSBA):** Відсутність уразливості переповнення стека повернень RSB.<br>**Біт 3 (SKIP_L1DFL_VMENTRY):** Гіпервізору не потрібно скидати L1D кеш при переході у гостьову VM.<br>**Біт 4 (SSB_NO):** Залізо не вразливе до Spectre v4.<br>**Біт 5 (MDS_NO):** Залізо не вразливе до атак вибірки мікроархітектурних буферів (MDS/RIDL). |
| `IA32_FLUSH_CMD` | `0x10B` | **Біт 0 (L1D_FLUSH):** Одноразова команда повного апаратного скидання кешу першого рівня L1D перед передачею керування ненадійному гостю VM. |

#### Детальний аналіз функціоналу бітів `IA32_SPEC_CTRL`

1. **IBRS (Indirect Branch Restricted Speculation, біт 0):** Коли цей біт встановлено в `1`, апаратні структури передбачення переходів (BTB) гарантують, що жодна історія розгалужень, накопичена під час виконання коду в просторі користувача (Ring 3), не братиметься до уваги, коли процесор переходить у простір ядра (Ring 0). Це унеможливлює отруєння буфера BTB для атак Spectre v2 на ядро. Проте в перших процесорах запис цього біта при кожному системному виклику коштував до 150 тактів.
2. **STIBP (Single Thread Indirect Branch Predictor, біт 1):** У процесорах із технологією одночасної багатонитковості (SMT / Hyper-Threading) два логічні ядра ділять єдиний фізичний кристал і спільні блоки передбачення переходів. Без STIBP процес, що крутиться на логічному ядрі 0, може отруїти таблицю BTB для процесу на логічному ядрі 1. Активація STIBP змушує апаратний блок розділяти таблиці передбачення між потоками.
3. **SSBD (Speculative Store Bypass Disable, біт 2):** Спекулятивні процесори вміють випереджати збереження: якщо команда читання `MOV EAX, [RDI]` слідує за командою запису `MOV [RSI], EBX`, а адреса `RSI` ще обчислюється, процесор спекулятивно читає пам'ять, вважаючи, що `RDI != RSI`. Якщо виявиться, що `RDI == RSI`, читання отримає застарілі дані (Spectre v4). Встановлення біта SSBD примусово забороняє читання пам'яті до завершення обчислення всіх попередніх адрес запису.
4. **BHI_DIS_S (Branch History Injection Disable, біт 10):** Новітня апаратна функція для протидії атакам типу Branch History Injection (BHI). Вона забороняє процесору використовувати спільний регістр глобальної історії розгалужень (Global Branch History Buffer, BHB) під час виконання коду супервізора, захищаючи ядро від ін'єкцій хибних послідовностей розгалужень.

#### Еволюція від класичного IBRS до eIBRS (Enhanced IBRS)

Класичний IBRS вимагав від ядра динамічного перемикання режиму: встановити біт при вході в системний виклик або переривання, скинути біт при виході в простір користувача. Це зумовлювалося тим, що увімкнений IBRS на ранніх мікроархітектурах суттєво обмежував спекулятивні можливості конвеєра і сповільнював навіть чисті обчислення.

У сучасних процесорах (Intel Cascade Lake, Ice Lake, Alder Lake, Raptor Lake; AMD Zen 3, Zen 4) реалізовано **Enhanced IBRS (eIBRS)**. Наявність eIBRS позначається бітом `IBRS_ALL` (біт 1) у регістрі `IA32_ARCH_CAPABILITIES`. За наявності цієї властивості ядро Linux записує значення `1` у `IA32_SPEC_CTRL` один раз під час завантаження системи. Апаратна логіка процесора автоматично активує ізоляцію переходів щоразу, коли рівень привілеїв змінюється на Ring 0, без жодної необхідності виконувати дорогі інструкції `WRMSR` під час системних викликів.

### Уразливості внутрішніх буферів: MDS, L1TF та інструкція `VERW`

Після публікації Spectre та Meltdown дослідники відкрили новий клас атак — **вибірку мікроархітектурних даних** (MDS, англ. *Microarchitectural Data Sampling*). Ці атаки експлуатують проміжні буфери всередині ядра CPU:

1. **RIDL (Rogue In-Flight Data Load / Line Fill Buffer):** Буфер заповнення ліній (LFB) утримує дані, що передаються між кешем L2 та кешем L1D. Коли спекулятивна операція читання завершується помилкою (Faulting Load), вона транзитно зчитує залишки чужих даних із сусідніх записів LFB.
2. **Fallout (Store Buffer Data Sampling):** Буфер збереження (Store Buffer) утримує результати операцій запису до їхньої фіксації в кеші L1D. Непривілейований процес спекулятивно вичитує конфіденційні дані ядра, які щойно записувалися драйверами.
3. **ZombieLoad / TAA (TSX Asynchronous Abort):** Асинхронне переривання транзакції Intel TSX призводить до того, що спекулятивні команди читають дані з внутрішніх портів завантаження (Load Ports).

#### Очищення буферів через інструкцію `VERW`

Оскільки для буферів LFB, Store Buffer та Load Ports не існувало апаратної команди очищення, інженери Intel оновили мікрокод процесорів, модифікувавши поведінку старої інструкції x86 `VERW` (Verify a Segment for Writing).

Якщо в регістрі `IA32_ARCH_CAPABILITIES` присутній прапорець `MDS_NO`, апаратні буфери безпечні. Якщо прапорця немає, ядро Linux виконує команду `VERW` з валідним дескриптором сегмента даних під час кожного повернення з ядра в простір користувача або передачі керування гостьовій віртуальній машині:

```
; Очищення мікроархітектурних буферів CPU (Line Fill Buffer / Store Buffer)
    sub rsp, 8
    mov word [rsp], ds
    verw [rsp]             ; Мікрокод скидає всі внутрішні буфери LFB/SB
    add rsp, 8
```

#### Захист від L1TF (L1 Terminal Fault) та інверсія сторінок (PTE Inversion)

Атака **L1TF (Foreshadow)** використовує особливість блоку MMU: коли в записі таблиці сторінок (PTE) біт присутності `Present` дорівнює `0` (сторінка вивантажена в swap або захищена), MMU негайно припиняє перевірку прав, але блок завантаження бере фізичні біти адреси з недійсного PTE і спекулятивно читає відповідну лінію з кешу L1D.

Ядро Linux вирішило цю проблему елегантним методом — **інверсією бітів сторінок** (PTE Inversion): коли сторінка позначається як недійсна (`Present = 0`), ядро інвертує всі біти фізичного номера фрейму. У результаті недійсний PTE вказує на неіснуючу фізичну адресу за межами встановленого обсягу DRAM, що унеможливлює знаходження лінії в L1D.

#### Спекулятивний обхід збереження (Spectre v4 / SSB) та біт SSBD

У конвеєрах Out-of-Order блок зняття неоднозначності пам'яті (Memory Disambiguator) передбачає, чи залежить наступна інструкція читання `MOV EAX, [RSI]` від попередньої інструкції запису `MOV [RDI], EBX`. Якщо адреса `RDI` ще не порахована, процесор спекулює, що адреси `RSI` та `RDI` не перетинаються, і дозволяє читанню випередити запис (Store Bypassing).

Якщо ж адреси збігаються, операція читання повертає застаріле значення з кешу замість оновленого значення `EBX`, що призводить до транзитного виконання з хибними даними (Spectre v4). Встановлення прапорця `PR_SPEC_STORE_BYPASS` через `prctl` записує біт `SSBD` у MSR `IA32_SPEC_CTRL`, повністю вимикаючи апаратний Memory Disambiguator для цього процесу.

#### Векторні інструкції та витік Gather Data Sampling (Downfall / GDS)

Атака **Downfall (CVE-2022-40982)** виявила вразливість у векторних розширеннях AVX2 та AVX-512 процесорів Intel. Векторні інструкції збору даних (`VPGATHERDD`, `VPGATHERQD`) дозволяють завантажувати розрізнені елементи масиву за вектором індексів.

Для пришвидшення роботи процесор використовує внутрішній апаратний буфер перевпорядкування векторних елементів (Gather Buffer). Під час спекулятивного або перерваного виконання інструкція `VPGATHER` транзитно підтягує вміст 128-бітних та 256-бітних векторних регістрів інших процесів і ядер, які нещодавно використовували спільні блоки SIMD.

Апаратне усунення GDS позначається бітом `GDS_NO` в `IA32_ARCH_CAPABILITIES`. Для старіших процесорів мікрокод вимикає апаратне злиття запитів у блоці `GATHER`, що знижує швидкість виконання векторних інструкцій на 10–50%, але гарантує повну ізоляцію векторних регістрів.

#### Захист від Retbleed та Inception: трампліни Return Thunks

У процесорах AMD Zen 1/Zen 2 та Intel Skylake інструкція повернення з функції `RET` поводиться як непрямий стрибок при вичерпанні стека RSB. Зловмисник може навмисно переповнити стек повернень, змусивши `RET` брати адреси з отруєного буфера BTB (Retbleed, CVE-2022-29900).

Ядро Linux нейтралізує цю атаку за допомогою компіляторних трамплінів `__x86_return_thunk` (Return Thunks). Замість виконання прямої інструкції `RET` компілятор вставляє виклик трампліна, який очищає глибину стека або виконує серію безпечних переходів із бар'єром `LFENCE`, унеможливлюючи спекулятивне перехоплення керування.

### Системний виклик Linux `prctl`: керування спекуляцією процесу

Для прикладного системного розробника прямий доступ до MSR-регістрів закритий. Проте критичні програми (криптографічні демони OpenSSL, сервіси управління ключами Vault, браузерні рушії V8) потребують можливості керувати рівнем спекулятивного захисту для конкретних процесів і потоків.

Для цього ядро Linux надає розширення системного виклику `prctl`:
- `PR_SET_SPECULATION_CTRL`: встановлення політики спекуляції для поточного потоку.
- `PR_GET_SPECULATION_CTRL`: зчитування поточної конфігурації захисту.

#### Параметри системного виклику `prctl`

Перший аргумент системного виклику визначає операцію (`PR_SET_SPECULATION_CTRL` або `PR_GET_SPECULATION_CTRL`).

Другий аргумент задає цільовий ресурс або механізм спекуляції:
1. `PR_SPEC_STORE_BYPASS` (`0`): керування спекулятивним обходом черги збереження (Spectre v4). Впливає на біт SSBD.
2. `PR_SPEC_INDIRECT_BRANCH` (`1`): керування непрямими розгалуженнями та захистом від міжпроцесного отруєння BTB (Spectre v2). Впливає на прапорці STIBP та виклики IBPB.
3. `PR_SPEC_L1D_FLUSH` (`2`): примусове очищення кешу даних першого рівня L1D під час перемикання контексту із заданого процесу.

Третій аргумент (для режиму `SET`) визначає бажану поведінку:
- `PR_SPEC_ENABLE` (`(1UL << 1)`): увімкнути спекуляцію (максимальна швидкість, захист вимкнено).
- `PR_SPEC_DISABLE` (`(1UL << 2)`): вимкнути спекуляцію для цього потоку. Потік може згодом знову увімкнути її самостійно.
- `PR_SPEC_FORCE_DISABLE` (`(1UL << 3)`): **незворотне вимкнення спекуляції**. Поточний процес, усі його потоки та всі майбутні нащадки (через `fork` або `clone`) назавжди втрачають право знову увімкнути спекуляцію. Спроба виконати `PR_SPEC_ENABLE` завершиться помилкою `EPERM`. Це золотий стандарт для ізоляції чутливих криптографічних задач.
- `PR_SPEC_DISABLE_NOEXEC` (`(1UL << 4)`): вимкнути спекуляцію для поточного процесу, але автоматично зняти обмеження, якщо процес виконає виклик `execve()` (запуск нової програми).

#### Програмний інтерфейс налаштування та моніторингу захисту

Нижче наведено повноцінну реалізацію системного контролера ізоляції потоків на мовах C та C++.

:::tabs
```c
#include <stdio.h>
#include <errno.h>
#include <sys/prctl.h>

/* Блокування непрямої спекуляції та спекулятивного читання пам'яті */
int enable_process_isolation(void) {
    /* Незворотно блокуємо отруєння непрямих переходів (STIBP / IBPB) */
    if (prctl(PR_SET_SPECULATION_CTRL,
              PR_SPEC_INDIRECT_BRANCH,
              PR_SPEC_FORCE_DISABLE, 0, 0) != 0) {
        perror("prctl PR_SPEC_INDIRECT_BRANCH");
        return -1;
    }

    /* Забороняємо спекулятивний обхід черги збереження (SSBD) */
    if (prctl(PR_SET_SPECULATION_CTRL,
              PR_SPEC_STORE_BYPASS,
              PR_SPEC_FORCE_DISABLE, 0, 0) != 0) {
        perror("prctl PR_SPEC_STORE_BYPASS");
        return -1;
    }

    return 0;
}

/* Перевірка поточного статусу захищеності процесу */
int is_isolation_enforced(void) {
    int res = prctl(PR_GET_SPECULATION_CTRL, PR_SPEC_INDIRECT_BRANCH, 0, 0, 0);
    if (res < 0) {
        return -1;
    }
    /* Перевіряємо чи прапорець встановлено через prctl та зафіксовано незворотно */
    return (res & PR_SPEC_PRCTL) && (res & PR_SPEC_FORCE_DISABLE);
}
```
```cpp
#include <iostream>
#include <system_error>
#include <cerrno>
#include <sys/prctl.h>

namespace security {

enum class SpeculationTarget : unsigned long {
    IndirectBranch = PR_SPEC_INDIRECT_BRANCH,
    StoreBypass    = PR_SPEC_STORE_BYPASS,
    L1dFlush       = PR_SPEC_L1D_FLUSH
};

class ProcessSpeculationController {
public:
    static void force_disable(SpeculationTarget target) {
        const auto resource = static_cast<unsigned long>(target);
        if (::prctl(PR_SET_SPECULATION_CTRL, resource, PR_SPEC_FORCE_DISABLE, 0, 0) != 0) {
            throw std::system_error(errno, std::generic_category(),
                                    "Не вдалося встановити PR_SPEC_FORCE_DISABLE");
        }
    }

    [[nodiscard]] static bool is_force_disabled(SpeculationTarget target) noexcept {
        const auto resource = static_cast<unsigned long>(target);
        const int status = ::prctl(PR_GET_SPECULATION_CTRL, resource, 0, 0, 0);
        if (status < 0) {
            return false;
        }
        return (status & PR_SPEC_PRCTL) && (status & PR_SPEC_FORCE_DISABLE);
    }
};

} // namespace security
```

### Інтерфейс діагностики ядра Linux у `sysfs`

Для адміністрування та перевірки стану вразливостей ядро Linux експортує глобальний стан усіх апаратних проблем у віртуальну директорію `/sys/devices/system/cpu/vulnerabilities/`. Кожен файл у цій директорії відповідає за окремий вектор мікроархітектурної атаки.

Програмне або консольне читання файлу повертає один із стандартизованих статусних рядків:

| Файл у `sysfs` | Типовий вміст захищеної системи | Технічне пояснення статусу |
|---|---|---|
| `meltdown` | `Mitigation: PTI` або `Not affected` | Для вразливих процесорів активний механізм KPTI (розділення CR3); для нових процесорів із бітом RDCL_NO або процесорів AMD — залізо повністю безпечне. |
| `spectre_v1` | `Mitigation: usercopy/swapgs barriers and __user pointer sanitization` | Ядро скомпільовано з бар'єрами `lfence` у точках передачі даних користувача (`copy_from_user`), обробниках `swapgs` та системних викликах. |
| `spectre_v2` | `Mitigation: Enhanced / Automatic IBRS, IBPB: conditional, RSB filling` | Комплексний захист ядра: апаратний eIBRS, умовне скидання буферів BTB через IBPB під час зміни контексту та заповнення стека RSB при виході з переривань. |
| `spec_store_bypass` | `Mitigation: Speculative Store Bypass disabled via prctl and seccomp` | Вимкнення спекулятивного читання до збереження для підозрілих або захищених процесів за допомогою системного виклику `prctl` або фільтрів `seccomp`. |
| `l1tf` | `Mitigation: PTE Inversion; VMX: conditional cache flushes, SMT vulnerable` | Інверсія фізичних бітів у недійсних сторінках пам'яті (PTE Inversion) для захисту від атаки Foreshadow (L1 Terminal Fault). |
| `mds` | `Mitigation: Clear CPU buffers; SMT disabled` | Очищення внутрішніх буферів мікроархітектури (Line Fill Buffer, Store Buffer) за допомогою мікрокодової інструкції `VERW` під час повернення в Ring 3. |
| `retbleed` | `Mitigation: Enhanced IBRS, return thunks` | Захист від атак на інструкції повернення `RET` на мікроархітектурах Zen 1/Zen 2 та Intel Skylake–Comet Lake. |

#### Параметри командного рядка ядра Linux для керування захистом

Системний адміністратор може перевизначити політику безпеки ядра під час завантаження системи за допомогою спеціальних параметрів завантажувача (GRUB/systemd-boot):
- `mitigations=auto`: режим за замовчуванням. Ядро автоматично вмикає всі доступні програмні та апаратні методи захисту відповідно до поточної моделі процесора.
- `mitigations=off`: повне вимкнення всіх мікроархітектурних захистів (KPTI, Retpoline, eIBRS, SSBD, L1TF, MDS). Забезпечує максимальну продуктивність заліза ціною повної втрати безпеки між процесами та ядром (використовується виключно в ізольованих обчислювальних кластерах HPC).
- `mitigations=auto,nosmt`: автоматичний захист із примусовим вимкненням одночасної багатонитковості (Hyper-Threading). Застосовується в хмарних середовищах із високими вимогами до ізоляції сусідніх віртуальних машин.

### Бар'єри компілятора та безгалузеве маскування індексів

На рівні компіляторів GCC та Clang захист критичних ділянок коду від спекулятивного виходу за межі масивів реалізується двома взаємодоповнюючими стратегіями: апаратними бар'єрами серіалізації та математичним маскуванням індексів (Speculative Load Hardening, SLH).

#### Бар'єр `LFENCE` проти маскування індексу

Інструкція `_mm_lfence()` змушує апаратний конвеєр процесора повністю зупинити вибірку та виконання наступних мікрооперацій доти, доки результат попередньої умовної гілки не зафіксується в буфері перевпорядкування (ROB). Це на 100% надійно усуває спекуляцію, але в критичних циклах додає затримку в 15–30 тактів.

Якщо потрібна максимальна продуктивність у гарячих циклах, застосовують техніку **безгалузевого маскування індексу** (Branchless Clamping / SLH): індекс обчислюється суто арифметично без використання команд умовного переходу `Jcc`. Оскільки в коді немає гілки, блок передбачення переходів не може зробити помилкову ставку.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <x86intrin.h>

/* Безгалузеве маскування індексу (Branchless Sanitization) */
static inline size_t sanitize_speculative_index(size_t index, size_t limit) {
    /* Якщо index < limit, старший біт різниці дорівнює 0, маска = 0xFFFFFFFFFFFFFFFF;
       якщо index >= limit, маска стає 0x0000000000000000 */
    int64_t mask = ((int64_t)(index ^ limit) | (int64_t)(index - limit)) >> 63;
    return index & (size_t)(~mask);
}

/* Читання елемента з апаратним бар'єром LFENCE */
uint8_t secure_read_with_fence(const uint8_t *arr, size_t len, size_t idx) {
    if (idx < len) {
        _mm_lfence(); /* Повна зупинка спекулятивного конвеєра */
        return arr[idx];
    }
    return 0;
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <optional>
#include <x86intrin.h>

namespace security {

template <typename T>
[[nodiscard]] size_t sanitize_index(size_t index, size_t limit) noexcept {
    const auto s_idx = static_cast<int64_t>(index);
    const auto s_lim = static_cast<int64_t>(limit);
    const int64_t mask = ((s_idx ^ s_lim) | (s_idx - s_lim)) >> 63;
    return index & static_cast<size_t>(~mask);
}

template <typename T>
[[nodiscard]] std::optional<T> secure_read_fenced(std::span<const T> data, size_t index) noexcept {
    if (index < data.size()) {
        _mm_lfence(); // Бар'єр серіалізації: гарантує завершення перевірки меж
        return data[index];
    }
    return std::nullopt;
}

} // namespace security
```
