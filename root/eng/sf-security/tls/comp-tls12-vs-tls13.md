# ⚖️ Архітектурне порівняння TLS 1.2 та TLS 1.3

Протокол TLS 1.3 (RFC 8446) не є черговим набором косметичних правок до TLS 1.2 (RFC 5246): це фундаментальний рефакторинг криптографічної моделі, протоколу узгодження та структури збереження конфіденційності метаданих у комп'ютерних мережах.

Нижче наведено структуроване зіставлення двох поколінь стандарту за ключовими інженерними, продуктивними та криптографічними осями.

```
+---------------------------+--------------------------------+--------------------------------+
| Характеристика            | TLS 1.2 (RFC 5246)             | TLS 1.3 (RFC 8446)             |
+---------------------------+--------------------------------+--------------------------------+
| Базова затримка з'єднання | 2 RTT                          | 1 RTT                          |
| Відновлення сесії         | 1 RTT (Session ID / Ticket)    | 0 RTT (Early Data via PSK)     |
| Обмін ключами             | Статичний RSA, DHE, ECDHE      | Виключно ефемерні (ECDHE, DHE) |
| Пряма секретність (PFS)   | Опціональна (залежить від набору)| Обов'язкова для всіх наборів  |
| Симетричне шифрування     | CBC, RC4, AEAD (GCM, CCM)      | Лише AEAD (GCM, Poly1305, CCM) |
| Структура MAC             | MAC-then-Encrypt, Encrypt-then-MAC | Вбудовано в AEAD (Auth Tag)  |
| Захист сертифіката        | Відкритий текст                | Зашифрований (Handshake Key)   |
| Захист розширень          | Відкритий текст                | Зашифровані (EncryptedExt)     |
| Кількість шифрокомплектів | Сотні комбінаторних варіантів  | 5 ортогональних AEAD наборів   |
| Дерево ключів             | PRF на базі HMAC (плоске)      | Деревоподібний HKDF (Extract/Expand)|
| Захист від відкату версії | Неявний (через Finished)       | Сентинели в ServerHello.random |
+---------------------------+--------------------------------+--------------------------------+
```

## 1. Затримка та оптимізація кругового обходу (RTT)

У протоколі TLS 1.2 повне встановлення криптографічного сеансу вимагає двох повних кругових обходів мережі (2 Round Trip Times — 2-RTT):
1. **Перший RTT:** Клієнт надсилає `ClientHello` з переліком підтримуваних шифрів. Сервер відповідає `ServerHello`, передає свій ланцюжок сертифікатів `Certificate`, генерує параметри обміну `ServerKeyExchange` і сигналізує про завершення першої фази повідомленням `ServerHelloDone`.
2. **Другий RTT:** Клієнт генерує та надсилає `ClientKeyExchange`, перемикає стан шифрування за допомогою `ChangeCipherSpec` і підтверджує цілісність рукостискання повідомленням `Finished`. Сервер перевіряє цілісність, надсилає власний `ChangeCipherSpec` та `Finished`.

Лише після цього клієнт отримує право надіслати перший байт корисного навантаження (наприклад, HTTP GET-запит). Якщо затримка між клієнтом і сервером становить 100 мс, користувач змушений чекати 200 мс лише на завершення TLS-фази, до якої додається початкове тристороннє TCP-рукостискання SYN/ACK (ще 1 RTT).

TLS 1.3 скорочує фазу повного рукостискання рівно до 1-RTT. Оскільки простір алгоритмів обміну ключами очищено від застарілих схем, клієнт оптимістично припускає найімовірніші еліптичні криві сервера (наприклад, Curve25519 або NIST P-256) і надсилає відкритий ключ Diffie — Hellman безпосередньо у першому польоті через розширення `key_share`. Сервер обчислює спільний секрет, генерує власний `key_share`, і вже всі наступні повідомлення сервера (`EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`) передаються зашифрованими. Клієнт може передавати дані додатку одразу після відправлення власного `Finished`.

Для повторних з'єднань TLS 1.3 пропонує режим 0-RTT (Early Data), у якому клієнт шифрує дані першого запиту за допомогою попередньо збереженого секрету (PSK), скорочуючи затримку старту передачі до абсолютного фізичного мінімуму. У той час як TLS 1.2 для відновлення сеансу вимагав щонайменше 1-RTT, TLS 1.3 дозволяє відправити HTTP-запит у першому ж IP-пакеті.

## 2. Модель безпеки обміну ключами та Perfect Forward Secrecy

У TLS 1.2 фундаментальною загрозою залишався обмін ключами на базі статичного RSA (`TLS_RSA_WITH_...`). У цій схемі клієнт генерував випадковий передголовний секрет (Pre-Master Secret), шифрував його відкритим RSA-ключем сервера з сертифіката і надсилав через мережу.

Такий підхід мав два критичні дефекти:
- **Відсутність прямої секретності (Perfect Forward Secrecy, PFS):** якщо приватний ключ сервера буде скомпрометовано або вилучено через роки після запису мережевого трафіку, атакуючий може розшифрувати всі збережені терабайти історичних сесій. Це дозволяло пасивним системам стеження збирати зашифрований інтернет-трафік у сховища та чекати компрометації ключів.
- **Оракули Блейхенбахера:** формат набивки PKCS#1 v1.5 створював витоки через коди помилок розшифрування, що дозволяло активному спостерігачеві підбирати сесійні ключі шляхом надсилання модифікованих шифротекстів.

TLS 1.3 повністю забороняє статичний RSA для обміну ключами. Єдиним дозволеним механізмом є протокол Діффі — Геллмана на ефемерних ключах: ECDHE (на еліптичних кривих) або DHE (у скінченних полях). Асиметричний ключ із сертифіката сервера використовується **виключно для цифрового підпису** транскрипту рукостискання (`CertificateVerify`), що гарантує строгу пряму секретність для кожного сеансу. Навіть якщо довгостроковий приватний ключ сервера потрапить до рук зловмисника, розшифрувати перехоплені сесії TLS 1.3 математично неможливо, оскільки тимчасові ефемерні ключі видаляються з пам'яті одразу після закриття сеансу.

## 3. Спрощення шифрокомплектів та ортогональність

У TLS 1.2 шифрокомплект (Cipher Suite) був громіздкою монолітною структурою, яка жорстко зв'язувала чотири незалежні криптографічні компоненти:
```
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
 ├── ECDHE   : алгоритм обміну ключами
 ├── RSA     : алгоритм автентифікації (підпису) сертифіката
 ├── AES_256 : симетричний шифр
 ├── GCM     : режим роботи шифру
 └── SHA384  : хеш-функція для PRF та MAC
```
Це призвело до комбінаторного вибуху: стандарт налічував понад 300 можливих шифрокомплектів, більшість із яких містили вразливі комбінації (наприклад, DHE з 512-бітними експортними групами, режими CBC разом із SHA-1, або застарілий шифр RC4).

У TLS 1.3 концепцію розділено на незалежні ортогональні площини:
1. Алгоритм обміну ключами узгоджується через розширення `supported_groups` та `key_share`.
2. Алгоритм цифрового підпису сервера узгоджується через `signature_algorithms`.
3. Шифрокомплект TLS 1.3 визначає **лише** симетричний алгоритм AEAD та базову хеш-функцію для HKDF.

Увесь протокол TLS 1.3 спирається лише на 5 стандартизованих шифрокомплектів:
- `TLS_AES_128_GCM_SHA256` (0x13, 0x01) — обов'язковий базовий набір;
- `TLS_AES_256_GCM_SHA384` (0x13, 0x02) — для високого рівня криптостійкості;
- `TLS_CHACHA20_POLY1305_SHA256` (0x13, 0x03) — оптимізований для мобільних CPU без апаратної підтримки AES-NI;
- `TLS_AES_128_CCM_SHA256` (0x13, 0x04) — для IoT та вбудованих систем;
- `TLS_AES_128_CCM_8_SHA256` (0x13, 0x05) — полегшений варіант із 64-бітним тегом автентичності.

Такий підхід повністю виключає помилки конфігурації адміністраторів, коли сильний шифр поєднувався зі слабким хешем або вразливим алгоритмом обміну.

## 4. Конфіденційність метаданих та шифрування рукостискання

У TLS 1.2 майже всі метадані рукостискання передавалися відкритим текстом:
- ланцюжок сертифікатів сервера X.509 дозволяв пасивному спостерігачеві миттєво ідентифікувати доменне ім'я ресурсу, до якого звертається користувач;
- сертифікат клієнта (при взаємній mTLS автентифікації) розкривав персональні дані та ідентичність користувача будь-якому транзитному вузлу;
- розширення `ClientHello` та `ServerHello` (включно зі списком розширень і протоколами ALPN) видавали операційну систему, версію браузера та внутрішню конфігурацію стеку.

У TLS 1.3 шифрування вмикається одразу після повідомлення `ServerHello`. Сервер генерує тимчасові ключі рукостискання (`Handshake Traffic Keys`) на базі отриманого `key_share` і передає сертифікати, підписи та всі розширення (`EncryptedExtensions`) у зашифрованому вигляді. Пасивний перехоплювач бачить у незахищеному вигляді лише початкові `ClientHello` та `ServerHello`.

## 5. Захист від атак зниження версії (Anti-Downgrade Defense)

Зловмисник, що контролює мережевий канал, міг провокувати фальшиві скидання TCP-з'єднань TLS 1.3, змушуючи клієнтську програму перезапускати з'єднання у режимі TLS 1.2 заради сумісності.

У TLS 1.3 сервер, який змушений погодитися на TLS 1.2 або TLS 1.1 через вимогу клієнта, вбудовує спеціальну магічну послідовність (сентинел) в останні 8 байтів поля `ServerHello.random`:
- при узгодженні TLS 1.2 сервер встановлює суфікс: `44 4F 57 4E 47 52 44 01` (ASCII-рядок `DOWNGRD\x01`);
- при узгодженні TLS 1.1 або нижче встановлюється: `44 4F 57 4E 47 52 44 00` (`DOWNGRD\x00`).

Якщо сучасний клієнт, що підтримує TLS 1.3, помічає цей сентинел у сесії TLS 1.2, він миттєво розпізнає активну атаку зниження версії (Downgrade Attack), негайно розриває зв'язок і сигналізує фатальною помилкою `illegal_parameter`.

## 6. Порівняння механізмів відновлення сесії

У TLS 1.2 існувало два окремі та несумісні механізми прискореного відновлення з'єднання:
1. **Session ID (RFC 5246):** сервер зберігав стан сесії у власній оперативній пам'яті та видавав клієнту 32-байтний ідентифікатор `session_id`. У розподілених кластерах із сотнями серверів це вимагало синхронізації гігабайтних кешів пам'яті між усіма балансувальниками.
2. **Session Tickets (RFC 5077):** сервер шифрував стан власним секретним ключем (STEK — Session Ticket Encryption Key) і передавав його клієнту як непрозорий блоб. Клієнт повертав квиток при повторному підключенні. Недоліком була відсутність прямої секретності: компрометація одного ключа STEK розкривала всі відновлені сесії.

У TLS 1.3 обидва підходи замінено на **уніфікований механізм PSK (Pre-Shared Key)**. Сесійний квиток у повідомленні `NewSessionTicket` більше не містить сирого стану: він вказує на ключ `Resumption Master Secret` у дереві ключів HKDF. 

## 7. Модернізація цифрових підписів: відмова від PKCS#1 v1.5 на користь RSA-PSS

У TLS 1.2 сервери з RSA-сертифікатами використовували для підпису повідомлень рукостискання схему набивки PKCS#1 v1.5. Ця схема є детермінованою і не містить математичного доведення стійкості у моделі випадкового оракула, що неодноразово створювало підґрунтя для атак на базі оракулів помилок.

TLS 1.3 повністю забороняє набивку PKCS#1 v1.5 для цифрового підпису повідомлень `CertificateVerify`, переводячи протокол на імовірнісну схему **RSA-PSS (Probabilistic Signature Scheme, RFC 8017)** або схеми на еліптичних кривих **ECDSA** та **Ed25519**. RSA-PSS додає випадкову сіль (salt) до кожного генерованого підпису, що унеможливлює атаку підбору підписів за відомими зразками та надає строге криптографічне доведення безпеки.

## 8. Захист від атак усічення сеансу (Truncation Attacks)

У ранніх версіях SSL/TLS зловмисник міг примусово розірвати TCP-з'єднання шляхом надсилання фальшивого TCP-пакета `FIN` або `RST`. Якщо прикладний протокол (наприклад, старий HTTP/1.0) не вказував точну довжину тіла відповіді через заголовок `Content-Length`, клієнт вважав отримані до розриву байти повною відповіддю сервера, що дозволяло непомітно обрізати банківські виписки чи юридичні документи.

У TLS 1.3 введено суворе правило двостороннього закриття сеансу:
- Будь-яке коректне закриття з'єднання **зобов'язане** супроводжуватися відправленням зашифрованого повідомлення тривоги `close_notify` на рівні протоколу записів.
- Якщо клієнт отримує скидання з'єднання на рівні TCP без попереднього сигналу `close_notify`, сеанс вважається скомпрометованим і завершується помилкою `unexpected_eof`.

Це гарантує, що жоден байт прикладного потоку не може бути відсічений або загублений без явного виявлення клієнтським додатком.
