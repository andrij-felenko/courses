# 📋 Специфікація автоматного стану та протоколу взаємодії CVD (ISO/IEC 29147 / 30111)

Процес узгодженого розкриття вразливостей (Coordinated Vulnerability Disclosure) стандартизований міжнародними нормами ISO/IEC 29147 («Вразливості безпеки — розкриття») та ISO/IEC 30111 («Процеси обробки вразливостей»). Для усунення невизначеності між дослідником, вендором та координаційними центрами життєвий цикл кожної вразливості описується як детермінований скінченний автомат станів із фіксованими часовими обмеженнями (SLA), строгими інваріантами конфіденційності та формалізованими протоколами обміну метаданими.

## Модель станів життєвого циклу вразливості

Автомат станів CVD-кейсу визначає допустимі фази обробки вразливості від моменту отримання первинного звіту до фінальної публікації бюлетеня безпеки та зняття режиму ембарго.

| Стан (State Enum) | Опис та семантика | Вхідні умови (Guard Conditions) | Дефолтний SLA |
| :--- | :--- | :--- | :--- |
| `STATE_SUBMITTED` | Звіт отримано через захищений канал зв'язку | Валідний PGP-підпис або автентифікована вебформа | 24–48 годин на підтвердження |
| `STATE_TRIAGED` | Первинний аналіз, відтворення та оцінка CVSS | Відтворення на актуальній версії, CVSS ≥ 0.1 | До 7 днів від надходження |
| `STATE_REJECTED` | Звіт відхилено (не є багом безпеки чи out-of-scope) | Надано технічне обґрунтування закриття | Фінальний стан |
| `STATE_DUPLICATE` | Вразливість уже відома вендору або виправлена | Надано посилання на раніший внутрішній тікет | Фінальний стан |
| `STATE_IN_PROGRESS` | Розробка виправлення та перевірка відсутності регресій | Призначено команду інженерів, зарезервовано CVE | До 75 днів від надходження |
| `STATE_PATCH_READY` | Виправлення скомпільовано, протестовано та затверджено | Успішні інтеграційні та регресійні тести | До 80 днів від надходження |
| `STATE_PRE_NOTIFY` | Попереднє сповіщення downstream-партнерів під NDA | Наявність списку довірених інтеграторів | 80–90 днів від надходження |
| `STATE_DISCLOSED` | Публічний реліз бюлетеня, зняття ембарго, публікація CVE | Настання дати розкриття або закінчення 90d (+14d) | Фінальний стан |
| `STATE_EMERGENCY` | Екстрене розкриття через витік або активну експлуатацію | Детекція 0-day in-the-wild або публічний PoC | 0–7 днів |

### Допустимі переходи та інваріанти станів

1. `STATE_SUBMITTED` → `STATE_TRIAGED` | `STATE_REJECTED` | `STATE_DUPLICATE`
   - *Інваріант:* Якщо вендор не надав відповіді про отримання протягом 7 календарних днів, дослідник має безумовне право звернутися до національного координатора (CERT/CC, CERT-UA) для примусової ескалації.
2. `STATE_TRIAGED` → `STATE_IN_PROGRESS`
   - *Інваріант:* Орган нумерації (CNA) зобов'язаний зарезервувати ідентифікатор у форматі `CVE-YYYY-NNNNN` у стані `RESERVED` без розкриття публічного опису. Встановлюється базова дата закінчення ембарго: `T_0 + 90 днів`.
3. `STATE_IN_PROGRESS` → `STATE_PATCH_READY`
   - *Інваріант:* Дослідник має право ознайомитися з чернеткою патча для перевірки повноти усунення вектора атаки та відсутності неповного закриття багу (англ. *incomplete fix*).
4. `STATE_PATCH_READY` → `STATE_PRE_NOTIFY`
   - *Інваріант:* Downstream-партнери (провайдери хмарних сервісів, дистрибутиви ОС) підписують договірні зобов'язання про нерозголошення (NDA) і не мають права публікувати бінарні оновлення або коміти у відкритих репозиторіях до загальної дати зняття ембарго.
5. `STATE_PRE_NOTIFY` → `STATE_DISCLOSED`
   - *Інваріант:* Одночасна публікація виправлень, офіційного бюлетеня безпеки (Security Advisory), публікація релізу CVE в базах MITRE та NIST NVD, а також публічне висловлення подяки першовідкривачу (Credits).
6. Будь-який стан → `STATE_EMERGENCY`
   - *Інваріант:* Спрацьовує автоматично при зміні статусу прапорців `flag_in_the_wild = true` або `flag_public_leak = true`. Встановлює новий стиснутий дедлайн: 7 днів для активної експлуатації або негайно (до 48 годин) для публічного витоку експлойта.

## Протокол захищеної взаємодії та discovery-файл RFC 9116 (security.txt)

Для забезпечення конфіденційності первинного контакту стандарти ISO/IEC 29147 та RFC 9116 регламентують розміщення на вебресурсах публічного машиночитаного файлу `/.well-known/security.txt`. Цей документ дозволяє автоматизованим сканерам та дослідникам безпеки однозначно визначати авторизовані канали передачі даних, відкриті PGP-ключі та строки дії політики.

```http
Contact: mailto:psirt@example.com
Contact: https://example.com/security/report-form
Encryption: https://example.com/pgp/psirt-key-2026.asc
Acknowledgments: https://example.com/security/hall-of-fame
Preferred-Languages: uk, en
Canonical: https://example.com/.well-known/security.txt
Policy: https://example.com/security/coordinated-vulnerability-disclosure
Expires: 2027-12-31T23:59:59.000Z
```

### Специфікація директив RFC 9116

- `Contact` (URI, обов'язкове, ≥ 1): Пряма адреса електронної пошти (`mailto:`) або посилання на захищену вебформу чи портал Bug Bounty (`https://`).
- `Expires` (ISO 8601 Timestamp, обов'язкове, рівно 1): Точний час закінчення строку дії поточної безпекової політики (максимальний строк чинності — не більше 365 днів від моменту розміщення). Файл із простроченою датою `Expires` вважається недійсним і не створює гарантій правового захисту Safe Harbor.
- `Encryption` (URI, рекомендоване): Посилання на відкритий PGP-ключ команди реагування на інциденти (PSIRT). Звіт має шифруватися виключно цим ключем для захисту від перехоплення третіми сторонами.
- `Policy` (URI, рекомендоване): Посилання на офіційний текст регламенту узгодженого розкриття компанії, де зафіксовані строки ембарго та положення про правовий захист дослідників.
- `Canonical` (URI, рекомендоване): Офіційна канонічна адреса файлу для запобігання підміні змісту через кешуючі проксі-сервери або сторонні дзеркала.

## Правила розрахунку часових строків та часових поясів

Для усунення розбіжностей під час роботи міжнародних команд розробки та координації діють єдині математичні правила розрахунку строків:

1. **Єдина часова шкала UTC:** Усі часові мітки в протоколі CVD фіксуються виключно за всесвітнім координованим часом (UTC). Використання локальних часових поясів заборонено для запобігання помилкам під час переходу на літній/зимовий час.
2. **Базовий інтервал 90 днів:** Момент закінчення ембарго `T_embargo` розраховується як `T_0 + 90 календарних днів`. Часом розкриття за замовчуванням є 14:00 UTC (10:00 EST / 17:00 EET), що забезпечує готовність інженерних команд чергування в більшості часових поясів.
3. **Правило перенесення на робочий день (Weekend Rollover):** Якщо 90-й день ембарго припадає на суботу або неділю, дата офіційного розкриття автоматично переноситься на найближчий понеділок о 14:00 UTC. Це захищає користувачів та чергових системних адміністраторів від необхідності термінового розгортання критичних патчів у вихідні дні.
4. **Умови надання 14-денного пільгового періоду (Grace Period):** Якщо на 85-й день вендор має повністю готовий та верифікований патч, але запланований релізний цикл або масштабне регресійне тестування потребує додаткового часу, вендор надсилає аргументований запит досліднику. Пільговий період продовжує ембарго максимум на 14 календарних днів (до `T_0 + 104 дні`).
5. **Екстрене скорочення (Emergency Timeline):** У разі фіксації активних атак або витоку експлойта дедлайн скорочується до `T_leak + 7 днів` (або `T_leak + 48 годин` при появі публічного робочого PoC). Попередні домовленості про 90-денне очікування анулюються.

## Коди помилок та обробка виняткових ситуацій

Під час роботи автомата станів протоколу виділяються стандартизовані виняткові ситуації:

- `ERR_SLA_TRIAGE_EXCEEDED`: Вендор не надав підтвердження валідації протягом 7 днів. Дія: ескалація до національного CSIRT/CERT для встановлення контакту через альтернативні канали.
- `ERR_EMBARGO_BREACH`: Виявлено публікацію PoC або деталей атаки до узгодженої дати. Дія: негайний перехід у стан `STATE_EMERGENCY` та публікація наявних мітигацій.
- `ERR_PATCH_REGRESSION`: Запропонований патч не повністю усуває вразливість або спричиняє відмову в обслуговуванні під час верифікації. Дія: активація запиту на Grace Period із детальним планом виправлення.
