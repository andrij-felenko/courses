# 🧮 Формальна метрика поверхні атаки Манадхати-Вінг (Manadhata-Wing Metric)

Кількісна оцінка безпеки програмної системи довгий час залишалася суб'єктивною експертною оцінкою. Інженери оперували якісними поняттями («більш захищений», «менш вразливий»), але не мали строгого математичного апарату, здатного довести, що зміна конфігурації або архітектурний рефакторинг об'єктивно зменшили ризик компрометації. У 2004–2011 роках дослідники Карнегі-Меллон Пратьюса Манадхата та Дженнет Вінг розробили першу формальну модель простору станів та метрику вимірювання поверхні атаки системи (англ. *Attack Surface Metric*), яка спирається на теорію автоматів, матриці доступу та зважені векторні простори ресурсів.

## 1. Формалізація системи як скінченного автомата

Програмна система моделюється як скінченний або зліченний перехідний автомат `M`, що взаємодіє з неконтрольованим зовнішнім оточенням `E` (лат. *ambitus* — оточення):

```
M = (S, S₀, I, O, T)
```

Де компоненти мають строгий системний зміст:
- `S` — простір станів виконання (пам'ять процесу, регістри, дескриптори відкритих файлів, сокети, таблиці бази даних);
- `S₀ ⊆ S` — множина початкових валідних станів після завантаження системи;
- `I` — множина вхідних подій або повідомлень (мережеві пакети, виклики функцій, сигнали ОС, дані stdin);
- `O` — множина вихідних подій (відповіді клієнту, записи в журнал, мережеві сповіщення);
- `T: S × I → S × O` — детерміноване або недетерміноване відношення переходів між станами.

Зловмисник (англ. *attacker*) не має прямого доступу до внутрішнього стану `S`. Він може взаємодіяти з системою виключно через ресурси системи, які перетинають межу довіри між оточенням `E` та автоматом `M`.

## 2. Множини ресурсів експозиції

Усі ресурси системи розбиваються на три неперетинні класи ресурсів експозиції:

### 2.1. Точки входу та виходу (Methods)
Множина `M_methods` складається з усіх функцій, обробників запитів та системних викликів, які можуть бути ініційовані або прочитані зовнішнім середовищем:
- Точки входу `Entry`: методи API, HTTP-маршрути, обробники сигналів, експортовані символи бібліотеки;
- Точки виходу `Exit`: функції зворотного виклику, генератори діагностичних повідомлень, виведення помилок.

### 2.2. Канали зв'язку (Channels)
Множина `C_channels` охоплює всі фізичні та логічні протокольні середовища, через які передаються дані:
- Мережеві endpoints (сокети TCP, UDP, SCTP);
- Локальні канали міжпроцесної взаємодії (Unix domain сокети, іменовані канали FIFO, черги POSIX mq);
- Спільна пам'ять (сегменти shm, mmap-буфери);
- Фізичні порти (USB, послідовні інтерфейси UART, SPI).

### 2.3. Елементи недовірених даних (Data Items)
Множина `D_data` містить усі структури та змінні стану, які можуть бути створені або модифіковані зовнішнім користувачем:
- Файли конфігурації, бази даних, ключі реєстру;
- Змінні оточення процесу (`ENV`);
- Серіалізовані пакети, токени сесій, куки.

Повний вектор експозиції системи визначається кортежем множин:

```
AS_vector = (M_methods, C_channels, D_data)
```

## 3. Зважування ресурсів: Потенціал шкоди та Права доступу

Просте підрахування кількості відкритих портів або ендпоінтів є некоректним: відкритий порт віддаленого шелла з правами `root` створює значно більшу небезпеку, ніж локальний Unix-сокет читання поточної температури процесора з правами `nobody`.

Для кожного ресурсу `r ∈ (M_methods ∪ C_channels ∪ D_data)` вводиться функція ваги `w(r)`, яка обчислюється як відношення потенціалу шкоди до бар'єра доступу:

```
w(r) = DP(r) / AR(r)
```

Де:
- `DP(r)` (англ. *Damage Potential*, лат. *potentialis* — можливий) — міра деструктивного впливу або привілеїв, якими володіє ресурс під час виконання:
  - `DP = 5`: виконання коду в просторі ядра (Ring 0 / Kernel driver);
  - `DP = 4`: виконання коду з привілеями адміністратора (Root / SYSTEM / `CAP_SYS_ADMIN`);
  - `DP = 3`: мутація критичного стану системи (запис у базу даних, заміна конфігурації);
  - `DP = 2`: виконання коду від імені непривілейованого користувача;
  - `DP = 1`: операція тільки для читання (Read-only інформаційний запит).
- `AR(r)` (англ. *Access Rights*, лат. *rectus* — право) — ступінь обмеження доступу до ресурсу:
  - `AR = 1`: анонімний доступ через відкриту мережу (будь-який неавтентифікований клієнт з інтернету);
  - `AR = 2`: автентифікований віддалений користувач зі стандартними правами;
  - `AR = 3`: локальний користувач операційної системи;
  - `AR = 4`: автентифікований адміністратор системи (Mutual TLS + MFA + рольова модель).

Звідси випливає фундаментальна властивість: чим вищі привілеї вимагаються для взаємодії з ресурсом (велике значення `AR`), тим менший внесок цього ресурсу в сумарну вагу поверхні атаки. І навпаки: ненадійний неавтентифікований ендпоінт із привілеями `root` (`AR = 1, DP = 4`) має максимальну вагу `w(r) = 4 / 1 = 4.0`.

## 4. Інтегральна метрика поверхні атаки

Інтегральна метрика поверхні атаки `S_total` обчислюється як зважена сума внесків за всіма трьома вимірами експозиції:

```
S_total = S_M + S_C + S_D
```

Розгорнуті суми для кожної складової мають вигляд:

```
S_M = ∑ w(m)    [для всіх m ∈ M_methods]
S_C = ∑ w(c)    [для всіх c ∈ C_channels]
S_D = ∑ w(d)    [для всіх d ∈ D_data]
```

## 5. Покроковий розрахунок: моноліт проти загартованого сервісу

Розглянемо практичний приклад математичного моделювання зміни поверхні атаки при рефакторингу мережевого мережевого демона обробки телеметрії.

### 5.1. Початковий стан: монолітний демон (Архітектура A)
- **Методи (`M`):** 8 REST-маршрутів (4 публічні для запису даних, 2 для читання, 2 приховані адмін-ручки для скидання кешу та виконання діагностичних команд ОС). Весь процес працює під користувачем `root`.
- **Канали (`C`):** TCP-порт `0.0.0.0:8080` (відкритий усім), TCP-порт `0.0.0.0:9090` (порт адмін-панелі), спільна пам'ять `/dev/shm/telemetry` з правами `0666`.
- **Дані (`D`):** JSON-пейлоад довільної структури, файл конфігурації `/etc/telemetry.conf` (доступний на запис процесу).

Обчислення ваг компонентів Архітектури A:

```
S_M(A)
= 4 · (DP=3 / AR=1) + 2 · (DP=1 / AR=1) + 2 · (DP=4 / AR=1)  [публічні + читання + адмін]
= 4 · 3.0 + 2 · 1.0 + 2 · 4.0                                 [підстановка часток]
= 12.0 + 2.0 + 8.0                                            [множення]
= 22.0

S_C(A)
= (DP=4 / AR=1) + (DP=4 / AR=1) + (DP=3 / AR=1)               [порти 8080, 9090 та shm]
= 4.0 + 4.0 + 3.0                                             [підстановка часток]
= 11.0

S_D(A)
= (DP=3 / AR=1) + (DP=4 / AR=1)                               [неструктурований JSON та конфіг]
= 3.0 + 4.0                                                   [підстановка часток]
= 7.0

S_total(A)
= S_M(A) + S_C(A) + S_D(A)
= 22.0 + 11.0 + 7.0
= 40.0
```

### 5.2. Цільовий стан: сервіс із розподілом привілеїв та ізоляцією (Архітектура B)
Застосовуємо чотири контрзаходи:
1. Вимикаємо порт `9090`, адмін-методи переносимо на захищений локальний сокет Unix `/run/telemetry/admin.sock` з перевіркою mTLS та прав `root` (`AR = 4`).
2. Основний мережевий парсер виносимо в непривілейований процес `UID nobody` (`DP = 2`), обмежений фільтром Seccomp-BPF та просторами імен (мережевий і монтування).
3. Публічний сокет залишаємо лише на порту `8080`, вхідні дані валідуються за суворою схемою FlatBuffers фіксованої довжини.
4. Конфігураційний файл монтується в режимі Read-Only (`DP = 1`).

Обчислення ваг компонентів Архітектури B:

```
S_M(B)
= 4 · (DP=2 / AR=1) + 2 · (DP=1 / AR=1) + 2 · (DP=2 / AR=4)  [парсер nobody + адмін через сокет]
= 4 · 2.0 + 2 · 1.0 + 2 · 0.5                                 [підстановка часток]
= 8.0 + 2.0 + 1.0                                             [множення]
= 11.0

S_C(B)
= (DP=2 / AR=1) + (DP=2 / AR=4) + 0                           [порт 8080 (nobody) + unix-сокет]
= 2.0 + 0.5 + 0.0                                             [підстановка часток]
= 2.5

S_D(B)
= (DP=1 / AR=1) + (DP=1 / AR=4)                               [типізований буфер та RO конфіг]
= 1.0 + 0.25                                                  [підстановка часток]
= 1.25

S_total(B)
= S_M(B) + S_C(B) + S_D(B)
= 11.0 + 2.5 + 1.25
= 14.75
```

### 5.3. Кількісне порівняння та висновок

Обчислюємо коефіцієнт зменшення поверхні атаки `R_AS`:

```
R_AS
= (S_total(A) - S_total(B)) / S_total(A)
= (40.0 - 14.75) / 40.0
= 25.25 / 40.0
= 0.63125  [63.1%]
```

Архітектурні зміни без видалення жодної корисної бізнес-функції скоротили формальну поверхню атаки системи на 63.1%. Зниження досягнуто не за рахунок «виправлення багів у парсері», а за рахунок радикального зменшення потенціалу шкоди `DP` та підняття бар'єра доступу `AR` для чутливих компонентів.
