# 📋 Специфікація RFC 9116: синтаксис, поля та правила валідації security.txt

Файл `security.txt` визначає машинно-читабельний та зручний для людини текстовий формат, за допомогою якого організації публікують контактні дані служб безпеки, криптографічні ключі та правила координації розкриття вразливостей. Стандарт RFC 9116 розв'язує фундаментальну проблему розвідки: зовнішній дослідник або користувач, що виявив дефект, не повинен шукати контакти інженерів через загальні форми підтримки чи соціальні мережі. Нижче наведено повну довідку директив, вимог до форматування, цифрового підпису та правил безпечного обслуговування файлу веб-серверами й вбудованими пристроями.

---

## 1. Синтаксис і структура файлу

Файл `security.txt` має простий лінійно-орієнтований синтаксис. Кожен рядок містить одну директиву у форматі `Ім'я-Поля: Значення` або коментар.

```text
security-txt-file = *( directive / comment / empty-line )
directive         = field-name ":" [SP] field-value [SP] CRLF
comment           = "#" *VCHAR CRLF
empty-line        = CRLF
```

### 1.1. Базові синтаксичні вимоги

- **Кодування**: виключно UTF-8 без мітки порядку байтів (BOM, Byte Order Mark).
- **Символи кінця рядка**: стандарт вимагає послідовність `CRLF` (`\r\n`), однак сумісні парсери зобов'язані коректно обробляти поодинокий символ `LF` (`\n`).
- **Регістронезалежність**: назви директив (Field Names) не чутливі до регістру (`contact:`, `Contact:` та `CONTACT:` є еквівалентними).
- **Пробіли**: перед двокрапкою пробіли заборонені; після двокрапки дозволено один або кілька символів пробілу або табуляції.
- **Коментарі**: починаються з символу `#` і тривають до кінця рядка. Парсери повинні ігнорувати коментарі та порожні рядки.

## 2. Перелік і опис директив

Специфікація RFC 9116 класифікує поля на обов'язкові та опційні. Файл вважається недійсним, якщо в ньому відсутня хоча б одна обов'язкова директива.

| Директива | Статус | Допустима кількість | Формат значення | Призначення |
| :--- | :--- | :--- | :--- | :--- |
| `Contact` | **Обов'язкова** | 1..N | URI (`mailto:`, `https:`, `tel:`) | Прямий канал для надсилання звіту про вразливість. |
| `Expires` | **Обов'язкова** | Рівно 1 | Дата/час за RFC 3339 / ISO 8601 | Момент закінчення терміну дії інформації у файлі. |
| `Encryption` | Опційна | 0..N | URI (`https:`, `openpgpkey:`) | Посилання на публічний PGP/GPG-ключ команди безпеки. |
| `Canonical` | Опційна | 0..N | URI (`https:`) | Канонічна адреса розміщення даного файлу. |
| `Policy` | Опційна | 0..N | URI (`https:`) | Посилання на політику розкриття вразливостей (VDP). |
| `Acknowledgments` | Опційна | 0..N | URI (`https:`) | Посилання на дошку пошани дослідників (Hall of Fame). |
| `Preferred-Languages`| Опційна | 0..1 | Спискові мовні теги RFC 5646 | Перелік підтримуваних мов спілкування (через кому). |
| `Hiring` | Опційна | 0..N | URI (`https:`) | Посилання на вакансії підрозділу кібербезпеки. |
| `CSAF` | Опційна | 0..N | URI (`https:`) | Посилання на постачальника бюлетенів CSAF (RFC 9116 §2.5.2). |

## 3. Детальний розбір директив

### 3.1. `Contact` (Обов'язкова)

Визначає адресу або веб-ресурс для первинного прийому репортів. Якщо вказано кілька директив `Contact`, вони інтерпретуються в порядку спадання пріоритету (перша — найбільш бажана).

```text
Contact: mailto:security@example.com
Contact: https://hackerone.com/example_corp
Contact: tel:+1-800-555-0199
```

- Схема `mailto:` повинна вказувати на функціональну скриньку групи реагування (PSIRT/SIRT), а не на персональну пошту співробітника.
- Схема `https:` повинна вести на захищену веб-форму подання або сторінку програми на платформі Bug Bounty.
- Схема `tel:` застосовується як резервний екстрений канал (наприклад, цілодобовий черговий SOC).

### 3.2. `Expires` (Обов'язкова)

Запобігає використанню застарілих контактних даних та занедбаних політик розкриття. Значення має суворо відповідати профілю RFC 3339 (підмножина ISO 8601) і вказувати час у нульовому часовому поясі UTC (суфікс `Z`).

```text
Expires: 2027-06-30T23:59:59.000Z
```

- **Правило парсера**: якщо поточний системний час перевищує дату `Expires`, клієнт зобов'язаний вважати файл недійсним і попередити користувача або зупинити автоматизовану обробку.
- **Рекомендований інтервал**: дата закінчення дії не повинна перевищувати 1 рік від моменту генерації чи підпису файлу. Оптимальний цикл оновлення — від 3 до 6 місяців.

### 3.3. `Encryption` (Опційна)

Вказує на криптографічний відкритий ключ, який дослідники мають використовувати для шифрування конфіденційної інформації (Proof of Concept, експлойти, трасування пам'яті).

```text
Encryption: https://example.com/keys/pgp-security-key.asc
Encryption: openpgpkey:security@example.com
Encryption: dns:openpgpkey.example.com?type=OPENPGPKEY
```

- Посилання `https:` має повертати текстовий ASCII-броньований ключ стандарту OpenPGP (RFC 4880 / RFC 9580) або сертифікат X.509.
- Заборонено посилатися на сторонні неперевірені публічні сервери ключів через незахищені протоколи (наприклад, HTTP або незашифрований HKP).

### 3.4. `Canonical` (Опційна)

Містить точну абсолютну URL-адресу, де цей файл повинен бути розташований на легітимному сервері.

```text
Canonical: https://example.com/.well-known/security.txt
```

- **Захист від підміни**: запобігає маніпуляціям, коли вміст `security.txt` копіюється на дзеркала, CDN або фішингові домени.
- Якщо URL у директиві `Canonical` не збігається з адресою, з якої завантажено файл, автоматизовані інструменти повинні відхилити файл як потенційно підроблений.

### 3.5. `Policy` (Опційна)

Вказує на документ політики розкриття вразливостей (Vulnerability Disclosure Policy — VDP) або правила програми винагород.

```text
Policy: https://example.com/security/vulnerability-disclosure-policy
```

- Сторінка політики повинна містити опис обсягу тестування (In-Scope / Out-of-Scope), умови правового захисту дослідника (Safe Harbor) та шкалу строків усунення недоліків (SLA).

### 3.6. `Preferred-Languages` (Опційна)

Повідомляє дослідникам, якими природними мовами команда безпеки здатна приймати та оперативно опрацьовувати звіти.

```text
Preferred-Languages: uk, en, pl
```

- Значення є списком мовних кодів BCP 47 (RFC 5646), розділених комами.
- Перша мова у списку є основною (дефолтною).

## 4. Цифровий підпис та цілісність (Cleartext OpenPGP)

Для запобігання підміні контактів зловмисником під час атак типу Man-in-the-Middle або компрометації кешу веб-сервера RFC 9116 настійно рекомендує підписувати файл `security.txt` за допомогою відкритого стандарту OpenPGP Cleartext Signature (RFC 4880 / RFC 9580).

### 4.1. Канонічний вигляд підписаного файлу

```text
-----BEGIN PGP SIGNED MESSAGE-----
Hash: SHA512

Contact: mailto:security@example.com
Contact: https://example.com/security/report
Expires: 2027-01-01T00:00:00.000Z
Encryption: https://example.com/keys/security-pgp.asc
Canonical: https://example.com/.well-known/security.txt
Policy: https://example.com/security/policy
Acknowledgments: https://example.com/security/hall-of-fame
Preferred-Languages: uk, en

-----BEGIN PGP SIGNATURE-----

iQIzBAEBCgAdFiEEf8X2gJz0k...
...
-----END PGP SIGNATURE-----
```

### 4.2. Правила перевірки підпису

1. Парсер відокремлює тіло повідомлення між заголовком `Hash:` та початком блоку `-----BEGIN PGP SIGNATURE-----`.
2. Видаляються службові екрануючі дефіси `- -` на початку рядків (Dash-Escaping), якщо вони були додані генератором PGP.
3. Обчислюється геш SHA-512 або SHA-256 від тексту із нормалізацією кінців рядків до `CRLF`.
4. Підпис верифікується за відкритим ключем команди, зазначеним у директиві `Encryption` або отриманим через авторитетний DNS-запис `OPENPGPKEY`.

## 5. Розміщення, маршрутизація та обслуговування

Стандарт встановлює суворі вимоги до мережевого розміщення файлу:

### 5.1. Канонічний шлях та зворотна сумісність

1. **Основне розташування**: `https://<домен>/.well-known/security.txt` (згідно зі стандартом реєстрації уніфікованих суфіксів RFC 8615).
2. **Резервне розташування (Legacy)**: `https://<домен>/security.txt`. Якщо файл відсутній у теці `/.well-known/`, клієнт може спробувати завантажити його з кореня домену.

### 5.2. Вимоги до протоколу HTTP/HTTPS

- **Лише HTTPS**: клієнти зобов'язані ігнорувати файл `security.txt`, завантажений через незахищений протокол HTTP, оскільки незашифрований канал дозволяє підмінити контакти безпеки на адреси зловмисника.
- **MIME-тип**: сервер повинен повертати заголовок `Content-Type: text/plain; charset=utf-8`.
- **Перенаправлення (Redirects)**: дозволені лише постійні перенаправлення (HTTP 301/308) на HTTPS у межах того самого домену або на офіційний портал прийому звітів, явно зазначений у сертифікаті TLS. Заборонено циклічні або ланцюгові редиректи через понад 2 переходи.
- **Заголовки кешування**: рекомендується встановлювати заголовок `Cache-Control: max-age=86400, must-revalidate` (не більше доби), щоб оновлення ключів і строків швидко доходили до сканерів.

### 5.3. Розміщення у вбудованих системах та прошивках IoT

Для автономних пристроїв, маршрутизаторів та промислових контролерів файл `security.txt` інтегрується безпосередньо в кореневу файлову систему образу прошивки:

- `/etc/security.txt` або `/usr/share/security/security.txt` — у Linux-подібних ОС.
- Віддається локальним вбудованим веб-сервером за адресою `http://192.168.1.1/.well-known/security.txt` (або через mTLS/HTTPS).
- Додатково вшивається у поле опису дескриптора USB/BLE (Device Information Service) у вигляді рядка з URI до хмарного `security.txt` виробника.
