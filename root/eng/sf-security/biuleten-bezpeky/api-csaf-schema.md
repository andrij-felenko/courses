# 📋 Специфікація схеми CSAF 2.0: поля, зв'язки та інваріанти

Стандарт CSAF 2.0 (Common Security Advisory Framework), затверджений консорціумом OASIS, визначає сувору структуру JSON-документа для публікації безпекових повідомлень. Головний профіль стандарту — `csaf_security_advisory` — призначений для опису вразливостей, їхнього оцінювання, ідентифікації зачеплених продуктів та публікації інструкцій з оновлення та пом'якшення.

Усі об'єкти документа зв'язані суворими внутрішніми посиланнями: будь-який програмний продукт, згаданий у секції вразливостей або виправлень, повинен мати формальне оголошення в дереві продуктів. Будь-яка суперечність між ідентифікаторами робить бюлетень невалідним і блокує його автоматичну обробку сканерами безпеки.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            CSAF 2.0 Document Root                           │
├────────────────────────┬────────────────────────────┬───────────────────────┤
│       document         │        product_tree        │    vulnerabilities    │
│  (Метадані видавця,    │ (Ієрархія компонентів,     │ (Описи CVE, бали CVSS,│
│  версії, трекінг)      │  ідентифікатори CPE, PURL) │  статуси та латки)    │
└────────────────────────┴────────────────────────────┴───────────────────────┘
```

## 1. Секція метаданих документа: `document`

Секція `document` містить юридично значущу інформацію про автора бюлетеня, його контактні дані, криптографічні реквізити, категорію документа та повну історію ревізій. Вона встановлює межі автентичності: сканер безпеки насамперед перевіряє видавця (`publisher`) та стан життєвого циклу повідомлення (`tracking.status`).

Видавець зобов'язаний вказати свій простір імен `namespace` у форматі канонічного вебдомену. Це запобігає підміні бюлетенів сторонніми суб'єктами: автоматизовані системи довіряють повідомленням лише тоді, коли `namespace` збігається з доменом завантаження або криптографічним сертифікатом ключа підпису.

```json
{
  "document": {
    "category": "csaf_security_advisory",
    "csaf_version": "2.0",
    "title": "Критичне переповнення буфера в службі TLS-термінації",
    "publisher": {
      "category": "vendor",
      "name": "Acme Cyber Systems PSIRT",
      "namespace": "https://security.acme.example.com",
      "contact_details": "psirt@acme.example.com, OpenPGP Key ID: 0x9B8A7C6D"
    },
    "tracking": {
      "id": "ACME-SA-2024-0042",
      "status": "final",
      "version": "1.0.0",
      "initial_release_date": "2024-04-12T08:00:00.000Z",
      "current_release_date": "2024-04-12T08:00:00.000Z",
      "generator": {
        "engine": {
          "name": "Acme Advisory Pipeline",
          "version": "2.4.1"
        }
      },
      "revision_history": [
        {
          "number": "1.0.0",
          "date": "2024-04-12T08:00:00.000Z",
          "summary": "Початковий офіційний реліз із виправленням"
        }
      ]
    },
    "notes": [
      {
        "category": "summary",
        "title": "Загальний огляд",
        "text": "Виявлено вразливість запису за межі виділеного буфера у компоненті парсингу сертифікатів X.509."
      }
    ]
  }
}
```

Блок відстеження `tracking` керує версіонуванням бюлетеня. Якщо після первинної публікації виявляються додаткові зачеплені версії продукту, видавець оновлює версію документа за правилами семантичного версіонування (наприклад, з `1.0.0` на `1.1.0`), фіксує нову дату в `current_release_date` та додає запис до масиву `revision_history`. При цьому первинна дата `initial_release_date` залишається незмінною протягом усього життєвого циклу.

| Поле | Тип | Обов'язкове | Призначення та інваріанти |
|---|---|---|---|
| `category` | `string` | Так | Профіль документа: `csaf_base`, `csaf_security_advisory`, `csaf_vex`, `csaf_informational_advisory`. |
| `csaf_version` | `string` | Так | Значення суворо `"2.0"`. |
| `title` | `string` | Так | Лаконічний людськочитний заголовок бюлетеня. |
| `publisher.category` | `string` | Так | Роль видавця: `vendor`, `coordinator`, `discoverer`, `other`. |
| `publisher.namespace` | `string` (URI) | Так | Канонічний вебдомен або URI вендора. |
| `tracking.id` | `string` | Так | Унікальний ідентифікатор бюлетеня в системі вендора (наприклад, `RHSA-2024:1234`). |
| `tracking.status` | `string` | Так | Життєвий цикл: `draft`, `interim`, `final`. |
| `tracking.version` | `string` | Так | Номер версії документа у форматі семантичного версіонування (наприклад, `1.0.0`). |
| `tracking.revision_history` | `array` | Так | Масив об'єктів ревізій із полями `number`, `date`, `summary`. |

## 2. Дерево продуктів: `product_tree`

Секція `product_tree` будує нормалізовану ієрархію програмних та апаратних засобів, які згадуються в бюлетені. Замість хаотичних текстових назв стандарт вимагає розділення продуктів на ієрархічні гілки (`branches`) за категоріями: виробник (`vendor`), родина продуктів (`product_family`), назва виробу (`product_name`) та конкретна версія (`product_version`).

Кожен кінцевий листок дерева отримує унікальний ідентифікатор `product_id`. Цей токен є внутрішнім ключем документа. Для зв'язку зі зовнішнім світом стандарт використовує об'єкт `product_identification_helper`, який містить два типи глобальних ідентифікаторів:
- Рядок CPE 2.3 (Common Platform Enumeration), наприклад `cpe:2.3:a:acme:secure_gateway:3.2.0:*:*:*:*:*:*:*`. Він використовується традиційними сканерами вразливостей операційних систем.
- Посилання Package URL (PURL), наприклад `pkg:deb/debian/acme-gateway@3.2.0` або `pkg:npm/express@4.18.2`. PURL забезпечує точне зіставлення в сучасних контейнерах, бекенд-сервісах та конвеєрах залежностей.

```json
{
  "product_tree": {
    "branches": [
      {
        "category": "vendor",
        "name": "Acme",
        "branches": [
          {
            "category": "product_name",
            "name": "Acme Secure Gateway",
            "branches": [
              {
                "category": "product_version",
                "name": "3.2.0",
                "product": {
                  "name": "Acme Secure Gateway 3.2.0",
                  "product_id": "CSAFPID-ACME-GW-320",
                  "product_identification_helper": {
                    "cpe": "cpe:2.3:a:acme:secure_gateway:3.2.0:*:*:*:*:*:*:*",
                    "purl": "pkg:deb/debian/acme-gateway@3.2.0"
                  }
                }
              },
              {
                "category": "product_version",
                "name": "3.2.1",
                "product": {
                  "name": "Acme Secure Gateway 3.2.1 (Patched)",
                  "product_id": "CSAFPID-ACME-GW-321",
                  "product_identification_helper": {
                    "cpe": "cpe:2.3:a:acme:secure_gateway:3.2.1:*:*:*:*:*:*:*",
                    "purl": "pkg:deb/debian/acme-gateway@3.2.1"
                  }
                }
              }
            ]
          }
        ]
      }
    ],
    "relationships": [
      {
        "category": "default_component_of",
        "full_product_name": {
          "name": "Модуль TLS у складі Gateway 3.2.0",
          "product_id": "CSAFPID-REL-TLS-GW-320"
        },
        "product_reference": "CSAFPID-MOD-TLS-100",
        "relates_to_product_reference": "CSAFPID-ACME-GW-320"
      }
    ]
  }
}
```

Секція взаємозв'язків `relationships` дозволяє описати складні архітектурні залежності. Наприклад, категорія `default_component_of` позначає вбудовану бібліотеку, `installed_on` — прив'язку пакета до конкретної версії операційної системи, а `depends_on` — динамічну залежність. Завдяки цьому бюлетень може вказати, що вразливість стосується модуля лише тоді, коли він розгорнутий на певній базовій платформі.

| Поле | Тип | Призначення та формат |
|---|---|---|
| `branches` | `array` | Деревовидна класифікація продуктів: вендор → родина → назва → версія. |
| `branches[].category` | `string` | Категорія вузла: `vendor`, `product_family`, `product_name`, `product_version`, `architecture`, `host_name`, `service_name`. |
| `product.product_id` | `string` | Унікальний токен продукту в межах даного документа (наприклад, `CSAFPID-0001`). Не повинен містити пробілів. |
| `product_identification_helper.cpe` | `string` | Рядок ідентифікатора у форматі CPE 2.3 (наприклад, `cpe:2.3:a:...`). |
| `product_identification_helper.purl` | `string` | Універсальне посилання на пакет за стандартом Package URL (наприклад, `pkg:npm/...`). |
| `relationships` | `array` | Зв'язки між продуктами: `is_part_of`, `installed_on`, `depends_on`, `default_component_of`. |

## 3. Секція вразливостей: `vulnerabilities`

Секція `vulnerabilities` містить технічні дефекти, зафіксовані в бюлетені. Один бюлетень може об'єднувати кілька пов'язаних вразливостей, кожна з яких має власний ідентифікатор CVE, класифікацію CWE та вектор CVSS.

Головна функція секції — пов'язати кожен дефект із продуктовими ідентифікаторами через об'єкт `product_status`. Стандарт вимагає точного розподілу продуктів за категоріями:
- `known_affected` — перелік продуктів, у яких наявність дефекту підтверджена вендором;
- `fixed` — версії, у яких дефект усунуто;
- `known_not_affected` — продукти, які перевірені та визнані безпечними;
- `under_investigation` — продукти, стан яких наразі досліджується лабораторією вендора.

```json
{
  "vulnerabilities": [
    {
      "cve": "CVE-2024-99999",
      "title": "Віддалене виконання коду через переповнення буфера в парсері X.509",
      "cwe": {
        "id": "CWE-787",
        "name": "Out-of-bounds Write"
      },
      "notes": [
        {
          "category": "description",
          "title": "Технічний опис вади",
          "text": "Функція parse_extension_asn1() не перевіряє довжину субполя під час обробки нетипових OID, що призводить до перезапису пам'яті стека."
        }
      ],
      "scores": [
        {
          "cvss_v3": {
            "version": "3.1",
            "vectorString": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H",
            "baseScore": 9.8,
            "baseSeverity": "CRITICAL"
          }
        }
      ],
      "product_status": {
        "known_affected": [
          "CSAFPID-ACME-GW-320"
        ],
        "fixed": [
          "CSAFPID-ACME-GW-321"
        ]
      },
      "remediations": [
        {
          "category": "vendor_fix",
          "details": "Оновіть пакет acme-gateway до версії 3.2.1 або новішої за допомогою штатного менеджера пакетів.",
          "product_ids": [
            "CSAFPID-ACME-GW-320"
          ],
          "url": "https://repo.acme.example.com/security/pool/acme-gateway_3.2.1_amd64.deb",
          "restart_required": {
            "category": "service",
            "details": "Потрібен перезапуск демона acme-gatewayd після оновлення бінарних файлів."
          }
        },
        {
          "category": "workaround",
          "details": "Якщо негайне оновлення неможливе, вимкніть підтримку клієнтських сертифікатів у файлі /etc/acme/gateway.conf, встановивши client_cert_validation = none.",
          "product_ids": [
            "CSAFPID-ACME-GW-320"
          ]
        }
      ]
    }
  ]
}
```

Секція `remediations` формує конкретні вказівки для захисника. Вона обов'язково класифікує дію за категорією:
- `vendor_fix` — офіційний реліз виправленого пакета, прошивки або патча;
- `workaround` — конфігураційна зміна без зміни коду (наприклад, вимкнення функції чи блокування порту);
- `mitigation` — дія на зовнішньому захисному контурі (наприклад, активація сигнатури на міжмережевому екрані чи WAF);
- `none_available` — фіксація факту відсутності рішення (Zero-Day або припинення життєвого циклу продукту).

Поле `restart_required` сигналізує автоматизованим системам про характер впливу на експлуатацію: `service` (перезапуск демона), `system` (перезавантаження всієї ОС), `machine` (апаратне вимкнення живлення) або `none`.

| Поле | Тип | Обов'язкове | Призначення |
|---|---|---|---|
| `cve` | `string` | Ні | Офіційний ідентифікатор у форматі `CVE-YYYY-NNNNN`. |
| `cwe.id` | `string` | Ні | Ідентифікатор дефекту у словнику CWE (наприклад, `CWE-787`, `CWE-89`). |
| `scores` | `array` | Так | Масив оцінок: об'єкти `cvss_v2`, `cvss_v3` (з `vectorString` та `baseScore`) або `cvss_v4`. |
| `product_status` | `object` | Так | Відображення `product_id` на списки: `known_affected`, `fixed`, `known_not_affected`, `first_affected`, `last_affected`. |
| `remediations` | `array` | Так | Масив дій: категорія (`vendor_fix`, `workaround`, `mitigation`, `none_available`), детальний текст, список `product_ids`, посилання на патч `url`. |
| `flags` | `array` | Ні | Машинні мітки для VEX-профілів (`component_not_present`, `inline_mitigations_already_exist`). |

## 4. П'ять офіційних профілів CSAF 2.0

Специфікація стандарту визначає п'ять функціональних профілів залежно від мети публікації:

1. **CSAF Base.** Мінімальний профіль, що вимагає лише заповнення базових метаданих `document`. Використовується як фундамент для розширення.
2. **Security Advisory (`csaf_security_advisory`).** Повноцінний безпековий бюлетень. Вимагає обов'язкової наявності дерева продуктів `product_tree`, щонайменше однієї вразливості у `vulnerabilities` із визначеними `product_status` та хоча б однієї інструкції виправлення `remediations`.
3. **VEX (`csaf_vex`).** Документ обміну статусами експлуатабельності. Використовується для зняття хибнопозитивних тривог сканерів SBOM. Вимагає обов'язкового зазначення обґрунтування безпеки у полі `justification` для всіх продуктів зі статусом `known_not_affected`.
4. **Informational Advisory (`csaf_informational_advisory`).** Інформаційне повідомлення про загальні проблеми захисту, архітектурні зміни або відкликання сертифікатів без прив'язки до конкретного CVE.
5. **Security Incident Response (`csaf_security_incident_response`).** Екстрене сповіщення про інцидент безпеки, що триває в реальному часі, з індикаторами компрометації (IoC) та оперативними заходами реагування.

## 5. Дистрибуція та криптографічна автентифікація

Для автоматичного виявлення бюлетенів вендор розміщує у корені свого захищеного вебсайту маніфест постачальника за стандартною адресою:

```
https://security.acme.example.com/.well-known/csaf/provider-metadata.json
```

Цей маніфест описує публічні ключі OpenPGP видавця, URL-адреси каталогів збереження файлів бюлетенів та канали синхронізації ROLIE (Resource-Oriented Lightweight Information Exchange, RFC 8322). Кожен JSON-файл бюлетеня супроводжується окремим файлом відкріпленого цифрового підпису `.json.asc` та файлом контрольної суми `.json.sha256`.

## 6. Обов'язкові структурні інваріанти схеми

Специфікація CSAF 2.0 встановлює набір логічних правил валідації, порушення яких робить документ невалідним і призводить до відхилення валідаторами:

1. **Цілісність продуктових посилань (Product Reference Integrity).** Кожен рядок `product_id`, використаний у `product_status`, `remediations` або `threats`, зобов'язаний бути попередньо оголошеним у гілках `product_tree.branches` або списку `product_tree.full_product_names`. Використання неоголошеного ідентифікатора є фатальною помилкою.
2. **Унікальність ідентифікаторів.** Усі значення `product_id` у межах одного документа повинні бути абсолютно унікальними. Заборонено повторно використовувати один і той самий токен для різних версій чи збірок.
3. **Узгодженість CVSS-вектора.** Поля `baseScore` та `baseSeverity` повинні математично точно відповідати вектору `vectorString`. Ручна зміна балу без оновлення компонентів метрики вважається фальсифікацією даних.
4. **Несуперечливість статусів.** Один і той самий `product_id` не може одночасно входити до масивів `known_affected` та `known_not_affected` в межах однієї вразливості. Продукт або вразливий, або ні.
5. **Хронологічна послідовність дат.** Значення `current_release_date` не може передувати `initial_release_date`. Дата кожної наступної ревізії в `revision_history` повинна бути строго більшою або рівною даті попередньої ревізії.
