# 📜 Від черв'яка Морріса до CSAF: еволюція бюлетенів безпеки

У листопаді 1988 року черв'як Роберта Морріса паралізував близько десяти відсотків усіх комп'ютерів, підключених до мережі ARPANET та раннього Інтернету. Системні адміністратори університетів і військових лабораторій намагалися зупинити епідемію, обмінюючись уривчастими порадами через телефонні дзвінки та хаотичні дописи в телеконференціях Usenet. Поради часто виявлялися помилковими, код сумнівних латок публікувався без жодної перевірки автентичності, а спроби заблокувати переповнення буфера в службі `fingerd` чи лазівку в `sendmail` призводили до повної відмови поштових серверів.

Хаос навколо інциденту змусив Агентство передових оборонних дослідницьких проєктів США (DARPA) профінансувати створення Координаційного центру CERT (англ. *Computer Emergency Response Team Coordination Center*, CERT/CC) при Інституті програмної інженерії Університету Карнегі — Меллон. Головним завданням новоствореної структури стала розробка стандартизованого каналу екстреного сповіщення — офіційного бюлетеня безпеки (англ. *Security Advisory*).

```
+-----------------------------------------------------------------------------+
| CERT Advisory CA-1988-01                                                    |
| December 1, 1988                                                            |
| FTAMD Vulnerability                                                         |
|                                                                             |
| A vulnerability has been discovered in the FTAMD file transfer program.     |
| Attackers can gain unauthorized root access by exploiting an unchecked      |
| buffer in the argument parsing routine.                                     |
|                                                                             |
| Impact: Root compromise.                                                    |
| Affected Systems: SunOS 3.5, BSD 4.3.                                       |
| Workaround: Disable ftamd in /etc/inetd.conf and kill -HUP <inetd_pid>.     |
| Fix: Apply vendor patch #1042-01 or update to SunOS 4.0.                    |
+-----------------------------------------------------------------------------+
```

## Епоха поштових бюлетенів RFC 822

Перші бюлетені CERT публікувалися у вигляді простих текстових повідомлень у форматі поштового стандарту RFC 822. Кожен документ мав фіксовану текстову структуру: ідентифікатор бюлетеня (наприклад, `CA-1988-01`), дату публікації, стислий опис проблеми, список зачеплених операційних систем, інструкцію з тимчасового вимкнення вразливого демона та посилання на патч.

З появою криптографічного пакета PGP у 1991 році тексти бюлетенів почали підписувати цифровим підписом. Це розв'язало критичну проблему фальсифікації: зловмисники більше не могли розіслати фальшиве «оновлення» від імені координаційного центру, яке містило б бекдор.

У середині 1990-х років розвиток культури повного розкриття (англ. *Full Disclosure*) та поява списку розсилки Bugtraq кардинально змінили баланс сил. Якщо CERT/CC дотримувався консервативної політики узгодженого розкриття і міг готувати бюлетень тижнями, то незалежні дослідники на Bugtraq викладали описи вад разом із готовими програмами експлуатації (англ. *Proof of Concept*, PoC). Вендори програмного забезпечення опинилися перед необхідністю створювати власні команди реагування (англ. *Product Security Incident Response Team*, PSIRT) та самостійно випускати бюлетені, не чекаючи публікацій сторонніх координаторів.

## Криза неструктурованого тексту

На початку 2000-х років масштаби інформаційних систем зросли на кілька порядків. Корпоративний парк серверів налічував тисячі вузлів із сотнями різноманітних програмних пакетів. Ручне читання текстових листів інженерами безпеки стало неможливим з кількох технічних причин:

1. **Неоднозначність назв продуктів.** Один вендор писав `Enterprise Linux 4`, інший — `RHEL-4.0-AS`, третій — `Red Hat EL v.4`. Скрипти автоматичного розбору не могли надійно зіставити текст із базою інвентаризації.
2. **Невизначеність діапазонів версій.** Фрази на кшталт «вразливі версії до 2.4.1 включно, крім збірок для архітектури SPARC» вимагали суб'єктивної інтерпретації людиною.
3. **Відсутність єдиної оцінки шкоди.** Кожен виробник використовував власну суб'єктивну шкалу тривожності («High», «Critical», «Important»), що заважало пріоритезації інцидентів.

Поява Словника загальновідомих вразливостей (англ. *Common Vulnerabilities and Exposures*, CVE) у 1999 році та Загальної системи оцінювання вразливостей (англ. *Common Vulnerability Scoring System*, CVSS) у 2005 році заклала фундамент для уніфікації. Проте самі бюлетені все ще залишалися текстами на вебсторінках або PDF-документами.

## Поява CVRF та XML-схем

У 2011 році консорціум ICASI (англ. *Industry Consortium for Advanced Program Interoperability*), до якого увійшли Cisco, Microsoft, IBM, Juniper Networks, HP та Oracle, створив стандарт CVRF 1.1 (англ. *Common Vulnerability Reporting Framework*).

CVRF став першою спробою перевести весь зміст бюлетеня безпеки у суворо валідований XML-документ. Стандарт визначив обов'язкові сутності:
- дерево продуктів (англ. *Product Tree*) з використанням єдиних назв платформ CPE (англ. *Common Platform Enumeration*);
- блоки вразливостей із прямим зв'язком між ідентифікатором CVE, балом CVSS та конкретними ідентифікаторами вузлів продуктового дерева;
- категоризовані секції засобів виправлення (англ. *Remediations*) з розрізненням офіційного патча (`vendor_fix`), тимчасового обходу (`workaround`) та пом'якшення (`mitigation`).

Попри структурну повноту, CVRF страждав від громіздкості XML-схем, складності мапування транзитивних залежностей та відсутності стандартизованого протоколу публікації та автоматичного завантаження файлів клієнтами.

## Народження стандарту CSAF 2.0

У 2017 році розвиток стандарту перейшов під егіду організації зі стандартизації OASIS Open (технічний комітет *CSAF Technical Committee*). Результатом п'ятирічної роботи став випуск у листопаді 2022 року стандарту CSAF 2.0 (англ. *Common Security Advisory Framework*).

CSAF 2.0 повністю відмовився від XML на користь стандарту JSON Schema. Архітектура стандарту врахувала реалії сучасних конвеєрів безперервної інтеграції та хмарних розгортань:
- **Універсальна ідентифікація пакетів.** До класичних рядків CPE 2.3 додано підтримку універсальних посилань на пакети PURL (англ. *Package URL*), що дозволило однозначно посилатися на бібліотеки в екосистемах `npm`, `PyPI`, `crates.io`, `Maven` та `Go`.
- **Суворі профілі документів.** Стандарт увів п'ять чітко розмежованих профілів (від базового інформаційного повідомлення до повноцінного бюлетеня з матрицею експлуатації VEX).
- **Стандартизована дистрибуція.** Специфікація закріпила обов'язковий протокол виявлення бюлетенів через `provider-metadata.json` за фіксованим URL `.well-known/csaf/provider-metadata.json`, підпис за стандартом OpenPGP та дзеркалювання через агрегатори ROLIE (RFC 8322).

Сучасний бюлетень безпеки остаточно перетворився з поштового листа для системного адміністратора на машинночитний інженерний API, який споживають сканери вразливостей, системи управління конфігураціями та автоматизовані оркестратори оновлень.
