# 🔌 Формати розкриття вразливостей: CSAF 2.0, VEX та OSV

Організація, яка експлуатує сучасну цифрову інфраструктуру, щодня отримує повідомлення про сотні виявлених дефектів. Проте завдання виробника операційної системи, постачальника хмарного сервісу (SaaS) та розробника відкритої бібліотеки кардинально різняться. Виробнику ОС необхідно надати вичерпний бюлетень із бінарними латками для десятків підтримуваних релізів; SaaS-провайдеру — швидко спростувати наявність небезпеки для клієнтів, пояснивши, що вразливий транзитивний компонент не викликається в коді; а мейнтейнеру опенсорс-пакета — зафіксувати точний коміт виправлення в репозиторії.

Для цих завдань в індустрії безпеки сформувалися три головні відкриті машинночитні формати: CSAF 2.0 (Common Security Advisory Framework), VEX (Vulnerability Exploitability eXchange) та OSV (Open Source Vulnerabilities).

## CSAF 2.0: Енциклопедія корпоративного вендора

Стандарт CSAF 2.0 розроблений технічним комітетом OASIS як універсальний формат для публікації безпекових бюлетенів вендорів будь-якого масштабу. Він є найдетальнішим і найповнішим серед усіх наявних форматів.

Головні характеристики CSAF 2.0:
- **Повна контекстна модель.** Один документ описує одразу кілька пов'язаних CVE, їхні класи CWE, вектори CVSS різних версій, ступінь загрози, інструкції зі встановлення оновлень та детальні тимчасові заходи.
- **Ієрархічне дерево продуктів.** Підтримує складні взаємозв'язки між програмними компонентами (`is_part_of`, `installed_on`, `depends_on`), дозволяючи пов'язувати один патч із сотнями модифікацій дистрибутива.
- **Багатопрофільність.** Специфікація визначає профілі: від загального інформаційного оголошення (`csaf_informational_advisory`) до повноцінного бюлетеня безпеки (`csaf_security_advisory`) та окремого документа експлуатабельності VEX (`csaf_vex`).
- **Транспортна інтеграція.** Вимагає розміщення індексу `provider-metadata.json`, криптографічних підписів OpenPGP і підтримує агрегацію через RSS/Atom і протокол ROLIE.

Головним недоліком CSAF 2.0 є його висока структурна складність: генерація валідного JSON-файлу вимагає від видавця наявності повної та точної інвентарної бази всіх продуктів і версій.

## VEX: Статус експлуатабельності у ланцюгу постачання

Формат VEX (Vulnerability Exploitability eXchange) створений як відповідь на «шум» від сканування специфікацій програмного забезпечення SBOM (англ. *Software Bill of Materials*). Якщо сканер виявляє у складі контейнера вразливу бібліотеку `log4j`, адміністратор бачить критичну загрозу. Проте якщо у скомпільованому додатку ніколи не ініціалізується клас `JndiLookup`, вразливість фізично недосяжна (англ. *unreachable*).

VEX існує у трьох варіантах реалізації: профіль `csaf_vex` у стандарті CSAF, розширення формату CycloneDX, а також мінімалістичний JSON-LD стандарт OpenVEX.

Ключова мета VEX — машинно повідомити один із чотирьох статусів для конкретного продукту:
1. `not_affected` — продукт не зачеплено (з обов'язковим зазначенням технічного обґрунтування: `component_not_present`, `code_not_present`, `code_not_reachable`, `inline_mitigations_already_exist`);
2. `affected` — продукт дійсно вразливий, потрібні дії захисника;
3. `fixed` — дефект усунуто у вказаній версії;
4. `under_investigation` — вендор досліджує проблему і надасть деталі пізніше.

VEX не містить докладних описів природи дефекту чи інструкцій компіляції: це швидкий машинний фільтр для автоматизованого відсікання хибнопозитивних спрацювань у SIEM та DevSecOps-конвеєрах.

## OSV: Легковаговий стандарт для екосистем відкритого коду

Формат OSV (Open Source Vulnerabilities) ініційований компанією Google та консорціумом OpenSSF для автоматизації безпеки в репозиторіях відкритого коду.

Основний фокус OSV — простота зіставлення версій та комітів у пакетних менеджерах (`npm`, `PyPI`, `Go`, `Maven`, `crates.io`, `Packagist`, `NuGet`, `Debian`, `Alpine`).

Структура документа OSV відрізняється простотою:
- фіксує ідентифікатор вади (наприклад, `GHSA-xxxx-xxxx-xxxx` або `CVE-2023-xxxxx`);
- вказує назву пакета в конкретній екосистемі (`pkg:npm/express`);
- задає діапазони комітів у системі контролю версій Git (хеш введення вразливості `introduced` та хеш виправлення `fixed`) або точні межі семантичного версіонування SemVer.

OSV розроблений так, щоб будь-який розробник або сканер залежностей (такий як `npm audit`, `pip-audit` чи `Trivy`) міг виконати перевірку через швидкий виклик простого REST API без необхідності будувати складні графи залежностей.

## Порівняльна матриця

| Критерій | CSAF 2.0 | VEX (OpenVEX / CycloneDX) | OSV (OpenSSF) |
|---|---|---|---|
| **Головне призначення** | Повний офіційний бюлетень безпеки вендора | Статус досяжності вади для кінцевого артефакту | Точний мапінг версій і комітів для опенсорс-пакетів |
| **Організація-куратор** | OASIS Open | CISA / Linux Foundation / OWASP | OpenSSF / Google |
| **Формат даних** | Строгий JSON Schema (довгий документ) | Компактний JSON / JSON-LD | Компактний JSON Schema |
| **Опис дефекту** | Повний (CVE, CWE, CVSS вектори, конфігурації) | Мінімальний (посилання на CVE/ID) | Середній (CVE/GHSA, короткий опис, посилання) |
| **Модель продуктів** | Дерево продуктів (CPE 2.3, PURL, Relationships) | Артефакт / контейнер / PURL / субкомпонент | Пакетний менеджер (Ecosystem + Package + PURL) |
| **Інструкції усунення** | Детальні (Патчі, Workarounds, Mitigations) | Статус + коротке технічне обґрунтування | Версії виправлення (`fixed: "1.4.2"`) |
| **Криптографічний підпис** | Вбудована вимога (OpenPGP, Detached signature) | Підпис через Cosign, In-Toto, Sigstore | Підпис джерела у відкритій базі даних |
| **Цільова аудиторія** | Корпоративні вендори, системні адміністратори, CISO | DevSecOps-інженери, оператори безпеки контейнерів | Розробники ПЗ, сканери залежностей, боти оновлень |

## Інженерний вибір формату

Вибір формату визначається місцем організації у ланцюгу створення вартості програмного продукту:

1. **Якщо ви вендор програмно-апаратних комплексів, дистрибутивів або комерційного ПЗ** — базовим стандартом є **CSAF 2.0**. Він надає клієнтам юридично вивірений, криптографічно захищений технічний бюлетень, придатний для корпоративного аудиту та імпорту в професійні сканери (Tenable, Qualys, Rapid7).
2. **Якщо ви постачаєте скомпільовані контейнери, прошивки або хмарні сервіси на базі сотень відкритих компонентів** — вашим інструментом є **VEX**. Він знімає блокування релізів через помилкові тривоги сканерів, документуючи реальну недосяжність застарілих бібліотек.
3. **Якщо ви ведете бібліотеку в екосистемі відкритого коду** — достатньо публікувати інформацію у форматі **OSV** (наприклад, через GitHub Security Advisories). Це автоматично захистить мільйони проєктів, які підтягують ваш пакет через стандартні пакетні менеджери.
