# Бюлетень безпеки: що написати й чого не писати

<preknowlist>
- [Оцінювання вразливостей: CVSS, EPSS](root:sf-security/vulnerability-scoring-cvss) — числова оцінка тяжкості вади та ймовірності її експлуатації в дикій природі.
- [Стрічки CVE проти власного SBOM](root:sf-security/strichky-cve-proty-vlasnoho-sbom) — ідентифікація дефектів через CVE ID та зіставлення їх із переліком компонентів.
- [Узгоджене розкриття й строки](root:sf-security/uzhodzhene-rozkryttia-i-stroky) — узгодження графіка випуску патча між дослідником і розробником до публікації.
- [Цифровий підпис](root:sf-security/hash-and-digital-signature) — автентифікація автора бюлетеня та контроль цілісності тексту/файлу через асиметричні ключі.
</preknowlist>

Коли чергова критична вада виявляється у базовому мережевому демоні чи бібліотеці шифрування, інженери безпеки та системні адміністратори опиняються під колосальним часовим тиском. Їм необхідно за лічені хвилини дати однозначну відповідь на два питання: чи зачіпає ця проблема їхню конкретну виробничу конфігурацію, і які точні технічні дії слід негайно виконати для захисту систем. Якщо вендор публікує розпливчасте повідомлення зі словами «виправлено помилки безпеки, будь ласка, оновіться», інженери не здатні оцінити ризик, не знають умов спрацювання дефекту й не мають змоги захиститися тимчасовими засобами, якщо плановий перезапуск кластера неможливий просто зараз.

Зворотна крайність є ще небезпечнішою. Якщо виробник у прагненні до повної прозорості викладає в публічний простір покроковий сценарій експлуатації пам'яті, готові запити з корисним навантаженням (англ. *payload*) чи точні зміщення адрес у бінарному файлі, він власноруч передає готову зброю в руки зловмисників. Автоматизовані ботнети починають сканувати публічний інтернет через хвилини після публікації, атакуючи сотні тисяч вузлів задовго до того, як адміністратори встигнуть протестувати й розгорнути офіційний патч.

Офіційний бюлетень безпеки (англ. *Security Advisory*) — це формальний інженерний контракт, укладений в умовах прямого протистояння між захисниками та нападниками. Його завдання — надати системним адміністраторам вичерпну інформацію для точної ідентифікації загрози, її фільтрації, аудиту та блокування, не перетворившись водночас на посібник для швидкого конструювання бойового експлойту.

## Анатомія конфлікту інтересів: Захисник проти Нападника

Публікація безпекового бюлетеня запускає незворотні перегони з часом. У момент публікації `T_0` інформація про дефект стає загальновідомою. З цієї секунди захисники та нападники рухаються паралельними, але принципово різними маршрутами.

![Часова шкала безпекового розкриття та вікно компрометації](/root/eng/sf-security/biuleten-bezpeky/img/advisory-disclosure-timeline.svg)
*Часова шкала безпекового розкриття: співвідношення часу реверс-інжинірингу патча нападниками та часу розгортання оновлення захисниками.*

Маршрут захисника складається з послідовних кроків:
1. Отримання бюлетеня та автоматизоване зіставлення його даних із власною базою активів і специфікацією компонентів [SBOM](root:sf-security/strichky-cve-proty-vlasnoho-sbom).
2. Оцінка реальної досяжності дефекту в поточній архітектурі мережі та активація тимчасових компенсаційних заходів (Workarounds), якщо такі існують.
3. Завантаження офіційного патча або оновленого пакета, перевірка його цифрового підпису та розгортання в тестовому (staging) середовищі для перевірки відсутності функціональних регресій.
4. Проведення контрольованого розгортання на промисловому парку серверів `T_patch`.

Маршрут нападника спрямований на створення 1-Day експлойту:
1. Завантаження виправленої та попередньої версій продукту.
2. Проведення бінарного порівняння (англ. *Binary Diffing*) або аналізу комітів у системі контролю версій для пошуку точного місця виправлення.
3. Дослідження умов виклику модифікованої функції та побудова ланцюжка передачі шкідливих вхідних даних (англ. *Weaponization*).
4. Запуск автоматизованого масового сканування інфраструктури в інтернеті `T_exploit`.

Інтервал часу між `T_exploit` та `T_patch` утворює критичне вікно компрометації (англ. *Exposure Window*). Будь-який бюлетень, складений некоректно, безпосередньо впливає на ширину цього вікна. Якщо в бюлетені пропущені важливі умови конфігурації чи точні номери версій, захисники втрачають години на безплідні спроби з'ясувати свій статус, що відсуває `T_patch` праворуч. Якщо ж бюлетень містить надмірні низькорівневі деталі експлуатації, нападники миттєво отримують готовий тригер без необхідності витрачати час на реверс-інжиніринг, що зсуває `T_exploit` вліво майже впритул до `T_0`.

Процес підготовки та узгодження дати релізу між дослідником, який виявив ваду, та інженерами вендора регламентується правилами [узгодженого розкриття й строків](root:sf-security/uzhodzhene-rozkryttia-i-stroky), а первинний канал прийому звітів описується в політиці [куди писати про дірку](root:sf-security/kudy-pysaty-pro-dirku). Розвиток цих практик пройшов довгий шлях від неструктурованих електронних листів кінця 1980-х років, про що детально розповідає [історичний нарис еволюції бюлетенів](root:sf-security/biuleten-bezpeky/hist-cert-and-first-advisories.md).

## Обов'язковий інженерний скелет бюлетеня

Щоб бюлетень безпеки виконав свою функцію, він повинен містити суворо визначений набір технічних розділів. Відсутність будь-якого з цих елементів руйнує процес автоматизованої обробки інциденту.

### 1. Унікальні ідентифікатори (Advisory ID та CVE ID)

Кожен бюлетень повинен мати власний незмінний ідентифікатор у системі вендора (наприклад, `RHSA-2024:1234` або `CISCO-SA-20240415-TLS`), а також один або кілька глобальних номерів [CVE](root:sf-security/strichky-cve-proty-vlasnoho-sbom) (Common Vulnerabilities and Exposures). Внутрішній ідентифікатор вендора дозволяє відстежувати документ у межах системи підтримки, а CVE ID є єдиним ключем, за яким бюлетень пов'язується з базами вразливостей, корпоративними сканерами та стрічками загроз по всьому світу.

### 2. Заголовок і стислий огляд (Title & Executive Summary)

Заголовок зобов'язаний лаконічно повідомляти клас дефекту та назву підсистеми, в якій його знайдено. Неприйнятними є абстрактні заголовки на кшталт «Оновлення системи безпеки за квітень». Правильний заголовок чітко вказує суть: «Виконання довільного коду через переповнення буфера в обробнику протоколу TLS».

Стислий огляд (Executive Summary) складається з двох-трьох абзаців чистого тексту без жаргонізмів. Він відповідає на три базові запитання керівника безпеки: який характер проблеми, який потенційний вплив на бізнес-процеси (витік конфіденційних даних, руйнування цілісності чи повна відмова в обслуговуванні) та чи зафіксовані факти реальної експлуатації цієї вади зловмисниками на момент релізу.

### 3. Каталог зачеплених і виправлених продуктів (Product & Version Matrix)

Це найкритичніша секція для системного адміністратора. Будь-яка неточність у формулюванні версій перетворює бюлетень на джерело хаосу. Секція повинна надавати вичерпний тривимірний розподіл:
- **Повні назви продуктів та компоненти.** Якщо дефект міститься в окремій бібліотеці, обов'язково зазначаються як назва самої бібліотеки, так і перелік усіх продуктів вендора, до складу яких вона входить як залежність.
- **Точні діапазони версій.** Неприпустимо писати «вразливі версії до 3.2». Слід вказувати точні числові інтервали: «вразливі всі версії від 3.0.0 до 3.2.4 включно; версії гілки 2.x дефекту не містять».
- **Архітектури та операційні системи.** Якщо помилка проявляється лише на 64-розрядних платформах x86_64 через особливості вирівнювання стека і відсутня на ARM64, цей факт повинен бути зафіксований явно.
- **Номери виправлених релізів.** Для кожної гілки підтримки вказується перший реліз, що містить виправлення (наприклад, `3.2.5` для основної гілки та `3.1.9` для попередньої версії з довготривалою підтримкою).

### 4. Вектор загрози та формальне оцінювання (CVSS та EPSS)

Публікація простого числового балу (наприклад, `9.8`) не дає захиснику можливості адаптувати оцінку під свою топологію мережі. Бюлетень зобов'язаний містити повний символьний рядок базового вектора [CVSS v3.1 або CVSS v4.0](root:sf-security/vulnerability-scoring-cvss):

```
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
```

Цей вектор розкриває інженерні параметри загрози:
- `AV:N` (Network) — вектор атаки мережевий, зловмиснику не потрібен локальний доступ до консолі;
- `AC:L` (Low) — складність атаки низька, не потрібні специфічні таймінги чи стан гонитви;
- `PR:N` (None) — автентифікація не потрібна, вразливий публічний порт;
- `UI:N` (None) — взаємодія з легітимним користувачем не потрібна;
- `C:H/I:H/A:H` — високий ступінь компрометації конфіденційності, цілісності та доступності.

Більше того, корпоративні бюлетені часто надають часові метрики (Temporal Metrics), зокрема рівень зрілості коду експлуатації (`E:U` — Unproven, `E:P` — Proof of Concept, `E:H` — High/Functional) та доступність офіційного рішення (`RL:O` — Official Fix, `RL:W` — Workaround). Якщо дефект має високий базовий бал 9.8, але атака можлива лише за наявності специфічного мережевого монітора, модифіковані метрики дозволяють системі безпеки обчислити скоригований екологічний бал (Environmental Score) для власної закритої інфраструктури.

Якщо вендор має дані зі стрічки EPSS (Exploit Prediction Scoring System), він зазначає розрахункову ймовірність появи експлойту в дикій природі. Це дозволяє команді SOC розставити черговість реагування між сотнями одночасно відкритих інцидентів.

### 5. Умови досяжності та необхідні конфігурації (Reachability & Prerequisites)

Більшість вразливостей проявляються не в базовій установці за замовчуванням, а лише за специфічних налаштувань. Бюлетень повинен чітко перелічити обов'язкові передумови:
- які конфігураційні прапорці повинні бути увімкнені (наприклад, `enable_legacy_v1_auth = true`);
- які мережеві порти мають бути відкритими для зовнішніх запитів;
- які нестандартні модулі чи розширення мають бути скомпільовані або завантажені в адресний простір ядра чи процесу;
- які права доступу потрібні для ініціалізації тригера (наприклад, роль звичайного автентифікованого користувача чи адміністратора бази даних).

Якщо сервіс у конфігурації за замовчуванням дефекту не викликає, це знижує терміновість нічних авральних робіт і дозволяє провести оновлення у плановому порядку без ризику падіння виробничих ліній.

### 6. Тимчасові компенсаційні заходи (Workarounds / Mitigations)

Встановлення повноцінного бінарного оновлення часто вимагає перезавантаження маршрутизатора ядра мережі або зупинки критичної бази даних, що веде до простою сервісів. Тому наявність дієвого тимчасового заходу (Workaround) є одним із найцінніших розділів бюлетеня.

Тимчасовий захід — це зміна конфігурації, правила міжмережевого екрана або вимкнення окремої другорядної функції, яка повністю блокує вектор атаки без необхідності модифікації виконуваного коду програми.

Опис Workaround повинен супроводжуватися аналізом операційних побічних ефектів: якщо вимкнення функції `compression` у вебсервері зупиняє атаку CRIME, вендор повинен прямо вказати, що це збільшить вихідний мережевий трафік на 15–20%.

### 7. Інструкція з остаточного виправлення (Remediation / Patches)

Розділ містить прямі гіперпосилання на офіційні бінарні пакети, репозиторії вихідного коду, контейнерні образи або файли прошивок. Для кожного файлу обов'язково публікується:
- точна криптографічна контрольна сума за алгоритмом SHA-256;
- цифровий підпис [OpenPGP / GPG](root:sf-security/hash-and-digital-signature), що гарантує захист від підміни пакета під час транспортування або компрометації дзеркала оновлень;
- вказівка на вимоги до перезапуску (`service restart`, `OS reboot` або `no restart required`).

### 8. Індикатори компрометації (Indicators of Compromise, IoC)

Захисники повинні не лише захистити систему на майбутнє, а й з'ясувати, чи не була вона скомпрометована до виходу бюлетеня (на етапі Zero-Day). Бюлетень надає криміналістичні артефакти:
- специфічні шаблони помилок чи аномальні послідовності байтів у системних журналах;
- назви тимчасових файлів, які створюються в разі аварійного завершення процесу;
- мережеві сигнатури для систем виявлення вторгнень (Snort, Suricata), що фіксують спроби відправки некоректних заголовків.

### 9. Історія ревізій та подяки (Revision History & Acknowledgments)

Секція подяк фіксує імена дослідників або назви координаційних організацій, які виявили ваду і повідомили про неї з дотриманням етичних норм узгодженого розкриття.

Журнал ревізій (Revision History) документує будь-які зміни, внесені до бюлетеня після його первинної публікації: додавання нових зачеплених версій, коригування правил Workaround або уточнення балу CVSS. Кожен запис супроводжується датою та номером версії документа.

## Межа безпечного розкриття: Де провести лінію між допомогою та зброєю

Найскладнішим інженерним та етичним завданням автора безпекового бюлетеня є точне дотримання балансу між інформативністю для захисника та скритністю від нападника.

![Баланс безпекового розкриття: захисна цінність проти наступальної зброї](/root/eng/sf-security/biuleten-bezpeky/img/advisory-content-balance.svg)
*Баланс безпекового розкриття: інформація, необхідна для захисту систем, проти деталей, що спрощують автоматизацію атаки.*

### Що необхідно розкривати повністю

Захиснику потрібні знання про функціональну поведінку системи та параметри фільтрації. Бюлетень обов'язково повинен містити:
1. **Формальний клас дефекту у класифікації CWE** (Common Weakness Enumeration), наприклад `CWE-787: Out-of-bounds Write`, `CWE-89: SQL Injection`, `CWE-287: Improper Authentication`. Це дозволяє архітекторам безпеки миттєво зрозуміти фізичну природу загрози.
2. **Точки входу та мережеві протоколи.** Який саме інтерфейс приймає шкідливі дані: відкритий REST API, внутрішній порт gRPC, обробник заголовків WebSocket чи сирий UDP-сокет.
3. **Формат аномальних вхідних даних на концептуальному рівні.** Наприклад: «вразливість викликається передачею поля довжини, що перевищує 65535 байт, у заголовку розширення X.509». Цього достатньо для створення правила фільтрації на рівні WAF, але недостатньо для автоматичного захоплення реєстрів процесора.
4. **Спосіб верифікації виправлення.** Інструкція, як адміністратор може переконатися, що оновлення успішно застосовано (наприклад, виклик `daemon --version` або опитування службового ендпойнта `/healthz`).

### Чого категорично не можна публікувати на момент релізу

Будь-які дані, що знижують бар'єр для автоматизованої експлуатації, повинні бути виключені з тексту бюлетеня:

1. **Готовий код PoC-експлойтів та команди `curl` з бойовим навантаженням.** Публікація готового скрипта перетворює будь-якого некваліфікованого зловмисника на оператора атаки, позбавляючи системних адміністраторів шансу на захист.
2. **Точні зміщення в структурах пам'яті (Memory Offsets).** Вказівка на те, що «зсув на 0x148 байт від початку буфера дозволяє перезаписати вказівник на таблицю віртуальних методів», автоматизує побудову ланцюжка захоплення керування (control flow hijack).
3. **Готові ланцюжки ROP-гаджетів (Return-Oriented Programming).** Пошук придатних інструкцій у бінарному файлі забирає у реверсера значний час. Публікація готових адрес інструкцій `pop rdi; ret` нівелює захисні механізми операційної системи.
4. **Техніки обходу вбудованих захистів (ASLR, DEP/NX, Stack Canaries).** Якщо для реалізації атаки зловмиснику потрібно попередньо організувати витік пам'яті (memory leak) для подолання ASLR, бюлетень у жодному разі не повинен підказувати, яка саме суміжна функція дозволяє це зробити.
5. **Натяки на вторинні незакриті вразливості.** Якщо під час аудиту коду інженери вендора виявили кілька споріднених вад, але поточний патч усуває лише першу з них, бюлетень не повинен згадувати про наявність аналогічних дефектів у сусідніх функціях до моменту випуску виправлення для них.

### Реалії 1-Day бінарного дифінгу

Автори бюлетенів повинні усвідомлювати, що випуск патча з відкритим вихідним кодом або оновленого бінарного файлу сам по собі є розкриттям інформації. Кваліфіковані дослідники та зловмисники застосовують інструменти бінарного зіставлення (Ghidra Version Tracking, BinDiff, Diaphora) для порівняння функцій до і після патча.

Зміна умови перевірки:

:::tabs
```c
// До виправлення:
if (length > MAX_BUF) return -1;

// Після виправлення:
if (length > MAX_BUF || length < HEADER_SIZE) return -1;
```
```cpp
// До виправлення:
if (payload.size() > MAX_BUF) return std::nullopt;

// Після виправлення:
if (payload.size() > MAX_BUF || payload.size() < HEADER_SIZE) return std::nullopt;
```
:::

миттєво вказує аналітику, що атака полягає у відправці значення `length < HEADER_SIZE`, що спричиняло від'ємне зміщення або цілочисельне переповнення.

Тому спроби вендора повністю «приховати» факт наявності дірки за фразою «виправлено дрібні недоліки» не захищають від професійних хакерів, але повністю позбавляють інформації власних користувачів. Баланс полягає в тому, щоб надати користувачам усю повноту контексту для захисту, не публікуючи готових експлойтів, які спрощують атаку низькокваліфікованим нападникам.

## Машинночитна революція: Стандарт CSAF 2.0

В умовах, коли корпоративна інфраструктура розгортається у вигляді тисяч мікросервісів у кластерах Kubernetes, ручний розбір PDF-документів чи поштових листів системними адміністраторами став технічно неможливим. Індустрія перейшла до використання машиночитних бюлетенів, головним глобальним стандартом яких став CSAF 2.0 (Common Security Advisory Framework), розроблений консорціумом OASIS.

Детальне порівняння CSAF 2.0 з іншими відкритими форматами розкриття наведено у [порівняльному аналізі CSAF 2.0, VEX та OSV](root:sf-security/biuleten-bezpeky/comp-csaf-vex-osv.md).

![Ієрархічна структура машиночитних даних CSAF 2.0](/root/eng/sf-security/biuleten-bezpeky/img/csaf-document-tree.svg)
*Ієрархічна структура машиночитних даних CSAF 2.0: взаємозв'язок метаданих документа, каталогу продуктів та окремих вразливостей.*

Документ CSAF 2.0 є суворо валідованим JSON-файлом, що складається з трьох ключових блоків:

1. **`document` (Метадані повідомлення).** Містить ідентифікатор бюлетеня, назву видавця, категорію документа (`csaf_security_advisory`), URL-простір імен, контакти команди PSIRT та повну історію ревізій із часовими мітками за стандартом ISO 8601.
2. **`product_tree` (Каталог програмних продуктів).** Описує ієрархічну структуру програмних комплексів організації. Кожен вузол отримує внутрішній ідентифікатор `product_id`, а також стандартизовані зовнішні ідентифікатори: CPE 2.3 (Common Platform Enumeration) для традиційного ПЗ та PURL (Package URL) для модулів у пакетних менеджерах (npm, PyPI, Go, Maven).
3. **`vulnerabilities` (Описи дефектів безпеки).** Масив об'єктів вразливостей. Кожен елемент пов'язує конкретний CVE ID, клас CWE, числові вектори CVSS v3/v4 зі списком `product_id` через матрицю статусів (`known_affected`, `fixed`, `known_not_affected`) та надає структуровані інструкції з оновлення (`remediations`).

Повна технічна специфікація полів, типів даних та обов'язкових інваріантів стандарту наведена у [довіднику схеми CSAF 2.0](root:sf-security/biuleten-bezpeky/api-csaf-schema.md).

Використання CSAF 2.0 дозволяє сканерам безпеки за секунди зіставити тисячі серверів із базою вразливостей вендора, відкинути неактуальні версії та сформувати автоматичні тікети на оновлення для чергових інженерів.

## Комплексні пакети вразливостей та пакетні релізи

У великих програмних екосистемах (наприклад, регулярні щоквартальні оновлення безпеки операційних систем або монолітні релізи баз даних) один бюлетень безпеки рідко обмежується єдиним дефектом. Бюлетень може описувати відразу кілька десятків вразливостей (від низького до критичного рівня), виявлених у різних субкомпонентах системи.

У таких сценаріях інженерна чіткість структури бюлетеня має вирішальне значення:
- **Багатопродуктове розщеплення статусів.** Якщо бюлетень закриває одразу п'ять CVE, кожен дефект повинен мати власну матрицю `product_status`. Неприпустимо узагальнювати статус на весь пакет, якщо дефект №1 стосується лише утиліти командного рядка, а дефект №2 — мережевого сервісу з правами суперкористувача.
- **Розподіл за пріоритетами виправлення.** Бюлетень повинен явно виділяти критичний шлях (Critical Path): які саме CVE несуть загрозу негайного дистанційного захоплення вузла (RCE без автентифікації), а які є локальними дефектами відмови в обслуговуванні (DoS).
- **Складені інструкції оновлення.** Якщо для усунення дефекту №1 достатньо оновити базову бібліотеку, а для дефекту №2 потрібна міграція схеми бази даних, секція `remediations` зобов'язана розділяти ці кроки на окремі інженерні процедури з чітко зазначеною послідовністю виконання.

## Тимчасові заходи (Workarounds) та їхня інженерна ціна

Розробка надійного тимчасового заходу (Workaround) вимагає глибокого розуміння внутрішньої архітектури системи. Тимчасовий захід не виправляє помилку в коді, але розриває ланцюжок доставки шкідливого навантаження до вразливого блоку пам'яті або бізнес-логіки.

```
Вхідний трафік (Запит) 
         │
         ▼
┌──────────────────┐    Workaround: Блокування
│  Зовнішній WAF   │ ─── на межі периметра ────► [ Відхилено 403 ]
└────────┬─────────┘     (Низька ціна)
         │
         ▼
┌──────────────────┐    Workaround: Зміна конфігурації
│ Локальний Демон  │ ─── вимкнення функції ────► [ Запит ігноровано ]
└────────┬─────────┘     (Втрата функціональності)
         │
         ▼
┌──────────────────┐
│ Вразлива функція │ ─── Тільки Vendor Patch ──► [ Безпечна обробка ]
│  (Код ядра/lib)  │     (Остаточне рішення)
└──────────────────┘
```

### Основні типи тимчасових пом'якшень

1. **Вимкнення вразливої функціональності через конфігурацію.** Якщо дефект локалізовано в модулі попереднього перегляду документів або механізмі автентифікації за застарілим протоколом NTLM, адміністраторам пропонується вимкнути відповідну опцію у конфігураційному файлі (`preview_enabled = false`). Це найбільш надійний тип захисту, оскільки вразливий код взагалі перестає ініціалізуватися в пам'яті.
2. **Фільтрація на межі периметра (Virtual Patching).** Розгортання правил на зворотному проксі-сервері (Nginx, Envoy) або Web Application Firewall (WAF). Правило перевіряє довжину URI, блокує специфічні HTTP-заголовки або забороняє певні методи запитів (`TRACE`, `DEBUG`). Перевага методу — відсутність необхідності змінювати сам захищений сервер.
3. **Обмеження мережевого доступу (Network ACL).** Якщо вразливий адміністративний інтерфейс не потребує доступу з усього інтернету, адміністратори звужують правила фаєрвола, дозволяючи підключення до порту лише з довірених IP-адрес VPN або підмережі управління.
4. **Зниження привілеїв процесу (Privilege Dropping).** Якщо вразливість дозволяє виконати довільний код, але демон запущено з правами суперкористувача `root`, тимчасовим заходом може стати налаштування ізоляції через простори імен Linux (Namespaces), обмеження системних викликів через `seccomp` або активація профілів AppArmor/SELinux. Це не запобігає експлуатації процесу, але блокує підвищення привілеїв у системі.

### Пастка хибної безпеки (False Sense of Security)

Найбільша небезпека невдалих Workarounds — створення ілюзії безпеки, коли адміністратори вважають систему захищеною, а зловмисники легко обходять фільтр:

- **Неповна нормалізація шляхів (URL/Path Normalization).** Якщо правило WAF блокує запити, що містять рядок `/admin/delete`, нападник надсилає `/admin/%2e%2e/admin/delete`, `/ADMIN/delete` або додає нульовий байт. Якщо WAF і бекенд декодують символи за різними правилами, фільтр пропускає атаку.
- **Обхід через альтернативні кодування символів.** Якщо дефект пов'язаний з ін'єкцією команд, наївне блокування пробілів обходиться використанням змінних середовища `${IFS}`, символів табуляції або перенаправлення введення `<`.
- **Функціональна деградація суміжних сервісів.** Вимкнення механізму пулу з'єднань (Connection Pooling) для захисту від стану гонитви може призвести до вичерпання дескрипторів сокетів і падіння всієї системи під звичайним навантаженням.

Тому будь-який Workaround у бюлетені повинен бути всебічно протестований у лабораторії вендора, а його опис зобов'язаний містити попередження: «Застосування цього заходу є тимчасовим засобом стримування і не скасовує необхідності встановлення офіційного оновлення».

Практична реалізація алгоритму зіставлення версій та автоматичного вибору відповідного Workaround наведена у [проєкті парсера та верифікатора бюлетенів](root:sf-security/biuleten-bezpeky/proj-advisory-generator.md).

## Дистрибуція, автентифікація та юридичні зобов'язання

Складання якісного тексту — лише половина завдання. Бюлетень безпеки повинен бути доставлений клієнтам захищеним каналом із гарантією незмінності вмісту.

### Автоматизоване виявлення через `.well-known`

Стандарт CSAF 2.0 закріпив єдиний механізм виявлення каналів безпеки. Організація розміщує у корені свого основного вебдомену службовий файл маніфесту:

```
https://example.com/.well-known/csaf/provider-metadata.json
```

Цей маніфест визначає:
- канонічну URL-адресу каталогу, де публікуються JSON-файли бюлетенів;
- відкритий ключ [цифрового підпису](root:sf-security/hash-and-digital-signature) OpenPGP або сертифікат Sigstore, яким підписуються файли;
- стрічки ROLIE (Resource-Oriented Lightweight Information Exchange), через які сканери клієнтів можуть автоматично отримувати лише нові та оновлені документи за останню добу.

### Криптографічна автентифікація бюлетенів

Публікація бюлетеня незахищеним каналом або без підпису створює критичний вектор атаки на [безпеку ланцюга постачання](root:sf-security/supply-chain-security) (Supply Chain Attack). Зловмисник, здатний перехопити DNS або підмінити HTTP-відповідь (MitM), може розіслати клієнтам фальшивий бюлетень із порадою «вимкнути шифрування» або посиланням на шкідливий бінарний пакет.

Вимоги безпеки до дистрибуції:
1. Кожен файл `advisory.json` супроводжується відкріпленим цифровим підписом `advisory.json.asc`, сформованим на офіційному закритому ключі PSIRT організації.
2. Поруч публікується контрольна сума `advisory.json.sha256`.
3. Усі вебдзеркала та API-ендпойнти працюють виключно за протоколом TLS із суворою перевіркою сертифікатів (HSTS).

### Нормативні зобов'язання щодо сповіщення

Для багатьох галузей (критична інфраструктура, фінансовий сектор, медичне обладнання, автомобільна промисловість) публікація безпекового бюлетеня є не просто доброю волею вендора, а суворою законодавчою вимогою. Нормативні акти (такі як Директива ЄС NIS 2, Акт про кіберстійкість EU Cyber Resilience Act або вимоги регуляторів США) встановлюють жорсткі часові рамки повідомлення користувачів та галузевих регуляторів про виявлені вразливості, що мають високий рівень критичності.

Юридичні тонкощі, процедури взаємодії з державними центрами CERT та відповідальність перед партнерами детально розглядаються у статті про [обов'язок повідомити: регулятор, власники, партнери](root:sf-security/oboviazok-povidomyty).

## Інженерні принципи бездоганного бюлетеня

Підсумовуючи інженерну практику розробки та супроводу безпекових повідомлень, можна виділити шість базових правил складання бюлетеня:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                 Шість інженерних правил безпекового бюлетеня                │
├──────────────────────────┬──────────────────────────────────────────────────┤
│ 1. Однозначність версій  │ Жодних суб'єктивних фраз: точні діапазони SemVer,│
│                          │ номери пакетів, CPE 2.3 та PURL.                 │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ 2. Повний вектор загрози │ Не лише бал 9.8, а повний рядок CVSS-вектора     │
│                          │ для адаптації під топологію захисника.           │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ 3. Дієвий Workaround     │ Інструкція тимчасового блокування загрози без    │
│                          │ термінового простою, з описом побічних ефектів.  │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ 4. Жодної зброї у релізі │ Заборона публікації готових PoC, зміщень пам'яті │
│                          │ та ланцюжків ROP на момент T_0.                  │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ 5. Машинна валідність    │ Обов'язкова валідація JSON-схеми CSAF 2.0        │
│                          │ та цілісності посилань product_id.               │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ 6. Криптографічний підпис│ Обов'язковий підпис OpenPGP та контрольна сума   │
│                          │ SHA-256 для захисту від фальсифікації.           │
└──────────────────────────┴──────────────────────────────────────────────────┘
```
