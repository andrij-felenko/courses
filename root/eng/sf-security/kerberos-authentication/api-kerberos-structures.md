# 📋 Специфікація ASN.1-структур повідомлень Kerberos v5 та двійкового формату MS-PAC

Цей довідник містить вичерпний опис форматів повідомлень, структур даних і двійкових контрактів протоколу Kerberos версії 5 згідно зі специфікаціями RFC 4120, криптографічними профілями RFC 3961 / RFC 3962 та розширеннями Microsoft Active Directory [MS-PAC] і [MS-KILE]. Матеріал слугує інженерним дороговказом для низькорівневого аналізу мережевих дампів, розробки клієнтських і серверних модулів автентифікації, реалізації синтаксичних аналізаторів ASN.1 та побудови систем аудиту безпеки.

## Правила кодування та архітектура ASN.1 у Kerberos v5

Протокол Kerberos v5 використовує для серіалізації всіх мережевих структур абстрактний синтаксис ASN.1 (англ. *Abstract Syntax Notation One*), закодований за канонічними правилами DER (англ. *Distinguished Encoding Rules*). На відміну від версії Kerberos v4, де структури залежали від порядку байтів процесора відправника (Little-Endian або Big-Endian), кодування DER гарантує однозначне, платформонезалежне двійкове представлення: кожне поле описується трійкою «тег — довжина — значення» (TLV, англ. *Tag-Length-Value*).

Усі повідомлення протоколу пакуються у контекстні теги класу `APPLICATION`. Номер тегу однозначно визначає тип повідомлення, що дозволяє мережевому стеку розпізнати очікувану структуру даних без попереднього розбору всього пакета. Числові значення передаються в кодуванні доповнення до двійки зі старшим байтом попереду (Big-Endian / Network Byte Order). Рядкові поля (імена принципалів, назви областей) кодуються як `GeneralString` або `KerberosString` (підмножина ASCII та UTF-8).

### Загальний реєстр типів повідомлень (Application Tags)

| Тег `APPLICATION` | Числовий код | Символічна назва | Функціональне призначення у протоколі |
|---|---|---|---|
| `[APPLICATION 10]` | 10 | `KRB_AS_REQ` | Початковий запит клієнта до служби AS для автентифікації та отримання TGT. |
| `[APPLICATION 11]` | 11 | `KRB_AS_REP` | Відповідь служби AS: містить квиток TGT та зашифрований сесійний ключ `K_{c,tgs}`. |
| `[APPLICATION 12]` | 12 | `KRB_TGS_REQ` | Запит клієнта до служби TGS для отримання сервісного квитка на конкретну службу. |
| `[APPLICATION 13]` | 13 | `KRB_TGS_REP` | Відповідь служби TGS: містить сервісний квиток (ST) та сервісний сесійний ключ `K_{c,s}`. |
| `[APPLICATION 14]` | 14 | `KRB_AP_REQ` | Запит автентифікації клієнта до сервера додатку із сервісним квитком та автентифікатором. |
| `[APPLICATION 15]` | 15 | `KRB_AP_REP` | Відповідь сервера додатку для підтвердження взаємної автентифікації клієнта. |
| `[APPLICATION 20]` | 20 | `KRB_SAFE` | Прикладне повідомлення, захищене криптографічною контрольною сумою (цілісність без шифрування). |
| `[APPLICATION 21]` | 21 | `KRB_PRIV` | Прикладне повідомлення, зашифроване сесійним ключем (цілісність і конфіденційність). |
| `[APPLICATION 22]` | 22 | `KRB_CRED` | Захищений контейнер для пересилання та делегування квитків між вузлами. |
| `[APPLICATION 30]` | 30 | `KRB_ERROR` | Уніфіковане повідомлення про помилку від KDC або сервера додатку. |

## Базові типи та криптографічні контейнери

Усі криптографічні операції в Kerberos v5 інкапсульовані в уніфіковані контейнери, які відокремлюють зашифровані дані від метаданих алгоритмів.

```asn1
PrincipalName ::= SEQUENCE {
    name-type       [0] Int32,
    name-string     [1] SEQUENCE OF KerberosString
}

EncryptionKey ::= SEQUENCE {
    keytype         [0] Int32,
    keyvalue        [1] OCTET STRING
}

EncryptedData ::= SEQUENCE {
    etype           [0] Int32,
    kvno            [1] UInt32 OPTIONAL,
    cipher          [2] OCTET STRING
}

Checksum ::= SEQUENCE {
    cksumtype       [0] Int32,
    checksum        [1] OCTET STRING
}
```

### Семантика полів базових типів

Поле `name-type` у структурі `PrincipalName` вказує семантику імені:
- `KRB_NT_PRINCIPAL` (значення `1`) — звичайне ім'я користувача (наприклад, `alice`).
- `KRB_NT_SRV_INST` (значення `2`) — служба з ім'ям хоста або інстансу (наприклад, `cifs/fileserver.example.org` або `HTTP/intranet.example.org`).
- `KRB_NT_SRV_HST` (значення `3`) — служба хоста без деталізації (`host/workstation01`).
- `KRB_NT_ENTERPRISE` (значення `10`) — корпоративне ім'я користувача у форматі UPN (наприклад, `user@corp.domain.com`), яке KDC транслює у канонічне доменне ім'я під час обробки.

Структура `EncryptedData` містить поле `etype`, яке визначає використаний алгоритм шифрування, необов'язкове поле `kvno` (англ. *Key Version Number* — номер версії ключа) та власне `cipher` — зашифровані байти. Поле `kvno` є критично важливим для сервісів та KDC: воно дозволяє безперервно змінювати та ротувати паролі й довгострокові ключі служб, знаючи, яка саме версія ключа була використана для шифрування конкретного квитка.

## Структури квитка (Ticket) та зашифрованої частини (EncTicketPart)

Квиток є центральним артефактом протоколу. Верхньорівнева структура `Ticket` передається відкрито мережею, проте вся інформація про автентифіковану особу та виданий сесійний ключ схована всередині зашифрованого блоку `enc-part`.

```asn1
Ticket ::= [APPLICATION 1] SEQUENCE {
    tkt-vno         [0] INTEGER (5),
    realm           [1] Realm,
    sname           [2] PrincipalName,
    enc-part        [3] EncryptedData
}

EncTicketPart ::= [APPLICATION 3] SEQUENCE {
    flags           [0] TicketFlags,
    key             [1] EncryptionKey,
    crealm          [2] Realm,
    cname           [3] PrincipalName,
    transited       [4] TransitedEncoding,
    authtime        [5] KerberosTime,
    starttime       [6] KerberosTime OPTIONAL,
    endtime         [7] KerberosTime,
    renew-till      [8] KerberosTime OPTIONAL,
    caddr           [9] HostAddresses OPTIONAL,
    authorization-data [10] AuthorizationData OPTIONAL
}
```

### Семантика полів та інваріанти EncTicketPart

- `flags` (`TicketFlags`) — бітова маска властивостей квитка, що визначає допустимі операції:
  - `forwardable` (біт `1`) — клієнт має право передати цей TGT службі KDC для випуску нового TGT з іншою мережевою адресою (основа делегування повноважень).
  - `forwarded` (біт `2`) — квиток було створено на основі пересланого TGT.
  - `proxiable` (біт `3`) — дозволяє отримувати сервісні квитки для обмеженого проксі-доступу.
  - `renewable` (біт `8`) — квиток може бути подовжений службою TGS без повторного введення пароля користувачем, доки не настане час `renew-till`.
  - `initial` (біт `9`) — підтверджує, що квиток видано безпосередньо службою AS на основі первинних облікових даних, а не обміняно через TGS.
  - `pre-authent` (біт `10`) — клієнт успішно пройшов попередню автентифікацію під час первинного запиту.
- `key` (`EncryptionKey`) — тимчасовий випадковий симетричний ключ сесії (`K_{c,tgs}` для квитка TGT або `K_{c,s}` для сервісного квитка ST). Цей ключ відомий лише KDC, клієнту та кінцевій службі.
- `crealm` та `cname` — автентифікована особа клієнта. Оскільки ці поля зашифровані ключем служби `K_s`, зловмисник не здатний змінити ім'я клієнта без порушення криптографічної цілісності.
- `transited` — запис усіх проміжних областей (Realms), через які пройшов квиток під час міждоменної автентифікації, що забезпечує аудит довіри між доменами.
- `authtime` — абсолютний час первинного успішного входу користувача на сервері AS.
- `starttime` та `endtime` — часовий інтервал дійсності квитка. Будь-який сервер зобов'язаний негайно відхилити квиток, якщо поточний час перевищує значення `endtime`.
- `renew-till` — граничний термін, до якого дозволено періодичне подовження квитка за допомогою прапорця `renewable`.
- `caddr` (`HostAddresses`) — список дозволених IP-адрес клієнта. У сучасних мережах із динамічною маршрутизацією та NAT це поле часто залишають порожнім для уникнення хибних блокувань.
- `authorization-data` — контейнер розширень авторизації. Саме сюди вбудовується структура Microsoft PAC (`AD-WIN2K-PAC`), яка містить повний перелік прав та груп користувача.

## Структура автентифікатора (Authenticator)

Автентифікатор генерується клієнтською бібліотекою безпосередньо перед надсиланням запиту до служби й шифрується сесійним ключем `K_{c,s}`. Він діє як одноразовий цифровий доказ того, що відправник володіє дійсним сесійним ключем.

```asn1
Authenticator ::= [APPLICATION 2] SEQUENCE {
    authenticator-vno [0] INTEGER (5),
    crealm            [1] Realm,
    cname             [2] PrincipalName,
    cksum             [3] Checksum OPTIONAL,
    cusec             [4] Microseconds,
    ctime             [5] KerberosTime,
    subkey            [6] EncryptionKey OPTIONAL,
    seq-number        [7] UInt32 OPTIONAL,
    authorization-data[8] AuthorizationData OPTIONAL
}
```

### Призначення полів автентифікатора

- `authenticator-vno` — версія формату автентифікатора (завжди `5`).
- `crealm` та `cname` — ім'я відправника. Сервер розшифровує автентифікатор сесійним ключем із квитка та строго порівнює ці поля з полями `crealm` і `cname`, витягнутими із зашифрованої частини квитка `EncTicketPart`. Будь-яка невідповідність викликає негайне розірвання з'єднання.
- `cksum` — криптографічна контрольна сума від прикладного запиту. Зв'язує автентифікатор із конкретними даними сеансу, запобігаючи підміні параметрів прикладного протоколу стороннім посередником.
- `ctime` та `cusec` — мітка часу генерації автентифікатора (секунди за UTC та залишок у мікросекундах). Використовується для захисту від повторного відтворення (Replay Attack).
- `subkey` — опційний випадковий ключ підвибірки (підсесії), запропонований клієнтом. Якщо сервер приймає його, подальший обмін даними шифрується саме цим підключем, що ізолює окремі з'єднання в межах одного загального квитка.
- `seq-number` — початковий 32-бітний номер послідовності пакетів для контролю втрати або вставки фальшивих повідомлень під час роботи через `KRB_SAFE` або `KRB_PRIV`.

## Запити та відповіді центру розподілу ключів (KDC-REQ та KDC-REP)

Обмін між клієнтом та сервером KDC на перших двох етапах уніфіковано через загальні схеми повідомлень `KDC-REQ` та `KDC-REP`.

```asn1
KDC-REQ ::= SEQUENCE {
    pvno            [1] INTEGER (5),
    msg-type        [2] INTEGER (10 -- AS-REQ -- | 12 -- TGS-REQ --),
    padata          [3] SEQUENCE OF PA-DATA OPTIONAL,
    req-body        [4] KDC-REQ-BODY
}

PA-DATA ::= SEQUENCE {
    padata-type     [1] Int32,
    padata-value    [2] OCTET STRING
}

KDC-REQ-BODY ::= SEQUENCE {
    kdc-options     [0] KDCOptions,
    cname           [1] PrincipalName OPTIONAL,
    realm           [2] Realm,
    sname           [3] PrincipalName OPTIONAL,
    from            [4] KerberosTime OPTIONAL,
    till            [5] KerberosTime,
    rtime           [6] KerberosTime OPTIONAL,
    nonce           [7] UInt32,
    etype           [8] SEQUENCE OF Int32,
    addresses       [9] HostAddresses OPTIONAL,
    enc-authorization-data [10] EncryptedData OPTIONAL,
    additional-tickets     [11] SEQUENCE OF Ticket OPTIONAL
}
```

### Поля KDC-REQ-BODY та їхня криптографічна роль

- `padata` (`PA-DATA`) — послідовність блоків преавтентифікації. У повідомленні `AS-REQ` тут передається зашифрована мітка часу `PA-ENC-TIMESTAMP`, що доводить знання пароля клієнтом. У повідомленні `TGS-REQ` через поле `padata` передається квиток TGT та автентифікатор, зашифрований сесійним ключем `K_{c,tgs}` (тип `PA-TGS-REQ`, код `1`).
- `kdc-options` — бітова маска параметрів запиту, що дублює та розширює прапорці квитка (вимога `forwardable`, `renewable`, `canonicalize` для приведення імен тощо).
- `cname` — ім'я користувача (присутнє лише у запиті `AS-REQ`; у `TGS-REQ` ім'я береться KDC безпосередньо з розшифрованого TGT).
- `sname` — ім'я цільової служби (для `AS-REQ` це зазвичай `krbtgt/EXAMPLE.ORG`, для `TGS-REQ` — ім'я сервісу, наприклад `cifs/fs.example.org`).
- `nonce` — криптографічно стійке псевдовипадкове 32-бітне число, згенероване клієнтом. Служба KDC зобов'язана повернути це саме число у зашифрованій відповіді `EncKDCRepPart`. Збіг чисел гарантує клієнту, що отримана відповідь є свіжою реакцією саме на цей запит, а не підсунутим старим повідомленням зловмисника.
- `etype` — упорядкований за пріоритетом список числових ідентифікаторів шифрів, які підтримує клієнт. KDC обирає найстійкіший взаємно підтримуваний алгоритм.

Структура відповіді KDC:

```asn1
KDC-REP ::= SEQUENCE {
    pvno            [0] INTEGER (5),
    msg-type        [1] INTEGER (11 -- AS-REP -- | 13 -- TGS-REP --),
    padata          [2] SEQUENCE OF PA-DATA OPTIONAL,
    crealm          [3] Realm,
    cname           [4] PrincipalName,
    ticket          [5] Ticket,
    enc-part        [6] EncryptedData
}

EncKDCRepPart ::= SEQUENCE {
    key             [0] EncryptionKey,
    last-req        [1] LastReq,
    nonce           [2] UInt32,
    key-expiration  [3] KerberosTime OPTIONAL,
    flags           [4] TicketFlags,
    authtime        [5] KerberosTime,
    starttime       [6] KerberosTime OPTIONAL,
    endtime         [7] KerberosTime,
    renew-till      [8] KerberosTime OPTIONAL,
    srealm          [9] Realm,
    sname           [10] PrincipalName,
    caddr           [11] HostAddresses OPTIONAL
}
```

У повідомленні `AS-REP` блок `enc-part` зашифровано довгостроковим ключем клієнта `K_c`, отриманим із пароля користувача. У повідомленні `TGS-REP` той самий блок шифрується попереднім сесійним ключем `K_{c,tgs}`.

## Обмін із кінцевим сервером додатку (AP-REQ та AP-REP)

```asn1
AP-REQ ::= [APPLICATION 14] SEQUENCE {
    pvno            [0] INTEGER (5),
    msg-type        [1] INTEGER (14),
    ap-options      [2] APOptions,
    ticket          [3] Ticket,
    authenticator   [4] EncryptedData
}

APOptions ::= BIT STRING {
    reserved(0),
    use-session-key(1),
    mutual-required(2)
}

AP-REP ::= [APPLICATION 15] SEQUENCE {
    pvno            [0] INTEGER (5),
    msg-type        [1] INTEGER (15),
    enc-part        [2] EncryptedData
}

EncAPRepPart ::= [APPLICATION 27] SEQUENCE {
    ctime           [0] KerberosTime,
    cusec           [1] Microseconds,
    subkey          [2] EncryptionKey OPTIONAL,
    seq-number      [3] UInt32 OPTIONAL
}
```

Якщо клієнт встановлює прапорець `mutual-required` у бітовій масці `ap-options`, сервер зобов'язаний сформувати відповідь `AP-REP`. У зашифрованій структурі `EncAPRepPart` сервер повертає часову мітку `ctime` та `cusec`, скопійовані з автентифікатора клієнта, і шифрує цей блок сесійним ключем `K_{c,s}`. Клієнт розшифровує відповідь і звіряє мітку: оскільки лише справжній сервер володіє ключем `K_s`, здатним розкрити квиток і витягти `K_{c,s}`, успішний розбір `AP-REP` слугує неспростовним доказом автентичності сервера.

## Реєстр типів преавтентифікації (PA-DATA Types)

Преавтентифікація виконується перед генерацією квитка TGT і забезпечує передачу додаткових криптографічних доказів та параметрів:

| Код типу | Символічна назва | Специфікація | Детальний опис механізму |
|---|---|---|---|
| 1 | `PA-ENC-TIMESTAMP` | RFC 4120 | Містить структуру `PA-ENC-TS-ENC`, зашифровану ключем `K_c`. Підтверджує, що клієнт знає пароль, без передачі самого пароля. |
| 11 | `PA-ETYPE-INFO` | RFC 4120 | Перелік підтримуваних шифрів та сіль для обчислення симетричного ключа з пароля. |
| 19 | `PA-ETYPE-INFO2` | RFC 4120 | Оновлена версія `PA-ETYPE-INFO`: передає тип шифру, строкову сіль та додаткові параметри функції деривації (`s2kparams`). |
| 16 | `PA-PK-AS-REQ` | RFC 4556 | Початковий запит клієнта з використанням сертифікатів відкритого ключа або смарт-карток (PKINIT). |
| 17 | `PA-PK-AS-REP` | RFC 4556 | Відповідь KDC з асиметричним підписом у протоколі PKINIT. |
| 128 | `PA-PAC-REQUEST` | [MS-KILE] | Булевий прапорець клієнта: запит до KDC включити авторизаційний сертифікат MS-PAC у виданий квиток. |
| 129 | `PA-FOR-USER` | [MS-SFU] | Розширення протоколу S4U2self (Service-for-User) для запиту квитка сервісом від імені довіреного користувача. |

Сучасний Kerberos v5 реалізує модульну криптографічну архітектуру відповідно до RFC 3961. Алгоритми шифрування розділені на профілі:

```
Номер etype 18: aes256-cts-hmac-sha1-96

Номер etype 23: rc4-hmac (ARCFOUR-HMAC-MD5, спадщина Microsoft Windows NT/2000)
```

## Двійковий формат сертифіката привілеїв Microsoft (MS-PAC)

Сертифікат MS-PAC передається всередині поля `authorization-data` квитка як елемент із типом `AD-WIN2K-PAC` (числове значення `128`). Він містить повну інформацію про ідентифікатори безпеки (SID), членство в групах та права користувача в домені Active Directory.

### Заголовок PACTYPE та таблиця дескрипторів

Структура починається 8-байтовим заголовком, за яким слідує масив дескрипторів буферів `PAC_INFO_BUFFER`:

```text
typedef struct _PACTYPE {
    ULONG cBuffers;                     // Кількість інформаційних буферів у масиві
    ULONG Version;                      // Версія структури (завжди 0x00000000)
    PAC_INFO_BUFFER Buffers[1];         // Масив розміром cBuffers
} PACTYPE;

typedef struct _PAC_INFO_BUFFER {
    ULONG ulType;                       // Тип даних буфера (ідентифікатор вмісту)
    ULONG cbBufferSize;                 // Розмір буфера в байтах
    ULONG64 Offset;                     // Зсув у байтах від початку заголовка PACTYPE (вирівняно на 8 байтів)
} PAC_INFO_BUFFER;
```

### Реєстр ідентифікаторів буферів PAC (`ulType`)

```
0x00000001 : PAC_LOGON_INFO
             Структура KERB_VALIDATION_INFO: містить User SID, Primary Group RID,
             масив Group SIDs (доменні групи, включно з Domain Admins),
             прапорці UserAccountControl та налаштування профілю.

0x00000006 : PAC_SERVER_CHECKSUM
             Криптографічний підпис вмісту PAC на ключі служби K_s.

0x00000007 : PAC_PRIVSVR_CHECKSUM
             Криптографічний підпис KDC на секретному ключі K_{tgs} (облікового запису krbtgt).

0x0000000A : PAC_CLIENT_INFO
             Містить часову мітку клієнта та ім'я облікового запису у форматі Unicode.

0x0000000B : PAC_CONSTRAINED_DELEGATION_INFO
             Список служб для протоколу обмеженого делегування S4U2proxy.

0x0000000C : PAC_UPN_DNS_INFO
             Повне доменне ім'я (FQDN) та UPN користувача.

0x00000010 : PAC_ATTRIBUTES_INFO
             Бітові прапорці стану та атрибутів захисту структури PAC.
```

### Механізм формування та верифікації подвійного підпису PAC

Цілісність та автентичність сертифіката MS-PAC гарантуються каскадом двох цифрових підписів `PAC_SIGNATURE_DATA`:

```text
typedef struct _PAC_SIGNATURE_DATA {
    ULONG SignatureType;                // Алгоритм підпису: KERB_CHECKSUM_HMAC_SHA1_96_AES256 (0x10)
                                        // або KERB_CHECKSUM_HMAC_MD5 (-138)
    UCHAR Signature[1];                 // Байти криптографічного HMAC
    USHORT ROCA_Reserved;               // Резервне поле вирівнювання
} PAC_SIGNATURE_DATA;
```

1. **Формування `PAC_SERVER_CHECKSUM`**: KDC створює структуру `PACTYPE`, заповнює всі інформаційні буфери, а в полях підписів записує нулі. Далі обчислюється HMAC від усього двійкового тіла `PACTYPE` на довгостроковому ключі служби `K_s`. Отриманий хеш записується в буфер `PAC_SERVER_CHECKSUM`. Сервер додатку перевіряє цей підпис під час обробки `AP-REQ` власним ключем `K_s`, що підтверджує: жоден мережевий вузол не змінив список груп користувача.
2. **Формування `PAC_PRIVSVR_CHECKSUM`**: KDC бере байти щойно згенерованого підпису `PAC_SERVER_CHECKSUM` і обчислює від них другий HMAC, використовуючи власний секретний ключ KDC `K_{tgs}` (ключ облікового запису `krbtgt`). Отримане значення записується в буфер `PAC_PRIVSVR_CHECKSUM`.
3. **Захист від ескалації привілеїв сервером**: Якби існував лише підпис сервера, скомпрометований цільовий сервер із відомим ключем `K_s` міг би самостійно змінити групи в розшифрованому PAC (додати собі права `Domain Admins`), перерахувати `PAC_SERVER_CHECKSUM` і звернутися до інших систем. Наявність `PAC_PRIVSVR_CHECKSUM` повністю блокує цей сценарій: сервер не знає ключа `K_{tgs}`, тому не здатний підробити підпис KDC. При зверненні до критичних ресурсів сервер перевірки може відправити PAC контролеру домену через RPC-виклик `NetrLogonSamLogon` для звірки підпису KDC.

## Транспортні прив'язки: UDP, TCP та проблема великих квитків (Large Tickets)

Протокол Kerberos v5 стандартизований для роботи як поверх ненадійного протоколу UDP, так і поверх повнодуплексних потоків TCP (обидва використовують зарезервований порт IANA `88`):

### 1. Передавання через UDP

При передаванні через UDP повідомлення Kerberos вміщується в єдину датаграму без додаткових транспортних заголовків. Оскільки протокол працює за схемою «запит — відповідь», клієнт самостійно реалізує механізм тайм-аутів і повторних спроб (типово 3 спроби з інтервалом 1–2 секунди).

Історично UDP був основним транспортом через мінімальні накладні витрати на встановлення з'єднання. Проте із впровадженням сертифікатів авторизації MS-PAC та списків членства в численних групах розмір повідомлень `KRB_AS_REP` та `KRB_TGS_REP` зріс від кількох сотень байтів до 8–16 кілобайтів. Якщо розмір зашифрованого квитка перевищує типовий розмір максимального блоку передачі мережі (MTU, зазвичай 1500 байтів), UDP-датаграма фрагментується на рівні IP. Втрата хоча б одного фрагмента на проміжних маршрутизаторах чи блокування фрагментованих пакетів міжмережевими екранами (Firewall) призводить до повної відмови автентифікації.

### 2. Передавання через TCP та заголовок довжини

Для вирішення проблеми фрагментації RFC 4120 встановлює граничний поріг розміру повідомлення (типово 1465 байтів). Якщо відповідь KDC перевищує цей поріг або клієнт заздалегідь очікує великий квиток, використовується TCP-з'єднання.

Оскільки TCP є неперервним байтовим потоком без меж повідомлень, стандарт Kerberos v5 вимагає додавання 4-байтового префікса довжини перед кожним ASN.1 DER пакетом:

```
+-----------------------------------+-----------------------------------+
|  4 байти (довжина в Big-Endian)    |   ASN.1 DER кодоване повідомлення  |
+-----------------------------------+-----------------------------------+
```

Префікс є 32-бітним беззнаковим цілим числом у мережевому порядку байтів (Big-Endian), яке позначає точний розмір наступного блоку ASN.1 DER у байтах без урахування самих чотирьох байтів заголовка.

Якщо клієнт надіслав запит через UDP, а підготовлена відповідь перевищує ліміт буфера, KDC повертає коротке повідомлення про помилку `KRB_ERROR` з кодом `KRB_ERR_RESPONSE_TOO_BIG` (код `52`). Отримавши таку відповідь, клієнтський стек зобов'язаний негайно відкрити TCP-з'єднання до порту 88 KDC та повторити запит із 4-байтовим префіксом довжини.

## Криптографічні номери використання ключів (Key Usage Numbers)

Фундаментальним механізмом захисту від атак міжпротокольної підміни та змішування повідомлень у Kerberos v5 є концепція числових ідентифікаторів використання ключів (англ. *Key Usage Numbers*), формалізована в RFC 3961.

Коли протокол використовує один і той самий симетричний сесійний ключ для шифрування різних структур даних (наприклад, для шифрування автентифікатора клієнта та відповіді сервера AP-REP), зловмисник міг би перехопити шифротекст з одного повідомлення та підсунути його замість іншого. Щоб унеможливити подібні атаки, Kerberos v5 ніколи не шифрує дані безпосередньо базовим сесійним ключем. Натомість базовий ключ `K` пропускається через функцію деривації (KDF, англ. *Key Derivation Function*), параметризовану унікальним числовим ідентифікатором призначення:

```
K_derived = KDF(K, Key_Usage_Number)
```

| Номер використання | Символічна назва константи | Цільова структура та захищена операція |
|---|---|---|
| 1 | `KU_PA_ENC_TIMESTAMP` | Зашифрована мітка часу преавтентифікації `PA-ENC-TIMESTAMP` у запиті `AS-REQ` (на ключі користувача `K_c`). |
| 2 | `KU_TICKET` | Зашифрована частина квитка `EncTicketPart` (на ключі служби `K_s` або ключі `K_{tgs}`). |
| 3 | `KU_AS_REP_ENC_PART` | Зашифрована частина відповіді `EncKDCRepPart` у повідомленні `AS-REP` (на ключі користувача `K_c`). |
| 7 | `KU_TGS_REQ_AUTH` | Автентифікатор у запиті `TGS-REQ` (на сесійному ключі TGT `K_{c,tgs}`). |
| 8 | `KU_TGS_REP_ENC_PART` | Зашифрована частина відповіді `EncKDCRepPart` у повідомленні `TGS-REP` (на сесійному ключі TGT `K_{c,tgs}`). |
| 11 | `KU_AP_REQ_AUTH` | Автентифікатор у запиті `AP-REQ` до сервера додатку (на сервісному сесійному ключі `K_{c,s}`). |
| 12 | `KU_AP_REP_ENC_PART` | Зашифрована відповідь взаємної автентифікації `EncAPRepPart` у повідомленні `AP-REP` (на ключі `K_{c,s}`). |
| 15 | `KU_KRB_SAFE_CKSUM` | Контрольна сума прикладних даних у повідомленні `KRB_SAFE`. |
| 16 | `KU_KRB_PRIV_ENC_PART` | Зашифроване тіло прикладного повідомлення `KRB_PRIV`. |

Завдяки розділенню ключів за номерами використання шифротекст автентифікатора, згенерований клієнтом із номером `11`, ніколи не буде успішно розпізнаний як валідна відповідь сервера з номером `12`, навіть якщо вони використовують ідентичний сесійний ключ `K_{c,s}`.

## Алгоритм синтаксичного розбору та верифікації квитка на сервері

Під час надходження запиту `KRB_AP_REQ` сервер додатку виконує сувору послідовність перевірок:

1. **Десеріалізація зовнішнього тегу `AP-REQ`**: Сервер перевіряє тег `[APPLICATION 14]`, номер версії `pvno == 5` та поле `msg-type == 14`.
2. **Вилучення квитка `Ticket`**: Зчитується поле `sname` та версія ключа `kvno`. За цими даними сервер вибирає відповідний довгостроковий ключ служби `K_s` зі свого локального сховища секретів (`keytab`).
3. **Розшифрування `EncTicketPart`**: Блок `enc-part` розшифровується за допомогою `K_s` із номером використання `Key Usage = 2`. Якщо контрольна сума цілісності не сходиться, сервер негайно повертає помилку `KRB_AP_ERR_BAD_INTEGRITY` (код `31`).
4. **Перевірка часових меж квитка**: Сервер порівнює поточний системний час `T_{now}` із полями квитка:
   - Якщо `T_{now} < authtime - Δ t` або `T_{now} < starttime - Δ t`, квиток ще не набув чинності.
   - Якщо `T_{now} > endtime + Δ t`, квиток вважається застарілим і повертається помилка `KRB_AP_ERR_TKT_EXPIRED` (код `32`).
5. **Вилучення сесійного ключа `K_{c,s}`**: Із розшифрованого `EncTicketPart` зчитується поле `key`.
6. **Розшифрування `Authenticator`**: Блок `authenticator` із структури `AP-REQ` розшифровується витягнутим сесійним ключем `K_{c,s}` із номером використання `Key Usage = 11`.
7. **Звірка імен принципалів**: Сервер строго порівнює `crealm` та `cname` з квитка з полями `crealm` та `cname` з автентифікатора. Будь-яка розбіжність призводить до блокування запиту з кодом `KRB_AP_ERR_BADMATCH` (код `36`).
8. **Перевірка вікна розсинхронізації часу (Clock Skew)**: Сервер обчислює різницю `|T_{now} - ctime|`. Якщо абсолютна похибка перевищує допустиме вікно (типово 300 секунд), повертається помилка `KRB_AP_ERR_SKEW` (код `37`).
9. **Перевірка кешу повторів (Replay Cache)**: Сервер шукає запис `(cname, ctime, cusec)` у локальному кеші. Якщо запис знайдено — фіксується атака повтору з кодом `KRB_AP_ERR_REPEAT` (код `34`). Якщо запису немає, він додається в кеш із часом життя `Δ t`.
10. **Генерація взаємної відповіді `AP-REP`**: Якщо встановлено прапорець `mutual-required`, сервер створює структуру `EncAPRepPart`, вказує отримані `ctime` та `cusec`, шифрує її ключем `K_{c,s}` із номером використання `Key Usage = 12` і повертає клієнту.

## Реєстр кодів помилок Kerberos (KRB_ERROR)

Коли виникає збій автентифікації, KDC або сервер повертають відкрите повідомлення `KRB_ERROR`, де поле `error-code` містить числовий код причини:

| Код | Символічна назва константи | Причина збою та рекомендована реакція клієнта |
|---|---|---|
| 6 | `KDC_ERR_C_PRINCIPAL_UNKNOWN` | Ім'я клієнта відсутнє в базі KDC. Клієнт має перевірити правильність введеного логіна чи суфікса домену. |
| 7 | `KDC_ERR_S_PRINCIPAL_UNKNOWN` | Запитуваний сервіс (SPN) не зареєстрований у домені. Адміністратор має зареєструвати SPN утилітою `setspn`. |
| 12 | `KDC_ERR_POLICY` | Запит відхилено політикою безпеки (наприклад, перевищено обмеження на години входу або робочі станції). |
| 18 | `KDC_ERR_CLIENT_REVOKED` | Обліковий запис користувача заблоковано через невірні спроби входу, вимкнено або термін дії пароля вичерпано. |
| 24 | `KDC_ERR_PREAUTH_FAILED` | Надані дані преавтентифікації `PA-ENC-TIMESTAMP` не вдалося розшифрувати. Користувач ввів невірний пароль. |
| 25 | `KDC_ERR_PREAUTH_REQUIRED` | KDC повідомляє клієнту, що запит `AS-REQ` без преавтентифікації відхилено, та повертає список солей `PA-ETYPE-INFO2`. Клієнт зобов'язаний повторити запит із зашифрованою міткою часу. |
| 31 | `KRB_AP_ERR_BAD_INTEGRITY` | Помилка розшифрування квитка або автентифікатора на сервері додатку. Свідчить про невідповідність версій ключів (`kvno`) або спробу підробки. |
| 32 | `KRB_AP_ERR_TKT_EXPIRED` | Час дії квитка вичерпано (`endtime < now`). Клієнтська бібліотека має виконати подовження або запросити новий квиток через TGS. |
| 34 | `KRB_AP_ERR_REPEAT` | Виявлено атаку повторного відтворення: хеш автентифікатора вже знайдено в локальному Replay Cache сервера. Запит негайно відхиляється. |
| 37 | `KRB_AP_ERR_SKEW` | Різниця між годинником клієнта та сервера перевищує допустиме вікно (`Δ t > 5` хвилин). Клієнт зобов'язаний синхронізувати системний годинник через NTP. |
| 41 | `KRB_AP_ERR_MODIFIED` | Контрольна сума в автентифікаторі не збігається з тілом прикладного повідомлення: дані були модифіковані в каналі зв'язку. |
| 52 | `KRB_ERR_RESPONSE_TOO_BIG` | Розмір відповіді перевищує ліміт UDP-буфера. Клієнт зобов'язаний переключитися на транспортний протокол TCP. |
