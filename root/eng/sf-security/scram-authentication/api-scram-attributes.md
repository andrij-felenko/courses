# 📋 Специфікація атрибутів, форматів повідомлень та помилок SCRAM

Цей довідник містить технічну специфікацію структури повідомлень, словника атрибутів, граматики GS2, кодів помилок та протокольних кадрів механізму автентифікації SCRAM відповідно до стандартів RFC 5802, RFC 7677 та RFC 5929. У ньому визначено суворий синтаксичний контракт для реалізації клієнтських драйверів та серверних демонів у розподілених системах зв'язку (SASL, PostgreSQL, MongoDB, XMPP, Apache Kafka).

## 1. Реєстр назв механізмів SASL

Протокол SCRAM зареєстровано в офіційному реєстрі IANA SASL під окремими ідентифікаторами залежно від використовуваної криптографічної геш-функції та підтримки прив'язки до каналу TLS (*Channel Binding*):

| Назва механізму SASL | Базова геш-функція | Розмір гешу (байти) | Прив'язка до каналу TLS | Стандарт |
| :--- | :--- | :--- | :--- | :--- |
| `SCRAM-SHA-1` | SHA-1 | 20 | Ні | RFC 5802 |
| `SCRAM-SHA-1-PLUS` | SHA-1 | 20 | Так (обов'язково) | RFC 5802 |
| `SCRAM-SHA-256` | SHA-256 | 32 | Ні | RFC 7677 |
| `SCRAM-SHA-256-PLUS` | SHA-256 | 32 | Так (обов'язково) | RFC 7677 |
| `SCRAM-SHA-512-PLUS` | SHA-512 | 64 | Так (обов'язково) | RFC 5802 / Draft |

Суфікс `-PLUS` однозначно вказує, що протокол вимагає обов'язкової передачі криптографічного відбитка транспортного тунелю TLS і відхиляє з'єднання, якщо зв'язування каналу відсутнє або не зійшлося.

## 2. Граматика заголовка GS2

Кожне початкове повідомлення SCRAM містить стандартизований заголовок GS2 (*Generic Security Services API v2*, RFC 5801), який узгоджує параметри прив'язки до каналу та ідентифікатор авторизації (*Authzid*).

Синтаксис GS2-заголовка визначається правилом:

```
gs2-header = gs2-cb-flag "," [gs2-authzid] ","
```

### Прапорці прив'язки до каналу (gs2-cb-flag)
1. `n` — Клієнт стверджує, що він **не підтримує** прив'язку до каналу (наприклад, з'єднання встановлено без TLS або використовується механізм `SCRAM-SHA-256`).
2. `y` — Клієнт підтримує прив'язку до каналу, але переконаний, що сервер її **не підтримує** (використовується для виявлення спроб примусового пониження захисту посередником).
3. `p=channel-binding-type` — Клієнт використовує конкретний тип прив'язки до каналу (наприклад, `p=tls-server-end-point` або `p=tls-unique` для `SCRAM-SHA-256-PLUS`).

### Ідентифікатор авторизації (gs2-authzid)
Якщо користувач проходить автентифікацію під одним іменем (наприклад, системний адміністратор `admin`), але бажає діяти від імені іншого облікового запису (наприклад, `service-worker`), поле `gs2-authzid` передає префікс `a=service-worker`. Якщо автентифікація та авторизація виконуються під одним акаунтом, це поле залишається порожнім.

**Типові приклади GS2-заголовків:**
- `n,,` — стандартний заголовок без прив'язки каналу та без окремого authzid;
- `n,a=alice,` — автентифікація без прив'язки каналу з дією від імені користувача `alice`;
- `p=tls-server-end-point,,` — заголовок із прив'язкою до TLS-сертифіката сервера.

## 3. Словник атрибутів протоколу

Повідомлення SCRAM формуються як послідовність пар `атрибут=значення`, розділених комами `,`. Будь-які лапки, пробіли навколо знаків рівності чи додаткові розділювачі суворо заборонені.

| Атрибут | Назва поля | Тип даних | Опис та правила кодування |
| :--- | :--- | :--- | :--- |
| `n` | `username` | Рядок UTF-8 | Ім'я користувача (SASLprep). Коми замінюються на `=2C`, знак `=` на `=3D`. |
| `a` | `authzid` | Рядок UTF-8 | Ідентифікатор авторизації (правила екранування як у `n`). |
| `r` | `nonce` | Рядок ASCII | Випадковий виклик. Клієнт генерує `r1`, сервер повертає `r1 ‖ r2`. |
| `s` | `salt` | Base64 | Індивідуальна криптографічна сіль користувача з бази даних сервера. |
| `i` | `iteration-count` | Ціле число | Кількість ітерацій алгоритму PBKDF2 (додатне десяткове число, наприклад `4096`). |
| `c` | `channel-binding` | Base64 | Закодований GS2-заголовок та додаткові дані зв'язування TLS. |
| `p` | `client-proof` | Base64 | Маскований доказ клієнта `ClientProof = ClientKey ⊕ ClientSignature`. |
| `v` | `server-signature` | Base64 | Підтвердження сервера `ServerSignature = HMAC(ServerKey, AuthMessage)`. |
| `e` | `error` | Рядок ASCII | Текстовий ідентифікатор стандартної помилки відхилення автентифікації. |

### Правила синтаксичного аналізу пар атрибутів
1. **Суворий порядок атрибутів:** Перше повідомлення клієнта обов'язково починається з `n=` (після GS2-заголовка), за яким слідує `r=`. Перше повідомлення сервера повинно містити `r=`, `s=`, `i=` саме у зазначеному порядку.
2. **Заборона дублікатів:** Повторна поява одного й того самого атрибута в межах одного повідомлення вважається критичною синтаксичною помилкою (`invalid-encoding`).
3. **Невідомі розширення:** Атрибути, що починаються з літери `m=` (*Mandatory Extension*), є обов'язковими розширеннями. Якщо сервер або клієнт не розпізнає назву розширення `m=`, він зобов'язаний негайно перервати автентифікацію з помилкою `extensions-not-supported`. Будь-які інші невідомі атрибути (наприклад, необов'язкові розширення) ігноруються.

## 4. Специфікація чотирьох повідомлень протокольного обміну

Повний цикл автентифікації складається з двох обертів повідомлень (чотирьох кроків).

### 1. Перше повідомлення клієнта (client-first-message)
Клієнт ініціює сесію, передаючи GS2-заголовок та власну частину повідомлення (*bare message*):

```
client-first-message = gs2-header client-first-message-bare
client-first-message-bare = [reserved-mext ","] username "," nonce ["," extensions]
```

**Приклад у дроті:**
```
n,,n=user,r=fyko+d2lbbFgONRv9qkxdawL
```

### 2. Перше повідомлення сервера (server-first-message)
Сервер перевіряє наявність користувача, обирає його параметри з бази даних, генерує додатковий випадковий виклик `r2` і надсилає відповідь:

```
server-first-message = [reserved-mext ","] nonce "," salt "," iteration-count ["," extensions]
```

**Приклад у дроті:**
```
r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j,s=QSXCR+Q6sek8bf92,i=4096
```

### 3. Фінальне повідомлення клієнта (client-final-message)
Клієнт виконує `PBKDF2`, формує `ClientProof`, додає атрибут прив'язки каналу `c=` і повертає доказ:

```
client-final-message = client-final-message-without-proof "," proof
client-final-message-without-proof = channel-binding "," nonce ["," extensions]
proof = "p=" base64-encoded-proof
```

**Приклад у дроті:**
```
c=biws,r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j,p=v0X8v3Bz2T0CJGbJQwF0X+HIoipvf0BlZoOqg2o05VQ=
```

### 4. Фінальне повідомлення сервера (server-final-message)
Сервер верифікує доказ клієнта. У разі успіху він надсилає підтверджувальний підпис `v=`, а в разі помилки — атрибут помилки `e=`:

```
server-final-message = (server-error / server-signature) ["," extensions]
server-signature = "v=" base64-encoded-signature
server-error = "e=" error-message
```

**Приклад успішної відповіді:**
```
v=rmF9pqV8S7suAoZWja4EzGhrrgeyHardDoSjhUK998U=
```

**Приклад повідомлення про помилку:**
```
e=invalid-proof
```

## 5. Стандартні коди помилок сервера

Стандарт RFC 5802 визначає закритий перелік офіційних кодів помилок, які повертаються в атрибуті `e=`:

| Код помилки | Значення та причина виникнення |
| :--- | :--- |
| `invalid-encoding` | Порушено синтаксис UTF-8 або базове форматування пар `атрибут=значення`. |
| `extensions-not-supported` | Клієнт надіслав обов'язкове розширення `m=`, яке сервер не підтримує. |
| `invalid-proof` | Наданий `ClientProof` є невірним (помилковий пароль або порушено цілісність). |
| `channel-bindings-dont-match` | Відбиток каналу TLS у клієнта не збігається з відбитком сервера (атака MITM). |
| `server-does-support-channel-binding` | Клієнт заявив `y`, але сервер насправді підтримує прив'язку до каналу. |
| `channel-binding-not-supported` | Клієнт запросив прив'язку каналу, яка не налаштована на сервері. |
| `unsupported-channel-binding-type` | Запитано тип прив'язки, невідомий серверу (наприклад, відмінний від `tls-server-end-point`). |
| `unknown-user` | Обліковий запис користувача відсутній у базі даних (якщо сервер не маскує помилку). |
| `invalid-authzid` | Запитаний ідентифікатор авторизації `a=` не дозволений для цього користувача. |
| `other-error` | Внутрішня помилка сховища, вичерпання ресурсів або системний збій. |

## 6. Нормалізація рядків за стандартом SASLprep (RFC 4013)

Для запобігання ситуаціям, коли візуально ідентичні паролі або імена користувачів відхиляються через різні двійкові коди символів Unicode, протокол SCRAM вимагає обов'язкової обробки рядків алгоритмом SASLprep.

Алгоритм SASLprep базується на профілі Stringprep (RFC 3454) і складається з чотирьох послідовних кроків:

1. **Відображення символів (*Mapping*):**
   - Усі нерозривні та керуючі пробіли (наприклад, `U+00A0`, `U+1680`, `U+2000`–`U+200B`) відображаються у стандартний пробіл ASCII `U+0020`.
   - «М'які» переноси та символи нульової ширини (наприклад, `U+00AD`, `U+200C`, `U+200D`) видаляються з рядка.
2. **Канонізація Unicode (*Normalization*):**
   - Рядок перетворюється у канонічну форму сумісності Unicode Normalization Form KC (NFKC). Це зводить складені символи (наприклад, літеру з діакритичним знаком, представлену двома кодовими позиціями) до єдиного нормалізованого коду.
3. **Перевірка заборонених символів (*Prohibited Output*):**
   - Рядок не повинен містити керуючих символів ASCII (`U+0000`–`U+001F`, `U+007F`), символів приватного використання (*Private Use Areas*, `U+E000`–`U+F8FF`), невизначених кодових позицій або замінників сурогатних пар. Виявлення таких символів викликає помилку підготовки рядка.
4. **Перевірка двонаправленого тексту (*Bidirectional Characters*):**
   - Якщо рядок містить символи писемностей справа-наліво (RTL, такі як арабська або іврит), він зобов'язаний починатися та закінчуватися символом категорії RTL і не може змішуватися з символами LTR без суворого дотримання правил Bidi.

## 7. Типи прив'язки до каналу TLS (Channel Binding RFC 5929 / RFC 9266)

У протоколі `SCRAM-SHA-256-PLUS` клієнт та сервер узгоджують тип криптографічної прив'язки до транспортного рівня. Стандарти IETF визначають три основні варіанти:

### 1. `tls-server-end-point` (RFC 5929 §4)
Найпоширеніший та універсальний тип прив'язки для TLS 1.2 та TLS 1.3:
- Відбиток каналу обчислюється як геш SHA-256 від сертифіката сервера у бінарному форматі ASN.1 DER, отриманого клієнтом під час фази рукостискання TLS (`Certificate` handshake message).
- Якщо алгоритм підпису сертифіката використовує сильнішу геш-функцію (наприклад, SHA-384 або SHA-512), використовується відповідна функція, інакше за замовчуванням застосовується SHA-256.

### 2. `tls-unique` (RFC 5929 §3)
Історичний тип прив'язки для протоколів TLS 1.0, 1.1 та 1.2:
- Відбиток формується з двійкових даних першого повідомлення `Finished`, надісланого під час рукостискання TLS (зазвичай 12 байтів).
- **Важливе застереження:** У стандарті TLS 1.3 (RFC 8446) тип `tls-unique` оголошено застарілим і забороненим через зміну архітектури повідомлень `Finished` та вразливість до атак повторного узгодження (*Triple Handshake Attack*).

### 3. `tls-exporter` (RFC 9266)
Сучасний стандарт прив'язки спеціально для протоколу TLS 1.3:
- Відбиток виводиться за допомогою стандартного експортера ключів TLS (*Keying Material Exporter*, RFC 5705) з міткою `"EXPORTER-Channel-Binding"` без контексту, повертаючи 32 байти унікального псевдовипадкового матеріалу, прив'язаного до майстер-секрету поточної сесії.

## 8. Контракт зберігання в базі даних

Сервер SCRAM не зберігає відкритий пароль `Password`, проміжний `SaltedPassword` чи клієнтський ключ `ClientKey`. База даних містить виключно чотири криптографічні поля для кожного користувача:

```
SCRAM-SHA-256$4096:QSXCR+Q6sek8bf92$L57e...=$m9F4...=
│             │    │                │         └─ ServerKey (32 байти, Base64)
│             │    │                └─────────── StoredKey = SHA-256(ClientKey) (32 байти, Base64)
│             │    └──────────────────────────── Сіль користувача (12-16 байтів, Base64)
│             └───────────────────────────────── Кількість ітерацій PBKDF2 (i)
└─────────────────────────────────────────────── Ідентифікатор криптографічного алгоритму
```

### Приклад схеми таблиці (SQL PostgreSQL):
```sql
CREATE TABLE user_credentials (
    username VARCHAR(64) PRIMARY KEY,
    scram_algorithm VARCHAR(32) NOT NULL DEFAULT 'SCRAM-SHA-256',
    iteration_count INT NOT NULL DEFAULT 4096,
    salt BYTEA NOT NULL,
    stored_key BYTEA NOT NULL,
    server_key BYTEA NOT NULL
);
```

## 9. Фреймування повідомлень у прикладних протоколах

SCRAM інтегрується у мережеві протоколи зв'язку через відповідні контейнери прикладного рівня:

### Протокол PostgreSQL Wire Protocol
1. Сервер надсилає повідомлення `AuthenticationSASL` (тип `'R'`, код `10`), що містить нуль-термінований список підтримуваних механізмів: `SCRAM-SHA-256\0\0`.
2. Клієнт відповідає повідомленням `SASLInitialResponse` (тип `'p'`), вказуючи назву механізму та початковий блок `client-first-message`.
3. Сервер надсилає `AuthenticationSASLContinue` (тип `'R'`, код `11`) із вмістом `server-first-message`.
4. Клієнт надсилає `SASLResponse` (тип `'p'`) із вмістом `client-final-message`.
5. Сервер завершує фазу повідомленням `AuthenticationSASLFinal` (тип `'R'`, код `12`) із вмістом `server-final-message`, після чого надсилає `AuthenticationOk` (код `0`).

### Протокол XMPP (Jabber, RFC 6120)
Повідомлення пакуються в XML-елементи простору імен `urn:ietf:params:xml:ns:xmpp-sasl`:

```xml
<!-- Крок 1: Клієнт ініціює автентифікацію -->
<auth xmlns='urn:ietf:params:xml:ns:xmpp-sasl' mechanism='SCRAM-SHA-256'>
  biwsbj11c2VyLHI9ZnlrbytkMmxiYkZnT05Sdjlxa3hkYXdM
</auth>

<!-- Крок 2: Сервер надсилає виклик -->
<challenge xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  cj1meWtvK2QybGJiRmdPTlJ2OXFreGRhd0wzcmZjTkhZSlkxWlZ2V1ZzN2oscz1RU1hDUitRNnNlazhiZjkyLGk9NDA5Ng==
</challenge>

<!-- Крок 3: Клієнт передає доказ -->
<response xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  Yz1iaXdzLHI9ZnlrbytkMmxiYkZnT05Sdjlxa3hkYXdMM3JmY05IWUpZMVpWdldWczdqLHA9djBYOHYzQnoyVDBDSkdiSlF3RjBYK0hJb2lwdmYwQmxaT09xZzJvMDVWUT0=
</response>

<!-- Крок 4: Сервер підтверджує успіх -->
<success xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  dj1ybUY5cHFWOFM3c3VBb1pXamE0RXpHaHJyZ2V5SGFyZERvU2poVUs5OThVPQ==
</success>
```

### Протокол MongoDB Wire Protocol (BSON Commands)
У базі даних MongoDB автентифікація SCRAM здійснюється через запуск спеціальних BSON-команд над системною базою даних `admin` або `$external`:

1. Клієнт надсилає команду `saslStart`:
   ```json
   {
     "saslStart": 1,
     "mechanism": "SCRAM-SHA-256",
     "payload": BinData(0, "n,,n=user,r=fyko+d2lbbFgONRv9qkxdawL"),
     "autoAuthorize": 1
   }
   ```
2. Сервер повертає BSON-документ із полем `conversationId` та `payload` (що містить рядок `server-first-message`):
   ```json
   {
     "conversationId": 1,
     "done": false,
     "payload": BinData(0, "r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j,s=QSXCR+Q6sek8bf92,i=4096"),
     "ok": 1.0
   }
   ```
3. Клієнт відповідає командою `saslContinue`, передаючи `conversationId` та `client-final-message`:
   ```json
   {
     "saslContinue": 1,
     "conversationId": 1,
     "payload": BinData(0, "c=biws,r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j,p=v0X8v3Bz2T0CJGbJQwF0X+HIoipvf0BlZoOqg2o05VQ=")
   }
   ```
4. Сервер повертає фінальне підтвердження з `"done": true` та `payload` із вмістом `server-final-message` (`v=...`).

### Протокол Apache Kafka SASL
У розподіленому брокері повідомлень Apache Kafka автентифікація SCRAM виконується на початку TCP-сесії за допомогою двох бінарних запитів Kafka Protocol:
1. `SaslHandshakeRequest` (API Key `17`): Клієнт передає рядок `"SCRAM-SHA-256"`. Брокер підтверджує готовність або повертає список дозволених механізмів.
2. `SaslAuthenticateRequest` (API Key `36`): Клієнт передає байти `client-first-message`. Брокер повертає відповідь `SaslAuthenticateResponse` із даними `server-first-message`. Подальший обмін продовжується повторними викликами `SaslAuthenticateRequest` до завершення процедури з кодом помилки `0` (*NoError*).

## 10. Матриця переходів скінченного автомата (State Machine)

Коректна реалізація SCRAM-клієнта та сервера повинна керуватися суворою матрицею станів, що запобігає атакам порушення послідовності (*Out-of-Order Message Injection*):

| Поточний стан | Отримане повідомлення | Необхідна дія та перевірка | Наступний стан |
| :--- | :--- | :--- | :--- |
| `INITIAL` (Клієнт) | Виклик `start()` | Генерація `r1`, відправка `client-first-message` | `CLIENT_FIRST_SENT` |
| `INITIAL` (Сервер) | `client-first-message` | Розбір GS2-заголовка, вибірка `Salt, i`, генерація `r2`, відправка `server-first-message` | `SERVER_FIRST_SENT` |
| `CLIENT_FIRST_SENT` (Клієнт) | `server-first-message` | Перевірка префікса `r1` у виклику `r`, виконання `PBKDF2`, відправка `client-final-message` | `CLIENT_FINAL_SENT` |
| `SERVER_FIRST_SENT` (Сервер) | `client-final-message` | Перевірка `c=`, відновлення `ClientKey'`, постійно-часове порівняння `SHA-256(ClientKey') == StoredKey`, відправка `server-final-message` | `AUTHENTICATED` або `FAILED` |
| `CLIENT_FINAL_SENT` (Клієнт) | `server-final-message` (успіх `v=`) | Верифікація `ServerSignature == HMAC(ServerKey, AuthMessage)` | `AUTHENTICATED` |
| `CLIENT_FINAL_SENT` (Клієнт) | `server-final-message` (помилка `e=`) | Розбір коду помилки, закриття сесії | `FAILED` |

Будь-яке повідомлення, отримане не у відповідному стані (наприклад, надходження `client-final-message` до отримання `client-first-message`), вважається протокольною аномалією. Сервер зобов'язаний негайно скинути TCP-з'єднання без розкриття додаткових діагностичних деталей.

## 11. Контрольний чекліст безпеки для розробників

Перед випуском бібліотеки чи модуля SCRAM у промислову експлуатацію необхідно перевірити виконання таких вимог:

1. **Криптографічна випадковість викликів (*CSPRNG*):** Значення `client_nonce` (`r1`) та `server_nonce` (`r2`) повинні генеруватися виключно криптографічно стійким генератором псевдовипадкових чисел (наприклад, `/dev/urandom`, `getrandom()` або `RAND_bytes()` в OpenSSL). Довжина виклику повинна бути не меншою за 18–24 друковані символи ASCII.
2. **Перевірка префікса у виклику сервера:** Клієнт зобов'язаний суворо перевірити, що отриманий від сервера комбінований виклик `r` починається точно з надісланого ним раніше рядка `r1`. Якщо префікс відрізняється, клієнт повинен негайно припинити обмін.
3. **Строга перевірка незмінності `AuthMessage`:** Обидві сторони повинні гарантувати, що рядок `AuthMessage` містить саме ті байти повідомлень, які були передані та прийняті через мережу, включаючи GS2-заголовок та атрибут `c=`.
4. **Константний час обробки помилок:** Час відповіді сервера при неправильному паролі не повинен відрізнятися від часу відповіді при неіснуючому імені користувача (застосування механізму фіктивної солі).
5. **Захист від спуфінгу каналу в TLS-проксі:** У разі використання `SCRAM-SHA-256-PLUS` клієнт зобов'язаний перевіряти сертифікат кінцевого вузла і не допускати підміни `tls-server-end-point` на відкритий незахищений режим `n,,`.

## 12. Еталонний двійковий трасувальний слід (RFC 7677 Trace)

Для верифікації низькорівневих криптографічних блоків та перевірки коректності побітових операцій стандарт RFC 7677 наводить повний двійковий відбиток проміжних буферів:

### Вхідні тестові дані:
- `Password`: `pencil` (6 байтів ASCII: `70 65 6e 63 69 6c`)
- `Salt` (двійкова, 12 байтів):
  `41 25 c2 47 e4 3a b1 e9 3c 6d ff 76`
- `Iteration count (i)`: `4096`

### Проміжні криптографічні масиви (по 32 байти):
1. **`SaltedPassword`** (вихід `PBKDF2-HMAC-SHA-256`):
   `4c cd a9 8b ab a2 62 a8 f5 0c 18 1e b5 f1 72 26 09 f8 91 de f5 a7 23 88 56 61 a1 fd 8a 8a ad b0`
2. **`ClientKey`** (`HMAC(SaltedPassword, "Client Key")`):
   `52 e3 b5 8e a0 d4 81 74 19 63 d6 a1 67 a0 d0 b3 27 5f 09 30 7a d6 89 d0 a2 c2 a5 a0 f4 f2 ed ee`
3. **`StoredKey`** (`SHA-256(ClientKey)`):
   `7e cf c6 a7 fa 09 1d a9 1a 45 42 de 7d c1 ba b0 67 d5 a3 e0 92 63 cf 44 23 93 2d dc 1b e8 fd ee`
4. **`ServerKey`** (`HMAC(SaltedPassword, "Server Key")`):
   `ae cb ed fc f4 42 71 ee 49 a2 41 85 8b 4e f9 33 53 e2 54 8d a9 b8 a6 b5 ad 2a ff 93 a1 ec df 21`

### Розрахунок доказу та підтвердження для AuthMessage:
- **`AuthMessage`** (192 байти ASCII):
  `n=user,r=fyko+d2lbbFgONRv9qkxdawL,r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j,s=QSXCR+Q6sek8bf92,i=4096,c=biws,r=fyko+d2lbbFgONRv9qkxdawL3rfcNHYJY1ZVvWVs7j`
- **`ClientSignature`** (`HMAC(StoredKey, AuthMessage)`):
   `df 45 fc bf 70 73 d9 3d 02 24 66 c9 43 01 74 5f e1 c8 a2 2a 6f 7f 40 65 66 83 aa 83 6a 34 e5 54`
- **`ClientProof`** (`ClientKey ⊕ ClientSignature`):
   `8d a6 49 bf 70 73 d9 3d 02 24 66 c9 43 01 74 5f e1 c8 a2 2a 6f 7f 40 65 66 83 aa 83 6a 34 e5 55` (Base64: `v0X8v3Bz2T0CJGbJQwF0X+HIoipvf0BlZoOqg2o05VQ=`)
- **`ServerSignature`** (`HMAC(ServerKey, AuthMessage)`):
   `ae 61 7d a6 a5 7c 4b bb 2e 02 86 56 8d ae 04 c6 68 6b ae 07 b2 1d a8 cd 0e 84 a3 85 42 bd f7 c5` (Base64: `rmF9pqV8S7suAoZWja4EzGhrrgeyHardDoSjhUK998U=`)

## 13. Повна граматика ABNF (RFC 5802 / RFC 7677)

Для побудови валідаторів та генераторів повідомлень наведено формальну граматику ABNF (RFC 5234):

```
scram-message       = (client-first-message /
                       server-first-message /
                       client-final-message /
                       server-final-message)

gs2-header          = gs2-cb-flag "," [gs2-authzid] ","
gs2-cb-flag         = ("p=" cb-name) / "n" / "y"
cb-name             = 1*(ALPHA / DIGIT / "." / "-")
gs2-authzid         = "a=" saslname

client-first-message = gs2-header client-first-message-bare
client-first-message-bare = [reserved-mext ","] username "," nonce ["," extensions]

username            = "n=" saslname
saslname            = 1*(value-safe-char / "=2C" / "=3D")
value-safe-char     = %x01-2B / %x2D-3C / %x3E-7F / UTF8-2 / UTF8-3 / UTF8-4

nonce               = "r=" 1*printable-char
printable-char      = %x21-2B / %x2D-7E

server-first-message = [reserved-mext ","] nonce "," salt "," iteration-count ["," extensions]
salt                = "s=" base64-value
iteration-count     = "i=" 1*DIGIT

client-final-message = client-final-message-without-proof "," proof
client-final-message-without-proof = channel-binding "," nonce ["," extensions]
channel-binding     = "c=" base64-value
proof               = "p=" base64-value

server-final-message = (server-error / server-signature) ["," extensions]
server-signature    = "v=" base64-value
server-error        = "e=" error-message
error-message       = 1*value-safe-char

reserved-mext       = "m=" 1*(ALPHA / DIGIT / "-")
extensions          = attr-val *("," attr-val)
attr-val            = ALPHA "=" 1*value-safe-char
base64-value        = 1*(ALPHA / DIGIT / "+" / "/" / "=")
```

Дотримання цієї граматики виключає будь-які синтаксичні неоднозначності та забезпечує стовідсоткову сумісність між різними мовами програмування та платформами.

## 14. Пастки синтаксичного розбору та захист від ін'єкцій

При розробці парсерів повідомлень SCRAM інженери часто припускаються типових помилок, що відкривають вразливості:

1. **Небезпека використання стандартних функцій поділу рядків (`strtok` / `split`):**
   - Використання розділювача коми `,` без урахування екранування призводить до некоректного розбору імен користувачів, що містять послідовності `=2C`. Парсер зобов'язаний спочатку розбивати рядок на атрибути за символом коми, і лише потім виконувати декодування послідовностей `=2C` (кома) та `=3D` (знак рівності) у значенні поля `n=`.
   - Зворотний порядок дій (розкодування перед розбиттям) дозволяє зловмиснику створити ім'я користувача, яке після розкодування додасть фальшиві поля (наприклад, підроблений виклик `r=` або прапорець `m=`), спричинивши атаку ін'єкції атрибутів (*Attribute Injection*).
2. **Перевірка відсутності завершальних ком (*Trailing Commas*):**
   - Повідомлення SCRAM не повинні містити коми на початку або в кінці рядка (за винятком GS2-заголовка, де кома є структурним розділювачем). Наявність порожніх елементів між комами (наприклад, `n=user,,r=nonce`) є критичною синтаксичною помилкою, яку парсер повинен відхиляти з кодом `invalid-encoding`.
3. **Обмеження розміру буферів та захист від вичерпання пам'яті (*DoS*):**
   - Довжина імен користувачів, викликів та полів Base64 повинна бути суворо обмежена (наприклад, не більше 1024 байтів на повідомлення). Це запобігає атакам переповнення пам'яті та зависанню регулярних виразів (*ReDoS*).
4. **Сувора перевірка валідності UTF-8:**
   - Усі текстові поля (`n=`, `a=`) повинні проходити обов'язкову перевірку на коректність послідовностей байтів UTF-8. Неприпустимі байти (наприклад, неповні мультибайтові послідовності або наддовгі кодування *Overlong UTF-8 Encoded Characters*) повинні негайно викликати помилку `invalid-encoding`, оскільки вони можуть використовуватися для обходу фільтрів безпеки та ін'єкцій у внутрішні структури баз даних.
