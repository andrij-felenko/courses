# 📋 Специфікація точок входу OIDC, параметрів запитів та структури тверджень

Повноцінна інтеграція з провайдерами OpenID Connect та OAuth 2.0 вимагає точного знання структури протокольних кінцевих точок, правил формування запитів та семантики стандартних тверджень (claims) у токенах і документах конфігурації. Цей довідник містить повну специфікацію документа автоматичного виявлення метаданих OIDC Discovery, параметрів точок авторизації, виштовхнутої авторизації (PAR), обміну токенів, деталізованих авторизаційних запитів (RAR), потоку авторизації пристроїв (Device Grant, RFC 8628), інтроспекції, відкликання, сесійного виходу, динамічної реєстрації клієнтів (RFC 7591) та реєстру протокольних помилок за стандартами OpenID Connect Core 1.0, RFC 6749, RFC 7636, RFC 7662, RFC 7009, RFC 9126, RFC 9396 та RFC 8414.

---

### 1. Документ виявлення конфігурації (OIDC Discovery Metadata)

Документ автоматичного виявлення метаданих дозволяє клієнтським застосункам динамічно отримувати повну інформацію про можливості та адреси сервера ідентичності без ручного копіювання адрес кінцевих точок. Відповідно до специфікації OpenID Connect Discovery 1.0 та RFC 8414 (OAuth 2.0 Authorization Server Metadata), документ публікується за фіксованим уніфікованим шляхом:

```
GET /.well-known/openid-configuration HTTP/1.1
Host: <issuer-domain>
```

#### Інваріанти валідації та життєвого циклу
1. **Сувора відповідність схеми HTTPS**: документ повинен обслуговуватися виключно через протокол TLS/HTTPS із дійсним довіреним сертифікатом. Використання незахищеного HTTP суворо заборонено навіть у середовищах розробки.
2. **Точність ідентифікатора видавця (`issuer`)**: рядок `issuer` у документі зобов'язаний посимвольно збігатися з базовим URL провайдера. Будь-які відмінності (наявність або відсутність кінцевого слеша `/`, регістр літер чи неявний порт) вважаються критичною помилкою конфігурації. Клієнт зобов'язаний відхилити документ, якщо отримане значення `issuer` не збігається з адресою, за якою було виконано запит.
3. **Кешування та оновлення**: сервер авторизації зобов'язаний надавати заголовок `Cache-Control` (зазвичай `public, max-age=86400`). Клієнт зберігає документ у пам'яті на зазначений проміжок часу, однак при виявленні невідомого ідентифікатора ключа `kid` у вхідних токенах виконує негайне примусове перезапитування документа конфігурації.

| Параметр метаданих | Тип | Обов'язковість | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `issuer` | `string (URI)` | **Обов'язковий** | Точний URL провайдера ідентичності. Повинен використовувати схему `https://` (без портів та query-параметрів) і точно збігатися з твердженням `iss` у виданих ID-токенах. |
| `authorization_endpoint` | `string (URI)` | **Обов'язковий** | URL кінцевої точки авторизації (фронт-канал) для перенаправлення користувача на екран входу та надання прав. |
| `token_endpoint` | `string (URI)` | **Обов'язковий** | URL кінцевої точки видачі токенів (бек-канал) для обміну авторизаційного коду, оновлення токенів або клієнтської автентифікації. |
| `jwks_uri` | `string (URI)` | **Обов'язковий** | URL документа з набором відкритих ключів провайдера у форматі JSON Web Key Set (RFC 7517) для перевірки підписів токенів. |
| `userinfo_endpoint` | `string (URI)` | Рекомендований | URL кінцевої точки захищеного API для отримання розширеного профілю користувача за пред'явленням `access_token`. |
| `registration_endpoint` | `string (URI)` | Опціональний | URL точки динамічної реєстрації клієнтів за специфікацією RFC 7591 (Dynamic Client Registration). |
| `pushed_authorization_request_endpoint` | `string (URI)` | Опціональний | URL точки PAR (RFC 9126) для попереднього виштовхування параметрів авторизаційного запиту через бек-канал. |
| `device_authorization_endpoint` | `string (URI)` | Опціональний | URL точки ініціалізації авторизації пристроїв без повноцінного браузера (RFC 8628 Device Authorization Grant). |
| `scopes_supported` | `array of string` | Рекомендований | Перелік усіх підтримуваних провайдером дозволів (обов'язково містить `openid`, а також `profile`, `email`, `offline_access` тощо). |
| `response_types_supported` | `array of string` | **Обов'язковий** | Список підтримуваних типів відповіді на точці `/authorize` (для сучасних конфігурацій: `["code"]`). |
| `response_modes_supported` | `array of string` | Опціональний | Способи передачі параметрів відповіді клієнту (`query`, `fragment`, `form_post`). |
| `grant_types_supported` | `array of string` | Опціональний | Перелік підтримуваних типів потоків надання прав (`authorization_code`, `refresh_token`, `client_credentials`, `urn:ietf:params:oauth:grant-type:device_code`). |
| `subject_types_supported` | `array of string` | **Обов'язковий** | Типи ідентифікаторів суб'єкта: `public` (однаковий `sub` для всіх клієнтів) або `pairwise` (унікальний псевдонім `sub` для кожного окремого клієнта). |
| `id_token_signing_alg_values_supported` | `array of string` | **Обов'язковий** | Підтримувані алгоритми цифрового підпису ID-токенів (`RS256`, `ES256`, `EdDSA`, `PS256`). Значення `none` суворо заборонене для публічних провайдерів. |
| `token_endpoint_auth_methods_supported` | `array of string` | Опціональний | Дозволені методи автентифікації клієнта на точці `/token` (`client_secret_basic`, `client_secret_post`, `private_key_jwt`, `none`). |
| `claims_supported` | `array of string` | Рекомендований | Список імен тверджень, які можуть повертатися в `id_token` та відповіді `/userinfo` (`sub`, `iss`, `name`, `email`, `picture` тощо). |
| `code_challenge_methods_supported` | `array of string` | Рекомендований | Підтримувані методи PKCE. Сучасні стандарти вимагають обов'язкової наявності `["S256"]`. |
| `introspection_endpoint` | `string (URI)` | Опціональний | URL точки інтроспекції токенів за RFC 7662 для перевірки валідності непрозорих (opaque) токенів ресурсними серверами. |
| `revocation_endpoint` | `string (URI)` | Опціональний | URL точки відкликання токенів за RFC 7009 для анулювання токенів доступу та оновлення при виході користувача. |
| `end_session_endpoint` | `string (URI)` | Опціональний | URL точки ініціалізації виходу (RP-Initiated Logout) для синхронного завершення сесії користувача на IdP. |

### 2. Кінцева точка авторизації (Authorization Endpoint)

Кінцева точка авторизації призначена для взаємодії з користувачем через його веб-браузер. Тут відбувається процес підтвердження особи, запит додаткових факторів автентифікації (MFA) та явне надання користувачем згоди (Consent Screen) на доступ стороннього застосунку до зазначених ресурсів.

#### Семантика формування запиту
Запит надсилається методом `GET` (або `POST` у разі передачі великого набору параметрів). Усі параметри повинні бути закодовані за правилами процентного кодування (URL-encoding, RFC 3986).

Клієнт зобов'язаний згенерувати та передати випадкове значення `state` для запобігання міжсайтовій підробці запитів (CSRF), а також випадковий рядок `nonce` та параметри захисту `code_challenge` і `code_challenge_method=S256` за специфікацією PKCE (RFC 7636).

| Параметр | Тип | Обов'язковість | Опис та вимоги стандарту |
| :--- | :--- | :--- | :--- |
| `response_type` | `string` | **Обов'язковий** | Тип очікуваного результату. Для сучасного потоку коду авторизації значення строго `code`. |
| `client_id` | `string` | **Обов'язковий** | Унікальний ідентифікатор клієнтського застосунку, виданий під час реєстрації в системі IdP. |
| `redirect_uri` | `string (URI)` | **Обов'язковий** | Зворотна адреса клієнта, на яку браузер перенаправляється після завершення входу. Мусить посимвольно збігатися з зареєстрованим значенням. |
| `scope` | `string` | **Обов'язковий** | Список дозволів через пробіл. Для ввімкнення OIDC обов'язково містить `openid`. |
| `state` | `string` | **Обов'язковий (BCP)** | Криптографічний токен сесії (мінімум 128 біт ентропії) для захисту від CSRF. Повертається клієнту без змін. |
| `nonce` | `string` | **Обов'язковий для OIDC** | Випадковий рядок клієнта, що вбудовується в ID-токен для захисту від атак повтору. |
| `code_challenge` | `string` | **Обов'язковий (PKCE)** | Базовий відбиток верифікатора: `BASE64URL(SHA256(code_verifier))`. |
| `code_challenge_method` | `string` | **Обов'язковий (PKCE)** | Метод перетворення. Дозволено виключно значення `S256`. |
| `prompt` | `string` | Опціональний | Керування поведінкою інтерфейсу: `none` (тихий вхід), `login` (примусовий ввід пароля), `consent` (примусова згода), `select_account` (вибір облікового запису). |
| `max_age` | `integer` | Опціональний | Максимальний допустимий вік сесії в секундах. Якщо користувач увійшов раніше ніж `max_age` секунд тому, IdP зобов'язаний вимагати повторний ввід пароля. |
| `ui_locales` | `string` | Опціональний | Пріоритетний перелік мов інтерфейсу входу за RFC 5646 (наприклад `uk-UA uk en`). |
| `login_hint` | `string` | Опціональний | Попередня підказка ідентифікатора користувача (email чи логін) для полегшення входу. |

#### Матриця поведінки параметра `prompt`
- `prompt=none`: сервер авторизації не має права відображати жодного користувацького інтерфейсу (форми входу чи екрана згоди). Якщо користувач не автентифікований у поточному браузері або не надав попередньої згоди, сервер негайно повертає перенаправлення з кодом помилки `error=login_required` або `error=interaction_required`. Цей режим використовується для фонової безшовної перевірки сесії в прихованих iframe.
- `prompt=login`: сервер авторизації ігнорує наявну активну сесію SSO і примусово показує форму введення облікових даних, що гарантує фізичну присутність користувача за комп'ютером.
- `prompt=consent`: сервер примусово виводить екран підтвердження дозволів, навіть якщо користувач уже надавав згоду раніше.
- `prompt=select_account`: сервер виводить список відомих облікових записів, дозволяючи користувачеві вибрати потрібний профіль для поточної сесії.

#### Формат успішної та помилкової відповіді
При успішній авторизації сервер повертає статус `302 Found` із заголовком `Location`, що містить параметри у рядку запиту:
```
HTTP/1.1 302 Found
Location: https://client.example.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=x8K2mN9pL3vQ1wR5
```

Якщо користувач відхилив запит або передано некоректні параметри, сервер повертає перенаправлення з описом помилки:
```
HTTP/1.1 302 Found
Location: https://client.example.com/callback?error=access_denied&error_description=User%20denied%20consent&state=x8K2mN9pL3vQ1wR5
```

### 3. Виштовхнуті авторизаційні запити (Pushed Authorization Requests, RFC 9126)

Стандарт PAR кардинально підвищує безпеку етапу авторизації, усуваючи необхідність передавати численні параметри (scopes, claims, redirect_uri, PKCE challenge) через відкритий рядок URL браузера.

#### Архітектурний механізм PAR
1. Клієнтський бекенд виконує прямий захищений HTTPS POST-запит на кінцеву точку `pushed_authorization_request_endpoint` сервера авторизації, передаючи всі параметри запиту авторизації у зашифрованому бек-каналі разом із повноцінною клієнтською автентифікацією (Basic Auth або `private_key_jwt`).
2. Сервер авторизації валідує всі параметри наперед, зберігає їх у внутрішньому сховищі та повертає клієнту короткоживучий непрозорий ідентифікатор запиту `request_uri` (строк дії зазвичай 60–90 секунд):
   ```json
   {
     "request_uri": "urn:ietf:params:oauth:request_uri:6b8b4567-ca58-4c6a-9c4c-28b9f1a23456",
     "expires_in": 90
   }
   ```
3. Клієнт перенаправляє браузер користувача на стандартну точку `/authorize`, передаючи в рядку запиту лише два параметри: `client_id` та отриманий `request_uri`:
   ```
   GET /authorize?client_id=web_app_01&request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3A6b8b4567... HTTP/1.1
   Host: idp.example.com
   ```

Це повністю усуває загрози підміни параметрів у фронт-каналі, запобігає витоку конфіденційних даних через логи проксі-серверів та знімає обмеження на довжину URL при передачі складних об'єктів дозволів (Rich Authorization Requests).

### 4. Кінцева точка видачі токенів (Token Endpoint)

Кінцева точка видачі токенів обслуговує виключно прямі серверні запити бек-каналу. Передача параметрів через відкритий рядок URL у запитах до цієї точки суворо заборонена: клієнт зобов'язаний використовувати метод `POST` із тілом запиту у форматі `application/x-www-form-urlencoded`.

#### Способи автентифікації клієнта на точці `/token`
1. **`client_secret_basic` (RFC 6749 §2.3.1)**: ідентифікатор та секрет клієнта кодуються за стандартом HTTP Basic у заголовку запиту: `Authorization: Basic BASE64(client_id:client_secret)`.
2. **`client_secret_post`**: параметри `client_id` та `client_secret` передаються безпосередньо в тілі POST-запиту.
3. **`private_key_jwt` (RFC 7523)**: клієнт не має статичного пароля, а формує асиметрично підписаний власним закритим ключем JWT (Client Assertion), що містить твердження `iss`, `sub`, `aud` та `exp`. Сервер авторизації верифікує підпис за попередньо зареєстрованим відкритим ключем клієнта.
4. **`tls_client_auth` / `self_signed_tls_client_auth` (RFC 8705)**: автентифікація клієнта відбувається на рівні протоколу TLS за допомогою взаємного пред'явлення X.509 сертифіката (mTLS).
5. **`none` (Публічні клієнти)**: для односторінкових застосунків (SPA) та мобільних клієнтів автентифікація клієнта відсутня, а безпека обміну цілком гарантується перевіркою параметра `code_verifier` за стандартом PKCE.

#### Контракт обміну коду (`grant_type=authorization_code`)

| Параметр тіла | Тип | Обов'язковість | Опис та правила валідації |
| :--- | :--- | :--- | :--- |
| `grant_type` | `string` | **Обов'язковий** | Фіксоване значення `authorization_code`. |
| `code` | `string` | **Обов'язковий** | Одноразовий авторизаційний код, отриманий через редірект. |
| `redirect_uri` | `string (URI)` | **Обов'язковий** | Повинен посимвольно збігатися зі значенням, переданим на кроці `/authorize`. |
| `client_id` | `string` | **Обов'язковий** | Ідентифікатор клієнта (якщо не передано через заголовок Basic Auth). |
| `client_secret` | `string` | Обов'язковий для конфіденційних | Секрет клієнта (за наявності). |
| `code_verifier` | `string` | **Обов'язковий (PKCE)** | Оригінальний секретний рядок 43–128 символів. Сервер обчислює `SHA256` та звіряє з `code_challenge`. |

#### Контракт ротації токенів оновлення (`grant_type=refresh_token`)

| Параметр тіла | Тип | Обов'язковість | Опис та правила валідації |
| :--- | :--- | :--- | :--- |
| `grant_type` | `string` | **Обов'язковий** | Фіксоване значення `refresh_token`. |
| `refresh_token` | `string` | **Обов'язковий** | Дійсний токен оновлення. При ротації старий токен негайно спалюється. |
| `scope` | `string` | Опціональний | Звужений перелік прав (не може перевищувати початковий набір). |
| `client_id` | `string` | **Обов'язковий** | Ідентифікатор клієнта. |
| `client_secret` | `string` | Обов'язковий для конфіденційних | Секрет клієнта. |

#### Контракт облікових даних клієнта (`grant_type=client_credentials`)
Використовується для міжсерверної взаємодії (M2M / Machine-to-Machine) без участі користувача.

| Параметр тіла | Тип | Обов'язковість | Опис та правила валідації |
| :--- | :--- | :--- | :--- |
| `grant_type` | `string` | **Обов'язковий** | Фіксоване значення `client_credentials`. |
| `scope` | `string` | Опціональний | Запитуваний перелік прав доступу до сервісних API. |
| `client_id` | `string` | **Обов'язковий** | Ідентифікатор клієнтського сервісу. |
| `client_secret` | `string` | **Обов'язковий** | Секрет клієнтського сервісу (або Client Assertion). |

#### Успішна відповідь сервера токенів (`200 OK`)
Відповідь повертається у форматі JSON із заголовками `Content-Type: application/json;charset=UTF-8`, `Cache-Control: no-store` та `Pragma: no-cache` (кешування токенів на проміжних проксі суворо заборонено).

  "expires_in": 3600,
  "refresh_token": "r_1a2b3c4d5e6f...",
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjFhMmIzYyJ9.eyJpc3MiOiJodHRwczovL2lkcC5leGFtcGxlLmNvbSIsInN1YiI6InVzcl80MiIsImF1ZCI6IndlYl9hcHBfcHJvZF8wMSIsIm5vbmNlIjoiazlQMm1XOHZONHFMMHpSNiIsImV4cCI6MTczNTczMjgwMCwiaWF0IjoxNzM1NzI5MjAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c",

### 5. Структура та стандартні твердження ID-токена (JWT Claims)

ID-токен — це підписаний об'єкт JSON Web Signature (JWS, RFC 7515). На відміну від `access_token`, формат якого для клієнта є непрозорим, структура `id_token` суворо стандартизована специфікацією OpenID Connect Core 1.0.

#### Структура заголовка (Header)
- `alg`: алгоритм підпису (наприклад `RS256`, `ES256`, `PS256`).
- `typ`: тип токена, фіксоване значення `JWT`.
- `kid`: унікальний ідентифікатор ключа в документі `jwks_uri`, яким підписано даний токен.

#### Стандартні твердження корисного навантаження (Payload)

| Твердження (Claim) | Тип | Обов'язковість | Опис та правила валідації |
| :--- | :--- | :--- | :--- |
| `iss` | `string (URI)` | **Обов'язковий** | Issuer: точний URL провайдера авторизації, що видав токен. |
| `sub` | `string` | **Обов'язковий** | Subject: унікальний та стабільний ідентифікатор користувача (до 255 символів). |
| `aud` | `string` або `array` | **Обов'язковий** | Audience: ідентифікатор застосунку (`client_id`), для якого призначено токен. |
| `exp` | `integer (Unix time)` | **Обов'язковий** | Expiration: момент часу в секундах, після якого токен вважається простроченим. |
| `iat` | `integer (Unix time)` | **Обов'язковий** | Issued At: точний час генерації токена на сервері IdP. |
| `auth_time` | `integer (Unix time)` | Обов'язковий при `max_age` | Точний час проходження автентифікації користувачем. |
| `nonce` | `string` | Обов'язковий (якщо був у запиті) | Значення рядка захисту від повтору. Повинно збігатися зі значенням у сесії клієнта. |
| `acr` | `string` | Опціональний | Authentication Context Class Reference: рівень надійності входу (наприклад LoA або FIDO2). |
| `amr` | `array of string` | Опціональний | Authentication Methods References: список використаних методів (`pwd`, `otp`, `fido`, `sms`). |
| `azp` | `string` | Обов'язковий при кількох `aud` | Authorized Party: ідентифікатор клієнта, якому видано токен. |
| `at_hash` | `string` | Обов'язковий при видачі `access_token` | Base64URL від лівої половини SHA-256 хешу від `access_token` для контролю цілісності пари токенів. |
| `c_hash` | `string` | Обов'язковий при видачі `code` | Base64URL від лівої половини SHA-256 хешу від коду авторизації. |

#### Парні псевдонімні ідентифікатори (Pairwise Pseudonymous Identifiers)
Коли провайдер налаштований на роботу в режимі `subject_types_supported: ["pairwise"]`, значення твердження `sub` генерується унікальним для кожного окремого клієнта або групи сайтів одного власника (Sector Identifier). Це унеможливлює відстеження дій користувача та зіставлення його активності між різними сторонніми сервісами. Якщо група застосунків одного вендора має різні доменні імена зворотних адрес `redirect_uri`, клієнт публікує JSON-документ `sector_identifier_uri`, що містить масив дозволених зворотних адрес, завдяки чому провайдер видає їм єдиний стабільний `sub`.

### 6. Реєстр стандартних дозволів (Scopes) та пов'язаних тверджень

Специфікація OpenID Connect Core 1.0 (§5.4) стандартизує назви дозволів та групує відповідні атрибути профілю користувача.

| Scope | Пов'язані твердження (Claims) | Призначення та семантика |
| :--- | :--- | :--- |
| `openid` | `sub`, `iss`, `aud`, `exp`, `iat`, `nonce` | **Обов'язковий базовий дозвіл**. Вмикає поведінку OIDC та генерацію `id_token`. Без цього scope потік функціонує як звичайний OAuth 2.0. |
| `profile` | `name`, `family_name`, `given_name`, `middle_name`, `nickname`, `preferred_username`, `profile`, `picture`, `website`, `gender`, `birthdate`, `zoneinfo`, `locale`, `updated_at` | Надає доступ до публічних атрибутів профілю користувача: імені, прізвища, посилання на аватарку, статі, часового поясу та мовних налаштувань. |
| `email` | `email`, `email_verified` | Надає доступ до адреси електронної пошти користувача та булевого прапорця `email_verified`, який засвідчує, що адресу верифіковано провайдером. |
| `address` | `address` (вкладений JSON: `formatted`, `street_address`, `locality`, `region`, `postal_code`, `country`) | Надає доступ до фізичної поштової адреси користувача, структурованої за полями стандарту. |
| `phone` | `phone_number`, `phone_number_verified` | Надає доступ до номера телефону користувача у форматі E.164 (наприклад `+380501234567`) та прапорця його верифікації через SMS/дзвінок. |
| `offline_access` | (Не додає полів, керує видачею `refresh_token`) | Запитує надання довгоживучого токена оновлення (`refresh_token`) для забезпечення доступу до ресурсів, коли користувач не взаємодіє із застосунком у реальному часі. |

### 7. Специфікація ключів JWKS (JSON Web Key Set, RFC 7517)

Документ `jwks_uri` повертає список дійсних відкритих ключів провайдера для верифікації підписів:

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "k_2026_01",
      "n": "u1Wv...[Base64URL modulus]...",
      "e": "AQAB"
    },
    {
      "kty": "EC",
      "use": "sig",
      "alg": "ES256",
      "crv": "P-256",
      "kid": "k_2026_ec",
      "x": "f83OJ3D2xF1Bg8vub9tLe1gHMzV76e8Tus9uPHvRVEU",
      "y": "x_da696PxgCm9je6KEpuYURmHUamExmstIpU95UdfTU"
    }
  ]
}
```

#### Семантика полів об'єкта JWK
- `kty`: сімейство криптографічного алгоритму (`RSA` для ключів RSA, `EC` для еліптичних кривих, `OKP` для Edwards-кривих Ed25519).
- `use`: цільове призначення ключа. Значення `sig` вказує на перевірку підпису, а `enc` — на асиметричне розшифрування корисного навантаження JWE.
- `alg`: алгоритм цифрового підпису, для якого призначено ключ (наприклад `RS256`, `ES256`, `EdDSA`).
- `kid`: унікальний ідентифікатор ключа. За цим полем клієнт зіставляє відкритий ключ із параметром `kid` у заголовку JWT.
- `n`, `e`: двійкові параметри відкритого ключа RSA (модуль та публічна експонента), закодовані у формат Base64URL.
- `crv`, `x`, `y`: назва еліптичної кривої та координати відкритої точки на кривій для алгоритмів сімейства ECDSA.

### 8. Деталізовані авторизаційні запити (Rich Authorization Requests, RFC 9396)

Традиційний механізм дозволів `scope` оперує простими плоскими рядками, розділеними пробілами (наприклад, `read:orders write:transfers`). Він стає повністю безпорадним у сучасних фінансових API (Open Banking / FAPI) та корпоративних системах, де право на дію вимагає суворої параметризації: зазначення граничної суми транзакції, валюти, номера рахунку IBAN та часового інтервалу.

Специфікація RAR розв'язує цю проблему, вводячи параметр `authorization_details` — структурований масив JSON-об'єктів:

```json
[
  {
    "type": "payment_initiation",
    "instructedAmount": {
      "currency": "UAH",
      "amount": "15000.00"
    },
    "creditorAccount": {
      "schemeName": "UA_IBAN",
      "identification": "UA123456789012345678901234567"
    },
    "debtorAccount": {
      "schemeName": "UA_IBAN",
      "identification": "UA987654321098765432109876543"
    },
    "actions": [
      "initiate",
      "execute"
    ]
  }
]
```

#### Правила обробки RAR на сервері авторизації
1. **Відображення на екрані згоди**: сервер IdP десеріалізує об'єкт `authorization_details` і відображає користувачеві точні параметри платіжного доручення (суму, валюту та рахунок одержувача) перед тим, як користувач підтвердить дію за допомогою біометрії чи OTP.
2. **Вбудовування у токен доступу**: після підтвердження затверджена структура `authorization_details` або її криптографічний відбиток вбудовується безпосередньо у твердження `access_token`.
3. **Контроль на ресурсному сервері**: API ресурсів перевіряє, що вхідний платіж відповідає зафіксованій у токені сумі та цільовому рахунку. Будь-яка спроба перевищити затверджену суму відхиляється з кодом `403 Forbidden`.

### 9. Авторизація пристроїв з обмеженим введенням (Device Authorization Grant, RFC 8628)

Для розумних телевізорів (Smart TV), консолей, медіаприставок або інструментів командного рядка (CLI), де неможливо запустити повноцінний веб-браузер або вводити довгі паролі за допомогою пульта, застосовується протокол Device Grant.

#### Послідовність викликів та контракт
1. Пристрій виконує POST-запит на `device_authorization_endpoint`:
   ```http
   POST /device/code HTTP/1.1
   Host: idp.example.com
   Content-Type: application/x-www-form-urlencoded

   client_id=smart_tv_app&scope=openid%20profile
   ```
2. Сервер авторизації повертає два коди та інструкції для користувача:
   ```json
   {
     "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysN",
     "user_code": "WDJB-MJHT",
     "verification_uri": "https://idp.example.com/device",
     "verification_uri_complete": "https://idp.example.com/device?user_code=WDJB-MJHT",
     "expires_in": 900,
     "interval": 5
   }
   ```
3. Пристрій виводить на екран телевізора короткий код `WDJB-MJHT` та QR-код із посиланням `verification_uri_complete`.
4. Користувач відкриває посилання на своєму смартфоні або комп'ютері, входить у свій обліковий запис та підтверджує авторизацію пристрою.
5. Пристрій тим часом періодично (кожні `interval` секунд, наприклад кожні 5 секунд) опитує точку `/token`:
   ```http
   POST /token HTTP/1.1
   Host: idp.example.com
   Content-Type: application/x-www-form-urlencoded

   grant_type=urn:ietf:params:oauth:grant-type:device_code
   &device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysN
   &client_id=smart_tv_app
   ```
6. Поки користувач не завершив вхід на смартфоні, сервер повертає статус `400 Bad Request` із помилкою `{"error": "authorization_pending"}`. Якщо клієнт опитує сервер частіше встановленого інтервалу, сервер повертає `{"error": "slow_down"}`. Після успішного входу користувача черговий запит пристрою повертає повний набір токенів (`access_token`, `refresh_token`, `id_token`).

### 10. Кінцеві точки профілю користувача, інтроспекції, відкликання та виходу

#### 1. Кінцева точка UserInfo (`GET /userinfo`)
Захищений ендпоінт для отримання додаткових тверджень профілю користувача. Клієнт передає токен доступу в заголовку `Authorization: Bearer <access_token>`.

```http
GET /userinfo HTTP/1.1
Host: idp.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
```

Відповідь повертається у форматі JSON із кодом `200 OK`:
```json
{
  "sub": "usr_42",
  "name": "Олександр Коваленко",
  "email": "oleksandr@example.com",
  "email_verified": true,
  "picture": "https://idp.example.com/photos/usr_42.jpg"
}
```
Клієнт зобов'язаний звірити значення `sub` із відповіді `/userinfo` зі значенням `sub` із раніше валідованого `id_token`.

#### 2. Кінцева точка інтроспекції токенів (RFC 7662 `POST /introspect`)
Використовується серверами ресурсів (API) для перевірки валідності та прав непрозорих (opaque) токенів через прямий HTTPS-запит:

```http
POST /introspect HTTP/1.1
Host: idp.example.com
Authorization: Basic cmVzb3VyY2Vfc2VydmVyOmFwaV9zZWNyZXQ=
Content-Type: application/x-www-form-urlencoded

token=mF_9.B5f-4.1JqM&token_type_hint=access_token
```

Сервер авторизації повертає JSON-відповідь:
```json
{
  "active": true,
  "scope": "read:photos write:orders",
  "client_id": "web_app_prod_01",
  "sub": "usr_42",
  "exp": 1735732800,
  "iat": 1735729200,
  "iss": "https://idp.example.com",
  "token_type": "Bearer"
}
```
Якщо токен прострочений або відкликаний, сервер повертає `{"active": false}`.

#### 3. Кінцева точка відкликання токенів (RFC 7009 `POST /revoke`)
Дозволяє клієнту явно анулювати токен оновлення або токен доступу при виході користувача з системи:

```http
POST /revoke HTTP/1.1
Host: idp.example.com
Authorization: Basic d2ViX2FwcF9wcm9kXzAxOnNlY3JldF9rZXlfOTg3
Content-Type: application/x-www-form-urlencoded

token=r_9kLmNpQrStUvWxYz12345&token_type_hint=refresh_token
```

Сервер авторизації анулює зазначений токен і всі пов'язані з ним похідні токени доступу, повертаючи статус `200 OK`.

#### 4. Ініціалізація виходу користувача (RP-Initiated Logout 1.0)
Для синхронного завершення сесії на сервері IdP та перенаправлення користувача назад у застосунок клієнт формує запит на `end_session_endpoint`:

```http
GET /protocol/openid-connect/logout?id_token_hint=eyJhbGciOiJSUzI1NiIs...
  &post_logout_redirect_uri=https%3A%2F%2Fclient.example.com%2Flogged-out
  &state=logout_state_456 HTTP/1.1
Host: idp.example.com
```

Параметр `id_token_hint` дозволяє серверу IdP однозначно визначити, яку саме сесію користувача слід завершити, та перевірити, чи адреса `post_logout_redirect_uri` входить до списку дозволених для даного клієнта.

### 11. Динамічна реєстрація клієнтів (Dynamic Client Registration, RFC 7591)

У відкритих протокольних екосистемах (наприклад, у банківських стандартах Open Banking або федеративних мережах) клієнтські застосунки реєструються автоматично без ручного втручання адміністратора.

Клієнт надсилає POST-запит на кінцеву точку `registration_endpoint` із JSON-документом метаданих:

```json
{
  "client_name": "Мобільний банкінг",
  "redirect_uris": [
    "https://client.example.com/callback",
    "com.example.app:/oauth2redirect"
  ],
  "grant_types": [
    "authorization_code",
    "refresh_token"
  ],
  "response_types": [
    "code"
  ],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://client.example.com/.well-known/jwks.json"
}
```

Сервер авторизації реєструє застосунок і повертає статус `201 Created` із реєстраційним документом, що містить `client_id`, реєстраційні дати та `registration_access_token` для майбутнього оновлення чи видалення конфігурації за стандартом RFC 7592.

### 12. Реєстр протокольних помилок та правила діагностики

Протоколи стандартизують коди помилок для однозначної обробки збоїв у клієнтських системах.

| Код помилки | Точка виникнення | Причина та стратегія відновлення |
| :--- | :--- | :--- |
| `invalid_request` | `/authorize`, `/token`, `/introspect` | У запиті відсутній обов'язковий параметр, передано непідтримуваний тип контенту або дублюються поля. Клієнт повинен перевірити валідність формування HTTP-запиту. |
| `unauthorized_client` | `/authorize`, `/token` | Даному клієнту заборонено використовувати цей тип потоку (`grant_type`) або тип відповіді (`response_type`). Вимагає коригування прав у кабінеті IdP. |
| `access_denied` | `/authorize` | Користувач натиснув «Скасувати» на екрані надання прав або не пройшов правила умовного доступу IdP. Клієнт виводить повідомлення про відхилення входу. |
| `unsupported_response_type` | `/authorize` | Сервер не підтримує запитаний `response_type`. Слід змінити параметр на значення `code`. |
| `invalid_scope` | `/authorize`, `/token` | Запитаний дозвіл є невідомим або забороненим для цього клієнта. Слід узгодити список scopes із підтримуваними провайдером. |
| `server_error` | Усі кінцеві точки | Внутрішній критичний збій на стороні сервера авторизації. Клієнт повторює запит з експоненційним відкладенням (Exponential Backoff). |
| `temporarily_unavailable` | Усі кінцеві точки | Сервер авторизації тимчасово перевантажений або перебуває на обслуговуванні. Клієнт повинен повторити спробу пізніше. |
| `invalid_grant` | `/token` | Авторизаційний код або токен оновлення прострочений, спалений або виявлено розбіжність PKCE верифікатора. Клієнт зобов'язаний розпочати повний потік входу з нуля. |
| `invalid_client` | `/token`, `/revoke` | Помилка автентифікації клієнта (неправильний пароль `client_secret` чи невалідний цифровий підпис Client Assertion). |

Цей довідник охоплює всі обов'язкові протокольні точки взаємодії, типи параметрів, вимоги безпеки, механізми виходу, розширення RAR/PAR/Device Flow та структури даних, необхідні для реалізації повністю сумісних, надійних клієнтських систем та серверів ресурсів в екосистемах OAuth 2.0 та OpenID Connect.
