# Повноваження (capabilities) як модель доступу

<preknowlist>
- [Моделі авторизації](root:sf-security/authorization-models) — класифікація підходів до розмежування доступу: DAC, MAC, RBAC та списки контролю (ACL).
- [Найменші привілеї й deny-by-default](root:sf-security/least-privilege) — концепція звуження прав процесу до мінімально необхідного набору дій.
- [Межі довіри](root:sf-security/trust-boundaries) — виокремлення ізольованих компонентів із різними рівнями привілеїв.
</preknowlist>

Коли системний демон друку або компілятор, що виконується з привілеями суперкористувача (UID 0), отримує від непривілейованого клієнта (UID 1000) запит на збереження діагностичного звіту за шляхом `/etc/shadow`, класична операційна система на основі списків контролю доступу (ACL) дозволяє запис і безповоротно знищує хеші системних паролів. Ядро перевіряє права процесу, що ініціював системний виклик `open()`, фіксує ідентифікатор UID 0 і санкціонує операцію, оскільки не має жодного архітектурного механізму з'ясувати, чи діє демон за власним наміром, чи виконує чуже доручення. Ця проблема виникає не через випадкову помилку в коді демона, а внаслідок фундаментальної архітектурної вади класичних операційних систем: розриву між позначенням об'єкта (текстовим шляхом у глобальній файловій системі) та правом на доступ до нього (фоновими привілеями процесу).

Модель безпеки на основі **повноважень** (англ. *capability-based security*, від латинського *capabilis* — здатний вмістити, сприйнятливий) усуває цю проблему, повністю скасовуючи саме поняття неявних фонових привілеїв. Замість перевірки «хто виконує дію», система вимагає пред'явлення неподільного цифрового токена, який одночасно вказує на конкретний об'єкт і визначає точний перелік дозволених над ним операцій. Якщо суб'єкт не володіє повноваженням, він позбавлений не лише права доступу, а й самої змоги адресувати цей ресурс у пам'яті чи системних викликах.

## 1. Проблема Confused Deputy та неявні привілеї (Ambient Authority)

Класичні операційні системи (зокрема родини Unix та Windows NT) організовані довкола матриці контролю доступу. Рядками цієї матриці є активні суб'єкти (користувачі, системні облікові записи або призначені їм ролі), а стовпчиками — пасивні об'єкти (файли, каталоги, сокети, пристрої). 

Коли процес викликає системну функцію `open("/var/log/system.log", O_WRONLY)`, ядро виконує три послідовні кроки:
1. Зчитує з контексту поточного процесу його ідентифікатори безпеки (наприклад, `current_euid()` у Linux або Security Token у Windows).
2. Виконує резолюцію текстового імені шляху в глобальному просторі імен файлової системи (VFS).
3. Зіставляє ідентифікатор суб'єкта зі списком контролю доступу (ACL) цільового інода або дескриптора безпеки.

Цей механізм базується на концепції **неявних фонових привілеїв** (англ. *ambient authority*): права процесу не прив'язані до конкретної переданої адреси чи дії — вони за замовчуванням «розлиті в повітрі» довкола процесу і автоматично застосовуються ядром до кожного його системного виклику.

### Механіка атаки «Збентежений заступник» (Confused Deputy)

Феномен «збентеженого заступника» виникає, коли привілейована програма (демон, мережевий шлюз, компілятор чи утиліта з бітом `setuid`) обслуговує запити від менш привілейованих клієнтів. Програма-заступник (*deputy*) законно володіє правами для виконання власних службових завдань (наприклад, оновлення системного білінгу або запису в захищений журнал), але водночас виконує дії на замовлення клієнта.

Розглянемо архітектуру привілейованого сервісу в класичній моделі:

:::tabs
```c
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

/* Код привілейованого заступника (виконується з UID 0) */
void handle_client_request(const char *user_chosen_path, const char *data) {
    /* 1. Запис результатів клієнта */
    int fd_out = open(user_chosen_path, O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd_out >= 0) {
        write(fd_out, data, strlen(data));
        close(fd_out);
    }

    /* 2. Запис внутрішнього системного білінгу від власного імені */
    int fd_bill = open("/var/log/service.bill", O_WRONLY | O_APPEND);
    if (fd_bill >= 0) {
        write(fd_bill, "BILLING_RECORD: +1 operation\n", 29);
        close(fd_bill);
    }
}
```
```cpp
#include <fcntl.h>
#include <unistd.h>
#include <string_view>
#include <system_error>

namespace legacy_service {

/* Код привілейованого заступника (виконується з UID 0) */
void handle_client_request(std::string_view user_chosen_path, std::string_view data) {
    /* 1. Запис результатів клієнта */
    int fd_out = ::open(user_chosen_path.data(), O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd_out >= 0) {
        ::write(fd_out, data.data(), data.size());
        ::close(fd_out);
    }

    /* 2. Запис внутрішнього системного білінгу від власного імені */
    int fd_bill = ::open("/var/log/service.bill", O_WRONLY | O_APPEND);
    if (fd_bill >= 0) {
        constexpr std::string_view record = "BILLING_RECORD: +1 operation\n";
        ::write(fd_bill, record.data(), record.size());
        ::close(fd_bill);
    }
}

} // namespace legacy_service
```
:::

Якщо непривілейований користувач передасть у параметрі `user_chosen_path` шлях до системного файлу `"/var/log/service.bill"`, сервіс відкриє цей файл для запису даних клієнта. Оскільки процес працює з привілеями `root`, виклик `open()` завершиться успішно, і внутрішній журнал буде знищений.

Сервіс потрапляє в стан замішання через те, що ядро об'єднує два принципово різні авторитети в одну нерозрізнену масу:
- Право сервісу писати у власний журнал обліку.
- Намір клієнта зберегти свої дані у власному каталозі.

У системних викликах на основі ACL не існує способу вказати: *«Відкрий цей шлях, але перевір лише повноваження, надані моїм клієнтом, а не мої власні»*. Тимчасове перемикання ідентифікаторів (`seteuid()`) не вирішує проблему в повному обсязі, оскільки є повільним, призводить до стану гонитви (race condition) у багатопотокових процесах і вимагає постійного ручного відстеження прав ([детальний історичний розбір інциденту](root:sf-security/capability-based-security/hist-confused-deputy-and-capabilities.md)).

Сучасним проявом цієї ж проблеми на рівні веб-сервісів є атака **SSRF** (*Server-Side Request Forgery*): коли бекенд-сервіс за запитом користувача робить HTTP-запит до внутрішнього хмарного API метаданих (`http://169.254.169.254/`), використовуючи свої неявні мережеві привілеї замість прав клієнта.

### Проблема утримання даних (The Confinement Problem)

У 1973 році Батлер Лемпсон (*Butler Lampson*) сформулював проблему утримання (*Confinement Problem*): як виконати ненадійну програму (наприклад, сторонній алгоритм оптимізації податків) над конфіденційними даними клієнта так, щоб гарантувати, що ця програма не зможе передати копію даних своєму автору або зберегти їх у прихованому місці.

У системі на основі ACL розв'язати проблему утримання неможливо: оскільки процес запускається від імені користувача, він успадковує всі його неявні права — створення тимчасових файлів у `/tmp`, відкриття вихідних сокетів, запис у спільну пам'ять IPC.

У моделі повноважень утримання досягається автоматично: ізольованому процесу взагалі не передають повноважень на мережеві сокети або файли журналів. Процес отримує рівно два повноваження: читання вхідного буфера та запис вихідного результату. Не маючи інших повноважень, процес фізично не здатний створити прихований канал передачі даних у файлову систему чи мережу.

## 2. Концепція Capability: сутність, невдаваність і відсутність глобальних імен

**Повноваження** (англ. *capability*) — це неподільний маркер (токен), що поєднує в єдиній структурі:
1. **Посилання на об'єкт (Object Pointer / Identifier):** адресу в пам'яті, дескриптор об'єкта ядра чи глобальний ідентифікатор вузла.
2. **Маску прав (Rights Mask):** чітко визначений набір дозволених операцій над цим об'єктом (читання, запис, виконання, передача іншим).

```
+─────────────────────────────────────────────────────────────+
|                     Повноваження (Capability)                |
|  +─────────────────────────────────+─────────────────────+  |
|  |  Посилання на ресурс (Pointer)  |  Маска прав (Perms)  |  |
|  |  • Фізична / віртуальна адреса  |  • Read              |  |
|  |  • Вказівник на об'єкт ядра     |  • Write             |  |
|  |  • Ідентифікатор вузла          |  • Grant / Transfer  |  |
|  +─────────────────────────────────+─────────────────────+  |
+─────────────────────────────────────────────────────────────+
```

У системі, заснованій на повноваженнях, діє базовий інваріант: **«Володіння повноваженням є єдиною і достатньою умовою доступу до ресурсу»**. Якщо суб'єкт має повноваження — ядро виконує операцію; якщо не має — суб'єкт не може навіть сформувати запит до цього ресурсу, оскільки не має чим його адресувати.

### Об'єктно-орієнтовані повноваження (OCap) та їхні фундаментальні правила

Об'єктно-орієнтована модель повноважень (*Object-Capability Model / OCap*) формалізує правила взаємодії суб'єктів через чотири закони передачі зв'язків:
1. **Початкове створення (Creation):** Коли процес створює новий об'єкт, він автоматично стає єдиним володарем первинного повноваження з повними правами на цей об'єкт.
2. **Передача через повідомлення (Introduction):** Процес А може передати повноваження на об'єкт Х процесу Б лише за умови, що процес А вже володіє каналом зв'язку з процесом Б і повноваженням на об'єкт Х.
3. **Тільки зв'язок породжує зв'язок (Only connectivity begets connectivity):** Неможливо отримати доступ до ресурсу через вгадування адрес, перебір ідентифікаторів чи сканування пам'яті.
4. **Монотонне звуження (Attenuation):** Будь-який суб'єкт під час передачі повноваження може накласти додаткові обмеження, створивши токен із меншим набором прав.

### Механізми забезпечення невдаваності (Unforgeability)

Абсолютним критерієм надійності capability-системи є її **невдаваність**: користувацький процес не повинен мати змоги підробити біти повноваження, розширити маску прав чи створити токен на неіснуючий або чужий ресурс.

Існують три основні архітектурні підходи до забезпечення невдаваності:

1. **Таблиці простору ядра (C-lists / C-nodes):**
   Усі повноваження зберігаються в захищеній пам'яті ядра. Процес у просторі користувача бачить лише числовий індекс у своїй локальній таблиці (дескриптор, handle, CPtr). Коли процес передає цей індекс у системному виклику, ядро саме знаходить відповідний запис у таблиці та перевіряє біти операцій.
2. **Криптографічні мандати (Cryptographic Capabilities):**
   Використовуються у відкритих мережевих середовищах, розподілених файлових сховищах (Tahoe-LAFS) та токенах авторизації (Macaroons). Повноваження зберігається в пам'яті клієнта, але захищене криптографічним кодом автентифікації повідомлень (HMAC) або цифровим підписом:
   ```
   Token = { Object_ID, Rights, Nonce, Expiration } || HMAC_K(Object_ID || Rights || Nonce || Expiration)
   ```
   Будь-яка зміна маски прав без знання секретного ключа `K` робить підпис недійсним і призводить до відхилення токена сервером.
3. **Апаратна тегова пам'ять (Hardware Memory Tagging):**
   Реалізується в процесорній архітектурі CHERI. Кожен регістр та блок оперативної пам'яті супроводжуються додатковим апаратним бітом тегу. Цей біт недоступний для прямого запису через команди арифметики. Будь-яка спроба модифікувати байти вказівника скидає тег у нуль, позбавляючи його статусу дійсного повноваження.

### Відсутність глобального простору імен (No Global Namespace)

У класичній системі файлові шляхи формують глобальний граф із коренем `/`. Будь-який процес може сконструювати рядок на кшталт `"/etc/shadow"` або `"C:\Windows\System32\config\SAM"` і передати його ядру.

У чистій моделі повноважень **глобальних просторів імен не існує**. Кожен процес володіє власним локальним простором повноважень (*Capability Space, CSpace*). Доступ до вкладеного ресурсу можливий лише шляхом ієрархічної навігації: володіючи повноваженням на каталог `dir_cap`, процес викликає операцію переходу, отримуючи нове повноваження на файл `file_cap`:

```
[ CSpace процесу ] ──► [ Повноваження на каталог /var/log ]
                                │
                         (lookup "app.log")
                                ▼
                       [ Повноваження на файл app.log ]
```

Якщо процесу не надали повноваження на кореневий або батьківський каталог, він не може звернутися до файлів за його межами за жодних умов.

## 3. Практичні втілення в ядрах операційних систем

### 3.1. Capsicum (FreeBSD)

Capsicum — це розширення ядра FreeBSD, розроблене Кембриджським університетом, яке інтегрує модель повноважень у середовище POSIX без зламу сумісності з наявним програмним забезпеченням.

Capsicum спирається на дві концепції:
1. **Режим повноважень (`cap_enter`):** Процес добровільно перемикає себе в capability mode. Після цього ядро блокує будь-які виклики, що приймають глобальні шляхи файлової системи (`open()`, `mkdir()`, `unlink()`, `link()`, `bind()`). Спроба виконати такий виклик повертає код помилки `ECAPMODE`.
2. **Звуження прав дескрипторів (`cap_rights_limit`):** Кожен класичний файловий дескриптор Unix розширюється структурою `cap_rights_t`, що містить бітові прапорці дозволених дій (`CAP_READ`, `CAP_WRITE`, `CAP_SEEK`, `CAP_FSTAT`, `CAP_MMAP`).

:::tabs
```c
#include <sys/capsicum.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

void run_sandboxed(void) {
    /* 1. Відкриваємо файл у звичайному режимі */
    int fd = open("/tmp/output.dat", O_RDWR | O_CREAT, 0600);

    /* 2. Обмежуємо дескриптор лише правом читання та fstat */
    cap_rights_t rights;
    cap_rights_init(&rights, CAP_READ, CAP_FSTAT);
    cap_rights_limit(fd, &rights);

    /* 3. Входимо в режим повної ізоляції */
    cap_enter();

    /* Прямий open тепер неможливий: */
    int bad = open("/etc/passwd", O_RDONLY); /* Повертає -1, errno = ECAPMODE */

    /* Запис у fd заборонено на рівні дескриптора: */
    write(fd, "test", 4); /* Повертає -1, errno = ENOTCAPABLE */
}
```
```cpp
#include <sys/capsicum.h>
#include <fcntl.h>
#include <unistd.h>
#include <system_error>
#include <cerrno>

namespace capsicum_demo {

void run_sandboxed() {
    /* 1. Відкриваємо файл у звичайному режимі */
    int fd = ::open("/tmp/output.dat", O_RDWR | O_CREAT, 0600);
    if (fd < 0) {
        throw std::system_error(errno, std::generic_category(), "open failed");
    }

    /* 2. Обмежуємо дескриптор лише правом читання та fstat */
    cap_rights_t rights;
    ::cap_rights_init(&rights, CAP_READ, CAP_FSTAT);
    if (::cap_rights_limit(fd, &rights) < 0) {
        ::close(fd);
        throw std::system_error(errno, std::generic_category(), "cap_rights_limit failed");
    }

    /* 3. Входимо в режим повної ізоляції */
    if (::cap_enter() < 0) {
        ::close(fd);
        throw std::system_error(errno, std::generic_category(), "cap_enter failed");
    }

    /* Прямий open тепер неможливий: повертає -1, errno = ECAPMODE */
    int bad = ::open("/etc/passwd", O_RDONLY);
    (void)bad;

    /* Запис у fd заборонено: повертає -1, errno = ENOTCAPABLE */
    ssize_t w = ::write(fd, "test", 4);
    (void)w;

    ::close(fd);
}

} // namespace capsicum_demo
```
:::

Для навігації структурою каталогів усередині пісочниці Capsicum застосовує виклики `openat(dirfd, "sub/path", ...)`: дескриптор каталогу `dirfd` слугує коренем ізольованого піддерева ([детальніше у практичній реалізації пісочниці на Capsicum](root:sf-security/capability-based-security/proj-capsicum-sandbox.md)).

### 3.2. seL4: CSpace, CNode та дерево об'єктів ядра

У математично верифікованому мікроядрі **seL4** модель повноважень є абсолютною: ядро не надає жодного системного виклику, який би не адресувався через повноваження.

![Організація CSpace та дерева похідних CDT у мікроядрі seL4](/root/eng/sf-security/capability-based-security/img/sel4-cspace-cnode-tree.svg)
*Ієрархія CNode, індексація через CPtr та зв'язок дерева похідних прав CDT для каскадного відкликання.*

Основні елементи простору повноважень seL4:
- **CNode (Capability Node):** Таблиця в пам'яті ядра, що складається зі слотів розміром 32 байти (на 64-бітних процесорах). Кожен слот містить покажчик на об'єкт ядра (TCB, Endpoint, Untyped, VSpace) та маску прав.
- **CPtr (Capability Pointer):** Числовий індекс, який потік передає ядру. Ядро використовує біти CPtr як координати для обходу дерева CNode. Адресація виконується за алгоритмом префіксного дерева (Radix Tree): CPtr розбивається на сегменти бітів відповідно до глибини (`depth`) кожного проміжного CNode.
- **Нетипізована пам'ять (Untyped Memory):** У seL4 ядро не містить власного розподільника пам'яті `kmalloc`. Вся вільна RAM передається користувацькому простору як повноваження `seL4_Untyped`. Процес перетворює цю пам'ять на нові CNode, потоки чи таблиці сторінок через операцію `seL4_Untyped_Retype()`. Це гарантує математично доведений захист від атак вичерпання пам'яті ядра (Kernel Memory Exhaustion DoS).

### 3.3. Fuchsia Zircon: Handles та канали

В операційній системі Fuchsia ядро Zircon реалізує об'єктний контроль доступу через цілочисельні **дескриптори** (*Handles*).

- Кожен процес має власну ізольовану таблицю дескрипторів.
- Дескриптор нерозривно пов'язаний із 32-бітною маскою прав (`ZX_RIGHT_READ`, `ZX_RIGHT_WRITE`, `ZX_RIGHT_DUPLICATE`, `ZX_RIGHT_TRANSFER`, `ZX_RIGHT_MAP`, `ZX_RIGHT_EXECUTE`).
- Обмін даними між процесами здійснюється через канали зв'язку (*Zircon Channels*). Канал підтримує операцію атомарного перенесення дескрипторів (*Handle Transfer*): разом із повідомленням процес може надіслати дескриптор пам'яті VMO або іншого каналу.
- Якщо в дескриптора скинуто біт `ZX_RIGHT_DUPLICATE`, отримувач повідомлення не може розмножити це повноваження і передати його іншим компонентам ([системний довідник функцій та кодів помилок](root:sf-security/capability-based-security/api-capsicum-rights.md)).

## 4. Апаратна підтримка: архітектура CHERI

Програмні моделі повноважень ізолюють окремі процеси або компоненти операційної системи, проте вони не здатні захистити структури даних усередині адресного простору самої програми (наприклад, запобігти переповненню буфера на стеку чи купі в мовах C/C++).

Архітектура **CHERI** (*Capability Hardware Enhanced RISC Instructions*), розроблена в Кембриджському університеті та SRI International (втілена в чіпах Arm Morello та CHERI-RISC-V), переносить модель повноважень безпосередньо в кремній центрального процесора.

![Апаратна структура повноваження CHERI](/root/eng/sf-security/capability-based-security/img/capability-anatomy-cheri.svg)
*Анатомія 128-бітного повноваження CHERI з позасмуговим теговим бітом та апаратними межами адресації.*

### Анатомія апаратного повноваження CHERI

У класичній 64-бітній архітектурі вказівник — це звичайне ціле число. CHERI замінює вказівники на 128-бітні апаратні повноваження (*Fat Pointers*), що містять:

1. **Віртуальну адресу / Курсор (64 біти):** Поточне значення адреси в пам'яті.
2. **Просторові межі (Base та Top):** Нижня та верхня межі пам'яті, доступ до якої дозволено через цей вказівник. Завдяки алгоритму стиснення *CHERI Concentrate* межі кодуються разом із метаданими у 64 бітах із використанням плаваючої шкали експонент (аналогічно до стандарту IEEE 754).
3. **Маску апаратних дозволів (Permissions):** Біти прав на читання даних (`Load`), запис (`Store`), виконання коду (`Execute`), читання інших повноважень (`Load Cap`) та запис повноважень (`Store Cap`).
4. **Тип об'єкта (Object Type / Sealing):** Поле для реалізації запечатаних маркерів, що блокують прямий доступ до внутрішнього стану об'єкта без ключа розпечатування.

### Апаратний теговий біт (Out-of-band Tag Bit)

Ключовим захисним елементом CHERI є **1-бітний тег**, що асоціюється з кожним 128-бітним блоком пам'яті:
- Тег зберігається на спеціальних виділених лініях кеш-пам'яті L1/L2/L3 та в додаткових службових бітах контролера DRAM.
- Тег фізично недоступний для запису через звичайні інструкції збереження байтів (`store byte`).
- Якщо `Tag == 1`, процесор сприймає значення регістру як валідне повноваження.
- Якщо програма спробує модифікувати байти повноваження неспеціалізованою командою (наприклад, побайтовим записом через `memcpy` або зміною бітів через побітове «АБО»), контролер пам'яті **апаратно скидає тег у 0**.
- Спроба розіменувати вказівник із `Tag == 0` або вийти за межі `[Base, Top)` миттєво генерує апаратне переривання (*Hardware Capability Exception / Trap*).

### Просторова й часова безпека пам'яті (Spatial and Temporal Safety)

1. **Просторова безпека (Spatial Memory Safety):**
   При виклику `malloc(64)` стандартна бібліотека повертає повноваження, де `Base = ptr`, а `Top = ptr + 64`. Спроба виконати читання або запис за межами 64 байтів зупиняється апаратно за 0 тактів додаткових накладних витрат.
2. **Часова безпека (Temporal Memory Safety):**
   Для запобігання атакам класу Use-After-Free архітектура застосовує підсистему **CHERI Cornucopia**: під час звільнення блоку пам'яті через `free()` апаратний фоновий сканер пам'яті (*Revoker*) знаходить усі старі повноваження в пам'яті процесу і скидає їхні тегові біти в нуль.

## 5. Делегування, звуження прав та проблема відкликання (Revocation)

### Монотонне звуження прав (Attenuation)

У системах на основі повноважень діє інваріант монотонності: **«Суб'єкт може передати іншому лише підмножину власних прав»**.

```
Батьківське повноваження: [ Об'єкт X | Read, Write, Execute, Grant ]
                                      │
                               (Звуження прав / Attenuation)
                                      ▼
Дочірнє повноваження:     [ Об'єкт X | Read-Only ]
```

Процес, що володіє повноваженням з правами `Read + Write`, може створити дочірню копію з правом `Read-Only` і передати її сторонній бібліотеці. Навіть якщо ця бібліотека буде повністю скомпрометована, атакуючий не зможе відновити право `Write`, оскільки для цього немає математичної чи системної змоги.

### Проблема відкликання прав (The Revocation Problem)

У моделі ACL відкликання реалізується тривіально: адміністратор видаляє запис користувача зі списку файлу, і наступний системний виклик блокується.

У capability-моделі токени вільно циркулюють між процесами: процес А передав копію процесу Б, а процес Б — процесу В. Якщо власник вирішує позбавити процес В доступу, простого видалення токена в процесу А недостатньо.

Для вирішення проблеми відкликання застосовують чотири фундаментальні інженерні підходи:

```
Підходи до відкликання повноважень:
┌─────────────────────────────────────────────────────────────┐
│ 1. Рівень посередника (Indirection / Caretaker / Membrane)  │
│    Власник розриває зв'язок у посереднику; копії нікчемні   │
├─────────────────────────────────────────────────────────────┤
│ 2. Дерево похідних прав ядра (Kernel Derivation Tree - CDT) │
│    Ядро знає всі нащадки і каскадно видаляє їх (seL4)       │
├─────────────────────────────────────────────────────────────┤
│ 3. Лічильники поколінь та епох (Generation / Epoch Counting)│
│    Інкремент покоління об'єкта інвалідує старі токени       │
├─────────────────────────────────────────────────────────────┤
│ 4. Апаратне сканування тегів (Hardware Tag Invalidation)    │
│    Обнулення тегів у фізичній пам'яті через Revoker (CHERI) │
└─────────────────────────────────────────────────────────────┘
```

1. **Рівень непрямої адресації (Indirection / Caretaker / Membrane):**
   Клієнту видається повноваження не на сам ресурс, а на проміжний об'єкт-шлюз (*Caretaker*). Шлюз перенаправляє операції до ресурсу. При відкликанні власник ресурсу надсилає команду шлюзу розірвати зв'язок (`target = NULL`). Усі копії токенів у системі залишаються в клієнтів, але будь-яка операція через них повертає помилку розірваного з'єднання.
2. **Дерево похідних прав ядра (Capability Derivation Tree, CDT):**
   Реалізовано в мікроядрі seL4. Кожен слот CNode містить вказівники на батьківські та дочірні слоти. Виклик `seL4_CNode_Revoke(cnode, slot)` рекурсивно обходить дерево нащадків у ядрі та видаляє всі повноваження, виведені з цього вузла.
3. **Епохи та номери поколінь (Generation Counting):**
   Об'єкт зберігає 64-бітний лічильник `generation`, а повноваження — копію цього значення. При відкликанні лічильник об'єкта збільшується на 1. Під час системного виклику ядро зіставляє числа: при незбігу доступ відхиляється.
4. **Апаратне сканування тегів:**
   У CHERI модуль Revoker сканує сторінки пам'яті процесу та скидає теги старих повноважень, фізично позбавляючи процес можливості виконати розіменування.

## 6. Порівняльна матриця: ACL, POSIX Capabilities та справжні повноваження (OCap)

В інженерній практиці термін *capabilities* інколи вживають у двох різних значеннях:
1. **POSIX Capabilities (Linux `cap_set_proc`, `CAP_NET_RAW`, `CAP_SYS_ADMIN`):** це поділ привілеїв суперкористувача `root` на окремі біти привілеїв процесу. Проте це все ще **неявні фонові привілеї (ambient authority)**: процес із прапорцем `CAP_NET_RAW` може відкрити будь-який сирий сокет у системі за глобальним викликом.
2. **Об'єктні повноваження (Object Capabilities — Capsicum, seL4, CHERI):** неподільне поєднання конкретного ресурсу та прав над ним без будь-яких неявних фонових дозволів.

| Критерій порівняння | Списки контролю доступу (ACL / DAC) | POSIX Capabilities (Linux) | Справжні повноваження (OCap / Capsicum / seL4) |
|---|---|---|---|
| **Основа авторизації** | Ідентичність (UID/GID). | Біти привілеїв процесу. | **Володіння неподільним токеном** (CPtr/Handle). |
| **Фонові привілеї (Ambient Authority)** | **Присутні повністю**. | **Присутні повністю**. | **Повністю відсутні** (доступ лише за токеном). |
| **Захист від Confused Deputy** | Вразливі за замовчуванням. | Вразливі за замовчуванням. | **Захищені за побудовою**. |
| **Делегування прав** | Статичне (через групи/root). | Спадкування прапорців. | **Динамічне, гранулярне, монотонно звужуване**. |
| **Локальність перевірки** | Глобальна (пошук у VFS). | Глобальна (перевірка в ядрі).| **Локальна** (перевірка маски дескриптора/регістру). |
| **Складність відкликання прав** | Тривіальна (зміна ACL). | Тривіальна (скид біта). | Вимагає структур (CDT, Caretaker, Revoker). |
| **Гранулярність контролю** | Рівень файлів/служб. | Рівень системних класів дій. | **Рівень окремих буферів, дескрипторів і байтів**. |
| **Продуктивність перевірки** | Повільна (парсинг шляхів VFS).| Середня (перевірка прапорців).| **Максимальна** (бітова маска в пам'яті / такт АЛП). |

## Підсумковий синтез

Модель безпеки на основі повноважень змінює парадигму розмежування доступу: замість запитання *«Хто звертається до ресурсу?»* система ставить запитання *«Яким саме повноваженням санкціонована ця дія?»*.

Ліквідуючи неявні фонові привілеї та поєднуючи адресацію ресурсу з правами на його використання, capability-архітектури фундаментально усувають вразливість Confused Deputy, забезпечують дотримання принципу найменших привілеїв (PoLP) на рівні окремих системних викликів і дозволяють будувати мікроядерні операційні системи (seL4, Fuchsia) та процесори майбутнього (CHERI) з доведеною надійністю просторової та часової ізоляції.
