# Похідні ключі: KDF і HKDF

<preknowlist>
- [Криптографічні хеш-функції](root:sf-security/cryptographic-hash-functions) — властивості односторонності, стійкість до колізій та лавинний ефект.
- [HMAC](root:sf-security/hmac) — механізм автентифікації повідомлень на основі симетричного ключа й геш-функції.
- [Обмін ключами Діффі — Геллмана](root:sf-security/diffie-hellman) — узгодження спільного таємного числа через незахищений канал.
- [Автентифіковане шифрування (AEAD)](root:sf-security/authenticated-encryption) — захист конфіденційності й цілісності повідомлення з роздільними ключами.
</preknowlist>

Коли двоє вузлів завершують протокол Діффі — Геллмана над еліптичною кривою Curve25519, вони отримують 32-байтну координату спільної точки. Якщо цей масив байтів передати безпосередньо в симетричний шифр AES-256-GCM як ключ шифрування, безпека сесії зазнає удару. Спільна точка на кривій має високу непередбачуваність (min-entropy), проте її біти не розподілені рівномірно: значення завжди лежить у межах визначеного алгебраїчного порядку підгрупи, а певні бітові патерни мають вищу ймовірність появи, ніж інші. Якщо ж ті самі сирі байти використати паралельно для автентифікації повідомлень, виникає небезпека перехресної взаємодії протоколів: бітовий зсув або маніпуляція відкритим текстом у шифрі може скомпрометувати геш-тег автентифікації.

Для подолання цієї прірви між сирим криптографічним матеріалом і вимогами симетричних шифрів слугують функції виведення ключів — KDF (англ. *Key Derivation Function*, від лат. *derivatio* — відведення, утворення похідного). KDF перетворює вхідний секрет довільної якості чи ентропії (англ. *entropy*, від грец. *ἐν* — в і *троπή* — зворот, перетворення) на один або декілька криптографічно незалежних ключів фіксованої довжини, біти яких статистично не відрізняються від справжнього випадкового шуму.

## Чому не можна шифрувати майстер-секретом напряму

Симетричні блокові шифри (AES, Camellia) та потокові шифри (ChaCha20) розробляються з фундаментальним математичним припущенням: ключ шифрування є послідовністю рівномірно розподілених випадкових бітів. Кожен можливий ключ довжиною 256 бітів мусить мати абсолютно однакову ймовірність генерації, рівну `2⁻²⁵⁶`.

```
Рівномірний ключ:  P(K = k) = 1 / 2²⁵⁶  для кожного k ∈ {0, 1}²⁵⁶
```

Сирі спільні секрети (англ. *shared secrets*), отримані в результаті асиметричних протоколів або операцій відкритого ключа, цьому критерію не відповідають.

### 1. Алгебраїчна нерівномірність та мін-ентропія

Спільний секрет класичного протоколу Діффі — Геллмана у скінченному полі `Z_p^*` є цілим числом `g^(ab) mod p`, яке строго менше за простий модуль `p`. Усі значення між `p` та `2ⁿ - 1` мають нульову ймовірність генерації. У випадку еліптичних кривих спільний секрет є координатою `x` точки `P = (x, y) = d_A · Q_B`, яка обов'язково задовольняє алгебраїчне рівняння кривої (наприклад, форму Монтгомері `B·y² = x³ + A·x² + x`). Це створює жорсткі математичні інваріанти та взаємозв'язки між окремими бітами координати.

У теоретичній інформатиці мірою непередбачуваності джерела є **мінімальна ентропія** (англ. *min-entropy*) за Шенноном та Реньї:

```
H_∞(X) = -log₂(max_x P(X = x))
```

Для 256-бітної точки кривої Curve25519 мінімальна ентропія є високою (близько 252 бітів), тобто вгадати точку перебором неможливо. Однак **статистична відстань** між розподілом координат точки та істинно рівномірним розподілом бітових рядків `{0, 1}²⁵⁶` є суттєвою. Якщо подати такий нерівномірний ключ безпосередньо в лінійні або нелінійні перетворення шифру, зловмисник отримує перевагу в диференційному або лінійному криптоаналізі.

### 2. Небезпека довжинної невідповідності

Симетричному шифру потрібен 256-бітний ключ, а результат операції над кривою NIST P-384 дає 384 біти, або навпаки — обчислення RSA чи модуль Diffie-Hellman дає 2048 чи 4096 бітів, з яких шифру потрібно взяти лише 32 байти.

Просте відсікання зайвих байтів (наприклад, взяття молодших 256 бітів) є небезпечною практикою: воно безповоротно відкидає наявну ентропію старших розрядів і зберігає локальні кореляції бітів. Навпаки, якщо потрібно отримати кілька ключів, жодне тривіальне дублювання чи розбиття блоків не здатне забезпечити їхню криптографічну взаємну незалежність.

### 3. Повторне використання ключа та перехресні атаки протоколів

Якщо один спільний секрет одночасно застосовується для шифрування трафіку «клієнт → сервер» і «сервер → клієнт», або для паралельного шифрування й автентифікації повідомлень, виникають класичні вразливості:

- **Атаки відбиття (Reflection attacks):** Зловмисник перехоплює зашифрований пакет від клієнта і надсилає його назад клієнту під виглядом відповіді сервера. Якщо обидві сторони використовують однаковий ключ шифрування та схему послідовних номерів (nonce), клієнт успішно розшифрує власне ж повідомлення.
- **Колізії потоків гами:** У потокових шифрах (ChaCha20, AES-CTR) шифрування двох різних повідомлень на одному ключі з однаковим вектором ініціалізації (IV) призводить до повного розкриття відкритого тексту через операцію XOR:
  ```
  C₁ ⊕ C₂ = (P₁ ⊕ KeyStream) ⊕ (P₂ ⊕ KeyStream) = P₁ ⊕ P₂
  ```
- **Перехресна взаємодія алгоритмів:** Спільне використання одного бітового рядка як ключа блокового шифру та ключа хеш-автентифікації (MAC) порушує базові докази безпеки композиції Authenticate-then-Encrypt або Encrypt-then-MAC.

### 4. Розділення доменів безпеки (Domain Separation)

Функція KDF розв'язує цю проблему через механізм **розділення доменів**. З єдиного кореневого майстер-секрету KDF математично коректно виводить строго ізольований набір спеціалізованих робочих підключів:

- Ключ шифрування прямого напрямку (`client_write_key`);
- Ключ шифрування зворотного напрямку (`server_write_key`);
- Вектори ініціалізації або базові маски одноразових чисел (`client_write_iv`, `server_write_iv`);
- Ключі автентифікації заголовків пакета або сесійних квитків (`resumption_key`);
- Ключі експортерів для сторонніх протоколів прикладного рівня (`exporter_master_secret`).

Криптографічна односторонність (англ. *one-wayness*) KDF гарантує: компрометація одного з підключів (наприклад, через витік сесійного IV або атаку на один окремий пакет) не розкриває ані початкового майстер-секрету, ані решти робочих ключів.

## Парадигма Extract-then-Expand

Історично ранні стандарти намагалися генерувати ключі примітивним гешуванням. Наприклад, схема ANSI X9.63 (KDF1/KDF2) та ISO/IEC 18033-2 обчислювали ключі простим ланцюжком:

```
K = Hash(Z || 0x00000001) || Hash(Z || 0x00000002) || ...
```

Такий підхід мав суттєві теоретичні та практичні вади:
- Звичайні криптографічні геш-функції (наприклад, сімейство SHA-2 на базі конструкції Меркла — Дамґорда) проєктувалися для захисту від колізій та пошуку прообразу, а не як ідеальні екстрактори ентропії;
- Конструкція залишалася вразливою до атак подовження повідомлення (length extension attack);
- Була відсутня математично доведена процедура рандомізації вилучення ентропії за допомогою солі;
- Контекст застосунку не мав стандартизованого криптографічного зв'язування.

У 2010 році криптограф Гуго Кравчик (Hugo Krawczyk) запропонував і формально довів архітектурну парадигму **Extract-then-Expand** (вилучення, потім розгортання), яка згодом була стандартизована Інженерною радою інтернету IETF як RFC 5869 (HKDF).

![Парадигма Extract-then-Expand у HKDF](/root/eng/sf-security/key-derivation-function/img/hkdf-extract-expand.svg)
*Парадигма Extract-then-Expand (RFC 5869): вилучення рівномірної ентропії за допомогою солі та розгортання в незалежні підключі з контекстним зв'язуванням info.*

Парадигма чітко розмежовує дві незалежні криптографічні задачі:

### 1. Фаза вилучення (Extract)

Завдання першої фази — прийняти вхідний ключовий матеріал (Input Keying Material, `IKM`), який містить концентровану, але статистично нерівномірну ентропію (наприклад, спільний секрет Діффі — Геллмана або попередньо узгоджений Pre-Shared Key), та «витиснути» всю наявну випадковість у компактний, криптографічно псевдовипадковий ключ (Pseudorandom Key, `PRK`) фіксованої довжини.

Математичним фундаментом фази вилучення є **Лема про залишковий геш** (Leftover Hash Lemma):

```
Якщо джерело X має мін-ентропію H_∞(X) ≥ k + 2·log₂(1/ε),
то застосування 2-універсального сімейства геш-функцій H_salt
дає вихід довжиною k бітів, статистична відстань якого від
істинно рівномірного розподілу U_k не перевищує малого числа ε.
```

Роль солі (`salt`) у фазі `Extract` полягає у виборі конкретної функції з універсального сімейства екстракторів. Сіль не зобов'язана бути таємною — вона є відкритим випадковим параметром. Навіть якщо зловмисник знає значення солі, властивості екстрактора гарантують рівномірність `PRK`.

### 2. Фаза розгортання (Expand)

Маючи якісний псевдовипадковий ключ `PRK`, розподіл якого статистично невідрізний від істинного бітового шуму, друга фаза використовує його як ключ для псевдовипадкової функції (PRF). Фаза `Expand` розгортає цей короткий ключ у потік вихідного матеріалу (Output Keying Material, `OKM`) довільної необхідної довжини `L`.

На фазі розгортання обов'язково використовується контекстний рядок `info`. Цей параметр включає назву протоколу, версію, ідентифікатори клієнта та сервера, номери сесій або типи ключів. Це створює суворе криптографічне розділення контекстів: зміна хоча б одного байта в рядку `info` призводить до генерації абсолютно незалежного набору підключів через лавинний ефект геш-функції.

## Стандарт HKDF (RFC 5869)

Стандарт **HKDF** реалізує парадигму Extract-then-Expand на базі блокового коду автентичності HMAC з базовою криптографічною геш-функцією (найчастіше SHA-256 або SHA-512).

Позначимо через `HashLen` довжину дайджесту обраної геш-функції в байтах (для SHA-256 `HashLen = 32`, для SHA-512 `HashLen = 64`).

```
Вхідні параметри HKDF:
  IKM  : Вхідний ключовий матеріал (Input Keying Material)
  salt : Опціональна сіль (якщо не задана — масив нулів довжини HashLen)
  info : Контекстний рядок застосунку (може бути порожнім)
  L    : Бажана довжина вихідного ключа в байтах (L ≤ 255 · HashLen)
```

### Алгоритм HKDF-Extract

Функція вилучення викликає HMAC, використовуючи сіль як ключ, а сирий секрет `IKM` — як вхідне повідомлення:

```
PRK = HKDF-Extract(salt, IKM)
    = HMAC-Hash(Key = salt, Data = IKM)      [вилучення ентропії у фіксований блок]
```

Зверніть увагу на архітектурну інверсію ролей: несекретна сіль стає ключем HMAC, а секретний `IKM` передається у полі даних. Властивості HMAC як псевдовипадкової функції гарантують, що за наявності достатньої ентропії в `IKM`, вихід `PRK` довжиною `HashLen` байтів має ідеальний псевдовипадковий розподіл.

Якщо параметр `salt` не передано застосунком або він порожній, стандарт автоматично ініціалізує сіль фіксованим масивом нулів довжиною `HashLen`:
```
default_salt = 0x00 0x00 ... 0x00  (масив довжиною HashLen байтів)
```

### Алгоритм HKDF-Expand

Функція розгортання генерує послідовність блоків `T(1), T(2), ..., T(N)` шляхом зчеплення їх у криптографічний ланцюг за допомогою HMAC з ключем `PRK`:

```
N = ceil(L / HashLen)                        [кількість необхідних HMAC-блоків]

T(0) = ""                                    [початковий нульовий рядок]
T(1) = HMAC-Hash(PRK, T(0) || info || 0x01)  [перший блок розгортання]
T(2) = HMAC-Hash(PRK, T(1) || info || 0x02)  [другий блок: зворотний зв'язок від T(1)]
T(3) = HMAC-Hash(PRK, T(2) || info || 0x03)  [третій блок: зворотний зв'язок від T(2)]
...
T(N) = HMAC-Hash(PRK, T(N-1) || info || N)   [N-й блок: де N кодується 1 байтом]

OKM = Перші L байтів конкатенації (T(1) || T(2) || ... || T(N))
```

Оператор `||` позначає бінарну конкатенацію байтових масивів. Кожен раунд змішує попередній згенерований блок `T(i-1)`, незмінний контекст `info` та 1-байтний лічильник `0x01 .. 0xFF`.

```
Покрокове обчислення для L = 48 байтів (на базі SHA-256, HashLen = 32):
  N = ceil(48 / 32) = 2 блоки

  T(0) = ""
  T(1) = HMAC-SHA256(PRK, ""   || "handshake key" || 0x01)   [дає 32 байти]
  T(2) = HMAC-SHA256(PRK, T(1) || "handshake key" || 0x02)   [дає 32 байти]

  OKM = Перші 48 байтів масиву (T(1) || T(2))
```

### Причина обмеження `L <= 255 * HashLen`

Лічильник блоків у стандарті HKDF кодується рівно одним байтом (`0x01` до `0xFF`), що обмежує максимальну кількість раундів числом 255. Це проектне обмеження обумовлене двома факторами:

1. **Запобігання виснаженню ентропії (Entropy leakage):** Зворотний зв'язок `T(i) = HMAC(PRK, T(i-1) || ...)` є спрощеним варіантом режиму зворотного зв'язку за виходом (OFB). При генерації надто великих обсягів даних на одному ключі зростає теоретична ймовірність виявлення коротких циклів або колізій внутрішнього стану PRF.
2. **Практична достатність:** Для SHA-256 ліміт становить `255 · 32 = 8160` байтів, а для SHA-512 — `16320` байтів. Жоден протокол автентифікації або шифрування каналів зв'язку не вимагає більше кількох сотень байтів ключів на сесію.

> 🔧 **Навіщо це.** Якщо застосунку потрібно згенерувати мегабайти псевдовипадкових байтів (наприклад, для шифрування дискових секторів або наповнення буферів тестування), HKDF використовують лише для виведення 256-бітного майстер-ключа симетричного генератора CSPRNG (наприклад, ChaCha20 або AES-CTR), який уже розгортає потік без обмеження довжини.

## Парольні KDF (Password-Based KDF) та апаратна асиметрія

HKDF спроєктований як високопродуктивний примітив: одне обчислення `HKDF-Extract` + `HKDF-Expand` виконується за частки мікросекунди. Для сесійних ключів з вхідною ентропією понад 128 бітів висока швидкість є перевагою, що дозволяє серверам обслуговувати сотні тисяч TLS-з'єднань на секунду.

Однак застосування швидких функцій (HKDF, одинарний SHA-256 або швидкий HMAC) до **паролів користувачів** веде до повної компрометації системи.

Звичайний пароль людини містить катастрофічно малу кількість ентропії — типово від 20 до 40 бітів. Якщо захистити такий пароль швидкою функцією, зловмисник, отримавши викрадену базу гешів, запускає масований перебір на спеціалізованому обладнанні:

```
Продуктивність перебору SHA-256 на споживчому GPU (RTX 4090):
  Швидкість: ~ 10 000 000 000 гешів/с (10 GH/s)
  Простір 36 бітів (малий пароль): 2³⁶ ≈ 68.7 мільярдів комбінацій
  Час повного перебору: 68.7 / 10 ≈ 6.8 секунди
```

![Спектр стійкості KDF до апаратного перебору](/root/eng/sf-security/key-derivation-function/img/kdf-memory-hardness.svg)
*Порівняння архітектурних підходів KDF для паролів: від процесорно-обмеженого PBKDF2 до пам'ятевитратного гібриду Argon2id.*

Для захисту паролів створено спеціальний клас алгоритмів — **Password-Based KDF**. Їхнє завдання — створити критичну асиметрію витрат: легітимний користувач при вході витрачає 100–300 мс процесорного часу та фіксований обсяг RAM, тоді як для атакуючого масовий паралельний перебір мільярдів варіантів стає економічно неможливим.

### 1. PBKDF2 (RFC 2898 / RFC 8018)

Стандарт PBKDF2 (Password-Based Key Derivation Function 2) намагався сповільнити зловмисника шляхом збільшення кількості процесорних ітерацій `c` базової псевдовипадкової функції `PRF` (зазвичай `HMAC-SHA256`):

```
DK = PBKDF2(Password, Salt, c, dkLen)
```

Внутрішнє ядро PBKDF2 обчислює кожен вихідний блок через ітеративний ланцюг XOR:

```
U(1) = PRF(Password, Salt || INT_32_BE(i))
U(2) = PRF(Password, U(1))
U(3) = PRF(Password, U(2))
...
U(c) = PRF(Password, U(c-1))

F(Password, Salt, c, i) = U(1) ⊕ U(2) ⊕ ... ⊕ U(c)
```

#### Чому PBKDF2 більше не захищає від ASIC та FPGA

Головна слабкість PBKDF2 полягає у **нульовому споживанні оперативної пам'яті**. Для обчислення одного раунду `HMAC-SHA256` потрібно менше 100 байтів стану, які повністю вміщуються у внутрішні регістри процесора.

Розробники апаратних майнерів та систем злому будують на базі FPGA та ASIC масивно-паралельні конвеєри: один кремнієвий чіп може містити десятки тисяч паралельних ядер PBKDF2, які працюють на максимальній тактовій частоті без жодних затримок на звернення до зовнішньої пам'яті. Навіть 600 000 ітерацій PBKDF2 перебираються на спеціалізованих фермах із швидкістю в сотні тисяч разів вищою, ніж на універсальних CPU.

### 2. bcrypt (1999)

Алгоритм **bcrypt**, створений Нільсом Провосом та Девідом Мазьєром, використовував іншу стратегію: прив'язку до пам'яті через симетричний шифр Blowfish (алгоритм `EksblowfishSetup`).

Внутрішній стан bcrypt містить 4 КіБ таблиць замін (S-блоків), які псевдовипадково модифікуються під час виконання тисяч раундів:

- Кожна ітерація потребує частих непередбачуваних читань та записів за довільними адресами всередині 4 КіБ;
- Це зламало ранні спроби перебору на GPU, оскільки відеокарти погано справлялися з незалежним випадковим доступом до локальної пам'яті для кожного з тисяч потоків.

Проте 4 КіБ пам'яті — це замало для сучасної мікроелектроніки: такий обсяг без проблем вміщується в L1-кеш сучасних графічних процесорів або у внутрішні блоки блочної пам'яті (Block RAM, BRAM) сучасних FPGA. Додатковим мінусом bcrypt є жорстке архітектурне обмеження на довжину пароля — не більше 72 байтів.

### 3. scrypt (RFC 7914)

У 2009 році Колін Персіваль запропонував алгоритм **scrypt**, ввівши поняття **послідовних пам'ятевитратних функцій** (Sequential Memory-Hard Functions, SMHF).

Основою scrypt є алгоритм `ROMix`, що працює у дві фази:

1. **Фаза заповнення пам'яті:** Алгоритм послідовно виділяє масив `V` розміром `N` великих блоків (наприклад, 128 МБ або 1 ГБ RAM), записуючи туди результати псевдовипадкового перемішування `BlockMix` на базі Salsa20/8:
   ```
   V[0] = X
   V[1] = BlockMix(V[0])
   ...
   V[N-1] = BlockMix(V[N-2])
   ```
2. **Фаза псевдовипадкового доступу:** Алгоритм виконує `N` кроків, де адреса наступного блоку для читання залежить від бітів поточного блоку (`data-dependent indexing`):
   ```
   j = Integerify(X) mod N
   X = BlockMix(X ⊕ V[j])
   ```

#### Компроміс час-пам'ять (Time-Memory Trade-Off, TMTO)

Зловмисник на ASIC опиняється перед жорстким вибором:
- Або оснастити кожне паралельне ядро 128–1024 МБ дорогої зовнішньої пам'яті DRAM (що робить чіп велетенським за площею і занадто дорогим);
- Або зберігати лише частину блоків (наприклад, кожен `k`-й блок), відновлюючи відсутні блоки повторним перерахунком Salsa20/8 при кожному зверненні, що призводить до падіння швидкості перебору пропорційно `k`.

### 4. Argon2 (RFC 9106, Переможець Password Hashing Competition)

Алгоритм **Argon2** (автори Алекс Бірюков, Даніель Діну, Дмитро Ховратович) здобув перемогу на конкурсі PHC у 2015 році та стандартизований як RFC 9106.

Argon2 будує матрицю блоків пам'яті розміром по 1024 байти (1 КіБ), перемішуючи їх 64-бітними раундами стиснення `G` на базі Blake2b. Алгоритм гнучко конфігурується трьома параметрами вартості:
- Час `t` (кількість проходів по матриці пам'яті);
- Пам'ять `m` (обсяг виділеної оперативної пам'яті в КіБ, наприклад `65536` для 64 МіБ);
- Паралелізм `p` (кількість паралельних потоків обчислення, що ділять пам'ять на незалежні смуги — lanes).

Алгоритм випускається у трьох варіантах:

```
┌─────────────┬─────────────────────────────────┬──────────────────────────────────┐
│ Модифікація │ Тип адресації пам'яті           │ Профіль захисту                  │
├─────────────┼─────────────────────────────────┼──────────────────────────────────┤
│ Argon2d     │ Data-dependent (залежить від    │ Максимальний захист від GPU/ASIC │
│             │ значень пароля і блоків)        │ Вразливий до атак по кешу CPU    │
├─────────────┼─────────────────────────────────┼──────────────────────────────────┤
│ Argon2i     │ Data-independent (генерується   │ Повний захист від Side-Channel   │
│             │ через псевдовипадковий генератор│ Дещо вразливіший до TMTO на ASIC │
├─────────────┼─────────────────────────────────┼──────────────────────────────────┤
│ Argon2id    │ Гібрид: 1-й прохід частково 2i, │ Оптимальний сучасний стандарт:   │
│             │ решта ітерацій — 2d             │ захист від кешу і стійкість ASIC │
└─────────────┴─────────────────────────────────┴──────────────────────────────────┘
```

#### Чому саме Argon2id є сучасним золотим стандартом

При використанні data-dependent адресації (Argon2d, scrypt) адреси зчитування пам'яті прямо залежать від секретних бітів пароля. Якщо сервер виконує автентифікацію у віртуалізованій хмарі або на спільній апаратній платформі, сусідній небезпечний процес може вимірювати затримки доступу до кеш-ліній процесора (атаки Prime+Probe, Flush+Reload). Відстеживши послідовність звернень до пам'яті, зловмисник відновлює значення пароля без перебору.

**Argon2id** усуває цей вектор атаки:
1. Першу половину першого проходу по пам'яті він здійснює суворо в режимі **Argon2i** (адреси формуються детермінованим псевдовипадковим генератором незалежно від секрету). Це повністю затирає будь-які сліди первинного пароля в кеш-пам'яті;
2. Другу половину першого проходу та всі наступні ітерації алгоритм виконує в режимі **Argon2d**, вмикаючи максимальну стійкість проти TMTO-атак на графічних процесорах та ASIC.

## Практичні протокольні схеми: TLS 1.3 та Noise Protocol

Розглянемо архітектуру застосування HKDF у двох найпоширеніших сучасних криптографічних протоколах.

### Дерево виведення ключів у TLS 1.3 (RFC 8446)

Протокол TLS 1.3 повністю замінив складні й неоднорідні механізми PRF з версії 1.2 на єдину, строго формалізовану схему на основі HKDF.

![Ланцюг виведення секретів у TLS 1.3](/root/eng/sf-security/key-derivation-function/img/tls13-key-schedule.svg)
*Ланцюг виведення секретів у TLS 1.3: поетапна еволюція стану рукостискання від Early Secret до Master Secret через HKDF-Extract та HKDF-Expand-Label.*

У TLS 1.3 визначено спеціальну обгортку над функцією `HKDF-Expand`, що називається `HKDF-Expand-Label`:

```
HKDF-Expand-Label(Secret, Label, Context, Length) =
    HKDF-Expand(Secret, HkdfLabel, Length)
```

Де `HkdfLabel` є структурованим байтовим масивом:

```
struct {
    uint16 length = Length;
    opaque label<7..255> = "tls13 " + Label;
    opaque context<0..255> = Context;
};
```

Додатково визначено макро-функцію `Derive-Secret`:

```
Derive-Secret(Secret, Label, Messages) =
    HKDF-Expand-Label(Secret, Label, Transcript-Hash(Messages), HashLen)
```

Тут `Transcript-Hash(Messages)` — це криптографічний геш усіх попередніх повідомлень рукостискання (від ClientHello до поточного моменту). Це унеможливлює підміну параметрів рукостискання активним посередником (MitM).

#### Поетапна еволюція секретів у сесії TLS 1.3:

1. **Фаза Early Secret (0-RTT):**
   ```
   Early Secret = HKDF-Extract(Salt = 0, IKM = PSK)
   ```
   Якщо клієнт не використовує відновлення сесії через PSK, замість `PSK` передається масив нулів довжиною `HashLen`. З `Early Secret` виводиться ключ `client_early_traffic_secret` для шифрування ранніх даних.

2. **Фаза Handshake Secret:**
   Коли клієнт і сервер обмінюються відкритими ключами ECDHE (наприклад, X25519) і обчислюють спільний секрет `ECDHE_Shared`:
   ```
   derived_e = Derive-Secret(Early Secret, "derived", "")
   Handshake Secret = HKDF-Extract(Salt = derived_e, IKM = ECDHE_Shared)
   ```
   З `Handshake Secret` генеруються ключі `client_handshake_traffic_secret` та `server_handshake_traffic_secret`. Ними шифрується решта повідомлень рукостискання, включаючи сертифікати сторін та підтвердження `Finished`.

3. **Фаза Master Secret:**
   Після перевірки автентичності обох сторін стан переходить до основного робочого секрету сесії:
   ```
   derived_hs = Derive-Secret(Handshake Secret, "derived", "")
   Master Secret = HKDF-Extract(Salt = derived_hs, IKM = 0)
   ```
   З `Master Secret` виводяться фінальні ключі прикладного трафіку (`client_application_traffic_secret_0`, `server_application_traffic_secret_0`) та квитки відновлення (`resumption_master_secret`).

#### Оновлення ключів у сесії (Key Update)

Якщо з'єднання TLS 1.3 передає гігабайти або терабайти даних без розриву сокета, лічильники nonce у AEAD-шифрах наближаються до небезпечних меж переповнення. TLS 1.3 оновлює ключі на льоту без повного повторного рукостискання за допомогою команди `KeyUpdate`:

```
client_application_traffic_secret_N+1 =
    HKDF-Expand-Label(client_application_traffic_secret_N, "traffic upd", "", HashLen)
```

Ця одностороння операція забезпечує внутрішню досконалу пряму таємність (Perfect Forward Secrecy): компрометація поточного сесійного ключа не дозволяє розшифрувати пакети, передані до останнього `KeyUpdate`.

### Двоетапний ланцюг у Noise Protocol Framework

Фреймворк **Noise Protocol** (основа WireGuard та протоколів месенджера Signal) використовує об'єкт `SymmetricState` з двома внутрішніми 32-байтними регістрами: `ck` (Chaining Key — ланцюговий секрет) та `h` (Handshake Hash).

При виконанні кожної операції Діффі — Геллмана стан оновлюється за допомогою двоетапного HKDF:

```
MixKey(dh_output):
  (ck, temp_k) = HKDF(Salt = ck, IKM = dh_output, num_outputs = 2)
  SetCipherKey(temp_k)
```

Функція HKDF виводить рівно два 32-байтні блоки:
- Перший блок стає новим значенням ланцюгового ключа `ck` для наступних кроків;
- Другий блок (`temp_k`) використовується для шифрування наступного пакета протоколу через AEAD ChaCha20-Poly1305.

## Інженерна реалізація та робота з таємницями

Нижче наведено практичну реалізацію алгоритму HKDF (Extract та Expand) на базі `HMAC-SHA256` відповідно до стандарту RFC 5869.

При роботі з ключовим матеріалом у пам'яті обов'язково дотримуються двох правил:
1. **Гарантоване затирання пам'яті (Secure Zeroization):** Усі проміжні змінні, що містять `PRK`, `IKM` або блоки `T(i)`, затираються одразу після використання. Звичайний виклик `memset()` може бути видалений оптимізатором компілятора (dead store elimination), тому слід використовувати `OPENSSL_cleanse()`, `explicit_bzero()` або спеціальні RAII-обгортки з бар'єрами пам'яті.
2. **Контроль довжини та меж лічильника:** Сувора перевірка умови `okm_len <= 255 * SHA256_DIGEST_LEN`.

:::tabs
```c
#include <openssl/hmac.h>
#include <openssl/sha.h>
#include <openssl/crypto.h>
#include <string.h>
#include <stdint.h>
#include <stdbool.h>

#define SHA256_DIGEST_LEN 32

/*
 * HKDF-Extract(salt, ikm) -> prk
 */
bool hkdf_extract_sha256(const uint8_t *salt, size_t salt_len,
                         const uint8_t *ikm, size_t ikm_len,
                         uint8_t prk_out[SHA256_DIGEST_LEN])
{
    uint8_t default_salt[SHA256_DIGEST_LEN] = {0};
    const uint8_t *actual_salt = salt;
    size_t actual_salt_len = salt_len;

    if (actual_salt == NULL || actual_salt_len == 0) {
        actual_salt = default_salt;
        actual_salt_len = sizeof(default_salt);
    }

    unsigned int out_len = 0;
    uint8_t *res = HMAC(EVP_sha256(),
                        actual_salt, (int)actual_salt_len,
                        ikm, ikm_len,
                        prk_out, &out_len);

    return (res != NULL && out_len == SHA256_DIGEST_LEN);
}

/*
 * HKDF-Expand(prk, info, okm_len) -> okm
 */
bool hkdf_expand_sha256(const uint8_t prk[SHA256_DIGEST_LEN],
                        const uint8_t *info, size_t info_len,
                        uint8_t *okm_out, size_t okm_len)
{
    if (okm_out == NULL || okm_len == 0) return false;
    if (okm_len > 255 * SHA256_DIGEST_LEN) return false;

    size_t n = (okm_len + SHA256_DIGEST_LEN - 1) / SHA256_DIGEST_LEN;
    uint8_t t_block[SHA256_DIGEST_LEN];
    size_t t_len = 0;
    size_t bytes_copied = 0;

    HMAC_CTX *ctx = HMAC_CTX_new();
    if (!ctx) return false;

    for (uint8_t i = 1; i <= (uint8_t)n; ++i) {
        if (!HMAC_Init_ex(ctx, prk, SHA256_DIGEST_LEN, EVP_sha256(), NULL)) {
            HMAC_CTX_free(ctx);
            OPENSSL_cleanse(t_block, sizeof(t_block));
            return false;
        }

        if (t_len > 0) {
            HMAC_Update(ctx, t_block, t_len);
        }
        if (info != NULL && info_len > 0) {
            HMAC_Update(ctx, info, info_len);
        }
        HMAC_Update(ctx, &i, 1);

        unsigned int written = 0;
        HMAC_Final(ctx, t_block, &written);
        t_len = written;

        size_t to_copy = (okm_len - bytes_copied < SHA256_DIGEST_LEN)
                         ? (okm_len - bytes_copied)
                         : SHA256_DIGEST_LEN;

        memcpy(okm_out + bytes_copied, t_block, to_copy);
        bytes_copied += to_copy;
    }

    HMAC_CTX_free(ctx);
    OPENSSL_cleanse(t_block, sizeof(t_block));
    return true;
}
```

```cpp
#include <openssl/evp.h>
#include <openssl/hmac.h>
#include <openssl/crypto.h>
#include <span>
#include <vector>
#include <array>
#include <optional>
#include <cstdint>
#include <memory>
#include <string_view>
#include <algorithm>

namespace crypto {

constexpr size_t sha256_digest_len = 32;

// Безпечний контейнер для секретних байтів, що затирає пам'ять при знищенні (RAII)
template <size_t N>
struct secure_array {
    std::array<uint8_t, N> data{};

    ~secure_array() {
        OPENSSL_cleanse(data.data(), data.size());
    }

    [[nodiscard]] std::span<const uint8_t, N> as_span() const noexcept {
        return std::span<const uint8_t, N>(data);
    }
};

class hkdf_sha256 {
public:
    using prk_type = secure_array<sha256_digest_len>;

    // Етап Extract: IKM + Salt -> PRK
    static std::optional<prk_type> extract(
        std::span<const uint8_t> ikm,
        std::span<const uint8_t> salt = {})
    {
        prk_type prk;
        std::array<uint8_t, sha256_digest_len> default_salt{};

        std::span<const uint8_t> actual_salt = salt.empty() 
            ? std::span<const uint8_t>(default_salt) 
            : salt;

        unsigned int out_len = 0;
        uint8_t* res = HMAC(EVP_sha256(),
                            actual_salt.data(), static_cast<int>(actual_salt.size()),
                            ikm.data(), ikm.size(),
                            prk.data.data(), &out_len);

        if (!res || out_len != sha256_digest_len) {
            return std::nullopt;
        }
        return prk;
    }

    // Етап Expand: PRK + Info + okm_len -> OKM
    static std::optional<std::vector<uint8_t>> expand(
        const prk_type& prk,
        std::span<const uint8_t> info,
        size_t okm_len)
    {
        if (okm_len == 0 || okm_len > 255 * sha256_digest_len) {
            return std::nullopt;
        }

        std::vector<uint8_t> okm(okm_len);
        const size_t num_blocks = (okm_len + sha256_digest_len - 1) / sha256_digest_len;

        std::array<uint8_t, sha256_digest_len> t_block{};
        size_t t_len = 0;
        size_t bytes_copied = 0;

        std::unique_ptr<HMAC_CTX, decltype(&HMAC_CTX_free)> ctx(HMAC_CTX_new(), &HMAC_CTX_free);
        if (!ctx) return std::nullopt;

        for (uint8_t i = 1; i <= static_cast<uint8_t>(num_blocks); ++i) {
            if (!HMAC_Init_ex(ctx.get(), prk.data.data(), prk.data.size(), EVP_sha256(), nullptr)) {
                OPENSSL_cleanse(t_block.data(), t_block.size());
                return std::nullopt;
            }

            if (t_len > 0) {
                HMAC_Update(ctx.get(), t_block.data(), t_len);
            }
            if (!info.empty()) {
                HMAC_Update(ctx.get(), info.data(), info.size());
            }
            HMAC_Update(ctx.get(), &i, 1);

            unsigned int written = 0;
            HMAC_Final(ctx.get(), t_block.data(), &written);
            t_len = written;

            const size_t to_copy = std::min(okm_len - bytes_copied, sha256_digest_len);
            std::copy_n(t_block.begin(), to_copy, okm.begin() + bytes_copied);
            bytes_copied += to_copy;
        }

        OPENSSL_cleanse(t_block.data(), t_block.size());
        return okm;
    }
};

} // namespace crypto
```

## Зведена порівняльна характеристика сучасних KDF

Для вибору оптимального примітиву в інженерній практиці слід спиратися на характеристики пам'яті, призначення та профіль загроз:

| Алгоритм | Базовий примітив | Пам'ять на потік | Основне призначення | Стійкість до ASIC / GPU | Стійкість до Side-Channel |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **HKDF (RFC 5869)** | HMAC (SHA-2/3) | ~0 байтів | Сесійні ключі, TLS 1.3, IKM високої ентропії | Не захищає паролі (високошвидкісний) | Повна (немає залежності від пам'яті) |
| **PBKDF2 (RFC 8018)** | HMAC (SHA-256) | ~0 байтів | Застарілі стандарти паролів | Вразливий до паралельних конвеєрів ASIC | Повна (CPU-only) |
| **bcrypt** | Blowfish (Eksblowfish) | 4 КіБ | Автентифікація користувачів (веб) | Помірна (вразливий до сучасних FPGA/ASIC) | Помірна |
| **scrypt (RFC 7914)** | Salsa20/8 + SHA-256 | 16–128 МіБ | Шифрування ключів і сховищ файлів | Висока (Sequential Memory-Hard) | Чутливий до витоків кешу CPU (TMTO) |
| **Argon2id (RFC 9106)**| Blake2b + Matrix | 64–1024 МіБ | Сучасний еталон гешування паролів | Найвища (Memory-hard + TMTO proof) | Захищений (двоетапний гібрид) |

Вибір KDF визначається походженням та ентропією секрету: для обчислювально непередбачуваних сирих ключів криптографічних протоколів (ECDH, PSK) де-факто стандартом є **HKDF**, тоді як для таємниць людського походження з низькою ентропією (паролі, пін-коди, мнемонічні фрази) безальтернативним інженерним вибором є **Argon2id**.
