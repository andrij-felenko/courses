# 📜 Історія W^X та біта No-Execute: від патчів ядра до апаратного стандарту

Історія захисту пам'яті від виконання — це літопис боротьби між програмними хаками для компенсації недоліків процесорів та поступовим визнанням виробниками кремнію того факту, що відсутність розрізнення коду й даних є фундаментальною загрозою безпеці обчислень.

---

## 1. Архітектурна спадщина x86 та виклик 1990-х років

Архітектура фон Неймана, реалізована в процесорах Intel починаючи з 8086 і закріплена в 32-розрядному захищеному режимі 80386 (IA-32), виходила з припущення, що пам'ять є універсальним середовищем для зберігання будь-якої інформації. У таблицях сторінок 32-розрядного x86 інженери Intel виділили лише один прапорець керування доступом: біт 1 (Read/Write, `R/W`). Якщо біт `R/W = 0`, сторінка доступна лише для читання; якщо `R/W = 1`, сторінка доступна для читання та запису. Окремого біта, який би контролював дозвіл на вибірку інструкцій (Instruction Fetch), у структурі запису таблиці сторінок (PTE) не існувало взагалі.

Наслідком цього спрощення стало правило: **будь-яка сторінка, доступна процесору для читання, автоматично вважалася виконуваною**. Коли процесор завантажував значення регістра покажчика інструкцій `EIP` з адреси, що належала стеку або купі, апаратний блок MMU бачив звичайний запит на зчитування даних і без жодних перешкод передавав байти конвеєру декодування інструкцій.

У 1996 році публікація статті Aleph One «Smashing The Stack For Fun And Profit» у журналі Phrack чітко показала наслідки: переповнення локального буфера на стеку давало змогу зловмиснику не просто порушити логіку програми, а записати в пам'ять стека масив власних машинних інструкцій (шелкод) і спрямувати туди `EIP`. Уразливими виявилися тисячі системних утиліт, мережевих служб і демонів Unix та Windows.

## 2. Перші програмні бар'єри: Solar Designer та проєкт PaX

Першу спробу виправити ситуацію без зміни процесорів здійснив у 1997 році розробник Олександр Песляк (відомий як *Solar Designer*), творець безпекового дистрибутива Openwall GNU/*/Linux.

### Патч невиконуваного стека Solar Designer (1997)

Оскільки сторінковий механізм x86 не мав біта виконання, Solar Designer звернувся до іншого механізму процесора 80386 — сегментації. У 32-розрядному Linux сегмент коду (`CS`) і сегмент даних (`DS`/`SS`) зазвичай перекривали весь 4-гігабайтний адресний простір від адреси `0x00000000` до `0xFFFFFFFF` (плоска модель пам'яті).

Solar Designer запропонував штучно обмежити розмір сегмента коду:
1. Сегмент коду `CS` налаштовувався так, щоб його верхня межа (segment limit) закінчувалася нижче області стека процесу (який у Linux традиційно починався біля адреси `0xC0000000` і ріс униз).
2. Якщо програма працювала в межах легітимного коду та бібліотек (розміщених у нижніх адресах), виконання тривало нормально.
3. Щойно значення `EIP` вказувало на адресу в області стека, апаратний блок сегментації x86 фіксував вихід за межу сегмента і генерував виняток загального захисту (General Protection Fault, переривання `#GP`, вектор 13), що миттєво вбивало атакований процес.

Це рішення мало недоліки: воно порушувало роботу вкладених функцій GCC (які генерували виконувані трампліни на стеку), вимагало фіксованого розподілу адресного простору та не захищало область динамічної пам'яті (купу).

```
+──────────────────────────────────────────────────────────────────────────+
|  0x00000000                                 0xBFFFFFFF       0xC0000000  |
|  [ Код програми (.text) | Бібліотеки ]      [ Стек (Stack) ] [ Ядро OS ] |
|  |<────── Межа сегмента CS (Limit) ────────>|                            |
|                                             |                            |
|  Спроба EIP потрапити сюди викликає #GP ───>| (Виконання заборонено)    |
+──────────────────────────────────────────────────────────────────────────+
```

### Проєкт PaX: PAGEEXEC та SEGMEXEC (2000)

У 2000 році анонімний дослідницький проєкт PaX запропонував значно радикальніший комплексний підхід. PaX реалізував дві технології емуляції біта заборони виконання:

1. **PAGEEXEC:** Використовував сторінковий механізм та особливості роботи буфера асоціативної трансляції (TLB). Якщо сторінка не повинна була виконуватися, PaX знімав із неї прапорець присутності (`Present = 0`) або прапорець користувача (`User = 0`). Будь-яке звернення до сторінки викликало сторінковий збій (#PF). Обробник ядра аналізував причину: якщо звернення відбулося для читання чи запису даних, ядро тимчасово оновлювало запис у TLB даних (dTLB) і дозволяло інструкції завершитися; якщо ж звернення ініціював блок вибірки інструкцій (iTLB), ядро фіксувало спробу несанкціонованого виконання коду й аварійно зупиняло процес. Це давало захист на рівні окремих сторінок, але створювало значні накладні витрати через часті виклики обробника `#PF`.
2. **SEGMEXEC:** Використовував сегментні регістри для дзеркального поділу адресного простору процесу на дві рівні половини по 1.5 ГБ: одну для даних, іншу для коду. Хоча накладні витрати на перевірки зникли, це вдвічі скорочувало доступний віртуальний простір програми.

## 3. Маніфест OpenBSD 3.3 та народження принципу W^X (2003)

У травні 2003 року Тео де Раадт (*Theo de Raadt*) та команда проєкту OpenBSD випустили реліз OpenBSD 3.3, у якому вперше на рівні системної політики було проголошено принцип **W^X** (*Write XOR Execute*).

Філософія OpenBSD базувалася на фундаментальному правилі: операційна система не повинна покладатися на добропорядність програм або випадковість. Жодна сторінка віртуальної пам'яті процесу в будь-який момент часу не повинна бути одночасно доступною для запису і виконання.

OpenBSD провела масштабний аудит усієї бази коду:
- З компіляторів та завантажувачів було усунуто виконувані трампліни на стеку.
- Сегменти ELF-бінарників були жорстко розмежовані на `PT_LOAD` з правами `PF_R | PF_X` (код) та `PT_LOAD` з правами `PF_R | PF_W` (дані).
- На архітектурах, де MMU підтримував апаратне розмежування (SPARC, Alpha, UltraSPARC), W^X увімкнули апаратно.
- На x86 було застосовано перекомпонування адресного простору та сегментні обмеження, аналогічні напрацюванням Solar Designer, із забороною системному виклику `mprotect()` встановлювати комбінацію `PROT_WRITE | PROT_EXEC`.

```
=============================================================================
Хронологія еволюції концепції захисту пам'яті від виконання:

1996  Aleph One: публікація "Smashing The Stack For Fun And Profit" (Phrack #49)
1997  Solar Designer: перший патч невиконуваного стека через сегментні ліміти x86
2000  Проєкт PaX: програмна емуляція заборони виконання (PAGEEXEC / SEGMEXEC)
2003  OpenBSD 3.3: системне впровадження політики W^X
2003  AMD: випуск архітектури AMD64 з апаратним бітом NX (Opteron / Athlon 64)
2004  Intel: випуск процесорів Prescott із бітом XD (Execute Disable)
2004  Microsoft: реліз Windows XP SP2 з технологією Hardware DEP
=============================================================================
```

## 4. Апаратна революція: біт NX в AMD64 та відповідь Intel

На початку 2000-х років компанія AMD розробляла принципово нову 64-розрядну архітектуру x86-64 (AMD64), покликану замінити застарілу IA-32. Проєктуючи новий формат 4-рівневих таблиць сторінок (PML4 -> PDPT -> PD -> PT), інженери AMD вирішили усунути головну ваду x86 на апаратному рівні.

### Біт NX від AMD (2003)

У квітні 2003 року разом із випуском серверного процесора AMD Opteron та у вересні 2003 року з випуском настільного Athlon 64 (мікроархітектура K8) компанія AMD офіційно представила біт **NX** (*No-Execute*).

Інженери виділили під прапорець заборони виконання найстарший, 63-й біт у кожному записі таблиць сторінок усіх рівнів трансляції:
- Якщо біт 63 встановлено в `0`, сторінка є виконуваною.
- Якщо біт 63 встановлено в `1`, будь-яка спроба процесора виконати Instruction Fetch за віртуальною адресою цієї сторінки призводить до апаратного сторінкового збою (#PF) безпосередньо в конвеєрі MMU.

Для сумісності з 32-розрядними операційними системами біт NX було також додано до розширеного 64-бітного формату таблиць сторінок PAE (*Physical Address Extension*), який вмикався через біт `NXE` (No-Execute Enable, біт 11) у службовому регістрі `EFER` (Extended Feature Enable Register, MSR `0xC0000080`).

### Реакція Intel: біт XD (2004)

Компанія Intel спочатку вважала, що ринок перейде на 64-розрядну архітектуру IA-64 (Itanium), де захист пам'яті реалізовувався через складну систему кілець і привілеїв. Проте ринковий тріумф AMD64 змусив Intel поспіхом ліцензувати архітектуру AMD64 (під назвою Intel 64 / EM64T).

У 2004 році Intel представила оновлені ядра Pentium 4 на базі мікроархітектури Prescott (степінг E0, роз'єм LGA775) та серверні процесори Xeon (ядро Nocona), у яких з'явилася точна копія біта NX під маркетинговою назвою **XD** (*Execute Disable*). Процесори Intel використовували той самий 63-й біт у таблицях сторінок і активувалися тим самим бітом у регістрі `MSR_EFER`.

Паралельно компанія ARM у 2002 році додала біт **XN** (*Execute-Never*) до архітектури ARMv6, закріпивши його як стандарт у всіх наступних поколіннях ARMv7-A та ARMv8-A.

## 5. Впровадження в масові ОС: Windows XP SP2 та технологія DEP

До 2003 року корпорація Microsoft ставилася до апаратних засобів захисту як до факультативних опцій. Проте в серпні 2003 року світ сколихнула епідемія хробака **Blaster** (який експлуатував переповнення стекового буфера в службі RPC DCOM Windows), а у травні 2004 року мережі паралізував хробак **Sasser** (вразливість у службі LSASS). Обидві атаки використовували пряму ін'єкцію шелкоду на стек та в пам'ять купи.

Збитки світової економіки вимірювалися мільярдами доларів, і Білл Гейтс ініціював усередині Microsoft ініціативу *Trustworthy Computing*.

У серпні 2004 року Microsoft випустила оновлення **Windows XP Service Pack 2 (SP2)**, головним нововведенням якого стала технологія **DEP** (*Data Execution Prevention*):
- **Hardware-enforced DEP:** Якщо процесор підтримував біт NX/XD, Windows XP SP2 автоматично переводила всі сторінки стека, купи та пулів пам'яті в режим `PAGE_READWRITE` без прапорця `PAGE_EXECUTE`.
- **Режими роботи DEP:** Операційна система отримала чотири політики (OptIn, OptOut, AlwaysOn, AlwaysOff), що регулювалися через файл `boot.ini` (а згодом через `bcdedit`). За замовчуванням у клієнтських версіях Windows вмикався режим *OptIn* (захист критичних системних процесів Windows), а в серверних Windows Server 2003 SP1 — *OptOut* (захист усіх процесів, крім явно доданих до списку винятків).

Впровадження DEP та біта NX стало переломним моментом в історії кібербезпеки: класична епоха виконання шелкоду на стеку, що тривала майже десятиліття, відійшла в минуле. Зловмисники втратили можливість виконувати довільний код шляхом простої доставки байтів у пам'ять даних, що змусило індустрію наступальної безпеки винаходити принципово нові парадигми атак — насамперед техніку повторного використання наявного коду (Return-to-libc та ROP).
