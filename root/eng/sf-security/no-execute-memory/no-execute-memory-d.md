# Пам'ять без права виконання: біт NX і правило W^X

<preknowlist>

- [Сторінкова організація пам'яті та MMU](root:sf-os/paging-and-mmu) — структура таблиць сторінок (PTE), трансляція віртуальних адрес і біти дозволів.
- [ASLR: рандомізація розкладки адресного простору](root:sf-security/aslr) — випадкове зміщення сегментів пам'яті під час завантаження процесу.
</preknowlist>

На архітектурах фон Неймана процесор за замовчуванням сприймає будь-яку послідовність байтів в оперативній пам'яті як потенційно виконувані інструкції — байт `0x90` (`nop`) у сегменті скомпільованого коду і байт `0x90` у локальній змінній на стеку апаратно не відрізняються один від одного. Коли програма містила вразливість переповнення буфера, зловмисник записував у пам'ять стека послідовність байтів шелкоду й перетирав збережену адресу повернення значенням адреси власного буфера. Під час виконання інструкції `ret` блок вибірки інструкцій (Instruction Fetch Unit) слухняно зчитував байти зі стека, передавав їх у конвеєр декодування та виконував системний виклик `execve("/bin/sh")` із привілеями атакованого процесу. Вразливість ставала фатальною не через сам факт помилки виходу за межі масиву, а внаслідок відсутності апаратного розмежування між даними (що повинні змінюватися під час обчислень) та кодом (що має залишатися незмінним і виконуваним).

## 1. Апаратна основа заборони виконання: еволюція MMU та біт NX

У 32-розрядній архітектурі Intel IA-32 (починаючи з процесора 80386) сторінковий механізм віртуальної пам'яті передбачав лише один прапорець керування доступом на рівні записів таблиць сторінок (Page Table Entry, PTE): біт 1 (`R/W`, Read/Write). Якщо цей біт дорівнював `0`, сторінка була доступна лише для читання; якщо `1` — для читання та запису. Окремого прапорця для контролю права на виконання інструкцій у структурі 32-розрядного запису PTE не існувало взагалі.

Апаратна логіка блоку керування пам'яттю (MMU) трактувала операцію вибірки інструкції процесором (*Instruction Fetch*) як звичайне читання пам'яті. Це означало, що будь-яка сторінка, відкрита для читання даних, автоматично ставала доступною для виконання коду. Спроби розробників операційних систем у 1990-х роках обмежити виконання коду на стеку за допомогою сегментних регістрів (`CS limit`) або програмної емуляції в проєкті PaX вимагали складних хаків ядра й суттєво сповільнювали роботу комп'ютера.

Апаратне розв'язання проблеми з'явилося у 2003 році з виходом 64-розрядної архітектури AMD64 (x86-64). Інженери AMD змінили формат записів таблиць сторінок, виділивши під прапорець заборони виконання найстарший 63-й біт запису PTE. Цей механізм отримав назву **біт NX** (*No-Execute*). Компанія Intel незабаром впровадила ідентичну функціональність у процесорах Pentium 4 на ядрі Prescott під назвою **біт XD** (*Execute Disable*), а в архітектурі ARM аналогічний прапорець називається **XN** (*Execute-Never*, біт 54 у дескрипторах сторінок VMSAv8-64).

```
 63                                  51                  12 11   2   1   0
+----+------------------------------+----------------------+---+---+---+---+
| NX |      Службові біти ОС        |  Фізична адреса      |...|U/S|R/W| P |
|    |      (Available / Ignored)   |  кадру пам'яті (PFN) |   |   |   |   |
+----+------------------------------+----------------------+---+---+---+---+
  │                                                            │   │   │
  │                                                            │   │   └─ Present (1 = сторінка в RAM)
  │                                                            │   └───── Read/Write (0 = R, 1 = RW)
  │                                                            └───────── User/Supervisor (0 = Ring 0, 1 = Ring 3)
  └────────────────────────────────────────────────────────────────────── No-Execute (1 = Виконання заборонено)
```

### Ієрархія трансляції сторінок та спадкування обмежень

У 64-розрядному режимі (Long Mode) трансляція віртуальної адреси у фізичну проходить крізь 4-рівневе дерево таблиць сторінок:
1. **PML4** (*Page Map Level 4*) — адресується покажчиком із регістра `CR3`.
2. **PDPT** (*Page Directory Pointer Table*) — визначає гігабайтні регіони пам'яті.
3. **PD** (*Page Directory*) — визначає 2-мегабайтні регіони.
4. **PT** (*Page Table*) — кінцева таблиця 4-кілобайтних сторінок (PTE).

Критичною особливістю архітектури x86-64 є те, що біт NX присутній у записах **кожного** з чотирьох рівнів ієрархії. Під час обходу дерева блок MMU обчислює результуючі права за правилом найсуворішого обмеження (побітове логічне «АБО» для бітів NX):

```
NX_effective = NX_PML4 ∨ NX_PDPT ∨ NX_PD ∨ NX_PTE
```

Якщо операційна система встановлює біт `NX = 1` на рівні запису каталогу `PD` (наприклад, для великої сторінки 2 МіБ), усі вкладені 512 сторінок по 4 КіБ автоматично стають невиконуваними, навіть якщо їхні індивідуальні записи в PTE мали значення `NX = 0`. Це дозволяє ядру ефективно захищати цілі діапазони пам'яті (стеки всіх потоків процесу або сегменти динамічної купи) одним записом у таблиці вищого рівня.

### Робота NX на 32-розрядних системах через PAE

Для підтримки біта NX на 32-розрядних процесорах x86 інженери задіяли механізм **PAE** (*Physical Address Extension*). У стандартному 32-розрядному режимі записи таблиць сторінок мали розмір лише 32 біти, і для нового прапорця не вистачало місця. При активації режиму PAE (через біт `PAE` у регістрі `CR4`) формат записів таблиць сторінок розширювався до 64 бітів, а в регістрі модельно-залежних функцій `IA32_EFER` (MSR `0xC0000080`) з'являвся біт активації `NXE` (*No-Execute Enable*, біт 11).

Якщо `IA32_EFER.NXE = 1`, 63-й біт розширених дескрипторів PAE починав функціонувати як повноцінний апаратний бар'єр заборони виконання.

### Механізм захисту в архітектурі ARM (AArch64)

В архітектурі ARM (ARMv8-A та ARMv9-A) підсистема віртуальної пам'яті VMSAv8-64 реалізує ще більш гранулярний контроль виконання за допомогою двох окремих бітів:
1. **UXN** (*Unprivileged Execute-Never*, біт 54): Забороняє виконання інструкцій у непривілейованому режимі користувача (EL0).
2. **PXN** (*Privileged Execute-Never*, біт 53): Забороняє виконання інструкцій у привілейованому режимі ядра (EL1).

Наявність біта `PXN` вирішує фундаментальну проблему атак підвищення привілеїв типу *ret2usr* (повернення в простір користувача): коли ядро під час обробки системного виклику помилково намагається виконати код, підготовлений зловмисником у користувацькому буфері, апаратний блок MMU фіксує порушення `PXN` і миттєво аварійно зупиняє систему (Kernel Panic), не дозволяючи коду користувача виконатися з правами ядра.

```
+──────────────────────────────────────────────────────────────────────────+
|                    Апаратна перевірка конвеєром процесора                |
|                                                                          |
|  1. Регістр лічильника команд (RIP / PC) містить віртуальну адресу.      |
|  2. Блок MMU транслює віртуальну адресу через дерево таблиць сторінок.   |
|  3. Перевірка: Якщо біт 63 (NX/XD) або біт 54 (XN) == 1:                 |
|     ─ Інструкції НЕ потрапляють у чергу Instruction Decoder;             |
|     ─ Генерується апаратне переривання Page Fault (#PF, Вектор 14);      |
|     ─ У стек виклику записується код помилки з бітом I/D = 1;            |
|     ─ Ядро надсилає процесу сигнал SIGSEGV з кодом SEGV_ACCERR.          |
+──────────────────────────────────────────────────────────────────────────+
```

![Апаратна перевірка біта No-Execute (NX / XD) в таблицях сторінок x86-64](/root/eng/sf-security/no-execute-memory/img/nx-bit-pte-architecture.svg)
*Схема апаратної перевірки біта NX у таблицях сторінок x86-64 блоком MMU під час фази Instruction Fetch.*

Після з'ясування механізму введемо точні терміни:
- **Біт NX / XD / XN** (англ. *No-Execute bit*, *Execute Disable*, *Execute Never*, від латинського *executio* — виконання, здійснення) — апаратний прапорець у дескрипторі таблиці сторінок віртуальної пам'яті, що забороняє процесору зчитувати та виконувати машинний код із відповідного фізичного кадру.
- **Блок керування пам'яттю** (англ. *Memory Management Unit*, *MMU*, від латинського *memoria* — пам'ять та *manus* — рука, керування) — апаратний вузол процесора, що відповідає за трансляцію віртуальних адрес у фізичні, кешування трансляцій у TLB та перевірку прав доступу до сторінок.
- **Сторінковий збій** (англ. *page fault*, від латинського *pagina* — сторінка та *fallere* — обманювати, давати збій) — апаратне переривання процесора, що виникає при спробі звернення до сторінки віртуальної пам'яті з порушенням дозволених атрибутів або за відсутності сторінки в фізичній пам'яті.

## 2. Принцип W^X (Write XOR Execute) та системний механізм DEP

Поява апаратного біта NX створила фундамент для формулювання головного інваріанта безпеки сучасних обчислювальних систем — принципу **W^X** (*Write XOR Execute*, «Запис виключає виконання»).

Формально правило W^X виражається логічним співвідношенням для будь-якої сторінки віртуальної пам'яті `P` в адресній карті процесу:

```
W(P) ⊕ X(P) = 1     [або еквівалентно: ¬(W(P) ∧ X(P))]
```

де `W(P)` — дозвіл на запис у сторінку, а `X(P)` — дозвіл на виконання коду зі сторінки. 

Інваріант W^X постулює: **жодна сторінка віртуальної пам'яті ні в який момент часу не може одночасно мати права на запис і на виконання**.

```
+──────────────────────────────────────────────────────────────────────────+
|                     Класифікація сегментів за правилом W^X               |
|                                                                          |
|  1. Сегменти коду (.text):            Читання + Виконання (RX, W=0, X=1) |
|  2. Сегменти даних (Stack, Heap):     Читання + Запис     (RW, W=1, X=0) |
|  3. Константи та метадані (.rodata):  Лише читання        (RO, W=0, X=0) |
|                                                                          |
|  ✗ ЗАБОРОНЕНИЙ СТАН:                  Запис + Виконання   (RWX, W=1, X=1)|
+──────────────────────────────────────────────────────────────────────────+
```

Логіка цього правила випливає з аналізу вектора кібератак. Щоб зловмисник зміг виконати власний код у пам'яті чужої програми, необхідне одночасне виконання двох умов:
1. Нападник повинен мати змогу **записати** байти коду в певну область пам'яті (через мережевий сокет, файл, консольне введення або вихід за межі масиву).
2. Процесор повинен мати змогу **виконати** байти з цієї самої області пам'яті.

Якщо система гарантує, що всі області, куди програма може записувати дані (стек викликів, динамічна купа, сегменти неініціалізованих даних `.bss`, статичні змінні `.data`), мають скинутий біт виконання (`X = 0`), записані байти назавжди залишаються лише пасивними даними. Спроба спрямувати покажчик інструкцій на ці байти гарантовано призводить до аварійного зупинення процесу апаратним блоком MMU. 

Натомість області пам'яті, звідки процесор виконує легітимні інструкції програми (сегмент `.text` виконуваного файлу та динамічних бібліотек `libc.so`), мають скинутий біт запису (`W = 0`). Будь-яка спроба зловмисника модифікувати вже наявний скомпільований код блокується ядром як порушення прав доступу на запис.

В операційній системі Windows ця концепція отримала назву **DEP** (*Data Execution Prevention* — запобігання виконанню даних), а в UNIX-подібних системах (OpenBSD, Linux, macOS) закріпилася під назвою **W^X** або **Non-Executable Stack/Heap** ([докладний історичний розбір становлення W^X та DEP](root:sf-security/no-execute-memory/hist-w-xor-x-and-dep.md)).

![Принцип W^X: Розподіл прав та переходи станів](/root/eng/sf-security/no-execute-memory/img/w-xor-x-principle-and-transitions.svg)
*Стани сторінок пам'яті за правилом W^X: легітимні стани коду й даних проти забороненого небезпечного стану RWX.*

Для керування правами пам'яті на рівні процесів операційні системи надають набір низькорівневих системних викликів, таких як `mprotect()` та розширення Intel MPK ([довідник системних викликів та структур пам'яті](root:sf-security/no-execute-memory/api-mprotect-and-virtual-memory.md)).

## 3. Захист стека та купи: маркування GNU_STACK в ELF

Апаратна наявність біта NX сама по собі не гарантує захисту процесу — операційна система та системний завантажувач повинні знати, які саме права призначати кожному сегменту пам'яті під час запуску виконуваного файлу.

У бінарному форматі **ELF** (*Executable and Linkable Format*), що є стандартом для Linux та більшості POSIX-систем, структура завантаження описується заголовками програми (*Program Headers*).

```
$ readelf -l /usr/bin/passwd

Program Headers:
  Type           Offset             VirtAddr           PhysAddr
                 FileSiz            MemSiz              Flags  Align
  PHDR           0x0000000000000040 0x0000000000000040 0x0000000000000040
                 0x00000000000002d8 0x00000000000002d8  R      0x8
  LOAD           0x0000000000000000 0x0000000000000000 0x0000000000000000
                 0x0000000000001c38 0x0000000000001c38  R      0x1000
  LOAD           0x0000000000002000 0x0000000000002000 0x0000000000002000
                 0x0000000000008451 0x0000000000008451  R E    0x1000
  LOAD           0x000000000000b000 0x000000000000b000 0x000000000000b000
                 0x00000000000014b8 0x00000000000016e0  RW     0x1000
  GNU_STACK      0x0000000000000000 0x0000000000000000 0x0000000000000000
                 0x0000000000000000 0x0000000000000000  RW     0x10
```

Коли завантажувач ядра Linux (`fs/binfmt_elf.c`) обробляє бінарний файл під час системного виклику `execve()`, він аналізує спеціальний заголовок програми: **`PT_GNU_STACK`**.

### Семантика прапорців PT_GNU_STACK

1. **`Flags = RW` (PF_R | PF_W):** Компілятор та лінкер гарантують, що жоден модуль програми не потребує виконання коду на стеку. Ядро виділяє віртуальну пам'ять для стека процесу з атрибутами `PROT_READ | PROT_WRITE`. У відповідних записах PTE встановлюється біт `NX = 1`.
2. **`Flags = RWE` (PF_R | PF_W | PF_X):** Програма явно вимагає виконуваного стека. Ядро змушене скинути біт NX для області стека (`NX = 0`), роблячи процес вразливим до класичного переповнення буфера.
3. **Заголовок `PT_GNU_STACK` відсутній:** Якщо бінарний файл або хоча б один скомпільований об'єктний файл (`.o`) зібрано застарілим компілятором без інформації про стек, ядро Linux з міркувань зворотної сумісності вмикає виконуваний стек (`READ_IMPLIES_EXEC`).

### Проблема вкладених функцій GCC (Trampolines)

Головною історичною причиною появи виконуваного стека в програмах на C були **вкладені функції** (*nested functions*) — нестандартне розширення компілятора GCC.

Якщо вкладена функція звертається до локальних змінних своєї батьківської функції, компілятору потрібен статичний ланцюжок викликів (*static chain pointer*). Для цього GCC на льоту генерував на стеку крихітний фрагмент машинного коду — **трамплін** (*trampoline*):

```
+──────────────────────────────────────────────────────────────────────────+
|  Стек функції:                                                           |
|  [ Локальні змінні ]                                                     |
|  [ Трамплін GCC: mov %rax, <static_chain>; jmp <nested_func_address> ]   |
|  [ Збережений RBP ]                                                      |
|  [ Адреса повернення ]                                                   |
+──────────────────────────────────────────────────────────────────────────+
```

Коли програма передавала покажчик на вкладену функцію як функцію зворотного виклику (callback), виконання передавалося на цей трамплін, розташований прямо в пам'яті стека. Для роботи такого механізму стек мусив мати права на виконання (`RWX`).

Сучасні версії GCC та Clang вирішили цю проблему за допомогою директиви асемблера `.note.GNU-stack` та переходу на альтернативні механізми передачі контексту (структури замикань або дескриптори функцій), що дозволило збирати 100% сучасного програмного коду з безпечним прапорцем `PT_GNU_STACK (RW)`.

### Захист динамічної купи (Heap NX)

Аналогічний захист діє і для динамічної пам'яті. Системні алокатори glibc (`malloc`, `calloc`, `realloc`) виділяють пам'ять у ядра за допомогою системних викликів `brk()` (збільшення розміру сегмента даних) або `mmap()` з прапорцями `MAP_ANONYMOUS | MAP_PRIVATE`.

В обох випадках ядро за замовчуванням призначає сторінкам купи права `PROT_READ | PROT_WRITE` з активним бітом `NX = 1`. Завдяки цьому зловмисник не може використати техніку *Heap Spraying* (розпилення шелкоду в купі) для прямого виконання коду — спроба стрибка на будь-яку адресу в купі призводить до негайного падіння процесу через `SIGSEGV`.

## 4. Практична демонстрація: апаратне перехоплення спроби стрибка на стек

Щоб побачити дію біта NX на практиці, розглянемо програму, яка розміщує машинний код інструкцій процесора в масиві на стеку, приводить адресу масиву до покажчика на функцію та намагається передати туди керування.

Нижче наведено реалізацію мовами C та C++, де зареєстровано обробник сигналу `SIGSEGV` через системну структуру `sigaction`. Обробник перевіряє код причини збою `si_code` і демонструє апаратне перехоплення спроби виконання стека блоком MMU.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <signal.h>
#include <unistd.h>
#include <ucontext.h>

/* Глобальний прапорець перехоплення апаратного збою */
static volatile sig_atomic_t g_caught_fault = 0;

/* Обробник сигналу сторінкового збою SIGSEGV */
static void segv_handler(int sig, siginfo_t *info, void *ucontext_raw) {
    g_caught_fault = 1;

    printf("\n[!] Апаратне перехоплення MMU: Отримано сигнал SIGSEGV (номер %d)\n", sig);
    printf("    Адреса збою (Faulting Address): %p\n", info->si_addr);

    /* Перевірка коду причини збою:
     * SEGV_ACCERR = 2 (Порушення прав доступу / Access Permissions Fault)
     * SEGV_MAPERR = 1 (Звернення за адресою, не відображеною в пам'ять)
     */
    if (info->si_code == SEGV_ACCERR) {
        printf("    Причина збою (si_code): SEGV_ACCERR (Порушення прав доступу до сторінки)\n");
        printf("    Висновок: Біт NX активний у PTE. Виконання коду зі стека заблоковано апаратно.\n");
    } else {
        printf("    Причина збою (si_code): %d\n", info->si_code);
    }

    /* Безпечний вихід із програми після фіксації перехоплення */
    _exit(EXIT_SUCCESS);
}

int main(void) {
    /* 1. Реєстрація розширеного обробника сигналу SIGSEGV */
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = segv_handler;
    sa.sa_flags = SA_SIGINFO;
    sigemptyset(&sa.sa_mask);

    if (sigaction(SIGSEGV, &sa, NULL) < 0) {
        perror("Помилка встановлення sigaction");
        return EXIT_FAILURE;
    }

    /* 2. Розміщення машинного коду на стеку (локальний масив)
     * Код інструкцій x86-64:
     *   0x90 - NOP (No Operation)
     *   0x90 - NOP
     *   0xC3 - RET (Повернення з функції)
     */
    uint8_t stack_code[] = { 0x90, 0x90, 0xC3 };

    printf("[+] Масив інструкцій розміщено на стеку за адресою: %p\n", (void *)stack_code);
    printf("[+] Спроба передачі керування процесора на стек (Instruction Fetch)...\n");

    /* 3. Приведення покажчика на масив стека до покажчика на функцію */
    typedef void (*func_ptr_t)(void);
    func_ptr_t execute_stack = (func_ptr_t)stack_code;

    /* 4. Спроба виконання: процесор завантажить адресу стека в RIP */
    execute_stack();

    /* Цей рядок ніколи не буде досягнутий, якщо біт NX увімкнено */
    printf("[-] ПОМИЛКА БЕЗПЕКИ: Код на стеку успішно виконався! Біт NX вимкнено.\n");
    return EXIT_FAILURE;
}
```

```cpp
#include <iostream>
#include <cstdint>
#include <cstring>
#include <array>
#include <span>
#include <csignal>
#include <system_error>
#include <unistd.h>

namespace security_demo {

/**
 * @brief Клас керування встановленням та відновленням сигнального обробника (RAII).
 */
class ScopedSignalHandler {
public:
    ScopedSignalHandler(int signum, void (*handler)(int, siginfo_t *, void *))
        : signum_(signum) {
        struct sigaction sa{};
        sa.sa_sigaction = handler;
        sa.sa_flags = SA_SIGINFO;
        ::sigemptyset(&sa.sa_mask);

        if (::sigaction(signum_, &sa, &old_act_) < 0) {
            throw std::system_error(errno, std::generic_category(), "sigaction registration failed");
        }
    }

    ~ScopedSignalHandler() noexcept {
        ::sigaction(signum_, &old_act_, nullptr);
    }

    ScopedSignalHandler(const ScopedSignalHandler &) = delete;
    ScopedSignalHandler &operator=(const ScopedSignalHandler &) = delete;

private:
    int signum_;
    struct sigaction old_act_{};
};

/* Обробник сигналу порушення захисту пам'яті */
void on_segfault(int sig, siginfo_t *info, void *) {
    std::cout << "\n[!] Апаратне перехоплення MMU: Сигнал SIGSEGV (" << sig << ")\n"
              << "    Адреса аварії: " << info->si_addr << "\n";

    if (info->si_code == SEGV_ACCERR) {
        std::cout << "    Код причини: SEGV_ACCERR (Спроба вибірки інструкції зі сторінки NX=1)\n"
                  << "    Результат: Апаратний захист W^X успішно запобіг виконанню стека.\n";
    }

    ::_exit(EXIT_SUCCESS);
}

} // namespace security_demo

int main() {
    try {
        /* Реєстрація RAII-обробника SIGSEGV */
        security_demo::ScopedSignalHandler guard(SIGSEGV, security_demo::on_segfault);

        /* Розміщення байтів машинного коду на стеку (NOP, NOP, RET) */
        alignas(16) std::array<uint8_t, 3> stack_code = { 0x90, 0x90, 0xC3 };

        std::cout << "[+] Стек-буфер розташовано за адресою: "
                  << static_cast<void *>(stack_code.data()) << "\n"
                  << "[+] Виклик функції за адресою стека...\n";

        using ShellcodeFunc = void (*)();
        auto execute_from_stack = reinterpret_cast<ShellcodeFunc>(stack_code.data());

        /* Передача керування: викличе апаратне переривання #PF на сторінці з бітом NX */
        execute_from_stack();

        std::cerr << "[-] КРИТИЧНО: Стек виконуваний! Захист NX відсутній.\n";
        return EXIT_FAILURE;
    } catch (const std::exception &ex) {
        std::cerr << "[-] Помилка: " << ex.what() << "\n";
        return EXIT_FAILURE;
    }
}
```

## 5. Проблема динамічної кодогенерації (JIT) та пастка W^X

Повсюдне впровадження правила W^X створило серйозну архітектурну проблему для рушіїв динамічної компіляції (Just-In-Time, JIT), які використовуються в інтерпретаторах JavaScript (V8 у Chrome та Node.js, JavaScriptCore у WebKit), віртуальних машинах Java (JVM HotSpot), середовищі .NET CLR та емуляторах (QEMU).

JIT-компілятор за своєю природою зобов'язаний виконувати дві дії:
1. **Генерувати код:** Перекладати байткод або абстрактне синтаксичне дерево (AST) у машинний код цільової архітектури і **записувати** ці байти в оперативну пам'ять.
2. **Виконувати код:** Передавати покажчик інструкцій процесора на згенеровані байти для їх прямого **виконання** на швидкості нативного заліза.

### Чому наївне перемикання через mprotect() є небезпечним

Наївне рішення полягає у виділенні буфера пам'яті через `mmap()` та почерговому виклику `mprotect()`: під час компіляції встановлюються права `PROT_READ | PROT_WRITE`, а перед викликом функції — `PROT_READ | PROT_EXEC`.

Цей підхід має дві критичні вади:
1. **Деградація швидкодії:** Системний виклик `mprotect()` вимагає перемикання контексту в простір ядра, взяття глобальних блокувань віртуальної пам'яті процесу (`mmap_lock`) та розсилання міжпроцесорних переривань (IPI) на всі ядра для скидання буфера асоціативної трансляції (TLB Shootdown). Це зводить нанівець переваги JIT-компіляції у високонавантажених сценаріях.
2. **Вікно гонитви (Race Condition / TOCTOU):** У багатопотоковому процесі (наприклад, веб-браузері з десятками Web Workers) права сторінки в таблицях сторінок є спільними для всіх потоків. Якщо потік JIT-компілятора відкриває сторінку на запис (`RW`), будь-який інший потік, скомпрометований через помилку псування пам'яті (Use-After-Free або Out-of-Bounds Write), може в цю ж мікросекунду переписати виконуваний код у JIT-буфері власним шелкодом.

```
Потік 1 (JIT Компілятор):   [ mprotect(RW) ] ───> [ Генерація коду ] ───> [ mprotect(RX) ]
                                    │                                              ▲
                                    ▼                                              │
                            Сторінка відкрита                                      │
                            на запис для всіх потоків!                             │
                                    │                                              │
Потік 2 (Зловмисник):               └───> [ Запис шелкоду в JIT-пам'ять ] ─────────┘
                                          (Підміна легітимного коду без перешкод)
```

### Архітектурне вирішення: подвійний мапінг (Dual Mapping)

Для усунення вікна вразливості та ліквідації накладних витрат на системні виклики застосовується техніка **подвійного відображення** (англ. *Dual Mapping*).

Один і той самий фізичний кадр оперативної пам'яті (Physical Page Frame) відображається у віртуальний адресний простір процесу **двічі** за двома різними віртуальними адресами:
- **Віртуальна адреса запису (`V_write`):** Має статичні права `PROT_READ | PROT_WRITE` (`NX = 1`). Використовується виключно внутрішнім потоком генератора JIT-коду.
- **Віртуальна адреса виконання (`V_exec`):** Має статичні права `PROT_READ | PROT_EXEC` (`NX = 0`, `W = 0`). Використовується для виклику та виконання функцій процесором.

![Архітектура подвійного відображення (Dual Mapping) для JIT-компіляторів](/root/eng/sf-security/no-execute-memory/img/jit-dual-mapping-architecture.svg)
*Архітектура Dual Mapping: дві незалежні віртуальні сторінки над одним спільним фізичним кадром RAM.*

У Linux подвійний мапінг реалізується через створення анонімного файлового дескриптора за допомогою системного виклику `memfd_create("jit_code", MFD_CLOEXEC)` та подвійний виклик `mmap()` із прапорцем `MAP_SHARED` ([детальна інженерна реалізація безпечного JIT-буфера з подвійним мапінгом у C та C++](root:sf-security/no-execute-memory/proj-jit-dual-mapping.md)).

### Апаратні розширення захисту JIT

Сучасні процесори пропонують апаратні інструменти для захисту JIT-буферів без подвійного мапінгу:
- **Apple APRR / SPRR:** На чипах Apple Silicon (M1/M2/M3) регістри керування пам'яттю дозволяють перемикати права виконання та запису для поточного потоку через непривілейовану функцію `pthread_jit_write_protect_np()` усього за 2–3 процесорні такти.
- **Intel Memory Protection Keys (MPK):** Дозволяє призначити сторінці JIT апаратний ключ і керувати доступом на запис через регістр `PKRU` інструкцією `WRPKRU`, блокуючи запис для всіх потоків, крім моменту безпосередньої генерації інструкцій.
- **Windows Arbitrary Code Guard (ACG):** Механізм захисту ядра Windows, що на системному рівні забороняє процесам створювати сторінки `PAGE_EXECUTE_READWRITE` або змінювати наявні сторінки коду на доступні для запису, змушуючи розробників використовувати спеціалізовані позапроцесні JIT-сервери.

## 6. Еволюція атак: від ін'єкції коду до Return-to-libc та ROP

Впровадження біта NX докорінно змінило ландшафт експлуатації бінарних вразливостей. До появи NX переважна більшість експлойтів будувалася за прямолінійною схемою **ін'єкції коду** (*Code Injection*):

```
Вхідні дані експлойту:
[ NOP Sled (0x90 0x90 ...) ] + [ Shellcode (/bin/sh) ] + [ Адреса буфера на стеку ]
```

Коли біт NX унеможливив виконання байтів, розташованих на стеку чи в купі, зловмисники більше не могли змусити процесор виконати свій код. Це змусило спільноту дослідників безпеки перейти від ін'єкції нового коду до концепції **повторного використання наявного коду** (*Code Reuse Attacks*).

### 1. Атака Return-to-libc

Першою відповіддю на захист стека від виконання стала техніка **Return-to-libc**, описана Solar Designer у 1997 році. 

Ідея полягає в тому, що атакована програма вже має завантажену в пам'ять стандартну бібліотеку мови C (`libc.so`), яка містить тисячі скомпільованих функцій. Оскільки сторінки коду `libc` мають легітимні права на виконання (`RX`), біт NX на них не реагує.

Зловмисник через переповнення буфера:
1. Перетирає адресу повернення адресою існуючої функції `system()` усередині `libc`.
2. Розміщує на стеку адресу рядка `"/bin/sh"` (який можна знайти всередині самої `libc` або передати в змінних оточення) так, щоб він виступав першим аргументом функції `system()`.

Під час виходу з функції процесор повертає керування не на стек, а на легітимну функцію `system()`, яка запускає командну оболонку.

```
Стек при атаці Return-to-libc (x86 32-bit):
+──────────────────────────────────────────+
|  Адреса рядка "/bin/sh" (Аргумент 1)     |
|  Фіктивна адреса повернення з system()   |
|  Адреса функції system() у libc (RX)     |  <── Замість адреси повернення функції
|  Збережений EBP                          |
|  Залишок переповненого буфера            |
+──────────────────────────────────────────+
```

### 2. Return-Oriented Programming (ROP)

На 64-розрядних архітектурах (x86-64) угода виклику функцій (System V AMD64 ABI) змінилася: аргументи функцій більше не передаються через стек — перший аргумент повинен знаходитися в регістрі `RDI`, другий — у `RSI`, третій — у `RDX`. Простий виклик `system()` через повернення на стек перестав працювати, оскільки стек не завантажував значення в регістри.

У 2007 році Ованес Шачам (*Hovav Shacham*) опублікував роботу «The Geometry of Innocent Flesh on the Bone», яка формалізувала техніку **Return-Oriented Programming (ROP)**.

Сутність ROP полягає в тому, що будь-яка велика скомпільована кодова база (зокрема `libc`) містить тисячі коротких послідовностей машинних інструкцій, що закінчуються інструкцією `ret` (`0xC3`). Такі послідовності називаються **ґаджетами** (*gadgets*).

Приклади типових ROP-ґаджетів:
- `pop rdi; ret` — знімає значення зі стека і завантажує його в регістр першого аргументу `RDI`.
- `mov [rax], rdx; ret` — записує 64-бітне значення з регістра `RDX` за адресою в `RAX`.
- `xor rax, rax; ret` — занулює регістр `RAX`.

Зловмисник конструює на стеку цілий ланцюжок адрес таких ґаджетів (*ROP Chain*). Кожна інструкція `ret` забирає зі стека адресу наступного ґаджета і стрибає на нього, перетворюючи стек програми на стрічку віртуальної машини, що володіє повнотою за Тюрінгом (*Turing completeness*).

```
Стек з ROP-ланцюжком (x86-64):
+─────────────────────────────────────────────────────────────+
|  Адреса функції system() у libc                             |
|  Адреса рядка "/bin/sh" у пам'яті                           |
|  Адреса ґаджета: pop rdi; ret                               | <── RIP стрибає сюди
|  Збережений RBP                                             |
+─────────────────────────────────────────────────────────────+
```

![Еволюція атак на пам'ять: від Shellcode до ROP](/root/eng/sf-security/no-execute-memory/img/nx-bypass-evolution-rop.svg)
*Еволюційний перехід від виконання чужих байтів у стеку даних до комбінування легітимного коду за допомогою ROP.*

### Комплексний захист: чому одного біта NX недостатньо

Поява технік Return-to-libc та ROP наочно продемонструвала важливе правило безпеки комп'ютерних систем: **жоден окремий бар'єр безпеки не є абсолютним**.

Біт NX повністю закрив клас атак із прямою ін'єкцією коду, проте він не здатний захистити від маніпуляцій з адресами повернення. Для ефективної протидії сучасним експлойтам операційні системи комбінують біт NX з іншими технологіями ешелонованого захисту:
1. **Рандомізація адресного простору (ASLR):** Випадкове зміщення базових адрес бібліотек під час кожного запуску програми позбавляє нападника знання точних адрес ґаджетів у `libc` ([детальніше про ASLR](root:sf-security/aslr)).
2. **Канарейки стека (Stack Canaries):** Спеціальні випадкові значення перед збереженим `RBP`, пошкодження яких сигналізує про переповнення буфера до виконання інструкції `ret` ([детальніше про переповнення буфера](root:sf-security/buffer-overflow-security)).
3. **Апаратний тіньовий стек (Intel CET / Shadow Stack):** Процесор дублює адреси повернення в ізольованому апаратному стеку, недоступному для запису звичайними інструкціями, що повністю блокує зміну адрес у ROP-ланцюжках.
4. **Цілісність потоку керування (Control-Flow Integrity / CFI):** Апаратна та програмна перевірка легітимності переходів непрямих викликів і стрибків ([детальніше про CFI](root:sf-security/control-flow-integrity)).
5. **Механізми Jump-Oriented Programming (JOP) та розширення BROP:** Подальша еволюція атак довела, що зловмисники можуть обходити навіть інструкції `ret`, використовуючи ґаджети, що закінчуються непрямими стрибками `jmp [reg]` або викликами `call [reg]`, що вимагає апаратного маркування допустимих цілей переходу за допомогою інструкцій `ENDBR64` (Intel IBT) або `BTI` (ARM Branch Target Identification).

> 🔧 **Навіщо це.**
> 
> У реальній системній розробці та аудиті безпеки дотримання правил W^X та контроль біта NX перевіряються щодня:
> 
> 1. **Перевірка бінарних файлів за допомогою `checksec`:**
>    Утиліта `checksec` миттєво показує стан захисту скомпільованого бінарника:
>    ```bash
>    checksec --file=/usr/bin/nginx
>    # RELRO           STACK CANARY      NX            PIE             RPATH
>    # Full RELRO      Canary found      NX enabled    PIE enabled     No RPATH
>    ```
>    Якщо в стовпчику `NX` зазначено `NX disabled`, бінарний файл зібрано з виконуваним стеком (прапорець `gcc -z execstack`), що є критичним дефектом конфігурації збірки.
> 
> 2. **Аудит карти пам'яті процесу в `/proc/[pid]/maps`:**
>    Системні інженери та засоби виявлення вторгнень (EDR) шукають небезпечні області `RWX` в активних процесах:
>    ```bash
>    grep "rwx" /proc/$(pgrep node)/maps
>    ```
>    Поява рядків з правами `rwxp` свідчить про те, що застосунок виділив пам'ять із порушенням W^X (наприклад, через некоректно налаштований JIT-рушій або сторонню плагін-бібліотеку), створивши плацдарм для експлуатації.
> 
> 3. **Монтування тимчасових каталогів з опцією `noexec`:**
>    Відповідно до вимог стандартів безпеки (CIS Benchmarks, PCI-DSS), каталоги спільного доступу на запис (`/tmp`, `/var/tmp`, `/dev/shm`) обов'язково монтуються в системі з прапорцем `noexec`:
>    ```bash
>    mount -o remount,noexec,nosuid,nodev /tmp
>    ```
>    Це блокує завантаження та виконання бінарних файлів зловмисниками навіть у разі отримання несанкціонованого доступу на збереження файлів у файлову систему.
