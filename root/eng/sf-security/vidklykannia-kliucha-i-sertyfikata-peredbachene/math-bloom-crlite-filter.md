# 🧮 Математична модель каскадних фільтрів Блума в системі CRLite

Традиційні списки відкликання (CRL) вимагають передачі повного переліку серійних номерів відкликаних сертифікатів (від лат. *certus* — певний + *facere* — робити), що призводить до лінійного зростання обсягу даних `O(N)`. Якщо зберегти кожен серійний номер як 16-байтне число, то для бази з 50 мільйонів відкликаних сертифікатів знадобиться щонайменше 800 мегабайтів пам'яті, що виключає можливість їхнього завантаження у вбудовані системи та шлюзи.

Архітектура **CRLite** вирішує це завдання за допомогою каскадної структури фільтрів Блума (Cascaded Bloom Filters), стискаючи інформацію про статус до кількох бітів на один сертифікат з **абсолютною математичною гарантією нульової ймовірності помилки** (нуль хибнопозитивних і нуль хибнонегативних результатів).

---

## 1. Інформаційно-теоретична границя та модель фільтра Блума

З погляду теорії інформації Клода Шеннона, завдання перевірки належності елемента до множини (Set Membership Problem) з допустимою ймовірністю хибного спрацьовування `p_fp` має фундаментальну теоретичну нижню границю обсягу пам'яті на один елемент:

```
bits_min = log₂(1 / p_fp) = - log₂(p_fp)
```

Класичний фільтр Блума (Bloom Filter), запропонований Бертоном Блумом у 1970 році, є компактною ймовірнісною структурою даних. Він складається з бітового масиву розміром `m` бітів, спочатку заповненого нулями, та набору з `k` незалежних геш-функцій `h₁, h₂, ..., hₖ`, кожна з яких відображає серійний номер сертифіката `x` у рівномірно розподілений індекс масиву `[0, m - 1]`.

Під час додавання елемента `x` установлюються біти:

```
A[h₁(x)] = 1,  A[h₂(x)] = 1,  ...,  A[hₖ(x)] = 1
```

Під час перевірки елемент вважається присутнім у множині тоді й лише тоді, коли всі `k` бітів за відповідними адресами дорівнюють одиниці. Якщо хоча б один біт дорівнює нулю, елемент гарантовано відсутній у множині (відсутність хибнонегативних помилок).

### 1.1. Виведення ймовірності хибнопозитивного спрацьовування та техніка подвійного гешування

У класичній схемі обчислення `k` незалежних геш-функцій вимагало б значних обчислювальних витрат процесора. На практиці в алгоритмах CRLite застосовується теорема Кірша-Мітценмахера (Kirsch-Mitzenmacher Optimization): для генерації `k` псевдонезалежних індексів достатньо обчислити лише дві базові 64-бітні геш-функції `h_a(x)` та `h_b(x)` (наприклад, за допомогою швидких алгоритмів MurmurHash3 або xxHash):

```
h_i(x) = (h_a(x) + i · h_b(x)) mod m
```

Ця техніка забезпечує ту саму асимптотичну ймовірність хибнопозитивного спрацьовування `p_fp`, що й `k` повністю незалежних криптографічних геш-функцій, скорочуючи кількість звернень до криптоядра до двох операцій.

Нехай у фільтр розміром `m` бітів додано `n` елементів за допомогою `k` геш-функцій.

Ймовірність того, що конкретний біт залишиться нулем після встановлення одного хешу одним елементом:

```
p_zero_single = 1 - 1/m
```

Ймовірність того, що біт залишиться нулем після додавання всіх `n` елементів, кожен з яких встановлює `k` бітів:

```
p_zero_total
= (1 - 1/m)^(k·n)
≈ e^(-k·n/m)                           [наближення границі другого чудового виразу при m >> 1]
```

Відповідно, ймовірність того, що випадковий біт бітового масиву дорівнює одиниці (фактична щільність заповнення фільтра):

```
p_one = 1 - e^(-k·n/m)
```

Ймовірність хибнопозитивного спрацьовування `p_fp` (ситуація, коли випадковий сторонній елемент, якого ніколи не додавали до множини, має всі `k` бітів у стані `1`):

```
p_fp = (1 - e^(-k·n/m))^k
```

### 1.2. Оптимальна кількість геш-функцій та питомий бюджет бітів

Для мінімізації функції `p_fp` при фіксованому відношенні розміру масиву до кількості елементів `(m/n)` знайдемо екстремум, продиференціювавши логарифм виразу за параметром `k`:

```
k_opt
= (m/n) · ln(2)                        [диференціювання ln(p_fp) за k і прирівняння до нуля]
≈ 0.693 · (m/n)                        [значення натурального логарифма ln(2) ≈ 0.693]
```

Підставивши `k_opt` у формулу ймовірності помилки, отримуємо фундаментальний зв'язок між питомим розміром пам'яті `(m/n)` та ймовірністю хибного спрацьовування:

```
p_fp
= (1 - e^(-((m/n)·ln(2))·n/m))^k_opt   [підстановка оптимального k_opt = (m/n)·ln(2)]
= (1 - e^(-ln(2)))^k_opt               [скорочення добутку (m/n)·(n/m) = 1 у показнику]
= (1 - 1/2)^((m/n)·ln(2))              [тотожність експоненти: e^(-ln 2) = 1/2]
= (1/2)^((m/n)·ln(2))                  [арифметика дробів: 1 - 1/2 = 1/2]
= 2^(-(m/n)·ln(2))                     [властивість від'ємного степеня: (1/2)^x = 2^(-x)]
```

Логарифмуючи обидві частини рівності за основою 2, отримуємо необхідну кількість бітів пам'яті на один елемент:

```
m/n
= - log₂(p_fp) / ln(2)                 [логарифмування виразу за основою 2]
≈ - 1.4427 · log₂(p_fp)                [константа переходу: 1/ln(2) ≈ 1.4427]
```

Коефіцієнт `1.4427` показує, що класичний фільтр Блума витрачає на 44% більше пам'яті порівняно з теоретичною інформаційною границею Шеннона через випадкові колізії бітів.

## 2. Математика каскадування в системі CRLite

Одинарний фільтр Блума має ненульову ймовірність помилки `p_fp > 0`. Якщо фільтр повертає `Revoked` для легітимного чинного сертифіката (хибне спрацьовування), клієнтський пристрій безпідставно розірве з'єднання з довіреним хмарним сервером.

CRLite усуває цю проблему за допомогою рекурсивної побудови каскаду шарів `L₀, L₁, L₂, ...`. Оскільки всі дійсні сертифікати відомі заздалегідь завдяки відкритим логам Certificate Transparency (CT Logs), алгоритм може детерміновано виправити всі помилки на етапі побудови.

### 2.1. Алгоритм розбиття множин за шарами

Нехай:
- `R` — множина всіх реально відкликаних сертифікатів (Revoked).
- `V` — множина всіх відомих чинних сертифікатів (Valid), отриманих з логів CT.

```
Крок 0 (Шар L₀ — первинна фільтрація відкликаних):
    Фільтр F₀ будується на множині R.
    Параметр m₀/|R| обирається так, щоб p₀ ≈ 0.5 (тобто k = 1 і m₀/|R| ≈ 1.44 біта на елемент).
    Хибнопозитивні: частина валідних сертифікатів V помилково позначається як відкликані:
    V₀ = { v ∈ V | F₀(v) == 1 }   =>   |V₀| ≈ 0.5 · |V|

Крок 1 (Шар L₁ — фільтр виправлення валідних):
    Фільтр F₁ будується ВИКЛЮЧНО на множині помилок V₀.
    Параметр m₁/|V₀| обирається так, щоб p₁ ≈ 0.5.
    Хибнопозитивні: частина відкликаних сертифікатів R помилково потрапляє у винятки:
    R₁ = { r ∈ R | F₁(r) == 1 }   =>   |R₁| ≈ 0.5 · |R|

Крок 2 (Шар L₂ — фільтр корекції відкликаних):
    Фільтр F₂ будується на множині помилок R₁.
    V₂ = { v ∈ V₀ | F₂(v) == 1 }  =>   |V₂| ≈ 0.5 · |V₀| ≈ 0.25 · |V|

...
Крок i (Термінальний шар):
    Оскільки потужність множини помилок на кожному кроці зменшується вдвічі (|S_{i+1}| ≈ 0.5·|S_i|),
    послідовність є строго спадною і процес зупиняється на кроці t, коли залишок стає порожнім:
    |R_t| = 0   або   |V_t| = 0
```

### 2.2. Дерево рішень під час перевірки сертифіката `x`

Процес перевірки сертифіката виконується послідовним опитуванням бітових масивів від шару 0 до термінального шару:

```
Вхід: Серійний номер сертифіката x

F₀(x) == 0 ?
├── ТАК  --> СТАТУС: VALID (не потрапив у первинний фільтр відкликаних)
└── НІ   --> Перевірка шару F₁(x) == 0 ?
            ├── ТАК  --> СТАТУС: REVOKED (відкликаний і не потрапив у список винятків)
            └── НІ   --> Перевірка шару F₂(x) == 0 ?
                        ├── ТАК  --> СТАТУС: VALID (корекція винятку)
                        └── НІ   --> ... перехід до наступного шару каскаду
```

Кількість обчислень гешів для будь-якого сертифіката є строго обмеженою кількістю шарів каскаду `t`, де `t <= 10` навіть для баз у сотні мільйонів записів.

## 3. Обчислення загального бюджету пам'яті

Обчислимо сумарну кількість бітів `M_total`, необхідну для представлення `|R|` відкликаних сертифікатів за умови фіксованої ймовірності переходу між шарами `p = 0.5`:

```
M_total
= m₀ + m₁ + m₂ + m₃ + ...                                                      [сума розмірів бітових масивів усіх шарів]
= 1.44·|R| + 1.44·|V₀| + 1.44·|R₁| + 1.44·|V₂| + ...                          [підстановка m_i = 1.44·n_i для p = 0.5]
= 1.44 · [ |R|·(1 + 0.5 + 0.25 + ...) + |V|·(0.5 + 0.25 + 0.125 + ...) ]      [групування за спадними частками множин]
```

Оскільки сума нескінченної спадної геометричної прогресії:

```
∑ (0.5)^i
= 1 / (1 - 0.5)                        [формула суми геометричного ряду: S = a / (1 - q)]
= 2                                    [обчислення знаменника: 1 / 0.5 = 2]
```

Завдяки попередній оптимізації та виключенню надлишкових сертифікатів середнє значення питомої ваги у реальних розгортаннях CRLite становить:

```
Cost_per_cert ≈ 3.2 ... 4.1 біта на один відкликаний сертифікат
```

### 3.1. Практичний числовий приклад розрахунку для IoT-шлюзу

**Вхідні дані**: База містить `|R| = 2 000 000` відкликаних сертифікатів та `|V| = 50 000 000` активних чинних сертифікатів глобального пулу довіри.

1. **Класичний CRL без стиснення**:
   Зберігання 16-байтних серійних номерів у вигляді масиву:
   `Size_CRL = 2 000 000 · 16 = 32 000 000 байтів ≈ 30.5 МБ`.
2. **Каскадний фільтр CRLite**:
   При питомому бюджеті 3.6 біта на запис:
   `Size_CRLite = (2 000 000 · 3.6) / 8 = 900 000 байтів ≈ 878 КБ`.

**Висновок**: Каскадна фільтрація забезпечує коефіцієнт стиснення **понад 35 разів**, зменшуючи розмір бази до менш ніж 1 мегабайта. Це дозволяє вбудованим шлюзам та мікроконтролерам виконувати миттєву автономну верифікацію сертифікатів за константний час `O(1)` без виходу в мережу і з нульовим ризиком блокування дійсних пристроїв.
