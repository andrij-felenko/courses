# Реалізація моделі майстер-воркер у простому сервері

## Запуск привілейованого майстер-процесу та відкриття сокетів

Багатопроцесорні сервери (такі як NGINX чи OpenSSH) використовують модель розділення привілеїв (@@en|Privilege Separation@@) для безпечної обробки мережевого трафіку. Системне правило ОС Linux вимагає прав привілейованого користувача `root` (UID 0) для прив'язки слухаючих сокетів до привілейованих мережевих портів з номерами менше 1024 (наприклад, порт 80 для HTTP або порт 443 для HTTPS). Окрім того, лише привілейований процес здатний зчитувати приватні криптографічні ключі TLS із захищених системних директорій `/etc/ssl/private`.

Ініціалізація починається із запуску єдиного привілейованого майстер-процесу. Майстер виступає в ролі роду довіри системи: він зчитує файл конфігурації, створює слухаючий TCP-сокет за допомогою системних викликів `socket()`, `bind()` та `listen()`, після чого зберігає отриманий дескриптор сокета `listen_fd` у своїй пам'яті. Для підвищення масштабованості на сучасних багатоядерних системах застосовується опція сокета `SO_REUSEPORT` через `setsockopt()`. Вона дозволяє декільком робочим процесам відкривати окремі слухаючі сокети на тому самому порту, при цьому ядро Linux автоматично розподіляє вхідні з'єднання між воркерами за допомогою хешування 4-кортежу IP/портів, усуваючи взаємне блокування та проблему "будячої зграї" (@@en|thundering herd problem@@). Жодної обробки запитів від зовнішніх клієнтів майстер не виконує — це захищає привілейований контекст від атак через мережу.

## Створення воркерів та пониження привілеїв (setuid/setgid)

Після підготовки мережевих портів та завантаження секретів майстер-процес породжує непривілейовані робочі процеси (@@en|workers@@). За допомогою системного виклику `fork()` майстер створює потрібну кількість дитячих процесів. Одразу після розгалуження кожен воркер виконує процедуру незворотного скидання привілеїв до рівня непривілейованого користувача (наприклад, `nobody` або спеціалізованого облікового запису `www-data`).

Зміна привілеїв виконується послідовним викликом `setgid()` (зміна ідентифікатора групи) та `setuid()` (зміна ідентифікатора користувача). Порядок викликів має вирішальне значення: спочатку скидається група, оскільки після відмови від UID 0 виклик `setgid()` стане неможливим. Додатково застосовується системний виклик `chroot()` для ізоляції файлової системи воркера в порожній директорії (@@en|chroot jail@@).

:::code proj-nginx-worker-model/c/passwd.c

Перед зниженням привілеїв критично важливо очистити масив змінних оточення `environ` (за допомогою `clearenv()`) та закрити всі відведені майстром файлові дескриптори, які не потрібні воркеру для виконання його безпосередніх обов'язків. Якщо не закрити відкриті конфігураційні файли або приватні ключі SSL до виклику `setuid()`, то навіть після скидання привілеїв до `nobody` воркер зберігатиме доступ до цих успадкованих файлових дескрипторів, що знівелює переваги ізоляції.

## Організація IPC між майстром та воркерами

Для управління життєвим циклом воркерів та перерозподілу мережевих з'єднань між ними майстер налаштовує міжпроцесні канали зв'язку на основі `socketpair()`. До запуску `fork()` майстер створює дуплексний сокетний канал, після чого передає один із дескрипторів воркеру.

Майстер-процес входить у безкінечний цикл моніторингу, де він очікує сигналів завершення або перезапуску конфігурації (`SIGHUP`, `SIGCHLD`). Якщо один із воркерів зазнає збою (наприклад, через критичну помилку в коді парсингу HTTP-пакетів), майстер отримує сигнал `SIGCHLD`, зчитує код завершення та негайно запускає новий непривілейований воркер.

Така архітектура гарантує, що навіть у разі компрометації воркера через мережевий експлойт зловмисник опиниться в ізольованому непривілейованому середовищі без доступних системних ресурсів чи приватних ключів.
