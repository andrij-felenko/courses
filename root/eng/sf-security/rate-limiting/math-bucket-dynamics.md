# 🧮 Математична динаміка накопичувачів маркерів та віконних алгоритмів

Ця математична вставка містить строгі аналітичні виведення рівнянь динаміки поповнення та витрати маркерів, оцінки максимальної тривалості сплесків, розрахунку затримок у чергах Leaky Bucket, доведення ізоморфізму між Generic Cell Rate Algorithm (GCRA) та Token Bucket, а також оцінки похибки зваженого ковзного вікна. Ці виведення потрібні інженерам для точного розрахунку параметрів місткості буферів і частоти поповнення під задані угоди про рівень обслуговування (SLA).

---

## 1. Неперервна динаміка накопичувача маркерів (Token Bucket)

Нехай система обмеження швидкості на базі накопичувача маркерів має такі параметри:
- `C` (маркерів) — максимальна місткість накопичувача (англ. *capacity* або *burst size*).
- `r` (маркерів/секунду) — швидкість неперервного поповнення накопичувача (англ. *refill rate*).
- `T(t)` — кількість доступних маркерів у момент часу `t`.

### Рівняння поповнення за відсутності споживання

Якщо в інтервалі `[t₀, t]` споживання маркерів не відбувається, кількість маркерів зростає лінійно з насиченням на рівні `C`:

```
T(t) = min(C, T(t₀) + r · (t - t₀))
```

де `t - t₀ = Δt` — тривалість інтервалу спокою.

### Поглинання пікового сплеску трафіку (Burst Dynamics)

Припустимо, що в момент `t = 0` накопичувач повністю заповнений: `T(0) = C`. Клієнт починає надсилати запити з постійною інтенсивністю `R_in` (запитів/с), причому `R_in > r` (вхідна швидкість перевищує швидкість поповнення). Кожен запит споживає рівно `1` токен.

Швидкість зміни кількості токенів у накопичувачі становить:

```
dT/dt = r - R_in    [оскільки R_in > r, похідна є від'ємною]
```

Інтегруючи за часом від `0` до моменту вичерпання `t_burst`, коли `T(t_burst) = 0`:

```
0 = C + (r - R_in) · t_burst      [гранична умова: T(t_burst) = 0]
(R_in - r) · t_burst = C           [перенесення доданка в ліву частину]
t_burst = C / (R_in - r)           [ділення на (R_in - r)]
```

**Висновок:** тривалість допустимого безперервного пікового навантаження `t_burst` обернено пропорційна різниці між вхідною швидкістю `R_in` та стабільною швидкістю `r`.

### Сумарний обсяг пропущених запитів за час сплеску

Загальна кількість запитів `V_burst`, успішно пропущених системою за час `t_burst`, дорівнює добутку вхідної швидкості на тривалість сплеску:

```
V_burst = R_in · t_burst                   [визначення сумарного обсягу]
        = R_in · (C / (R_in - r))          [підстановка виразу для t_burst]
        = C + r · t_burst                  [розкриття через баланс токенів]
```

**Приклад розрахунку:**
Нехай `C = 100` токенів, `r = 20` токенів/с, а вхідний потік становить `R_in = 120` запитів/с:

```
t_burst = 100 / (120 - 20) = 100 / 100 = 1.0 с
V_burst = 120 · 1.0 = 120 запитів
```

Система дозволить клієнту виконати 120 запитів за першу секунду, після чого його пропускна здатність буде жорстко обмежена швидкістю `r = 20` запитів/с.

## 2. Затримка та розмір черги в алгоритмі Leaky Bucket

На відміну від Token Bucket, що скидає надлишкові запити негайно (Traffic Policing), Leaky Bucket із буфером затримує запити в черзі FIFO (Traffic Shaping).

Параметри:
- `B` — максимальна місткість черги очікування (запитів).
- `r_leak` — постійна швидкість обробки запитів із черги (запитів/с).
- `Q(t)` — поточна кількість запитів у черзі в момент `t`.

### Динаміка черги

Швидкість зміни довжини черги при вхідному потоці `R_in(t)`:

```
dQ/dt = R_in(t) - r_leak    (при Q(t) > 0)
```

За умови надходження миттєвого пакунку з `N` запитів (`N ≤ B`), запити стають у чергу. Час перебування `W_k` для `k`-го запиту в черзі становить:

```
W_k = k / r_leak    [де k ∈ {1, 2, ..., N}]
```

Максимальний час затримки (найгірший час відгуку для останнього запиту в повній черзі):

```
W_max = B / r_leak
```

### Зв'язок із законом Літтла (Little's Law)

Згідно із законом Літтла, середня кількість запитів у стаціонарній системі `L` дорівнює добутку середньої інтенсивності вхідного потоку `λ` на середній час перебування запиту в системі `W`:

```
L = λ · W
```

Для повністю завантаженого Leaky Bucket із чергою:

```
B = r_leak · W_max
W_max = B / r_leak
```

Якщо `W_max` перевищує допустимий клієнтський HTTP-таймаут (наприклад, `5.0` секунд), місткість черги `B` необхідно зменшити, щоб не утримувати «мертві» запити, відповіді на які клієнт уже не чекає.

## 3. Математичний ізоморфізм GCRA та Token Bucket

Generic Cell Rate Algorithm (GCRA) моделює роботу накопичувача без збереження лічильника токенів за допомогою єдиної часової мітки — **теоретичного часу прибуття** `TAT` (англ. *Theoretical Arrival Time*).

Параметри GCRA:
- `T` — інтервал випромінювання (англ. *emission interval*): мінімальний інтервал між запитами при стабільній швидкості. Зв'язок зі швидкістю `r`: `T = 1 / r`.
- `τ` (tau) — допуск сплеску (англ. *limit tolerance* / *burst tolerance*).

### Різницеві рівняння GCRA

Нехай черговий запит надходить у фізичний момент часу `t_arr`.
Алгоритм приймає рішення за правилом:

```
1. Розрахунок границі допуску:
   t_earliest = TAT_prev - τ

2. Перевірка відповідності:
   Якщо t_arr < t_earliest:
       РІШЕННЯ = REJECT (відхилити запит, TAT_next = TAT_prev)
   Інакше:
       РІШЕННЯ = ACCEPT (прийняти запит)
       TAT_next = max(t_arr, TAT_prev) + T
```

### Доведення еквівалентності параметрів

Доведемо, що GCRA з параметрами `(T, τ)` еквівалентний Token Bucket з місткістю `C` та швидкістю `r = 1 / T`.

Нехай у момент `t = 0` система перебуває у стані спокою: `TAT = 0`.
Припустимо, що в момент `t = 0` надходить пачка з `K` миттєвих запитів.

Для кожного успішно прийнятого `k`-го запиту (`k = 1, 2, ..., K`):

```
TAT_k = TAT_{k-1} + T = k · T
```

Умова допуску для `K`-го запиту:

```
t_arr ≥ TAT_{K-1} - τ
0 ≥ (K - 1) · T - τ
(K - 1) · T ≤ τ
K - 1 ≤ τ / T
K ≤ (τ / T) + 1
```

Максимальна кількість запитів `K_max`, яку система здатна пропустити миттєво (розмір сплеску `C`):

```
C = ⌊τ / T⌋ + 1
```

Звідси виражаємо часовий допуск `τ` через місткість `C`:

```
τ = (C - 1) · T = (C - 1) / r
```

**Висновок:** збереження одного 64-бітного цілого числа `TAT` повністю замінює необхідність зберігати два окремі поля `(tokens, last_refill_timestamp)`.

## 4. Оцінка похибки алгоритму Sliding Window Counter

Алгоритм зваженого ковзного лічильника обчислює кількість запитів за останні `W` секунд без збереження окремих часових міток кожного запиту.

Час розбивається на дискретні вікна фіксованої довжини `W`.
Нехай:
- `N_prev` — точна кількість запитів у попередньому вікні `[t_win - W, t_win)`.
- `N_curr` — кількість запитів, зафіксованих у поточному вікні `[t_win, t_now]`.
- `t_offset = t_now - t_win` — час, що минув від початку поточного вікна (`0 ≤ t_offset < W`).

Ковзна оцінка кількості запитів `N_est` розраховується як зважена лінійна інтерполяція:

```
вага попереднього вікна: w = (W - t_offset) / W = 1 - (t_offset / W)
N_est = N_prev · w + N_curr
```

### Аналіз максимальної похибки

Припустимо, що в попередньому вікні всі `N_prev` запитів надійшли в найпершу секунду вікна, а в решту часу трафіку не було.
Тоді на момент `t_now` (коли `t_offset > 0`) реальна кількість запитів за останні `W` секунд становить рівно `N_curr`, оскільки всі запити попереднього вікна вже застаріли (вийшли за межі 60-секундного інтервалу).

Проте формула лінійної інтерполяції оцінить їх як:

```
N_est = N_prev · (1 - t_offset / W) + N_curr > N_curr
```

Абсолютна похибка оцінки:

```
ΔN = N_est - N_real = N_prev · (1 - t_offset / W)
```

Відносна похибка в найгіршому теоретичному випадку досягає `1 - t_offset / W`. Проте на практиці мережевий трафік розподілений більш рівномірно. За даними аналізу інженерів Cloudflare, для пуассонівського розподілу трафіку середня квадратична похибка алгоритму не перевищує **0.05%** від встановленого ліміту.

## 5. Порівняльний аналіз складності алгоритмів

Нижче наведено таблицю обчислювальної складності (Time Complexity) та витрат пам'яті (Space Complexity) на одного відстежуваного клієнта:

```
┌─────────────────────────┬──────────────┬──────────────┬──────────────────────────────┐
│ Алгоритм                │ Час перевірки│ Пам'ять (RAM)│ Обробка сплесків (Burst)     │
├─────────────────────────┼──────────────┼──────────────┼──────────────────────────────┤
│ Fixed Window Counter    │ O(1)         │ 8 байтів     │ Подвійний сплеск на межі 2×  │
│ Sliding Window Log      │ O(log N + M) │ O(N) байтів  │ Ідеальна строга точність     │
│ Sliding Window Counter  │ O(1)         │ 16 байтів    │ Згладжена (похибка < 1%)     │
│ Token Bucket            │ O(1)         │ 16 байтів    │ Допускає сплеск розміром C   │
│ Leaky Bucket (Queue)    │ O(1)         │ O(B) байтів  │ Перетворює сплеск у чергу    │
│ GCRA (Virtual Schedule) │ O(1)         │ 8 байтів     │ Еквівалентно Token Bucket    │
└─────────────────────────┴──────────────┴──────────────┴──────────────────────────────┘
```

де:
- `N` — кількість запитів клієнта за поточне вікно.
- `M` — кількість видалених застарілих запитів.
- `B` — місткість черги очікування.
