# 📋 Протокольні заголовки HTTP RateLimit та Redis Lua контракти

Ця довідкова вставка містить вичерпний опис протокольних інтерфейсів передачі стану обмеження швидкості між сервером та клієнтом: специфікацію коду відповіді HTTP 429, сучасні стандартизовані заголовки IETF Draft, застарілі legacy-заголовки, формат JSON-помилок RFC 7807, правила клієнтської обробки експоненційного відступу з джитером, конфігураційні директиви проксі-серверів, а також повний інтерфейсний контракт і код атомарного Redis Lua-скрипта для розподіленого Token Bucket. Вона слугує еталонним довідником для розробників API, системних архітекторів та інженерів інфраструктури.

## 1. Код стану HTTP: 429 Too Many Requests

Код стану **429 Too Many Requests** стандартизовано в **RFC 6585** (*Additional HTTP Status Codes*).

```http
HTTP/1.1 429 Too Many Requests
Date: Thu, 20 Aug 2026 18:30:00 GMT
Content-Type: application/problem+json
Content-Length: 328
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
RateLimit-Policy: 100;w=60
```

Семантичні вимоги стандарту:
- Сервер повідомляє клієнту, що той перевищив дозволену кількість запитів за визначений період часу.
- Сервер **не повинен** виконувати бізнес-логіку запиту (запит відхиляється на рівні шлюзу чи проміжного ПЗ до звернення до бази даних чи бізнес-сервісів).
- Відповідь **повинна** містити чіткі інструкції про те, коли саме клієнт може безпечно повторити спробу (через заголовок `Retry-After`).
- Код 429 не є фатальною системною помилкою сервера (як 500 Internal Server Error чи 503 Service Unavailable), а вказує на тимчасове вичерпання квоти клієнтом.

## 2. Стандартні заголовки IETF Draft RateLimit

Робоча група IETF HTTPAPI стандартизує єдиний набір полів заголовків для усунення фрагментації нестандартних префіксів `X-`:

| Заголовок | Тип даних | Опис | Приклад |
|---|---|---|---|
| `RateLimit-Limit` | `Integer` або `List` | Загальна квота запитів за поточне вікно політики | `RateLimit-Limit: 100` |
| `RateLimit-Remaining` | `Integer` | Кількість невикористаних запитів у межах поточної квоти | `RateLimit-Remaining: 15` |
| `RateLimit-Reset` | `Integer` | Кількість секунд до повного скидання/поповнення квоти | `RateLimit-Reset: 45` |
| `RateLimit-Policy` | `String` | Опис застосованої політики (квота, тривалість вікна `w` у секундах) | `RateLimit-Policy: 100;w=60` |

### Заголовок `Retry-After` (RFC 9110)

Вказує клієнту мінімальний час очікування перед надсиланням наступного запиту:
1. **Дельта в секундах (рекомендований варіант для API):**
   ```http
   Retry-After: 60
   ```
2. **Абсолютна дата у форматі HTTP-date (GMT):**
   ```http
   Retry-After: Thu, 20 Aug 2026 18:31:00 GMT
   ```

## 3. Де-факто застарілі заголовки (Legacy X-RateLimit)

До появи чернетки IETF більшість вебсервісів використовували заголовки з префіксом `X-`. Їхня підтримка необхідна для збереження зворотної сумісності з наявними клієнтськими SDK:

| Заголовок | Формат | Опис | Провайдери |
|---|---|---|---|
| `X-RateLimit-Limit` | Число | Максимальна квота запитів | GitHub, Twitter, Stripe |
| `X-RateLimit-Remaining` | Число | Кількість залишкових запитів | GitHub, Twitter, Stripe |
| `X-RateLimit-Reset` | Unix Epoch (сек) або секунди | Час скидання (Unix Timestamp у секундах) | GitHub, Twitter |
| `X-RateLimit-Reset-After` | Число (секунди) | Кількість секунд до скидання | Discord, Cloudflare |

## 4. Специфікація тіла помилки (RFC 7807 Problem Details)

Тіло відповіді HTTP 429 формується у форматі `application/problem+json` для автоматизованого машинно-зчитуваного парсингу клієнтськими бібліотеками:

```json
{
  "type": "https://api.example.com/errors/rate-limit-exceeded",
  "title": "Too Many Requests",
  "status": 429,
  "detail": "Квоту в 100 запитів на хвилину вичерпано для вашого API-ключа.",
  "instance": "/v1/payments/charge/req_98a7b1c",
  "retry_after_seconds": 30,
  "limit": 100,
  "remaining": 0,
  "reset_at": "2026-08-20T18:30:30Z"
}
```

## 5. Контракт Redis Lua-скрипта для розподіленого Token Bucket

Для забезпечення атомарності операції перевірки та списання токенів у кластерному середовищі використовується вбудований інтерпретатор Lua у Redis. Це запобігає стану гонки (Race Condition / TOCTOU) між незалежними вузлами API Gateway.

### Сигнатура виклику через EVALSHA

```
EVALSHA <sha1_hash> 1 <rate_limit_key> <capacity> <refill_rate> <cost> <now_timestamp_sec>
```

Параметри виклику:
- `KEYS[1]` — ключ стану клієнта в Redis (наприклад, `rate:user_12345` або `rate:ip:203.0.113.19`).
- `ARGV[1]` — `capacity` (максимальна місткість відра, токенів).
- `ARGV[2]` — `refill_rate` (швидкість поповнення, токенів на секунду).
- `ARGV[3]` — `cost` (кількість токенів, необхідна для поточного запиту, зазвичай 1).
- `ARGV[4]` — `now` (поточний час у секундах із плаваючою комою, передається клієнтом для усунення різниці внутрішніх таймерів Redis).

### Код Lua-скрипта

```lua
-- Отримання вхідних аргументів
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local now = tonumber(ARGV[4])

-- Зчитування поточного стану з Redis Hash
local data = redis.call("HMGET", key, "tokens", "last_updated")
local tokens = tonumber(data[1])
local last_updated = tonumber(data[2])

if tokens == nil then
    -- Перший запит: відро повністю заповнене
    tokens = capacity
    last_updated = now
else
    -- Обчислення лінивого поповнення токенів
    local elapsed = math.max(0, now - last_updated)
    tokens = math.min(capacity, tokens + elapsed * refill_rate)
    last_updated = now
end

local allowed = 0
local remaining = tokens
local retry_after = 0

if tokens >= cost then
    -- Запит дозволено
    allowed = 1
    tokens = tokens - cost
    remaining = tokens
else
    -- Запит відхилено: розрахунок часу очікування до накопичення необхідних токенів
    allowed = 0
    local needed = cost - tokens
    retry_after = math.ceil(needed / refill_rate)
end

-- Збереження оновленого стану
redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)

-- Встановлення TTL: час до повного поповнення порожнього відра + запас 60 с
local ttl = math.ceil(capacity / refill_rate) + 60
redis.call("EXPIRE", key, ttl)

-- Повернення масиву результату: [allowed (1 або 0), remaining_tokens, retry_after_sec]
return { allowed, math.floor(remaining), retry_after }
```

### Формат поверненого результату

Lua-скрипт повертає триелементний масив `[allowed, remaining, retry_after]`:
1. `allowed` (`1` — пропустити запит; `0` — повернути HTTP 429).
2. `remaining` — залишок доступних токенів (значення для `RateLimit-Remaining`).
3. `retry_after` — кількість секунд очікування (значення для `Retry-After`).

## 6. Клієнтський контракт: Експоненційний відступ із випадковим джитером

Клієнтські бібліотеки (SDK) зобов'язані коректно реагувати на код 429. Найгірша стратегія — негайний повтор запиту (Immediate Retry), що викликає лавиноподібне перевантаження (Thundering Herd Problem).

Стандартний алгоритм експоненційного відступу з повним джитером (Full Jitter):

```
sleep_duration = random(0, min(MAX_BACKOFF, BASE_BACKOFF · 2^attempt))
```

Якщо сервер повернув заголовок `Retry-After: S`, клієнт зобов'язаний почекати щонайменше `S` секунд плюс невеликий випадковий шум (джитер) `Δt ∈ [0.1, 0.5]` секунд, щоб уникнути синхронного сплеску тисяч клієнтів в одну й ту саму мілісекунду.

## 7. Конфігурація на рівні шлюзів (NGINX та Envoy)

На практиці первинне відсікання здійснюється зворотними проксі-серверами без передавання запитів у прикладний бекенд.

### Директиви NGINX (Leaky Bucket / Token Bucket)

```nginx
# Визначення зони пам'яті на 10 МБ для відстеження IP-адрес (10 запитів/с)
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

server {
    location /api/ {
        # burst=20 дозволяє сплеск до 20 токенів
        # nodelay забезпечує поведінку Token Bucket (миттєвий пропуск без штучної черги)
        limit_req zone=api_limit burst=20 nodelay;
        limit_req_status 429;

        proxy_pass http://backend_upstream;
    }
}
```

### Конфігурація Envoy Proxy (gRPC Rate Limit Service)

Envoy делегує перевірку лімітів зовнішньому gRPC-сервісу RLS (Rate Limit Service):

```yaml
rate_limits:
  - actions:
      - request_headers:
          header_name: "X-User-Id"
          descriptor_key: "user_id"
```

## 8. Виміри ідентифікації клієнта (Client Identity Dimensions)

Ефективність політики обмеження швидкості критично залежить від вибору ключа ідентифікації (`KEYS[1]`):

1. **IP-адреса клієнта (`client_ip`):**
   - *Переваги:* Працює для неавтентифікованих запитів (сторінки входу, реєстрація, публічні ресурси).
   - *Пастки:* Корпоративні мережі та мобільні оператори використовують технологію Carrier-Grade NAT (CGNAT), де тисячі легітимних користувачів ділять одну спільну публічну IP-адресу. Жорсткий ліміт за IP заблокує цілий офіс чи регіон через надмірну активність однієї особи. Крім того, ботнети з тисяч заражених IoT-пристроїв легко обходять по-IP ліміти.
2. **Токен доступу або API-ключ (`api_key` / `Bearer JWT`):**
   - *Переваги:* Точна персоналізована прив'язка до облікового запису або передплатного тарифу (Free, Pro, Enterprise).
   - *Пастки:* Не захищає публічні endpoints до моменту проходження автентифікації.
3. **Комбінований ключ (Compound Key / Fingerprint):**
   - Промисловий стандарт для захисту чутливих маршрутів: комбінація `hash(IP + User-Agent + Target_Endpoint)` або `hash(API_Key + Organization_ID)`. Це дозволяє ізолювати сплески на «дорогих» маршрутах (наприклад, генерація звітів чи запит до LLM) без блокування легких читальних операцій (`GET /health`).

## 9. Багаторівневі політики обмеження (Multi-Tier Hierarchy)

На практиці надійна система застосовує не один ізольований ліміт, а каскад взаємодоповнюючих часових вікон:
- **Секундний ліміт (Anti-Burst):** `10 запитів/с` (захист від мікросплесків та зависання пулу потоків).
- **Хвилинний ліміт (Operational Rate):** `300 запитів/хв` (контроль стаціонарного навантаження).
- **Денний ліміт (Billing Quota):** `50 000 запитів/добу` (фінансовий захист від вичерпання платного ліміту сторонніх сервісів).

Заголовок `RateLimit-Policy` у такому випадку повертає перелік усіх активних рівнів:

```http
RateLimit-Policy: 10;w=1, 300;w=60, 50000;w=86400
```

## 10. Контракт резервного перемикання (Fallback Policy)

Якщо з'єднання з центральним сервером Redis втрачено (таймаут зв'язку, падіння вузла кластера, розділення мережі Split-Brain), API Gateway зобов'язаний застосувати одну з двох узгоджених архітектурних стратегій:

1. **Fail Open (Пріоритет доступності системи):**
   Пропускати всі запити клієнтів без перевірки ліміту. Ця стратегія обирається для критичних користувацьких шляхів бізнесу (наприклад, оформлення замовлення або авторизація в системі). У системні логи аудиту записується попередження високого рівня `RateLimiterDegradedMode`.
2. **Fail to Local In-Memory Partition (Пріоритет стійкості бекенду):**
   Кожен вузол шлюзу перемикається на локальний `LockFreeGcraLimiter` в оперативній пам'яті процесу із квотою `Quota_local = Quota_total / N_nodes`. Це захищає внутрішні бази даних від колапсу навіть за повної відсутності доступу до Redis.
