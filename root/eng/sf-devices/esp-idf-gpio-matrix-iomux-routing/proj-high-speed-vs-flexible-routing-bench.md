# Бенчмарк затримок та пропускної здатності: прямий IO_MUX проти гнучкої маршрутизації GPIO Matrix в ESP32

Цей проєкт реалізує комплексний порівняльний аналіз часових характеристик та стабільності передачі даних між двома режимами комутації виводів у мікроконтролері ESP32: прямим апаратним байпасом IO_MUX та цифровим комутатором GPIO Matrix.

## Архітектура вимірювання затримок розповсюдження

У швидкісних синхронних інтерфейсах (SPI, QSPI, SDIO) час кругової затримки сигналу (@@en|round-trip loop delay@@) визначає граничну робочу частоту шини. Для експериментальної перевірки вимірюється інтервал між виставленням тактового перепаду `SCK` периферійним модулем та моментом фактичної появи даних на вході `MISO`.

У режимі прямого байпасу (IO_MUX Native) сигнал оминає синхронізатори ядра, проходячи лише через аналоговий мультиплексор контактного майданчика:

```
Периферія SPI ──[ IO_MUX Bypass (1.8 нс) ]──> Фізичний контакт (PAD)
```

У матричному режимі (GPIO Matrix) кожен фронт сигналу захоплюється тригерами, що тактуються шиною APB з частотою 80 МГц (період 12.5 нс):

```
Периферія SPI ──[ Синхронізатор APB (12.5-25 нс) ]──> IO_MUX ──> PAD
```

## Реалізація модуля бенчмарку на мові C

Структура результатів та інтерфейс тестування оголошені у файлі [gpio_benchmark.h](root:sf-devices/esp-idf-gpio-matrix-iomux-routing/proj-high-speed-vs-flexible-routing-bench/c/gpio_benchmark.h):

```c
typedef enum {
    ROUTING_MODE_IOMUX_NATIVE = 0,
    ROUTING_MODE_GPIO_MATRIX
} routing_mode_t;

typedef struct {
    routing_mode_t mode;
    uint32_t frequency_hz;
    uint32_t measured_propagation_delay_ps;
    uint32_t round_trip_error_count;
    bool invert_signal;
} gpio_bench_result_t;
```

Вимірювальна функція у файлі [gpio_benchmark.c](root:sf-devices/esp-idf-gpio-matrix-iomux-routing/proj-high-speed-vs-flexible-routing-bench/c/gpio_benchmark.c) симулює поведінку шини SPI на частотах 40 МГц та 80 МГц. Затримка розповсюдження фіксується у пікосекундах (`ps`):

- **IO_MUX Native:** асинхронна затримка складає `1850` пс (`1.85` нс). На частоті 80 МГц тривалість тактового імпульсу становить `6.25` нс, тому зсув у 1.85 нс повністю вкладається у фазовий запас надійності (@@en|timing budget@@), а лічильник помилок `round_trip_error_count` дорівнює нулю.
- **GPIO Matrix:** затримка синхронізації шини APB додає `26400` пс (`26.4` нс). На частоті 40 МГц (період 25 нс) система зберігає працездатність завдяки вбудованому апаратному механізму фазової компенсації (зчитування на спадному фронті). Проте на частоті 80 МГц кругова затримка перевищує два повні такти, що призводить до порушення синхронізації та появи пакетних помилок фази.

## Апаратна інверсія ліній без втрати швидкості

Окремим тестом перевіряється функціонал апаратної інверсії через конфігурацію біта `GPIO_FUNCn_OUT_INV_SEL` у регістрі матриці `GPIO_FUNCn_OUT_SEL_CFG_REG`. Увімкнення апаратної інверсії виконується комбінаційним логічним інвертором усередині матриці, тому час поширення сигналу не збільшується ні на один такт APB:

```c
// Налаштування виходу через ROM API ESP-IDF з апаратною інверсією
gpio_matrix_out(pin_num, signal_idx, true, false); // 3-й аргумент: invert = true
```

Це дозволяє підключати зовнішні інвертуючі каскади та транзисторні ключі без додаткових витрат процесорного часу ядра CPU.

## Реалізація на мові C++

У файлі [gpio_benchmark.hpp](root:sf-devices/esp-idf-gpio-matrix-iomux-routing/proj-high-speed-vs-flexible-routing-bench/cpp/gpio_benchmark.hpp) реалізовано шаблонний C++ інтерфейс `esp_bench::RoutingBenchmark`. Клас використовує `constexpr` методи для перевірки статусу валідності результатів:

```cpp
auto res = esp_bench::RoutingBenchmark::run(RoutingMode::IoMuxNative, 80000000);
if (res.is_successful()) {
    // Конфігурація гарантує стабільну передачу даних без збоїв
}
```

Тестові запуски у файлах [c/main.c](root:sf-devices/esp-idf-gpio-matrix-iomux-routing/proj-high-speed-vs-flexible-routing-bench/c/main.c) та [cpp/main.cpp](root:sf-devices/esp-idf-gpio-matrix-iomux-routing/proj-high-speed-vs-flexible-routing-bench/cpp/main.cpp) наочно демонструють межі застосування: до 40 МГц рекомендується використовувати гнучку маршрутизацію через GPIO Matrix для спрощення трасування друкованої плати, а для частот від 40 до 80 МГц слід суворо дотримуватися нативних виводів IO_MUX.
