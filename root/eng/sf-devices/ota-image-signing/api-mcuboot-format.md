# 📋 Специфікація двійкового формату MCUboot та типів TLV

Цей довідник містить вичерпний опис двійкових структур заголовка образу (Image Header), дескрипторів Type-Length-Value (TLV), трейлера слота (Slot Trailer), масок конфігураційних прапорців та кодів станів для захищених завантажувачів стандарту MCUboot.

### Двійковий заголовок образу (Image Header)

Заголовок розміщується на початку двійкового файлу прошивки за нульовим зміщенням і має фіксований розмір 32 байти. Усі багатобайтові цілі числа закодовані в порядку від молодшого до старшого байта (Little-Endian).

:::tabs
```c
struct image_version {
    uint8_t  iv_major;        /* Старший номер версії */
    uint8_t  iv_minor;        /* Молодший номер версії */
    uint16_t iv_revision;     /* Номер ревізії */
    uint32_t iv_build_num;    /* Номер збірки */
};

struct image_header {
    uint32_t ih_magic;             /* Магічне число образу (0x96f3b83d) */
    uint32_t ih_load_addr;         /* Адреса завантаження в RAM (0 для XIP) */
    uint16_t ih_hdr_size;          /* Фізичний розмір заголовка та вирівнювання коду */
    uint16_t ih_protect_tlv_size;  /* Сумарний розмір захищеної зони TLV */
    uint32_t ih_img_size;          /* Розмір виконуваного двійкового коду програми */
    uint32_t ih_flags;             /* Бітова маска властивостей та режимів образу */
    struct image_version ih_ver;   /* 8-байтна семантична версія прошивки */
    uint32_t _pad1;                /* Резервне поле для вирівнювання 32 байтів */
};
```
```cpp
#include <cstdint>

namespace mcuboot {

struct ImageVersion {
    uint8_t  major{0};
    uint8_t  minor{0};
    uint16_t revision{0};
    uint32_t build_num{0};
};

struct alignas(4) ImageHeader {
    uint32_t magic{0};
    uint32_t load_addr{0};
    uint16_t hdr_size{0};
    uint16_t protect_tlv_size{0};
    uint32_t img_size{0};
    uint32_t flags{0};
    ImageVersion ver{};
    uint32_t reserved{0};
};

} // namespace mcuboot
```
:::

#### Поля, адресне вирівнювання та перевірка меж

Магічне число `ih_magic` є фіксованою 32-бітною константою `0x96f3b83d`. Коли мікроконтролер виконує холодний старт або прокидається після скидання, завантажувач зчитує перші чотири байти з початку активного та пасивного флеш-слотів. Якщо ця сигнатура не збігається, слот вважається порожнім або пошкодженим, що дозволяє миттєво відкинути неініціалізовану пам'ять (стерті байти `0xFFFFFFFF`) без запуску ресурсомістких криптографічних процедур.

Поле `ih_load_addr` визначає цільову адресу в оперативній пам'яті (SRAM) для платформ, де програма не може виконуватися безпосередньо з Flash. У більшості мікроконтролерів із підтримкою XIP (Execute-In-Place) це поле містить нульове значення, що означає запуск за фізичною адресою розташування слота у Flash.

Поле `ih_hdr_size` визначає точну відстань від початку двійкового контейнера до першого байта виконуваного коду (векторної таблиці переривань). У процесорах архітектури ARM Cortex-M регістр зсуву векторів переривань (`SCB->VTOR`) вимагає, щоб початкова адреса таблиці векторів була вирівняна за степенем двійки, пропорційним кількості підтримуваних апаратних переривань. Зазвичай це 128, 256 або 512 байтів. Заголовок займає 32 байти, а залишок відступу до значення `ih_hdr_size` заповнюється нулями для досягнення апаратного вирівнювання.

Сумарний розмір корисного навантаження коду програми задається полем `ih_img_size`. Під час парсингу завантажувач обов'язково обчислює зміщення кінця коду `total_code_end = ih_hdr_size + ih_img_size` і перевіряє, щоб ця сума не виходила за фізичні межі розділу слота. Будь-яке арифметичне переповнення при обчисленні зміщень повинно негайно призводити до відхилення образу для запобігання атакам класу виходу за межі пам'яті (Out-of-Bounds Read).

Поле `ih_protect_tlv_size` вказує довжину захищеної області метаданих. Якщо це поле не дорівнює нулю, завантажувач зобов'язаний перейти за зміщенням `ih_hdr_size + ih_img_size` і провести аудит захищених дескрипторів, які безпосередньо покриваються цифровим підписом.

Поле `ih_flags` кодує поведінку завантажувача щодо копіювання коду в RAM або розшифрування сесійними ключами, а структура `ih_ver` зберігає семантичну версію для діагностичних цілей та звітності прикладного програмного забезпечення.

### Бітові прапорці конфігурації (Image Flags)

Поле `ih_flags` інструктує завантажувач щодо особливих вимог до обробки та запуску образу:

:::tabs
```c
#define IMAGE_F_RAM_LOAD           0x00000020U /* Копіювати в RAM перед запуском */
#define IMAGE_F_NON_BOOTABLE       0x00000010U /* Образ не є виконуваним кодом */
#define IMAGE_F_ENCRYPTED_AES128   0x00000004U /* Тіло зашифровано ключем AES-128-KW */
#define IMAGE_F_ENCRYPTED_AES256   0x00000008U /* Тіло зашифровано ключем AES-256-KW */
#define IMAGE_F_ENCRYPTED_EC256    0x00000040U /* Тіло зашифровано ECIES-P256 */
#define IMAGE_F_ENCRYPTED_X25519   0x00000080U /* Тіло зашифровано ECIES-X25519 */
```
```cpp
#include <cstdint>

namespace mcuboot {

enum class ImageFlags : uint32_t {
    None             = 0,
    EncryptedAes128  = 0x00000004U,
    EncryptedAes256  = 0x00000008U,
    NonBootable      = 0x00000010U,
    RamLoad          = 0x00000020U,
    EncryptedEc256   = 0x00000040U,
    EncryptedX25519  = 0x00000080U
};

[[nodiscard]] constexpr bool has_flag(uint32_t mask, ImageFlags flag) noexcept {
    return (mask & static_cast<uint32_t>(flag)) != 0;
}

} // namespace mcuboot
```
:::

| Прапорець | Значення біта | Опис механізму |
| :--- | :--- | :--- |
| `IMAGE_F_RAM_LOAD` | `0x00000020U` | Завантажувач зобов'язаний скопіювати `ih_img_size` байтів із Flash в область оперативної пам'яті за адресою `ih_load_addr` перед передачею керування на точку входу. |
| `IMAGE_F_NON_BOOTABLE` | `0x00000010U` | Образ є контейнером допоміжних даних (наприклад, конфігураційного образу файлової системи, нейромережевої моделі чи двійкових шрифтів) і не містить виконуваного коду процесора. Завантажувач перевіряє його цілісність, але не виконує стрибок. |
| `IMAGE_F_ENCRYPTED_AES128` | `0x00000004U` | Тіло програми зашифроване симетричним алгоритмом AES-128-CTR. Трейлер TLV містить загорнутий сесійний ключ за стандартом RFC 3394 (AES Key Wrap). |
| `IMAGE_F_ENCRYPTED_AES256` | `0x00000008U` | Тіло програми зашифроване симетричним алгоритмом AES-256-CTR для профілів підвищеної таємності. |
| `IMAGE_F_ENCRYPTED_EC256` | `0x00000040U` | Сесійний ключ зашифровано за асиметричною схемою ECIES на еліптичній кривій NIST P-256 з використанням відкритого ключа пристрою. |
| `IMAGE_F_ENCRYPTED_X25519` | `0x00000080U` | Сесійний ключ зашифровано за схемою ECIES на базі протоколу Діффі-Геллмана на кривій Curve25519 (X25519). |

### Структури дескрипторів Type-Length-Value (TLV)

Метадані образу організовані у вигляді списку елементів TLV. Кожна секція TLV починається загальним заголовком:

:::tabs
```c
struct image_tlv_info {
    uint16_t it_magic;   /* Сигнатура типу зони TLV */
    uint16_t it_tlv_tot; /* Загальний розмір області TLV разом із заголовком */
};

struct image_tlv {
    uint16_t it_type;    /* Тип дескриптора метаданих */
    uint16_t it_len;     /* Довжина поля значення (Value) у байтах */
};
```
```cpp
#include <cstdint>

namespace mcuboot {

struct alignas(2) TlvInfo {
    uint16_t magic{0};
    uint16_t total_len{0};
};

struct alignas(2) TlvItem {
    uint16_t type{0};
    uint16_t len{0};
};

} // namespace mcuboot
```
:::

Стандарт розрізняє дві принципово різні зони розміщення метаданих:

1. **Захищена зона (Protected TLV, Magic `0x6908`):** розміщується безпосередньо після тіла виконуваного коду (`ih_hdr_size + ih_img_size`). Дані цієї зони **включаються в розрахунок SHA-256 хешу** образу. Жоден біт у цій зоні не можна модифікувати без порушення валідності цифрового підпису.
2. **Незахищений трейлер (Non-Protected TLV Trailer, Magic `0x6907`):** розміщується наприкінці всього файлу. Містить сам результат хешування, цифровий підпис та службові відбитки ключів.

#### Механізм обходу дескрипторів та правила обробки невідомих типів

Коли завантажувач парсить блок TLV, він ітерується по списку записів за формулою зміщення `next_offset = current_offset + sizeof(struct image_tlv) + it_len`. Для кожного запису обов'язково перевіряється, чи не перевищує розмір `it_len` залишок загального блоку `it_tlv_tot`. Якщо довжина хоча б одного елемента виходить за межі заявленої секції, вся таблиця TLV вважається скомпрометованою, і завантажувач повертає помилку пошкодження структури.

Якщо завантажувач зустрічає невідомий код типу `it_type`, поведінка залежить від того, чи встановлено біт критичності. За замовчуванням невідомі дескриптори в незахищеному трейлері просто пропускаються, що забезпечує зворотну сумісність при розширенні специфікації новими діагностичними мітками. Проте невідомі дескриптори в захищеній зоні (`0x6908`), які вимагають обов'язкової апаратної інтерпретації (наприклад, непідтримувані розширення захисту від відкату), змушують завантажувач відхилити образ для запобігання обходу політик безпеки.

#### Реєстр типів дескрипторів TLV

| Константа типу | Код | Розмір значення | Зона | Опис вмісту та правила валідації |
| :--- | :--- | :--- | :--- | :--- |
| `IMAGE_TLV_KEYHASH` | `0x0001` | 32 байти | Trailer (`0x6907`) | SHA-256 відбиток відкритого ключа підписувача. Завантажувач порівнює цей хеш зі своєю таблицею публічних ключів, щоб обрати потрібний ключ для перевірки підпису. |
| `IMAGE_TLV_SHA256` | `0x0010` | 32 байти | Trailer (`0x6907`) | Еталонний дайджест SHA-256, обчислений над блоком `[Header + Payload + Protected TLVs]`. |
| `IMAGE_TLV_SHA384` | `0x0011` | 48 байтів | Trailer (`0x6907`) | Еталонний дайджест SHA-384 для високостійких криптографічних конфігурацій. |
| `IMAGE_TLV_SHA512` | `0x0012` | 64 байти | Trailer (`0x6907`) | Еталонний дайджест SHA-512 (стандартний для схем підпису Ed25519). |
| `IMAGE_TLV_RSA2048` | `0x0020` | 256 байтів | Trailer (`0x6907`) | Двійковий цифровий підпис RSA-2048 (за схемою PKCS#1 v1.5 або PSS). |
| `IMAGE_TLV_ECDSA224` | `0x0021` | 56 байтів | Trailer (`0x6907`) | Цифровий підпис ECDSA на кривій NIST P-224 (зчеплення координат `r \|\| s`). |
| `IMAGE_TLV_ECDSA256` | `0x0022` | 64 байти | Trailer (`0x6907`) | Цифровий підпис ECDSA на кривій NIST P-256 (координати `r \|\| s`, по 32 байти). |
| `IMAGE_TLV_RSA3072` | `0x0023` | 384 байти | Trailer (`0x6907`) | Двійковий цифровий підпис RSA-3072. |
| `IMAGE_TLV_ED25519` | `0x0024` | 64 байти | Trailer (`0x6907`) | Цифровий підпис Ed25519 (стиснута точка `R` 32B + скаляр `S` 32B за RFC 8032). |
| `IMAGE_TLV_ENC_KW` | `0x0031` | 24 байти | Trailer (`0x6907`) | Загорнутий 128-бітний симетричний ключ розшифрування прошивки (AES Key Wrap). |
| `IMAGE_TLV_ENC_EC256` | `0x0032` | 96 байтів | Trailer (`0x6907`) | Тимчасовий відкритий ключ ECIES та зашифрований симетричний ключ. |
| `IMAGE_TLV_ENC_X25519` | `0x0033` | 80 байтів | Trailer (`0x6907`) | Тимчасовий відкритий ключ X25519 та симетричний ключ AES. |
| `IMAGE_TLV_SEC_CNT` | `0x0050` | 4 байти | Protected (`0x6908`) | 32-бітний монотонний лічильник безпеки для апаратного захисту від відкату версії. |
| `IMAGE_TLV_BOOT_RECORD` | `0x0060` | Змінний | Protected (`0x6908`) | CBOR-структура вимірювань завантаження за стандартом IETF Entity Attestation Token (EAT). |

### Трейлер слота та метадані перемикання (Slot Trailer)

У самому кінці кожного розділу Flash, виділеного під Slot 0 або Slot 1, MCUboot розміщує спеціальну службову структуру, яка зберігає поточний стан атомарного обміну та результати тестування прошивки.

```text
+-------------------------------------------------------------+
| Залишок розділу слота (вільний простір)                     |
+-------------------------------------------------------------+
| Записи прогресу свопу: Swap Status Entries                  |
| (кількість записів залежить від розміру секторів Flash)     |
+-------------------------------------------------------------+
| Encryption Key 0 (16B / 32B, якщо активне шифрування)       |
+-------------------------------------------------------------+
| Encryption Key 1 (16B / 32B, якщо активне шифрування)       |
+-------------------------------------------------------------+
| Swap Size (4 байти, розмір корисних даних для перенесення)  |
+-------------------------------------------------------------+
| Swap Info (1 байт: тип операції свопу та номер кроку)       |
+-------------------------------------------------------------+
| Copy Done Flag (1 байт: 0x01 = завершено, 0xFF = у процесі) |
+-------------------------------------------------------------+
| Image OK Flag (1 байт: 0x01 = підтверджено, 0xFF = тест)    |
+-------------------------------------------------------------+
| Magic Number (16 байтів: 0x77 0xc2 0x98 0x69 0x1c 0x58      |
|               0x72 0xc3 0x69 0x65 0x46 0x46 0x74 0x79 0x6e  |
|               0x5a)                                         |
+-------------------------------------------------------------+
```

#### Призначення та механіка полів трейлера

Фіксоване 16-байтне значення `Magic Number` у самому кінці розділу свідчить про те, що даний флеш-слот містить дійсні метадані стану MCUboot. Якщо ці 16 байтів не збігаються з еталоном (наприклад, містять нестерту або стерту пам'ять), завантажувач ігнорує прапорці слота й не виконує жодних дій щодо зміни стану.

Ключову роль у відмовостійкості відіграє байт `Image OK Flag`. Коли завантажувач уперше копіює новий образ у робочий Slot 0, ця комірка залишається у стані `0xFF` (що відповідає стану випробування `TESTING`). Фізична особливість пам'яті NOR Flash полягає в тому, що окремі біти можна змінювати з `1` на `0` без попереднього стирання цілого блоку. Коли новий застосунок підтверджує свою стабільність, функція `boot_set_confirmed()` записує значення `0x01` у байт `Image OK`. Якщо ж до цього моменту станеться перезавантаження або зависання, завантажувач побачить `0xFF` і негайно поверне попередню стабільну прошивку.

Поле `Copy Done Flag` сигналізує про завершення копіювання чи обміну секторів, а масив `Swap Status Entries` фіксує проміжний стан переміщення кожного окремого сектора. Завдяки цьому при раптовому вимкненні живлення завантажувач точно знає, які сектори вже перенесені у розділ підкачки Scratch, а які ще очікують запису, запобігаючи руйнуванню прошивки.

### Програмний інтерфейс взаємодії застосунку із завантажувачем

Для керування станом образу з простору застосунку стандартна бібліотека MCUboot надає такі інтерфейси:

:::tabs
```c
/* Позначити поточний запущений образ як постійний і робочий */
int boot_set_confirmed(void);

/* Запитати тестове перемикання на новий образ у вторинному слоті після рестарту */
int boot_set_pending(int permanent);

/* Отримати інформацію про тип очікуваного перемикання */
int boot_swap_type(void);
```
```cpp
#include <expected>
#include <cstdint>

namespace mcuboot {

enum class SwapType : uint8_t {
    None   = 1,
    Test   = 2,
    Perm   = 3,
    Revert = 4,
    Fail   = 5,
    Panic  = 6
};

class BootManager {
public:
    [[nodiscard]] static std::expected<void, int> mark_confirmed() noexcept;
    [[nodiscard]] static std::expected<void, int> request_upgrade(bool permanent) noexcept;
    [[nodiscard]] static SwapType current_swap_type() noexcept;
};

} // namespace mcuboot
```
:::

Функція `boot_set_pending(int permanent)` викликається фоновим демоном оновлення після успішного завантаження нового образу у Slot 1. Якщо аргумент `permanent` дорівнює нулю, завантажувач на наступному старті виконає пробний запуск (`TESTING`). Якщо передати одиницю, завантажувач одразу закріпить новий образ без права відкату.

Функція `boot_set_confirmed()` викликається основним циклом або менеджером ініціалізації нового застосунку після завершення внутрішнього самотестування. Вона записує прапорець `Image OK = 0x01` у Flash, закріплюючи поточну прошивку назавжди.

#### Коди типів перемикання слотів (`boot_swap_type`)

:::tabs
```c
enum boot_swap_type {
    BOOT_SWAP_TYPE_NONE     = 1, /* Образ у Slot 0 готовий, перемикання не потрібне */
```
