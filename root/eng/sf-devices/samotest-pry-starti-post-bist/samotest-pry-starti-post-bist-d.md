Електричний нагрівальний котел потужністю 24 кВт подає напругу на силові симістори через ШІМ-канал мікроконтролера. При температурі теплоносія 85 °C програма обчислює різницю з уставкою і формує команду вимкнення нагріву. Проте через дефект кремнію у блоці регістрів процесора (коротке замикання затвора на лінію живлення в регістрі R3) нульове значення під час запису примусово замінюється на `0x000000FF`. Процесор безперервно генерує стовідсотковий коефіцієнт заповнення ШІМ. Код виконується без жодних збоїв, лічильник команд просувається штатно, сторожовий таймер справно скидається в кінці циклу, але вода нагрівається до 115 °C, тиск у контурі перевищує 4 бари, і систему рятує лише аварійний механічний клапан скидання.

З погляду операційної системи чи базової прошивки процесор абсолютно «здоровий»: він не потрапив у HardFault і не завис у нескінченному циклі. Проте його обчислювальне ядро або підсистема пам'яті спотворюють дані. Факт виконання інструкцій не доводить справності кремнію. Щоб виявити приховані фізичні дефекти ще до виникнення аварії, мікроконтролер повинен володіти внутрішнім комплексом самоперевірки: стартовим самотестом під час подачі живлення (**Power-On Self-Test — POST**) та фоновою періодичною самодіагностикою під час роботи (**Built-In Self-Test — BIST**).

## Нормативні вимоги функційної безпеки

У побутових приладах, промислових верстатах та автомобільній електроніці відмова мікроконтролера не повинна призводити до пожежі, ураження струмом чи механічної травми людини. Для цього міжнародні стандарти стандартизували перелік обов'язкових самотестів процесора та пам'яті.

### Класифікація стандартів: IEC 60730, IEC 61508 та ISO 26262

Головним нормативним документом для вбудованих систем загального та побутового призначення є стандарт **IEC 60730** (зокрема додаток *Annex H*), який класифікує керуюче програмне забезпечення за трьома категоріями:

1. **Class A (некритичні функції):** системи, відмова яких не створює небезпеки для користувача (електронні термометри для кімнати, інтерфейсні дисплеї, підсвітка кнопок, таймери поливу газону). Спеціальних засобів самодіагностики ядра та пам'яті не вимагається.
2. **Class B (запобігання небезпечній роботі):** системи, де одинична несправність у мікроконтролері або програмі може призвести до небезпечної ситуації (пральні машини з блокуванням люка, кухонні електроплити, холодильні компресори, електроінструмент). Стандарт вимагає виявлення будь-якої одиничної відмови процесора, пам'яті, генератора такту чи ліній введення-виведення.
3. **Class C (запобігання вибуху та катастрофічним руйнуванням):** обладнання, несправність якого безпосередньо загрожує життю людей (газові пальники, клапани подачі палива, системи захисту від закипання під тиском). Вимагає дублювання каналів керування (1oo2 або 2oo3) та стійкості до множинних послідовних відмов.

У промисловості діє стандарт **IEC 61508** з рівнями повноти безпеки від **SIL 1** до **SIL 4** (*Safety Integrity Level*), де вимоги Class B відповідають рівню SIL 2, а Class C — рівню SIL 3. В автоелектроніці аналогічну шкалу задає **ISO 26262** через класи **ASIL** (*Automotive Safety Integrity Level*) від ASIL A до ASIL D.

![Класифікація функційної безпеки та часовий бюджет реакції на відмову](/root/eng/sf-devices/samotest-pry-starti-post-bist/img/safety-standards-classes.svg)
*Класифікація безпеки за IEC 60730 та зв'язок часових інтервалів: період діагностики FDTI та час переходу FRT мають суворо вкладатися у загальний бюджет безпеки процесу PST.*

### Метрики надійності: DC, SFF та часовий бюджет PST

Для оцінки ефективності алгоритмів самодіагностики стандарт вводить поняття діагностичного покриття (**Diagnostic Coverage — DC**):

```
Формула діагностичного покриття:
  DC = (Кількість виявлених небезпечних відмов) / (Загальна кількість небезпечних відмов)
```

Для сертифікації за Class B (SIL 2) рівень діагностичного покриття DC повинен перевищувати **90%** (середній рівень — Medium), а частка безпечних відмов (**Safe Failure Fraction — SFF**) має становити щонайменше 90%.

Друга критична вимога — час реакції. Фізичний процес володіє власною інерцією, яка визначає граничний час безпеки процесу (**Process Safety Time — PST**). Наприклад, для перегріву індукційної конфорки без посуду PST становить 500 мс, а для займання газу при відмові датчика полум'я — лише 100 мс.

Система самодіагностики повинна гарантувати часове співвідношення:

```
Часова нерівність функційної безпеки:
  FDTI + FRT <= PST

де:
  FDTI  [Fault Detection Time Interval] = максимальний інтервал між запусками BIST-тесту
  FRT   [Fault Reaction Time]           = час переведення системи у безпечний стан
  PST   [Process Safety Time]           = час від виникнення збою до початку руйнування
```

Якщо BIST-тест пам'яті запускається раз на 2 секунди, а процес переходить у небезпечну фазу за 300 мс, такий тест є неефективним — аварія станеться до того, як мікроконтролер виявить збій.

## Дві фази самодіагностики: стартовий POST та фоновий BIST

Самоперевірка пристрою розбивається на дві принципово різні за своєю природою фази, кожна з яких виконується у власному операційному середовищі.

![Життєвий цикл самотестування: стартовий POST та фоновий BIST](/root/eng/sf-devices/samotest-pry-starti-post-bist/img/post-vs-runtime-timeline.svg)
*Життєвий цикл самотестування: стартовий POST перевіряє апаратну частину на 100% до запуску runtime C, а періодичний BIST виконує неруйнівні зрізи під час штатної роботи.*

### Стартовий тест (Power-On Self-Test — POST)

POST виконується безпосередньо після апаратного скидання процесора (`Reset_Handler`) **до** того, як стандартне середовище C обнулить секцію `.bss` та скопіює значення початкових змінних у секцію `.data`.

У цій точці прошивка має унікальні переваги:
1. **Оперативна пам'ять не містить робочих даних:** можна виконувати руйнівні тести (запис інверсних шаблонів по всьому простору SRAM) без потреби збереження та відновлення байтів.
2. **Переривання вимкнені за замовчуванням:** відсутній ризик виникнення перегонів або переривання критичного тесту таймером чи периферією.
3. **Виконавчі механізми знеструмлені:** реле та силові транзистори ще не активовані, що дозволяє витратити на повну діагностику від 10 до 200 мілісекунд без ризику для технологічного процесу.

Якщо POST виявляє дефект, пристрій взагалі не переходить до ініціалізації прикладного коду (`main()`), а блокує запуски й сигналізує про апаратну несправність.

### Періодичний самотест (Periodic Runtime BIST)

Після запуску основного циклу (Super-loop або задач RTOS) в оперативній пам'яті розміщені стеки задач, черги повідомлень, глобальні змінні та буфери мережевих пакетів. Проводити повний тест пам'яті чи зупиняти процесор на 100 мс неприпустимо, оскільки це призведе до втрати даних та порушення часових інтервалів керування.

Тому фоновий BIST реалізується як **неруйнівний зріз** (*non-destructive slicing*):
* Пам'ять тестується малими вікнами (наприклад, по 16 слів або 64 байти за ітерацію);
* Перед тестом вміст вікна атомарно зберігається у резервний буфер;
* На час маршового прогону вимикаються переривання;
* Після завершення фази дані повертаються на місце, переривання дозволяються, а вказівник зрізу зміщується далі;
* Контрольна сума Flash обчислюється інкрементально блоками по 512 або 1024 байти за кожен прохід циклу.

Повний цикл тестування прокручується за фіксовану кількість ітерацій, яка обов'язково менша за FDTI.

## Самотестування ядра процесора (CPU Core BIST)

Центральний процесор складається з масиву регістрів загального призначення, лічильника команд, вказівника стека та арифметико-логічного пристрою (АЛП). Одиничний дефект перенесення біта в АЛП або залипання біта в регістрі робить неможливим коректне виконання навіть найпростішої логіки порівняння `if (temperature > MAX)`.

### 1. Тестування регістрів процесора (Register Bank Check)

Для мікроконтролерів Cortex-M необхідно перевірити регістри R0–R12, вказівник зв'язку (LR), вказівники стека (MSP та PSP) і регістр стану програми (xPSR/APSR).

Кожен регістр повинен пройти перевірку на два критичні дефекти:
* **Залипання в 0 або 1 (Stuck-At Fault):** лінія пам'яті регістра замкнена на шину живлення чи землю;
* **Місткове замикання сусідніх ліній (Bridging / Coupling Fault):** зміна значення у біті k викликає зміну у сусідньому біті k + 1.

Для виявлення обох дефектів використовують шахові взаємно комплементарні бітові маски: `0x55555555` (двійкове `01010101...`) та `0xAAAAAAAA` (двійкове `10101010...`). Перший шаблон перевіряє чергування нулів та одиниць; другий — повністю інвертує кожен біт.

```
Тестування регістрів взаємно комплементарними шаблонами:
  Крок 1: Запис у R_n значення 0x55555555 -> Зчитування та перевірка рівності
  Крок 2: Запис у R_n значення 0xAAAAAAAA -> Зчитування та перевірка рівності
```

Якщо регістр має залипання третього біта в нуль, на першому кроці він поверне `0x55555555`, але на другому кроці замість `0xAAAAAAAA` процесор прочитає `0xAAAAAAA2` (біт 3 залишився нулем), що призведе до негайної фіксації відмови.

Тест реалізується виключно мовою асемблера або через жорстко прив'язані регістрові змінні GCC (`register uint32_t r0 __asm__("r0")`), щоб оптимізатор компілятора не замінив реальний доступ до фізичного регістра роботою зі стеком або константною згорткою.

### 2. Тестування прапорців АЛП (ALU Condition Flags)

Арифметико-логічний пристрій визначає логіку переходів за допомогою прапорців регістра стану `APSR`:
* **N (Negative):** результат операції від'ємний (старший біт 31 встановлений);
* **Z (Zero):** результат операції дорівнює нулю;
* **C (Carry):** відбулося перенесення або позика біта;
* **V (Overflow):** арифметичне переповнення знакового діапазону.

Тест синтезує такі математичні вирази, які гарантовано змушують АЛП змінити стан кожного прапорця з 0 в 1 і назад:

```
Синтез операцій перевірки прапорців:
  1. Тест Z та C:
     0xFFFFFFFF + 0x00000001 = 0x00000000  -> Встановлює Z=1 та C=1
  2. Тест N та V:
     0x7FFFFFFF + 0x00000001 = 0x80000000  -> Встановлює N=1 та V=1
  3. Скидання прапорців:
     0x00000002 - 0x00000001 = 0x00000001  -> Скидає Z=0, N=0, V=0
```

Якщо лінія формування сигналу переповнення у кремнії перегоріла, другий вираз не встановить прапорець `V`, подальша інструкція умовного переходу `BGT` (Branch if Greater Than) спрацює помилково, а POST-тест зафіксує несправність.

### 3. Тестування лічильника команд (Program Counter — PC)

Дефект адресної шини вибірки команд може призвести до того, що біт адреси A_4 не встановлюється в одиницю. У такому разі виклик функції за адресою `0x08000110` призведе до помилкового переходу на інструкцію за адресою `0x08000100`.

Для перевірки лічильника команд створюють фіксовану послідовність функцій-пасток із перехресними викликами:

```
Алгоритм верифікації Program Counter:
  Func_A (адреса з бітом A_k = 0) -> встановлює підпис 0xAA01 -> викликає Func_B
  Func_B (адреса з бітом A_k = 1) -> перевіряє підпис, змінює на 0xBB02 -> повертає керування
  Фінальна точка -> перевіряє валідність ланцюжка сигнатур
```

Якщо під час виконання виклику лічильник команд зіб'ється або стрибне через дефект дешифратора в обхід проміжної точки, фінальна сигнатура не співпаде з еталоном.

### 4. Тестування сторожового таймера (Watchdog BIST)

[Watchdog](root:sf-devices/watchdog) є останнім бар'єром порятунку пристрою від зависання. Проте якщо його внутрішній лічильник зупинився через обрив тактування або транзистор апаратного скидання вийшов з ладу, система залишається беззахисною.

IEC 60730 вимагає перевірки функціонування сторожового таймера під час старту. Механізм тесту виглядає так:
1. При холодному включенні (Power-On Reset) прошивка перевіряє прапорець причини перезавантаження у регістрі скиду (наприклад, `RCC_CSR` в STM32);
2. Якщо це перший запуск, прошивка записує в енергонезалежний регістр відмітку `WDT_TEST_IN_PROGRESS`, налаштовує сторожовий таймер на мінімальний таймаут (наприклад, 15 мс) і входить у навмисний нескінченний цикл `while(1)`;
3. Сторожовий таймер спрацьовує і скидає процесор;
4. Після рестарту `Reset_Handler` знову читає регістр скиду: якщо прапорець вказує на спрацювання Watchdog (`WWDGRSTF` / `IWDGRSTF`), а в оперативній пам'яті збережено відмітку `WDT_TEST_IN_PROGRESS`, робиться висновок: *апаратний скид сторожовим таймером працює на 100%*;
5. Прапорець очищується, і мікроконтролер переходить до звичайної ініціалізації.

## Тестування оперативної пам'яті (SRAM BIST): алгоритми March

Матриця статичної пам'яті є найщільнішою структурою кристала і піддається деградації через дефекти літографії, витоки зарядів та вплив завад живлення.

### Чому простий запис констант не працює

Поширена помилка розробників — тестування ОЗП простим циклом запису байта `0xAA` з негайним зчитуванням назад:

:::tabs
```c
/* НАЇВНИЙ ТА НЕЕФЕКТИВНИЙ ТЕСТ: ЗАБОРОНЕНО СТАНДАРТАМИ */
for (int i = 0; i < RAM_SIZE; i++) {
    ram[i] = 0xAA;
    if (ram[i] != 0xAA) return FAIL;
}
```
```cpp
// НАЇВНИЙ ТА НЕЕФЕКТИВНИЙ ТЕСТ: ЗАБОРОНЕНО СТАНДАРТАМИ
for (auto& cell : ram_span) {
    cell = 0xAA;
    if (cell != 0xAA) return Status::Fail;
}
```
:::

Такий код пропускає до 70% реальних апаратних несправностей:
1. **Дефекти дешифратора адреси (Address Decoder Faults — AF):** якщо через коротке замикання ліній адреси A_2 та A_3 звернення за адресою `0x20000004` фізично записує дані у комірку `0x2000000C`, цей цикл успішно пройде, оскільки читання виконується одразу після запису за тією ж самою спотвореною адресою.
2. **Дефекти взаємного впливу (Coupling Faults — CF):** коли зміна стану в комірці k інвертує значення в сусідній комірці m, простий прохід цього не побачить, якщо комірка m ще не була перевірена або була перезаписана пізніше.

Детальний математичний апарат, моделі несправностей SAF, TF, AF, CFin, CFid та формальні доведення повноти покриття наведені у вставці [Математичний аналіз дефектів пам'яті в алгоритмах March C- та March X](root:sf-devices/samotest-pry-starti-post-bist/math-march-algorithms.md).

### Алгоритм March C-

Стандарт IEC 60730 прямо вказує на алгоритм **March C-** як на базовий метод тестування ОЗП для систем Class B. Він володіє складністю 10N (10 операцій читання/запису на кожну комірку масиву з N слів) і складається з 6 послідовних фаз сканування.

![Алгоритм March C- для тестування ОЗП: 6 фаз сканування пам'яті](/root/eng/sf-devices/samotest-pry-starti-post-bist/img/march-c-phases.svg)
*Шість фаз алгоритму March C-: сканування у висхідному та низхідному напрямках повністю викриває залипання, дефекти переходів, збої дешифрації та перехресні наведення.*

Послідовність операцій March C-:
1. **M0: ⇕ (w0)** — заповнення всього масиву нулями в довільному порядку;
2. **M1: ⇑ (r0, w1)** — висхідний прохід (від адреси 0 до N - 1): зчитуємо 0 (перевірка попереднього запису), записуємо 1;
3. **M2: ⇑ (r1, w0)** — висхідний прохід: зчитуємо 1, записуємо 0;
4. **M3: ⇓ (r0, w1)** — низхідний прохід (від адреси N - 1 до 0): зчитуємо 0, записуємо 1;
5. **M4: ⇓ (r1, w0)** — низхідний прохід: зчитуємо 1, записуємо 0;
6. **M5: ⇕ (r0)** — фінальна верифікація: зчитуємо 0 з усіх комірок.

Зміна напрямку адресації (⇑ висхідний та ⇓ низхідний) є ключовою: якщо комірка зі старшою адресою впливає на комірку з молодшою адресою, висхідний прохід не зможе зафіксувати аномалію, проте вона буде миттєво викрита під час низхідного проходу на фазі M3 чи M4.

### Неруйнівний квант March C- під час роботи (Periodic RAM Slice)

Для роботи в супер-циклі застосовують буферизований слайсер. Реалізацію алгоритму March C- та механізм захищеного зрізу наведено у вставці [Модульна бібліотека самотестування POST/BIST за стандартом IEC 60730](root:sf-devices/samotest-pry-starti-post-bist/proj-iec60730-bist.md).

```
Кроки виконання одного кванта фонового тесту ОЗП:
  1. primask = disable_interrupts()      [Заборона всіх переривань]
  2. memcpy(backup_buf, current_ptr, 64) [Копіювання 64 байтів у тіньовий буфер]
  3. execute_march_c(current_ptr, 64)    [Прогін 6 фаз March C- на живому зрізі]
  4. memcpy(current_ptr, backup_buf, 64) [Повернення вихідних даних на місце]
  5. restore_interrupts(primask)         [Дозвіл переривань]
  6. current_ptr += 64                   [Зсув до наступного вікна]
```

Оскільки 64 байти тестуються за кілька мікросекунд, затримка реакції на переривання (Interrupt Latency) практично не впливає на роботу периферії, а весь простір ОЗП (наприклад, 128 КБ) повністю перевіряється за 2000 ітерацій основного циклу.

## Тестування постійної пам'яті (Flash / ROM Integrity)

Флеш-пам'ять мікроконтролера піддається деградації через витік заряду з плаваючих затворів (*charge leakage*), особливо в умовах високих робочих температур (понад 85 °C). Зміна навіть одного біта в таблиці векторів переривань чи коді функції призводить до непередбачуваної поведінки.

### Алгоритми контролю цілісності: CRC-32 проти Fletcher та SHA-256

1. **Проста адитивна сума (Checksum-16/32):** підсумовування всіх байтів програми. Стандарти безпеки забороняють цей метод, оскільки взаємна зміна двох бітів (один 0 -> 1, другий 1 -> 0) дає ту саму суму, маскуючи дефект.
2. **Алгоритм Флетчера (Fletcher-16 / Fletcher-32):** обчислює два блоки сум одночасно, враховуючи позицію бітів. Має високу швидкість на процесорах без апаратного прискорювача, але поступається CRC за виявленням пакетних помилок.
3. **Циклічний надлишковий код (CRC-32):** стандартний промисловий вибір (поліном IEEE 802.3 `0x04C11DB7` або поліном Castagnoli `0x1EDC6F41`). Виявляє всі одиничні, подвійні та пакетні спотворення довжиною до 32 біт. Багато сучасних мікроконтролерів (STM32, NXP LPC, ESP32) мають вбудований апаратний рушій CRC, здатний перевіряти 32-бітне слово за один такт шини.
4. **Криптографічні хеші (SHA-256):** забезпечують абсолютну стійкість, але вимагають надто багато обчислювальних ресурсів для фонового періодичного виконання.

```
Математичне представлення полінома CRC-32 (IEEE 802.3):
  P(x) = x^32 + x^26 + x^23 + x^22 + x^16 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1
```

### Фоновий інкрементальний розрахунок Flash CRC

Під час компіляції прошивки спеціальна утиліта (наприклад, `srec_cat` або скрипт постасемблінгу) розраховує еталонну CRC32 для всієї області пам'яті програм і записує її за фіксованою адресою у фінальний сектор Flash.

Під час роботи періодичний BIST бере квант розміром 1 КБ за один крок:

```
Інкрементальне сканування Flash:
  Ітерація k   : CRC_k = CRC32_Update(CRC_{k-1}, Flash_Block_k)
  ...
  Ітерація N   : Фінальне порівняння:
                 Якщо (CRC_N != EXPECTED_CRC) -> bist_enter_safe_state(BIST_ERR_FLASH_CRC);
```

Це дозволяє уникнути тривалих пауз у роботі пристрою: Flash об'ємом 512 КБ перевіряється за 512 ітерацій фонового циклу без навантаження на систему.

## Тестування системного тактування та периферії

Програмний код спирається на коректність системної частоти: затримки, розрахунок інтегральних складових у ПІД-регуляторах, таймаути протоколів зв'язку та робота силових перетворювачів залежать від генератора такту.

### Перехресна перевірка тактування (Clock Plausibility via Cross-Checking)

Кварцовий резонатор (HSE) може зазнати фізичного пошкодження (тріщина кристала від вібрації) або дрейфу частоти внаслідок старіння та зміни температури. Оскільки процесор тактується від того ж самого резонатора, він не може самостійно виявити сповільнення часу: інструкції виконуватимуться повільніше, але з погляду внутрішніх лічильників секунда здаватиметься правильною.

Єдиний надійний спосіб контролю — **перехресне вимірювання за допомогою незалежного допоміжного генератора**.

![Перехресна перевірка частоти тактування основного генератора допоміжним](/root/eng/sf-devices/samotest-pry-starti-post-bist/img/clock-cross-check.svg)
*Принцип перехресної перевірки частоти: апаратний таймер рахує імпульси основного високочастотного PLL, фіксуючи період незалежного низькочастотного генератора LSI/LSE.*

Апаратна реалізація перевірки:
1. Основне ядро та таймер `TIM_MAIN` тактуються від системного генератора (наприклад, 168 МГц від PLL/HSE);
2. Допоміжний внутрішній RC-генератор (LSI ~32 кГц) або годинниковий резонатор (LSE 32.768 кГц) підключається до входу каналу захоплення (`Input Capture`) таймера `TIM_MAIN`;
3. Таймер вимірює кількість тактів основної частоти між двома послідовними фронтами сигналу LSI:

```
Формула розрахунку очікуваної кількості тактів:
  N_expected = f_main / f_ref

Приклад:
  f_main = 168 000 000 Гц (PLL)
  f_ref  = 32 000 Гц (LSI)
  N_expected = 168 000 000 / 32 000 = 5250 тактів
```

Прошивка перевіряє потрапляння виміряного значення у допустиме вікно (наприклад, ±5% для урахування температурного дрейфу LSI):

```
Критерій валідності частоти:
  N_min <= N_measured <= N_max
  5250 * 0.95 <= N_measured <= 5250 * 1.05  ->  4987 <= N_measured <= 5512
```

Якщо значення виходить за межі вікна, це свідчить про зрив генерації PLL, розкол кварцу або фатальне просідання живлення. Крім того, на апаратному рівні активується система безпеки тактування (**Clock Security System — CSS**), яка при зникненні імпульсів HSE автоматично генерує немасковане переривання (NMI) і перемикає ядро на аварійний внутрішній генератор HSI.

### Самотестування АЦП та опорної напруги (ADC / VREF Self-Test)

Аналогово-цифровий перетворювач використовується для читання критичних датчиків (струм двигуна, тиск газу, температура нагрівача). Зсув внутрішнього джерела опорної напруги (V_REF) призводить до того, що АЦП інтерпретує небезпечну температуру як нормальну.

Процедура діагностики АЦП включає:
1. **Вимірювання каналу внутрішньої опорної напруги (V_REFINT):** кристал має прецизійний стабілізатор на базі забороненої зони (типово 1.20 В або 1.25 В). Під час заводського калібрування виробник записує точне значення коду АЦП для V_REFINT у захищену пам'ять Flash OTP (наприклад, `VREFINT_CAL`). BIST зчитує поточний стан каналу і порівнює його з калібрувальною константою.
2. **Вимірювання каналу температури кристала (V_TS):** виявляє перегрів чи порушення контакту кристала з тепловідводом.
3. **Тест на закорочення входу АЦП:** вимірювання внутрішнього каналу «землі» (має повернути 0) та внутрішньої лінії живлення V_DDA (має повернути 2^B - 1, де B — розрядність АЦП).

### Тестування ліній введення-виведення (GPIO Plausibility)

Лінії керування критичними виконавчими органами (наприклад, сигнал дозволу запалювання газу) повинні перевірятися на залипання контактної площадки мікросхеми:
* **Тест підтяжки (Pull-Up / Pull-Down Toggle Test):** вивід перемикається у режим високого імпедансу (вхід) із послідовним увімкненням внутрішнього резистора підтяжки до живлення (Pull-Up), а потім до землі (Pull-Down). Якщо вхідний регістр `IDR` не змінює свого стану відповідно до підтяжки, лінія фізично замкнена на шину живлення, землю або інший вивід.
* **Тест зворотного зчитування (Output-to-Input Readback):** після запису значення в регістр вихідних даних `ODR` програма зчитує фізичний стан піна через регістр вхідних даних `IDR`. Невідповідність виявляє коротке замикання зовнішнього кола на сусідній силовий провідник.

## Перехід у безпечний стан (Safe State)

Якщо будь-який етап стартового POST або періодичного BIST повертає помилку, система не має права продовжувати нормальну роботу. Вона повинна негайно перейти в детермінований **безпечний стан (Safe State)** за час, менший за FRT.

### Фізичні дії переходу в Safe State

1. **Миттєве знеструмлення виконавчих механізмів:**
   * Скидання регістрів керування таймерами ШІМ (`MOE = 0` — Main Output Enable, переведення силових виходів у високоімпедансний стан);
   * Примусове встановлення ліній керування реле, клапанами та контакторами у пасивний розімкнений стан;
   * Блокування ліній драйверів через апаратні входи блокування (*Hardware Interlock / Emergency Break Pin*).
2. **Фіксація діагностичного коду відмови:**
   * Запис коду помилки (наприклад, `BIST_ERR_RAM_MARCH_C`), ідентифікатора несправного блоку та дампу критичних регістрів у енергонезалежні регістри збереження (RTC Backup Registers) або зовнішню пам'ять EEPROM/Fram;
   * Активація аварійної світлової або звукової сигналізації для обслуговуючого персоналу.
3. **Блокування ядра:**
   * Заборона глобальних переривань (`cpsid i`);
   * Вхід у нескінченний цикл очікування апаратного скидання або утримання процесора в інструкції `WFI` (Wait For Interrupt) до перезавантаження сторожовим таймером, якщо системна конфігурація передбачає циклічний перезапуск з аналізом лічильника відмов.

## Підсумковий огляд діагностичного комплексу

Реалізація надійного самотестування вимагає збалансованого розподілу ресурсів мікроконтролера між робочим завданням та фоновою діагностикою:

| Компонент діагностики | Фаза виконання | Метод перевірки | Стандартне тестове покриття (DC) |
| :--- | :--- | :--- | :--- |
| **Регістри процесора** | POST + Periodic | Шахові маски 0x55555555 / 0xAAAAAAAA | 100% (SAF, Bridging) |
| **Прапорці АЛП** | POST + Periodic | Синтез переповнення, переносу, знака та нуля | 100% (ALU Logic) |
| **Лічильник команд (PC)** | POST | Таблиця неперервності адресних переходів | >90% (Jump/Call Path) |
| **Сторожовий таймер** | POST | Навмисний таймаут та аналіз прапорців скиду | 100% (WDT Circuit) |
| **Оперативна пам'ять (SRAM)** | POST (100%) / BIST (слайси) | Алгоритм March C- (10N) з буферизацією | >99% (SAF, TF, AF, CFin, CFid) |
| **Пам'ять програм (Flash)** | POST + Periodic (слайси) | Інкрементальний CRC-32 (IEEE 802.3) | 99.999% (Bit Rot, Charge Loss) |
| **Тактування (Clock)** | Periodic | Перехресне захоплення таймером частоти LSI/LSE | >95% (Frequency Drift, Stuck) |
| **АЦП та VREF** | Periodic | Контроль VREFINT за заводською калібровкою OTP | >90% (ADC Reference Faults) |
| **Лінії GPIO** | POST + Periodic | Тест підтяжок Pull-Up/Pull-Down та Readback | >90% (Pin Stuck-At) |

Впровадження повного модульного стеку POST/BIST перетворює мікроконтролер із «сліпого» автомата на самодіагностовану систему, яка здатна локалізувати фізичну деградацію кремнію та перевести обладнання в безпечний стан задовго до того, як апаратний збій викличе аварію чи створить загрозу людині.
