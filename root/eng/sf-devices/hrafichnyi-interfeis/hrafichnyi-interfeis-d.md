Екран із роздільною здатністю 480×320 точок при 16-бітному кольорі (RGB565) вимагає 307 200 байтів оперативної пам'яті лише на один повнорозмірний кадровий буфер. Якщо для усунення розривів зображення (тирингу) застосувати класичну подвійну буферизацію, апаратні потреби зростають до 614,4 КБ. У типового мікроконтролера Cortex-M4 чи Cortex-M7 (наприклад, STM32F407 або ESP32) весь обсяг внутрішньої статичної пам'яті (SRAM) обмежений 128–512 КБ. Спроба виділити монолітний подвійний фреймбуфер у внутрішньому ОЗП призводить до аварійної помилки лінкувальника ще під час компіляції або змушує встановлювати зовнішню мікросхему SDRAM/PSRAM, яка ускладнює розведення друкованої плати, збільшує енергоспоживання на 30–80 мА і сповільнює доступ до пікселів через вузьку зовнішню шину.

Графічний рушій для вбудованих систем вирішує це протиріччя через модель **часткового перемальовування** (англ. *partial rendering*): замість зберігання всього зображення в ОЗП бібліотека виділяє компактний буфер лише на 1/10 або 1/20 площі дисплея (15–30 КБ), прораховує в ньому пікселі лише тих віджетів, стан яких змінився, і передає готову смугу в контролер екрана через прямий доступ до пам'яті (DMA).

## Фізика пам'яті: три моделі буферизації екрана

У графічних системах на мікроконтролерах вибір моделі буферизації визначає баланс між витратами SRAM, завантаженням ядра та частотою оновлення кадрів (FPS). Графічний рушій LVGL (англ. *Light and Versatile Graphics Library*) підтримує три базові режими виділення пам'яті під рендеринг.

![Режими буферизації дисплея в графічному рушії мікроконтролера](/root/eng/sf-devices/hrafichnyi-interfeis/img/display-buffer-modes.svg)
*Три схеми організації пам'яті дисплея: одинарний частковий буфер із блокуванням процесора, подвійний частковий буфер (Ping-Pong) із паралельною роботою CPU і DMA, та повнорозмірний подвійний фреймбуфер у зовнішній пам'яті SDRAM.*

### 1. Одинарний частковий буфер (Single Partial Buffer)

У цьому режимі в SRAM виділяється один блок пам'яті, що вміщує смугу екрана (наприклад, 480×32 пікселі при загальній висоті 320 рядків). Обсяг пам'яті становить:

```
Розмір_буфера = 480 × 32 × 2 байти = 30 720 байтів (30 КБ)
```

Конвеєр працює суворо послідовно:
1. Процесор малює пікселі першої брудної смуги в буфер.
2. Рушій викликає функцію скидання (`flush_cb`), запускаючи передачу по SPI або 8080-інтерфейсу.
3. Процесор переходить у стан очікування або блокується, поки вся смуга не надійде в контролер дисплея.
4. Тільки після повного завершення передачі процесор береться за розрахунок наступної смуги.

Головний недолік схеми — простої обчислювального ядра. Якщо передача смуги по SPI на частоті 40 МГц триває 6,1 мс, а її рендеринг займає 3,5 мс, загальний час обробки смуги становить 9,6 мс. Процесор завантажений лише на 36% часу, але решту 64% вимушено чекає завершення роботи шини.

### 2. Подвійний частковий буфер (Double Partial Buffer / Ping-Pong)

Щоб ліквідувати простої процесора, у внутрішньому ОЗП виділяють два окремі буфери (`buf1` і `buf2`) однакового розміру:

```
Загальна_пам'ять = 2 × (480 × 32 × 2) = 61 440 байтів (60 КБ)
```

Робота організується за принципом чергування (пінг-понг):
- Поки контролер DMA спустошує `buf1`, самостійно пересилаючи байти через SPI у контролер екрана, процесор паралельно прораховує наступну ділянку інтерфейсу в `buf2`.
- Коли DMA завершує передачу, обробник переривання викликає `lv_disp_flush_ready()`, перемикаючи ролі буферів: `buf2` стає на передачу в DMA, а `buf1` звільняється для нового рендерингу CPU.

Час формування смуги стає рівним не сумі, а максимуму з двох тривалостей: `max(T_render, T_transfer)`. Якщо `T_transfer` = 6,1 мс, а `T_render` = 3,5 мс, кадр оновлюється кожні 6,1 мс замість 9,6 мс — продуктивність зростає майже на 60% без підключення додаткових зовнішніх мікросхем пам'яті.

### 3. Повний подвійний фреймбуфер і прямий режим (Direct Mode)

Якщо мікроконтролер має апаратний контролер паралельного дисплея (наприклад, STM32 LTDC — LCD-TFT Display Controller або ESP32 RGB LCD) та зовнішню мікросхему пам'яті SDRAM/PSRAM, використовують два повнорозмірні фреймбуфери розміром 480×320×2 = 300 КБ кожен.

- **Active / Front Buffer**: з цього буфера апаратний контролер LTDC неперервно генерує синхросигнали (DOTCLK, HSYNC, VSYNC) та сканує пікселі на екран.
- **Draw / Back Buffer**: у цей буфер графічний рушій рендерить нові кадри.

У звичайному режимі подвійного фреймбуфера для кожного кадру доводиться повністю копіювати вміст із одного фреймбуфера в інший. LVGL пропонує **Direct Mode** (прямий режим): рушій малює лише змінені прямокутники безпосередньо в неактивний фреймбуфер, а перед перемиканням копіює тільки ці оновлені області у зворотний буфер, зменшуючи навантаження на шину пам'яті в рази.

> 🔧 **Навіщо це.**
> У портативних приладах із живленням від акумулятора кожен додатковий чип пам'яті додає 30–80 мА струму споживання у динамічному режимі. Подвійний частковий буфер на 1/10 екрана у внутрішньому SRAM дозволяє отримати 30–45 кадрів на секунду взагалі без зовнішньої SDRAM, зберігаючи струм споживання мікроконтролера в межах 20–40 мА.

## Конвеєр рендерингу LVGL: від зміни значення до `flush_cb`

Рендеринг у LVGL побудований на концепції **недійсних областей** (англ. *invalidated areas*) та відкладеної перерисовки (англ. *deferred rendering*). Жодна зміна стану кнопки, повзунка чи тексту не викликає негайного малювання на екрані.

![Конвеєр формування кадру в LVGL: від інвалідації до передачі через DMA](/root/eng/sf-devices/hrafichnyi-interfeis/img/rendering-pipeline.svg)
*Послідовність етапів графічного конвеєра: від виклику API інвалідації до пошарового растрування, поділу на смуги під буфер SRAM та підтвердження завершення DMA.*

### Анатомія дерева віджетів та інвалідація

Усі візуальні елементи в LVGL організовані в ієрархічне дерево об'єктів `lv_obj_t`. Кожен об'єкт має координати прямокутника на екрані (`coords` типу `lv_area_t` з полями `x1, y1, x2, y2`), покажчик на батьківський об'єкт, список дочірніх елементів і набір стилів.

Коли прикладний код змінює стан віджета — наприклад, викликає `lv_slider_set_value(slider, 75, LV_ANIM_OFF)`:
1. Віджет перераховує свої внутрішні розміри (положення повзунка).
2. Віджет викликає внутрішню функцію `lv_obj_invalidate(obj)`.
3. Координати об'єкта додаються до списку брудних прямокутників поточного дисплея (`disp->inv_areas`).

### Оптимізація та злиття областей (Dirty Area Joining)

Якщо на екрані одночасно змінилося кілька дрібних елементів (наприклад, три сусідні іконки стану), створення окремої транзакції на кожен дрібний прямокутник призвело б до величезних накладних витрат на передачу команд адресації вікна контролера дисплея.

Перед початком малювання LVGL виконує оптимізацію списку `inv_areas`:
- Перевіряє взаємне перекриття прямокутників.
- Якщо дві області перетинаються або розташовані впритул одна до одної, рушій об'єднує їх у спільний обмежувальний прямокутник (bounding box) за допомогою функції `_lv_area_join()`.
- Якщо результуючий прямокутник за площею перевищує розмір буфера рендерингу, рушій автоматично нарізає його на горизонтальні або вертикальні смуги, кожна з яких точно вміщується у виділений `draw_buf`.

### Головний цикл: `lv_timer_handler()` та пошаровий растр

Рендеринг запускається періодично, коли операційна система викликає функцію `lv_timer_handler()`. Усередині рушія спрацьовує системний таймер оновлення дисплея `_lv_disp_refr_timer()`:

1. **Ініціалізація смуги**: рушій обирає перший вільний буфер (`draw_buf->buf_act`) і встановлює поточну область `draw_buf->area`.
2. **Пошаровий обхід дерева об'єктів**:
   - Дерево рекурсивно обходиться знизу вгору (від фону до верхніх віджетів).
   - Для кожного об'єкта обчислюється перетин його прямокутника з поточною смугою: `_lv_area_intersect(&clip_area, &obj->coords, &draw_buf->area)`. Якщо перетину немає, об'єкт повністю відсікається від рендерингу (Clipping).
   - Якщо об'єкт потрапляє в смугу, послідовно малюються його візуальні шари:
     - Фоновий прямокутник із радіусом закруглення кутів (`draw_bg`).
     - Межі та внутрішні рамки (`draw_border`).
     - Тіні з розмиттям за Гаусом (`draw_shadow`).
     - Растрові зображення та іконки (`draw_img`).
     - Текстові написи за матрицями гліфів шрифтів (`draw_label`).
3. **Виклик драйвера**: коли вся смуга заповнена пікселями, рушій викликає зареєстровану функцію `disp_drv.flush_cb(disp_drv, &area, color_map)`.
4. **Очікування готовності**: рушій блокує повторне використання поточного буфера, доки не отримає сигнал `lv_disp_flush_ready()`.

Специфікація структур даних, дескрипторів та сигнатур функцій зворотного виклику детально наведена у вставці [Довідник API портування LVGL та структур даних](root:sf-devices/hrafichnyi-interfeis/api-lvgl-porting.md).

## Апаратне прискорення 2D: DMA2D (Chrom-ART) та розвантаження CPU

У типових графічних інтерфейсах значну частку часу процесора забирають дві операції: заливка великих областей однорідним кольором (очищення фону, підкладки карток) та **альфа-змішування** (англ. *alpha blending*) для прозорих шарів, антиаліасингу шрифтів і тіней.

### Обчислювальна ціна програмного блітингу

Математична формула накладання напівпрозорого пікселя переднього плану (`src`) на піксель фону (`dst`) з коефіцієнтом прозорості `alpha` ∈ [0..255] виглядає так:

```
dst_r = (src_r · alpha + dst_r · (255 - alpha)) / 255
dst_g = (src_g · alpha + dst_g · (255 - alpha)) / 255
dst_b = (src_b · alpha + dst_b · (255 - alpha)) / 255
```

Для 16-бітного формату RGB565 процесор мусить:
1. Розпакувати 16-бітне число на три окремі канали R (5 біт), G (6 біт), B (5 біт) за допомогою бітових масок і зсувів.
2. Виконати три операції множення та три операції додавання/зсуву.
3. Запакувати результат назад у 16-бітне значення `(R << 11) | (G << 5) | B`.

Для прямокутника розміром 200×100 пікселів це 20 000 пікселів, що вимагає близько 600 000 машинних інструкцій. На процесорі Cortex-M4 із частотою 168 МГц одне лише накладання такої напівпрозорої плашки займає 3,5–4 мілісекунди чистого процесорного часу.

### Архітектура DMA2D (Chrom-ART Accelerator)

Мікроконтролери сімейства STM32 (лінійки STM32F4/F7/H7) містять спеціалізований апаратний 2D-рушій — **DMA2D** (Chrom-ART Accelerator). Це автономний контролер прямого доступу до пам'яті з вбудованим блоком перетворення форматів та апаратним змішувачем кольорів.

![Апаратний прискорювач 2D-графіки (STM32 Chrom-ART / DMA2D)](/root/eng/sf-devices/hrafichnyi-interfeis/img/dma2d-chrom-art.svg)
*Три апаратні режими DMA2D (R2M, M2M+PFC, M2M Blend) та ланцюг забезпечення узгодженості кешу даних L1 D-Cache між ядром процесора і графічним прискорювачем.*

DMA2D підтримує три ключові режими роботи:

1. **Регістр-у-пам'ять (Register-to-Memory, R2M)**:
   - Значення кольору записується у вихідний регістр кольору DMA2D (`DMA2D->OCOLR`).
   - Прискорювач заповнює прямокутну область у пам'яті заданим кольором на максимальній швидкості системної шини (1 піксель за такт шини).
   - Заливка області 320×240 пікселів триває менше 0,5 мс без участі процесора.

2. **Пам'ять-у-пам'ять із конвертацією формату (Memory-to-Memory with PFC)**:
   - Вхідні зображення (наприклад, іконки у Flash-пам'яті) можуть зберігатися у форматі ARGB8888, RGB888 або індексованій палітрі L8/AL44.
   - DMA2D читає вихідний масив, апаратно перетворює його у цільовий формат дисплея (RGB565) і записує у буфер рендерингу.

3. **Пам'ять-у-пам'ять зі змішуванням (Memory-to-Memory with Blending)**:
   - Прискорювач одночасно читає два джерела пам'яті: передній план (Foreground Layer) та фоновий шар (Background Layer).
   - Апаратний конвеєр перемножує канали на альфа-значення за один такт і записує змішаний піксель за адресою вихідного буфера.

При використанні LVGL інтеграція з DMA2D вмикається макросом `LV_USE_GPU_STM32_DMA2D 1` у файлі `lv_conf.h`. Рушій замінює програмні цикли заповнення прямокутників та блітингу зображень на прямий запуск транзакцій DMA2D, знижуючи завантаження CPU при складних анімаціях із 95% до 15–20%.

### Архітектурна пастка Cortex-M7: узгодженість кешу даних (D-Cache)

На високопродуктивних мікроконтролерах із ядрами Cortex-M7 (STM32F7, STM32H7) та Cortex-M33 увімкнено дворівневий кеш: кеш інструкцій (I-Cache) та кеш даних (L1 D-Cache).

Кеш даних працює за політикою відкладеного запису (**Write-Back**): коли процесор малює пікселі в буфер, нові значення осідають у швидкому L1-кеші, а у фізичну пам'ять SRAM ще не скидаються. Якщо після цього запустити апаратний блок DMA або DMA2D, він звернеться безпосередньо до шини пам'яті SRAM і прочитає застарілі дані («сміття»).

Для запобігання артефактам діють два обов'язкові правила:
1. **Вирівнювання пам'яті**: графічні буфери обов'язково оголошуються з вирівнюванням за розміром рядка кешу (32 байти): `alignas(32)` або `__attribute__((aligned(32)))`.
2. **Скидання кешу (Clean)**: перед кожним запуском передачі DMA викликається функція очищення кешу для адреси та довжини буфера `SCB_CleanDCache_by_Addr((uint32_t*)color_p, byte_count)` (або CMSIS-інтринсик).
3. **Інвалідація кешу (Invalidate)**: якщо DMA2D записує результат у пам'ять, яку процесор пізніше читатиме, кеш за цими адресами інвалідується через `SCB_InvalidateDCache_by_Addr((uint32_t*)color_p, byte_count)`.

## Сенсорне введення: архітектура InDev та обробка дотиків

Графічний інтерфейс реагує на дії користувача через підсистему пристроїв введення (InDev — Input Device).

![Конвеєр обробки сенсорного введення (Touch Driver InDev) в LVGL](/root/eng/sf-devices/hrafichnyi-interfeis/img/touch-indev-flow.svg)
*Конвеєр реєстрації дотиків: апаратне зчитування по I2C, калібрування і фільтрація координат, генерація подій та диспетчеризація до віджета.*

### Принцип роботи сенсорного контролера

Ємнісні сенсорні панелі (наприклад, на базі контролерів FocalTech FT6206, Hynitron CST816 або Goodix GT911) взаємодіють з мікроконтролером через шину I2C та дискретну лінію переривання `TOUCH_INT` (IRQ).

При торканні пальцем скла:
1. Контролер сенсора виявляє зміну ємності матриці електродів, обчислює координати `(X, Y)` і переводить лінію `TOUCH_INT` у низький логічний рівень.
2. Драйвер InDev мікроконтролера у функції `read_cb` зчитує по I2C блок регістрів зі значеннями координат та кількістю точок дотику.
3. Драйвер заповнює структуру `lv_indev_data_t`:
   - `data->point.x = raw_x;`
   - `data->point.y = raw_y;`
   - `data->state = is_touched ? LV_INDEV_STATE_PR : LV_INDEV_STATE_REL;`

### Нормалізація, фільтрація та калібрування

Сирі координати із сенсорної матриці майже ніколи не збігаються з піксельною сіткою дисплея. У функції зворотного виклику здійснюється:
- **Мапування орієнтації (Orientation Mapping)**: обмін осей `X ↔ Y` або інверсія значень при повороті дисплея на 90°, 180° або 270°.
- **Масштабування діапазону**: якщо роздільна здатність сенсора 4096×4096, а дисплея — 320×240, координати перераховуються лінійною інтерполяцією.
- **Фільтрація шумів**: через паразитні наведенки від імпульсних стабілізаторів живлення сенсор може генерувати поодинокі відхилення координат. Для плавного перетягування (Drag/Scroll) застосовують просте ковзне середнє або медіанний фільтр по трьох останніх вибірках.

### Диспетчеризація подій та жести

LVGL опитує зареєстрований `read_cb` кожні 30 мс (налаштовується параметром `LV_INDEV_DEF_READ_PERIOD`). На основі зміни станів рушій керує внутрішньою машиною станів:

- **LV_EVENT_PRESSED**: курсор щойно торкнувся віджета. Віджет переходить у стан `LV_STATE_PRESSED` (кнопка змінює колір або просідає).
- **LV_EVENT_PRESSING**: палець утримується на екрані.
- **LV_EVENT_SCROLL_BEGIN / SCROLL**: вектор зсуву між послідовними точками `(ΔX, ΔY)` перевищив поріг `scroll_limit` (за замовчуванням 3 пікселі). Батьківський контейнер перехоплює подію і починає плавне прокручування списку.
- **LV_EVENT_RELEASED**: палець відірвано від екрана.
- **LV_EVENT_CLICKED**: дотик і відпускання відбулися в межах того самого віджета без зміщення на скролінг.

## Керування пам'яттю віджетів: алокатор TLSF

Окрім буферів рендерингу, графічний інтерфейс динамічно створює та видаляє сотні дрібних об'єктів: вузли дерева віджетів `lv_obj_t`, структури стилів, дескриптори анімацій та елементи черг подій.

Використання стандартного системного алокатора `malloc()` / `free()` з бібліотеки C на вбудованих системах призводить до важкої фрагментації оперативної пам'яті:
- Через чергування дрібних виділень пам'яті (16–64 байти на стиль) та більших блоків (масиви точок графіків) суцільний простір ОЗП розбивається на ізольовані фрагменти.
- Через кілька годин активної роботи пристрою `malloc()` повертає `NULL`, хоча сумарний обсяг вільної пам'яті може становити десятки кілобайтів.

LVGL вирішує проблему фрагментації за допомогою власного алокатора **TLSF** (англ. *Two-Level Segregated Fit*), який активується у файлі `lv_conf.h` через параметр `LV_MEM_CUSTOM 0`:
1. **Фіксований пул пам'яті**: графічне ядро резервує суцільний статичний масив розміром `LV_MEM_SIZE` (типово 32–64 КБ).
2. **Дворівневий пошук блоків**: вільні блоки пам'яті категоризуються за двома рівнями логарифмічних списків розмірів (First-Level і Second-Level).
3. **Гарантований час O(1)**: операції виділення (`lv_mem_alloc`) та звільнення (`lv_mem_free`) виконуються за строго фіксовану кількість тактів процесора незалежно від кількості активних об'єктів у системі.
4. **Миттєве злиття суміжних блоків**: при виклику `lv_mem_free` алокатор автоматично об'єднує сусідні вільні ділянки, запобігаючи накопиченню мікрофрагментів.

## Енергозбереження та динамічне керування частотою кадрів

У пристроях з автономним живленням безперервний рендеринг екрана з частотою 60 Гц швидко виснажує батарею. Графічний рушій мікроконтролера використовує стратегію **подієвого оновлення** (англ. *event-driven rendering*):

1. **Детекція статичного стану**: якщо в поточному такті жоден віджет не інвалідовано і немає активних анімацій, функція `_lv_disp_refr_timer()` не виконує жодних обчислень і не чіпає контролер DMA.
2. **Динамічний період таймера**: функція `lv_timer_handler()` повертає час у мілісекундах до моменту спрацьовування наступного запланованого таймера або анімації.
3. **Глибокий сон мікроконтролера (Low-Power Sleep)**:
   - Графічна задача FreeRTOS викликає `uint32_t next_ms = lv_timer_handler()`.
   - Задача блокується на семафорі або засинає через `vTaskDelay(pdMS_TO_TICKS(next_ms))`.
   - Ядро процесора переводиться в режим `WFI` (Wait For Interrupt / Sleep Mode), вимикаючи тактування ядра та знижуючи струм споживання з 30 мА до кількох мікроампер.
4. **Миттєве пробудження за перериванням**: коли користувач торкається сенсорного скла, лінія `TOUCH_INT` генерує зовнішнє переривання EXTI. Обробник переривання надсилає повідомлення задачі GUI через `xTaskNotifyFromISR()`, негайно повертаючи систему до повної частоти 60 FPS для обробки жесту.

## Бюджет кадру, частота оновлення (FPS) та боротьба з тирингом

Частота оновлення інтерфейсу (FPS — Frames Per Second) обмежена двома фізичними чинниками: часом рендерингу пікселів у пам'яті мікроконтролера (`T_render`) та пропускною здатністю апаратної шини (`T_bus`).

### Розрахунок граничної швидкості шини

Для екрана 320×240 (RGB565, 153 600 байтів на кадр) час передачі одного повного кадру на різних інтерфейсах становить:

1. **Стандартний SPI на частоті 40 МГц**:
   ```
   Пропускна_здатність = 40 000 000 / 8 = 5 000 000 байтів/с (4,76 МБ/с)
   Час_кадру = 153 600 / 5 000 000 = 0,0307 с = 30,7 мс
   Максимальний_FPS = 1 / 0,0307 ≈ 32,5 FPS (при 100% оновленні площі)
   ```
2. **Quad-SPI (QSPI 4-bit) на частоті 40 МГц**:
   ```
   Пропускна_здатність = (40 000 000 × 4) / 8 = 20 000 000 байтів/с (19,07 МБ/с)
   Час_кадру = 153 600 / 20 000 000 = 7,68 мс
   Максимальний_FPS = 1 / 0,00768 ≈ 130 FPS
   ```
3. **Паралельна 16-бітна шина FMC на частоті 60 МГц**:
   ```
   Пропускна_здатність = 60 000 000 × 2 байти = 120 000 000 байтів/с
   Час_кадру = 153 600 / 120 000 000 = 1,28 мс
   Максимальний_FPS = 1 / 0,00128 ≈ 780 FPS
   ```

Оскільки LVGL оновлює лише брудні ділянки, реальний час передачі пропорційний площі змін. Якщо на екрані рухається повзунок площею 100×30 пікселів (6000 байтів), його передача по SPI 40 МГц триває лише 1,2 мс, що дає миттєву швидкість реакції інтерфейсу у 60 FPS навіть на повільній шині.

### Синхронізація з лінією TE (Tearing Effect)

Коли контролер дисплея (наприклад, ST7789) неперервно зчитує свою внутрішню грам-пам'ять (GRAM) і регенерує рядки LCD-матриці з частотою 60 Гц, а мікроконтролер одночасно записує нові пікселі в ту саму пам'ять, виникає ефект **розриву кадру** (англ. *tearing*). На екрані з'являється горизонтальна лінія розриву, де верхня частина зображення належить новому кадру, а нижня — попередньому.

Більшість контролерів дисплеїв мають вихідний пін **TE (Tearing Effect)**. Контролер виставляє високий рівень на цій лінії під час вертикального зворотного ходу променя (V-Blanking), коли сканування матриці завершено, і промінь повертається до верхнього лівого кута.

Для усунення тирингу лінію TE підключають до піна зовнішнього переривання (EXTI) мікроконтролера. Запуск передачі смуг через DMA прив'язують до фронту сигналу TE, гарантуючи, що запис нових пікселів ніколи не наздожене лінію зчитування матриці.

Повний інженерний приклад налаштування підсистеми відображення з неблокуючим DMA, синхронізацією FreeRTOS та кешуванням наведено у вставці [Практична реалізація подвійної буферизації та DMA-драйвера](root:sf-devices/hrafichnyi-interfeis/proj-double-buffer-dma.md).

## Практичний каркас конфігурації та запуску LVGL

Нижче наведено базовий шаблон ініціалізації графічного середовища, реєстрації подвійного буфера та запуску обробки подій мовами C та C++.

```c
#include "lvgl.h"

#define DISP_HOR_RES 480
#define DISP_VER_RES 320
#define BUF_LINES    32

static lv_color_t __attribute__((aligned(32))) buf1[DISP_HOR_RES * BUF_LINES];
static lv_color_t __attribute__((aligned(32))) buf2[DISP_HOR_RES * BUF_LINES];

static lv_disp_draw_buf_t draw_buf;
static lv_disp_drv_t      disp_drv;

extern void my_lcd_flush_dma(lv_disp_drv_t *drv, const lv_area_t *area, lv_color_t *color_p);

void app_gui_setup(void)
{
    lv_init();

    /* 1. Ініціалізація структури подвійного буфера */
    lv_disp_draw_buf_init(&draw_buf, buf1, buf2, DISP_HOR_RES * BUF_LINES);

    /* 2. Налаштування та реєстрація драйвера дисплея */
    lv_disp_drv_init(&disp_drv);
    disp_drv.hor_res  = DISP_HOR_RES;
    disp_drv.ver_res  = DISP_VER_RES;
    disp_drv.flush_cb = my_lcd_flush_dma;
    disp_drv.draw_buf = &draw_buf;
    lv_disp_drv_register(&disp_drv);

    /* 3. Створення базових графічних об'єктів */
    lv_obj_t *btn = lv_btn_create(lv_scr_act());
    lv_obj_align(btn, LV_ALIGN_CENTER, 0, 0);

    lv_obj_t *label = lv_label_create(btn);
    lv_label_set_text(label, "Старт системи");
}
```

```cpp
#include "lvgl.h"
#include <span>
#include <memory>

namespace app::ui {

template <size_t HorRes, size_t VerRes, size_t Lines>
class GraphicsSystem {
public:
    static constexpr size_t kBufferSize = HorRes * Lines;

    GraphicsSystem() = default;

    void initialize(void (*flushCallback)(lv_disp_drv_t*, const lv_area_t*, lv_color_t*))
    {
        lv_init();

        lv_disp_draw_buf_init(&draw_buf_, buffer1_, buffer2_, kBufferSize);

        lv_disp_drv_init(&disp_drv_);
        disp_drv_.hor_res   = static_cast<lv_coord_t>(HorRes);
        disp_drv_.ver_res   = static_cast<lv_coord_t>(VerRes);
        disp_drv_.flush_cb  = flushCallback;
        disp_drv_.draw_buf  = &draw_buf_;
        disp_drv_.user_data = this;

        lv_disp_drv_register(&disp_drv_);

        buildUserInterface();
    }

    void process()
    {
        lv_timer_handler();
    }

private:
    alignas(32) lv_color_t buffer1_[kBufferSize]{};
    alignas(32) lv_color_t buffer2_[kBufferSize]{};

    lv_disp_draw_buf_t draw_buf_{};
    lv_disp_drv_t      disp_drv_{};

    void buildUserInterface()
    {
        lv_obj_t* btn = lv_btn_create(lv_scr_act());
        lv_obj_align(btn, LV_ALIGN_CENTER, 0, 0);

        lv_obj_t* label = lv_label_create(btn);
        lv_label_set_text(label, "Старт системи");
    }
};

} // namespace app::ui
```
