Один виклик `printf("Angle: %f, Current: %d\r\n", angle, current)` усередині кілогерцового циклу стабілізації безколекторного мотора здатний перетворити працюючий пристрій на некерований генератор аварій. Доданий для спостереження рядок не просто виводить текст: він вимагає завантаження математичного рушія розбору десяткових дробів, виділяє сотні байтів під локальні буфери на стеку і примушує процесор крутитися в глухому циклі очікування апаратного регістра передавача. На стандартній швидкості 115200 бод відправка такого повідомлення довжиною в 40 символів краде в ядра майже 3.5 мілісекунди. За цей час мотор встигає тричі пропустити крок оновлення ШІМ, викликаючи фазовий зрив і [апаратне виключення HardFault](root:sf-devices/hardfault).

Текстове логування у вбудованих системах — це фундаментальний інструмент інтроспекції, але його ціна принципово відрізняється від серверного програмування. На мікроконтролері з 32 КБ Flash та 8 КБ SRAM стандартний підхід стандартної бібліотеки мови C споживає ресурси так, ніби під ним працює повноцінна операційна система з віртуальною пам'яттю та гігагерцовим процесором.

## Від виклику printf до заліза: механізм перенаправлення

Коли програма викликає `printf()`, компілятор звертається до стандартної бібліотеки мови C (`libc`, найчастіше `newlib` або `picolibc` у збірках під ARM та RISC-V). У настільних операційних системах ця бібліотека зрештою здійснює системний виклик ядра ОС (наприклад, `write(1, buf, len)` у Linux). Проте в мікроконтролері без операційної системи (bare-metal) ядра ОС не існує, тому бібліотека вимагає реалізації **шару системних заглушок** (англ. *syscall retargeting*).

Ланцюг виконання проходить кілька чітко розмежованих стадій:

1. **Форматування рядка.** Функція `printf()` приймає змінну кількість аргументів (англ. *variadic arguments*) і передає їх у внутрішній рушій `vfprintf()`. Цей блок аналізує рядок форматування символ за символом, виявляє специфікатори `%d`, `%s`, `%x`, `%f`, перетворює двійкові числа у текстове представлення згідно з прапорцями ширини та точності й формує потік вихідних байтів.
2. **Буферизація потоку.** Бібліотека оперує структурою стандартного потоку виводу `stdout` (тип `FILE`). Залежно від налаштувань використовується рядкова буферизація (скидання байтів лише після зустрічі `\n`), блокова або повна відсутність буферизації.
3. **Низькорівневий виклик.** Коли буфер готовий до скидання, бібліотека викликає платформозалежну функцію. У середовищі `newlib` (GCC) це функція `_write()`, а в середовищі Keil MicroLib або IAR — посимвольна функція `fputc()`.
4. **Апаратний драйвер.** Функція `_write()` перенаправляє байти у конкретний фізичний інтерфейс: апаратний передавач UART, модуль трасування ARM ITM або дескриптор пам'яті SEGGER RTT.

![Ланцюг викликів printf: від коду застосунку через vfprintf та системний виклик _write до фізичних інтерфейсів](/root/eng/sf-devices/printf-na-prystroi/img/printf-retarget-chain.svg)

*Ланцюг перенаправлення стандартного виводу: високорівневий виклик транслюється бібліотекою форматування у виклик _write, який спрямовує байти у вибраний апаратний транспорт.*

Нижче наведено базову реалізацію системного перенаправлення `_write()` для набору інструментів GCC/Newlib.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>

/* Оголошення апаратних функцій конкретного чіпа */
extern void uart_send_byte_blocking(uint8_t ch);
extern void itm_send_byte(uint8_t ch);

/* Перевизначення системного виклику newlib libc */
int _write(int fd, const char *buf, int len) {
    /* Дескриптори 1 (stdout) та 2 (stderr) спрямовуємо в апаратний порт */
    if (fd == 1 || fd == 2) {
        for (int i = 0; i < len; ++i) {
            /* Автоматична заміна \n на послідовність \r\n для терміналів */
            if (buf[i] == '\n') {
                uart_send_byte_blocking((uint8_t)'\r');
            }
            uart_send_byte_blocking((uint8_t)buf[i]);
        }
        return len;
    }
    return -1;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <string_view>

extern "C" void uart_send_byte_blocking(uint8_t ch);
extern "C" void itm_send_byte(uint8_t ch);

/* C++ обгортка над системним викликом із використанням std::span */
extern "C" int _write(int fd, const char *buf, int len) {
    if ((fd == 1 || fd == 2) && buf != nullptr && len > 0) {
        std::span<const char> data(buf, static_cast<size_t>(len));
        for (const char ch : data) {
            if (ch == '\n') {
                uart_send_byte_blocking(static_cast<uint8_t>('\r'));
            }
            uart_send_byte_blocking(static_cast<uint8_t>(ch));
        }
        return len;
    }
    return -1;
}
```
:::

> 🔧 **Навіщо це.** Перевизначення `_write()` дозволяє використовувати стандартні функції `printf()`, `puts()`, `putchar()` або `std::cout` без зміни коду застосунку: перемикання з фізичного UART на налагоджувальний інтерфейс SWD змінює рівно один файл ініціалізації системи введення-виведення.

## Фізичні канали доставки: UART, SWO та RTT

Вибір фізичного носія для текстового потоку визначає необхідну кількість виводів чіпа, швидкість передачі та апаратну залежність від налагоджувального обладнання.

**Апаратний UART (послідовний порт).** Найпоширеніший спосіб. Вимагає одного цифрового виводу GPIO (TX) та зовнішнього перетворювача USB-UART (FT232, CH340, CP2102) для підключення до комп'ютера. Головна перевага — повна незалежність від налагоджувача: пристрій може виводити логи у польових умовах на будь-який реєстратор чи термінал. Недолік — низька швидкість та високі часові накладні витрати ядра на передачу кожного байта.

**ARM ITM / SWO (Instrumentation Trace Macrocell / Single Wire Output).** Апаратний блок ядра Cortex-M3/M4/M7/M33. Дозволяє програмі записувати байти безпосередньо в спеціальний 32-бітний регістр пам'яті `ITM->PORT[0]`. Апаратний контролер трасування всередині чіпа самостійно серіалізує ці байти та видає їх на окремий фізичний вивід SWO через апаратний FIFO-буфер.
- Запис одного символу займає рівно один такт процесора: `ITM_SendChar(ch)`.
- Якщо апаратний буфер ITM переповнений, ядро або очікує звільнення, або символ відкидається апаратно без зупинки CPU.
- Вимагає підключеного апаратного налагоджувача (J-Link, ST-Link v3, CMSIS-DAP v2), здатного декодувати манчестерське кодування або UART-подібний протокол виводу SWO.

:::tabs
```c
#include <stdint.h>

/* Базові адреси CMSIS для прямого запису в регістр ITM Stimulus Port 0 */
#define ITM_PORT0_U8  (*(volatile uint8_t*)0xE0000000UL)
#define ITM_PORT0_U32 (*(volatile uint32_t*)0xE0000000UL)
#define ITM_TER       (*(volatile uint32_t*)0xE0000E00UL)
#define ITM_TCR       (*(volatile uint32_t*)0xE0000E80UL)
#define DEMCR         (*(volatile uint32_t*)0xE000EDFCUL)

void itm_send_char_fast(uint8_t ch) {
    /* Перевіряємо, чи увімкнено модуль трасування налагоджувачем */
    if ((DEMCR & (1UL << 24)) && (ITM_TCR & (1UL << 0)) && (ITM_TER & (1UL << 0))) {
        /* Очікуємо готовності апаратного FIFO буфера порту 0 */
        while (ITM_PORT0_U32 == 0UL) {
            /* Пауза у разі заповнення апаратного буфера */
        }
        ITM_PORT0_U8 = ch;
    }
}
```
```cpp
#include <cstdint>

namespace itm_trace {
    inline volatile uint8_t& port0_u8() noexcept {
        return *reinterpret_cast<volatile uint8_t*>(0xE0000000UL);
    }
    inline volatile uint32_t& port0_u32() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(0xE0000000UL);
    }
    inline volatile uint32_t& ter() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(0xE0000E00UL);
    }
    inline volatile uint32_t& tcr() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(0xE0000E80UL);
    }
    inline volatile uint32_t& demcr() noexcept {
        return *reinterpret_cast<volatile uint32_t*>(0xE000EDFCUL);
    }

    inline void send_char(uint8_t ch) noexcept {
        if ((demcr() & (1UL << 24)) && (tcr() & (1UL << 0)) && (ter() & (1UL << 0))) {
            while (port0_u32() == 0UL) {
                // Очікування готовності апаратного FIFO
            }
            port0_u8() = ch;
        }
    }
}
```
:::

**SEGGER RTT (Real-Time Transfer).** Технологія нульових часових втрат. Текстовий рядок записується програмою у виділений кільцевий буфер, розміщений у звичайній пам'яті SRAM мікроконтролера. Апаратний зонд налагоджувача (підключений через 2 дроти [інтерфейсу SWD](root:sys-ide/swd-jtag-internals)) постійно опитує оперативну пам'ять чіпа через апаратну шину налагодження AHB-AP у фоновому режимі. Завдяки прямому доступу до шини мікроконтролера передача даних взагалі не потребує участі процесорного ядра і не витрачає жодного такту на очікування порту.

## Прихована ціна стандартного printf

Використання повнофункціонального `printf()` зі стандартної бібліотеки тягне за собою три фундаментальні проблеми: надмірне споживання пам'яті Flash, блокування виконання коду в реальному часі та ризик переповнення стека.

### 1. Розмір коду у Flash (15–30 КБ) та конвенція викликів AAPCS

Стандарт C вимагає від `printf` повної підтримки всіх специфікаторів: позиційних аргументів, локалей, динамічного вирівнювання ширини, шістнадцяткових чисел та чисел з плаваючою комою подвійної точності (`double`).

Найбільшу частку Flash забирає підтримка чисел із плаваючою комою (`%f`, `%e`, `%g`). Алгоритми точного перетворення двійкового формату IEEE 754 у десятковий дріб без втрати точності (такі як Dragon4 або Grisu3) вимагають операцій над 64-бітними та 128-бітними цілими числами, великих таблиць степенів десятки та складних циклів округлення.

Існує ще одна підступна деталь стандарту C: **правило підвищення типів у варіативних функціях** (англ. *default argument promotion*). За стандартом, будь-який аргумент типу `float` (32 біти), переданий у функцію зі змінною кількістю аргументів на кшталт `printf()`, автоматично підвищується компілятором до `double` (64 біти). 

Це означає, що навіть якщо мікроконтролер має апаратний математичний співпроцесор FPU для 32-бітних чисел (Cortex-M4F або Cortex-M7 з одинарною точністю), виклик `printf("%f", float_val)` примушує лінкер підтягнути повну програмну бібліотеку 64-бітної емуляції плаваючої коми! Цей рудимент стандарту коштує від 12 до 25 КБ пам'яті програм Flash.

```
+-------------------------------------------------------------+
| Звичайна програма керування GPIO та датчиком: ~2.5 КБ Flash  |
+-------------------------------------------------------------+
                              +
+-------------------------------------------------------------+
| Перший виклик printf("%d"):    +12 КБ Flash (newlib-nano)   |
| Перший виклик printf("%f"):    +18..28 КБ Flash (newlib)    |
+-------------------------------------------------------------+
```

Сучасна бібліотека `picolibc` (розроблена Кейтом Пакардом) частково вирішує цю проблему: завдяки заміні застарілого парсера на сучасний цілочисельний алгоритм Ryu розмір коду підтримки float вдалося зменшити до ~4.5 КБ Flash. Проте у традиційному тулчейні `arm-none-eabi-gcc` за замовчуванням лінкується класична `newlib`.

### 2. Блокування ядра та похибка швидкості UART

Розглянемо фізику передачі даних через асинхронний передавач UART у стандартній конфігурації 8N1 (1 старт-біт, 8 бітів даних, 1 стоп-біт = 10 бітів на кожен байт).

Розрахуємо тривалість передачі одного байта на швидкості 115200 бод:

```
T_bit = 1 / 115200 с ≈ 8.6806 мкс
T_byte = 10 · T_bit
       = 10 · 8.6806 мкс
       ≈ 86.8 мкс                      [час передачі 1 байта UART]
```

Якщо програма логує типовий рядок стану:
`"STATUS: Temp=24.5C, Voltage=12.3V, State=RUNNING\r\n"` (довжина 48 байтів).

```
T_total = 48 · 86.8 мкс
        = 4166.4 мкс
        ≈ 4.17 мс                      [час передачі рядка з 48 байтів]
```

Оцінимо кількість втрачених тактів процесора на частоті 80 МГц (STM32, ESP32, RP2040):

```
N_cycles = 4.1664 мс · 80 000 000 Гц
         = 333 312 тактів              [ядро крутиться у циклі polling]
```

Понад 330 тисяч тактів процесор нічого не робить, окрім побайтового опитування біта готовності передавача (`USART_ISR_TXE`). Якщо система керує джерелом живлення, інвертором або читає дані через [кадр UART](root:com-devices/uart-frame) із зовнішнього модуля, така затримка призводить до переповнення вхідних апаратних буферів UART/SPI (Overrun Error), дрейфу фази програмних таймерів та зриву дедлайнів обробки датчиків.

Крім того, на високих швидкостях (наприклад, 921600 або 2000000 бод) апаратний дільник частоти UART (`BRR` — Baud Rate Register) може вносити суттєву похибку. Апаратна формула розрахунку коефіцієнта ділення для режиму дискретизації 16x (OVER8 = 0) має вигляд:

```
USARTDIV = f_CK / (16 · Baud)
```

Якщо тактова частота периферійної шини `f_CK = 84 МГц`, а бажана швидкість `Baud = 921600`:

```
USARTDIV = 84 000 000 / (16 · 921600)
         = 84 000 000 / 14 745 600
         ≈ 5.6966
```

Регістр `BRR` може зберегти цілу частину `5` та дробову частину в 4 бітах (`0.6966 · 16 ≈ 11 = 0xB`). Реальний дільник становитиме `5 + 11/16 = 5.6875`. Розрахуємо реальну швидкість і похибку:

```
Baud_real = 84 000 000 / (16 · 5.6875)
          = 923 076.9 бод
Похибка = (923076.9 - 921600) / 921600
        ≈ +0.16%                       [відмінна точність, кадр стабільний]
```

Однак при невдало підібраній частоті шини (наприклад, `f_CK = 80 МГц`) похибка на швидкості 921600 перевищує 2.8%, що призводить до регулярних помилок синхронізації стоп-біта (Framing Error) при нагріванні кварцового генератора.

![Часові діаграми навантаження процесорного ядра при блокуючому виводі, асинхронному DMA та Segger RTT](/root/eng/sf-devices/printf-na-prystroi/img/uart-blocking-timeline.svg)

*Порівняння витрат процесорного часу при виводі 50 байтів: блокуючий UART блокує ядро на понад 4 мс, тоді як DMA та RTT передають керування за лічені мікросекунди.*

### 3. Навантаження на стек і нереентрантність

Згідно з угодою про виклики функцій архітектури ARM (AAPCS), перші 4 аргументи передаються через регістри `r0`–`r3`. Проте стандартна функція `printf` зі змінною кількістю аргументів вимагає лінійного покажчика на аргументи в пам'яті. Тому пролог `vfprintf` починається з примусового збереження (скидання) регістрів `r0`–`r3` у стек (так званий Register Save Area). Навіть якщо викликати `printf("OK\n")` без додаткових аргументів, ядро обов'язково витрачає від 16 до 32 байтів стека лише на скидання регістрів.

Загальний розмір стекового кадру одного виклику `printf` у стандартній `newlib` сягає від 250 до 600 байтів через внутрішні масиви перетворення чисел та таблиці прапорців. На мікроконтролерах із сумарним розміром SRAM у 2–4 КБ виклик `printf` спричиняє переповнення стека (Stack Overflow) та пошкодження сусідніх змінних.

Крім того, стандартний `printf` **не є реентрантним** (англ. *reentrant*): він використовує глобальну структуру контексту потоку `_reent` (на яку вказує покажчик `_impure_ptr`) та внутрішні блокування потокобезпеки. 

В операційних системах реального часу (FreeRTOS, Zephyr) кожна задача повинна мати власну копію структури `struct _reent` (опція `configUSE_NEWLIB_REENTRANT = 1` у FreeRTOS). Кожна така копія додає понад 100 байтів RAM до дескриптора керування задачею (TCB). Якщо ж викликати `printf()` без увімкненої реентрантності з основного потоку програми, і в цей момент виникає апаратне переривання (ISR), обробник якого також викликає `printf()`, виникає стан взаємного блокування (Deadlock) або пошкодження внутрішніх статичних буферів форматування.

Якщо дві задачі різного пріоритету виводять повідомлення через блокуючий м'ютекс над спільним UART, низькопріоритетна задача блокує передавач на 5 мс, викликаючи небезпечну інверсію пріоритетів (Priority Inversion) для високопріоритетної задачі.

## Легковажні альтернативи: оптимізовані міні-бібліотеки

Для подолання надмірності `libc` у вбудованій розробці застосовують спеціалізовані міні-бібліотеки (наприклад, відкриту бібліотеку `mpaland/printf` або власні оптимізовані процедури `itoa`/`utoa`).

Основні оптимізаційні принципи легковажного printf:
1. **Відмова від dynamic memory allocation.** Жодного виклику `malloc()` чи створення дескрипторів `FILE`.
2. **Використання цілочисельних алгоритмів перетворення.** Числа переводяться в символи через пряме ділення на основу системи числення (10 або 16) у короткий локальний буфер фіксованого розміру (до 16 байтів).
3. **Фіксована крапка замість апаратної/програмної плаваючої коми.** Якщо необхідно вивести температуру `24.53 °C`, число зберігають як ціле `2453` у сотих частках і виводять цілу та дробову частини окремо через формат `printf("%d.%02d", temp / 100, temp % 100)`. Це повністю виключає необхідність бібліотеки IEEE 754 і зберігає до 20 КБ Flash.

Нижче наведено алгоритм компактного безстекового перетворення цілого числа в рядок (`utoa_fast`) та приклад реалізації мініатюрного засобу форматування:

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <stdarg.h>

/* Швидке перетворення беззнакового цілого в рядок без виклику libc */
static size_t fast_utoa(uint32_t val, char *buf) {
    char temp[11];
    size_t i = 0;
    
    if (val == 0) {
        buf[0] = '0';
        return 1;
    }
    
    while (val > 0) {
        temp[i++] = (char)('0' + (val % 10U));
        val /= 10U;
    }
    
    /* Розвертаємо символи у вихідний буфер */
    for (size_t j = 0; j < i; ++j) {
        buf[j] = temp[i - 1U - j];
    }
    return i;
}

/* Приклад легковажного форматування без залежностей від malloc та float */
int mini_snprintf(char *out, size_t max_len, const char *fmt, ...) {
    if (max_len == 0 || out == NULL || fmt == NULL) {
        return 0;
    }
    
    va_list args;
    va_start(args, fmt);
    
    size_t written = 0;
    while (*fmt != '\0' && written + 1 < max_len) {
        if (*fmt == '%' && *(fmt + 1) != '\0') {
            fmt++;
            if (*fmt == 'u') {
                uint32_t u = va_arg(args, uint32_t);
                char num_buf[11];
                size_t num_len = fast_utoa(u, num_buf);
                for (size_t k = 0; k < num_len && (written + 1 < max_len); ++k) {
                    out[written++] = num_buf[k];
                }
            } else if (*fmt == 's') {
                const char *s = va_arg(args, const char*);
                if (s == NULL) s = "(null)";
                while (*s != '\0' && written + 1 < max_len) {
                    out[written++] = *s++;
                }
            } else if (*fmt == '%') {
                out[written++] = '%';
            }
        } else {
            out[written++] = *fmt;
        }
        fmt++;
    }
    
    out[written] = '\0';
    va_end(args);
    return (int)written;
}
```

        }

## Неблокуюче логування: кільцевий буфер та UART DMA

Щоб повністю ліквідувати блокування ядра під час передачі повідомлень через UART, шар форматування відокремлюють від фізичного передавача за допомогою [кільцевого буфера FIFO](root:sf-algorithms/ring-buffer) та апаратного [прямого доступу до пам'яті (DMA)](root:hw-arch/dma).

Принцип роботи конвеєра:
1. Застосунок форматує рядок у тимчасовий буфер у RAM і викликає функцію запису в логер `async_log_write()`.
2. Функція копіює байти в кільцевий буфер пам'яті (на це витрачається лише декілька мікросекунд на виконання `memcpy`) та оновлює покажчик голови `head`.
3. Якщо передавач DMA наразі вільний, драйвер автоматично налаштовує дескриптор каналу DMA на вичитку лінійного шматка буфера і запускає апаратну транзакцію.
4. Контролер DMA забирає байти з пам'яті та самостійно подає їх на вхідний регістр UART у фоновому режимі, поки процесор виконує основний алгоритм керування.
5. По закінченню передачі спрацьовує переривання DMA Transfer Complete (TC), яке зміщує покажчик хвоста `tail` і, якщо в буфері лишилися нові повідомлення, негайно запускає наступну порцію.

Детальний розбір алгоритмів лінійних зрізів кільцевого буфера, синхронізації з перериваннями та захисту від пошкодження кешу пам'яті наведено в окремому проекті: [повна реалізація асинхронного логера з кільцевим буфером](root:sf-devices/printf-na-prystroi/proj-dma-logger.md).

## Високошвидкісне логування через SEGGER RTT

Технологія SEGGER Real-Time Transfer (RTT) є галузевим стандартом для високошвидкісного зняття діагностики на чіпах із ядрами ARM Cortex-M та RISC-V під час підключеного апаратного налагоджувача.

### Архітектура дескриптора RTT

RTT не використовує жодної периферії зв'язку мікроконтролера (ні UART, ні USB, ні SPI). Замість цього в пам'яті SRAM виділяється керуюча структура `SEGGER_RTT_CB` (Control Block):

:::tabs
```c
typedef struct {
    char*        sName;             /* Назва каналу (наприклад, "Terminal") */
    char*        pBuffer;           /* Вказівник на масив буфера в SRAM */
    unsigned int SizeOfBuffer;      /* Розмір буфера в байтах */
    unsigned int WrOff;             /* Зсув запису (пише MCU) */
    unsigned int RdOff;             /* Зсув читання (пише Host) */
    unsigned int Flags;             /* Режим: SKIP / TRIM / BLOCK */
} SEGGER_RTT_BUFFER;

typedef struct {
    char              acID[16];          /* Сигнатурний рядок "SEGGER RTT" */
    int               MaxNumUpBuffers;   /* Кількість каналів виводу MCU -> Host */
    int               MaxNumDownBuffers; /* Кількість каналів вводу Host -> MCU */
    SEGGER_RTT_BUFFER aUp[3];            /* Канали передачі */
    SEGGER_RTT_BUFFER aDown[3];          /* Канали прийому */
} SEGGER_RTT_CB;
```

Кожен канал описується структурою кільцевого буфера:
- `pBuffer`: адреса масиву символів у SRAM;
- `SizeOfBuffer`: розмір масиву в байтах;
- `WrOff`: індекс запису, який **модифікує мікроконтролер**;
- `RdOff`: індекс читання, який **модифікує хост-налагоджувач**;
- `Flags`: режим поведінки при переповненні.

![Розподіл дескриптора SEGGER RTT у SRAM мікроконтролера та фоновий доступ зонда налагоджувача](/root/eng/sf-devices/printf-na-prystroi/img/rtt-memory-structure.svg)

*Архітектура пам'яті SEGGER RTT: ядро MCU лише оновлює індекс WrOff у SRAM, а хост-налагоджувач вичитує байти через шинний міст AHB-AP.*

### Механізм взаємодії з хостом

1. Під час підключення хост-утиліта (J-Link RTT Viewer, OpenOCD або RTT Client) сканує діапазон оперативної пам'яті SRAM мікроконтролера через інтерфейс SWD у пошуках сигнатури `"SEGGER RTT"`.
2. Знайшовши структуру, зонд зчитує вказівник на буфер `pBuffer`, розмір `SizeOfBuffer` та значення покажчиків `WrOff` і `RdOff`.
3. Коли мікроконтролер записує повідомлення, він копіює рядок у буфер, оновлює `WrOff` і продовжує виконання. Весь запис повідомлення в 50 байтів займає **менше ніж 1 мікросекунду** (близько 80 тактів на копіювання).
4. Апаратний модуль налагодження всередині чіпа (DAP — Debug Access Port) надає зонду доступ до системної шини AHB/AXI безпосередньо. Зонд вичитує нові байти між `RdOff` та `WrOff` і сам записує нове значення `RdOff` у пам'ять чіпа.

### Режими обробки переповнення буфера RTT

Коли швидкість генерації повідомлень перевищує пропускну здатність зонда SWD або коли налагоджувач фізично відключений, прапорець `Flags` у структурі буфера визначає одну з трьох стратегій:

1. `SEGGER_RTT_MODE_NO_BLOCK_SKIP` (за замовчуванням): якщо місця в буфері недостатньо для розміщення нового рядка, повідомлення або його хвіст тихо відкидається. Програма ніколи не блокується. Це дозволяє залишати виклики логування в релізній прошивці без ризику зависання.
2. `SEGGER_RTT_MODE_NO_BLOCK_TRIM`: записується лише та частина повідомлення, яка вміщується у залишок буфера, решта відкидається.
3. `SEGGER_RTT_MODE_BLOCK_IF_FIFO_FULL`: мікроконтролер зупиняється в циклі очікування, доки хост-налагоджувач не вичитає дані й не звільнить місце. Використовується для зняття суворих діагностичних трас, де втрата навіть одного символу неприпустима.

## Бінарне логування та структуроване відкладене форматування

Найсучаснішим підходом до вирішення проблеми логування на мікроконтролерах є концепція **відкладеного форматування** (англ. *deferred formatting* або *binary logging*), реалізована в таких бібліотеках, як `defmt` (екосистема Rust), `nanolog` та `TRICE` (C/C++).

### Чому текстові рядки у Flash — це марнотратство

У класичному `printf("Motor %d fault: code %x\r\n", id, err)` рядок формату зберігається у секції `.rodata` у пам'яті Flash мікроконтролера в повному обсязі (31 байт). Якщо прошивка містить 500 діагностичних повідомлень, вони забирають від 15 до 40 КБ дорогоцінної пам'яті Flash лише на збереження символів тексту.

Крім того, процесор витрачає час на парсинг цього рядка і генерацію вихідного ASCII-тексту, а канал зв'язку змушений передавати десятки байтів тексту замість 8 байтів корисних даних.

### Принцип роботи бінарного логера (на прикладі TRICE / defmt)

1. **Індексація рядків на етапі компіляції.** Спеціальний препроцесор або плагін компілятора сканує всі виклики логування в коді. Кожному унікальному рядку форматування призначається числовий 16-бітний або 32-бітний ідентифікатор (ID).
2. **Вилучення тексту з прошивки.** Самі символьні рядки формату переносяться у спеціальну секцію ELF-файлу (наприклад, `.debug_log_strings` або `.defmt`), яка позначена типом `NOLOAD` або `(INFO)` у скрипті лінкера (`linker.ld`). Ця секція **не прошивається у Flash пам'ять мікроконтролера**, а залишається лише на комп'ютері розробника в таблиці символів.
3. **Формування двійкового кадру.** У процесі виконання мікроконтролер записує в буфер передачі лише компактний бінарний пакет фіксованого розміру:

```
+---------------+---------------+---------------+---------------+
|  Log ID (16)  | Timestamp(16) |  Arg 1 (32)   |  Arg 2 (32)   |  = 12 байтів
+---------------+---------------+---------------+---------------+
```

Замість 48 байтів тексту передається 12 байтів двійкових даних. Процесор не виконує жодних перетворень чисел у текст — він просто упаковує 32-бітні змінні у масив. Для додаткового стиснення застосовують пакування змінної довжини (Varint / LEB128), де малі значення лічильників займають лише 1 байт.

4. **Декодування на хості.** Спеціальна утиліта на комп'ютері приймає двійковий пакет, читає `Log ID`, знаходить відповідний рядок у збереженому ELF-файлі збірки й форматує повідомлення на екрані розробника.

## Підсумкова інженерна стратегія

1. Для пристроїв на етапі прототипування та розробки на столі з підключеним налагоджувачем оптимальним вибором є **SEGGER RTT**: він забезпечує максимальну швидкість без блокування ядра процесора і не вимагає виділення окремих виводів UART.
2. Для автономних польових пристроїв, що працюють без зонда налагодження, обов'язковою є зв'язка **легковажного форматувальника (або бінарного протоколу) з кільцевим буфером та UART DMA**. Блокуючий `printf` у промисловому коді систем реального часу неприпустимий.
3. У викликах форматування слід уникати чисел із плаваючою комою: збереження даних у форматі фіксованої коми з виводом через роздільні цілі числа заощаджує десятки кілобайтів Flash-пам'яті та усуває ризик вичерпання стека.
