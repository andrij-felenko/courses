# 📋 Структура секцій DWARF CFI та .eh_frame

Формат DWARF CFI (англ. *Call Frame Information* — інформація про кадри викликів) визначає машинно-незалежний двійковий контракт, за яким налагоджувачі та системні бібліотеки обробки винятків відновлюють стан процесора та лічильник команд для будь-якої точки виконання скомпільованої програми.

У двійкових файлах формату ELF ця інформація зберігається у двох секціях:
- `.debug_frame` — повна таблиця для налагодження згідно зі специфікацією стандарту DWARF. Вона не завантажується в оперативну пам'ять під час запуску процесу й видаляється під час оптимізації розміру командою `strip`;
- `.eh_frame` — оптимізована версія для середовища виконання мови C++ (англ. *Exception Handling*) та аварійного розмотування за стандартом Itanium C++ ABI. Ця секція завантажується в адресний простір програми як спеціальний сегмент `PT_GNU_EH_FRAME`.

### Запис загальної інформації (CIE)

Секція `.eh_frame` є неперервною послідовністю двійкових блоків двох типів: спільних записів **CIE** (англ. *Common Information Entry*) та функціональних записів **FDE** (англ. *Frame Description Entry*).

Запис CIE встановлює базові константи архітектури процесора та початкові правила віртуальної машини DWARF для цілої групи функцій:

| Поле структури CIE | Розмір / Формат | Призначення та інженерний опис |
|---|---|---|
| `Length` | 4 байти (u32) | Загальний розмір запису CIE в байтах без урахування самого поля довжини. Спеціальне значення `0xFFFFFFFF` перемикає формат у 64-бітний DWARF |
| `CIE ID` | 4 байти (u32) | Маркер типу запису: у секції `.eh_frame` значення строго дорівнює `0x00000000`, тоді як у `.debug_frame` містить `0xFFFFFFFF` |
| `Version` | 1 байт (u8) | Версія формату метаданих: версія 1 для DWARF 2, версія 3 для DWARF 3, версія 4 для DWARF 4 |
| `Augmentation String` | ASCIIZ-рядок | Рядок прапорців розширення (наприклад, `"zR"` або `"zPLR"`), що визначає наявність додаткових полів |
| `Code Alignment Factor` | ULEB128 | Множник кроку лічильника команд. Для архітектури x86-64 зі змінною довжиною інструкцій дорівнює 1 |
| `Data Alignment Factor` | SLEB128 | Множник знакових зміщень стека. Для архітектури x86-64 зі стеком, що росте вниз, дорівнює `-8` |
| `Return Address Reg` | ULEB128 | Фізичний номер архітектурного регістра, де зберігається адреса повернення (номер 16 для `RIP` на x86-64) |
| `Augmentation Data` | Змінна довжина | Додаткові параметри розширення (кодування покажчиків, адреса personality routine) |
| `Initial Instructions` | Байти опкодів | Початкова програма віртуальної машини, що задає стартовий стан таблиці на вході у функцію |

### Рядки розширення аугментації (Augmentation Strings)

Специфікація GNU Exception Handling розширює базовий DWARF за допомогою рядка аугментації. Кожна літера в рядку позначає наявність обов'язкового поля в структурі CIE або FDE:

1. Символ `'z'`: першим байтом після рядка аугментації йде поле `Augmentation Data Length` (у форматі ULEB128), яке точно вказує розмір наступного блоку розширень. Це дозволяє парсеру пропустити невідомі прапорці без зупинки.
2. Символ `'P'` (Personality): поле містить 1 байт кодування та покажчик на функцію особистості середовища мови (наприклад, `__gxx_personality_v0` у C++ або `__gcc_personality_v0` у C). Вона визначає правила зіставлення типів винятків під час розмотування.
3. Символ `'L'` (Language-Specific Data Area): визначає 1-байтне правило кодування адреси таблиці LSDA для поточного кадру.
4. Символ `'R'` (FDE Encoding): задає 1-байтне правило кодування адрес полів `PC Begin` та `PC Range` у записах FDE.

### Формат кодування вказівників (DW_EH_PE_*)

Щоб двійковий код лишався незалежним від положення в пам'яті (Position-Independent Executable, PIE) і підтримував рандомізацію адресного простору ASLR, адреси у секціях метаданих кодуються за допомогою модифікаторів `DW_EH_PE_*`:

- Молодші 4 біти задають тип даних: `DW_EH_PE_absptr` (`0x00` — пряма абсолютна адреса), `DW_EH_PE_uleb128` (`0x01`), `DW_EH_PE_udata4` (`0x03` — беззнакове 32-бітне число), `DW_EH_PE_sdata4` (`0x0B` — знакове 32-бітне число), `DW_EH_PE_sdata8` (`0x0C` — знакове 64-бітне число).
- Старші 4 біти визначають базу відліку: `DW_EH_PE_pcrel` (`0x10` — відносно поточної адреси лічильника `PC`), `DW_EH_PE_textrel` (`0x20` — відносно початку секції коду `.text`), `DW_EH_PE_datarel` (`0x30` — відносно секції даних), `DW_EH_PE_indirect` (`0x80` — значення в пам'яті є покажчиком на реальну адресу).

Найпоширеніша комбінація для 64-бітних бібліотек Linux — `0x1B` (`DW_EH_PE_pcrel | DW_EH_PE_sdata4`), що зберігає адресу як 32-бітне знакове зміщення відносно поточної позиції, заощаджуючи 50% пам'яті порівняно з абсолютними 64-бітними покажчиками.

### Кодування змінної довжини LEB128

Числові зміщення та номери регістрів у DWARF стискаються за алгоритмом **LEB128** (англ. *Little Endian Base 128* — основа 128 у порядку молодшого байта). Кожен байт використовує молодші 7 бітів для збереження значення числа, а найстарший 8-й біт служить прапорцем продовження:
- `біт 7 = 1`: далі йде наступний байт числа;
- `біт 7 = 0`: поточний байт є останнім.

Беззнаковий формат **ULEB128** використовується для додатних величин (номери регістрів, довжини блоків). Знаковий формат **SLEB128** застосовує пряме доповнення для від'ємних величин (зміщення відносно верхівки стека), де знак визначається найстаршим значущим бітом останнього прочитаного байта. Завдяки цьому малі числа від `-64` до `+63` займають у пам'яті рівно 1 байт замість 4 або 8 байтів.

### Дескриптор кадру функції (FDE)

Кожна функція у програмі описується окремим двійковим записом FDE, який посилається на свій базовий CIE:

| Поле структури FDE | Розмір / Формат | Призначення та інженерний опис |
|---|---|---|
| `Length` | 4 байти (u32) | Довжина запису FDE без урахування самого поля довжини |
| `CIE Pointer` | 4 байти (s32) | Відносне зміщення назад до початку відповідного запису CIE в секції `.eh_frame` |
| `PC Begin` | Змінний (`DW_EH_PE_*`) | Початкова адреса діапазону машинних інструкцій функції |
| `PC Range` | Змінний (`DW_EH_PE_*`) | Розмір кодового блоку функції в байтах |
| `Augmentation Data` | Змінна довжина | Вказівник на таблицю типів обробників LSDA для операцій C++ `catch` |
| `Call Frame Instructions` | Потік байт-коду | Інструкції віртуальної машини `DW_CFA_*`, що покроково змінюють матрицю стану кадру |

### Система команд віртуальної машини DWARF CFA

Віртуальна машина DWARF інтерпретує потік інструкцій `DW_CFA_*`, обчислюючи **CFA** (канонічну адресу кадру) та правила відновлення регістрів для кожної точки виконання:

| Інструкція | Формат операндів | Семантика дії віртуальної машини |
|---|---|---|
| `DW_CFA_advance_loc` | `delta` (6 бітів в коді) | Збільшує лічильник команд: `PC = PC + delta * Code_Alignment` |
| `DW_CFA_advance_loc1` | 1 байт (u8) `delta` | Збільшує лічильник команд на 1-байтну величину `delta` |
| `DW_CFA_advance_loc2` | 2 байти (u16) `delta` | Збільшує лічильник команд на 2-байтну величину `delta` |
| `DW_CFA_advance_loc4` | 4 байти (u32) `delta` | Збільшує лічильник команд на 4-байтну величину `delta` |
| `DW_CFA_def_cfa` | `register`, `offset` | Задає формулу CFA: `CFA = Register_Value + Offset` |
| `DW_CFA_def_cfa_register` | `register` | Змінює базовий регістр правила CFA, зберігаючи попереднє зміщення |
| `DW_CFA_def_cfa_offset` | `offset` (ULEB128) | Змінює зміщення CFA, зберігаючи поточний базовий регістр |
| `DW_CFA_offset` | `reg` (в коді), `offset` | Регістр збережено на стеку: `Reg = *(CFA + offset * Data_Alignment)` |
| `DW_CFA_offset_extended` | `reg`, `offset` | Розширена версія збереження регістра з номерами > 63 |
| `DW_CFA_val_offset` | `register`, `offset` | Значення самого регістра дорівнює: `Reg = CFA + offset * Data_Alignment` |
| `DW_CFA_register` | `reg1`, `reg2` | Значення регістра `reg1` тимчасово скопійовано в регістр `reg2` |
| `DW_CFA_remember_state` | немає | Зберігає поточний стан усіх правил CFA у внутрішній стек розмотувача |
| `DW_CFA_restore_state` | немає | Відновлює стан усіх правил CFA зі стека віртуальної машини |
| `DW_CFA_undefined` | `register` | Оголошує значення регістра втраченим (не підлягає відновленню) |
| `DW_CFA_same_value` | `register` | Значення регістра не змінювалося протягом виконання кадру |
| `DW_CFA_nop` | немає | Байт вирівнювання структури до межі машинного слова (`0x00`) |

### Двійкова структура пошукового індексу .eh_frame_hdr

Щоб уникнути повільного послідовного перебору тисяч записів FDE під час кожного виклику `throw` або зняття аварійного стека, компілятор створює секцію `.eh_frame_hdr`. Вона містить бінарний пошуковий масив фіксованого розміру, що забезпечує пошук дескриптора кадру за логарифмічний час `O(log N)`:

```
+------------------------------------+------------------------------------+
| version (1 байт) = 0x01            | eh_frame_ptr_enc (1 байт) = 0x1B   |
+------------------------------------+------------------------------------+
| fde_count_enc (1 байт) = 0x03      | table_enc (1 байт) = 0x3B          |
+------------------------------------+------------------------------------+
| eh_frame_ptr (4 байти, знакове зміщення до початку секції .eh_frame)    |
+-------------------------------------------------------------------------+
| fde_count (4 байти, загальна кількість функцій / записів FDE у таблиці) |
+-------------------------------------------------------------------------+
| Впорядкована двійкова таблиця пар (двійковий пошук за адресою PC):     |
|   [0] initial_func_pc_0 (4 байти) -> fde_offset_0 (4 байти)             |
|   [1] initial_func_pc_1 (4 байти) -> fde_offset_1 (4 байти)             |
|   ...                                                                   |
|   [N-1] initial_func_pc_N-1 (4 байти) -> fde_offset_N-1 (4 байти)       |
+-------------------------------------------------------------------------+
```

### Практичний розбір реального FDE через readelf

Щоб наочно побачити роботу віртуальної машини DWARF, виконаємо інспекцію бінарного файлу за допомогою системної утиліти `readelf -wF` (або `llvm-dwarfdump --eh-frame`):

```
00000018 0000001c 0000001c FDE cie=00000000 pc=00401120..0040115b
   LOC           CFA      rbp   ra
00401120       rsp+8    u     c-8
00401121       rsp+16   c-16  c-8
00401124       rbp+16   c-16  c-8
0040115a       rsp+8    c-16  c-8
```

Розберемо кожен рядок цієї роздрукованої матриці стану:
- На вході у функцію за адресою `0x00401120` інструкція `call` щойно поклала адресу повернення на верхівку стека. Тому `CFA` дорівнює `rsp + 8`, а адреса повернення `ra` розташована за адресою `CFA - 8`. Регістр `rbp` позначено як `u` (undefined — його значення поки що не змінювалося).
- Після виконання першої команди прологу `push %rbp` за адресою `0x00401121` верхівка стека зменшилася ще на 8 байтів. Нове правило стає `CFA = rsp + 16`, а попереднє значення `rbp` збережено за зміщенням `CFA - 16` (`c-16`).
- Після виконання другої команди прологу `mov %rsp, %rbp` за адресою `0x00401124` компілятор фіксує базу кадру в регістрі `RBP`. Базове правило CFA перемикається на `rbp + 16`. Від цієї миті й до самого епілогу будь-які зміни покажчика `RSP` (виділення локальних масивів, передача параметрів через стек) не впливають на правило обчислення `CFA`.
- Нарешті, в епілозі функції за адресою `0x0040115a` після виконання команди `pop %rbp` правило CFA повертається до початкового стану `rsp + 8`, готуючи процесор до фінальної інструкції `ret`.

### Складні вирази DW_CFA_expression та обмеження eBPF

Окрім простих числових зміщень, стандарт DWARF підтримує інструкції `DW_CFA_expression` та `DW_CFA_val_expression`. Вони містять повні програми для обчислювальної машини DWARF (операції зі стеком значень, арифметичні та логічні інструкції, умовні розгалуження й читання довільних комірок оперативної пам'яті).

Такі вирази використовуються компілятором у складних випадках оптимізації: динамічне вирівнювання стека за допомогою векторних інструкцій AVX-512, обробка нестандартних фреймів сигналів ядра або оптимізація розташування змінних у регістрах.

Саме наявність виразів `DW_CFA_expression` робить стандартний DWARF CFI непридатним для використання у верифікаторі ядра Linux eBPF. Оскільки програма виразу DWARF потенційно може містити нескінченні цикли або звертатися до заборонених ділянок пам'яті ядра, її виконання в контексті апаратного переривання створює неприйнятний ризик падіння операційної системи. Це стало головною рушійною силою розробки спрощеного формату SFrame.
