Мобільний робот масою 40 кг рухається цехом зі швидкістю 1.5 м/с у напрямку цільової полиці за 20 метрів. Обчислення глобального маршруту з обходом колон, оптимізацією радіусів повороту та побудовою графа на сітці зайнятості займає в мікроконтролера 400 мс. Якщо просто перед колесами на відстані 20 см несподівано з'являється вантаж або нога людини, очікування наступного циклу планувальника призведе до того, що машина проїде 60 см і вріжеться в перешкоду на повній швидкості задовго до завершення обчислень. З іншого боку, якщо прибрати глобальний планувальник і залишити лише швидкі локальні рефлекси відбивання від перешкод, робот неминуче застрягне в першому ж глухому U-подібному кутку. Щоб пристрій одночасно досягав далекої мети й не розбивався об раптові перешкоди, прийняття рішень розділяють на два незалежні часові шари: швидкий реактивний і повільний планувальний.

## Конфлікт двох часових масштабів

Будь-яка автономна вбудована система стикається з фундаментальною математичною суперечністю між якістю рішення та часом на його пошук. Оптимальне рішення (найкоротший шлях, мінімальне споживання енергії батареї, плавний профіль прискорення без ривків) вимагає обробки великого обсягу інформації: карти простору, кінематичних обмежень, поточного теплового стану силових ключів і динаміки навантаження.

Алгоритмічна складність пошуку шляху на графі (наприклад, алгоритм `A*` чи пошук на деревах випадкових напрямків `RRT*`) залежить від розмірності простору станів і кількості вузлів. Навіть на високопродуктивних мікроконтролерах із тактовою частотою сотні мегагерців повний перерахунок траєкторії вимагає від десятків до сотень мілісекунд:

```
T_plan = O(|V| · log|V| + |E|)   [обчислювальна складність пошуку на графі]
```

Тим часом закони фізики вимагають від системи негайної реакції на критичні події. Якщо струм через обмотку мотора перевищив гранично допустиме значення під час клину редуктора, кристал силового MOSFET-транзистора нагріється до температури теплового пробою за лічені мікросекунди. Якщо кінцевий вимикач осі верстата зафіксував вихід за межі робочої зони, гальмо повинно спрацювати за фіксований час, який вимірюється частками мілісекунди, інакше каретка зріже механічні упори.

Спроба об'єднати обидві задачі в один монолітний цикл керування неминуче призводить до глухого кута. Якщо зробити цей цикл швидким (`T = 1 мс`), у ньому не вистачить обчислювального часу для побудови складних планів. Якщо зробити його повільним (`T = 200 мс`), система втрачає детерміністичний час реакції на аварійні події.

![Дворівнева архітектура: швидкий рефлекторний і повільний дорадчий шари](/root/eng/sf-devices/reaktsiia-chy-plan/img/two-layer-architecture.svg)

*Дворівнева гібридна архітектура: швидкий рефлекторний шар із жорстким дедлайном і повільний дорадчий шар із глобальною моделлю світу.*

Єдиним стійким інженерним рішенням є розділення керування на два ізольовані контури, що виконуються асинхронно з різними періодами дискретизації:
- **Швидкий шлях (Fast Path / Реактивний шар):** локальний контур рефлексів із жорстким детермінованим часом реакції (`T ≤ 1 мс`). Його завдання — негайний захист механіки, утримання рівноваги, лімітування струмів та уникнення прямих зіткнень.
- **Повільний шлях (Slow Path / Планувальний шар):** дорадчий (від лат. *deliberatio* — «зважування, обдумування») контур глобального планування з плаваючим часом виконання (`T = 100…1000 мс`). Його завдання — побудова оптимального маршруту, генерація гладких траєкторій і координація довгострокової місії.

## Реактивний шар: детермінізм, рефлекси та обмеження

Реактивний шар будується за принципом «стимул — реакція». Він не займається прогнозуванням майбутнього, не зберігає в пам'яті історію подій і не будує гіпотез про навколишній світ. Його логіка зводиться до прямого відображення поточних векторів давачів на безпечні керуючі команди актуаторів (від лат. *actus* — «дія»).

Головна характеристика реактивного контуру — **абсолютна гарантія дедлайну виконання** (Hard Real-Time). Час виконання функції обробки не може залежати від вхідних даних: у ньому немає нескінченних циклів пошуку, динамічного виділення пам'яті (`malloc`/`free`) чи очікування на блокуючі синхропримітиви операційної системи (м'ютекси, черги з таймаутом).

Реактивний шар бере на себе такі критичні обов'язки:
1. **Апаратні відсічки та обмеження потужності:** контроль струму шунтів, захист від перегріву інвертора, моніторинг напруги акумуляторної батареї. Якщо струм перевищує поріг захисту, реактивний шар миттєво зменшує шпаруватість ШІМ або повністю знеструмлює силові ключі, не запитуючи дозволу в планувальника.
2. **Аварійне гальмування (Emergency Stop):** обробка сигналів кінцевих вимикачів, апаратних кнопок аварійного вимкнення або критичного наближення до перешкоди за даними лідара чи ультразвукового сонара.
3. **Локальні силові поля (Virtual Potential Fields):** відштовхування від перешкод. Перешкода розглядається як джерело віртуальної сили відштовхування, що спадає обернено пропорційно квадрату відстані:

```
F_rep = k_rep · (1/d - 1/d_safe) · (1/d²)   [сила відштовхування перешкоди]
```

Ця віртуальна сила додається до вектора руху безпосередньо в контурі керування швидкістю коліс, автоматично відхиляючи робота від стіни ще до того, як повільний планувальник встигне перемалювати карту.

Бюджет часу на виконання реактивного кроку в мікроконтролері типово становить від 50 до 200 мкс при періоді виклику 1000 мкс (частота 1 кГц). Завдяки цьому 80–95% процесорного часу залишається вільним для фонових задач планувальника або низькопріоритетних процесів операційної системи.

## Математика штучних потенційних полів у швидкому контурі

Для реалізації реактивного ухилення від перешкод на рівні швидкого контуру найчастіше застосовують метод штучних потенційних полів (Artificial Potential Fields), запропонований Уссамою Хатібом (англ. *Oussama Khatib*). Просторова конфігурація робота рухається в умовному енергетичному полі, де ціль формує гравітаційну яму притягання, а перешкоди — потенційні пагорби відштовхування.

Загальна потенційна функція простору визначається сумою двох компонентів:

```
U_total(q) = U_att(q) + U_rep(q)
```

Притягальний потенціал цілі розраховується як квадратична функція відстані до цільової координати `q_goal`:

```
U_att(q) = 0.5 · k_att · ||q - q_goal||²
```

Відштовхувальний потенціал діє лише всередині захисної зони радіусом `d_safe` навколо перешкоди:

```
U_rep(q) = 0.5 · k_rep · (1/d(q) - 1/d_safe)²    при d(q) ≤ d_safe
U_rep(q) = 0                                     при d(q) > d_safe
```

Результуюча сила керування є антиградієнтом (напрямком найшвидшого спуску) сумарного потенціалу:

```
F_total = -∇U_total = F_att + F_rep
```

У швидкому циклі керування (1 кГц) вектор `F_total` проектується на кінематичні осі актуаторів за час менше ніж 30 мкс. Це дозволяє машині м'яко й безперервно оминати дрібні несподівані перешкоди без переривання загального руху.

Проте штучні потенційні поля мають відому ваду — **пастку локального мінімуму**: якщо вектор притягання до цілі виявляється прямо протилежним вектору відштовхування від стіни (симетричний рух у глухий кут або U-подібну перешкоду), сумарна сила `F_total` стає рівною нулю, і робот зупиняється назавжди. Саме тут вступає в дію другий шар: повільний планувальник виявляє відсутність прогресу просування до цілі, будує глобальний топологічний граф обходу й виводить систему з глухого кута.

## Планувальний шар: пошук оптимуму без блокування безпеки

Планувальний шар відповідає за інтелектуальну поведінку пристрою. На відміну від рефлексів, цей шар володіє повною моделлю системи та навколишнього середовища: він знає координати цілі, топологію карти, енергетичний баланс акумулятора та обмеження прискорення кожної механічної осі.

Робота планувальника будується на розв'язанні оптимізаційних задач:
- **Глобальне планування шляху:** побудова послідовності опорних точок (waypoint) від поточного положення до цілі на двовимірній чи тривимірній сітці з урахуванням відомих статичних перешкод.
- **Генерація гладких профілів руху:** інтерполяція відрізків шляху кривими Безьє, B-сплайнами або поліномами п'ятого степеня для забезпечення неперервності першої (швидкість, $C¹$), другої (прискорення, $C²$) та третьої (ривок, $C³$) похідних координати за часом.
- **Оптимізація ресурсів:** вибір швидкості руху відповідно до теплового стану моторів або залишку заряду батареї.

Оскільки всі ці операції вимагають мільйонів тактів процесора й можуть тривати від 100 до 1000 мс, планувальний шар виконується як фонова низькопріоритетна задача RTOS або виноситься на окремий обчислювальний модуль (наприклад, супровідний мікрокомп'ютер на Linux, що спілкується з керуючим мікроконтролером через шину SPI чи UART).

Головне архітектурне правило взаємодії: **планувальник ніколи не видає команди безпосередньо на силові актуатори**. Він генерує лише *бажану траєкторію* (уставки положення, швидкості й прискорення), яку передає до буфера реактивного шару. Якщо планувальник зависне, впаде в помилку ділення на нуль або витратить на розрахунок більше часу, ніж планувалося, швидкий реактивний шар не втратить працездатності: він продовжить плавно утримувати останній безпечний стан або виконає штатно контрольовану зупинку.

## Архітектура придушення Брукса: ієрархія без центрального диктатора

Історично першою та найбільш елегантною моделлю поєднання рефлексів і складних поведінок стала **архітектура придушення** (Subsumption Architecture, від лат. *subsumere* — «підпорядковувати, включати до складу»), розроблена Родні Бруксом у Лабораторії штучного інтелекту MIT у 1986 році.

До появи ідей Брукса розробники робототехнічних систем намагалися будувати класичні ієрархічні піраміди: центральний блок збирав усі сенсорні дані, оновлював гігантську модель світу, ухвалював єдине рішення й спускав команди вниз по ланцюжку. Така піраміда виявлялася крихкою: збій будь-якого давача або затримка центрального планувальника повністю паралізували всю систему.

Брукс запропонував розрізати систему не горизонтально на функціональні блоки («сенсори → обробка → план → мотори»), а **вертикально на автономні шари поведінки** (англ. *layers of competence*).

![Архітектура придушення Брукса: вертикальні шари поведінки](/root/eng/sf-devices/reaktsiia-chy-plan/img/brooks-subsumption.svg)

*Ієрархія шарів у системі Subsumption: рефлекси нульового рівня мають безумовний пріоритет перехоплення виходу над дорадчими шарами.*

Кожен шар у такій системі є завершеним автоматом, що напряму з'єднує входи давачів із виходами приводів:
- **Рівень 0 (Уникнення перешкод):** читає сонари/бампери, видає команду відкату при наближенні до стіни. Працює завжди, гарантуючи фізичне виживання.
- **Рівень 1 (Блукання / Дослідження):** генерує плавний випадковий рух уперед, якщо попереду чисто.
- **Рівень 2 (Пошук цілі):** коригує курс у бік світлового або радіомаяка.
- **Рівень 3 (Картографування та довгостроковий план):** аналізує пройдений шлях і оптимізує маршрут.

Взаємодія між шарами відбувається без участі центрального диспетчера лише через два базові асинхронні механізми:
1. **Придушення виходу (Suppression / Subsumption):** вихідний сигнал вищого за пріоритетом шару (наприклад, Рівня 0) підключається паралельно до вихідної лінії нижчого шару (Рівня 1) через вузол придушення. Коли Рівень 0 активний, він перехоплює лінію керування мотором, підміняючи команду Рівня 1 своєю власною. Щойно небезпека минає, перехоплення знімається, і мотор знову слухає Рівень 1.
2. **Гальмування входу (Inhibition):** вищий шар може тимчасово заблокувати потік даних від конкретного давача до нижчого шару, змушуючи той тимчасово вважати, що вхідний сигнал дорівнює нулю.

Нижчі шари взагалі нічого не знають про існування вищих. Якщо верхній рівень планування зависне чи вимкнеться, нижчі рівні продовжать безпечно вести робота коридором, огинаючи перешкоди. Детальний аналіз експериментів Брукса з роботами Allen, Herbert і Genghis наведено у [нарисі про походження та розвиток архітектури придушення](root:sf-devices/reaktsiia-chy-plan/hist-subsumption-brooks.md).

## Арбітраж і злиття траєкторій (Bumpless Transfer)

У реальних промислових пристроях і сервоприводах чисте перехоплення сигналів за Бруксом стикається з серйозною фізичною проблемою: **механічним ударом при стрибку завдання**.

Уявімо маніпулятор, який плавно рухається за планом зі швидкістю 1.0 м/с. Раптово реактивний шар фіксує перешкоду й перехоплює керування, миттєво виставляючи команду нульової швидкості. Коли перешкода зникає, реактивний шар просто відпускає лінію. У цей момент планувальник, який продовжував рахувати свій таймлайн, вимагає, щоб вісь перебувала на 30 см попереду і рухалася зі швидкістю 1.2 м/с.

Ступінчастий розрив уставки положення `Δq` викликає миттєвий сплеск сигналу неузгодженості в ПІД-контурі положення:

```
e(t) = q_plan(t) - q_actual(t) = Δq   [миттєва помилка неузгодженості]
```

Диференціальна ланка регулятора реагує на стрибок нескінченною похідною, а пропорційна — максимальним насиченням струму. Відбувається сильний механічний удар (англ. *jerk* — «ривок»), який здатний зрізати зуби зубчастої передачі, зірвати кроковий двигун у пропуск кроків або спричинити спрацьовування захисту за струмом частотного перетворювача.

![Злиття траєкторій та безударне перемикання](/root/eng/sf-devices/reaktsiia-chy-plan/img/trajectory-blending.svg)

*Злиття траєкторій: після рефлекторного ухилення система виконує плавний перехід без стрибка швидкості й механічного удару.*

Для розв'язання цієї проблеми в архітектуру впроваджують механізм **безударного перемикання** (Bumpless Transfer — термін із класичної теорії автоматичного керування) та **зворотної синхронізації стану** (State Re-anchoring):

1. **Ресинхронізація планувальника (Re-anchoring):** у момент перехоплення керування реактивним шаром арбітр виставляє прапорець `replan_required`. Планувальник отримує фактичні фізичні координати `(x0, v0, a0)`, на яких зупинилася вісь, скидає свій внутрішній генератор траєкторії та починає розрахунок нового плану саме від фактичної точки, а не від віртуальної точки старого графіка.
2. **Злиття швидкостей та прискорень (Trajectory Blending):** перехід між реактивною зупинкою та плановим рухом здійснюється не стрибком, а через перехідний сплайн тривалістю `T_blend = 100…300 мс`. Протягом цього інтервалу вихідна уставка плавно інтерполюється кубічним поліномом Ерміта:

```
q_cmd(t) = h₀₀(s)·q_actual + h₁₀(s)·v_actual·T_blend + h₀₁(s)·q_plan + h₁₁(s)·v_plan·T_blend
```

де `s = t / T_blend ∈ [0, 1]` — нормований час інтерполяції. Це гарантує гладкість першої похідної швидкості ($C¹$) та виключає стрибки струму в обмотках двигуна.

3. **Захист від інтегрального насичення (Anti-Windup):** поки реактивний шар тримає керування актуатором, інтегральна ланка основного регулятора положення має бути або заморожена (`clamped`), або повністю скинута в нуль. Інакше накопичена за час стояння помилка викличе неконтрольований викид швидкості в момент відновлення планового руху.

## Проміжний шар: Dynamic Window Approach (DWA) та Time-Elastic Band

У сучасній робототехніці між швидким рефлекторним шаром (1 кГц) та глобальним планувальником шляху (1–5 Гц) нерідко виділяють проміжний шар — **локальний планувальник траєкторій**, що працює з частотою 20–50 Гц.

Двома класичними алгоритмами цього проміжного рівня є:
- **Підхід динамічного вікна (Dynamic Window Approach, DWA):** алгоритм розглядає простір можливих швидкостей `(v, ω)` робота та звужує його до підпростору швидкостей, які фізично досяжні за наступний крок дискретизації з урахуванням обмежень прискорення актуаторів:

```
V_d = { (v, ω) | v ∈ [v_cur - a_max·dt, v_cur + a_max·dt], 
                 ω ∈ [ω_cur - α_max·dt, ω_cur + α_max·dt] }
```

Із цього динамічного вікна відсікаються пари швидкостей, які не дозволяють зупинитися до перешкоди, а серед тих, що залишилися, максимізується цільова функція (близькість до глобального шляху, швидкість руху та дистанція до перешкод).

- **Еластична часова стрічка (Time-Elastic Band, TEB):** алгоритм деформує глобальну траєкторію як пружну гумову нитку під дією зовнішніх сил відштовхування перешкод, одночасно оптимізуючи часові інтервали між точками з урахуванням неолономних кінематичних обмежень коліс.

Локальний планувальник бере на себе складну геометрію об'їзду людей або динамічних візків, знімаючи це навантаження з глобального планувальника. Проте навіть за наявності DWA чи TEB найнижчий рефлекторний шар 1 кГц залишається обов'язковим: якщо динамічний локальний планувальник не встигне порахувати вікно через раптову перешкоду, рефлекс аварійної зупинки спрацює безпосередньо в контурі переривання за 1 мс.

## Апаратна підтримка швидкого шляху в мікроконтролерах

Максимальна надійність швидкого шляху досягається тоді, коли реакція на критичну подію делегується безпосередньо апаратній периферії мікроконтролера, оминаючи навіть програмний код обробника переривань:

1. **Апаратний вхід аварійного вимкнення (Break Input / Fault Pin):** сучасні мікроконтролери для керування двигунами (наприклад, розширені таймери TIM1/TIM8 у лінійках STM32 або модулі MCPWM в ESP32) оснащені спеціальним входом `BKIN`. При зміні логічного рівня на цьому піні (спрацювання оптичного датчика, компаратора надструму чи аварійної кнопки E-Stop) логіка таймера миттєво переводить виходи ШІМ у безпечний високоомний стан (Hi-Z) або примусово замикає нижні ключі для динамічного гальмування. Час апаратної реакції становить від 30 до 100 нс, що повністю усуває будь-яку залежність від затримок коду чи блокування переривань іншими драйверами.
2. **Апаратні аналогові компаратори (Internal Analog Comparators):** сигнал зі струмового шунта подається безпосередньо на вбудований швидкодіючий компаратор мікроконтролера. Опорна напруга задається внутрішнім ЦАП. Поріг спрацьовування компаратора прив'язується безпосередньо до входу Break таймера ШІМ без генерації процесорного переривання, забезпечуючи циклічне покрокове обмеження струму (Cycle-by-Cycle Current Limiting) на кожному періоді ШІМ.
3. **Асиметричні багатоядерні архітектури (Heterogeneous Multicore):** у складних системах процесор розділяють фізично:
   - Ядро реального часу (наприклад, Cortex-M4/M7 із пам'яттю TCM з нульовим часом очікування) виконує виключно 1 кГц контур рефлексів, ПІД-регулятори та обробку енкодерів.
   - Загальносистемне ядро (Cortex-A або друге ядро Cortex-M) виконує операційну систему, стек зв'язку, інтерфейси користувача та високорівневий планувальник траєкторій.

Обмін між ядрами відбувається через спільну пам'ять із захистом через апаратні семафори (HSEM / Mutex registers) або безблокові черги IPC.

## Триканальний арбітраж: оператор, планувальник і безпека

У багатьох практичних пристроях (дрони, самохідні візки AGV, мобільні маніпулятори) джерел команд більше ніж два: крім автономного планувальника та рефлексів безпеки існує канал **ручного дистанційного керування оператора** (RC-пульт, джойстик або операторська консоль через Wi-Fi/радіоканал).

Вбудовування людини в архітектуру підпорядкування вимагає суворого розподілу пріоритетів між трьома джерелами:

```
[ Шар 0: Рефлекс безпеки / E-Stop ]   (Пріоритет 1 — абсолютний)
                 ▲
                 │ придушує
[ Шар 1: Ручний пульт оператора ]     (Пріоритет 2 — вищий за автономію)
                 ▲
                 │ придушує
[ Шар 2: Автономний планувальник ]    (Пріоритет 3 — дорадчий)
```

Логіка арбітражу в такій системі працює за такими правилами:
- **Оператор витісняє автономний план:** якщо оператор відхиляє джойстик від нейтрального положення, арбітр миттєво відключає уставки планувальника й передає керування ручним командам.
- **Рефлекс обмежує оператора:** якщо оператор спрямовує машину на повній швидкості прямо в стіну, реактивний шар 0 виявляє критичне наближення й обмежує максимальну доступну швидкість або примусово зупиняє привід. Людина не має права скасувати апаратне обмеження безпеки без спеціального фізичного ключа допуску (Interlock).
- **Повернення до плану:** коли оператор відпускає джойстик у нейтраль, система не починає різко наздоганяти старий графік, а знову виконує процедуру безударного злиття (Bumpless Transfer) із нової точки, у якій машину залишив оператор.

## Діагностика та обробка збоїв давачів у реактивному шарі

Швидкий реактивний шар настільки ж надійний, наскільки надійні його первинні давачі. Якщо ультразвуковий сонар або оптичний датчик наближення раптово обірветься чи видасть серію хибних шумів через оптичний відблиск, реактивний шар ризикує або безпідставно зупинити систему на рівному місці, або навпаки — не помітити реальної перешкоди.

Для захисту від сенсорних аномалій у швидкому контурі застосовують три обов'язкові фільтри:
1. **Антидребезг подій (Glitch Filter):** сигнал перешкоди вважається валідним лише тоді, коли він підтверджується протягом `N` послідовних тактів швидкого контуру (наприклад, 3 такти по 1 мс = 3 мс фільтрації). Для екстрених апаратних входів (кнопка E-Stop) фільтрація мінімальна (50–100 мкс), а для далекомірів — трохи довша.
2. **Контроль цілісності каналу давача (Heartbeat / Plausibility):** якщо давач перестає оновлювати дані, видає за межами допустимого діапазону (out-of-range) або шина I2C/SPI повертає помилку зв'язку, швидкий шар миттєво переходить у режим «безпечної деградації» (Safe Fallback) — обмежує максимальну швидкість руху до мінімальної або зупиняє машину з індикацією аварії давача.
3. **Гістерезис спрацьовування:** поріг переходу в аварійне гальмування (`d_enter = 25 см`) завжди вибирають меншим за поріг виходу з нього (`d_exit = 35 см`). Різниця в 10 см запобігає високочастотному деренчанню режимів (chattering), коли робот починає нескінченно смикатися туди й назад на межі порогу спрацьовування.

## Тестування та верифікація методом ін'єкції збоїв (Fault Injection)

Надійність дворівневої гібридної системи неможливо перевірити лише в ідеальних лабораторних умовах. Основним методом верифікації прошивки є апаратно-програмне тестування з ін'єкцією збоїв (Software-in-the-Loop та Hardware-in-the-Loop Fault Injection):

- **Штучне зависання планувальника:** у нитку планувальника вбудовують тестовий нескінченний цикл або затримку на 5 секунд під час руху на максимальній швидкості. Тест вважається успішним, якщо швидкий реактивний шар фіксує затримку оновлення буфера, продовжує безпечне утримання поточної позиції або виконує штатно контрольоване сповільнення до нуля без падіння процесора.
- **Імітація раптової перешкоди:** під час виконання довгого лінійного розгону на вхід давача наближення подається стрибок сигналу за 10 см до робота. Осцилографом фіксується час від фронту сигналу до спадання струму моторів і відсутність коливального ривка швидкості після зняття сигналу перешкоди.
- **Синхронне профілювання джиттера (Jitter Analysis):** вимірюється стабільність періоду виклику швидкого контуру `T = 1.000 мс`. Максимально допустимий джиттер (відхилення часу старту обробника) у якісно спроектованій системі не перевищує `±5 мкс`.

## Архітектурні моделі міжрівневої взаємодії

Організація обміну даними між швидким реактивним шаром і повільним планувальником вимагає суворого дотримання правил багатопотокового програмування без взаємних блокувань:

| Модель зв'язку | Де застосовується | Плюси | Підводні камені |
|---|---|---|---|
| **Подвійна буферизація (Double Buffering)** | Передача готових масивів точок траєкторії від планувальника до контуру 1 кГц | Абсолютно без блокувань (`lock-free`), `O(1)` час читання в ISR | Вимагає атомарних операцій індексування (`memory_order_release` / `acquire`) |
| **Кільцевий буфер команд (Ring Buffer with Override)** | Послідовне виконання команд місії з можливістю скидання черги | Простота додавання нових шляхових точок | При аварії вся черга має бути миттєво інвалідована одним атомарним прапорцем |
| **Спільна пам'ять із контролем версій (Seqlock)** | Передача складних структур стану робота (карта, одометрія) | Читач ніколи не блокує письменника | Якщо планувальник оновлює дані надто часто, читач може потрапити в цикл повторного читання |

У системах із жорстким детермінізмом найчастіше застосовують саме схему **подвійної буферизації з атомарним перемиканням індексу**. Планувальник формує масив координат у фоновому слоті, після чого виконує атомарний запис індексу активного буфера. Обробник переривання таймера читає активний буфер за два машинних такти, ніколи не ризикуючи прочитати частково записану або пошкоджену структуру.

> 🔧 **Навіщо це.** Якщо розробник спробує захистити спільну траєкторію звичайним м'ютексом (`pthread_mutex` або `xSemaphoreTake`), виникає ризик інверсії пріоритетів: низькопріоритетний планувальник захопить м'ютекс якраз перед тим, як його витіснить інша фонова задача, а високопріоритетний контур керування мотором заблокується в очікуванні звільнення ресурсу. Пропуск хоча б одного такту переривання 1 кГц на силовому інверторі може призвести до збою фазової комутації та миттєвого виходу з ладу силових транзисторів. Lock-free структури повністю виключають таку можливість.

## Worked-приклад: реалізація дворівневого гібридного контролера

Повний приклад вбудованого модуля, що об'єднує швидкий реактивний контур 1 кГц (із перевіркою давача наближення та екстреним гальмуванням) і повільний планувальний контур (із подвійною буферизацією та безударним злиттям траєкторій за Ермітом).

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <stdatomic.h>
#include <math.h>

#define CONTROL_DT            0.001f  // 1 мс крок швидкого контуру (1 кГц)
#define MAX_EMERGENCY_DECEL   12.0f   // м/с^2 максимальне аварійне гальмування
#define SAFE_PROXIMITY_M      0.25f   // Поріг реактивного спрацювання (25 см)
#define BLEND_TIME_S          0.15f   // 150 мс інтервал злиття (Bumpless Transfer)

typedef enum {
    MODE_FOLLOW_PLAN,
    MODE_REACTIVE_OVERRIDE,
    MODE_BLEND_RECOVERY
} arbiter_mode_t;

typedef struct {
    float pos;
    float vel;
} traj_point_t;

typedef struct {
    traj_point_t slots[2];
    atomic_int active_slot;
} double_buf_t;

typedef struct {
    float actual_pos;
    float actual_vel;
    arbiter_mode_t mode;
    double_buf_t plan_input;
    
    // Параметри для інтерполяції злиття
    float blend_start_p;
    float blend_start_v;
    float blend_t;
    
    atomic_bool replan_flag;
} hybrid_arbiter_t;

void arbiter_init(hybrid_arbiter_t *arb) {
    arb->actual_pos = 0.0f;
    arb->actual_vel = 0.0f;
    arb->mode = MODE_FOLLOW_PLAN;
    atomic_init(&arb->plan_input.active_slot, 0);
    atomic_init(&arb->replan_flag, false);
    arb->blend_t = 0.0f;
}

// ── Повільний шар: запис нової уставки планувальником (10–50 Гц) ──────────────
void arbiter_push_plan_point(hybrid_arbiter_t *arb, float target_pos, float target_vel) {
    int active = atomic_load_explicit(&arb->plan_input.active_slot, memory_order_relaxed);
    int next = 1 - active;
    
    arb->plan_input.slots[next].pos = target_pos;
    arb->plan_input.slots[next].vel = target_vel;
    atomic_store_explicit(&arb->plan_input.active_slot, next, memory_order_release);
}

// ── Швидкий шар: 1 кГц детерміністичний крок із ISR таймера ──────────────────
float arbiter_fast_step(hybrid_arbiter_t *arb, float distance_sensor_m) {
    bool obstacle_near = (distance_sensor_m < SAFE_PROXIMITY_M);
    
    // 1. Пріоритетне реактивне перехоплення (Subsumption)
    if (obstacle_near && arb->mode != MODE_REACTIVE_OVERRIDE) {
        arb->mode = MODE_REACTIVE_OVERRIDE;
        atomic_store_explicit(&arb->replan_flag, true, memory_order_release);
    }
    
    float cmd_vel = 0.0f;
    
    switch (arb->mode) {
        case MODE_REACTIVE_OVERRIDE: {
            // Екстрене гальмування рефлекторного шару
            if (arb->actual_vel > 0.0f) {
                arb->actual_vel -= MAX_EMERGENCY_DECEL * CONTROL_DT;
                if (arb->actual_vel < 0.0f) arb->actual_vel = 0.0f;
            } else if (arb->actual_vel < 0.0f) {
                arb->actual_vel += MAX_EMERGENCY_DECEL * CONTROL_DT;
                if (arb->actual_vel > 0.0f) arb->actual_vel = 0.0f;
            }
            
            arb->actual_pos += arb->actual_vel * CONTROL_DT;
            cmd_vel = arb->actual_vel;
            
            // Якщо загроза минула й вісь зупинилася — переходимо до згладжування
            if (!obstacle_near && fabsf(arb->actual_vel) < 0.01f) {
                arb->mode = MODE_BLEND_RECOVERY;
                arb->blend_start_p = arb->actual_pos;
                arb->blend_start_v = arb->actual_vel;
                arb->blend_t = 0.0f;
            }
            break;
        }
        
        case MODE_BLEND_RECOVERY: {
            // Кубічний сплайн Ерміта для безударного переходу
            arb->blend_t += CONTROL_DT / BLEND_TIME_S;
            int active = atomic_load_explicit(&arb->plan_input.active_slot, memory_order_acquire);
            traj_point_t target = arb->plan_input.slots[active];
            
            if (arb->blend_t >= 1.0f) {
                arb->mode = MODE_FOLLOW_PLAN;
                arb->actual_pos = target.pos;
                arb->actual_vel = target.vel;
                cmd_vel = target.vel;
            } else {
                float s = arb->blend_t;
                float h00 = 2.0f * s * s * s - 3.0f * s * s + 1.0f;
                float h10 = s * s * s - 2.0f * s * s + s;
                float h01 = -2.0f * s * s * s + 3.0f * s * s;
                float h11 = s * s * s - s * s;
                
                float p_blend = h00 * arb->blend_start_p +
                                h10 * arb->blend_start_v * BLEND_TIME_S +
                                h01 * target.pos +
                                h11 * target.vel * BLEND_TIME_S;
                
                cmd_vel = (p_blend - arb->actual_pos) / CONTROL_DT;
                arb->actual_pos = p_blend;
                arb->actual_vel = cmd_vel;
            }
            break;
        }
        
        case MODE_FOLLOW_PLAN:
        default: {
            int active = atomic_load_explicit(&arb->plan_input.active_slot, memory_order_acquire);
            traj_point_t target = arb->plan_input.slots[active];
            arb->actual_pos = target.pos;
            arb->actual_vel = target.vel;
            cmd_vel = target.vel;
            break;
        }
    }
    
    return cmd_vel; // Видача на PWM-генератор драйвера мотора
}
```

```cpp
#include <atomic>
#include <cmath>
#include <array>
#include <algorithm>

class HybridDecisionArbiter {
public:
    enum class Mode : uint8_t {
        FollowPlan,
        ReactiveOverride,
        BlendRecovery
    };

    struct TrajectoryPoint {
        float pos{0.0f};
        float vel{0.0f};
    };

    explicit HybridDecisionArbiter(float safe_distance = 0.25f, 
                                  float max_emergency_decel = 12.0f,
                                  float blend_duration = 0.15f) noexcept
        : safe_distance_m_(safe_distance),
          max_emergency_decel_(max_emergency_decel),
          blend_duration_s_(blend_duration) {}

    // ── Повільний шар: надсилання уставки планувальником (10–50 Гц) ───────────
    void push_planned_setpoint(float target_pos, float target_vel) noexcept {
        const auto active = active_slot_.load(std::memory_order_relaxed);
        const auto write_slot = 1 - active;

        plan_buffer_[write_slot] = TrajectoryPoint{target_pos, target_vel};
        active_slot_.store(write_slot, std::memory_order_release);
    }

    // Перевірка планувальником: чи потрібно перебудувати глобальний маршрут
    [[nodiscard]] bool check_and_clear_replan_event() noexcept {
        return replan_event_.exchange(false, std::memory_order_acq_rel);
    }

    // ── Швидкий шар: 1 кГц детерміністичний такт переривання ──────────────────
    [[nodiscard]] float process_fast_cycle(float distance_sensor_m, float dt = 0.001f) noexcept {
        const bool obstacle_near = (distance_sensor_m < safe_distance_m_);

        // 1. Реактивне перехоплення пріоритету
        if (obstacle_near && mode_ != Mode::ReactiveOverride) {
            mode_ = Mode::ReactiveOverride;
            replan_event_.store(true, std::memory_order_release);
        }

        float cmd_velocity = 0.0f;

        switch (mode_) {
            case Mode::ReactiveOverride: {
                // Аварійне гальмування
                if (actual_vel_ > 0.0f) {
                    actual_vel_ = std::max(0.0f, actual_vel_ - max_emergency_decel_ * dt);
                } else if (actual_vel_ < 0.0f) {
                    actual_vel_ = std::min(0.0f, actual_vel_ + max_emergency_decel_ * dt);
                }

                actual_pos_ += actual_vel_ * dt;
                cmd_velocity = actual_vel_;

                if (!obstacle_near && std::abs(actual_vel_) < 0.01f) {
                    mode_ = Mode::BlendRecovery;
                    blend_start_p_ = actual_pos_;
                    blend_start_v_ = actual_vel_;
                    blend_progress_ = 0.0f;
                }
                break;
            }

            case Mode::BlendRecovery: {
                // Злиття траєкторій за поліномом Ерміта
                blend_progress_ += dt / blend_duration_s_;
                const auto active = active_slot_.load(std::memory_order_acquire);
                const auto& target = plan_buffer_[active];

                if (blend_progress_ >= 1.0f) {
                    mode_ = Mode::FollowPlan;
                    actual_pos_ = target.pos;
                    actual_vel_ = target.vel;
                    cmd_velocity = target.vel;
                } else {
                    const float s = blend_progress_;
                    const float s2 = s * s;
                    const float s3 = s2 * s;

                    const float h00 = 2.0f * s3 - 3.0f * s2 + 1.0f;
                    const float h10 = s3 - 2.0f * s2 + s;
                    const float h01 = -2.0f * s3 + 3.0f * s2;
                    const float h11 = s3 - s2;

                    const float p_blend = h00 * blend_start_p_ +
                                          h10 * blend_start_v_ * blend_duration_s_ +
                                          h01 * target.pos +
                                          h11 * target.vel * blend_duration_s_;

                    cmd_velocity = (p_blend - actual_pos_) / dt;
                    actual_pos_ = p_blend;
                    actual_vel_ = cmd_velocity;
                }
                break;
            }

            case Mode::FollowPlan:
            default: {
                const auto active = active_slot_.load(std::memory_order_acquire);
                const auto& target = plan_buffer_[active];

                actual_pos_ = target.pos;
                actual_vel_ = target.vel;
                cmd_velocity = target.vel;
                break;
            }
        }

        return cmd_velocity;
    }

    [[nodiscard]] Mode current_mode() const noexcept { return mode_; }
    [[nodiscard]] float position() const noexcept { return actual_pos_; }
    [[nodiscard]] float velocity() const noexcept { return actual_vel_; }

private:
    float safe_distance_m_;
    float max_emergency_decel_;
    float blend_duration_s_;

    float actual_pos_{0.0f};
    float actual_vel_{0.0f};
    Mode mode_{Mode::FollowPlan};

    std::array<TrajectoryPoint, 2> plan_buffer_{};
    std::atomic<int> active_slot_{0};

    float blend_start_p_{0.0f};
    float blend_start_v_{0.0f};
    float blend_progress_{0.0f};

    std::atomic<bool> replan_event_{false};
};
```

## Правила проектування дворівневих систем

1. **Реактивний шар володіє актуатором:** планувальник пропонує, але рефлекторний шар затверджує або блокує дію. Фізичний доступ до ШІМ, реле чи сервоприводів має лише контур швидкого захисту.
2. **Нульова залежність від успіху планувальника:** якщо задача планувальника зависла, викинула виняток чи вичерпала ліміт пам'яті, швидкий контур зобов'язаний автоматично перевести систему в безпечний стан у межах одного свого такту.
3. **Безударність у будь-якому переході:** будь-яка передача керування між шарами повинна супроводжуватися перевіркою неперервності фізичних змінних ($q, v, a$) та ресинхронізацією стану внутрішньої моделі планувальника.
4. **Розділення пам'яті без блокувань:** реактивний контур ніколи не чекає на планувальник; обмін уставками виконується через подвійну буферизацію з атомарним індексом.
