# 🔌 Статичний аналіз артефактів проти динамічного моніторингу на кристалі

Контроль бюджетів апаратних ресурсів у вбудованому та системному програмному забезпеченні спирається на дві взаємодоповнюючі інженерні парадигми: статичний аналіз артефактів збірки на хості та динамічний моніторинг виконання безпосередньо на цільовому кристалі чи в емуляторі. 

Кожен із цих підходів має власні сліпі зони, межі точності та обчислювальну ціну, тому надійний релізний конвеєр будується на їхньому поєднанні, а не на протиставленні.

---

## Порівняльна матриця підходів

Статичний підхід перевіряє код до його завантаження в мікроконтролер, аналізуючи структуру секцій ELF, карти компонування та стек-фрейми функцій. Динамічний підхід спостерігає за фактичною поведінкою пам'яті та часовими інтервалами під час виконання реальних тестових сценаріїв.

| Критерій | Статичний аналіз артефактів (`.map`, `.elf`, `.su`) | Динамічний моніторинг (MPU, водяні знаки, DWT) |
|---|---|---|
| **Місце виконання** | Сервер CI/CD (хост компіляції) | Цільовий кристал / HIL-стенд / емулятор QEMU |
| **Аналізовані метрики** | Розміри секцій Flash/RAM, найгірша глибина стека (WCEP), таблиці символів | Фактичний пік стека, фрагментація купи, реальний час старту, затримки ISR |
| **Покриття шляхів виконання** | 100% потенційних шляхів у дереві викликів (Call Graph) | Лише ті шляхи, які активовані поточними вхідними даними тестів |
| **Час роботи в конвеєрі** | Частки секунди (парсинг текстових та бінарних файлів) | Секунди або хвилини (прошивання, виконання тестів, вичитка логів) |
| **Вплив на продуктивність** | Нульовий (код залишається незмінним) | Додаткові інструкції, апаратні переривання MPU, пам'ять під канарки |
| **Сліпі зони** | Вказівники на функції, віртуальні таблиці (vtables), рекурсія, переривання | Непокриті тестами рідкісні гілки, найгірші збіги переривань |

## Механізми статичного аналізу: переваги та обмеження

Статичний аналіз у конвеєрі CI базується на вилученні інформації, згенерованої компілятором (`gcc`, `clang`) та компонувальником (`ld`, `lld`).

### Переваги статичного підходу
1. **Детермінізм та швидкість**: Перевірка 500 КБ прошивки займає менше 100 мілісекунд, що дозволяє запускати перевірку на кожен окремий коміт.
2. **Гарантія найгіршого випадку (WCET / WCEP)**: Аналізатор викликів обчислює максимальну сумарну глибину стек-фреймів для всіх гілок, включно з обробниками аварій, які в тестах можуть ніколи не викликатися.
3. **Ранній зворотний зв'язок (Shift-Left)**: Помилка переповнення статичної пам'яті виявляється на стадії компонування, ще до запуску апаратних тестів.

### Сліпі зони статичного підходу
1. **Непрямі виклики (Indirect Calls)**: Якщо функція викликається через вказівник або таблицю віртуальних методів C++, компілятор не знає точного графа викликів і позначає виклик як невизначений (`[indeterminate]` або `[unknown]`).
2. **Динамічна пам'ять (Heap)**: Статичний аналіз неспроможний передбачити фрагментацію купи, витоки пам'яті та результат викликів `malloc()` чи оператора `new`.
3. **Збіг пріоритетів переривань**: Компоновщик не знає, які саме переривання (ISR) можуть витіснити одне одного в найгірший момент часу.

## Механізми динамічного моніторингу

Динамічний контроль використовує апаратні та програмні засоби мікроконтролера під час прогону інтеграційних тестів у конвеєрі.

### 1. Метод водяних знаків стека (Stack Watermarking)
Перед запуском ядра або створенням задачі RTOS уся виділена область стека заповнюється спеціальним байтовим патерном — зазвичай `0xA5` або `0xDEADBEEF`.

Під час роботи задача використовує пам'ять, перезаписуючи водяні знаки реальними стек-фреймами. При завершенні тесту діагностичний модуль сканує пам'ять від дна стека вгору і знаходить перший байт, відмінний від `0xA5`. Це дає точний фактичний пік використання стека під час тесту.

### 2. Апаратний захист через MPU (Memory Protection Unit)
Блок захисту пам'яті програмується на встановлення захисної зони (англ. *guard region*) розміром 32–128 байтів безпосередньо за дном стека кожної задачі. 

Будь-яка спроба інструкції `PUSH` або запису локальної змінної вийти за межі стека негайно викликає апаратне переривання `MemManage_Handler` або `HardFault`, унеможливлюючи тихе пошкодження сусідніх глобальних змінних.

### 3. Таймери DWT (Data Watchpoint and Trace)
Для вимірювання часу ініціалізації використовується лічильник циклів ядра `DWT->CYCCNT` (доступний у ядрах ARM Cortex-M3/M4/M7/M33). Лічильник запускається на першому кроці функції `Reset_Handler` і фіксує точну кількість тактів процесора на кожній контрольній точці завантаження.

## Практична реалізація: вимірювання заповнення стека та контрольних точок

:::tabs
== C
```c
#include <stdint.h>
#include <stddef.h>

#define STACK_WATERMARK_PATTERN 0xA5A5A5A5U

void stack_paint(uint32_t *stack_start, size_t word_count) {
    for (size_t i = 0; i < word_count; ++i) {
        stack_start[i] = STACK_WATERMARK_PATTERN;
    }
}

size_t stack_measure_used_bytes(const uint32_t *stack_start, size_t word_count) {
    size_t unused_words = 0;
    while (unused_words < word_count && stack_start[unused_words] == STACK_WATERMARK_PATTERN) {
        unused_words++;
    }
    return (word_count - unused_words) * sizeof(uint32_t);
}
```
== C++
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <algorithm>

class StackMonitor {
public:
    static constexpr uint32_t Watermark = 0xA5A5A5A5U;

    static void paint(std::span<uint32_t> stack_arena) noexcept {
        std::fill(stack_arena.begin(), stack_arena.end(), Watermark);
    }

    [[nodiscard]] static size_t measure_used_bytes(std::span<const uint32_t> stack_arena) noexcept {
        const auto it = std::find_if(stack_arena.begin(), stack_arena.end(),
                                     [](uint32_t val) noexcept { return val != Watermark; });
        const auto unused_words = static_cast<size_t>(std::distance(stack_arena.begin(), it));
        return (stack_arena.size() - unused_words) * sizeof(uint32_t);
    }
};
```

## Гібридна архітектура контролю в CI/CD

Оптимальна інженерна стратегія полягає у дворівневому бар'єрі:
1. **Швидкі статичні ворота (Fast PR Gate)**: на кожному коміті розбирається `.map` файл та генерується граф `-fstack-usage`. Злиття блокується, якщо сума секцій або теоретичний WCEP стека перевищує ліміт.
2. **Динамічні нічні прогони (Nightly HIL Gate)**: на апаратному стенді або в емуляторі проганяються стрес-тести з увімкненим MPU, водяними знаками та збором тривалості завантаження через DWT.
