# 📋 Специфікація декларативного бюджету ресурсів: budget.yml

Декларативна специфікація бюджету ресурсів `budget.yml` визначає строгий інженерний контракт між архітектурою вбудованої системи та конвеєром неперервної інтеграції CI/CD. Вона перетворює неявні апаратні обмеження цільового мікроконтролера на формальні машиночитні правила валідації, що виконуються автоматично на кожному етапі збірки та перевірки запитів на злиття.

Специфікація стандартизує абсолютні апаратні стелі пам'яті, гранично допустимі квоти приросту коду в окремих комітах, максимальні ліміти глибини стек-фреймів для задач операційної системи реального часу та часові контрольні мітки етапів холодного старту.

---

## Призначення та місце в архітектурі проєкту

Конфігураційний файл бюджету зберігається у системі контролю версій поруч із вихідним кодом прошивки за стандартним шляхом `.ci/budget.yml` або `config/budget.yml`. Це гарантує версіонування бюджетних правил разом із розвитком архітектури пристрою: зміна апаратної ревізії плати або перехід на мікроконтролер із більшим обсягом пам'яті супроводжується явною модифікацією специфікації в тому ж самому коміті.

Валідатор конвеєра CI зчитує специфікацію перед аналізом згенерованих компілятором та компонувальником артефактів (`.map`, `.elf`, `.su`), зіставляє фактичні показники з декларованими порогами та генерує структурований звіт для розробників.

```text
Структура декларативного контракту budget.yml:
├── version: "1.2" (Версія схеми специфікації)
├── target: "stm32f407vg" (Апаратна платформа та профіль)
├── memory_limits (Абсолютні стелі фізичної Flash та SRAM)
├── delta_policy  (Диференційні обмеження приросту для PR)
├── task_stacks   (Ліміти глибини стека WCEP для задач RTOS та ISR)
├── boot_timeline (Часові бюджети етапів холодного старту)
└── components    (Індивідуальні квоти на підсистеми та бібліотеки)
```

---

## Секція 1: memory_limits (Абсолютні межі фізичної пам'яті)

Секція `memory_limits` визначає граничні обсяги фізичної пам'яті, доступні для бінарного образу прошивки. Вона враховує розподіл кристала між основним додатком, завантажувачем (Bootloader), сектором емуляції енергонезалежної пам'яті (EEPROM/NVM) та другим банком бездротового оновлення (Dual-Bank A/B OTA).

### Опис параметрів секції `memory_limits`

* `flash_total_bytes` (`integer`, обов'язкове): граничний розмір виконуваного образу у Flash-пам'яті в байтах. Розраховується як сума секцій `.text`, `.rodata`, векторної таблиці переривань та початкових значень секції `.data`. Якщо образ перевищує це значення, компіляція вважається аварійною.
* `flash_warning_threshold_pct` (`float`, необов'язкове): поріг заповнення Flash у відсотках (наприклад, `85.0`), при досягненні якого конвеєр генерує попередження про наближення до вичерпання ресурсів.
* `ram_static_max_bytes` (`integer`, обов'язкове): максимальний сумарний розмір статично виділеної оперативної пам'яті (`.data + .bss`). Цей параметр запобігає розростанню глобальних масивів і буферів, що загрожує простору динамічних стеків.
* `ram_dynamic_min_bytes` (`integer`, обов'язкове): мінімальний гарантований резерв SRAM, який повинен залишатися вільним від статичних змінних для розміщення динамічної купи (Heap) та стеків задач операційної системи.
* `alignment_padding_bytes` (`integer`, необов'язкове): вимога до вирівнювання кінцевої межі образу (наприклад, `2048` байтів), що необхідно для коректного стирання сторінок Flash під час прошивання через завантажувач.

## Секція 2: delta_policy (Диференційні обмеження для Pull Request)

Секція `delta_policy` встановлює межі допустимого зростання споживання пам'яті в межах одного запиту на злиття. Її мета — зупинити повільне накопичення дрібних неконтрольованих розширень коду різними розробниками.

### Опис параметрів секції `delta_policy`

* `max_flash_growth_bytes` (`integer`, обов'язкове): максимально допустимий приріст розміру Flash порівняно з базовою гілкою `main`. Типове значення становить від 512 до 2048 байтів.
* `max_ram_growth_bytes` (`integer`, обов'язкове): максимально допустимий приріст статичної пам'яті SRAM (`.data + .bss`) у рамках одного PR (зазвичай від 64 до 256 байтів).
* `block_on_regression` (`boolean`, обов'язкове): якщо встановлено значення `true`, конвеєр завершує роботу з кодом помилки `1` та блокує кнопку злиття на GitHub/GitLab при перевищенні будь-якої дельти.
* `waiver_label` (`string`, необов'язкове): назва мітки в системі рецензування коду (наприклад, `budget-override-approved`), наявність якої дозволяє обійти перевірку дельти у виняткових випадках за наявності погодження архітектора.

---

## Секція 3: task_stacks (Бюджети стеків задач реального часу)

Секція `task_stacks` декларує список усіх потоків керування (задач RTOS та обробників апаратних переривань ISR) із зазначенням точки входу та граничного розміру найгіршого шляху виконання (Worst-Case Execution Path — WCEP).

### Опис параметрів кожної задачі

* `entry_symbol` (`string`, обов'язкове): точна назва функції точки входу (наприклад, `Task_Telemetry_Run` або `USART1_IRQHandler`), від якої аналізатор починає обхід графа викликів.
* `max_wcep_bytes` (`integer`, обов'язкове): максимальна допустима сума стек-фреймів усіх функцій на найдовшому шляху виконання від точки входу до листових викликів.
* `allow_dynamic_allocation` (`boolean`, обов'язкове): заборона використання динамічного виділення стека (`alloca`, масиви змінної довжини VLA). Для надійного вбудованого коду цей параметр завжди має значення `false`.
* `include_isr_overhead` (`boolean`, необов'язкове): вимога автоматично додавати розмір стек-фрейму найважчого обробника переривання до розрахованого стека фонової задачі, що моделює витіснення в найгірший момент часу.

---

## Секція 4: boot_timeline (Хронометрія фаз завантаження)

Секція `boot_timeline` встановлює часові нормативи на виконання окремих фаз ініціалізації прошивки від моменту зняття апаратного скидання до повної функціональної готовності пристрою.

### Опис параметрів секції `boot_timeline`

* `t_reset_to_main_ms` (`float`, обов'язкове): ліміт часу на апаратний старт генераторів, перемикання частоти PLL, копіювання значень секції `.data` з Flash в SRAM та обнулення пам'яті секції `.bss`.
* `t_static_constructors_ms` (`float`, необов'язкове): максимальна тривалість виконання глобальних конструкторів об'єктів C++ (`__libc_init_array`). Перевищення цього ліміту зазвичай сигналізує про небажані обчислення під час старту.
* `t_peripherals_ready_ms` (`float`, обов'язкове): граничний час готовності апаратних драйверів датчиків та шин обміну даними (SPI, I2C, UART).
* `t_first_can_frame_ms` (`float`, обов'язкове): жорсткий дедлайн надсилання першого діагностичного повідомлення в шину CAN або Ethernet (наприклад, 45.0 мілісекунд для гарантованого вкладання в автомобільний норматив 50.0 мілісекунд).

---

## Секція 5: components (Квоти на підсистеми та сторонні бібліотеки)

Секція `components` дозволяє закріпити персональні ліміти споживання ресурсів за конкретними підсистемами, модулями або сторонніми бібліотеками (наприклад, стеком TCP/IP lwIP, ядром FreeRTOS або бібліотекою криптографії mbedTLS).

Парсер воріт збірки зіставляє шляхи вихідних об'єктних файлів у карті компонування з назвами компонентів та ізольовано перевіряє дотримання виділеного бюджету, що унеможливлює ситуацію, коли одна підсистема негласно споживає ресурси, відведені для іншої.

## Повний зразок конфігураційного файлу

Нижче наведено повний виробничий приклад файлу `budget.yml` для мікроконтролера STM32F407VG:

```yaml
version: "1.2"
target: "stm32f407vg"

memory_limits:
  flash_total_bytes: 491520        # 480 КБ (із 512 КБ, 32 КБ зарезервовано під завантажувач)
  flash_warning_threshold_pct: 85.0
  ram_static_max_bytes: 40960       # 40 КБ під .data + .bss
  ram_dynamic_min_bytes: 81920      # 80 КБ гарантовано під купу та стеки задач
  alignment_padding_bytes: 4

delta_policy:
  max_flash_growth_bytes: 2048      # Не більше +2 КБ Flash на один PR
  max_ram_growth_bytes: 256         # Не більше +256 Б статичної RAM на один PR
  block_on_regression: true
  waiver_label: "budget-waiver-approved"

task_stacks:
  telemetry_task:
    entry_symbol: "Task_Telemetry_Run"
    max_wcep_bytes: 512
    allow_dynamic_allocation: false
    include_isr_overhead: true
  
  control_loop_task:
    entry_symbol: "Task_MotorControl_Run"
    max_wcep_bytes: 384
    allow_dynamic_allocation: false
    include_isr_overhead: true

  can_rx_isr:
    entry_symbol: "CAN1_RX0_IRQHandler"
    max_wcep_bytes: 128
    allow_dynamic_allocation: false
    include_isr_overhead: false

boot_timeline:
  t_reset_to_main_ms: 3.5
  t_static_constructors_ms: 4.0
  t_peripherals_ready_ms: 15.0
  t_first_can_frame_ms: 45.0        # Норматив стандарту ISO 26262 (≤ 50 мс)

components:
  freertos_kernel:
    max_flash_bytes: 14336          # 14 КБ
    max_ram_bytes: 4096             # 4 КБ
  lwip_tcpip:
    max_flash_bytes: 65536          # 64 КБ
    max_ram_bytes: 20480            # 20 КБ
```

## Формат машинного звіту про порушення (JSON Output)

При виявленні невідповідності будь-якому з правил валідатор воріт формує структурований JSON-звіт для автоматичної обробки сторонніми інструментами аналітики:

```json
{
  "status": "FAILED",
  "exit_code": 1,
  "timestamp": "2026-08-28T03:50:00Z",
  "violations": [
    {
      "category": "MEMORY_LIMIT",
      "metric": "ram_static_max_bytes",
      "limit": 40960,
      "actual": 42112,
      "delta": 1152,
      "message": "Static RAM overflow by 1152 bytes in section .bss"
    },
    {
      "category": "STACK_WCEP",
      "task": "telemetry_task",
      "limit": 512,
      "actual": 648,
      "delta": 136,
      "path": ["Task_Telemetry_Run (48B)", "Format_Payload (128B)", "Serialize_JSON (472B)"],
      "message": "Stack depth exceeds budget on path Serialize_JSON"
    }
  ]
}
```

## Правила обробки винятків (Waiver Policy)

Якщо розширення функціоналу обґрунтовано вимагає збільшення споживання Flash або RAM понад ліміт дельти (наприклад, інтеграція нового криптографічного протоколу або драйвера дисплея), застосовується регламентована процедура обходу (Waiver):

1. **Архітектурний запит**: автор змін додає до опису Pull Request обґрунтування приросту розміру та аналіз впливу на залишковий ресурс пристрою.
2. **Перевірка абсолютної стелі**: обхід дельти дозволяється лише в тому випадку, якщо загальний розмір прошивки не порушує абсолютну фізичну стелю `flash_total_bytes` та `ram_static_max_bytes`.
3. **Присвоєння мітки**: відповідальний системний архітектор перевіряє зміни та встановлює на PR мітку, зазначену в полі `waiver_label`.
4. **Оновлення базових лімітів**: після злиття гілки нові абсолютні значення фіксуються в конфігурації `budget.yml` як новий базовий рівень для наступних комітів.
