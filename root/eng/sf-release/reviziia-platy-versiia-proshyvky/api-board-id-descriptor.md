# 📋 Специфікація дескриптора Board ID та бінарного формату TLV

У промислових контролерах, безпілотних апаратах та вбудованих пристроях з виділеною енергонезалежною пам'яттю EEPROM (шина I2C, мікросхеми серії 24C01, 24C02, 24C04) або захищеними секціями One-Time Programmable (OTP) внутрішнього Flash-мікроконтролера апаратна конфігурація кодується у бінарному форматі **TLV** (англ. *Type-Length-Value*).

Застосування формату TLV замість прямого дампу C-структур обумовлене фундаментальною вимогою довготривалої експлуатаційної сумісності. Фіксована бінарна структура `struct` у мові C має небезпечну чутливість до вирівнювання полів компілятором (англ. *structure padding*), різного порядку байтів між процесорними архітектурами (англ. *endianness*) та не дозволяє додавати нові змінні без руйнування зміщень для старих версій коду. На противагу цьому, формат TLV дозволяє базовій прошивці версії v1.0 зчитувати лише відомі їй теги, безпечно пропускаючи невідомі поля наступних апаратних ревізій, додані через кілька років серійного виробництва.

```text
КАРТА ПАМ'ЯТІ EEPROM (256 БАЙТІВ):
 0x00       0x08       0x10       0x18       0x2C       0x36                  0xFE
┌──────────┬──────────┬──────────┬──────────┬──────────┬─────────────────────┬──────────┐
│ Magic    │ HW Rev   │ BOM Var  │ Serial N │ MAC Addr │ Calib Data (TLV)... │ CRC-16   │
│ Tag 0x01 │ Tag 0x02 │ Tag 0x03 │ Tag 0x04 │ Tag 0x05 │ Теги 0x06..0xFE     │ Tag 0xFF │
│ (8 байт) │ (6 байт) │ (6 байт) │ (20 байт)│ (10 байт)│ (Змінний розмір)    │ (6 байт) │
└──────────┴──────────┴──────────┴──────────┴──────────┴─────────────────────┴──────────┘
```

## 1. Специфікація полів та реєстр тегів TLV

Кожен окремий запис дескриптора складається з трьох обов'язкових елементів, упакованих у строгому порядку:
- **`Tag` (2 байти, uint16_t, Little-Endian):** унікальний числовий ідентифікатор типу даних;
- **`Length` (2 байти, uint16_t, Little-Endian):** точний розмір корисного навантаження `Value` у байтах;
- **`Value` (N байтів):** сирі бінарні дані поля.

| Тег (Tag) | Назва поля | Тип даних | Довжина (Len) | Опис та інженерне призначення поля |
|---|---|---|---|---|
| `0x0001` | `TAG_MAGIC` | `uint32_t` | 4 байти | Магічне число `0x424F5244` (ASCII «BORD») для швидкої перевірки наявності валідного блоку |
| `0x0002` | `TAG_HW_REVISION` | `uint16_t` | 2 байти | Апаратна ревізія друкованої плати: старший байт — Major, молодший — Minor (`0x0100` = v1.0, `0x0201` = v2.1) |
| `0x0003` | `TAG_BOM_VARIANT` | `uint16_t` | 2 байти | Варіант комплектації компонентів (`0x0000` = Standard, `0x0001` = Low-Power, `0x0002` = Pro GPS) |
| `0x0004` | `TAG_SERIAL_NUM` | `char[]` | 16 байтів | Унікальний заводський серійний номер приладу в кодуванні ASCII (без нуль-термінатора) |
| `0x0005` | `TAG_MAC_ETH` | `uint8_t[6]` | 6 байтів | Апаратна MAC-адреса інтерфейсу Ethernet або Wi-Fi, виділена з пулу OUI виробника |
| `0x0006` | `TAG_VREF_CALIB` | `uint16_t` | 2 байти | Точне калібрувальне значення внутрішнього джерела опорної напруги Vref у мілівольтах (наприклад, 3304 мВ) |
| `0x0007` | `TAG_IMU_ALIGN` | `int8_t[9]` | 9 байтів | Матриця орієнтації осей сенсора `3×3` відносно корпусу (елементи з множини `{-1, 0, 1}`) |
| `0x0008` | `TAG_CRYPTO_PUBKEY` | `uint8_t[32]` | 32 байти | Відкритий ключ пристрою (Curve25519) для автентифікації на захищеному хмарному сервері |
| `0x00FF` | `TAG_CRC16` | `uint16_t` | 2 байти | Контрольна сума CRC-16/CCITT (`0x1021`, init `0xFFFF`), розрахована від байта 0 до кінця передостаннього тегу |

## 2. Алгоритм парсингу та контролю цілісності

Під час первинного старту завантажувач або диспетчер платформи зчитує весь бінарний образ EEPROM в буфер оперативної пам'яті SRAM та виконує послідовну верифікацію за чотири кроки:

1. **Перевірка заголовка та магічного числа:** парсер зчитує перші 4 байти поля `Value` тегу `0x0001`. Якщо отримане значення відмінне від магічної константи `0x424F5244`, пам'ять вважається незапрограмованою або фізично пошкодженою;
2. **Розрахунок контрольної суми CRC-16:** алгоритм проходить по масиву байтів від нульового зміщення до байта початку тегу `0x00FF`. Обчислене значення порівнюється з полем контрольної суми, збереженим у пам'яті. Неспівпадіння хоча б одного біта свідчить про спотворення даних через перешкоди або просідання напруги живлення;
3. **Ітеративний розбір записів:** покажчик зміщення збільшується на `4 + Length` байтів на кожній ітерації. Відомі програмі теги розпаковуються у відповідні поля внутрішньої структури контексту ядра;
4. **Безпечна обробка невідомих тегів:** якщо зустрічається тег із невідомим номером (доданий у новіших ревізіях плати), парсер не перериває роботу, а додає довжину `Length` до поточного зміщення покажчика, зберігаючи пряму сумісність із майбутніми апаратними релізами.

```c
#ifndef BOARD_ID_API_H
#define BOARD_ID_API_H

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

#ifdef __cplusplus
extern "C" {
#endif

#define BOARD_ID_MAGIC 0x424F5244U

/* Коди повернення підсистеми ідентифікації */
typedef enum {
    BOARD_ID_OK               =  0,
    BOARD_ID_ERR_I2C_FAULT    = -1,
    BOARD_ID_ERR_BAD_MAGIC    = -2,
    BOARD_ID_ERR_CRC_MISMATCH = -3,
    BOARD_ID_ERR_UNSUPPORTED  = -4,
    BOARD_ID_ERR_CORRUPT_TLV  = -5
} board_id_status_t;

/* Розпакована структура параметрів плати */
typedef struct {
    uint16_t hw_revision;        /* Формат: Major.Minor (0x0200 = Rev B) */
    uint16_t bom_variant;       /* Варіант комплектації сенсорів */
    char serial[17];            /* Null-terminated ASCII рядок */
    uint8_t mac[6];             /* 48-бітний MAC-ідентифікатор */
    uint16_t vref_calib_mv;     /* Калібрована напруга опорного джерела */
    int8_t imu_matrix[9];       /* Матриця трансформації осей IMU */
} board_info_t;

/**
 * @brief Зчитує дескриптор з EEPROM, перевіряє цілісність CRC16 та розпаковує теги.
 * 
 * @param[out] out_info Вказівник на структуру, куди записуються розпарсені параметри.
 * @return BOARD_ID_OK у разі успіху, або від'ємний код помилки.
 */
board_id_status_t board_id_read_and_validate(board_info_t *out_info);

/**
 * @brief Повертає бітову маску апаратних можливостей для зазначеної ревізії.
 */
uint32_t board_id_get_capabilities(uint16_t hw_rev);

#define BOARD_CAP_HAS_IMU_BMI270   (1U << 0)
#define BOARD_CAP_HAS_FLASH_MX25L  (1U << 1)
#define BOARD_CAP_HAS_CAN_FD       (1U << 2)
#define BOARD_CAP_HAS_SECURE_CHIP  (1U << 3)

#ifdef __cplusplus
}
#endif

#endif /* BOARD_ID_API_H */
```

## 4. Протокол заводської прошивки на тестовому стенді (ATE Provisioning)

Під час масового виробництва прошивка дескриптора виконується автоматизованим тестовим обладнанням (англ. *Automated Test Equipment, ATE*). Стенд підключається до тестових точок (Test Points) друкованої плати через матрицю пружинних контактів (Pogo Pins) і виконує детерміністичну послідовність операцій:

1. **Подача живлення та вимірювання струмів споживання:** стенд перевіряє відсутність коротких замикань на лініях 3.3V та 5V;
2. **Апаратне розблокування запису:** щуп стенда примусово притискає вивід WP мікросхеми EEPROM до землі GND;
3. **Вимірювання фізичних калібрувальних величин:** прецизійний цифровий мультиметр стенда вимірює точне значення напруги внутрішнього джерела Vref мікроконтролера та опорну частоту кварцового генератора;
4. **Генерація структури TLV:** керівний комп'ютер стенда формує бінарний образ дескриптора, записує серійний номер з бази даних підприємства, виділяє унікальну MAC-адресу, розраховує підсумкову контрольну суму CRC-16 та записує блок по шині I2C;
5. **Верифікація зворотним зчитуванням (Readback Verification):** стенд повністю зчитує записану пам'ять, перевіряє побайтовий збіг із буфером та знімає потенціал із виводу WP, активуючи апаратний захист від запису.

## 5. Апаратні захисти та експлуатаційні протоколи

1. **Апаратний захист від перезапису (Hardware Write-Protect, лінія WP):** вивід WP мікросхеми EEPROM на платі підтягується постійним резистором 10 кОм до лінії живлення VDD. У такому стані внутрішня логіка чіпа блокує будь-які операції запису та стирання байтів, унеможливлюючи спотворення дескриптора при аварійних коливаннях напруги живлення;
2. **Протокол відновлення завислої шини I2C (Bus Lockup Recovery):** якщо під час транзакції читання EEPROM стався раптовий скид процесора (Watchdog Reset або зовнішня перешкода), ведена мікросхема EEPROM залишається в режимі передачі поточного байта, утримуючи лінію даних SDA притиснутою до землі низьким рівнем. У такій ситуації контролер I2C не може згенерувати умову START. Драйвер раннього старту зобов'язаний перед ініціалізацією контролера перевести пін тактування SCL у режим програмного виходу (GPIO Bit-Banging), згенерувати серію з 9 імпульсів частотою 100 кГц і завершити послідовність формуванням стопового біта STOP. Це гарантовано виводить ведений чіп EEPROM зі стану передачі та звільняє шину;
3. **Атомарність оновлення калібрувальних даних:** якщо дескриптор містить поля, що перезаписуються під час польової експлуатації (наприклад, накопичений час напрацювання двигунів або зміщення гіроскопа після перекалібрування), EEPROM розбивають на дві симетричні сторінки (Primary та Shadow). Запис завжди виконується у тіньову сторінку з розрахунком нової контрольної суми CRC-16, після чого за один цикл запису оновлюється прапорець активної сторінки, що гарантує цілісність даних при раптовому вимиканні живлення.
