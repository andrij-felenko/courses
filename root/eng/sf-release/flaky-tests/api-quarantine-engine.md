# 📋 Специфікація та API карантинного рушія для CI/CD

Карантинний рушій (*Quarantine Engine*) — це сервіс проміжного аналізу результатів тестування в конвеєрах неперервної інтеграції (CI/CD), який автоматично виявляє недетерміновані тести, ізолює їх від блокування релізного пайплайну розробників та керує процесом верифікації виправлень.

Рушій функціонує як незалежний брокер перевірки якості між тестовими раннерами (pytest, CTest, GoogleTest), серверами збірки (Jenkins, GitLab CI, GitHub Actions) та системою управління дефектами (Jira, Bugzilla).

## Архітектурний контракт та протокол взаємодії

Під час виконання конвеєра збірки кожен тестовий раннер після завершення прогону експортує структурований звіт. Карантинний рушій перехоплює цей звіт до формування фінального статусу збірки, звіряє ідентифікатори тестів із поточною базою нестабільних цілей і динамічно маніпулює кодом повернення процесу.

Якщо тест перебуває у статусі `QUARANTINED`, його падіння трансформується у стан попередження `WARNING` із детальним логуванням, дозволяючи продовжити злиття коду, якщо всі інші тести пройшли чисто.

## Схема конфігурації рушія (quarantine-policy.json)

Поведінка карантинного рушія визначається декларативним JSON-файлом конфігурації:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "version": "1.4.0",
  "policy": {
    "flakiness_threshold": 0.05,
    "min_samples_window": 50,
    "auto_quarantine_enabled": true,
    "max_consecutive_failures": 3,
    "verification_target_runs": 500,
    "quarantine_ttl_days": 14
  },
  "alerting": {
    "issue_tracker": "jira",
    "project_key": "HIL_EMBEDDED",
    "issue_priority": "High",
    "notify_channel": "#ci-quarantine-alerts"
  },
  "rules": [
    {
      "suite_pattern": "hil_bench_*",
      "override_policy": {
        "verification_target_runs": 1000,
        "flakiness_threshold": 0.01
      }
    }
  ]
}
```

### Семантика полів конфігурації

1. **`flakiness_threshold` (діапазон 0.0–1.0):** Поріг коефіцієнта нестабільності `F_score`. Якщо частка невідтворюваних збоїв тесту перевищує це значення (наприклад, 5% запусків), тест автоматично переводиться у карантинний пул.
2. **`min_samples_window`:** Мінімальний обсяг історичної вибірки запусків для конкретного тесту. Запобігає помилковому переведенню свіжих тестів у карантин після першого ж одиничного збою.
3. **`auto_quarantine_enabled`:** Глобальний перемикач автоматизації. У вимкненому стані рушій лише маркує тести в дашборді та генерує рекомендації для інженерів з якості, не змінюючи статус блокування PR.
4. **`max_consecutive_failures`:** Пороговий лічильник стабільного падіння. Якщо тест падає `N` разів поспіль на різних комітах без жодного успішного проходження, він класифікується як стабільно зламаний (*Broken*), негайно повертається в блокуючий статус і блокує всі подальші збірки.
5. **`verification_target_runs`:** Цільова кількість бездоганних послідовних прогонів на спеціалізованому стрес-раннері, яка є обов'язковою умовою для відновлення довіри до тесту.
6. **`quarantine_ttl_days`:** Граничний час перебування в ізоляції. Якщо протягом зазначеного терміну відповідальна команда не випустила виправлення, тест вважається закинутим і примусово відключається із загального набору тестів.

## Інтерфейс командного рядка (CLI Interface)

Утиліта `flaky-quarantine-cli` інтегрується в сценарії збірки CI як фінальний крок перевірки тестових звітів (JUnit XML, TAP або CTest JSON).

### 1. Оцінка результатів прогону: `evaluate`

Команда аналізує вхідний файл звіту, звертається до центральної бази даних за актуальними статусами тестів та виставляє підсумковий статус збірки.

```bash
flaky-quarantine-cli evaluate \
  --report-format=junit \
  --report-path=./build/test-results.xml \
  --policy=./ci/quarantine-policy.json \
  --db-url=postgres://ci_tracker:5432/flaky_db \
  --commit-sha=$GIT_COMMIT \
  --branch=$GIT_BRANCH
```

**Коди повернення процесу (Exit Codes):**
- `0`: Усі обов'язкові тести пройшли успішно. Збоїлися лише тести з активного списку карантину (збірка вважається успішною для злиття).
- `1`: Зафіксовано збій обов'язкового (активного) тесту, який не перебуває в карантині (збірка блокується).
- `2`: Виявлено новий миготливий тест; тест автоматично додано до карантину, але поточна збірка помічена попередженням (*Warning*).
- `3`: Помилка конфігурації, невалідний формат звіту або недоступність бази даних історії.

### 2. Запит списку карантину: `list`

Команда повертає деталізований реєстр усіх ізольованих тестів з метриками їхньої стабільності та посиланнями на зареєстровані задачі в трекері.

```bash
flaky-quarantine-cli list --suite=hil_bench_uart --format=json
```

**Формат вихідної структури даних JSON:**

```json
{
  "total_quarantined": 2,
  "quarantined_tests": [
    {
      "test_id": "test_uart_dma_ring_buffer_stress",
      "suite": "hil_bench_uart",
      "quarantined_at": "2026-08-20T14:22:00Z",
      "flakiness_score": 0.084,
      "total_runs": 1200,
      "failed_runs": 101,
      "status": "QUARANTINED",
      "ticket_id": "HIL_EMBEDDED-4091",
      "responsible_team": "firmware-comms"
    },
    {
      "test_id": "test_relay_matrix_chatter_protection",
      "suite": "hil_bench_power",
      "quarantined_at": "2026-08-25T09:10:00Z",
      "flakiness_score": 0.120,
      "total_runs": 450,
      "failed_runs": 54,
      "status": "VERIFYING",
      "verification_progress": "340/500",
      "ticket_id": "HIL_EMBEDDED-4112",
      "responsible_team": "hw-test-rig"
    }
  ]
}
```

### 3. Реєстрація виправлення та запуск верифікації: `verify`

Коли інженер додає виправлення (наприклад, усуває гонку або додає антибрязкіт), він сповіщає рушій про необхідність верифікації.

```bash
flaky-quarantine-cli verify \
  --test-id="test_uart_dma_ring_buffer_stress" \
  --fix-commit=$GIT_COMMIT \
  --target-runs=500
```

Команда переводить тест зі стану `QUARANTINED` у стан `VERIFYING` та ініціює паралельний стрес-прогін 500 ітерацій у фоновому стендовому пулі. Якщо під час прогону трапляється хоча б один збій, тест автоматично повертається в стан `QUARANTINED`, а в тікет Jira додається оновлений лог помилки.

## Математичний алгоритм обчислення коефіцієнта нестабільності (Flakiness Score)

Коефіцієнт нестабільності `F_score` розраховується з урахуванням часового згасання ваги минулих запусків за експоненційним ковзним середнім (EMA), що дозволяє швидко реагувати на деградацію стабільності та плавно забувати старі виправлені збої:

```
F_score(t)
= α · FlakyFlip(t) + (1 - α) · F_score(t - 1)    [експоненційне згладжування]
```

Параметри формули мають чітке фізичне трактування:
- `FlakyFlip(t) = 1`, якщо тест на одному й тому самому сирцевому коміті при повторному автоматичному перезапуску змінив результат (Pass → Fail або Fail → Pass), і `0` якщо результат обох прогонів був ідентичним.
- `α = 2 / (K + 1)` — ваговий коефіцієнт згладжування для ковзного вікна розміром `K = 50` запусків.

## HTTP REST API для інтеграції з серверами збірки та панелями моніторингу

Карантинний рушій надає RESTful сервіс для автоматичної синхронізації зі стендовими серверами та візуалізації надійності релізів.

### 1. Отримання хронології тесту: `GET /api/v1/tests/{test_id}/history`

Повертає деталізований масив останніх запусків, включаючи час виконання, джитер затримок та статус кожного прогону.

**Приклад відповіді сервера:**

```json
{
  "test_id": "test_uart_dma_ring_buffer_stress",
  "flakiness_score": 0.084,
  "history": [
    {"run_id": "r-9812", "status": "PASSED", "duration_ms": 42.1, "timestamp": "2026-08-28T02:15:00Z"},
    {"run_id": "r-9811", "status": "FAILED", "duration_ms": 150.0, "timestamp": "2026-08-28T01:45:00Z"}
  ]
}
```

### 2. Ручне керування статусом: `POST /api/v1/quarantine/override`

Дозволяє лід-архітектору або інженеру з релізу примусово змінити статус тесту (наприклад, зняти з карантину перед критичним випуском продукту).

**Тіло запиту (Request Body):**

```json
{
  "test_id": "test_uart_dma_ring_buffer_stress",
  "action": "FORCE_RESTORE",
  "reason": "Hardware relay board was replaced on bench #4",
  "authorized_by": "lead-qa-engineer"
}
```

## Безпека, автентифікація та обробка збоїв мережі

1. **Автентифікація через HMAC-токени:** Усі запити від раннерів CI повинні містити заголовок `X-Quarantine-Signature`, згенерований за алгоритмом HMAC-SHA256 зі спільним секретом проєкту. Це виключає можливість підробки статусів карантину неавторизованими гілками.
2. **Поведінка при збої бази даних (Fail-Safe Strategy):** Якщо карантинний сервіс недоступний через мережевий збій, CLI-утиліта переходить у безпечний автономний режим: використовується локальний кешований файл політики, а всі невідомі збої тестів трактуються як блокуючі.
3. **Дедуплікація параметризованих тестів:** Для матричних збірок (Matrix Builds на різних версіях компилятора та архітектурах ARM/x86) ідентифікатор `test_id` формується як хеш від назви тестової функції та набору параметрів оточення, що запобігає спотворенню статистики для різних цільових платформ.
