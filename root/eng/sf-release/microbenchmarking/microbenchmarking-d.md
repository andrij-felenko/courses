# Мікробенчмарк: як не збрехати собі виміром

<preknowlist>
- [Профілювання](root:sf-release/profiling) — вимірювання витрат процесорного часу та виявлення гарячих точок коду.
- [Оптимізації компілятора](root:sf-lang/compiler-optimizations) — перетворення проміжного представлення, інлайнінг, усунення мертвого коду та згортання констант.
- [Ієрархія кеш-пам'яті](root:hw-arch/cache) — рівні L1, L2, L3, кеш-лінії, промахи та затримки звернення до оперативної пам'яті.
- [Вибіркові оцінки та усереднення](root:math-probability/averaging) — математичні властивості вибіркового середнього та похибки оцінювання.
</preknowlist>

Коли інженер намагається з'ясувати, чи стала нова функція парсингу цілих чисел швидшою на чотири наносекунди, прямий замір через звичайний цикл з обгорткою `clock()` або `std::chrono` видає результат, який не має нічого спільного з дійсністю. Компілятор із увімкненою оптимізацією помічає, що результат обчислень усередині циклу нікуди не передається, і повністю видаляє тіло функції, залишаючи порожній лічильник на 0.00 наносекунд. Якщо ж результат примусово зберегти у змінну, вимір зіштовхується з фізикою кремнію: нерозігріті кеші процесора, динамічне підвищення тактової частоти Turbo Boost та перемикання контексту ядра операційної системи створюють розкид значень у 400–600%, де реальний виграш у кілька тактів повністю тоне в апаратному шумі.

## Фізика наномасштабу: чому профілювання не рятує

Загальносистемне [профілювання](root:sf-release/profiling) працює за принципом статистичного семплінгу або макроінструментації: воно відповідає на питання, у яких модулях великої працюючої програми зосереджено 80% часу виконання. Проте семплер із типовою частотою 1000 знімків на секунду бачить стан процесора раз на мільйон наносекунд. Він принципово не здатний оцінити швидкодію атомарної операції — пошуку в хеш-таблиці, обчислення контрольної суми CRC32, розкодування UTF-8 чи множення матриць 4×4, які тривають від 2 до 50 наносекунд.

Для ізольованої оцінки таких ділянок застосовують **мікробенчмарк** (англ. *micro-* від давньогрец. *mikros* — малий + *benchmark* від давньоангл. *benc* — лава, верстак + *mearc* — позначка, реперна точка для вимірювання висоти). Це спеціально спроєктований тестовий контур, який багаторазово виконує ізольований фрагмент коду в контрольованому середовищі, вимірюючи чистий час його виконання.

Головна складність мікробенчмаркінгу полягає у співвідношенні масштабів величин:
- Одна базова інструкція сучасного процесора виконується за 0.25–1.0 наносекунди (на тактовій частоті 3–4 ГГц);
- Читання системного таймера через vDSO триває 15–30 наносекунд;
- Звернення до оперативної пам'яті DRAM в обхід кешу потребує 60–100 наносекунд;
- Одне апаратне переривання таймера операційної системи або перемикання контексту забирає від 2000 до 50000 наносекунд.

Спостереження за процесором виявляється на порядки важчим за сам досліджуваний код. Будь-яка неточність у постановці експерименту спотворює вимірювану величину настільки, що інженер починає оптимізувати випадковий системний шум або артефакти поведінки транслятора.

## Пастки компілятора: оптимізатор як супротивник

Сучасний компілятор C та C++ оптимізує код відповідно до фундаментального стандарту «якщо не видно різниці» (As-If Rule): транслятор має право змінювати, переставляти або повністю видаляти будь-які інструкції, якщо це не змінює спостережуваної поведінки програми (операцій введення-виведення, взаємодії з леткою пам'яттю або системних викликів ядра). Для оптимізатора тестовий цикл без побічних дій — це мертвий код, який необхідно викинути.

Існує чотири головні механізми, через які транслятор фальсифікує наївні виміри:

1. **Усунення мертвого коду (Dead Code Elimination, DCE).** Якщо функція виконує складні обчислення, але повернене значення ніде не записується у зовнішній файл, мережевий сокет чи глобальну змінну, оптимізатор видаляє обчислення разом із викликом функції. У вихідному асемблері залишається порожній цикл, який виконує лише декремент лічильника.
2. **Згортання та поширення констант (Constant Folding & Propagation, від лат. *constans* — стійкий, незмінний).** Якщо аргументи функції відомі під час компіляції (наприклад, тестовий рядок `"12345"`), компілятор виконує алгоритм прямо на етапі трансляції. Замість виконання коду в рантаймі асемблер отримує готову константу `mov eax, 12345`, що виконується за 0 тактів конвеєра.
3. **Агресивний інлайнінг (Inlining, від англ. *in-* — всередину + *line* — рядок).** Компілятор підставляє тіло функції безпосередньо в точку виклику всередині вимірювального циклу. Це знищує накладні витрати виклику функції (збереження регістрів, інструкції `call` та `ret`), але водночас дозволяє транслятору винести інваріантні обчислення за межі циклу (Loop Invariant Code Motion).
4. **Автовекторизація (Auto-Vectorization).** Оптимізатор може перетворити скалярний цикл з N однакових операцій на набір векторних інструкцій AVX2 або AVX-512, обробляючи по 8 або 16 елементів за такт. У реальній програмі дані можуть надходити по одному з мережі, і векторний шлях там ніколи не виконається.

![Пастка оптимізації](/root/eng/sf-release/microbenchmarking/img/compiler-optimization-trap.svg)
*Пастка компілятора при мікробенчмаркінгу. Без оптимізаційного бар'єра компілятор викидає весь вимірювальний цикл як мертвий код (DCE), створюючи ілюзію нульової затримки. Бар'єр примушує зберегти результат у регістрі без додавання зайвих інструкцій.*

Окрім перелічених механізмів, компілятор може змінювати вирівнювання коду в пам'яті (Code Alignment). Переміщення початку циклу на 1 байт (наприклад, з адреси, кратної 64 байтам, на некратну) здатне сповільнити або прискорити його виконання на 15–20% через перетин меж кеш-ліній інструкцій (L1i) та вікон вибірки декодера мікрооперацій (uop Cache / Decoded Stream Buffer).

Ця боротьба триває від появи перших синтетичних тестів 1970-х років. Про те, як виробники компіляторів навчилися розпізнавати штучні циклові конструкції та маніпулювати показниками тестів Dhrystone і Whetstone, детально викладено у вставці [Від Dhrystone до сучасних бенчмарків](root:sf-release/microbenchmarking/hist-synthetic-benchmarks.md).

## Бар'єри компілятора: примус до чесного виконання

Щоб отримати достовірні дані, інженер повинен явно заборонити компілятору спрощувати досліджувану ділянку, не додаючи при цьому зайвих інструкцій у процесорний конвеєр.

Поширена помилка — використання ключового слова `volatile` (від лат. *volatilis* — леткий). Оголошення змінної як `volatile` забороняє компілятору зберігати її в регістрах процесора і примушує виконувати запис та читання зі стека в оперативній пам'яті на кожній ітерації. Це повністю руйнує нормальний розподіл регістрів і робить код у 3–5 разів повільнішим, ніж він є насправді.

Правильним рішенням є **оптимізаційний бар'єр** (Optimization Barrier) — вбудована асемблерна інструкція-заглушка, яка виступає для компілятора «чорною скринькою»:

:::tabs
```c
/* Оптимізаційний бар'єр на мові C */
static inline void do_not_optimize(uint64_t val) {
    asm volatile("" : : "r,m"(val) : "memory");
}
```
```cpp
/* Ідіоматичний оптимізаційний бар'єр на C++ */
namespace bench {

template <typename T>
inline void do_not_optimize(T&& val) {
    #if defined(__clang__)
    asm volatile("" : "+r,m"(val) : : "memory");
    #else
    asm volatile("" : : "g"(val) : "memory");
    #endif
}

} // namespace bench
```
:::

Конструкція розшифровується так:
- `asm volatile` повідомляє транслятору, що блок має невідомі побічні ефекти і його не можна видаляти або переносити відносно інших операцій.
- Порожній рядок команд `""` означає, що реальних процесорних інструкцій у машинний код не додається (0 накладних тактів).
- Обмеження входу `"r,m"(val)` змушує компілятор підготувати значення `val` або в регістрі процесора, або в пам'яті, вважаючи, що асемблерний блок його прочитає. Це гарантує повне обчислення значення й унеможливлює усунення мертвого коду.
- Клоббер `"memory"` повідомляє компілятору, що блок міг прочитати або змінити будь-яку комірку оперативної пам'яті. Це блокує винесення читань і записів за межі вимірювального циклу.

У професійній практиці цей механізм стандартизовано функціями `benchmark::DoNotOptimize()` та `benchmark::ClobberMemory()`. Детальний опис методів цієї бібліотеки, передачі параметрів та автоматичного визначення складності коду наведено у вставці [Інтерфейс Google Benchmark](root:sf-release/microbenchmarking/api-google-benchmark.md).

## Пастки апаратури: кеші, конвеєр та передбачувач

Навіть якщо компілятор згенерував ідеальний машинний код, час його виконання на сучасному суперскалярному процесорі залежить від внутрішнього стану мікроархітектурних блоків.

### 1. Прогрів кеш-пам'яті (Cache Warmup)
Процесор має трирівневу [ієрархію кеш-пам'яті](root:hw-arch/cache): надшвидкий L1 (~1 нс, 32–64 КБ), середній L2 (~3–4 нс, 512 КБ–1 МБ) та спільний L3 (~10–15 нс, 16–64 МБ). Перший запуск функції завжди відбувається на **холодному кеші** (Cold Cache): інструкції та дані відсутні в L1, процесор блокується в очікуванні вибірки з оперативної пам'яті DRAM (затримка 70–100 нс). Після кількох ітерацій кеш стає **прогрітим** (Warm Cache), і затримка падає до 1–3 нс. Мікробенчмарк зобов'язаний явно розділяти ці два режими: або виконувати обов'язкову фазу прогріву перед заміром, або свідомо скидати кеш-лінії інструкцією `clflush` для вимірювання холодного старту.

Крім того, апаратні передвісники вибірки (Hardware Prefetchers) у процесорі розпізнають послідовний доступ до пам'яті й заздалегідь підвантажують наступні кеш-лінії в L2/L1. Якщо тестовий масив обходиться послідовно, затримка пам'яті маскується; якщо ж алгоритм у бойових умовах виконує випадковий доступ (Pointer Chasing), апаратний префетчер виявляється безсилим, і час операції зростає у 5–10 разів.

### 2. Стан передбачувача переходів (Branch Predictor)
Процесори використовують складні таблиці історії переходів (Branch Target Buffer, BTB та Pattern History Table, PHT) для передбачення результатів умовних операторів `if/else`. Якщо тестовий масив містить відсортовані дані, передбачувач навчається за кілька ітерацій і досягає 100% точності: конвеєр працює без пауз. Якщо ж у бойових умовах дані випадкові, помилка передбачення (Branch Misprediction) спричиняє скидання конвеєра (Pipeline Flush) із втратою 15–20 тактів на кожен промах. Запуск тесту на спрощених шаблонних даних дає завищену в рази швидкість.

### 3. Суперскалярність, позачергове виконання та паралелізм інструкцій
Сучасне процесорне ядро є суперскалярним і підтримує позачергове виконання (Out-of-Order Execution). Воно розщеплює асемблерні команди на мікрооперації (uops) і розподіляє їх по декількох паралельних портах виконання (Execution Ports: цілочисельні ALU, блоки завантаження/збереження, векторні блоки). Якщо вимірюваний цикл викликає операції над незалежними змінними, ядро може виконувати до 4–6 інструкцій за один такт (Instructions Per Cycle, `IPC > 4`). Якщо ж у коді є строгий ланцюг залежностей за даними (`x = hash(x)`), кожна наступна операція чекає на завершення попередньої, і продуктивність падає до 1 інструкції за кілька тактів (`IPC < 0.5`). Мікробенчмарк зобов'язаний моделювати реальні залежності за регістрами.

### 4. Аномалії вирівнювання коду та кеш мікрооперацій (uop Cache)
У процесорах архітектури x86-64 інструкції мають змінну довжину (від 1 до 15 байтів). Блок вибірки інструкцій (Instruction Fetch Unit) зчитує машинний код з L1-кешу інструкцій 16- або 32-байтними блоками. Якщо початок короткого циклу потрапляє на межу 64-байтної кеш-лінії, процесору потрібно два такти замість одного для завантаження тіла циклу в конвеєр. Компілятори намагаються вирівнювати мітки переходів за допомогою вставки інструкцій-заповнювачів (NOP padding), але зміна непов'язаного коду в сусідній функції може змістити адресу циклу на кілька байтів. Це явище називають **аномалією вирівнювання коду** (Code Alignment Anomaly). Воно може змінювати виміряний час одного й того самого алгоритму на 10–25% без жодної зміни у вихідному коді.

### 5. Когерентність кешів та фальшивий поділ (False Sharing)
У багатопотокових бенчмарках кілька ядер процесора можуть обробляти незалежні змінні, які випадково розташовані поруч у пам'яті (у межах однієї 64-байтної кеш-лінії). Коли одне ядро записує результат у свою змінну, апаратний протокол когерентності (MESI/MOESI) змушений інвалідувати всю кеш-лінію на всіх інших ядрах. Це спричиняє так званий **фальшивий поділ** (False Sharing, від англ. *false* — хибний + *sharing* — спільне використання), через який час виконання операції зростає з 1 наносекунди до 50–70 наносекунд на кожен запис. Усі структури даних у багатопотокових тестах повинні вирівнюватися за межею кеш-лінії за допомогою директиви `alignas(64)` або `__attribute__((aligned(64)))`.

## Пастки операційної системи: частота, ядра та джиттер

Програма виконується не у вакуумі, а під управлінням операційної системи, яка постійно змінює параметри заліза.

### 1. Динамічне масштабування частоти (DVFS та Turbo Boost)
Технології Intel Turbo Boost та AMD Precision Boost автоматично підвищують частоту окремих ядер за наявності запасу за температурою та струмом. Коли бенчмарк стартує, ядро може працювати на базовій частоті 2.4 ГГц. Через 100 мікросекунд процесор розганяється до 4.8 ГГц (час виконання операції падає вдвічі). Через 5 секунд безперервного тесту чип нагрівається, спрацьовує термотротлінг (Thermal Throttling), і частота просідає до 3.2 ГГц. Якщо порівнювати два алгоритми в такому режимі, переможе не кращий код, а той, що випадково запустився на піку турбо-частоти.

Для усунення цього джиттеру перед початком замірів частоту фіксують через говернор `performance`:
```bash
# Переведення всіх ядер у режим фіксованої максимальної частоти
sudo cpupower frequency-set -g performance
# Вимкнення Turbo Boost на процесорах Intel
echo "1" | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo
```

### 2. Стани сну процесора (C-States)
Для економії енергії бездіяльні ядра переводяться в глибокі стани сну (C1, C6). Вихід із стану C6 займає до 50 мікросекунд. Якщо бенчмарк запускається на щойно розбудженому ядрі, перша серія замірів отримує величезну штучну затримку. Обов'язкова фаза прогріву гарантує, що ядро перейде в активний стан C0 до початку запису часових міток.

### 3. Міграція потоків між ядрами та топологія NUMA
Планувальник ОС може в будь-який момент перенести потік бенчмарку на інше фізичне ядро. При цьому локальний L1/L2-кеш втрачається, конвеєр скидається, а виконання зупиняється на кілька мікросекунд. На багатопроцесорних серверах із топологією NUMA (Non-Uniform Memory Access) міграція на ядро іншого сокета призводить до того, що локальна пам'ять перетворюється на віддалену: звернення через шину UPI/Infinity Fabric додає 50–100 нс до кожного промаху кешу. Для стабільності потік необхідно жорстко прив'язувати до виділеного ізольованого ядра процесора за допомогою системного виклику `sched_setaffinity()` у Linux або через параметр ядра `isolcpus`.

## Таймери високої точності та вартість спостереження

Для вимірювання наносекундних проміжків використовують апаратний лічильник тактів процесора — регістр TSC (Time Stamp Counter), доступний через асемблерну інструкцію `RDTSC`. На сучасних процесорах лічильник TSC є «інваріантним» (Invariant TSC): він збільшується з фіксованою базовою частотою незалежно від поточних змін частоти ядра чи переходу в турбо-режим.

Проте на процесорах з позачерговим виконанням інструкція `RDTSC` не є бар'єром конвеєра: процесор може виконати читання таймера раніше або пізніше за досліджуваний код. Щоб зафіксувати точні межі, застосовують **серіалізацію інструкцій** (Instruction Serialization, від лат. *series* — ряд, послідовність) за допомогою бар'єра `LFENCE`:

:::tabs
```c
/* Читання серіалізованого лічильника тактів на C */
static inline uint64_t rdtsc_start(void) {
    uint32_t cycles_high, cycles_low;
    asm volatile("lfence\n\t"
                 "rdtsc\n\t"
                 : "=a"(cycles_low), "=d"(cycles_high));
    return ((uint64_t)cycles_high << 32) | cycles_low;
}

static inline uint64_t rdtsc_end(void) {
    uint32_t cycles_high, cycles_low;
    asm volatile("rdtscp\n\t"
                 "lfence\n\t"
                 : "=a"(cycles_low), "=d"(cycles_high)
                 :
                 : "rcx");
    return ((uint64_t)cycles_high << 32) | cycles_low;
}
```
```cpp

inline std::uint64_t rdtsc_start() noexcept {

                 "lfence\n\t"
```

Інструкція `LFENCE` гарантує, що всі попередні інструкції завершили виконання до читання `RDTSC`, а `RDTSCP` чекає завершення всіх інструкцій усередині вимірюваного блоку.

Читання монотонного годинника ОС через `clock_gettime(CLOCK_MONOTONIC_RAW)` працює через механізм vDSO безпосередньо в просторі користувача без виконання важкого системного виклику ядра, але додає фіксовані накладні витрати (близько 15–25 нс). Цей зсув називають **накладними витратами вимірювача** (`t_bias`). Його значення необхідно один раз виміряти на порожньому виклику й віднімати від загального результату.

## Протокол прогону: калібрування ітерацій та батчинг

Якщо операція триває 3 наносекунди, а роздільна здатність таймера становить 20 наносекунд, прямий замір однієї ітерації дає похибку понад 600%. Для подолання дискретності таймера застосовують **групування в батчі** (Batching): операцію повторюють у внутрішньому циклі `N` разів, вимірюють сумарний час батчу `Δt_batch`, після чого обчислюють ефективний час однієї операції:

```
t_effective
= (Δt_batch − t_bias) / N       [розрахунок чистого часу однієї ітерації в батчі]
```

Розмір батчу `N` підбирається автоматично під час фази калібрування так, щоб загальний час вимірювання одного зразка складав не менше 2–5 мілісекунд (що перевищує роздільність таймера у 100 000 разів).

![Конвеєр мікробенчмарку](/root/eng/sf-release/microbenchmarking/img/microbenchmark-pipeline.svg)
*Конвеєр надійного мікробенчмаркінгу. Послідовність із п'яти етапів гарантує ізоляцію процесорного ядра, стабілізацію стану кеш-пам'яті, усунення дискретності таймера та захист від компиляторних спрощень.*

Повну реалізацію такого тестового рушія з калібруванням і прив'язкою до ядра наведено у вставці [Автономний каркас мікробенчмаркінгу](root:sf-release/microbenchmarking/proj-custom-microbenchmark.md).

## Статистична обробка: оманливість середнього та влада перцентилів

Найпоширеніша помилка аналізу мікробенчмарків — обчислення середнього арифметичного та стандартного відхилення. Середнє арифметичне спирається на припущення про симетричний нормальний розподіл помилок, якого в мікроархітектурі не існує.

Розподіл затримок у комп'ютері завжди є **багатомодальним** (Multimodal, від лат. *modus* — міра, спосіб):
- Перший пік (найвищий): попадання в L1-кеш (швидкі ітерації);
- Другий пік: попадання в L2/L3-кеш;
- Третій пік: звернення до оперативної пам'яті;
- Довгий шлейф (хвіст розподілу): затримки через переривання ОС та перемикання контексту.

![Багатомодальний розподіл](/root/eng/sf-release/microbenchmarking/img/multimodal-latency-distribution.svg)
*Багатомодальний розподіл затримки мікробенчмарку. Дискретні піки відповідають різним рівням кеш-пам'яті та оперативної пам'яті. Середнє арифметичне спотворюється рідкісними перериваннями ОС і потрапляє в порожній проміжок, тоді як медіана (p50) та перцентилі (p95, p99) точно описують реальну поведінку системи.*

Якщо серед 1000 замірів по 4 наносекунди трапиться один замір на 50 000 наносекунд (спрацював обробник мережевого пакета), середнє арифметичне підскочить до 54 наносекунд. Воно опиниться в зоні, де процесор не провів жодної реальної ітерації алгоритму.

Для коректного опису використовують непараметричну рангову статистику:
1. **Медіана (`p50`, від лат. *medianus* — середній):** значення, що ділить відсортовану вибірку навпіл. Вона відображає істинну швидкість гарячого тракту алгоритму й абсолютно нечутлива до поодиноких сплесків.
2. **Інтерквартильний розмах (`IQR = Q3 - Q1`, від лат. *inter* — між + *quartus* — четвертий):** діапазон, у якому лежать центральні 50% усіх замірів. Він характеризує стабільність виміру.
3. **Хвостові перцентилі (`p95`, `p99`, `p99.9`):** максимальний час, у який вкладається відповідний відсоток операцій, що показує поведінку системи під навантаженням.

Математичні формули інтерполяції квантилів, правила відсікання аномалій та методику непараметричного бутстреп-порівняння викладено у вставці [Статистика вимірювання затримок](root:sf-release/microbenchmarking/math-latency-distribution.md).

## Практичний приклад: надійний вимір алгоритму

Нижче наведено закінчений приклад мікробенчмарку для порівняння двох методів підрахунку встановлених бітів (Population Count): наївного побітового зсуву та апаратної інструкції `popcnt`.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include <time.h>
#include <sched.h>

static inline void do_not_optimize(uint64_t v) {
    __asm__ volatile("" : : "r,m"(v) : "memory");
}

static inline uint64_t get_time_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return (uint64_t)ts.tv_sec * 1000000000ULL + (uint64_t)ts.tv_nsec;
}

/* Метод 1: Наївний побітовий прохід */
static uint64_t popcount_naive(uint64_t x) {
    uint64_t count = 0;
    while (x) {
        count += (x & 1ULL);
        x >>= 1ULL;
    }
    return count;
}

/* Метод 2: Вбудована апаратна інструкція CPU (POPCNT) */
static uint64_t popcount_builtin(uint64_t x) {
    return (uint64_t)__builtin_popcountll(x);
}

typedef uint64_t (*PopcountFn)(uint64_t);

static double benchmark_popcount(PopcountFn fn, const uint64_t *data, size_t size, size_t iters) {
    // Фаза прогріву
    for (size_t i = 0; i < size; ++i) {
        uint64_t res = fn(data[i]);
        do_not_optimize(res);
    }

    uint64_t t0 = get_time_ns();
    for (size_t it = 0; it < iters; ++it) {
        for (size_t i = 0; i < size; ++i) {
            uint64_t res = fn(data[i]);
            do_not_optimize(res);
        }
    }
    uint64_t dt = get_time_ns() - t0;
    return (double)dt / (double)(size * iters);
}

int main(void) {
    // Фіксація потоку на ядрі 0 для усунення міграції
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(0, &cpuset);
    sched_setaffinity(0, sizeof(cpu_set_t), &cpuset);

    const size_t N = 1024;
    uint64_t test_data[N];
    for (size_t i = 0; i < N; ++i) {
        test_data[i] = ((uint64_t)rand() << 32) | (uint64_t)rand();
    }

    double t_naive = benchmark_popcount(popcount_naive, test_data, N, 10000);
    double t_builtin = benchmark_popcount(popcount_builtin, test_data, N, 10000);

    printf("popcount_naive:   %.3f нс / операція\n", t_naive);
    printf("popcount_builtin: %.3f нс / операція\n", t_builtin);
    printf("Прискорення:      %.2fx\n", t_naive / t_builtin);

    return 0;
}
```

```cpp
#include <iostream>
#include <vector>
#include <random>
#include <chrono>
#include <cstdint>
#include <bit>
#include <iomanip>
#include <pthread.h>

namespace bench {

template <typename T>
inline void do_not_optimize(T&& val) {
    #if defined(__clang__)
    asm volatile("" : "+r,m"(val) : : "memory");
    #else
    asm volatile("" : : "g"(val) : "memory");
    #endif
}

inline bool pin_to_core(int core_id) noexcept {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);
    return pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset) == 0;
}

} // namespace bench

// Метод 1: Наївний побітовий прохід
uint64_t popcount_naive(uint64_t x) noexcept {
    uint64_t count = 0;
    while (x) {
        count += (x & 1ULL);
        x >>= 1ULL;
    }
    return count;
}

// Метод 2: Стандартний C++20 std::popcount (апаратна інструкція POPCNT)
uint64_t popcount_std(uint64_t x) noexcept {
    return static_cast<uint64_t>(std::popcount(x));
}

template <typename Func>
double measure(Func&& fn, const std::vector<uint64_t>& data, std::size_t iters) {
    using clock = std::chrono::high_resolution_clock;

    // Фаза прогріву
    for (const auto val : data) {
        auto res = fn(val);
        bench::do_not_optimize(res);
    }

    const auto t0 = clock::now();
    for (std::size_t it = 0; it < iters; ++it) {
        for (const auto val : data) {
            auto res = fn(val);
            bench::do_not_optimize(res);
        }
    }
    const auto dt = std::chrono::duration_cast<std::chrono::nanoseconds>(clock::now() - t0);
    return static_cast<double>(dt.count()) / static_cast<double>(data.size() * iters);
}

int main() {
    bench::pin_to_core(0);

    constexpr std::size_t N = 1024;
    std::mt19937_64 rng(1337);
    std::vector<uint64_t> test_data(N);
    for (auto& item : test_data) {
        item = rng();
    }

    const double t_naive = measure(popcount_naive, test_data, 10000);
    const double t_std = measure(popcount_std, test_data, 10000);

    std::cout << std::fixed << std::setprecision(3);
    std::cout << "popcount_naive: " << t_naive << " нс / операція\n";
    std::cout << "popcount_std:   " << t_std << " нс / операція\n";
    std::cout << "Прискорення:    " << (t_naive / t_std) << "x\n";

    return 0;
}
```

## Інженерна дисципліна та чекліст надійного бенчмарку

Перед тим як довіряти числам мікробенчмарку або додавати оптимізацію в кодову базу, обов'язково виконайте перевірку за інженерним чеклістом:

1. **Контроль асемблерного виходу:** скомпілюйте бенчмарк із прапорцем `-S` або перегляньте код через утиліту `objdump -d`. Переконайтеся, що тіло функції присутнє в асемблері й не згорнуте в константу.
2. **Перевірка бар'єрів оптимізації:** усі вхідні та вихідні змінні мають проходити крізь `benchmark::DoNotOptimize()`.
3. **Репрезентативність тестових даних:** вхідні дані мають бути псевдовипадковими та непередбачуваними, якщо тільки алгоритм спеціально не розрахований на впорядковані масиви.
4. **Ізоляція оточення:** частоту процесора зафіксовано (`cpupower`), Turbo Boost вимкнено, вимірювальний потік прив'язано до конкретного ядра (`taskset` / `sched_setaffinity`).
5. **Наявність фази прогріву:** перед початком замірів виконано не менше 10 000 ітерацій для стабілізації кешів і таблиць історії переходів.
6. **Достатній розмір батчу:** тривалість одного вимірюваного блоку перевищує 2 мілісекунди, щоб похибка таймера була меншою за 0.1%.
7. **Непараметрична оцінка:** для аналізу використовуються медіана `p50`, квартильний розмах `IQR` та перцентилі `p95/p99`, а не середнє арифметичне.
8. **Порівняння бінарних образів:** перевірте, чи не призвела зміна прапорців компілятора до регресії в інших функціях через зміщення вирівнювання або роздуття розміру коду.
