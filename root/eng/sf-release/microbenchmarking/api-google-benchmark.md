# 📋 Інтерфейс Google Benchmark: контракт бібліотеки та керування прогоном

Бібліотека Google Benchmark є загальновизнаним галузевим стандартом для написання мікробенчмарків на мовах C та C++. Вона інкапсулює управління життєвим циклом вимірювань, автоматичне калібрування ітерацій, статистичну агрегацію повторів, роботу з параметричними просторами та інтеграцію з низькорівневими апаратними лічильниками продуктивності. Проєктування бібліотеки спрямоване на усунення рутинного коду таймінгу, захист від оптимізацій компілятора та забезпечення високої повторюваності вимірів у контурах безперервної інтеграції. Нижче наведено структуровану довідку публічного інтерфейсу, макросів реєстрації, методів стану, правил конфігурації та параметрів командного рядка.

## Анатомія тестової функції та життєвий цикл State

Будь-який мікробенчмарк у системі реєструється як вільна функція (або метод класу-фікстури), що приймає посилання на об'єкт `benchmark::State`. Цей об'єкт керує процесом вимірювання, відліком часу та передачею вхідних параметрів:

```cpp
#include <benchmark/benchmark.h>
#include <vector>
#include <numeric>

static void BM_VectorAccumulate(benchmark::State& state) {
    const auto size = static_cast<std::size_t>(state.range(0));
    std::vector<int> data(size, 42);

    // Головний вимірювальний цикл: бібліотека автоматично підбирає
    // кількість проходів для досягнення стабільного часу заміру
    for (auto _ : state) {
        int sum = std::accumulate(data.begin(), data.end(), 0);
        benchmark::DoNotOptimize(sum);
    }

    // Реєстрація метрик оброблених даних
    state.SetBytesProcessed(static_cast<int64_t>(state.iterations()) *
                            static_cast<int64_t>(size * sizeof(int)));
    state.SetItemsProcessed(static_cast<int64_t>(state.iterations()) *
                            static_cast<int64_t>(size));
}
BENCHMARK(BM_VectorAccumulate)->Range(64, 1 << 16);
```

Під час запуску бібліотека виконує кілька фаз калібрування. Вона запускає цикл `for (auto _ : state)` зі зростаючою кількістю ітерацій (1, 10, 100, 1000...), доки сумарний час роботи не досягне значення, встановленого параметром `MinTime` (за замовчуванням 0.5 секунди). Час, витрачений на підготовку масиву `data` поза межами циклу `for (auto _ : state)`, не враховується у підсумковий результат.

### Публічні методи класу `benchmark::State`

| Метод | Сигнатура | Призначення та поведінка |
|---|---|---|
| `iterations()` | `uint64_t iterations() const` | Повертає загальну кількість виконаних ітерацій у поточному запуску вимірювального циклу. |
| `range()` | `int64_t range(size_t pos = 0) const` | Отримує цілочисельний параметр за вказаним індексом із набору аргументів, переданих через `->Arg()` або `->Range()`. |
| `PauseTiming()` | `void PauseTiming()` | Тимчасово зупиняє внутрішній таймер бенчмарку. Використовується для скидання стану структур даних або повторної ініціалізації між ітераціями. |
| `ResumeTiming()` | `void ResumeTiming()` | Відновлює відлік вимірювального часу після попереднього виклику `PauseTiming()`. |
| `SkipWithError()` | `void SkipWithError(const char* msg)` | Достроково перериває виконання бенчмарку та позначає прогін як помилковий із виведенням текстового повідомлення у звіт. |
| `SetBytesProcessed()` | `void SetBytesProcessed(int64_t bytes)` | Фіксує сумарний обсяг оброблених байтів для автоматичного розрахунку пропускної здатності пам'яті (MB/s або GB/s). |
| `SetItemsProcessed()` | `void SetItemsProcessed(int64_t items)` | Фіксує кількість оброблених структурних елементів для розрахунку питомої швидкості (items/s або ops/s). |
| `SetComplexityN()` | `void SetComplexityN(int64_t n)` | Передає поточний розмір вхідної задачі `N` для автоматичної регресійної оцінки асимптотичної складності (Big-O). |

## Бар'єри компілятора (Optimization Barriers)

Для запобігання фальсифікації результатів оптимізатором бібліотека надає два низькорівневі апаратні бар'єри:

### 1. `benchmark::DoNotOptimize(const T& value)`
Ця функція реалізована через асемблерну інструкцію з розширеними обмеженнями входу. Вона змушує компілятор вважати, що змінна `value` прочитана й збережена в регістрі або комірці пам'яті, що блокує видалення мертвого коду (Dead Code Elimination).

```cpp
// Примушує обчислити функцію та зберегти результат у регістрі
uint64_t res = compute_heavy_hash(input);
benchmark::DoNotOptimize(res);
```

### 2. `benchmark::ClobberMemory()`
Цей бар'єр інформує компілятор про те, що весь простір оперативної пам'яті міг бути довільно модифікований або прочитаний стороннім кодом. Це унеможливлює винесення операцій запису за межі виклику (Store Hoisting) та примушує транслятор скидати значення регістрів у пам'ять перед виконанням наступних кроків.

```cpp
// Забезпечує, що всі попередні записи у вектор дійсно завершені в пам'яті
data[idx] = new_value;
benchmark::ClobberMemory();
```

## Декларативна параметризація простору аргументів

Google Benchmark підтримує гнучку систему конфігурації вхідних параметрів за допомогою ланцюжкових викликів (Fluent Interface):

```cpp
// 1. Поодинокі аргументи або фіксовані списки розмірів
BENCHMARK(BM_Sort)->Arg(100)->Arg(1000)->Arg(10000);
BENCHMARK(BM_MatrixMul)->Args({32, 32})->Args({64, 64});

// 2. Геометрична шкала: від 8 до 8192 з множником 8 (8, 64, 512, 4096)
BENCHMARK(BM_Lookup)->RangeMultiplier(8)->Range(8, 8192);

// 3. Декартовий добуток діапазонів (2D/3D матриця параметрів)
BENCHMARK(BM_Transform)->ArgsProduct({
    benchmark::CreateRange(8, 512, 8),
    {1, 2, 4, 8} // кількість потоків або каналів
});

// 4. Налаштування тривалості, повторів та статистичної агрегації
BENCHMARK(BM_NetworkSend)
    ->MinTime(1.5)                 // Мінімальний час прогону (1.5 секунди)
    ->Repetitions(10)              // 10 незалежних прогонів для статистики
    ->ReportAggregatesOnly(true)   // Виводити лише Mean/Median/StdDev
    ->DisplayAggregatesOnly(true);
```

## Внутрішній таймінг: CPU Time проти Real Time (Wall-clock)

За замовчуванням бібліотека фіксує дві часові метрики одночасно:
1. **CPU Time (процесорний час):** сумарний час, проведений ядрами процесора в просторі користувача та ядра ОС при виконанні інструкцій цього процесу (вимірюється через системний виклик `clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` або `CLOCK_THREAD_CPUTIME_ID`). Цей таймер ігнорує час, коли потік спав, чекав на м'ютекс або був витіснений планувальником ОС.
2. **Real Time (фізичний астрономічний час):** різниця показань монотонного годинника від старту до завершення заміру (`CLOCK_MONOTONIC`).

У однопотокових обчисленнях обидва показники практично збігаються. Проте в багатопотокових бенчмарках процесорний час підсумовується по всіх ядрах (на 8 потоках 1 секунда реального часу перетворюється на 8 секунд CPU-часу). Виклик методу `->UseRealTime()` примушує бібліотеку обчислювати затримку на одну операцію за фізичним годинником, що є єдино правильним підходом для тестування блокувальних структур даних, черг повідомлень та паралельних алгоритмів.

## Багатопотоковість та асимптотична складність

### Багатопотоковий бенчмаркінг
Бібліотека підтримує паралельне тестування багатопотокових структур даних. При вказанні методу `->Threads(N)` або `->ThreadRange(min, max)` бібліотека автоматично створює відповідну кількість робочих потоків ОС і синхронізує їхній одночасний старт за допомогою внутрішнього бар'єра синхронізації:

```cpp
static void BM_ConcurrentQueue(benchmark::State& state) {
    static LockFreeQueue queue;
    for (auto _ : state) {
        if (state.thread_index() == 0) {
            queue.push(42);
        } else {
            queue.pop();
        }
    }
}
BENCHMARK(BM_ConcurrentQueue)->ThreadRange(1, 16)->UseRealTime();
```

Кожен потік виконує власну копію функції бенчмарку, маючи доступ до свого ідентифікатора через `state.thread_index()`. Вимірювальний час завершується лише тоді, коли всі паралельні потоки повністю завершать призначену кількість ітерацій.

### Автоматичний розрахунок складності (Big-O)
Google Benchmark вміє автоматично перевіряти теоретичну асимптотичну складність алгоритму. Для цього в циклі передається розмір задачі `state.SetComplexityN(n)`, а при реєстрації вказується очікуваний клас складності:

```cpp
static void BM_BinarySearch(benchmark::State& state) {
    const auto n = state.range(0);
    std::vector<int> v(n);
    std::iota(v.begin(), v.end(), 0);

    for (auto _ : state) {
        bool found = std::binary_search(v.begin(), v.end(), n / 2);
        benchmark::DoNotOptimize(found);
    }
    state.SetComplexityN(n);
}
BENCHMARK(BM_BinarySearch)->Range(64, 1 << 20)->Complexity(benchmark::oLogN);
```

Під час аналізу результатів бібліотека виконує регресійну апроксимацію методом найменших квадратів, підбираючи коефіцієнти для обраної моделі (`o1`, `oN`, `oLogN`, `oNLogN`, `oN_Square`, `oAuto`), та виводить коефіцієнт кореляції та константу нахилу кривої.

## Інтеграція з апаратними лічильниками Linux Perf

Бібліотека вміє збирати апаратні лічильники продуктивності процесора (Performance Monitoring Counters, PMC) безпосередньо під час виконання заміру через системний виклик `perf_event_open`. Для цього бенчмарк запускається з прапорцем `--benchmark_perf_counters`:

```bash
./my_bench --benchmark_perf_counters="CYCLES,INSTRUCTIONS,BRANCH-MISSES,L1D-LOADS,L1D-LOAD-MISSES"
```

У підсумковій таблиці з'являються додаткові стовпчики:
- `INSTRUCTIONS / CYCLES (IPC)` — середня кількість інструкцій, що виконуються за один такт процесора (показник ефективності утилізації конвеєра);
- `BRANCH-MISSES` — абсолютна кількість та відсоток помилок передбачення переходів;
- `L1D-LOAD-MISSES` — кількість промахів повз кеш даних першого рівня.

Це дозволяє точно локалізувати причину сповільнення: чи сталося воно через зростання кількості машинних інструкцій, чи через простої конвеєра в очікуванні пам'яті.

## Керування прогоном через прапорці командного рядка (CLI)

Після збирання виконуваного файлу прогоном можна гнучко керувати без перекомплікації за допомогою системних прапорців:

| Прапорець | Приклад використання | Опис дії |
|---|---|---|
| `--benchmark_filter` | `--benchmark_filter=BM_Vector.*` | Фільтрує запуск тестів за регулярним виразом назви. |
| `--benchmark_min_time` | `--benchmark_min_time=2.0s` | Задає мінімальний час калібрування кожного бенчмарку. |
| `--benchmark_repetitions` | `--benchmark_repetitions=15` | Виконує вказану кількість незалежних повторів кожного тесту для статистичної обробки. |
| `--benchmark_format` | `--benchmark_format=json` | Формат виведення в консоль (`console`, `json`, `csv`). |
| `--benchmark_out` | `--benchmark_out=results.json` | Шлях до файлу для збереження результатів прогону. |
| `--benchmark_out_format` | `--benchmark_out_format=json` | Формат запису у файл (`json`, `csv`, `console`). |
| `--benchmark_color` | `--benchmark_color=false` | Примусове вмикання або вимикання кольорового ANSI-форматування термінала. |
| `--benchmark_perf_counters` | `--benchmark_perf_counters=CYCLES,INSTRUCTIONS` | Інтеграція з підсистемою `perf` ядра Linux для збору апаратних лічильників CPU. |

Типовий виклик для збереження відтворюваного звіту в системі неперервної інтеграції (CI/CD):
```bash
./my_benchmarks --benchmark_filter="BM_Hash.*" \
                --benchmark_repetitions=10 \
                --benchmark_min_time=1.0s \
                --benchmark_format=console \
                --benchmark_out=perf_report.json \
                --benchmark_out_format=json
```

## Неперервний бенчмаркінг у CI/CD (Continuous Benchmarking)

Для автоматичного відстеження регресій продуктивності між комітами утиліта постачається зі скриптом `compare.py`. Він приймає два JSON-звіти (базовий `main.json` та тестовий `pr.json`) і проводить непараметричну статистичну перевірку гіпотези (U-критерій Манна-Вітні):

```bash
# Порівняння базової гілки та пул-реквесту
python3 /path/to/compare.py benchmarks main_report.json pr_report.json
```

Скрипт виводить таблицю змін у відсотках із позначенням статистичної достовірності (p-value): якщо час виконання збільшився на 5%, але p-value > 0.05, система визнає зміну статистичним шумом і не блокує збірку.

## Інженерні пастки використання бібліотеки

1. **Виділення динамічної пам'яті всередині циклу:** Якщо викликати `new`, `malloc` або змінювати розмір `std::vector` всередині `for (auto _ : state)`, бенчмарк вимірюватиме роботу системного алокатора пам'яті та конкуренцію за м'ютекси купи, а не цільовий алгоритм. Усі буфери мають виділятися до входу в цикл вимірювання.
2. **Перетворення типів при передачі в бар'єр:** Передача тимчасового об'єкта або rvalue-посилання в `DoNotOptimize` вимагає сумісності компілятора. На старих версіях Clang некоректне використання константних посилань могло призводити до зайвого копіювання об'єкта на стек.
3. **Нехтування прогрівом фікстур:** При використанні класів `benchmark::Fixture` метод `SetUp(const benchmark::State&)` викликається перед кожним окремим запуском, але не прогріває L1-кеш для самого вимірювального циклу. Перші кілька ітерацій усередині першого батчу можуть мати підвищену затримку через вибірку інструкцій.
4. **Некоректний підрахунок оброблених байтів:** Якщо викликати `state.SetBytesProcessed(N)` всередині тіла `for (auto _ : state)`, підсумкове число буде перемножене на кількість ітерацій двічі. Метод слід викликати рівно один раз після завершення циклу, передаючи загальну кількість байтів за всі ітерації.
