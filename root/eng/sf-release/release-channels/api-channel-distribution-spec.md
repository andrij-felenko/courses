# 📋 Специфікація протоколу та маніфестів доставки каналів оновлення

Сервер доставки каналів виконує роль авторизованого джерела правди (англ. *Authoritative Source of Truth*) для розподіленого парку пристроїв та клієнтських додатків. Протокол базується на принципах безпечного оновлення фреймворку TUF (The Update Framework) та відкритих специфікаціях Omaha від Google. Архітектура протоколу суворо розмежовує два функціональні рівні: рівень декларативних підписаних метаданих (канальних маніфестів) та рівень роздачі бінарних блобів (образів прошивок, кореневих файлових систем, контейнерів або пакетів).

Взаємодія між клієнтськими агентами та сервером конфігурацій відбувається через захищений транспортний протокол HTTPS/TLS 1.3. Для захисту від атак типу «людина посередині» (MitM) та підміни DNS клієнтський стек використовує механізм фіксації сертифікатів (англ. *Certificate Pinning*), де кореневі відкриті ключі інфраструктури відбитків зашиті в незмінну пам'ять завантажувача.

## 1. Специфікація ендпоінтів сервера доставки

### 1.1. Періодичне опитування стану каналу (Update Polling)

Клієнтський демон за розкладом або у відповідь на подію системного тригера виконує POST-запит до точки входу оновлень. Запит містить повний контекст апаратного та програмного стану вузла, що дозволяє серверу ухвалювати рішення про видачу конкретного бінарного артефакту.

```http
POST /v1/channels/poll HTTP/1.1
Host: ota.fleet.internal
User-Agent: FleetOTA-Agent/2.4 (Linux armv7l; SoC STM32MP157C)
Content-Type: application/json
Accept: application/json
X-Device-Signature: t=1724810400,v1=9f83a2b1c4e6...
```

#### Тіло запиту клієнта (Client Polling Payload)

```json
{
  "protocol_version": "2.0",
  "client_id": "urn:uuid:8b3e4f1a-9c7d-41a2-b8e5-3d2f1c0e9a74",
  "hardware": {
    "board_revision": "rev-c2",
    "soc_model": "STM32MP157C",
    "secure_boot_enabled": true,
    "efuse_channel_lock": "lts"
  },
  "current_state": {
    "active_partition": "bank_a",
    "installed_version": "1.4.2",
    "installed_channel": "lts",
    "subscribed_channel": "lts",
    "rollback_counter": 1420,
    "uptime_seconds": 864200,
    "last_boot_successful": true
  },
  "telemetry_summary": {
    "crash_count_24h": 0,
    "memory_pressure_events": 0,
    "storage_free_bytes": 104857600
  },
  "auth": {
    "device_cert_fingerprint": "SHA256:7e8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b",
    "channel_token": "ctkn_live_lts_89a1f2c3e4b5"
  }
}
```

#### Поля клієнтського запиту:
* `protocol_version`: версія протоколу канального обміну (фіксує формат структур і підписів).
* `client_id`: глобально унікальний ідентифікатор пристрою (UUIDv4 або апаратний хеш крипточипа ATECC608A).
* `hardware.board_revision`: ревізія друкованої плати, що визначає сумісність дерева пристроїв (Device Tree).
* `hardware.efuse_channel_lock`: апаратне обмеження каналу, зчитане з регістрів OTP-пам'яті процесора.
* `current_state.active_partition`: поточний завантажений розділ (`bank_a` або `bank_b`).
* `current_state.rollback_counter`: апаратний монотонний лічильник версії для захисту від відкоту.
* `auth.channel_token`: криптографічний сесійний токен, виданий сервером авторизації під час реєстрації вузла.

## 2. Структура маніфесту оновлення каналу

Коли для запитаного каналу стає доступною нова версія, яка перевищує поточний `installed_version`, відповідає апаратній сумісності та задовольняє політику поступового викочування, сервер повертає статус `200 OK` із підписаним маніфестом.

```json
{
  "manifest_version": "2.0",
  "generated_at": "2026-08-28T03:00:00Z",
  "expires_at": "2026-08-28T15:00:00Z",
  "channel": {
    "name": "lts",
    "tier": "tier_industrial",
    "minimum_soak_days": 30,
    "key_ring_id": "kr_lts_2026_v1"
  },
  "release": {
    "version": "1.4.4",
    "semver": "1.4.4+lts.b214",
    "release_type": "security_fix",
    "criticality": "high",
    "rollback_counter_min": 1440,
    "allowed_source_versions": ["1.4.0", "1.4.1", "1.4.2", "1.4.3"]
  },
  "artifact": {
    "target_partition": "bank_b",
    "format": "raucb_bundle",
    "size_bytes": 28456120,
    "sha256": "4b6f12a8c3d9e0f7a1b2c3d4e5f60718293a4b5c6d7e8f9a0b1c2d3e4f5a6b7c",
    "mirrors": [
      "https://cdn-a.fleet.internal/blobs/firmware-1.4.4-lts.raucb",
      "https://cdn-b.fleet.internal/blobs/firmware-1.4.4-lts.raucb"
    ]
  },
  "preconditions": {
    "minimum_free_space_bytes": 67108864,
    "minimum_battery_charge_pct": 50,
    "disallowed_system_states": ["actuator_in_motion", "safety_interlock_open"]
  },
  "signatures": [
    {
      "key_id": "key_hsm_lts_signer_01",
      "algorithm": "ed25519",
      "sig": "MEQCICv3y9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c2"
    },
    {
      "key_id": "key_hsm_lts_signer_02",
      "algorithm": "ed25519",
      "sig": "MEQCIA3k9f8e7d6c5b4a3f2e1d0c9b8a7f6e5d4c3b2a1f0e9d8c7b6a5f4e3d2c"
    }
  ]
}
```

#### Поля маніфесту оновлення:
* `generated_at` / `expires_at`: часові мітки дійсності маніфесту. Запобігають атакам повторного відтворення (англ. *replay attacks*).
* `channel.name`: цільовий канал постачання (`nightly`, `beta`, `stable`, `lts`).
* `release.rollback_counter_min`: мінімальне значення апаратного лічильника захисту від відкоту. Якщо залізо має більше значення, ніж указано в маніфесті, агент відхиляє оновлення.
* `release.allowed_source_versions`: список версій, із яких дозволено пряме оновлення. Захищає від пропуску проміжних критичних міграцій файлової системи чи завантажувача.
* `artifact.format`: формат пакета оновлення (`raucb_bundle`, `swupdate_cpio`, `ostree_commit`, `fit_image`).
* `artifact.sha256`: криптографічний геш усього бінарного файлу для перевірки цілісності після завантаження.
* `signatures`: масив цифрових підписів. Для каналу LTS вимагається наявність кількох підписів незалежних ключів згідно з порогом кворуму.

## 3. Модель криптографічної ієрархії ключів за каналами

Сервер оновлень та клієнтський демон реалізують ієрархічну модель розподілу довіри. Кожен канал оновлення функціонує як незалежний домен безпеки зі своїм набором відкритих ключів (Key Ring).

```text
                               КОРІНЬ ДОВІРИ (Root of Trust)
                                          │
       ┌──────────────────┬───────────────┴───────────────┬──────────────────┐
       ▼                  ▼                               ▼                  ▼
[ Nightly Ring ]    [ Beta Ring ]                  [ Stable Ring ]     [ LTS Ring ]
  1 ключ (CI)       2 ключі (Lead Dev)             3 ключі (SecOps)   Кворум 3-з-5 (HSM)
```

### Таблиця параметрів криптографічних ланцюжків каналів

| Канал | Алгоритм підпису | Розташування приватного ключа | Вимоги до кворуму | Термін дії сертифіката |
|---|---|---|---|---|
| **Nightly** | Ed25519 | Автоматичний сервісний Vault у CI/CD | 1-з-1 (автопідпис) | 30 днів (щомісячна ротація) |
| **Beta** | Ed25519 | Розподілений Secret Manager реліз-інженерів | 1-з-2 підписи | 90 днів |
| **Stable** | ECDSA P-256 / Ed25519 | Мережевий апаратний HSM у датацентрі | 2-з-3 підписи | 1 рік |
| **LTS** | RSA-4096 / Ed25519 | Офлайн-HSM у фізичному сейфі | 3-з-5 (кворум директорів безпеки) | 3 роки |

Клієнтський пристрій під час валідації маніфесту вибирає зв'язку ключів, яка відповідає **поточному підписаному каналу пристрою**, а не текстовому полю з маніфесту. Це унеможливлює підміну ключів шляхом фальсифікації назви каналу в тілі відповіді.

## 4. Верифікація метаданих за стандартом TUF (The Update Framework)

Для забезпечення максимального захисту від компрометації серверної інфраструктури протокол реалізує чотирирівневу верифікацію метаданих за стандартом TUF:

1. **Кореневі метадані (Root Metadata):** визначають список довірених відкритих ключів для всіх інших ролей. Підписуються довгоживучими офлайн-ключами. Оновлюються лише у разі планової або аварійної ротації ключів інфраструктури.
2. **Метадані цілей (Targets Metadata):** містять список доступних бінарних артефактів для кожного каналу, їхні точні розміри в байтах та криптографічні хеші SHA-256. Підписуються реліз-інженерами або HSM-модулями каналів.
3. **Метадані знімка (Snapshot Metadata):** фіксують точні версії всіх файлів цілей, унеможливлюючи атаку часткового оновлення (Mix-and-Match Attack), коли зловмисник намагається підсунути старий уразливий пакет разом із новим маніфестом.
4. **Метадані часової мітки (Timestamp Metadata):** мають короткий термін дії (від кількох годин до доби) і підписуються онлайн-сервером оновлень. Захищають від атак заморозки стану (Freeze Attacks), коли клієнту блокують інформацію про вихід патчів безпеки.

## 5. Дельта-оновлення та оптимізація бінарного трафіку

Для економії стільникового трафіку в розподілених IoT-мережах сервер підтримує генерацію бінарних дельт між послідовними версіями каналу. Замість повного образу розміром 30–50 МБ клієнт завантажує диференційний патч розміром 2–5 МБ.

Процес побудови та застосування дельти складається з трьох послідовних кроків:
1. **Генерація дельти на сервері:** утиліти `casync` або `rauc` обчислюють бінарну різницю між образом вихідної версії `v1.4.2` та нової версії `v1.4.4` за алгоритмом блокового гешування (Chunked Content-Addressable Storage).
2. **Передача чанків:** маніфест містить список відсутніх блоків даних та їхніх SHA-256 хешів. Клієнт завантажує виключно змінені блоки.
3. **Реконструкція образу на пристрої:** клієнтський демон читає старі блоки з активного банку `Bank A`, об'єднує їх із завантаженими новими блоками та послідовно записує реконструйований повний образ у пасивний банк `Bank B`. Після завершення запису обчислюється підсумковий хеш цільового розділу, який зобов'язаний суворо збігатися з контрольним значенням `artifact.sha256`.

## 6. Специфікація кодів помилок клієнта та сервера

| Код помилки | HTTP статус | Причина виникнення | Дія клієнтського агента |
|---|---|---|---|
| `ERR_CHANNEL_FORBIDDEN` | `403 Forbidden` | Пристрій із апаратним замком (eFuse) намагається підписатися на несанкціонований канал (наприклад, `lts` запитує `nightly`). | Негайно перервати сесію, зафіксувати спробу несанкціонованого доступу в системному журналі безпеки, залишитися на чинній прошивці. |
| `ERR_ROLLBACK_BLOCKED` | `409 Conflict` | Значення `rollback_counter_min` у маніфесті менше за поточний лічильник безпеки в пам'яті NVRAM. | Відкинути маніфест без завантаження бінарного блоба (захист від Downgrade Attack). |
| `ERR_SIGNATURE_MISMATCH` | `422 Unprocessable` | Жоден із наданих цифрових підписів не збігається з публічними сертифікатами локального Keyring цільового каналу. | Відкинути пакет, заблокувати адресу CDN, повторити спробу через резервний контур. |
| `ERR_PRECONDITION_FAILED` | `412 Precondition` | Заряд акумулятора менше 50% або вільний обсяг флеш-пам'яті не задовольняє вимоги розпакування образу. | Відкласти встановлення до переходу системи в безпечний стан заряджання. |
| `ERR_CHANNEL_DEPRECATED` | `410 Gone` | Поточний канал виведено з експлуатації (наприклад, закриття бета-тестування версії 2025 року). | Автоматично перемкнутися на відповідний базовий стабільний канал (`stable`). |

## 7. Протокол звітування та фіксації успішного запуску (Commit Handshake)

Процес оновлення вважається завершеним лише після проходження фази підтвердження працездатності (англ. *Health Check Confirmation*). 

Після запису образу в пасивний розділ `bank_b`, перемикання прапорця завантажувача U-Boot та першого успішного старту (відпрацювання сторожового таймера watchdog без аварійного перезавантаження), клієнт зобов'язаний надіслати підтвердження:

```http
POST /v1/channels/commit HTTP/1.1
Host: ota.fleet.internal
Content-Type: application/json

{
  "client_id": "urn:uuid:8b3e4f1a-9c7d-41a2-b8e5-3d2f1c0e9a74",
  "confirmed_version": "1.4.4",
  "active_partition": "bank_b",
  "status": "boot_successful",
  "verification_duration_ms": 1420,
  "telemetry_health": {
    "selftest_passed": true,
    "sensors_online_count": 8,
    "bus_error_count": 0
  }
}
```

Сервер оновлень фіксує успішну міграцію вузла, додає одиницю до лічильника безаварійних сесій каналу та оновлює індекс прогресивного розгортання для наступних когорт пристроїв парку.
