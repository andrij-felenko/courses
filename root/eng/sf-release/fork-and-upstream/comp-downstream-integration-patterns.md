# 🔌 Архітектурні патерни інтеграції з апстримом: монолітний форк, сабмодулі, West та Yocto meta-шари

Під час проектування комерційного продукту на базі відкритої платформи (операційної системи реального часу, ядра загального призначення чи бібліотеки драйверів) вибір способу фізичної інтеграції стороннього коду визначає вартість супроводу системи на роки вперед. У практиці інженерії сформувалося п'ять основних архітектурних патернів підключення апстриму.

---

## 1. Монолітний довгоживучий Git-форк (Raw Monolithic Fork)

Організація створює прямий клон репозиторію апстриму у власному просторі імен (наприклад, у внутрішньому GitLab чи GitHub Enterprise). Усі локальні доопрацювання — драйвери, конфігурації плат, прикладний код і латки — фіксуються безпосередньо у гілках цього репозиторію.

```text
my-product-firmware/ (Єдиний Git-репозиторій — повний клон апстриму)
├── arch/                  <- Змішаний код апстриму та локальні патчі
├── drivers/
│   ├── i2c/               <- Змінений апстрим-драйвер
│   └── proprietary_sensor/<- Власний драйвер, доданий прямо в дерево
├── boards/custom_board/   <- Опис плати
└── app/                   <- Прикладний код
```

* **Переваги:** простота старту (не вимагає додаткових інструментів крім стандартного клієнта Git); атомарні коміти, що охоплюють зміни в ядрі та застосунку одночасно; тривіальний пошук за кодом (`git grep`).
* **Недоліки:** катастрофічне наростання боргу злиття; межа між власним кодом і сторонньою бібліотекою розмивається; ризик випадкового витоку комерційної таємниці під час публікації патчів або втрати ліцензійної чистоти.

## 2. Git Submodules (Апстрим як зафіксований зовнішній репозиторій)

Власний проєкт живе в окремому репозиторії, а незмінний вихідний код апстриму підключається як підмодуль (англ. *git submodule*) у підкаталог через файл `.gitmodules`. Головний репозиторій зберігає лише посилання на конкретний хеш коміту в апстримі.

```text
my-product-repo/ (Головний приватний репозиторій)
├── .gitmodules            <- Вказує URL апстриму та шлях vendor/zephyr
├── app/                   <- Прикладний код продукту
├── drivers/custom/        <- Власні драйвери
├── bsp/                   <- Описи плат
└── vendor/
    └── zephyr/            <- Незмінний чистий репозиторій апстриму (submodule)
```

```ini
# Вміст файлу .gitmodules
[submodule "vendor/zephyr"]
    path = vendor/zephyr
    url = https://github.com/zephyrproject-rtos/zephyr.git
    branch = v3.5-branch
```

* **Переваги:** абсолютна чистота дерева апстриму — модифікувати сторонній код випадково неможливо; гарантована фіксація версії (криптографічний SHA-1 коміту гарантує стабільність збірки).
* **Недоліки:** незручність для розробників (`git submodule update --init --recursive` після кожного перемикання гілок); складність тимчасового тестування локальних латок у ядрі.

## 3. Git Subtree (Фізичне вшивання коду зі збереженням історії)

Команда `git subtree` імпортує зовнішній репозиторій безпосередньо в підкаталог поточного проєкту як єдиний плоский стан, але зберігає внутрішню можливість витягувати нові зміни (`git subtree pull`) та відправляти локальні коміти назад (`git subtree push`).

```bash
# Додавання апстриму в підкаталог через subtree
git subtree add --prefix=external/freertos \
    https://github.com/FreeRTOS/FreeRTOS-Kernel.git V10.5.1 --squash

# Оновлення на нову версію
git subtree pull --prefix=external/freertos \
    https://github.com/FreeRTOS/FreeRTOS-Kernel.git V10.6.0 --squash
```

* **Переваги:** відсутність проблем із синхронізацією субмодулів — будь-який розробник просто робить `git clone` і одразу отримує повністю працездатне дерево; вся збірка повністю самодостатня.
* **Недоліки:** роздування розміру основного репозиторію; заплутана історія комітів; надзвичайно висока складність зворотного виокремлення латок для передачі в апстрим.

## 4. Декларативний робочий простір Zephyr West (Multi-Repo Manifest)

Сучасні екосистеми вбудованого програмного забезпечення (зокрема RTOS Zephyr) відмовилися від субмодулів Git на користь виділеного інструменту оркестрації репозиторіїв — `west`. Користувацький репозиторій містить маніфест `west.yml`, який описує дерево залежностей, репозиторії HAL від виробників мікроконтролерів (NXP, ST, Nordic) та зовнішні бібліотеки (mbedTLS, LittleFS).

```yaml
# Приклад маніфесту west.yml у корені власного репозиторію
manifest:
  remotes:
    - name: zephyrproject
      url-base: https://github.com/zephyrproject-rtos
    - name: mycompany
      url-base: git@gitlab.internal.company.com:embedded

  projects:
    - name: zephyr
      remote: zephyrproject
      revision: v3.5.0
      import: true

    - name: custom-telemetry-driver
      remote: mycompany
      revision: main
      path: modules/drivers/telemetry

  self:
    path: application
```

```text
my-workspace/
├── .west/                 <- Керуючі метадані утиліти west
├── application/           <- Основний репозиторій продукту (містить west.yml)
│   ├── src/main.c
│   ├── boards/
│   └── prj.conf
├── zephyr/                <- Незмінний апстрим Zephyr RTOS
└── modules/
    ├── hal/stm32/         <- Апстрим HAL вендора мікроконтролера
    └── drivers/telemetry/ <- Приватний модуль компанії
```

* **Переваги:** ідеальна ізоляція компонентів; кожна бібліотека живе у власному незалежному репозиторії; модулі реєструються в системі збирання CMake автоматично через дескриптор `zephyr/module.yml`; оновлення апстриму зводиться до зміни одного рядка `revision: v3.6.0` у файлі `west.yml`.
* **Недоліки:** прив'язка до інструментарію Zephyr; вимагає навчання команди роботі з утилітою `west`.

## 5. Композиція шарів Yocto / OpenEmbedded (BSP Meta-Layers)

Вбудовані системи на базі Embedded Linux використовують підхід декларативного нашарування (англ. *layering*). Базова система OpenEmbedded та мета-шари вендорів кристалів (наприклад, `meta-freescale` чи `meta-raspberrypi`) залишаються повністю недоторканими. Розробник створює власний шар `meta-custom-product`.

```text
yocto-workspace/
├── sources/
│   ├── poky/                  <- Базова система Yocto (чистий апстрим)
│   ├── meta-openembedded/     <- Спільнотні рецепти (чистий апстрим)
│   ├── meta-ti/               <- BSP-шар виробника чипа (Texas Instruments)
│   └── meta-myproduct/        <- ВЛАСНИЙ ШАР ПРОДУКТУ
│       ├── conf/layer.conf
│       ├── recipes-kernel/
│       │   └── linux/
│       │       ├── linux-ti-staging_%.bbappend <- Модифікація рецепта ядра
│       │       └── files/
│       │           ├── defconfig
│       │           └── custom-pinmux.dts
│       └── recipes-apps/
│           └── myapp/myapp_1.0.bb
└── build/
    └── conf/bblayers.conf     <- Декларативне підключення шарів
```

Усі доопрацювання ядра здійснюються без внесення змін у вихідний код — за допомогою файлів розширення `.bbappend`, які накладають латки, додають файли накладок Device Tree (`.dts/.dtso`) або перевизначають конфігурацію `defconfig` під час збирання.

* **Переваги:** неперевершена архітектурна гнучкість; повне розділення відповідальності між постачальником ОС, виробником заліза та розробником кінцевого продукту; відтворюваність збірок на рівні окремих бітів (англ. *bit-for-bit reproducibility*).
* **Недоліки:** екстремально високий поріг входження в інструментарій Yocto/BitBake; тривалий час первинної компіляції.

## Порівняльна матриця та критерії вибору

| Критерій оцінки | Монолітний форк | Git Submodules | Git Subtree | Zephyr West | Yocto Meta-Layers |
|---|---|---|---|---|---|
| **Ізоляція приватного коду** | 🔴 Критично низька | 🟡 Середня | 🔴 Низька | 🟢 Ідеальна | 🟢 Ідеальна |
| **Складність оновлення ядра** | 🔴 3–8 тижнів | 🟡 2–5 днів | 🔴 1–3 тижні | 🟢 1–2 години | 🟢 Кілька годин |
| **Зручність Upstream First** | 🔴 Незручно | 🟢 Зручно | 🔴 Вкрай важко | 🟢 Природно | 🟢 Природно |
| **Швидкість старту команди** | 🟢 Миттєво | 🟡 Потрібен інструктаж | 🟢 Швидко | 🟡 Потрібен `west` | 🔴 2–4 тижні навчання |
| **Цільове призначення** | Короткочасні прототипи | Загальні C/C++ бібліотеки | Прості залежності | Сучасні RTOS (MCU) | Embedded Linux (SoC) |

### Практичне правило вибору
* Для проєктів на мікроконтролерах із Zephyr RTOS безальтернативним вибором є **West Workspace** з винесенням драйверів у позадеревні модулі.
* Для повноцінних пристроїв на базі Linux єдиним стійким стандартом є **Yocto Meta-Layers** з накладанням змін через `.bbappend`.
* Для прикладних бібліотек загального призначення найкраще підходять **Git Submodules**.
* Використання прямого монолітного форку виправдане виключно для одноразових дослідницьких прототипів (Proof of Concept, PoC) з терміном життя до двох місяців.
