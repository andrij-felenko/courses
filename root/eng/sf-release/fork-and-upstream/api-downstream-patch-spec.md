# 📋 Специфікація метаданих локальних латок та маніфесту синхронізації з апстримом

Для забезпечення надійного та автоматизованого супроводу похідного репозиторію кожен файл латки (`.patch`), що зберігається в локальній черзі змін, а також конфігураційний маніфест синхронізації повинні відповідати суворим формальним специфікаціям метаданих. Без єдиного стандарту опису походження змін інженерні команди швидко втрачають розуміння того, які патчі є тимчасовими виправленнями дефектів, які вже відправлені на перевірку до відкритої спільноти, а які становлять закриту апаратну специфіку продукту.

Формалізація метаданих дозволяє автоматизованим конвеєрам безперервної інтеграції (CI) самостійно аналізувати чергу локальних латок, перевіряти статус їхнього прийняття в апстримі за криптографічними хешами комітів, виконувати автоматичне списання застарілих виправлень та блокувати небезпечні злиття за наявності нерозв'язаних конфліктів.

## 1. Специфікація заголовків латки (Downstream Patch Header Spec)

Кожен файл латки, що генерується утилітою `git format-patch` або керується системою ведення черг `quilt`, повинен містити структурований блок метаданих у форматі поштових заголовків RFC 822 перед тілом диференціала. Заголовки розташовуються безпосередньо після опису мети зміни (Subject та Commit Message) і відділяються від коду потрійним дефісом (`---`).

```text
СИНТАКСИЧНА СТРУКТУРА ФАЙЛУ ЛАТКИ З МЕТАДАНИМИ
┌─────────────────────────────────────────────────────────────┐
│ From <hash> Mon Sep 17 00:00:00 2001                        │
│ From: Автор <author@company.ua>                             │
│ Date: Fri, 15 Mar 2026 14:22:10 +0200                       │
│ Subject: [PATCH] підсистема: стислий опис проблеми          │
├─────────────────────────────────────────────────────────────┤
│ Розширений технічний опис інженерного контексту:            │
│ чому дефект виникає, які умови його відтворюють,            │
│ як саме зміна відновлює очікуваний інваріант.               │
├─────────────────────────────────────────────────────────────┤
│ Upstream-Status: <Статус>                                   │
│ Upstream-Commit: <40-hex-SHA>                               │
│ Upstream-PR: <URL>                                          │
│ CVE: <Ідентифікатор>                                        │
│ Issue: <Внутрішній квиток>                                  │
│ Signed-off-by: Інженер <author@company.ua>                  │
├─────────────────────────────────────────────────────────────┤
│ ---                                                         │
│  drivers/spi/spi_ll.c | 8 ++++++++                          │
│  1 file changed, 8 insertions(+)                            │
│ diff --git a/drivers/spi/spi_ll.c b/drivers/spi/spi_ll.c     │
└─────────────────────────────────────────────────────────────┘
```

### Формальні визначення полів метаданих

Парсер автоматизації зчитує файл зверху вниз до першого роздільника `---`. Усі рядки, що починаються з відомих ключів, аналізуються як пари «ключ-значення».

* `Upstream-Status` (Обов'язкове поле): визначає поточну фазу життєвого циклу латки відносно основного репозиторію відкритого проєкту. Використовується ботом для ухвалення рішення про необхідність тестування, відправки чи видалення патча.
* `Upstream-Commit` (Обов'язкове для статусів `Accepted` та `Backport`): повний 40-символьний шістнадцятковий SHA-1 або 64-символьний SHA-256 хеш коміту в офіційному репозиторії апстриму. Бот виконує команду `git merge-base --is-ancestor <hash> <target_ref>`, щоб переконатися, що коміт дійсно увійшов до цільової гілки оновлення.
* `Upstream-PR` (Обов'язкове для статусу `Submitted`): постійне гіперпосилання на відкритий Pull Request на GitHub/GitLab або на тред у публічному поштовому архіві (Lore/Patchwork). Дозволяє відстежувати хід відкритого код-рев'ю безпосередньо з локального репозиторію.
* `CVE` (Обов'язкове для патчів виправлення вразливостей): стандартизований ідентифікатор загальновідомої вразливості у форматі `CVE-YYYY-NNNN`. Наявність цього поля дозволяє системам аудиту безпеки автоматично формувати SBOM (Software Bill of Materials) для регуляторних органів.
* `Signed-off-by` (Обов'язкове юридичне поле): рядок підтвердження авторства та ліцензійної чистоти за стандартом Developer Certificate of Origin (DCO). Засвідчує, що автор має право передавати цей код під ліцензією апстриму.
* `Issue` (Рекомендоване поле): внутрішній ідентифікатор завдання в системі трекінгу компанії (Jira, Linear, GitHub Issues) для забезпечення двостороннього зв'язку між комерційними вимогами та кодом.
* `Cherry-picked-from` (Обов'язкове для `Backport`): вказує локальний або віддалений хеш, з якого створено бекпорт, якщо він відрізняється від `Upstream-Commit`.

### Модель переходів станів `Upstream-Status`

Статус кожної латки змінюється відповідно до суворої моделі скінченного автомата. Будь-які несанкціоновані переходи блокуються лінтером метаданих на етапі перевірки Pull Request у внутрішньому репозиторії.

```text
                  МАТРИЦЯ СТАНІВ ТА ПЕРЕХОДІВ ЛАТКИ
  ┌──────────────┐      Надіслано в апстрим      ┌───────────────┐
  │   Pending    ├──────────────────────────────►│   Submitted   │
  └──────┬───────┘                               └───────┬───────┘
         │                                               │
         │ Рішення про непублічність                     │ Спільнота апстриму
         ▼                                               ▼ прийняла код
  ┌──────────────┐                               ┌───────────────┐
  │Inappropriate │                               │   Accepted    │
  └──────────────┘                               └───────┬───────┘
         ▲                                               │
         │ Відхилено апстримом                           │ Плановий rebase
         │ (потребує рефакторингу)                       ▼ виявив хеш у ядрі
  ┌──────┴───────┐                               ┌───────────────┐
  │    Denied    │                               │    Retired    │
  └──────────────┘                               └───────────────┘
```

1. **`Pending`:** початковий стан. Зміну створено локально для вирішення виробничої проблеми. Латка проходить внутрішнє тестування на апаратурі. Інженер готує код до публікації (видаляє внутрішні префікси, додає тести).
2. **`Submitted`:** латку надіслано в апстрим. Поле `Upstream-PR` містить активне посилання. Конвеєр CI щоденно перевіряє статус обговорення через API платформи розробки.
3. **`Accepted`:** зміну прийнято мейнтейнерами апстриму і злито в стовбур розробки. Поле `Upstream-Commit` обов'язково оновлюється фіксованим хешем з гілки `main`.
4. **`Retired`:** термінальний стан. Під час чергової синхронізації форку з новим релізом апстриму утиліта синхронізації фіксує наявність `Upstream-Commit` у новій базі та безслідно видаляє файл латки з локального каталогу.
5. **`Backport`:** ізольований статус для стабільних виправлень, перенесених із новіших версій апстриму в поточну релізну гілку продукту.
6. **`Inappropriate`:** статус для тимчасових діагностичних хаків, налагоджувальних виводів у консоль або нестандартних тестів для тестових стендів, які не мають сенсу для зовнішнього світу.
7. **`Denied`:** апстрим остаточно відхилив запропоновану реалізацію через архітектурну несумісність. Обов'язково вимагає перегляду архітектури та перенесення коду в шар адаптації (Shim Layer).

## 2. Специфікація маніфесту синхронізації (`upstream-sync.yaml`)

Для управління процесом періодичного оновлення похідного форку використовується декларативний маніфест `upstream-sync.yaml`. Цей документ визначає джерела даних, правила зіставлення гілок, політики розв'язання типових ситуацій та команди верифікації цілісності збірки.

```yaml
# upstream-sync.yaml — Конфігурація автоматизованого контуру синхронізації
version: "1.0"

upstream:
  name: "zephyr-mainline"
  url: "https://github.com/zephyrproject-rtos/zephyr.git"
  tracking_ref: "tags/v3.5.0"
  target_ref: "tags/v3.6.0"
  fetch_depth: 0

downstream:
  local_branch: "product-v3.5-release"
  target_rebase_branch: "product-v3.6-candidate"
  patch_directory: "patches/kernel"
  quilt_series_file: "patches/kernel/series"

sync_policy:
  strategy: "rebase-linear"           # rebase-linear | merge-recursive
  auto_retire_accepted_patches: true  # Автоматично списувати латки з Upstream-Commit
  stop_on_conflict: true              # Зупиняти виконання для ручного арбітражу
  allow_inappropriate_patches: false # Забороняти продакшен-збірку з Inappropriate латками

validation:
  pre_check_command: "git diff-index --quiet HEAD --"
  build_command: "west build -b industrial_gateway_v2 application -p auto"
  test_command: "twister -T tests/hardware_integration -v --inline-logs"
  bisect_on_failure: true
  bisect_test_script: "scripts/ci/bisect_verify_spi.sh"
```

### Повний опис семантики параметрів маніфесту

* `upstream.url`: повна мережева адреса автентичного віддаленого репозиторію. Підтримуються протоколи `https://` для відкритих проєктів та `ssh://` / `git@` для приватних апстримів.
* `upstream.tracking_ref`: базовий орієнтир (тег або назва гілки), на якому базується поточна стабільна версія продукту.
* `upstream.target_ref`: цільовий тег або коміт нової версії, на яку планується перенести локальну серію змін.
* `downstream.patch_directory`: відносний шлях до каталогу всередині проєкту, де зберігаються індивідуальні файли латок з метаданими.
* `sync_policy.strategy`: алгоритм інтеграції. `rebase-linear` виконує послідовне накладання атомарних змін через `git am -3` поверх цільового тегу, гарантуючи лінійну історію. `merge-recursive` створює триточкове злиття (використовується лише у виняткових випадках).
* `sync_policy.auto_retire_accepted_patches`: прапорець, що дозволяє боту самостійно видаляти рядок латки з файлу `series`, якщо відповідний коміт уже присутній у цільовому релізі апстриму.
* `validation.build_command`: обов'язкова команда збирання бінарного образу прошивки. Виконується в ізольованому контейнері або середовищі віртуалізації після накладання кожного патча.
* `validation.bisect_on_failure`: активує запуск алгоритму двійкового пошуку проблемного комміта в історії апстриму, якщо фінальна збірка успішна, але інтеграційні тести повертають ненульовий код помилки.

## 3. Специфікація дескриптора модуля Zephyr (`zephyr/module.yml`)

Для підключення власних позадеревних драйверів, файлів прив'язки Device Tree та конфігурацій Kconfig без внесення жодного рядка змін у дерево Zephyr RTOS використовується дескриптор `zephyr/module.yml`. Цей файл розміщується у корені власного ізольованого репозиторію драйверів.

```yaml
# zephyr/module.yml — Контракт реєстрації позадеревного модуля розширення
name: enterprise_industrial_bsp
build:
  cmake: zephyr
  kconfig: zephyr/Kconfig
  settings:
    dts_root: .
    board_root: .
    snippet_root: .
```

* `name`: унікальний глобальний ідентифікатор модуля в системі збирання CMake. Використовується для створення змінних вигляду `ZEPHYR_ENTERPRISE_INDUSTRIAL_BSP_MODULE_DIR`.
* `build.cmake`: вказує відносний шлях до файлу `CMakeLists.txt`, який реєструє вихідні файли власних драйверів у системі збирання ядра.
* `build.kconfig`: шлях до файлу конфігурації меню, що додає власні прапорці налагодження та включення драйверів до стандартного інтерфейсу `menuconfig`.
* `build.settings.dts_root`: реєструє кореневий каталог для автоматичного пошуку файлів описів синтаксису вузлів Device Tree (`dts/bindings/`) та файлів накладок (`.overlay`).
* `build.settings.board_root`: оголошує каталог для визначення власних моделей друкованих плат, дозволяючи системі збирання знаходити плату за назвою `industrial_gateway_v2` без її додавання до стандартного каталогу `boards/` апстриму.

## 4. Конфігурація шару Yocto OpenEmbedded (`conf/layer.conf`)

Для вбудованих систем на базі Linux інтеграція приватних патчів та драйверів описується за допомогою декларативного шару Yocto. Файл `conf/layer.conf` визначає пріоритети накладання змін та правила маскування стандартних рецептів.

```bitbake
# conf/layer.conf — Конфігурація власного ізольованого шару BSP
BBPATH .= ":${LAYERDIR}"

BBFILES += "${LAYERDIR}/recipes-*/*/*.bb \
            ${LAYERDIR}/recipes-*/*/*.bbappend"

BBFILE_COLLECTIONS += "meta-custom-bsp"
BBFILE_PATTERN_meta-custom-bsp = "^${LAYERDIR}/"
BBFILE_PRIORITY_meta-custom-bsp = "10"

LAYERDEPENDS_meta-custom-bsp = "core openembedded-layer"
LAYERSERIES_COMPAT_meta-custom-bsp = "scarthgap nanbield"
```

* `BBFILE_PRIORITY`: ціле число, що визначає вагу нашого шару відносно шарів постачальника чипа (BSP Vendor). Значення `10` гарантує, що конфігурації та файли `.bbappend` нашого шару матимуть вищий пріоритет над стандартними правилами вендора.
* `LAYERSERIES_COMPAT`: список кодових імен релізів Yocto (наприклад, Scarthgap, Nanbield), з якими гарантовано сумісний наш шар. Запобігає випадковому запуску збирання на несумісній мажорній версії базового дистрибутива.

## 5. Довідник кодів помилок та регламент відновлення конвеєра

У разі порушення цілісності метаданих або виникнення технічних збоїв під час синхронізації автоматизований конвеєр повертає стандартизовані коди помилок.

```text
СХЕМА ОБРОБКИ ІНЦИДЕНТІВ КОНВЕЄРА СИНХРОНІЗАЦІЇ
 ┌──────────────────────────┐
 │ Запуск чергового rebase  │
 └────────────┬─────────────┘
              │
              ▼
   [ Чи валідні метадані? ] ────(НІ)───► ERR_PATCH_MISSING_HEADER (Блок CI)
              │ (ТАК)
              ▼
   [ Чи є нові коміти? ]    ────(НІ)───► Завершення: змін немає
              │ (ТАК)
              ▼
   [ Списання Accepted ]    ────(Хеш відсутній)──► ERR_ACCEPTED_WITHOUT_HASH
              │ (Успіх)
              ▼
   [ Тестове накладання ]   ────(Конфлікт)───────► ERR_REBASE_CONFLICT (Арбітраж)
              │ (Успіх)
              ▼
   [ Інтеграційні тести ]   ────(Збій)───────────► ERR_BISECT_FOUND_REGRESSION
              │ (Успіх)
              ▼
 ┌──────────────────────────┐
 │ Промоція нової версії    │
 └──────────────────────────┘
```

| Код помилки | Категорія збою | Опис ситуації та механізм діагностики | Регламентні дії інженера |
|---|---|---|---|
| `ERR_PATCH_MISSING_HEADER` | Метадані | У файлі латки відсутній один із обов'язкових заголовків (`Upstream-Status` або `Signed-off-by`). | Відкрити файл латки у текстовому редакторі, заповнити обов'язковий блок метаданих та повторити запуск перевірки. |
| `ERR_ACCEPTED_WITHOUT_HASH` | Валідація | Латка позначена як `Accepted`, проте поле `Upstream-Commit` порожнє або містить недійсний хеш. | Знайти комміт в офіційному репозиторії апстриму, скопіювати його повний 40-символьний хеш та вставити у відповідне поле. |
| `ERR_SUBMITTED_WITHOUT_URL` | Валідація | Вказано статус `Submitted`, але пропущено або вказано недійсний URL у полі `Upstream-PR`. | Додати пряме посилання на відкритий Pull Request або лист у публічному архіві розробників. |
| `ERR_REBASE_CONFLICT` | Злиття | Автоматичне накладання латки через `git am -3` завершилося структурним конфліктом вихідного коду. | Створити ізольовану робочу гілку, виконати ручний триточковий rebase, оновити файл латки та перезапустити конвеєр. |
| `ERR_BISECT_FOUND_REGRESSION`| Регресія | Латки накладено чисто, проте тестовий набір зафіксував падіння тестів апаратної сумісності. | Переглянути звіт `git bisect`, створити дефект у баг-трекері апстриму з посиланням на виявлений коміт і тимчасово адаптувати шар Shim. |
