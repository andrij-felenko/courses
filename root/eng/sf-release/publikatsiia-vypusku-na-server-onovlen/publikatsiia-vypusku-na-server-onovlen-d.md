Парк із 60 000 телематичних шлюзів керує критичними вузлами розподільчої електромережі. Інженерна команда виправляє вразливість нульового дня у мережевому драйвері, успішно збирає новий образ операційної системи Linux на сервері безперервної інтеграції та завантажує двійковий файл прошивки на загальнодоступний файловий сервер. Оскільки процес публікації зведено до простого копіювання файлу без автоматизованої перевірки апаратної сумісності, образ, скомпільований для нової ревізії апаратної плати (Rev B з 16 ГБ eMMC та контролером живлення I2C), негайно призначається всьому парку пристроїв.

Перші 12 000 шлюзів старішої ревізії (Rev A з 8 ГБ Flash-пам'яті та відмінною картою регістрів SPI) завантажують бінарний файл через стільникову мережу. Під час запису образ виходить за фізичні межі системного розділу і перезаписує таблицю первинного завантажувача U-Boot. Одночасно несумісне дерево пристроїв (Device Tree Blob, DTB) переводить контролери керування живленням у некерований стан. За сорок секунд 12 000 підстанцій повністю втрачають зв'язок із диспетчерським центром; пристрої перетворюються на непрацездатний текстоліт, а відновлення вимагає фізичного виїзду бригад із програматорами та оцінюється у сотні тисяч доларів.

Ця аварія розкриває фундаментальну природу оновлення віддалених систем: публікація релізу не може бути пасивним збереженням бінарних файлів на файловий сервер. Доставка програмного забезпечення у фізичний світ вимагає наявності суворої керуючої площини (OTA Control Plane), яка бере на себе криптографічне зв'язування компонентів у релізний маніфест, багатофакторну перевірку сумісності з апаратним інвентарем, автоматизований аудит цілісності артефактів перед відкриттям доступу пристроям та фіксацію абсолютної незмінності опублікованого коду.

## Сутність механізму: розділення площини керування та площини даних

У надійній архітектурі доставки оновлень процес публікації випуску базується на строгому розподілі двох незалежних контурів: **керуючої площини (Control Plane)** та **площини даних (Data Plane)**.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    РОЗДІЛЕННЯ ПЛОЩИН OTA-АРХІТЕКТУРИ                        │
│                                                                             │
│ [ CI/CD Конвеєр ] ──> (1) Завантаження двійкових файлів ──> [ S3 / CDN ]   │
│         │                                                        │         │
│         │ (2) Метадані + Підпис Ed25519                          │         │
│         ▼                                                        │         │
│ [ OTA Control Plane ] ──> (3) Pre-flight аудит ──> [ Реєстр ]    │ (5) Data│
│         │                                                        │   Stream│
│         │ (4) Підписаний маніфест + Presigned URLs               │         │
│         ▼                                                        ▼         │
│ [ Парк пристроїв ] <─────────────────────────────────────────────┘         │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Площина даних (Data Plane / Storage):** Представлена розподіленими об'єктними сховищами (Amazon S3, MinIO, Google Cloud Storage) та глобальними мережами доставки контенту (CDN). Вона відповідає виключно за збереження великих двійкових блоків (образів кореневих файлових систем `rootfs`, контейнерних шарів, мікрокоду копроцесорів) та їхнє високошвидкісне паралельне завантаження клієнтами через протокол HTTPS.
2. **Керуюча площина (Control Plane / OTA Management Server):** Це інтелектуальне серце системи (реалізоване на базі таких систем, як Eclipse hawkBit, Mender Server або AWS IoT OTA). Сервер оновлень не займається роздачею багатогігабайтних файлів через власний веб-сервер. Його завдання — зберігати базу знань про пристрої (Device Registry), керувати станами життєвого циклу релізів, формувати криптографічні маніфести сумісності та оркеструвати кампанії розгортання.

![Топологія системи публікації випуску на сервер оновлень](/root/eng/sf-release/publikatsiia-vypusku-na-server-onovlen/img/ota-publication-architecture.svg)
*Архітектурна топологія публікації випуску: взаємодія конвеєра CI/CD, модуля підпису HSM, сервера керування оновленнями, сховища артефактів та парку пристроїв.*

[Історію еволюції серверів оновлень від сирих FTP-скриптів до сучасних стандартів TUF, Mender та hawkBit](root:sf-release/publikatsiia-vypusku-na-server-onovlen/hist-ota-evolution.md) варто розглянути окремо — вона демонструє, як подолання масових аварій сформувало сучасні криптографічні стандарти надійності.

Коли інженерна команда або конвеєр CI/CD готує новий випуск, двійковий образ спочатку завантажується в ізольований контур об'єктного сховища. Сервер оновлень реєструє чернетку випуску, вимагає накладання асиметричного цифрового підпису, проводить незалежне передрелізне зондування і лише після успішної валідації відкриває випуск для цільових груп обладнання.

[Архітектурне порівняння провідних серверів оновлень Eclipse hawkBit, Mender Server, AWS IoT OTA та RAUC/SWUpdate](root:sf-release/publikatsiia-vypusku-na-server-onovlen/comp-ota-platforms.md) наведено в окремому матеріалі — воно допомагає обрати оптимальну платформу залежно від специфіки пристроїв та вимог до автономності інфраструктури.

## Фаза прийому артефактів: багатопотокове завантаження та адресація за вмістом

Процес публікації розпочинається на етапі безперервної інтеграції (CI/CD), коли складальний раннер завершує бінарну збірку образів операційної системи. Образи сучасних вбудованих систем варіюються від компактних бінарників RTOS розміром кілька сотень кілобайт до повноцінних образів кореневої файлової системи Linux (rootfs) розміром від 500 МБ до 4 ГБ.

Передача таких обсягів даних вимагає застосування протоколу багатопотокового завантаження частинами (Multi-part Chunked Upload). Конвеєр розбиває бінарний артефакт на рівні блоки (зазвичай розміром по 8–16 МБ) і паралельно передає їх у тимчасову буферну зону об'єктного сховища S3.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 КОНВЕЄР БАГАТОПОТОКОВОГО ЗАВАНТАЖЕННЯ                       │
│                                                                             │
│ [ Бінарний образ 2 ГБ ] ──> [ Розбиття на блоки по 16 МБ ]                  │
│                                    │                                        │
│          ┌─────────────────────────┼─────────────────────────┐              │
│          ▼                         ▼                         ▼              │
│ [ Блок 1 (16 МБ) ]       [ Блок 2 (16 МБ) ]       [ Блок N (16 МБ) ]        │
│   └── SHA-256_1            └── SHA-256_2            └── SHA-256_N          │
│          │                         │                         │              │
│          └─────────────────────────┼─────────────────────────┘              │
│                                    ▼                                        │
│         [ S3 Staging Bucket: Атомарна збірка + Повний SHA-256 ]             │
└─────────────────────────────────────────────────────────────────────────────┘
```

Під час завантаження виникає важлива технічна відмінність між внутрішнім хешем S3 (ETag) та криптографічним хешем файлу. За замовчуванням Amazon S3 обчислює ETag багаточастинного завантаження як склеєний конкатенацією MD5-хеш окремих блоків з додаванням кількості частин (наприклад, `d41d8cd98f00b204e9800998ecf8427e-128`). Цей рядок не є криптографічним хешем самого двійкового файлу і не може використовуватися клієнтами для перевірки цілісності.

Тому конвеєр збірки зобов'язаний самостійно, паралельно з передачею блоків, обчислювати монолітний криптографічний дайджест SHA-256 та BLAKE3 над усім нестисненим і стисненим тілом файлу. Після завершення завантаження всіх частин конвеєр передає ці контрольні суми керуючій площині сервера оновлень для включення у проект маніфесту.

Файли зберігаються за принципом адресації за вмістом (Content-Addressable Storage, CAS), де шляхом до файлу в сховищі є значення його SHA-256 хешу:
`s3://ota-artifacts-prod/cas/sha256/e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`

Така структура гарантує абсолютну дедуплікацію: якщо різні версії випусків містять ідентичні системні компоненти або модулі мікроконтролерів, вони зберігаються в єдиному екземплярі, заощаджуючи ресурси сховища та спрощуючи кешування на проміжних проксі-серверах.

## Анатомія релізного маніфесту: криптографічний контракт істини

Центральним артефактом процесу публікації є **релізний маніфест** (англ. *Release Manifest*). Це структурований документ у форматі JSON або Protocol Buffers, який виконує роль юридично обов'язкового контракту між сервером оновлень та агентом на пристрої.

Маніфест усуває будь-яку неоднозначність щодо того, які саме файли мають бути записані, у які фізичні слоти пам'яті, за яких апаратних умов та як перевірити їхню автентичність.

![Анатомія та криптографічні шари релізного маніфесту](/root/eng/sf-release/publikatsiia-vypusku-na-server-onovlen/img/release-manifest-structure.svg)
*Криптографічна структура релізного маніфесту: зв'язування метаданих, матриці апаратної сумісності, хешів артефактів та цифрового підпису Ed25519.*

Маніфест складається з чотирьох строго обов'язкових секцій:

### 1. Метадані випуску (Release Metadata)
Містять загальні атрибути ідентифікації:
- `release_id` — глобально унікальний ідентифікатор випуску (UUIDv4).
- `name` та `version` — назва програмного продукту та номер версії відповідно до семантичного версіонування (наприклад, `3.4.0`).
- `security_epoch` — монотонно зростаюче ціле число (Anti-Rollback Counter). Цей лічильник унеможливлює атаки зі зниженням версії: якщо пристрій перейшов на епоху `4`, він відхилить будь-який старіший реліз з епохою `3`, навіть якщо той підписаний легітимним ключем.
- `created_at` та `expires_at` — часові мітки створення та завершення терміну дії маніфесту (захист від атак заморожуванням у стилі TUF).

### 2. Матриця апаратної сумісності (Hardware Compatibility Matrix)
Описує строгі межі фізичного застосування випуску:
- `device_type` — символьний ідентифікатор типу пристрою (наприклад, `edge-gateway-imx8mp`).
- `hw_revisions` — масив підтримуваних апаратних ревізій плати (наприклад, `["2.0", "2.1", "2.2"]`).
- `min_bootloader_version` — мінімально допустима версія первинного завантажувача U-Boot або UEFI, здатна коректно передати керування новому ядру Linux.
- `min_storage_bytes` та `min_ram_bytes` — фізичні вимоги до розміру флеш-накопичувача eMMC та оперативної пам'яті.

### 3. Реєстр компонентів та артефактів (Artifacts Registry)
Перелічує конкретні файли та образи, що входять до складу випуску:
- `name` та `type` — назва файлу та тип компонента (`system-image`, `mcu-firmware`, `fpga-bitstream`, `app-container`).
- `target_slot` — цільовий розділ або інтерфейс програмування на пристрої (`rootfs.B`, `boot.B`, `/dev/spidev0.0`).
- `install_order` — черговість встановлення (наприклад, оновлення мікроконтролера керування живленням перед оновленням основного образу ОС).
- `checksums` — криптографічні хеші файлу (`sha256`, `blake3`), обчислені над нестисненим та стисненим двійковим тілом.
- `size_bytes` — точний розмір файлу в байтах.
- `download_url` — підписане тимчасове посилання для завантаження через CDN.

### 4. Криптографічний підпис (Cryptographic Signature Envelope)
Забезпечує захист маніфесту від підробки та модифікації. Секція містить:
- `key_id` — ідентифікатор відкритого ключа у сховищі довіри пристрою.
- `algorithm` — назву алгоритму асиметричного підпису (`Ed25519`, `RSA-PSS-4096`, `ECDSA-P256`).
- `signature` — бінарне значення підпису в кодуванні Base64, накладене на байтовий потік канонізованого JSON (RFC 8785).

[Детальну специфікацію API та схему релізного маніфесту](root:sf-release/publikatsiia-vypusku-na-server-onovlen/api-release-manifest-spec.md) наведено в окремому довіднику — вона містить повні схеми запитів, JSON Schema та таблицю кодів діагностичних помилок.

## Апаратне шлюзування та валідація конфігурацій заліза

Найбільш підступні аварії при оновленні парку пристроїв виникають через непомітні апаратні відмінності між ревізіями друкованих плат. Під час масового виробництва схемотехніки часто змінюють постачальників другорядних мікросхем (наприклад, перехід на інший чіп оперативної пам'яті LPDDR4, заміна контролера Ethernet PHY або зміна напруги живлення шини введення-виведення з 3.3 В на 1.8 В).

Такі зміни фіксуються зміною ревізії плати (наприклад, з Rev 2.1 на Rev 2.2) і вимагають іншого файлу конфігурації дерева пристроїв (Device Tree Blob, DTB). Якщо скомпільоване ядро Linux завантажується з деревом пристроїв від старої ревізії, виникає електричний або логічний конфлікт: лінії GPIO можуть опинитися у стані короткого замикання, напруга на лініях зв'язку вийде за допустимі межі, або драйвер контролера живлення вимкне стабілізатори ядра.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 МАТРИЦЯ АПАРАТНОЇ СУМІСНОСТІ РЕЛІЗУ                         │
│                                                                             │
│ Маніфест v3.4.0:                                                            │
│   • Board Family: gateway-imx8mp                                            │
│   • Supported Revs: [ 2.1, 2.2 ]                                            │
│   • Bootloader Min: 2024.04-r1                                              │
│                                                                             │
│ Звірка з інвентарем парку:                                                  │
│   ┌──────────────────────────────┬──────────────────────────────────────┐   │
│   │ Когорта пристроїв            │ Статус сумісності                    │   │
│   ├──────────────────────────────┼──────────────────────────────────────┤   │
│   │ 42 000 плат (Rev 2.1, 2.2)   │ ПІДТВЕРДЖЕНО (Цільова аудиторія)     │   │
│   │ 15 000 плат (Rev 1.9, 2.0)   │ БЛОКОВАНО (Несумісний DTB / Живлення)│   │
│   │  3 000 плат (Старий U-Boot)  │ ПОПЕРЕДЖЕННЯ (Потрібен bootloader-up)│   │
│   └──────────────────────────────┴──────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

Тому процес публікації релізу включає обов'язковий етап **апаратного шлюзування (Hardware Gating)**. Сервер оновлень виконує аналітичний запит до бази даних парку, перевіряючи:
1. Чи є серед зареєстрованих пристроїв плати з ревізіями, для яких призначено цей реліз.
2. Чи не містить цільова група пристроїв із застарілим мікрокодом вторинних контролерів (наприклад, чіпів безпеки Secure Element або копроцесорів STM32), несумісних із новим протоколом зв'язку по шині I2C/SPI.
3. Чи достатньо вільного обсягу накопичувача в пасивному слоті eMMC для розпакування образу з урахуванням вирівнювання блоків файлової системи (зазвичай 4 КБ або 64 КБ).

Якщо виявляється, що випуск заблокує оновлення для значної частини парку, керуюча площина не дозволяє пряму публікацію і змушує інженерів сформувати поетапний план міграції.

## Криптографічний ланцюг довіри: асиметричний підпис та захист ключів

Чому для публікації випусків неприпустимо використовувати симетричні ключі (HMAC або AES-GCM)?

Якщо автентичність образу перевіряється симетричним спільним ключем, цей ключ повинен бути записаний у постійну пам'ять кожного з десятків тисяч пристроїв у полі. Зловмиснику достатньо фізично захопити один польовий пристрій, зчитати ключ із незахищеної Flash-пам'яті за допомогою логічного аналізатора і отримати можливість самостійно підписувати довільні шкідливі оновлення для всього глобального парку.

Тому стандарт промислової безпеки вимагає використання **асиметричної криптографії з відкритим ключем (Public Key Cryptography)**.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    АСИМЕТРИЧНИЙ ЛАНЦЮГ ДОВІРИ OTA                           │
│                                                                             │
│ [ Ізольований HSM / KMS ]                                                   │
│   └── Приватний ключ Ed25519 (Private Key) ──> Підпис маніфесту             │
│                                                       │                     │
│                                                       ▼                     │
│ [ Захищена пам'ять пристрою (OTP / eFuse / TrustZone) ]                    │
│   └── Відкритий ключ (Public Key)          ──> Верифікація маніфесту        │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Закритий ключ (Private Key):** Зберігається виключно в ізольованому апаратному модулі безпеки (Hardware Security Module, HSM) або хмарному сховищі ключів (AWS KMS / Cloud HSM) з багатофакторним контролем доступу (M-of-N Quorum). Приватний ключ ніколи не потрапляє на сервери збірки чи сервер оновлень у відкритому вигляді. Сервер формує нормалізований дайджест маніфесту і звертається до HSM для накладання підпису.
2. **Відкритий ключ (Public Key):** Прошивається на етапі фабричного виробництва пристрою в одноразово програмовану захищену пам'ять (One-Time Programmable eFuses, TrustZone Secure Storage або апаратний крипточип типу ATECC608A). Навіть повний фізичний реверс-інжиніринг пристрою дає зловмиснику лише публічний ключ, за допомогою якого неможливо сфальсифікувати підпис.

### Ротація ключів та перехідні випуски (Key Migration)

Криптографічні ключі мають обмежений життєвий цикл (зазвичай від 1 до 3 років) через вимоги стандартів безпеки або необхідність заміни у разі планової ротації. Для безперервного оновлення парку пристроїв застосовують протокол **перехідного подвійного підпису (Dual-Signing Transition Release)**:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                      СХЕМА РОТАЦІЇ КЛЮЧІВ РЕЛІЗУ                            │
│                                                                             │
│ Реліз переходу (v3.9.0-transition):                                         │
│   ├── Підпис 1: СТАРИЙ КЛЮЧ (Key-2025) ──> Дозволяє старим пристроям прийняти│
│   ├── Підпис 2: НОВИЙ КЛЮЧ (Key-2026) ──> Підтверджує легітимність ротації │
│   └── Корисне навантаження: Оновлення кореневого сертифіката в eFuse/Keystore│
│                                                                             │
│ Наступний реліз (v4.0.0):                                                   │
│   └── Підпис: ТІЛЬКИ НОВИЙ КЛЮЧ (Key-2026)                                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

Пристрій, що працює на старій версії, верифікує перехідний маніфест за допомогою свого старого відкритого ключа `Key-2025`. У процесі встановлення оновлення система записує новий відкритий ключ `Key-2026` у захищене сховище довіри. Усі наступні випуски підписуються виключно новим ключем `Key-2026`.

## Скінченний автомат станів життєвого циклу публікації

Реліз на сервері оновлень не з'являється миттєво як готовий до завантаження. Він проходить строгу послідовність станів скінченного автомата (State Machine), що унеможливлює публікацію недописаних або пошкоджених файлів.

![Скінченний автомат життєвого циклу публікації релізу](/root/eng/sf-release/publikatsiia-vypusku-na-server-onovlen/img/publication-state-machine.svg)
*Скінченний автомат станів життєвого циклу релізу на сервері оновлень від чернетки до бойової публікації та фіксації незмінності.*

### Фази життєвого циклу релізу:

1. **`Draft` (Чернетка):** Конвеєр CI/CD створює запис про випуск, резервує ідентифікатор `release_id` та отримує тимчасові посилання для завантаження файлів. На цьому етапі випуск є повністю невидимим для парку пристроїв.
2. **`Validating` (Передрелізна перевірка):** Після завершення завантаження всіх бінарних компонентів сервер ініціює конвеєр автоматизованого аудиту (Pre-flight Validation Pipeline). Обчислюються контрольні суми файлів, перевіряється цифровий підпис та валідується схема маніфесту. Якщо хоча б один байт не сходиться, реліз переходить у термінальний стан `Rejected` (Карантин) із генерацією сповіщення інженерам.
3. **`Staged` (Внутрішнє тестування / Канарка):** Усі криптографічні та апаратні перевірки завершено успішно. Реліз стає доступним виключно для внутрішніх апаратних стендів (Hardware-in-the-Loop, HIL) та виділеної когорти канаркових пристроїв команди QA.
4. **`Published` (Опубліковано / Бойовий):** Відповідальний інженер з релізів або автоматизований гейт підтверджує стабільність релізу на канарках. Сервер встановлює прапорець незмінності (`immutable = true`) і передає випуск планувальнику масових кампаній оновлення.
5. **`Deprecated` / `Revoked` (Застарілий або Відкликаний):** Випуск заміщується новішою версією або терміново блокується в разі виявлення критичної вразливості нульового дня, запобігаючи його встановленню новими пристроями.

### Інваріант незмінності (Immutability Invariant)

Головне правило безпеки керуючої площини: **опублікований випуск (`Published`) категорично заборонено редагувати, доповнювати або перезаписувати**.

Якщо після публікації версії `3.4.0` виявляється помилка в скрипті ініціалізації чи конфігураційному файлі, заборонено підміняти файл у сховищі під тим самим номером версії. Зміна коду вимагає випуску нової версії з підвищенням патч-номера SemVer (наприклад, `3.4.1`) та проходженням повного циклу верифікації з новим цифровим підписом.

Незмінність гарантує, що стан пристрою в полі є абсолютно детермінованим і відтворюваним у лабораторних умовах.

## Конвеєр автоматизованої передрелізної верифікації (Pre-flight Validation)

Перед тим як перевести реліз зі стану `Draft` у `Staged`, керуюча площина запускає багатоетапний конвеєр перевірок, який діє як безкомпромісний фільтр якості.

![Конвеєр автоматизованої передрелізної верифікації](/root/eng/sf-release/publikatsiia-vypusku-na-server-onovlen/img/pre-flight-verification-pipeline.svg)
*Послідовність етапів конвеєра передрелізної перевірки артефактів: перевірка схеми, цифрового підпису, хешів та сумісності з інвентарем парку.*

### Етап 1: Валідація схеми та синтаксису (Schema Conformance)
Маніфест перевіряється проти еталонної JSON Schema або структури Protobuf:
- валідність формату семантичної версії (відповідність SemVer 2.0.0);
- коректність ідентифікаторів UUID;
- наявність усіх обов'язкових полів для кожного оголошеного артефакту;
- валідність значень епохи безпеки (`security_epoch >= 1`).

### Етап 2: Верифікація криптографічного підпису (Signature Verification)
Сервер нормалізує маніфест за правилами Canonical JSON (RFC 8785), витягує відкритий ключ довіреного ланцюга відповідно до поля `key_id` і здійснює математичну перевірку підпису Ed25519 або RSA-PSS. Також перевіряється, чи не закінчився термін дії сертифіката підпису (`expires_at`) і чи не внесено ключ до списку відкликаних (CRL).

### Етап 3: Потокова звірка хешів та розмірів артефактів (Digest & Size Audit)
Сервер виконує контрольне потокове зчитування збережених в об'єктному сховищі файлів блоками по 64 КБ:
- обчислює підсумковий хеш SHA-256 та порівнює його з оголошеним у маніфесті;
- перевіряє точний розмір у байтах;
- якщо файл стиснено алгоритмом Zstandard (`.zst`) або XZ (`.xz`), сервер перевіряє валідність заголовка архіву та звіряє очікуваний розмір розпакованого образу (`uncompressed_size_bytes`).

### Етап 4: Аудит сумісності з парком пристроїв (Fleet Inventory Gating)
Сервер виконує перехресний запит до реляційної бази даних інвентарю пристроїв:
- перевіряє, скільки активних пристроїв у системі відповідають заявленому типу `device_type` та ревізіям `hw_revisions`;
- виявляє пристрої з застарілими версіями завантажувача U-Boot, які не зможуть запустити новий реліз;
- якщо виявляється, що випуск заблокує оновлення для критичної частки парку, система генерує попередження та вимагає створення ланцюжка проміжних оновлень (Transition Releases).

### Етап 5: Перевірка реплікації та прогрів CDN (CDN Warmup Verification)
Сервер генерує тестові запити з підписаними посиланнями (Presigned URLs) до регіональних вузлів мережі доставки контенту (CDN edge locations), переконуючись, що артефакти доступні для паралельного завантаження з високою пропускною здатністю.

[Практичну реалізацію автономного валідатора та рушія публікації релізів мовами C та C++](root:sf-release/publikatsiia-vypusku-na-server-onovlen/proj-release-publisher.md) наведено в окремому проекті — він містить алгоритми потокового розрахунку хешів, константно-часову перевірку підписів Ed25519 та код автомата станів публікації.

## Роздача артефактів: підписані посилання та ефективне кешування

Коли пристрій звертається до сервера оновлень і отримує підтвердження наявності релізу, сервер не транслює гігабайти двійкових даних через власний інтерфейс. Передача файлів делегується глобальній мережі CDN та об'єктному сховищу S3 за допомогою механізму **підписаних посилань (Presigned URLs)**.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    СХЕМА РОЗДАЧІ АРТЕФАКТІВ ЧЕРЕЗ CDN                       │
│                                                                             │
│ 1. GET /api/v1/devices/{id}/manifest                                        │
│    Пристрій ───────────────────────────> OTA Server (Control Plane)         │
│                                                │                            │
│ 2. Маніфест + Presigned CDN URLs               │                            │
│    Пристрій <─────────────────────────── OTA Server                         │
│                                                                             │
│ 3. GET /artifacts/rootfs.ext4.zst?token=... (Range: bytes=0-10485759)      │
│    Пристрій ───────────────────────────> CDN Edge Server (Data Plane)       │
│                                                │                            │
│ 4. 206 Partial Content (Потік блоків)          │ (Кеш S3)                   │
│    Пристрій <─────────────────────────── CDN Edge Server                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Принципи безпечної та масштабованої роздачі:
1. **Короткий термін дії токенів:** URL для завантаження генерується з обмеженим часом життя (наприклад, 2 години). Якщо зловмисник перехопить посилання, воно швидко стане недійсним.
2. **Підтримка докачування (HTTP Range Requests):** Пристрої, що працюють через нестабільний стільниковий зв'язок 2G/3G/LTE, завантажують файли блоками по 4–10 МБ за допомогою заголовка `Range: bytes=X-Y`. У разі обриву з'єднання клієнт поновлює завантаження з останнього підтвердженого байта, не витрачаючи дорогий трафік на повторне скачування всього файлу.
3. **Кешування на рівні CDN та усунення скидання кешів:** Завдяки адресації за криптографічним хешем артефакти маркуються заголовком `Cache-Control: public, max-age=31536000, immutable`. Це дозволяє крайовим серверам CDN кешувати образ один раз і роздавати його тисячам пристроїв у регіоні на максимальній швидкості локального каналу зв'язку. Оскільки реліз є незмінним, інженерній команді ніколи не потрібно виконувати дорогу операцію інвалідації (purge) кешу CDN — нова версія завжди з'являється за новою унікальною криптографічною адресою.

## Дельта-випуски: оптимізація трафіку для обмежених каналів

Для польових пристроїв, підключених через супутниковий зв'язок (Iridium, Inmarsat) або енергоощадні стільникові протоколи (NB-IoT, LTE-M), передача повного монолітного образу rootfs розміром 500 МБ є економічно неприпустимою або фізично неможливою через обмеження батареї.

У таких сценаріях сервер публікації підтримує генерацію та поширення **дельта-оновлень (бінарних різниць)**.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 МАТРИЦЯ ГЕНЕРАЦІЇ ДЕЛЬТА-ОНОВЛЕНЬ                           │
│                                                                             │
│ Попередній образ (v3.3.0) ──┐                                               │
│                             ├──> [ Генератор bsdiff / courgette ]           │
│ Новий образ        (v3.4.0) ──┘                  │                          │
│                                                  ▼                          │
│                                    Дельта-патч (Delta Patch: 18 МБ)         │
│                                                  │                          │
│ Маніфест пов'язує:                               │                          │
│   • source_sha256 (Хеш образу v3.3.0)            │                          │
│   • target_sha256 (Хеш цільового v3.4.0)         │                          │
│   • patch_sha256  (Хеш самого дельта-файлу) <────┘                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Вимоги до публікації дельта-релізів:
1. **Явна прив'язка до базової версії:** Дельта-маніфест зобов'язаний містити точний хеш `source_sha256`. Клієнтський агент на пристрої перед застосуванням патча обчислює хеш активного розділу пам'яті. Якщо хоча б один блок відрізняється (наприклад, через ручну модифікацію конфігурації в полі), дельта-патч не застосовується, і клієнт запитує у сервера повний монолітний образ.
2. **Граф дельта-переходів (Delta Graph):** Сервер оновлень підтримує спрямований ациклічний граф (DAG) доступних бінарних різниць. Це дозволяє пристрою, який пропустив два релізи (наприклад, знаходиться на версії `3.1.0`), отримати або прямий кумулятивний дельта-патч `3.1.0 → 3.4.0`, або послідовний ланцюжок дрібних різниць.

## Клієнтський протокол виконання оновлення: від маніфесту до A/B слота

Отримавши валідний маніфест від керуючої площини, клієнтський агент (RAUC або Mender) виконує детермінований алгоритм розгортання:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 КЛІЄНТСЬКИЙ ЦИКЛ РОЗГОРТАННЯ A/B СЛОТІВ                     │
│                                                                             │
│ 1. Верифікація підпису Ed25519 маніфесту за допомогою відкритого ключа eFuse│
│ 2. Звірка security_epoch з апаратним лічильником платформи                  │
│ 3. Визначення неактивного слота (якщо активний Слот A ──> пишемо в Слот B)  │
│ 4. Потоковий запис образу через HTTPS Presigned URL з перевіркою SHA-256    │
│ 5. fsync() накопичувача + встановлення прапорця U-Boot: boot_trial=1        │
│ 6. Перезавантаження (Reboot)                                                │
│ 7. Виконання Health Check зондів у новому контурі                           │
│ 8. Якщо OK ──> boot_confirmed=1; Якщо CRASH ──> Watchdog повертає Слот A    │
└─────────────────────────────────────────────────────────────────────────────┘
```

Цей клієнтський цикл гарантує повну атомарність: пристрій або успішно переходить на нову версію, або залишається на старій гарантовано робочій системі без втрати керування.

## Телеметрія кампанії та автоматичне аварійне припинення

Керуюча площина не просто роздає маніфести, а безперервно збирає телеметричні звіти про статус кожного вузла під час кампанії:
- `downloading` — артефакт транслюється через CDN;
- `verifying` — клієнт перевіряє хеші блоків та підпис Ed25519;
- `installing` — запис у неактивний слот пам'яті eMMC;
- `rebooting` — пристрій перезавантажується у пробному режимі;
- `success` — нова система підтвердила працездатність та скинула таймер сторожового пса (Watchdog);
- `failure` / `rollback` — система зазнала збою та повернулася до попереднього слота.

Якщо частота помилок (Error Rate) на першій хвилі канаркових пристроїв (наприклад, 1% парку) перевищує встановлений поріг безпеки (наприклад, 0.5%), сервер оновлень автоматично ставить кампанію на аварійну паузу (Circuit Breaker). Це запобігає розповсюдженню прихованого дефекту на решту 99% пристроїв.

## Інженерні пастки, крайові випадки та регламенти відмови

Практична експлуатація систем публікації оновлень пов'язана з низкою неочевидних архітектурних ризиків:

### 1. Несумісність дерева пристроїв (Device Tree Blob mismatch)
Найбільш поширена причина виходу з ладу вбудованих плат при оновленні ядра Linux — зміна розпіновки або драйверів у файлі `.dtb`. Якщо ядро версії `v2` завантажується зі старим деревом пристроїв `v1`, система зависає на етапі ініціалізації контролера пам'яті. **Правило:** Ядро Linux, модулі та DTB зобов'язані публікуватися як неподільний єдиний артефакт (комбінований FIT-образ ядра або монолітний образ `rootfs`).

### 2. Розсинхронізація системного часу (Clock Drift & TLS failure)
Якщо пристрій тривалий час перебував на складі без живлення, його апаратний годинник реального часу (RTC) скидається до базової дати (наприклад, 1 січня 1970 року). Під час першого підключення пристрій не зможе встановити TLS-з'єднання з сервером через помилку `Certificate not yet valid`, а також відхилить валідний маніфест оновлення через невідповідність часових міток `created_at`. **Рішення:** Керуюча площина повинна підтримувати протокол синхронізації часу (NTP або захищений Roughtime) на окремому незахищеному від часових помилок порту до початку процедури верифікації релізу.

### 3. Обрив мережі під час багатопотокового завантаження артефактів
Якщо конвеєр CI/CD завантажує реліз із п'яти модулів і на четвертому модулі стається обрив з'єднання з об'єктним сховищем S3, виникає небезпека «зависання» частково опублікованого релізу. **Рішення:** Операція публікації реалізується за принципом двофазної фіксації (Two-Phase Commit): файли спочатку потрапляють у тимчасову буферну теку, і лише після підтвердження отримання всіх 100% артефактів та їхніх хешів сервер атомарно генерує фінальний маніфест і переводить статус у `Staged`.

## Підсумковий синтез архітектурних інваріантів

Публікація випуску на сервер оновлень — це комплексний інженерний протокол, що гарантує надійність функціонування всього парку пристроїв на основі п'яти непорушних принципів:

1. **Розділення обов'язків:** Керуюча площина (OTA Control Plane) керує маніфестами, сумісністю та станами, а площина даних (Storage / CDN) забезпечує високонадійну паралельну роздачу бінарних блоків.
2. **Криптографічний ланцюг довіри:** Автентичність та цілісність випуску гарантуються асиметричними цифровими підписами Ed25519, накладеними в апаратних модулях безпеки (HSM) та верифікованими захищеними відкритими ключами заліза.
3. **Автоматизоване передрелізне зондування:** Жоден бінарний файл не стає доступним пристроям без автоматичного проходження всіх стадій перевірки хешів, цифрових підписів та аудиту матриці апаратної сумісності з активним інвентарем.
4. **Абсолютна незмінність (Immutability):** Опублікований випуск заблокований від будь-яких подальших модифікацій; будь-яке виправлення вимагає створення нового релізу з інкрементом SemVer.
5. **Захист від атак відкату:** Механізм монотонно зростаючих епох безпеки (`security_epoch`) гарантує, що парк пристроїв не може бути примусово повернутий зловмисником до застарілих версій із відомими вразливостями.
