# 📋 Специфікація API та схема релізного маніфесту для сервера оновлень

Ця специфікація визначає формальний контракт REST API керуючої площини (OTA Control Plane) для створення, завантаження, криптографічного підпису, автоматизованої верифікації та публікації випусків вбудованого програмного забезпечення. Документ також регламентує структуру релізного маніфесту, вимоги до канонічної серіалізації даних та клієнтський протокол виявлення оновлень пристроями парку.

Усі точки входу API використовують протокол HTTPS з обов'язковим шифруванням TLS версії 1.3. Аутентифікація конвеєрів збірки (CI/CD) та інженерних сервісів здійснюється через криптографічні Bearer-токени стандарту OAuth 2.0 / JWT з обмеженим радіусом доступу (scopes: `releases:write`, `artifacts:upload`, `releases:publish`). Взаємодія з клієнтськими пристроями захищається взаємною автентифікацією сертифікатів (mTLS), де відкритий ключ кожного пристрою жорстко прив'язаний до його апаратного ідентифікатора в базі даних інвентарю.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 МАРШРУТИ REST API КЕРУВАННЯ ВИПУСКАМИ                       │
│                                                                             │
│ POST /api/v1/releases                     ──> Створення чернетки випуску    │
│ PUT  /api/v1/releases/{id}/artifacts/{art}──> Завантаження бінарного файлу  │
│ POST /api/v1/releases/{id}/signatures     ──> Накладання цифрового підпису  │
│ POST /api/v1/releases/{id}/preflight      ──> Автоматизована верифікація    │
│ POST /api/v1/releases/{id}/publish        ──> Атомарна бойова публікація   │
│                                                                             │
│ GET  /api/v1/devices/{dev_id}/manifest    ──> Отримання маніфесту клієнтом  │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 1. Схема та правила серіалізації релізного маніфесту

Релізний маніфест — це центральний документ випуску, який пов'язує воєдино версію програмного забезпечення, обмеження апаратної сумісності, криптографічні хеші бінарних файлів та електронні підписи розробників. Маніфест передається з MIME-типом `application/vnd.ota.manifest+json;version=1.0`.

Для забезпечення математичної незмінності підпису маніфест підлягає обов'язковій нормалізації за стандартом **Canonical JSON (RFC 8785)**:
- усі ключі об'єктів сортуються в лексикографічному порядку за кодовими точками Unicode;
- видаляються всі зайві пробільні символи, переноси рядків та табуляції поза рядковими літералами;
- числа серіалізуються без експоненційної форми, якщо це не вимагається точністю;
- рядки кодуються виключно в UTF-8 без BOM.

Будь-який підпис накладається виключно на байтовий потік, отриманий після канонічної серіалізації тіла маніфесту (без самого поля `signatures`). Якщо сервер або клієнт серіалізує JSON із відмінним порядком ключів, обчислений дайджест не збіжиться, що призведе до миттєвого відхилення оновлення.

### Семантика ключових полів:
- `release.security_epoch` — монотонно зростаючий лічильник безпеки для захисту від атак відкату (Anti-Rollback Protection). Якщо пристрій уже працює на епосі 4, він категорично відхилить будь-який маніфест із меншим значенням, навіть якщо той має валідний підпис.
- `compatibility.hw_revisions` — масив допустимих апаратних ревізій друкованої плати. Запобігає застосуванню прошивки до несумісних ревізій із відмінним деревом пристроїв (Device Tree).
- `artifacts[].install_order` — строга послідовність запису та оновлення компонентів. Дозволяє оновити мікрокод допоміжних контролерів перед записом образу основної операційної системи.

## 2. Ендпоінти конвеєра публікації (Producer API)

Керування життєвим циклом випуску на стороні CI/CD розгортається через послідовні транзакційні виклики.

### 2.1. Створення чернетки випуску (`POST /api/v1/releases`)
Ініціалізує сутність випуску в базі даних сервера, створює унікальний ідентифікатор `release_id` та переводить статус у `Draft`.

- **Вхідні параметри:** Словник JSON із секціями `release`, `compatibility` та списком очікуваних артефактів `artifacts`.
- **Поведінка сервера:** Сервер перевіряє унікальність пари `(name, version)`, валідує синтаксис SemVer та генерує для кожного артефакту тимчасові підписані URL (S3 Presigned URLs) для прямого завантаження двійкових файлів в об'єктне сховище.
- **Код успіху:** `201 Created` з поверненням структури завантаження.

### 2.2. Завантаження бінарних артефактів (`PUT /api/v1/releases/{release_id}/artifacts/{artifact_id}`)
Використовується, якщо завантаження здійснюється безпосередньо через проксі-шлюз сервера оновлень, або як зворотний виклик (callback) після успішного завантаження файлу в хмарне сховище S3.

- **Вхідні дані:** Потоковий двійковий потік (MIME-тип `application/octet-stream` або `application/x-tar`).
- **Поведінка сервера:** Сервер здійснює потокове обчислення контрольних сум SHA-256 та BLAKE3 на льоту, зберігає файл на диск або в сховище та звіряє підсумковий розмір у байтах із попередньо задекларованим значенням.
- **Код успіху:** `200 OK` (артефакт зафіксовано в сховищі).

### 2.3. Реєстрація цифрового підпису (`POST /api/v1/releases/{release_id}/signatures`)
Передає асиметричний цифровий підпис маніфесту, згенерований апаратним модулем безпеки (HSM) або сервісом керування ключами (KMS).

- **Вхідні дані:** JSON-об'єкт із полями `key_id`, `algorithm` (`Ed25519`, `RSA-PSS-4096`, `ECDSA-P256`) та значенням підпису в кодуванні Base64.
- **Поведінка сервера:** Сервер знаходить відкритий ключ із зазначеним `key_id` у локальному сховищі довіри (Trust Store), канонізує поточний стан маніфесту і перевіряє математичну валідність підпису. Якщо підпис не сходиться хоча б на один біт, виклик відхиляється.
- **Код успіху:** `200 OK`.

### 2.4. Запуск передрелізної верифікації (`POST /api/v1/releases/{release_id}/preflight-check`)
Ініціює автоматизований комплексний аудит релізу перед відкриттям доступу пристроям.

- **Поведінка сервера:** Виконуються чотири обов'язкові перевірки:
  1. *Цілісність файлів:* повне зчитування байтів артефактів зі сховища та звірка хешів.
  2. *Криптографічний ланцюг:* перевірка терміну дії ключів та списків відкликання (CRL).
  3. *Аудит сумісності парку:* виконання SQL-запиту до бази інвентарю для перевірки, чи існують у системі пристрої з цільовою ревізією заліза та чи немає ізольованих апаратних конфігурацій, які будуть зламані цим релізом.
  4. *Прогрів CDN:* перевірка реплікації артефактів на регіональні вузли видачі контенту.
- **Код успіху:** `200 OK` із детальним діагностичним звітом та переведенням релізу в статус `Staged`.

### 2.5. Фіксація та бойова публікація (`POST /api/v1/releases/{release_id}/publish`)
Атомарна фіксація релізу. Переводить статус у `Published` та встановлює прапорець `immutable = true`.

- **Поведінка сервера:** Після успішного виконання цього методу база даних блокує будь-які подальші операції редагування, перезапису або видалення метаданих чи бінарників випуску. Реліз стає доступним для планувальника кампаній та автоматичних хвиль доставки.
- **Код успіху:** `200 OK`.

## 3. Клієнтський інтерфейс опитування та доставки (Consumer API)

Клієнтський демон (наприклад, RAUC або Mender-client) взаємодіє з сервером через періодичне опитування (polling) або реактивно за сигналом з брокера MQTT/WebSockets.

### Запит перевірки оновлення (`GET /api/v1/devices/{device_id}/manifest`)

Пристрій передає свій поточний апаратний та програмний контекст у заголовках HTTP-запиту:

```http
GET /api/v1/devices/dev-gw-991204/manifest HTTP/1.1
Host: api.updates.example.com
Authorization: Bearer <DEVICE_SESSION_TOKEN>
X-Device-Type: edge-gw-arm64
X-HW-Revision: 2.1
X-Current-OS-Version: 3.2.1
X-Bootloader-Version: 2024.04-r1
X-Security-Epoch: 3
If-None-Match: "w/e7b92f44-rev1"
```

### Логіка обробки запиту сервером:
1. **Автентифікація та авторизація:** Сервер верифікує клієнтський TLS-сертифікат і токен сесії. Якщо пристрій позначений у реєстрі як відкликаний або викрадений, повертається `403 Forbidden`.
2. **Зіставлення матриці сумісності:** Сервер знаходить активні кампанії, призначені для когорти цього пристрою. Якщо версія завантажувача або ревізія плати клієнта не відповідає вимогам маніфесту, сервер повертає `412 Precondition Failed` або підбирає проміжний реліз оновлення.
3. **Генерація Presigned URLs:** Сервер генерує короткоживучі підписані посилання на завантаження артефактів із CDN (термін дії посилань зазвичай становить від 30 хвилин до 4 годин).
4. **Кешування та трафік:** Якщо пристрій передав заголовок `If-None-Match`, що збігається з хешем поточного актуального релізу, сервер повертає статус `304 Not Modified` без тіла відповіді, заощаджуючи стільниковий трафік клієнта.

## 4. Довідник кодів помилок

| Код помилки | HTTP статус | Технічна причина | Дія клієнта або конвеєра |
|---|---|---|---|
| `SCHEMA_VIOLATION` | `400 Bad Request` | Відсутні обов'язкові поля в JSON або передано невалідний формат дати / SemVer. | Виправити структуру маніфесту та повторити запит створення. |
| `INVALID_SIGNATURE` | `422 Unprocessable Entity` | Цифровий підпис не проходить верифікацію відкритим ключем довіреного ланцюга. | Перепідписати маніфест дійсним приватним ключем релізу в HSM. |
| `CHECKSUM_MISMATCH` | `422 Unprocessable Entity` | Хеш фактично збереженого в сховищі файлу відрізняється від оголошеного в маніфесті. | Видалити пошкоджений файл та повторно завантажити бінарний артефакт. |
| `HARDWARE_INCOMPATIBLE`| `409 Conflict` | Матриця сумісності релізу конфліктує з конфігурацією зареєстрованих плат у базі. | Перевірити список підтримуваних ревізій заліза у файлі конфігурації. |
| `DOWNGRADE_FORBIDDEN` | `409 Conflict` | Значення `security_epoch` релізу нижче за лічильник поточної активної версії. | Заборонено політикою безпеки Anti-Rollback; підняти епоху випуску. |
| `IMMUTABILITY_LOCKED` | `423 Locked` | Спроба перезапису, зміни або видалення артефактів релізу у статусі `Published`. | Зміни заборонені; створити новий випуск із підвищенням версії SemVer. |
| `STORAGE_UNAVAILABLE` | `503 Service Unavailable` | Об'єктне сховище S3 або сервіс підпису тимчасово недоступні через тайм-аут мережі. | Застосувати експоненційну затримку (exponential backoff) з випадковим джитером (jitter). |
