# 🔌 Матриця адресації нотаток випуску за ролями

Коли програмно-апаратний комплекс, вбудована система чи розподілений сервіс отримує чергове оновлення, один і той самий пакет супровідної документації потрапляє до рук фахівців із кардинально різними обов'язками, технічним контекстом і рівнем відповідальності. Інформація, життєво необхідна для польового інженера (наприклад, карта розподілу секторів флеш-пам'яті під час перепрошивки чи допустимий діапазон напруги живлення), є зайвим когнітивним шумом для оператора установки або клієнта сервісу. І навпаки: опис змін у призначенні кнопок панелі керування ніяк не допоможе розробнику мережевого шлюзу, чий драйвер раптово перестав розбирати байти телеметрії.

У цій порівняльній матриці зіставлено інформаційні потреби, критичні ризики умовчання, межі корисного змісту та типові антипатерни оформлення нотаток випуску для чотирьох ключових експлуатаційних ролей.

## Порівняльна матриця вимог до змісту

| Критерій оцінки | 1. Кінцевий користувач / Власник приладу | 2. Сервісний інженер / Оператор парку | 3. Інтегратор API / SDK розробник | 4. Офіцер безпеки / Аудитор (SecOps) |
|---|---|---|---|---|
| **Головне питання** | «Що змінилося в моїй роботі й що я повинен зробити?» | «Як розгорнути це без аварії та як відкотитися назад?» | «Де зламається мій код і які сигнатури змінилися?» | «Які вразливості усунуто та який рівень загрози парку?» |
| **Ключові секції нотаток** | • Нові функції (Features)<br>• Зміни поведінки інтерфейсу<br>• Обов'язкові ручні дії (Action Required) | • Сумісність ревізій заліза (PCB)<br>• Вимоги до бутлоадера<br>• Матриця відкату (Rollback safety)<br>• Контрольні суми (SHA-256) | • Ламкі зміни API (Breaking changes)<br>• Застарілі виклики (Deprecations)<br>• Нові бінарні кадри / RPC<br>• Приклади коду міграції | • Ідентифікатори CVE та CWE<br>• Скоринг і вектор CVSS v3.1<br>• Опис зачепленого компонента<br>• Заходи пом'якшення (Mitigation) |
| **Критичний ризик умовчання** | Користувач не знає про зміну логіки кнопки й припускається помилки в експлуатації | Контролер блокується («окрипичується») через несумісний завантажувач чи збій схеми NVM | Клієнтські сервіси та шлюзи падають через неочікувану зміну бінарного протоколу | Критичний патч RCE відкладається на місяці через відсутність оцінки загрози |
| **Шкідлива надмірність** | Технічний дамп регістрів, стек-трейси, внутрішні номери комітів | Маркетингові гасла та абстрактні описи без вказівки номерів ревізій плат | Опис внутрішніх оптимізацій ядра, що не впливають на публічний контракт | Покроковий експлойт (PoC) або шелкод, який зловмисник може застосувати проти парку |
| **Формат подачі** | Простий структурований текст, графічні підказки в UI, короткі інструкції | Машинно-читабельний JSON-маніфест, таблиця сумісності, бінарні геші | Документація API (Swagger, Protobuf), changelog у стилі `Keep a Changelog`, diff | Стандартизований звіт CSAF, JSON для OSV, таблиця CVE з вектором CVSS |

## Аналіз ролей та специфіка сприйняття

### 1. Кінцевий користувач та власник пристрою
Ця роль взаємодіє з системою через графічний або фізичний інтерфейс. Її завдання — вирішувати прикладні завдання бізнесу: вимірювати тиск, перекачувати рідину, відстежувати маршрут або керувати процесом.

Коли користувач бачить у нотатках технічні терміни на кшталт «Оптимізовано стек TCP/IP за допомогою пулу буферів DMA», це викликає відчуття розгубленості та відторгнення. Єдине, що має значення для цієї аудиторії — це прямий вплив на операційну діяльність: чи стала система працювати швидше, які нові можливості з'явилися на екрані, і чи потрібно виконати будь-яку дію власноруч (наприклад: «Після оновлення необхідно зайти в меню налаштувань та виконати калібрування нульової точки датчика»).

### 2. Сервісний інженер та оператор парку
Польовий інженер або оператор системи масового оновлення відповідає за фізичну працездатність пристроїв у реальному середовищі. Його головний страх — отримати «цеглину» (непрацездатний пристрій із пошкодженим завантажувачем або заблокованою пам'яттю) на віддаленому об'єкті за триста кілометрів від найближчого сервісного центру.

Для цієї ролі критично важливими є апаратні обмеження: сумісність із ревізіями друкованих плат (PCB Revision), версія первинного завантажувача, вимоги до стабільності напруги живлення під час перезапису Flash-пам'яті та **матриця безпеки відкату (Rollback safety)**. Якщо оновлення змінює формат запису калібрувальних коефіцієнтів у енергонезалежній пам'яті (EEPROM/Flash), оператор повинен чітко знати: чи дозволено відкочуватися назад на попередню прошивку в разі збоїв, чи цей крок призведе до повної втрати калібрування.

### 3. Інтегратор зовнішніх API та розробник SDK
Інтегратор створює клієнтське програмне забезпечення, яке взаємодіє з пристроєм через мережеві або польові інтерфейси (CAN, Modbus, UART, gRPC, REST API). Його головна турбота — стабільність публічного контракту ([Interface vs Implementation](root:sf-apps/interface-vs-implementation)).

Будь-яка неоголошена зміна бінарного формату кадру, зміна порядку байтів (Endianness), видалення обов'язкового поля чи зміна діапазону значень перетворюється на нічну аварію клієнтського сервісу. Інтегратору потрібен точний перелік змін у сигнатурах викликів, попередження про застарілі інтерфейси ([Deprecations](root:sf-apps/deprecation-policy)) із графіком їхнього остаточного виведення з експлуатації та готові зразки коду для швидкої адаптації.

### 4. Офіцер безпеки та аналітик вразливостей (SecOps)
Фахівець з інформаційної безпеки розглядає випуск як подію управління ризиками. Його завдання — мінімізувати поверхню атаки ([Attack Surface](root:sf-security/attack-surface)) на парк пристроїв без зупинки виробничих процесів.

Фраза «Виправлено помилки безпеки» позбавляє аудитора можливості виконати оцінку загрози. Офіцеру потрібен міжнародний ідентифікатор вразливості [CVE](root:sf-security/biuleten-bezpeky), числовий бал та векторний рядок [CVSS v3.1](root:sf-security/vulnerability-scoring-cvss), а також інструкція з тимчасового захисту (компенсаційних заходів), якщо негайне оновлення обладнання неможливе з технологічних причин.

## Анатомія поширених антипатернів

### Антипатерн 1: «Універсальний маркетинг»
Спроба замінити технічний зміст загальними оптимістичними формулюваннями («Ми зробили наш продукт ще стабільнішим і швидшим»).
- **Чому це ламає експлуатацію:** Сервісний інженер не знає про зміну вимог до завантажувача; інтегратор не підозрює про зміну бітрейту CAN; безпека не бачить критичного виправлення RCE.
- **Як виправити:** Застосовувати багатошарову структуру бюлетеня, де кожна секція маркується відповідною піктограмою та адресована конкретній ролі.

### Антипатерн 2: «Сирий дамп репозиторію»
Публікація повного журналу `git log` без фільтрації та змістовної категоризації.
- **Чому це ламає експлуатацію:** У суцільному потоці службових записів на кшталт `fix typo`, `merge branch dev`, `bump dependencies` губляться критичні застереження про несумісність.
- **Як виправити:** Використовувати автоматизований конвеєр на основі Conventional Commits, де службові коміти (`chore`, `ci`, `test`) фільтруються автоматично, а ламкі зміни (`BREAKING CHANGE`) виносяться в окремий блок уваги.

### Антипатерн 3: «Прихована незворотність міграції»
Випуск прошивки, яка змінює структуру енергонезалежної пам'яті (Flash/EEPROM), без явного попередження про заборону даунгрейду.
- **Чому це ламає експлуатацію:** При виникненні непередбачених аномалій оператор намагається прошити попередній стабільний образ. Стара версія не розпізнає нову структуру налаштувань, затирає пам'ять дефолтними значеннями або зациклюється в перезавантаженні.
- **Як виправити:** Розміщувати блок **Матриця безпеки відкату (Rollback safety)** на початку релізного документа, безпосередньо під секцією метаданих.
