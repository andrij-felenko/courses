# 📜 Від GNU ChangeLog до багатошарових бюлетенів: еволюція нотаток випуску

Коли в середині 1980-х років формувалися перші стандарти відкритого програмного забезпечення, питання комунікації змін вирішувалося гранично просто: якщо програміст змінив рядок коду, він мав зафіксувати це в текстовому файлі поруч із вихідними текстами. Річард Столлман у настановах проєкту GNU (*GNU Coding Standards*, 1987) закріпив формат файлу `ChangeLog`. Цей документ був суто хронологічним реєстром правок: дата, ім'я автора, назва зміненого файлу, ім'я функції у круглих дужках та стислий коментар про те, що саме підправлено (наприклад, `* parse.c (yyparse): Fixed buffer overrun on long identifiers`).

Цей підхід ідеально відповідав епосі, коли користувачами, збирачами та розробниками програми були ті самі люди. Щоб запустити нову версію компілятора GCC або текстового редактора Emacs, користувач мав завантажити архів із вихідними текстами, запустити компіляцію на своїй Unix-робочій станції та за потреби самостійно усунути локальні помилки несумісності. Читання пофайлового `ChangeLog` давало системному програмісту вичерпну картину того, які функції зазнали правок.

## Розкол інтересів: народження файлу NEWS

Зі зростанням складності систем та розширенням кола користувачів у 1990-х роках виявилася фундаментальна проблема: пофайловий журнал коду нічого не повідомляв людині, яка просто користується програмою. Двісті записів про рефакторинг внутрішніх вказівників у бібліотеці `glibc` маскували той факт, що в новій версії змінився синтаксис файлу конфігурації або додано підтримку нового мережевого протоколу.

Проєкти GNU відповіли на це розділенням документації на два окремі потоки:
1. `ChangeLog` — залишався технічним журналом для розробників, що описував зміни на рівні вихідного коду;
2. `NEWS` — став високорівневим бюлетенем, де кожен випуск групував лише помітні користувачеві нововведення (*User-Visible Changes*), зміни в синтаксисі команд та попередження про застарілі можливості.

Файл `NEWS` став прямим предком сучасних нотаток випуску (англ. *release notes*). Він уперше зафіксував принцип фільтрації: внутрішній інженерний шум компіляції та тестів відсікається, а на перший план виносяться наслідки оновлення для зовнішнього середовища.

## Епоха вебу, пакунків та ініціатива Keep a Changelog

На початку 2010-х років розповсюдження мобільних додатків, хмарних сервісів та автоматизованих менеджерів пакунків (npm, RubyGems, PyPI, Cargo) спричинило кризу комунікації. Сотні тисяч бібліотек випускали оновлення щотижня. Розробники масово впадали в крайнощі: одні вставляли у випуски незрозумілий сирий дамп заголовків git-комітів (`git log --oneline`), де переважали записи на кшталт `wip`, `fix typo` та `merged branch feat`, інші — обмежувалися маркетинговою відпискою «Bug fixes and performance improvements».

У відповідь на цей хаос у 2014 році Олів'є Лакан (Olivier Lacan) опублікував маніфест і стандарт `Keep a Changelog`. Головна ідея маніфесту полягала в тому, що журнал змін пишеться для людей, а не для роботів чи компіляторів. Стандарт запропонував жорстку рубрикацію для кожної версії:
- `Added` — для нових функцій;
- `Changed` — для змін у наявній функціональності;
- `Deprecated` — для функцій, які невдовзі будуть видалені;
- `Removed` — для видалених можливостей;
- `Fixed` — для виправлених дефектів;
- `Security` — для оновлень, що усувають вразливості.

Поєднання рубрикації `Keep a Changelog` із семантичним версіонуванням ([SemVer](root:sf-release/semantic-versioning)) створило зрозумілу систему координат для розробників прикладного програмного забезпечення: номер версії сигналізував про рівень ризику, а рубрики журналу розкривали деталі переходу.

## Автоматизація та Conventional Commits

Невдовзі виявилася наступна слабка ланка: ручне ведення `CHANGELOG.md` постійно відставало від коду. Розробники забували оновлювати документ перед релізом, або записи виходили неповними.

У середині 2010-х років спільнота Angular запропонувала стандартизувати повідомлення самих комітів у системі контролю версій. Ця ініціатива оформилася в загальноприйняту специфікацію `Conventional Commits`. Завдяки жорсткому формату `type(scope): message` інструменти конвеєра ([CI/CD](root:sf-release/ci-cd)) — такі як `semantic-release` та `standard-version` — отримали можливість автоматично аналізувати синтаксичне дерево історії Git, обчислювати наступний номер SemVer і генерувати структуровані нотатки випуску без жодного ручного втручання.

## Складні парки та бюлетені безпеки CSAF і OSV

У 2020-х роках розвиток Інтернету речей (IoT), критичної інфраструктури, робототехніки та вбудованих пристроїв висунув до нотаток випуску принципово нові вимоги. Оновлення прошивки промислового контролера чи авіаційного автопілота — це не просто оновлення бібліотеки в хмарі. Помилка в оцінці сумісності ревізії плати чи залежності від завантажувача здатна вивести з ладу фізичне обладнання на мільйони доларів.

Сучасні нотатки випуску для парку пристроїв еволюціонували у багатошарові технічні бюлетені. Вони поєднують:
- людсько-читабельні документи з матрицями сумісності апаратних ревізій та правилами безпечного відкату;
- машинно-читабельні маніфести (JSON/YAML) для серверів масового оновлення через радіоефір (OTA);
- стандартизовані безпекові бюлетені у форматах CSAF (*Common Security Advisory Framework*) та OSV (*Open Source Vulnerabilities*), які дозволяють автоматизованим сканерам оцінювати ризики вразливостей без ручного перегляду документації.

Таким чином, за чотири десятиліття нотатки випуску подолали шлях від скромного пофайлового коментаря програміста до багаторівневого інженерного контракту, що узгоджує роботу розробників, системних операторів та автоматизованих конвеєрів.
