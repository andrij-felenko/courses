# 📋 Специфікація W3C Trace Context та семантичні конвенції OpenTelemetry

Розподілений трейсинг спирається на суворі міжнародні специфікації форматів передачі даних та узгоджені семантичні угоди іменування атрибутів. Без єдиного стандарту назв полів телеметрія від різних мов програмування, фреймворків та інфраструктурних компонентів перетворюється на неструктурований набір ключів, що унеможливлює автоматичну кореляцію, побудову графів сервісів та роботу аналітичних панелей.

Нижче наведено повний довідковий опис формату заголовків стандарту W3C Trace Context, специфікації W3C Baggage, ресурсних і спан-атрибутів OpenTelemetry Semantic Conventions, еволюції схем та трансляції Schema URL, мови перетворень OTTL, специфікації протоколу OTLP, сумісності з легасі-форматами та архітектури конфігурації OpenTelemetry Collector.

## 1. Специфікація заголовка W3C traceparent

Заголовок `traceparent` описує стан поточного запиту в розподіленому дереві викликів і передається у відкритому вигляді через транспортні протоколи (HTTP/1.1, HTTP/2, HTTP/3, gRPC, WebSockets, AMQP, Kafka).

### Синтаксична граматика ABNF (Augmented Backus-Naur Form)

```abnf
traceparent       = version "-" trace-id "-" parent-id "-" trace-flags
version           = 2HEXDIGLC ; 00..fe, значення ff заборонено
trace-id          = 32HEXDIGLC ; 16 байтів, всі нулі заборонено
parent-id         = 16HEXDIGLC ; 8 байтів, всі нулі заборонено
trace-flags       = 2HEXDIGLC ; 8-бітова маска
HEXDIGLC          = %x30-39 / %x61-66 ; цифри 0-9 та малі літери a-f
```

### Побайтова структура та валідація полів

| Поле | Довжина (символи) | Тип даних | Значення за замовчуванням | Опис і правила валідації |
|---|---|---|---|---|
| **`version`** | 2 hex | `uint8_t` | `00` | Поточна версія специфікації — `00`. Значення `ff` вважається неприпустимим назавжди. Якщо отримано версію вище за `00`, парсер зчитує перші 55 символів за правилами `00`, ігноруючи додаткові байти після 4-го дефіса. |
| **`trace-id`** | 32 hex | 16 байтів | Обов'язкове | Глобально унікальний 128-бітний ідентифікатор усієї транзакції. Формується кореневим сервісом за допомогою криптографічного генератора ентропії. Значення `00000000000000000000000000000000` заборонене. |
| **`parent-id`** | 16 hex | 8 байтів | Обов'язкове | 64-бітний локальний ідентифікатор безпосереднього батьківського спана (виклику або операції). Значення `0000000000000000` заборонене. |
| **`trace-flags`** | 2 hex | 8-бітова маска | `00` | Побайтні прапорці керування поведінкою трейсу. Поточна специфікація визначає біт `0x01` (Recorded). Решта 7 бітів (`0x02`..`0x80`) зарезервовані. |

### Чому обрано шістнадцяткове кодування (Hex) замість Base64
Розробники стандарту W3C свідомо відмовилися від компактнішого кодування Base64 на користь фіксованого шістнадцяткового представлення:
1. **Відсутність заборонених символів:** Base64 містить символи `+`, `/` та `=`, які мають спеціальне значення в URL-шляхах, параметрах запитів та заголовках HTTP, вимагаючи додаткового екранування.
2. **Фіксована побайтова сітка:** кожні два hex-символи строго відповідають одному байту пам'яті. Це спрощує низькорівневий парсинг на рівні ядра ОС (eBPF, XDP) та апаратних мережевих карт (NIC Offloading).
3. **Зручність інженерного аналізу:** ідентифікатори легко читаються людиною в консольних утилітах `tcpdump`, `curl -v` або інтерфейсах Wireshark без необхідності ручного декодування.

### Бітова маска прапорців trace-flags

* **`0x01` (`Recorded`):** якщо біт встановлено в `1`, це сигналізує проміжним сервісам, що цей трейс було відібрано для запису алгоритмом семплювання (Head-based sampling). Сервіси повинні збирати спани, атрибути та логи для цієї транзакції.
* **`0x00` (`Not Recorded`):** трейс не семпльовано на вході. Сервіси продовжують поширювати контекст (`traceparent`) далі за ланцюгом викликів для збереження цілісності графа, але не виділяють важкі структури спанів і не експортують їх у сховище.

## 2. Специфікація заголовка W3C tracestate

Заголовок `tracestate` розширює `traceparent` непрозорими специфічними даними окремих систем моніторингу та вендорів без порушення стандартизованого формату ідентифікаторів.

### Граматика та обмеження формату

```abnf
tracestate = list-member *( OWS "," OWS list-member )
list-member = key "=" value
key = simple-key / tenant-key
simple-key = ( %x61-7a ) *( %x61-7a / %x30-39 / "_" / "-"/ "*" / "/" )
tenant-key = tenant-id "@" system-id
tenant-id = ( %x61-7a / %x30-39 ) *( %x61-7a / %x30-39 / "_" / "-"/ "*" / "/" )
system-id = ( %x61-7a ) *( %x61-7a / %x30-39 / "_" / "-"/ "*" / "/" )
value = *( %x20-2b / %x2d-3c / %x3e-7e ) ; друковані символи ASCII без коми та знака рівності
```

### Правила обробки та мутації tracestate

1. **Ліміт списку:** не більше 32 елементів (пар ключ-значення).
2. **Ліміт довжини рядка:** максимальний сумарний розмір заголовка — 512 символів US-ASCII.
3. **Пріоритет та оновлення позиції:** щоразу, коли проміжний компонент модифікує значення власного ключа або додає новий запис, ця пара ключ-значення **повинна бути переміщена на першу (крайню ліву) позицію списку**.
4. **Витіснення (Eviction policy):** якщо додавання нового ключа перевищує ліміт у 32 елементи або 512 байтів, система зобов'язана видалити найправіший (найстаріший) елемент зі списку.
5. **Мультитенентні ключі:** для ізоляції даних різних клієнтів в одній системі ключ може містити префікс організації: `tenant_id@system_id=opaque_value` (наприклад, `myorg@congo=t61rcWkgMzE`).

## 3. Специфікація заголовка W3C Baggage

Заголовок `baggage` слугує для передачі користувацьких пар ключ-значення бізнес-рівня вздовж усього розподіленого графа виконання.

### Формат синтаксису

```http
baggage: userId=alice,serverNode=df28,isVIP=true;priority=high
```

### Правила валідації та обмеження

* **Синтаксис списку:** пари `key=value`, розділені комами. Кожна пара може мати необов'язкові властивості метаданих, розділені крапкою з комою (`;prop1=val1`).
* **Кодування:** будь-які значення, що містять спеціальні символи (пробіли, коми, крапки з комою, слеші або символи поза діапазоном ASCII `0x21`..`0x7E`), повинні підлягати Percent-encoding (URL-кодуванню за RFC 3986).
* **Рекомендований розмір:** не більше 8192 байтів на весь заголовок, щоб запобігти помилкам проксі-серверів `431 Request Header Fields Too Large`.
* **Фільтрація на периметрі:** публічні API-шлюзи зобов'язані видаляти заголовок `baggage` від неавторизованих зовнішніх клієнтів для запобігання підміні внутрішніх службових параметрів.

## 4. Модель даних спана, статус-коди та зв'язки (Links)

Спан є базовим будівельним блоком розподіленого трейсу. Кожен спан описує неперервний у часі фрагмент роботи.

### Структура спана (Span Data Model)

* **`Name` (рядок):** лаконічна назва операції з низькою кардинальністю (наприклад, `HTTP GET /users/{id}` або `SELECT users`).
* **`SpanContext`:** комбінація `TraceId`, `SpanId`, `TraceFlags` та `TraceState`.
* **`ParentSpanId`:** 64-бітний ідентифікатор батька (порожній для Root Span).
* **`Kind` (тип спана):**
  * `INTERNAL (0)`: внутрішня операція всередині процесу (обчислення, бізнес-логіка);
  * `SERVER (1)`: синхронна обробка вхідного мережевого запиту (HTTP-сервер, gRPC handler);
  * `CLIENT (2)`: синхронний вихідний мережевий виклик (HTTP-клієнт, DB-клієнт);
  * `PRODUCER (3)`: асинхронне створення та відправка повідомлення в брокер (Kafka, RabbitMQ);
  * `CONSUMER (4)`: асинхронне вилучення та обробка повідомлення з черги.
* **`StartTime` / `EndTime`:** часові мітки початку та завершення операції у наносекундах від початку епохи UNIX (UTC).
* **`Attributes`:** масив пар ключ-значення з обмеженою кількістю типів (String, Boolean, Int64, Double, масиви примітивів).
* **`Events`:** структуровані журнальні події всередині спана з точною міткою часу (`timestamp`, `name`, `attributes`).
* **`Links`:** причинно-наслідкові зв'язки між незалежними трейсами (використовуються для операцій пакетної обробки Batching або Fan-in).

### Статуси виконання спана (Span Status)

Специфікація OpenTelemetry визначає три числових коди статусу:

| Статус | Числовий код | Опис та семантика |
|---|---|---|
| **`UNSET`** | `0` | Стан за замовчуванням. Означає, що операція завершилася в штатному режимі без явної фіксації бізнес-успіху або аварії. |
| **`OK`** | `1` | Операція завершилася успішно. Встановлюється розробником явно у випадках, коли попередній збій було виправлено або успіх має бути зафіксовано примусово. |
| **`ERROR`** | `2` | Операція зазнала критичного збою (виняток, HTTP 5xx, помилка бази даних). Повинен супроводжуватися атрибутами винятку або текстовим полем `Description`. |

### Механіка зв'язків між спанами (Span Links)

У класичній деревоподібній моделі спан може мати лише одного безпосереднього батька (`ParentSpanId`). Проте в розподілених системах регулярно виникають патерни взаємодії, де деревоподібна ієрархія порушується:

1. **Пакетна обробка повідомлень (Batch Processing):** фоновий воркер зчитує з топіка Kafka пакет із 50 повідомлень, створених 50 різними користувацькими транзакціями. Створювати 50 батьківських зв'язків неможливо. Воркер створює один єдиний спан обробки пакету і додає до нього 50 об'єктів `SpanLink`, кожен із яких вказує на відповідний вхідний `TraceID`/`SpanID`.
2. **Агрегація результатів (Fan-In):** сервіс збирає відповіді від п'яти паралельних пошукових кластерів.
3. **Асинхронне фонове виконання (Fire-and-Forget):** операція ініціює довготривалий процес (наприклад, щонічний перерахунок аналітичних звітів), який живе незалежно від життєвого циклу HTTP-запиту клієнта.

## 5. Семантичні конвенції OpenTelemetry (Semantic Conventions)

Семантичні конвенції встановлюють суворі стандартні імена та типи атрибутів для різних підсистем.

### 5.1. Ресурсні атрибути (Resource Attributes)

Ресурсні атрибути описують середовище, в якому виконується сервіс (хост, контейнер, хмарний провайдер, версія застосунку), і додаються до кожного експортованого спана автоматично:

| Атрибут | Тип | Приклад значення | Опис |
|---|---|---|---|
| `service.name` | `string` | `"order-service"` | Логічна назва мікросервісу (обов'язкове поле). |
| `service.namespace` | `string` | `"ecommerce.checkout"` | Простір імен сервісу для логічного групування команд. |
| `service.version` | `string` | `"2.4.1"` | Семантична версія кодової бази або хеш Git-коміту. |
| `service.instance.id` | `string` | `"pod-order-6f8b9-x7k2"` | Унікальний ідентифікатор конкретного екземпляра процесу. |
| `host.name` | `string` | `"worker-node-14.k8s.local"` | Мережеве ім'я хоста. |
| `host.arch` | `string` | `"amd64"`, `"arm64"` | Архітектура центрального процесора. |
| `os.type` | `string` | `"linux"`, `"windows"`, `"darwin"` | Тип операційної системи. |
| `container.name` | `string` | `"order-api"` | Назва контейнера в середовищі виконання. |
| `container.id` | `string` | `"a1b2c3d4e5f6"` | Унікальний 64-символьний хеш контейнера Docker/CRI-O. |
| `k8s.cluster.name` | `string` | `"prod-eu-central-1"` | Назва кластера Kubernetes. |
| `k8s.namespace.name` | `string` | `"production"` | Простір імен Kubernetes. |
| `k8s.pod.name` | `string` | `"order-service-78f8695888-9wlzq"` | Назва пода Kubernetes. |
| `k8s.deployment.name` | `string` | `"order-service"` | Назва об'єкта Deployment у Kubernetes. |
| `cloud.provider` | `string` | `"aws"`, `"gcp"`, `"azure"` | Ідентифікатор публічного хмарного провайдера. |
| `cloud.region` | `string` | `"eu-central-1"`, `"us-east-1"` | Географічний регіон датацентру. |
| `cloud.availability_zone` | `string` | `"eu-central-1a"` | Зона доступності всередині хмарного регіону. |

### 5.2. HTTP та мережеві атрибути (HTTP Client & Server)

| Атрибут | Тип | Приклад значення | Опис |
|---|---|---|---|
| `http.request.method` | `string` | `"POST"` | Стандартизований метод HTTP-запиту (у верхньому регістрі). |
| `http.response.status_code` | `int` | `200`, `503` | Числовий статус-код HTTP-відповіді. |
| `url.full` | `string` | `"https://api.shop.ua/v1/orders?id=42"` | Повний URL запиту включно зі схемою, хостом та параметрами запиту. |
| `url.path` | `string` | `"/v1/orders"` | Шлях запиту (URI path). |
| `url.query` | `string` | `"id=42"` | Рядок параметрів запиту без початкового знака `?`. |
| `http.route` | `string` | `"/users/{user_id}"` | Шаблон параметризованого маршруту веб-фреймворку (низька кардинальність). |
| `server.address` | `string` | `"api.shop.ua"`, `"10.0.1.15"` | Доменне ім'я або IP-адреса цільового сервера. |
| `server.port` | `int` | `443`, `8080` | TCP/UDP порт сервера. |
| `client.address` | `string` | `"192.168.1.100"` | IP-адреса вихідного клієнта. |
| `network.protocol.version` | `string` | `"1.1"`, `"2"`, `"3"` | Версія транспортного протоколу HTTP. |

### 5.3. Атрибути баз даних (Database Client)

| Атрибут | Тип | Приклад значення | Опис |
|---|---|---|---|
| `db.system` | `string` | `"postgresql"`, `"redis"`, `"clickhouse"` | Ідентифікатор системи керування базами даних. |
| `db.namespace` | `string` | `"production_db"`, `"shard_02"` | Назва бази даних, схеми або простору ключів. |
| `db.collection.name` | `string` | `"orders"`, `"users"` | Назва таблиці (SQL) або колекції (NoSQL). |
| `db.operation.name` | `string` | `"SELECT"`, `"UPDATE"`, `"HGETALL"` | Тип операції над даними. |
| `db.query.text` | `string` | `"SELECT * FROM orders WHERE id = ?"` | Текст запиту із замаскованими конфіденційними літералами (санітизований). |
| `db.response.status_code` | `string` | `"42P01"` (Undefined table) | Код помилки, повернутий сервером бази даних. |

### 5.4. Атрибути систем обміну повідомленнями (Messaging & Queues)

| Атрибут | Тип | Приклад значення | Опис |
|---|---|---|---|
| `messaging.system` | `string` | `"kafka"`, `"rabbitmq"`, `"aws_sqs"` | Назва брокера повідомлень. |
| `messaging.destination.name` | `string` | `"orders.payment.v1"` | Назва топіка, черги або теми обміну. |
| `messaging.operation` | `string` | `"publish"`, `"receive"`, `"process"` | Тип дії (публікація, отримання, обробка). |
| `messaging.message.id` | `string` | `"msg_9872136"` | Унікальний ідентифікатор повідомлення у брокері. |
| `messaging.batch.message_count` | `int` | `50` | Кількість повідомлень у пакеті під час масової вибірки. |

### 5.5. Атрибути винятків та аварійних подій (Exceptions)

Коли спан перехоплює виняток, формується подія з назвою `exception` та наступними атрибутами:

| Атрибут | Тип | Приклад значення | Опис |
|---|---|---|---|
| `exception.type` | `string` | `"java.net.SocketTimeoutException"` | Повна назва класу або типу винятку. |
| `exception.message` | `string` | `"Connection timed out after 5000ms"` | Текстове повідомлення про помилку. |
| `exception.stacktrace` | `string` | `"at com.shop.Client.connect(Client.java:42)..."` | Повний стек викликів на момент виникнення збою. |
| `exception.escaped` | `boolean` | `true`, `false` | Чи призвів виняток до аварійного переривання обробника (`true`), чи був перехоплений (`false`). |

## 6. Еволюція схем та трансляція через Schema URL

У міру розвитку семантичних конвенцій назви полів можуть уточнюватися або перейменовуватися (наприклад, застарілий атрибут `http.status_code` було замінено на `http.response.status_code`, а `net.peer.name` — на `server.address`).

Для забезпечення зворотної сумісності OpenTelemetry використовує механізм **Schema URL**:
* Кожен пакет телеметрії містить посилання на версію схеми: `schema_url: "https://opentelemetry.io/schemas/1.26.0"`.
* OpenTelemetry Collector має вбудований транслятор схем (Schema Translator), який у рантаймі автоматично приводить застарілі атрибути до актуальної версії або навпаки, транслює нові атрибути у старі формати для збереження працездатності існуючих дашбордів Grafana.

## 7. Сумісність із легасі-форматами заголовків

Під час міграції застарілих корпоративних систем на єдиний стандарт W3C Trace Context виникає необхідність підтримки та взаємного перетворення заголовків попередніх поколінь:

| Формат / Система | Заголовки запиту | Правила трансляції у W3C Trace Context |
|---|---|---|
| **Zipkin B3 (Multi-Header)** | `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-Sampled`, `X-B3-ParentSpanId` | Якщо `X-B3-TraceId` має 64 біти (16 hex), він доповнюється 16 нулями зліва (`0000000000000000...`) до 128 бітів. `X-B3-Sampled: 1` транслюється у прапорець `trace-flags: 01`. |
| **Zipkin B3 (Single Header)** | `b3: {TraceId}-{SpanId}-{SamplingState}-{ParentSpanId}` | Поля розділені дефісом, аналогічно розпаковуються у відповідні змінні W3C. |
| **Jaeger Native** | `uber-trace-id: {trace-id}:{span-id}:{parent-span-id}:{flags}` | Поля розділені двокрапкою. Шістнадцятковий прапорець `1` стає `01` у W3C. |
| **AWS X-Ray** | `X-Amzn-Trace-Id: Root=1-{time_hex}-{unique_id};Parent={span_id};Sampled=1` | Специфічний префікс `1-` відкидається, 32-бітний час епохи та 96-бітний унікальний ID зливаються у 128-бітний W3C Trace ID. |
| **Google Cloud Trace** | `X-Cloud-Trace-Context: {trace_id}/{span_id};o={options}` | Розділювач скісна риска `/`, десятковий `span_id` перетворюється у 16-символьний шістнадцятковий рядок. |

Для забезпечення безшовного переходу використовується комбінований пропагатор OpenTelemetry `CompositePropagator`: на вході він перевіряє наявність заголовків у порядку `W3C -> B3 -> Jaeger -> AWS`, витягує перший валідний контекст, а на виході транслює як сучасний `traceparent`, так і старий легасі-заголовок для сумісності з немодифікованими бекендами.

## 8. Протокол експорту OTLP (OpenTelemetry Protocol)

Протокол OTLP є офіційним двійковим транспортом передачі телеметрії в OpenTelemetry.

### Ієрархія Protobuf-структур
Усі дані серіалізуються за трирівневою схемою групування для мінімізації дублювання метаданих:
1. **`ResourceSpans`:** об'єднує всі спани, що виникли в межах одного фізичного процесу чи контейнера (ресурсні атрибути `service.name`, `k8s.pod.name` кодуються рівно один раз на весь пакет).
2. **`ScopeSpans`:** групує спани за конкретною інструментованою бібліотекою (наприклад, `io.opentelemetry.spring-webmvc` версії `1.32.0`).
3. **`Span`:** безпосередній масив окремих спанів із таймстемпами та локальними атрибутами.

### Порівняння форматів транспортування телеметрії

* **OTLP/gRPC (порт 4317):** використовує HTTP/2 потокове мультиплексування бінарних Protobuf-повідомлень. Забезпечує найнижчі накладні витрати на CPU та мінімальне використання смуги пропускання мережі.
* **OTLP/HTTP (порт 4318):** передає Protobuf або JSON-корисне навантаження через класичні `POST /v1/traces` запити. Ідеально підходить для браузерних застосунків (Frontend Web Tracing), мобільних додатків та мереж із суворими брандмауерами, що блокують gRPC.
* **Стиснення трафіку (Compression):** для великих потоків телеметрії обов'язково застосовується алгоритм `zstd` або `gzip`. Використання `zstd` рівня стиснення 3 зменшує мережевий трафік на 82–88% за навантаження на процесор менше ніж 1.5% одного ядра.

### 8.1. Конфігурація BatchSpanProcessor в SDK застосунків

На рівні клієнтських бібліотек SDK передача спанів контролюється компонентом `BatchSpanProcessor`, який накопичує записи в оперативній пам'яті перед їх експортом у колектор:

* **`max_queue_size` (за замовчуванням 2048):** максимальна кількість спанів у черзі пам'яті. Якщо фоновий експортер не встигає надсилати дані (наприклад, через затримки мережі або перевантаження колектора), нові спани скидаються з фіксацією помилки в лічильнику `telemetry.spans.dropped`.
* **`max_export_batch_size` (за замовчуванням 512):** максимальний розмір одного пакету OTLP, що передається через мережу в одному RPC-виклику.
* **`scheduled_delay_millis` (за замовчуванням 5000 мс):** інтервал між примусовими скиданнями буфера, навіть якщо розмір пакету ще не досяг `max_export_batch_size`.
* **`export_timeout_millis` (за замовчуванням 30000 мс):** максимальний час очікування відповіді від сервера збору телеметрії перед розривом з'єднання та повторною спробою.

**Штатне завершення роботи процесу (Graceful Shutdown):**
Під час зупинки сервісу (сигнали SIGTERM/SIGINT) SDK викликає метод `TracerProvider.Shutdown()`, який блокує створення нових спанів, примусово скидає всі накопичені в черзі спани методом `ForceFlush()` і чекає завершення мережевої передачі перед поверненням керування в ОС, запобігаючи втраті фінальних транзакцій.

## 9. Мова перетворень OTTL та маскування даних

У багатьох організаціях законодавчі вимоги (GDPR, PCI-DSS, HIPAA) забороняють передачу конфіденційної інформації (паролі, номери банківських карток, токени авторизації) у системи зберігання трейсів. Для динамічної модифікації атрибутів без перезапуску застосунків OpenTelemetry Collector надає процесор `transform` на базі декларативної мови OTTL (OpenTelemetry Transformation Language).

### Приклади виразів OTTL для санітизації:
```yaml
processors:
  transform:
    error_mode: ignore
    trace_statements:
      - context: span
        statements:
          # Маскування JWT-токенів у рядку Authorization
          - replace_pattern(attributes["http.request.header.authorization"], "Bearer [A-Za-z0-9-_=]+\\.[A-Za-z0-9-_=]+\\.?[A-Za-z0-9-_.+/=]*", "Bearer ***")
          # Маскування номерів кредитних карток у тілі запиту
          - replace_pattern(attributes["http.request.body"], "\\b(?:\\d[ -]*?){13,16}\\b", "****-****-****-****")
          # Видалення конфіденційних параметрів з URL
          - replace_pattern(attributes["url.full"], "(password|token|secret)=[^&]+", "$$1=REDACTED")
          # Встановлення регіону за IP-адресою
          - set(attributes["geo.datacenter"], "eu-west-1") where attributes["server.address"] == "10.100.4.1"
```

Мова OTTL обробляє правила у нативному компільованому коді на Go, додаючи менше ніж 50 наносекунд на один спан, що дозволяє виконувати фільтрацію та санітизацію терабайтних потоків спанів у реальному часі.

## 10. Конфігурація OpenTelemetry Collector та маршрутизація

OpenTelemetry Collector використовує конфігурацію у форматі YAML для визначення конвеєрів збору, обробки та маршрутизації телеметрії.

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  # 1. Захист колектора від переповнення пам'яті (OOM Killer)
  memory_limiter:
    check_interval: 1s
    limit_percentage: 75
    spike_limit_percentage: 20

  # 2. Фільтрація та tail-based семплювання помилок і «довгих хвостів»
  tail_sampling:
    decision_wait: 10s
    num_traces: 100000
    expected_new_traces_per_sec: 2000
    policies:
      # Завжди зберігати 100% трейсів із помилками
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ ERROR ] }

      # Завжди зберігати трейси із затримкою понад 1.5 секунди
      - name: latency-policy
        type: latency
        latency: { threshold_ms: 1500 }

      # Зберігати лише 1% швидких успішних трейсів
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: { sampling_percentage: 1.0 }

  # 3. Пакетування даних перед відправкою у сховище
  batch:
    send_batch_size: 1024
    timeout: 500ms

exporters:
  # Відправка у сховище ClickHouse через gRPC
  otlp/clickhouse:
    endpoint: clickhouse.internal:4317
    tls:
      insecure: true

  # Відправка в об'єктне сховище Grafana Tempo
  otlp/tempo:
    endpoint: tempo.internal:4317
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [ otlp ]
      processors: [ memory_limiter, tail_sampling, batch ]
      exporters: [ otlp/clickhouse, otlp/tempo ]
```

### Механіка процесорів у конвеєрі:
1. **`memory_limiter`:** обов'язково розміщується першим у списку `processors`. Регулярно перевіряє використання оперативної пам'яті процесом колектора. Якщо споживання наближається до 75% від загального ліміту контейнера, процесор тимчасово відхиляє вхідні дані та надсилає клієнтам сигнал повторити запит пізніше (Backpressure), запобігаючи аварійному завершенню процесу операційною системою через Out-Of-Memory (OOM).
2. **`tail_sampling`:** утримує в оперативній пам'яті буфер завершених спанів для кожного `TraceID` протягом заданого інтервалу очікування (`decision_wait: 10s`). Щойно надходить кореневий спан або минає тайм-аут, рушій перевіряє правила: якщо хоча б один спан містить статус `ERROR` або затримку понад поріг, весь трейс пропускається далі на експорт.
3. **`batch`:** накопичує спани у пачки перед мережевою серіалізацією, зменшуючи кількість операцій введення-виведення та навантаження на мережеві інтерфейси сховища.

### Балансування навантаження за Trace ID (Consistent Hashing)
У кластерних розгортаннях OpenTelemetry Collector, де працює кілька паралельних екземплярів колектора, виникає фундаментальна проблема: якщо мікросервіс А відправить кореневий спан на `Collector-1`, а мікросервіс Б відправить дочірній спан із помилкою на `Collector-2`, жоден із двох колекторів не матиме повного дерева трейсу для прийняття рішення в `tail_sampling`.

Для вирішення цієї проблеми розгортається дволанцюгова топологія:
1. **Перший рівень (Load-Balancing Gateway):** шлюз на базі `loadbalancingexporter` обчислює хеш-функцію від 128-бітного `TraceID` (`hash(TraceID) % N`) і направляє абсолютно всі спани з однаковим ідентифікатором трейсу на один і той самий бекенд-колектор другого рівня.
2. **Другий рівень (Sampling Cluster):** вузол другого рівня накопичує 100% спанів даного трейсу у локальній пам'яті, виконує аналіз правил `tail_sampling` і передає узгоджений результат у постійне сховище.
