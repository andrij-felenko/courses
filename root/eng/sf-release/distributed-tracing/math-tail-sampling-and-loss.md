# 🧮 Математика семплінгу: аналіз втрат рідкісних подій та зміщення перцентилів

У високонавантажених розподілених системах збереження 100% згенерованих спанів є економічно та технічно недоцільним: кластер із 100 000 запитів на секунду за середньої глибини трейсу в 20 спанів генерує 2 000 000 спанів щомиті, що еквівалентно сотням гігабайтів мережевого трафіку та десяткам терабайтів щоденного дискового простору. 

Для оптимізації витрат інженери застосовують статистичну вибірку (семплювання). Проте наївне зменшення частоти збору даних кардинально змінює статистичні властивості вибірки: виникає ризик повної втрати рідкісних критичних збоїв та суттєве зміщення оцінок хвостових перцентилів затримок (`p99`, `p99.9`).

Нижче наведено строгий математичний аналіз імовірностей детекції аномалій під час рівномірного Head-based семплінгу, оцінку дисперсії порядкових статистик затримок, математичне обґрунтування збереження цілісності графа викликів (DAG), динамічне адаптивне семплювання на базі Token Bucket та доведення незміщеності й мінімізації дисперсії відновлення популяційних метрик за допомогою оцінювача Горвіца-Томпсона в Tail-based семплінгу.

## 1. Імовірнісна модель рівномірного Head-based семплінгу

Розглянемо потік вхідних транзакцій як послідовність незалежних випробувань Бернуллі.

Нехай за фіксований проміжок часу система обробляє `N` розподілених запитів. Кожен запит на вхідному шлюзі з імовірністю `s` (`0 < s ≤ 1`) позначається прапорцем `Recorded` (`trace-flags = 01`) і зберігається, а з імовірністю `1 - s` відкидається. Величина `s` називається коефіцієнтом семплювання (англ. *sampling rate*).

Припустимо, що в системі виникає рідкісна аномалія (наприклад, стан гонки, витік пам'яті або відмова репліки бази даних), яка спричиняє збій із фіксованою ймовірністю `p_e` на один запит (`p_e ≪ 1`).

Загальна кількість помилкових запитів `K` у вибірці обсягом `N` є біноміальною випадковою величиною:

```
K ~ Binomial(N, p_e)
E[K] = N · p_e
```

### Імовірність фіксації хоча б одного збою

Якщо за період спостереження виникло рівно `k` збоїв, кожен із них незалежно потрапляє у вибірку з імовірністю `s`. Нехай випадкова величина `X` позначає кількість зафіксованих помилкових трейсів у сховищі. Тоді `X` підпорядковується біноміальному розподілу:

```
X ~ Binomial(k, s)
```

Імовірність того, що система **не зафіксує жодного** з `k` збоїв (повна сліпота моніторингу), дорівнює:

```
P(X = 0 | k) = (1 - s)ᵏ
```

Відповідно, імовірність успішного виявлення **хоча б одного** проблемного трейсу складає:

```
P(X ≥ 1 | k)
= 1 - P(X = 0 | k)      [правило доповнення події]
= 1 - (1 - s)ᵏ          [біноміальна ймовірність нуля успіхів]
```

### Граничний перехід до закону рідкісних подій Пуассона

Коли кількість транзакцій `N` прямує до нескінченності (`N → ∞`), а ймовірність виникнення помилки мала (`p_e → 0`), кількість збоїв `K` апроксимується розподілом Пуассона з параметром інтенсивності `λ = N · p_e`.

Оскільки процес семплювання є проріджуванням пуассонівського процесу (англ. *Poisson thinning*) з імовірністю збереження `s`, кількість збережених помилкових трейсів `X` також є пуассонівською випадковою величиною з параметром `μ = s · λ = s · N · p_e`:

```
P(X = m) = (μᵐ · e⁻ᵐᵘ) / m!
P(X ≥ 1) = 1 - e⁻ˢ·ᴺ·ᵖᵉ
```

### Розрахунок мінімального коефіцієнта семплювання

Інженерна задача полягає у виборі такого коефіцієнта вибірки `s`, який гарантує детекцію аномалії з заданим рівнем статистичної довіри `1 - β` (де `β` — допустима ймовірність пропуску дефекту, наприклад `β = 0.01` для 99% надійності):

```
P(X ≥ 1) ≥ 1 - β
1 - (1 - s)ᵏ ≥ 1 - β
(1 - s)ᵏ ≤ β
k · ln(1 - s) ≤ ln(β)
ln(1 - s) ≤ ln(β) / k
```

Застосовуючи наближення Тейлора першого порядку для малих `s` (`ln(1 - s) ≈ -s`):

```
-s ≤ ln(β) / k
s ≥ -ln(β) / k
s ≥ ln(1 / β) / k
```

**Числовий приклад:** нехай під час релізу виникає новий критичний баг, який проявляється у `k = 10` користувачів. Якщо в системі налаштовано стандартний Head-based семплінг `s = 0.01` (1% трафіку), то ймовірність виявити бодай один трейс становить:

```
P(X ≥ 1 | k = 10)
= 1 - (1 - 0.01)¹⁰     [підстановка k = 10 та s = 0.01]
= 1 - (0.99)¹⁰         [обчислення 1 - 0.01]
= 1 - 0.90438          [піднесення до степеня 10]
= 0.09562              [віднімання ймовірності нуля успіхів, лише 9.56%]
```

У 90.44% випадків інженери взагалі не побачать жодного трейсу з цією помилкою у системі моніторингу. Щоб забезпечити 95% імовірність фіксації (`β = 0.05`), необхідний коефіцієнт семплювання:

```
s ≥ ln(1 / 0.05) / 10  [підстановка рівня помилки β = 0.05 та k = 10]
= ln(20) / 10          [обчислення 1 / 0.05 = 20]
= 2.9957 / 10          [натуральний логарифм 20]
≈ 0.30                 [ділення на 10, вимагає не менше 30% трафіку]
```

Звідси випливає фундаментальне обмеження Head-based семплінгу: **рівномірна вибірка не здатна забезпечити спостережуваність рідкісних подій без пропорційного збільшення витрат на збереження основного обсягу нормального трафіку**.

## 2. Цілісність графа викликів (DAG) та експоненційне згасання

Розглянемо розподілену систему, де виконання транзакції проходить через ланцюг із `H` незалежних послідовних мікросервісів (глибина виклику `H`).

### Чому незалежне локальне семплювання катастрофічне
Якби кожен із `H` мікросервісів приймав рішення про збереження свого спана самостійно та незалежно з імовірністю `s`, імовірність зберегти **повне, нерозірване дерево викликів** дорівнювала б добутку ймовірностей:

```
P(Повний граф) = sᴴ
```

Для ланцюга глибиною `H = 6` мікросервісів за стандартного коефіцієнта семплювання `s = 0.1` (10%):

```
P(Повний граф) = (0.1)⁶ = 0.000001 (один на мільйон!)
```

У 99.9999% випадків інженер отримував би фрагментовані шматки трейсів без початку або без кінця.

### Доведення необхідності узгодженого поширення прапорця Context Propagation
Коли вхідний шлюз приймає рішення про семплювання один раз на вході та записує результат у прапорець `trace-flags` (біт `0x01`), який внутрішньосмугово транслюється всіма наступними вузлами:

```
P(Вузол i зберігає спан | Вузол 1 вибрав семплінг) = 1.0
P(Повний граф) = s · 1.0 · 1.0 · ... · 1.0 = s
```

Імовірність отримати повний граф стає рівною `s` і **не залежить від глибини системи `H`**. Це математично доводить, чому внутрішньосмугова передача прапорця `Recorded` є обов'язковою вимогою стандарту W3C Trace Context.

## 3. Динамічне адаптивне семплювання: алгоритм Token Bucket

Для захисту системи збереження телеметрії від перевантаження під час непередбачуваних сплесків трафіку застосовується адаптивне обмеження швидкості на базі алгоритму «відра токенів» (Token Bucket).

Нехай відро має максимальну місткість `B` токенів і поповнюється з постійною швидкістю `r` токенів на секунду. Кожен новий вхідний трейс для отримання статусу `Recorded` вимагає списання 1 токена.

Якщо поточна інтенсивність вхідного потоку запитів дорівнює `λ` запитів на секунду:

1. **В умовах низького навантаження (`λ ≤ r`):** токенів завжди достатньо. Усі трейси отримують статус `Recorded`. Коефіцієнт семплювання:
   ```
   s(λ) = 1.0
   ```
2. **В умовах пікового сплеску (`λ > r`):** за тривалого перевантаження швидкість генерації записаних трейсів жорстко обмежується швидкістю надходження токенів `r`. Ефективний коефіцієнт семплювання автоматично падає:
   ```
   s(λ) = r / λ
   ```

Математичне сподівання кількості збережених трейсів за одиницю часу:
```
E[Записаних трейсів / сек] = min(λ, r)
```

Це гарантує 100% збереження діагностичних даних під час нічного затишшя та надійний захист бекенду від вичерпання дискового простору під час денних піків.

## 4. Спотворення та дисперсія перцентилів затримок

Оцінка якості функціонування сервісів за угодами SLA/SLO традиційно базується на високих перцентилях часу відгуку: `p95`, `p99` та `p99.9`. Розглянемо, як зменшення обсягу вибірки внаслідок семплювання впливає на точність емпіричних перцентилів.

Нехай час виконання запиту описується неперервною випадковою величиною `T` із функцією розподілу `F(t) = P(T ≤ t)`. Справжній теоретичний перцентиль рівня `q` (`0 < q < 1`) визначається як квантиль:

```
t_q = F⁻¹(q)
```

Якщо із загальної генеральної сукупності `N` запитів випадково відібрано `m = s · N` трейсів, вибірка затримок впорядковується у варіаційний ряд:

```
T₍₁₎ ≤ T₍₂₎ ≤ ... ≤ T₍ₘ₎
```

Емпірична оцінка перцентиля `t̂_q` обчислюється як `k`-та порядкова статистика, де `k = ⌈m · q⌉`:

```
t̂_q = T₍ₖ₎
```

### Асимптотичний розподіл порядкових статистик

Згідно з центральною граничною теоремою для порядкових статистик, за умови гладкості та додатності густини ймовірності `f(t_q) = F'(t_q) > 0`, оцінка `T₍ₖ₎` є асимптотично нормальною випадковою величиною:

```
t̂_q ~ Normal(t_q, σ_q²)
```

Дисперсія вибіркового перцентиля `σ_q²` виражається формулою:

```
σ_q² = (q · (1 - q)) / (m · [f(t_q)]²)
```

Стандартна похибка оцінки перцентиля `SE(t̂_q)` дорівнює:

```
SE(t̂_q) = √[q · (1 - q) / (s · N)] · (1 / f(t_q))
```

### Точні довірчі інтервали для перцентилів через порядкові статистики

Для довільного обсягу вибірки `m` точний непараметричний довірчий інтервал для квантиля `t_q` із рівнем довіри `1 - α` будується між порядковими статистиками `T₍ᵣ₎` та `T₍ₛ₎` (`r < s`).

Імовірність того, що справжній квантиль `t_q` знаходиться між `T₍ᵣ₎` та `T₍ₛ₎`, визначається біноміальною сумою:

```
P(T₍ᵣ₎ ≤ t_q ≤ T₍ₛ₎) = ∑_{j=r}^{s-1} C(m, j) · qʲ · (1 - q)ᵐ⁻ʲ ≥ 1 - α
```

Для вибірки обсягом `m = 500` спроба оцінити перцентиль `p99.9` (`q = 0.999`) виявляється математично неможливою: навіть максимальна порядкова статистика `T₍₅₀₀₎` має ймовірність бути меншою за справжній `p99.9`:

```
P(T₍₅₀₀₎ < t₀.₉₉₉) = (0.999)⁵⁰⁰ ≈ 0.6063 (60.63%)
```

Тобто у 60.6% випадків вся вибірка з 500 трейсів не міститиме жодного значення з хвостової зони `p99.9`, створюючи ілюзію стабільної системи під час реальної деградації.

### Числове порівняння ширини довірчого інтервалу для p99

Розглянемо оцінку перцентиля `p99` (`q = 0.99`) за двох різних розмірів вибірки:
1. **Вибірка після агресивного семплінгу (`m = 1000` трейсів):**
   Використовуючи нормальне наближення, 95% довірчий інтервал для рангу перцентиля становить `m · q ± 1.96 · √(m · q · (1 - q))`:
   ```
   Ранг: 1000 · 0.99 ± 1.96 · √(1000 · 0.99 · 0.01) [підстановка m = 1000 та q = 0.99]
   = 990 ± 1.96 · √(9.9)                           [множення та обчислення дисперсії]
   = 990 ± 1.96 · 3.146                            [добування квадратного кореня]
   = 990 ± 6.16                                    [множення на z-квантиль 1.96, ранги від T₍₉₈₄₎ до T₍₉₉₆₎]
   ```
   В інтервалі від 984-го до 996-го значення (всього 12 точок) квантиль варіюється від `p98.4` до `p99.6`. У реальних системах із логнормальним розподілом затримок це відповідає розкиду оцінки часу відгуку від 180 мс до 1200 мс — похибка у понад 600%.
2. **Вибірка після Tail-based семплінгу повільних запитів (`m = 50 000` трейсів у хвості):**
   ```
   Ранг: 50000 · 0.99 ± 1.96 · √(50000 · 0.99 · 0.01) [підстановка m = 50000 та q = 0.99]
   = 49500 ± 1.96 · √(495)                            [множення та обчислення дисперсії]
   = 49500 ± 1.96 · 22.25                             [добування квадратного кореня]
   = 49500 ± 43.6                                     [множення на z-квантиль 1.96, ранги від T₍₄₉₄₅₆₎ до T₍₄₉₅₄₄₎]
   ```
   Відносний розкид квантиля становить лише `0.9891`..`0.9909` (похибка менше ніж 0.1%), що звужує довірчий інтервал затримки до кількох мілісекунд (`180 ± 4 мс`), перетворюючи трейсинг на надійне джерело метрик для автоскейлінгу та SLA-аудиту.

## 5. Tail-based семплінг та оцінювач Горвіца-Томпсона

Tail-based семплінг вирішує проблему втрати рідкісних збоїв шляхом стратифікації (розшарування) трафіку. Замість прийняття рішення на вході, OpenTelemetry Collector буферизує всі спани до завершення транзакції, після чого відносить трейс до однієї з взаємовиключних страт (класів):

* **Страта 1 (Помилки):** трейси зі статусом `status_code == ERROR` або HTTP 5xx. Коефіцієнт збереження `s₁ = 1.0` (100%).
* **Страта 2 (Висока затримка):** трейси з тривалістю `duration > T_threshold` (наприклад, понад 1000 мс). Коефіцієнт збереження `s₂ = 1.0` (100%).
* **Страта 3 (Швидкі штатні запити):** успішні швидкі транзакції. Коефіцієнт збереження `s₃ = s₀ ≪ 1` (наприклад, 0.1% або 0.001).

### Проблема зміщення вибірки (Sampling Bias)

Якщо просто обчислити середню затримку або частку помилок за збереженими даними Tail-based семплінгу, результат буде катастрофічно викривленим: через 100% збереження помилок та повільних запитів середня затримка у вибірці виявиться завищеною в десятки разів, а розрахований відсоток збоїв — у сотні разів вищим за реальний.

### Теорема Горвіца-Томпсона (Незміщена реконструкція популяції)

Нехай генеральна сукупність містить `N` трейсів. Для кожного `i`-го трейсу відома ймовірність його потрапляння у вибірку `πᵢ = P(i ∈ Sample)`.

Для стратифікованого Tail-based семплінгу:
```
πᵢ = 1.0,  якщо i ∈ Страта 1 або i ∈ Страта 2
πᵢ = s₀,   якщо i ∈ Страта 3
```

Оцінювач Горвіца-Томпсона (англ. *Horvitz-Thompson Estimator*) для сумарного значення довільної метрики `Y = ∑ᵢ₌₁ᴺ yᵢ` (наприклад, сумарного часу обробки або кількості запитів) визначається як зважена сума збережених елементів вибірки `S`:

```
Ŷ_HT = ∑_{i ∈ S} (yᵢ / πᵢ)
```

Кожен елемент вибірки масштабується на коефіцієнт ваги `wᵢ = 1 / πᵢ`:
* Повільні та помилкові запити входять із вагою `wᵢ = 1 / 1.0 = 1`;
* Швидкі нормальні запити входять із вагою `wᵢ = 1 / s₀ = 1 / 0.001 = 1000`.

### Доведення незміщеності оцінювача

Введемо індикаторну випадкову величину `Iᵢ`, де `Iᵢ = 1`, якщо `i`-й трейс потрапив у вибірку `S`, та `Iᵢ = 0` в іншому випадку. 

За визначенням математичного сподівання індикатора:
```
E[Iᵢ] = 1 · P(Iᵢ = 1) + 0 · P(Iᵢ = 0) = πᵢ
```

Запишемо оцінювач Горвіца-Томпсона через індикаторні змінні над усією генеральною сукупністю:

```
Ŷ_HT = ∑_{i=1}ᴺ (yᵢ / πᵢ) · Iᵢ
```

Обчислимо математичне сподівання оцінки `E[Ŷ_HT]`:

```
E[Ŷ_HT]
= E[ ∑_{i=1}ᴺ (yᵢ / πᵢ) · Iᵢ ]
= ∑_{i=1}ᴺ (yᵢ / πᵢ) · E[Iᵢ]    [лінійність математичного сподівання]
= ∑_{i=1}ᴺ (yᵢ / πᵢ) · πᵢ        [підстановка E[Iᵢ] = πᵢ]
= ∑_{i=1}ᴺ yᵢ                   [скорочення πᵢ]
= Y                             [точне сумарне значення генеральної сукупності]
```

Оскільки `E[Ŷ_HT] = Y`, оцінювач Горвіца-Томпсона є **строго математично незміщеним** (англ. *unbiased*).

### Дисперсія оцінювача Горвіца-Томпсона та її мінімізація

Загальна дисперсія оцінювача Горвіца-Томпсона має вигляд:

```
Var(Ŷ_HT) = ∑_{i=1}ᴺ ∑_{j=1}ᴺ (πᵢⱼ - πᵢ·πⱼ) · (yᵢ / πᵢ) · (yⱼ / πⱼ)
```

де `πᵢⱼ = P(i ∈ S ∧ j ∈ S)` — сумісна ймовірність включення пари трейсів.

Оскільки рішення про семплювання кожного окремого трейсу в колекторі приймається незалежно (вибірка Пуассона), для `i ≠ j` маємо `πᵢⱼ = πᵢ · πⱼ`, тому всі недіагональні коваріаційні члени обнуляються (`πᵢⱼ - πᵢ·πⱼ = 0`). Для `i = j` маємо `πᵢᵢ = πᵢ`. Формула дисперсії спрощується до однієї суми:

```
Var(Ŷ_HT) = ∑_{i=1}ᴺ ((1 - πᵢ) / πᵢ) · yᵢ²
```

Звідси стає очевидною головна математична перевага Tail-based семплінгу:
1. Для всіх критичних аномалій (помилки та хвостові затримки), де спостережуваність є найважливішою, встановлено `πᵢ = 1.0`.
2. Член `(1 - πᵢ) = (1 - 1.0) = 0`.
3. Отже, **всі рідкісні помилки та аномальні затримки роблять рівно нульовий внесок у дисперсію оцінки** (`0 · yᵢ² = 0`). Дисперсія генерується виключно фоновим штатним трафіком зі Страти 3, де значення затримок `yᵢ` є малими та однорідними.

Цей результат узгоджується з принципом оптимального розподілу Неймана (англ. *Neyman optimal allocation*) для стратифікованих вибірок, згідно з яким частка вибірки в кожній страті повинна бути пропорційною стандартному відхиленню метрики всередині цієї страти (`s_h ∝ σ_h`). Оскільки варіативність затримок у хвості є максимальною, виділення 100% квоти збереження для хвостових страт мінімізує глобальну дисперсію агрегованих метрик системи за мінімального розміру загального сховища.

## 6. Порівняльний розрахунковий приклад

Розглянемо платформу електронної комерції з добовим обсягом трафіку `N = 10 000 000` запитів.

### Структура генеральної сукупності трафіку:
1. **Швидкі успішні запити:** `N₁ = 9 989 900` (99.899%), середня тривалість `25 мс`.
2. **Повільні успішні запити (> 1000 мс):** `N₂ = 10 000` (0.100%), середня тривалість `1400 мс`.
3. **Критичні збої (HTTP 500):** `N₃ = 100` (0.001%), середня тривалість `5000 мс` (тайм-аут).

Порівняємо дві стратегії семплювання за однакового ліміту збереження сховища (приблизно 20 000 трейсів на добу):

### Стратегія А: Рівномірний Head-based семплінг із коефіцієнтом `s = 0.002` (0.2%)
* Загальна кількість збережених трейсів: `10 000 000 · 0.002 = 20 000` трейсів.
* Очікувана кількість зафіксованих помилок: `E[X₃] = 100 · 0.002 = 0.2` трейси.
* Імовірність виявити бодай один збій:
  ```
  P(X₃ ≥ 1) = 1 - (1 - 0.002)¹⁰⁰ = 1 - (0.998)¹⁰⁰ ≈ 1 - 0.8186 = 0.1814 (18.14%)
  ```
* Очікувана кількість збережених повільних трейсів: `10 000 · 0.002 = 20` трейсів (недостатньо для локалізації вузьких місць).

### Стратегія Б: Стратифікований Tail-based семплінг
* Параметри політики: `s_error = 1.0`, `s_slow = 1.0`, `s_fast = 0.001` (0.1%).
* Збережено помилок: `100 · 1.0 = 100` трейсів (100% покриття збоїв, `P = 1.0`).
* Збережено повільних запитів: `10 000 · 1.0 = 10 000` трейсів (100% покриття для побудови діаграм затримок).
* Збережено швидких запитів: `9 989 900 · 0.001 ≈ 9 990` трейсів.
* Разом збережено трейсів: `100 + 10 000 + 9 990 = 20 090` трейсів.

### Підсумок ефективності:
За однакового навантаження на диск та сховище (~20 000 трейсів) Tail-based семплінг підвищує ймовірність фіксації критичних аварій з 18.14% до 100%, забезпечуючи вичерпні діагностичні дані для розслідування інцидентів без втрати точності аналітики.
