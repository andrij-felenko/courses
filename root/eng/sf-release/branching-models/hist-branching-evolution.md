# 📜 Еволюція моделей розгалуження: від монопольного блокування файлів до розподіленого DAG

Коли на початку 1980-х років кілька розробників одночасно намагалися змінити спільний вихідний код у системі SCCS (англ. *Source Code Control System*, створеній Марком Рочкіндом у Bell Labs, 1972) або ранньому RCS (англ. *Revision Control System*, Волтер Тічі, 1982), вони стикалися з жорстким песимістичним блокуванням (англ. *pessimistic locking*). Щоб відкрити файл на редагування, інженер виконував команду `co -l` (англ. *check-out with lock*), яка встановлювала монопольний прапорець запису в операційній системі. Будь-який інший учасник команди, якому потрібно було внести навіть виправлення однієї коми в той самий файл, отримував відмову й був змушений чекати фізичного завершення роботи колеги.

У таких умовах паралельне існування кількох версій продукту — наприклад, виправлення критичного дефекту в уже відвантаженій клієнтам системі одночасно з написанням нового функціонала — вимагало фізичного дублювання всього каталогу на магнітній стрічці або окремому серверному диску. Будь-яке розгалуження було не логічною операцією в системі контролю версій, а важкою інфраструктурною процедурою з ручним порівнянням роздруківок або запусків утиліти `diff`.

## Поява оптимістичного розгалуження: ера CVS та ClearCase

Наприкінці 1980-х років Дік Грюн запропонував принципово іншу парадигму — оптимістичне паралельне редагування (англ. *optimistic concurrency*), що лягло в основу CVS (англ. *Concurrent Versions System*, 1986–1990). CVS дозволила розробникам одночасно редагувати локальні робочі копії без блокувань, перенісши тягар вирішення конфліктів на момент фіксації (`commit`) та злиття (`update`).

Разом із цим з'явилася перша масштабована концепція гілок (англ. *branches*). Проте внутрішня архітектура CVS зберігала історію на рівні окремих файлів (формат `,v` з RCS), а не репозиторію як цілісного знімка стану. Це призводило до фатальних наслідків:
1. **Неатомарність злиття:** створення гілки або встановлення тегу для проєкту з десяти тисяч файлів вимагало модифікації заголовка кожного файлу окремо. Якщо процес переривався через збій мережі або переповнення диска, репозиторій опинявся в напіврозгалуженому стані.
2. **Втрата пам'яті про злиття (Merge Memory Loss):** CVS не фіксувала факт попереднього злиття. Якщо розробник переносив зміну з гілки в стовбур у понеділок, а потім повторював операцію в п'ятницю, CVS намагалася знову застосувати понеділкові зміни, породжуючи масивні штучні конфлікти.

У промисловому секторі 1990-х років стандартом став пропрієтарний комплекс Rational ClearCase. ClearCase реалізував концепцію динамічних віртуальних файлових систем (MVFS), де кожна гілка формувалася складними конфігураційними правилами (англ. *config specs*). Це породило складні багатогілкові топології: команди створювали окремі ізольовані гілки під кожного розробника, під кожну підсистему, компонент та реліз.

Однак на практиці ClearCase призвів до явища, яке інженери охрестили «пеклом злиття» (англ. *Merge Hell*). Інтеграція підсистем відкладалася на тижні або місяці. Коли наближався дедлайн випуску, команди зупиняли розробку на кілька тижнів («період стабілізації» чи «freeze»), проводячи безсонні ночі за ручним зіставленням тисяч несумісних файлів.

## Революція Subversion та межі централізованих дерев

Створена у 2000 році компанією CollabNet система Subversion (SVN) виправила фундаментальні вади CVS:
* Ревізії стали глобальними атомарними знімками всього дерева каталогів.
* Гілка перестала бути властивістю файлу — вона стала дешевою копією каталогу всередині спеціальної структури (`/trunk`, `/branches/v1.0`, `/tags/v1.0.0`) завдяки механізму Copy-on-Write у сховищі FSFS.

Попри цей крок уперед, SVN тривалий час (до версії SVN 1.5 у 2008 році) не мала вбудованого механізму відстеження історії злиттів (англ. *merge tracking*). Інженерам доводилося вручну записувати в коментарях до коміту номери ревізій:
```text
svn merge -r 14205:14280 http://svn.example.com/repos/trunk .
svn commit -m "Merged revisions 14205 through 14280 from trunk into release-1.2"
```

Будь-яка помилка в номері ревізії призводила або до пропуску критичного виправлення, або до повторного застосування змін і пошкодження робочого коду. Бекпорт перетворювався на кропітку бухгалтерську роботу, схильну до людських помилок.

## Народження Git та спрямованого ациклічного графу (DAG)

У 2005 році Лінус Торвальдс для потреб розробки ядра Linux створив Git. В основі Git лежить не дерево каталогів і не списки змін, а спрямований ациклічний граф (англ. *Directed Acyclic Graph*, DAG), де кожен коміт є незмінним криптографічним хешем (SHA-1, згодом SHA-256) від знімка дерева файлів, метаданих автора та масиву батьківських комітів.

У цій архітектурі:
* Гілка — це просто 41-байтний текстовий файл у каталозі `.git/refs/heads/`, що містить хеш останнього коміту. Створення, перемикання чи видалення гілки стало операцією складності `O(1)`.
* Злиття перестало бути сліпим накладанням латок: Git автоматично знаходить найближчого спільного предка (англ. *merge base*) у графі та застосовує тристороннє злиття (англ. *3-way merge*).
* З'явилася операція `git cherry-pick`, яка дозволила витягати дельту конкретного коміту та застосовувати її до абсолютно довільної гілки з автоматичним вирахуванням контексту.

## Суперечка 2010-х: Маятник GitFlow проти Trunk-Based

Легкість створення гілок у Git породила зворотну проблему: інженери почали створювати їх у надмірній кількості.

У 2010 році Вінсент Дріссен опублікував статтю «A successful Git branching model», яка описала шаблон **GitFlow**. Модель пропонувала жорстку ієрархію:
* Вічна гілка `master` (лише готові до продакшену релізи).
* Вічна гілка `develop` (основна інтеграційна лінія).
* Довгоживучі гілки `feature/*` для кожної нової задачі.
* Тимчасові гілки `release/*` для ручної стабілізації.
* Гілки `hotfix/*` для екстрених латок, які зливалися одночасно і в `master`, і в `develop`.

Протягом кількох років GitFlow став де-факто стандартом індустрії. Проте з поширенням методологій безперервної інтеграції (CI) та безперервної доставки (CD), описаних Джезом Гамблом і Дейвом Фарлі (2010), виявилися системні дефекти GitFlow:
1. **Відкладена інтеграція:** гілки `feature` жили тижнями. Розробники не бачили змін один одного, що відроджувало старе «пекло злиття» ClearCase.
2. **Двобічне злиття та десинхронізація:** злиття `hotfix` у дві різні гілки (`master` та `develop`) через різницю в їхній історії часто призводило до того, що виправлення, накладене в продакшені, губилося при наступному плановому випуску з `develop`.

У відповідь гіганти індустрії (Google, Meta, ThoughtWorks, Netflix) сформулювали альтернативу — **Trunk-Based Development (TBD)**. Її кредо: єдиний основний стовбур (`main`/`trunk`), відсутність довгоживучих функціональних гілок (час життя гілки обмежується кількома годинами), а неготові можливості ізолюються в коді за допомогою динамічних прапорців функцій.

Для продуктів, що не можуть оновлюватися безперервно (вбудовані мікроконтролери, операційні системи, медичні прилади, локальні корпоративні інсталяції), індустрія виробила гібрид: **Trunk-Based Development із гілками супроводу релізів (Release/LTS Branches)**. У цій схемі розробка ведеться виключно в стовбурі, а гілка версії створюється в момент релізу лише для стабілізації та подальшого точкового бекпорту критичних виправлень за принципом Upstream-First.
