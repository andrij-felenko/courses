# 📋 Специфікація маніфесту бекпорту та протоколу маркування комітів

Автоматизація бекпортів виправлень у багатогілкових репозиторіях вимагає суворого контракту між розробниками, роботами CI/CD та реєстром релізів. Відсутність формалізованого стандарту призводить до появи невідстежуваних латок, заблокованих черг злиття, пошкодження бінарної сумісності та пропущених регресій.

Цей документ визначає повну специфікацію декларативного маніфесту конфігурації бекпорту (`.github/backport.yml` або `backport.json`), стандартизовану структуру метаданих коміту, стани автомата обробки латок, схему подій життєвого циклу та протокол REST/Webhook інтерфейсу для сервісів автоматичного створення бекпорт-PR.

## Специфікація декларативного маніфесту (`backport.yml`)

Маніфест розміщується в корені репозиторію в гілці за замовчуванням (`main`) і зчитується автоматизованим ботом під час обробки подій злиття Pull Request. Будь-які зміни в правилах супроводу версій набувають чинності лише після злиття оновленого маніфесту в стовбур.

```yaml
# Специфікація конфігурації автоматизованого бекпорту версії 2.0
version: 2

# Глобальні налаштування бота
settings:
  # Шаблон заголовка створюваного Backport PR
  pr_title_template: "[%{target_branch}] %{original_title}"
  
  # Шаблон повідомлення коміту cherry-pick
  commit_message_template: |
    %{original_title}

    %{original_body}

    (cherry picked from commit %{commit_sha})
    Upstream-commit: %{commit_sha}
    Backport-generated-by: release-bot/v2.4
  
  # Автоматичне копіювання міток і рецензентів
  copy_labels: true
  copy_assignees: true
  auto_merge: false

# Правила зіставлення гілок і міток PR
rules:
  - target_branch: "support/v2.4"
    trigger_label: "backport/v2.4"
    merge_strategy: "cherry-pick"
    conflict_resolution: "fail" # [fail, draft-pr, open-issue]
    required_checks:
      - "ci/hil-matrix-v2.4"
      - "ci/security-scanner"
    reviewers:
      - "lts-maintainers-v2"

  - target_branch: "support/v1.8"
    trigger_label: "backport/v1.8"
    merge_strategy: "cherry-pick"
    conflict_resolution: "draft-pr"
    allow_refactoring: false
    max_line_delta: 250
    required_checks:
      - "ci/legacy-toolchain-gcc9"
      - "ci/regression-lts-v1"
    reviewers:
      - "lts-maintainers-v1"
      - "security-lead"
```

### Семантика полів маніфесту

* `version` *(ціле число, обов'язкове)*: версія схеми маніфесту. Поточна актуальна версія — `2`. Використання застарілих версій схемы блокується валідатором конвеєра.
* `settings.pr_title_template` *(рядок, обов'язковий)*: форматування назви автоматично відкритого запиту на злиття. Дозволяє фільтрувати релізні запити в панелях моніторингу за префіксом гілки.
* `settings.commit_message_template` *(багаторядковий текст, обов'язковий)*: шаблон формування опису коміту під час операції переносу. Змінна `%{commit_sha}` розгортається в повний 40-символьний хеш вихідного коміту в стовбурі.
* `settings.copy_labels` *(булеве значення)*: прапорець дублювання категорійних міток (наприклад, `security`, `bug`, `networking`) з оригінального запиту.
* `settings.auto_merge` *(булеве значення)*: дозвіл на автоматичне злиття бекпорт-PR у цільову гілку після успішного проходження всіх обов'язкових перевірок статусу без участі людини. У лініях підтримки з високим рівнем ризику рекомендується вимикати (`false`).
* `rules[].target_branch` *(рядок, обов'язковий)*: точне ім'я цільової гілки супроводу (`support/v2.4`) або шаблон пошуку за маскою (`support/v*`).
* `rules[].trigger_label` *(рядок, обов'язковий)*: мітка в інтерфейсі хостингу репозиторіїв (GitHub/GitLab), наявність якої в момент злиття вихідного PR сигналізує боту про необхідність запуску перенесення латки.
* `rules[].conflict_resolution` *(перелічуваний тип: `fail`, `draft-pr`, `open-issue`)*: стратегія обробки синтаксичних та контекстних конфліктів:
  * `fail`: негайне завершення задачі з ненульовим кодом і публікація коментаря з помилкою;
  * `draft-pr`: створення чорнового запиту на злиття з конфліктними маркерами та призначенням відповідального інженера для ручного виправлення;
  * `open-issue`: реєстрація нового інциденту в трекері задач без створення гілок.
* `rules[].max_line_delta` *(ціле число)*: максимально допустима сума змінених рядків (`insertions + deletions`). Запобігає випадковому бекпорту масштабних рефакторингів під виглядом виправлень дефектів.

## Протокол трейлерів коміту (Git Commit Trailers)

Для забезпечення машинозчитуваності та збереження походження змін усі коміти бекпорту зобов'язані містити стандартизовані трейлери відповідно до стандарту `git-interpret-trailers`:

```text
[v2.4] fix(crypto): prevent timing attack in signature verification

Constant-time comparison was broken when processing truncated nonces.
This patch replaces standard memcmp with secure_memcmp_const.

(cherry picked from commit 8f4a21b3c990a174f82d1c9b3a0e4)
Upstream-commit: 8f4a21b3c990a174f82d1c9b3a0e4
Fixes: CVE-2026-3109
Regression-of: 4c129e00fa1b
Backport-risk: LOW
Sign-off-by: Security Lead <sec@example.com>
```

### Визначення ключів трейлерів

* **`Upstream-commit`** *(Обов'язковий)*: Повний 40-символьний хеш (або 64-символьний для SHA-256) оригінального коміту в стовбурі `main`. Використовується автоматизованими сканерами для побудови матриці покриття вразливостей.
* **`Fixes`** *(Рекомендований)*: Ідентифікатор виправленої помилки, дефекту або вразливості в системі відстеження (наприклад, `CVE-2026-3109`, `ISSUE-4091`).
* **`Regression-of`** *(Опціональний)*: Хеш коміту, який первинно вніс дефект у кодову базу. Дозволяє автоматично обмежувати діапазон пошуку під час запуску `git bisect` на застарілих гілках.
* **`Backport-risk`** *(Опціональний)*: Рівень складності та ризику латки (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`). Значення `HIGH` вимагає обов'язкового подвійного рецензування провідними архітекторами релізу.

## Життєвий цикл автомата обробки бекпортів

Автоматизований сервіс бекпорту функціонує як детермінований скінченний автомат:

1. **Фаза валідації вхідних даних (Ingress Validation):** перевірка факту злиття вихідного PR у стовбур, валідація наявності GPG-підпису автора та зчитування списку міток запуску.
2. **Фаза блокування гілки (Branch Concurrency Lock):** встановлення тимчасового блокування (Mutex) на цільову релізну гілку в базі даних координатора. Це унеможливлює паралельне накладання двох різних бекпортів, що могло б призвести до гонитви за номерами ревізій або конфліктів у спільних файлах.
3. **Фаза виконання операції перенесення (Cherry-Pick Execution):** клонування репозиторію в ізольоване тимчасове середовище, перемикання на цільову гілку та виконання команди `git cherry-pick -x <SHA>`.
4. **Фаза верифікації бінарної сумісності (ABI Compliance):** запуск статичного аналізатора заголовкових файлів (`abi-dumper` / `libabigail`). Якщо патч змінює розмір структур, зміщення полів чи сигнатури експортованих функцій, процес переривається.
5. **Фаза публікації та реєстрації (Publish & Register):** створення нової віддаленої гілки `backport/v2.4-pr-1420`, відкриття Pull Request через REST API хостингу та призначення команди супроводу.

## Специфікація подій життєвого циклу Webhook

Сервіс автоматизації генерує події для сповіщення зовнішніх систем моніторингу та конвеєрів збирання:

* **`backport.triggered`**: зафіксовано факт злиття в `main` PR із міткою бекпорту. Містить хеш джерела та перелік цільових гілок.
* **`backport.applied`**: латка успішно накладена на робочу копію гілки без синтаксичних конфліктів.
* **`backport.conflict`**: операція `cherry-pick` зупинилася через несумісність коду. Подія містить список конфліктних файлів.
* **`backport.abi_violation`**: виявлено злам бінарної сумісності інтерфейсів у публічних заголовках.
* **`backport.merged`**: бекпорт-PR успішно перевірено матрицею CI та влито в лінію довготривалого супроводу.

## Безпека та модель прав доступу бота

Для запобігання несанкціонованим змінам у захищених гілках релізу бот повинен відповідати наступним стандартам безпеки:
* **Принцип найменших привілеїв:** бот використовує токен GitHub App із правами запису лише у гілки з префіксом `backport/*` та відкриття Pull Request. Прямий пуш у гілки `support/*` блокується правилами захисту гілок (Branch Protection Rules).
* **Криптографічний підпис комітів:** усі автоматично створені коміти бекпорту підписуються виділеним GPG/SSH ключем бота для проходження перевірки `commit signature verification`.
* **Захист від несанкціонованого бекпорту:** мітка `backport/vX.Y` може бути додана до PR лише інженерами з правами супроводу релізу (Release Maintainers / Code Owners).

## REST API інтерфейс вебхука бекпорту

### `POST /api/v1/backport/execute`
Ініціює процедуру перенесення злитого коміту в зазначену гілку.

#### Заголовки запиту (Request Headers)
* `Content-Type: application/json`
* `X-Release-Signature: sha256=...` — криптографічний підпис HMAC тіла запиту на базі спільного секретного ключа для захисту від підробки запитів.

#### Тіло запиту (Request Body)
```json
{
  "repository": "hardware/firmware-core",
  "source_commit_sha": "8f4a21b3c990a174f82d1c9b3a0e4123456789ab",
  "target_branch": "support/v2.4",
  "original_pr_number": 1420,
  "author": "john.dev",
  "force": false
}
```

#### Успішна відповідь (`201 Created`)
```json
{
  "status": "SUCCESS",
  "backport_pr_number": 1425,
  "backport_pr_url": "https://github.com/hardware/firmware-core/pull/1425",
  "cherry_picked_sha": "c39e1284fa00b171f92e1d0c4b1a23456789cdef",
  "conflicts": []
}
```

#### Відповідь при конфлікті (`409 Conflict`)
```json
{
  "status": "CONFLICT",
  "error_code": "ERR_CHERRY_PICK_CONFLICT",
  "message": "Automatic cherry-pick failed due to syntactic conflicts.",
  "conflicted_files": [
    "drivers/net/ethernet_core.c",
    "include/drivers/net_types.h"
  ],
  "draft_pr_number": 1426,
  "action_required": "MANUAL_RESOLUTION"
}
```

## Довідник кодів помилок бекпорт-сервісу

| Код помилки | HTTP статус | Причина виникнення | Спосіб усунення |
| :--- | :--- | :--- | :--- |
| `ERR_SOURCE_NOT_ON_MAIN` | `400 Bad Request` | Вихідний коміт не знайдено серед предків гілки `main`. | Забезпечити злиття коміту в стовбур за принципом Upstream-First. |
| `ERR_BRANCH_FROZEN` | `423 Locked` | Цільова гілка переведена в статус завершення життєвого циклу (EOL). | Оновити маніфест супроводу або перевести пристрої на новішу версію. |
| `ERR_CHERRY_PICK_CONFLICT` | `409 Conflict` | Синтаксичні конфлікти при спробі автоматичного накладання diff. | Створити локальну робочу копію та розв'язати конфлікти вручну. |
| `ERR_ABI_BREAKAGE` | `422 Unprocessable` | Патч ламає бінарну сумісність у стабільній бібліотеці. | Переписати латку так, щоб зберегти розміри структур і сигнатури функцій. |
| `ERR_DIFF_LIMIT_EXCEEDED` | `413 Payload Too Large` | Кількість змінених рядків перевищує встановлений ліміт `max_line_delta`. | Розбити коміт на точкове виправлення та супутні зміни. |
