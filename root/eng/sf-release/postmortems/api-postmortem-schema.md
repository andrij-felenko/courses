# 📋 Канонічна схема постмортему, структуровані інваріанти та CLI-контракт

Машинночитний контракт артефакту постмортему фіксує структуру метаданих інциденту, правила валідації хронології та інтерфейс командного рядка для автоматизованої перевірки звітів. Використання стандартизованої схеми усуває суб'єктивність під час розбору аварій і дає змогу агрегувати патерни системних дефектів у межах усієї інженерної організації.

---

## 1. Концепція артефакту як коду

Постмортем розглядається не як вільний текстовий документ у довільному форматі, а як типізований версійований артефакт, що зберігається в репозиторії поряд із вихідним кодом інфраструктури або у форматі Markdown із суворим YAML-заголовком (Frontmatter).

Такий підхід забезпечує чотири фундаментальні властивості:
1. **Машинна валідація на етапі неперервної інтеграції (CI):** конвеєр автоматично перевіряє повноту заповнення полів, монотонність часових міток і наявність відповідальних за коригувальні дії інженерів.
2. **Програмна агрегація метрик надійності:** аналітичні сервіси витягують інтервали MTTD/MTTR, відсоток вичерпання бюджету помилок і частоту відмов окремих компонентів безпосередньо з репозиторію.
3. **Автоматична синхронізація завдань:** парсер генерує та відстежує стан виконання задач у системі відстеження помилок для кожного пункту виправлень.
4. **Імутабельність та простежуваність історії:** історія інциденту фіксується за допомогою криптографічно підписаних комітів, що гарантує збереження первинних свідчень без можливості прихованого редагування.

## 3. Семантичний опис полів та інваріанти структури

Кожна секція схеми накладає чіткі семантичні обмеження на значення, що вносяться інженерною командою під час розслідування.

### 3.1. Блок ідентифікації та статусів (`metadata`)
* `id` — унікальний стабільний ключ інциденту за шаблоном `INC-РРРР-ММ-ДД-<слуг>`. Слуг повинен стисло відображати технічний механізм збою (наприклад, `INC-2026-08-14-checkout-deadlock`), а не оціночні судження чи імена інженерів.
* `title` — лаконічний технічний заголовок довжиною від 10 до 160 символів, який містить назву постраждалої підсистеми та характер відмови.
* `severity` — рівень критичності інциденту, визначений на основі об'єктивних метрик впливу на бізнес та угоду про рівень обслуговування.
* `status` — поточний етап життєвого циклу постмортему:
  * `draft` — початкове наповнення таймлайну та збір сирих логів безпосередньо після завершення аварії;
  * `in_review` — чернетку завершено, документ передано на рецензування фасилітатору та технічним експертам суміжних команд;
  * `approved` — спільний міт огляду проведено, системні чинники узгоджено, відповідальних за заходи призначено;
  * `actions_completed` — усі завдання з масиву `action_items` верифіковано та закрито в трекері завдань.

### 3.2. Ролі та обов'язки (`roles`)
Схема вимагає обов'язкової фіксації персональної відповідальності за розслідування, щоб уникнути ситуації, коли документ залишається незавершеним:
* `incident_commander` — інженер, який координував локалізацію аварії в оперативному штабі;
* `scribe` — секретар, який у реальному часі вів протокол дій та фіксував часові мітки в інцидентному чаті;
* `postmortem_owner` — автор підсумкового звіту, відповідальний за детальну реконструкцію механізму збою;
* `review_facilitator` — нейтральний інженер із культури надійності, який проводить зустріч розбору та стежить за дотриманням культури без вини.

### 3.3. Кількісна оцінка впливу (`impact`)
* `services_affected` — список ідентифікаторів сервісів згідно з внутрішнім каталогом архітектури.
* `user_facing_duration_minutes` — тривалість спостережуваного клієнтами погіршення якості сервісу. Математично повинна збігатися з інтервалом між подіями `impact_started` та `impact_ended`.
* `error_budget_consumed_percent` — точна частка місячного бюджету помилок за відповідним індикатором рівня обслуговування, спалена під час інциденту.
* `requests_failed_count` — абсолютна кількість запитів користувачів, які завершилися помилками класу 5xx або скиданням з'єднання через вичерпання таймаутів.
* `data_loss_occurred` — логічний прапорець, що вказує на наявність незворотної втрати або пошкодження стану в сховищах даних.

## 4. Скінченний автомат життєвого циклу артефакту (State Machine)

Перехід артефакту між станами регулюється суворим скінченним автоматом:

```text
[Інцидент локалізовано] ──> draft ──(чернетка заповнена)──> in_review
                                                                │
                     ┌──────────────────────────────────────────┘
                     ▼
                 approved ──(усі Action Items закриті в Jira)──> actions_completed
```

Правила переходу:
1. `draft → in_review`: вимагає наявності щонайменше трьох подій у хронології, заповнених полів `roles`, `impact` та хоча б однієї сформульованої гіпотези системного фактора.
2. `in_review → approved`: вимагає проведення спільного мітингу огляду, підпису фасилітатора (`review_facilitator`) та наявності валідних посилань на створені задачі в полі `issue_url` для кожного коригувального заходу.
3. `approved → actions_completed`: перехід здійснюється автоматичним фоновим демоном CI після того, як вебхук трекера завдань підтвердить закриття останнього тікета з прив'язкою до цього інциденту.

## 5. Матриця критичності (Severity Matrix) та операційні SLA

Рівень критичності інциденту визначає вимоги до термінів складання звіту, глибини аудиту та обов'язкових класів коригувальних дій:

| Рівень | Критерій впливу на користувача / SLO | Обов'язковість постмортему | SLA на огляд звіту | SLA на закриття Tier 1/2 дій |
|---|---|---|---|---|
| **SEV-1** | Повна недоступність ключового сервісу; втрата даних; падіння > 50% запитів; спалено > 20% місячного SLO | Обов'язково (повний аудит) | ≤ 48 годин | ≤ 14 календарних днів |
| **SEV-2** | Часткова деградація (p99 латентність > 3x порогу); відмова другорядного функціоналу; спалено 5–20% SLO | Обов'язково (стандартний) | ≤ 5 робочих днів | ≤ 30 календарних днів |
| **SEV-3** | Внутрішній збій без помітного впливу на клієнтів; майже-аварія (*near-miss*) з високим потенціалом | За рішенням ліда сервісу | ≤ 10 робочих днів | ≤ 60 календарних днів |
| **SEV-4** | Дрібні аномалії, ізольовані флакаючі тести, одиничні виправні перезапуски подів | Не обов'язково (лог у трекер) | Не застосовується | Не застосовується |

## 6. Класифікація системних чинників (Contributing Factors Taxonomy)

Категоризація сприяючих факторів у полі `category` дає змогу виявляти системні слабкості в інженерних процесах компанії:

1. `architectural_vulnerability` — дефекти проєктування взаємодії компонентів: відсутність обмеження конкурентності, блокувальні мережеві виклики всередині транзакцій, відсутність ізоляції відмов.
2. `testing_gap` — невідповідність середовищ тестування продакшену, відсутність негативних тестів на розрив мережі або хибні припущення в мок-об'єктах.
3. `observability_blind_spot` — відсутність необхідних метрик, зависокий поріг спрацьовування алертів, агрегація за середнім значенням замість процентилів або відсутність наскрізних ідентифікаторів трасування.
4. `deployment_tooling` — дефекти конвеєрів розгортання: відсутність перевірки стану перед перемиканням трафіку, неможливість швидкого автоматичного відкату версії.
5. `capacity_saturation` — вичерпання пулу з'єднань, дефіцит пам'яті (OOM), дискового простору або процесорних лімітів через нелінійне зростання навантаження.
6. `dependency_failure` — відмова або деградація сторонніх хмарних провайдерів, платіжних шлюзів, DNS-резолверів або авторизаційних центрів.
7. `cognitive_overload` — надмірна складність інтерфейсу інструментів керування, шторм нерелевантних алертів під час аварії або суперечлива документація в регламентах.

## 7. Ієрархія коригувальних дій (Action Items Hierarchy)

Кожен захід із масиву `action_items` зобов'язаний мати визначений рівень інженерного контролю:

* `tier_1_elimination` (Архітектурне усунення) — повне усунення можливості виникнення збою на рівні дизайну системи (наприклад, перехід на незмінну інфраструктуру, типізовані контракти схем, фізичне вилучення небезпечних операцій з інтерфейсу).
* `tier_2_automation` (Інженерна автоматизація) — програмні бар'єри та запобіжники (автоматичний відкіт канарки, circuit breakers, ліміти швидкості запитів, валідаційні вебхуки у Kubernetes).
* `tier_3_detection` (Діагностика та спостережуваність) — додавання чутливих метрик, синтетичного моніторингу та гранулярних алертів, що скорочують час виявлення (MTTD).
* `tier_4_procedural` (Процедури та документація) — оновлення інструкцій, регламентів реагування та проведення тренінгів. Має найнижчу надійність, оскільки покладається на людську пам'ять під час стресу.

```yaml
# Розширений аналіз інциденту INC-2026-08-14-checkout-deadlock

## Короткий зміст (Executive Summary)
14 серпня 2026 року о 02:16 UTC під час старту нічного розпродажу сервіс оформлення замовлень checkout-gateway зазнав каскадної відмови тривалістю 68 хвилин. Загалом було відхилено 142 800 спроб оплати, спалено 38.4% місячного бюджету помилок. Причиною стало блокування пулу бази даних синхронним викликом зовнішнього сервісу податкових ставок. Роботу відновлено перемиканням прапорця на локальний приблизний розрахунок.

## Причинно-наслідковий ланцюг (5 Whys)
1. **Чому впав checkout-gateway?** Усі потоки обробки зависли в очікуванні вільного з'єднання з базою даних у пулі HikariCP.
2. **Чому з'єднання пулу були зайняті?** Кожне з'єднання утримувало відкриту SQL-транзакцію впродовж 1200–1800 мс замість звичних 15 мс.
3. **Чому транзакції тривали так довго?** Всередині блоку `@Transactional` виконувався HTTP-запит до стороннього податкового шлюзу TaxCloud.
4. **Чому сторонній шлюз сповільнився?** Шлюз вендора зазнав навантаження і відповідав повільно, але не рвав з'єднання.
5. **Чому код містив блокувальний виклик у транзакції?** Відсутній архітектурний лінтер і статичний аналізатор заборони мережевого I/O всередині контексту транзакцій.
```

## 9. Правила верифікації та інваріанти цілісності

Програмний валідатор постмортемів перевіряє такі системні правила:

1. **Строга хронологічна монотонність:**
   Часові мітки в списку `timeline` повинні бути строго монотонно впорядковані за зростанням. Жодна дія з фази пом'якшення (`mitigation_applied`) не може мати часову мітку, що передує фіксації виявлення (`detected_by_alert`).
2. **Обов'язковість сильних бар'єрів для SEV-1/SEV-2:**
   Для будь-якого інциденту критичності SEV-1 або SEV-2 масив `action_items` зобов'язаний містити **щонайменше один захід рівня `tier_1_elimination` або `tier_2_automation`**. Якщо звіт містить виключно процедурні пункти («оновити документацію», «нагадати команді на мітингу»), валідатор відхиляє документ із кодом помилки `DEFECT_NO_SYSTEMIC_REMEDIATION`.
3. **Персональна відповідальність без розмивання:**
   Поле `owner` кожної дії має містити дійсну електронну пошту конкретного інженера. Призначення на групові скриньки (наприклад, `devs@company.internal`) заборонено, оскільки це призводить до втрати контролю над виконанням завдання.
4. **Контроль тривалості деградації:**
   Значення `user_facing_duration_minutes` має математично відповідати інтервалу між `impact_started` та `impact_ended` у таймлайні з допустимим розходженням не більше 60 секунд.

## 10. Алгоритм розрахунку спаленого бюджету помилок

Для автоматичного заповнення поля `error_budget_consumed_percent` утиліта інтегрується з базою даних часових рядів моніторингу (Prometheus / VictoriaMetrics).

Розрахунок виконується за формулою інтегральної суми збійних запитів за період інциденту:
```text
Total_Requests = ∫ (від T_impact_start до T_impact_end) Rate(http_requests_total) dt
Bad_Requests   = ∫ (від T_impact_start до T_impact_end) Rate(http_requests_5xx_total) dt

Allowed_Bad_Requests = Total_Requests_Monthly · (1 − SLO_Target)
Error_Budget_Burned  = (Bad_Requests / Allowed_Bad_Requests) · 100%
```

Якщо за 68 хвилин аварії сервіс отримав 1 000 000 запитів, із яких 142 800 завершилися збоєм, а місячний бюджет помилок за цільового SLO 99.9% становить 372 000 запитів, спалена частка складає:
```text
Error_Budget_Burned = (142 800 / 372 000) · 100% = 38.38%
```

Валідатор автоматично перевіряє зазначене у звіті число з точністю до десятих часток відсотка шляхом виконання прямого PromQL-запиту до сховища метрик за відповідний інтервал часу.

## 11. Інтеграція з конвеєрами CI/CD та блокування релізів

Утиліта `postmortem-lint` використовується як обов'язковий крок у процесі неперервної доставки:

1. **Блокування розгортання при невиконаних SLA:**
   Якщо за сервісом закріплено затверджений постмортем рівня SEV-1, у якому дія рівня `tier_1_elimination` або `tier_2_automation` перевищила встановлений 14-денний термін виконання (`target_sla_days`), конвеєр CI блокує злиття нових функціональних PR для цього сервісу, дозволяючи лише виправлення помилок надійності.
2. **Автоматична перевірка лінків на телеметрію:**
   Під час валідації утиліта надсилає тестові HTTP HEAD-запити до систем збору логів (Loki, Elasticsearch) та трейсингу (Jaeger, Tempo), перевіряючи, що посилання на графіки та логи є дійсними й доступними для перегляду всіма інженерами організації.

## 12. Словник кодів діагностики валідатора (Diagnostic Codes)

Під час виконання аудиту утиліта видає стандартизовані коди дефектів:

* `ERR_TIMELINE_NOT_MONOTONIC` — часова мітка `t[i+1]` є меншою за `t[i]`. Виникає через часовий зсув (clock drift) або неузгодженість часових поясів серверів.
* `ERR_SEV1_MISSING_STRONG_TIER` — для інциденту рівня SEV-1 або SEV-2 відсутні заходи класів `tier_1_elimination` або `tier_2_automation`.
* `ERR_GENERIC_ACTION_OWNER` — поле `owner` містить групову розсилку замість персональної адреси відповідального інженера.
* `ERR_UNREACHABLE_TELEMETRY_LINK` — зазначене у хронології посилання на збережений запит у Grafana чи Kibana повертає HTTP 404 або вимагає приватних прав доступу.
* `ERR_DISCREPANCY_DURATION_IMPACT` — різниця між задекларованим `user_facing_duration_minutes` та фактичним інтервалом у таймлайні перевищує 60 секунд.
* `ERR_SLO_BURN_CALCULATION_MISMATCH` — відхилення між спаленим бюджетом у звіті та перевірочним PromQL-запитом перевищує 1.5%.

## 13. Агрегація патернів відмов та пошуковий індекс бази знань

Організаційний ефект від постмортемів досягається лише тоді, коли інженери можуть знаходити схожі інциденти минулих років за лічені секунди:

1. **Автоматична індексація за категоріями сприяючих факторів:**
   Сервіс бази знань парсить поле `root_contributing_factors` і будує граф системних залежностей. Якщо за останні шість місяців п'ять незалежних сервісів зазнали деградації через категорію `capacity_saturation` у бібліотеці пулу з'єднань, інфраструктурна платформа автоматично генерує спільне системне завдання на зміну глобальних налаштувань за замовчуванням.
2. **Семантичний пошук та виявлення прихованого зв'язку:**
   Векторні ембеддінги описів інцидентів дозволяють знаходити аналоги збоїв, навіть якщо команди використовують різну термінологію (наприклад, «падіння шлюзу через чергу» та «таймаут зворотного проксі через переповнення сокетів»).
3. **Регулярний огляд майже-аварій (Near-Miss Analytics):**
   Щоквартальний звіт агрегує інциденти рівня SEV-3, де спрацювали автоматичні захисні бар'єри (circuit breakers або аварійний відкіт), виявляючи вузькі місця архітектури до того, як вони спричинять повномасштабну аварію SEV-1.
4. **Дедуплікація та злиття дублікатів інцидентів:**
   Якщо під час масштабного мережевого збою кілька чергових інженерів у різних дата-центрах паралельно відкривають власні звіти, схема підтримує поле `merged_into_id`. Автоматичний аналізатор виявляє часовий збіг подій, об'єднує суміжні таймлайни та перераховує спільний спалений бюджет помилок для всієї інфраструктури.
5. **Мультирегіональна нормалізація впливу:**
   Для розподілених систем, розгорнутих у кількох регіонах хмарних провайдерів (наприклад, AWS us-east-1 та eu-central-1), схема фіксує радіус ураження для кожного географічного кластера окремо. Це дає змогу виявити, чи спрацювала ізоляція відмов на рівні комірок (Cell-based architecture) або ж каскад перекинувся через трансконтинентальну реплікацію.

## 14. Безпека даних та санітизація телеметрії

Перед збереженням артефакту постмортему у загальнодоступному репозиторії виконується автоматичне очищення конфіденційної інформації:
* **Персональні дані користувачів (PII):** імена, номери телефонів, адреси електронної пошти та платіжні реквізити клієнтів у наведених фрагментах логів маскуються або замінюються на синтетичні хеші.
* **Секрети та облікові дані:** токени авторизації, ключі API, паролі до баз даних та сесійні куки вилучаються за допомогою регулярних виразів безпеки.

## 15. CLI-контракт утиліти postmortem-lint

Інструмент командного рядка `postmortem-lint` інтегрується в Git pre-commit хуки та конвеєри перевірки вихідного коду:

```text
УЖИТОК:
  postmortem-lint <шлях-до-файлу-або-каталогу> [команда] [опції]

КОМАНДИ:
  validate     Перевірити валідність JSON-схеми та виконання бізнес-інваріантів
  metrics      Обчислити інтервали MTTD, MTTA, MTTM, MTTR та спалений бюджет помилок
  export-jira  Синхронізувати action_items зі створенням тікетів у трекері Jira
  sanitize     Перевірити та замаскувати конфіденційні дані й секрети у фрагментах логів

ОПЦІЇ:
  --strict     Вимагати 100% наявності прямих посилань на графіки телеметрії
  --json       Вивести результат діагностики у машиночитному форматі JSON
  --schema     Вказати шлях до альтернативного файлу JSON-схеми
  --prom-url   Вказати URL сервера Prometheus для верифікації спаленого бюджету
```

### Формат REST API запиту на експорт у трекер задач (Jira Payload)
Під час виконання команди `postmortem-lint export-jira` інструмент надсилає структурований JSON-пакет до системи Jira API:

```json
{
  "fields": {
    "project": { "key": "RELIABILITY" },
    "summary": "[POSTMORTEM-ACT] INC-2026-08-14: Винести виклик стороннього API податків за межі транзакції БД",
    "description": "Автоматично створено з артефакту postmortem-INC-2026-08-14-checkout-deadlock.md.\nРівень контролю: tier_1_elimination.\nSLA: 14 днів.",
    "issuetype": { "name": "Action Item" },
    "priority": { "name": "Critical" },
    "assignee": { "name": "dmytro.koval" },
    "customfield_10042": "INC-2026-08-14-checkout-deadlock",
    "customfield_10043": "tier_1_elimination"
  }
}
```

### Коди виходу (Exit Codes)
* `0` — Документ повністю валідний, усі інваріанти та правила надійності виконано.
* `1` — Помилка бізнес-логіки (відсутній Tier 1/2 захід для SEV-1, порушена монотонність часових міток, прострочений SLA огляду).
* `2` — Синтаксична помилка парсингу YAML Frontmatter або невалідний Markdown.
* `3` — Неприпустимі аргументи командного рядка або відсутність доступу до файлу.
