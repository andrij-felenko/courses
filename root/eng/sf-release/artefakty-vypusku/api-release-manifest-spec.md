# 📋 Специфікація бінарного маніфесту прошивки та схеми JSON-пакета релізу

Ця специфікація визначає два взаємодоповнюючі рівні інтерфейсного контракту релізного пакета:
1. **Бінарний заголовок прошивки (англ. *Firmware Header Spec*):** компактна фіксована бінарна структура розміром 128 байтів, що передує виконуваному образу у Flash-пам'яті та інтерпретується первинним завантажувачем (Bootloader) мікроконтролера.
2. **Схема JSON-маніфесту випуску (англ. *Release Metadata Schema*):** декларативний документ `release-metadata.json`, який супроводжує повний релізний архів у сховищі артефактів (Artifact Registry) та використовується серверами OTA, конвеєрами DevSecOps і аудиторськими системами.

## 1. Архітектурні принципи бінарного заголовка

Для забезпечення надійної роботи на вбудованих платформах без операційної системи бінарний заголовок проектується з урахуванням суворих апаратних обмежень:

- **Фіксований розмір та вирівнювання:** Розмір заголовка строго зафіксовано на рівні 128 байтів (`0x0080`), що кратно типовим лініям кешу та розмірам сторінок запису внутрішньої Flash-пам'яті (Flash write page). Усі 16-бітні та 32-бітні поля вирівняні за власними природними межами адрес, що унеможливлює виникнення винятків апаратного невирівняного доступу (англ. *UsageFault: UNALIGNED access*) на процесорах ARM Cortex-M0/M3/M4.
- **Порядок байтів (Endianness):** Усі числові поля кодуються у форматі Little-Endian (найменш значущий байт розташовується за молодшою адресою пам'яті), що відповідає нативному порядку байтів більшості сучасних мікроконтролерів архітектур ARM Cortex-M та RISC-V.
- **Дворівнева перевірка цілісності:** Спочатку завантажувач перевіряє швидку апаратну контрольну суму `header_crc32` від перших 44 байтів заголовка, щоб відсікти пошкодження метаданих через збій живлення Flash. Лише після цього обчислюється ресурсомісткий криптографічний геш SHA-256 від усього багатокілобайтного образу прошивки та перевіряється цифровий підпис.

### Розкладка пам'яті та зміщення полів бінарного заголовка

| Зміщення (Offset) | Поле структури | Тип даних | Призначення та діапазон допустимих значень |
|---|---|---|---|
| `0x00` (0) | `magic` | `uint32_t` | Магічне число ідентифікації: `0x42554E44` (ASCII `"BUND"`). Захищає від спроби інтерпретації випадкових стертих байтів `0xFFFFFFFF`. |
| `0x04` (4) | `header_version` | `uint16_t` | Версія формату заголовка (поточна актуальна версія: `0x0001`). |
| `0x06` (6) | `header_size` | `uint16_t` | Повний розмір заголовка в байтах: `128` (`0x0080`). |
| `0x08` (8) | `flags` | `uint32_t` | Бітові прапорці конфігурації: біт 0 = шифрування (AES-CTR), біт 1 = стиснення (LZ4), біт 2 = тестова збірка (Debug/Staging). |
| `0x0C` (12) | `image_type` | `uint16_t` | Тип образу: `0x0001` (Application), `0x0002` (Bootloader), `0x0003` (Recovery OS). |
| `0x0E` (14) | `target_hw_family` | `uint16_t` | Ідентифікатор родини процесора: `0x0001` (STM32F4 Cortex-M4), `0x0002` (ESP32-S3 Xtensa), `0x0003` (RP2350 RISC-V). |
| `0x10` (16) | `target_hw_rev_mask`| `uint32_t` | Бітова маска сумісних ревізій плати. Якщо біт `N` дорівнює `1`, прошивка валідна для ревізії `N`. |
| `0x14` (20) | `version_major` | `uint16_t` | Мажорна версія випуску (SemVer Major). |
| `0x16` (22) | `version_minor` | `uint16_t` | Мінорна версія випуску (SemVer Minor). |
| `0x18` (24) | `version_patch` | `uint16_t` | Патч-версія випуску (SemVer Patch). |
| `0x1A` (26) | `reserved0` | `uint16_t` | Зарезервовано для майбутніх розширень, заповнюється нулями (`0x0000`). |
| `0x1C` (28) | `anti_rollback_ver` | `uint32_t` | Монотонно зростаючий лічильник безпеки. Забороняє встановлення застарілих вразливих прошивок. |
| `0x20` (32) | `image_load_addr` | `uint32_t` | Фізична базова адреса розміщення образу у Flash-пам'яті (наприклад, `0x08010000`). |
| `0x24` (36) | `image_entry_point` | `uint32_t` | Початкова адреса вектору `Reset_Handler` для передачі керування після перевірки. |
| `0x28` (40) | `image_size_bytes` | `uint32_t` | Точний розмір виконуваного бінарного тіла без урахування 128-байтного заголовка. |
| `0x2C` (44) | `header_crc32` | `uint32_t` | Контрольна сума CRC-32 (поліном MPEG-2 `0x04C11DB7`) від полів зі зміщеннями `0x00`–`0x2B`. |
| `0x30` (48) | `image_sha256` | `uint8_t[32]` | Криптографічний дайджест SHA-256 від усього тіла прошивки довжиною `image_size_bytes`. |
| `0x50` (80) | `signature_algo` | `uint8_t` | Ідентифікатор криптографічного алгоритму: `1` = Ed25519, `2` = ECDSA-P256-SHA256, `3` = RSA-PSS-3072. |
| `0x51` (81) | `reserved1` | `uint8_t[15]` | Резервне поле параметрів шифрування (вектор ініціалізації AES-IV / Nonce / Salt). |
| `0x60` (96) | `signature` | `uint8_t[64]` | Асиметричний цифровий підпис заголовка та образу відкритим ключем виробника. |

## 2. Протокол валідації та статуси помилок завантажувача

Коли завантажувач отримує команду на оновлення або запускає пристрій після скидання живлення, він виконує послідовну валідацію за наступним кінцевим автоматом:

1. **Етап ідентифікації:** Зчитування перших чотирьох байтів. Якщо `magic != 0x42554E44`, повертається помилка `FW_ERR_INVALID_MAGIC` і запуск блокується.
2. **Етап цілісності заголовка:** Обчислення CRC-32 від зміщення `0x00` до `0x2B`. Якщо результат не збігається з полем `header_crc32`, повертається `FW_ERR_HEADER_CRC_FAIL`. Це захищає завантажувач від читання пошкоджених параметрів розміру чи адрес.
3. **Етап апаратної сумісності:** Опитування апаратних виводів визначення ревізії плати (англ. *Hardware Board Strapping*). Якщо відповідний біт у `target_hw_rev_mask` дорівнює нулю, повертається `FW_ERR_HW_MISMATCH`.
4. **Етап анти-відкату:** Зчитування поточного значення безпеки з пам'яті OTP (англ. *One-Time Programmable*) мікроконтролера. Якщо `anti_rollback_ver < otp_counter`, завантажувач фіксує спробу атаки та повертає `FW_ERR_ROLLBACK_DETECTED`.
5. **Етап криптографічної перевірки:** Обчислення SHA-256 від усього тіла прошивки. Якщо дайджест не збігається з `image_sha256`, повертається `FW_ERR_IMAGE_SHA_MISMATCH`. Далі перевіряється цифровий підпис у полі `signature`. У разі успіху завантажувач атомарно оновлює OTP-лічильник та здійснює стрибок на `image_entry_point`.

### Стандартизована таблиця кодів повернення завантажувача

| Код (Hex) | Назва статусу (Enum) | Причина виникнення та реакція системи |
|---|---|---|
| `0x00` | `FW_VERIFY_SUCCESS` | Усі перевірки пройдено успішно. Образ валідний, дозволено передачу керування. |
| `0x01` | `FW_ERR_INVALID_MAGIC` | Значення `magic` відмінне від `0x42554E44`. Пам'ять стерта або образ пошкоджено. |
| `0x02` | `FW_ERR_HEADER_CRC_FAIL` | Помилка контрольної суми CRC32 заголовка. Апаратне пошкодження Flash-пам'яті. |
| `0x03` | `FW_ERR_UNSUPPORTED_VERSION`| Невідома версія формату `header_version > 1`. Завантажувач потребує оновлення. |
| `0x04` | `FW_ERR_HW_MISMATCH` | Ревізія плати не підтримується прошивкою (захист від збірки під інше залізо). |
| `0x05` | `FW_ERR_ROLLBACK_DETECTED` | Спроба пониження версії прошивки нижче зафіксованої в eFuse/OTP відмітки. |
| `0x06` | `FW_ERR_SIZE_OVERFLOW` | Розмір `image_size_bytes` виходить за межі виділеного розділу Flash-пам'яті. |
| `0x07` | `FW_ERR_IMAGE_SHA_MISMATCH`| Обчислений геш тіла прошивки не відповідає значенню, записаному в заголовку. |
| `0x08` | `FW_ERR_SIGNATURE_INVALID` | Цифровий підпис Ed25519/ECDSA не підтверджено вбудованим відкритим ключем. |

## 3. Двоетапне оновлення в архітектурах Dual-Bank (A/B)

У надійних промислових та автомобільних системах Flash-пам'ять мікроконтролера розділяється на два рівнозначні слоти — **Slot A (Active)** та **Slot B (Candidate)**. Бінарний маніфест керує автоматом станів пробного запуску (англ. *Trial Boot State Machine*):

1. **Запис у слот кандидата:** Нова прошивка завантажується у пасивний слот B без порушення роботи активної системи в слоті A.
2. **Пробний старт (Trial Mode):** Завантажувач встановлює статус образу в `IMAGE_STATE_TESTING` і передає керування на слот B, попередньо активуючи апаратний сторожовий таймер (Watchdog).
3. **Підтвердження успішності (Self-Test Confirmation):** Нова прошивка виконує самодіагностику периферії, перевіряє зв'язок із сервером і викликає системний виклик підтвердження. Завантажувач змінює прапорець на `IMAGE_STATE_CONFIRMED`.
4. **Автоматичний відкат при збої:** Якщо під час першого запуску виникає HardFault, зависання або сторожовий таймер перезавантажує процесор до підтвердження, завантажувач розпізнає невдалий старт і автоматично перемикає виконання назад на перевірений слот A.

## 4. Специфікація цифрового підпису Ed25519

Для вбудованого середовища цифровий підпис зберігається у вигляді прямого 64-байтного масиву `R || S` (32 байти координати точки `R` та 32 байти скаляра `S`), як визначено у стандарті RFC 8032. 

Використання сирого бінарного формату замість ASN.1 DER (який часто застосовується в сертифікатах X.509) усуває потребу у парсерах динамічної пам'яті всередині завантажувача. Перевірка підпису виконується з фіксованим стековим буфером без використання динамічної купи (Heap), що повністю виключає вразливості фрагментації та витоку пам'яті на етапі ініціалізації пристрою.

## 6. Контракт тривалого збереження та правила незмінності

Для задоволення галузевих вимог довгострокового архівування (автомобільний стандарт ISO 26262, медичний IEC 62304 та промисловий IEC 61508) релізний маніфест підпорядковується чотирьом непорушним правилам життєвого циклу:

1. **Абсолютна незмінність артефактів (англ. *Artifact Immutability*):** Опублікований пакет отримує статус "Write Once, Read Many" (WORM). Жоден файл усередині пакета не може бути відредагований, перезаписаний чи частково оновлений. Якщо у коментарях чи документації виявлено неточність, конвеєр зобов'язаний згенерувати новий номер збірки (Build Number) та випустити незалежний релізний пакет із власними криптографічними підписами.
2. **Герметична відтворюваність середовища:** Поле `builder_image_digest` містить незмінний криптографічний SHA-256 геш образу OCI-контейнера збірки. Це гарантує, що навіть через 10 років інженерна команда зможе розгорнути ідентичне середовище (версію GCC, заголовочні файли Newlib, CMake та скрипти лінкера) та скомпілювати патч байт-у-байт без дрейфу адрес символів.
3. **Наскрізна верифікація контрольних сум (`SHA256SUMS`):** Усі файли пакету фіксуються в кореневому текстовому реєстрі `SHA256SUMS`. Автентичність самого реєстру підтверджується від'єднаним цифровим підписом `SHA256SUMS.sig`, згенерованим на апаратному модулі безпеки (HSM). Будь-яка модифікація байта в будь-якому звіті чи файлі мапи пам'яті призводить до недійсності підпису всього релізу.
