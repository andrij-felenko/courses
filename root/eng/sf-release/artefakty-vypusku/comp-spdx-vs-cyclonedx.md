# 🔌 Порівняння форматів SBOM: SPDX проти CycloneDX

Коли у релізний пакет вбудованого продукту додають машинно-зчитувану специфікацію компонентів (англ. *Software Bill of Materials*, SBOM), інженерні команди постають перед вибором між двома домінантними міжнародними стандартами: **SPDX** (англ. *Software Package Data Exchange*) від Linux Foundation та **CycloneDX** від консорціуму OWASP (англ. *Open Web Application Security Project*). 

Обидва формати призначені для вирішення однієї фундаментальної задачі: перетворити невідомий бінарний моноліт на структурований інвентар усіх використаних бібліотек, версій, авторів, ліцензій та криптографічних гешів. Проте через різну історію походження, архітектурну філософію та цільові сценарії ці два стандарти суттєво відрізняються у внутрішній моделі даних, підтримці вбудованих пристроїв та інтеграції з конвеєрами безпеки.

---

## Походження та філософія проектування

Історичне коріння кожного формату визначає його ключові пріоритети під час аналізу коду:

- **SPDX (ISO/IEC 5962:2021):** проект виник 2010 року під егідою Linux Foundation. Початковою метою була сувора юридична відповідність відкритим ліцензіям (англ. *open-source license compliance*) та захист інтелектуальної власності. Юристам і ліцензійним аудиторам був потрібен стандарт для відстеження авторських прав, ліцензійних умов (GPL, Apache-2.0, MIT, BSD) та включення вихідних фрагментів коду (англ. *snippets*). Згодом у версіях 2.2, 2.3 та 3.0 стандарт розширили для покриття задач кібербезпеки та ланцюга постачання, а 2021 року SPDX отримав статус офіційного міжнародного стандарту ISO.
- **CycloneDX:** проект створений 2017 року спільнотою OWASP спеціально для задач практичної безпеки застосунків (AppSec) та управління ризиками ланцюга постачання програмного забезпечення (англ. *Software Supply Chain Risk Management*). Формат із самого початку проектувався для автоматизованого пошуку вразливостей (CVE), аналізу застарілих компонентів, генерації графів залежностей та обміну статусами експлуатабельності (VEX).

```
SPDX:       [Юридична чистота та ліцензії] ──(еволюція 2010-2024)──> [ISO Стандарт + Безпека]
CycloneDX:  [Кібербезпека, вразливості, VEX] ──(дизайн 2017-2024)──> [AppSec + Апаратний SBOM]
```

## Модель даних та рівні деталізації

Архітектурна побудова стандартів демонструє різний рівень гранулярності опису артефактів:

### 1. Структура документа SPDX
Модель даних SPDX базується на реляційному графі сутностей:
- **SPDX Document:** кореневий контейнер метаданих із зазначенням версії специфікації, ліцензії самого документа (`CC0-1.0`), автора збірки та унікального простору імен (URI).
- **Packages (Пакунки):** логічні одиниці коду (бібліотека `mbedTLS`, ядро `FreeRTOS`, драйвер `HAL`). Пакунок містить назву, версію, походження, декларовану ліцензію, ліцензію з вихідного коду (англ. *concluded license*) та контрольні суми.
- **Files (Файли):** окремі вихідні чи скомпільовані файли (`bme280.c`, `libcrypto.a`), що належать пакунку.
- **Snippets (Фрагменти):** діапазони рядків або байтів усередині файлу (актуально, коли окрему математичну функцію скопійовано з іншого відкритого проекту під специфічною ліцензією).
- **Relationships (Зв'язки):** формальний перелік відношень між елементами за допомогою предикатів (`CONTAINS`, `DEPENDS_ON`, `DESCRIBED_BY`, `GENERATED_FROM`).

### 2. Структура документа CycloneDX
Модель даних CycloneDX оптимізована для швидкої автоматизованої обробки сканерами безпеки:
- **Metadata:** інформація про інструмент генерації, часову мітку, виробника, цільовий продукт та алгоритми гешування.
- **Components:** ієрархічний масив складових частин. Кожен компонент має типізацію (`type`: `application`, `framework`, `library`, `container`, `operating-system`, `device`, `firmware`, `file`).
- **Dependencies:** спрямований граф (BOM-Link), де чітко зафіксовано прямі та транзитивні залежності між компонентами.
- **Vulnerabilities & VEX:** вбудовані секції для фіксації виявлених дефектів та декларацій експлуатабельності.
- **Formulation / Services / Compositions:** описи середовища розгортання, мережевих ендпоінтів та ступеня повноти самого BOM-документа.

## Специфіка вбудованих систем та апаратного забезпечення

У світі вбудованих мікроконтролерів більшість коду не встановлюється через стандартні пакетні менеджери на кшталт `npm`, `pip` чи `cargo`. Бібліотеки додаються як Git-сабмодулі, статичні файли в папках `Third_Party/` або прекомпільовані пропрієтарні архіви `.a`.

| Критерій порівняння | SPDX (v2.3 / v3.0) | OWASP CycloneDX (v1.5 / v1.6) |
|---|---|---|
| **Міжнародний статус** | Офіційний стандарт ISO/IEC 5962:2021 | Відкритий стандарт під егідою OWASP Foundation |
| **Формати серіалізації** | JSON, YAML, RDF, Tag-Value (текстовий) | JSON, XML, Protocol Buffers (Protobuf) |
| **Ідентифікатори пакетів** | Package URL (pURL), CPE 2.2/2.3, SWID | Package URL (pURL), CPE 2.2/2.3, SWID, OmniBOR |
| **Опис апаратного забезпечення** | Підтримка профілю Hardware у версії 3.0 | Вбудовані типи компонентів `device`, `firmware` |
| **Облік ліцензій** | Детальний аналіз на рівні файлів і фрагментів | Спрощений перелік ліцензій за ідентифікаторами SPDX |
| **Декларації безпеки (VEX)** | Окремий профіль безпеки у версії 3.0 | Нативна вбудована інтеграція у структурі документа |
| **Формулювання збірки** | Профіль Build у версії 3.0 | Розділ `formulation` для фіксації інструментів і параметрів |

Вбудовані пристрої мають унікальну перевагу у CycloneDX завдяки типу компонента `firmware` та `device`. У маніфесті можна одночасно описати мікросхему мікроконтролера STM32F407 (компонент типу `device` із зазначенням ревізії кристала та серійного номера), прошивку операційної системи реального часу (тип `operating-system`), мережевий стек `lwIP` (тип `library`) та кінцевий виконуваний бінарник (тип `application`).

## Ідентифікація пакетів: pURL проти CPE

Щоб автоматичний сканер вразливостей міг перевірити базу даних CVE (англ. *Common Vulnerabilities and Exposures*), компоненти в SBOM повинні мати універсальні ідентифікатори. Обидва стандарти підтримують дві ключові схеми:

### 1. Package URL (pURL)
Стандартизований URI для однозначної адресації програмних компонентів у будь-якій екосистемі:
```
pkg:generic/mbedtls@3.4.0?checksum=sha256:7f3b1a98c520...&download_url=https://github.com/Mbed-TLS/mbedtls
```
Для вбудованого коду без пакетного менеджера схема `pkg:generic` дозволяє зафіксувати назву, точну версію, URL-адресу репозиторію та геш вихідного архіву.

### 2. Common Platform Enumeration (CPE)
Словник Національної бази вразливостей США (NVD/NIST):
```
cpe:2.3:a:arm:mbed_tls:3.4.0:*:*:*:*:*:*:*
```
CPE необхідний для зіставлення з класичними звітами безпеки NIST, проте страждає від неоднозначності назв постачальників (наприклад, назва компанії може писатися як `arm`, `arm_ltd` або `mbed`).

## Обмін статусами вразливостей: механізм VEX

Критичною проблемою класичного аудиту SBOM є «шум вразливостей» (англ. *false positives*). Сканер безпеки, виявивши у прошивці бібліотеку `mbedTLS 3.4.0`, видає попередження про наявність критичної CVE в алгоритмі RSA-CRT. Проте вбудований пристрій використовує виключно криптографію на еліптичних кривих Ed25519, а всі функції RSA були повністю видалені лінкером на етапі оптимізації за допомогою прапорця `-Wl,--gc-sections`.

Спроба заблокувати реліз через таку «вразливість» паралізує команду. Для вирішення цієї проблеми створено механізм **VEX (англ. *Vulnerability Exploitability eXchange*)**.

VEX дозволяє розробникам прошивки додати до релізного SBOM формальні машиночитані вердикти щодо кожної відомої CVE:
- `not_affected` — код вразливості відсутній або фізично недосяжний у системі;
- `justification`: `code_not_reachable` (код не викликається), `code_not_present` (видалено лінкером), `inline_mitigations_already_exist` (захищено зовнішнім брандмауером чи фільтром);
- `affected` — вразливість підтверджена, ведеться робота над патчем;
- `fixed` — виправлено у поточному випуску;
- `under_investigation` — аналіз триває.

CycloneDX підтримує VEX нативно прямо у структурі документа, що дозволяє сканерам безпеки на стороні замовника автоматично ігнорувати недосяжні вразливості без ручного листування з технічною підтримкою.

## Практичні критерії вибору для інженерної команди

Вибір між SPDX та CycloneDX диктується вимогами замовників та структурою конвеєра збірки:

1. **Обирайте SPDX, якщо:**
   - Головною вимогою контракту або регулятора є відповідність міжнародному стандарту ISO/IEC 5962:2021;
   - Проект містить суворі вимоги до ліцензійної чистоти коду, аудиту авторських прав та перевірки наявності GPL-коду;
   - Замовник вимагає документ у текстовому форматі Tag-Value або RDF для інтеграції з існуючими корпоративними базами даних ліцензій.

2. **Обирайте CycloneDX, якщо:**
   - Основний фокус зосереджено на DevSecOps, автоматичному скануванні CVE, моніторингу застарілих компонентів та управлінні ланцюгом постачання;
   - Необхідно нативно публікувати звіти VEX про недосяжність знайдених вразливостей для зниження кількості хибних тривог;
   - Випускається складний вбудований комплекс, де потрібно в одному маніфесті описати апаратну платформу, прошивку мікроконтролера та хмарні мікросервіси.
