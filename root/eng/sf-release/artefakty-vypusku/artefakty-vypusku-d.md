Коли промисловий контролер автоматизації або бортовий комп'ютер автомобіля раптово зависає на об'єкті через три роки після випуску, журнал аварійного скидання фіксує лише кілька чисел із процесорних регістрів: лічильник команд `PC = 0x08004f2c`, регістр зв'язку `LR = 0x08002a11` та вказівник стека `SP = 0x20001fe0`. Якщо команда розробників вважала «релізом» лише сирий бінарний файл `firmware.bin`, надісланий на завод під час виробництва, інженери підтримки опиняються у глухому куті. За адресою `0x08004f2c` у знеособленій Flash-пам'яті лежать шістнадцяткові байти машинних інструкцій, за якими неможливо впізнати назву функції C, ім'я файлу чи номер рядка коду.

Спроба скомпілювати той самий вихідний код із репозиторію сьогодні дає інший результат: оновлена мінорна версія компілятора GCC або зміна системних заголовків на робочій станції розробника інакше оптимізує цикли, вбудовує інлайн-функції та зміщує адреси у скомпільованому бінарнику. Адреса збою `0x08004f2c` тепер вказує на зовсім іншу підпрограму або середину рядкового літерала. Помилка стає невідтворюваною, гарантійне розслідування заходить у глухий кут, а компанія ризикує відкликанням усієї партії пристроїв.

Ця криза виникає через фундаментальну хибу мислення: ототожнення виконуваного бінарного файлу з повноцінним релізним випуском. Виконуваний бінарник — це лише мінімальне фізичне тіло програми, оптимізоване для виконання кремнієвим процесором. Справжній релізний випуск (англ. *Release Bundle*) — це герметичний, криптографічно підписаний та самодостатній інженерний комплекс артефактів, який зберігає повний контекст створення продукту, його математичну мапу пам'яті, символи налагодження, склад сторонніх компонентів та юридично завірені протоколи випробувань.

Історію того, як індустрія пройшла шлях від запису шістнадцяткових дампів на ультрафіолетові мікросхеми EPROM до сучасних захищених релізних контейнерів, детально розглянуто в нарисі: [Еволюція релізного пакета: від бінарної дискети до захищеного ланцюга постачання](root:sf-release/artefakty-vypusku/hist-release-bundle-evolution.md).

## Сім складових частин виробничого випуску

Повноцінний релізний пакет вбудованого продукту або системного сервісу об'єднує сім обов'язкових артефактів, кожен із яких відповідає за ізольовану функцію життєвого циклу:

1. **Виробничий бінарний образ (`.bin`, `.hex`, `.dfu`, `.fit`):** компактний образ машинних інструкцій без налагоджувальних метаданих, призначений для запису у Flash-пам'ять мікроконтролера на конвеєрі заводу або доставки клієнту через механізм OTA.
2. **Налагоджувальний образ ELF із DWARF-символами (`.elf`, `.debug`):** повний вихід лінкера, що містить секції символьних таблиць, структури типів, зміщення локальних змінних та відповідність адрес пам'яті рядкам вихідного коду.
3. **Файл мапи пам'яті лінкера (`.map`):** текстовий звіт лінкера, що документує точне фізичне розташування кожної функції, глобального буфера, секцій `.text`, `.rodata`, `.data`, `.bss`, а також граф перехресних посилань між об'єктними модулями.
4. **Криптографічно підписаний маніфест прошивки (`manifest.json` / `manifest.sig`):** декларативний бінарний або JSON-заголовок, що містить версію SemVer, бітову маску сумісних апаратних ревізій плати, монотонний лічильник захисту від відкату (Anti-rollback) та цифровий підпис Ed25519/ECDSA.
5. **Специфікація складу компонентів (SBOM):** структурований машиночитаний документ у стандарті SPDX або CycloneDX, що фіксує перелік усіх включених відкритих і комерційних бібліотек, операційних систем реального часу, драйверів, їхніх точних версій і ліцензій.
6. **Звіти валідації та кваліфікації:** протоколи автоматизованого прогону модульних тестів (JUnit XML), звіти відповідності стандартам безпечного коду (MISRA C/C++ у форматі SARIF), виміри тестового покриття та логи апаратного тестування (HIL).
7. **Реєстр контрольних сум (`SHA256SUMS` + підпис):** текстовий перелік криптографічних гешів усіх файлів пакета, підписаний закритим ключем релізного центру безпеки для гарантії неподільності та незмінності архіву.

## Налагоджувальний ELF та DWARF: збереження контексту виконання

Коли компілятор транслює вихідний код C або C++ у машинний код, він генерує об'єктні файли формату **ELF (англ. *Executable and Linkable Format*)**. За наявності прапорців налагодження `-g3 -gdwarf-4` або `-gdwarf-5` компілятор включає в об'єктні файли стандартизовані секції метаданих **DWARF (англ. *Debugging With Attributed Record Formats*)**:

- `.debug_info`: ієрархічне дерево дескрипторів інформації про налагодження (англ. *Debugging Information Entries*, DIE). Кожен вузол містить числовий тег (наприклад, `DW_TAG_subprogram` для функцій, `DW_TAG_variable` для змінних, `DW_TAG_structure_type` для структур) та набір атрибутів (`DW_AT_name`, `DW_AT_decl_file`, `DW_AT_decl_line`, `DW_AT_low_pc`, `DW_AT_high_pc`, `DW_AT_type`).
- `.debug_abbrev`: таблиця скорочень, яка визначає схему кодування атрибутів для кожного тегу DIE у секції `.debug_info`. Вона використовує компактне кодування чисел змінної довжини LEB128 (англ. *Little-Endian Base 128*), що дозволяє істотно зменшити обсяг метаданих.
- `.debug_line`: матриця відповідності між віртуальними адресами інструкцій процесора та номерами рядків і назвами файлів вихідного коду. У стандарті DWARF-5 ця таблиця містить оптимізовані директорії та хеші файлів для прискорення парсингу у налагоджувачах.
- `.debug_frame`: таблиця розгортання стека (англ. *Call Frame Information*, CFI). Вона містить структури CIE (англ. *Common Information Entry*) та FDE (англ. *Frame Description Entry*), що описують канонічну адресу стекового фрейму (англ. *Canonical Frame Address*, CFA) та правила відновлення регістрів процесора для кожної точки виконання.
- `.debug_loc` та `.debug_loclists`: таблиці динамічного розташування змінних. Коли компілятор оптимізує код із рівнем `-O2` або `-O3`, локальна змінна може частину часу жити в регістрі `R4`, потім переміститися у стек `[SP, #12]`, а згодом бути повністю видаленою. Секція описує точні діапазони адрес інструкцій, де змінна має конкретне фізичне розташування.
- `.debug_ranges` та `.debug_rnglists`: списки діапазонів адрес функцій, код яких було розбито оптимізатором на неперервні та відокремлені блоки (англ. *hot/cold splitting*).
- `.symtab` та `.strtab`: класичні таблиці імен глобальних і локальних символів разом з їхніми рядковими назвами.

*Відокремлення символів DWARF: формування компактного бінарника для Flash та збереження повного ELF для аналізу аварійних дампів*

### Анатомія розбору аварійного дампу пам'яті (Crash Dump Triage)

Коли у мікроконтролері з ядром ARM Cortex-M виникає фатальна помилка пам'яті (HardFault або MemManage Fault), апаратний блок обробки переривань автоматично зберігає у поточний стек базовий стековий кадр із восьми 32-бітних регістрів:

```text
[SP + 0x00]: R0   (Перший аргумент функції або результат)
[SP + 0x04]: R1   (Другий аргумент)
[SP + 0x08]: R2   (Третій аргумент)
[SP + 0x0C]: R3   (Четвертий аргумент)
[SP + 0x10]: R12  (Тимчасовий внутрішньопроцедурний регістр IP)
[SP + 0x14]: LR   (Регістр повернення Link Register)
[SP + 0x18]: PC   (Адреса інструкції, на якій стався збій)
[SP + 0x1C]: xPSR (Регістр стану програми)
```

Обробник помилки копіює цей зріз разом із наступними 64 словами стека у захищену енергонезалежну область пам'яті (`.noinit`). Під час наступного старту пристрій передає дамп на сервер діагностики.

Маючи збережений релізний файл DWARF-символів, інструмент діагностики виконує розгортання стека:
1. За адресою `PC` у таблиці `.debug_line` визначається точний вихідний файл і рядок коду, де відбулося звернення за недійсною адресою;
2. За таблицею `.debug_frame` обчислюється розмір фрейму поточної функції та знаходиться адреса збереженого регістра `LR`, що вказує на точку виклику в батьківській функції;
3. Крок повторюється рекурсивно, відновлюючи повне дерево викликів аж до точки входу в завдання RTOS.

Секції DWARF займають у 5–15 разів більше місця, ніж самі виконувані інструкції. Наприклад, прошивка з 180 кілобайтами машинного коду формує ELF-файл розміром 4.5 мегабайти. Завантажувати такий масив у Flash-пам'ять мікроконтролера фізично неможливо і безглуздо, оскільки апаратне ядро процесора Cortex-M або RISC-V ніколи не звертається до секцій `.debug_*`.

Тому на етапі релізної збірки виконується операція контрольованого розділення артефактів за допомогою утиліт крос-компілятора:

```bash
# 1. Створення ізольованого архіву символів DWARF
arm-none-eabi-objcopy --only-keep-debug firmware.elf firmware.debug

# 2. Очищення основного ELF-файлу від налагоджувальної інформації
arm-none-eabi-strip --strip-debug --strip-unneeded firmware.elf

# 3. Зв'язування очищеного бінарника з файлом символів через секцію .gnu_debuglink
arm-none-eabi-objcopy --add-gnu-debuglink=firmware.debug firmware.elf

# 4. Формування чистого лінійного бінарного образу для запису у Flash
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
```

Очищений бінарник `firmware.bin` містить виключно сегменти завантаження: `.isr_vector` (таблиця переривань), `.text` (машинний код), `.rodata` (рядкові літерали та константи) та `.data` (початкові значення змінних). Він має мінімальний розмір і прошивається у пристрій.

Файл `firmware.debug` (або оригінальний нестрипнутий `firmware.elf`) маркується унікальним ідентифікатором збірки **Build ID** — 160-бітним SHA-1 або 256-бітним SHA-256 гешем, який компілятор вбудовує в секцію `.note.gnu.build-id` за допомогою прапорця `-Wl,--build-id=sha1`. 

Коли пристрій у полі генерує дамп падіння, він виводить свій Build ID та адресу регістра `PC = 0x08004f2c`. Інженер завантажує відповідний `firmware.debug` з релізного сховища й однією командою отримує повний стек викликів:

```bash
arm-none-eabi-addr2line -e firmware.debug -f -C 0x08004f2c
# Вивід:
# bme280_read_pressure_raw
# /build/drivers/sensors/bme280.c:142
```

Без збереженого файлу DWARF-символів точне відновлення вихідного контексту аварії через три або п'ять років після релізу стає математично неможливим завданням.

## Мапа пам'яті лінкера (.map): анатомія простору Flash і RAM

Файл мапи пам'яті лінкера (Linker Memory Map) генерується під час компонування за допомогою прапорців `-Wl,-Map=firmware.map,--cref`. Цей текстовий документ фіксує математичну модель розміщення всіх компонентів програми у фізичних адресних просторах мікроконтролера.

![Анатомія файлу мапи пам'яті](/root/eng/sf-release/artefakty-vypusku/img/memory-map-analysis-flow.svg)
*Анатомія мапи лінкера: фізичний розподіл Flash і RAM, таблиця перехресних посилань і зазор між стеком та купою*

Файл мапи містить п'ять критичних пластів діагностичної інформації:

### 1. Звіт конфігурації регіонів пам'яті (Memory Configuration)
Показує фізичні межі апаратної пам'яті, визначені у скрипті лінкера (`.ld`), та поточний рівень їхньої утилізації:
```text
Memory Configuration

Name             Origin             Length             Attributes
FLASH            0x08000000         0x00080000         xr
RAM              0x20000000         0x00020000         xrw
*default*        0x00000000         0xffffffff

Linker script and memory map
Address of section .text set to 0x08000000
```

### 2. Розподіл секцій та адреси VMA проти LMA
Лінкер відображає два типи адрес для кожної секції програми:
- **VMA (Virtual Memory Address / Execution Address):** адреса, за якою код або дані розташовуються під час виконання програми.
- **LMA (Load Memory Address):** адреса, за якою дані зберігаються у постійній Flash-пам'яті до старту програми.

Секція `.data` (ініціалізовані глобальні та статичні змінні) має VMA в оперативній пам'яті (`0x20000000`), але LMA у Flash-пам'яті (`0x0802d400`). Під час запуску процесора процедура `Reset_Handler` зчитує початкові значення з Flash за адресою LMA та копіює їх у RAM за адресою VMA. 

Мапа пам'яті показує точний розмір цієї секції, дозволяючи проконтролювати, щоб витрати Flash на копіювання даних не перевищили бюджет:
```text
.data           0x20000000     0x00003000 load address 0x0802d400
 Core/Src/main.o (.data)
                0x20000000       0x00000020 g_system_config
 Middlewares/FreeRTOS/tasks.o (.data)
                0x20000020       0x00000400 pxCurrentTCB
```

Секція `.bss` (неініціалізовані або нульові статичні змінні) не займає місця у Flash-пам'яті взагалі — під час старту стартап-код процесора просто заповнює цей діапазон адрес нулями у RAM.

### 3. Секція збереження стану між перезавантаженнями (`.noinit`)
У надійних системах частина оперативної пам'яті виділяється під спеціальну секцію `.noinit`. На відміну від `.bss`, ця секція виключається з процедури обнулення при старті процесора. У ній розміщують діагностичні журнали аварійних перезапусків, стек викликів попереднього збою або калібрувальні коефіцієнти датчиків. Мапа пам'яті дозволяє перевірити, що секція `.noinit` розміщена за фіксованою адресою та не перекривається зі звичайними змінними.

### 4. Аналіз фрагментації та прихованого роздування (Padding Bytes)
Через вимоги апаратного вирівнювання (наприклад, 4-байтне або 8-байтне вирівнювання для 64-бітних чисел з рухомою комою чи буферів DMA) лінкер змушений вставляти порожні байти-заповнювачі між змінними та функціями. 

Файл мапи документує всі проміжки вирівнювання рядками виду `*fill* 0x20000021 0x3`:
```text
.bss.buffer1    0x20000000       0x00000021 Core/Src/sensor.o
 *fill*         0x20000021       0x00000003
.bss.buffer2    0x20000024       0x00000040 Core/Src/telemetry.o
```
Якщо інженери не контролюють порядок полів у структурах (без прапорця компілятора `-Wpadded`), невирівняні змінні можуть марно витрачати десятки кілобайтів дорогоцінної оперативної пам'яті.

### 5. Очищення мертвого коду (`--gc-sections`) та таблиця перехресних посилань
За замовчуванням лінкер компонує весь об'єктний файл цілком, навіть якщо з нього викликається лише одна маленька допоміжна функція. Щоб усунути невикористовуваний код, компілятор запускають із прапорцями `-ffunction-sections -fdata-sections`, а лінкер — із прапорцем `-Wl,--gc-sections`. 

Мапа пам'яті документує кожну відкинуту функцію у спеціальному розділі `Discarded input sections`:
```text
Discarded input sections
 .text.unused_display_driver
                0x00000000      0x00000320 Drivers/display.o
 .text.legacy_crc16_calc
                0x00000000      0x00000084 Core/Src/utils.o
```

Таблиця перехресних посилань (`Cross Reference Table`) слугує зворотним інструментом: вона показує повний граф викликів для кожного збереженого символу. Якщо важка функція обробки графіки потрапила у фінальний бінарник, таблиця дозволяє миттєво знайти випадковий виклик, який змусив лінкер підтягнути її з бібліотеки.

### 6. Оцінка ризику колізії стека й купи (Stack-Heap Collision)
В оперативній пам'яті мікроконтролера секція неініціалізованих змінних `.bss` закінчується міткою `_end`. Від цієї мітки починається динамічна купа (Heap), яка росте вгору до старших адрес під час викликів `malloc()` або створення завдань RTOS. З іншого боку, вершина пам'яті `_estack` (наприклад, `0x20020000`) є початком головного стека (MSP), який у процесі виконання функцій та обробки переривань зростає вниз до молодших адрес.

Мапа пам'яті дозволяє обчислити статичний зазор безпеки:

```
Зазор безпеки = _estack - Розмір стека - _end
```

Якщо цей зазор становить менше 10–15% від загального обсягу RAM, релізний конвеєр повинен блокувати випуск, оскільки будь-яке пікове вкладення переривань або виділення пам'яті призведе до перекриття стека й купи (англ. *Stack-Heap Collision*) та непередбачуваного руйнування пам'яті.

У промисловому конвеєрі CI/CD порівняння мапи пам'яті попереднього випуску `v1.0.0.map` з новою збіркою `v1.0.1.map` (механізм Diff Map) автоматично виявляє приховані регресії: випадкове збільшення буфера черги на 4 КБ або додавання важкої бібліотеки форматування рядків.

## Підписаний маніфест прошивки: безпечне завантаження та OTA

Сучасні пристрої не можуть дозволити собі сліпо записувати бінарний потік у Flash-пам'ять. Для захисту від пошкодження коду під час передачі та запобігання атакам зловмисників виробничий образ постачається з криптографічним маніфестом.

Детальну специфікацію полів бінарного заголовка, структуру регістрів завантажувача та схему JSON-маніфесту викладено у довіднику інтерфейсу: [Специфікація бінарного маніфесту прошивки та схеми JSON-пакета релізу](root:sf-release/artefakty-vypusku/api-release-manifest-spec.md).

Маніфест вирішує три критичні задачі захисту:

### 1. Апаратна автентифікація та захист від оновлення чужим образом
Якщо компанія випускає дві моделі приладу — базову на платі Rev.A та розширену на платі Rev.B з іншим трансивером — спроба прошити образ Rev.B у плату Rev.A викличе збій периферії або електричне коротке замикання на виводах GPIO. Маніфест містить 32-бітну бітову маску сумісних ревізій заліза `target_hw_rev_mask`. Завантажувач перевіряє апаратні підтяжки на платі й миттєво відхиляє чужий образ.

### 2. Захист від атак зниження версії (Anti-Rollback Protection)
Якщо у версії v1.2.0 було виявлено вразливість переповнення буфера, виправлену у v1.3.0, зловмисник може перехопити канал зв'язку й примусово надіслати на пристрій старий, але валідний підписаний бінарник v1.2.0, щоб експлуатувати стару дірку. Маніфест фіксує монотонний лічильник `anti_rollback_version`. Після перевірки завантажувач записує це значення в апаратні eFuse або захищену OTP-пам'ять (англ. *One-Time Programmable*) кристала. Будь-яка спроба встановити прошивку з меншим лічильником апаратно блокується.

### 3. Автомат пробного запуску в архітектурах Dual-Bank (A/B)
Для захисту від «оцеглинення» пристрою Flash-пам'ять поділяється на два розділи — Slot A (активний) та Slot B (кандидат). Завантажувач розгортає нову версію у пасивний слот і вмикає сторожовий таймер (Watchdog). Нова прошивка зобов'язана після старту провести самодіагностику та підтвердити працездатність записом статусу `IMAGE_CONFIRMED` у службовий сектор. 

Якщо протягом 30 секунд підтвердження не відбулося або процесор впав у HardFault, сторожовий таймер перезавантажує мікроконтролер, а завантажувач автоматично повертає виконання на старий перевірений слот.

Практичну реалізацію утиліти пакування релізних файлів та алгоритму верифікації прошивки наведено в практичному проекті: [Генератор підписаного релізного маніфесту та перевірка цілісності артефактів](root:sf-release/artefakty-vypusku/proj-release-bundle-generator.md).

## Специфікація компонентів (SBOM): прозорість ланцюга постачання

Сучасне програмне забезпечення вбудованих систем на 80–90% складається зі сторонніх бібліотек, відкритих фреймворків та драйверів виробників чипів. Коли виявляється глобальна вразливість нульового дня (наприклад, у криптографічній бібліотеці або стеку TCP/IP), служба безпеки повинна за лічені секунди визначити, які саме пристрої в експлуатації містять вразливий компонент.

Для цього кожен релізний пакет зобов'язаний містити **SBOM (англ. *Software Bill of Materials*)** — стандартизований машинно-зчитуваний інвентар компонентів.

Глибоке порівняння двох домінантних міжнародних стандартів SBOM наведено у порівняльній вставці: [Порівняння форматів SBOM: SPDX проти CycloneDX](root:sf-release/artefakty-vypusku/comp-spdx-vs-cyclonedx.md).

```
Релізний бінарник ──(генерація в CI)──> SBOM (CycloneDX / SPDX JSON)
                                              │
                                              ├── Ідентифікатори pURL / CPE
                                              ├── Ліцензії компонентів
                                              └── Граф залежностей + VEX
```

SBOM обов'язково включає:
- **Універсальні ідентифікатори (pURL та CPE):** однозначні рядки ідентифікації бібліотеки в глобальних реєстрах (наприклад, `pkg:generic/mbedtls@3.4.0` або `cpe:2.3:a:arm:mbed_tls:3.4.0:*:*:*:*:*:*:*`);
- **Криптографічні геші вихідних компонентів:** підтвердження автентичності використаного сирцевого коду;
- **Декларації експлуатабельності VEX (англ. *Vulnerability Exploitability eXchange*):** формальні машиночитані пояснення, чому певні відомі CVE не впливають на цей пристрій (наприклад, якщо вразливий модуль бібліотеки було видалено лінкером через прапорець `--gc-sections` як невикористовуваний).

Автоматизовані сканери на стороні клієнта чи регулятора аналізують файл SBOM проти Національної бази вразливостей (NVD/NIST) і бази GitHub Advisory без необхідності проводити дорогий і тривалий реверс-інжиніринг самого бінарного файлу.

## Звіти валідації та реєстр цілісності

Випуск продукту не вважається завершеним без збереження доказів його коректності та проходження випробувань на момент збірки. У регульованих галузях (медицина за стандартом IEC 62304, автомобільний транспорт за ISO 26262, промислова автоматика за IEC 61508) відсутність протоколу тестування прирівнюється до дефекту самого коду.

До релізного пакета додаються такі звіти:
1. **Звіти модульних та інтеграційних тестів (JUnit XML / TAP):** фіксують точну кількість успішно пройдених тестів, час виконання та відсоток покриття рядків коду (Line Coverage / Branch Coverage).
2. **Звіти статичного аналізу коду (SARIF — Static Analysis Results Interchange Format):** документують перевірку правил безпечного програмування (MISRA C:2012, CERT C) та фіксують відсутність критичних дефектів переповнення буферів чи неініціалізованих змінних.
3. **Логи апаратного тестування (HIL — Hardware-in-the-Loop):** протоколи запусків на реальних стендах з емуляцією сигналів датчиків, шин CAN/UART та осцилографічними знімками перехідних процесів.

Усі ці файли разом із бінарними образами реєструються у фінальному файлі `SHA256SUMS`:

```text
7f3b1a98c520188ef7b819f074d28442034fa969a531cfd93ef86d9a973a8f11  firmware.bin
c94d2e85a0678d46114b7454848d5333f2eb305c48ab03b719be40aa8838380e  firmware.debug
5a8d9f4a21096738b556f8f5341be9b16541f534887349141cb02787ec347c61  firmware.map
1a84f09a32c253509fd71b78912ef6c5186cf954a5c5f470559f2a77884d9435  sbom.cdx.json
3d4f56a938b8d4e78291f09c6239841893c52a0a2f4460b815f2a8934501a34d  tests-report.xml
```

Файл `SHA256SUMS` завіряється від'єднаним цифровим підписом `SHA256SUMS.sig` приватним ключем реліз-інженера за допомогою інструментів OpenPGP, Cosign або Minisign. Це перетворює набір розрізнених файлів на монолітний, юридично значимий доказовий пакет.

## Стратегія довгострокового архівування (10+ років) та герметичні збірки

Термін експлуатації промислового верстата, вітрогенератора, медичного томографа або автомобіля становить від 10 до 25 років. Протягом усього цього часу виробник зобов'язаний надавати патчі безпеки, аналізувати аварійні ситуації та відповідати на регуляторні аудити.

![Конвеєр довгострокового архівування](/root/eng/sf-release/artefakty-vypusku/img/long-term-archival-pipeline.svg)
*Конвеєр довгострокового архівування: герметичне середовище збірки, незмінне сховище та фоновий скрабінг цілісності*

Зберегти вихідний код у Git недостатньо. Через сім років оригінальний компілятор `gcc-arm-none-eabi-10.3` не скомпілюється на новій версії Linux через несумісність з оновленою системною бібліотекою `glibc`.

Тому стратегія довгострокового архівування (англ. *Long-Term Archival*, LTA) базується на трьох взаємопов'язаних інженерних принципах:

### 1. Герметичне середовище збірки (Hermetic Build Environment)
Увесь ланцюг компіляції фіксується у вигляді OCI/Docker-контейнера. У релізний маніфест записується незмінний криптографічний дайджест образу компілятора (`sha256:...`). 

Для забезпечення повної бінарної відтворюваності (англ. *Reproducible Builds*) компілятору передаються спеціальні прапорці усунення дрейфу шляхів файлової системи:
```bash
# Фіксація часової мітки у бінарнику
export SOURCE_DATE_EPOCH=1787887800

# Перетворення абсолютних шляхів збірки у відносні для DWARF
arm-none-eabi-gcc -ffile-prefix-map=/home/runner/work/firmware=. -g3 -O2 ...
```
Цей образ контейнера консервується разом із релізним пакетом, гарантуючи, що через 10 років збірка з того самого коміту дасть результат байт-у-байт.

### 2. Сховища WORM (Write Once, Read Many)
Архів релізу поміщається у хмарне сховище з активованим режимом Object Lock (наприклад, AWS S3 Glacier Compliance Mode) або записується на фізичні магнітні стрічки LTO (англ. *Linear Tape-Open*). Режим WORM на рівні сховища забороняє будь-кому — включаючи системних адміністраторів та облікові записи власника компанії — видаляти чи змінювати файли до закінчення 10-річного терміну зберігання.

### 3. Захист від тихого пошкодження носіїв (Bit-rot Prevention)
З часом магнітні домени на стрічках або жорстких дисках деградують через космічні промені та термічні флуктуації, що призводить до непомітної зміни окремих бітів («гниття бітів», англ. *Bit-rot*). 

Автоматичний конвеєр архіву раз на шість місяців проводить фоновий скрабінг (англ. *Data Scrubbing*): зчитує всі архіви, обчислює контрольні суми та звіряє їх із підписаним маніфестом `SHA256SUMS`. У разі виявлення розбіжності пошкоджений файл автоматично відновлюється з географічно розподіленої резервної копії.

## Управління криптографічними ключами та корінь довіри (Root of Trust)

Довгострокова життєздатність релізного пакета критично залежить від безпеки ключів підпису. Компрометація закритого ключа, яким підписувалися релізні маніфести, дозволяє зловмисникам створити підроблене оновлення з шкідливим кодом.

Безпечна архітектура релізного підпису будується на чотирьох рівнях:

1. **Апаратний модуль безпеки (HSM / KMS):** Закритий ключ для формування підписів випуску (`Ed25519` або `ECDSA P-256`) ніколи не експортується у вигляді файлу на жорсткий диск сервера збірки. Він генерується та постійно зберігається всередині апаратного модуля безпеки (HSM за стандартом FIPS 140-2 Level 3). Сервер CI/CD передає в HSM лише готовий 32-байтний SHA-256 геш релізу та отримує готовий 64-байтний підпис.
2. **Розділення ключів розробки та виробництва:** Збірки для внутрішнього тестування (Staging/Dev) підписуються тимчасовими ключами з нульовою довірою у виробничих завантажувачах. Лише фінальний реліз, який пройшов усі автоматизовані ворота перевірок, направляється на процедуру виробничого підпису (Production Release Signing).
3. **Апаратний корінь довіри (Hardware Root of Trust, RoT):** Відкритий ключ перевірки підпису або його незворотний SHA-256 геш прошивається у захищені апаратні регістри eFuse чи масковану ROM-пам'ять процесора на заводі під час первинного програмування. Завантажувач використовує цей геш для перевірки сертифіката релізного ключа перед валідацією самого маніфесту.
4. **Процедура ротації та відкликання ключів (Key Revocation):** Для захисту від компрометації маніфест підтримує ієрархію ключів. Якщо поточний релізний ключ скомпрометовано, оновлення підписується спеціальним резервним кореневим ключем (Root Recovery Key), який активує спалювання відповідного біта в eFuse мікроконтролера, назавжди забороняючи використання скомпрометованого ключа.

## Інженерний контрольний список формування випуску

Перед тим як перевести релізний пакет у статус фінального та опублікувати його у виробниче сховище, конвеєр зобов'язаний автоматично перевірити виконання наступного чекліста:

- [x] **Виробничий бінарник:** очищений від налагоджувальних символів, упакований у формат `.bin`/`.hex`, розмір суворо вкладається у виділений сектор Flash.
- [x] **Налагоджувальний ELF:** містить повні DWARF-секції, зареєстрований із криптографічним Build ID, збігається з бінарником за контрольною сумою секції `.gnu_debuglink`.
- [x] **Мапа лінкера:** містить повну таблицю символів та крос-референсів, зазор між стеком і купою перевищує мінімальний поріг безпеки.
- [x] **Маніфест прошивки:** містить валідну маску сумісності ревізій плати, монотонний лічильник анти-відкату та підписаний приватним ключем релізу.
- [x] **SBOM:** згенерований у форматі SPDX або CycloneDX, містить повний перелік компонентів із pURL, ліцензіями та VEX-деклараціями.
- [x] **Звіти валідації:** усі модульні тести пройшли на 100%, звіти SARIF не містять блокуючих дефектів MISRA C, протоколи HIL-тестів зафіксовані.
