- [Copy-on-Write](root:sf-os/copy-on-write) — механізм копіювання сторінок і файлів лише в момент модифікації для економії ресурсів.
- [Криптографічні хеш-функції](root:sf-security/cryptographic-hash) — незворотні алгоритми контролю цілісності та формування унікальних дайджестів даних.
- [CI/CD](root:sf-release/ci-cd) — автоматизований конвеєр збірки, тестування та фіксації артефактів.
- [Оркестрація](root:sf-release/container-orchestration) — керування життєвим циклом розподілених контейнерних застосунків у кластері.
</preknowlist>

Коли на кластері із сорока серверів потрібно розгорнути нову версію сервісу авторизації, системний конвеєр повинен доставити виконуваний бінарний файл, бібліотеки зв'язування `glibc` або `musl`, конфігураційні шаблони та набір сертифікатів безпеки на кожен вузол. Якщо запакувати цей стек у традиційний образ віртуальної машини розміром три гігабайти, паралельне оновлення сорока машин спричинить передачу 120 гігабайтів надлишкових даних через мережеві комутатори датацентру. Час холодного розгортання перевищить двадцять хвилин, а дискові масиви хостів вичерпають доступну місткість через багаторазове дублювання однакових системних файлів операційної системи. Ба більше, при аварійному перезапуску вузла мережева затримка викачування важкого дискового моноліту не дозволить вкластися у цільовий час відновлення працездатності сервісу.

Ця проблема виникає тому, що традиційні віртуальні диски сприймають операційну систему як єдиний неподільний бінарний блок. На противагу цьому контейнерна віртуалізація розглядає середовище виконання як ієрархію незалежних зрізів файлової системи — **шарів (англ. *layers*)**, упакованих у стандартні архіви **тарболи (англ. *tarball*, від *tape archive* — стрічковий архів файлів)** та об'єднаних детермінованим графом криптографічних метаданих.

Для уніфікації форматів пакування та мережевої передачі таких артефактів консорціум Open Container Initiative затвердив дві базові специфікації: **OCI Image Format Specification** (структура файлів та метаданих образу) та **OCI Distribution Specification** (мережевий протокол взаємодії з реєстрами).

Історію розвитку форматів контейнерних образів від перших монолітних схем Docker v1 до сучасних відкритих стандартів OCI викладено в історичному нарисі: [Від хаосу тарболів Docker v1 до відкритих стандартів OCI](root:sf-release/container-image-and-registry/hist-oci-and-docker-image-spec.md).

## Анатомія та ієрархія сутностей OCI Image Format

Контейнерний образ за стандартом OCI не є монолітним архівом. Це суворо типізоване дерево JSON-документів та бінарних блобів, де кожна сутність виконує ізольовану функцію.

Ієрархія складається з чотирьох послідовних структурних компонентів:

### 1. Мультиархітектурний індекс (OCI Image Index)
Сучасні хмарні застосунки одночасно розгортаються на серверах з архітектурою `x86_64` (AMD/Intel), енергоефективних процесорах `aarch64` (ARM Graviton/Apple Silicon) або системах `riscv64`. Щоб користувачу не доводилося вручну вказувати специфічні назви на кшталт `myorg/app:v1.0.0-arm64v8`, протокол надає шар абстракції — **Image Index (Fat Manifest)**.

Image Index — це JSON-документ із типом медіа-вмісту `application/vnd.oci.image.index.v1+json`. Він містить масив дескрипторів `manifests`, кожен із яких вказує на конкретний маніфест образу та визначає цільову платформу (операційну систему, архітектуру процесора та апаратні розширення):

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.index.v1+json",
  "manifests": [
    {
      "mediaType": "application/vnd.oci.image.manifest.v1+json",
      "size": 7122,
      "digest": "sha256:7f3b1a98c520188ef7b819f074d28442034fa969a531cfd93ef86d9a973a8f11",
      "platform": {
        "architecture": "amd64",
        "os": "linux"
      }
    },
    {
      "mediaType": "application/vnd.oci.image.manifest.v1+json",
      "size": 7118,
      "digest": "sha256:c94d2e85a0678d46114b7454848d5333f2eb305c48ab03b719be40aa8838380e",
      "platform": {
        "architecture": "arm64",
        "os": "linux",
        "variant": "v8"
      }
    }
  ]
}
```

Коли клієнт виконує операцію `pull`, він аналізує системні виклики `uname(2)` поточного хоста і обирає з масиву `manifests` саме той дескриптор, який відповідає архітектурі поточного ядра Linux. Якщо збігу не знайдено, клієнт повертає помилку `no matching manifest for linux/arm64 in the manifest list entries`.

### 2. Маніфест образу (OCI Image Manifest)
**Маніфест (лат. *manifestus* — явний, очевидний, публічний опис вантажу на торговому судні)** — це кореневий декларативний документ конкретного бінарного образу для фіксованої платформи (`application/vnd.oci.image.manifest.v1+json`).

Маніфест зв'язує докупи дві фундаментальні сутності:
1. **Дескриптор конфігурації (`config`):** посилання на JSON-документ із параметрами запуску.
2. **Впорядкований список дескрипторів шарів (`layers`):** масив бінарних архівів файлової системи, де кожен наступний шар накладається поверх попередніх.

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "size": 3450,
    "digest": "sha256:5a8d9f4a21096738b556f8f5341be9b16541f534887349141cb02787ec347c61"
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "size": 29845120,
      "digest": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    },
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "size": 14210048,
      "digest": "sha256:1a84f09a32c253509fd71b78912ef6c5186cf954a5c5f470559f2a77884d9435"
    },
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "size": 2150490,
      "digest": "sha256:3d4f56a938b8d4e78291f09c6239841893c52a0a2f4460b815f2a8934501a34d"
    }
  ]
}
```

Порядок у масиві `layers` є суворо детермінованим: індекс 0 є базовим шаром (Base OS rootfs), а кожен наступний індекс накладається вище за попередній.

### 3. Конфігурація образу (Image Config JSON)
На відміну від маніфесту, який є транспортним конвертом для мережевої доставки, `Image Config JSON` описує стан середовища процесу всередині контейнера. Він транслюється системним рантаймом (`runc`, `crun`) у низькорівневу специфікацію `config.json` стандарту OCI Runtime Spec:

- `architecture` та `os` — цільова апаратна архітектура та операційна система (наприклад, `amd64`, `linux`).
- `config.Env` — масив змінних оточення у форматі `KEY=VALUE` (наприклад, `PATH=/usr/local/sbin:...`, `PORT=8080`).
- `config.Entrypoint` та `config.Cmd` — масиви аргументів для виконання системного виклику `execve(2)`. Розділення на `Entrypoint` та `Cmd` дозволяє визначити незмінний виконуваний бінарник за замовчуванням (`Entrypoint: ["/app/server"]`) та параметри, які користувач може перевизначити при запуску (`Cmd: ["--port", "8080"]`).
- `config.WorkingDir` — робочий каталог контейнера перед стартом процесу.
- `config.User` — числовий UID/GID або ім'я користувача, від імені якого запускається ізольований процес (запобігання небезпечному виконанню з правами `root:0`).
- `config.StopSignal` — сигнал завершення роботи (наприклад, `SIGTERM` або `SIGQUIT`), який надсилається процесу при зупинці контейнера.
- `rootfs.diff_ids` — критично важливий масив нестиснутих SHA-256 хешів кожного шару файлової системи.

### 4. Бінарні блоби шарів (Layer Tarball Blobs)
Кожен шар у масиві `layers` є архівом `tar`, упакованим алгоритмом Gzip (`.tar+gzip`) або Zstandard (`.tar+zstd`). Шар містить виключно **дельту (різницю)** файлів відносно попереднього стану: нові файли, змінені файли та спеціальні маркери видалення.

## Адресація за вмістом (Content-Addressable Storage) та дедуплікація

Фундаментальним інженерним принципом збереження та передачі контейнерних образів є **адресація за вмістом (Content-Addressable Storage — CAS)**.

У звичайних файлових системах доступ до файлу здійснюється за його людським іменем або шляхом (наприклад, `/etc/nginx/nginx.conf`). Якщо вміст файлу змінюється, його шлях залишається старим. В архітектурі CAS об'єкт не має власного імені: його адресою та ідентифікатором є **криптографічний дайджест (лат. *digestus* від *digerere* — систематизувати, розщеплювати, незмінний результат хешування)**, обчислений безпосередньо від масиву його байтів:

```
Дайджест = "sha256:" + Hex_Кодування(SHA256(Потік_Байтів_Об'єкта))
```

В OCI-реєстрі та в локальному сховищі хоста (`/var/lib/containerd/io.containerd.content.v1.content/blobs/sha256/`) абсолютно все зберігається у вигляді блобів під своїми SHA-256 хешами: маніфести, конфігурації та шари файлової системи.

![Адресація за вмістом та дедуплікація](/root/eng/sf-release/container-image-and-registry/img/content-addressable-storage.svg)
*Адресація за вмістом (CAS) та дедуплікація шарів: спільні базові шари зберігаються на диску хоста в єдиному екземплярі*

### Стиснутий Digest проти розпакованого DiffID
В архітектурі OCI існує суворе розмежування між двома типами хешів шару:
1. **`layer.digest` (Транспортний хеш у маніфесті):** це SHA-256 хеш від стиснутого бінарного архіву `.tar.gz`, як він лежить у сховищі реєстру та передається мережею. Він використовується для перевірки цілісності завантаження.
2. **`diff_id` (Внутрішній хеш у Config JSON):** це SHA-256 хеш від розпакованого вихідного tarball-потоку байтів.

Чому одного хешу недостатньо? Різні версії утиліти `gzip` або різні рівні компресії (наприклад, `gzip -6` проти `gzip -9`) продукують зовсім різні за байтами стиснуті архіви з абсолютно ідентичного набору вихідних файлів. Якби образ спирався лише на стиснутий хеш, зміна компресора ламала б ідентичність файлової системи. Наявність `diff_ids` гарантує, що після розпакування на вузлі ядро отримає саме ту файлову систему, яку створив збирач, незалежно від алгоритму компресії.

### Змінні теги проти незмінних дайджестів: пастка безпеки
Звернення до образу в реєстрі може відбуватися двома способами:
1. **За тегом (Tag Reference):** `registry.example.com/payment/api:v1.2.0` або `api:latest`.
2. **За дайджестом маніфесту (Digest Pinning):** `registry.example.com/payment/api@sha256:7f3b1a98c520188ef7b819f074d28442034fa969a531cfd93ef86d9a973a8f11`.

Тег — це лише змінний покажчик (мутабельне посилання), аналог гілки в системі Git. Власник реєстру або зловмисник із правами запису може в будь-який момент надіслати новий маніфест і перезаписати покажчик `:v1.2.0` або `:latest` на інший код. Якщо у конфігурації продакшен-кластера вказано тег, два різні сервери при виконанні операції pull у різний час отримають кардинально різний бінарний вміст.

Дайджест маніфесту є абсолютно незмінним (імутабельним). Якщо в коді застосунку змінюється хоча б один біт, SHA-256 хеш маніфесту незворотно зміниться. Використання закріплення за дайджестом (Digest Pinning) є єдиним способом гарантувати стовідсотковий детермінізм та безпеку ланцюжка постачання ПЗ.

### Математика дедуплікації на хості
Якщо на одному сервері запускається `N` мікросервісів, кожен із яких базується на однаковому базовому шарі ОС розміром `S[base]`, але має власний унікальний шар коду розміром `S[app_i]`, сумарне дискове споживання за традиційної монолітної моделі становить:

```
V[monolith] = ∑(S[base] + S[app_i])  для i = 1..N
            = N · S[base] + ∑ S[app_i]
```

Завдяки моделі CAS рантайм контейнерів завантажує та зберігає базовий шар `S[base]` рівно один раз. Реальне дискове споживання становить:

```
V[CAS] = S[base] + ∑ S[app_i]        [дедуплікація: спільний шар у пулі CAS]
```

Економія пам'яті та мережевого трафіку виражається формулою:

```
ΔV = V[monolith] - V[CAS]
   = (N - 1) · S[base]               [чистий виграш за рахунок дедуплікації]
```

Для сорока контейнерів на базі Ubuntu (`S[base] ≈ 30 MB`) економія дискового простору та мережевого трафіку становить `39 · 30 MB = 1170 MB` лише на базовому шарі.

## Протокол OCI Distribution (HTTP REST API v2): звідки береться pull

Процес отримання образу з віддаленого **реєстру (лат. *registrum* від *regerere* — вносити записи, офіційний журнал обліку)** виконується за строго стандартизованим мережевим протоколом OCI Distribution Spec.

Повний довідник ендпоінтів, заголовків та кодів помилок наведено в окремій специфікації: [Специфікація протоколу OCI Distribution Spec](root:sf-release/container-image-and-registry/api-oci-distribution-spec.md).

![Хронологія та протокол OCI Distribution Spec Pull](/root/eng/sf-release/container-image-and-registry/img/distribution-pull-protocol.svg)
*Хронологія та протокол OCI Distribution Specification (Pull Workflow): виклики REST API v2, авторизація та завантаження блобів*

Процедура операції `pull` складається з восьми послідовних фаз:

### Фаза 1: Парсинг локатора образу
Клієнт розбирає рядок образу на складові:
```
docker.io/library/ubuntu:22.04
├── Хост реєстру: registry-1.docker.io (за замовчуванням для Docker Hub)
├── Простір імен і репозиторій: library/ubuntu
└── Референс (тег або дайджест): 22.04
```

### Фаза 2: Автентифікаційний виклик (Bearer Token Auth Challenge)
Клієнт робить початковий неавторизований HTTP-запит до кореневого ендпоінту реєстру:
```http
GET /v2/ HTTP/1.1
Host: registry-1.docker.io
```
Реєстр повертає статус `401 Unauthorized` зі спеціальним заголовком виклику:
```http
HTTP/1.1 401 Unauthorized
Www-Authenticate: Bearer realm="https://auth.docker.io/token",service="registry.docker.io",scope="repository:library/ubuntu:pull"
```
Клієнт вилучає URL сервера автентифікації (`realm`), передає туди свої облікові дані (або запитує анонімний доступ) і отримує короткоживучий JWT токен:
```http
GET /token?service=registry.docker.io&scope=repository:library/ubuntu:pull HTTP/1.1
Host: auth.docker.io
```
Відповідь: `{"token": "eyJhbGciOiJSUzI1NiIs..."}`.

### Фаза 3: Отримання маніфесту (Manifest Fetching)
Клієнт повторює запит на отримання маніфесту, додаючи отриманий Bearer-токен та вказуючи підтримувані формати медіа-вмісту в заголовку `Accept`:
```http
GET /v2/library/ubuntu/manifests/22.04 HTTP/1.1
Host: registry-1.docker.io
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
Accept: application/vnd.oci.image.manifest.v1+json, application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.v2+json
```
Реєстр повертає JSON маніфесту та критичний заголовок `Docker-Content-Digest: sha256:...`. Клієнт самостійно обчислює SHA-256 від отриманого тіла маніфесту і перевіряє, що воно збігається із заголовком. Якщо виявлено невідповідність хоча б в один байт, процес негайно анулюється.

### Фаза 4: Локальна перевірка блобів (Local CAS Cache Lookup)
Отримавши маніфест, клієнт вилучає дескриптор конфігурації `config.digest` та список дескрипторів `layers[].digest`. Клієнт звертається до свого локального сховища CAS на диску: якщо блоб із таким хешем уже завантажений (наприклад, для іншого образу), повторне викачування блокується.

### Фаза 5: Перевірка метаданих відсутніх блобів (HEAD Check)
Для кожного відсутнього блобу клієнт може надіслати легковаговий запит `HEAD /v2/<name>/blobs/<digest>`, щоб перевірити доступність об'єкта та отримати його точний розмір у байтах (`Content-Length`) для побудови індикатора прогресу.

### Фаза 6: Паралельне завантаження блобів та перенаправлення (Blob Streaming)
Клієнт ініціює паралельні потоки завантаження відсутніх шарів:
```http
GET /v2/library/ubuntu/blobs/sha256:e3b0c44298fc1c... HTTP/1.1
Host: registry-1.docker.io
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
```
Більшість сучасних публічних та корпоративних реєстрів (Docker Hub, AWS ECR, GCP Artifact Registry) не роздають гігабайтні бінарні архіви безпосередньо з серверів API. Натомість реєстр повертає статус перенаправлення `307 Temporary Redirect`:
```http
HTTP/1.1 307 Temporary Redirect
Location: https://s3.us-east-1.amazonaws.com/docker-registry-blobs/sha256_e3b0c44...?AWSAccessKeyId=...
```
Клієнт автоматично переходить за адресою S3-сховища або CDN та завантажує бінарний потік на максимальній швидкості мережевого каналу.

### Фаза 7: Потокова перевірка криптографічного дайджесту (Streaming Verification)
Під час зчитування потоку байтів із мережевого сокета клієнт безперервно передає кожен блок у криптографічний контекст OpenSSL (`SHA256_Update`). Коли з'єднання закривається, клієнт фіналізує хеш (`SHA256_Final`) і порівнює його з дайджестом із маніфесту.

> 🔧 **Навіщо це:** Потокова перевірка захищає від атак класу Man-in-the-Middle (MitM) та пошкоджень файлів при обривах мережі. Якщо проксі-сервер підмінив хоча б один біт у завантаженому архіві або завантаження обірвалося на 99%, пошкоджений блоб ніколи не потрапить у системний каталог хоста.

### Фаза 8: Розпакування та реєстрація в системному сховищі (Snapshotter)
Перевірений стиснутий архів передається підсистемі керування знімками (**Snapshotter** у containerd). Snapshotter розпаковує tarball у виділений каталог шару, фіксує його розпакований `diff_id` і реєструє шар у графі залежностей.

## Монтаж шарів у ядрі Linux: механізм OverlayFS

Коли всі шари завантажені та розпаковані на диску, постає задача: як перетворити стопку ізольованих каталогів із файлами у єдине цілісне дерево кореневої файлової системи (`/`), яке побачить процес всередині контейнера після виконання системних викликів `pivot_root(2)` або `chroot(2)`?

Для цього ядро Linux надає спеціалізовану файлову систему каскадного об'єднання — **OverlayFS (англ. *overlay*, від давньоангл. *oferlecgan* — накладати один шар поверх іншого)**.

![Монтаж та композиція шарів через OverlayFS](/root/eng/sf-release/container-image-and-registry/img/overlayfs-layer-mounting.svg)
*Монтаж шарів у ядрі Linux через OverlayFS: об'єднання незмінних нижніх шарів, каталог запису upperdir та результуюча rootfs*

### Структура каталогів OverlayFS
OverlayFS об'єднує декілька фізичних каталогів в одну віртуальну точку монтування за допомогою чотирьох ключових сутностей:
1. **`lowerdir` (Незмінний стек шарів образу):** список каталогів, розділених двокрапкою (`:`), змонтованих у режимі виключно для читання (Read-Only). Порядок переліку має вирішальне значення: крайній лівий каталог має найвищий пріоритет. Якщо файл із однаковим шляхом існує і в шарі 3, і в шарі 1, процес побачить версію із шару 3.
2. **`upperdir` (Контейнерний шар читання-запису):** єдиний ізольований каталог, відкритий для запису (Read-Write). Усі операції створення, редагування чи видалення файлів, які виконує процес контейнера, фізично відбуваються виключно в `upperdir`. Самі шари образу в `lowerdir` залишаються абсолютно незайманими.
3. **`workdir` (Службовий каталог ядра):** технічний каталог на тій самій файловій системі, що й `upperdir`. Він необхідний ядру Linux для підготовки тимчасових файлів перед їх атомарним переміщенням у `upperdir` під час операцій копіювання та видалення.
4. **`merged` (Точка монтування):** віртуальний каталог, що є результатом накладання. Саме цей каталог передається як кореневий для процесу контейнера.

Команда монтування в терміналі виглядає так:
```bash
mount -t overlay overlay -o lowerdir=/layers/L3:/layers/L2:/layers/L1:/layers/L0,upperdir=/containers/c1/upper,workdir=/containers/c1/work /containers/c1/merged
```

### Механізм копіювання при записі (Copy-Up)
Коли процес у контейнері відкриває файл, можливі два сценарії:
- **Читання (`O_RDONLY`):** Ядро послідовно шукає файл: спочатку в `upperdir`, потім у шарах `lowerdir` зліва направо. Знайдений файл відкривається на читання напряму з незмінного шару образу з нульовими накладними витратами.
- **Модифікація (`O_WRONLY` або `O_RDWR`):** Якщо файл існує лише в нижньому шарі `lowerdir`, ядро перехоплює системний виклик `open(2)`, атомарно копіює весь файл із `lowerdir` у `upperdir` (операція **Copy-Up**), і лише після цього надає процесу дескриптор файлу в `upperdir`.

> ⚠️ **Дефект великих файлів:** Якщо контейнер намагається додати один байт у кінець лог-файлу розміром 10 ГБ, який лежить у базовому шарі образу, ядро буде змушене скопіювати всі 10 ГБ у `upperdir` перед першим записом. Це створює раптову дискову затримку (latency spike) та може вичерпати вільне місце на хості. Бази даних та великі файли даних завжди мають монтуватися через зовнішні томи (Volumes), а не зберігатися в шарах образу.

### Видалення файлів та каталогів: Whiteouts та Opaque
Оскільки нижні шари `lowerdir` змонтовані в режимі Read-Only, ядро фізично не може видалити файл із нижнього каталогу на диску. Для емуляції видалення OverlayFS використовує два механізми:
1. **Whiteout файлу:** Якщо процес видаляє файл `/bin/old_tool` (виклик `unlink(2)`), OverlayFS створює в каталозі `upperdir` спеціальний символьний пристрій (character device) із нульовими номерами пристрою `0:0` (`mknod(path, S_IFCHR, makedev(0, 0))`). Коли VFS ядра бачить такий пристрій під час сканування каталогу, вона приховує однойменний файл із нижчих шарів.
2. **Непрозорий каталог (Opaque directory):** Якщо процес повністю видаляє каталог, а потім створює новий порожній каталог із такою ж назвою, OverlayFS позначає новий каталог в `upperdir` розширеним атрибутом `trusted.overlay.opaque="y"`. Це вказує ядру повністю ігнорувати вміст однойменного каталогу в усіх нижчих шарах `lowerdir`.

У тарболах OCI Image Format ці маркери серіалізуються у вигляді спеціальних файлів із префіксом `.wh.`:
- Видалений файл: `.wh.old_tool`.
- Непрозорий каталог: маркерний файл `.wh..wh..opq` всередині каталогу.

## Новітні підходи: ліниве завантаження (Lazy Pulling)

Традиційний процес `pull` вимагає повного завантаження та розпакування всіх гігабайтів шарів до того, як контейнер зможе виконати першу інструкцію процесу. Проте емпіричні дослідження Google та CERN показують, що контейнери під час свого життєвого циклу зчитують лише 6–15% файлів, запакованих у їхні образи (решта — неактивні утиліти, заголовні файли та документація).

Для усунення цієї затримки було розроблено технології **лінивого завантаження (Lazy Pulling)**:
- **eStargz (Extended Stargz):** Спеціальний формат gzip-архіву, в кінець якого додається зміст (TOC — Table of Contents) із точними зміщеннями (byte offsets) кожного окремого файлу. Клієнт завантажує лише 50 КБ змісту, монтує віртуальну файлову систему FUSE і миттєво стартує контейнер. Файли викачуються з реєстру фоново через HTTP Range-запити лише в момент реального звернення процесу (`on-demand file retrieval`).
- **Nydus / Dragonfly:** Окремий блоковий формат образу, оптимізований для розподілених P2P-мереж та швидкого зчитування файлових блоків без накладних витрат на декомпресію tarball-структур.

## Системна реалізація клієнта та монтажу rootfs

Повний код робочого клієнта OCI, обробки whiteout-файлів та автоматизованого монтажу OverlayFS rootfs мовами C та C++ наведено у практичній вставці: [Реалізація клієнта OCI реєстру та монтажу rootfs](root:sf-release/container-image-and-registry/proj-oci-registry-client.md).

Нижче наведено системний фрагмент коду, який демонструє формування параметрів монтування ядра Linux на мовах C та C++:

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mount.h>
#include <errno.h>

/* Формування рядка опцій та системний виклик mount(2) для OverlayFS */
int mount_container_rootfs(const char *lower_layers, const char *upper, 
                           const char *work, const char *target) {
    char options[2048];
    snprintf(options, sizeof(options), "lowerdir=%s,upperdir=%s,workdir=%s",
             lower_layers, upper, work);

    /* Системний виклик ядра mount */
    if (mount("overlay", target, "overlay", 0, options) != 0) {
        fprintf(stderr, "Помилка монтування rootfs (%s): %s\n", target, strerror(errno));
        return -1;
    }

    printf("Rootfs успішно змонтовано у %s\n", target);
    return 0;
}
```
```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <sys/mount.h>
#include <cerrno>
#include <cstring>
#include <stdexcept>
#include <filesystem>

namespace fs = std::filesystem;

class ContainerRootfsManager {
public:
    static void mount_rootfs(std::string_view lower_layers,
                             const fs::path& upper_dir,
                             const fs::path& work_dir,
                             const fs::path& target_merged) {
        std::string options = "lowerdir=" + std::string(lower_layers) +
                              ",upperdir=" + upper_dir.string() +
                              ",workdir=" + work_dir.string();

        fs::create_directories(target_merged);

        if (::mount("overlay", target_merged.c_str(), "overlay", 0, options.c_str()) != 0) {
            throw std::runtime_error("Системна помилка mount OverlayFS: " + 
                                     std::string(std::strerror(errno)));
        }

        std::cout << "[OK] OverlayFS rootfs змонтовано у " << target_merged << "\n";
    }
};
```

## Підсумковий синтез

Контейнерний образ OCI — це не віртуальний диск і не монолітний архів. Це математично детермінований граф криптографічно адресованих блобів (Content-Addressable Storage), побудований на чотирьох наріжних каменях:
1. **Ієрархія OCI:** мультиархітектурний `Image Index` посилається на `Image Manifest`, який пов'язує параметри середовища `Config JSON` із впорядкованим масивом стиснутих шарів файлової системи `Layers`.
2. **Адресація за вмістом (CAS):** дедуплікація блобів на рівні сховища хоста та реєстру, де незмінний криптографічний дайджест SHA-256 гарантує цілісність даних та захист від підміни коду.
3. **Протокол Distribution Spec:** клієнт завантажує маніфест за дайджестом, дедуплікує блоби проти локального сховища та паралельно викачує відсутні шари через оптимізовані CDN-редиректи з безперервною перевіркою контрольних сум SHA-256.
4. **Монтаж OverlayFS:** ядро Linux об'єднує стопку незмінних каталогів `lowerdir` з ізольованим шаром запису `upperdir`, формуючи єдине робоче дерево rootfs за допомогою семантики Copy-Up та спецпристроїв Whiteout.

Ця архітектура дозволяє сучасним хмарним платформам передавати мережею лише дельти коду, економити терабайти дискового простору та запускати ізольовані процеси за мілісекунди на будь-якому сервері світу.
