# 📜 Від хаосу тарболів Docker v1 до відкритих стандартів OCI

Коли у березні 2013 року Соломон Хайкс презентував Docker на конференції PyCon у Санта-Кларі, революція контейнеризації полягала не у винайденні нових примітивів ядра Linux — системні виклики `clone(2)`, простори імен `namespaces` та контрольні групи `cgroups` вже успішно використовувалися в LXC, Google lmctfy та системі cgroups ядра з 2007 року. Справжнім проривом стала стандартизація пакування та розповсюдження: перетворення статичного набору файлів кореневої файлової системи (rootfs) на єдиний артефакт, який можна зібрати на комп'ютері розробника і за секунди запустити на будь-якому сервері без ручного налаштування залежностей.

Проте перша версія формату образів Docker (Manifest Schema 1) створювалася поспіхом і несла в собі важкі архітектурні вади. Образ складався з ланцюжка шарів, де кожен шар містив власний JSON-файл конфігурації із посиланням на батьківський шар (`parent_id`). Ця деревоподібна схема призводила до того, що зміна одного байта в метаданих автора ламала всі ідентифікатори дочірніх шарів, унеможливлюючи ефективне кешування. Ба більше, у Schema 1 для розрахунку контрольних сум використовувався алгоритм `tarsum` — спроба рахувати хеш файлів всередині tarball без урахування порядку запису та заголовків tar. `tarsum` вимагав повного розпакування кожного архіву під час розрахунку контрольної суми, створював колосальне навантаження на диск і процесор, але все одно страждав від несумісності через різні версії утиліти `tar` та часові мітки (mtime).

Найкритичнішою проблемою Schema 1 була криптографічна небезпека: підпис маніфесту вбудовувався безпосередньо в тіло JSON через механізм JWS (JSON Web Signatures). Якщо реєстр або проміжний проксі-сервер змінював форматування пробілів чи порядок ключів у JSON-документі, цифровий підпис маніфесту ставав недійсним, хоча самі бінарні дані шарів залишалися незмінними.

До 2014 року Docker Inc. одноосібно контролювала як клієнтську утиліту `docker`, так і специфікацію реєстру та демона dockerd. Компанія почала агресивно перетворювати відкритий інструмент на комерційну платформу, інтегруючи систему оркестрації Docker Swarm безпосередньо в монолітний системний демон. Це викликало занепокоєння спільноти та інших гравців ринку.

У грудні 2014 року компанія CoreOS на чолі з Алексом Полві публічно виступила з критикою монополізації контейнерного стека і представила альтернативну систему запуску контейнерів `rkt` (Rocket) разом із відкритою специфікацією **AppC (Application Container Specification)**. AppC спиралася на прості принципи: образ — це архів `.aci`, який має чітко відокремлені метадані, перевіряється стандартними підписами PGP і може завантажуватися за звичайним протоколом HTTPS без обов'язкового пропрієтарного демона.

Індустрія опинилася під загрозою розколу на два несумісні табори: екосистему Docker та екосистему AppC. Інженерам довелося б створювати окремі образи для різних середовищ виконання. У цій ситуації великі хмарні провайдери та корпорації (Google, Red Hat, IBM, Microsoft, Cisco) виступили посередниками, змусивши лідерів ринку сісти за стіл переговорів.

У червні 2015 року на конференції DockerCon було оголошено про створення консорціуму **Open Container Initiative (OCI)** під егідою некомерційного фонду Linux Foundation. 

Умови компромісу були взаємними:
1. Docker Inc. передала у власність OCI свій низькорівневий рушій `libcontainer`, виділений у незалежний проект `runc`, який ліг в основу стандарту **OCI Runtime Specification**.
2. Було створено робочу групу з розробки **OCI Image Format Specification** на базі доопрацьованого формату Docker Image Manifest Schema 2. Специфікація AppC була оголошена завершеною, а її найкращі ідеї (зокрема, чітке розділення маніфесту та конфігурації) інтегровані в OCI.
3. Протокол передачі образів було стандартизовано в рамках **OCI Distribution Specification**, що гарантувало можливість підключення будь-якого клієнта (Podman, containerd, CRI-O, Skopeo) до будь-якого сумісного реєстру (Docker Hub, GitHub Packages, AWS ECR, Google Artifact Registry, Harbor).

У липні 2017 року консорціум OCI офіційно затвердив версію 1.0 специфікацій Image Format та Runtime. У 2021 році статус 1.0 отримала й Distribution Specification.

Перехід до стандартів OCI остаточно закріпив парадигму адресації за вмістом (Content-Addressable Storage — CAS):
- Було ліквідовано залежність від алгоритму `tarsum`: кожен блоб тепер ідентифікується прямим криптографічним хешем `sha256:` від стиснутого потоку байтів, як він передається мережею.
- З'явився мультиархітектурний `Image Index` (fat manifest), що дозволило одним і тим самим тегом посилатися на образи для архітектур `amd64`, `arm64`, `riscv64`, `s390x` та `windows/amd64`.
- Метадані виконання було остаточно відокремлено від шарів файлової системи в окремий документ `Image Config JSON`, а контрольні суми розпакованих шарів зафіксовано у масиві `rootfs.diff_ids`.

Сучасний розвиток OCI (версії 1.1+) вийшов далеко за межі традиційних контейнерів Linux. Завдяки стандартизованим MIME-типам та універсальній схемі дескрипторів блобів, OCI-реєстри перетворилися на універсальні сховища артефактів (Artifact Registries). Сьогодні через протокол OCI поширюються бінарні модулі WebAssembly (Wasm), Helm-чарти Kubernetes, моделі штучного інтелекту, криптографічні підписи Cosign та електронні паспорти компонентів програмного забезпечення (SBOM — Software Bill of Materials), використовуючи спільні механізми автентифікації, кешування та дедуплікації.
