# 📜 Еволюція стабілізації коду: від монолітних блокад до релізних поїздів

Стабілізація кодової бази перед передачею програми замовнику виникла в момент, коли вартість виправлення дефекту після відвантаження фізичного носія перевищила бюджет усієї розробки. У 1960-х роках під час створення операційної системи OS/360 для комп'ютерів IBM System/360 інженери вперше зіткнулися з явищем системної ентропії: що більше програмістів одночасно вносило зміни для виправлення виявлених помилок, то більше нових збоїв з'являлося в сусідніх модулях. Фред Брукс (Frederick Brooks) у книзі «The Mythical Man-Month» (1975) задокументував цей ефект як закон спадної віддачі, коли спроба виправити дефект на пізніх етапах без жорсткої ізоляції змін збільшує невизначеність системи в геометричній прогресії.

## Монолітні заморозки в аерокосмічних системах

У пілотованій космічній програмі NASA Apollo розробка бортового комп'ютера AGC (Apollo Guidance Computer) під керівництвом Маргарет Гамільтон (Margaret Hamilton) в MIT Instrumentation Laboratory вимагала абсолютної надійності. Програмний код прошивався у постійний запам'ятовувальний пристрій на магнітних осердях (core rope memory) буквально вручну: мідні дроти протягувалися крізь феритові кільця фабричними робітницями (так званий метод LOL, «Little Old Ladies»). Процес виготовлення матриць пам'яті тривав місяцями, тому вартість програмної помилки після початку плетіння дорівнювала зриву графіка польотів і мільйонам доларів збитків.

Для захисту від випадкових мутацій коду команда MIT запровадила процедуру жорсткої фіксації специфікацій:
1. За шість місяців до запланованого запуску вводився повний мораторій на будь-які структурні зміни алгоритмів.
2. Кожна зміна в кодовому рядку вимагала схвалення Ради з контролю змін (Change Control Board, CCB).
3. Після затвердження фінального варіанта програми генерувався машинний лістинг, який перевірявся незалежними групами інженерів через симуляцію польотних траєкторій на аналогових та цифрових стендах.
4. Фінальний дамп пам'яті отримував статус "Golden" і відправлявся на виробництво матриць.

Ця модель довела свою ефективність під час місії «Аполлон-11» у липні 1969 року, коли комп'ютер AGC перевантажився через помилкові сигнали радарного інтерфейсу, але завдяки стабілізованій структурі пріоритетів завдань успішно скинув другорядні процеси й завершив посадку модуля на Місяць.

## Каскадні релізи 1980–1990-х та криза нескінченної стабілізації

З переходом комерційної індустрії на розповсюдження комерційного програмного забезпечення на дискетах і компакт-дисках (CD-ROM) практика монолітної заморозки стала стандартом для таких гігантів, як Microsoft, Oracle та Sun Microsystems. Процес випуску операційних систем Windows 95 та Windows NT базувався на багатомісячних фазах:
- **Feature Freeze (FF)**: припинення додавання функцій;
- **Zero Bug Bounce (ZBB)**: момент, коли кількість відкритих критичних багів вперше досягає нуля (після чого зазвичай відкривається нова хвиля вторинних дефектів);
- **Release Candidate (RC)**: формування тиражного кандидата для зовнішнього бета-тестування;
- **Release to Manufacturing (RTM)**: запис золотого диска для тиражування на заводах штампування дисків.

Проте за каскадної моделі (Waterfall) стадія заморозки часто перетворювалася на кризу: команди розробників поспішали «заштовхати» сирі функції в останню ніч перед Feature Freeze, що спричиняло лавину дефектів. Фаза стабілізації розтягувалася на місяці, а інколи й на роки. Під час розробки Windows Vista (проєкт Longhorn) у 2004 році накопичена нестабільність архітектурних компонентів досягла критичної маси, через що керівництву довелося здійснити так званий "Development Reset" — повністю зупинити розробку, викинути нестійкі напрацювання й почати збірку на базі перевіреного коду Windows Server 2003.

## Поява моделі релізних поїздів (Release Trains)

На початку 2000-х років розвиток систем контролю версій (BitKeeper, а згодом Git) та методологій безперервної інтеграції докорінно змінив інженерні підходи. Спільноти відкритого коду та комерційні розробники усвідомили: прив'язка релізу до плаваючого списку функцій руйнує детермінізм випуску.

У ядрі Linux під керівництвом Лінуса Торвальдса (Linus Torvalds) у 2005 році було формалізовано концепцію двохтижневого вікна злиття (**Merge Window**), за яким слідувала послідовна серія кандидатів `rc1`–`rc8`:
- Після випуску фінального ядра відкривається 14-денне вікно для прийому нових підсистем у гілку `linux-next`.
- Після закриття вікна формується `vX.Y-rc1` і настає повний Code Freeze: у дерево ядра приймаються виключно патчі, що виправляють регресії попередніх версій або закривають дірки безпеки.
- Реліз виходить за розкладом (кожні 9–10 тижнів), незалежно від того, чи встигли розробники конкретної підсистеми завершити свій драйвер.

```
Merge Window (14 днів) ──> rc1 ──> rc2 ──> rc3 ──> ... ──> rc7/rc8 ──> Фінальний реліз vX.Y
      [Нові фічі]          [Тільки виправлення критичних регресій]       [Стабільне ядро]
```

Цей принцип отримав назву «релізного поїзда» (Release Train): поїзд відправляється суворо за графіком. Якщо функція не готова до моменту закриття станційних дверей (Feature Freeze), вона не затримує весь поїзд, а залишається чекати наступного рейсу.

У 2010-х роках інженерні команди Google (Chrome), Mozilla (Firefox) та Apple інтегрували релізні поїзди у виробництво прошивок та мобільних клієнтів. Команда Google Chromium перейшла на жорсткий 6-тижневий (а згодом 4-тижневий) цикл випуску: кожна гілка відсікається від `main` за календарем, проходить автоматизоване тестування на фермах пристроїв і переходить через канали Canary → Dev → Beta → Stable.

## Заморозка у світі вбудованих систем (Embedded Hardware)

Для виробників автомобільної електроніки (стандарти ISO 26262, AUTOSAR), медичних приладів (IEC 62304) та промислової автоматики еволюція релізних процесів призвела до суворого поєднання гнучких реліз-трейнів з апаратними воротами верифікації (HIL Gates).

Замість паперових підписів ради директорів 1970-х років сучасна інженерія використовує криптографічні підписи та автоматизовані арбітри:
- Кандидатний бінарник збирається у повністю відтворюваному контейнерному оточенні (Hermetic Build).
- Спеціальний арбітр у конвеєрі перевіряє хеш-суми, бюджети пам'яті за `.map`-файлами лінкера та логи автоматичних стендів Hardware-in-the-Loop.
- Тільки за умови нульового рівня регресій криптографічний процесор HSM (Hardware Security Module) накладає цифровий підпис заводським ключем, перетворюючи тестовий `RC` на захищений `GA Golden Master`.

Історія інженерії випусків довела: заморозка коду є не бюрократичним обмеженням, а термодинамічним інструментом охолодження складної системи, без якого неможливо гарантувати передбачувану поведінку заліза в реальних умовах експлуатації.
