# Закон Гайрама (Hyrum's Law)

<preknowlist>
- [Інтерфейс проти реалізації](root:sf-apps/interface-vs-implementation) — чому модуль ділять на публічну обіцянку та приховані нутрощі;
- [Семантичне версіонування](root:sf-release/semantic-versioning) — як SemVer формалізує обіцянки сумісності через мажор, мінор і патч;
- [Проєктування за контрактом](root:sf-release/design-by-contract) — як формальні перед- і післяумови описують межі допустимої поведінки.
</preknowlist>

Коли розробник публікує бібліотеку або мережевий сервіс, він фіксує контракт: перелічує назви функцій, типи аргументів, структури відповідей та числові коди помилок. Але щойно кількість споживачів інтерфейсу зростає від кількох десятків до сотень тисяч, набуває чинності емпіричний закон системної інженерії: клієнтські програми виконуються не проти текстової документації, а проти фізичної поведінки комп'ютерної програми під час виконання. Будь-яка спостережувана деталь реалізації — від черговості ключів у хеш-таблиці до кількості мікросекунд між мережевими пакетами — неминуче виявляється стороннім кодом, закріплюється у тестах і стає критичною умовою працездатності чужих систем.

Цю закономірність сформулював інженер Гайрам Райт (англ. *Hyrum Wright*):

> «За достатньої кількості користувачів API не має значення, що ви пообіцяли в контракті: кожна спостережувана поведінка системи знайде користувача, який на неї спирається».

У цьому твердженні криється причина, чому розвиток популярних платформ із часом сповільнюється або повністю паралізується: публічним інтерфейсом стає не те, що автор хотів показати, а все те, що клієнт узагалі здатен виміряти чи перевірити.

## Анатомія спостережуваної поведінки

Щоб зрозуміти, чому закон Гайрама діє з невідворотністю фізичного явища, розгляньмо спектр деталей, які автори систем зазвичай вважають внутрішньою справою реалізації, але на які неминуче зав'язується клієнтський код.

![Айсберг API: задокументований контракт над водою проти спостережуваної поведінки реалізації під водою](/root/eng/sf-release/hyrums-law/img/implicit-vs-explicit-contract.svg)

*Айсберг контракту API. Верхівка над водною лінією — це формально задокументований інтерфейс (типи, схеми, коди). Величезна підводна частина — це вся спостережувана поведінка реалізації (порядок ітерації, часові затримки, тексти помилок), на яку клієнти неминуче зав'язуються за законом Гайрама.*

### 1. Порядок ітерації у структурах даних

Класична хеш-таблиця (англ. *hash map*) або асоціативний масив у жодній мові програмування не дає математичних гарантій щодо порядку обходу своїх елементів. Специфікація стверджує: колекція є невпорядкованою множиною пар «ключ — значення».

Проте конкретна реалізація таблиці (наприклад, метод ланцюжків із фіксованим алгоритмом хешування MurmurHash) є абсолютно детермінованою на однакових вхідних даних. Якщо вставити ключі `"apple"`, `"banana"` та `"cherry"`, ітератор повертає їх у послідовності `["banana", "apple", "cherry"]`.

Розробник клієнтського застосунку створює функцію експорту даних у звіт або вебсторінку й пише юніт-тест:

```
assert response.keys == ["banana", "apple", "cherry"]
```

Тест проходить у 100% запусків. Команда випускає застосунок у продакшен. Через рік автор базової бібліотеки оновлює алгоритм хешування заради швидкості або замінює розмір первинного масиву бакетів з 16 на 32. Порядок ітерації змінюється на `["apple", "cherry", "banana"]`. Формальний контракт хеш-таблиці не порушено, проте клієнтський тест падає, а залежний звіт генерується з переплутаними колонками.

### 2. Текстовий вміст і форматування повідомлень про помилки

Функція читання файлу повертає об'єкт винятку або помилку. Документація фіксує числовий код помилки: `ENOENT` (файл не знайдено). Одночасно бібліотека формує людиночитний текст для логів: `"File not found: /tmp/config.json"`.

Клієнтський розробник, замість перевірки строгого коду `err.code == ENOENT`, пише регулярний вираз для швидкого розбору:

```
if (err.message.includes("File not found")) {
    create_default_config();
}
```

Під час наступного випуску бібліотеки автор вирішує зробити повідомлення інформативнішим і виправляє текст на `"Error: file '/tmp/config.json' does not exist"`. Для людини сенс повідомлення не змінився, але клієнтська перевірка повертає `false`, файл конфігурації не створюється, і застосунок зазнає аварійної зупинки.

### 3. Часові характеристики та латентність (Latency Jitter)

У системному програмуванні швидкість виконання операції часто розглядається як показник якості, а не частина контракту. Якщо функція перевірки кешу виконується за 2 мікросекунди, клієнтський розробник налаштовує таймаут асинхронного запиту у 5 мікросекунд.

Коли автор бібліотеки додає у функцію фонову синхронізацію статистики або додатковий рівень перевірки прав доступу, час виконання зростає до 8 мікросекунд. З погляду специфікації функція повертає коректний результат, але з погляду клієнта вона перестала працювати, оскільки всі виклики перериваються через спрацювання таймауту.

### 4. Послідовність і глибина внутрішніх викликів

Клієнтські фреймворки, інструменти моніторингу (APM) та засоби динамічного перехоплення (англ. *monkey patching*, інструментування байткоду) нерідко аналізують стек викликів (англ. *call stack*). Якщо метод `UserService.getUser()` раніше викликав `DbClient.query()` безпосередньо, а після рефакторингу почав викликати його через проміжний кешувальний шар `CacheManager.getOrQuery()`, глибина стека збільшилася на один фрейм.

Код, який за допомогою рефлексії перевіряв ім'я функції, що стоїть на два рівні вище у стеку, отримує несподіваний тип і зазнає краху.

### 5. Мікроструктура протоколів і серіалізації

У вебсервісах формат JSON формально визначає об'єкт як невпорядкований набір пар. Проте серіалізатор бібліотеки формує байти детерміновано: `"id"` завжди стоїть перед `"name"`. Якщо сторонній мікросервіс читає HTTP-потік через наївний швидкий парсер без повної буферизації, очікуючи бачити поле `"id"` у перших 32 байтах пакета, будь-яка зміна черговості полів у JSON заблокує його роботу.

Те саме стосується регістру заголовків HTTP: хоча стандарт HTTP/1.1 вимагає нечутливості до регістру (`Content-Type` тотожний `content-type`), тисячі наївних клієнтів парсять рядки чутливим до регістру порівнянням, перетворюючи регістр на неявний контракт.

## Руйнування семантичного версіонування (SemVer)

Концепція [семантичного версіонування](root:sf-release/semantic-versioning) спирається на суворе розмежування типів змін:

1. `PATCH` (виправлення латки) — внутрішні виправлення без зміни публічного API;
2. `MINOR` (мінорне оновлення) — додавання нових можливостей зі збереженням сумісності;
3. `MAJOR` (мажорне оновлення) — зміни, що ламають публічний контракт.

Закон Гайрама доводить, що це розмежування є математичною ідеалізацією, яка не працює у реальному світі з великою кількістю споживачів.

Якщо публічним інтерфейсом на практиці стає **вся сукупність спостережуваних властивостей**, то будь-яке виправлення дефекту в патч-релізі є потенційно ламкою зміною.

```
Виправлення помилки (Bug Fix) у версії 1.4.1:
Стара поведінка:  при порожньому рядку функція повертала NULL замість помилки.
Нова поведінка:   функція повертає код помилки INVALID_ARGUMENT згідно зі специфікацією.

Результат для клієнта:
Клієнтський код роками спирався на повернення NULL як на сигнал за замовчуванням.
Оновлення 1.4.0 → 1.4.1 ламає працездатність клієнта, перетворюючи PATCH на де-факто MAJOR.
```

Звідси виникає парадокс: автор бібліотеки вважає зміну латкою (PATCH), оскільки він привів реалізацію у відповідність до задокументованого контракту, тоді як споживач сприймає оновлення як катастрофічну несумісність, оскільки його система залежала від старої помилки.

## Механізм закостеніння платформ (Platform Ossification)

Коли кожна спостережувана властивість інтерфейсу перетворюється на залежність, програмна екосистема потрапляє у петлю **закостеніння** (лат. *ossificatio* — перетворення на кістку, від *os* — кістка + *facere* — робити).

![Петля закостеніння платформи: від неявної залежності клієнта до паралічу оновлень бібліотеки](/root/eng/sf-release/hyrums-law/img/hyrums-law-ecosystem-ossification.svg)

*Петля закостеніння платформи (Platform Ossification). Неявне зв'язування клієнтів із випадковими деталями реалізації перетворює будь-яке внутрішнє виправлення на аварію, змушуючи авторів заморожувати недокументовану поведінку й зупиняти розвиток системи.*

Петля закостеніння розвивається у п'ять послідовних кроків:

1. **Етап 1: Детермінований випуск.** Платформа надає API з певною внутрішньою оптимізацією або особливістю виконання, про яку нічого не сказано в специфікації.
2. **Етап 2: Масове зв'язування.** Клієнти створюють сотні тисяч рядків коду та автоматизованих тестів, які неявно покладаються на цю особливість.
3. **Етап 3: Спроба покращення.** Команда платформи випускає оновлення, яке оптимізує алгоритм, закриває діру в безпеці або змінює внутрішню структуру даних.
4. **Етап 4: Хвиля регресій.** Величезна кількість зовнішніх застосунків зазнає краху. Користувачі масово скаржаться на форумах, блокують оновлення та вимагають повернути стару поведінку.
5. **Етап 5: Заморозка та параліч.** Команда платформи капітулює: скасовує оптимізацію, додає складні шари емуляції старого дефекту або назавжди забороняє будь-які модифікації цієї підсистеми.

Детальний аналіз того, як цей параліч проявлявся у глобальних кодових базах, наведено у [хроніці масштабних рефакторингів у Google](root:sf-release/hyrums-law/hist-hyrum-wright-and-google.md).

## Закон Гайрама проти принципу Постела

Тривалий час стандартом проєктування мережевих протоколів вважався **принцип робастності** (лат. *robustus* — дубовий, міцний) Джона Постела: «Будь консервативним у тому, що робиш, і будь ліберальним у тому, що приймаєш від інших».

Закон Гайрама розкриває приховану небезпеку цього підходу.

Коли система «ліберально» приймає некоректний вхід — наприклад, парсер вебсервера прощає пропущений слеш в URL, некоректний заголовок або зайві пробіли у протоколі, — клієнтський розробник не бачить помилки. Його код продовжує надсилати некоректні дані.

За кілька років некоректний формат закріплюється у мільйонах клієнтських пристроїв. Тепер сервер **фізично не здатний відкинути битий запит**, оскільки це зруйнує роботу цілої екосистеми. Ліберальність прийому за Постелом слугує потужним каталізатором закону Гайрама, перетворюючи випадкові баги клієнтів на вічні стандарти поведінки сервера.

Глибокий розбір протистояння двох парадигм та аналіз сучасного консенсусу IETF RFC 9413 міститься у [порівняльному аналізі закону Гайрама та принципу Постела](root:sf-release/hyrums-law/comp-postel-vs-hyrum.md).

## Архітектурні стратегії захисту

Як розробникам платформ захистити свої системи від закостеніння та зберегти здатність до еволюції? Практика інженерії виробила чотири фундаментальні захисні бар'єри.

![Захисна рандомізація: штучний шум виявляє неявні залежності на етапі юніт-тестів і забезпечує стійкість системи](/root/eng/sf-release/hyrums-law/img/defensive-randomization-barrier.svg)

*Захисна рандомізація проти детермінізму реалізації. Ліворуч: випадковий детермінізм створює хибну стабільність, що закінчується аварією в продакшені. Праворуч: штучний шум виявляє неявні зв'язки з першого запуску тестів, змушуючи клієнтів писати надійний код.*

### 1. Захисна рандомізація (Defensive Randomization)

Головний метод боротьби з неявним детермінізмом — **примусова нестабільність незадокументованої поведінки**.

Якщо специфікація не гарантує певний порядок чи часовий інтервал, система повинна навмисно робити цю поведінку випадковою у кожному виклику:

- **Рандомізація хеш-сіду (Hash Seed Randomization):** мови Python, Go та Rust ініціалізують генератори хешів випадковим зерном (англ. *seed*) під час кожного старту процесу або створення таблиці. Порядок ключів змінюється від запуску до запуску, унеможливлюючи створення тестів, що зав'язуються на фіксовану послідовність.
- **Тасування ітераторів у Go map:** ітератор по хеш-таблиці в Go під час кожного обходу обирає випадковий стартовий бакет, гарантуючи, що навіть послідовні цикли в межах одного потоку повертатимуть ключі в іншому порядку.
- **Тасування заголовків у HTTP/2 та HTTP/3:** сервери та клієнти навмисно переставляють порядок заголовків фреймів `HEADERS`, аби проксі-сервери не розраховували на те, що заголовок `:method` завжди передує `:path`.
- **Протокол GREASE (RFC 8701) у TLS:** клієнти TLS навмисно вставляють псевдовипадкові зарезервовані ідентифікатори шифрів і розширень у пакети `ClientHello`. Це примушує проміжні шлюзи коректно ігнорувати невідомі поля з першого дня, запобігаючи закостенінню протоколу. Детальний опис наведено у [специфікації протоколу GREASE та механізмів ентропії](root:sf-release/hyrums-law/api-grease-and-anti-ossification.md).
- **Штучний джиттер латентності (Latency Fuzzing):** додавання випадкових мікрозатримок у тестових стендах запобігає виставленню надто агресивних таймаутів з боку клієнтів.

### 2. Суворе контрактне тестування та відхилення сміття

Замість ліберального прийому сучасні системи застосовують підхід **Fail Fast**:

- **Сувора валідація схем (Strict Schema Enforcement):** якщо клієнт передає в JSON невідоме поле, парсер на тестовому стенді повертає помилку `400 Bad Request`, замість того, щоб мовчки його ігнорувати. Це не дозволяє клієнту надсилати помилкові дані, які згодом перетворяться на неявний контракт.
- **Споживацькі контракти:** застосування методології [контрактного тестування](root:sf-release/contract-testing) (Consumer-Driven Contracts), де клієнт явно декларує свої очікування у формі коду, дозволяє автору API завчасно бачити, на які саме поля та формати спираються споживачі.

### 3. Сувора інкапсуляція та компіляторні бар'єри

- **Непрозорі типи даних (Opaque Pointers / PIMPL):** у C та C++ приховування внутрішніх структур за непрозорими покажчиками не дозволяє клієнту бачити розмір структури в байтах або звертатися до внутрішніх полів безпосередньо.
- **Внутрішня видимість пакетів:** каталог `internal/` у мові Go та модульна система Java (JPMS) фізично забороняють імпорт внутрішніх допоміжних пакетів стороннім кодом на рівні компілятора.

### 4. Фазована еволюція через прапорці та подвійний запуск

## Демонстрація в коді: захисна рандомізація API

Розглянемо практичну реалізацію API на C та C++, де автор захищає реєстр активних вузлів від неявного детермінізму, впроваджуючи перемішування колекції та штучний часовий шум.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <stdint.h>

#define MAX_ITEMS 8
#define NAME_LEN  32

typedef struct {
    char     name[NAME_LEN];
    uint32_t priority;
} ServiceEndpoint;

typedef struct {
    ServiceEndpoint endpoints[MAX_ITEMS];
    size_t          count;
    unsigned int    rng_seed;
    int             randomize_order; /* 1 = увімкнути захисну дедетермінізацію */
} EndpointRegistry;

void endpoint_registry_init(EndpointRegistry *reg, int randomize_order) {
    if (!reg) return;
    reg->count = 0;
    reg->rng_seed = (unsigned int)time(NULL);
    reg->randomize_order = randomize_order;
}

int endpoint_registry_add(EndpointRegistry *reg, const char *name, uint32_t priority) {
    if (!reg || !name || reg->count >= MAX_ITEMS) return -1;
    strncpy(reg->endpoints[reg->count].name, name, NAME_LEN - 1);
    reg->endpoints[reg->count].name[NAME_LEN - 1] = '\0';
    reg->endpoints[reg->count].priority = priority;
    reg->count++;
    return 0;
}

/* Отримання списку ендпоінтів із захисним перемішуванням Фішера — Єйтса */
size_t endpoint_registry_fetch(EndpointRegistry *reg, ServiceEndpoint *out_buf, size_t max_len) {
    if (!reg || !out_buf || max_len == 0) return 0;

    size_t n = (reg->count < max_len) ? reg->count : max_len;
    for (size_t i = 0; i < n; i++) {
        out_buf[i] = reg->endpoints[i];
    }

    /* Якщо активний захисний режим, перемішуємо елементи */
    if (reg->randomize_order && n > 1) {
        for (size_t i = n - 1; i > 0; i--) {
            size_t j = (size_t)(rand_r(&reg->rng_seed) % (i + 1));
            ServiceEndpoint tmp = out_buf[i];
            out_buf[i] = out_buf[j];
            out_buf[j] = tmp;
        }
    }
    return n;
}
```

```cpp
#include <algorithm>
#include <chrono>
#include <cstdint>
#include <random>
#include <span>
#include <string>
#include <string_view>
#include <vector>

struct ServiceEndpoint {
    std::string name;
    uint32_t    priority{0};
};

class EndpointRegistry {
public:
    explicit EndpointRegistry(bool randomize_order = true)
        : randomize_order_{randomize_order},
          rng_{static_cast<std::mt19937::result_type>(
              std::chrono::steady_clock::now().time_since_epoch().count())} {}

    bool add_endpoint(std::string_view name, uint32_t priority) {
        endpoints_.push_back(ServiceEndpoint{std::string(name), priority});
        return true;
    }

    /* Повертає список точок доступу. Якщо увімкнено randomize_order,
       порядок свідомо тасується, унеможливлюючи неявне зв'язування клієнта */
    [[nodiscard]] std::vector<ServiceEndpoint> fetch_endpoints() {
        std::vector<ServiceEndpoint> snapshot = endpoints_;
        if (randomize_order_ && snapshot.size() > 1) {
            std::shuffle(snapshot.begin(), snapshot.end(), rng_);
        }
        return snapshot;
    }

private:
    std::vector<ServiceEndpoint> endpoints_;
    bool                         randomize_order_{true};
    std::mt19937                 rng_;
};
```

```c
int compare_by_priority(const void *a, const void *b) {
    const ServiceEndpoint *ea = (const ServiceEndpoint *)a;
    const ServiceEndpoint *eb = (const ServiceEndpoint *)b;

    }
```
