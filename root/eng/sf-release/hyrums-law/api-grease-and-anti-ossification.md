# 📋 Специфікація антизакостеніння: протокол GREASE та механізми ентропії

Специфікація стандартних механізмів штучної ентропії описує протокольні структури, зарезервовані значення та інтерфейси середовищ виконання, призначені для примусового збереження розширюваності та запобігання закостенінню систем.

## Специфікація RFC 8701: GREASE у протоколах TLS 1.3 та QUIC

Протокол **GREASE** (англ. *Generate Random Extensions And Sustain Extensibility* — генерація випадкових розширень для підтримки розширюваності), стандартизований IETF у документі **RFC 8701**, вирішує проблему прихованого закостеніння мережевих шлюзів (англ. *middleboxes*), фаєрволів та систем виявлення вторгнень (IDS/IPS).

Мережеві шлюзи, аналізуючи трафік, часто припускаються помилки: вони розраховані лише на ті значення протокольних полів, які існували на момент їх випуску. Коли робоча група IETF стандартизує новий шифронабір або нове розширення TLS, такий шлюз сприймає невідомий ідентифікатор як аномалію і розриває TCP-з'єднання скиданням прапорця `RST` або мовчазним відкиданням пакетів (`DROP`).

Механізм GREASE запобігає цій деградації через постійне введення випадкових зарезервованих значень у кожен сеанс зв'язку.

### Таблиця зарезервованих констант GREASE (16-бітні значення)

Специфікація виділяє 16 симетричних шістнадцяткових значень вигляду `0x?A?A`, де обидва байти збігаються, а молодший напівбайт дорівнює `0xA`. Вони гарантовано ніколи не будуть призначені IETF для реальних розширень:

| Шістнадцятковий код | Десяткове значення | Область застосування у TLS 1.3 / QUIC |
|---|---|---|
| `0x0A0A` | 2570 | Cipher Suites, Supported Groups, ALPN Identifiers |
| `0x1A1A` | 6682 | Cipher Suites, Extensions, Named Curves |
| `0x2A2A` | 10794 | Cipher Suites, Extensions, Signature Algorithms |
| `0x3A3A` | 14906 | Cipher Suites, Supported Groups |
| `0x4A4A` | 19018 | Cipher Suites, Extensions, ALPN |
| `0x5A5A` | 23130 | Cipher Suites, Named Groups |
| `0x6A6A` | 27242 | Cipher Suites, Extensions, Signature Schemes |
| `0x7A7A` | 31354 | Cipher Suites, Supported Versions |
| `0x8A8A` | 35466 | Cipher Suites, Extensions |
| `0x9A9A` | 39578 | Cipher Suites, Key Share Groups |
| `0xAAAA` | 43690 | Cipher Suites, Extensions |
| `0xBABA` | 47802 | Cipher Suites, ALPN Protocol Identifiers |
| `0xCACA` | 51914 | Cipher Suites, Extensions |
| `0xDADA` | 56026 | Cipher Suites, Supported Groups |
| `0xEAEA` | 60138 | Cipher Suites, Extensions |
| `0xFAFA` | 64250 | Cipher Suites, Extensions |

### Розширення GREASE для протоколу HTTP/2 та HTTP/3

Аналогічний підхід стандартизовано для транспортних параметрів QUIC та кадрів керування протоколу HTTP/2:

- **HTTP/2 SETTINGS Parameters:** Клієнти надсилають випадкові ідентифікатори параметрів `0x?a?a` у кадрі `SETTINGS`. Сервер зобов'язаний зберегти з'єднання та проігнорувати невідомий параметр згідно з RFC 7540 §5.5.
- **HTTP/2 Frame Types:** Періодичне надсилання порожніх кадрів експериментальних типів для перевірки того, що проміжні проксі коректно пропускають невідомі типи кадрів.
- **QUIC Transport Parameters:** Включення зарезервованих ідентифікаторів у `EncryptedExtensions` для гарантії підтримки майбутніх оптимізацій транспорту.

### Інваріанти поведінки згідно з RFC 8701

1. **Заборона узгодження (No Negotiation):** Сервер НІКОЛИ не повинен обирати значення GREASE як узгоджений шифронабір або підтверджене розширення у відповіді `ServerHello`. Вибір значення GREASE сервером є критичною помилкою протоколу і призводить до негайного розриву зв'язку з `illegal_parameter alert`.
2. **Обов'язковість ігнорування (Mandatory Ignore):** Отримувач (сервер чи проміжний шлюз) зобов'язаний успішно завершити рукостискання, повністю проігнорувавши всі невідомі йому поля, включно з GREASE.
3. **Псевдовипадковий вибір (Stochastic Injection):** Клієнт обирає значення GREASE з наведеної таблиці випадково для кожної нової сесії. Якщо шлюз спробує захардкодити одне значення GREASE, він спіткнеться на іншому з 16 можливих.

```
[Клієнт]                                                     [Сервер / Шлюз]
   │                                                               │
   │ ─── ClientHello ────────────────────────────────────────────► │
   │       CipherSuites: [TLS_AES_128_GCM_SHA256, 0x1A1A (GREASE)]  │
   │       Extensions:   [server_name, supported_versions, 0x5A5A] │
   │                                                               │
   │                                             [Обробка шлюзом]  │
   │                                             • 0x1A1A невідомий│
   │                                             • За специфікацією│
   │                                               ігноруємо його  │
   │                                                               │
   │ ◄── ServerHello ───────────────────────────────────────────── │
   │       CipherSuite: TLS_AES_128_GCM_SHA256 (НЕ GREASE!)        │
   │                                                               │
```

## Механізми ентропії у середовищах виконання мов програмування

Сучасні компілятори та віртуальні машини вбудовують механізми захисної дедетермінізації безпосередньо у базові контейнери та системні виклики.

### 1. Середовище Go: рандомізація точки входу ітератора Map

У середовищі виконання Go (файл вихідників `src/runtime/map.go`) обхід хеш-таблиці `map` навмисно не має фіксованого порядку, навіть якщо таблиця не змінювалася між ітераціями.

Під час виклику функції ініціалізації ітератора `runtime.mapiterinit` рушій зчитує апаратний генератор псевдовипадкових чисел `fastrand()`:

```
// Псевдокод ініціалізації ітератора Go Runtime (map.go)
r := uintptr(fastrand())
// Випадковий стартовий бакет у масиві бакетів
it.startBucket = r & (uintptr(1)<<h.B - 1)
// Випадковий зсув комірки всередині стартового бакета
it.offset = uint8(r >> h.B & (bucketCnt - 1))
```

- **Механізм обходу:** Ітератор починає обхід із випадково обраного бакета `startBucket` та комірки `offset`, проходить усі бакети по колу за модулем кількості бакетів і завершує роботу, коли повертається до вихідної точки.
- **Архітектурна ціль:** Змусити розробника явно викликати `sort.Slice` або `slices.Sort`, якщо йому потрібен детермінізм, захищаючи кодову базу Go від неявного зрощення з внутрішньою розкладкою бакетів.

### 2. Середовище Python: рандомізація хеш-сіду рядків

Починаючи з випуску Python 3.3, алгоритм хешування рядкових та байтових об'єктів (функція `hash()`) використовує випадковий 128-бітний секретний ключ, який генерується з системної ентропії операційної системи під час кожного старту процесу `python`.

| Змінна середовища / Параметр | Значення | Семантика для середовища виконання |
|---|---|---|
| `PYTHONHASHSEED=random` | За замовчуванням (Python 3.3+) | Генерується криптографічно стійкий випадковий сід; `hash("id")` різний у кожному процесі |
| `PYTHONHASHSEED=0` | Ціле число `0` | Дедетермінізацію вимкнено; хеші рядків стають константними між запусками (режим налагодження) |
| `PYTHONHASHSEED=<N>` | Число в межах `[1, 4294967295]` | Фіксований сід для точного покрокового відтворення падінь у тестах |

Без цього захисту порядок ключів у словниках `dict` (до запровадження гарантії порядку вставки в Python 3.7) та множинах `set` залежав лише від хешу рядка. Це призводило до масового падіння тестів при зміні версії інтерпретатора або платформи. Для множин `set` дедетермінізація порядку ітерації зберігається повною мірою.

### 3. Середовище Rust: `RandomState` у `std::collections::HashMap`

Стандартна бібліотека Rust реалізує структуру `std::collections::HashMap` із захистом від атак алгоритмічної складності (HashDoS) та закостеніння порядку обходу.

- **Генератор стану:** За замовчуванням конструктор `HashMap::new()` використовує трейт `BuildHasher`, реалізований через структуру `std::collections::hash_map::RandomState`.
- **Ініціалізація ключів:** Під час створення кожного окремого екземпляра `HashMap` структура `RandomState::new()` викликає системний генератор ентропії (`getrandom` у Linux, `BCryptGenRandom` у Windows) для створення двох незалежних 64-бітних ключів `k0` та `k1`.
- **Алгоритм SipHash 1-3:** Функція хешування обчислює значення за формулою `SipHash13(key, k0, k1)`. Навіть у межах одного потоку виконання дві однакові таблиці з ідентичним набором ключів мають абсолютно різний внутрішній розподіл елементів по комірках.

### 4. Реляційні бази даних: `PRAGMA query_only` та відсутність `ORDER BY`

Специфікація мови SQL стандарту ANSI/ISO явно стверджує: реляційна таблиця є невпорядкованою множиною рядків. Запит `SELECT` без явної пропозиції `ORDER BY` повертає рядки у невизначеному порядку.

- **Оптимізатор запитів:** У SQLite, PostgreSQL та MySQL порядок повернення рядків без `ORDER BY` залежить від обраного плану виконання (Index Scan, Seq Scan, Parallel Bitmap Scan), розташування сторінок у кеші пам'яті та кількості робочих потоків.
- **Пастка клієнта:** У тестах на базі з трьома рядками `Seq Scan` завжди повертає рядки у порядку додавання (`id=1, 2, 3`). Клієнтський код пише перевірку без `ORDER BY`. При переході на бойову базу з індексами оптимізатор обирає `Index Scan`, рядки повертаються у зворотному порядку, і сервіс ламається.
- **Захисний інструмент:** Спеціальні тестові діалекти (наприклад, прапорець SQLite `reverse_unordered_selects`) змушують рушій бази даних повертати рядки у зворотному або перемішаному порядку, якщо у запиті відсутній `ORDER BY`, негайно виявляючи приховані порушення реляційного контракту.
