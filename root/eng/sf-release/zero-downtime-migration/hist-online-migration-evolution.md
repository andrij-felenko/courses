# 📜 Від нічних вікон простою до непомітної міграції: еволюція перенесення даних під навантаженням

Коли наприкінці 1990-х років реляційна база даних корпоративної системи розросталася до кількох десятків гігабайтів, зміна типу однієї колонки або додавання вторинного індексу означало неминуче оголошення «технологічного вікна». Адміністратори зупиняли вебсервери опівночі щонеділі, запускали блокуючу утиліту `ALTER TABLE`, чекали три години, поки СКБД перебудує B-дерева на диску, і лише після цього повертали трафік клієнтам. З появою цілодобових глобальних інтернет-сервісів із сотнями мільйонів користувачів у різних часових поясах поняття «нічного вікна» втратило будь-який практичний сенс: зупинка прийому платежів чи замовлень навіть на три хвилини почала завдавати мільйонних фінансових і репутаційних збитків.

## Епоха ексклюзивних блокувань і наївних DDL-команд

У ранніх версіях реляційних систем (зокрема MySQL 3.23–5.0 та класичних релізах PostgreSQL) зміна схеми таблиці (*Data Definition Language, DDL*) була виключно монопольною операцією. СКБД виконувала наступний детермінований алгоритм:
1. Захоплювалося ексклюзивне блокування таблиці (`ACCESS EXCLUSIVE` або блокування метаданих на рівні таблиці), що повністю забороняло будь-які операції запису (`INSERT`, `UPDATE`, `DELETE`) та, у багатьох випадках, операції читання (`SELECT`).
2. На диску створювалася нова тимчасова порожня таблиця з оновленою схемою.
3. Усі рядки з вихідної таблиці по черзі копіювалися в тимчасову таблицю з перерахунком усіх індексів.
4. Стара таблиця видалялася, а тимчасова перейменовувалася на місце оригінальної, після чого блокування знімалося.

Якщо таблиця містила 50 мільйонів рядків, дискові накопичувачі того часу (повільні масиви HDD зі швидкістю випадкового доступу 100–150 IOPS) виконували копіювання годинами. Усі черги запитів до застосунку переповнювалися, пули з'єднань до бази вичерпувалися за лічені секунди, і система зазнавала повного каскадного колапсу.

## 2006–2011: Поява тригерних утиліт і революція Percona

У середині 2000-х років інженери компаній із високим навантаженням (Flickr, LiveJournal, Yahoo!) усвідомили, що покладатися на вбудовані команди СКБД неможливо. Першим системним проривом стала утиліта `oak-online-alter-table`, створена Шломі Ноахом (*Shlomi Noach*), та інструмент `facebook-osc` від інженерної команди Facebook.

У 2011 році барон Шварц (*Baron Schwartz*) та інженери компанії Percona узагальнили цей досвід у відкритому інструменті **`pt-online-schema-change`** (частина пакету Percona Toolkit). Ідея полягала у створенні «тіньової» копії таблиці прямо на живому сервері:
* Утиліта створювала порожню таблицю `_new_users` із новою схемою.
* На вихідну таблицю `users` навішувалися три синхронні тригери СКБД: `AFTER INSERT`, `AFTER UPDATE`, `AFTER DELETE`. Будь-яка жива мутація, що надходила від користувачів у стару таблицю, автоматично й транзакційно дублювалася в нову.
* Фоновий потік маленькими чанками (наприклад, по 1000 рядків через `INSERT LOW_PRIORITY IGNORE INTO _new_users SELECT ... WHERE id BETWEEN x AND y`) копіював історичні дані.
* Наприкінці виконувалася атомарна операція перейменування таблиць: `RENAME TABLE users TO _old_users, _new_users TO users`.

Тригерний підхід уперше дозволив змінювати схеми таблиць обсягом у сотні гігабайтів без зупинки користувацького трафіку. Проте зі зростанням навантаження виявилися фундаментальні вади тригерів:
1. **Накладні витрати на кожну транзакцію:** тригери виконувалися в тому самому транзакційному потоці клієнта, подвоюючи кількість операцій запису й суттєво збільшуючи затримку (*latency*) запитів.
2. **Взаємні блокування (Deadlocks):** конкурентні оновлення споріднених рядків у двох таблицях під тригерами часто призводили до взаємних блокувань транзакцій, аварійно обриваючи користувацькі сесії.
3. **Блокування метаданих при встановленні тригерів:** команда `CREATE TRIGGER` сама по собі вимагала короткочасного ексклюзивного блокування таблиці. Якщо в цей момент у базі виконувався довгий `SELECT`, виникала черга очікування, яка блокувала всю СКБД.

## 2016: Прорив GitHub та створення безтригерного `gh-ost`

До 2016 року інфраструктура платформи GitHub оперувала терабайтними базами даних MySQL із десятками тисяч транзакцій на секунду. Регулярні збої та деградація продуктивності через блокування `pt-online-schema-change` змусили інженера Шломі Ноаха створити принципово новий рушій — **`gh-ost`** (*GitHub Online Schema Transformations*).

`gh-ost` здійснив революцію, повністю відмовившись від тригерів СКБД. Замість втручання в транзакційне ядро бази, `gh-ost` підключався до MySQL як звичайний реплікаційний клієнт (*Binlog Stream Consumer*):
1. Він зчитував бінарний журнал транзакцій (*Row-Based Replication, RBR*), що генерувався сервером асинхронно.
2. Фоновий бекфіл копіював історичні рядки, а потік змін із бінарного журналу паралельно застосовував нові мутації до тіньової таблиці.
3. Застосунок узагалі не відчував накладних витрат: жодних тригерів, жодних додаткових блокувань у клієнтських транзакціях.
4. Процес можна було будь-якої миті безпечно зупинити, уповільнити (дроселювати за рівнем реплікаційного лагу) або відкотити без жодного ризику для цілісності вихідних даних.

## Еволюція у світі PostgreSQL та розподілених СКБД

Паралельно розвивалися механізми міграції в екосистемі PostgreSQL. Історично PostgreSQL підтримував транзакційне DDL (можливість виконати `ALTER TABLE` всередині `BEGIN ... ROLLBACK`), проте тривалі блокування `ACCESS EXCLUSIVE` залишалися критичною проблемою.

Починаючи з PostgreSQL 8.2 з'явилася команда `CREATE INDEX CONCURRENTLY`, яка будувала індекс у два проходи без блокування операцій запису. У версії PostgreSQL 11 було реалізовано метадані за замовчуванням: додавання нової колонки з фіксованим значенням `DEFAULT` перестало вимагати фізичного перезапису всіх сторінок таблиці на диску.

У середині 2010-х років розвиток мікросервісної архітектури та платформ розподіленого потокового оброблення (Apache Kafka, Debezium, AWS DMS) переніс концепцію нульового простою з рівня окремої СКБД на рівень розподіленої системи. Міграції перестали бути суто операцією над однією таблицею — вони трансформувалися в патерн **Expand/Contract** та потокове вилучення змін (*Change Data Capture, CDC*), що дозволяє безперешкодно переносити живі дані між гетерогенними сховищами (наприклад, із монолітного Oracle або PostgreSQL у розподілені сховища CockroachDB, Cassandra чи Elasticsearch).
