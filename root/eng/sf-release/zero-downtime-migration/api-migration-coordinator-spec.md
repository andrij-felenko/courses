# 📋 Специфікація координатора та протокол керування міграцією

Координатор міграції даних без простою (*Zero-Downtime Migration Coordinator*) забезпечує детерміноване керування життєвим циклом перенесення інформації між різнорідними або однорідними сховищами даних. Його обов'язками є виконання безпечних переходів між фазами патерну Expand/Contract, безперервний аудит узгодженості, автоматичне дроселювання фонових потоків при деградації цільової або первинної бази даних, а також надання інтерфейсу для оперативного керування та екстреного відкату.

## Архітектурні компоненти координатора

Координатор функціонує як високодоступний оркестратор, що складається з чотирьох взаємодіючих підсистем:

1. **Рушій станів та консенсусу (State Machine Engine):**
   Забезпечує лінеаризовність і незмінність фазових переходів. Стан поточної міграції зберігається в розподіленому сховищі конфігурацій (наприклад, etcd, Consul або спеціальній таблиці метаданих СКБД із розподіленим блокуванням). Це гарантує, що при перезапуску або аварії вузла координатора новий лідер підхоплює процес точно з останньої зафіксованої точки.

2. **Контролер протитиску та адаптивного дроселювання (Backpressure Controller):**
   Безперервно збирає телеметрію з обох сховищ: реплікаційний лаг, завантаження процесора (CPU utilization), чергу очікування з'єднань пулу та 99-й перцентиль затримки запитів (`p99 latency`). При перевищенні встановлених порогів контролер надсилає сигнал уповільнення або тимчасової зупинки фоновим воркерам.

3. **Маршрутизатор трафіку (Traffic Routing Controller):**
   Взаємодіє з сервісною мережею (*Service Mesh / Envoy*), API-шлюзами та серверами динамічних прапорців (*Feature Flags*). Відповідає за канареечне ступеневе перемикання відсотка читань і записів між старою та новою базами даних.

4. **Аналізатор тіньової верифікації (Shadow Verification Analyzer):**
   Асинхронно зіставляє результати паралельного виконання запитів, розраховує статистичну значущість розходжень і блокує перехід до фази перемикання, якщо виявлено бодай один невідповідний рядок.

## Скінченний автомат станів міграції (State Machine)

Процес міграції моделюється детермінованим скінченним автоматом із суворими інваріантами для кожного стану:

```
[INIT] 
   │
   ▼ (застосовано неблокуюче розширення схеми)
[EXPAND_APPLIED] 
   │
   ▼ (увімкнено подвійний запис у застосунку)
[DUAL_WRITE_ENABLED] 
   │
   ▼ (запуск фонового копіювання історії)
[BACKFILLING] ◄──┐ (динамічне регулювання швидкості)
   │             │
   ▼             └── [THROTTLED]
[BACKFILL_DONE] 
   │
   ▼ (увімкнення 100% тіньової верифікації / Dark Reading)
[VALIDATING] 
   │
   ├──────────────────────────────┐ (виявлено розходження > 0)
   ▼ (розходжень 0, лаг < 50 мс)   ▼
[CUTOVER_READY]                [ABORTED / ROLLED_BACK]
   │
   ▼ (перемикання джерела читання і запису на нову базу)
[CUTOVER_COMPLETED]
   │
   ▼ (зупинка запису в стару схему та видалення застарілих структур)
[CONTRACT_APPLIED] 
   │
   ▼
[COMPLETED]
```

### Інваріанти та правила переходів між станами:

1. **`INIT` → `EXPAND_APPLIED`:** перехід дозволяється лише після успішного виконання DDL-скриптів створення цільових структур (нових таблиць або nullable-стовпчиків). Джерелом правди залишається первинна база даних.
2. **`EXPAND_APPLIED` → `DUAL_WRITE_ENABLED`:** застосунок починає дублювати всі нові операції створення та оновлення в обидва сховища. Якщо цільове сховище недоступне, помилка логується, але не блокує основний бізнес-потік.
3. **`DUAL_WRITE_ENABLED` → `BACKFILLING`:** запускається фоновий рушій копіювання історичних даних із курсорною пагінацією та умовним збереженням.
4. **`BACKFILLING` ↔ `THROTTLED`:** якщо реплікаційний лаг перевищує ліміт `max_replication_lag_ms` або час відповіді бази даних `p99` перевищує 100 мс, воркер переходить у стан очікування до нормалізації метрик.
5. **`BACKFILL_DONE` → `VALIDATING`:** після досягнення кінця таблиці вмикається асинхронне тіньове читання (*Dark Reading*). Кожен запит на читання дублюється у фоні до обох баз із порівнянням контрольних сум.
6. **`VALIDATING` → `CUTOVER_READY`:** фіксується стан, коли протягом вікна спостереження (`validation_window_hours`) кількість розходжень дорівнює нулю, а лаг потоку CDC не перевищує 50 мілісекунд.
7. **`CUTOVER_READY` → `CUTOVER_COMPLETED`:** виконання фінального перемикання трафіку: нова база даних стає основним джерелом правди для читань і записів. Одночасно запускається зворотна реплікація (*Reverse Sync*) у стару базу на випадок необхідності відкату.
8. **`CUTOVER_COMPLETED` → `CONTRACT_APPLIED` → `COMPLETED`:** після успішної роботи під повним навантаженням (зазвичай 48–72 години) зворотний потік вимикається, стара схема видаляється, а міграція позначається як завершена.

## Специфікація конфігураційного маніфесту (YAML/JSON)

Кожна міграційна задача описується декларативним документом, що визначає параметри надійності, ліміти швидкості та правила верифікації:

```yaml
migration_task:
  id: "mig-users-v2-to-v3"
  description: "Розділення сутності користувача на профіль та фінансовий гаманець"
  source_table: "users"
  target_table: "users_v3"
  primary_key: "id"
  version_column: "updated_at"
  
  backfill:
    batch_size: 1500
    concurrency_workers: 4
    sleep_between_batches_ms: 15
    max_replication_lag_ms: 1000
    lag_check_interval_sec: 5
    retry_limit_per_batch: 5
    
  dual_write:
    strategy: "application_dual_write" # або "cdc_debezium"
    fail_on_target_error: false        # джерело правди лишається старим
    async_queue_capacity: 50000
    drop_policy: "log_and_reconcile"
    
  validation:
    shadow_read_percentage: 100
    checksum_fields: ["email", "status", "balance", "updated_at"]
    max_divergence_tolerance: 0
    validation_window_hours: 24
    sample_rate_for_full_diff: 0.05
    
  cutover:
    reverse_sync_enabled: true         # зворотна реплікація з нової в стару базу
    read_switch_step_percentage: 25    # канареечне перемикання читань
    step_duration_minutes: 10
    rollback_timeout_sec: 5
```

## Інтерфейс керування (HTTP REST API)

Координатор надає набір програмних ендпоінтів для автоматизації у складі CI/CD конвеєрів та ручного контролю інженерами експлуатації.

### 1. Створення та запуск задачі міграції
* **Метод і шлях:** `POST /v1/migrations`
* **Заголовки:** `Content-Type: application/json`, `Idempotency-Key: <UUID>`
* **Тіло запиту:** Повний конфігураційний маніфест у форматі JSON.
* **Відповідь `201 Created`:**
```json
{
  "migration_id": "mig-users-v2-to-v3",
  "status": "DUAL_WRITE_ENABLED",
  "created_at": "2026-08-20T10:00:00Z",
  "coordinator_node": "coord-01.infra.internal"
}
```

### 2. Моніторинг статусу та динамічного прогресу
* **Метод і шлях:** `GET /v1/migrations/{id}/status`
* **Опис:** повертає деталізовану інформацію про кількість оброблених рядків, поточну швидкість, оцінку часу до завершення та стан здоров'я бази даних.
* **Відповідь `200 OK`:**
```json
{
  "migration_id": "mig-users-v2-to-v3",
  "status": "BACKFILLING",
  "progress": {
    "total_rows_estimated": 45000000,
    "rows_migrated": 31500000,
    "percentage": 70.0,
    "current_cursor_id": 31500000,
    "current_tps": 3200,
    "estimated_time_remaining_sec": 4218
  },
  "health": {
    "replication_lag_ms": 140,
    "is_throttled": false,
    "source_cpu_utilization": 0.42,
    "consecutive_failures": 0
  },
  "verification": {
    "total_shadow_reads": 12500000,
    "mismatches_detected": 0
  }
}
```

### 3. Ініціація перемикання трафіку (Cutover)
* **Метод і шлях:** `POST /v1/migrations/{id}/cutover`
* **Опис:** активує режим фінального перемикання джерела правди за умови проходження валідації.
* **Тіло запиту:**
```json
{
  "enable_reverse_replication": true,
  "force": false
}
```
* **Відповідь `200 OK`:**
```json
{
  "migration_id": "mig-users-v2-to-v3",
  "status": "CUTOVER_COMPLETED",
  "primary_datastore": "users_v3",
  "reverse_sync_status": "ACTIVE_STREAMING",
  "cutover_timestamp": "2026-08-20T14:30:00Z"
}
```

### 4. Екстрений аварійний відкат (Rollback)
* **Метод і шлях:** `POST /v1/migrations/{id}/rollback`
* **Опис:** миттєво перемикає клієнтський трафік назад на первинне сховище без втрати даних, використовуючи накопичені зміни зі зворотного потоку реплікації.
* **Тіло запиту:**
```json
{
  "reason": "Target query latency p99 exceeded 250ms SLA on production load"
}
```
* **Відповідь `200 OK`:**
```json
{
  "migration_id": "mig-users-v2-to-v3",
  "status": "ROLLED_BACK",
  "active_primary": "users",
  "data_loss_records": 0,
  "message": "Traffic redirected back to source datastore successfully."
}
```

## Канареечне розгортання та захист від деградації

Канареечне перемикання трафіку (*Canary Rollout*) розбивається на декілька послідовних етапів (1%, 5%, 25%, 50%, 100%). На кожному кроці координатор робить паузу тривалістю щонайменше 10–15 хвилин для накопичення статистичних метрик.

Якщо частка помилок HTTP 5xx перевищує поріг 0.01% або час виконання запитів `p99` зростає більш ніж на 15% порівняно з базовою лінією, координатор автоматично скасовує операцію і повертає маршрутизацію до попереднього безпечного кроку.

## Матриця обробки аварійних сценаріїв

Координатор містить детерміновані правила реакції на системні збої:

* **Мережеве розділення (Split-Brain / Network Partition):**
  Якщо зв'язок між координатором і цільовою базою обривається під час бекфілу, воркер переходить у режим очікування і повторює спроби з експоненційною затримкою. Основний трафік продовжує обслуговуватися первинною базою даних без будь-якого впливу на клієнтів.
* **Помилки унікальності (Unique Constraint Violation):**
  Якщо під час бекфілу або подвійного запису виникає конфлікт первинного чи вторинного ключа, координатор реєструє подію, створює запис у журналі розходжень і передає інцидент системі автоматичної [звірки](topic:sf-distributed/reconciliation).
* **Аварійне завершення вузла координатора:**
  Оскільки прогрес бекфілу зберігається у вигляді значення `last_processed_id` після кожної успішно підтвердженої пачки, новий екземпляр координатора відновлює роботу без повторного сканування всієї таблиці та без ризику дублювання записів.

## Контракт метрик моніторингу (Prometheus / OpenTelemetry)

| Метрика | Тип | Опис та розмірність |
| :--- | :--- | :--- |
| `migration_backfill_rows_total` | Counter | Загальна кількість успішно перенесених рядків бекфілу |
| `migration_backfill_skipped_race_total` | Counter | Кількість рядків, пропущених через наявність свіжішого стану |
| `migration_replication_lag_seconds` | Gauge | Поточний лаг реплікації або потоку CDC (секунди) |
| `migration_shadow_read_mismatches_total` | Counter | Кількість розходжень даних під час тіньової верифікації |
| `migration_batch_duration_seconds` | Histogram | Розподіл тривалості виконання однієї транзакційної пачки |
| `migration_rate_limited_seconds_total` | Counter | Сумарний час простою воркера в режимі захисного дроселювання |
