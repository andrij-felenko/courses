# ⚙️ Санітайзери на практиці й кілька правил MISRA

Задача: статичний аналіз лише **підозрює** дефект на одному зі шляхів, бо не знає реальних даних. Треба інструмент, що на справжньому запуску скаже напевно — і покаже точне місце. Для C це санітайзери: компілятор вплітає перевірки прямо в код, і вони спрацьовують під час виконання. Розберімо, як їх увімкнути на хості, як читати їхній звіт і як він зчіплюється зі статичним аналізом, а наприкінці — практичний розбір кількох правил MISRA-C на коді.

## Збірка під ASan і UBSan на хості

Прошивку цілком на мікроконтролері санітайзером не покриєш — він потребує підтримки рантайму, якої на голому залізі нема. Але **переносну частину** логіки (розбір протоколів, скінченні автомати, обчислення, роботу з буферами) майже завжди можна зібрати й прогнати на ПК — і саме там натиснути на неї санітайзерами. Це той самий принцип, що й [тести на хості](root:embedded/firmware-testing): виносимо незалежний від заліза код на велику машину й знущаємося з нього вдосталь.

Увімкнення — кілька прапорців до звичайної збірки тестів на хості:

```bash
# AddressSanitizer + UndefinedBehaviorSanitizer разом:
gcc -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer \
    parser.c test_parser.c -o test_parser
./test_parser
```

Розбір прапорців:

```
-g                       символи для імен і номерів рядків у звіті
-O1                      легка оптимізація: швидше, ще без втрати точності
-fsanitize=address       ASan: межі, use-after-free, double-free, витоки
-fsanitize=undefined     UBSan: переповнення, зсуви, ділення на 0, UB
-fno-omit-frame-pointer  зберегти кадрові покажчики — рівний, читний стек
```

Санітайзер уповільнює код у кілька разів і збільшує пам'ять — тому це режим для **тестів і налагодження**, не для релізної збірки. У реліз іде звичайна оптимізована прошивка без інструментування.

## Як читати звіт ASan

Хай тест прогнав функцію з помилкою «на одиницю»:

```c
// parser.c
int sum_first(const int *a, int n) {
    int s = 0;
    for (int i = 0; i <= n; i++)   // пастка: <= замість <
        s += a[i];                 // на останній ітерації a[n] — за межею
    return s;
}
```

Виклик `sum_first(buf, 4)` на масиві з чотирьох елементів читає `buf[4]` — поза масивом. ASan уриває виконання й друкує:

```
==12345==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7ffe...
READ of size 4 at 0x7ffe... thread T0
    #0 0x... in sum_first parser.c:5
    #1 0x... in main test_parser.c:11

Address 0x7ffe... is located in stack of thread T0 at offset 32
  'buf' (line 10) <== Memory access at offset 32 overflows this variable
```

Звіт читають згори вниз. Перший рядок — **клас дефекту** (`stack-buffer-overflow` — вихід за масив на стеку) і чи це читання, чи запис (`READ`). Далі — **стек викликів**: дефект стався в `sum_first` на рядку 5, куди прийшли з `main` рядка 11. Останній блок — **яку саме змінну** зачепили: масив `buf`, оголошений на рядку 10. Це повна адреса дефекту: клас, місце, винна змінна — без жодного відлагоджувача.

> 🔧 **Навіщо це.** Той самий `buf[4]` без санітайзера на ПК найчастіше «працює»: читає сусідній байт стека, повертає трохи неправильну суму — і тест навіть може випадково пройти. На мікроконтролері це тиха псувань сусідньої змінної, яку потім ловитимеш годинами [у живому чипі](root:embedded/jtag-swd-tools). ASan перетворює тиху, плавучу помилку на гучну аварію з точною адресою — і робить це на хості за секунди.

## Як читати звіт UBSan

ASan стереже пам'ять; UBSan стереже **невизначену поведінку** (англ. *undefined behavior*, UB — те, що стандарт мови лишає невизначеним, тож компілятор має право зробити будь-що). Найпідступніший її різновид — переповнення знакового цілого. Класична пастка — перевести час із мілісекунд у мікросекунди:

```c
// time.c
int64_t us_from_ms(int32_t ms) {
    return ms * 1000;      // пастка: множення йде в int, розширення до int64 — лише ПОТІМ
}
```

Здається, тип результату `int64_t` усе врятує — та ні. Вираз `ms * 1000` компілятор рахує в `int` (обидва операнди — 32-розрядні), і аж **готовий** добуток розширює до 64 розрядів. Досить, щоб `ms` дорівнювало 3 000 000 (це 50 хвилин у мілісекундах), і `ms * 1000` = 3 000 000 000 уже не влазить у 32-розрядний `int`, чия стеля — 2 147 483 647: переповнення знакового, тобто UB. Тому помилка гірша, ніж здається: компілятор, якому стандарт каже «знакове переповнення неможливе», має право **припустити, що його й нема**, і викинути ваші ж перевірки на кшталт `if (result < 0)` — код, що мав би її впіймати, зникає разом із причиною. UBSan ловить її в момент події:

```
time.c:3:15: runtime error: signed integer overflow:
    3000000 * 1000 cannot be represented in type 'int'
```

Звіт точний: файл, рядок, **яка операція** переповнилася, з якими операндами і **в якому типі**. Лікування — завести множення в ширший тип **до** обчислення, а не після: `return (int64_t)ms * 1000;`. Тепер перший операнд одразу 64-розрядний, `1000` підтягується до нього, і добуток рахується в 64 розрядах без переповнення. Статичний аналіз таке переповнення лише **підозрює** (бо результат залежить від значення `ms`); UBSan **доводить** на конкретному вході.

Суміжна, але **інша** пастка — звуження. Якщо ширше значення присвоїти назад у вузький тип (`int16_t x = wide;`, де `wide` — 32-розрядне число понад 32767), воно не влазить — та, на відміну від переповнення, це вже **не** UB, а поведінка, **визначена реалізацією** (стандарт C лишає результат на розсуд компілятора, а не «будь-що»). Тому дефолтний `-fsanitize=undefined` звуження **не** ловить: у Clang для нього є окрема, не типова група `-fsanitize=implicit-conversion`, а в GCC санітайзерної перевірки на це нема взагалі — звуження стереже вже статичний аналіз попередженням `-Wconversion`. Ці дві речі легко сплутати, а вони різні: переповнення в обчисленні (UB, ловить UBSan) і звуження при присвоєнні (визначене реалізацією, ловить `-Wconversion`).

## Як санітайзер і статика наводять одне на одне

Знахідка санітайзера — це привід **повернутися до статики**. ASan довів, що `sum_first` виходить за межу на конкретних даних. Тепер варто прогнати `-fanalyzer` або `cppcheck` по всьому файлу: можливо, той самий зразок «цикл з `<=` до межі» є ще в трьох функціях, куди тест просто не зайшов. Динаміка знайшла **один** випадок на пройденому шляху; статика розмножить підозру на **всі** схожі місця.

І навпаки. Аналізатор повідомив «на гілці обробки помилки `p` може бути NULL» — але ви не певні, чи ця гілка взагалі досяжна. Напишіть тест, що навмисно подає вхід, який жене виконання в ту гілку, і зберіть під ASan. Якщо гілка досяжна й `p` справді NULL — отримаєте чітку аварію `SEGV on NULL`; якщо ні — підозра була хибною, і її гасять придушенням із поясненням. Так дві сітки доводять одна одній те, що поодинці лишалося б здогадом.

## Точкове виключення для «брудного» коду

Іноді код **навмисно** робить те, що ASan вважає порушенням, — типово робота з апаратними адресами або власний алокатор. Тоді конкретну функцію виключають з інструментування атрибутом:

```c
// доступ до апаратного регістру за фіксованою адресою — для ASan це «дикий»
// покажчик, але насправді це коректний MMIO
__attribute__((no_sanitize("address")))
uint32_t read_reg(uintptr_t addr) {
    return *(volatile uint32_t *)addr;
}
```

Правило те саме, що й для статичних придушень: виключення **завжди з причиною** в коментарі. Голе `no_sanitize` без пояснення — борг, який наступний читач не зможе оцінити.

## Кілька правил MISRA на коді

Коли «не падає» замало й потрібне «безпечно за будь-яких умов», над звичайним аналізом стає [MISRA-C](root:sf-release/static-analysis/detail) — підмножина мови, що відрізає небезпечне. Кілька правил у дії показують її дух.

**Правило 14.4 (required): керівний вираз `if` і циклу має бути по суті булевим.** Жодних покажчиків чи цілих у ролі умови — лише явне порівняння:

```c
// порушує 14.4 — покажчик і ціле як умова:
if (p)            { ... }
while (count)     { ... }

// сумісно — намір явний:
if (p != NULL)    { ... }
while (count != 0U) { ... }
```

Мета — прибрати плутанину «нуль/не нуль/NULL/істина», на якій так легко спіткнутися саме в критичному коді.

**Правило 17.7 (required): значення з не-`void` функції має бути використане.** Це родич ворнінга `-Wunused-result`, піднятий до сили правила:

```c
// порушує 17.7 — скільки прочитано, викинуто:
fread(buf, 1, n, f);

// сумісно — результат перевірено:
size_t got = fread(buf, 1, n, f);
if (got != n) { handle_short_read(); }

// якщо значення справді не потрібне — намір роблять явним:
(void)printf("ready\n");
```

Приведення `(void)` перед викликом — канонічний спосіб сказати компіляторові й аудиторові «ігную **навмисно**». Воно перетворює мовчазний недогляд на задокументований намір — а саме цього й вимагає сертифікація.

## Куди це ставити у збірці

Санітайзери не безкоштовні: інструментований код біжить у кілька разів повільніше й їсть помітно більше пам'яті. Тому їх **не вмикають у релізну прошивку** — у залізо йде звичайна оптимізована збірка без жодного інструментування. Місце санітайзерів — у хост-тестах, і найприродніше прогнати їх там автоматично, у неперервній збірці (англ. *continuous integration*, CI — сервер, що сам збирає й перевіряє кожен внесок).

Зручний підхід — **окрема тестова збірка під санітайзерами**, паралельна до звичайної:

```bash
# Звичайний прогін тестів — швидко, на кожен внесок:
gcc -O2 tests/*.c src/*.c -o run_tests && ./run_tests

# Санітайзерний прогін тих самих тестів — повільніше, теж у CI:
gcc -g -O1 -fsanitize=address,undefined tests/*.c src/*.c -o run_tests_san
ASAN_OPTIONS=detect_leaks=1 ./run_tests_san
```

Той самий набір тестів проганяють двічі: швидко (звичайна збірка) і прискіпливо (під ASan/UBSan). Перший дає миттєвий сигнал «логіка ціла», другий — гарантію «пам'ять і UB чисті на всіх пройдених шляхах». Змінна оточення `ASAN_OPTIONS` тонко керує поведінкою: `detect_leaks=1` вмикає пошук витоків, `halt_on_error=0` дозволяє зібрати всі знахідки за один прогін, а не спинятися на першій.

Тут і змикаються обидві сітки: що **краще покриті тести** (більше пройдених шляхів), то більше бачить санітайзер; а те, до чого тести не дійшли, добирає статичний аналіз, який не залежить від запуску. Слабке тестове покриття робить санітайзер майже сліпим — він стереже лише ті шляхи, якими реально пройшли.

Окрема обачність — із кодом, що працює з апаратними адресами. На хості справжніх регістрів нема, тож доступ до фіксованої адреси під ASan виглядає як «дикий» покажчик і дає хибну тривогу. Тому переносну логіку відділяють від доступу до заліза: на хості регістри підмінюють звичайними змінними (моками), а функції, що чіпають апаратні адреси напряму, або не тягнуть у хост-збірку взагалі, або виключають атрибутом `no_sanitize` — завжди з поясненням, чому це безпечно. Це той самий поділ «логіка окремо, залізо окремо», без якого ні [тести на хості](root:embedded/firmware-testing), ні санітайзери на прошивці не працюють.

Пастка наостанок: санітайзери й MISRA дивляться в **різні** боки. Санітайзер ловить те, що **сталося** на конкретному запуску; MISRA забороняє конструкції, що **могли б** колись зробити негаразд, навіть якщо на ваших тестах вони поводяться чемно. Тому одне одного вони не заміняють: на критичному проєкті потрібні обидва — динамічний доказ на даних і статична гарантія на всьому коді.
