# 📋 Специфікація двійкового дескриптора версії та структури .version_header

Ця специфікація визначає двійковий формат, правила розміщення в пам'яті, гарантії сумісності та програмний інтерфейс доступу до структури метаданих версії `version_info_t`, яка розміщується у виділеній секції виконуваного файлу `.version_header` (або в еквівалентній фіксованій секції двійкового образу прошивки). Формат призначений для швидкого й однозначного зчитування паспорта випуску зовнішніми утилітами (`readelf`, `objcopy`, Python-дамперами, серверами оновлень через радіоканал OTA та завантажувачами) без необхідності запуску коду програми чи розбору важких налагоджувальних таблиць DWARF.

## Базові вимоги та модель пам'яті

Для забезпечення надійної взаємодії між різнорідними інструментами аналізу та виконуваним кодом встановлюються такі системні інваріанти:

1. **Порядок байтів (Endianness):** дескриптор використовує прямий порядок байтів (англ. *Little-Endian*, молодший байт за меншою адресою) як канонічний формат представлення цілих чисел. Якщо компіляція виконується для архітектури з зворотним порядком байтів (Big-Endian), інструменти генерації коду зобов'язані переставляти байти полів у канонічний Little-Endian вигляд, щоб зовнішній аналізатор не залежав від архітектури мікропроцесора.
2. **Вирівнювання та розмір (Alignment and Size):** структура пакується з вирівнюванням по 4-байтовій межі (`#pragma pack(push, 4)` у мові C або атрибут `alignas(4)` у C++). Усі поля розташовані з фіксованими зсувами без непередбачуваного внутрішнього вирівнювання компілятора. Загальний розмір фіксованого заголовка становить рівно 72 байти (`0x48`).
3. **Незмінність у пам'яті (Read-Only):** секція маркується атрибутами `SHF_ALLOC` та `SHF_MERGE` у заголовку секції ELF і розміщується в енергонезалежній пам'яті (Flash / ROM). Секція ніколи не копіюється в оперативну пам'ять (RAM) під час старту програми, що економить пам'ять даних у мікроконтролерах.
4. **Захист від оптимізації компонувальника:** у скриптах компонувальника (Linker Script) секція обов'язково огортається командою `KEEP(*(.version_header))`, щоб прапорець оптимізації мертвого коду `--gc-sections` не видалив дескриптор, якщо на нього немає явних посилань із функції `main()`.

## Двійкова розкладка полів (Memory Layout)

Усі зміщення вказані у шістнадцятковому та десятковому форматах від початку секції `.version_header`:

| Зміщення (Offset) | Поле структури | Тип даних | Значення за замовчуванням | Опис та семантичні обмеження |
|---|---|---|---|---|
| `0x00 .. 0x03` (0..3) | `magic` | `uint32_t` | `0x56455253` | Магічне число `VERS` у кодуванні ASCII для швидкого сканування сирого дампу пам'яті або прошивки. |
| `0x04 .. 0x05` (4..5) | `struct_version` | `uint16_t` | `0x0001` | Версія формату заголовка. Поточна ревізія: `1`. Визначає правила інтерпретації наступних полів. |
| `0x06 .. 0x07` (6..7) | `flags` | `uint16_t` | `0x0000` | Бітове поле прапорців середовища та чистоти робочого дерева. |
| `0x08 .. 0x09` (8..9) | `major` | `uint16_t` | `0` | Старший номер версії SemVer (злам зворотної сумісності інтерфейсів або протоколу). |
| `0x0A .. 0x0B` (10..11) | `minor` | `uint16_t` | `0` | Молодший номер версії SemVer (додавання нової зворотно сумісної функціональності). |
| `0x0C .. 0x0D` (12..13) | `patch` | `uint16_t` | `0` | Номер патчу SemVer (зворотно сумісне виправлення виявлених дефектів та помилок). |
| `0x0E .. 0x0F` (14..15) | `reserved` | `uint16_t` | `0x0000` | Резервне поле для майбутнього розширення; вирівнює наступне поле до 4-байтової межі. |
| `0x10 .. 0x13` (16..19) | `commit_count` | `uint32_t` | `0` | Кількість комітів у гілці після найближчого тегу. Для офіційного релізу дорівнює нулю. |
| `0x14 .. 0x1B` (20..27) | `git_sha_short` | `char[8]` | `\0\0\0\0\0\0\0\0` | Перші 7 шістнадцяткових символів SHA-1/SHA-256 хешу коміту HEAD + завершальний нуль. |
| `0x1C .. 0x23` (28..35) | `timestamp` | `uint64_t` | `0` | Часова мітка створення коміту за стандартом Unix Epoch (кількість секунд з 1 січня 1970 року UTC). |
| `0x24 .. 0x43` (36..67) | `tag_name` | `char[32]` | `\0...` | Рядок назви найближчого тегу в репозиторії, доповнений нульовими байтами до 32 символів. |
| `0x44 .. 0x47` (68..71) | `crc32` | `uint32_t` | Розрахункове | Контрольна сума CRC-32 (IEEE 802.3 `0xEDB88320`), обчислена від байтів зсувів `0x00 .. 0x43`. |

## Семантика та бітові прапорці стану (Build Flags)

Поле `flags` розміром 16 бітів кодує умови, середовище та контекст формування двійкового файлу:

* `BIT 0 (0x0001) — BUILD_FLAG_DIRTY`: обов'язково встановлюється, якщо на момент запуску збірки робоче дерево або індекс Git містили бодай один модифікований, доданий чи видалений файл. Наявність цього біта свідчить про невідтворюваність вихідного коду та категорично забороняє використання бінарника як релізного артефакту.
* `BIT 1 (0x0002) — BUILD_FLAG_DEBUG`: встановлюється під час збірки з вимкненою оптимізацією (`-O0`) або ввімкненими динамічними перевірками пам'яті (Sanitizers, Assertions).
* `BIT 2 (0x0004) — BUILD_FLAG_PRERELEASE`: сигналізує про статус тестової версії (альфа, бета або кандидат у випуск `rc`).
* `BIT 3 (0x0008) — BUILD_FLAG_CI`: встановлюється конвеєром безперервної інтеграції (наприклад, раннером GitHub Actions чи GitLab CI) для розмежування автоматичних збірок від збірок, виконаних розробником локально.
* `BITS 4..15 (0xFFF0)`: зарезервовані для майбутніх розширень стандарту. При генерації структури ревізії 1 вони обов'язково повинні містити нульові значення.

## Алгоритм валідації та перевірки цілісності (Integrity Verification)

Для виявлення випадкового пошкодження пам'яті або некоректної прошивки флеш-пам'яті використовується стандартний алгоритм контрольної суми CRC-32 (поліном IEEE 802.3 зі значенням зворотного двійкового представлення `0xEDB88320`).

Процедура перевірки виконується за такими кроками:
1. Зчитуються перші 4 байти секції. Якщо вони не збігаються з константою `0x56455253` (`VERS`), структура вважається відсутньою або непідтримуваною.
2. Зчитується поле `struct_version`. Якщо значення більше за версію, яку підтримує аналізатор, структура відхиляється як несумісна (Forward Compatibility Guard).
3. Обчислюється CRC-32 від початкових 68 байтів структури (зсуви від `0x00` до `0x43` включно). Поле `crc32` при цьому не включається у розрахунок.
4. Якщо отримане значення збігається з 4 байтами, записаними за зсувом `0x44`, заголовок вважається цілісним і валідним.

## Правила еволюції формату (Forward and Backward Compatibility)

У міру розвитку інфраструктури розробки структура метаданих може розширюватися новими полями (наприклад, ідентифікатором цільової апаратної ревізії або криптографічним відкритим ключем підпису образу). Для забезпечення плавної сумісності діють такі правила:

- **Збереження базового префіксу:** перші 8 байтів структури (`magic`, `struct_version`, `flags`, `major`) залишаються незмінними в усіх наступних ревізіях специфікації. Будь-який аналізатор здатен прочитати номер версії самої структури та базові прапорці.
- **Мажорна зміна специфікації (`struct_version > 1`):** якщо нова версія структури вимагає зміни розташування наявних полів або збільшення загального розміру заголовка понад 72 байти, поле `struct_version` інкрементується. Завантажувачі старого покоління зобов'язані перевіряти це поле й відмовлятися від розбору незнайомих розширень, запобігаючи читанню некоректних адрес.
- **Використання резервного поля:** поле `reserved` за зсувом `0x0E` зарезервовано для розширення прапорців до 32-бітного діапазону без порушення 4-байтового вирівнювання решти полів.

## Політика верифікації завантажувачем (Bootloader Invariants)

Вбудований первинний або вторинний завантажувач (Bootloader) використовує дескриптор версії для реалізації захисних механізмів оновлення прошивки:

1. **Захист від відкату на застарілу версію (Anti-Rollback Protection):** завантажувач зчитує поля `major` та `minor` нового образу перед записом у робочий розділ флеш-пам'яті. Якщо нова версія менша за зафіксовану безпечну версію (наприклад, через виправлені вразливості безпеки), оновлення блокується на апаратному рівні.
2. **Блокування брудних бінарників у продакшні:** якщо пристрій працює в режимі захищеного виробничого середовища (Production Mode), наявність біта `BUILD_FLAG_DIRTY` у прапорцях нового образу викликає безумовну відмову завантажувача від передачі керування цій прошивці.
3. **Контроль цілісності образу:** завантажувач перевіряє `CRC32` дескриптора версії перед початком виконання основної програми. Якщо контрольна сума не збігається (наприклад, через збій живлення під час запису сторінки флеш-пам'яті), пристрій автоматично переходить у режим аварійного відновлення (Recovery Mode).

## Програмний інтерфейс реалізації (C та C++)

Нижче наведено еталонну реалізацію структур даних, констант і функцій валідації мовами C та C++.

```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define VERSION_HEADER_MAGIC 0x56455253U

#pragma pack(push, 4)
typedef struct {
    uint32_t magic;
    uint16_t struct_version;
    uint16_t flags;
    uint16_t major;
    uint16_t minor;
    uint16_t patch;
    uint16_t reserved;
    uint32_t commit_count;
    char     git_sha_short[8];
    uint64_t timestamp;
    char     tag_name[32];
    uint32_t crc32;
} version_descriptor_t;
#pragma pack(pop)

/* Обчислення стандарту CRC32 (IEEE 802.3) */
static uint32_t calculate_crc32(const uint8_t *data, size_t length) {
    uint32_t crc = 0xFFFFFFFFU;
    for (size_t i = 0; i < length; ++i) {
        crc ^= data[i];
        for (int j = 0; j < 8; ++j) {
            crc = (crc >> 1) ^ (0xEDB88320U & -(crc & 1U));
        }
    }
    return ~crc;
}

/* Валідація структури дескриптора */
bool validate_version_descriptor(const version_descriptor_t *desc) {
    if (!desc) return false;
    if (desc->magic != VERSION_HEADER_MAGIC) return false;
    if (desc->struct_version != 1U) return false;

    /* Обчислення контрольної суми перших 68 байтів структури */
    uint32_t expected_crc = calculate_crc32((const uint8_t *)desc, 68);
    return (desc->crc32 == expected_crc);
}
```
```cpp
#pragma once

#include <cstdint>
#include <span>
#include <string_view>
#include <optional>
#include <array>

namespace firmware_abi {

inline constexpr std::uint32_t magic_value = 0x56455253U;

#pragma pack(push, 4)
struct VersionDescriptor {
    std::uint32_t magic;
    std::uint16_t struct_version;
    std::uint16_t flags;
    std::uint16_t major;
    std::uint16_t minor;
    std::uint16_t patch;
    std::uint16_t reserved;
    std::uint32_t commit_count;
    std::array<char, 8> git_sha_short;
    std::uint64_t timestamp;
    std::array<char, 32> tag_name;
    std::uint32_t crc32;
};
#pragma pack(pop)

class VersionValidator {
public:
    static constexpr std::uint32_t compute_crc32(std::span<const std::uint8_t> data) noexcept {
        std::uint32_t crc = 0xFFFFFFFFU;
        for (std::uint8_t b : data) {
            crc ^= b;
            for (int j = 0; j < 8; ++j) {
                crc = (crc >> 1) ^ (0xEDB88320U & -(crc & 1U));
            }
        }
        return ~crc;
    }

    [[nodiscard]] static bool is_valid(const VersionDescriptor& desc) noexcept {
        if (desc.magic != magic_value || desc.struct_version != 1U) {
            return false;
        }
        auto payload = std::span<const std::uint8_t>(
            reinterpret_cast<const std::uint8_t*>(&desc),
            sizeof(VersionDescriptor) - sizeof(desc.crc32)
        );
        return desc.crc32 == compute_crc32(payload);
    }
};

} // namespace firmware_abi
```

## Інтерфейс утиліт зовнішнього аналізу (CLI & Python)

Зовнішні сервери розгортання, складальні конвеєри та виробничі випробувальні стенди читають метадані двома основними способами:

1. **Через стандартний інструментарій GNU Binutils або LLVM:**
   Команда `readelf -x .version_header firmware.elf` виводить шістнадцятковий дамп структури безпосередньо з об'єктного файлу. Команда `llvm-objdump --section=.version_header -s firmware.elf` повертає вміст байтів секції.
2. **Через автономний скрипт прямого розбору двійкового образу:**
   Скрипт читає перші блоки бінарного файлу (наприклад, сирого `.bin` образу прошивки), знаходить сигнатуру `0x56455253`, розпаковує двійкові поля та проводить автоматичну верифікацію контрольної суми:

```py
import struct
import zlib
import sys

def parse_firmware_binary(file_path):
    with open(file_path, "rb") as f:
        data = f.read()

    # Пошук магічного числа 'VERS' у бінарному файлі
    offset = data.find(b"VERS")
    if offset == -1:
        raise ValueError("Секцію .version_header не знайдено в двійковому файлі!")

    header_bytes = data[offset : offset + 72]
    if len(header_bytes) < 72:
        raise ValueError("Пошкоджений або усічений заголовок версії!")

    # Розпакування формату Little-Endian:
    # I (magic), H (struct_ver), H (flags), H (major), H (minor),
    # H (patch), H (reserved), I (commits), 8s (sha), Q (timestamp),
    # 32s (tag), I (crc32)
    fmt = "<IHHHHHHI8sQ32sI"
    fields = struct.unpack(fmt, header_bytes)

    magic, s_ver, flags, maj, min_, patch, res, commits, sha, ts, tag, crc = fields

    # Валідація контрольної суми CRC32 від перших 68 байтів
    computed_crc = zlib.crc32(header_bytes[:68])
    if crc != computed_crc:
        raise ValueError(f"Помилка CRC32: очікувалося {hex(computed_crc)}, отримано {hex(crc)}")

    is_dirty = bool(flags & 0x0001)
    tag_clean = tag.decode("utf-8", errors="replace").rstrip("\0")
    sha_clean = sha.decode("utf-8", errors="replace").rstrip("\0")

    return {
        "version": f"{maj}.{min_}.{patch}",
        "commits_ahead": commits,
        "git_sha": sha_clean,
        "tag": tag_clean,
        "is_dirty": is_dirty,
        "timestamp_unix": ts,
    }
```

Такий підхід забезпечує повну автономність засобів аудиту: сервіс доставки оновлень, стенд прошивки на виробничій лінії або завантажувач у польових умовах миттєво отримують точний паспорт пристрою без виконання коду та без завантаження повного налагоджувального контексту.
