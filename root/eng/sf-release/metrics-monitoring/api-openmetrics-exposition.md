# 📋 Специфікація текстового формату OpenMetrics / Prometheus

<preknowlist>
- [Метрики й числовий моніторинг](root:sf-release/metrics-monitoring) — базове розуміння типів метрик (Counter, Gauge, Histogram, Summary) та багатовимірних міток.
</preknowlist>

Формат передачі числових показників OpenMetrics (IETF RFC Draft) та сумісний із ним текстовий формат Prometheus Exposition Format v0.0.4 є промисловими стандартами для експорту та збору телеметрії. Формат оптимізований для простоти генерації в користувацьких процесах, потокового парсингу без виділення пам'яті (streaming parsing) та ефективного стиснення при передачі через HTTP.

## Загальна структура документа

Документ є текстовим потоком у кодуванні **UTF-8**, що складається з окремих рядків, розділених символом переводу рядка `\n` (LF, байт `0x0A`). Символи повернення каретки `\r` (CR) у стандарті OpenMetrics заборонені.

Кожен рядок належить до одного з трьох типів:
1. **Рядок метаданих (Metadata Line):** Починається з символу решітки `#` і містить службову інформацію (`HELP`, `TYPE`, `UNIT`).
2. **Рядок вимірювання (Sample Line):** Містить назву метрики, необов'язковий набір міток у фігурних дужках, числове значення та необов'язкову часову мітку.
3. **Маркер завершення (EOF Marker):** Обов'язковий фінальний рядок `# EOF\n` (лише в OpenMetrics).

```text
# HELP http_requests_total Загальна кількість оброблених HTTP-запитів
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 10482 1625097600000
http_requests_total{method="POST",status="500"} 12 1625097600000
# EOF
```

## Рядки метаданих

Метадані описують семантику метрики для систем візуалізації та зберігання. Метадані групуються безпосередньо перед першим рядком вимірювань даної метрики.

### 1. Опис призначення (# HELP)

Задає текстове пояснення сенсу метрики для оператора.

```text
# HELP <metric_name> <текстовий_опис>
```

* Порядок: необов'язковий (рекомендований).
* Правила екранування в описі:
  * Зворотний слеш `\` кодується як `\\`.
  * Перевід рядка `\n` кодується як `\n`.

### 2. Тип даних (# TYPE)

Визначає семантичний тип метрики.

```text
# TYPE <metric_name> <type>
```

Допустимі значення `<type>`:

| Тип | Семантика | Допустимі суфікси та правила |
| :--- | :--- | :--- |
| `counter` | Монотонний лічильник, що тільки зростає або скидається в 0 при перезапуску | В OpenMetrics назва метрики **мусить** закінчуватися суфіксом `_total` (наприклад, `requests_total`) |
| `gauge` | Числовий рівень, що може довільно зростати та спадати | Не має обов'язкових суфіксів (наприклад, `memory_allocated_bytes`) |
| `histogram` | Кумулятивна гістограма розподілу значень за кошиками | Генерує ряди з суфіксами `_bucket`, `_sum`, `_count`, `_created` |
| `summary` | Статистичний підсумок із квантилями, обчисленими на клієнті | Генерує ряди з міткою `quantile`, а також `_sum`, `_count`, `_created` |
| `stateset` | Дискретний набір взаємовиключних або бітових станів | Кожен стан передається значенням `1` або `0` (наприклад, `system_state{state="ready"} 1`) |
| `info` | Статична інформація про реліз, збірку чи оточення | Значення завжди фіксоване `1` (наприклад, `build_info{version="1.4.2"} 1`) |
| `gaugehistogram` | Гістограма, чиї кошики є покажчиками (gauge) | Використовується для розподілів миттєвих станів (наприклад, розміри черг) |
| `unknown` / `untyped` | Нетипізована метрика (усталене значення при відсутності `# TYPE`) | Застосовується для зворотної сумісності зі старими системами |

### 3. Одиниця вимірювання (# UNIT)

Задає фізичну одиницю вимірювання (лише в OpenMetrics).

```text
# UNIT <metric_name> <unit>
```

* Базові одиниці вимірювання мають відповідати системі SI: `seconds`, `bytes`, `volts`, `amperes`, `meters`, `celsius`, `ratio`.
* Скорочення (наприклад, `ms`, `MB`, `KB`) заборонені: усі значення нормалізуються до базових одиниць (`seconds`, `bytes`).
* Суфікс одиниці вимірювання має бути присутнім у назві метрики: наприклад, для `# UNIT disk_read_bytes bytes` назва метрики закінчується на `_bytes`.

## Синтаксис рядка вимірювання (Sample Line)

Рядок вимірювання задає конкретну точку часового ряду:

```text
<metric_name>[{<label_name>="<label_value>", ...}] <value> [<timestamp>] [# {<exemplar_labels>} <exemplar_val> [<exemplar_ts>]]
```

### 1. Правила іменування метрик

* Допустимі символи для назви метрики: `[a-zA-Z_:][a-zA-Z0-9_:]*` у форматі Prometheus, та `[a-zA-Z_][a-zA-Z0-9_]*` у OpenMetrics.
* Двокрапка `:` зарезервована для правил користувацької агрегації (Recording Rules) на сервері TSDB і не повинна використовуватися в прямій інструментації клієнтських бібліотек.
* Суфікси `_total` (для counter), `_bucket`, `_sum`, `_count`, `_created` (для histogram/summary) зарезервовані за відповідними типами.

### 2. Назви та значення міток (Labels)

Мітки задають багатовимірні атрибути вимірювання.

* **Назва мітки (`label_name`):** Строго відповідає регулярному виразу `[a-zA-Z_][a-zA-Z0-9_]*`.
* **Службовий префікс `__`:** Назви міток, що починаються з двох підкреслень (наприклад, `__address__`, `__name__`), зарезервовані для внутрішнього використання сервером Prometheus під час конфігурації скрейпу та релейблінгу (relabeling). Клієнтським бібліотекам заборонено генерувати мітки з префіксом `__`.
* **Значення мітки (`label_value`):** Довільний рядок у кодуванні UTF-8, взятий у подвійні лапки `"..."`.
* **Правила екранування всередині значень міток:**
  * Подвійна лапка `"` кодується як `\"`.
  * Зворотний слеш `\` кодується як `\\`.
  * Перевід рядка кодується як `\n`.

### 3. Числове значення (`value`)

* Значення записується як 64-бітне дійсне число з плаваючою комою (IEEE 754 float64).
* Підтримується десятковий запис (`42`, `123.456`, `0.001`) та експоненційна нотація (`1.5e-3`, `4.8e+6`).
* **Спеціальні числові константи:**
  * `NaN` — Not a Number (невизначене значення або помилка розрахунку).
  * `+Inf` — позитивна нескінченність (обов'язкова для останнього кошика гістограми).
  * `-Inf` — негативна нескінченність.

### 4. Мітка часу (`timestamp`)

* **Необов'язкове поле:** Якщо таймстемп відсутній, сервер моніторингу автоматично призначає вимірюванню час початку виконання скрейп-запиту.
* **Формат у Prometheus 0.0.4:** Ціле число мілісекунд від початку Unix-епохи (1 січня 1970 00:00:00 UTC). Приклад: `1625097600000`.
* **Формат у OpenMetrics:** Дійсне число секунд із десятковою дробовою частиною (наносекундна точність). Приклад: `1625097600.000123456`.

## Екземпляри (Exemplars)

Стандарт OpenMetrics ввів механізм **екземплярів (Exemplars)** — пряму прив'язку конкретного вимірювання метрики до розподіленого трейсингу.

Коли додаток фіксує повільний запит у гістограмі, він може прикріпити до рядка кошика ідентифікатор трасування `trace_id` та `span_id`:

```text
http_request_duration_seconds_bucket{le="0.5"} 9812 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 0.482 1625097600.123
```

Синтаксис екземпляра:
* Відокремлюється від основного значення символом решітки `#`.
* Містить мітки екземпляра у фігурних дужках `{trace_id="..."}`.
* Містить точне виміряне значення вибірки (`0.482 с`).
* Необов'язковий таймстемп моменту спостереження.

Завдяки екземплярам інженер на графіку перцентилів у Grafana може клікнути на окрему точку піку p99 і миттєво відкрити повне дерево розподіленого трейсингу в Jaeger чи Tempo для цього конкретного запиту.

## Контракти спеціалізованих типів

### 1. Контракт типу StateSet

Тип `stateset` описує сутність, що може перебувати у фіксованому наборі дискретних станів.
Кожен можливий стан експортується окремим часовим рядом із міткою назви стану та двійковим значенням `1` (активний) або `0` (неактивний):

```text
# HELP daemon_status Поточний стан системного демона
# TYPE daemon_status stateset
daemon_status{daemon_status="starting"} 0
daemon_status{daemon_status="running"} 1
daemon_status{daemon_status="stopping"} 0
daemon_status{daemon_status="failed"} 0
```

### 2. Контракт типу Info

Тип `info` передає метадані про додаток, версію бібліотек або середовище розгортання, які не змінюються під час роботи процесу:

```text
# HELP node_uname_info Інформація про версію ядра Linux
# TYPE node_uname_info info
node_uname_info{sysname="Linux",release="5.15.0-76-generic",version="#83-Ubuntu",machine="x86_64"} 1
```

Значення метрики типу `info` завжди строго дорівнює `1`. У PromQL такі метрики використовуються для об'єднання (Join) з іншими часовими рядами через оператор `* on (instance) group_left(version)`.

### 3. Контракт типу GaugeHistogram

Тип `gaugehistogram` використовується для кумулятивних гістограм, значення кошиків яких не монотонно накопичуються від старту, а відображають миттєвий розподіл (наприклад, розподіл розмірів пакетів, що знаходяться в мережевих буферах прямо зараз). На відміну від звичайної гістограми, значення кошиків `gaugehistogram` можуть зменшуватися при звільненні буферів.

## Рідні експоненційні гістограми (Native / Exponential Histograms)

У сучасних версіях Prometheus та OpenMetrics впроваджено формат **рідних гістограм (Native Histograms)**. Замість фіксованих користувацьких меж кошики розраховуються динамічно за експоненційною сіткою: `boundary[i] = 2^(i · 2^(-scale))`.

* **Параметр масштабу (`scale`):** Ціле число в діапазоні від `-4` до `8`. Задає точність і кількість кошиків на ступінь двійки (при `scale = 3` кожен фактор 2 розбивається на 8 кошиків із постійною відносною похибкою ~8.6%).
* **Нульовий кошик (`zero_count`, `zero_threshold`):** Окремий лічильник для спостережень, близьких до нуля (наприклад, затримки менше 10 мкс), щоб уникнути нескінченної кількості дрібних експоненційних кошиків.
* **Стиснення спанів (Positive / Negative Spans):** Замість передачі сотень порожніх кошиків передаються лише непорожні інтервали у вигляді списку довжин і зсувів, що скорочує розмір гістограми в 10–20 разів.

## Інтеграція та трансляція з OpenTelemetry (OTel Bridge)

Системи, побудовані на базі OpenTelemetry Collector, виконують автоматичну двосторонню трансляцію між моделями даних OpenMetrics та OpenTelemetry Metric Data Model:

1. **Трансляція назв метрик (Name Sanitization):**
   Крапки в ієрархічних іменах OpenTelemetry замінюються на підкреслення (наприклад, `http.server.duration` → `http_server_duration_seconds`). Якщо метрика містить одиницю вимірювання, вона додається як суфікс згідно з правилами OpenMetrics.
2. **Трансляція атрибутів ресурсів (Resource Attributes):**
   Глобальні атрибути оточення (`service.name`, `k8s.pod.name`) автоматично конвертуються у мітки `service="order-service"` або додаються через спеціальний службовий ряд `target_info`.
3. **Трансляція агрегації (Cumulative vs Delta Temporality):**
   Prometheus вимагає строго кумулятивної моделі (Cumulative Temporality). Якщо джерело OTLP генерує дельти за інтервал (Delta Temporality), колектор OpenTelemetry використовує процесор `cumulativetodelta` для збереження накопичувальних значень перед формуванням скрейп-ендпоінта.

## Протокол Pushgateway для пакетних завдань

Для короткоживучих процесів (Cron jobs, ETL-скрипти, тренування моделей ML), які завершуються швидше за інтервал скрейпу, застосовують проміжний буфер **Prometheus Pushgateway**.

### 1. Ендпоінти публікації метрик

```http
PUT /metrics/job/<job_name>[/<label_name>/<label_value>...]
POST /metrics/job/<job_name>[/<label_name>/<label_value>...]
DELETE /metrics/job/<job_name>[/<label_name>/<label_value>...]
```

* **Метод `PUT`:** Повністю замінює всі метрики для заданої комбінації `job` та міток екземпляра.
* **Метод `POST`:** Додає нові метрики або оновлює лише вказані часові ряди, зберігаючи попередньо надіслані.
* **Метод `DELETE`:** Видаляє метрики завершеного завдання, усуваючи появу мертвих рядів у системі моніторингу.
* **Base64-кодування для слешів у мітках:** Якщо значення мітки містить слеш `/` (наприклад, шлях `/usr/local/bin`), значення кодується у форматі URL-safe Base64 без доповнення та предваряється суфіксом `@base64`:
  ```http
  PUT /metrics/job/backup_job/path@base64/L3Zhci9kYXRh HTTP/1.1
  ```

## Протокол Prometheus Remote Write

Для довгострокового зберігання метрик у масштабованих сховищах (Cortex, Thanos, M3DB, VictoriaMetrics) Prometheus надсилає збережені блоки через протокол **Remote Write**:

* **Транспорт:** HTTP POST `/api/v1/write`.
* **Формат серіалізації:** Google Protocol Buffers (`remote.proto`), стиснені алгоритмом Google Snappy.
* **Пейлоад:** Батчі часових рядів `TimeSeries`, що містять масив пар міток `Label` та масив вибірок `Sample { double value; int64 timestamp; }`.
* **Вимоги до черги:** Клієнт Remote Write реалізує буферизацію у пам'яті з відкиданням застарілих даних за принципом Ring Buffer при недоступності віддаленого сховища, та експоненційне повторення (exponential backoff) при отриманні статус-кодів `429 Too Many Requests` або `503 Service Unavailable`.

## Мережевий протокол та HTTP-транспорт

Збір метрик відбувається через стандартний протокол HTTP/1.1 або HTTP/2 за методом `GET`.

### 1. Узгодження контенту (Content Negotiation)

Клієнт моніторингу надсилає заголовок `Accept`:

```http
GET /metrics HTTP/1.1
Host: service.internal:8080
Accept: application/openmetrics-text; version=1.0.0; charset=utf-8, text/plain; version=0.0.4; q=0.5
```

Сервер відповідає відповідним заголовком `Content-Type`:

```http
HTTP/1.1 200 OK
Content-Type: application/openmetrics-text; version=1.0.0; charset=utf-8
Content-Length: 4820
Cache-Control: no-cache, no-store, must-revalidate
Connection: close

# HELP http_requests_total Загальна кількість запитів
# TYPE http_requests_total counter
http_requests_total{status="200"} 42
# EOF
```

### 2. Стиснення трафіку (Compression)

Для зменшення мережевого трафіку скрейпери підтримують заголовок `Accept-Encoding: gzip, deflate, zstd`. Оскільки текстовий формат містить велику кількість повторюваних імен метрик і ключів міток, алгоритм gzip стискає вихідний документ у **5–10 разів** (коефіцієнт стиснення понад 85%).

## Синтетичні метрики та контракт скрейпера

Під час кожного опитування цільового інстансу сервер моніторингу автоматично генерує набір **службових синтетичних метрик**, що описують якість і результат самої операції збору:

1. `up`:
   * Значення `1`: ендпоінт відповів статус-кодом `200 OK`, документ успішно спарсено без синтаксичних помилок і досягнуто маркера `# EOF`.
   * Значення `0`: тайм-аут з'єднання, помилка DNS, скидання TCP-сесії або некоректний формат відповіді.
2. `scrape_duration_seconds`:
   * Час, витрачений сервером моніторингу на виконання HTTP-запиту, завантаження пейлоаду та збереження точок у TSDB.
3. `scrape_samples_scraped`:
   * Кількість вимірювань, витягнутих із документа під час даного скрейпу.
4. `scrape_samples_post_metric_relabeling`:
   * Кількість вимірювань, що залишилися після проходження через правила фільтрації (metric relabeling).
5. `scrape_series_added`:
   * Кількість нових часових рядів, створених у базі даних уперше під час цього опитування.

## Конфігурація правил релейблінгу (Relabeling Engine)

Релейблінг — це декларативна система трансформації міток перед збереженням метрик у сховище TSDB або маршрутизацією сповіщень.

```yaml
# Приклад конфігурації скрейпу з релейблінгом у Prometheus:
scrape_configs:
  - job_name: 'backend-services'
    scrape_interval: 15s
    scrape_timeout: 10s
    metrics_path: '/metrics'
    
    # 1. Трансформація міток інфраструктури (Target Relabeling)
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: service
        action: replace
      - source_labels: [__meta_kubernetes_namespace]
        target_label: env
        regex: 'prod-(.*)'
        replacement: '${1}'
        action: replace
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        regex: 'true'
        action: keep

    # 2. Фільтрація та нормалізація метрик (Metric Relabeling)
    metric_relabel_configs:
      # Видалення небезпечних міток із високою кардинальністю
      - regex: '^(user_id|session_token|raw_ip)$'
        action: labeldrop
      # Відкидання непотрібних метрик налагодження
      - source_labels: [__name__]
        regex: 'debug_.*'
        action: drop
```

Допустимі операції релейблінгу:
* `replace`: застосовує регулярний вираз `regex` до `source_labels` та записує результат шаблону `replacement` у `target_label`.
* `keep`: зберігає лише ті таргети або ряди, чиє значення `source_labels` відповідає `regex`; решта відкидається.
* `drop`: відкидає таргети або ряди, що відповідають `regex`.
* `labeldrop`: видаляє з вимірювання всі мітки, назва яких відповідає заданому `regex`.
* `labelkeep`: зберігає у вимірюванні лише ті мітки, назва яких відповідає заданому `regex`.
* `hashmod`: обчислює MD5-хеш від `source_labels` і бере залишок від ділення на `modulus` (використовується для шардингу скрейперів).

## Автомат станів потокового лексера OpenMetrics

Для швидкого парсингу метрик без завантаження всього документа в пам'ять застосовують скінченний автомат (Finite State Machine, FSM), що обробляє потік байтів за один прохід:

```text
               ┌──────────────┐
               │  LINE_START  │
               └──────┬───────┘
          #           │           letter / '_'
     ┌────────────────┴────────────────────────┐
     ▼                                         ▼
┌──────────────┐                      ┌─────────────────┐
│ METADATA_TAG │                      │   METRIC_NAME   │
│ (HELP/TYPE)  │                      └────────┬────────┘
└──────┬───────┘                               │ '{'
       │                                       ▼
       │                              ┌─────────────────┐
       │                              │   LABEL_NAME    │
       │                              └────────┬────────┘
       │                                       │ '=' '"'
       │                                       ▼
       │                              ┌─────────────────┐
       │                              │   LABEL_VALUE   │
       │                              └────────┬────────┘
       │                                       │ '}'
       │                                       ▼
       │                              ┌─────────────────┐
       │                              │  SAMPLE_VALUE   │
       │                              └────────┬────────┘
       │                                       │ '\n'
       └──────────────────┬────────────────────┘
                          ▼
                  [ Збереження ряду ]
```

Стани парсера:
1. `STATE_LINE_START`: очікування першого символу рядка. Пропускає порожні рядки. Якщо символ `#` — перехід у стан парсингу метаданих або коментаря; якщо літера — старт назви метрики.
2. `STATE_METRIC_NAME`: читання символів ідентифікатора метрики до появи пробілу (значення) або символу `{` (список міток).
3. `STATE_LABEL_NAME`: читання назви мітки. Завершується символом `=`.
4. `STATE_LABEL_VALUE`: читання рядка в подвійних лапках із розпізнаванням екранованих послідовностей `\\`, `\"`, `\n`. Завершується символом `"`.
5. `STATE_VALUE`: парсинг 64-бітного числа з плаваючою комою (за допомогою високошвидкісних безвидільних алгоритмів, таких як `fast_float` чи `dtoa`).
6. `STATE_EXEMPLAR`: читання блоку екземпляра після символу `#`.
7. `STATE_LINE_END`: перевірка коректності завершення рядка символом `\n` та емісія готової точки часового ряду у чергу обробки.

## Граматика формату в нотації EBNF

Нижче наведено формальну граматику формату OpenMetrics у розширеній нотації Бекуса — Наура (EBNF):

```ebnf
openmetrics_doc = { line } , eof_line ;

line = metadata_line | sample_line | empty_line ;

empty_line = "\n" ;
eof_line   = "# EOF" , "\n" ;

metadata_line = "#" , " " , ( help_decl | type_decl | unit_decl ) , "\n" ;
help_decl     = "HELP" , " " , metric_name , " " , text_description ;
type_decl     = "TYPE" , " " , metric_name , " " , type_name ;
unit_decl     = "UNIT" , " " , metric_name , " " , unit_name ;

sample_line = metric_name , [ "{" , label_list , "}" ] , " " , number_value , [ " " , timestamp ] , [ " " , exemplar ] , "\n" ;

exemplar    = "#" , " " , "{" , label_list , "}" , " " , number_value , [ " " , timestamp ] ;

label_list  = label_pair , { "," , label_pair } ;
label_pair  = label_name , "=" , '"' , label_value , '"' ;

metric_name = ( letter | "_" ) , { letter | digit | "_" } ;
label_name  = ( letter | "_" ) , { letter | digit | "_" } ;

label_value      = { utf8_char_escaped } ;
text_description = { utf8_char_escaped } ;

number_value = [ "+" | "-" ] , ( float_literal | "NaN" | "Inf" ) ;
timestamp    = [ "+" | "-" ] , digit , { digit } , [ "." , digit , { digit } ] ;

letter = "A" ... "Z" | "a" ... "z" ;
digit  = "0" ... "9" ;
```

## Правила парсингу та діагностика помилок

Клієнтський парсер або агент збору телеметрії повинен дотримуватися таких обов'язкових інваріантів:

1. **Одноразовість метаданих:** Для однієї назви метрики рядки `# HELP` та `# TYPE` можуть з'являтися у документі щонайбільше один раз. Повторне оголошення типу для тієї самої метрики вважається фатальною синтаксичною помилкою `ERR_DUPLICATE_METRIC_METADATA`.
2. **Невід'ємність та монотонність кошиків:** Усі кошики гістограми з однаковим набором міток мають бути впорядковані за зростанням значення `le`. Значення лічильників у кошиках повинні монотонно зростати: `bucket[i] <= bucket[i+1]`. Якщо виявлено порушення монотонності, гістограма вважається пошкодженою (`ERR_NON_MONOTONIC_HISTOGRAM_BUCKETS`) і відкидається.
3. **Обов'язковість кошика `+Inf`:** Гістограма без кошика `le="+Inf"` є невалідною (`ERR_MISSING_INF_BUCKET`), оскільки унеможливлює точний розрахунок загальної кількості спостережень та обчислення перцентилів.
4. **Стійкість до невідомих типів:** Якщо парсер зустрічає рядок `# TYPE` з невідомим типом (наприклад, тип, доданий у майбутніх ревізіях стандарту), вимірювання цієї метрики повинні інтерпретуватися як `untyped` без переривання парсингу решти документа.
5. **Захист від нескінченних рядків:** Парсер повинен обмежувати максимальну довжину окремого рядка (типово 64 КБ) та максимальний сумарний розмір документа (типово 32 МБ), щоб запобігти атакам на вичерпання пам'яті (`ERR_EXCEEDED_MAX_LINE_LENGTH`).
6. **Обов'язковість маркера EOF:** У потоці з `Content-Type: application/openmetrics-text` відсутність фінального рядка `# EOF\n` сигналізує про обрив TCP-з'єднання або передчасне завершення буфера експортера (`ERR_PREMATURE_STREAM_TRUNCATION`), що змушує систему збору відкинути весь отриманий батч даних для збереження атомарності скрейпу.
