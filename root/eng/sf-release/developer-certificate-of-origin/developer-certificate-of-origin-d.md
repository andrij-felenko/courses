# Під якою ліцензією випускати своє: DCO, CLA, подвійне ліцензування

<preknowlist>
- [Ліцензії відкритого коду](root:sys-notary/open-source-licenses) — дозвільні та копілефтні ліцензії, юридична природа прав і зобов'язань.
- [Моделі володіння кодом](root:sf-release/code-ownership-models) — розподіл авторських прав між окремими інженерами, корпораціями та некомерційними фондами.
- [Контроль версій](root:sf-release/version-control) — структура комітів, авторів, комітерів і метаданих у Git.
- [Неперервна інтеграція та доставка](root:sf-release/ci-cd) — автоматизовані пайплайни перевірок якості, комплаєнсу та безпеки.
</preknowlist>

Коли інженер уперше публікує вихідний код у публічному репозиторії, виникає оманливе враження, що код просто стає доступним усім охочим без жодних правових наслідків. У правовому полі більшості юрисдикцій світу — відповідно до Бернської конвенції про охорону літературних і художніх творів — комп'ютерна програма визнається об'єктом авторського права тієї ж миті, коли її текст записано на постійний носій. Авторське право (англ. *copyright*) виникає автоматично й неподільно належить автору коду або його роботодавцю, якщо код створено в межах трудових обов'язків як службовий твір. Публікація коду під відкритою ліцензією на кшталт [MIT](root:sys-notary/open-source-licenses), [Apache-2.0](root:sys-notary/open-source-licenses) чи [GPLv3](root:sys-notary/open-source-licenses) не є відмовою від права власності: це лише односторонній юридичний дозвіл невизначеному колу осіб використовувати, модифікувати та поширювати вашу інтелектуальну власність на чітко визначених умовах.

Справжня інженерна та правова складність починається тоді, коли в репозиторій надходить перший Pull Request від стороннього розробника. Інженер із сусіднього міста чи іншого континенту надсилає триста рядків, які виправляють критичну гонку станів у драйвері чи оптимізують обробку запитів. Коли мейнтейнер натискає кнопку злиття (*Merge*), у репозиторії виникає спільна складена праця (англ. *aggregate work* / *joint work*). Авторське право на ці триста рядків залишається у контриб'ютора. Якщо ж автор ненавмисно скопіював алгоритм із закритої бази коду своєї компанії або порушив угоду про нерозголошення, увесь спільний репозиторій миттєво стає юридично забрудненим (англ. *tainted*), наражаючи всіх користувачів на ризик судових позовів.

Щоб масштабувати розробку без ризику правового колапсу та зберегти за собою архітектурний контроль над майбутнім продукту, індустрія програмної інженерії створила три ключові механізми: децентралізоване **Свідоцтво про походження коду (DCO)** з підписом `Signed-off-by`, централізовану **Угоду контриб'ютора (CLA)** та бізнес-моделі **подвійного ліцензування (Dual Licensing)**.

## Анатомія авторського права у відкритому коді

Щоб зрозуміти причини появи DCO та CLA, необхідно розібрати правову механіку, яка керує кожним символом у Git-репозиторії.

Авторське право у сфері програмного забезпечення складається з двох принципово різних пакетів прав:
1. **Особисті немайнові права (Moral Rights):** Право визнаватися автором твору (право авторства) та право вимагати збереження цілісності твору без викривлень. У більшості континентальних правових систем (зокрема в Україні, Німеччині, Франції) ці права є невідчужуваними: інженер не може продати чи подарувати свій статус автора ні за які гроші.
2. **Майнові (виключні) права (Economic Rights):** Право дозволяти або забороняти копіювання, компіляцію, розповсюдження, модифікацію, публічний показ та комерційне використання коду. Саме майнові права є предметом ліцензійних угод та комерційного обігу.

Коли проєкт розвивається як відкритий, кожен сторонній внесок несе в собі неявну юридичну невизначеність. Якщо контриб'ютор надіслав патч електронною поштою чи через вебінтерфейс, чи означає це, що він надав проєкту безвідкличне право на цей код? Чи мав він право віддавати код, якщо його трудовий контракт містить пункт про повну передачу всієї інтелектуальної власності роботодавцю (*Invention Assignment Agreement*)?

```text
+-------------------------------------------------------------------------------+
|                    РОЗПОДІЛ ПРАВ НА ВИТРИМКУ ЧАСУ                            |
|                                                                               |
|  [Розробник у компанії X] -----> Написав 200 рядків коду (Службовий твір)     |
|          |                                                                    |
|          v                                                                    |
|  [Майнові права належать X] ---> Працівник відправляє PR у відкритий проєкт Y |
|          |                                                                    |
|          v                                                                    |
|  [Проєкт Y зливає PR] ---------> Юридична колізія: компанія X може вимагати   |
|                                  негайного видалення коду та компенсацій      |
+-------------------------------------------------------------------------------+
```

### Пастка спільного володіння (Joint Work)

Якщо в репозиторії накопичується внесок від сотень незалежних інженерів, кодова база перетворюється на складну мозаїку. У проєкті під чистою відкритою ліцензією змінити ліцензійні умови (наприклад, перейти з [GPLv2](root:sys-notary/open-source-licenses) на [GPLv3](root:sys-notary/open-source-licenses) або на комерційну ліцензію) неможливо без отримання письмової згоди від **100% авторів усіх фрагментів коду**, які коли-небудь потрапили до репозиторію. Якщо хоча б один розробник, який написав двадцять рядків десять років тому, не виходить на зв'язок або виступає проти, реліцензування кодової бази заблоковано назавжди.

Саме з цією проблемою зіткнулося ядро Linux: перехід із GPLv2 на GPLv3 виявився фізично неможливим, оскільки над ядром працювали понад двадцять тисяч розробників із сотень різних корпорацій, і зібрати стовідсоткову згоду було нереально.

## Походження коду та уроки кризи SCO проти IBM

Проблема юридичної чистоти походження довго лишалася суто теоретичною для більшості інженерів, поки на початку 2000-х років не вибухнув найбільший судовий процес в історії вільного софту — справа *The SCO Group проти IBM*.

Історія цього конфлікту та те, як загроза мільярдних позовів проти користувачів Linux змусила Лінуса Торвальдса та інженерну спільноту створити перший формальний механізм перевірки походження, детально викладена у нарисі [Народження DCO: судова битва SCO проти IBM і порятунок ядра Linux](root:sf-release/developer-certificate-of-origin/hist-sco-v-ibm-origins.md).

Головний урок тієї кризи полягав у тому, що відкритій кодовій базі потрібен нерозривний, документально зафіксований **ланцюг передачі прав (Chain of Custody)**. Кожен коміт мусить нести в собі юридично обов'язкову заяву розробника: «Я маю законне право передати цей код проєкту».

![Ланцюг походження коду в ядрі Linux від автора до апстриму](/root/eng/sf-release/developer-certificate-of-origin/img/sco-linux-provenance-chain.svg)
*Ланцюг перевіреного походження (DCO Provenance Chain) в ядрі Linux. Кожен учасник процесу — від автора патча до Лінуса Торвальдса — додає свій рядок Signed-off-by, підтверджуючи юридичну чистоту внеску та фіксуючи незламний аудиторський слід у системі контролю версій.*

## DCO: механіка Developer Certificate of Origin

Щоб розв'язати проблему доказу походження без створення бюрократичного пекла для розробників, у травні 2004 року було прийнято специфікацію **Developer Certificate of Origin (DCO) версії 1.1**.

DCO — це не договір передачі прав і не ліцензія. Це коротка юридична декларація, що складається з чотирьох пунктів, під якою автор підписується щоразу, коли створює коміт:

> ### Текст Developer Certificate of Origin 1.1
> 
> Надсилаючи цей внесок, я засвідчую, що:
> 
> **(a)** Внесок створено мною повністю або частково, і я маю право надати його під відкритою ліцензією, зазначеною у файлі проєкту; **або**  
> **(b)** Внесок базується на попередній роботі, яка покривається сумісною відкритою ліцензією, і я маю право надати модифіковану роботу під тією самою відкритою ліцензією; **або**  
> **(c)** Внесок надано мені іншою особою, яка засвідчила пункти (a), (b) або (c), і я не вносив змін; **або**  
> **(d)** Я розумію та погоджуюся, що цей проєкт і внесок є публічними, а запис про внесок (включно з особистою інформацією та адресою пошти) зберігатиметься безстроково і може розповсюджуватися далі згідно з відкритою ліцензією.

### Розбір юридичних пунктів DCO

Розглянемо, від яких саме ризиків захищає кожен окремий пункт цієї декларації:

- **Пункт (a) — Власна розробка:** Закриває базовий ризик: розробник стверджує, що написав код сам, або отримав прямий дозвіл від свого роботодавця на публікацію коду під відкритою ліцензією проєкту. Якщо пізніше роботодавець спробує заявити, що код було вкрадено, відповідальність несе співробітник, який дав неправдиву декларацію, а репозиторій має письмовий доказ добросовісності.
- **Пункт (b) — Запозичення сумісного коду:** Дозволяє брати алгоритми з інших відкритих проєктів (наприклад, переносити підсистему з FreeBSD під [BSD-3-Clause](root:sys-notary/open-source-licenses) до Linux під [GPLv2](root:sys-notary/open-source-licenses)), якщо ліцензії є сумісними за напрямком поширення.
- **Пункт (c) — Ланцюг проміжного передавання (Forwarding):** Критично важливий для багаторівневих проєктів. Мейнтейнер драйвера бере патч від стороннього розробника і пересилає його головному архітектору підсистеми. Мейнтейнер не є автором рядків коду, але він засвідчує, що отримав патч із валідним підписом попередника.
- **Пункт (d) — Безвідкличність та публічність:** Блокує спроби контриб'юторів заднім числом вимагати видалення своїх рядків із репозиторію через конфлікти у спільноті або посилаючись на закони про захист персональних даних (GDPR).

### Технічне втілення: трейлер `Signed-off-by`

На технічному рівні згода з DCO фіксується додаванням одного рядка трейлера в кінець повідомлення коміту:

```text
Signed-off-by: Ivan Petrenko <ivan.petrenko@example.org>
```

У системі контролю версій Git цей процес автоматизовано на рівні CLI за допомогою прапорця `-s` (або `--signoff`):

```sh
# Створення коміту з автоматичним додаванням DCO-підпису
git commit -s -m "fix(driver): resolve null pointer dereference during device probe"
```

Коли інженер виконує `git commit -s`, Git зчитує змінні `user.name` та `user.email` із локальної конфігурації та форматує стандартний трейлер. 

### Чому DCO зберігає децентралізацію
Ключова архітектурна властивість DCO полягає в тому, що автор **не відчужує свої майнові права** і не передає їх третім особам чи фондам. Автор залишається 100% власником свого коду, надаючи проєкту стандартну ліцензію ([GPLv2](root:sys-notary/open-source-licenses), [Apache-2.0](root:sys-notary/open-source-licenses), [MIT](root:sys-notary/open-source-licenses) тощо).

Це гарантує, що кодова база назавжди залишиться спільною власністю її авторів. Жодна приватна корпорація не зможе приватизувати проєкт, змінити ліцензію на комерційну чи перетворити розробку на закриту пропрієтарну монополію.

> 🔧 **Навіщо це.** Якщо ваш проєкт є спільним інфраструктурним стандартом, бібліотекою чи платформою, яка має об'єднати конкуруючі компанії (як Linux, Kubernetes чи OpenSearch), DCO — це найкращий вибір. Він повністю знімає страх корпоративних юристів перед захопленням кодової бази одним гравцем і усуває бюрократичне тертя для розробників.

## CLA: угода контриб'ютора та централізація контролю

Зовсім інший підхід реалізує модель **Contributor License Agreement (CLA)**. Якщо DCO — це проста декларація походження, то CLA — це повноцінний юридичний договір між контриб'ютором та організацією, яка керує проєктом (фондом або комерційною компанією).

![Потоки прав інтелектуальної власності за моделями DCO, CLA та передачі прав (Copyright Assignment)](/root/eng/sf-release/developer-certificate-of-origin/img/dco-vs-cla-ip-flow.svg)
*Порівняння розподілу прав інтелектуальної власності: децентралізована модель DCO (автор зберігає права), централізована модель CLA (автор передає широкі повноваження управителю) та класична модель FSF Copyright Assignment (повне відчуження прав).*

### Механізм дії CLA

За умовами типової CLA (наприклад, Apache ICLA або угод Canonical, Meta, Google), автор формально зберігає копірайт, але надає управителю проєкту:
1. **Безвідкличну всесвітню безоплатну ліцензію** на використання, модифікацію та дистрибуцію коду.
2. **Право субліцензування:** управитель отримує право передавати код третім особам під будь-якими іншими ліцензіями, зокрема закритими комерційними.
3. **Патентну ліцензію:** автор та його роботодавець гарантують відмову від пред'явлення патентних претензій до користувачів проєкту.

Детальний порівняльний аналіз правових ризиків, бар'єрів для розробників та структури контролю між DCO і CLA викладено у вставці [DCO проти CLA: порівняльний аналіз правових ризиків, тертя розробників та контролю над проєктом](root:sf-release/developer-certificate-of-origin/comp-dco-vs-cla.md).

### Асиметрія влади та корпоративне тертя

Модель CLA створює значну асиметрію прав. Розробник, який надсилає виправлення, не отримує жодних прав на чужий код, проте віддає управителю проєкту практично необмежені повноваження щодо власного внеску.

Це призводить до двох серйозних наслідків:
- **Ризик зміни ліцензії (Relicensing Risk):** Маючи підписані CLA від усіх авторів, компанія-власник проєкту може будь-якої миті змінити відкриту ліцензію наступних випусків на комерційну чи обмежену (наприклад, Business Source License — BSL або Server Side Public License — SSPL), як це сталося з проєктами MongoDB, Elastic, Redis та Terraform.
- **Корпоративний бар'єр (Onboarding Friction):** Інженер, що працює у великій компанії, юридично не має права підписувати індивідуальну ICLA самостійно, оскільки створений ним код належить його роботодавцю. Для надсилання патча компанія розробника мусить укласти з проєктом спеціальну корпоративну угоду **Corporate CLA (CCLA)**, що вимагає тижнів бюрократичних погоджень між юридичними департаментами.

## Подвійне ліцензування: бізнес-архітектура та копілефтний важіль

Чому ж комерційні компанії так наполегливо вимагають підписання CLA або взагалі уникають зовнішніх контриб'юцій? Відповідь лежить у площині бізнес-моделей відкритого коду, найуспішнішою з яких історично стало **подвійне ліцензування (Dual Licensing)**.

![Матриця бізнес-моделі подвійного ліцензування: взаємодія копілефту та комерційних винятків](/root/eng/sf-release/developer-certificate-of-origin/img/dual-licensing-matrix.svg)
*Архітектура подвійного ліцензування (Dual Licensing). Єдина кодова база випускається одночасно під строгою копілефтною ліцензією (GPL/AGPL) для відкритої спільноти та під платною комерційною ліцензією (Commercial OEM) для корпоративних клієнтів. Копілефтний важіль змушує бізнес купувати платну ліцензію для збереження комерційної таємниці власного коду.*

### Принцип дії копілефтного важеля (The Copyleft Ratchet)

Класична модель подвійного ліцензування (піонерами якої стали MySQL AB, Trolltech із бібліотекою Qt, Sleepycat Software з Berkeley DB) базується на витонченому використанні юридичних обмежень строгого [копілефту](root:sys-notary/open-source-licenses):

1. **Відкрита гілка (GPLv2 / GPLv3 / AGPLv3):** Продукт публікується у відкритому доступі під строгою вірусною ліцензією. Будь-який розробник, студент чи некомерційна організація може завантажити вихідний код безкоштовно. Проте ліцензія GPL містить жорстку умову: якщо ви створюєте похідну роботу, лінкуєтеся з цим кодом або вбудовуєте його у власний пристрій і розповсюджуєте бінарний файл, **ви зобов'язані відкрити весь вихідний код власної програми** під тією самою ліцензією GPL.
2. **Комерційна пастка для бізнесу:** Великі виробники обладнання (OEM), банки чи закриті корпорації розробляють власні пропрієтарні модулі. Вони не можуть відкрити свій код через вимоги комерційної таємниці або захисту інтелектуальної власності. Отже, вони юридично не мають права поширювати свій продукт із GPL-компонентом.
3. **Комерційний вихід (Commercial OEM License):** Власник проєкту пропонує рішення: платну комерційну ліцензію. Заплативши роялті або придбавши річну підписку, корпорація отримує ту саму кодову базу, але зі спеціальним юридичним звільненням (*exception/waiver*) від вимог GPL. Компанія отримує законне право вбудовувати модуль у закриту прошивку чи комерційний продукт і не оприлюднювати власний код.

### Історичні прецеденти та уроки ринку

- **Справа MySQL AB:** Шведська компанія MySQL AB створила найпопулярнішу реляційну базу даних у світі, розповсюджуючи її під ліцензією GPLv2. Користувачі, які будували звичайні вебсайти на стеку LAMP (Linux, Apache, MySQL, PHP), використовували базу безкоштовно, оскільки вони не розповсюджували сам бінарний код MySQL клієнтам. Проте виробники заліза (Cisco, HP) та вендори комерційного ПЗ, які вбудовували `libmysqlclient` у свої закриті інсталятори, платили сотні тисяч доларів за комерційні ліцензії без копілефту. У 2008 році Sun Microsystems придбала MySQL AB за $1 млрд саме завдяки цій чистій бізнес-моделі.
- **Угода KDE Free Qt Foundation:** Коли норвезька компанія Trolltech розвивала графічний фреймворк Qt за моделлю подвійного ліцензування (GPL + комерційна версія), спільнота середовища KDE остерігалася, що компанія колись закриє код. Було підписано історичну юридичну угоду: якщо Trolltech будь-коли припинить випускати Qt під вільною ліцензією, фонд KDE отримує автоматичне право випустити всю кодову базу під безвідкличною ліцензією [BSD](root:sys-notary/open-source-licenses). Це створило довгостроковий баланс довіри.

### Чому DCO несумісний із комерційним подвійним ліцензуванням

Тут криється головна інженерно-економічна теорема відкритого коду:

> **Теорема про подвійне ліцензування:**  
> Компанія може продавати комерційні ліцензії на вихідний код лише тоді, коли вона є **одноосібним власником 100% майнових прав** на кожний рядок кодової бази або володіє безвідкличним правом субліцензування через **CLA**.

Якщо компанія приймає зовнішні внески за моделлю **DCO**, автори цих внесків залишають майнові права за собою й ліцензують свій код під GPL. Якщо компанія спробує продати комерційну версію продукту (включно з патчами зовнішніх авторів) третій стороні без дотримання GPL, компанія сама перетвориться на порушника авторських прав цих контриб'юторів!

Саме тому комерційні вендори, що будують бізнес на подвійному ліцензуванні, опиняються перед жорстким вибором:
- Або писати 100% коду силами власних штатних працівників;
- Або вимагати підписання суворої CLA від кожного стороннього розробника;
- Або відмовитися від подвійного ліцензування на користь сервісної моделі підтримки (як це зробила компанія Red Hat).

## Хвиля реліцензування 2018–2024 та народження форків під DCO

Події останнього десятиліття наочно продемонстрували, як юридична структура копірайту впливає на виживання екосистем.

Між 2018 та 2024 роками низка великих комерційних компаній, які роками розвивали популярні інфраструктурні проєкти за моделлю CLA (MongoDB, Elastic, Redis Labs, HashiCorp), оголосили про відмову від відкритих ліцензій OSI. Вони перевели наступні версії своїх продуктів на ліцензії обмеженого доступу — Server Side Public License (SSPL), Redis Source Available License (RSAL) та Business Source License (BSL).

Причиною такого кроку було бажання заблокувати хмарних гігантів (перш за все AWS та Google Cloud) від надання відповідних систем як керованих хмарних сервісів без оплати вендору. Оскільки всі сторонні розробники свого часу підписали обов'язкові CLA, компанії володіли повним юридичним правом змінити ліцензію в односторонньому порядку без згоди спільноти.

### Відповідь індустрії: нейтральні форки під егідою DCO

Реакція відкритої спільноти та корпорацій-користувачів виявилася миттєвою та показовою. Замість підкорення новим закритим ліцензіям індустрія об'єдналася навколо нейтральних некомерційних фондів (перш за все The Linux Foundation) і створила повністю відкриті форки кодових баз, зафіксованих на останньому відкритому коміті:

1. **Terraform → OpenTofu:** Після зміни ліцензії Terraform на BSL компанії Gruntwork, Spacelift, env0 та сотні інженерів створили форк [OpenTofu](root:sf-release/code-ownership-models) під егідою Linux Foundation.
2. **Elasticsearch → OpenSearch:** AWS та спільнота створили форк [OpenSearch](root:sf-release/code-ownership-models) під ліцензією [Apache-2.0](root:sys-notary/open-source-licenses).
3. **Redis → Valkey:** Після відмови Redis від ліцензії BSD у березні 2024 року компанії AWS, Google Cloud, Oracle, Ericsson, Huawei та ключові мейнтейнери ядра Redis заснували проєкт **Valkey** у межах Linux Foundation.

Найважливішим уроком для архітекторів є те, що **всі ці форки принципово відмовилися від CLA та обрали модель DCO**. Спільнота винесла суворий вердикт: CLA створює небезпечну монополію одного вендора, тоді як DCO гарантує, що кодова база назавжди залишиться нейтральною і захищеною від повторної приватизації.

## Автоматизація комплаєнсу в конвеєрах CI/CD

Юридичні правила не працюють, якщо їхнє виконання покладено виключно на людську дисципліну. В реальних проєктах розробники регулярно забувають прапорець `git commit -s`, плутають корпоративні адреси електронної пошти або роблять злиття з веб-інтерфейсу без підпису.

Тому сучасний процес розробки вимагає повної автоматизації комплаєнсу в [конвеєрах неперервної інтеграції](root:sf-release/ci-cd).

![Конвеєр автоматизованої перевірки DCO та комплаєнсу у CI/CD](/root/eng/sf-release/developer-certificate-of-origin/img/dco-ci-verification-pipeline.svg)
*Архітектура автоматизованого шлюзу DCO у CI/CD. Webhook ініціює перевірку метаданих коміту, DCO-бот розбирає трейлери, зіставляє пошту автора та блокує злиття Pull Request до повного усунення порушень.*

### Алгоритм роботи DCO-бота

1. **Перехоплення події:** Під час відкриття або оновлення Pull Request хмарна платформа (GitHub, GitLab) надсилає webhook-подію до комплаєнс-сервісу.
2. **Аналіз кожного коміту в PR:** Бот послідовно перевіряє всю історію гілки від точки розгалуження з `main`. Перевіряти лише останній коміт неприпустимо: у репозиторій не повинен потрапити жоден неподписаний проміжний об'єкт.
3. **Парсинг трейлерів:** Бот вилучає останній блок рядків повідомлення коміту та перевіряє наявність рядка `Signed-off-by: Real Name <email@domain>`.
4. **Звірка ідентичності:** Адреса електронної пошти у трейлері `Signed-off-by:` звіряється з полем `author.email` самого Git-коміту. Якщо розробник зафіксував коміт як `author: ivan@company.com`, а підписався як `Signed-off-by: Ivan <home@gmail.com>`, бот фіксує невідповідність.
5. **Встановлення блокувального статусу:** Через REST API статусів комітів (*Commit Status API*) бот встановлює стан `failure` або `success`, фізично блокуючи злиття гілки через захищені правила (*Branch Protection Rules*).

Повні технічні специфікації клієнтських хуків Git, формат конфігурації `.github/dco.yml` та структуру JSON-пейлоадів описано у довіднику [Специфікація трейлерів Git, конфігурація хуків commit-msg та верифікація вебхуків DCO](root:sf-release/developer-certificate-of-origin/api-dco-git-hooks.md).

Високопродуктивний рушій валідації трейлерів, розроблений мовами C та C++ для вбудовування в автономні CI-воркери, реалізовано у проєктній вставці [Інженерний рушій верифікації DCO-комплаєнсу на C та C++](root:sf-release/developer-certificate-of-origin/proj-dco-verifier-bot.md).

### Різниця між DCO та криптографічним підписом GPG/SSH

Початківці часто плутають перевірку DCO (`Signed-off-by`) із криптографічним підписом комітів за допомогою GPG або SSH-ключів (`git commit -S`):

```text
+-------------------------------------------------------------------------------+
|                       DCO vs КРИПТОГРАФІЧНИЙ ПІДПИС                           |
|                                                                               |
|  Трейлер Signed-off-by (DCO):           Криптографічний підпис (GPG / SSH):   |
|  • Юридична заява про права на код      • Технічний доказ авторства коміту    |
|  • Звичайний текстовий рядок            • Асиметрична криптографія (RSA/Ed25519)|
|  • Захищає від позовів по копірайту     • Захищає від підробки авторства (spoofing)|
|  • Читається людиною без ключів         • Перевіряється відкритим ключем      |
+-------------------------------------------------------------------------------+
```

Ці два механізми не замінюють, а **доповнюють** один одного:
- **GPG/SSH підпис** підтверджує, що цей коміт справді створив власник приватного ключа `Ivan Petrenko`, а не зловмисник, який підробив ім'я в заголовку Git.
- **Трейлер DCO** підтверджує, що цей власник ключа юридично гарантує правомірність передачі коду під відкритою ліцензією проєкту.

## Worked-приклад: аудит репозиторію та виправлення порушень DCO

Розглянемо практичну ситуацію, з якою регулярно стикається команда розробки.

### Сценарій проблеми
Інженер надіслав Pull Request із трьома комітами. CI-бот запустив комплаєнс-перевірку та повернув помилку: PR заблоковано.

```sh
# Перевіряємо історію останніх трьох комітів у робочій гілці
git log -n 3 --format="Commit: %h%nAuthor: %an <%ae>%nMessage:%n%B---"
```

Вивід журналу Git:
```text
Commit: 8f3a1b2
Author: Oleksandr Bondar <o.bondar@techcorp.ua>
Message:
fix(net): add bounds check for udp packet header

Signed-off-by: Oleksandr Bondar <o.bondar@techcorp.ua>
---
Commit: c4d5e6f
Author: Oleksandr Bondar <o.bondar@techcorp.ua>
Message:
refactor(net): extract checksum validation to helper function

Signed-off-by: Alex Bond <alex.personal@gmail.com>
---
Commit: a1b2c3d
Author: Oleksandr Bondar <o.bondar@techcorp.ua>
Message:
test(net): add unit tests for corrupted packet handling
---
```

### Аналіз виявлених дефектів:
1. **Коміт `8f3a1b2`:** Повністю валідний. Є рядок `Signed-off-by:`, пошта підпису точно збігається з автором `o.bondar@techcorp.ua`.
2. **Коміт `c4d5e6f`:** Порушення відповідності (Email Mismatch). Автор коміту — корпоративна пошта `o.bondar@techcorp.ua`, але підпис зроблено особистою поштою `alex.personal@gmail.com`. Юридично незрозуміло, від імені якої особи чи роботодавця надається внесок.
3. **Коміт `a1b2c3d`:** Критичне порушення (Missing Sign-off). Автор забув додати прапорець `-s`, трейлер підпису взагалі відсутній.

### Покрокове виправлення через інтерактивний Rebase

Щоб виправити історію без створення зайвих merge-комітів, розробник виконує інтерактивну перебудову гілки:

```sh
# 1. Запускаємо інтерактивний rebase на глибину трьох останніх комітів
git rebase -i HEAD~3
```

У відкритому редакторі замінюємо команду `pick` на `edit` для проблемних комітів:
```text
edit a1b2c3d test(net): add unit tests for corrupted packet handling
edit c4d5e6f refactor(net): extract checksum validation to helper function
pick 8f3a1b2 fix(net): add bounds check for udp packet header
```

Після збереження та закриття файлу Git зупиняється на першому проблемному коміті:

```sh
# 2. Додаємо підпис до першого коміту, не змінюючи опис
git commit --amend -s --no-edit

# 3. Продовжуємо rebase до другого коміту
git rebase --continue

# 4. Виправляємо підпис у другому коміті, щоб він збігався з автором
git commit --amend -s --no-edit

# 5. Завершуємо rebase
git rebase --continue
```

**Швидкий однорядковий спосіб виправлення всієї гілки:**  
Якщо гілка містить десятки комітів, їх можна підписати автоматично за одну команду:

```sh
git rebase origin/main --exec "git commit --amend -s --no-edit"
```

Після цього оновлена гілка відправляється на сервер із безпечним прапорцем оновлення історії:

```sh
git push --force-with-lease origin feature/net-fix
```

CI-бот миттєво перевіряє оновлені хеші комітів, знаходить коректні трейлери `Signed-off-by:` і встановлює зелений статус: Pull Request розблоковано для технічного злиття.

## Чек-лист: як організувати ліцензійну політику власного репозиторію

Щоб захистити кодову базу проєкту та налаштувати прозорі правила для всієї команди, дотримуйтеся наступного порядку дій:

1. **Оберіть базову ліцензію коду:**  
   - Дозвільна ([Apache-2.0](root:sys-notary/open-source-licenses) або [MIT](root:sys-notary/open-source-licenses)) — для широкого прийняття бібліотек та фреймворків;
   - Строгий копілефт ([GPLv3](root:sys-notary/open-source-licenses) / [AGPLv3](root:sys-notary/open-source-licenses)) — для захисту кодової бази від закриття конкурентами або для побудови подвійного ліцензування.
2. **Оберіть модель контриб'юцій:**  
   - Якщо ви некомерційний проєкт, відкрита спільнота або корпоративний консорціум — впроваджуйте **DCO**.
   - Якщо ви стартап з моделлю подвійного ліцензування чи Open Core — впроваджуйте **CLA**.
3. **Створіть файл `DCO.md` у корені репозиторію:** Зафіксуйте точний текст Свідоцтва про походження коду версії 1.1.
4. **Опишіть вимоги у `CONTRIBUTING.md`:** Поясніть розробникам, як використовувати `git commit -s` та як налаштувати локальні хуки перевірки.
5. **Увімкніть автоматизованого DCO-бота в CI:** Додайте обов'язкову перевірку трейлерів до конвеєра збірки.
6. **Захистіть головну гілку (*Branch Protection*):** Заблокуйте прямі push-коміти в `main` та увімкніть обов'язковий статус *Require branches to be up to date before merging* для перевірки DCO.
