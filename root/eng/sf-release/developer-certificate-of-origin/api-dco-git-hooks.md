# 📋 Специфікація трейлерів Git, конфігурація хуків commit-msg та верифікація вебхуків DCO

Інтеграція перевірки Свідоцтва про походження коду (DCO) у процес інженерної розробки спирається на дві точки контролю: локальне робоче місце розробника (де формується повідомлення коміту) та централізований серверний шлюз [неперервної інтеграції](root:sf-release/ci-cd) (де валідуються метадані вхідних Pull Request). Ця довідкова специфікація містить вичерпний опис граматики структурованих метаданих Git, правила функціонування клієнтських хуків перехоплення, протокол взаємодії вебхуків та схему декларативної конфігурації комплаєнс-ботів.

## Граматика трейлерів Git та синтаксис `Signed-off-by`

Відповідно до специфікації вбудованої утиліти `git interpret-trailers` та конвенцій поштових заголовків RFC 5322 (розділ 3.6), трейлери Git розміщуються у строго визначеному блоці в самому кінці тіла повідомлення коміту. Блок трейлерів мусить бути відокремлений від описової частини коміту щонайменше одним порожнім рядком. Будь-який рядок, схожий на трейлер, що з'являється всередині опису до порожнього рядка (наприклад, у цитатах виводу консолі чи в прикладах diff), парсери вважають звичайним текстом і не зараховують як юридичний підпис.

```text
Зрозумілий короткий заголовок коміту (до 50-72 символів)

Детальний опис внеску: які саме зміни внесено, чому це необхідно
та як саме розв'язано проблему. Описова частина може займати кілька
абзаців і пояснювати архітектурні рішення, передумови та вплив на систему.

Signed-off-by: Іван Петренко <ivan.petrenko@company.org>
Co-authored-by: Олена Коваль <olena.koval@partner.com>
Reviewed-by: Сергій Ткаченко <sergiy.tkachenko@review.org>
```

### Формальні правила валідації рядка `Signed-off-by`

Щоб підпис мав повну юридичну силу та успішно проходив машинний аналіз, рядок мусить задовольняти наступні критерії:

1. **Ключ трейлера:** Рівно рядок `Signed-off-by:` (регістронезалежний, але канонічний вигляд вимагає заголовних літер та двокрапки без пробілу перед нею).
2. **Справжнє ім'я підписанта (Real Name):** Справжнє ім'я та прізвище розробника (щонайменше два слова або одне загальноприйняте повне ім'я). Заборонено використовувати системні нікнейми на кшталт `root`, `admin`, `dev123`, `localhost` або псевдоніми облікових записів. Кодування імені обов'язково має бути у валідному UTF-8 без пошкоджених мультибайтних послідовностей.
3. **Формат електронної пошти:** Адреса обов'язково розміщується всередині кутових дужок `<user@domain.tld>` відповідно до стандарту RFC 5322. Заборонено наявність пробілів усередині дужок або незакритих символів.
4. **Збіг автора (Author Matching):** Адреса електронної пошти в `Signed-off-by:` мусить **побітово збігатися** зі значенням змінної середовища `GIT_AUTHOR_EMAIL` (або значенням конфігурації `git config user.email`), від імені якої зафіксовано авторство в об'єкті коміту Git. Винятком є лише ланцюжок передачі патча (forwarding), коли комітер відрізняється від первинного автора.
5. **Розташування та суміжність:** Трейлер мусить перебувати у фінальному блоці метаданих. Якщо після трейлера слідує звичайний неструктурований текст без двокрапки, парсер вважає весь блок пошкодженим.

### Повний перелік стандартних трейлерів розробки

| Трейлер | Призначення та семантика | Хто встановлює | Юридичний та інженерний статус |
| :--- | :--- | :--- | :--- |
| `Signed-off-by:` | Засвідчення Свідоцтва про походження коду DCO 1.1 (чистота коду та право на передачу) | Автор коміту та всі проміжні мейнтейнери ланцюга | Офіційна юридична заява, що накладає правову відповідальність |
| `Co-authored-by:` | Атрибуція співавтора внеску (парне програмування, спільна розробка) | Автор коміту | Зазначає спільне авторство та володіння часткою копірайту |
| `Acked-by:` | Схвалення загального підходу або архітектурного рішення мейнтейнером компонента | Мейнтейнер підсистеми або модуля | Технічне погодження без взяття юридичної відповідальності за патч |
| `Reviewed-by:` | Підтвердження проходження формального процесу [рев'ю коду](root:sf-release/code-review) | Незалежний рецензент | Свідчення ретельної перевірки коду на логічні дефекти |
| `Tested-by:` | Підтвердження успішного ручного або апаратного тестування виправлення | QA-інженер або користувач | Підтвердження працездатності патча у специфічному середовищі |
| `Reported-by:` | Атрибуція користувача чи дослідника, який знайшов та зареєстрував баг | Автор виправлення | Етична подяка за знайдений дефект без ліцензійних прав |
| `Suggested-by:` | Вказівка на людину, яка запропонувала ідею чи алгоритм розв'язання | Автор реалізації | Фіксація авторства ідеї |
| `Fixes:` | Посилання на 12-символьний SHA-1 коміту, що спричинив регресію | Автор виправлення | Технічний зв'язок для систем автоматичного бекпортування в LTS |

## Клієнтська автоматизація: локальні хуки Git

Щоб інженери команди не забували додавати підпис вручну під час кожного виклику `git commit`, у репозиторії або налаштуваннях робочої станції конфігурують клієнтські хуки життєвого циклу Git у каталозі `.git/hooks/`.

Життєвий цикл створення коміту проходить через чітку послідовність етапів:
1. `pre-commit` — перевірка якості коду (лінтери, статичний аналіз) до відкриття редактора.
2. `prepare-commit-msg` — автоматичне формування шаблону повідомлення, куди підставляються метадані.
3. `commit-msg` — фінальна строга валідація сформованого тексту; повернення ненульового коду блокує запис об'єкта коміту.
4. `post-commit` — сповіщення про успішне створення коміту.

### 1. Хук автопідпису: `.git/hooks/prepare-commit-msg`
Цей скрипт виконується безпосередньо перед відкриттям текстового редактора коміту й автоматично додає коректний рядок `Signed-off-by:` на основі поточної конфігурації `user.name` та `user.email`:

```sh
#!/bin/sh
# .git/hooks/prepare-commit-msg
# Автоматичне додавання Signed-off-by трейлера, якщо його ще немає

COMMIT_MSG_FILE="$1"
COMMIT_SOURCE="$2"

# Не модифікуємо автоматичні повідомлення злиттів (merge) або squash-комітів
if [ "$COMMIT_SOURCE" = "merge" ] || [ "$COMMIT_SOURCE" = "squash" ]; then
    exit 0
fi

NAME=$(git config user.name)
EMAIL=$(git config user.email)

if [ -z "$NAME" ] || [ -z "$EMAIL" ]; then
    echo "ПОМИЛКА: git config user.name або user.email не налаштовано!" >&2
    exit 1
fi

SOB_LINE="Signed-off-by: $NAME <$EMAIL>"

# Перевіряємо, чи підпис уже присутній у файлі
if ! grep -qs "^$SOB_LINE" "$COMMIT_MSG_FILE"; then
    # Додаємо порожній рядок і трейлер у кінець повідомлення
    printf "\n%s\n" "$SOB_LINE" >> "$COMMIT_MSG_FILE"
fi
```

### 2. Хук суворої валідації: `.git/hooks/commit-msg`
Цей хук є захисним шлюзом на боці клієнта: якщо автор випадково видалив підпис або адреса електронної пошти розходиться з глобальними налаштуваннями, хук повертає код завершення `exit 1` і скасовує створення коміту:

```sh
#!/bin/sh
# .git/hooks/commit-msg
# Сувора валідація наявності DCO підпису перед створенням об'єкта коміту

MSG_FILE="$1"
AUTHOR_EMAIL=$(git config user.email)

# Шукаємо валідний рядок Signed-off-by за стандартом RFC 5322
SOB_REGEX="^Signed-off-by: .+ <[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}>$"

if ! grep -Eqs "$SOB_REGEX" "$MSG_FILE"; then
    echo "================================================================" >&2
    echo "ПОМИЛКА КОМПЛАЄНСУ DCO: Повідомлення коміту не містить підпису!" >&2
    echo "Будь ласка, використовуйте прапорець: git commit -s" >&2
    echo "Очікуваний формат: Signed-off-by: Ім'я Прізвище <email@domain>" >&2
    echo "================================================================" >&2
    exit 1
fi

# Перевіряємо збіг пошти автора з поштою у знайденому підписі
if ! grep -qs "<$AUTHOR_EMAIL>" "$MSG_FILE"; then
    echo "ПОМИЛКА: Email у Signed-off-by не збігається з git config user.email ($AUTHOR_EMAIL)!" >&2
    exit 1
fi

exit 0
```

### 3. Глобальний шаблон для автоматичного розгортання хуків
Щоб кожен розробник команди автоматично отримував налаштовані хуки під час клонування будь-якого нового репозиторію, налаштовують глобальний каталог шаблонів Git:

```sh
# Створюємо директорію шаблонів та копіюємо хуки
mkdir -p ~/.git-templates/hooks
cp prepare-commit-msg ~/.git-templates/hooks/
cp commit-msg ~/.git-templates/hooks/
chmod +x ~/.git-templates/hooks/*

# Реєструємо шаблон у глобальній конфігурації Git
git config --global init.templateDir ~/.git-templates
```

## Налаштування вбудованого механізму трейлерів Git

Git має вбудовану систему декларативного управління трейлерами через файл `.gitconfig`. За допомогою команди `git interpret-trailers` можна налаштувати автоматичні правила розміщення та форматування:

```ini
# Приклад конфігурації у ~/.gitconfig або .git/config репозиторію
[trailer "sign"]
    key = "Signed-off-by: "
    where = end
    ifexists = doNothing
    ifmissing = add
    command = "echo \"$(git config user.name) <$(git config user.email)>\""

[trailer "review"]
    key = "Reviewed-by: "
    where = end
    ifexists = add
```

Ці параметри визначають поведінку:
- `where = end` — трейлер завжди розміщується у самому кінці блоку метаданих;
- `ifexists = doNothing` — якщо підпис уже присутній, повторний дублікат не створюється;
- `ifmissing = add` — автоматичне додавання при виконанні команди маніпуляції трейлерами;
- `command` — динамічне виконання shell-команди для генерації значення трейлера.

## Декларативна конфігурація DCO-бота (`.github/dco.yml`)

Для проєктів, розміщених на GitHub або GitLab, правила перевірки DCO декларативно описуються у файлі конфігурації репозиторію:

```yaml
# .github/dco.yml — Специфікація перевірки DCO для GitHub Probot DCO
# Схема підтримується додатком: https://github.com/dcoapp/app

# Вимоги до аналізу комітів у межах одного Pull Request
require:
  allCommits: true       # Вимагати Signed-off-by для кожного окремого коміту
  matchAuthor: true      # Звіряти email автора коміту з email у трейлері
  allowCoAuthors: true   # Дозволяти спільні підписи через Co-authored-by

# Перелік винятків для автоматизованих сервісних облікових записів
skip:
  users:
    - dependabot[bot]
    - renovate[bot]
    - github-actions[bot]
    - web-flow           # Коміти злиттів, створені через вебінтерфейс GitHub
  branches:
    - gh-pages
    - release/archive-*

# Шаблон повідомлення, яке бот залишає у коментарях PR у разі виявлення дефекту
messages:
  failure: |
    Дякуємо за ваш внесок! Цей проєкт вимагає дотримання **Developer Certificate of Origin (DCO)**.
    Один або кілька комітів у цьому PR не містять обов'язкового підпису `Signed-off-by:`.
    
    **Як виправити ваші коміти через Git CLI:**
    ```sh
    git checkout YOUR_BRANCH
    git rebase -i origin/main --exec "git commit --amend -s --no-edit"
    git push --force-with-lease origin YOUR_BRANCH
    ```
```

## Інтеграція перевірки DCO у GitLab CI, GitHub Actions та Gerrit

У корпоративних контурах без хмарних додатків перевірку реалізують безпосередньо через декларативні пайплайни або конфігурацію сервера рецензування.

### 1. Робочий процес для GitHub Actions (`.github/workflows/dco.yml`)
```yaml
name: DCO Compliance Check
on:
  pull_request:
    branches: [ main, release/* ]

jobs:
  verify-dco:
    name: Verify DCO Sign-off
    runs-on: ubuntu-latest
    steps:
      - name: Checkout pull request branch
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Run DCO Verification Action
        uses: actions/dco@v1
        with:
          check-all-commits: true
```

### 2. Пайплайн для GitLab CI (`.gitlab-ci.yml`)
```yaml
# .gitlab-ci.yml — Перевірка DCO для кожного Merge Request у GitLab
dco-verification:
  stage: test
  image: alpine:latest
  before_script:
    - apk add --no-cache git bash
  script:
    - |
      echo "Перевірка DCO для гілки ${CI_MERGE_REQUEST_SOURCE_BRANCH_NAME}..."
      # Отримуємо список усіх комітів між цільовою гілкою та гілкою MR
      COMMITS=$(git log --no-merges --format="%H" origin/${CI_MERGE_REQUEST_TARGET_BRANCH_NAME}..HEAD)
      FAILED=0
      for SHA in $COMMITS; do
        AUTHOR_EMAIL=$(git log -1 --format="%ae" $SHA)
        SOB=$(git log -1 --format="%(trailers:key=Signed-off-by,valueonly=true)" $SHA)
        if [ -z "$SOB" ]; then
          echo "ПОМИЛКА: Коміт $SHA не має трейлера Signed-off-by!" >&2
          FAILED=1
        elif ! echo "$SOB" | grep -qs "<$AUTHOR_EMAIL>"; then
          echo "ПОМИЛКА: Коміт $SHA має розбіжність пошти автора ($AUTHOR_EMAIL) та підпису ($SOB)!" >&2
          FAILED=1
        else
          echo "OK: Коміт $SHA підписано валідно ($SOB)"
        fi
      done
      if [ $FAILED -ne 0 ]; then
        echo "Перевірку DCO провалено. Виправте коміти за допомогою git commit --amend -s" >&2
        exit 1
      fi
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

### 3. Конфігурація для Gerrit Code Review
У системі Gerrit перевірка DCO є вбудованою функцією на рівні прав репозиторію. У файлі `project.config` гілки `refs/meta/config` встановлюють директиву:

```ini
[project]
    description = "Core kernel subsystem"
[receive]
    requireSignedOffBy = true
```

Коли розробник надсилає зміну через `git push origin HEAD:refs/for/main`, сервер Gerrit автоматично парсить повідомлення коміту і відхиляє операцію відправлення, якщо обов'язковий підпис відсутній.

## REST API статусів перевірки (Commit Status API)

Після завершення аналізу комітів CI-бот надсилає HTTP POST-запит до REST API хостингу репозиторію для встановлення статусу перевірки та розблокування злиття:

```http
POST /repos/owner/repo/statuses/a1b2c3d4e5f67890123456789abcdef012345678 HTTP/1.1
Host: api.github.com
Authorization: Bearer ghp_secret_ci_token_value
Content-Type: application/json

{
  "state": "success",
  "target_url": "https://ci.company.org/dco/check/142",
  "description": "All 2 commits have a valid DCO Signed-off-by trailer",
  "context": "dco/compliance-verifier"
}
```

### Специфікація полів REST API

| Поле JSON | Тип даних | Дозволені значення | Опис призначення |
| :--- | :--- | :--- | :--- |
| `state` | string | `"pending"`, `"success"`, `"error"`, `"failure"` | Стан комплаєнс-шлюзу (блокує злиття при failure) |
| `context` | string | `"dco/compliance-verifier"` | Унікальний ідентифікатор перевірки в списку статусів PR |
| `description` | string | До 140 символів | Коротке текстове пояснення причини для розробника |
| `target_url` | string | Валідний HTTPS URL | Посилання на сторінку детального аудиторського звіту |

## Обробка крайніх випадків у CI/CD

Під час проектування комплаєнс-шлюзів у CI необхідно враховувати кілька специфічних сценаріїв:

1. **Коміти веб-редактора GitHub (Web-Flow):** Коли автор виправляє документацію через вебінтерфейс GitHub, автором стає його обліковий запис, але коммитером — системний користувач `web-flow <noreply@github.com>`. Якщо вебінтерфейс не додає підпис 자동, CI-бот мусить або вимагати ручного підпису, або перевіряти наявність верифікованого GPG-підпису ключем GitHub.
2. **Анонімізовані адреси GitHub (`@users.noreply.github.com`):** Багато розробників вмикають функцію приховування пошти у налаштуваннях конфіденційності. У такому разі `GIT_AUTHOR_EMAIL` набуває вигляду `123456+username@users.noreply.github.com`. Підпис `Signed-off-by:` мусить містити саме цю службову адресу для збереження рівності з автором.
3. **Squash and Merge:** Якщо репозиторій використовує стратегію об'єднання комітів при злитті, підсумковий єдиний коміт мусить зберегти всі трейлери `Signed-off-by:` від усіх розробників, чиї коміти увійшли до складу об'єднаного блоку.
