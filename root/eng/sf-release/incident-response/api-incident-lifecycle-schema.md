# 📋 Специфікація протоколів та схем даних управління інцидентами

Надійне функціонування сучасного інженерного процесу реагування на збої неможливе без жорстко специфікованих контрактів даних: від бінарних вебхуків систем моніторингу до декларативних матриць критичності, протоколів команд месенджерів (ChatOps) та структурованих схем незмінних хронологій подій. У цій довідці зведено точні специфікації, схеми JSON, числові константи, часові SLA та контракти взаємодії, необхідні для повної автоматизації інцидентного конвеєра.

## 1. Матриця класифікації критичності (Severity Matrix)

Рівень критичності інциденту (англ. *Severity Level*) є фундаментальною категорією, яка визначає пріоритет мобілізації ресурсів інженерної організації, швидкість сповіщення чергових змін, частоту обов'язкових публічних та внутрішніх комунікацій, а також межі повноважень призначеного командира інциденту (Incident Commander).

Класифікація базується на кількісно вимірюваних показниках впливу на користувачів, бізнес-метрик втрати доходу та радіуса ураження інфраструктури (англ. *Blast Radius*).

### Таблиця рівнів критичності та оперативних нормативів

| Рівень | Вплив на бізнес і користувачів | Радіус ураження (Blast Radius) | Цільовий MTTA | Інтервал Comms | Приклади збоїв |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `SEV-1` | Критичний колапс сервісу: повна зупинка прийому платежів, масова недоступність головної сторінки, ризик втрати даних. | Понад 20% активних користувачів або всі ключові платіжні шлюзи. | ≤ 5 хв | Кожні 15 хв | Відмова основного кластера PostgreSQL, падіння DNS-провайдера, блокування балансувальника Ingress. |
| `SEV-2` | Тяжка деградація: основний функціонал працює з високою затримкою (p99 > 5с), або повністю відмовила важлива вторинна підсистема. | Від 5% до 20% користувачів; відсутні обхідні шляхи (workarounds). | ≤ 15 хв | Кожні 30 хв | Збій генерації PDF-звітів, відмова пошукового кластера Elastic, блокування авторизації через сторонній OAuth. |
| `SEV-3` | Помірна деградація: функціонал частково обмежений, але доступні обхідні шляхи; вплив на користувачів мінімальний. | Менше 5% користувачів; внутрішні адмін-панелі або бек-офіс. | ≤ 30 хв | Кожні 60 хв | Зависання черги експорту аналітики, затримка синхронізації кешу рекомендацій на 10 хвилин. |
| `SEV-4` | Дрібний збій / Низький пріоритет: косметичні дефекти інтерфейсу або поодинокі внутрішні попередження моніторингу. | Незначна кількість користувачів; функціонал не порушено. | Наступний робочий день | За запитом | Некоректне відображення іконки профілю в браузері Safari, попередження про заповнення диска бекапів на 75%. |

### Правила динамічної переоцінки критичності (Severity Escalation & Downgrade)
- **Підвищення рівня (Escalation):** Якщо під час діагностики з'ясовується, що локальний збій кешу спричинив каскадну зупинку реляційної бази даних, командир інциденту зобов'язаний негайно підвищити рівень (наприклад, з `SEV-2` до `SEV-1`), що автоматично запускає додатковий пейджинг інженерів та скорочує комунікаційний інтервал.
- **Зниження рівня (Downgrade):** Зниження критичності дозволяється лише після застосування стабільного пом'якшення, коли основний потік клієнтських запитів успішно обслуговується (наприклад, перехід із `SEV-1` у `SEV-3` після перемикання на резервний регіон).

## 2. Специфікація скінченного автомата життєвого циклу

Життєвий цикл кожного інциденту регулюється строгим графом переходів між дискретними станами. Будь-який несанкціонований перехід блокується валідатором рушія.

### Схема станів та інваріантів

```
                ┌──────────────────────────────────┐
                │            TRIGGERED             │
                └────────────────┬─────────────────┘
                                 │
                   ACK (токен валідний) / Ескалація
                                 │
                                 ▼
                ┌──────────────────────────────────┐
                │           ACKNOWLEDGED           │
                └────────────────┬─────────────────┘
                                 │
                   Оголошення команди (SEV-1/2)
                                 │
                                 ▼
                ┌──────────────────────────────────┐
                │           MOBILIZING             │
                └────────────────┬─────────────────┘
                                 │
                   Канал і міст відкрито
                                 │
                                 ▼
                ┌──────────────────────────────────┐
                │          INVESTIGATING           │ ◄───┐
                └────────────────┬─────────────────┘     │ Повторна
                                 │                       │ деградація
                   Застосовано пом'якшення               │
                                 │                       │
                                 ▼                       │
                ┌──────────────────────────────────┐     │
                │            MITIGATED             ├─────┘
                └────────────────┬─────────────────┘
                                 │
                   Витримка soak window (15-60 хв)
                                 │
                                 ▼
                ┌──────────────────────────────────┐
                │             RESOLVED             │
                └────────────────┬─────────────────┘
                                 │
                   Генерація артефактів аналізу
                                 │
                                 ▼
                ┌──────────────────────────────────┐
                │         POSTMORTEM_OPEN          │
                └──────────────────────────────────┘
```

### Контракт валідації переходів та семантичні правила

1. **`TRIGGERED → ACKNOWLEDGED`:**
   - *Передумова:* Надходження сигналу підтвердження від чергового інженера.
   - *Валідація:* Обов'язкова наявність ідентифікатора чергового `responder_id` та валідного криптографічного токена `ack_token`.
   - *Побічний ефект:* Зупинка таймера дедлайну ескалації, фіксація мітки часу `t_ack` для розрахунку MTTA.

2. **`ACKNOWLEDGED → MOBILIZING`:**
   - *Передумова:* Інцидент класифіковано як `SEV-1` або `SEV-2`.
   - *Побічний ефект:* Автоматичне створення виділеного каналу в месенджері (наприклад, `#inc-20260820-pg-pool`), генерування посилання на кімнату відеозв'язку (Incident Bridge) та надсилання запрошень призначеним лідам.

3. **`MOBILIZING → INVESTIGATING`:**
   - *Передумова:* Зафіксовано явне призначення або добровільне прийняття ролі Incident Commander (IC).
   - *Побічний ефект:* Початок ведення протоколу робочих гіпотез та запуск таймера регулярних статусних оновлень.

4. **`INVESTIGATING → MITIGATED`:**
   - *Передумова:* Метрика SLI повернулася у допустимі межі SLO внаслідок застосування аварійного виправлення.
   - *Валідація:* Обов'язкова наявність текстового опису виконаної дії `mitigation_action` (наприклад, посилання на коміт відкоту, зміну правила маршрутизатора або прапорець конфігурації).
   - *Побічний ефект:* Запуск таймера стабілізаційного вікна (soak period, зазвичай від 15 до 60 хвилин).

5. **`MITIGATED → INVESTIGATING` (Регресія / Відкат):**
   - *Передумова:* Повторне погіршення показників телеметрії протягом періоду стабілізації.
   - *Побічний ефект:* Скасування таймера стабілізації, генерація сповіщення черговій команді про неефективність попереднього виправлення.

6. **`MITIGATED → RESOLVED`:**
   - *Передумова:* Успішне завершення стабілізаційного періоду без повторних аномалій.
   - *Побічний ефект:* Оголошення статусу «All-Clear», закриття публічного інциденту на сторінці стану (StatusPage).

7. **`RESOLVED → POSTMORTEM_OPEN`:**
   - *Побічний ефект:* Створення чернетки документа постмортему в системі документації та призначення відповідального за проведення ретроспективи.

## 3. Схема вебхука вхідного сигналу моніторингу (Alertmanager / OpenAlerts)

Системи моніторингу (Prometheus Alertmanager, Grafana OnCall, Datadog) надсилають на вхідний вебхук диспетчера структурований JSON-документ за специфікацією Alertmanager Webhook v4.

### JSON-схема контракту вебхука

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "IncidentAlertWebhookPayload",
  "type": "object",
  "required": [
    "receiver",
    "status",
    "alerts",
    "groupLabels",
    "commonLabels",
    "commonAnnotations",
    "externalURL",
    "version",
    "groupKey"
  ],
  "properties": {
    "version": { "type": "string", "enum": ["4"] },
    "groupKey": { "type": "string", "description": "Унікальний ключ групи алертів для дедуплікації" },
    "status": { "type": "string", "enum": ["firing", "resolved"] },
    "receiver": { "type": "string" },
    "groupLabels": { "type": "object", "additionalProperties": { "type": "string" } },
    "commonLabels": {
      "type": "object",
      "required": ["alertname", "severity", "service", "environment"],
      "properties": {
        "alertname": { "type": "string" },
        "severity": { "type": "string", "enum": ["critical", "warning", "info"] },
        "service": { "type": "string" },
        "environment": { "type": "string", "enum": ["production", "staging"] },
        "cluster": { "type": "string" }
      }
    },
    "commonAnnotations": {
      "type": "object",
      "required": ["summary", "description", "runbook_url"],
      "properties": {
        "summary": { "type": "string" },
        "description": { "type": "string" },
        "runbook_url": { "type": "string", "format": "uri" },
        "dashboard_url": { "type": "string", "format": "uri" }
      }
    },
    "alerts": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["status", "labels", "annotations", "startsAt", "fingerprint"],
        "properties": {
          "status": { "type": "string", "enum": ["firing", "resolved"] },
          "labels": { "type": "object", "additionalProperties": { "type": "string" } },
          "annotations": { "type": "object", "additionalProperties": { "type": "string" } },
          "startsAt": { "type": "string", "format": "date-time" },
          "endsAt": { "type": "string", "format": "date-time" },
          "generatorURL": { "type": "string", "format": "uri" },
          "fingerprint": { "type": "string", "pattern": "^[a-f0-9]{16}$" }
        }
      }
    }
  }
}
```

### Словник полів вебхука

- `groupKey`: Унікальний текстовий ідентифікатор групи сповіщень, що формується Alertmanager на основі конфігурації `group_by`. Використовується рушієм ескалацій для дедуплікації та запобігання створенню паралельних інцидентів на одну й ту саму системну подію.
- `commonLabels.alertname`: Канонічна назва правила алертингу, що спрацювало (наприклад, `HighErrorRate5xx` або `DatabaseReplicationLag`).
- `commonLabels.severity`: Рівень критичності сигналу моніторингу (`critical` транслюється диспетчером у `SEV-1`/`SEV-2`, `warning` — у `SEV-3`).
- `commonAnnotations.runbook_url`: Пряме гіперпосилання на стандартизовану інструкцію з локалізації збою. Черговий зобов'язаний розпочати діагностику саме з виконання кроків плейбука.
- `alerts[].fingerprint`: 64-бітний шістнадцятковий хеш відсортованого списку міток конкретного екземпляра алерту, обчислений за алгоритмом FNV-1a. Дозволяє відстежувати життєвий цикл кожного окремого екземпляра у складі агрегованої групи.

## 4. Специфікація ChatOps-протоколу команд управління інцидентом

Команди керування через чат-боти дозволяють оперативно змінювати параметри інциденту без перемикання між сторонніми вкладками браузера.

### Граматика та параметри команд

| Команда | Аргументи | Призначення | Дозволені ролі |
| :--- | :--- | :--- | :--- |
| `/incident declare` | `<title> --sev <1-4> [--service <name>]` | Відкриття нового інциденту вручну. Автоматично створює канал, міст та призначає ініціатора тимчасовим IC. | Будь-який інженер |
| `/incident role` | `<assign|claim> <ic|ops|comms|scribe> [@user]` | Призначення або добровільне взяття оперативної ролі в командній структурі ICS. | IC, призначений користувач |
| `/incident status` | `[<update_text>]` | Запит поточного зведення або публікація чергового статусного оновлення в таймлайн. | Будь-хто (читання), IC/Comms (запис) |
| `/incident timeline` | `<add> <text> [--time <ISO8601>]` | Додавання важливої події чи спостереження в офіційну хронологію інциденту. | Scribe, IC, Ops Lead |
| `/incident mitigate` | `--action "<description>" [--pr <url>]` | Фіксація усунення впливу на користувачів та старт таймера стабілізації (soak period). | IC, Ops Lead |
| `/incident resolve` | `--summary "<summary_text>"` | Остаточне закриття гарячої фази інциденту та переведення каналу в режим архіву. | Incident Commander |

### Безпека та верифікація запитів ChatOps (HMAC-SHA256)
Усі HTTP-запити від корпоративного месенджера до вебхука диспетчера обов'язково підписуються заголовком `X-Slack-Signature`. Диспетчер проводить валідацію за формулою:

```
sig_basestring = 'v0:' + X-Slack-Request-Timestamp + ':' + raw_http_body
expected_signature = 'v0=' + HMAC_SHA256(slack_signing_secret, sig_basestring)
```
Якщо мітка часу `X-Slack-Request-Timestamp` відрізняється від системного часу сервера більш ніж на 300 секунд, або підпис не збігається, запит негайно відхиляється з кодом `401 Unauthorized` для захисту від атак повторного відтворення (replay attacks).

## 5. Схема структурованого постмортем-звіту (Postmortem JSON Schema)

Після закриття інциденту вся накопичена інформація експортується в єдиний структурований документ для безвинного ретроспективного аналізу та автоматичного імпорту в бази знань.

### JSON-схема звіту про інцидент

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "IncidentPostmortemReport",
  "type": "object",
  "required": [
    "incident_id",
    "title",
    "severity",
    "impact",
    "metrics",
    "roles",
    "timeline",
    "root_cause_analysis",
    "action_items"
  ],
  "properties": {
    "incident_id": { "type": "string" },
    "title": { "type": "string" },
    "severity": { "type": "string", "enum": ["SEV-1", "SEV-2", "SEV-3", "SEV-4"] },
    "impact": {
      "type": "object",
      "required": ["user_facing_impact", "services_affected", "estimated_revenue_loss_usd"],
      "properties": {
        "user_facing_impact": { "type": "string" },
        "services_affected": { "type": "array", "items": { "type": "string" } },
        "affected_user_percentage": { "type": "number", "minimum": 0, "maximum": 100 },
        "estimated_revenue_loss_usd": { "type": "number", "minimum": 0 }
      }
    },
    "metrics": {
      "type": "object",
      "required": ["mttd_seconds", "mtta_seconds", "mttm_seconds", "mttr_seconds"],
      "properties": {
```

### Класифікація коригувальних дій (Action Items Taxonomy)

Кожне завдання, вироблене за підсумками постмортему, належить до одного з чотирьох типів:
- `PREVENT` (Запобігання): Зміни в архітектурі чи коді, що роблять повторення даного класу помилок технічно неможливим (наприклад, додавання статичного лінтера або ізоляція пулу потоків).
- `MITIGATE` (Прискорення пом'якшення): Впровадження автоматичних запобіжників (circuit breakers, автоскейлінг, аварійні прапорці функцій), які зменшують час відновлення у разі виникнення збою.
- `DETECT` (Покращення моніторингу): Створення нових правил SLO-алертингу або оптимізація порогів чутливості для скорочення часу виявлення (MTTD).
- `PROCESS` (Організаційні зміни): Оновлення документації плейбуків, проведення тренувань чергових (Wheel of Misfortune) або зміна політики релізів.

## 6. Специфікація публічних комунікацій (StatusPage Contract)

Під час оновлення зовнішньої сторінки статусу сервісу (StatusPage) координатор комунікацій використовує нормалізовані шаблони повідомлень. Це забезпечує прозорість для клієнтів і унеможливлює спекулятивні оцінки до завершення повного технічного аналізу.

### Шаблони повідомлень за фазами інциденту

```text
[ФАЗА 1: INVESTIGATING / РОЗСЛІДУВАННЯ]
Заголовок: Спостерігається підвищена затримка та помилки під час оформлення замовлень
Тіло: Наразі ми фіксуємо проблеми в роботі модуля оформлення замовлень. Користувачі можуть стикатися з помилками при спробі оплати. Наша інженерна команда вже мобілізована та проводить активну діагностику. Наступне оновлення статусу буде опубліковано протягом 15 хвилин.

[ФАЗА 2: IDENTIFIED / ЛОКАЛІЗАЦІЯ]
Заголовок: Причину збою локалізовано, триває застосування виправлення
Тіло: Ми локалізували першопричину збою в підсистемі керування пулами з'єднань баз даних. Інженери застосовують стабілізаційні заходи для відновлення нормального проходження трафіку.

[ФАЗА 3: MONITORING / МОНІТОРИНГ ТА СТАБІЛІЗАЦІЯ]
Заголовок: Працездатність відновлено, ведеться спостереження за телеметрією
Тіло: Ми застосували необхідні коригувальні дії. Усі сервіси повернулися до штатного режиму обробки замовлень. Ми продовжуємо пильний моніторинг показників продуктивності до повного підтвердження стабільності.

[ФАЗА 4: RESOLVED / ЗАКРИТО]
Заголовок: Інцидент повністю вичерпано
Тіло: Роботу платіжного шлюзу та модуля замовлень повністю стабілізовано. Усі компоненти платформи функціонують у штатному режимі. Детальний звіт про причини інциденту та вжиті заходи буде надано після завершення внутрішнього аналізу.
```

### Комунікаційні антипатерни
- **Заборона публічного звинувачення третіх сторін:** Навіть якщо причиною збою є аварія в дата-центрі AWS або збій API платіжного шлюзу Stripe, перше офіційне повідомлення фіксує вплив на рівні власного продукту («Ми фіксуємо збої при обробці платежів»), а не перекладає провину («Провайдер Stripe знову лежить»).
- **Заборона публікації неперевірених гіпотез:** Публічне повідомлення містить лише підтверджені технічні факти, щоб не вводити в оману службу підтримки та клієнтів.

## 7. Специфікація інтеграції з голосовими шлюзами телефонії (Twilio / SIP TwiML Contract)

Для здійснення автоматичних телефонних дзвінків черговим диспетчер взаємодіє з VoIP-провайдерами через протокол TwiML (XML).

### Специфікація сценарію виклику

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Response>
    <Say voice="Polly.Jan" language="uk-UA">
        Увага! Зафіксовано критичний інцидент першого рівня на сервісі чекаут.
        Вичерпання пулу з'єднань реляційної бази даних.
        Для підтвердження отримання введіть шість цифр коду на клавіатурі телефону.
    </Say>
    <Gather numDigits="6" action="/api/v1/voice/gather-ack?incident_id=inc-4092" method="POST" timeout="15">
        <Say voice="Polly.Jan" language="uk-UA">Очікую введення коду.</Say>
    </Gather>
    <Say voice="Polly.Jan" language="uk-UA">Код не отримано. Виклик ескалюється на наступну лінію.</Say>
    <Hangup/>
</Response>
```

- Атрибут `numDigits="6"` налаштовує зчитувач DTMF-сигналів клавіатури чергового.
- Якщо протягом `timeout="15"` секунд користувач не ввів 6 цифр, шлюз перериває виклик (`Hangup`), а вебхук повертає звіт про збій, що негайно ініціює ескалацію на рівень Tier-2.

## 8. Специфікація розподіленого трейс-контексту (Forensics Trace Injection)

Для забезпечення можливості ретроспективного пошуку всіх запитів користувачів, що завершилися збоєм під час інциденту, диспетчер формує єдиний контекст трасування відповідно до стандарту W3C Trace Context:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: inc=4092,sev=1,env=prod
```

### Структура полів заголовка `tracestate`
- `inc`: Унікальний числовий або рядковий ідентифікатор інциденту.
- `sev`: Зафіксований рівень критичності на момент виконання запиту.
- `env`: Середовище виконання (`prod`, `staging`).

Будь-який проміжний сервіс (Envoy, NGINX, клієнтські gRPC-інтерцептори) автоматично прокидає ці заголовки у внутрішні спани OpenTelemetry, що дає змогу інженерам після завершення аварії за одним SQL-запитом у сховищі трейсів (ClickHouse / Jaeger) отримати вибірку всіх 100% запитів, які зазнали деградації під час активної фази інциденту.

## 9. Специфікація декларативного опису ескалаційних політик (Escalation Policy DSL)

Для конфігурації маршрутизації сповіщень черговим використовується декларативний YAML-формат. Політика визначає правила передачі зміни (Shift Handoff), часові пояси та порядок fallback-ескалацій.

```yaml
version: "v1alpha1"
kind: "EscalationPolicy"
metadata:
  name: "checkout-core-escalation"
  team: "payments-sre"
spec:
  timezone: "Europe/Kyiv"
  handoff_time: "09:00" # Щоденна передача чергової зміни о 9:00 ранку
  rules:
    - severity: "SEV-1"
      tiers:
        - tier: 1
          target: "schedule:payments-primary-oncall"
          ack_timeout_seconds: 300 # 5 хвилин
          channels: ["voip_call", "sms", "slack_direct"]
        - tier: 2
          target: "schedule:payments-secondary-lead"
          ack_timeout_seconds: 300 # 5 хвилин
          channels: ["voip_call", "sms"]
        - tier: 3
          target: "role:incident-commander-oncall"
          ack_timeout_seconds: 600 # 10 хвилин
          channels: ["emergency_broadcast_all"]
    - severity: "SEV-2"
      tiers:
        - tier: 1
          target: "schedule:payments-primary-oncall"
          ack_timeout_seconds: 900 # 15 хвилин
          channels: ["push_notification", "slack_direct"]
        - tier: 2
          target: "schedule:payments-secondary-lead"
          ack_timeout_seconds: 900
          channels: ["voip_call", "sms"]
```

Цей DSL парситься рушієм під час старту, перетворюючись на скінченний автомат таймерів, специфікований у секції 2.

## 10. Специфікація REST API диспетчера інцидентів

Для програмної інтеграції з конвеєрами CI/CD, внутрішніми панелями керування та мікросервісами диспетчер надає RESTful API.

### Ендпоінти управління

#### 1. Створення інциденту: `POST /api/v1/incidents`
Створює новий екземпляр інциденту, запускає політику ескалацій та надсилає пейдж черговому.

```http
POST /api/v1/incidents HTTP/1.1
Host: incident-engine.internal
Content-Type: application/json
Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-1234567890ab

{
  "title": "Вичерпання пулу з'єднань БД PostgreSQL",
  "severity": "SEV-1",
  "service": "checkout",
  "environment": "production",
  "description": "Пул активних сесій перевищив 98%",
  "labels": {
    "cluster": "prod-eu-central-1",
    "datacenter": "fra1"
  }
}
```

*Коди відповідей:*
- `201 Created`: Інцидент успішно створено. У тілі повертається повний об'єкт із полями `id`, `state: "TRIGGERED"` та `created_at`.
- `400 Bad Request`: Відсутні обов'язкові поля або передано некоректний рівень `severity`.
- `409 Conflict`: Інцидент із таким ключем ідемпотентності або збіжним активним відбитком `fingerprint` уже існує.

#### 2. Підтвердження черговим: `POST /api/v1/incidents/{id}/ack`
Зупиняє таймер ескалації та закріплює відповідального.

```http
POST /api/v1/incidents/inc-4092/ack HTTP/1.1
Host: incident-engine.internal
Content-Type: application/json

{
  "token": 482190,
  "responder_name": "Олексій С.",
  "responder_id": "usr-8812"
}
```

*Коди відповідей:*
- `200 OK`: Підтвердження прийнято, стан змінено на `ACKNOWLEDGED`.
- `401 Unauthorized`: Невірний одноразовий токен підтвердження.
- `422 Unprocessable Entity`: Інцидент перебуває у невідповідному стані (наприклад, уже закритий або пом'якшений).

#### 3. Фіксація пом'якшення: `POST /api/v1/incidents/{id}/mitigate`
Переводить інцидент у стан спостереження за стабільністю.

```http
POST /api/v1/incidents/inc-4092/mitigate HTTP/1.1
Host: incident-engine.internal
Content-Type: application/json

{
  "action": "Збільшено max_connections до 500 та перезапущено pgBouncer",
  "soak_period_seconds": 1800
}
```

*Коди відповідей:*
- `200 OK`: Стан переведено в `MITIGATED`, таймер витримки активовано.
- `400 Bad Request`: Не вказано опис застосованої дії.

#### 4. Повне закриття інциденту: `POST /api/v1/incidents/{id}/resolve`
Переводить інцидент у термінальний стан `RESOLVED` та генерує драфт постмортему.

```http
POST /api/v1/incidents/inc-4092/resolve HTTP/1.1
Host: incident-engine.internal
Content-Type: application/json

{
  "resolution_summary": "Пул з'єднань розширено, виправлений образ v2.14.1 розгорнуто в проді",
  "postmortem_required": true
}
```

*Коди відповідей:*
- `200 OK`: Інцидент закрито, посилання на чернетку постмортему згенеровано.
- `409 Conflict`: Неможливо закрити інцидент, який не пройшов фазу пом'якшення `MITIGATED`.

## 11. Політика безпеки та матриця привілеїв аварійного доступу (Break-Glass IAM)

Під час гарячої фази інциденту виникає потреба в тимчасовому наданні підвищених адміністративних привілеїв (SSH на продакшн-вузли, прямий доступ до консолі бази даних, модифікація правил брандмауера). Щоб уникнути ризиків безпеки, застосовується протокол екстреного доступу Break-Glass:

1. **Запит доступу (Emergency Elevation Request):**
   Інженер виконує команду `/incident access request --role dba-admin --reason "INC-4092"`.
2. **Активація через консенсус:**
   Тимчасові права активуються лише за умови схвалення Incident Commander або автоматично для призначеного `Operations Lead` на час тривалості інциденту.
3. **Таймаут оренди прав (TTL Lease):**
   Привілеї надаються у вигляді тимчасових сертифікатів або токенів із максимальним часом життя `TTL = 120 хвилин`.
4. **Аудит сесій:**
   Усі введені команди протоколюються в захищеному централізованому журналі аудиту (Session Recording / Auditd), який неможливо модифікувати чи видалити.
5. **Автоматичне відкликання (Auto-Revocation):**
   Щойно інцидент переходить у стан `RESOLVED`, усі тимчасові ролі та сертифікати автоматично інвалідуються.

## 12. Специфікація структури подій аудиту для систем Compliance (SOC2 / ISO 27001)

Для проходження щорічних аудитів безпеки та відповідності стандартам SOC2 Type II, ISO 27001 та PCI-DSS, рушій фіксує незмінний криптографічний журнал усіх змін стану інциденту.

Кожен запис аудиту містить такі обов'язкові атрибути:
- `event_id`: Глобально унікальний ідентифікатор події (UUIDv4).
- `incident_id`: Ідентифікатор пов'язаного інциденту.
- `timestamp`: Точний час у форматі ISO 8601 UTC із наносекундною дискретністю.
- `actor`: Об'єкт, що містить `user_id`, `ip_address` та `auth_method` (наприклад, `sso_mfa` або `bot_token`).
- `action`: Тип операції (`STATE_CHANGE`, `ROLE_ASSIGNMENT`, `ACCESS_ELEVATION`, `CONFIG_MUTATION`).
- `state_before` та `state_after`: Повні зрізи об'єкта до та після виконання дії.
- `signature`: Цифровий підпис SHA-256 від конкатенації попереднього хеша запису та поточного корисного навантаження (Merkle Hash Chain).

Завдяки ланцюговій структурі хешів будь-яка спроба заднім числом змінити таймлайн чи видалити скомпрометовані дії операторів призводить до порушення цілісності криптографічного ланцюга і негайно фіксується внутрішнім контуром безпеки.

## 13. Специфікація експорту звітності щодо виконання SLA та розрахунку доступності (SLA Compliance Export)

Для корпоративних клієнтів (B2B-сегмент) диспетчер автоматично генерує щомісячний звіт виконання зобов'язань SLA за стандартизованою схемою:

```json
{
  "contract_id": "sla-ent-2026-corp",
  "reporting_period": "2026-08",
  "sla_target_availability_percent": 99.95,
  "actual_availability_percent": 99.982,
  "total_outage_duration_seconds": 472,
  "qualifying_incidents": [
    {
      "incident_id": "INC-4092",
      "severity": "SEV-1",
      "outage_duration_seconds": 472,
      "root_cause_category": "INFRASTRUCTURE_DATABASE",
      "sla_credit_eligible": false
    }
  ],
  "excluded_maintenance_seconds": 3600,
  "financial_credits_accrued_usd": 0.00
}
```

- **Правило виключення запланованих робіт (Scheduled Maintenance Exclusion):** Вікна планового технічного обслуговування не враховуються у показник загального простою (downtime), якщо клієнти були попереджені за 72 години, а загальна тривалість вікон не перевищила 4 годин за календарний місяць.
- **Розрахунок фінансових компенсацій (Service Credits):** Якщо доступність падає нижче контрактного порогу (наприклад, менше 99.90% для 3.5 дев'яток), система автоматично розраховує відсоток знижки на наступний розрахунковий період відповідно до тарифної сітки договору.

## 14. Версіонування схем та зворотна сумісність контрактів

Усі наведені JSON-схеми та REST-контракти підтримують семантичне версіонування (SemVer). Будь-які модифікації полів відповідають правилам зворотної сумісності:
- Додавання нових необов'язкових полів дозволяється в межах мінорних оновлень схеми (наприклад, перехід від v1.1 до v1.2) без зміни шляху ендпоінта.
- Видалення, перейменування полів або зміна семантики статусів вимагають випуску нової мажорної версії API (наприклад, `/api/v2/incidents`) із паралельною підтримкою попередньої версії протягом щонайменше 180 днів.

Дотримання наведених специфікацій та схем даних гарантує узгодженість взаємодії всіх ланок інженерної системи, виключаючи людські помилки передачі контексту під час екстреного реагування.
