# 📋 Схема структурованого логу: канонічні поля, рівні та формат

У розподілених системах із десятками мікросервісів структурований лог є інженерним контрактом між застосунком, конвеєром збору телеметрії та аналітичним сховищем. Якщо кожен сервіс використовує власні назви полів (`user_id`, `userId`, `customer_id`, `uid`), аналітичне сховище не здатне побудувати наскрізний індекс, а чергові інженери під час інциденту витрачають дорогоцінний час на узгодження запитів.

Тут зафіксовано канонічний контракт структурованого логу на основі моделі даних **OpenTelemetry Log Data Model** та специфікації **Elastic Common Schema (ECS)**, правила семантичних просторів імен, трирівневу ієрархію атрибутів OTLP, зіставлення рівнів важливості, граматику форматів JSON Lines і Logfmt, конвеєр обробки в OpenTelemetry Collector та Vector, правила індексації в аналітичних СКБД, правила еволюції схеми, а також правила безпеки, аудиту та маскування чутливих даних.

## Канонічний конверт події (Envelope)

Кожне повідомлення логу в розподіленій системі має фіксований набір метаданих верхнього рівня, що утворюють так званий «конверт» (*envelope*). Конверт описує коли, де, ким і на якому рівні важливості була зафіксована подія:

| Поле OTel | Поле ECS | Тип | Обов'язковість | Опис та інженерна семантика |
| :--- | :--- | :--- | :--- | :--- |
| `timestamp` | `@timestamp` | `string` / `int64` | **Обов'язкове** | Точний час генерації події у форматі ISO 8601 / RFC 3339 UTC із наносекундною або мікросекундною точністю. |
| `observed_timestamp` | `event.ingested` | `string` / `int64` | Опціональне | Час, коли агент збору (Vector, Fluent Bit) отримав подію (дозволяє виявляти затримки буферизації). |
| `severity_number` | `log.level_num` | `uint8` (1..24) | **Обов'язкове** | Числове значення рівня важливості за стандартизованою шкалою OpenTelemetry. |
| `severity_text` | `log.level` | `string` | **Обов'язкове** | Канонічна текстова назва рівня: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`. |
| `body` | `message` | `string` | **Обов'язкове** | Статичний семантичний шаблон повідомлення без інтерполяції динамічних змінних (`"payment_failed"`). |
| `service.name` | `service.name` | `string` | **Обов'язкове** | Унікальне логічне ім'я мікросервісу (`"billing-api"`, `"auth-service"`). |
| `service.version` | `service.version`| `string` | Опціональне | Семантична версія артефакту чи Git commit hash (`"v2.14.0"`, `"sha:a1b2c3"`). |
| `service.environment` | `service.environment` | `string` | **Обов'язкове** | Оточення розгортання: `"production"`, `"staging"`, `"development"`. |
| `service.instance_id` | `service.node.name` | `string` | Опціональне | Унікальний ідентифікатор екземпляра процесу чи Pod UUID. |
| `host.name` | `host.hostname` | `string` | Опціональне | Мережеве ім'я фізичного сервера чи віртуального вузла Kubernetes. |

## Трирівнева ієрархія атрибутів OpenTelemetry (Resource, Scope, Record)

У протоколі OpenTelemetry OTLP (OpenTelemetry Protocol) метадані логів не дублюються в кожному записі, а організовані в трирівневу ієрархічну модель для максимальної економії мережевого трафіку та пам'яті:

1. **Рівень ресурсу (Resource Attributes):** описує сутність, яка породжує телеметрію. Ці атрибути є спільними для мільйонів подій від одного екземпляра процесу: `service.name`, `service.version`, `service.environment`, `host.name`, `k8s.pod.name`, `k8s.namespace`. Передаються один раз на весь пакет повідомлень (*batch*).
2. **Рівень області видимості (Scope / Instrumentation Scope):** ідентифікує конкретну бібліотеку або модуль, що створив запис: назва логера (`name: "com.example.billing.PaymentProcessor"`) та версія бібліотеки (`version: "1.4.2"`).
3. **Рівень запису події (LogRecord Attributes):** динамічні змінні, що належать винятково цій точці виклику: `user_id`, `order_id`, `duration_ms`, `error.*`.

Такий поділ дозволяє бінарному протоколу OTLP стискати потік логів у 4–6 разів ефективніше за наївний JSON, оскільки статичні метадані передаються лише в заголовку пакета.

## Бінарний транспорт: Protobuf OTLP проти JSON на дроті

Хоча для запису в локальний стандартний вивід (`stdout`) використовується текстовий формат JSON Lines, для міжсерверної передачі телеметрії між агентами та колекторами застосовують бінарний протокол **OTLP over gRPC / HTTP/2**.

Визначення структури `LogRecord` у Protocol Buffers v3:

```text
message LogRecord {
  fixed64 time_unix_nano = 1;
  fixed64 observed_time_unix_nano = 11;
  SeverityNumber severity_number = 2;
  string severity_text = 3;
  AnyValue body = 5;
  repeated KeyValue attributes = 6;
  uint32 dropped_attributes_count = 7;
  fixed32 flags = 8;
  bytes trace_id = 9;
  bytes span_id = 10;
}
```

Використання Protobuf усуває необхідність парсингу текстових роздільників і перетворення рядків у числа на кожному транзитному вузлі мережі. Агент збору отримує двійковий масив байтів, перевіряє теги полів за константний час `O(1)` і записує дані у вихідний сокет без динамічних виділень пам'яті.

## Ієрархія та зіставлення рівнів важливості

Різні мови програмування, фреймворки та системні протоколи історично використовували несумісні шкали рівнів логування. Стандарт OpenTelemetry уніфікував їх у 24-рівневу дискретну шкалу, розбиту на 6 основних діапазонів по 4 градації в кожному.

Така структура дозволяє відобразити тонкі градації всередині бібліотек, зберігаючи однозначне зіставлення з класичними рівнями системного логування:

```
Діапазон OTel      Числа       Syslog RFC 5424    Java / SLF4J    Python / Go       Семантичне призначення
----------------------------------------------------------------------------------------------------------------------
TRACE (1..4)       1, 2, 3, 4  7 (Debug)          TRACE           DEBUG (низький)   Наддетальний потік, кроки циклів, дампи байтів.
DEBUG (5..8)       5, 6, 7, 8  7 (Debug)          DEBUG           DEBUG             Діагностика для розробки, параметри функцій.
INFO (9..12)       9, 10,11,12 6 (Informational)  INFO            INFO              Ключові бізнес-події, старт/стоп, оброблені запити.
WARN (13..16)      13,14,15,16 4 (Warning)        WARN            WARNING           Нештатні ситуації, автоматичні повтори, деградація.
ERROR (17..20)     17,18,19,20 3 (Error)          ERROR           ERROR             Збій операції або запиту клієнта, потрібна реакція.
FATAL (21..24)     21,22,23,24 0 (Emergency),     FATAL           CRITICAL          Неможливість продовження роботи, аварія процесу.
                               1 (Alert)
```

Канонічні числові константи за замовчуванням:
- `TRACE` = 1 (OTel SeverityNumber 1)
- `DEBUG` = 5 (OTel SeverityNumber 5)
- `INFO`  = 9 (OTel SeverityNumber 9)
- `WARN`  = 13 (OTel SeverityNumber 13)
- `ERROR` = 17 (OTel SeverityNumber 17)
- `FATAL` = 21 (OTel SeverityNumber 21)

## Семантичні простори імен (Semantic Conventions)

Щоб уникнути хаосу в назвах полів, стандарт OpenTelemetry та Elastic Common Schema впроваджують ієрархічні простори імен з крапковим роздільником. Це дозволяє аналітичним базам даних (ClickHouse, OpenSearch) автоматично групувати атрибути за категоріями:

### 1. Простір HTTP-запитів (`http.*`, `url.*`, `client.*`)
Фіксує деталі вхідних та вихідних мережевих HTTP-викликів:
- `http.request.method` (`string`): HTTP-метод у верхньому регістрі (`"GET"`, `"POST"`, `"DELETE"`).
- `http.response.status_code` (`int`): Числовий статус відповіді сервера (`200`, `404`, `504`).
- `url.path` (`string`): Шлях запиту без query-параметрів (`"/api/v1/orders"`).
- `url.query` (`string`): Рядок параметрів запиту з попередньо замаскованими секретами.
- `client.address` (`string`): IP-адреса або хост клієнта, який надіслав запит.
- `user_agent.original` (`string`): Повний рядок заголовка `User-Agent`.

### 2. Простір баз даних та сховищ (`db.*`)
Описує звернення до баз даних, кешів та сховищ ключ-значення:
- `db.system` (`string`): Тип СКБД (`"postgresql"`, `"redis"`, `"clickhouse"`, `"mongodb"`).
- `db.name` (`string`): Назва цільової бази даних чи схеми (`"billing_production"`).
- `db.operation` (`string`): Тип операції (`"SELECT"`, `"INSERT"`, `"UPDATE"`, `"HGET"`).
- `db.statement` (`string`): Параметризований запит із прибраними літералами (`"SELECT * FROM users WHERE id = $1"`).
- `db.response.time_ms` (`number`): Тривалість виконання запиту на боці драйвера в мілісекундах.

### 3. Простір черг та повідомлень (`messaging.*`)
Використовується для подій брокерів повідомлень (Kafka, RabbitMQ, SQS):
- `messaging.system` (`string`): Назва системи обміну повідомленнями (`"kafka"`, `"rabbitmq"`).
- `messaging.destination.name` (`string`): Назва топіка чи черги (`"orders.v1.events"`).
- `messaging.message.id` (`string`): Унікальний ідентифікатор повідомлення у брокері.
- `messaging.operation` (`string`): Дія (`"publish"`, `"receive"`, `"ack"`).

### 4. Простір інфраструктури Kubernetes (`k8s.*`)
Збагачується агентом збору логів на рівні ноди:
- `k8s.pod.name` (`string`): Назва Pod-а (`"billing-api-7c48df8f4-z8k2l"`).
- `k8s.namespace.name` (`string`): Простір імен Kubernetes (`"prod-eu"`).
- `k8s.container.name` (`string`): Назва контейнера всередині Pod-а (`"app"`).
- `k8s.node.name` (`string`): Ім'я фізичного чи віртуального вузла кластера (`"k8s-node-worker-04"`).

## Контекст розподіленого трасування (Correlation Context)

Для безшовного зв'язку між структурованими логами та розподіленими трейсами (Jaeger, Tempo, OpenSearch Tracing) лог-запис містить стандартизовані поля специфікації W3C TraceContext:

```json
{
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "trace_flags": "01"
}
```

1. **`trace_id`** — 16-байтний глобальний ідентифікатор усього наскрізного запиту, закодований як 32 шістнадцяткові символи в нижньому регістрі.
2. **`span_id`** — 8-байтний ідентифікатор поточної виконуваної операції (спану), закодований як 16 шістнадцяткових символів.
3. **`trace_flags`** — 1-байтне бітове поле (2 hex-символи). Значення `"01"` вказує, що трейс пройшов процедуру семплювання (*sampled*) і повністю збережений у сховищі трейсів.

Наявність цих полів дозволяє UI-інтерфейсам спостережності (Grafana, Kibana, Datadog) реалізувати перехід за один клік: від графіку затримки спану безпосередньо до переліку логів, згенерованих цим спаном, і навпаки.

## Об'єкт помилки (Error & Exception Schema)

Коли лог фіксує помилку або виняток, усі деталі збою групуються у виділений вкладений об'єкт `error` замість хаотичного склеювання в рядок повідомлення:

| Поле | Тип | Приклад значення | Опис |
| :--- | :--- | :--- | :--- |
| `error.type` | `string` | `"DatabaseConnectionTimeout"` | Канонічна назва класу винятку або типу помилки. |
| `error.message` | `string` | `"failed to acquire pool connection after 3000ms"` | Текстовий опис причини помилки. |
| `error.code` | `string` / `int`| `"504"` або `"ERR_PG_CONN_TIMEOUT"` | Протокольний або бізнес-код помилки. |
| `error.stack_trace`| `string` | `"at Repo.Query (repo.go:42)\n..."` | Повний стектрейс виконання на момент виникнення збою. |
| `error.target` | `string` | `"postgres_primary_eu"` | Цільовий сервіс або залежність, виклик до якої зазнав невдачі. |

## Типізація та підводні камені JSON

JSON підтримує обмежений набір типів: рядки, числа, булеві значення, масиви та об'єкти. Під час проєктування схеми логів слід враховувати важливі обмеження:

### 1. Втрата точності 64-бітних цілих чисел (Integer Precision Trap)
Стандарт JavaScript (IEEE 754 Double Precision) точно представляє цілі числа лише до `2^53 - 1` (значення `9007199254740991`). Якщо ваш сервіс використовує 64-бітні Snowflake ID (наприклад, Twitter Snowflake або ідентифікатори Discord `1482910481928491824`), веб-інтерфейс Kibana чи Grafana тихо спотворить останні цифри числа під час відображення.

*Інженерне правило:* 64-бітні ідентифікатори, хеші та бітові маски повинні передаватися як рядки (`string`), або база даних логів повинна мати підтримку нативних 64-бітних типів (як ClickHouse `UInt64`).

### 2. Крапкова нотація проти вкладених об'єктів
Існує дві форми представлення структурованих ключів:
- **Пласка крапкова нотація (Flat dot-notation):** `{"http.request.method": "GET", "http.response.status_code": 200}`
- **Вкладені JSON-об'єкти (Nested objects):** `{"http": {"request": {"method": "GET"}, "response": {"status_code": 200}}}`

Elasticsearch та OpenSearch однаково індексують обидва варіанти, проте вкладені об'єкти споживають більше пам'яті під час парсингу. ClickHouse краще працює з пласькими стовпцями (`http_request_method`), які стискаються на 90% краще, ніж глибокі динамічні JSON-структури.

### 3. Масиви та списки в логах
Зберігання масивів у логах вимагає суворого контролю їхнього розміру. Додавання масиву з тисячі об'єктів товарів у кошику клієнта до лог-повідомлення призводить до різкого роздування розміру логу з 500 байтів до 50 кілобайтів. У високонавантажених точках вхідні колекції агрегують до кількості елементів (`cart.items_count: 42`) або зберігають лише ключові ідентифікатори у вигляді фіксованого масиву.

## Індексація та оптимізація запитів у сховищах логів

Різні аналітичні бази даних по-різному індексують структуровані логи, що впливає на швидкість вибірок:

### 1. Колонкові бази даних (ClickHouse / VictoriaLogs)
ClickHouse зберігає кожне поле в окремому файлі на диску, стискаючи однакові рядки алгоритмами LZ4 або ZSTD.
- Для швидкого пошуку за `trace_id` створюють індекс розріджених фільтрів Блума: `INDEX idx_trace trace_id TYPE bloom_filter(0.01) GRANULARITY 1`.
- Первинний ключ таблиці будують за часом і сервісом: `ORDER BY (service_name, severity_number, timestamp)`.

### 2. Документоорієнтовані індекси (Elasticsearch / OpenSearch)
Elasticsearch будує інвертований індекс (*inverted index*) для кожного текстового поля. Для структурованих полів використовують тип `keyword` замість `text`, щоб уникнути непотрібного повнотекстового морфологічного аналізу та зменшити розмір індексу втричі.

### 3. Індексація міток без індексації тіла (Grafana Loki)
Loki індексує лише високорівневі мітки (*stream labels*: `service`, `environment`, `level`), а саме JSON-тіло зберігає у вигляді стиснених блоків. Розбір полів відбувається під час виконання запиту через LogQL-вираз `| json | duration_ms > 3000`, що значно здешевлює вартість зберігання терабайтів логів.

## Специфікація форматів серіалізації

### 1. Формат JSON Lines (ndjson)
Кожен запис логу являє собою валідний JSON-об'єкт, що завершується символом перенесення рядка `\n` (ASCII 0x0A). Усередині об'єкта не допускаються неек Spike-перенесення рядків (усі стектрейси повинні бути екрановані послідовністю `\n`).

Приклад валідного ndjson:
```json
{"timestamp":"2026-08-20T03:14:12.802Z","severity_text":"ERROR","service.name":"billing-api","service.environment":"production","msg":"payment_failed","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"00f067aa0ba902b7","user_id":84920,"order_id":19482,"duration_ms":3004,"error":{"type":"GatewayTimeout","code":504,"message":"timeout contacting upstream stripe gateway"}}
```

### 2. Граматика формату Logfmt
Формат Logfmt кодує подію у вигляді послідовності пар `key=value`, розділених пробілами:

```text
ts=2026-08-20T03:14:12.802Z lvl=ERROR service=billing-api env=production msg="payment failed" trace_id=4bf92f3577b34da6 span_id=00f067aa0ba902b7 user_id=84920 duration_ms=3004 err_type=GatewayTimeout
```

Правила синтаксису Logfmt у нотації EBNF:
```
LogRecord   ::= Field ( ' ' Field )* '\n'
Field       ::= Key '=' Value
Key         ::= [a-zA-Z0-9_.-]+
Value       ::= SimpleValue | QuotedValue
SimpleValue ::= [^\s"=]+
QuotedValue ::= '"' ( [^"\\] | '\\"' | '\\\\' )* '"'
```

Якщо значення містить пробіли, лапки `"` або знак рівності `=`, воно обов'язково береться в подвійні лапки, а внутрішні лапки екрануються зворотним слешем `\"`.

## Валідація схеми: JSON Schema (Draft 2020-12)

Для автоматичної валідації логів у CI/CD тестах та на шлюзах збору телеметрії застосовується формальний контракт JSON Schema:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "StructuredLogRecord",
  "type": "object",
  "required": [
    "timestamp",
    "severity_text",
    "service.name",
    "service.environment",
    "msg"
  ],
```

## Обробка логів у Vector через VRL (Vector Remap Language)

На рівні агента збору логів (Vector) потік структурованих повідомлень перевіряється, нормалізується та збагачується за допомогою декларативного скрипта трансформації:

```text
# Розбір сирого JSON рядка
. = parse_json!(string!(.message))

# Валідація обов'язкових полів та заповнення за замовчуванням
if !exists(.timestamp) {
    .timestamp = now()
}

# Маскування секретів у query-параметрах
if exists(.url.query) {
    .url.query = replace(string!(.url.query), r'token=[^&]+', "token=[REDACTED]")
}

# Видалення заборонених полів авторизації
del(.headers.authorization)
del(.password)
```

Такий конвеєр гарантує, що навіть якщо розробник випадково передав чутливий об'єкт у логер, дані буде перехоплено й замасковано до відправки в мережу.

## Конфігурація конвеєра в OpenTelemetry Collector

Для високонавантажених інфраструктур агрегацію та маршрутизацію структурованих логів організовують через централізований OpenTelemetry Collector. Конфігурація конвеєра (`pipelines`) включає приймачі, обробники та експортери:

```text
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 1s
    limit_percentage: 75
    spike_limit_percentage: 20
  batch:
    send_batch_size: 8192
    timeout: 200ms
  transform:
    log_statements:
      - context: log
        statements:
          - set(attributes["environment"], resource.attributes["service.environment"])
          - replace_pattern(attributes["http.target"], "password=[^&]+", "password=[REDACTED]")

exporters:
  clickhouse:
    endpoint: tcp://clickhouse-cluster:9000?database=telemetry
  otlp/loki:
    endpoint: http://loki-distributor:3100/otlp

service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [memory_limiter, batch, transform]
      exporters: [clickhouse, otlp/loki]
```

## Політики збереження та аудиту (Retention & Compliance)

Структуроване логування є фундаментом для дотримання регуляторних вимог безпеки даних (GDPR, PCI-DSS, SOC 2, HIPAA):

1. **Терміни збереження (Data Retention Policies):**
   - Діагностичні логи розробки (`DEBUG`, `TRACE`): зберігаються 3–7 діб, після чого автоматично видаляються планувальником (*TTL / Time-To-Live*).
   - Експлуатаційні логи сервісів (`INFO`, `WARN`, `ERROR`): зберігаються 30–90 діб для розслідування інцидентів та ретроспективного аналізу збоїв.
   - Аудиторські події безпеки (`auth.login_success`, `admin.role_changed`, `billing.refund_issued`): зберігаються від 1 до 5 років у незмінному сховищі (*WORM / Write Once Read Many* або S3 Object Lock).

2. **Ізоляція чутливих потоків:**
   Логи, що містять інформацію про стан здоров'я чи платіжні транзакції, маркуються семантичним тегом `compliance.tier: "pci_dss"` та автоматично маршрутизуються у зашифрований контур із суворим контролем доступу (RBAC).

## Правила еволюції схеми (Schema Evolution Rules)

У великих організаціях схема структурованих логів постійно розвивається разом із бізнес-вимогами. Порушення сумісності схеми логів здатне зупинити прийом телеметрії для всього кластера.

Правила безпечної еволюції:
1. **Зворотна сумісність (Backward Compatibility):** Додавання нових полів є повністю безпечним і не ламає парсери. Сховища повинні ігнорувати або автоматично створювати нові колонки для невідомих полів.
2. **Заборона зміни типів (No Type Mutation):** Суворо заборонено змінювати тип існуючого поля (наприклад, зміна `user_id` з числа `84920` на рядок `"usr_84920"`). У колонкових базах (ClickHouse) або документоорієнтованих індексах (Elasticsearch) така зміна призводить до помилки *TypeMismatch* або *Mapping Explosion*, через що всі наступні логи сервісу відкидаються. Якщо зміна типу необхідна, заводять нове поле з іншим іменем (наприклад, `user.uid`).
3. **Захист від вибуху кардинальності ключів (Key Cardinality Explosion):** Імена ключів індексуються базою даних окремо від значень. Заборонено створювати динамічні імена ключів:

```json
// АНТИПАТЕРН: генерує новий стовпець у базі на кожного користувача
{"user_84920_status": "active"}

// КАНОНІЧНИЙ ПАТЕРН: фіксований стовпець, динамічне значення
{"user_id": 84920, "status": "active"}
```

## Автоматизована фільтрація та маскування чутливих даних (PII Redaction)

Структурований формат дозволяє застосовувати детерміновані правила маскування на рівні енкодера програми або шлюзу збору логів до того, як конфіденційні дані покинуть межі вузла.

### 1. Заборонені поля (Full Redaction)
Поля, що містять паролі, токени та криптографічні ключі, повністю замінюються константою `"[REDACTED]"`:
- `password`, `passphrase`, `secret`
- `authorization`, `token`, `bearer`, `api_key`, `access_token`
- `card_cvv`, `cvv2`, `pin`

### 2. Часткове маскування (Masking)
- **Платіжні картки (PAN)**: за стандартом PCI-DSS зберігаються лише перші 6 цифр (BIN) та останні 4 цифри номера: `411111******1111`.
- **Номери телефонів**: `+380******789`.
- **Електронна пошта**: `u***r@example.com`.

### 3. Незворотна псевдонімізація (HMAC Hashing)
Якщо для аналітики або відстеження інциденту необхідно зіставляти повторні дії одного й того самого користувача без розкриття його реальної особистості, ідентифікатор хешується за допомогою алгоритму `HMAC-SHA256` із секретною сіллю, яка регулярно оновлюється:

```text
user.pseudo_id = HMAC-SHA256("user@example.com", salt_key)
```

Це гарантує неможливість відновлення персональних даних навіть у разі повного витоку аналітичного сховища логів.
