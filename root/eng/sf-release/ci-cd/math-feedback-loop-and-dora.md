# 🧮 Математика черг, розміру пачок і метрик DORA

Ефективність та надійність конвеєрів неперервної інтеграції та доставлення визначаються не суб'єктивною інтуїцією розробників, а фундаментальними законами теорії масового обслуговування, теорії ймовірностей та математичної статистики. Розмір інтегрованої пачки коду, завантаженість черги агентів збірки та частота появи нестабільних тестів підкоряються суворим математичним залежностям, нехтування якими призводить до експоненційного зростання затримок та паралічу розробки.

## Ймовірнісна модель накопичення дефектів у пачці змін

Розглянемо процес внесення змін до вихідного коду як послідовність атомарних логічних одиниць модифікації (рядків, окремих функцій або локальних комітів). Нехай `p` — імовірність того, що окрема атомарна зміна містить приховану семантичну помилку, регресію або несумісність контрактів (`0 < p < 1`).

Якщо розробник або команда інтегрує велику пачку (англ. *batch*), яка складається з `n` незалежних атомарних змін, імовірність того, що жодна з цих змін не містить дефекту, за правилом множення ймовірностей для незалежних подій дорівнює `(1 - p)ⁿ`. Відповідно, імовірність виникнення принаймні однієї критичної поломки збірки `P(D)` виражається як:

```text
P(D) = 1 - (1 - p)ⁿ
```

Для малих значень `p` та помірних `n` формула наближається лінійною залежністю за біноміальним розкладом:

```text
1 - (1 - p)ⁿ ≈ 1 - (1 - n·p) = n·p      [за біноміальним наближенням для n·p ≪ 1]
```

Проте при зростанні розміру пачки `n` ризик не лінійно, а експоненційно наближається до неминучої одиниці:

| Кількість змін у пачці (`n`) | Ризик дефекту при `p = 0.01` (1%) | Ризик дефекту при `p = 0.002` (0.2%) |
| :--- | :--- | :--- |
| **1 (атомарний коміт у CI)** | `1 - (0.99)¹ = 1.0%` | `1 - (0.998)¹ = 0.2%` |
| **10 (дрібний PR)** | `1 - (0.99)¹⁰ = 9.56%` | `1 - (0.998)¹⁰ = 1.98%` |
| **50 (тижнева гілка)** | `1 - (0.99)⁵⁰ = 39.50%` | `1 - (0.998)⁵⁰ = 9.52%` |
| **200 (місячний реліз)** | `1 - (0.99)²⁰⁰ = 86.60%` | `1 - (0.998)²⁰⁰ = 32.99%` |
| **500 (квартальне злиття)** | `1 - (0.99)⁵⁰⁰ = 99.34%` | `1 - (0.998)⁵⁰⁰ = 63.26%` |

Математичний висновок однозначний: зі збільшенням розміру пачки ймовірність зламати систему прямує до 100%. Більше того, математичне сподівання кількості дефектів у пачці виражається як `E[D] = n · p`. Якщо `n = 500` та `p = 0.01`, пачка містить у середньому 5 одночасних незалежних дефектів. Їхня інтерференція створює комбінаторний вибух складності при локалізації, оскільки падіння одного тесту може бути спричинене суперпозицією двох різних помилок. Практика малих пачок у неперервній інтеграції гарантує, що `n ≈ 1`, утримуючи ймовірність поломки на мінімально можливому рівні `p`, де локалізація збою в одному коміті займає мінімальний робочий час окремого інженера.

## Економічна модель оптимального розміру пачки коду

Чому розробники природно тяжіють до великих пачок, якщо малі пачки математично безпечніші? Відповідь полягає у співвідношенні транзакційних витрат та витрат на утримання незавершеної роботи.

Повна функція вартості розробки TC(n) залежно від розміру пачки n описується класичною моделлю економічного розміру замовлення (англ. *Economic Order Quantity*):

```text
TC(n) = C_transaction(n) + C_holding(n) = (K / n) + (c · n)
```

де:
* K — транзакційна вартість виконання однієї інтеграції (ручне оформлення документів, ручний деплой, узгодження з комітетом змін).
* c — коефіцієнт вартості утримання незавершеного коду в ізоляції (застарівання гілки, ризик конфліктів).

Взявши першу похідну за розміром пачки та прирівнявши її до нуля, отримуємо оптимальний розмір пачки:

```text
dTC / dn = -K / n² + c = 0  ===>  n* = sqrt(K / c)
```

Якщо процес інтеграції ручний і дорогий (K >> 0), оптимальний розмір пачки n* зміщується в бік великих партій (місячних релізів). Неперервна інтеграція та автоматизація конвеєрів повністю усувають людську рутину, прямуючи транзакційні витрати до нуля: K → 0. У результаті оптимальний розмір пачки коду n* → 1, роблячи одиничний коміт економічно найвигіднішою, найдешевшою та найбезпечнішою одиницею поставки програмного забезпечення.

## Теорія масового обслуговування в чергах CI: закон Літтла та ефект насичення

Конвеєр CI/CD моделюється як система масового обслуговування (СМО) типу `M/M/c` або `M/G/c`, де:
* `λ` (інтенсивність вхідного потоку) — середня кількість нових комітів або запитів на злиття (PR) за одиницю часу.
* `μ` (інтенсивність обслуговування) — кількість збірок, яку один агент здатен виконати за годину.
* `c` — кількість паралельних агентів збірки в пулі.
* `T_s = 1 / μ` — середня тривалість прогону одного пайплайну.

Коефіцієнт завантаження системи (утилізація пулу агентів) позначається грецькою літерою `ρ`:

```text
ρ = λ / (c · μ)
```

За **законом Літтла** (англ. *Little's Law*), середня кількість задач у системі `L` (тих, що виконуються на агентах, плюс тих, що очікують у черзі) прямо пропорційна інтенсивності вхідного потоку `λ` та середньому повному часу перебування задачі в системі `W`:

```text
L = λ · W
```

Повний час доставки зворотного зв'язку `W` складається з часу очікування в черзі `W_q` та безпосереднього часу виконання `T_s`:

```text
W = W_q + T_s = W_q + (1 / μ)
```

Для одноканальної моделі `M/M/1` середній час очікування в черзі виражається формулою Хінчина-Поллачека:

```text
W_q = ρ / (μ · (1 - ρ))
```

Поведінка функції часу очікування `W_q(ρ)` має яскраво виражену гіперболічну нелінійність при наближенні `ρ → 1`:

```text
Коли ρ = 0.50 (50% завантаження): W_q = 0.50 / (μ · 0.50) = 1.0 · T_s
Коли ρ = 0.80 (80% завантаження): W_q = 0.80 / (μ · 0.20) = 4.0 · T_s
Коли ρ = 0.90 (90% завантаження): W_q = 0.90 / (μ · 0.10) = 9.0 · T_s
Коли ρ = 0.95 (95% завантаження): W_q = 0.95 / (μ · 0.05) = 19.0 · T_s
```

### Формула Кінгмана для загальних розподілів часу збірок (G/G/1)
У реальних CI-системах час надходження комітів не є пуассонівським (інженери відкривають PR переважно наприкінці робочого дня), а час виконання тестів має високу дисперсію. Наближення Кінгмана для системи G/G/1 враховує коефіцієнти варіації часу надходження C_a = σ_a / (1/λ) та часу виконання C_s = σ_s / T_s:

```text
W_q ≈ (ρ / (1 - ρ)) · ((C_a² + C_s²) / 2) · T_s
```

Ця формула математично доводить, що нестабільність тривалості тестів (C_s > 1) та групові надсилання PR (C_a > 1) помножують час очікування в черзі у кілька разів. Якщо інфраструктура CI завантажена на 95%, затримка черги зростає в десятки разів. Для забезпечення стабільного зворотного зв'язку до 10 хвилин система зобов'язана підтримувати утилізацію ρ ≤ 0.70...0.75 та автоматично масштабувати пул агентів за допомогою автоскейлерів.

## Математична оптимізація паралельного шардування тестів (LPT Scheduling)

Коли тестовий набір налічує десятки тисяч тестів із сумарним часом послідовного виконання в кілька годин, виникає класична задача теорії розкладів: розподілити N тестів з відомими тривалостями t_1, t_2, ..., t_N між M паралельними воркерами так, щоб мінімізувати максимальний час завершення (англ. *makespan* C_max):

```text
C_max = max_{1 ≤ j ≤ M} ∑_{i ∈ S_j} t_i
```

Ця задача є NP-повною у сильному сенсі (еквівалент задачі про пакування у місткості). Наївний підхід випадкового розбиття або розбиття за алфавітом файлів призводить до високої асиметрії, коли один воркер отримує довгий тест на 15 хвилин, а решта закінчують роботу за 1 хвилину і простоюють.

Оптимальним детермінованим наближенням є евристика **Longest Processing Time First (LPT)**:
1. Тести сортуються за спаданням історичної тривалості: t_(1) ≥ t_(2) ≥ ... ≥ t_(N).
2. Кожен наступний тест призначається тому воркеру, чий поточний накопичений час виконання є мінімальним.

За класичною теоремою Грехема, якість розкладу за алгоритмом LPT гарантує обмеження зверху:

```text
C_max(LPT) ≤ (4/3 - 1/(3M)) · C_max(OPT)
```

де C_max(OPT) — теоретично недосяжний ідеальний оптимум. Для 4 воркерів розклад LPT гарантовано відхиляється від ідеалу не більше ніж на 25%, а для великої кількості малих тестів розбіжність не перевищує 2–3%.

## Математична модель впливу кешування на ефективний час збірки

Нехай повна чиста компіляція та збірка без кешу займає час T_full, а відновлення об'єктів з контентно-адресованого сховища (CAS) займає час T_cache << T_full.

Якщо ймовірність потрапляння в кеш (англ. *cache hit ratio*) дорівнює h ∈ [0, 1], то математичне сподівання ефективного часу збірки T_eff становить:

```text
E[T_eff] = h · T_cache + (1 - h) · T_full = T_full - h · (T_full - T_cache)
```

При зростанні коефіцієнта попадання в кеш від h = 0.5 до h = 0.95 при T_full = 600 с та T_cache = 20 с:
* При h = 0.50: E[T_eff] = 0.50 · 20 + 0.50 · 600 = 310 с (прискорення в 1.9 раза).
* При h = 0.80: E[T_eff] = 0.80 · 20 + 0.20 · 600 = 136 с (прискорення в 4.4 раза).
* При h = 0.95: E[T_eff] = 0.95 · 20 + 0.05 · 600 = 49 с (прискорення в 12.2 раза).

Зменшення середнього часу обслуговування T_eff прямо пропорційно збільшує пропускну здатність пулу воркерів μ = 1 / E[T_eff], зменшуючи завантаженість системи ρ та запобігаючи нелінійному зростанню черги затримок у контурі розробки.

## Математична отрута нестабільних тестів (Flaky Tests)

Нестабільним (англ. *flaky*) називається тест, який на абсолютно ідентичному кодовому стані може як пройти успішно, так і впасти через недетерміновані чинники: гонки потоків (англ. *race conditions*), таймаути вводу-виводу, неізольований спільний стан у базі даних або залежність від системного годинника.

Нехай тестовий набір складається з `k` незалежних тестів. Кожен окремий тест має ймовірність `f` помилково впасти на робочому коді (`0 < f ≪ 1`).

Ймовірність того, що весь тестовий набір успішно пройде на коректному коді `P(Pass)`, дорівнює добутку ймовірностей успіху кожного тесту:

```text
P(Pass) = (1 - f)ᵏ
```

Відповідно, ймовірність хибнопозитивного падіння всього CI-конвеєра `P(False_Alarm)` становить:

```text
P(False_Alarm) = 1 - (1 - f)ᵏ
```

Розрахуємо хибні спрацьовування конвеєра залежно від розміру тестового набору `k` та рівня нестабільності `f`:

| Розмір набору (`k`) | `f = 0.001` (0.1% поломок) | `f = 0.005` (0.5% поломок) | `f = 0.01` (1% поломок) |
| :--- | :--- | :--- | :--- |
| **50 тестів** | `1 - (0.999)⁵⁰ = 4.88%` | `1 - (0.995)⁵⁰ = 22.17%` | `1 - (0.99)⁵⁰ = 39.50%` |
| **200 тестів** | `1 - (0.999)²⁰⁰ = 18.14%` | `1 - (0.995)²⁰⁰ = 63.30%` | `1 - (0.99)²⁰⁰ = 86.60%` |
| **1 000 тестів** | `1 - (0.999)¹⁰⁰⁰ = 63.23%` | `1 - (0.995)¹⁰⁰⁰ = 99.34%` | `1 - (0.99)¹⁰⁰⁰ = 99.99%` |
| **5 000 тестів** | `1 - (0.999)⁵⁰⁰⁰ = 99.33%` | `1 - (0.995)⁵⁰⁰⁰ = 100.0%` | `1 - (0.99)⁵⁰⁰⁰ = 100.0%` |

Якщо у великому корпоративному проєкті з 1 000 тестів кожен тест падає без причини лише в одному випадку з двохсот (`f = 0.5%`), то конвеєр буде червоним у **99.34% випадків**. Це паралізує довіру інженерів до результатів перевірки, змушує перезапускати збірки навмання та нівелює саму суть неперервної інтеграції.

### Статистичний критерій автоматичного карантину
Для автоматичного виявлення нестабільних тестів застосовується біноміальний критерій. Якщо тест запускається M разів на етапі верифікації PR і демонструє X падінь, оцінка ймовірності збою становить f_hat = X / M.

За статистичним критерієм Неймана-Пірсона ми мінімізуємо помилку другого роду (пропуск реального дефекту) при фіксованому рівні помилки першого роду (хибна ізоляція стабільного тесту). Нульова гіпотеза H_0: f = 0 відхиляється на користь альтернативи H_1: f > 0, якщо кількість падінь X ≥ 1 на зафіксованому детермінованому кодовому стані. Такий тест негайно переміщується до карантинного пулу, зберігаючи прохідність основної черги злиття.

## Метрики DORA: математичні формалізації ефективності поставки

Група дослідників DevOps Research and Assessment (DORA) визначила чотири ключові метрики, що описують продуктивність та стабільність інженерної системи.

### 1. Частота розгортань (Deployment Frequency, DF)
Середня інтенсивність успішних випусків артефактів у продакшен за одиницю часу:

```text
DF = N_deploy / T_total
```
де `N_deploy` — кількість релізів, а `T_total` — період вимірювання (дні або тижні). Елітні команди мають `DF ≥ 1...10` розгортань на день.

### 2. Час виконання змін (Lead Time for Changes, LTTC)
Час від першого коміту в гілці до моменту, коли цей код починає обслуговувати живий трафік у продакшені. Інтегрально обчислюється як сума затримок по всіх стадіях конвеєра:

```text
LTTC = T_dev + T_review + T_queue + T_ci + T_cd + T_rollout
```

Оскільки емпіричний розподіл часу виконання змін T_LTTC має важкий правий хвіст, розрахунок середнього арифметичного дає оманливу картину через поодинокі заблоковані PR. Статистичний аналіз вимагає оцінки за квантилями та кумулятивною функцією розподілу F(t) = P(LTTC ≤ t):

```text
LTTC_p50 = inf { t : F(t) ≥ 0.50 }   [Медіанний час поставки]
LTTC_p90 = inf { t : F(t) ≥ 0.90 }   [Гарантований час поставки для 90% змін]
```

### 3. Частка невдалих змін (Change Failure Rate, CFR)
Відношення кількості розгортань, що призвели до деградації сервісу, відкату або випуску термінового виправлення, до загальної кількості розгортань:

```text
CFR = N_failed / N_total
```

Для розрахунку довірчого інтервалу при невеликих обсягах випусків використовується інтервал Вільсона (Wilson Score Interval) для біноміальної пропорції з рівнем довіри 1 - α:

```text
CI(CFR) = (CFR + z²/(2N) ± z · sqrt((CFR·(1-CFR) + z²/(4N))/N)) / (1 + z²/N)
```
де z = Φ⁻¹(1 - α/2) — квантиль стандартного нормального розподілу. Для високоефективних інженерних систем точкова оцінка `CFR ≤ 0.05` (менше 5%). Управління якістю поставки спирається на концепцію бюджету помилок (англ. *Error Budget*): якщо CFR перевищує поріг, нові функціональні релізи призупиняються на користь задач підвищення надійності та стабільності конвеєра.

### 4. Середній час відновлення сервісу (Mean Time to Restore, MTTR)
Математичне сподівання тривалості інциденту від моменту його виявлення T_incident до повного відновлення працездатності системи T_recovered:

```text
MTTR = (1 / M) · ∑ (T_recovered_i - T_incident_i)     [для всіх M зафіксованих інцидентів]
```

Тривалість відновлення описується функцією надійності S(t) = P(T > t) = exp(-(t/λ)^k) у межах моделі Вейбулла. Завдяки незмінним OCI-образам, криптографічно підписаним релізам та автоматичним канарочним відкатам у сучасному CI/CD параметр масштабу λ скорочується з кількох діб до лічених хвилин, мінімізуючи сумарні збитки бізнесу від простою та гарантуючи надійне дотримання контрактів про рівень обслуговування (SLA).
