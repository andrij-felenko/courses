# 📋 Специфікація метрик, порогів та схеми конфігурації нічних прогонів

Цей документ визначає формальний контракт структури конфігурації нічних регресійних тестів, формат серіалізації вхідних і вихідних телеметричних даних, правила розрахунку агрегованих метрик та політику класифікації дефектів для автономних випробувальних стендів.

Стандартизація формату конфігурації та звітів є обов'язковою інженерною вимогою для забезпечення сумісності між різнорідними тестовими стендами (Hardware-in-the-Loop для мікроконтролерів STM32/ESP32, виділені Bare-Metal сервери на базі архітектур x86_64 та ARM64) та централізованою системою збереження історичних метрик і генерації сповіщень. Без чіткого контракту кожна інженерна підсистема генерує логи у власному форматі, що унеможливлює автоматичний порівняльний аналіз регресій між релізами.

---

## 1. Схема конфігурації тестового прогону (`nightly-config.json`)

Кожен стенд нічного тестування перед початком сесії зчитує декларативний маніфест конфігурації. Цей файл визначає тривалість прогону, електричні параметри профілювання живлення, вимоги до навантаження динамічної купи та допустимі статистичні межі відхилення показників продуктивності.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "NightlyRunConfiguration",
  "type": "object",
  "required": [
    "suite_name",
    "target_platform",
    "duration_seconds",
    "metrics_thresholds"
  ],
  "properties": {
    "suite_name": {
      "type": "string",
      "description": "Унікальний ідентифікатор тестового набору в системі CI/CD"
    },
    "target_platform": {
      "type": "string",
      "enum": ["hil_stm32", "hil_esp32", "bare_metal_x86_64", "arm64_server"],
      "description": "Тип цільового апаратного стенду виконання"
    },
    "duration_seconds": {
      "type": "integer",
      "minimum": 300,
      "maximum": 86400,
      "description": "Тривалість тестової сесії в секундах (рекомендовано 28800 = 8 годин)"
    },
    "power_profiling": {
      "type": "object",
      "required": ["voltage_v", "sample_rate_hz"],
      "properties": {
        "voltage_v": { "type": "number", "minimum": 0.5, "maximum": 48.0 },
        "sample_rate_hz": { "type": "number", "minimum": 10.0, "maximum": 100000.0 },
        "baseline_energy_joules": { "type": "number" },
        "max_sleep_current_ua": { "type": "number" },
        "max_active_current_ma": { "type": "number" }
      }
    },
    "metrics_thresholds": {
      "type": "object",
      "required": ["statistical_model"],
      "properties": {
        "statistical_model": {
          "type": "string",
          "enum": ["cusum", "ewma", "mann_whitney", "hard_limit"]
        },
        "max_allowed_frag_index": {
          "type": "number",
          "minimum": 0.0,
          "maximum": 1.0,
          "description": "Максимально допустимий індекс фрагментації купи"
        },
        "max_leak_rate_bytes_per_hour": {
          "type": "number",
          "minimum": 0.0,
          "description": "Гранична швидкість лінійного витоку пам'яті"
        },
        "tail_latency_p99_max_us": {
          "type": "number",
          "description": "Верхня межа 99-го перцентиля затримки"
        },
        "cusum_h_threshold_sigmas": {
          "type": "number",
          "default": 4.5
        }
      }
    }
  }
}
```

### Призначення полів та інваріанти конфігурації

1. **`suite_name` (рядок)**: текстовий ідентифікатор сценарію тестування (наприклад, `ble_sensor_telemetry_soak`). Слугує ключем для вибірки історичного базового профілю (Baseline) із бази даних метрик.
2. **`target_platform` (перелічення)**: визначає апаратний драйвер стенду. Для стендів класу `hil_*` активується керування цифровим аналізатором живлення та релейними комутаторами. Для `bare_metal_*` активуються підсистеми збору апаратних лічильників продуктивності процесора (PMC) через `perf` та eBPF.
3. **`duration_seconds` (ціле число)**: тривалість безперервного прогону. Мінімальний поріг у 300 секунд призначений для швидкого калібрування стенду; стандартне нічне навантаження становить 28 800 секунд (вісім годин), що забезпечує виконання понад одного мільйона робочих циклів.
4. **`power_profiling.voltage_v` (дійсне число)**: номінальна напруга живлення стенду, що виставляється на виході програмованого лабораторного джерела (наприклад, 3.3 В для мікроконтролерів або 12.0 В для промислових контролерів).
5. **`power_profiling.sample_rate_hz` (дійсне число)**: частота опитування струмовимірювального АЦП. Для виявлення коротких мікросекундних імпульсів радіопередавача частота має становити не менше 10 000 Гц (10 кГц).
6. **`metrics_thresholds.statistical_model` (перелічення)**: визначає алгоритм прийняття рішення:
   - `cusum`: кумулятивна сума відхилень — рекомендована для середньої споживаної потужності та базового струму сну;
   - `ewma`: експоненційне ковзне середнє — для відстеження повільних трендів;
   - `mann_whitney`: непараметричний ранговий тест для порівняння розподілів затримок;
   - `hard_limit`: жорсткий абсолютний ліміт (використовується лише для критичних порогів відмови апаратури).
7. **`metrics_thresholds.max_allowed_frag_index` (дійсне число)**: поріг індексу фрагментації динамічної купи `F = 1 - (max_free_block / total_free)`. Перевищення порогу 0.50 свідчить про деградацію структури пам'яті, коли найбільший вільний блок займає менше половини вільної пам'яті.

## 2. Формат підсумкового звіту нічного прогону (`nightly-report.json`)

Після завершення випробувальної сесії оркестратор аналізує зібрані сирі масиви телеметрії, розраховує агреговані статистичні показники та формує єдиний вихідний звіт.

### Семантика секцій вихідного звіту

- **`run_id` та `commit_sha`**: унікальний ідентифікатор сесії та повний хеш перевіреного коміту в системі контролю версій Git.
- **`status`**: фінальний вердикт прогону:
  - `PASSED`: усі показники в межах норми;
  - `FAILED`: виявлено регресію щонайменше за однією критичною метрикою;
  - `INFRA_ERROR`: збій вимірювального стенду (обрив зв'язку з профайлером, знеструмлення хоста).
- **`failure_reasons`**: масив стандартизованих кодів причин відмови для швидкої фільтрації в дашбордах спостережності.
- **`metrics.power`**: блок фізичних вимірювань енергії. Містить сумарну кількість спожитих джоулів, середню потужність у міліватах, струм у режимі сну в мікроамперах та підсумкове значення статистики CUSUM.
- **`metrics.memory`**: блок стану динамічної купи. Фіксує початковий і фінальний розмір вільної пам'яті, швидкість витоку (байтів на годину), розмір найбільшого неперервного вільного блоку та індекс фрагментації.
- **`metrics.latency`**: статистичний розподіл затримок обробки подій (перцентилі p50, p95, p99, p99.9 у мікросекундах) та розраховане p-значення критерію Манна — Вітні відносно історичного еталону.
- **`bisect_result`**: результат роботи автоматизованого бінарного пошуку винного коміту, якщо процедуру було активовано.

## 3. Таблиця стандартних кодів помилок та вердиктів конвеєра

Під час інтеграції тестового раннера з конвеєрами CI/CD (GitLab CI, GitHub Actions, Jenkins) процес завершується зі стандартизованим кодом виходу (Exit Code), що визначає подальший маршрут сповіщення.

| Код завершення | Ідентифікатор вердикту | Опис причини збою | Дія конвеєра |
|---|---|---|---|
| `0` | `VERDICT_PASS` | Усі метрики перебувають у межах допустимих статистичних коридорів | Публікація звіту, схвалення нічного артефакту |
| `10` | `ERR_POWER_LEAK_SLEEP` | Струм у режимі сну перевищив допуск (витік через GPIO, завислий WakeLock) | Авто-bisect, блокування релізного кандидата, алерт команді апаратного ПЗ |
| `11` | `ERR_POWER_ACTIVE_DRIFT` | Інтеграл енергії або середня потужність активної фази перевищили CUSUM-поріг | Авто-bisect, алерт авторам останніх змін у драйверах |
| `20` | `ERR_HEAP_LINEAR_LEAK` | Виявлено стійкий монотонний витік пам'яті (`leak_rate > limit`) | Запуск Valgrind/ASan аналізу, сповіщення в трекер дефектів |
| `21` | `ERR_HEAP_FRAGMENTATION` | Розмір найбільшого вільного блоку колапсував при наявності вільної пам'яті | Запит рефакторингу виділення пам'яті на пули фіксованого розміру |
| `30` | `ERR_LATENCY_P99_EXPLOSION` | Деградація 99-го або 99.9-го перцентиля затримки reaction time | Збір eBPF-траси off-CPU блокувань, профіль локів |
| `31` | `ERR_LATENCY_DIST_SHIFT` | Статистичний зсув форми розподілу за критерієм Манна — Вітні (`p < 0.01`) | Попередження про повільний дрейф продуктивності |
| `40` | `ERR_TARGET_HARD_FAULT` | Апаратний збій мікроконтролера (HardFault, Panic) під навантаженням | Збереження дампу пам'яті регістрів, аварійний алерт |
| `50` | `ERR_STAND_INFRASTRUCTURE` | Обрив зв'язку з профайлером живлення, перегрів тестової камери | Сповіщення черговому інженеру лабораторії |

## 4. Обробка крайових випадків та відновлення після збоїв

Реальна тривала експлуатація тестових стендів неминуче стикається з фізичними та системними аномаліями. Контракт специфікації вимагає детермінованої обробки наступних ситуацій:

1. **Апаратний збій тестової плати (HardFault / Kernel Panic)**:
   - Якщо цільовий пристрій перестає передавати пакети телеметрії по UART протягом 30 секунд, раннер фіксує таймаут сторожового таймера.
   - Раннер надсилає команду на релейний комутатор живлення стенду для виконання апаратного скидання (Power Cycle).
   - Зчитується лог аварійного дампу з енергонезалежної пам'яті або відлагоджувального інтерфейсу SWD/JTAG (вміст регістрів процесора R0-R15, стек викликів).
   - Звіт позначається кодом `ERR_TARGET_HARD_FAULT`.

2. **Дрейф тактової частоти та часова синхронізація**:
   - При зміні температури навколишнього середовища частота внутрішніх RC-генераторів мікроконтролера може «плисти» в межах ±2–3%.
   - Для запобігання похибкам інтегрування енергії всі часові мітки вимірювань струму формуються виключно апаратним таймером самого аналізатора живлення, синхронізованого з хостом по протоколу PTP/NTP, а не за внутрішніми часовими мітками цільового мікроконтролера.

3. **Короткочасні стрибки струму під час увімкнення (Inrush Current)**:
   - Під час первинного заряду вхідних блокувальних конденсаторів плати виникає імпульс струму амплітудою до 2–5 А тривалістю кілька мікросекунд.
   - Специфікація вимагає ігнорувати перші 500 мілісекунд після подачі напруги під час розрахунку інтеграла робочої енергії та оцінки базового струму сну.
