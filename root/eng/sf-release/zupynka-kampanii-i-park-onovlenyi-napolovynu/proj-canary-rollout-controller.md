# Диспетчер канаркових релізів із автоматичним аналізом телеметрії та аварійним Kill Switch

У високонавантажених розподілених системах ручне перемикання ваг балансувальника та візуальний моніторинг дашбордів під час викачування релізів неминуче призводять до запізнілої реакції на деградацію продуктивності. Коли новий бінарний реліз викликає спорадичні блокування або повільний витік ресурсів пам'яті, затримка реакції інженера-оператора навіть на дві хвилини може спричинити вичерпання пулів з'єднань, переповнення черг брокера повідомлень і масштабний відмив транзакцій. Автономний контролер канаркового розгортання бере на себе повний цикл керування життєвим циклом релізу: від дозованого виділення когорт трафіку та безперервної статистичної верифікації метрик до миттєвого спрацьовування аварійного Kill Switch та ізоляції дефектних екземплярів у карантинний контур.

Цей проект реалізує закінчений виробничий диспетчер канаркових випусків (Canary Rollout Controller), що функціонує в режимі реального часу. Диспетчер поєднує детерміновану машину скінченних станів, кільцеві буфери накопичення телеметрії високої роздільної здатності, непараметричний статистичний аналізатор аномалій на основі U-критерію Манна-Вітні, підсистему генераційного огородження (Epoch Fencing) та керований механізм штатного дренажу активних сокетів.

```text
Архітектура автономного диспетчера канаркових релізів:

                  ┌──────────────────────────────────────────────────────────┐
                  │              ВХІДНИЙ L7 ТРАФІК СИСТЕМИ                   │
                  └─────────────────────────────┬────────────────────────────┘
                                                │
                                                ▼
                  ┌──────────────────────────────────────────────────────────┐
                  │  L7 Dynamic Router (Зважена маршрутизація та хешування)  │
                  └──────────────┬───────────────────────────┬───────────────┘
                                 │                           │
                   [ 100% - W% ] │                           │ [ W% Канарка ]
                                 ▼                           ▼
                  ┌──────────────────────────┐┌──────────────────────────────┐
                  │    Контрольна група      ││       Канаркова група        │

       │ Наступна когорта: W = W * k          │    │ АВАРІЙНИЙ KILL SWITCH             │
       │ Оновлення Epoch Token                │    │ 1. Маршрутна вага W -> 0%         │

```

## Інженерний контекст та виклики автономного керування релізами

Під час експлуатації критичних розподілених систем головним ворогом надійності є час затримки реакції зворотного зв'язку (Feedback Loop Latency). Традиційний процес викачування нового коду за участю чергового інженера містить щонайменше чотири послідовні фази затримки:

1. **Затримка агрегації телеметрії (Ingestion Lag):** системи моніторингу на основі періодичного опитування (scrape-based, наприклад Prometheus) збирають метрики з інтервалом у 15–30 секунд.
2. **Затримка обчислення агрегатів (Query Evaluation Lag):** правила алертингу обчислюються за плаваючими вікнами тривалістю від 1 до 5 хвилин, щоб згладити поодинокі викиди.
3. **Людський фактор (Human Triage Latency):** отримавши сповіщення про зростання помилок, інженер витрачає від 60 до 300 секунд на перевірку графіків, визначення джерела проблеми та прийняття рішення про зупинку розгортання.
4. **Затримка виконання команди відкату (Actuation Lag):** запуск ручного конвеєра або виконання команд консолі для скидання трафіку займає додатковий час.

Сумарний час між виникненням критичного дефекту в новому бінарному файлі та повною ізоляцією трафіку при ручному керуванні сягає 5–10 хвилин. За інтенсивності вхідного потоку у 100 000 запитів на секунду це призводить до відправки понад 30 мільйонів потенційно дефектних запитів клієнтам, переповнення черг повторних спроб (Retry Storms) та вичерпання дескрипторів сокетів по всьому кластеру.

Автономний диспетчер канаркових релізів скорочує весь ланцюг реакції до мілісекундного діапазону. Завдяки потоковому аналізу необроблених замірів затримок у пам'яті процесу та математичному апарату рангової статистики контролер фіксує деградацію за 2–3 секунди від моменту появи перших аномалій і миттєво активує апаратний Kill Switch без залучення людини.

## Системні вимоги та модель скінченних станів контролера

Автономний контролер релізів спроектований як детермінована машина скінченних станів (Finite State Machine, FSM) із нульовими динамічними алокаціями на гарячому шляху маршрутизації. Це виключає накладні витрати на роботу алокатора пам'яті та гарантує стабільний час відповіді навіть під час екстремальних навантажень.

### Граф станів та правила переходів

Контролер підтримує строгий набір експлуатаційних станів:

```text
                        ┌────────────────────────┐
                        │          IDLE          │ (Очікування старту релізної кампанії)
                        └───────────┬────────────┘
                                    │ StartRollout()
                                    ▼
                        ┌────────────────────────┐
                        │      INITIALIZING      │ (Верифікація зондів готовності вузлів)
                        └───────────┬────────────┘
                                    │ HealthChecksPassed()
                                    ▼
                 ┌───────────> ┌────────────────────────┐
                 │             │    PROMOTING_COHORT    │ (Оновлення ваги W у таблиці маршрутизації)
                 │             └───────────┬────────────┘
                 │                         │ WeightApplied()
                 │                         ▼
                 │             ┌────────────────────────┐
                 │             │        SOAKING         │ (Накопичення вибірок затримок)
                 │             └───────────┬────────────┘
                 │                         │ SoakWindowExpired()
                 │                         ▼
                 │             ┌────────────────────────┐
                 │             │     EVALUATING_ACA     │ (Статистичний тест Манна-Вітні)
                 │             └─────┬────────────┬─────┘
                 │                   │            │
                 │   [ ACA: Pass ]   │            │ [ ACA: Fail ]
                 └── (W < 100%) ─────┘            ▼
                 │                      ┌────────────────────────┐
                 │                      │ EMERGENCY_KILL_SWITCH  │ (Скидання W -> 0%, інкремент епохи)
                 ▼ (W == 100%)          └───────────┬────────────┘
        ┌────────────────────────┐                  │
        │     PROMOTED_FULL      │                  ▼
        └────────────────────────┘      ┌────────────────────────┐
                                        │   QUARANTINE_DRAINING  │ (GOAWAY кадр, вичерпання сокетів)
                                        └───────────┬────────────┘
                                                    │ DrainTimeout()
                                                    ▼
                                        ┌────────────────────────┐
                                        │      ROLLED_BACK       │ (Ізоляція дампу, звіт про інцидент)
                                        └────────────────────────┘
```

Кожен перехід між станами супроводжується атомарним логуванням та верифікацією системних інваріантів:

* `IDLE`: контролер очікує передачі маніфесту нового релізу. Маршрутна вага канарки зафіксована на рівні 0.0%, усі запити обслуговуються вузлами поточної базової версії (Baseline).
* `INITIALIZING`: контролер перевіряє доступність цільових серверних вузлів версії v2 через HTTP-ендпоінти `/healthz` та переконується у відповідності хеш-сум бінарних файлів.
* `PROMOTING_COHORT`: контролер атомарно оновлює ваговий коефіцієнт у таблиці маршрутизатора відповідно до поточної прогресії (1% → 5% → 25% → 50% → 100%).
* `SOAKING`: контролер утримує виділену частку трафіку протягом фіксованого часового інтервалу (періоду вистоювання), накопичуючи заміри затримок у кільцевих буферах для обох когорт.
* `EVALUATING_ACA`: модуль статистичного аналізу вичитує синхронний зліпок буферів телеметрії та виконує тест Манна-Вітні. Якщо деградація відсутня і поточна вага досягла 100%, автомат переходить у стан `PROMOTED_FULL`; якщо вага менша 100% — переходить до наступного кроку `PROMOTING_COHORT`.
* `EMERGENCY_KILL_SWITCH`: стан екстреного переривання з найвищим пріоритетом. Вага канарки миттєво обнуляється, а генераційний токен консенсусу інкрементується.
* `QUARANTINE_DRAINING`: канаркові вузли надсилають клієнтам сигнал завершення стрімів і очікують доопрацювання активних транзакцій протягом тайм-ауту безпеки.
* `ROLLED_BACK`: дренаж завершено, канаркові процеси переведені в режим аудиту для збереження Core Dump та профілю пам'яті.

## Математичний фундамент та обчислювальна складність аналізатора ACA

Оцінка продуктивності в розподілених сервісах стикається з проблемою нестаціонарності та важких хвостів розподілу затримок (Latency Tails). Якщо сервіс стикається з мікропаузами планувальника ядра або короткочасними блокуваннями сторінок пам'яті, середнє арифметичне значення часу відповіді може майже не змінитися, проте затримка на 99-му процентилі зростає на порядки.

### Формулювання непараметричного тесту Манна-Вітні з корекцією зв'язок

Непараметричний U-критерій Манна-Вітні не робить припущень про гауссівську форму розподілу даних і є стійким до важких хвостів. Алгоритм порівнює дві незалежні вибірки: вибірку затримок контрольної групи Baseline розміром n та вибірку затримок канаркової когорти Canary розміром m.

1. Усі N = n + m спостережень об'єднуються у спільний масив:

```text
Z = { z_1, z_2, ..., z_N } = { x_1, ..., x_n, y_1, ..., y_m }
```

2. Масив сортується за зростанням за час O(N log N).
3. Кожному елементу присвоюється ранг. Якщо група елементів має однакові числові значення затримки (зв'язані ранги, ties), кожному з них присвоюється середнє арифметичне відповідного діапазону рангів:

```text
ранг_зв'язки = 1.0 + (індекс_початку + індекс_кінця) / 2.0
```

4. Обчислюється сума рангів для контрольної групи R_1 та канаркової групи R_2.
5. U-статистика розраховується за формулами:

```text
U_1 = n * m + (n * (n + 1)) / 2 - R_1
U_2 = n * m + (m * (m + 1)) / 2 - R_2
U   = min(U_1, U_2)
```

6. Корекція дисперсії на наявність зв'язаних рангів:
У дискретній телеметрії високої частоти (наприклад, заміри затримок із дискретністю до 1 мс або мікросекундні відповіді з кешу пам'яті) значна кількість вимірювань набуває однакових значень. Якщо об'єднаний масив містить g груп однакових значень, де k-та група має розмір t_k спостережень, класична формула дисперсії завищує теоретичний розкид, оскільки усереднення рангів зменшує дисперсію рангової суми. Точна дисперсія зі скоригованими зв'язками розраховується як:

```text
математичне_сподівання = (n * m) / 2
дисперсія_скоригована = ((n * m) / 12) * [ (n + m + 1) - сума_{k=1}^g (t_k^3 - t_k) / ((n + m) * (n + m - 1)) ]
стандартне_відхилення_скориговане = sqrt(дисперсія_скоригована)
```

7. Поправка на неперервність Йейтса та Z-статистика:
Оскільки дискретна U-статистика апроксимується неперервним нормальним розподілом, для виключення похибок квантування на межах інтервалів застосовується поправка на неперервність величиною 0.5:

```text
якщо U < математичне_сподівання:
    Z_score = (U - математичне_сподівання + 0.5) / стандартне_відхилення_скориговане
якщо U > математичне_сподівання:
    Z_score = (U - математичне_сподівання - 0.5) / стандартне_відхилення_скориговане
якщо U == математичне_сподівання:
    Z_score = 0.0
```

8. Оцінка рівня значущості (p-value) обчислюється через додаткову функцію помилок erfc:

```text
p_value = erfc( |Z_score| / sqrt(2.0) )
```

Якщо Z_score < 0 (що вказує на зміщення канаркових затримок у бік більших рангів) та p_value < 0.01, контролер фіксує статистично достовірну деградацію надійності релізу з рівнем довіри 99%.

### Оцінка практичного розміру ефекту: дельта Кліффа та оцінювач Ходжеса-Лемана

У високонавантажених сервісах винятково низького значення p-value недостатньо для безпечного прийняття рішення про зупинку релізу. При великих обсягах вибірок телеметрії (наприклад, N = 2 048 або 4 096 замірів) статистичний критерій стає надчутливим (Overpowered): мікроскопічний зсув медіани затримки на 0.05 мілісекунди, спричинений природними флуктуаціями мережевого планувальника, дасть p_value < 0.001. Якщо контролер реагуватиме виключно на p-value, виникне явище лавиноподібних хибних відкатів (Rollback Storms).

Для розрізнення статистичної значущості та практичної інженерної деградації аналізатор ACA обчислює метрики розміру ефекту (Effect Size):

1. **Рангово-бісеріальна дельта Кліффа (Cliff's Delta):**
Непараметрична оцінка ймовірнісної переваги між двома розподілами. Вона визначає частку випадків, коли затримка в канарковій групі перевищує затримку в базовій групі, за вирахуванням зворотної частки:

```text
d = (2 * U) / (n * m) - 1 = ( count(y_j > x_i) - count(y_j < x_i) ) / (n * m)
```

Значення d знаходиться в строгому діапазоні `[-1.0; +1.0]`:
* `|d| < 0.147`: ефект зневажливо малий (Negligible), різниця в затримках лежить у межах фонового шуму ядра ОС;
* `0.147 <= |d| < 0.330`: слабкий ефект (Small);
* `0.330 <= |d| < 0.474`: помірний ефект (Medium);
* `|d| >= 0.474`: критичний зсув (Large), затримка канарки суттєво перевершує контрольну групу.

2. **Оцінювач зсуву Ходжеса-Лемана (Hodges-Lehmann Estimator):**
Непараметрична псевдомедіана всіх попарних різниць між вимірами контрольної та досліджуваної груп:

```text
Delta_HL = median( { y_j - x_i | 1 <= i <= n, 1 <= j <= m } )
```

Величина `Delta_HL` показує точний фізичний зсув затримки у мілісекундах. Вона є абсолютно стійкою до поодиноких викидів (до 29% забруднення вибірки екстремальними аномаліями).

3. **Дворівневий критерій спрацьовування аварійного вимикача (Dual Gate Trigger):**
Контролер переводить систему в стан `EMERGENCY_KILL_SWITCH` лише за одночасного виконання статистичної та практичної умов:

```text
спрацювати_Kill_Switch = (Z_score < Z_критичне) AND (p_value < alpha) AND ((Delta_HL > SLA_tolerance_ms) OR (d > 0.33))
```

Такий підхід гарантує, що релізна кампанія переривається лише тоді, коли виявлена регресія є водночас математично достовірною та перевищує виділений системний бюджет помилок.

### Багатовимірний вектор стабільності та контроль групової помилки (FDR)

У промислових мікросервісах деградація рідко обмежується лише загальною затримкою обробки. Контролер аналізує багатовимірний вектор показників стабільності когорти:

```text
M = [ P99_затримка, P50_затримка, частка_помилок_5xx, темп_споживання_CPU_на_RPS, приріст_пам'яті_RSS, паузи_GC ]
```

Одночасне проведення незалежних статистичних тестів Манна-Вітні для K різних метрик призводить до накопичення групової ймовірності помилки першого роду (Family-Wise Error Rate, FWER):

```text
FWER = 1 - (1 - alpha)^K
```

Якщо контролер відстежує K = 8 метрик за рівня значущості alpha = 0.05, сумарна ймовірність хибного спрацьовування на здоровому релізі зростає до 1 - (1 - 0.05)^8 ≈ 33.7%.

Для усунення цієї проблеми аналізатор ACA реалізує процедуру контролю частки хибних відкриттів Беньяміні-Гохберга (Benjamini-Hochberg False Discovery Rate, BH-FDR):

1. Для кожної з K метрик обчислюється індивідуальне значення p-value: `p_1, p_2, ..., p_K`.
2. Значення впорядковуються за зростанням: `p_(1) <= p_(2) <= ... <= p_(K)`.
3. Знаходиться максимальний індекс r, для якого виконується умова:

```text
p_(r) <= (r / K) * q_FDR
```

де `q_FDR = 0.05` — допустимий поріг частки хибних відкриттів.
4. Усі метрики з індексами `k <= r` визнаються такими, що мають статистично достовірну деградацію.
5. Якщо серед відхилених метрик присутні показники першого класу критичності (Tier-1: частка помилок HTTP 5xx або зростання p99-затримки понад ліміт SLA), FSM негайно запускає аварійний Kill Switch. Якщо ж регресія зафіксована лише у вторинних показниках (Tier-2: мікрозростання CPU на 3%), контролер блокує подальше розширення когорти (стан `SOAKING_FROZEN`) і надсилає сповіщення черговому інженеру без припинення обслуговування користувачів.

### Алгоритмічна оптимізація та асимптотична складність аналізатора ACA

Обчислення рангової статистики Манна-Вітні на гарячому шляху контролера не повинно створювати навантаження на процесорні кеші або блокувати системний планувальник. Оптимізована реалізація алгоритму забезпечує такі характеристики:

* **Швидке комбіноване сортування (IntroSort):** об'єднання вибірок загальним розміром N = n + m сортується за час O(N log N) без виділення динамічної пам'яті на купі процесу (використовується фіксований стек-буфер розміром 2 048 елементів).
* **Гістограмний розрахунок для квантованої телеметрії:** для мікросекундних цілочисельних замірів контролер підтримує альтернативний шлях обчислення рангів через кошики гістограми та масив префіксних сум. Це знижує часову складність ранжування до строго лінійної O(N + B), де B — кількість бінів гістограми (B = 1000).
* **Векторизація SIMD (AVX2/NEON):** підсумовування рангів та попарні операції обчислення U-статистики виконуються з використанням 256-бітних векторних регістрів, що скорочує час повного прогону тесту для N = 2 048 до менше 35 мікросекунд.

### Вимоги до мінімального розміру вибірки та статистичної потужності

Застосування статистичних критеріїв на вибірках занадто малого розміру (n, m < 10) призводить до високої ймовірності помилки другого роду (Type II Error) — пропуску реальної деградації через дефіцит статистичної потужності. З іншого боку, накопичення надмірно великих вибірок (n > 100 000) розмиває локальні за часом сплески аномалій.

Контролер підтримує оптимальний розмір ковзного вікна у 1 024 заміри. Це забезпечує потужність тесту понад 95% для виявлення 15%-го зсуву затримок і одночасно обмежує час обчислення тесту величиною менше 120 мікросекунд на сучасному процесорі x86_64.

### Потокова оцінка квантилів затримки (P95/P99) та алгоритм T-Digest

Окрім рангового критерію Манна-Вітні, промисловий контролер відстежує точні значення квантилів p95 та p99 у режимі реального часу. Збереження всіх індивідуальних вимірювань затримок у пам'яті для великих потоків (мільйони запитів на секунду) вимагає гігабайтів оперативної пам'яті. Для вирішення цього завдання контролер інтегрує алгоритм T-Digest.

T-Digest групує близькі числові значення затримок у кластери (центроїди), кожен із яких характеризується середнім значенням та сумарною вагою. Стиснення центроїдів виконується таким чином, що точність оцінки на краях розподілу (наприклад, для квантилів 0.99 та 0.999) є максимальною, тоді як у центрі розподілу допускається більше укрупнення. Це дозволяє контролеру з точністю до 0.1% відстежувати затримку p99, використовуючи менше 8 КБ пам'яті на кожну когорту.

### Послідовний аналіз Вальда (Sequential Probability Ratio Test, SPRT)

Для динамічного скорочення періоду вистоювання у випадках, коли якість канарки є бездоганною або навпаки катастрофічно низькою, контролер підтримує послідовний аналіз відношення правдоподібностей Вальда (SPRT).

Замість фіксованого очікування завершення 30-хвилинного вікна, контролер обчислює логарифмічне відношення правдоподібності LLR після кожного пакету вимірювань:

```text
LLR_k = LLR_{k-1} + ln( P(y_k | H_1) / P(y_k | H_0) )
```

де H_0 — гіпотеза про еквівалентність версій, а H_1 — гіпотеза про деградацію на 20%. Встановлюються дві межі прийняття рішень:

```text
A = ln( (1 - beta) / alpha )
B = ln( beta / (1 - alpha) )
```

Якщо `LLR >= A`, контролер негайно зупиняє кампанію (Kill Switch), не чекаючи завершення soak-періоду. Якщо `LLR <= B`, контролер достроково підтверджує стабільність когорти та переходить до наступного кроку. Якщо `B < LLR < A`, накопичення вибірок продовжується. Це скорочує середній час безпечного розгортання на 40–60%.

## Детальний аналіз внутрішніх структур даних та патернів проектування

Для забезпечення роботи в багатопотоковому середовищі без блокування гарячого шляху передачі пакетів контролер використовує спеціалізовані структури даних.

### 1. Вирівнювання структур по лініях кешу процесора (Cache-Line Alignment)

У симетричних багатопроцесорних системах (SMP) одночасне звернення кількох ядер процесора до сусідніх змінних у межах одного 64-байтного рядка кешу викликає явище помилкового розділення (False Sharing). Коли один потік записує нову затримку в буфер телеметрії канарки, кеш-лінія Baseline-буфера на іншому ядрі стає невалідною через протокол узгодженості кешів MESI.

Для усунення цього явища критичні структури контролера вирівнюються за межами 64 байтів за допомогою специфікатора вирівнювання:

```cpp
struct alignas(64) AlignedTelemetryBuffer {
    // Внутрішні поля буфера ізольовані у власній кеш-лінії
};
```

Це виключає взаємне блокування ядер і підвищує пропускну здатність накопичення телеметрії на 35–40%.

### 2. Кільцевий буфер телеметрії без динамічної пам'яті (Fixed-Size Ring Buffer)

Кільцевий буфер базується на статичному масиві типу `double` фіксованого розміру `MAX_SAMPLES_CAPACITY = 1024`. Покажчик голови `head` монотонно зміщується за модулем розміру буфера при кожному новому вимірюванні:

```text
head = (head + 1) % MAX_SAMPLES_CAPACITY
```

Під час виконання статистичного аналізу модуль ACA знімає миттєвий зліпок (Snapshot) буфера під легким м'ютексом. Час утримання блокування становить лише час копіювання 1 024 чисел з плаваючою крапкою (менше 2 мікросекунд), що повністю виключає вплив на потоки збору телеметрії.

### 3. Маршрутизація на основі консистентного хешування

Для забезпечення стабільності сесій клієнтів (Sticky Sessions) розподіл трафіку між Baseline та Canary виконується за алгоритмом хешування ідентифікатора користувача. 32-бітний хеш перетворюється на нормалізоване значення в діапазоні `[0.0; 100.0)`:

```text
кошик = (user_hash % 10000) / 100.0
обрати_канарку = (кошик < поточна_вага_когорти)
```

Якщо обчислений кошик менший за поточну вагу (наприклад, `кошик < 5.0` для 5% когорти), запит делегується вузлу з прапорцем `is_canary = true`. Завдяки цьому клієнт, що потрапив у канаркову вибірку на етапі 5%, гарантовано залишається в ній на наступних етапах 25% і 50%, що усуває міжверсійні стрибки стану сесії.

### 4. Багатопотоковий захист через RWLock та атомарні токени

Стан контролера захищено блокуванням читання-запису (`pthread_rwlock_t` у C99 або `std::shared_mutex` у C++20):

* **Операція маршрутизації `routeRequest()`:** захоплює спільне блокування на читання (`shared_lock`). Тисячі паралельних потоків воркерів можуть одночасно читати топологію без взаємних затримок.
* **Операція зміни ваги та спрацювання Kill Switch:** захоплює ексклюзивне блокування на запис (`unique_lock`). Зміна стану та обнулення ваги виконуються атомарно за константний час O(1).
* **Генераційний токен `active_epoch_token`:** інкрементується при кожному аварійному переході, забезпечуючи захист від Split-Brain на рівні взаємодії з розподіленою базою даних.

### 5. Асинхронна безпечна обробка сигналів ОС (Async-Signal Safety)

У системному програмуванні обробники сигналів Linux (`SIGTERM`, `SIGINT`, `SIGHUP`) мають обмеження: всередині обробника заборонено викликати небезпечні функції (`malloc`, `free`, `printf`, захоплення звичайних м'ютексів), оскільки це може спричинити дедлок.

Контролер реалізує патерн `signalfd` (або `self-pipe` для POSIX-сумісності):
* Сигнали ядра перетворюються у файловий дескриптор за допомогою системного виклику `signalfd()`.
* Дескриптор підключається до головного циклу обробки подій `epoll_wait()`.
* Отримання сигналу завершення обробляється як звичайна подія вводу-виводу в головному потоці, що дозволяє безпечно виконати штатний дренаж з'єднань і звільнити ресурси без ризику пошкодження пам'яті.

## Протокол аварійного дренажу сокетів (Graceful Connection Draining Protocol)

Аварійна зупинка розгортання не повинна супроводжуватися грубим обривом відкритих з'єднань. Якщо канарковий вузол обробляє тривалий розрахунковий запит, миттєве знищення процесу викличе помилку у користувача і повторну спробу запиту.

Контролер реалізує трифазний протокол штатного дренажу:

```text
[ Спрацювання Kill Switch ]
            │
            ▼
[ Фаза 1: L7 Відсікання ] ──> Маршрутна вага канарки = 0%. Нові клієнти спрямовуються на v1.
            │
            ▼
[ Фаза 2: Сигналізація L7 ] ──> Надсилання HTTP/2 GOAWAY кадру або прапорця Connection: close.
            │
            ▼
[ Фаза 3: Вичерпання сокетів ] ──> Очікування завершення активних потоків протягом вікна безпеки (30 сек).
            │
            ▼
[ Фаза 4: Переведення в Quarantine ] ──> Зняття Core Dump, відключення від внутрішньої шини.
```

При взаємодії через HTTP/2 канарковий сервер надсилає службовий кадр `GOAWAY` із зазначенням номера останнього прийнятого стріму (`Last-Stream-ID`). Це інформує клієнтський балансувальник, що нові запити по цьому TCP-з'єднанню відправляти заборонено, проте поточні запити будуть коректно доопрацьовані без виникнення помилок зв'язку.

### Низькорівнева поведінка сокетів у ядрі Linux під час дренажу

Під час виконання фази дренажу ядро операційної системи Linux переводить клієнтські сокети через ланцюг станів `ESTABLISHED -> FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT`. Контролер налаштовує параметри мережевого стека хоста:

* `net.ipv4.tcp_fin_timeout = 15`: скорочує час перебування сокета у стані `FIN_WAIT_2` до 15 секунд у разі, якщо клієнт не надіслав фінальний пакет закриття.
* `net.ipv4.tcp_max_orphans = 65536`: лімітує кількість закритих сокетів, не прив'язаних до дескриптора процесу, запобігаючи вичерпанню пам'яті ядра під час масового дренажу тисяч з'єднань.

## Апаратне відсікання трафіку через eBPF/XDP

Для ультра-високонавантажених кластерів (100GbE мережеві інтерфейси, понад 10 мільйонів пакетів на секунду) перемикання маршрутизації на рівні користувацького простору (User Space) створює надмірне навантаження на процесор. Автономний контролер підтримує пряму інтеграцію з ядром через eBPF/XDP (eXpress Data Path).

Контролер підтримує спільну BPF-карту типу `BPF_MAP_TYPE_ARRAY` або `BPF_MAP_TYPE_HASH`, у якій зберігається поточна вага канарки та список IP-адрес вузлів. Коли модуль контролера приймає рішення про спрацювання Kill Switch, він записує значення `0` у BPF-карту через системний виклик `bpf_map_update_elem()`. XDP-програма, що виконується безпосередньо в драйвері мережевої карти, перенаправляє всі наступні вхідні мережеві пакети на IP-адреси вузлів v1 за час менше 50 наносекунд без перемикання контексту процесора.

## Інтеграція з розподіленим консенсусом та генераційне огородження

У розподілених архітектурах контролер розгортання не функціонує в ізоляції. Будь-яка зміна маршрутної ваги або аварійна зупинка повинні синхронізуватися з кластерним координатором консенсусу (etcd, HashiCorp Consul або внутрішня Raft-група).

### Механіка координації епох через транзакції CAS

Коли контролер активує `triggerEmergencyKillSwitch()`, він виконує атомарну транзакцію порівняння зі збереженням (Compare-And-Swap, CAS) у розподіленому реєстрі:

```text
txn = etcd.Txn()
txn.If(
    etcd.Compare(Version("rollout/epoch"), "==", current_epoch)
).Then(
    etcd.Put("rollout/epoch", current_epoch + 1),
    etcd.Put("rollout/canary_weight", "0.0"),
    etcd.Put("rollout/status", "HALTED_QUARANTINE")
)
```

Будь-які прикладні RPC-запити між мікросервісами несуть заголовок `X-Cluster-Epoch: 1001`. Якщо вузол нової версії v2 намагається виконати запис у базу даних зі застарілим токеном `Epoch: 1000`, проміжний проксі або тригер сховища негайно відхиляє мутацію. Це виключає загрозу неконсистентного оновлення записів, навіть якщо окремий вузол канарки ще не встиг отримати команду дренажу сокетів через мережеву затримку.

### Взаємодія з балансувальником Envoy через xDS API

У промислових середовищах на базі сервіс-мешу контролер транслює стан вагових коефіцієнтів у площину керування Envoy (Control Plane) через протокол Dynamic Route Discovery Service (RDS):

1. Контролер формує оновлений маніфест кластерів `envoy.config.route.v3.WeightedCluster`.
2. Базовий кластер `cluster_v1` отримує вагу `100 - W`, канарковий кластер `cluster_v2` отримує вагу `W`.
3. Оновлення надсилається по gRPC стріму xDS. Envoy застосовує нову конфігурацію без розриву активних TCP-сесій за час менше 10 мілісекунд.

## Покроковий розбір сценаріїв виконання

Розглянемо послідовність внутрішніх операцій контролера у двох типових сценаріях: штатному успішному просуванні релізу та аварійній деградації з миттєвим перериванням.

### Сценарій 1: Штатне просування когорт без деградації

1. **Ініціалізація:** зовнішній виклик `startRollout()` переводить контролер зі стану `IDLE` у стан `INITIALIZING`. Перевіряється доступність усіх вузлів у пулі.
2. **Фаза 1 (1% трафіку):** вага маршрутизації встановлюється у значення `current_weight_percent = 1.0`. Буфери телеметрії очищаються від застарілих даних. Диспетчер переходить у стан `SOAKING`.
3. **Вистоювання та набір телеметрії:** маршрутизатор спрямовує клієнтів із хешем `hash < 100` на канарку, а решту 99% — на контрольну групу (Baseline). Кільцеві буфери паралельно накопичують заміри затримок у мікросекундах.
4. **Статистичний аналіз ACA:** після закінчення вікна вистоювання модуль `StatisticalEngine::evaluate` обчислює рангову U-статистику. Оскільки медіани та хвости затримок обох груп ідентичні, значення `z_score` знаходиться в межах `[-0.4; +0.3]`, а `p_value > 0.05`. Гіпотеза про деградацію відхиляється.
5. **Послідовне розширення:** контролер автоматично підвищує вагу: 5% → 25% → 50% → 100%. На фінальному кроці реліз закріплюється у стані `PROMOTED_FULL`.

### Сценарій 2: Аварійна деградація на етапі 25% та Kill Switch

1. **Виникнення аномалії:** на етапі 25% канарковий бінарний файл v2 починає зазнавати внутрішніх блокувань м'ютексів. Затримки p99 канарки зростають до 450 мілісекунд, тоді як контрольна група показує стабільні 12 мілісекунд.
2. **Фіксація регресії статистичним суддею:** під час чергового такту `tick()` у стані `EVALUATING_ACA` обчислена Z-статистика Манна-Вітні падає до значення `z_score = -4.12` при `p_value = 0.000038` (строго менше порогу `alpha = 0.01`).
3. **Миттєве переривання O(1):** контролер викликає `triggerEmergencyKillSwitch()`. Стан змінюється на `EMERGENCY_KILL_SWITCH`, вага канарки миттєво обнуляється (`current_weight_percent = 0.0`), а лічильник генерації `active_epoch_token` інкрементується.
4. **Маршрутна ізоляція:** усі наступні виклики `routeRequest()` відкидають будь-які канаркові вузли та спрямовують 100% потоку виключно на стабільну версію v1.14.
5. **Дренаж активних стрімів:** канаркові вузли позначаються прапорцем `is_draining = true`. Контролер витримує паузу для завершення прийнятих транзакцій.
6. **Карантин та замороження:** контролер переходить у фінальний стан `ROLLED_BACK`. Канаркові процеси переводяться в режим аудиту для зняття Core Dump, а змішаний парк продовжує стабільне функціонування.

## Експлуатаційний гайд: тестування надійності, Chaos Engineering та запуск

Перед введенням автономного контролера в експлуатацію на промисловому кластері проводять обов'язковий комплекс верифікації надійності.

### 1. Тестування стійкості до розривів мережі (Network Partition Testing)

У контурі тестування емулюється повна втрата мережевого зв'язку між контролером та половиною серверних вузлів за допомогою утиліти `iptables`:

```bash
# Блокування трафіку телеметрії від канаркових вузлів
iptables -A INPUT -p tcp --dport 9090 -s 10.244.3.0/24 -j DROP
```

Контролер фіксує зупинку надходження зразків телеметрії від канарки. Оскільки мінімальний поріг вибірки `n >= 10` не досягається, автомат блокує просування до наступної когорти та активує попереджувальний сигнал `STALLED_TELEMETRY`.

### 2. Симуляція дедлоків та лавиноподібного зростання пам'яті (Chaos Injection)

За допомогою тестових утиліт інжекції несправностей у канаркові процеси впроваджуються штучні затримки:

```bash
# Інжекція 500 мс штучної затримки у 30% запитів канаркового вузла
curl -X POST http://127.0.0.1:8081/chaos/inject_latency -d '{"delay_ms": 500, "ratio": 0.3}'
```

Аналізатор ACA фіксує розходження рангів за 2.4 секунди та викликає Kill Switch, підтверджуючи коректність математичного порогу Z-score.

### 3. Комплексна конфігурація контролера для виробничого контуру

Промисловий екземпляр демона контролера налаштовується за допомогою файлу конфігурації у форматі JSON або YAML:

```json
{
  "controller": {
    "evaluation_interval_ms": 1000,
    "soak_period_seconds": 1800,
    "alpha_significance_level": 0.01,
    "critical_z_score": -2.58,
    "min_samples_threshold": 30,
    "ring_buffer_capacity": 2048,
    "drain_timeout_seconds": 45,
    "fencing": {
      "consensus_backend": "etcd",
      "lease_ttl_seconds": 10,
      "epoch_key_path": "/production/rollouts/epoch"
    },
    "routing_progression_steps": [
      1.0,
      5.0,
      25.0,
      50.0,
      100.0
    ]
  }
}
```

### 4. Інтеграція з Prometheus та експорт метрик у режимі реального часу

Контролер підтримує вбудований HTTP-ендпоінт для скрейпінгу системою Prometheus за стандартом OpenMetrics. Моніторинг надає черговій зміні вичерпні показники здоров'я FSM:

* `rollout_state_current`: поточний стан скінченного автомата (0 = IDLE, 4 = EVALUATING_ACA, 5 = KILL_SWITCH).
* `rollout_canary_weight_ratio`: поточна вага трафіку канаркової когорти (від 0.0 до 1.0).
* `aca_mann_whitney_z_score`: поточне значення Z-статистики тесту Манна-Вітні.
* `aca_mann_whitney_p_value`: поточний рівень статистичної значущості p-value.
* `active_epoch_token_total`: актуальний лічильник генераційного токена консенсусу.
* `draining_sockets_in_flight`: кількість активних клієнтських стрімів на вузлах, що проходять штатний дренаж.

### 5. Поведінка пулів потоків воркерів під час різкого повернення навантаження

Коли канаркові вузли виводяться з балансування через Kill Switch, навантаження на базові вузли v1 миттєво зростає. Для запобігання падінню базового пулу контролер взаємодіє з підсистемою автоскейлінгу:

* **Обмежені черги задач (Bounded Worker Queues):** кожен воркер має чергу фіксованої довжини (10 000 задач). При переповненні черги надлишкові запити відхиляються з кодом `HTTP 429 Too Many Requests` замість аварійного падіння процесу через брак пам'яті.
* **Прив'язка потоків до процесорних ядер (CPU Pinning):** потоки накопичення телеметрії закріплюються за окремими ізольованими ядрами за допомогою `pthread_setaffinity_np()`, що виключає затримки на контекстні перемикання операційної системи.

### 6. Регламент судової експертизи в карантині (Post-Incident Forensics)

Після переведення канаркових екземплярів у режим карантину автоматичний скрипт виконує збір діагностичних артефактів:

1. Демон надсилає процесу сигнал `SIGABRT` або генерує дампи пам'яті за допомогою утиліти `gcore`:
   ```bash
   gcore -o /var/log/quarantine/core_dump_canary_node_104 $(pgrep canary_service)
   ```
2. Знімається детальний зліпок алокацій купи пам'яті (Heap Profiling) за допомогою `jemalloc` profiler.
3. Експортуються останні 100 000 записів із внутрішнього кільцевого буфера трасування запитів (Flight Recorder).
4. Отриманий діагностичний архів передається команді розробників для ретроспективного аналізу без зупинки виробничого кластера.

### 7. Динамічне перечитування конфігурації без зупинки демона (SIGHUP Hot Reload)

У промисловій експлуатації зміна порогових коефіцієнтів (наприклад, калібрування значення `critical_z_score` або зміна тривалості soak-вікна) не повинна вимагати перезапуску самого демона контролера, оскільки це призвело б до тимчасової втрати спостережуваності над активним розгортанням.

Контролер підтримує протокол гарячого перечитування конфігурації за сигналом `SIGHUP`:
* Головний потік отримує подію через `signalfd` і зчитує новий JSON-маніфест у тіньову структуру конфігурації.
* Виконується валідація діапазонів числових параметрів (перевірка, що `alpha > 0.0` та прогресія кроків є строго монотонною).
* Захоплюється ексклюзивне блокування на запис `unique_lock` і покажчик конфігурації атомарно підміняється за константний час.
* Активна фаза FSM продовжує виконання з новими калібрувальними порогами без скидання накопичених буферів телеметрії.

### 8. Архітектура плагінів та розширюваність аналізаторів ACA

Для адаптації контролера під специфічні прикладні домени (наприклад, оцінка транзакційних помилок фінансового процесингу, коефіцієнтів відхилення замовлень або бітрейту медіа-стрімінгу) підсистема ACA підтримує модульну архітектуру плагінів:

* **Інтерфейс `IEvaluationPlugin`:** визначає обов'язкові методи `EvaluateSamples()`, `GetPluginName()` та `GetHealthVerdict()`, що інкапсулюють специфічні правила валідації для різнорідних типів бізнес-метрик.
* **Динамічне завантаження бібліотек (`dlopen` / `dlsym`):** контролер може підключати додаткові скомпільовані статистичні бібліотеки під час виконання без перекомплікації або рестарту бінарного ядра системи.
* **Каскадна оцінка метрик:** підсумкове рішення про безпеку переходу когорти формується як зважений консенсус групи плагінів (затримка, частка помилок HTTP 5xx, інтенсивність споживання ресурсів пам'яті CPU/RSS, темп вичерпання пулів дескрипторів). Якщо хоча б один плагін фіксує критичну аномалію вище граничного порогу, FSM виконує негайне аварійне переривання.
* **Журнал ретроспективних викликів:** кожен зареєстрований плагін записує розраховані статистичні коефіцієнти у спільний діагностичний журнал для подальшого аудиту.

### 9. Регламент ручного втручання та скидання аварійного стану

Якщо аварійна зупинка відбулася через хибне спрацьовування (наприклад, викликане зовнішнім збоєм тестового стенду), черговий інженер може безпечно скинути стан контролера:

```bash
# Виклик адміністративного ендпоінта скидання FSM контролера
curl -X POST http://127.0.0.1:9000/api/v1/rollout/reset \
  -H "X-Admin-Token: $SECRET_ADMIN_TOKEN" \
  -d '{"target_state": "IDLE", "force_epoch_advance": true}'
```

Після виконання команди контролер повертається у стан `IDLE`, перевіряє стан вузлів і стає готовим до запуску нового релізного циклу.

### 10. Інваріанти виробничої експлуатації

Автономний контролер гарантує виконання чотирьох ключових експлуатаційних інваріантів:
1. **Детермінізм часу реакції:** перехід у стан `EMERGENCY_KILL_SWITCH` та обнулення маршрутної ваги канарки відбуваються за час O(1) менше 1 мілісекунди після виявлення аномалії.
2. **Нульовий Stop-the-World:** операції читання таблиць маршрутизації виконуються паралельно тисячами воркерів без блокування потоків виконання.
3. **Захист від пошкодження даних:** інкремент генераційного токена епохи виключає виконання застарілих транзакцій изолированими вузлами.
4. **Збереження діагностичних слідів:** автоматичний перехід дефектних екземплярів у карантинний контур дозволяє команді розробників отримати повний зліпок пам'яті та журнал транзакцій для швидкого усунення дефекту.
