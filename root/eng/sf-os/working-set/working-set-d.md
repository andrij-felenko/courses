Коли скомпільована програма виконує обчислювальний цикл або обробляє вхідний запит мережевого сокета, вона взаємодіє не з усіма мегабайтами виділеної їй віртуальної пам'яті одночасно. Із сотень тисяч сторінок, які операційна система відобразила в адресний простір задачі (код бібліотек, структури стеків, буфери купи), лише невелика підмножина отримує звернення на читання чи запис протягом короткого відрізка часу. Якщо ця активна група сторінок повністю розміщена у фізичних кадрах оперативної пам'яті, процесор виконує інструкції на штатній частоті, звертаючись до даних за лічені наносекунди через апаратні кеші та буфер трансляції адрес (TLB). Проте якщо операційна система витіснить на вторинний накопичувач хоча б одну сторінку з цього активного ядра, перша ж інструкція процесора викличе апаратний сторінковий збій, примусово зупинить потік і змусить його очікувати на операцію дискового читання протягом десятків тисяч тактів.

Ця фундаментальна нерівномірність звернень до пам'яті вимагає від операційної системи чіткого механізму визначення того, які саме сторінки процесу є критично важливими тут і зараз, а які можуть бути безпечно вивантажені на диск.

## Принцип локальності та модель Деннінга

Здатність системи передбачати майбутні потреби процесу в пам'яті спирається на емпіричну властивість алгоритмів — **локальність звернень** (від лат. *localis* — місцевий, від *locus* — місце). Локальність проявляється у двох вимірах:

1. **Часова локальність** (від лат. *temporalis* — часовий): якщо інструкція звернулася до адреси в пам'яті, з високою ймовірністю до цієї самої адреси або сусідніх даних відбудеться повторне звернення в найближчі цикли виконання (наприклад, змінні лічильників циклів, верхівка стека викликів, гарячі записи геш-таблиці).
2. **Просторова локальність** (від лат. *spatium* — простір): звернення до певної комірки пам'яті робить імовірним наступне звернення до комірок із близькими адресами (послідовне проходження масиву, виконання лінійного блоку машинних інструкцій).

У 1968 році американський дослідник Пітер Деннінг (Peter J. Denning) формалізував зв'язок між локальністю та керуванням пам'яттю, запропонувавши **модель робочої множини** (англ. *working set model*; від праслов. *orbъ* — праця, множина від *mъnogъ* — численний).

Поведінка процесу розглядається як дискретний потік звернень до сторінок:

```
r(1), r(2), r(3), ..., r(t)
```

де `r(t)` — номер віртуальної сторінки, до якої процесор звертається під час виконання `t`-ї інструкції.

Для аналізу вводиться параметр `Δ` — **вікно спостереження** (observation window), що вимірюється кількістю виконаних інструкцій пам'яті або інтервалом процесорного часу.

**Робоча множина** `W(t, Δ)` у момент часу `t` визначається як сукупність усіх унікальних сторінок, до яких процес звертався протягом інтервалу `[t - Δ + 1, t]`:

```
W(t, Δ) = { r(τ) : t - Δ + 1 ≤ τ ≤ t }
```

Кількість сторінок у цій підмножині називається **розміром робочої множини** і позначається як `w(t, Δ) = |W(t, Δ)|`.

![Вікно спостереження часової локальності за моделлю Деннінга](/root/eng/sf-os/working-set/img/denning-window.svg)
*Вікно спостереження часової локальності за моделлю Деннінга: стрічка звернень та виділення унікальних активних сторінок.*

Історичні передумови появи цієї моделі, криза ранніх алгоритмів заміщення сторінок FIFO та відкриття аномалії Беладі детально висвітлені у вставці [Від аномалії Беладі до моделі Деннінга](root:sf-os/working-set/hist-denning-model.md).

З моделі випливає ключовий висновок: пам'ять процесу не є монолітною статичною величиною. Замість виділення фіксованої кількості сторінкових кадрів ядро мусить безперервно підлаштовувати обсяг виділеної фізичної пам'яті під поточний розмір `w(t, Δ)`.

## Динаміка фаз виконання та крива розміру робочої множини

Програми не зберігають незмінний патерн доступу до пам'яті протягом усього життєвого циклу. Виконання коду розпадається на послідовність стабільних інтервалів — **фаз** (від грец. *φάσις* — поява, фаза), розділених короткими перехідними періодами.

Під час стабільної фази (наприклад, виконання вкладеного циклу обробки матриці) процес багаторазово циркулює по одній і тій самій невеликій групі сторінок коду та даних. Робоча множина `W(t, Δ)` залишається сталою за складом і компактною за розміром. Проте коли алгоритм завершує розрахунок і переходить до наступного кроку (наприклад, сортування результатів або запису на диск), стара множина сторінок миттєво стає холодною, а процес починає інтенсивно звертатися до нових ділянок віртуального простору. У цей перехідний момент виникає сплеск сторінкових збоїв, після чого формується нова стабільна робоча множина.

Якщо дослідити залежність середнього розміру робочої множини `w(Δ)` від ширини вікна спостереження `Δ` для типової фази програми, крива демонструє чітко виражену трифазну структуру:

1. **Фаза внутрішньоциклової локальності (малі `Δ`):** При збільшенні вікна від 1 до кількох сотень звернень розмір `w(Δ)` стрімко зростає. У вікно потрапляють безпосередні робочі змінні, локальні масиви та тіло поточного циклу.
2. **Фаза стабільного плато (робоче вікно `Δ*`):** Коли вікно стає достатнім для покриття всього тіла поточної підпрограми чи алгоритмічного кроку, зростання `w(Δ)` сповільнюється або повністю зупиняється. Усі звернення потрапляють у вже враховані сторінки. Точка перегину `Δ*` визначає мінімально необхідний розмір пулу кадрів для безперешкодної роботи задачі.
3. **Фаза повного адресного простору (великі `Δ`):** При надмірно великих значеннях `Δ` вікно починає охоплювати попередні фази виконання програми (наприклад, етап зчитування конфігурації або минулий цикл обробки). Розмір `w(Δ)` поступово наближається до загального обсягу виділеної віртуальної пам'яті програми (VSS), утримуючи в пам'яті вже непотрібні холодні дані.

![Характеристична крива розміру робочої множини та частоти збоїв](/root/eng/sf-os/working-set/img/working-set-curve.svg)
*Характеристична крива розміру робочої множини w(Δ) та частоти збоїв m(Δ): оптимальний розмір кадрового пулу.*

Між розміром робочої множини та частотою виникнення сторінкових збоїв `m(Δ)` (missing page rate) існує строгий математичний зв'язок. Якщо процес забезпечений кадрами пам'яті для утримання `W(t, Δ)`, сторінковий збій на кроці `t + 1` стається тоді і тільки тоді, коли наступне звернення `r(t + 1)` виходить за межі поточної множини:

```
r(t + 1) ∉ W(t, Δ)
```

Математичне сподівання частоти збоїв дорівнює приросту розміру робочої множини при одиничному розширенні вікна:

```
m(Δ) = w(Δ + 1) - w(Δ)
```

У неперервному наближенні:

```
m(Δ) = dw(Δ) / dΔ
```

Частота сторінкових збоїв є похідною від характеристики розміру робочої множини. На ділянці плато (де `dw/dΔ ≈ 0`) частота збоїв прямує до нуля. Це означає, що утримання в оперативній пам'яті саме `w(Δ*)` сторінок гарантує практично безперервне виконання коду без затримок на вторинних накопичувачах.

Повний математичний вивід цієї тотожності, моделі незалежних звернень (IRM) та стекових відстаней розібрано у вставці [Математична модель робочої множини](root:sf-os/working-set/math-working-set-size.md).

## Трішинг: катастрофічний колапс продуктивності

Коли в багатозадачній операційній системі одночасно працює `N` процесів, кожен із них потребує певної кількості фізичних кадрів для розміщення своєї робочої множини `w_i(t, Δ)`. Нехай загальна кількість фізичних кадрів оперативної пам'яті, доступних для користувацьких процесів, дорівнює `M_avail`.

Поки сума робочих множин не перевищує обсяг фізичної пам'яті:

```
∑ [i=1..N] w_i(t, Δ) ≤ M_avail
```

система працює в стабільному режимі. Центральний процесор утилізує обчислювальні потужності на високому рівні, а сторінкові збої виникають переважно при зміні фаз виконання задач.

Проте якщо кількість процесів зростає або один із процесів різко збільшує свій робочий набір так, що:

```
∑ [i=1..N] w_i(t, Δ) > M_avail
```

виникає системна криза, відома як **трішинг** (від англ. *thrashing* — битися, молотити, безладно метатися, від давньоангл. *þrescan*).

![Явище трішингу та обвал корисної роботи процесора](/root/eng/sf-os/working-set/img/thrashing-collapse.svg)
*Явище трішингу: обвал завантаження CPU при перевищенні сумарними робочими множинами доступної фізичної пам'яті.*

Механізм розвитку трішингу має характер самопідсилюваної ланцюгової реакції:

1. **Брак кадрів для розміщення множин:** Процес `A` звертається до сторінки, якої немає в пам'яті, і викликає сторінковий збій.
2. **Витіснення чужої робочої сторінки:** Оскільки вільних фізичних кадрів немає, алгоритм глобального заміщення пам'яті обирає сторінку-жертву, що належить процесу `B`. Проте сторінка процесу `B` не є холодною — вона входить до його активної робочої множини `W_B`.
3. **Каскадні збої:** Процес `B` отримує квант часу від планувальника, виконує одну інструкцію і негайно зазнає сторінкового збою, оскільки його активна сторінка щойно була відібрана. Ядро, намагаючись врятувати процес `B`, забирає сторінку у процесу `C` або повертає щойно виділений кадр у процесу `A`.
4. **Колапс дискової підсистеми:** Усі активні процеси переходять у стан очікування дискового введення-виведення (стан блокування `D` у Linux). Черга запитів до сховища зростає лавиноподібно.
5. **Обвал утилізації CPU:** Оскільки всі потоки заблоковані на I/O, планувальник не має готових до виконання задач (`Runnable`). Завантаження процесора падає майже до 0%, хоча система перебуває в стані граничного перевантаження.

Важливо розуміти, що збільшення простору підкачки (swap) не усуває трішинг. Своп лише надає додаткове дискове сховище для розміщення витіснених сторінок, але швидкість дискового читання (навіть для найшвидших накопичувачів NVMe) відстає від швидкості RAM на три-чотири порядки (мікросекунди проти наносекунд). Якщо активні робочі множини процесів не поміщаються у фізичній пам'яті, система неминуче витрачатиме 99% часу на безперервне перекачування сторінок між RAM та диском.

У класичних операційних системах захистом від трішингу слугував **контроль допустимості** (admission control): якщо сума робочих множин перевищувала обсяг RAM, система примусово вивантажувала один із процесів цілком у простір підкачки (swapping) та блокувала його запуск, вивільняючи ресурси для стабільної роботи решти задач.

> 🔧 **Навіщо це.**
> У сучасних хмарних серверах та контейнеризованих кластерах (Kubernetes) трішинг є головною причиною раптової деградації затримок сервісів (Latency Spikes). Якщо сумарні ліміти пам'яті контейнерів на одній фізичній ноді перевищують обсяг RAM (Overcommit), виникнення сплеску трафіку одночасно на кількох сервісах провокує сторінковий шторм. Розуміння межі робочої множини дозволяє інженерам налаштовувати безпечні рівні перепідписки та своєчасно ізолювати перевантажені cgroups.

## Оцінка робочої множини в ядрі Linux

Точна програмна реалізація вікна спостереження за моделлю Деннінга в реальному часі неможлива: реєстрація кожного звернення до пам'яті програмним шляхом сповільнила б роботу процесора в сотні разів.

Тому ядро Linux використовує апаратну підтримку процесора та багаторівневі компромісні алгоритми. Під час кожного звернення процесора до адреси через таблицю сторінок блок MMU автоматично виставляє спеціальний прапорець у записі сторінки (PTE) — **біт звернення** (`Accessed` на архітектурі x86-64 або `Access Flag (AF)` на ARM64).

### Двосмугові списки LRU: Active та Inactive

Для керування сторінками пам'яті ядро групує фізичні кадри в списки сторінок за принципом найменш вживаних (Least Recently Used, LRU). Щоб відрізнити справді гарячу робочу множину від сторінок, до яких звернулися лише один раз під час фонового сканування, Linux підтримує роздільні списки сторінок для кожного вузла пам'яті (структура `pglist_data` у NUMA) та контрольної групи (структура `lruvec` у cgroups v2):

- **`Active List` (активний список):** Сторінки, що активно використовуються (їхній апаратний біт `Accessed` періодично встановлюється в `1`, а в структурі сторінки встановлено прапорець `PG_active`). Вони захищені від негайного вилучення і формують поточну оцінку робочої множини.
- **`Inactive List` (неактивний список):** Сторінки-кандидати на витіснення (прапорець `PG_active` скинуто). Якщо ядру потрібні вільні кадри, сторінки вилучаються саме з хвоста неактивного списку.

Списки додатково розділені за типом збережених даних:
- **Анонімні списки (`anon_active`, `anon_inactive`):** Купа, стек, дані процесів (`malloc`, `mmap MAP_ANONYMOUS`), що можуть бути скинуті лише у простір підкачки (swap).
- **Файлові списки (`file_active`, `file_inactive`):** Кеш сторінок (Page Cache) зчитування та запису файлів, які можуть бути негайно скинуті або записані назад у файлову систему.

![Архітектура списків Active/Inactive та алгоритм Refault Distance у Linux](/root/eng/sf-os/working-set/img/linux-lru-refault.svg)
*Оцінка робочої множини в ядрі Linux: взаємодія списків Active/Inactive та розрахунок дистанції повторного збою.*

Фоновий демон ядра **`kswapd`** регулярно сканує сторінки в активному списку функцією `shrink_active_list()`. Ядро обходить таблиці сторінок через механізм зворотного відображення (reverse mapping, rmap), очищає біт `Accessed` у PTE і скидає прапорець `PG_referenced`. Через деякий час стан сторінки перевіряється знову:
- Якщо біт залишився рівним `0`, сторінка не використовувалася протягом інтервалу перевірки. Вона деактивується (скидається прапорець `PG_active` і сторінка переміщується в `Inactive List`).
- Якщо біт знову встановлений у `1`, сторінка підтверджує свій статус активної робочої множини і залишається в `Active List`.

Коли пам'ять потребує негайного вивільнення, функція `shrink_inactive_list()` бере сторінки з хвоста неактивного списку. Для кожної сторінки викликається `shrink_page_list()`:
1. Перевіряється, чи сторінка не була модифікована (`PG_dirty`).
2. Якщо сторінка чиста (чистий файловий кеш), вона негайно вилучається з таблиць сторінок та кешу сторінок, а її фізичний кадр повертається алокатору двійкових близнюків.
3. Якщо сторінка брудна (анонімна пам'ять або незбережений файл), ядро ініціює асинхронний запис у простір підкачки або на диск (`pageout()`), позначає сторінку прапорцем `PG_reclaim` і звільняє її після завершення операції запису.

Якщо сторінка з неактивного списку отримує повторний доступ до моменту вилучення, спрацьовує активація: вона негайно позначається `PG_active` і повертається на початок `Active List`.

### Баланс між анонімною та файловою пам'яттю

Під час сканування списків ядро мусить вирішити, скільки сторінок сканувати з анонімного списку, а скільки — з файлового. Цей баланс регулюється параметром ядра `vm.swappiness` (від 0 до 200) та розрахунком відносного пріоритету сканування:

```
anon_prio = swappiness
file_prio = 200 - swappiness
```

Ядро пропорційно ділить зусилля `kswapd` між `shrink_list(anon)` та `shrink_list(file)`. Якщо `swappiness = 60` (значення за замовчуванням), ядро віддає перевагу вилученню файлового кешу (`file_prio = 140`), оскільки читання чистої сторінки з файлу часто є дешевшим за вивантаження анонімної пам'яті у своп.

### Алгоритм Refault Distance (workingset.c)

Традиційний двосмуговий LRU страждав від фундаментального недоліку: співвідношення розмірів активного та неактивного списків було фіксованим (за замовчуванням 2:1 або 1:1). Якщо процес активно працював із великим файловим кешем, активний список витісняв інші сторінки в неактивний, де вони передчасно скидалися на диск.

Для подолання цієї проблеми Йоганнес Вайнер (Johannes Weiner) розробив алгоритм **Refault Distance** (реалізований у файлі ядра `mm/workingset.c`):

1. **Тіньовий запис вилучення (Eviction Shadow Entry):** Коли сторінка витісняється з неактивного списку на диск, її структура `struct page` вивільняється, але в дереві радікс-покажчиків кешу сторінок (XArray) залишається компактний дескриптор — **тіньовий запис** (shadow entry). Він містить глобальний лічильник кількості вилучень сторінок `eviction_counter`, зафіксований на момент скидання.
2. **Повторний сторінковий збій (Refault):** Коли процес знову звертається до цієї самої сторінки, виникає сторінковий збій. Ядро знаходить тіньовий запис і обчислює дистанцію вилучення:
   ```
   refault_distance = current_eviction_counter - shadow_eviction_counter
   ```
3. **Оцінка належності до робочої множини:** Ядро порівнює отриману дистанцію з поточним розміром активного списку `active_list_size`:
   - Якщо `refault_distance ≤ active_list_size`, це означає: якби пам'ять була трохи більшою (або активний список не займав надмірно багато місця), ця сторінка не була б вилучена. Її витіснення було передчасною помилкою.
   - У цьому випадку ядро **негайно промотує сторінку прямо в `Active List`**, оминаючи неактивний список, і динамічно збільшує квоту активного списку за рахунок неактивного.

Завдяки цьому механізму ядро Linux автоматично адаптує баланс між активними та неактивними сторінками під реальну часову локальність робочого навантаження.

### Вплив прозорих гігантських сторінок (THP) на робочу множину

Використання прозорих гігантських сторінок (Transparent Huge Pages, THP обсягом 2 МБ на архітектурі x86-64) суттєво змінює динаміку робочої множини:

1. **Зниження навантаження на TLB:** Одна гігантська сторінка покриває 512 стандартних сторінок по 4 КБ. Це скорочує кількість записів у буфері трансляції адрес TLB у 512 разів, зменшуючи латентність звернень на фазі інтенсивного доступу до пам'яті.
2. **Збільшення гранулярності робочої множини:** Якщо процес реально звертається лише до 8 КБ даних у межах 2-мегабайтного діапазону, ядро змушене виділити та утримувати в оперативній пам'яті всі 2 МБ фізичного кадру. Це штучно роздуває робочу множину (внутрішня фрагментація).
3. **Розщеплення сторінок при дефіциті (Page Splitting):** Коли тиск на пам'ять наростає, функція ядра `split_huge_page()` розбиває неактивні 2-мегабайтні сторінки на 512 незалежних 4-кілобайтних сторінок, дозволяючи витіснити лише холодні залишки діапазону й утримати гаряче ядро робочої множини.

### Multi-Gen LRU (MGLRU): сучасна еволюція відстеження робочої множини

Починаючи з версії Linux 6.1, у ядро інтегровано архітектуру **Multi-Gen LRU (MGLRU)**. Класичний двосмуговий LRU страждає від високих накладних витрат на глобальне блокування списків (`lru_lock`) на багатоядерних серверах із терабайтами пам'яті.

MGLRU замінює два списки (Active/Inactive) ієрархією когорт — поколінь (generations):
- Пам'ять розбивається на кілька вікових генерацій сторінок (від наймолодшої до найстарішої).
- Замість безперервного переміщення окремих сторінок між двозв'язними списками ядро просуває ціле покоління вперед за допомогою лічильника поколінь (Generation Index).
- Оцінка гарячості сторінок виконується за допомогою швидкого сканування таблиць сторінок (Page Table Scanning) та багаторівневих бітів звернення, що усуває конкуренцію за блокування пам'яті й підвищує точність утримання робочої множини на високонавантажених серверах.

## Шкала тиску пам'яті, PSI та аварійне реагування

Коли алокація пам'яті процесами починає випереджати швидкість звільнення сторінок демоном `kswapd`, система проходить чотири послідовні градації дефіциту ресурсів.

Для розмежування цих станів підсистема керування пам'яттю використовує три **водяні знаки** (watermarks; від англ. *watermark* = *water* + *mark* від герм. *marka* — межа):
- `WMARK_HIGH`: Рівень безпеки. Виділення пам'яті відбувається миттєво.
- `WMARK_LOW`: Поріг активації фонового звільнення. Прокидається `kswapd` і працює у фоні, повертаючи вільні кадри до рівня `WMARK_HIGH`. Процеси не блокуються.
- `WMARK_MIN`: Критичний поріг. Фоновий реклейм не встигає. Процеси переходять у режим **прямого реклейму** (Direct Reclaim) — сам потік, що викликав виділення пам'яті, блокується на CPU і змушений власноруч сканувати списки LRU та записувати брудні сторінки на диск.

### Механізм дротелювання у Control Groups v2

Усередині контейнерів керування пам'яттю забезпечується контрольними групами cgroups v2. Замість раптового аварійного знищення процесу ядро застосовує механізм поступового уповільнення — **дротелювання** (throttling):

- Коли споживання пам'яті контрольної групи перевищує поріг `memory.high`, ядро не зупиняє процес, але під час кожного наступного системного виклику виділення пам'яті примусово додає штучну затримку (sleep на кілька мілісекунд).
- Тривалість затримки пропорційна величині перевищення ліміту. Це сповільнює генерацію запитів до пам'яті швидкозростаючим сервісом, даючи фоновому реклейму час звільнити неактивні кадри без виникнення сторінкового колапсу.
- Якщо ж споживання досягає жорсткої межі `memory.max`, потік блокується повністю для виконання прямого реклейму. Якщо вивільнити пам'ять не вдається — ініціюється виклик OOM Killer для цієї конкретної cgroup.

### Метрики тиску PSI (Pressure Stall Information)

Традиційні метрики моніторингу (обсяг зайнятої пам'яті в байтах або відсотках) не дають відповіді на питання, чи вистачає процесам пам'яті: майже весь обсяг RAM у сучасних Linux-серверах штатно заповнений кешем сторінок.

Для прямого вимірювання затримок було створено інтерфейс **Pressure Stall Information (PSI)**, доступний через `/proc/pressure/memory`:

- **`some`:** Частка часу, протягом якого хоча б один потік виконання був заблокований на очікуванні пам'яті (Direct Reclaim або зчитування сторінок).
- **`full`:** Частка часу, протягом якого **всі** активні потоки процесора були одночасно заблоковані на пам'яті. Значення `full > 0%` свідчить про початок трішингу.

На основі подій PSI працюють сучасні демони захисту пам'яті в просторі користувача, такі як **`systemd-oomd`** або **`oomd`** від Meta. Вони реєструють тригери через виклик `epoll()` і при перевищенні заданого порогу тиску (наприклад, `full > 20%` протягом 1 секунди) завершують найменш пріоритетні фонові процеси або скидають некритичні кеші задовго до того, як зависне все ядро.

Детальний опис форматів даних, налаштувань cgroup v2 та системних параметрів sysctl зібрано у вставці [Інтерфейси ядра Linux: тиск пам'яті та PSI](root:sf-os/working-set/api-linux-memory-pressure.md).

### Останній рубіж: Out-Of-Memory (OOM) Killer

Якщо всі механізми реклейму вичерпані, рівень вільної пам'яті падає нижче `WMARK_MIN`, а черга запитів блокує виконання системи, спрацьовує крайній захисний механізм ядра — **OOM Killer**.

Ядро сканує таблицю процесів і для кожної задачі розраховує підсумкову оцінку схильності до аварійного завершення (`oom_score`). Формула базується на частці фізичної пам'яті, яку утримує процес:

```
oom_score ≈ (кількість_сторінок_процесу / загальний_обсяг_RAM) · 1000 + oom_score_adj
```

Параметр `oom_score_adj` налаштовується адміністратором у діапазоні від `-1000` (повна заборона аварійного завершення процесу, типово для `systemd` або `sshd`) до `+1000` (першочерговий кандидат на знищення).

Процес із найвищим балом отримує сигнал `SIGKILL`, що змушує його негайно звільнити всі утримувані фізичні кадри й запобігти повному зависанню обладнання.

## Практична інспекція робочої множини процесу

Для аналізу поведінки реального застосунку в просторі користувача ядро Linux надає механізм точного скидання та зчитування бітів звернення через віртуальну файлову систему `/proc`.

Методика складається з трьох послідовних кроків:
1. Запис значення `1` у файл `/proc/[pid]/clear_refs` скидає апаратний біт `Accessed` у всіх записах таблиць сторінок (PTE) цільового процесу.
2. Програма виконує свої штатні функції протягом фіксованого вікна спостереження `Δ` (наприклад, 2 секунди). Під час роботи процесорний блок MMU виставляє біти звернення лише на тих сторінках, які були реально задіяні інструкціями читання чи запису.
3. Зчитування файлу `/proc/[pid]/smaps_rollup` повертає поле `Referenced`, яке містить точний обсяг у кілобайтах пам'яті, використаної у цьому вікні (робоча множина `W(t, Δ)`).

Повний практикум зі створення системних утиліт аналізу пам'яті, інспекції дескрипторів сторінок через `/proc/[pid]/pagemap` та тестування резидентності через виклик `mincore()` наведено у вставці [Практикум: утиліта інспекції робочої множини](root:sf-os/working-set/proj-working-set-probe.md).

Нижче наведено робочий приклад вимірювання активної робочої множини та порівняння її з повним резидентним розміром (RSS) процесу.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

/*
 * Зчитує показники RSS та Referenced зі smaps_rollup для заданого PID.
 */
static int get_working_set_kb(pid_t pid, unsigned long *rss_kb, unsigned long *ref_kb) {
    char path[64];
    snprintf(path, sizeof(path), "/proc/%d/smaps_rollup", pid);

    FILE *f = fopen(path, "r");
    if (!f) return -1;

    char line[256];
    *rss_kb = 0;
    *ref_kb = 0;

    while (fgets(line, sizeof(line), f)) {
        if (strncmp(line, "Rss:", 4) == 0) {
            sscanf(line + 4, "%lu", rss_kb);
        } else if (strncmp(line, "Referenced:", 11) == 0) {
            sscanf(line + 11, "%lu", ref_kb);
        }
    }

    fclose(f);
    return 0;
}

/*
 * Скидає біти звернення через clear_refs.
 */
static int reset_page_references(pid_t pid) {
    char path[64];
    snprintf(path, sizeof(path), "/proc/%d/clear_refs", pid);

    FILE *f = fopen(path, "w");
    if (!f) return -1;

    fputs("1\n", f);
    fclose(f);
    return 0;
}

int main(int argc, char **argv) {
    if (argc < 3) {
        fprintf(stderr, "Використання: %s <pid> <вікно_сек>\n", argv[0]);
        return EXIT_FAILURE;
    }

    pid_t pid = (pid_t)atoi(argv[1]);
    int window_sec = atoi(argv[2]);

    if (reset_page_references(pid) != 0) {
        perror("Не вдалося скинути біти звернення (перевірте права доступу)");
        return EXIT_FAILURE;
    }

    printf("Спостереження за процесом PID=%d протягом %d с...\n", pid, window_sec);
    sleep(window_sec);

    unsigned long rss = 0, referenced = 0;
    if (get_working_set_kb(pid, &rss, &referenced) != 0) {
        perror("Помилка зчитування smaps_rollup");
        return EXIT_FAILURE;
    }

    double active_ratio = (rss > 0) ? ((double)referenced / (double)rss) * 100.0 : 0.0;

    printf("Повна резидентна пам'ять (RSS):       %lu kB\n", rss);
    printf("Активна робоча множина W(t, Δ):        %lu kB\n", referenced);
    printf("Частка активно задіяної пам'яті:       %.1f %%\n", active_ratio);

    return EXIT_SUCCESS;
}
```

```cpp
#include <iostream>
#include <fstream>
#include <string>
#include <sstream>
#include <chrono>
#include <thread>
#include <filesystem>
#include <system_error>

namespace fs = std::filesystem;

struct WorkingSetReport {
    unsigned long rss_kb{0};
    unsigned long referenced_kb{0};
};

class MemoryProfiler {
public:
    explicit MemoryProfiler(pid_t pid) : pid_(pid) {
        proc_root_ = "/proc/" + std::to_string(pid_);
        if (!fs::exists(proc_root_)) {
            throw std::runtime_error("Процес PID=" + std::to_string(pid_) + " не знайдено.");
        }
    }

    void reset_references() const {
        std::ofstream clear_file(proc_root_ + "/clear_refs");
        if (!clear_file.is_open()) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити clear_refs");
        }
        clear_file << "1\n";
    }

    [[nodiscard]] WorkingSetReport sample_report() const {
        std::ifstream smaps_file(proc_root_ + "/smaps_rollup");
        if (!smaps_file.is_open()) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити smaps_rollup");
        }

        WorkingSetReport report{};
        std::string line;
        while (std::getline(smaps_file, line)) {
            if (line.starts_with("Rss:")) {
                std::istringstream(line.substr(4)) >> report.rss_kb;
            } else if (line.starts_with("Referenced:")) {
                std::istringstream(line.substr(11)) >> report.referenced_kb;
            }
        }
        return report;
    }

private:
    pid_t pid_;
    std::string proc_root_;
};

int main(int argc, char* argv[]) {
    if (argc < 3) {
        std::cerr << "Використання: " << argv[0] << " <pid> <вікно_сек>\n";
        return 1;
    }

    try {
        const pid_t pid = std::stoi(argv[1]);
        const int window_sec = std::stoi(argv[2]);

        MemoryProfiler profiler(pid);
        profiler.reset_references();

        std::cout << "Спостереження за PID=" << pid << " протягом " << window_sec << " с...\n";
        std::this_thread::sleep_for(std::chrono::seconds(window_sec));

        const auto report = profiler.sample_report();
        const double active_ratio = (report.rss_kb > 0)
            ? (static_cast<double>(report.referenced_kb) / static_cast<double>(report.rss_kb)) * 100.0
            : 0.0;

        std::cout << "Повна резидентна пам'ять (RSS):       " << report.rss_kb << " kB\n";
        std::cout << "Активна робоча множина W(t, Δ):        " << report.referenced_kb << " kB\n";
        std::cout << "Частка активно задіяної пам'яті:       " << active_ratio << " %\n";

    } catch (const std::exception& ex) {
        std::cerr << "Помилка інспекції: " << ex.what() << "\n";
        return 1;
    }

    return 0;
}
```

## Синтез

Концепція робочої множини Пітера Деннінга перетворила керування оперативною пам'яттю з інтуїтивного перебору евристик на математично вивірену науку про локальність. Робоча множина є мінімальним квантом потреби програми в пам'яті: доки вся множина `W(t, Δ)` утримується у фізичних кадрах RAM, програма працює з максимальною швидкодією, а її сторінкові збої зведені до нуля.

Сучасні операційні системи побудовані як багаторівнева система захисту робочої множини: від апаратних бітів звернення в MMU та списків Active/Inactive LRU до динамічного розрахунку дистанцій повторного збою Refault Distance та телеметрії тиску PSI. Для системного інженера розуміння механізмів робочої множини дає змогу проектувати кеш-орієнтовані алгоритми, коректно конфігурувати пам'ять хмарних мікросервісів та запобігати руйнівним сторінковим кризам у високонавантажених середовищах.
