# 📋 Інтерфейси процесів і потоків: системні виклики та POSIX API

Керування процесами та потоками в операційних системах сімейства POSIX (Linux, macOS, FreeBSD) побудоване на чіткому розмежуванні двох рівнів абстракції: системних викликів керування адресними просторами (`fork`, `execve`, `waitpid`) та стандартного інтерфейсу потоків виконання `POSIX Threads` (`pthreads`), а також низькорівневого уніфікованого виклику ядра Linux `clone()`.

Розуміння контракту цих інтерфейсів вимагає чіткого усвідомлення того, як саме ядро передає керування, як розподіляються файлові дескриптори та які інваріанти накладаються на обробку помилок і пам'ять.

---

### Системні виклики керування процесами (POSIX Process API)

Керування життєвим циклом класичного процесу в операційних системах Unix базується на фундаментальній парадигмі «створення дубліката → заміщення образу пам'яті → очікування завершення». Цей розподіл на окремі кроки дає розробнику унікальну можливість налаштувати оточення дочірньої програми (перенаправити стандартні потоки вводу-виводу, змінити робочий каталог, налаштувати обмеження ресурсів) ще до того, як новий виконуваний образ почне свою роботу.

:::tabs
```c
#include <sys/types.h>
#include <unistd.h>
#include <sys/wait.h>

pid_t fork(void);
int execve(const char *pathname, char *const argv[], char *const envp[]);
pid_t waitpid(pid_t pid, int *wstatus, int options);
void _exit(int status);
```

#### Механізм роботи системного виклику `fork`

Виклик `fork()` роздвоює викликаючий процес. Головна особливість виклику полягає в тому, що він викликається один раз, але повертає значення двічі: у контексті батьківського процесу він повертає числовий ідентифікатор `PID` новоствореного нащадка, тоді як у контексті дочірнього процесу повертає число `0`. Це дозволяє програмі за допомогою простого розгалуження `if (pid == 0)` розділити логіку батька та дитини.

Сучасні операційні системи не копіюють всю фізичну пам'ять у момент виклику `fork()`. Замість цього ядро дублює лише таблиці сторінок віртуальної пам'яті та позначає всі фізичні сторінки як доступні лише для читання. Фізичне копіювання сторінки відбувається лише тоді, коли один із процесів намагається виконати запис — цей механізм відомий як [копіювання при записі](root:sf-algorithms/copy-on-write-structures).

#### Заміщення образу програми через `execve`

Системний виклик `execve()` є базовим примітивом сімейства `exec`. Він повністю знищує поточний віртуальний адресний простір процесу: старі сегменти коду, глобальних даних, купи та стека вивільняються, а на їхнє місце завантажуються секції з нового бінарного файлу формату ELF. 

При цьому сам числовий ідентифікатор процесу (`PID`), зв'язки спорідненості з батьком та відкриті файлові дескриптори (якщо для них не було встановлено спеціальний прапорець `FD_CLOEXEC`) зберігаються. Якщо виклик `execve()` завершується успішно, він ніколи не повертає керування у викликаючу функцію, оскільки самого старого коду в пам'яті більше не існує.

#### Очікування нащадків та утилізація зомбі: `waitpid`

Коли дочірній процес завершує виконання, операційна система звільняє всю його пам'ять та закриває відкриті файли, але зберігає мінімальний запис у системній таблиці процесів ядра (структуру `task_struct`), що містить код повернення та статистику використання ресурсів. У такому стані процес називається зомбі (*zombie*).

Батьківський процес зобов'язаний зчитати стан завершення нащадка за допомогою виклику `waitpid()`. Тільки після цього ядро остаточно видаляє запис про процес із таблиці. Якщо батьківський процес завершується раніше за своїх нащадків, усі діти стають сиротами (*orphans*) і автоматично перепідпорядковуються кореневому процесу ініціалізації системи (`systemd` або `init` з `PID = 1`), який бере на себе обов'язок періодично викликати `waitpid` для очищення зомбі.

### Інтерфейс потоків виконання (POSIX Threads / pthreads)

Стандарт POSIX.1c визначає набір бібліотечних функцій для створення та координації потоків виконання всередині єдиного адресного простору. На відміну від процесів, де ізоляція забезпечується апаратно через MMU, потоки повністю довіряють одне одному й можуть вільно маніпулювати спільними вказівниками.

:::tabs
```c
#include <pthread.h>

int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
int pthread_join(pthread_t thread, void **retval);
int pthread_detach(pthread_t thread);
void pthread_exit(void *retval);
pthread_t pthread_self(void);
int pthread_equal(pthread_t t1, pthread_t t2);
```

:::

#### Створення та життєвий цикл потоку

Функція `pthread_create()` алокує новий блок керування потоком, виділяє в адресному просторі процесу ділянку віртуальної пам'яті під індивідуальний стек потоку (типово від 2 до 8 мегабайтів) із захисною невідображеною сторінкою знизу (*guard page*) для перехоплення переповнення стека, та викликає системний виклик ядра `clone()`.

Створений потік може перебувати в одному з двох станів:
1. **Приєднуваний (joinable)** — стан за замовчуванням. Після завершення роботи потік зберігає свій код повернення доти, доки інший потік не викличе для нього `pthread_join()`. Невикликаний `pthread_join` для приєднуваного потоку призводить до витоку службової пам'яті бібліотеки `pthread`.
2. **Від'єднаний (detached)** — стан, у якому потік після завершення автоматично та безслідно знищується операційною системою. Перевести потік у такий стан можна заздалегідь через атрибути `pthread_attr_setdetachstate()` або динамічно через виклик `pthread_detach()`.

На відміну від стандартних системних викликів Unix, які сигналізують про помилку поверненням значення `-1` та встановленням глобальної змінної `errno`, функції стандарту `pthreads` повертають код помилки безпосередньо як цілочисельний результат виклику (нуль означає успіх, додатне число — код помилки).

### Системний виклик ядра Linux: `clone()` та `clone3()`

Ядро Linux не розрізняє поняття «процес» і «потік» на рівні внутрішніх структур планувальника. Кожна одиниця виконання описується екземпляром структури `task_struct`. Уніфікований системний виклик `clone()` дозволяє точно налаштувати ступінь спільності ресурсів між батьківським і дочірнім контекстами за допомогою набору бітових прапорців.

:::tabs
```c
#define _GNU_SOURCE
#include <sched.h>

int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...
          /* pid_t *parent_tid, void *tls, pid_t *child_tid */ );
```
```cpp
#include <sched.h>
#include <span>
#include <expected>
#include <system_error>
#include <cstddef>

// C++ обгортка над системним викликом clone
std::expected<pid_t, std::error_code> clone_task(
    int (*fn)(void*), std::span<std::byte> stack, int flags, void* arg) noexcept;
```
:::

#### Семантика прапорців спільності ресурсів

Прапорці системного виклику `clone` визначають, які саме підсистеми будуть спільними, а які отримають незалежний дублікат:

- **`CLONE_VM` (Virtual Memory)**: вмикає спільне використання адресного простору. Батьківський і дочірній процеси використовують єдиний набір таблиць сторінок. Будь-яке виділення пам'яті через `malloc` чи запис за адресою одразу стає доступним іншому контексту.
- **`CLONE_FS` (File System)**: робить спільною інформацію про файлову систему, включно з кореневим каталогом, поточним робочим каталогом та маскою прав створення файлів (`umask`). Виклик `chdir()` в одному потоці змінює каталог для всієї програми.
- **`CLONE_FILES` (File Table)**: спільна таблиця файлових дескрипторів. Якщо один потік відкриває новий сокет або закриває файл, номер дескриптора стає валідним або анулюється для всіх інших потоків негайно.
- **`CLONE_SIGHAND` (Signal Handlers)**: спільні диспозиції сигналів. Зміна обробника сигналу через `sigaction()` діє на весь процес. Прапорець вимагає обов'язкової наявності `CLONE_VM`.
- **`CLONE_THREAD` (Thread Group)**: розміщує новий потік у тій самій групі потоків (Thread Group). Це означає, що системний виклик `getpid()` повертатиме спільний `TGID` (ідентифікатор головного процесу), а у файловій системі `/proc` потік з'явиться як підкаталог у `/proc/<PID>/task/<TID>`.
- **`CLONE_SETTLS` (Thread-Local Storage)**: налаштовує сегментний регістр процесора (`FS` на x86-64 або `TPIDR_EL0` на ARM) на передану адресу пам'яті, що забезпечує апаратну роботу локальних змінних потоку (`__thread` або `thread_local`).
- **`CLONE_CHILD_CLEARTID`**: критично важливий прапорець для реалізації `pthread_join`. Коли потік завершує своє виконання, ядро операційної системи автоматично обнуляє цілочисельне поле за вказаною адресою в пам'яті та викликає системний виклик `futex` для пробудження всіх потоків, що чекали на його завершення.

### Порівняльна структура спільних та індивідуальних ресурсів

Нижче наведено зведену таблицю, що описує статус кожного ресурсу операційної системи для процесів і потоків.

| Ресурс / Підсистема | Спільний для потоків процесу | Індивідуальний для потоку |
| :--- | :---: | :---: |
| **Віртуальний адресний простір** (код, глобальні змінні, купа) | **Так** | Ні |
| **Регістри процесора** (`PC`, `SP`, загальні регістри, прапорці) | Ні | **Так** |
| **Стек викликів** (локальні змінні функцій) | Ні* | **Так** |
| **Таблиця файлових дескрипторів** (файли, сокети, пайпи) | **Так** | Ні |
| **Поточна позиція читання/запису у файлі** (*file offset*) | **Так** | Ні |
| **Ідентифікатор процесу (`PID` / `TGID`)** | **Так** | Ні |
| **Ідентифікатор потоку (`TID` / `pthread_t`)** | **Так** (у групі) | **Так** (унікальний) |
| **Права доступу та обліковий запис (`UID`, `GID`, `EUID`)** | **Так** | Ні |
| **Поточний робочий каталог (`CWD`) та корінь (`chroot`)** | **Так** | Ні |
| **Таблиця обробників сигналів (`sigaction`)** | **Так** | Ні |
| **Маска заблокованих сигналів (`pthread_sigmask`)** | Ні | **Так** |
| **Локальна пам'ять потоку (TLS, `thread_local`)** | Ні | **Так** |
| **Змінна стану помилок (`errno`)** | Ні | **Так** |
| **Маска прив'язки до процесорних ядер (CPU Affinity)** | Може бути | **Так** |

*\* Примітка щодо ізоляції стека: захист стека потоку є виключно конвенційним. Оскільки всі стеки лежать у спільному адресному просторі, некоректний запис за покажчиком з одного потоку може зруйнувати локальні змінні або адресу повернення іншого потоку, спричинивши важковловимі помилки пам'яті.*

### Діагностика через псевдофайлову систему procfs

Операційна система Linux надає детальне відображення стану процесів і потоків у псевдофайловій системі `/proc`:

1. `/proc/<PID>/status` — відображає загальний стан процесу, кількість потоків у полі `Threads:`, пікове та поточне споживання резидентної пам'яті (`VmRSS`, `VmSize`).
2. `/proc/<PID>/task/` — містить список підкаталогів для кожного потоку процесу. Назва кожного підкаталогу відповідає системному `TID` потоку.
3. `/proc/<PID>/task/<TID>/stat` — детальна статистика конкретного потоку: час виконання в режимі користувача (`utime`) та ядра (`stime`), номер процесорного ядра, на якому потік востаннє виконувався.
4. `/proc/<PID>/maps` — карта віртуальної пам'яті процесу, де чітко видно адреси сегментів коду, купи та виділених блоків під стеки кожного потоку з захисними сторінками (*guard pages*).
