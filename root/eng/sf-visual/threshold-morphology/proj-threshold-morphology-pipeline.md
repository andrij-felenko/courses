# ⚙️ Конвеєр «поріг + морфологія» на C: від кадру до лічби

**Задача.** Камера на контролері віддає сірий кадр — один байт яскравості на піксель, `gray[H][W]`. Треба пройти повний шлях машинного бачення в його найпрактичнішому вигляді: бінаризувати кадр **адаптивним** порогом (бо світло в реальній сцені рідко рівне), вичистити сиру маску **відкриттям** (геть дрібні цятки) і **закриттям** (залатати дірки), а тоді **порахувати** білі пікселі — площу виділеного. Усе це — на залізі без операційної системи, **без жодного `malloc`**, із чесною обробкою країв кадру і з оглядкою на кожен байт пам'яті. Саме такий конвеєр крутиться в датчику присутності, лічильнику деталей на конвеєрі чи у вузлі, що ловить посадковий знак для дрона.

**Ідея.** Кожен крок поодинці тривіальний — уся складність у тім, щоб **скласти** їх правильно і не наступити на типові граблі вбудованого коду: вихід за межі масиву на краю кадру, переповнення проміжних сум, зайвий буфер, який не влазить у кілька кілобайтів пам'яті. Тож конвеєр будуємо так, щоб (1) кожна стадія читала вхід і писала в **окремий** вихід — морфологію не можна робити «на місці», бо змінений піксель зіпсував би сусіда, який ще не оброблений; (2) краї оброблялися явною стратегією, а не випадково; (3) проміжні величини жили в типах, що гарантовано не переповняться.

Підемо стадіями: спершу адаптивний поріг (з чесним інтегральним зображенням, щоб вікно 15×15 не коштувало 225 читань на піксель), тоді ерозія й дилатація як цеглинки, з них — відкриття й закриття, і нарешті лічба. У кінці зберемо все в одну функцію-конвеєр і пройдемося пастками.

## Стадія 1: адаптивний поріг через інтегральне зображення

Глобальний поріг (одне T на весь кадр) ламається, щойно одна частина сцени світліша за іншу. [Адаптивний поріг](root:sf-visual/threshold-morphology) лікує це так: для кожного пікселя беремо середню яскравість його **околу** (вікна `S×S`) і порівнюємо піксель саме з нею, з невеликим запасом `C`:

```
T(x,y) = mean(окіл S×S навколо (x,y)) − C
маска(x,y) = 255, якщо gray(x,y) > T(x,y),  інакше 0
```

Запас `C` (типово 2…10) відсікає дрібний шум: піксель мусить бути не просто яскравішим за окіл, а **помітно** яскравішим, щоб стати білим. Це прибирає крапинки на рівному тлі, де яскравість пікселя й околу майже збігається.

Наївно середнє вікна `15×15` коштує 225 додавань **на кожен піксель** — для кадру це десятки мільйонів операцій, забагато. Рятунок — **інтегральне зображення** (англ. *integral image*, воно ж *summed-area table*): спершу за один прохід будуємо таблицю `I`, де `I[y][x]` = сума яскравостей усього прямокутника від `(0,0)` до `(x,y)`. Тоді сума **будь-якого** прямокутного вікна береться за **чотири** звернення до таблиці, незалежно від розміру вікна:

```
сума(x1..x2, y1..y2) = I[y2][x2] − I[y1−1][x2] − I[y2][x1−1] + I[y1−1][x1−1]
```

Це принцип включення-виключення: від великого прямокутника віднімаємо дві смуги ліворуч і вгорі, а кутик, що відняли двічі, додаємо назад. Будуємо таблицю теж наростанням, рядок за рядком:

```c
#include <stdint.h>

#define W 160
#define H 120

// Інтегральне зображення: I[y][x] = сума gray[0..y][0..x].
// uint32_t вистачає: 160·120·255 ≈ 4.9·10⁶ ≪ 4.29·10⁹ (межа uint32).
// Для великих кадрів (понад ~16 Мп·255) брати uint64_t.
static uint32_t I[H][W];

void build_integral(const uint8_t gray[H][W]) {
    for (int y = 0; y < H; y++) {
        uint32_t row_sum = 0;                  // біжуча сума поточного рядка
        for (int x = 0; x < W; x++) {
            row_sum += gray[y][x];
            uint32_t up = (y > 0) ? I[y-1][x] : 0;
            I[y][x] = up + row_sum;            // зверху + накопичене в рядку
        }
    }
}
```

Тепер сам поріг. Вікно `S×S` навколо пікселя обрізаємо краєм кадру (clamp) — на рамці воно просто менше, і ділити треба на **фактичну** кількість пікселів вікна, а не на `S²`, інакше край вийде хибно темним. Беремо `S = 15`, тож півширина `R = 7`:

```c
#define WIN   15
#define RAD   (WIN / 2)        // = 7
#define CCONST 5               // запас C: піксель мусить бути помітно яскравішим за окіл

// Сума прямокутника [x1..x2]×[y1..y2] за чотири звернення до інтегралу.
static uint32_t rect_sum(int x1, int y1, int x2, int y2) {
    uint32_t a = I[y2][x2];
    uint32_t b = (x1 > 0)            ? I[y2][x1-1]   : 0;
    uint32_t c = (y1 > 0)            ? I[y1-1][x2]   : 0;
    uint32_t d = (x1 > 0 && y1 > 0)  ? I[y1-1][x1-1] : 0;
    return a - b - c + d;
}

void adaptive_threshold(const uint8_t gray[H][W], uint8_t mask[H][W]) {
    for (int y = 0; y < H; y++) {
        for (int x = 0; x < W; x++) {
            int x1 = x - RAD, y1 = y - RAD;
            int x2 = x + RAD, y2 = y + RAD;
            if (x1 < 0) x1 = 0;                 // обрізаємо вікно краєм кадру
            if (y1 < 0) y1 = 0;
            if (x2 >= W) x2 = W - 1;
            if (y2 >= H) y2 = H - 1;

            uint32_t area = (uint32_t)(x2 - x1 + 1) * (y2 - y1 + 1);
            uint32_t sum  = rect_sum(x1, y1, x2, y2);
            int      mean = (int)(sum / area);  // середня яскравість фактичного вікна
            int      thr  = mean - CCONST;      // локальний поріг T(x,y)

            mask[y][x] = (gray[y][x] > thr) ? 255 : 0;
        }
    }
}
```

Ключ тут — `area` рахується від **обрізаних** меж, тож на краю кадру (де вікно вужче) середнє лишається чесним. Це найчастіша помилка адаптивного порога: поділити на `S²` всюди — і отримати темну рамку по периметру маски.

**Умова: піксель (40,30) має яскравість 150, середнє його вікна 15×15 = 120, C = 5. Бінаризуємо.**
```c
// mean = 120, CCONST = 5  →  thr = 115
// gray = 150 > 115  →  mask = 255  (білий: піксель помітно яскравіший за окіл)
//
// якби gray = 122:  122 > 115 → 255 теж (ледь яскравіший — але запас C його ще пропускає)
// якби gray = 118:  118 > 115 → 255;  а 113 > 115 → 0 (тоне в тлі, бо не дотяг запасу C)
```

## Стадія 2: ерозія й дилатація як цеглинки

Маска готова, але сира — по ній цятки шуму й дірки в тілах. Чистимо [морфологією](root:sf-visual/threshold-morphology). Дві базові дії над бінарною маскою структурним елементом 3×3:

- **Ерозія** — піксель лишається білим, лише якщо **весь** окіл 3×3 білий. На бінарній масці це **мінімум** по вікну.
- **Дилатація** — піксель стає білим, якщо в околі 3×3 є **хоч один** білий. Це **максимум** по вікну.

Найважливіше інженерне рішення: морфологію **не можна робити на місці**. Якщо писати результат у той самий масив, то піксель, який ми щойно змінили, спотворить обчислення для свого сусіда праворуч і знизу — вони прочитають уже «нове» значення замість вихідного. Тому кожна дія читає `src` і пише в **окремий** `dst`.

Другий момент — **край кадру**. У пікселів на рамці немає повного околу 3×3. Дві чесні стратегії:
- **zero-padding** (за межами вважаємо чорне, 0): на краю ерозія завжди стиратиме біле (бо «сусід» за межею — чорний), маска по периметру худне. Просто, але край трохи з'їдається.
- **reflect / clamp** (за межами беремо найближчий наявний піксель, дзеркалимо): край поводиться як продовження кадру, нічого штучно не темніє. Трохи більше коду, зате рамка не псується.

Беремо **clamp** (повтор краю) — він безпечніший для лічби площі, бо не вносить хибної межі. Допоміжна функція читає піксель із затиском координат:

```c
// Безпечне читання маски: координати за межами затискаються до краю (clamp).
// Жодного звернення поза масивом — головне правило вбудованого коду.
static uint8_t at_clamp(const uint8_t m[H][W], int y, int x) {
    if (x < 0) x = 0; else if (x >= W) x = W - 1;
    if (y < 0) y = 0; else if (y >= H) y = H - 1;
    return m[y][x];
}

void erode3(const uint8_t src[H][W], uint8_t dst[H][W]) {
    for (int y = 0; y < H; y++)
        for (int x = 0; x < W; x++) {
            uint8_t mn = 255;                          // ерозія = мінімум по 3×3
            for (int dy = -1; dy <= 1; dy++)
                for (int dx = -1; dx <= 1; dx++) {
                    uint8_t v = at_clamp(src, y+dy, x+dx);
                    if (v < mn) mn = v;
                }
            dst[y][x] = mn;
        }
}

void dilate3(const uint8_t src[H][W], uint8_t dst[H][W]) {
    for (int y = 0; y < H; y++)
        for (int x = 0; x < W; x++) {
            uint8_t mx = 0;                             // дилатація = максимум по 3×3
            for (int dy = -1; dy <= 1; dy++)
                for (int dx = -1; dx <= 1; dx++) {
                    uint8_t v = at_clamp(src, y+dy, x+dx);
                    if (v > mx) mx = v;
                }
            dst[y][x] = mx;
        }
}
```

`at_clamp` ціною двох порівнянь на читання назавжди прибирає вихід за межі — а вихід за межі масиву на краю кадру є найпідступнішою вадою такого коду: він не падає одразу, а тихо читає сусідній рядок (чи зовсім чужу пам'ять), і маска по краю виходить «брудна» без видимої причини.

## Стадія 3: відкриття й закриття

Тепер цеглинки складаються в чистку. Ерозія й дилатація поодинці міняють **розмір** тіла (ерозія все потоншує, дилатація потовщує). Складені в пару в потрібному порядку, вони прибирають дрібне, **не змінивши** розміру головного об'єкта:

- **Відкриття** = ерозія, **потім** дилатація. Ерозія знищує дрібні цятки (їм нема чим триматися) і відриває тонкі перемички, а наступна дилатація повертає головному тілу втрачений розмір. Підсумок: **цятки геть, об'єкт цілий**.
- **Закриття** = дилатація, **потім** ерозія. Дилатація затягує дірки й щербини, ерозія повертає розмір. Підсумок: **дірки залатано, об'єкт цілий**.

Кожна пара потребує **одного проміжного** буфера (вихід першої дії — вхід другої). Щоб не плодити масиви, заведемо рівно **два** робочих буфери на весь конвеєр і ганятимемо дані між ними «туди-сюди»:

```c
// Два робочих буфери на весь конвеєр — більше не потрібно.
static uint8_t buf_a[H][W];
static uint8_t buf_b[H][W];

// Відкриття: src → (ерозія) tmp → (дилатація) dst.  tmp ≠ src, tmp ≠ dst.
void opening3(const uint8_t src[H][W], uint8_t dst[H][W], uint8_t tmp[H][W]) {
    erode3(src, tmp);
    dilate3(tmp, dst);
}

// Закриття: src → (дилатація) tmp → (ерозія) dst.
void closing3(const uint8_t src[H][W], uint8_t dst[H][W], uint8_t tmp[H][W]) {
    dilate3(src, tmp);
    erode3(tmp, dst);
}
```

## Стадія 4: лічба білих пікселів

Чиста маска готова — лишилося відповісти на питання, заради якого все робилося: **скільки** виділеної площі в кадрі? Один прохід із лічбою. Тут — ще одна мовчазна пастка: лічильник має бути досить широким. Кадр 160×120 — це 19200 пікселів, влазить у `uint16_t` (до 65535) ледь-ледь; кадр 320×240 — уже 76800, `uint16_t` **переповниться** й дасть нісенітницю. Беремо `uint32_t` без вагань:

```c
uint32_t count_white(const uint8_t mask[H][W]) {
    uint32_t n = 0;
    for (int y = 0; y < H; y++)
        for (int x = 0; x < W; x++)
            if (mask[y][x]) n++;               // будь-яке ненульове = білий піксель
    return n;
}
```

Часто корисніша не сама лічба, а **частка** кадру: `(float)n / (H*W)`. За нею вже легко спрацьовує логіка — «об'єкт у кадрі, якщо біле понад 3% площі» тощо.

## Усе разом: конвеєр

Зберемо стадії в одну функцію. Порядок буферів продуманий так, щоб обійтися двома робочими масивами (`buf_a`, `buf_b`) плюс окремий вихід `mask`:

```c
// Повний конвеєр: сірий кадр → чиста маска + площа виділеного.
// Буфери buf_a/buf_b/I/mask — статичні (без malloc), живуть увесь час роботи.
uint32_t pipeline(const uint8_t gray[H][W], uint8_t mask[H][W]) {
    build_integral(gray);                      // 1. таблиця сум для адаптивного порога
    adaptive_threshold(gray, buf_a);           // 2. сира маска → buf_a

    opening3(buf_a, buf_b, mask);              // 3. відкриття: buf_a → buf_b (tmp = mask)
    closing3(buf_b, mask, buf_a);              // 4. закриття: buf_b → mask  (tmp = buf_a)

    return count_white(mask);                  // 5. площа виділеного
}
```

Прослідкуймо потік даних, бо саме в ньому вся охайність. `adaptive_threshold` кладе сиру маску в `buf_a`. `opening3` робить ерозію `buf_a → mask`, тоді дилатацію `mask → buf_b` — після нього **очищена** маска лежить у `buf_b`, а `mask` ми тимчасово позичили під проміжок (його вміст зараз сміття, не страшно). `closing3` робить дилатацію `buf_b → buf_a`, тоді ерозію `buf_a → mask` — після нього **готова** чиста маска лежить у `mask`, а `buf_a` знову вільний. Жодна стадія не пише туди, звідки ще читає; три статичних буфери (`buf_a`, `buf_b`, `mask`) плюс інтегральне `I` — і весь конвеєр обходиться без жодного динамічного виділення.

**Умова: кадр 160×120, у ньому світла деталь і кілька цяток шуму. Проганяємо конвеєр.**
```c
static uint8_t gray[H][W];      // заповнюється з камери (DMA/опитування)
static uint8_t mask[H][W];      // вихід

void on_frame(void) {
    // gray[][] уже містить свіжий сірий кадр
    uint32_t area = pipeline(gray, mask);

    // частка кадру, зайнята виділеним
    float frac = (float)area / (float)(H * W);

    if (frac > 0.03f) {
        // об'єкт у кадрі — реагуємо (лічильник, тривога, наведення…)
    }
    // mask[][] тепер чиста бінарна маска, готова до пошуку об'єктів
}
```

## Скільки це коштує і де воно крутиться

Порахуймо порядок величин на кадрі 160×120 = 19200 пікселів. Інтегральне зображення — один прохід, ~2 додавання на піксель. Адаптивний поріг — чотири читання таблиці + ділення на піксель (ділення дороге, але одне). Кожна ерозія/дилатація — 9 порівнянь на піксель; відкриття + закриття — це 4 такі дії, разом ~36 порівнянь на піксель. Лічба — один прохід. Усього — кілька десятків простих цілочислових операцій на піксель, тобто близько мільйона операцій на кадр. Навіть скромний контролер на 48–72 МГц прожує це за одиниці мілісекунд — реальний час для відеопотоку в десятки кадрів за секунду.

Пам'ять — ось що тисне сильніше за такти. Чотири масиви `H×W` байтів (`gray`, `mask`, `buf_a`, `buf_b`) плюс інтегральне `I` у `uint32_t` (учетверо більше). Для 160×120 це `4·19200 + 4·19200 = 153 600` байтів — близько 150 КБ, що вже забагато для зовсім дрібного MCU. Звідси два практичних ходи: (1) тримати інтегральне `I` не для всього кадру, а **смугою** в кілька рядків — ковзне вікно, бо порогу для рядка `y` потрібні лише рядки `y−R … y+R`; (2) для дуже малих контролерів брати **глобальний** Оцу замість адаптивного (тоді `I` не потрібне зовсім) і працювати «на льоту» рядками. Конвеєр від цього не змінюється — змінюється лише стадія 1.

> 🔧 **Навіщо це.** Це кістяк будь-якого «порахуй/знайди на масці» завдання на залізі: датчик присутності, лічильник деталей, груба локалізація мітки чи знака. Адаптивний поріг рятує від нерівного цехового світла, відкриття гасить шум сенсора, закриття латає дірки в тілі деталі, лічба дає число для рішення. Усе на статичній пам'яті, без купи (`malloc` на MCU без потреби — джерело фрагментації й несподіваних відмов), за кілька мілісекунд на кадр.

## Пастки — зведено

- **Морфологія «на місці».** Писати результат у вхідний масив не можна: змінений піксель псує обчислення сусіда. Завжди окремий `dst`. У конвеєрі тому й крутимо два буфери.
- **Вихід за межі на краю кадру.** Окіл 3×3 (чи вікно `S×S`) на рамці вилазить за масив. Читати поза масивом — найпідступніша вада: не падає, а тихо бере чужу пам'ять і брудить край. Лік — `at_clamp` або явний padding; ніколи не індексувати без перевірки меж.
- **Ділення на `S²` замість фактичної площі вікна.** На краю обрізане вікно менше; поділ на повний `S²` робить край хибно темним. Ділити на реальну кількість пікселів вікна.
- **Переповнення лічильника.** `uint16_t` тримає лише до 65535 — кадр 320×240 його переповнить. Лічильник площі — завжди `uint32_t`.
- **Переповнення інтегрального зображення.** `I[y][x]` росте як `площа·255`. Для кадру понад ~16 Мп `uint32_t` мало — брати `uint64_t`. Тихе обгортання тут дає поріг «з нізвідки».
- **Забутий запас C.** Адаптивний поріг без `C` (або з `C = 0`) ловить власний шум: піксель, що рівний середньому околу, мерехтить між 0 і 255 від кадру до кадру. Невеликий `C` (2…10) стабілізує маску.
- **Зайва пам'ять.** Повне інтегральне зображення на весь кадр часто не влазить. Якщо тісно — смуга рядків замість усього кадру, або глобальний Оцу без інтегралу взагалі.
- **Порядок ерозії/дилатації.** Переплутати відкриття (ерозія→дилатація) із закриттям (дилатація→ерозія) — і замість прибирання цяток дістанеш роздуте тіло з замазаними дірками. Відкриття чистить, закриття латає; порядок дій — це і є вся різниця.
