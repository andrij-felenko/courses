# ⚙️ Еквалізація на MCU: гістограма → LUT → застосування

Завдання просте на словах: узяти 8-бітне сіре зображення з камери, вирівняти його гістограму й віддати назад — на мікроконтролері, де немає ні плаваючої точки на кожен піксель, ні зайвих кілобайтів, ні часу на ділення в гарячому циклі. Покажемо, як це робиться трьома проходами, кожен з яких чесний робочий C — без псевдокоду й без хитрощів, яких не буває в реальній прошивці.

Ідея вся в одному реченні: уся «математика» еквалізації — це 256 чисел [таблиці замін](root:sf-visual/histogram/math-equalization.md) «старе значення → нове», порахованих один раз; далі кадр обробляється підстановкою з таблиці, без арифметики на піксель. Тож робота ділиться на три кроки: побудувати гістограму, побудувати з неї LUT, застосувати LUT.

## Крок 1. Гістограма за один прохід

Гістограма 8-бітного кадру — це масив з 256 лічильників. Проходимо кожен піксель і збільшуємо кошик, що відповідає його яскравості. Один прохід, складність O(N) за кількістю пікселів, жодного множення.

:::tabs
```c
#include <stdint.h>
#include <string.h>

// img    — буфер пікселів (8 біт на піксель, рядок за рядком)
// n      — кількість пікселів (width * height)
// hist   — вихід: 256 лічильників
void build_histogram(const uint8_t *img, uint32_t n, uint32_t hist[256])
{
    memset(hist, 0, 256 * sizeof(uint32_t));   // обнулити кошики
    for (uint32_t i = 0; i < n; ++i)
        hist[img[i]]++;                        // піксель сам каже, який кошик рахувати
}
```
```python
# img  — послідовність байтів пікселів (8 біт на піксель, рядок за рядком)
# повертає: список з 256 лічильників
def build_histogram(img):
    hist = [0] * 256                           # обнулити кошики
    for px in img:
        hist[px] += 1                          # піксель сам каже, який кошик рахувати
    return hist
```
:::

Чому лічильник саме `uint32_t`. Кадр 320×240 — це 76800 пікселів; навіть якщо всі однакові, найбільший кошик не перевищить 76800, що влазить у 17 біт. `uint16_t` (максимум 65535) переповнився б уже на суцільному кадрі 256×256 і тихо обнулився б — а тиха помилка тут найгірша, бо CDF поїде й картинка зіпсується без жодного сигналу. `uint32_t` тримає до 4.29 мільярда — запас на будь-який реальний кадр з лишком. Це коштує рівно один кілобайт ОЗП на таблицю (256 × 4 байти), і він того вартий.

## Крок 2. LUT із CDF за один прохід по 256 кошиках

Тепер будуємо таблицю замін. За формулою еквалізації нове значення яскравості `v` дорівнює `round( CDF(v) · 255 )`, де `CDF(v)` — накопичена частка пікселів, не темніших за `v`. Накопичуємо суму на ходу й одразу пишемо результат у `lut[v]`.

Тут одна тонкість, заради якої варто думати про ділення. Якби ми рахували `CDF(v)` у плаваючій точці (`(double)acc / n`), на кожен з 256 кроків було б ділення — на MCU без FPU це повільно. Зробимо інакше: тримаємо цілочисельний накопичувач `acc` (сума лічильників) і рахуємо нове значення цілочисельно — одне ділення на кошик, без плаваючої точки. Більше того, бажане округлення `round` робиться без плаваючої точки: до чисельника додаємо половину знаменника перед діленням.

:::tabs
```c
// hist  — гістограма з кроку 1
// n     — кількість пікселів (та сама, що рахували)
// lut   — вихід: таблиця замін 256 байтів
void build_lut(const uint32_t hist[256], uint32_t n, uint8_t lut[256])
{
    if (n == 0) {                              // порожній кадр — нема що ділити
        for (int v = 0; v < 256; ++v) lut[v] = (uint8_t)v;   // тотожна таблиця
        return;
    }

    uint32_t acc = 0;                          // накопичена сума лічильників = CDF·n
    for (int v = 0; v < 256; ++v) {
        acc += hist[v];                        // тепер acc = h(0)+…+h(v)
        // нове = round( (acc/n) · 255 ) = (acc·255 + n/2) / n   — цілочисельно
        uint32_t mapped = (acc * 255u + n / 2u) / n;
        lut[v] = (uint8_t)mapped;              // 0…255 гарантовано: acc ≤ n
    }
}
```
```python
# hist  — гістограма з кроку 1
# n     — кількість пікселів (та сама, що рахували)
# повертає: таблиця замін із 256 значень 0…255
def build_lut(hist, n):
    if n == 0:                                 # порожній кадр — нема що ділити
        return list(range(256))                # тотожна таблиця

    lut = [0] * 256
    acc = 0                                    # накопичена сума лічильників = CDF·n
    for v in range(256):
        acc += hist[v]                         # тепер acc = h(0)+…+h(v)
        # нове = round( (acc/n) · 255 ) = (acc·255 + n//2) // n   — цілочисельно
        lut[v] = (acc * 255 + n // 2) // n     # 0…255 гарантовано: acc ≤ n
    return lut
```
:::

Кілька слів, чому це коректно. По-перше, `acc` після кроку `v` дорівнює сумі всіх лічильників від 0 до `v` включно — тобто `CDF(v) · n`. Множимо на 255 і ділимо на `n` — дістаємо `CDF(v) · 255`. Додавання `n/2` перед діленням — це і є цілочисельне округлення до найближчого: дробова частина ≥ 0.5 штовхає результат угору. По-друге, межі: на останньому кроці `acc == n`, тож `mapped = (n·255 + n/2)/n = 255` (точно, без вилазу за 255). Найтемніший зайнятий тон отримає невелике, але не обов'язково нульове значення — це нормально, бо `CDF` у першій зайнятій точці вже більша за нуль.

Перевірмо переповнення множення. `acc` не перевищує `n`, а `n` для 8-бітного кадру — це число пікселів. `acc * 255u` для кадру 320×240: 76800 × 255 ≈ 19.6 млн — спокійно влазить у `uint32_t` (до 4.29 млрд). Межа настає близько `n ≈ 16.8 млн` пікселів (бо `n · 255` має лишитися під 2³²), тобто кадр приблизно до 4096×4096 — для MCU це астрономія. Для більших кадрів або про запас множник рахують у `uint64_t`; на 8-бітному відео це зайве.

## Крок 3. Застосування LUT за один прохід

Найдешевший крок. Кожен піксель замінюємо на відповідне значення з таблиці — одне читання масиву на піксель, жодного множення чи ділення. Можна писати назад у той самий буфер (обробка на місці), бо кожен піксель залежить тільки від себе.

:::tabs
```c
// img — буфер пікселів, переписується на місці
// n   — кількість пікселів
// lut — таблиця замін із кроку 2
void apply_lut(uint8_t *img, uint32_t n, const uint8_t lut[256])
{
    for (uint32_t i = 0; i < n; ++i)
        img[i] = lut[img[i]];                  // старе значення індексує нове
}
```
```python
# img — змінюваний буфер пікселів (bytearray), переписується на місці
# lut — таблиця замін із кроку 2
def apply_lut(img, lut):
    for i in range(len(img)):
        img[i] = lut[img[i]]                   # старе значення індексує нове
```
:::

Складність — O(N), і константа крихітна: вибірка з 256-байтової таблиці майже напевно потрапляє в кеш (а на дрібних MCU кеша й нема — там це просто читання з ОЗП). Та сама таблиця, до речі, годиться не лише для еквалізації: підставивши інший вміст `lut[]`, тим самим циклом роблять [розтягнення, гамма-корекцію чи поріг](root:sf-visual/threshold-morphology) — будь-яке поточкове відображення яскравості. LUT — універсальний механізм, еквалізація лише один з його мешканців.

## Усе разом

:::tabs
```c
void equalize_gray(uint8_t *img, uint32_t n)
{
    uint32_t hist[256];
    uint8_t  lut[256];
    build_histogram(img, n, hist);
    build_lut(hist, n, lut);
    apply_lut(img, n, lut);
}
```
```python
def equalize_gray(img):                        # img — bytearray, на місці
    hist = build_histogram(img)
    lut = build_lut(hist, len(img))
    apply_lut(img, lut)
```
:::

Три проходи по кадру плюс один по 256 кошиках — і все. Пам'яті: 1 КБ під гістограму (`uint32_t[256]`) та 256 байтів під LUT, разом трохи більш як кілобайт, який можна звільнити одразу після обробки. Жодного множення на піксель у гарячих циклах (вони лише в коротенькому кроці 2), жодної плаваючої точки взагалі. Саме тому еквалізацію роблять прямо на камері-сенсорі чи на копійчаному контролері в реальному часі.

Для **відео** є гарний трюк, що прибирає навіть один зайвий прохід із критичного шляху. Сусідні кадри потоку майже однакові за освітленням, тож LUT, порахований по **попередньому** кадру, чудово годиться для **поточного**. Тоді в реальному часі лишається один прохід — застосування таблиці, — а гістограму нового кадру рахують паралельно, готуючи LUT для наступного. Затримка падає до одного проходу, а смикання яскравості від кадру до кадру навіть зменшується, бо LUT міняється плавно. Якщо потік пускають через DMA рядками, застосування LUT природно лягає на обробку рядка по мірі надходження — таблиця стала, тож кожен піксель обробляється незалежно, щойно прийшов.

Чому не можна злити **всі три** проходи в один. Спокусливо порахувати гістограму й одразу застосувати LUT за один прохід — але це неможливо для одного кадру: LUT залежить від **повної** гістограми (CDF потребує всіх пікселів), тож поки не пройшли весь кадр, таблиці ще немає. Звідси й мінімум два проходи по кадру на один знімок (гістограма, потім застосування); трюк із відео обходить це лише тому, що бере готову таблицю з минулого кадру.

## Граничні випадки й пастки

**Порожній або повністю чорний кадр.** Якщо `n == 0`, ділити нема на що — повертаємо тотожну таблицю (ми це й зробили). Окремий випадок — кадр, де *всі* пікселі однакові (наприклад, суцільне чорне, `hist[0] == n`): тоді `acc` стрибає з 0 до `n` рівно на одному кошику, і всі ці пікселі дістають значення 255 (бо `CDF` у цій точці вже дорівнює 1). Тобто чорний кадр стане білим — не помилка, а чесний наслідок «розтягни єдиний тон на всю шкалу». Хочете лишити такий кадр як є — додайте перевірку «зайнятий лише один кошик → тотожна таблиця».

**16-бітні зображення.** Тепловізор чи медичний сенсор дають 12–16 біт на піксель. Гістограма на 65536 кошиків — це вже 256 КБ під `uint32_t[65536]`, чого на MCU зазвичай нема, та й більшість кошиків порожні. Тоді або зменшують роздільність гістограми (групують по 16–64 сусідні значення в один кошик), або працюють з повним діапазоном лише там, де є пам'ять. Важливе попередження про переповнення: при підрахунку `acc * 65535u` для 16-бітного кадру множник більший, і `uint32_t` переповнюється вже близько `n ≈ 65 тисяч пікселів` — мізерний кадр. Для 16 біт чисельник **обов'язково** рахують у `uint64_t`, інакше тиха катастрофа.

**Шум на однорідних ділянках.** Глобальна еквалізація підсилює контраст там, де тонів багато — а отже й шум на великих рівних ділянках (небо, стіна). Якщо це заважає, глобальний метод заміняють локальним з обрізанням піку (CLAHE), де гістограму будують по тайлах і обрізають занадто високі кошики перед побудовою CDF. Та сама ідея LUT лишається — просто таблиць стає багато (одна на тайл), і між ними інтерполюють. Це окрема, складніша робота, але фундамент той самий: гістограма → CDF → таблиця замін.

**Кольорове зображення.** Не ганяйте цей код по каналах R, G, B окремо — три незалежні CDF зсунуть кольори й кадр позеленіє чи посиніє. Переведіть у простір, де яскравість окремо від кольору (наприклад, перетворіть RGB у яскравість + два кольороносні канали), вирівняйте **лише** канал яскравості тим самим `equalize_gray`, потім поверніть назад. Тоді тони розтягнуться, а кольори лишаться на місці.
