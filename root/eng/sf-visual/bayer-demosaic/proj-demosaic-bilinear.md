# ⚙️ Білінійна демозаїка RGGB: повний прохід

**Задача.** Сенсор віддає один байт на піксель — сиру баєрівську мозаїку `raw[H][W]`. Кожна точка має лише одну виміряну складову: червону, зелену чи синю — залежно від позиції у візерунку RGGB. Треба зробити повний кадр `out[H][W]`, де в кожному пікселі є всі три: R, G, B. Дві з трьох доведеться відновити з сусідів.

**Ідея.** Відсутні складові не можна виміряти заднім числом — їх лишається тільки **оцінити з оточення**, спираючись на просту, але майже завжди правдиву гадку: у малому клаптику зображення колір змінюється плавно. Якщо сусідні зелені пікселі дають приблизно однакову зелену яскравість, то й у точці між ними зелене десь таке саме. Білінійна інтерполяція — це найпряміше втілення цієї гадки: відсутню складову беремо як середнє найближчих виміряних сусідів того самого кольору. Працює доти, доки в кадрі немає різкої межі впритул, — а там, де є, ця сама гадка й ламається (про це нижче).

У сітці RGGB колір пікселя однозначно задає його позиція. Беремо лівий верхній кут за `(0,0)`; тоді парний рядок іде `R G R G …`, непарний — `G B G B …`. Отже:

```text
парність (y%2, x%2):
  (0,0) → червоний піксель   (виміряно R; G і B — вгадати)
  (0,1) → зелений на R-рядку (виміряно G; R з боків, B зверху/знизу)
  (1,0) → зелений на B-рядку (виміряно G; B з боків, R зверху/знизу)
  (1,1) → синій піксель      (виміряно B; G і R — вгадати)
```

Відсутню складову беремо як **середнє сусідів того самого кольору** — це й є білінійна інтерполяція. Хто де лежить, видно одразу: для червоного пікселя зелені сидять по боках (хрест), а сині — по діагоналях; для зеленого пікселя другий і третій колір лежать по сусідніх рядку та стовпці. Усі суми — байти, тож рахуємо в `int`, додаємо половину дільника для чесного округлення й аж тоді ділимо.

**Робочий код.** Спершу внутрішня область, де всі сусіди на місці; край — окремо нижче. У C ідемо піксель за пікселем; у Python та сама логіка лягає на зрізи `numpy` — кожен тип пікселя обробляємо цілим підмасивом за раз, без явного циклу.

```c
#include <stdint.h>

typedef struct { uint8_t r, g, b; } RGB;

static uint8_t avg2(int a, int b)            { return (uint8_t)((a + b + 1) / 2); }
static uint8_t avg4(int a, int b, int c, int d){ return (uint8_t)((a + b + c + d + 2) / 4); }

// raw[H][W] — сира RGGB-мозаїка; out[H][W] — повний RGB.
// Обробляємо лише ВНУТРІШНІ пікселі 1..H-2 / 1..W-2 (у краю бракує сусідів).
void demosaic_bilinear(int H, int W, const uint8_t raw[H][W], RGB out[H][W]) {
    for (int y = 1; y < H - 1; y++) {
        for (int x = 1; x < W - 1; x++) {
            int up = raw[y-1][x],   dn = raw[y+1][x];
            int lf = raw[y][x-1],   rt = raw[y][x+1];
            int ul = raw[y-1][x-1], ur = raw[y-1][x+1];
            int dl = raw[y+1][x-1], dr = raw[y+1][x+1];
            uint8_t c = raw[y][x];                 // виміряна складова цього пікселя
            int ey = y & 1, ex = x & 1;

            if (ey == 0 && ex == 0) {              // червоний піксель
                out[y][x].r = c;
                out[y][x].g = avg4(up, dn, lf, rt);
                out[y][x].b = avg4(ul, ur, dl, dr);
            } else if (ey == 0 && ex == 1) {       // зелений на R-рядку
                out[y][x].r = avg2(lf, rt);        // червоні — по боках
                out[y][x].g = c;
                out[y][x].b = avg2(up, dn);        // сині — зверху/знизу
            } else if (ey == 1 && ex == 0) {       // зелений на B-рядку
                out[y][x].r = avg2(up, dn);        // червоні — зверху/знизу
                out[y][x].g = c;
                out[y][x].b = avg2(lf, rt);        // сині — по боках
            } else {                               // синій піксель
                out[y][x].r = avg4(ul, ur, dl, dr);
                out[y][x].g = avg4(up, dn, lf, rt);
                out[y][x].b = c;
            }
        }
    }
}
```

```python
import numpy as np

def demosaic_bilinear(raw):
    """raw: 2-D uint8 RGGB-мозаїка -> out: (H, W, 3) uint8 RGB.
    Кожен із чотирьох типів пікселя — окремий зріз [початок::2]; сусідів
    беремо зсунутими зрізами й усереднюємо в int, аби не переповнити байт."""
    H, W = raw.shape
    r = raw.astype(np.int32)                      # у int, щоб суми не обгорнулись
    out = np.zeros((H, W, 3), np.int32)

    def avg(*a):                                  # чесне округлення: +half перед /n
        return (sum(a) + len(a) // 2) // len(a)

    # координатні зрізи внутрішньої області та її восьми сусідів
    c  = r[1:-1, 1:-1]
    up, dn = r[0:-2, 1:-1], r[2:, 1:-1]
    lf, rt = r[1:-1, 0:-2], r[1:-1, 2:]
    ul, ur = r[0:-2, 0:-2], r[0:-2, 2:]
    dl, dr = r[2:, 0:-2],  r[2:, 2:]
    o = out[1:-1, 1:-1]                            # вид на внутрішні пікселі виходу

    ey = np.arange(1, H - 1)[:, None] & 1          # парність рядка/стовпця
    ex = np.arange(1, W - 1)[None, :] & 1

    red   = (ey == 0) & (ex == 0)                  # червоний піксель
    grn_r = (ey == 0) & (ex == 1)                  # зелений на R-рядку
    grn_b = (ey == 1) & (ex == 0)                  # зелений на B-рядку
    blue  = (ey == 1) & (ex == 1)                  # синій піксель

    o[red]   = np.stack([c, avg(up, dn, lf, rt), avg(ul, ur, dl, dr)], -1)[red]
    o[grn_r] = np.stack([avg(lf, rt), c, avg(up, dn)], -1)[grn_r]
    o[grn_b] = np.stack([avg(up, dn), c, avg(lf, rt)], -1)[grn_b]
    o[blue]  = np.stack([avg(ul, ur, dl, dr), avg(up, dn, lf, rt), c], -1)[blue]
    return out.astype(np.uint8)
```

Логіка тримається на одній табличці парностей: за `(y&1, x&1)` ми точно знаємо, яка складова виміряна, а решту збираємо із сусідів потрібного кольору. Зелене у червоному й синьому пікселях має аж чотири сусіди (хрест) — тому й `avg4`; у зелених пікселях два інші кольори лежать рівно по два, тому `avg2`. Розкладка тут не випадкова, а прямо випливає з геометрії RGGB: навколо червоного пікселя зелені сидять по хресту, а сині — по кутах; у зеленого пікселя один із відсутніх кольорів лежить уздовж його рядка, а другий — уздовж стовпця. Варто один раз вималювати квадрат 2×2 на папері — і всі чотири гілки `if` стають очевидними.

**Скільки це коштує.** На піксель припадає кілька цілочислових додавань і одне ділення на 2 чи 4 (а ділення на степінь двійки компілятор зведе до зсуву). Жодних буферів історії, жодних умножень, один прохід по кадру — складність лінійна, `O(H·W)`. Саме ця дешевизна й зробила білінійну демозаїку стандартним вибором для слабких контролерів камер: вона встигає в реальному часі навіть там, де на складніший алгоритм не вистачило б ні такту, ні пам'яті. Якщо потрібна швидкість понад усе, гілки `if` усередині циклу прибирають, обробляючи кадр чотирма окремими проходами — по одному на кожен тип пікселя з кроком 2; тіло циклу тоді без жодного розгалуження, і процесор його любить.

**Розумніший крок — дивитися на край.** Слабке місце білінійного середнього — що воно всереднює наосліп, не питаючи, чи немає поруч різкої межі. Перший дешевий апгрейд стосується зеленого каналу (він найгустіший, тож від нього найбільше залежить різкість): перш ніж усереднювати, порівнюємо градієнт **по горизонталі** й **по вертикалі**. Якщо ліво-правий перепад менший за верх-низ, межа радше горизонтальна — тоді беремо зелене лише з лівого й правого сусідів (уздовж межі), а не з усіх чотирьох. І навпаки. Так інтерполяція йде **вздовж** контуру, а не впоперек, і «застібка» на межах майже зникає. Червоне й синє потім відновлюють уже відносно цього кращого зеленого. Коштує це лиш кількох порівнянь на піксель, а артефактів прибирає помітно — тому крайо-чутливий зелений став наступним за популярністю після голого білінійного.

**Маленький числовий приклад.** Хай внутрішній червоний піксель виміряв `R = 200`, а його зелені сусіди по хресту дають `190, 198, 202, 194`, сині по кутах — `40, 44, 38, 46`. Тоді зелене відновлюємо як `(190+198+202+194+2)/4 = 786/4 = 196`, синє — як `(40+44+38+46+2)/4 = 170/4 = 42`. На виході піксель `(R, G, B) = (200, 196, 42)` — теплий жовто-зелений, цілком у дусі оточення. Видно й роль округлення: без `+2` зелене вийшло б `784/4 = 196` (тут збіглося), але на сумах на кшталт `785` різниця між `196` і `197` накопичується по всьому кадру в ледь помітне потемніння — тому половину дільника додаємо завжди.

**Край кадру.** На рамці частини сусідів не існує (`y-1` чи `x+1` вилазить за межі). Найпростіше й безпечно — **повторити край**: для відсутнього сусіда брати найближчий наявний (clamp координати). Дешева заміна — продублювати перший/останній рядок і стовпець у тимчасовий буфер на один піксель ширший з кожного боку, тоді внутрішній цикл накриває й колишній край без жодного `if`. Аби на рамці не лишилося сміття, головне правило одне: ніколи не читати поза масивом.

**Пам'ять і порядок обходу.** Сира мозаїка — це суцільний масив байтів, рядок за рядком. Демозаїка читає для кожної точки лише її безпосередніх сусідів — тобто поточний рядок і по одному над ним і під ним. Це означає, що тримати в пам'яті весь кадр не обов'язково: достатньо **трьох рядків** — і можна обробляти потік прямо з сенсора, видаючи готові пікселі рядок за рядком (це називають обробкою «ковзним вікном»). Для контролера камери з кількома кілобайтами пам'яті це принципово: повний кадр на 12 МП туди не вліз би, а три рядки — легко. Обходити кадр треба саме рядками (за зростанням `x` усередині рядка): так сусідні читання лягають поряд у пам'яті й кеш працює на тебе, а не проти. Обхід стовпцями дав би ту саму картинку, але куди повільніше через постійні промахи кеша.

**Пастки.**

- **Зсув візерунка.** Якщо кадр читають з обрізанням або з іншим кутом відліку, парність `(y%2, x%2)` зсувається — і весь колір «їде»: червоне стає синім. Перш ніж демозаїчити, переконайся, який саме фазовий варіант віддає твій сенсор (RGGB, BGGR, GRBG, GBRG) — їх чотири, і кожен зсунутий на півклітинки.
- **Округлення вниз.** `(a+b)/2` без `+1` систематично занижує колір на пів-одиниці на кожному пікселі — на великому полі це помітний потемнілий відтінок. Додаємо половину дільника перед діленням.
- **Артефакти на межах.** Білінійне середнє спокійно всереднює сусідів з обох боків різкої межі — звідси «застібка» вздовж контурів і несправжній колір на тонких смужках. Це не баг коду, а межа самого методу: розумніша демозаїка спершу оцінює **напрям краю** й інтерполює **вздовж** нього, а не впоперек.
- **Тип переповнення.** Сума чотирьох байтів — до 1020, це далеко за межу `uint8_t`. Рахувати проміжне обов'язково в `int` (як вище), інакше дістанеш обгортання й кольорові плями там, де їх нема.
- **Колірний зсув від світла.** Біле світло різної температури по-різному «фарбує» сирі канали ще до демозаїки — зняте при лампі розжарювання тхне жовтим. Інтерполяція цього не виправляє, бо вона лише заповнює дірки в межах кожного каналу. Баланс білого — окремий крок: множення каналів на коефіцієнти; робити його варто **після** демозаїки (або узгоджено з нею), а не плутати з інтерполяцією.

Це найдешевший робочий варіант — кілька додавань на піксель, жодних буферів історії. Для контролю кольору в машинному баченні з нього й починають, а коли артефакти заважають — переходять на крайо-чутливий алгоритм або працюють із сирою мозаїкою напряму. Головне розуміти: жодна демозаїка не **повертає** втрачене, вона лише **правдоподібно домальовує** — тож якщо колірна деталь критична, її треба знімати каналом, який її реально виміряв, а не сподіватися на гадку з сусідів.
