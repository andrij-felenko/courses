Коли компілятор обробляє сирцеві файли програми, він створює набір релоковних об'єктних файлів (`.o`), у кожному з яких адреси секцій починаються з нуля (`0x00000000`). На комп'ютері під керуванням операційної системи цим нулям не обов'язково відповідати фізичний кремній: системний завантажувач ELF-файлів і модуль керування пам'яттю (MMU) виділяють віртуальні сторінки, налаштовують таблиці трансляції адрес і динамічно зв'язують виклики.

У вбудованих мікроконтролерних системах (ARM Cortex-M, RISC-V, AVR) операційної системи та динамічного завантажувача немає. Процесор стартує безпосередньо з апаратного скидання, звертаючись до жорстко розведених шин пам'яті: енергонезалежний Flash-контролер розміщений за адресою `0x08000000`, блок оперативної пам'яті SRAM — за адресою `0x20000000`, а спеціалізована пам'ять прямого зв'язку з ядром (CCMRAM) — за адресою `0x10000000`. Якщо об'єктні файли просто склеїти докупи без точного плану, процесор з першого ж такту спробує виконати випадкові байти, запише змінні у захищену від запису пам'ять або переповнить стек.

Скрипт компонувальника (англ. *Linker Script*, зазвичай файл із розширенням `.ld`) — це архітектурне креслення бінарного образу програми. Він надає компонувальнику (GNU LD) вичерпні правила: які фізичні банки пам'яті існують у чипі, в які ділянки пам'яті слід покласти інструкції, де розмістити незмінні таблиці, як організувати перенесення змінних із Flash у RAM під час увімкнення живлення та як розрахувати початковий покажчик стека.

## 1. Фізична пам'ять і директива `MEMORY`

Першим завданням скрипта компонувальника є опис апаратної топології мікроконтролера. Компонувальник повинен знати, які регіони адрес існують на кристалі, скільки байтів у них вміщується та які операції над ними дозволені (читання, запис чи виконання інструкцій). Для цього використовується блок `MEMORY`.

```ld
MEMORY
{
  FLASH   (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM     (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
  CCMRAM  (rw)  : ORIGIN = 0x10000000, LENGTH = 64K
  BKPSRAM (rw)  : ORIGIN = 0x40024000, LENGTH = 4K
}
```

Кожен рядок всередині блоку описує окремий фізичний банк:

1. **Ім'я регіону** (`FLASH`, `RAM`, `CCMRAM`, `BKPSRAM`): внутрішній ідентифікатор, який використовується далі у секціях для прив'язки коду чи даних.
2. **Атрибути доступу** в круглих дужках:
   * `r` (read) — дозволено читання (секції констант `.rodata`);
   * `w` (write) — дозволено запис (секції змінних `.data`, `.bss`);
   * `x` (execute) — дозволено виконання коду як інструкцій процесора (секція `.text`);
   * `a` (allocatable) — під секцію виділяється пам'ять під час завантаження;
   * `i` (initialized) — секція містить початкові дані;
   * `!` — інвертує перевірку атрибутів.
3. **`ORIGIN` (або `org`, `o`)**: базова фізична адреса, з якої починається банк пам'яті в адресному просторі мікроконтролера.
4. **`LENGTH` (або `len`, `l`)**: максимальний розмір банку в байтах (підтримуються суфікси `K` — множник 1024, та `M` — множник 1024 × 1024).

Призначення атрибутів — не просто документація, а суворий контроль цілісності. Якщо під час збірки розмір скомпільованого коду перевищить розмір виділеного банку `FLASH`, GNU LD згенерує помилку:

```text
arm-none-eabi-ld: firmware.elf section `.text' will not fit in region `FLASH'
arm-none-eabi-ld: region `FLASH' overflowed by 14280 bytes
```

Це запобігає створенню пошкодженого двійкового файлу, який під час прошивання міг би тихо обрізатися або затерти сусідні сектори пам'яті.

Для побудови універсальних BSP (Board Support Packages) під різні модифікації чипів однієї лінійки використовується директива `REGION_ALIAS("ALIAS_NAME", REGION_NAME)`. Вона дозволяє створювати єдиний базовий шаблон секцій, підключаючи конкретну карту пам'яті через `INCLUDE`. Повний перелік синтаксичних конструкцій наведено у вставці [Довідник синтаксису GNU LD](root:sf-lang/linker-script/api-ld-syntax.md).

## 2. Анатомія секцій та директива `SECTIONS`

Скомпільовані об'єктні файли містять набір стандартних вхідних секцій (Input Sections). Завдання директиви `SECTIONS` — згрупувати ці вхідні секції з усіх об'єктних файлів проєкту і призначити їм вихідні секції (Output Sections), зв'язавши кожну вихідну секцію з відповідним банком пам'яті.

![Анатомія та внутрішня структура скрипта компонувальника GNU LD](/root/eng/sf-lang/linker-script/img/linker-script-architecture.svg)
*Анатомія скрипта компонувальника GNU LD. Директива MEMORY декларує фізичні банки Flash та RAM, а блок SECTIONS розподіляє вхідні секції об'єктних файлів, обчислює символи меж пам'яті та керує адресами завантаження (LMA) і виконання (VMA).*

Стандартний образ мікроконтролерної програми складається з п'яти обов'язкових вихідних секцій:

### 1. Таблиця векторів переривань (`.isr_vector`)
В архітектурі ARM Cortex-M перші слова пам'яті Flash за адресою `0x08000000` жорстко зарезервовані процесором під векторну таблицю: слово 0 містить початкове значення покажчика стека (MSP), слово 1 — адресу функції скидання `Reset_Handler`, а наступні слова — адреси обробників винятків та апаратних переривань.

```ld
.isr_vector :
{
  . = ALIGN(4);
  KEEP(*(.isr_vector))
  . = ALIGN(4);
} >FLASH
```

Ключове слово `KEEP()` забороняє компонувачу видаляти цю секцію під час оптимізації прапорцем `--gc-sections`. Оскільки у програмі на C/C++ немає явного виклику таблиці векторів як функції, оптимізатор без `KEEP()` вважав би її «мертвим кодом» і викинув би зі збірки.

### 2. Секція коду (`.text`)
Містить виконувані машинні інструкції всіх функцій програми.

```ld
.text :
{
  . = ALIGN(4);
  *(.text)           /* Секції .text з усіх об'єктних файлів */
  *(.text*)          /* Додаткові секції на кшталт .text.main, .text.printf */
  *(.glue_7)         /* Допоміжний код перемикання ARM-Thumb */
  *(.glue_7t)
  *(.eh_frame)

  KEEP (*(.init))
  KEEP (*(.fini))

  . = ALIGN(4);
  _etext = .;        /* Глобальний символ: кінець виконуваного коду */
} >FLASH
```

### 3. Секція сталих даних (`.rodata`)
Містить константи, числові коефіцієнти, константні структури та рядкові літерали (`"System OK"`). Оскільки ці дані не змінюються під час роботи, вони залишаються у Flash і читаються напряму через шину даних (D-Code / AHB).

```ld
.rodata :
{
  . = ALIGN(4);
  *(.rodata)
  *(.rodata*)
  . = ALIGN(4);
} >FLASH
```

### 4. Секція ініціалізованих змінних (`.data`)
Містить глобальні та статичні змінні з ненульовими початковими значеннями (наприклад, `int timeout_ms = 5000;`). Оскільки змінні змінюються під час виконання, їхнім місцем роботи має бути RAM. Проте оперативна пам'ять при вимкненні живлення втрачає вміст, тому початкові значення повинні зберігатися у Flash і копіюватися в RAM при кожному старті процесора.

### 5. Секція неініціалізованих змінних (`.bss`)
Містить глобальні змінні, не ініціалізовані явно (`int counter;`) або явно ініціалізовані нулем (`int status = 0;`), а також великі буфери. Зберігати мегабайти нулів у Flash немає сенсу — образ прошивки роздувся б порожніми байтами. Тому у Flash зберігається лише інформація про її розмір, а стартовий код заповнює відповідну ділянку RAM нулями (`0x00`).

```ld
.bss :
{
  . = ALIGN(4);
  _sbss = .;         /* Маркер початку .bss */
  __bss_start__ = _sbss;
  *(.bss)
  *(.bss*)
  *(COMMON)          /* Спільні неініціалізовані символи за стандартом C */
  . = ALIGN(4);
  _ebss = .;         /* Маркер кінця .bss */
  __bss_end__ = _ebss;
} >RAM
```

### 6. Спеціальні секції: розміщення коду в швидкій RAM
Деякі алгоритми (наприклад, швидке перетворення Фур'є для DSP або функції запису у Flash-пам'ять) вимагають виконання з оперативної пам'яті без затримок читання Flash. Для цього створюють окрему секцію, яка завантажується у Flash, але виконується в оперативній пам'яті (RAM або CCMRAM):

```ld
.ccmram :
{
  . = ALIGN(4);
  _sccmram = .;
  *(.ccmram)
  *(.ccmram*)
  . = ALIGN(4);
  _eccmram = .;
} >CCMRAM AT> FLASH
_siccmram = LOADADDR(.ccmram);
```

У вихідному коді на C/C++ функцію чи масив прив'язують до цієї секції за допомогою атрибута: `__attribute__((section(".ccmram")))`.

## 3. Дуальність адрес: LMA проти VMA

Найважливіша концепція низькорівневого компонування — різниця між адресою завантаження та адресою виконання:

* **VMA (Virtual Memory Address / Execution Address)** — адреса, за якою секція знаходиться **під час роботи програми**. Саме ці адреси компонувальник підставляє в машинні інструкції при зверненні до змінних або функцій.
* **LMA (Load Memory Address)** — адреса, за якою секція фізично розташована **у бінарному образі прошивки** у Flash-пам'яті перед початком роботи.

Для секцій `.text` та `.rodata` VMA збігається з LMA: код і константи прошиваються у Flash за адресою `0x08000000` і під час роботи процесор читає їх безпосередньо з Flash за тією ж адресою `0x08000000`. Це називається прямим виконанням на місці (XIP — eXecute In Place).

Для секції `.data` VMA та LMA **завжди відрізняються**:
* VMA знаходиться в RAM (наприклад, `0x20000000`), бо процесор повинен мати можливість читати й змінювати значення змінних;
* LMA знаходиться у Flash (наприклад, `0x08004500`, відразу після завершення секції `.rodata`), бо початкові значення змінних повинні переживати вимкнення живлення.

![Співвідношення фізичних банків пам'яті, адрес завантаження LMA та адрес виконання VMA](/root/eng/sf-lang/linker-script/img/memory-regions-lma-vma.svg)
*Співвідношення фізичних банків пам'яті Flash та RAM. Секції .text та .rodata мають однаковий VMA та LMA у Flash. Секція .data зберігається у Flash (LMA = _sidata), але виконується в RAM (VMA = _sdata). Секція .bss існує виключно в RAM.*

У синтаксисі GNU LD дуальність LMA та VMA виражається операторами `>REGION_VMA AT>REGION_LMA`:

```ld
.data :
{
  . = ALIGN(4);
  _sdata = .;        /* VMA початку .data в RAM */
  *(.data)
  *(.data*)
  . = ALIGN(4);
  _edata = .;        /* VMA кінця .data в RAM */
} >RAM AT> FLASH

/* Отримання фізичної адреси початку .data у Flash (LMA) */
_sidata = LOADADDR(.data);
```

Оператор `>RAM` вказує компонувальнику: «розраховуй усі покажчики на змінні цієї секції так, ніби вони живуть у `RAM` з адреси `_sdata`». А оператор `AT> FLASH` вказує: «помісти байти початкових значень цих змінних у бінарний файл у секцію `FLASH`». Вбудована функція `LOADADDR(.data)` повертає абсолютну адресу Flash (LMA), де збережено ці початкові байти, і записує її в символ `_sidata`.

## 4. Лічильник адреси та вирівнювання `ALIGN`

Ключовим елементом обчислення позицій у скрипті є **лічильник адреси** (Location Counter), який позначається символом крапки `.`.

Лічильник адреси зберігає поточну позицію в адресному просторі:
1. Коли компонувальник додає черговий об'єктний файл у вихідну секцію, значення `.` автоматично збільшується на розмір доданих даних.
2. Програміст може зчитувати значення `.`, присвоюючи його символам: `_sdata = .;`.
3. Програміст може примусово змінювати `.`, створюючи проміжки або вирівнюючи адреси.

### Чому небезпечний нерівний Location Counter

Архітектура ARM Cortex-M має 32-розрядну системну шину даних. Інструкції швидкого завантаження слів (`LDR`, `STR`, `LDM`, `STM`) працюють максимально ефективно, коли адреса кратна 4 байтам (32 біти). Більше того, інструкції завантаження подвійних слів (`LDRD`, `STRD`) для 64-розрядних чисел або регістрів FPU вимагають 8-байтного вирівнювання.

Уявімо, що секція коду `.text` закінчилася за непарною адресою `0x08001023` (через байтовий константний рядок або масив символів). Якщо секція `.data` почнеться відразу з `0x08001023`, то:
1. Адреса завантаження `_sidata` стане некратною 4.
2. Стартовий код, який копіює слова по 4 байти за допомогою `uint32_t*`, спробує прочитати пам'ять за некратною адресою `0x08001023`.
3. Якщо на чипі активовано апаратний контроль вирівнювання (біт `UNALIGN_TRP` у системному регістрі керування конфігурацією `SCB->CCR`), ядро негайно перейде в стан апаратної аварії **UsageFault / HardFault**. Якщо ж контроль вимкнено, зчитування виконуватиметься за два цикли шини замість одного, сповільнюючи завантаження.

Щоб запобігти цій помилці, перед початком і після завершення кожної секції обов'язково застосовують функцію вирівнювання:

```ld
. = ALIGN(4);
```

Функція `ALIGN(n)` обчислює найближчу адресу, більшу або рівну поточному значенню `.`, яка ділиться на `n` без залишку:

```
нова_адреса = (поточна_адреса + n - 1) & ~(n - 1)
```

Якщо `.` дорівнює `0x08001023`, то виклик `. = ALIGN(4);` збільшить значення крапки до `0x08001024`, заповнивши 1 проміжний байт нулем.

## 5. Символи лінкера: чому це адреси, а не змінні

Одна з найпоширеніших помилок при роботі зі скриптами компонування полягає у нерозумінні природи символів лінкера в мовах C та C++.

Розглянемо рядок у скрипті компонувальника:

```ld
_sdata = .;
```

Для компілятора мови C декларація змінної `uint32_t x = 100;` означає дві речі:
1. Компілятор виділяє 4 байти в пам'яті для збереження числа 100.
2. Ідентифікатор `x` асоціюється з цією коміркою пам'яті. Коли в коді пишуть `x`, процесор зчитує вміст за цією адресою.

Для скрипта компонувальника символ `_sdata` — це **запис у таблиці символів ELF (`.symtab`)**, під який **не виділяється жодного байта пам'яті**. Символ — це суто число (адреса), яка існує лише під час збірки.

```
+-------------------------------------------------------------+
|                Таблиця символів ELF (.symtab)               |
+-------------------------------------------------------------+
| Ім'я символу |  Значення (Адреса) | Розмір | Секція         |
+--------------+--------------------+--------+----------------+
| _sdata       |  0x20000000        | 0      | .data (VMA)    |
| _edata       |  0x20000240        | 0      | .data (VMA)    |
| _sidata      |  0x08003100        | 0      | FLASH (LMA)    |
| _sbss        |  0x20000240        | 0      | .bss (VMA)     |
| _ebss        |  0x20001000        | 0      | .bss (VMA)     |
| _estack      |  0x20020000        | 0      | *ABS*          |
+-------------------------------------------------------------+
```

### Звернення до символів лінкера з C та C++

Якщо оголосити символ лінкера як звичайну змінну `extern uint32_t _sdata;` і спробувати прочитати її значення без взяття адреси, процесор виконає інструкцію читання пам'яті за цією адресою. У результаті програма отримає перші 4 байти самих даних секції, а не адресу їхнього початку.

Тому звернення до символів лінкера завжди вимагає або оператора взяття адреси `&`, або оголошення символу як неповнорозмірного масиву (incomplete array):

:::tabs
```c
/* Отримання адрес символів лінкера мовою C */
#include <stdint.h>

/* Варіант 1: Оголошення як змінної та взяття адреси через & */
extern uint32_t _sdata;
extern uint32_t _edata;

/* Варіант 2: Оголошення як масиву без розміру (ім'я масиву є адресою) */
extern uint32_t _sbss[];
extern uint32_t _ebss[];

void memory_audit(void) {
    /* Отримання числових адрес початку та кінця .data */
    uint32_t *p_data_start = &_sdata;
    uint32_t *p_data_end   = &_edata;
    uint32_t data_bytes    = (uint8_t*)p_data_end - (uint8_t*)p_data_start;

    /* Отримання числових адрес початку та кінця .bss */
    uint32_t *p_bss_start  = _sbss;
    uint32_t *p_bss_end    = _ebss;
    uint32_t bss_bytes     = (uint8_t*)p_bss_end - (uint8_t*)p_bss_start;
}
```
```cpp
// Отримання адрес символів лінкера мовою C++20
#include <cstdint>
#include <span>
#include <concepts>

// Експорт символів із лінкер-скрипта через масиви
extern "C" {
    extern std::uint32_t _sdata[];
    extern std::uint32_t _edata[];
    extern std::uint32_t _sbss[];
    extern std::uint32_t _ebss[];
}

struct MemorySectionInfo {
    std::uintptr_t start_address;
    std::uintptr_t end_address;
    std::size_t size_bytes;
};

MemorySectionInfo get_data_section_info() noexcept {
    const auto start = reinterpret_cast<std::uintptr_t>(_sdata);
    const auto end   = reinterpret_cast<std::uintptr_t>(_edata);
    return {
        .start_address = start,
        .end_address   = end,
        .size_bytes    = end - start
    };
}

MemorySectionInfo get_bss_section_info() noexcept {
    const auto start = reinterpret_cast<std::uintptr_t>(_sbss);
    const auto end   = reinterpret_cast<std::uintptr_t>(_ebss);
    return {
        .start_address = start,
        .end_address   = end,
        .size_bytes    = end - start
    };
}
```
:::

### Директива `PROVIDE`

Директива `PROVIDE(symbol = expr)` оголошує символ лише в тому випадку, якщо він використовується в об'єктних файлах і не був визначений у самому вихідному коді програми:

```ld
PROVIDE(_estack = ORIGIN(RAM) + LENGTH(RAM));
PROVIDE(end = .);
```

Якщо в одному з вихідних файлів розробник явно напише `void *end = &custom_heap;`, лінкер використає змінну з сирцевого коду. Якщо ж визначення немає, компонувальник створить символ автоматично на основі виразу в `PROVIDE`.

## 6. Взаємодія Startup-коду з лінкер-скриптом

Стартовий код (Startup Code) — це перші інструкції, які виконуються мікроконтролером після подачі живлення або сигналу скидання. Він виступає мостом між статичним описом пам'яті у `.ld` файлі та динамічним виконанням програми у функції `main()`.

![Послідовність виконання стартового коду при апаратному скиданні](/root/eng/sf-lang/linker-script/img/startup-initialization-flow.svg)
*Послідовність апаратної та програмної ініціалізації Cortex-M. Апаратне ядро зчитує початковий покажчик стека _estack та адресу Reset_Handler. Стартовий код відновлює секцію .data зі сховища Flash, очищує .bss, викликає конструктори C++ і передає керування у main().*

### Апаратний старт процесора (Hardware Reset Sequence)
Під час виходу з сигналу RESET апаратна логіка ARM Cortex-M виконує два обов'язкових кроки:
1. Зчитує 32-бітне значення з нульової адреси пам'яті `0x08000000` і завантажує його в регістр головного покажчика стека (MSP). У лінкер-скрипті за цією адресою записано значення `_estack` (`0x20020000`).
2. Зчитує наступне 32-бітне значення з адреси `0x08000004` і завантажує його в лічильник інструкцій (PC). Це адреса функції `Reset_Handler` (з молодшим бітом 1, що вказує на виконання в наборі інструкцій Thumb).
3. Процесор починає виконання інструкцій функції `Reset_Handler`.

### Програмна підготовка середовища
До того, як керування перейде до першого рядка функції `main()`, `Reset_Handler` повинен виконати критичні дії з підготовки пам'яті:

:::tabs
```c
/* startup.c — Стартова ініціалізація пам'яті мовою C */
#include <stdint.h>

/* Символи-маркери, експортовані лінкер-скриптом */
extern uint32_t _sidata;  /* Початок початкових значень .data у Flash (LMA) */
extern uint32_t _sdata;   /* Початок .data у RAM (VMA) */
extern uint32_t _edata;   /* Кінець .data у RAM (VMA) */
extern uint32_t _sbss;    /* Початок .bss у RAM (VMA) */
extern uint32_t _ebss;    /* Кінець .bss у RAM (VMA) */

extern void __libc_init_array(void);
extern int main(void);

void Reset_Handler(void) {
    /* 1. Копіювання ініціалізованих змінних .data з Flash у SRAM */
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) {
        *dst++ = *src++;
    }

    /* 2. Очищення секції .bss (заповнення нулями) */
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0U;
    }

    /* 3. Виклик статичних і глобальних конструкторів C++ */
    __libc_init_array();

    /* 4. Запуск головної логіки застосунку */
    main();

    /* Якщо main() завершився — зупинка процесора */
    while (1) {
        __asm volatile("wfi");
    }
}
```
```cpp
// startup.cpp — Ідіоматична стартова ініціалізація мовою C++20
#include <cstdint>
#include <span>
#include <algorithm>

// Імпорт символів зі скрипта компонування
extern "C" {
    extern std::uint32_t _sidata[];
    extern std::uint32_t _sdata[];
    extern std::uint32_t _edata[];
    extern std::uint32_t _sbss[];
    extern std::uint32_t _ebss[];

    void __libc_init_array() noexcept;
    int main();
    void Reset_Handler() noexcept;
}

void Reset_Handler() noexcept {
    // 1. Безпечне перенесення .data через std::span та std::copy
    const auto data_words = static_cast<std::size_t>(_edata - _sdata);
    const std::span<const std::uint32_t> flash_data{_sidata, data_words};
    const std::span<std::uint32_t> ram_data{_sdata, data_words};
    std::copy(flash_data.begin(), flash_data.end(), ram_data.begin());

    // 2. Обнулення .bss через std::fill
    const auto bss_words = static_cast<std::size_t>(_ebss - _sbss);
    const std::span<std::uint32_t> ram_bss{_sbss, bss_words};
    std::fill(ram_bss.begin(), ram_bss.end(), 0U);

    // 3. Ініціалізація глобальних об'єктів C++ (конструктори .init_array)
    __libc_init_array();

    // 4. Передача керування в main()
    main();

    while (true) {
        asm volatile("wfi");
    }
}
```
:::

Повний приклад побудови проєкту зі складанням таблиці векторів, стартапом і конфігурацією збірки винесено у вставку [Практика розробки: Bare-Metal стартап і Linker Script для ARM Cortex-M](root:sf-lang/linker-script/proj-baremetal-cortexm.md).

## 7. Спеціальні секції: Купа, Стек, C++ винятки та No-Init

Окрім класичних секцій коду та даних, реальні прошивки вимагають розміщення спеціалізованих структур пам'яті.

### Динамічна купа (Heap) та стек (Stack)

Секція `._user_heap_stack` резервує простір для динамічного виділення пам'яті функцією `malloc()` (або оператором `new`) через системний виклик `_sbrk()`, а також встановлює межі для головного стека процесора:

```ld
._user_heap_stack :
{
  . = ALIGN(8);
  PROVIDE ( end = . );
  PROVIDE ( _end = . );
  . = . + _Min_Heap_Size;
  . = . + _Min_Stack_Size;
  . = ALIGN(8);
} >RAM
```

Символи `end` та `_end` вказують на початок вільної динамічної пам'яті для стандартної бібліотеки Newlib.

### C++ розгортання винятків (`.ARM.extab` та `.ARM.exidx`)

Якщо у проєкті на C++ увімкнено підтримку винятків (`try` / `catch` без прапорця `-fno-exceptions`), компілятор генерує таблиці розгортання стека (Stack Unwinding Tables). Вони розміщуються у Flash-пам'яті:

```ld
.ARM.extab : {
  *(.ARM.extab* .gnu.linkonce.armextab.*)
} >FLASH

.ARM.exidx : {
  PROVIDE_HIDDEN (__exidx_start = .);
  *(.ARM.exidx* .gnu.linkonce.armexidx.*)
  PROVIDE_HIDDEN (__exidx_end = .);
} >FLASH
```

Якщо ці секції не описати у лінкер-скрипті, компонувальник або відкине їх, зробивши обробку винятків неможливою, або розмістить за замовчуванням у випадковому місці образу.

### Незанулювана пам'ять (`.noinit`)

Коли мікроконтролер перезавантажується за сигналом сторожового таймера (Watchdog Reset) або програмного скидання (Software Reset), вміст оперативної пам'яті SRAM фізично зберігається (якщо не вимикалося живлення). Проте стандартний стартовий код при кожному старті затирає секцію `.bss` нулями.

Щоб зберегти журнал діагностики аварії (Crash Log) або лічильник перезапусків між скиданнями, створюють секцію з прапорцем `(NOLOAD)`:

```ld
.noinit (NOLOAD) :
{
  . = ALIGN(4);
  *(.noinit)
  *(.noinit*)
  . = ALIGN(4);
} >RAM
```

Оскільки секція позначена як `(NOLOAD)`, вона не потрапляє у діапазон між `_sbss` та `_ebss`, і стартовий код не торкається її байтів під час ініціалізації.

## 8. Аналіз карти пам'яті (`.map`) та діагностика

Під час розробки вбудованого програмного забезпечення недостатньо просто отримати статус успішного завершення збірки. Необхідно точно знати, як саме розподілилися ресурси мікроконтролера. Для цього під час виклику компонувальника передають прапорець генерації карти пам'яті:

```bash
arm-none-eabi-gcc ... -Wl,-Map=output.map,--cref
```

Карта пам'яті (`.map`) — це структурований текстовий звіт компонувальника, який показує:
1. **Memory Configuration** — список банків пам'яті, їхні початкові адреси, максимальні довжини та залишкові вільні байти.
2. **Linker script and memory map** — детальний перелік кожної вихідної секції з точними адресами VMA та LMA, а також список усіх функцій і змінних, які до неї увійшли (із зазначенням конкретного `.o` файлу та розміру в байтах).
3. **Cross Reference Table (`--cref`)** — таблиця перехресних посилань: де оголошено кожен символ і які інші файли на нього посилаються.

### Приклад аналізу секції `.data` у `.map`

```text
.data           0x20000000       0x24 load address 0x08004120
                0x20000000                _sdata = .
 *(.data*)
 .data.uart_cfg 0x20000000       0x14 uart.o
                0x20000000                uart_cfg
 .data.pid_gain 0x20000014       0x0c control.o
                0x20000014                pid_gain
                0x20000020                . = ALIGN (0x4)
                0x20000024                _edata = .
                0x08004120                _sidata = LOADADDR (.data)
```

З цього фрагмента інженер отримує точну інформацію:
* Змінна `uart_cfg` з файлу `uart.o` має розмір 20 байтів (`0x14`) і розташована в RAM за адресою `0x20000000`.
* Змінна `pid_gain` з файлу `control.o` має розмір 12 байтів (`0x0c`) і починається за адресою `0x20000014`.
* Сумарний розмір секції `.data` складає 36 байтів (`0x24`).
* У Flash-пам'яті ці початкові байти збережено за адресою LMA `0x08004120`.

### Діагностика переповнення стека та купи

Динамічна купа (Heap) та системний стек (Stack) ділять між собою залишок оперативної пам'яті SRAM після секцій `.data` та `.bss`. Купа росте від молодших адрес до старших (вгору), а стек процесора Cortex-M — від вершини `_estack` до молодших адрес (вниз).

```
Нижні адреси RAM 0x20000000                                 Верхні адреси RAM 0x20020000
+----------+----------+------------------------+---------------------------------------+
|  .data   |   .bss   | Heap (росте вгору ->)  |  (<- росте вниз) Main Stack Pointer   |
| (змінні) | (нулі)   | malloc / new           | локальні змінні, кадри переривань     |
+----------+----------+------------------------+---------------------------------------+
                      ^                        ^                                       ^
                   _ebss                    Heap Limit                              _estack
```

Якщо секції `.data` та `.bss` розростаються через великі статичні буфери, проміжок між купою та стеком зменшується. Якщо купа перетнеться зі стеком під час виконання програми, виникне тихе пошкодження даних (Memory Corruption): запис у локальну змінну виклику функції затре блок пам'яті, виділений через `malloc()`, або навпаки.

Щоб компонувальник виявляв дефіцит пам'яті автоматично ще під час компіляції, у скрипт додають статичні обмеження через директиву `ASSERT`:

```ld
_Min_Heap_Size  = 0x800;  /* Потрібно щонайменше 2 КБ для купи */
_Min_Stack_Size = 0x1000; /* Потрібно щонайменше 4 КБ для стека */

ASSERT(_ebss + _Min_Heap_Size + _Min_Stack_Size <= ORIGIN(RAM) + LENGTH(RAM),
       "Помилка компонування: Залишок SRAM замалий для гарантованого розміщення стека й купи!")
```

Якщо після розміщення статичних змінних залишок оперативної пам'яті буде меншим за 6 КБ (2 КБ + 4 КБ), лінкер негайно перерве процес збірки з виведенням зрозумілого повідомлення про помилку.

## 9. Практичний патерн: Bootloader та зміщення векторів

У промислових пристроях прошивка часто розділяється на два незалежних двійкових образи:
1. **Завантажувач (Bootloader)** — розміщений на початку Flash (`0x08000000`, розмір 64 КБ), відповідає за оновлення по повітрю (OTA) або через шини CAN/UART.
2. **Основний застосунок (Application)** — розміщений зі зміщенням (`0x08010000`, залишок Flash).

Для основного застосунку лінкер-скрипт модифікують, змінюючи початкову адресу регіону `FLASH`:

```ld
MEMORY
{
  /* Зміщення на 64 КБ від початку Flash */
  FLASH (rx) : ORIGIN = 0x08010000, LENGTH = 448K
  RAM  (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
}
```

При цьому в коді `Reset_Handler` основного застосунку додають перенесення апаратної таблиці векторів через зміщення регістра `SCB->VTOR`:

:::tabs
```c
/* Переприв'язка таблиці векторів на початок секції застосунку в C */
SCB->VTOR = 0x08010000;
```
```cpp
// Переприв'язка таблиці векторів у C++
constexpr std::uint32_t app_vector_offset = 0x08010000;
SCB->VTOR = app_vector_offset;
```
:::

Завдяки цьому переривання починають оброблятися таблицею векторів основного застосунку, а не старого завантажувача.

Воно дозволяє розміщувати критичні обробники переривань у надшвидкій пам'яті CCMRAM/ITCM для виключення затримок читання Flash, виділяти спеціальні незанулювані секції (`.noinit`) для збереження журналів аварій при перезавантаженні за сторожовим таймером (Watchdog), створювати спільні секції пам'яті для багатоядерних процесорів (наприклад, Cortex-M4 + Cortex-M0+) та оптимізувати прошивку для роботи з кастомними Bootloader-завантажувачами через зміщення адреси вектора `ORIGIN = 0x08010000`.
