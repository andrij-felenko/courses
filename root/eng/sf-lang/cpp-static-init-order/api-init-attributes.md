# 📋 Довідник атрибутів та механізмів контролю ініціалізації

Управління черговістю запуску глобальних об'єктів, впорядкування викликів конструкторів і запобігання катастрофі статичної ініціалізації в C та C++ здійснюється через набір стандартних специфікаторів мови, класів стандартної бібліотеки та низькорівневих директив конкретних компіляторів.

Усі механізми діляться на три фундаментальні категорії: засоби перенесення ініціалізації на етап компіляції (статична фаза), примітиви відкладеного створення за вимогою під час виконання (динамічна лінива фаза) та директиви прямого впорядкування адрес у двійкових таблицях завантажувача операційної системи.

Нижче наведено зведений довідник контрактів, пріоритетів, бінарних секцій та діагностичних засобів.

## Стандартні специфікатори мови (C++11 — C++20)

| Специфікатор / Механізм | Стандарт | Призначення | Обмеження та правила |
|---|---|---|---|
| `constinit` | C++20 | Примусово вимагає ініціалізації змінної у статичній фазі (*Constant Initialization*). Забороняє відкладення конструювання на динамічну фазу рантайму. | Застосовується виключно до змінних зі статичною або потоковою (`thread_local`) тривалістю зберігання. Змінна не є константною (може змінюватися під час виконання). |
| `constexpr` | C++11 | Оголошує вираз або об'єкт як обчислюваний під час компіляції. Робить об'єкт незмінним (`const`). | Тип об'єкта повинен бути літеральним (*LiteralType*). Не дозволяє динамічного виділення пам'яті, що виходить за межі етапу компіляції. |
| `consteval` | C++20 | Оголошує функцію як негайну (*immediate function*). Будь-який виклик функції зобов'язаний обчислюватися виключно під час компіляції. | Не може викликатися у динамічному runtime-контексті напряму без константних аргументів. |
| Локальний `static` (Meyer's) | C++11 | Гарантує ініціалізацію локальної статичної змінної під час першого проходження потоку виконання через її оголошення. | Потокобезпека забезпечується автоматичними викликами рантайму (`__cxa_guard_acquire` / `__cxa_guard_release`). |

## Специфікатор C++20 constinit та константна фаза

Специфікатор `constinit` вирішує головну архітектурну суперечність системного програмування: як гарантувати надійне заповнення пам'яті глобального об'єкта компілятором у секції `.data` до старту будь-якого виконуваного коду, одночасно зберігши можливість вільно змінювати стан цього об'єкта під час подальшої роботи програми.

До появи стандарту C++20 єдиним інструментом гарантованої ініціалізації під час компіляції був специфікатор `constexpr`. Проте `constexpr` нерозривно пов'язував статичне створення з константністю типу (`const`), унеможливлюючи подальшу модифікацію полів об'єкта під час обробки запитів. Специфікатор `constinit` знімає це обмеження: він вимагає виконання константної ініціалізації на етапі збирання, але залишає сам об'єкт повністю мутабельним.

```cpp
#include <string_view>

struct EngineConfig {
    int worker_threads;
    double tick_rate_hz;
    bool is_running;

    // Конструктор зобов'язаний бути constexpr
    constexpr EngineConfig(int threads, double rate)
        : worker_threads(threads), tick_rate_hz(rate), is_running(false) {}
};

// Гарантовано константна ініціалізація, але змінний стан у рантаймі:
constinit EngineConfig g_engine_config(8, 60.0);

void start_engine() {
    // Зміна дозволена, оскільки constinit не накладає константності:
    g_engine_config.is_running = true;
}
```

Якщо ініціалізатор містить функцію або вираз, який компілятор не здатний розрахувати статично через виклики сторонніх неконстантних бібліотек або виділення пам'яті в купі, збирання негайно переривається з діагностичним повідомленням про помилку:

```text
error: variable 'g_bad_config' does not have a constant initializer
note: non-constexpr function 'get_system_cores()' cannot be used in a constant expression
```

Застосування `constinit` повністю ліквідує ризик SIOF для даного об'єкта. Компілятор записує готові біти структури безпосередньо у бінарний файл, уникаючи генерації викликів у секції `.init_array`.

## Компіляторні атрибути: GCC та Clang

Компілятори родини GCC та Clang взаємодіють із форматом виконуваних файлів ELF через низькорівневі механізми секцій компонувальника.

Коли компілятор генерує код для глобального C++ об'єкта, він створює спеціальну функцію-обгортку та поміщає покажчик на неї у секцію `.init_array`. За замовчуванням усі такі покажчики зливаються в один суцільний список у довільному порядку. Атрибут пріоритету дозволяє розробникові розбити цей список на впорядковані підгрупи.

### Атрибут init_priority для глобальних C++ об'єктів

Синтаксис застосування: `__attribute__((init_priority(priority)))` або стандартний атрибут формату C++11 `[[gnu::init_priority(priority)]]`.

Атрибут змушує компілятор згенерувати для даного об'єкта запис у спеціальній підсекції вигляду `.init_array.NNNNN`, де `NNNNN` — числове значення пріоритету, вирівняне провідними нулями до п'яти цифр (наприклад, `.init_array.00150` або `.init_array.00300`).

Під час компонування стандартний скрипт компонувальника GNU ld або LLVM lld застосовує директиву `SORT_BY_INIT_PRIORITY`, яка сортує ці підсекції строго за алфавітом. Це гарантує, що підсекція `.init_array.00150` буде розміщена в пам'яті раніше за `.init_array.00300`, а системний завантажувач процесу викличе їхні конструктори у точній числовій черговості.

```cpp
#include <iostream>

class MemoryManager {
public:
    MemoryManager() { std::cout << "[INIT 150] Менеджер пам'яті готовий\n"; }
};

class TaskScheduler {
public:
    TaskScheduler() { std::cout << "[INIT 300] Планувальник задач готовий\n"; }
};

// Менше число = вищий пріоритет (виконується раніше)
MemoryManager g_mem_mgr [[gnu::init_priority(150)]];
TaskScheduler g_sched [[gnu::init_priority(300)]];
```

*Діапазони числових пріоритетів:*
- `0` — `100`: Зарезервовано для системної реалізації C-рантайму та стандартної бібліотеки мови (наприклад, для внутрішніх буферів вводу-виводу). Використання цих значень у прикладному коді заборонено або генерує попередження компілятора.
- `101` — `65535`: Дозволено для використання у коді користувацьких бібліотек та прикладних систем. Об'єкти з меншими числовими значеннями (наприклад, `101`) гарантовано конструюються раніше за об'єкти з більшими номерами (наприклад, `5000`).
- Об'єкти без атрибута отримують стандартне розміщення у базовій секції `.init_array` і виконуються після завершення всіх пріоритетних ініціалізаторів.

### Атрибути constructor та destructor для функцій

Для функцій мов C та C++ компілятори GCC та Clang надають атрибути `constructor` та `destructor`. Вони дозволяють реєструвати процедурні точки входу, які виконуються системним завантажувачем до виклику функції `main()` та після завершення роботи процесу:

:::tabs
```c
#include <stdio.h>

/* Виконується до main() у порядку зростання пріоритетів (150 -> 200) */
void __attribute__((constructor(150))) init_hardware_bus(void) {
    printf("[C HW] Активація системної шини периферії\n");
}

/* Виконується після exit() у порядку спадання пріоритетів (200 -> 150) */
void __attribute__((destructor(150))) shutdown_hardware_bus(void) {
    printf("[C HW] Вимкнення системної шини периферії\n");
}
```
```cpp
#include <iostream>

/* Еквівалентний C++ синтаксис атрибутів GNU */
extern "C" {
    [[gnu::constructor(150)]] void init_hardware_bus_cpp() {
        std::cout << "[C++ HW] Активація системної шини периферії\n";
    }

    [[gnu::destructor(150)]] void shutdown_hardware_bus_cpp() {
        std::cout << "[C++ HW] Вимкнення системної шини периферії\n";
    }
}
```
:::

Ці атрибути особливо корисні у спільних динамічних бібліотеках (`.so`), оскільки вони автоматично спрацьовують під час завантаження бібліотеки в пам'ять через системний виклик `dlopen()` та під час вивантаження через `dlclose()`.

## Директиви компілятора Microsoft Visual C++ (MSVC)

У середовищі Microsoft Visual Studio та форматі файлів PE/COFF впорядкування ініціалізаторів організовано через сегмент пам'яті `.CRT`.

Компілятор розкладає покажчики на функції ініціалізації по спеціальних секціях з іменами від `.CRT$XCA` до `.CRT$XCZ`. Компонувальник MSVC склеює ці секції в єдиний масив, сортуючи їх строго за алфавітом символу після знака долара:

```cpp
// Директива управління секцією ініціалізації для поточної одиниці трансляції:
#pragma init_seg(compiler) // Секція .CRT$XCC (найраніший запуск, рівень компілятора)
#pragma init_seg(lib)      // Секція .CRT$XCL (рівень системних і сторонніх бібліотек)
#pragma init_seg(user)     // Секція .CRT$XCU (рівень користувача за замовчуванням)

// Можливість створення власної проміжної секції з довільним ім'ям:
#pragma init_seg(".CRT$XCM")
```

Послідовність виконання у таблиці `.CRT`:
1. `.CRT$XCA` — маркер початку таблиці C-ініціалізаторів.
2. `.CRT$XCC` — внутрішній код компілятора MSVC (`compiler`).
3. `.CRT$XCL` — код системних і сторонніх бібліотек (`lib`).
4. `.CRT$XCU` — стандартні конструктори глобальних об'єктів C++ користувача (`user`).
5. `.CRT$XCZ` — маркер кінця таблиці C++ ініціалізаторів.

Використання `#pragma init_seg(lib)` у файлі реалізації власної бібліотеки гарантує, що її глобальні сервіси сконструюються раніше за будь-які користувацькі класи, скомпільовані зі стандартним рівнем `user`.

## Стандартний клас std::ios_base::Init

Клас `std::ios_base::Init` інкапсулює реалізацію ідіоми Nifty Counter у стандартній бібліотеці для забезпечення безпечного доступу до потоків `std::cin`, `std::cout`, `std::cerr` та `std::clog`.

```cpp
#include <ios>

namespace std {
    class ios_base::Init {
    public:
        // Збільшує внутрішній лічильник посилань.
        // При переході 0 -> 1 виконує placement new для об'єктів потоків.
        Init();

        // Зменшує внутрішній лічильник посилань.
        // При переході 1 -> 0 скидає буфери (flush) та викликає деструктори потоків.
        ~Init();
    };
}
```

Кожна одиниця трансляції, яка підключає заголовок `<iostream>`, автоматично отримує статичний екземпляр `std::ios_base::Init`. Оскільки включення заголовка зазвичай стоїть на початку файлу, конструктор `Init` гарантовано виконується до створення користувацьких об'єктів у цьому модулі.

## Примітиви потокобезпечної відкладеної ініціалізації

Для забезпечення безпечного відкладеного створення ресурсів у багатопотокових системах заголовок `<mutex>` надає функцію `std::call_once` та тип `std::once_flag`:

```cpp
#include <mutex>
#include <memory>

class HardwareRegistry {
public:
    static HardwareRegistry& instance() {
        std::call_once(s_init_flag, []() {
            s_instance.reset(new HardwareRegistry());
        });
        return *s_instance;
    }

private:
    HardwareRegistry() = default;
    static inline std::unique_ptr<HardwareRegistry> s_instance;
    static inline std::once_flag s_init_flag;
};
```

Сигнатура функції:
```cpp
template<class Callable, class... Args>
void call_once(std::once_flag& flag, Callable&& f, Args&&... args);
```

*Семантика виконання:*
- Якщо кілька потоків одночасно викликають `std::call_once` з однаковим прапорцем `flag`, рівно один потік отримує право виконати передану функцію `f`, а решта потоків блокуються і пасивно чекають завершення ініціалізації.
- Пам'ять синхронізується з семантикою `acquire-release`: усі зміни даних, здійснені всередині функції `f`, гарантовано стають видимими для всіх інших потоків після їхнього виходу з `std::call_once`.
- Якщо виконання функції `f` переривається винятком, стан прапорця `flag` не фіксується як завершений, що дозволяє наступному потоку, який очікує, повторити спробу ініціалізації.

## Автоматизовані перевірки та діагностика

Компілятори та інструменти статичного аналізу коду дозволяють виявляти небезпечну динамічну ініціалізацію на етапі неперервної інтеграції (CI):

1. **Clang-Tidy `bugprone-dynamic-static-initializers`**: знаходить змінні зі статичною тривалістю зберігання, чия ініціалізація вимагає виконання нетривіального динамічного коду замість константної фази.
2. **Clang-Tidy `cert-err58-cpp`**: правило безпеки стандарту CERT C++, яке категорично забороняє викидання винятків під час конструювання або знищення глобальних об'єктів до входу в `main()`, оскільки такий виняток неможливо перехопити через блок `try-catch` у `main()`, що призводить до негайної аварійної зупинки програми через `std::terminate()`.
3. **Прапорець компіляції `-Wglobal-constructors` (Clang)**: генерує попередження для кожного глобального об'єкта, який вимагає реєстрації функції ініціалізації у секції `.init_array`, допомагаючи розробникам створювати системи з миттєвим детермінованим стартом без прихованих накладних витрат.
