# 📜 Історія появи Schwarz Counter у Cfront 2.0

Коли Б'ярн Страуструп (дан. *Bjarne Stroustrup*) на початку 1980-х років розробляв C++ у лабораторіях Bell Labs (AT&T), однією з ключових переваг нової мови над класичною Сі мала стати типобезпечна та розширювана бібліотека введення-виведення. Замість функцій сімейства `printf` та `scanf`, які покладалися на неперевірені форматуючі рядки й легко спричиняли пошкодження пам'яті через невідповідність типів аргументів, C++ запропонував оператори зсуву потоків `<<` та `>>` у бібліотеці `iostream`. Проте інженерна реалізація цієї ідеї майже одразу наштовхнулася на фундаментальну проблему архітектури компіляторів.

## Криза глобального потоку виведення

Для зручності розробників стандартні потоки виведення — `std::cout`, `std::cin` та `std::cerr` — проєктувалися як глобальні об'єкти. Програміст мав мати можливість підключити заголовок `<iostream>` і одразу викликати `std::cout << "Привіт";` у будь-якій частині коду, зокрема всередині конструкторів власних глобальних або статичних класів:

```cpp
#include <iostream>

struct DiagnosticProbe {
    DiagnosticProbe() {
        std::cout << "[INIT] Підсистему діагностики активовано.\n";
    }
};

DiagnosticProbe g_probe; // Глобальний об'єкт користувача
```

У ранніх версіях транслятора Cfront (який перекладав код C++ у чистий C) глобальні об'єкти ініціалізувалися простим викликом автоматично згенерованої функції ініціалізації перед викликом функції `main()`. Проте якщо програма складалася з кількох вихідних файлів (`.c` або `.cpp`), транслятор не мав жодної можливості керувати тим, у якому порядку компонувальник зв'яже ці модулі у фінальний виконуваний бінарник.

Якщо об'єктний файл користувача компонувався раніше, ніж об'єктний файл стандартної бібліотеки `iostream.o`, виникала катастрофа: конструктор `DiagnosticProbe` викликався до того, як конструктор `std::cout` налаштовував внутрішні буфери та покажчик `streambuf`. У результаті виклик оператора `<<` намагався писати через нульовий покажчик у неініціалізовану пам'ять, і програма завершувалася аварійно (Segmentation Fault) ще до того, як потік виконання доходив до першого рядка функції `main()`.

## Винахід Джеррі Шварца

Розв'язання цієї проблеми у 1989 році запропонував Джеррі Шварц (англ. *Jerry Schwarz*), співробітник Bell Labs, який очолював переробку бібліотеки потоків для релізу **Cfront 2.0**.

Шварц усвідомив: не можна покладатися на глобальний об'єкт `std::cout` як на звичайну змінну у файлі реалізації. Необхідно створити механізм, який гарантуватиме виконання коду ініціалізації потоків у кожній одиниці трансляції ще **до** того, як почнуть конструюватися будь-які глобальні змінні користувача в цьому модулі.

Ідея отримала назву **лічильник Шварца** (англ. *Schwarz Counter*), або в пізнішій літературі — **Nifty Counter** (від англ. *nifty* — витончений, кмітливий).

Шварц запропонував включити у відкритий заголовковий файл `<iostream>` визначення спеціального допоміжного класу та статичний екземпляр цього класу:

```cpp
// Концептуальний вигляд рішення Джеррі Шварца в iostream.h (1989)
class ios_base_init {
public:
    ios_base_init();
    ~ios_base_init();
private:
    static int init_count; // Глобальний лічильник посилань
};

// Кожна одиниця трансляції, яка підключає <iostream.h>,
// отримує власну внутрішню статичну змінну:
static ios_base_init __ios_init;
```

Механізм базувався на трьох суворих правилах трансляції:

1. **Порядок усередині одиниці трансляції.** Компілятор завжди ініціалізує глобальні та статичні змінні строго зверху вниз у порядку їхньої появи в тексті. Оскільки `#include <iostream>` майже завжди розташовується на самому початку файлу, змінна `__ios_init` гарантовано створюється раніше за будь-які глобальні об'єкти користувача в цьому `.cpp` файлі.
2. **Лічильник посилань під час запуску.** Конструктор `ios_base_init` атомарно або послідовно збільшує спільний лічильник `init_count`. Коли лічильник змінює значення з `0` на `1` (перша одиниця трансляції в програмі), виконується реальна ініціалізація внутрішніх буферів `std::cout`, `std::cin` та `std::cerr` через низькорівневе конструювання у заздалегідь виділеній сирій пам'яті. Для всіх наступних одиниць трансляції лічильник просто збільшується, пропускаючи важку ініціалізацію.
3. **Симетричне звільнення під час завершення.** Коли програма завершує роботу, деструктор `~ios_base_init` зменшує лічильник. Лише коли значення падає з `1` до `0` (остання одиниця трансляції завершує роботу), викликається явний деструктор потоків виведення і буфери скидаються на диск. Це повністю ліквідувало проблему передчасного руйнування потоків при виході.

## Значення для еволюції мови C++

Рішення Джеррі Шварца увійшло до першого міжнародного стандарту ISO/IEC 14882:1998 (C++98) у формі класу `std::ios_base::Init`, де воно залишається обов'язковою частиною стандарту й донині.

Винахід лічильника Шварца став першим в історії C++ канонічним шаблоном проєктування для керування життєвим циклом статичних ресурсів між незалежними одиницями трансляції. До появи стандарту C++11 (який увів потокобезпечні локальні статичні змінні Мейєрса) та C++20 (який дав `constinit`), ідіома Шварца була єдиним переносним способом безпечної організації міжмодульних бібліотек у мові C++.
