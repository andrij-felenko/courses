# 📜 Історія обчислень під час компіляції: від трюків із шаблонами до constexpr

Ідея перенести частину роботи з процесора кінцевого користувача на компілятор народилася разом із першими мовами програмування. Якщо значення виразу можна передбачити до запуску програми, витрачати на нього такти процесора, енергію акумулятора та пам'ять під час виконання видається марнотратством. Проте шлях до елегантного імперативного синтаксису, яким сьогодні володіє C++, пролягав через десятиліття випадкових відкриттів, синтаксичних мутацій та екстремального використання засобів, які ніколи не проектувалися для загальних обчислень.

### Ранні спроби: макроси препроцесора та константні вирази в C

У мові C від самого початку існувало базове [згортання сталих](topic:sf-lang/compiler-optimizations) (англ. *constant folding*): вирази на кшталт `3 * 1024` компілятор обчислював безпосередньо під час розбору синтаксису. Проте виразність таких конструкцій обмежувалася елементарною арифметикою. Розміри статичних масивів чи значення елементів переліків `enum` вимагали сталих, відомих компілятору (англ. *integral constant expressions*), але будь-яка спроба описати нетривіальний алгоритм неминуче впиралася в глухий кут.

Єдиним інструментом автоматизації був [препроцесор C](topic:sf-lang/preprocessor-macros) з його макросами `#define`. Програмісти будували складні каскади макросів, генеруючи кодові блоки або таблиці сталих значень. Але препроцесор не мав уявлення про типи даних, область видимості змінних чи семантику мови — він лише маніпулював неструктурованим текстом. Помилка в макросі призводила до незрозумілих повідомлень компілятора на зовсім інших рядках, а небезпека подвійного обчислення аргументів (`#define SQUARE(x) ((x) * (x))` із викликом `SQUARE(i++)`) стала класичним джерелом важковиправних багів.

### 1994 рік: випадкове відкриття Ервіна Унру

Справжній переворот стався випадково. На засіданні комітету зі стандартизації C++ (ISO WG21) у Сан-Хосе 1994 року німецький інженер Ервін Унру (Erwin Unruh) продемустрував дивовижний код. Він прагнув показати можливості системи шаблонів, щойно доданої до мови, але результат перевершив усі очікування.

Код Унру не містив виконуваної функції `main` і взагалі не міг скомпілюватися без помилок. Проте самі діагностичні повідомлення компілятора являли собою послідовність простих чисел:

```
// Концептуальний вигляд помилки компілятора в коді Унру:
error: cannot convert 'Prime<2>' to 'void*'
error: cannot convert 'Prime<3>' to 'void*'
error: cannot convert 'Prime<5>' to 'void*'
error: cannot convert 'Prime<7>' to 'void*'
```

Компілятор, інстанціюючи рекурсивні шаблони класів для пошуку дільників, фактично виконував обчислення під час аналізу типів. Спільнота раптом усвідомила: механізм зіставлення шаблонів C++ є повноцінною Тюрінг-повною мовою обчислень, що виконується всередині компілятора.

### Епоха шаблонного метапрограмування (TMP)

Наприкінці 1990-х та на початку 2000-х років почався розквіт шаблонного метапрограмування (англ. *Template Metaprogramming, TMP*). Інженери зрозуміли, що замість написання окремих скриптів на Python чи Perl для генерації коду можна змусити сам компілятор генерувати типи, розгортати цикли та оптимізувати структури даних.

Тодд Вельдхейзен (Todd Veldhuizen) створив бібліотеку Blitz++ для наукових обчислень, де техніка виразних шаблонів (англ. *expression templates*) усувала створення проміжних тимчасових масивів при матричних операціях. У 2001 році Андрій Александреску (Andrei Alexandrescu) опублікував фундаментальну працю «Modern C++ Design», показавши, як за допомогою списків типів (`typelists`) та шаблонних структур будувати гнучкі архітектури на етапі компіляції. Девід Вандевурд (David Vandevoorde) та Ніколай Джосуттіс (Nicolai Josuttis) систематизували ці знання у своїй книзі про шаблони C++.

Бібліотека Boost.MPL остаточно закріпила статус TMP як промислової технології. Але цей підхід мав колосальну ціну:

1. **Неприродний синтаксис.** Програмування перетворилося на чистий функційний діалект: замість звичайних змінних — статичні константи `enum { value = ... }` або `static const int value = ...`, замість циклів — глибока рекурсія шаблонів, замість умовних операторів — часткова спеціалізація класів.
2. **Катастрофічний час збірки.** Кожен крок рекурсії породжував новий екземпляр шаблонного класу в пам'яті компілятора, роздуваючи внутрішні таблиці символів до гігабайтів.
3. **Неможливість налагодження.** Помилка в глибині інстанціювання шаблону породжувала багатометрові полотна діагностичних повідомлень, де знайти справжню причину збою було майже неможливо.

Стало зрозуміло: розробники хочуть обчислювати речі на етапі компіляції, але вони хочуть писати звичайний код, а не викручувати систему типів навиворіт.

### Пропозиція Б'ярна Страуструпа та Габріеля Дос Рейса: народження `constexpr`

У середині 2000-х років творець мови C++ Б'ярн Страуструп (Bjarne Stroustrup) разом із Габріелем Дос Рейсом (Gabriel Dos Reis) запропонували вихід із глухого кута. Їхня спільна пропозиція для комітету WG21 під назвою «Generalized Constant Expressions» (документ N2235, 2007 рік) заклала основу нового підходу.

Головна теза була простою: мова програмування для етапу компіляції має бути тією самою мовою C++, якою пишуть звичайні функції, а не окремим дивним езотеричним діалектом. Якщо функція складається з детермінованих операцій над відомими даними, компілятор повинен мати право виконати її сам.

Так у стандарті **C++11** з'явилося нове ключове слово `constexpr`. Проте перший варіант був надзвичайно обережним і консервативним. Комітет побоювався перевантажити розробників компіляторів, тому на функції `constexpr` наклали жорсткі рамки:
- тіло функції могло містити рівно один оператор `return`;
- заборонялося оголошувати будь-які локальні змінні;
- заборонялися цикли (`for`, `while`) та розгалуження через `if` (дозволявся лише тернарний оператор `?:`);
- заборонялася будь-яка мутація стану.

Це все ще нагадувало чисте функційне програмування, де навіть простий факторіал доводилося записувати через рекурсію:

```cpp
constexpr int factorial(int n) {
    return (n <= 1) ? 1 : (n * factorial(n - 1));
}
```

Однак це вже був справжній C++: із нормальною перевіркою типів аргументів, стандартним синтаксисом виклику функцій та можливістю повторного використання тієї ж самої функції у звичайному рантайм-коді.

### C++14: зняття кайданів

Обмеження C++11 протрималися недовго. Інженери Девід Вандевурд та Річард Сміт (Richard Smith, головний архітектор фронтенду Clang) підготували пропозицію N3652 («Relaxing constraints on constexpr functions»), яка увійшла в стандарт **C++14**.

C++14 зняв практично всі штучні бар'єри:
- дозволено оголошувати та ініціалізувати локальні змінні;
- дозволено використовувати імперативні цикли (`for`, `while`, `do-while`);
- дозволено оператори розгалуження `if` та `switch`;
- дозволено змінювати локальний стан об'єктів під час обчислення (локальна мутація).

Тепер алгоритми на етапі компіляції виглядали абсолютно природно: факторіал став звичайним циклом, парсери рядків позбулися вигадливих рекурсивних викликів, а обчислювальна швидкість самих компіляторів зросла, оскільки пряма ітерація в інтерпретаторі AST вимагала значно менше ресурсів, ніж побудова дерева рекурсії.

### C++17: статичне розгалуження `if constexpr`

Хоча функції стали імперативними, взаємодія з шаблонами все ще вимагала старої магії SFINAE (Substitution Failure Is Not An Error) або `std::enable_if`, якщо треба було вибірково компілювати код залежно від властивостей типу.

Стандарт **C++17** вирішив цю проблему, запровадивши `if constexpr`. Це дозволило викидати неактивні гілки коду безпосередньо під час компіляції. Якщо умова `if constexpr` була хибною, компілятор повністю ігнорував тіло гілки для поточного набору шаблонних параметрів, навіть якщо в ньому викликалися методи, яких у цього типу взагалі не існувало. Метапрограмування вперше позбулося багатоповерхових шаблонних переходів.

Крім того, у C++17 лямбда-функції стали неявно `constexpr`, якщо їхнє тіло задовольняло вимоги константних виразів.

### C++20 та C++23: повна зрілість і злиття світів

Стандарт **C++20** перетворив обчислення на етапі компіляції на повноцінну підсистему мови. Було прийнято кілька революційних пропозицій:

1. **`consteval` (Immediate Functions, P1073R3):** функції, які *гарантовано* виконуються виключно на етапі компіляції. Виклик такої функції з динамічними аргументами тепер викликає жорстку помилку компіляції.
2. **`constinit` (P1143R2):** ключове слово для змінних зі статичною тривалістю життя, що гарантує їхню ініціалізацію під час компіляції, усуваючи катастрофічну проблему невизначеного порядку динамічної ініціалізації (англ. *static initialization order fiasco*).
3. **Динамічна пам'ять у константному виразі (P0784R7):** компілятор дозволив використовувати оператори `new` та `delete` всередині `constexpr`. Це відкрило шлях для використання стандартних контейнерів `std::vector` та `std::string` під час компіляції, за умови, що вся виділена пам'ять звільняється до завершення константного виразу (англ. *transient allocation*).
4. **Поліморфізм та віртуальні функції (P1064R0):** віртуальні методи отримали статус `constexpr`. Компілятор зміг динамічно резолвити таблиці віртуальних методів у своїй віртуальній машині.
5. **`std::is_constant_evaluated()` та `if consteval` (C++23):** можливість для автора бібліотеки чітко розрізняти контекст і пропонувати для компілятора простий алгоритм, а для рантайму — оптимізований апаратний варіант із SIMD-інструкціями.

### Погляд у майбутнє: статична рефлексія

Еволюція не зупинилася. Наступним фундаментальним кроком у розвитку мови є статична рефлексія (англ. *Static Reflection*, пропозиція P2996 для C++26). Якщо раніше `constexpr` обробляв лише призначені для користувача дані, то статична рефлексія дозволить коду на етапі компіляції аналізувати саму структуру програми: перелічувати поля класів, отримувати типи аргументів, генерувати функції серіалізації без жодних макросів чи сторонніх генераторів коду.

Те, що починалося в 1994 році як загадкова помилка компілятора в коді Ервіна Унру, за тридцять років перетворилося на одну з найдосконаліших систем статичних обчислень у сучасному програмуванні.
