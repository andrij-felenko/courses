# ⚙️ Генерація пошукових таблиць та валідація даних на етапі компіляції

У вбудованих системах, мережевих комутаторах, файлових системах та графічних рушіях пошукові таблиці (англ. *Lookup Tables, LUT*) є фундаментальним засобом оптимізації швидкодії. Замість того, щоб повторно виконувати дорогі математичні операції, розрахунки контрольних сум чи нелінійні перетворення для кожного байта вхідного потоку даних, програма звертається до попередньо згенерованого масиву значень за константний час `O(1)`.

Проте традиційно інженери стояли перед неприємним компромісом між двома недосконалими підходами:

1. **Динамічна ініціалізація під час запуску.** Програма виділяє масив в оперативній пам'яті RAM і при першому виклику запускає цикл заповнення таблиці. Це уповільнює старт пристрою, марно витрачає акумулятор, споживає дефіцитну пам'ять RAM і створює ризик [гонки даних](root:sys-plang-cpp/std-atomic) у багатопотоковому середовищі.
2. **Зовнішня генерація вихідних текстів.** Перед збіркою запускається допоміжний скрипт на Python або Perl, який генерує файл із сирими числовими масивами на кшталт `const uint32_t table[256] = { 0x00000000, ... };`. Цей підхід розриває монолітність збірки, змушує дублювати логіку двома різними мовами та вимагає ручної синхронізації файлів при кожній зміні алгоритму.

Сучасний C++ дозволяє повністю вирішити цю задачу засобами самої мови: згенерувати таблицю безпосередньо інтерпретатором компілятора під час трансляції, розмістити її як незмінний двійковий блок у секції `.rodata` Flash-пам'яті та статично підтвердити її коректність через `static_assert` ще до формування остаточного двійкового файлу прошивки.

### Математична основа: алгоритм контрольної суми CRC-32

Контрольна сума CRC-32 (циклічний надлишковий код, англ. *Cyclic Redundancy Check*) базується на діленні двійкового полінома у скінченному полі Галуа `GF(2)`. Для мережевих стандартів Ethernet (IEEE 802.3), форматів стиснення ZIP/GZIP та файлів PNG використовується канонічний зворотний поліном `0xEDB88320u`.

Побайтовий алгоритм обробки замінює побітовий зсув 8 бітів прямим вибірковим індексуванням таблиці на 256 елементів типу `uint32_t` (загальним розміром 1024 байти). Кожен елемент таблиці відповідає значенню контрольної суми для одного байта від `0` до `255`, зсунутого на 8 бітів із застосуванням операції зворотного зв'язку за модулем 2 (`XOR`).

Математично операція для кожного біта вхідного байта виглядає так: якщо молодший біт поточного проміжного значення дорівнює одиниці, значення зсувається праворуч на 1 розряд і комбінується операцією `XOR` із фіксованим поліномом; якщо нуль — виконується лише зсув. Повторення цієї процедури вісім разів для кожного з 256 можливих станів формує повністю детерміновану таблицю переходів.

#### Порівняння параметрів системних ресурсів

| Параметр ресурсу | Реалізація на чистому C | Реалізація на C++20 constexpr |
|---|---|---|
| Використання пам'яті RAM | 1024 байти у секції `.bss` + прапорець ініціалізації | **0 байтів** (уся таблиця знаходиться у Flash / `.rodata`) |
| Затримка старту (Boot Time) | 256 × 8 = 2048 ітерацій циклу під час першого виклику | **0 тактів процесора** (таблиця зашита в бінарний образ) |
| Потокобезпечність (Thread Safety) | Потребує м'ютексів або атомарних прапорців | **Абсолютна** (незмінні константні дані) |
| Перевірка цілісності алгоритму | Тільки в рантаймі через runtime `assert()` | **Під час збірки** за допомогою `static_assert` |

Застосування `std::array` у C++ замість сирих C-масивів має вирішальне значення: `std::array` є повноцінним типом значення (value type), його можна повертати з функцій за значенням, копіювати, використовувати в константних виразах та передавати в шаблони без небезпеки неявного приведення до вказівника (array-to-pointer decay).

### Детальний розбір асемблерного виходу

Погляньмо на реальний машинний код, згенерований компілятором GCC / Clang з оптимізацією `-O2` для архітектури x86-64 у двох випадках:

#### 1. Обчислення хешу від статичного літерала

Якщо ми запитуємо контрольну суму константного заголовка пакета:

```cpp
uint32_t get_static_packet_hash() {
    return crc32::calculate_compile_time("PACKET_HEADER_TYPE_A");
}
```

Асемблерний лістинг:

```nasm
get_static_packet_hash():
    mov     eax, 2816997946        ; Завантаження готового результату 0xA7E7C63A
    ret
```

Компілятор повністю розгорнув і виконав функцію `calculate_compile_time` всередині свого інтерпретатора. У машинному коді відсутні звернення до таблиці, цикли, зсуви та інструкції XOR — залишилася лише одна команда запису готового 32-бітного числа в регістр результату `EAX`.

### Пастки налагодження та ліміти інтерпретатора

1. **Ненавмисний запуск у рантаймі.**
   Якщо результат виклику `constexpr`-функції присвоюється звичайній локальній змінній (`uint32_t hash = crc32::calculate("str");`), оптимізатор за низьких рівнів оптимізації (`-O0`) може згенерувати звичайний динамічний виклик. Щоб примусово вимагати виконання на етапі компіляції, завжди використовуйте специфікатор `constexpr` для змінної або викликайте функцію з модифікатором `consteval`.

2. **Ліміти кількості кроків інтерпретатора.**
   Для генерації великих таблиць (наприклад, тригонометричних таблиць на 65536 записів або фільтрів зображень) інтерпретатор компілятора може перевищити встановлений ліміт кроків оцінки.
   Щоб розширити ліміт операцій:
   - Для **GCC**: прапорець `-fconstexpr-ops-limit=100000000`
   - Для **Clang**: прапорець `-fconstexpr-steps=10000000`

3. **Діагностика помилок усередині CTFE.**
   Оскільки стандартні функції вводу/виводу (`std::cout`, `printf`) заборонені в константних виразах, для налагодження використовують умовне викидання помилок через `static_assert` або штучне провокування ділення на нуль при порушенні проміжних інваріантів алгоритму.

4. **Гібридні оптимізації: LUT проти апаратних інструкцій SIMD.**
   У сучасних процесорах x86-64 існує апаратна інструкція `PCLMULQDQ` (Carry-less Multiplication), яка дозволяє розраховувати CRC без таблиць ще швидше. Використовуючи конструкцію `if consteval` (C++23) або `std::is_constant_evaluated()` (C++20), ви можете поєднати обидва світи: під час компіляції використовувати простий та переносний алгоритм на основі таблиці LUT, а в динамічному рантаймі перемикатися на векторизований апаратний асемблер.
