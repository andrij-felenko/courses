# 📋 Довідник прапорців, утиліт та змінних середовища PGO

Цей довідник містить повну номенклатуру прапорців компіляторів, утиліт індексації, параметрів апаратного профілювання та змінних середовища для налаштування оптимізації за профілем у сучасних екосистемах (Clang/LLVM, GCC, Rust, MSVC, AutoFDO та BOLT). Окрім синтаксису викликів, тут описано внутрішні механізми кожного перемикача, правила злиття профілів, діагностику розбіжностей та конфігурацію автоматизованих конвеєрів CI/CD.

---

### 1. Екосистема Clang / LLVM

У компіляторній інфраструктурі LLVM підтримується два фундаментально різних рівні інструментації коду: на рівні абстрактного синтаксичного дерева (Frontend PGO / AST-level PGO) та на рівні канонічного проміжного представлення (IR-level PGO / LLVM-PGO).

#### Внутрішня відмінність між Frontend PGO та IR-level PGO

- **Frontend PGO (`-fprofile-instr-generate`)**: вставляє лічильники на ранньому етапі трансляції у фронтенді Clang до застосування будь-яких компіляторних спрощень. Це створює точний зв'язок із номерами вихідних рядків коду для вимірювання покриття тестами (Source-based Code Coverage), проте збільшує розмір бінарника та уповільнює виконання тренувального бінарника через надмірну кількість лічильників.
- **IR-level PGO (`-fprofile-generate`)**: компілятор спочатку запускає базові фази оптимізації проміжного коду (Early Inlining, SimplifyCFG, InstCombine, Dead Code Elimination), спрощує граф CFG і лише після цього розміщує лічильники за алгоритмом мінімального остовного дерева (Knuth MST). Завдяки цьому кількість точок інструментації скорочується на 35–50%, що знижує накладні витрати тренувального прогону та підвищує точність оптимізатора. Саме IR-level PGO є промисловим стандартом для високопродуктивного C/C++ та Rust коду.

#### Контекстно-чутливий профіль (CSSPGO)

У стандартному PGO виникає проблема втрати контексту: коли функція вбудовується (інлайниться) у кілька різних місць програми, компілятор бачить лише сумарну статистику для початкового тіла функції, але не знає, як саме змінюється поведінка її внутрішніх гілок залежно від місця виклику. Технологія **Context-Sensitive PGO (CSSPGO)** розв'язує цю проблему через двопрохідну схему:
1. Спочатку збирається базовий PGO-профіль і застосовується міжмодульний інлайнінг (ThinLTO).
2. Потім згенерований біткод інструментується повторно (`-fcs-profile-generate`), фіксуючи лічильники вже для кожного окремого вбудованого контексту.
3. Фінальна збірка (`-fcs-profile-use`) отримує максимальну точність передбачення розгалужень у глибоко інлайненому коді.

#### Прапорці виклику `clang` та `clang++`

| Прапорець | Призначення та внутрішній механізм |
| :--- | :--- |
| `-fprofile-instr-generate[=<файл>]` | Вмикає інструментацію на рівні AST фронтенду. Якщо шлях не вказано, рантайм скидає профіль у файл `default.profraw`. |
| `-fprofile-instr-use=<шлях.profdata>` | Застосовує індексований профіль фронтенду для фінальної кодогенерації. |
| `-fprofile-generate[=<каталог>]` | Активує високопродуктивну інструментацію на рівні LLVM IR. Рекомендовано для серверних застосунків та баз даних. |
| `-fprofile-use=<шлях.profdata>` | Завантажує індексований IR-профіль для застосування оптимізацій. |
| `-fcs-profile-generate[=<каталог>]` | Context-Sensitive PGO (CSSPGO): виконує другий прохід інструментації над уже скомпільованим PGO+ThinLTO кодом для збору профілів з урахуванням глибокого контексту інлайнених функцій. |
| `-fcs-profile-use=<шлях.profdata>` | Застосовує додатковий контекстно-чутливий профіль для усунення помилок інлайнінгу другого порядку. |
| `-fprofile-sample-use=<шлях.afdo>` | Завантажує профіль, зібраний на основі семплювання апаратних лічильників (AutoFDO / SampleFDO). |
| `-fprofile-sample-accurate` | Повідомляє оптимізатору, що вибірковий профіль є вичерпно повним; функції без зафіксованих викликів розглядаються як повністю холодні. |
| `-fbasic-block-sections=labels` | Генерує окремі асемблерні мітки для кожного базового блоку в секціях ELF, що необхідно для роботи пост-лінкерних оптимізаторів Propeller та BOLT. |
| `-fsplit-machine-functions` | Вмикає автоматичне розділення функцій на гарячі та холодні фрагменти на рівні бекенду LLVM. |

#### Діагностика узгодженості та дрейфу профілю

Під час активної розробки вихідний код часто змінюється швидше, ніж оновлюється файл профілю. Компілятор LLVM обчислює 64-бітний контрольний геш для графу CFG кожної функції. Якщо геш у профілі не збігається з поточною структурою функції, компілятор відкидає застарілі дані та повертається до статичних евристик. Для суворого контролю якості в конвеєрах CI/CD використовуються діагностичні прапорці:

| Прапорець | Тип події та реакція |
| :--- | :--- |
| `-Wprofile-instr-out-of-date` | Генерує попередження, якщо контрольна сума функції у вихідному коді відрізняється від збереженої у файлі `.profdata`. |
| `-Wprofile-instr-unprofiled` | Попереджає про появу нових функцій, інформація про які повністю відсутня у профілі. |
| `-Wprofile-instr-missing` | Сигналізує про те, що для всього вихідного файлу не знайдено відповідного профілю. |
| `-Werror=profile-instr-out-of-date` | Перетворює попередження про розбіжність профілю на фатальну помилку компілятора, блокуючи створення неякісного релізного бінарника. |

#### Утиліта обробки профілів `llvm-profdata`

Службова утиліта `llvm-profdata` виконує перетворення неструктурованих сирих файлів `.profraw` у бінарне деревоподібне представлення `.profdata`, яке оптимізатор здатний читати з постійною часовою складністю `O(1)`.

##### 1. Об'єднання та зважування (`merge`)
```bash
# Базове злиття кількох файлів сирих профілів в єдиний індексований файл
llvm-profdata merge -output=code.profdata input1.profraw input2.profraw

# Злиття з ваговими коефіцієнтами для комбінування денного та нічного навантаження
llvm-profdata merge -weighted-input=8,day_read.profdata \
                    -weighted-input=2,night_write.profdata \
                    -output=production_blend.profdata

# Експорт бінарного профілю у текстовий вигляд для ручного аналізу
llvm-profdata merge -text -output=profile.txt code.profdata
```

##### 2. Статистичний аналіз та інспекція (`show`)
```bash
# Зведені відомості: загальна кількість функцій, максимальні лічильники та контрольні суми
llvm-profdata show code.profdata

# Детальний вивід кількості проходжень для кожної функції та кожного ребра CFG
llvm-profdata show --all-functions --counts code.profdata

# Вивід списку 20 найбільш навантажених функцій (hot functions)
llvm-profdata show --topn=20 code.profdata
```

##### 3. Оцінка дрейфу та кореляції (`overlap`)
```bash
# Розрахунок коефіцієнта збігу профілів між двома різними релізами (від 0.0 до 1.0)
llvm-profdata overlap profile_v1.profdata profile_v2.profdata
```

### 2. Екосистема GNU Compiler Collection (GCC)

У компіляторі GCC оптимізація за профілем спирається на інфраструктуру `gcov`. Лічильники переходів записуються під час трансляції у службові файли `.gcno` (Graph Node Coverage), а рантайм-статистика виконання формується у файлах `.gcda` (Graph Counter Data).

#### Прапорці виклику `gcc` та `g++`

| Прапорець GCC | Опис та механізм дії |
| :--- | :--- |
| `-fprofile-generate[=<каталог>]` | Інструментує програму лічильниками ребер та профілюванням значень. За замовчуванням файли `.gcda` записуються в робочий каталог збірки. |
| `-fprofile-use[=<каталог>]` | Активує PGO-оптимізації на базі наявних файлів `.gcda`. Автоматично вмикає агресивний інлайнінг, розділення функцій та перевпорядкування блоків. |
| `-fprofile-dir=<шлях>` | Встановлює базовий каталог для пошуку та збереження файлів профілю під час виконання інструментованого бінарника. |
| `-fprofile-values` | Вмикає спеціалізовані лічильники значень (цільові адреси непрямих переходів, дільники в арифметичних операціях ділення, розміри буферів для `memcpy`/`memset`). |
| `-fprofile-correction` | Дозволяє GCC автоматично коригувати розбіжності в лічильниках багатопотокових програм, що виникають через відсутність апаратних атомарних операцій при паралельному записі. |
| `-fprofile-reorder-functions` | Вмикає групування гарячих функцій у виділену секцію `.text.hot` на основі частоти взаємних викликів. |
| `-fauto-profile[=<файл>]` | Вмикає режим AutoFDO на основі профілю семплювання, перетвореного у формат GCC утилітою `create_gcov`. |
| `-Wcoverage-mismatch` | Попереджає про невідповідність структури файлів вихідного коду та наявних файлів лічильників `.gcda`. |

#### Службові утиліти `gcov-dump` та `gcov-tool`

GCC надає набір інструментів для маніпулювання файлами лічильників `.gcda`:
- `gcov-dump file.gcda` — здійснює повнотекстовий дамп вмісту двійкового файлу лічильників (частоти переходів, значення та гістограми).
- `gcov-tool merge dir1 dir2 -o merged_dir` — виконує пряме бінарне злиття наборів файлів `.gcda` з двох різних тестових запусків із можливістю масштабування ваг.

### 3. Екосистема Rust (`rustc` та `cargo-pgo`)

Мова Rust транслює код через LLVM IR, що забезпечує повну сумісність із профілювальними рантаймами та форматами LLVM.

#### Покроковий конвеєр через прапорці `rustc`
```bash
# Крок 1. Збірка інструментованого релізного бінарника
RUSTFLAGS="-C profile-generate=/tmp/pgo-data" cargo build --release

# Крок 2. Тренувальний прогін під типовим робочим навантаженням
./target/release/server_app --benchmark

# Крок 3. Індексація зібраних профілів через llvm-profdata
llvm-profdata merge -output=/tmp/pgo-data/merged.profdata /tmp/pgo-data

# Крок 4. Оптимізована збірка з використанням профілю та діагностикою
RUSTFLAGS="-C profile-use=/tmp/pgo-data/merged.profdata -C llvm-args=-pgo-warn-missing-function" cargo build --release
```

#### Використання плагіна автоматизації `cargo-pgo`
```bash
# Встановлення офіційного помічника
cargo install cargo-pgo

# Автоматичне виконання повного ланцюга
cargo pgo build
cargo pgo run -- --config production.toml
cargo pgo optimize
```

### 4. Microsoft Visual C++ (MSVC)

MSVC реалізує трифазну оптимізацію за профілем у тісній зв'язці між компілятором `cl.exe`, лінкером `link.exe` та менеджером бази даних профілю `pgomgr.exe`.

#### Фази конвеєра MSVC

| Етап | Команди виклику | Механізм |
| :--- | :--- | :--- |
| 1. Інструментація | `cl /O2 /GL /c main.cpp`<br>`link /LTCG:PGINSTRUMENT /PGD:app.pgd main.obj` | Прапорець `/GL` створює проміжне представлення, а `/LTCG:PGINSTRUMENT` збирає інструментований виконуваний файл і створює початковий файл бази даних `app.pgd`. |
| 2. Тренувальний запуск | `app.exe` | Під час роботи створюються один або кілька файлів лічильників з розширенням `app!1.pgc`, `app!2.pgc`. |
| 3. Злиття лічильників | `pgomgr /merge app!1.pgc app.pgd` | Утиліта `pgomgr` імпортує тимчасові лічильники `.pgc` у головну базу даних `.pgd`. |
| 4. Фінальна кодогенерація | `link /LTCG:PGOPTIMIZE /PGD:app.pgd main.obj` | Лінкер зчитує `.pgd` і генерує фінальний бінарник із перевпорядкованими базовими блоками та девіртуалізованими викликами. |

### 5. Sample-based PGO (AutoFDO) та Linux `perf`

Sample-based PGO дозволяє отримувати профілі безпосередньо з робочих серверів під реальним трафіком без інструментації коду та без уповільнення обробки запитів.

#### Механізм апаратного буфера LBR (Last Branch Record)

Сучасні мікропроцесори Intel та AMD містять апаратний кільцевий буфер LBR, який у режимі реального часу апаратно фіксує адреси джерела та призначення для останніх 16–32 виконаних переходів (Taken Branches). Системний профілювальник Linux `perf` налаштовується на зчитування стану буфера LBR з фіксованою частотою семплювання (наприклад, одне переривання на кожен 1 000 003 виконаний перехід).

```bash
# Крок 1. Компіляція з налагоджувальними мітками (без зміни коду програми)
clang++ -O3 -gline-tables-only -fdebug-info-for-profiling main.cpp -o app_server

# Крок 2. Збір траси переходів через perf LBR на бойовому сервері (тривалість 60 с)
perf record -b -e br_inst_retired.near_taken:pp -c 1000003 -o perf.data -- ./app_server

# Крок 3. Перетворення траси апаратних адрес у формат вихідних рядків LLVM
create_llvm_prof --binary=app_server --profile=perf.data --out=app.afdo

# Крок 4. Компіляція релізу з використанням вибіркового профілю
clang++ -O3 -fprofile-sample-use=app.afdo main.cpp -o app_server_opt
```

### 6. LLVM BOLT (Binary Optimization and Layout Tool)

LLVM BOLT — це пост-лінкерний оптимізатор, який перетворює готовий слінкований ELF-бінарник на основі профілю переходів LBR.

#### Конвеєр оптимізації через BOLT
```bash
# Крок 1. Збірка програми з обов'язковим збереженням таблиць релокацій
clang++ -O3 -flto=thin -Wl,-q -Wl,--emit-relocs main.cpp -o app_bin

# Крок 2. Збір апаратного LBR-профілю під навантаженням
perf record -e cycles:u -j any,u -o perf.data -- ./app_bin

# Крок 3. Перетворення бінарної траси perf у текстовий профіль переходів BOLT
perf2bolt -p perf.data -o app.fdata app_bin

# Крок 4. Запуск бінарної трансформації коду
llvm-bolt app_bin -o app_bin.bolt \
          -data=app.fdata \
          -reorder-blocks=ext-tsp \
          -reorder-functions=hfsort+ \
          -split-functions \
          -split-all-cold \
          -dyno-stats
```

#### Опис параметрів `llvm-bolt`

- `-reorder-blocks=ext-tsp`: алгоритм впорядкування базових блоків на основі розширеної евристики комівояжера (Extended TSP). Максимізує кількість послідовних переходів (fall-through) і мінімізує перетини меж 64-байтних ліній кешу L1i.
- `-reorder-functions=hfsort+`: кластеризує та впорядковує тіла функцій у пам'яті так, щоб функції, які часто викликають одна одну, знаходилися на сусідніх сторінках пам'яті (мінімізація iTLB misses).
- `-split-functions` / `-split-all-cold`: виносить холодні базові блоки (обробники рідкісних винятків, логування) у спеціальну відокремлену секцію бінарника.
- `-dyno-stats`: генерує детальний звіт про динамічну кількість усунених переходів та скорочення холостих тактів конвеєра.

### 7. Змінні середовища рантайму

| Змінна середовища | Шаблони та призначення |
| :--- | :--- |
| `LLVM_PROFILE_FILE` | Задає шаблон імені вихідного файлу `.profraw` під час запуску інструментованого Clang/LLVM бінарника.<br>• `%p` — ідентифікатор поточного процесу (PID).<br>• `%h` — мережеве ім'я комп'ютера (hostname).<br>• `%m` — 64-бітний унікальний геш бінарного модуля (запобігає перезапису профілів різних програм).<br>• `%t` — системний таймстемп у наносекундах.<br>• `%c` — атомарний лічильник конфліктів у пам'яті.<br>*Приклад виробничого шаблону:* `LLVM_PROFILE_FILE="/var/log/profiles/app-%m-%p.profraw"` |
| `GCOV_PREFIX` | Визначає кореневий каталог для скидання файлів лічильників `.gcda` у бінарниках GCC. Дозволяє відокремити збереження профілів від вихідного каталогу збірки проєкту. |
| `GCOV_PREFIX_STRIP` | Числове значення, що вказує компілятору GCC, скільки початкових рівнів каталогів потрібно відкинути від абсолютного шляху вихідного файлу при формуванні структури підкаталогів у `GCOV_PREFIX`. |
