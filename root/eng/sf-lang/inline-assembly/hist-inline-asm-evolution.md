# 📜 Від базового рядка до контракту оптимізатора: еволюція вбудованого асемблера

Історія вбудованого асемблера — це історія запеклої боротьби між двома світоглядами: бажанням системного програміста повністю контролювати кожен такт процесора та прагненням компілятора перевпорядковувати й видаляти команди задля максимальної швидкодії.

Коли Денніс Рітчі (Dennis Ritchie) на початку 1970-х років розробляв мову C для комп'ютера PDP-11 в Bell Labs, мова позиціонувалася як «портативний асемблер». Компілятор C не мав складних оптимізацій: він транслював кожен вираз майже один в один у послідовність машинних інструкцій. Потреба звертатися до спеціальних регістрів процесора (наприклад, увімкнення переривань, керування диспетчером пам'яті MMU чи зчитування статусних регістрів) вирішувалася найпримітивнішим способом — базовим оператором `asm("...")`.

У первісній моделі компілятор сприймав рядок всередині `asm` як звичайний текст для конвеєра асемблера `as`. Компілятор просто копіював символи у вихідний асемблерний файл без жодного синтаксичного чи семантичного аналізу. У світі без оптимізацій це працювало: змінні жили у фіксованих комірках на стеку або у глобальній пам'яті, а програміст вручну писав `mov _x, r0` та `add _y, r0`.

:::tabs
```c
/* Примітивний базовий асемблер раннього C (PDP-11 / V7 Unix) */
void enable_interrupts(void) {
    __asm__("spl 0"); /* встановити рівень пріоритету процесора */
}
```
```cpp
/* Еквівалент на C++ */
void enable_interrupts() noexcept {
    asm("spl 0");
}
```
:::

## Криза оптимізувальних компіляторів

Наприкінці 1980-х років парадигма компіляції зазнала тектонічного зсуву. З'явилися роботи Френсіс Аллен (Frances Allen) та Грегорі Чайтіна (Gregory Chaitin) щодо глобального аналізу потоків даних, проміжного представлення у формі SSA (Static Single Assignment) та розподілу регістрів через розфарбовування графів інтерференції.

Компілятори перетворилися з простих трансляторів на агресивні математичні оптимізатори. Змінна в мові C більше не мала сталої адреси в пам'яті: вона могла мігрувати між п'ятьма різними регістрами, видалятися як мертвий код (Dead Code Elimination) або взагалі обчислюватися заздалегідь на етапі компіляції (Constant Folding).

У цьому новому світі базовий `asm("...")` спричинив катастрофу:
1. **Сліпота оптимізатора:** компілятор не знав, які регістри використовує інструкція всередині рядка. Якщо програміст писав `asm("mov $1, %eax")`, а компілятор у цей самий момент тримав у регістрі `%eax` важливу змінну циклу, процесор затирав змінну без жодного попередження.
2. **Невидимість залежностей:** оптимізатор вважав, що рядок асемблера не читає і не змінює змінні C. Згідно з [правилом «ніби»](topic:sf-lang/as-if-rule), компілятор мав право винести «непотрібний» асемблерний код за межі циклу або повністю видалити його.
3. **Неефективність обміну даними:** щоб передати значення змінної в асемблерний блок, доводилося записувати її в глобальну пам'ять, виконувати команду і знову зчитувати назад у C-змінну, що зводило нанівець усю швидкодію.

Стало очевидно: вбудований асемблер не може залишатися неконтрольованим чорним ящиком. Необхідно було укласти формальний договір (контракт) між програмістом та розподілювачем регістрів компілятора.

## Народження Extended Asm у проєкті GCC

Рішення запропонували Річард Столлман (Richard Stallman) та інженери компанії Cygnus Support (зокрема Майкл Тіманн та Ян Ленс Тейлор) під час розробки GNU Compiler Collection (GCC) версій 1.x та 2.x на зламі 1980-х і 1990-х років.

Вони створили синтаксис розширеного асемблера (**Extended Asm**), який базувався на декларативній системі обмежень (constraints):

:::tabs
```c
/* Контракт Extended Asm у GCC 2.0 (1992 рік) */
int add_extended(int a, int b) {
    int result;
    __asm__ __volatile__ (
        "addl %2, %0"
        : "=r" (result)        /* вихідний операнд */
        : "0" (a), "r" (b)     /* вхідні операнди */
        : "cc"                 /* зіпсовані прапорці */
    );
    return result;
}
```
```cpp
/* Еквівалент на C++ */
int add_extended(int a, int b) noexcept {
    int result = 0;
    asm volatile (
        "addl %2, %0"
        : "=r" (result)
        : "0" (a), "r" (b)
        : "cc"
    );
    return result;
}
```
:::

Замість жорсткого закріплення конкретних фізичних регістрів програміст декларував *роль* операндів:
- символ `"r"` означав: «компіляторе, сам обери будь-який вільний регістр загального призначення»;
- символ `"="` гарантував: «цей операнд буде перезаписано»;
- список **clobbers** попереджав генератор коду: «ці апаратні ресурси будуть модифіковані, збережи їхній вміст заздалегідь».

Ця система була революційною: вона дозволила безшовно інтегрувати непрозорі інструкції в оптимізаційний конвеєр компілятора. Розподілювач регістрів сприймав блок асемблера як вузол графа залежностей і підставляв обрані апаратні регістри безпосередньо в шаблон.

## Драматичний розкол: шлях Microsoft Visual C++

Поки світ Unix стандартизував синтаксис GCC, компанія Microsoft пішла принципово іншим шляхом у компіляторі Visual C++ (MSVC) для платформи x86.

Microsoft представила блоковий синтаксис `__asm { ... }` з нотацією Intel (destination first):

:::tabs
```c
/* Модель MSVC для 32-розрядної архітектури x86 */
int add_msvc(int a, int b) {
    int res;
    __asm {
        mov eax, a
        add eax, b
        mov res, eax
    }
    return res;
}
```
```cpp
/* Еквівалент MSVC у C++ */
int add_msvc(int a, int b) noexcept {
    int res = 0;
    __asm {
        mov eax, a
        add eax, b
        mov res, eax
    }
    return res;
}
```
:::

Синтаксис MSVC здавався розробникам набагато простішим і читабельнішим за складний механізм двокрапок та лапок у GCC. Проте з точки зору архітектури компілятора це була міна сповільненої дії:
- У MSVC `__asm` не мав секції операндів і clobber-списків.
- Щоб запобігти руйнуванню даних, компілятор MSVC був змушений застосовувати найгіршу песимістичну стратегію: перед кожним блоком `__asm` скидати (spill) абсолютно всі кешовані змінні з регістрів у стек, а після завершення блоку — зчитувати їх заново.
- Оптимізатор повністю відключав глобальний розподіл регістрів для всієї функції, яка містила хоча б один рядок `__asm`.

Коли на початку 2000-х років компанія AMD анонсувала 64-розрядну архітектуру AMD64 (x86-64), команда розробників бекенду MSVC ухвалила безпрецедентне радикальне рішення: **повністю видалити підтримку `__asm` з 64-розрядного компілятора Visual C++**.

Головний архітектор оптимізатора MSVC пояснив це тим, що підтримка непрозорого `__asm` унеможливлює роботу нового генератора коду з SSA-формою та швидким глобальним планувальником інструкцій на 16 регістрах. Microsoft поставила розробників перед вибором:
1. Писати окремі файли на чистому асемблері й компілювати їх через MASM (`ml64.exe`).
2. Використовувати **вбудовані функції компілятора (intrinsics)**, такі як `__readcr3()`, `_InterlockedIncrement()` чи `__rdtsc()`.

У спільноті розробників Windows це викликало величезний резонанс, проте це рішення підштовхнуло індустрію до масового впровадження стандартизованих intrinsic-функцій.

## Тріумф GCC-моделі та інтеграція в LLVM/Clang

На противагу Microsoft, проєкт LLVM та фронтенд Clang під керівництвом Кріса Латтнера (Chris Lattner), що стартував у 2000-х роках, реалізували повну сумісність із синтаксисом Extended Asm від GCC.

В інфраструктурі LLVM блок вбудованого асемблера моделюється як спеціальний вузол `llvm::InlineAsm`, який на рівні проміжного представлення (LLVM IR) має точні типи параметрів, атрибути побічних ефектів (`sideeffect`, що відповідає `volatile`) та обмеження для бекенда. Це дозволило LLVM підтримувати єдиний механізм генерації коду для сотень різних процесорних архітектур — від крихітних мікроконтролерів AVR та ARM Cortex-M до суперкомп'ютерних систем RISC-V та POWER.

Сьогодні синтаксис GCC Extended Asm є де-факто загальновизнаним промисловим стандартом системного програмування на мовах C, C++ та Rust, забезпечуючи точний баланс між апаратним контролем та оптимізаційною потужністю компіляторів.
