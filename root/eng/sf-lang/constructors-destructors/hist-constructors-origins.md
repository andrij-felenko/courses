# 📜 Від Simula-67 до C with Classes: як ініціалізація та очищення стали частиною мови

Наприкінці 1970-х років у комп'ютерній індустрії панувала криза надійності системного програмного забезпечення. Операційні системи, драйвери периферії та телекомунікаційні комутатори писалися переважно мовою C або асемблером. У цій моделі пам'ять процесу розглядалася як сукупність безформних послідовностей байтів: функція `malloc()` виділяла блок запитуваного розміру, повертаючи покажчик `void*`, у якому лежало випадкове «сміття» попередніх операцій. Ініціалізація полів структури покладалася виключно на пам'ять та дисципліну програміста.

Якщо розробник забував викликати спеціальну функцію ініціалізації на зразок `init_buffer(&buf)` або помилково звертався до полів до цього виклику, програма читала невизначені значення, розіменовувала «дикі» покажчики й аварійно завершувала роботу. Ще більшою катастрофою було звільнення: будь-яке дострокове повернення з функції через код помилки оминало виклик `cleanup_buffer(&buf)`, породжуючи невидимі витоки пам'яті, незакриті дескриптори файлів та заблоковані апаратні переривання.

## Спадщина Simula-67 та ідея активного типу

Коріння концепції конструктора сягає 1967 року, коли норвезькі вчені Оле-Йоган Дал (норв. *Ole-Johan Dahl*) та Крістен Нюгор (норв. *Kristen Nygaard*) у Норвезькому обчислювальному центрі створили мову Simula-67. Розробляючи інструмент для моделювання поведінки складних систем — черг у портах, руху транспорту та ядерних реакторів, — вони запропонували об'єднати дані та операції над ними в єдину сутність: `class`.

У Simula-67 клас по суті був співпрограмою (англ. *coroutine*). Тіло самого класу слугувало кодом його ініціалізації:

```simula
Class Point(x, y); Real x, y;
Begin
    ! Тіло класу виконується автоматично при виклику new Point(1.0, 2.0);
    If x < 0.0 Then x := 0.0;
    If y < 0.0 Then y := 0.0;
End;
```

Створення екземпляра через оператор `new` виділяло пам'ять і негайно передавало керування тілу класу, яке встановлювало коректний початковий стан. Проте в Simula-67 не було концепції деструктора. Мова покладалася на автоматичний збирач сміття (англ. *garbage collector*), який сканував пам'ять у фоновому режимі й повертав недосяжні об'єкти системі.

Цей підхід чудово працював для академічних задач моделювання, але виявився абсолютно непридатним для систем реального часу. Збирач сміття породжував непередбачувані затримки виконання (паузи *stop-the-world*), споживав значні ресурси процесора і, головне, ніяк не вирішував проблему керування зовнішніми системними ресурсами — сокетами, блокуваннями шини та дескрипторами вводу-виводу, які необхідно повертати негайно в точний момент завершення роботи.

## Дослідження Б'ярне Страуструпа в Bell Labs (1979–1980)

У 1979 році данський дослідник Б'ярне Страуструп (дан. *Bjarne Stroustrup*) прийшов на роботу в дослідницький центр Bell Laboratories (Нью-Джерсі, США). Його завданням було моделювання розподілених обчислювальних систем та аналіз поведінки ядра операційної системи Unix на мультипроцесорних машинах.

Під час написання докторської дисертації в Кембриджі Страуструп активно використовував Simula-67 і високо цінував її здатність структурувати код за допомогою класів. Проте для моделювання комунікаційного обладнання Simula виявилася занадто повільною, а мова C, яку використовували в Bell Labs, забезпечувала феноменальну швидкість виконання, але не давала жодних засобів високорівневого контролю коректності даних.

Страуструп вирішив об'єднати сувору дисципліну типів Simula-67 із продуктивністю та прямим апаратним контролем мови C. Так народився препроцесор **C with Classes** («C з класами»), який транслював розширений синтаксис у стандартний C-код.

Головною інновацією Страуструпа стало фундаментальне правило проектування типів: **об'єкт не може існувати в пам'яті у неініціалізованому стані**. Для цього в мову було введено спеціальну функцію-член, ім'я якої збігалося з ім'ям класу — **конструктор** (від лат. *constructor* — той, хто будує). Щойно компілятор зустрічав оголошення змінної або оператор `new`, він автоматично генерував виклик цієї функції одразу після виділення пам'яті.

## Винайдення деструктора та символіка тільди

Ініціалізація розв'язала половину проблеми, але системне програмування вимагало симетричного рішення для очищення. Якщо об'єкт у процесі свого життя відкриває файл, виділяє сторінку в купі або захоплює апаратний семафор, це володіння має завершитися в строго визначений момент.

Страуструп сформулював концепцію **деструктора** (від лат. *destructor* — той, хто руйнує) — спеціальної функції, яка гарантовано викликається компілятором у момент виходу змінної з області видимості (на стеку) або при явному знищенні через `delete`.

Постало питання синтаксису: як назвати функцію знищення? Страуструп відхилив варіанти з префіксами на зразок `destroy_ClassName` чи ключовими словами `delete`, щоб не ускладнювати таблицю символів. Замість цього він звернувся до фундаментальної операції мови C — побітового заперечення (доповнення), що позначається знаком тільди `~`.

Логіка була бездоганною: якщо конструктор `ClassName` створює об'єкт і стверджує його стан, то побітове заперечення `~ClassName` означає логічну інверсію — розбирання стану, знищення та повернення виділених ресурсів.

```cpp
class Vector {
    int* elem;
    int sz;
public:
    Vector(int s);  // Конструктор: захоплює пам'ять
    ~Vector();      // Деструктор: ~ як заперечення народження об'єкта
};
```

Деструктор став першим в історії мов програмування механізмом **детермінованого автоматичного керування ресурсами без збирача сміття**.

## Поява винятків і народження ідіоми RAII

У середині 1980-х років Страуструп разом із комітетом зі стандартизації почав проектувати механізм обробки виняткових ситуацій (*exceptions*). Класична модель винятків у ранніх мовах (наприклад, у PL/I чи Lisp) під час аварії просто переривала виконання й виконувала стрибок у глобальний обробник, залишаючи відкриті ресурси завислими в невідомому стані.

Страуструп запропонував зв'язати винятки з життєвим циклом об'єктів через процес **розгортання стека** (англ. *stack unwinding*). Якщо під час виконання вкладеного блоку виникає аварійна ситуація, рантайм перед передачею керування в блок `catch` покроково згортає стек викликів, викликаючи деструктори всіх локальних об'єктів у порядку, строго зворотному до їх створення.

Це відкриття лягло в основу парадигми **RAII** (*Resource Acquisition Is Initialization*), сформульованої Б'ярне Страуструпом та Ендрю Кенігом (англ. *Andrew Koenig*) наприкінці 1980-х. Відтоді конструктор і деструктор перестали бути просто синтаксичною зручністю для обнулення полів: вони перетворилися на математичний інструмент гарантування цілості системних ресурсів, що визначив розвиток системного програмування на наступні десятиліття.
