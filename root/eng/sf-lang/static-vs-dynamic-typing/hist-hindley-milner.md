# 📜 Від парадоксу Рассела до теореми Мілнера: як типи стали доказами

Коли Бертран Рассел у 1901 році виявив, що наївна теорія множин Готлоба Фреге дозволяє сконструювати «множину всіх множин, які не містять себе як елемент», математична логіка опинилася перед фундаментальною кризою. Спроба відповісти на питання, чи містить ця множина саму себе, призводила до нерозв'язної суперечності: якщо містить — то за власним означенням не повинна, а якщо не містить — то зобов'язана належати до себе. Щоб усунути цей парадокс, Рассел у 1908 році запропонував **теорію типів** (англ. *type theory*): він розділив усі математичні сутності на рівні або типи. Об'єкт нульового типу — це індивід; множина індивідів належить до першого типу; множина таких множин — до другого типу. Правило забороняло предикатам застосовуватися до сутностей свого або вищого типу, що автоматично унеможливило циклічні самовідносні конструкції.

Через три десятиліття, у 1940 році, американський логік Алонзо Черч застосував ідею Рассела до обчислень, створивши **типізоване лямбда-числення** (англ. *Simply Typed Lambda Calculus*, `λ→`). У вихідному безтиповому численні Черча будь-яка функція могла приймати на вхід саму себе, породжуючи нескінченні рекурсивні ланцюжки (як-от комбінатор `Y`). Додавши типи до термів, Черч довів, що кожна коректно типізована програма гарантовано завершує свою роботу за скінченну кількість кроків (властивість сильної нормалізації). Типи вперше стали інструментом формального обмеження простору обчислень заради математичної передбачуваності.

```
Сходинка типів Рассела:
Тип 0 (Індивід)  ──>  Тип 1 (Множина індивідів)  ──>  Тип 2 (Множина множин)
   [x = 5]                [S = {1, 2, 3}]                   [M = {S₁, S₂}]
Заборона: елемент не може містити об'єкти свого або вищого рівня
```

## Народження динамічної традиції: Lisp і Smalltalk

Паралельно з розвитком математичної логіки формувалася практична інженерія обчислювальних машин. У 1958 році Джон Маккарті створив мову **Lisp** (англ. *List Processing*) для досліджень у галузі штучного інтелекту. Обчислення в Lisp будувалися на маніпуляціях зі списками та символами довільної структури. Для задач символьної алгебри, планування дій та аналізу природної мови тип даних не міг бути жорстко зафіксований під час написання тексту програми: функція мала приймати список, елементами якого могли бути як атомарні числа, так і вкладені дерева або інші функції.

Маккарті відкинув ідею прив'язування типів до змінних чи синтаксичних виразів. Натомість типи стали властивостями самих значень у машинній пам'яті комп'ютера IBM 704. Одне машинне слово довжиною 36 бітів містило покажчики `CAR` і `CDR`, а тип сутності визначався спеціальним префіксом у пам'яті або адресою в спеціальній зоні пам'яті. Так народилася **динамічна типізація**: програма могла вільно передавати дані між підпрограмами, а інтерпретатор перевіряв допустимість операцій безпосередньо в момент обчислення.

У 1970-х роках у науково-дослідному центрі Xerox PARC Алан Кей, Ден Інгаллс та Адель Голдберг розвинули цю концепцію в мові **Smalltalk**. У філософії Smalltalk усе є об'єктом, а виконання програми — це надсилання повідомлень між об'єктами. Змінна не має типу; вона є лише нейтральним покажчиком на об'єкт. Коли ви викликаєте метод, об'єкт-отримувач під час виконання шукає відповідний обробник у своїй таблиці методів. Якщо метод знайдено — він виконується; якщо ні — об'єкт отримує повідомлення `doesNotUnderstand:`, генеруючи помилку часу виконання. Цей підхід дав розробникам безпрецедентну швидкість прототипування та інтерактивного редагування живого образу системи (англ. *image-based programming*), але переклав тягар перевірки коректності типів на плечі розробника та тести.

## Робін Мілнер і тріумф статичного виведення типів

У той самий час розробники статичних мов зіткнулися з проблемою надмірної багатослівності. Мови на зразок Algol-68, Pascal або ранніх версій Fortran вимагали явного ручного зазначення типу для кожного ідентифікатора, параметра та тимчасової змінної:

```
var x: integer;
var buffer: array [1..256] of char;
```

Така рутина створювала психологічний бар'єр: програмісти сприймали типізацію як бюрократичну перешкоду, яка змушує писати зайвий код і ускладнює рефакторинг.

Прорив стався у 1978 році в Единбурзькому університеті. Британський вчений Робін Мілнер (Robin Milner), спираючись на маловідому роботу логіка Роджера Гіндлі 1969 року, розробив систему типів для мови **ML** (Meta Language), яку згодом назвали алгоритмом **Гіндлі-Мілнера** (англ. *Hindley-Milner Type System*).

Мілнер запропонував математичний алгоритм (відомий як *Algorithm W*), який аналізував синтаксичне дерево програми і автоматично реконструював найзагальніший допустимий тип для кожного виразу без жодної ручної анотації з боку програміста. Компілятор будував систему рівнянь над типами і розв'язував її за допомогою алгоритму уніфікації Робінсона:

```
Вираз у коді:        f(x) = x + 1
1. Введення змінних: x : α,  f : α -> β
2. Аналіз операції:  (+) : int -> int -> int
3. Уніфікація:       α = int,  β = int
4. Результат:        f : int -> int   [тип виведено автоматично!]
```

Головним досягненням Мілнера стало математичне доведення безпеки типу (англ. *Type Safety*). У своїй класичній статті 1978 року «A Theory of Type Polymorphism in Programming» Мілнер сформулював фундаментальну тезу, яка стала гаслом теорії мов програмування:

> **«Well-typed programs cannot go wrong.»**  
> *(Коректно типізовані програми не можуть зійти на манівці).*

У строгому математичному сенсі фраза «cannot go wrong» означала, що програма, яка пройшла статичну перевірку типів, ніколи не потрапить у стан невизначеної поведінки чи незрозумілої машинної аварії (наприклад, спроби виконати ціле число як покажчик на машинну команду або прочитати байти рядка як числа з плаваючою комою). Доведення базувалося на двох взаємопов'язаних лемах:
1. **Просування (Progress):** Кожен коректно типізований вираз є або завершеним значенням, або може зробити щонайменше один коректний крок обчислення.
2. **Збереження (Preservation / Subject Reduction):** Якщо вираз типу `T` робить крок обчислення і переходить у новий вираз, цей новий вираз також має тип `T`.

```
Теорема безпеки типів (Milner / Wright-Felleisen):

                Вираз e₁ типу T
                      │
           (Progress) │ робить крок обчислення
                      ▼
                Вираз e₂ типу T   <── (Preservation: тип залишається незмінним)
```

## Ізоморфізм Каррі-Говарда: тип як теорема

У 1969 році Вільям Говард задокументував відкриття, яке раніше помітив логік Гаскелл Каррі: між системами статичних типів і конструктивною логікою існує пряма математична еквівалентність — **ізоморфізм Каррі-Говарда** (англ. *Curry-Howard correspondence*):

- **Тип** у мові програмування відповідає **логічному твердженню (теоремі)** у математичній логіці.
- **Програма (значення даного типу)** відповідає **доведенню цієї теореми**.
- **Перевірка типів компілятором** відповідає **механічній перевірці правильності доведення**.

```
Логіка інтуїціонізму         Мови програмування
────────────────────────────────────────────────────
Твердження A              <──>  Тип A
Доведення теореми         <──>  Програма / Вираз
Імплікація A ⇒ B          <──>  Функція A -> B
Кон'юнкція A ∧ B          <──>  Кортеж / Структура (A, B)
Диз'юнкція A ∨ B          <──>  Сума типів / Variant (A | B)
Істина (True)             <──>  Одиничний тип Unit ()
Хибність / Абсурд (False) <──>  Порожній тип Never / Void
```

Це фундаментальне відкриття остаточно змінило сприйняття статичної типізації. Статичні типи перестали бути просто підказками для компілятора щодо розміру комірки пам'яті (чи виділяти 4 байти під `int`, чи 8 під `double`). Вони перетворилися на формальні логічні контракти, де компілятор виступає автоматичним верифікатором коректності логіки програми ще до її запуску.

## Велике зближення: поступова типізація XXI століття

Протягом чотирьох десятиліть індустрія розробки була розділена на два табори: прихильники динамічних мов (Lisp, Smalltalk, Perl, Python, Ruby, JavaScript) цінували швидкість розробки, гнучкість метапрограмування та відсутність бюрократії типів; прихильники статичних мов (Ada, C++, Java, Haskell, OCaml, Rust) наполягали на швидкодії, машинних гарантіях надійності та простоті рефакторингу великих кодових баз.

Коли розмір проектів на динамічних мовах перевищив сотні тисяч і мільйони рядків коду, підтримка таких систем стала критично складною. Зміна сигнатури методу або форми об'єкта вимагала повного ручного аудиту або 100% покриття тестами, оскільки пропущена помилка виявлялася лише в продакшені під час виконання рідкісної гілки логіки.

Відповіддю наукової спільноти стала **поступова типізація** (англ. *Gradual Typing*), формалізована Джеремі Сіком та Валідом Тахою (Jeremy Siek, Walid Taha) у 2006 році. Поступова типізація дозволяє поєднувати статично типізовані та динамічно типізовані фрагменти в межах одного файлу або проекту, використовуючи спеціальний динамічний тип `any` або `unknown` на межі взаємодії.

Практичним втіленням цієї теорії стали системи типів наступного покоління:
- **TypeScript** (2012, розроблений Андерсом Гейлсбергом у Microsoft) — статична надбудова над динамічним JavaScript, де типи повністю стираються під час компіляції, але забезпечують тотальний контроль над структурами даних у процесі розробки.
- **Python Type Hints / MyPy** (2014, PEP 484 під керівництвом Гвідо ван Россума та Юкки Лехтосало) — додавання статичного аналізу поверх чистого рантайму CPython.
- **Sorbet** для Ruby та **Hack** для PHP.

Історія довела, що конфлікт між статичною та динамічною типізацією не був боротьбою добра зі злом: це була еволюція інструментів під різні масштаби систем. Динамічна типізація залишається незамінною для швидких експериментів, сценаріїв автоматизації та компактних скриптів; статична типізація із сучасним виведенням типів стала обов'язковим стандартом для складних, довговічних та високонавантажених програмних комплексів.
