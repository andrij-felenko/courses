Коли програмі потрібно знайти в тексті точний рядок, наприклад `"status"`, задача розв'язується прямим порозрядним порівнянням за алгоритмами Боєра–Мура або Кнута–Морріса–Пратта. Проте пошук структурних даних — ідентифікаторів змінних `[a-zA-Z_][a-zA-Z0-9_]*`, шістнадцяткових адрес `0x[0-9a-fA-F]+`, чисел із рухомою комою або записів системних журналів — вимагає зіставлення не з фіксованим текстом, а з нескінченною множиною допустимих послідовностей символів. Написання ручних розпізнавачів на основі вкладених умов `if/else` і циклів для кожного такого шаблону призводить до громіздкого, вразливого до помилок коду, який неможливо динамічно конфігурувати.

Цю проблему розв'язує математичний апарат формальних мов. Регулярний вираз (*regular expression*, скорочено *regex*, від лат. *regularis* — правильний, підпорядкований правилу) є декларативною нотацією для визначення регулярних множин рядків над скінченним алфавітом. Замість опису покрокового алгоритму перевірки символів розробник формулює компактний шаблон, який компілятор або системна бібліотека автоматично транслює у виконавчу обчислювальну модель — скінченний автомат.

## Теоретичний фундамент: алгебра Кліні та еквівалентність автоматам

Математичну основу регулярних мов сформулював американський математик Стівен Кліні у 1950-х роках під час дослідження формальних нейронних мереж. Теорема Кліні стверджує: довільний регулярний вираз породжує мову, яку можна розпізнати скінченним автоматом із пам'яттю, обмеженою кількістю станів, і навпаки — будь-яка мова, розпізнавана скінченним автоматом, виражається регулярним виразом.

З погляду алгебри, регулярний вираз над алфавітом `Σ` будується лише з трьох елементарних операцій:

1. **Конкатенація** (зчеплення, від лат. *concatenatio* — з'єднання ланцюгом): послідовне слідування двох виразів `A · B`. Рядок підходить під `A · B`, якщо його перша частина відповідає `A`, а наступна — `B`.
2. **Чергування** (альтернація, від лат. *alternare* — чергуватися): логічний вибір між гілками `A | B`. Рядок підходить, якщо він належить або до множини `A`, або до множини `B`.
3. **Замикання Кліні** (ітерація, зірочка `*`): повторення підвиразу нуль або довільну кількість разів `A*`.

Всі інші звичні оператори — плюс `A+` (одне або більше повторень), знак питання `A?` (нуль або один раз), діапазони символів `[a-z]` — є виключно синтаксичним цукром над цими трьома базовими конструкціями:

```
A+
= A · A*          [один обов'язковий блок, за яким слідує нуль або більше повторень]

A?
= A | ε           [вибір між виразом A та порожнім рядком ε]

[ab]
= a | b           [чергування одиничних символів]
```

Детальніше про шлях від математичних праць Маккалока, Піттса та Кліні до текстових редакторів Bell Labs можна дізнатися у статті про [історію створення та розвитку регулярних виразів](root:sf-lang/regular-expressions/hist-regex-evolution.md).

> 🔧 **Навіщо це.**
> Розуміння базової трійки операцій дозволяє передбачити вартість компіляції виразу. Оскільки будь-який складний квантифікатор транслюється в комбінацію конкатенацій та замикання, внутрішній розмір графа автомата пропорційний кількості елементарних операцій.

## Архітектура автоматних рушіїв: DFA проти Thompson NFA

Коли вираз зчитується програмою, він транслюється у граф станів і переходів. За способом організації цього графа та алгоритмом його виконання рушії регулярних виразів поділяються на два принципово різні класи: **автоматні рушії** (*Deterministic / Non-deterministic Finite Automata*) та **рушії з поверненням** (*Backtracking NFA*).

### Конструкція Томпсона (генерація NFA)

Алгоритм Кена Томпсона (1968) будує недетермінований скінченний автомат з `ε`-переходами (`ε`-NFA) за один прохід по синтаксичному дереву виразу. `ε`-перехід дозволяє автомату миттєво перейти в інший стан без зчитування будь-якого вхідного символу.

![Конструкція Томпсона](/root/eng/sf-lang/regular-expressions/img/thompson-nfa-construction.svg)
*Конструкція Томпсона: структурна індукція базових будівельних блоків недетермінованого скінченного автомата з ε-переходами.*

Побудова графа виконується за індуктивними правилами:
- Для базового символу `a` створюються два стани з переходом між ними за символом `a`.
- Для конкатенації `A · B` вихідний стан автомата `A` з'єднується `ε`-переходом із вхідним станом автомата `B`.
- Для чергування `A | B` створюється новий вхідний стан із двома `ε`-переходами до `A` та `B`, а їхні виходи з'єднуються `ε`-переходами зі спільним кінцевим станом.
- Для замикання `A*` додаються зворотний `ε`-перехід із виходу `A` на його вхід (цикл) та прямий `ε`-перехід зі входу на вихід (пропуск при 0 повторень).

Автомат Томпсона для виразу довжини `M` містить не більше `2M` станів і `4M` переходів.

### Покрокова симуляція NFA та детермінізація в DFA

Автоматний рушій (використовується в утилітах `grep`, `egrep`, системній бібліотеці POSIX `regexec`, Google RE2 та компіляторі мови Rust) виконує зіставлення в режимі паралельного потоку (*lockstep streaming*).

Під час обробки чергового символу тексту автомат зберігає не один стан, а **множину всіх одночасно активних станів**:

1. Початкова множина станів `S₀` містить початковий стан та всі стани, досяжні з нього за `ε`-переходами (`ε`-замикання).
2. Для кожного чергового символу тексту `c` обчислюється нова множина активних станів `S_{i+1}`: перевіряються переходи за символом `c` з усіх станів множини `S_i`, після чого застосовується `ε`-замикання.
3. Якщо наприкінці вхідного рядка множина `S_N` містить допускальний (фінальний) стан, рядок відповідає шаблону.

Розглянемо практичний приклад симуляції для шаблону `(a|b)*abb` на вхідному рядку `"ababb"`:
- **Початок:** початковий стан автомата через `ε`-замикання активує стани циклу `(a|b)*` та перший стан очікування символу `'a'` для кінцевого суфікса `abb`. Множина `S₀ = {s_start, s_loop_a, s_loop_b, s_suffix_a}`.
- **Крок 1 (символ 'a'):** стан `s_loop_a` переходить у вихід циклу і повертається в цикл; стан `s_suffix_a` переходить у `s_suffix_b1` (перша літера `'b'` суфікса). Нова множина `S₁` містить стани циклу та стан очікування `'b'`.
- **Крок 2 (символ 'b'):** стан циклу обробляє `'b'`, а стан `s_suffix_b1` переходить у `s_suffix_b2` (друга літера `'b'`).
- **Крок 3 (символ 'a'):** стан `s_suffix_b2` відкидається (бо він чекав `'b'`, а прийшла `'a'`), але цикл знову активує `s_suffix_a`.
- **Кроки 4 та 5 (символи 'b', 'b'):** суфікс проходить через `s_suffix_b1` та досягає фінального стану `s_accept`. Оскільки `s_accept ∈ S₅`, рядок визнано збігом.

![Моделі виконання: DFA проти бектрекінгу](/root/eng/sf-lang/regular-expressions/img/dfa-vs-backtracking.svg)
*Порівняння моделей виконання: паралельний потік станів у DFA/NFA проти рекурсивного пошуку з відкатами у рушіях бектрекінгу.*

Математичні властивості автоматного підходу:
- **Часова складність:** час обробки тексту довжиною `N` на автоматі розміром `M` становить строго `O(M · N)` для NFA або `O(N)` для DFA.
- **Відсутність відкатів:** вхідний текст зчитується рівно один раз, зліва направо. Жоден символ не перевіряється повторно.
- **Пам'ять:** пам'ять обмежена фіксованим вектором станів `O(M)` і не залежить від довжини вхідного тексту.

Для досягнення абсолютної швидкості `O(N)` автомат NFA можна заздалегідь перетворити на детермінований автомат DFA за алгоритмом підмножин Рабіна–Скотта. У DFA для кожного стану та кожного символу існує строго один перехід, тому зіставлення зводиться до швидкого переходу за таблицею індексів: `стан = dfa_table[стан][символ]`.

Ціною детермінізації є потенційний експоненційний вибух кількості станів: вираз виду `(a|b)* a (a|b)ⁿ` вимагає `n+1` стан у NFA, але рівно `2ⁿ` станів у DFA. Сучасні бібліотеки (зокрема `RE2`) застосовують «ліниву» детермінізацію: стани DFA генеруються в кеші динамічно під час зчитування реального тексту і скидаються при перевищенні ліміту виділеної оперативної пам'яті.

Детальніше про алгоритм підмножин Рабіна–Скотта та математичні доведення складності можна прочитати у вставці про [математичний апарат теорії автоматів та леми про розростання](root:sf-lang/regular-expressions/math-kleene-automata.md).

## Стандарти POSIX: Basic (BRE) проти Extended (ERE)

В операційних системах сімейства Unix історично виникли дві несумісні синтаксичні традиції, які у 1992 році були офіційно стандартизовані комітетом IEEE POSIX у документі IEEE Std 1003.2.

![Діалекти регулярних виразів](/root/eng/sf-lang/regular-expressions/img/bre-vs-ere-vs-pcre-dialects.svg)
*Еволюція та синтаксичні відмінності між стандартами BRE, ERE та PCRE.*

Головна відмінність між BRE та ERE полягає в **семантиці екранування** (від фр. *écran* — щит, захисна перегородка). В одному стандарті спеціальний символ потребує зворотного слеша `\` для набуття службового значення, тоді як в іншому зворотний слеш, навпаки, позбавляє символ службового значення, перетворюючи його на звичайний текст.

### Basic Regular Expressions (BRE)

Базові регулярні вирази є стандартом за замовчуванням для класичних утиліт Unix: `grep`, `sed`, `ed`, `vi`.

У синтаксисі BRE метасимволами за замовчуванням (без зворотного слеша) є лише:
- `.` — довільний одиничний символ;
- `^` та `$` — прив'язка до початку та кінця рядка (лише на першій та останній позиціях підвиразу);
- `*` — нуль або більше повторень попереднього елемента;
- `[...]` — символьний клас (наприклад, `[0-9]`).

Символи круглих дужок `(` `)` та фігурних дужок `{` `}` у BRE вважаються **звичайними літералами**. Щоб перетворити їх на службові оператори групування та діапазону повторень, їх необхідно обов'язково екранувати зворотним слешем:
- `\(` ... `\)` — визначає підгрупу для захоплення або пріоритету;
- `\{m,n\}` — квантифікатор діапазону (від `m` до `n` повторень);
- `\1` .. `\9` — зворотне посилання (*backreference*), що вимагає точного збігу з текстом, раніше захопленим `n`-ю групою.

Операції чергування `|`, плюса `+` та знака питання `?` у чистому стандарті POSIX BRE взагалі відсутні. Утиліта GNU `grep` додає їх як власне розширення, але з обов'язковим зворотним слешем: `\|`, `\+`, `\?`.

Приклад пошуку дат формату `YYYY-MM-DD` у синтаксисі BRE:
```
^[0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}$
```

Приклад заміни в утиліті `sed` (виділення першого слова та його подвоєння):
```
sed 's/^\([a-zA-Z]\+\)/\1-\1/'
```

### Extended Regular Expressions (ERE)

Розширені регулярні вирази використовуються утилітами `egrep`, `awk`, системною бібліотекою POSIX при передачі прапорця `REG_EXTENDED`, а також сучасними утилітами пошуку `ripgrep` та `ag`.

У синтаксисі ERE всі спеціальні символи є метасимволами **за замовчуванням**, без жодних зворотних слешів:
- `(` ... `)` — групування виразів;
- `{m,n}` — діапазон повторень;
- `+` — одне або більше повторень;
- `?` — нуль або одне повторення (опційність);
- `|` — чергування гілок.

Якщо в ERE потрібно знайти буквальний символ плюс, дужку або вертикальну риску, їх необхідно екранувати зворотним слешем: `\+`, `\(`, `\|`.

Приклад того самого пошуку дати в синтаксисі ERE:
```
^[0-9]{4}-[0-9]{2}-[0-9]{2}$
```

Важлива теоретична деталь: чистий стандарт POSIX ERE **не підтримує зворотні посилання** `\1`. Це зроблено навмисно: наявність зворотних посилань виводить мову за межі регулярних і робить неможливою гарантовану лінійну обробку на автоматі DFA.

### Локалі та символьні класи POSIX

Поширеною пасткою у виразах POSIX є використання діапазонів на кшталт `[a-z]`. В оригінальному стандарті ASCII символи розташовані послідовно від коду 97 (`a`) до 122 (`z`). Проте за стандартом POSIX порядок сортування символів визначається змінною середовища `LC_COLLATE`. У багатьох європейських локалях (наприклад, `en_US.UTF-8`) порядок сортування чергує регістри: `a, A, b, B, c, C ... z, Z`. Як наслідок, діапазон `[a-z]` у такому середовищі несподівано зіставляється з великими літерами `B`, `C`, `D`, але пропускає велику `Z`.

Для уникнення залежності від системного сортування POSIX увів стандартизовані символьні класи:
- `[[:lower:]]` — малі літери поточної локалі;
- `[[:upper:]]` — великі літери;
- `[[:alpha:]]` — будь-які літери;
- `[[:digit:]]` — десяткові цифри `0-9`;
- `[[:alnum:]]` — літери та цифри;
- `[[:space:]]` — пробільні символи (пробіл, табуляція, новий рядок);
- `[[:punct:]]` — розділові знаки.

Зведену порівняльну таблицю всіх метасимволів, класів символів `[:alpha:]` та прапорців функцій можна знайти у [довіднику синтаксису та API регулярних виразів](root:sf-lang/regular-expressions/api-regex-syntax.md).

## Рушії з поверненням (PCRE): розширені можливості

У 1980–1990-х роках розвиток мов сценаріїв (зокрема мови Perl, створеної Ларрі Воллом) висунув до регулярних виразів вимоги, які класичні автомати DFA не могли задовольнити:
1. Витягування точних меж підрядків для кожної дужкової групи.
2. Підтримка зворотних посилань (наприклад, перевірка збігу відкриваючого та закриваючого тегів XML: `<([a-z]+)>.*?</\1>`).
3. Випереджальні та ретроспективні перевірки без переміщення курсора (*lookaround*).
4. Керування жадібністю квантифікаторів (ліниві квантифікатори `*?`, `+?`).

Для реалізації цих можливостей у Perl (а пізніше у бібліотеці PCRE — *Perl Compatible Regular Expressions*) класичний автоматний алгоритм замінили на **пошук із поверненням** (*backtracking*, від англ. *backtrack* — повертатися назад власним слідом).

Бектрекінг-рушій працює як рекурсивний інтерпретатор: він обирає першу можливу гілку шаблону і намагається просунутися по тексту якомога далі. Якщо на черговому кроці виникає невідповідність символу, рушій відкочує позицію вхідного тексту до останньої точки розгалуження і пробує наступний варіант.

### Нефіксуючі групи та квантифікатори жадібності

У PCRE дужки `(...)` за замовчуванням зберігають захоплений фрагмент у пам'ять для подальшого вилучення. Якщо дужки потрібні лише для встановлення пріоритету або застосування квантифікатора, збереження тексту створює зайві накладні витрати на виділення пам'яті.

Для таких випадків введено **нефіксуючу групу** (*non-capturing group*):
```
(?:https?|ftp)://[a-z0-9.-]+
```
Префікс `?:` вказує рушію не виділяти слот підгрупи для цього блоку.

Квантифікатори (від лат. *quantitas* — кількість + *facere* — робити) у PCRE за замовчуванням є **жадібними** (*greedy*): вони захоплюють максимальну кількість символів, віддаючи їх назад по одному під час бектрекінгу. Додавання знака питання перетворює квантифікатор на **лінивий** (*lazy / non-greedy*):
```
<p>.*</p>      [жадібний: захопить увесь текст від першого <p> до останнього </p> у файлі]
<p>.*?</p>     [лінивий: зупиниться на найближчому закриваючому тегу </p>]
```

### Нульові перевірки (Lookaround Assertions)

Асерції (від лат. *asserere* — стверджувати, заявляти) перевіряють контекст навколо поточної позиції тексту, не включаючи перевірені символи до загального результату збігу (нульова ширина, *zero-width*):

- **Позитивна перевірка вперед (*Positive Lookahead*), `(?=...)`:** перевіряє, що безпосередньо за поточною позицією слідує заданий шаблон.
  ```
  \d+(?=px)    [знайде число лише тоді, коли за ним одразу стоїть "px", але "px" не увійде у збіг]
  ```
- **Негативна перевірка вперед (*Negative Lookahead*), `(?!...)`:** перевіряє, що попереду НЕ слідує заданий шаблон.
  ```
  passwd(?!_bak) [знайде "passwd", якщо за ним не слідує "_bak"]
  ```
- **Позитивна перевірка назад (*Positive Lookbehind*), `(?<=...)`:** перевіряє текст, що передує поточній позиції.
  ```
  (?<=\$)\d+   [знайде цифри лише після знака долара "$"]
  ```
- **Негативна перевірка назад (*Negative Lookbehind*), `(?<!...)`:** перевіряє, що перед поточною позицією немає заданого шаблону.
  ```
  (?<!\\)'     [знайде одинарну лапку, перед якою немає екрануючого слеша]
  ```

> 🔧 **Навіщо це.**
> Асерції дозволяють формулювати складні правила валідації паролів за один прохід, наприклад: `^(?=.*[A-Z])(?=.*[a-z])(?=.*[0-9]).{8,}$` перевіряє наявність великої літери, малої літери, цифри та мінімальної довжини у 8 символів без необхідності писати кілька окремих перевірок.

## Катастрофічний бектрекінг та вразливість ReDoS

Головною небезпекою рушіїв із поверненням є нелінійна часова складність у найгіршому випадку. Якщо регулярний вираз містить неоднозначні перекриття між сусідніми квантифікаторами, алгоритм перебору вироджується в експоненційний пошук `O(2ⁿ)`.

Цей ефект називається **катастрофічним бектрекінгом** (*catastrophic backtracking*), а його зловмисна експлуатація у мережевих сервісах та веб-додатках — атакою **ReDoS** (*Regular Expression Denial of Service*).

![Катастрофічний бектрекінг](/root/eng/sf-lang/regular-expressions/img/redos-backtracking-explosion.svg)
*Катастрофічний бектрекінг (ReDoS): експоненційне дерево перебору всіх можливих розбиттів рядка при невдалому збігу.*

Розглянемо три класичні шаблони, що провокують катастрофічний бектрекінг (так звані *Evil Regexes*):

1. **Вкладені квантифікатори:** `(a+)+$`, `(a*)*$`, `(a+)*$`
   Якщо на вхід подати рядок `"aaaaaaaaaaaa!"` (30 символів `'a'` та знак оклику наприкінці):
   - Рушій жадібно захоплює всі 30 символів `'a'` першим внутрішнім квантифікатором.
   - Наприкінці рядка перевіряється символ `$` (кінець рядка), але там стоїть знак `'!'` — збігу немає.
   - Рушій повертається назад і віддає один символ `'a'` зовнішньому квантифікатору. Текст ділиться як `(29 літер) + (1 літера)`.
   - Знову перевіряється кінець рядка, знову невдача `'!'`.
   - Рушій пробує розбиття `(28 + 2)`, `(28 + 1 + 1)`, `(27 + 3)` і так далі.

   Кількість способів розбити послідовність довжини `N` на непустих підмножин дорівнює кількості композицій числа `N`, що становить рівно `2^(N - 1)`. Для `N = 30` це `2²⁹ = 536 870 912` рекурсивних викликів. Замість кількох мікросекунд обробка одного рядка блокує ядро процесора на десятки секунд.

2. **Перекриття альтернацій із квантифікаторами:** `(a|a+)+$` або `(a|ab)+$`
   Кожен символ `'a'` може бути оброблений як першою, так і другою гілкою чергування, що створює експоненційне розгалуження дерева пошуку `2ⁿ`.

3. **Сусідні перекриваючі квантифікатори:** `.*a.*b` на текстах без кінцевого символа `'b'`.

Реальний інцидент світового масштабу стався 2 липня 2019 року в інфраструктурі Cloudflare. В оновленні правил фаєрволу WAF з'явився регулярний вираз для пошуку XSS-атак:
```
(?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`)\s{0,256}[-+/&|:*%^<>!=<>?~])
```
Некоректно скомпільований патерн із незбалансованими квантифікаторами потрапив на рядок із символом `=`, що викликало 100% завантаження всіх ядер процесорів на прикордонних серверах компанії та призвело до падіння значної частини світового веб-трафіку на 27 хвилин.

### Захист від ReDoS

Для усунення катастрофічного бектрекінгу в архітектурі систем застосовують три інженерні підходи:

1. **Атомарне групування `(?>...)` та посесивні квантифікатори `++`, `*+`:**
   Атомарна група (*atomic group*) вказує рушію відкинути всі збережені точки повернення одразу після того, як група успішно зіставилася. Якщо наступна частина шаблону не підійде, рушій не повертатиметься всередину атомарної групи:
   ```
   ^(?>a+)+$     [виконається за мікросекунди: внутрішня група не віддає символи назад]
   ^a++$         [посесивний квантифікатор: захоплює символи намертво без бектрекінгу]
   ```

2. **Застосування лінійних автоматних бібліотек:**
   Для обробки неперевірених користувацьких шаблонів замість PCRE та стандартного `std::regex` використовують бібліотеки на основі DFA / Thompson NFA (Google `RE2`, Rust `regex`, Intel `Hyperscan`). Вони принципово гарантують лінійний час виконання `O(N)` і цілковитий імунітет до ReDoS, відмовляючись від зворотних посилань і перевірок змінної довжини.

3. **Обмеження глибини та кроків пошуку (*Match Limits*):**
   Бібліотека PCRE2 дозволяє виставити ліміти `pcre2_set_match_limit` та `pcre2_set_depth_limit`. При перевищенні заданого порогу кроків рушій негайно перериває обчислення з помилкою замість зависання.

## Практична реалізація: POSIX C API та RAII в C++

Стандартний інтерфейс POSIX C надає мінімальний і надійний API для компіляції та виконання регулярних виразів через заголовок `<regex.h>`.

Процес використання складається з трьох обов'язкових кроків:
1. `regcomp()` — компіляція текстового рядка шаблону у внутрішню структуру автомата `regex_t`.
2. `regexec()` — зіставлення тексту з автоматоном із заповненням масиву зміщень `regmatch_t`.
3. `regfree()` — звільнення динамічної пам'яті, виділеної для таблиць переходів автомата.

Нижче наведено приклад компіляції виразу для валідації ідентифікаторів та виділення підгруп на мовах C та C++.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <regex.h>

#define MAX_MATCHES 3

int validate_identifier(const char *text) {
    regex_t regex;
    regmatch_t matches[MAX_MATCHES];
    char err_buf[128];

    /* Компіляція виразу ERE з ігноруванням регістру */
    int ret = regcomp(&regex, "^([a-zA-Z_][a-zA-Z0-9_]*)=([0-9]+)$", REG_EXTENDED | REG_ICASE);
    if (ret != 0) {
        regerror(ret, &regex, err_buf, sizeof(err_buf));
        fprintf(stderr, "Помилка компіляції: %s\n", err_buf);
        return -1;
    }

    /* Зіставлення з рядком */
    ret = regexec(&regex, text, MAX_MATCHES, matches, 0);
    if (ret == 0) {
        printf("Збіг успішний для \"%s\":\n", text);
        for (int i = 0; i < MAX_MATCHES; i++) {
            if (matches[i].rm_so == -1) continue;
            int len = matches[i].rm_eo - matches[i].rm_so;
            printf("  Група %d: %.*s\n", i, len, text + matches[i].rm_so);
        }
    } else if (ret == REG_NOMATCH) {
        printf("Рядок \"%s\" не відповідає формату.\n", text);
    }

    /* Обов'язкове вивільнення ресурсів */
    regfree(&regex);
    return ret == 0;
}

int main(void) {
    validate_identifier("timeout_ms=5000");
    validate_identifier("123_bad_name=10");
    return 0;
}
```

```cpp
#include <iostream>
#include <string_view>
#include <vector>
#include <stdexcept>
#include <regex.h>

// Безпечна RAII-обгортка над POSIX regex_t
class RegexEngine {
public:
    explicit RegexEngine(std::string_view pattern, int flags = REG_EXTENDED) {
        std::string null_terminated(pattern);
        int ret = regcomp(&reg_, null_terminated.c_str(), flags);
        if (ret != 0) {
            char buf[128];
            regerror(ret, &reg_, buf, sizeof(buf));
            throw std::runtime_error(std::string("regcomp failed: ") + buf);
        }
    }

    ~RegexEngine() noexcept {
        regfree(&reg_);
    }

    // Заборона небезпечного копіювання
    RegexEngine(const RegexEngine&) = delete;
    RegexEngine& operator=(const RegexEngine&) = delete;

    // Дозвіл переміщення ресурсу
    RegexEngine(RegexEngine&& other) noexcept {
        reg_ = other.reg_;
        other.reg_ = {};
    }

    RegexEngine& operator=(RegexEngine&& other) noexcept {
        if (this != &other) {
            regfree(&reg_);
            reg_ = other.reg_;
            other.reg_ = {};
        }
        return *this;
    }

    std::vector<std::string_view> search(std::string_view text, size_t max_groups = 4) const {
        std::vector<regmatch_t> pmatch(max_groups);
        std::string null_terminated(text);

        int ret = regexec(&reg_, null_terminated.c_str(), max_groups, pmatch.data(), 0);
        if (ret == REG_NOMATCH) {
            return {};
        }
        if (ret != 0) {
            char buf[128];
            regerror(ret, &reg_, buf, sizeof(buf));
            throw std::runtime_error(std::string("regexec failed: ") + buf);
        }

        std::vector<std::string_view> groups;
        groups.reserve(max_groups);

        for (size_t i = 0; i < max_groups; ++i) {
            if (pmatch[i].rm_so == -1) {
                groups.emplace_back("");
            } else {
                size_t start = static_cast<size_t>(pmatch[i].rm_so);
                size_t len = static_cast<size_t>(pmatch[i].rm_eo - pmatch[i].rm_so);
                groups.emplace_back(text.substr(start, len));
            }
        }
        return groups;
    }

private:
    regex_t reg_{};
};

int main() {
    try {
        RegexEngine re("^([a-zA-Z_][a-zA-Z0-9_]*)=([0-9]+)$");

        std::string_view line = "timeout_ms=5000";
        auto matches = re.search(line, 3);

        if (!matches.empty()) {
            std::cout << "Змінна: " << matches[1] << "\n";
            std::cout << "Значення: " << matches[2] << "\n";
        }
    } catch (const std::exception& e) {
        std::cerr << "Виняток: " << e.what() << "\n";
    }
    return 0;
}
```

## Порівняльний аналіз та критерії вибору рушія

Вибір конкретного інструменту та діалекту регулярних виразів визначається вимогами системи до швидкості, безпеки та складності правил розбору.

| Критерій вибору | Автоматні рушії (DFA / Thompson NFA) | Рушії з поверненням (PCRE / Perl / Python) |
|---|---|---|
| **Реалізації** | `grep`, POSIX `regexec`, Google `RE2`, Rust `regex` | `PCRE2`, Python `re`, JS `RegExp`, Java `Pattern`, C++ `std::regex` |
| **Час виконання** | Строго `O(N)` або `O(M · N)` (лінійний) | `O(N)` у найкращому, `O(2ⁿ)` у найгіршому |
| **Стійкість до ReDoS** | Абсолютна (вразливість неможлива за будовою) | Вразливі (вимагають атомарних груп або таймаутів) |
| **Потокова обробка** | Працює з нескінченним потоком даних без збереження тексту | Вимагає збереження всього рядка в оперативній пам'яті |
| **Зворотні посилання `\1`** | Не підтримуються (теоретичне обмеження DFA) | Підтримуються |
| **Lookaround-асерції** | Лише фіксованої ширини або не підтримуються | Повна підтримка будь-яких умов |
| **Призначення** | Компілятори (лексери), мережеві фільтри (WAF), grep | Складний розбір форматів, валідація форм, рефакторинг |

У розробці компіляторів та системного програмного забезпечення лексичні аналізатори (лексери) завжди будуються виключно на основі DFA: це гарантує, що час токенізації вихідного коду програми залишатиметься строго пропорційним його розміру у байтах незалежно від складності синтаксичних конструкцій.
