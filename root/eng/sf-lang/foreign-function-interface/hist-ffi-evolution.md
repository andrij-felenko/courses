# 📜 Від мостів Lisp до універсального клею систем

У середині 1980-х років розробники великих символьних систем на мові Lisp (англ. *List Processing*) опинилися перед інженерним глухим кутом. Середовища Lisp надавали динамічну типізацію, автоматичне збирання сміття та інтерактивні макроси, проте обчислювальна лінійна алгебра, тривимірна графіка та мережеві драйвери були написані мовами Fortran і C. Переписування мільйонів рядків математичного коду на Lisp було економічно неможливим, а продуктивність числових обчислень у ранніх динамічних інтерпретаторах поступалася скомпільованому машинному коду в десятки разів.

Постала потреба у механізмі, який дозволив би програмі на Lisp безпосередньо завантажувати скомпільований об'єктний файл, передавати аргументи у низькорівневі змінні та отримувати результат. Саме в середовищі розробників Common Lisp (зокрема в реалізаціях Franz Lisp та CMU Common Lisp) народився термін **Foreign Function Interface** (FFI — «інтерфейс чужоземних функцій», від лат. *foris* — «зовні»).

## Чому саме C став універсальним стандартом

У 1970-х і 1980-х роках майже кожна мова програмування мала власний формат виклику функцій. Pascal передавав аргументи зліва направо й очищав стек всередині викликаної функції (`stdcall`), Fortran передавав усі аргументи виключно за посиланням через непрямі адреси, а перші версії C передавали параметри справа наліво через стек, залишаючи очищення викликачу (`cdecl`), що уможливлювало функції зі змінною кількістю аргументів на зразок `printf`.

Перелом стався наприкінці 1980-х років із прийняттям стандарту ANSI C (C89/C90) та поширенням операційних систем сімейства Unix. Ядро Unix та системні бібліотеки були написані мовою C. Щоб здійснити будь-який системний виклик (відкрити файл, виділити сторінку пам'яті, надіслати пакет у мережу), будь-яка інша мова програмування мусила вміти сформувати двійковий виклик саме за правилами C.

Коли в 1990-х роках стрімко розвивалася мова C++, багато хто очікував, що вона замінить C як новий міжмовний стандарт. Проте C++ увів механізми, які зруйнували двійкову стабільність: спотворення імен (англ. *name mangling*), нерегульовану таблицю віртуальних методів (`vtable`), розкрутку стека винятків (англ. *exception unwinding*) та складні конструктори копіювання. Різні компілятори C++ (GCC, Clang, MSVC) не могли злінкувати код навіть між собою, не кажучи вже про інші мови.

У результаті мова C, завдяки простоті своїх структур, відсутності прихованих заголовків об'єктів і прямій відповідності машинним регістрам, стала загальним знаменником — *lingua franca* всієї обчислювальної індустрії.

## Народження libffi та динамічний прорив

На початку 1990-х років для кожного міжмовного виклику програміст мусив писати статичну функцію-обгортку (англ. *wrapper* або *stub*) на C, компілювати її під кожну операційну систему й лінкувати з рантаймом. Якщо бібліотека містила п'ятсот функцій, потрібно було згенерувати п'ятсот окремих C-функцій переходу.

У 1996 році інженер Ентоні Грін (англ. *Anthony Green*), працюючи в компанії Cygnus Solutions над проектом GCC Java Runtime (GCJ), зіткнувся з фундаментальною проблемою. Віртуальна машина Java (JVM) інтерпретувала байткод і під час виконання зустрічала виклики довільних нативних методів із сигнатурами, невідомими на етапі збирання самого компілятора. Потрібен був динамічний асемблерний міст, здатний під час виконання прийняти масив довільних типів, розкласти їх по апаратних регістрах процесора згідно з поточною архітектурою та викликати довільну адресу пам'яті.

Так народилася бібліотека **libffi**. Грін написав універсальний рушій, який розділив завдання на дві частини:
1. Високорівневий опис інтерфейсу виклику (англ. *Call Interface* — CIF), де типи аргументів описуються незалежними від платформи структурами.
2. Низькорівневий асемблерний трамплін (англ. *trampoline*), написаний окремо для кожної процесорної архітектури (x86, SPARC, Alpha, ARM, MIPS, PowerPC).

Бібліотека libffi виявилася настільки компактною та надійною, що її швидко запозичили творці мов сценаріїв. Томас Геллер (англ. *Thomas Heller*) інтегрував її у Python у вигляді модуля `ctypes`, зробивши виклик C-бібліотек доступним безпосередньо з коду Python без встановлення компілятора C на машині користувача. Згодом libffi стала фундаментом для JNA у світі Java, FFI у Ruby, Node.js, PHP та OCaml.

## Епоха нульових витрат: LuaJIT та Rust

На початку 2010-х років розробник Майк Полл (англ. *Mike Pall*) представив рушій LuaJIT FFI. На відміну від класичного libffi, який щоразу формував динамічний масив аргументів, JIT-компілятор LuaJIT інтегрував C-декларації безпосередньо в граф проміжного представлення (IR). Компілятор перетворював звернення до C-структур на прямі машинні інструкції читання та запису пам'яті, усуваючи будь-які накладні витрати на маршалінг. C-код, викликаний з LuaJIT, виконувався з тією ж швидкістю, що й нативний C.

У цей же час мова Rust відмовилася від власного важкого рантайму й оголосила сумісність із C ABI першокласною властивістю мови. Ключове слово `extern "C"` дозволяє Rust експортувати та імпортувати функції без проміжних обгорток, а атрибут `#[repr(C)]` гарантує байтову ідентичність структур даних.

Сьогодні FFI залишається головним клеєм сучасного програмного забезпечення: саме через нього нейромережеві моделі на Python керують високопродуктивними ядрами CUDA на GPU, операційні системи на Rust викликають legacy-модулі ядра Linux на C, а мобільні додатки на Swift та Kotlin працюють із загальними C++ рушіями.
