# 📋 Інтерфейс динамічного виклику libffi: структури CIF та диспетчеризація

Бібліотека **libffi** надає переносний інтерфейс низькорівневого виклику функцій за довільними C-сигнатурами, сформованими під час виконання програми. Її використовують інтерпретатори мов програмування (Python `ctypes`, Ruby `fiddle`, OpenJDK FFM/JNI, LuaJIT) для динамічного виклику експортованих символів спільних бібліотек (`.so`, `.dll`, `.dylib`) без попередньої генерації статичного асемблерного коду під кожну можливу функцію.

## 1. Головні структури даних

Контракт libffi базується на двох фундаментальних структурах: описі окремого типу (`ffi_type`) та дескрипторі інтерфейсу виклику (`ffi_cif`).

### Структура `ffi_type`

Описує скалярний базовий тип або складену C-структуру:

```c
typedef struct _ffi_type {
    size_t               size;       /* Розмір типу в байтах */
    unsigned short       alignment;  /* Вирівнювання типу в байтах */
    unsigned short       type;       /* Числовий ідентифікатор типу */
    struct _ffi_type   **elements;   /* Масив покажчиків на поля (для структур), завершується NULL */
} ffi_type;
```

Вбудовані константи базових типів:
- `&ffi_type_void` — порожній тип повернення `void`;
- `&ffi_type_uint8`, `&ffi_type_sint8` — 8-бітні цілі (`uint8_t`, `int8_t`);
- `&ffi_type_uint16`, `&ffi_type_sint16` — 16-бітні цілі (`uint16_t`, `int16_t`);
- `&ffi_type_uint32`, `&ffi_type_sint32` — 32-бітні цілі (`uint32_t`, `int32_t`);
- `&ffi_type_uint64`, `&ffi_type_sint64` — 64-бітні цілі (`uint64_t`, `int64_t`);
- `&ffi_type_float`, `&ffi_type_double` — числа з плаваючою комою IEEE 754;
- `&ffi_type_pointer` — універсальний покажчик на машинну пам'ять (`void*`, `char*`).

Для створення користувацької структури створюється об'єкт `ffi_type`, де поле `type = FFI_TYPE_STRUCT`, а `elements` вказує на `NULL`-термінований масив покажчиків на типи полів. Поля `size` та `alignment` ініціалізуються нулями — функція `ffi_prep_cif()` автоматично обчислить зміщення кожного поля, додасть необхідну набивку (англ. *padding*) та встановить загальне вирівнювання за правилами цільового ABI.

### Структура `ffi_cif` (Call Interface)

Інкапсулює скомпільовану інформацію про стек, регістри та угоду про виклики:

```c
typedef struct {
    ffi_abi             abi;        /* Використовувана угода про виклики */
    unsigned int        nargs;      /* Кількість вхідних аргументів */
    ffi_type          **arg_types;  /* Масив покажчиків на ffi_type аргументів */
    ffi_type           *rtype;      /* Покажчик на ffi_type результату */
    unsigned int        bytes;      /* Кількість байтів, необхідних на стеку */
    unsigned int        flags;      /* Внутрішні прапорці диспетчеризації */
} ffi_cif;
```

## 2. Основні функції API та їхні контракти

### `ffi_prep_cif`

Ініціалізує структуру `ffi_cif` для фіксованої кількості аргументів.

```c
ffi_status ffi_prep_cif(
    ffi_cif       *cif,
    ffi_abi        abi,
    unsigned int   nargs,
    ffi_type      *rtype,
    ffi_type     **atypes
);
```

**Параметри:**
- `cif` — покажчик на виділену викликачем структуру `ffi_cif`.
- `abi` — цільовий ABI (зазвичай `FFI_DEFAULT_ABI`, що відповідає стандартному ABI поточної платформи: System V AMD64 на Linux/macOS, Microsoft x64 на Windows, AAPCS64 на ARM64).
- `nargs` — загальна кількість параметрів функції.
- `rtype` — покажчик на `ffi_type` повертаного значення.
- `atypes` — масив довжиною `nargs` із покажчиками на `ffi_type` кожного аргументу.

**Повертає:**
- `FFI_OK` (0) — підготовка успішна.
- `FFI_BAD_TYPEDEF` — передано некоректний опис типу (наприклад, нульове вирівнювання або порожня структура).
- `FFI_BAD_ABI` — вказана угода про виклики не підтримується на цій апаратній архітектурі.

Під час виконання `ffi_prep_cif()` бібліотека розраховує:
1. Скільки цілочисельних та векторних регістрів потребує виклик на цільовій архітектурі.
2. Скільки байтів аргументів не вміщаються в регістри й мають бути розміщені на стеку.
3. Як повертається результат: через регістри (`%rax`/`%rdx`, `%xmm0`), чи через непрямий прихований покажчик (англ. *hidden return pointer* у регістрі `%rdi`/`%rcx`), якщо розмір повертаної структури перевищує 16 байтів.

### `ffi_prep_cif_var`

Ініціалізує `ffi_cif` для функцій зі змінною кількістю аргументів (англ. *variadic functions*, наприклад `printf(const char *fmt, ...)`).

```c
ffi_status ffi_prep_cif_var(
    ffi_cif       *cif,
    ffi_abi        abi,
    unsigned int   nfixedargs,
    unsigned int   ntotalargs,
    ffi_type      *rtype,
    ffi_type     **atypes
);
```

**Параметри:**
- `nfixedargs` — кількість обов'язкових фіксованих аргументів.
- `ntotalargs` — сумарна кількість аргументів для конкретного виклику (`nfixedargs` + варіативні).

На архітектурі System V AMD64 кількість переданих векторних аргументів із плаваючою комою у варіативній функції записується в регістр `%al` (щоб викликана функція знала, скільки регістрів `XMM` зберігати на стек). `ffi_prep_cif_var` гарантує правильне встановлення цього службового лічильника.

### `ffi_call`

Здійснює безпосередній апаратний виклик цільової функції за підготовленим `ffi_cif`.

```c
void ffi_call(
    ffi_cif  *cif,
    void    (*fn)(void),
    void     *rvalue,
    void    **avalues
);
```

**Параметри:**
- `cif` — раніше підготовлений дескриптор `ffi_cif`.
- `fn` — адреса машинної функції, яку необхідно викликати (отримана, наприклад, через `dlsym` або `GetProcAddress`).
- `rvalue` — покажчик на буфер пам'яті, куди буде записано повернене значення. Буфер повинен мати розмір не менше ніж `max(sizeof(ffi_arg), rtype->size)` і бути вирівняним за правилами цільового типу.
- `avalues` — масив покажчиків типу `void*` довжиною `cif->nargs`. Кожен елемент `avalues[i]` вказує на комірку пам'яті, де лежить значення відповідного аргументу.

## 3. Зворотні виклики: Замикання (Closures API) та механіка W^X

Замикання libffi дозволяють створити нативну адресу C-функції (покажчик на функцію), виклик якої перенаправляється в універсальний динамічний обробник (callback) мови вищого рівня.

```c
/* Виділення виконуваної пам'яті для трампліна */
void* ffi_closure_alloc(size_t size, void **code);

/* Налаштування прив'язки трампліна до обробника */
ffi_status ffi_prep_closure_loc(
    ffi_closure *closure,
    ffi_cif     *cif,
    void       (*fun)(ffi_cif *cif, void *ret, void **args, void *user_data),
    void        *user_data,
    void        *codeloc
);

/* Вивільнення пам'яті замикання */
void ffi_closure_free(void *closure);
```

### Механізм подвійного відображення сторінок (Dual Mapping)

Сучасні операційні системи (Linux, macOS, OpenBSD, Windows) підтримують захист **W^X** (англ. *Write XOR Execute* — «запис виключає виконання»): сторінка оперативної пам'яті може бути або доступною для запису, або доступною для виконання, але ніколи одночасно.

Функція `ffi_closure_alloc` вирішує цю проблему за допомогою подвійного відображення пам'яті через анонімні файлові дескриптори (`mmap` / `VirtualAlloc`):
1. Повертається покажчик запису `closure` (права `PROT_READ | PROT_WRITE`), куди функція `ffi_prep_closure_loc` записує машинний трамплін та службові покажчики.
2. Через вихідний параметр `code` повертається апаратний покажчик виконання (права `PROT_READ | PROT_EXEC`), який передається стороннім C-бібліотекам як звичайний callback.

Коли C-код викликає адресу `code`, процесор виконує кілька інструкцій асемблерного трампліна, які зберігають вхідні регістри в стек, завантажують адресу структури `ffi_closure` в службовий регістр і передають керування універсальній функції `fun`.

## 4. Практичний приклад динамічного виклику

Наведений приклад демонструє динамічний виклик стандартної функції `puts("Привіт зі світу FFI")` без прямого звернення до імені функції на етапі компіляції:

:::tabs
```c
#include <stdio.h>
#include <ffi.h>

int main(void) {
    ffi_cif cif;
    ffi_type *args[1];
    void *values[1];

    /* Опис аргументів: один покажчик (const char*) */
    args[0] = &ffi_type_pointer;

    /* Підготовка дескриптора виклику */
    if (ffi_prep_cif(&cif, FFI_DEFAULT_ABI, 1, &ffi_type_sint32, args) != FFI_OK) {
        fprintf(stderr, "Помилка ініціалізації CIF\n");
        return 1;
    }

    const char *message = "Привіт зі світу libffi!";
    values[0] = &message; /* Покажчик на комірку з аргументом */

    int result = 0;

    /* Динамічний виклик puts */
    ffi_call(&cif, FFI_FN(puts), &result, values);

    printf("puts повернув код: %d\n", result);
    return 0;
}
```
```cpp
#include <iostream>
#include <vector>
#include <string_view>
#include <ffi.h>

int main() {
    ffi_cif cif;
    std::vector<ffi_type*> arg_types = { &ffi_type_pointer };
    std::vector<void*> arg_values(1);

    if (ffi_prep_cif(&cif, FFI_DEFAULT_ABI, static_cast<unsigned int>(arg_types.size()),
                     &ffi_type_sint32, arg_types.data()) != FFI_OK) {
        std::cerr << "Помилка ініціалізації CIF\n";
        return 1;
    }

    const char* message = "Привіт зі світу libffi (C++)!";
    arg_values[0] = const_cast<char**>(&message);

    int result = 0;
    ffi_call(&cif, FFI_FN(puts), &result, arg_values.data());

    std::cout << "puts повернув код: " << result << '\n';
    return 0;
}
```

## 5. Критичні інваріанти та вимоги до пам'яті

1. **Непряма передача в `avalues`:** Масив `avalues` містить не самі значення аргументів, а **покажчики на ці значення**. Якщо функція приймає число `int x = 42`, то `values[0]` має містити `&x`, а не число `42`. Передача сирого значення замість покажчика призведе до того, що асемблерний міст розіменує число `42` як адресу пам'яті, викликавши помилку сегментації (Segmentation Fault).
2. **Розмір буфера `rvalue` та просування типів:** Якщо функція повертає тип, менший за розмір машинного слова (наприклад, `uint8_t`, `int16_t` або `bool`), асемблерний код libffi на більшості 64-бітних архітектур записує в буфер `rvalue` повне 64-бітне значення регістра `%rax` (`ffi_arg`). Якщо викликач виділить під результат лише 1 або 2 байти на стеку, виклик `ffi_call()` перезапише сусідні 6 байтів стека, що спричинить важковловиме пошкодження кадру виклику. Буфер `rvalue` повинен мати розмір щонайменше `sizeof(ffi_arg)` (8 байтів на 64-бітних CPU).
3. **Час життя масиву `arg_types`:** Структура `ffi_cif` не копіює масиви описів типів, а зберігає прямий покажчик на масив `arg_types`, переданий у `ffi_prep_cif()`. Якщо цей масив було виділено на локальному стеку функції підготовки й цей стек звільнився до виклику `ffi_call()`, бібліотека звернеться до сміття. Масив `arg_types` мусить залишатися валідним у пам'яті протягом усього життєвого циклу `ffi_cif`.
