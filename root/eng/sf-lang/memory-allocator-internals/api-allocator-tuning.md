# 📋 Інтерфейс системного налаштування й діагностики алокатора

Стандартний інтерфейс виділення пам'яті POSIX (`malloc`, `free`, `realloc`, `calloc`) свідомо спрощений: він приймає лише кількість байтів і повертає нетипізований покажчик `void*`. Проте за цим простим фасадом приховані складні евристичні механізми керування аренами, порогами виклику `mmap`, кешами потоків та тримінгом сторінок.

У високонавантажених серверах, контейнеризованих мікросервісах із жорсткими лімітами пам'яті (cgroups) та базах даних стандартні налаштування алокатора за замовчуванням можуть призводити до несподіваного розростання віртуального адресного простору (VSZ), надлишкового утримання фізичних сторінок (RSS) або високої міжпотокової конкуренції на м'ютексах.

Системні бібліотеки C — насамперед GNU C Library (`ptmalloc`) та `jemalloc` — надають спеціалізовані програмні інтерфейси та системні змінні оточення для тонкого налаштування поведінки алокатора без необхідності модифікації коду всієї програми.

### Програмний інтерфейс GNU libc (`malloc.h`)

Бібліотека GNU libc надає розширений заголовок `<malloc.h>`, який містить функції інспектування внутрішньої статистики та зміни системних параметрів `ptmalloc`.

#### 1. Тонке налаштування параметрів: `mallopt`

Функція `mallopt` дозволяє динамічно змінювати глобальні конфігураційні прапорці алокатора:

:::tabs
```c
#include <malloc.h>

// Змінює системний параметр param на значення value
int mallopt(int param, int value);
```
```cpp
#include <malloc.h>

// C++ інтерфейс виклику mallopt у просторі імен глобальних системних викликів
extern "C" int mallopt(int param, int value);
```
:::

Нижче наведено огляд головних керуючих параметрів:

| Параметр `mallopt` | Призначення та вплив на поведінку пам'яті | Значення за замовчуванням |
|---|---|---|
| `M_ARENA_MAX` | Встановлює верхню межу кількості одночасно створюваних арен пам'яті. Зменшення параметра (наприклад, до `2` або `4`) суттєво скорочує використання віртуальної пам'яті процесом ціною незначного підвищення міжпотокової конкуренції. | `8 × N_cores` (64-bit) |
| `M_MMAP_THRESHOLD` | Поріг розміру запиту в байтах, починаючи з якого алокатор оминає арени й виділяє пам'ять окремим викликом `mmap`. Зменшення порогу зменшує фрагментацію основної купи. | Динамічний (`128 КіБ – 32 МіБ`) |
| `M_TRIM_THRESHOLD` | Поріг вільної неперервної пам'яті на верхівці купи `brk`, при перевищенні якого виклик `free()` автоматично викликає `sbrk(-N)` для повернення пам'яті операційній системі. | `128 КіБ` |
| `M_TOP_PAD` | Обсяг додаткової пам'яті в байтах, який алокатор резервує про запас під час кожного виклику розширення купи `sbrk`. Зменшує кількість дорогих системних викликів. | `128 КіБ` |
| `M_PERTURB` | Якщо параметр встановлено у ненульове значення `N`, байти нововиділеної пам'яті заповнюються значенням `~N`, а звільнені — `N`. Дозволяє виявляти баги читання сміття та Use-After-Free. | `0` (вимкнено) |

#### 2. Примусове повернення пам'яті: `malloc_trim`

Функція `malloc_trim` змушує алокатор вивільнити всю невикористану пам'ять із верхівки головної купи `brk` та допоміжних арен, повертаючи сторінки операційній системі через `sbrk` або `madvise(MADV_DONTNEED)`:

:::tabs
```c
#include <malloc.h>

// Звільняє невикористану пам'ять, залишаючи pad байтів запасу на верхівці
int malloc_trim(size_t pad);
```
```cpp
#include <malloc.h>

// Примусове повернення пам'яті ядру ОС
extern "C" int malloc_trim(size_t pad);
```
:::

Функція повертає `1`, якщо вдалося реально вивільнити пам'ять і зменшити споживання процесу, або `0`, якщо вільних блоків на межі купи не виявлено.

#### 3. Діагностика та метрики: `malloc_stats` та `mallinfo2`

Для моніторингу витоків пам'яті, внутрішніх резервів та фрагментації застосовують діагностичні функції:

:::tabs
```c
#include <malloc.h>

// Виводить детальний текстовий звіт про стан усіх арен безпосередньо у потік stderr
void malloc_stats(void);

// Повертає структуру з точними 64-бітними лічильниками розподілу пам'яті
struct mallinfo2 mallinfo2(void);
```
```cpp
#include <malloc.h>

// Діагностичні інтерфейси GNU libc
extern "C" void malloc_stats(void) noexcept;
extern "C" struct mallinfo2 mallinfo2(void) noexcept;
```
:::

Поля структури `struct mallinfo2` надають точну інформацію про внутрішню бухгалтерію:
- `arena` — сумарний обсяг пам'яті у байтах, виділений під традиційну купу через `sbrk`;
- `hblkhd` — сумарний обсяг пам'яті у байтах, виділений під великі блоки через `mmap`;
- `uordblks` — обсяг пам'яті, який безпосередньо зайнятий активними виділеннями користувача;
- `fordblks` — сумарний обсяг вільної пам'яті, що утримується всередині внутрішніх списків алокатора (кешований резерв, ще не повернутий системі).

Співвідношення `fordblks / arena` слугує числовим індикатором зовнішньої фрагментації пам'яті процесу.

### Керування алокатором через змінні оточення та GLIBC_TUNABLES

Поведінку алокатора можна модифікувати під час запуску виконуваного файлу без внесення змін до вихідного коду програми:

```bash
# 1. Обмеження кількості арен для мінімізації споживання пам'яті в Docker
MALLOC_ARENA_MAX=2 ./backend_service

# 2. Фіксація порогу виділення через mmap на рівні 64 КіБ
MALLOC_MMAP_THRESHOLD_=65536 ./backend_service

# 3. Увімкнення суворої перевірки пошкодження цілісності купи (діагностика багів)
MALLOC_CHECK_=3 ./debug_binary

# 4. Тонке налаштування потокового кешу tcache через GLIBC_TUNABLES (glibc 2.34+)
GLIBC_TUNABLES="glibc.malloc.tcache_max=1024:glibc.malloc.tcache_count=16" ./app
```

Механізм `GLIBC_TUNABLES` є сучасним стандартом конфігурації у дистрибутивах Linux. Він дозволяє задавати:
- `glibc.malloc.tcache_max` — максимальний розмір чанка в байтах, який дозволено розміщувати у швидкому потоковому кеші `tcache` (за замовчуванням `1032` байти);
- `glibc.malloc.tcache_count` — максимальна кількість чанків одного розмірного класу, яка може одночасно утримуватися в кеші потоку (за замовчуванням `7` штук);
- `glibc.malloc.tcache_unsorted_limit` — ліміт розміру для перенесення з невпорядкованого кошика;
- `glibc.malloc.mmap_max` — максимальна кількість одночасно відкритих анонімних відображень `mmap`.

### Модель затухання сторінок у jemalloc: `mallctl` та Decay Purging

Якщо застосунок скомпільовано або запущено з алокатором `jemalloc`, керування та моніторинг здійснюються через ієрархічне дерево параметрів `mallctl`:

:::tabs
```c
#include <jemalloc/jemalloc.h>

// Читання та запис параметрів jemalloc через рядковий MIB-інтерфейс
int mallctl(const char *name, void *oldp, size_t *oldlenp, void *newp, size_t newlen);
```
```cpp
#include <jemalloc/jemalloc.h>

// Інтерфейс mallctl у середовищі C++
extern "C" int mallctl(const char *name, void *oldp, size_t *oldlenp, void *newp, size_t newlen) noexcept;
```
:::

У `jemalloc` реалізовано трифазну модель життєвого циклу сторінок (*Decay-based Purging*):
1. **Dirty (Брудні):** сторінки містять звільнені дані користувача й залишаються в пам'яті DRAM для швидкого повторного виділення без сторінкових збоїв.
2. **Muzzy (Напіввивільнені):** сторінки, для яких викликано `madvise(MADV_FREE)`. Ядро звільнить їх лише у випадку загальної нестачі оперативної пам'яті.
3. **Clean (Чисті):** сторінки, для яких викликано `madvise(MADV_DONTNEED)` або `munmap`. Вони негайно повертаються ядру.

Параметри `dirty_decay_ms` та `muzzy_decay_ms` задають час (у мілісекундах), за який вільні сторінки плавно переходять між станами за сигмоїдною кривою. Це запобігає різким стрибкам завантаження процесора на системні виклики очищення:

```bash
# Плавне повернення пам'яті ядру протягом 5 секунд (5000 мс)
MALLOC_CONF="dirty_decay_ms:5000,muzzy_decay_ms:10000" ./app

# Увімкнення профілювання пам'яті на льоту без перекомпіляції
MALLOC_CONF="prof:true,prof_prefix:jeprof.out,prof_active:true" ./app
```

### Простеження стану пам'яті на рівні ядра Linux

Щоб оцінити реальний вплив налаштувань алокатора на споживання ресурсів комп'ютера, розробник повинен зіставляти внутрішні метрики `mallinfo2` із системними показниками ядра через віртуальну файлову систему `/proc`:

1. **Файл `/proc/[pid]/status`:**
   - `VmSize` — сумарний розмір віртуального адресного простору процесу (включно з усіма зарезервованими аренами);
   - `VmRSS` (*Resident Set Size*) — обсяг фізичної пам'яті DRAM, яка реально закріплена за процесом у цей момент;
   - `RssAnon` — фізична пам'ять, зайнята анонімними даними купи (найважливіший показник для детекції витоків);
   - `RssFile` — сторінки виконуваного коду та динамічних бібліотек, завантажених із диска.

2. **Файл `/proc/[pid]/smaps_rollup`:**
   Надає миттєвий зведений звіт про використання сторінок процесу без високих накладних витрат на парсинг окремих діапазонів `maps`. Дозволяє побачити лічильник `LazyFree` — обсяг сторінок, для яких виконано `madvise(MADV_FREE)`, але які ядро ще не встигло відібрати.

### Практичний приклад утиліти діагностики та очищення пам'яті

Наведемо повноцінний інженерний приклад на мовах C та C++, що демонструє зміну параметрів `M_ARENA_MAX`, вимірювання обсягу внутрішніх резервів через `mallinfo2` та примусовий тримінг сторінок.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <malloc.h>

void print_allocator_state(const char* checkpoint_label) {
    struct mallinfo2 info = mallinfo2();
    printf("[%s]\n", checkpoint_label);
    printf("  Купа (arena):        %8zu КіБ\n", info.arena / 1024);
    printf("  Блоки mmap (hblkhd): %8zu КіБ\n", info.hblkhd / 1024);
    printf("  Зайнято (uordblks):  %8zu КіБ\n", info.uordblks / 1024);
    printf("  Резерв (fordblks):   %8zu КіБ\n", info.fordblks / 1024);
}

int main(void) {
    // 1. Обмежуємо максимальну кількість арен двома
    mallopt(M_ARENA_MAX, 2);

    print_allocator_state("Початковий стан");

    // 2. Інтенсивне виділення 1000 блоків по 16 КіБ (сумарно 16 МіБ)
    void* buffers[1000];
    for (int i = 0; i < 1000; i++) {
        buffers[i] = malloc(16 * 1024);
    }
    print_allocator_state("Після виділення 16 МіБ");

    // 3. Звільнення всіх блоків
    for (int i = 0; i < 1000; i++) {
        free(buffers[i]);
    }
    print_allocator_state("Після free() (пам'ять у внутрішньому резерві)");

    // 4. Примусовий тримінг пам'яті назад ядру операційної системи
    int trimmed = malloc_trim(0);
    printf("Результат malloc_trim: %s\n", trimmed ? "успішно" : "без змін");

    print_allocator_state("Після malloc_trim()");

    return 0;
}
```
```cpp
#include <iostream>
#include <vector>
#include <memory>
#include <span>
#include <malloc.h>

struct MemorySnapshot {
    size_t arena_kb{0};
    size_t mmap_kb{0};
    size_t in_use_kb{0};
    size_t free_cached_kb{0};

    [[nodiscard]] static MemorySnapshot capture() noexcept {
        const auto info = mallinfo2();
        return MemorySnapshot{
            .arena_kb = info.arena / 1024,
            .mmap_kb = info.hblkhd / 1024,
            .in_use_kb = info.uordblks / 1024,
            .free_cached_kb = info.fordblks / 1024
        };
    }
};

std::ostream& operator<<(std::ostream& os, const MemorySnapshot& s) {
    os << "  Купа (arena):        " << s.arena_kb << " КіБ\n"
       << "  Блоки mmap (hblkhd): " << s.mmap_kb << " КіБ\n"
       << "  Зайнято (in_use):    " << s.in_use_kb << " КіБ\n"
       << "  Резерв (free_cache): " << s.free_cached_kb << " КіБ";
    return os;
}

int main() {
    // 1. Конфігурація алокатора
    mallopt(M_ARENA_MAX, 2);

    std::cout << "[Початковий стан]\n" << MemorySnapshot::capture() << "\n\n";

    // 2. Блок виділення пам'яті з використанням RAII
    {
        std::vector<std::unique_ptr<char[]>> buffers;
        buffers.reserve(1000);
        for (size_t i = 0; i < 1000; ++i) {
            buffers.push_back(std::make_unique<char[]>(16 * 1024));
        }
        std::cout << "[Після виділення 16 МіБ]\n" << MemorySnapshot::capture() << "\n\n";
    }

    std::cout << "[Після знищення vector (пам'ять повернуто в списки)]\n"
              << MemorySnapshot::capture() << "\n\n";

    // 3. Примусове скидання сторінок ядру
    const int result = malloc_trim(0);
    std::cout << "Результат malloc_trim: " << (result ? "успішно" : "без змін") << "\n";
    std::cout << "[Після malloc_trim()]\n" << MemorySnapshot::capture() << "\n";

    return 0;
}
```

### Типові виробничі сценарії та підводні камені

1. **Мікросервіси в Kubernetes під загрозою OOMKilled:** якщо контейнер має ліміт пам'яті 512 МБ, але запущений на 64-ядерному сервері, `ptmalloc` створить до 512 арен. Кожна арена попередньо резервує пам'ять віртуальними сторінками, що провокує раптове перевищення ліміту `memory.max` і примусове аварійне вбивство контейнера ядром Linux. Встановлення змінної `MALLOC_ARENA_MAX=2` або `4` обмежує кількість арен і утримує процес у межах виділеної квоти.
2. **Сервери пакетної обробки (Batch Jobs):** після виконання важкої фази індексації або обробки великих JSON-документів мільйони звільнених об'єктів залишаються в кошиках алокатора. Виклик `malloc_trim(0)` після завершення пакетного завдання дозволяє негайно повернути фізичні кадри DRAM операційній системі без перезапуску процесу.
3. **Пастка різниці між `MADV_DONTNEED` та `MADV_FREE`:** прапорець `MADV_DONTNEED` негайно скидає сторінки DRAM, зменшуючи лічильник `VmRSS` процесу. Натомість прапорець `MADV_FREE` (вживаний деякими версіями jemalloc) лише позначає сторінки як «ліниво вивільнювані»: ядро забирає їх лише за умови виникнення загального дефіциту оперативної пам'яті на сервері. Це призводить до того, що моніторингові системи Prometheus/Grafana показують високе фіктивне споживання пам'яті процесом, хоча фактично пам'ять вільна.
