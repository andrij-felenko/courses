# 📋 Специфікація інтерфейсу та політик стійкого кешування

Налаштування кешування в розподілених системах часто зводять до єдиного числового параметра `ttl_seconds`. Такий спрощений інтерфейс приховує справжню поведінку системи під час збоїв, не дозволяє гнучко регулювати випадковий розкид часу життя, кешування порожнечі чи асинхронну фонову ревалідацію, а також унеможливлює повноцінний моніторинг стану оперативної пам'яті через промислові метрики.

Промисловий контракт стійкого кешування поєднує параметри конфігурації часу життя, структури повернення діагностичних метаданих, типові виробничі профілі навантаження, правила автоматичного оповіщення (Alerting) та інтерфейси розподіленої спостережуваності (англ. *observability*).

## 1. Структура конфігурації політик (`CachePolicyOptions`)

Кожен простір назв або тип сутності конфігурується незалежною структурою параметрів, яка визначає поведінку записів на всіх етапах життєвого циклу:

| Поле конфігурації | Тип | Типове значення | Опис та інженерне призначення |
| :--- | :--- | :--- | :--- |
| `base_ttl_sec` | `uint32` | `3600` | Базовий номінальний час життя свіжого запису в кеші. |
| `jitter_ratio` | `float32` | `0.15` | Коефіцієнт випадкового розкиду (`±15 %`). Розраховує `TTL_actual = base_ttl · (1 ± jitter)`. |
| `negative_ttl_sec`| `uint32` | `60` | Час життя маркера порожнього результату (404) для захисту від проникнення. |
| `soft_ttl_ratio` | `float32` | `0.75` | Частка від `base_ttl`, після якої вмикається фонове оновлення Stale-While-Revalidate (`Soft TTL`). |
| `xfetch_beta` | `float32` | `1.00` | Коефіцієнт агресивності алгоритму імовірнісного оновлення XFetch (`0.0` вимикає XFetch). |
| `stale_if_error` | `bool` | `true` | Дозвіл віддавати застарілі дані у разі повної відмови первинної бази даних (Stale Fallback). |
| `max_stale_sec` | `uint32` | `86400` | Максимальний додатковий час, протягом якого дозволено віддавати застарілі дані під час аварії СУБД. |
| `max_capacity` | `uint64` | `100000` | Ліміт кількості записів у пам'яті для захисту від переповнення за політикою W-TinyLFU / LRU. |
| `async_threads` | `uint16` | `8` | Розмір фіксованого пулу воркерів для виконання асинхронних рейсів оновлення. |

### Правила взаємної валідації параметрів
Під час ініціалізації конфігурації клієнт перевіряє такі інваріанти:
1. `soft_ttl_ratio` повинен суворо належати інтервалу `(0.0, 1.0)`. Встановлення значення `1.0` вимикає вікно Stale-While-Revalidate, зводячи роботу системи до звичайного блокуючого кешу.
2. `negative_ttl_sec` повинен бути суттєво меншим за `base_ttl_sec` (як правило, не більше 5–10 % від базового TTL). Занадто довге кешування порожнечі створює ризик тривалого розходження стану, якщо неіснуюча сутність буде створена невдовзі після запису маркера.
3. `jitter_ratio` рекомендується в діапазоні `[0.05, 0.25]`. Менше значення не забезпечує достатнього розмазування піків вичерпання, а більше призводить до передчасного виселення записів.

## 2. Статуси повернення та метадані результату

Під час виконання операції читання клієнт повертає корисні дані разом із діагностичними метаданими:

```
enum CacheLookupStatus {
    STATUS_FRESH_HIT      = 0,  // Значення актуальне (t < Soft TTL), прочитано з RAM
    STATUS_STALE_HIT      = 1,  // Значення застаріле (Soft TTL <= t < Hard TTL), запущено фоновий рейс
    STATUS_NEGATIVE_HIT   = 2,  // Знайдено маркер відсутності (сутності не існує в базі, 404)
    STATUS_HARD_MISS      = 3,  // Синхронний промах, виконано блокуюче завантаження з джерела
    STATUS_FALLBACK_STALE = 4,  // Джерело повернуло помилку, віддано застарілий стан для порятунку проду
    STATUS_ERROR          = 5   // Помилка джерела за відсутності будь-яких закешованих даних
};
```

### Метадані відповіді (`CacheResponseMetadata`)

| Поле метаданих | Тип | Опис значення |
| :--- | :--- | :--- |
| `status` | `CacheLookupStatus` | Детальний результат проходження запиту через рівні кешування. |
| `age_seconds` | `float64` | Кількість секунд, що минули з моменту збереження корисного навантаження. |
| `ttl_remaining_sec`| `float64` | Залишок часу до настання абсолютного виселення `Hard TTL`. |
| `is_stale` | `bool` | Прапорець того, що повернуті дані не є гарантовано свіжими. |
| `backend_latency_ms`| `float64` | Час звернення до первинного сховища (0 для чистих влучань у пам'ять). |

## 3. Типові виробничі профілі налаштувань

Залежно від бізнес-вимог до узгодженості та навантаження на систему застосовують три стандартні конфігураційні профілі:

### Профіль А: Каталог товарів та публічний контент (Read-Heavy Hot Data)
Призначений для карток товарів, статей, категорій та головних сторінок, де допустиме невелике запізнення оновлення заради максимальної пропускної здатності:
- `base_ttl_sec = 7200` (2 години);
- `jitter_ratio = 0.20` (розкид ±24 хвилини);
- `soft_ttl_ratio = 0.70` (фонове оновлення починається через 1.4 години);
- `xfetch_beta = 1.2` (агресивне попереджувальне оновлення для найгарячіших товарів);
- `negative_ttl_sec = 60` (захист від скрапінгу та ботів);
- `stale_if_error = true`, `max_stale_sec = 86400` (під час падіння СУБД каталог залишається доступним для перегляду протягом доби).

### Профіль Б: Профілі користувачів та налаштування (Moderately Dynamic Data)
Призначений для даних особистих кабінетів, де важлива оперативна видимість змін після редагування:
- `base_ttl_sec = 1800` (30 хвилин);
- `jitter_ratio = 0.10` (розкид ±3 хвилини);
- `soft_ttl_ratio = 0.85`;
- `xfetch_beta = 0.0` (детерміноване Soft TTL оновлення без XFetch);
- `negative_ttl_sec = 30`;
- `stale_if_error = true`, `max_stale_sec = 3600`;
- Обов'язкова пряма інвалідація ключа за подією мутації через шину Pub/Sub.

### Профіль В: Перевірка прав доступу та безпека (Security & Authorisation)
Призначений для ролей, прав та блокувань акаунтів, де застарілі дані несуть прямі ризики безпеки:
- `base_ttl_sec = 60` (1 хвилина);
- `jitter_ratio = 0.05`;
- `soft_ttl_ratio = 0.90`;
- `xfetch_beta = 0.0`;
- `negative_ttl_sec = 10` (швидка реакція на розблокування користувача);
- `stale_if_error = false` (категорично заборонено віддавати застарілі права, якщо база авторизації недоступна — система повертає відмову в доступі `403/500`).

## 4. Словник метрик спостережуваності (Prometheus)

Для діагностики та налаштування сповіщень система експортує повний набір лічильників, гістограм та показників стану:

### Лічильники запитів (Counters)
- `cache_requests_total{namespace="...", status="fresh_hit|stale_hit|negative_hit|hard_miss|fallback_stale|error"}` — загальна кількість звернень за статусами.
- `cache_async_refreshes_total{namespace="...", result="success|failure|dropped_queue_full"}` — кількість асинхронних рейсів фонового оновлення.
- `cache_negative_writes_total{namespace="..."}` — кількість збережених маркерів порожнечі.
- `cache_invalidation_events_total{namespace="...", type="direct|namespace_bump|pubsub"}` — кількість операцій інвалідації.

### Гістограми розподілу часу (Histograms)
- `cache_lookup_duration_seconds{namespace="...", hit_type="memory|network_l2"}` — розподіл затримок читання з локальної пам'яті (L1) та Redis (L2).
- `cache_stale_serving_age_seconds{namespace="..."}` — вік застарілих даних, що повертаються клієнтам під час фонової ревалідації.
- `cache_backend_refresh_duration_seconds{namespace="..."}` — тривалість виконання SQL-запитів фоновими потоками.

### Показники стану (Gauges)
- `cache_entries_count{namespace="...", type="positive|negative"}` — поточна кількість активних ключів у пам'яті.
- `cache_memory_used_bytes{namespace="..."}` — обсяг пам'яті, виділений під структуру кешу.
- `cache_async_queue_depth{namespace="..."}` — кількість завдань у черзі очікування пулу фонових воркерів.

## 5. Правила моніторингу та оповіщення (Alerting Rules)

На базі експортованих метрик налаштовують такі виробничі правила для виявлення деградації кешу до настання відмови:

1. **Аварійне падіння частки влучань (Hit Ratio Drop):**
   Якщо частка влучань для простору падає нижче 85 % протягом трьох хвилин, це свідчить про лавиноподібне вичерпання або засмічення кешу сканами.
   Вираз PromQL:
   `sum(rate(cache_requests_total{status=~"fresh_hit|stale_hit|negative_hit"}[3m])) / sum(rate(cache_requests_total[3m])) < 0.85`

2. **Переповнення черги фонової ревалідації (Async Worker Saturation):**
   Якщо кількість завдань у черзі фонового пулу наближається до ліміту, фонові оновлення починають відкидатися, що призведе до синхронних промахів.
   Вираз PromQL:
   `cache_async_queue_depth > 50`

3. **Сплеск віддачі аварійного застарілого кешу (Stale Fallback Spike):**
   Зростання показника `fallback_stale` сигналізує про деградацію або падіння первинної бази даних, хоча користувачі ще не бачать помилок 500.
   Вираз PromQL:
   `rate(cache_requests_total{status="fallback_stale"}[1m]) > 10`

## 6. Інтеграція з протоколами HTTP, gRPC та OpenTelemetry

При використанні кеш-клієнта на рівні HTTP API Gateway або зворотного проксі метадані транслюються у стандартні заголовки HTTP/1.1 та HTTP/2:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=300, stale-while-revalidate=3300, stale-if-error=86400
Age: 420
Warning: 110 - "Response is Stale"
X-Cache-Status: STALE_HIT
X-Cache-Namespace: catalog_products
```

У разі повернення негативного кешу клієнт автоматично формує статус `404 Not Found` із заголовком `Cache-Control: max-age=60`, що запобігає повторному транзиту однакових запитів через зовнішні CDN-мережі та захищає шлюзи від перевантаження.

Для мікросервісів на базі gRPC метадані кешу передаються через трейлери виклику (англ. *gRPC Trailers / Metadata*):
- `x-cache-status: STALE_HIT` — інформує викликаючий сервіс про статус відповіді;
- `x-cache-age: 420` — вік запису в секундах;
- Якщо результат є негативним кешем, gRPC-сервіс негайно повертає канонічний код помилки `codes.NotFound` («NOT_FOUND»), уникаючи відкриття важких RPC-каналів до бекенд-сервісів або сховищ даних.

У системі розподіленого трасування (OpenTelemetry / Jaeger) кожен виклик операції кешування додає атрибути спану:
- `cache.status = "stale_hit"`;
- `cache.key = "product:4192"`;
- `cache.namespace = "catalog_products"`;
- `cache.item_age_seconds = 420.5`.

Якщо операція ініціює фоновий рейс оновлення, створюється дочірній асинхронний спан `cache.background_refresh` із посиланням на батьківський контекст (`SpanContext`), що дозволяє інженерам відстежувати повний ланцюг затримок від клієнтського запиту до SQL-виклику в СУБД.
