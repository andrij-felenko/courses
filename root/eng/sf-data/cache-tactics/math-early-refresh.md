# 🧮 Математичне обґрунтування раннього імовірнісного оновлення XFetch

Коли термін придатності гарячого ключа в кеші добігає кінця, традиційний підхід очікує повного настання моменту вичерпання TTL. У цю мить перший наступний клієнтський запит неминуче отримує промах і змушений чекати повний час обчислення нового значення в базі даних `Δ`. Якщо ключ читають тисячі разів на секунду, навіть за наявності локального блокування Single-Flight виникає відчутний сплеск затримки для першого запиту, а в разі затримки обчислення або збою бази даних — ціла черга завислих клієнтських потоків.

Цей розділ наводить математичну модель та аналітичне виведення алгоритму раннього імовірнісного оновлення (англ. *probabilistic early expiration*, відомого як алгоритм XFetch, запропонований Ваттані, К'єрікетті та Левенштейном), який завчасно й асинхронно ініціює перерахунок даних у фоні, зводячи ймовірність синхронного промаху до нуля за мінімальної кількості додаткових звернень до сховища.

## 1. Постановка задачі та ймовірнісна модель

Нехай до гарячого ключа надходить стаціонарний пуассонівський потік запитів на читання з інтенсивністю `λ` (кількість клієнтських запитів за одну секунду).

Параметри системи:
- `T` — номінальний час життя запису в кеші (англ. *Time To Live*, TTL) у секундах;
- `Δ` — час, необхідний для обчислення або зчитування свіжого значення з первинного джерела (бази даних чи віддаленого мікросервісу);
- `t` — поточний момент часу, виміряний від миті збереження запису в кеш (`0 ≤ t ≤ T`);
- `T − t` — залишковий час життя запису;
- `β > 0` — безрозмірний коефіцієнт агресивності оновлення (конфігураційний параметр).

Якщо система намагається оновлювати кеш суто детерміновано за фіксований час `t_refresh = T − Δ`, виникає дві фундаментальні проблеми:
1. Якщо в часовому вікні `[T − Δ, T]` не надійде жодного запиту (наприклад, через тимчасове зниження активності), детермінований таймер не спрацює заздалегідь, і ключ усе одно вичерпається, спричинивши промах для наступного запиту.
2. Якщо в це вікно потрапить одночасно кілька десятків інстансів застосунку без централізованого координатора, усі вони детерміновано побачать необхідність оновлення рівно в один і той самий момент часу, створивши небажаний паралельний шторм запитів до первинної бази даних.

Тому ймовірність того, що запит, який надійшов у момент часу `t`, запустить фоновий перерахунок, повинна плавно й монотонно зростати в міру наближення `t` до `T`.

## 2. Ймовірнісна функція спрацьовування та нерівність XFetch

Алгоритм XFetch визначає, що під час кожного запиту на читання в момент часу `t` генерується псевдовипадкова величина `U`, рівномірно розподілена на неперервному інтервалі `(0, 1]`, тобто `U ~ Uniform(0, 1]`.

Умова ініціалізації фонового оновлення формулюється як нерівність:

```
−β · Δ · ln(U) > T − t
```

Перетворимо цю нерівність за правилами алгебри, щоб виразити точну ймовірність `P_refresh(t)` того, що окремий запит у момент `t` запустить оновлення:

```
−β · Δ · ln(U) > T − t
ln(U) < −(T − t) / (β · Δ)        [поділили на від'ємну величину −β · Δ з розворотом знака нерівності]
U < exp(−(T − t) / (β · Δ))       [експоненціювання обох частин нерівності]
```

Оскільки випадкова величина `U` розподілена рівномірно на інтервалі `(0, 1]`, функція розподілу ймовірностей для `x ∈ (0, 1]` має вигляд `P(U < x) = x`. Звідси отримуємо аналітичний вираз для ймовірності запуску оновлення під час одного звернення:

```
P_refresh(t) = exp(−(T − t) / (β · Δ))
```

Аналіз поведінки функції:
1. Коли запис щойно створено (`t = 0` за умови `T ≫ β · Δ`), залишок часу великий, тому степінь є великим від'ємним числом: `exp(−T / (β · Δ)) ≈ 0`. Ймовірність передчасного оновлення практично нульова.
2. Коли час добігає кінця (`t → T`), залишок `T − t → 0`, показник степеня прямує до нуля: `exp(0) = 1`. Ймовірність запуску оновлення досягає 100 %.
3. Що довший час обчислення `Δ`, то ширшим стає вікно попереджувального оновлення, гарантуючи, що ресурсомісткі запити почнуть обчислюватися заздалегідь.

## 3. Ймовірність синхронного промаху для потоку запитів

Обчислимо ймовірність того, що за весь період життя ключа `[0, T]` жоден із запитів вхідного пуассонівського потоку не запустить фонового оновлення, внаслідок чого ключ згасне й система отримає холодний промах (англ. *cache miss*).

Оскільки потік запитів на читання є пуассонівським з інтенсивністю `λ`, процес ініціації оновлень є неоднорідним пуассонівським процесом зі змінною в часі інтенсивністю:

```
λ_refresh(t) = λ · P_refresh(t) = λ · exp(−(T − t) / (β · Δ))
```

Очікувана кількість ініціацій оновлення `E[N]` за весь період життя запису `[0, T]` дорівнює визначеному інтегралу від інтенсивності:

```
E[N]
= ∫₀ᵀ λ_refresh(t) dt             [інтегрування сумарної інтенсивності за часом життя]
= λ · ∫₀ᵀ exp(−(T − t) / (β · Δ)) dt  [винесення константи швидкості потоку λ за знак інтеграла]
= λ · [β · Δ · exp(−(T − t) / (β · Δ))]₀ᵀ  [обчислення первісної експоненційної функції]
= λ · β · Δ · (exp(0) − exp(−T / (β · Δ)))  [підстановка верхньої та нижньої меж інтегрування]
= λ · β · Δ · (1 − exp(−T / (β · Δ)))       [спрощення значення в точці t = T: exp(0) = 1]
```

Оскільки для будь-якої практичної системи кешування час життя значно перевищує тривалість обчислення (`T ≫ β · Δ`), доданок `exp(−T / (β · Δ))` є зникаюче малим (`< 10⁻⁶`). Звідси маємо просту й точну апроксимацію:

```
E[N] ≈ λ · β · Δ
```

Ймовірність нульової кількості спрацьовувань оновлення до настання моменту `T` (тобто ймовірність виникнення синхронного промаху `P_miss`) за пуассонівським розподілом дорівнює:

```
P_miss
= exp(−E[N])                      [нульовий член пуассонівського розподілу імовірностей]
= exp(−λ · β · Δ)                 [підстановка математичного сподівання кількості подій]
```

Розглянемо практичний розрахунок для гарячої сутності в електронній комерції:
- Інтенсивність звернень: `λ = 120` запитів на секунду;
- Час виконання складного аналітичного SQL-запиту: `Δ = 0.04` с (40 мс);
- Коефіцієнт агресивності: `β = 1.0`.

Обчислимо очікувану кількість оновлень та підсумкову ймовірність промаху:

```
λ · β · Δ
= 120 · 1.0 · 0.04
= 4.8                             [середня кількість фонових оновлень у вікні переходу]
```

```
P_miss
= exp(−4.8)
≈ 0.0082                          [ймовірність промаху складає лише 0.82 %]
```

Якщо збільшити коефіцієнт `β` до `1.5`, показник степеня зростає до `7.2`, а ймовірність промаху падає до `exp(−7.2) ≈ 0.00074` (менше 0.08 %).

## 4. Оптимізація коефіцієнта агресивності та баланс витрат

Параметр `β` регулює фундаментальний компроміс між надійністю захисту від промахів та обчислювальною ціною зайвих фонових оновлень.

Введемо функцію втрат системи:
- `C_miss` — штраф за синхронний промах (затримка користувача, блокування пулу потоків, ризик каскадного перевантаження);
- `C_calc` — фінансова та ресурсна вартість одного повторного обчислення значення в базі даних.

Сумарні очікувані витрати на один життєвий цикл запису описуються виразом:

```
Cost(β) = C_miss · exp(−λ · β · Δ) + C_calc · (1 + λ · β · Δ)
```

Щоб знайти оптимальне значення `β*`, візьмемо похідну за параметром `β` і прирівняємо її до нуля:

```
d(Cost) / dβ
= −C_miss · λ · Δ · exp(−λ · β · Δ) + C_calc · λ · Δ  [взяття похідної від сумарних витрат]
= 0                               [умова екстремуму функції втрат]
```

Розв'яжемо рівняння відносно `β`:

```
C_miss · exp(−λ · β · Δ) = C_calc  [скорочення спільного множника λ · Δ]
exp(−λ · β · Δ) = C_calc / C_miss  [поділ на штраф промаху C_miss]
−λ · β · Δ = ln(C_calc / C_miss)   [логарифмування обох частин рівняння]
β* = ln(C_miss / C_calc) / (λ · Δ) [вираження оптимального коефіцієнта агресивності]
```

Якщо ціна падіння бази від промаху в тисячу разів перевищує вартість окремого SQL-запиту (`C_miss / C_calc = 1000`), оптимальний поріг становить:

```
ln(1000) / (λ · Δ) ≈ 6.91 / (λ · Δ)
```

На практиці для високонавантажених сервісів встановлюють `β = 1.0`, що забезпечує майже ідеальний компроміс: очікувана кількість оновлень рідко перевищує 1.2–1.5 на цикл за повного усунення піків очікування.

## 5. Динамічне оцінювання затримки бекенду (EWMA)

У реальних виробничих середовищах час обчислення `Δ` не є фіксованою константою — він коливається через навантаження на диск, мережеві затримки та паузи збирача сміття.

Якщо зашити в конфігурацію статичне `Δ = 50 мс`, а база сповільниться до 300 мс під час вечірнього піку, ймовірнісне вікно виявиться замалим, і система отримає шторм промахів.

Для захисту від дрейфу затримки значення `Δ` оновлюють динамічно після кожного успішного фонового обчислення через експоненційно зважене ковзне середнє (англ. *Exponentially Weighted Moving Average*, EWMA):

```
Δ_new = α · Δ_measured + (1 − α) · Δ_previous
```

де `α ∈ [0.1, 0.2]` — коефіцієнт згладжування. Таке адаптивне коригування автоматично розширює вікно XFetch при сповільненні бекенду, зберігаючи нульову частку промахів навіть за умов деградації первинного сховища.
