# 📋 Довідник конфігурації та налаштування VACUUM і Purge

Управління життєвим циклом застарілих версій кортежів (Dead Tuples) та своєчасне очищення журналів відкату є критично важливими аспектами системного адміністрування та проектування архітектури реляційних баз даних. Неправильне налаштування параметрів фонового очищення призводить до неконтрольованого розростання таблиць (Table Bloat), незворотної деградації продуктивності дискової підсистеми I/O, вимивання кешу буферного пулу та ризику аварійної зупинки СУБД внаслідок вичерпання простору 32-бітного лічильника ідентифікаторів транзакцій.

Цей довідник містить вичерпний опис інтерфейсів керування процесами `VACUUM` у PostgreSQL та підсистемою `Purge` у MySQL InnoDB, включаючи повний реєстр системних каталогів, детальний аналіз формул тригерів спрацьовування, алгоритми розрахунку дискових витрат та виробничі діагностичні SQL-запити.

### Системні команди та інтерфейс VACUUM у PostgreSQL

У PostgreSQL процес очищення табличного простору викликається за допомогою декларативної SQL-команди `VACUUM`. Команда підтримує широкий набір модифікаторів, що змінюють режим блокування, глибину аналізу та поведінку щодо індексів:

```sql
VACUUM [ ( option [, ...] ) ] [ table_and_columns [, ...] ];
```

#### Повний реєстр опцій команди VACUUM

| Опція | Тип блокування | Механізм дії та архітектурний вплив |
| :--- | :--- | :--- |
| `FULL` | `AccessExclusiveLock` | Виконує фізичну перебудову таблиці з нуля. Створює новий дисковий файл, послідовно копіюючи туди виключно живі кортежі без пустот. Повністю блокує будь-яке читання (`SELECT`) та запис (`INSERT`, `UPDATE`, `DELETE`) до завершення операції. Потребує до 100% додаткового вільного місця на файловій системі. |
| `FREEZE` | `ShareUpdateExclusiveLock` | Примусово встановлює спеціальний прапорець заморожування `FrozenTransactionId` для всіх зафіксованих кортежів на сторінках, навіть якщо їхній вік не досяг порогового значення `vacuum_freeze_min_age`. Використовується для запобігання переповненню лічильника XID. |
| `ANALYZE` | `ShareUpdateExclusiveLock` | Одночасно з очищенням сторінок збирає свіжу статистику розподілу даних у стовпчиках (гістограми, найчастіші значення MCV, кількість унікальних значень) і записує її в системний каталог `pg_statistic` для вартісного оптимізатора запитів. |
| `VERBOSE` | Не змінює блокування | Виводить у клієнтський потік та системний лог деталізований звіт: кількість відсканованих сторінок, знайдених та вилучених мертвих кортежів, оновлених індексних блоків та точний час виконання кожної фази. |
| `INDEX_CLEANUP { AUTO | ON | OFF }` | Не змінює блокування | Дозволяє вимкнути або примусово увімкнути сканування індексів B-Tree під час очищення. Опція `OFF` дозволяє екстрено звільнити місце на сторінках купи без тривалого оновлення важких індексів. |
| `PROCESS_MAIN { TRUE | FALSE }` | Не змінює блокування | Дозволяє пропустити обробку основного табличного простору, обмежившись лише пов'язаними TOAST-таблицями. |
| `PARALLEL n` | Не змінює блокування | Виділяє `n` фонових процесів (Background Workers) для одночасного паралельного сканування та очищення кількох індексів однієї таблиці (підтримується з PostgreSQL 13). |

### Консольна утиліта vacuumdb

Для автоматизації регламентних робіт через планувальники завдань (cron) PostgreSQL надає системну бінарну утиліту `vacuumdb`:

```bash
# Паралельне очищення всіх баз даних кластера у 4 потоки
vacuumdb --all --parallel=4 --analyze --verbose

# Очищення конкретної таблиці з агресивним заморожуванням XID
vacuumdb -d production_db -t orders --freeze --analyze
```

Ключові прапорці утиліти:
* `-a, --all`: сканувати та очищати всі наявні бази даних у кластері;
* `-j, --jobs=NUM`: кількість паралельних одночасних з'єднань для обробки різних таблиць;
* `-z, --analyze`: одночасно оновлювати статистику для оптимізатора запитів;
* `-F, --freeze`: запускати примусове заморожування ідентифікаторів кортежів.

### Внутрішні фази виконання VACUUM

Звичайний неблокуючий `VACUUM` виконується у п'ять послідовних етапів:

1. **Фаза ініціалізації та розрахунку горизонту**: Демон визначає глобальне значення `OldestXmin` для всього кластера, враховуючи активні транзакції, відкриті курсори, слоти фізичної реплікації та підготовлені двофазні транзакції (`PREPARED TRANSACTIONS`).
2. **Фаза сканування купи (Heap Scan)**: Послідовне читання сторінок таблиці розміром 8 КБ. Кортежі, для яких поле `t_xmax` менше за `OldestXmin`, класифікуються як мертві, а їхні фізичні адреси (TID) заносяться у виділений буфер оперативної пам'яті `maintenance_work_mem`.
3. **Фаза очищення індексів (Index Vacuum)**: Якщо знайдено мертві кортежі, процес сканує всі індекси таблиці та вилучає з листових сторінок B-Tree посилання на знайдені TID. Якщо обсяг списку TID перевищує `maintenance_work_mem`, сканування індексів розбивається на кілька ітерацій.
4. **Фаза дефрагментації сторінок купи (Heap Vacuum)**: Повернення до сторінок купи, вилучення тіл мертвих кортежів, зміщення живих кортежів до кінця сторінки та оновлення бітової карти вільного простору (Free Space Map, FSM).
5. **Фаза оновлення карт видимості (Visibility Map Update)**: Якщо на сторінці не залишилося жодного незамороженого або мертвого кортежу, у файлі VM виставляються біти `all-visible` та `all-frozen`, що дозволяє подальшим запитам виконувати Index-Only Scan без звернення до дискової купи.

### Детальна конфігурація демона Autovacuum

Фоновий демон `autovacuum` складається з процесу-координатора (Autovacuum Launcher), який щохвилини інспектує стан бази через систему статистики `pgstat`, та пулу робочих процесів (Autovacuum Workers).

#### Розрахунок порогу запуску Autovacuum

Робочий процес автоматично призначається для очищення таблиці, щойно поточна кількість мертвих кортежів `dead_tuples` перевищує динамічний поріг:

```text
Threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples
```

Аналогічно, для автоматичного збору статистики `ANALYZE` поріг обчислюється за формулою:

```text
Threshold_analyze = autovacuum_analyze_threshold + autovacuum_analyze_scale_factor * reltuples
```

де `reltuples` — загальна кількість живих рядків у таблиці згідно з останніми статистичними даними каталогу `pg_class.reltuples`.

#### Повний реєстр параметрів конфігурації Autovacuum у postgresql.conf

| Назва параметра | Тип даних | Дефолт | Рекомендація для OLTP | Детальний опис та вплив на дискову підсистему |
| :--- | :--- | :--- | :--- | :--- |
| `autovacuum` | bool | `on` | `on` | Глобальне увімкнення підсистеми автоочищення. Вимикання категорично заборонено у промислових середовищах. |
| `autovacuum_max_workers` | int | `3` | `6 - 12` | Максимальна кількість одночасно працюючих процесів очищення. Кожен воркер обробляє окрему таблицю. |
| `autovacuum_naptime` | time | `1min` | `15s - 30s` | Періодичність пробудження координатора Launcher для аналізу каталогів. Менший час прискорює реакцію на сплески навантаження. |
| `autovacuum_vacuum_threshold` | int | `50` | `100` | Базова константна кількість мертвих кортежів, необхідна для старту очищення. |
| `autovacuum_vacuum_scale_factor` | float | `0.2` (20%) | `0.02 - 0.05` (2-5%) | Відносна частка змінених рядків. Дефолтні 20% є занадто високими для великих таблиць (наприклад, таблиця на 100 млн рядків чекатиме 20 млн оновлень до початку очищення). |
| `autovacuum_vacuum_cost_limit` | int | `-1` (200) | `1000 - 2000` | Загальний бюджет балів операцій введення-виведення на всі активні воркери. Щойно сумарна вартість операцій досягає ліміту, всі воркери примусово засинають на `cost_delay`. |
| `autovacuum_vacuum_cost_delay` | time | `2ms` | `2ms` | Тривалість сну робочого процесу при вичерпанні ліміту вартості. Дозволяє обмежити утилізацію дисків процесом вакуумізації. |
| `vacuum_cost_page_hit` | int | `1` | `1` | Вартість знаходження потрібної сторінки в пам'яті спільного буферного пулу (Shared Buffers). |
| `vacuum_cost_page_miss` | int | `2` | `2` | Вартість читання сторінки з дискового сховища операційної системи. |
| `vacuum_cost_page_dirty` | int | `20` | `20` | Вартість модифікації чистої сторінки, яка потребує подальшого запису на диск. |
| `autovacuum_freeze_max_age` | int | `200000000` | `200000000` | Жорсткий поріг віку транзакцій. При досягненні 200 млн транзакцій рушій запускає агресивний вакуум навіть за наявності блокувань для захисту від переповнення XID. |

### Підсистема очищення Purge у MySQL InnoDB

У рушії MySQL InnoDB багатоверсійність організована через зберігання дельт у сегментах журналу відкату (Undo Logs). За очищення цих записів відповідає підсистема `Purge`.

#### Механізм роботи InnoDB Purge Coordinator

Коли транзакція виконує фіксацію `COMMIT`, її зміни стають постійними. Проте відповідні Undo-записи не можуть бути вилучені негайно, оскільки вони можуть бути потрібні іншим паралельним транзакціям, що стартували раніше і працюють під ізоляцією Repeatable Read.

Координатор Purge виконує такі функції:
1. Знаходить найстаріший активний знімок читання (`Read View`) серед усіх відкритих транзакцій.
2. Вилучає всі Undo-записи, які належать зафіксованим транзакціям з ідентифікаторами, меншими за номер найстарішого `Read View`.
3. Виконує фізичне видалення індексних записів, позначених прапорцем видалення (`delete-marked flag`).
4. Звільняє сторінки в дискових просторах `Undo Tablespaces`.

#### Ключові системні змінні конфігурації Purge у MySQL

| Змінна | Дефолт | Діапазон | Інженерне призначення |
| :--- | :--- | :--- | :--- |
| `innodb_purge_threads` | `4` | `1 - 32` | Кількість виділених системних потоків фонового очищення. Збільшення до 8–16 дозволяє уникнути відставання очищення на NVMe-дисках. |
| `innodb_purge_batch_size` | `300` | `1 - 5000` | Кількість сторінок Undo, які потік очищає за один безперервний цикл парсингу журналу. |
| `innodb_max_purge_lag` | `0` | `0 - 4294967295` | Поріг затримки черги Undo. Якщо кількість очікуючих сторінок перевищує це значення, InnoDB починає примусово сповільнювати клієнтські операції запису (`DML`) на мікросекунди, забезпечуючи пріоритет потокам очищення. |
| `innodb_undo_log_truncate` | `ON` | `ON / OFF` | Дозволяє автоматично зменшувати розмір фізичних файлів `undo_001`, `undo_002` на диску при досягненні ліміту `innodb_max_undo_log_size` (зазвичай 1 ГБ). |

### Практичні інженерні сценарії налаштування для високого навантаження

При проектуванні високонавантажених сервісів з інтенсивним потоком оновлень стандартні налаштування автовакууму призводять до деградації:

1. **Індивідуальні налаштування для гарячих таблиць**: Для черг завдань або таблиць замовлень з мільйонами `UPDATE` на добу слід перевизначати параметри на рівні конкретної таблиці за допомогою директиви `ALTER TABLE`:
   ```sql
   ALTER TABLE orders SET (
       autovacuum_vacuum_scale_factor = 0.01,
       autovacuum_vacuum_threshold = 500,
       autovacuum_vacuum_cost_limit = 5000,
       autovacuum_vacuum_cost_delay = 0
   );
   ```
2. **Уникнення вимивання буферного кешу**: Для запобігання ситуації, коли вакуумізація великої таблиці витісняє гарячі дані OLTP з оперативної пам'яті, PostgreSQL використовує кільцевий буфер розміром лише 256 КБ (Buffer Access Strategy). Це ізолює фоновий процес від основного пулу пам'яті `shared_buffers`.
3. **Моніторинг блокувань на рівні реплікації**: Якщо на репліці виконується довгий аналітичний запит, він утримує `OldestXmin` на первинному сервері, якщо увімкнено параметр `hot_standby_feedback = on`. Це запобігає конфліктам реплікації (`replication conflict`), але створює розростання таблиць на майстрі.

### Виробничі діагностичні SQL-запити

#### 1. Детальний моніторинг мертвих кортежів та ефективності Autovacuum у PostgreSQL

```sql
SELECT 
    schemaname,
    relname AS table_name,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_live_tup AS live_tuples,
    n_dead_tup AS dead_tuples,
    round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 2) AS dead_tuple_percent,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
WHERE n_dead_tup > 500
ORDER BY n_dead_tup DESC;
```

#### 2. Виявлення блокуючих довгих транзакцій, що гальмують переміщення OldestXmin

```sql
SELECT 
    pid,
    usename,
    client_addr,
    state,
    backend_xid,
    backend_xmin,
    now() - xact_start AS transaction_age,
    now() - state_change AS state_age,
    query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL OR backend_xid IS NOT NULL
ORDER BY transaction_age DESC;
```

#### 3. Моніторинг небезпеки вичерпання 32-бітного лічильника транзакцій (XID Wraparound)

```sql
SELECT 
    datname,
    age(datfrozenxid) AS xid_age,
    2147483648 - age(datfrozenxid) AS xids_until_emergency_stop,
    round(100.0 * age(datfrozenxid) / 2147483648, 2) AS percent_towards_wraparound
FROM pg_database
ORDER BY xid_age DESC;
```
