# 📜 Відкриття JSON: від вилучення XML до світового стандарту

Коли на початку 2000-х років розробники намагалися передати структуровані дані між сервером і браузером, єдиним загальноприйнятим стандартом вважався XML (англ. *Extensible Markup Language*). Разом із ним у корпоративному стеку панував протокол SOAP (англ. *Simple Object Access Protocol*): кожна відповідь загорталася в багаторівневі конверти (*Envelope*), простори імен (*Namespaces*) та супроводжувалася строгими описами схем XML Schema (XSD). Щоб видобути одне число або рядок, браузер мав побудувати в оперативній пам'яті важке дерево Document Object Model (DOM), обійти його через довгі виклики `getElementsByTagName()` або задіяти повільний транслятор XSLT. На комп'ютерах тієї доби це призводило до відчутних затримок інтерфейсу та надмірного споживання трафіку, де службові кутові дужки й схеми важили в рази більше за корисні дані.

Потреба в мінімалістичному, легкому форматі обміну виникла з практичної задачі компанії State Software, яку на початку 2001 року заснували Дуглас Крокфорд (англ. *Douglas Crockford*) та Чіп Морнінгстар (англ. *Chip Morningstar*). Вони створювали браузерні застосунки реального часу — те, що пізніше назвуть Ajax — і шукали спосіб надсилати повідомлення крізь приховані фрейми `<iframe>` без перезавантаження сторінки. Замість винаходу нового синтаксису з нуля Крокфорд звернув увагу на вже наявну конструкцію мови програмування: літерали об'єктів і масивів у стандарті ECMAScript третьої редакції (ECMA-262 Third Edition, грудень 1999 року).

### Чому «відкриття», а не «винахід»

Крокфорд неодноразово наголошував, що він не «винайшов» JSON, а саме «відкрив» його (*discovered, not invented*). Синтаксис опису структур уже був повністю реалізований у кожному сучасному веб-браузері: фігурні дужки `{}` для словників ключ-значення, квадратні дужки `[]` для впорядкованих списків, лапки для рядків і звичний запис чисел.

```json
{
  "user": "olena",
  "id": 48291,
  "active": true,
  "roles": ["admin", "editor"]
}
```

Перше задокументоване повідомлення у новому форматі Морнінгстар та Крокфорд надіслали у квітні 2001 року під час тестування прототипу. Уся процедура розбору на боці браузера на той час зводилася до виклику штатного інтерпретатора JavaScript. Браузер перетворював рядок безпосередньо у нативні структури пам'яті за частки мікросекунди без жодних сторонніх бібліотек чи виснажливого обходу DOM-вузлів. Формат назвали **JSON** — JavaScript Object Notation (англ. *позначення об'єктів JavaScript*).

### Навмисне вилучення коментарів

На ранньому етапі розробники часто запитували Крокфорда, чому в JSON немає коментарів на кшталт `/* ... */` або `//`, хоча в самій мові JavaScript вони завжди підтримувалися. Відповідь автора форматів здивувала багатьох, але стала одним із найважливіших інженерних рішень для збереження стабільності екосистеми: коментарі було прибрано **свідомо і безповоротно**.

Крокфорд помітив, як попередні формати (включно з директивами препроцесорів, HTML-коментарями та XML-анотаціями) швидко деградували: розробники інструментів та бібліотек починали ховати всередину коментарів власні службові інструкції (прагми парсера, директиви типізації, умовну компіляцію на кшталт `<!--[if IE]>`). Щойно парсери починали тлумачити коментарі як команди поведінки, документ переставав бути універсальним: файл, розрахований на одну бібліотеку, ламався або некоректно інтерпретувався іншою.

Повна відсутність синтаксису коментарів у JSON позбавила виробників програмного забезпечення можливості додавати приховані «розширення». Документ JSON став виключно нейтральним каналом передавання стану даних, де кожен байт структури підпорядкований єдиному незмінному правилу.

### Шлях до стандартизації: json.org, RFC та ECMA

Поширення формату відбувалося знизу вгору. 2002 року Крокфорд зареєстрував веб-сайт `json.org`, де розмістив повний граматичний опис стандарту на одній сторінці разом із набором простих референсних парсерів для різних мов програмування (зокрема Java та C). Синтаксис був настільки лаконічним, що вмістився у кілька графічних діаграм залізничного типу (*railroad diagrams*).

1. **RFC 4627 (липень 2006 року):** Перша офіційна публікація в IETF (англ. *Internet Engineering Task Force*). Документ мав статус інформаційного (*Informational RFC*), закріпив MIME-тип `application/json` та встановив конвенції сумісності з HTTP.
2. **ECMA-404 (жовтень 2013 року):** Консорціум Ecma International стандартизував чистий синтаксис JSON як незалежний міжнародний стандарт (англ. *The JSON Data Interchange Syntax*). ECMA-404 зосередився виключно на граматичних правилах символів і структур, свідомо залишивши питання обробки та інтероперабельності на розсуд інженерів протоколів.
3. **RFC 7159 (березень 2014 року) та RFC 8259 (грудень 2017 року):** IETF випустила стандарти повного циклу (*Internet Standard STD 90*). RFC 8259 остаточно зафіксував обов'язковість кодування **UTF-8** для мережевого обміну, скасував використання застарілих кодувань UTF-16/32 без явної домовленості, заборонив мітку порядку байтів (BOM) і роз'яснив вимоги до меж точності чисел IEEE 754.

Перехід веб-індустрії від багатослівного XML/SOAP до лаконічного JSON став основою архітектурного стилю REST API та сучасних односторінкових веб-застосунків (SPA). Формат перетворився на головну мову текстового обміну даними у світовій цифровій інфраструктурі завдяки простоті, що спирається на мінімальну кількість базових типів і нульові витрати на узгодження складних схем.
