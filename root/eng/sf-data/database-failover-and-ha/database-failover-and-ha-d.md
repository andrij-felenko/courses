Коли основний сервер бази даних раптово втрачає живлення або мережевий інтерфейс перестає відповідати посеред обробки десяти тисяч транзакцій на секунду, клієнтські застосунки миттєво стикаються з розривом TCP-з'єднань, а черга реплікації на резервних вузлах заморожується на останньому отриманому байті журналу. Якщо перемикання на резервний вузол виконує черговий інженер вручну, бізнес гарантовано отримує від двадцяти хвилин до кількох годин повного простою сервісу. Якщо ж процес автоматизувати без суворого математичного консенсусу, виникає зворотна катастрофа: тимчасово ізольований сервер продовжує приймати транзакції паралельно з новообраним лідером, що незворотно розколює масив даних на дві несумісні гілки історії.

## Анатомія збою: показники надійності, RPO та RTO

Безперервність функціонування системи зберігання даних оцінюється через співвідношення часу її повноцінної роботи до загального життєвого циклу. Коли компоненти комплексу (дискові контролери, оперативна пам'ять, мережеві комутатори чи операційна система) неминуче деградують або аварійно вимикаються, надійність кластера описується двома базовими статистичними характеристиками:

```
MTBF (Mean Time Between Failures) — середній час безвідмовної роботи між сусідніми аваріями
MTTR (Mean Time To Repair)        — середній час відновлення працездатності після аварії
```

Частка часу, протягом якого база даних залишається повністю доступною для виконання операцій читання та запису, визначається відношенням:

```
A = MTBF / (MTBF + MTTR)   [коефіцієнт готовності: частка часу справної роботи]
```

Здатність системи протистояти апаратним та програмним дефектам без переривання обслуговування називають відмовостійкістю (англ. *fault tolerance*, від лат. *tolerare* — терпіти, витримувати), а властивість забезпечувати доступ до даних за встановленим стандартом доступністю (англ. *availability*, від лат. *habilis* — зручний, придатний). У промисловій інженерії рівень доступності вимірюють відсотковими класами — «кількістю дев'яток». Для річного інтервалу часу `T[рік] = 365.25 · 24 · 3600 = 31 557 600` секунд сумарний допустимий час простою `D[рік]` обчислюється через коефіцієнт простою `U = 1 - A`:

```
D[рік] = T[рік] · (1 - A)   [добуток секунд року на частку простою]
```

Розрахуємо річний бюджет простою для трьох класичних рівнів доступності:

**Клас 99.9% («три дев'ятки» — типова поодинока реляційна база даних):**
```
D[рік] = 525 960 хв · (1 - 0.999)
= 525 960 · 0.001                [множення на частку простою]
= 525.96 хвилин                  [підсумок у хвилинах]
= 8 годин 45 хвилин 58 секунд    [переведення в години]
```

**Клас 99.99% («чотири дев'ятки» — високодоступний кластер із автоматичним перемиканням):**
```
D[рік] = 525 960 хв · (1 - 0.9999)
= 525 960 · 0.0001               [множення на частку простою]
= 52.596 хвилин                  [підсумок у хвилинах]
= 52 хвилини 36 секунд           [переведення в хвилини та секунди]
```

**Клас 99.999% («п'ять дев'яток» — георозподілені кластери з розподіленим консенсусом):**
```
D[рік] = 525 960 хв · (1 - 0.99999)
= 525 960 · 0.00001              [множення на частку простою]
= 5.2596 хвилин                  [підсумок у хвилинах]
= 5 хвилин 16 секунд             [переведення в секунди]
```

Будь-яка аварія лідера ставить перед архітектурою бази даних дві незалежні цілі відновлення:

1. **RTO (Recovery Time Objective)** — цільовий час відновлення працездатності: максимальний часовий проміжок від моменту фізичної відмови вузла до моменту, коли новий лідер кластера готовий приймати запити на запис.
2. **RPO (Recovery Point Objective)** — цільова точка відновлення: максимальний обсяг даних (виражений у часовому еквіваленті або кількості транзакцій), втрата якого допустима під час катастрофи.

Якщо реплікація працює в суто асинхронному режимі, репліка відстає від лідера на деяку кількість байтів у журналі транзакцій `Δ_LSN`. У момент раптової загибелі лідера всі транзакції, записані в локальний журнал на диску лідера, але ще не передані через сокет реплікації, безповоротно втрачаються, формуючи `RPO > 0`. За синхронної реплікації транзакція підтверджується клієнту лише після збереження запису щонайменше на одній репліці, що гарантує `RPO = 0`, проте збільшує затримку кожної операції запису на час мережевого кругового обігу пакетів (RTT).

Операцію автоматичного передавання функцій основного вузла резервному в разі аварії називають аварійним перемиканням або failover (англ. *failover*, від *fail* — зазнавати невдачі та *over* — перехід через край).

![Життєвий цикл та фази аварійного перемикання](/root/eng/sf-data/database-failover-and-ha/img/ha-failover-state-machine.svg)
*Фази життєвого циклу failover: від моменту відмови лідера, очікування таймауту лізингу й ізоляції до виборів нового primary і перенаправлення клієнтського трафіку із загальним внеском у RTO.*

Загальний час відновлення RTO складається з послідовності обов'язкових інженерних кроків:

```
RTO = T[detect] + T[fence] + T[elect] + T[promote] + T[route]
де:
T[detect]  — час виявлення збою (вичерпання таймауту лізингу або лічильника пульсу)
T[fence]   — гарантована ізоляція старого лідера для запобігання паралельному запису
T[elect]   — вибір резервного вузла з найповнішим журналом змін серед доступних
T[promote] — завершення застосування накопиченого журналу та перехід СКБД у Read-Write
T[route]   — оновлення маршрутів у балансувальниках або перепідключення клієнтських пулів
```

Детальний математичний апарат розрахунку надійності, марковські ланцюги переходів між аварійними станами кластера та ймовірнісні оцінки кворумів розібрано у вставці [Математика доступності, кворумів та таймаутів лізингу](root:sf-data/database-failover-and-ha/math-ha-availability-and-quorum.md).

## Виявлення збоїв: імпульси серцебиття, оренда та хибні тривоги

Перша проблема на шляху до автоматичного відновлення полягає в тому, що у ненадійних асинхронних мережах неможливо миттєво відрізнити остаточну загибель сервера від тимчасової затримки зв'язку. Процес на лідері може зупинитися на кілька секунд через тривалу паузу збирача сміття (Stop-the-World GC), ядра операційної системи можуть вичерпати черги пам'яті через сплеск навантаження, комутатор може скидати пакети через переповнення буферів, або віртуальна машина може зазнати короткочасного зависання на рівні гіпервізора.

Якщо система реагує на кожну затримку відповіді негайним оголошенням аварії, кластер потрапляє в стан хибних спрацьовувань: постійні непотрібні перемикання лідерів (flapping / ping-pong failover) деградують продуктивність сильніше, ніж реальні апаратні збої.

Історично першим способом контролю стану була відправка періодичних контрольних імпульсів — серцебиття (англ. *heartbeat*, від давньогерм. *heorte* — серце та *beatan* — бити). Вузли обмінювалися UDP- або TCP-повідомленнями через фіксовані інтервали часу. Якщо протягом `N` інтервалів відповідь не надходила, вузол вважався мертвим. Проте прямий обмін імпульсами між парою серверів має критичний дефект: при обриві кабелю між двома вузлами обидва сервери залишаються абсолютно справними, але втрачають зв'язок один з одним, що робить симетричне рішення неможливим.

Сучасні відмовостійкі архітектури переносять координацію у зовнішнє розподілене сховище консенсусу (DCS — Distributed Consensus Store, такі як `etcd` або `Consul`), побудоване на протоколах Raft або Paxos. Координація спирається на концепцію оренди на обмежений термін або лізингу (англ. *TTL lease*, від англо-норм. *les* — передача майна у тимчасове користування):

1. Чинний лідер кластера створює в DCS ключ лідера (наприклад, `/service/production/leader`) із прив'язкою до тимчасової сесії з таймером життя `TTL[lease]` (зазвичай 10 секунд).
2. Поки лідер функціонує коректно, його фоновий потік оновлення надсилає запити продовження оренди через кожні `T[renew]` (наприклад, кожні 2 або 3 секунди).
3. Якщо лідер втрачає живлення, зависає або потрапляє в мережеву ізоляцію, він втрачає зв'язок із кворумом DCS і більше не може надсилати сигнали продовження.
4. Після вичерпання інтервалу `TTL[lease]` розподілене сховище консенсусу автоматично видаляє ключ лідера.
5. Резервні вузли, підписані на зміни цього ключа через механізм сповіщень (Watch API), миттєво фіксують зникнення запису і розпочинають вибори нового лідера.

Для запобігання передчасним виборам через випадкові сплески мережевої латентності часові інтервали системи лізингу зобов'язані задовольняти строгу інженерну нерівність:

```
TTL[lease] > T[renew] + T[net_jitter] + T[process_pause] + T[dcs_rtt]
```

Якщо сумарна затримка мережі та внутрішня пауза процесу перевищують залишок часу оренди, лідер зобов'язаний добровільно скласти повноваження до того, як спливе термін його ключа в DCS.

## Розщеплення мозку та механізми ізоляції (Fencing / STONITH)

Найнебезпечнішим станом розподіленої бази даних є розщеплення мозку (англ. *split-brain*, від *split* — розколювати та *brain* — мозок). Ця ситуація виникає, коли внаслідок мережевого розриву кластер розділяється на два ізольовані сегменти, і в кожному з них одночасно починає функціонувати власний лідер із правами на запис:

1. **Сегмент A:** Старий primary-сервер не знає про те, що зв'язок із рештою серверів втрачено, і продовжує приймати транзакції від клієнтів, які залишилися підключеними до його локального мережевого сегмента.
2. **Сегмент B:** Резервний сервер, не отримуючи сигналів від primary, оголошує його мертвим, перемагає у виборах і відкривається для запису нових транзакцій.

Коли два сервери паралельно виконують модифікації тих самих таблиць, вони генерують суперечливі версії рядків із однаковими первинними ключами. Журнали транзакцій WAL розходяться на різні незв'язні часові шкали (timelines). Після відновлення зв'язку між сегментами ці зміни неможливо об'єднати автоматично без порушення семантики ACID: частину бізнес-транзакцій доведеться безповоротно стерти або відновлювати вручну з бінарних дампів.

![Розщеплення мозку та ізоляція вузла через Fencing](/root/eng/sf-data/database-failover-and-ha/img/split-brain-and-fencing.svg)
*Анатомія розщеплення мозку за відсутності ізоляції проти детермінованого захисту цілісності даних через апаратний STONITH або системний watchdog-таймер.*

Єдиним надійним захистом від розщеплення мозку є огородження або примусова ізоляція (англ. *fencing*, від *fence* — паркан, огорожа). Принцип fencing вимагає: **жоден резервний вузол не має права підвищити свій статус до лідера (promote), доки немає абсолютної апаратної або програмної гарантії, що старий лідер позбавлений можливості записати бодай один байт на диск чи відповісти клієнту**.

Ізоляція реалізується на кількох незалежних рівнях:

### 1. Апаратна ізоляція (STONITH)
Акронім STONITH розшифровується як *«Shoot The Other Node In The Head»* («Вистрель іншому вузлу в голову»). Якщо резервний вузол фіксує збій лідера, він звертається до незалежного апаратного каналу управління:
- Інтелектуальний блок розподілу живлення (Switched PDU): команда через SNMP або SSH фізично вимикає подачу струму на розетку старого primary-сервера.
- Апаратний інтерфейс управління материнською платою (IPMI, Dell iDRAC, HPE iLO): надсилання команди апаратного скидання живлення (`chassis power off`).
- Хмарні API (AWS EC2 StopInstances, GCP compute.instances.stop): негайне примусове вимкнення інстансу через гіпервізор.

Фізично знеструмлений або заморожений гіпервізором сервер математично не здатний виконати жодної операції запису.

### 2. Системний сторожовий таймер (Watchdog)
У бездискових або хмарних середовищах, де прямий доступ до IPMI відсутній, застосовують програмно-апаратний сторожовий таймер (англ. *watchdog*, від англосакс. *waeccende* — пильний та *docga* — собака).

Керівний демон бази даних (наприклад, Patroni) відкриває спеціальний пристрій операційної системи `/dev/watchdog`. Демон зобов'язаний періодично скидати таймер ядра (наприклад, кожні 5 секунд). Якщо система зависає або втрачає зв'язок із кворумом DCS на час `T > TTL[watchdog]`, апаратний модуль материнської плати або драйвер ядра Linux автоматично ініціює апаратне перезавантаження сервера (Kernel Panic / Hard Reset) без збереження кешів операційної системи.

```
Правило безпеки лізингу:
TTL[watchdog] ≤ TTL[lease] / 2
```

Завдяки цьому співвідношенню старий лідер гарантовано перезавантажиться і знищить свої активні процеси раніше, ніж резервні вузли отримають право перехопити звільнений ліз у DCS.

### 3. Токени покоління (Fencing Tokens / Epoch)
Якщо вузол звертається до зовнішнього мережевого сховища (SAN/NFS) або проксі-шару, кожне обрання нового лідера збільшує монотонний числовий лічильник епохи (англ. *generation clock* або *epoch*).

Новий лідер отримує токен `Epoch = k + 1`. Сховище або балансувальник відкидає будь-які запити, марковані застарілим токеном `Epoch ≤ k`, навіть якщо старий лідер все ще вважає себе активним.

Історичний шлях розвитку механізмів ізоляції від нуль-модемних кабелів Linux-HA до сучасного хмарного fencing описано у вставці [Еволюція архітектур високої доступності](root:sf-data/database-failover-and-ha/hist-evolution-of-ha.md).

## Кворуми, вибори лідера та вибір найсвіжішої репліки

Щоб прийняти однозначне рішення про зміну ролей без ризику розколу на рівні самого керуючого шару, вибори лідера спираються на принцип абсолютної більшості голосів — кворум (лат. *quorum* — «яких [достатньо] для прийняття рішення»).

Для кластера з `N` вузлів мінімальний розмір кворуму `Q` становить:

```
Q = ⌊N / 2⌋ + 1   [сувора більшість вузлів кластера]
```

Максимальна кількість одночасних апаратних відмов `F`, яку здатна витримати система без втрати можливості обирати лідера:

```
F = ⌊(N - 1) / 2⌋   [гранична кількість допустимих аварій]
```

| Кількість вузлів (`N`) | Розмір кворуму (`Q`) | Допустима кількість відмов (`F`) | Примітка інженерної стійкості |
|---|---|---|---|
| 1 | 1 | 0 | Відсутня відмовостійкість |
| 2 | 2 | 0 | Будь-яка відмова позбавляє кворуму |
| 3 | 2 | 1 | Класична конфігурація для однієї відмови |
| 4 | 3 | 1 | Не додає надійності порівняно з 3 вузлами |
| 5 | 3 | 2 | Оптимально для стійкості до двох аварій |

Парна кількість вузлів (наприклад, 2 або 4) є нераціональною: кластер із 4 серверів вимагає кворуму в 3 голоси, тобто витримує відмову лише 1 сервера — стільки ж, скільки кластер із 3 серверів, але має вдвічі більшу ймовірність внутрішньої аварії через більшу кількість компонентів.

### Вибір найсвіжішої репліки за LSN та GTID
Коли кворум DCS дозволяє почати вибори, керівний координатор не може призначити лідером довільну репліку. За асинхронної чи напівсинхронної реплікації різні standby-сервери можуть мати різний прогрес застосування журналу.

У системі PostgreSQL кожна зміна сторінки даних позначається монотонним 64-бітним цілим числом — Log Sequence Number (LSN), яке вказує на точне байтове зміщення в журналі попереднього запису WAL. У системі MySQL аналогічну роль відіграють Global Transaction Identifiers (GTID) — структуровані набори зафіксованих інтервалів транзакцій.

Алгоритм виборів лідера виконує такі кроки:
1. Кожна доступна репліка зчитує власну актуальну позицію відтворення журналу (`pg_last_wal_replay_lsn()` у PostgreSQL або `Executed_Gtid_Set` у MySQL).
2. Кандидати публікують свої значення LSN у службовій гілці DCS.
3. Право претендувати на ключ лідера отримує лише той вузол, у якого поточний LSN є максимальним серед усіх активних реплік:

```
LSN[candidate] == max(LSN[replica_1], LSN[replica_2], ..., LSN[replica_m])
```

4. Якщо найсвіжіша репліка все ще має в локальному буфері байти WAL, отримані від старого primary, але ще не застосовані до таблиць, вона завершує процес відтворення (catch-up replay).
5. Виконується системна команда підвищення ролі `pg_promote()`. Двигун СКБД закриває попередню гілку журналу, збільшує ідентифікатор часової шкали (`Timeline ID = Timeline ID + 1`), генерує маркерний запис у WAL і переводить внутрішні структури у повноцінний режим Read-Write.

### Повернення старого лідера: механізм pg_rewind
Якщо старий primary-сервер після ізоляції та відновлення перезапускається, його локальний журнал WAL містить транзакції старої часової шкали, які не потрапили на репліку і відсутні на новому primary.

Раніше такий вузол доводилося повністю видаляти і копіювати гігабайти даних з нуля через `pg_basebackup`. Сучасні системи застосовують утиліту `pg_rewind`:
1. Утиліта порівнює журнали WAL обох серверів і знаходить спільну точку розгалуження (fork point) — останній LSN, у якому їхні часові шкали збігалися.
2. `pg_rewind` сканує журнал старого лідера від точки розгалуження вперед, визначає всі блоки даних на диску, які зазнали локальних змін.
3. Із нового діючого лідера копіюються лише ці конкретні пошкоджені 8-кілобайтні блоки, повертаючи стан файлової системи до точки розгалуження.
4. Вузол перемикається в режим репліки, підключається до нового лідера і починає транслювати нову часову шкалу WAL.

## Архітектура промислових HA-систем: Patroni та балансування трафіку

Повноцінний промисловий кластер високої доступності об'єднує транзакційний рушій СКБД, розподілений консенсусний шар та динамічний шар маршрутизації клієнтських запитів.

![Архітектура високодоступного кластера з Patroni та etcd](/root/eng/sf-data/database-failover-and-ha/img/patroni-etcd-architecture.svg)
*Трирівнева архітектура: клієнтські застосунки, шар балансування HAProxy/PgBouncer на основі HTTP health-checks та вузли СКБД під керуванням агентів Patroni, скоординованих через etcd.*

Центральним керуючим процесом на кожному вузлі виступає агент **Patroni** — демон на Python, який напряму керує життєвим циклом локального екземпляра PostgreSQL:

1. **Супервізор процесу:** Patroni самостійно запускає, перезавантажує, конфігурує та зупиняє процес `postgres`, генеруючи файли конфігурації `postgresql.conf` на основі глобальних параметрів у DCS.
2. **REST API перевірки стану:** Кожен агент Patroni відкриває локальний HTTP-порт (за замовчуванням 8008), який повертає динамічний статус вузла:
   - Ендпоінт `GET /primary` повертає `HTTP 200 OK`, якщо локальний вузол є активним лідером кластера, і `HTTP 503 Service Unavailable`, якщо вузол є реплікою або перебуває в аварійному стані.
   - Ендпоінт `GET /replica` повертає `HTTP 200 OK` виключно для працюючих реплік у режимі Read-Only.
   - Ендпоінт `GET /patroni` повертає розгорнутий JSON із поточною роллю, LSN, станом реплікаційного лагу та версією конфігурації.

### Маршрутизація трафіку через зворотні проксі
Клієнтські застосунки ніколи не підключаються до фізичних IP-адрес серверів бази даних напряму, оскільки зміна лідера вимагала б одночасного переконфігурування сотень мікросервісів. Трафік проходить через шар проксі-балансувальників (HAProxy, PgBouncer або Envoy):

```haproxy
# Приклад конфігурації HAProxy для маршрутизації на Primary-лідера
frontend db_write_frontend
    bind *:5000
    default_backend db_write_backend

backend db_write_backend
    mode tcp
    option httpchk GET /primary
    http-check expect status 200
    default-server inter 1s fall 2 rise 3 on-marked-down shutdown-sessions
    server db-node-1 10.0.1.11:5432 maxconn 200 check port 8008
    server db-node-2 10.0.1.12:5432 maxconn 200 check port 8008
    server db-node-3 10.0.1.13:5432 maxconn 200 check port 8008
```

Коли primary-вузол зазнає збою або втрачає ліз у etcd:
- Його локальний Patroni перемикає відповідь `/primary` з 200 на 503 і примусово переводить локальну СКБД у Read-Only.
- HAProxy під час чергової перевірки (health-check з інтервалом 1 секунда) фіксує помилку 503 і директивою `shutdown-sessions` негайно розриває всі активні клієнтські TCP-з'єднання до старого вузла.
- Після промоушену репліки її агент Patroni починає відповідати кодом 200 на запит `/primary`.
- HAProxy реєструє новий primary і перенаправляє всі нові вхідні з'єднання на порт 5432 нового лідера.

Час перемикання балансувальника складає менше двох секунд, що повністю усуває необхідність скидання DNS-кешів чи використання крихких віртуальних IP-адрес (VIP).

## Клієнтський рівень: виявлення збою, бекофф та безпечне перепідключення

Навіть найшвидша серверна інфраструктура failover не здатна вберегти клієнтський застосунок від отримання помилок у момент фізичного падіння вузла. Активні транзакції, які виконувалися в момент аварії, обриваються з помилками `ECONNRESET`, `Broken pipe` або `FATAL: terminating connection due to administrator command`.

Завдання клієнтського драйвера та пулу з'єднань — перехопити аварійний розрив, уникнути шторму повторних запитів і безпечно відновити з'єднання з новим лідером.

### Робота з мультихостовими рядками підключення
Сучасні клієнтські бібліотеки (зокрема `libpq` для PostgreSQL та сумісні JDBC-драйвери) підтримують перелік усіх вузлів кластера безпосередньо в рядку з'єднання:

```
postgresql://node1:5432,node2:5432,node3:5432/appdb?target_session_attrs=read-write&connect_timeout=2
```

Параметр `target_session_attrs=read-write` змушує драйвер під час встановлення з'єднання виконати перевірку `SHOW transaction_read_only;`. Якщо вузол перебуває в режимі Read-Only (репліка), драйвер розриває сокет і негайно перевіряє наступний хост зі списку, доки не знайде активного primary.

### Автомат станів перепідключення та експоненційний бекофф
Якщо сотні екземплярів мікросервісів одночасно виявлять розрив з'єднання і почнуть безупинно надсилати запити на підключення, новий primary зазнає відмови через перевантаження (лавинний ефект, Thundering Herd).

Для запобігання перевантаженню клієнтський драйвер реалізує автомат станів з алгоритмом експоненційного відступу з випадковим тремтінням (Exponential Backoff with Full Jitter):

```
T[backoff] = random(0, min(T[max], T[base] · 2^attempt))
```

Нижче наведено практичну реалізацію клієнтського драйвера з автоматом станів перемикання та валідацією прав запису.

```c
/* client_failover_driver.c — Клієнтський автомат станів перепідключення до primary */
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <stdint.h>
#include <string.h>
#include <unistd.h>
#include <time.h>

#define MAX_HOSTS 3
#define BASE_BACKOFF_MS 100
#define MAX_BACKOFF_MS 3000
#define MAX_RETRY_ATTEMPTS 10

typedef enum {
    STATE_DISCONNECTED,
    STATE_PROBING_HOSTS,
    STATE_CONNECTED_PRIMARY,
    STATE_BACKOFF_WAIT,
    STATE_FATAL_FAILURE
} client_state_t;

typedef struct {
    char host[64];
    uint16_t port;
    bool is_alive;
    bool is_read_only;
} db_host_node_t;

typedef struct {
    db_host_node_t hosts[MAX_HOSTS];
    size_t host_count;
    size_t active_host_idx;
    client_state_t state;
    uint32_t current_attempt;
} db_cluster_client_t;

/* Імітація перевірки вузла на доступність та режим Read-Write */
static bool mock_db_check_is_primary(const char* host, uint16_t port) {
    /* У реальній системі: надсилання запиту "SHOW transaction_read_only" через сокет */
    if (strcmp(host, "10.0.1.12") == 0) {
        return true; /* Вузол 2 став новим primary */
    }
    return false;
}

/* Обчислення випадкового експоненційного відступу (Full Jitter) */
static uint32_t calculate_backoff_ms(uint32_t attempt) {
    uint32_t max_sleep = BASE_BACKOFF_MS * (1U << (attempt > 6 ? 6 : attempt));
    if (max_sleep > MAX_BACKOFF_MS) {
        max_sleep = MAX_BACKOFF_MS;
    }
    return (uint32_t)(rand() % (max_sleep + 1));
}

void db_client_init(db_cluster_client_t* client) {
    client->host_count = 3;
    client->active_host_idx = 0;
    client->state = STATE_DISCONNECTED;
    client->current_attempt = 0;

    strncpy(client->hosts[0].host, "10.0.1.11", 64);
    client->hosts[0].port = 5432;
    strncpy(client->hosts[1].host, "10.0.1.12", 64);
    client->hosts[1].port = 5432;
    strncpy(client->hosts[2].host, "10.0.1.13", 64);
    client->hosts[2].port = 5432;
}

bool db_client_execute_query_with_failover(db_cluster_client_t* client, const char* sql) {
    while (client->state != STATE_FATAL_FAILURE) {
        switch (client->state) {
            case STATE_DISCONNECTED:
                client->state = STATE_PROBING_HOSTS;
                break;

            case STATE_PROBING_HOSTS: {
                bool found_primary = false;
                for (size_t i = 0; i < client->host_count; ++i) {
                    size_t idx = (client->active_host_idx + i) % client->host_count;
                    if (mock_db_check_is_primary(client->hosts[idx].host, client->hosts[idx].port)) {
                        client->active_host_idx = idx;
                        client->state = STATE_CONNECTED_PRIMARY;
                        client->current_attempt = 0;
                        found_primary = true;
                        fprintf(stdout, "[CLIENT] Успішно підключено до Primary: %s:%u\n",
                                client->hosts[idx].host, client->hosts[idx].port);
                        break;
                    }
                }
                if (!found_primary) {
                    client->state = STATE_BACKOFF_WAIT;
                }
                break;
            }

            case STATE_CONNECTED_PRIMARY:
                /* Імітація виконання транзакції */
                fprintf(stdout, "[CLIENT] Виконання SQL на primary (%s): %s\n",
                        client->hosts[client->active_host_idx].host, sql);
                return true;

            case STATE_BACKOFF_WAIT: {
                client->current_attempt++;
                if (client->current_attempt >= MAX_RETRY_ATTEMPTS) {
                    fprintf(stderr, "[CLIENT] Перевищено ліміт спроб! Кластер недоступний.\n");
                    client->state = STATE_FATAL_FAILURE;
                    return false;
                }
                uint32_t sleep_ms = calculate_backoff_ms(client->current_attempt);
                fprintf(stderr, "[CLIENT] Primary не знайдено. Спроба %u/%u. Очікування %u мс...\n",
                        client->current_attempt, MAX_RETRY_ATTEMPTS, sleep_ms);
                usleep(sleep_ms * 1000);
                client->state = STATE_PROBING_HOSTS;
                break;
            }

            case STATE_FATAL_FAILURE:
                return false;
        }
    }
    return false;
}
```

```cpp
// client_failover_driver.hpp — Ідіоматичний C++20 клієнт із підтримкою failover
#pragma once
#include <iostream>
#include <vector>
#include <string>
#include <string_view>
#include <random>
#include <chrono>
#include <thread>
#include <expected>
#include <memory>
#include <optional>

namespace db::ha {

enum class ClusterState {
    Disconnected,
    ProbingHosts,
    ConnectedPrimary,
    BackoffWait,
    FatalFailure
};

enum class ClientError {
    ClusterUnavailable,
    QueryExecutionFailed,
    Timeout
};

struct Endpoint {
    std::string host;
    uint16_t port{5432};
};

class FailoverClient {
public:
    explicit FailoverClient(std::vector<Endpoint> endpoints)
        : endpoints_(std::move(endpoints)), rng_(std::random_device{}()) {}

    [[nodiscard]] std::expected<void, ClientError> execute_write(std::string_view query) {
        ClusterState state = ClusterState::ProbingHosts;
        uint32_t attempt = 0;

        while (state != ClusterState::FatalFailure) {
            switch (state) {
                case ClusterState::ProbingHosts: {
                    if (auto primary_idx = probe_endpoints(); primary_idx.has_value()) {
                        active_index_ = *primary_idx;
                        state = ClusterState::ConnectedPrimary;
                        attempt = 0;
                    } else {
                        state = ClusterState::BackoffWait;
                    }
                    break;
                }

                case ClusterState::ConnectedPrimary: {
                    std::cout << "[CLIENT-CXX] Успішний запис на "
                              << endpoints_[active_index_].host << ":"
                              << endpoints_[active_index_].port << " | SQL: " << query << '\n';
                    return {};
                }

                case ClusterState::BackoffWait: {
                    ++attempt;
                    if (attempt >= max_attempts_) {
                        std::cerr << "[CLIENT-CXX] Вичерпано ліміт спроб підключення до Primary.\n";
                        return std::unexpected(ClientError::ClusterUnavailable);
                    }
                    const auto wait_dur = compute_backoff(attempt);
                    std::cerr << "[CLIENT-CXX] Очікування нового Primary: "
                              << wait_dur.count() << " мс (спроба " << attempt << ")\n";
                    std::this_thread::sleep_for(wait_dur);
                    state = ClusterState::ProbingHosts;
                    break;
                }

                default:
                    return std::unexpected(ClientError::ClusterUnavailable);
            }
        }
        return std::unexpected(ClientError::ClusterUnavailable);
    }

private:
    [[nodiscard]] std::optional<size_t> probe_endpoints() const {
        for (size_t i = 0; i < endpoints_.size(); ++i) {
            size_t idx = (active_index_ + i) % endpoints_.size();
            if (mock_is_primary(endpoints_[idx])) {
                return idx;
            }
        }
        return std::nullopt;
    }

    [[nodiscard]] static bool mock_is_primary(const Endpoint& ep) noexcept {
        return ep.host == "10.0.1.12"; // Симуляція виявлення нового промоутеного лідера
    }

    [[nodiscard]] std::chrono::milliseconds compute_backoff(uint32_t attempt) {
        const uint32_t shift = (attempt > 6) ? 6 : attempt;
        const uint32_t max_ms = std::min(max_backoff_ms_, base_backoff_ms_ * (1U << shift));
        std::uniform_int_distribution<uint32_t> dist(0, max_ms);
        return std::chrono::milliseconds(dist(rng_));
    }

    std::vector<Endpoint> endpoints_;
    size_t active_index_{0};
    uint32_t base_backoff_ms_{100};
    uint32_t max_backoff_ms_{3000};
    uint32_t max_attempts_{10};
    mutable std::mt19937 rng_;
};

} // namespace db::ha
```

> Робота з базою даних у розподіленому середовищі вимагає від архітектора проектування всіх операцій модифікації за принципом ідемпотентності (англ. *idempotency*). Коли під час виконання `INSERT INTO orders ...` з'єднання обривається через аварію primary, клієнт не може знати напевно, чи зафіксувалася транзакція перед падінням. Якщо клієнт наївно повторить неідемпотентний запит на новому primary, це призведе до подвійного списання коштів або дублювання записів. Застосування глобальних ключів ідемпотентності (`Idempotency-Key`) та конструкцій `INSERT ... ON CONFLICT DO NOTHING` є обов'язковою умовою надійної інтеграції з HA-кластером.

## Інженерні компроміси, пастки та ціна високої доступності

Впровадження автоматичного аварійного перемикання не є безкоштовним покращенням: воно ускладнює експлуатацію і створює нові специфічні класи відмов.

### 1. Пастка синхронної реплікації та доступність запису
Прагнення досягти нульової втрати даних (`RPO = 0`) спонукає встановлювати суворий синхронний режим (`synchronous_commit = on` у PostgreSQL або `sync_binlog = 1` з `rpl_semi_sync_master_wait_point = AFTER_SYNC` у MySQL).

У такій конфігурації кожен `COMMIT` блокує клієнтський потік до отримання підтвердження від репліки. Якщо єдина синхронна репліка виходить з ладу, основний сервер бази даних повністю зупиняє обробку всіх операцій запису. Кластер стає менш доступним, ніж звичайна поодинока база даних без реплікації взагалі.

Інженерним компромісом є налаштування списків пріоритетів і кворумної синхронізації:

```
synchronous_standby_names = 'FIRST 1 (node_standby_1, node_standby_2)'
```

За такої схеми лідер чекає відповіді від будь-якої однієї репліки з переліку. Якщо одна репліка падає, запис продовжується через другу без зупинки кластера.

### 2. Залежність від кворуму DCS
Автоматичний failover на базі Patroni робить саму базу даних залежною від здоров'я кластера `etcd`. Якщо в кластері з трьох вузлів `etcd` падають два сервери, розподілене сховище консенсусу втрачає кворум. У цей момент Patroni на активному primary фіксує неможливість оновити ліз і заради запобігання split-brain **примусово переводить працюючу базу даних у режим Read-Only**.

Таким чином, помилка в обслуговуванні сервісу консенсусу здатна призвести до простою здорової бази даних. DCS-кластери вимагають розміщення вузлів у різних зонах доступності (Availability Zones) та окремого виділеного моніторингу.

### 3. HA не замінює резервне копіювання
Найнебезпечніша ілюзія полягає в ототожненні високої доступності з резервним копіюванням. HA-кластер захищає виключно від відмови обладнання чи операційної системи. Якщо розробник випадково виконає команду `DROP TABLE users;` або деструктивну міграцію, ця операція реплікується на всі репліки за мілісекунди. Захист від людських помилок досягається лише ізольованими незмінними резервними копіями (Point-In-Time Recovery, PITR) на базі архівування WAL.

### Порівняльна матриця архітектур перемикання

| Архітектурний підхід | Механізм консенсусу | Типовий RTO | Ризик Split-Brain | Складність експлуатації |
|---|---|---|---|---|
| **Ручне перемикання** | Людина-оператор | 20–120 хв | Низький (контроль людиною) | Низька (але високий стрес) |
| **Active-Standby (VIP / Pacemaker)** | Corosync / Heartbeat + STONITH | 30–60 с | Середній (ризик збою IPMI) | Висока (крихкість Pacemaker) |
| **DCS Lease (Patroni / etcd)** | Raft / TTL-лізинг у etcd/Consul | 5–15 с | Мінімальний (захист лізингом) | Середня (стандарт індустрії) |
| **MySQL Orchestrator** | Зовнішній моніторинг топології + GTID | 10–30 с | Низький (автоматичний fencing) | Середня |
| **Distributed SQL (CockroachDB/Spanner)** | Вбудований Raft/Paxos на рівні шарду | < 1 с | Нульовий (математична модель) | Низька для користувача |

Побудова відмовостійкої бази даних з високою доступністю — це завжди пошук балансу між ризиком втрати даних (RPO), часом перемикання (RTO), накладними витратами на міжвузлову латентність і надійністю механізмів ізоляції вузлів.
