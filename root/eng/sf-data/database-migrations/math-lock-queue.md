# 📐 Математична формалізація черги блокувань DDL та каскадного блокування

Виконання команд зміни схеми (Data Definition Language, DDL) у реляційних базах даних регулюється матрицею сумісності блокувань та детермінованою чергою запитів на рівні ядра СУБД. Навіть мілісекундна затримка DDL-операції, яка потребує ексклюзивного блокування (наприклад, `AccessExclusiveLock`), може спричинити лавиноподібне блокування всіх активних клієнтських підключень (Lock Cascade / Connection Starvation).

Ця вставка містить математичну формалізацію черги транзакційних блокувань, матрицю конфліктів режимів доступу та аналітичну модель оцінки затримки клієнтських транзакцій за теорією масового обслуговування.

---

### Формальна модель простору транзакцій і режимів блокувань

Нехай `T = {t_1, t_2, ..., t_n}` — множина активних транзакцій у системі, а `R` — цільовий табличний ресурс (Relation).

Кожна транзакція `t` запитує доступ до ресурсу `R` у певному режимі блокування `m(t) \in M`.

У системі PostgreSQL множина режимів блокування відношень `M` містить 8 рівнів, упорядкованих за спаданням сумісності:
1. `AccessShare` (читання `SELECT`)
2. `RowShare` (`SELECT FOR UPDATE`)
3. `RowExclusive` (`INSERT`, `UPDATE`, `DELETE`)
4. `ShareUpdateExclusive` (`VACUUM`, `CREATE INDEX CONCURRENTLY`)
5. `Share` (`CREATE INDEX`)
6. `ShareRowExclusive` (`CREATE TRIGGER`)
7. `Exclusive` (`REFRESH MATERIALIZED VIEW CONCURRENTLY`)
8. `AccessExclusive` (`ALTER TABLE`, `DROP TABLE`, `TRUNCATE`)

---

### Матриця конфліктності та предикат сумісності

Сумісність між двома режимами блокування задається симетричною булевою функцією `Compatible(m_1, m_2) \in {true, false}`.

Два режими сумісні тоді й лише тоді, коли паралельне виконання відповідних операцій не порушує фізичної та логічної цілісності структури таблиці в оперативній пам'яті.

Ключовий інваріант максимального блокування:

```text
Для будь-якого режиму m із множини M: Compatible(AccessExclusive, m) = false
```

Це означає, що режим `AccessExclusive` несумісний із жодним іншим режимом, включно з найпростішим читанням `AccessShare`.

---

### Динаміка черги блокувань (Lock Queue)

Черга блокувань ресурсу `R` представляється впорядкованим списком `Q = <q_1, q_2, ..., q_k>`, де кожен елемент `q_i = (t_i, m_i)` представляє транзакцію та запитаний режим.

Правило диспетчеризації черги (FIFO з блокуванням сумісності):

1. **Транзакція отримує блокування (Granted Lock)**: Транзакція `q_j` переходить у стан виконання тоді й лише тоді, коли її режим `m_j` сумісний з усіма вже активними транзакціями `Active(R)`, і перед нею в черзі `Q` немає жодної несумісної очікуючої транзакції.
2. **Блокування наступних запитів (Head-of-Line Blocking)**: Якщо в чергу потрапляє транзакція `t_ddl` із запитом `AccessExclusive`, вона переходить у стан очікування (Wait State), доки не завершаться всі активні `SELECT`-запити.
3. **Каскадне зависання нових читачів**: Будь-який новий `SELECT`-запит `t_new`, що надходить після `t_ddl`, стає в кінець черги `Q` позаду `t_ddl`. Хоча `t_new` сумісний з активними транзакціями `AccessShare`, планувальник СУБД блокує його виконання для захисту від голодування (Starvation) операції `t_ddl`.

```text
Стан системи:
[Активні]: SELECT (AccessShare, триває 10 сек)
[Черга #1]: ALTER TABLE (AccessExclusive, чекає завершення SELECT)
[Черга #2..N]: Нові швидкі SELECT/INSERT (Заблоковані чергою #1!)
```

### Ймовірнісна модель накопичення каскаду блокувань

Нехай вхідний потік коротких OLTP-транзакцій до таблиці `R` є пуассонівським із середньою інтенсивністю `\lambda` транзакцій на секунду.

Нехай час виконання випадкової тривалої транзакції читання, яка утримує `AccessShare`, становить `D` секунд.

Якщо команда `ALTER TABLE` надходить у випадковий момент часу `\tau`, час її очікування `W_ddl` становить залишковий час роботи активного читача:

```text
Середній час очікування E[W_ddl] = D / 2
```

За час очікування `W_ddl` у черзі позаду DDL накопичується випадкова кількість заблокованих звичайних транзакцій `N_blocked`:

```text
Середня кількість заблокованих запитів: E[N_blocked] = \lambda * E[W_ddl] = \lambda * (D / 2)
```

#### Розрахунок ризику вичерпання пулу з'єднань

Нехай максимальний розмір пулу з'єднань СУБД становить `C_{max}` (наприклад, 200 підключень).

Ймовірність повного вичерпання пулу та відмови системи (HTTP 500 / Connection Timeout) визначається формулою:

```text
P(Downtime) = P(N_blocked >= C_{max})
```

Для розподілу Пуассона ця ймовірність описується сумою:

```text
P(Downtime) = 1 - \sum_{k=0}^{C_{max}-1} \frac{(\lambda * W_ddl)^k * e^{-(\lambda * W_ddl)}}{k!}
```

**Числовий приклад розрахунку катастрофи:**
* Інтенсивність запитів: `\lambda = 500` запитів/сек.
* Залишковий час тривалого фонового звіту: `W_ddl = 3` секунди.
* Кількість підключень у пулі: `C_{max} = 200`.

Середня кількість накопичених запитів за 3 секунди:

```text
E[N_blocked] = 500 * 3 = 1500 запитів
```

Оскільки 1500 значно перевищує ємність пулу `C_{max} = 200`, пул підключень буде повністю вичерпано вже через `200 / 500 = 0.4` секунди після старту команди `ALTER TABLE`. Усі наступні користувацькі запити до будь-яких інших таблиць завершаться критичною помилкою `FATAL: remaining connection slots are reserved for non-replication superuser connections`.

### Математичне обґрунтування захисного тайм-ауту lock_timeout

Для запобігання каскадному блокуванню транзакція DDL зобов'язана встановлювати строгий ліміт очікування на рівні сесії:

```sql
SET lock_timeout = '1s';
```

Якщо протягом часу `T_{lock} < C_{max} / \lambda` блокування не було надано, СУБД автоматично перериває DDL-операцію з помилкою `ERROR: 55P03: canceling statement due to lock timeout`.

Це гарантує верхню межу накопичення черги:

```text
N_blocked <= \lambda * T_{lock} < C_{max}
```

Пул підключень не вичерпується, а система продовжує стабільно обслуговувати користувачів без зупинки роботи сервісу.

### Аналіз взаємних блокувань (Deadlock Detection Graph)

Коли міграція змінює дві пов'язані таблиці (наприклад, додає зовнішній ключ між `orders` та `users`), транзакція запитує множинні замки: `Lock(R_1)` та `Lock(R_2)`.

Нехай паралельна транзакція `t_app` модифікує рядки у зворотному порядку: спершу захоплює рядок у `users`, а потім вставляє запис у `orders`.

Граф очікування (Wait-For Graph) `G = (V, E)` містить цикл:

```text
t_ddl -> t_app (очікування замка на users)
t_app -> t_ddl (очікування замка на orders)
```

#### Теорема про виявлення циклу в графі очікувань

Наявність циклу в орієнтованому графі `G` є необхідною і достатньою умовою виникнення взаємного блокування (Deadlock). Фоновий детектор ядра СУБД сканує граф `G` раз на `deadlock_timeout` (за дефолтом 1 секунда), знаходить топологічний цикл та примусово скасовує одну з транзакцій помилкою `ERROR: 40P01: deadlock detected`.

Встановлення параметра `lock_timeout` меншим за `deadlock_timeout` гарантує, що міграція коректно завершиться та звільнить чергу до того, як детектор дедлоків запустить важкий аналіз графів.

---

### Аналіз алгоритму повторних спроб (Exponential Backoff with Jitter)

Коли міграція переривається через спрацювання `lock_timeout`, автоматичний агент повторює спробу через інтервал часу `t_{retry}`:

```text
t_{retry} = min(t_{max}, t_{base} * 2^k + random(0, \delta))
```

Де `k` — номер невдалої спроби, а `random(0, \delta)` — випадковий шум (Jitter), що запобігає синхронному зіткненню повторних DDL-запитів із періодичними фоновими завданнями (Cron jobs / Vacuum workers).

Математично доведено, що додавання випадкового шуму зменшує ймовірність повторного конфлікту блокувань на понад 80%, дозволяючи безпечно інтегрувати міграції у високонавантажені цілодобові конвеєри розгортання без ризику деградації пропускної здатності.
