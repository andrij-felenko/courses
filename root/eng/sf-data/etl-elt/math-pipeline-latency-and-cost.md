# 🧮 Математичні моделі конвеєрів: затримка, пропускна здатність та вартість обчислень

Архітектурний вибір між ETL та ELT зводиться до балансу трьох фізичних обмежень комп'ютерної системи: пропускної здатності мережі, обсягу оперативної пам'яті для операцій з'єднання та вартості оренди обчислювальних ядер у хмарі.

## 1. Декомпозиція наскрізної затримки конвеєра

Нехай із джерела надходить батч обсягом `N` сирих записів. Середній розмір сирого запису дорівнює `s_in` байтів. У процесі фільтрації та агрегації обсяг записів скорочується з коефіцієнтом вибірковості (селективності) `σ ≤ 1`, а розмір вихідного агрегованого рядка становить `s_out` байтів.

### Затримка в моделі ETL (обробка в проміжному кластері)

Дані проходять два мережевих плеча: від джерела до проміжного обчислювача (пропускна здатність `B_src`), а після фільтрації — від обчислювача до сховища (пропускна здатність `B_dwh`).

```
T_ETL
= T_net_in + T_cpu_mid + T_net_out + T_dwh_write             [сума затримок чотирьох послідовних фаз конвеєра]
= (N · s_in / B_src) + (N · τ_mid) + (σ · N · s_out / B_dwh) + (σ · N · τ_write)  [підстановка обсягів, трафіку та тривалості запису]
= N · (s_in / B_src + τ_mid + σ · (s_out / B_dwh + τ_write)) [винесення загального множника N за дужки]
```

де:
- `τ_mid` — середній час десеріалізації, трансформації та валідації одного запису на ядрах проміжного обчислювача (секунд/запис);
- `τ_write` — питомий час індексації та запису одного рядка у фінальну таблицю сховища (секунд/запис).

### Затримка в моделі ELT (пряме скидання та обробка рушієм сховища)

Сирі дані одразу записуються у шар прийому (staging/bronze) сховища через одне мережеве плече, після чого всередині сховища запускається паралельний SQL-рушій.

```
T_ELT
= T_net_direct + T_dwh_raw_write + T_sql_transform           [сума прямої передачі, скидання сирого блоку та SQL-трансформації]
= (N · s_in / B_src) + (N · τ_raw_write) + T_sql(N, P)       [підстановка параметрів мережевого потоку, запису та кластера]
```

де:
- `τ_raw_write` — питомий час блокового скидання сирих неіндексованих байтів (append-only запис у Parquet/ORC);
- `T_sql(N, P)` — час виконання трансформаційного запиту паралельно на `P` вузлах сховища.

### Точка рівноваги затримки

Порівняємо різницю в затримках `ΔT = T_ETL - T_ELT`:

```
ΔT
= T_ETL - T_ELT                                              [різниця тривалості повного циклу двох архітектур]
= N · (τ_mid - τ_raw_write + σ · (s_out / B_dwh + τ_write)) - T_sql(N, P)  [підстановка аналітичних виразів затримок]
```

Коли обсяг вхідних даних `N` великий, а коефіцієнт скорочення слабкий (`σ ≈ 1`), паралельний стовпцевий рушій сховища виконує обробку за час `T_sql(N, P) = O(N / P)`. Оскільки проміжний ETL-сервер зазвичай має фіксовану кількість ядер `P_mid ≪ P`, при зростанні `N` затримка `T_ETL` росте значно швидше за `T_ELT`.

## 2. Оптимізація інтервалу мікробатчу та затримка черги

Якщо конвеєр працює не безперервно, а запускається періодично з часовим вікном `W` секунд (розмір порції), на затримку доступності даних накладаються накладні витрати запуску транзакцій.

Нехай вхідний потік подій має середню інтенсивність `λ` записів/с. Тоді за інтервал `W` накопичується порція `N(W) = λ · W` записів.

Кожен запуск батчу вимагає фіксованого часу накладних витрат `T_fix` (створення з'єднання, відкриття файлів, запис транзакційного лога, оновлення маніфесту партицій). Питомий час обробки одного запису становить `τ`.

```
Час обробки одного батчу:
T_proc(W)
= T_fix + τ · λ · W      [фіксована ініціалізація + лінійна обробка порції]
```

### Середня затримка доступності запису

Запис, що надійшов у буфер, очікує в середньому `W / 2` секунд до моменту закриття вікна, після чого очікує завершення обробки всього батчу:

```
L(W)
= (W / 2) + T_proc(W)      [час очікування у вікні + тривалість обчислення]
= W / 2 + T_fix + τ · λ · W
= T_fix + W · (1/2 + τ · λ)
```

### Умова стабільності конвеєра

Щоб черга вхідних даних не зростала необмежено, обробка батчу повинна завершуватися до закінчення наступного інтервалу накопичення:

```
T_proc(W) < W
T_fix + τ · λ · W < W      [підстановка часу обробки]
W · (1 - τ · λ) > T_fix    [перенесення членів з W]
W > T_fix / (1 - τ · λ)    [за умови, що навантаження системи τ · λ < 1]
```

Якщо `τ · λ ≥ 1`, система перевантажена, і жоден розмір вікна `W` не врятує конвеєр від відставання (*lag*).

### Оптимальне вікно за критерієм сукупних витрат

Збільшення `W` зменшує частоту запусків і сумарні витрати на ініціалізацію транзакцій `c_tx / W`, але збільшує штраф за запізнення даних `c_lat · L(W)`.

```
Сукупна функція вартості:
C(W)
= c_lat · L(W) + c_tx / W
= c_lat · (T_fix + W · (1/2 + τ · λ)) + c_tx / W

Мінімізація функції вартості (похідна за W дорівнює нулю):
dC/dW = c_lat · (1/2 + τ · λ) - c_tx / W² = 0
W² = c_tx / (c_lat · (1/2 + τ · λ))
W_opt = √( c_tx / (c_lat · (1/2 + τ · λ)) )
```

Ця формула визначає оптимальну точку перемикання між потоковим мікробатчем (малий `W`, секунди) та класичним пакетним завантаженням (великий `W`, хвилини або години).

## 3. Обмеження пам'яті та дискове скидання операцій з'єднання

Найважчою операцією трансформації є з'єднання (*JOIN*) потоку фактів `S` із таблицею вимірів `R`.

### Хеш-з'єднання в пам'яті (In-Memory Hash Join)

Для виконання швидкого з'єднання конвеєр будує хеш-таблицю над меншою таблицею `R`. Якщо розмір таблиці `|R|` записів, а коефіцієнт накладних витрат хеш-структури дорівнює `α` (типово `α ≈ 0.4–0.8`), необхідний обсяг RAM становить:

```
M_hash = |R| · s_R · (1 + α)
```

Якщо `M_hash ≤ M_RAM`, з'єднання виконується в один прохід зі складністю часу `O(|R| + |S|)`.

### Дискове скидання (Spill to Disk) у проміжному ETL

Якщо вимір `R` не вміщується в пам'ять виділеного воркера (`M_hash > M_RAM`), рушій вимушений використовувати гібридне хеш-з'єднання або зовнішнє сортування-злиття (*External Sort-Merge Join*).

Кількість додаткових дискових операцій вводу-виводу (*I/O passes*):

```
IO_spill
= 2 · (|R| · s_R + |S| · s_S) · ⌈log_{K}(|R| · s_R / M_RAM)⌉
```

де `K` — фактор злиття (*fan-in/fan-out factor*).

Кожен дисковий скид уповільнює ETL-конвеєр у 5–20 разів через перехід від швидкості RAM (~50 ГБ/с) до швидкості локального NVMe або мережевого блокового накопичувача (~0.5–2 ГБ/с).

### Перевага розподіленого ELT над стовпцевими даними

У моделі ELT з'єднання виконує аналітичне сховище, яке використовує паралельний розподіл за ключем (*Shuffle / Broadcast Join*):
1. Якщо вимір невеликий (`M_hash ≤ M_node`), рушій транслює його на всі `P` обчислювальних вузлів (*Broadcast*), уникаючи пересилання великої таблиці `S`.
2. Якщо обидві таблиці великі, рушій партиціонує обидва набори за хешем ключа з'єднання між вузлами кластера, зводячи локальний розмір порції до `|R| / P`.

```
Обсяг пам'яті на один вузол у розподіленому ELT:
M_node = (|R| / P) · s_R · (1 + α)
```

Збільшуючи кількість обчислювальних вузлів `P` під час нічного перерахунку, ELT утримує операцію в межах RAM без деградації на дискове скидання.

## 4. Модель сукупної вартості володіння (TCO)

Вартість експлуатації конвеєрів у хмарній інфраструктурі складається з вартості обчислювальних ресурсів, трафіку та дисків:

```
Вартість ETL:
Cost_ETL = P_mid_server · T_uptime + P_egress · (N · s_in) + P_storage · Size_DWH

Вартість ELT:
Cost_ELT = P_light_loader · T_load + P_dwh_query · T_sql_active + P_storage · (Size_Raw + Size_DWH)
```

де:
- `P_mid_server` — фіксована погодинна оренда виділеного ETL-кластера (Spark/Airflow workers);
- `P_dwh_query` — вартість безсерверних обчислень DWH за секунду активного виконання запиту;
- `P_egress` — ціна передачі трафіку між зонами доступності чи хмарами;
- `Size_Raw` — обсяг сирих незмінних даних в об'єктному сховищі.

Оскільки ціна холодного об'єктного зберігання `P_storage` надзвичайно низька (~$0.02 за ГБ на місяць), а безсерверні обчислення тарифікуються посекундно лише під час виконання запиту, модель ELT виявляється економічно вигіднішою для більшості аналітичних сценаріїв, де важкі перерахунки відбуваються за розкладом, а не цілодобово.
