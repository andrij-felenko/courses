# Ліниве завантаження

<preknowlist>
- [Інтерфейс проти реалізації](root:sf-apps/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні, і тим, ЯК він це робить усередині; заступник підставляється за тим самим інтерфейсом, і клієнт не помічає підміни.
- [Поліморфізм і динамічне зв'язування](root:sf-lang/polymorphism) — виклик через спільний тип у рантаймі йде в потрібну реалізацію; без цього клієнт розрізняв би заступника й справжній об'єкт.
</preknowlist>

Уяви, що просиш у бази даних одне замовлення — `findOrder(42)`. У пам'яті програми замовлення це об'єкт `Order`, і в нього є поле з покупцем, у покупця список його замовлень, у кожному замовленні товари, у товару постачальник, у постачальника знову замовлення. Об'єктна модель у голові програми це суцільна павутина, де від будь-чого можна дійти майже до будь-чого. База ж тримає все це пласко, розкладеним по таблицях, і цей розрив між зв'язаним графом об'єктів і плоскими рядками зветься [об'єктно-реляційна неузгодженість](root:sf-data/object-relational-mismatch).

І тут постає незручне питання: коли ти кажеш «завантаж `Order` номер 42», що саме має опинитися в пам'яті? Якщо чесно матеріалізувати все, до чого замовлення дотягується, один невинний `findOrder(42)` перетягне в оперативну пам'ять половину бази — покупця, всі його інші замовлення, всі товари в них, усіх постачальників, і так по колу, доки не скінчаться записи. Ніхто цього не хотів. Ти просив одне замовлення.

Отже, павутину треба десь **розрізати**. Власні поля `Order` — номер, дату, суму — завантажити обов'язково. А там, де `Order` показує на покупця, покласти не самого покупця, а **обіцянку його дістати**: щось, що виглядає як посилання на покупця, але всередині тримає лише «покупець №7, ще не завантажений». Доторкнешся до нього — воно збігає в базу й підтягне покупця. Не доторкнешся — так і лишиться обіцянкою, і база не почує жодного зайвого запиту.

Оцей прийом — «клади замість даних обіцянку дістати їх і виконуй її лише коли по дані справді прийшли» — і є **ліниве завантаження (англ. *lazy* — лінивий, у сенсі "не роблю роботу, поки мене не змусять"; *load* — завантаження)**. Слово «лінивий» тут технічне й давнє: у теорії обчислень [лінивим](root:sf-lang/lazy-evaluation) називають усе, що відкладає роботу до моменту, коли результат насправді знадобиться. Мартін Фаулер, який завів цей прийом у свій каталог патернів корпоративних застосунків, сформулював суть так: об'єкт, що «не містить усіх потрібних даних, але знає, як їх дістати».

Прийом має одну форму, хоч би як його будували: об'єкт, що вдає з себе цілого, а насправді є заглушкою, яка знає, як себе доповнити. Зібрати таку заглушку можна чотирма способами, і вони по-різному відповідають на питання «хто саме тримає лінь і наскільки помітно».

![Ліворуч жадібне завантаження: у центрі об'єкт Order, від нього суцільні стрілки до Customer, LineItem, Product, і ті знову розгалужуються в щільну павутину зв'язаних коробок — підпис "один запит тягне всю павутину". Праворуч ліниве: той самий Order суцільний, але його зв'язки ведуть до пунктирних заглушок з написом "ключ, підтягнеться на дотик" — підпис "вантажимо Order, решту на вимогу"](img/graph-cut.svg)

*Об'єктний граф зв'язаний наскрізь, тож жадібне завантаження одного вузла тягне за собою майже все. Ліниве розрізає граф на межі: вантажить сам об'єкт, а на місце зв'язків кладе легкі заглушки, що знають лише ключ.*

## Найдешевший спосіб — лінива ініціалізація

У найпростішому вигляді ліниве завантаження не потребує ні окремих класів, ні хитрощів — лише порожнього поля й геттера, що заповнює його на перший доступ. Це **лінива ініціалізація (англ. *lazy initialization*)**.

:::tabs
```ts
class Order {
  private _customer: Customer | null = null;      // ще не тягнули
  constructor(readonly id: number, private customerId: number) {}

  get customer(): Customer {
    if (this._customer === null) {
      this._customer = db.loadCustomer(this.customerId);   // один похід у базу
    }
    return this._customer;
  }
}
```
```py
class Order:
    def __init__(self, id: int, customer_id: int) -> None:
        self.id = id
        self._customer_id = customer_id
        self._customer: Customer | None = None          # ще не тягнули

    @property
    def customer(self) -> Customer:
        if self._customer is None:
            self._customer = db.load_customer(self._customer_id)   # один похід у базу
        return self._customer
```
:::

Усе, що читає `order.customer`, бачить покупця й навіть не підозрює, що перше читання тихо сходило в базу. Кожне наступне читання віддає вже готове поле — база більше не чіпається. Коштує це майже нічого: одне поле й кілька рядків. Ідея «порахувати раз і запам'ятати результат» — це, по суті, [мемоізація](root:sf-algorithms/memoization), застосована до одного поля.

Але в самому «порожнє поле означає не завантажено» схована пастка. Ознакою «ще не тягнув» тут служить `null`. А що, як `null` — це законне значення? Замовлення без покупця (гостьова покупка) цілком реальне. Тоді геттер не може відрізнити «покупця немає» від «покупця ще не тягнув» і на кожен доступ марно грюкає в базу по тому, чого там і нема. Лікують це окремим прапорцем, що чесно каже, вантажили вже чи ні:

```ts
private _customer: Customer | null = null;
private loaded = false;

get customer(): Customer | null {
  if (!this.loaded) {
    this._customer = db.loadCustomer(this.customerId);
    this.loaded = true;
  }
  return this._customer;   // тепер null означає «покупця немає», а не «не вантажив»
}
```

> 🔧 **Навіщо це.** Лінива ініціалізація — це той хід, який варто пробувати першим, бо він найдешевший: жодного нового типу, лінь живе прямо в об'єкті-власнику. Вона окупається там, де важке лише **одне поле**, а не весь об'єкт: звіт із дорогою діаграмою, велике зображення, обчислення, яке потрібне не завжди. Кладеш поле порожнім, ховаєш підтягування в геттер — і решта коду користується об'єктом, не знаючи, що частина його з'являється пізно.

## Віртуальний проксі — заступник із тим самим інтерфейсом

Лінива ініціалізація ховає лінь усередині власника: це `Order` вирішує, коли підтягнути покупця. Але буває, що власника чіпати не можна, а ліниву поведінку треба почепити на сам об'єкт, що вантажиться, — так, щоб будь-хто, хто тримає посилання на покупця, отримував лінь безкоштовно. Тоді замість справжнього об'єкта клієнтові підсовують **заступника** з тим самим інтерфейсом, який тримає лише ключ, а справжній об'єкт створює на перший виклик і далі передоручає йому виклики. Це [віртуальний проксі](root:sf-apps/proxy) — окремий випадок патерна «проксі».

```ts
class CustomerProxy implements Customer {
  private real: RealCustomer | null = null;
  constructor(private id: number) {}                   // тримає лише ключ

  private load(): RealCustomer {
    return this.real ??= db.loadCustomer(this.id);     // справжнього створює раз
  }
  get name(): string  { return this.load().name; }     // кожен метод делегує
  get email(): string { return this.load().email; }
}
```

Різниця з лінивою ініціалізацією принципова. Там порожнім було одне поле всередині цілого об'єкта; тут порожнім є **весь об'єкт**, підмінений заступником. Клієнт тримає в руках тип «покупець», викликає в нього методи й ніяк не може здогадатися, що перед ним не справжній покупець, а підставний, який тільки на перший метод збігає в базу. Через цю прозорість проксі й зручний: його можна вкрутити в уже написану систему, не змінивши в ній жодного рядка.

Платити доводиться двома речами. По-перше, проксі мусить **чесно повторити весь інтерфейс** справжнього об'єкта: додав покупцеві метод — не забудь додати його й у проксі, інакше заступник відстане від оригіналу. По-друге, проксі — це **інший об'єкт**, ніж справжній покупець, тож порівняння за посиланням (`proxy === real`) дасть хибу, і код, що звіряє об'єкти на тотожність, спіткнеться. Саме тому проксі рідко ходять поодинці: їх ставлять поряд з [identity map](root:sf-data/identity-map), яка стежить, щоб один рядок бази завжди давав один і той самий об'єкт у пам'яті.

## Тримач значення — обгортка навколо самого значення

Писати окремий клас-проксі на кожен тип нудно. Третій спосіб знімає цю рутину: замість заступника, що вдає покупця, беруть **тримач значення (англ. *value holder*)** — узагальнену обгортку з одним методом `getValue()`, яка сама знає, як дістати те, що тримає. Замовлення тримає в полі не покупця, а тримача покупця.

```ts
class ValueHolder<T> {
  private value: T | null = null;
  constructor(private fetch: () => T) {}                 // як дістати — знає обгортка

  getValue(): T {
    if (this.value === null) this.value = this.fetch();  // перший виклик тягне
    return this.value;
  }
}

class Order {
  readonly customer: ValueHolder<Customer>;
  constructor(readonly id: number, customerId: number) {
    this.customer = new ValueHolder(() => db.loadCustomer(customerId));
  }
}

order.customer.getValue().name;   // клієнт свідомо просить значення
```

Тримач чесніший за проксі: клієнт бачить `.getValue()` і **знає**, що тут лінь, — прозорості немає, зате немає й підступності. За цю чесність він отримує узагальненість: один `ValueHolder<T>` обслуговує і покупця, і товар, і будь-що інше, тоді як проксі треба писати окремо під кожен тип. Ця ідея — маленький об'єкт, що «тримає місце» значення й уміє його дістати — [народилася в Smalltalk](root:sf-data/lazy-loading/hist-value-holder-smalltalk.md) задовго до сучасних бібліотек доступу до даних.

## Привид — сам об'єкт, завантажений наполовину

Четвертий спосіб — найтонший. **Привид (англ. *ghost* — привид, тінь)** це сам справжній об'єкт, але створений з одним лише ключем і порожніми полями. Він не заступник і не обгортка — це той самий об'єкт, тільки ще не наповнений. Перший же доступ до будь-якого поля змушує привида підтягнути в базу **всі свої поля разом**, одним запитом, і далі він поводиться як звичайний повний об'єкт.

```ts
class Customer {
  private loaded = false;
  private _name = "";
  private _email = "";
  constructor(readonly id: number) {}          // «привид»: лише id, полів ще нема

  private fill(): void {
    if (this.loaded) return;
    const row = db.loadCustomer(this.id);       // один запит — і ВСІ поля разом
    this._name = row.name;
    this._email = row.email;
    this.loaded = true;
  }
  get name(): string  { this.fill(); return this._name; }
  get email(): string { this.fill(); return this._email; }
}
```

Порівняй із віртуальним проксі, і різниця стане чіткою. Проксі — це **окремий** об'єкт, що на перший виклик створює **другий**, справжній, і делегує йому; звідси й морока з тотожністю. Привид — це **один** об'єкт, що доповнює **сам себе** на місці, тож його тотожність із самого початку правильна. І ще: проксі можна змусити вантажити по полю за раз, а привид за задумом тягне все за один похід — що зазвичай і треба, бо один запит на всі поля дешевший за десяток дрібних. Саме на привидах і проксі стоять справжні [ORM](root:sf-data/orm) — бібліотеки, що відображають об'єкти на таблиці: коли ти дістаєш замовлення, його покупець найчастіше повертається саме привидом.

## Тіньовий бік — брижі запитів

Ліниве завантаження оманливо приємне, і саме приємність його підводить. Поки ти торкаєшся лінивих зв'язків зрідка — усе чудово. Але постав ліниве завантаження за замовчуванням, а тоді пройдися циклом — і воно обернеться штормом дрібних запитів.

Дістаєш сто замовлень одним запитом. Потім у циклі для кожного показуєш ім'я покупця — торкаєшся `order.customer.name`. Кожен дотик будить лінивого покупця, і той біжить у базу окремим запитом. Один запит на список плюс по одному на кожен елемент — разом сто один запит там, де мало бути кілька:

```
1 запит   — SELECT * FROM orders            → 100 замовлень
+ 100      — SELECT * FROM customers WHERE id = ?   (по разу на кожне)
= 101 запит до бази заради одного екрана
```

Це і є сумнозвісна **проблема N+1** (у Фаулера — *ripple loading*, «брижі завантаження»): одна логічна дія розсипається на хвильку з N дрібних запитів. У світі ORM це чи не найпоширеніша причина, чому застосунок раптом починає повзати. Лікують її не відмовою від лінивого завантаження, а **знанням свого сценарію**: там, де ти напевно пройдешся по покупцях, попроси базу підтягнути їх наперед, одним запитом-з'єднанням, замість ста ледачих. Тобто ліниве завантаження — це не чеснота, а **регулятор за замовчуванням**: лінивий, щоб не тягнути всю павутину даремно, і жадібний саме на тих стежках, якими ти точно підеш. Числа за цим компромісом розкладено в [окремому розборі N+1](root:sf-data/active-record/math-n-plus-one.md).

![Угорі "ліниво в циклі": один запит зліва повертає N замовлень, далі цикл, і від кожного замовлення окрема коротка стрілка-запит до бази — разом підпис "1 + N = 101 запит при N=100". Унизу "жадібно наперед": один запит-з'єднання зліва одразу повертає замовлення разом з покупцями — підпис "1 запит". Стрілка-висновок збоку: той самий екран, у 100 разів менше походів у базу](img/ripple-nplus1.svg)

*Ліниве завантаження в циклі перетворює одну дію на зливу дрібних запитів (N+1). Коли наперед відомо, що зв'язок знадобиться, жадібне з'єднання забирає всі дані одним запитом.*

## Коли брати, а коли ні

Тепер видно всю картину, і компроміс простий. Ліниве завантаження виграє, коли пов'язані дані **часто не потрібні** й водночас **дорогі**: тоді відкладене підтягування економить і пам'ять, і час на те, чим ніхто не скористався. І воно програє у двох випадках. Перший — коли дані потрібні **завжди**: тоді лінь лише додає зайвий похід у базу пізніше замість того, щоб узяти все відразу. Другий — коли лінь **ховає ціну**: віддалений виклик, замаскований під звичайне читання поля, виглядає безкоштовним, і про його вартість забувають — аж поки цикл не обернеться тими самими брижами.

Є й третя пастка, тонша. Ліниве поле, яке вперше заповнюють, — це запис, і якщо до нього одночасно дотягнуться два потоки, вони можуть завантажити його двічі або, гірше, побачити напівзаповнений об'єкт. Тому ліниву ініціалізацію в багатопотоковому коді доводиться захищати — і тут спливають ті самі прийоми, що й у сінглтоні: [подвійна перевірка з блокуванням](root:sf-apps/singleton/math-double-checked-locking.md) та інші механізми [потокової безпеки](root:sf-tasks/thread-safety).

Чотири способи вишиковуються в спектр за тим, наскільки лінь помітна й де вона живе. **Лінива ініціалізація** тримає лінь усередині власника — найдешевша, добра для одного важкого поля. **Віртуальний проксі** підставляє прозорого заступника — непомітний клієнтові, але коштує окремого класу й мороки з тотожністю. **Тримач значення** робить лінь явною й узагальненою — чесний, але клієнт мусить знати про `getValue()`. **Привид** доповнює сам себе на місці, одним запитом на всі поля — зберігає тотожність, і на ньому стоять ORM. Способи не ворогують: їх [комбінують у робочому коді](root:sf-data/lazy-loading/proj-lazy-loading-graph.md), де видно і як усі чотири працюють над одним графом об'єктів, і як N+1 виникає й лікується під лічильником запитів.

Суть же одна, і варто тримати її в голові окремо від технік. Ліниве завантаження розділяє дві речі, які легко сплутати: **мати посилання на дані** й **мати самі дані**. Об'єкт може тримати посилання, не тримаючи даних, а лише спосіб їх дістати. У цьому вся сила прийому — не тягнути павутину, поки по неї не прийшли, — і вся його небезпека: розтягнути те саме тягання на сотню дрібних ковтків, коли по павутину таки прийшли, та ще й у циклі.
