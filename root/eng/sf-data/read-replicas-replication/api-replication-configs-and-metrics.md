# 📋 Параметри конфігурації, системні виклики та метрики реплікації (PostgreSQL, MySQL, ProxySQL)

Керування кластером реплікації вимагає точного розуміння внутрішніх механізмів ядра СКБД, налаштування мережевих протоколів передачі журналу, конфігурації проміжних балансувальників та безперервного моніторингу метрик затримки. У цьому довіднику наведено вичерпний опис конфігураційних параметрів, системних представлень, діагностичних запитів, сесійних функцій координації та правил маршрутизації для PostgreSQL 14+, MySQL 8.0+ та ProxySQL 2.x з детальним аналізом їхнього впливу на надійність та продуктивність системи.

## 1. Конфігураційний інтерфейс PostgreSQL

Архітектура фізичної та логічної реплікації PostgreSQL спирається на параметри файлу `postgresql.conf`, які визначають поведінку генерації журналу попереднього запису (WAL), кількість фонових процесів передачі даних, рівні синхронності транзакцій та правила вирішення конфліктів у режимі `Hot Standby`.

### Параметри первинного вузла (Primary)

#### `wal_level` (перелік: `minimal`, `replica`, `logical`)
Визначає обсяг та структуру інформації, що записується у журнал WAL.
- `minimal`: Фіксує лише інформацію, необхідну для відновлення після раптового збою живлення (Crash Recovery). У цьому режимі операції масового завантаження (`COPY`, `CREATE INDEX`) не записують повні образи сторінок у WAL. Стримінгова реплікація та базове резервне копіювання заблоковані.
- `replica` (значення за замовчуванням): Записує повну інформацію про всі зміни дискових сторінок, фіксації транзакцій та структури каталогів, необхідну для підтримки фізичних реплік (`Hot Standby`) та потокового відновлення до точки в часі (PITR).
- `logical`: На додаток до даних рівня `replica` додає логічні маркери зміни рядків, схеми таблиць та інформацію про первинні ключі, необхідну плагінам логічного декодування (Logical Decoding / CDC). Вимагає приблизно на 10–15% більше дискового простору під WAL.

#### `max_wal_senders` (ціле число, замовчуванням `10`)
Встановлює максимальну кількість одночасних процесів `walsender`. Кожна підключена фізична або логічна репліка, а також кожна утиліта зняття резервних копій (`pg_basebackup`, pgBackRest) займає рівно один процес `walsender`. Якщо ліміт вичерпано, нові репліки отримують помилку підключення `FATAL: number of requested standby connections exceeds max_wal_senders`. Значення повинно перевищувати планову кількість реплік щонайменше на 3–5 одиниць для забезпечення вікон бекапу.

#### `max_replication_slots` (ціле число, замовчуванням `10`)
Визначає ліміт зареєстрованих слотів реплікації. **Слот реплікації (англ. *Replication Slot*)** — це механізм гарантії того, що первинний вузол не видалить і не перезапише сегменти журналу WAL (навіть під час проходження чекпоінтів), поки відповідна репліка не підтвердить їх отримання.
- *Експлуатаційна небезпека:* Якщо репліка відключається на тривалий час (наприклад, аварія сервера або мережева ізоляція), первинний вузол продовжує накопичувати всі нові сегменти WAL у директорії `pg_wal`. Без належного моніторингу це може призвести до 100% заповнення системного диска лідера та повної зупинки кластера.
- *Захисний параметр:* `max_slot_wal_keep_size` (за замовчуванням `-1` — нескінченно) обмежує максимальний обсяг WAL, який дозволено утримувати слоту (наприклад, `64GB`). Якщо відстаюча репліка перевищує цей ліміт, слот інвалідується, лідер видаляє старі сегменти для власного порятунку, а репліка переходить у стан помилки та потребує повторної ініціалізації з бекапу.

#### `synchronous_commit` (перелік: `off`, `local`, `remote_write`, `on`, `remote_apply`)
Керує гарантіями довговічності та затримкою фіксації транзакцій.
1. `off`: Клієнт отримує підтвердження `COMMIT` негайно після запису транзакції у пам'ять WAL-буферів лідера без очікування системного виклику `fsync()`. Знижує латентність до мікросекунд, але у разі знеструмлення можлива втрата останніх транзакцій (до 3 × `wal_writer_delay`).
2. `local` (стандарт для асинхронних систем): `COMMIT` повертається після скидання WAL на локальний диск лідера через `fsync()`. Передача на репліки відбувається асинхронно у фоні.
3. `remote_write`: Лідер очікує, поки виділена репліка підтвердить отримання байтів WAL та запис їх у буфер операційної системи (`write()`), без очікування дискового `fsync()` на репліці. Захищає від падіння процесу PostgreSQL на репліці, але не від повного знеструмлення заліза.
4. `on` (напівсинхронний/синхронний режим): Лідер очікує підтвердження від репліки про повне завершення системного виклику `fsync()` на її диску.
5. `remote_apply`: Лідер очікує не лише скидання WAL на диск репліки, а й фактичного застосування змін процесом відновлення (`startup process`) у буферний пул репліки. Це повністю ліквідує реплікаційний лаг і гарантує *Causal Consistency*, але збільшує латентність запису на лідері на час повного циклу apply на репліці.

#### `synchronous_standby_names` (рядок формату)
Задає список та пріоритет реплік, які беруть участь у синхронній фіксації.
- Пріоритетний список: `'FIRST 1 (standby1, standby2, standby3)'` — лідер очікує підтвердження від `standby1`. Якщо `standby1` стає недоступним, лідер автоматично переключається на очікування `standby2`.
- Кворумний список: `'ANY 2 (standby1, standby2, standby3)'` — лідер фіксує транзакцію, як тільки будь-які дві репліки з трьох підтвердили отримання журналу.

### Параметри репліки читання (`postgresql.conf`)

#### `hot_standby` (булеве: `on`, `off`)
Дозволяє відкривати клієнтські сесії та виконувати запити на читання (`SELECT`), поки сервер перебуває у стані відновлення (безперервно застосовує вхідний потік WAL). Якщо параметр вимкнено (`off`), сервер працює як холодний резерв (`Warm Standby`), відхиляючи будь-які зовнішні з'єднання.

#### `hot_standby_feedback` (булеве: `on`, `off`)
Вмикає зворотний зв'язок між реплікою та лідером.
- *Механіка:* Процес `walreceiver` на репліці періодично відправляє процесу `walsender` на лідері значення `xmin` (найстарішу активну транзакцію серед усіх відкритих сесій читання на репліці). Первинний вузол враховує це значення під час роботи фонового процесу `VACUUM`, забороняючи йому фізично видаляти старі версії рядків (мертві кортежі), які ще можуть знадобитися активним запитам на репліці.
- *Ціна рішення:* Повністю запобігає виникненню конфліктів відновлення (`snapshot conflicts`) на репліці, проте якщо на репліці зависає довгий аналітичний запит, процес `VACUUM` на лідері блокується, викликаючи критичне роздування таблиць та індексів (Table and Index Bloat) на всій системі.

#### `max_standby_streaming_delay` (час, замовчуванням `30s`)
Максимальний інтервал часу, протягом якого репліка відкладає застосування записів WAL, якщо вони конфліктують з активним запитом читання. Якщо за 30 секунд клієнтський запит не завершився, PostgreSQL примусово перериває його з помилкою `ERROR: canceling statement due to conflict with recovery`, звільняючи шлях для накатування журналу. Значення `-1` дозволяє нескінченне очікування, що призводить до необмеженого зростання реплікаційного лагу.

### Системні представлення діагностики PostgreSQL

#### Представлення `pg_stat_replication` (на боці Primary)

| Колонка | Тип | Опис та призначення |
| :--- | :--- | :--- |
| `application_name` | `text` | Назва підключеної репліки (параметр `application_name` у рядку підключення `primary_conninfo`). |
| `client_addr` | `inet` | IP-адреса хоста репліки. |
| `state` | `text` | Поточний стан потоку: `startup`, `catchup` (наздоганяє лідер), `streaming` (штатний потоковий режим), `backup`. |
| `sync_state` | `text` | Стан синхронності: `async` (асинхронна), `sync` (активна синхронна), `potential` (кандидат у синхронні), `quorum`. |
| `sent_lsn` | `pg_lsn` | Останній LSN, відправлений мережевим сокетом процесом `walsender`. |
| `write_lsn` | `pg_lsn` | Останній LSN, записаний процесом `walreceiver` у буфер ОС на репліці. |
| `flush_lsn` | `pg_lsn` | Останній LSN, фізично зафіксований на диску репліки викликом `fsync()`. |
| `replay_lsn` | `pg_lsn` | Останній LSN, фактично застосований процесом відновлення до сторінок пам'яті репліки. |
| `write_lag` | `interval` | Часова затримка між локальним записом на лідері та записом у буфер репліки. |
| `flush_lag` | `interval` | Часова затримка між локальним скиданням на лідері та `fsync()` на репліці. |
| `replay_lag` | `interval` | Повна часова затримка від моменту фіксації на лідері до видимості даних для читачів на репліці. |

#### Представлення `pg_stat_database_conflicts` (на боці репліки)

Відображає статистику скасованих запитів читання за типами конфліктів:
- `confl_tablespace`: Запит скасовано через те, що на лідері було видалено або переміщено табличний простір.
- `confl_lock`: Запит утримував блокування на таблиці (наприклад, `AccessShareLock`), яке конфліктувало з ексклюзивним блокуванням (наприклад, `AccessExclusiveLock` від `ALTER TABLE` або `DROP TABLE`), що надійшло з WAL.
- `confl_snapshot`: Процес відновлення мав перезаписати або очистити сторінку з мертвими рядками, які були необхідні знімку транзакції клієнта.
- `confl_bufferpin`: Клієнтський запит утримував штифт (Pin) сторінки в пам'яті надто довго, блокуючи операцію розщеплення або очищення блоку.
- `confl_deadlock`: Виникло взаємне блокування між процесом відновлення журналу та локальною транзакцією клієнта.

## 2. Конфігураційний інтерфейс MySQL (GTID & Multi-Threaded Replication)

У MySQL 8.0+ реплікація спирається на бінарний лог (Binlog), механізм глобальних ідентифікаторів транзакцій (GTID) та багатопотоковий рушій застосування змін (Multi-Threaded Slave, MTS).

### Параметри сервера (`my.cnf`)

#### `gtid_mode = ON` та `enforce_gtid_consistency = ON`
Вмикає генерацію та суворий контроль глобальних ідентифікаторів транзакцій.
- Кожна зафіксована транзакція отримує унікальний тег вигляду `Server_UUID:Transaction_ID` (наприклад, `3E11FA47-71CA-11E1-9E33-C80AA9429562:1420`).
- Дозволяє автоматично позиціонувати репліку при підключенні (`MASTER_AUTO_POSITION = 1`) без необхідності вручну вказувати назви файлів журналу та байти зміщення.
- `enforce_gtid_consistency` забороняє виконання SQL-конструкцій, які не гарантують атомарності в бінарному журналі (наприклад, транзакційні `CREATE TEMPORARY TABLE` всередині транзакцій або `CREATE TABLE ... SELECT`).

#### `binlog_format = ROW`
Переводить бінарний журнал у рядковий формат. Кожна подія журналу містить первинний ключ та точний образ змінених колонок рядка. Це усуває будь-який недетермінізм функцій часу та генераторів псевдовипадкових чисел.

#### `replica_parallel_workers` (ціле число, наприклад `8` або `16`)
Кількість робочих потоків пулу застосування транзакцій на репліці. За замовчуванням (значення `0` або `1`) реплікація виконується в один потік `SQL_THREAD`, що робить її вузьким місцем системи. Значення від 8 до 16 дозволяє репліці паралельно застосовувати незалежні транзакції, повністю утилізуючи всі процесорні ядра.

#### `replica_parallel_type = LOGICAL_CLOCK`
Визначає алгоритм визначення незалежності транзакцій для паралельного виконання.
- `DATABASE`: Паралельно можуть виконуватися лише транзакції, які змінюють різні схеми (бази даних). Для систем з однією основною базою даних це призводить до деградації в один потік.
- `LOGICAL_CLOCK`: Аналізує часові мітки груп комітів на первинному вузлі (Group Commit). Якщо дві або більше транзакцій перебували у процесі фіксації на Primary одночасно і не конфліктували за блокування рядків, репліка гарантовано може застосувати їх одночасно на різних ядрах.

#### `rpl_semi_sync_source_enabled = 1` та `rpl_semi_sync_source_timeout = 1000`
Вмикає модуль напівсинхронної реплікації. Первинний вузол після запису в бінарний лог чекає, поки хоча б одна репліка з увімкненим плагіном `rpl_semi_sync_replica` збереже подію у свій Relay Log. Якщо протягом 1000 мс підтвердження не надходить (наприклад, обрив мережі), сервер тимчасово переходить у чисто асинхронний режим, запобігаючи зупинці обслуговування клієнтів.

### Діагностика та контроль стану реплікації MySQL

#### Аналіз виводу `SHOW REPLICA STATUS`

Запит повертає критичні метрики стану реплікаційного конвеєра:

```sql
SHOW REPLICA STATUS\G
```

Ключові діагностичні поля:
1. `Replica_IO_State`: Поточний стан мережевого потоку читання. Нормальний стан — `Waiting for source to send event`.
2. `Replica_IO_Running: Yes`: Потік `IO_THREAD` успішно підключений до Primary і зчитує бінарний лог. Значення `No` свідчить про мережевий збій, невірні облікові дані або досягнення ліміту з'єднань на лідері.
3. `Replica_SQL_Running: Yes`: Потік `SQL_THREAD` успішно застосовує транзакції до сховища InnoDB. Значення `No` сигналізує про аварійну зупинку реплікації через помилку виконання (наприклад, дублікат унікального ключа `Error 1062` або відсутність рядка для оновлення `Error 1032`).
4. `Seconds_Behind_Source`: Наближена часова оцінка затримки накатування транзакцій у секундах. Розраховується як різниця між поточним системним годинником репліки та позначкою часу останньої транзакції, витягнутої з бінарного логу.
5. `Executed_Gtid_Set`: Діапазон усіх GTID, які повністю зафіксовані в локальній базі даних.
6. `Retrieved_Gtid_Set`: Діапазон GTID, які завантажені у локальний журнал Relay Log, але можуть ще очікувати застосування в черзі.

#### Сесійний виклик очікування GTID: `WAIT_FOR_EXECUTED_GTID_SET`

Дозволяє клієнтській сесії призупинити виконання читання, доки репліка не застосує вказаний набір транзакцій:

```sql
SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:1-150', 3.0);
```

- Аргумент 1: Специфікація необхідного набору GTID.
- Аргумент 2: Максимальний таймаут очікування в секундах (тип `double`, наприклад `3.0`).
- Повертає: `0` у разі успішного досягнення стану (можна безпечно виконувати `SELECT`); `1` якщо таймаут минув до завершення застосування транзакцій; `NULL` у разі помилки валідації аргументів.

## 3. Конфігураційний інтерфейс ProxySQL

ProxySQL керується через власний SQL-інтерфейс адміністрування (за замовчуванням порт `6032`). Конфігурація зберігається в оперативній пам'яті та трьох шарах: `MEMORY`, `RUNTIME` (активний робочий стан) та `DISK` (персистентна база даних SQLite).

### Реєстрація серверів у групах хостів (`mysql_servers`)

```sql
-- Очистити таблицю серверів
DELETE FROM mysql_servers;

-- Реєстрація первинного вузла у групі запису (hostgroup 0)
INSERT INTO mysql_servers (
    hostgroup_id, hostname, port, weight, max_connections, max_replication_lag
) VALUES (
    0, '10.0.1.10', 3306, 1000, 1000, 0
);

-- Реєстрація пулу реплік у групі читання (hostgroup 1)
-- Встановлення ліміту лагу 2 секунди
INSERT INTO mysql_servers (
    hostgroup_id, hostname, port, weight, max_connections, max_replication_lag
) VALUES 
    (1, '10.0.1.21', 3306, 100, 1000, 2),
    (1, '10.0.1.22', 3306, 100, 1000, 2),
    (1, '10.0.1.23', 3306, 100, 1000, 2);

-- Завантажити сервери в активний runtime та зафіксувати на диску
LOAD MYSQL SERVERS TO RUNTIME;
SAVE MYSQL SERVERS TO DISK;
```

*Механізм автоматичного виключення з пулу:*
ProxySQL містить вбудований монітор, який щосекунди надсилає запит `SHOW REPLICA STATUS` до всіх серверів у `hostgroup_id = 1`. Якщо для будь-якої репліки значення `Seconds_Behind_Source` перевищує `max_replication_lag` (у прикладі `2` секунди), ProxySQL змінює статус вузла на `SHUNNED` і виключає його з пулу розподілу читання. Як тільки репліка наздоганяє лідер (`lag <= max_replication_lag`), її статус автоматично повертається до `ONLINE`.

### Правила маршрутизації SQL-запитів (`mysql_query_rules`)

```sql
DELETE FROM mysql_query_rules;

-- Правило 1: Усі транзакції з блокуванням рядків відправляти на Primary (hostgroup 0)
INSERT INTO mysql_query_rules (
    rule_id, active, match_pattern, destination_hostgroup, apply
) VALUES (
    10, 1, '^SELECT.*FOR (UPDATE|SHARE)', 0, 1
);

-- Правило 2: Запити читання відправляти на пул реплік (hostgroup 1)
INSERT INTO mysql_query_rules (
    rule_id, active, match_pattern, destination_hostgroup, apply
) VALUES (
    20, 1, '^SELECT', 1, 1
);

-- Правило 3: Усі інші запити (INSERT, UPDATE, DELETE, DDL, SET) відправляти на Primary (hostgroup 0)
INSERT INTO mysql_query_rules (
    rule_id, active, match_pattern, destination_hostgroup, apply
) VALUES (
    30, 1, '.*', 0, 1
);

LOAD MYSQL QUERY RULES TO RUNTIME;
SAVE MYSQL QUERY RULES TO DISK;
```

## 4. Метрики Prometheus та правила тривог Alertmanager

Для забезпечення спостережуваності та надійного функціонування кластера реплікації експортери метрик (`postgres_exporter`, `mysqld_exporter`) збирають кількісні показники затримки та конфліктів.

### Ключові метрики моніторингу

| Метрика | Система | Тип | Опис та інтерпретація |
| :--- | :--- | :--- | :--- |
| `pg_stat_replication_replay_lag_seconds` | PostgreSQL | Gauge | Часовий лаг застосування WAL реплікою. Перевищення 5–10 секунд свідчить про деградацію або перевантаження диска репліки. |
| `pg_replication_slots_active` | PostgreSQL | Gauge | Статус активності слота реплікації (1 — підключений, 0 — відключений). Неактивний слот загрожує переповненням диска лідера. |
| `pg_stat_database_conflicts_confl_snapshot` | PostgreSQL | Counter | Швидкість зростання кількості скасованих запитів читання через конфлікт із процесом `VACUUM`. |
| `mysql_slave_status_seconds_behind_master` | MySQL | Gauge | Лаг репліки MySQL у секундах. |
| `mysql_slave_status_slave_io_running` | MySQL | Gauge | Булевий прапорець (1/0) активності потоку зчитування логу з лідера. |
| `mysql_slave_status_slave_sql_running` | MySQL | Gauge | Булевий прапорець (1/0) активності потоку накатування змін на репліці. |

### Конфігурація правил алертингу Prometheus (Alertmanager YAML)

```yaml
groups:
  - name: database_replication_alerts
    rules:
      # Критичний лаг реплікації PostgreSQL
      - alert: PostgresReplicationLagHigh
        expr: pg_stat_replication_replay_lag_seconds > 5
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "Високий лаг реплікації PostgreSQL на вузлі {{ $labels.application_name }}"
          description: "Репліка відстає від лідера на {{ $value | printf \"%.2f\" }} секунд протягом понад 2 хвилин."

      # Неактивний слот реплікації (загроза диску)
      - alert: PostgresInactiveReplicationSlot
        expr: pg_replication_slots_active == 0
        for: 15m
        labels:
          severity: critical
        annotations:
          summary: "Неактивний слот реплікації: загроза переповнення pg_wal"
          description: "Слот {{ $labels.slot_name }} неактивний понад 15 хвилин. Лідер утримує сегменти WAL."

      # Зупинка потоків реплікації MySQL
      - alert: MySQLReplicationThreadDown
        expr: mysql_slave_status_slave_io_running == 0 or mysql_slave_status_slave_sql_running == 0
        for: 30s
        labels:
          severity: page
        annotations:
          summary: "Потік реплікації MySQL зупинився на {{ $labels.instance }}"
          description: "Потік IO або SQL перейшов у стан 0 через мережеву помилку або конфлікт транзакції."
```
