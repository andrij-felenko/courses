# 📜 IBM System R і народження вартісної оптимізації

Коли 1970 року Едґар Кодд (англ. *Edgar F. Codd*) опублікував свою маніфестну працю про реляційну модель, інженерна спільнота зустріла її з глибоким скепсисом. У тогочасних ієрархічних і мережевих базах даних (як-от IBM IMS або CODASYL) програміст вручну прокладав маршрут вибірки: писав цикли, переходив за фізичними покажчиками між записами на магнітних дисках і сам обирав, який масив сканувати першим. Декларативна мова запитів, де користувач лише описує бажаний результат виразом реляційної алгебри, здавалася теоретикам елегантною, а практикам — катастрофічно повільною. Побутувала думка, що жодна автоматична система не здатна зрівнятися за швидкістю з досвідченим інженером, який знає фізичне розташування циліндрів на диску.

Відповіддю на цей виклик став дослідницький проект IBM System R, започаткований у лабораторії IBM San Jose Research Laboratory в середині 1970-х років. Саме в його стінах народилася мова SQL (тоді SEQUEL) і з'явилася перша повноцінна реляційна СУБД. Проте головним інженерним тріумфом проекту стало створення першого оптимізатора запитів, заснованого на вартості (англ. *Cost-Based Optimizer*, CBO).

## Прорив Патриції Селінджер

Ключову роль у створенні планувальника відіграла дослідниця Патриція Селінджер (англ. *Patricia Selinger*). 1979 року група вчених під її керівництвом опублікувала класичну статтю «Access Path Selection in a Relational Database Management System». Ця робота заклала математичний та алгоритмічний фундамент, на якому й сьогодні працюють планувальники PostgreSQL, Oracle, Microsoft SQL Server, MySQL та SQLite.

До Селінджер перші спроби оптимізації спиралися виключно на евристичні правила (англ. *Rule-Based Optimization*, RBO). Системи використовували жорсткий набір пріоритетів: наприклад, «якщо є індекс — завжди використовуй індекс», «якщо в умові стоїть рівність — віддай їй перевагу над діапазоном». Евристичний підхід був сліпим до обсягів даних: він змушував СУБД використовувати індекс навіть тоді, коли запит обирав 90% рядків таблиці, що призводило до мільйонів повільних випадкових читань диска замість одного швидкого послідовного проходу.

Селінджер запропонувала кардинально інший підхід: перетворити вибір плану на задачу оптимізації цільової функції. Оптимізатор повинен оцінювати кожен можливий спосіб виконання запиту в єдиних фізичних одиницях вартості, враховуючи два головні ресурси комп'ютера:
1. Кількість операцій дискового вводу-виводу (I/O) для читання сторінок даних та індексів.
2. Кількість тактів процесора (CPU) для перевірки умов фільтрації, порівняння ключів і сортування кортежів.

Щоб порахувати ці витрати до фактичного виконання запиту, система System R уперше почала збирати каталог статистичних характеристик збережених таблиць: загальну кількість сторінок, кількість рядків, кількість унікальних значень у кожному стовпці та висоту індексних дерев.

## Динамічне програмування та лівоглибокі дерева

Головною обчислювальною перешкодою для вартісного оптимізатора став комбінаторний вибух простору пошуку. Для запиту, що з'єднує `N` таблиць, кількість можливих порядків з'єднання зростає факторіально. Навіть для скромного запиту з 6 таблиць існує `6! = 720` перестановок, а з урахуванням вибору фізичних алгоритмів (вкладений цикл чи злиття) та лівих/правих дерев кількість варіантів вимірюється сотнями тисяч. Повний перебір був неможливий за прийнятний час компіляції запиту.

Група Селінджер розв'язала цю задачу двома інженерними рішеннями:

1. **Обмеження простору лівоглибокими деревами (англ. *left-deep trees*).** Оптимізатор розглядав лише плани, де правим операндом будь-якого з'єднання завжди виступає базова таблиця, а не результат іншого проміжного з'єднання. Це дозволило конвеєризувати виконання: кортеж із лівої гілки передається вгору без необхідності матеріалізувати проміжні результати у тимчасових таблицях на диску.
2. **Динамічне програмування за розміром підмножин.** Замість перебору всіх перестановок алгоритм розбиває задачу на фази:
   - **Фаза 1:** Знайти найкращий шлях доступу (послідовне читання чи індекс) для кожної окремої таблиці `{A}`, `{B}`, `{C}`.
   - **Фаза 2:** Знайти найкращий спосіб з'єднати всі пари таблиць: `{A, B}`, `{A, C}`, `{B, C}`, спираючись на збережені оптимальні плани з фази 1.
   - **Фаза k:** Знайти оптимальний план для підмножини з `k` таблиць, додаючи одну таблицю до збереженого оптимального плану для `(k-1)` таблиць.

Завдяки властивості оптимальності для підзадач субоптимальні плани відкидалися на кожному кроці. Для `N` таблиць алгоритм оцінював не `O(N!)`, а приблизно `O(N · 2^N)` варіантів. Для 6–10 таблиць це займало лічені мілісекунди.

## Відкриття «цікавих порядків»

Під час розробки динамічного програмування інженери System R зіткнулися з підступною пасткою. Нехай для окремої таблиці `A` послідовне сканування коштує 100 одиниць, а індексне сканування за стовпцем `user_id` коштує 120 одиниць. Згідно з жадібним правилом оптимізатор мав би відкинути індексне сканування як дорожче.

Проте якщо далі у запиті стоїть `ORDER BY user_id` або планується оператор `Merge Join` за цим полем, вибір індексного сканування віддає потік рядків, який **вже відсортований**. Використання послідовного сканування змусить систему пізніше виконати явне сортування кортежів, що додасть ще 80 одиниць вартості (разом `100 + 80 = 180`). Індексний план, попри локальну дорожнечу, дає загальну вартість `120 + 0 = 120`, тобто виявляється глобально оптимальним.

Селінджер ввела фундаментальне поняття **цікавих порядків сортування** (англ. *interesting orders*). Оптимізатор зберігає не один найдешевший план для підмножини таблиць, а найкращий план для кожного унікального фізичного порядку сортування кортежів, який може знадобитися наступним операторам запиту (`JOIN`, `GROUP BY`, `ORDER BY`, `DISTINCT`). Цей механізм зберігся у всіх сучасних реляційних рушіях.

## Еволюція: від System R до Volcano та Cascades

Архітектура Селінджер залишалася промисловим стандартом понад півтора десятиліття. Проте в 1990-х роках реляційні СУБД почали підтримувати складні типи даних, геопросторові запити, об'єктні розширення та нові фізичні оператори (зокрема паралельне виконання та Hash Join). Монолітний алгоритм динамічного програмування з жорстко закодованими формулами стало важко розширювати.

1993–1995 років дослідник Гетц Ґрефе (англ. *Goetz Graefe*) розробив модульні розширювані архітектури оптимізації **Volcano** та **Cascades**. Замість монолітного коду Ґрефе запропонував:
- Відокремити логічні оператори (реляційна алгебра: фільтрація, проекція, з'єднання) від фізичних алгоритмів виконання (Nested Loop, Hash Join, Index Scan).
- Описувати оптимізаційні перетворення декларативними правилами трансформації (англ. *transformation rules*).
- Використовувати структуру даних **Memo** — компактний граф еквівалентних груп планів, що усуває дублювання спільних підвиразів.

Сьогодні архітектура Cascades лежить в основі оптимізаторів Microsoft SQL Server, Apache Calcite, CockroachDB та Greenplum Orca, тоді як PostgreSQL продовжує розвивати класичний, надзвичайно вилизаний підхід на основі динамічного програмування та генетичних алгоритмів (GEQO) для великих з'єднань.

Проект IBM System R довів усьому світові, що декларативні запити можуть бути не лише зручними для програміста, але й продуктивнішими за ручний навігаційний код, відкривши шлях сучасній індустрії баз даних.
