# 🧮 Кількісна оптимізація ярусів зберігання та виведення точки окупності міграції

Переміщення даних у дешевий холодний архів або хмарний Glacier без точного математичного розрахунку часто призводить до суттєвого зростання сукупних витрат порівняно зі збереженням на швидких накопичувачах. Ця математична модель формалізує баланс між економією на щомісячному зберіганні та сумою накладних витрат на міграцію, запити й штрафи за розморожування байтів, визначаючи точну аналітичну точку окупності `t*` та оптимальні часові межі для багаторівневих ієрархій.

### 1. Модель згасання інтенсивності звернень

У розподілених сховищах даних (журнали подій, транзакційні архіви, аналітичні вітрини) частота читання записів стрімко падає зі збільшенням їхнього віку `t`. Емпіричні вимірювання показують, що ймовірність звернення до партиції підпорядковується узагальненому степеневому закону Парето-Ціпфа:

```
λ(t) = λ₀ · (1 + t / τ)^(-α)
```

де:
- `t` — вік даних (у днях або місяцях) від моменту їхньої фіксації в системі;
- `λ₀` — початкова інтенсивність читання свіжих даних (кількість запитів читання на гігабайт на місяць);
- `τ` — характерний часовий масштаб активної фази (типово 3–14 днів);
- `α` — показник експоненційного згасання (для журналів подій `1.2 ≤ α ≤ 2.5`).

Сумарна очікувана кількість запитів читання `Q(t₁, t₂)` до блоку даних у часовому інтервалі `[t₁, t₂]` обчислюється через інтеграл функції інтенсивності:

```
Q(t₁, t₂) = ∫[t₁...t₂] λ(t) dt
```

Для показника згасання `α > 1` первісна функції має вигляд:

```
∫ λ₀ · (1 + t / τ)^(-α) dt
= λ₀ · τ · (1 + t / τ)^(1 - α) / (1 - α) + Const   [інтегрування степеневої функції]
= - λ₀ · τ / ((α - 1) · (1 + t / τ)^(α - 1)) + Const [винесення мінуса в знаменник]
```

Підставляючи межі інтегрування від моменту міграції `t_m` до планового строку видалення `T_ret`:

```
Q(t_m, T_ret)
= ∫[t_m...T_ret] λ(t) dt
= [ - λ₀ · τ / ((α - 1) · (1 + t / τ)^(α - 1)) ] | [t_m...T_ret] [підстановка меж]
= (λ₀ · τ / (α - 1)) · ( (1 + t_m / τ)^(1 - α) - (1 + T_ret / τ)^(1 - α) ) [різниця значень на межах]
```

Якщо строк утримання даних значний (`T_ret >> t_m`), другим доданком у дужках можна знехтувати:

```
Q(t_m, ∞) ≈ (λ₀ · τ / (α - 1)) · (1 + t_m / τ)^(1 - α)
```

### 2. Функція сукупної вартості володіння (TCO)

Розглянемо блок незмінних даних обсягом `V` гігабайтів, що зберігається протягом загального періоду `T` місяців. 

Введемо параметри вартості системи зберігання:
- `S_hot` — вартість зберігання на гарячому ярусі ($/ГБ·місяць);
- `S_cold` — вартість зберігання на холодному ярусі ($/ГБ·місяць), де `S_cold < S_hot`;
- `ΔS` — питома різниця вартості зберігання: `ΔS = S_hot - S_cold`;
- `P_trans` — разовий тариф на перенесення 1 ГБ у холодний ярус ($/ГБ, включає операції `PUT`/`COPY` та мережевий трафік);
- `P_ret_gb` — тариф за розморожування/читання 1 ГБ із холодного ярусу ($/ГБ);
- `P_ret_req` — вартість одного запиту на відновлення або `GET`-операції ($/запит);
- `b` — середній розмір зчитування за один запит у гігабайтах (`b ≤ V`).

#### Сценарій А: Зберігання виключно на гарячому ярусі

При збереженні на швидких накопичувачах (NVMe SSD) плата за зчитування байтів та обробку внутрішніх запитів дорівнює нулю (`P_ret = 0`), а вартість визначається виключно обсягом і часом:

```
Cost_hot(V, T) = V · S_hot · T
```

#### Сценарій Б: Дворівневе зберігання з міграцією на моменті `t_m`

Якщо дані перебувають на гарячому ярусі протягом часу `t_m`, а потім мігрують на холодний ярус на залишок часу `(T - t_m)`:

```
Cost_tiered(V, T, t_m)
= Cost_hot_phase + Cost_migration + Cost_cold_storage + Cost_retrieval
```

Розпишемо кожну складову:

```
Cost_hot_phase = V · S_hot · t_m
Cost_migration = V · P_trans
Cost_cold_storage = V · S_cold · (T - t_m)
Cost_retrieval = Q(t_m, T) · (b · P_ret_gb + P_ret_req)
```

### 3. Виведення точки беззбитковості міграції `t*`

Міграція є економічно виправданою тоді й тільки тоді, коли сукупні витрати дворівневої системи менші за витрати на постійне зберігання в гарячому ярусі:

```
Cost_tiered(V, T, t_m) < Cost_hot(V, T)
```

Підставимо формули складових у нерівність:

```
V · S_hot · t_m + V · P_trans + V · S_cold · (T - t_m) + Cost_retrieval < V · S_hot · T
```

Згрупуємо члени, що містять `S_hot` та `S_cold`:

```
V · P_trans + Cost_retrieval < V · S_hot · (T - t_m) - V · S_cold · (T - t_m) [перенесення hot_phase вправо]
V · P_trans + Cost_retrieval < V · (S_hot - S_cold) · (T - t_m)              [винесення спільного множника]
V · P_trans + Cost_retrieval < V · ΔS · (T - t_m)                              [підстановка різниці тарифів ΔS]
```

Розділимо обидві частини нерівності на `V · ΔS`:

```
(P_trans / ΔS) + (Cost_retrieval / (V · ΔS)) < T - t_m
```

Позначимо залишковий час перебування даних у холодному ярусі як `Δt_cold = T - t_m`. Отримуємо строгу умову беззбитковості для мінімальної тривалості холодного зберігання `Δt_cold*`:

```
Δt_cold* = (P_trans / ΔS) + (Cost_retrieval / (V · ΔS))
```

Розглянемо випадок, коли звернення до холодного архіву повністю відсутні або надзвичайно рідкісні (`Cost_retrieval ≈ 0`):

```
Δt_min_static = P_trans / ΔS
```

Це фундаментальний поріг: **дані повинні зберігатися на холодному ярусі щонайменше `Δt_min_static` місяців лише для того, щоб зекономлені кошти на оренді сховища компенсували накладні витрати на виконання самої операції міграції.**

### 4. Розрахунок критичної частоти звернень (порогу завалу в збитки)

Якщо дані після міграції все ж продовжують зчитуватися з частотою `λ_cold` запитів на місяць на весь об'єм `V` (при повному читанні `b = V`), місячна вартість утримання в холодному ярусі з урахуванням зчитувань дорівнює:

```
Cost_monthly_cold = V · S_cold + λ_cold · (V · P_ret_gb + P_ret_req)
```

Міграція стає збитковою (штрафна пастка), коли щомісячні операційні витрати на холодному ярусі перевищують щомісячну вартість гарячого ярусу:

```
Cost_monthly_cold > Cost_monthly_hot
V · S_cold + λ_cold · (V · P_ret_gb + P_ret_req) > V · S_hot
```

Виведемо критичну частоту звернень `λ_crit`:

```
λ_cold · (V · P_ret_gb + P_ret_req) > V · (S_hot - S_cold) [перенесення зберігання вправо]
λ_cold · (V · P_ret_gb + P_ret_req) > V · ΔS               [заміна на ΔS]
λ_cold > (V · ΔS) / (V · P_ret_gb + P_ret_req)            [ділення на вартість одиничного читання]
```

Для великих блоків даних, де вартістю запиту `P_ret_req` можна знехтувати порівняно з платою за обсяг `V · P_ret_gb`:

```
λ_crit ≈ (V · ΔS) / (V · P_ret_gb)
= ΔS / P_ret_gb                                           [скорочення на об'єм V]
```

### 5. Оптимізація трирівневої ієрархії (Hot → Warm → Cold)

У сучасних дата-інженерних архітектурах застосовують три яруси: гарячий (NVMe SSD, ціна `S_1`), теплий (S3 Standard / HDD, ціна `S_2`) та холодний (S3 Glacier, ціна `S_3`), де `S_1 > S_2 > S_3`.

Загальна функція вартості володіння за період `T` при моментах переходу `t_1` (Hot → Warm) та `t_2` (Warm → Cold) записується як:

```
TCO(t_1, t_2) = Cost_storage(t_1, t_2) + Cost_trans(t_1, t_2) + Cost_read(t_1, t_2)
```

Розгорнемо складові для одиничного гігабайта (`V = 1`):

```
Cost_storage(t_1, t_2) = S_1 · t_1 + S_2 · (t_2 - t_1) + S_3 · (T - t_2)
Cost_trans(t_1, t_2) = P_12 + P_23
Cost_read(t_1, t_2) = P_ret2 · Q(t_1, t_2) + P_ret3 · Q(t_2, T)
```

Щоб знайти оптимальний момент міграції `t_1*` з гарячого ярусу в теплий, візьмемо частинну похідну функції `TCO` за змінною `t_1` і прирівняємо її до нуля:

```
∂(TCO) / ∂t_1 = 0
∂ / ∂t_1 [ S_1 · t_1 + S_2 · (t_2 - t_1) + P_ret2 · ∫[t_1...t_2] λ(t) dt ] = 0 [виділення залежних від t_1 членів]
S_1 - S_2 - P_ret2 · λ(t_1) = 0                                                [диференціювання інтеграла за нижньою межею]
P_ret2 · λ(t_1*) = S_1 - S_2                                                   [перенесення різниці тарифів]
λ(t_1*) = (S_1 - S_2) / P_ret2                                                 [вираження критичної інтенсивності]
```

Оскільки на теплому ярусі додаткова плата за зчитування байтів часто відсутня (`P_ret2 ≈ 0`), перехід Hot → Warm обмежується не вартістю читання, а суто обсягом доступної ємності швидких накопичувачів NVMe. 

Натомість для другого порогу `t_2*` (перехід Warm → Cold), де плата за зчитування `P_ret3 > 0`:

```
∂(TCO) / ∂t_2 = 0
∂ / ∂t_2 [ S_2 · (t_2 - t_1) + S_3 · (T - t_2) + P_ret3 · ∫[t_2...T] λ(t) dt ] = 0 [виділення залежних від t_2 членів]
S_2 - S_3 - P_ret3 · λ(t_2*) = 0                                                    [диференціювання за нижньою межею]
λ(t_2*) = (S_2 - S_3) / P_ret3                                                      [формула оптимального зрізу активності]
```

Підставивши модель згасання `λ(t) = λ₀ · (1 + t / τ)^(-α)`, знаходимо точний аналітичний розв'язок для моменту витіснення в холодний архів:

```
λ₀ · (1 + t_2* / τ)^(-α) = (S_2 - S_3) / P_ret3                              [підстановка моделі Парето]
(1 + t_2* / τ)^α = λ₀ · P_ret3 / (S_2 - S_3)                                 [піднесення до степеня -1]
1 + t_2* / τ = ( (λ₀ · P_ret3) / (S_2 - S_3) )^(1 / α)                       [взяття кореня степеня α]
t_2* = τ · [ ( (λ₀ · P_ret3) / (S_2 - S_3) )^(1 / α) - 1 ]                   [вираження оптимального часу t_2*]
```

Ця формула доводить: чим вища вартість відновлення `P_ret3` і чим повільніше згасає інтерес до даних (менший `α`), тим пізніше слід переносити масив у холодний архів.

### 6. Вплив розміру об'єкта та мінімального порогу тарифікації

У хмарних сховищах (Amazon S3, Google Cloud Storage, Azure Blob) діє правило мінімального розміру об'єкта для холодних класів (типово `S_min_size = 128` КіБ). Якщо застосунок зберігає файли розміром `s < 128` КіБ (наприклад, JSON-документи по 4 КіБ), провайдер тарифікує кожен файл як повні 128 КіБ.

Введемо коефіцієнт накладних витрат метаданих та розміру `k_overhead(s)`:

```
k_overhead(s) = max(1.0, 128 КіБ / s)
```

Ефективна вартість холодного зберігання для дрібних об'єктів становить:

```
S_cold_effective(s) = S_cold · k_overhead(s)
```

Для файлу розміром 4 КіБ коефіцієнт становить `128 / 4 = 32`. Ефективна вартість зберігання на S3 Glacier зростає у 32 рази:

```
S_cold_effective(4 КіБ)
= $0.0036 · 32            [множення базового тарифу на коефіцієнт накладних витрат]
= $0.1152 / ГБ·місяць     [обчислення ефективної вартості з урахуванням порогу 128 КіБ]
```

Це в 5 разів дорожче, ніж зберігання того ж файлу на дорогому гарячому ярусі S3 Standard ($0.023 / ГБ·міс). Таким чином, міграція дрібних об'єктів без попередньої агрегації в монолітні пакунки (Parquet, Tar, Zip) є гарантовано збитковою.

### 7. Числовий приклад розрахунку на реальних тарифах

Розглянемо реальні параметри переміщення 100 ТБ логів (`V = 100 000` ГБ) між класами Amazon S3 Standard та Amazon S3 Glacier Flexible Retrieval:

| Параметр | Позначення | Значення |
|---|---|---|
| S3 Standard зберігання | `S_hot` | $0.023 / ГБ·міс |
| S3 Glacier Flexible зберігання | `S_cold` | $0.0036 / ГБ·міс |
| Економія на оренді | `ΔS` | $0.0194 / ГБ·міс |
| Вартість запитів переходу (PUT/Lifecycle) | `P_trans` | $0.05 на 1 000 об'єктів (для блоків 100 МБ: $0.0005 / ГБ) |
| Плата за вивантаження з Glacier | `P_ret_gb` | $0.03 / ГБ |
| Мінімальний обов'язковий строк | `T_min_bill` | 90 днів (3 місяці) |

Обчислимо статичний строк окупності:

```
Δt_min_static
= P_trans / ΔS               [підстановка формули порогу]
= 0.0005 / 0.0194            [підстановка числових значень тарифів]
≈ 0.0258 місяця ≈ 0.77 дня   [переведення в календарні дні: 0.0258 · 30]
```

Статичний перехід окупається менше ніж за добу. Проте мінімальний розрахунковий період Glacier становить 90 днів. Якщо видалити об'єкт через 10 днів після міграції, провайдер нарахує штраф за раннє видалення (англ. *pro-rated early deletion fee*) за залишок у 80 днів:

```
Early_Deletion_Penalty
= V · S_cold · ((90 - 10) / 30)  [розрахунок залишку неоплачених місяців]
= 100 000 · 0.0036 · 2.667       [підстановка обсягу 100 ТБ і ставки Glacier]
= $960.12                        [множення складових штрафу]
```

Тепер обчислимо критичну частоту звернень `λ_crit`:

```
λ_crit
= ΔS / P_ret_gb                  [формула критичної точки беззбитковості]
= 0.0194 / 0.03                  [підстановка економії на оренді та плати за читання]
≈ 0.6467 звернень на місяць      [ділення: гранична інтенсивність читання]
```

**Інженерний висновок:** якщо до архівного масиву звертаються частіше ніж 1 раз на 46 днів (`1 / 0.6467 ≈ 1.54` місяця), переведення даних у Glacier є фінансово збитковим і призводить до прямих грошових втрат компанії порівняно зі збереженням на S3 Standard.
