# 📋 Специфікація інтерфейсу бекфілу: контракт оркестратора, CLI та перевірка узгодженості

Промисловий процес перерахунку історичних даних не може бути неструктурованим ручним запуском скриптів або набором нерегламентованих SQL-команд. Коли конвеєр оновлює таблиці з терабайтами фінансових транзакцій чи клієнтської телеметрії, будь-яка неоднозначність у передачі часових меж, форматі ідентифікаторів або правилах блокування ресурсів призводить до пошкодження аналітичного сховища та падіння бізнес-звітів.

Для надійної інтеграції з системами оркестрації (Apache Airflow, Dagster, Temporal), чергами розподілених задач та корпоративними каталогами аудиту кожен сервіс бекфілу зобов'язаний реалізовувати суворий публічний контракт взаємодії.

Ця специфікація детально описує ключові рівні інтерфейсу: протокол командного рядка (CLI), формат детермінованого контексту задач оркестратора, схему контрольних точок і протокол оренди (*distributed lease*), контракт валідації якості даних (*pre-commit quality gate*), мережевий REST/gRPC API для динамічного керування процесом, механізми регулювання навантаження (*backpressure & throttling*) та правила сповіщення каталогів походження даних (*Data Lineage*).

---

### 1. Контракт інтерфейсу командного рядка (CLI Interface)

Утиліта або контейнеризований мікросервіс бекфілу приймає уніфікований набір параметрів командного рядка. Головне правило інтерфейсу полягає у повній відмові від неявних значень за замовчуванням для часових меж: усі часові мітки передаються суворо у форматі `ISO 8601 UTC`.

| Параметр CLI | Тип даних | Обов'язковий | Призначення та семантика |
| :--- | :--- | :--- | :--- |
| `--start-date` | `String (YYYY-MM-DD)` | **Так** | Ліва замкнена межа інтервалу подій `[t_start, t_end)` |
| `--end-date` | `String (YYYY-MM-DD)` | **Так** | Права відкрита межа інтервалу подій |
| `--granularity` | `Enum (hour, day, month)` | Ні (дефолт: `day`) | Крок нарізки чанків для ізольованих транзакцій |
| `--concurrency` | `Integer` | Ні (дефолт: `4`) | Ліміт паралельних воркерів/потоків обробки |
| `--dry-run` | `Boolean` | Ні (дефолт: `false`) | Прогін без фінального SWAP (генерація звіту розбіжностей) |
| `--force-recompute`| `Boolean` | Ні (дефолт: `false`) | Ігнорувати статус `COMMITTED` у журналі чекпоінтів |
| `--max-drift-pct` | `Float` | Ні (дефолт: `0.05`) | Допустимий поріг відносної розбіжності сум (5%) |
| `--catalog-uri` | `String (URI)` | **Так** | Адреса сховища метаданих (Iceberg/Hive Catalog) |

#### Стандартизовані коди повернення процесу (Exit Codes)

* `0 (SUCCESS)`: Усі чанки зазначеного діапазону успішно обчислені, пройшли всі автоматичні перевірки інваріантів та зафіксовані в основній таблиці.
* `1 (VALIDATION_FAILED)`: Виявлено порушення бізнес-інваріантів (наприклад, від'ємні значення виручки, поява порожніх первинних ключів або перевищення порогу розбіжності сум). Робоча таблиця лишилася без змін, тимчасові дані знищено.
* `2 (LOCK_TIMEOUT)`: Не вдалося захопити розподілене блокування партиції протягом встановленого таймауту через роботу іншого активного процесу бекфілу.
* `3 (PARTIAL_FAILURE)`: Частина чанків зафіксована успішно, але процес було перервано через апаратний збій або помилку мережі. Наступний запуск автоматично продовжить обчислення з першого незафіксованого чанка.

### 2. Контракт контексту оркестратора (DAG Context Contract)

Під час виконання задачі перерахунку в оркестраторі (наприклад, у DAG Apache Airflow або активності Temporal) системі категорично заборонено спиратися на локальний системний час сервера `datetime.now()` чи неявні змінні середовища. 

Оркестратор зобов'язаний передавати у задачу ізольований незмінний об'єкт контексту `BackfillTaskContext`, що містить точні межі інтервалу та детермінований токен ідемпотентності (*idempotency token*).

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "BackfillTaskContext",
  "type": "object",
  "required": [
    "job_id",
    "target_table",
    "data_interval_start",
    "data_interval_end",
    "idempotency_token"
  ],
  "properties": {
    "job_id": {
      "type": "string",
      "format": "uuid",
      "description": "Унікальний ідентифікатор сесії бекфілу"
    },
    "target_table": {
      "type": "string",
      "description": "Повна назва цільової таблиці (schema.table_name)"
    },
    "data_interval_start": {
      "type": "string",
      "format": "date-time",
      "description": "Початок вікна подій у шкалі UTC (ISO 8601)"
    },
    "data_interval_end": {
      "type": "string",
      "format": "date-time",
      "description": "Кінець вікна подій у шкалі UTC (ISO 8601)"
    },
    "idempotency_token": {
      "type": "string",
      "description": "Детермінований хеш sha256(target_table + interval_start + interval_end)"
    },
    "dry_run": {
      "type": "boolean",
      "default": false
    }
  }
}
```

### 3. Специфікація таблиці контрольних точок та протокол оренди (Checkpoints & Fencing)

Для координації розподілених воркерів, запобігання конфліктам подвійного запису та захисту від аварійних відключень використовується централізований реєстр контрольних точок.

#### Схема таблиці метаданих контрольних точок:

```sql
CREATE TABLE backfill_job_checkpoints (
    idempotency_token VARCHAR(64) PRIMARY KEY,
    target_table VARCHAR(128) NOT NULL,
    chunk_partition VARCHAR(32) NOT NULL, -- Наприклад: '2026-08-20'
    window_start TIMESTAMP WITH TIME ZONE NOT NULL,
    window_end TIMESTAMP WITH TIME ZONE NOT NULL,
    status VARCHAR(16) NOT NULL, -- 'PENDING', 'VALIDATED', 'COMMITTED', 'FAILED'
    worker_id VARCHAR(64) NOT NULL,
    fence_token BIGINT NOT NULL, -- Монотонно зростаючий лічильник для захисту від зомбі-воркерів
    heartbeat_at TIMESTAMP WITH TIME ZONE NOT NULL,
    lease_expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    rows_inserted BIGINT DEFAULT 0,
    metrics_checksum VARCHAR(64),
    error_payload JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

#### Протокол захисту від зомбі-воркерів (Fencing Token Protocol)

1. **Захоплення оренди**: воркер виконує умовне оновлення рядка чанка `UPDATE ... SET worker_id = my_id, fence_token = fence_token + 1, lease_expires_at = now() + 5 min WHERE status = 'PENDING' OR lease_expires_at < now()`.
2. **Пульсація (Heartbeat)**: під час обчислень воркер кожні 30 секунд оновлює поле `heartbeat_at` та продовжує термін оренди.
3. **Захист від розділеного мозку (Split-Brain)**: якщо воркер затримався через паузу складання сміття (GC pause) і його оренда спливла, інший воркер перехоплює задачу з вищим значенням `fence_token`. Будь-яка спроба запізнілого воркера записати результат із застарілим токеном відхиляється на рівні бази метаданих.

### 4. Контракт валідації та аудиту (Pre-Commit Quality Gate)

Перед заміною даних у робочій таблиці воркер формує стандартизований конверт аудиту (*Audit Envelope*). Якщо хоча б одна умова повертає помилку, транзакція скасовується, а метадані помилки передаються в систему спостережливості (*Data Observability*).

```json
{
  "chunk_partition": "2026-08-20",
  "audit_timestamp": "2026-08-20T21:00:00Z",
  "engine_version": "2.4.0",
  "assertions": [
    {
      "check_name": "row_count_positive",
      "expected": "count > 0",
      "actual": 142050,
      "passed": true
    },
    {
      "check_name": "null_primary_keys",
      "expected": "null_count == 0",
      "actual": 0,
      "passed": true
    },
    {
      "check_name": "sum_reconciliation_drift",
      "expected": "abs(staged_sum - raw_sum) == 0",
      "actual": 0,
      "passed": true
    }
  ],
  "commit_decision": "PROCEED"
}
```

### 5. Мережевий REST / gRPC API керування бекфілом

Для платформних команд, які керують перерахунками через веб-інтерфейси або автоматизовані пайплайни CI/CD, бекфіл-рушій надає стандартизований API керування життєвим циклом:

#### 1. Створення задачі перерахунку
* **Метод**: `POST /api/v1/backfills`
* **Тіло запиту**:
  ```json
  {
    "target_table": "analytics.daily_user_revenue",
    "start_date": "2026-01-01",
    "end_date": "2026-06-01",
    "granularity": "day",
    "concurrency": 8,
    "dry_run": false
  }
  ```
* **Відповідь**: `202 Accepted` з ідентифікатором `job_id` та посиланням на потік подій стану.

#### 2. Моніторинг прогресу та телеметрії
* **Метод**: `GET /api/v1/backfills/{job_id}/status`
* **Відповідь**: повертає поточний статус (`QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`), кількість завершених чанків, загальну кількість оброблених рядків, графік використання пам'яті та прогнозований час завершення (*Estimated Time of Arrival, ETA*).

#### 3. Аварійне скасування та безпечна зупинка
* **Метод**: `POST /api/v1/backfills/{job_id}/abort`
* **Семантика**: коректно зупиняє активні чанки, скасовує незафіксовані транзакції у staging-шарі, звільняє розподілені блокування та позначає незавершені чанки для подальшого аналізу інженерами.

### 6. Контроль навантаження та троттлінг (Throttling & Backpressure)

Масштабний бекфіл за кілька років здатен перевантажити як цільове аналітичне сховище, так і зовнішні системи-джерела (платіжні шлюзи, CRM, сторонні API збагачення даних). Для запобігання відмовам в обслуговуванні (*Denial of Service*) контракт виконання передбачає автоматичне динамічне регулювання швидкості обробки.

Рушій відстежує три групи метрик зворотного тиску:
1. **Затримка реплікації (Replication Lag)**: якщо відставання реплік бази даних перевищує 5 секунд, процес призупиняє запуск нових чанків до стабілізації кластера.
2. **Ліміти запитів API (Rate Limits)**: при зверненні до зовнішніх ендпоінтів діє алгоритм «дірявого відра» (*Leaky Bucket*) з експоненційним відкатом (*Exponential Backoff*) при отриманні статусів HTTP 429.
3. **Використання CPU та дискового вводу-виводу**: якщо навантаження на ноди сховища перевищує 85%, кількість паралельних потоків автоматично знижується.

### 7. Інтеграція з протоколом походження даних (Data Lineage / OpenLineage)

Для забезпечення повної прозорості змін під час кожного успішного перерахунку конвеєр генерує подію стандарту **OpenLineage**. Ця подія сповіщає аналітичні каталоги (DataHub, Marquez, Collibra) про те, які саме версії сирих файлів були використані та яка частина історичного графа була оновлена.

Подія містить три ключові фасети (*facets*):
* `dataSource`: URI та версія зрізу вихідного незмінного логу (Snapshot ID у сховищі Apache Iceberg).
* `schema`: точна версія контракту схеми, за якою виконувалося перетворення.
* `outputDataset`: ідентифікатор цільової таблиці із зазначенням конкретної заміненої партиції та списку пройдених валідаційних перевірок.

Дотримання цієї специфікації гарантує, що бекфіл функціонує як детермінована, контрольована та повністю аудитована інженерна операція, захищена від людських помилок та збоїв розподіленого середовища.
