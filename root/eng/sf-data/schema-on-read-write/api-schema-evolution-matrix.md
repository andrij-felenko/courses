# 📋 Довідник еволюції схем даних: Матриця сумісності та формати

У розподілених сервісах та конвеєрах обробки даних схеми безперервно змінюються: додаються нові атрибути, застарілі поля позначаються як deprecated, а типи даних уточнюються.

Цей довідник містить правила сумісності версій схем (Schema Evolution Compatibility Rules), матрицю бінарних форматів серіалізації, правила безпечного додавання й видалення полів, правила міграцій, стратегії версіонування та чекліст аудиту Schema Registry.

---

### Матриця режимів сумісності схем (Compatibility Modes)

| Режим сумісності | Хто оновлюється першим | Правило валідації | Дозволені зміни схеми | Заборонені зміни схеми |
| :--- | :--- | :--- | :--- | :--- |
| **BACKWARD** | Споживачі (Consumers) | Нова схема може читати дані, створені попередньою схемою | • Додавання полів зі значенням за замовчуванням (Default)<br>• Видалення необов'язкових полів | • Додавання обов'язкових полів без дефолту<br>• Зміна типу існуючого поля |
| **BACKWARD_TRANSITIVE** | Споживачі (Consumers) | Нова схема може читати дані, створені **всіма** попередніми версіями | • Додавання полів з обов'язковим Default<br>• Видалення необов'язкових полів | • Будь-які зміни, що ламають найстарішу збережену версію |
| **FORWARD** | Виробники (Producers) | Стара схема може читати дані, згенеровані новою схемою | • Додавання обов'язкових полів<br>• Видалення полів із дефолтом | • Видалення обов'язкових полів<br>• Зміна назв полів |
| **FORWARD_TRANSITIVE** | Виробники (Producers) | Найстаріша схема споживача може читати найновіші повідомлення | • Суворе дотримання дефолтів для всіх доданих полів | • Будь-яке видалення обов'язкового поля з історії |
| **FULL** | Будь-який порядок | Одночасна зворотна та пряма сумісність (Zero-Downtime) | • Лише додавання необов'язкових полів з Default<br>• Лише видалення необов'язкових полів | • Додавання або видалення будь-якого обов'язкового поля |
| **FULL_TRANSITIVE** | Будь-який порядок | Усі версії схем у системі взаємно сумісні між собою | • Найсуворіший режим для критичних фінтех-систем | • Будь-які несумісні мутації в усій історії сервісу |
| **NONE** | Ручне узгодження | Перевірка сумісності вимкнена | • Будь-які зміни схеми (ризик аварійного падіння) | • Не рекомендується для виробничого середовища |

### Порівняння форматів серіалізації зі схемою

| Формат | Тип зв'язування схеми | Розташування схеми | Швидкість серіалізації | Стиснення даних | Сфера застосування |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Protocol Buffers** | Schema-on-write | Код компіляції (`.proto`) | Винятково висока (двійкова) | Відмінне (Varint, Tagged) | RPC-виклики мікросервісів (gRPC), низькі затримки |
| **Apache Avro** | Schema-on-write / Registry | Окремий JSON або Schema Registry | Висока (двійкова без тегів) | Максимальне (без дублювання ключів) | Потокові шини повідомлень (Apache Kafka, Event Sinks) |
| **Apache Parquet** | Гібридний колонковий | Метадані у футтері файлу | Середня на запис, екстремальна на читання | Колосальне (Snappy, Zstd, RLE, Bit-Packing) | Аналітичні озера даних (Data Lake / S3 / Spark / DuckDB) |
| **JSON Schema** | Schema-on-read з валідатором | Окремий JSON-документ валідації | Низька (текстовий парсинг) | Низьке (надлишкові назви ключів) | Публічні REST/GraphQL API для фронтенд-клієнтів |
| **FlatBuffers** | Schema-on-write (Zero-Copy) | Бінарний лейаут пам'яті | Максимальна (читання без розбору) | Помірне (зберігає вирівнювання) | Мобільні ігри, машинне навчання (TensorFlow Lite) |

### Правила безпечної модифікації полів (Evolution Safe Rules)

1. **Правило додавання нового поля**:
   Завжди вказуйте значення за замовчуванням (`default = null` або `default = 0`). Ніколи не додавайте обов'язкове поле `required` до діючої схеми без оновлення всіх споживачів.
2. **Правило видалення існуючого поля**:
   Видалення поля відбувається у три етапи:
   * Етап 1: Позначити поле як `deprecated` у коментарях та документації.
   * Етап 2: Оновити споживачів, переставши читати це поле.
   * Етап 3: Оновити виробників, припинивши відправку поля, та видалити його зі схеми в режимі сумісності FULL.
3. **Правило перейменування поля**:
   Пряме перейменування поля еквівалентне одночасному видаленню старого та додаванню нового, що ламає сумісність. Замість перейменування використовуйте аліаси (`aliases: ["old_name"]` в Avro) або додавайте нове поле з поступовою міграцією.
4. **Правило зміни типу даних**:
   Зміна типу дозволена лише в бік розширення діапазону (наприклад, `int` -> `long`, але ніколи `long` -> `int` через ризик переповнення).
5. **Правило числових тегів у Protocol Buffers**:
   Номери полів (Field Numbers) ніколи не можна змінювати або повторно призначати. При видаленні поля резервуйте його номер через ключове слово `reserved 4, 8; reserved "old_field";`.
6. **Правило перерахувань (Enums)**:
   При додаванні нового значення в Enum завжди призначайте першим елементом `UNKNOWN = 0`, щоб старі споживачі не падали при зустрічі з невідомим значенням.
7. **Правило нормалізації імен просторів (Namespaces)**:
   Усі схеми повинні мати чітко визначений пакет або простір імен для запобігання колізіям однакових назв структур у різних підсистемах.
8. **Правило збереження невідомих полів (Field Preservation)**:
   При отриманні повідомлення проміжний сервіс-маршрутизатор зобов'язаний зберігати невідомі поля та передавати їх далі без обрізання.
9. **Правило обов'язкової документації бізнес-сенсу**:
   Кожне поле повинно містити пояснення одиниць вимірювання (наприклад, `timeout_ms` замість `timeout`, або `amount_cents` замість `amount`), щоб усунути ризик розбіжностей при інтеграції нових мікросервісів.
10. **Стратегія Canary-тестування схем**:
   Перед оновленням схеми на всіх продюсерах нова версія розгортається на одному вузлі (Canary Instance) із перевіркою коректності обробки всіма активними споживачами.
11. **Політика версіонування топіків при несумісних змінах (Breaking Changes)**:
   Якщо потрібна зміна, що порушує сумісність (наприклад, кардинальна зміна моделі даних), створюється новий топік або шлях з суфіксом версії (наприклад, `orders-v2`), а старий підтримується паралельно до повного виведення з експлуатації.

### Типові помилки керування схемами

* **Помилка 1: Видалення поля без резервування тега**: Новий розробник призначає старий номер новому полю, що призводить до тихого пошкодження даних старих споживачів.
* **Помилка 2: Відсутність дефолтів у нових атрибутах**: Додавання поля без значення за замовчуванням блокує розгортання споживачів через помилки валідації.
* **Помилка 3: Вимкнення валідації в продакшені (NONE mode)**: Публікація несумісної схеми викликає масові збої всього парку мікросервісів організації.
* **Помилка 4: Зміна семантики поля без зміни назви**: Зміна одиниць вимірювання (наприклад, передача мілісекунд замість секунд у полі з назвою `timestamp`) руйнує логіку споживачів без синтаксичних помилок.
* **Помилка 5: Відсутність версіонування у сховищах**: Спроба читати старі збережені файли новою версією аналітичного коду без перевірки метаданих призводить до падіння нічних розрахунків.
* **Помилка 6: Циклічні залежності у визначеннях схем**: Використання взаємних посилань між структурами блокує автоматичну кодогенерацію клієнтських SDK у строго типізованих мовах (C++, Rust, Go).

### Контрольний чекліст аудиту Schema Registry

Перед публікацією нової версії схеми в продакшен перевірте:

1. **Режим валідації**: Чи увімкнено режим сумісності `BACKWARD_TRANSITIVE` або `FULL_TRANSITIVE` для топіка Kafka?
2. **Наявність дефолтів**: Чи кожне нове поле має явно визначений атрибут `default`?
3. **Унікальність числових тегів (Protobuf)**: Чи не було повторно використано номер тега (Field Tag Number) раніше видаленого поля?
4. **Тестування споживачів**: Чи перевірено поведінку старих сервісів під час отримання повідомлень нової схеми на тестовому контурі?
5. **Моніторинг помилок десеріалізації**: Чи налаштовано алертинг у Prometheus/Grafana на помилки `DeserializationException` та відправку битих повідомлень у Dead-Letter Queue (DLQ)?
6. **Документація полів**: Чи кожне поле містить зрозумілий опис (doc-string) для інших команд розробки?
7. **Автоматизація в CI/CD**: Чи інтегровано плагін `schema-registry-maven-plugin` або GitHub Actions для автоматичної перевірки сумісності при створенні Pull Request?
8. **Політика збереження версій**: Чи зберігаються всі попередні версії схеми в реєстрі безстроково для підтримки читання історичних бекапів?
9. **Аудит безпеки та PII**: Чи розмічено персональні дані користувачів (PII) спеціальними анотаціями для автоматичного маскування або шифрування у сховищах логів?
10. **Ідемпотентність споживачів**: Чи готові обробники до отримання повідомлень зі старими версіями схем при повторному відтворенні (Replay) з архіву?
