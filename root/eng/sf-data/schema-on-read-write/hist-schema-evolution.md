# 📜 Історія та еволюція підходів Schema-on-write та Schema-on-read

Питання про те, де саме повинна жити схема даних — усередині сховища під час запису чи в коді додатку під час читання — є однією з фундаментальних дискусій в історії комп'ютерних наук.

Розглянемо історичний шлях від монолітних схем мережевих баз CODASYL та реляційної моделі Едгара Кодда (1970) через XML/XSD-бум, революцію NoSQL/Big Data до сучасного синтезу в гібридних форматах Parquet та Schema Registry.

---

### Епоха абсолютного домінування Schema-on-write (1970–1990-ті)

У 1970 році Едгар Кодд опублікував свою революційну працю про реляційну модель. Через високу вартість дискового простору та оперативної пам'яті комп'ютерів того часу сувора типізація (Schema-on-write) була єдиним можливим інженерним вибором:
* СУБД зобов'язана була знати точний розмір кожного стовпця (`INTEGER` = 4 байти, `CHAR(32)` = 32 байти), щоб обчислювати зміщення байтів у блоках пам'яті без збереження назв полів у кожному рядку.
* Схема описувалася командами DDL (`CREATE TABLE`, `ALTER TABLE`) і жорстко контролювалася сервером бази даних.
* Будь-яка спроба записати рядок із невідповідною кількістю атрибутів або порушенням обмежень цілісності (Integrity Constraints) блокувалася на апаратно-програмному рівні рушія.
* Усі модифікації структури таблиць вимагали ексклюзивних блокувань дискових сторінок, зупиняючи паралельні транзакції бізнес-додатків.

---

### XML, JSON та зародження напівструктурованих даних (1998–2008)

Наприкінці 1990-х років розвиток Інтернету та міжсерверної взаємодії породив формати XML та JSON:
* Розробники спробували накласти суворі схеми на XML за допомогою стандартів DTD та XSD (XML Schema Definition).
* Проте надмірна складність, важкий синтаксис та повільний парсинг XSD-схем призвели до розчарування індустрії та переходу до легкого формату JSON.
* Поява динамічних мов програмування (Python, Ruby, JavaScript) популяризувала "качину типізацію" (Duck Typing) в обробці даних.
* Архітектори почали цінувати швидкість прототипування та автономність команд розробки вище за жорсткий централізований контроль реляційних адміністраторів баз даних (DBA).

### Бум NoSQL, Hadoop та концепція Schema-on-read (2009–2015)

З появою Apache Hadoop та документоорієнтованих баз даних (MongoDB, CouchDB) у 2009 році відбувся радикальний поворот у бік **Schema-on-read (Схема при читанні)**:
1. **Збереження сирих даних у Data Lake**: Hadoop дозволив записувати терабайти сирих текстових логів на розподілену файлову систему HDFS без попереднього створення таблиць чи валідації типів.
2. **Інтерпретація через MapReduce / Hive**: Аналітик визначав структуру даних лише у момент написання SQL-запиту в Apache Hive, накладаючи регулярні вирази або парсери безпосередньо на сирий текст.
3. **Гнучкість ітерацій**: Стартапи отримали можливість додавати нові фічі без написання міграційних скриптів, просто додаючи нові ключі у JSON-документи клієнтських додатків.

Проте через кілька років компанії зіткнулися зі зворотною стороною відсутності схем — явищем **Data Swamp (Болото даних)**: через відсутність контролю в сховище потрапляли пошкоджені файли, поля змінювали назви без попередження, а аналітичні запити падали з незрозумілими помилками типізації під час виконання.

---

### Сучасний синтез: Контракти схем та формати Lakehouse

Сьогодні індустрія відмовилася від крайніх позицій на користь гібридних рішень:
* **Колонкові бінарні формати (Apache Parquet, Apache ORC)**: Зберігають метадані схеми у футтері файлу, забезпечуючи високу швидкість сканування та строгу типізацію без важкого DDL-керування.
* **Schema Registry (Confluent / Apache Pulsar)**: Перевіряють сумісність повідомлень (Avro, Protobuf, JSON Schema) у шинах подій Kafka на етапі публікації.
* **Data Lakehouse (Delta Lake, Apache Iceberg)**: Накладають транзакційний шар ACID та перевірку схем поверх сирих об'єктних сховищ Amazon S3, поєднуючи дешевизну Data Lake із надійністю реляційних баз.
* **Сучасні гібридні формати**: Створення стандарту OpenAPI/JSON Schema та Protocol Buffers v3 дозволило автоматизувати кодогенерацію клієнтських DTO та перевірку інваріантів на межах мікросервісів.
* **Культура Data Contracts**: Виробники даних (Data Producers) та споживачі (Data Consumers) укладають формальні угоди про формати, типи та SLA оновлення даних, автоматизуючи перевірки через конвеєри CI/CD.
