# 📐 Математичний аналіз складності доступу та накладних витрат: Schema-on-write проти Schema-on-read

Вибір між фіксацією схеми під час запису (Schema-on-write) та її інтерпретацією під час читання (Schema-on-read) визначає алгоритмічну складність доступу до полів, обсяг метаданих, кеш-локальність, енергоефективність та коефіцієнт стиснення даних на диску.

Ця вставка містить строгий математичний аналіз часової складності операцій адресації атрибутів, розрахунок оверхеду пам'яті (Space Overhead), аналіз кеш-промахів процесора, оцінку вартості десеріалізації та розрахунок інформаційної ентропії сховища.

---

### Алгоритмічна складність доступу до атрибута

Нехай запис містить `K` атрибутів `A = {a_1, a_2, ..., a_K}` загальною довжиною `L` байтів. Необхідно отримати значення `j`-го атрибута `a_j`.

#### 1. Модель Schema-on-write (Фіксовані бінарні зміщення)
У реляційній схемі зміщення кожного стовпця `Offset(a_j)` обчислюється на етапі компіляції схеми або створення таблиці:

```text
\text{Offset}(a_j) = \sum_{i=1}^{j-1} \text{Size}(a_i)
```

Адресація поля в пам'яті виконується за одну інструкцію процесора з константною часовою складністю:

```text
T_{\text{write}}(a_j) = O(1) \text{ операцій}
```

Константний час доступу досягається завдяки тому, що компілятор або рушій СУБД генерує пряме асемблерне зміщення відносно базової адреси кортежу. Процесору не потрібно перевіряти наявність поля, декодувати його довжину або валідувати межі пам'яті.

#### 2. Модель Schema-on-read (Динамічний парсинг JSON / BSON)
У неструктурованому або напівструктурованому документі назви полів та їхні типи закодовані безпосередньо в тілі запису. Отримання поля `a_j` вимагає лексичного розбору тексту:

* Послідовне сканування байтів до виявлення ключа: `O(L)` операцій порівняння символів.
* Хеш-пошук у динамічній словниковій структурі: `O(K)` викликів хеш-функцій.
* Числова конвертація тексту в двійковий формат (`strtod` / `strtoll`): `O(D)` тактів, де `D` — довжина рядкового представлення числа.

```text
T_{\text{read}}(a_j) = O(L + D) \text{ операцій парсингу}
```

При виконанні агрегації по 100 мільйонах записів різниця між `O(1)` прямим читанням пам'яті та `O(L)` текстовим парсингом призводить до різниці в часі виконання від 0.2 секунди (PostgreSQL / C-struct) до 45 секунд (динамічний парсинг JSON у Python / Node.js).

### Розрахунок накладних витрат пам'яті на метадані (Space Overhead)

Нехай база зберігає `N` сутностей. Кожна сутність містить `K` полів із середньою довжиною назви поля `m` байтів та середньою довжиною значення `v` байтів.

#### 1. Обсяг зберігання Schema-on-write:
Метадані схеми зберігаються один раз у системному каталозі бази:

```text
S_{\text{write}} = S_{\text{catalog}} + N * \sum_{i=1}^K \text{Size}(v_i) \approx N * K * v
```

Оверхед назв полів на рівні рядків дорівнює строго **0 байтів**.

#### 2. Обсяг зберігання Schema-on-read (JSON):
Кожен рядок дублює назви ключів, лапки, коми та розділові символи:

```text
S_{\text{read}} = N * \sum_{i=1}^K (m_i + v_i + c_{\text{syntax}}) \approx N * K * (m + v + 4)
```

Коефіцієнт надлишковості метаданих `R_{\text{meta}}` визначається відношенням:

```text
R_{\text{meta}} = \frac{S_{\text{read}}}{S_{\text{write}}} = 1 + \frac{m + 4}{v}
```

#### Числовий приклад:
Для IoT-сенсора, що передає числові показники температури (`v = 4` байти `float`), де назва поля `temperature_sensor_kitchen` має довжину `m = 26` байтів:

```text
R_{\text{meta}} = 1 + \frac{26 + 4}{4} = 1 + 7.5 = 8.5 \times
```

У форматі JSON сире сховище споживає у 8.5 раза більше дискового простору та мережевої пропускної здатності, ніж строго типізована бінарна таблиця.

### Аналіз кеш-ліній та пропускної здатності шини пам'яті

Нехай розмір лінії кешу процесора становить `B = 64` байти.

* **Schema-on-write**: Однорідний масив структур `struct { float temp; uint32_t ts; }` розміщує `64 / 8 = 8` повних записів в одній кеш-лінії. При послідовному скануванні апаратний префетчер (Hardware Prefetcher) завантажує наступні лінії без затримок, забезпечуючи коефіцієнт кеш-попадань `Cache Hit Rate \approx 99.8%`.
* **Schema-on-read**: Кожен JSON-об'єкт зберігається як покажчик на виділений блок пам'яті в купі (Heap Object), розміром від 64 до 256 байтів. Сканування списку перетворюється на випадкові стрибки по пам'яті (Pointer Chasing), викликаючи до 80% кеш-промахів L3 та зупинок конвеєра CPU (CPU Pipeline Stalls).

Кожен кеш-промах вимагає звернення до повільної оперативної пам'яті DDR4/DDR5 з латентністю від 60 до 100 наносекунд. Для масиву з мільйона записів різниця в затримках доступу до пам'яті перетворюється на додаткові десятки секунд очікування процесора.

### Ентропійний аналіз та ефективність компресії

Інформаційна ентропія Шеннона для потоку даних зі схемою розраховується як:

```text
H(X) = -\sum_{i=1}^M p(x_i) \log_2 p(x_i)
```

* **Schema-on-write (Колонковий формат Parquet / ClickHouse)**: Поділ даних на однорідні стовпці однакового типу різко знижує ентропію сусідніх значень, дозволяючи застосовувати спеціалізовані алгоритми: DoubleDelta, Bit-Packing, Run-Length Encoding (RLE) з коефіцієнтом стиснення до `10x -- 20x`.
* **Schema-on-read (JSON)**: Висока дисперсія чергування тексту, чисел та синтаксичного шуму обмежує коефіцієнт універсального стиснення (gzip / zstd) на рівні `2.5x -- 4x`.

Колонкові сховища з фіксованою схемою здатні групувати значення за типами даних, що мінімізує інформаційну ентропію кожного блоку і робить можливим пряме виконання фільтрів та предикатів над стисненими байтами без повної декомпресії.

### Математична межа пропускної здатності (Roofline Model)

Згідно з моделлю Roofline, продуктивність операцій агрегації обмежується або пропускною здатністю шини пам'яті (Memory Bandwidth Bound), або обчислювальною потужністю ALU процесора (Compute Bound):

* Для Schema-on-write операція `sum(column)` є суто Memory-Bound: процесор споживає менше 1 такту на елемент, а швидкість обробки сягає максимуму пропускної здатності RAM (до 50 ГБ/с).
* Для Schema-on-read операція стає важким Compute-Bound процесом: на розбір чисел витрачається понад 50 тактів на байт, що знижує швидкість обробки до менш ніж 500 МБ/с на ядро CPU.
* Використання векторних інструкцій SIMD дозволяє додатково розширити теоретичну стелю пропускної здатності для бінарних схем, обробляючи до 64 байтів за такт на сучасних процесорах AVX-512.
