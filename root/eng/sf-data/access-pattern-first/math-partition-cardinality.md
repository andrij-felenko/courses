# 📐 Математичний аналіз ентропії ключів партиціонування та гарячих партицій

У розподілених NoSQL системах (Amazon DynamoDB, Apache Cassandra, ScyllaDB) пропускна здатність кластера масштабується лінійно лише за умови рівномірного розподілу запитів між усіма фізичними вузлами. Якщо ключ партиціонування (Partition Key) має низьку кардинальність або нерівномірний розподіл імовірностей, виникає явище **гарячої партиції (Hot Partition)**, що призводить до тротлінгу (Throttling) та деградації всієї системи.

Ця вставка містить математичну формалізацію ентропії ключів партиціонування (Shannon Entropy), модель узгодженого хешування (Consistent Hashing), розрахунок дисперсії навантаження на вузли, аналіз закону Ціпфа, оцінку нерівномірності через коефіцієнт Джині, аналіз розміру колізій та техніки соління ключів (Key Salting) для запобігання перевантаженню.

---

### Формальна модель розподілу ключів у кільці хешування

Нехай множина ключів партиціонування `K = {k_1, k_2, ..., k_M}` відображається у 128-бітний простір хеш-значень за допомогою рівномірної криптографічної або некриптографічної хеш-функції (наприклад, `MurmurHash3` або `MD5`):

```text
h: K -> [0, 2^{128} - 1]
```

Кластер складається з `N` фізичних вузлів `V = {v_1, v_2, ..., v_N}`. Кожен вузол відповідає за неперервний інтервал значень хеш-кільця довжиною `L_i = 2^{128} / N`.

Якщо ймовірність звернення до ключа `k` описується дискретним розподілом `P(k)`, сумарний потік запитів до фізичного вузла `v_i` визначається сумою:

```text
\lambda(v_i) = \Lambda * \sum_{k \in K, h(k) \in \text{Range}(v_i)} P(k)
```

Де `\Lambda` — сумарний вхідний потік запитів до всієї бази даних (Requests Per Second, RPS).

### Оцінка ентропії Шеннона та рівномірності розподілу

Ентропія множини ключів партиціонування визначає ступінь невизначеності та рівномірності звернень:

```text
H(K) = - \sum_{i=1}^M P(k_i) * \log_2 P(k_i)
```

#### Граничні випадки:
1. **Ідеальний рівномірний розподіл (Uniform Distribution)**: `P(k_i) = 1 / M` для всіх `i`.
   Максимальна ентропія досягає значення:
   ```text
   H_{max}(K) = \log_2 M
   ```
   У цьому випадку навантаження ідеально збалансоване: `\lambda(v_i) = \Lambda / N`.
2. **Вироджений розподіл (Single Hot Key)**: Один ключ генерує більшість звернень (наприклад, `P(k_1) = 0.9`, а решта ділять `0.1`).
   Ентропія різко падає:
   ```text
   H(K) << \log_2 M
   ```
   Вузол, що обслуговує ключ `k_1`, отримує `0.9 * \Lambda` усього трафіку, що спричиняє вичерпання ліміту IOPS/RCU/WCU та відхилення запитів кодом 429 (Too Many Requests).

### Моделювання нерівномірного доступу за законом Ціпфа (Zipf's Law)

У реальних веб-сервісах популярність сутностей (наприклад, акаунти знаменитостей у соцмережах або топові товари в інтернет-магазинах) часто описується законом Ціпфа:

```text
P(k_r) = \frac{1 / r^s}{\sum_{n=1}^M (1 / n^s)}
```

Де `r` — ранг популярності ключа (r = 1, 2, ..., M), а `s` — параметр експоненти (зазвичай `s ≈ 1`).

При `s = 1` перший найпопулярніший ключ отримує частку трафіку:

```text
P(k_1) \approx \frac{1}{\ln M + \gamma}
```

Для бази з `M = 10^6` ключів один єдиний ключ отримує понад 7% усього навантаження гігантського кластера, створюючи критичну гарячу точку.

---

### Оцінка дисбалансу через коефіцієнт Джині (Gini Coefficient)

Для кількісної оцінки нерівномірності розподілу навантаження між фізичними вузлами застосовується коефіцієнт нерівності Джині:

```text
G = \frac{\sum_{i=1}^N \sum_{j=1}^N |\lambda(v_i) - \lambda(v_j)|}{2 N \sum_{i=1}^N \lambda(v_i)}
```

Значення `G = 0` відповідає ідеальному балансу, тоді як `G -> 1` сигналізує про критичну концентрацію запитів на одиничних серверах, що вимагає негайної реконфігурації ключів.

---

### Ймовірнісний розрахунок тротлінгу (Throttling Probability)

Нехай кожен фізичний вузол має максимальну пропускну здатність `C_{max}` операцій на секунду.

Якщо надходження запитів підпорядковується пуассонівському процесу з параметром `\lambda(v_i)`, імовірність переповнення буфера вузла та виникнення тротлінгу розраховується за формулою хвоста пуассонівського розподілу:

```text
P(Throttle | v_i) = P(X > C_{max}) = 1 - \sum_{j=0}^{C_{max}} \frac{\lambda(v_i)^j * e^{-\lambda(v_i)}}{j!}
```

Якщо `\lambda(v_i) > C_{max}`, система переходить у нестабільний режим черги, а затримка зростає за гіперболічним законом:

```text
T_{latency} \approx \frac{1}{C_{max} - \lambda(v_i)} -> \infty
```

### Техніка соління ключів (Key Salting / Sharded Keys)

Для ліквідації гарячих партицій із виродженим розподілом застосовують детерміноване або випадкове **соління ключів (Key Salting)**.

#### Математична схема розбиття:
Замість збереження запису за єдиним ключем `PK = "STATUS#PENDING"` ключ модифікується додаванням випадкового цілочисельного суфікса з діапазону `[0, S - 1]`:

```text
PK_{salted} = Concat(PK, "#", Random(0, S - 1))
```

Де `S` — коефіцієнт соління (Sharding Factor), що обирається з умови:

```text
S >= \lceil \frac{\lambda(PK)}{C_{max}} \rceil
```

#### Оцінка балансування навантаження після соління:
Після додавання солі сумарний потік запитів розбивається на `S` незалежних підпотоків:

```text
\lambda(PK_j) = \frac{\lambda(PK)}{S} <= C_{max}
```

Кожен суфікс спрямовується хеш-функцією на інший фізичний вузол, повністю усуваючи локальний перегрів.

#### Ціна операції читання (Fan-out Query Cost):
При вибірці всіх записів за вихідним ключем `PK` клієнтський додаток зобов'язаний виконати `S` паралельних запитів `Query` до всіх солей від `0` до `S - 1` та об'єднати результати в пам'яті:

```text
T_{read_all} = \max_{j=0}^{S-1} ( T_{query}(PK_j) )
```

Завдяки паралельному виконанню час вибірки обмежується затримкою найповільнішого запиту (Tail Latency), тоді як пропускна здатність на запис зростає у `S` разів.

### Аналіз ентропії часових партицій (Time-Bucket Partitioning)

При збереженні високоінтенсивних часових рядів (IoT-сенсори, фінансові котирування) використання поточного дня як Partition Key (`PK = "2024-05-12"`) призводить до того, що 100% операцій запису в поточний момент часу потрапляють в одну єдину партицію сьогоднішнього дня.

#### Рішення через двовимірне шардування:
Ключ розбивається на композитне сполучення ідентифікатора сенсора та часового бакета (Time Bucket):

```text
PK = Concat(sensor_id, "#", YearMonth)
SK = Timestamp
```

Такий підхід забезпечує рівномірне розсіювання записів від тисяч сенсорів по всьому хеш-кільцю, обмежуючи максимальний розмір однієї партиції константним обсягом місячних даних одного пристрою та виключаючи ризик переповнення дискових лімітів окремого вузла.

#### Вибір розміру бакета:
Оптимальний розмір часового бакета `B` (день, тиждень, місяць) розраховується за формулою:

```text
B = \frac{\text{Max Partition Size}}{\text{Daily Ingestion Rate}}
```

Якщо пристрій генерує 1 МБ даних на добу, а максимальний розмір партиції в Cassandra становить 100 МБ, бакет розміром в 1 місяць (30 МБ) забезпечує триразовий запас надійності без деградації читання.
