# 📋 Довідник патернів моделювання NoSQL: DynamoDB та Cassandra

Моделювання даних під шаблони доступу (Access-Pattern-First) вимагає переходу від класичних нормалізованих зв'язків до композитних ключів, колекцій елементів та розріджених глобальних індексів.

Цей довідник містить готові шаблони проєктування основних типів зв'язків (1:1, 1:N, M:N), техніки перевантаження індексів (GSI Overloading), патерни розріджених індексів (Sparse Indexes), стратегії Keyset-пагінації, антипатерни та практичні правила оптимізації витрат.

---

### Матриця патернів моделювання зв'язків у Single Table Design

| Тип зв'язку | Формат Partition Key (PK) | Формат Sort Key (SK) | Операція вибірки | Переваги |
| :--- | :--- | :--- | :--- | :--- |
| **Сутність (1:1)** | `USER#<user_id>` | `#METADATA` | `GetItem(PK, SK)` | Прямий O(1) доступ до профілю |
| **Один-до-багатьох (1:N)**| `USER#<user_id>` | `ORDER#<date>#<order_id>`| `Query(PK, begins_with(SK))` | Завантаження користувача з усіма замовленнями за 1 RTT |
| **Багато-до-багатьох (M:N)**| `STUDENT#<s_id>` (або `CLASS#<c_id>`) | `CLASS#<c_id>` (або `STUDENT#<s_id>`) | `Query` за базовою таблицею або GSI1 | Прямий та зворотний пошук без проміжної JOIN-таблиці |
| **Ієрархія (Дерево)** | `ORG#<org_id>` | `DEP#<dep_id>#TEAM#<team_id>`| `Query(PK, begins_with(SK))` | Вибірка всієї гілки підрозділів за один запит |
| **Розріджений статус (Sparse)**| `GSI1PK = "ORDER#STATUS#PENDING"` | `GSI1SK = "<timestamp>"` | `Query` за GSI1 | Вибірка лише активних замовлень без сканування завершених |

### Детальні рецепти конфігурації патернів

#### 1. Моделювання зв'язку Багато-до-Багатьох (M:N) через Adjacency List

Розглянемо систему запису студентів на університетські курси:

```text
Базова таблиця:
PK: STUDENT#101, SK: COURSE#CS101  -> Студент 101 записаний на CS101
PK: STUDENT#101, SK: COURSE#MATH201 -> Студент 101 записаний на MATH201

Глобальний вторинний індекс (GSI1):
GSI1PK (інвертований SK): COURSE#CS101
GSI1SK (інвертований PK): STUDENT#101
```

* **Запит 1**: Знайти всі курси студента 101 -> `Query(PK = "STUDENT#101", SK begins_with "COURSE#")`
* **Запит 2**: Знайти всіх студентів курсу CS101 -> `Query_GSI1(GSI1PK = "COURSE#CS101", GSI1SK begins_with "STUDENT#")`

Обидва запити виконуються за константний час `O(1)` без використання реляційних проміжних таблиць зв'язку (Junction Tables).

---

#### 2. Патерн розрідженого індексу (Sparse Index) для фільтрації черг

У типовій e-commerce системі 99% замовлень мають статус `COMPLETED`, і лише 1% перебуває у статусі `PENDING` (очікує обробки оператором).

Якщо проіндексувати всю таблицю, індекс міститиме мільйони непотрібних рядків.

#### Рішення через Sparse GSI:
* Для рядків зі статусом `PENDING` записується атрибут `GSI1PK = "STATUS#PENDING"` та `GSI1SK = "<created_at>"`.
* Для рядків зі статусом `COMPLETED` атрибут `GSI1PK` видаляється або встановлюється у `NULL`.

Оскільки DynamoDB автоматично виключає з індексу елементи, що не мають ключового атрибута GSI, розмір індексу скорочується у 100 разів, а опитування черги `Query(GSI1PK = "STATUS#PENDING")` відбувається миттєво.

### Патерни проєктування ключів для Apache Cassandra та ScyllaDB

У CQL (Cassandra Query Language) таблиця моделюється суворо під один конкретний запит:

```sql
-- Таблиця для вибірки останніх 50 вимірювань сенсора за інтервал часу
CREATE TABLE sensor_readings_by_time (
    sensor_id text,
    year int,
    recorded_at timestamp,
    temperature double,
    humidity double,
    PRIMARY KEY ((sensor_id, year), recorded_at)
) WITH CLUSTERING ORDER BY (recorded_at DESC);
```

#### Правила побудови ключів у Cassandra:
1. **Складений Partition Key `(sensor_id, year)`**: Запобігає нескінченному зростанню однієї партиції понад рекомендований ліміт (100 МБ або 100 000 рядків).
2. **Clustering Column `recorded_at DESC`**: Зберігає дані на диску в порядку спадання часу, дозволяючи виконувати вибірку `SELECT * FROM sensor_readings_by_time WHERE sensor_id = 'S42' AND year = 2024 LIMIT 50;` шляхом послідовного зчитування перших блоків файлу SSTable.

### Реалізація беззбійної пагінації (Keyset Pagination)

Використання зміщень `OFFSET` у розподілених базах даних заборонено, оскільки воно вимагає сканування та відкидання всіх попередніх рядків.

#### Патерн пагінації через LastEvaluatedKey у DynamoDB:

```json
{
  "TableName": "SingleTable",
  "KeyConditionExpression": "PK = :pk AND SK begins_with :sk",
  "ExpressionAttributeValues": {
    ":pk": {"S": "USER#1001"},
    ":sk": {"S": "ORDER#"}
  },
  "Limit": 20,
  "ExclusiveStartKey": {
    "PK": {"S": "USER#1001"},
    "SK": {"S": "ORDER#2024-05-01#0020"}
  }
}
```

База даних негайно позиціонує курсор на значення `ExclusiveStartKey` через B-Tree індекс за час `O(log N)`, повертаючи наступну сторінку без перегляду попередніх записів.

### Стратегії оптимізації вартості (Cost Optimization) у DynamoDB

1. **Проєкція атрибутів у GSI (Index Projections)**:
   * `KEYS_ONLY`: Індекс містить лише ключові атрибути. Мінімальний розмір на диску та мінімальні витрати WCU.
   * `INCLUDE`: До індексу додаються лише ті поля, які реально потрібні екрану вибірки.
   * `ALL`: Копіює весь документ. Застосовується тільки за крайньої потреби, оскільки подвоює витрати пам'яті та WCU.
2. **Агрегація дрібних сутностей у JSON-документи (Document Inlining)**: Якщо сутність (наприклад, список товарних позицій `OrderItems`) завжди читається та оновлюється виключно разом із батьківським замовленням `Order`, її не слід виносити в окремі рядки таблиці; достатньо зберегти її як вкладений JSON-масив усередині запису замовлення.
3. **Утилізація транзакцій запису**: Замість виклику `TransactWriteItems` (який споживає подвійну кількість WCU: 2 WCU за кожні 1 КБ даних) використовуйте умовні вирази `ConditionExpression` для одинарних `PutItem`/`UpdateItem`.

### Типові архітектурні антипатерни та як їх уникати

* **Антипатерн 1: Використання дати як єдиного Partition Key**: `PK = "2024-05-12"` концентрує 100% записів у поточну добу на один вузол. Виправляється композитним ключем `PK = "SENSOR#101#2024-05"`.
* **Антипатерн 2: Виконання Scan замість Query**: Сканування всієї таблиці призводить до вичерпання лімітів RCU та уповільнення роботи інших клієнтів.
* **Антипатерн 3: Неконтрольоване зростання розміру рядка**: Збереження зростаючого масиву логів усередині одного JSON-атрибута призводить до перевищення ліміту 400 КБ на елемент. Логи обов'язково розбиваються на окремі рядки з унікальним `SK`.
* **Антипатерн 4: Створення зайвих Global Secondary Indexes**: Кожен новий GSI додає фінансову вартість зберігання та споживає додаткові WCU при кожному записі; об'єднуйте кілька патернів в один універсальний GSI за допомогою перевантаження ключів.
* **Антипатерн 5: Неузгоджені типи атрибутів у композитних ключах**: Використання чисел замість форматованих рядків із фіксованою довжиною (наприклад, `ORDER#1` замість `ORDER#00001`) ламає лексикографічне сортування `SK`.

### Контрольний чекліст аудиту моделі NoSQL перед релізом

1. **Повна відповідність шаблонам доступу**: Для кожного запиту користувацького інтерфейсу існує точний виклик `GetItem` або `Query`; заборонено використання операцій `Scan` або `ALLOW FILTERING`.
2. **Перевірка кардинальності Partition Key**: Переконайтеся, що ключ партиціонування має достатню кількість унікальних значень (використовуйте `user_id`, `device_id`, `uuid`), щоб уникнути утворення гарячих точок.
3. **Обмеження розміру партицій**: Розмір однієї Item Collection у DynamoDB з LSI не повинен перевищувати 10 ГБ; у Cassandra — не більше 100 МБ на одну партицію.
4. **Контроль витрат на GSI**: Пам'ятайте, що кожен запис у базову таблицю генерує асинхронний запис у всі активні GSI, подвоюючи витрати WCU; проєктуйте проєкції атрибутів (`KEYS_ONLY`, `INCLUDE`) замість копіювання всіх полів (`ALL`).
5. **Стратегія видалення застарілих даних (TTL)**: Налаштуйте автоматичний Time-To-Live для тимчасових сесій, логів та черг для безкоштовного очищення дискового простору рушієм СУБД.
6. **Ізоляція транзакцій запису**: Застосовуйте умовні вирази `attribute_not_exists(PK)` для операцій `PutItem` для захисту від випадкового перезапису існуючих сутностей при конкурентних запитах.
7. **Контроль розміру одного елемента**: Розмір окремого елемента в DynamoDB жорстко обмежений 400 КБ; великі бінарні файли (зображення, PDF) повинні зберігатися в об'єктному сховищі (Amazon S3), а в таблиці зберігається лише посилання на URL.
8. **Моніторинг метрик Throttling**: Налаштуйте алерти в CloudWatch на метрики `ReadThrottleEvents` та `WriteThrottleEvents` для своєчасного виявлення гарячих партицій.
