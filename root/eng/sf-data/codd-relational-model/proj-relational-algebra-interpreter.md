# ⚙️ Реалізація інтерпретатора реляційної алгебри

Ця вставка містить практичну реалізацію програмного рушія реляційної алгебри у пам'яті (in-memory relational algebra execution engine). Програми на C та C++ показують, як фундаментальні математичні оператори — селекція `σ`, проекція `π`, декартів добуток `×`, природне з'єднання `⋈`, об'єднання `∪` та різниця `\` — реалізуються на рівні низкорівневих структур даних та алгоритмів.

## Архітектура програмного рушія та макет пам'яті

Для виконання операцій реляційної алгебри програмний рушій оперує двома основними типами абстракцій:
1. **Кортеж (Tuple):** Послідовність скалярних значень фіксованої довжини, що відповідає одному рядку реляційної таблиці.
2. **Відношення (Relation):** Динамічний контейнер, який зберігає заголовок (схему з іменами атрибутів) та множину унікальних кортежів.

У низькорівневих мовах програмування реалізація реляційної алгебри вимагає розв'язання кількох фундаментальних інженерних задач:
- **Забезпечення множинної семантики:** При додаванні нового кортежу до відношення рушій мусить перевірити унікальність і вилучити дублікати.
- **Динамічне картування атрибутів:** Оскільки проекція та з'єднання змінюють порядок та склад колонок, рушій мусить будувати проміжні карти зсувів (index mappings) для переносу значень між операндами та результатом.
- **Управління пам'яттю:** Оператори алгебри створюють нові тимчасові відношення. Кожне таке відношення має правильно виділяти та звільняти оперативну пам'ять, унеможливлюючи витоки ресурсів.

Нижче подано дві реалізації програмного рушія мовами C та C++. Реалізація мовою C показує низкорівневу роботу з фіксованими масивами, покажчиками та процедурним обробленням помилок. Реалізація мовою C++ демонструє сучасні ідіоми: автоматичне управління ресурсами RAII, семантику переміщення, контейнери Стандартної бібліотеки та трьохсторонній оператор порівняння (spaceship operator `<=>`).

## Детальний аналіз реалізації та алгоритмічної складності

Розглянемо докладніше, як саме зведені алгоритми реалізують кожну алгебраїчну операцію та які пастки виникають при практичній розробці.

### 1. Реалізація Селекції (`σ`)
Оператор селекції фільтрує рядки відношення за логічною умовою. У поданій реалізації функція `relation_select` сканує вихідне відношення `src` за один прохід.
- Пошук індексу атрибута `find_attr` виконується за `O(k)`, де `k` — кількість атрибутів у схемі.
- Сканування `N` кортежів займає `O(N · k)` дій.
- Складність за пам'яттю становить `O(N' · k)`, де `N'` — кількість кортежів, що задовольнили умову (`N' ≤ N`).

У промислових СУБД лінійне сканування (SeqScan) замінюється індексним доступом (IndexScan) за допомогою B-дерев або хеш-індексів, що знижує алгоритмічну складність знаходження відповідних кортежів з `O(N)` до `O(log N)` або `O(1)`.

### 2. Реалізація Проекції (`π`) та вилучення дублікатів
Оператор проекції створює нове відношення зі зменшеним набором атрибутів. Головна алгоритмічна складність проекції полягає у **вилученні дублікатів** (Duplicate Elimination).

Коли з таблиці видаляються атрибути (наприклад, видалення первинного ключа `ID` з відношення `Users(ID, Name, City)`), різні кортежі можуть перетворитися на ідентичні рядки.
- У мові C перевірка унікальності виконується у функції `relation_add_tuple`, яка порівнює новий кортеж з усіма вже доданими за `O(N')` за допомогою `strcmp`. У результаті підсумкова складність проекції стає квадратичною: `O(N² · k)`.
- У мові C++ вилучення дублікатів можна прискорити до `O(N log N)` за допомогою `std::set` або до `O(N)` за допомогою `std::unordered_set` зі спеціальною хеш-функцією для кортежу.

Якщо знехтувати вилученням дублікатів (як це робиться за замовчуванням у мові SQL без ключового слова `DISTINCT`), вираз алгебри перетворюється на мультимножинну алгебру (Bag Algebra). Однак у чистому каноні Кодда збереження дублікатів руйнує еквівалентності алгебраїчних тотожностей.

### 3. Реалізація Природного З'єднання (`⋈`)
Природне з'єднання `relation_natural_join` виконується за допомогою класичного алгоритму **вкладених петель** (Nested Loop Join):
1. Рушій знаходить спільні атрибути двох відношень.
2. Для кожного кортежу `t₁` з першої таблиці `R₁` (зовнішня петля) рушій ітерується по всіх кортежах `t₂` з другої таблиці `R₂` (внутрішня петля).
3. Якщо значення за спільними атрибутами збігаються, рушій конкатенує атрибути `t₁` та `t₂` і додає об'єднаний кортеж до результату.

Часова складність алгоритму вкладених петель становить `O(|R₁| · |R₂|)`. На великих обсягах даних (наприклад, при з'єднанні таблиць по 1 мільйону рядків) цей алгоритм потребує `10¹²` порівнянь, що є неприпустимим.

Промислові СУБД для оптимізації з'єднання застосовують алгоритм **Хеш-з'єднання** (Hash Join):
- Спочатку будується хеш-таблиця для меншого відношення `R₁` за ключем з'єднання: `O(|R₁|)`.
- Потім сканується більше відношення `R₂`, і для кожного кортежу виконується швидкий пошук у хеш-таблиці: `O(|R₂|)`.
- Підсумкова складність Хеш-з'єднання становить `O(|R₁| + |R₂|)`, що дозволяє з'єднувати мільйонні таблиці за частки секунди.

Іншим поширеним фізичним алгоритмом є **З'єднання сортуванням і злиттям** (Sort-Merge Join). Спочатку обидва відношення сортуються за ключем з'єднання за `O(|R| log |R|)`, після чого виконується одночасний лінійний прохід двох відношень за один цикл `O(|R| + |S|)`. З'єднання сортуванням є ідеальним для баз даних, де дані вже впорядковані первинним індексом.

## Покроковий розбір виконання запиту на прикладі коду

У функції `main` представлених програм виконується комплексний вираз реляційної алгебри:

```
Result = π_{Name, Amount}(σ_{City = 'Київ'}(Users) ⋈ Orders)
```

Послідовність виконання у рушії відповідає таким крокам:
1. **Ініціалізація баз даних:** Створюються два відношення `Users` (з атрибутами `ID, Name, City`) та `Orders` (з атрибутами `OrderID, ID, Amount`).
2. **Крок 1 (Селекція `σ_{City = 'Київ'}`):** Сканується таблиця `Users`. З трьох кортежів лише кортежі з `ID = 101` (Аліса) та `ID = 103` (Єва) мають значення `City = "Київ"`. Формується тимчасове відношення `kyiv_users` з 2 кортежами.
3. **Крок 2 (Природне з'єднання `⋈`):** Тимчасова таблиця `kyiv_users` з'єднується з `Orders` за спільним атрибутом `ID`. Для Аліси (`ID = 101`) знаходяться два замовлення (`OrderID = 5001` на 250.0 та `OrderID = 5002` на 120.0). Для Єви (`ID = 103`) замовлень немає. Для Боба (`ID = 102`) замовлення є, але Боб не потрапив у `kyiv_users` через селекцію. Результатом з'єднання є відношення `joined` з 2 кортежами та 4 атрибутами (`ID, Name, City, OrderID, Amount`).
4. **Крок 3 (Проекція `π_{Name, Amount}`):** З відношення `joined` вирізаються дві колонки `Name` та `Amount`. Формується підсумкова таблиця `result`, яка друкується на екран.

Дана послідовність кроків показує, як алгоритм Кодда автоматично гарантує коректність обчислення реляційних запитів будь-якої складності.

## Управління пам'яттю та порівняння мовних парадигм C та C++

Реалізація реляційної алгебри підкреслює глибокі відмінності між процедурним підходом мови C та об'єктно-орієнтованим підходом сучасного C++:

1. **Фіксовані буфери проти динамічних векторів:**
   - Мова C використовує статично розраховані одновимірні та двовимірні масиви `values[MAX_ATTRS][MAX_VAL_LEN]`. Це усуває накладні витрати на динамічне виділення купи, але обмежує максимальний розмір таблиць значеннями констант `MAX_TUPLES` та `MAX_ATTRS`.
   - Мова C++ оперує динамічними контейнерами `std::vector<std::string>`, що дозволяє обробляти таблиці довільної арності та кардинальності.
2. **Автоматичне очищення пам'яті (RAII):**
   - У мові C створення тимчасових відношень усередині складеного виразу запиту вимагає від розробника явного стеження за життєвим циклом об'єктів. При роботі з динамічною пам'яттю (`malloc`/`free`) кожен проміжний крок алгебри мусить мати відповідальний виклик звільнення пам'яті.
   - У мові C++ деструктори класів `std::vector` та `std::string` автоматично звільняють оперативну пам'ять при виході з області видимості, гарантуючи строгу виняткову безпеку (Strong Exception Guarantee).
3. **Оператори порівняння та кастомне сортування:**
   - У C++20 запроваджено трьохсторонній оператор порівняння `operator<=>` (`default`), який автоматично ґенерує лексикографічне порівняння для всіх елементів `std::vector<std::string>`. Це дозволяє використовувати кортежі у стандартних алгоритмах `std::sort` та в контейнерах `std::set` без написання власних компораторів.

## Організація фізичного збереження: Порядкове (Row-Store) проти Колоночного (Column-Store)

У поданих прикладах коду відношення реалізовано у вигляді **рядкового збереження** (Row-Store або N-ary Relational Model, NSM). Кортежі зберігаються послідовно один за одним у пам'яті.

Рядкова організація є ідеальною для **OLTP-навантажень** (Online Transaction Processing), де запити зазвичай читають або оновлюють усі атрибути одного кортежу (наприклад, вибірка профілю користувача за ID).

Проте для **OLAP-навантажень** (Online Analytical Processing — побудова звітів, агрегація за терабайтами даних), рядкове збереження є неефективним. Якщо аналітичному запиту потрібно порахувати середню суму всіх замовлень `AVG(Amount)`, row-store рушій змушений вичитати з диска та клейшу процесора всі інші атрибути (`OrderID`, `UserID`, `Date`), що марнує пропускну здатність пам'яті.

Сучасні аналітичні СУБД (ClickHouse, Snowflake, DuckDB) використовують **колоночне збереження** (Column-Store або Decomposition Storage Model, DSM). Кожен атрибут зберігається у окремому суцільному векторі пам'яті:

```
Column_ID:     [101, 102, 103]
Column_Name:   ["Аліса", "Боб", "Єва"]
Column_Amount: [250.0, 120.0, 890.0]
```

При виконанні проекції `π_{Amount}(Orders)` колоночний рушій вичитує лише вектор `Column_Amount`, повністю ігноруючи сусідні атрибути. Окрім того, однакові типи даних у межах одного вектора стискаються зі значно вищим коефіцієнтом за допомогою алгоритмів RLE (Run-Length Encoding), Bit-Packing або Frame of Reference.

### Векторизоване виконання (Vectorized Execution / Volcano Model)

Для обробки великих баз даних класична модель ітераторів «по одному кортежу за виклик» (Volcano Iterator Model) створює занадто високі накладні витрати на віртуальні виклики функцій у пелі.

Сучасні реляційні рушії застосовують **векторизоване виконання**: замість одного кортежу метод `next()` повертає вектор (векторний блок) з 1024 або 4096 кортежів. Це дозволяє комбілювати операції реляційної алгебри за допомогою SIMD-інструкцій сучасних процесорів (AVX-512 / ARM Neon), піднімаючи швидкість обробки реляційних запитів до десятків мільярдів рядків на секунду.

## Компільовані запити (JIT Query Compilation)

Додатковим напрямком прискорення виконання реляційної алгебри у сучасних СУБД (таких як HyPer чи PostgreSQL із сумісними розширеннями LLVM) є **JIT-компіляція запитів** (Just-In-Time Compilation).

Замість обходу інтерпретованого дерева реляційної алгебри під час виконання, СУБД під час підготовки запиту ґенерує машинні інструкції (на базі компіляторного інфраструктури LLVM), які зливають селекцію, проекцію та хешування в один суцільний цикл машинного коду без проміжних збережень кортежів у пам'яті. Завдяки цьому продуктивність виконання виразів реляційної алгебри наближається до швидкості виконання ручно написаного коду мовою C.

## Управління буферним пулом (Buffer Pool Manager) та дисковим кешем

При роботі з дисковими базами даних (де розмір таблиць значно перевищує обсяг оперативної пам'яті), виконання операцій реляційної алгебри абстрагується від фізичних дискових блоків за допомогою **менеджера буферного пулу** (Buffer Pool Manager).

1. Таблиця розбивається на сторінки пам'яті (зазвичай розміром 8 КБ у PostgreSQL або 16 КБ у MySQL).
2. Оператори селекції та з'єднання запитують сторінки у буферного пулу за заголовочним ідентифікатором `PageID`.
3. За наявності вільних фреймів сторінка читається з диска і блокується у пам'яті (pinning). При вичерпанні обсягу пам'яті алгоритми витіснення (LRU-K, Clock-Sweep) скидають брудні сторінки (dirty pages) назад на диск.

Таким чином, реляційна алгебра працює над абстрактними кортежами незалежно від того, де фізично розміщені дані: у надшвидкій L1/L2 оперативній пам'яті, на NVMe SSD-накопичувачі чи на віддаленому мережевому сховищі Amazon S3.

## Оптимізація запитів на основі вартості (Cost-Based Optimization, CBO)

При перетворенні виразу реляційної алгебри у фізичний план виконання оптимізатор СУБД будує множину еквівалентних дерев запиту.
Для кожного фізичного плану обчислюється підсумкова вартість (Cost):

```
Cost = (I/O Pages Read × W_io) + (CPU Tuples Processed × W_cpu) + (Operator Memory × W_mem)
```

Оптимізатор збирає гістограми розподілу значень атрибутів (HyperLogLog, Equi-Width / Equi-Depth Histograms) для точної оцінки селективності (Selectivity) предикатів `σ_φ`. На основі селективності вибирається порядок з'єднання відношень (наприклад за допомогою алгоритму динамічного програмування або генетичних алгоритмів для складних запитів із понад 10 таблицями).

Використання статистики селективності запобігає «катастрофічним» фізичним планам, у яких велика таблиця з'єднується з іншою великою таблицею перед застосуванням селекції, зменшуючи проміжні обсяги даних у тисячі разів.

### Паралельні фізичні плани (Parallel Query Execution)

У багатиядерних системах фізичні оператори реляційної алгебри розщеплюються на паралельні потоки (Parallel Scans, Parallel Hash Joins, Parallel Aggregations). Потік-координатор розділяє вхідне відношення на секції (chunks) та розподіляє їх між воркер-потоками (Worker Threads), об'єднуючи проміжні результати оператором `Gather`. Це дозволяє лінійно масштабувати швидкість обчислення реляційних запитів із кількістю CPU-ядер.

Окрім цього, сучасні ін-меморі рушії (наприклад DuckDB або Velox) поєднують паралельне виконання з векторизацією: кожен воркер-потік працює над власною векторною пачкою даних у межах локального процесорного кешу (L1/L2 Cache locality), унеможливлюючи міжядерну синхронізацію та міжпроцесорні затримки NUMA (Non-Uniform Memory Access).

Практичний інтерпретатор, представлений у даній вставці, відображає концептуальне ядро будь-якої комерційної СУБД: незважаючи на величезний комплекс інженерних оптимізацій (індекси, буферні пули, векторизація, JIT), фундаментальні виклики та результати залишаються строго підпорядкованими математичним законам реляційної алгебри Кодда.

Низькорівневий аналіз показує, що правильне проектування реляційного рушія полягає у дотриманні границь між логічною алгеброю та фізичним виконанням: доки реляційна алгебра гарантує декларативну еквівалентність виразів, фізичний рушій може вільним чином замінювати алгоритми виконання (наприклад зкладені петлі на хеш-з'єднання), покращуючи швидкість запитів без ризику викривлення результатів.

Завдяки відокремленню логічного шару реляційної алгебри від фізичного шару алгоритмів та форматів збереження даних, програмні рушії баз даних зберігають модульність: зміна фізичної структури збереження на диску або додання нового алгоритму з'єднання не вимагає переписування запитів реляційної алгебри.

Такий підхід дозволяє розробникам інфраструктурного ПЗ оптимізувати виконання запитів до конкретного апаратного забезпечення (наприклад з використанням графічних прискорювачів GPU або FPGA-карт для паралельного з'єднання), залишаючи логічний код реляційної алгебри незмінним. У результаті реляційна модель Кодда виявляється не лише строгою математичною теорією, а й надзвичайно гнучкою практичною архітектурою для побудови сучасних високонавантажених обчислювальних систем.

## Типові пастки реалізації та крайові випадки

1. **Несумісність схем (Schema Mismatch):** Спроба виконати об'єднання `∪` або різницю `\` над відношеннями з різними атрибутами або неузгодженими типами даних у C++ спричиняє виняток `std::invalid_argument`, а в C — невизначену поведінку або вихід за межі масиву.
2. **Переповнення буфера у мові C:** Фіксований розмір буферів `MAX_TUPLES` та `MAX_VAL_LEN` потребує суворого контролю меж (`snprintf`, `strncpy`), щоб запобігти вразливостям переповнення буфера на стеку.
3. **Обробка NULL значень:** При виконанні проекції за атрибутом, який відсутній у вихідній схемі, програмний рушій підставляє константу `"NULL"`. Однако у повній реалізації тризначної логіки `NULL` не дорівнює іншому `NULL`, що вимагає внесення особливих правил порівняння у функцію `tuple_equals`.
