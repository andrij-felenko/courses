# 📜 Від моноліту SGML до спартанського XML: народження універсального синтаксису

У 1969 році троє дослідників компанії IBM — Чарльз Ґолдфарб (Charles Goldfarb), Едвард Мошер (Edward Mosher) та Реймонд Лорі (Raymond Lorie) — зіткнулися з проблемою ведення складної юридичної документації на мейнфреймах. Різні комп'ютерні програми вимагали специфічних керуючих кодів для друку: один набір байтів для форматування абзацу на терміналі, інший — для фотоскладального апарата. Будь-яка зміна друкарського обладнання вимагала переписування тисяч сторінок документів. Ґолдфарб із колегами запропонували революційну ідею: відокремити зміст та логічну структуру тексту від його візуального оформлення. Так з'явилася мова **GML (Generalized Markup Language)**, названа за першими літерами прізвищ її авторів (Goldfarb, Mosher, Lorie). Замість інструкцій типу «зробити цей рядок жирним шрифтом 12 пунктів» автори ввели декларативні теги: `:h1.` для заголовка першого рівня, `:p.` для абзацу та `:ol.` для впорядкованого списку.

Успіх GML у корпоративному секторі привернув увагу Міжнародної організації зі стандартизації (ISO). Чарльз Ґолдфарб очолив комітет, який розробляв загальносвітовий стандарт розмітки. Результатом багаторічної праці став стандарт **ISO 8879:1986 — SGML (Standard Generalized Markup Language)**.

## Тягар універсальності SGML

SGML створювався як метамова, здатна описати будь-яку схему розмітки для будь-якої предметної галузі: від технічних посібників військової авіації до академічних словників і видавничих систем. Проте це прагнення до абсолютної гнучкості перетворило стандарт на 500-сторінковий математичний трактат із колосальною синтаксичною складністю.

У 1980-х роках дисковий простір був обмеженим, а оператори набирали тексти вручну на повільних терміналах. Щоб зекономити байти та пальці наборщиків, у специфікацію SGML заклали механізми **мінімізації тегів (англ. *tag omission*)**. У схемі DTD дозволялося вказувати прапорці `- O` (перший дефіс означає обов'язковий відкривальний тег, а літера `O` — англ. *omissible*, тобто закривальний тег можна пропустити). Наприклад, якщо схема знала, що елемент списку `<li>` не може містити всередині інший `<li>`, автору дозволялося не писати `</li>`: синтаксичний аналізатор мав здогадатися про закриття попереднього пункту в момент відкриття наступного.

Більше того, SGML підтримував **скорочені форми запису (англ. *SHORTTAG*)**, складні правила згортання пробільних символів та препроцесорну підстановку довільних текстових макросів. Наслідок виявився фатальним для автоматизації: **розпарсити документ SGML було неможливо без попереднього завантаження та повного обчислення граматики DTD**. Синтаксичний аналізатор не знав, де закінчується один елемент і починається інший, якщо він не володів повною схемою типів документа. Написання повноцінного SGML-парсера вимагало років роботи цілих інженерних команд, а розмір самого коду аналізатора перевищував можливості тогочасного персонального комп'ютера.

Коли Тім Бернерс-Лі (Tim Berners-Lee) у 1989–1990 роках створював Всесвітнє павутиння (World Wide Web), він узяв синтаксис SGML за основу мови HTML. Проте браузери 1990-х років (NCSA Mosaic, Netscape Navigator, Internet Explorer) не були повноцінними SGML-процесорами: вони містили спрощені саморобні рушії, які ігнорували відсутність закривальних тегів, пропускали невідомі елементи та прощали будь-які синтаксичні порушення. Це породило феномен «супу з тегів» (англ. *tag soup*): документи в Інтернеті писалися з помилками, а кожен браузер намагався відновити структуру на основі власних евристик, що призводило до різного відображення однієї й тієї самої сторінки.

## Робоча група W3C та правило 80/20

До середини 1990-х років стало очевидно, що HTML вичерпав себе як формат для передачі довільних структурованих даних. Розробникам програмного забезпечення був потрібен спосіб передавати між серверами каталоги товарів, банківські транзакції, медичні карти та наукові вектори. Використовувати для цього HTML було неможливо через фіксований набір тегів (`<p>`, `<div>`, `<table>`), які описували візуальне подання, а не бізнес-сутність. Використовувати ж повний SGML у браузерах та на мобільних пристроях було нереально через його монструозність.

У травні 1996 року на конференції SGML '96 Джон Босак (Jon Bosak) з компанії Sun Microsystems запропонував консорціуму W3C створити спеціальну робочу групу з метою перенести потужність SGML у веб. Робоча група дістала назву **W3C XML Working Group**, до її ядра увійшли:
- **Джон Босак (Jon Bosak)** — голова комітету, який забезпечував дипломатичний баланс між ворогуючими гігантами індустрії (Microsoft, Sun, Netscape, IBM);
- **Тім Брей (Tim Bray)** — співредактор специфікації;
- **Майкл Сперберг-Макквін (C. M. Sperberg-McQueen)** — співредактор та глибокий теоретик структурованих текстів;
- **Джеймс Кларк (James Clark)** — автор перших еталонних SGML-парсерів і згодом найшвидшого потокового C-парсера `expat`.

Головним дороговказом групи стало **правило Парето (принцип 80/20)**: викинути 80% непотрібної складності SGML, зберігши 80% його практичної сили. Робота тривала менше двох років, і 10 лютого 1998 року консорціум W3C опублікував офіційну рекомендацію **XML 1.0 (Extensible Markup Language)**.

## Революційні принципи XML 1.0

XML 1.0 не був винаходом принципово нового синтаксису — це було радикальне та безжальне хірургічне очищення SGML від нашарувань компромісів минулого:

1. **Концепція коректної формованості (англ. *Well-formedness*):**
   У SGML документ без DTD був безглуздим набором літер. XML увів фундаментальне розмежування: документ називається *well-formed*, якщо він підпорядковується суворим синтаксичним правилам мови (кожен відкривальний тег має відповідний закривальний або є самозакривальним, атрибути взяті в лапки, дерево має єдиний корінь). Такий документ може бути розібраний на складові вузли будь-яким парсером за один лінійний прохід **без завантаження жодних зовнішніх схем чи словників**.

2. **Драконівська обробка помилок (англ. *Draconian error handling*):**
   Це було найрадикальніше рішення комітету, зафіксоване в розділі 1.2 специфікації XML 1.0. Якщо аналізатор натрапляє на найменше синтаксичне порушення (наприклад, пропущена закривальна дужка `>` або незакритий тег `<br>`), процесор **зобов'язаний негайно припинити нормальну обробку та повідомити про фатальну помилку (fatal error)**. Парсерам категорично заборонялося застосовувати евристики відновлення чи намагатися вгадати намір автора. Цей пункт викликав шалений опір веб-розробників, звиклих до всеїдності HTML, проте він уберіг XML від фрагментації та гарантував, що некоректні дані не потраплять у фінансові та системні бази даних.

3. **Справжня підтримка Юнікоду:**
   Усі XML-процесори були зобов'язані за замовчуванням підтримувати кодування UTF-8 та UTF-16, усунувши хаос регіональних кодових сторінок, які роками розривали сумісність текстових файлів.

4. **Ліквідація мінімізацій:**
   Будь-яке опущення тегів було заборонено. Якщо елемент порожній, він повинен записуватися або як `<tag></tag>`, або через компактний самозакривальний синтаксис `<tag/>`. Значення всіх атрибутів стали обов'язково братися в подвійні чи одинарні лапки (`name="value"`).

## Ера розквіту та переосмислення

Поява XML 1.0 спричинила справжній технологічний вибух на рубежі 1990–2000-х років. Корпоративні платформи сприйняли XML як святий Грааль інтеграції гетерогенних систем. Навколо базового стандарту виникло сузір'я технологій консорціуму W3C:
- **XML Namespaces (1999)** — механізм ізоляції словників через префікси та URI;
- **DOM Level 1–3 та SAX** — стандартизовані інтерфейси маніпуляції деревом у пам'яті та потоці;
- **XPath та XSLT** — мови адресації вузлів та декларативної трансформації документів;
- **XML Schema (XSD)** — сувора типізація даних на заміну застарілому DTD;
- **SOAP та WSDL** — протоколи корпоративних веб-сервісів (Enterprise SOA).

На XML було побудовано формати векторної графіки (SVG), геоданих (KML, GPX), математичних формул (MathML), конфігурацій (Apache Ant, Maven, Spring Framework) та стандарти офісних документів (OpenDocument / ODF та Microsoft Office Open XML / DOCX, XLSX).

Хоча у 2010-х роках у сфері легкозважних веб-API та мобільної розробки формат JSON значною мірою потіснив XML завдяки прямому відображенню на примітивні типи даних JavaScript (словники, масиви, числа), спадщина XML лишається фундаментом комп'ютерної індустрії. Документоорієнтовані структури з довільним змішаним текстом (англ. *mixed content*), суворою валідацією схем і глобальними просторами імен досі не мають рівноцінної заміни, а суворий принцип коректної формованості XML став еталоном проектування форматів обміну даними.
