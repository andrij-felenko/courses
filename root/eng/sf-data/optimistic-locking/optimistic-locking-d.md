- [Песимістичне блокування](root:sf-data/pessimistic-locking) — монопольне захоплення фізичних рядків через блокування на рівні СУБД.
</preknowlist>

Коли два незалежні процеси одночасно зчитують один і той самий рядок із таблиці реляційної бази даних, обчислюють новий стан у локальній пам'яті застосунку протягом кількох секунд і записують результат назад, виникає руйнівна колізія паралелізму.

Розглянемо банківський рахунок клієнта із залишком 1000 доларів. Перший процес зчитує баланс $1000 для списання щомісячної комісії за обслуговування в розмірі $200. Одночасно другий процес зчитує той самий баланс $1000 для проведення операції зняття готівки в банкоматі на суму $300. Обидва процеси виконують незалежні локальні обчислення: перший отримує новий баланс $800 (`1000 - 200`), другий — $700 (`1000 - 300`). Перший процес надсилає до бази даних SQL-запит `UPDATE accounts SET balance = 800 WHERE id = 1` і успішно фіксує транзакцію. За мілісекунду після цього другий процес виконує власний запит `UPDATE accounts SET balance = 700 WHERE id = 1`.

Результат виконання є катастрофічним: баланс рахунку стає $700, а факт списання $200 першим процесом безслідно зникає, наче цієї операції ніколи не існувало. Така ситуація називається **аномалією втраченого оновлення** (лат. *anomalia* від грец. *ἀνωμαлія* — нерівність, відхилення від норми; англ. *Lost Update Anomaly*).

Класичне розв'язання цієї проблеми в теорії реляційних систем полягає у використанні песимістичного блокування рядка через команду `SELECT ... FOR UPDATE`. Однак утримання фізичного монопольного замка на рядку бази даних упродовж усього часу, поки користувач переглядає сторінку в браузері чи заповнює форму замовлення, паралізує систему. Відкрита транзакція блокує підключення з пулу з'єднань, спричиняє взаємні блокування (Deadlocks) і унеможливлює роботу інших користувачів із цим записом.

Для усунення цього вузького місця застосовують інший підхід: читання виконується абсолютно вільно без накладання будь-яких блокувань СУБД, але разом із бізнес-даними зчитується числовий маркер версії рядка. Коли настає момент запису, застосунок надсилає команду оновлення з умовою, що номер версії в базі не змінився: `UPDATE accounts SET balance = @new_val, version = version + 1 WHERE id = @id AND version = @old_version`. Якщо за час обчислень інший процес уже встиг оновити рядок і збільшити версію, умова `WHERE` не знаходить жодного запису, кількість змінених рядків дорівнює нулю, і операція безпечно відхиляється.

Цей архітектурний механізм називається **оптимістичним блокуванням** (лат. *optimus* — найкращий; очікування найбільш сприятливого перебігу подій без частих колізій; англ. *Optimistic Concurrency Control*, *OCC* / *Optimistic Locking*). Поняття «блокування» тут є умовним: фізичні блокування на рівні СУБД не утримуються під час бізнес-обчислень, а цілісність даних гарантується умовною перевіркою версії в момент фіксації.

### Анатомія трифазної моделі OCC

У класичній комп'ютерній теорії, формалізованій дослідниками Сян-Цуном Кунгом і Джоном Робінсоном (детальний аналіз першоджерела наведено у вставці [Історія виникнення OCC](root:sf-data/optimistic-locking/hist-occ-origins.md)), кожна транзакція з оптимістичним керуванням конкурентністю проходить три послідовні фази:

```
[ 1. Фаза читання ]      --->     [ 2. Фаза валідації ]     --->     [ 3. Фаза запису ]
(Read Phase)                      (Validation Phase)                 (Write Phase)
Зчитування кортежу та             Атомарна перевірка:                Успіх: version = version + 1
версії у пам'ять RAM              version_db == version_read         Колізія: відхилення (Rows = 0)
```

1. **Фаза читання (Read Phase)**:
   Застосунок виконує стандартний SQL-запит `SELECT id, balance, version FROM accounts WHERE id = 42`. База даних повертає кортеж, і застосунок зберігає поточний номер версії (наприклад, `version = 1`) у локальній змінній або стані об'єкта. Ніякі блокувальні замки в таблиці блокувань СУБД не реєструються, а рядок залишається повністю доступним для паралельного читання та запису іншими транзакціями.

2. **Фаза валідації (Validation Phase)**:
   Після завершення обчислень у пам'яті застосунок має перевірити, чи не порушено серіалізованість. У сучасних реляційних базах даних фаза валідації поєднується з фазою запису в межах єдиної атомарної операції `UPDATE` за допомогою предикату порівняння.

3. **Фаза запису (Write Phase)**:
   Застосунок виконує команду модифікації, яка атомарно перевіряє версію та інкрементує її:

```sql
UPDATE accounts
SET balance = 800,
    version = version + 1
WHERE id = 42
  AND version = 1;
```

Якщо рядок із `id = 42` досі має `version = 1`, СУБД записує новий баланс 800, встановлює `version = 2` і повертає застосунку статус успіху: кількість змінених рядків (`affected rows`) дорівнює `1`.

Якщо ж інший клієнт уже змінив рядок і збільшив версію до `2`, предикат `WHERE id = 42 AND version = 1` повертає хибний результат (`FALSE`). СУБД не змінює жодного байта в таблиці та повертає кількість змінених рядків `0`. Застосунок інтерпретує це значення як виявлення колізії конкурентного доступу (**Optimistic Concurrency Conflict**) і переходить до процедури обробки помилки.

![Часова шкала конкурентних спроб запису та виявлення колізії](/root/eng/sf-data/optimistic-locking/img/occ-timeline.svg)
*Конкурентний доступ двох клієнтів: Клієнт 1 успішно фіксує нову версію, тоді як Клієнт 2 отримує нуль змінених рядків через застарілий маркер версії*

### Стратегії формування маркерів версіонування

Для відстеження змін у кортежі реляційної бази даних використовують чотири основні типи **маркерів версії** (лат. *versio* — видозміна, поворот; англ. *Version Token*):

| Тип маркера | SQL-тип стовпця | Логіка перевірки | Переваги | Ризики та недоліки |
|---|---|---|---|---|
| **Цілочисельний лічильник** | `BIGINT` або `INT` | `WHERE id = @id AND version = @old_v` | Абсолютна монотонність, імунітет до проблеми ABA, мінімальний розмір (4–8 байтів) | Вимагає додавання окремої колонки до схеми таблиці |
| **Часова мітка (Timestamp)** | `TIMESTAMP(6)` | `WHERE id = @id AND updated_at = @old_ts` | Зрозумілість для людини, фіксація часу останньої модифікації | Розсинхронізація системних годинників (Clock Skew), межа роздільної здатності |
| **Криптографічний хеш** | `CHAR(64)` або `BYTEA` | `WHERE id = @id AND row_hash = @old_hash` | Не потребує лічильника; чутливий до реальної зміни даних | Витрати процесора на хешування, ризик помилкового пропуску при циклічній зміні (ABA) |
| **Пополярне порівняння** | Усі змінені колонки | `WHERE id = @id AND col1 = @old1 AND col2 = @old2` | Не вимагає додаткових колонок у схемі таблиці | Складність SQL-запитів, пастки з `NULL`, колосальне навантаження на індекси |

#### 1. Монотонний цілочисельний лічильник (Integer Version)
Це загальноприйнятий галузевий стандарт, реалізований у більшості сучасних ORM-фреймворків (анотація `@Version` у JPA/Hibernate, `[ConcurrencyCheck]` в Entity Framework, колонка `lock_version` в Ruby on Rails Active Record).

Таблиця оголошується з цілочисельним полем:

```sql
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    price_cents BIGINT NOT NULL,
    stock_quantity INT NOT NULL,
    lock_version BIGINT NOT NULL DEFAULT 1
);
```

Під час створення запису поле `lock_version` ініціалізується одиницею. Кожне наступне оновлення виконує строго монотонний інкремент:

```sql
UPDATE products
SET stock_quantity = stock_quantity - 1,
    lock_version = lock_version + 1
WHERE id = 105
  AND lock_version = 14;
```

Використання 64-бітного типу `BIGINT` повністю виключає ризик переповнення лічильника: навіть при 1 000 000 оновлень рядка на секунду лічильник вичерпає свій діапазон лише через 584 000 років.

#### 2. Часова мітка (Timestamp)
Замість лічильника використовують поле дати й часу останньої модифікації:

```sql
UPDATE documents
SET content = @new_text,
    updated_at = CURRENT_TIMESTAMP(6)
WHERE id = 42
  AND updated_at = '2026-08-25 14:30:15.123456+00';
```

Використання часових міток несе три приховані інженерні ризики:
1. **Розсинхронізація годинників (Clock Skew)**: Якщо мітка часу генерується на рівні серверів застосунку, різниця показів годинників між серверами навіть у кілька мілісекунд може призвести до того, що пізніше оновлення отримає ранішу мітку часу. Тому значення часової мітки завжди повинно генеруватися виключно сервером СУБД (`CURRENT_TIMESTAMP`).
2. **Обмеження роздільної здатності**: Якщо дві транзакції модифікують запис протягом однієї мікросекунди, вони отримають ідентичну часову мітку, що призведе до пропуску колізії.
3. **Високосні секунди та переведення часу**: Стрибки системного часу NTP можуть спричинити повернення часу назад, що ламає інваріант монотонного зростання маркера.

#### 3. Криптографічний хеш або контрольна сума (Content Hash / Checksum)
У цій схемі застосунок або тригер СУБД обчислює криптографічний хеш (наприклад, SHA-256) від конкатенації всіх значущих бізнес-полів кортежу.

Цей підхід є основою механізму умовних запитів у розподілених RESTful-сервісах за стандартом HTTP/1.1 (RFC 9110). Сервер повертає клієнту сутність разом із заголовком `ETag: "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"`. Коли клієнт надсилає оновлення, він передає заголовок `If-Match: "e3b0c442..."`. Якщо стан ресурсу на сервері змінився, веб-сервер повертає статус `412 Precondition Failed`.

Головний недолік використання хешів — так звана **проблема ABA** (англ. *ABA Problem*): якщо значення поля спочатку було змінено зі стану `A` на `B`, а потім інша транзакція повернула його назад зі стану `B` на `A`, хеш повернеться до початкового значення. Поточна транзакція вважатиме, що запис не зазнавав змін, хоча насправді в системі відбулися дві проміжні мутації.

#### 4. Порівняння всіх стовпців (All Columns Comparison)
Якщо змінювати схему бази даних заборонено, застосунок може включити у предикат `WHERE` старі значення всіх колонок, які зчитувалися на початку:

```sql
UPDATE employees
SET salary = 5000,
    department_id = 12
WHERE id = 99
  AND salary = 4200
  AND (department_id = 10 OR (department_id IS NULL AND @old_dep IS NULL))
  AND (bonus IS NULL);
```

Цей метод надзвичайно крихкий. Він вимагає громіздкої обробки значень `NULL` через особливості тризначної логіки SQL (де вираз `NULL = NULL` повертає `UNKNOWN`, а не `TRUE`), створює величезні текстові запити та призводить до сканування всієї таблиці, якщо для порівнюваних стовпців відсутні вторинні індекси.

### Фізичний механізм виконання CAS у реляційному рушії

Нерідко виникає хибне враження, що конструкція оптимістичного оновлення `UPDATE ... WHERE id = @id AND version = @v` може сама бути схильною до стану гонитви (Race Condition), якщо два процеси одночасно надішлють цю команду до СУБД.

Щоб зрозуміти, чому оптимістичне блокування є абсолютно надійним, необхідно розглянути фізичну послідовність дій рушія реляційної бази даних під час виконання одного оператора `UPDATE`:

```
1. Пошук сторінки в Buffer Pool за індексом (B-Tree Scan)
2. Захоплення короткочасної ексклюзивної засувки сторінки (Page Exclusive Latch)
3. Накладання ексклюзивного блокування рядка (Row-Level Exclusive Lock / X-Lock)
4. Оцінка предикату: WHERE id = @id AND version = @old_version
     ├─ Предикат ІСТИННИЙ:
     │    - Запис образу зміни в журнал випереджального запису (WAL Record)
     │    - Модифікація кортежу на сторінці (встановлення нового значення та version + 1)
     │    - Збільшення лічильника змінених рядків: affected_rows = 1
     └─ Предикат ХИБНИЙ:
          - Пропуск рядка без модифікації
          - affected_rows = 0
5. Вивільнення ексклюзивного блокування рядка та засувки сторінки
6. Повернення клієнту значення affected_rows
```

Реляційний рушій оцінює умову `WHERE` не в ізольованому вакуумі, а **під захистом короткочасного апаратного та рядкового блокування**.

Якщо транзакції `T1` та `T2` одночасно намагаються виконати `UPDATE` для одного рядка, СУБД серіалізує їхній доступ на рівні сторінки або рядка. Транзакція `T1` першою захоплює блокування рядка, бачить `version = 1`, змінює версію на `2`, записує зміну в журнал WAL і звільняє замок.

Транзакція `T2`, яка чекала на вивільнення замка, отримує доступ до фізичного кортежу наступною. Вона зчитує актуальний заголовок кортежу на сторінці, де поле `version` уже дорівнює `2`. Перевірка умови `WHERE version = 1` дає хибний результат, оновлення не виконується, і рушій повертає клієнту статус `affected_rows = 0`.

Таким чином, оптимістичне блокування на рівні застосунку спирається на апаратний та транзакційний примітив **порівняння зі заміною** (англ. *Compare-And-Swap*, *CAS*), гарантований ядром СУБД.

### Стратегії реагування на виявлені колізії

Коли застосунок отримує результат `affected_rows == 0`, це означає, що паралельний потік змінив стан сутності. Залежно від бізнес-вимог застосовують одну з трьох стратегій вирішення конфлікту:

#### 1. Швидке відхилення (Fail Fast)
Застосунок негайно перериває операцію та повідомляє ініціатора про конфлікт.

Ця стратегія є обов'язковою для інтерактивних користувацьких інтерфейсів (редагування статей у CMS, модифікація карточки клієнта в CRM або спільне редагування документів). Користувачеві показують повідомлення про те, що дані були змінені іншим оператором, разом із інтерфейсом порівняння різниці (Diff Viewer), де він може вручну вирішити, які зміни слід зберегти.

#### 2. Автоматичний цикл повторних спроб (Automatic Retry Loop)
Якщо зміна виконується автоматичним фоновим сервісом (наприклад, списання балансу, оновлення лічильника переглядів або зміна статусу замовлення за подією з черги Kafka), помилка не повинна відхиляти бізнес-процес.

Застосунок автоматично виконує повторне читання свіжого стану, наново проводить бізнес-перевірки та повторює спробу фіксації. Щоб уникнути ефекту «навали запитів» (Thundering Herd) та синхронізації конфліктуючих потоків, між спробами застосовують **експоненційний відступ із випадковим джитером (Exponential Backoff with Jitter)**:

```
t_sleep = random(0, min(T_max, T_base · 2^attempt))
```

Повний аналіз та робочий програмний код реалізації циклу повторних спроб мовами C та C++ наведено у вставці [Реалізація retry-петлі з експоненційним відступом](root:sf-data/optimistic-locking/proj-optimistic-retry-loop.md).

#### 3. Автоматичне триканальне злиття (Three-Way Merge)
Якщо перший користувач змінив поле `phone_number`, а другий — поле `shipping_address`, конфлікту на рівні бізнес-логіки немає: змінені множини атрибутів не перетинаються.

Застосунок зчитує новий стан із бази даних, накладає локальні зміни другого користувача виключно на змінені ним поля (якщо вони не конфліктують із полями, зміненими першим користувачем) і повторює запис із новим номером версії.

### Порівняльний аналіз: OCC проти песимістичного блокування

Вибір між оптимістичною та песимістичною моделлю керування конкурентністю визначається рівнем конкуренції за дані (**Contention Rate**) та характером навантаження.

![Пропускна здатність OCC проти песимістичного блокування](/root/eng/sf-data/optimistic-locking/img/occ-vs-pessimistic-throughput.svg)
*Залежність реальної пропускної здатності від рівня конкуренції за записи: OCC домінує при низькій конкуренції, але зазнає колапсу продуктивності через лавину повторів при високій конкуренції*

При низькому рівні конкуренції (`P_conflict < 10%`) оптимістичне блокування забезпечує максимальну пропускну здатність, оскільки запити на читання не створюють жодних записів у таблицях блокувань СУБД, не викликають змагання за лінії кешу процесора та не вимагають обходу графу взаємних блокувань.

Проте коли частка конфліктних операцій перевищує критичний поріг (20–25%), оптимістична модель зазнає стрімкого колапсу продуктивності: ресурси процесора та мережі марно витрачаються на обчислення транзакцій, які будуть відхилені, а лавина повторних спроб (Retry Storm) перевантажує СУБД.

Строге математичне виведення точки фазового переходу, формули ймовірності колізії за розподілом Ципфа та закону Літтла представлено у вставці [Математичний аналіз імовірності колізій та пропускної здатності](root:sf-data/optimistic-locking/math-occ-collision-probability.md).

### Патерн версіонування кореня агрегату (Aggregate Root Version Bumping)

Один із найнебезпечніших крайових випадків оптимістичного блокування виникає під час роботи зі складними ієрархічними структурами даних або агрегатами в термінах предметно-орієнтованого проєктування (Domain-Driven Design, DDD).

Розглянемо агрегат `Замовлення (Order)`, що складається з кореневого запису в таблиці `orders` та списку дочірніх позицій у таблиці `order_items`.

Бізнес-інваріант вимагає: загальна вартість замовлення не може перевищувати кредитний ліміт клієнта у $500.

Нехай поточне замовлення містить товарів на $400, а поле `orders.lock_version = 5`.
1. Клієнт 1 додає нову позицію `OrderItem(id=3, price=$50)`. Транзакція виконує `INSERT INTO order_items ...`. Сам рядок `orders` при цьому не змінюється.
2. Одночасно Клієнт 2 додає іншу позицію `OrderItem(id=4, price=$70)`. Транзакція також виконує `INSERT INTO order_items ...`.

Обидві транзакції паралельно перевіряють інваріант у пам'яті: `400 + 50 ≤ 500` (успіх) та `400 + 70 ≤ 500` (успіх). Обидва оператори `INSERT` успішно додають рядки до таблиці `order_items`. У результаті сумарна вартість замовлення стає $520, що грубо порушує бізнес-правило.

Оскільки рядок `orders` не модифікувався, версія `lock_version` не змінилася, і стандартне оптимістичне блокування не помітило колізії!

![Патерн оновлення версії кореня агрегату](/root/eng/sf-data/optimistic-locking/img/occ-aggregate-versioning.svg)
*Примусовий інкремент версії кореня агрегату (Order) при додаванні або видаленні дочірніх сутностей (Order Items)*

Для вирішення цієї проблеми застосовують патерн **примусового оновлення версії кореня агрегату (Force Increment / Aggregate Root Version Bumping)**: будь-яка операція додавання, видалення або зміни дочірнього елемента зобов'язана виконати явний CAS-інкремент версії кореневого об'єкта:

```sql
-- У межах транзакції додавання позиції товару:
INSERT INTO order_items (order_id, sku, price_cents, quantity)
VALUES (101, 'MOUSE', 5000, 1);

-- Примусовий інкремент версії батьківського замовлення:
UPDATE orders
SET lock_version = lock_version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = 101
  AND lock_version = 5;
```

Якщо інша транзакція паралельно додала інший елемент і вже збільшила `lock_version` до `6`, другий запит поверне `affected_rows = 0`, транзакція відкотиться, і інваріант кредитного ліміту буде збережено.

### Аномалія перекосу запису (Write Skew) та матеріалізація конфліктів

Навіть якщо кожен окремий рядок захищений оптимістичною версією, класичне оптимістичне блокування окремих кортежів безсиле проти аномалії **перекосу запису** (англ. *Write Skew*), коли бізнес-інваріант охоплює кілька взаємопов'язаних, але фізично різних рядків.

Розглянемо класичну задачу про чергування лікарів у лікарні. Правило вимагає: на зміні завжди повинен залишатися щонайменше один активний черговий лікар.

У системі зареєстровано двох лікарів:
* Лікар А: `{id: 1, name: 'Alice', on_call: true, version: 1}`
* Лікар Б: `{id: 2, name: 'Bob', on_call: true, version: 1}`

Обидва лікарі одночасно надсилають запит на зняття з чергування через погане самопочуття:
1. Транзакція `T_A` перевіряє умову: `SELECT COUNT(*) FROM doctors WHERE on_call = true`. Отримує результат `2`. Оскільки `2 > 1`, лікар Alice може піти з чергування.
2. Одночасно транзакція `T_B` перевіряє ту саму умову: `SELECT COUNT(*) FROM doctors WHERE on_call = true`. Також отримує `2` і дозволяє Bob піти.
3. Транзакція `T_A` виконує: `UPDATE doctors SET on_call = false, version = 2 WHERE id = 1 AND version = 1`. Рядок лікаря Alice оновлено (`affected_rows = 1`).
4. Транзакція `T_B` виконує: `UPDATE doctors SET on_call = false, version = 2 WHERE id = 2 AND version = 1`. Рядок лікаря Bob також успішно оновлено (`affected_rows = 1`), адже версія рядка з `id = 2` досі дорівнювала `1`!

У результаті обидва лікарі зняті з чергування (`on_call = false` для всіх), а лікарня залишилася без чергового персоналу. Оптимістична перевірка окремих рядків не виявила колізії, тому що транзакції модифікували різні кортежі.

Для захисту від аномалії Write Skew застосовують архітектурний патерн **матеріалізації конфліктів (Materializing Conflicts)**: створюють штучний спільний рядок (або використовують батьківський запис зміни), версію якого зобов'язані оновити всі транзакції, що змінюють конфігурацію чергування:

```sql
-- Таблиця розкладу чергування:
-- id: 10, shift_date: '2026-08-25', schedule_version: 4

-- Обидві транзакції виконують CAS-перевірку спільного ресурсу:
UPDATE hospital_shifts
SET schedule_version = schedule_version + 1
WHERE id = 10
  AND schedule_version = 4;
```

Транзакція `T_A` успішно збільшить `schedule_version` до `5`. Транзакція `T_B` отримає `affected_rows = 0`, буде відхилена і під час повторної спроби побачить, що на зміні залишився лише один лікар, запобігши порушенню інваріанту.

### Розподілене оптимістичне блокування у NoSQL та хмарних сервісах

При переході від монолітних реляційних баз даних до розподілених сховищ концепція оптимістичного блокування стає головним фундаментом горизонтального масштабування.

#### 1. Amazon DynamoDB: Умовні вирази (Conditional Writes)
У DynamoDB відсутній менеджер розподілених блокувань. Будь-яка операція запису `PutItem`, `UpdateItem` або `DeleteItem` може містити параметр `ConditionExpression`:

```json
{
  "TableName": "UserProfiles",
  "Key": { "user_id": { "S": "usr_99" } },
  "UpdateExpression": "SET email = :new_email, version = version + :inc",
  "ConditionExpression": "attribute_exists(user_id) AND version = :expected_version",
  "ExpressionAttributeValues": {
    ":new_email": { "S": "new@example.com" },
    ":expected_version": { "N": "3" },
    ":inc": { "N": "1" }
  }
}
```

Якщо інший клієнт уже збільшив `version`, вузол-координатор DynamoDB повертає помилку `ConditionalCheckFailedException` (HTTP 400), запобігаючи перезапису чужих даних.

#### 2. Apache CouchDB: Ланцюжки ревізій (`_rev`)
У документоорієнтованій СУБД CouchDB кожен документ має службове поле `_rev` вигляду `"2-7051cbeaa8d870d092b1ec6114e9e343"`. Перша цифра позначає порядковий номер ревізії, а шістнадцятковий суфікс — MD5-хеш вмісту документа.

При спробі оновити документ клієнт зобов'язаний передати поточний `_rev`. Якщо в базі вже зафіксовано новішу ревізію, CouchDB повертає `HTTP 409 Conflict`, що змушує клієнта виконати злиття змін (Replication Conflict Resolution).

#### 3. Redis: Оптимістичні транзакції через `WATCH`
У високопродуктивному сховищі Redis оптимістичний контроль реалізовано за допомогою команди `WATCH`:

```text
WATCH user:42:balance
val = GET user:42:balance
new_val = val - 100
MULTI
SET user:42:balance new_val
EXEC
```

Команда `WATCH` реєструє ключ у списку спостереження поточного клієнтського підключення. Якщо до моменту виконання блоку `MULTI ... EXEC` будь-який інший клієнт модифікує ключ `user:42:balance`, команда `EXEC` повертає порожній результат `(nil)`, скасовуючи виконання всієї транзакції.

### Патерн шардованих лічильників для боротьби з надвисокою конкуренцією

Коли окремий запис бази даних стає «надгарячим» (наприклад, лічильник лайків вірусного відео на YouTube або баланс акційного товару під час масштабного розпродажу), класичне оптимістичне блокування зазнає колапсу: 99% транзакцій зазнають колізії, а час очікування стрімко зростає.

Для подолання цього обмеження застосовують патерн **шардованих лічильників (Sharded Counters / Distributed Accumulators)**:

```sql
CREATE TABLE product_stock_shards (
    product_id BIGINT NOT NULL,
    shard_id INT NOT NULL,
    available_stock INT NOT NULL CHECK (available_stock >= 0),
    lock_version BIGINT NOT NULL DEFAULT 1,
    PRIMARY KEY (product_id, shard_id)
);

-- Розбиваємо 100 одиниць товару на 10 незалежних слотів:
INSERT INTO product_stock_shards (product_id, shard_id, available_stock)
VALUES 
    (501, 0, 10), (501, 1, 10), (501, 2, 10), (501, 3, 10), (501, 4, 10),
    (501, 5, 10), (501, 6, 10), (501, 7, 10), (501, 8, 10), (501, 9, 10);
```

Коли клієнт бронює одиницю товару:
1. Застосунок випадково обирає слот: `random_shard = rand() % 10`.
2. Виконує CAS-списання лише для цього конкретного слота:

```sql
UPDATE product_stock_shards
SET available_stock = available_stock - 1,
    lock_version = lock_version + 1
WHERE product_id = 501
  AND shard_id = @random_shard
  AND available_stock >= 1
  AND lock_version = @old_version;
```

Завдяки розподілу на 10 шарді інженерне навантаження та ймовірність колізій на кожному окремому рядку зменшуються рівно в 10 разів. Якщо в обраному слоті закінчився залишок, алгоритм послідовно пробує сусідні шарди. Загальний залишок товару обчислюється швидким агрегатним читанням `SELECT SUM(available_stock) FROM product_stock_shards WHERE product_id = 501`.

### Генераційні токени та гонка інвалідації кешу

У сучасних триланкових архітектурах перед реляційною базою даних майже завжди розміщується шар кешування (Redis/Memcached). Неузгодженість між оптимістичним записом у СУБД та асинхронним оновленням кешу може призвести до довготривалого отруєння кешу застарілими даними (**Stale Cache Pollution**).

Розглянемо гонку:
1. Потік `T0` зчитує з бази даних рядок `{id: 42, val: 'Old', version: 1}` через промах кешу (Cache Miss).
2. Потік `T1` оновлює базу даних: `UPDATE ... SET val = 'New', version = 2 WHERE id = 42 AND version = 1`.
3. Потік `T1` успішно фіксує транзакцію і видаляє старий ключ із кешу Redis: `DEL user:42`.
4. Повільний потік `T0`, чий мережевий пакет затримався, нарешті доходить до Redis і записує своє раніше зчитане застаріле значення: `SET user:42 'Old'`.

Кеш виявляється отруєним застарілим станом `'Old'` на весь час життя ключа (TTL), попри те, що в базі даних уже давно зафіксовано стан `'New'`.

Для запобігання цій гонці номер версії з оптимістичного блокування використовують як **генераційний токен огорожі (Fencing / Generation Token)**. У кеш записують складену структуру `{val, version}`, а запис у Redis виконують за допомогою атомарного Lua-скрипта:

```lua
-- Lua-скрипт умовного оновлення кешу в Redis:
local current_version = redis.call('HGET', KEYS[1], 'version')
if not current_version or tonumber(ARGV[2]) >= tonumber(current_version) then
    redis.call('HSET', KEYS[1], 'val', ARGV[1], 'version', ARGV[2])
    return 1
else
    return 0 -- Застарілий запис відхилено
end
```

Потік `T0` передасть `version = 1`. Якщо потік `T1` уже встановив у кеші `version = 2`, Redis відхилить запізнілий запис `T0`, зберігши актуальність даних у кеші.

### Офлайн-блокування у тривалих бізнес-процесах (Optimistic Offline Lock)

У корпоративних системах часто виникає потреба в бізнес-транзакціях, які тривають хвилинами чи годинами й охоплюють кілька послідовних веб-сторінок майстра оформлення (Multi-Step Wizard).

Мартін Фаулер у класичній праці «Patterns of Enterprise Application Architecture» розділив такі сценарії на дві моделі:

1. **Песимістичне офлайн-блокування (Pessimistic Offline Lock)**:
   При відкритті форми сутність позначається у спеціальній таблиці блокувань як зайнята конкретним користувачем (`INSERT INTO lock_table (entity_id, user_id, locked_at)`). Якщо користувач закриє вкладку браузера чи втратить інтернет-зв'язок, запис залишається заблокованим для всієї компанії, доки адміністратор не скине замок вручну або не вичерпається таймаут сесії (Lease TTL).

2. **Оптимістичне офлайн-блокування (Optimistic Offline Lock)**:
   Система не реєструє жодних блокувань під час проходження майстра. Номер версії сутності передається через приховані поля форми або стан клієнтського SPA-застосунку (`hidden input name="version" value="42"`). На фінальному кроці «Підтвердити та зберегти» сервер виконує єдину коротку транзакцію СУБД із предикатом `WHERE version = 42`.

Якщо за час заповнення майстра інший менеджер уже вніс зміни до карточки клієнта, фінальний крок повертає повідомлення про колізію, а користувач бачить різницю між своїми даними та зафіксованим станом. Це повністю виключає завислі блокування в системі.

### Взаємодія OCC з рівнями ізоляції транзакцій

Поведінка оптимістичного блокування істотно відрізняється залежно від налаштованого рівня ізоляції реляційної СУБД (детально рівні ізоляції описані в [Рівні ізоляції транзакцій](root:sf-data/isolation-levels)):

#### 1. Рівень `Read Committed` (дефолтний у PostgreSQL, Oracle, SQL Server)
Під цим рівнем ізоляції кожен оператор `UPDATE` працює за правилом «останнього зафіксованого стану» (Current Read).

Коли виконується команда `UPDATE ... WHERE id = @id AND version = @old_v`, рушій шукає найсвіжішу зафіксовану версію кортежу. Якщо версія була змінена іншою зафіксованою транзакцією, предикат повертає `FALSE`, команда завершується без помилки, повертаючи `affected_rows = 0`. Поточна транзакція залишається працездатною, і застосунок може виконати повторне читання всередині тієї ж транзакції або відкатити її.

#### 2. Рівень `Repeatable Read` / `Snapshot Isolation` (дефолтний у MySQL InnoDB)
Під рівнем `Repeatable Read` рушій СУБД гарантує, що транзакція бачить знімок даних на момент свого початку.

У СУБД PostgreSQL, якщо транзакція `T2` намагається оновити рядок, який уже був змінений і зафіксований паралельною транзакцією `T1` після створення знімка `T2`, рушій генерує помилку серіалізації:

```text
ERROR: could not serialize access due to concurrent update
SQLSTATE: 40001
```

У цьому випадку команда `UPDATE` не просто повертає `0` змінених рядків — СУБД переводить усю поточну транзакцію у статус помилки (`ABORTED`). Будь-які наступні SQL-запити відхилятимуться. Застосунок зобов'язаний виконати повний відкат транзакції (`ROLLBACK`), відкрити нову транзакцію, отримати новий транзакційний знімок і повторити операцію спочатку.

### Зведена матриця: Вибір моделі конкурентного контролю

| Модель синхронізації | Механізм контролю | Затримка при низькому конфлікті | Поведінка при піковому конфлікті | Ризик взаємних блокувань (Deadlocks) | Типовий сценарій застосування |
|---|---|---|---|---|---|
| **Песимістичне (2PL)** | `SELECT FOR UPDATE`, фізичні замки рядків | Висока (витрати на Lock Manager) | Стабільне упорядкування у чергу замків | Високий (вимагає строгого сортування ключів) | Банківські перекази, резервування квитків на концерт, короткі локальні транзакції |
| **Оптимістичне (OCC)** | `WHERE version = @v`, CAS у СУБД | Мінімальна (нульові накладні замки) | Колапс продуктивності (лавина Retry) | Відсутній (блокування не утримуються під час читання) | Веб-форми, CMS, електронна комерція, безстатусні API, довготривалі бізнес-транзакції |
| **Багатоверсійне (MVCC)** | Знімки стану, `xmin`/`xmax`, Undo Log | Мінімальна (читачі не блокують письменників) | Конфлікти серіалізації при паралельних записах | Низький для читачів, середній для письменників | Аналітичні звіти паралельно з операційним навантаженням OLTP |
| **Послідовна черга (Serial Execution)** | Однопотоковий Event Loop (Redis, LMAX) | Ультранизька (нуль синхронізації між ядрами) | Пропускна здатність обмежена швидкістю одного ядра | Повністю відсутній | Торгові біржові платформи (Matching Engines), In-Memory лічильники |

### Практична реалізація: SQL DDL, CAS-запити та обробка у коді

Розглянемо практичний приклад реалізації оптимістичного блокування для системи інвентаризації складських залишків.

#### 1. Структура таблиці (DDL)
```sql
CREATE TABLE warehouse_inventory (
    sku VARCHAR(64) PRIMARY KEY,
    item_name VARCHAR(255) NOT NULL,
    available_stock INT NOT NULL CHECK (available_stock >= 0),
    reserved_stock INT NOT NULL DEFAULT 0,
    lock_version BIGINT NOT NULL DEFAULT 1,
    last_updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Початкові дані
INSERT INTO warehouse_inventory (sku, item_name, available_stock, reserved_stock, lock_version)
VALUES ('CPU-RYZEN-9', 'AMD Ryzen 9 7950X', 15, 0, 1);
```

#### 2. SQL-шаблон безпечного резервування товару (CAS UPDATE)
```sql
-- Крок 1: Читання поточного стану без блокувань
SELECT sku, available_stock, reserved_stock, lock_version
FROM warehouse_inventory
WHERE sku = 'CPU-RYZEN-9';
-- Отримано: available_stock = 15, reserved_stock = 0, lock_version = 1

-- Крок 2: Бізнес-перевірка в пам'яті: 15 >= 2 (потрібно зарезервувати 2 шт.)

-- Крок 3: Атомарна фіксація з предикатом версії
UPDATE warehouse_inventory
SET available_stock = available_stock - 2,
    reserved_stock = reserved_stock + 2,
    lock_version = lock_version + 1,
    last_updated_at = CURRENT_TIMESTAMP
WHERE sku = 'CPU-RYZEN-9'
  AND lock_version = 1;
```

Нижче наведено фрагмент коду, що демонструє роботу з абстрактним драйвером реляційної СУБД та перевірку `affected_rows`:

```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

/* Результат виконання SQL-команди */
typedef struct {
    int64_t affected_rows;
    bool has_error;
    char error_msg[128];
} SqlExecResult;

/* Структура складського запису */
typedef struct {
    char sku[64];
    int32_t available_stock;
    int32_t reserved_stock;
    uint64_t lock_version;
} InventoryItem;

/* Імітація виклику інтерфейсу бази даних */
SqlExecResult execute_inventory_update(const char *sku, int32_t qty, uint64_t expected_version);
bool fetch_inventory_item(const char *sku, InventoryItem *out_item);

/* Функція резервування товару з оптимістичною перевіркою */
bool reserve_stock_optimistic(const char *sku, int32_t reserve_qty) {
    InventoryItem item;
    
    // 1. Читання стану без блокування СУБД
    if (!fetch_inventory_item(sku, &item)) {
        fprintf(stderr, "Помилка: товар %s не знайдено\n", sku);
        return false;
    }

    // 2. Перевірка бізнес-інваріанту в пам'яті
    if (item.available_stock < reserve_qty) {
        fprintf(stderr, "Брак залишків: доступно %d, запитано %d\n", 
                item.available_stock, reserve_qty);
        return false;
    }

    // 3. Атомарна спроба CAS-модифікації
    SqlExecResult res = execute_inventory_update(sku, reserve_qty, item.lock_version);
    
    if (res.has_error) {
        fprintf(stderr, "Системна помилка СУБД: %s\n", res.error_msg);
        return false;
    }

    // 4. Перевірка кількості змінених рядків
    if (res.affected_rows == 0) {
        // Колізія: рядок було змінено паралельною транзакцією
        fprintf(stderr, "Колізія версії для SKU %s (очікувалась версія %lu)\n", 
                sku, item.lock_version);
        return false; // Сигнал для запуску повторної спроби (Retry)
    }

    printf("Успішно зарезервовано %d шт. для товару %s\n", reserve_qty, sku);
    return true;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <cstdint>
#include <expected>

struct InventoryItem {
    std::string sku;
    int32_t available_stock{0};
    int32_t reserved_stock{0};
    uint64_t lock_version{0};
};

enum class ReservationError {
    ItemNotFound,
    InsufficientStock,
    VersionConflict,
    DatabaseFailure
};

class InventoryRepository {
public:
    virtual ~InventoryRepository() = default;
    [[nodiscard]] virtual std::expected<InventoryItem, ReservationError> get_by_sku(std::string_view sku) const = 0;
    [[nodiscard]] virtual std::expected<int64_t, ReservationError> execute_cas_reserve(
        std::string_view sku, int32_t qty, uint64_t expected_version) = 0;
};

class StockService {
public:
    explicit StockService(InventoryRepository& repo) : repo_(repo) {}

    [[nodiscard]] std::expected<void, ReservationError> reserve_stock(std::string_view sku, int32_t qty) {
        // 1. Читання стану сутності без блокувань
        auto item_res = repo_.get_by_sku(sku);
        if (!item_res) {
            return std::unexpected(item_res.error());
        }

        const auto& item = *item_res;

        // 2. Валідація бізнес-правил у пам'яті
        if (item.available_stock < qty) {
            return std::unexpected(ReservationError::InsufficientStock);
        }

        // 3. Атомарне CAS-оновлення
        auto rows_res = repo_.execute_cas_reserve(sku, qty, item.lock_version);
        if (!rows_res) {
            return std::unexpected(rows_res.error());
        }

        // 4. Перевірка колізії конкурентного доступу
        if (*rows_res == 0) {
            return std::unexpected(ReservationError::VersionConflict);
        }

        return {};
    }

private:
    InventoryRepository& repo_;
};
```
