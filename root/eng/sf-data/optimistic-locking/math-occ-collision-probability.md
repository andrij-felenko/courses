# 🧮 Математична модель колізій OCC та пропускної здатності системи

Ефективність оптимістичного керування конкурентним доступом базується на припущенні, що ймовірність паралельного оновлення одного й того самого запису є низькою. Якщо це припущення справджується, OCC забезпечує мінімальну затримку та максимальну пропускну здатність завдяки повній відсутності накладних витрат на захоплення та координацію замків.

Проте при зростанні конкуренції за записи система зазнає нелінійного падіння продуктивності через лавину повторних спроб і марну витрату обчислювальних ресурсів на транзакції, які будуть відхилені.

Нижче наведено строге математичне виведення ймовірності колізії, залежності пропускної здатності від навантаження та точки фазового переходу (колапсу пропускної здатності).

---

### 1. Ймовірність колізії за рівномірного розподілу доступу

Нехай база даних містить `M` незалежних записів (кортежів), а до системи надходить потік транзакцій із середньою інтенсивністю `λ` транзакцій на секунду. Кожна транзакція зчитує один випадковий запис, виконує обчислення в пам'яті застосунку протягом часу `t_tx` (тривалість фази читання та бізнес-логіки) і намагається виконати атомарне CAS-оновлення.

Середня кількість транзакцій, які одночасно перебувають у системі у стані обчислень, за законом Літтла становить:

```
N = λ · t_tx
```

Коли деяка транзакція `T_0` завершує свої обчислення у момент часу `t` і намагається зафіксувати результат, вона зазнає колізії тоді і тільки тоді, коли хоча б одна інша транзакція успішно зафіксувала зміну *того самого* запису за інтервал `[t - t_tx, t]`.

Нехай за інтервал `t_tx` у системі успішно зафіксувалося `k` транзакцій запису. Якщо розподіл звернень до `M` записів є рівномірним, ймовірність того, що конкретна транзакція оновила саме наш цільовий запис, дорівнює `1 / M`. Відповідно, ймовірність того, що вона оновила інший запис, дорівнює `1 - 1 / M`.

Ймовірність відсутності колізії для транзакції `T_0` при `k` зафіксованих паралельних транзакціях:

```
P_success(k)
= (1 - 1 / M)^k                               [незалежність вибору записів]
≈ e^(-k / M)                                   [експоненційне наближення при M >> 1]
```

Якщо надходження транзакцій підпорядковується пуассонівському процесу з параметром `k = λ · t_tx`, загальна ймовірність виникнення колізії (ймовірність відхилення транзакції `P_conflict`) набуває вигляду:

```
P_conflict
= 1 - P_success                                [протилежна подія до успішної фіксації]
= 1 - e^(-(λ · t_tx) / M)                      [підстановка експоненційного наближення P_success]
```

Застосовуючи розклад функції `e^(-x)` у ряд Тейлора для малих значень аргументу `(λ · t_tx) / M << 1`:

```
P_conflict
= 1 - (1 - (λ · t_tx) / M + ((λ · t_tx) / M)² / 2 - ...)   [розклад Тейлора для експоненти]
≈ (λ · t_tx) / M                                           [лінійне наближення першого порядку]
```

Звідси випливає фундаментальний інженерний висновок: **ймовірність колізії прямо пропорційна інтенсивності навантаження `λ` та часу обчислень `t_tx`, і обернено пропорційна розміру простору даних `M`**.

### 2. Ймовірність колізії при нерівномірному доступі (розподіл Ципфа / Скев)

У реальних системах доступ до даних ніколи не є рівномірним: 80% усіх запитів зазвичай звертаються до 20% найпопулярніших записів (правило Парето або степеневий розподіл Ципфа).

Нехай доступ до записів визначається розподілом Ципфа з параметром форми `s > 0`. Ймовірність звернення до `i`-го за популярністю запису (`i ∈ [1, M]`) становить:

```
p_i = (1 / i^s) / (∑_{j=1}^M (1 / j^s))
```

Ймовірність колізії для транзакції, яка звертається до конкретного запису `i`:

```
P_conflict(i) = 1 - (1 - p_i)^(λ · t_tx) ≈ 1 - e^(-λ · t_tx · p_i)
```

Усереднена по всій системі ймовірність колізії дорівнює математичному сподіванню по всіх записах:

```
P_conflict_total
= ∑_{i=1}^M p_i · P_conflict(i)                [математичне сподівання по простору ключів]
≈ ∑_{i=1}^M p_i · (1 - e^(-λ · t_tx · p_i))    [підстановка формули колізії для i-го ключа]
```

Для самого «гарячого» запису системи (`i = 1`), частка звернень до якого становить `p_1`:
* Якщо `p_1 = 0.05` (5% усіх транзакцій оновлюють один спільний лічильник),
* `λ = 200` транзакцій/с,
* `t_tx = 0.05` с (50 мс),

тоді ймовірність колізії на цьому записі:

```
P_conflict(1)
= 1 - e^(-200 · 0.05 · 0.05)                   [підстановка числових параметрів]
= 1 - e^(-0.5)                                 [перемноження степеня: 200 · 0.05 · 0.05 = 0.5]
= 1 - 0.6065                                   [обчислення експоненти e^(-0.5)]
= 0.3935                                       [39.35% спроб завершаться провалом]
```

Один гарячий ключ створює локальний затор, який руйнує масштабованість усієї системи.

### 3. Ефективна пропускна здатність та лавина повторів (Retry Multiplier)

Нехай кожна транзакція, що зазнала колізії, виконує повторну спробу (Retry) до моменту успішної фіксації.

Позначимо через `P = P_conflict` ймовірність невдачі на кожній окремій спробі. Середня кількість спроб `E[K]`, необхідна для успішної фіксації однієї бізнес-операції, є сумою геометричної прогресії:

```
E[K]
= 1 · (1 - P) + 2 · P · (1 - P) + 3 · P² · (1 - P) + ...  [зважена сума номерів спроб]
= (1 - P) · ∑_{j=1}^∞ j · P^(j-1)                          [винесення множника (1 - P)]
= (1 - P) · (1 / (1 - P)²)                                 [сума похідної геометричного ряду]
= 1 / (1 - P)                                              [коефіцієнт помноження навантаження]
```

Величину `M_retry = 1 / (1 - P)` називають **множником повторних спроб (Retry Multiplier)**.

Якщо зовнішній вхідний потік становить `λ_in` бізнес-операцій на секунду, то сумарна кількість спроб транзакцій `λ_total`, яку фактично змушена обробляти база даних, становить:

```
λ_total
= λ_in · M_retry                               [множення на середню кількість спроб]
= λ_in / (1 - P)                               [підстановка формули множника повторів]
```

### 4. Точка біфуркації та колапс пропускної здатності

Нехай база даних має максимальну апаратну продуктивність `μ` транзакцій на секунду (максимальна пропускна здатність процесора, пам'яті та дискової підсистеми WAL).

Умовою стабільності системи є те, що сумарне навантаження не перевищує пікову ємність:

```
λ_total < μ
```

Підставляючи вираз для `λ_total`:

```
λ_in / (1 - P(λ_total)) < μ
```

Оскільки сама ймовірність колізії `P` залежить від сумарного внутрішнього навантаження `λ_total`:

```
P(λ_total) ≈ (λ_total · t_tx) / M
```

Отримуємо квадратне рівняння відносно `λ_total`:

```
λ_total · (1 - (λ_total · t_tx) / M) = λ_in
λ_total - (t_tx / M) · λ_total² - λ_in = 0
(t_tx / M) · λ_total² - λ_total + λ_in = 0
```

Дискримінант цього квадратного рівняння:

```
D = (-1)² - 4 · (t_tx / M) · λ_in = 1 - (4 · t_tx · λ_in) / M
```

Дійсні корені існують лише за умови `D ≥ 0`. Звідси отримуємо **критичну межу вхідного навантаження (Critical Load Threshold)**, перевищення якої призводить до незворотного колапсу:

```
λ_max = M / (4 · t_tx)
```

При досягненні `λ_in = λ_max`:
1. Ймовірність колізії сягає критичного значення `P_crit = 0.5` (50%).
2. Множник повторів сягає `M_retry = 2.0`.
3. Будь-яке найменше додаткове збільшення вхідного потоку спричиняє лавиноподібне зростання `λ_total → ∞`, черги переповнюються, затримка прямує до нескінченності, а корисна пропускна здатність системи спадає майже до нуля.

```
Ефективна пропускна здатність T_eff(λ_in):

  T_eff ^
        |            /---------\
  λ_max |           /           \   <-- Обвал через лавину повторів
        |          /             \      (Retry Storm Collapse)
        |         /               \
        |        /                 \
        |       /                   \
        +-----------------------------------> λ_in
                0.5 · λ_max   λ_max
```

### Практичні висновки математичної моделі

1. **Зменшення `t_tx`**: Найефективніший спосіб підвищити поріг стійкості OCC — мінімізувати час утримання версії в пам'яті. Довгі обчислення, виклики зовнішніх HTTP-сервісів або очікування введення користувача всередині транзакційного циклу неприпустимі.
2. **Партиціювання гарячих ключів**: Збільшення ефективного простору `M` (наприклад, розбиття одного балансу на 10 паралельних слотів-лічильників) пропорційно піднімає стелю `λ_max`.
3. **Межа застосування**: Якщо розрахункова ймовірність колізії для конкретної таблиці перевищує 15–20%, система наближається до критичної зони: на таких ділянках необхідно переходити на песимістичне блокування чергою або безблокувальні черги повідомлень (LMAX Disruptor / Serial Queue).
