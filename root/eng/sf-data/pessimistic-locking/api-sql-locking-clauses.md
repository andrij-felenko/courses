# 📋 Специфікація операторів блокування SQL та системні параметри керування замками

Реляційні системи керування базами даних надають прикладним розробникам набір явних конструкцій для керування гранулярними рядковими замками безпосередньо в операторах вибірки `SELECT`. Коректне використання цих модифікаторів дає змогу вибирати між блокуючим очікуванням, миттєвим аварійним виходом і пропуском зайнятих рядків для черг обробки.

## 1. Специфікація синтаксису та граматики операторів блокування

У стандарті SQL та діалектах провідних реляційних рушіїв (PostgreSQL, MySQL InnoDB, Oracle Database) пропозиція блокування додається в кінці запиту вибірки `SELECT`. Вона вказує планувальнику запитів та менеджеру блокувань ядра СУБД, що для кожного відібраного кортежу необхідно отримати відповідний рівень блокування ще до передачі рядка на клієнтський рівень.

```sql
SELECT select_list
FROM table_expression
[ WHERE condition ]
[ ORDER BY order_expression ]
[ LIMIT count ]
FOR { UPDATE | NO KEY UPDATE | SHARE | KEY SHARE } [ OF table_name [, ...] ] [ NOWAIT | SKIP LOCKED ];
```

Опціональна пропозиція `OF table_name` дозволяє явно вказати, які саме таблиці у складному запиті з об'єднаннями (`JOIN`) підлягають блокуванню. Якщо конструкція `OF` відсутня, рушій накладає замки на рядки абсолютно всіх таблиць, перелічених у секції `FROM`. Якщо ж вказано `FOR UPDATE OF t1`, то рядки таблиці `t1` блокуються монопольно, тоді як приєднані дані з таблиці `t2` зчитуються у звичайному неблокуючому режимі через версійний знімок MVCC.

### Режими блокування рядків та їхнє призначення

Різні типи операцій вимагають різного ступеня монопольного контролю. Сучасні реляційні ядра підтримують чотири дискретні рівні рядкових замків:

1. **FOR UPDATE (Ексклюзивний замок кортежа):** Найпотужніший режим монопольного володіння. Використовується, коли транзакція планує виконати повну модифікацію (`UPDATE`) або фізичне видалення (`DELETE`) рядка. Цей режим блокує будь-які паралельні спроби модифікації або блокуючого читання цього самого кортежу іншими сесіями. Звичайні неблокуючі `SELECT` без блокуючих пропозицій продовжують читати старий знімок кортежу без жодних перешкод.
2. **FOR NO KEY UPDATE (Монопольне блокування без зміни ключів):** Спеціалізований режим PostgreSQL, оптимізований для оновлення атрибутів, які не входять до складу первинних ключів (`PRIMARY KEY`) та унікальних індексів (`UNIQUE INDEX`). Цей режим захищає рядок від паралельних змін, але дозволяє іншим транзакціям одночасно накладати слабкі замки `FOR KEY SHARE`.
3. **FOR SHARE (Спільне блокування читання):** Режим спільного володіння (Shared Lock). Захищає зчитаний рядок від будь-яких модифікацій чи видалень з боку інших процесів, одночасно дозволяючи іншим транзакціям вільно накладати такі самі замки `FOR SHARE` та читати актуальний стан кортежа.
4. **FOR KEY SHARE (Спільне блокування первинного ключа):** Найслабший спільний замок, призначений для гарантування цілісності зовнішніх ключів (`FOREIGN KEY`). Коли транзакція створює запис у дочірній таблиці, рушій автоматично бере `FOR KEY SHARE` на батьківський рядок, що гарантує: батьківський рядок не буде видалено і його первинний ключ не зміниться, доки триває транзакція вставки.

| Режим блокування | Опис та призначення | Дозволені конкурентні операції | Заблоковані конкурентні операції |
|---|---|---|---|
| `FOR UPDATE` | Найсильніший монопольний замок (Exclusive). Отримується перед `UPDATE` або `DELETE` будь-яких стовпців. | Звичайний `SELECT` (через знімки MVCC). | Усі інші блокуючі читання (`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`), а також операції `UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`. |
| `FOR NO KEY UPDATE` (PostgreSQL) | Замок модифікації без зміни унікальних ключів. Блокує зміну рядка, але не чіпає стовпці унікальних індексів і первинних ключів. | Звичайний `SELECT`, а також конкурентний `FOR KEY SHARE` (наприклад, перевірка зовнішніх ключів з інших таблиць). | `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, а також будь-які операції `UPDATE` і `DELETE`. |
| `FOR SHARE` | Спільний замок читання (Shared). Захищає рядок від модифікації чи видалення іншими транзакціями, дозволяючи спільне читання. | Звичайний `SELECT`, конкурентні `FOR SHARE`, `FOR KEY SHARE`. | Конкурентні `FOR UPDATE`, `FOR NO KEY UPDATE`, прямі операції `UPDATE`, `DELETE`. |
| `FOR KEY SHARE` (PostgreSQL) | Найслабший спільний замок для підтримки цілісності зовнішніх ключів (`FOREIGN KEY`). | Звичайний `SELECT`, `FOR SHARE`, `FOR KEY SHARE`, а також `FOR NO KEY UPDATE`. | Конкурентний `FOR UPDATE`, прямі операції `DELETE` та `UPDATE` стовпців первинного/унікального ключа. |

## 2. Модифікатори конкурентної реакції: NOWAIT та SKIP LOCKED

Коли запит вибірки намагається отримати замок на рядок, який уже заблокований паралельною нефіксованою транзакцією, виникає стан конфлікту. Поведінка рушія у цій точці визначається модифікатором черги:

1. **Блокуюче очікування (За замовчуванням):** Запит призупиняє виконання поточного клієнтського потоку. Потік засинає на семафорі менеджера блокувань і чекає, поки блокуюча транзакція виконає `COMMIT` або `ROLLBACK`. Якщо встановлено сесійний параметр `lock_timeout`, очікування триває до вичерпання ліміту, після чого запит аварійно переривається.
2. **NOWAIT (Миттєва відмова):** Запит категорично відмовляється чекати. Якщо хоча б один рядок із результуючої вибірки заблоковано, СУБД негайно повертає клієнту помилку SQLSTATE `55P03` (`lock_not_available`) у PostgreSQL або Error `3572` у MySQL. Це дозволяє веб-серверам не блокувати робочі пули потоків і миттєво повертати клієнту повідомлення «Ресурс зайнятий іншим користувачем».
3. **SKIP LOCKED (Неблокуючий пропуск):** Революційний модифікатор для паралельних архітектур. Рушій бази даних послідовно перевіряє рядки за індексом: якщо кортеж вільний, він блокується і додається до відповіді; якщо кортеж утримується іншою сесією, рушій **ігнорує його і переходить до наступного запису**. Завдяки цьому запит повертає лише вільні рядки з нульовою затримкою.

| Модифікатор | Поведінка рушія при зіткненні із зайнятим замком | Типовий сценарій використання |
|---|---|---|
| *(За замовчуванням)* | Транзакція переходить у стан очікування (блокується) до моменту завершення транзакції-власника (`COMMIT` або `ROLLBACK`) або до перевищення `lock_timeout`. | Фінансові транзакції, переказ коштів між рахунками, сувора послідовна консистентність. |
| `NOWAIT` | Запит не стає в чергу очікування, а негайно завершується помилкою (SQLSTATE `55P03` `lock_not_available` у PostgreSQL, Error `3572` у MySQL). | Інтерактивні інтерфейси користувача, де тривале зависання неприпустиме і краще одразу повідомити клієнта про зайнятість ресурсу. |
| `SKIP LOCKED` | Запит ігнорує будь-які рядки, які вже заблоковані іншими транзакціями, та повертає лише перші вільні записи, що відповідають умові `WHERE`. | Високонавантажені черги завдань (Task Queues), пул паралельних обробників повідомлень без взаємного блокування. |

## 3. Матриця сумісності режимів блокувань

Матриця сумісності визначає, чи може новий замок бути наданий транзакції, якщо на цьому кортежі вже існує активний замок іншої транзакції. Значення **OK** означає, що замок надається паралельно без очікування; значення **Конфлікт** означає, що другий процес змушений чекати або аварійно переривається.

| Утримуваний замок ↓ \ Запитуваний замок → | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
|---|---|---|---|---|
| **FOR KEY SHARE** | OK | OK | OK | Конфлікт |
| **FOR SHARE** | OK | OK | Конфлікт | Конфлікт |
| **FOR NO KEY UPDATE** | OK | Конфлікт | Конфлікт | Конфлікт |
| **FOR UPDATE** | Конфлікт | Конфлікт | Конфлікт | Конфлікт |

Зверніть увагу на симетрію та спеціальні властивості:
- Режим `FOR KEY SHARE` повністю сумісний із `FOR NO KEY UPDATE`. Це дозволяє паралельно перевіряти зовнішні ключі під час активного оновлення бізнес-полів (наприклад, балансу чи опису).
- Будь-який замок несумісний із монопольним `FOR UPDATE`.
- Два спільні замки `FOR SHARE` абсолютно сумісні між собою, що уможливлює паралельне блокуюче читання багатьма клієнтами одночасно.

## 4. Порівняння діалектів провідних СУБД

Різні виробники реляційних баз даних реалізують песимістичне блокування з відмінностями у ключових словах та механізмах:

| СУБД | Синтаксис монопольного блокування | Підтримка NOWAIT | Підтримка SKIP LOCKED | Особливості реалізації |
|---|---|---|---|---|
| **PostgreSQL** | `SELECT ... FOR UPDATE` / `FOR NO KEY UPDATE` | Так (`NOWAIT`) | Так (`SKIP LOCKED`) | Замки зберігаються в заголовках кортежів (`t_xmax`, `MultiXactId`). Немає ескалації блокувань. |
| **MySQL (InnoDB)** | `SELECT ... FOR UPDATE` | Так (з версії 8.0) | Так (з версії 8.0) | Блокує індексні записи та проміжки між ними (Next-Key Locks, Gap Locks). |
| **Oracle Database** | `SELECT ... FOR UPDATE` | Так (`NOWAIT`, `WAIT n`) | Так (`SKIP LOCKED`) | Замки маркуються в заголовках блоків (ITL — Interested Transaction List). |
| **Microsoft SQL Server** | `SELECT ... WITH (UPDLOCK, ROWLOCK)` / `WITH (XLOCK)` | Так (`WITH (NOWAIT)`) | Так (`WITH (READPAST)`) | Використовує табличні підказки (*Table Hints*). Застосовує ескалацію блокувань при вичерпанні пам'яті. |

## 5. Системні параметри конфігурації СУБД

Правильне налаштування системних тайм-аутів є головною лінією оборони від зависання пулів підключень та масових відмов веб-сервісів.

### PostgreSQL (файл `postgresql.conf` або сесійні змінні `SET`)

```sql
-- Максимальний час очікування будь-якого замка перед аварійним перериванням запиту (0 = нескінченно)
SET lock_timeout = '3s';

-- Максимальний час виконання будь-якого оператора SQL
SET statement_timeout = '10s';

-- Захист від завислих транзакцій: автоматичний розрив з'єднання, якщо транзакція відкрита без активних запитів
SET idle_in_transaction_session_timeout = '30s';

-- Час очікування перед першим запуском детектора взаємних блокувань (Deadlock Detector)
SET deadlock_timeout = '1s';
```

Параметр `idle_in_transaction_session_timeout` критично важливий для захисту від помилок додатків: якщо бекенд відкрив транзакцію, заблокував гарячий рядок через `SELECT ... FOR UPDATE`, а потім завис на зовнішньому HTTP-виклику, PostgreSQL примусово розірве TCP-з'єднання через 30 секунд, відкотить транзакцію і звільнить замок для інших процесів.

### MySQL InnoDB (файл `my.cnf` або параметри сесії)

```sql
-- Час очікування рядкового замка InnoDB у секундах перед викиданням помилки 1205 (Lock wait timeout exceeded)
SET innodb_lock_wait_timeout = 5;

-- Увімкнення/вимкнення внутрішнього графового детектора дедлоків (за замовчуванням ON)
SET GLOBAL innodb_deadlock_detect = ON;
```

## 6. Системні розрізи діагностики замків

### Діагностика блокувань у PostgreSQL

Для виявлення сесій, які утримують замки і блокують інші транзакції, адміністратори використовують системне представлення `pg_locks` разом із таблицею активності процесів `pg_stat_activity`:

```sql
-- Перегляд активних блокувань та заблокованих запитів
SELECT
    blocked_locks.pid     AS blocked_pid,
    blocked_activity.usename  AS blocked_user,
    blocking_locks.pid    AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query    AS blocked_statement,
    blocking_activity.query   AS current_statement_in_blocking_process,
    now() - blocked_activity.query_start AS waiting_duration
FROM  pg_catalog.pg_locks         blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks         blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

Для миттєвого знаходження ідентифікаторів процесів (PID), які безпосередньо блокують конкретну сесію, використовується вбудована функція PostgreSQL:

```sql
-- Отримати масив PID процесів, які блокують сесію з PID 12345
SELECT pg_blocking_pids(12345);
```

### Діагностика блокувань у MySQL 8.0+

У сучасних версіях MySQL моніторинг замків виконується через підсистему `performance_schema`:

```sql
-- Інформація про заблоковані транзакції та очікування у MySQL InnoDB
SELECT 
    r.trx_id waiting_trx_id,
    r.trx_mysql_thread_id waiting_thread,
    r.trx_query waiting_query,
    b.trx_id blocking_trx_id,
    b.trx_mysql_thread_id blocking_thread,
    b.trx_query blocking_query
FROM performance_schema.data_lock_waits w
JOIN information_schema.innodb_trx b 
    ON b.trx_id = w.blocking_engine_transaction_id
JOIN information_schema.innodb_trx r 
    ON r.trx_id = w.requesting_engine_transaction_id;
```

## 7. Стандартизовані коди помилок та винятків (SQLSTATE)

Коли клієнтська програма виконує запити з песимістичним блокуванням, прикладний код повинен перехоплювати стандартизовані коди помилок SQLSTATE і реалізовувати відповідну логіку повтору або повідомлення:

| СУБД | Код помилки | SQLSTATE | Символічна назва | Причина виникнення |
|---|---|---|---|---|
| PostgreSQL | `55P03` | `55P03` | `lock_not_available` | Спроба отримати замок за допомогою `NOWAIT`, коли ресурс вже утримується іншою транзакцією. |
| PostgreSQL | `40P01` | `40P01` | `deadlock_detected` | Виявлено взаємне блокування транзакцій; рушій примусово відкотив поточну транзакцію як жертву. |
| PostgreSQL | `57014` | `57014` | `query_canceled` | Перевищено `lock_timeout` або `statement_timeout`. |
| MySQL | `1205` | `HY000` | `ER_LOCK_WAIT_TIMEOUT` | Перевищено системний ліміт очікування замка (`innodb_lock_wait_timeout`). |
| MySQL | `1213` | `40001` | `ER_LOCK_DEADLOCK` | Виявлено взаємне блокування під час виконання транзакції InnoDB. |
| MySQL | `3572` | `HY000` | `ER_LOCK_NOWAIT` | Запит `NOWAIT` зіткнувся із заблокованим рядком. |
