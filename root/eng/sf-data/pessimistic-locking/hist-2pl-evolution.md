# 📜 Еволюція двофазного блокування: від предикатних замків System R до рядкових MultiXact

На світанку розвитку реляційних систем керування базами даних у середині 1970-х років паралельна обробка запитів була суто теоретичною дисципліною. Інженери Дослідницького центру IBM у Сан-Хосе (IBM San Jose Research Laboratory), працюючи над прототипом експериментальної СУБД System R, зіткнулися з фундаментальною проблемою: як дозволити десяткам програм одночасно змінювати таблиці на дискових накопичувачах так, щоб результат завжди збігався з послідовним виконанням транзакцій, не руйнуючи цілісність зв'язків.

```
1976: Есваран, Ґрей, Лорі, Трейґер ──► Формалізація протоколу 2PL (Growing / Shrinking)
  │
1977: Джим Ґрей (IBM System R)    ──► Введення ієрархії гранулярності та замків наміру (IS, IX, SIX)
  │
1981: Предикатні замки (Predicate)──► Спроба блокувати логічні умови (висока обчислювальна складність)
  │
1990: Рядкові замки та блокування ──► Перехід до інтервальних замків (Next-Key / Gap Locking в InnoDB)
      інтервалів індексів
  │
2000+: Замки у заголовках кортежів ──► PostgreSQL: MultiXactId замість таблиці замків у пам'яті
```

## Теорема 1976 року та відкриття Джима Ґрея

У 1976 році четверо дослідників IBM — Капу Есваран (*Kapali Eswaran*), Джим Ґрей (*Jim Gray*), Реймонд Лорі (*Raymond Lorie*) та Ірвінг Трейґер (*Irving Traiger*) — опублікували епохальну статтю *«The Notions of Consistency and Predicate Locks in a Database System»*. У цій роботі вони вперше математично довели фундаментальну теорему: **якщо всі транзакції дотримуються протоколу двофазного блокування (Two-Phase Locking, 2PL), результуючий розклад виконання гарантовано є конфліктно-серіалізовним**.

Початковий протокол складався з двох суворих фаз:
1. **Фаза росту (Growing Phase):** транзакція може захоплювати будь-які необхідні замки (на читання чи запис), але не має права звільнити жодного.
2. **Фаза спадання (Shrinking Phase):** транзакція може поступово звільняти утримувані замки, але більше не може отримати жодного нового замка.

Проте перший же практичний запуск 2PL у системі System R виявив тяжку ваду класичного протоколу — проблему **каскадних відкатів (Cascading Aborts)**. Якщо транзакція `T1` змінювала рядок, потім відпускала замок у фазі спадання, транзакція `T2` зчитувала новий стан і починала власні обчислення, а після цього транзакція `T1` зазнавала аварійного збою і виконувала `ROLLBACK`, транзакцію `T2` доводилося теж примусово відкочувати. Якщо від результатів `T2` залежали транзакції `T3` і `T4`, виникала руйнівна ланцюгова реакція, яка паралізувала роботу ядра СУБД.

Щоб назавжди усунути каскадні відкати, Джим Ґрей модифікував протокол, створивши **суворе двофазне блокування (Strict 2PL)**, у якому всі ексклюзивні замки (X-locks) утримуються аж до моменту фіксації (`COMMIT`) або повного відкату (`ROLLBACK`). Пізніше з'явилася ще жорсткіша форма — **Rigorous 2PL**, де до кінця транзакції утримуються абсолютно всі замки, включно зі спільними замками читання (S-locks). Саме Strict 2PL та Rigorous 2PL стали промисловим фундаментом реляційного світу.

## Проблема фантомів та крах предикатних замків

Коли інженери System R спробували гарантувати повну серіалізовність для операцій вибірки за діапазоном значень (наприклад, `WHERE age > 30`), вони натрапили на феномен фантомного читання: блокування наявних рядків не заважало іншій транзакції вставити абсолютно новий рядок, який задовольняв ту саму умову.

Першою відповіддю дослідників стали **предикатні замки (Predicate Locks)**. Ідея полягала в тому, щоб блокувати не фізичні адреси записів на диску, а сам математичний вираз предиката (логічну умову запиту). Якщо транзакція виконувала вибірку `WHERE salary BETWEEN 5000 AND 10000`, рушій СУБД мав перевіряти кожен наступний `INSERT` у системі на перетин із зареєстрованими предикатами.

На практиці предикатні замки зазнали фіаско. Задача перевірки довільних логічних виразів на взаємний перетин вимагала зіставлення складних дерев предикатів (з логічними операторами `AND`, `OR`, `NOT`, регулярними виразами та функціями), що зводилося до алгоритмічно важкої задачі задовольняння булевих формул (SAT-problem). Навантаження на процесор під час кожної вставки зростало пропорційно кількості відкритих транзакцій, перетворюючи менеджер блокувань на катастрофічне вузьке горло.

## Компроміс 1990-х: блокування інтервалів (Next-Key Locks)

Вихід із глухого кута запропонував у 1990 році Курт Моган (*C. Mohan*) у дослідницькому центрі IBM Almaden, розробивши алгоритм **ARIES/KVL** (Key-Value Locking), який згодом еволюціонував у механізм **інтервальних замків (Gap Locks та Next-Key Locks)** у структурах B-дерев.

Замість обчислення абстрактних предикатів рушій бази даних почав використовувати фізичний порядок ключів у B-дереві:
- **Record Lock:** блокує конкретний індексний запис.
- **Gap Lock:** блокує інтервал (проміжок) між двома сусідніми індексними записами, запобігаючи вставці нових ключів у цей діапазон.
- **Next-Key Lock:** об'єднує блокування самого запису та інтервалу перед ним.

Цей елегантний перехід від довільної математики до фізичного індексного простору дозволив рушіям на зразок MySQL InnoDB забезпечувати рівень ізоляції `Repeatable Read` без фантомів за константний час `O(log N)`.

## Революція PostgreSQL: перенесення замків у кортежі (MultiXact)

Традиційні реляційні СУБД (IBM DB2, Microsoft SQL Server, Oracle) зберігали всі інформаційні структури блокувань у спеціально виділеному сегменті оперативної пам'яті — таблиці блокувань (Lock Table). Коли транзакція змінювала мільйони рядків, пам'ять під замки вичерпувалася, і рушій був змушений застосовувати **ескалацію блокувань (Lock Escalation)**: скидати мільйон дрібних рядкових замків і накладати один монопольний замок на всю таблицю, раптово блокуючи роботу всіх суміжних підсистем.

Розробники PostgreSQL під керівництвом Брюса Момджана (*Bruce Momjian*) та Вадима Міхеєва пішли радикально іншим шляхом, інтегрувавши песимістичне блокування безпосередньо у формат сторінки зберігання кортежів (Heap Tuples):

```
+───────────────────────────────────────────────────────────────────────────+
|                       ЗАГОЛОВОК КОРТЕЖА POSTGRESQL (HeapTupleHeaderData)  |
|                                                                           |
|   [ t_xmin: 32 bit ]   [ t_xmax: 32 bit ]   [ t_infomask: 16 bit ]        |
|     ID транзакції        ID блокуючої         Бітові прапорці режимів     |
|      створення           транзакції / Multi   (HEAP_XMAX_LOCK_ONLY тощо)  |
+───────────────────────────────────────────────────────────────────────────+
```

Коли клієнт виконує `SELECT ... FOR UPDATE`, PostgreSQL не створює об'єкт замка в оперативній пам'яті менеджера блокувань. Натомість рушій записує ідентифікатор поточної транзакції безпосередньо в поле `t_xmax` заголовка рядка на диску і встановлює відповідні прапорці в масці `t_infomask`. 

Якщо на один і той самий рядок накладається кілька спільних замків читання (`FOR SHARE`), PostgreSQL створює **MultiXactId** — мультиплікативний ідентифікатор транзакцій, масив якого зберігається у підкаталозі `pg_multixact/`. Завдяки цьому PostgreSQL принципово не знає проблем із браком оперативної пам'яті на рядкові замки і ніколи не виконує ескалацію до рівня таблиці, зберігаючи стабільний паралелізм за будь-якого обсягу транзакцій.
