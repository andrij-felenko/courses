# 🧮 Математична модель узгодженості, лінеаризованості та затримки потоків CDC

Захоплення змінних даних (CDC) є математичним відображенням внутрішнього дискретного стану транзакційної бази даних у розподілений неперервний потік подій. Для гарантування того, що зовнішні споживачі (пошукові індекси, кеші, аналітичні сховища) отримують точну й несуперечливу копію первинних даних, система CDC повинна забезпечувати суворі формальні гарантії порядку, лінеаризованості та ідемпотентності.

Нижче наведено формальну алгебраїчну модель функціонування логічного CDC-конвеєра, доведення збереження причинно-наслідкового порядку, теорему узгодженості зовнішніх ключів та математичний розрахунок динаміки затримки реплікації.

---

### Формалізація транзакційного стану та журналу

Нехай простір можливих станів реляційної бази даних позначається як `Σ`. 

Початковий стан системи у момент часу `t = 0` позначається як `σ₀ ∈ Σ`.

Будь-яка зафіксована транзакція `tx` є функцією переходу стану `δ: Σ × TX → Σ`. Послідовне виконання множини з `n` транзакцій породжує детерміністичний ланцюг станів:

```
σₙ = δ(δ(...δ(δ(σ₀, tx₁), tx₂)...), txₙ)
```

Транзакційний журнал попереднього запису (WAL) встановлює строгий повний порядок (Strict Total Order) на множині всіх зафіксованих операцій:

```
(TX, ≺_LSN)
```

де відношення `tx_a ≺_LSN tx_b` виконується тоді й лише тоді, коли монотонний числовий номер фіксації першої транзакції менший за номер другої:

```
CommitLSN(tx_a) < CommitLSN(tx_b)
```

### Відображення мутацій у потік подій та лінеаризованість за ключем

Процес логічного декодування є гомоморфним відображенням `Φ`, яке транслює кожну транзакцію `tx` у впорядкований кортеж елементарних атомарних подій мутації рядків:

```
Φ(tx) = ⟨e₁, e₂, ..., e_m⟩
```

Кожна елементарна подія `e` описується кортежем:

```
e = (k, v, op, LSN, CommitLSN)
```

де `k ∈ K` — первинний ключ сутності, `v ∈ V` — стан даних (значення стовпців), `op ∈ {INSERT, UPDATE, DELETE}` — тип операції.

#### Теорема про лінеаризованість за ключем партиціонування
Якщо розподілений брокер подій (наприклад, Apache Kafka) використовує детерміністичну функцію партиціонування `h: K → {0, 1, ..., P - 1}` за первинним ключем `k`:

```
partition(e) = h(k) mod P
```

тоді для будь-яких двох послідовних мутацій `e_i` та `e_j` над одним і тим самим ключем `k` (`k_i = k_j = k`), де `e_i ≺_LSN e_j`, гарантується збереження порядку в черзі партиції:

```
offset(e_i) < offset(e_j)
```

#### Доведення:
1. Оскільки `k_i = k_j`, значення функції хешування збігаються: `h(k_i) = h(k_j)`.
2. Відповідно, обидві події потрапляють в одну й ту саму партицію `p = h(k) mod P`.
3. Рушій CDC є однопотоковим екстрактором для окремого слота реплікації та публікує події в брокер строго монотонно за зростанням `LSN`.
4. Брокер призначає послідовні монотонні зміщення `offset` всередині однієї партиції.
5. Отже, відношення `e_i ≺_LSN e_j` строго тягне за собою `offset(e_i) < offset(e_j)`, що й доводить лінеаризованість (Linearizability) послідовності станів для кожного окремого об'єкта `k`.

### Причинно-наслідкова узгодженість між таблицями (Causal Consistency)

Якщо транзакція `tx` модифікує одночасно дві зв'язані таблиці (наприклад, створює замовлення `Order #101` та додає позицію `OrderItem #501`), у транзакційному журналі події мають однаковий `CommitLSN`.

Проте, якщо події потрапляють у різні топіки або різні партиції Kafka:
* `partition(Order #101) = p_A`
* `partition(OrderItem #501) = p_B`

Споживач партиції `p_B` може вичитати позицію замовлення раніше, ніж споживач партиції `p_A` вичитає саме замовлення. Це породжує стан тимчасового порушення реляційної цілісності на стороні споживача.

#### Теорема про збереження глобального порядку:
Повна транзакційна причинно-наслідкова узгодженість (Transactional Causal Consistency) між довільними сутностями зберігається тоді й лише тоді, коли:
1. Або всі події спрямовуються в **єдину глобальну партицію** (`P = 1`), що обмежує пропускну здатність системи швидкодією одного вузла брокера.
2. Або споживач виконує потокове з'єднання (Stream-Table Join) з буферизацією за `CommitLSN` чи використовує патерн **Transactional Outbox**, де весь агрегат цілком серіалізується в один рядок із єдиним ключем партиціонування.

### Алгебра згортки та ідемпотентність відновлення стану

Стан матеріалізованого подання `S(t)` на стороні зовнішнього споживача є результатом лівої згортки (Fold) потоку подій `E_t = ⟨e₁, e₂, ..., e_N⟩`:

```
S(t) = foldl(apply, S₀, E_t)
```

У реальних розподілених мережах через аварійні перезапуски виникає семантика доставки «щонайменше один раз» (at-least-once), за якої споживач отримує потік `E' = E ∪ D`, де `D` — підмножина повторно надісланих подій-дублікатів.

Щоб гарантувати збіжність `S(E') = S(E)`, оператор застосування мутації `apply(S, e)` визначається як умовний селектор із захистом за монотонним номером версії (Version / LSN Guard):

```
apply(S, e) = 
  якщо e.LSN > S[e.k].LSN:
      S ∪ { e.k ↦ (e.v, e.LSN) }
  інакше:
      S
```

#### Доведення ідемпотентності:
Розглянемо повторне застосування довільної події `e_dup = (k, v, LSN_dup)` до стану `S`, у якому вже зафіксовано подію з `LSN ≥ LSN_dup`:

```
apply(apply(S, e_dup), e_dup)
= apply(S', e_dup)                      [визначення проміжного стану S': S'[k].LSN = LSN_dup]
= S'                                    [умова e_dup.LSN > S'[k].LSN є хибною: LSN_dup ≤ LSN_dup]
```

Таким чином, функція `apply` є алгебраїчно ідемпотентною відносно повторів однакових або застарілих подій, що забезпечує детерміністичну кінцеву узгодженість (Eventual Consistency) цільового сховища.

### Динаміка затримки реплікації та розрахунок дискового ліміту

Затримка реплікації (Replication Lag) у системі CDC вимірюється у двох вимірах: байтовому відставанні транзакційного журналу та наскрізній часовій затримці.

#### 1. Байтове відставання (Byte Lag)
Байтове відставання `L_bytes(t)` визначається як різниця між поточним максимальним LSN, згенерованим транзакціями у базі даних (`LSN_head`), та LSN, підтвердженим споживачем CDC (`LSN_flushed`):

```
L_bytes(t) = LSN_head(t) - LSN_flushed(t)
```

#### 2. Наскрізний бюджет часової затримки (End-to-End Latency)
Повна наскрізна затримка `T_e2e` від моменту завершення SQL-запиту клієнтом до моменту оновлення матеріалізованого індексу споживачем складається з суми чотирьох незалежних фаз:

```
T_e2e = t_flush + t_decode + t_network + t_apply
```

де:
* `t_flush`: час синхронізації WAL на диск СУБД через виклик `fsync()`.
* `t_decode`: час вичитування сторінки та десеріалізації кортежу процесом логічного декодування.
* `t_network`: час передачі події брокеру повідомлень та підтвердження запису в розподілений журнал.
* `t_apply`: час десеріалізації та запису оновленого значення у цільову базу споживача.

#### Диференціальне рівняння накопичення журналу
Нехай середня швидкість генерації журналу основною базою даних дорівнює `R_write` (байтів/с), а пропускна здатність вичитування, декодування та передачі подій рушієм CDC дорівнює `R_cdc` (байтів/с).

Динаміка зміни обсягу нескинутого WAL на диску описується диференціальним балансом:

```
dL/dt = R_write(t) - R_cdc(t)
```

Якщо споживач CDC зупиняється через аварію (`R_cdc(t) = 0`), обсяг журналу WAL на диску СУБД зростає лінійно:

```
L(t) = L₀ + R_write · t
```

#### Виведення максимального безпечного часу простою споживача (Max Safe Downtime)
Нехай вільний дисковий простір, виділений під зберігання журналу WAL, дорівнює `Disk_free` байтів, а встановлений системний ліміт слота дорівнює `max_slot_wal_keep_size`.

Визначимо максимальний допустимий час простою `τ_max`, після якого або переповниться диск СУБД, або слот реплікації буде інвалідовано ядром PostgreSQL:

```
τ_max
= (L_limit - L₀) ÷ R_write              [розв'язання лінійного рівняння: L₀ + R_write · τ_max = L_limit]
```

де `L_limit = min(Disk_free, max_slot_wal_keep_size)`.

#### Числовий приклад розрахунку:
Приймемо такі параметри високоінтенсивної OLTP-системи:
* Швидкість запису WAL: `R_write = 20 МБ/с` (1.2 ГБ/хв).
* Вільний дисковий простір під журнал: `Disk_free = 100 ГБ`.
* Системний ліміт слота: `max_slot_wal_keep_size = 64 ГБ` (`65536 МБ`).
* Початкове відставання: `L₀ = 4 ГБ` (`4096 МБ`).

Розрахуємо граничний безпечний час простою `τ_max`:

```
τ_max
= (65536 - 4096) ÷ 20                  [підстановка значень: L_limit = 65536 МБ, L₀ = 4096 МБ, R_write = 20 МБ/с]
= 61440 ÷ 20                           [обчислення різниці доступного обсягу журналу]
= 3072 секунди                         [ділення обсягу на швидкість запису]
= 51.2 хвилини                         [переведення секунд у хвилини: 3072 ÷ 60]
```

Висновок: якщо споживач CDC не відновить читання протягом 51 хвилини, слот реплікації перейде у стан `lost`, а цілісний потоковий конвеєр вимагатиме повторної повної ініціалізації знімка бази даних.
