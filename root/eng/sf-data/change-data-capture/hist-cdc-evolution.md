# 📜 Еволюція захоплення змін: від тіньових журналів до потокових платформ

Архітектурна потреба в реплікації та перенесенні модифікацій даних виникла одночасно з появою перших комерційних систем керування базами даних на мейнфреймах наприкінці 1970-х та на початку 1980-х років. У класичній моделі корпоративної обробки інформації існував єдиний монолітний вузол (зокрема IBM IMS або ранній IBM DB2 на архітектурі System/370), де концентрувалися всі фінансові та облікові операції. Однак із розвитком бізнес-аналітики з'явилася потреба будувати аналітичні звіти без зупинки та деградації основної транзакційної системи (OLTP).

Першим технічним рішенням цієї задачі став пакетний процес вивантаження, перетворення та завантаження (ETL — Extract, Transform, Load). Раз на добу, зазвичай у нічні години так званого «пакетного вікна» (Batch Window), спеціальні скрипти виконували повне сканування таблиць, порівнювали знімки стану (Full Table Diffing) або вичитували записи за штучними індикаторами часу модифікації. 

Зі зростанням обсягів даних до сотень гігабайтів обчислювальна складність нічного порівняння двох таблиць `O(N · log N)` почала перевищувати тривалість нічного вікна. Спроба сканувати гігантські масиви активної бази навантажувала дискові масиви випадковим читанням, блокувала оперативні транзакції та спричиняла масові затримки у бізнес-процесах. Стало очевидним, що стан таблиці є лише похідним результатом послідовності мутацій, і передавати потрібно не статичні знімки, а безперервний потік первинних змін.

### Народження апаратного та програмного CDC: ера GoldenGate та LogMiner

На початку 1990-х років на ринку реляційних баз даних відбувся вибух розподілених клієнт-серверних архітектур на базі Unix-серверів та платформ Oracle, Sybase і Microsoft SQL Server. Потреба в катастрофостійкості (Disaster Recovery) та реплікації даних між географічно віддаленими дата-центрами унеможливила періодичний пакетний експорт.

У 1995 році інженери Ерік Фіш (Eric Fish) і Тодд Девідсон (Todd Davidson) заснували компанію GoldenGate Software. Вони запропонували фундаментально новий підхід: замість того, щоб звертатися до таблиць бази даних через SQL-інтерфейс, процес захоплення змін мав підключатися безпосередньо до фізичного бінарного журналу транзакцій (Redo Log у СУБД Oracle) в асинхронному режимі. 

Ця технологія отримала назву **Change Data Capture (CDC)** на основі журналу (Log-based CDC):

1. Процес вичитування (Capture Engine / Extractor) читав послідовні байти транзакційного журналу з диска або оперативної пам'яті сервера без блокування таблиць.
2. Процес декодував бінарні структури змін у проміжний канонічний формат (так звані Trail Files).
3. Мережевий агент передавав потік трейл-файлів на цільовий сервер.
4. Процес застосування (Applier) виконував відповідні SQL-команди або прямі модифікації сторінок на цільовій базі даних.

GoldenGate продемонстрував, що вичитування журналу зменшує навантаження на основну СУБД до часток відсотка від загального споживання ресурсів процесора, забезпечуючи водночас затримку реплікації (Replication Lag) менше однієї секунди. Успіх технології був настільки показовим, що у 1999 році корпорація Oracle представила власний вбудований інструмент Oracle LogMiner для аналізу журналів, а в 2009 році остаточно поглинула GoldenGate Software, інтегрувавши продукт у власну корпоративну платформу Oracle GoldenGate.

Паралельно власні механізми CDC розвивали інші постачальники: IBM випустила InfoSphere DataStage та CDC Replication (на базі придбаної технології DataMirror), а Microsoft додала рідну функціональність Change Data Capture у SQL Server 2008 на основі фонового сканування журналу транзакцій за допомогою агентів SQL Server Agent.

### Парадигмальний зсув: «Вивертання бази даних навиворіт»

До середини 2010-х років захоплення змінних даних розглядалося виключно як утилітарний інструмент вузького призначення: реплікація типу «активний-резервний» (Active-Passive), створення сховищ даних (Data Warehousing) або міграція між різними версіями однієї СУБД.

Ситуація кардинально змінилася з поширенням мікросервісної архітектури та платформ поліглотного збереження даних (Polyglot Persistence). Застосунки більше не могли задовольнятися єдиною реляційною базою: для текстового пошуку був потрібен Elasticsearch, для низьколатентного читання за ключем — Redis, для аналітики часових рядів чи колоночних агрегацій — ClickHouse чи Snowflake, а для обміну даними між мікросервісами — брокери повідомлень.

Спроби розробників самостійно записувати дані водночас у кілька сховищ із коду вебсервісу призвели до масових аномалій подвійного запису (Dual-Write Problem), розсинхронізації кешів та втрати консистентності під час збоїв.

У 2015 році британський дослідник систем розподілених даних Мартін Клеппманн (Martin Kleppmann) сформулював концептуальний маніфест під назвою «Turning the database inside out with Apache Samza» («Вивертання бази даних навиворіт»), а згодом детально закріпив його у фундаментальній монографії «Designing Data-Intensive Applications» (2017).

Клеппманн показав, що традиційну СУБД можна концептуально розділити на дві незалежні частини:
* **Транзакційний журнал (Log)** — лінійний потік первинних незмінних фактів і рішень (Single Source of Truth), упорядкованих у часі.
* **Таблиці, індекси та матеріалізовані подання** — вторинні, похідні стани (Derived State), що є функцією від послідовного накатування журналу подій:

```
Стан(T) = Згорнути(Початковий_стан, Журнал_подій[0...T])
```

За цією моделлю зовнішні сервіси, пошукові індекси та кеші є нічим іншим, як матеріалізованими поданнями центрального транзакційного журналу. Замість того, щоб ускладнювати бізнес-код координацією розподілених транзакцій, достатньо побудувати надійний конвеєр захоплення подій із журналу транзакцій основної бази даних та транслювати їх у розподілений незмінний лог повідомлень, такий як Apache Kafka.

### Ера відкритого коду: Debezium та сучасний стан CDC

Реалізація ідей Клеппманна у світі відкритого програмного забезпечення вимагала стандартизованих механізмів вичитування журналів безпосередньо з популярних СУБД. 

У реляційній системі PostgreSQL переломним моментом став випуск версії PostgreSQL 9.4 у 2014 році, де було вперше реалізовано повноцінне **логічне декодування (Logical Decoding)** та введено механізм **слотів реплікації (Replication Slots)**. Це дозволило стороннім процесам підключатися до потоку WAL як логічним підписникам, отримуючи структуровані кортежі замість сирих двійкових сторінок пам'яті. У версії PostgreSQL 10 з'явився рідний бінарний протокол `pgoutput`, що став промисловим стандартом.

У 2016 році інженер Рендалл Гауч (Randall Hauch) та команда компанії Red Hat започаткували проєкт **Debezium** — платформу розподілених конекторів CDC на базі екосистеми Apache Kafka Connect. Згодом до проєкту приєднався Гуннар Морлінг (Gunnar Morling), який очолив його подальший розвиток. 

Debezium об'єднав логічне декодування PostgreSQL, бінарний лог MySQL (Binlog через протокол емуляції репліки `COM_BINLOG_DUMP`), журнал транзакцій SQL Server, MongoDB Change Streams та Oracle Oplog під єдиним уніфікованим інтерфейсом потокових подій у форматах JSON та Apache Avro.

Сьогодні технологія Change Data Capture перетворилася з вузькоспеціалізованого механізму резервного копіювання на основу архітектури сучасних розподілених систем: вона живить патерн Transactional Outbox, уможливлює безпечний перехід від монолітів до мікросервісів (патерн Strangler Fig), синхронізує шар читання у шаблоні CQRS та забезпечує передачу транзакційних даних у реальному часі до аналітичних сховищ та озер даних.
