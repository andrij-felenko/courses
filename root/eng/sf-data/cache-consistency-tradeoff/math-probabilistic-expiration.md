# 🧮 Математика ймовірнісного вичерпання: виведення алгоритму XFetch

Коли сотні серверів одночасно звертаються до одного запису в розподіленому кеші, класичний детермінований час життя (TTL) створює математичну сингулярність. Усі клієнти бачать точний момент смерті ключа, і цей спільний факт викликає миттєву синхронізацію незалежних процесів у катастрофічний сплеск запитів до бази даних.

Математичне розв'язання цієї проблеми полягає в заміні фіксованої миті закінчення терміну дії випадковою величиною, розподіл якої гарантує дві протилежні властивості: ймовірність пропуску оновлення спадає до нуля швидше за експоненту, а очікувана кількість запитів до бази даних залишається строго обмеженою сталою величиною незалежно від частоти звернень клієнтів.

## Модель наївного TTL та розрахунок сили лавини (Cache Stampede)

Нехай потік запитів на читання гарячого ключа є стаціонарним пуассонівським процесом з інтенсивністю `λ` (кількість запитів за одну секунду). Час, необхідний первинній базі даних для обчислення значення та збереження його в кеш, позначимо через `δ` (у секундах).

Запис у кеші має фіксований час придатності, що завершується в мить `T_expiry`.

```
0                        T_expiry       T_expiry + δ
|───────────────────────────|────────────────|─────────────> час t
          Кеш валідний         Вікно пробою:
        (100 % влучань)       усі бачать промах
```

У часовому проміжку `[0, T_expiry)` кожне звернення є влучанням (`cache hit`), тому навантаження на базу даних дорівнює нулю:

```
R_db(t) = 0,    при t < T_expiry
```

У мить `t = T_expiry` запис стає недійсним. Перший запит, що надходить у мить `t₁ ≥ T_expiry`, фіксує промах і запускає обчислення в базі даних, яке триватиме `δ` секунд — до моменту `t₁ + δ`.

Оскільки кеш не оновлено, усі наступні запити, які надійдуть у проміжку `[t₁, t₁ + δ]`, також отримають промах і також відправлять запит до бази даних. Кількість таких запитів `K` підпорядковується розподілу Пуассона з параметром `μ = λ · δ`:

```
P(K = k) = ( (λ · δ)ᵏ · e^(−λ · δ) ) / k!
```

Обчислімо математичне сподівання та дисперсію кількості паралельних запитів, які надійдуть у базу даних протягом вікна обчислення:

```
E[K] = λ · δ                      [властивість пуассонівського розподілу]
Var(K) = λ · δ                    [дисперсія дорівнює математичному сподіванню]
```

Для типового навантаження високонавантаженого сервісу (`λ = 10 000` запитів на секунду, `δ = 0.05` секунди, тобто 50 мілісекунд):

```
E[K]
= 10 000 · 0.05                   [підстановка параметрів потоку та затримки]
= 500                             [середня кількість важких SQL-запитів]
```

Стандартне відхилення кількості запитів становить:

```
σ
= √(λ · δ)                        [квадратний корінь із дисперсії]
= √500                            [обчислення для 500 запитів]
≈ 22.36                           [розкид величини]
```

Застосувавши нерівність Чебишова або апроксимацію нормальним розподілом, бачимо, що з імовірністю понад 0.9999 база даних отримає від 430 до 570 одночасних важких запитів на одну таблицю протягом 50 мілісекунд. Це спричиняє миттєве вичерпання пулу з'єднань і параліч сервера.

## Ідея ймовірнісного раннього вичерпання (XFetch)

Щоб усунути синхронний пробій, час вичерпання ключа роблять імовірнісним. Замість того, щоб чекати миті `T_expiry`, система починає генерувати ймовірність промаху за деякий час ДО номінального закінчення терміну дії.

У 2015 році дослідники Андреа Ваттані, Флавіо К'єрікетті та Кіган Ловенштайн (Andrea Vattani, Flavio Chierichetti, Keegan Lowenstein) опублікували на конференції VLDB алгоритм XFetch.

Правило алгоритму формулюється так: під час кожного читання в момент часу `t` клієнт генерує випадкове число `U`, рівномірно розподілене на інтервалі `(0, 1]`, і перевіряє умову раннього вичерпання:

```
−β · δ · ln(U) > T_expiry − t
```

де:
- `t` — поточний астрономічний час читання;
- `T_expiry` — номінальний час вичерпання запису;
- `T_expiry − t` — залишковий час життя запису (якщо `t ≥ T_expiry`, різниця ≤ 0);
- `δ` — час, витрачений на останнє обчислення значення (зберігається разом із даними в кеші);
- `β > 0` — коефіцієнт агресивності оновлення (за замовчуванням `β = 1.0`);
- `ln(U)` — натуральний логарифм випадкової величини `U ∈ (0, 1]`.

Якщо нерівність виконується, клієнт вважає запис простроченим, запускає асинхронне фонове оновлення з бази даних і віддає користувачеві поточне (ще цілком валідне!) значення без будь-якої затримки.

## Виведення функції ймовірності спрацювання

Знайдемо аналітичний вигляд імовірності `P(t)` того, що окремий запит у момент `t` викличе оновлення.

Позначимо залишковий час життя через `Δt = T_expiry − t`.

Оскільки `U` розподілена рівномірно на `(0, 1]`, випадкова величина `Y = −ln(U)` має стандартний експоненційний розподіл із параметром `1`:

```
P(Y ≤ y) = 1 − e^(−y),    для y ≥ 0
```

Перетворимо умову спрацювання XFetch:

```
−β · δ · ln(U) > Δt
= ln(U) < −Δt / (β · δ)           [ділення на додатне число β · δ]
= U < e^(−Δt / (β · δ))           [експоненціювання обох частин нерівності]
```

Оскільки `U` рівномірна на `(0, 1]`, імовірність події `U < p` для будь-якого `p ∈ (0, 1]` дорівнює в точності `p`:

```
P(trigger | t)
= P( U < e^(−Δt / (β · δ)) )      [ймовірність рівномірної величини]
= e^(−(T_expiry − t) / (β · δ))   [формула ймовірності раннього оновлення]
```

Проаналізуймо поведінку цієї функції:
1. **Далеко до вичерпання (`t ≪ T_expiry`):**
   Різниця `T_expiry − t ≫ β · δ`, тому показник експоненти прямує до мінус нескінченності:
   `P(t) ≈ e^(−∞) = 0`.
   Ймовірність випадкового оновлення нульова.
2. **Наближення до кінця (`t → T_expiry`):**
   Різниця `T_expiry − t → 0`, тому показник прямує до `0`:
   `P(t) → e^0 = 1`.
   Ймовірність оновлення плавно зростає до 100 %.
3. **Після номінального вичерпання (`t ≥ T_expiry`):**
   Різниця `T_expiry − t ≤ 0`, показник експоненти ≥ 0, значення `e^(...) ≥ 1`. Оскільки `U ≤ 1`, умова виконується завжди:
   `P(t) = 1.0`.

## Доведення відсутності лавини промахів

Тепер покажемо, що пуассонівський потік запитів гарантовано викличе оновлення ДО настання `T_expiry`, тобто реального промаху з пробоєм не станеться ніколи.

Нехай запити надходять як пуассонівський потік з інтенсивністю `λ`. Інтенсивність оновлень у момент `t` (кількість тригерів на одиницю часу) дорівнює:

```
λ_refresh(t) = λ · P(trigger | t) = λ · e^(−(T_expiry − t) / (β · δ))
```

Знайдемо загальну кількість очікуваних тригерів `N` на нескінченному інтервалі часу аж до миті `T_expiry`:

```
E[N]
= ∫_{−∞}^{T_expiry} λ_refresh(t) dt               [інтеграл інтенсивності потоку]
= ∫_{−∞}^{T_expiry} λ · e^(−(T_expiry − t)/(β·δ)) dt [підстановка функції ймовірності]
```

Зробимо заміну змінної `u = (T_expiry − t) / (β · δ)`, звідки `dt = −β · δ · du`:
- коли `t = −∞`, `u = +∞`;
- коли `t = T_expiry`, `u = 0`.

```
E[N]
= ∫_{0}^{∞} λ · e^(−u) · (β · δ) du               [заміна змінної та зміна меж]
= λ · β · δ · ∫_{0}^{∞} e^(−u) du                 [винесення сталих величин]
= λ · β · δ · [−e^(−u)]_{0}^{∞}                   [первісна експоненти]
= λ · β · δ · (0 − (−1))                          [підстановка меж інтегрування]
= λ · β · δ                                       [інтегральне сподівання тригерів]
```

Оскільки потік тригерів є неоднорідним пуассонівським процесом, імовірність того, що за весь час до `T_expiry` відбудеться **хоча б одне** раннє оновлення (`N ≥ 1`), дорівнює:

```
P(хоча б 1 тригер до T_expiry)
= 1 − P(N = 0)                                   [доповняльна ймовірність]
= 1 − e^(−E[N])                                   [пуассонівська ймовірність нуля подій]
= 1 − e^(−λ · β · δ)                             [фінальна ймовірність успіху]
```

Підставмо наші реальні числа (`λ = 10 000` зап/с, `δ = 0.05` с, `β = 1.0`):

```
λ · β · δ
= 10 000 · 1.0 · 0.05                            [обчислення показника]
= 500                                            [величина експоненти]

P(успіху)
= 1 − e^(−500)                                   [ймовірність відсутності лавини]
≈ 1 − 1.4 · 10^(−217)                            [число з 217 нулями після коми]
≈ 1.0000000000000000...
```

Ймовірність пропустити раннє оновлення становить `10^(−217)` — це практично фізична неможливість. Запис завжди оновлюється у фоні заздалегідь.

## Мінімізація функції сукупних втрат (Cost Function)

Щоб оцінити оптимальність будь-якої стратегії оновлення кешу, сформулюймо задачу як мінімізацію математичного сподівання сукупних втрат системи `L(S)` для деякої політики `S`.

У будь-якій системі кешування існують три незалежні складові вартості:
1. **Ціна застарілості даних (`C_stale`):** штраф за повернення клієнту копії, яка відстає від стану первинного сховища більше ніж на допустимий інтервал `T_expiry`.
2. **Ціна навантаження на первинне сховище (`C_compute`):** вартість виконання обчислення або важкої вибірки в базі даних (утилізація процесора, споживання пам'яті, блокування рядків).
3. **Ціна затримки відповіді (`C_latency`):** штраф за час, протягом якого користувач блокується в очікуванні відповіді від бази даних при промаху кешу.

Сукупні втрати за один життєвий цикл запису визначаються інтегралом:

```
L(S) = C_compute · E[N_calc] + C_latency · E[N_blocked] + C_stale · ∫ E[Staleness(t)] dt
```

де:
- `E[N_calc]` — очікувана кількість викликів джерела правди;
- `E[N_blocked]` — кількість запитів клієнтів, які отримали блокуючу затримку `δ`;
- `E[Staleness(t)]` — ступінь застарілості даних у момент `t`.

Порівняймо поведінку цієї функції для чотирьох фундаментальних стратегій:

### 1. Детермінований пасивний TTL (Passive Expiration)
Запис вважається валідним до моменту `T_expiry`. При настанні `T_expiry` запис видаляється:
- `E[N_calc] = λ · δ` (лавина запитів);
- `E[N_blocked] = λ · δ` (усі `λ · δ` клієнтів чекають на базі);
- `L(Passive) = (C_compute + C_latency) · λ · δ`.
Втрати лінійно зростають із ростом інтенсивності трафіку `λ`. Для гарячих ключів (`λ → ∞`) втрати прямують до нескінченності.

### 2. Детерміноване фіксоване раннє оновлення (Static Window)
Система намагається оновити запис за фіксований час `W = k · δ` до його смерті (наприклад, за 200 мілісекунд до `T_expiry`).
Якщо в інтервал `[T_expiry − W, T_expiry]` надійде хоча б один запит, він викличе оновлення. Проте якщо інтенсивність трафіку низька (`λ < 1 / W`), з імовірністю `e^(−λ · W)` у це вікно не потрапить жоден запит, і система знову впаде в класичний пробій пасивного TTL.
Якщо ж інтенсивність трафіку висока (`λ ≫ 1 / W`), перший же запит рівно в момент `T_expiry − W` викличе оновлення, що штучно зменшить ефективний час життя запису на `W` секунд, збільшуючи частоту фонових викликів бази.

### 3. Stale-While-Revalidate з фіксованим вікном толерантності
Кеш віддає застаріле значення протягом додаткового періоду `T_stale`, а у фоні запускає асинхронне оновлення:
- `E[N_blocked] = 0` (жоден клієнт не блокується);
- Якщо фоновий запит захищений замком (`Singleflight`), `E[N_calc] = 1`;
- Проте застарілість даних строго ненульова: клієнти гарантовано читають старий стан протягом часу `δ` після настання `T_expiry`.

### 4. Імовірнісне випереджальне оновлення XFetch
- `E[N_blocked] = 0` (значення завжди береться з пам'яті до настання пробою);
- `E[N_calc] ≈ β` (стала величина, незалежна від `λ`);
- `E[Staleness] → 0` (запис оновлюється в межах валідного інтервалу `[0, T_expiry)`).

Таким чином, XFetch мінімізує всі три складові функції втрат одночасно, забезпечуючи оптимальний компроміс за Парето.

## Стохастичний процес відновлення (Renewal Theory)

Розглянемо послідовність життєвих циклів одного ключа як стохастичний процес відновлення. Нехай номінальний час життя запису дорівнює `TTL`. Позначимо через `X_i` фактичну тривалість `i`-го циклу (час між двома послідовними оновленнями запису в кеші).

Оскільки момент виклику XFetch є випадковою величиною `t_trig < T_expiry`, фактичний час життя ключа є меншим за номінальний `TTL` на випадкову величину випередження `W = T_expiry − t_trig`.

Знайдемо розподіл випадкової величини `W` (на скільки секунд раніше відбудеться оновлення).

Функція розподілу величини `W` визначається інтегралом імовірностей спрацювання за час, що передує `T_expiry`. Густина ймовірності того, що перший тригер спрацює за `w` секунд до закінчення терміну дії, за умови пуассонівського потоку звернень `λ`, має вигляд:

```
f_W(w) = λ · e^(−w / (β · δ)) · exp( − ∫_{w}^{∞} λ · e^(−s / (β · δ)) ds )
```

Обчислимо внутрішній інтеграл:

```
∫_{w}^{∞} λ · e^(−s / (β · δ)) ds
= λ · β · δ · [−e^(−s / (β · δ))]_{w}^{∞}
= λ · β · δ · e^(−w / (β · δ))
```

Позначимо `M = λ · β · δ` (очікувану кількість потенційних тригерів). Тоді густина розподілу часу випередження становить:

```
f_W(w) = (M / (β · δ)) · e^(−w / (β · δ)) · exp( −M · e^(−w / (β · δ)) )
```

Це розподіл Ґумбеля (граничний розподіл мінімуму експоненційних величин). Знайдемо математичне сподівання часу випередження `E[W]`:

```
E[W]
= β · δ · (ln(M) + γ)                             [математичне сподівання розподілу Ґумбеля]
= β · δ · (ln(λ · β · δ) + γ)                     [розгортання параметра M]
```

де `γ ≈ 0.57721566...` — стала Ейлера — Маскероні.

З цього виведення випливає важливий практичний наслідок: середній час випередження оновлення зростає лише як **логарифм інтенсивності запитів** `ln(λ)`. Навіть якщо трафік на ключ зросте в 1000 разів (від `λ = 100` до `λ = 100 000`), час випередження збільшиться лише на:

```
ΔE[W]
= β · δ · ln(1000)                                [різниця логарифмів]
≈ β · δ · 6.907                                   [обчислення для тисячократного зростання]
```

При затримці бази `δ = 50` мс і `β = 1.0` зсув моменту оновлення складе всього `0.05 · 6.907 ≈ 345` мілісекунд! Це означає, що ефективний час життя запису практично не скорочується навіть під колосальним тиском трафіку.

## Врахування варіативності часу обчислення δ

У реальних виробничих системах час виконання запиту до бази даних `δ` не є строго сталою величиною. Він підпорядковується логнормальному розподілу через коливання навантаження на дискову підсистему, конкуренцію за блокування рядків та роботу збирача сміття (GC).

Що станеться з алгоритмом XFetch, якщо час виконання запиту раптово підскочить від 10 мс до 500 мс?

Якщо зберігати в кеші лише одне останнє виміряне значення `δ_last`, випадковий викид затримки (outlier) призведе до того, що наступні читання переоцінять необхідне вікно оновлення:
`W_refresh = 3 · β · δ_last = 3 · 1.0 · 500 мс = 1.5 с`.
Кеш почне оновлюватися за півтори секунди до завершення TTL, здійснюючи зайву роботу.

Навпаки, якщо після тривалого важкого обчислення випадково трапиться надшвидка відповідь (`δ_last = 1 мс`), вікно стиснеться до 3 мс, що створить загрозу пробою, якщо наступне реальне обчислення знову займе 50 мс.

Для стабілізації алгоритму в продакшені час обчислення `δ` згладжують експоненційним ковзним середнім (англ. *Exponential Moving Average*, EMA):

```
δ_smooth(n) = α · δ_sample + (1 − α) · δ_smooth(n − 1)
```

де коефіцієнт згладжування `α ∈ [0.1, 0.2]`.

Крім того, для захисту від сплесків 99-го перцентиля затримки (p99 latency) у критичних сервісах замість середнього значення використовують оцінку p99 затримки, отриману через резервуарну вибірку (Reservoir Sampling) або t-digest. Тоді формула XFetch гарантує безпечне оновлення навіть у найгірших 1 % випадків затримки сховища.

## Аналітичне виведення оптимального параметра β*

Знайдемо аналітичний мінімум функції втрат `L(β)` відносно коефіцієнта агресивності `β`.

Припустимо, що система не використовує блокування `Singleflight`, а покладається виключно на ймовірнісну фільтрацію. Тоді кількість обчислень у базі даних `N_calc` за один цикл становить `1 + E[N_redundant] ≈ 1 + β · (1 − e^(−1/β))`.

Ймовірність катастрофічного пробою становить `P_fail = e^(−λ · β · δ)`. Якщо пробій трапляється, система сплачує штраф `C_stampede = C_latency · λ · δ + C_crash`.

Запишімо цільову функцію оптимізації:

```
L(β) = C_compute · (1 + β · (1 − e^(−1/β))) + C_stampede · e^(−λ · β · δ)
```

Знайдемо першу похідну за параметром `β` та прирівняємо її до нуля:

```
∂L / ∂β
= C_compute · (1 − e^(−1/β) − (1/β) · e^(−1/β)) − C_stampede · (λ · δ) · e^(−λ · β · δ)
= 0                                               [умова екстремуму функції втрат]
```

Для високоінтенсивного трафіку (`λ · δ ≫ 1`), розклавши експоненти в ряд Тейлора, отримуємо асимптотичний розв'язок:

```
β* ≈ (1 / (λ · δ)) · ln( (C_stampede · λ · δ) / C_compute )
```

Оскільки вартість аварії бази даних `C_stampede` на порядки перевищує вартість одного штатного обчислення `C_compute` (типове співвідношення `C_stampede / C_compute > 10 000`), оптимальне значення `β*` лежить в інтервалі:

```
0.8 ≤ β* ≤ 1.5
```

Саме тому емпіричне значення `β = 1.0`, запропоноване Ваттані та співавторами, є універсально оптимальним для переважної більшості реальних вебсистем: воно надійно утримує експоненту аварії біля нуля, не створюючи помітного надлишкового навантаження на обчислювальну підсистему.

## Багаторівневе поширення ймовірнісного оновлення (L1/L2 Cache)

У сучасних мікросервісних архітектурах кеш рідко буває однорівневим. Зазвичай застосовують дво- або трирівневу ієрархію:
1. **Рівень L1:** локальна пам'ять процесу додатка (Go in-memory map або C++ LRU-кеш, час доступу `τ₁ ≈ 100` нс).
2. **Рівень L2:** спільний розподілений кластер (Redis або Memcached, час доступу `τ₂ ≈ 1` мс).
3. **Рівень L3 (Source of Truth):** первинна база даних (PostgreSQL або MySQL, час виконання запиту `δ ≈ 50` мс).

Як узгоджуються між собою ймовірнісні параметри на різних рівнях?

Якщо на рівні L1 встановлено час життя `TTL_1`, а на рівні L2 — `TTL_2` (де `TTL_1 ≪ TTL_2`), то формула XFetch застосовується на **обох рівнях із власними часовими параметрами**:

```
Рівень L1 (оновлення з L2):
−β₁ · τ₂ · ln(U) > TTL_1 − t_1

Рівень L2 (оновлення з L3/БД):
−β₂ · δ · ln(U) > TTL_2 − t_2
```

Завдяки такій каскадній формулі сотні незалежних інстансів сервісу спочатку ймовірнісно згладжують запити до розподіленого Redis-кешу (затримка `τ₂`), а сам кластер Redis згладжує навантаження на дискову базу даних (затримка `δ`). Жоден шар архітектури не зазнає резонансних сплесків трафіку.
