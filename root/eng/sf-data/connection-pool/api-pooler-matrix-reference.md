# 📋 Матриця параметрів та поведінки PgBouncer, ProxySQL та HikariCP

Цей довідник містить зведену інженерну матрицю конфігураційних параметрів, режимів мультиплексування, механізмів очищення сесійного стану, діагностичних команд, типових кодів помилок та правил обробки підготовлених виразів для трьох провідних інструментів організації шва з'єднань: PgBouncer, ProxySQL та HikariCP.

## 1. Порівняння рівнів та архітектурних характеристик

Вибір інструменту для організації шва з'єднань визначається архітектурним рівнем, на якому виникає потреба в оптимізації. Внутрішньопроцесний пул HikariCP вирішує задачу локального керування дескрипторами всередині одного екземпляра віртуальної машини, тоді як PgBouncer та ProxySQL виступають зовнішніми мережевими проксі, що захищають кластер бази даних від сумарного тиску тисяч клієнтських процесів.

| Характеристика | PgBouncer (PostgreSQL) | ProxySQL (MySQL / MariaDB) | HikariCP (JVM / JDBC) |
|---|---|---|---|
| **Місце розміщення** | Зовнішній проксі-сервер / Sidecar | Зовнішній проксі-сервер / Sidecar | Внутрішньопроцесна бібліотека |
| **Модель обробки I/O** | Однопотоковий цикл `libevent` (epoll) | Багатопотоковий неблокуючий C++ рушій | Пул у пам'яті JVM на lock-free CAS |
| **Основна спеціалізація** | Зменшення кількості бекендів PostgreSQL | Маршрутизація, сплітінг Read/Write, кеш | Мікрооптимізація затримок взяття з'єднання |
| **Режими пулінгу** | `session`, `transaction`, `statement` | `multiplexing` (еквівалент transaction) | `session` (фізичний сокет утримується клієнтом) |
| **Швидкість взяття сокета** | ~0.2–1.0 мс (TCP оверхед проксі) | ~0.2–0.8 мс (TCP оверхед проксі) | ~0.00005–0.0002 мс (атомарне CAS у RAM) |

## 2. Конфігурація PgBouncer (`pgbouncer.ini`)

PgBouncer керується текстовим файлом конфігурації `pgbouncer.ini`. Нижче наведено розширений опис ключових параметрів ядра, розподілу пулів, контролю пам'яті та часових обмежень із поясненням їхнього впливу на поведінку продуктивної системи.

```ini
[databases]
; Синтаксис: <аліас> = host=<вузол> port=<порт> dbname=<база> pool_size=<ліміт> pool_mode=<режим>
app_production = host=127.0.0.1 port=5432 dbname=production_db pool_size=30 pool_mode=transaction

[pgbouncer]
logfile = /var/log/postgresql/pgbouncer.log
pidfile = /var/run/postgresql/pgbouncer.pid

listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

; ── Режим пулінгу ──
; transaction: сокет утримується тільки всередині BEGIN...COMMIT
; session: сокет утримується від connect до disconnect клієнта
; statement: сокет виділяється на 1 SQL-оператор (забороняє BEGIN...COMMIT)
pool_mode = transaction

; ── Ліміти з'єднань ──
max_client_conn = 5000         ; Максимальна кількість вхідних підключень від застосунків
default_pool_size = 25         ; Кількість серверних з'єднань до кожного бекенду на пару (db, user)
min_pool_size = 5              ; Гарячий мінімум підтримуваних відкритих сокетів до СУБД
reserve_pool_size = 5          ; Додатковий резерв сокетів у разі сплеску черги
reserve_pool_timeout = 5.0     ; Час очікування в черзі (сек) до відкриття резервних сокетів
max_db_connections = 60        ; Жорстка сумарна стеля сокетів до конкретної бази даних

; ── Очищення та безпека сесійного стану ──
; Команда скидання стану бекенду при поверненні в пул
server_reset_query = DISCARD ALL
server_reset_query_always = 0  ; 0 — викликати тільки коли сокет передається новому клієнту

; ── Таймаути ──
server_idle_timeout = 600.0    ; Закриття неактивного серверного сокета після 10 хвилин
server_lifetime = 3600.0       ; Ротація серверного з'єднання кожну годину
client_idle_timeout = 0.0      ; 0 — необмежено (або таймаут відключення завислих клієнтів)
query_timeout = 30.0           ; Примусове переривання запитів, довших за 30 секунд
query_wait_timeout = 15.0      ; Максимальний час очікування клієнта у черзі вільного сокета

; ── Підготовлені вирази (PgBouncer 1.21+) ──
max_prepared_statements = 100  ; Протокольне кешування та відстеження іменованих PREPARE
```

### Пояснення параметрів ядра PgBouncer

1. `pool_mode`: визначає момент звільнення серверного сокета. При значенні `transaction` клієнт може тримати TCP-з'єднання з PgBouncer годинами, але серверний бекенд PostgreSQL використовується лише мілісекунди активної транзакції.
2. `max_client_conn`: верхня межа дескрипторів файлів, яку PgBouncer виділяє під клієнтські сокети. Оскільки клієнтські сокети в PgBouncer є вкрай дешевими (кожен сокет займає лише буфери вводу-виводу обсягом від 2 до 8 КБ), цей ліміт можна безпечно піднімати до десятків тисяч за умови відповідного налаштування системного ліміту ядра ОС `nofile` (`ulimit -n`).
3. `default_pool_size`: кількість відкритих з'єднань безпосередньо до PostgreSQL для кожної унікальної пари «користувач + база даних». Якщо застосунок підключається під одним користувачем `app_user` до однієї бази `app_db`, сумарна кількість сокетів дорівнюватиме `default_pool_size`.
4. `server_reset_query`: інструкція, яка автоматично надсилається бекенду PostgreSQL перед тим, як віддати його наступному клієнту. Команда `DISCARD ALL` гарантує повне скидання тимчасових таблиць, змінних середовища та консультативних блокувань, унеможливлюючи витік конфіденційних даних між різними транзакціями.
5. `reserve_pool_size` та `reserve_pool_timeout`: механізм аварійного демпфування. Якщо черга клієнтських запитів очікує на вільний сокет довше за `reserve_pool_timeout` секунд, PgBouncer тимчасово відкриває додаткові `reserve_pool_size` з'єднань до бази, щоб розвантажити сплеск трафіку, а після спаду навантаження плавно закриває їх.

### Діагностика стану пулів через віртуальну консоль PgBouncer

PgBouncer містить спеціальну віртуальну адміністративну базу даних `pgbouncer`, доступну через команду `psql -p 6432 pgbouncer`. Нижче наведено основні команди моніторингу:

- `SHOW POOLS`: відображає список пулів із розділенням на активні клієнтські з'єднання (`cl_active`), клієнтів, що очікують у черзі сокета (`cl_waiting`), активні серверні з'єднання (`sv_active`), серверні з'єднання в стані очікування (`sv_idle`) та заблоковані з'єднання (`sv_used`).
- `SHOW CLIENTS`: виводить детальну інформацію про кожен підключений клієнтський сокет, його IP-адресу, тривалість сесії та час очікування останнього запиту.
- `SHOW SERVERS`: показує список фізичних бекенд-процесів PostgreSQL, їхній поточний стан (`active`, `idle`, `tested`) та час перебування у відповідному стані.
- `SHOW STATS`: показує агреговану статистику: сумарну кількість оброблених транзакцій (`total_xact_count`), загальну кількість SQL-запитів (`total_query_count`), обсяг отриманого й відправленого мережевого трафіку та середню тривалість виконання запитів.

## 3. Керування та змінні ядра ProxySQL

ProxySQL є спеціалізованим проксі-сервером для реляційних СУБД із протоколом MySQL (MySQL, MariaDB, Percona Server). Він містить трирівневу модель конфігурації: оперативна пам'ять виконання (`RUNTIME`), пам'ять керування (`MEMORY`) та дискове сховище (`DISK` на базі вбудованого SQLite).

| Змінна ядра ProxySQL | Значення за замовчуванням | Інженерний опис та вплив на систему |
|---|---|---|
| `mysql-multiplexing` | `true` | Дозволяє мультиплексування запитів різних клієнтів через один серверний сокет бекенду. |
| `mysql-max_connections` | `2048` | Максимальна кількість вхідних клієнтських TCP-сокетів, яку приймає проксі. |
| `mysql-free_connections_pct` | `10` | Відсоток вільних прогрітих з'єднань, що утримуються в пулі для мінімізації латентності. |
| `mysql-connection_max_age_ms` | `0` (вимкнено) | Граничний вік серверного сокета в мілісекундах перед його плановою ротацією. |
| `mysql-connect_timeout_server` | `1000` (мс) | Таймаут встановлення зв'язку з екземпляром MySQL до фіксації мережевої помилки. |
| `mysql-ping_interval_server_msec`| `10000` (мс) | Інтервал відправки команд `COM_PING` для апаратної валідації життєздатності пулу. |
| `mysql-query_retries_on_failure` | `1` | Кількість автоматичних повторних спроб виконання запиту у разі розриву сокета під час відправки. |

### Автоматичне блокування мультиплексування (Multiplexing Disabled)

Критичною особливістю ProxySQL є евристичний алгоритм відстеження сесійного стану. Якщо в процесі аналізу SQL-потоку парсер виявляє оператори, що залишають стан у сесії, він встановлює прапорець блокування мультиплексування:

1. **Користувацькі змінні**: вираз `SET @var_name = 1` змушує ProxySQL зафіксувати фізичний сокет за поточним клієнтом, оскільки інші клієнти не повинні бачити значення цієї змінної.
2. **Сесійні функції результатів**: виклики `FOUND_ROWS()`, `ROW_COUNT()`, `LAST_INSERT_ID()` потребують зв'язку з бекендом, на якому щойно виконувався попередній запит.
3. **Тимчасові таблиці**: оператор `CREATE TEMPORARY TABLE` закріплює серверний сокет за клієнтом до явного знищення таблиці або розриву з'єднання.
4. **Іменовані блокування**: виклики `GET_LOCK('mutex_key', 10)` утримують контекст блокування на рівні потоку бекенду MySQL.
5. **Транзакційні межі**: після отримання команди `START TRANSACTION` або вимкнення автоматичної фіксації `SET autocommit = 0` проксі фіксує сокет за клієнтом до моменту відправки `COMMIT` чи `ROLLBACK`.

## 4. Конфігурація HikariCP (Java / JVM)

HikariCP проектувався як гранично оптимізований внутрішньопроцесний пул з'єднань для середовища Java Virtual Machine. Його параметри зосереджені на запобіганні блокуванням потоків та уникненні прихованих затримок під час сплесків навантаження.

| Параметр HikariCP | Рекомендоване значення | Інженерне призначення та правила налаштування |
|---|---|---|
| `maximumPoolSize` | `(CPU_cores * 2) + disks` | Максимальна кількість фізичних JDBC-сокетів, що відкриваються до СУБД. |
| `minimumIdle` | Дорівнює `maximumPoolSize` | Фіксований розмір пулу запобігає затримкам виділення сокетів під час сплесків навантаження. |
| `connectionTimeout` | `30000` (30 сек) | Максимальний час, який клієнтський потік чекає на вільне з'єднання перед генерацією `SQLException`. |
| `idleTimeout` | `600000` (10 хв) | Час простою сокета перед його закриттям (актуально, якщо `minimumIdle < maximumPoolSize`). |
| `maxLifetime` | `1800000` (30 хв) | Максимальний час життя сокета. Обов'язково має бути на 2–5 хвилин меншим за серверні таймаути бази або мережевого балансувальника. |
| `keepaliveTime` | `120000` (2 хв) | Інтервал «пінгу» сокета для запобігання тихому скиданню з'єднання проміжними NAT-шлюзами чи фаєрволами. |
| `validationTimeout` | `5000` (5 сек) | Таймаут швидкої перевірки життєздатності з'єднання перед видачею клієнту (`test-on-borrow`). |
| `leakDetectionThreshold` | `10000` (10 сек) | Час, після якого пул фіксує підозру на витік з'єднання (забутий виклик `close()`) і друкує стек виклику. |

### Правило фіксованого розміру пулу (Fixed Pool Sizing)

Головною практичною рекомендацією для HikariCP у високонавантажених системах є встановлення однакових значень для `maximumPoolSize` та `minimumIdle`. Динамічне розширення та стиснення пулу під час коливань трафіку створює небажані затримки: під час раптового напливу запитів потоки застосунку змушені чекати на проходження повного циклу встановлення TCP-хендшейків та аутентифікації сокетів замість миттєвого отримання прогрітого дескриптора з пам'яті. Фіксований пул гарантує детерміновану поведінку системи за будь-якого профілю трафіку.

## 5. Типові помилки шва з'єднань та методи їх локалізації

Під час експлуатації систем із пулерами інженери регулярно стикаються зі специфічними помилками протоколу та мережевого шва. Нижче наведено перелік діагностичних ознак та шляхів їх усунення:

1. `ERROR: no more connections allowed (max_client_conn)`:
   Виникає, коли кількість клієнтських процесів перевищила ліміт `max_client_conn` у PgBouncer. Рішення полягає у збільшенні системного ліміту файлових дескрипторів операційної системи (`ulimit -n 65535`) та піднятті `max_client_conn` до необхідного значення.
2. `ERROR: query_wait_timeout`:
   Клієнтський запит провів у черзі PgBouncer більше часу, ніж дозволено параметром `query_wait_timeout`, оскільки всі серверні бекенди були зайняті виконанням повільних SQL-транзакцій. Рішення: оптимізація повільних запитів через індексацію, додавання ліміту `statement_timeout` у PostgreSQL та перевірка наявності довгих блокувань рядків (`exclusive row locks`).
3. `ERROR: prepared statement "S_1" does not exist`:
   Застосунок намагається повторно використати іменований підготовлений вираз через транзакційний PgBouncer без увімкненого параметра `max_prepared_statements`. Рішення: переведення клієнтського драйвера в режим неіменованих підготовлених виразів (Simple Query Protocol або Anonymous Extended Query) або оновлення PgBouncer до версії 1.21+ з увімкненням кешування дескрипторів.
4. `SSL SYSCALL error: EOF detected`:
   Свідчить про раптове закриття з'єднання проміжним мережевим обладнанням (AWS NAT Gateway, Azure Load Balancer або апаратний фаєрвол), яке скинуло TCP-таблицю трансляції через тривалий простій сокета. Рішення: налаштування системних параметрів TCP Keepalive у конфігурації ОС (`tcp_keepalives_idle = 60`, `tcp_keepalives_interval = 10`, `tcp_keepalives_count = 3`) або зменшення параметра `maxLifetime` у клієнтському пулі.
