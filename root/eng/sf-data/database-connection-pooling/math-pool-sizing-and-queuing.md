# 🧮 Математика розміру пулу: теорія черг, закон Літтла та формула насичення СУБД

Розрахунок оптимального розміру пулу з'єднань — це класична інженерна оптимізаційна задача теорії масового обслуговування. Поширена інтуїтивна помилка розробників полягає в припущенні, що збільшення розміру пулу автоматично збільшує пропускну здатність системи. Якщо сервер застосунків має 500 робочих потоків, інженер часто налаштовує розмір пулу на 500 з'єднань. На практиці це призводить до різкого падіння продуктивності, лавиноподібного зростання затримки та відмови СУБД.

Математичне моделювання показує, що пул з'єднань діє як дросель пропускної здатності, який узгоджує високу конкурентність прикладного рівня з обмеженою кількістю фізичних обчислювальних ресурсів сервера бази даних.

## Закон Літтла та базова пропускна здатність

Фундаментальним інваріантом будь-якої стаціонарної системи масового обслуговування є закон Літтла (англ. *Little's Law*), сформульований математиком Джоном Літтлом у 1961 році:

```
L = λ · W      [закон Літтла: зв'язок кількості клієнтів, інтенсивності та часу перебування]
```

де:
- `L` — середня кількість транзакцій, що одночасно обробляються в системі (англ. *concurrency*, розмір активного пулу з'єднань);
- `λ` (лямбда) — середня швидкість надходження нових транзакцій (інтенсивність вхідного потоку, запитів на секунду, RPS);
- `W` — середній час, який транзакція проводить у системі (повна затримка виконання, або латентність).

Час перебування `W` складається з двох послідовних компонентів:
```
W = W_q + W_s      [час у черзі очікування сокета W_q + час виконання запиту в СУБД W_s]
```

Якщо припустити, що пул з'єднань ідеально збалансований і запити не простоюють у черзі (`W_q ≈ 0`), то мінімально необхідна кількість з'єднань `N_min` для обслуговування цільового трафіку `λ` при середньому часі виконання запиту `T_query` визначається прямим перетворенням:

```
N_min = λ · T_query      [мінімальний розмір пулу за законом Літтла при W_q = 0]
```

### Розрахунок мінімального розміру пулу:
Припустимо, веб-сервіс обслуговує `λ = 10 000` запитів на секунду. Кожен запит виконує швидкий індексний пошук у базі даних, який триває `T_query = 2` мілісекунди (`0.002` с).

```
N_min = 10000 · 0.002    [підстановка вхідних параметрів λ = 10000 і T_query = 0.002 с]
      = 20               [обчислення добутку: достатньо рівно 20 активних з'єднань]
```

Усього 20 відкритих сокетів здатні прокачувати 10 000 операцій на секунду, якщо кожен сокет безперервно утилізується корисною роботою.

## Модель M/M/k та формула Ерланга C для черги пулу

Реальний вхідний потік запитів не є строго детермінованим: запити надходять випадково, утворюючи пуассонівський процес з інтенсивністю `λ`, а час обробки запитів підпорядковується експоненційному розподілу з середнім часом обслуговування `1/μ` (де `μ` — продуктивність одного з'єднання, виміряна в запитах на секунду).

Така система описується класичною марковською моделлю `M/M/k`, де `k` — розмір пулу з'єднань (кількість паралельних обслуговуючих каналів).

### Виведення ймовірності черги з рівнянь балансу станів

Розглянемо процес народження і загибелі (англ. *birth-death process*), де стан системи `n` позначає загальну кількість запитів (як тих, що виконуються на сокетах, так і тих, що очікують у черзі пулу).

Інтенсивність надходження нових вимог у будь-якому стані постійна:
```
λ_n = λ      [пуассонівський вхідний потік не залежить від стану системи]
```

Інтенсивність обслуговування `μ_n` залежить від кількості зайнятих сокетів `n`:
```
μ_n = n · μ      [якщо n < k: працює n паралельних з'єднань]
μ_n = k · μ      [якщо n ≥ k: усі k з'єднань зайняті, решта запитів стоїть у черзі]
```

Рівняння локального балансу ймовірностей для стаціонарного режиму мають вигляд:
```
p_n · λ = p_{n+1} · μ_{n+1}      [рівновага потоків переходів між сусідніми станами n та n+1]
```

Виразимо ймовірність стану `p_n` через ймовірність порожньої системи `p_0`. Введемо запропоноване навантаження `a = λ / μ` (виражене в безрозмірних одиницях — ерлангах):

Для `n ≤ k`:
```
p_n = (aⁿ / n!) · p_0      [виведення ймовірності для n менше або дорівнює k]
```

Для `n > k`:
```
p_n = (aⁿ / (k! · k^{n-k})) · p_0
    = (aᵏ / k!) · (a / k)^{n-k} · p_0
    = (aᵏ / k!) · ρ^{n-k} · p_0      [де коефіцієнт завантаження пулу ρ = a / k = λ / (k · μ)]
```

Для стабільності системи коефіцієнт завантаження обов'язково має задовольняти умову `ρ < 1`. Застосуємо умову нормування суми всіх ймовірностей `∑ [n=0..∞] p_n = 1`:

```
1 = p_0 · (∑ [n=0..k-1] (aⁿ / n!) + ∑ [n=k..∞] (aᵏ / k!) · ρ^{n-k})      [розділення суми на дві частини]
1 = p_0 · (∑ [n=0..k-1] (aⁿ / n!) + (aᵏ / k!) · ∑ [m=0..∞] ρᵐ)          [заміна індексу m = n - k]
1 = p_0 · (∑ [n=0..k-1] (aⁿ / n!) + (aᵏ / k!) · (1 / (1 - ρ)))           [сума нескінченної геометричної прогресії]
```

Звідси знаходимо ймовірність того, що всі з'єднання вільні:
```
p_0 = 1 / (∑ [n=0..k-1] (aⁿ / n!) + (aᵏ / k!) · (1 / (1 - ρ)))      [ймовірність порожнього пулу]
```

Ймовірність того, що новоприбулий запит застане всі `k` з'єднань зайнятими й потрапить у чергу очікування, дорівнює сумі ймовірностей станів `n ≥ k`. Це і є знаменита формула Ерланга C (англ. *Erlang C formula*):

```
P_wait = ∑ [n=k..∞] p_n
       = (aᵏ / k!) · (1 / (1 - ρ)) · p_0
       = (aᵏ / k!) · (1 / (1 - ρ)) / (∑ [n=0..k-1] (aⁿ / n!) + (aᵏ / k!) · (1 / (1 - ρ)))      [формула Ерланга C]
```

### Середня довжина черги та час очікування оренди

Знаючи ймовірність затримки `P_wait`, визначимо середню кількість запитів, що очікують у черзі `L_q`:

```
L_q = ∑ [n=k..∞] (n - k) · p_n                                   [математичне сподівання довжини черги]
    = p_0 · (aᵏ / k!) · ∑ [m=0..∞] m · ρᵐ                         [винесення констант за знак суми]
    = p_0 · (aᵏ / k!) · (ρ / (1 - ρ)²)                            [сума степеневого ряду ∑ m·ρᵐ = ρ/(1-ρ)²]
    = P_wait · (ρ / (1 - ρ))                                      [вираз середньої довжини черги через P_wait]
```

Застосувавши закон Літтла до черги (`L_q = λ · W_q`), отримаємо середній час очікування сокета `W_q`:

```
W_q = L_q / λ                                                     [закон Літтла для черги очікування]
    = (P_wait · ρ) / (λ · (1 - ρ))                                [підстановка L_q]
    = (P_wait · (λ / (k · μ))) / (λ · (1 - λ / (k · μ)))          [підстановка ρ = λ / (k·μ)]
    = P_wait / (k · μ - λ)                                        [скорочення на λ у чисельнику й знаменнику]
```

Звідси повна затримка виконання транзакції `W` (від моменту виклику `acquire()` до повернення результату клієнту) становить:

```
W = W_q + 1/μ                                                     [сума часу в черзі та часу виконання на сокеті]
  = P_wait / (k · μ - λ) + 1/μ                                    [фінальна формула повної затримки запиту]
```

Коли утилізація пулу `ρ = λ / (k · μ)` наближається до `1.0`, знаменник `(k · μ - λ)` прямує до нуля, викликаючи так зване «коліно затримки» (англ. *latency knee*) — вибухове зростання часу очікування в черзі.

## Розподіл затримок у хвості (Tail Latency) та розрахунок таймауту

Середній час затримки `W_q` дає лише частину картини. Для високонавантажених систем критичним параметром є затримка в хвості розподілу — 95-й, 99-й та 99.9-й процентилі (англ. *tail latency*).

У системі `M/M/k` час перебування запиту в черзі `T_wait` для тих запитів, які взагалі зазнали затримки, підпорядковується експоненційному закону з параметром `k · μ - λ`:

```
P(T_wait > t) = P_wait · e^{-(k · μ - λ) · t}      [хвостова функція розподілу часу очікування]
```

Звідси процентиль затримки `t_p` (час, за який виконується `p` частка запитів, наприклад `p = 0.99` для 99-го процентиля) обчислюється розв'язанням рівняння `P(T_wait > t_p) = 1 - p`:

```
1 - p = P_wait · e^{-(k · μ - λ) · t_p}                                        [рівняння процентиля черги]
e^{-(k · μ - λ) · t_p} = (1 - p) / P_wait                                      [ділення на ймовірність P_wait]
-(k · μ - λ) · t_p = ln((1 - p) / P_wait)                                      [взяття натурального логарифма]
t_p = ln(P_wait / (1 - p)) / (k · μ - λ)                                       [фінальна формула процентиля затримки]
```

Якщо `P_wait < 1 - p`, то черга настільки вільна, що `p`-й процентиль затримки в черзі дорівнює нулю (`t_p = 0`).

### Математичний вибір connectionTimeout

Таймаут взяття з'єднання з пулу `connectionTimeout` (параметр `T_timeout`) визначає, через який час очікування в черзі потік застосунку відмовиться від спроби й викине помилку `SQLException` або поверне клієнту `504 Gateway Timeout`.

Ймовірність того, що клієнт отримає таймаут, дорівнює:
```
P_timeout = P(T_wait > T_timeout)
          = P_wait · e^{-(k · μ - λ) · T_timeout}      [ймовірність вичерпання дедлайну пулу]
```

Якщо налаштувати `T_timeout` занадто малим (наприклад, 10 мс), система відкидатиме легітимні короткочасні сплески трафіку. Якщо налаштувати `T_timeout` занадто великим (наприклад, 30 секунд), сотні потоків веб-сервера осядуть у черзі очікування сокета, заблокують пул потоків сервованої програми (Tomcat / Netty / Go runtime) і спричинять каскадну відмову всього сервісу.

Оптимальне значення дедлайну розраховується з умови обмеження частки помилок `P_timeout ≤ ε` (де `ε = 10⁻⁴` — 0.01% допустимих відмов):

```
T_timeout = ln(P_wait / ε) / (k · μ - λ)      [математичний розрахунок оптимального дедлайну]
```

## Універсальний закон масштабованості Гюнтера (USL)

Чому не можна усунути чергу, просто нескінченно збільшуючи розмір пулу `k`? Тому що реляційна база даних — це не набір незалежних вузлів, а єдина система зі спільними структурами пам'яті (журнал транзакцій WAL, кеш сторінок, таблиці блокувань).

Ніл Гюнтер (Neil J. Gunther) у 1993 році узагальнив закон Амдала у вигляді Універсального закону масштабованості (англ. *Universal Scalability Law, USL*). Продуктивність системи `C(N)` як функція від кількості паралельних робочих потоків `N` описується рівнянням:

```
C(N) = N / (1 + α · (N - 1) + β · N · (N - 1))      [універсальний закон масштабованості Гюнтера]
```

де:
- `N` — кількість одночасних з'єднань / процесів бекенду СУБД;
- `α` (альфа) — коефіцієнт серіалізації (англ. *contention*): частка роботи, яка виконується строго послідовно через захоплення спільних замків (наприклад, блокування рядків таблиць, атомарне додавання записів у WAL);
- `β` (бета) — коефіцієнт узгодження (англ. *coherency penalty*): накладні витрати на перехресну синхронізацію кешів процесора (MESI-протокол) та передачу прав володіння сторінками пам'яті між процесорними ядрами. Член `β · N · (N - 1)` пропорційний кількості парних взаємодій між усіма `N` процесами (`N · (N - 1) / 2`).

### Поведінка кривої масштабованості:
1. **Лінійна зона (`N` мале, `α` і `β` не домінують):** Продуктивність зростає майже пропорційно кількості з'єднань `C(N) ≈ N`.
2. **Зона насичення (закон Амдала, `β = 0`):** При збільшенні `N` продуктивність виходить на асимптотичне плато `C_max = 1 / α`.
3. **Зона ретроградної деградації (`β > 0`):** Коли `N` перевищує критичну точку, член другого порядку `β · N · (N - 1)` починає домінувати. Продуктивність системи різко падає нижче початкового рівня через постійне інвалідування кешів процесора та очікування на спінлоках.

Точка екстремуму (оптимальний розмір пулу `N_opt`), де база даних видає абсолютний максимум транзакцій на секунду, знаходиться взяттям похідної `dC/dN = 0`:

```
N_opt = √((1 - α) / β)      [оптимальна кількість з'єднань за законом Гюнтера]
```

Якщо для конкретної СУБД виміряні коефіцієнти становлять `α = 0.02` (2% послідовного коду) та `β = 0.0008` (взаємне інвалідування кешів):

```
N_opt = √((1 - 0.02) / 0.0008)    [підстановка параметрів α = 0.02 та β = 0.0008]
      = √(0.98 / 0.0008)          [обчислення підкореневого виразу]
      = √1225                     [спрощення дробу]
      = 35                        [оптимальний розмір пулу з'єднань]
```

Збільшення пулу з 35 до 200 з'єднань на цій системі зменшить пропускну здатність у 3 рази й збільшить p99 затримку у 20 разів.

## Модель рандомізації вибуття з'єднань (Jitter Eviction)

Кожне з'єднання в пулі має максимальний термін життя `maxLifetime` (наприклад, 30 хвилин) для захисту від поступових витоків пам'яті на стороні бекенда та оновлення маршрутів балансувальників.

Якщо всі `N` з'єднань пулу ініціалізуються одночасно при старті сервісу в момент `t = 0`, то рівно в момент `t = maxLifetime` усі `N` сокетів одночасно закриються. Виникає катастрофічний стан перегонів — «громоподібне стадо» (англ. *thundering herd*): сотні потоків застосунку одночасно намагаються встановити нові TCP/TLS-з'єднання, перевантажуючи ядро бази даних.

Для усунення цього ефекту час життя кожного з'єднання рандомізується додаванням рівномірного випадкового відхилення (англ. *variance / jitter*):

```
T_lifetime = maxLifetime - Uniform(0, Jitter_Max)      [рандомізація часу життя з'єднання]
```

де `Jitter_Max = 0.1 · maxLifetime` (10% від базового часу).

Густина розподілу ймовірності вибуття з'єднань стає рівномірною на інтервалі `[0.9 · maxLifetime, maxLifetime]`. Інтенсивність створення нових з'єднань `λ_reconnect` розподіляється рівномірно в часі:

```
λ_reconnect = N / Jitter_Max      [швидкість перепідключення сокетів]
```

Якщо `N = 40`, а `maxLifetime = 1800` с (`Jitter_Max = 180` с):
```
λ_reconnect = 40 / 180            [ділення кількості з'єднань на вікно джитера]
            ≈ 0.22 з'єднань/с     [одне нове з'єднання кожні 4.5 секунди]
```

Така інтенсивність не створює жодного вимірного навантаження на мережевий стек та процесор бази даних.

## Фізичні обмеження СУБД: формула PostgreSQL та Oracle

База даних виконує три типи апаратних операцій:
1. **Обчислення в CPU (Cache/RAM hit):** Сканування рядків у пам'яті, агрегація, сортування, перевірка умов у буферному кеші.
2. **Дисковий I/O (Disk read/write):** Зчитування сторінок з NVMe SSD або синхронний запис у транзакційний журнал (WAL).
3. **Очікування замків (Lock contention):** Синхронізація доступу до рядків та сторінок пам'яті через внутрішні спінлоки.

Процесор із `C` фізичними ядрами може одночасно виконувати рівно `C` потоків машинних інструкцій. Якщо на 16-ядерному сервері запустити 500 процесів СУБД, операційна система Linux змушена постійно перемикати контекст між цими процесами:

```
T_cpu_total = T_useful_work + T_context_switch · (N_processes - 1)      [баланс часу CPU]
```

Накладні витрати на одне перемикання контексту процесу ядра Linux (скидання буфера асоціативної трансляції TLB та витіснення рядків кешу L1/L2) становлять `T_context_switch ≈ 2–5` мікросекунд. При 500 процесах процесор втрачає до 40% корисної потужності лише на роботу планувальника ядра.

На основі великої кількості апаратних вимірювань інженери PostgreSQL та Oracle сформулювали емпіричну інженерну формулу розрахунку максимальної кількості одночасних підключень:

```
Connections = Cores · 2 + Effective_Spindle_Count      [емпірична формула розміру пулу PostgreSQL]
```

де:
- `Cores` — кількість фізичних ядер процесора сервера бази даних;
- `Effective_Spindle_Count` — ефективна кількість паралельних дискових черг вводу-виводу (для сучасних NVMe SSD масивів із швидким часом відгуку береться значення від 4 до 16).

### Приклад розрахунку для 16-ядерного сервера з NVMe SSD:
```
Connections = 16 · 2 + 8      [підстановка 16 ядер CPU та 8 дискових черг NVMe]
            = 32 + 8          [проміжне множення Cores · 2]
            = 40              [фінальний оптимальний розмір пулу для сервера СУБД]
```

## Модель споживання оперативної пам'яті

Кожен клієнтський процес PostgreSQL або сесійний потік MySQL утримує власний обсяг віртуальної та фізичної пам'яті:

```
RAM_total = RAM_shared + ∑ [i=1..N] (RAM_base_session + RAM_work_mem[i] + RAM_temp_buffers[i])
```

У PostgreSQL:
- `RAM_shared` — спільні буфери (`shared_buffers`), фіксовані при старті СУБД (наприклад, 16 ГБ);
- `RAM_base_session` — пам'ять процесу бекенду під системний каталог (`relcache`, `syscache`), кеш планів запитів та стек процесу (~15 МБ на з'єднання);
- `RAM_work_mem` — динамічна пам'ять для сортування, хеш-таблиць та з'єднань таблиць (`work_mem`). При складному запиті з 4 операціями `Hash Join` один процес виділяє `4 · work_mem`.

Якщо `work_mem = 64` МБ, а пул роздуто до `N = 500` з'єднань:

```
RAM_sessions_peak = N · (RAM_base + 4 · work_mem)        [формула пікового споживання пам'яті бекендами]
                  = 500 · (15 МБ + 4 · 64 МБ)            [підстановка параметрів N = 500, base = 15 МБ, work_mem = 64 МБ]
                  = 500 · (15 МБ + 256 МБ)               [множення кількості вузлів на пам'ять одного вузла]
                  = 500 · 271 МБ                         [сумарне споживання пам'яті одним активним процесом]
                  = 135500 МБ                            [множення на 500 процесів]
                  ≈ 132.3 ГБ                             [переведення мегабайтів у гігабайти діленням на 1024]
```

Якщо сервер має лише 64 ГБ пам'яті, ядро операційної системи Linux активує механізм `OOM Killer` і аварійно вб'є головний процес бази даних через сигнал `SIGKILL`.

Зменшення пулу до розрахункового `N = 40` з'єднань нормалізує споживання пам'яті:

```
RAM_sessions_peak = 40 · 271 МБ                          [розрахунок для оптимізованого пулу N = 40]
                  = 10840 МБ                             [множення 40 на 271 МБ]
                  ≈ 10.6 ГБ                              [переведення у гігабайти: безпечно вкладається у 64 ГБ RAM]
```

## Дисципліна черги: математичне порівняння FIFO та LIFO

Внутрішня організація черги очікування вільних з'єднань пулу визначає не лише середній час затримки `W_q`, але й форму її дисперсії (англ. *variance*, `Var(W)`).

При використанні дисципліни **FIFO (First-In, First-Out)**:
- Усі запити отримують з'єднання строго в порядку прибуття.
- Дисперсія часу очікування є мінімальною:
```
Var_FIFO(W_q) = (P_wait · (2 - P_wait)) / (k · μ - λ)²      [дисперсія затримки при черзі FIFO]
```
- Недолік FIFO: з'єднання в пулі використовуються рівномірно по колу, через що неактивні з'єднання частіше закриваються проміжними маршрутизаторами та NAT за таймаутом бездіяльності TCP (300 с).

При використанні дисципліни **LIFO (Last-In, First-Out / Stack)**:
- Останнє повернене в пул з'єднання негайно видається наступному запиту.
- Математичне сподівання середнього часу `E[W_q]` залишається точно таким самим, як у FIFO, але дисперсія різко зростає:
```
Var_LIFO(W_q) = (2 · P_wait) / ((1 - ρ) · (k · μ - λ)²)      [дисперсія затримки при черзі LIFO]
```
- Перевага LIFO для апаратної частини: невелика підмножина сокетів залишається постійно «гарячою» в оперативній пам'яті та кешах L1/L2 процесора, а «холодні» з'єднання в кінці стека можуть бути безпечно вивільнені фоновим прибиральником для економії пам'яті.

## Двостадійний закон Літтла для конвеєра веб-потоків і пулу

У реальному сервері запит клієнта спочатку очікує звільнення робочого потоку веб-сервера (`Thread Pool`), а потім усередині бізнес-логіки очікує сокета з пулу бази даних (`Connection Pool`). Повна затримка системи визначається сумою двох послідовних систем масового обслуговування:

```
W_total = W_thread_queue + W_app_compute + W_conn_queue + W_db_execute      [повний конвеєр затримки запиту]
```

Застосовуючи закон Літтла до всього конвеєра:
```
L_total = λ · (W_thread_queue + W_app_compute + W_conn_queue + W_db_execute)      [загальна кількість запитів у системі]
```

Якщо розмір пулу з'єднань налаштовано неправильно (`k >> N_opt`), час `W_db_execute` зростає через блокування ядра СУБД, що миттєво викликає зростання черги `W_conn_queue`, утримання веб-потоків `W_app_compute` і лавиноподібне переповнення черги потоків `W_thread_queue`. Двостадійний баланс доводить: оптимізація пулу бази даних є головною умовою стабільності всієї високорівневої веб-інфраструктури.

## Зведене правило розміщення та балансування черг

У розподіленій системі з `M` екземплярів мікросервісу розмір локального пулу кожного інстансу `PoolSize_app` обчислюється як:

```
PoolSize_app = floor(Total_DB_Connections / M)      [розподіл ліміту СУБД між екземплярами застосунку]
```

Якщо `Total_DB_Connections = 40`, а кількість подів у Kubernetes `M = 20`:
```
PoolSize_app = floor(40 / 20)      [ділення глобального ліміту 40 на 20 подів]
             = 2                   [розмір пулу кожного пода]
```

Якщо кількість подів перевищує `Total_DB_Connections` (наприклад, 100 подів при ліміті 40 з'єднань), прямий клієнтський пулінг стає математично неможливим (`40 / 100 < 1`). У такій системі обов'язковим є встановлення проміжного проксі-пулера (PgBouncer або ProxySQL), який утримує чергу `M/M/k` на мережевому рівні й передає на фізичний сервер СУБД рівно `Connections = Cores · 2 + Spindles` стабільних потоків.
