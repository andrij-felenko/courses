# 📋 Реляційні обмеження цілісності та DDL-контракт схеми даних

Реляційна модель гарантує узгодженість стану бази даних не через прикладний процедурний код, а за допомогою декларативних обмежень цілісності (integrity constraints), зафіксованих у мові опису даних (Data Definition Language, DDL). Покладання цілісності на прикладні сервіси є небезпечною антипатерною практикою: паралельні транзакції, прямі виклики через консоль адміністратора, аналітичні скрипти або помилки в бізнес-коді неминуче призводять до виникнення висячих посилань та розриву логічних інваріантів. База даних виступає останнім і непорушним рубежем захисту коректності інформації.

Нижче наведено структуровану специфікацію реляційних обмежень, їхньої семантики виконання, правил посилальної цілісності та крайових випадків у сучасних реляційних СУБД.

## Класифікація обмежень реляційної цілісності

Реляційна СУБД автоматично верифікує інваріанти при кожній операції модифікації даних (`INSERT`, `UPDATE`, `DELETE`). Будь-яке порушення обмеження призводить до негайної відмови у виконанні інструкції та відкочування поточної транзакції з поверненням стандартного SQL-коду помилки (SQLSTATE).

| Обмеження | Рівень застосування | Математичний інваріант | Поведінка при порушенні |
| :--- | :--- | :--- | :--- |
| `NOT NULL` | Атрибут (колонка) | `∀ t ∈ R: t[A] ≠ ⊥` | Заборона збереження невизначеного значення `NULL`. |
| `CHECK (cond)` | Атрибут / Кортеж | `∀ t ∈ R: cond(t) ≢ FALSE` | Відхилення операції, якщо предикат обчислюється у `FALSE`. |
| `UNIQUE` | Набір колонок | `∀ t₁, t₂ ∈ R: (t₁[K] = t₂[K] ∧ t₁[K] ≠ ⊥) ⇒ t₁ = t₂` | Відхилення дублікатів значень. |
| `PRIMARY KEY` | Таблиця (відношення) | `UNIQUE(K) ∧ NOT NULL(K)` | Забезпечення однозначної адресації рядків відношення. |
| `FOREIGN KEY` | Зв'язок таблиць | `∀ t₁ ∈ R₁: t₁[FK] ≠ ⊥ ⇒ ∃ t₂ ∈ R₂: t₂[PK] = t₁[FK]` | Забезпечення посилальної цілісності між таблицями. |

### Механіка роботи та крайові випадки базових обмежень

#### 1. Обмеження непорожності (NOT NULL)
Забороняє атрибуту набувати значення `NULL`. На фізичному рівні сторінкового зберігання СУБД (як-от PostgreSQL чи MySQL InnoDB) зберігає бітову маску наявності `NULL` у заголовку кожного рядка. Оголошення стовпця як `NOT NULL` дозволяє оптимізатору запитів спрощувати плани виконання, усувати непотрібні перевірки на невизначеність і зменшувати накладні витрати пам'яті.

#### 2. Обмеження перевірки (CHECK)
Задає предикат істинності для окремого стовпця або всього кортежу. Важлива тонкість стандарту SQL полягає у тризначній логіці: обмеження `CHECK` вважається виконаним, якщо вираз повертає `TRUE` або `UNKNOWN` (невизначеність), і порушується **виключно тоді, коли вираз явно обчислюється у `FALSE`**. Якщо поле містить `NULL`, вираз на кшталт `CHECK (age >= 18)` поверне `UNKNOWN`, і вставка буде дозволена. Якщо потрібно гарантувати обов'язковість перевірки, вираз обов'язково комбінують із `NOT NULL`.

Предикати `CHECK` мають бути суто детермінованими: у них заборонено використовувати підзапити до інших таблиць або недетерміновані функції поточного часу (як-от `NOW()` чи `RANDOM()`), оскільки зміна зовнішніх даних може заднім числом зробити існуючий рядок недійсним.

#### 3. Обмеження унікальності (UNIQUE)
Створює унікальний індекс на базі B-дерева. За стандартом SQL значення `NULL` вважається відсутністю значення, тому два значення `NULL` не дорівнюють одне одному (`NULL = NULL` повертає `UNKNOWN`). Унаслідок цього класичне обмеження `UNIQUE` дозволяє вставляти довільну кількість рядків із `NULL` у колонці.

Якщо бізнес-логіка вимагає вважати `NULL` окремим унікальним значенням (дозволяючи щонайбільше один порожній запис), у стандарті SQL:2023 та PostgreSQL 15+ використовують розширений синтаксис:
```sql
CONSTRAINT uq_tax_number UNIQUE NULLS NOT DISTINCT (tax_number);
```

#### 4. Первинний ключ (PRIMARY KEY)
Складається з комбінації `NOT NULL` та `UNIQUE`. У багатьох СУБД (наприклад, MySQL InnoDB або SQLite) первинний ключ визначає фізичний порядок розміщення даних у кластеризованому індексі (Clustered Index), де рядки таблиці зберігаються безпосередньо в листових вузлах B+ дерева.

## Специфікація посилальної цілісності (FOREIGN KEY)

Зовнішній ключ зв'язує дочірній запис `R₁` з батьківським записом `R₂`. При зміні або видаленні батьківського кортежу СУБД виконує задану посилальну дію (`Referential Action`).

```sql
FOREIGN KEY (child_column_1, child_column_2)
    REFERENCES parent_table (parent_column_1, parent_column_2)
    [ON DELETE { RESTRICT | NO ACTION | CASCADE | SET NULL | SET DEFAULT }]
    [ON UPDATE { RESTRICT | NO ACTION | CASCADE | SET NULL | SET DEFAULT }]
    [DEFERRABLE [INITIALLY DEFERRED | INITIALLY IMMEDIATE]]
```

### Детальна семантика посилальних дій

1. `RESTRICT` — СУБД негайно перевіряє наявність дочірніх записів і блокує операцію модифікації батьківського рядка до того, як виконаються будь-які тригери чи каскадні події. Це найсуворіший захист від випадкового пошкодження зв'язків.
2. `NO ACTION` — за замовчуванням діє подібно до `RESTRICT`. Проте якщо зовнішній ключ оголошено як `DEFERRABLE INITIALLY DEFERRED`, перевірка посилальної цілісності відкладається до моменту фіксації транзакції (`COMMIT`). Це критично необхідно для складних циклічних операцій — наприклад, коли таблиця `Department` має колонку `manager_id`, що посилається на `Employee`, а таблиця `Employee` має `department_id`, що посилається на `Department`.
3. `CASCADE` — автоматично поширює модифікацію на всі дочірні записи. При видаленні замовлення автоматично видаляються всі його позиції. Інженер повинен бути обережним із довгими ланцюжками каскадного видалення: видалення одного облікового запису користувача може неявно стерти мільйони пов'язаних журнальних записів, викликаючи тривале ексклюзивне блокування таблиць і вичерпання пулу блокувань пам'яті СУБД.
4. `SET NULL` — записує `NULL` у колонки зовнішнього ключа всіх дочірніх записів. Вимагає, щоб відповідні дочірні стовпці дозволяли значення `NULL` (не мали обмеження `NOT NULL`).
5. `SET DEFAULT` — встановлює значення за замовчуванням, визначене у директиві `DEFAULT` дочірнього стовпця (наприклад, перепризначає замовлення на системного користувача-бота).

### Крайові випадки складених зовнішніх ключів (MATCH Options)

Коли зовнішній ключ складається з двох або більше стовпців, виникає питання інтерпретації часткових значень `NULL` (коли одна колонка заповнена, а інша — `NULL`). Стандарт SQL визначає три режими зіставлення:

- `MATCH SIMPLE` (режим за замовчуванням у більшості СУБД): Якщо хоча б один стовпець складеного зовнішнього ключа містить `NULL`, уся перевірка зовнішнього ключа пропускається, і вставка дозволяється без перевірки існування батька за непорожніми стовпцями.
- `MATCH FULL`: Вимагає, щоб усі стовпці складеного ключа були або повністю заповнені валідними значеннями, що існують у батьківській таблиці, або всі без винятку містили `NULL`. Змішування заповнених колонок і `NULL` заборонене.
- `MATCH PARTIAL`: Дозволяє часткові `NULL`, але вимагає, щоб для непорожніх колонок існував хоча б один батьківський рядок, що збігається за цими атрибутами.

### Необхідність індексації зовнішніх ключів

Створення обмеження `FOREIGN KEY` автоматично створює індекс на батьківській таблиці (оскільки батьківський стовпець зобов'язаний бути `PRIMARY KEY` або `UNIQUE`). Проте реляційні СУБД **не створюють автоматично індекс на колонках зовнішнього ключа у дочірній таблиці**.

Якщо дочірній стовпець не проіндексовано вручну:
1. Будь-яка операція `DELETE` або `UPDATE` первинного ключа в батьківській таблиці вимагатиме повного послідовного сканування (Sequential Scan) усієї дочірньої таблиці для перевірки відсутності посилань.
2. Під час видалення батьківського рядка СУБД може накласти блокування на всю дочірню таблицю, паралізуючи паралельні операції запису інших транзакцій.
3. З'єднання `JOIN` між батьком і дочірньою таблицею будуть повільними через неможливість використання індексного пошуку (Index Scan).

Створення індексу на кожній колонці `FOREIGN KEY` є обов'язковим стандартом промислового проектування баз даних.

## Еталонна DDL-схема нормалізованої системи

Нижче наведено повну схему бази даних електронної комерції, спроектовану за вимогами третьої нормальної форми (3NF) з використанням усіх типів декларативних обмежень цілісності:

```sql
-- 1. Довідник категорій товарів
CREATE TABLE product_categories (
    category_id   INT GENERATED ALWAYS AS IDENTITY,
    category_code VARCHAR(32) NOT NULL,
    title         VARCHAR(128) NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_product_categories PRIMARY KEY (category_id),
    CONSTRAINT uq_categories_code UNIQUE (category_code)
);

-- 2. Каталог товарів
CREATE TABLE products (
    product_id    INT GENERATED ALWAYS AS IDENTITY,
    category_id   INT NOT NULL,
    sku           VARCHAR(64) NOT NULL,
    name          VARCHAR(255) NOT NULL,
    unit_price    NUMERIC(12, 2) NOT NULL,
    is_active     BOOLEAN NOT NULL DEFAULT TRUE,

    CONSTRAINT pk_products PRIMARY KEY (product_id),
    CONSTRAINT uq_products_sku UNIQUE (sku),
    CONSTRAINT fk_products_category FOREIGN KEY (category_id)
        REFERENCES product_categories (category_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE,
    CONSTRAINT chk_products_price CHECK (unit_price >= 0.00)
);

-- Індекс на зовнішній ключ для швидких операцій видалення та з'єднання
CREATE INDEX idx_products_category_id ON products (category_id);

-- 3. Клієнти
CREATE TABLE customers (
    customer_id   INT GENERATED ALWAYS AS IDENTITY,
    email         VARCHAR(255) NOT NULL,
    first_name    VARCHAR(64) NOT NULL,
    last_name     VARCHAR(64) NOT NULL,
    city          VARCHAR(128) NOT NULL,
    phone         VARCHAR(32),

    CONSTRAINT pk_customers PRIMARY KEY (customer_id),
    CONSTRAINT uq_customers_email UNIQUE (email),
    CONSTRAINT chk_customers_email_format CHECK (email LIKE '%_@__%.__%')
);

-- 4. Замовлення (Заголовок замовлення)
CREATE TABLE orders (
    order_id      BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id   INT NOT NULL,
    order_status  VARCHAR(24) NOT NULL DEFAULT 'PENDING',
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_orders PRIMARY KEY (order_id),
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE,
    CONSTRAINT chk_orders_status CHECK (
        order_status IN ('PENDING', 'PAID', 'SHIPPED', 'CANCELLED')
    )
);

CREATE INDEX idx_orders_customer_id ON orders (customer_id);

-- 5. Позиції замовлення (Деталі замовлення)
CREATE TABLE order_items (
    order_id      BIGINT NOT NULL,
    product_id    INT NOT NULL,
    quantity      INT NOT NULL DEFAULT 1,
    actual_price  NUMERIC(12, 2) NOT NULL,

    CONSTRAINT pk_order_items PRIMARY KEY (order_id, product_id),
    CONSTRAINT fk_order_items_order FOREIGN KEY (order_id)
        REFERENCES orders (order_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id)
        REFERENCES products (product_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE,
    CONSTRAINT chk_order_items_qty CHECK (quantity > 0),
    CONSTRAINT chk_order_items_price CHECK (actual_price >= 0.00)
);

CREATE INDEX idx_order_items_product_id ON order_items (product_id);
```

## Інваріанти збереження історії цін

Зверніть увагу на атрибут `order_items.actual_price`: на перший погляд це може здатися надлишковим дублюванням вартості `products.unit_price`. Проте з точки зору семантики предметної області це два абсолютно різні атрибути:
- `products.unit_price` — це поточна пропозиція ціни в каталозі товарів, яка може вільно змінюватися адміністратором щодня.
- `order_items.actual_price` — це зафіксований історичний юридичний факт фінансової транзакції на момент підтвердження замовлення.

Якби схема брала ціну виключно через `JOIN` із таблицею `products`, будь-яка майбутня зміна вартості товару в каталозі спотворила б фінансові звіти компанії за попередні роки, змінивши загальну суму минулих замовлень. Збереження історичного знімка ціни у рядку замовлення є строго коректним рішенням, яке не порушує правил 3NF і забезпечує бізнес-цілісність системи.
