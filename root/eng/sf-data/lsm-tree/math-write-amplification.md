# 🧮 Аналіз Write Amplification Factor (WAF) та математика Compaction у LSM-деревах

У базах даних та системах збереження даних вибір структури індексації визначається не просто часовою складністю за нотацією O(1) чи O(log N), а жорсткими фізичними компромісами між пропускною здатністю запису, швидкодією читання та накладними витратами дискової пам'яті.

---

## 1. Коефіцієнт підсилення запису (WAF) та трилема RUM

Головною метрикою ефективності роботи дискової системи є **коефіцієнт підсилення запису** (**Write Amplification Factor, WAF**). Він виражає відношення загального обсягу даних, фактично записаного на накопичувач, до обсягу даних, який надіслав застосунок:

```
        Загальний обсяг даних, записаних на диск (байти)
WAF = ───────────────────────────────────────────────────────
       Обсяг корисних даних, надісланих користувачем (байти)
```

Якщо користувач записує ключ-значення розміром 100 байтів, а база даних у результаті перезапису сторінок та журналювання скидає на диск 2000 байтів, WAF дорівнює:

```
WAF = 2000 / 100 = 20
```

Високий WAF створює три фундаментальні проблеми:
1. **Знижує пропускну здатність запису (Write Throughput):** Якщо фізична швидкість SSD становить 500 MB/s, а WAF = 20, реальна швидкість збереження користувацьких даних не перевищить `500 / 20 = 25 MB/s`.
2. **Прискорює знос SSD:** Флеш-осередки витримують фіксовану кількість циклів стирання (P/E cycles). При WAF = 20 термін служби накопичувача скорочується у 20 разів.
3. **Створює процесорні затримки (CPU overhead):** Процес ущільнення (Compaction) вимагає постійного сортування та десеріалізації даних у фонових потоках.

### Трилема RUM (RUM Conjecture)

Відповідно до гіпотези RUM (**Read / Update / Memory Space Conjecture**, Athanassoulis et al.), жодна структура даних не може одночасно мінімізувати всі три метрики. Ви завжди обираєте компроміс між трьома параметрами:

```
                     Оновлення (Update / WAF)
                              / \
                             /   \
                            /     \
                           /  RUM  \
                          /   три-  \
                         /    лема   \
                        /             \
                       /_______________\
   Читання (Read Amp)                    Пам'ять (Space Amp)
```

* **B-дерева** оптимізують **Read Amp** (читання точного ключа вимагає O(log N) I/O) та **Space Amp** (немає дублікатів ключів), але мають катастрофічний **Update WAF** (перезапис цілої 4 KB сторінки заради зміни 10 байтів дає WAF ≈ 400).
* **LSM-дерева** оптимізують **Update WAF** (записи спочатку групуються в RAM і скидаються послідовно), платячи за це вищим **Read Amp** або **Space Amp** залежно від обраного алгоритму ущільнення (**Compaction**).

## 2. Математика ущільнення Size-Tiered (STCS)

У стратегії **Size-Tiered Compaction Strategy (STCS)** файли накопичуються на диску в рамках одного рівня, поки їхня кількість не досягне порога N (зазвичай N = 4). Після цього всі N файлів подібного розміру зливаються методом **Merge-Sort** в один новий файл, який є у N разів більшим і переходить на наступний рівень.

```
Рівень 0:  [10 MB] [10 MB] [10 MB] [10 MB]  ──> Злиття (Compaction)
                                 │
                                 ▼
Рівень 1:                    [40 MB]
```

### Математичний вивід WAF для STCS

Нехай розмір MemTable дорівнює M, поріг кількості файлів на рівні дорівнює N, а загальний обсяг даних у базі дорівнює D.

Кількість рівнів у системі визначається логарифмічною глибиною:

```
L = log_N (D / M)
```

Оскільки на кожному рівні кожен байт даних бере участь у злитті точно 1 раз під час переходу на наступний рівень, загальний WAF запису на диск дорівнює кількості рівнів плюс 1 (початкове скидання з MemTable):

```
WAF_STCS = 1 + L = 1 + log_N (D / M)
```

### Накладні витрати пам'яті та читання у STCS

1. **Коефіцієнт підсилення простору (Space Amplification):**
   Під час злиття N файлів розміром S кожен, система змушена тримати на диску як старі N файлів, так і новий файл розміром N · S, поки злиття не завершиться. 
   
   ```
   Space_Amp_STCS ≈ 100%  (необхідно до 50% вільного місця на диску)
   ```

2. **Коефіцієнт підсилення читання (Read Amplification):**
   Оскільки файли на одному рівні мають діапазони ключів, що перетинаються, при пошуку відсутнього ключа доводиться перевіряти кожен файл на кожному рівні:
   
   ```
   Read_Amp_STCS = N · L = N · log_N (D / M)
   ```

## 3. Математика ущільнення Levelled (LCS)

У стратегії **Levelled Compaction Strategy (LCS)** (яка використовується в LevelDB та RocksDB за замовчуванням) кожен рівень L_k має суворо обмежений максимальний обсяг:

```
Capacity(L_k) = M · T^k
```

де T — коефіцієнт зростання (Fan-out factor, зазвичай T = 10), а M — розмір рівня L₁ (наприклад, 10 MB).

На відміну від STCS, файли на рівнях L₁, L₂, ..., L_k **не мають перетинів у діапазонах ключів**. Файли розбиті на фіксовані блоки (наприклад, по 64 MB), і їхні ключі відсортовані строго послідовно від першого до останнього файлу рівня.

```
Рівень L1 (10 MB):   [1..30] [31..60] [61..90]   (неперетинні діапазони)
                       │
                       ▼ Compaction (злиття з L2)
Рівень L2 (100 MB):  [1..15] [16..30] [31..45] [46..60] ...
```

### Математичний вивід WAF для LCS

Коли рівень L_k перевищує свій ліміт обсягу, алгоритм обирає 1 файл розміром S із рівня L_k і зливає його з файлами рівня L_{k+1}, чиї діапазони ключів перетинаються з обраним файлом.

Оскільки коефіцієнт зростання між рівнями дорівнює T, один файл із рівня L_k у середньому перетинається з T файлами на рівні L_{k+1}. Отже, під час злиття одного файлу система змушена перечитати й переписати T файлів наступного рівня!

При загальній кількості рівнів L = log_T (D / M) загальний WAF для Levelled Compaction становить:

```
WAF_LCS ≈ 1 + T · L = 1 + T · log_T (D / M)
```

Зауважте: оскільки T = 10, параметр T · log_T (D / M) дає значно вищий WAF, ніж у STCS!

### Переваги LCS: Низькі Read Amp та Space Amp

Чому ж використовують LCS, якщо його WAF вищий? Відповідь полягає в мінімізації читання та економії диска:

1. **Коефіцієнт підсилення читання (Read Amplification):**
   Оскільки на кожному рівні L₁ ... L_k діапазони ключів не перетинаються, шуканий ключ може перебувати **максимум в одному файлі** на кожному рівні!
   
   ```
   Read_Amp_LCS = 1 (у MemTable) + Num_Files(L_0) + L
   ```
   Завдяки фільтрам Блума кількість звернень до диска при точковому `GET` знижується практично до 1 ... 2 дискових I/O.

2. **Коефіцієнт підсилення простору (Space Amplification):**
   Оскільки ущільнення відбувається точково (один файл розміром S зливається з T файлами наступного рівня), максимальне тимчасове перевищення обсягу становить лише частку останнього рівня:
   
   ```
   Space_Amp_LCS ≈ 1 / T ≈ 10%  (при T = 10)
   ```

## 4. Порівняльна таблиця та розрахований worked-приклад

Порівняємо математичні характеристики двох методів ущільнення та B-дерева:

| Метрика / Стратегія | B-tree (In-place) | Size-Tiered (STCS) | Levelled (LCS, T=10) |
| :--- | :--- | :--- | :--- |
| **Write Amplification (WAF)** | ≈ 100 ... 400 | 1 + log_N (D/M) (Низький ≈ 4 ... 8) | 1 + T · log_T (D/M) (Середній ≈ 10 ... 30) |
| **Read Amplification (Uncached)** | O(log_B N) ≈ 3 ... 4 I/O | N · log_N (D/M) (Високий ≈ 20 ... 40) | 1 + L_0 + log_T (D/M) (Низький ≈ 2 ... 5) |
| **Space Amplification** | ≈ 33% ... 50% | ≈ 100% (Потрібно 2× диска) | ≈ 10% (Потрібно 1.1× диска) |
| **Головне призначення** | OLTP з переважанням читання | Високонавантажений запис (Logs, IoT) | Збалансовані Key-Value бази |

### Worked-приклад: Обчислення WAF та терміну служби SSD

**Умова:**
База даних обсягом D = 100 GB працює на LSM-дереві з Levelled Compaction (T = 10). Розмір MemTable M = 64 MB. Застосунок генерує інтенсивний потік запису 20 MB/s корисних даних 24/7. Накопичувач — NVMe SSD ємністю 1 TB із гарантованим ресурсом TBW = 600 TB (Terabytes Written).

**Крок 1. Обчислимо кількість рівнів у LSM-дереві:**

```
D / M = 100 GB / 0.064 GB = 1562.5

L = ceil(log_10 (1562.5)) = ceil(3.19) = 4 рівні
```

**Крок 2. Обчислимо теоретичний WAF для Levelled Compaction:**

```
WAF_LCS ≈ 1 + T · L = 1 + 10 · 4 = 41
```

*(У реальних умовах завдяки частковому перетину діапазонів середня кількість злитих файлів становить близько 15–25, тому приймемо практичний WAF = 20).*

**Крок 3. Обчислимо реальний фізичний потік запису на SSD:**

```
Фізичний потік = 20 MB/s × WAF = 20 MB/s × 20 = 400 MB/s
```

**Крок 4. Розрахуємо щоденний обсяг записаних даних на SSD:**

```
Денний запис = 400 MB/s × 86 400 с = 34 560 000 MB/день ≈ 34.56 TB/день
```

**Крок 5. Обчислимо час до повного фізичного зносу SSD:**

```
Термін служби = TBW / Денний запис = 600 TB / 34.56 TB/день ≈ 17.36 днів!
```

**Висновок і практичне рішення:**
При невдалому виборі параметрів ущільнення та високому WAF = 20 інтенсивний запис здатний повністю знищити ресурс накопичувача менше ніж за місяць! 

Для оптимізації інженер здатний встановити більший розмір MemTable (M = 256 MB), увімкнути стиснення LZ4/ZSTD перед дампом, або переключити ущільнення гарячого рівня L₀ → L₁ на Size-Tiered (Dynamic Level Strategy), що знизить WAF до значення 5 ... 7 і подовжить термін служби SSD до року.
