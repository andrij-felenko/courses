# 📋 Специфікація інтерфейсу BBM: регістри ONFI, зміщення OOB та дескриптори Linux MTD

Цей довідник містить точні структури даних, зміщення байтів у службовій зоні (OOB), бітові маски регістрів стану апаратного інтерфейсу ONFI, системні структури та функції ядра Linux, а також низькорівневі системні виклики `ioctl`, що використовуються для реалізації та діагностики підсистеми управління бракованими блоками (BBM).

---

### 1. Регістр стану ONFI (Status Register, команда 0x70)

Після надсилання будь-якої операції програмування сторінки (`0x80 ... 0x10`) або стирання блоку (`0x60 ... 0xD0`) контролер опитує регістр стану за допомогою команди `0x70` (Read Status). Опитування виконується на апаратній шині до моменту, поки мікросхема не підтвердить готовність внутрішнього автомата станів (FSM).

| Біт | Назва | Призначення | Значення при збої (Fault) |
|---|---|---|---|
| 0 | `FAIL` (або `FAIL_C`) | Результат виконання останньої операції (Program / Erase) | `1` — операція зазнала невдачі (помилка запису чи стирання) |
| 1 | `FAIL_N` | Результат передостанньої операції (для конвеєрних операцій) | `1` — попередня операція завершилася збоєм |
| 2–4 | *Reserved* | Зарезервовано стандартом ONFI | `0` |
| 5 | `ARDY` | Готовність масиву комірок (Array Ready) | `0` — масив зайнятий внутрішнім перенесенням заряду |
| 6 | `RDY` | Загальна готовність чипа (Ready / Busy#) | `0` — мікросхема виконує команду, `1` — готова до нової команди |
| 7 | `WP_N` | Стан апаратного захисту від запису (Write Protect) | `0` — запис апаратно заборонено (вивід WP# заземлений) |

Якщо біт 0 (`FAIL`) встановлений у `1` після операції стирання, блок підлягає негайному виведенню з експлуатації як динамічно дефектний (Grown Bad Block). Якщо біт 0 встановлений у `1` після програмування сторінки, дані з незавершеного блоку евакуюються у новий фізичний блок, а поточний блок маркується як дефектний.

#### Апаратна послідовність стирання та опитування стану:

```
[Хост]  ── 0x60 (Erase Setup) ──>  [NAND]
[Хост]  ── Адреса рядка (Row) ──>  [NAND]
[Хост]  ── 0xD0 (Erase Exec)  ──>  [NAND]  ──> (Високовольтний цикл стирання tBERS ≈ 2–5 мс)
[Хост]  ── 0x70 (Read Status) ──>  [NAND]
[Хост]  <── Байт статусу (SR) ──  [NAND]
        [Перевірка: SR & 0x01 == 0 ? УСПІХ : ЗБІЙ СТИРАННЯ]
```

Типові часові характеристики за специфікацією ONFI:
- `tBERS` (Block Erase Time): 2.0–5.0 мс. Перевищення ліміту свідчить про деградацію тунельного оксиду.
- `tPROG` (Page Program Time): 300–800 мкс для SLC; 1.2–2.5 мс для TLC/QLC.
- `tR` (Page Read Time): 25–40 мкс для SLC; 60–120 мкс для TLC/QLC.

### 2. Таблиця параметрів ONFI (ONFI Parameter Page, команда 0xEC)

Для автоматичного визначення геометрії чипа, лімітів браку та вимог до ECC контролер зчитує 256-байтну таблицю параметрів за допомогою команди `0xEC`. Байти містять критичні для BBM константи:

| Зміщення (Bytes) | Назва поля | Тип даних | Опис значення для драйвера BBM |
|---|---|---|---|
| 0–3 | `Signature` | `char[4]` | Магічні символи `"ONFI"` (`0x4F, 0x4E, 0x46, 0x49`) |
| 32–35 | `BytesPerPage` | `uint32_t` | Кількість байтів даних у сторінці (наприклад, 4096) |
| 36–37 | `SpareBytesPerPage` | `uint16_t` | Розмір області OOB на сторінку (наприклад, 224) |
| 40–43 | `PagesPerBlock` | `uint32_t` | Кількість сторінок у фізичному блоці (наприклад, 64 або 128) |
| 44–47 | `BlocksPerLUN` | `uint32_t` | Кількість фізичних блоків на один логічний кристал (LUN) |
| 105–106 | `MaxBadBlocksPerLUN` | `uint16_t` | Гарантований виробником максимум заводського браку на LUN |
| 112 | `ReqECCBits` | `uint8_t` | Мінімальна виправна здатність ECC на сектор 512 байтів |

Значення `MaxBadBlocksPerLUN` є основою для визначення мінімального розміру резервного пулу при ініціалізації накопичувача. Якщо драйвер виділить менше блоків, ніж зазначено в цьому полі, виробник анулює гарантію надійності зберігання даних.

### 3. Багатоплощинні операції та правила ізоляції дефектів (Multi-Plane BBM)

Сучасні мікросхеми високої щільності поділяють фізичний кристал на дві або чотири незалежні площини (Planes). Це дозволяє виконувати паралельні операції читання, запису та стирання (Multi-Plane Operations).

Правила обробки дефектів у багатоплощинних масивах:
1. **Ізоляція на рівні площини:** Якщо блок 42 у площині 0 (Plane 0) є дефектним, відповідний йому за адресою блок 42 у площині 1 (Plane 1) може залишатися повністю справним.
2. **Обмеження зв'язаних операцій (Super-Block Mode):** Якщо драйвер використовує концепцію суперблоків (об'єднання однойменних блоків усіх площин в один логічний суперблок для прискорення запису), вихід із ладу блоку хоча б в одній площині вимагає або виведення всього суперблоку, або застосування динамічного ремапінгу всередині відповідної площини.
3. **Окремі байти статусу площин:** Під час паралельного стирання двох площин біт 0 регістру стану відображає результат для поточної активної площини, а додаткова розширена команда читання стану `0x78` повертає індивідуальні прапорці `FAIL` для кожної площини окремо.

### 4. Зміщення маркера браку в області Spare (OOB)

Виробники мікросхем NAND записують заводський маркер дефекту у виділені байти службової зони (Spare Area). Значення `0xFF` означає справний блок; будь-яке значення, відмінне від `0xFF` (найчастіше `0x00`), свідчить про заводський брак.

| Тип архітектури NAND | Розмір сторінки (Main + OOB) | Номери сторінок для перевірки | Зміщення маркера в OOB (Offset) | Виробники / Стандарти |
|---|---|---|---|---|
| Small-Page (застарілі) | 512 + 16 байтів | Сторінка 0 | Байт 5 (зміщення `0x05` в OOB, `517` від початку сторінки) | Samsung, Toshiba (SLC 512B) |
| Small-Page (альтернативні) | 512 + 16 байтів | Сторінка 0 або 1 | Байт 0 (зміщення `0x00` в OOB, `512` від початку сторінки) | Micron, Hynix (SLC 512B) |
| Large-Page (стандартні) | 2048 + 64 байти | Сторінки 0 та 1 | Байт 0 (зміщення `0x00` в OOB, `2048` від початку сторінки) | ONFI 1.0+, Micron, Toshiba, Kioxia |
| Large-Page (підвищена місткість) | 4096 + 128/224 байти | Сторінки 0, 1 та остання (`N-1`) | Байт 0 (зміщення `0x00` в OOB, `4096` від початку сторінки) | Samsung MLC/TLC, SK Hynix |
| Advanced 3D NAND | 8192/16384 + OOB | Сторінка 0 та остання сторінка блоку | Байт 0 першої площини (Plane 0) | Сучасні TLC/QLC масиви |

#### Розподіл службових байтів усередині Spare Area (Layout):
Область OOB розміром 224 байти для сторінки 4096 байтів розділяється на функціональні зони:
- **Байти 0–1:** Маркер бракованого блоку (Bad Block Marker).
- **Байти 2–31:** Метадані файлової системи (UBI EC Header або JFFS2 cleanmarker).
- **Байти 32–223:** Паритетні коди апаратного блоку корекції помилок ECC (BCH 16-bit або LDPC).

### 5. Формат бітової карти BBT у пам'яті (2 біти на блок)

Для мінімізації споживання оперативної пам'яті таблиця дефектів кодується у вигляді компактного бітового масиву, де стан кожного фізичного блоку визначається парою бітів.

| Двійкове значення (`bits[1:0]`) | Шістнадцятковий код | Стан фізичного блоку | Опис та правила обробки |
|---|---|---|---|
| `00b` | `0x0` | **Factory Bad Block** | Заводський брак, виявлений під час первинного сканування OOB. Блок назавжди ізольовано від розподільника. |
| `01b` | `0x1` | **Reserved / Inactive** | Блок зарезервовано для зберігання самої таблиці BBT або службових метаданих FTL. |
| `10b` | `0x2` | **Grown Bad Block** | Експлуатаційний збій (помилка стирання, збій запису, знос діелектрика). Блок виведено з пулу. |
| `11b` | `0x3` | **Good Block** | Повністю справний блок, доступний для читання, запису та стирання підсистемою FTL/UBI. |

Для накопичувача на 4096 фізичних блоків розмір таблиці становить:

```
Розмір BBT = (4096 блоків × 2 біти) ÷ 8 біт/байт = 1024 байти (1 КБ)
```

Формула доступу до бітів блоку `B`:
- Байт у масиві: `byte_index = B / 4`
- Бітовий зсув у байті: `bit_offset = (B % 4) * 2`
- Маска стану: `state = (bbt_array[byte_index] >> bit_offset) & 0x03`

### 6. Системні структури дескриптора BBT (Linux MTD та C++ еквівалент)

У підсистемі Linux MTD апаратний опис таблиці BBT на флеш-носії задається структурою `nand_bbt_descr`. Нижче наведено визначення мовою C та ідіоматичний C++ еквівалент з типізованими прапорцями.

:::tabs
```c
#include <stdint.h>

#define NAND_MAX_CHIPS        8
#define NAND_BBT_USE_FLASH    0x00020000
#define NAND_BBT_NO_OOB       0x00040000
#define NAND_BBT_SCANALLPAGES 0x00000400
#define NAND_BBT_VERSION      0x00000020
#define NAND_BBT_CREATE       0x00000001

struct nand_bbt_descr {
    int      options;                      // Бітові прапорці конфігурації
    int      pages[NAND_MAX_CHIPS];        // Номери сторінок, де збережено BBT
    int      offs;                         // Зміщення сигнатури або даних у сторінці
    int      veroffs;                      // Зміщення байта версії
    uint8_t  version[NAND_MAX_CHIPS];      // Поточна версія таблиці
    int      len;                          // Довжина сигнатури
    int      maxblocks;                    // Кількість блоків від кінця кристала
    char     *pattern;                     // Магічний патерн ("Bbt0" / "1tbB")
};
```
```cpp
#include <cstdint>
#include <string_view>
#include <array>

namespace mtd {

enum class BbtOption : uint32_t {
    CreateOnDemand = 0x00000001,
    StoreVersion   = 0x00000020,
    ScanAllPages   = 0x00000400,
    UseFlashMemory = 0x00020000,
    StoreInMainArea= 0x00040000
};

constexpr uint32_t operator|(BbtOption a, BbtOption b) noexcept {
    return static_cast<uint32_t>(a) | static_cast<uint32_t>(b);
}

template <size_t MaxChips = 8>
struct NandBbtDescriptor {
    uint32_t                      options{0};
    std::array<int32_t, MaxChips> pages{};
    int32_t                       offset{0};
    int32_t                       versionOffset{0};
    std::array<uint8_t, MaxChips> version{};
    int32_t                       patternLength{4};
    int32_t                       maxSearchBlocks{4};
    std::string_view              pattern{"Bbt0"};
};

} // namespace mtd
```
:::

#### Ключові прапорці конфігурації (`options`):

- `NAND_BBT_USE_FLASH` (`0x00020000`): вимагає збереження таблиці BBT у постійній флеш-пам'яті замість повторного сканування OOB під час кожного старту системи.
- `NAND_BBT_NO_OOB` (`0x00040000`): таблиця BBT записується безпосередньо в основну область даних сторінки (Main Area), а не в OOB.
- `NAND_BBT_SCANALLPAGES` (`0x00000400`): перевіряти маркер браку на всіх сторінках блоку під час побудови первинної карти.
- `NAND_BBT_VERSION` (`0x00000020`): зберігати 8-бітний лічильник версій поряд із сигнатурою для вирішення колізій при раптовому вимиканні живлення.
- `NAND_BBT_CREATE` (`0x00000001`): автоматично створити та записати таблицю BBT на флеш, якщо вона відсутня.

#### Магічні сигнатури для парної схеми захисту (Primary / Mirror):

- **Основна таблиця (Primary BBT):** сигнатура `"Bbt0"` (ASCII `0x42, 0x62, 0x74, 0x30`), зміщення `offs = 0`.
- **Дзеркальна таблиця (Mirror BBT):** сигнатура `"1tbB"` (ASCII `0x31, 0x74, 0x62, 0x42`), зміщення `offs = 0`.

### 7. Програмний інтерфейс Linux MTD та ioctl простору користувача

Підсистема MTD ядра Linux експортує набір внутрішніх функцій для драйверів та викликів `ioctl` для системних утиліт простору користувача:

| Виклик ядра або `ioctl` | Параметри | Призначення та повертане значення |
|---|---|---|
| `mtd_block_isbad()` | `(struct mtd_info *mtd, loff_t ofs)` | Повертає `1`, якщо блок за зміщенням `ofs` є дефектним; `0`, якщо справний; `< 0` при помилці введення-виведення. |
| `mtd_block_markbad()` | `(struct mtd_info *mtd, loff_t ofs)` | Маркує фізичний блок як дефектний, оновлює бітову карту BBT у RAM та записує оновлену таблицю на Flash. Повертає `0` або `-EIO`. |
| `MEMGETBADBLOCK` | `ioctl(fd, MEMGETBADBLOCK, &offset)` | Перевіряє статус фізичного блоку за байтовим зміщенням `offset` із простору користувача. Повертає `0` (good), `1` (bad) або `-1`. |
| `MEMSETBADBLOCK` | `ioctl(fd, MEMSETBADBLOCK, &offset)` | Примусово вносить фізичний блок у таблицю дефектів як `Grown Bad` (використовується утилітами тестування надійності). |

Внутрішня синхронізація в ядрі гарантується м'ютексом `mtd->lock`, що запобігає стану гонитви між паралельними операціями збирання сміття та оновлення таблиці дефектів.

### 8. Діагностика через sysfs та утиліти простору користувача

У середовищі Linux стан дефектних блоків можна проінспектувати та протестувати за допомогою стандартних утиліт пакета `mtd-utils`:

```bash
# Перегляд переліку розділів MTD та розмірів блоків стирання
cat /proc/mtd

# Отримання детальної інформації про апаратні параметри NAND
mtdinfo /dev/mtd0

# Сканування дефектних блоків у розділі
nanddump --bb=dumpbad /dev/mtd0

# Форматування розділу зі збереженням заводських маркерів браку
flash_erase --jffs2 /dev/mtd0 0 0

# Ручне маркування блоку як збійного (для тестування відмовостійкості)
flash_erase --markbad /dev/mtd0 0x00400000
```

Ці засоби дозволяють системному інженеру повністю контролювати стан напівпровідникового масиву, діагностувати виникнення динамічних збоїв під час польових випробувань та верифікувати коректність конфігурації On-Flash BBT.
