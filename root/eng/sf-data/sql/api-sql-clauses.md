# 📋 Специфікація секцій та порядок виконання запитів SQL

Специфікація міжнародного стандарту ANSI/ISO SQL (ISO/IEC 9075) чітко розмежовує зовнішній синтаксичний порядок запису операторів мови та внутрішній логічний порядок їх обчислення рушієм бази даних. Розуміння цієї послідовності є обов'язковим для інженерів, оскільки саме логічний порядок визначає доступність стовпців, область видимості псевдонімів, поведінку предикатів фільтрації та коректність обчислення агрегатних виразів.

## Логічний конвеєр обчислення секцій вибірки (DQL)

У процесі виконання запиту `SELECT` вхідний набір даних послідовно проходить через десять логічних фаз трансформації. Кожна стадія приймає одне або кілька віртуальних відношень і повертає нове проміжне відношення для наступного кроку.

| Фаза | Секція SQL | Вхідний набір | Вихідний набір | Трансформація кардинальності | Дозволені вирази |
|---|---|---|---|---|---|
| 1 | `FROM & JOIN / ON` | Фізичні таблиці, подання, підзапити | Базове робоче відношення | Кардинальність: `|R₁ × R₂|` зі звуженням за умовою `ON` | Стовпці вихідних таблиць, предикати з'єднання |
| 2 | `WHERE` | Робоче відношення | Відфільтроване відношення | Кардинальність: `≤` попередньої | Скалярні предикати над рядками, підзапити (заборонено агрегати) |
| 3 | `GROUP BY` | Відфільтроване відношення | Множина груп кортежів | Згортання: `N → K` (де `K` — число унікальних ключів) | Стовпці групування, детерміновані вирази |
| 4 | `HAVING` | Згруповані кортежі | Відфільтровані групи | Кардинальність груп: `≤ K` | Агрегатні функції (`SUM`, `COUNT`, `AVG`), ключі `GROUP BY` |
| 5 | `WINDOW (OVER)` | Відфільтровані групи або рядки | Розширене відношення | Кардинальність не змінюється: `N → N` | Віконні функції (`ROW_NUMBER`, `RANK`, `LEAD`, `LAG`), партиції |
| 6 | `SELECT` | Проміжне відношення | Спроектоване відношення | Зміна арності схеми (кількості колонок) | Скалярні вирази, функції, псевдоніми (`AS alias`) |
| 7 | `DISTINCT` | Спроектоване відношення | Множина без дублікатів | Кардинальність: `≤` попередньої | Усі атрибути, визначені в секції `SELECT` |
| 8 | `UNION / EXCEPT` | Два сумісні набори | Об'єднане відношення | Множинне додавання або віднімання | Повна відповідність типів колонок у схемах |
| 9 | `ORDER BY` | Результуюче відношення | Впорядкований список | Кардинальність не змінюється | Псевдоніми з `SELECT`, стовпці `FROM`, порядкові номери |
| 10 | `LIMIT / OFFSET` | Впорядкований список | Зріз кортежів | Кардинальність: `min(limit, N - offset)` | Цілочислові константи або параметри зміщення |

## Семантичний контракт секцій запиту

### 1. `FROM`, `JOIN` та предикати `ON` проти `WHERE`

Секція `FROM` визначає множину джерел даних. Якщо вказано кілька таблиць без явного `JOIN` або з ключовим словом `CROSS JOIN`, рушій формує прямий Декартів добуток.

При використанні операторів зовнішнього з'єднання (`LEFT / RIGHT / FULL OUTER JOIN`) критично важливим є місце розташування умов фільтрації:

```sql
/* Варіант A: Умова в секції ON */
SELECT c.id, c.name, o.total
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id AND o.status = 'completed';

/* Варіант B: Умова в секції WHERE */
SELECT c.id, c.name, o.total
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'completed';
```

Механіка виконання обох варіантів кардинально відрізняється:
- **Умова в секції `ON` (Варіант A):** Обчислюється безпосередньо під час формування з'єднання. Якщо для клієнта немає замовлень зі статусом `'completed'`, клієнт все одно залишається в результуючому наборі, а поля таблиці `orders` (`o.total`, `o.status`) заповнюються маркерами `NULL`.
- **Умова в секції `WHERE` (Варіант B):** Обчислюється **після** завершення операції `LEFT JOIN`. Для клієнтів без замовлень поле `o.status` набуває значення `NULL`. Оскільки вираз `NULL = 'completed'` у тризначній логіці обчислюється як `unknown`, секція `WHERE` відкидає ці рядки. У результаті зовнішнє з'єднання фактично деградує до звичайного внутрішнього `INNER JOIN`, що спотворює бізнес-логіку вибірки.

### 2. `WHERE` та інваріанти предикатної фільтрації

Секція `WHERE` виконує порядкову фільтрацію базових кортежів. Вона підтримує порівняння скалярних значень (`=`, `<>`, `<`, `>`, `<=`, `>=`), перевірку входження в діапазон (`BETWEEN a AND b`), зіставлення зі списком (`IN (v1, v2, ...)`), пошук за шаблоном (`LIKE`, `ILIKE`, `SIMILAR TO`) та предикати існування підзапитів (`EXISTS`, `NOT EXISTS`, `IN (SELECT ...)`).

Головний інваріант фази `WHERE`: **жодна агрегатна функція не може бути виконана в секції `WHERE`**. Причина полягає в тому, що фільтрація `WHERE` відбувається на рівні індивідуальних кортежів до формування будь-яких груп чи накопичення проміжних сум.

### 3. `GROUP BY` та правила проекції атрибутів

Секція `GROUP BY` розбиває відфільтроване відношення на множину взаємно неперетинних груп за набором ключів групування. Після завершення групування індивідуальні рядки всередині групи втрачають пряму доступність.

**Інваріант стандарту SQL-92:** Будь-який стовпець, вказаний у секціях `SELECT`, `HAVING` або `ORDER BY`, мусить або входити до списку ключів `GROUP BY`, або бути параметром агрегатної функції (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `STRING_AGG`, `ARRAY_AGG`).

```sql
/* Некоректний запит (помилка компіляції за стандартом SQL-92) */
SELECT department_id, employee_name, AVG(salary)
FROM employees
GROUP BY department_id;

/* Коректний запит з агрегацією та групуванням */
SELECT department_id, COUNT(employee_name) AS staff_count, AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id;
```

*Виняток стандарту SQL:1999 (Правило функціональної залежності):* Якщо в секції `GROUP BY` вказано первинний ключ таблиці, у секції `SELECT` дозволено використовувати будь-які інші стовпці цієї ж таблиці без агрегації, оскільки вони функціонально повно залежать від первинного ключа.

### 4. `HAVING` проти `WHERE`: механіка фільтрації груп

Секція `HAVING` застосовує предикати фільтрації до сформованих груп після агрегації.
- Якщо предикат містить лише стовпці з `GROUP BY` (наприклад, `HAVING department_id = 10`), оптимізатор запитів автоматично проштовхує його в секцію `WHERE` (`Predicate Pushdown`), щоб скоротити кількість рядків до дорогої операції групування.
- Якщо предикат спирається на агрегатні обчислення (наприклад, `HAVING SUM(amount) > 10000` або `HAVING COUNT(*) >= 3`), він обчислюється суворо на фазі `HAVING`.

### 5. Специфікація віконних функцій (`OVER`)

Віконні функції виконують обчислення над множиною рядків (вікном), пов'язаних із поточним кортежем, без зменшення кардинальності вихідного набору:

```
функція() OVER (
    [PARTITION BY стовпець_партиції, ...]
    [ORDER BY стовпець_сортування [ASC | DESC], ...]
    [ROWS | RANGE | GROUPS віконна_рамка]
)
```

Специфікація віконної рамки (`Window Frame`) визначає діапазон рядків відносно поточного кортежу всередині поточної партиції:

```
{ ROWS | RANGE | GROUPS } BETWEEN <початок_рамки> AND <кінець_рамки>
```

Допустимі межі віконної рамки:
- `UNBOUNDED PRECEDING` — від першого рядка поточної партиції.
- `n PRECEDING` — `n` рядків (для `ROWS`) або діапазон значень `val - n` (для `RANGE`) перед поточним рядком.
- `CURRENT ROW` — поточний рядок (або група однакових значень для `RANGE`).
- `n FOLLOWING` — `n` рядків або діапазон значень після поточного рядка.
- `UNBOUNDED FOLLOWING` — до останнього рядка поточної партиції.

Якщо всередині секції `OVER` вказано `ORDER BY`, але рамку не задано явно, стандарт встановлює значення за замовчуванням: `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Це забезпечує накопичувальний підсумок (Running Total) від початку партиції до поточного значення сортування.

### 6. Секція `SELECT`, призначення псевдонімів та `DISTINCT`

Секція `SELECT` виконує фінальну проекцію атрибутів, обчислення скалярних математичних виразів, перетворення типів (`CAST(val AS type)`) та присвоєння псевдонімів стовпцям (`AS alias`).

Оператор `DISTINCT` виконує дедуплікацію отриманих кортежів. Для цього рушій СУБД або сортує вибірку за всіма спроектованими атрибутами, або будує тимчасову хеш-таблицю в пам'яті (`HashAggregate`), відкидаючи повторні входження.

### 7. Множинні операції: `UNION`, `INTERSECT`, `EXCEPT`

Стандарт SQL підтримує класичні операції над множинами результатів кількох незалежних блоків вибірки:
- `UNION` — об'єднання двох вибірок з автоматичним вилученням дублікатів.
- `UNION ALL` — конкатенація двох вибірок із збереженням усіх дублікатів (не вимагає сортування чи хешування, працює значно швидше).
- `INTERSECT` — знаходження спільних кортежів, присутніх в обох вибірках.
- `EXCEPT` (або `MINUS`) — знаходження кортежів, які присутні в першій вибірці, але відсутні в другій.

Вимоги до схем: обидва запити мусять мати однакову кількість стовпців, а типи даних відповідних позицій повинні бути сумісними за доменами.

### 8. `ORDER BY`, `LIMIT` та `OFFSET`

Секція `ORDER BY` є єдиним засобом гарантування порядку повернення рядків клієнту. Без явного `ORDER BY` реляційний рушій має право повертати кортежі в довільному порядку, який залежить від фізичного розташування сторінок на диску, порядку сканування індексів чи багатопотокового виконання.

Секція `LIMIT n OFFSET m` повертає зріз із `n` рядків, пропускаючи перші `m` записів. При великих значеннях зміщення (`OFFSET 1000000`) рушій змушений прочитати та відсортувати всі 1 000 000 рядків, перш ніж віддати наступні 10, що створює значне навантаження на підсистему пам'яті та процесор.

## Стандартні коди завершення SQLSTATE

Стандарт SQL-92 зафіксував єдину систему кодів завершення операцій через 5-символьний літерно-цифровий ідентифікатор `SQLSTATE`. Перші два символи вказують на загальний клас стану, останні три — на конкретний підклас.

| Клас SQLSTATE | Назва категорії | Типові коди та їх значення |
|---|---|---|
| `00` | Success | `00000` — Успішне завершення оператора |
| `01` | Warning | `01004` — Текстове значення обрізано праворуч (`string_data_right_truncation`) |
| `02` | No Data | `02000` — Курсор досяг кінця вибірки або запит повернув 0 рядків |
| `08` | Connection Exception | `08001` — Не вдалося встановити клієнтське з'єднання із сервером |
| `22` | Data Exception | `22012` — Спроба ділення на нуль (`division_by_zero`), `22001` — Переповнення рядкового поля |
| `23` | Integrity Violation | `23505` — Порушення унікальності (`unique_violation`), `23503` — Порушення зовнішнього ключа (`foreign_key_violation`), `23502` — Спроба запису NULL у поле NOT NULL |
| `40` | Transaction Rollback | `40P01` — Виявлено взаємне блокування (`deadlock_detected`), `40001` — Помилка серіалізації транзакцій |
| `42` | Syntax / Access Error | `42601` — Синтаксична помилка SQL, `42P01` — Таблицю не знайдено (`undefined_table`), `42703` — Стовпець не знайдено |
| `57` | Operator Intervention | `57014` — Запит скасовано за таймаутом або адміністратором (`query_canceled`) |
| `XX` | Internal Error | `XX000` — Внутрішня критична помилка сервера бази даних |

Використання стандартизованих кодів `SQLSTATE` дозволяє прикладним бібліотекам, драйверам з'єднань та ORM-системам реалізовувати надійну обробку помилок (наприклад, автоматичний повтор транзакції при отриманні коду `40001` або `40P01`) незалежно від конкретного виробника СУБД.
