# 📜 Еволюція розподілу читання й запису: від ручних SQL-скриптів Web 2.0 до LSN-проксі та безсерверних хмарних сховищ

Ідея розділення потоків зчитування та модифікації даних у базах даних виникла не як теоретична концепція комп'ютерних наук, а як вимушена реакція інженерів на вибухове зростання навантаження раннього інтернету. Наприкінці 1990-х років більшість веб-ресурсів функціонували за моделлю класичного клієнт-сервера: єдиний скрипт мовою Perl чи PHP відкривав TCP-з'єднання з єдиним екземпляром СКБД (найчастіше MySQL або PostgreSQL) і виконував усі SQL-запити через один дескриптор підключення. Поки сайти залишалися статичними візитками, обчислювальної потужності одного сервера вистачало.

Проте зародження епохи Web 2.0 докорінно змінило профіль навантаження. Сайти перетворилися на динамічні платформи для спілкування: блоги, форуми, дошки оголошень та перші новинні агрегатори. На кожну дію публікації нового коментаря чи статті припадало від 20 до 100 переглядів сторінок іншими читачами. У 2000 році співзасновники MySQL AB Девід Аксмарк (David Axmark) та Міхаель Віденіус (Michael Widenius) представили у версії MySQL 3.23.15 фундаментальну функцію — асинхронну реплікацію за бінарним журналом (binlog). Це дозволило мати один головний сервер (Master) для запису та один або кілька підпорядкованих серверів (Slave) для зняття резервних копій та виконання важких аналітичних вибірок.

Це відкриття породило нову інженерну проблему: застосунки тепер мусили самостійно вирішувати, який SQL-запит на який сервер відправляти. Наступні два десятиліття стали історією еволюції механізмів цієї маршрутизації — від примітивних розгалужень у вихідному коді застосунків до інтелектуальних безсерверних проксі-шарів, що оперують глобальними векторами транзакцій.

## Епоха ручних з'єднань: PHP, LiveJournal та MediaWiki (2000–2006)

Першим і найбільш очевидним рішенням було створення двох глобальних змінних підключення до бази даних безпосередньо у коді веб-застосунку. У типових кодових базах на PHP 4 чи Perl з'явилися конструкції виду `$dbh_master` та `$dbh_slave`.

```
                    ┌─────────────────────────┐
                    │     PHP-скрипт          │
                    │  $dbh_master = DB::W()  │
                    │  $dbh_slave  = DB::R()  │
                    └────┬───────────────┬────┘
      INSERT / UPDATE    │               │    SELECT
      через $dbh_master  │               │    через $dbh_slave
                         ▼               ▼
                  ┌────────────┐   ┌────────────┐
                  │ Master DB  │──►│  Slave DB  │
                  └────────────┘   └────────────┘
                                   Асинхронний binlog
```

У 2001 році Бред Фіцпатрік (Brad Fitzpatrick), творець популярної платформи блогів LiveJournal, зіткнувся з тим, що єдиний сервер бази даних не витримував напливу сотень тисяч користувачів. Фіцпатрік розробив власну бібліотеку абстракції `LJ::DB`, яка примусово направляла всі виклики `SELECT` на пули реплік, а `INSERT`, `UPDATE` та `DELETE` — на головний вузол. Одночасно аналогічну архітектуру впровадила команда MediaWiki для обслуговування Wikipedia: кожен запит веб-сервера аналізувався, і залежно від HTTP-методу (`GET` чи `POST`) фреймворк обирав відповідний дескриптор СКБД.

Цей наївний підхід швидко виявив критичні вади:
1. **Людський фактор та помилки розробників**: інженери часто забували змінювати дескриптор і випадково викликали `INSERT` через `$dbh_slave`. Якщо на репліці був увімкнений прапорець `read_only = 1`, запит падав із фатальною помилкою; якщо прапорець був вимкнений, репліка локально модифікувала свій стан, після чого реплікація з головного вузла ламалася через конфлікт первинних ключів.
2. **Аномалія читання власного запису (Read-Your-Own-Writes)**: користувач оновлював свій статус у блозі через `$dbh_master`, отримував успішну відповідь, браузер перенаправляв його на сторінку перегляду, яка надсилала `SELECT` до `$dbh_slave`. Через затримку реплікації в 200 мілісекунд репліка ще не встигала застосувати бінарний журнал, і користувач бачив свій старий статус, повторно натискаючи кнопку збереження.
3. **Вибух пулів підключень**: кожен процес Apache або PHP-FPM відкривав щонайменше два TCP-з'єднання (до Master і до Slave). При розгортанні сотень веб-серверів кількість підключень до СКБД сягала десятків тисяч, що призводило до вичерпання дескрипторів сокетів та пам'яті ядра операційної системи.

## Перші виділені проксі: mysql-proxy та Spock (2007–2012)

Усвідомивши, що логіка маршрутизації засмічує кодову базу застосунків і створює проблеми при зміні топології серверів, спільнота звернулася до ідеї проміжного мережевого проксі (Middleware / Database Proxy).

У 2007 році Ян Кнешке (Jan Kneschke), співробітник MySQL AB і творець веб-сервера Lighttpd, презентував проект `mysql-proxy`. Програма являла собою мережевий демон, який розміщувався між застосунками та кластером MySQL. `mysql-proxy` використовував інтерпретатор мови Lua для інспекції мережевих пакетів протоколу MySQL. Розробники могли написати скрипт на Lua, який аналізував перший токен SQL-запиту: якщо рядок починався зі слова `SELECT`, пакет перенаправлявся на пул Slave-серверів, а всі інші запити — на Master.

```lua
-- Ранній прототип маршрутизації у mysql-proxy (2007)
function read_query(packet)
    if packet:byte() == proxy.COM_QUERY then
        local query = packet:sub(2)
        if query:match("^%s*[Ss][Ee][Ll][Ee][Cc][Tt]") then
            proxy.connection.backend_ndx = 2 -- Slave Backend
        else
            proxy.connection.backend_ndx = 1 -- Master Backend
        end
    end
end
```

Одночасно інженери сервісу Spock розробили `Spock Proxy` — форк `mysql-proxy` з підтримкою базового шардингу та горизонтального розділення читання. Проте перше покоління SQL-проксі зазнало невдачі у високонавантажених системах через дві фундаментальні проблеми:
- **Низька продуктивність Lua-обробника**: інтерпретація Lua для кожного SQL-запиту створювала значний оверхед на процесор. Затримка обробки запитів (RTT) зростала на 2–5 мілісекунд, а пропускна здатність проксі впиралася в блокування інтерпретатора.
- **Втрата контексту сесій і транзакцій**: наївний парсинг рядків за першим словом ламав транзакційну цілісність. Якщо всередині транзакції `BEGIN ... COMMIT` застосунок виконував `SELECT`, проксі відправляв його на репліку, де зміни поточної транзакції були ще не зафіксовані. Крім того, змінні сесії (наприклад, `SET @user_id = 42`) встановлювалися на одному з'єднанні репліки, а наступний `SELECT` міг піти на іншу репліку, де ця змінна була відсутня.

## Поява промислових проксі: ProxySQL, MaxScale та Vitess (2013–2018)

У 2013–2015 роках відбувся якісний стрибок. Інженери відмовилися від скриптових інтерпретаторів на користь високооптимізованих системних мов C та C++ з використанням неблокуючого вводу-виводу на базі системних викликів `epoll` та `kqueue`.

У 2015 році Рене Каннао (René Cannaò), колишній DBA у Dropbox та PalominoDB, створив **ProxySQL**. Це був прорив у світі масштабування MySQL:
- Проксі отримав повноцінний парсер абстрактного синтаксичного дерева (AST), який розбивав запит на лексеми на нативній швидкості C++;
- Було впроваджено концепцію хостгруп (Hostgroups): Hostgroup 0 для запису (Writer) та Hostgroup 1 для читання (Reader);
- Реалізовано інтелектуальний пул з'єднань із мультиплексуванням: 10 000 клієнтських підключень транслювалися у 100 постійно відкритих швидких з'єднань із реальними серверами СКБД;
- Впроваджено правила маршрутизації за регулярними виразами, дайджестами запитів (Query Digest) та прапорцями транзакційного стану клієнта.

Паралельно компанія MariaDB Corporation розробила **MariaDB MaxScale** — модульний проксі з вбудованими плагінами маршрутизації (`ReadWriteSplit`), який умів автоматично відстежувати зміни ролей у кластері та блокувати виконання запитів під час автоматичного перемикання при відмовах (Failover).

Для надвеликих екосистем компанія Google відкрила вихідний код **Vitess** — системи, створеної у 2010 році для горизонтального масштабування бази даних YouTube. Vitess запропонував шар `VTGate` — stateless-проксі мовою Go, який брав на себе повне керування читанням, записом, шардингом та реплікаційними топологіями тисяч вузлів MySQL, роблячи весь розподілений кластер схожим на одну логічну СКБД.

## Перехід до причинної узгодженості: GTID та LSN (2013–2020)

Довгий час головним компромісом розподілу читання й запису залишалася нестабільність реплікаційного лагу. Якщо репліка відставала на кілька секунд через важке дискове навантаження, користувачі читали застарілі дані (Stale Reads).

Революція настала з появою строгих глобальних ідентифікаторів транзакцій:
1. **MySQL 5.6 (2013)** впровадив **GTID (Global Transaction Identifier)** — унікальний монотонний номер кожної зафіксованої транзакції у форматі `UUID:Sequence_Number`.
2. **PostgreSQL** стандартизував роботу з **LSN (Log Sequence Number)** — 64-бітним зміщенням у журналі випереджального запису (WAL).

Це дозволило реалізувати механізм **сесійної причинної узгодженості (Causal Consistency via Session Tokens)**:
- Коли клієнт виконує операцію запису, Primary повертає йому токен із зафіксованим номером `LSN_commit` (або `GTID_commit`);
- При наступному запиті на зчитування клієнт передає цей токен у заголовку запиту;
- Розумний маршрутизатор (або драйвер) запитує у репліки її поточний показник застосованого журналу (`Replica_Replay_LSN`);
- Якщо `Replica_Replay_LSN >= LSN_commit`, маршрутизатор безпечно відправляє запит на репліку, знаючи на 100%, що репліка містить щойно записані клієнтом дані;
- Якщо репліка відстає, маршрутизатор або короткочасно призупиняє виконання (`WAIT_FOR_EXECUTED_GTID_SET`), або перенаправляє читання на Primary.

Цей механізм повністю усунув аномалію Read-Your-Own-Writes, зберігши при цьому всі переваги розвантаження головного сервера.

## Сучасність: хмарні архітектури з розділенням обчислень і пам'яті (з 2014)

Останнім етапом еволюції став перехід від традиційної фізичної реплікації дисків до хмарних архітектур із розділенням обчислювального рівня (Compute Tier) та розподіленого сховища (Storage Tier).

```
   ┌────────────────────────────────────────────────────────────┐
   │            ТРАДИЦІЙНА РЕПЛІКАЦІЯ (Share-Nothing)          │
   │  Primary Server (CPU + SSD) ──[WAL мережею]──► Replica     │
   │  (Дублювання запису сторінок на кожен фізичний диск)       │
   └────────────────────────────────────────────────────────────┘
                                 ▼
   ┌────────────────────────────────────────────────────────────┐
   │           ХМАРНА ДЕКУПЛІНГ-АРХІТЕКТУРА (Shared Storage)    │
   │  Writer Node (CPU)          Reader Node 1    Reader Node 2 │
   │         │                         ▲                ▲       │
   │         ▼                         │                │       │
   │  ┌────────────────────────────────┴────────────────┴────┐  │
   │  │   Розподілене спільне сховище журналу (Log Engine)   │  │
   │  │       (Zero-Copy реплікація змін сторінок в RAM)     │  │
   │  └──────────────────────────────────────────────────────┘  │
   └────────────────────────────────────────────────────────────┘
```

У 2014 році Amazon Web Services представила **Amazon Aurora**. Головна інновація полягала у винесенні журналу транзакцій у спеціалізоване розподілене сховище:
- Primary-вузол більше не записує змінені сторінки даних (Data Pages) на диск і не надсилає важкі дампи реплікам; він лише передає потік записів redo log у спільний шар сховища;
- Усі Read-репліки Aurora читають дані з того самого спільного сховища, оновлюючи лише свій локальний кеш у пам'яті (Buffer Pool) на основі змін журналу;
- Лаг реплікації скоротився з сотень мілісекунд до 5–20 мілісекунд, а додавання нових Read-реплік стало миттєвим, оскільки їм більше не потрібно копіювати гігабайти фізичних файлів даних.

Слідом за Aurora аналогічні моделі впровадили Google Cloud (AlloyDB), Microsoft Azure (Hyperscale) та відкриті хмарні СКБД нового покоління (Neon, TiDB, CockroachDB). Розподіл читання й запису трансформувався з костиля над повільними дисками у фундаментальний закон організації сучасних хмарних систем зберігання даних.
