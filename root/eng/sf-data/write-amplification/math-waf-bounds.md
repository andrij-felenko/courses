# 🧮 Математичні моделі та виведення меж Write Amplification Factor

Підсилення запису (Write Amplification Factor, WAF) є результативом алгоритмічних і фізичних рішень щодо впорядкування даних на носіях із блоковою або сторінковою адресацією. Розуміння математичних меж WAF дозволяє проектувати системи зберігання з передбачуваною продуктивністю та розраховувати термін служби твердотільних накопичувачів. У цьому аналітичному розборі виведено точні математичні моделі та межі WAF для двох фундаментальних класів систем: контролерів флеш-пам'яті (FTL) та алгоритмів ущільнення в базах даних (LSM-Tree та B-Tree).

---

## 1. Математична модель WAF у накопичувачах NAND Flash (FTL GC)

Аналітичне моделювання збирання сміття у флеш-пам'яті спирається на аналіз імовірностей заповнення блоків стирання валідними та невалідними сторінками. 

Розглянемо накопичувач із загальною фізичною місткістю N сторінок, розділених на блоки стирання по B сторінок у кожному. Нехай логічний обсяг даних, доступний користувачу, становить U сторінок. Коефіцієнт додатково виділеного резервного простору (Over-Provisioning, OP) визначається відношенням вільного виділеного простору до користувацького:

```
OP = (N - U) / U
```

Коефіцієнт використання фізичного диска позначимо через u, який визначається відношенням корисного логічного обсягу до загальної фізичної місткості:

```
u = U / N = 1 / (1 + OP)
```

Припустимо, що система перебуває в усталеному режимі (steady-state), коли всі блоки містять суміш валідних та невалідних сторінок, а нові записи виконуються випадковим чином по всьому логічному простору. Ця концепція відома як узагальнена модель Бен-Ароя — Толедо (Ben-Aroya / Toledo model).

### Ждібне збирання сміття (Greedy Garbage Collection)

При ждібному алгоритмі (Greedy GC) контролер FTL для збирання сміття завжди обирає той блок, який містить найменшу кількість валідних сторінок (і, відповідно, найбільшу кількість невалідних сторінок). Якщо припустити рівномірний випадковий розподіл застарівання сторінок, середня частка валідних сторінок у вибраному віктимному блоці у найгіршому випадку не перевищує загальний коефіцієнт використання u.

Кількість валідних сторінок V у блоці розміром B становить:

```
V = B · u
```

Для звільнення одного блоку FTL повинен зчитати V валідних сторінок і скопіювати їх у новий порожній блок. Кількість нових сторінок даних від хоста W_host, які можна записати у звільнений блок, дорівнює залишковому порожньому місцю `W_host = B - V`. Підставляючи вираз для валідних сторінок `V = B · u`, виносимо спільний множник `B` за дужки:

```
W_host = B - V                  [різниця загального обсягу блоку B та валідних сторінок V]
       = B - B · u              [підстановка значення V = B · u]
       = B · (1 - u)            [винесення спільного множника B за дужки]
```

Загальна кількість сторінок, записаних на NAND Flash під час цієї операції (фізичний запис W_phys), складається з перенесених валідних сторінок V та нових хостових даних W_host. Підставляючи значення `V = B · u` та `W_host = B · (1 - u)`, отримуємо вираз фізичного запису:

```
W_phys = V + W_host             [сума перенесених валідних сторінок V та хостових даних W_host]
       = B · u + B · (1 - u)    [підстановка виразів V = B · u та W_host = B · (1 - u)]
       = B                      [розкриття дужок і спрощення суми: B · u + B - B · u = B]
```

Отже, коефіцієнт підсилення запису WAF обчислюється як відношення W_phys до W_host:

```
WAF = W_phys / W_host           [визначення WAF як відношення фізичних записів до хостових]
    = B / (B · (1 - u))         [підстановка виразів W_phys = B та W_host = B · (1 - u)]
    = 1 / (1 - u)               [вираження WAF через коефіцієнт використання u]
```

Замінивши коефіцієнт використання `u` через Over-Provisioning `OP` за формулою `u = 1 / (1 + OP)`, висловимо частку вільного простору `1 - u`. Заміна `1` на дріб `(1 + OP) / (1 + OP)` дозволяє звести вираз до спільного знаменника:

```
1 - u = 1 - 1 / (1 + OP)        [підстановка u = 1 / (1 + OP)]
      = (1 + OP) / (1 + OP) - 1 / (1 + OP) [представлення одиниці як (1 + OP) / (1 + OP)]
      = (1 + OP - 1) / (1 + OP) [зведення до спільного знаменника (1 + OP)]
      = OP / (1 + OP)           [спрощення чисельника: 1 + OP - 1 = OP]

WAF = (1 + OP) / OP             [підстановка виразу 1 - u = OP / (1 + OP) у формулу WAF = 1 / (1 - u)]
    = 1 + 1 / OP                [почленне ділення чисельника (1 + OP) на OP]
```

### Аналіз залежності WAF від Over-Provisioning

Математична залежність гіперболічно залежить від розміру резервного простору:

```
Over-Provisioning (OP)    Коефіцієнт u    WAF (Greedy GC)
-------------------------------------------------------
  7% (Типовий consumer)       0.935           15.3
 20% (Enterprise SSD)         0.833            6.0
 28% (High-write SSD)         0.781            4.6
 50% (Оптимізований)          0.667            3.0
100% (Половина диска)         0.500            2.0
```

Висновок з формули: при зменшенні Over-Provisioning з 28% до 7% WAF зростає нелінійно з 4.6 до 15.3. Це пояснює фізичну причину, чому заповнення SSD понад 90% призводить до катастрофічного падіння продуктивності запису та прискореного деградування осередків.

## 2. Математичні моделі ущільнення в LSM-деревах (Leveled vs Size-Tiered)

У базах даних типу RocksDB, LevelDB та Cassandra дані впорядковані на дисках за рівнями або tier-прошарками. Різні алгоритми ущільнення дають кардинально різні математичні оцінки WAF.

### Ампліфікація при Leveled Compaction (LCS)

У Leveled Compaction дані впорядковані за рівнями L_0, L_1, ..., L_k.
Нехай кожен рівень L_i має максимальний обсяг C_i, причому розміри сусідніх рівнів пов'язані коефіцієнтом розширення (fanout factor) T:

```
C_i = C_0 · Tⁱ
```

Типово T = 10 (рівень L_1 = 10 MB, L_2 = 100 MB, L_3 = 1 GB, L_4 = 10 GB).

Під час Leveled Compaction один SSTable-файл розміром S з рівня L_i зливається з перекритими файлами рівня L_(i+1). Оскільки діапазон ключів одного файлу на рівні L_i у найгіршому випадку перекриває до T файлів на рівні L_(i+1), обсяг даних, зчитаних з рівня L_(i+1), становить T · S.

Сумарний обсяг записаних даних при ущільненні між двома сусідніми рівнями дорівнює:

```
W_level = S + T · S = S · (1 + T) [факторизація за спільним множником S]
```

Оскільки вихідний файл мав розмір S, підсилення запису на один рівень становить:

```
WAF_level = W_level / S = 1 + T [скорочення S]
```

Загальний WAF для LSM-дерева глибиною L рівня за повної прокачки даних дорівнює:

```
WAF_LSM_leveled = WAF_flush + ∑ (WAF_level_i)   [сума ампліфікацій по всіх L рівнях]
                = 1 + L · T                      [підстановка WAF_level ≈ T для кожного рівня]
```

Для типових параметрів RocksDB (T = 10, L = 4):

```
WAF_LSM_leveled = 1 + 4 · 10 = 41               [обчислення для T=10, L=4]
```

### Ампліфікація при Size-Tiered Compaction (STCS)

У Size-Tiered Compaction (використовується в Apache Cassandra та RocksDB Universal Compaction) рівні містять N неперекритих файлів схожого розміру (типово N = 4). Коли на рівні накопичується N файлів, вони всі зливаються в один більший файл наступного прошарку.

Оскільки N файлів розміром S зливаються за один прохід, підсилення на один прошарок становить 1.0 (кожен елемент читається і пишеться один раз при злитті).

Загальний WAF для Size-Tiered Compaction при глибині прошарків L_st:

```
WAF_LSM_tiered = L_st = log_N (Total_Data / MemTable_Size)
```

Для N = 4 та обсягу даних, більшого за MemTable у 256 разів:

```
WAF_LSM_tiered = log_4 (256) = 4.0
```

Порівняння показує: Size-Tiered Compaction дає WAF = 4.0 проти WAF = 41.0 у Leveled Compaction, проте жертвує підсиленням простору (Space Amplification може сягати 100% тимчасового дублювання даних).

## 3. Порівняльний математичний аналіз B-Tree vs LSM-Tree

Розглянемо запис N записів розміром r байтів кожен (загальний логічний обсяг W_app = N · r). Нехай розмір дискової сторінки становить P байтів (наприклад, 4096 байтів або 16384 байти), причому розмір модифікації набагато менший за сторінку (r ≪ P, наприклад, r = 100 байтів, P = 4096 байтів).

### Випадковий запис у B-Tree (Random Writes)

У найгіршому випадку кожен випадковий запис потрапляє у випадкову сторінку B-дерева. Модифікація одного запису розміром r вимагає перезапису усієї сторінки P.

```
WAF_btree_rand = P / r [відношення розміру сторінки P до модифікації r]
```

Для r = 100 байтів та P = 4096 байтів:

```
WAF_btree_rand = 4096 / 100 = 40.96 [ділення сторінки на розмір запису]
```

Якщо СУБД додатково використовує Journaling / WAL (запис зміни в WAL розміром `r + w`, де `w` — заголовок журналу) та Doublewrite Buffer (дублювання всієї сторінки `P`), сумарний запис на операцію становить `P + P + r + w`. Оскільки `r, w ≪ P` (дрібні записи порівняно з розміром сторінки), сумою `r + w` у чисельнику можна знехтувати, що дає апроксимацію `(2 · P) / r`:

```
WAF_btree_full = (P + P + r + w) / r   [сумарний запис: 2 сторінки P (Doublewrite) + WAL (r + w)]
               = (2 · P + r + w) / r   [групування двох сторінок P + P = 2 · P]
               ≈ (2 · P) / r           [апроксимація: нехтування r + w ≪ P у чисельнику]
               = (2 · 4096) / 100      [підстановка числових значень P = 4096, r = 100]
               = 81.92                 [обчислення підсумкового відношення]
```

### Зведений підсумок меж WAF

```
Структура / Носій           Найкращий WAF    Типовий WAF    Найгірший WAF
-----------------------------------------------------------------------
B-Tree (Послідовний)            1.05             1.2            2.0
B-Tree (Випадковий 4 KB page)   5.0             40.0           100.0+
LSM-Tree (Size-Tiered)          2.0              4.0            8.0
LSM-Tree (Leveled, T=10, L=4)  10.0             25.0           41.0
SSD FTL (Sequential Write)      1.0              1.1            1.3
SSD FTL (Random Write, OP 7%)   2.0              8.0           15.3+
```

Висновок з порівняльного аналізу: LSM-Tree жертвує підсиленням запису під час ущільнення (WAF ≈ 10–30) заради перетворення випадкових записів хоста на послідовні дискові операції, що дозволяє SSD FTL працювати з мінімальним власним WAF ≈ 1.0–1.2.
