Коли високонавантажений сервіс із потоком у 25 000 запитів на секунду розгортає нову версію, і автоматичний скрипт виконує інструкцію `ALTER TABLE orders ADD COLUMN loyalty_points integer NOT NULL DEFAULT 0;` над таблицею на 80 мільйонів рядків, реляційне ядро негайно запитує монопольне блокування всієї таблиці (`AccessExclusiveLock`). Якщо в цей момент у системі виконується хоча б один фоновий аналітичний звіт тривалістю понад дві секунди, команда модифікації структури стає в чергу очікування. Ядро СУБД, прагнучи запобігти голодуванню операції зміни метаданих, блокує всі наступні операції читання та запису до цієї таблиці. За 800 мілісекунд пул з'єднань додатку на 500 підключень повністю вичерпується, черга вхідного трафіку переповнює буфери балансувальника, і вся платформа зазнає каскадного збою з кодами помилок HTTP 504.

Одночасно з цим спроба запустити виконання міграцій безпосередньо всередині точок входу сорока нових контейнерів додатку в кластері Kubernetes створює гонку за системний каталог. Кілька процесів одночасно намагаються перевірити наявність колонок, створити однакові індекси або внести записи до службового журналу, що призводить до взаємних блокувань (дедлоків) на рівні словника даних СУБД та аварійного перезапуску подів.

Керування змінами фізичної структури даних вимагає відокремлення еволюції схеми від коду бізнес-логіки. Для цього будується автоматизований конвеєр (фр. *convoyeur*, від *convoyer* — супроводжувати, перевозити) міграцій (лат. *migratio* — переміщення, переселення) схеми (грец. *σχῆμα* — форма, план, вигляд) — багаторівневий процес перевірки, координації та застосування DDL-інструкцій у середовищах CI/CD, що гарантує збереження цілісності даних і нульовий час простою (zero-downtime) під робочим навантаженням.

### Анатомія блокувального колапсу під DDL-навантаженням

Щоб зрозуміти, чому конвеєр міграцій потребує суворих архітектурних бар'єрів, необхідно простежити фізику обробки замків усередині реляційного ядра.

У СУБД PostgreSQL та MySQL кожна операція над таблицею потребує певного рівня блокування в ієрархії замків:

```
[Ієрархія блокувань таблиці]
AccessShareLock            (SELECT) ───────────────────┐ (Сумісні між собою)
RowShareLock               (SELECT FOR UPDATE)         │
RowExclusiveLock           (INSERT, UPDATE, DELETE) ───┘
ShareUpdateExclusiveLock   (VACUUM, CREATE INDEX CONCURRENTLY, VALIDATE CONSTRAINT)
ShareLock                  (CREATE INDEX стандартний)
ShareRowExclusiveLock      (CREATE TRIGGER, деякі FOREIGN KEY)
ExclusiveLock              (Блокування паралельних DDL)
AccessExclusiveLock        (ALTER TABLE, DROP TABLE, TRUNCATE) ── (Несумісний з УСІМА)
```

Коли клієнт виконує звичайний запит читання, він захоплює замок `AccessShareLock`. Тисячі паралельних читачів і записувачів (`RowExclusiveLock`) співіснують без взаємних затримок. Проте операції модифікації схеми (Data Definition Language, DDL) — такі як додавання колонки, зміна типу даних чи видалення таблиці — вимагають найвищого монопольного блокування **`AccessExclusiveLock`**, яке несумісне з жодним іншим замком, навіть із простим читанням одного рядка.

#### Механізм черги та блокування початку черги (Head-of-Line Blocking)

Катастрофа розгортається у чотири послідовні фази:

```text
Транзакція 1 (Аналітика): [── SELECT триває 15 секунд (AccessShareLock) ──]
                                              │
Транзакція 2 (Мігратор):                      ├──> Запит: ALTER TABLE (AccessExclusiveLock)
                                              │    Статус: ОЧІКУВАННЯ (Черга замків)
                                              │
Транзакція 3..500 (Веб-запити):               └──> Нові швидкі SELECT (1мс)
                                                   Статус: ЗАБЛОКОВАНО планувальником!
```

1. **Довгий читач:** транзакція 1 виконує сканування таблиці для побудови аналітичного звіту й утримує `AccessShareLock`.
2. **Надходження DDL:** мігратор виконує `ALTER TABLE orders ADD COLUMN loyalty_points integer;`. Запит вимагає `AccessExclusiveLock`. Оскільки замок несумісний з `AccessShareLock`, СУБД ставить мігратор у системну чергу очікування (`pg_locks`).
3. **Захист від голодування:** планувальник блокувань СУБД фіксує, що в черзі стоїть монопольний запит. Щоб запобігти його нескінченному відкладанню (голодуванню, англ. *starvation*) через безперервний потік читачів, планувальник починає блокувати **всі нові транзакції**, що звертаються до цієї таблиці, навіть якщо це мікросекундні читання за первинним ключем.
4. **Колапс з'єднань:** за 500 мілісекунд усі доступні з'єднання в пулі додатку (PgBouncer, HikariCP) виявляються зайнятими заблокованими потоками. Додаток припиняє обробляти будь-які запити, буфери TCP-сокетів переповнюються, і система зазнає повного відключення.

### Архітектура та фази конвеєра міграцій у CI/CD

Трансформація схеми у сучасному безперервному розгортанні розбивається на п'ять послідовних ізольованих етапів. Кожен етап має чіткі критерії проходження, що відсікають небезпечні операції задовго до потрапляння коду на продакшн.

![Архітектура та фази конвеєра міграцій бази даних у CI/CD](/root/eng/sf-data/database-migration-pipeline/img/migration-pipeline-lifecycle.svg)
*Архітектура та фази конвеєра міграцій бази даних у CI/CD: від статичного аналізу й тіньового тестування до пре-деплой запуску, розкатки додатку та фонового бекфілу*

#### 1. Статичний аналіз та лінтинг DDL у системі CI

Будь-який pull request, що містить нові файли міграцій, проходить автоматичний статичний аналіз (лінтинг, англ. *lint* — пух, вичісування дрібного сміття). Аналізатор розбирає SQL-код у синтаксичне дерево (Abstract Syntax Tree, AST) і перевіряє його проти набору правил безпеки:

- Заборона інструкцій, що вимагають ексклюзивного блокування на тривалий час (наприклад, зміна типів даних із переписуванням таблиці або додавання виразів за замовчуванням у старих версіях СУБД).
- Заборона звичайного створення індексів `CREATE INDEX` замість неблокувального варіанта `CREATE INDEX CONCURRENTLY` (PostgreSQL) або `ONLINE / ALGORITHM=INPLACE` (MySQL).
- Обов'язкова наявність сесійних обмежень `lock_timeout` та `statement_timeout`.
- Перевірка валідності імен, унікальності ідентифікаторів та сумісності з попередніми версіями додатку.

#### 2. Тіньове тестування на ефемерному клоні схеми

Статичного аналізу недостатньо для виявлення проблем продуктивності та конфліктів даних. На другому етапі CI/CD розгортає тимчасову базу даних (тіньовий клон, англ. *shadow database* або *thin clone* на базі copy-on-write знімків ZFS/Btrfs чи хмарних сервісів), на якій відтворено актуальну схему та анонімізований статистичний зріз продакшн-даних:

- Виконується тестовий прогін (dry-run) нової міграції із заміром реального часу виконання кожної інструкції.
- Перевіряється зворотна операція відкату (down-міграція або compensation-скрипт) для перевірки повноти очищення артефактів.
- Виконується повторний запуск для підтвердження ідемпотентності (лат. *idem* — той самий + *potens* — здатний): повторне виконання вже застосованого скрипту не повинно призводити до збою.
- Виявляється дрейф схеми (англ. *schema drift*) — розбіжність між очікуваним станом у репозиторії та фізичною структурою бази.

#### 3. Пре-деплой виконання міграцій (CD Runner)

Застосування DDL до продакшн-бази виконується **до** оновлення подів додатку. Міграції запускає виділений процес (Kubernetes Job або ізольований раннер у CD-агенті):

- Раннер захоплює глобальний розподілений замок (Advisory Lock) у СУБД, блокуючи спроби паралельного виконання іншими процесами.
- Перевіряються SHA-256 хеші раніше застосованих файлів у реєстрі `schema_migrations`.
- DDL виконується всередині транзакції (якщо СУБД та тип операції підтримують транзакційний DDL).
- У разі перевищення `lock_timeout` міграція негайно скасовується, знімає замок і завершується помилкою, дозволяючи CD-пайплайну повторити спробу пізніше без деградації клієнтського трафіку.

#### 4. Розкатка коду додатку (Rolling / Blue-Green)

Після того як схема переведена у стан v2, конвеєр розпочинає плавне оновлення контейнерів додатку. На цьому етапі виникає фаза змішаного трафіку: частина екземплярів сервісу ще працює за старим кодом v1, тоді як нова частина вже виконує код v2. 

Схема v2 повинна бути суворо сумісною як з кодом v1 (який не знає про нові колонки і продовжує читати/писати лише старі поля), так і з кодом v2.

#### 5. Пост-деплой асинхронний бекфіл та звуження схеми

Якщо міграція вимагає трансформації мільйонів історичних рядків (наприклад, розбиття стовпця `full_name` на `first_name` та `last_name`), важке оновлення даних (Data Manipulation Language, DML) не виконується всередині кроку DDL.

Замість цього після завершення деплою запускаються фонові воркери, які порційно (чанками) копіюють та перетворюють дані з постійним контролем лагу реплікації. Після завершення бекфілу наступний реліз видаляє застарілі структури.

### Статичний аналіз DDL: правила виявлення блокувальних операцій

Виконання команд DDL під навантаженням несе специфічні ризики для кожної реляційної СУБД. Статичний аналізатор перевіряє код міграцій на відповідність суворим правилам.

```
       ┌────────────────────────┐
       │ SQL Migration File AST │
       └───────────┬────────────┘
                   │
         [ AST Rule Engine ]
                   │
    ┌──────────────┼──────────────┐
    ▼              ▼              ▼
[Lock Check] [Timeout Guard] [Compat Check]
    │              │              │
    └──────────────┼──────────────┘
                   │
       ┌───────────▼────────────┐
       │ PASS / REJECT Pipeline │
       └────────────────────────┘
```

#### Небезпечні та безпечні еквіваленти DDL у PostgreSQL

| Небезпечна інструкція (BLOCKED) | Механізм загрози | Безпечна альтернатива (ALLOWED) |
|---|---|---|
| `ALTER TABLE users ADD COLUMN age int NOT NULL;` | Блокує таблицю, оскільки значення `NULL` заборонене, а дефолт відсутній — призводить до помилки на наявних рядках. | `ALTER TABLE users ADD COLUMN age int;` (дозволити `NULL`, заповнити бекфілом, додати обмеження `CHECK`). |
| `ALTER TABLE users ADD COLUMN status text DEFAULT 'active';` *(PostgreSQL < 11)* | Повне переписування таблиці на диску для запису дефолтного значення у кожен рядок під `AccessExclusiveLock`. | У PostgreSQL 11+ оптимізовано (запис у системний каталог без переписування). Якщо дефолт містить волатильну функцію (`DEFAULT now()`), таблиця все одно переписується. Безпечно: додати `NULL`, бекфіл, встановити `SET DEFAULT`. |
| `CREATE INDEX idx_users_email ON users(email);` | Захоплює `ShareLock`, блокуючи всі операції запису (`INSERT`, `UPDATE`, `DELETE`) на весь час сканування та побудови індексу. | `CREATE INDEX CONCURRENTLY idx_users_email ON users(email);` (виконує побудову у два проходи без блокування запису). |
| `ALTER TABLE orders ADD CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users(id);` | Сканує всю таблицю `orders` під `ShareRowExclusiveLock`, блокуючи будь-які модифікації зв'язаних таблиць. | `ALTER TABLE orders ADD CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;` з наступним `ALTER TABLE orders VALIDATE CONSTRAINT fk_user;`. |
| `ALTER TABLE items ALTER COLUMN price TYPE bigint;` | Повне фізичне переписування таблиці та перебудова всіх індексів під монопольним блокуванням. | Патерн Expand/Contract: нова колонка `price_v2 bigint`, подвійний запис, фоновий бекфіл. |
| `ALTER TABLE users RENAME COLUMN email TO contact_email;` | Миттєво ламає всі працюючі екземпляри коду v1, які продовжують надсилати запити з назвою `email`. | Патерн Expand/Contract: додавання нової колонки, синхронізація через код/тригер, поступове переведення сервісів. |

#### Чому `CREATE INDEX CONCURRENTLY` потребує особливого поводження

Команда неблокувальної побудови індексу виконується у два окремі проходи таблиці:
1. Під час першого проходу транзакція реєструє індекс у системному каталозі `pg_class` зі статусом `indisready = false`, очікує завершення всіх активних транзакцій запису і починає накопичувати нові зміни у спеціальний буфер.
2. Під час другого проходу індекс сканує всі наявні рядки таблиці, застосовує накопичені зміни та очікує завершення транзакцій читання.

Через необхідність очікування двох різних знімків стану (Snapshots) команда `CREATE INDEX CONCURRENTLY` **фізично не може виконуватися всередині транзакційного блоку `BEGIN ... COMMIT`**. Якщо операцію перервано або скасовано через помилку валідації унікальності, індекс залишається в каталозі зі статусом `INVALID`. Такий індекс не використовується оптимізатором запитів, проте продовжує сповільнювати операції `INSERT` та `UPDATE`. Раннер міграцій зобов'язаний виявляти невдалі спроби створення та автоматично видаляти невалідні індекси командою `DROP INDEX CONCURRENTLY`.

#### Валідація зовнішніх ключів без зупинки запису

Додавання зовнішнього ключа (`FOREIGN KEY`) до таблиці на 100 мільйонів рядків класичним способом блокує будь-які зміни в обох таблицях на час повної перевірки посилальної цілісності. Безпечний конвеєр розбиває операцію на дві інструкції:

```sql
-- Крок 1: Миттєве додавання обмеження без перевірки наявних рядків (займає < 5 мс)
ALTER TABLE orders 
ADD CONSTRAINT fk_orders_user_id 
FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;

-- Крок 2: Фонова валідація наявних даних (утримує лише ShareUpdateExclusiveLock)
-- Читання та запис у таблицю orders продовжують працювати без перешкод!
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_user_id;
```

#### Автоматизація перевірок через лінтер

Приклад конфігурації перевірок у конвеєрі CI (на базі правил інструменту `squawk` або `atlas`):

```yaml
# .github/workflows/migration-lint.yml
name: Database Migration Lint
on:
  pull_request:
    paths:
      - 'migrations/**.sql'

jobs:
  lint-migrations:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Migration Linter
        run: |
          curl -sSf https://atlasgo.sh | sh

      - name: Run Schema Security Analysis
        run: |
          atlas migrate lint \
            --dir "file://migrations" \
            --dev-url "docker://postgres/16/dev" \
            --latest 1
```

Якщо розробник додасть інструкцію `CREATE INDEX` без ключового слова `CONCURRENTLY`, лінтер зупинить збірку з кодом помилки та рекомендацією:

```text
Error: destructive change detected in migration 20260825120000_add_user_idx.sql:
  - Non-concurrent index creation on table "users" blocks all concurrent writes.
    Fix: Use "CREATE INDEX CONCURRENTLY" and ensure migration runs outside a transaction block.
```

### Патерн розширення та звуження (Expand / Contract)

Будь-яка нетривіальна трансформація даних під навантаженням вимагає тимчасового дублювання структур. Патерн паралельних змін (англ. *Parallel Change* або *Expand/Contract*) розбиває одну зміну на чотири послідовні релізи.

![Патерн паралельних змін Expand / Contract для безпечної еволюції схеми](/root/eng/sf-data/database-migration-pipeline/img/expand-contract-phases.svg)
*Чотири фази патерну Expand/Contract: гарантія повної сумісності схеми зі старими та новими версіями додатку під час живого розгортання*

Етимологія термінів відображає фізику процесу: розширення (лат. *expandere* — розгортати, поширювати) збільшує інтерфейс та обсяг сховища, а звуження (лат. *contrahere* — стягувати, скорочувати) прибирає надлишковий тимчасовий шар після завершення міграції.

#### Приклад: зміна формату стовпця `phone` з `varchar(32)` на стандартизований E.164 `varchar(16)` з перевіркою валідності

```
Фаза 1 (Expand):       [ phone (старе) ]  ──>  [ phone_e164 (нове, NULL) ]
                            │
Фаза 2 (Dual Write):   Код пише в ОБОЄ: phone ТА phone_e164
                       Фоновий воркер конвертує старі рядки
                            │
Фаза 3 (Switch Read):  Код читає з phone_e164, але продовжує писати в обидва
                            │
Фаза 4 (Contract):     Код пише ТІЛЬКИ в phone_e164
                       DDL: ALTER TABLE users DROP COLUMN phone;
```

#### Фаза 1: Розширення (Expand — Реліз 1)
У базу додається новий стовпець `phone_e164`. Він обов'язково дозволяє значення `NULL`, оскільки для наявних рядків даних нове значення ще не сформоване:

```sql
-- 20260825010000_expand_phone_e164.sql
SET lock_timeout = '2s';
ALTER TABLE users ADD COLUMN phone_e164 varchar(16);
```

Код застосунку залишається версії v1.0 і повністю ігнорує колонку `phone_e164`.

#### Фаза 2: Подвійний запис та бекфіл (Dual Write & Backfill — Реліз 2)
Розгортається код версії v1.1. Логіка запису оновлюється так, щоб заповнювати обидва стовпці:

:::tabs
```go
// Логіка оновлення профілю у версії коду v1.1 (Dual Write)
func UpdateUserPhone(ctx context.Context, db *sql.DB, userID int64, rawPhone string) error {
    normalizedPhone, err := formatE164(rawPhone)
    if err != nil {
        return fmt.Errorf("невалідний телефон: %w", err)
    }

    query := `
        UPDATE users 
        SET phone = $1, 
            phone_e164 = $2, 
            updated_at = NOW() 
        WHERE id = $3`
    _, err = db.ExecContext(ctx, query, rawPhone, normalizedPhone, userID)
    return err
}
```
```cpp
// Логіка оновлення профілю у версії коду v1.1 (Dual Write)
void update_user_phone(PgConnection& conn, int64_t user_id, std::string_view raw_phone) {
    std::string normalized_phone = format_e164(raw_phone);

    std::string query = std::format(
        "UPDATE users SET phone = '{}', phone_e164 = '{}', updated_at = NOW() WHERE id = {};",
        raw_phone, normalized_phone, user_id
    );
    PgResultPtr res(conn.exec(query));
}
```
:::

Паралельно запускається асинхронний бекфіл історичних даних:

```sql
-- Пакетне перенесення даних (виконується воркером у циклі)
UPDATE users 
SET phone_e164 = normalize_to_e164(phone)
WHERE id BETWEEN 100000 AND 105000 
  AND phone_e164 IS NULL;
```

#### Фаза 3: Перемикання читання (Switch Read — Реліз 3)
Після того як бекфіл завершив обробку 100% рядків, розгортається код версії v1.2. Додаток починає читати дані виключно з `phone_e164`. Запис продовжує дублюватися у старе поле на випадок потреби термінового відкату:

```go
// Версія v1.2: читання тільки з нового поля
func GetUserPhone(ctx context.Context, db *sql.DB, userID int64) (string, error) {
    var phoneE164 string
    err := db.QueryRowContext(ctx, "SELECT phone_e164 FROM users WHERE id = $1", userID).Scan(&phoneE164)
    return phoneE164, err
}
```

#### Фаза 4: Звуження (Contract — Реліз 4)
Коли метрики підтвердили стабільність роботи нової схеми, розгортається версія v2.0, яка більше не взаємодіє зі старим полем `phone`. Останнім кроком виконується фінальна DDL-міграція:

```sql
-- 20260825040000_contract_drop_old_phone.sql
SET lock_timeout = '2s';
ALTER TABLE users DROP COLUMN phone;
```

### Онлайн-трансформація великих таблиць (Online Schema Change — OSC)

Коли таблиця досягає сотень гігабайтів або мільярдів рядків, навіть стандартні оптимізації СУБД створюють надмірне дискове навантаження. Для таких обсягів застосовують зовнішні інструменти онлайн-зміни схем: **`gh-ost`** (GitHub Online Schema Transformations) або **`pt-online-schema-change`** (Percona Toolkit).

![Внутрішній механізм Online Schema Change](/root/eng/sf-data/database-migration-pipeline/img/online-schema-change-ghost.svg)
*Внутрішня архітектура онлайн-міграції через інструменти gh-ost та pt-osc: використання бінарних логів, чанкового бекфілу, тротлінгу та атомарного перемикання*

#### Принципова різниця між pt-osc та gh-ost

- **`pt-online-schema-change` (Тригерний підхід):** створює тіньову таблицю та вішає тригери `AFTER INSERT`, `AFTER UPDATE`, `AFTER DELETE` на оригінальну таблицю. Кожен клієнтський запит синхронно дублюється в тіньову таблицю. Головний недолік: тригери збільшують час відгуку клієнтських транзакцій, створюють високе конкурентне навантаження на блокування рядків і можуть призводити до каскадних дедлоків під піковим трафіком.
- **`gh-ost` (Асинхронний лог-оркестратор):** не створює жодних тригерів. Замість цього `gh-ost` підключається до реплікаційного потоку MySQL (Binlog) як віртуальна репліка, перехоплює події змін оригінальної таблиці в асинхронному режимі та транслює їх у тіньову таблицю `_users_gho`.

#### Чотири складові безпечного копіювання

1. **Чанковий копіювальник (Chunker):** читає оригінальну таблицю діапазонами первинного ключа (`WHERE id BETWEEN 50000 AND 55000`) та копіює дані в тіньову таблицю пакетами.
2. **Зчитувач журналу подій (Binlog Streamer):** паралельно накочує свіжі зміни, які користувачі роблять у вже скопійованих або ще не скопійованих діапазонах.
3. **Адаптивний тротлінг (Throttler):** кожні 100 мс опитує репліки СУБД. Якщо затримка реплікації перевищує заданий ліміт (наприклад, `max-lag=1s`) або завантаження процесора сягає 80%, процес копіювання миттєво призупиняється.
4. **Атомарний Cutover:** фінальна підміна таблиць виконується за кілька мілісекунд через блокування та атомарну зміну імен:

```sql
-- Атомарна підміна таблиць у MySQL
RENAME TABLE users TO _users_old, _users_gho TO users;
```

Детальніше про зародження цих механізмів та історію подолання блокувань читайте у вставці про [історію становлення підходів до еволюції схем](root:sf-data/database-migration-pipeline/hist-schema-evolution-origins.md).

### Оркестрація виконання: ізольовані раннери та розподілені замки

Поширена помилка початкових архітектур — запуск мігратора під час старту основного процесу застосунку (наприклад, команда `entrypoint: npm run migrate && npm start`).

```
[АНТИПАТЕРН: Запуск у кожному поді]
Pod 1 ──> [npm run migrate] ──┐
Pod 2 ──> [npm run migrate] ──┼──> [Конфлікт у schema_migrations, Deadlock СУБД]
Pod 3 ──> [npm run migrate] ──┘

[ПРАВИЛЬНО: Декомпільований CD Runner]
CD Pipeline ──> [K8s Migration Job (1 Pod)] ──> [СУБД (Advisory Lock)]
                        │ (Успіх)
                        ▼
            [Rolling Update Pods v2]
```

#### Чому запуск у подах неприпустимий

1. **Гонка процесів (Race Condition):** при одночасному масштабуванні кількох подів десятки процесів одночасно намагаються перевірити та виконати той самий DDL. Навіть за наявності транзакцій виникають помилки `duplicate key value violates unique constraint "schema_migrations_pkey"` або дедлоки на блокуваннях таблиць системного каталогу.
2. **Порушення послідовності станів:** якщо под 1 застосував міграцію v2, а под 2 впав через помилку конфігурації, частина трафіку починає йти на нову схему з кодом старої версії без контролю з боку оркестратора розгортання.

#### Архітектура виділеного Kubernetes Migration Job

Конвеєр CD запускає міграції як одноразове завдання (Kubernetes Job) з суворими обмеженнями перезапуску:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: schema-migration-v2-4-0
spec:
  backoffLimit: 0          # Не перезапускати автоматично при помилці DDL
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migration-runner
          image: registry.internal/app-migrator:v2.4.0
          env:
            - name: DB_LOCK_TIMEOUT
              value: "2000ms"
            - name: DB_STATEMENT_TIMEOUT
              value: "30000ms"
            - name: DB_ADVISORY_LOCK_KEY
              value: "84729104958172"
          command: ["/bin/runner", "migrate", "--dir=/migrations"]
```

#### Механізм розподіленого блокування (Advisory Locks)

Щоб унеможливити конкурентний запуск міграцій між різними конвеєрами або ручними утилітами адміністратора, раннер захоплює числовий замок на рівні СУБД.

У **PostgreSQL** використовуються консультативні замки (Advisory Locks), які не блокують жодних користувацьких таблиць, але забезпечують взаємне виключення між міграційними процесами:

```sql
-- Спроба неблокувального захоплення замка за 64-бітним ключем проекту
SELECT pg_try_advisory_lock(84729104958172);
-- Повертає 'true' якщо замок захоплено, або 'false' якщо інший раннер уже працює
```

У **MySQL** аналогічна поведінка реалізується через іменовані рядкові замки метаданих:

```sql
-- Захоплення іменованого замка з таймаутом 5 секунд
SELECT GET_LOCK('migration_pipeline_lock', 5);
-- Звільнення замка після завершення
SELECT RELEASE_LOCK('migration_pipeline_lock');
```

#### Захист цілісності через контрольні суми (Checksum Ledger)

Таблиця `schema_migrations` слугує незмінним реєстром виконаних змін. Кожен запис містить не лише версію, а й криптографічний хеш вмісту SQL-файлу:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version VARCHAR(128) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    checksum VARCHAR(64) NOT NULL,
    applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    execution_time_ms BIGINT NOT NULL
);
```

Якщо розробник випадково або навмисно відредагує текст файлу міграції, який уже було застосовано на продакшні пів року тому, раннер обчислить новий SHA-256 хеш файлу, виявить розбіжність зі значенням у базі та негайно зупинить розгортання:

```
[FATAL] Schema Integrity Violation:
Migration "20251110090000_create_accounts.sql" has been modified after execution!
  Expected Checksum: a3b92f...
  Found Checksum:    e810c4...
Pipeline aborted to prevent unpredictable schema state.
```

Повний вихідний код промислового раннера наведено у вставці [робочу реалізацію транзакційного раннера з advisory-замками](root:sf-data/database-migration-pipeline/proj-migration-runner.md).

### Сесійні бар'єри безпеки (Guardrails)

Критична вимога до виконання будь-якої міграції на живому кластері — ізоляція часу очікування замків. 

Якщо DDL-інструкція не може отримати блокування таблиці негайно через активні фонові запити, вона не повинна чекати нескінченно, утворюючи чергу перед собою. Раннер примусово встановлює два ліміти перед виконанням кожного SQL-файлу:

```sql
-- Встановлення захисних бар'єрів на рівні поточної сесії мігратора
SET lock_timeout = '2000ms';
SET statement_timeout = '30000ms';
```

1. **`lock_timeout = '2000ms'`:** якщо таблиця утримується іншими транзакціями понад 2 секунди, СУБД примусово перериває запит міграції з помилкою `canceling statement due to lock timeout`. Черга вхідних клієнтських запитів звільняється, запобігаючи падінню сервісу.
2. **`statement_timeout = '30000ms'`:** якщо операція DDL отримала блокування, але саме її виконання (наприклад, побудова індексу або додавання обмеження) триває понад 30 секунд, операція скасовується для захисту від перевантаження дискової підсистеми.

#### Алгоритм повторів з експоненційним відступом (Exponential Backoff)

Коли міграція переривається через `lock_timeout`, раннер не повинен падати відразу. Застосовується стратегія повторних спроб із випадковим відступом (Jitter):

:::tabs
```c
/* Обчислення паузи перед повторною спробою захоплення блокування */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <time.h>

long calculate_backoff_delay_ms(int attempt, long base_ms, long max_ms) {
    long delay = base_ms * (1L << attempt);
    if (delay > max_ms) {
        delay = max_ms;
    }
    /* Додавання випадкового джитера від 0 до 50% */
    long jitter = rand() % (delay / 2 + 1);
    return delay + jitter;
}
```
```cpp
// Обчислення паузи перед повторною спробою захоплення блокування (C++)
#include <chrono>
#include <random>
#include <algorithm>

std::chrono::milliseconds calculate_backoff_delay(int attempt, 
                                                  std::chrono::milliseconds base, 
                                                  std::chrono::milliseconds max_delay) {
    auto factor = 1ULL << std::min(attempt, 30);
    auto raw_delay = std::min(base * factor, max_delay);

    static thread_local std::mt19937_64 rng(std::random_device{}());
    std::uniform_int_distribution<int64_t> dist(0, raw_delay.count() / 2);

    return raw_delay + std::chrono::milliseconds(dist(rng));
}
```
:::

### Взаємодія бекфілу з MVCC та роздуванням таблиць (Table Bloat)

Виконання масових операцій `UPDATE` під час другої фази патерну Expand/Contract безпосередньо впливає на механізм багатоверсійності MVCC (Multi-Version Concurrency Control).

У PostgreSQL інструкція `UPDATE` фізично не перезаписує байтове представлення рядка на сторінці пам'яті. Замість цього створюється новий кортеж (`HeapTuple`), а старий кортеж позначається як неактивний встановленням значення `xmax`. Якщо бекфіл намагається оновити 50 мільйонів рядків одним неперервним запитом:

```sql
-- КАТАСТРОФІЧНИЙ АНТИПАТЕРН: Оновлення всієї таблиці в одній транзакції
UPDATE users SET phone_e164 = normalize_to_e164(phone);
```

Виникають три руйнівні наслідки:
1. **Зсув горизонту очищення (Vacuum Horizon):** транзакція, що виконує гігантський `UPDATE`, утримує один старий ідентифікатор транзакції `xmin`. Механізм очищення `VACUUM` не має права звільняти жодні мертві рядки в усій базі даних, створені після старту цієї транзакції. У результаті розмір усіх активних таблиць кластера починає лавиноподібно роздуватися.
2. **Переповнення журналу транзакцій (WAL Flooding):** генерація десятків гігабайтів записів у WAL перевантажує диск та канали реплікації, змушуючи репліки відставати на хвилини або години.
3. **Фізичне подвоєння розміру таблиці (Page Bloat):** створення 50 мільйонів нових версій рядків подвоює обсяг файлів таблиці на диску. Навіть після видалення старих версій таблиця не зменшується фізично в ОС без важкої блокувальної операції `VACUUM FULL`.

#### Чанковий бекфіл з контролем розміру пачок

Щоб уникнути цих деградацій, раннер розбиває бекфіл на мікропакети по 1000–5000 рядків, кожен з яких виконується в окремій транзакції з мікропаузою:

```sql
-- Безпечний крок чанкового бекфілу за кластеризованим первинним ключем
UPDATE users 
SET phone_e164 = normalize_to_e164(phone)
WHERE id >= 100001 AND id <= 105000 
  AND phone_e164 IS NULL;
```

Коротка транзакція на 5000 рядків завершується за 15–30 мілісекунд, негайно вивільняє свій `xmin`, дозволяє процесу `autovacuum` вчасно повторно використовувати сторінки пам'яті та утримує навантаження на реплікацію в допустимих межах.

### Розширені сценарії: партиціонування монолітних таблиць

Коли обсяг транзакційної таблиці (наприклад, `audit_logs` або `orders`) перевищує кілька терабайтів, виникає потреба переведення монолітної структури на декларативне секціонування (Declarative Partitioning). Пряма спроба виконати `ALTER TABLE ... PARTITION BY` не підтримується синтаксисом СУБД або вимагає повного блокування таблиці на час перекопіювання всіх даних.

Конвеєр міграцій реалізує безшовне секціонування через чотири фази:

```text
1. Створення нової партиціонованої таблиці: orders_partitioned
2. Створення нових секцій за часовими діапазонами (місяці/квартали)
3. Підключення існуючої монолітної таблиці orders як секції за замовчуванням:
   ALTER TABLE orders_partitioned ATTACH PARTITION orders DEFAULT;
4. Асинхронний бекфіл рядків з дефолтної секції у відповідні діапазонні секції
5. Фінальний RENAME: orders_partitioned -> orders
```

Такий підхід дозволяє перевести терабайтне сховище на секціоновану архітектуру, зберігаючи неперервну доступність операцій читання та запису для клієнтських сервісів.

### Координація версій: сумісність n-1 / n+1

Основне джерело збоїв під час релізів — невідповідність очікувань коду структурі бази даних. Доки триває процес розгортання (Rolling Update), у кластері одночасно існують екземпляри коду двох версій.

```
       Версія Схеми в БД:  [ Схема v2 (з новою колонкою) ]
                                  ▲
                    ┌─────────────┴─────────────┐
                    │                           │
          [ Поди Додатку v1 ]          [ Поди Додатку v2 ]
         (Старий код: ігнорує)       (Новий код: використовує)
```

#### Загроза використання `SELECT *` та кешування підготовлених планів
Найпоширеніша вразливість у коді додатків — використання неявного вибору всіх полів (`SELECT * FROM users` або неналаштовані ORM-мапери). 

Якщо міграція додає в таблицю нову колонку, активні поди старої версії v1 виконують `SELECT *` і отримують на один стовпець більше, ніж очікує їхній внутрішній буфер або скомпільований DTO. Це призводить до помилок гідрації моделей (наприклад, `mapping error: unexpected column count`), розриву з'єднань та збоїв бізнес-логіки.

Крім того, пулери з'єднань, що використовують підготовлені вирази (Prepared Statements), можуть зберігати скомпільований план виконання. Зміна типу колонки або додавання стовпця ламає бінарний контракт, викликаючи в PostgreSQL фатальну помилку `ERROR: cached plan must not change result type`. Клієнтські бібліотеки зобов'язані перехоплювати цей код помилки та автоматично перевиконувати запит з оновленням плану або надсилати команду `DISCARD ALL` під час повернення з'єднання в пул.

#### Правило явного проектування полів
Кожен SQL-запит у коді застосунку зобов'язаний явно перелічувати необхідні колонки (`SELECT id, email, status FROM users`). 

У фреймворках Active Record та ORM впроваджується налаштування ігнорування нових колонок старим кодом:

```ruby
# Конфігурація моделі у версії коду v1
class User < ApplicationRecord
  # Явне ігнорування колонки доти, доки всі сервіси не перейдуть на версію v2
  self.ignored_columns += ["loyalty_points"]
end
```

### Моніторинг та алертинг конвеєра в реальному часі

Безпечний конвеєр міграцій спирається на безперервний збір метрик СУБД у реальному часі. Під час виконання DDL та чанкового бекфілу система телеметрії (Prometheus, Datadog) відстежує чотири ключові показники:

1. **Кількість очікуючих блокувань (`pg_stat_activity`):**
   ```sql
   SELECT count(*) FROM pg_stat_activity 
   WHERE wait_event_type = 'Lock' AND wait_event = 'relation';
   ```
   Якщо кількість заблокованих запитів перевищує 5, раннер отримує сигнал на негайне призупинення бекфілу.
2. **Затримка реплікації (`pg_stat_replication`):**
   ```sql
   SELECT client_addr, application_name, 
          EXTRACT(EPOCH FROM (now() - replay_lsn_timestamp)) AS replay_lag_seconds
   FROM pg_stat_replication;
   ```
   Якщо показник `replay_lag_seconds` на будь-якій репліці перевищує 1.5 секунди, швидкість надсилання чанків автоматично сповільнюється (тротлінг).
3. **Темп генерації журналу WAL:** різкий сплеск швидкості запису байтів у WAL (`pg_current_wal_lsn()`) сигналізує про небезпечно великий розмір чанку або про переписування сторінок індексів.
4. **Утилізація пулу з'єднань:** відсоток зайнятих клієнтських сокетів у PgBouncer. Наближення до 80% сигналізує про виникнення блокувального каскаду і вимагає примусового завершення DDL через `lock_timeout`.

### Підводні камені та крайові випадки конвеєра

1. **Неподільні DDL-операції у PostgreSQL:** створення індексів за допомогою `CREATE INDEX CONCURRENTLY` або модифікація значень перелічуваних типів `ALTER TYPE ... ADD VALUE` не можуть виконуватися всередині транзакційного блоку (`ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`). Раннер аналізує директиви в заголовку міграційного файлу (наприклад, `-- +migrate Transactional:false`) і виконує такі команди через пряме сесійне з'єднання без блоку `BEGIN ... COMMIT`.
2. **Неявний COMMIT (Implicit Commit) у MySQL:** на відміну від PostgreSQL, виконання будь-якої інструкції DDL у MySQL автоматично фіксує поточну транзакцію. Якщо скрипт містить три команди `ALTER TABLE`, і остання зазнає невдачі, перші дві залишаються застосованими назавжди. Конвеєр повинен суворо вимагати розміщення **лише однієї DDL-команди в одному файлі міграції** для MySQL.
3. **Зависання advisory-замків через пулери з'єднань:** якщо застосунок використовує PgBouncer або ProxySQL у режимі пулінгу транзакцій (`pool_mode = transaction`), сесійні замки `pg_advisory_lock` не можуть використовуватися коректно, оскільки після завершення транзакції з'єднання повертається в пул і може бути видане іншому клієнту разом із утримуваним замком. Раннер міграцій зобов'язаний підключатися до СУБД через прямий службовий порт або використовувати виключно транзакційні advisory-замки `pg_advisory_xact_lock()`.
4. **Конфлікти паралельних гілок у Git:** використання цілочисельної нумерації файлів (`001_init.sql`, `002_add_user.sql`) неминуче спричиняє колізії при злитті гілок кількох розробників. Конвеєр зобов'язаний валідувати формат міграцій виключно за часовими мітками UTC (`YYYYMMDDHHMMSS_name.sql`).
5. **Дрейф схеми через ручні модифікації DBA:** якщо інженер вручну додає індекс або змінює дефолтне значення безпосередньо у виробничій базі даних через термінал `psql`, репозиторій Git втрачає статус єдиного джерела істини. Конвеєр CI/CD зобов'язаний щоденно запускати періодичне завдання (Cron Job), яке генерує поточний DDL-дамп продакшн-каталогу та порівнює його з еталонним станом у Git за допомогою інструментів `atlas migrate diff` або `pgmetrics`. Будь-яка виявлена невідповідність викликає негайне сповіщення команди експлуатації.

### Новий синтез: схема як динамічний контракт

Еволюція бази даних у високодоступних системах остаточно перестала бути статичним актом перезапуску системи. Схема реляційної бази даних — це не нерухомий моноліт, а динамічний, безперервно змінюваний контракт між даними на диску та розподіленими обчислювальними вузлами. 

Конвеєр міграцій забезпечує математичну та операційну гарантію того, що в будь-який момент часу кожен байт на диску відповідає контракту, який підтримується всіма активними процесами в кластері, перетворюючи складну реляційну еволюцію на невід'ємну складову безперервної інженерної доставки.
