# 📜 Еволюція моделей узгодження стану: від імперативних скриптів до Promise Theory та контролерів Kubernetes

Коли розподілена система складається з тисяч автономних вузлів або віддалених пристроїв із нестабільним зв'язком, спроба керувати ними прямими імперативними командами неминуче призводить до розсинхронізації, накопичення прихованих помилок і дрейфу конфігурації. Цей історичний огляд розкриває еволюцію архітектурної думки: як інженерія перейшла від одноразових виконуваних сценаріїв і RPC-викликів до теорії автономних обіцянок, безперервних циклів зближення (convergence loops) та сучасного стандарту розділення бажаного і звітованого станів.

## 1990-ті: Ера імперативних сценаріїв і крихкої автоматизації

На світанку розвитку мережевих серверних парків системне адміністрування спиралося на імперативні сценарії оболонки (shell scripts), які запускалися вручну через SSH або періодично за розкладом через `cron`. Типовий сценарій складався з послідовності команд: перевірити наявність файлу, створити користувача, завантажити архів, розпакувати конфігурацію та перезапустити демон.

```bash
# Типовий імперативний підхід 1990-х років
if [ ! -f /etc/app.conf ]; then
    cp /mnt/share/app.conf /etc/app.conf
    chown root:root /etc/app.conf
    chmod 644 /etc/app.conf
    systemctl restart app.service
fi
```

Головною вадою такого підходу була відсутність формальної моделі кінцевого стану. Сценарій описував *кроки переходу*, а не *цільовий стан*. Якщо зв'язок обривався посеред виконання (наприклад, після копіювання файлу, але до виклику `chmod`), система залишалася в напівзламаному проміжному стані. Повторний запуск сценарію міг викликати збій, оскільки файл уже існував, але мав неправильні права доступу.

Імперативні команди не мали властивості [ідемпотентності](root:sf-data/idempotent-reprocessing) (лат. *idem* — той самий, *potens* — здатний): виконання тієї самої команди двічі призводило до непередбачуваних побічних ефектів. Якщо локальний адміністратор на сервері вручну змінював параметр у файлі конфігурації, центральний керівний скрипт про це не знав і не міг повернути систему до вихідного еталона без повного ручного перезапису.

## Марк Берджесс, CFEngine та народження Promise Theory

У 1993 році фізик і системний дослідник Марк Берджесс (Mark Burgess) з Університету Осло створив проект CFEngine (Configuration Engine). Берджесс підійшов до проблеми адміністрування з позицій теоретичної фізики та імунології. Замість того, щоб надсилати вузлам накази «зроби дію X», він запропонував описувати стан вузла декларативно як набір інваріантів, які локальний агент зобов'язаний безперервно підтримувати.

```cfengine
# Декларативний опис інваріанта в ранньому CFEngine
files:
    /etc/app.conf
        mode=0644
        owner=root
        group=root
        action=fix
```

У 2004–2005 роках Берджесс формалізував цей підхід у математичній концепції **Promise Theory** (Теорія обіцянок). Ключова теза теорії полягає в тому, що в розподілених системах жоден зовнішній контролер не може гарантувати виконання дії на віддаленому вузлі силою наказу. Зовнішній вплив завжди опосередкований мережею та локальними обмеженнями. Єдине, що може існувати в надійній системі, — це *обіцянка* (promise) автономного агента підтримувати свій внутрішній стан у відповідності до заданої специфікації.

Берджесс сформулював принцип **конвергенції стану** (лат. *convergere* — сходитися до спільної точки). Якщо поточний стан системи `S(t)` відрізняється від бажаного стану `S_target`, оператор узгодження діє як асимптотичний стабілізатор:

```
Δ = S_target - S(t)
S(t + 1) = S(t) + f(Δ)
```

При кожному проході циклу різниця `Δ` прямує до нуля. Навіть якщо система зазнає зовнішнього збурення (ручне втручання, збій диска, перезавантаження), локальний цикл зворотного зв'язку автоматично повертає її до точки рівноваги без участі оператора.

## Хвиля конфігураційного менеджменту: Puppet, Chef, Ansible

Наприкінці 2000-х років ідеї декларативного опису інфраструктури стали масовими. У 2005 році Люк Каніс (Luke Kanies) створив Puppet, запровадивши спеціалізовану мову (DSL) для компіляції каталогів ресурсів. У 2009 році Адам Джейкоб (Adam Jacob) запустив Chef, використавши вбудований Ruby DSL.

Ці системи чітко розділили процес на дві фази:
1. **Фаза компіляції / визначення специфікації (Compile phase):** генерація графу бажаного стану (Desired State Graph) на сервері.
2. **Фаза зближення / виконання (Convergence / Execution phase):** локальний агент на цільовому сервері опитує фактичний стан (Reported State), будує різницю і послідовно викликає провайдери для усунення розбіжностей.

Однак інструменти першого покоління конфігураційного менеджменту все ще запускалися періодично (зазвичай раз на 30 хвилин через `cron` або фоновий демон). Це залишало вікно невизначеності: між запусками агентів система могла накопичувати невідповідності (configuration drift), а інформація про реальний стан на серверах залишалася застарілою.

## Від Google Borg до Kubernetes: Тріумф Level-Triggered циклів

На початку 2000-х років компанія Google розробляла внутрішню систему оркестрації контейнерів Borg. У Borg життєвим циклом завдань керував центральний монолітний Borgmaster. Стан завдань передавався через явні події зміни стану (State Transition Events). З ростом масштабу до сотень тисяч контейнерів інженери Google зіткнулися з проблемою втрати подій: якщо повідомлення про завершення процесу губилося в черзі або вузол тимчасово випадав із мережі, Borgmaster зависав у стані очікування, вимагаючи складних процедур очищення.

У 2014 році команда засновників Kubernetes (Джо Беда, Брендан Бернс, Крейг Маклакі, Браян Грант, Тім Хокін) переосмислила цей досвід. Вони відмовилися від подієво-орієнтованих кінцевих автоматів на користь моделі **Level-Triggered Reconciliation Loop** (цикл узгодження за рівнем, а не за фронтом сигналу).

Замість того, щоб реагувати на повідомлення «под зупинився», контролер Kubernetes постійно порівнює дві структури даних в `etcd`:
- `spec` (специфікація — бажаний стан, записаний користувачем);
- `status` (статус — фактичний стан, зареєстрований агентом `kubelet`).

Архітектура контролера була зведена до єдиної чистішої сигнатури:

```go
// Фундаментальний контракт контролера в Kubernetes
type Reconciler interface {
    Reconcile(context.Context, Request) (Result, error)
}
```

Контролеру не важливо, скільки подій сталося за час його відсутності чи скільки разів перезавантажувалася мережа. Він просто зчитує поточний `spec`, зчитує поточний `status`, знаходить різницю і виконує коригувальні дії, доки `status == spec`.

## Поява цифрових двійників в IoT: AWS IoT Device Shadow

Паралельно з розвитком хмарної оркестрації подібна проблема виникла в Інтернеті речей (IoT). Мільйони пристроїв (розумні лічильники, підключені автомобілі, датчики, верстати) працювали через нестабільні стільникові та супутникові канали з обмеженою пропускною здатністю.

Якщо мобільний додаток користувача надсилав команду «увімкнути кондиціонер» через прямий HTTP/RPC-запит, а пристрій у цей момент перебував поза зоною покриття мережі, запит завершувався таймаутом `504 Gateway Timeout`. Користувач не знав, чи виконається команда після відновлення зв'язку.

У 2015 році компанія Amazon Web Services представила сервіс **AWS IoT Device Shadow** (Тінь пристрою). Концепція тіні (Digital Twin — цифровий двійник) перенесла патерн розділення стану на фізичні об'єкти:

```json
{
  "state": {
    "desired": { "power": "ON", "target_temp": 22 },
    "reported": { "power": "OFF", "target_temp": 18 },
    "delta": { "power": "ON", "target_temp": 22 }
  },
  "version": 42
}
```

1. Додаток більше не звертається до фізичного заліза. Він виконує швидкий локальний запис у поле `state.desired` хмарного документа тіні.
2. Хмарний брокер автоматично вираховує поле `state.delta` як математичну різницю між `desired` та `reported`.
3. Коли пристрій виходить на зв'язок через протокол MQTT, він підписується на топік дельти, вичитує необхідні дії, налаштовує локальні апаратні регістри й публікує свій фактичний стан у `state.reported`.
4. Після публікації `reported == desired` поле `delta` стає порожнім об'єктом `{}`.

Цей підхід згодом стандартизували Azure Digital Twins, Google Cloud IoT Core та open-source проект Eclipse Ditto. Розділення бажаного і звітованого стану остаточно перетворилося з локального інженерного трюку на фундаментальний архітектурний шаблон проектування надійних розподілених систем.
