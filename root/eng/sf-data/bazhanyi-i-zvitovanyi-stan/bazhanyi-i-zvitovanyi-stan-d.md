Коли центральний керівний сервіс намагається налаштувати тисячі розподілених серверів або віддалених IoT-пристроїв через прямі імперативні RPC-виклики на кшталт `setSpeed(120)` чи `reboot()`, система ламається на першому ж нестабільному мережевому з'єднанні. Якщо пакет губиться у стільниковому каналі або цільовий вузол перебуває в тунелі без зв'язку, клієнт отримує таймаут, не знаючи, чи виконано команду. Повторна відправка наказу призводить до порушення черговості: запізніла стара команда здатна перетерти свіжіше ручне налаштування, виконане локальним оператором на місці, а одночасні запити від двох адміністраторів заганяють пам'ять пристрою в суперечливий стан.

Щоб припинити накопичення помилок, архітектуру взаємодії ділять на дві повністю незалежні площини: опис того, як система *має виглядати* (**бажаний стан**, desired state / spec), і факт того, чим вона *є насправді* (**звітований стан**, reported state / status). Між ними розташовують довговічне хмарне сховище (Device Shadow або реєстр etcd), а локальний автономний контролер безперервно обчислює різницю між цими площинами та зводить розбіжність до нуля.

![Імперативні команди проти декларативного узгодження стану](/root/eng/sf-data/bazhanyi-i-zvitovanyi-stan/img/imperative-vs-declarative-control.svg)
*Порівняння імперативного виконання прямих команд, де обрив зв'язку ламає послідовність дій, та декларативного узгодження через розв'язані площини desired і reported*

## Крах імперативної моделі: чому прямі команди руйнують розподілені системи

В імперативній моделі клієнт відправляє на кінцевий вузол наказ виконати дію: «відкрий клапан на 45 градусів», «створи 3 контейнери», «підвищ напругу на 0.5 В». Такий підхід виглядає природним у локальній програмі, але перетворюється на джерело хаосу в розподіленому середовищі з ненадійними каналами зв'язку.

Розглянемо послідовність дій, яка призводить до непоправного розходження стану в імперативній системі:

```
Клієнт A                     Мережа                     Вузол (Клапан)
   |                            |                             |
   |--- POST /setAngle(45) ---->| (пакет затримано в черзі)   |
   |    [таймаут 3000 мс]       |                             |
   |                            |                             |
   |                            | <--- Оператор на місці -----|
   |                            |      вручну ставить 0°     |
   |                            |      (аварійна зупинка)     |
   |                            |                             |
   |                            |--- запізнілий пакет 45° --->|
   |                            |    застосовується!          |
   |                            |                             |
   v                            v                             v
[У базі клієнта: помилка]   [Дріт мовчить]         [Фактично відкрито 45°!]
```

У цій точці виникає фундаментальний розрив реальності:
1. **Втрата контексту часу:** пакет із командою `45°` був коректним у момент генерації, але став небезпечним після локального втручання оператора. Імперативна команда не несе в собі інформації про те, від якого початкового стану вона відштовхувалася.
2. **Невизначеність результату при збої зв'язку (RPC In-Doubt):** якщо сервер відправив команду, вузол її успішно виконав, але зворотний пакет із підтвердженням `200 OK` загубився через розрив TCP-сесії, клієнт вважає операцію проваленою. Якщо клієнт виконає сліпий повтор відносної мутації на кшталт `incrementCounter(5)`, значення лічильника збільшиться двічі.
3. **Блокування клієнтських додатків:** якщо пристрій вимкнено або він спить у режимі глибокого енергозбереження (deep sleep) для економії акумулятора, прямий HTTP/RPC-запит змушений чекати на пробудження або завершуватися помилкою `504 Gateway Timeout`. Користувач не може зберегти налаштування в системі, поки залізо фізично недоступне.

Ці проблеми неможливо вирішити простим додаванням повторних спроб чи збільшенням таймаутів. Корінь проблеми полягає в хибному ототожненні *наміру* керування з *фактом* його виконання.

Детальний аналіз переходу індустрії від імперативних командних сценаріїв до теорії автономних агентів та зближення інваріантів розібрано у вставці [Еволюція моделей узгодження стану: від імперативних скриптів до Promise Theory та контролерів Kubernetes](root:sf-data/bazhanyi-i-zvitovanyi-stan/hist-state-convergence.md).

## Архітектурний розтин: Специфікація проти Телеметрії

Декларативна модель розділяє інформаційний простір системи на дві взаємно доповнюючі сутності, які зберігаються в довговічній базі даних (наприклад, у документі цифрового двійника Device Shadow або сховищі etcd):

1. **Бажаний стан (Desired State / `spec`):** декларативний опис цільових характеристик системи, сформований зовнішніми споживачами (користувачами, розкладами, оптимізаційними алгоритмами). Це *специфікація* (лат. *specificatio*, від *species* — вид та *facere* — робити) того, як система зобов'язана функціонувати.
2. **Звітований стан (Reported State / `status`):** об'єктивний телеметричний знімок (грец. *tele* — далеко та *metron* — вимірювання), згенерований сенсорами, апаратними регістрами або операційною системою кінцевого вузла. Це факт поточної реальності.

![Анатомія документа цифрового двійника](/root/eng/sf-data/bazhanyi-i-zvitovanyi-stan/img/device-shadow-three-way-split.svg)
*Структурне розбиття документа цифрового двійника на desired, reported та автоматично обчислювану дельту з метаданими версій*

Завдяки цьому розділенню досягається повна асинхронність взаємодії:

- **Запис бажаного стану ніколи не блокується на пристрої.** Користувач у мобільному додатку виставляє цільову температуру `22.5°C`. Цей намір миттєво зберігається в базі даних як `desired.target_temp = 22.5` з новою версією документа `version = 1042`. Запит завершується за 5 мілісекунд, навіть якщо сам пристрій зараз вимкнений або перебуває на іншому континенті.
- **Читання поточного стану ніколи не навантажує сенсори вузла.** Користувацькі інтерфейси, аналітичні вітрини та панелі моніторингу вичитують дані виключно з кешованої гілки `reported` у хмарі. Мільйон одночасних користувачів можуть переглядати статус пристрою, не надсилаючи жодного байта запитів на фізичний мікроконтролер.

Повний набір мережевих топіків MQTT, схем JSON Merge Patch та gRPC-сервісів для передачі бажаних і звітованих параметрів зафіксовано у вставці [Специфікація протоколу та контракти синхронізації стану: Device Shadow, MQTT та gRPC API](root:sf-data/bazhanyi-i-zvitovanyi-stan/api-shadow-reconciliation-contract.md).

## Дельта та виявлення дрейфу (Drift Detection)

Коли бажаний і звітований стани існують як паралельні документи, різниця між ними визначає обсяг незавершеної роботи.

Ця розбіжність називається **дрейфом стану** (нідерл. *drijven* / англ. *drift* — відхилення від заданого курсу під впливом течії). Обчислення дрейфу є математичною операцією знаходження **дельти** (грец. *delta*, позначення приросту або різниці величин).

Нехай `D` — множина пар `(ключ, значення)` бажаного стану, а `R` — множина пар звітованого стану. Тоді вектор дельти `Δ` визначається як різниця множин, де для кожного спільного ключа значення не збігаються:

```
Δ = { (k, v_d) ∈ D | k ∉ R  або  (k, v_r) ∈ R ∧ v_d ≠ v_r }
```

Якщо `Δ = ∅` (порожня множина), система перебуває у стані повної рівноваги: фізичний об'єкт точно відповідає своїй специфікації.

### Алгоритм пополярного порівняння (Field-Level Diffing)

При обчисленні дельти сервер або локальний агент обходить дерево документа зверху вниз:

```
Вихідні дані:
  desired  = { "mode": "AUTO", "speed": 100, "valve": "CLOSED", "filter_alert": null }
  reported = { "mode": "MANUAL", "speed": 100, "temp": 36.6, "filter_alert": "WARN" }

Крок 1 (mode):
  desired.mode ("AUTO") ≠ reported.mode ("MANUAL")
  → Додати до Δ: { "mode": "AUTO" }

Крок 2 (speed):
  desired.speed (100) == reported.speed (100)
  → Збіг, пропустити.

Крок 3 (valve):
  valve відсутній у reported
  → Додати до Δ: { "valve": "CLOSED" }

Крок 4 (temp):
  temp присутній лише в reported (суто телеметричний параметр)
  → Не є дрейфом бажаного стану, пропустити.

Крок 5 (filter_alert):
  desired містить null (надгробок / tombstone на видалення)
  → Додати до Δ: { "filter_alert": null }

Результат:
  delta = { "mode": "AUTO", "valve": "CLOSED", "filter_alert": null }
```

Зверніть увагу: суто телеметричні властивості сенсорів (наприклад, поточна виміряна температура `temp = 36.6`), які пристрій публікує у `reported`, не генерують дельту, якщо вони відсутні в `desired`. Бажаний стан визначає лише керовані параметри конфігурації.

## Математична модель оператора зближення (Convergence Algebra)

З точки зору абстрактної алгебри, простір станів системи утворює напівґратку (semi-lattice) з частковим порядком. Оператор узгодження `R` відображає пару станів `(S_desired, S_reported)` у новий фактичний стан `S_reported'`:

```
S_reported' = R(S_desired, S_reported)
```

Цей оператор задовольняє три фундаментальні алгебраїчні властивості:
1. **Ідемпотентність (Idempotency):**
   ```
   R(S_desired, R(S_desired, S_reported)) = R(S_desired, S_reported)
   ```
   Повторне застосування оператора узгодження до вже синхронізованої системи не викликає додаткових дій і залишає результат незмінним.
2. **Конвергенція (Convergence):**
   Для будь-якого початкового фізичного стану `S_0` існує скінченна кількість кроків `n`, за яких:
   ```
   Δ(n) = ||S_desired - S_reported(n)|| = 0
   ```
3. **Монотонність ревізій (Monotonicity):**
   Версія документа `v` монотонно зростає при кожній мутації:
   ```
   v(t + 1) > v(t), ∀ t
   ```

Це гарантує, що система під дією контролера завжди прямує до глобального атрактора — бажаного стану, незалежно від проміжних збурень та траєкторії руху.

## Цикл узгодження: Level-Triggered проти Edge-Triggered

Серцем системи, що використовує розділення стану, є **цикл узгодження** або **реконсиляція** (лат. *reconciliatio* — відновлення єдності, примирення, повернення до ладу).

Контролер узгодження є безперервним автоматом, що реалізує чотири фази замкненого циклу:

![Життєвий цикл циклу узгодження](/root/eng/sf-data/bazhanyi-i-zvitovanyi-stan/img/reconciliation-state-machine.svg)
*Чотирифакторний цикл узгодження: спостереження, виявлення дрейфу, ідемпотентна дія та фіксація оновленого звіту*

1. **Observe (Спостереження):** зчитування актуального `desired` стану з бази даних та вимірювання поточного `reported` стану з обладнання.
2. **Diff (Виявлення дрейфу):** обчислення вектора розбіжностей `Δ = D \ R`. Якщо `Δ = ∅`, контролер переходить у режим очікування.
3. **Actuate (Дія):** виконання фізичних або системних дій для застосування дельти (перемикання реле, запуск системного демона, зміна конфігураційного файлу).
4. **Report (Звіт):** після успішного виконання апаратних дій контролер зчитує нові показники сенсорів і публікує оновлений `reported` стан у центральну базу даних, підтверджуючи усунення дрейфу.

### Чому Edge-Triggered ламається, а Level-Triggered перемагає

Існує два принципово різні підходи до запуску циклу узгодження:

- **Edge-Triggered (Спрацьовування за фронтом події):** контролер реагує на конкретні повідомлення про події («користувач змінив параметр X», «температура впала на 2 градуси»). Якщо повідомлення про подію губиться в мережі через обрив сокета, система ніколи не дізнається про необхідність змін і назавжди зависне в розсинхронізованому стані.
- **Level-Triggered (Спрацьовування за рівнем різниці):** контролеру байдуже, скільки подій сталося чи скільки пакетів загубилося. Він реагує на сам *наявний факт розбіжності* між `desired` і `reported`.

Якщо мережа зникла на три дні, а користувач за цей час змінив параметр п'ять разів, Edge-Triggered системі потрібно відновити всю чергу з п'яти повідомлень без жодної втрати. Level-Triggered системі після відновлення зв'язку достатньо зчитати один-єдиний поточний зріз `desired` і один раз привести обладнання до фінального стану.

Програмну реалізацію надійного Level-Triggered контролера узгодження з потокобезпечними чергами на мовах C та C++ детально представлено у вставці [Програмна реалізація рушія узгодження стану та детекції дрейфу](root:sf-data/bazhanyi-i-zvitovanyi-stan/proj-state-reconciler.md).

## Механізм 3-way merge при конкурентних модифікаціях

У реальній експлуатації система рідко зазнає змін лише з одного боку. Типовою є ситуація, коли зовнішній користувач оновлює цільову специфікацію (`desired`), локальний оператор на фізичному об'єкті вручну перемикає частину тумблерів (`reported`), а попередня порція змін все ще перебуває в дорозі (`in-flight`).

Для безконфліктного об'єднання цих потоків застосовується **тристороннє злиття** (3-Way Merge). Алгоритм спирається на три вектори:
1. `S_base` — базовий знімок стану (остання узгоджена ревізія, зафіксована обома сторонами).
2. `S_desired` — нова цільова специфікація від контрольної площини.
3. `S_reported` — поточні телеметричні дані від фізичного заліза.

```
                  ┌──────────────────────┐
                  │ S_base (Остання      │
                  │ узгоджена ревізія)   │
                  └──────────┬───────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
┌──────────────────────┐          ┌──────────────────────┐
│ S_desired (Зміни     │          │ S_reported (Локальні │
│ керуючої площини)    │          │ фізичні зміни)       │
└──────────┬───────────┘          └───────────┬──────────┘
           │                                  │
           └────────────────┬─────────────────┘
                            ▼
                  ┌──────────────────────┐
                  │ S_merged (Результат  │
                  │ тристороннього diff) │
                  └──────────────────────┘
```

Для кожного поля `k` алгоритм оцінює характер змін відносно бази `S_base`:

| Стан поля у `S_desired` | Стан поля у `S_reported` | Рішення 3-Way Merge | Пояснення інженерного правила |
|---|---|---|---|
| Змінено (`v_d ≠ v_base`) | Не змінювалося (`v_r = v_base`) | Прийняти `v_d` у план дій | Чисте оновлення специфікації з хмари |
| Не змінювалося (`v_d = v_base`) | Змінено (`v_r ≠ v_base`) | Зберегти `v_r` у звіті | Локальна телеметрія сенсорів без конфлікту |
| Змінено однаково (`v_d = v_r`) | Змінено однаково (`v_r = v_d`) | Прийняти `v_d = v_r` | Обидві сторони незалежно зійшлися на одному значенні |
| Змінено по-різному (`v_d ≠ v_r ≠ v_base`) | Змінено по-різному (`v_r ≠ v_d ≠ v_base`) | **Семантичний конфлікт** | Потрібне застосування правила пріоритету або OCC |

При виникненні семантичного конфлікту на тому самому полі система застосовує політику домену:
- **Safety Priority (Пріоритет безпеки):** локальні апаратні блокування (наприклад, спрацювання датчика перегріву `emergency_shutdown = true`) мають безумовну перевагу над віддаленою командою `power = ON`.
- **Operator Override (Пріоритет оператора):** локальний ручний перемикач на щиті автоматики блокує виконання віддалених дельт, поки не буде переведений у режим `REMOTE_CONTROL`.

## Ієрархічні та складені ресурси (Composite Reconcilers)

У складних системах керований об'єкт не є плоским списком із кількох полів. Він організований як орієнтований ациклічний граф (DAG) взаємопов'язаних ресурсів.

У Kubernetes такий зв'язок реалізується через ланцюжок `Deployment → ReplicaSet → Pods → Containers`. В автономному електротранспорті чи енергетичних сховищах (BMS) ієрархія має вигляд `EnergyStorageSystem → InverterUnits → BatteryStrings → CellModules`.

```
                    ┌─────────────────────────┐
                    │ ESS Controller (Батько) │
                    │ Desired: Power = 500 kW │
                    └────────────┬────────────┘
                                 │ Розщеплення навантаження
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
     ┌───────────────────────┐       ┌───────────────────────┐
     │ Inverter 1 Controller │       │ Inverter 2 Controller │
     │ Desired: 250 kW       │       │ Desired: 250 kW       │
     │ Reported: 250 kW      │       │ Reported: 210 kW (збій)│
     └───────────┬───────────┘       └───────────┬───────────┘
                 │ Агрегація статусу             │
                 └───────────────┬───────────────┘
                                 ▼
                    ┌─────────────────────────┐
                    │ ESS Status Aggregator   │
                    │ Reported: Power = 460 kW│
                    │ Delta = -40 kW (Дрейф)  │
                    └─────────────────────────┘
```

Контролери ієрархічних систем реалізують два зустрічні потоки узгодження:
1. **Top-Down Cascading (Каскадування згори донизу):** батьківський контролер розщеплює глобальну мету (500 кВт) на локальні специфікації дочірніх підсистем (по 250 кВт кожному інвертору) і записує їх у відповідні `desired` документи.
2. **Bottom-Up Status Aggregation (Згортання статусу знизу догори):** дочірні контролери автономно приводять свої інвертори до норми і публікують локальні `reported` значення. Батьківський контролер читає звіти дітей, агрегує їх у сумарну потужність `460 кВт` і фіксує сумарний статус системи.

Якщо один з інверторів зазнає аварії, батьківський контролер під час наступного проходу циклу виявляє дельту в `40 кВт` і динамічно перерозподіляє навантаження, виставляючи робочому інвертору нове значення `desired = 290 kW` (якщо це дозволяють паспортні ліміти заліза).

## Оптимістичне блокування, версіонування та розв'язання конфліктів

Оскільки бажаний стан може змінюватися користувачами та алгоритмами одночасно з тим, як пристрій публікує свій телеметричний звіт, виникає загроза гонок оновлень (Race Conditions) та прихованої втрати модифікацій (Lost Updates).

Для захисту від спотворення даних застосовується **оптимістичне блокування** (лат. *optimus* — найкращий та *claudere* — замикати) на основі монотонних лічильників версій (Document Versioning / etcd ResourceVersion).

![Оптимістичне блокування та запобігання гонкам](/root/eng/sf-data/bazhanyi-i-zvitovanyi-stan/img/optimistic-versioning-race.svg)
*Запобігання гонкам оновлень за допомогою лічильника версій: клієнт B отримує 409 Conflict через зміну версії клієнтом A*

Механізм працює за таким алгоритмом:
1. Кожен документ стану містить ціле додатне число `version`.
2. Будь-яка успішна мутація (як `desired`, так і `reported`) атомарно інкрементує версію: `version = version + 1`.
3. Коли клієнт або пристрій відправляє оновлення, він передає параметр `expected_version` — версію документа, на основі якої він розрахував своє оновлення.
4. Сервер виконує атомарну перевірку умовного запису:

```
ЯКЩО incoming.expected_version == current_doc.version ТОДІ
    current_doc.state = merge(current_doc.state, incoming.state)
    current_doc.version = current_doc.version + 1
    ПОВЕРНУТИ 200 OK (нова версія current_doc.version)
ІНАКШЕ
    ВІДХИЛИТИ ЗАПИС
    ПОВЕРНУТИ 409 Conflict (stale version)
КІНЕЦЬ
```

Якщо два клієнти одночасно зчитали документ версії `10`, перший клієнт успішно запише свої зміни і переведе версію в `11`. Запит другого клієнта з `expected_version = 10` буде відхилено із кодом `409 Conflict`. Другий клієнт зобов'язаний вичитати новий стан версії `11`, повторно оцінити предметні правила і лише тоді надіслати оновлений запит.

## Відмовостійкість: експоненційний відкат, джитер та захист від осциляцій

У реальній експлуатації цикл узгодження постійно стикається з апаратними відмовами, заклинюванням механічних приводів та перевантаженням шин зв'язку. Наївний контролер, який намагається виконати дію в нескінченному щільному циклі (busy loop), спалює процесор і виводить з ладу реле.

Для забезпечення живучості застосовуються три інженерні запобіжники:

### 1. Експоненційний відкат із повним випадковим джитером (Full Jitter Backoff)

Якщо спроба привести актуатор до бажаного стану зазнає невдачі, контролер не повторює її негайно. Інтервал очікування між спробами експоненційно зростає:

```
t_backoff = min(t_max, t_base · 2^attempt)
```

Щоб запобігти ситуації, коли тисячі вузлів після збою живлення одночасно прокидаються і штурмують шину в однакові моменти часу (проблема **узгодженого шторму**, Thundering Herd), інтервал рандомізують за схемою **Full Jitter**:

```
t_sleep = random(0, t_backoff)
```

### 2. Зона нечутливості та гістерезис (Deadband & Hysteresis)

Аналогові сенсори (тиск, вологість, температура, рівень струму) піддаються дії теплового шуму. Якщо цільова температура дорівнює `22.0°C`, а датчик через шум постійно скаче між `21.99°C` та `22.01°C`, наївний diff-алгоритм буде безперервно вмикати й вимикати компресор.

Вводиться параметр зони нечутливості `ε` (deadband). Дрейф вважається значущим лише за умови:

```
|S_desired - S_reported| > ε
```

### 3. Захист від частих перемикань (Anti-Flapping Rate Limiting)

Якщо бажаний стан швидко змінюється зовнішнім користувачем або нестабільним скриптом (наприклад, перемикання режиму `ON/OFF` тричі на секунду), контролер обмежує частоту фізичних дій (Rate Limiting). Команди акумулюються у ковзному часовому вікні, а фізичний актуатор перемикається лише після стабілізації наміру протягом мінімального часу утримання (Hold Time).

## Мережеві партиції, оренда та захист від Split-Brain

Коли мережевий сегмент втрачає зв'язок із центральною хмарою, виникає дилема: чи повинен локальний вузол продовжувати керуватися останнім відомим бажаним станом, чи йому слід перейти в режим безпечної зупинки (Fail-Safe Default)?

Для запобігання небезпечним діям за застарілими інструкціями застосовується концепція **оренди стану (State Lease)**:

1. Разом із документом `desired` контрольна площина передає мітку часу закінчення оренди `lease_expire_timestamp` (наприклад, `now + 60 секунд`).
2. Поки зв'язок працює стабільно, хмара періодично продовжує оренду (Heartbeat Renewal).
3. Якщо мережа обривається і термін оренди спливає, локальний контролер фіксує втрату авторизації і переводить актуатори в аварійний безпечний стан (наприклад, глушить двигун або закриває газовий клапан), ігноруючи старі значення `desired`.

Це гарантує, що при виникненні мережевої партиції (Network Partition) відрізані від світу пристрої не продовжуватимуть виконувати застарілі та потенційно аварійні сценарії.

## Практичні шаблони в індустрії

Розділення бажаного і звітованого стану лежить в основі провідних хмарних та інфраструктурних платформ:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ПОРІВНЯННЯ РЕАЛІЗАЦІЙ                           │
├───────────────────┬──────────────────────┬─────────────────────────────┤
│ Платформа / Сфера │ Бажаний стан         │ Звітований стан             │
├───────────────────┼──────────────────────┼─────────────────────────────┤
│ AWS IoT Core      │ state.desired        │ state.reported              │
│ Kubernetes        │ spec                 │ status                      │
│ Azure IoT Hub     │ properties.desired   │ properties.reported         │
│ Terraform         │ .tf конфігурація     │ terraform.tfstate / reality │
│ GitOps (ArgoCD)   │ Git репозиторій      │ Стан кластера K8s           │
└───────────────────┴──────────────────────┴─────────────────────────────┤
```

### 1. Kubernetes Control Plane
Усі ресурси Kubernetes (Deployment, Pod, Service) описуються маніфестами, де користувач задає секцію `spec` (наприклад, `replicas: 5`). Агенти на вузлах (`kubelet`) та контролери (`kube-controller-manager`) підраховують фактичну кількість запущених контейнерів і записують її в секцію `status.replicas = 3`. Контролер виявляє дрейф `Δ = 5 - 3 = +2` і відправляє команди API на створення двох додаткових подів, доки `status.replicas == spec.replicas`.

### 2. Хмарні цифрові двійники (AWS IoT Device Shadow)
Сервіс AWS IoT створює віртуальний JSON-документ для кожного зареєстрованого пристрою. Мобільні додатки модифікують гілку `state.desired`. Якщо пристрій підключено через MQTT, брокер автоматично надсилає обчислену дельту в системний топік `$aws/things/{id}/shadow/update/delta`. Пристрій застосовує конфігурацію і публікує новий стан у `$aws/things/{id}/shadow/update` із заповненою гілкою `state.reported`.

### 3. Інфраструктура як код (Terraform Drift Detection)
У системному адмініструванні код декларативних файлів Terraform (`.tf`) виступає бажаним станом інфраструктури. Команда `terraform plan` виконує фазу **Observe**: вона опитує реальні API хмарних провайдерів (Reported State), порівнює їх із файлом `.tf` і формує граф змін (Delta DAG) для приведення хмари у відповідність до коду.

> 🔧 **Навіщо це в реальній розробці.**
> Без розділення бажаного і звітованого стану неможливо побудувати жодну масштабовану систему Інтернету речей або хмарної оркестрації. Спроба керувати парком із 50 000 лічильників газу чи електромобілів через прямі RPC-запити призведе до лавиноподібних збоїв при першому ж падінні базової станції стільникового зв'язку. Розділення стану перетворює ненадійні фізичні пристрої на стійкі асинхронні двійники: бізнес-логіка працює з гарантовано доступною моделлю бажаного стану, а цикли реконсиляції беруть на себе всю брудну роботу з автономного виправлення дрейфу.

## Типові виробничі помилки (Post-Mortem патерни)

При проектуванні та експлуатації систем з розділеним станом інженери регулярно припускаються трьох критичних помилок:

### 1. Нескінченний цикл реконсиляції (The Infinite Loop Hazard)
Поширена помилка в контролерах Kubernetes та IoT-демонах: у тілі функції узгодження розробник помилково записує телеметричні дані (наприклад, час останнього опитування `last_probe_time`) у секцію `spec` замість `status`. Оновлення `spec` генерує нову подію в черзі `watch`, що знову викликає функцію `Reconcile()`. Контролер входить у нескінченний рекурсивний цикл, спалюючи 100% CPU та перевантажуючи базу даних тисячами операцій запису на секунду.

*Правило:* контролер узгодження має право записувати лише в секцію `status` (Reported). Секція `spec` (Desired) належить виключно клієнтам і зовнішній керуючій логіці.

### 2. Читання із застарілого кешу (Stale Informer Cache Hazard)
Для зниження навантаження на базу даних контролери часто читають стан через локальний кеш (наприклад, Kubernetes Informers). Якщо після успішної модифікації зовнішнього ресурсу контролер негайно перевіряє стан через локальний кеш, який ще не встиг оновитися по мережі, контролер помилково вирішує, що дія не виконана, і відправляє дублюючу команду.

*Правило:* цикл узгодження повинен спиратися на монотонні версії та використовувати механізм оптимістичного очікування (Expectations Tracker) перед повторною модифікацією ресурсів.

### 3. Відсутність гістерезису на критичних актуаторах
Встановлення порогового правила «увімкнути охолодження при температурі >= 25.0°C» без зони гістерезису (наприклад, вимикання лише при <= 23.0°C) призводить до того, що при температурі 25.0°C пускове реле компресора клацає кожні 2 секунди через шум сенсора. Це виводить із ладу силову комутаційну апаратуру за кілька діб.

## Інженерні компроміси, ціна та межі застосування

Розділення стану не є безкоштовним універсальним рішенням. Воно вимагає усвідомлення архітектурних компромісів та обмежень:

### 1. Збільшення накладних витрат на збереження та трафік (Storage & Wire Amplification)
Замість збереження одного рядка конфігурації система змушена зберігати два повні документи (`desired` і `reported`), їхні версії та детальні часові мітки для кожного поля. При кожній зміні обчислюється і передається дельта. Для систем із мікроконтролерами з 16 КБ оперативної пам'яті це вимагає ретельної оптимізації структур даних і відмови від важких форматів на користь компактних бінарних схем.

### 2. Узгодженість у кінцевому підсумку (Eventual Consistency)
Система з розділеним станом не дає миттєвих синхронних гарантій. Коли користувач увімкнув підігрів сидінь в автомобілі через мобільний додаток, додаток показує статус «Очікує застосування», поки автомобіль не підтвердить факт увімкнення через `reported`. Якщо бізнес-процес вимагає строгої транзакційності за моделлю ACID тут і зараз (наприклад, банківський переказ між рахунками), модель зближення бажаного і звітованого стану не підходить.

### 3. Конвергенція проти критичних за часом дій (Hard Real-Time Latency)
Цикл узгодження оптимізований для *надійності зближення*, а не для *мінімізації мікросекундної затримки*. Якщо команді необхідно зупинити верстат у разі перетину оптичного бар'єра людиною за 5 мілісекунд, ця дія має виконуватися локальним апаратним перериванням на самому контролері, а не через хмарний цикл оновлення бажаного стану.

Декларативне розділення бажаного і звітованого станів залишається золотим стандартом там, де панує розподіленість, нестабільність каналів передачі та потреба в надійному автономному самозціленні систем будь-якого масштабу.
