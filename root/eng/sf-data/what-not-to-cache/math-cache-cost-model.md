# 🧮 Математична модель економіки та ефективності кешу

Коли інженер додає в розподілену систему кешувальний шар, інтуїція підказує, що запити стануть швидшими, а база даних — вільнішою. Проте в реальних системах кеш не завжди зменшує затримку: за низької частки влучань або високої частоти мутацій додатковий мережевий стрибок і витрати на інвалідацію роблять систему повільнішою, ніж пряме звернення до первинного сховища. Щоб точно визначити, які типи даних приносять виграш, а які генерують чисті збитки, потрібен строгий математичний апарат розрахунку середньої затримки, порогової частки влучань, пуассонівського балансу читань і записів, аналізу квантилів затримки, ентропії простору ключів та економічної вартості оперативної пам'яті.

## Середня затримка та поріг беззбитковості

Розглянемо розподілений сервіс, який отримує запити на читання сутностей. Без використання проміжного кешу кожен запит вирушає безпосередньо до первинного сховища (бази даних або дискового сховища). Позначимо час виконання прямого запиту як `T_origin`.

Якщо перед сховищем встановлено кеш, запит спочатку звертається до нього. Час читання з кешу позначимо як `T_cache`. Можливі два результати:

1. **Влучання (Cache Hit)** з імовірністю `h` (де `0 ≤ h ≤ 1`): дані знайдено в кеші, повна затримка становить `T_hit = T_cache`.
2. **Промах (Cache Miss)** з імовірністю `1 − h`: даних немає, сервіс змушений виконати читання з кешу, переконатися у відсутності ключа, звернутися до первинного сховища, отримати відповідь і зберегти її в кеш. Сумарний час становить `T_miss = T_cache + T_origin + T_write_cache`.

Для спрощення базового виведення знехтуємо асинхронним часом запису `T_write_cache` (припускаючи, що запис у кеш відбувається у фоновому потоці або паралельно з поверненням відповіді клієнту). Тоді середня очікувана затримка запиту `E[T]` обчислюється як математичне сподівання:

```
E[T]
= h · T_hit + (1 − h) · T_miss                      [математичне сподівання дискретних випадків]
= h · T_cache + (1 − h) · (T_cache + T_origin)      [підстановка часу влучання та промаху]
= h · T_cache + (1 − h) · T_cache + (1 − h) · T_origin [розкриття дужок]
= T_cache + (1 − h) · T_origin                      [спрощення: h + (1 - h) = 1]
```

Кешування є технічно виправданим (тобто знижує середню затримку), якщо математичне сподівання затримки з кешем строго менше за затримку без нього:

```
E[T] < T_origin                                     [умова ефективності кешу]
T_cache + (1 − h) · T_origin < T_origin             [підстановка виведеного виразу]
T_cache + T_origin − h · T_origin < T_origin         [розкриття дужок]
T_cache < h · T_origin                              [віднімання T_origin з обох частин]
h > T_cache / T_origin                              [ділення на T_origin]
```

Величину `h_min = T_cache / T_origin` називають **порогом беззбитковості кешу (Break-Even Hit Ratio)**. Якщо реальна частка влучань для конкретного типу даних менша за `h_min`, встановлення кешу **сповільнює** систему.

**Розрахунок порогової частки для типового мікросервісу:**

```
Час читання з Redis по мережі (T_cache)  = 1.5 мс
Час виконання індексованого SQL-запиту (T_origin) = 15.0 мс

h_min
= T_cache / T_origin                                [формула точки беззбитковості]
= 1.5 / 15.0                                        [підстановка виміряних значень]
= 0.10                                              [результат: поріг 10 %]
```

Якщо частка влучань для сутності становить лише 5 % (наприклад, для рідкісних пошукових фільтрів або унікальних звітів), середня затримка складе:

```
E[T]
= 1.5 + (1 − 0.05) · 15.0                           [підстановка h = 0.05]
= 1.5 + 0.95 · 15.0                                 [обчислення частки промахів]
= 1.5 + 14.25                                       [множення на час бази даних]
= 15.75 мс                                          [підсумок: зростання затримки]
```

Замість очікуваного прискорення кожен клієнт у середньому чекає на 0.75 мс довше, а інфраструктура витрачає додаткову оперативну пам'ять і мережевий трафік на обслуговування кешу.

## Багаторівнева модель: локальний пам'яттєвий кеш (L1) та розподілений кеш (L2)

У сучасних архітектурах нерідко використовують багаторівневе кешування:
- **L1 (In-process cache)**: локальна хеш-таблиця в адресній пам'яті процесу (`T_L1 ≈ 50 нс`).
- **L2 (Distributed cache)**: віддалений сервіс Redis / Memcached (`T_L2 ≈ 1.5 мс`).
- **L3 (Database Origin)**: дискова первинна база даних (`T_origin ≈ 20 мс`).

Нехай `h_1` — частка влучань у локальний кеш L1, а `h_2` — частка влучань у розподілений кеш L2 серед тих запитів, які промахнулися повз L1. Повна ймовірність влучання на рівні L2 дорівнює `(1 − h_1) · h_2`, а ймовірність промаху до первинної бази даних — `(1 − h_1) · (1 − h_2)`.

Середня затримка трирівневої системи виводиться як:

```
E[T_3tier]
= h_1 · T_L1 + (1 − h_1) · h_2 · (T_L1 + T_L2) + (1 − h_1) · (1 − h_2) · (T_L1 + T_L2 + T_origin) [зважена сума затримки за трьома рівнями]
= T_L1 + (1 − h_1) · T_L2 + (1 − h_1) · (1 − h_2) · T_origin                                     [групування доданків]
```

Звідси видно важливий архітектурний наслідок: якщо сутність є дешевою для обчислення в процесі (`T_origin < T_L2`), встановлення розподіленого кешу L2 строго погіршує затримку при будь-якому значенні `h_2 < 1`.

Якщо чисте локальне обчислення (наприклад, форматування рядка або перевірка прав у пам'яті) займає `T_compute = 2 мкс`, а звернення до Redis займає `T_L2 = 1.5 мс = 1500 мкс`, то поріг беззбитковості для L2 дорівнює:

```
h_min_L2 = T_L2 / T_compute = 1500 / 2 = 750
```

Оскільки частка влучань не може перевищувати 100 % (`h ≤ 1`), створення розподіленого кешу для дешевих локальних функцій є **математично неможливим для оптимізації**: звернення до мережі завжди в 750 разів повільніше за прямий розрахунок на CPU.

## Динаміка мутацій: пуассонівська модель читань і записів

У системах із частими змінами даних кожна операція запису призводить до одного з двох наслідків:
- **Інвалідація (Cache Invalidation)**: видалення застарілого запису з кешу.
- **Оновлення (Cache Update / Write-Through)**: перезапис значення новим вмістом.

Обидві операції мають ціну. Нехай потік запитів на читання ключа утворює найпростіший пуассонівський потік з інтенсивністю `λ_r` (кількість читань за секунду), а потік оновлень — незалежний пуассонівський потік з інтенсивністю `λ_w` (кількість записів за секунду). Кожен запис у кеші має максимальний час життя `TTL` (Time To Live).

Запис у кеші лишається валідним і корисним від моменту створення до першої з двох подій:
1. Закінчення часу життя `TTL`.
2. Приходу наступної операції запису (мутації), яка інвалідує ключ.

Час до наступної мутації `X_w` є випадковою величиною з експоненційним розподілом із щільністю ймовірності `f_w(t) = λ_w · e^(−λ_w · t)`. Відповідно, ефективний час валідності запису `T_valid` дорівнює `min(TTL, X_w)`.

Ймовірність того, що ключ буде прочитано хоча б один раз до того, як його буде інвалідовано або видалено за TTL, дорівнює частці корисних записів у кеш:

```
P(успішне повторне читання)
= P(перше читання настане раніше за інвалідацію та до завершення TTL)
= ∫[0..TTL] P(X_r < t | X_w = t) · f_w(t) dt + P(X_r < TTL) · P(X_w > TTL)
```

Для експоненційного закону розподілу ймовірність того, що перша подія читання настане раніше за першу подію запису, визначається відношенням інтенсивностей:

```
P(read_before_write) = λ_r / (λ_r + λ_w)
```

З урахуванням обмеження часу життя `TTL`, імовірність успішного влучання для свіжозакешованого значення набуває вигляду:

```
h(λ_r, λ_w, TTL) = (λ_r / (λ_r + λ_w)) · (1 − e^(−(λ_r + λ_w) · TTL))
```

Розглянемо три характерні режими поведінки системи:

### 1. Переважання записів над читанням (Write-Heavy, `λ_w ≫ λ_r`)
Нехай координати кур'єра оновлюються кожні 500 мс (`λ_w = 2.0 / с`), а користувач відкриває екран відстеження раз на 30 секунд (`λ_r = 0.033 / с`). Встановлено `TTL = 60 с`.

```
λ_r / (λ_r + λ_w)
= 0.033 / (0.033 + 2.0)                             [підстановка інтенсивностей]
= 0.033 / 2.033                                     [сума інтенсивностей у знаменнику]
≈ 0.0162                                            [частка читань: 1.62 %]

1 − e^(−(0.033 + 2.0) · 60)
= 1 − e^(−121.98)                                   [обчислення показника експоненти]
≈ 1.0                                               [експонента спадає до нуля]

h
≈ 0.0162 · 1.0                                      [множення ймовірностей]
= 0.0162                                            [підсумкова частка влучань: 1.62 %]
```

Частка влучань складає лише 1.62 %. Це значно нижче порогу беззбитковості `h_min = 10 %`. На кожні 100 записів у кеш припадає менше двох влучань. Решта 98 записів — це марне спалювання процесорного часу на серіалізацію та мережевих сокетів на запис і видалення ключів у Redis.

### 2. Короткий TTL за рідкісного читання (`TTL ≪ 1 / λ_r`)
Якщо дані читаються в середньому раз на хвилину (`λ_r = 0.0167 / с`, `λ_w = 0`), але розробник встановив `TTL = 5 с`, щоб мінімізувати вікно застарілості:

```
h
= 1 · (1 − e^(−0.0167 · 5))                         [підстановка інтенсивності та TTL = 5 с]
= 1 − e^(−0.0835)                                   [обчислення аргументу експоненти]
≈ 1 − 0.920                                         [значення експоненти]
= 0.080                                             [підсумок: 8.0 % влучань]
```

Запис живе 5 секунд і з імовірністю 92 % вмирає за таймаутом до того, як надійде наступний запит на читання. Кеш знову працює в збиток.

### 3. Рівноважний стан і критичне співвідношення
Щоб кешування окупало додаткові витрати на інвалідацію, відношення читань до записів `R = λ_r / λ_w` повинно задовольняти нерівність:

```
h(λ_r, λ_w, TTL) > h_min
λ_r / (λ_r + λ_w) > h_min / (1 − e^(−(λ_r + λ_w) · TTL))
```

За умови тривалого `TTL` критичне співвідношення спрощується:

```
R / (R + 1) > h_min
R > h_min / (1 − h_min)
```

Для `h_min = 0.10` отримуємо `R > 0.10 / 0.90 ≈ 0.111` (мінімум одне читання на дев'ять записів). Але якщо врахувати витрати на інвалідацію та подвійний мережевий I/O, емпіричний поріг рентабельності зміщується до `R ≥ 5` (на один запис має припадати щонайменше п'ять читань).

## Ентропія простору ключів та ймовірність влучання для одноразових запитів

Кешування спирається на нерівномірність звернень. Якщо потік запитів має високу інформаційну ентропію (наприклад, повнотекстовий пошук за довільними комбінаціями слів, аналітичні скани діапазонів або пакетний експорт), розподіл звернень наближається до дискретного рівномірного розподілу.

Нехай загальна кількість унікальних можливих ключів або запитів дорівнює `M`, а кеш здатний одночасно зберігати `K` записів (де `K ≪ M`). Кожен запит обирає випадковий ключ з імовірністю `1 / M` незалежно від попередніх звернень.

За стаціонарного режиму роботи кешу ймовірність того, що довільний новий запит виявить свій ключ у кеші, дорівнює відношенню обсягу кешу до потужності простору ключів:

```
h_uniform = K / M
```

**Оцінка для пошукових фільтрів та аналітики:**
Нехай користувачі генерують складні пошукові комбінації товарів (сортування, ціновий діапазон, категорії, геопозиція, наявність знижки), що створює `M = 10 000 000` унікальних станів пошукової видачі. Кеш на виділеному сервері вміщує `K = 20 000` результатів.

```
h_uniform = 20 000 / 10 000 000 = 0.002  (0.2 %)
```

Частка влучань становить мізерні 0.2 %, що у 50 разів менше за поріг беззбитковості `h_min = 10 %`. Спроба кешувати кожну комбінацію пошукових параметрів перетворює кеш на транзитну пам'ять із постійним витісненням (Thrashing): кожен новий запис негайно викидає щойно доданий ключ, не приносячи жодного повторного влучання.

## Вартість серіалізації, десеріалізації та навантаження на Garbage Collector

Коли об'єкт зберігається в розподіленому кеші, сервіс витрачає ресурси процесора на кодуванні та декодуванні структури даних (наприклад, перетворення між об'єктом мови програмування та JSON або Protocol Buffers).

Позначимо:
- `CPU_origin` — витрати CPU на виконання запиту в первинній БД та повернення відповіді сервісу.
- `CPU_ser` — процесорний час серіалізації об'єкта під час запису в кеш.
- `CPU_deser` — процесорний час десеріалізації об'єкта під час читання з кешу.
- `CPU_net` — процесорний час на обслуговування мережевого стеку сокетів (epoll, копіювання буферів ядра).

Повні витрати процесорного часу при роботі без кешу:

```
CPU_total_no_cache = CPU_origin
```

Повні витрати процесорного часу при роботі з кешем з урахуванням частки влучань `h`:

```
CPU_total_with_cache
= h · (CPU_deser + CPU_net) + (1 − h) · (CPU_net + CPU_origin + CPU_ser + CPU_net) [сума витрат CPU для влучань і промахів]
= CPU_net + h · CPU_deser + (1 − h) · (CPU_origin + CPU_ser + CPU_net)             [винесення базового мережевого overhead]
```

Якщо серіалізований об'єкт є великим (наприклад, дерево категорій чи повний каталог користувача розміром 5 МБ у форматі JSON), час парсингу `CPU_deser` у мовах із керованою пам'яттю (Go, Java, Node.js, C#) може досягати 10–25 мс. Крім того, створення сотень тисяч дрібних об'єктів у купі під час парсингу створює пікове навантаження на збирач сміття (Garbage Collector), провокуючи паузи `Stop-The-World`.

Якщо час десеріалізації перевищує час отримання компактного бінарного результату з локальної пам'яті або швидкого дискового індексу (`CPU_deser > CPU_origin`), кешування у форматі високорівневих текстових DTO призводить до **зростання навантаження на CPU прикладного вузла** навіть при високій частці влучань.

## Аналіз хвостових квантилів затримки (p99 і p99.9)

Середня затримка `E[T]` приховує поведінку системи на граничних навантаженнях. У розподілених системах якість обслуговування визначається перцентилями `p95`, `p99` та `p99.9`.

Коли запит зазнає промаху повз кеш, він створює додаткове навантаження на базу даних. Якщо промахи відбуваються синхронно (наприклад, під час одночасного закінчення TTL для популярного ключа або примусової інвалідації), виникає ефект «стадного набігу» (Cache Stampede).

Нехай `N_conc` клієнтів одночасно звертаються за ключем, якого немає в кеші. Без механізму м'ютекса блокування запитів (Singleflight / Mutex) усі `N_conc` запитів одночасно надходять до бази даних. Час відповіді бази за наявності черги запитів описується моделлю теорії масового обслуговування `M/M/1`:

```
T_origin_loaded = T_origin_base / (1 − ρ)
```

де `ρ = λ_miss / μ_DB` — коефіцієнт завантаження пулу з'єднань бази даних.

Коли частка влучань `h` падає:

```
λ_miss = (1 − h) · λ_total
```

Якщо `λ_miss` наближається до максимальної пропускної здатності бази `μ_DB` (`ρ → 1`), затримка бази прямує до нескінченності. У цей момент квантиль `p99` затримки зростає не лінійно, а експоненційно:

```
p99_latency ≈ T_cache + T_origin_base / (1 − (1 − h) · λ_total / μ_DB) · ln(100)
```

Це доводить, що некешовані дані з високою дисперсією звернень або нестабільним TTL здатні деградувати не лише власні запити, але й зруйнувати затримку `p99` для всіх сусідніх сервісів, які ділять із ними спільний пул з'єднань до бази даних.

## Економічна вартість збереження: модель TCO пам'яті проти диска

Крім часової затримки, кеш має пряму фінансову вартість. Збереження даних у швидкій оперативній пам'яті (RAM) вузлів Redis чи Memcached у десятки разів дорожче за збереження на дискових накопичувачах (NVMe SSD) у хмарній інфраструктурі.

Позначимо:
- `C_RAM` — вартість зберігання одного гігабайта даних у RAM за місяць ($ / ГБ · міс).
- `C_SSD` — вартість зберігання одного гігабайта даних на NVMe SSD за місяць ($ / ГБ · міс).
- `C_CPU_query` — вартість процесорного часу на виконання одного запиту до первинної бази даних ($ / млн запитів).
- `N` — загальна кількість сутностей у системі.
- `S` — середній розмір серіалізованої сутності в байтах.
- `Q` — сумарна кількість запитів до сутності за місяць.

Сукупна вартість володіння (TCO — Total Cost of Ownership) без кешування визначається лише навантаженням на базу даних:

```
TCO_no_cache = N · S · C_SSD + Q · C_CPU_query
```

Сукупна вартість із використанням суцільного кешу (де кешуються всі `N` об'єктів):

```
TCO_with_cache = N · S · C_SSD + N · S · C_RAM + (1 − h) · Q · C_CPU_query + Q · C_cache_ops
```

Кешування є економічно вигідним тоді й лише тоді, коли зекономлена вартість запитів до бази даних перевищує вартість оренди оперативної пам'яті та операцій з кешем:

```
TCO_with_cache < TCO_no_cache
N · S · C_RAM + Q · C_cache_ops < h · Q · C_CPU_query
h > (N · S · C_RAM + Q · C_cache_ops) / (Q · C_CPU_query)
```

**Порівняльний аналіз на прикладі довгого хвоста (Long-Tail Data):**
Уявімо каталог із `N = 50 000 000` товарів. Середній розмір картки товару `S = 4 КБ`.
Загальний обсяг каталогу: `50 000 000 · 4 КБ = 200 ГБ`.

```
Вартість RAM у хмарі (C_RAM) = 6.50 $ / ГБ · місяць
Вартість 200 ГБ RAM для кешу  = 200 · 6.50 = 1 300 $ / місяць

Кількість запитів до хвоста каталогу (Q_tail) = 5 000 000 запитів / місяць
Вартість читання з БД (C_CPU_query)           = 0.05 $ / 10 000 запитів = 5.00 $ / млн запитів
Повна вартість виконання всіх цих запитів у БД = 5 · 5.00 = 25 $ / місяць
```

Якщо повністю закешувати всі 50 мільйонів товарів, щоб отримати навіть 100 % влучань у хвості (`h = 1.0`), бізнес витратить **$1300 на місяць** на оперативну пам'ять заради економії **$25 навантаження на базу даних**.

Це демонструє ключовий висновок економічної моделі: **дані з рівномірним розподілом і низькою частотою повторних звернень (довгий хвіст) економічно збитково тримати в пам'яті кешу**. Кешувати слід лише вершину розподілу Зіпфа (гаряче ядро), де невелика частка пам'яті обслуговує переважну більшість запитів.
