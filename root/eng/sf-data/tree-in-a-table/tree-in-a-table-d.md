В інтернет-магазині із каталогом на пів мільйона найменувань товарна сітка організована у вигляді багаторівневого дерева категорій: «Електроніка → Комп'ютери → Ноутбуки → Ультрабуки». Користувач відкриває розділ «Комп'ютери» та очікує побачити сумарну кількість товарів у всіх вкладених підкатегоріях, навігаційний ланцюжок предків («хлібні крихти») та фільтри за характеристиками. Якщо база даних зберігає зв'язки між категоріями наївно, сервер застосунку змушений виконувати десятки послідовних рекурсивних SQL-запитів до кожного дочірнього вузла. Мережева затримка (network round-trip) множиться на кількість рівнів і розгалужень: формується антипатерн «N+1 запитів», час відповіді сторінки перевищує 800 мілісекунд, пул з'єднань із базою вичерпується, а будь-яка циклічна помилка в даних призводить до нескінченної рекурсії та аварійної зупинки робочих процесів.

Ця проблема виникає через фундаментальний конфлікт між природою даних та архітектурою реляційних СУБД. Ієрархія (грец. *hierarchia*, від *hieros* — священний та *arche* — влада/початок) є рекурсивним математичним графом довільної глибини. Натомість реляційне відношення — це пласка двовимірна множина кортежів, де перша нормальна форма (1NF) забороняє вкладені списки чи масиви покажчиків всередині клітинок. Для ефективного збереження, навігації та модифікації дерев у реляційних таблицях розроблено чотири фундаментальні моделі, кожна з яких пропонує власний інженерний компроміс між швидкістю читання піддерев та вартістю модифікації структури.

## Невідповідність моделей: граф у плаському відношенні

Математично дерево визначається як зв'язний орієнтований ациклічний граф:

```
T = (V, E, r)
```

де:
- `V` — скінченна множина вершин (вузлів) кардинальності (лат. *cardinalis* — головний, від *cardo* — стрижень/дверна завіса) `|V| = n`;
- `E ⊆ V × V` — множина напрямлених ребер від батька до дитини;
- `r ∈ V` — єдиний корінь із нульовим півстепенем заходу (`in-degree(r) = 0`);
- кожен інший вузол `v ≠ r` має рівно одного батька (`in-degree(v) = 1`).

Реляційна алгебра Едгара Кодда оперує логікою першого порядку над скінченними кортежами фіксованої арності. У класичній реляційній алгебрі операції селекції, проекції та з'єднання (`JOIN`) мають фіксовану глибину розгортання: один оператор з'єднання може зв'язати батька з дитиною, два оператори — з онуком. Проте реляційна алгебра першого порядку принципово не містить оператора довільного транзитивного замикання (транзитивність від лат. *transitivus* — перехідний, від *transire* — переходити): неможливо одним фіксованим реляційним виразом отримати всіх нащадків довільного вузла, якщо глибина дерева невідома на момент компіляції запиту.

![Конфлікт ієрархічного графа та пласкої таблиці](/root/eng/sf-data/tree-in-a-table/img/fig1-tree-relational-conflict.svg)
*Конфлікт між графовою рекурсивною природою ієрархій та вимогами першої нормальної форми (1NF) реляційних таблиць.*

З погляду дескриптивної складності (теореми Фагіна та мови `FO(TC)`), виразність логіки першого порядку обмежена локальними властивостями околів вершин. Обчислення зв'язності та досяжності в графах вимагає оператора найменшої фіксованої точки (Least Fixed Point, LFP), що виходить за межі первинного реляційного числення кортежів.

Якщо намагатися розв'язати проблему за допомогою жорстко зафіксованої кількості з'єднань (`LEFT JOIN ... LEFT JOIN ... LEFT JOIN ...`), схема стає надзвичайно крихкою. Вона вимагає регулярної ручної модифікації прикладної логіки щоразу, коли глибина вкладеності перевищує заздалегідь прописаний ліміт. Збереження дерева у вигляді вкладених JSONB-документів або масивів усередині одного рядка руйнує реляційну атомарність, унеможливлює декларативну посиланняльну цілісність через зовнішні ключі (Foreign Keys) і блокує паралельне оновлення окремих гілок різними транзакціями через блокування всього рядка-документа.

Детальний аналіз історичної еволюції цієї проблеми — від фізичних дискових вказівників у СУБД IBM IMS та CODASYL до появи стандарту SQL:1999 — викладено у вставці [📜 Історія ієрархічних даних у базах: від навігаційних мереж до SQL-рекурсії](root:sf-data/tree-in-a-table/hist-hierarchical-data-sql.md).

## Модель 1: Список суміжності та рекурсивні CTE

Найпростішим і найприроднішим способом представлення зв'язків є **список суміжності** (Adjacency List; термін *суміжність* походить від праслов'янського *межа* — прилеглий через спільну границю, лат. *adjacere* — прилягати). Кожен рядок таблиці представляє один вузол дерева та містить явне посилання на свій безпосередній батьківський вузол через зовнішній ключ:

```sql
CREATE TABLE categories (
    id SERIAL PRIMARY KEY,
    parent_id INT NULL REFERENCES categories(id) ON DELETE CASCADE,
    name VARCHAR(128) NOT NULL
);

CREATE INDEX idx_categories_parent_id ON categories(parent_id);
```

### Механізм виконання рекурсивних запитів (WITH RECURSIVE)

До появи стандарту SQL:1999 вибірка піддерева зі списку суміжності вимагала процедурного циклу на клієнті. Стандарт SQL:1999 увів конструкцію `WITH RECURSIVE` (Common Table Expression, CTE; рекурсія від лат. *recursio* — повернення назад), яка реалізує декларативне обчислення найменшої фіксованої точки безпосередньо всередині рушія бази даних.

Рекурсивний запит складається з двох частин, об'єднаних оператором `UNION ALL`:
1. **Якірний член (Anchor Member):** базовий невибірковий запит, що повертає початковий вузол (або множину стартових вузлів) нульового рівня.
2. **Рекурсивний член (Recursive Member):** запит, що з'єднує робочу проміжну таблицю попереднього кроку з основною таблицею за умовою `child.parent_id = parent.id`.

```sql
WITH RECURSIVE category_tree AS (
    -- Якірний член: починаємо з обраного кореня (наприклад, id = 1)
    SELECT id, parent_id, name, 0 AS depth, ARRAY[id] AS path
    FROM categories
    WHERE id = 1

    UNION ALL

    -- Рекурсивний член: приєднуємо дітей до знайдених батьків
    SELECT c.id, c.parent_id, c.name, ct.depth + 1, ct.path || c.id
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT id, parent_id, name, depth, path
FROM category_tree
ORDER BY depth, id;
```

![Список суміжності та рекурсивний CTE](/root/eng/sf-data/tree-in-a-table/img/fig2-adjacency-list-and-cte.svg)
*Архітектура списку суміжності та покрокова ітерація рекурсивного табличного виразу до досягнення фіксованої точки.*

Рушій бази даних виконує цей запит за суворим ітеративним алгоритмом:
1. Виконується якірний запит. Отримані рядки записуються у дві внутрішні структури: накопичувальний результат (`Result`) та проміжну робочу таблицю (`Intermediate`).
2. Доки `Intermediate` не порожня:
   - Рекурсивний член виконується, де ім'я CTE посилається виключно на вміст таблиці `Intermediate`.
   - Отримані нові рядки замінюють вміст `Intermediate` і дописуються до `Result`.
3. Коли чергова ітерація повертає нуль рядків (досягнуто листків дерева), досягається фіксована точка. Виконання циклу зупиняється, і клієнт отримує таблицю `Result`.

Під час аналізу плану запиту (`EXPLAIN ANALYZE`) у СУБД PostgreSQL рекурсивний CTE відображається як вузол плану `Recursive Union`. Для кожної ітерації планувальник виконує `WorkTable Scan` над проміжною таблицею та з'єднує її з основною таблицею через `Index Scan` за індексом `idx_categories_parent_id`. Якщо розмір проміжних даних перевищує виділений ліміт оперативної пам'яті (`work_mem`), проміжні результати скидаються на диск у тимчасові файли (`temp files`), що знижує швидкість виконання.

Для оптимізації рекурсивного сканування часто створюють покриваючий індекс (Covering Index) за допомогою виразу `CREATE INDEX idx_tree_covering ON categories(parent_id) INCLUDE (id, name)`. Це дозволяє виконувати `Index Only Scan` без звернення до основних сторінок таблиці (Heap Pages), скорочуючи кількість читань сторінок пам'яті до абсолютного мінімуму.

### Захист від циклічних посилань

Якщо через помилку в даних або збій транзакції утворюється цикл (наприклад, вузол 3 посилається на вузол 2, а вузол 2 — на вузол 3), класичний рекурсивний CTE потрапляє у нескінченний цикл, генеруючи гігабайти тимчасових даних і вичерпуючи дисковий простір (`work_mem` / `temp_tablespaces`).

Для запобігання зацикленню застосовують два підходи:
1. **Масив відвіданих ідентифікаторів:** у запит додається стовпчик `ARRAY[id]`, і рекурсивний крок перевіряє умову `WHERE NOT (c.id = ANY(ct.path))`.
2. **Конструкція CYCLE (SQL:2008 / PostgreSQL 14+):**
   ```sql
   WITH RECURSIVE category_tree AS (...)
   CYCLE id SET is_cycle USING path_history
   SELECT * FROM category_tree WHERE NOT is_cycle;
   ```

### Характеристики складності

- **Вставка нового вузла:** `O(1)`. Достатньо вставити один рядок із вказанням `parent_id`.
- **Переміщення піддерева:** `O(1)`. Оновлюється рівно одне поле `parent_id` у корені переміщуваної гілки; усі її нащадки автоматично залишаються прив'язаними до неї.
- **Видалення піддерева:** `O(k)` (де `k` — кількість нащадків) за наявності каскадного зовнішнього ключа `ON DELETE CASCADE`.
- **Вибірка піддерева або предків:** `O(k)` ітерацій із накладними витратами на проміжні таблиці в пам'яті.

Список суміжності є найкращим вибором для систем із частими змінами структури (OLTP), але для глибоких дерев із частими складними агрегаційними запитами навантаження на процесор СУБД може бути відчутним.

## Модель 2: Матеріалізований шлях (Materialized Path)

**Матеріалізований шлях** (Materialized Path; матеріалізація від лат. *materialis* — речовинний, від *materia* — речовина) усуває необхідність рекурсивних з'єднань завдяки явному зберіганню повного родоводу вузла у вигляді текстового рядка або масиву ідентифікаторів безпосередньо в кожному записі.

Кожен запис містить конкатенацію ідентифікаторів усіх своїх предків від кореня до поточного вузла, розділених спеціальним символом (найчастіше слешем або крапкою): `'/1/2/4/'`.

```sql
CREATE TABLE categories_path (
    id SERIAL PRIMARY KEY,
    path VARCHAR(1024) NOT NULL, -- Формат: '/1/2/4/'
    name VARCHAR(128) NOT NULL
);

-- B-Tree індекс для текстового пошуку за шаблоном (префіксне сканування)
CREATE INDEX idx_categories_path_prefix ON categories_path (path varchar_pattern_ops);
```

![Матеріалізований шлях](/root/eng/sf-data/tree-in-a-table/img/fig3-materialized-path.svg)
*Префіксна адресація матеріалізованого шляху: миттєва вибірка піддерева без рекурсії та каскадне оновлення префіксів при переміщенні.*

### Операції над шляхами

Завдяки префіксній структурі ієрархічні запити перетворюються на стандартні рядкові операції:

**1. Вибірка всіх нащадків піддерева:**
Щоб отримати категорію «Електроніка» (шлях `'/1/2/'`) та всі її підкатегорії будь-якої глибини, виконується простий префіксний запит:
```sql
SELECT * FROM categories_path
WHERE path LIKE '/1/2/%'
ORDER BY path;
```
СУБД використовує звичайний B-Tree індекс, виконуючи швидке префіксне діапазонне сканування без жодного рекурсивного виклику. Важливо використовувати операторний клас `varchar_pattern_ops` (у PostgreSQL): стандартний B-Tree індекс використовує правила сортування поточної мовної локалі (Collation), через що планувальник не може застосувати індексне сканування для виразів `LIKE 'prefix%'`. Операторний клас `varchar_pattern_ops` вимикає локалезалежні правила та зіставляє байти напряму.

**2. Вибірка всіх предків («хлібні крихти»):**
Якщо відомий шлях поточного вузла `'/1/2/4/'`, його предками є вузли з ідентифікаторами 1, 2 та 4. Їх можна отримати, розбивши рядок на масив:
```sql
SELECT * FROM categories_path
WHERE id = ANY(string_to_array(trim(both '/' from '/1/2/4/'), '/')::int[])
ORDER BY length(path);
```

**3. Переміщення піддерева:**
Якщо категорію «Електроніка» (`'/1/2/'`) потрібно перенести всередину категорії «Одяг» (`'/1/3/'`), новий шлях для неї стане `'/1/3/2/'`. Переміщення всієї гілки виконується одним масовим оператором заміни текстового префікса:
```sql
UPDATE categories_path
SET path = '/1/3/2/' || substring(path from length('/1/2/') + 1)
WHERE path LIKE '/1/2/%';
```

### Спеціалізований тип PostgreSQL: ltree

У СУБД PostgreSQL існує вбудований модуль `ltree`, який оптимізує матеріалізовані шляхи на рівні бінарного представлення. Замість неефективних рядків `VARCHAR` шляхи зберігаються у компактному двійковому форматі міток із крапками (`Top.Electronics.Phones`).

Модуль надає спеціалізовані оператори та індекси:
- `<@` — оператор «є нащадком» (`path <@ 'Top.Electronics'`);
- `@>` — оператор «є предком» (`path @> 'Top.Electronics.Phones'`);
- `~` — зіставлення за регулярними виразами над рівнями дерева (`'Top.*{1,2}.Phones'`);
- **GiST / GIN індекси:** забезпечують екстремально швидку фільтрацію навіть при мільйонах записів за допомогою бітових сигнатур (Signature Bitmaps).

### Характеристики складності та підводні камені

- **Читання піддерева:** `O(log N + k)` — швидкість звичайного пошуку за діапазоном B-Tree.
- **Вставка нового листка:** `O(1)` — формується конкатенацією `parent.path || new_id || '/'`.
- **Переміщення гілки:** `O(k)` — вимагає блокування та перезапису рядків для всіх `k` нащадків переміщуваного вузла.
- **Головний дефект:** відсутність декларативної посиланняльної цілісності. Якщо хтось видалить проміжний вузол або вручну змінить рядок шляху в обхід бізнес-логіки, структура дерева буде пошкоджена без попередження від СУБД. Крім того, при паралельному переміщенні гілок транзакції повинні використовувати блокування `SELECT FOR UPDATE` над усім піддеревом, щоб запобігти утворенню розірваних шляхів.

## Модель 3: Вкладені множини (Nested Sets)

Модель **вкладених множин** (Nested Sets), запропонована Джо Селко у 1996 році, розглядає дерево не як набір вузлів і ребер, а як систему вкладених одне в одне числових множин (інтервалів; інтервал від лат. *intervallum* — проміжок між валами укріплення, від *inter* — між та *vallum* — вал).

У цій моделі кожен вузол отримує два цілих числа: лівий ключ `lft` та правий ключ `rgt`. Ці ключі формуються за допомогою повного ейлерового обходу графа в глибину (DFS). Під час першого входу у вузол лічильник кроків записується в `lft`, алгоритм рекурсивно обходить усіх дітей, і перед виходом із вузла поточне значення лічильника записується в `rgt`.

```sql
CREATE TABLE categories_nested (
    id SERIAL PRIMARY KEY,
    lft INT NOT NULL,
    rgt INT NOT NULL,
    name VARCHAR(128) NOT NULL,
    CONSTRAINT chk_nested_valid CHECK (lft < rgt)
);

CREATE INDEX idx_nested_lft ON categories_nested (lft);
CREATE INDEX idx_nested_rgt ON categories_nested (rgt);
CREATE INDEX idx_nested_range ON categories_nested (lft, rgt);
```

![Вкладені множини Джо Селко](/root/eng/sf-data/tree-in-a-table/img/fig4-nested-sets-intervals.svg)
*Топологічне інтервальне кодування моделі вкладених множин: миттєве діапазонне сканування на читання та висока ціна зсуву ключів на запис.*

### Топологічні властивості інтервалів

Математичний фундамент моделі базується на строгому геометричному вкладенні числових відрізків `[lft, rgt]`:
1. Вузол `B` є нащадком вузла `A` тоді й лише тоді, коли інтервал `[lft_B, rgt_B]` строго міститься всередині інтервалу `[lft_A, rgt_A]`:
   ```
   A.lft < B.lft  ТА  B.rgt < A.rgt
   ```
2. Будь-які два інтервали в дереві або строго вкладені один в один, або повністю не перетинаються. Ситуація часткового перекриття відрізків математично неможлива.
3. Кількість усіх нащадків вузла (розмір піддерева) обчислюється без звернення до бази:
   ```
   Descendants = (rgt - lft - 1) / 2
   ```
4. Вузол є листком дерева (не має дітей) тоді й лише тоді, коли:
   ```
   rgt - lft = 1
   ```

Строге математичне доведення теореми про вкладення інтервалів та матричні представлення порядків наведено у вставці [🧮 Математичні основи деревоподібних порядків: інтервальне кодування та транзитивне замикання](root:sf-data/tree-in-a-table/math-nested-sets-intervals.md).

### Канонічні запити у моделі Селко

**1. Вибірка всього піддерева:**
Для отримання всіх нащадків кореня `id = 2` (з відомими `lft = 2` та `rgt = 7`) не потрібні жодні з'єднання чи рекурсії:
```sql
SELECT * FROM categories_nested
WHERE lft BETWEEN 2 AND 7
ORDER BY lft;
```
Цей запит є найшвидшим з усіх можливих у реляційних базах: він зводиться до одного апаратного B-Tree діапазонного сканування.

**2. Вибірка всіх предків до кореня («хлібні крихти»):**
Для вузла з `lft = 5` його предками є всі вузли, чий лівий ключ менший за 5, а правий — більший за 5:
```sql
SELECT * FROM categories_nested
WHERE lft < 5 AND rgt > 5
ORDER BY lft ASC;
```

**3. Визначення глибини вузлів:**
Глибина кожного вузла в дереві дорівнює кількості предків, що його оточують:
```sql
SELECT node.name, COUNT(parent.id) - 1 AS depth
FROM categories_nested AS node
JOIN categories_nested AS parent
  ON node.lft BETWEEN parent.lft AND parent.rgt
GROUP BY node.id, node.name, node.lft
ORDER BY node.lft;
```

### Катастрофа модифікації даних у вкладених множинах

Феноменальна швидкість читання компенсується критичним недоліком: екстремальною ціною операцій запису.

Оскільки між сусідніми ключами немає вільних проміжків, вставка одного нового вузла вимагає «розсунути» числовий простір на 2 одиниці. Для цього необхідно оновити стовпчики `lft` та `rgt` в усіх рядках таблиці, чиї значення розташовані праворуч від точки вставки:

```sql
BEGIN;
-- Звільняємо місце для нового вузла в позиції :target_rgt
UPDATE categories_nested SET rgt = rgt + 2 WHERE rgt >= :target_rgt;
UPDATE categories_nested SET lft = lft + 2 WHERE lft > :target_rgt;

-- Вставляємо новий вузол
INSERT INTO categories_nested (lft, rgt, name)
VALUES (:target_rgt, :target_rgt + 1, 'Нова категорія');
COMMIT;
```

У високонавантаженому OLTP-середовищі такий `UPDATE` блокує половину таблиці монопольними блокуваннями рядків (`ExclusiveLock`), що миттєво створює черги транзакцій та взаємні блокування (deadlocks). У СУБД MySQL з рушієм InnoDB це призводить до блокування інтервалів індексу (Next-Key / Gap Locks), що унеможливлює паралельні вставки сусідніми сесіями. Через це класична модель вкладених множин практично не застосовується для динамічних дерев із частими операціями додавання чи переміщення вузлів.

Для подолання цієї проблеми існують теоретичні модифікації на основі **дробових інтервалів** (Fractional Nested Intervals), де координати вузлів задаються раціональними числами `p/q` з використанням дерева Штерна-Броко (Stern-Brocot Tree). Новий вузол отримує інтервал-медіанту між двома сусідніми дробами без перенумерації існуючих записів, проте точність обмежена розрядністю типів із плаваючою або довільною точністю (`NUMERIC`).

## Модель 4: Таблиця замикання (Closure Table)

Модель **таблиці замикання** (Closure Table; замикання від лат. *clausura* / укр. *замикати* — операція отримання замкненої множини) повністю розділяє зберігання сутностей та зберігання структури зв'язків.

Замість збереження структурних атрибутів (`parent_id`, `path`, `lft`/`rgt`) всередині основної таблиці створюється окрема нормалізована таблиця-міст (Bridge Table), яка матеріалізує всі прямі та транзитивні шляхи між усіма парами предків і нащадків у дереві:

```sql
-- Таблиця сутностей (не містить жодних зовнішніх ключів дерева)
CREATE TABLE categories_node (
    id SERIAL PRIMARY KEY,
    name VARCHAR(128) NOT NULL
);

-- Таблиця замикання: зберігає всі пари (предок, нащадок) та відстань між ними
CREATE TABLE category_closure (
    ancestor_id INT NOT NULL REFERENCES categories_node(id) ON DELETE CASCADE,
    descendant_id INT NOT NULL REFERENCES categories_node(id) ON DELETE CASCADE,
    depth INT NOT NULL,
    PRIMARY KEY (ancestor_id, descendant_id)
);

CREATE INDEX idx_closure_descendant ON category_closure (descendant_id, depth);
```

![Таблиця замикання](/root/eng/sf-data/tree-in-a-table/img/fig5-closure-table.svg)
*Матриця транзитивних зв'язків таблиці замикання: швидкі індексовані з'єднання та підтримка посилальної цілісності.*

У таблицю замикання обов'язково записуються три типи зв'язків:
1. **Рефлексивний зв'язок (Self-loop):** зв'язок вузла із самим собою з нульовою глибиною `(id, id, depth = 0)`. Це спрощує SQL-запити, дозволяючи включати сам вузол у вибірку піддерева без додаткового `UNION`.
2. **Прямий батьківський зв'язок:** `(parent_id, child_id, depth = 1)`.
3. **Транзитивні зв'язки:** пари для всіх дідусів, прадідів і прапрадідів `(ancestor_id, descendant_id, depth = k)`.

### Канонічні операції над таблицею замикання

**1. Вибірка всього піддерева:**
```sql
SELECT n.*, c.depth
FROM categories_node n
JOIN category_closure c ON n.id = c.descendant_id
WHERE c.ancestor_id = :target_root_id
ORDER BY c.depth;
```
Запит виконує просте індексне з'єднання за первинним ключем: він не потребує рекурсії CTE, текстового парсингу чи блокування числових просторів.

**2. Вибірка тільки прямих дітей:**
Достатньо додати фільтр за глибиною:
```sql
SELECT n.*
FROM categories_node n
JOIN category_closure c ON n.id = c.descendant_id
WHERE c.ancestor_id = :parent_id AND c.depth = 1;
```

**3. Вибірка всіх предків («хлібні крихти»):**
```sql
SELECT n.*, c.depth
FROM categories_node n
JOIN category_closure c ON n.id = c.ancestor_id
WHERE c.descendant_id = :target_node_id
ORDER BY c.depth DESC;
```

**4. Вставка нового вузла:**
Щоб додати новий вузол `new_id` до батька `parent_id`, потрібно скопіювати всі шляхи, що вели до батька, збільшивши їхню глибину на 1, і додати власний рефлексивний запис:
```sql
INSERT INTO category_closure (ancestor_id, descendant_id, depth)
SELECT ancestor_id, :new_id, depth + 1
FROM category_closure
WHERE descendant_id = :parent_id
UNION ALL
SELECT :new_id, :new_id, 0;
```
Ця операція виконується за сталий час `O(depth)` без блокування інших вузлів таблиці.

**5. Переміщення піддерева:**
Перенесення піддерева `moving_id` під нового батька `new_parent_id` складається з двох кроків:
- Видаляються старі зв'язки між предками попереднього батька та всіма нащадками переміщуваної гілки;
- Створюються нові зв'язки шляхом декартового добутку (`CROSS JOIN`) між предками нового батька та нащадками переміщуваного вузла.

```sql
BEGIN;
-- Крок 1: Видалення старих предків для переміщуваного піддерева
DELETE FROM category_closure
WHERE descendant_id IN (
    SELECT descendant_id FROM category_closure WHERE ancestor_id = :moving_id
)
AND ancestor_id IN (
    SELECT ancestor_id FROM category_closure
    WHERE descendant_id = :moving_id AND ancestor_id != :moving_id
);

-- Крок 2: Встановлення нових зв'язків
INSERT INTO category_closure (ancestor_id, descendant_id, depth)
SELECT supertree.ancestor_id, subtree.descendant_id, supertree.depth + subtree.depth + 1
FROM category_closure AS supertree
CROSS JOIN category_closure AS subtree
WHERE supertree.descendant_id = :new_parent_id
  AND subtree.ancestor_id = :moving_id;
COMMIT;
```

## Порівняльний інженерний аналіз моделей

Кожна з розглянутих моделей оптимізує певний набір операцій ціною ускладнення інших. Вибір архітектури визначається профілем навантаження системи: співвідношенням операцій читання піддерев до операцій вставки та переміщення вузлів.

| Критерій оцінки | Список суміжності (Adjacency List + CTE) | Матеріалізований шлях (Materialized Path) | Вкладені множини (Nested Sets) | Таблиця замикання (Closure Table) |
| :--- | :--- | :--- | :--- | :--- |
| **Читання піддерева** | Повільне (рекурсивні `JOIN` у пам'яті) | Швидке (префіксне B-Tree сканування) | Екстремально швидке (один `BETWEEN`) | Екстремально швидке (індексний `JOIN`) |
| **Читання предків** | Повільне (рекурсивний підйом по CTE) | Швидке (розбір рядка шляху) | Швидке (`lft < X AND rgt > X`) | Екстремально швидке (індексний `JOIN`) |
| **Вставка нового вузла** | Екстремально швидка `O(1)` | Швидка `O(1)` | Катастрофічна (блокує всю таблицю) | Швидка `O(depth)` |
| **Переміщення піддерева** | Екстремально швидке `O(1)` (один `UPDATE`) | Помірне `O(k)` (оновлення префікса) | Катастрофічне (перерахунок ключів) | Швидке `O(k · depth)` (декартів добуток) |
| **Видалення піддерева** | Швидке (`ON DELETE CASCADE`) | Помірне (`DELETE WHERE path LIKE`) | Катастрофічне (перерахунок ключів) | Швидке (`ON DELETE CASCADE`) |
| **Витрати пам'яті** | Мінімальні `O(N)` | Низькі `O(N · length)` | Мінімальні `O(N)` | Помірні `O(N · depth)` (у середньому `N log N`) |
| **Посиланняльна цілісність**| Повна (нативні Foreign Keys) | Відсутня (рядковий формат) | Відсутня (числові інтервали) | Повна (нативні Foreign Keys) |
| **Підтримка DAG (орграфів)**| Ні (лише один батько) | Складно (дублювання рядків) | Ні (лише строгі дерева) | Так (природна підтримка поліієрархій) |

У сучасних розподілених архітектурах часто використовують гібридні підходи: список суміжності слугує первинним джерелом правди (Single Source of Truth) в операційній реляційній базі даних OLTP завдяки максимальній швидкості транзакційного запису та суворій посиланняльній цілісності, тоді як матеріалізовані шляхи або транзитивні замикання автоматично генеруються фоновими асинхронними процесами (CDC / triggers) та передаються в кеші або аналітичні пошукові сховища (Elasticsearch / ClickHouse) для миттєвої фільтрації та навігації.

Таблиця замикання також вирізняється унікальною властивістю: вона є єдиною моделлю, яка без зміни реляційної схеми природно підтримує орієнтовані ациклічні графи (DAG) та поліієрархії, де один і той самий товар або категорія може одночасно мати кількох різних батьків (наприклад, категорія «Смарт-годинники» належить одночасно і до «Електроніки», і до «Аксесуарів»).

### Транзакційна ізоляція та поведінка під час конкурентних блокувань

Особливу увагу в багатокористувацьких системах слід приділяти рівням ізоляції транзакцій:
1. **Список суміжності:** за рівня ізоляції `READ COMMITTED` операція переміщення вузла `UPDATE categories SET parent_id = :new_parent WHERE id = :node_id` блокує лише один цільовий рядок за допомогою ексклюзивного рядкового блокування (`RowExclusiveLock`). Проте паралельні транзакції, що одночасно переміщують вузол `A` під `B`, а вузол `B` під `A`, можуть створити взаємне блокування або утворити циклічний зв'язок, якщо транзакції не використовують явне блокування кореня дерева.
2. **Матеріалізований шлях:** масовий `UPDATE categories_path SET path = ... WHERE path LIKE '/1/2/%'` захоплює блокування на всі рядки піддерева. Якщо інша сесія одночасно намагається вставити новий дочірній елемент у це ж піддерево, вона або заблокується до завершення першої транзакції, або запише старий шлях, що призведе до порушення ієрархічної цілісності.
3. **Вкладені множини:** оновлення числових меж вимагає блокування діапазонів (Gap Locks / Next-Key Locks). Навіть за найнижчого рівня ізоляції вставка нового вузла повністю серіалізує доступ до таблиці, знижуючи пропускну здатність системи до одиниць операцій на секунду.
4. **Таблиця замикання:** додавання нового вузла вставляє `depth + 1` нових рядків у таблицю зв'язків без модифікації існуючих записів, що мінімізує конфлікти блокувань і дозволяє досягати десятків тисяч вставок на секунду в паралельних потоках.

> 🔧 **Навіщо це.**
> - **Список суміжності з CTE:** обирають за замовчуванням для більшості стандартних веб-застосунків із помірною глибиною дерева (до 5–8 рівнів) та частими модифікаціями структури (організаційні структури компаній, коментарі на форумах, файлові менеджери).
> - **Матеріалізований шлях (`ltree`):** ідеальний для каталогів контенту та класифікаторів із великою кількістю пошукових запитів за шаблонами рівнів, де читання значно переважає запис, а рекурсія CTE створює відчутний оверхед на CPU.
> - **Вкладені множини:** застосовують виключно у статичних архівах, довідниках географічних об'єктів або класифікаторах стандартів, де структура формується один раз під час деплою і ніколи не змінюється в реальному часі.
> - **Таблиця замикання:** промисловий стандарт для високонавантажених корпоративних систем, де потрібна максимальна продуктивність вибірки піддерев, сувора посиланняльна цілісність через зовнішні ключі, можливість паралельного додавання вузлів без взаємних блокувань або підтримка поліієрархій (коли один товар належить до кількох батьківських категорій одночасно).
