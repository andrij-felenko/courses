# Шлюз рядка даних

<preknowlist>
- [Реляційна модель](root:sf-data/relational-model) — дані лежать таблицями, кожен запис — рядок, у рядка є первинний ключ; цей патерн обгортає рівно один такий рядок.
- [Шлюз (PoEAA)](root:sf-apps/gateway) — об'єкт, що замикає в собі доступ до зовнішньої системи й показує назовні звичайний метод; тут «зовнішня система» — це база, а «запис» — один рядок.
- [ORM](root:sf-data/orm) — навіщо взагалі перекладати рядки таблиць в об'єкти і де цей переклад починає муляти.
</preknowlist>

У тебе є таблиця `orders` із колонками `id`, `customer_id`, `total`, `status`, і десятки місць у програмі, яким час від часу треба прочитати або записати рядок цієї таблиці. Найгірше, що можна зробити, — розсипати `SELECT` і `UPDATE` по всіх цих місцях: тоді назва колонки `total` виявиться вписаною в контролер, у звіт, у фонову задачу й у шаблон сторінки, і перейменувати її стане маленькою катастрофою. Отже, доступ до рядка треба зібрати в одну точку. Питання лише — **яку форму дати цій точці**.

Один із відповідей уже названо: [шлюз](root:sf-apps/gateway) — об'єкт, що замикає весь доступ до чужого ресурсу й показує назовні звичайний метод. База даних — саме такий чужий ресурс. Але база — не одноликий сервіс: вона складається з рядків, і найприроднішою одиницею доступу тут є **один рядок**. Що, як зробити шлюз рівно на **один рядок таблиці** — об'єкт, чиї поля дзеркалять колонки того рядка, а всі методи зводяться до «вставити цей рядок», «оновити цей рядок», «видалити цей рядок»? Такий об'єкт і зветься **шлюз рядка даних (англ. *Row Data Gateway* — ворота до рядка даних)**.

## Об'єкт, що є рядком — і більше нічим

Означення Мартіна Фаулера з його каталогу корпоративних патернів коротке: **об'єкт, що діє як шлюз до одного запису в джерелі даних; на кожен рядок — свій екземпляр** (усталене формулювання, [PoEAA, 2002](root:sf-data/row-data-gateway/hist-data-source-patterns.md)). Розберімо це по частинах, бо кожне слово несе обмеження.

«На кожен рядок — свій екземпляр» означає, що об'єкт шлюзу не представляє таблицю взагалі — він представляє **один конкретний рядок**. Об'єкт із `id = 42` — це рядок 42, його поля тримають значення саме тих колонок, і оновити він уміє тільки себе. Хочеш попрацювати з рядком 43 — то буде інший об'єкт.

«Шлюз до запису» означає, що вся справа об'єкта — **перенести рядок туди й назад**. Прочитати з бази — розкласти по полях; записати в базу — зібрати поля назад у `INSERT` чи `UPDATE`. Ані рядком більше. І тут — головна, визначальна риса патерну, яку легко проґавити: **у шлюзі рядка немає жодного предметного правила**. Він не знає, чи можна скасувати замовлення, скільки з нього податку, чи не завеликий підсумок. Він знає лише, як рядок лягає в об'єкт і як повертається в таблицю. Це чистий перекладач між формою рядка й формою об'єкта — і свідомо порожній від усього іншого.

![Ліворуч таблиця orders із колонками id, customer_id, total, status і трьома рядками, рядок 42 виділено. Посередині рамка OrderFinder із методом find(42), від неї стрілка з підписом SELECT веде праворуч. Праворуч об'єкт OrderGateway для рядка 42: угорі поля id, customerId, total, status, що дзеркалять колонки; нижче три методи insert, update, delete; ще нижче перекреслений рядок canCancel з підписом ПРАВИЛ НЕМАЄ. Від об'єкта стрілка назад до таблиці підписана INSERT або UPDATE](img/rdg-anatomy.svg)

*Шлюз рядка — це один рядок, одягнений в об'єкт: поля дзеркалять колонки, три дієслова переносять його в базу й назад. Правил у ньому немає за задумом. А оскільки об'єкт існує лише разом зі своїм рядком, знайти рядок він сам не може — цим займається окремий шукач.*

## Хто знаходить рядки, якщо об'єкт — це вже рядок

Ось перша нетривіальність, і вона випливає прямо з означення. Раз екземпляр шлюзу — це **один уже наявний рядок**, то поставити на нього метод «знайди рядок за ключем» логічно не виходить: щоб покликати `find(42)`, тобі вже потрібен якийсь об'єкт, а він якраз і мав би народитися внаслідок пошуку. Курка й яйце: пошук має віддати шлюз, але шлюз — це вже знайдений рядок.

Розв'язок, який пропонує патерн, — винести пошук **в окремий клас**, [шукач (англ. *finder* — той, що знаходить)](root:sf-data/row-data-gateway/proj-row-data-gateway.md). Шукач не представляє жодного рядка; його справа — виконати `SELECT`, узяти сирі рядки з відповіді й **збудувати з кожного по шлюзу**. Один запит повернув сто рядків — шукач віддасть сто об'єктів-шлюзів. Так обов'язки чисто розходяться: шукач відповідає на питання «які рядки?», а шлюз — на питання «як цей рядок покласти назад?».

Задача суто бекендова — розмова з базою, — тож пишемо мовами, що там реально живуть; TypeScript і Python лягають на неї однаково природно.

:::tabs
```ts
// Таблиця: orders(id INTEGER PRIMARY KEY, customer_id TEXT, total REAL, status TEXT)
type Row = { id: number; customer_id: string; total: number; status: string };

// ── ШЛЮЗ: рівно один рядок — його поля й три дієслова доступу. Правил тут немає. ──
class OrderGateway {
  constructor(
    public id: number | null,
    public customerId: string,
    public total: number,
    public status: string,
  ) {}

  async insert(): Promise<void> {
    const res = await db.run(
      "INSERT INTO orders (customer_id, total, status) VALUES (?, ?, ?)",
      this.customerId, this.total, this.status,
    );
    this.id = res.lastID;               // рядок народився — об'єкт запам'ятав ключ
  }

  async update(): Promise<void> {
    await db.run(
      "UPDATE orders SET customer_id = ?, total = ?, status = ? WHERE id = ?",
      this.customerId, this.total, this.status, this.id,
    );
  }

  async delete(): Promise<void> {
    await db.run("DELETE FROM orders WHERE id = ?", this.id);
  }
}

// ── ШУКАЧ: окремий клас; знаходить рядки й будує з них шлюзи. ──
class OrderFinder {
  static async find(id: number): Promise<OrderGateway | null> {
    const row: Row | undefined = await db.get("SELECT * FROM orders WHERE id = ?", id);
    return row ? OrderFinder.load(row) : null;
  }

  static async findByStatus(status: string): Promise<OrderGateway[]> {
    const rows: Row[] = await db.all("SELECT * FROM orders WHERE status = ?", status);
    return rows.map(OrderFinder.load);   // кожен рядок → свій шлюз
  }

  private static load(r: Row): OrderGateway {
    return new OrderGateway(r.id, r.customer_id, r.total, r.status);
  }
}
```
```py
# Таблиця: orders(id INTEGER PRIMARY KEY, customer_id TEXT, total REAL, status TEXT)

# ── ШЛЮЗ: рівно один рядок — його поля й три дієслова доступу. Правил тут немає. ──
class OrderGateway:
    def __init__(self, id, customer_id, total, status):
        self.id = id                    # None → рядка ще немає
        self.customer_id = customer_id
        self.total = total
        self.status = status

    def insert(self):
        cur = db.execute(
            "INSERT INTO orders (customer_id, total, status) VALUES (?, ?, ?)",
            (self.customer_id, self.total, self.status),
        )
        self.id = cur.lastrowid         # рядок народився — об'єкт запам'ятав ключ

    def update(self):
        db.execute(
            "UPDATE orders SET customer_id = ?, total = ?, status = ? WHERE id = ?",
            (self.customer_id, self.total, self.status, self.id),
        )

    def delete(self):
        db.execute("DELETE FROM orders WHERE id = ?", (self.id,))


# ── ШУКАЧ: окремий клас; знаходить рядки й будує з них шлюзи. ──
class OrderFinder:
    @staticmethod
    def find(id):
        row = db.execute("SELECT * FROM orders WHERE id = ?", (id,)).fetchone()
        return OrderFinder._load(row) if row else None

    @staticmethod
    def find_by_status(status):
        rows = db.execute("SELECT * FROM orders WHERE status = ?", (status,)).fetchall()
        return [OrderFinder._load(r) for r in rows]   # кожен рядок → свій шлюз

    @staticmethod
    def _load(r):
        return OrderGateway(r["id"], r["customer_id"], r["total"], r["status"])
```
:::

Зверни увагу на дрібницю, що насправді не дрібниця: у кожному запиті значення передане **окремим параметром** (`?`), а не вклеєне в текст `SELECT`. Уся розмова з базою замкнена в цих двох класах — і зробити її стійкою до підставленого лихого вводу треба саме тут, в одному місці, а не в кожному контролері. Це і є те, заради чого доступ узагалі збирають у шлюз: одна точка, яку легко зробити правильною.

## Уся суть — у тому, чого тут немає

Тепер повернімося до найважливішого: чому правила винесені геть. Дивись, як виглядає користування шлюзом — рішення «чи можна скасувати» ухвалює **не** об'єкт-шлюз, а той код, що ним послуговується:

:::tabs
```ts
const gw = await OrderFinder.find(42);
// правило живе ТУТ, зовні — шлюз про нього не знає
if (gw && (gw.status === "new" || gw.status === "paid")) {
  gw.status = "cancelled";
  await gw.update();            // шлюз лише переносить рядок назад у базу
}
```
```py
gw = OrderFinder.find(42)
# правило живе ТУТ, зовні — шлюз про нього не знає
if gw and gw.status in ("new", "paid"):
    gw.status = "cancelled"
    gw.update()                 # шлюз лише переносить рядок назад у базу
    db.commit()
```
:::

Правило `status in ("new", "paid")` стоїть **над** шлюзом, у сценарії, що його викликає. Це і є навмисна межа патерну — і саме вона робить шлюз рядка окремим, упізнаваним рішенням, а не половинкою чогось.

Щоб побачити, чому межа важлива, візьми той самий шлюз і **встав правило всередину** — додай йому метод `canCancel()`, а поряд `taxAmount()`, а там і `applyDiscount()`. Щойно ти це зробив, об'єкт перестав бути чистим перекладачем рядка: тепер він і носій даних, і сховище правил. Такий об'єкт має власне ім'я — [Active Record](root:sf-data/active-record): це рівно шлюз рядка, у який **вкладено предметну логіку**. Уся різниця між двома патернами — в одному русі: лишив об'єкт порожнім від правил — маєш шлюз рядка; наситив його правилами — дістав Active Record.

![Ліворуч рамка Row Data Gateway: поля рядка плюс insert, update, delete, з підписом самі дані й доступ, правил немає. Від неї дві стрілки. Верхня, з підписом додай предметні правила В ТОЙ САМИЙ клас, веде до рамки Active Record: ті самі поля й доступ плюс canCancel, taxAmount. Нижня, з підписом лиши шлюз чистим, а правила поклади ЗВЕРХУ, веде до рамки Transaction Script, від якої стрілка назад униз до шлюзу з підписом кличе insert або update](img/rdg-boundary.svg)

*Шлюз рядка — це порожня від правил підлога. Далі два шляхи: вкласти правила в той самий об'єкт — і він стане Active Record; або лишити шлюз чистим, а правила винести окремим сценарієм над ним. Патерн — це саме нижній вибір, свідомо зроблений.*

> 🔧 **Навіщо це.** Практична проба, чи перед тобою справді шлюз рядка: подивись на його клас і спитай, чи є в ньому **бодай один метод, що ухвалює предметне рішення**. Якщо є `canCancel`, `isOverdue`, `applyPromo` — це вже не шлюз, а Active Record (можливо, ненавмисний). Чистий шлюз відповідає лише на «прочитай мій рядок» і «запиши мій рядок». Тримати цю межу варто тоді, коли ти **хочеш**, щоб доступ до бази й предметні правила лежали в різних місцях: правила тоді тестуються без бази, а весь SQL сидить у тонкому передбачуваному шарі, куди легко зазирнути, коли щось гальмує.

Другий шлях — лишити шлюз чистим — веде до природного напарника патерну. Якщо правил у застосунку небагато й кожна дія — це короткий сценарій («скасувати замовлення», «нарахувати знижку»), то ці сценарії кладуть окремо, а рядки вони чіпають через шлюз. Таку організацію логіки звуть [сценарієм транзакції](root:sf-apps/transaction-script), і шлюз рядка — її типовий постачальник даних: сценарій вирішує **що** зробити, шлюз знає **як** дістати й покласти рядок.

## «Рядок» у назві — на противагу «таблиці»

Назва наголошує на слові «рядок» не випадково — вона протиставляє цей патерн його близькому родичу. Уяви інший розподіл: замість об'єкта **на кожен рядок** зробити **один об'єкт на всю таблицю**, і хай усі його методи приймають ключ. Не `gw.update()` для конкретного рядка, а `gateway.update(42, ...)` для будь-якого; не сто об'єктів на сто рядків, а один об'єкт, що вміє дістати й записати будь-який рядок таблиці. Такий об'єкт віддає назовні не окремі шлюзи, а сирі набори рядків — і зветься [шлюз таблиці даних (англ. *Table Data Gateway*)](root:sf-data/table-data-gateway).

![Ліворуч підпис Шлюз ТАБЛИЦІ даних: один об'єкт OrderTableGateway на всю таблицю, його методи find(id), update(id, дані), delete(id) приймають ключ; від нього стрілка до таблиці orders з усіма рядками, підпис один екземпляр обслуговує ВСІ рядки, повертає сирі набори. Праворуч підпис Шлюз РЯДКА даних: три окремі об'єкти-шлюзи, кожен прив'язаний до свого рядка 41, 42, 43; підпис свій екземпляр на КОЖЕН рядок, об'єкт і є рядок](img/row-vs-table.svg)

*Два шлюзи PoEAA діляться за одиницею доступу. Шлюз таблиці — один об'єкт на цілу таблицю, його методи беруть ключ і повертають сирі рядки. Шлюз рядка — свій об'єкт на кожен рядок, і цей об'єкт сам є рядком. Звідси й «рядок» проти «таблиці» в назвах.*

Обидва — шлюзи, обидва замикають доступ до бази в одному місці. Різниця суто в тому, **скільки рядків обслуговує один екземпляр**. Шлюз таблиці зручний, коли даними оперують радше пачками й у стилі, близькому до самого SQL: дістав набір, пробіг по ньому. Шлюз рядка зручний, коли з кожним рядком працюють як з окремою річчю, що має свою тотожність, — і тоді природно, щоб цій речі відповідав свій об'єкт. Ім'я патерну чесно каже, який з двох поділів обрано.

## Де він на своєму місці, а де зайвий

Шлюз рядка живе у вузькій, але реальній ніші, і найкраще видно її на тлі двох сусідів.

З одного боку — **розсипаний по коду SQL**. Проти нього шлюз виграє завжди: доступ до рядка зібрано в одну точку, назви колонок не протікають у контролери, параметризацію легко зробити правильно один раз. Тут вагань немає — навіть тонкий шлюз кращий за `SELECT` у шаблоні сторінки.

З іншого боку — **Active Record**. І ось тут вибір тонший. Якщо предметних правил над рядком мало й вони прості, то тримати окремо шлюз, окремо шукач і окремо сценарій з правилом — це три сутності там, де Active Record обійшовся б однією: правило просто лягло б у той самий об'єкт. За таку роздільність платять зайвими класами, і плата виправдана лише тоді, коли роздільність справді потрібна — коли ти хочеш, щоб предметна логіка **не залежала від бази ні на крихту** й перевірялася без неї. Немає такої потреби — Active Record дешевший, бо не бере грошей за межу, якою ти не користуєшся.

Через це самостійним рішенням шлюз рядка обирають нечасто. Куди частіше він з'являється **всередині** іншого патерну як службовий шар. Коли доступ до бази виносять у [Data Mapper](root:sf-data/data-mapper) — окремий клас, що перекладає рядки в багату предметну модель, — цьому маперу теж треба десь тримати сиру роботу з рядком, і шлюз рядка добре лягає на цю внутрішню роль: мапер вирішує, як рядок стає предметним об'єктом, а шлюз під ним просто носить рядок у базу й назад. І так само шлюз — природна пара до [сценарію транзакції](root:sf-apps/transaction-script): тонкий сценарій тримає правило, а рядки бере через шлюз, не змішуючи логіку з SQL. У ролі непомітного будівельного блока під іншими шарами шлюз рядка трапляється значно частіше, ніж на видноті.

> 🔧 **Навіщо це.** Правило вибору, що не бреше: **порахуй, скільки предметної логіки над рядком і чи хочеш ти відв'язати її від бази.** Логіки обмаль, відв'язувати нема чого — бери Active Record, не плоди класів. Логіки багато, вона складна й мусить тестуватися без живої таблиці — не тягни її в Active Record, а розділяй, і тоді шлюз рядка (частіше — під Data Mapper) стане тим тонким шаром, що знає SQL, поки правила його не знають. А коли доступ до рядка розсипаний по застосунку в сирому вигляді — збери його в шлюз навіть без інших патернів: одна точка правди про те, як таблиця перетворюється на об'єкт, окупається першою ж зміною схеми.

Варто назвати й межу, за яку шлюз рядка природно не заходить. Правило «один об'єкт — один рядок» зручне рівно доти, доки предметна річ **і є** один рядок. Щойно вона розкладається на кілька таблиць — замовлення разом із позиціями й адресою, — шлюз рядка починає боротися з формою даних так само, як Active Record: або кілька шлюзів, які ніхто не тримає купи, або ліплення понад патерн. Це не вада реалізації, а стеля самої ідеї: вона про рядок, і поза рядком її сила закінчується. Спорідненість зі своїм родичем — [об'єктом доступу до даних (DAO)](root:sf-apps/data-access-object), який виріс у світі J2EE з тієї ж потреби заховати доступ до даних за об'єктом, — теж лежить рівно тут: усі ці патерни малюють одну межу — між тим, як дані **зберігаються**, і тим, як програма про них **думає**.

## Що лишається в руках

Шлюз рядка даних — це об'єкт, що **є одним рядком таблиці**: його поля дзеркалять колонки, три дієслова переносять рядок у базу й назад, а знаходженням рядків відає окремий шукач, бо сам об'єкт існує лише разом зі своїм уже знайденим рядком. Це спеціалізація загального [шлюзу](root:sf-apps/gateway) — той самий задум «замкни доступ до чужого ресурсу в одному класі», застосований до найдрібнішої одиниці бази.

Визначає патерн не те, що в ньому є, а те, чого в ньому свідомо немає: **жодного предметного правила**. Ця порожнеча — не недогляд, а вся суть. Вкладеш правила в об'єкт — він перетвориться на [Active Record](root:sf-data/active-record), і межа між доступом і логікою зникне. Лишиш чистим — правила осядуть окремо, у [сценарії транзакції](root:sf-apps/transaction-script) чи в багатій моделі поверх [мапера](root:sf-data/data-mapper), — і ти дістанеш те, заради чого межу й тримають: логіку, яку можна перевірити без бази, і весь SQL, зібраний у тонкому шарі, куди легко зазирнути. Обирай шлюз рядка не тому, що він модний — він радше службовий, — а тоді, коли тобі справді потрібно, щоб форма зберігання й форма думки жили окремо. Немає такої потреби — сусід простіший; є — цей тонкий, порожній від правил перекладач рядка окупить кожен свій зайвий клас.
