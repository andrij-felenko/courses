# 📜 Від міноносця USS Coronado до DuckDB: історія вбудованих баз даних

Потреба у вбудованому сховищі даних виникла з фундаментального конфлікту між надійністю автономної системи та крихкістю клієнт-серверної архітектури, у якій збій мережевого демона або сокета паралізує роботу всієї програми.

### 1980-ті: Витоки вбудованих сховищ та ера Berkeley DB

До появи реляційних систем у просторі процесу зберігання структурованих записів опиралося на прості бібліотеки хешування файлів у стилі UNIX `dbm` (розробленої Кеном Томпсоном у 1979 році) та `ndbm`. Ці бібліотеки надавали примітивний інтерфейс словника «ключ-значення», але не підтримували багатопотоковості, паралельного доступу різних процесів і транзакційної надійності за стандартом ACID.

У 1991 році в Каліфорнійському університеті в Берклі Марго Зельцер (Margo Seltzer) та Кіт Бостік (Keith Bostic) розробили **Berkeley DB (libdb)** для заміни застарілого коду UNIX на вільну реалізацію з відкритим кодом. Berkeley DB стала першою повноцінною вбудованою системою зберігання, яка запропонувала механізм сторінкового кешування в оперативній пам'яті, підтримку B-дерев, хеш-таблиць та транзакційного журналу відновлення (Write-Ahead Logging).

У 1996 році автори заснували компанію Sleepycat Software, зробивши Berkeley DB стандартом для поштових серверів (Sendmail, Postfix), LDAP-каталогів (OpenLDAP) та ранніх версій вебсерверів. Berkeley DB дотримувалася філософії programmatic toolkit: вона не мала мови SQL, працювала виключно через системні виклики C API та надавала байтовий доступ до масивів даних. Проте потреба у виразних реляційних декларативних запитах всередині окремого процесу залишалася незадоволеною.

### 2000 рік: Військовий корабель USS Coronado та народження SQLite

Навесні 2000 року американський програміст Двейн Річард Гіпп (D. Richard Hipp), працюючи за контрактом із компанією General Dynamics, брав участь у створенні програмного забезпечення для Центру управління бойовими діями на борту штабного корабля ВМС США USS Coronado (AGF-11).

Система моніторингу та оцінки пошкоджень спиралася на клієнт-серверний сервер баз даних Informix. В умовах бойових навчань та тестування апаратури сервер Informix регулярно втрачав зв'язок: мережеві інтерфейси перевантажувалися, демон бази даних зависав або не міг запуститися через відсутність прав системного адміністратора на машині. Коли сервер баз даних падав, корабельна система контролю живучості повністю втрачала працездатність, видаючи помилку з'єднання з сокетом `pipe` або `TCP port`.

Гіпп дійшов висновку, що для керування зброєю, навігацією та сенсорами потрібна система керування базами даних, яка фізично нездатна втратити мережеве з'єднання, оскільки скомпільована безпосередньо у виконуваний файл програми. Програма повинна була відкривати файл на диску за допомогою стандартного системного виклику `open()` і читати сторінки пам'яті безпосередньо через адреси в адресному просторі застосунку.

У травні 2000 року Річард Гіпп спроєктував першу версію **SQLite**:

1. **SQLite 1.0 (серпень 2000)**: Використовувала gdbm (GNU dbm) як внутрішній рушій зберігання та реалізовувала базовий парсер підмножини SQL. Запити транслювалися в ітерації по файлових блоках.
2. **SQLite 2.0 (2001)**: Отримала власну реалізацію дискового B-дерева з фіксованим розміром сторінок, позбувшись сторонніх залежностей. База даних зберігалася в єдиному кросплатформному файлі на диску.
3. **SQLite 3.0 (2004)**: Повна перебудова архітектури за фінансової підтримки консорціуму SQLite (включно з Motorola та іншими індустріальними гігантами). Було впроваджено віртуальну машину VDBE (Virtual DataBase Engine), динамічну типізацію колонок (manifest typing), підтримку юнікоду UTF-8/UTF-16 та блокування файлів через POSIX `fcntl`.

У 2010 році у версії SQLite 3.7.0 з'явився режим журналу попереднього запису (WAL) та спільна пам'ять (`.shm`), що дозволило паралельним потокам читати дані без блокування єдиного потоку, що здійснює запис. SQLite стала найбільш розповсюдженим програмним забезпеченням у світі: вона вбудована в кожний смартфон на базі Android та iOS, у всі сучасні веббраузери (Chrome, Firefox, Safari), операційні системи Windows, macOS, Linux та в автомобільні бортові комп'ютери.

### 2011–2013: Революція вбудованих сховищ типу «ключ-значення» (LevelDB та RocksDB)

Зі зростанням обсягів даних у вебсервісах та появою швидких твердотільних накопичувачів (NVMe SSD) класичні дискові B-дерева SQLite зіткнулися з проблемою ампліфікації випадкового запису (Random Write Amplification).

У 2011 році провідні інженери Google Джефф Дін (Jeff Dean) та Санджай Гемават (Sanjay Ghemawat) створили **LevelDB** — компактну вбудовану бібліотеку сховища ключ-значення, засновану на алгоритмі LSM-дерева (Log-Structured Merge-tree). LevelDB створювалася як рушій для реалізації стандарту `IndexedDB` у браузері Google Chrome, а також як спрощена open-source реалізація базових концепцій Google BigTable. Вона перетворила всі операції вставки на послідовний запис у пам'ять (MemTable) та журнальний лог (WAL), забезпечивши високу швидкість збереження.

У 2013 році команда інженерів Facebook під керівництвом Дгруби Бортакура (Dhruba Borthakur) форкнула LevelDB, створивши проєкт **RocksDB**. Основним завданням RocksDB була адаптація вбудованого рушія до серверного обладнання з десятками ядер CPU та терабайтними масивами Flash-пам'яті:

* **Багатопотокова компактифікація**: LevelDB виконувала фонове ущільнення рівнів в один потік, що призводило до «зависань» запису (write stalls). RocksDB реалізувала масштабований пул фонових потоків.
* **Конкурентний MemTable**: Було реалізовано lock-free структуру даних SkipList для одночасного запису з багатьох потоків хост-процесу.
* **Розподілений кеш блоків**: Інтеграція кешу розпакованих блоків пам'яті прямо в купу процесу.

RocksDB стала базовим вбудованим рушієм зберігання для великих розподілених СУБД, таких як CockroachDB, YugabyteDB, TiKV, а також для обробки потокових даних у Apache Kafka Streams.

### 2018–2020: Вакуум аналітики та поява DuckDB

До 2018 року склалася ситуація, коли для транзакційного вбудованого навантаження (OLTP) існував беззаперечний стандарт SQLite, але для аналітичної обробки (OLAP) вбудованих інструментів не було взагалі.

Якщо програмісту на Python, R, C++ або Go потрібно було виконати складний SQL-запит над масивом у 10 мільйонів рядків із групуванням, агрегаціями та з'єднаннями (JOIN), він мусив:
1. Або підіймати важкий серверний кластер (PostgreSQL, ClickHouse, Snowflake), що додавало накладні витрати на конфігурацію, автентифікацію та серіалізацію мільйонів рядків через TCP-сокет.
2. Або вантажити дані в таблиці SQLite, де порядковий ітератор (Volcano-модель) обробляв один кортеж за виклик функції, викликаючи масові промахи кешу процесора (L1/L2 cache misses) та деградацію швидкодії.

У 2018 році дослідники Центру математики та інформатики в Амстердамі (CWI) Ганнес Мюлейзен (Hannes Mühleisen) та Марк Раасвельдт (Mark Raasveldt) створили **DuckDB**, яку неофіційно назвали «SQLite для аналітики».

DuckDB поєднала простоту використання SQLite (одна бібліотека без зовнішніх залежностей, єдиний файл бази даних) із технологіями сучасних векторних СУБД:

* **Векторизоване виконання (Vectorized Execution)**: Дані обробляються пачками (DataChunk) по 2048 значень, що ідеально лягає в L1/L2 кеш та задіює SIMD-інструкції процесорів (AVX2, AVX-512, ARM NEON).
* **Стовпцевий формат пам'яті**: Читаються лише ті колонки, які фігурують у запиті.
* **Безкопійна інтеграція з екосистемою даних**: Прямий доступ за покажчиками до структур Apache Arrow, датафреймів Pandas та Polars без копіювання байтів пам'яті.

Еволюція вбудованих СУБД продемонструвала циклічний розвиток: від примітивних словників ключ-значення через повноцінні реляційні транзакційні рушії до високопродуктивних векторних аналітичних процесорів, здатних обробляти гігабайти даних за мілісекунди безпосередньо всередині пам'яті застосунку.
