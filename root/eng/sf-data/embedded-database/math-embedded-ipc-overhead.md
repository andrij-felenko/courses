# 🧮 Математична модель накладних витрат IPC та затримок виконання запитів

Оцінка часової складності запитів між клієнт-серверними та вбудованими СУБД базується на декомпозиції повного часу обробки запиту (`T_total`) на фізичні фази: перетворення структур даних у байти, перемикання контексту процесора, проходження стека ядра операційної системи та безпосереднє виконання обчислень рушієм зберігання.

---

### Декомпозиція повного часу запиту в клієнт-серверній моделі

У клієнт-серверній архітектурі (наприклад, застосунок взаємодіє з PostgreSQL або MySQL через локальний сокет Unix Domain Socket або мережевий стек TCP/IP) виконання одного запиту з передачею `N` рядків розміром `S` байтів кожен описується рівнянням:

```text
T_remote = T_client_ser + T_ipc_send + T_server_deser + T_exec + T_server_ser + T_ipc_recv + T_client_deser
```

Розглянемо кожну компоненту на рівні апаратних інструкцій та системних викликів ядра операційної системи:

1. **Серіалізація та десеріалізація (`T_ser`, `T_deser`)**:
   Перетворення об'єктів пам'яті (структур мов C/C++, Rust або об'єктів високорівневих мов) у бінарний або текстовий дротовий протокол вимагає обходу полів, перевірки кодування та копіювання байтів у проміжний буфер:
```text
T_client_ser = N · S · t_byte_ser
T_server_deser = N · S · t_byte_deser
```
   де `t_byte_ser` — середній час серіалізації одного байта процесором (типово `1.5 - 3.0` нс/байт для бінарних протоколів без стиснення).

2. **Накладні витрати системних викликів та перемикання контексту (`T_ipc`)**:
   Передача даних через сокет вимагає викликів ядра `sendto()` / `recvfrom()` або `write()` / `read()`:
```text
T_ipc_send = T_syscall_enter + T_skb_alloc + T_user_to_kernel_copy + T_ctx_switch + T_syscall_exit
```

Фізичні константи для сучасної архітектури x86-64 (процесор 3.5 ГГц, Linux Kernel 6.x):
* `T_syscall`: пара системних викликів (вхід + вихід через інструкцію `syscall`/`sysret`) ≈ `120 - 250` нс (з урахуванням захистів від уразливостей спекулятивного виконання Meltdown/Spectre через механізм KPTI).
* `T_ctx_switch`: перемикання контексту між процесом клієнта та процесом сервера (збереження регістрів загального призначення, оновлення покажчика кореня таблиці сторінок пам'яті `CR3`, повна або часткова інвалідація записів у TLB) ≈ `1200 - 2500` нс.
* `T_copy_kernel`: побайтове копіювання даних із простору користувача у сокетні буфери ядра `sk_buff` та назад у простір отримувача через функцію ядра `copy_from_user()` / `copy_to_user()`:
```text
T_copy_kernel = 2 · (N · S / B_dram)
```
де `B_dram` — реальна пропускна здатність оперативної пам'яті (для двоканальної DDR5-5600 ≈ `50 - 65` ГБ/с = `50 - 65` байтів/нс).

### Декомпозиція часу у вбудованій СУБД

У вбудованій базі даних (SQLite, DuckDB, RocksDB) рушій скомпільований у той самий адресний простір. Передача параметрів запиту та отримання результату виконується як звичайний виклик функції через двійковий інтерфейс програми (ABI):

```text
T_embedded = T_abi_call + T_exec + T_zero_copy_read
```

де:
* `T_abi_call`: передача покажчика на підготовлений вираз у регістрах CPU (`RDI`, `RSI` за конвенцією System V AMD64 ABI) та виконання інструкції `call` / `ret` ≈ `5 - 15` нс.
* `T_zero_copy_read`: отримання адреси комірки або стовпця за прямим покажчиком пам'яті без проміжних копіювань:
```text
T_zero_copy_read = N · t_ptr_deref
```
де `t_ptr_deref` — пряме зчитування адреси з L1-кешу CPU ≈ `1.0 - 1.2` нс (4 такти процесора).

### Розрахунок 1: Одиничний точковий запит (Single Point Lookup)

**Умова:** Запит за первинним ключем `SELECT name, balance FROM accounts WHERE id = 42`.
* Обсяг корисного навантаження: 1 рядок, `S = 64` байти.
* Час виконання індексного пошуку в B-Tree у L3-кеші / RAM: `T_exec = 1200` нс (1.2 мкс).

**1. Клієнт-серверний сценарій (через локальний сокет Unix Domain Socket):**

```text
T_remote
= T_ser_req + T_ipc_req + T_deser_req + T_exec + T_ser_resp + T_ipc_resp + T_deser_resp  [повне рівняння]
= 80 + 2200 + 70 + 1200 + 90 + 2400 + 80                                               [підстановка наносекунд]
= 6120 нс ≈ 6.12 мкс                                                                   [підсумок затримки]
```

Частка корисних обчислень (робота індексу B-Tree):
```text
η_remote
= T_exec / T_remote                     [визначення коефіцієнта корисної дії]
= 1200 / 6120                           [числова підстановка]
= 0.196 = 19.6%                         [80.4% часу змарновано на IPC та серіалізацію]
```

**2. Вбудований сценарій (SQLite у тому ж процесі):**

```text
T_embedded
= T_abi_call + T_exec + T_zero_copy_read  [прямий виклик функції через регістри]
= 12 + 1200 + 4                          [виклик sqlite3_step + індексний пошук + sqlite3_column_blob]
= 1216 нс ≈ 1.22 мкс                     [підсумок затримки]
```

Частка корисних обчислень:
```text
η_embedded
= T_exec / T_embedded                   [визначення коефіцієнта корисної дії]
= 1200 / 1216                           [числова підстановка]
= 0.987 = 98.7%                         [лише 1.3% часу на виклик функції ABI]
```

Прискорення (Speedup) для одиничного запиту:
```text
S_point
= T_remote / T_embedded                 [відношення затримок]
= 6120 / 1216                           [числова підстановка]
= 5.03 ≈ 5.0x                           [вбудована база в 5 разів швидша на точкових вибірках]
```

### Розрахунок 2: Пакетне сканування (Batch Scan: 10 000 рядків)

**Умова:** Запит вибірки журналу транзакцій `SELECT * FROM events WHERE sensor_id = 7 LIMIT 10000`.
* Кількість рядків: `N = 10 000`.
* Розмір одного рядка: `S = 100` байтів.
* Загальний обсяг даних: `V = 10 000 · 100 = 1 000 000` байтів ≈ `1 МБ`.
* Час послідовного зчитування з буферного пулу: `T_exec = 80 000` нс (80 мкс).

**1. Клієнт-серверний сценарій (1 МБ через TCP Loopback / UDS):**

```text
T_ser_resp = 1 000 000 · 1.8 = 1 800 000 нс = 1.8 мс
T_deser_client = 1 000 000 · 1.6 = 1 600 000 нс = 1.6 мс
T_copy_kernel = 2 · (1 000 000 / 50) = 40 000 нс = 0.04 мс
T_ctx_switches = 4 · 1800 = 7 200 нс = 0.0072 мс
```

```text
T_remote
= T_ser_resp + T_deser_client + T_copy_kernel + T_ctx_switches + T_exec  [сума вагомих складових]
= 1800000 + 1600000 + 40000 + 7200 + 80000                              [підстановка наносекунд]
= 3527200 нс ≈ 3.53 мс                                                  [підсумок затримки]
```

Пропускна здатність клієнт-серверної передачі:
```text
BW_remote
= V / T_remote                          [обсяг даних / час передачі]
= 1.0 МБ / 0.00353 с                    [числова підстановка]
= 283.3 МБ/с                            [обмеження пропускної здатності серіалізацією CPU]
```

**2. Вбудований сценарій (DuckDB / SQLite Zero-Copy з буфера пам'яті):**

```text
T_zero_copy = 10 000 · 1.2 нс = 12 000 нс = 0.012 мс
```

```text
T_embedded
= T_exec + T_zero_copy                  [сканування сторінок + отримання адрес]
= 80000 + 12000                         [підстановка наносекунд]
= 92000 нс ≈ 0.092 мс                   [підсумок затримки]
```

Пропускна здатність вбудованого читання:
```text
BW_embedded
= V / T_embedded                        [обсяг даних / час зчитування]
= 1.0 МБ / 0.000092 с                   [числова підстановка]
= 10869.5 МБ/с ≈ 10.87 ГБ/с             [пряма швидкість шини пам'яті процесора]
```

Прискорення (Speedup) для пакетного сканування:
```text
S_batch
= T_remote / T_embedded                 [відношення часу обробки]
= 3527200 / 92000                       [числова підстановка]
= 38.34 ≈ 38x                           [вбудована база в 38 разів швидша при передачі 1 МБ]
```

### Розрахунок 3: Аналітична агрегація (1 000 000 рядків із SIMD)

**Умова:** Виконання аналітичного запиту обчислення суми `SELECT SUM(amount) FROM transactions`.
* Кількість значень: `M = 1 000 000` чисел типу `int64` (8 байтів).
* Загальний обсяг стовпця: `V_col = 8 000 000` байтів ≈ `8 МБ`.

**1. Рядковий ітератор Volcano (SQLite / клієнт-серверний покроковий FETCH):**
Кожен крок вимагає виклику віртуальної функції `step()`, перевірки типу, розпакування кортежу та додавання:
```text
t_row_iter ≈ 15 нс/значення
T_volcano = 1 000 000 · 15 нс = 15 000 000 нс = 15.0 мс
```

**2. Векторизоване стовпцеве виконання DuckDB з інструкціями AVX2 (256-біт):**
Регістр AVX2 вміщує `256 / 64 = 4` цілих числа `int64`. Інструкція `_mm256_add_epi64` виконується за 1 такт CPU:
```text
Кількість векторних операцій = 1 000 000 / 4 = 250 000 операцій
Такти CPU на частоті 3.5 ГГц = 250 000 / 3.5 · 10⁹ с ≈ 71 428 нс = 0.071 мс
```

З урахуванням завантаження стовпцевих векторів `DataChunk` (по 2048 елементів) у кеш L1/L2:
```text
T_vectorized
= T_l2_load + T_simd_exec               [час зчитування кешу + час інструкцій AVX2]
= 180000 + 71428                        [підстановка наносекунд]
= 251428 нс ≈ 0.25 мс                   [підсумок затримки DuckDB]
```

Прискорення векторизованої вбудованої аналітики над рядковим клієнт-серверним підходом:
```text
S_olap
= T_volcano / T_vectorized              [відношення тривалості обчислень]
= 15.0 / 0.25                           [числова підстановка]
= 60.0 = 60x                            [вбудована векторна СУБД швидша у 60 разів]
```

### Апаратний аналіз: Інвалідація кеш-ліній та протокол когерентності MESI

Коли два різні процеси ОС (клієнт і сервер бази даних) виконують обмін даними через сокетний буфер, операційна система часто запускає їх на різних фізичних ядрах процесора (`Core A` та `Core B`).

1. `Core B` (сервер СУБД) записує рядок у буфер сокета в пам'яті: кеш-лінія переходить у стан **Modified (M)** в кеші L1/L2 ядра B.
2. `Core A` (клієнт) викликає `read()`: для отримання даних апаратна шина повинна надіслати запит когерентності **Read For Ownership (RFO)** через протокол MESI/MOESI.
3. Кеш ядра B скидає лінію в спільний L3-кеш або RAM, а в кеші ядра B лінія маркується як **Invalid (I)**.

Ця між'ядерна транзакція на шині додає апаратну затримку в `40 - 80` нс на кожні 64 байти даних (розмір кеш-лінії).

У вбудованій СУБД, коли той самий потік послідовно готує запит, виконує пошук та обробляє результат, дані залишаються в гарячому кеші L1/L2 одного ядра, мінімізуючи трафік на внутрішньопроцесорній шині зв'язку.

Крім того, виділення пам'яті під структури вбудованої бази даних відбувається через пули пам'яті (Arena Allocators), що не спричиняє повторних системних викликів `mmap()`/`brk()` та виключає промахи таблиці трансляції адрес (TLB Misses), які неминуче виникають при регулярному створенні та знищенні тимчасових структур мережевого сокета ядра.
