Коли застосунок виконує запит до зовнішньої реляційної бази даних, шлях між бізнес-логікою та дисковими сторінками перетинає кілька важких бар'єрів операційної системи. Застосунок перетворює внутрішні об'єкти пам'яті на бінарні пакети дротового протоколу, виконує системні виклики `send()` або `write()`, ядро перемикає контекст процесора на стек сокетів TCP або Unix Domain Socket, копіює байти в буфери ядра, а демон сервера СУБД у власному адресному просторі зчитує потік через виклики `recv()`, десеріалізує структури та планує роботу власних потоків. Для запиту, що повертає 50 000 рядків, сумарний час копіювання байтів, перемикання контексту ядра та парсингу протоколу становить від 80% до 95% загальної затримки, тоді як сам пошук у пам'яті займає лише мікросекунди.

Усунення цих накладних витрат досягається відмовою від відокремленого процесу сервера: рушій керування даними компілюється безпосередньо у бінарний файл застосунку як статична (`.a`, `.lib`) або динамічна (`.so`, `.dll`) бібліотека. Така архітектурна форма називається **вбудованою базою даних** (англ. *embedded database*, від лат. *im-* — всередину, давн.-англ. *bed* — ложе; лат. *basis* — основа, від грец. *βάσις*). Вбудована СУБД виконується в єдиному віртуальному адресному просторі процесу, а міжпроцесна взаємодія замінюється прямими викликами функцій через двійковий інтерфейс програми (ABI).

### Архітектура прямого виклику та єдиний адресний простір

Фундаментальна відмінність вбудованої бази даних полягає у ліквідації межі між процесами (Process Boundary). У клієнт-серверній моделі клієнт і сервер ізольовані апаратно: кожен має власну таблицю сторінок пам'яті (Page Table), власний покажчик на каталог сторінок у регістрі процесора `CR3` та окремий простір дескрипторів файлів.

У вбудованій архітектурі код застосунку та код рушія СУБД ділять спільні ресурси:

1. **Прямий виклик функцій через регістри процесора**:
   Замість формування мережевого пакета програма викликає бібліотечну функцію (наприклад, `sqlite3_step()` або `duckdb_query()`). За стандартною конвенцією викликів System V AMD64 ABI перші шість аргументів передаються безпосередньо в регістрах процесора `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`. Час передачі керування становить `5–15` наносекунд (кілька тактів CPU) проти `20–50` мікросекунд для локального сокета ядра та `0.5–2.0` мілісекунд для мережевого з'єднання TCP/IP.
2. **Спільна купа та сторінковий пул (Shared Heap & Buffer Pool)**:
   Буферний кеш вбудованої СУБД виділяється зі спільної динамічної пам'яті процесу (`malloc`, `mmap`, власні арени пам'яті). Коли рушій бази даних зчитує сторінку таблиці з диска в оперативну пам'ять, ці байти фізично доступні для прямого розіменування покажчиками з боку коду застосунку.
3. **Відсутність дублювання структур у пам'яті**:
   У клієнт-серверній базі кожен рядок існує мінімум у трьох примірниках: у сторінковому кеші сервера, у сокетному буфері ядра ОС та в об'єктах DTO пам'яті клієнта. Вбудована база тримає дані в єдиному екземплярі сторінки пам'яті.

Детальний математичний аналіз витрат на перемикання контексту, пропускну здатність шини пам'яті та інвалідацію кеш-ліній наведено у вставці [Накладні витрати IPC та математична модель затримок](root:sf-data/embedded-database/math-embedded-ipc-overhead.md).

### Віртуальна машина VDBE та конвеєр виконання запитів у SQLite

Для виконання декларативних SQL-запитів SQLite використовує власну регістрову віртуальну машину — **VDBE (Virtual DataBase Engine)**. На відміну від серверних баз даних, де оптимізатор будує складне дерево фізичних реляційних операторів у динамічній пам'яті, SQLite транслює текст запиту в компактну послідовність низькорівневих інструкцій байт-коду.

```text
[SQL-запит] ──> [Лексичний аналізатор / Парсер Lemon] ──> [Генератор коду] ──> [Байт-код VDBE]
                                                                                       │
                                                                                       ▼
[Клієнтський код] <── sqlite3_step() <── [Цикл інтерпретатора VDBE (Опкоди)] <── [B-Tree / Pager]
```

Кожна інструкція VDBE складається з коду операції (Opcode) та п'яти операндів:
* **`P1`**: Зазвичай цілочисельний індекс регістра або курсора таблиці.
* **`P2`**: Номер цільового регістра або адреса переходу в разі виконання умови розгалуження.
* **`P3`**: Третій цілочисельний параметр або кількість послідовних регістрів.
* **`P4`**: Довільний покажчик пам'яті (текстовий рядок, константа, структура індексу).
* **`P5`**: Бітова маска прапорців поведінки інструкції.

Розглянемо виконання простого запиту `SELECT balance FROM accounts WHERE id = 42;`. Компілятор SQLite генерує такий ланцюг опкодів:

```text
addr  opcode         p1    p2    p3    p4             p5  comment
----  -------------  ----  ----  ----  -------------  --  -----------------------
0     Init           0     8     0                    00  Перехід на ініціалізацію
1     OpenRead       0     2     0     2              00  Відкрити курсор 0 для таблиці accounts (root page = 2)
2     Integer        42    1     0                    00  Записати число 42 у регістр r[1]
3     SeekRowId      0     7     1                    00  Знайти рядок з id = r[1] через B-Tree індекс; якщо нема -> перехід на 7
4     Column         0     1     2                    00  Прочитати колонку 1 (balance) курсора 0 у регістр r[2]
5     ResultRow      2     1     0                    00  Повернути кортеж з регістра r[2] застосунку
6     Halt           0     0     0                    00  Успішне завершення запиту
7     Close          0     0     0                    00  Закрити курсор
```

Коли хост-застосунок викликає `sqlite3_step(stmt)`, інтерпретатор VDBE входить у цикл `switch(pOp->opcode)`. Він знаходить рядок у B-дереві (`SeekRowId`), витягує зміщення колонки зі сторінки пам'яті (`Column`) і зупиняється на інструкції `ResultRow`, повертаючи статус `SQLITE_ROW` у вихідний регістр процесора `RAX`. Уся ця послідовність дій виконується без єдиного системного виклику ОС чи виділення додаткової динамічної пам'яті.

### Безкопійний доступ до даних та спільне володіння пам'яттю

Традиційна робота з базами даних вимагає копіювання даних на кожному шарі абстракції: від драйвера до ORM і кінцевих бізнес-моделей. Вбудовані СУБД уможливлюють принципово інший підхід — **безкопійний доступ** (англ. *zero-copy access*, від англ. *zero* через староітал. *zefiro* від араб. *ṣifr* — нуль; середньофранц. *copie*, від лат. *copia* — розмноження; лат. *accessus* — наближення).

```text
+-------------------------------------------------------------------+
|               Адресний простір процесу застосунку                 |
|                                                                   |
|  [Буферний пул СУБД]                       [Код застосунку]       |
|  +---------------------------+             +-------------------+  |
|  | Сторінка B-Tree (4096 B)  |             | std::span / ptr   |  |
|  | ... [BLOB: 0x4A 0x8F ...] |<------------| const uint8_t*    |  |
|  +---------------------------+  (покажчик) +-------------------+  |
|                                                                   |
+-------------------------------------------------------------------+
```

Коли застосунок запитує бінарні дані (BLOB) або довгий текст, рушій не створює копію масиву в купі. Функція `sqlite3_column_blob()` повертає пряму адресу `const void*`, яка вказує безпосередньо у відкриту сторінку B-дерева в оперативній пам'яті.

:::tabs
```c
/* Отримання прямої адреси даних у сторінковому буфері SQLite */
const void *raw_payload = sqlite3_column_blob(stmt, 2);
int payload_bytes = sqlite3_column_bytes(stmt, 2);

/* Обробка байтів на місці без виклику malloc/memcpy */
if (payload_bytes >= 4) {
    uint32_t header = *((const uint32_t*)raw_payload);
    process_header(header);
}
```
```cpp
/* Ідіоматична безпечна обробка через неволодіючий std::span у C++20 */
const auto* raw_payload = static_cast<const uint8_t*>(sqlite3_column_blob(stmt.get(), 2));
int payload_bytes = sqlite3_column_bytes(stmt.get(), 2);

std::span<const uint8_t> payload_view(raw_payload, static_cast<size_t>(payload_bytes));

if (payload_view.size() >= sizeof(uint32_t)) {
    uint32_t header = 0;
    std::memcpy(&header, payload_view.data(), sizeof(header));
    process_header(header);
}
```
:::

#### Власні аллокатори пам'яті (MemSys) у вбудованих СУБД

Для роботи у критичних вбудованих системах реального часу (бортові контролери, медичні прилади, авіоніка) динамічне виділення пам'яті через стандартний системний `malloc()` неприйнятне через непередбачуваний час виконання та ризик фрагментації купи.

SQLite надає підсистему пам'яті **MemSys**:
1. **MemSys5**: Реалізує алгоритм двійкового розподілу пам'яті (Buddy Allocator) у межах єдиного заздалегідь виділеного статичного буфера (Static Memory Pool). Застосунок на старті виділяє масив розміром, наприклад, 128 МБ (`sqlite3_config(SQLITE_CONFIG_HEAP, buffer, 128*1024*1024, 64)`). Протягом усієї роботи СУБД не робить жодного виклику `brk()` або `mmap()`, повністю гарантуючи відсутність системних збоїв пам'яті.
2. **Zero-Malloc режим**: При використанні підготовлених виразів та MemSys5 виконання запитів відбувається з нульовою кількістю системних виділень пам'яті, що забезпечує стабільний час відгуку в межах мікросекунди.

#### Відображення файлів у пам'ять (Memory-Mapped I/O, mmap)

SQLite дозволяє увімкнути пряме відображення сторінок бази даних у віртуальний адресний простір за допомогою директиви `PRAGMA mmap_size = 1073741824;` (1 ГБ).

У цьому режимі рушій оминає виклики `read()` та `pread()`. Замість копіювання дискової сторінки в проміжний буфер SQLite, ядро операційної системи відображає сторінковий кеш ОС (Page Cache) безпосередньо у віртуальні сторінки процесу. Звернення до будь-якої ділянки таблиці перетворюється на звичайне розіменування покажчика: якщо сторінки немає в RAM, процесор генерує апаратне переривання Page Fault, і ядро підвантажує блок без участі коду користувача.

Проте використання `mmap` має інженерні компроміси:
* **Небезпека сигналу `SIGBUS`**: Якщо інший процес або користувач уріже розмір файлу на диску через системний виклик `ftruncate()`, спроба читання за відображеною адресою викличе апаратну помилку шини `SIGBUS`, яка негайно вбиває весь процес застосунку.
* **Обмеження 32-бітних платформ**: На 32-розрядних мікроконтролерах та процесорах адресний простір обмежений 4 ГБ, що не дозволяє відображати бази даних розміром понад кілька сотень мегабайтів.

#### Інваріанти безпеки пам'яті та час життя покажчиків

Безкопійний доступ забезпечує граничну швидкодію, проте накладає жорсткі обмеження на керування пам'яттю:

1. **Строгий час життя покажчика**: Покажчик, повернутий функціями `sqlite3_column_blob()` або `sqlite3_column_text()`, залишається валідним лише доти, доки вираз перебуває у поточному стані `SQLITE_ROW`. Наступний виклик `sqlite3_step()`, `sqlite3_reset()` або `sqlite3_finalize()` може витіснити сторінку з буферного пулу (Page Eviction) або переписати її новими даними. Збереження такого покажчика призводить до завислого покажчика (Dangling Pointer) та пошкодження пам'яті (Use-After-Free).
2. **Конкуренція за квоту пам'яті процесу**: Буферний пул СУБД ділить ліміт Resident Set Size (RSS) з іншими структурами програми. Якщо застосунок працює в контейнері під керуванням Linux cgroups з лімітом 1 ГБ, а конфігурація кешу СУБД встановлена у 800 МБ, сплеск виділення пам'яті бізнес-логікою призведе до того, що операційна система знищить весь процес сигналом `SIGKILL` через механізм Out-Of-Memory (OOM) Killer.
3. **Керування пам'яттю кешу**: Для запобігання неконтрольованому зростанню розмір кешу сторінок обмежується директивами на кшталт `PRAGMA cache_size = -65536;` (що задає жорсткий ліміт 64 МБ для SQLite) або конфігурацією `block_cache` у RocksDB.

Повні сигнатури C API та таблиці контрактів володіння пам'яттю зібрано у вставці [Специфікація інтерфейсів та двійкових контрактів вбудованих СУБД](root:sf-data/embedded-database/api-embedded-db-interfaces.md).

### Моделі конкурентного доступу та паралелізму в SQLite

Оскільки вбудована база даних не має централізованого диспетчера процесів, координація одночасних операцій читання та запису покладається на внутрішні м'ютекси бібліотеки та блокування файлової системи ОС.

Історично вбудовані бази даних розвивалися від простих словників ключ-значення до складних багатопотокових систем. Історію створення перших вбудованих СУБД та їхню еволюцію описано у вставці [Історія виникнення SQLite та еволюція вбудованих СУБД](root:sf-data/embedded-database/hist-embedded-sqlite-birth.md).

#### Режими потокобезпечності SQLite

SQLite підтримує три взаємовиключні режими багатопотокової роботи:

1. **Однопотоковий (Single-thread)**: Усі внутрішні м'ютекси скомпільовані як порожні заглушки (`#define`). Будь-яке паралельне звернення з двох потоків веде до руйнування структур пам'яті. Забезпечує максимальну швидкодію в однопотокових середовищах.
2. **Багатопотоковий (Multi-thread, `SQLITE_OPEN_NOMUTEX`)**: Рушій гарантує безпеку за умови, що кожне окреме з'єднання `sqlite3*` використовується строго одним потоком. Різні потоки можуть паралельно виконувати запити, використовуючи власні незалежні дескриптори.
3. **Серіалізований (Serialized, `SQLITE_OPEN_FULLMUTEX`)**: Усі виклики до будь-якого дескриптора автоматично захищаються внутрішніми м'ютексами. Потокобезпечно, але створює контенцію (Thread Contention) на рівні процесорних ядер.

#### Традиційний журнал відкату проти режиму WAL

У класичному режимі відкату (**Rollback Journal**) SQLite застосовує грубе блокування на рівні всього файлу бази даних через системні виклики `fcntl()`:

```text
[Читач 1 (SHARED)] ──┐
[Читач 2 (SHARED)] ──┼──> [Файл бази .db] <─── [Записувач (EXCLUSIVE)]  => БЛОКУВАННЯ!
[Читач 3 (SHARED)] ──┘
```

За наявності хоча б одного активного читача записувач не може зафіксувати транзакцію (`SQLITE_BUSY`). Навпаки, активний записувач блокує будь-які операції читання.

Розв'язанням цієї проблеми став **журнал випереджального запису (Write-Ahead Logging, WAL)** та механізм спільної пам'яті:

![Архітектура конкурентного доступу SQLite у режимі WAL](/root/eng/sf-data/embedded-database/img/sqlite-wal-concurrency.svg)
*Конкурентний доступ у SQLite через WAL: потік-записувач додає кадри в лог, не блокуючи паралельних читачів*

У режимі WAL створюються два додаткові файли:
1. **Файл журналу `.db-wal`**: Послідовний журнал, куди записувач додає нові змінені сторінки (кадри) без модифікації основного файлу бази даних.
2. **Індекс спільної пам'яті `.db-shm`**: Спеціальний файл, що відображається у віртуальну пам'ять кожного процесу через системний виклик `mmap()`. Він містить хеш-таблицю відповідності номерів сторінок та їхніх найсвіжіших зміщень у файлі WAL.

```text
Алгоритм читання в режимі WAL:
1. Потік фіксує поточний максимальний номер кадру у WAL (Read Mark).
2. Для кожної запитуваної сторінки потік перевіряє хеш-індекс у .db-shm:
   - Якщо сторінка є у WAL з номером <= Read Mark:
       Зчитати свіжу сторінку безпосередньо з .db-wal.
   - Інакше:
       Зчитати базову сторінку з основного файлу .db.
3. Читач не блокує записувача, оскільки записувач лише дописує нові кадри в кінець логу.
```

#### Внутрішня будова файлу спільної пам'яті (.db-shm)

Файл `.db-shm` розбитий на сторінки розміром 32 КБ. Перша сторінка містить 136-байтовий системний заголовок:
* **`wal_header`**: Номер версії формату WAL, розмір сторінки даних, поточний індекс транзакції.
* **Масив `read_marks[5]`**: П'ять 32-бітних чисел, які позначають максимальні номери кадрів WAL, зафіксовані активними читачами. Коли читач починає транзакцію, він захоплює спільне блокування на один із байтів у діапазоні зміщень `120..127` файлу `.db-shm` через `fcntl(F_SETLK)` і записує свій `Read Mark`.
* **Хеш-таблиці кадрів**: Решта простору сторінки містить хеш-індекси, які дозволяють за час `O(1)` з'ясувати, чи міститься конкретна сторінка `PageID` у поточному WAL-файлі, усуваючи необхідність лінійного сканування мегабайтних дискових логів.

Практичну реалізацію багатопотокового пулу з'єднань із WAL-режимом наведено у вставці [Практична реалізація багатопотокової обробки на SQLite та DuckDB](root:sf-data/embedded-database/proj-embedded-sqlite-duckdb.md).

### Векторизована аналітика в процесі: Архітектура DuckDB

Якщо транзакційні СУБД (SQLite) чудово оптимізовані для точкових вставок та вибірок окремих кортежів (OLTP), то при аналітичних запитах (OLAP) над мільйонами рядків традиційна порядкова модель ітератора Volcano зазнає краху.

При класичній обробці Volcano кожен рядок вимагає виклику віртуальної функції `step()`. Для 10 мільйонів рядків це означає 10 мільйонів викликів функцій, постійне скидання конвеєра інструкцій процесора (Branch Misprediction) та розсіювання даних по кешах процесора (Instruction Cache Thrashing).

Цю проблему вирішує **векторизоване виконання** (англ. *vectorized execution*, від лат. *vector* — носій, перевізник, від *vehere* — везти; лат. *exsecutio* — виконання, доведення до кінця), реалізоване у вбудованій СУБД DuckDB.

![Векторизоване стовпцеве виконання DuckDB в оперативній пам'яті](/root/eng/sf-data/embedded-database/img/duckdb-vector-columnar.svg)
*Стовпцевий конвеєр DuckDB: опрацювання векторів DataChunk у кеші процесора із застосуванням SIMD*

#### Фізична організація векторів та пакетів DataChunk

DuckDB оперує даними у стовпцевому форматі (Columnar Layout). Основним квантом обробки є `DataChunk` — набір масивів фіксованого розміру (за замовчуванням 2048 значень на вектор):

1. **Неперервні масиви в оперативній пам'яті**:
   Кожен вектор стовпця (`Vector`) є послідовним масивом скалярних значень (`int64_t[]`, `double[]`). Масив розміром `2048 × 8 байтів = 16 КБ` повністю гарантовано вміщується у надшвидкий кеш даних першого рівня L1 Data Cache сучасного процесора (типовий розмір 32–48 КБ на ядро).
2. **Апаратна локальність кеш-ліній та апаратний попередній вибір (Prefetching)**:
   При рядковому розміщенні (Row-oriented) зчитування одного стовпця з таблиці на 20 колонок завантажує всю 64-байтну лінію кешу, з якої корисними є лише 4–8 байтів (коефіцієнт використання шини пам'яті лише 5–10%). У стовпцевому форматі DuckDB 100% завантаженої кеш-лінії містить цільові значення, а апаратний блок попереднього вибору процесора (Hardware Stream Prefetcher) автоматично підвантажує наступні блоки пам'яті до того, як процесор їх запитає.
3. **Апаратна SIMD-векторизація**:
   Завдяки тому, що дані лежать у пам'яті послідовно без проміжних заголовків рядків, компілятор генерує векторні інструкції AVX2 / AVX-512 (x86-64) або ARM NEON (AArch64). Процесор виконує операції фільтрації, множення та агрегації над 4–8 значеннями за один такт CPU.
4. **Morsel-Driven паралелізм**:
   DuckDB автоматично розпаралелює сканування таблиць між доступними ядрами хост-процесу. Потоки застосунку розбирають невеликі кванти даних (Morsels по 100 000 рядків) із черги без централізованих блокувань.
5. **Стандарт Apache Arrow та нульова вартість інтеграції**:
   DuckDB підтримує бінарний стандарт Apache Arrow C Data Interface. Якщо застосунок використовує аналітичні бібліотеки Python (Polars, Pandas), Rust або C++, передача масиву на мільярди чисел між DuckDB та пам'яттю програми відбувається без жодного копіювання байтів — передаються лише покажчики на структури `ArrowArray`.

### Вбудовані сховища типу ключ-значення: Архітектура RocksDB

Для високонавантажених сценаріїв із переважним потоком запису (телеметрія, черги подій, кеші стану) реляційні сторінкові структури B-Tree стикаються з проблемою ампліфікації випадкового запису (Write Amplification). У цих випадках стандартом стали вбудовані рушії на базі **дерева злиття зі структурою журналу** (Log-Structured Merge-tree, LSM-tree; англ. *log-structured merge*, від грец. *δένдрон* — дерево; лат. *mergere* — поєднувати).

Найвідомішим прикладом є бібліотека **RocksDB** (розроблена Meta на базі Google LevelDB).

![Архітектура вбудованого LSM-рушія RocksDB у пам'яті процесу](/root/eng/sf-data/embedded-database/img/rocksdb-lsm-embedded.svg)
*Пам'ять та дискові шари RocksDB: запис у MemTable у купі процесу та фонова багатопотокова компактифікація*

#### Внутрішні структури пам'яті RocksDB

1. **Активний `MemTable`**:
   Усі операції запису (`Put`, `Delete`) додаються до структури даних у купі хост-процесу — зазвичай сортованого списку з пропусками (**SkipList**). SkipList забезпечує паралельний конкурентний запис із багатьох потоків застосунку без глобальних блокувань за допомогою атомарних інструкцій CAS (Compare-And-Swap).
2. **Журнал попереднього запису (WAL)**:
   Одночасно з додаванням у `MemTable` запис послідовно фіксується у файлі WAL на диску для забезпечення надійності за стандартом ACID.
3. **Незмінні таблиці `Immutable MemTables`**:
   Коли активний MemTable заповнюється (наприклад, досягає 64 МБ), він переводиться у стан лише для читання і стає в чергу на скидання на диск (Flush). Застосунок продовжує писати у новий свіжий MemTable.
4. **Фоновий пул потоків (Flush & Compaction)**:
   RocksDB створює пул фонових потоків безпосередньо всередині хост-процесу. Потоки скидають заповнені MemTable на диск у вигляді незмінних сортованих файлів (SSTables — Sorted String Tables) та виконують їхнє фонове ущільнення і видалення застарілих версій (Compaction).
5. **Блоковий кеш (Block Cache)**:
   Кеш розпакованих блоків даних з SSTable зберігається в купі процесу під керуванням алгоритму LRU або 2Q, усуваючи повторні дискові зчитування для гарячих ключів.

#### Запобігання зупинкам запису (Write Stalls)

У вбудованому LSM-рушії швидкість надходження даних із потоків застосунку в оперативну пам'ять (MemTable) часто перевищує пропускну здатність дискової підсистеми I/O під час компактифікації.

Якщо кількість нескинутих файлів нульового рівня (Level 0 SSTables) перевищує поріг `level0_slowdown_writes_trigger` (типово 20 файлів), RocksDB штучно сповільнює виклики `Put()` хост-процесу, додаючи мікросекундні паузи. Якщо кількість файлів досягає `level0_stop_writes_trigger` (типово 36 файлів), усі потоки запису застосунку повністю блокуються, доки фонові воркери хост-процесу не завершать компактифікацію. Тому правильний тюнінг пулу фонових потоків `IncreaseParallelism()` та лімітів пам'яті є критичним для запобігання деградації затримок хост-сервісу.

### Межі надійності, ізоляція збоїв та блокування файлів

Вибір між вбудованою та клієнт-серверною базою даних завжди вимагає компромісу між максимальною продуктивністю та надійністю ізоляції помилок.

#### Радіус ураження збоїв (Blast Radius)

У клієнт-серверній архітектурі апаратні помилки та аварійні завершення строго ізольовані межею процесів ОС:
* Якщо процес клієнта падає з помилкою `Segmentation Fault` (помилка сегментації через невалідний покажчик), сервер СУБД продовжує стабільно працювати, закриваючи обірваний сокет і відкочуючи незавершену транзакцію.
* Якщо падає сервер СУБД, клієнт отримує виняток `Connection Reset` і може спробувати перепідключитися до резервної репліки.

У вбудованій СУБД ізоляція пам'яті між кодом програми та базою відсутня:

```text
+------------------------------------------------------------------+
|                   Єдиний процес застосунку                       |
|                                                                  |
|  [Код застосунку]                  [Вбудована СУБД (SQLite)]     |
|  Помилка сегментації:               Пошкодження сторінок пам'яті: |
|  *wild_ptr = 0xDEAD;  -------->    Buffer Pool / Index Corrupted |
|                                                                  |
|  ==============================================================  |
|            КРАХ УСЬОГО ПРОЦЕСУ (SIGSEGV / SIGABRT)               |
+------------------------------------------------------------------+
```

1. **Пошкодження сторінкового кешу (Memory Corruption)**: Помилка в коді програми на C/C++ (вихід за межі масиву, запис за випадковим покажчиком) може безпосередньо перезаписати байти у сторінковому пулі SQLite або MemTable RocksDB. Якщо ці пошкоджені сторінки згодом будуть скинуті на диск командою `fsync()`, файл бази даних буде незворотно зруйновано.
2. **Фатальні помилки бібліотеки**: Будь-яке аварійне спрацювання системного макроса `assert()` або паніка через вичерпання ресурсів всередині бібліотеки СУБД негайно завершує виконання всього хост-процесу.

#### Блокування у багатопроцесному середовищі та небезпека мережевих файлових систем

Вбудовані СУБД підтримують одночасне відкриття одного файлу бази даних різними процесами ОС. Координація здійснюється за допомогою консультативних блокувань POSIX `fcntl()` (`F_SETLK`).

Проте використання вбудованих СУБД через мережеві файлові системи (NFS, SMB/CIFS) несе критичні ризики:
* **Ненадійність або відсутність реалізації блокувань `fcntl`**: Багато мережевих сховищ не підтримують коректну семантику діапазонних блокувань байтів (Byte-Range Locks). Два процеси на різних серверах можуть одночасно вирішити, що вони володіють ексклюзивним правом на запис, що призводить до негайного пошкодження внутрішньої структури B-дерева.
* **Кешування на боці клієнта NFS**: Клієнтські драйвери мережевих ФС агресивно кешують дискові сторінки в пам'яті ядра. Коли один процес записує нову сторінку, інший процес на сусідньому сервері читає застарілу версію зі свого локального кешу ядра, порушуючи інваріанти ACID.

> **Інженерне правило:** Файли вбудованих баз даних SQLite, DuckDB та RocksDB повинні розміщуватися виключно на локальних блокових пристроях (NVMe, SSD, HDD) або в пам'яті (`tmpfs`), де операційна система гарантує суворе виконання семантики POSIX-блокувань.

### Інженерні компроміси та критерії вибору архітектури

Порівняння архітектурних характеристик вбудованих та клієнт-серверних баз даних:

| Характеристика | Вбудована СУБД (SQLite, DuckDB, RocksDB) | Клієнт-серверна СУБД (PostgreSQL, MySQL, ClickHouse) |
|---|---|---|
| **Мінімальна затримка запиту** | `5–25` наносекунд (виклик функції ABI) | `0.1–2.0` мілісекунди (IPC / TCP сокети) |
| **Пропускна здатність читання** | Обмежена лише швидкістю шини пам'яті (до `50–60` ГБ/с) | Обмежена серіалізацією та мережевим інтерфейсом (`1–5` ГБ/с) |
| **Адміністрування та експлуатація** | Нульова (Zero-conf, єдиний файл, немає процесів демонів) | Висока (налаштування прав, портів, резервного копіювання, моніторингу) |
| **Масштабування запису** | Строго 1 записувач на файл (SQLite WAL) або обмежене ядром | Масштабоване (пули з'єднань, рядкові блокування, шардинг) |
| **Мережевий доступ** | Відсутній (лише локальний доступ із процесу) | Нативний (підключення багатьох мікросервісів через мережу) |
| **Ізоляція збоїв** | Відсутня (збій пам'яті хоста руйнує базу) | Повна (процес клієнта і процес СУБД ізольовані ОС) |
| **Споживання пам'яті** | Мінімальне (від кількох сотень кілобайтів) | Значне (від сотень мегабайтів на екземпляр) |

> 🔧 **Навіщо це в реальній розробці.**
> 1. **Клієнтські та мобільні застосунки (Edge & Mobile)**: Вбудована СУБД SQLite є де-факто стандартом для збереження стану на мобільних платформах iOS та Android, у веббраузерах (історія, закладки, локальний кеш WebSQL/IndexedDB) та десктопних програмах, забезпечуючи миттєвий старт без встановлення сторонніх сервісів.
> 2. **Швидка локальна аналітика (In-Memory OLAP)**: DuckDB дозволяє дата-сайєнтистам та бекенд-розробникам виконувати складні агрегаційні SQL-запити над гігабайтними файлами Parquet та CSV безпосередньо всередині Python/Rust процесів за мілісекунди, усуваючи необхідність розгортання важких кластерів Spark або ClickHouse.
> 3. **Внутрішні рушії зберігання розподілених систем**: RocksDB використовується як базовий дисковий рушій у великих розподілених СУБД (CockroachDB, TiKV, YugabyteDB) та брокерах повідомлень (Apache Kafka Streams), де низькорівневе LSM-дерево забезпечує максимальну швидкість запису на NVMe-накопичувачі.
