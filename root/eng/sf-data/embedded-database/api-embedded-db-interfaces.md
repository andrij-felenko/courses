# 📋 Специфікація інтерфейсів та двійкових контрактів вбудованих СУБД

Вбудована СУБД експортує прямий двійковий інтерфейс мови C (C Application Binary Interface, C ABI), через який хост-застосунок передає параметри запитів, отримує прямі адреси буферів пам'яті та керує станом транзакцій без проміжних мережевих протоколів. На відміну від драйверів клієнт-серверних баз даних, де клієнт надсилає текстові або бінарні кадри через мережевий сокет і чекає на відповідь через системні виклики операційної системи, звернення до вбудованого рушія є послідовністю прямих викликів бібліотечних функцій із передачею покажчиків через регістри центрального процесора.

Нижче наведено технічний довідник контрактів основних вбудованих рушіїв: транзакційної реляційної системи SQLite, векторизованої аналітичної системи DuckDB та сховища пар «ключ-значення» RocksDB.

---

### 1. Ядро інтерфейсу SQLite C API та життєвий цикл виразів

Архітектура взаємодії з SQLite будується навколо двох ключових структур: дескриптора з'єднання `sqlite3` та скомпільованого байт-коду запиту `sqlite3_stmt`. Життєвий цикл запиту є детермінованим скінченним автоматом із такими станами:
1. **Підготовка (Preparation)**: Текст SQL транслюється компілятором у внутрішній байт-код для віртуальної машини VDBE (Virtual DataBase Engine).
2. **Зв'язування параметрів (Binding)**: Аргументи запиту прив'язуються до позиційних або іменованих параметрів без необхідності конкатенації рядків, що запобігає SQL-ін'єкціям.
3. **Крокове виконання (Stepping)**: Віртуальна машина VDBE виконує інструкції, зупиняючись на кожному згенерованому рядку або досягаючи завершення обходу індексу.
4. **Скидання або фіналізація (Reset / Finalization)**: Звільнення ресурсів і повернення байт-коду до початкового стану для повторного використання або повного видалення з купи.

#### Відкриття та конфігурація з'єднання: `sqlite3_open_v2`

```text
int sqlite3_open_v2(
    const char *filename,   /* Шлях до файлу в UTF-8 або ":memory:" */
    sqlite3 **ppDb,         /* Вихідний покажчик на структуру з'єднання */
    int flags,              /* Бітова маска прапорців режиму доступу */
    const char *zVfs        /* Ім'я модуля віртуальної файлової системи (VFS) або NULL */
);
```

Функція `sqlite3_open_v2` ініціалізує контекст з'єднання в купі процесу, відкриває відповідні дескриптори файлів в операційній системі та відображає службові сторінки заголовка бази в пам'ять.

**Таблиця бітових прапорців режиму доступу (`flags`):**

| Прапорець | Числове значення | Призначення та вплив на пам'ять |
|---|---|---|
| `SQLITE_OPEN_READONLY` | `0x00000001` | База відкривається лише для читання. Запис заборонений на рівні VFS. |
| `SQLITE_OPEN_READWRITE` | `0x00000002` | Дозволяє операції читання та запису за наявності прав у файловій системі. |
| `SQLITE_OPEN_CREATE` | `0x00000004` | Створює новий файл бази даних, якщо він відсутній на диску. |
| `SQLITE_OPEN_NOMUTEX` | `0x00008000` | Багатопотоковий режим (Multi-thread): відключає м'ютекси всередині з'єднання. З'єднання не можна одночасно викликати з різних потоків. |
| `SQLITE_OPEN_FULLMUTEX` | `0x00010000` | Серіалізований режим (Serialized): внутрішній м'ютекс захищає всі виклики. Потокобезпечно, але створює блокування ядер. |
| `SQLITE_OPEN_MEMORY` | `0x00000080` | Створює повністю in-memory базу, знищувану при закритті останнього дескриптора. |

#### Підготовка скомпільованого виразу: `sqlite3_prepare_v3`

```text
int sqlite3_prepare_v3(
    sqlite3 *db,            /* Дескриптор відкритого з'єднання */
    const char *zSql,       /* Текст SQL-запиту в UTF-8 */
    int nByte,              /* Довжина рядка в байтах (або -1 для читання до нульового байта) */
    unsigned int prepFlags, /* Прапорці оптимізації компілятора запитів */
    sqlite3_stmt **ppStmt,  /* Вихідний покажчик на байт-код виразу VDBE */
    const char **pzTail     /* Покажчик на залишок нерозібраного SQL-рядка */
);
```

**Прапорці підготовки (`prepFlags`):**

* `SQLITE_PREPARE_PERSISTENT` (`0x01`): Підказує планувальнику, що вираз виконуватиметься багаторазово. SQLite оптимізує розміщення байт-коду в пам'яті та уникає передчасного скидання кешу планів.
* `SQLITE_PREPARE_NORMALIZE` (`0x02`): Увімкнення генерації нормалізованого тексту запиту для аналітичних логів.
* `SQLITE_PREPARE_NO_VTAB` (`0x04`): Забороняє запиту звертатися до віртуальних таблиць (Virtual Tables), захищаючи від атак через підміну розширень.

#### Покрокове виконання: `sqlite3_step`

```text
int sqlite3_step(sqlite3_stmt *pStmt);
```

Функція переводить віртуальну машину VDBE на наступну інструкцію формування кортежу. Якщо результат запиту містить рядки, функція повертає `SQLITE_ROW`, після чого застосунок може викликати функції сімейства `sqlite3_column_*`.

**Коди повернення та стани автомата:**

| Код повернення | Опис стану віртуальної машини VDBE |
|---|---|
| `SQLITE_ROW` (`100`) | Доступний черговий рядок результату. Можна викликати функції `sqlite3_column_*`. |
| `SQLITE_DONE` (`101`) | Запит успішно виконано (або вибірка завершилася). Потрібен виклик `sqlite3_reset()` для повторного запуску. |
| `SQLITE_BUSY` (`5`) | Файл заблоковано іншим процесом/потоком. Слід повторити виклик після паузи. |
| `SQLITE_LOCKED` (`6`) | Конфлікт блокування таблиці в межах одного з'єднання або спільного кешу. |
| `SQLITE_ERROR` (`1`) | Помилка часу виконання (порушення обмежень цілісності, помилка типу). |
| `SQLITE_MISUSE` (`21`) | Некоректне використання API (виклик функції у невідповідному стані або з паралельного потоку). |

#### Безкопійне отримання даних: `sqlite3_column_*`

Отримання результатів здійснюється прямим зчитуванням комірок пам'яті сторінки, яка завантажена в буферний пул.

| Сигнатура функції | Повертане значення | Контракт володіння пам'яттю (Memory Ownership) |
|---|---|---|
| `const void* sqlite3_column_blob(sqlite3_stmt*, int iCol)` | Пряма адреса бінарних даних у буфері сторінки | **Заборонено звільняти через `free()`**. Покажчик валідний лише до наступного виклику `step()`, `reset()`, `finalize()`. |
| `const unsigned char* sqlite3_column_text(sqlite3_stmt*, int iCol)` | Покажчик на UTF-8 рядок із нульовим символом на кінці | **Заборонено змінювати або звільняти**. Валідний до наступної зміни стану виразу. |
| `sqlite3_int64 sqlite3_column_int64(sqlite3_stmt*, int iCol)` | 64-бітне ціле число зі знаком | Передається за значенням у регістрах CPU. |
| `double sqlite3_column_double(sqlite3_stmt*, int iCol)` | 64-бітне число з рухомою комою (IEEE 754) | Передається за значенням у регістрах XMM/FPU. |
| `int sqlite3_column_bytes(sqlite3_stmt*, int iCol)` | Розмір BLOB або довжина тексту в байтах | Розраховується миттєво з заголовка запису. |

#### Механіка блокувань транзакцій: `BEGIN DEFERRED`, `IMMEDIATE`, `EXCLUSIVE`

SQLite підтримує три рівні захоплення блокувань при старті транзакції:
1. **`BEGIN DEFERRED` (за замовчуванням)**: Блокування не захоплюється в момент старту. З'єднання починає роботу у стані `UNLOCKED`. При першій операції читання захоплюється спільне блокування `SHARED`. Якщо згодом виконується запис, з'єднання намагається підвищити рівень блокування до `RESERVED`. Якщо інше з'єднання вже встигло отримати `RESERVED`, запит зазнає невдачі з помилкою `SQLITE_BUSY`.
2. **`BEGIN IMMEDIATE`**: З'єднання негайно намагається захопити блокування `RESERVED`. Інші потоки можуть продовжувати читання (`SHARED`), але жоден інший потік не зможе розпочати транзакцію запису. Це запобігає взаємним тупиковим блокуванням (Deadlocks) між паралельними записувачами.
3. **`BEGIN EXCLUSIVE`**: Захоплюється ексклюзивне блокування `EXCLUSIVE`, яке повністю забороняє будь-яке читання та запис іншим з'єднанням (у режимі rollback-журналу).

#### Контрольна точка журналу WAL: `sqlite3_wal_checkpoint_v2`

```text
int sqlite3_wal_checkpoint_v2(
    sqlite3 *db,            /* Дескриптор з'єднання */
    const char *zDb,        /* Ім'я схеми ("main" або NULL для всіх схем) */
    int eMode,              /* Режим виконання контрольної точки */
    int *pnLog,             /* Вихідний розмір WAL у кадрах на момент старту */
    int *pnCkpt             /* Вихідна кількість успішно перенесених кадрів */
);
```

Контрольна точка (Checkpoint) забезпечує перенесення змінених сторінок із журналу `.db-wal` назад в основний файл бази даних `.db`.

**Режими чекпойнта (`eMode`):**

1. `SQLITE_CHECKPOINT_PASSIVE` (`0`): Переносить сторінки без зупинки інших потоків. Не чекає завершення активних читачів.
2. `SQLITE_CHECKPOINT_FULL` (`1`): Очікує завершення всіх читачів, які блокують перенесення сторінок, блокує нові читання і скидає весь лог на диск.
3. `SQLITE_CHECKPOINT_RESTART` (`2`): Аналогічно `FULL`, але додатково очікує, поки всі читачі перемкнуться на основний файл, щоб наступний запис почався з кадру 0.
4. `SQLITE_CHECKPOINT_TRUNCATE` (`3`): Аналогічно `RESTART`, але після завершення викликає `ftruncate()`, зменшуючи розмір файлу `.db-wal` до 0 байтів.

### 2. Специфікація DuckDB C API та векторний обмін

DuckDB розроблена для аналітичних навантажень і базується на векторизованій моделі обробки. Основною структурною одиницею обміну даними є `duckdb_data_chunk`, що інкапсулює набір стовпцевих векторів фіксованої довжини (типово 2048 елементів).

```text
/* Ініціалізація та керування з'єднанням */
duckdb_state duckdb_open(const char *path, duckdb_database *out_database);
duckdb_state duckdb_connect(duckdb_database database, duckdb_connection *out_connection);
void duckdb_disconnect(duckdb_connection *connection);
void duckdb_close(duckdb_database *database);

/* Виконання запиту та отримання результуючого набору */
duckdb_state duckdb_query(duckdb_connection connection, const char *query, duckdb_result *out_result);
void duckdb_destroy_result(duckdb_result *result);

/* Векторизована ітерація по чанках */
idx_t duckdb_result_chunk_count(duckdb_result result);
duckdb_data_chunk duckdb_result_get_chunk(duckdb_result result, idx_t chunk_index);
idx_t duckdb_data_chunk_get_size(duckdb_data_chunk chunk);
duckdb_vector duckdb_data_chunk_get_vector(duckdb_data_chunk chunk, idx_t col_idx);
void* duckdb_vector_get_data(duckdb_vector vector);
uint64_t* duckdb_vector_get_validity(duckdb_vector vector);
void duckdb_destroy_data_chunk(duckdb_data_chunk *chunk);
```

#### Контракти векторного доступу та інтеграція з Apache Arrow

1. **Неперервність масиву в пам'яті**: Функція `duckdb_vector_get_data()` повертає прямий покажчик на послідовний блок пам'яті відповідного скалярного типу (наприклад, `int64_t*` або `double*`). Це дозволяє задіяти компіляторну автовекторизацію та SIMD-інструкції (AVX2, AVX-512, ARM NEON).
2. **Бітова маска валідності**: Наявність значень NULL відстежується окремим бітовим вектором через `duckdb_vector_get_validity()`. Якщо функція повертає `NULL`, вектор гарантовано не містить пропущених значень, що усуває необхідність покрокової перевірки кожного елемента в гарячому циклі.
3. **Apache Arrow C Data Interface**: DuckDB підтримує безкопійний експорт та імпорт через стандартні структури `ArrowSchema` та `ArrowArray`. Передача таблиць між процесором DuckDB та аналітичними бібліотеками (Python Polars, Pandas, C++ Arrow) відбувається виключно передачею 64-бітних адрес структур без побайтового копіювання даних.

### 3. Специфікація RocksDB C API та керування ресурсами

RocksDB надає інтерфейс вбудованого сховища ключ-значення, де дані зберігаються у вигляді сортованих байтових послідовностей (LSM-дерево).

```text
/* Керування конфігурацією та базою */
rocksdb_options_t* rocksdb_options_create(void);
void rocksdb_options_set_create_if_missing(rocksdb_options_t*, unsigned char);
void rocksdb_options_increase_parallelism(rocksdb_options_t*, int total_threads);
rocksdb_t* rocksdb_open(const rocksdb_options_t *options, const char *name, char **errptr);
void rocksdb_close(rocksdb_t *db);

/* Точкові операції */
void rocksdb_put(rocksdb_t *db, const rocksdb_writeoptions_t *options, 
                 const char *key, size_t keylen, const char *val, size_t vallen, char **errptr);
char* rocksdb_get(rocksdb_t *db, const rocksdb_readoptions_t *options, 
                 const char *key, size_t keylen, size_t *vallen, char **errptr);
void rocksdb_delete(rocksdb_t *db, const rocksdb_writeoptions_t *options, 
                    const char *key, size_t keylen, char **errptr);

/* Атомарні пакети */
rocksdb_writebatch_t* rocksdb_writebatch_create(void);
void rocksdb_writebatch_put(rocksdb_writebatch_t*, const char *key, size_t klen, const char *val, size_t vlen);
void rocksdb_writebatch_delete(rocksdb_writebatch_t*, const char *key, size_t klen);
void rocksdb_write(rocksdb_t *db, const rocksdb_writeoptions_t *options, 
                   rocksdb_writebatch_t *batch, char **errptr);
void rocksdb_writebatch_destroy(rocksdb_writebatch_t*);
```

#### Правила виділення пам'яті в RocksDB C API

1. **Значення результатів точкового читання**: Функція `rocksdb_get()` виділяє динамічний буфер у купі процесу під кожне знайдене значення. Застосунок несе строге зобов'язання викликати функцію `rocksdb_free(val)` після завершення обробки рядка, інакше виникає витік пам'яті (Memory Leak).
2. **Обробка рядків помилок**: Якщо покажчик `*errptr` після виконання операції не дорівнює `NULL`, рядок із повідомленням про помилку виділено рушієм і має бути звільнений через `rocksdb_free(*errptr)`.

### Матриця потокобезпечності та лімітів конкурентності

| СУБД | Дескриптор екземпляра (Engine/DB) | Дескриптор з'єднання (Connection/Handle) | Одночасні читачі | Одночасні записувачі |
|---|---|---|---|---|
| **SQLite (Default)** | Відсутній (є лише з'єднання) | Потокобезпечний (Full-mutex) | 1 потік на з'єднання | 1 потік на файл |
| **SQLite (WAL + NoMutex)** | Відсутній (є лише з'єднання) | **Не потокобезпечний** (1 потік = 1 з'єднання) | Необмежено (паралельно) | **Строго 1 записувач на файл** |
| **DuckDB** | Потокобезпечний (`duckdb_database`) | **Не потокобезпечний** (`duckdb_connection`) | Необмежено (Morsel Parallelism) | 1 активний транзакційний записувач |
| **RocksDB** | Потокобезпечний (`rocksdb_t`) | Спільний екземпляр | Необмежено (Lock-free MemTable / SST) | Паралельні атомарні записи (WriteBatch) |
