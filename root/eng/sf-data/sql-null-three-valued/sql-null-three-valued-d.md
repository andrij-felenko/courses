У серпні 1996 року головний сервер медичного страхування великої мережі клінік Каліфорнії надіслав помилкові рахунки на суму понад вісімсот тисяч доларів пацієнтам пенсійного віку. Причиною збою стала колонка «вік пацієнта», у якій розробники за старою традицією мови COBOL записували число `999` щоразу, коли реальна дата народження людини була невідома під час первинної госпіталізації. Коли аналітичний відділ запустив автоматичний скрипт нарахування спеціальних тарифів із фільтром вибірки для людей похилого віку, система вивантажила тисячі новонароджених дітей та екстрених пацієнтів як глибоких довгожителів, а функція підрахунку середнього віку пацієнтів відділення кардіології видала абсолютно абсурдне число.

Аналогічна аварія трапилася в банківській системі розрахунку кредитних ризиків у Нью-Йорку, де інженери використовували число `-1` для позначення відсутності кредитного рейтингу нових клієнтів. Агрегатна функція підрахунку середнього скорингового балу портфеля автоматично врахувала від'ємні одиниці, штучно занизила загальну оцінку капіталізації банку та спровокувала автоматичне блокування міжбанківських кредитних ліній регулятором.

Ці інциденти викрили фундаментальну ваду підходу, побудованого на використанні «сигнальних значень» (sentinel values, від латинського *sentina* — «сторожовий знак»). Якщо відсутність значення позначати спеціальними числами (`-1`, `0`, `999`, `9999-12-31`) чи порожніми рядками `""`, домен дійсних даних забруднюється метаінформацією. Будь-яка агрегатна функція, математичне перетворення чи діапазонне порівняння починає сприймати службовий маркер як реальне вимірювання, що неминуче руйнує коректність математичних обчислень та призводить до прихованих фінансових і системних збитків.

*Порівняння підходів: використання магічних сигнальних чисел у домені даних проти винесення факту відсутності на рівень реляційних метаданих.*

## Маркер відсутності значення та природа NULL

Аби захистити домени даних від забруднення сигнальними числами, реляційна модель у 1979 році ввела спеціальний маркер відсутності інформації — `NULL` (від латинського *nullus* — «жоден, ніякий»). Фундаментальне правило реляційної теорії стверджує: `NULL` не є числом, рядком чи якимось особливим значенням типу даних. Це метаінформаційний прапорець, який сигналізує рушію бази даних про те, що значення в цій позиції кортежу наразі **невідоме**, **відсутнє** або **незастосовне**.

Оскільки `NULL` не є значенням, до нього не можна застосовувати звичайні операції порівняння. Якщо у базі даних є дві різні людини, і про жодну з них невідомий розмір заробітної плати, чи можна стверджувати, що їхні заробітні плати однакові? Класична логіка не має підстав стверджувати ані «так», ані «ні». Їхні зарплати можуть виявитися як однаковими, так і кардинально різними, якщо ми колись дізнаємося справжні цифри.

Тому твердження `Salary = NULL` або навіть `NULL = NULL` не може оцінюватися як істина (`TRUE`) чи хибність (`FALSE`). Воно має статус **невідомості**. Ця необхідність коректної обробки неповної інформації змусила реляційні СУБД відмовитися від класичної двійкової логіки Джорджа Буля (Boolean logic, 2VL) і перейти до **тризначної логіки** (Three-Valued Logic, 3VL, тривалентна логіка, від латинського *valens* — «маючий значення»).

Детальний аналіз історичної полеміки довкола введення `NULL` між творцем реляційної моделі Едгаром Коддом та його критиками Крісом Дейтом і Г'ю Дарвеном викладено у вставці [📜 Історія виникнення NULL у реляційній моделі та суперечки Кодда, Дейта й Дарвена](root:sf-data/sql-null-three-valued/hist-codd-null-debate.md).

## Алгебра тризначної логіки Клини (3VL)

Стандарт мови SQL використовує тризначну логіку, сформульовану американським математиком Стівеном Коулом Кліні (Stephen Cole Kleene) у 1938 році. У цій системі множина істиннісних значень складається з трьох елементів:

```
L₃ = {FALSE, UNKNOWN, TRUE}
```

Для побудови строгих алгебраїчних операцій цим станам зіставляють числові ступені достовірності на відрізку `[0, 1]`: `FALSE = 0`, `UNKNOWN = 1/2`, `TRUE = 1`.

![Решітка тризначної логіки Клини](/root/eng/sf-data/sql-null-three-valued/img/fig2-three-valued-logic-lattice.svg)
*Решітка істинності Клини: впорядкування значень та обчислення логічних операторів кон'юнкції, диз'юнкції та заперечення.*

Між цими трьома станами встановлюється природне лінійне впорядкування:

```
FALSE (0) < UNKNOWN (1/2) < TRUE (1)
```

Будь-які логічні зв'язки мови SQL над предикатами обчислюються за трьома універсальними алгебраїчними правилами:

1. **Кон'юнкція (`AND`):** результат дорівнює **мінімуму** ступенів істинності операндів:
   ```
   val(A AND B) = min(val(A), val(B))
   ```
2. **Диз'юнкція (`OR`):** результат дорівнює **максимуму** ступенів істинності операндів:
   ```
   val(A OR B) = max(val(A), val(B))
   ```
3. **Заперечення (`NOT`):** результат дорівнює **доповненню** ступеня істинності до одиниці:
   ```
   val(NOT A) = 1 - val(A)
   ```

### Таблиці істинності зв'язок у 3VL

З цих трьох формул безпосередньо випливають правила взаємодії відомих булевих станів із невизначеністю `UNKNOWN`.

Таблиця оператора `AND`:

| `AND` | `FALSE` (0) | `UNKNOWN` (1/2) | `TRUE` (1) |
|---|---|---|---|
| **`FALSE` (0)** | `FALSE` | `FALSE` | `FALSE` |
| **`UNKNOWN` (1/2)** | `FALSE` | `UNKNOWN` | `UNKNOWN` |
| **`TRUE` (1)** | `FALSE` | `UNKNOWN` | `TRUE` |

Зверніть увагу на клітинку `UNKNOWN AND FALSE = FALSE`. Якщо ліва частина виразу невідома, але права частина точно хибна, весь кон'юнктивний вираз гарантовано хибний, оскільки `min(1/2, 0) = 0`. Жодне потенційне розкриття невідомого значення в майбутньому не здатне перетворити хибний вираз на істинний.

Таблиця оператора `OR`:

| `OR` | `FALSE` (0) | `UNKNOWN` (1/2) | `TRUE` (1) |
|---|---|---|---|
| **`FALSE` (0)** | `FALSE` | `UNKNOWN` | `TRUE` |
| **`UNKNOWN` (1/2)** | `UNKNOWN` | `UNKNOWN` | `TRUE` |
| **`TRUE` (1)** | `TRUE` | `TRUE` | `TRUE` |

Аналогічно, `UNKNOWN OR TRUE = TRUE`, оскільки `max(1/2, 1) = 1`. Якщо хоча б один компонент диз'юнкції істинний, загальний результат уже визначено на користь істини незалежно від невизначеності другого операнда.

Таблиця оператора `NOT`:

| `A` | `NOT A` |
|---|---|
| `FALSE` | `TRUE` |
| `UNKNOWN` | `UNKNOWN` |
| `TRUE` | `FALSE` |

Заперечення невідомості залишається невідомістю: `1 - 1/2 = 1/2`. Повне математичне виведення алгебраїчних властивостей решітки Клини та законів де Моргана у 3VL наведено у вставці [🧮 Алгебраїчна структура тризначної логіки Клини та решітка істинності](root:sf-data/sql-null-three-valued/math-three-valued-logic.md).

## Руйнування класичних законів логіки в SQL

Перехід від двозначної логіки до 3VL має високу ціну: у мові SQL руйнуються фундаментальні закони класичної дедуктивної логіки, на які звикли спиратися інженери.

### 1. Втрата закону виключеного третього

У класичній булевій алгебрі вираз `p OR NOT p` (закон виключеного третього, латинське *tertium non datur*) є абсолютною тавтологією (від грецького *tauto* — «те саме» та *logos* — «слово, положення»): він завжди набуває значення `TRUE`.

У тризначній логіці SQL, якщо предикат `p` оцінюється як `UNKNOWN` (наприклад, `Age > 18` для рядка з `Age IS NULL`), обчислення дає:

```
p OR NOT p
= UNKNOWN OR NOT UNKNOWN    [підстановка стану UNKNOWN]
= UNKNOWN OR UNKNOWN        [бо NOT UNKNOWN = UNKNOWN]
= UNKNOWN                   [бо max(1/2, 1/2) = 1/2]
```

Це означає, що вираз `Age > 18 OR Age <= 18` не є істинним для всіх рядків таблиці. Для кожного рядка, де вік не вказано, предикат набуває значення `UNKNOWN`.

### 2. Втрата закону несуперечності

У булевій логіці вираз `p AND NOT p` завжди хибний. У логіці SQL для стану `UNKNOWN`:

```
p AND NOT p
= UNKNOWN AND NOT UNKNOWN   [підстановка стану UNKNOWN]
= UNKNOWN AND UNKNOWN       [бо NOT UNKNOWN = UNKNOWN]
= UNKNOWN                   [бо min(1/2, 1/2) = 1/2]
```

Вираз `UNKNOWN AND NOT UNKNOWN` не дорівнює `FALSE` — він повертає `UNKNOWN`. Це унеможливлює спрощення запитів оптимізатором за класичними правилами доведення від супротивного.

## Дуалізм обробки UNKNOWN: фільтрація WHERE проти обмежень CHECK

Одне з найпідступніших джерел дефектів у реляційних застосунках — це принципова відмінність у тому, як рушій бази даних реагує на стан `UNKNOWN` у блоках фільтрації (`WHERE`, `HAVING`, `JOIN ON`) та в обмеженнях цілісності схеми (`CHECK constraints`).

![Пастка предикатів WHERE проти CHECK](/root/eng/sf-data/sql-null-three-valued/img/fig4-predicate-acceptance-trap.svg)
*Асиметрія обробки UNKNOWN: фільтрація відкидає все, крім строгої істини, тоді як обмеження CHECK дозволяють вставку будь-чого, крім строгої хиби.*

### Фільтрація вибірки: правило «Приймати лише TRUE»

У виразах селекції (від латинського *selectio* — «відбір») `WHERE`, `HAVING` та `ON` реляційний рушій застосовує жорсткий критерій: кортеж потрапляє до вихідної вибірки **лише тоді, коли предикат набуває строго значення `TRUE`**.

Якщо результат обчислення предиката дорівнює `FALSE` або `UNKNOWN`, кортеж відкидається:

```sql
-- Таблиця співробітників з колонкою age, де є значення NULL
SELECT * FROM employees WHERE age > 18;
-- Рядки з age IS NULL відкидаються (UNKNOWN != TRUE)

SELECT * FROM employees WHERE NOT (age > 18);
-- Рядки з age IS NULL ЗНОВУ відкидаються! (NOT UNKNOWN = UNKNOWN != TRUE)
```

Як наслідок, якщо об'єднати результати цих двох взаємодоповнювальних запитів за допомогою `UNION ALL`, результуючий набір не міститиме співробітників із невизначеним віком: вони мовчки випадають з аналізу в обох запитах.

### Обмеження цілісності таблиці: правило «Відхиляти лише FALSE»

В обмеженнях цілісності (латинське *integritas* — «неподільність, чистота») `CHECK` діє діаметрально протилежне правило: СУБД генерує помилку порушення констрейнту **виключно тоді, коли вираз набуває строго значення `FALSE`**.

Якщо результат обчислення обмеження `CHECK` дорівнює `TRUE` або `UNKNOWN`, вставка чи оновлення рядка **дозволяється**:

```sql
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance DECIMAL(10,2),
    CHECK (balance > 0)
);

-- Ця вставка пройде успішно!
INSERT INTO accounts (id, balance) VALUES (1, NULL);
```

Коли виконується `INSERT` зі значенням `balance = NULL`, умова `CHECK (balance > 0)` оцінюється як `NULL > 0`, що дає `UNKNOWN`. Оскільки `UNKNOWN` не є `FALSE`, рушій пропускає запис у таблицю.

> 🔧 **Навіщо це.** Обмеження `CHECK (col > 0)` ніколи не замінює обмеження `NOT NULL`. Якщо колонка повинна містити лише додатні числа і не може бути порожньою, схема таблиці обов'язково має явно декларувати обидва правила: `balance DECIMAL(10,2) NOT NULL CHECK (balance > 0)`.

## Обмеження UNIQUE та зовнішні ключі FOREIGN KEY

Поведінка `NULL` у деклараціях унікальності (`UNIQUE`) та зовнішніх ключів (`FOREIGN KEY`) має критичні особливості, які безпосередньо впливають на архітектуру бази даних.

### Унікальність: чи рівні між собою маркери NULL?

За стандартом ANSI SQL унікальне обмеження `UNIQUE` стверджує, що в таблиці не може бути двох однакових дійсних значень. Оскільки для двох маркерів `NULL` операція порівняння `NULL = NULL` повертає `UNKNOWN` (тобто не доводить рівності), стандарт дозволяє зберігати **необмежену кількість рядків зі значенням `NULL`** в одній і тій самій колонці з обмеженням `UNIQUE`:

```sql
CREATE TABLE clients (
    id INT PRIMARY KEY,
    tax_number VARCHAR(20) UNIQUE
);

-- Усі три вставки завершаться успішно!
INSERT INTO clients (id, tax_number) VALUES (1, NULL);
INSERT INTO clients (id, tax_number) VALUES (2, NULL);
INSERT INTO clients (id, tax_number) VALUES (3, NULL);
```

У складених унікальних ключах (`UNIQUE (a, b)`) стандарт SQL-92 розрізняє режими:
* `UNIQUE NULLS DISTINCT` (поведінка за замовчуванням у PostgreSQL, MySQL та Oracle): кортежі `(1, NULL)` та `(1, NULL)` вважаються різними і можуть співіснувати в одній таблиці.
* `UNIQUE NULLS NOT DISTINCT` (стандарт SQL:2023, підтримується у PostgreSQL 15+): забороняє повторення однакових кортежів навіть тоді, коли окремі атрибути містять `NULL`.

### Зовнішні ключі з неповними даними (MATCH SIMPLE)

Якщо зовнішній ключ складається з кількох колонок, а дочірній рядок містить `NULL` хоча б в одній із них, виникає питання: чи повинна СУБД перевіряти посиланняльну цілісність?

Стандартний режим обробки (відомий як `MATCH SIMPLE`) діє за правилом: **якщо хоча б один стовпець зовнішнього ключа містить `NULL`, уся перевірка цілісності ігнорується**. Це дозволяє вставити в дочірню таблицю рядок, де перша частина ключа посилається на неіснуючий запис батьківської таблиці, якщо друга частина ключа дорівнює `NULL`.

Щоб уникнути таких аномалій, стандарт надає режим `MATCH FULL`, який вимагає, щоб усі стовпці складеного зовнішнього ключа були або повністю заповнені дійсними значеннями, або всі одночасно містили `NULL`.

## Порівняння з NULL: оператори IS NULL, IS DISTINCT FROM та функції підстановки

Будь-яка спроба порівняти значення атрибута з `NULL` за допомогою звичайних реляційних операторів порівняння (`=`, `<>`, `<`, `>`, `<=`, `>=`) повертає `UNKNOWN`:

```sql
-- ПОМИЛКА: цей запит ЗАВЖДИ повертає порожній набір рядків!
SELECT * FROM users WHERE status = NULL;
```

Вираз `status = NULL` для кожного рядка обчислюється як `UNKNOWN`. Оскільки `WHERE` вимагає `TRUE`, жоден користувач не буде знайдений.

Для перевірки наявності маркера відсутності мова SQL надає спеціальні унарні предикати:
* `IS NULL` — повертає `TRUE`, якщо значення відсутнє, і `FALSE`, якщо присутнє.
* `IS NOT NULL` — повертає `TRUE`, якщо значення присутнє, і `FALSE`, якщо відсутнє.

Ці оператори є строго двозначними (2VL): вони ніколи не повертають `UNKNOWN`.

### Безпечне порівняння: IS DISTINCT FROM

У багатьох алгоритмах (наприклад, під час виявлення змінених полів при аудиті чи реплікації даних) розробнику потрібно дізнатися, чи змінилося значення колонки. Якщо одне зі значень дорівнює `NULL`, а інше — числу `42`, вони повинні вважатися різними; якщо обидва значення `NULL`, вони повинні вважатися однаковими.

Звичайне порівняння `old.val <> new.val` не працює, бо якщо хоча б одне поле `NULL`, вираз поверне `UNKNOWN`. Стандарт SQL:1999 ввів спеціальний предикат `IS DISTINCT FROM` (та його протилежність `IS NOT DISTINCT FROM`):

```sql
-- Коректне порівняння з урахуванням NULL:
SELECT * FROM audit_log 
WHERE old_value IS DISTINCT FROM new_value;
```

Таблиця поведінки `IS DISTINCT FROM`:

| `A` | `B` | `A = B` | `A IS DISTINCT FROM B` |
|---|---|---|---|
| `10` | `10` | `TRUE` | `FALSE` |
| `10` | `20` | `FALSE` | `TRUE` |
| `10` | `NULL` | `UNKNOWN` | `TRUE` |
| `NULL` | `NULL` | `UNKNOWN` | `FALSE` |

Оператор `IS DISTINCT FROM` розглядає два маркери `NULL` як невідмінні один від одного, повертаючи строгий булевий результат `TRUE` або `FALSE`.

### Функції підстановки: COALESCE та NULLIF

Для зручної роботи з невизначеними даними стандарт SQL надає дві спеціалізовані функції:

1. **`COALESCE(arg1, arg2, ..., argN)`:** повертає перший не-NULL аргумент у списку зліва направо за принципом лінивого обчислення (short-circuit evaluation). Якщо всі аргументи дорівнюють `NULL`, повертає `NULL`:
   ```sql
   -- Якщо телефон не вказано, використовуємо email; якщо і email порожній — підставляємо текст
   SELECT COALESCE(phone, email, 'Контакти відсутні') FROM users;
   ```
2. **`NULLIF(a, b)`:** повертає `NULL`, якщо `a = b`, і значення `a` у протилежному випадку. Ця функція незамінна для запобігання діленню на нуль у фінансових запитах:
   ```sql
   -- Захист від помилки division by zero: якщо total_items = 0, NULLIF поверне NULL,
   -- а ділення на NULL безпечно поверне NULL замість аварійного збою запиту
   SELECT total_cost / NULLIF(total_items, 0) FROM sales_reports;
   ```

## Підступні пастки 3VL у запитах SQL

Нерозуміння тризначної логіки породжує приховані аномалії, які надзвичайно складно виявити на етапі тестування.

### 1. Катастрофа виразу NOT IN з підзапитом

Розглянемо класичний запит пошуку клієнтів, які ще не зробили жодного замовлення:

```sql
SELECT customer_id FROM customers 
WHERE customer_id NOT IN (SELECT customer_id FROM orders);
```

Якщо в таблиці `orders` є хоча б один рядок, де `customer_id` містить `NULL` (наприклад, анонімне замовлення), **весь запит поверне порожній результат, навіть якщо в системі є мільйони клієнтів без замовлень**.

![Пастка NOT IN з NULL](/root/eng/sf-data/sql-null-three-valued/img/fig5-not-in-null-trap.svg)
*Покрокова деструкція кон'юнкції: чому один NULL у списку аргументів NOT IN перетворює весь результат на порожню множину.*

За стандартом SQL вираз `x NOT IN (a, b, c)` еквівалентний кон'юнкції нерівностей:

```
x <> a AND x <> b AND x <> c
```

Якщо один з елементів списку є `NULL`, вираз розгортається в:

```
x <> 10 AND x <> 20 AND x <> NULL
= TRUE AND TRUE AND UNKNOWN          [бо порівняння з NULL дає UNKNOWN]
= UNKNOWN                            [бо min(1, 1, 1/2) = 1/2]
```

Оскільки `UNKNOWN` відкидається блоком `WHERE`, запит не повертає жодного рядка.

**Безпечне рішення:** використання оператора `NOT EXISTS`, який стійкий до наявності `NULL`:

```sql
SELECT c.customer_id FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);
```

### 2. Пастка лівого з'єднання (LEFT JOIN) та фільтрації WHERE

Початківці часто припускаються помилки, переносячи умови фільтрації правої таблиці з блоку `ON` у блок `WHERE` під час лівого зовнішнього з'єднання (`LEFT JOIN`):

```sql
-- ПОМИЛКА: цей запит неявно перетворюється на INNER JOIN!
SELECT c.name, o.order_date 
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'COMPLETED';
```

Коли для деякого клієнта замовлення відсутні, оператор `LEFT JOIN` генерує рядок, де всі поля правої таблиці `orders` заповнені синтезованими маркерами `NULL` (`o.status IS NULL`).

Потім реляційний рушій застосовує фільтр `WHERE o.status = 'COMPLETED'`. Оскільки `NULL = 'COMPLETED'` обчислюється як `UNKNOWN`, цей рядок відкидається. У результаті всі клієнти без замовлень зникають із вибірки, що повністю нівелює сенс використання `LEFT JOIN`.

**Коректний варіант:** умова повинна залишатися всередині зв'язки `ON`:

```sql
SELECT c.name, o.order_date 
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id AND o.status = 'COMPLETED';
```

### 3. Агрегатні функції та порожні множини

Агрегатні функції мови SQL (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`) обробляють `NULL` за двома різними правилами залежно від того, як вони викликаються:

1. **Ігнорування `NULL` у колонках:** Усі агрегатні функції над конкретною колонкою (наприклад, `AVG(salary)` або `SUM(bonus)`) повністю ігнорують рядки, де значення атрибута дорівнює `NULL`. Якщо в таблиці з 4 співробітників зарплати становлять `1000`, `2000`, `NULL`, `NULL`, функція `AVG(salary)` обчислить `(1000 + 2000) / 2 = 1500`, а не `3000 / 4 = 750`.
2. **Агрегація над порожньою вибіркою:** Якщо запит не знаходить жодного рядка, що задовольняє умові `WHERE`:
   * `COUNT(*)` та `COUNT(col)` завжди повертають число `0`.
   * `SUM(col)`, `AVG(col)`, `MIN(col)`, `MAX(col)` повертають `NULL`!

Ця асиметрія часто ламає фінансовий код у прикладному шарі:

```sql
-- Якщо замовлень не було, запит поверне NULL, а не 0.00!
SELECT SUM(total_amount) FROM orders WHERE user_id = 99999;
```

Якщо прикладний код на мовах C, C++, Java чи Go очікує отримати примітивне число з плаваючою крапкою, спроба прочитати `NULL` призведе до падіння програми або некоректного приведення типів.

### 4. Групування, сортування та віконні функції

Попри те, що предикат `NULL = NULL` повертає `UNKNOWN`, оператори групування та множинні операції SQL діють за правилами ідентичності:
* `GROUP BY`: усі рядки, що містять `NULL` у групувальному стовпці, об'єднуються в **одну спільну групу**.
* `DISTINCT`: множина однакових значень `NULL` згортається в один екземпляр.
* `UNION`, `INTERSECT`, `EXCEPT`: розглядають маркери `NULL` як еквівалентні між собою елементи множин.
* `ORDER BY`: стандарт SQL дозволяє рушіям самостійно обирати, де розташовувати невизначені значення під час сортування. У PostgreSQL значення `NULL` за замовчуванням вважаються більшими за будь-які інші значення (розташовуються в кінці при `ASC`), тоді як у MySQL вони вважаються найменшими (розташовуються на початку). Для уникнення неоднозначності стандарт вимагає явного використання модифікаторів `NULLS FIRST` або `NULLS LAST`.

У віконних функціях (`OVER (PARTITION BY ... ORDER BY ...)`) стандарт SQL:2016 ввів спеціальні директиви `IGNORE NULLS` та `RESPECT NULLS` для навігаційних функцій `LEAD`, `LAG`, `FIRST_VALUE`, `LAST_VALUE` та `NTH_VALUE`. Директива `IGNORE NULLS` змушує віконну функцію пропускати невизначені значення та повертати найближче попереднє чи наступне дійсне число.

## Вплив на оптимізатор запитів та статистику

Оптимізатор запитів реляційної СУБД (Query Planner / Cost Optimizer) використовує внутрішню статистику для оцінки кардинальності (кількості очікуваних рядків на кожному кроці плану).

У системному каталозі (наприклад, у таблиці `pg_statistic` СУБД PostgreSQL) для кожної колонки обов'язково зберігається поле `null_frac` — частка значень `NULL` серед усіх рядків відношення (дійсне число від `0.0` до `1.0`).

Якщо оптимізатор зустрічає предикат `WHERE col = 42`, він розраховує селективність виразу, автоматично виключаючи частку `null_frac` із простору пошуку:

```
selectivity = (1 - null_frac) / distinct_values
```

Якщо колонка на 95% заповнена значеннями `NULL` (`null_frac = 0.95`), а розробник шукає `WHERE col IS NOT NULL`, оптимізатор вибере індексне сканування (Index Scan) замість послідовного читання таблиці (Seq Scan), оскільки індекс знайде 5% рядків майже миттєво.

### Часткові індекси (Partial Indexes)

Для розріджених колонок з великою кількістю `NULL` найбільш ефективним рішенням є створення **часткового індексу**:

```sql
-- Індекс будується виключно для не-NULL значень
CREATE INDEX idx_orders_unprocessed 
ON orders (processed_at) 
WHERE processed_at IS NULL;
```

Такий індекс займає у сотні разів менше місця на диску та в оперативній пам'яті (Buffer Pool), оскільки містить лише записи з реальними маркерами відсутності, повністю виключаючи мільйони вже оброблених рядків.

## Фізичне розміщення NULL у сторінках пам'яті та диска

Як реляційні СУБД фізично зберігають маркер `NULL` всередині сторінок на диску? Зберігання окремого сигнального байта чи текстового рядка для кожної колонки призвело б до неприпустимих втрат дискового простору та пропускної здатності шини пам'яті.

Сучасні промислові СУБД (PostgreSQL, MySQL InnoDB, Oracle, SQLite) використовують компактні **бітові карти наявності** (Null Bitmap, від англійського *bit* — binary digit та *map* — карта) у заголовку кожного рядка.

![Фізична структура кортежу з Null Bitmap](/root/eng/sf-data/sql-null-three-valued/img/fig3-tuple-null-bitmap-layout.svg)
*Анатомія заголовка кортежу PostgreSQL (HeapTupleHeaderData): бітова карта t_bits вказує на наявність даних, дозволяючи пропускати байти для колонок зі значенням NULL.*

### Анатомія рядка у PostgreSQL (HeapTupleHeaderData)

У PostgreSQL кожен рядок таблиці (heap tuple) має фіксований заголовок розміром 23 байти (`HeapTupleHeaderData`), який містить транзакційні ідентифікатори `t_xmin`, `t_xmax`, поля блокувань та службову бітову маску `t_infomask`.

Якщо хоча б один атрибут у кортежі має значення `NULL`, у полі `t_infomask` виставляється бітовий прапорець `HEAP_HASNULL` (`0x0001`). За наявності цього прапорця одразу за заголовком кортежу розміщується масив байтів `t_bits[]` — бітова карта, де кожній колонці схеми таблиці виділено рівно 1 біт:
* Біт `1` означає, що значення атрибута присутнє (`NOT NULL`).
* Біт `0` означає, що значення атрибута відсутнє (`IS NULL`).

Якщо таблиця містить 16 колонок, бітова карта займає рівно 2 байти `(16 / 8)`.

Коли рушій читає кортеж, він сканує бітову карту: для кожної колонки з бітом `0` розмір даних у тілі кортежу (payload) дорівнює **рівно 0 байтів**. Зсув до наступної дійсної колонки не збільшується. Це забезпечує колосальну економію дискового простору для розріджених таблиць (де сотні необов'язкових полів залишаються порожніми).

Детальний приклад реалізації низькорівневого сховища кортежів із бітовою картою та векторного обчислювача мовами C та C++ наведено у вставці [⚙️ Реалізація представлення бітової карти NULL та паралельного 3VL-обчислювача](root:sf-data/sql-null-three-valued/proj-null-bitmap-engine.md).

### Індексування значень NULL у B-Tree

Різні СУБД принципово по-різному будують індекси B-Tree над колонками, що допускають `NULL`:
* **PostgreSQL:** B-Tree індекси завжди включають значення `NULL` (вони розміщуються на правому або лівому краю дерева). Тому запит `SELECT * FROM users WHERE email IS NULL` може ефективно використовувати звичайний індекс.
* **Oracle:** Класичні B-Tree індекси Oracle **не зберігають кортежі**, у яких усі індексовані колонки мають значення `NULL`. Якщо виконати пошук `WHERE col IS NULL`, Oracle буде змушений виконати повне сканування таблиці (Full Table Scan), якщо не створити спеціальний складений або бітмап-індекс.
* **MySQL (InnoDB):** Зберігає значення `NULL` на самому початку B-Tree індексу як найменші можливі елементи.

## Векторизація та SIMD-обчислення тризначної логіки

В аналітичних СУБД (OLAP, таких як ClickHouse, DuckDB чи векторизований рушій PostgreSQL) обробка запитів здійснюється не порядково, а блоками (векторами) з тисяч значень.

У векторизованому форматі колонка з підтримкою `NULL` представляється двома паралельними плоскими масивами в оперативній пам'яті:
1. **Масив значень (`data array`):** неперервний буфер пам'яті з примітивними значеннями (`int32_t`, `double`).
2. **Масив маски відсутності (`null mask array`):** байтовий масив, де кожен байт дорівнює `1`, якщо комірка `NULL`, і `0`, якщо присутня.

Це дозволяє виконувати операції фільтрації 3VL за допомогою векторних SIMD-інструкцій (AVX-512 / ARM Neon) без жодного розгалуження процесора:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

/* Векторна оцінка предиката (col > 100) над пакетом із n значень */
void filter_vector_3vl(const int32_t* data, const uint8_t* null_mask, 
                        uint8_t* out_result_mask, uint8_t* out_null_mask, int n) {
    for (int i = 0; i < n; ++i) {
        if (null_mask[i]) {
            out_null_mask[i] = 1;   /* UNKNOWN */
            out_result_mask[i] = 0;
        } else {
            out_null_mask[i] = 0;   /* Визначено */
            out_result_mask[i] = (data[i] > 100) ? 1 : 0;
        }
    }
}
```
```cpp
#include <vector>
#include <cstdint>
#include <span>

struct ColumnVector {
    std::vector<int32_t> data;
    std::vector<uint8_t> null_mask; /* 1 = IS NULL, 0 = VALID */
};

/* Ідіоматична C++ векторизована фільтрація 3VL */
void filter_vector_3vl_cpp(std::span<const int32_t> data, 
                           std::span<const uint8_t> null_mask,
                           std::span<uint8_t> out_val,
                           std::span<uint8_t> out_is_null) noexcept {
    const size_t n = data.size();
    for (size_t i = 0; i < n; ++i) {
        if (null_mask[i] != 0) {
            out_is_null[i] = 1; /* UNKNOWN */
            out_val[i] = 0;
        } else {
            out_is_null[i] = 0; /* Чітке булеве значення */
            out_val[i] = (data[i] > 100) ? 1 : 0;
        }
    }
}
```

## Відображення на мови програмування та типізація

Головна практична проблема при інтеграції реляційних баз даних із мовами високого рівня — це невідповідність між об'єктною та реляційною моделями (Object-Relational Impedance Mismatch, від латинського *impedire* — «перешкоджати»).

Примітивні типи мов C та C++ (`int`, `double`, `bool`) не мають вбудованого третього стану для представлення `NULL`. Якщо драйвер бази даних намагається записати `NULL` у звичайну змінну `int salary`, програма або аварійно завершується, або ініціалізує змінну випадковим значенням.

### Сучасний підхід: std::optional та алгебраїчні типи

У сучасному C++ (починаючи зі стандарту C++17) реляційні поля з підтримкою `NULL` відображаються на шаблонний клас `std::optional<T>`:

:::tabs
```c
#include <stdio.h>
#include <stdbool.h>

/* C-стиль представлення nullable поля через структуру з прапорцем */
typedef struct {
    int value;
    bool has_value;
} NullableInt;

NullableInt make_null(void) {
    NullableInt res = { 0, false };
    return res;
}

NullableInt make_int(int val) {
    NullableInt res = { val, true };
    return res;
}
```
```cpp
#include <iostream>
#include <optional>
#include <string>

struct EmployeeRecord {
    int id;
    std::string name;
    std::optional<double> salary;     /* Відповідає NULL у колонці salary */
    std::optional<std::string> phone;  /* Відповідає NULL у колонці phone */
};

void print_employee(const EmployeeRecord& emp) {
    std::cout << "Співробітник: " << emp.name;
    if (emp.salary.has_value()) {
        std::cout << ", Зарплата: " << *emp.salary << " грн\n";
    } else {
        std::cout << ", Зарплата: [НЕ ВКАЗАНО]\n";
    }
}
```
:::

Особливу небезпеку становить тип `std::optional<bool>` у C++. Він має три можливі стани:
1. `std::optional<bool>(true)` — істина (`TRUE`).
2. `std::optional<bool>(false)` — хиба (`FALSE`).
3. `std::nullopt` — невизначеність (`UNKNOWN`).

Якщо розробник помилково напише `if (opt_flag)` замість перевірки `if (opt_flag.value_or(false))`, умова виконається і для `true`, і для `false`, оскільки об'єкт `std::optional` повертає `true` за будь-якої наявності значення.

## Архітектурна дискусія: чи потрібен NULL?

Введення `NULL` та тризначної логіки залишається найбільш суперечливим рішенням за всю історію реляційних баз даних.

Один із головних теоретиків реляційної моделі Крістофер Дейт (Christopher J. Date) разом із Г'ю Дарвеном (Hugh Darwen) у праці «The Third Manifesto» виступили з різкою критикою концепції Кодда. Вони довели, що 3VL руйнує логічну замкненість мови, провокує приховані дефекти в бізнес-логіці та змушує інженерів пам'ятати сотні спеціальних правил для обробки винятків.

Дейт і Дарвен запропонували альтернативне проєктування баз даних без жодного використання `NULL`:
1. **Декомпозиція схем до 6NF (Шоста нормальна форма):** усі необов'язкові атрибути виносяться в окремі зв'язані відношення. Якщо у користувача немає телефонного номера, замість запису `NULL` у таблиці `Users` запис просто відсутній у таблиці `UserPhones`. Запит із `NATURAL JOIN` повертає точні кортежі в межах класичної двозначної булевої логіки.
2. **Типізовані доменні значення:** використання чітких предметних статусів замість універсальної невизначеності.

Попри теоретичні застереження, мова SQL обрала шлях прагматичного компромісу: `NULL` та 3VL стали промисловим стандартом. Розуміння механізму тризначної логіки, правил роботи решітки Клини, поведінки оператора `NOT IN` та фізичної структури бітових карт є обов'язковою кваліфікаційною вимогою для побудови надійних, масштабованих та математично коректних реляційних систем обробки даних.
