# 📋 Специфікація та команди керування курсорами в SQL

Курсори в реляційних базах даних регулюються стандартом ISO/IEC 9075 (SQL:1992, SQL:1999, SQL:2016) та мають розширені специфікації у промислових рушіях СУБД (PostgreSQL, Oracle Database, Microsoft SQL Server, MySQL). 

У реляційній моделі будь-який запит повертає математичну множину кортежів. Проте процедурні середовища виконання та мережеві протоколи вимагають покрокової або блокової передачі даних. Курсор виступає стандартизованим контрактом, що зв'язує декларативне дерево плану запиту з імперативним інтерфейсом зчитування.

Нижче наведено повний синтаксичний та поведінковий довідник інструкцій оголошення, позиціонування, зчитування, модифікації даних та обробки помилок за допомогою курсорів.

## 1. Синтаксис та життєвий цикл курсора

Управління курсором складається з чіткої послідовності фаз: створення опису, ініціалізація серверного стану, ітеративне переміщення покажчика та вивільнення виділених структур пам'яті.

```sql
-- Загальна структура оголошення курсора в стандарті SQL
DECLARE cursor_name [SCROLL | NO SCROLL] [INSENSITIVE] [WITH HOLD | WITHOUT HOLD]
CURSOR FOR query_expression
[FOR { READ ONLY | UPDATE [OF column_name_list] }];
```

| Оператор SQL | Фізична дія сервера | Обов'язковість / Контекст |
|---|---|---|
| `DECLARE cursor_name ... CURSOR FOR query` | Реєструє назву курсора, виконує синтаксичний аналіз та планування запиту, виділяє структуру порталу. | Обов'язковий перший крок; у PostgreSQL створює активний портал у транзакційному контексті. |
| `OPEN cursor_name` | Захоплює знімок транзакційного стану (Snapshot), ініціалізує дерево операторів і позиціонує покажчик перед першим рядком. | Використовується в процедурних мовах (PL/pgSQL, PL/SQL, T-SQL). У SQL-сесії PostgreSQL `DECLARE` відкриває курсор негайно. |
| `FETCH [direction] [count] FROM cursor_name [INTO target_variables]` | Викликає фізичні вузли плану для отримання кортежів, зсуває позицію покажчика і передає дані клієнту або у змінні. | Основна операція конвеєра зчитування даних. |
| `MOVE [direction] [count] FROM cursor_name` | Зсуває позицію покажчика курсора на задану кількість рядків без передачі даних по мережі (еквівалент `FETCH` без повернення кортежів). | Доступно в PostgreSQL, Oracle; суттєво економить пропускну здатність мережі під час пропуску сторінок. |
| `UPDATE table_name SET col = val WHERE CURRENT OF cursor_name` | Модифікує рядок у базовій таблиці за фізичним дисковим ідентифікатором поточного кортежу курсора. | Вимагає оголошення курсора з модифікатором `FOR UPDATE`. |
| `DELETE FROM table_name WHERE CURRENT OF cursor_name` | Фізично або логічно вилучає поточний рядок таблиці за збереженим покажчиком позиції. | Вимагає оголошення курсора з модифікатором `FOR UPDATE`. |
| `CLOSE cursor_name` | Закриває серверний портал, скидає виділений контекст пам'яті (`MemoryContext`) та видаляє тимчасові файли (`tuplestore`). | Обов'язковий для запобігання витоку серверних дескрипторів. |

## 2. Напрямки позиціонування та синтаксис інструкції FETCH

Інструкція `FETCH` підтримує гнучке просторове переміщення покажчика. Напрямок визначається ключовим словом `direction`:

```sql
FETCH [ NEXT | PRIOR | FIRST | LAST | ABSOLUTE count | RELATIVE count | FORWARD [count] | BACKWARD [count] | ALL ]
FROM cursor_name;
```

Семантика кожного варіанта переміщення:

- `NEXT` (за замовчуванням): переміщує покажчик на один рядок уперед від поточної позиції та зчитує його. Підтримується в усіх типах курсорів (`NO SCROLL` та `SCROLL`);
- `PRIOR`: переміщує покажчик на один рядок назад до початку набору і повертає його. Вимагає режиму `SCROLL`;
- `FIRST`: здійснює стрибок на перший рядок результуючого набору і повертає його значення. Вимагає режиму `SCROLL`;
- `LAST`: переходить на останній рядок вибірки. Якщо план запиту не був попередньо матеріалізований, сервер змушений прочитати всі рядки до кінця;
- `ABSOLUTE count`: виконує абсолютне позиціонування. Якщо `count > 0`, покажчик стає на рядок з номером `count` від початку (нумерація з 1). Якщо `count < 0`, відлік ведеться з кінця вибірки (`-1` — останній рядок). Якщо `count = 0`, покажчик стає у фіктивну позицію перед першим рядком без повернення даних;
- `RELATIVE count`: виконує відносне переміщення на `count` рядків від поточної позиції вперед (`count > 0`) або назад (`count < 0`). Значення `RELATIVE 0` повторно зчитує поточний рядок;
- `FORWARD [count]` або `BACKWARD [count]`: зчитує пакет із `count` послідовних рядків у прямому або зворотному напрямку відповідно;
- `ALL`: зчитує абсолютно всі рядки, що залишилися від поточної позиції до кінця результуючого набору.

Під час виконання команди `MOVE` сервер застосовує точно такі самі правила зміни внутрішнього зміщення в сховищі кортежів або дереві ітераторів, але повністю пропускає серіалізацію колонок у двійкові мережеві структури, що робить операцію на порядок швидшою за `FETCH`.

## 3. Атрибути чутливості, матеріалізації та транзакційних меж

Поведінка курсора під час виконання та обсяг споживаних ресурсів визначаються трьома фундаментальними парами атрибутів:

### SCROLL проти NO SCROLL
- `NO SCROLL`: однонаправлений рух тільки вперед. Сервер підтримує конвеєрний режим: прочитані кортежі негайно видаляються з пам'яті. Це єдиний режим із фіксованим споживанням пам'яті `O(1)`;
- `SCROLL`: двонапрямлений рух. Сервер змушений зберігати історію всіх видобутих рядків у двонапрямленому сховищі кортежів (`tuplestore`). При перевищенні ліміту пам'яті `work_mem` дані вивантажуються у тимчасові дискові файли, що створює дискове навантаження.

### WITHOUT HOLD проти WITH HOLD
- `WITHOUT HOLD` (за замовчуванням): курсор жорстко прив'язаний до поточної транзакції. При виклику `COMMIT` або `ROLLBACK` портал автоматично знищується;
- `WITH HOLD`: курсор залишається відкритим і придатним для читання після завершення транзакції через `COMMIT`. У момент фіксації транзакції сервер примусово вичитує всі залишки результату у тимчасовий дисковий файл і знімає всі блокування таблиць, дозволяючи новоствореним транзакціям читати цей фіксований знімок.

### INSENSITIVE проти SENSITIVE
- `INSENSITIVE`: курсор ізольований від будь-яких подальших змін у базових таблицях. Працює над фіксованим знімком стану на момент відкриття;
- `SENSITIVE`: курсор реагує на паралельні зміни даних іншими транзакціями. Під час кожного кроку сервер здійснює повторну перевірку наявності та актуальності фізичного рядка.

## 4. Змінні стану курсора в процедурних середовищах

У процедурних діалектах SQL (PL/pgSQL, PL/SQL, T-SQL) стан відкритого курсора відстежується через вбудовані атрибути:

```
+---------------------------------------------------------------------------------------------------+
| Атрибут / Змінна   | Рушій           | Тип       | Семантичне значення та логіка                  |
+--------------------+-----------------+-----------+------------------------------------------------+
| %FOUND             | PL/SQL, PL/pgSQL| BOOLEAN   | TRUE, якщо останній FETCH повернув кортеж      |
| %NOTFOUND          | PL/SQL, PL/pgSQL| BOOLEAN   | TRUE, якщо досягнуто кінця вибірки (EOF)       |
| %ISOPEN            | PL/SQL, PL/pgSQL| BOOLEAN   | TRUE, якщо портал курсора відкрито в пам'яті  |
| %ROWCOUNT          | PL/SQL, PL/pgSQL| INTEGER   | Загальна кількість рядків, витягнутих досі     |
| @@FETCH_STATUS     | T-SQL           | INTEGER   | 0 = успіх, -1 = вихід за межі, -2 = рядок зник |
| SQLSTATE '02000'   | Стандарт ANSI   | CHAR(5)   | Стандартний код успішного завершення (No Data) |
+---------------------------------------------------------------------------------------------------+
```

Типовий шаблон ітеративної обробки в процедурному блоці PL/pgSQL:

```sql
DO $$
DECLARE
    cur_trans CURSOR FOR SELECT id, amount FROM transactions WHERE status = 'PENDING';
    rec_trans RECORD;
BEGIN
    OPEN cur_trans;
    LOOP
        FETCH NEXT FROM cur_trans INTO rec_trans;
        EXIT WHEN NOT FOUND; -- Перевірка стану %NOTFOUND
        
        -- Логіка обробки окремого рядка
        PERFORM process_single_transaction(rec_trans.id, rec_trans.amount);
    END LOOP;
    CLOSE cur_trans;
END $$;
```

## 5. Порівняльна специфікація підтримки в СУБД

Різні рушії реляційних баз даних реалізують специфікацію курсорів із суттєвими архітектурними відмінностями:

### PostgreSQL
- Курсори реалізовано через внутрішню підсистему порталів (`Portal`). Усі активні курсори сеансу доступні для моніторингу через системне представлення `pg_cursors`;
- Підтримуються параметри `SCROLL`, `NO SCROLL`, `WITH HOLD`, `BINARY` (вивантаження у двійковому форматі без перетворення на текст);
- Реалізовано повну підтримку позиційного оновлення `WHERE CURRENT OF cursor_name`;
- Оптимізатор враховує наявність курсора через конфігураційний параметр `cursor_tuple_fraction` (за замовчуванням `0.1`), віддаючи перевагу планам із швидким поверненням перших рядків (Fast Startup Cost), таким як індексне сканування, перед повільними планами з повною хеш-агрегацією.

### Oracle Database
- Розрізняють явні курсори (`Explicit Cursors`, керовані розробником) та неявні курсори (`Implicit Cursors`, створювані для кожного оператора SQL);
- Підтримується масова вибірка `BULK COLLECT INTO` з параметром `LIMIT`, що дозволяє зчитувати пачки рядків безпосередньо в колекції PL/SQL;
- Керування виділеною пам'яттю здійснюється через параметри `OPEN_CURSORS` у системній глобальній області (SGA/PGA), а активні дескриптори відстежуються через представлення `V$OPEN_CURSOR`.

### Microsoft SQL Server (T-SQL)
- Підтримує чотири типи фізичних курсорів: `STATIC` (матеріалізація у базі `tempdb`), `KEYSET` (фіксація списку ключів), `DYNAMIC` (чутливий до всіх змін) та `FAST_FORWARD` (високооптимізований однонаправлений потоковий курсор);
- Керування позиціонуванням контролюється глобальною системною функцією `@@FETCH_STATUS`.

### MySQL (InnoDB)
- Курсори підтримуються виключно всередині збережених процедур (Stored Procedures) та функцій;
- Курсори є строго однонаправленими (`READ ONLY`, `NO SCROLL`);
- MySQL не підтримує синтаксис `WHERE CURRENT OF` та вимагає явної обробки завершення вибірки через обробник помилок `DECLARE CONTINUE HANDLER FOR NOT FOUND`.

## 6. Коди помилок SQLSTATE під час роботи з курсорами

Під час порушення протоколу взаємодії з курсором СУБД генерує стандартизовані коди помилок згідно зі стандартом SQL:

| Код SQLSTATE | Назва класу помилки | Причина виникнення та діагностика |
|---|---|---|
| `24000` | `invalid_cursor_state` | Спроба виконати `FETCH`, `CLOSE` або позиційний `UPDATE` над закритим або неініціалізованим курсором. |
| `02000` | `no_data` | Нормальний стан завершення: інструкція `FETCH` досягла кінця результуючого набору даних. |
| `34000` | `invalid_cursor_name` | Звернення до курсора за іменем, якого не існує у поточному просторі імен сеансу. |
| `55000` | `object_in_use` | Спроба виконати DDL-команду (`DROP TABLE`, `ALTER TABLE`) над таблицею, яка заблокована відкритим курсором. |
| `25001` | `active_sql_transaction` | Спроба оголосити курсор поза межами активного транзакційного блоку у рушіях, де транзакція є обов'язковою. |
| `40001` | `serialization_failure` | Конфлікт серіалізації при спробі модифікації рядка курсором на рівні ізоляції `SERIALIZABLE`. |
| `40P01` | `deadlock_detected` | Взаємне блокування транзакцій під час виконання позиційного оновлення `FOR UPDATE`. |
