# 📜 Еволюція курсорів у базах даних: від навігаційного CODASYL до SQL-92 та ODBC

У 1960-х роках управління корпоративними даними здійснювалося виключно через навігаційні моделі — ієрархічну (IBM IMS) та мережеву, стандартизовану комісією CODASYL (Conference on Data Systems Languages). У цих системах прикладний програміст мислив категоріями фізичних записів та покажчиків: програма мовою COBOL чи PL/I відкривала файл або область (`AREA`), знаходила початковий запис-власник (`FIND FIRST Customer`) і у циклі пересувала покажчик на наступний запис-член (`FIND NEXT Order WITHIN Customer-Orders`), вичитуючи поля в оперативну пам'ять командою `GET`. Обробка даних була строго послідовною, імперативною і працювала за принципом «один запис за один крок» (record-at-a-time).

Коли у 1970 році Едгар Кодд опублікував математичний маніфест реляційної моделі, він проголосив перехід від навігаційного мислення до декларативних множинних операцій (set-at-a-time). Реляційний запит повертав не покажчик на запис, а цілісне відношення — математичну множину кортежів. Проте інженери Дослідницького центру IBM у Сан-Хосе (San Jose Research Laboratory), створюючи першу реляційну СУБД System R у 1974–1979 роках під керівництвом Дональда Чемберліна (Donald Chamberlin) та Рея Бойса (Ray Boyce), зіткнулися з фундаментальним інженерним розривом: хост-мови програмування (Host Languages) не вміли працювати з математичними множинами довільного розміру.

Змінна у мові C, Фортран чи COBOL може містити лише одне скалярне значення чи фіксовану структуру даних. Якщо SQL-запит генерує мільйон рядків, хост-програма не має синтаксичної конструкції для одночасного збереження всього відношення без ризику переповнення оперативної пам'яті. Виникла потреба в архітектурному адаптері, який перетворював би декларативну реляційну множину на послідовний потік кортежів, сумісний з імперативними циклами `while` та `for`. Цим адаптером став курсор (cursor).

## Народження вбудованого SQL (Embedded SQL) та System R

У системі System R інженери IBM розробили концепцію вбудованого SQL (Embedded SQL). Запити записувалися безпосередньо в тіло програми на мові C або PL/I з префіксом `EXEC SQL`. Для вибірки множини рядків було введено чотири базові оператори:
1. `DECLARE CURSOR` — зв'язував ім'я курсора з декларативним виразом `SELECT`;
2. `OPEN` — ініціював виконання запиту планувальником СУБД і створював активний контекст виконання (знімок даних);
3. `FETCH` — зчитував поточний кортеж у змінні хост-програми (`INTO :var1, :var2`) і зсував внутрішній покажчик на одну позицію вперед;
4. `CLOSE` — звільняв ресурси сервера та закривав контекст вибірки.

Такий підхід дозволив зберегти математичну виразність SQL під час оптимізації плану запиту на сервері, надавши програмісту звичний інтерфейс послідовної ітерації. Проте перші реалізації курсорів у System R та ранніх версіях Oracle були строго однонаправленими (forward-only): програма могла рухатися лише від початку вибірки до її кінця.

## Стандартизація ANSI/ISO SQL-86 та розширення SQL-92

У першому міжнародному стандарті SQL (ANSI X3.135-1986 / ISO 9075:1987) курсори було офіційно закріплено як єдиний стандартизований спосіб взаємодії процедурного коду з реляційними результатами. Однак розвиток графічних інтерфейсів користувача (GUI) наприкінці 1980-х років вимагав нової функціональності: табличні віджети на екрані вимагали прокручування списку записів як уперед, так і назад, а також стрибків на довільний номер рядка.

Стандарт SQL-92 здійснив революцію в семантиці курсорів, запровадивши концепцію **прокручуваних курсорів** (`SCROLL CURSOR`). Оператор `FETCH` отримав багату просторову навігацію:
- `FETCH PRIOR` — крок назад;
- `FETCH FIRST` та `FETCH LAST` — перехід на початок чи в кінець результуючого набору;
- `FETCH ABSOLUTE n` — прямий перехід на рядок із номером `n`;
- `FETCH RELATIVE n` — відносний зсув на `n` позицій від поточного місця.

Окрім навігації, SQL-92 стандартизував модифікацію даних за місцем розташування покажчика: вираз `WHERE CURRENT OF cursor_name` в операторах `UPDATE` та `DELETE` дозволив програмам модифікувати саме той фізичний рядок, на якому зараз зупинився курсор, без необхідності повторного сканування індексів за первинним ключем.

## Епоха клієнт-серверної архітектури: ODBC, SQL/CLI та мережевий протокол

На початку 1990-х років монолітні мейнфрейми поступилися місцем клієнт-серверній архітектурі, де застосунок виконувався на персональному комп'ютері, а СУБД — на віддаленому сервері. Вбудований SQL вимагав окремого прекомпілятора для кожної мови програмування, що було вкрай незручно для динамічних середовищ розробки.

У 1992 році консорціум SQL Access Group за участі Microsoft, Digital Equipment Corporation та IBM створив специфікацію Call Level Interface (SQL/CLI), яка лягла в основу стандарту Microsoft ODBC (Open Database Connectivity) та згодом JDBC (Java Database Connectivity). У цій парадигмі курсори перестали бути виключно серверними структурами. З'явився чіткий поділ:
- **Серверні курсори (Server-side cursors):** активний стан, блокування та позиція зберігаються в процесі СУБД, а клієнт витягує дані порціями через мережеві запити;
- **Клієнтські курсори (Client-side cursors):** клієнтська бібліотека повністю завантажує весь результуючий набір через сокет у локальний буфер оперативної пам'яті комп'ютера і забезпечує локальну навігацію (`SCROLL`, фільтрацію, сортування) без додаткових звернень до мережі.

Ця еволюція сформувала сучасний ландшафт обробки даних, де інженер балансує між навантаженням на сервер, накладними витратами мережі та використанням оперативної пам'яті клієнта.
