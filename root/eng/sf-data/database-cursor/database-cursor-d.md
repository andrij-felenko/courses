Коли фонова служба аналітики або формування податкової звітності надсилає до сервера реляційної бази даних запит на вибірку всіх транзакцій за рік (`SELECT * FROM transactions WHERE created_at >= '2025-01-01'`), результуючий набір може містити п'ятдесят мільйонів рядків загальним обсягом понад шістдесят гігабайтів. Якщо клієнтська бібліотека працює за схемою повного накопичення результату, сервер змушений прочитати всі дискові сторінки, серіалізувати десятки мільйонів рядків у двійковий формат мережевого протоколу й безперервно вивантажувати їх у TCP-сокет. Клієнтський застосунок, отримуючи цей масив даних, намагається розмістити всі отримані об'єкти в оперативній пам'яті свого процесу, що неминуче викликає вичерпання виділеного ліміту пам'яті (Out Of Memory, OOM) та аварійне завершення процесу ще до того, як перший рядок потрапить у бізнес-логіку обробника.

Спроба розв'язати цю проблему за допомогою розбиття запиту на сторінки через конструкцію зміщення та ліміту (`SELECT ... ORDER BY id LIMIT 1000 OFFSET k`) у циклі призводить до квадратичної деградації продуктивності. Для кожного наступного блоку `OFFSET k` дисковий рушій бази даних змушений послідовно зчитувати з індексу або таблиці `k` попередніх рядків, перевіряти їхню видимість і відкидати, виконуючи колосальний обсяг марних дискових операцій введення-виведення. Ба більше, якщо між двома послідовними запитами сторінок паралельні транзакції додадуть або видалять рядки, зміщення зсунеться, і клієнт отримає спотворені дані: окремі рядки будуть оброблені двічі, а інші випадуть з обробки взагалі.

Фізичний рушій виконання запитів реляційної СУБД усередині влаштований інакше: вузли плану виконання формують конвеєр ітераторів, де кожен оператор генерує кортежі не всі одразу, а строго по одному за запитом споживача. Щоб надати прикладному коду безпечний доступ до цього внутрішнього конвеєра обчислень без необхідності вивантаження всього набору даних у пам'ять, використовується спеціальний механізм ітеративного позиціонування.

Цей механізм називається **курсором** (від латинського *cursor* — бігун, вісник, той, хто вказує шлях, від дієслова *currere* — бігти). Курсор являє собою керований дескриптор активного стану запиту на сервері бази даних, який зберігає поточну позицію сканування в результуючому наборі та дозволяє клієнтській програмі послідовно або довільно вибирати фіксовану кількість рядків зі стабільним споживанням пам'яті `O(1)`.

![Порівняння клієнтського буферизування та серверного курсора](/root/eng/sf-data/database-cursor/img/fig1-cursor-streaming-vs-buffering.svg)
*Порівняння двох підходів до вибірки великих наборів даних: повне буферизування у пам'яті клієнта проти потокового курсорного читання з фіксованим споживанням ресурсів.*

Історичні передумови виникнення цієї абстракції на межі між декларативною реляційною алгеброю та імперативними мовами програмування детально висвітлено у вставці [📜 Еволюція курсорів у базах даних: від навігаційного CODASYL до SQL-92 та ODBC](root:sf-data/database-cursor/hist-cursor-evolution.md).

## Фізична архітектура: Модель ітераторів Volcano, портали та керування пам'яттю

Щоб зрозуміти, як курсор взаємодіє з ядром СУБД, необхідно розглянути класичну модель виконання реляційних запитів — **модель ітераторів Volcano** (Volcano Iterator Model), сформульовану Гойцом Грефе (Goetz Graefe). 

У цій архітектурі скомпільований план запиту подається у вигляді дерева фізичних операторів (вузлів плану: `SeqScan`, `IndexScan`, `Filter`, `HashJoin`, `Sort`, `Limit`). Кожен вузол реалізує уніфікований інтерфейс ітератора, що складається з трьох фундаментальних методів:
1. `open()` — ініціалізує внутрішній стан вузла, виділяє структури пам'яті та рекурсивно викликає `open()` для всіх дочірніх операторів;
2. `next()` — повертає наступний обчислений кортеж або спеціальний маркер кінця потоку (`EOF`). Для отримання кортежу оператор за потреби запитує кортежі у своїх дочірніх вузлів;
3. `close()` — звільняє виділену динамічну пам'ять, закриває дискові дескриптори та очищає стан вузлів піддерева.

![Модель ітераторів Volcano та інтеграція курсора](/root/eng/sf-data/database-cursor/img/fig2-volcano-iterator-engine.svg)
*Анатомія виконання запиту за моделлю Volcano: серверний портал курсора викликає метод next() кореневого вузла дерева фізичного плану.*

За поведінкою споживання даних фізичні оператори поділяються на дві принципово різні категорії:
- **Потокові (конвеєрні, non-blocking):** оператори, які здатні повернути перший кортеж миттєво після отримання першого вхідного рядка від дочірнього вузла (`SeqScan`, `IndexScan`, `NestedLoopJoin`, `Projection`, фільтрація `Filter`). Вони не потребують проміжного накопичення даних у пам'яті;
- **Матеріалізуючі (блокуючі, pipeline breakers):** оператори, які не можуть повернути жодного рядка, доки повністю не вичитають і не опрацюють увесь вхідний потік даних від дочірнього піддерева (`Sort` без індексу, `HashJoin` під час побудови хеш-таблиці, `Aggregate` з групуванням, віконні функції).

Коли прикладний код виконує інструкцію оголошення курсора `DECLARE cur CURSOR FOR SELECT ...`, сервер СУБД не запускає негайне обчислення всього запиту. Замість цього сервер створює так званий **портал** (від середньовічного латинського *portale* — вхідна брама, від *porta* — ворота). 

Портал — це серверна структура управління активним виконанням запиту, яка зберігає дерево скомпільованого фізичного плану, покажчики на виділені контексти пам'яті (`MemoryContext`), знімок транзакційного стану (Transaction Snapshot) та поточний числовий зсув прочитаних рядків.

### Внутрішні фази виконання порталу на сервері

У ядрі сервера обробка порталу проходить через п'ять суворо розмежованих етапів внутрішнього API (на прикладі підсистеми `pquery.c` у PostgreSQL):
1. `PortalCreate` — виділення дескриптора порталу в таблиці хешів відкритих сеансових об'єктів;
2. `PortalDefineQuery` — зв'язування абстрактного синтаксичного дерева (AST) та скомпільованого плану виконання з дескриптором;
3. `PortalStart` — створення транзакційного знімка стану (Snapshot), ініціалізація структур `EState` та виклик `ExecutorStart()`;
4. `PortalRun` (або `PortalRunSelect`) — безпосередній запуск конвеєра на виконання із заданим лімітом рядків `count`. Виконавець викликає метод `ExecutorRun()`, який крокує по дереву операторів рівно стільки разів, скільки рядків запросив клієнт;
5. `PortalDrop` — виклик `ExecutorEnd()`, закриття задіяних індексів, звільнення пам'яті та видалення порталу з системної таблиці.

### Вплив курсора на вибір плану запиту оптимізатором

При плануванні стандартного запиту оптимізатор шукає план із мінімальною загальною вартістю (Total Cost), тобто орієнтується на якнайшвидше отримання останнього рядка. Для цього планувальник часто обирає паралельне послідовне сканування або побудову хеш-таблиць (`HashJoin`), оскільки вони ефективні для повної обробки мільйонів записів, хоча й вимагають тривалого часу розігріву (Startup Cost).

Коли запит оголошується як курсор, сервер змінює мету оптимізації. У конфігурації PostgreSQL за це відповідає параметр `cursor_tuple_fraction` (за замовчуванням `0.1`). Цей коефіцієнт вказує планувальнику, що застосунок, імовірно, вичитає лише частину результуючого набору (наприклад, перші `10%` рядків). 

У результаті планувальник віддає перевагу планам із мінімальною вартістю повернення першого рядка (Startup Cost), таким як сканування за B-Tree індексом (`IndexScan`) або з'єднання вкладеними циклами (`NestedLoop`), навіть якщо їхня гіпотетична вартість вичитування всього набору до кінця була б вищою за хеш-з'єднання. Це забезпечує клієнту миттєвий відгук на перший виклик `FETCH`.

### Ієрархія контекстів пам'яті під час виконання курсора

У ядрі СУБД виділення пам'яті організовано у вигляді строгого дерева контекстів. Для відкритого курсора створюється виділений підконтекст `PortalContext`, розташований під загальним `TopMemoryContext` сеансу.

Усередині `PortalContext` функціонують два ключові рівні:
1. **Рівень стану плану (ExecutorState):** містить довготривалі структури операторів, опис схеми стовпців (`TupleDesc`) та індексні дескриптори. Ця пам'ять живе протягом усього часу існування відкритого курсора;
2. **Рівень обчислення виразів (ExprContext):** тимчасовий робочий простір, де виконується фільтрація предикатів, перетворення типів та обчислення функцій над поточним рядком.

Після обробки кожного окремого пакета рядків (наприклад, після завершення `FETCH 1000`) рушій викликає функцію `ResetExprContext()`. Це миттєво звільняє всю пам'ять, виділену під тимчасові значення та десеріалізовані кортежі. Завдяки такому циклічному скиданню контексту при використанні конвеєрного плану запиту споживання оперативної пам'яті серверного бекенду залишається константним протягом усієї вибірки, незалежно від кількості вичитаних мільйонів рядків.

Під час виконання команди `FETCH n FROM cur` сервер викликає метод `next()` кореневого оператора плану рівно `n` разів, формує мережевий пакет із видобутих кортежів і надсилає його клієнту, після чого «заморожує» стан порталу до наступної команди `FETCH`. Якщо дерево плану складається виключно з потокових операторів, запит виконується у строго конвеєрному режимі без матеріалізації на диску та з фіксованим споживанням пам'яті на сервері.

## Серверні та клієнтські курсори: Мережевий протокол і баланс навантаження

У прикладній розробці поняття «курсор» часто використовується в двох різних значеннях, які мають діаметрально протилежну фізичну поведінку: **серверний курсор** (Server-side Cursor) та **клієнтський курсор** (Client-side Cursor / Driver Buffering).

```
+-------------------------------------------------------------------------------+
| Критерій                 | Серверний курсор           | Клієнтське буферизування |
+--------------------------+----------------------------+-----------------------+
| Місце збереження стану   | Пам'ять процесу СУБД (Portal)| RAM клієнтського драйвера|
| Використання RAM клієнта | Bounded: O(розмір пакета)   | Unbounded: O(всі рядки) |
| Час до першого рядка     | Мінімальний (мілісекунди)  | Максимальний (весь I/O) |
| Навантаження на з'єднання| Утримує відкриту транзакцію| Звільняє з'єднання одразу|
| Накладні витрати мережі  | Вищі (багато пакетів FETCH)| Мінімальні (один потік) |
| Ризик витоку ресурсів    | Високий (якщо забути CLOSE)| Нульовий на сервері   |
+-------------------------------------------------------------------------------+
```

Серверний курсор переносить тягар зберігання стану на процес бази даних. Клієнт керує потоком за допомогою двійкових повідомлень мережевого протоколу (наприклад, у розширеному протоколі PostgreSQL Frontend/Backend Protocol це повідомлення `Execute` з параметром максимальної кількості рядків `max_rows`). Це гарантує захист клієнтського вузла від переповнення пам'яті, проте створює ризик навантаження на сервер у разі зависання або некоректного завершення клієнтської програми.

### Мережевий двійковий протокол та режим Single-Row Mode

Під час прямого виконання запиту через низькорівневий сокет сервер надсилає послідовність повідомлень:
1. `RowDescription` (байт `'T'`) — метадані колонок (імена стовпців, ідентифікатори типів OID, модифікатори довжини);
2. Серія повідомлень `DataRow` (байт `'D'`) — двійкові або текстові дані кортежів;
3. `CommandComplete` (байт `'C'`) — статус виконання (`SELECT 50000000`);
4. `ReadyForQuery` (байт `'Z'`) — сервер готовий прийняти наступну транзакцію.

Якщо клієнтська бібліотека викликає стандартну функцію `PQexec()`, вона перехоплює всі повідомлення `DataRow` і накопичує їх у пам'яті до отримання байта `'Z'`. 

Альтернативою іменованим курсорам є спеціальний клієнтський режим потокового читання — **поодинокий режим** (`PQsetSingleRowMode` у бібліотеці `libpq`). Після надсилання запиту клієнт активує цей режим, і функція `PQgetResult()` повертає керування після отримання кожного окремого рядка (`PGRES_SINGLE_TUPLE`). Це дозволяє програмі споживати дані в потоковому режимі без створення іменованого серверного порталу, однак з'єднання залишається заблокованим до повного зчитування всього набору.

### Мережева балакучість і розмір пакета (Batch Size)

Ключовим параметром продуктивності під час роботи із серверним курсором є розмір пакетної вибірки (`fetch_size` або аргумент команди `FETCH n`).

Якщо програма вичитує дані по одному рядку (`FETCH 1`), для передачі кожної сутності потрібен окремий мережевий раунд-тріп (Round-Trip Time, RTT) між клієнтом і базою даних. Якщо затримка мережі становить `1` мілісекунду, то вибірка `1 000 000` рядків займе щонайменше `1000` секунд (понад `16` хвилин) суто через очікування підтверджень мережевих пакетів, навіть якщо сервер здатен згенерувати всі дані за пів секунди.

Час виконання вибірки `T_total` описується залежністю від загальної кількості рядків `N`, розміру пакета `B`, мережевої затримки `RTT` та часу фізичної обробки одного кортежу `t_row`:

```
T_total = (N ÷ B) · RTT + N · t_row
```

Збільшення розміру пакета `B` від `1` до `1000` скорочує кількість мережевих звернень у тисячу разів, зводячи накладні витрати передачі практично до нуля. Проте надмірне збільшення `B` (наприклад, понад `100 000`) знову наближає поведінку системи до клієнтського буферизування, збільшуючи використання оперативної пам'яті та затримку перед початком обробки кожної порції. На практиці оптимальним діапазоном розміру пакета для більшості аналітичних та експортних задач є від `500` до `5000` рядків.

## Класифікація та життєвий цикл курсорів у SQL

Стандарт мови SQL та реалізації провідних СУБД надають розгалужену систему параметрів, що визначають просторову навігацію, транзакційну довговічність та чутливість курсора до змін.

![Життєвий цикл курсора та типи матеріалізації](/root/eng/sf-data/database-cursor/img/fig3-cursor-lifecycle-and-types.svg)
*Життєвий цикл курсора (DECLARE, OPEN, FETCH, CLOSE) та порівняння параметрів SCROLL і WITH HOLD.*

### 1. Напрямок переміщення: `NO SCROLL` проти `SCROLL`

- **Однонаправлений (`NO SCROLL`, Forward-Only):** курсор може пересуватися результуючим набором виключно вперед від першого рядка до останнього за допомогою команди `FETCH NEXT`. Це найбільш ефективний режим: якщо план запиту конвеєрний, серверу не потрібно зберігати вже вичитані рядки. Прочитані сторінки негайно видаляються з контексту виконання;
- **Прокручуваний (`SCROLL`, Scrollable):** курсор підтримує довільні переміщення: рух назад (`FETCH PRIOR`), стрибок на початок або в кінець (`FETCH FIRST`, `FETCH LAST`), а також абсолютне і відносне позиціонування (`FETCH ABSOLUTE 42`, `FETCH RELATIVE -10`).

Щоб забезпечити можливість повернення назад, рушій СУБД змушений матеріалізувати всі вичитані кортежі у спеціальну тимчасову структуру зберігання — **сховище кортежів** (`tuplestore` у PostgreSQL). Сховище кортежів починає роботу в оперативній пам'яті як масив структур `MinimalTuple`. 

Якщо обсяг вибірки перевищує виділений ліміт оперативної пам'яті сеансу (`work_mem`), сховище автоматично скидає дані у тимчасові файли на диску (`pgsql_tmp`). Це перетворює конвеєрний запит на блокуючий і створює суттєве додаткове навантаження на підсистему введення-виведення.

### 2. Межі транзакцій: `WITHOUT HOLD` проти `WITH HOLD`

Життєвий цикл класичного курсора жорстко прив'язаний до життєвого циклу транзакції, в якій його було відкрито. За замовчуванням курсор створюється з властивістю `WITHOUT HOLD`. Коли транзакція завершується інструкцією `COMMIT` або `ROLLBACK`, сервер автоматично закриває всі пов'язані з нею портали та звільняє виділені структури пам'яті.

Якщо довготривала пакетна обробка вимагає періодичної фіксації проміжних результатів (наприклад, оновлення статусу кожних 1000 записів із виконанням `COMMIT`, щоб не блокувати журнал випереджального запису WAL), звичайний курсор закриється після першого ж коміту. Для вирішення цієї задачі використовується параметр збереження після фіксації — **курсор із утриманням** (`WITH HOLD`):

```sql
DECLARE batch_cur CURSOR WITH HOLD FOR 
SELECT id, payload FROM queue_tasks WHERE status = 'NEW';
```

Під час виконання команди `COMMIT` сервер бази даних знаходить усі відкриті портали з прапорцем `WITH HOLD`, примусово вичитує всі залишки результуючого набору через дерево плану і записує їх у тимчасовий дисковий файл (`tuplestore`). Після цього поточна транзакція успішно фіксується, всі блокування рядків у базових таблицях знімаються, а клієнтський застосунок отримує можливість продовжувати ітерацію через `FETCH` у нових транзакціях, вичитуючи зафіксований знімок із тимчасового файлу.

Повний синтаксичний довідник інструкцій позиціонування, статусних змінних та прапорців сумісності наведено у вставці [📋 Специфікація та команди керування курсорами в SQL](root:sf-data/database-cursor/api-sql-cursor-reference.md).

### 3. Чутливість до паралельних змін: `INSENSITIVE` проти `SENSITIVE`

Параметр чутливості визначає, чи бачитиме відкритий курсор зміни (вставки, оновлення, видалення), здійснені іншими паралельними транзакціями або поточним сеансом під час ітерації:
- **Нечутливий (статичний, `INSENSITIVE`):** курсор відкривається над фіксованим знімком стану. Будь-які модифікації базових таблиць, виконані після команди `OPEN`, повністю невидимі для операцій `FETCH`;
- **Керований ключами (Keyset-driven cursor):** під час відкриття курсор зчитує та фіксує лише список первинних ключів (`Primary Keys` або фізичних адрес рядків `ROWID`). Під час кожного наступного виклику `FETCH` сервер здійснює точкове дочитування актуальних значень стовпців із таблиці за відповідним ключем. Такий курсор бачить оновлення існуючих рядків, але не бачить новостворених записів (фантомних рядків);
- **Динамічний (чутливий, `SENSITIVE`):** курсор не фіксує навіть списку ключів і динамічно переоцінює умови предикатів сканування під час кожного руху покажчика. Це найбільш ресурсомісткий режим, що вимагає високих рівнів блокування.

### 4. Модифікація за місцем розташування: `WHERE CURRENT OF`

Традиційний підхід до оновлення рядків під час ітеративної обробки передбачає виконання повторного запиту: `UPDATE accounts SET balance = balance + 10 WHERE id = :current_id`. Цей запит змушує рушій бази даних повторно проходити по B-Tree індексу таблиці для пошуку фізичної адреси блоку за первинним ключем.

Якщо курсор оголошено з модифікатором блокування `FOR UPDATE`, сервер зберігає у внутрішньому контексті позиції фізичний ідентифікатор рядка (Tuple ID / `ctid` у PostgreSQL, `ROWID` в Oracle). Для миттєвої модифікації або видалення поточного рядка без повторного сканування індексів використовується спеціальний синтаксис позиційного оновлення:

```sql
BEGIN;
DECLARE cur_acc CURSOR FOR 
    SELECT balance FROM accounts WHERE status = 'ACTIVE' FOR UPDATE;

FETCH NEXT FROM cur_acc;

-- Миттєве оновлення без повторного пошуку за індексом
UPDATE accounts 
SET balance = balance * 1.05 
WHERE CURRENT OF cur_acc;

CLOSE cur_acc;
COMMIT;
```

Під час виконання `UPDATE ... WHERE CURRENT OF cur_acc` виконавець бере збережену дискову адресу поточного рядка, перевіряє активне блокування рядка і здійснює модифікацію за нульовий час пошуку.

## Вплив на паралелізм, MVCC та небезпеки відкритих курсорів

Використання серверних курсорів у системах із високим навантаженням вимагає суворої дисципліни управління транзакціями через їхній безпосередній вплив на підсистему багатоверсійного керування паралелізмом (Multi-Version Concurrency Control, MVCC).

![Вплив довготривалого курсора на очищення MVCC та горизонт xmin](/root/eng/sf-data/database-cursor/img/fig4-cursor-mvcc-vacuum-impact.svg)
*Механізм утримання транзакційного горизонту xmin відкритим курсором: блокування фонового очищення (VACUUM) та розростання фізичних сторінок таблиці.*

Коли транзакція відкриває курсор над реляційним запитом, рушій СУБД фіксує для неї транзакційний знімок. У знімку реєструється номер найстарішої активної транзакції — **горизонт транзакцій** (`xmin` у PostgreSQL або Transaction Read View в InnoDB).

У моделі MVCC під час оновлення чи видалення рядків старі версії кортежів не знищуються на диску фізично: вони залишаються у сторінках таблиці (Heap Pages) для забезпечення узгодженого читання іншими транзакціями. Очищення мертвих версій кортежів покладається на фоновий процес очищення (процес `VACUUM` у PostgreSQL або потік `Purge` в InnoDB).

Головне правило процесу очищення формулюється так: **жодна мертва версія рядка не може бути вилучена з диска, якщо номер транзакції її модифікації більший або рівний найменшому значенню `xmin` серед усіх активних транзакцій у системі**.

Якщо клієнтський застосунок відкриває серверний курсор для обробки мільйона рядків, але обробляє кожен запис повільно (наприклад, виконуючи тривалі мережеві виклики до зовнішніх HTTP API), транзакція з курсором залишається відкритою протягом багатьох годин. Це призводить до критичних системних наслідків:
1. **Заморожування горизонту `xmin`:** усі оновлення та видалення, здійснені будь-якими іншими користувачами системи за ці години, не можуть бути фізично вичищені процесом `VACUUM`;
2. **Розростання таблиць та індексів (Table and Index Bloat):** мертві кортежі накопичуються у сторінках даних, багаторазово збільшуючи фізичний розмір таблиць на диску. Сканування індексів уповільнюється для всієї бази даних через необхідність перевірки мільйонів мертвих вказівників;
3. **Вичерпання ліміту лічильника транзакцій (Transaction ID Wraparound):** екстремальне утримання найстарішого `xmin` створює загрозу аварійної зупинки СУБД для запобігання переповненню 32-бітного лічильника транзакцій.

### Блокування та взаємні блокування (Deadlocks)

Якщо курсор оголошено з інструкцією `FOR UPDATE`, він накладає ексклюзивні блокування на кожен прочитаний рядок таблиці (`ExclusiveLock` або `RowShareLock` на рівні відношення). Якщо два паралельні процеси відкривають курсори `FOR UPDATE` над тими самими таблицями, але сканують дані в різному порядку (наприклад, один за зростанням індексу, а інший за спаданням), неминуче виникає взаємне блокування (Deadlock). Обидві транзакції зупиняються, очікуючи звільнення рядків одна одної, доки серверний детектор взаємних блокувань не перерве одну з них через помилку `deadlock_detected`.

Для уникнення блокування черг використовуються неблокуючі модифікатори:
- `FOR UPDATE NOWAIT`: якщо рядок заблокований іншою транзакцією, запит миттєво повертає помилку, не очікуючи зняття блокування;
- `FOR UPDATE SKIP LOCKED`: курсор автоматично пропускає заблоковані рядки, вибираючи лише вільні. Це ідеальний механізм для побудови високопродуктивних черг повідомлень на базі реляційних таблиць.

### Моніторинг та діагностика активних курсорів

Для запобігання аварійним ситуаціям системний адміністратор здійснює діагностику відкритих порталів за допомогою системних утиліт та представлень:

```sql
-- Перегляд усіх відкритих курсорів у поточному сеансі
SELECT name, statement, is_holdable, is_binary, is_scrollable, creation_time 
FROM pg_cursors;

-- Пошук завислих транзакцій, що утримують старий горизонт xmin
SELECT pid, usename, state, age(backend_xmin) AS xmin_age, query, query_start 
FROM pg_stat_activity 
WHERE backend_xmin IS NOT NULL 
ORDER BY age(backend_xmin) DESC;
```

Якщо показник `xmin_age` перевищує критичні пороги (наприклад, понад мільйон транзакцій), такий сеанс підлягає примусовому завершенню за допомогою функції `pg_terminate_backend(pid)`. Для автоматичного захисту в конфігурації СУБД налаштовуються параметри `idle_in_transaction_session_timeout` (примусове закриття неактивних транзакцій через заданий інтервал) та `statement_timeout`.

## Курсор чи Keyset-пагінація: Архітектурний вибір

При проектуванні веб-сервісів, API та конвеєрів обробки виникає необхідність вибору між двома конкурентними стратегіями ітеративного доступу: серверним курсором та **пагінацією за ключами** (Keyset Pagination / Seek Method).

```
+---------------------------------------------------------------------------------------+
| Властивість             | Серверний курсор (Cursor) | Keyset-пагінація (WHERE id > k) |
+-------------------------+---------------------------+---------------------------------+
| Збереження стану        | Stateful (з'єднання зайняте)| Stateless (без стану між HTTP)|
| Підтримка в REST API    | Непридатна для вебу       | Ідеальна для REST / GraphQL     |
| Консистентність даних   | Абсолютна (єдиний знімок) | Зміни між сторінками видимі     |
| Вимоги до індексів      | Довільний складний запит  | Строго вимагає B-Tree за ключем |
| Сфера застосування      | Фоновий ETL, експорт файлу| Публічні API, веб-інтерфейси    |
+---------------------------------------------------------------------------------------+
```

Keyset-пагінація будується на безстановому предикаті фільтрації за композитним або первинним ключем:
```sql
SELECT id, user_id, amount, created_at 
FROM transactions 
WHERE (created_at, id) > (:last_seen_created_at, :last_seen_id)
ORDER BY created_at ASC, id ASC 
LIMIT 1000;
```

Кожен такий запит є повністю незалежним, виконується за логарифмічний час `O(log N)` за наявності відповідного B-Tree індексу і не утримує відкритих транзакцій на сервері. Проте Keyset-пагінація не гарантує ізольованого знімка на момент старту обробки і вимагає чіткої монотонності та детермінованого сортування за унікальними полями.

Серверний курсор, навпаки, є найкращим інструментом для **внутрішніх фонових пакетних завдань** (Batch Processing, Data Migration, ETL-конвеєри), де обробка виконується в межах одного неперервного процесу з монопольним володінням з'єднанням і вимагає гарантованої математичної узгодженості результуючого набору.

## Інженерний приклад: Потоковий конвеєр мовами C та C++

Практичну реалізацію високопродуктивного конвеєра потокової пакетної обробки наведено нижче. Клієнтський код відкриває з'єднання через бібліотеку `libpq`, оголошує однонаправлений курсор `NO SCROLL`, пакетами витягує рядки й агрегує суми без накопичення масиву в оперативній пам'яті.

```c
/* cursor_stream_processor.c — Потокова обробка через серверний курсор мовою C */
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <libpq-fe.h>

#define CHUNK_SIZE 1000

typedef struct {
    unsigned long count;
    double sum;
} StreamResult;

static bool exec_statement(PGconn *conn, const char *sql) {
    PGresult *res = PQexec(conn, sql);
    if (PQresultStatus(res) != PGRES_COMMAND_OK) {
        fprintf(stderr, "Помилка виконання SQL [%s]: %s\n", sql, PQerrorMessage(conn));
        PQclear(res);
        return false;
    }
    PQclear(res);
    return true;
}

int process_large_dataset_c(const char *conninfo, StreamResult *out) {
    PGconn *conn = PQconnectdb(conninfo);
    if (PQstatus(conn) != CONNECTION_OK) {
        fprintf(stderr, "Збій підключення: %s\n", PQerrorMessage(conn));
        PQfinish(conn);
        return -1;
    }

    out->count = 0;
    out->sum = 0.0;

    /* 1. Старт транзакції з рівнем ізоляції знімка */
    if (!exec_statement(conn, "BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;")) {
        PQfinish(conn);
        return -1;
    }

    /* 2. Створення однонаправленого потокового курсора */
    const char *decl_query = 
        "DECLARE trans_cur NO SCROLL CURSOR FOR "
        "SELECT amount FROM transactions WHERE status = 'SUCCESS';";
    if (!exec_statement(conn, decl_query)) {
        exec_statement(conn, "ROLLBACK;");
        PQfinish(conn);
        return -1;
    }

    char fetch_cmd[64];
    snprintf(fetch_cmd, sizeof(fetch_cmd), "FETCH %d FROM trans_cur;", CHUNK_SIZE);

    /* 3. Циклічне вичитування з фіксованим розміром буфера */
    while (true) {
        PGresult *res = PQexec(conn, fetch_cmd);
        if (PQresultStatus(res) != PGRES_TUPLES_OK) {
            fprintf(stderr, "Помилка вибірки FETCH: %s\n", PQerrorMessage(conn));
            PQclear(res);
            exec_statement(conn, "ROLLBACK;");
            PQfinish(conn);
            return -1;
        }

        int rows = PQntuples(res);
        if (rows == 0) {
            PQclear(res);
            break; /* Досягнуто кінця результуючого набору */
        }

        for (int i = 0; i < rows; ++i) {
            if (!PQgetisnull(res, i, 0)) {
                out->sum += strtod(PQgetvalue(res, i, 0), NULL);
                out->count++;
            }
        }
        PQclear(res);
    }

    /* 4. Закриття порталу та фіксація транзакції */
    exec_statement(conn, "CLOSE trans_cur;");
    exec_statement(conn, "COMMIT;");

    PQfinish(conn);
    return 0;
}
```
```cpp
// cursor_stream_processor.cpp — Ідіоматичний RAII-конвеєр на C++20
#include <iostream>
#include <memory>
#include <string>
#include <string_view>
#include <format>
#include <stdexcept>
#include <libpq-fe.h>

struct PgConnDeleter {
    void operator()(PGconn* c) const noexcept { if (c) PQfinish(c); }
};

struct PgResultDeleter {
    void operator()(PGresult* r) const noexcept { if (r) PQclear(r); }
};

using UniquePgConn = std::unique_ptr<PGconn, PgConnDeleter>;
using UniquePgResult = std::unique_ptr<PGresult, PgResultDeleter>;

struct StreamStats {
    uint64_t total_rows = 0;
    double total_sum = 0.0;
};

/* Безпечна RAII-обгортка над життєвим циклом транзакції та серверного курсора */
class ScopedDatabaseCursor {
public:
    ScopedDatabaseCursor(PGconn* conn, std::string_view cursor_name, std::string_view sql_query, size_t chunk_size = 1000)
        : conn_(conn), name_(cursor_name), chunk_size_(chunk_size) {
        
        execute_command("BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;");
        
        std::string decl_sql = std::format("DECLARE {} NO SCROLL CURSOR FOR {};", name_, sql_query);
        execute_command(decl_sql);
        
        fetch_sql_ = std::format("FETCH {} FROM {};", chunk_size_, name_);
    }

    ~ScopedDatabaseCursor() noexcept {
        try {
            if (active_) {
                execute_command(std::format("CLOSE {};", name_));
                execute_command("COMMIT;");
            }
        } catch (...) {
            // Деструктори не повинні викидати винятків
        }
    }

    ScopedDatabaseCursor(const ScopedDatabaseCursor&) = delete;
    ScopedDatabaseCursor& operator=(const ScopedDatabaseCursor&) = delete;
    ScopedDatabaseCursor(ScopedDatabaseCursor&&) noexcept = default;

    UniquePgResult fetch_chunk() {
        if (!active_) return nullptr;

        auto res = UniquePgResult(PQexec(conn_, fetch_sql_.c_str()));
        if (PQresultStatus(res.get()) != PGRES_TUPLES_OK) {
            throw std::runtime_error(std::format("Помилка виконання FETCH: {}", PQerrorMessage(conn_)));
        }

        if (PQntuples(res.get()) == 0) {
            active_ = false;
            return nullptr;
        }
        return res;
    }

private:
    void execute_command(std::string_view sql) {
        auto res = UniquePgResult(PQexec(conn_, sql.data()));
        if (PQresultStatus(res.get()) != PGRES_COMMAND_OK) {
            throw std::runtime_error(std::format("Помилка SQL [{}]: {}", sql, PQerrorMessage(conn_)));
        }
    }

    PGconn* conn_;
    std::string name_;
    size_t chunk_size_;
    std::string fetch_sql_;
    bool active_ = true;
};

StreamStats process_large_dataset_cpp(std::string_view conninfo) {
    UniquePgConn conn(PQconnectdb(conninfo.data()));
    if (PQstatus(conn.get()) != CONNECTION_OK) {
        throw std::runtime_error(std::format("Збій з'єднання з базою даних: {}", PQerrorMessage(conn.get())));
    }

    StreamStats stats;
    constexpr size_t BATCH_SIZE = 1000;
    std::string_view query = "SELECT amount FROM transactions WHERE status = 'SUCCESS'";

    ScopedDatabaseCursor cursor(conn.get(), "trans_cur", query, BATCH_SIZE);

    while (auto chunk = cursor.fetch_chunk()) {
        int rows = PQntuples(chunk.get());
        for (int i = 0; i < rows; ++i) {
            if (!PQgetisnull(chunk.get(), i, 0)) {
                std::string_view val = PQgetvalue(chunk.get(), i, 0);
                stats.total_sum += std::stod(std::string(val));
                stats.total_rows++;
            }
        }
    }

    return stats;
}
```

> 🔧 **Навіщо це.**
>
> 1. **Захист від OOM у фонових завданнях:** Серверні курсори з пакетною вибіркою (`FETCH 1000`) є стандартом побудови надійних ETL-конвеєрів, експорту великих масивів даних у CSV/Parquet та міграцій, де обсяг вибірки вимірюється гігабайтами і не вміщується в пам'ять клієнтського контейнера.
> 2. **Запобігання деградації через OFFSET:** Курсор гарантує час вибірки `O(1)` для кожного наступного пакета рядків, усуваючи катастрофічне квадратичне сканування дисків, притаманне глибокій пагінації через `OFFSET`.
> 3. **Дотримання гігієни транзакцій:** Серверний курсор ніколи не повинен залишатися відкритим довше, ніж триває активна обробка даних. Тривале утримання порталу заморожує горизонт транзакцій `xmin` і блокує процес очищення бази даних (`VACUUM`), що призводить до фізичного розростання таблиць та деградації всієї СУБД.
