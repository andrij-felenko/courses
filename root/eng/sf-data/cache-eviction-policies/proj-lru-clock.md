# ⚙️ Два кеші зі стелею: точний LRU за O(1) і CLOCK на кільці

Тут зібрано робочий код обох структур на C++ і чесний рахунок їхньої вартості: скільки байтів іде на службові дані понад самі дані, скільки кеш-ліній чіпає одне влучання й скільки з них пише, скільки кроків коштує витіснення і що з кожною зі структур зробить шістнадцять потоків, які б'ють у кеш одночасно. Різниця між ними зводиться до однієї дрібниці — чи пише щось спільне звичайне читання, — і саме з цієї дрібниці виростає різниця на два порядки в пропускній здатності.

## Умови задачі

Обидва кеші мають однаковий інтерфейс, щоб їх можна було міняти місцями у вимірюванні:

```cpp
std::optional<V> get(const K& key);   // влучання повертає значення, промах — nullopt
void put(const K& key, V val);        // вставка; якщо місця немає — когось витіснити
```

Місткість задано **в записах**, а не в байтах: інакше довелося б окремо міряти розмір значень, а нас цікавить службова частина. Ключ і значення в замірах — `uint64_t`, тобто шістнадцять байтів корисних даних на запис; тримайте це число в голові, бо все службове порівнюватиметься саме з ним.

Міряти будемо чотири речі. Скільки байтів службових даних припадає на запис. Скільки кеш-ліній чіпає одне влучання і скільки з них **пише**. Скільки кроків коштує одне витіснення. І яка частка запитів мусить пройти крізь спільну точку, коли потоків багато.

## Точний LRU: дві вимоги задають структуру

Правило «викинути того, кого найдовше не питали» вимагає порядку записів за свіжістю. Порядок — це список; питання лише в тому, як у нього швидко потрапляти.

Вимог рівно дві, і кожна вибирає собі структуру. **За ключем дійти до запису за сталий час** — це [хеш-таблиця](topic:sf-algorithms/hash-table): вона за середній сталий час перетворює ключ на адресу запису. **Маючи запис на руках, вирвати його із середини порядку за сталий час** — це [двобічний список](topic:sf-algorithms/linked-list): вузол знає обох сусідів, тож перечепити три покажчики можна не шукаючи нічого обходом.

Друга вимога має тонкість, яку легко пропустити: список дає O(1) на вилучення **тільки тоді, коли вузол уже в руках**. Знайти вузол у списку самотужки коштувало б O(n) — і вся конструкція розсипалася б. Тому список має бути **інтрузивним**: зв'язки живуть усередині самого запису кеша, а не в окремих вузлах, що зберігають копію запису. Тоді хеш-таблиця віддає нам адресу запису — і разом із нею, безкоштовно, місце запису в порядку свіжості.

Класична навчальна збірка з двох стандартних контейнерів — `std::list<std::pair<K,V>>` плюс `std::unordered_map<K, std::list<...>::iterator>` — цю вимогу формально виконує (ітератори `std::list` не псуються від чужих вставок і вилучень). Але платить за це тричі: два окремих виділення пам'яті на кожен запис, вузли розкидані по купі, і ключ збережено двічі. Тому нижче — та сама ідея, складена вручну: усі вузли живуть в одному масиві, а роль покажчиків грають 32-бітні номери слотів.

```cpp
#include <cstdint>
#include <optional>
#include <unordered_map>
#include <vector>

// Точний LRU зі стелею в cap записів.
// Вузли лежать у суцільному масиві; зв'язки — номери слотів, а не покажчики.
template <class K, class V>
class LruCache {
    static constexpr uint32_t NIL = 0xFFFFFFFFu;
    struct Node { K key; V val; uint32_t prev = NIL, next = NIL; };

    std::vector<Node> slots_;                 // усі записи живуть тут
    std::unordered_map<K, uint32_t> index_;   // ключ → номер слота
    uint32_t head_ = NIL, tail_ = NIL, cap_;
    uint64_t hits_ = 0, misses_ = 0, evictions_ = 0;

public:
    explicit LruCache(uint32_t cap) : cap_(cap) {
        slots_.reserve(cap_);       // жодного перерозподілу за весь час життя
        index_.reserve(cap_ * 2);   // щоб таблиця не перебудовувалася на ходу
    }

    // Значення повертаємо КОПІЄЮ: посилання назовні віддавати не можна —
    // наступний put може витіснити саме цей запис і перевикористати слот.
    std::optional<V> get(const K& key) {
        auto it = index_.find(key);
        if (it == index_.end()) { ++misses_; return std::nullopt; }
        ++hits_;
        touch(it->second);                    // ЧИТАННЯ, ЯКЕ ПИШЕ
        return slots_[it->second].val;
    }

    void put(const K& key, V val) {
        if (auto it = index_.find(key); it != index_.end()) {
            slots_[it->second].val = std::move(val);
            touch(it->second);
            return;
        }
        uint32_t i;
        if (slots_.size() < cap_) {           // кеш іще не повний — новий слот
            i = static_cast<uint32_t>(slots_.size());
            slots_.emplace_back();
        } else {                              // повний — жертва з хвоста
            i = tail_;
            unlink(i);
            index_.erase(slots_[i].key);      // ключ ще живий: слот не чіпали
            ++evictions_;
        }
        slots_[i].key = key;
        slots_[i].val = std::move(val);
        index_.emplace(key, i);
        push_front(i);
    }

    double hit_ratio() const {
        uint64_t n = hits_ + misses_;
        return n ? static_cast<double>(hits_) / static_cast<double>(n) : 0.0;
    }

private:
    void unlink(uint32_t i) {
        Node& n = slots_[i];
        (n.prev == NIL ? head_ : slots_[n.prev].next) = n.next;
        (n.next == NIL ? tail_ : slots_[n.next].prev) = n.prev;
        n.prev = n.next = NIL;
    }

    void push_front(uint32_t i) {
        Node& n = slots_[i];
        n.prev = NIL;
        n.next = head_;
        if (head_ != NIL) slots_[head_].prev = i;
        head_ = i;
        if (tail_ == NIL) tail_ = i;
    }

    void touch(uint32_t i) {
        if (i == head_) return;               // найсвіжіший — робити нічого
        unlink(i);
        push_front(i);
    }
};
```

Три місця тут не декоративні, і кожне колись комусь коштувало вечора.

`slots_.reserve(cap_)` у конструкторі — не оптимізація, а **умова коректності**: доки місткість не перевищено, масив не перерозподіляється, тож номери слотів лишаються дійсними назавжди. Без `reserve` перший же `emplace_back` за межею ємності перенесе весь масив, і всі посилання, узяті на нього раніше, стануть сміттям.

Порядок рядків у гілці витіснення. Спершу `unlink`, потім `index_.erase(slots_[i].key)` — і лише після цього слот перезаписують новим ключем. Поміняйте два останні кроки місцями — і `erase` шукатиме в таблиці вже новий ключ, а старий назавжди лишиться в індексі покажчиком на чужий запис. Це не гіпотетична біда: витягти її з продакшену можна тільки за симптомом «кеш віддає не те значення», бо структура при цьому лишається зовні цілою.

І `touch` із раннім виходом. Найсвіжіший ключ просять найчастіше — саме тому він і найсвіжіший, — тож перевірка `i == head_` знімає більшу частину перестановок, ніж здається на око.

Тепер порахуймо, у що обходиться одне влучання на рівні пам'яті. `find` чіпає масив кошиків і вузол таблиці — це дві кеш-лінії, обидві на читання. Далі `touch` читає слот і пише в нього два числа, пише в слот попереднього сусіда, у слот наступного і в слот колишньої голови — до чотирьох різних ліній, усі **на запис**. Разом одне «читання» з погляду користувача чіпає до шести кеш-ліній, чотири з яких бруднить. Це і є ціна точного порядку, виражена в тому, що справді коштує грошей на сучасній машині.

## «Шістнадцять байтів на запис» — це не вся правда

Двобічний список у навчальних текстах оцінюють у два покажчики на запис. Порахуймо всю службову частину для кеша на 10 млн записів із ключем і значенням по 8 байтів:

```
корисні дані (ключ 8 + значення 8)                 = 16 Б

масив слотів: зв'язки prev, next по 4 Б            =  8 Б
хеш-індекс, вузлова таблиця:
   вузол = покажчик next 8 + копія ключа 8
           + номер слота 4 (+ вирівнювання 4)      = 24 Б
   службовий заголовок алокатора на КОЖЕН вузол    ≈  8…16 Б
   масив кошиків, ≈1 покажчик на запис             =  8 Б
──────────────────────────────────────────────────────────
службових разом на запис                           ≈ 48…56 Б
на 10 млн записів: даних 0.16 ГБ, службових        ≈ 0.5 ГБ
```

Числа варто прочитати двічі. Зв'язки списку — 8 байтів із півсотні; **основну частину службової пам'яті з'їдає не порядок, а сам індекс**. Це прямо суперечить звичному висновку «замінімо точний LRU на щось із одним бітом і заощадимо пам'ять»: індекс потрібен будь-якій політиці однаково, бо без нього ключ не знайти. Одним бітом заощаджують сім байтів із п'ятдесяти, а не п'ятдесят із п'ятдесяти.

Заощадити тут можна двома різними ходами. Перший — плоска (з відкритою адресацією) хеш-таблиця замість вузлової: замість окремого виділення на запис — масив слотів із коефіцієнтом заповнення близько 0.8, тобто приблизно 15–17 байтів на запис замість 40–48. Другий — не зберігати ключ двічі: у наведеному коді копія ключа лежить і у вузлі, і в індексі. Для восьмибайтового ключа це вісім зайвих байтів, для рядкового — ще одне виділення пам'яті на кожен запис.

Але жодне з цих чисел не варто брати на віру, зокрема й моє: заголовок алокатора, коефіцієнт заповнення й вирівнювання залежать від збірки. Виміряйте своє — це двадцять рядків:

```cpp
#include <cstddef>
#include <memory>

inline size_t g_index_bytes = 0;              // C++17 inline-змінна

template <class T>
struct CountingAlloc {
    using value_type = T;
    CountingAlloc() = default;
    template <class U> CountingAlloc(const CountingAlloc<U>&) {}

    T* allocate(size_t n) {
        g_index_bytes += n * sizeof(T);
        return std::allocator<T>{}.allocate(n);
    }
    void deallocate(T* p, size_t n) {
        g_index_bytes -= n * sizeof(T);
        std::allocator<T>{}.deallocate(p, n);
    }
    template <class U> bool operator==(const CountingAlloc<U>&) const { return true; }
};

using Index = std::unordered_map<
    uint64_t, uint32_t, std::hash<uint64_t>, std::equal_to<uint64_t>,
    CountingAlloc<std::pair<const uint64_t, uint32_t>>>;

// заповнити Index десятьма мільйонами пар і надрукувати g_index_bytes / 10'000'000
```

Одне застереження до результату: лічильник бачить лише те, скільки контейнер **попросив**, а не скільки алокатор насправді зайняв. Справжня цифра завжди більша — на заголовок і на округлення розміру шматка. Тому поруч із цим числом варто дивитися ще й на `RSS` процесу до й після заповнення: різниця між ними й буде правдою.

## Читання, яке пише, і що з ним робить замок

Погляньте ще раз на `get`. З погляду користувача це читання. З погляду структури — запис у спільні дані: `touch` переставляє вузол. Отже, два потоки, які одночасно влучили в кеш, не можуть просто розійтися — вони псують одне одному покажчики, і це звичайнісінька [гонка за спільними даними](topic:sf-tasks/atomicity-races) з невизначеною поведінкою, а не «трохи неточний порядок».

Найпростіші ліки виглядають так:

```cpp
template <class K, class V>
class LockedLru {
    LruCache<K, V> impl_;
    std::mutex mu_;                     // shared_mutex тут НЕ допоможе

public:
    std::optional<V> get(const K& key) {
        std::lock_guard lk(mu_);        // ексклюзивний навіть на читанні
        return impl_.get(key);
    }
    void put(const K& key, V val) {
        std::lock_guard lk(mu_);
        impl_.put(key, std::move(val));
    }
};
```

Коментар про `std::shared_mutex` — головне в цьому фрагменті. Замок «багато читачів або один письменник» рятує там, де читачі справді лише читають. Тут кожне влучання пише, тож усі мусять брати замок ексклюзивно, і читачі стають у чергу один до одного. Ані розділення на читачів і письменників, ані атомарні операції на окремих полях цього не змінюють: перестановка вузла — це п'ять записів у чотири різні місця, і вони мусять статися разом.

Далі арифметика, яку варто вміти робити на серветці:

```
критична секція (пошук + перестановка вузла)         ≈ 100 нс
частка запитів, що мусять пройти її по черзі:
   точний LRU        1.00
   CLOCK (h = 0.99)  1 − h = 0.01

стеля пропускної здатності = 1 / (частка · критична секція)
   точний LRU   1 / (1.00 · 100 нс) =   10 млн запитів/с
   CLOCK        1 / (0.01 · 100 нс) = 1000 млн запитів/с
```

Замок — це один сервер: скільки б ядер ви не поставили, крізь нього проходить не більше однієї критичної секції за раз. Тому перший рядок — стеля **на весь кеш**, а не на ядро, і додавання ядер її не підіймає. Ба гірше: реальна стеля нижча за розрахункову, бо під тиском лінія із самим замком і лінія з головою списку починають літати між ядрами, а потоки, що не дочекалися, ідуть спати в ядро операційної системи.

Праворуч CLOCK: кожне ядро пише у свій байт у масиві байтів звернення, а замок бере лише промах — при 99 % влучань це 1 % запитів](img/hotpath.svg)
*Правило вибору жертви в обох випадках майже однакове. Різниця в тому, яка частка запитів мусить пройти крізь спільну точку: у точного LRU це всі сто відсотків, бо влучання переставляє вузол, у CLOCK — лише промахи, бо влучання пише байт у своєму місці.*

Напрошується проміжний хід: розрізати кеш на 16 незалежних кешів за хешем ключа, у кожного свій замок. Він і справді допомагає — тиск на кожен замок падає приблизно в шістнадцять разів. Але зверніть увагу, чим за це заплачено: кожен шматок витісняє **свою** жертву зі своєї шістнадцятої частини пам'яті, тож глобального порядку за свіжістю більше немає. Розрізаний на шматки точний LRU — це вже наближення LRU. А якщо наближення однаково доводиться прийняти, варто хоча б вибрати найдешевше з них.

## CLOCK: увесь облік свіжості — один байт

Найдешевше наближення прибирає з влучання не замок, а саму причину замка: спільний запис. У кожного слота є прапорець «до мене зверталися». Влучання ставить свій прапорець в одиницю — і на цьому все. Записи стоять по колу, по колу ходить стрілка, і вся розумова робота відкладена на витіснення: стрілка крокує, одиниці скидає в нулі й дає власникам ще один шанс, а першого-ліпшого власника нуля забирає.

Важливо не переплутати, що саме тут замінили. Хеш-індекс нікуди не подівся — без нього ключ не знайти. CLOCK прибрав **структуру порядку**: список зі своїми перестановками замінено на масив прапорців і одну змінну-стрілку.

```cpp
// CLOCK: кільце слотів + один БАЙТ прапорця на слот (не біт — див. нижче).
template <class K, class V>
class ClockCache {
    struct Slot { K key; V val; };

    std::vector<Slot> slots_;
    std::vector<uint8_t> ref_;                // прапорці звернення
    std::unordered_map<K, uint32_t> index_;
    uint32_t hand_ = 0, cap_;
    uint64_t hits_ = 0, misses_ = 0, evictions_ = 0, steps_ = 0;

public:
    explicit ClockCache(uint32_t cap) : cap_(cap) {
        slots_.reserve(cap_);
        ref_.reserve(cap_);
        index_.reserve(cap_ * 2);
    }

    std::optional<V> get(const K& key) {
        auto it = index_.find(key);
        if (it == index_.end()) { ++misses_; return std::nullopt; }
        ++hits_;
        ref_[it->second] = 1;                 // УВЕСЬ облік свіжості — цей рядок
        return slots_[it->second].val;
    }

    void put(const K& key, V val) {
        if (auto it = index_.find(key); it != index_.end()) {
            slots_[it->second].val = std::move(val);
            ref_[it->second] = 1;
            return;
        }
        uint32_t i;
        if (slots_.size() < cap_) {
            i = static_cast<uint32_t>(slots_.size());
            slots_.push_back(Slot{key, std::move(val)});
            ref_.push_back(1);
        } else {
            i = evict();                      // слот i звільнено й вилучено з індексу
            slots_[i] = Slot{key, std::move(val)};
            ref_[i] = 1;
        }
        index_.emplace(key, i);
    }

    double steps_per_eviction() const {
        return evictions_ ? static_cast<double>(steps_) / evictions_ : 0.0;
    }

private:
    uint32_t evict() {
        for (;;) {
            uint32_t i = hand_;
            hand_ = (hand_ + 1 == cap_) ? 0 : hand_ + 1;
            ++steps_;
            if (ref_[i] == 0) {               // жертва знайдена
                index_.erase(slots_[i].key);  // ключ ще на місці — слот не чіпали
                ++evictions_;
                return i;
            }
            ref_[i] = 0;                      // другий шанс
        }
    }
};
```

Один рядок у цьому коді — не деталь реалізації, а прихована політика: `ref_.push_back(1)` і `ref_[i] = 1` після вставки, тобто **новачок отримує прапорець одиницею**. Це дарує йому цілий оберт стрілки недоторканності — і саме через це CLOCK так само беззахисний перед наскрізним проходом даними, як і LRU: мільйон одноразових ключів заходить із повним імунітетом. Поставте новачкові нуль — і він помре при першому ж наближенні стрілки, якщо до нього не звернулися повторно. Це вже інша політика з іншими вадами, але знати, що ця розвилка сидить в одному символі, корисно: у чужому коді вона ніде не підписана.

### Скільки кроків коштує витіснення

Стрілка може обійти майже все коло — то чи не перетворили ми дешеве влучання на дороге витіснення? Рахунок такий:

```
N запитів, h — частка влучань; промахів (1−h)·N,
кожен промах у повному кеші = рівно одне витіснення.

Кожен крок стрілки або (а) знаходить жертву — таких кроків рівно один
на витіснення, або (б) скидає одиницю в нуль. А одиницю ставить лише
влучання, тож переходів 0→1 за весь час не більше, ніж влучань: h·N.

усього кроків ≤ (1−h)·N + h·N = N              → ≤ 1 крок на ЗАПИТ
кроків на одне витіснення ≤ N / ((1−h)·N) = 1/(1−h)

   h = 0.50 →  до 2 кроків на витіснення
   h = 0.90 →  до 10
   h = 0.99 →  до 100
найдовший окремий обхід ≤ cap + 1 крок (усі прапорці були одиницями)
```

Два висновки, і другий несподіваний. Перший: у перерахунку на запит стрілка коштує не більше одного кроку — це той самий тип міркування, що й [амортизований аналіз](topic:computability/amortized-analysis) будь-якої структури, де дорога операція трапляється рідко й оплачена дешевими. Другий: **чим кращий кеш, тим довші обходи**. При 99 % влучань одне витіснення обходиться в сотню кроків — бо між двома витісненнями стрілці встигли наставити сотню одиниць. Сумарна робота від цього не росте, але вся вона тепер сидить в одній рідкісній операції.

Практично це важить у двох місцях. Обхід відбувається на шляху промаху, який і так повільний (там уже є похід у базу), тож на затримку користувача він майже не впливає. А от якщо стрілка крокує **під ексклюзивним замком**, сотня кроків тримає замок сотню разів довше — і рідкісна операція знову душить часті. Ліки прості: витісняти пачками (за один захід замка звільнити 16 слотів наперед і покласти їх у список вільних) або тримати стрілку у фоновому потоці, який підтримує невеликий запас вільних слотів — так роблять і буферні менеджери баз даних, і кеші об'єктів у пам'яті.

## Чому саме тут зникає замок із читання

Тепер найцікавіше — що ця заміна дала багатопотоковості. Влучання більше не переставляє нічого: воно читає індекс, читає значення й пише один байт **свого** слота. Два потоки, що влучили в різні ключі, не мають жодного спільного місця для запису.

Байт треба записати атомарно — не заради впорядкування, а щоб компілятор не мав права вигадувати з ним фокусів:

```cpp
// C++20: той самий байт у тому самому масиві, але запис атомарний
static_assert(std::atomic_ref<uint8_t>::required_alignment == 1);

std::atomic_ref<uint8_t>(ref_[i]).store(1, std::memory_order_relaxed);
```

`memory_order_relaxed` — це «атомарно, але нічого не впорядковуй»: запис не можна розірвати навпіл і не можна вигадати з повітря, проте інші потоки можуть побачити його із запізненням, і жодні сусідні читання чи записи він не притримує. Саме тому він майже безкоштовний — на x86-64 це звичайна інструкція запису; докладніше про цю шкалу гарантій — [std::atomic і порядок пам'яті](topic:sys-plang-cpp/std-atomic).

І тут же — головна причина, чому в кеші так можна, а в списку не можна. **Прапорець звернення — це підказка, а не істина.** Якщо він загубився чи спізнився, наслідок рівно один: колись стрілка витіснить трохи не той запис і кеш недоотримає частку відсотка влучань. Якщо ж загубиться перестановка вузла в списку, наслідок — порваний список і невизначена поведінка. Одна структура терпить неточність, друга — ні, і саме тому перша обходиться без узгодження між ядрами.

Замок при цьому не зникає зовсім — він переїжджає. Індекс і слоти на шляху промаху таки треба міняти узгоджено, інакше читач побачить напівперезаписаний слот. Але тепер у цьому місці `std::shared_mutex` нарешті працює як задумано: `get` бере його **спільно** (він більше нічого не пише в спільні структури), `put` — ексклюзивно. Читачі йдуть паралельно, серіалізується тільки та частка запитів, що промахнулася.

> 🔧 **Навіщо це.** Різниця між двома кешами не в правилі й не в пам'яті — у частці запитів, які мусять стати в чергу. Перш ніж міняти структуру кеша, порахуйте цю частку для свого трафіку: при 90 % влучань точний LRU серіалізує вдесятеро більше запитів, ніж CLOCK, при 99 % — у сто разів. І тією ж міркою перевіряйте чужі бібліотеки: якщо в описі кеша є слова «точний LRU» і «потокобезпечний», а слова «шардинг» немає, ви знаєте, де стоятиме черга. Заміряти це просто — проженіть той самий бенчмарк на 1, 4 і 16 потоках: у структури із замком на читанні пропускна здатність перестане рости десь на четвертому потоці, а далі почне падати.

Чесно про ціну наближення: `std::shared_mutex` теж не безкоштовний — його лічильник читачів сам є атомарною операцією читання-зміни-запису на одній лінії, і при сотнях тисяч влучань за секунду ця лінія теж почне літати між ядрами. Наступні кроки для тих, кому й цього мало, — шардинг індексу за хешем ключа (у кожного шматка свій `shared_mutex`) і схеми з відкладеним звільненням пам'яті, де читач узагалі не пише нічого спільного; про цей клас прийомів — [структури без замків](topic:sf-tasks/lock-free-basics).

## Пастки

**Посилання, віддане назовні, помирає від наступного `put`.** Спокуса повернути `const V&` замість копії дуже сильна — і це найпідступніша помилка з усіх тут можливих:

```cpp
const V& v = cache.get_ref(key);   // взяли посилання на слот
cache.put(other_key, other_val);   // а цей put витіснив саме наш запис
use(v);                            // читаємо з чужого, уже перезаписаного слота
```

Помилка проявляється рідко (треба, щоб жертвою став саме ваш запис), не падає, а тихо віддає чужі дані — тобто виглядає як «кеш іноді бреше». Виходів три: повертати копію (як у коді вище); повертати `std::shared_ptr<const V>`, якщо значення незмінне й велике — тоді читач тримає його живим сам; або зробити те, що роблять буферні менеджери баз даних, — **прикріплення**: у слота є лічильник читачів, витіснити слот із ненульовим лічильником не можна, і читач зобов'язаний відпустити його явно.

**Ітератори й перерозподіли.** У вузлі спокусливо зберігати `index_.find(key)`, щоб не шукати вдруге, — і це помилка: перебудова хеш-таблиці псує всі ітератори (посилання на елементи, до речі, лишаються дійсними — стандарт розрізняє ці два випадки). Номер слота такою вадою не страждає: він лишається дійсним, доки живий сам кеш. З масивом слотів застереження те саме: `reserve(cap_)` один раз при створенні, і жодного зростання далі; інакше перерозподіл масиву перетворить усі раніше взяті посилання на сміття.

**Витік вузлів і осиротілі записи в індексі.** У версії з `new Node` є два дзеркальні способи все зламати: вилучити з індексу, але забути звільнити вузол (витік), або звільнити вузол, але забути вилучити з індексу (звернення до звільненої пам'яті). Обидва зникають самі, коли слоти живуть у масиві: володіння не переходить нікуди, слот просто перевикористовується. Але один інваріант варто перевіряти в зневаджувальній збірці, бо він ловить усі помилки цього класу за один прохід:

```cpp
void audit() const {
    assert(index_.size() == slots_.size());
    size_t n = 0;
    for (uint32_t i = head_; i != NIL; i = slots_[i].next) {
        auto it = index_.find(slots_[i].key);
        assert(it != index_.end() && it->second == i);   // індекс і список згодні
        ++n;
    }
    assert(n == slots_.size());                          // і в списку всі
}
```

**Хибне спільне використання на масиві прапорців.** Тепер зрозуміло, чому вище стояв байт, а не біт. Якби прапорці лежали упакованими по одному біту, встановлення прапорця стало б читанням-зміною-записом цілого слова — і два потоки, що ставлять сусідні біти, губили б результати одне одного. Це не «трохи неточність»: у моделі пам'яті C++ окремою одиницею є **байт**, тож два записи в різні біти одного байта — це гонка з невизначеною поведінкою, а два записи в різні байти — цілком законна дія, навіть звичайними операціями. Ціна відмови від упаковки для 10 млн записів:

```
прапорці по біту  : 10 000 000 / 8   = 1.25 МБ, 512 слотів на кеш-лінію
прапорці по байту : 10 000 000       = 10 МБ,   64 слоти на кеш-лінію
службових усього (з індексом)        ≈ 500 МБ
```

Вісім мегабайтів різниці на півгігабайта службових даних — не та ціна, за яку варто торгуватися. Апаратне хибне спільне використання, щоправда, лишається й на байтах: 64 сусідніх слоти сидять на одній лінії, і записи з різних ядер усе одно ганяють її туди-сюди — про механізм цього гальмування є окрема тема, [хибне спільне використання кеш-лінії](topic:hw-arch/false-sharing). Але тут воно не смертельне: запис прапорця нікого не чекає, а спізнена підказка нічого не ламає. І головне — **не розсовуйте прапорці по окремих лініях**: вирівнювання кожного на 64 байти зробило б із 10 МБ шістсот, тобто відібрало б у кеша пам'ять, а разом із нею й відсотки влучань — заради проблеми, яка тут не коштує коректності. Вирівнювати варто одне: саму стрілку `hand_` разом із лічильниками витіснень, бо їх справді правлять із різних потоків.

**Вимірювання частки влучань.** Три способи виміряти неправду, усі поширені.

Перший — лічильники. `hits_` і `misses_` у наведеному коді — звичайні числа, і в багатопотоковій збірці їх треба або зробити атомарними, або порахувати окремо в кожного потоку. Робити їх спільними атомарними — найгірший вихід: `fetch_add` на кожному запиті створить рівно ту саму гарячу лінію, яку ми щойно прибирали, і бенчмарк вимірюватиме свої лічильники. Правильно — структура лічильників на потік, вирівняна на кеш-лінію, і підсумовування наприкінці.

Другий — стрічка. Якщо ганяти бенчмарк на **рівномірно випадкових** ключах, усі політики покажуть однакову частку влучань, і вона дорівнюватиме відношенню місткості до розміру універсуму. Це не збіг: коли всі ключі однаково ймовірні, байдуже, які саме з них лежать у кеші. Бенчмарк на рівномірному потоці ключів не може відрізнити LRU від CLOCK від випадкового викидання — він відповідає на інше питання, ніж ви поставили. Потрібна або записана стрічка з продакшену, або хоча б генератор із перекосом популярності.

Третій — межі вимірювання. Не рахуйте промахи, доки кеш наповнюється: перші `cap` запитів промахуються завжди, і на короткому прогоні вони самі й дають усю статистику. І рахуйте запит один раз: типова пара «`get` промахнувся → сходили в базу → `put`» — це **один** промах, а не промах плюс вставка.

І ще одне число, яке варто виводити поруч із часткою влучань у будь-якої реалізації CLOCK: середню кількість кроків стрілки на витіснення. Формула вище дає для неї стелю 1/(1−h); якщо виміряне значення в неї не вкладається, десь прапорці ставлять частіше, ніж на влучанні, — наприклад, їх виставляє фонове прогрівання або обхід, який ви не рахуєте за звернення.
