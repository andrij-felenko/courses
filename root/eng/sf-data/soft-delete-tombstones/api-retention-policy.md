# 📋 Інтерфейс політик утримання даних та конфігурація надгробків

Керування життєвим циклом даних у навантажених архітектурах вимагає суворого узгодженого контракту між трьома системними рівнями: реляційними політиками ізоляції на рівні рядків (Row-Level Security), конфігурацією збирача сміття розподілених дискових рушіїв (LSM Compaction Garbage Collection) та декларативними маніфестами фонових сервісів очищення (Purge Daemons). 

Якщо будь-який із цих рівнів спроєктовано без чіткого інтерфейсу, виникає або випадковий витік неактивних кортежів у користувацькі запити, або аварійна деградація дискової підсистеми через неконтрольоване накопичення мільйонів надгробків.

---

### Контракт реляційного рівня: PostgreSQL Row-Level Security та часткові індекси

У реляційних СУБД головним викликом м'якого видалення є необхідність гарантувати, що звичайні SQL-запити від бізнес-сервісів ніколи не прочитають мертві рядки, тоді як системні процеси аудиту, відновлення та фізичного очищення збережуть повний доступ до всього масиву кортежів.

Механізм RLS інтегрується безпосередньо в планувальник запитів ядра PostgreSQL. Коли для таблиці ввімкнено RLS, етап перезапису запитів (Query Rewriter) прозоро вбудовує предикат політики у синтаксичне дерево кожного оператора `SELECT`, `UPDATE` та `DELETE`. 

Для бізнес-коду це означає, що запит `SELECT * FROM accounts` на етапі виконання автоматично перетворюється на `SELECT * FROM accounts WHERE deleted_at IS NULL`. Оптимізатор запитів враховує цей предикат під час вибору плану виконання: якщо для таблиці створено частковий індекс із тією самою умовою, планувальник обирає швидке сканування компактного індексу замість повного перегляду таблиці.

```sql
-- 1. Увімкнення механізму безпеки на рівні рядків для цільової таблиці
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;

-- За замовчуванням власник таблиці та суперкористувач ігнорують RLS. 
-- Команда FORCE гарантує, що політики застосовуватимуться навіть до власника схеми,
-- що унеможливлює випадкове виконання скриптів без урахування м'якого видалення.
ALTER TABLE accounts FORCE ROW LEVEL SECURITY;

-- 2. Політика для стандартних користувачів та бізнес-сервісів (видимі лише активні рядки)
-- Конструкція USING фільтрує читання (SELECT), а WITH CHECK забороняє створення або 
-- модифікацію рядків, які не відповідають критерію живого запису.
CREATE POLICY active_records_only ON accounts
    FOR ALL
    TO application_user
    USING (deleted_at IS NULL)
    WITH CHECK (deleted_at IS NULL);

-- 3. Політика для аудиторів та фонового сервісу очищення (повний доступ до всіх рядків)
CREATE POLICY audit_and_purge_access ON accounts
    FOR ALL
    TO purge_daemon_user, compliance_auditor
    USING (TRUE)
    WITH CHECK (TRUE);
```

#### Динамічне перемикання контексту через сесійні змінні

Якщо застосунок використовує пул з'єднань із єдиним технічним користувачем бази даних (наприклад, через PgBouncer у режимі Transaction Pooling), створення окремих користувачів БД для кожної ролі є неможливим. У такому разі розділення прав реалізується через змінні сесійного контексту `current_setting()`.

Механізм працює через передачу сесійного прапорця: на початку транзакції адміністративний сервіс надсилає команду `SET LOCAL`, яка змінює поведінку RLS виключно в межах поточного з'єднання до моменту завершення транзакції (`COMMIT` або `ROLLBACK`), не впливаючи на паралельні клієнтські запити.

```sql
-- Створення універсальної контекстної політики
CREATE POLICY dynamic_context_policy ON accounts
    FOR ALL
    USING (
        deleted_at IS NULL 
        OR NULLIF(current_setting('app.override_soft_delete', true), '')::boolean = true
    );
```

Щоб тимчасово отримати доступ до м'яко видалених записів у межах поточної транзакції (наприклад, для відновлення помилково видаленого клієнта), сервіс виконує:

```sql
BEGIN;
-- Встановлюємо локальний прапорець сесії лише на час поточної транзакції
SET LOCAL app.override_soft_delete = 'true';

-- Запит повертає як активні, так і м'яко видалені рядки
SELECT id, email, deleted_at FROM accounts WHERE id = 42;

-- Відновлення запису
UPDATE accounts SET deleted_at = NULL WHERE id = 42;
COMMIT;
```

#### Контракт часткових індексів (Partial Index Specification)

Будь-яка таблиця з м'яким видаленням зобов'язана визначати два типи часткових індексів. Перший індекс захищає від конфліктів унікальності, а другий створює швидкісний канал доступу для фонового процесу фізичного очищення.

Головна перевага часткового індексу полягає в тому, що м'яко видалені рядки взагалі не потрапляють у структуру B-Tree. Це зменшує глибину дерева індексу, дозволяє тримати весь гарячий індекс у кеші оперативної пам'яті (Buffer Pool) і повністю ліквідує деградацію операцій вставки нових записів.

```sql
-- Частковий унікальний індекс: гарантує унікальність email лише серед живих записів
CREATE UNIQUE INDEX idx_accounts_unique_active_email 
    ON accounts (email) 
    WHERE deleted_at IS NULL;

-- Частковий індекс для оптимізації фонового процесу очищення застарілих даних
-- Забезпечує миттєвий пошук кандидатів на фізичне видалення без сканування всієї таблиці
CREATE INDEX idx_accounts_retention_purge 
    ON accounts (deleted_at) 
    WHERE deleted_at IS NOT NULL;
```

### Контракт розподіленого сховища: параметри надгробків Apache Cassandra / ScyllaDB

У незмінних розподілених сховищах на базі LSM-дерев надгробки не видаляються миттєво, оскільки їхня присутність є математичною вимогою для забезпечення кінцевої узгодженості між репліками. Поведінка надгробків конфігурується декларативно на рівні схеми таблиці.

Стратегія ущільнення визначає, яким чином файли SSTable об'єднуються у фоні. Для звичайних реляційно-подібних таблиць використовується `SizeTieredCompactionStrategy` (STCS) або `LeveledCompactionStrategy` (LCS). Для часових рядів (Time-Series) або черг завдань із масовим видаленням найкращим вибором є `TimeWindowCompactionStrategy` (TWCS), оскільки вона дозволяє миттєво видаляти цілі часові вікна файлів SSTable разом з усіма надгробками без необхідності їхнього дорогого побайтового злиття.

```cql
CREATE TABLE user_timeline (
    user_id uuid,
    event_time timestamp,
    payload text,
    PRIMARY KEY (user_id, event_time)
) WITH compaction = {
    'class': 'SizeTieredCompactionStrategy',
    'tombstone_threshold': '0.2',
    'tombstone_compaction_interval': '86400',
    'unchecked_tombstone_compaction': 'true'
}
AND gc_grace_seconds = 864000;
```

#### Специфікація та правила налаштування параметрів надгробків

Параметри життєвого циклу надгробків безпосередньо впливають на баланс між надійністю реплікації та накладними витратами на дисковий простір.

1. **`gc_grace_seconds` (час захисту надгробка):** Ціле число в секундах (за замовчуванням `864000`, тобто 10 діб). Визначає мінімальний час, протягом якого надгробок гарантовано залишається на диску і не знищується під час ущільнення. Цей період надає захисне вікно для відновлення реплік, які тимчасово втратили зв'язок із кластером. Якщо відключений вузол повертається до роботи в межах `gc_grace_seconds`, він отримує інформацію про надгробок через механізми Hinted Handoff або Read Repair. Якщо ж репліка була недоступною довше, ніж триває цей період, її ввімкнення без попереднього повного відновлення (`nodetool repair`) призведе до фатального воскресіння старих видалених даних на всіх вузлах кластера.
2. **`tombstone_threshold` (поріг щільності надгробків):** Дійсне число від 0 до 1 (за замовчуванням `0.2`, тобто 20%). Вказує співвідношення кількості надгробків до загальної кількості рядків усередині одного файлу SSTable. Якщо частка надгробків перевищує встановлений ліміт, файл позначається як пріоритетний кандидат на позачергове злиття, що дозволяє вивільнити дисковий простір достроково.
3. **`tombstone_compaction_interval` (інтервал повторного аналізу):** Мінімальний проміжок часу в секундах (за замовчуванням `86400`, 24 години) між перевірками однієї й тієї самої SSTable на перевищення порогу `tombstone_threshold`. Запобігає циклічному переписуванню великих файлів (I/O Thrashing), якщо надгробки в них ще не досягли віку `gc_grace_seconds`.
4. **`unchecked_tombstone_compaction` (однотабличне ущільнення):** Булевий прапорець (за замовчуванням `false`). Дозволяє рушію запускати ущільнення одного окремого файлу SSTable без необхідності злиття його з іншими сусідніми таблицями, якщо понад 20% його рядків є надгробками, чий вік перевищив `gc_grace_seconds`.

### Декларативна конфігурація сервісу утримання даних (Retention Daemon)

Фоновий демон очищення працює за стандартизованою схемою JSON-маніфесту. Маніфест визначає правила каскадного очищення, розміри безпечних пакетів та інтеграцію зі службою криптографічного стирання (Crypto-shredding).

Схема маніфесту проектується так, щоб забезпечити повну прозорість дій для служб інформаційної безпеки. Кожне правило чітко розмежовує сутності, які підлягають повному фізичному знищенню (наприклад, сесії та персональні маркери), та сутності, які повинні бути знеособлені для збереження фінансового аудиту (наприклад, накладні замовлень, де адреса та номер телефону затираються, але сума транзакції та перелік товарів залишаються).

```json
{
  "$schema": "https://specs.internal/schemas/retention-policy-v1.json",
  "version": "1.0",
  "policy_name": "gdpr_compliant_customer_retention",
  "targets": [
    {
      "schema": "public",
      "table": "users",
      "deletion_column": "deleted_at",
      "primary_key": "id",
      "retention_window_days": 30,
      "batch_size": 5000,
      "throttle_delay_ms": 100,
      "hard_delete_mode": "physical_and_shred",
      "crypto_key_service": {
        "provider": "kms_vault",
        "key_identifier_column": "dek_vault_id",
        "action": "revoke_and_destroy"
      },
      "child_cascades": [
        {
          "table": "user_sessions",
          "foreign_key": "user_id",
          "action": "immediate_hard_delete"
        },
        {
          "table": "orders",
          "foreign_key": "user_id",
          "action": "anonymize_pii_keep_financials",
          "anonymize_columns": ["shipping_address", "phone_number", "billing_name"]
        }
      ]
    }
  ]
}
```

### Сигнатури інтерфейсу ядра фонового очищувача (Purge Engine API)

Для вбудовування в мікросервіси обслуговування баз даних рушій очищення надає програмний контракт з ідемпотентними гарантіями. 

Програмний інтерфейс розроблений з урахуванням обробки помилок конкурентного доступу. Якщо під час видалення чергового батчу виникає тайм-аут блокування (Lock Timeout) через конфлікт із пріоритетною користувацькою транзакцією, рушій не аварійно перериває всю роботу, а здійснює експоненційний відкат (Exponential Backoff), реєструє телеметрію та повторює спробу для наступного діапазону ключів.

:::tabs
@tab C
```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    const char *table_name;
    const char *time_column;
    const char *primary_key;
    uint32_t retention_days;
    uint32_t batch_size;
    uint32_t throttle_sleep_ms;
} PurgePolicyConfig;

typedef struct {
    uint64_t rows_scanned;
    uint64_t rows_purged;
    uint64_t batches_executed;
    uint64_t duration_ms;
    bool completed_without_errors;
} PurgeExecutionStats;

/**
 * Виконує неблокувальне порційне очищення м'яко видалених записів.
 * @param config Декларативна конфігурація таблиці та лімітів
 * @param stats Структура для запису телеметрії виконання
 * @return 0 при успіху, код помилки у разі збою
 */
int execute_chunked_purge(const PurgePolicyConfig *config, PurgeExecutionStats *stats);
```
@tab C++
```cpp
#include <string>
#include <chrono>
#include <expected>
#include <cstdint>

struct PurgePolicyConfig {
    std::string table_name;
    std::string time_column;
    std::string primary_key;
    std::chrono::hours retention_window{24 * 30}; // 30 днів
    uint32_t batch_size{5000};
    std::chrono::milliseconds throttle_delay{100};
};

struct PurgeExecutionStats {
    uint64_t rows_scanned{0};
    uint64_t rows_purged{0};
    uint64_t batches_executed{0};
    std::chrono::milliseconds duration{0};
};

enum class PurgeError {
    ConnectionFailed,
    LockTimeout,
    ForeignKeyViolation,
    KmsShreddingFailed
};

class IPurgeEngine {
public:
    virtual ~IPurgeEngine() = default;
    
    [[nodiscard]] virtual std::expected<PurgeExecutionStats, PurgeError> 
    execute_chunked_purge(const PurgePolicyConfig& config) noexcept = 0;
};
```

#### Обробка крайових випадків реплікації та реляційних каскадів

Під час виконання пакетного видалення сервіс очищення повинен враховувати два критичні фактори виробничого середовища:

1. **Затримка потокової реплікації (Streaming Replication Lag):** Швидке видалення мільйона рядків генерує гігабайти записів WAL. Якщо репліки читання (Read Replicas) не встигають застосовувати WAL-потік, тривалі аналітичні запити на репліках можуть бути примусово скасовані через параметри `max_standby_streaming_delay`. Контракт очищувача повинен перевіряти відставання реплік через системне представлення `pg_stat_replication` і автоматично збільшувати затримку `throttle_delay_ms`, якщо лаг перевищує допустимий поріг (наприклад, 5 секунд).
2. **Блокування неіндексованих зовнішніх ключів:** Якщо таблиця, що очищується, є батьківською для іншої таблиці, в якій стовпець зовнішнього ключа не має B-Tree індексу, кожна операція `DELETE` викличе повне сканування (Sequential Scan) дочірньої таблиці зі спільним блокуванням. Це призводить до миттєвого зависання всієї системи. Контракт вимагає попередньої валідації наявності індексів на всіх пов'язаних зовнішніх ключах перед запуском конвеєра.

Завдяки чітко визначеному контракту сервіс очищення гарантує безпечне поступове видалення записів без виникнення взаємних блокувань (Deadlocks), переповнення журналів транзакцій та неконтрольованої деградації дискових масивів.
