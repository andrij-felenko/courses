# 🧮 Розрахунок розгалуження, висоти та вартості I/O у B-деревах

Ефективність дискового індексу визначається кількістю операцій введення-виведення (I/O), необхідних для знаходження запису серед великого масиву даних. На відміну від структур в оперативній пам'яті, де вартість переходу за покажчиком вимірюється наносекундами, звернення до дискового блоку вимагає читання цілої сторінки фіксованого розміру. Нижче наведено математичний аналіз коефіцієнта розгалуження, висоти дерева та витрат на обслуговування сторінок.

## 1. Геометрія сторінки та коефіцієнт розгалуження (Fan-out)

Дискова сторінка індексу має фіксований фізичний розмір `P` (типово `P = 8192` байти у PostgreSQL або `P = 16384` байти у MySQL InnoDB). Сторінка містить службовий заголовок розміром `H`, масив лінійних покажчиків (line pointers), корисне навантаження ключів і спеціальну кінцеву зону (opaque/special space).

Позначимо параметри елементів індексу:
- `P` — загальний розмір сторінки в байтах;
- `H` — фіксований розмір заголовка сторінки (`PageHeaderData`, 24 байти) разом зі спеціальною зоною `S` (у B-дереві 16 байтів на `High Key` та `RightLink`), тобто `H = 24 + 16 = 40` байтів;
- `K` — розмір індексованого ключа в байтах (наприклад, 8 байтів для цілого числа `BIGINT`);
- `V_p` — розмір покажчика на дочірню сторінку у внутрішньому вузлі (8 байтів);
- `V_t` — розмір ідентифікатора кортежу (TID: `BlockNumber` + `OffsetNumber`, 6 байтів у листовому вузлі);
- `L` — розмір елемента масиву покажчиків `ItemId` на сторінці (4 байти).

Розмір одного запису у внутрішньому вузлі (маршрутизаторі) `R_int`:
```
R_int = K + V_p + L
      = 8 + 8 + 4         [підстановка розмірів: ключ 8Б, покажчик сторінки 8Б, ItemId 4Б]
      = 20 байтів         [арифметика додавання]
```

Розмір одного запису в листовому вузлі (листі) `R_leaf`:
```
R_leaf = K + V_t + L
       = 8 + 6 + 4        [підстановка розмірів: ключ 8Б, TID 6Б, ItemId 4Б]
       = 18 байтів        [арифметика додавання]
```

Теоретична максимальна місткість внутрішнього вузла (максимальний коефіцієнт розгалуження `B_max`):
```
B_max = ⌊(P - H) / R_int⌋
      = ⌊(8192 - 40) / 20⌋    [підстановка: сторінка 8192Б, заголовок 40Б, запис 20Б]
      = ⌊8152 / 20⌋           [корисний простір сторінки]
      = 407 нащадків          [округлення вниз до цілого числа]
```

Максимальна місткість листового вузла `C_leaf`:
```
C_leaf = ⌊(P - H) / R_leaf⌋
       = ⌊(8192 - 40) / 18⌋   [підстановка: сторінка 8192Б, заголовок 40Б, запис 18Б]
       = ⌊8152 / 18⌋          [корисний простір сторінки]
       = 452 записи           [округлення вниз до цілого числа]
```

## 2. Коефіцієнт заповнення сторінок (Fill Factor)

У реальних умовах вставки ключів не відбуваються виключно в порядку зростання. При випадковому рівномірному розподілі ключів сторінки заповнюються до межі й розщеплюються навпіл (50/50 split).

Згідно з класичною теоремою Яо (Yao's B-tree analysis, 1978), середній коефіцієнт заповнення випадково збудованого B-дерева асимптотично наближається до натурального логарифма двох:

```
f_avg = ln(2)
      ≈ 0.69315           [теорема Яо: середнє заповнення випадкового B-дерева]
```

При практичному розрахунку приймають стандартний коефіцієнт заповнення `f = 0.70` (70%). Звідси випливає ефективний коефіцієнт розгалуження внутрішніх вузлів `B_eff` та ефективна місткість листів `C_eff`:

```
B_eff = ⌊f · B_max⌋
      = ⌊0.70 · 407⌋      [коефіцієнт заповнення 70% від максимуму 407]
      = 284 нащадки       [округлення вниз до цілого числа]
```

```
C_eff = ⌊f · C_leaf⌋
      = ⌊0.70 · 452⌋      [коефіцієнт заповнення 70% від максимуму 452]
      = 316 записів       [округлення вниз до цілого числа]
```

## 3. Розрахунок висоти дерева залежно від кількості рядків

B+дерево висоти `h` (де корінь має висоту `h = 1`) складається з одного кореневого вузла, `h - 2` рівнів проміжних вузлів та одного рівня листових вузлів на дні.

Загальна кількість листових сторінок `L_pages` для збереження `N` записів таблиці:
```
L_pages = ⌈N / C_eff⌉
```

Кількість внутрішніх сторінок на рівні над листами:
```
I_1 = ⌈L_pages / B_eff⌉
```

Кількість внутрішніх сторінок на рівні `k` над попереднім:
```
I_k = ⌈I_(k-1) / B_eff⌉
```

Процес повторюється, доки кількість сторінок на рівні не зменшиться до 1 (коренева сторінка). Загальна висота дерева `h` аналітично виражається через логарифм:

```
h = 1 + ⌈log_(B_eff)(L_pages)⌉
  = 1 + ⌈ln(⌈N / C_eff⌉) / ln(B_eff)⌉    [перехід до натурального логарифма]
```

### Покроковий розрахунок для таблиці на 100 000 000 рядків

Нехай таблиця містить `N = 100 000 000` (сто мільйонів) кортежів. Обчислимо необхідну кількість сторінок та висоту B+дерева:

**Крок 1: Кількість листових сторінок**
```
L_pages = ⌈100 000 000 / 316⌉
        = ⌈316 455.696⌉   [ділення 100 млн на 316 записів на сторінку]
        = 316 456 сторінок [округлення вгору до цілої сторінки]
```

**Крок 2: Внутрішній рівень 1 (над листами)**
```
I_1 = ⌈316 456 / 284⌉
    = ⌈1114.28⌉           [розподіл 316 456 сторінок по 284 покажчики]
    = 1115 сторінок       [округлення вгору]
```

**Крок 3: Внутрішній рівень 2**
```
I_2 = ⌈1115 / 284⌉
    = ⌈3.926⌉             [розподіл 1115 сторінок по 284 покажчики]
    = 4 сторінки          [округлення вгору]
```

**Крок 4: Кореневий рівень**
```
I_3 = ⌈4 / 284⌉
    = 1 сторінка          [одна коренева сторінка покриває 4 нащадки]
```

Загальна висота індексу:
```
h = 1 + 2 + 1             [корінь + 2 внутрішні рівні + листи]
  = 4 рівні               [підсумок висоти дерева]
```

Загальна кількість сторінок індексу:
```
Total_pages = 1 + 4 + 1115 + 316 456  [сума сторінок усіх рівнів]
            = 317 576 сторінок        [загальна кількість сторінок]
```

Загальний обсяг індексу на диску:
```
Size_bytes = 317 576 · 8192           [множення кількості сторінок на розмір блоку]
           = 2 601 582 592 байти      [точний обсяг у байтах]
           ≈ 2.42 ГБ                  [переведення у гігабайти]
```

Для порівняння: купа самої таблиці (при середньому розмірі рядка 200 байтів, близько 35 рядків на сторінку) займає:
```
Heap_pages = ⌈100 000 000 / 35⌉       [ділення кортежів на місткість сторінки купи]
           ≈ 2 857 142 сторінки       [кількість блоків купи]
           ≈ 21.8 ГБ                  [обсяг таблиці на диску]
```
Індекс розміром 2.42 ГБ складає лише 11% від обсягу таблиці.

## 4. Порівняння вартості пошуку: Двійкове дерево проти B-дерева

Порівняємо теоретичні та реальні витрати введення-виведення для пошуку одного рядка серед `N = 100 000 000` записів.

### Двійкове збалансоване дерево (AVL / Red-Black)
У двійковому дереві кожен вузол зберігає один ключ і має коефіцієнт розгалуження `B = 2`.
```
h_bst = ⌈log_2(N)⌉
      = ⌈log_2(100 000 000)⌉          [висота двійкового дерева для 100 млн елементів]
      = ⌈26.575⌉                      [логарифм за основою 2]
      = 27 переходів                  [округлення вгору]
```
Якщо кожен вузол розміщений в окремому дисковому блоці, пошук вимагає 27 дискових звернень. На магнітному диску (HDD) із затримкою доступу 8 мс:
```
T_bst_hdd = 27 · 0.008 с              [27 читань по 8 мс на пошук головки HDD]
          = 0.216 с                   [216 мілісекунд]
```
На NVMe SSD із затримкою читання блоку 50 мкс:
```
T_bst_ssd = 27 · 0.000050 с           [27 читань по 50 мкс на NVMe SSD]
          = 0.00135 с                 [1.35 мілісекунди]
```

### B+дерево на сторінках 8 КБ
Висота дерева `h = 4`. Пошук виконує рівно 4 операції читання сторінок індексу плюс 1 читання сторінки купи за знайденим TID, загалом 5 сторінок.

У реальній СУБД буферний пул оперативної пам'яті (shared buffers) кешує верхні рівні дерева:
- Корінь (1 сторінка = 8 КБ) кешується зі 100% імовірністю.
- Рівень 2 (4 сторінки = 32 КБ) кешується зі 100% імовірністю.
- Рівень 1 (1115 сторінок = 8.9 МБ) повністю вміщується в кеші навіть бюджетного сервера.

Отже, перші 3 звернення відбуваються в оперативній пам'яті (RAM hit, час доступу близько 100 наносекунд). Фізичне читання з диска вимагається лише для:
1. Однієї листової сторінки індексу.
2. Однієї сторінки купи з даними кортежу.

Фактичні дискові витрати:
```
IO_actual = 1 + 1                     [1 листова сторінка індексу + 1 сторінка купи]
          = 2 операції I/O            [дискові звернення за промаху в кеші]
```
Час виконання на NVMe SSD:
```
T_btree_ssd = 3 · 0.0000001 с + 2 · 0.000050 с  [3 звернення в RAM + 2 читання з NVMe]
            ≈ 0.0001003 с                       [приблизно 0.1 мілісекунди]
```
Швидкодія зростає в 13 разів порівняно з двійковим деревом на SSD і в 50 разів на механічному накопичувачі.

## 5. Ймовірність розщеплення сторінки при випадковій вставці

При додаванні нового кортежу в листовий вузол він може виявитися переповненим. Якщо на сторінці вже міститься `C_max` елементів, відбувається розщеплення (page split), що вимагає виділення нової сторінки та запису двох блоків замість одного, а також вставки розділового ключа в батьківський вузол.

Ймовірність того, що довільна вставка у випадково обрану листову сторінку спричинить розщеплення:
```
P_split = 1 / C_eff
        = 1 / 316                     [імовірність потрапляння в переповнену сторінку]
        ≈ 0.00316                     [близько 0.316%]
```
Це означає, що лише одна з приблизно 316 операцій `INSERT` призводить до розщеплення листової сторінки.

Ймовірність каскадного розщеплення внутрішнього вузла рівня 1:
```
P_split_internal = P_split · (1 / B_eff)
                 = 0.00316 · (1 / 284) [імовірність каскадного переповнення вузла]
                 ≈ 0.0000111           [близько 0.0011%]
```
Ймовірність розщеплення кореня (збільшення висоти дерева):
```
P_split_root = P_split_internal · (1 / B_eff)
             ≈ 3.9 · 10⁻⁸              [імовірність розщеплення кореня]
```
Завдяки високому коефіцієнту розгалуження витрати на зміну структури дерева амортизуються, роблячи середню вартість операції вставки `O(log_B N)` практично константною.
