# 📋 Структура двійкового чанка та контракт індексу TSDB

Архітектура систем збереження часових рядів (на прикладі промислового стандарту Prometheus V2/V3 TSDB) спирається на суворе розділення даних на незмінні блоки фіксованої часової тривалості (за замовчуванням дві години). Кожен такий блок являє собою автономний каталог у файловій системі операційної системи. Він містить бінарні файли сегментів чанків зі стисненими вимірами, двійковий інвертований індекс для селекції рядів за мітками, метадані часового діапазону та бітовий журнал логічно видалених інтервалів.

Така фізична організація гарантує, що старі часові діапазони залишаються незмінними, захищеними від випадкової модифікації та готовими для прямого відображення в пам'ять процесу без ризику блокування або гонки потоків.

## Структура каталогу блоку на файловій системі

Кожен блок отримує унікальне ім'я у форматі ULID (англ. *Universally Unique Lexicographically Sortable Identifier*), чиї старші 48 бітів кодують час створення блоку:

```
data/01J5K4M2E9VBN3R7P8X9QW12ZY/
├── meta.json       # Метадані блоку: часовий діапазон, кількість рядів, статистика
├── tombstones      # Інтервали логічно видалених точок (minTime, maxTime для seriesID)
├── chunks/         # Сегментовані файли зі стисненими точками часових рядів
│   ├── 000001      # Файл чанків розміром до 512 МБ (Gorilla bitstream + CRC32)
│   └── 000002
└── index           # Інвертований індекс: словник символів, таблиці postings, ряди
```

Каталог блоку є повністю самодостатнім: його можна скопіювати на інший сервер, перенести в резервний архів або відправити в хмарне об'єктне сховище (Amazon S3, Google Cloud Storage) без необхідності читання будь-яких інших файлів бази даних.

## Формат метаданих блоку: `meta.json`

Файл `meta.json` зберігає дескриптор блоку у форматі JSON і зчитується сервером під час ініціалізації для побудови глобального дерева блоків у пам'яті:

| Поле | Тип | Опис призначення |
| :--- | :--- | :--- |
| `ulid` | `string` | Унікальний 128-бітний ідентифікатор блоку (сортований за часом ULID) |
| `minTime` | `int64` | Мінімальна часова мітка вимірів у блоці (UNIX-час у мілісекундах) |
| `maxTime` | `int64` | Максимальна часова мітка вимірів у блоці (UNIX-час у мілісекундах) |
| `stats.numSamples` | `uint64` | Загальна кількість збережених вимірів у всіх чанках блоку |
| `stats.numSeries` | `uint64` | Кількість унікальних часових рядів, присутніх у блоці |
| `stats.numChunks` | `uint64` | Загальна кількість створених чанків у підкаталозі `chunks/` |
| `compaction.level` | `int` | Рівень ущільнення блоку (1 = початковий 2h блок, 2 = 8h, 3 = 24h) |
| `compaction.sources`| `array[ulid]` | Список ідентифікаторів вихідних блоків, що увійшли до цього блоку |
| `version` | `int` | Версія формату метаданих (наприклад, `1`) |

Значення `minTime` та `maxTime` дозволяють планувальнику запитів миттєво відсікати цілі блоки файлів, якщо часове вікно користувацького запиту не перетинається із діапазоном блоку. Це запобігає зайвому навантаженню на дискову підсистему під час виконання точкових діапазонних вибірок.

## Двійковий макет сегмента чанків: `chunks/000001`

Файли в підкаталозі `chunks/` мають фіксований ліміт розміру (за замовчуванням 512 МБ). Коли поточний файл сегмента заповнюється, створюється наступний файл `000002`. Це запобігає фрагментації та спрощує роботу механізму відображення пам'яті.

Структура заголовка файлу сегмента:

```
+-----------------------------------------------------------------------+
| Magic Number (4 байти): 0x85BB00EC                                    |
+-----------------------------------------------------------------------+
| Version (1 байт): 0x01                                                |
+-----------------------------------------------------------------------+
| Padding (3 байти): 0x00 0x00 0x00                                     |
+-----------------------------------------------------------------------+
| [Послідовність чанків вимірів ...]                                   |
+-----------------------------------------------------------------------+
```

Макет кожного окремого чанка в сегменті:

| Зміщення | Довжина (байти) | Тип | Опис поля |
| :--- | :--- | :--- | :--- |
| `0` | `4` | `uint32` | Довжина тіла чанка `L` (без урахування поля довжини та CRC32) |
| `4` | `1` | `uint8` | Тип стиснення корисного навантаження (`1` = Gorilla / XOR) |
| `5` | `2` | `uint16` | Кількість вимірів `N` у цьому чанку (зазвичай до 120 точок) |
| `7` | `L - 3` | `bytes` | Стиснений бітовий потік точок `(timestamp, value)` за алгоритмом Gorilla |
| `4 + L` | `4` | `uint32` | Контрольна сума CRC32-Castagnoli (обчислюється від байтів `[4 .. 4+L-1]`) |

Контрольна сума CRC32 захищає дані від тихого пошкодження бітів на дискових накопичувачах. Якщо під час розпакування чанка розрахована сума не збігається із записаною, рушій ізолює пошкоджений чанк і генерує попередження без аварійної зупинки всього вузла бази даних.

## Двійковий макет файлу індексу: `index`

Файл `index` розташовується в корені каталогу блоку. Він проектується таким чином, щоб за будь-якою комбінацією селекторів міток знайти точні байтові зміщення потрібних чанків у файлах сегментів без повного зчитування індексу в оперативну пам'ять.

Файл складається з кількох послідовних таблиць і завершується змістом TOC (англ. *Table of Contents*):

```
+-----------------------------------------------------------------------+
| Magic Number (4 байти): 0xBAAA7957                                    |
+-----------------------------------------------------------------------+
| Version (1 байт): 0x02                                                |
+-----------------------------------------------------------------------+
| Таблиця символів (Symbols Table)                                      |
+-----------------------------------------------------------------------+
| Секція описів рядів (Series Section)                                  |
+-----------------------------------------------------------------------+
| Секція списків входжень (Postings Section)                            |
+-----------------------------------------------------------------------+
| Таблиця зміщень списків входжень (Postings Offset Table)              |
+-----------------------------------------------------------------------+
| Зміст файлу (TOC: 6 зміщень по 8 байтів)                              |
+-----------------------------------------------------------------------+
| Magic Number TOC (8 байтів): 0x0107FFE97D008B33                       |
+-----------------------------------------------------------------------+
| CRC32 (4 байти)                                                       |
+-----------------------------------------------------------------------+
```

### 1. Таблиця символів (Symbols Table)
Зберігає дедуплікований масив усіх унікальних назв міток і їхніх текстових значень. Усі рядки впорядковані лексикографічно. Це дозволяє використовувати бінарний пошук для знаходження символу за `O(log S)`:
- `len` (`uint32`): загальна кількість рядків у словнику.
- Масив записів: кожен запис складається з довжини у форматі `uvarint` та масиву UTF-8 байтів без нульового байта на кінці.

### 2. Секція опису ряду (Series Section)
Для кожного часового ряду із внутрішнім числовим номером `SeriesID` зберігається дескриптор:
- `num_labels` (`uvarint`): кількість пар міток цього ряду.
- Масив пар `(name_symbol_idx, value_symbol_idx)` у вигляді числових індексів у таблиці символів.
- `num_chunks` (`uvarint`): кількість чанків вимірів, що належать цьому ряду в межах поточного 2-годинного блоку.
- Масив чанкових дескрипторів:
  - `min_time` (`varint`): часова мітка першого виміру в чанку.
  - `max_time` (`varint`): часова мітка останнього виміру в чанку.
  - `file_ref` (`uint64`): складений покажчик на місцезнаходження чанка на диску (старші 16 бітів визначають порядковий номер файлу в каталозі `chunks/`, а молодші 48 бітів — пряме байтове зміщення всередині файлу).

### 3. Секція списків входжень (Postings Section)
Для кожної пари `Ім'я_мітки=Значення_мітки` зберігається відсортований за зростанням список усіх `SeriesID`, які містять цю пару. 
Списки ідентифікаторів стискаються за допомогою бітових карт Roaring Bitmaps або різницевого пакування varint. Roaring Bitmaps адаптивно обирають найкращу внутрішню структуру для кожного діапазону значень:
- Для розріджених списків (мало рядів) використовується простий відсортований масив 16-бітних цілих чисел (`ArrayContainer`).
- Для щільних списків (велика кількість рядів) використовується фіксована бітова маска довжиною 8192 байти (65536 бітів, `BitmapContainer`).
- Для неперервних діапазонів ідентифікаторів застосовується RLE-кодування інтервалів (`RunContainer`).

Таке гібридне представлення гарантує, що операції об'єднання та перетину списків виконуються за лічені мікросекунди навіть над мільйонами рядів.

### 4. Таблиця зміщень списків входжень (Postings Offset Table)
Містить відображення між індексами термів та абсолютними байтовими зміщеннями їхніх списків postings всередині файлу `index`. Завдяки цьому рушій не сканує весь індекс, а здійснює прямий перехід до потрібного списку ідентифікаторів за один виклик читання пам'яті через зміщення у файлі.

## Алгоритм виконання селекторів запиту

Під час обчислення аналітичного запиту (наприклад, `http_requests_total{status="500", method="POST"}` у часовому інтервалі від `T_start` до `T_end`):

1. **Пошук термів у словнику:** Через бінарний пошук у таблиці символів знаходяться індекси для рядків `__name__`, `http_requests_total`, `status`, `500`, `method`, `POST`.
2. **Зчитування списків Postings:** За допомогою таблиці зміщень Postings Offset Table з диску підвантажуються відповідні списки `SeriesID`:
   - `Postings(__name__="http_requests_total")`
   - `Postings(status="500")`
   - `Postings(method="POST")`
3. **Обчислення перетину (Merge Join):** Виконується порозрядне бітове множення (Bitwise AND) над отриманими бітовими картами:
   `MatchedSeries = Postings(__name__) ∩ Postings(status) ∩ Postings(method)`.
4. **Фільтрація за часовим вікном:** Для кожного знайденого `SeriesID ∈ MatchedSeries` зчитується масив дескрипторів чанків. Відбираються лише ті покажчики `file_ref`, для яких виконується умова перетину інтервалів:
   `max_time ≥ T_start` та `min_time ≤ T_end`.
5. **Нульове копіювання (Zero-Copy Read):** Відібрані чанки зчитуються безпосередньо з файлів у каталозі `chunks/` через системний виклик `mmap()`. Бітовий потік передається декодеру Gorilla для видобування масивів чисел у конвеєр векторних обчислень.
