# 📋 Специфікація двійкового протоколу підготовлених виразів

Реляційні бази даних використовують спеціалізовані двійкові протоколи прикладного рівня для взаємодії між клієнтськими бібліотеками та сервером. На відміну від текстового протоколу (де запит передається як один суцільний рядок SQL, а результати повертаються у вигляді ASCII-тексту), протокол підготовлених виразів розбиває взаємодію на окремі повідомлення зі строго типізованими бінарними кодами.

Це забезпечує дві критичні переваги: усунення повторного синтаксичного аналізу запитів на боці сервера та ліквідацію витрат на серіалізацію і десеріалізацію даних. Замість того, щоб кодувати 64-бітне число в рядок із десяткових цифр на клієнті та парсити його функцією `strtoll` на сервері, значення передається безпосередньо у вигляді 8 сирих байтів пам'яті.

Нижче наведено технічну специфікацію двох найпоширеніших двійкових протоколів: **PostgreSQL Extended Query Protocol (v3.0)** та **MySQL Binary Protocol (Client/Server)**.

## 1. PostgreSQL Extended Query Protocol (Frontend / Backend v3.0)

Протокол розширених запитів PostgreSQL використовує 5-фазний цикл повідомлень: `Parse` → `Bind` → `Describe` → `Execute` → `Sync`.

### Механізм фреймінгу та буферизації повідомлень

Кожен мережевий пакет протоколу PostgreSQL починається з 1 байта ідентифікатора типу повідомлення (символ ASCII) та 4 байтів довжини повідомлення (ціле число Big-Endian `Int32`, що включає власну довжину, але не включає байт типу). Така структура дозволяє мережевому стеку на базі системних викликів `epoll` чи `kqueue` зчитувати точний розмір фрейму без попереднього парсингу тіла.

```
+---------------+-------------------+-----------------------------------+
| Байт типу (1B)| Довжина Int32 (4B)| Тіло повідомлення (N - 4 байтів)  |
+---------------+-------------------+-----------------------------------+
```

### Повідомлення клієнта (Frontend)

| Байт типу | Назва повідомлення | Призначення та структура тіла |
|---|---|---|
| `'P'` (`0x50`) | **Parse** | Реєструє та компілює шаблон запиту.<br>• `String`: ім'я підготовленого виразу (пустий рядок `""` позначає безіменний вираз).<br>• `String`: текст SQL-шаблону з позиційними параметрами `$1`, `$2`.<br>• `Int16`: кількість типів параметрів.<br>• `Int32[]`: масив OID типів даних (0 — визначити автоматично). |
| `'B'` (`0x52`) | **Bind** | Створює портал (Portal), прив'язуючи конкретні значення до підготовленого виразу.<br>• `String`: ім'я порталу (пустий рядок `""` — безіменний).<br>• `String`: ім'я підготовленого виразу.<br>• `Int16`: кількість кодів форматів параметрів (`k`).<br>• `Int16[]`: коди форматів (`0` = текст, `1` = двійковий Big-Endian).<br>• `Int16`: кількість значень параметрів (`n`).<br>• Для кожного параметра: `Int32` (довжина байтів; `-1` позначає `NULL`) + масив сирих байтів.<br>• `Int16`: кількість кодів форматів для стовпців результату + `Int16[]`. |
| `'D'` (`0x44`) | **Describe** | Запитує метадані виразу або порталу.<br>• `Byte`: `'S'` для підготовленого виразу, `'P'` для порталу.<br>• `String`: ім'я об'єкта. |
| `'E'` (`0x45`) | **Execute** | Запускає виконання порталу.<br>• `String`: ім'я порталу.<br>• `Int32`: максимальна кількість рядків для повернення (0 = без обмеження). |
| `'S'` (`0x53`) | **Sync** | Завершує конвеєр розширеного протоколу, закриває неявну транзакцію та сигналізує серверу скинути буфери. Не містить додаткового тіла (довжина = 4). |
| `'C'` (`0x43`) | **Close** | Звільняє пам'ять виразу або порталу на сервері.<br>• `Byte`: `'S'` (вираз) або `'P'` (портал).<br>• `String`: ім'я об'єкта. |

### Повідомлення відповіді сервера (Backend)

| Байт типу | Назва відповіді | Опис вмісту |
|---|---|---|
| `'1'` (`0x31`) | **ParseComplete** | Підтвердження успішного синтаксичного аналізу та компіляції. |
| `'2'` (`0x32`) | **BindComplete** | Підтвердження успішного зв'язування параметрів у портал. |
| `'t'` (`0x74`) | **ParameterDescription** | Список очікуваних OID типів для параметрів виразу. |
| `'T'` (`0x54`) | **RowDescription** | Опис колонок результату: назва поля, OID таблиці, номер атрибута, OID типу, розмір, модифікатор типу, код формату (текст/бінарний). |
| `'D'` (`0x44`) | **DataRow** | Кортеж даних: `Int16` (кількість стовпців), далі для кожного стовпця — `Int32` (довжина) та сирі байти поля. |
| `'C'` (`0x43`) | **CommandComplete** | Тег завершення команди (наприклад, `SELECT 42`, `INSERT 0 1`). |
| `'Z'` (`0x5A`) | **ReadyForQuery** | Стан сервера (`'I'` = Idle, `'T'` = у транзакції, `'E'` = помилка транзакції). |
| `'E'` (`0x45`) | **ErrorResponse** | Повідомлення про помилку з полями (`Severity`, `SQLSTATE`, `Message`, `Detail`, `Hint`, `Position`). |

### Покроковий аналіз пакетного потоку (Packet Trace)

Розглянемо реальну послідовність байтів, яка передається сокетом TCP під час виконання запиту `SELECT balance FROM accounts WHERE id = $1` зі значенням параметра `42` (`int64`):

1. **Клієнт надсилає повідомлення `Parse`:**
   - Байт `0x50` (`'P'`).
   - Довжина `0x0000003B` (59 байтів).
   - Рядок імені виразу: `"stmt_1\0"`.
   - Рядок SQL-шаблону: `"SELECT balance FROM accounts WHERE id = $1\0"`.
   - Кількість параметрів: `0x0001` (1).
   - OID типу `int8` (BigInt): `0x00000014` (20 у десятковій системі).

2. **Клієнт надсилає повідомлення `Bind` у тому ж мережевому буфері (Pipelining):**
   - Байт `0x52` (`'B'`).
   - Довжина `0x00000021` (33 байти).
   - Рядок імені порталу: `""\0` (безіменний портал).
   - Рядок імені виразу: `"stmt_1\0"`.
   - Кількість форматів параметрів: `0x0001` (1 формат).
   - Код формату: `0x0001` (двійковий Big-Endian).
   - Кількість параметрів: `0x0001` (1 параметр).
   - Довжина значення: `0x00000008` (8 байтів).
   - Значення параметра (число 42 у Big-Endian): `0x000000000000002A`.
   - Кількість форматів колонок результату: `0x0001` (1 формат).
   - Код формату результату: `0x0001` (двійковий формат для читання стовпця `balance`).

3. **Клієнт додає повідомлення `Execute` та `Sync`:**
   - Байт `0x45` (`'E'`), довжина `9`, ім'я порталу `""\0`, максимальна кількість рядків `0x00000000` (без обмеження).
   - Байт `0x53` (`'S'`), довжина `4` (команда синхронізації транзакційного стану).

4. **Сервер надсилає пакет відповідей після обробки конвеєра:**
   - `ParseComplete` (`'1'`, довжина 4).
   - `BindComplete` (`'2'`, довжина 4).
   - `DataRow` (`'D'`, довжина 18): 1 стовпець, довжина 8 байтів, значення IEEE-754 double (наприклад, баланс `1500.50` у шістнадцятковому виді `0x4097720000000000`).
   - `CommandComplete` (`'C'`, довжина 13, текст `"SELECT 1\0"`).
   - `ReadyForQuery` (`'Z'`, довжина 5, статус `'I'` — Idle поза транзакцією).

### Обробка помилок та синхронізаційний бар'єр

Якщо під час виконання конвеєра одне з повідомлень спричиняє помилку (наприклад, повідомлення `Bind` передає несумісний тип параметра або посилається на неіснуючий вираз), сервер негайно надсилає пакет `ErrorResponse` (`'E'`).

Після генерації помилки сервер входить у стан блокування конвеєра: усі наступні вхідні повідомлення (`Describe`, `Execute`) повністю ігноруються без виконання. Сервер зчитує та скидає байти вхідного сокета доти, доки не зустріне повідомлення `Sync` (`'S'`).

Повідомлення `Sync` виступає синхронізаційним бар'єром. Отримавши `Sync`, сервер скидає стан поточної перерваної операції, переводить транзакцію у стан помилки (якщо вона була відкрита) та надсилає клієнту пакет `ReadyForQuery` зі статусом `'E'` (Error in transaction) або `'I'` (Idle). Клієнтський драйвер гарантовано знає, що після отримання `ReadyForQuery` мережевий потік відновлено, а наступна команда буде оброблена в чистому стані.

## 2. MySQL Binary Protocol (Client / Server)

У протоколі MySQL підготовлені вирази ідентифікуються 4-байтовим цілим дескриптором `statement_id`, який сервер виділяє під час виклику `COM_STMT_PREPARE`.

### Команди клієнта (MySQL Command Packets)

Кожен пакет MySQL починається з 3 байтів довжини корисного навантаження (Little-Endian) та 1 байта номера послідовності (Sequence ID), після чого йде 1 байт коду команди:

```
+---------------------+-------------------+-------------------+------------------------+
| Довжина payload (3B)| Sequence ID (1B)  | Код команди (1B)  | Тіло команди (N байтів)|
+---------------------+-------------------+-------------------+------------------------+
```

| Код команди | Назва команди | Параметри корисного навантаження |
|---|---|---|
| `0x16` | **COM_STMT_PREPARE** | Текстовий рядок SQL-запиту з параметрами `?` (без завершального нуль-байта). |
| `0x17` | **COM_STMT_EXECUTE** | • `Int32`: `statement_id`.<br>• `Byte`: прапорці курсора (`0x00` = `CURSOR_TYPE_NO_CURSOR`, `0x01` = `CURSOR_TYPE_READ_ONLY`).<br>• `Int32`: ітераційний лічильник (завжди `1`).<br>• Якщо `num_params > 0`:<br>  - **Null-Bitmap**: бітова маска довжиною `(num_params + 7) / 8` байтів, де встановлений біт означає значення `NULL`.<br>  - `Byte`: прапорець `new_params_bound_flag` (1 — типи передаються, 0 — типи ті самі).<br>  - `Int16[]`: масив типів параметрів (по 2 байти на параметр: код типу та прапорець signed/unsigned).<br>  - **Binary Values**: двійкові байти значень для всіх параметрів, які не позначені як `NULL` у масці. |
| `0x18` | **COM_STMT_SEND_LONG_DATA** | Передача великих бінарних об'єктів (BLOB/CLOB) частинами до виклику `EXECUTE`.<br>• `Int32`: `statement_id`.<br>• `Int16`: номер параметра.<br>• `Byte[]`: фрагмент бінарних даних. |
| `0x19` | **COM_STMT_CLOSE** | Закриття та деалокація підготовленого виразу.<br>• `Int32`: `statement_id`. Відповідь від сервера не очікується. |
| `0x1A` | **COM_STMT_RESET** | Скидання стану зв'язування та видалення раніше завантажених довгих даних `LONG_DATA`.<br>• `Int32`: `statement_id`. |

### Формат відповіді сервера на підготовку (COM_STMT_PREPARE_OK)

Якщо компіляція успішна, сервер повертає пакет `0x00` наступної структури:

```
+-----------------------------+------------------------------------------------------+
| Поле                        | Тип і розмір                                         |
+-----------------------------+------------------------------------------------------+
| status_flag                 | 1 байт (0x00 = OK)                                   |
| statement_id                | 4 байти (Int32 Little-Endian)                        |
| num_columns                 | 2 байти (Int16 Little-Endian) — кількість колонок     |
| num_params                  | 2 байти (Int16 Little-Endian) — кількість параметрів  |
| reserved                    | 1 байт (0x00)                                        |
| warning_count               | 2 байти (Int16 Little-Endian)                        |
+-----------------------------+------------------------------------------------------+
```

Якщо `num_params > 0`, далі сервер надсилає `num_params` пакетів із метаданими параметрів (`Column Definition`), що завершуються пакетом `EOF`. Якщо `num_columns > 0`, далі слідують метадані стовпців результату, також завершені пакетом `EOF`.

### Бінарне кодування типів даних MySQL

У двійковому протоколі типи даних пакуються безпосередньо у машинному форматі Little-Endian:

| Код типу | Назва типу | Двійкове представлення значення |
|---|---|---|
| `0x01` | `MYSQL_TYPE_TINY` | 1 байт (Int8 / UInt8) |
| `0x02` | `MYSQL_TYPE_SHORT` | 2 байти (Int16 Little-Endian) |
| `0x03` | `MYSQL_TYPE_LONG` | 4 байти (Int32 Little-Endian) |
| `0x08` | `MYSQL_TYPE_LONGLONG` | 8 байтів (Int64 Little-Endian) |
| `0x04` | `MYSQL_TYPE_FLOAT` | 4 байти (IEEE 754 float) |
| `0x05` | `MYSQL_TYPE_DOUBLE` | 8 байтів (IEEE 754 double) |
| `0x0A` | `MYSQL_TYPE_DATE` | 1 байт довжини (`0`, `4` або `7`) + рік (2B), місяць (1B), день (1B) |
| `0x0C` | `MYSQL_TYPE_DATETIME` | 1 байт довжини (`0`, `4`, `7` або `11`) + дата + година, хвилина, секунда, мікросекунди |
| `0xFD` | `MYSQL_TYPE_VAR_STRING` | Довжина рядка у форматі `Length-Encoded Integer` + байти рядка |
| `0xFC` | `MYSQL_TYPE_BLOB` | Довжина у форматі `Length-Encoded Integer` + байти бінарного блоку |

### Робота з бітовою маскою NULL (Null-Bitmap) у MySQL

Для компактного кодування відсутності значень протокол MySQL не передає спеціальних рядків `"NULL"`. Натомість на початку пакета `COM_STMT_EXECUTE` виділяється бітова маска.

Розмір маски обчислюється формулою:

```
null_bitmap_bytes = (num_params + 7) / 8
```

Кожен біт відповідає за один параметр:
- Якщо `bit_index = 0` (перший параметр), він записується в нульовий біт нульового байта маски (`byte_0 & 0x01`).
- Якщо біт встановлено в `1`, значення вважається `NULL`. Для цього параметра в тілі пакета не виділяється жодного байта корисної інформації, що заощаджує мережевий трафік.
- Якщо біт дорівнює `0`, сервер зчитує чергову порцію байтів із потоку відповідно до типу параметра, вказаного в масиві типів.

### Передача великих об'єктів через COM_STMT_SEND_LONG_DATA

Коли застосунку потрібно передати великий бінарний файл або документ (наприклад, зображення розміром 50 МБ), спроба запакувати його в єдиний пакет `COM_STMT_EXECUTE` викличе помилку перевищення максимального ліміту буфера (`max_allowed_packet`).

Для таких сценаріїв клієнт використовує команду `COM_STMT_SEND_LONG_DATA`. Клієнт розбиває файл на порції по кілька сотень кілобайтів і надсилає їх послідовними пакетами, вказуючи числовий дескриптор виразу `statement_id` та індекс параметра. Сервер накопичує отримані шматки у внутрішньому тимчасовому буфері пам'яті або файлі на диску. Після завершення завантаження всіх фрагментів клієнт надсилає звичайний пакет `COM_STMT_EXECUTE`, у якому відповідний параметр позначається як раніше завантажений, і сервер виконує запит із зібраним бінарним об'єктом.

## 3. Порівняльна характеристика протоколів

| Характеристика | PostgreSQL Extended Protocol | MySQL Binary Protocol |
|---|---|---|
| **Порядок байтів (Endianness)** | Big-Endian (мережевий порядок) | Little-Endian (машинний x86/ARM) |
| **Ідентифікатор виразу** | Текстовий рядок (наприклад, `"stmt_1"`) або пустий для anonymous | 32-бітне ціле число (`statement_id`) |
| **Передача NULL значень** | Спеціальне значення довжини `-1` перед даними параметра | Компактний бітовий масив (Null-Bitmap) на початку пакета |
| **Конвеєризація (Pipelining)** | Повна підтримка: клієнт відправляє `Parse+Bind+Execute` пачкою і викликає `Sync` один раз | Роздільні запити/відповіді на кожну операцію `PREPARE` та `EXECUTE` |
| **Метадані вихідних стовпців** | Окремий явний запит `Describe` | Повертаються автоматично під час відповіді на `COM_STMT_PREPARE` |
| **Керування пам'яттю виразу** | Явне повідомлення `Close` або закриття сесії | Команда `COM_STMT_CLOSE` або закриття TCP-з'єднання |

Розділення взаємодії на двійкові пакети дозволяє мережевим драйверам ефективно мультиплексувати запити, повторно використовувати виділені буфери пам'яті та уникати будь-яких небезпечних строкових маніпуляцій при передачі критичних даних.
