# 📜 Від хаосу конкатенації до параметризації: як ін'єкції SQL змінили архітектуру СУБД

Наприкінці 1970-х років реляційна модель Едгара Кодда та мова SEQUEL (згодом SQL), розроблена в дослідницькому центрі IBM System R, створювалися для взаємодії людини з терміналом. Аналітик або адміністратор вводив текст запиту вручну, сервер парсив рядок, виконував пошук і повертав результат на монохромний екран. У цій моделі не існувало поняття «зовнішніх неперевірених даних»: автор тексту та ініціатор виконання були однією й тією ж довіреною особою.

Коли наприкінці 1980-х років з'явилися клієнт-серверні архітектури, а в середині 1990-х років вибухнув інтернет із вебсерверами на базі CGI-скриптів (Perl, C), PHP/FI та Microsoft ASP, парадигма взаємодії з базами даних радикально змінилася. Сервери застосунків почали генерувати SQL-код динамічно «на льоту», вбудовуючи параметри з HTTP-запитів безпосередньо в тіло команд за допомогою простої конкатенації рядків:

```sql
"SELECT * FROM users WHERE login = '" + input_user + "' AND pass = '" + input_pass + "'";
```

## Відкриття вразливості: Phrack 54 та Rain Forest Puppy

У грудні 1998 року дослідник безпеки під псевдонімом Rain Forest Puppy (RFP) опублікував у легендарному хакерському журналі *Phrack Magazine* (випуск 54, стаття 8) матеріал під назвою «NT Web Technology Vulnerabilities». Серед переліку проблем авторизації та обходу фільтрів у Microsoft IIS та ASP автор описав метод підміни логіки автентифікації.

Якщо поле введення пароля містило значення `admin'--`, сформований вебзастосунком запит трансформувався у вираз:

```sql
SELECT * FROM users WHERE login = 'admin'--' AND pass = '...'
```

Символи `--` позначали в стандарті SQL початок коментаря до кінця рядка. Синтаксичний аналізатор СУБД ігнорував перевірку пароля, повертаючи запис адміністратора. Інший варіант введення — `' OR '1'='1` — перетворював умову `WHERE` на тотожно істинний вираз, дозволяючи зловмиснику зчитувати записи всіх користувачів системи.

Цей клас атак отримав назву **ін'єкція SQL** (англ. *SQL injection*). Наступні п'ять років стали епохою масових зламів баз даних у всьому світі, оскільки практично кожен вебзастосунок першого покоління використовував динамічну конкатенацію запитів.

## Епоха наївних рішень: чорні списки та екранування символів

Першою реакцією інженерної спільноти була спроба «очищення» (санітизації) рядків перед підстановкою. Розробники почали писати регулярні вирази для видалення лапок, крапок з комою та коментарів або замінювати лапку `'` на безпечну послідовність `\'` чи `''`.

У мові PHP з'явилася сумнозвісна директива конфігурації `magic_quotes_gpc`, яка автоматично екранувала всі вхідні HTTP-параметри зворотною скісною рискою. У бібліотеках доступу до MySQL з'явилися функції `mysql_escape_string()` та `mysql_real_escape_string()`.

Проте підхід із текстовим екрануванням виявився крихким і породжував нові вектори вразливостей:

1. **Нечислові контексти без лапок:** якщо запит мав вигляд `WHERE id = " + input_id`, де параметр очікувався як ціле число, екранування лапок не рятувало: введення `42 OR 1=1` не містило лапок взагалі, але успішно модифікувало структуру запиту.
2. **Багатобайтові кодування та обхід `0x5C`:** у кодуваннях GBK, Big5 або SJIS другий байт символу міг мати значення `0x5C` (ASCII-код зворотної скісної риски `\`). Зловмисник передавав послідовність `0xbf 0x27`. Функція екранування вставляла перед лапкою (`0x27`) байт `0x5C`, утворюючи послідовність `0xbf 0x5c 0x27`. У китайському кодуванні пара байтів `0xbf 0x5c` інтерпретувалася як один ієрогліф, а одинарна лапка `0x27` залишалася «вільною» і ламала синтаксис запиту.
3. **Вторинні ін'єкції (Second-Order SQL Injection):** екранований рядок безпечно зберігався в базі даних як сирий текст (без скісних рисок). Коли інший модуль застосунку зчитував цей запис із бази та вставляв його конкатенацією в новий запит, ін'єкція спрацьовувала зсередини довіреного сховища.

Стало очевидно: текстове екранування бореться з симптомами, а не з причиною. Фундаментальна вада полягала в змішуванні **керуючих інструкцій** (коду мови SQL) та **даних користувача** в одному недиференційованому текстовому потоці.

## Архітектурна революція: відділення коду від даних

Єдиним надійним інженерним рішенням стало розділення передачі структури запиту та значень його змінних на рівні протоколу зв'язку та архітектури ядра СУБД.

Хоча конструкції динамічного SQL `PREPARE` та `EXECUTE` існували ще в стандарті ANSI SQL-92 (для вбудованого SQL у мовах C та COBOL), масове впровадження цієї концепції в клієнтські бібліотеки відбулося на межі 1990-х та 2000-х років:

- **ODBC 2.0 / 3.0 та JDBC (1996–1997):** інтерфейс `java.sql.PreparedStatement` стандартизував роботу з параметризованими шаблонами через символи-заповнювачі `?`. Застосунок відправляв шаблон запиту один раз, після чого викликав типізовані методи зв'язування (`setInt`, `setString`), передаючи параметри окремо від коду.
- **PostgreSQL 7.4 (2003):** впроваджено третю версію двійкового протоколу (Frontend/Backend Protocol 3.0) із повноцінною підтримкою протоколу розширених запитів (Extended Query Protocol). Команди `Parse`, `Bind`, `Execute` та `Sync` отримали окремі бінарні пакети, повністю ізолювавши передачу байтів параметрів від синтаксичного дерева AST.
- **MySQL 4.1 (2004):** з'явився двійковий клієнтський протокол підготовлених виразів (`COM_STMT_PREPARE`, `COM_STMT_EXECUTE`), що поклало край домінуванню текстового інтерфейсу `mysql_query()`. У PHP випущено розширення `mysqli` та рівень абстракції `PDO` (PHP Data Objects), де підготовлені вирази стали стандартом за замовчуванням.

## Підсумок історичного уроку

Історія боротьби з ін'єкціями SQL повторила класичний закон комп'ютерної безпеки: спроби перевірити або очистити вхідні дані за допомогою чорних списків символів завжди зазнають поразки через складність граматики та кодувань.

Підготовлені вирази вирішили проблему ін'єкцій не шляхом ретельного очищення тексту, а шляхом зміни фази обробки: коли сирі байти користувача потрапляють до сервера, синтаксичний аналіз уже завершено, синтаксичне дерево зафіксовано, і жоден вхідний байт фізично не здатний стати новим оператором чи ключовим словом мови запитів.
