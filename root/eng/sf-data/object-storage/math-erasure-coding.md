# 🧮 Математика кодування стиранням: матриці Вандермонда, відновлення даних та надійність 11 дев'яток

Математичний апарат кодування стиранням (Erasure Coding) за алгоритмом Ріда-Соломона над полями Галуа дозволяє досягти надійності зберігання 99.999999999% (одинадцять дев'яток) при накладних витратах дискового простору лише 30–50% порівняно з 200% при трикратній реплікації.

## Чому простого XOR недостатньо: обмеження парності

У класичних дискових масивах RAID-5 для захисту від збою одного диска використовується операція побітового виключного «АБО» (XOR, позначимо як ⊕).

Якщо масив складається з `K` блоків даних `D₁, D₂, ..., D_K`, то блок парності `P` обчислюється як:

```
P = D₁ ⊕ D₂ ⊕ ... ⊕ D_K
```

У разі втрати будь-якого одного диска `D_i` (наприклад, `D₂`), його значення відновлюється за один прохід застосуванням тієї самої операції до вцілілих дисків і блоку парності:

```
D₂ = D₁ ⊕ D₃ ⊕ ... ⊕ D_K ⊕ P
```

Ця схема ідеальна за швидкістю, проте вона має фундаментальне математичне обмеження: вона здатна виправити рівно **одне стирання** (`M = 1`). Якщо одночасно виходять із ладу два диски (наприклад, `D₁` та `D₂`), у нас залишається одне лінійне рівняння з двома невідомими:

```
D₁ ⊕ D₂ = D₃ ⊕ ... ⊕ D_K ⊕ P
```

Це рівняння має множину розв'язків у бінарній алгебрі і не дозволяє однозначно визначити `D₁` та `D₂`.

Щоби система зберігання витримувала одночасний збій двох, чотирьох або більше накопичувачів (`M ≥ 2`), необхідна система з `M` незалежних лінійних рівнянь. Проте у звичайній арифметиці дійсних чисел ділення та множення призводять до дробових чисел і переповнення фіксованої розрядності пам'яті (роздування 8-бітного байта до 32 чи 64 бітів).

Виходом із цього глухого кута є **арифметика скінченних полів Галуа**.

## Арифметика полів Галуа GF(2ʷ)

Скінченне поле Галуа `GF(2ʷ)` — це алгебраїчна структура, яка містить рівно `2ʷ` елементів, де операції додавання, віднімання, множення та ділення (крім ділення на нуль) завжди дають результат, який належить тій самій множині та поміщається у вихідні `w` бітів без переповнення та втрати точності.

У комп'ютерних системах зберігання найчастіше використовується поле `GF(2⁸)` (`w = 8` бітів), оскільки кожен елемент поля ідеально відповідає одному байту (діапазон від `0` до `255`).

### 1. Додавання та віднімання в GF(2⁸)

Додавання та віднімання в полях характеристики 2 тотожні й виконуються як звичайне побітове XOR:

```
A + B = A ⊕ B
A - B = A ⊕ B
```

Оскільки `A ⊕ A = 0`, кожен елемент є власним протилежним: `-A = A`.

### 2. Множення та незвідний многочлен

Множення двох байтів розглядається як множення поліномів зі степенями до 7, де коефіцієнти беруться за модулем 2. Якщо степінь добутку досягає 8 або більше, результат приводиться за модулем спеціального **незвідного многочлена** (англ. *irreducible polynomial*).

Для `GF(2⁸)` стандартом є поліном Ріда-Соломона:

```
P(x) = x⁸ + x⁴ + x³ + x² + 1    [шістнадцяткове представлення: 0x11D, десяткове: 285]
```

Множення на `x` (множення на 2) реалізується через побітовий зсув уліво з умовним XOR на константу `0x1D`:

```
mul2(b) = (b << 1) ⊕ (0x1D, якщо старший біт b дорівнював 1)
```

Завдяки цьому операції множення та ділення в сучасних процесорах виконуються за один такт за допомогою векторних інструкцій AVX-512 / ARM Neon або попередньо обчислених таблиць логарифмів та експонент.

## Кодування Ріда-Соломона за схемою (K + M)

Нехай вхідний об'єкт розбито на `K` однакових за розміром блоків даних (шардів даних):

```
D = [d₁, d₂, ..., d_K]ᵀ
```

Ми хочемо створити `M` додаткових блоків парності:

```
P = [p₁, p₂, ..., p_M]ᵀ
```

Разом вони утворюють закодований вектор `E` розміром `(K + M)`:

```
E = [d₁, d₂, ..., d_K, p₁, p₂, ..., p_M]ᵀ
```

Цей вектор отримується множенням генераторної матриці `G` розміром `(K + M) × K` на вектор даних `D`:

```
E = G · D
```

Генераторна матриця `G` конструюється як блокова матриця:
* Верхня частина розміром `K × K` — це одинична матриця `I_K`. Завдяки цьому перші `K` елементів вектора `E` збігаються з вихідними даними `D` (таке кодування називається *систематичним*).
* Нижня частина розміром `M × K` — це матриця коефіцієнтів парності `B`.

```
        ┌               ┐
        │  1  0 ...  0  │
        │  0  1 ...  0  │  } K рядків (одинична матриця I_K)
        │  .  . ...  .  │
    G = │  0  0 ...  1  │
        ├───────────────┤
        │ b₁₁ b₁₂ ... b₁K│
        │ b₂₁ b₂₂ ... b₂K│  } M рядків (матриця парності B)
        │  .   .  ...  . │
        │ bM₁ bM₂ ... bMK│
        └               ┘
```

### Вимога до матриці: лінійна незалежність підматриць

Щоби систему можна було розв'язати при втраті будь-яких `M` блоків, будь-яка підматриця розміром `K × K`, утворена вибором будь-яких `K` рядків матриці `G`, зобов'язана бути **невиродженою** (її детермінант у полі `GF(2⁸)` не дорівнює нулю: `det(G_sub) ≠ 0`).

Для побудови такої матриці використовують **матриці Вандермонда** або **матриці Коші**.

Елемент матриці Вандермонда в рядку `i` та стовпці `j` задається як степінь:

```
V[i, j] = α[i]ʲ⁻¹
```

Шляхом елементарних перетворень рядків матрицю Вандермонда зводять до систематичної форми `[I_K | B]ᵀ`. Матриці Коші, де елементи задаються дробом `1 / (x[i] ⊕ y[j])`, мають ту перевагу, що будь-яка їхня підматриця гарантовано невироджена над будь-яким полем без додаткових перетворень.

## Алгоритм відновлення даних при збоях (Реконструкція)

Припустимо, що у сховищі зі схемою `RS(4 + 2)` (`K = 4, M = 2`, всього 6 вузлів) два вузли вийшли з ладу. Наприклад, втрачено шард даних `d₂` та шард парності `p₁`.

Клієнт або фоновий відновлювач зчитує 4 будь-які вцілілі шарди: `d₁, d₃, d₄, p₂`.

Процес реконструкції складається з трьох кроків:

1. **Формування підматриці `G_sub`.** Із вихідної матриці `G` вибираються 4 рядки, що відповідають уцілілим шардам: рядки 1, 3, 4 та 6. Отримуємо квадратну матрицю `G_sub` розміром `4 × 4`.
2. **Інверсія матриці (Знаходження `G_sub⁻¹`).** Оскільки `det(G_sub) ≠ 0`, у полі `GF(2⁸)` існує обернена матриця `G_sub⁻¹`. Вона обчислюється методом виключення Гауса-Жордана.
3. **Обчислення вихідних даних.** Вихідний вектор даних `D` відновлюється множенням оберненої матриці на вектор доступних шардів `E_sub`:

```
D = G_sub⁻¹ · E_sub
```

Отримавши вектор `D = [d₁, d₂, d₃, d₄]ᵀ`, відновлювач дістає втрачений блок `d₂`, а також за потреби заново обчислює втрачену парність `p₁ = G[5] · D` і записує відновлені фрагменти на нові справні накопичувачі.

## Числовий приклад обчислення та відновлення в GF(2⁸)

Щоби зробити математичний механізм відчутним, розглянемо числовий приклад для схеми `RS(2 + 2)` над полем `GF(2⁸)`.

Нехай маємо два байти вихідних даних:
* `d₁ = 0x05` (двійкове `00000101`)
* `d₂ = 0x09` (двійкове `00001001`)

Визначимо матрицю генератора `G` розміром `4 × 2`:

```
        ┌       ┐
        │ 1   0 │  <- рядок d₁
    G = │ 0   1 │  <- рядок d₂
        │ 1   1 │  <- рядок p₁ (простий XOR)
        │ 1   2 │  <- рядок p₂ (з коефіцієнтом множення 2)
        └       ┘
```

Обчислимо байти парності:
* `p₁ = (1 · d₁) ⊕ (1 · d₂) = 0x05 ⊕ 0x09 = 0x0C` (двійкове `00001100`).
* `p₂ = (1 · d₁) ⊕ (2 · d₂) = 0x05 ⊕ mul2(0x09)`.

Оскільки для `0x09` старший біт дорівнює 0, операція `mul2(0x09)` є простим зсувом уліво: `0x09 << 1 = 0x12`.
Тоді: `p₂ = 0x05 ⊕ 0x12 = 0x17`.

Усі 4 збережені байти на дисках: `E = [0x05, 0x09, 0x0C, 0x17]ᵀ`.

### Сценарій подвійного збою: втрачено обидва диски даних d₁ та d₂

Припустимо, що диски 1 та 2 одночасно вийшли з ладу. У нас залишилися лише блоки парності `p₁ = 0x0C` та `p₂ = 0x17`.

Підматриця уцілілих рядків (рядки 3 та 4):

```
            ┌       ┐
    G_sub = │ 1   1 │
            │ 1   2 │
            └       ┘
```

Обчислимо детермінант `G_sub` у полі `GF(2⁸)`:

```
det(G_sub) = (1 · 2) ⊕ (1 · 1) = 2 ⊕ 1 = 3
```

Обернена матриця `G_sub⁻¹`:

```
               1    ┌       ┐
    G_sub⁻¹ = ─── · │ 2   1 │
               3    │ 1   1 │
                    └       ┘
```

В `GF(2⁸)` мультиплікативно оберненим до `3` є `0xF4` (оскільки `3 · 0xF4 ≡ 1` за модулем `P(x)`).
Обчислюємо елементи оберненої матриці:
* `(2 / 3) = 2 · 0xF4 = 0xF5`
* `(1 / 3) = 1 · 0xF4 = 0xF4`

```
              ┌             ┐
    G_sub⁻¹ = │ 0xF5   0xF4 │
              │ 0xF4   0xF4 │
              └             ┘
```

Відновлюємо вектор даних:

```
d₁ = (0xF5 · p₁) ⊕ (0xF4 · p₂)
   = (0xF5 · 0x0C) ⊕ (0xF4 · 0x17)
   = 0x08 ⊕ 0x0D = 0x05  [відновлено точно!]

d₂ = (0xF4 · p₁) ⊕ (0xF4 · p₂)
   = 0xF4 · (p₁ ⊕ p₂)
   = 0xF4 · (0x0C ⊕ 0x17)
   = 0xF4 · 0x1B = 0x09  [відновлено точно!]
```

Обидва байти відновлено зі 100% точністю без знання їхніх початкових значень.

## Накладні витрати дискового простору: Реплікація проти EC

Коефіцієнт накладних витрат зберігання (англ. *Storage Overhead Factor*) визначається як відношення загального обсягу збережених байтів до корисного обсягу даних:

```
Factor = (K + M) / K = 1 + (M / K)
Overhead_% = (M / K) · 100%
```

Порівняємо характеристики різних схем:

| Схема зберігання | Допустима кількість збоїв (M) | Коефіцієнт роздування | Накладні витрати (%) | Економія диска відносно 3× реплікації |
| :--- | :--- | :--- | :--- | :--- |
| 3-кратна реплікація (3×) | 2 | 3.0× | 200% | 0% (базовий рівень) |
| Reed-Solomon RS(4 + 2) | 2 | 1.5× | 50% | 50% економії |
| Reed-Solomon RS(8 + 4) | 4 | 1.5× | 50% | 50% економії (вдвічі надійніше) |
| Reed-Solomon RS(10 + 4) | 4 | 1.4× | 40% | 53.3% економії |
| Reed-Solomon RS(16 + 4) | 4 | 1.25× | 25% | 58.3% економії |

Схема `RS(8 + 4)` споживає рівно вдвічі менше дискового простору, ніж 3-кратна реплікація (`1.5×` замість `3.0×`), при цьому витримує одночасну втрату **4 дисків замість 2**.

## Розрахунок надійності: Математична модель 11 дев'яток

Провідні хмарні провайдери декларують надійність об'єктного сховища на рівні **99.999999999% (11 дев'яток)** на рік. Звідки береться це число і що воно означає математично?

Річна ймовірність втрати об'єкта `P_loss` пов'язана з надійністю співвідношенням:

```
Durability = 1 - P_loss
```

Для 11 дев'яток річна ймовірність безповоротної втрати хоча б одного об'єкта становить:

```
P_loss = 10⁻¹¹ = 0.00000000001
```

Це означає: якщо зберегти 100 мільярдів об'єктів (`10¹¹`), у середньому за один рік очікується втрата не більше ніж 1 об'єкта.

### Розрахунок за моделлю ланцюгів Маркова

Нехай середньорічна ймовірність відмови одного жорсткого диска становить `AFR = 1.5%` (Annualized Failure Rate). Тоді інтенсивність відмов одного диска `λ` (лямбда) дорівнює:

```
λ = AFR / (365 · 24) ≈ 0.015 / 8760 ≈ 1.712 · 10⁻⁶ відмов / годину
```

Середній час напрацювання на відмову диска (MTTF):

```
MTTF = 1 / λ ≈ 584 000 годин (≈ 66.6 років)
```

Коли диск виходить із ладу, система починає паралельне відновлення шардів на резервні накопичувачі по мережі. Час відновлення одного шарда `T_repair` у розподіленому сховищі становить у середньому **15 хвилин** (`T_repair = 0.25` години), оскільки відновлення розподілене між тисячами вузлів кластера.

Інтенсивність відновлення `μ` (мю):

```
μ = 1 / T_repair = 1 / 0.25 = 4.0 відновлень / годину
```

Для схеми кодування `RS(K + M)`, де втрата даних настає лише за умови одночасного збою `(M + 1)` дисків до моменту завершення відновлення, середній час до безповоротної втрати даних (MTTDL — Mean Time To Data Loss) розраховується за формулою марковського процесу загибелі та розмноження:

```
            μᴹ
MTTDL = ─────────────
        (K+M) · λᴹ⁺¹
```

Підставимо значення для схеми `RS(8 + 4)` (`K = 8, M = 4`, тобто втрата настає при 5 збоях, `K + M = 12`):

```
Чисельник:  μ⁴ = 4.0⁴ = 256

Знаменник: (8 + 4) · λ⁵ = 12 · (1.712 · 10⁻⁶)⁵
           = 12 · 1.468 · 10⁻²⁹
           = 1.7616 · 10⁻²⁸

MTTDL = 256 / (1.7616 · 10⁻²⁸)
      ≈ 1.453 · 10³⁰ годин
```

Ймовірність втрати конкретного об'єкта протягом одного року (`T_year = 8760` годин):

```
P_loss = T_year / MTTDL
       = 8760 / (1.453 · 10³⁰)
       ≈ 6.03 · 10⁻²⁷
```

Значення `6.03 · 10⁻²⁷` на багато порядків перевершує поріг `10⁻¹¹`.

## Локальні коди відновлення (Local Reconstruction Codes, LRC)

У класичній схемі `RS(K + M)` для відновлення навіть одного втраченого диска необхідно зчитати `K` шардів з інших вузлів. Для схеми `RS(10 + 4)` це означає, що при збої одного накопичувача мережа дата-центру навантажується передачею `10 × 1 ГБ = 10 ГБ` трафіку на кожен терабайт відновлених даних.

Оскільки 99% усіх збоїв у дата-центрах є одиничними відмовами дисків, сучасні хмарні системи (Microsoft Azure Storage, AWS S3) використовують **локальні коди відновлення (LRC)**.

У схемі `LRC(K, L, G)`:
* `K` шардів даних діляться на `L` локальних груп.
* Для кожної локальної групи створюється 1 локальний шард парності.
* Для всього масиву створюється `G` глобальних шардів парності.

Наприклад, у схемі `LRC(12, 2, 2)` 12 шардів даних розбиваються на дві групи по 6 шардів (`D₁...D₆` та `D₇...D₁₂`). При виході з ладу одного диска в першій групі його відновлення вимагає зчитування лише 6 шардів (5 даних + 1 локальна парність) замість 12, що зменшує мережевий трафік відновлення рівно на 50%.

## Захист від тихого пошкодження даних (Bit Rot)

Окрім повного виходу з ладу фізичних накопичувачів, існує загроза **тихого пошкодження бітів (Bit Rot)** — спонтанного перемикання бітів у магнітному шарі HDD або комірках флеш-пам'яті SSD внаслідок теплових шумів чи космічного випромінювання.

Контролер накопичувача повертає успішний статус читання, проте прочитані дані містять помилку.

Щоби унеможливити поширення таких спотворень:
1. Кожен шард супроводжується поліноміальним кодом `CRC32C` (поліном `0x1EDC6F41`). Ймовірність пропустити випадкове бітове пошкодження для 64-КБ блоку становить `2⁻³² ≈ 2.33 · 10⁻¹⁰`.
2. На рівні об'єкта обчислюється криптографічний дайджест SHA-256 або MD5 (ETag).
3. Фоновий сканер цілісності (Background Scrubber) безперервно вичитує блоки з дисків і порівнює фактичний хеш із метаданими. У разі виявлення розбіжності пошкоджений шард негайно відкидається як «стертий» та реконструюється з інших шардів кодування Ріда-Соломона.

## Затримка деградованого читання та хеджування запитів

Коли один із накопичувачів у схемі `RS(K + M)` зазнає збою або відповідає з великою затримкою, виникає явище **деградованого читання (Degraded Read)**.

У штатному режимі клієнт паралельно надсилає запити до `K` вузлів даних і збирає потік байтів зі швидкістю найповільнішого з `K` вузлів:

```
T_read_normal = max(t₁, t₂, ..., t_K)
```

Якщо один із вузлів даних недоступний, клієнт або шлюз сховища змушений звернутися до вузла парності `p₁`, виконати додатковий мережевий виклик та розрахувати інверсію матриці в оперативній пам'яті:

```
T_read_degraded = max(t₁, ..., t_{K-1}, t_{parity}) + T_decode
```

Оскільки затримки в розподілених мережах мають довгий хвіст розподілу (Long-Tail Latency), імовірність того, що хоча б один із `K` запитів потрапить у 99-й процентиль затримки `P99`, стрімко зростає зі збільшенням `K`:

```
P_tail_stripe = 1 - (1 - p_tail)^K
```

Для схеми `RS(10 + 4)` при ймовірності сплеску затримки на окремому вузлі `p_tail = 1%` імовірність уповільнення читання всього об'єкта становить:

```
P_tail_stripe = 1 - (1 - 0.01)¹⁰ ≈ 1 - 0.9044 = 9.56%
```

Майже кожен десятий запит відчував би затримку вузла, що завис.

Для подолання цієї затримки застосовують техніку **хеджованих запитів (Hedged Requests)**: клієнт одночасно надсилає запити не на `K`, а на `K + 1` вузлів (включаючи перший вузол парності). Щойно надходять перші `K` відповідей, зайвий запит негайно скасовується. Це усуває вплив найповільнішого вузла на хвостову затримку системи та стабілізує P99 на рівні мілісекунд.

## Моделювання корельованих збоїв та топологічна антиафінність

Марковська формула надійності `MTTDL` спирається на припущення про статистичну незалежність відмов окремих накопичувачів. Проте в реальному дата-центрі диски не є повністю незалежними:

1. **Збої серверних стійок (Rack Failures).** Вихід із ладу загального комутатора стійки (Top-of-Rack Switch, ToR) або блоку розподілу живлення (PDU) миттєво робить недоступними всі 40–80 дисків цієї стійки.
2. **Температурні коливання та виробничі партії.** Диски з однієї заводської партії мають однаковий виробничий дефект і можуть одночасно деградувати при перегріві серверної зали.
3. **Катастрофи дата-центрів.** Пожежа, затоплення або аварія магістрального живлення виводить із ладу всю зону доступності.

Щоби математична ймовірність втрати даних залишалася на рівні `10⁻¹¹`, розподілена система впроваджує правила **топологічної антиафінності (Fault Domain Anti-Affinity)**:

* Усі `(K + M)` шардів одного об'єкта обов'язково розміщуються на різних фізичних серверах.
* Жодні два шарди не можуть належати одній стійці або живитися від одного PDU.
* При схемі `RS(8 + 4)` у мультизонній конфігурації (Multi-AZ) шарди розподіляються між 3 географічно віддаленими дата-центрами за пропорцією `4 + 4 + 4`.

При такій топології повна втрата одного дата-центру (4 шарди) залишає рівно `12 - 4 = 8` доступних шардів у двох інших зонах, що в точності дорівнює `K = 8` і гарантує безперервну доступність та 100% збереження даних без жодної втрати байтів.
