# 📜 Еволюція рушіїв шаблонізації: від макропідстановок до пісочниць та мультиканальних AST

З моменту відправки першого електронного листа між комп'ютерами PDP-10 через мережу ARPANET у жовтні 1971 року інженери намагалися вирішити одне й те саме прикладне завдання: як узяти статичний текст повідомлення, динамічно підставити в нього дані конкретного адресата та надійно доставити результат людині. Те, що на зорі обчислювальної техніки виглядало банальною посимвольною заміною плейсхолдерів у пам'яті, з появою комерційного інтернету, мобільних операційних систем та глобальних розподілених сервісів перетворилося на складний архітектурний конвеєр.

Історія шаблонізації — це безперервна боротьба між виразністю мови шаблонів і безпекою виконання, між зручністю бізнес-авторів і строгими вимогами компіляторів, а також між фрагментованими рушіями відображення поштових і мобільних клієнтів.

## 1. Епоха мейнфреймів: Mail Merge та небезпечний форматний рядок (1970–1980-ті)

Сам термін **шаблон** походить від німецького *Schablone* (зразок, вирізаний трафарет для нанесення однакових контурів). У комп'ютерну еру цей принцип уперше матеріалізувався у великих бізнес-системах на базі мейнфреймів IBM System/370 та перших текстових процесорах кінця 1970-х років, таких як Electric Pencil та WordStar (розроблений Робом Барнабі у 1978 році).

Для масової розсилки квитанцій чи повідомлень клієнтам компанії використовували технологію **Mail Merge** (поштове злиття). Механізм діяв за принципом прямої заміни текстових міток: оператор готував документ із заповнювачами на зразок `&FIRSTNAME&` або `&BALANCE&`, а програма послідовно читала рядки з плоского файлу бази даних чи перфокарт і виконувала байтове заміщення.

```
[Шаблон WordStar]     Шановний &NAME&, ваш баланс: &SUM& USD.
                              │
[Дані з перфокарт]    NAME="Олександр", SUM="150"
                              ▼
[Результат у буфері]  Шановний Олександр, ваш баланс: 150 USD.
```

Цей підхід мав критичні обмеження:
1. **Відсутність типізації:** система не знала, чи є значення числом, датою чи довільним текстом, що унеможливлювало форматування чи валідацію.
2. **Нечутливість до синтаксису:** якщо значення поля містило службовий символ `&`, алгоритм розбору ламався або спотворював структуру документа.

У 1972 році Браян Керніган та Денніс Рітчі під час створення мови C запропонували форматний рядок для функцій сімейства `printf` та `sprintf`:

:::tabs
```c
/* Традиційний нетипізований sprintf у C */
sprintf(buffer, "Користувач %s здійснив %d операцій на суму %.2f грн.", name, count, amount);
```
```cpp
// Сучасний типізований std::format у C++20
auto text = std::format("Користувач {} здійснив {} операцій на суму {:.2f} грн.", name, count, amount);
```
:::

Функція `sprintf` інтерпретувала символи з префіксом `%` як специфікатори типів, зчитуючи байти безпосередньо зі стека викликів процесора. Проте для генерації сповіщень людям цей механізм виявився непридатним через дві фундаментальні вади.

По-перше, виникла вразливість **Format String Vulnerability**: якщо неперевірений вхідний рядок користувача передавався у функцію як перший аргумент (`printf(user_input)` замість `printf("%s", user_input)`), специфікатори `%x` та `%n` дозволяли зловмиснику зчитувати довільні ділянки пам'яті та перезаписувати адреси повернення на стеку, отримуючи повний контроль над процесом.

По-друге, форматні рядки мови C мали жорстко фіксований позиційний порядок аргументів. Якщо для англійського тексту порядок був `"%s sent %d files to %s"`, а німецька чи японська граматика вимагала переставити іменники місцями, локалізація ставала неможливою без переписування вихідного коду програми на C.

## 2. Веб-бум та хаос вбудованого коду: PHP, ASP та ERB (1990-ті – початок 2000-х)

У 1994 році данський програміст Расмус Лердорф (Rasmus Lerdorf) створив набір бінарних утиліт мовою C для відстеження відвідувачів свого онлайн-резюме, назвавши їх *Personal Home Page Tools* (PHP). Лердорф запропонував змінити парадигму: замість того, щоб компільована програма генерувала текст сповіщення чи HTML-документ через виклики функцій друку, сам текстовий документ ставав програмою, у яку вставлялися фрагменти коду за допомогою спеціальних тегів `<?php ... ?>`.

Цю ідею негайно підхопили та стандартизували технологічні гіганти:
- Microsoft випустила **Active Server Pages (ASP)** у 1996 році з синтаксисом `<% ... %>` на базі VBScript.
- Sun Microsystems у 1999 році представила **JavaServer Pages (JSP)** для екосистеми Java Enterprise.
- Девід Хейнемейєр Ханссон (David Heinemeier Hansson) у 2004 році зробив вбудований інтерпретатор **ERB (Embedded Ruby)** стандартом генерації поштових повідомлень у фреймворку Ruby on Rails (`ActionMailer`).

```erb
<%# Типовий лист в екосистемі ActionMailer / ERB середини 2000-х %>
<h1>Вітаємо, <%= @user.name %>!</h1>
<% if @order.total > 1000 %>
  <p>Вам нараховано преміальний статус за замовлення #<%= @order.id %>.</p>
  <% @user.apply_discount! %> <%# Мутація бізнес-стану всередині шаблону! %>
<% end %>
```

Цей підхід забезпечив колосальну швидкість розробки, але до кінця 2000-х років спричинив системну інженерну кризу:

* **Змішування рівнів абстракції (Spaghetti Architecture):** шаблони почали містити важкі SQL-запити до баз даних, виклики мережевих API та мутації бізнес-сутностей. Зміна дизайну електронного листа дизайнером могла випадково зламати транзакцію оплати.
* **Епідемія вразливостей міжсайтового скриптингу (XSS):** у перших версіях PHP та ERB вставка змінної через `<%= variable %>` виконувала "сирий" вивід без санітизації. Якщо ім'я користувача містило `<script>` або `onload=`, воно без змін потрапляло в поштовий клієнт чи веб-інтерфейс отримувача.
* **Server-Side Template Injection (SSTI):** компанії прагнули надати маркетологам і контент-менеджерам можливість редагувати тексти сповіщень через веб-адмінку. Шаблони почали зберігатися в базі даних і динамічно інтерпретуватися сервером. Оскільки рушії мали повний доступ до системного середовища виконання, зловмисник міг зберегти шаблон вигляду `<%= system("rm -rf /") %>` або `{{ config.__class__.__init__.__globals__['os'].popen('id').read() }}`, що давало миттєве виконання довільного коду (Remote Code Execution) на серверах відправки сповіщень.

## 3. Маніфест Logic-less та поява безпечних пісочниць (2008–2012)

У 2009 році Кріс Ванстрат (Chris Wanstrath, співзасновник GitHub) опублікував бібліотеку **Mustache** та маніфест *Logic-less Templates* («Шаблони без логіки»). Головна теза маніфесту стверджувала: у файлі шаблону не повинно бути жодних керуючих конструкцій, арифметичних операцій, присвоєння змінних чи викликів методів об'єктів.

Синтаксис Mustache складався виключно з подвійних фігурних дужок `{{ ... }}` (які візуально нагадували вуса, звідки й пішла назва):
- `{{name}}` — автоматично екранована вставка змінної.
- `{{{raw_html}}}` — явна неекранована вставка (вимагала усвідомленої дії розробника).
- `{{#items}}...{{/items}}` — універсальна секція: якщо значення є масивом, виконується ітерація; якщо булевим `true` — умовний показ; якщо `null` чи порожній масив — блок пропускається.

```mustache
{{! Шаблон Mustache: повна відсутність бізнес-логіки }}
<p>Шановний {{customerName}},</p>
{{#hasDiscount}}
  <p>Ваша знижка: {{discountPercent}}%</p>
{{/hasDiscount}}
```

Розвиваючи цей рух, інженери створили нове покоління рушіїв:

1. **Handlebars (Єгуда Кац, 2010):** розширив Mustache до повноцінного синтаксичного дерева (AST), додав строгі хелпери форматування та можливість компіляції шаблону в оптимізований байт-код JavaScript.
2. **Liquid (Тобіас Лютке / Shopify, 2006):** розроблений для електронної комерції. Запровадив концепцію **фільтрів** (`{{ order.date | date: "%Y-%m-%d" }}`) та жорсткої **пісочниці** (Sandbox), яка фізично не мала доступу до середовища Ruby чи файлової системи хоста.
3. **Jinja2 (Армін Ронахер / Pocoo Team, 2008):** став еталоном пісочничної шаблонізації в екосистемі Python, запропонувавши суворий контроль за доступом до атрибутів об'єктів та ліміти часу виконання проти атак на виснаження процесора.

```
Вхідний рядок шаблону: "{{user.name}} має {{count}} повідомлень"
                         │
                         ▼  [Lexer / Токенізатор]
Токени: [VAR("user.name"), TEXT(" має "), VAR("count"), TEXT(" повідомлень")]
                         │
                         ▼  [Parser / Синтаксичний аналізатор]
Абстрактне синтаксичне дерево (AST):
  ├── Node: VariableResolve(path="user.name", escape=HTML)
  ├── Node: LiteralText(" має ")
  ├── Node: VariableResolve(path="count", escape=HTML)
  └── Node: LiteralText(" повідомлень")
                         │
                         ▼  [Sandbox Compiler]
Виконувана функція: render(context) -> з перевіркою глибини та ліміту пам'яті
```

Перехід до компіляції в AST дозволив валідувати безпеку шаблонів на етапі збереження в базі даних, унеможливлюючи SSTI-атаки до початку виконання розсилки.

## 4. Боротьба з мовною складністю: від gettext до ICU MessageFormat

Паралельно з безпекою розвивалася проблема міжнародної локалізації (i18n). У 1995 році Ульріх Дреппер (Ulrich Drepper) випустив бібліотеку **GNU gettext**, яка запропонувала каталоги перекладів `.po` та першу формулу множини:

```po
# Заголовок каталогу перекладів GNU gettext (.po)
Plural-Forms: nplurals=3; plural=(n%10==1 && n%100!=11 ? 0 : n%10>=2 && n%10<=4 && (n%100<10 || n%100>=20) ? 1 : 2);
```

Хоча `ngettext()` вирішував задачу для одного числівника, у складних сповіщеннях (наприклад: *«Олена додала 3 фотографії до 2 альбомів»*) підхід gettext повністю руйнувався, оскільки не підтримував комбінацію кількох незалежних числівників в одному рядку без каскаду вкладених умовних операторів у коді.

Наприкінці 1990-х років корпорація IBM розпочала проект **ICU (International Components for Unicode)**, переданий згодом консорціуму Unicode. У межах проекту було створено стандарт **ICU MessageFormat** та репозиторій мовних правил **CLDR (Common Locale Data Repository)**.

ICU запровадив граматичні мітки множини (`zero`, `one`, `two`, `few`, `many`, `other`) та декларативне розгалуження тексту всередині одного шаблону:

```
{gender, select,
  female {{userName} додала {photoCount, plural,
            one {# фотографію}
            few {# фотографії}
            many {# фотографій}
            other {# фотографії}
         } до {albumCount, plural,
            one {# альбому}
            other {# альбомів}
         }}
  other  {{userName} додав {photoCount, plural,
            one {# фотографію}
            few {# фотографії}
            many {# фотографій}
            other {# фотографії}
         } до {albumCount, plural,
            one {# альбому}
            other {# альбомів}
         }}
}
```

У 2012 році комітет TC39 стандартизував API `Intl` в специфікації ECMAScript (ECMA-402), інтегрувавши правила CLDR (`Intl.PluralRules`, `Intl.NumberFormat`, `Intl.DateTimeFormat`) безпосередньо в усі сучасні браузери та платформи виконання Node.js, Deno і Bun.

## 5. Мультиканальна революція та парадокс поштових рушіїв (2010–2020-ті)

У 2007 році компанія Microsoft ухвалила рішення, яке визначило долю email-шаблонізації на наступні два десятиліття: у поштовому клієнті Microsoft Outlook 2007 рушій рендерингу HTML на базі Internet Explorer було замінено на рушій рендерингу **Microsoft Word**.

Це рішення відкинуло стандарти верстки електронних листів на п'ятнадцять років назад. Поштовий клієнт втратив підтримку більшості CSS-властивостей (зокрема `flexbox`, `grid`, `position`, `margin: auto`), перестав розуміти семантичні блокові теги та вимагав використання вкладених таблиць `<table>` із явним зазначенням атрибутів `width`, `cellpadding` та умовних коментарів для Microsoft Office (`<!--[if mso]>`). Одночасно мобільні клієнти (Apple Mail, Gmail App) вимагали сучасного адаптивного дизайну через `@media`-запити.

Для подолання цієї прірви інженерна спільнота створила спеціалізовані абстракції:

1. **CSS-інлайнери (Premailer, Juice, Roadie, 2010–2015):** бібліотеки, що парсили повноцінні таблиці стилів `<style>` і автоматично перетворювали класи на інлайнові атрибути `style="..."` для кожного HTML-елемента, захищаючи лист від вирізання стилів поштовим клієнтом Gmail.
2. **MJML (Mailjet, 2016):** декларативна XML-подібна мова розмітки високого рівня (`<mj-section>`, `<mj-column>`, `<mj-button>`), транслятор якої компілював абстрактні компоненти у стабільний, кросклієнтський табличний HTML-код.
3. **React Email та JSX-компоненти (2022–дотепер):** перехід до компонентної моделі на базі TypeScript/JSX (`<Html>`, `<Button>`, `<Tailwind>`). Шаблон став типізованою функцією, яка на етапі збірки генерує як безпечний HTML із вбудованими стилями, так і синхронний текстовий двійник (`text/plain`) без необхідності підтримувати два окремі файли вручну.

Сучасний вузол шаблонізації більше не є простим текстовим транслятором. Він еволюціонував у повноцінний розподілений компілятор, який приймає строго типізований бізнес-контракт події, верифікує його за схемою, запускає пісочницю з правилами локалі CLDR та паралельно випускає оптимізовані артефакти для десятка несумісних між собою цифрових каналів.
