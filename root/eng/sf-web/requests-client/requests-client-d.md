Коли програма взаємодіє з віддаленим веб-сервісом, вона не може розглядати мережевий канал як простий текстовий потік символів. Повноцінна клієнтська транзакція протоколу HTTP вимагає узгодженої роботи десятка автономних механізмів: коректного синтаксичного розбору та екранування параметрів URL, нормалізації заголовків без урахування регістру символів, узгодження криптографічного шифрування й перевірки ланцюжків сертифікатів TLS, збереження та перевірки часу життя сесійних cookie, потокового кодування великих тіл без переповнення оперативної пам'яті, проходження ланцюжків перенаправлень із захистом від витоку облікових даних, а також автоматичного розпакування та декодування бінарних потоків у правильне текстове кодування.

Спроба реалізувати ці операції безпосередньо над системними сокетами операційної системи або через низькорівневі примітиви стандартної бібліотеки змушує писати сотні рядків шаблонного зв'язуючого коду. Будь-яка помилка в такому коді — наприклад, забутий тайм-аут на операції читання, неможливість повторного використання відкритого TCP-з'єднання чи неправильне зіставлення кодувань — призводить до вичерпання дескрипторів файлів, зависання робочих потоків або критичних вразливостей безпеки.

## Розділення обов'язків: ергономіка requests проти рушія urllib3

Архітектура сучасної взаємодії з HTTP у Python будується на чіткому розділенні двох рівнів: декларативного людино-орієнтованого інтерфейсу бібліотеки `requests` та системного мережевого рушія `urllib3`. Про те, як виникла ця концепція і чому стандартні модулі `urllib` та `urllib2` виявилися непридатними для сучасного вебу, розповідає [історію появи концепції «HTTP for Humans» та відокремлення транспортного пулу urllib3](root:sf-web/requests-client/hist-python-http-clients.md).

Бібліотека `requests` надає верхній рівень абстракції: вона перетворює словники параметрів, об'єкти автентифікації, структури даних JSON та завантажувані файли у структуровані запити, керує глобальним контекстом сесії, обробляє цикли перенаправлень і надає єдину ієрархію об'єктів відповідей і винятків.

Нижче розташований рушій `urllib3`, який повністю бере на себе низькорівневу інженерію зв'язку: відкриття TCP-сокетів, виконання криптографічного рукостискання TLS з верифікацією за базою кореневих сертифікатів (CA bundle), організацію черг відкритих каналів (Connection Pooling) для уникнення повторних триетапних рукостискань TCP, роботу через HTTP/HTTPS проксі-сервери та прозору декомпресію стиснутих потоків даних (gzip, deflate, brotli).

![Багаторівнева архітектура HTTP-клієнта: від інтерфейсу requests до сокетів ОС](/root/eng/sf-web/requests-client/img/requests-layers.svg)

*Багаторівнева архітектура виконання запиту: клієнтський рівень requests готує об'єкт PreparedRequest, передає його транспортному адаптеру HTTPAdapter, який використовує менеджер пулів urllib3 для зв'язку з системними сокетами операційної системи.*

Для прикладного програміста цей розподіл проявляється в тому, що виклик верхнього рівня `requests.get()` чи робота з об'єктом `requests.Session` ніколи не оперує безпосередньо сокетами або байтовими фреймами. Натомість запит проходить крізь суворий конвеєр перетворень і передається транспортним адаптерам. Архітектурне рішення залишити базовий рушій на перевіреній моделі HTTP/1.1 з пулом з'єднань забезпечує абсолютну передбачуваність: на відміну від мультиплексування HTTP/2 чи HTTP/3, де збій одного потоку може впливати на спільне TCP-вікно, пул ізольованих сокетів `urllib3` гарантує повну автономність кожної паралельної транзакції.

## Життєвий цикл запиту: конвеєр перетворення у PreparedRequest

Коли викликається функція `requests.get()` або метод `session.post()`, бібліотека не відправляє байти в мережу негайно. Першим кроком є створення декларативного об'єкта `Request`, який інкапсулює сирі аргументи користувача, та його передача в конвеєр підготовки `Session.prepare_request(request)`, результатом якого стає повністю нормалізований об'єкт `PreparedRequest`.

Об'єкт `PreparedRequest` — це незмінний зліпок HTTP-запиту, де всі компоненти приведені до стандартів IETF (RFC 7230, RFC 7231, RFC 3986):

```python
import requests

# 1. Створення сирого декларативного запиту
req = requests.Request(
    method="POST",
    url="https://api.example.com/v1/items",
    params={"category": "електроніка", "limit": 10},
    json={"name": "Датчик тиску", "price": 450.0},
    headers={"Accept": "application/json", "X-Custom-Trace": "9a7f"},
    auth=("admin", "secret_pass")
)

# 2. Сесія виконує підготовку та нормалізацію
session = requests.Session()
prepared = session.prepare_request(req)

# Огляд сформованого зліпка запиту
print(prepared.method)   # 'POST'
print(prepared.url)      # 'https://api.example.com/v1/items?category=%D0%B5%D0%BB%D0%B5%D0%BA%D1%82%D1%80%D0%BE%D0%BD%D1%96%D0%BA%D0%B0&limit=10'
print(prepared.headers)  # CaseInsensitiveDict з автоматично доданими Content-Type, Content-Length, Authorization
print(prepared.body)     # b'{"name": "\xd0\x94\xd0\xb0\xd1\x82\xd1\x87\xd0\xb8\xd0\xba \xd1\x82\xd0\xb8\xd1\x81\xd0\xba\xd1\x83", "price": 450.0}'
```

![Життєвий цикл запиту: конвеєр обробки та перетворень](/root/eng/sf-web/requests-client/img/request-lifecycle.svg)

*Повний конвеєр життєвого циклу запиту: від початкового декларативного об'єкта Request до його підготовки в PreparedRequest, передачі в сокет, аналізу статус-кодів перенаправлення та формування кінцевого Response.*

Конвеєр підготовки запиту складається з шести послідовних кроків:

1. **Нормалізація та кодування URL (`prepare_url`):**
   - Перевіряється наявність схеми (`http://` або `https://`). Якщо схема відсутня, конвеєр переривається винятком `MissingSchema`.
   - Якщо доменне ім'я містить не-ASCII символи (наприклад, кирилицю чи умлаути), воно конвертується у сумісний формат Punycode за стандартом IDNA (Internationalized Domain Names in Applications). Наприклад, домен `тест.укр` транскодується в ASCII-безпечний вигляд `xn--e1aybc.xn--j1amh`.
   - Словник або список кортежів `params` серіалізується у query-рядок. Усі символи поза межами безпечного діапазону RFC 3986 (пробіли, кирилиця, спецсимволи) піддаються percent-encoding за допомогою функції `urllib.parse.quote_plus`. Значення сортуються для передбачуваності кешування.
2. **Нормалізація заголовків (`prepare_headers`):**
   - Заголовки запиту огортаються в спеціалізовану структуру `CaseInsensitiveDict`. Оскільки стандарт RFC 7230 вимагає нечутливості імен заголовків до регістру, пошук `headers['content-type']`, `headers['Content-Type']` та `headers['CONTENT-TYPE']` повертає однакове значення.
   - Заголовки, вказані на рівні запиту, зливаються із заголовками за замовчуванням об'єкта `Session` (наприклад, глобальними `User-Agent` або `Authorization`), причому локальні заголовки мають пріоритет.
   - Автоматично виставляються обов'язкові службові заголовки, якщо вони не були задані явно: `Host`, `User-Agent: python-requests/x.y.z`, `Accept-Encoding: gzip, deflate, br`, `Connection: keep-alive`.
3. **Серіалізація та пакування тіла (`prepare_body`):**
   - Якщо передано параметр `json`, об'єкт серіалізується у двійковий UTF-8 рядок через `json.dumps()`, а в заголовки автоматично додається `Content-Type: application/json`, якщо його не було вказано явно.
   - Якщо передано словник у `data`, він кодується у формат форми `application/x-www-form-urlencoded` за допомогою `urllib.parse.urlencode()`.
   - Якщо передано словник `files`, формується складне багатокомпонентне тіло `multipart/form-data`: генерується унікальний випадковий роздільник (MIME boundary), формуються індивідуальні службові заголовки `Content-Disposition` для кожного фрагмента та обчислюється загальний обсяг.
   - Якщо тіло є байтовим або рядковим масивом фіксованої довжини, обчислюється і встановлюється заголовок `Content-Length`.
   - Якщо тіло є генератором, файлоподібним потоком без відомої довжини або ітератором, заголовок `Content-Length` опускається, а замість нього виставляється заголовок `Transfer-Encoding: chunked` (поблокова передача даних).
4. **Застосування автентифікації (`prepare_auth`):**
   - Якщо об'єкт запиту містить кортеж автентифікації або спеціальний обробник `AuthBase`, викликається відповідний обробник. Для стандартної схеми HTTP Basic Auth формується заголовок `Authorization: Basic <base64(login:password)>`. Для складних схем (наприклад, HTTP Digest Auth) обробник може зареєструвати функцію зворотного виклику для обробки виклику-відповіді `401 Unauthorized`.
5. **Зведення cookie (`prepare_cookies`):**
   - Сесія зіставляє цільовий домен і шлях запиту зі своїм внутрішнім сховищем `CookieJar`. Усі валідні cookie для цього хоста об'єднуються з cookie, переданими безпосередньо у виклик, та серіалізуються в єдиний заголовок `Cookie: name1=val1; name2=val2`.
6. **Реєстрація зворотних викликів (`prepare_hooks`):**
   - До запиту прикріплюються обробники подій (наприклад, хук `response`, який викликається одразу після надходження відповіді від сервера).

Повний перелік параметрів методів, структур даних та повну ієрархію об'єктів містить [детальний опис структур Request, PreparedRequest, Response та ієрархію винятків](root:sf-web/requests-client/api-requests-structures.md).

## Транспортні адаптери та маршрутизація пулів з'єднань

Коли об'єкт `PreparedRequest` повністю сформований, об'єкт `Session` повинен вирішити, як саме доставити байти до адресата. Ця задача вирішується через механізм **транспортних адаптерів** (Transport Adapters).

У кожному об'єкті `Session` зареєстровано внутрішній словник префіксів URL:

```python
session = requests.Session()
# За замовчуванням зареєстровано два адаптери:
# 'https://' -> HTTPAdapter()
# 'http://'  -> HTTPAdapter()
```

Коли виконується виклик `session.send(prepared_request)`, сесія сканує зареєстровані префікси за алгоритмом найдовшого збігу (longest prefix match) і обирає відповідний екземпляр адаптера. Стандартним класом адаптера є `requests.adapters.HTTPAdapter`.

![Маршрутизація адаптерів Session та пулу з'єднань urllib3](/root/eng/sf-web/requests-client/img/transport-pool-routing.svg)

*Маршрутизація транспортних адаптерів: об'єкт Session зіставляє префікс URL із зареєстрованим адаптером HTTPAdapter, який обирає відповідний пул HTTPConnectionPool для конкретного хоста й порту.*

Головне завдання `HTTPAdapter` — трансляція запиту `PreparedRequest` у виклик менеджера пулів `urllib3.PoolManager`. Адаптер інкапсулює такі критичні мережеві параметри:

1. **Керування пулом сокетів (`pool_connections` та `pool_maxsize`):**
   - `pool_connections` визначає, скільки окремих екземплярів `HTTPConnectionPool` зберігається в кеші адаптера. Кожен унікальний кортеж `(схема, хост, порт)` отримує власний пул. Якщо сесія звертається до 20 різних мікросервісів, але `pool_connections=10`, адаптер буде витісняти найстаріші пули за принципом LRU, що змусить повторно встановлювати TCP-з'єднання при черговому зверненні до витісненого хоста.
   - `pool_maxsize` визначає максимальну кількість відкритих TCP-з'єднань, що утримуються в стані очікування всередині черги `LifoQueue` кожного пулу. Якщо програма виконує запити з кількох паралельних потоків, цей параметр задає ліміт одночасно відкритих сокетів. За замовчуванням `pool_maxsize=10`.
   - `pool_block`: булевий параметр. Якщо `pool_block=False` (за замовчуванням), при вичерпанні вільних з'єднань у пулі `urllib3` відкриває тимчасове з'єднання поза пулом і закриває його одразу після виконання запиту. Якщо `pool_block=True`, робочий потік блокується доти, доки один із зайнятих сокетів не повернеться в чергу, або доки не спливе таймаут.
2. **Розділення таймаутів (Connect Timeout проти Read Timeout):**
   - Мережевий таймаут у `requests` можна задавати єдиним числом `timeout=5.0` або кортежем із двох чисел `timeout=(3.0, 10.0)`.
   - **Connect Timeout (таймаут з'єднання):** граничний час на виконання системного виклику `connect()`, отримання відповіді TCP SYN/ACK від сервера та завершення TLS-рукостискання. Якщо мережевий маршрутизатор скидає пакети або сервер не відповідає, цей таймер запобігає тривалому блокуванню процесу. Зазвичай обирають значення, дещо більше за стандартний час повторної передачі TCP SYN (наприклад, 3.05 с).
   - **Read Timeout (таймаут читання):** максимальний інтервал очікування між отриманням чергових байтів даних від відкритого сокета після того, як з'єднання вже успішно встановлено. Якщо сервер прийняв запит, але завис під час генерації відповіді або виконання важкого SQL-запиту, спрацьовує `ReadTimeout`.
3. **Політика автоматичних повторів (`max_retries`):**
   - За замовчуванням `HTTPAdapter` виконує обмежену кількість повторів у разі раптового обриву TCP-з'єднання на рівні сокета. Розробник може передати повноцінний екземпляр `urllib3.util.Retry`, налаштувавши експоненційну затримку (backoff) та список кодів відповідей (429, 502, 503, 504), на які потрібно реагувати повтором.
4. **Оптимізація DNS-резолвінгу через утримання з'єднань:**
   - Системний виклик `socket.getaddrinfo()` у стандартній бібліотеці Python є синхронним блокуючим викликом. Якщо клієнт створює новий сокет на кожен HTTP-запит, затримка DNS-запиту додається до кожної операції. Повторне використання відкритого TCP-каналу всередині `HTTPConnectionPool` повністю усуває звернення до DNS для всіх наступних запитів до того самого хоста.

Як реалізувати власний адаптер із наскрізним трасуванням, вимірюванням затримок та кастомною логікою повторів, покроково розбирає [практичний проект створення користувацького HTTPAdapter для трасування та моніторингу затримок](root:sf-web/requests-client/proj-transport-adapter.md).

## Криптографічний шар: валідація сертифікатів TLS, CA-bundle certifi та mTLS

Під час звернення до захищених ресурсів через схему `https://` транспортний адаптер ініціює процес криптографічного рукостискання TLS поверх встановленого TCP-з'єднання. Ця процедура виконується модулем `ssl` мови Python, що базується на системній бібліотеці OpenSSL.

Процес перевірки захищеного каналу складається з трьох обов'язкових етапів:

1. **Індикація імені сервера (Server Name Indication, SNI):** Клієнт передає цільовий домен у незашифрованому полі розширення `server_name` у повідомленні `ClientHello`. Це дозволяє віддаленому серверу, який хостить сотні різних веб-сайтів на одній IP-адресі, вибрати та надіслати клієнту правильний сертифікат X.509 ще до встановлення зашифрованого тунелю.
2. **Перевірка ланцюжка довіри за базою CA:** За замовчуванням `requests` використовує пакет `certifi`, що містить регулярно оновлювану базу кореневих центрів сертифікації Mozilla. Клієнт будує ланцюжок від кінцевого сертифіката сервера через проміжні сертифікати до одного з довірених кореневих сертифікатів у сховищі, перевіряючи цифрові підписи кожного вузла ланцюжка, строк дії сертифіката та відповідність імені хоста полю `Subject Alternative Name` (SAN).
3. **Взаємна автентифікація TLS (mTLS):** У закритих корпоративних або банківських API сервер вимагає криптографічного підтвердження особи клієнта. Для цього у виклик передається параметр `cert=('client.crt', 'client.key')`. Під час рукостискання клієнт відправляє свій публічний сертифікат та підписує тимчасовий рядок виклику своїм приватним ключем, доводячи право на доступ до системи.

## Протокол поблокового передавання (Chunked Transfer Encoding)

Під час завантаження великих файлів (наприклад, резервних копій баз даних чи відеопотоків) клієнт часто не може заздалегідь знати загальний розмір тіла запиту у байтах для виставлення заголовка `Content-Length`. Завантаження всього файлу в пам'ять процесу для підрахунку його довжини призвело б до падіння процесу через вичерпання RAM (Out of Memory).

Для розв'язання цієї проблеми протокол HTTP 1.1 визначає механізм поблокової передачі `Transfer-Encoding: chunked`. У цьому режимі тіло розбивається на послідовність автономних блоків безпосередньо у сокетному потоці. Кожен блок має наступну двійкову структуру на рівні сокета:

```http
<розмір_блоку_в_шістнадцятковій_системі>\r\n
<байти_даних_блоку>\r\n
```

Завершення передачі всього документа позначається спеціальним термінальним блоком нульової довжини: `0\r\n\r\n`.

Бібліотека `requests` автоматично активує цей механізм, якщо у параметр `data` передано генератор або ітератор байтів:

```python
def stream_large_file(file_path: str):
    with open(file_path, "rb") as f:
        while chunk := f.read(65536): # Читання блоками по 64 КБ
            yield chunk

# Відправлення гігабайтного файлу без виділення гігабайта в RAM
response = requests.post(
    "https://storage.example.com/upload",
    data=stream_large_file("/var/backups/db.dump")
)
```

## Проксі-сервери: тунелювання через HTTP CONNECT

У корпоративних мережах прямий вихід у зовнішній інтернет із робочих станцій чи серверів часто заблокований, і весь трафік спрямовується через проміжні проксі-сервери. `requests` підтримує роботу через проксі шляхом налаштування словника `proxies` або автоматичного зчитування змінних середовища операційної системи `HTTP_PROXY`, `HTTPS_PROXY` та `NO_PROXY`.

Механіка взаємодії різниться залежно від схеми протоколу:

1. **Для незашифрованого HTTP:** Клієнт надсилає звичайний запит безпосередньо на проксі-сервер, вказуючи повний абсолютний URL у першому рядку: `GET http://example.com/index.html HTTP/1.1`. Проксі розбирає запит, самостійно звертається до цільового сервера й повертає результат клієнту.
2. **Для захищеного HTTPS (метод HTTP CONNECT):** Проксі не має права розшифровувати трафік клієнта. Тому клієнт спершу надсилає запит встановлення тунелю: `CONNECT example.com:443 HTTP/1.1`. Якщо проксі схвалює операцію, він відповідає `200 Connection Established` і перетворює з'єднання на прозорий байтовий міст. Після цього клієнт виконує стандартне рукостискання TLS безпосередньо з кінцевим сервером крізь створений тунель.

## Декодування відповіді, управління пам'яттю та життєвий цикл сокета

Після того як `urllib3` відправив байти запиту в сокет і прочитав статусний рядок та заголовки сервера, `HTTPAdapter.build_response()` створює екземпляр класу `requests.Response`. 

На цьому етапі виникає критична розвилка у роботі з оперативною пам'яттю та мережевим сокетом: **жадібне читання** (`stream=False`, за замовчуванням) проти **потокового читання** (`stream=True`).

### Жадібне читання (`stream=False`)

За замовчуванням `requests` негайно вичитує все тіло відповіді з сокета в оперативну пам'ять процесу. Щойно останній байт прочитано:
1. Сирі байти зберігаються у внутрішньому атрибуті `response._content`.
2. Сокетне з'єднання звільняється і негайно повертається в чергу відповідного `HTTPConnectionPool` для наступних запитів.
3. Доступ до `response.content` миттєво повертає байти з пам'яті без будь-якого повторного мережевого введення-виведення.

Це гарантує безпеку: розробник не може випадково заблокувати або вичерпати пул з'єднань, навіть якщо забуде закрити об'єкт відповіді.

### Потокове читання (`stream=True`) та небезпека вичерпання пулу

Якщо у виклик передано аргумент `stream=True`, бібліотека зчитує лише заголовки HTTP. Тіло відповіді залишається у відкритому сокеті, а доступ до нього здійснюється через ітератори `response.iter_content(chunk_size)` або `response.iter_lines()`:

```python
import requests

# Потокове завантаження великого архіву без завантаження всього файлу в RAM
with requests.get("https://cdn.example.com/large-dataset.tar.gz", stream=True) as response:
    response.raise_for_status()
    with open("dataset.tar.gz", "wb") as f:
        for chunk in response.iter_content(chunk_size=65536): # 64 КБ буфер
            if chunk:
                f.write(chunk)
```

Головна пастка полягає в тому, що **доки потік не вичитано до кінця або не викликано `response.close()`, TCP-сокет залишається закріпленим за цим конкретним об'єктом відповіді**. Він не повертається в пул і не може бути використаний іншими запитами. Якщо програма відкриє кілька таких потоків і не закриє їх (наприклад, через виникнення винятку), пул з'єднань буде заблоковано, і всі наступні запити до цього хоста зависнуть або впадуть із помилкою.

### Розпакування та визначення кодувань: content проти text

Об'єкт `Response` надає дві принципово різні властивості для доступу до тіла:

1. **`response.content` (байти):**
   - Повертає сирий масив байтів (`bytes`).
   - Якщо сервер повернув стиснені дані з заголовком `Content-Encoding: gzip` (або `deflate`/`br`), `urllib3` прозоро декомпресує потік. Властивість `response.content` містить уже розпаковані байти.
2. **`response.text` (Unicode-рядок):**
   - Перетворює байти `response.content` у текстовий рядок `str` за допомогою кодування, вказаного в `response.encoding`.
   - Якщо заголовок `Content-Type` містить явну директиву кодування (наприклад, `text/html; charset=utf-8`), `requests` використовує значення `utf-8`.
   - Якщо директива відсутня, бібліотека запускає евристичний детектор (`charset_normalizer` або `chardet`), який аналізує байти тіла для визначення ймовірного кодування.

Історичною пасткою версій HTTP 1.1 за стандартом RFC 2616 було правило, згідно з яким будь-який документ типу `text/*` без явного `charset` вважався закодованим у `ISO-8859-1` (Latin-1). Довгий час `requests` суворо слідував цьому правилу, через що кириличні або східноазійські сайти без явного `charset` у заголовку перетворювалися в `response.text` на нечитабельні спотворені символи (кракозябри). У таких випадках розробник повинен або явно перезаписати `response.encoding = 'utf-8'`, або самостійно декодувати байти: `response.content.decode('utf-8')`.

## Механізм перенаправлень та збереження стану

Протокол HTTP визначає сімейство статус-кодів перенаправлення `3xx`. Якщо сервер повертає статус `301`, `302`, `303`, `307` чи `308`, клієнт повинен вирішити: чи переходити за новим URL, вказаним у заголовку `Location`, як змінити HTTP-метод та чи безпечно передавати конфіденційні заголовки.

У `requests` за цю логіку відповідає внутрішній генератор `Session.resolve_redirects`:

```python
response = requests.post(
    "http://example.com/login",
    data={"user": "alice"},
    allow_redirects=True
)

# Якщо сервер відповів 301 на HTTPS-версію, response містить фінальну відповідь
print(response.status_code) # 200
print(response.url)         # 'https://example.com/dashboard'

# Історія перенаправлень зберігається у вигляді ланцюжка
for prev in response.history:
    print(f"Крок: {prev.status_code} -> {prev.headers.get('Location')}")
```

Механізм редиректів виконує три ключові правила безпеки та сумісності:

1. **Мутація методів:**
   - Код `303 See Other` завжди змушує клієнта змінити метод на `GET`, а тіло запиту скидається.
   - Коди `301 Moved Permanently` та `302 Found` для методів `POST` за замовчуванням історично змінюються клієнтами на `GET` (патерн Post/Redirect/Get).
   - Коди `307 Temporary Redirect` та `308 Permanent Redirect` суворо забороняють зміну HTTP-методу: якщо первинний запит був `POST` з бінарним тілом, повторний запит за новою адресою буде виконано тим самим методом `POST` із збереженням тіла.
2. **Очищення конфіденційних заголовків (Cross-Origin Protection):**
   - Якщо перенаправлення веде на інший хост або змінює протокол (наприклад, з `https://auth.internal.corp` на сторонній `https://cdn.partner.com`), сесія автоматично видаляє заголовки `Authorization` та `Proxy-Authorization`. Це запобігає витоку секретних Bearer-токенів чи паролів на зовнішні сервери під час відкритих редиректів.
3. **Захист від нескінченних циклів:**
   - Якщо сервери перенаправляють запит по колу (`A -> B -> A`), сесія відстежує лічильник переходів і після перевищення `max_redirects` (за замовчуванням 30) генерує виняток `requests.exceptions.TooManyRedirects`.

## Порівняння із системними реалізаціями клієнтів на C та C++

Щоб зрозуміти, яку саме роботу приховує високорівневий інтерфейс `requests`, корисно зіставити його з низькорівневою реалізацією аналогічного HTTP-клієнта мовами C та C++ на базі промислової бібліотеки `libcurl`.

У C/C++ відправлення запиту вимагає ручного керування структурами пам'яті, створення списків заголовків `curl_slist`, реєстрації функцій зворотного виклику для збирання чанків відповіді в пам'ять та явного звільнення кожного ресурсу.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <curl/curl.h>

struct HttpResponse {
    char *data;
    size_t size;
};

static size_t write_memory_callback(void *contents, size_t size, size_t nmemb, void *userp) {
    size_t total_size = size * nmemb;
    struct HttpResponse *resp = (struct HttpResponse *)userp;

    char *ptr = realloc(resp->data, resp->size + total_size + 1);
    if (!ptr) return 0; // Нестача оперативної пам'яті

    resp->data = ptr;
    memcpy(&(resp->data[resp->size]), contents, total_size);
    resp->size += total_size;
    resp->data[resp->size] = '\0';

    return total_size;
}

int main(void) {
    curl_global_init(CURL_GLOBAL_DEFAULT);
    CURL *curl = curl_easy_init();

    if (!curl) {
        fprintf(stderr, "Помилка ініціалізації curl\n");
        return 1;
    }

    struct HttpResponse response = { .data = malloc(1), .size = 0 };
    struct curl_slist *headers = NULL;

    headers = curl_slist_append(headers, "Content-Type: application/json");
    headers = curl_slist_append(headers, "Accept: application/json");

    const char *payload = "{\"sensor\":\"BMP280\",\"pressure_hpa\":1013.25}";

    // Налаштування параметрів запиту (аналог PreparedRequest)
    curl_easy_setopt(curl, CURLOPT_URL, "https://httpbin.org/post");
    curl_easy_setopt(curl, CURLOPT_POSTFIELDS, payload);
    curl_easy_setopt(curl, CURLOPT_HTTPHEADER, headers);
    curl_easy_setopt(curl, CURLOPT_WRITEFUNCTION, write_memory_callback);
    curl_easy_setopt(curl, CURLOPT_WRITEDATA, (void *)&response);
    curl_easy_setopt(curl, CURLOPT_TIMEOUT, 10L);
    curl_easy_setopt(curl, CURLOPT_CONNECTTIMEOUT, 3L);
    curl_easy_setopt(curl, CURLOPT_FOLLOWLOCATION, 1L); // allow_redirects=True

    CURLcode res = curl_easy_perform(curl);

    if (res == CURLE_OK) {
        long status_code = 0;
        curl_easy_getinfo(curl, CURLINFO_RESPONSE_CODE, &status_code);
        printf("HTTP-статус: %ld, Отримано байтів: %zu\n", status_code, response.size);
    } else {
        fprintf(stderr, "Мережевий збій: %s\n", curl_easy_strerror(res));
    }

    // Ручне звільнення всіх низькорівневих ресурсів
    curl_slist_free_all(headers);
    free(response.data);
    curl_easy_cleanup(curl);
    curl_global_cleanup();

    return 0;
}
```

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <memory>
#include <expected>
#include <format>
#include <curl/curl.h>

class NativeHttpClient {
public:
    struct Response {
        long status_code{0};
        std::string body;
    };

    struct SListDeleter {
        void operator()(curl_slist* list) const noexcept {
            if (list) curl_slist_free_all(list);
        }
    };
    using SListPtr = std::unique_ptr<curl_slist, SListDeleter>;

    struct CurlDeleter {
        void operator()(CURL* handle) const noexcept {
            if (handle) curl_easy_cleanup(handle);
        }
    };
    using CurlPtr = std::unique_ptr<CURL, CurlDeleter>;

    NativeHttpClient() : curl_(curl_easy_init()) {
        if (!curl_) {
            throw std::runtime_error("Неможливо ініціалізувати CURL дескриптор");
        }
    }

    std::expected<Response, std::string> post_json(const std::string& url, const std::string& json_body, long timeout_sec = 10) {
        std::string response_buffer;
        SListPtr headers;

        // Безпечне додавання заголовків
        headers.reset(curl_slist_append(headers.release(), "Content-Type: application/json"));
        headers.reset(curl_slist_append(headers.release(), "Accept: application/json"));

        curl_easy_setopt(curl_.get(), CURLOPT_URL, url.c_str());
        curl_easy_setopt(curl_.get(), CURLOPT_POSTFIELDS, json_body.c_str());
        curl_easy_setopt(curl_.get(), CURLOPT_HTTPHEADER, headers.get());
        curl_easy_setopt(curl_.get(), CURLOPT_WRITEFUNCTION, &NativeHttpClient::writeCallback);
        curl_easy_setopt(curl_.get(), CURLOPT_WRITEDATA, &response_buffer);
        curl_easy_setopt(curl_.get(), CURLOPT_TIMEOUT, timeout_sec);
        curl_easy_setopt(curl_.get(), CURLOPT_CONNECTTIMEOUT, 3L);
        curl_easy_setopt(curl_.get(), CURLOPT_FOLLOWLOCATION, 1L);

        CURLcode res = curl_easy_perform(curl_.get());
        if (res != CURLE_OK) {
            return std::unexpected(std::format("Помилка запиту libcurl: {}", curl_easy_strerror(res)));
        }

        long status_code = 0;
        curl_easy_getinfo(curl_.get(), CURLINFO_RESPONSE_CODE, &status_code);

        return Response{
            .status_code = status_code,
            .body = std::move(response_buffer)
        };
    }

private:
    static size_t writeCallback(char* ptr, size_t size, size_t nmemb, void* userdata) {
        auto* buffer = static_cast<std::string*>(userdata);
        size_t total = size * nmemb;
        buffer->append(ptr, total);
        return total;
    }

    CurlPtr curl_;
};

int main() {
    curl_global_init(CURL_GLOBAL_DEFAULT);
    try {
        NativeHttpClient client;
        auto result = client.post_json("https://httpbin.org/post", "{\"sensor\":\"BMP280\",\"pressure_hpa\":1013.25}");
        if (result) {
            std::cout << std::format("Успіх! Статус: {}, Тіло: {} байтів\n", result->status_code, result->body.size());
        } else {
            std::cerr << result.error() << '\n';
        }
    } catch (const std::exception& e) {
        std::cerr << "Виняток: " << e.what() << '\n';
    }
    curl_global_cleanup();
    return 0;
}
```

## Діагностика сокетів та спостереження за пулом з'єднань

Для діагностики поведінки пулу з'єднань у промислових умовах операційні системи надають спеціалізовані інструменти аудиту мережевих дескрипторів. У середовищі Linux відкриті сокети процесу можна простежити через віртуальну файлову систему `procfs` та системні утиліти `ss` (Socket Statistics) або `lsof`:

```bash
# Перегляд відкритих сокетів конкретного Python-процесу за його PID
lsof -p 14205 -a -i tcp

# Моніторинг активних TCP-каналів, стану черг send/recv та таймерів Keep-Alive
ss -t -i -p '( sport = :http or sport = :https or dport = :https )'
```

Якщо в журналі `ss` з'являється велика кількість з'єднань у стані `TIME_WAIT` або `CLOSE_WAIT`, це свідчить про системні проблеми:
- Велика кількість `TIME_WAIT` означає, що клієнт постійно ініціює закриття з'єднань замість їх повторного використання через пул `Session`.
- Наявність `CLOSE_WAIT` вказує на те, що сервер уже закрив TCP-канал (надіслав пакет TCP FIN), але клієнтська програма не викликала `response.close()` або не завершила читання з об'єкта `Response`, утримуючи дескриптор файлу у завислому стані.

## Поняття та термінологія

Після детального розгляду внутрішнього улаштування клієнта сформулюємо ключові терміни, що лежать в основі цієї архітектури:

- **Сесія** (від лат. *sessio* — «сидіння», тривале перебування в певному стані) — об'єкт збереження контексту між кількома послідовними запитами до одного або кількох серверів, що інкапсулює спільні заголовки, сховище cookie та конфігурацію автентифікації.
- **Адаптер** (від лат. *adaptare* — «пристосовувати») — проміжний програмний компонент, який перетворює стандартні об'єкти підготовленого запиту в специфічні виклики конкретного мережевого рушія або протоколу.
- **Транспорт** (від лат. *transportare* — «переносити через») — рівень мережевого стека, відповідальний за фізичну або логічну передачу байтових потоків між вузлами мережі через сокети.
- **Пул** (від фр. *poule* — «спільна каса», колективний фонд) — черга попередньо створених і збережених ресурсів (мережевих TCP-з'єднань), готових до миттєвого повторного використання для уникнення накладних витрат на їх повторне відкриття.
- **Проксі** (від англ. *proxy*, що походить від лат. *procurator* — «управитель, представник») — проміжний серверний вузол, який приймає запити клієнта, передає їх кінцевому призначенню та повертає відповідь клієнту, маскуючи його мережеву адресу або здійснюючи фільтрацію трафіку.
- **Декодування** (від лат. *de-* — «скасування/зняття» та *codex* — «збірник правил, книга») — процес зворотного перетворення сирої послідовності байтів у символьні представлення згідно з визначеною таблицею кодування символів.

## Крайові випадки, пастки та вартість виконання

Робота з високорівневим клієнтом приховує кілька небезпечних системних пасток, які виникають при переході в промислове середовище:

1. **Зависання потоків через відсутність таймаутів:** За замовчуванням у `requests` значення `timeout=None`. Якщо віддалений сервер або проміжний фаєрвол мовчки скине TCP-пакети (DROP замість REJECT), сокет зависне у стані очікування на системному виклику `recv()`, утримуючи потік виконання невизначено довго. Будь-який виробничий виклик зобов'язаний містити явний таймаут: `session.get(url, timeout=(3.05, 15.0))`.
2. **Вимкнення перевірки TLS (`verify=False`):** Встановлення `verify=False` вимикає валідацію сертифікатів X.509. У такому режимі клієнт стає вразливим до атак типу Man-in-the-Middle (MITM), коли зловмисник на рівні маршрутизатора чи DNS підміняє сертифікат і перехоплює конфіденційні дані (токени, паролі).
3. **Вичерпання черги пулу при багатопотоковості:** Якщо 100 потоків одночасно намагаються відправити запит до одного хоста через сесію з `pool_maxsize=10`, за замовчуванням надлишкові з'єднання створюються поза пулом і знищуються одразу після використання. Це призводить до сплеску споживання системних файлових дескрипторів (`EMFILE: Too many open files`). Налаштування `HTTPAdapter(pool_maxsize=100, pool_block=True)` змушує потоки безпечно очікувати звільнення сокетів у черзі.
4. **Неідемпотентні повтори (Non-idempotent retries):** Налаштування агресивних автоматичних повторів для методів `POST` або `PATCH` є небезпечним: якщо сервер отримав запит на списання коштів, виконав операцію в базі даних, але обірвав з'єднання до передачі відповіді, повторний запит виконає операцію вдруге.
5. **Багатопотокова модифікація Session (Race Conditions):** Хоча внутрішній пул сокетів `urllib3` є потокобезпечним, сам екземпляр `requests.Session` не є повністю потокобезпечним для мутацій стану. Якщо один потік змінює `session.headers` або `session.cookies` під час того, як інший потік виконує `session.get()`, виникає стан гонитви (race condition). У багатопотокових сервісах рекомендується або створювати окремий екземпляр `Session` на кожен робочий потік, або передавати специфічні заголовки виключно як локальні аргументи конкретного виклику `request()`.
6. **Обрив з'єднання з боку сервера (Broken Pipe та ECONNRESET):** Сервери часто налаштовують таймаут простою каналу (Keep-Alive Timeout, наприклад, 5 секунд у Nginx). Якщо з'єднання пролежало в пулі клієнта довше цього часу, сервер надсилає TCP FIN і закриває свою половину сокета. Якщо клієнт спробує відправити новий запит у цей сокет без попередньої перевірки його стану через `poll()` / `select()`, операційна система згенерує помилку `ConnectionResetError` або `BrokenPipeError`. Менеджер `urllib3` автоматично перехоплює такі збої «мертвих сокетів» і прозоро повторює спробу на новому TCP-каналі, якщо запит є ідемпотентним.
