# 📜 Історія HTTP-клієнтів у Python: від urllib2 до requests та відокремлення urllib3

Коли 1994 року в стандартну бібліотеку Python 1.1 було включено модуль `urllib`, протокол HTTP 1.0 був простим текстовим протоколом: клієнт відкривав TCP-з'єднання, відсилав один рядок запиту `GET /path HTTP/1.0`, отримував HTML-документ і сервер негайно розривав сокет. Для такої моделі функція `urllib.urlopen("http://example.com")` була досконалим рішенням — вона маскувала мережевий виклик під звичайне відкриття локального файлу, повертаючи об'єкт із методом `read()`.

Проте розвиток інтернету швидко зламав цю просту модель. Поява протоколу HTTP 1.1 із тривалими з'єднаннями (Keep-Alive), заголовками віртуальних хостів `Host:`, проміжними проксі-серверами, складними схемами автентифікації (Basic, Digest) та кукі вимагала збереження стану між викликами.

## Розпад стандартної бібліотеки: urllib проти urllib2

У спробі адаптувати мову до нового веб-середовища розробники Python 2.0 (2000 рік) створили новий модуль — `urllib2`. Проте замість заміни старого модуля `urllib` його залишили поруч, створивши хаотичне розділення обов'язків:
- `urllib` містив функції кодування параметрів `urlencode` та розбору рядків;
- `urllib2` надавав об'єктно-орієнтовану модель `Request` та механізм обробників `OpenerDirector` і `BaseHandler`.

Щоб виконати елементарну дію, яка стала стандартом сучасної веб-розробки — наприклад, надіслати `POST`-запит із даними JSON, передати заголовок авторизації та автоматично зберегти сесійні cookie, — розробнику на Python доводилося писати понад двадцять рядків заплутаного низькорівневого коду:

```python
import json
import urllib
import urllib2
import cookielib

# Створення сховища cookie
cookie_jar = cookielib.CookieJar()
cookie_processor = urllib2.HTTPCookieProcessor(cookie_jar)

# Налаштування менеджера автентифікації
password_mgr = urllib2.HTTPPasswordMgrWithDefaultRealm()
password_mgr.add_password(None, "https://api.example.com", "user", "secret")
auth_handler = urllib2.HTTPBasicAuthHandler(password_mgr)

# Збирання конвеєра відкриття
opener = urllib2.build_opener(cookie_processor, auth_handler)
urllib2.install_opener(opener)

# Підготовка тіла та заголовків
payload = json.dumps({"query": "status"}).encode("utf-8")
request = urllib2.Request(
    "https://api.example.com/v1/data",
    data=payload,
    headers={
        "Content-Type": "application/json; charset=utf-8",
        "Accept": "application/json",
        "User-Agent": "CustomApp/1.0"
    }
)

# Виконання запиту та ручне перехоплення статус-кодів
try:
    response = opener.open(request, timeout=10)
    body = response.read()
except urllib2.HTTPError as exc:
    print(f"Помилка HTTP {exc.code}: {exc.read()}")
except urllib2.URLError as exc:
    print(f"Помилка мережі: {exc.reason}")
```

У цій моделі кожен аспект мережевого зв'язку — додавання обробника перенаправлень, керування проксі чи валідація сертифікатів TLS — вимагав створення окремого класу-обробника (`Handler`) та повторного збирання ланцюжка `build_opener`. Якщо сервер повертав статус `404 Not Found` або `500 Internal Server Error`, `urllib2` генерував виняток `HTTPError`, який одночасно був об'єктом відповіді, що ламало передбачуваність обробки помилок.

Крім того, `urllib2` не мав вбудованого пулу з'єднань. Кожен новий виклик створював новий TCP-сокет і виконував повторне рукостискання TLS, що сповільнювало взаємодію з REST API у десятки разів.

## Поява urllib3: інженерія пулів з'єднань

2008 року Андрій Петров (Andrey Petrov) розпочав роботу над проектом `urllib3`. Його метою було вирішення суто системних інженерних задач, які ігнорувала стандартна бібліотека:
1. **Повторне використання сокетів (Connection Pooling):** утримання пулу відкритих TCP-з'єднань до кожного хоста, що усувало накладні витрати на триетапне рукостискання TCP та обмін сертифікатами TLS під час серії запитів.
2. **Потокобезпечність (Thread Safety):** можливість одночасного використання одного пулу з'єднань багатьма робочими потоками без блокувань і взаємних перезаписів буферів завдяки використанню потокобезпечних черг `LifoQueue`.
3. **Потокове передавання та декомпресія:** прозоре розпакування алгоритмами gzip/deflate прямо на льоту під час читання сокетного потоку без потреби накопичувати все тіло в оперативній пам'яті.
4. **Політика надійних повторів (Retry Strategies):** автоматичне повторення запитів у разі розриву TCP-з'єднання або тимчасової недоступності шлюзу за експоненційним законом затримки.

`urllib3` став еталонним мережевим рушієм, але його інтерфейс залишався орієнтованим на системні деталі: розробник повинен був оперувати менеджерами пулів (`PoolManager`), самостійно форматувати рядки запитів і вручну керувати життєвим циклом буферів.

## 2011 рік: маніфест «HTTP for Humans» Кеннета Рейтца

На початку 2011 року американський розробник Кеннет Рейтц (Kenneth Reitz) сформулював концепцію бібліотеки, що мала радикально змінити досвід взаємодії з HTTP у мові Python. Він висунув тезу, що робота з мережею повинна відповідати ментальній моделі людини, а не внутрішньому улаштуванню сокетного стека операційної системи.

13 лютого 2011 року Рейтц опублікував першу версію бібліотеки `requests` під гаслом «HTTP for Humans» (HTTP для людей):

```python
import requests

response = requests.post(
    "https://api.example.com/v1/data",
    json={"query": "status"},
    auth=("user", "secret"),
    timeout=10
)
data = response.json()
```

Замість багатоповерхового конструювання обробників, виклик зводився до одного виразного рядка. Ключовими інноваціями інтерфейсу requests стали:
- **Декларативні параметри:** аргументи `json=`, `data=`, `params=`, `headers=`, `auth=` брали на себе кодування, серіалізацію та виставлення відповідних службових заголовків `Content-Type` і `Content-Length`.
- **Єдиний об'єкт сесії (`Session`):** збереження cookie, заголовків за замовчуванням та конфігурації TLS у межах контексту сесії.
- **Передбачувана обробка помилок:** статус-коди `4xx` та `5xx` не викидали винятків автоматично, дозволяючи прочитати тіло відповіді сервера, але надавали явний метод `response.raise_for_status()`.
- **Автоматичне декодування кодувань:** використання заголовка `Content-Type` та евристичного аналізу для прозорого перетворення сирих байтів у рядки `response.text`.

## Симбіоз requests та urllib3

Перші версії `requests` використовували всередині стандартний `httplib`, проте Рейтц швидко зіткнувся з обмеженнями продуктивності та відсутністю пулів з'єднань. У версії `requests 0.8.0` відбулося злиття архітектур: `requests` повністю перейшов на `urllib3` як базовий транспортний рушій.

Це розділення обов'язків визначило сучасну архітектуру:
- `requests` відповідає за **людино-орієнтований інтерфейс**, підготовку об'єктів `PreparedRequest`, управління сесіями, маршрутизацію через транспортні адаптери `HTTPAdapter` та обробку редиректів;
- `urllib3` відповідає за **транспортну інженерію**: пули TCP-з'єднань `HTTPConnectionPool`, черги сокетів, безпеку TLS та низькорівневе читання потоків.

## Вплив на індустрію та спадщина

Успіх `requests` створив новий стандарт проектування API у мовах програмування. До появи `requests` бібліотеки клієнтів у більшості мов відтворювали низькорівневу термінологію сокетів та обробників. Після 2011 року архітектурні патерни Кеннета Рейтца — декларативні параметри методів, об'єкти сесій, структуровані адаптери та метод `raise_for_status()` — були запозичені в десятках інших екосистем:
- у мові Rust бібліотека `reqwest` побудована за прямим зразком `requests`;
- у мові Go бібліотека `go-resty` реалізує ідентичну ланцюжкову модель параметрів;
- у мові Python наступне покоління асинхронних клієнтів (`httpx`, `aiohttp`) зберегло сигнатури та поведінкові інваріанти `requests`.

Станом на середину 2020-х років бібліотека `requests` завантажується понад 300 мільйонів разів на місяць і залишається найпопулярнішим мережевим інструментом у світовій практиці програмування на Python.
