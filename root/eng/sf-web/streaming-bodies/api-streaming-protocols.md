# 📋 Специфікація протоколів потокового передавання: HTTP/1.1 chunked, HTTP/2 DATA та системні сокети

Потокове передавання великих тіл у сучасному вебі спирається на три рівні стандартизованих специфікацій: текстове кадрування HTTP/1.1 за стандартом RFC 9112, бінарне фреймування та керування потоком HTTP/2 за RFC 9113, а також низькорівневі системні інтерфейси конфігурації мережевих буферів сокетів POSIX.

### Граматика блокового кодування HTTP/1.1 (RFC 9112 §7.1)

Блокове кодування (`Transfer-Encoding: chunked`) трансформує неструктурований потік байтів у послідовність самоописових фрагментів. Формальний синтаксис розширеної форми Бекуса — Наура (ABNF) визначає таку структуру повідомлення:

```http
chunked-body     = *chunk
                   last-chunk
                   trailer-section
                   CRLF

chunk            = chunk-size [ BWS chunk-ext ] CRLF
                   chunk-data CRLF
chunk-size       = 1*HEXDIG
last-chunk       = 1*("0") [ BWS chunk-ext ] CRLF

chunk-data       = 1*OCTET ; рівно стільки байтів, скільки вказано в chunk-size
chunk-ext        = *( BWS ";" BWS chunk-ext-name [ BWS "=" BWS chunk-ext-val ] )
chunk-ext-name   = token
chunk-ext-val    = token / quoted-string

trailer-section  = *( field-line CRLF )
```

Кожен фрагмент складається з обов'язкового рядка розміру, корисного навантаження та завершального розділювача. Розмір блоку задається послідовністю шістнадцяткових цифр без префікса `0x`. Дозволено використання символів як нижнього (`a-f`), так і верхнього (`A-F`) регістрів. Наявність будь-яких проміжних пробілів безпосередньо всередині шістнадцяткового числа суворо заборонена й трактується парсером як критична помилка формату запиту з поверненням клієнтові статусу 400 Bad Request.

Після шістнадцяткового значення розміру опціонально можуть слідувати параметри розширення фрагмента (`chunk-ext`), відокремлені крапкою з комою. Якщо клієнт або проміжний проксі-сервер не підтримує зазначене розширення, стандарт RFC 9112 вимагає проігнорувати його й продовжити читання даних. Завершується рядок розміру обов'язковою послідовністю символів повернення каретки та переведення рядка `\r\n` (CRLF). Застосування самого лише символу нового рядка `\n` без повернення каретки `\r` порушує граматику протоколу.

Завершення всього тіла передавання сигналізується термінальним блоком `last-chunk`, у якому розмір дорівнює нулю (`0\r\n`). Після цього блоку може слідувати секція трейлерів, яка завершується кінцевим порожнім рядком `\r\n`.

### Специфікація секції трейлерів (Trailer Headers)

Трейлери дозволяють відправникові передавати додаткові метадані, розраховані або зібрані безпосередньо під час генерації та трансляції потоку, без потреби попереднього перегляду даних або їхнього тимчасового збереження в буфері оперативної пам'яті.

Для того щоб одержувач знав про наявність трейлерів і не закривав сесію розбору передчасно, відправник повинен оголосити список усіх запланованих заголовків у головній секції HTTP-заголовків через директиву `Trailer: Header-Name1, Header-Name2`. Якщо клієнт явно зазначає у своєму запиті заголовок `TE: trailers`, це сигналізує серверу про повну готовність приймати та обробляти кінцеві метадані.

Стандарт RFC 9112 §7.1.2 накладає суворі обмеження на типи заголовків, які дозволено передавати в секції трейлерів. Заборонено розміщувати такі класи полів:
1. **Заголовки керування транспортом і кодуванням:** `Transfer-Encoding`, `Content-Length`, `Connection`, `Keep-Alive`, `Upgrade`. Їхня поява в кінці потоку порушила б детермінізм роботи транспортного автомата.
2. **Заголовки маршрутизації та адресації:** `Host`, `Authority`. Ці поля критично необхідні проксі-серверам до початку передавання тіла для вибору цільового вузла.
3. **Заголовки безпеки, авторизації та керування сесіями:** `Authorization`, `Set-Cookie`, `Cookie`, `WWW-Authenticate`, `Proxy-Authenticate`. Клієнтська сторона не повинна змінювати стан автентифікації на основі даних, отриманих після завершення передавання основного ресурсу.
4. **Валідатори та умовні заголовки кешування:** `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Range`.

### Бінарне кадрування та фрейми DATA в HTTP/2 (RFC 9113)

У протоколі HTTP/2 текстове блокове кодування було повністю вилучено зі специфікації, а натомість запроваджено єдину систему бінарного фреймування. Будь-яке корисне навантаження запиту чи відповіді розбивається на окремі бінарні фрейми типу `DATA` (числовий тип `0x00`).

Кожен фрейм починається зі стандартного 9-байтового заголовка фіксованого формату:

```
 +-----------------------------------------------+
 |                 Length (24)                   |
 +---------------+---------------+---------------+
 |   Type (8)    |   Flags (8)   |
 +-+-------------+---------------+---------------+
 |R|                 Stream Identifier (31)      |
 +=+=============================================+
 |                   Data (*)                    |
 +-----------------------------------------------+
```

Поле довжини займає 24 біти й задає розмір корисного навантаження конкретного фрейму. За замовчуванням максимальний розмір одного фрейму обмежено величиною 16 384 байти (16 КБ). Клієнт і сервер можуть узгодити більший ліміт (аж до `2²⁴ - 1 = 16 777 215` байтів) через передавання параметра `SETTINGS_MAX_FRAME_SIZE` під час початкового узгодження параметрів з'єднання.

Поле прапорців (Flags) містить бінарні індикатори стану. Ключовим для потокового передавання є прапорець `END_STREAM` (біт `0x01`). Коли відправник надсилає останній фрагмент даних у потоці, встановлення цього прапорця інформує протилежну сторону про успішне завершення передавання тіла, еквівалентно до нульового блоку `0\r\n\r\n` у HTTP/1.1. Прапорець `PADDED` (біт `0x08`) вказує на наявність вирівнювального заповнення для маскування точного розміру переданих даних від атак на основі аналізу трафіку.

Поле `Stream Identifier` (31 біт) визначає логічний потік, до якого належить фрейм. Завдяки цьому в одному фізичному TCP-з'єднанні можуть одночасно транслюватися сотні незалежних потоків даних, чергуючи окремі фрейми `DATA` без ризику сплутування їхнього вмісту.

### Дворівневе керування потоком (Flow Control) через WINDOW_UPDATE

Для захисту повільних споживачів від переповнення внутрішніх буферів швидкими відправниками протокол HTTP/2 реалізує власний прикладний механізм зворотного тиску. Він функціонує паралельно з транспортним керуванням вікном TCP, але забезпечує ізоляцію окремих логічних потоків.

Керування вікном є строго двоконтурним:
1. **Вікно на рівні окремого потоку (Stream-Level Window):** обмежує обсяг даних, які можуть бути надіслані в конкретний потік. За замовчуванням після відкриття потоку його розмір становить 65 535 байтів.
2. **Вікно на рівні всього з'єднання (Connection-Level Window):** обмежує сумарний обсяг даних усіх паралельних потоків у межах одного фізичного сокета (також 65 535 байтів за замовчуванням).

Одержувач даних, вичитуючи фрейми `DATA` зі свого буфера додатку, періодично відправляє відправникові службові фрейми `WINDOW_UPDATE` (тип `0x08`). У такому фреймі передається 31-бітне беззнакове число, яке показує, на скільки байтів збільшується доступний кредит на передавання. Якщо баланс вікна відправника падає до нуля, він зобов'язаний негайно призупинити надсилання фреймів `DATA` для цього потоку або з'єднання в цілому, доки не надійде черговий `WINDOW_UPDATE`. Спроба відправити дані понад розмір відкритого вікна карається розривом потоку помилкою `FLOW_CONTROL_ERROR`.

### Параметри конфігурації системних сокетів POSIX та буфери ядра

Ефективність потокового конвеєра на рівні операційної системи визначається взаємодією між системними викликами введення-виведення та внутрішніми структурами мережевого стека ядра Linux.

Основними параметрами керування буферизацією є системні опції, які налаштовуються через виклик `setsockopt()`:

:::tabs
```c
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

void configure_streaming_socket(int sock_fd) {
    int rcvbuf = 128 * 1024;
    setsockopt(sock_fd, SOL_SOCKET, SO_RCVBUF, &rcvbuf, sizeof(rcvbuf));

    int sndbuf = 128 * 1024;
    setsockopt(sock_fd, SOL_SOCKET, SO_SNDBUF, &sndbuf, sizeof(sndbuf));

    int nodelay = 1;
    setsockopt(sock_fd, IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay));
}
```
```cpp
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

void configure_streaming_socket(int sock_fd) noexcept {
    constexpr int kBufferSize = 128 * 1024;
    ::setsockopt(sock_fd, SOL_SOCKET, SO_RCVBUF, &kBufferSize, sizeof(kBufferSize));
    ::setsockopt(sock_fd, SOL_SOCKET, SO_SNDBUF, &kBufferSize, sizeof(kBufferSize));

    constexpr int kNoDelay = 1;
    ::setsockopt(sock_fd, IPPROTO_TCP, TCP_NODELAY, &kNoDelay, sizeof(kNoDelay));
}
```
:::

Параметр `SO_RCVBUF` визначає розмір приймального буфера ядра. У сучасних версіях Linux за увімкненого автопідлаштування вікон TCP значення цього буфера динамічно змінюється ядром у межах діапазону, заданого системною конфігурацією `/proc/sys/net/ipv4/tcp_rmem` (мінімальний, типовий та максимальний розміри). Ручне встановлення `SO_RCVBUF` фіксує буфер на подвоєному значенні вказаного числа й вимикає механізм автоматичного тюнінгу TCP.

Параметр `SO_SNDBUF` задає верхню межу передавального буфера ядра. Коли додаток викликає `send()`, байти копіюються з пам'яті процесу в буфер `SO_SNDBUF`. Якщо цей буфер заповнений, системний виклик у блокуючому режимі зупиняє виконання потоку, а в неблокуючому повертає помилку `EWOULDBLOCK`, передаючи зворотний тиск у логіку програми.

Опція `TCP_NODELAY` вимикає алгоритм Нейгла (Nagle's algorithm). За замовчуванням цей алгоритм затримує відправлення малих мережевих пакетів, очікуючи підтвердження ACK від попереднього сегмента або накопичення повного розміру кадру MSS. У потокових сценаріях із чанками змінного розміру ввімкнений алгоритм Нейгла може спричиняти штучні затримки від 40 до 200 мілісекунд, тому для потокових HTTP-клієнтів активація `TCP_NODELAY` є обов'язковою практикою.

Додатковий прапорець `SO_RCVLOWAT` дозволяє задати мінімальний рівень заповнення буфера ядра (у байтах), необхідний для того, щоб виклики `select()`, `poll()` або `epoll_wait()` згенерували подію готовності до читання `POLLIN`. Це знижує кількість перемикань контексту між простором користувача та простором ядра під час обробки неперервних потоків даних.
