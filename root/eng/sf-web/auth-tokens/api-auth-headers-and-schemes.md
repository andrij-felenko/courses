# 📋 Довідник заголовків, схем і параметрів HTTP-автентифікації

HTTP-автентифікація спирається на стандартизований набір заголовків клієнтського запиту та серверної відповіді, формалізованих у специфікаціях RFC 7235 (HTTP/1.1 Authentication), RFC 7617 (Basic), RFC 6750 (Bearer), RFC 6749 (OAuth 2.0), RFC 8705 (mTLS Token Binding) та RFC 9449 (DPoP).

Кожен заголовок виконує чітку роль у протокольному автоматі станів автентифікації: від ініціювання запиту клієнтом до формування серверного виклику (*challenge*), узгодження параметрів безпеки та інтроспекції токенів на прикордонних шлюзах.

## 1. Реєстр HTTP-заголовків автентифікації

| Заголовок | Сторона | Специфікація | Призначення та поведінка |
|---|---|---|---|
| `Authorization` | Клієнт | RFC 7235 §4.2 | Передає облікові дані клієнта цільовому ресурсному серверу. Застосовується для схем Basic, Bearer, Digest, DPoP та власних префіксів. |
| `WWW-Authenticate` | Сервер | RFC 7235 §4.1 | Повертається разом зі статусом `401 Unauthorized`. Містить щонайменше одну схему автентифікації та параметри виклику (*challenge parameters*). |
| `Proxy-Authorization` | Клієнт | RFC 7235 §4.4 | Передає облікові дані проміжному проксі-серверу під час проходження корпоративних шлюзів чи встановлення HTTP CONNECT тунелю. |
| `Proxy-Authenticate` | Проксі | RFC 7235 §4.3 | Повертається проксі-вузлом зі статусом `407 Proxy Authentication Required`, коли доступ до транспортного каналу вимагає авторизації. |
| `X-API-Key` | Клієнт | Де-факто | Нестандартизований, але загальноприйнятий заголовок прямої передачі статичного секретного ключа сервісу або розробника. |
| `DPoP` | Клієнт | RFC 9449 | Заголовок доказу володіння ключем (*Demonstrating Proof-of-Possession*). Передає підписаний клієнтським приватним ключем асиметричний JWT. |
| `DPoP-Nonce` | Сервер | RFC 9449 | Одноразовий рядок, який сервер змушує клієнта підписати у наступному DPoP-доказі для запобігання атакам повторного відтворення. |

### Семантика статусних кодів автентифікації та авторизації

Стандарти HTTP чітко розмежовують проблему відсутності посвідчення особи від проблеми відсутності прав на конкретний ресурс. Коректне розпізнавання статусів у клієнтському адаптері запобігає нескінченним повторам завідомо заборонених дій:

```
┌─────────────────────────┬────────────────────────────────────────────────────────────────────────┐
│ Статус HTTP             │ Значення й поведінка клієнтського адаптера                            │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 401 Unauthorized        │ Облікові дані відсутні, невалідні або термін їхньої дії вичерпано.   │
│                         │ Клієнт МАЄ право оновити токен або надати нові дані та ПОВТОРИТИ запит.│
│                         │ Сервер ЗОБОВ'ЯЗАНИЙ надіслати заголовок WWW-Authenticate із деталями. │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 403 Forbidden           │ Особу клієнта успішно встановлено, проте йому ЗАБОРОНЕНО доступ до дії.│
│                         │ Автоматичний повтор виклику з тим самим токеном МАРНИЙ.                 │
│                         │ Оновлення токена не змінить дозволи, якщо адміністратор не надав прав. │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 407 Proxy Auth Required │ Потрібна авторизація на рівні шлюзу-посередника (Forward/Edge Proxy).  │
│                         │ Запит перехоплено мережевим екраном ще до досягнення цільового бекенда.│
└─────────────────────────┴────────────────────────────────────────────────────────────────────────┘
```

## 2. Формати та схеми заголовка `Authorization`

Загальний синтаксис запису заголовка визначається граматикою BNF (Backus-Naur Form):
```http
Authorization = credentials
credentials   = auth-scheme [ 1*SP ( token68 / #auth-param ) ]
```

### Схема Basic (RFC 7617)
Схема кодує пару імені користувача та пароля у форматі `username:password` за алгоритмом Base64. Клієнт формує байти з рядка, кодує їх у 64-символьний алфавіт ASCII і додає схему `Basic`:

```http
GET /api/v1/system/status HTTP/1.1
Host: admin.example.com
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
```

Коли неавторизований клієнт звертається до захищеного маршруту, сервер відхиляє запит і надсилає деталі виклику:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Control Panel", charset="UTF-8"
```
Параметр `realm` задає текстову область захисту, яку браузер показує у діалоговому вікні введення пароля, а `charset="UTF-8"` вказує на коректне розпізнавання символів національних алфавітів при кодуванні байтів.

### Схема Bearer (RFC 6750)
Схема призначена для передачі токенів пред'явника (непрозорих рядків або підписаних JWT-структур):

```http
GET /api/v1/wallets HTTP/1.1
Host: payments.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c3JfMTA5MjEiLCJzY29wZSI6InJlYWQ6d2FsbGV0cyIsImV4cCI6MTc2NjcwMDkwMH0.V7kX9...
```

Якщо токен прострочено або підпис скомпрометовано, сервер повертає статус 401 із директивами `error` та `error_description`:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="payments",
                         error="invalid_token",
                         error_description="The access token expired at 2026-08-25T18:00:00Z"
```

Якщо токен дійсний, але користувач намагається виконати модифікацію даних без відповідних прав, сервер повертає статус 403:

```http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer realm="payments",
                         error="insufficient_scope",
                         error_description="The token lacks write permission for this resource",
                         scope="wallets:write"
```

### Схема DPoP (RFC 9449 — Demonstrating Proof-of-Possession)
Схема розв'язує фундаментальну вразливість класичних Bearer-токенів — неможливість довести, що токен надсилає саме той клієнт, якому його було видано. При використанні DPoP токен криптографічно прив'язується до пари ключів клієнтського застосунку.

Клієнт генерує ефемерну пару ключів (наприклад, ECDSA на еліптичній кривій P-256) і для кожного окремого HTTP-виклику створює та підписує унікальний одноразовий JWT-доказ:

```http
POST /api/v1/transfers HTTP/1.1
Host: bank.example.com
Authorization: DPoP eyJhbGciOiJSUzI1NiIsImtpZCI6Inh5eiJ9...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7Imt0eSI6IkVDIiwiY3J2IjoiUC0yNTYiLCJ4Ijoi...
```

Заголовок `DPoP` містить службовий JWT, у якому закодовано:
* `htm` (*HTTP Method*) — метод цільового запиту (`POST`);
* `htu` (*HTTP URI*) — повний цільовий шлях (`https://bank.example.com/api/v1/transfers`);
* `iat` (*Issued At*) — час створення доказу з точністю до секунди;
* `ath` (*Access Token Hash*) — SHA-256 хеш самого Access-токена, закодований у Base64Url;
* `nonce` — одноразовий рядок із серверного заголовка `DPoP-Nonce`, якщо сервер вимагає суворої синхронізації.

Якщо зловмисник перехопить Access-токен, він не зможе використати його без закритого ключа клієнта, оскільки підробити цифровий підпис у заголовку `DPoP` неможливо.

## 3. Проксі-автентифікація та тунелювання

Під час роботи у захищених корпоративних мережах клієнтський трафік проходить крізь проміжні проксі-сервери (*Forward Proxies*). Протокол HTTP виділяє автентифікацію на проксі в повністю незалежний канал за допомогою заголовків `Proxy-Authenticate` та `Proxy-Authorization`.

Коли клієнт намагається відкрити пряме з'єднання або встановити захищений тунель `CONNECT api.example.com:443 HTTP/1.1`, неавторизований проксі перехоплює запит і відповідає:

```http
HTTP/1.1 407 Proxy Authentication Required
Proxy-Authenticate: Basic realm="Corporate Secure Gateway"
Proxy-Authenticate: Negotiate
```

Клієнт зобов'язаний повторити запит до проксі, додавши заголовок `Proxy-Authorization`:

```http
CONNECT api.example.com:443 HTTP/1.1
Host: api.example.com:443
Proxy-Authorization: Basic dXNlcjpwYXNz
```

Після успішного рукостискання проксі створює наскрізний TCP-тунель і переходить у режим прозорого пересилання байтів. Усі подальші TLS-пакети та прикладні заголовки `Authorization` передаються безпосередньо цільовому серверу без участі проксі.

## 4. Директиви виклику `WWW-Authenticate` (RFC 6750)

Під час повернення статусу `401 Unauthorized` сервер надає клієнту вичерпні машиночитні відомості щодо причин відхилення запиту:

| Директива | Тип | Опис та правила використання | Приклад |
|---|---|---|---|
| `realm` | Опційна | Рядок ідентифікації домену безпеки. Допомагає клієнту визначити, які саме облікові дані використовувати. | `realm="api-gateway"` |
| `scope` | Опційна | Список розділених пробілами дозволів, які необхідні для доступу до викликаного маршруту. | `scope="read:profile write:orders"` |
| `error` | Опційна | Стандартизований машиночитний код помилки авторизації. | `error="invalid_token"` |
| `error_description` | Опційна | Читабельне пояснення причини помилки для розробника або системного журналу. | `error_description="Signature verification failed"` |
| `error_uri` | Опційна | Абсолютний URI з документацією щодо регламенту усунення помилки. | `error_uri="https://api.example.com/errors/invalid-token"` |

### Стандартизовані значення директиви `error`

* **`invalid_request`** — Запит сформовано з порушенням синтаксису: відсутній обов'язковий параметр, передано кілька несумісних заголовків авторизації, або тіло запиту містить неприпустимі керуючі символи. Повертається разом зі статусом `400 Bad Request`.
* **`invalid_token`** — Наданий Access-токен прострочений (*expired*), відкликаний у чорному списку (*revoked*), має спотворений криптографічний підпис або випущений невідомим сервером авторизації. Повертається разом зі статусом `401 Unauthorized`.
* **`insufficient_scope`** — Токен автентичний, його підпис валідний і час життя не минув, проте список дозволів (*scopes*) у корисному навантаженні не містить прав на цю конкретну операцію. Повертається разом зі статусом `403 Forbidden`.

## 5. Контракт точки видачі токенів OAuth 2.0 (RFC 6749)

Сервер авторизації надає виділений ендпоінт (зазвичай `/oauth/v2/token`), який приймає виключно `POST`-запити у форматі форми `application/x-www-form-urlencoded`.

### 1. Запит на оновлення токена (Refresh Grant)
Коли клієнтський перехоплювач фіксує закінчення терміну дії Access-токена, він надсилає запит на оновлення:

```http
POST /oauth/v2/token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded
Cache-Control: no-store
Pragma: no-cache

grant_type=refresh_token
&refresh_token=rF9_z18.k9Xq-0.2LmK84920
&client_id=mobile_ios_production
&scope=read:profile%20write:orders
```

* `grant_type` (*обов'язкове*) — Фіксований рядок `refresh_token`.
* `refresh_token` (*обов'язкове*) — Чинний токен оновлення, виданий під час первинного входу.
* `client_id` (*обов'язкове для публічних клієнтів*) — Публічний ідентифікатор клієнтського застосунку.
* `scope` (*опційне*) — Запитана область прав (може бути звужена відносно первинної, але не розширена).

### 2. Успішна відповідь сервера видачі токенів (200 OK)
Сервер авторизації повертає JSON-документ із суворою забороною кешування:

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "nQ4_w52.m7Yp-8.3RtN10943",
  "scope": "read:profile write:orders"
}
```

* `access_token` (*string, обов'язкове*) — Новий токен доступу до ресурсного сервера.
* `token_type` (*string, обов'язкове*) — Тип схеми автентифікації. Зазвичай `Bearer` (або `DPoP`).
* `expires_in` (*integer, рекомендоване*) — Час життя Access-токена в секундах від моменту генерації відповіді.
* `refresh_token` (*string, опційне*) — Новий токен оновлення при увімкненій ротації одноразових токенів.
* `scope` (*string, опційне*) — Перелік прав, якщо він відрізняється від запитаного.

### 3. Відповідь сервера при відхиленні оновлення (400 Bad Request)

Якщо токен оновлення вже було спалено або його час життя завершився, сервер повертає статус `400`:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store

{
  "error": "invalid_grant",
  "error_description": "The refresh token has expired or was already rotated"
}
```

* **`invalid_grant`** — Токен оновлення недійсний, відкликаний або використаний повторно. Клієнт зобов'язаний негайно скинути локальне сховище сесії та спрямувати користувача на форму первинного входу.
* **`unauthorized_client`** — Клієнту з таким `client_id` заборонено використовувати механізм оновлення токенів.
* **`unsupported_grant_type`** — Сервер авторизації не підтримує вказаний тип надання `grant_type`.
