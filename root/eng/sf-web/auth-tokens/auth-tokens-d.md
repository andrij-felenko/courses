Мережевий протокол HTTP за своєю фундаментальною архітектурою не зберігає стану між окремими викликами. Коли клієнтський застосунок виконує два послідовні запити `GET /api/v1/profile` та `POST /api/v1/orders`, операційна система може передати їх через різні TCP-з'єднання або навіть крізь різні проміжні балансувальники навантаження в хмарі. Сервер не має вбудованої пам'яті про попередні дії того самого пристрою: кожен окремий HTTP-пакет зобов'язаний нести в собі явний, однозначний і захищений від підробки доказ того, кому належить запит і які права надано ініціатору.

Якщо передавати сирий логін і пароль користувача у тілі кожного прикладного виклику, система зазнає критичних загроз безпеки. Клієнтський застосунок змушений постійно тримати постійний пароль користувача у відкритій оперативній пам'яті, що робить його вразливим до зняття дампів пам'яті шкідливими процесами. Логування на проміжних шлюзах, фаєрволах та балансувальниках фіксує чутливі дані у файлах трасування. Компрометація навіть одного запиту дає зловмиснику необмежений і безстроковий доступ до всього облікового запису, без можливості відкликати лише одну конкретну компрометовану сесію на смартфоні чи обмежити дії сторонньої програми лише читанням даних.

Щоб розв'язати цю суперечність між безстановостю транспорту та вимогою безпеки, мережева індустрія винесла передачу прав доступу в окремий стандартизований шар — метадані HTTP-заголовків і тимчасові криптографічні послідовності символів.

## Схеми передачі облікових даних у HTTP-заголовках

Розміщення облікових даних безпосередньо в HTTP-заголовках (англ. *headers*, від *head* — голова, шапка повідомлення) забезпечує чітке відокремлення метаданих безпеки від бізнес-тіла запиту (*payload*). Заголовки обробляються API-шлюзами та зворотними проксі ще до виділення пам'яті під розбір великих JSON- або бінарних тіл, що дає змогу відсікати неавторизований трафік на зовнішньому периметрі кластера без навантаження на внутрішні мікросервіси.

Основним стандартизованим каналом передачі облікових даних у запитах клієнта є заголовок `Authorization`.

![Схеми передачі облікових даних у HTTP-заголовках](/root/eng/sf-web/auth-tokens/img/auth-schemes-comparison.svg)
*Порівняння трьох основних підходів до передачі облікових даних: базова автентифікація, статичні ключі API та тимчасові токени пред'явника.*

Історично склалося кілька фундаментальних схем заповнення цього заголовка, кожна з яких розв'язувала власну прикладну задачу ([як розвивалися заголовки та схеми автентифікації від перших RFC до OAuth 2.0 та JWT](root:sf-web/auth-tokens/hist-auth-headers-evolution.md)).

### 1. Схема HTTP Basic Authentication

Схема **Basic** (стандартизована в RFC 7617) є найстарішим механізмом автентифікації в протоколі HTTP. Клієнт формує єдиний рядок із логіна та пароля, розділених двокрапкою (`користувач:пароль`), кодує його за алгоритмом Base64 і розміщує в заголовку:

```http
GET /api/v1/metrics HTTP/1.1
Host: monitoring.internal
Authorization: Basic YWRtaW46c3VwZXJzZWNyZXQxMjM=
```

Якщо неавторизований клієнт надсилає запит без заголовка, сервер повертає статус `401 Unauthorized` разом із заголовком виклику (*challenge*):

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Internal Monitoring Area", charset="UTF-8"
```

Кодування Base64 не є шифруванням: будь-який вузол у мережі декодує рядок за одну операцію. Схема Basic безпечна виключно за умови примусового шифрування транспортного рівня через TLS. Головні обмеження схеми: неможливість безпечного виходу із сесії в браузерах (браузер кешує облікові дані до перезапуску процесу), відсутність обмеження прав за сферами застосування (*scopes*) та необхідність звернення до бази даних користувачів для перевірки хешу пароля на кожен HTTP-запит.

### 2. Схема API Keys (Ключі API)

Для взаємодії між автономними сервісами (англ. *machine-to-machine*, M2M), консольними утилітами (CLI), скриптами CI/CD та фоновими демонами використовують **ключі API** (англ. *API Keys*). Ключ являє собою довгий криптостійкий псевдовипадковий рядок із високою ентропією (наприклад, 256 бітів у шістнадцятковому або Base64Url кодуванні), згенерований сервером за допомогою криптографічно стійкого генератора псевдовипадкових чисел (CSPRNG) і прив'язаний до конкретного сервісного акаунта або проекту.

Ключі передаються або через спеціалізований заголовок `X-API-Key`, або через схему `ApiKey` у заголовку `Authorization`:

```http
POST /v1/ingest HTTP/1.1
Host: telemetry.service.com
X-API-Key: ak_live_4f98e2b7c1094da591873210b3a4f65c
```

Ключі API розвантажують сервер від перевірки паролів і дозволяють жорстко прив'язувати квоти запитів (*rate limits*) до ідентифікатора ключа на рівні кешу пам'яті API-шлюзу. Для зручності адміністрування інженери часто додають до ключів читабельні префікси (наприклад, `ak_live_` для робочого середовища чи `ak_test_` для тестового), що спрощує їх виявлення сканерами витоків секретів у коді.

> 🔧 **Навіщо це.** Передача ключів API через параметри URL-рядка (`https://api.example.com/data?api_key=secret`) є грубим порушенням безпеки. URL-адреси повністю зберігаються в журналах вебсерверів, проксі-вузлів, історії браузера та передаються стороннім ресурсам у заголовку `Referer`. Ключі повинні передаватися виключно через захищені HTTP-заголовки.

Головний недолік API Keys — їхня статичність. Ключі часто не мають обмеженого терміну придатності, тому випадковий витік ключа у публічний git-репозиторій створює постійну діру в безпеці доти, доки адміністратор не виконає ручну інвалідацію та ротацію.

### 3. Схема Bearer Tokens (Токени пред'явника)

Сучасним стандартом авторизації в розподілених вебзастосунках і мобільних клієнтах є схема **Bearer** (формалізована в RFC 6750 як частина каркаса OAuth 2.0).

Слово **Bearer** (англ. *носій*, *пред'явник*, від дієслова *to bear* — нести, тримати) визначає фундаментальний принцип: будь-який суб'єкт, який тримає у руках цей токен, визнається законним власником прав, закодованих у ньому. Сервер не вимагає від клієнта володіння криптографічним закритим ключем для підтвердження володіння токеном пред'явника:

```http
GET /api/v1/user/cards HTTP/1.1
Host: bank.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMDk4MiIsImV4cCI6MTc2NjcwMDAwMH0...
```

Оскільки токен Bearer еквівалентний фізичному ключу від замка, витік токена означає повний витік прав доступу на час його життя. Безпека схеми Bearer тримається на трьох обов'язкових стовпах:
1. Обов'язкове шифрування каналу передачі (TLS), що унеможливлює перехоплення токена посередниками в мережі.
2. Жорстке обмеження часу життя токена (від кількох хвилин до кількох годин).
3. Автоматизований механізм оновлення за допомогою довгоживучого токена оновлення (*Refresh Token*).

Детальні вимоги до синтаксису параметрів виклику `WWW-Authenticate`, розширення DPoP та кодів помилок винесено в окрему довідкову специфікацію ([детальна структура заголовків Authorization, кодів відповідей 401/403 та параметрів WWW-Authenticate](root:sf-web/auth-tokens/api-auth-headers-and-schemes.md)).

## Внутрішня будова токенів: Opaque проти JWT

Токен, що передається в заголовку `Authorization: Bearer <token>`, за своєю внутрішньою організацією належить до одного з двох кардинально відмінних архітектурних класів: непрозорих або структурованих токенів.

```
Непрозорий токен (Opaque):
"d3b07384d113edec49eaa6238ad5ff00" ──► Мережевий запит ──► База даних сесій / Redis

Структурований токен (JWT):
┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ Header (JSON)  │.│ Payload (JSON) │.│ Signature      │ ──► Автономна перевірка підпису
│ Алгоритм, тип  │ │ Суб'єкт, права │ │ Криптографічний│     (без звернення до бази)
└────────────────┘ └────────────────┘ └────────────────┘
```

### Непрозорі токени (Opaque Tokens)

**Непрозорий токен** (англ. *opaque* — каламутний, непрозорий) являє собою довільний криптостійкий псевдовипадковий ідентифікатор без внутрішньої структури (наприклад, 128-бітний UUID або випадковий рядок із 32 байтів). Сам по собі цей рядок не містить жодних даних про користувача.

Коли ресурсний сервер отримує непрозорий токен, він зобов'язаний виконати операцію інтроспекції (*token introspection*, RFC 7662): надіслати запит до централізованої бази даних сесій (наприклад, Redis або кластера авторизації) для пошуку запису, зіставленого з цим ідентифікатором.

* **Перевага:** Миттєве відкликання доступу. Якщо користувач натискає «Вийти на всіх пристроях», сервер видаляє запис із Redis, і наступний же запит з цим токеном буде відхилено.
* **Недолік:** Високі накладні витрати на введення-виведення (I/O) і додаткова мережева затримка на кожен вхідний HTTP-запит, а також поява єдиної точки відмови в системі.

### Структуровані токени (JSON Web Tokens, JWT)

**JSON Web Token** (RFC 7519) — це структурований відкритий стандарт представлення заяв (*claims*) у формі компактного текстового контейнера. JWT складається з трьох частин, закодованих за алгоритмом Base64Url (який замінює символи `+` і `/` на `-` та `_`, а також опускає кінцеві символи доповнення `=`) і з'єднаних крапками:

```
<Заголовок>.<Корисне навантаження>.<Підпис>
```

1. **Заголовок (Header):** містить службові метадані про тип токена та криптографічний алгоритм підпису:
```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "auth-key-2026-v1"
}
```
Поле `kid` (*Key ID*) вказує на конкретний публічний ключ у наборі ключів сервера (JWKS, RFC 7517), яким було виконано підпис.

2. **Корисне навантаження (Payload / Claims):** містить твердження про користувача, його роль, дозволи та часові межі:
```json
{
  "sub": "user_849204",
  "name": "Олена Коваль",
  "scope": "read:profile write:orders",
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "exp": 1766700900,
  "nbf": 1766700000,
  "iat": 1766700000,
  "jti": "8f3b20c9-45d1-4e9a-9812-76a0c5b3d102"
}
```

Стандарт визначає зареєстровані поля (*registered claims*):
* `iss` (*Issuer*) — унікальний ідентифікатор сервера, що випустив токен;
* `sub` (*Subject*) — ідентифікатор користувача або сервісу в системі;
* `aud` (*Audience*) — список цільових ресурсних серверів, для яких призначено токен;
* `exp` (*Expiration Time*) — момент завершення терміну дії токена (UNIX timestamp);
* `nbf` (*Not Before*) — момент часу, раніше якого токен не є валідним;
* `iat` (*Issued At*) — точний час створення токена;
* `jti` (*JWT ID*) — унікальний ідентифікатор конкретного екземпляра токена для захисту від повторного відтворення.

3. **Криптографічний підпис (Signature):** обчислюється сервером авторизації від конкатенації закодованих заголовка та навантаження за допомогою симетричного секретного ключа або асиметричного приватного ключа (наприклад, RSA чи ECDSA).

Розрахунок цифрового підпису для симетричного алгоритму HMAC-SHA256 описується виразом:

```
Signature = HMAC_SHA256(
    Base64Url(Header) + "." + Base64Url(Payload),
    SecretKey
)
```

Ресурсний сервер або прикордонний API-шлюз, завантаживши набір публічних ключів JWKS (`/.well-known/jwks.json`), перевіряє цілісність підпису локально у власній оперативній пам'яті. Для захисту від атак за часом виконання (*timing attacks*) перевірка підпису завжди здійснюється через порівняння за фіксований час (*constant-time comparison*), де порівнюються всі байти рядка без передчасного виходу з циклу.

Якщо хоча б один біт у корисному навантаженні (наприклад, значення `exp` або `sub`) було змінено зловмисником, математична перевірка підпису завершується помилкою.

Завдяки цьому JWT дозволяє реалізувати повністю безстановочну (*stateless*) валідацію: тисячі мікросервісів перевіряють мільйони запитів на секунду без жодного звернення до центральної бази даних.

Ціною цієї швидкості є складність відкликання: валідний JWT неможливо анулювати до настання часу `exp`, якщо не вести розподілений чорний список відкликаних токенів (*revocation list / blocklist*). Саме тому час життя Access-токена роблять гранично коротким, покладаючись на механізм оновлення.

### Вплив розміру токенів на мережевий транспорт

Структурований JWT містить десятки полів і криптографічний підпис довжиною від 256 до 512 байтів. Загальний розмір закодованого токена часто перевищує 1.5–3 кілобайти.

У протоколі HTTP/1.1 передача такого масивного заголовка в кожному виклику споживає суттєву частину пропускної здатності каналу. У протоколах HTTP/2 та HTTP/3 ситуація оптимізується механізмами стиснення заголовків HPACK та QPACK. Проте під час кожного планового оновлення токена значення заголовка змінюється, що інвалідує динамічну таблицю стиснення та спричиняє передачу повного нестисненого рядка байтів по мережі.

Для розв'язання цієї проблеми в архітектурах високого навантаження застосовують патерн **Phantom Token**: зовнішній клієнт отримує компактний 128-бітний непрозорий токен, а API-шлюз на зовнішньому периметрі замінює його на повнорозмірний внутрішній JWT під час пересилання запиту у внутрішню мережу кластера.

## Життєвий цикл пари токенів: Access і Refresh

Щоб поєднати швидкодію безстановочних JWT з можливістю оперативного контролю та відкликання доступу, архітектура OAuth 2.0 розділяє повноваження між парою взаємопов'язаних токенів: **токеном доступу** (*Access Token*) та **токеном оновлення** (*Refresh Token*).

```
┌──────────────────────────────┬──────────────────────────────┐
│ Токен доступу (Access Token) │ Токен оновлення (Refresh)    │
├──────────────────────────────┼──────────────────────────────┤
│ Короткоживучий (5–15 хвилин) │ Довгоживучий (дні, місяці)   │
│ Надсилається в КОЖНОМУ виклику│ Надсилається ТІЛЬКИ на Auth  │
│ Передається до ресурсних API │ Зберігається в захищеному сховищі│
│ Автономна валідація (JWT)    │ Перевірка в базі / ротація   │
└──────────────────────────────┴──────────────────────────────┘
```

![Життєвий цикл пари токенів та автоматичне оновлення](/root/eng/sf-web/auth-tokens/img/token-lifecycle-and-refresh.svg)
*Повний цикл взаємодії: первинний вхід, звернення до ресурсного API, виявлення прострочення та прозоре оновлення пари токенів на сервері авторизації.*

### Ротація токенів оновлення (Refresh Token Rotation)

У класичній моделі компрометація довгоживучого Refresh-токена давала зловмиснику можливість роками оновлювати Access-токени за спиною справжнього користувача. Для усунення цієї вразливості сучасні стандарти (OAuth 2.0 Security Best Current Practice) вимагають використання механізму **ротації токенів оновлення** (англ. *Refresh Token Rotation*).

Принцип ротації полягає в одноразовості кожного Refresh-токена:
1. Коли клієнт звертається до сервера авторизації з токеном `Refresh_Token_1`, сервер не просто видає новий `Access_Token_2`, а й випускає повністю новий одноразовий `Refresh_Token_2`.
2. Старий `Refresh_Token_1` негайно анулюється в базі даних авторизації та позначається як використаний.
3. Якщо зловмисник, перехопивши `Refresh_Token_1`, спробує використати його повторно після того, як легітимний клієнт уже отримав `Refresh_Token_2`, сервер авторизації фіксує спробу атаки повторного відтворення (*replay attack*).
4. За правилом виявлення повторного використання (*Automatic Reuse Detection*) сервер негайно інвалідує **всю родину токенів** цього користувача, примусово розриваючи всі активні сесії та вимагаючи повторного введення пароля чи проходження біометрії.

## Клієнтський конвеєр автоматичного оновлення

Клієнтський застосунок повинен підтримувати безперервність сесії користувача так, щоб інтерфейс не зависав і не повертав помилок під час планового закінчення терміну дії Access-токена.

Існує дві взаємодоповнюючі моделі виявлення прострочення токена на боці клієнта:

```
Модель 1: Проактивна перевірка (Proactive Check)
Клієнт перевіряє (t_now >= t_exp - Δt_skew) ДО відправки ──► Якщо так: оновлення перед запитом

Модель 2: Реактивна обробка (Reactive Handling)
Клієнт надсилає запит ──► Отримує 401 Unauthorized ──► Оновлює токен ──► Повторює запит
```

### 1. Проактивна перевірка часу дії (Proactive Clock Skew Check)

Клієнт аналізує термін придатності токена ще до надсилання мережевого виклику. Час завершення дії обчислюється на основі поля `expires_in` із відповіді сервера авторизації або з поля `exp` у самому JWT.

Щоб запит не прострочився в дорозі через затримку передачі пакетів у стільниковій мережі, клієнт вводить упереджувальний часовий зсув (*clock skew threshold* `Δt_skew`, зазвичай від 30 до 60 секунд).

Умова потреби в упереджувальному оновленні токена записується так:

```
Потреба_в_оновленні = (t_поточний ≥ t_закінчення - Δt_зсуву)
```

де `t_поточний` — поточний UNIX-час клієнта, `t_закінчення` — абсолютний момент втрати чинності токеном, а `Δt_зсуву` — запас надійності.

### 2. Реактивна обробка статусу 401 Unauthorized

Проактивна перевірка не захищає від ситуацій, коли адміністратор анулював токен достроково на бекенді або сесію було скинуто через зміну прав. Тому клієнтський мережевий адаптер повинен містити реактивний перехоплювач (*HTTP Interceptor / Transport Adapter*), який ловить статус відповіді `401 Unauthorized`, ініціює виклик точки оновлення `/oauth/token` і повторює первинний невдалий запит із новим заголовком `Authorization`.

### Проблема паралельних запитів: ефект «громового стада»

У сучасних клієнтах графічний інтерфейс завантажує екран за допомогою кількох паралельних запитів: одночасно летять виклики за списком сповіщень, профілем користувача та станом кошика.

Якщо Access-токен прострочився, усі ці паралельні запити одночасно отримають статус 401 або одночасно зафіксують завершення часу дії. Якщо кожен потік самостійно кинеться надсилати запит на оновлення токена, виникне катастрофічний стан гонитви (*race condition*).

![Конкурентні запити та клієнтський м'ютекс оновлення](/root/eng/sf-web/auth-tokens/img/concurrent-refresh-mutex.svg)
*Зліва: відсутність синхронізації спричиняє паралельне надсилання старого токена оновлення, що розцінюється сервером як атака та призводить до блокування акаунта. Справа: Single-Flight механізм на базі м'ютекса пропускає лише один виклик, шикуючи інші запити в чергу.*

При увімкненій ротації одноразових Refresh-токенів запит від Потоку 1 першим дістанеться сервера авторизації. Сервер оновить токен і анулює попередній. Запити від Потоків 2 і 3, що прийдуть через кілька мілісекунд, передадуть уже спалений токен. Сервер вирішить, що сталася крадіжка токена, активує механізм захисту від повторів, інвалідує всю сесію і примусово викине користувача на екран авторизації.

Розв'язанням є патерн **Single-Flight Refresh** (поодиноке оновлення під блокуванням):
1. Перший потік, який зафіксував потребу в оновленні, захоплює м'ютекс (*Mutex*) і бере на себе роль координатора (*Leader*).
2. Усі інші конкурентні потоки, які потребують токена, переходять у стан очікування на умовній змінній (*Condition Variable*) або стають у чергу обіцянок (*Promise Queue*).
3. Потік-координатор виконує рівно один мережевий виклик `POST /oauth/token`.
4. Отримавши нову пару токенів, координатор записує їх у спільне сховище, знімає блокування та будить усі заблоковані потоки за допомогою широкомовного сигналу (*broadcast*).
5. Потоки, що прокинулися, отримують уже свіжий Access-токен і прозоро повторюють свої оригінальні бізнес-запити без жодної помилки для користувача.

import time
import threading
from dataclasses import dataclass
from typing import Optional


@dataclass
class TokenState:
    access_token: str
    refresh_token: str
    expires_at: float


class ThreadSafeAuthInterceptor:
    def __init__(self, skew_seconds: float = 30.0):
        self._skew_seconds = skew_seconds
        self._state: Optional[TokenState] = None
        self._lock = threading.Lock()
        self._cv = threading.Condition(self._lock)
        self._is_refreshing = False

    def update_tokens(self, access: str, refresh: str, expires_in: float) -> None:
        with self._lock:
            self._state = TokenState(access, refresh, time.time() + expires_in)

    def get_authorized_token(self) -> str:
        """Повертає дійсний токен, синхронізуючи оновлення між потоками."""
        with self._lock:
            while True:
                if self._state is None:
                    raise RuntimeError("Сесія відсутня")

                now = time.time()
                is_expired = now >= (self._state.expires_at - self._skew_seconds)

                if not is_expired:
                    return self._state.access_token

                if not self._is_refreshing:
                    self._is_refreshing = True
                    current_refresh = self._state.refresh_token
                    break
                else:
                    self._cv.wait()

        # Виконуємо виклик сервера авторизації поза блокуванням основного стану
        try:
            new_tokens = self._call_token_endpoint(current_refresh)
            with self._lock:
                self._state = new_tokens
                self._is_refreshing = False
                self._cv.notify_all()
                return self._state.access_token
        except Exception:
            with self._lock:
                self._is_refreshing = False
                self._cv.notify_all()
            raise

    def _call_token_endpoint(self, refresh_token: str) -> TokenState:
        # Імітація мережевого запиту POST /oauth/v2/token
        time.sleep(0.05)
        now = time.time()
        return TokenState(
            access_token=f"acc_{int(now * 1000)}",
            refresh_token=f"ref_{int(now * 1000)}",
            expires_at=now + 900.0
        )

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <stdbool.h>
#include <pthread.h>
#include <unistd.h>

#define MAX_TOKEN_LEN 256

typedef struct {
    char access_token[MAX_TOKEN_LEN];
    char refresh_token[MAX_TOKEN_LEN];
    time_t expires_at;
} token_data_t;

typedef struct {
    token_data_t data;
    bool has_data;
    bool is_refreshing;
    double skew_sec;
    pthread_mutex_t lock;
    pthread_cond_t cond;
} c_auth_interceptor_t;

void c_auth_init(c_auth_interceptor_t *it, double skew) {
    memset(&it->data, 0, sizeof(token_data_t));
    it->has_data = false;
    it->is_refreshing = false;
    it->skew_sec = skew;
    pthread_mutex_init(&it->lock, NULL);
    pthread_cond_init(&it->cond, NULL);
}

static bool perform_oauth_refresh(const char *old_refresh, token_data_t *out_data) {
    usleep(50000); // 50 мс затримки виклику
    time_t now = time(NULL);
    snprintf(out_data->access_token, MAX_TOKEN_LEN, "c_acc_%ld", (long)now);
    snprintf(out_data->refresh_token, MAX_TOKEN_LEN, "c_ref_%ld", (long)now);
    out_data->expires_at = now + 900;
    return true;
}

bool c_auth_get_token(c_auth_interceptor_t *it, char *dest, size_t dest_len) {
    pthread_mutex_lock(&it->lock);

    while (1) {
        if (!it->has_data) {
            pthread_mutex_unlock(&it->lock);
            return false;
        }

        time_t now = time(NULL);
        bool expired = (now >= (it->data.expires_at - (time_t)it->skew_sec));

        if (!expired) {
            strncpy(dest, it->data.access_token, dest_len - 1);
            dest[dest_len - 1] = '\0';
            pthread_mutex_unlock(&it->lock);
            return true;
        }

        if (!it->is_refreshing) {
            it->is_refreshing = true;
            break;
        } else {
            pthread_cond_wait(&it->cond, &it->lock);
        }
    }

    char active_refresh[MAX_TOKEN_LEN];
    strncpy(active_refresh, it->data.refresh_token, MAX_TOKEN_LEN - 1);
    pthread_mutex_unlock(&it->lock);

    token_data_t fresh_data;
    bool success = perform_oauth_refresh(active_refresh, &fresh_data);

    pthread_mutex_lock(&it->lock);
    if (success) {
        it->data = fresh_data;
        strncpy(dest, it->data.access_token, dest_len - 1);
        dest[dest_len - 1] = '\0';
    }
    it->is_refreshing = false;
    pthread_cond_broadcast(&it->cond);
    pthread_mutex_unlock(&it->lock);

    return success;
}

## Зв'язування токенів: DPoP та mTLS

Класичний Bearer-токен має фундаментальну вразливість: він не прив'язаний до клієнта. Якщо зловмисник перехопить токен через вразливість у проксі, витік логів або XSS, він може надіслати його з будь-якої точки світу.

Для усунення цієї загрози сучасні стандарти високої безпеки (Open Banking, eIDAS, FAPI) впроваджують механізми **криптографічного зв'язування токенів** (*Token Binding*).

### 1. Доказ володіння ключем DPoP (RFC 9449)
Клієнтський застосунок генерує локальну асиметричну пару ключів (наприклад, ECDSA P-256). Під час запиту на отримання токена клієнт підтверджує володіння цим ключем. Сервер авторизації випускає Access-токен, у корисне навантаження якого вшиває хеш публічного ключа клієнта (`cnf.jkt`).

Під час кожного наступного виклику до ресурсного API клієнт додає заголовок `DPoP` із короткоживучим JWT, підписаним своїм закритим ключем. API-шлюз перевіряє, що підпис у заголовку `DPoP` відповідає хешу `cnf.jkt`, вшитому в Access-токен. Викрадений токен без закритого ключа стає абсолютно непридатним для використання.

### 2. Взаємний TLS (mTLS Token Binding, RFC 8705)
На рівні транспортного протоколу TLS 1.3 клієнт надає свій X.509 сертифікат під час фази рукостискання. Сервер авторизації вшиває відбиток цього сертифіката (`cnf.x5t#S256`) у виданий JWT. Ресурсний сервер перевіряє, що клієнтський сертифікат відкритого TCP-з'єднання збігається з відбитком у токені.

## Безпечне зберігання токенів на клієнті

Те, де саме клієнтський застосунок зберігає Access і Refresh токени між запитами, визначає його стійкість до зламів і шкідливого коду.

### Вебсередовище та браузери

У браузерних односторінкових застосунках (SPA) розробники часто припускаються помилки, зберігаючи токени в `window.localStorage` або `window.sessionStorage`.
* **Загроза:** Сховище `localStorage` повністю доступне будь-якому JavaScript-коду, що виконується в контексті домену. Якщо на сторінці спрацьовує міжсайтовий скриптинг (англ. *Cross-Site Scripting*, XSS) — через вразливу сторонню бібліотеку аналітики чи коментарів — шкідливий скрипт зчитує токени за один рядок коду і відправляє їх на сервер зловмисника.
* **Надійне рішення:** Зберігання токенів у захищених cookie-файлах з обов'язковими атрибутами `HttpOnly` (забороняє читання через JavaScript), `Secure` (передача виключно через HTTPS) та `SameSite=Strict` або `SameSite=Lax` (захист від міжсайтової підробки запитів CSRF). У чистих SPA застосовують архітектурний патерн **Backend for Frontend (BFF)**, де браузер обмінюється з проміжним легким вузлом безпечними cookie, а вже сам BFF додає заголовок `Authorization: Bearer` до внутрішніх мікросервісів.

### Мобільні та десктопні платформи

На нативних платформах токени ніколи не записують у звичайні текстові конфігураційні файли чи незашифровані бази даних SQLite. Використовують апаратно захищені сховища операційної системи:
* **iOS / macOS:** *Keychain Services* (криптографічне сховище, апаратно захищене Secure Enclave).
* **Android:** *Android Keystore* у поєднанні з *EncryptedSharedPreferences* (апаратна ізоляція ключів у Trusted Execution Environment або StrongBox).
* **Windows:** *Data Protection API (DPAPI)* (шифрування ключів прив'язкою до облікового запису користувача ОС).
* **Linux:** *Secret Service API* (через демони Freedesktop / GNOME Keyring / KWallet).

## Термінологічний підсумок

Для закріплення розуміння системних понять наведено зведення ключових термінів із мовами їхнього походження та вихідними коренями:

* **Автентифікація** (грец. *authentikos* — справжній, первинний, авторитетний) — процедура перевірки справжності суб'єкта та підтвердження того, що він є саме тим, за кого себе видає.
* **Авторизація** (лат. *auctoritas* — право, повноваження, влада) — перевірка наявності прав у вже автентифікованого суб'єкта на виконання конкретної операції над ресурсом.
* **Токен** (давньоангл. *tacen*, англ. *token* — знак, видимий символ, доказ, розпізнавальний знак) — компактний двійковий або текстовий артефакт, що виступає доказом прав суб'єкта в безстановочних протоколах.
* **Пред'явник / Носій** (англ. *bearer*, від прагерм. *beranan* — нести, тримати в руках) — концепція токена, згідно з якою доступ надається будь-кому, хто володіє цим значенням.
* **Заголовок** (англ. *header*, від прагерм. *haubidam* — голова, шапка) — стандартизована структура пар «ключ-значення», що передається на початку мережевого повідомлення перед тілом для передачі метаданих протоколу.
* **Облікові дані** (лат. *credentia*, від *credere* — вірити, довіряти) — сукупність секретних атрибутів (паролі, сертифікати, токени), що посвідчують особу клієнта.
* **Експірація / Закінчення терміну** (лат. *expirare*, від *ex-* — з, назовні, та *spirare* — дихати, буквально «видихати, добігати кінця») — момент завершення легітимного терміну використання криптографічного артефакту.
* **Перехоплювач / Інтерцептор** (лат. *intercipere*, від *inter-* — між, та *capere* — хапати, перехоплювати по дорозі) — програмний посередник, що вбудовується в конвеєр передачі запитів для прозорої модифікації заголовків або повтору дій при помилках.
* **М'ютекс** (англ. *mutex*, скорочення від *mutual exclusion*, лат. *mutuus* — взаємний, та *excludere* — виключати, не допускати) — примітив синхронізації, що гарантує доступ до спільного ресурсу лише одному потоку одночасно.
