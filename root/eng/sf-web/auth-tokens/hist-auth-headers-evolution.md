# 📜 Від відкритого пароля до криптографічних підписів: еволюція HTTP-автентифікації

У першій специфікації протоколу HTTP 0.9, створеній Тімом Бернерсом-Лі в 1991 році в стінах CERN, автентифікація була відсутня повністю. Протокол розроблявся як відкрита система обміну науковими гіпертекстовими документами, де кожен файл був публічним за замовчуванням, а єдиний метод `GET` приймав лише шлях до файлу.

Стрімке розгортання комерційного інтернету в 1993–1995 роках зажадало обмеження доступу до корпоративних баз даних, комерційних каталогів і перших вебсерверів NCSA HTTPd та Apache.

## Народження HTTP Basic: простота ціною безпеки

У травні 1996 року Інженерна рада інтернету (IETF) опублікувала RFC 1945 (специфікація HTTP/1.0), формалізувавши схему **HTTP Basic Authentication** (згодом виділену в окремий RFC 2617, а нині оновлену до RFC 7617).

Ідея полягала в мінімалізмі: клієнт формував рядок `користувач:пароль`, перекодовував його за алгоритмом Base64 і надсилав у заголовку `Authorization: Basic <base64>`. Якщо заголовок був відсутній, сервер відповідав статусом `401 Unauthorized` із заголовком виклику `WWW-Authenticate: Basic realm="Restricted"`.

```
Клієнт                             Сервер
  │                                   │
  │ GET /private/doc                  │
  ├──────────────────────────────────►│
  │                                   │
  │ 401 Unauthorized                  │
  │ WWW-Authenticate: Basic realm="..."│
  │◄──────────────────────────────────┤
  │                                   │
  │ GET /private/doc                  │
  │ Authorization: Basic dXNlcjpwYXNz │
  ├──────────────────────────────────►│ (успіх: 200 OK)
```

Ця простота приховувала критичну вразливість. Кодування Base64 є алгоритмом оборотного представлення двійкових даних текстовими символами, а не шифруванням. У середині 1990-х років більшість інтернет-трафіку передавалася відкритим текстом по незахищеному HTTP через хаби та маршрутизатори, де будь-який пасивний аналізатор пакетів (*sniffer*) миттєво перехоплював облікові дані.

Ба більше, браузери зберігали отриманий логін і пароль у внутрішньому кеші процесу до повного закриття вікна застосунку: протокол не передбачав жодної штатної команди чи заголовка для завершення сесії (*logout*).

## Спроба дайджесту: заплутана криптографія RFC 2069

У відповідь на очевидну слабкість Basic-схеми робоча група HTTP IETF під керівництвом Джона Франкса (John Franks) та Філіпа Галлам-Бейкера (Phillip Hallam-Baker) у 1997 році запропонувала схему **Digest Access Authentication** (RFC 2069, згодом удосконалений у RFC 2617).

Digest-автентифікація спиралася на принцип «виклик-відповідь» (*challenge-response*) за допомогою алгоритму хешування MD5:
1. Сервер генерував унікальне одноразове число (*nonce*) і відсилав його в заголовку `WWW-Authenticate: Digest nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093", realm="test"`.
2. Клієнт обчислював криптографічний дайджест із логіна, пароля, отриманого nonce, HTTP-методу та URI.
3. Сервер виконував аналогічний розрахунок на своєму боці й порівнював отримані геші.

Пароль більше не передавався відкритим каналом зв'язку, а випадковий `nonce` захищав від атак повторного відтворення трафіку (*replay attacks*). Проте Digest-схема зазнала ринкової поразки.

По-перше, для перевірки дайджесту сервер мусив або зберігати паролі користувачів у відкритому вигляді, або тримати в базі проміжний хеш `MD5(username:realm:password)`. Це унеможливлювало використання сучасних стійких функцій формування ключа з сіллю (таких як bcrypt, scrypt чи argon2).

По-друге, перевірка дайджесту порушувала модель кешування проміжних проксі-серверів та вимагала збереження стану активних `nonce` у пам'яті розподіленого кластера, що руйнувало масштабованість вебсервісів.

## Ера Cookie та монополія браузерів

Паралельно з невдачею Digest Лу Монтуллі (Lou Montulli) з корпорації Netscape у 1994 році розробив механізм HTTP Cookie (стандартизований у RFC 2109 та RFC 6265).

Замість надсилання пароля в кожному виклику клієнт проходив автентифікацію один раз через HTML-форму, а сервер повертав у відповіді заголовок `Set-Cookie: session_id=xyz; HttpOnly; Secure`. Браузер автоматично додавав цей cookie до всіх наступних запитів на той самий домен.

```
Браузер                              Сервер
   │                                    │
   │ POST /login (user, password)       │
   ├───────────────────────────────────►│
   │                                    │
   │ 200 OK                             │
   │ Set-Cookie: sid=abc; HttpOnly      │
   │◄───────────────────────────────────┤
   │                                    │
   │ GET /dashboard                     │
   │ Cookie: sid=abc                    │
   ├───────────────────────────────────►│ (пошук sid у пам'яті/БД)
```

Сесійні cookie вирішили задачу для людей у браузерах, але виявилися непридатними для нової хвилі сервісно-орієнтованої архітектури (SOA), мобільних застосунків на iOS та Android і відкритих REST API:
* Cookie автоматично надсилалися браузером у міжсайтових запитах, що породило клас атак міжсайтової підробки запитів (англ. *Cross-Site Request Forgery*, CSRF).
* Сторонні мобільні клієнти та скрипти автоматизації були змушені парсити HTML-сторінки та імітувати роботу cookie-движків браузера.
* Спільний доступ вимагав прямої передачі пароля: щоб сторонній застосунок для аналізу пошти міг читати листи, користувач мусив віддати йому свій головний пароль від акаунта.

## Криптографічний глухий кут: OAuth 1.0

У 2006–2007 роках інженери Блейн Кук (Blaine Cook, головний архітектор Twitter), Кріс Мессіна (Chris Messina) та Ларрі Гелфф (Larry Halff) сформували робочу групу для створення протоколу делегованого доступу без розкриття паролів — **OAuth 1.0** (RFC 5849, квітень 2010 року).

OAuth 1.0 запровадив розділення ролей: клієнт отримував тимчасовий токен і підписував кожен HTTP-запит цифровим підписом HMAC-SHA1 або RSA-SHA1. Підпис включав метод, нормалізований URL, мітку часу (*timestamp*), унікальне випадкове число (*nonce*) і всі параметри запиту.

```
Authorization: OAuth oauth_consumer_key="dpf43f3p2l4k3l03",
  oauth_token="nnch734d00sl2jdk",
  oauth_signature_method="HMAC-SHA1",
  oauth_timestamp="137131201",
  oauth_nonce="chRp9gah2Q",
  oauth_version="1.0",
  oauth_signature="MdpQRFwgDydZGtWay%2FQnurHHKUU%3D"
```

Протокол гарантував високу безпеку навіть поверх відкритого HTTP, але став нічним жахом для розробників клієнтських бібліотек. Будь-яка розбіжність у порядку сортування параметрів запиту, пробілах чи кодуванні відсоткових символів (*percent-encoding*) між клієнтом і шлюзом призводила до невідповідності підпису та відмови з помилкою 401.

Обчислення підписів вимагало колосальних обчислювальних витрат на серверах і в мобільних пристроях з обмеженою автономністю.

## Перелом: OAuth 2.0 і народження Bearer-токенів

У жовтні 2012 року робоча група IETF опублікувала дві взаємопов'язані специфікації, які визначили сучасний вигляд вебу:
* **RFC 6749** — Каркас авторизації OAuth 2.0 (*The OAuth 2.0 Authorization Framework*);
* **RFC 6750** — Використання токенів пред'явника (*Bearer Token Usage*).

Архітектурний зсув полягав у відмові від ручного криптографічного підписування кожного HTTP-пакета на прикладному рівні. Безпека каналу зв'язку була повністю перекладена на обов'язковий транспортний рівень TLS (HTTPS).

Завдяки цьому заголовок автентифікації спростився до єдиного рядка:
```http
Authorization: Bearer mF_9.B5f-4.1JqM
```

Термін **Bearer** (англ. *носій*, *пред'явник*) буквально означав, що володіння цією послідовністю символів дає право на доступ до ресурсів кожному, хто її пред'явить.

Щоб мінімізувати ризик викрадення токена, OAuth 2.0 розділив поняття доступу на два токени з принципово різним життєвим циклом:
1. **Access Token** — короткоживучий ключ доступу (тривалістю від кількох хвилин до години), що передається з кожним запитом до ресурсного API.
2. **Refresh Token** — довгоживучий ключ відновлення, що зберігається в захищеному сховищі клієнта та використовується виключно для взаємодії з сервером авторизації.

## Автономна валідація: JSON Web Tokens (JWT)

Початково RFC 6749 не визначав внутрішньої структури токена: більшість систем використовували непрозорі випадкові рядки (*opaque tokens*), стан яких зберігався в базі даних (наприклад, Redis чи Memcached). Коли мікросервісна архітектура почала витісняти моноліти, кожен вхідний запит до сотень незалежних сервісів генерував лавину внутрішніх мережевих запитів до єдиної бази сесій для валідації токена.

У травні 2015 року група інженерів (Майкл Джонс із Microsoft, Джон Бредлі з Ping Identity та Нат Сакімура з Nomura Research Institute) стандартизувала **JSON Web Token (JWT, RFC 7519)**.

JWT перетворив токен із простого випадкового ідентифікатора на компактний самодостатній двійковий контейнер у текстовому форматі Base64Url:
* Заголовок (*Header*) містить алгоритм підпису (HMAC-SHA256, RSA чи Ed25519).
* Корисне навантаження (*Payload / Claims*) містить ідентифікатор користувача, термін придатності (`exp`), час видачі (`iat`) і перелік прав (`scope`).
* Криптографічний підпис (*Signature*) гарантує, що жоден байт у заголовку чи навантаженні не був змінений після підписання приватним ключем сервера авторизації.

Цей крок завершив тридцятирічну еволюцію: від незахищеного відкритого тексту HTTP Basic і надскладних клієнтських підписів OAuth 1.0 індустрія перейшла до моделі, де клієнт надсилає стандартизований заголовок `Authorization: Bearer <JWT>`, а ресурсні сервери й API-шлюзи миттєво перевіряють автентичність запиту локально за допомогою публічного ключа без єдиного дискового чи мережевого блокування.
