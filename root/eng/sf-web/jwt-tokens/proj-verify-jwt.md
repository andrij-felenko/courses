# ⚙️ JWT власноруч: видача, перевірка і дві класичні атаки

<preknowlist>
- [HMAC](root:sf-security/hmac) — короткий тег, порахований від повідомлення й таємного ключа; зробити його або перевірити годен лише той, хто має ключ. Саме це і є підпис `HS256`.
- [Криптографія з відкритим ключем](root:sf-security/public-key-crypto) — пара ключів: приватним підписують, відкритим (він роздається всім) перевіряють. Знадобиться для другої атаки — плутанини `RS256` з `HS256`.
</preknowlist>

Зберімо видачу й перевірку JWT на `HS256` голими руками — без жодної JWT-бібліотеки, лише на тому, що є в стандартній поставці мови: base64, HMAC, SHA-256, JSON. Мета не в тому, щоб це поставити в прод (у проді бери перевірену бібліотеку — про це наприкінці). Мета інша: коли за кілька хвилин ми **підробимо** два зловмисні токени, має бути видно точний рядок, об який кожна підробка розбивається. Поки перевірку ховає чужа бібліотека, «прибити алгоритм» звучить як заклинання. Коли перевірку пишеш сам, видно, що це буквально один `if` — і що досить його прибрати, як обидві атаки проходять наскрізь.

## Задача й ідея

Токен — це три шматки base64url через крапку: `header.payload.signature`. Отже, роботи рівно дві.

**Видати** — узяти твердження (хто користувач, доти й доти дійсний), серіалізувати заголовок і навантаження в JSON, перекодувати в base64url, з'єднати крапкою й **підписати** цей рядок HMAC-ом; підпис — третій шматок.

**Перевірити** — розбити токен на три частини, **самому перерахувати** тег від перших двох частин своїм ключем і звірити з тим тегом, що прийшов. Збіглося — довіряємо навантаженню; ні — на смітник. Жодного «розшифрування підпису» немає: HMAC не розшифровують, його переобчислюють і порівнюють.

Уся надійність тримається на одному непомітному рішенні: **хто вирішує, яким алгоритмом перевіряти токен**. Наївна відповідь — «а в токені ж написано, `alg` у заголовку». І саме ця відповідь відчиняє двері обом класичним атакам. Правильна відповідь: алгоритм і ключ перевіряч бере **зі свого конфігу**, а `alg` із заголовка не читає взагалі. Це і є пінінг.

> 🔧 **Навіщо це.** Заголовок токена пише той, кого ми ще не автентифікували, — тобто потенційний зловмисник. Питати в нього, яким алгоритмом його ж перевіряти, — те саме, що дати підозрюваному самому обрати, чи будуть його обшукувати. Тому в коді нижче найперша дія перевірки — не звірка підпису, а `alg == "HS256"` зі свого боку: очікуваний алгоритм прибитий цвяхом, а заявленому в токені ми не віримо ні на йоту.

## Робочий модуль: видача й перевірка

Ось повний модуль — три однакові за поведінкою реалізації трьома рідними для бекенду мовами. Кожна містить усе: base64url із паддингом, підпис `HS256`, порівняння сталого часу, прибитий алгоритм і перевірку часових тверджень `exp`/`nbf`/`iat`.

```python
import base64, hashlib, hmac, json, time

# ── base64url без службових '=' (JWT їх не тримає) ────────────────────────
def b64url_encode(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode("ascii")

def b64url_decode(s: str) -> bytes:
    pad = "=" * (-len(s) % 4)          # добити довжину до кратної чотирьом
    return base64.urlsafe_b64decode(s + pad)

def hs256(msg: bytes, secret: bytes) -> bytes:
    return hmac.new(secret, msg, hashlib.sha256).digest()

class InvalidToken(Exception):
    pass

# ── ВИДАЧА ────────────────────────────────────────────────────────────────
def issue(claims: dict, secret: bytes, ttl: int = 900) -> str:
    now = int(time.time())
    header  = {"alg": "HS256", "typ": "JWT"}
    payload = {**claims, "iat": now, "nbf": now, "exp": now + ttl}
    signing_input = (
        b64url_encode(json.dumps(header,  separators=(",", ":")).encode())
        + "." +
        b64url_encode(json.dumps(payload, separators=(",", ":")).encode())
    )
    sig = b64url_encode(hs256(signing_input.encode(), secret))
    return signing_input + "." + sig

# ── ПЕРЕВІРКА ──────────────────────────────────────────────────────────────
def verify(token: str, secret: bytes, leeway: int = 30) -> dict:
    parts = token.split(".")
    if len(parts) != 3:
        raise InvalidToken("не три частини")
    header_b64, payload_b64, sig_b64 = parts

    # (1) АЛГОРИТМ ПРИБИТО: очікуваний — НАШ, а не той, що в токені
    if json.loads(b64url_decode(header_b64)).get("alg") != "HS256":
        raise InvalidToken("несподіваний alg")

    # (2) ПОРІВНЯННЯ СТАЛОГО ЧАСУ на сирих байтах підпису
    expected = hs256((header_b64 + "." + payload_b64).encode(), secret)
    if not hmac.compare_digest(expected, b64url_decode(sig_b64)):
        raise InvalidToken("підпис не збігається")

    # (3) ЧАСОВІ ТВЕРДЖЕННЯ (з невеликим допуском на розбіжність годинників)
    payload = json.loads(b64url_decode(payload_b64))
    now = int(time.time())
    if "exp" in payload and now > payload["exp"] + leeway:
        raise InvalidToken("протермінований")
    if "nbf" in payload and now + leeway < payload["nbf"]:
        raise InvalidToken("ще не набув чинності")
    if "iat" in payload and now + leeway < payload["iat"]:
        raise InvalidToken("виданий у майбутньому")
    return payload
```

```go
package jwt

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
	"encoding/json"
	"errors"
	"strings"
	"time"
)

// RawURLEncoding — це base64url БЕЗ службових '=', саме як у JWT.
var b64 = base64.RawURLEncoding

func hs256(msg, secret []byte) []byte {
	m := hmac.New(sha256.New, secret)
	m.Write(msg)
	return m.Sum(nil)
}

var ErrInvalid = errors.New("невалідний токен")

// ── ВИДАЧА ─────────────────────────────────────────────────────────────────
func Issue(claims map[string]any, secret []byte, ttl time.Duration) (string, error) {
	now := time.Now().Unix()
	claims["iat"] = now
	claims["nbf"] = now
	claims["exp"] = now + int64(ttl.Seconds())

	h, _ := json.Marshal(map[string]string{"alg": "HS256", "typ": "JWT"})
	p, err := json.Marshal(claims)
	if err != nil {
		return "", err
	}
	signingInput := b64.EncodeToString(h) + "." + b64.EncodeToString(p)
	sig := b64.EncodeToString(hs256([]byte(signingInput), secret))
	return signingInput + "." + sig, nil
}

// ── ПЕРЕВІРКА ────────────────────────────────────────────────────────────────
func Verify(token string, secret []byte, leeway time.Duration) (map[string]any, error) {
	parts := strings.Split(token, ".")
	if len(parts) != 3 {
		return nil, ErrInvalid
	}
	headerJSON, err := b64.DecodeString(parts[0])
	if err != nil {
		return nil, ErrInvalid
	}
	var header struct {
		Alg string `json:"alg"`
	}
	if json.Unmarshal(headerJSON, &header) != nil {
		return nil, ErrInvalid
	}
	// (1) АЛГОРИТМ ПРИБИТО
	if header.Alg != "HS256" {
		return nil, ErrInvalid
	}
	// (2) СТАЛИЙ ЧАС: hmac.Equal порівнює до кінця незалежно від вмісту
	sig, err := b64.DecodeString(parts[2])
	if err != nil {
		return nil, ErrInvalid
	}
	if !hmac.Equal(hs256([]byte(parts[0]+"."+parts[1]), secret), sig) {
		return nil, ErrInvalid
	}
	// (3) ЧАСОВІ ТВЕРДЖЕННЯ
	payloadJSON, err := b64.DecodeString(parts[1])
	if err != nil {
		return nil, ErrInvalid
	}
	var claims map[string]any
	if json.Unmarshal(payloadJSON, &claims) != nil {
		return nil, ErrInvalid
	}
	now, skew := time.Now().Unix(), int64(leeway.Seconds())
	if exp, ok := asUnix(claims["exp"]); ok && now > exp+skew {
		return nil, ErrInvalid
	}
	if nbf, ok := asUnix(claims["nbf"]); ok && now+skew < nbf {
		return nil, ErrInvalid
	}
	if iat, ok := asUnix(claims["iat"]); ok && now+skew < iat {
		return nil, ErrInvalid
	}
	return claims, nil
}

// JSON-числа в Go розпаковуються у float64 — обережно з ними.
func asUnix(v any) (int64, bool) {
	f, ok := v.(float64)
	return int64(f), ok
}
```
```ts
import { createHmac, timingSafeEqual } from "node:crypto";

// Node вміє кодек 'base64url' (від v14) — він без службових '='.
const enc = (buf: Buffer): string => buf.toString("base64url");
const dec = (s: string): Buffer => Buffer.from(s, "base64url");

const hs256 = (msg: string, secret: Buffer): Buffer =>
  createHmac("sha256", secret).update(msg).digest();

type Claims = Record<string, unknown>;

// ── ВИДАЧА ────────────────────────────────────────────────────────────────
export function issue(claims: Claims, secret: Buffer, ttl = 900): string {
  const now = Math.floor(Date.now() / 1000);
  const header = { alg: "HS256", typ: "JWT" };
  const payload = { ...claims, iat: now, nbf: now, exp: now + ttl };
  const signingInput =
    enc(Buffer.from(JSON.stringify(header))) + "." +
    enc(Buffer.from(JSON.stringify(payload)));
  return `${signingInput}.${enc(hs256(signingInput, secret))}`;
}

// ── ПЕРЕВІРКА ──────────────────────────────────────────────────────────────
export function verify(token: string, secret: Buffer, leeway = 30): Claims {
  const parts = token.split(".");
  if (parts.length !== 3) throw new Error("не три частини");
  const [headerB64, payloadB64, sigB64] = parts;

  // (1) АЛГОРИТМ ПРИБИТО
  const header = JSON.parse(dec(headerB64).toString());
  if (header.alg !== "HS256") throw new Error("несподіваний alg");

  // (2) СТАЛИЙ ЧАС: timingSafeEqual вимагає буфери однакової довжини
  const expected = hs256(`${headerB64}.${payloadB64}`, secret);
  const got = dec(sigB64);
  if (expected.length !== got.length || !timingSafeEqual(expected, got))
    throw new Error("підпис не збігається");

  // (3) ЧАСОВІ ТВЕРДЖЕННЯ
  const payload = JSON.parse(dec(payloadB64).toString()) as Claims;
  const now = Math.floor(Date.now() / 1000);
  const num = (k: string) =>
    typeof payload[k] === "number" ? (payload[k] as number) : undefined;
  const exp = num("exp"), nbf = num("nbf"), iat = num("iat");
  if (exp !== undefined && now > exp + leeway) throw new Error("протермінований");
  if (nbf !== undefined && now + leeway < nbf) throw new Error("ще не набув чинності");
  if (iat !== undefined && now + leeway < iat) throw new Error("виданий у майбутньому");
  return payload;
}
```

Три речі в цьому коді варті окремого погляду, бо кожна — це або пастка, або майбутній щит.

**Перевіряй по тих байтах, що прийшли, а не по перерахованих.** Тег рахують від рядка `header_b64 + "." + payload_b64`, **узятого прямо з отриманого токена**, — а не так, що ми розкодуємо навантаження, знову серіалізуємо JSON і підписуємо результат. Різниця тонка, але вбивча. Дві бібліотеки серіалізують той самий словник по-різному: одна лишить пробіли після ком, інша посортує ключі, третя інакше екранує не-ASCII. Перекодуй — і байти вже не ті, підпис чесного токена «розсиплеться» на порожньому місці. Тому підпис завжди звіряють з **дослівним** отриманим рядком; що там усередині JSON — читаємо лише **після** того, як тег зійшовся.

**Порівнюй теги сталим часом.** `hmac.compare_digest`, `hmac.Equal`, `timingSafeEqual` — це не примха, а щит від [атаки за часом](root:sf-security/timing-attack). Звичайне `==` на рядках спиняється на першому відмінному байті: збіглися два перші символи — воно зробить трохи більше роботи, ніж коли не збігся жоден. Ця крихітна різниця в часі відповіді — щілина, крізь яку впертий зловмисник вгадує правильний тег байт за байтом, мільйонами спроб намацуючи, де відповідь сповільнилась. Порівняння, що **завжди йде до кінця** незалежно від того, де перша відмінність, цю щілину закриває.

**Прибитий алгоритм — це рядок (1), і він найперший.** Не звірка підпису, а `alg != "HS256"`. Чому саме перший і чому взагалі окремий — стане очевидно, щойно ми спробуємо його обійти.

## Атака перша: `alg: none`

Стандарт JWT колись передбачив алгоритм «жодного» — токен без підпису взагалі, для випадків, де цілість гарантована іншим шаром. Наслідок вийшов катастрофічний: сила-силенна ранніх бібліотек, побачивши в заголовку `{"alg":"none"}` й порожній третій шматок, **вважали такий токен перевіреним**. Зловмисникові лишалося виставити `alg` на `none`, стерти підпис і написати в навантаженні будь-що.

Підробити такий токен — це навіть не злам, а три рядки складання рядка (форжити його можна будь-якою мовою так само тривіально):

```python
def forge_none(claims: dict) -> str:
    header  = b64url_encode(json.dumps({"alg": "none", "typ": "JWT"},
                                       separators=(",", ":")).encode())
    payload = b64url_encode(json.dumps(claims, separators=(",", ":")).encode())
    return header + "." + payload + "."      # третій шматок порожній — підпису немає

evil = forge_none({"sub": "42", "role": "admin"})
# eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiJ9.
```

Тепер — уразливий перевіряч, той, що читає алгоритм із токена. Він виглядає невинно, навіть дбайливо: «а, тут `none`, підписувати не треба, просто віддам навантаження».

```python
def verify_naive(token: str, secret: bytes) -> dict:
    header_b64, payload_b64, sig_b64 = token.split(".")
    alg = json.loads(b64url_decode(header_b64)).get("alg")   # ← вірить токену
    if alg == "none":
        return json.loads(b64url_decode(payload_b64))        # ← ЖОДНОЇ перевірки
    if alg == "HS256":
        expected = hs256((header_b64 + "." + payload_b64).encode(), secret)
        if not hmac.compare_digest(expected, b64url_decode(sig_b64)):
            raise InvalidToken("підпис не збігається")
        return json.loads(b64url_decode(payload_b64))
    raise InvalidToken("невідомий alg")
```

Зіткнімо підробку з обома перевіряками:

**Умова.** Зловмисник шле `evil` — токен `{"role":"admin"}` із заголовком `alg:none` й порожнім підписом. Ключа сервера він, звісно, не має, але для `none` ключ і не потрібен.

```
verify_naive(evil, secret)  →  {"sub": "42", "role": "admin"}   ← ПРОЛІЗ: адмін без підпису
verify(evil, secret)        →  InvalidToken("несподіваний alg")  ← alg != "HS256", стоп на рядку (1)
```

**Висновок.** Наш `verify` навіть не дійшов до підпису: перша ж дія — `alg == "HS256"` — не справдилася, бо в токені `none`, і токен відпав. Прибитий алгоритм зупиняє атаку **до** будь-якої криптографії, самим фактом, що заявлений алгоритм — не той, на який ми погодилися. А наївний перевіряч сам собі відчинив двері: він спитав у токена, як його перевіряти, і токен відповів «ніяк». Навіть якби `none`-гілки не було, а токен якимось дивом проліз до звірки з порожнім підписом, `compare_digest` 32-байтового тега з нульом байтів усе одно дав би `False` — але покладатися на це не варто: щит тут — саме прибитий алгоритм, а не випадковий добіг до порівняння.

## Атака друга: плутанина `RS256` → `HS256`

Ця витонченіша, і вона показує, чому пінінг важить навіть тоді, коли `none` заборонено, а підпис справжній.

Нагадаю розстановку з [асиметричним підписом](root:sf-security/public-key-crypto). Служба входу підписує токен `RS256` — своїм **приватним** ключем, якого нема ні в кого більше. Десяток мікросервісів перевіряє токени **відкритим** ключем, який роздано вільно: відкритим ключем підпис перевірити можна, а створити — ні. Право видавати лишається в одних руках, перевіряти може кожен. Гарно — доки перевіряч не почне вибирати алгоритм із заголовка.

Ось наївний перевіряч, що підтримує обидва сімейства й — фатально — бере алгоритм із токена, а «ключ» щоразу подає той самий, що йому налаштували:

```python
def verify_naive_multi(token: str, key: bytes) -> dict:
    """key — це те, що сервіс тримає для перевірки. Для RS256 — ВІДКРИТИЙ ключ (PEM)."""
    header_b64, payload_b64, sig_b64 = token.split(".")
    alg = json.loads(b64url_decode(header_b64)).get("alg")   # ← знову вірить токену
    signing_input = (header_b64 + "." + payload_b64).encode()
    sig = b64url_decode(sig_b64)
    if alg == "RS256":
        rsa_verify(signing_input, sig, key)                  # key як ВІДКРИТИЙ ключ
    elif alg == "HS256":
        if not hmac.compare_digest(hs256(signing_input, key), sig):
            raise InvalidToken("підпис не збігається")       # key як HMAC-СЕКРЕТ (!)
    else:
        raise InvalidToken("невідомий alg")
    return json.loads(b64url_decode(payload_b64))
```

Ось де западня. Той самий параметр `key` — рядок PEM відкритого ключа — на гілці `RS256` тлумачиться як **відкритий ключ**, а на гілці `HS256` — як **HMAC-секрет**. Для наївної бібліотеки це просто «ключ», байти й байти; що вони означають, вирішує `alg`. А `alg` вибирає зловмисник.

І він вибирає `HS256`. Секрет для HMAC йому потрібен — але це ж відкритий ключ, він **відомий усім**, отже, є і в зловмисника. Тепер підробка — це наш власний `hs256`, той самий, що ми написали на початку, з відкритим ключем на місці секрету. Жодного приватного ключа, жодного справжнього RSA:

```python
# Відкритий ключ сервера — не таємниця, його роздано вільно:
PUBLIC_PEM = b"-----BEGIN PUBLIC KEY-----\nMFkwEwYHKoZI...AENc9\n-----END PUBLIC KEY-----\n"

def forge_confusion(claims: dict, public_pem: bytes) -> str:
    header  = b64url_encode(json.dumps({"alg": "HS256", "typ": "JWT"},
                                       separators=(",", ":")).encode())
    payload = b64url_encode(json.dumps(claims, separators=(",", ":")).encode())
    signing_input = header + "." + payload
    sig = b64url_encode(hs256(signing_input.encode(), public_pem))   # СЕКРЕТ = відкритий ключ
    return signing_input + "." + sig

evil = forge_confusion({"sub": "42", "role": "admin"}, PUBLIC_PEM)
verify_naive_multi(evil, PUBLIC_PEM)   # →  {"role": "admin"}   БЕЗ приватного ключа
```

Наївний перевіряч бачить `alg:HS256`, бере наданий йому `key` (відкритий ключ) як HMAC-секрет, рахує `hs256(signing_input, PUBLIC_PEM)` — і дістає **точно той тег**, що поклав зловмисник. Збіг. Той, хто мав лише *перевіряти*, раптом навчився *підробляти* — не діставши приватного ключа, а лише зловживши тим, що перевіряч сам обрав, як тлумачити ключ.

Зверни увагу: справжня перевірка `RS256` (`rsa_verify` — це виклик криптобібліотеки, тут за межами: `public_key.verify(sig, msg, padding.PKCS1v15(), SHA256())`) в атаці **не виконується жодного разу**. Уся підробка їде на гілці `HS256`. RSA ламати не довелося — досить було переконати перевіряч піти не тією гілкою.

Тепер — чому пінінг закриває і цю щілину, до того ж двома незалежними способами.

Наш `verify` з початку статті пінить один алгоритм — `HS256` — і його секрет **фіксований у конфізі**: це справжній спільний секрет сервера, а не відкритий ключ. Форжений токен справді має `alg:HS256`, тож рядок (1) пропустить його далі. Але на рядку (2) ми рахуємо `hs256(msg, secret)` **нашим секретом**, а зловмисник підписав відкритим ключем; наш секрет ≠ відкритий ключ, теги різні — відмова.

А сервіс, що по-справжньому перевіряє асиметричні токени, пінить `RS256` і **тільки** його:

```python
def verify_rs256(token: str, pubkey: bytes) -> dict:
    header_b64, payload_b64, sig_b64 = token.split(".")
    if json.loads(b64url_decode(header_b64)).get("alg") != "RS256":   # ПРИБИТО: лише RS256
        raise InvalidToken("несподіваний alg")
    rsa_verify((header_b64 + "." + payload_b64).encode(),
               b64url_decode(sig_b64), pubkey)                        # тільки відкритим ключем
    return json.loads(b64url_decode(payload_b64))
```

Форжений токен несе `alg:HS256`, а цей перевіряч приймає лише `RS256` — і токен помирає на рядку пінінгу, ще до того, як хтось спробує щось порахувати. Гілки `HS256`, за яку чіплялася вся атака, тут просто немає.

Спільний корінь обох атак — той самий: **перевіряч дозволив токенові вибрати, як його перевіряти**. `alg:none` каже «не перевіряй ніяк»; плутанина каже «перевіряй тим алгоритмом, під який я підмінив ключ». Обидві розбиваються об те саме правило — алгоритм і ключ беруть із конфігу, заголовок ігнорують.

*Дві атаки, один замок. Ліворуч — обидві підробки: `alg:none` зі стертим підписом і плутанина, де підпис — це HMAC на всім відомому відкритому ключі. Обидві націлені на те, щоб перевіряч узяв алгоритм із заголовка. Перевіряч, який натомість бере алгоритм і ключ зі свого конфігу, а заявлений у токені ігнорує, відкидає обидві на першому ж рядку — заявлений алгоритм не той, на який сервер погодився.*

## Складність і пастки

Обчислювально тут усе дешеве: один HMAC-SHA-256 на видачу й один на перевірку, тобто прохід по кількох десятках байтів заголовка й навантаження — це наносекунди, підпис ніколи не буде вузьким місцем. Уся «складність» цього коду — не в швидкодії, а в місцях, де легко зробити небезпечно. Ось ті, що коштували галузі найбільше крові.

**Ніколи не серіалізуй наново для перевірки.** Це варто повторити, бо помилка тиха: код працює на своїх токенах і ламається на чужих. Перевіряй тег дослівно по отриманому рядку `header_b64.payload_b64`; розкодований JSON — лише для читання тверджень після того, як тег зійшовся.

**Паддинг base64url — місце, де мови різняться.** JWT стирає службові `=`, і декодер мусить їх повернути. Python-ів `urlsafe_b64decode` без паддингу кине помилку — тому ми самі добиваємо `"=" * (-len(s) % 4)`. Go-в `RawURLEncoding` і Node-ів `'base64url'` очікують рядок **без** паддингу й роблять це самі. Переплутаєш кодек із паддингом і без — і чесні токени почнуть зрідка відпадати на тих, де довжина не кратна чотирьом.

**Порядок перевірок — не косметика.** Спершу структура (рівно три частини), потім прибитий алгоритм, потім підпис, і лише **потім** довіра будь-якому твердженню з навантаження. Найтиповіший смертельний гріх — прочитати `role` чи `user_id` з навантаження *до* звірки підпису (як це робить `verify_naive` на гілці `none`): це і є «діяти за словами неперевіреного токена».

**`decode` — не `verify`.** У багатьох бібліотеках є окрема функція, що лише розкодовує навантаження без жодної звірки підпису (для налагодження, для читання `exp` протухлого токена). Викличеш її замість перевіряльної — і твій «захист» перетворюється на розкодування будь-чого, що надіслав клієнт. Імена на кшталт `decode` й `verify` поруч у API — граблі самі по собі.

**Допуск на годинники (`leeway`) — так, нуль — ні.** Годинники клієнта, видавача й перевіряча розходяться на секунди. Без допуску свіжовиданий токен із `nbf`, що дорівнює «зараз» видавача, відпаде на перевіряча, чий годинник відстав на секунду. Кілька десятків секунд допуску прибирають цей клас несправжніх відмов. Але допуск — це маленька щілина: величезний `leeway` продовжує життя протухлому токену, тож тримай його секундами, не хвилинами. І пам'ятай: `exp`/`nbf`/`iat` — це **секунди** Unix-часу, не мілісекунди; переплутаєш масштаб — і токен «дійсний» до 55-тисячного року.

**`kid` та інші поля заголовка — теж ворожий ввід.** Якщо за `kid` (ідентифікатором ключа) сервер шукає ключ у файлі чи базі, то `kid` — це рядок від зловмисника, і його підставляння в шлях або в SQL відкриває звичні ін'єкції та обхід каталогу. Заголовок увесь походить від того, кому ми ще не довіряємо; жодне його поле не можна брати як безпечне.

**А тепер найважливіше: цей код — щоб зрозуміти, а не щоб поставити.** Ми написали його, аби побачити на власні очі, об який рядок розбиваються атаки. У проді бери **перевірену бібліотеку** (`jose`, `PyJWT`, `golang-jwt`) — там уже враховано десятки крайніх випадків, яких тут немає: строгий розбір JSON, стійкість до дивних кодувань, підтримка цілих сімейств алгоритмів. Але одне бібліотека **не зробить за тебе**: вона не вгадає, який алгоритм ти очікуєш. Тому єдиний непорушний рядок при будь-якій бібліотеці — явний білий список алгоритмів у виклику перевірки: `jwt.decode(token, key, algorithms=["HS256"])`. Пропустиш `algorithms=` — і повернешся рівно до `verify_naive`, хоч би яка добра була бібліотека під ним.

Ці дві діри — `alg:none` і плутанина `RS256`/`HS256` — не вигадка для прикладу. Їх зібрав і оприлюднив дослідник Тім Маклейн (Tim McLean) 31 березня 2015 року, показавши той самий подвійний недогляд одразу в купі бібліотек різними мовами; плутанину алгоритмів у `node-jsonwebtoken` до версії 4.2.2 занесено як CVE-2015-9235 (*документований факт*). Саме після цього до перевіряльних функцій почали додавати обов'язковий параметр очікуваного алгоритму, а уроки згодом звели в окремий звід добрих практик — RFC 8725. Один недогляд — «спитати в токена, як його перевіряти» — коштував галузі стількох злитих обліковок, що з нього зробили стандарт.
