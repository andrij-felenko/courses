# 📋 Параметри конфігурації сесій та пулів з'єднань

Ефективність повторного використання з'єднань, стійкість до мережевих збоїв та споживання ресурсів операційної системи визначаються параметрами конфігурації клієнтських пулів і сесій. Неправильно підібрані ліміти призводять або до штучного блокування потоків через чергу очікування сокета, або до виснаження портів і перевантаження сервера зайвими паралельними з'єднаннями.

Архітектура будь-якого клієнтського пулу з'єднань будується на багаторівневому контролі життєвого циклу ресурсів: від рівня операційної системи (TCP-сокети, черги ядра) до рівня абстракцій мови програмування (адаптери, черги очікування, менеджери повторів).

## Конфігурація пулу в Python: requests та urllib3

Керування пулами в бібліотеці `requests` здійснюється через підключення екземпляра `HTTPAdapter` до об'єкта `Session`. Адаптер інкапсулює клас `urllib3.PoolManager`, який відповідає за розподіл сокетів за ключами `(scheme, host, port)`.

```python
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

session = requests.Session()

# Налаштування стратегії повторних спроб
retries = Retry(
    total=3,
    backoff_factor=0.5,
    status_forcelist=[500, 502, 503, 504],
    allowed_methods={"HEAD", "GET", "PUT", "DELETE", "OPTIONS"},
    raise_on_status=False
)

# Монтування адаптера з параметрами пулу
adapter = HTTPAdapter(
    pool_connections=20,  # Кількість кешованих пулів хостів
    pool_maxsize=50,       # Максимум з'єднань на один хост
    max_retries=retries,   # Політика повторів
    pool_block=True        # Блокувати потік при вичерпанні ліміту
)

session.mount("https://", adapter)
session.mount("http://", adapter)
```

### Довідник параметрів HTTPAdapter та PoolManager

Параметри адаптера визначають межі пам'яті та ступінь паралелізму клієнта:

| Параметр | Тип | За замовчуванням | Призначення та поведінка |
|---|---|---|---|
| `pool_connections` | `int` | `10` | Кількість окремих пулів хостів (Origin), які утримуються в пам'яті за алгоритмом LRU. Якщо запити йдуть до 50 різних доменів при значенні 10, найстаріші пули хостів закриватимуться разом із їхніми відкритими сокетами. |
| `pool_maxsize` | `int` | `10` | Максимальна кількість одночасних відкритих з'єднань (сокети в оренді + вільні в черзі) для одного конкретного хоста `(scheme, host, port)`. |
| `pool_block` | `bool` | `False` | Режим поведінки при вичерпанні `pool_maxsize`. Якщо `False`, клієнт створює нове з'єднання понад ліміт, але після завершення запиту одразу закриває його, виводячи попередження `ConnectionPool is full`. Якщо `True`, потік блокується до звільнення сокета або вичерпання `timeout`. |
| `max_retries` | `int` \| `Retry` | `0` (в urllib3: `3`) | Кількість автоматичних повторних спроб або об'єкт `urllib3.util.Retry` із налаштуванням експоненційної витримки (backoff), переліку HTTP-статусів та ідемпотентних методів. |

### Формула експоненційної витримки (Exponential Backoff)

Об'єкт `urllib3.util.Retry` обчислює інтервал очікування між послідовними невдалими спробами за експоненційним законом:

```
пауза = backoff_factor · 2^(спроба - 1)
```

Якщо `backoff_factor = 0.5`, тривалість пауз складатиме:
- 1-ша повторна спроба: `0.5 · 2^0 = 0.5` секунди;
- 2-га повторна спроба: `0.5 · 2^1 = 1.0` секунда;
- 3-тя повторна спроба: `0.5 · 2^2 = 2.0` секунди.

Це запобігає ефекту шторму повторів (Retry Storm), коли сотні клієнтів одночасно бомбардують сервер після короткочасного збою, не даючи йому відновитися.

### Механіка тайм-аутів запиту

Тайм-аут у `requests` передається у виклики методів `get()`, `post()`, `request()` кортежем із двох значень `(connect_timeout, read_timeout)`:

```python
# (connect_timeout, read_timeout) у секундах
response = session.get("https://api.example.com/data", timeout=(3.05, 10.0))
```

- **Connect Timeout (`3.05` с):** Граничний час на завершення DNS-резолвінгу, встановлення TCP-з'єднання (SYN/ACK) та проходження TLS-рукостискання. Рекомендовано задавати дробове значення, дещо більше за ціле число секунд (наприклад, 3.05 замість 3.0), оскільки внутрішній таймер повторного надсилання TCP SYN у ядрі Linux становить рівно 3.0 секунди. Дробовий запас дозволяє ядру встигнути надіслати повторний пакет до спрацювання клієнтського тайм-ауту.
- **Read Timeout (`10.0` с):** Максимальний інтервал між отриманням окремих байтів відповіді від сервера після успішного встановлення з'єднання. Якщо сервер перестав передавати дані довше ніж на 10 секунд, генерується `requests.exceptions.ReadTimeout`.

## Конфігурація пулу в Go (net/http Transport)

У стандартній бібліотеці мови Go управління з'єднаннями та пулом Keep-Alive інкапсульовано у структурі `http.Transport`.

Особливістю Go є вкрай низьке значення параметра `MaxIdleConnsPerHost` за замовчуванням (всього 2 сокети). У високонавантажених мікросервісних застосунках, де сотні горутин паралельно звертаються до одного бекенду, це призводить до масового закриття сокетів після кожного виклику та виникнення затримок через постійні повторні TLS-хендшейки.

```go
package main

import (
	"net"
	"net/http"
	"time"
)

func createOptimizedClient() *http.Client {
	transport := &http.Transport{
		Proxy: http.ProxyFromEnvironment,
		DialContext: (&net.Dialer{
			Timeout:   5 * time.Second,  // Граничний час на TCP Connect
			KeepAlive: 30 * time.Second, // Інтервал TCP Keep-Alive зондів (L4)
		}).DialContext,
		ForceAttemptHTTP2:     true,
		MaxIdleConns:          100,              // Загальний ліміт сокетів у стані IDLE
		MaxIdleConnsPerHost:   20,               // Вільних сокетів для одного хоста
		MaxConnsPerHost:       50,               // Жорсткий ліміт активних+вільних (0 = безлім)
		IdleConnTimeout:       90 * time.Second, // Час життя неактивного сокета в пулі
		TLSHandshakeTimeout:   5 * time.Second,  // Тайм-аут на TLS
		ResponseHeaderTimeout: 10 * time.Second, // Очікування першого байта заголовків
		DisableKeepAlives:     false,            // false = тримати сокети відкритими
	}

	return &http.Client{
		Transport: transport,
		Timeout:   30 * time.Second, // Загальний тайм-аут на весь життєвий цикл запиту
	}
}
```

### Довідник полів http.Transport

| Поле `http.Transport` | Тип | Значення за замовчуванням | Пояснення та наслідки конфігурації |
|---|---|---|---|
| `MaxIdleConns` | `int` | `100` | Максимальна сумарна кількість сокетів у стані спокою (IDLE) для всіх хостів разом. При перевищенні найстаріші сокети закриваються. |
| `MaxIdleConnsPerHost` | `int` | `2` | **Найкритичніше поле!** За замовчуванням лише 2 вільних з'єднання утримуються для одного хоста. Усі наступні з'єднання понад 2 закриваються відразу після завершення запиту, зводячи ефективність пулу нанівець. Рекомендовано підвищувати до 20–100 для мікросервісів. |
| `MaxConnsPerHost` | `int` | `0` (без обмежень) | Максимальна кількість відкритих з'єднань (активні в роботі + вільні в пулі) до одного хоста. При досягненні ліміту нові виклики блокуються до звільнення каналу. |
| `IdleConnTimeout` | `time.Duration` | `90s` | Максимальний час очікування нового запиту у вільному стані перед закриттям сокета клієнтом. |
| `ResponseHeaderTimeout` | `time.Duration` | `0` (нескінченно) | Максимальний час очікування відповіді від сервера після надсилання тіла запиту до отримання першого байта заголовків. |
| `DisableKeepAlives` | `bool` | `false` | Якщо `true`, відключає персистентні з'єднання і додає заголовок `Connection: close` до кожного запиту. |

## Керування пулом у C/C++ через libcurl

У нативних застосунках системного рівня найпоширенішою бібліотекою є `libcurl`. Бібліотека підтримує автоматичне кешування з'єднань через дескриптор `CURL*` або менеджер мульти-дескрипторів `CURLM*`.

Ключові опції конфігурації пулу в libcurl:
- `CURLOPT_MAXCONNECTS`: максимальна кількість одночасно кешованих відкритих з'єднань. Якщо ліміт вичерпано, найстаріше неактивне з'єднання закривається за алгоритмом LRU.
- `CURLOPT_FRESH_CONNECT`: при значенні `1L` змушує бібліотеку відкрити нове з'єднання для поточного запиту, ігноруючи вже наявні вільні сокети в пулі, але дозволяючи новоствореному сокету повернутися в пул після завершення.
- `CURLOPT_FORBID_REUSE`: при значенні `1L` вимагає негайного закриття сокета після виконання запиту (додає семантику `Connection: close`), унеможливлюючи його потрапляння в пул.
- `CURLMOPT_MAX_HOST_CONNECTIONS`: для асинхронного інтерфейсу `curl_multi` задає жорстке обмеження на кількість одночасних з'єднань до одного конкретного хоста.

Слід пам'ятати, що дескриптор `CURL*` не є потокобезпечним: один дескриптор не можна використовувати з кількох потоків одночасно без зовнішнього м'ютекса. Для багатопотокового пулу кожен потік створює власний `CURL*` дескриптор, але може спільно використовувати глобальний пул з'єднань через дескриптор `CURLSH*` (Shared Handle) із блокуванням блокувальних функцій `CURL_LOCK_DATA_CONNECT`.

## Налаштування параметрів сокета на рівні ОС

Для запобігання затримкам та детекції розривів каналу застосовуються системні опції сокетів (`setsockopt`):

| Опція сокета | Рівень | Типове значення | Вплив на роботу пулу |
|---|---|---|---|
| `TCP_NODELAY` | `IPPROTO_TCP` | `1` (увімкнено) | Вимикає алгоритм Наґла (Nagle's Algorithm). Запобігає затримці 40–200 мс при надсиланні дрібних HTTP-запитів, передаючи байти в мережу негайно без очікування заповнення буфера до розміру MSS. |
| `SO_KEEPALIVE` | `SOL_SOCKET` | `1` (увімкнено) | Вмикає періодичне надсилання порожніх TCP ACK-пакетів (зондування) на транспортному рівні L4 для перевірки живучості сокета при тривалій бездіяльності. |
| `TCP_KEEPIDLE` | `IPPROTO_TCP` | `60` (секунд) | Час спокою сокета перед відправленням першого TCP Keep-Alive зонда (Linux). |
| `TCP_KEEPINTVL` | `IPPROTO_TCP` | `10` (секунд) | Інтервал між повторними зондами, якщо відповідь не отримана. |
| `TCP_KEEPCNT` | `IPPROTO_TCP` | `5` (спроб) | Кількість втрачених зондів, після якої ядро ОС вважає з'єднання розірваним і повертає `ETIMEDOUT`. |

## Матриця конфігурації для типових профілів навантаження

Залежно від характеру взаємодії сервісу з зовнішнім світом параметри пулу налаштовуються за різними стратегіями:

### 1. Мікросервісний клієнт (високий RPS, фіксована кількість відомих бекендів)
- `pool_connections`: дорівнює кількості цільових мікросервісів (наприклад, 10–20).
- `pool_maxsize` (`MaxIdleConnsPerHost`): 50–100 на кожен сервіс для підтримки паралельних потоків без створення нових сокетів.
- `pool_block`: `True`, щоб запобігти вибуховому відкриттю тисяч одноразових сокетів при сплесках запитів.
- `connect_timeout`: 1.05–2.05 с (у внутрішній мережі датацентру RTT мінімальний).
- `read_timeout`: 3.0–5.0 с.

### 2. Веб-краулер або парсер (тисячі випадкових доменів, низький RPS на один домен)
- `pool_connections`: 100–500, щоб утримувати відкриті з'єднання до великої кількості сайтів.
- `pool_maxsize`: 2–5 на кожен домен, оскільки надсилати десятки паралельних запитів на один сайт небажано через ризик потрапити під блокування Rate Limiter.
- `pool_block`: `False`, щоб не зупиняти чергу сканування при повільних відповідях.
- `connect_timeout`: 5.05 с.
- `read_timeout`: 15.0–30.0 с.

### 3. Низьколатентний торговий бот або RPC-клієнт
- `pool_connections`: 1–2.
- `pool_maxsize`: дорівнює кількості робочих потоків.
- `TCP_NODELAY`: 1 (обов'язково).
- `connect_timeout`: 0.5 с.
- `read_timeout`: 1.0 с.

## Типові винятки та діагностика системних ресурсів

- **`requests.exceptions.ConnectionError: ('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))`:** Сервер закрив TCP-з'єднання за власним таймаутом `keepalive_timeout` рівно в момент відправлення клієнтом наступного запиту з пулу. Розв'язується налаштуванням `Retry(total=3)` для ідемпотентних методів.
- **`urllib3.exceptions.PoolOverflowError: Connection pool is full, discarding connection: api.example.com`:** Усі `pool_maxsize` слотів зайняті, а параметр `pool_block=False`. З'єднання виконало запит і було знищене замість повернення в пул.
- **`OSError: [Errno 99] Cannot assign requested address` (`EADDRNOTAVAIL`):** Виснаження пулу локальних ефемерних портів через масове відкриття одноразових з'єднань без Keep-Alive і накопичення десятків тисяч сокетів у стані `TIME_WAIT`.
- **Діагностика через системні утиліти Linux:** Кількість сокетів у стані `TIME_WAIT` та `ESTABLISHED` перевіряється командою `ss -s` або `netstat -nat | grep TIME_WAIT | wc -l`.
- **Тюнінг ядра Linux для високого навантаження:** Увімкнення `sysctl -w net.ipv4.tcp_tw_reuse=1` дозволяє безпечно перевикористовувати сокети у стані `TIME_WAIT` для нових вихідних з'єднань, якщо це не суперечить часовим міткам TCP Timestamps (RFC 1323).
