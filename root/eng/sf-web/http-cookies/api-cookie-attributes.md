# 📋 Довідник заголовків і директив Set-Cookie та Cookie

Цей довідник містить вичерпний опис синтаксичної структури, керуючих директив, алгоритмів зіставлення областей видимості, правил обробки дат, захисних префіксів та обмежень пам'яті для заголовків `Set-Cookie` та `Cookie` відповідно до стандартів RFC 6265 та RFC 6265bis.

## 1. Синтаксична структура та граматика (BNF)

Протокол HTTP використовує два різні заголовки для керування станом. Сервер надсилає заголовок `Set-Cookie` у відповіді (по одному заголовку на кожне cookie, яке потрібно встановити або оновити). Клієнт (браузер) повертає збережені пари у єдиному заголовку `Cookie` під час кожного відповідного HTTP-запиту.

Формальний синтаксис описується розширеною формою Бекуса — Наура (ABNF):

```
Set-Cookie        = cookie-name "=" cookie-value *( ";" SP cookie-av )
cookie-name       = 1*<будь-який US-ASCII символ крім CTLs, SP і роздільників>
cookie-value      = *cookie-octet / ( DQUOTE *cookie-octet DQUOTE )
cookie-octet      = %x21 / %x23-2B / %x2D-3A / %x3C-5B / %x5D-7E
                    ; Будь-який друкований ASCII-символ крім керуючих, пробілу,
                    ; подвійних лапок, коми, крапки з комою та зворотного слешу.

cookie-av         = expires-av / max-age-av / domain-av /
                    path-av / secure-av / httponly-av /
                    samesite-av / partitioned-av / extension-av

Cookie            = "Cookie:" SP cookie-pair *( ";" SP cookie-pair )
cookie-pair       = cookie-name "=" cookie-value
```

Символи-роздільники (separators), які заборонено використовувати в імені та в нелапковому значенні без попереднього кодування:
`(` `)` `<` `>` `@` `,` `;` `:` `\` `"` `/` `[` `]` `?` `=` `{` `}` та символ пробілу.

Якщо застосунку потрібно передати довільні рядки в кодуванні UTF-8, бінарні геші або складні структури даних, їх обов'язково кодують за допомогою стандартного URL-кодування (Percent-Encoding, наприклад, через `encodeURIComponent` або `urllib.parse.quote`) або Base64.

## 2. Повний опис директив Set-Cookie

Директиви передаються після пари `ім'я=значення` через крапку з комою та пробіл. Порядок директив у заголовку стандартом не регламентується, а їхній регістр є нечутливим (`httponly` еквівалентно `HttpOnly`).

### Директива `name=value` (Обов'язкова пара)
Визначає ідентифікатор та корисне навантаження.
- Якщо заголовок не містить знака `=`, браузер інтерпретує весь рядок до першої крапки з комою як ім'я з порожнім значенням.
- Якщо сервер надсилає `Set-Cookie` з тим самим іменем, дотичним доменом і шляхом, що й уже збережене cookie, старий запис у сховищі повністю замінюється новим значенням і новими атрибутами.

### Директива `Expires=<HTTP-date>` (Абсолютний час згасання)
Задає граничний момент часу, після настання якого браузер зобов'язаний негайно вилучити cookie зі свого сховища.
- Формат дати: стандартний рядок дати за RFC 1123, RFC 850 або asctime (наприклад, `Expires=Wed, 21 Oct 2026 07:28:00 GMT`).
- Часовий пояс: обов'язково всесвітній координований час (GMT або UTC). Вказівка локальних зміщень (`+0300`) заборонена стандартом.
- Якщо дата вказана в некоректному або нерозпізнаваному форматі, браузер ігнорує директиву `Expires` і вважає cookie звичайним сесійним.

### Директива `Max-Age=<number>` (Відносний строк життя)
Визначає тривалість життя cookie в секундах від моменту отримання заголовка клієнтом.
- Значення має бути цілим числом: додатним, нульовим або від'ємним.
- `Max-Age > 0`: cookie зберігається в енергонезалежній пам'яті на вказану кількість секунд.
- `Max-Age <= 0`: браузер негайно видаляє це cookie з пам'яті та диска.
- **Пріоритет:** Якщо у заголовку одночасно присутні і `Max-Age`, і `Expires`, усі сучасні браузери (за вимогою RFC 6265) повністю ігнорують `Expires` і керуються виключно значенням `Max-Age`.

### Директива `Domain=<domain-value>` (Область видимості за доменом)
Визначає перелік хостів, яким дозволено отримувати cookie.
- **Відсутність директиви (Host-Only Cookie):** якщо директиву `Domain` не вказано взагалі, створюється запис, прив'язаний виключно до точного хоста з URL відповіді. Cookie надсилатиметься лише на цей сервер і ніколи не потрапить на його піддомени.
- **Явна вказівка домену:** якщо вказано `Domain=example.com`, cookie надсилатиметься на сам домен `example.com` та на абсолютно всі його піддомени будь-якої вкладеності (`api.example.com`, `auth.stage.example.com`).
- **Спадщина старих стандартів:** початкова крапка (`Domain=.example.com`), яка була обов'язковою в RFC 2109, стандартом RFC 6265 ігнорується. Браузери автоматично відкидають провідну крапку й обробляють запис як `example.com`.

### Директива `Path=<path-value>` (Область видимості за шляхом)
Встановлює префікс URL-шляху, для якого діє cookie.
- Якщо директиву опущено, браузер використовує шлях із URL поточного запиту без кінцевого сегмента файлу (наприклад, для запиту до `/docs/api/v1` шляхом за замовчуванням стане `/docs/api`).
- Cookie додається до запиту тоді й лише тоді, коли шлях цільового URL починається з префікса `Path`. Наприклад, `Path=/app` підходить для `/app`, `/app/`, `/app/login` та `/app-info` (якщо шлях не завершено слешем). Щоб уникнути помилкового зіставлення з `/app-extra`, шлях рекомендується завершувати косим слешем: `Path=/app/`.

### Директива `Secure` (Вимога шифрування каналу)
Забороняє передачу cookie відкритим каналом зв'язку.
- Браузер надсилає це cookie виключно у складі HTTP-запитів, які передаються через зашифрований протокол TLS/HTTPS.
- Якщо користувач переходить за незахищеним посиланням `http://`, cookie з прапорцем `Secure` вилучається з вихідного заголовка `Cookie`.
- **Виняток для розробки:** сучасні браузери дозволяють передавати `Secure`-cookie на `localhost` та адреси зворотного зв'язку (`127.0.0.1`) навіть без сертифіката TLS, щоб спростити локальну розробку та тестування.

### Директива `HttpOnly` (Ізоляція від клієнтського коду)
Приховує cookie від клієнтських скриптів і DOM API.
- Властивість `document.cookie` у JavaScript не відображає записів із прапорцем `HttpOnly`.
- Клієнтські скрипти не мають змоги читати, змінювати чи видаляти такі cookie через виклики API.
- Мережевий стек браузера продовжує автоматично додавати `HttpOnly`-cookie до всіх відповідних вихідних HTTP-запитів, включаючи ті, що ініційовані функціями `fetch()` або `XMLHttpRequest`.
- Це головний архітектурний засіб захисту сесійних токенів від викрадення в разі успішної атаки міжсайтового скриптингу (XSS).

### Директива `SameSite=<Strict|Lax|None>` (Міжсайтова ізоляція)
Керує відправленням cookie у міжсайтових контекстах (Cross-Site Requests) для запобігання атакам підробки запитів (CSRF) та захисту приватності.
- **`Strict`:** Cookie надсилається виключно тоді, коли поточний сайт у вкладці та адреса запиту збігаються. Будь-які зовнішні переходи (навіть клік по простому посиланню зі стороннього ресурсу) блокують передачу cookie.
- **`Lax` (Сучасне значення за замовчуванням):** Cookie блокується при небезпечних або фонових запитах зі сторонніх сайтів (POST-форми, `<img>`, `<iframe>`, `fetch()`), але дозволяється при безпечній навігації верхнього рівня (Top-Level GET navigation, наприклад, звичайний клік по посиланню `<a href="...">`).
- **`None`:** Cookie надсилається в усіх контекстах, включаючи сторонні вбудовані ресурси та міжсайтові форми. **Обов'язкова вимога:** `SameSite=None` працює лише за наявності прапорця `Secure`. Якщо `Secure` відсутній, браузер відхиляє весь заголовок `Set-Cookie`.

### Директива `Partitioned` (CHIPS — розділене сховище)
Вмикає режим Cookies Having Independent Partitioned State.
- Cookie зберігається не в глобальному сховищі сторонніх ресурсів, а в окремому ізольованому розділі, прив'язаному до пари: `(Сайт верхнього рівня, Домен вбудованого ресурсу)`.
- Дозволяє вбудованим віджетам (платіжним формам, чатам) зберігати стан без можливості здійснювати міжсайтове стеження за користувачем.

## 4. Захисні префікси імен (RFC 6265bis)

Щоб захистити чутливі cookie від підміни скомпрометованими піддоменами або через відкриті незашифровані канали, RFC 6265bis визначає два зарезервовані префікси імен: `__Secure-` та `__Host-`.

Якщо назва cookie починається з одного з цих префіксів, мережевий стек браузера здійснює сувору перевірку перед збереженням. Якщо хоча б одна вимога порушена, браузер відкидає заголовок повністю.

```
Вимоги префікса __Secure-:
1. Відповідь отримана виключно через HTTPS.
2. Присутня директива Secure.
(Директиви Domain та Path можуть бути будь-якими валідними).

Вимоги префікса __Host- (Максимальна ізоляція):
1. Відповідь отримана виключно через HTTPS.
2. Присутня директива Secure.
3. Директива Domain ПОВНІСТЮ ВІДСУТНЯ (cookie зобов'язане бути Host-Only).
4. Директива Path присутня і має точне значення "/" (Path=/).
```

### Порівняльна таблиця префіксів

| Параметр перевірки | Звичайне cookie | `__Secure-name` | `__Host-name` |
| :--- | :--- | :--- | :--- |
| **Протокол передачі** | HTTP або HTTPS | Тільки HTTPS | Тільки HTTPS |
| **Прапорець `Secure`** | Опціонально | Обов'язково | Обов'язково |
| **Директива `Domain`** | Дозволена | Дозволена | **Категорично заборонена** |
| **Директива `Path`** | Будь-який валідний | Будь-який валідний | **Тільки `Path=/`** |
| **Стійкість до підміни піддоменами** | Низька (піддомен може перетерти) | Низька (піддомен може перетерти) | **Абсолютна (піддомени ізольовані)** |

## 5. Алгоритми зіставлення та правила роботи Cookie Jar

Перед відправленням будь-якого вихідного HTTP-запиту браузер виконує покроковий алгоритм фільтрації кожного збереженого запису:

```
[Початок перевірки запису cookie]
               │
               ▼
   1. Перевірка безпеки каналу (Secure)
   ├─ Cookie має прапорець Secure, але схема запиту http:// ──► [ВІДХИЛИТИ]
   └─ Схема запиту https:// або cookie не має Secure ─────────► ПРОДОВЖИТИ
               │
               ▼
   2. Перевірка домену (Domain Match)
   ├─ Host-Only cookie: домен запиту != домен cookie ─────────► [ВІДХИЛИТИ]
   ├─ Доменне cookie: домен запиту не є суфіксом домену cookie ► [ВІДХИЛИТИ]
   └─ Збіг успішний ──────────────────────────────────────────► ПРОДОВЖИТИ
               │
               ▼
   3. Перевірка шляху (Path Match)
   ├─ Шлях запиту не починається з префікса Path cookie ──────► [ВІДХИЛИТИ]
   └─ Шлях збігається ────────────────────────────────────────► ПРОДОВЖИТИ
               │
               ▼
   4. Перевірка строку дії (Expiry Check)
   ├─ Поточний час перевищує Expires або Max-Age ─────────────► [ВИДАЛИТИ Й ВІДХИЛИТИ]
   └─ Строк чинний ───────────────────────────────────────────► ПРОДОВЖИТИ
               │
               ▼
   5. Перевірка міжсайтового контексту (SameSite Match)
   ├─ Strict при міжсайтовому переході будь-якого типу ────────► [ВІДХИЛИТИ]
   ├─ Lax при міжсайтовому POST-запиті, iframe або fetch() ────► [ВІДХИЛИТИ]
   └─ Дозволено контекстом ────────────────────────────────────► ПРОДОВЖИТИ
               │
               ▼
[Додати пару "ім'я=значення" до вихідного заголовка Cookie]
```

### Алгоритм парсингу дат (RFC 6265 §5.1.1)
Алгоритм розбору значень директиви `Expires` стандартизовано для роботи з реальними даними веб-серверів:
1. Рядок розбивається на послідовність лексем за роздільниками (пробіли, коми, двокрапки, дефіси).
2. Алгоритм послідовно знаходить компоненти: час `HH:MM:SS`, день місяця `DD` (1–31), назву місяця (трилітерні скорочення англійською: `Jan`, `Feb`, `Mar`, `Apr`, `May`, `Jun`, `Jul`, `Aug`, `Sep`, `Oct`, `Nov`, `Dec`) та рік `YYYY`.
3. Якщо рік вказано двома цифрами: значення від 70 до 99 розширюється до `1970–1999`, а значення від 00 до 69 розширюється до `2000–2069`.
4. Якщо будь-який компонент відсутній або виходить за допустимі межі (наприклад, 32 січня), дата визнається недійсною, і браузер автоматично вважає cookie сесійним.

### Алгоритм зіставлення доменів (Domain Matching, RFC 6265 §5.1.3)
Рядок хоста запиту `H` відповідає рядку домену cookie `D`, якщо виконується одна з умов:
1. Рядки `H` та `D` ідентичні за байтовим порівнянням (без урахування регістру символів ASCII).
2. Рядок `D` є суфіксом рядка `H`, причому символ у `H`, який безпосередньо передує суфіксу `D`, є крапкою `.`, і хост `H` не є сирою IP-адресою (IPv4 або IPv6).

Це правило гарантує, що домен `example.com` матчить `app.example.com` (суфікс відділено крапкою), але ніколи не збіжиться з `myexample.com` чи `fakeexample.com`.

### Алгоритм зіставлення шляхів (Path Matching, RFC 6265 §5.1.4)
Шлях запиту `P_req` відповідає шляху cookie `P_cookie`, якщо виконується одна з трьох умов:
1. Рядок `P_req` ідентичний `P_cookie`.
2. Рядок `P_req` починається з префікса `P_cookie`, і останній символ у `P_cookie` є косим слешем `/` (наприклад, `P_cookie=/api/`, `P_req=/api/users`).
3. Рядок `P_req` починається з префікса `P_cookie`, і першим символом у `P_req` після закінчення префікса є косий слеш `/` (наприклад, `P_cookie=/api`, `P_req=/api/users`).

### Алгоритм сортування заголовка Cookie
Якщо для даного запиту збіглося декілька cookie:
1. Браузер сортує всі підібрані записи за спаданням довжини директиви `Path` (cookie з довшим і точнішим шляхом додаються першими: наприклад, `Path=/api/v1/` передує `Path=/api/` та `Path=/`).
2. Якщо довжина шляху однакова, стандарти RFC 6265 не гарантують фіксованого порядку між Host-Only та доменними записами. Це робить критично важливим використання префікса `__Host-` для уникнення колізій імен.

## 6. Взаємодія з Storage Access API, CORS та сторонніми фреймами

Сучасні браузери (Safari ITP, Firefox ETP, Chrome Privacy Sandbox) реалізують багаторівневі механізми захисту від стеження (Tracking Prevention), які автоматично ізолюють сховища різних доменів.

### Storage Access API (SAA)
Якщо сторонньому сервісу (наприклад, віджету авторизації через соціальну мережу або платіжному модулю) необхідно отримати доступ до своїх непарційованих cookie всередині `iframe`, він зобов'язаний скористатися **Storage Access API (SAA)**:

```javascript
// Перевірка та запит доступу до сторонніх cookie всередині iframe
if (document.requestStorageAccess) {
  document.hasStorageAccess().then(hasAccess => {
    if (!hasAccess) {
      // Вимагає прямої взаємодії користувача (User Gesture: клік або тач)
      document.requestStorageAccess().then(
        () => { /* Доступ надано: document.cookie тепер бачить власні cookie */ },
        () => { /* Користувач або браузер відхилив доступ */ }
      );
    }
  });
}
```

Виклик `document.requestStorageAccess()` викликає системне діалогове вікно браузера з проханням надати дозвіл. Якщо користувач погоджується, браузер тимчасово відкриває доступ до сховища cookie стороннього ресурсу виключно у контексті поточної вкладки.

### Взаємодія з політиками CORS (Cross-Origin Resource Sharing)
Якщо клієнтський JavaScript здійснює крос-доменний асинхронний запит через `fetch('https://api.example.com/data', { credentials: 'include' })`, на передачу cookie накладаються особливі правила:
1. Клієнт обов'язково вказує `credentials: 'include'`. За замовчуванням `fetch` не надсилає cookie на сторонні Origin.
2. Сервер `api.example.com` зобов'язаний повернути заголовок `Access-Control-Allow-Credentials: true`.
3. Заголовок `Access-Control-Allow-Origin` на сервері **категорично не може дорівнювати зірочці `*`**. Сервер зобов'язаний явно вказати точне походження клієнта (наприклад, `Access-Control-Allow-Origin: https://app.example.com`). Якщо вказано `*`, браузер блокує відповідь і не передає отримані дані скрипту.

### Нестандартні та застарілі розширення: Priority та P3P
У різні періоди розвитку веб-технологій компанії намагалися впроваджувати власні директиви:
- **`Priority=Low|Medium|High`:** нестандартне розширення Chromium, що дозволяє вказати пріоритет витіснення cookie при переповненні сховища (записи з `Priority=High` видаляються останніми).
- **`P3P (Platform for Privacy Preferences)`:** застарілий заголовок політики конфіденційності Microsoft (наприклад, `P3P: CP="CAO PSA OUR"`), який використовувався в Internet Explorer для дозволу сторонніх cookie. Стандартом RFC 6265 повністю скасований і сучасними браузерами ігнорується.

## 7. Квоти пам'яті, витіснення та конфігурація серверів

Браузери та веб-сервери накладають суворі технічні ліміти на обсяг даних у заголовках cookie.

### Клієнтські обмеження сховища (Cookie Jar)
- **Мінімальний розмір одного cookie:** 4096 байтів (4 КБ), включаючи ім'я, значення та всі атрибути в `Set-Cookie`. Якщо сервер надсилає заголовок, довжина якого перевищує 4 КБ, браузер повністю відкидає такий запис.
- **Кількість cookie на один домен:** від 50 до 180 записів залежно від браузера (у Chromium — 180, у Firefox — 150). При перевищенні ліміту браузер автоматично видаляє найстаріші записи за алгоритмом найменш недавнього використання (LRU, Least Recently Used).
- **Загальна кількість cookie у браузері:** від 3000 до 10 000 записів.

### Пріоритети під час витіснення (Eviction Priority)
Коли ліміт записів на домен вичерпано:
1. Браузер видаляє всі прострочені cookie, строк яких уже минув за часом `Expires`/`Max-Age`.
2. Якщо пам'яті все ще недостатньо, витісняються сесійні та незахищені cookie за принципом найдавнішого звернення (LRU).
3. Сучасні рушії (Chromium, Gecko) захищають записи з префіксами `__Host-` та прапорцем `Secure` від передчасного витіснення звичайними незахищеними cookie, запобігаючи випадковому скиданню автентифікації користувача.

### Серверні ліміти та взаємодія з кешуванням
Веб-сервери виділяють фіксовані буфери пам'яті під заголовки клієнтських запитів. Якщо сумарний розмір усіх cookie перевищує встановлений поріг, сервер повертає статус помилки:
- **`431 Request Header Fields Too Large`:** розмір окремого заголовка або всіх заголовків разом перевищив допустиму норму.
- **`400 Bad Request`:** заголовок містить заборонені байти, нерозпізнані керуючі символи або пошкоджене кодування.

Якщо відповідь сервера містить заголовок `Set-Cookie`, проміжні проксі-сервери (CDN, зворотні проксі) зобов'язані **не кешувати** цей заголовок для інших користувачів. Сервер повинен супроводжувати такі відповіді директивою `Cache-Control: private` або `Cache-Control: no-cache="Set-Cookie"`, щоб уникнути витоку чужої сесії іншим клієнтам мережі.

### Налаштування лімітів буфера заголовків у серверах
- **Nginx:** директиви `large_client_header_buffers 4 8k;` та `client_header_buffer_size 1k;`.
- **Apache HTTP Server:** директива `LimitRequestFieldSize 8190`.
- **Node.js (HTTP Parser):** параметр `--max-http-header-size=16384` (за замовчуванням 16 КБ).
- **Envoy Proxy:** параметр `max_request_headers_kb` (за замовчуванням 60 КБ).
