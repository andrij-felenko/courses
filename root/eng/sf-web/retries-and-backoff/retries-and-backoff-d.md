Клієнтський застосунок надсилає HTTP-запит до платіжного шлюзу або каталогу товарів, що обробляє 5000 операцій за секунду. Раптово під час планового оновлення контейнерів або короткочасної паузи збирача сміття (Garbage Collection) сервер перестає відповідати на 200 мілісекунд: черга очікування вхідних з'єднань (`listen backlog`) у ядрі операційної системи переповнюється, і мережевий стек надсилає клієнтам пакети `TCP RST` або обриває з'єднання за тайм-аутом (`ETIMEDOUT`). Одночасно 500 активних клієнтів отримують помилку зв'язку. Якщо кожен із цих клієнтів негайно повторить запит у ту саму мілісекунду, на сервер, який щойно намагався розібрати накопичену чергу, впаде подвійна хвиля з 1000 запитів. Навантаження на процесор і пул з'єднань бази даних досягне 100%, проміжний балансувальник визнає екземпляри непрацездатними й виведе їх із пулу, а короткочасне коливання тривалістю в частку секунди перетвориться на повномасштабну відмову всієї інфраструктури.

Така лавиноподібна самодеградація розподіленої системи виникає через відсутність контролю за повторними спробами. Щоб перетворити мережевий клієнт із потенційного генератора відмови в обслуговуванні на стійкий компонент, інженерія розподілених систем спирається на три взаємопов'язані принципи: розпізнавання природи помилок, адаптивне розсіювання повторних спроб у часі за допомогою експоненційного відступу з випадковим тремтінням (Jitter) та гарантію ідемпотентності мутуючих операцій.

## Анатомія тимчасових збоїв у розподілених системах

Усі помилки, з якими стикається мережевий клієнт під час взаємодії через HTTP, поділяються на два принципово різні класи:

1. **Фатальні (перманентні) помилки:** виникають через некоректні дії клієнта або незворотні стани сервера. Якщо клієнт надіслав невалідний JSON (`400 Bad Request`), звернувся без валідного токена (`401 Unauthorized`), запросив заборонений ресурс (`403 Forbidden`) чи неіснуючий маршрут (`404 Not Found`), жоден повтор запиту без зміни його тіла чи прав доступу не змінить результат. Повторювати такі запити безглуздо — клієнт зобов'язаний негайно повернути помилку на рівень бізнес-логіки.
2. **Тимчасові (минущі) збої (від англ. *transient faults*, лат. *transire* — «проминати, переходити»):** спричинені короткочасними фізичними чи програмними станами компонентів на шляху між клієнтом і сервером. До них належать мікро-розриви зв'язку в бездротових мережах, перезапуск робочих процесів під час кочення релізу, миттєве вичерпання пулу підключень до бази даних або перевищення локального ліміту пропускної здатності. Головна властивість тимчасового збою полягає в тому, що через певний проміжок часу система самостійно повертається до нормального функціонування, і повторний виклик буде успішним.

```
                  ┌──────────────────────────────────────────────────────────┐
                  │                 Класифікація помилок                     │
                  └─────────────────────────────┬────────────────────────────┘
                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 ▼                                                             ▼
  ┌───────────────────────────────┐                             ┌───────────────────────────────┐
  │       Фатальні помилки        │                             │       Тимчасові збої          │
  │    (Retry ЗАБОРОНЕНО)         │                             │     (Retry ДОЗВОЛЕНО)         │
  ├───────────────────────────────┤                             ├───────────────────────────────┤
  │ 400 Bad Request               │                             │ 429 Too Many Requests         │
  │ 401 Unauthorized              │                             │ 502 Bad Gateway               │
  │ 403 Forbidden                 │                             │ 503 Service Unavailable       │
  │ 404 Not Found                 │                             │ 504 Gateway Timeout           │
  │ 422 Unprocessable Entity      │                             │ TCP RST (ECONNRESET)          │
  │ 405 Method Not Allowed        │                             │ Socket Timeout (ETIMEDOUT)    │
  └───────────────────────────────┘                             └───────────────────────────────┘
```

На рівні системних викликів операційної системи Linux поведінка мережевого сокета регулюється чергами ядра:
- **`tcp_max_syn_backlog`:** черга напіввідкритих з'єднань (стадія `SYN_RECV`). Якщо вона заповнюється через шквал запитів, ядро або мовчки скидає вхідні пакети `SYN`, або за наявності увімкненого механізму SYN Cookies надсилає відповідь із криптографічним номером послідовності.
- **`net.core.somaxconn`:** черга повністю встановлених з'єднань (`ESTABLISHED`), які очікують виклику `accept()` прикладним процесом веб-сервера. Якщо веб-сервер завис у збирачі сміття, черга переповнюється, і ядро за замовчуванням надсилає клієнтам пакет `TCP RST` (при параметрі ядра `net.ipv4.tcp_abort_on_overflow = 1`), що транслюється в помилку `ECONNRESET` на клієнті.
- **`SO_RCVTIMEO` / `SO_SNDTIMEO`:** сокетні тайм-аути читання та запису. Коли балансувальник або бекенд перестає зчитувати дані чи надсилати байти відповіді довше заданого інтервалу, клієнтський сокет генерує системну помилку `ETIMEDOUT`.

Серед статус-кодів HTTP тимчасовими вважаються:
- **`429 Too Many Requests`:** сервер чи API-шлюз зафіксував перевищення клієнтської квоти (Rate Limit). Сервер працездатний, але вимагає від клієнта знизити темп відправлення запитів.
- **`503 Service Unavailable`:** сервер тимчасово не здатний обробити запит через перевантаження або проведення технічного обслуговування. Це прямий сигнал про брак ресурсів у поточний момент.
- **`502 Bad Gateway` та `504 Gateway Timeout`:** проміжний вузол (зворотний проксі-сервер Nginx, балансувальник ALB або API-шлюз) не зміг отримати вчасну відповідь від бекенда через його зависання або падіння робочого процесу.

Окреме місце посідає код **`500 Internal Server Error`**. Він може означати як фатальну помилку в коді (наприклад, розіменування нульового вказівника чи необроблений виняток ділення на нуль, які повторювати марно), так і тимчасову проблему інфраструктури (втрату зв'язку з реплікою бази даних). Безпечно повторювати помилку 500 можна лише тоді, коли архітектура сервісу чітко гарантує, що неперехоплені інфраструктурні збої загортаються в цей код без порушення стану системи.

## Механіка повторного шторму (Retry Storm) та каскадний колапс

Найпростіша клієнтська реакція на мережевий збій — негайно виконати виклик ще раз у циклі `while (retries < 3)`. У спокійному стані системи, коли поодинокий клієнт стикається з випадковою втратою одного IP-пакета на локальному Wi-Fi маршрутизаторі, такий наївний повтор спрацьовує непомітно: за 5 мілісекунд надходить успішна відповідь.

Проте коли збій має системний характер (наприклад, база даних заблокувала таблицю на 2 секунди через виконання важкої аналітичної міграції), наївні повтори породжують катастрофічне явище — **повторний шторм** (англ. *retry storm*, лат. *tempestas* — «буря, натиск»).

![Порівняння реакцій системи: наївний повторний шторм проти розсіювання з джитером](/root/eng/sf-web/retries-and-backoff/img/retry-storm-cascade.svg)

*Ліворуч негайні повтори створюють лавину запитів, що остаточно добиває перевантажений сервер; праворуч експоненційний відступ із випадковим тремтінням розтягує навантаження в часі, дозволяючи системі розвантажити черги й відновитися.*

Механізм розвитку повторного шторму розгортається за суворим каскадним сценарієм:

1. **Первинна деградація:** бекенд уповільнює обробку запитів з 20 мс до 800 мс. Черга запитів перед веб-сервером починає зростати.
2. **Масовий тайм-аут:** у 1000 активних клієнтів одночасно спрацьовує налаштований тайм-аут очікування (наприклад, 500 мс). З'єднання розриваються, але сервер ще продовжує виконувати вже непотрібну роботу над первинними запитами, марнуючи процесорний час.
3. **Хвиля множення трафіку:** усі 1000 клієнтів миттєво відправляють повторний запит (спроба #2). Вхідний трафік на сервер зростає вдвічі (2000 запитів/с замість базових 1000).
4. **Колапс сокетів:** черга вхідних з'єднань операційної системи переповнюється. Сервер починає відповідати кодами 503 або відкидати пакети SYN.
5. **Третя хвиля:** клієнти роблять спробу #3. Трафік досягає 3000–4000 запитів/с. Витрати пам'яті на утримання черг і контекстів призводять до спрацьовування механізму аварійного завершення процесів ядра (OOM Killer). Сервіс повністю перестає відповідати.

Ситуація додатково погіршується взаємодією з проміжними балансувальниками навантаження. Балансувальник надсилає періодичні запити перевірки стану (Health Checks, наприклад `GET /healthz` кожні 2 секунди). Перевантажений сервер не встигає відповісти на Health Check за виділений тайм-аут у 500 мс. Балансувальник маркує вузол як мертвий і виводить його з експлуатації (Node Eviction). Навантаження, що йшло на цей вузол, миттєво перерозподіляється між рештою сусідніх вузлів кластера, які ще працювали. Сусідні вузли також зазнають перевантаження, падають один за одним, і відбувається повний каскадний колапс (Cascading Failure) усієї інфраструктури.

Замість захисту застосунку наївний повтор перетворює власну клієнтську базу на розподілений ботнет, який не дає серверу жодного шансу завершити накопичені транзакції та повернутися в робочий стан.

## Експоненційний відступ: охолодження системи через нарощування пауз

Щоб розірвати коло повторного шторму, клієнт повинен керуватися базовим правилом теорії масового обслуговування: **що більше разів поспіль операція зазнає невдачі, то довше клієнт зобов'язаний чекати перед наступною спробою**.

Цей принцип реалізує алгоритм **експоненційного відступу** (англ. *exponential backoff*, від лат. *exponere* — «виставляти напоказ, нарощувати»). Після кожної невдалої спроби тривалість очікування подвоюється:

```
t[i] = min(t_max, t_base · 2ⁱ)
```

де:
- `i` — порядковий номер повторної спроби (`i = 0, 1, 2...`);
- `t_base` — базовий початковий інтервал очікування (наприклад, 100 або 200 мс);
- `t_max` — максимальна верхня межа паузи (`max_backoff`, наприклад, 10 або 30 секунд), яка не дозволяє інтервалу зростати до нескінченності;
- `min()` — функція обмеження (зрізання, англ. *truncation*), що фіксує стелю затримки.

> 📜 Про те, як цей алгоритм народився у 1970-х роках для розведення радіосигналів між Гавайськими островами, став фундаментальною основою локальних мереж Ethernet та врятував глобальний Інтернет від колапсу пропускної здатності в 1986 році, докладно розповідає [історія винаходу двійкового відступу Робертом Меткалфом для Ethernet та його перехід у TCP і хмарні системи](root:sf-web/retries-and-backoff/hist-ethernet-backoff.md).

При базовому інтервалі `t_base = 100 мс` детерміновані паузи між спробами складатимуть:
- Спроба 1: `100 · 2⁰ = 100 мс`
- Спроба 2: `100 · 2¹ = 200 мс`
- Спроба 3: `100 · 2² = 400 мс`
- Спроба 4: `100 · 2³ = 800 мс`
- Спроба 5: `100 · 2⁴ = 1600 мс`

Експоненційне зростання забезпечує подвійний ефект: якщо збій був випадковою мікро-флуктуацією мережі, клієнт отримує відповідь уже через 100 мс; якщо ж сервер переживає важку аварію чи рестарт бази даних, запити клієнта автоматично розріджуються, надаючи серверній інфраструктурі «вікно тиші» для завершення ініціалізації та прогріву кешів.

## Пастка фазової синхронізації та випадкове тремтіння (Jitter)

Попри математичну елегантність, чистий експоненційний відступ містить приховану фатальну вразливість у середовищі з багатьма клієнтами.

Уявімо, що 10 000 клієнтів одночасно отримали відмову в момент часу `T = 0`. Якщо кожен із них використовує формулу `t[i] = 100 · 2ⁱ`, поведінка всієї групи стає абсолютно детермінованою:
- Усі 10 000 клієнтів мовчать рівно 100 мс.
- У момент `T = 100 мс` усі 10 000 клієнтів **одночасно** надсилають повторний запит. Сервер отримує потужний удар імпульсного навантаження тієї ж сили, що й у момент первинного падіння.
- Сервер знову падає під синхронним ударом і повертає 503.
- Усі 10 000 клієнтів відраховують 200 мс і завдають наступного синхронного удару в момент `T = 300 мс` (`100 + 200`).
- Третій синхронний удар припадає точно на момент `T = 700 мс` (`300 + 400`).

Виникає автоколивальний процес: трафік перетворюється на серію синхронних ударних хвиль (англ. *lockstep pulsed traffic*). Сервер перебуває або в стані повного простою, або під нищівним піковим перевантаженням.

![Алгоритми випадкового тремтіння: порівняння часових інтервалів](/root/eng/sf-web/retries-and-backoff/img/jitter-algorithms-comparison.svg)

*Порівняння чотирьох стратегій відступу: чистий експоненційний відступ концентрує навантаження в дельта-точках; повний, рівний та декорельований джитер розмивають імовірність виклику по часовій осі.*

Щоб зруйнувати фазову синхронізацію клієнтів, у розрахунок паузи вводиться стохастичний компонент — **випадкове тремтіння**, або **джитер** (англ. *jitter* — «дрібне тремтіння, хаотичне коливання»). Джитер штучно зсуває момент відправлення кожного запиту, розмазуючи пікове навантаження в часі.

В інженерній практиці використовують три основні алгоритми рандомізації відступу:

### 1. Повний джитер (Full Jitter)
Клієнт обчислює поточну експоненційну межу `B = min(t_max, t_base · 2ⁱ)`, після чого обирає випадкову тривалість очікування рівномірно на відрізку від `0` до `B`:

```
t = Uniform(0, min(t_max, t_base · 2ⁱ))
```

Full Jitter забезпечує найвищий рівень дисперсії. Оскільки запити рівномірно розподіляються по всьому інтервалу від 0 до експоненційного максимуму, пікове навантаження на сервер у будь-який момент часу є мінімально можливим.

### 2. Рівний джитер (Equal Jitter)
Клієнт ділить розраховану експоненційну стелю навпіл: перша половина є гарантованою базовою паузою, а друга половина обирається випадково:

```
half = min(t_max, t_base · 2ⁱ) / 2
t = half + Uniform(0, half)
```

Equal Jitter гарантує, що клієнт ніколи не зробить повторний запит занадто швидко (мінімальна затримка дорівнює `half`), уникаючи майже нульових пауз, які інколи трапляються у Full Jitter. Платою за це є зменшення дисперсії розсіювання вдвічі.

### 3. Декорельований джитер (Decorrelated Jitter)
Замість прямої прив'язки до експоненти від номера спроби `2ⁱ`, кожна наступна пауза обчислюється на основі фактичної тривалості попередньої паузи `t_prev` за допомогою випадкового блукання:

```
t[0] = t_base
t[i] = min(t_max, Uniform(t_base, t[i-1] · 3))
```

Кожен клієнт блукає власною випадковою траєкторією. Навіть якщо тисяча клієнтів одночасно перебуває на третій спробі повтору, їхні затримки не групуються біля однакових значень, що повністю ліквідує будь-які залишкові кореляції в кластері.

> 🧮 Суворе математичне виведення формул математичного сподівання `E[T]`, дисперсії `Var(T)` та ймовірності колізій черг для кожного з трьох розподілів наведено у [математичному аналізі й порівнянні дисперсій розподілів Full, Equal та Decorrelated Jitter](root:sf-web/retries-and-backoff/math-jitter-distributions.md).

## Серверне регулювання: заголовок Retry-After та ліміти швидкості

Хоча клієнтський експоненційний відступ ефективно захищає систему, клієнт діє «наосліп»: він не знає реального внутрішнього стану бекенда й може лише здогадуватися про необхідну тривалість паузи.

Коли сервер має вбудовану систему захисту від перевантажень або обмежувач швидкості (Rate Limiter), він сам повідомляє клієнту точний інтервал очікування за допомогою стандартизованого HTTP-заголовка **`Retry-After`** (RFC 9110).

Заголовок `Retry-After` повертається у відповідях із кодами `429 Too Many Requests` або `503 Service Unavailable` в одному з двох форматів:

1. **Кількість секунд (ціле додатне число):**
   ```http
   HTTP/1.1 429 Too Many Requests
   Retry-After: 30
   Content-Type: application/json

   {"error": "Rate limit exceeded. Please slow down."}
   ```
2. **Абсолютна дата й час за стандартом HTTP-date (GMT/UTC):**
   ```http
   HTTP/1.1 503 Service Unavailable
   Retry-After: Fri, 31 Dec 2026 23:59:59 GMT
   Content-Type: application/json

   {"error": "Database maintenance in progress."}
   ```

Сучасні REST API також доповнюють відповідь заголовками сімейства RateLimit (IETF Draft):
- `RateLimit-Limit`: загальний ліміт запитів у поточному вікні;
- `RateLimit-Remaining`: кількість доступних запитів до скидання вікна;
- `RateLimit-Reset`: час у секундах до повного відновлення квоти.

> 🔧 **Золоте правило клієнтського відступу:** якщо сервер надіслав валідний заголовок `Retry-After`, клієнт **зобов'язаний надати йому абсолютний пріоритет** над власними локальними формулами експоненційного відступу. Клієнт призупиняє виконання на вказану сервером кількість секунд плюс невеликий випадковий додаток (позитивний джитер у межах 0.1–0.5 с), щоб уникнути одночасного залпу всіх клієнтів у момент скидання ліміту.

## Інваріанти ідемпотентності та небезпека мутуючих запитів

Найбільш критична інженерна пастка при реалізації повторів полягає не в математиці затримок, а в **семантиці повторюваної операції**.

Усі методи протоколу HTTP згідно зі стандартом RFC 9110 поділяються за двома фундаментальними ознаками:

1. **Безпечні методи (Safe Methods):** `GET`, `HEAD`, `OPTIONS`, `TRACE`. За визначенням не змінюють стан ресурсів на сервері. Їх можна повторювати будь-яку кількість разів без жодного ризику для цілісності даних.
2. **Ідемпотентні методи (Idempotent Methods, від лат. *idem* — «той самий» + *potens* — «здатний, сильний»):** `PUT`, `DELETE`, а також усі безпечні методи. Повторне виконання ідемпотентного запиту `N` разів призводить до того самого кінцевого стану системи, що й одноразове виконання. Наприклад, виклик `DELETE /users/42` або `PUT /articles/10` (з повною заміною тіла) за першим разом видаляє чи оновлює запис, а за наступних — констатує вже досягнутий стан, не створюючи дублікатів.
3. **Неідемпотентні (мутуючі) методи:** `POST`, `PATCH`. Кожен новий виклик `POST /orders` або `POST /payments/charge` створює *новий* супровідний ресурс або додає зміну до поточного стану (списує гроші з рахунку, генерує нове замовлення).

### Парадокс мережевої невизначеності

У розподілених мережах клієнт і сервер розділені фізичним каналом. Якщо клієнт виконав `POST /payments/charge` і через 5 секунд отримав обрив TCP-з'єднання (`ECONNRESET`) або тайм-аут, виникає принципова невизначеність:
- **Сценарій А:** запит загубився по дорозі до сервера. Сервер нічого не отримував, гроші не списано.
- **Сценарій Б:** сервер успішно отримав запит, провів платіж у базі даних, зняв гроші з картки клієнта, але пакет із відповіддю `200 OK` був втрачений на зворотному шляху через падіння проміжного комутатора.

```
Клієнт                                                 Сервер
  │                                                      │
  │─── 1. POST /payments (Списати 100$) ────────────────►│
  │                                                      │ [Транзакція виконана]
  │                                                      │ [Гроші списано: -100$]
  │                                                      │
  │   ✕ ОБРИВ ЗВ'ЯЗКУ (Відповідь 200 OK втрачено) ───────│
  │                                                      │
  ▼                                                      ▼
[Клієнт бачить Timeout / ECONNRESET]
[Клієнт НЕ ЗНАЄ, чи пройшла оплата!]
  │
  │─── 2. НАЇВНИЙ RETRY: POST /payments ────────────────►│
  │                                                      │ [УВАГА: Друга транзакція!]
  │                                                      │ [Подвійне списання: -200$!]
```

Якщо клієнт у ситуації Б наївно повторить запит `POST /payments/charge`, сервер сприйме його як *нову незалежну платіжну операцію* і спише гроші вдруге. Сліпий повтор неідемпотентних запитів — прямий шлях до фінансових втрат і розсинхронізації даних.

### Заголовок Idempotency-Key та серверна дедуплікація

Єдиним надійним архітектурним розв'язанням проблеми повтору мутуючих операцій є використання механізму **ключів ідемпотентності** (заголовок `Idempotency-Key`, стандартизований IETF Draft та популяризований платіжними шлюзами рівня Stripe).

![Життєвий цикл ідемпотентного повтору: захист від подвійної обробки транзакцій](/root/eng/sf-web/retries-and-backoff/img/idempotency-key-flow.svg)

*Життєвий цикл запиту з ідемпотентним ключем: клієнт фіксує UUID перед першою спробою, а сервер використовує атомарний кеш ключів для дедуплікації транзакцій під час мережевих збоїв.*

Протокол взаємодії з використанням `Idempotency-Key` функціонує за чітким кінцевим автоматом:

1. **Генерація ключа на клієнті:** перед відправленням першого запиту клієнт генерує глобально унікальний ідентифікатор (UUID версії 4, наприклад `7b9e4c21-8f12-4d2a-9e3b-5a1c2d3e4f5a`) і прикріплює його у заголовок:
   ```http
   POST /v1/charges HTTP/1.1
   Host: api.example.com
   Idempotency-Key: 7b9e4c21-8f12-4d2a-9e3b-5a1c2d3e4f5a
   Content-Type: application/json

   {"amount": 10000, "currency": "usd", "customer": "cus_99"}
   ```
2. **Атомарне захоплення на сервері:** отримавши запит, сервер перевіряє наявність ключа в швидкому розподіленому сховищі (Redis або таблиці транзакцій SQL):
   - **Якщо ключ новий:** сервер атомарно записує статус `PROCESSING` із блокуванням (TTL 60–120 секунд), обчислює контрольний хеш тіла запиту `SHA-256(payload)` і передає запит у бізнес-логіку.
   - **Якщо ключ уже має статус `PROCESSING`:** інший потік ще обробляє первинний запит. Сервер негайно повертає код `409 Conflict` або чекає на звільнення блокування.
   - **Якщо ключ має статус `COMPLETED`:** операція вже була успішно виконана раніше. Сервер перевіряє відповідність хешу поточного тіла запиту збереженому хешу (захист від випадкової колізії ключів). Якщо хеші збігаються, сервер **не виконує бізнес-логіку повторно**, а негайно повертає з кешу точно збережене тіло та HTTP-статус оригінальної відповіді (`201 Created`).
3. **Збереження результату:** після завершення транзакції сервер зберігає тіло відповіді, заголовки та код статусу в таблиці ключів із часом життя (TTL) від 24 до 72 годин, переводячи ключ у статус `COMPLETED`.

Завдяки цьому механізму клієнт отримує право безпечно повторювати будь-які `POST`-запити при мережевих обривах: скільки б разів клієнт не надсилав запит із тим самим ключем `7b9e4c21...`, гроші спишуться рівно один раз.

## Наскрізні дедлайни та розмноження повторів у мікросервісних ланцюжках

У мікросервісній архітектурі один вхідний клієнтський запит часто породжує дерево вкладених викликів: Шлюз → Сервіс замовлень → Сервіс оплати → Банківський шлюз.

Якщо кожен із цих проміжних мікросервісів має незалежно налаштовану політику повторів із 3 спробами, виникає небезпечний ефект **розмноження повторів (Retry Amplification / Fan-out Explosion)**:
- Шлюз робить 3 спроби до Сервісу замовлень.
- На кожну зі спроб Сервіс замовлень робить по 3 спроби до Сервісу оплати (сумарно `3 · 3 = 9` запитів).
- Сервіс оплати робить по 3 спроби до Банківського шлюзу (сумарно `3 · 3 · 3 = 27` запитів).

Один вхідний збій призводить до множення навантаження на нижній рівень у 27 разів.

Щоб запобігти цьому, застосовують дві практики:
1. **Повтори дозволені лише на межі системи (Edge/Client Retries):** внутрішні мікросервіси не повинні сліпо повторювати виклики своїх сусідів, якщо вищий рівень уже має власний контур повторів.
2. **Контексти розподілених дедлайнів (Deadlines / Distributed Timeouts):** заголовок запиту передає абсолютний часовий дедлайн усієї операції (наприклад, заголовок `X-Request-Deadline: 1771891200` або `grpc-timeout: 2000m`). Коли Сервіс оплати отримує запит, він перевіряє, скільки мілісекунд залишилося до загального дедлайну операції клієнта. Якщо до дедлайну залишилося 50 мс, а повтор триватиме 200 мс, мікросервіс негайно відмовляється від повтору (Fail-Fast), оскільки клієнт усе одно розірве з'єднання раніше, ніж надійде відповідь.

## Клієнтські контури самозахисту: Бюджет повторів та Запобіжник

Навіть ідеально налаштований експоненційний відступ із джитером та ідемпотентними ключами не захищає систему, якщо кількість клієнтів у системі перевищує десятки тисяч, а сервіс лежить повністю й безповоротно. Якщо 50 000 клієнтів зроблять по 3 повтори, це створить 150 000 зайвих мережевих викликів.

Для запобігання надлишковим витратам клієнтських ресурсів та захисту зовнішніх сервісів застосовують два механізми самообмеження:

![Клієнтський самозахист: Бюджет повторів та Запобіжник](/root/eng/sf-web/retries-and-backoff/img/retry-budget-circuit.svg)

*Два контури захисту: Retry Budget обмежує частку повторів у загальному потоці трафіку, а Circuit Breaker миттєво відсікає звернення до непрацюючого сервісу.*

### 1. Бюджет повторів (Retry Budget)
Замість того, щоб дозволяти кожному запиту безумовно робити 3 спроби, клієнт веде глобальний облік співвідношення між первинними успішними викликами та повторами (алгоритм маркерного кошика / Token Bucket):
- Кожен успішний первинний запит (`2xx`) додає в пул невелику частку токена (наприклад, `+0.2` токена).
- Кожна повторна спроба списує з пулу `1.0` токен.
- Якщо пул порожній (частка повторів перевищила 20% від загального трафіку за останнє ковзне вікно), право на повтор блокується: запит негайно завершується помилкою після першого ж невдалого виклику.

Це гарантує, що за будь-яких масштабів аварії обсяг повторного трафіку від клієнтів ніколи не перевищить фіксованого ліміту (10–20%) від нормального потоку.

### 2. Запобіжник (Circuit Breaker)
Патерн Circuit Breaker (розмикач кола) діє як автоматичний електричний вимикач. Він має три стани:
- **`CLOSED` (Замкнено):** нормальний робочий режим. Усі запити безперешкодно проходять у мережу. Клієнт веде статистику збоїв.
- **`OPEN` (Розімкнено):** якщо частка помилок (5xx / тайм-аути) за останнє вікно перевищує критичний поріг (наприклад, 50% помилок на вибірці з 20 запитів), запобіжник розмикає коло. Усі наступні виклики до цього сервісу **миттєво зазнають невдачі локально на клієнті (Fail-Fast)** без надсилання жодного IP-пакета в мережу.
- **`HALF-OPEN` (Напіврозімкнено):** після закінчення часу остигання (наприклад, 15–30 секунд) запобіжник пропускає рівно один пробний запит. Якщо пробний запит завершився успіхом, коло повертається в стан `CLOSED`; якщо знову сталася помилка — таймер остигання перезапускається, і коло лишається в стані `OPEN`.

> ⚙️ Повний код інженерної реалізації стійкого клієнта з контуром перевірки станів Circuit Breaker, пулом токенів Retry Budget та автоматичною дедуплікацією ідемпотентних ключів наведено у [практичній реалізації промислового клієнта з бюджетом повторів та збереженням ключів ідемпотентності](root:sf-web/retries-and-backoff/proj-idempotent-retry.md).

## Спостережуваність і метрики надійності

Без детальної телеметрії система з автоматичними повторами стає «чорною скринькою», маскуючи серйозні внутрішні проблеми бекенда: користувачі бачать успішні сторінки, але час завантаження зростає вп'ятеро, бо кожен виклик проходить лише з третьої спроби.

Промисловий клієнт зобов'язаний експортувати стандартні метрики у форматі Prometheus / OpenTelemetry:
- **`http_client_requests_total{method, status, retry_attempt}`:** лічильник загальної кількості запитів із розподілом за номерами спроб (`0` — первинний, `1` — перший повтор, `2` — другий).
- **`http_client_retry_rate`:** співвідношення повторів до загального обсягу викликів. Якщо ця метрика перевищує 5%, черговий інженер отримує попередження про деградацію мережі чи бекенда.
- **`http_client_request_duration_seconds_bucket`:** гістограма сумарного часу обробки запиту з урахуванням усіх пауз відступу для точного відстеження хвостів затримок (p95, p99, p99.9).
- **`circuit_breaker_state{service_name}`:** калібрувальний індикатор поточного стану запобіжника (`0 = Closed`, `1 = Half-Open`, `2 = Open`).

## Практична конфігурація у виробничому коді

Розглянемо, як базові інваріанти повторів конфігуруються у стандартних бібліотеках та реалізуються на мовах системного програмування.

### Реалізація в екосистемі Python: urllib3 та requests

У Python еталонним інструментом керування повторами є клас `urllib3.util.Retry`, інтегрований через транспортний адаптер `HTTPAdapter` бібліотеки `requests`:

```python
import uuid
import requests
from urllib3.util import Retry
from requests.adapters import HTTPAdapter


class IdempotentHTTPAdapter(HTTPAdapter):
    """Транспортний адаптер з автоматичним додаванням Idempotency-Key."""

    def send(self, request, **kwargs):
        # Додаємо унікальний ключ для мутуючих методів, якщо він не заданий явно
        if request.method in ("POST", "PATCH", "PUT"):
            if "Idempotency-Key" not in request.headers:
                request.headers["Idempotency-Key"] = str(uuid.uuid4())
        return super().send(request, **kwargs)


def create_resilient_session() -> requests.Session:
    session = requests.Session()

    # Налаштування політики повторів:
    # total=3: максимум 3 спроби повтору
    # backoff_factor=0.5: інтервали очікування 0.5s, 1.0s, 2.0s...
    # status_forcelist: повторюємо лише тимчасові коди збоїв
    # allowed_methods: безпечні та ідемпотентні методи (POST додано під захистом Idempotency-Key)
    # respect_retry_after_header=True: суворе дотримання серверного Retry-After
    retry_strategy = Retry(
        total=3,
        backoff_factor=0.5,
        status_forcelist=[429, 500, 502, 503, 504],
        allowed_methods=frozenset(["GET", "HEAD", "PUT", "DELETE", "OPTIONS", "POST"]),
        raise_on_status=False,
        respect_retry_after_header=True
    )

    adapter = IdempotentHTTPAdapter(max_retries=retry_strategy)
    session.mount("https://", adapter)
    session.mount("http://", adapter)

    return session
```

### Системна реалізація мовами C та C++

У низькорівневих мережевих клієнтах та вбудованих системах керування повторами реалізується вручну через цикли відступу з рандомізацією та перевіркою статус-кодів.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdbool.h>
#include <unistd.h>
#include <time.h>

#define MAX_RETRIES 3
#define BASE_BACKOFF_MS 100
#define MAX_BACKOFF_MS 10000

typedef struct {
    int status_code;
    int retry_after_sec;
    char body[256];
} http_raw_response_t;

/* Генерація псевдо-UUIDv4 для ключа ідемпотентності */
void generate_idempotency_uuid(char *buf, size_t sz) {
    snprintf(buf, sz, "%04x%04x-%04x-4%03x-8%03x-%04x%04x%04x",
             rand() & 0xFFFF, rand() & 0xFFFF, rand() & 0xFFFF,
             rand() & 0x0FFF, rand() & 0x0FFF,
             rand() & 0xFFFF, rand() & 0xFFFF, rand() & 0xFFFF);
}

/* Обчислення Full Jitter: Uniform(0, min(MAX, BASE * 2^i)) */
long calculate_full_jitter_ms(int attempt, int retry_after_sec) {
    if (retry_after_sec > 0) {
        return ((long)retry_after_sec * 1000) + (rand() % 150); /* +0..150 мс джитер */
    }
    long upper_bound = BASE_BACKOFF_MS * (1L << attempt);
    if (upper_bound > MAX_BACKOFF_MS) {
        upper_bound = MAX_BACKOFF_MS;
    }
    return (rand() % (upper_bound + 1));
}

/* Симуляція відправки HTTP-пакета через сокет */
http_raw_response_t mock_send_http(const char *method, const char *url,
                                   const char *idemp_key, int attempt) {
    http_raw_response_t res;
    memset(&res, 0, sizeof(res));

    /* Імітуємо відновлення сервера на третій спробі */
    if (attempt < 2) {
        res.status_code = 503;
        res.retry_after_sec = 0;
        snprintf(res.body, sizeof(res.body), "Service Unavailable");
    } else {
        res.status_code = 201;
        res.retry_after_sec = 0;
        snprintf(res.body, sizeof(res.body), "{\"status\":\"Created\",\"key\":\"%s\"}", idemp_key);
    }
    return res;
}

int execute_http_with_retry(const char *url, const char *payload, http_raw_response_t *out_res) {
    char idemp_key[40];
    generate_idempotency_uuid(idemp_key, sizeof(idemp_key));

    for (int attempt = 0; attempt <= MAX_RETRIES; ++attempt) {
        *out_res = mock_send_http("POST", url, idemp_key, attempt);

        if (out_res->status_code >= 200 && out_res->status_code < 300) {
            return 0; /* Успіх */
        }

        bool is_transient = (out_res->status_code == 429 ||
                             out_res->status_code == 502 ||
                             out_res->status_code == 503 ||
                             out_res->status_code == 504);

        if (!is_transient || attempt == MAX_RETRIES) {
            return -1; /* Фатальний код або вичерпано ліміт спроб */
        }

        long delay_ms = calculate_full_jitter_ms(attempt, out_res->retry_after_sec);
        usleep((useconds_t)(delay_ms * 1000));
    }
    return -1;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <chrono>
#include <random>
#include <thread>
#include <expected>
#include <format>
#include <algorithm>

struct HttpResponsePayload {
    int status_code{0};
    int retry_after_sec{0};
    std::string response_body;
};

enum class ClientFailure {
    FatalStatus,
    TransientLimitReached
};

class ResilientHttpClientWrapper {
public:
    struct Options {
        int max_attempts = 3;
        std::chrono::milliseconds base_delay{100};
        std::chrono::milliseconds max_delay{10000};
    };

    explicit ResilientHttpClientWrapper(Options opt = {})
        : opt_(opt), rng_(std::random_device{}()) {}

    std::expected<HttpResponsePayload, ClientFailure> post(std::string_view url, std::string_view body) {
        const std::string idempotency_key = create_uuid_v4();

        for (int attempt = 0; attempt <= opt_.max_attempts; ++attempt) {
            HttpResponsePayload resp = mock_transport_send("POST", url, idempotency_key, body, attempt);

            if (resp.status_code >= 200 && resp.status_code < 300) {
                return resp;
            }

            const bool is_transient = (resp.status_code == 429 ||
                                       resp.status_code == 502 ||
                                       resp.status_code == 503 ||
                                       resp.status_code == 504);

            if (!is_transient || attempt == opt_.max_attempts) {
                return std::unexpected(ClientFailure::TransientLimitReached);
            }

            const auto pause = compute_full_jitter_delay(attempt, resp.retry_after_sec);
            std::this_thread::sleep_for(pause);
        }

        return std::unexpected(ClientFailure::TransientLimitReached);
    }

private:
    Options opt_;
    std::mt19937 rng_;

    std::chrono::milliseconds compute_full_jitter_delay(int attempt, int retry_after_sec) {
        if (retry_after_sec > 0) {
            std::uniform_int_distribution<int> jitter(0, 150);
            return std::chrono::seconds(retry_after_sec) + std::chrono::milliseconds(jitter(rng_));
        }

        const auto exponential_limit = opt_.base_delay.count() * (1LL << attempt);
        const auto capped_limit = std::min(static_cast<long long>(opt_.max_delay.count()), exponential_limit);

        std::uniform_int_distribution<long long> dist(0, capped_limit);
        return std::chrono::milliseconds(dist(rng_));
    }

    std::string create_uuid_v4() {
        std::uniform_int_distribution<uint32_t> dist(0, 0xFFFFFFFF);
        return std::format("{:08x}-{:04x}-4{:03x}-a{:03x}-{:08x}",
                           dist(rng_), dist(rng_) & 0xFFFF,
                           dist(rng_) & 0x0FFF, dist(rng_) & 0x0FFF, dist(rng_));
    }

    HttpResponsePayload mock_transport_send(std::string_view method, std::string_view url,
                                            std::string_view idemp_key, std::string_view body, int attempt) {
        if (attempt < 2) {
            return HttpResponsePayload{.status_code = 503, .retry_after_sec = 0, .response_body = "Unavailable"};
        }
        return HttpResponsePayload{
            .status_code = 201,
            .retry_after_sec = 0,
            .response_body = std::format(R"({{"status":"Created","idempotency_key":"{}"}})", idemp_key)
        };
    }
};
```

## Зведена матриця інженерних рішень

| Сценарій / Стан | Статус-код / Помилка | Дозволеність Retry | Алгоритм відступу | Вимога до ідемпотентності |
|---|---|---|---|---|
| **Клієнтська помилка валідації** | `400`, `422` | **Заборонено** | Відсутній (Fail-Fast) | Не застосовується |
| **Помилка автентифікації** | `401`, `403` | **Заборонено** | Оновлення токена без retry | Не застосовується |
| **Перевищення квоти швидкості** | `429 Too Many Requests` | **Дозволено** | Суворий `Retry-After` + Jitter | Обов'язкова для POST |
| **Перевантаження / рестарт** | `503 Service Unavailable` | **Дозволено** | Full / Decorrelated Jitter | Обов'язкова для POST |
| **Шлюзовий тайм-аут** | `502`, `504` | **Дозволено** | Експоненційний + Full Jitter | Обов'язкова для POST |
| **Мережевий розрив сокета** | `ECONNRESET`, `ETIMEDOUT` | **Дозволено** | Експоненційний + Full Jitter | Заголовок `Idempotency-Key` |
| **Масова аварія інфраструктури** | Серійні збої (>50%) | **Блокується** | Розмикання Circuit Breaker | Захист пулу потоків |

Стійкість розподіленої системи ніколи не зводиться до сліпого збільшення кількості повторів. Надійний мережевий шар будується на усвідомленому балансі: швидке розпізнавання фатальних помилок, захист бекенда через експоненційний відступ з випадковим тремтінням, суворе дотримання вказівок сервера в заголовках `Retry-After`, гарантія атомарності мутуючих операцій через ключі ідемпотентності, передача наскрізних дедлайнів по ланцюжку мікросервісів та обмеження сумарного трафіку повторів за допомогою клієнтських запобіжників і бюджетів.
