# 📋 Інтерфейс валідації сертифікатів: OpenSSL та ssl.SSLContext

Під час встановлення захищеного з'єднання клієнтський стек TLS повинен виконати сувору криптографічну перевірку віддаленого вузла. Усі сучасні бібліотеки та високорівневі мови програмування спираються або безпосередньо на інтерфейс OpenSSL/BoringSSL, або на власні абстракції над системними сховищами сертифікатів.

У цьому довіднику зведено сигнатури викликів, життєвий цикл об'єктів, конфігураційні прапорці валідації, роботу черги помилок OpenSSL, взаємодію з відновленням сесій, механізм ALPN та таблицю числових діагностичних кодів стандарту X.509.

## Модель пам'яті та життєвий цикл контексту в OpenSSL

Архітектура OpenSSL чітко розмежовує довгоживучу глобальну конфігурацію та короткоживучий стан окремого мережевого з'єднання:

1. **Контекст `SSL_CTX` (Factory / Shared State):** створюється один раз під час запуску програми за допомогою виклику `SSL_CTX_new()`. Він містить бандли довірених кореневих сертифікатів, списки відкликання, параметри верифікації, налаштовані клієнтські ключі mTLS та кеш TLS-сесій. Об'єкт `SSL_CTX` є потокобезпечним для операцій читання: один екземпляр контексту безпечно розділяється між сотнями робочих потоків веб-сервера чи HTTP-клієнта.
2. **Сесія `SSL` (Per-Connection State):** створюється для кожного нового TCP-сокета викликом `SSL_new(ctx)`. Цей об'єкт інкапсулює стан поточного рукостискання, симетричні сесійні ключі, буфери шифрування та копію параметрів перевірки. Об'єкт `SSL` не є потокобезпечним і повинен обслуговуватися виключно одним потоком одночасно.
3. **Управління пам'яттю та підрахунок посилань:** більшість структур OpenSSL (`X509`, `EVP_PKEY`, `SSL_CTX`, `SSL`) використовують внутрішній підрахунок посилань. Функції з суфіксом `_free` (`SSL_CTX_free`, `X509_free`) зменшують лічильник посилань на одиницю і звільняють пам'ять лише тоді, коли він досягає нуля. Завантаження сертифікатів через `SSL_CTX_use_certificate` збільшує лічильник посилань, тоді як функції `_file` самостійно створюють та очищають проміжні структури.

## Зіставлення сигнатур: C (OpenSSL) проти Python (ssl)

Нижче наведено зіставлення основних операцій конфігурації TLS-контексту в бібліотеці OpenSSL API та стандартному модулі Python `ssl`.

| Операція | OpenSSL C API | Python `ssl.SSLContext` | Призначення та поведінка |
|---|---|---|---|
| Створення контексту | `SSL_CTX_new(TLS_client_method())` | `ssl.create_default_context()` | Ініціалізація структури параметрів клієнта з безпечними системними дефолтами. |
| Режим верифікації | `SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL)` | `ctx.verify_mode = ssl.CERT_REQUIRED` | Вимога обов'язкової наявності та валідації сертифіката сервера. Забороняє анонімні з'єднання. |
| Перевірка імені хоста | `X509_VERIFY_PARAM_set1_host(param, "api.com", 0)` | `ctx.check_hostname = True` | Зіставлення запитуваного домену з розширенням SAN кінцевого сертифіката за правилами RFC 6125. |
| Завантаження CA | `SSL_CTX_load_verify_locations(ctx, "ca.pem", NULL)` | `ctx.load_verify_locations(cafile="ca.pem")` | Додавання власного файлу або директорії довірених центрів сертифікації до списку довіри. |
| Системні CA | `SSL_CTX_set_default_verify_paths(ctx)` | `ctx.load_default_certs()` | Підключення системного сховища сертифікатів операційної системи (наприклад, `/etc/ssl/certs`). |
| Клієнтський сертифікат (mTLS) | `SSL_CTX_use_certificate_chain_file(ctx, "client.crt")` | `ctx.load_cert_chain("client.crt", "client.key")` | Завантаження відкритого сертифіката та ланцюжка проміжних центрів для взаємної автентифікації. |
| Приватний ключ клієнта | `SSL_CTX_use_PrivateKey_file(ctx, "client.key", SSL_FILETYPE_PEM)` | Входить у виклик `ctx.load_cert_chain()` | Завантаження та обов'язкова перевірка відповідності приватного ключа сертифікату клієнта. |
| Мінімальна версія TLS | `SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION)` | `ctx.minimum_version = ssl.TLSVersion.TLSv1_2` | Заборона застарілих та вразливих версій протоколу SSLv3, TLS 1.0 та TLS 1.1. |
| Індикація хоста (SNI) | `SSL_set_tlsext_host_name(ssl, "api.com")` | Автоматично при виклику `wrap_socket(..., server_hostname="api.com")` | Передача імені домену в розширенні ClientHello для вибору віртуального хоста на сервері. |
| Узгодження ALPN | `SSL_CTX_set_alpn_protos(ctx, "\x02h2\x08http/1.1", 12)` | `ctx.set_alpn_protocols(['h2', 'http/1.1'])` | Узгодження протоколу прикладного рівня (HTTP/2 проти HTTP/1.1) безпосередньо у фазі handshake. |
| Отримання сертифіката | `SSL_get_peer_certificate(ssl)` | `sslobj.getpeercert()` | Отримання розібраної структури сертифіката сервера після завершення фази рукостискання. |
| Результат валідації | `SSL_get_verify_result(ssl)` | `sslobj.getpeercert()` викидає `SSLCertVerificationError` | Отримання числового коду результату валідації ланцюжка довіри X.509. |

## Налаштування параметрів перевірки через X509_VERIFY_PARAM

Бібліотека OpenSSL надає структуру `X509_VERIFY_PARAM` для детального контролю над поведінкою алгоритму побудови та перевірки шляху сертифікатів. Вона отримується з контексту через `SSL_CTX_get0_param(ctx)` або асоціюється з окремим сокетом через `SSL_set1_param(ssl, vpm)`.

Прапорці поведінки встановлюються функцією `X509_VERIFY_PARAM_set_flags(param, flags)`:

| Прапорець | Опис поведінки та інженерні наслідки |
|---|---|
| `X509_CHECK_FLAG_NO_WILDCARDS` | Повністю забороняє зіставлення за маскою `*.domain.com`. Вимагає виключно точного посимвольного збігу доменного імені в розширенні SAN. |
| `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` | Забороняє часткові підстановки на кшталт `api-*.example.com`. Дозволяє лише канонічні шаблони виду `*.example.com`, де зірочка є єдиним символом крайнього лівого ярлика. |
| `X509_CHECK_FLAG_MULTI_LABEL_WILDCARDS` | Дозволяє підстановці покривати кілька рівнів домену (наприклад, `*.example.com` підійде для `a.b.example.com`). Категорично не рекомендується через ризики безпеки. |
| `X509_CHECK_FLAG_ALWAYS_CHECK_SUBJECT` | Змушує перевіряти застаріле поле `Subject Common Name` навіть тоді, коли розширення SAN присутнє в сертифікаті. |
| `X509_CHECK_FLAG_NEVER_CHECK_SUBJECT` | Суворо вимагає наявності розширення `Subject Alternative Name` (SAN) і повністю відкидає перевірку поля `Subject CN` (сучасний стандарт безпеки RFC 6125). |
| `X509_V_FLAG_CRL_CHECK` | Вмикає перевірку списків відкликання (CRL) для кінцевого сертифіката сервера. Якщо CRL не знайдено, з'єднання буде відхилено. |
| `X509_V_FLAG_CRL_CHECK_ALL` | Вимагає наявності дійсних CRL для абсолютно всіх ланцюжків ієрархії, включаючи проміжні центри сертифікації. |
## Механізм користувацьких функцій зворотного виклику (verify_callback)

Розробник може перехопити процес покрокової перевірки кожного сертифіката в ланцюжку за допомогою власної функції зворотного виклику:

:::tabs
```c
int custom_verify_callback(int preverify_ok, X509_STORE_CTX *x509_ctx) {
    if (!preverify_ok) {
        int err = X509_STORE_CTX_get_error(x509_ctx);
        int depth = X509_STORE_CTX_get_error_depth(x509_ctx);
        fprintf(stderr, "Помилка валідації на глибині %d: %s\n",
                depth, X509_verify_cert_error_string(err));
    }
    return preverify_ok;
}
```
```cpp
#include <iostream>
#include <string_view>
#include <openssl/x509_vfy.h>

int custom_verify_callback(int preverify_ok, X509_STORE_CTX *x509_ctx) noexcept {
    if (!preverify_ok) {
        const int err = X509_STORE_CTX_get_error(x509_ctx);
        const int depth = X509_STORE_CTX_get_error_depth(x509_ctx);
        const std::string_view err_str = X509_verify_cert_error_string(err);
        std::cerr << "[!] Помилка валідації на глибині " << depth << ": " << err_str << "\n";
    }
    return preverify_ok;
}
```
:::

Ця функція викликається бібліотекою OpenSSL для кожного сертифіката в ланцюжку знизу вгору: спочатку для кореневого CA (найбільша глибина, наприклад `depth = 2`), потім для проміжних центрів (`depth = 1`), і врешті для кінцевого сертифіката сервера (`depth = 0`).

Параметр `preverify_ok` сигналізує про результат стандартної внутрішньої перевірки OpenSSL для поточного сертифіката: `1` означає успіх, `0` — виявлення помилки (закінчився термін дії, невірний підпис тощо).

Через контекст `x509_ctx` доступні службові функції інспекції:
- `X509_STORE_CTX_get_current_cert(x509_ctx)` — повертає вказівник на сертифікат `X509*`, що перевіряється в даний момент.
- `X509_STORE_CTX_get_error_depth(x509_ctx)` — повертає глибину сертифіката в ланцюжку.
- `X509_STORE_CTX_get_error(x509_ctx)` — повертає код поточної помилки `X509_V_ERR_*`.
- `X509_STORE_CTX_set_error(x509_ctx, err)` — дозволяє встановити власну помилку валідації.

> ⚠️ **Головна пастка безпеки:** якщо функція зворотного виклику завжди повертає `1` (наприклад, для придушення попереджень під час налагодження), вона повністю нівелює всю перевірку OpenSSL. Навіть підроблений або прострочений сертифікат буде прийнято як дійсний. Функція повинна повертати `0`, якщо `preverify_ok == 0`, хіба що додаток реалізує усвідомлену логіку винятків для конкретних довірених відбитків ключів.

## Відновлення сесії (Session Resumption) та валідація

У протоколах TLS 1.2 та TLS 1.3 для прискорення повторних з'єднань використовується механізм відновлення сесії через Session ID або безпам'ятні зашифровані сесійні квитки (англ. *Session Tickets*, RFC 5077 / RFC 8446 PSK).

Інженерна особливість полягає в тому, що під час відновлення сесії **повна процедура валідації сертифіката X.509 не повторюється**. Клієнт і сервер використовують узгоджений раніше майстер-секрет (Master Secret або Resumption PSK), пропускаючи фази надсилання сертифікатів та перевірки ланцюжка. Це економить час обчислень асиметричної криптографії та скорочує час встановлення з'єднання до 0-RTT або 1-RTT. Проте, якщо сертифікат сервера було відкликано вже після встановлення початкової сесії, клієнт дізнається про це лише після закінчення терміну дії сесійного квитка (зазвичай від 2 до 24 годин).

Для керування кешем сесій в OpenSSL використовуються функції:
- `SSL_CTX_set_session_cache_mode(ctx, SSL_SESS_CACHE_CLIENT)` — вмикає збереження сесій на боці клієнта.
- `SSL_get1_session(ssl)` — витягує об'єкт сесії `SSL_SESSION*` для повторного використання у виклику `SSL_set_session(ssl, session)`.

## Робота з чергою помилок OpenSSL

Бібліотека OpenSSL зберігає діагностичні повідомлення в потоко-локальній кільцевій черзі помилок. Кожна невдала криптографічна операція додає новий запис у кінець черги.

1. **Отримання помилки:** виклик `ERR_get_error()` витягує найстаріший 32-бітний код помилки з черги та видаляє його. Для форматування коду в текстовий рядок використовується `ERR_error_string(code, buf)` або `ERR_error_string_n(code, buf, len)`.
2. **Очищення черги:** перед початком критичних операцій (таких як `SSL_connect()` або `SSL_read()`) необхідно викликати `ERR_clear_error()`. Якщо цього не зробити, застаріла помилка від попередньої операції введення-виведення може бути помилково інтерпретована як збій поточного рукостискання.

## Таблиця діагностичних кодів валідації (X509_V_ERR)

Коли виклик `SSL_do_handshake()` повертає від'ємне значення через збій валідації, точна причина з'ясовується викликом `SSL_get_verify_result(ssl)`. Нижче наведено перелік основних констант, їх числові значення та інженерні рекомендації щодо усунення несправностей.

| Константа коду | Число | Текстове значення в OpenSSL | Причина виникнення та інженерні кроки розв'язання |
|---|---|---|---|
| `X509_V_OK` | 0 | `ok` | Перевірка успішна, ланцюг довіри повністю підтверджено. |
| `X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT` | 2 | `unable to get issuer certificate` | Клієнт не зміг знайти сертифікат видавця для побудови ланцюга. Перевірте наявність кореневого CA в локальному Trust Store або додайте його через `SSL_CTX_load_verify_locations`. |
| `X509_V_ERR_UNABLE_TO_GET_CRL` | 3 | `unable to get certificate CRL` | Увімкнено обов'язкову перевірку CRL, але список відкликання не вдалося завантажити чи розібрати. |
| `X509_V_ERR_UNABLE_TO_DECRYPT_CERT_SIGNATURE` | 4 | `unable to decrypt certificate's signature` | Не вдалося розшифрувати цифровий підпис відкритим ключем видавця. Свідчить про пошкодження файлу або використання невідповідного відкритого ключа. |
| `X509_V_ERR_CERT_SIGNATURE_FAILURE` | 7 | `certificate signature failure` | Обчислений SHA-256 геш від секції `tbsCertificate` не збігається зі значенням підпису. Сертифікат було модифіковано, підроблено або пошкоджено під час передачі. |
| `X509_V_ERR_CERT_NOT_YET_VALID` | 9 | `certificate is not yet valid` | Поточний системний час клієнта передує даті `notBefore`. Перевірте синхронізацію системного годинника через службу NTP. |
| `X509_V_ERR_CERT_HAS_EXPIRED` | 10 | `certificate has expired` | Поточний час перевищує дату `notAfter`. Сертифікат застарів і повинен бути оновлений власником сервера. |
| `X509_V_ERR_DEPTH_ZERO_SELF_SIGNED_CERT` | 18 | `self signed certificate` | Кінцевий сертифікат сервера є самопідписаним і відсутній у списку довірених коренів клієнта. |
| `X509_V_ERR_SELF_SIGNED_CERT_IN_CHAIN` | 19 | `self signed certificate in certificate chain` | Ланцюжок містить самопідписаний проміжний сертифікат, який не входить до локального сховища довіри. |
| `X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT_LOCALLY` | 20 | `unable to get local issuer certificate` | Найпоширеніша помилка в Інтернеті: сервер надіслав лише свій кінцевий сертифікат, забувши передати бандл проміжних сертифікатів (Intermediate CA). Налаштуйте веб-сервер на надсилання повного ланцюжка (fullchain). |
| `X509_V_ERR_CERT_REVOKED` | 23 | `certificate revoked` | Сертифікат було офіційно відкликано центром сертифікації через компрометацію приватного ключа. |
| `X509_V_ERR_INVALID_CA` | 24 | `invalid CA certificate` | Сертифікат, що виступає видавцем у ланцюжку, не містить розширення `Basic Constraints: CA: TRUE` або не має прапорця `Key Usage: keyCertSign`. |
| `X509_V_ERR_PATH_LENGTH_EXCEEDED` | 25 | `path length constraint exceeded` | Довжина ланцюжка проміжних центрів перевищує ліміт `pathLenConstraint`, заданий вищим центром сертифікації. |
| `X509_V_ERR_INVALID_PURPOSE` | 26 | `unsupported certificate purpose` | Сертифікат сервера не містить `Extended Key Usage: serverAuth`, або сертифікат клієнта для mTLS не містить `clientAuth`. |
| `X509_V_ERR_HOSTNAME_MISMATCH` | 62 | `Hostname mismatch` | Запитуване доменне ім'я з URL не збігається з жодним записом у розширенні `Subject Alternative Name` (SAN). |

## Практична діагностика через утиліти командного рядка

Для швидкої ізоляції проблем конфігурації TLS на сервері або клієнті використовують утиліту OpenSSL CLI `s_client`.

```bash
# 1. Повна перевірка з показом усіх сертифікатів ланцюжка та індикацією SNI
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts

# 2. Тестування з використанням власного локального CA бандла
openssl s_client -connect api.internal.corp:443 -servername api.internal.corp -CAfile /etc/ssl/custom-ca.pem

# 3. Тестування mTLS з надсиланням сертифіката та приватного ключа клієнта
openssl s_client -connect secure-gw.bank.com:8443 \
    -servername secure-gw.bank.com \
    -CAfile /etc/ssl/ca-bundle.pem \
    -cert client.crt \
    -key client.key
```

Під час аналізу результатів звертайте увагу на рядок `Verify return code`: код `0 (ok)` підтверджує абсолютну валідність ланцюжка, тоді як будь-яке інше числове значення відповідає конкретному рядку в наведеній вище таблиці кодів помилок.
