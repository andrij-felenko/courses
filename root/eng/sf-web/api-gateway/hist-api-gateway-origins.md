# 📜 Від зворотного проксі та важких корпоративних шин до API-шлюзів

Наприкінці 1990-х років архітектура всесвітнього павутиння була переважно монолітною. Вебсайти будувалися як цілісні програми на Perl, C чи PHP, що генерували статичний HTML через стандартний шлюзовий інтерфейс CGI (англ. *Common Gateway Interface*). Уся взаємодія користувача з сервером зводилася до завантаження HTML-сторінок та відправки простих форм. Єдиним посередником між публічною мережею та вебсервером виступав звичайний зворотний проксі-сервер (англ. *reverse proxy*) — Apache з модулем `mod_proxy` або спеціалізовані апаратні прискорювачі на кшталт Squid. Їхня роль була суто транспортною: закешувати незмінні статичні файли (зображення, стилі), розвантажити повільні клієнтські канали та завершити навантаження шифрування SSL. Зворотний проксі нічого не знав про внутрішній устрій програми; для нього за спиною існував лише один великий серверний процес.

На початку 2000-х років великі корпорації зіткнулися з іншою фундаментальною проблемою — інтеграційним хаосом. У межах одного банку, авіакомпанії чи телекомунікаційного гіганта одночасно працювали десятки несумісних систем: мейнфрейми IBM на COBOL, реляційні бази даних Oracle, ERP-системи SAP та нові застосунки на Java EE. Раніші спроби уніфікації через бінарні протоколи віддаленого виклику процедур (CORBA, Microsoft DCOM, Java RMI) зазнали невдачі на відкритому інтернет-периметрі: вони вимагали жорсткої прив'язки до компіляторів, пробивали фаєрволи довільними динамічними TCP-портами та не витримували гетерогенного мережевого середовища.

З'явилася концепція сервісно-орієнтованої архітектури (англ. *Service-Oriented Architecture*, SOA). Щоб зв'язати ці несумісні світи, виробники корпоративного програмного забезпечення (IBM WebSphere, TIBCO, Oracle Service Bus, BEA AquaLogic, MuleSoft) винайшли корпоративну сервісну шину — ESB (англ. *Enterprise Service Bus*).

Шина ESB пропонувала універсальне вирішення інтеграції на базі протоколу SOAP та важкого сімейства стандартів WS-* (WS-Security, WS-Addressing, WS-ReliableMessaging, WS-AtomicTransaction). Усі дані пакувалися в багатослівний формат XML. Шина брала на себе майже всю складність координації: вона виконувала динамічну трансформацію схем даних за допомогою XSLT-шаблонів, маршрутизувала пакети на основі глибокого аналізу вмісту (Content-Based Routing), координувала розподілені двофазні транзакції (Two-Phase Commit) та оркеструвала складні тривалі бізнес-процеси за стандартом BPEL (англ. *Business Process Execution Language*).

До 2010 року ця парадигма зайшла в глухий кут. На практиці корпоративна шина перетворилася на класичний антипатерн «надрозумної труби з дурними кінцевими вузлами» (англ. *smart pipes, dumb endpoints*). Замість обіцяної гнучкості компанії отримали колосальне організаційне та технічне вузьке місце. Будь-яка зміна в інтерфейсі мікросервісу вимагала залучення спеціалізованої команди інтеграторів, яка місяцями переписувала складні XSLT-перетворення на центральній шині. Парсинг велетенських XML-дерев вимагав гігабайтів оперативної пам'яті та спалював процесорні цикли, призводячи до величезних затримок обробки викликів. А головне — збій у скрипті одного другорядного модуля шини призводив до падіння інтеграційного контуру всієї корпорації.

Переломним моментом став вибух популярності мобільних смартфонів (iPhone, Android) та масовий перехід провідних інтернет-компаній від монолітів до мікросервісів на початку 2010-х років. Коли у 2011–2012 роках компанія Netflix почала переносити свій сервіс потокового відео з фізичних дата-центрів у хмару AWS, розбиваючи монолітний бекенд на сотні незалежних дрібних мікросервісів, інженери виявили, що прямий доступ мобільних клієнтів до внутрішніх сервісів є технічно неможливим.

Мобільні мережі 3G та раннього 4G страждали від високої затримки сигналу (RTT 100–200 мс). Клієнтська програма, якій для відмальовки головного екрана потрібно було зробити 10–15 послідовних викликів до різних сервісів, завантажувалася неприпустимо довго. До того ж кожен реліз нового мобільного інтерфейсу змушував змінювати контракти бекенда, а старі версії застосунків у мільйонів користувачів неможливо було оновити одномоментно. Повертатися до важких, повільних і дорогих ESB компанія не збиралася.

У 2012 році Netflix представила та опублікувала у відкритому доступі проєкт **Zuul 1** — перший спеціалізований API-шлюз мікросервісної епохи. Zuul 1 працював на базі Java Servlet API і запропонував гранично просту та модульну архітектуру: послідовний ланцюжок динамічних фільтрів (Pre-filters для автентифікації та збору метрик, Routing-filters для пересилання трафіку, Post-filters для модифікації заголовків та Error-filters для перехоплення винятків). Фільтри писалися динамічною мовою Groovy і могли змінюватися прямо на льоту без перезапуску процесу. Zuul повністю відкинув XML і WS-* стандарти на користь легкого протоколу HTTP та формату JSON, повернувшись до канонічного принципу розподіленого дизайну: «Розумні кінцеві вузли, прості канали зв'язку» (англ. *smart endpoints, dumb pipes*).

У 2014–2015 роках компанія Mashape (пізніше Kong Inc.) представила шлюз **Kong**. На відміну від Java-орієнтованого стека Netflix, Kong було побудовано поверх надшвидкого C-вебсервера Nginx та середовища виконання Lua (OpenResty). Kong зробив ставку на субмілісекундну затримку та плагінну екосистему: автентифікація JWT/OAuth2, захист від перевантаження Rate Limiting через швидке сховище Redis, перетворення заголовків та збір аналітики підключалися як декларативні модулі з мінімальними накладними витратами на пам'ять.

Проте в середині 2010-х років проявилася фундаментальна проблема архітектури Zuul 1: блокуюча модель вводу-виводу (потік ОС на кожен клієнтський запит, *thread-per-request*). Коли сотні тисяч мобільних клієнтів тримали відкриті повільні TCP-з'єднання, у шлюзу закінчувалися пули потоків, а пам'ять вичерпувалася під стеки потоків. Це змусило Netflix повністю переписати шлюз на неблокуючий асинхронний стек Netty — так у 2018 році з'явився **Zuul 2**.

Того ж часу, у 2016 році, Метт Кляйн та команда інженерів компанії Lyft представили **Envoy** — новий L4/L7 проксі-сервер, написаний на сучасному C++ з нуля для високодинамічних хмарних середовищ. Lyft зіткнулася з проблемою поліглотного мікросервісного середовища (мішанина Python, Go, Java, C++), де кожна мова мала власну ненадійну реалізацію HTTP-клієнтів, ретраїв та метрик. Envoy створювався як єдиний мережевий шар даних (Data Plane), що виносив усю мережеву складність за межі процесу застосунку.

Envoy поєднав екстремально швидкий подієвий неблокуючий цикл обробки (`epoll`), детерміноване ручне керування пам'яттю без пауз збирача сміття та революційну систему динамічного конфігурування без перезавантаження процесу через gRPC-протокол (xDS API: LDS, RDS, CDS, EDS). Переданий до фундації CNCF (Cloud Native Computing Foundation) у 2017 році, Envoy став де-факто стандартом індустрії та ядром більшості сучасних шлюзів нового покоління (Envoy Gateway, Gloo, Emissary-ingress).

Паралельно розвивалися інші спеціалізовані рішення: у 2016 році компанія Containous створила **Traefik** на мові Go, сфокусувавшись на автоматичному виявленні мікросервісів у Docker та Kubernetes без ручного написання конфігурацій. У 2019 році з'явився **Apache APISIX**, який переосмислив досвід Kong, запропонувавши динамічну площину керування на базі сховища etcd замість реляційних баз даних.

З масовим переходом індустрії на контейнерну оркестрацію в Kubernetes (2018–2024 роки) еволюція шлюзів досягла повної стандартизації. Спочатку екосистема використовувала простий контролер Ingress, але його функціональності бракувало для тонкого L7-маршрутизування, канаркових релізів та багатоорендності. Консорціум Kubernetes SIG-Network розробив **Gateway API** — багатошаровий відкритий стандарт декларативного керування шлюзами, який остаточно закріпив розподіл обов'язків між інфраструктурними операторами та розробниками мікросервісів.

Так за двадцять п'ять років еволюція вхідного посередника пройшла повне діалектичне коло: від простого кешувального проксі для статичних сторінок через перевантажені корпоративні моноліти шин до сучасного високоефективного, асинхронного та декларативно керованого шлюзу на периметрі розподілених систем.
