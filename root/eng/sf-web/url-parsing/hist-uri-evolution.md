# 📜 Від універсального ідентифікатора до живого стандарту: еволюція URI, URL та WHATWG

Потреба в універсальному способі вказувати на будь-який документ у розподіленій комп'ютерній мережі виникла одночасно з концепцією Всесвітньої павутини (World Wide Web). Коли Тім Бернерс-Лі (*Tim Berners-Lee*) у 1989–1990 роках створював перші прототипи веб-сервера й браузера в ЦЕРН (CERN — Європейська організація з ядерних досліджень), головним бар'єром була несумісність протоколів: файли лежали на FTP-серверах, новини передавалися через NNTP, локальні документи відкривалися через системні шляхи Unix чи VMS, а доступ до баз даних здійснювався через telnet. Кожна система мала власні правила адресації, чутливість до регістру та заборонені символи.

У червні 1994 року Тім Бернерс-Лі опублікував RFC 1630 — перший інформаційний документ IETF під назвою *«Universal Resource Identifiers in WWW»*. У ньому було сформульовано фундаментальний принцип: адреса повинна складатися з префікса схеми доступу (наприклад, `http:`, `ftp:`, `mailto:`), за яким слідує специфічна для цієї схеми частина. Початкове слово «Universal» (універсальний) підкреслювало намір об'єднати всі наявні мережеві протоколи під одним синтаксичним дахом.

## Філософський розкол: URI, URL чи URN?

У середині 1990-х років у робочій групі IETF спалахнула академічна дискусія щодо сутності адрес. Інженери розділилися на два табори:

1. **Прихильники локації (URL — Uniform Resource Locator):** стверджували, що ідентифікатор повинен прямо вказувати первинний механізм доступу та мережеве місце розташування ресурсу (сервер і шлях). Якщо файл перемістили на інший сервер, URL змінюється.
2. **Прихильники постійного імені (URN — Uniform Resource Name):** наполягали, що ресурс повинен мати вічне, глобально унікальне ім'я, незалежне від поточного сервера чи протоколу (наприклад, `urn:isbn:0-486-27557-4` для книжки). Спеціальна розподілена служба каталогів мала розв'язувати URN у поточну адресу під час запиту.

Компромісом став парасольковий термін **URI (Uniform Resource Identifier)**, закріплений у листопаді 1994 року в RFC 1738 (*«Uniform Resource Locators»*) та згодом у RFC 2396 (серпень 1998 року, автори Тім Бернерс-Лі, Рой Філдінг і Ларрі Мазінтер). Формула проголошувала: URI — це загальний рід, а URL та URN — його видові прояви. URL позначає ресурс через спосіб його знаходження, тоді як URN дає ресурсу ім'я без прив'язки до локації.

У практичній розробці URN не набули масового поширення через брак глобальної децентралізованої інфраструктури розв'язання імен. Весь інтернет фактично побудований на URL, хоча в інженерній літературі та специфікаціях W3C термін URI продовжував домінувати як суворіше математичне позначення синтаксису.

## Канонізація синтаксису: RFC 3986 Роя Філдінга

У січні 2005 року IETF затвердив **RFC 3986** (*«Uniform Resource Identifier (URI): Generic Syntax»*), який став вершиною класичної формалізації веб-адрес. Його головний автор — Рой Філдінг (*Roy Fielding*), творець архітектурного стилю REST і співавтор протоколу HTTP.

RFC 3986 навів суворий математичний порядок у хаосі попередніх чернеток:
- Зафіксував 5-компонентну модель (`scheme`, `authority`, `path`, `query`, `fragment`) через розширену форму Бекуса — Наура (ABNF).
- Чітко розділив набір символів ASCII на **незарезервовані** (unreserved: літери, цифри, `-`, `.`, `_`, `~`) та **зарезервовані** (reserved), розділені на головні роздільники (*gen-delims*: `:`, `/`, `?`, `#`, `[`, `]`, `@`) і допоміжні (*sub-delims*: `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`).
- Стандартизував кодування IPv6-адрес у квадратних дужках `[2001:db8::1]`, розв'язавши конфлікт двокрапок у шістнадцяткових адресах із двокрапкою номера порту.
- Описав детермінований алгоритм нормалізації та усунення крапкових сегментів шляху `remove_dot_segments`.

RFC 3986 залишається фундаментальним стандартом для протоколів прикладного рівня, бекенд-серверів, шлюзів, проксі та мов програмування загального призначення.

## Бунт браузерів: створення WHATWG URL Living Standard

Попри бездоганну математичну красу RFC 3986, у 2010-х роках виявилася глибока прірва між формальною специфікацією IETF та поведінкою реальних веб-браузерів.

RFC 3986 був **дескриптивною граматикою**: він описував, які рядки є валідними URI, і вимагав відхиляти некоректні вхідні дані. Але реальні користувачі вводили в адресний рядок браузера невалідні конструкції:
- Зворотні скісні риски у шляху: `http://example.com\path\to\file` (браузери Windows традиційно перетворювали `\` на `/`).
- Некодовані пробіли або кириличні літери прямо в адресному рядку.
- Нестандартні шістнадцяткові чи вісімкові IP-адреси (`http://0177.0.0.1` або `http://2130706433` замість `127.0.0.1`).
- Відсутність схеми або неповні відносні адреси.

Кожен браузер (Internet Explorer, Firefox, Chrome, Safari) мав власну евристику відновлення після помилок. Якщо сайт працював у Chrome через специфічний автовиправний парсинг, але ламався у Firefox, розробники звинувачували Firefox.

Щоб подолати фрагментацію, група **WHATWG** (Web Hypertext Application Technology Working Group) під керівництвом Анне ван Кестерена (*Anne van Kesteren*) розробила **WHATWG URL Living Standard**.

Замість декларативної граматики ABNF стандарт WHATWG побудовано як **імперативний кінцевий автомат (State Machine)**. Він покроково визначає, що саме повинен робити рушій із кожним байтом вхідного рядка, як нормалізувати порти для «спеціальних схем» (наприклад, автоматично відкидати порт 80 для `http:` або 443 для `https:`), як розв'язувати кодування хостів IDN (Internationalized Domain Names) у Punycode, і як заповнювати відсутні компоненти.

Сьогодні стандарти співіснують:
- **WHATWG URL API** (об'єкт `window.URL` та `URLSearchParams` у JavaScript/Node.js/браузерах) керує клієнтським світом веб-додатків.
- **RFC 3986** є базою для мережевих серверів (Nginx, Envoy, Apache), стандартних бібліотек системних мов (C, C++, Rust, Go, Python `urllib.parse`) та специфікацій інфраструктурного рівня (OAuth 2.0, AWS Signature V4, OpenID Connect).
