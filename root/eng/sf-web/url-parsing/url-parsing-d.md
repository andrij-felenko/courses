# Розбір URL і кодування параметрів

<preknowlist>
- [HTTP](root:com-protocol/http) — модель обміну «запит–відповідь», структура стартового рядка та методи передачі даних.
- [ASCII і UTF-8](root:sf-data/ascii-utf8) — байти, кодові позиції та правила представлення символів у комп'ютерній пам'яті й мережевих протоколах.
- [DHCP і DNS](root:com-transport/dhcp-dns) — доменні імена, ієрархія зон та перетворення символьних адрес на IP-адреси.
- [REST-архітектура](root:com-protocol/rest-api) — ідентифікація ресурсів через URI та передача параметрів фільтрації й пошуку.
</preknowlist>

Клієнтська програма формує запит до веб-сервера для пошуку товарів за запитом користувача: назва категорії містить скісну риску `C/C++`, пошуковий рядок складається з кількох слів `blue sky`, а фільтр вимагає передачі математичного знаку плюса `+10%`. Якщо надіслати цей текст у стартовому рядку протоколу HTTP без попередньої синтаксичної обробки, мережевий стек зазнає миттєвої деструктуризації. Сервер сприйме скісну риску `/` як перехід у глибину файлової ієрархії, пробіл ` ` розділить стартовий рядок протоколу HTTP на фальшиві частини, знак плюса `+` перетвориться на порожній пробіл, а символ решітки `#` змусить клієнтський стек відкинути решту рядка ще до відправлення в сокет.

Комп'ютерні мережі потребують універсального, однозначного та стійкого до синтаксичних конфліктів механізму ідентифікації ресурсів. Цю роль виконує єдиний покажчик ресурсу — **URL** (від англ. *Uniform Resource Locator* — «однорідний локатор ресурсів»). URL є конкретним функціональним різновидом загальнішого поняття **URI** (від англ. *Uniform Resource Identifier* — «однорідний ідентифікатор ресурсу», від лат. *identicus* — «однаковий, тотожний»). Про те, як інженерна спільнота шукала баланс між абстрактними постійними іменами документів та реальними мережевими адресами, розповідає [історія розвитку стандартів від RFC 1630 Тіма Бернерса-Лі до RFC 3986 та живого стандарту WHATWG URL](root:sf-web/url-parsing/hist-uri-evolution.md).

## Анатомія адреси за стандартом RFC 3986

Фундаментальним технічним стандартом, що визначає синтаксичну граматику та алгоритми розбору веб-адрес, є специфікація IETF **RFC 3986**. Вона описує універсальну структуру будь-якого URI як строгу послідовність із п'яти компонентів:

```text
URI = scheme ":" ["//" authority] path ["?" query] ["#" fragment]
```

![Анатомія URL за стандартом RFC 3986](/root/eng/sf-web/url-parsing/img/url-structure.svg)

*Анатомія URL за RFC 3986: п'ять базових компонентів та синтаксичні роздільники, що визначають їхні межі.*

Кожен компонент виконує суворо окреслену інженерну функцію та має власні обмеження на набір дозволених символів.

### 1. Схема (Scheme)

**Схема** (від грец. *σχῆμα* — «образ, вигляд, форма») визначає протокол прикладного рівня або контекст інтерпретації адреси (`https`, `http`, `ftp`, `mailto`, `file`, `ws`, `git+ssh`).

Схема завжди розпочинається з літери латинського алфавіту і може містити лише малі та великі літери, цифри, знак плюса `+`, дефіс `-` та крапку `.`:

```text
scheme = ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )
```

Схема відділяється від наступної частини адреси символом двокрапки `:`. Назва схеми нечутлива до регістру: `HTTPS://` та `https://` абсолютно еквівалентні, проте канонічною формою завжди є нижній регістр. Символи підкреслення `_` або пробіли в схемі суворо заборонені.

### 2. Орган повноважень (Authority)

**Орган повноважень** (від лат. *auctoritas* — «вплив, повноваження, джерело») ідентифікує мережевий вузол, відповідальний за надання доступу до ресурсу. Компонент завжди передується двома скісними рисками `//` і завершується першим символом скісної риски `/`, знаку питання `?`, решітки `#` або кінцем рядка адреси.

Внутрішня структура authority складається з трьох підкомпонентів:

```text
authority = [ userinfo "@" ] host [ ":" port ]
```

- **Облікові дані (Userinfo):** містить ім'я користувача або пару `user:password` перед символом `@`. Передача відкритих паролів в URL вважається застарілою (*deprecated*) практикою та грубим порушенням безпеки, оскільки URL відкрито зберігаються в журналах веб-серверів, кешах проксі та історії браузера. Сучасні браузери повністю ігнорують поле пароля в authority для запобігання фішинговим атакам.
- **Хост (Host):** ім'я домену ([DHCP і DNS](root:com-transport/dhcp-dns)), десяткова адреса IPv4 (`192.168.1.1`) або шістнадцяткова адреса IPv6. Оскільки адреса IPv6 містить власні внутрішні двокрапки як роздільники шістнадцяткових груп (наприклад, `2001:db8::1`), виникає синтаксичний конфлікт із двокрапкою номера порту. Для усунення цієї неоднозначності RFC 3986 вимагає брати адреси IPv6 у квадратні дужки: `[2001:db8::1]:8080`.
- **Порт (Port):** десятковий номер транспортного TCP- або UDP-порту від `0` до `65535`, що слідує після двокрапки `:`. Якщо номер порту відсутній, клієнтський стек використовує порт за замовчуванням для обраної схеми (`80` для `http`, `443` для `https`, `21` для `ftp`).

### 3. Шлях (Path)

**Шлях** (від прагерм. *\*patha-* — «стежка, дорога») вказує на ієрархічне розташування ресурсу в межах заданого органу повноважень. Шлях складається з послідовності сегментів, розділених скісною рискою `/`.

Шлях є обов'язковим компонентом URI, навіть якщо він порожній. Якщо authority присутній, шлях повинен або бути порожнім, або починатися з `/` (так званий *path-abempty*). Якщо authority відсутній, шлях може починатися безпосередньо з назви сегмента (наприклад, у непрозорій схемі `mailto:user@example.com` або відносних посиланнях `images/logo.png`).

Окрім ієрархічних сегментів через `/`, у деяких архітектурах (наприклад, Java JAX-RS або Spring Web) використовуються так звані **матричні параметри** (*Matrix Parameters*, запропоновані Тімом Бернерсом-Лі в RFC 1738). Матричні параметри відокремлюються крапкою з комою `;` всередині конкретного сегмента шляху (наприклад, `/users;status=active/profile;format=json`). Вони застосовуються тоді, коли параметр стосується виключно одного проміжного вузла ієрархії, а не всієї операції запиту.

### 4. Рядок запиту (Query)

**Запит** (від лат. *quaerere* — «шукати, запитувати») містить неієрархічні параметри, що передаються ресурсу для модифікації операції (фільтрація, сортування, пагінація, ідентифікатори пошуку).

Рядок запиту починається з першого символу знаку питання `?` і завершується символом решітки `#` або кінцем рядка адреси:

```text
query = *( pchar / "/" / "?" )
```

Усередині рядка запиту дані традиційно організуються у вигляді пар `ключ=значення`, відокремлених символом амперсанда `&` (наприклад, `?category=electronics&sort=asc&page=2`). Символи `/` та `?` дозволені всередині рядка запиту у відкритому вигляді без кодування, оскільки вони не є роздільниками для цього компонента.

### 5. Фрагмент (Fragment)

**Фрагмент** (від лат. *fragmentum* — «уламок, частина») ідентифікує вторинний ресурс або якір усередині основного документа (наприклад, підзаголовок сторінки, часову мітку відео чи стан клієнтського маршрутизатора в Single Page Application).

Фрагмент починається із символу решітки `#` і триває до самого кінця рядка.

Фундаментальне правило клієнт-серверної архітектури: **фрагмент є виключно клієнтською сутністю і ніколи не передається на сервер у заголовках чи стартовому рядку HTTP-запиту**. Браузер або HTTP-клієнт зобов'язаний відсікти фрагмент під час парсингу URL перед встановленням мережевого з'єднання. Якщо користувач переходить за адресою `https://example.com/docs#installation`, клієнт відправляє на сервер лише `GET /docs HTTP/1.1`, а прокручування до якоря `installation` здійснює локальний рушій рендерингу після завантаження тіла відповіді.

## Механізм відсоткового кодування (Percent-Encoding)

Мережеві протоколи інтернету історично створювалися під 7-бітний набір символів US-ASCII. Будь-який байт за межами діапазону від `0x00` до `0x7F`, а також символи, що виконують синтаксичну роль роздільників компонентів адреси, не можуть з'являтися у відкритому вигляді всередині значень даних.

Для розв'язання цієї проблеми RFC 3986 впроваджує механізм **відсоткового кодування** (*Percent-Encoding*, також відомий як *URL-encoding*).

![Конвеєр відсоткового кодування](/root/eng/sf-web/url-parsing/img/percent-encoding-flow.svg)

*Конвеєр перетворення довільних текстових даних у безпечний формат Percent-Encoding.*

Принцип роботи механізму є детермінованим: заборонений або службовий байт замінюється трисимвольною послідовністю `%HH`, де `%` — літерал відсотка, а `HH` — двозначне шістнадцяткове представлення числового значення байта у верхньому регістрі.

### Класифікація символів за категоріями

Стандарт RFC 3986 чітко ділить усю множину символів на дві головні категорії: **незарезервовані** та **зарезервовані**.

1. **Незарезервовані символи (Unreserved characters):**
   Сюди належать символи, які ніколи не мають спеціального синтаксичного значення в жодній частині URL:
   - Латинські літери верхнього та нижнього регістрів: `A-Z`, `a-z`
   - Десяткові цифри: `0-9`
   - Чотири спеціальні знаки: дефіс `-`, крапка `.`, підкреслення `_`, тильда `~`
   
   Незарезервовані символи **ніколи не потребують кодування**. Якщо у вхідному URL вони закодовані (наприклад, `%41` замість `A`), парсер під час нормалізації зобов'язаний перетворити їх назад у звичайні символи.

2. **Зарезервовані символи (Reserved characters):**
   Символи, що використовуються як структурні роздільники граматики URI. Вони поділяються на дві групи:
   - **Головні роздільники (Gen-delims):** `:`, `/`, `?`, `#`, `[`, `]`, `@` — розділяють основні 5 компонентів адреси.
   - **Підроздільники (Sub-delims):** `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=` — розділяють дані всередині компонентів (наприклад, `&` та `=` у рядку запиту).

Якщо зарезервований символ використовується не як синтаксичний роздільник, а як частина корисних даних (наприклад, символ `/` всередині назви книги `AC/DC` або `+` у номері телефону `+380501234567`), він **мусить бути обов'язково закодований**:
- `/` стає `%2F`
- `?` стає `%3F`
- `#` стає `%23`
- `&` стає `%26`
- `=` стає `%3D`
- `+` стає `%2B`
- Пробіл ` ` стає `%20`

Повний перелік категорій, матрицю дозволених символів для кожного компонента адреси та порівняння стандартів наведено в [довіднику специфікації символьних наборів і правил кодування URL](root:sf-web/url-parsing/api-url-standards.md).

### Кодування Юнікоду (UTF-8)

Коли виникає потреба закодувати символи національних алфавітів (кирилиця, ієрогліфи) чи емодзі, відсоткове кодування застосовується не до абстрактних символів, а до їхнього побайтового бінарного представлення в кодуванні [UTF-8](root:sf-data/ascii-utf8).

Алгоритм перетворення:
1. Текстовий рядок перетворюється на масив байтів UTF-8.
2. Байти, що відповідають незарезервованим символам ASCII (`0x00–0x7F`), залишаються без змін.
3. Кожен байт, що перевищує значення `0x7F`, перетворюється на три символи `%HH`.

Розглянемо покрокове кодування українського слова «Київ»:

```text
Символ 'К': кодова позиція U+041A → байти UTF-8: 0xD0 0x9A → %D0%9A
Символ 'и': кодова позиція U+0438 → байти UTF-8: 0xD0 0xB8 → %D0%B8
Символ 'ї': кодова позиція U+0457 → байти UTF-8: 0xD1 0x97 → %D1%97
Символ 'в': кодова позиція U+0432 → байти UTF-8: 0xD0 0xB2 → %D0%B2

Результат: «Київ» → %D0%9A%D0%B8%D1%97%D0%B2
```

Один символ Юнікоду в кодуванні UTF-8 займає від двох до чотирьох байтів, тому в URL він розгортається у послідовність від 6 до 12 друкованих ASCII-символів.

## Канонізація та нормалізація шляхів

У веб-системах однаковий логічний ресурс може бути записаний десятками синтаксично різних способів. Наприклад:
- `http://EXAMPLE.com:80/a/b/../c/./`
- `http://example.com/a/c/`
- `http://example.com/%61/c/`

Якщо проксі-сервер або система кешування порівнює URL як прості рядки, вона вважатиме ці адреси різними ресурсами. Це призведе до роздвоєння кешу (*cache pollution*) та відкриє вектор для обходу правил доступу.

**Нормалізація** (від лат. *normalis* — «прямий, за правилом») — це процес приведення синтаксису адреси до єдиної канонічної форми.

RFC 3986 визначає такі рівні нормалізації:

1. **Нормалізація регістру (Case Normalization):** назва схеми (`HTTPS` → `https`) та хост (`API.Example.COM` → `api.example.com`) приводяться до нижнього регістру. Шістнадцяткові цифри у відсоткових послідовностях приводяться до верхнього регістру (`%d0%9a` → `%D0%9A`).
2. **Нормалізація відсоткового кодування (Percent-Encoding Normalization):** якщо незарезервований символ був помилково закодований, він розкодовується (`%41` → `A`, `%7E` → `~`). Проте зарезервовані символи у шляху розкодовувати заборонено: `%2F` не можна перетворювати на `/`, оскільки це змінить кількість і межі сегментів шляху!
3. **Нормалізація портів за замовчуванням:** якщо порт у компоненті authority збігається зі стандартним для схеми (`:80` для `http` або `:443` для `https`), він видаляється.
4. **Усунення крапкових сегментів (Path Segment Normalization):** розв'язання відносних сегментів `.` (поточний каталог) та `..` (батьківський каталог).

### Алгоритм remove_dot_segments

Алгоритм RFC 3986 §5.2.4 оперує двома рядковими буферами: вхідним буфером, що містить вихідний шлях, і вихідним буфером, куди складається нормалізований результат.

![Нормалізація відносних шляхів remove_dot_segments](/root/eng/sf-web/url-parsing/img/path-normalization.svg)

*Покроковий рух сегментів між вхідним та вихідним буферами в алгоритмі remove_dot_segments.*

Кроки алгоритму виконуються в циклі, доки вхідний буфер не стане порожнім:

```text
1. Якщо вхідний буфер починається з "../" або "./":
   -> видалити цей префікс із вхідного буфера.

2. Якщо вхідний буфер починається з "/./" або дорівнює "/.":
   -> замінити префікс у вхідному буфері на "/".

3. Якщо вхідний буфер починається з "/../" або дорівнює "/..":
   -> замінити префікс у вхідному буфері на "/";
   -> видалити останній сегмент (разом із попереднім "/") з вихідного буфера.

4. Якщо вхідний буфер складається лише з "." або "..":
   -> очистити вхідний буфер.

5. Інакше (звичайний сегмент):
   -> перемістити перший символ "/" (якщо є) та всі наступні символи до наступного "/" 
      або кінця рядка з вхідного буфера в кінець вихідного буфера.
```

Цей алгоритм гарантує, що шлях `/static/images/../css/./main.css` детерміновано перетвориться на `/static/css/main.css`.

> Розбіжності в реалізації алгоритму `remove_dot_segments` між зворотним проксі-сервером (Nginx, Cloudflare, Envoy) та бекенд-додатком породжують найнебезпечніші вразливості сучасної веб-архітектури: **Directory Traversal** та **Path Confusion**.
>
> Якщо зворотний проксі налаштований блокувати доступ до адмін-панелі за правилом `location /admin { deny all; }`, зловмисник може надіслати запит `/public/..%2fadmin`. Якщо проксі не розкодовує `%2f` перед перевіркою правила, він пропустить запит як безпечний шлях `/public/..%2fadmin`. Проте коли бекенд-сервер розкодує послідовність у `/public/../admin` і виконає `remove_dot_segments`, він віддасть сторінку `/admin`, повністю обійшовши захист проксі.

## Розв'язання відносних посилань (Reference Resolution)

У реальних веб-сторінках та API посилання рідко записуються у повному абсолютному вигляді. Замість повного `https://example.com/v1/users/42/avatar.png` HTML-документ або клієнтський додаток оперує **відносними посиланнями** (*Relative References*): `/avatar.png`, `../settings`, `?tab=bio` або `#profile`.

Алгоритм розв'язання посилань за RFC 3986 §5.2 перетворює пару `(Базовий URL, Відносне посилання)` на цільовий абсолютний URL за суворими правилами спадкування компонентів:

1. **Якщо відносне посилання містить схему:** воно розглядається як абсолютно новий незалежний URL, і базовий URL повністю ігнорується.
2. **Якщо схема відсутня, але присутній authority (починається з `//`):** схема успадковується від базового URL, а authority, шлях і параметри беруться з відносного посилання (так звані *Network-Path References*, наприклад `//cdn.example.com/lib.js`).
3. **Якщо authority відсутній, а шлях починається з `/`:** схема та authority успадковуються від базового URL, а шлях замінюється на шлях відносного посилання (абсолютний шлях на тому самому хості).
4. **Якщо шлях відносного посилання не починається з `/` (відносний шлях):**
   - Береться шлях базового URL до останнього символу `/` (каталог базового документа).
   - До нього конкатенується відносний шлях посилання.
   - Отриманий результат нормалізується через алгоритм `remove_dot_segments`.
5. **Якщо шлях відносного посилання порожній:**
   - Повністю зберігаються схема, authority та шлях базового URL.
   - Якщо у відносному посиланні присутній query, він замінює query базового URL; інакше query також успадковується.
   - Фрагмент завжди береться з відносного посилання.

```text
Базовий URL:       https://example.com/v1/reports/monthly.html?year=2026

1. Посилання:     "../users/list"
   Злиття шляхів: "/v1/reports/" + "../users/list"
   Нормалізація:  "/v1/users/list"
   Результат:     https://example.com/v1/users/list

2. Посилання:     "?sort=desc"
   Шлях лишається: "/v1/reports/monthly.html"
   Результат:     https://example.com/v1/reports/monthly.html?sort=desc

3. Посилання:     "#chart"
   Результат:     https://example.com/v1/reports/monthly.html?year=2026#chart
```

## Безпека інтернаціоналізованих імен: гомографічні атаки

При розборі компонента хоста стандарт RFC 3986 спирається на набір US-ASCII. Проте стандарт IDN (*Internationalized Domain Names*) дозволяє користувачам реєструвати доменні імена національними мовами за допомогою кодування Punycode (префікс `xn--`).

Це відкриває можливість для небезпечних **гомографічних атак** (*IDN Homograph Attacks*). Багато символів кирилиці, грецького чи вірменського алфавітів візуально неможливо відрізнити від латинських літер:
- Латинська `a` (U+0061) та кирилична `а` (U+0430)
- Латинська `o` (U+006F) та кирилична `о` (U+043E)
- Латинська `p` (U+0070) та кирилична `р` (U+0440)

Зловмисник може зареєструвати домен `pаypаl.com`, де замість латинських літер `a` використано кириличні гліфи. У мережевому шарі цей домен розкривається як `xn--pypal-4ve.com`, проте недосвідчений користувач в адресному рядку бачить звичне ім'я платіжної системи.

Для захисту користувачів сучасні браузери (Chromium, Firefox, Safari) застосовують евристику **Mixed-Script Detection** (виявлення змішаних писемностей за стандартом Unicode UTS #39): якщо в межах однієї мітки домену змішуються символи з різних систем письма (наприклад, латиниця з кирилицею), або якщо домен містить символи поза дозволеним білим списком національних абеток користувача, браузер примусово відображає домен у сирому вигляді Punycode `xn--...`.

## Робота з параметрами запиту (Query String)

Рядок запиту містить пари `ключ=значення`, проте його внутрішній синтаксис не стандартизований базовим документом RFC 3986. Специфікація розглядає query як єдиний суцільний рядок непрозорих даних від `?` до `#`. Правила розділення на пари `&` та присвоєння `=` виникли в ранніх специфікаціях HTML-форм і закріпилися як фактичний консенсус індустрії.

### Пастка кодування пробілу: `%20` проти `+`

У веб-розробці існує два принципово різних підходи до кодування пробілів у рядку запиту, що є причиною постійних дефектів обробки даних:

1. **Стандарт RFC 3986 (URI Generic Syntax):** пробіл завжди кодується строго як `%20`. Символ плюса `+` належить до групи `sub-delims` і є дозволеним символом у значенні, що позначає саме математичний плюс.
2. **Специфікація HTML-форм (`application/x-www-form-urlencoded`):** історично використовувала символ `+` для заміни пробілів, а справжній плюс вимагала кодувати як `%2B`.

Розглянемо практичний конфлікт: клієнт шукає мову програмування `C++` за допомогою пошукового параметра:

```text
Параметр: query = "C++"

1. Кодування за стандартом RFC 3986:
   "C++" → "query=C++" (плюси не кодуються)
   Сервер, що очікує application/x-www-form-urlencoded, сприйме '+' як пробіли:
   Отримане значення: "C  " (помилка!)

2. Кодування за application/x-www-form-urlencoded:
   "C++" → "query=C%2B%2B"
   Сервер коректно розкодує: "C++"
```

Золоте правило формування запитів: **усі значення параметрів перед конкатенацією в URL повинні кодуватися з урахуванням конвенції приймача**. Якщо бекенд використовує стандартний парсер форм, символ `+` у даних повинен обов'язково кодуватися як `%2B`, а пробіл — як `%20` або `+`.

### Множинні та масивні параметри

Коли необхідно передати кілька значень для одного параметра (наприклад, фільтр за кількома тегами), різні серверні екосистеми очікують різний синтаксис:

1. **Повторення ключів (RFC-сумісний підхід):**
   `?tag=web&tag=api&tag=security`
   Стандартний підхід для Python (Django, FastAPI), Java (Spring) та Go.
2. **Синтаксис квадратних дужок:**
   `?tag[]=web&tag[]=api`
   Традиційний синтаксис мови PHP та бібліотеки `qs` в екосистемі Node.js. Зауважте, що символи `[` та `]` є `gen-delims` у RFC 3986, тому в суворих клієнтах вони вимагають кодування: `?tag%5B%5D=web&tag%5B%5D=api`.
3. **Розділення комами:**
   `?tags=web,api,security`
   Компактний варіант, де клієнт і сервер домовляються про власний внутрішній формат розбору рядка.

### Канонізація параметрів для кешування та підпису запитів

Для ефективного HTTP-кешування на рівні CDN та криптографічної перевірки цілісності запитів (наприклад, алгоритм AWS Signature Version 4 або OAuth 1.0/2.0 HMAC) порядок параметрів у рядку запиту має вирішальне значення.

Два запити з однаковими параметрами, розміщеними в різному порядку:
- `https://api.example.com/items?sort=asc&category=books`
- `https://api.example.com/items?category=books&sort=asc`

Для сервера повертають ідентичні дані, проте для CDN-сервера це два абсолютно різні ключі кешу (*Cache Keys*). У результаті ефективність кешу падає вдвічі, а пам'ять проксі засмічується дублікатами.

**Алгоритм канонізації рядка запиту:**
1. Розбити рядок запиту на окремі пари `ключ=значення` за роздільником `&`.
2. Відсотково закодувати кожен ключ і кожне значення за правилами RFC 3986.
3. Відсортувати пари у строгому лексикографічному порядку за зростанням байтових значень ключів (у разі збігу ключів — за значенням).
4. Об'єднати відсортовані пари через символ `&`.

```text
Вихідний запит:  ?b=2&a=10&b=1
Після сортування: ?a=10&b=1&b=2
```

## Відмінності між HTTP/1.1 та бінарними протоколами HTTP/2 і HTTP/3

У класичному протоколі HTTP/1.1 клієнт самостійно розбирає повний URL і відправляє його шматки в різні частини текстового повідомлення: хост поміщається в заголовок `Host: example.com:8080`, а шлях і параметри запиту — у стартовий рядок `GET /v1/items?page=1 HTTP/1.1`.

У бінарних протоколах [HTTP/2](root:com-protocol/http) та HTTP/3 структура адреси формалізована у вигляді спеціальних **псевдозаголовків** (*Pseudo-headers*), що починаються з двокрапки:
- `:scheme` — передає протокол (`https` або `http`).
- `:authority` — замінює старий заголовок `Host`, передаючи `host[:port]`.
- `:path` — містить конкатенацію абсолютного шляху та рядка запиту (`/v1/items?page=1`). Якщо шлях порожній, протокол HTTP/2 вимагає обов'язкової передачі символу `/`.

Таке розділення дозволяє бінарним протоколам застосовувати алгоритми стиснення заголовків (HPACK у HTTP/2 та QPACK у HTTP/3), повністю усуваючи надлишкове повторне передавання статичних доменних імен і префіксів схем між послідовними запитами в одному мультиплексованому TCP/QUIC-з'єднанні.

## Архітектура парсера: скінченний автомат проти регулярних виразів

Для синтаксичного розбору URL в інженерній практиці застосовують два підходи: регулярні вирази та скінченні автомати (*Finite State Machine*, FSM).

У додатку B (*Appendix B*) стандарту RFC 3986 наведено офіційний регулярний вираз для декомпозиції адреси:

```text
^(([^:/?#]+):)?(//([^/?#]*))?([^?#]*)(\?([^#]*))?(#(.*))?
 12            3  4          5       6  7        8 9
```

Цей регулярний вираз використовує 9 груп захоплення для виділення схеми, authority, шляху, запиту та фрагмента. Попри компактність, регулярні вирази мають суттєві обмеження:
- Вони вимагають виділення динамічної пам'яті під об'єкти збігів у більшості мов програмування.
- Вони не проводять внутрішньої валідації компонентів (наприклад, коректності IPv6 або заборонених символів у схемі).
- Вони можуть бути вразливими до атак типу *ReDoS* (*Regular Expression Denial of Service*) на спеціально сконструйованих довгих рядках.

У високопродуктивних системах розбір виконують за допомогою потокового скінченного автомата без жодної алокації пам'яті.

![Скінченний автомат парсера URL](/root/eng/sf-web/url-parsing/img/url-parser-state-machine.svg)

*Скінченний автомат потокового розбору компонентів URL за символами-роздільниками.*

Автомат рухається по масиву символів за один лінійний прохід `O(N)`:
1. **Стан SCHEME:** накопичує символи схеми. Зустріч двокрапки `:` фіксує схему та переводить автомат у стан AUTHORITY (якщо наступні символи `//`) або PATH.
2. **Стан AUTHORITY:** шукає роздільники `@` (userinfo), `[` та `]` (IPv6), `:` (порт), `/` або `?` чи `#` (перехід до наступних компонентів).
3. **Стан PATH:** зчитує сегменти шляху до зустрічі `?` (перехід у стан QUERY) або `#` (перехід у стан FRAGMENT).
4. **Стан QUERY:** зчитує рядок параметрів до зустрічі `#` або кінця буфера.
5. **Стан FRAGMENT:** зчитує залишок рядка як клієнтський якір.

Повну системну реалізацію такого автомата на мовах C, C++ (із використанням `std::string_view`) та Python наведено в [проєктній вставці з реалізації швидкого парсера URL та кодувальника параметрів](root:sf-web/url-parsing/proj-url-parser.md).

## Практика роботи з URL у Python та C/C++

Розглянемо, як виконувати розбір, збирання, нормалізацію та кодування адрес у стандартних бібліотеках мов програмування.

### Робота з URL у Python (`urllib.parse`)

Стандартна бібліотека Python надає модуль `urllib.parse`, що містить повний набір функцій для маніпуляцій з адресами:

```python
import urllib.parse

raw_url = "https://api.example.com:8443/v1/search?query=blue%20sky&category=books#top"

# 1. Розбір URL на компоненти
# Рекомендується urlsplit замість застарілого urlparse (не відокремлює params у шляху)
res = urllib.parse.urlsplit(raw_url)

print(f"Схема:    {res.scheme}")     # https
print(f"Хост:     {res.hostname}")   # api.example.com
print(f"Порт:     {res.port}")       # 8443
print(f"Шлях:     {res.path}")       # /v1/search
print(f"Запит:    {res.query}")      # query=blue%20sky&category=books
print(f"Фрагмент: {res.fragment}")   # top

# 2. Розбір рядка запиту в словник
params = urllib.parse.parse_qs(res.query)
print(f"Параметри: {params}")
# Виведе: {'query': ['blue sky'], 'category': ['books']} (значення автоматично розкодовано)

# 3. Модифікація та зворотне збирання
params['query'] = ['C++ & Python']
params['page'] = ['1']

# Кодування параметрів за правилами RFC 3986 (quote_via=urllib.parse.quote)
new_query = urllib.parse.urlencode(params, doseq=True, quote_via=urllib.parse.quote)

# Збирання URL назад
new_url = urllib.parse.urlunsplit((
    res.scheme,
    res.netloc,
    res.path,
    new_query,
    res.fragment
))
print(f"Новий URL: {new_url}")
# https://api.example.com:8443/v1/search?query=C%2B%2B%20%26%20Python&category=books&page=1#top
```

У модулі `urllib.parse` функція `urlsplit` є переважнішою за `urlparse`, оскільки `urlparse` намагається розбирати застарілі параметри RFC 2396 у шляху через крапку з комою `;`, що ламає сучасні REST-маршрути. 

Для кодування окремих значень параметрів функція `quote` приймає необов'язковий параметр `safe`: за замовчуванням `safe='/'`, що дозволяє прямим скісним рискам залишатися незакодованими. Якщо значення містить шлях як параметр (наприклад, `file=docs/manual.pdf`), для уникнення неоднозначностей необхідно передавати `safe=''`.

### Реалізація на C та C++

У системному програмуванні на C та C++ критично важливо уникати створення проміжних динамічних рядків при розборі. У C++ для цього використовується `std::string_view`, а в C — структури зі вказівником і довжиною `size_t`.

:::tabs
```c
#include <stdio.h>
#include <string.h>
#include <stdbool.h>

typedef struct {
    const char *scheme;
    size_t      scheme_len;
    const char *host;
    size_t      host_len;
    int         port;
    const char *path;
    size_t      path_len;
    const char *query;
    size_t      query_len;
} url_parts_t;

/* Простий нуль-алокаційний виділювач компонентів */
bool parse_http_url(const char *url, url_parts_t *parts) {
    memset(parts, 0, sizeof(*parts));
    const char *p = url;

    /* Схема */
    const char *scheme_end = strstr(p, "://");
    if (!scheme_end) return false;
    parts->scheme = p;
    parts->scheme_len = scheme_end - p;
    p = scheme_end + 3;

    /* Хост і порт */
    const char *host_start = p;
    while (*p && *p != '/' && *p != '?' && *p != '#' && *p != ':') {
        p++;
    }
    parts->host = host_start;
    parts->host_len = p - host_start;

    if (*p == ':') {
        p++;
        parts->port = 0;
        while (*p >= '0' && *p <= '9') {
            parts->port = parts->port * 10 + (*p - '0');
            p++;
        }
    } else {
        parts->port = (parts->scheme_len == 5 && memcmp(parts->scheme, "https", 5) == 0) ? 443 : 80;
    }

    /* Шлях */
    if (*p == '/') {
        const char *path_start = p;
        while (*p && *p != '?' && *p != '#') p++;
        parts->path = path_start;
        parts->path_len = p - path_start;
    } else {
        parts->path = "/";
        parts->path_len = 1;
    }

    /* Запит */
    if (*p == '?') {
        p++;
        const char *q_start = p;
        while (*p && *p != '#') p++;
        parts->query = q_start;
        parts->query_len = p - q_start;
    }

    return true;
}
```

```cpp
#include <iostream>
#include <string_view>
#include <optional>
#include <charconv>

struct UrlParts {
    std::string_view scheme;
    std::string_view host;
    int port{80};
    std::string_view path{"/"};

};

class FastUrlParser {
public:
    static std::optional<UrlParts> parse(std::string_view url) noexcept {
        UrlParts parts;
        auto scheme_pos = url.find("://");
        if (scheme_pos == std::string_view::npos) return std::nullopt;

        parts.scheme = url.substr(0, scheme_pos);
        url.remove_prefix(scheme_pos + 3);

        // Відокремлюємо authority від шляху
        auto path_pos = url.find_first_of("/?#");
        auto auth = (path_pos == std::string_view::npos) ? url : url.substr(0, path_pos);

        if (auto colon = auth.find(':'); colon != std::string_view::npos) {
            parts.host = auth.substr(0, colon);
            auto port_str = auth.substr(colon + 1);
            std::from_chars(port_str.data(), port_str.data() + port_str.size(), parts.port);
        } else {
            parts.host = auth;
            parts.port = (parts.scheme == "https") ? 443 : 80;
        }

        if (path_pos != std::string_view::npos) {
            url.remove_prefix(path_pos);
            auto query_pos = url.find('?');
            auto frag_pos = url.find('#');

            if (query_pos != std::string_view::npos) {
                parts.path = url.substr(0, query_pos);
                auto query_end = (frag_pos != std::string_view::npos) ? frag_pos : url.size();
                parts.query = url.substr(query_pos + 1, query_end - (query_pos + 1));
            } else if (frag_pos != std::string_view::npos) {
                parts.path = url.substr(0, frag_pos);
            } else {
                parts.path = url;
            }
        }

        return parts;
    }
};
```

## Типові помилки та безпекові ризики

Неправильний розбір та недбале кодування веб-адрес регулярно входять до списків найкритичніших веб-вразливостей OWASP Top 10.

1. **Подвійне розкодування (Double Decoding):**
   Якщо проксі-сервер перевіряє шлях після одноразового розкодування, а бекенд-додаток або фреймворк автоматично розкодовує його вдруге, атакуючий надсилає послідовність `%252F` (`%25` — це закодований символ `%`). Проксі розкодовує `%252F` у `%2F` і вважає рядок безпечним значенням без скісних рисок. Бекенд розкодовує `%2F` у звичайний `/` і відкриває закритий шлях.
2. **Вразливість SSRF (Server-Side Request Forgery):**
   Виникає, коли бекенд приймає URL від клієнта і самостійно здійснює HTTP-запит до вказаного хоста. Якщо парсер неправильно обробляє облікові дані користувача або символи `@` та `#`, атакуючий може обійти білий список доменів:
   `https://expected-domain.com@169.254.169.254/latest/meta-data/`
   Поганий парсер вважатиме хостом `expected-domain.com`, тоді як мережевий клієнт з'єднається з внутрішньою IP-адресою хмарних метаданих `169.254.169.254`.
3. **Null Byte Injection (`%00`):**
   Передача шістнадцяткового нуля `%00` у шляху або параметрах. У мовах високого рівня (Python, Java) рядок розглядається як безпечний об'єкт фіксованої довжини, проте при передачі в системні виклики C (`open()`, `stat()`) нульовий байт передчасно обриває шлях файлової системи, дозволяючи зрізати розширення файлу (наприклад, `/uploads/avatar.png%00.php`).
4. **Конфлікт обробки пробілів у заголовках:**
   Впровадження символів повернення каретки та переведення рядка (`%0D%0A` або `\r\n`) у незавалідовані параметри URL, що використовуються для редиректів. Це призводить до вразливості *HTTP Response Splitting*, коли атакуючий може вставити довільні заголовки відповіді або підробити тіло сторінки.

Надійний веб-клієнт і сервер зобов'язані здійснювати сувору санітизацію, розділяти розбір синтаксису і бізнес-інтерпретацію даних та застосовувати канонічні алгоритми RFC 3986 на кожному кроці мережевого конвеєра.
