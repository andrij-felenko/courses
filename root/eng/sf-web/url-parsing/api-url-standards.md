# 📋 Специфікація символьних наборів і правила кодування URL

Мережеві адреси URI та URL спираються на 7-бітний набір символів US-ASCII. Будь-який байт за межами дозволеного підмножини або байт, що має спеціальне синтаксичне значення як роздільник, повинен кодуватися у шістнадцятковому форматі `%HH`. Нижче наведено зведену специфікацію дозволених і зарезервованих символів за стандартом RFC 3986, аналіз механізмів обробки інтернаціоналізованих доменних імен (IDN/Punycode), правила нормалізації адрес IPv6 та порівняння з моделлю WHATWG URL і форматом форм `application/x-www-form-urlencoded`.

## Класифікація символів за RFC 3986

Усі 128 символів таблиці US-ASCII поділяються стандартом RFC 3986 на три взаємовиключні категорії: незарезервовані (*unreserved*), зарезервовані (*reserved*) та заборонені/інші (*other/percent-encoded*).

| Категорія | Символи | Кількість | Правило обробки |
|---|---|---|---|
| **Незарезервовані (Unreserved)** | `A-Z`, `a-z`, `0-9`, `-`, `.`, `_`, `~` | 66 | Ніколи не вимагають екранування. Якщо закодовані у вигляді `%HH` (наприклад, `%41` для `A`), парсер зобов'язаний їх розкодовувати при нормалізації. |
| **Головні роздільники (Gen-delims)** | `:`, `/`, `?`, `#`, `[`, `]`, `@` | 7 | Визначають межі 5 основних компонентів URL. Усередині значень даних обов'язково кодуються через `%HH`. |
| **Підроздільники (Sub-delims)** | `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=` | 11 | Використовуються як роздільники всередині окремих компонентів (наприклад, `&` та `=` у рядку запиту). |
| **Заборонені в URL (Disallowed)** | Пробіл ` `, лапки `"`, `<`, `>`, `\`, `^`, `` ` ``, `{`, `\|`, `}`, символи керування (0x00–0x1F, 0x7F) | 33+ | Не можуть бути присутніми у вихідному вигляді в валідному URI за RFC 3986. Завжди кодуються через `%HH`. |
| **Не-ASCII байти (UTF-8)** | Байти з діапазону `0x80` – `0xFF` | 128 | Перетворюються на послідовність байтів UTF-8, після чого кожен байт замінюється на `%HH` (наприклад, українська літера «і» = `0xD1 0x96` → `%D1%96`). |

Незарезервовані символи мають особливий статус у синтаксичному розборі. Чотири символи пунктуації — дефіс `-`, крапка `.`, підкреслення `_` та тильда `~` — обрано розробниками стандарту IETF тому, що вони не викликають синтаксичних конфліктів у жодній операційній чи файловій системі та не є керуючими символами в оболонках командного рядка (Shell).

Зарезервовані символи, навпаки, захищені стандартом саме тому, що їхня пряма присутність у тексті змінює контекст розбору. Наприклад, поява сирої двокрапки `:` усередині першого сегмента шляху робить неможливим однозначне визначення того, де закінчується схема протоколу й де починається шлях (особливо у відносних адресах на кшталт `my:file.txt`). Тому в таких сегментах двокрапка обов'язково повинна замінюватися на `%3A`.

## Дозволені символи за компонентами URL

Кожен компонент URL має власну граматику ABNF. Символ, дозволений у рядку запиту без екранування, може бути суворо заборонений у хості чи схемі.

| Компонент | Дозволені символи у сирому вигляді | Заборонені роздільники (вимагають %HH при появі у даних) | Типовий приклад компонента |
|---|---|---|---|
| **Scheme** | `ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )` | Усі інші символи, включаючи `_`, `/`, `?`, `#` | `https`, `git+ssh`, `custom-app` |
| **Userinfo** | `unreserved`, `sub-delims`, `%HH`, `:` | `@`, `/`, `?`, `#` | `alice`, `admin:secret%21` |
| **Host (DNS/IP)** | `unreserved`, `sub-delims`, IPv6 у `[...]` | `:`, `/`, `?`, `#`, `@` | `api.example.com`, `[::1]` |
| **Port** | `*DIGIT` (число 0–65535) | Усі нецифрові символи | `443`, `8080` |
| **Path Segment** | `unreserved`, `sub-delims`, `%HH`, `@`, `:` | `/` (розділяє сегменти), `?`, `#` | `v1`, `orders`, `user%2Fprofile` |
| **Query (Key/Val)** | `unreserved`, `sub-delims` (окрім `&`, `=`), `%HH`, `:`, `@`, `/`, `?` | `&` (розділяє пари), `=` (розділяє ключ і значення), `#` | `search=sky%20blue&sort=asc` |
| **Fragment** | `unreserved`, `sub-delims`, `%HH`, `:`, `@`, `/`, `?` | `#` (завершує або починає новий якір) | `section-3.2`, `top` |

Граматика шляху вимагає розрізнення понять *segment* (сегмент без роздільників) та *segment-nz* (непорожній сегмент). Усередині сегмента символи `@` та `:` є абсолютно легальними й не потребують екранування (наприклад, `/users/admin@example.com/profile`), оскільки скісна риска `/` однозначно ізолює цей сегмент від схеми та органу повноважень.

Рядок запиту (*Query*) має найбільш ліберальний набір дозволених символів серед усіх компонентів. Символи `/` та `?` дозволено передавати у відкритому вигляді без кодування (наприклад, `?redirect=/dashboard/view?id=10`), оскільки парсер знає, що рядок запиту може бути завершений виключно символом `#` або кінцем URL. Проте символи `&` та `=` усередині значень параметрів вимагають обов'язкового відсоткового кодування (`%26` та `%3D`), інакше вони змінять структуру пар ключ-значення.

## Інтернаціоналізовані домени (IDN) та алгоритм Punycode

Стандарт RFC 3986 забороняє використання не-ASCII символів у компоненті хоста. Для підтримки національних доменів верхнього та другого рівнів (наприклад, `президент.укр` або `münchen.de`) система DNS та веб-клієнти використовують механізм **IDN** (*Internationalized Domain Names in Applications*, RFC 5890 / RFC 5891).

Механізм базується на алгоритмі кодування **Punycode** (RFC 3492), що перетворює будь-який рядок символів Юнікоду в унікальний ASCII-сумісний рядок (*ASCII Compatible Encoding*, ACE) із префіксом `xn--`.

Етапи трансформації доменного імені:
1. **Нормалізація (Nameprep / UTS #46):** символи переводяться в нижній регістр, усуваються невидимі пробіли та символи форматування (Zero-Width Joiner).
2. **Розбиття на мітки:** доменне ім'я ділиться на сегменти за символом крапки `.`.
3. **Punycode-кодування:** для кожної мітки, що містить не-ASCII символи, виділяються всі ASCII-літери (якщо є), після чого додається дефіс `-` і шістнадцяткове представлення позицій та значень Юнікод-символів. На початку мітки додається префікс `xn--`.

Приклад перетворення українського домену:
- Вихідний домен: `тест.укр`
- Сегмент `тест` → `xn--e1aybc`
- Сегмент `укр` → `xn--j1amh`
- Канонічний URL для мережевого рівня: `http://xn--e1aybc.xn--j1amh/`

Браузери здійснюють зворотне перетворення ACE-рядка в людиночитабельний вигляд під час відображення в адресному рядку, застосовуючи суворі фільтри проти гомографічних атак (наприклад, підміни латинської літери `a` на візуально ідентичну кириличну літеру `а` в домені банку).

## Специфікація адрес IPv6 в Authority

Синтаксис IPv6-адрес (RFC 4291) використовує двокрапки для розділення 16-бітних шістнадцяткових блоків (наприклад, `fe80:0000:0000:0000:0204:61ff:fe9d:f152`). Для запобігання неоднозначності з двокрапкою номера порту стандарт RFC 3986 §3.2.2 визначає обов'язкові правила:

1. **Квадратні дужки:** будь-яка IPv6-адреса в компоненті authority повинна обрамлятися символами `[` та `]`, наприклад: `http://[fe80::1]:8080/status`.
2. **Стиснення нулів (RFC 5952):** найбільша послідовність суміжних нульових 16-бітних блоків повинна замінюватися подвійною двокрапкою `::`. Подвійна двокрапка може з'являтися в адресі лише один раз.
3. **Зонні індекси (Scope ID / Zone Identifier):** у локальних мережевих адресах link-local (`fe80::/10`) для вказівки мережевого інтерфейсу використовується суфікс зонного ідентифікатора. Оскільки символ `%` у URL зарезервований під відсоткове кодування, RFC 6874 вимагає кодувати зонний роздільник як `%25`, наприклад: `http://[fe80::1%25eth0]/index.html`.

## Порівняння трьох режимів кодування

У веб-розробці паралельно існують три різні системи кодування, що часто призводить до помилок розкодування та плутанини з символом плюса `+` і пробілом.

| Властивість | RFC 3986 (Generic URI) | `application/x-www-form-urlencoded` | WHATWG URL Standard |
|---|---|---|---|
| **Кодування пробілу** | Завжди `%20` | Символ `+` (або `%20`) | `%20` для URL; `+` лише у `URLSearchParams` |
| **Символ `+` у даних** | Залишається як `+` (бо це `sub-delim`) | Обов'язково кодується як `%2B` | Залишається `+` у Path; `%2B` у `URLSearchParams` |
| **Символ `~` (тильда)** | Незарезервований (не кодується) | Кодується як `%7E` у застарілих парсерах (RFC 1738) | Незарезервований (не кодується) |
| **Символ `\` (зворотний слеш)** | Заборонений (вимагає `%5C`) | Кодується як `%5C` | Автоматично перетворюється на `/` у спеціальних схемах |
| **Регістр `%HH`** | Рекомендується верхній регістр (`%2F`, `%D0`) | Не регламентується | Верхній регістр при серіалізації |
| **Спеціальні схеми** | Усі схеми мають однаковий синтаксичний статус | Не застосовується | Особливий статус для `http`, `https`, `ws`, `wss`, `ftp`, `file` |

Спеціальні схеми в стандарті WHATWG URL (`http`, `https`, `ws`, `wss`, `ftp`, `file`) отримують унікальні правила нормалізації:
- Якщо хост містить зворотні скісні риски `\`, рушій автоматично перетворює їх на прямі скісні риски `/`.
- Якщо порт збігається зі стандартним (80 для `http`, 443 для `https`), він повністю видаляється з серіалізованого представлення.
- Порожній шлях автоматично замінюється на косий слеш `/` (тобто `http://example.com` перетворюється на `http://example.com/`).

## Правила нормалізації крапкових сегментів (RFC 3986 §5.2.4)

Нормалізація шляху `remove_dot_segments` виконує детерміноване перетворення відносних сегментів:

1. Якщо вхідний буфер починається з `../` або `./`, цей префікс видаляється.
2. Якщо вхідний буфер починається з `/./` або дорівнює `/.`, замінити префікс на `/`.
3. Якщо вхідний буфер починається з `/../` або дорівнює `/..`, замінити префікс на `/` і видалити останній сегмент із вихідного буфера.
4. Якщо вхідний буфер містить лише `.` або `..`, видалити їх.
5. Перемістити перший або наступний сегмент шляху з вхідного буфера у вихідний до наступного символу `/` або кінця рядка.

Застосування цих правил є обов'язковим кроком перед передачею шляху до файлової системи чи маршрутизатора додатку, що гарантує захист від несанкціонованого виходу за межі дозволеного кореневого каталогу.
