# 📋 Протокол маршрутизації Redis Cluster: геш-слоти, редиректи MOVED/ASK та RESP3 Client-Side Tracking

Розподілений кластер Redis Cluster реалізує децентралізовану схему маршрутизації запитів без виділених проксі-вузлів. Клієнтська взаємодія регулюється бінарними та текстовими протоколами: алгоритмом розбиття на 16 384 геш-слоти, кодами редиректів `MOVED` і `ASK`, кластерними керуючими командами, протоколом пліток (Cluster Bus) та механізмом асинхронного сповіщення про інвалідацію клієнтського кешу (RESP3 Client-Side Tracking).

## 1. Алгоритм розрахунку геш-слота та вилучення геш-тегів

Простір ключів у Redis Cluster розбивається на 16 384 дискретні слоти з діапазону від 0 до 16383. Це число було обрано розробниками як оптимальний компроміс між гранулярністю балансування та розміром службових заголовків: бітова карта з 16 384 слотів займає рівно 2048 байтів (2 КБ), що дозволяє передавати повний стан володіння слотами в кожному службовому пакеті протоколу пліток без фрагментації мережевих кадрів TCP.

Номер цільового слота обчислюється на основі 16-бітної контрольної суми CRC16 за стандартом CCITT/XMODEM (поліном `0x1021` з початковим значенням `0x0000`). Якщо назва ключа є звичайним рядком без спеціальних роздільників, контрольній сумі піддається весь масив байтів ключа. Отримане 16-бітне ціле число накладається на бітову маску `0x3FFF` (десяткове число 16383), що еквівалентно операції взяття залишку від ділення на 16 384:

```text
slot = CRC16(effective_key) & 16383
```

### Синтаксис та правила обробки геш-тегів (Hash Tags)

У розподілених системах операції над кількома ключами (Multi-Key Operations, такі як `MGET`, `MSET`, транзакційні блоки `MULTI/EXEC` та виконання скриптів Lua) вимагають, щоб усі задіяні ключі фізично перебували в оперативній пам'яті одного й того самого шарду. Якщо ключі гешуються незалежно, вони потрапляють у різні слоти, і сервер повертає помилку `-CROSSSLOT`.

Для гарантованого розміщення пов'язаних сутностей на одному вузлі застосовують механізм геш-тегів. Якщо рядок ключа містить відкриваючу фігурну дужку `{`, парсер ядра Redis шукає першу наступну закриваючу фігурну дужку `}`. Якщо між дужками є хоча б один символ, функція `CRC16` обчислюється виключно від підрядка всередині дужок, а решта назви ключа ігнорується:

1. **Одиночний ключ без дужок**: у ключі `user:100:profile` гешується весь рядок. Ключ потрапляє у випадковий слот відповідно до свого повного імені.
2. **Ко-локація сутностей одного користувача**: для ключів `{user:100}:profile`, `{user:100}:orders` та `{user:100}:cart` алгоритм виділяє підрядок `user:100`. Оскільки підрядок ідентичний, усі три ключі гарантовано отримують однаковий номер слота і зберігаються на одному фізичному Master-вузлі.
3. **Крайовий випадок порожніх дужок**: у ключі `user:{}:data` між дужками немає символів. Парсер розпізнає такий тег як невалідний і обчислює хеш від повного рядка `user:{}:data`.
4. **Крайовий випадок вкладених дужок**: у ключі `order:{{123}}:meta` алгоритм бере підрядок від першої відкритої дужки до першої закритої, тобто `{123`.

## 2. Коди помилок та протокол редиректів

Оскільки клієнтські додатки спілкуються з вузлами кластера напряму, періодично виникає ситуація, коли запит потрапляє на вузол, який не обслуговує слот цього ключа. Це трапляється через застарівання локальної карти слотів у клієнта, зміну топології після аварії майстра або під час динамічного перерозподілу даних.

Замість самостійного проксіювання запиту на правильний сервер (що створило б додатковий мережевий стрибок і приховало б зміну топології), вузол Redis повертає клієнту спеціальну помилку протоколу RESP з інструкцією перенаправлення.

### Редирект `-MOVED`: постійна зміна топології

Помилка `-MOVED` означає, що запитаний слот постійно і безповоротно закріплений за іншим Master-вузлом.

```text
Формат повідомлення:
  -MOVED <slot_id> <target_ip>:<target_port>

Приклад обміну кадрами:
  Клієнт ➔ Вузол 10.0.0.1:6379: GET user:42
  Вузол  ➔ Клієнт:              -MOVED 5462 10.0.0.2:6379
```

Отримавши код `-MOVED`, клієнтський драйвер зобов'язаний виконати наступну послідовність дій:
1. Зафіксувати зміну конфігурації у своїй локальній таблиці маршрутизації (Slot Map), перезаписавши адресу власника для слота `5462` на `10.0.0.2:6379`.
2. Знайти або відкрити постійне TCP-з'єднання з новим сервером `10.0.0.2:6379`.
3. Повторити вихідну команду `GET user:42` за новою адресою.
4. Усі наступні команди для ключів із цього ж слота клієнт надалі надсилатиме одразу на вузол `10.0.0.2`, усуваючи повторні редиректи.

### Редирект `-ASK`: тимчасовий стан під час міграції

Помилка `-ASK` повертається виключно під час виконання процедури динамічної міграції слота (Resharding) між двома серверами. У цьому стані частина ключів слота вже фізично перенесена на новий вузол, але частина ще залишається на старому, тому слот ще не переданий у повне володіння новому майстру.

```text
Формат повідомлення:
  -ASK <slot_id> <target_ip>:<target_port>

Приклад обміну кадрами:
  Клієнт ➔ Вузол 10.0.0.1:6379 (Source): GET user:99
  Вузол  ➔ Клієнт:                       -ASK 12000 10.0.0.3:6379
```

Обробка редиректу `-ASK` кардинально відрізняється від `-MOVED`:
1. Клієнт **не має права змінювати** свою постійну локальну карту слотів, оскільки для інших ключів цього ж слота запити все ще повинні надходити на вихідний вузол `10.0.0.1`.
2. Клієнт тимчасово підключається до вузла `10.0.0.3:6379`.
3. Першою командою клієнт надсилає спеціальний одноразовий прапорець `ASKING`. Ця преамбула змушує вузол `10.0.0.3` одноразово обслужити наступну команду для слота, який знаходиться у стані імпорту (`IMPORTING`).
4. Одразу за преамбулою надсилається цільова команда `GET user:99`.
5. Якщо надіслати `GET user:99` на вузол `10.0.0.3` без команди `ASKING`, цей вузол відхилить запит і поверне зворотний редирект `-MOVED 12000 10.0.0.1:6379`, створивши нескінченний цикл маршрутизації.

### Специфічні кластерні коди помилок

- **`-TRYAGAIN`**: повертається, якщо цільовий ключ наразі заблокований системним процесом перенесення даних (наприклад, виконується команда `MIGRATE`). Клієнт повинен зробити паузу в 10–50 мілісекунд і повторити запит.
- **`-CROSSSLOT`**: виникає, коли команда оперує кількома ключами, які належать до різних геш-слотів (наприклад, `MGET keyA keyB`). Розробник зобов'язаний або об'єднати ключі за допомогою геш-тегу `{...}`, або розбити операцію на незалежні паралельні запити.
- **`-CLUSTERDOWN`**: свідчить про аварію кластера. Помилка виникає, якщо більше половини Master-вузлів недоступні, або якщо хоча б один із 16 384 слотів не закріплений за жодним живим вузлом (при конфігурації `cluster-require-full-coverage yes`).

## 3. Процедура динамічної міграції слотів (Resharding Protocol)

Перенесення слота з вузла `A` на вузол `B` без зупинки обслуговування трафіку вимагає суворої координації через спеціальні команди керування станом:

1. **Ініціалізація імпорту на вузлі-приймачі**: керуюча утиліта відправляє команду `CLUSTER SETSLOT <slot> IMPORTING <node_A_id>` на вузол `B`. Вузол `B` переходить у стан готовності приймати ключі цього слота та відповідати на запити клієнтів із преамбулою `ASKING`.
2. **Ініціалізація міграції на вузлі-джерелі**: команда `CLUSTER SETSLOT <slot> MIGRATING <node_B_id>` відправляється на вузол `A`. Вузол `A` продовжує обслуговувати ключі, які ще є в його пам'яті, але на всі запити щодо вже перенесених ключів повертає клієнтам код `-ASK`.
3. **Поетапне атомарне перенесення ключів**:
   - Утиліта запитує пачку ключів: `CLUSTER GETKEYSINSLOT <slot> 100`.
   - Для кожного отриманого масиву ключів викликається блокуюча команда міграції:
     `MIGRATE <node_B_ip> <node_B_port> "" 0 5000 KEYS key1 key2 ...`
   - Команда `MIGRATE` серіалізує структури даних у бінарний потік RDB, передає його по TCP на вузол `B`, чекає на підтвердження успішного збереження і лише після цього атомарно видаляє ключі з пам'яті вузла `A`.
4. **Фіналізація та оголошення нового власника**: після того як утиліта перенесла всі ключі, вона розсилає команду `CLUSTER SETSLOT <slot> NODE <node_B_id>` усім вузлам кластера. Стан міграції скидається, і вузол `B` стає єдиним законним власником слота.

## 4. Команди адміністрування та моніторингу кластера

Керування топологією кластера, додавання нових машин та перемикання реплік здійснюється через набір команд `CLUSTER *`:

### Команда CLUSTER SLOTS

Основна команда, яку викликає кожен клієнтський драйвер під час ініціалізації з'єднання. Вона повертає оптимізований масив діапазонів слотів із зазначенням IP-адрес, портів та унікальних 160-бітних SHA1-ідентифікаторів Master-вузлів та всіх їхніх реплік.

Клієнт розбирає цю відповідь і будує в оперативній пам'яті плоский масив із 16 384 покажчиків на відповідні пули сокетів, що забезпечує миттєвий вибір сокета за `O(1)`.

### Команда CLUSTER NODES

Повертає повний текстовий звіт про стан кластера у форматі, де кожен рядок описує один вузол:
- Унікальний 40-символьний ідентифікатор Node ID.
- IP-адреса, клієнтський порт та порт кластерної шини (наприклад, `10.0.0.1:6379@16379`).
- Бітові прапорці ролі: `myself` (поточний вузол), `master` (провідний вузол), `slave` (репліка), `fail` (підтверджена відмова), `fail?` (стан підозри на відмову PFAIL).
- Node ID майстра, якщо цей вузол є веденою реплікою.
- Час останньої відправки PING та отримання PONG у мілісекундах Epoch.
- Локальна епоха конфігурації (Config Epoch), що використовується алгоритмом консенсусу для вирішення конфліктів версій.
- Стан зв'язку (`connected` або `disconnected`).
- Список закріплених за вузлом діапазонів слотів і стан міграції (наприклад, `0-5460 [12000->-node_B_id]`).

### Команди керування життєвим циклом вузла

- `CLUSTER MEET <ip> <port>`: змушує поточний вузол ініціювати TCP-підключення до вказаного сервера та почати процедуру рукостискання (Handshake). Після цього новий сервер інтегрується в загальну мережу пліток.
- `CLUSTER FORGET <node_id>`: видаляє вузол із таблиць кластера на 60 секунд, запобігаючи його повторній автореєстрації через пакети пліток від сусідів.
- `CLUSTER REPLICATE <master_node_id>`: переводить поточний вузол у режим репліки вказаного майстра з автоматичним запуском первинної реплікації (Full Sync).
- `CLUSTER FAILOVER [FORCE|TAKEOVER]`: ручне перемикання репліки в роль нового майстра. Режим `FORCE` виконує перемикання без попереднього узгодження з поточним майстром, а `TAKEOVER` здійснює захоплення лідерства без збору кворуму голосів інших майстрів (використовується для аварійного відновлення між дата-центрами).

## 5. RESP3 Client-Side Tracking (Кешування на стороні клієнта)

Протокол Redis 6.0 (RESP3) впровадив стандартизований асиметричний механізм відстеження ключів, який дозволяє клієнтам безпечно кешувати дані в локальній пам'яті процесу (L1 Near-Cache), повністю довіряючи серверу сповіщення про зміну або видалення цих значень.

### Режими відстеження

Активація механізму виконується командою:

```text
CLIENT TRACKING on|off [REDIRECT client_id] [PREFIX prefix] [BCAST] [OPTIN] [OPTOUT] [NOLOOP]
```

1. **Режим відстеження за замовчуванням (Default Mode)**:
   - Сервер зберігає глобальну геш-таблицю відстеження (Invalidation Table), де кожному зчитаному ключу співставляється список числових ID активних TCP-з'єднань, які його запитували.
   - Коли будь-який клієнт змінює значення ключа (`SET`, `INCR`, `DEL`, `EXPIRE`), сервер надсилає асинхронний push-кадр інвалідації всім клієнтам зі списку, після чого видаляє запис із таблиці.
   - Для захисту від переповнення пам'яті розмір таблиці обмежений параметром `tracking-table-max-keys`. У разі переповнення сервер примусово скидає випадкові ключі, надсилаючи інвалідаційні повідомлення.

2. **Широкомовний режим (Broadcast Mode / BCAST)**:
   - Сервер взагалі не зберігає стан по кожному окремому ключу, заощаджуючи пам'ять.
   - Клієнт реєструє підписку на один або кілька префіксів простору імен:
     `CLIENT TRACKING on BCAST PREFIX user: PREFIX catalog:`
   - Будь-яка зміна будь-якого ключа, що починається з зареєстрованого префікса, автоматично генерує сповіщення для всіх широкомовних клієнтів. Сервер використовує префіксні дерева (Radix Tree) для зіставлення імен за частки мікросекунди.

### Структура кадру інвалідації в протоколі RESP3

Повідомлення про інвалідацію передається як асинхронний push-тип даних протоколу RESP3 (позначається символом `>`):

```text
Формат бінарного кадру:
  >2\r\n
  $10\r\n
  invalidate\r\n
  *1\r\n
  $15\r\n
  user:42:profile\r\n

Аналіз полів кадру:
  >2           ➔ Push-масив із двох елементів.
  $10          ➔ Рядок типу повідомлення довжиною 10 байтів.
  invalidate   ➔ Назва системної події інвалідації.
  *1           ➔ Масив імен ключів, які стали недійсними.
  $15          ➔ Довжина рядка ключа.
  user:42:profile
```

Якщо сталася масова інвалідація або внутрішнє переповнення таблиць сервера, замість списку конкретних ключів масив містить єдиний елемент `nil` (`$-1\r\n`), що слугує для клієнта сигналом повного очищення (Flush) усього локального кешу L1.

## 6. Бінарний протокол кластерної шини (Cluster Bus)

Вузли кластера підтримують постійні повнодуплексні TCP-з'єднання через окремий порт шини `ClientPort + 10000` (наприклад, 16379). Обмін станом відбувається через децентралізований протокол пліток (Gossip Protocol).

Кожні 100 мілісекунд кожен вузол випадковим чином обирає кілька інших вузлів і відправляє бінарний пакет `PING`, очікуючи у відповідь пакет `PONG`. У кожному повідомленні передається заголовок із повним станом поточного вузла та випадкова вибірка інформації про стан інших відомих йому учасників кластера.

### Бінарна структура повідомлення ClusterMsg

:::tabs
```c
typedef struct {
    char sig[4];                  /* Сигнатура протоколу: "RCmb" (Redis Cluster message bus) */
    uint32_t totlen;              /* Загальна довжина пакета в байтах */
    uint16_t ver;                 /* Версія протоколу кластера (1) */
    uint16_t port;                /* Базовий TCP-порт клієнтських підключень */
    uint16_t type;                /* Тип повідомлення: PING, PONG, MEET, FAIL, PUBLISH */
    uint16_t count;               /* Кількість вкладених блоків Gossip-секції */
    uint64_t currentEpoch;        /* Поточна глобальна епоха конфігурації */
    uint64_t configEpoch;         /* Епоха конфігурації цього конкретного вузла */
    uint64_t offset;              /* Зсув реплікації (Replication Offset) */
    char sender[40];              /* 160-бітний Node ID відправника */
    unsigned char myslots[2048];  /* Бітова маска з 16384 бітів: слоти, закріплені за вузлом */
    char slaveof[40];             /* Node ID майстра (якщо відправник є реплікою) */
    uint16_t my_ip[16];           /* IP-адреса відправника */

    uint16_t flags;               /* Прапорці вузла: CLUSTER_NODE_MASTER, etc. */

} clusterMsg;
```

Бітова карта `myslots[2048]` містить 16 384 біти. Якщо біт на індексі `k` дорівнює `1`, це означає, що вузол-відправник обслуговує слот `k`.
