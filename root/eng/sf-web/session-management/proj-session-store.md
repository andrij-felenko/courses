# ⚙️ Робочий склад сесій: сховище за інтерфейсом

Модель сесії проста на словах: сервер тримає правду в себе, клієнтові дає номер. Але між «на словах» і «в бою» лежить купа інженерних рішень, кожне з яких, зроблене недбало, перетворює струнку модель на дірку. Де взяти номер, щоб його не вгадали? Куди покласти запис, щоб його підняв будь-який із десятка серверів? Як зробити так, щоб згасання за простоєм і тверда стеля згори не заважали одне одному? Як при виході знищити сесію, а не лише попросити браузер забути cookie? Зберемо це руками — не псевдокод, а робочий склад, який можна взяти й поставити.

Головна думка, навколо якої усе крутиться: **розділити політику й механізм**. Політика — це *що* сесія означає: звідки береться номер, скільки живе, коли міняється, коли вмирає. Механізм — це *де* лежать байти: у `Map` в пам'яті одного процесу чи в спільному Redis на всі сервери. Якщо ці двоє змішати, вийде код, у якому не можна поміняти сховище, не переписавши правила безпеки, і не можна полагодити правило, не зачепивши сховище. Тому між ними ставимо шов — **інтерфейс сховища** з чотирьох операцій: `create`, `lookup`, `rotate`, `destroy`. HTTP-шар і політика знають лише цей інтерфейс; що за ним — `Map` чи Redis — їм байдуже.

![Вертикальний стос шарів: угорі HTTP-шар (login/logout/кожен запит), під ним SessionManager із політикою (номер із CSPRNG, ковзний простій плюс абсолютний строк, ротація на вході, відкликання на виході), під ним інтерфейс Store з чотирьох операцій, а від нього — дві реалізації: Map у пам'яті для розробки й Redis як спільне сховище для продакшену](img/store-layers.svg)

*HTTP-шар і політика бачать лише інтерфейс `Store`. Поміняти реалізацію — з `Map` на Redis — можна, не торкнувшись жодного рядка політики чи обробників: обидва вищі шари не знають, де саме лежать байти.*

## Крок 1: номер, який неможливо вгадати

Номер сесії відмикає обліковий запис цілком, тож він мусить родитися **лише** з криптографічного джерела випадковості — [CSPRNG](topic:sf-security/csprng): генератора, чий наступний вихід неможливо обчислити, навіть маючи багато попередніх. Звичайний `Math.random()`, `rand()` чи будь-який генератор, засіяний часом, тут — готова вразливість: він видає числа за передбачуваним правилом, і, побачивши кілька виданих номерів, зловмисник рахує наступні.

У кожній мові є свій правильний примірник. У Node — `crypto.randomBytes`; у Python — модуль `secrets`. Беремо 18 байтів (144 біти) і кодуємо в `base64url` — це дає короткий ASCII-рядок без символів `+`, `/`, `=`, що безпечно їде в заголовку cookie:

:::tabs
```ts
import { randomBytes } from "node:crypto";

// 18 байтів = 144 біти ентропії; base64url → 24 ASCII-символи, безпечні для cookie
export function newSid(): string {
  return randomBytes(18).toString("base64url");
}
```
```py
import secrets

def new_sid() -> str:
    # 18 байтів ентропії; token_urlsafe одразу віддає готовий ASCII-рядок
    return secrets.token_urlsafe(18)
```
:::

Чому саме 18 байтів, а не 4 і не 64: 144 біти з запасом перекривають практичне правило OWASP (щонайменше 128 біт номера й не менш як 64 біти справжньої ентропії) — стільки, що перебором номер не взяти за жоден розумний час, і водночас рядок лишається коротким. Це той рідкісний випадок, коли «більше» майже нічого не коштує, тож беремо з запасом.

Одну звабу тут варто назвати вголос, бо на ній спотикаються: **не порівнюй номери побайтово й не бійся timing-атаки на сам номер**. У наївних схемах, де секрет звіряють рядок-із-рядком, витік через час порівняння — реальна загроза. Але тут номер — це **ключ** у хеш-таблиці чи в Redis: сховище або знаходить запис за ключем, або ні, і час пошуку не «протікає» посимвольно. Тож жодних порівнянь у сталий час городити не треба — правильна структура даних уже прибрала цей клас атак.

> 🔧 **Навіщо це.** Одне слово — `Math.random()` замість `crypto`/`secrets` — обнуляє всю решту оборони: скільки прапорців ні став на cookie, передбачуваний номер зловмисник просто **обчислить**, нічого не крадучи. Рефлекс: усе, що відмикає доступ, — номери сесій, токени скидання пароля, разові коди — родиться **тільки** з CSPRNG. Побачив «випадковий» ідентифікатор із лічильника чи `Math.random()` — це вже дірка, а не стиль.

## Крок 2: інтерфейс сховища — чотири операції й один запис

Тепер сам шов. Сховище вміє рівно чотири речі, і кожна має точний контракт:

- **`create(userId) → sid`** — завести новий запис із свіжим номером і повернути номер.
- **`lookup(sid) → Session | null`** — підняти запис за номером; якщо його немає або він згас — повернути «нічого». **Усередині цієї ж операції** живуть обидва таймаути: вона ковзає дедлайн простою й перевіряє абсолютну стелю. Це навмисно: якщо звести обидва лічильники в одну точку, ні сховище, ні HTTP-шар не зможуть їх забути.
- **`rotate(sid) → newSid`** — видати запису **новий** номер, ті самі дані лишити, старий номер тієї ж миті вбити. Це серце захисту від фіксації.
- **`destroy(sid)`** — викинути запис. Відкликання — саме це, і саме тому серверні сесії відкличні: досить прибрати запис, і номер миттєво мертвий.

Найчистіше цей контракт виражає Go — інтерфейс там річ першого класу; поруч той самий контракт у TypeScript:

:::tabs
```go
package session

import "time"

type Session struct {
    UserID    string
    CreatedAt time.Time // початок відліку абсолютного строку
}

// Store ховає, ДЕ лежать сесії. Політика (строки, ротація) — вище, над ним.
type Store interface {
    Create(userID string) (sid string, err error)
    Lookup(sid string) (*Session, error)           // nil — немає/згасла; усередині ковзає idle
    Rotate(sid string) (newSid string, err error)  // новий номер, ті самі дані, старий мертвий
    Destroy(sid string) error
}
```
```ts
export interface Session {
  userId: string;
  createdAt: number;                              // мс, початок абсолютного строку
}

export interface Store {
  create(userId: string): Promise<string>;        // → новий sid
  lookup(sid: string): Promise<Session | null>;   // null — немає/згасла; усередині ковзає idle
  rotate(sid: string): Promise<string | null>;    // новий номер, ті самі дані, старий мертвий
  destroy(sid: string): Promise<void>;
}
```
:::

Запис навмисно худий: `userId` — щоб знати, хто це, і `createdAt` — щоб знати, коли впаде абсолютна стеля. Момент останньої дії (для ковзного простою) реалізація тримає по-своєму: у пам'яті — окремим полем, у Redis — це просто TTL самого ключа. Ролі, права, ім'я — усе, що змінюється, — тримати в записі не варто: підняв `userId`, а решту дістав зі свого джерела правди, щоб відкликання ролі спрацьовувало миттєво, а не «до кінця сесії».

Два строки, якими керує політика, задамо константами — тридцять хвилин ковзного простою й дванадцять годин твердої стелі; конкретні числа диктує ризик застосунку (банк — хвилини, форум — доба):

```ts
const IDLE_MS = 30 * 60_000;          // ковзний простій: 30 хв без дії — і сесія гасне
const ABSOLUTE_MS = 12 * 3_600_000;   // тверда стеля: 12 год від входу, хоч би яка активність
```

## Крок 3: реалізація в пам'яті — і пастка, що чигає одразу

Поки сервер один, сховище — це `Map` (чи `dict`) у його пам'яті. Спокуса написати три рядки — «клади в `Map`, діставай із `Map`, видаляй із `Map`» — і піти. І прямо тут причаїлася найтихіша пастка проєкту: **звичайна `Map` не має TTL**. Ніхто сам собою не викине з неї згаслу сесію. Наслідків одразу два, і обидва погані. По-перше, `Map` **тече**: кожен, хто бодай раз зайшов, лишає запис навіки, і пам'ять процесу росте, аж поки його не вб'є OOM. По-друге, згасання за простоєм і абсолютна стеля **не працюють самі** — покинута сесія живе вічно, поки хтось не подивиться на її дату.

Ліки — двошарові. **Ліниве згасання**: `lookup` сам перевіряє обидва строки й викидає запис, якщо той протух, — так мертвий номер ніколи не пройде, навіть якщо його ще не підмели. І **періодичне прибирання** (sweep): раз на хвилину пробігтися й викинути протухлі, щоб `Map` не роздувалася від сесій, на які ніхто вже не дивиться. Разом вони й дають те, що в Redis робить сам движок:

:::tabs
```ts
import { randomBytes } from "node:crypto";

type Rec = { userId: string; createdAt: number; lastSeen: number };

export class MemoryStore implements Store {
  private map = new Map<string, Rec>();

  constructor() {
    // без прибирання Map тече, а згаслі сесії живуть далі — тож підмітаємо
    setInterval(() => this.sweep(), 60_000).unref();
  }

  async create(userId: string): Promise<string> {
    const sid = randomBytes(18).toString("base64url");
    const now = Date.now();
    this.map.set(sid, { userId, createdAt: now, lastSeen: now });
    return sid;
  }

  async lookup(sid: string): Promise<Session | null> {
    const r = this.map.get(sid);
    if (!r) return null;
    const now = Date.now();
    if (now - r.lastSeen > IDLE_MS || now - r.createdAt > ABSOLUTE_MS) {
      this.map.delete(sid);              // згасла за простоєм АБО впала абсолютна стеля
      return null;
    }
    r.lastSeen = now;                     // ковзання: посунули дедлайн простою вперед
    return { userId: r.userId, createdAt: r.createdAt };
  }

  async rotate(sid: string): Promise<string | null> {
    const r = this.map.get(sid);
    if (!r) return null;
    const next = randomBytes(18).toString("base64url");
    this.map.set(next, { ...r, lastSeen: Date.now() });
    this.map.delete(sid);                 // старий номер мертвий тієї ж миті
    return next;
  }

  async destroy(sid: string): Promise<void> {
    this.map.delete(sid);                 // відкликання — просто викидаємо запис
  }

  private sweep(): void {
    const now = Date.now();
    for (const [sid, r] of this.map)
      if (now - r.lastSeen > IDLE_MS || now - r.createdAt > ABSOLUTE_MS)
        this.map.delete(sid);
  }
}
```
```py
import secrets, time, threading

IDLE_S = 30 * 60          # ковзний простій: 30 хв
ABSOLUTE_S = 12 * 3600    # тверда стеля: 12 год

class MemoryStore:
    def __init__(self) -> None:
        self._map: dict[str, dict] = {}
        self._lock = threading.Lock()      # кілька потоків можуть лізти водночас

    def create(self, user_id: str) -> str:
        sid = secrets.token_urlsafe(18)
        now = time.time()
        with self._lock:
            self._map[sid] = {"user_id": user_id, "created_at": now, "last_seen": now}
        return sid

    def lookup(self, sid: str) -> dict | None:
        now = time.time()
        with self._lock:
            r = self._map.get(sid)
            if r is None:
                return None
            if now - r["last_seen"] > IDLE_S or now - r["created_at"] > ABSOLUTE_S:
                del self._map[sid]         # згасла за простоєм АБО впала абсолютна стеля
                return None
            r["last_seen"] = now           # ковзання
            return {"user_id": r["user_id"], "created_at": r["created_at"]}

    def rotate(self, sid: str) -> str | None:
        with self._lock:
            r = self._map.pop(sid, None)   # старий номер мертвий тієї ж миті
            if r is None:
                return None
            nxt = secrets.token_urlsafe(18)
            r["last_seen"] = time.time()
            self._map[nxt] = r
            return nxt

    def destroy(self, sid: str) -> None:
        with self._lock:
            self._map.pop(sid, None)

    def sweep(self) -> None:               # кликати періодично (напр., раз на хвилину)
        now = time.time()
        with self._lock:
            dead = [s for s, r in self._map.items()
                    if now - r["last_seen"] > IDLE_S or now - r["created_at"] > ABSOLUTE_S]
            for s in dead:
                del self._map[s]
```
:::

Ця реалізація чудова для розробки й тестів, але має вбудовану стелю: щойно серверів стане більше одного, `Map` у пам'яті кожного з них перестане бачити сесії сусіда. Тому наступний крок — той самий інтерфейс, але поверх спільного сховища.

## Крок 4: реалізація на Redis — коли серверів багато

Коли за [балансувальником](topic:sf-distributed/load-balancing) стоїть кілька серверів, сесії треба винести туди, звідки їх підніме будь-який із них, — у [спільний швидкий кеш](topic:sf-distributed/distributed-cache) на кшталт Redis. Той самий інтерфейс, інша начинка — і жоден вищий шар не помітить підміни. Redis тут дарує головне даром: **власний TTL на ключі**. Ковзний простій — це просто TTL ключа сесії, який ми освіжаємо на кожному `lookup`; коли TTL спливе, Redis сам викине ключ — жодних прибирань руками.

Абсолютна стеля хитріша, і саме на ній народжується показова помилка. Спокуса: закодувати абсолют теж через TTL. Але ж ми **ковзаємо** TTL на кожному запиті — і кожне ковзання зсуває стелю вперед, тож у активного користувача сесія стає **безсмертною**, а абсолютний строк випаровується. Тому абсолют мусить жити **окремим полем** `createdAt` у самому записі, а ковзання — бути **обмеженим** цим полем: новий idle-TTL ніколи не проб'є абсолютну стелю. Одна ця перевірка — `min(idle, абсолют − now)` — і робить два лічильники по-справжньому незалежними.

:::tabs
```ts
import { randomBytes } from "node:crypto";
import type Redis from "ioredis";

const KEY = (sid: string) => `sess:${sid}`;
const IDLE_S = 30 * 60;
const ABSOLUTE_S = 12 * 3600;

export class RedisStore implements Store {
  constructor(private redis: Redis) {}

  async create(userId: string): Promise<string> {
    const sid = randomBytes(18).toString("base64url");
    const value = JSON.stringify({ userId, createdAt: Date.now() });
    // NX — на випадок (астрономічно рідкої) колізії; EX — idle-TTL одразу на ключі
    await this.redis.set(KEY(sid), value, "EX", IDLE_S, "NX");
    return sid;
  }

  async lookup(sid: string): Promise<Session | null> {
    const raw = await this.redis.get(KEY(sid));
    if (!raw) return null;                       // ключа немає — Redis уже згасив за idle
    const s: Session = JSON.parse(raw);
    const absLeft = s.createdAt / 1000 + ABSOLUTE_S - Date.now() / 1000;
    if (absLeft <= 0) {                          // впала абсолютна стеля
      await this.redis.del(KEY(sid));
      return null;
    }
    // ковзання, ОБМЕЖЕНЕ абсолютом: idle ніколи не проб'є стелю
    await this.redis.expire(KEY(sid), Math.floor(Math.min(IDLE_S, absLeft)));
    return s;
  }

  async rotate(sid: string): Promise<string | null> {
    const next = randomBytes(18).toString("base64url");
    // атомарно одним скриптом: прочитати, покласти під новим ключем, знищити старий
    const ok = await this.redis.eval(ROTATE_LUA, 2, KEY(sid), KEY(next), String(IDLE_S));
    return ok ? next : null;
  }

  async destroy(sid: string): Promise<void> {
    await this.redis.del(KEY(sid));              // відкликання — один DEL
  }
}

// KEYS[1] старий ключ, KEYS[2] новий, ARGV[1] idle-TTL
const ROTATE_LUA = `
  local v = redis.call('GET', KEYS[1])
  if not v then return nil end
  redis.call('SET', KEYS[2], v, 'EX', ARGV[1])
  redis.call('DEL', KEYS[1])
  return 1`;
```
```py
import secrets, time, json
import redis

IDLE_S = 30 * 60
ABSOLUTE_S = 12 * 3600

_ROTATE = """
local v = redis.call('GET', KEYS[1])
if not v then return nil end
redis.call('SET', KEYS[2], v, 'EX', ARGV[1])
redis.call('DEL', KEYS[1])
return 1
"""

class RedisStore:
    def __init__(self, r: redis.Redis) -> None:
        self._r = r
        self._rotate = r.register_script(_ROTATE)   # Lua — атомарний rotate

    def _key(self, sid: str) -> str:
        return f"sess:{sid}"

    def create(self, user_id: str) -> str:
        sid = secrets.token_urlsafe(18)
        value = json.dumps({"user_id": user_id, "created_at": time.time()})
        self._r.set(self._key(sid), value, ex=IDLE_S, nx=True)
        return sid

    def lookup(self, sid: str) -> dict | None:
        raw = self._r.get(self._key(sid))
        if raw is None:
            return None                              # ключа немає — Redis згасив за idle
        s = json.loads(raw)
        abs_left = s["created_at"] + ABSOLUTE_S - time.time()
        if abs_left <= 0:
            self._r.delete(self._key(sid))           # впала абсолютна стеля
            return None
        self._r.expire(self._key(sid), int(min(IDLE_S, abs_left)))  # ковзання, обмежене абсолютом
        return s

    def rotate(self, sid: str) -> str | None:
        nxt = secrets.token_urlsafe(18)
        ok = self._rotate(keys=[self._key(sid), self._key(nxt)], args=[IDLE_S])
        return nxt if ok else None

    def destroy(self, sid: str) -> None:
        self._r.delete(self._key(sid))
```
:::

*Уся політика строків зведена в одну операцію. `lookup` — це «мозок» сховища: idle живе як TTL ключа, що ковзає за кожним зверненням, а абсолют — як поле `createdAt`, що обмежує це ковзання. Два лічильники, одна точка рішення — тож жоден шар вище не має шансу забути котрийсь.*

Два робочі нюанси, які видно лише коли пишеш це руками. Перший: у `lookup` ми ходимо в Redis двічі — `GET`, потім `EXPIRE`. Redis дає команду `GETEX` (з версії 6.2), що зливає читання й оновлення TTL в **одну атомарну** операцію — ідеально для ковзних сесій. Але освіжити треба не «на повний idle», а на `min(idle, абсолют − now)`, а щоб узяти цей мінімум, спершу треба прочитати `createdAt`. Тож коли абсолют обмежує ковзання, чесніший саме `GET` + `EXPIRE`; `GETEX key EX idle` доречний, коли абсолютної стелі нема й ковзаєш на повний простій. Другий: `EXPIRE` на **кожному** запиті — це запис у Redis на кожен запис, і на гарячому шляху воно перетворюється на помітну хвилю записів. Пом'якшення просте — ковзати не завжди, а лише коли TTL уже помітно просів (скажімо, освіжати щонайбільше раз на хвилину); більшість сесій цього навіть не помітить, а записів меншає в рази.

## Крок 5: політика зверху — вхід міняє номер, вихід гасить правду

Сховище готове; лишається натягти на нього два обробники, у яких і живе решта безпеки. **Вхід** — це не просто «створити сесію». Якщо з запитом уже приїхав чийсь номер (анонімний або підсунутий зловмисником), його треба **вбити** й видати цілком свіжий — це ротація в найсильнішій формі: не просто новий ключ, а новий запис із чистим відліком абсолютного строку. Саме так велить канон безпеки (OWASP): на кожній зміні рівня прав, і насамперед — на вході, старий номер знищити, новий видати, щоб підсунута копія після входу вже нічого не відмикала.

```ts
// ВХІД: перевірили пароль → знищили те, що приїхало → видали свіжий номер
async function login(req, res, username: string, password: string) {
  const user = await verifyPassword(username, password);   // автентифікація
  if (!user) return res.status(401).end();

  const incoming = parseCookie(req.headers.cookie).sid;
  if (incoming) await store.destroy(incoming);   // ротація: старий номер тепер мертвий
  const sid = await store.create(user.id);       // новий запис, чистий відлік строку

  res.setHeader("Set-Cookie",
    `sid=${sid}; HttpOnly; Secure; SameSite=Lax; Path=/`);
}

// ВИХІД: спершу гасимо ПРАВДУ у сховищі, і лише потім прибираємо cookie
async function logout(req, res) {
  const sid = parseCookie(req.headers.cookie).sid;
  if (sid) await store.destroy(sid);             // запис мертвий → номер нічого не варт
  res.setHeader("Set-Cookie",
    `sid=; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=0`);
}
```

Форма цих обробників однакова в будь-якому фреймворку й будь-якій мові — важлива не мова, а порядок дій: на вході спершу `destroy` вхідного номера, тоді `create`; на виході спершу `destroy` у сховищі, і лише потім чистка cookie. А `rotate` з інтерфейсу лишається для випадків, коли сесія триває, але рівень прав змінився серед сеансу, — увімкнув режим адміністратора, підвищив собі роль: там запис треба зберегти, а номер під ним — поміняти.

> 🔧 **Навіщо це.** Вихід, який лише стирає cookie, — не вихід, а ілюзія. Запис у сховищі живий, і хто встиг переписати номер собі, той і далі заходить як ти, хоч ти вже «вийшов». Правило залізне: **гаси правду там, де вона лежить** — спершу `destroy` у сховищі, cookie прибираєш другою дією. Те саме на вході навпаки: спершу вбий той номер, що приїхав, і тільки тоді видавай новий.

## Складність і пастки

Уся арифметика тут дешева, і це не випадковість, а наслідок того, що номер — це **ключ**. `create`, `lookup`, `rotate`, `destroy` — усі O(1): пошук за ключем у хеш-таблиці чи в Redis, без обходів і сканів. Пам'ять — O(активних сесій), і саме тому прибирання протухлих не косметика, а те, що тримає її обмеженою. Найтонше тут те, що сховище **саме є списком відкликання**: щоб погасити сесію, досить одного `DEL` — на відміну від підписаного [токена без стану (JWT)](topic:sf-web/jwt-tokens), який доводиться відкликати окремим чорним списком, бо самого запису на сервері нема.

А тепер пастки — кожна вже названа по ходу, зведімо їх докупи, бо саме на них найчастіше й ламаються:

- **Вихід лише стирає cookie.** Найпоширеніша й найтихіша: `logout`, що ставить `Max-Age=0` на cookie, але не чіпає запису у сховищі. Сесія жива, украдений заздалегідь номер працює далі. Лік — `destroy` **у сховищі** першою дією.

```ts
// ✗ ПАСТКА: «вихід», що лишає сесію живою у сховищі
async function logoutBroken(req, res) {
  res.setHeader("Set-Cookie", "sid=; Max-Age=0");   // запис у Redis НЕ чіпнуто — сесія жива
}
```

- **Номер переживає вхід.** Якщо на вході не вбити той номер, що приїхав, а лишити його ж і просто дописати `userId`, — це відчинені двері для фіксації: підсунутий жертві номер після входу стає повноправним. Лік — на вході завжди `destroy` старого + `create` нового.

- **Нема TTL у сховищі.** `Map` без прибирання тече й тримає згаслі сесії вічно; ключ у Redis, покладений без `EX`, — те саме, тільки ще й переживе перезапуск. Лік — TTL/прибирання **на рівні сховища**, а не «колись потім у крон-задачі».

- **Абсолют закодований як TTL, а не як поле.** Якщо абсолютну стелю тримати самим лише TTL ключа й водночас ковзати той TTL — активна сесія стає безсмертною. Лік — абсолют як поле `createdAt`, ковзання обмежене через `min(idle, абсолют − now)`.

- **Ротація не атомарна.** «Прочитати старий → записати новий → видалити старий» трьома окремими походами в Redis має вікно, де паралельний запит або збій лишить два живі номери чи нуль. Лік — зробити всі три кроки одним Lua-скриптом (або `MULTI`), як вище.

- **Ковзання пише на кожному запиті.** `EXPIRE` щоразу — це хвиля записів у Redis на гарячому шляху. Лік — освіжати TTL не завжди, а лише коли він помітно просів.

Склад зібрано: номер із CSPRNG, за ним інтерфейс із чотирьох операцій, дві реалізації під однаковим контрактом, обидва строки зведені в один `lookup`, вхід міняє номер, вихід гасить правду. Поміняти `Map` на Redis, додати третю реалізацію на іншій базі, підкрутити строки під ризик застосунку — усе це тепер локальні правки за швом, а не переписування безпеки з нуля. Саме заради цього шва все й розділяли на політику й механізм.
