# 🧮 Нерівномірність навантаження і ймовірність відмови за сесійної прив'язки

Коли системний архітектор обирає між сесійною прив'язкою до оперативної пам'яті окремих вузлів (stateful sticky affinity) та повністю бездержавним пулом із зовнішнім сховищем (stateless shared store), інженерний вибір спирається на точні кількісні характеристики.

Ці характеристики вимірюються шістьма строгими математичними моделями:
1. Дисперсією навантаження між вузлами в умовах важких хвостів Парето;
2. Максимальною довжиною черги за теоремою про вибір із двох випадкових альтернатив;
3. Радіусом руйнування відмови та ймовірністю безповоротної втрати користувацького стану;
4. Бюджетом мережевих затримок, пропускної здатності та оптимізацією ковзного поновлення TTL;
5. Математикою накладних витрат клієнтських шифрованих cookie;
6. Ймовірністю колізій і гонок паралельних запитів клієнта.

Нижче наведено математичні виведення та числові розрахунки для кластера з `N` обчислювальних вузлів та `U` активних користувацьких сесій.

## 1. Розподіл сесій і важкі хвости активності користувачів

У веб-системах активність користувачів ніколи не підпорядковується симетричному нормальному розподілу. Тривалість сесії, кількість переглянутих сторінок та частота запитів описуються степеневим розподілом Парето з «важким хвостом»:

```
P(X > x) = (x_min / x)^α
```
де `x_min` — мінімальний поріг тривалості сесії (наприклад, 1 хвилина), а показник форми `α` для веб-трафіку зазвичай перебуває в діапазоні `1.1 ≤ α ≤ 1.6`.

Обчислимо математичне сподівання та дисперсію для випадкової величини `X` з розподілом Парето:

```
E[X]
= (α · x_min) / (α − 1)                    [математичне сподівання розподілу Парето за умови α > 1]
```

Для дисперсії маємо вираз:

```
Var(X)
= (α · x_min²) / ((α − 1)² · (α − 2))       [дисперсія розподілу Парето за умови α > 2]
```

Зверніть увагу на знаменник `α − 2`: якщо показник `α ≤ 2` (що є стандартом для користувацького трафіку веб-сайтів), теоретична дисперсія навантаження окремої сесії прямує до нескінченності. Це означає, що в системі завжди присутня частка «надважких» сесій (пошукові боти, парсери цін, корпоративні користувачі з тисячами автоматизованих дій), які генерують на кілька порядків більше запитів, ніж звичайний користувач.

### Дисперсія навантаження за бездержавної моделі (Stateless)

За бездержавної архітектури балансувальник навантаження не прив'язує користувача до конкретного сервера, а маршрутизує кожен окремий HTTP-запит незалежно за алгоритмом `Round-Robin` або `Least-Connections`.

Нехай сумарний вхідний потік запитів до системи є пуассонівським процесом з інтенсивністю `λ` (запитів за секунду). Тоді вхідний потік на кожен із `N` однакових вузлів становить:

```
λ_i
= λ / N                                    [інтенсивність вхідного потоку на один вузол]
```

Кількість запитів `k`, що надійшли на вузол за довільний інтервал часу `t`, має розподіл Пуассона з параметром `μ_k = λ_i · t`. Обчислимо математичне сподівання та дисперсію кількості запитів:

```
E[k_stateless]
= (λ · t) / N                              [математичне сподівання пуассонівського процесу]

Var(k_stateless)
= (λ · t) / N                              [властивість пуассонівського розподілу: дисперсія дорівнює математичному сподіванню]
```

Обчислимо відносне стандартне відхилення (коефіцієнт варіації навантаження `CV`), що показує рівень нерівномірності завантаження серверів:

```
CV_stateless
= σ / μ                                    [означення коефіцієнта варіації]
= √( (λ · t) / N ) / ( (λ · t) / N )       [підстановка стандартного відхилення і середнього]
= 1 / √( (λ · t) / N )                     [спрощення алгебраїчного дробу]
```

Для високонавантаженої системи (наприклад, `λ = 10 000` запитів/с, `N = 10` вузлів, інтервал спостереження `t = 10` секунд, тобто `(λ · t) / N = 10 000` запитів на вузол):

```
CV_stateless
= 1 / √(10 000)                            [підстановка числових параметрів]
= 1 / 100                                  [добування квадратного кореня]
= 0.01                                     [відносне відхилення навантаження становить лише 1%]
```

Це доводить, що за бездержавної схеми навантаження розподіляється між усіма вузлами кластера практично ідеально рівномірно.

### Дисперсія навантаження за сесійної прив'язки (Sticky Sessions)

За сесійної прив'язки балансувальник розподіляє між вузлами не окремі запити, а неподільні сесії цілком. Нехай `U` сесій випадково розподіляються між `N` вузлами. Кожна окрема сесія `j` генерує за інтервал спостереження випадкову кількість запитів `W_j` з математичним сподіванням `E[W]` та дисперсією `Var(W)`.

Кількість сесій `K`, закріплених за одним вузлом, є випадковою величиною з біноміальним розподілом `Bin(U, 1/N)`:

```
E[K]
= U / N                                    [математичне сподівання кількості сесій на вузлі]

Var(K)
= U · (1 / N) · (1 − 1 / N)                [дисперсія біноміального розподілу]
= (U · (N − 1)) / N²                       [алгебраїчне спрощення виразу]
```

Сумарне навантаження на вузол `L_i` є випадковою сумою випадкової кількості доданків `L_i = ∑_{j=1}^{K} W_j`. За формулою повної дисперсії (теоремою Івніса — Бруно):

```
Var(L_sticky)
= E[K] · Var(W) + (E[W])² · Var(K)         [формула повної дисперсії для випадкової суми випадкових величин]
= (U / N) · Var(W) + (E[W])² · ( (U · (N − 1)) / N² ) [підстановка параметрів біноміального розподілу K]
```

Оскільки через важкі хвости Парето величина `Var(W)` на порядки перевищує `(E[W])²`, перший доданок `(U / N) · Var(W)` повністю домінує. Дисперсія навантаження вузлів за сесійної прив'язки в сотні разів перевищує пуассонівську дисперсію бездержавного пулу.

Це створює неминучий ефект «гарячих вузлів» (*hotspots*), коли випадкове потрапляння кількох важких користувачів на один сервер призводить до його локального перевантаження, тоді як сусідні сервери кластера залишаються недовантаженими.

## 2. Теорема про вибір із двох альтернатив і довжина пікової черги

Розглянемо проблему пікового перевантаження найгіршого (найбільш завантаженого) сервера в кластері з `N` машин під час обробки `M` задач.

Згідно з класичною теорією розміщення «кульок у кошиках» та теоремою Міценмахера (Michael Mitzenmacher):

1. **За гешованої або випадкової прив'язки без зворотного зв'язку (Sticky Routing):**
   Коли балансувальник направляє сесію за гешем від IP-адреси або cookie без урахування поточної завантаженості черги вузла, максимальне навантаження на найгіршому сервері кластера масштабується як:
   ```
   Max_Load_sticky
   = (M / N) + √( (2 · M · ln(N)) / N )    [асимптотична оцінка максимального заповнення кошика]
   ```
   Для великих значень `M` це дає суттєві випадкові викиди черги на окремих серверах.

2. **За бездержавного динамічного балансування (Power of Two Random Choices / Least-Connections):**
   Балансувальник вибирає два випадкові вузли кластера, порівнює поточну довжину черги запитів і відправляє новий запит тому вузлу, чия черга коротша. У такому випадку максимальна довжина черги на найгіршому вузлі кластера зменшується до подвійного логарифма:
   ```
   Max_Queue_stateless
   = (ln(ln(N)) / ln(2)) + O(1)            [експоненційне скорочення максимальної черги в системі]
   ```

Для кластера з `N = 100` вузлів:
- За сесійної прив'язки випадковий перекіс створює на окремих серверах черги з десятків запитів.
- За бездержавного вибору з двох найменш завантажених вузлів черга на жодному сервері не перевищує 2–3 запитів за будь-якого загального навантаження.

## 3. Час очікування в черзі за формулою Поллачека — Хінчина

Розглянемо вплив нерівномірності навантаження на час відповіді сервера з точки зору теорії масового обслуговування. Моделюємо кожен обчислювальний вузол як систему `M/G/1` (пуассонівський вхідний потік, довільний розподіл часу обслуговування, один процесорний сервер).

Згідно з формулою Поллачека — Хінчина, середня кількість запитів, що очікують у черзі `L_q`, визначається виразом:

```
L_q
= (ρ² · (1 + C_s²)) / (2 · (1 − ρ))        [формула Поллачека — Хінчина для черги M/G/1]
```
де:
- `ρ = λ_i / μ` — коефіцієнт використання процесорної потужності сервера (`0 ≤ ρ < 1`);
- `μ` — середня пропускна здатність сервера (кількість запитів, які вузол здатний обробити за секунду);
- `C_s = σ_s / μ_s` — коефіцієнт варіації тривалості обробки одного запиту.

За законом Літтла (`L_q = λ_i · W_q`), середній час очікування запиту в черзі `W_q` до початку його фактичного виконання дорівнює:

```
W_q
= L_q / λ_i                                [закон Літтла для часу перебування в черзі]
= (ρ · (1 + C_s²)) / (2 · μ · (1 − ρ))     [підстановка формули Поллачека — Хінчина]
```

Порівняємо два практичні сценарії для сервера з продуктивністю `μ = 200` запитів/с і коефіцієнтом варіації тривалості обробки `C_s = 1`:

**Сценарій 1: Бездержавний збалансований пул (усі сервери завантажені рівномірно на `ρ = 0.70`):**
```
W_q_stateless
= (0.70 · (1 + 1²)) / (2 · 200 · (1 − 0.70)) [підстановка параметрів у формулу]
= (0.70 · 2) / (400 · 0.30)                [обчислення чисельника і знаменника]
= 1.40 / 120                               [ділення чисел]
≈ 0.0117 с                                 [затримка в черзі становить 11.7 мілісекунди]
```

**Сценарій 2: Перевантажений сервер через сесійний перекіс (`ρ = 0.95`):**
```
W_q_hotspot
= (0.95 · (1 + 1²)) / (2 · 200 · (1 − 0.95)) [підстановка критичного завантаження]
= (0.95 · 2) / (400 · 0.05)                [обчислення чисельника і знаменника]
= 1.90 / 20                                [ділення чисел]
= 0.0950 с                                 [затримка в черзі зростає до 95.0 мілісекунд]
```

Зверніть увагу: затримка в черзі на перевантаженому вузлі зросла в `95.0 / 11.7 ≈ 8.12` раза.

Оскільки затримка на 99-му процентилі (`p99 latency`) для експоненційних черг масштабується як `T_p99 ≈ −ln(1 − 0.99) · W_q ≈ 4.6 · W_q`, користувачі «гарячого» вузла стикаються із затримками понад `4.6 · 95 мс ≈ 437 мс`, що призводить до таймаутів у браузері та суб'єктивного відчуття повного зависання інтерфейсу.

## 4. Математика радіуса руйнування відмови (Blast Radius)

Нехай веб-застосунок обслуговує `U = 100 000` активних користувачів, а обчислювальний кластер складається з `N = 10` однакових серверів.

### Випадок 1: Сесії зберігаються в оперативній пам'яті вузлів (Stateful Sticky)

Кожен сервер утримує у своїй локальній пам'яті частку сесій:

```
U_node
= U / N                                    [кількість сесій на одному сервері]
= 100 000 / 10                             [підстановка чисел]
= 10 000 сесій                             [локальний обсяг стану одного вузла]
```

У разі раптового збою заліза, перезавантаження операційної системи чи падіння процесу через вичерпання пам'яті (Out-Of-Memory Killer), ймовірність втрати сесії для довільного користувача становить:

```
P(втрата_сесії)
= 1 / N                                    [частка втраченого стану при падінні одного вузла]
= 1 / 10                                   [підстановка кількості серверів]
= 0.10                                     [10% користувачів втрачають стан]
```

Кількість користувачів, чий сесійний стан (авторизація, кошик, незавершені кроки транзакції) буде безповоротно знищено:

```
ΔU_lost
= U · P(втрата_сесії)                      [розрахунок абсолютної кількості постраждалих]
= 100 000 · 0.10                           [підстановка параметрів]
= 10 000 користувачів                      [пряма втрата бізнес-транзакцій]
```

### Випадок 2: Бездержавний пул із зовнішнім сховищем (Stateless)

Усі сесії виносяться у виділений кластер Redis із фактором реплікації `R = 2` (один основний вузол і один асинхронний реплікат на кожен шард даних). Падіння будь-якого з `N = 10` бездержавних обчислювальних воркерів має такі наслідки:

```
P(втрата_сесії)
= 0                                        [стан повністю ізольований від обчислювального воркера]
```

Кількість втрачених сесій становить строго `ΔU_lost = 0`.

Балансувальник навантаження фіксує падіння вузла за результатами чергової перевірки стану (Health Check) і миттєво перенаправляє наступний HTTP-запит клієнта на будь-який із решти `N − 1 = 9` активних воркерів.

Відносне зростання навантаження на кожен уцілілий сервер кластера становить:

```
ΔLoad
= (N / (N − 1)) − 1                        [формула відносного приросту навантаження]
= (10 / 9) − 1                             [підстановка кількості вузлів]
= 1.111 − 1                                [обчислення коефіцієнта]
≈ +11.1%                                   [безпечний приріст навантаження на уцілілі вузли]
```

## 5. Бюджет мережевої затримки, пропускної здатності та оптимізація TTL

Бездержавна архітектура вимагає додаткових мережевих звернень (network round-trips) до розподіленого сховища сесій. Розрахуємо точну ціну цієї операції для високопродуктивного дата-центру та математику оптимізації ковзного часу життя сесії (Sliding TTL).

### Затримка обробки (Latency Breakdown)

Сумарний час звернення до зовнішнього сховища сесій складається з трьох послідовних фаз:

```
T_session
= T_net_rtt + T_serdes + T_lookup          [структура загальної затримки виклику сесії]
```
де:
- `T_net_rtt` — затримка передачі пакета туди-назад у локальній мережі дата-центру (10GbE / 25GbE мережа з використанням комутаторів прямого пересилання *cut-through switching* дає `0.20–0.40 мс`);
- `T_serdes` — процесорний час серіалізації та десеріалізації сесійного об'єкта розміром 2 КБ за допомогою швидкого парсера JSON або MessagePack (`0.05–0.12 мс`);
- `T_lookup` — час операції читання ключа в оперативній пам'яті Redis (`O(1)` операція в геш-таблиці, зазвичай `0.02–0.04 мс`).

**Розрахунок сумарної затримки:**
```
T_session
= 0.30 мс + 0.08 мс + 0.03 мс              [підстановка типових параметрів production-інфраструктури]
= 0.41 мс                                  [менше половини мілісекунди на весь цикл]
```

Для типового веб-запиту з загальною тривалістю обробки бізнес-логіки `T_request = 40 мс`, частка накладних витрат становить:

```
Overhead_pct
= (T_session / T_request) · 100%           [розрахунок відносних накладних витрат]
= (0.41 мс / 40 мс) · 100%                 [підстановка значень]
= 1.025%                                   [близько одного відсотка від загального бюджету часу]
```

### Пропускна здатність мережевого каналу (Bandwidth Budget)

Нехай система обробляє піковий потік `Q = 10 000` запитів на секунду. Розмір сесійного документа в бінарному представленні становить `S = 2 КБ = 2048 байтів`. На кожен вхідний запит виконується одне читання (2 КБ), а запис оновленого стану виконується лише для модифікуючих операцій (ймовірність модифікації `p_write = 0.30`).

Обчислимо необхідну смугу пропускання мережі між пулом веб-серверів та сховищем Redis:

```
B_total
= Q · (S_read + p_write · S_write)         [формула сумарного мережевого трафіку сесій]
= 10 000 · (2048 + 0.30 · 2048)            [підстановка параметрів навантаження]
= 10 000 · (2048 + 614.4)                  [обчислення обсягу даних на один запит]
= 10 000 · 2662.4                          [множення на частоту запитів]
= 26 624 000 байтів/с                      [точний трафік у байтах за секунду]
= 26.624 МБ/с                              [переведення в мегабайти на секунду]
= 212.992 Мбіт/с                           [переведення в мегабіти на секунду (множення на 8)]
```

Для стандартного оптичного мережевого інтерфейсу `10 Гбіт/с` (`10 000 Мбіт/с`), встановленого на сервері сховища:

```
Util_bandwidth
= (212.992 Мбіт/с / 10 000 Мбіт/с) · 100%  [розрахунок утилізації пропускної здатності каналу]
≈ 2.13%                                    [канал завантажено лише на два відсотки]
```

### Оптимізація ковзного оновлення TTL (Throttled Touch)

Якщо на кожен запит читання відправляти в Redis додаткову команду оновлення часу життя (`EXPIRE sid 1800`), кількість операцій запису в Redis зростає на `100%` (по одній команді `EXPIRE` на кожне читання).

Щоб уникнути цього навантаження, застосовують порогове поновлення: час життя сесії оновлюється лише тоді, коли від попереднього поновлення минуло більше ніж частка `γ` від загального інтервалу `TTL` (зазвичай `γ = 0.20`, тобто 20% від півгодинного тайм-ауту — 6 хвилин).

Обчислимо частку запитів читання `p_touch`, які реально викликатимуть команду `EXPIRE`, якщо користувач робить у середньому `n_req = 15` запитів за 6 хвилин:

```
p_touch
= 1 / n_req                                [частота викликів оновлення TTL]
= 1 / 15                                   [підстановка середньої кількості дій]
≈ 0.0667                                   [лише 6.67% запитів читання оновлюють TTL]
```

Економія кількості операцій запису на кластер Redis становить:

```
Save_writes
= (1 − p_touch) · 100%                     [відсоток скорочення операцій оновлення]
= (1 − 0.0667) · 100%                      [підстановка отриманого значення]
≈ 93.33%                                   [скорочення операцій EXPIRE на 93.3%]
```

## 6. Накладні витрати клієнтських шифрованих сесій (Client-Side Cookies)

Альтернативою зовнішньому сховищу є збереження всього сесійного стану безпосередньо в cookie браузера у зашифрованому та підписаному вигляді (алгоритм автентифікованого шифрування AES-256-GCM або ChaCha20-Poly1305).

Розрахуємо розмір зашифрованого cookie `S_cookie` для корисного навантаження сесії `S_raw = 800 байтів`:
1. Вектор ініціалізації (IV): `12 байтів`;
2. Тег автентифікації GCM: `16 байтів`;
3. Сумарний бінарний шифротекст: `800 + 12 + 16 = 828 байтів`;
4. Кодування Base64URL для передачі в HTTP-заголовку (збільшення розміру на 33.3%): `⌈828 / 3⌉ · 4 = 1104 байти`;
5. Заголовок cookie та метадані (`Cookie: __Host-sess=...; Path=/; Secure; HttpOnly`): `~60 байтів`.

Сумарний розмір заголовка становить `S_header ≈ 1164 байти`.

Обчислимо паразитна витрату зовнішнього інтернет-трафіку для `Q = 10 000` запитів/с:

```
B_client_cookie
= Q · S_header                             [формула додаткового трафіку HTTP-заголовків]
= 10 000 · 1164                            [підстановка значень]
= 11 640 000 байтів/с                      [байти за секунду]
= 11.64 МБ/с                               [мегабайти за секунду]
= 93.12 Мбіт/с                             [мегабіти за секунду вихідного інтернет-каналу]
```

За місяць безперервної роботи цей заголовок генерує:

```
V_monthly
= 11.64 МБ/с · 86 400 с/день · 30 днів     [обчислення місячного обсягу]
≈ 30 170 000 МБ                            [обсяг у мегабайтах]
≈ 30.17 ТБ трафіку                         [понад 30 терабайтів оплачуваного хмарного трафіку лише на заголовки]
```

Це доводить, що клієнтські сесії вигідні лише для компактного стану (< 200 байтів), тоді як для насичених сесій зовнішнє сховище є значно дешевшим і ефективнішим.

## 7. Ймовірність колізій і гонок при паралельних запитах (Race Conditions)

Коли користувач відкриває одночасно кілька вкладок у браузері або сучасний клієнтський SPA-застосунок надсилає фонові асинхронні AJAX/Fetch-запити паралельно, виникає ймовірність того, що два запити від одного користувача будуть оброблятися різними вузлами в один і той самий інтервал часу.

Нехай користувач генерує запити з локальною інтенсивністю `λ_u = 2` запити/с, а тривалість обробки запиту сервером становить `τ = 0.1` с (100 мілісекунд).

За пуассонівською моделлю ймовірність часового перетину виконання двох запитів одного користувача становить:

```
P(перетин_запитів)
= 1 − e^(−λ_u · τ)                         [ймовірність появи наступного запиту за інтервал τ]
= 1 − e^(−2 · 0.1)                         [підстановка значень інтенсивності й тривалості]
= 1 − e^(−0.2)                             [обчислення показника експоненти]
= 1 − 0.8187                               [значення експоненційної функції]
≈ 0.1813                                   [18.13% ймовірність паралельного виконання]
```

Якщо система реалізує неконтрольований перезапис стану (стратегія *Last-Write-Wins*), кожен п'ятий паралельний запит призводить до аномалії втраченого оновлення (*Lost Update*), коли зміни одного запиту безслідно затираються другим запитом.

Запровадження оптимістичного версіонування з операцією Compare-And-Swap (`CAS`):
- Запит 1 зчитує документ з версією `v = 1`, модифікує стан і атомарно записує його з новою версією `v = 2`.
- Запит 2, що зчитав початкову версію `v = 1`, намагається виконати запис з очікуваною версією `1`, але отримує відмову `409 Conflict` (оскільки актуальна версія в сховищі вже `2`).
- Запит 2 перечитує актуальний стан з версією `2`, накладає свою зміну і успішно записує версію `3`.

Завдяки оптимістичному версіонуванню ймовірність незворотної втрати бізнес-даних стає нульовою:

```
P(втрата_даних_CAS)
= 0                                        [повний математичний захист цілісності стану]
```

## 8. Розрахунок потреби в оперативній пам'яті (RAM Footprint)

Визначимо точний обсяг оперативної пам'яті, необхідний для утримання `U_active = 500 000` одночасних сесій у кластері Redis.

Розмір одного запису в пам'яті складається з:
1. Корисного навантаження сесії: `S_payload = 1500 байтів`;
2. Накладних витрат внутрішніх структур Redis (структура `robj`, заголовок `dictEntry`, ключ `sid:32_chars`): `S_overhead = 128 байтів`;
3. Фактора фрагментації пам'яті алокатора jemalloc: `K_frag = 1.25`;
4. Фактора реплікації даних (один основний вузол і один реплікат): `R = 2`.

Розрахунок необхідного обсягу пам'яті кластера:

```
M_cluster_RAM
= U_active · (S_payload + S_overhead) · K_frag · R [формула сумарної оперативної пам'яті]
= 500 000 · (1500 + 128) · 1.25 · 2                [підстановка параметрів]
= 500 000 · 1628 · 2.50                            [обчислення добутку множників]
= 2 035 000 000 байтів                             [значення в байтах]
= 2.035 · 10⁹ байтів                              [експоненційний вигляд]
≈ 1.895 ГБ RAM                                     [переведення в гігабайти (ділення на 1024³)]
```

Для підтримки півмільйона активних користувачів усе сесійне сховище з повним дублюванням репліками займає менше ніж `2 ГБ` оперативної пам'яті, що є мінімальними витратами для сучасних хмарних серверів.

| Характеристика | Сесійна прив'язка (Sticky / In-Memory) | Бездержавний пул (Stateless + Redis) |
|---|---|---|
| Дисперсія навантаження серверів `Var(L)` | Висока (домінує важкий хвіст Парето `Var(W)`) | Мінімальна пуассонівська (`(λ · t) / N`) |
| Максимальна довжина черги `L_q` на піковому вузлі | Зростає у 8–15 разів через локальні перекоси | Знижується до подвійного логарифма завдяки Least-Connections |
| Радіус руйнування відмови (Blast Radius) | `1 / N` (10 000 втрачених сесій на кластері з 10 вузлів) | `0` (стан користувачів повністю збережено у сховищі) |
| Додаткова затримка на запит | `0.00 мс` (розіменування вказівника в пам'яті) | `0.41 мс` (~1% загального часу відповіді) |
| Завантаження каналу 10GbE при 10 000 req/s | `0.00%` | `~2.13%` (незначне навантаження на інфраструктуру) |
| Захист від втрати даних при паралельних вкладках | Вимагає складних блокувань у межах процесу | Забезпечується атомарним CAS-версіонуванням або Redis Lua |
| Пам'ять для 500 000 сесій з реплікацією | Дефрагментована пам'ять кожного процесу | `~1.9 ГБ` у виділеному кластері оперативної пам'яті |
