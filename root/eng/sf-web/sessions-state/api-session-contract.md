# 📋 Контракт бездержавного сесійного сховища та протокол обміну

Цей документ визначає повну формальну специфікацію програмного інтерфейсу, схему бінарного конверта, правила безпечного транспортування через HTTP-заголовки, контракт обробки паралельних гонок, протокол взаємодії з клієнтськими токенами, правила мультирегіональної реплікації та матрицю системних кодів помилок для абстракції бездержавного сесійного сховища (**Stateless Session Store**).

Специфікація стандартизує взаємодію між сервісним шаром веб-бекенда (незалежно від мови програмування та фреймворку) і розподіленими системами зберігання оперативного стану (Redis, Key-Value кластери, NoSQL бази даних).

---

## 1. Архітектурні інваріанти та гарантії контракту

Реалізація сесійного сховища зобов'язана неухильно дотримуватися чотирьох фундаментальних системних інваріантів:

1. **Інваріант взаємозамінності процесів (Share-Nothing Invariant):** Жоден обчислювальний вузол бекенда не має права утримувати локальний стан сесії в оперативній пам'яті процесу між окремими HTTP-запитами. Будь-який запит від будь-якого користувача повинен коректно виконуватися на довільному воркері кластера за наявності валідного сесійного ідентифікатора.
2. **Інваріант монотонності версій (Monotonic Version Invariant):** Поле `version` у сесійному документі є строго монотонно зростаючим цілим числом. Будь-яка успішна операція модифікації даних зобов'язана збільшувати версію рівно на `+1`. Зменшення номера версії, повторне використання або пропуск номерів суворо заборонені.
3. **Інваріант незалежності від системного годинника (Clock Independence):** Валідність та час життя сесії визначаються виключно механізмами тайм-аутів самого сховища (TTL у Redis / Key-Value базі). Контракт забороняє спиратися на локальний настінний час окремих веб-серверів для перевірки згасання сесії, що захищає систему від розбіжностей NTP-годинників (Clock Skew).
4. **Інваріант ідемпотентності видалення (Idempotent Deletion):** Метод знищення сесії `destroy(sessionId)` є строго ідемпотентним: повторний виклик для вже неіснуючої або простроченої сесії не повинен генерувати помилок і повертає передбачуване значення.

## 2. Специфікація методів програмного інтерфейсу

Сесійний шар надає єдиний програмний контракт для всіх операцій читання, створення, мутації, ротації та відкликання сесійного стану.

```ts
export interface ISessionStore {
  create(initialData?: SessionData, ttlSeconds?: number): Promise<SessionEnvelope>;
  get(sessionId: string): Promise<SessionEnvelope | null>;
  update(
    sessionId: string,
    expectedVersion: number,
    mutator: (current: SessionData) => SessionData,
    ttlSeconds?: number
  ): Promise<SessionEnvelope>;
  touch(sessionId: string, ttlSeconds?: number): Promise<boolean>;
  destroy(sessionId: string): Promise<boolean>;
  destroyAllForUser(userId: string): Promise<number>;
  rotate(oldSessionId: string, ttlSeconds?: number): Promise<SessionEnvelope>;
}
```

### Детальний опис методів та їхніх контрактів

#### 1. `create(initialData, ttlSeconds)`
- **Призначення:** Створює новий сесійний запис у сховищі.
- **Вхідні параметри:**
  - `initialData` *(SessionData, необов'язково)*: Початковий словник бізнес-даних (ідентифікатор користувача, роль, прапорці доступу). Якщо не передано — ініціалізується порожнім об'єктом `{}`.
  - `ttlSeconds` *(integer, необов'язково)*: Час життя сесії в секундах. Якщо не вказано — використовується значення конфігурації за замовчуванням (`1800` секунд / 30 хвилин).
- **Поведінка:** Генерує новий 128-бітний ідентифікатор сесії через криптографічний генератор CSPRNG, формує конверт із початковою версією `version = 1`, записує серіалізований JSON у сховище з виставленням TTL. Якщо в даних присутній `userId`, метод автоматично додає ідентифікатор сесії до вторинного індексу користувача.
- **Повертає:** Створений об'єкт `SessionEnvelope`.
- **Винятки:** `StoreUnavailableError` при збої мережевого з'єднання зі сховищем.

#### 2. `get(sessionId)`
- **Призначення:** Зчитує сесійний конверт за його ідентифікатором.
- **Вхідні параметри:**
  - `sessionId` *(string, обов'язково)*: 32-символьний шістнадцятковий рядок ідентифікатора.
- **Поведінка:** Виконує читання ключа зі сховища. Якщо ключ знайдено, десеріалізує конверт, ініціює фонову неблокуючу операцію дросельованого поновлення TTL (Throttled Touch) і повертає конверт. Якщо ключ відсутній або термін його дії закінчився — повертає `null`.
- **Повертає:** `SessionEnvelope | null`.
- **Винятки:** `StoreUnavailableError` при недоступності сховища.

#### 3. `update(sessionId, expectedVersion, mutator, ttlSeconds)`
- **Призначення:** Атомарна модифікація корисного навантаження сесії із захистом від паралельних гонок (Compare-And-Swap).
- **Вхідні параметри:**
  - `sessionId` *(string, обов'язково)*: Ідентифікатор сесії.
  - `expectedVersion` *(integer, обов'язково)*: Номер версії документа, отриманий під час попереднього читання.
  - `mutator` *(Function, обов'язково)*: Чиста синхронна функція `(currentData) => nextData`. Функція не повинна містити асинхронних викликів вводу-виводу, оскільки може виконуватися повторно в циклі retry.
  - `ttlSeconds` *(integer, необов'язково)*: Оновлений час життя сесії.
- **Поведінка:** Виконує атомарний Lua-скрипт у Redis. Скрипт перевіряє рівність поточної збереженої версії та `expectedVersion`. У разі збігу — збільшує версію на `+1`, оновлює часові мітки `updatedAt` і `lastTouch`, зберігає документ і повертає оновлений конверт.
- **Повертає:** Оновлений об'єкт `SessionEnvelope`.
- **Винятки:**
  - `VersionConflictError` — якщо актуальна версія в сховищі більша за `expectedVersion` (ознака паралельної модифікації іншим запитом).
  - `SessionNotFoundError` — якщо сесія зникла зі сховища під час обробки.
  - `StoreUnavailableError` — при відмові мережевого кластера.

#### 4. `touch(sessionId, ttlSeconds)`
- **Призначення:** Примусове або дросельоване поновлення тайм-ауту сесії без зміни бізнес-даних.
- **Вхідні параметри:** `sessionId`, `ttlSeconds`.
- **Поведінка:** Оновлює TTL ключа в Redis. Застосовується мідлваром на безпечних операціях читання (GET-запитах).
- **Повертає:** `boolean` (true, якщо ключ існував і TTL оновлено; false, якщо сесію не знайдено).

#### 5. `destroy(sessionId)`
- **Призначення:** Знищення сесії користувача на поточному пристрої (Single Logout).
- **Вхідні параметри:** `sessionId`.
- **Поведінка:** Видаляє сесійний ключ у сховищі. Якщо в конверті був прив'язаний `userId`, видаляє ідентифікатор із множини сесій користувача.
- **Повертає:** `boolean` (true, якщо запис було видалено).

#### 6. `destroyAllForUser(userId)`
- **Призначення:** Глобальне відкликання всіх сесій конкретного облікового запису на всіх пристроях (Global Logout / Password Reset Revocation).
- **Вхідні параметри:** `userId` *(string)*.
- **Поведінка:** Зчитує список усіх `sid` із вторинного індексу користувача `sess:user:<userId>` і видаляє всі знайдені сесійні ключі та сам індекс через атомарний пакетний конвеєр (Pipeline).
- **Повертає:** `integer` (кількість успішно видалених сесій).

#### 7. `rotate(oldSessionId, ttlSeconds)`
- **Призначення:** Ротація ідентифікатора сесії при зміні привілеїв користувача для повного захисту від атак фіксації сесії (Session Fixation Defense за стандартом OWASP).
- **Вхідні параметри:** `oldSessionId`, `ttlSeconds`.
- **Поведінка:** Зчитує дані старої сесії, генерує абсолютно новий випадковий ідентифікатор `newSessionId`, атомарно зберігає стан під новим ключем з інкрементом версії, оновлює індекс користувача і видаляє старий ключ `oldSessionId`.
- **Повертає:** Новий об'єкт `SessionEnvelope`.

## 3. Схема структури даних сесійного конверта (Envelope Schema)

Сесійний конверт стандартизує метадані для всіх типів сесійних сховищ. Нижче наведено точний опис полів схеми.

| Назва поля | Тип даних | Обов'язкове | Допустимі значення та обмеження |
|---|---|---|---|
| `id` | `string` | Так | Рівно 32 шістнадцяткові символи в нижньому регістрі (`^[0-9a-f]{32}$`). Несе 128 біт криптографічної ентропії. |
| `version` | `integer` | Так | Ціле число `≥ 1`. Починається з `1`, монотонно зростає при кожному CAS-записі. |
| `schemaVersion` | `integer` | Так | Ціле позитивне число `≥ 1`. Вказує версію структури даних для лінивої міграції полів. |
| `createdAt` | `integer` | Так | Часова мітка Unix Epoch у мілісекундах. Фіксується при створенні, ніколи не мутує. |
| `updatedAt` | `integer` | Так | Часова мітка останньої успішної зміни даних у мілісекундах (Unix Epoch ms). |
| `lastTouch` | `integer` | Так | Часова мітка останнього поновлення TTL у сховищі для алгоритму дроселювання. |
| `data` | `object` | Так | Словник довільних серіалізованих бізнес-полів користувача (`userId`, `role`, `cart`, тощо). |

### Приклад JSON-конверта у сховищі

```json
{
  "id": "c7f92a18b0e43d92015fa84c3e891b24",
  "version": 5,
  "schemaVersion": 2,
  "createdAt": 1700000000000,
  "updatedAt": 1700000600000,
  "lastTouch": 1700000450000,
  "data": {
    "userId": "usr_alpha_441",
    "role": "manager",
    "permissions": ["orders:read", "orders:write"],
    "cartTotal": 1420.50
  }
}
```

## 4. Специфікація транспортних HTTP-заголовків (Wire Contract)

Транспортування ідентифікатора сесії між клієнтським браузером і балансувальником навантаження регламентується правилами протоколів HTTP/1.1, HTTP/2 та RFC 6265bis.

### 1. Формат заголовка встановлення сесії (`Set-Cookie`)

Сервер повертає клієнту заголовок `Set-Cookie` при первинному створенні сесії або після успішної ротації ідентифікатора:

```http
Set-Cookie: __Host-sid=c7f92a18b0e43d92015fa84c3e891b24; Max-Age=1800; Path=/; Secure; HttpOnly; SameSite=Lax
```

#### Обов'язкові директиви безпеки:
- **Префікс `__Host-`:** Ім'я cookie повинно починатися з `__Host-` (наприклад, `__Host-sid`). За стандартом RFC 6265bis такий cookie приймається браузером виключно за умови дотримання трьох вимог: передача тільки через захищений HTTPS-канал (`Secure`), шлях встановлено в корінь (`Path=/`), а директива `Domain` повністю відсутня. Це блокує атаку *Cookie Tossing*, у якій піддомен зловмисника намагається підкинути фальшиву сесію основному домену.
- **Директива `HttpOnly`:** Повністю блокує доступ до значення cookie з JavaScript через об'єкт `document.cookie`. Запобігає викраденню ідентифікатора сесії у випадку XSS-вразливостей.
- **Директива `Secure`:** Дозволяє браузеру надсилати cookie виключно у зашифрованих TLS/HTTPS-з'єднаннях, виключаючи перехоплення у відкритих Wi-Fi мережах.
- **Директива `SameSite=Lax`:** Забороняє надсилання сесійного cookie у міжсайтових POST/PUT-запитах, ініційованих сторонніми ресурсами, забезпечуючи надійний перший ешелон захисту від атак міжсайтової підробки запитів (CSRF).
- **Директива `Max-Age`:** Задає точний час життя cookie в секундах, синхронізований із серверним TTL сесії.

### 2. Формат заголовка передачі сесії клієнтом (`Cookie`)

Браузер автоматично прикріплює збережений сесійний cookie до кожного наступного HTTP-запиту:

```http
GET /api/orders HTTP/1.1
Host: shop.example.com
Cookie: __Host-sid=c7f92a18b0e43d92015fa84c3e891b24
```

### 3. Формат заголовка видалення сесії (Logout)

Для негайного очищення cookie на боці клієнта сервер повертає нульовий час життя та минулу дату:

```http
Set-Cookie: __Host-sid=; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Path=/; Secure; HttpOnly; SameSite=Lax
```

### 4. Альтернативний транспорт: заголовок `Authorization: Bearer`

Для мобільних додатків та REST API без підтримки браузерних cookie ідентифікатор сесії передається у стандартному заголовку авторизації:

```http
GET /api/v1/profile HTTP/1.1
Host: api.example.com
Authorization: Bearer c7f92a18b0e43d92015fa84c3e891b24
```

### 5. Правила взаємодії з міждоменними запитами (CORS Policy)

Коли бекенд обслуговує запити з іншого домену (Cross-Origin Resource Sharing), серверний шлюз зобов'язаний дотримуватися суворого протоколу заголовків:
1. Заголовок `Access-Control-Allow-Credentials: true` — дозволяє браузеру прикріплювати cookie до крос-доменних AJAX/Fetch-викликів.
2. Заголовок `Access-Control-Allow-Origin: https://app.example.com` — **повинен містити явний дозволений домен**. Використання підстановочного символу `Access-Control-Allow-Origin: *` разом із прапорцем `Allow-Credentials: true` суворо заборонено браузерними стандартами безпеки і призводить до автоматичного блокування відповіді.

## 5. Специфікація клієнтських шифрованих токенів (Encrypted Client State)

Для архітектур, що обирають зберігання стану безпосередньо на клієнті (Stateless Cookie Tokens / Flask & Rails Session style), встановлюється наступний криптографічний протокол:

### 1. Формат бінарного шифроконверта
Шифрування здійснюється за схемою автентифікованого шифрування з прив'язаними даними (**AEAD** на базі AES-256-GCM або ChaCha20-Poly1305):

```
[ Ідентифікатор ключа: 4 байти (kid) ]
[ Вектор ініціалізації: 12 байтів (IV / Nonce) ]
[ Зашифрований корисний payload (Ciphertext) ]
[ Тег автентифікації: 16 байтів (Auth Tag) ]
```

### 2. Правила ротації криптографічних ключів
- Поле `kid` (Key ID) дозволяє підтримувати в пам'яті воркерів кілька ключів шифрування одночасно.
- Під час ротації ключів новий ключ виставляється як активний для шифрування нових сесій, а старий ключ зберігається у списку дозволених для розшифрування протягом 48 годин.
- Якщо токен підписано невідомим або відкликаним `kid`, він негайно відкидається зі статусом `401 Unauthorized`.

### 3. Ліміт розміру корисного навантаження
Сумарний розмір cookie разом із заголовком та назвою не повинен перевищувати **4096 байтів** (жорстке обмеження стандарту браузерів). Якщо бізнес-стан перевищує 3 КБ, клієнтські сесії стають неможливими, і система зобов'язана перейти на серверне сховище Redis.

## 6. Життєвий цикл сесії та скінченний автомат станів (State Machine)

Кожна сесія в бездержавному середовищі проходить через суворо детермінований набір станів:

```
 [Початок]
     │
     ▼  create()
┌───────────┐         touch()          ┌───────────┐
│  CREATED  │ ───────────────────────► │  ACTIVE   │ ◄────┐
└───────────┘                          └───────────┘      │
     │                                       │            │ update() CAS OK
     │                                       ▼ update()   │
     │                                 ┌───────────┐      │
     │                                 │  MUTATED  │ ─────┘
     │                                 └───────────┘
     │                                       │
     │                                       ▼ rotate()
     │                                 ┌───────────┐
     │                                 │  ROTATED  │
     │                                 └───────────┘
     │                                       │
     │ destroy() / TTL Expiry                │ destroy() / TTL Expiry
     ▼                                       ▼
┌──────────────────────────────────────────────────┐
│              EXPIRED / REVOKED                   │
│         (Ключ остаточно видалено)                │
└──────────────────────────────────────────────────┘
```

### Правила переходів автомата:
1. **`CREATED` → `ACTIVE`:** Сесію записано в сховище з `version = 1`. Воркер отримує дескриптор і може читати або продовжувати час життя.
2. **`ACTIVE` → `MUTATED`:** Метод `update()` успішно застосовує функцію-мутатор і атомарно перевіряє `CAS`. Версія збільшується до `version + 1`. Стан повертається до `ACTIVE`.
3. **`ACTIVE` → `ROTATED`:** Після зміни контексту безпеки (авторизація користувача, підвищення ролі) викликається `rotate()`. Старий ідентифікатор переходить у `REVOKED`, а новий переходить у `ACTIVE`.
4. **`ACTIVE` → `EXPIRED / REVOKED`:** Відбувається прямий виклик `destroy()` або закінчення таймауту `TTL` у Redis. Будь-які спроби виклику `update()` на сесії в цьому стані зобов'язані завершуватися помилкою `SESSION_NOT_FOUND` і ніколи не повинні воскрешати видалений ключ.

## 7. Валідація даних та захист від вичерпання ресурсів

Для захисту кластера Redis від переповнення пам'яті та атак на відмову в обслуговуванні (DoS) сесійний шар накладає суворі обмеження на корисне навантаження:

1. **Контроль глибини та серіалізовності:** Об'єкт `SessionData` повинен бути чистим JSON-серіалізовним словником. Заборонено передавати циклічні посилання, нативні дескриптори файлів, потоки читання (Streams) або екземпляри класів із методами.
2. **Бюджет розміру сесійного документа:**
   - **Рекомендований розмір (Soft Limit):** `≤ 4 КБ`. При перевищенні генерується попереджувальний лог.
   - **Граничний розмір (Hard Limit):** `32 КБ`. Спроба зберегти сесію більшого розміру негайно відхиляється помилкою `413 Payload Too Large`. Сесійне сховище призначене для збереження стану взаємодії, а не для заміни бази даних чи сховища файлів.
3. **Захист від забруднення прототипу (Prototype Pollution Defense):** Парсер JSON зобов'язаний блокувати ключі `__proto__`, `constructor` та `prototype`, створюючи плоскі об'єкти без наслідування (`Object.create(null)`).

## 8. Мультирегіональна реплікація та георозподілені кластери (Multi-Region Topology)

У географічно розподілених системах, розгорнутих у кількох дата-центрах (наприклад, Європа та Північна Америка), застосовується одна з двох стратегій синхронізації сесійного стану:

### 1. Стратегія регіональної сесійної локальності (Home Region Stickiness)
Сесія створюється і зберігається у найближчому до користувача регіоні. Глобальний DNS або Anycast маршрутизує клієнта до домашнього регіону. При міжрегіональній міграції клієнта (подорож користувача) запит перенаправляється через внутрішній бекенд-шлюз до домашнього кластера Redis.

### 2. Стратегія глобальної Active-Active реплікації (CRDT / Global Key-Value)
Сесійне сховище спирається на мультирегіональні розподілені таблиці (DynamoDB Global Tables або Redis Enterprise CRDT). Конфлікти одночасного запису з різних континентів вирішуються за правилом найвищої версії або векторного годинника (Vector Clocks). Завдяки атомарному конверту з монотонною версією система гарантує конвергенцію даних без виникнення розділення стану (*Split-Brain*).

## 9. Матриця системних помилок та статусів відповідей

Сесійний шар забезпечує строгу типізацію виняткових ситуацій для передбачуваної реакції клієнтських додатків.

| Системний код помилки | HTTP-статус | Категорія причини | Опис причини виникнення | Протокол реакції системи |
|---|---|---|---|---|
| `SESSION_NOT_FOUND` | `401 Unauthorized` | Клієнтська | Ідентифікатор відсутній у сховищі (видалено, згасло за таймаутом або фальшивий ID). | Очистити клієнтський cookie, перенаправити на екран повторного входу. |
| `VERSION_CONFLICT` | `409 Conflict` | Паралелізм | Спроба CAS-запису з застарілим номером `expectedVersion` (гонка між вкладками). | Виконати цикл автоматичного повтору (Optimistic Retry Loop) на бекенді. |
| `SESSION_EXPIRED` | `401 Unauthorized` | Безпека | Перевищено максимальний абсолютний ліміт тривалості життя сесії. | Анулювати сесію в Redis, вимагати нового підтвердження автентифікації. |
| `STORE_UNAVAILABLE` | `503 Service Unavailable` | Інфраструктура | Кластер Redis недоступний через падіння вузлів або мережевий поділ (Split-Brain). | Для запису — перервати операцію (Fail-Closed); для читання — перейти в режим гостя. |
| `INVALID_SESSION_ID` | `400 Bad Request` | Валідація | Cookie містить символи поза діапазоном `[0-9a-f]` або має довжину, відмінну від 32. | Відхилити заголовок, створити новий гостьовий ідентифікатор. |
| `SCHEMA_MISMATCH` | `500 Internal Error` | Сумісність | Помилка парсингу JSON або критична несумісність полів сесійного документа. | Знищити пошкоджений ключ у сховищі, записати критичний лог аварії. |

## 10. Протокол повторних спроб при колізіях (Concurrency Retry Protocol)

Коли метод `update()` повертає `VersionConflictError`, викликаючий код застосовує алгоритм експоненційного затримання з випадковим джитером (*Exponential Backoff with Full Jitter*).

### Математичний контракт затримки:
```
T_wait = random(0, min(T_ceiling, T_base · 2^(attempt − 1)))
```
де:
- `T_base = 5 мс` — базовий квант затримки;
- `T_ceiling = 40 мс` — верхня межа паузи між спробами;
- `maxRetries = 3` — ліміт повторних спроб;
- `attempt` — порядковий номер спроби (`1, 2, 3`).

### Алгоритм виконання повтору:
1. Перехоплення винятку `VersionConflictError`;
2. Виконання асинхронної паузи тривалістю `T_wait`;
3. Повторне зчитування актуального документа `get(sessionId)` з отриманням свіжої версії `v_actual`;
4. Повторне застосування чистої функції мутатора `mutator(actualData)`;
5. Повторна спроба атомарного CAS-запису `update(sessionId, v_actual, mutator)`.
