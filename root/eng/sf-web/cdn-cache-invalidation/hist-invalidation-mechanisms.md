# 📜 Від нічних скриптів до мілісекундного purge: еволюція інвалідації в CDN

Еволюція керування крайовими кешами — це історія подолання фундаментального компромісу між швидкістю роздачі контенту та його актуальністю: від перших багатохвилинних черг очищення на глобальних серверах Akamai до сучасних субсекундних шин широкомовлення та семантичних сурогатних ключів.

## Народження розподіленого кешування та ера тривалого TTL (1998–2005)

Наприкінці 1990-х років вибухове зростання Всесвітньої павутини зіткнулося з проблемою так званого «ефекту Слейшдота» (англ. *Slashdot effect*): коли популярний новинний ресурс публікував посилання на веб-сайт, сотні тисяч одночасних звернень миттєво перевантажували центральний сервер-джерело (англ. *origin server*), приводячи до повної відмови в обслуговуванні через вичерпання черги з'єднань веб-сервера Apache та процесорних лімітів операційної системи.

У 1998 році професор прикладної математики Массачусетського технологічного інституту (MIT) Том Лейтон (англ. *Tom Leighton*) та його аспірант Денні Левін (англ. *Danny Lewin*) розробили алгоритми послідовного хешування (англ. *consistent hashing*) для оптимального розподілу інтернет-трафіку між тисячами географічно віддалених серверів без повної перебудови хеш-таблиці при виході з ладу окремих вузлів. Це математичне дослідження лягло в основу компанії Akamai Technologies, заснованої восени 1998 року.

```
1998–2005: Akamai & Squid                 2006–2011: Varnish & Regex Bans           2012–сучасність: Instant Purge & Mesh
┌───────────────────────────────────────┐ ┌───────────────────────────────────────┐ ┌───────────────────────────────────────┐
│ • Пасивний TTL (години/дні)           │ │ • Локальний Varnish Cache             │ │ • Fastly Instant Purge (~150 мс)    │
│ • Ручний Purge через SOAP / Email     │ │ • Механізм ban-списків (regex)        │ │ • Семантичні Surrogate-Keys / Tags  │
│ • Затримка інвалідації: 30–60 хвилин  │ │ • Проблема O(N) деградації пам'яті    │ │ • Широкомовні шини (Quicksilver/NATS)│
└───────────────────────────────────────┘ └───────────────────────────────────────┘ └───────────────────────────────────────┘
```

Перше покоління мереж доставки контенту (англ. *Content Delivery Network*, CDN) розглядало кеш виключно як статичний буфер для незмінних медіафайлів: зображень у форматах GIF та JPEG, аудіофайлів та заздалегідь згенерованих таблиць стилів. Керування кешем ґрунтувалося на пасивному часі життя об'єктів (англ. *Time-To-Live*, TTL), який встановлювався за допомогою заголовків HTTP/1.0 `Expires` або HTTP/1.1 `Cache-Control: max-age`.

Попередниками комерційних CDN були прямі кешуючі проксі-сервери, насамперед Squid (створений Дуейном Весселсом у 1996 році в рамках дослідницького проекту Harvest Національного наукового фонду США). Squid використовував протоколи ICP (англ. *Internet Cache Protocol*, RFC 2187) та пізніше HTCP (англ. *Hyper Text Caching Protocol*, RFC 2756) для опитування сусідніх вузлів щодо наявності об'єкта. Однак ці протоколи вимагали надсилання додаткових UDP-запитів між проксі, що було ефективно в межах університетського кампусу або локальної мережі інтернет-провайдера, але абсолютно не масштабувалося на трансконтинентальні відстані.

Якщо на центральному бекенді змінювалася новина, ціна товару чи критичний скрипт, інженерам доводилося ініціювати примусове видалення об'єкта (англ. *cache purge*). У перших архітектурах Akamai процедура очищення була надзвичайно складною і повільною:
1. Адміністратор надсилав запит через веб-портал або за протоколом SOAP у центральну систему керування конфігурацією (CCU — Content Control Utilities).
2. Центральний координатор додавав запит у масивну розподілену чергу на реляційній базі даних.
3. Демони оновлення на крайових серверах опитували центральну чергу періодичними пакетами (polling) раз на 5–15 хвилин і поступово вичищали файлові дескриптори на десятках тисяч серверів.

Час поширення команди інвалідації по глобальній мережі становив від 30 до 60 хвилин. Через таку величезну затримку динамічний HTML-контент та транзакційні API взагалі забороняли кешувати (`Cache-Control: private, no-cache, no-store`), що змушувало розробників утримувати дорогі й неефективні серверні ферми для обслуговування динамічних сторінок, навіть коли 95% вмісту сторінки залишалися незмінними.

## Varnish, списки заборон та межі локальної інвалідації (2006–2011)

Паралельно з розвитком комерційних CDN у світі відкритого програмного забезпечення відбувалася революція локального веб-прискорення. У 2006 році данський розробник Поуль-Геннінг Камп (дан. *Poul-Henning Kamp*), один із провідних архітекторів ядра операційної системи FreeBSD, представив Varnish Cache.

Камп критикував архітектуру Squid за те, що вона розглядала операційну систему як ворога: Squid підтримував власні буфери пам'яті, сам вирішував, коли записувати сторінки на диск, і виконував тисячі системних викликів `read`/`write`. Varnish обрав принципово інший шлях: він довірив керування пам'яттю ядру операційної системи через виклик `mmap`, дозволивши підсистемі віртуальної пам'яті ядра автоматично скидати неактивні сторінки кешу у swap або на диск. Крім того, Varnish впровадив гнучку мову конфігурації VCL (англ. *Varnish Configuration Language*), яка компілювалася в машинний код C прямо під час завантаження демона.

Головною інновацією Varnish у сфері інвалідації став механізм заборон (англ. *bans*). Замість перебору та фізичного видалення гігабайтів об'єктів з оперативної пам'яті Varnish записував предикати перевірки у глобальний двозв'язний список:

```
ban req.url ~ ^/articles/ && req.http.host == example.com
```

Коли клієнт звертався до об'єкта в кеші, Varnish порівнював мітку часу створення об'єкта з мітками часу активних заборон у списку. Якщо об'єкт був створений раніше, ніж була додана відповідна заборона, і підпадав під регулярний вираз, він вважався застарілим і вирушав на повторну вибірку на бекенд.

Однак списки заборон мали фундаментальне обмеження масштабування. При інтенсивній публікації контенту довжина списку заборон зростала до десятків тисяч елементів. Кожен вхідний запит був змушений послідовно обчислювати регулярні вирази за часом `O(N)`, де `N` — кількість активних заборон. Це призводило до різкого стрибка утилізації процесора (англ. *CPU spike*) та деградації пропускної здатності. Хоча фоновий прибиральник (англ. *ban lurker*) поступово вичищав старі заборони під час простою процесора, перенесення такої моделі на глобальні мережі з тисячами розподілених вузлів було неможливим через вибухове зростання накладних витрат на синхронізацію списків.

## Поява Fastly та революція миттєвої інвалідації (2011–2015)

У 2011 році Артур Бергман (англ. *Artur Bergman*), колишній технічний директор соціальних платформ Wikia та LiveJournal, заснував компанію Fastly. Бергман поставив перед собою мету: перетворити CDN зі сховища статичних файлів на динамічну площину виконання, де будь-який HTML або JSON може кешуватися безстроково, оскільки час його інвалідації не перевищуватиме часу проходження мережевого пакета.

Fastly модифікувала ядро Varnish, перенесла обробку пакетів на сучасні мережеві карти з підтримкою черг 10GbE/100GbE та побудувала спеціалізовану високошвидкісну шину обміну повідомленнями між усіма своїми точками присутності (англ. *Points of Presence*, PoP). Замість повільного опитування черг команда `PURGE` транслювалася по виділених волоконно-оптичних каналах одночасно на всі крайові вузли, скоротивши середній час інвалідації до 150 мілісекунд.

```
Origin Server                      Global Broadcast Mesh                      Edge PoPs (100+ локацій)
┌──────────────┐                  ┌─────────────────────────┐                ┌─────────────────────────┐
│ Зміна запису │ ── POST /purge ─►│ Виділене ядро розсилки  │ ── 150 мс ───► │ London PoP   [Evicted]  │
│  у базі даних│                  │ (Quicksilver / Kafka)   │                │ Frankfurt PoP[Evicted]  │
└──────────────┘                  └─────────────────────────┘                │ Tokyo PoP    [Evicted]  │
                                                                             └─────────────────────────┘
```

Одночасно виникла концепція **сурогатних ключів (англ. *surrogate keys*)**, стандартизована у робочих документах консорціуму W3C та інженерної групи IETF. Замість прив'язки інвалідації до конкретної URL-адреси бекенд отримав можливість повертати в заголовку `Surrogate-Key` набір абстрактних міток сутностей:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Surrogate-Key: product-9482 category-laptops brand-apple
```

Коли користувач купував останній ноутбук або менеджер змінював ціну товару, серверу джерела більше не було потрібно знати, на яких саме сторінках відображається цей товар (головна вітрина, каталог, сторінка пошукової видачі, RSS-стрічка). Достатньо було надіслати один запит `PURGE /service/KEY/product-9482`, і крайові вузли за лічені мілісекунди маркували як застарілі всі пов'язані URL-представлення за константний час `O(1)` завдяки інвертованому індексу в оперативній пам'яті.

## Хмарні гіганти та сучасний консенсус інвалідації (2015–2026)

Успіх підходу Fastly змусив решту ринку кардинально переглянути свої підсистеми кешування.

Компанія Cloudflare у середині 2010-х років розробила власну систему розподіленої реплікації стану під назвою Quicksilver — транзакційну базу даних у пам'яті, що працює на кожному сервері мережі. Quicksilver використовує оптимізований протокол консенсусу та поширює ключі інвалідації та метадані конфігурації менш ніж за 150–200 мілісекунд у глобальному масштабі, підтримуючи як прямий URL Purge, так і механізм `Cache-Tag`.

Amazon Web Services, чий сервіс CloudFront історично страждав від 10–15-хвилинних затримок інвалідації та стягував окрему плату за запити очищення понад безкоштовний ліміт (1000 шляхів на місяць), у 2020-х роках суттєво оптимізував внутрішню чергу інвалідації на базі AWS Kinesis та DynamoDB Accelerator, скоротивши середній час скидання до кількох секунд та інтегрувавши підтримку політик `stale-while-revalidate` (RFC 5861).

Паралельно робоча група HTTP Working Group (HTTPbis) консорціуму IETF під керівництвом Марка Ноттінгема (англ. *Mark Nottingham*) та за участі Роя Філдінга (англ. *Roy Fielding*) прийняла низку ключових стандартів:
- **RFC 5861 (2010):** директиви `stale-while-revalidate` та `stale-if-error`, що узаконили асинхронне оновлення фонових об'єктів без блокування клієнтських запитів.
- **RFC 9211 (2022):** заголовок `Cache-Status`, який стандартизував діагностику стану кешу (хіт, промах, застарілий стан, причина провалу) для всіх проміжних проксі-серверів.
- **RFC 9213 (2022):** заголовок `CDN-Cache-Control`, що дозволив чітко розмежовувати інструкції для браузерного клієнтського кешу та глобальної крайової інфраструктури.

Сьогодні інвалідація кешу перетворилася з аварійної ручної процедури на регулярний компонент архітектури розподілених систем, де семантичні теги та субсекундні широкомовні шини усувають затримку між зміною стану в базі даних та відображенням оновлення кінцевому користувачеві на будь-якому континенті.
