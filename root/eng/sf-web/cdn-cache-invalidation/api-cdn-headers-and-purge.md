# 📋 Заголовки керування кешем та API інвалідації крайових мереж

Довідник протокольних контрактів, керуючих HTTP-заголовків та API-інтерфейсів примусової інвалідації кешу для сучасних мереж доставки контенту (Fastly, Cloudflare, AWS CloudFront, Akamai та RFC-стандарти).

## 1. Специфікація керуючих HTTP-заголовків

Поведінка крайового кешу налаштовується через комбінацію стандартних заголовків відповідей бекенда. Нижче наведено розгорнутий аналіз директив, їхній пріоритет та вплив на клієнтський браузер і розподілені вузли CDN.

### Базові директиви заголовка Cache-Control (RFC 9111)

Заголовок `Cache-Control` є основним засобом декларації політик кешування в протоколі HTTP/1.1 та HTTP/2.

```http
Cache-Control: public, max-age=3600, s-maxage=86400, stale-while-revalidate=60
```

| Директива | Область дії | Поведінка та семантика |
|---|---|---|
| `public` | Усі рівні | Явно дозволяє зберігати відповідь будь-якому кешу (браузеру, проксі, CDN), навіть якщо запит містив заголовок `Authorization`. |
| `private` | Лише браузер | Відповідь призначена виключно для кінцевого користувача. Спільні проміжні вузли (CDN, реверс-проксі) **не мають права зберігати цей об'єкт**. |
| `no-cache` | Браузер і CDN | Дозволяє зберігати об'єкт у сховищі, але **вимагає обов'язкової відправки умовного запиту** (`ETag`/`If-None-Match`) на бекенд перед кожною видачею клієнту. |
| `no-store` | Браузер і CDN | **Категорична заборона запису** на будь-який енергонезалежний носій або в оперативну пам'ять. Застосовується для платіжних даних, персональної інформації та одноразових токенів. |
| `max-age=<sec>` | Браузер і CDN | Задає максимальний вік свіжості об'єкта в секундах від моменту його генерації на бекенді. |
| `s-maxage=<sec>` | Лише спільні кеші | Перевизначає значення `max-age` для спільних (shared) проміжних вузлів. Браузер ігнорує цю директиву і продовжує керуватися `max-age`. |
| `must-revalidate` | Браузер і CDN | Повідомляє кешу, що після закінчення терміну свіжості об'єкт не може використовуватися повторно без успішної відповіді бекенда, навіть якщо зв'язок із джерелом тимчасово втрачено. |
| `proxy-revalidate` | Лише спільні кеші | Аналог `must-revalidate`, але застосовується виключно до проміжних шлюзів та CDN, не обмежуючи поведінку браузерного кешу. |
| `no-transform` | Браузер і CDN | Забороняє проміжному проксі вносити будь-які модифікації в тіло та заголовки відповіді (наприклад, стискати зображення або перекодовувати WebP). |
| `immutable` (RFC 8246) | Браузер і CDN | Вказує, що тіло ресурсу ніколи не зміниться протягом усього часу життя `max-age`. Запобігає умовним запитам при оновленні сторінки користувачем. |

### Директиви асинхронної ревалідації та відмовостійкості (RFC 5861)

Директиви розширення `stale-while-revalidate` та `stale-if-error` забезпечують безперебійну роботу системи в умовах високого навантаження або збоїв на джерелі.

```http
Cache-Control: public, max-age=600, stale-while-revalidate=120, stale-if-error=86400
```

- **`stale-while-revalidate=<sec>`:** Якщо вік об'єкта перевищив `max-age`, але вкладається у додаткове вікно свіжості (у прикладі: між 600 та 720 секундами), крайовий сервер негайно повертає клієнту застарілу версію, одночасно ініціюючи фоновий асинхронний запит до бекенда для оновлення кешу.
- **`stale-if-error=<sec>`:** Якщо термін свіжості минув і запит на ревалідацію до сервера-джерела зазнав невдачі (бекенд повернув HTTP 500, 502, 503, 504 або обірвав TCP-з'єднання), крайовий вузол має право віддавати застарілу копію протягом зазначеного інтервалу (у прикладі: до 24 годин), маскуючи аварію від користувача.

### Таргетоване керування: CDN-Cache-Control (RFC 9213)

Для розв'язання конфліктів між налаштуваннями браузера та CDN стандарт RFC 9213 ввів заголовок `CDN-Cache-Control`. Якщо цей заголовок присутній у відповіді бекенда, CDN повністю ігнорує поле `Cache-Control` (і директиву `s-maxage`) та керується виключно значеннями з `CDN-Cache-Control`.

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=60
CDN-Cache-Control: max-age=604800, stale-while-revalidate=300
Cloudflare-CDN-Cache-Control: max-age=2592000
```

Ієрархія пріоритетів обробки крайовим кешем (від найвищого до найнижчого):
1. Провайдер-специфічний заголовок (наприклад, `Cloudflare-CDN-Cache-Control` або `Fastly-CDN-Cache-Control`).
2. Загальний стандартний заголовок `CDN-Cache-Control` (RFC 9213).
3. Заголовок `Surrogate-Control` (традиційний стандарт Fastly/Varnish).
4. Директива `s-maxage` у стандартному заголовку `Cache-Control`.
5. Директива `max-age` у заголовку `Cache-Control`.
6. Заголовок HTTP/1.0 `Expires`.

## 2. Заголовки валідації та умовні запити (RFC 9110)

Умовні запити дозволяють крайовому проксі перевірити актуальність застарілого ресурсу без повторного завантаження повного тіла відповіді.

### Механізм сильних та слабких валідаторів

Бекенд формує один із двох типів валідаторів:
- **Сильний ETag (`"33a64df551425fcc"`):** Гарантує побайтову ідентичність тіла відповіді. Будь-яка зміна хоча б одного біта даних призводить до генерації нового ETag.
- **Слабкий ETag (`W/"33a64df551425fcc"`):** Гарантує семантичну еквівалентність (наприклад, однаковий вміст HTML, але з відмінностями у форматуванні пробілів або внутрішніх коментарях).
- **Часова мітка (`Last-Modified: Wed, 19 Aug 2026 22:15:00 GMT`):** Дата останньої зміни файлу на файловій системі з точністю до однієї секунди.

```http
Запит ревалідації від CDN до Origin:
GET /api/v1/products/1084 HTTP/1.1
Host: api.example.com
If-None-Match: "33a64df551425fcc"
If-Modified-Since: Wed, 19 Aug 2026 22:15:00 GMT

Відповідь джерела при відсутності змін:
HTTP/1.1 304 Not Modified
Date: Thu, 20 Aug 2026 02:00:00 GMT
Cache-Control: public, s-maxage=3600
ETag: "33a64df551425fcc"
```

## 3. Детальна анатомія заголовка Vary та матриця варіювання

Заголовок `Vary` визначає, які поля клієнтського запиту беруть участь у формуванні складеного ключа кешування.

```http
Vary: Accept-Encoding, Accept, Origin
```

Якщо заголовок `Vary` містить ненормалізовані поля, кількість збережених варіантів одного ресурсу зростає експоненційно, спричиняючи деградацію кешу (англ. *cache fragmentation*).

### Правила нормалізації заголовків на рівні CDN

1. **Нормалізація стиснення (Accept-Encoding):**
   - Клієнт надсилає: `Accept-Encoding: gzip, deflate, br;q=1.0, zstd;q=0.9`.
   - Проксі перетворює заголовок на єдине канонічне значення: `br` (якщо підтримується) або `gzip`.
   - Ключ кешування отримує суфікс `:br` або `:gzip`.
2. **Нормалізація типу контенту (Accept):**
   - Запити REST API із заголовком `Accept: application/json, text/plain, */*` нормалізуються до базового MIME-типу `application/json`.
3. **Обробка заголовка CORS (Origin):**
   - Якщо бекенд повертає `Vary: Origin`, CDN зберігає окремі копії відповіді для кожного дозволеного домену, зазначеного в списку `Access-Control-Allow-Origin`.

## 4. Семантика стиснення заголовків у HTTP/2 та HTTP/3 (HPACK та QPACK)

У сучасних бінарних протоколах передачі даних розмір службових заголовків має прямий вплив на швидкість обробки пакетів:
- **HPACK (RFC 7541 у HTTP/2):** Використовує статичну та динамічну таблиці для стиснення повторюваних рядків заголовків. Якщо бекенд повертає масивний заголовок `Surrogate-Key` на 16 КБ, динамічна таблиця HPACK може переповнитися, витісняючи корисні службові поля сесії.
- **QPACK (RFC 9204 у HTTP/3 / QUIC):** Усуває блокування початку черги (Head-of-Line Blocking) між незалежними потоками шляхом асинхронного узгодження динамічних індексів.

**Архітектурне правило:** Проміжний проксі CDN зобов'язаний розбирати заголовок `Surrogate-Key` у пам'яті та повністю видаляти його з вихідного HTTP-потоку перед серіалізацією кадрів HPACK/QPACK у бік клієнтського браузера. Це захищає динамічну таблицю стиснення від деградації та усуває накладні витрати пропускної здатності на мобільних з'єднаннях.

## 5. Заголовки семантичного тегування (Surrogate Keys / Cache-Tags)

Заголовки тегування дозволяють об'єднати довільну множину URL-адрес під єдиними бізнес-ідентифікаторами сутностей.

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: public, max-age=3600
Surrogate-Key: product-1084 category-electronics brand-sony in-stock warehouse-eu
Cache-Tag: product-1084,category-electronics,brand-sony,in-stock,warehouse-eu
Edge-Cache-Tag: product-1084,category-electronics
```

### Правила та обмеження тегування

1. **`Surrogate-Key` (Fastly / Varnish):**
   - Розділювач: символ пробілу (` `).
   - Ліміти: до 16 384 байтів загальної довжини заголовка; до 1024 унікальних ключів на одну відповідь.
   - Стрипінг: CDN в обов'язковому порядку видаляє заголовок `Surrogate-Key` перед передачею відповіді браузеру, захищаючи службові метадані від зовнішнього спостереження.
2. **`Cache-Tag` (Cloudflare):**
   - Розділювач: кома (`,`).
   - Ліміти: довжина одного тегу — до 1024 символів (тільки ASCII без пробілів); до 128 тегів на одну HTTP-відповідь.
   - Підтримка: доступно на тарифах Cloudflare Enterprise.
3. **`Edge-Cache-Tag` (Akamai):**
   - Розділювач: кома (`,`).
   - Ліміти: до 128 тегів на ресурс; сумарна довжина заголовка до 8 КБ.

## 6. Діагностичні заголовки стану (RFC 9211 Cache-Status)

Сучасні CDN додають заголовок `Cache-Status` для повної прозорості ланцюжка кешування.

```http
Cache-Status: Fastly; hit; ttl=245; age=115; grace=3600, OriginShield; fwd=uri-miss
Cache-Status: "Cloudflare"; hit; fwd=stale; ttl=1800; key="https://example.com/api/p/42"
```

### Словник параметрів поля Cache-Status

- `hit` — відповідь успішно знайдена в локальному кеші та віддана клієнту.
- `fwd=<reason>` — запит було перенаправлено далі по ланцюжку (на Shield або Origin). Значення причини:
  - `uri-miss` — об'єкта не було в кеші.
  - `stale` — об'єкт застарів і потребував ревалідації.
  - `bypass` — кешування вимкнено конфігурацією або правилом `no-store`.
- `fwd-status=<status>` — HTTP-код відповіді, отриманий від бекенда при промаху (наприклад, `fwd-status=304`).
- `stored` — об'єкт було успішно збережено в кеші після отримання відповіді.
- `collapsed` — запит було схлопнуто в один потік із сусіднім паралельним запитом у рамках Single-Flight Coalescing.
- `ttl=<sec>` — залишок часу життя об'єкта в секундах на момент віддачі.

### Багаторівневе трасування через Cache-Status

Якщо запит проходить через крайовий вузол (Edge PoP) та регіональний концентратор (Origin Shield), заголовок `Cache-Status` містить список елементів через кому, що відповідає кожному рівню обробки:

```http
Cache-Status: "Edge-Frankfurt"; hit; fwd=stale; ttl=0, "Shield-London"; hit; ttl=1420
```

У цьому прикладі крайовий сервер у Франкфурті зафіксував застарілий стан об'єкта (`ttl=0`) і перенаправив запит на щит у Лондоні. Лондонський щит мав свіжу копію (`ttl=1420`), тому оновив франкфуртський вузол без жодного звернення до основного дата-центру.

## 7. Протоколи прямого очищення: HTTP метод PURGE

Найпростіший спосіб інвалідації конкретної адреси — відправка спеціалізованого HTTP-запиту з методом `PURGE` безпосередньо на крайовий вузол або Ingress-проксі.

```http
PURGE /api/v1/products/1084 HTTP/1.1
Host: api.example.com
Fastly-Key: sec_token_9481abf02e8c4
Fastly-Soft-Purge: 1
User-Agent: Invalidation-Worker/2.4
```

Успішна відповідь крайового вузла:
```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Purge-Status: ok

{
  "status": "ok",
  "id": "184-1708291044-98412",
  "mode": "soft",
  "purged_at": "2026-08-20T01:45:00Z"
}
```

- Якщо передано заголовок `Fastly-Soft-Purge: 1` (або `X-Purge-Mode: soft`), об'єкт не видаляється з пам'яті, а переводиться у стан `stale`, що активує алгоритм `stale-while-revalidate`.
- За відсутності заголовка виконується жорстке вилучення (`hard purge`), і наступний запит призведе до синхронного `cache miss`.

## 8. Специфікація REST API провідних провайдерів

Для масової інвалідації або видалення за тегами використовується керуюча площина (Control Plane API) через виклики REST.

### Cloudflare API: Очищення за тегами, префіксами та хостами

Кінцева точка: `POST https://api.cloudflare.com/client/v4/zones/{zone_identifier}/purge_cache`
Автентифікація: Заголовок `Authorization: Bearer <API_TOKEN>` або `X-Auth-Key: <KEY>`.

#### Очищення за списком Cache-Tags (до 30 тегів за один виклик)
```json
{
  "tags": [
    "product-1084",
    "category-electronics",
    "brand-sony"
  ]
}
```

#### Очищення за точними префіксами URL (до 30 префіксів)
```json
{
  "prefixes": [
    "api.example.com/static/js/",
    "example.com/assets/images/catalog/"
  ]
}
```

#### Очищення за повними URL-адресами (до 30 файлів)
```json
{
  "files": [
    "https://example.com/index.html",
    {
      "url": "https://example.com/style.css",
      "headers": {
        "Origin": "https://example.com",
        "Accept-Encoding": "gzip, br"
      }
    }
  ]
}
```

#### Повне очищення всієї зони (Purge Everything)
```json
{
  "purge_everything": true
}
```

Формат відповіді:
```json
{
  "success": true,
  "errors": [],
  "messages": [],
  "result": {
    "id": "9a01f89bc72d41a498b3c108"
  }
}
```

### Fastly API: Миттєве очищення за сурогатними ключами

Кінцева точка для одного ключа: `POST https://api.fastly.com/service/{service_id}/purge/{surrogate_key}`

```http
POST /service/SU49219A01/purge/product-1084 HTTP/1.1
Host: api.fastly.com
Fastly-Key: d3b07384d113edec49eaa6238ad5ff00
Fastly-Soft-Purge: 1
Accept: application/json
```

Відповідь Fastly:
```json
{
  "status": "ok",
  "id": "291-1708291880-128491"
}
```

#### Масове очищення сурогатних ключів (до 256 ключів за виклик)
Кінцева точка: `POST https://api.fastly.com/service/{service_id}/purge`
```json
{
  "surrogate_keys": [
    "product-1084",
    "product-1085",
    "category-phones",
    "brand-apple"
  ]
}
```

### AWS CloudFront API: Створення пакета інвалідації

Кінцева точка: `POST https://cloudfront.amazonaws.com/2020-05-31/distribution/{DistributionId}/invalidation`

Тіло запиту (JSON):
```json
{
  "InvalidationBatch": {
    "CallerReference": "release-build-2026-08-20-v14.2.1",
    "Paths": {
      "Quantity": 3,
      "Items": [
        "/index.html",
        "/assets/styles/*",
        "/api/v2/catalog*"
      ]
    }
  }
}
```

Відповідь AWS CloudFront:
```json
{
  "Location": "https://cloudfront.amazonaws.com/2020-05-31/distribution/E1A2B3C4D5E6F/invalidation/I1234567890ABC",
  "Invalidation": {
    "Id": "I1234567890ABC",
    "Status": "InProgress",
    "CreateTime": "2026-08-20T01:30:05.120Z",
    "InvalidationBatch": {
      "CallerReference": "release-build-2026-08-20-v14.2.1",
      "Paths": {
        "Quantity": 3,
        "Items": [
          "/index.html",
          "/assets/styles/*",
          "/api/v2/catalog*"
        ]
      }
    }
  }
}
```

Отримання статусу виконання інвалідації:
`GET https://cloudfront.amazonaws.com/2020-05-31/distribution/{DistributionId}/invalidation/{InvalidationId}`

Статуси:
- `InProgress` — запит обробляється крайовими вузлами мережі.
- `Completed` — інвалідацію підтверджено на 100% точок присутності CloudFront.

### Akamai Fast Purge API (CCU v3)

Кінцева точка: `POST https://akab-xxxx.purge.akamaiapis.com/ccu/v3/invalidate/tag/production`
Автентифікація: Стандарт Akamai EdgeGrid HMAC-SHA256.

```json
{
  "objects": [
    "product-1084",
    "category-electronics"
  ]
}
```

Відповідь Akamai:
```json
{
  "httpStatus": 201,
  "detail": "Request accepted",
  "estimatedSeconds": 5,
  "purgeId": "69a8b1c2-3d4e-5f6a-7b8c-9d0e1f2a3b4c"
}
```

## 9. Безпека та автентифікація викликів Purge API

API інвалідації є критичним вектором безпеки: несанкціонований доступ до очищення кешу дозволяє зловмиснику організувати розподілену атаку на відмову в обслуговуванні (DDoS) шляхом безперервного скидання кешу та перевантаження бази даних.

### Механізми автентифікації запитів

1. **HMAC-підпис запитів (AWS SigV4 та Akamai EdgeGrid):**
   Кожен виклик API підписується криптографічним хешем SHA256 із використанням секретного ключа та мітки часу. Запит стає недійсним через 300 секунд після генерації, що виключає атаки повторного відтворення (replay attacks).
2. **Обмеження за білими списками IP (IP Whitelisting):**
   Панель керування CDN дозволяє приймати запити `PURGE` та звернення до REST API виключно зі статичних IP-адрес шлюзів безпеки або внутрішніх раннерів CI/CD.
3. **Гранулярні області доступу (Scoped API Tokens):**
   Сервісні облікові записи отримують мінімально необхідні права за принципом найменших привілеїв: наприклад, дозвіл `Purge-by-Tag` виключно для зони `api.example.com` без прав зміни конфігурації DNS чи SSL-сертифікатів.

## 10. Порівняння лімітів та квот Purge API

Нижче наведено зведену таблицю обмежень та характеристик систем інвалідації провідних провайдерів.

| Параметр | Fastly | Cloudflare Enterprise | AWS CloudFront | Akamai Fast Purge |
|---|---|---|---|---|
| **Середня затримка інвалідації (p95)** | ~150 мс | ~150–200 мс | 2–5 секунд | 2–5 секунд |
| **Очищення за тегами (Surrogate Keys)** | Підтримується (до 256/виклик) | Підтримується (до 30/виклик) | Не підтримується | Підтримується (до 100/виклик) |
| **Очищення за префіксами (Wildcard)** | Не рекомендовано (через VCL ban) | До 30 префіксів | Підтримується (`/*`) | Підтримується через CP-коди |
| **Підтримка Soft Purge** | Рідна (`Fastly-Soft-Purge`) | Підтримується через Ruleset | Підтримується через Cache Policy | Підтримується (Hold Stale) |
| **Ліміт запитів на годину** | Без обмежень (в межах RPS) | До 1200 викликів/хв | 3000 активних інвалідацій | 10 000 об'єктів/хв |
| **Ціноутворення** | Включено в базовий тариф | Включено в Enterprise | Перші 1000 шляхів/міс безкоштовно | Включено в контракт |

## 11. Коди помилок Purge API та стратегії повторів (Retries)

Під час масових релізів та автоматизованих інвалідацій клієнтські скрипти зобов'язані коректно обробляти помилки API керуючої площини.

| Код відповіді | Причина помилки | Рекомендована дія клієнта |
|---|---|---|
| `200 OK / 201 Created` | Запит успішно прийнято в обробку. | Фіксація успішного вилучення в журналах. |
| `400 Bad Request` | Некоректний синтаксис тегу або невалідний URL. | Не повторювати; перевірити форматування ASCII та відсутність пробілів. |
| `401 Unauthorized` | Відсутній або недійсний API-токен. | Оновити секрети автентифікації. |
| `403 Forbidden` | Токен не має прав `Purge` для даної зони. | Перевірити ACL та дозволи сервісного облікового запису. |
| `429 Too Many Requests` | Перевищено ліміт частоти звернень (Rate Limit). | Виконати повтор з експоненційним відкатом та джитером (Exponential Backoff with Jitter). |
| `500 / 502 / 503 / 504` | Тимчасовий збій керуючої площини CDN. | Повторити запит через 2, 4, 8 секунд. |

## 12. Програмне керування кешем на рівні Edge Workers

Сучасні платформи крайових обчислень (Cloudflare Workers, Fastly Compute, Vercel Edge Functions) надають прямий доступ до кеш-движка через JavaScript API (W3C Cache API).

```javascript
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const cacheKey = new Request(url.toString(), request);
    const cache = caches.default;

    // 1. Спроба вибірки з локального крайового кешу
    let response = await cache.match(cacheKey);

    if (!response) {
      // 2. Cache Miss: запит на Origin
      response = await fetch(request);

      // 3. Модифікація заголовків перед збереженням
      const headers = new Headers(response.headers);
      headers.set("Cache-Control", "public, max-age=86400, stale-while-revalidate=60");
      headers.set("Surrogate-Key", "catalog-products brand-sony");

      response = new Response(response.body, { ...response, headers });

      // 4. Асинхронний запис у кеш без затримки клієнтської відповіді
      ctx.waitUntil(cache.put(cacheKey, response.clone()));
    }

    return response;
  }
};
```

## 13. Інтеграція інвалідації в конвеєри CI/CD

Автоматизоване розгортання статичних та динамічних ресурсів у пайплайнах GitHub Actions або GitLab CI вимагає виконання кроку очищення після успішного оновлення файлів в об'єктному сховищі S3/GCS.

```yaml
# Приклад кроку в GitHub Actions для AWS CloudFront
- name: Invalidate CloudFront Distribution
  run: |
    INVALIDATION_ID=$(aws cloudfront create-invalidation \
      --distribution-id ${{ secrets.CLOUDFRONT_DIST_ID }} \
      --paths "/index.html" "/version.json" \
      --query 'Invalidation.Id' \
      --output text)
    echo "Created invalidation: $INVALIDATION_ID"
    
    # Очікування підтвердження завершення
    aws cloudfront wait invalidation-completed \
      --distribution-id ${{ secrets.CLOUDFRONT_DIST_ID }} \
      --id $INVALIDATION_ID
```

## 14. Телеметрія та OpenTelemetry конвенції для інвалідації

Для наскрізного трасування життєвого циклу інвалідації система моніторингу фіксує спани та атрибути згідно зі стандартом OpenTelemetry Semantic Conventions for HTTP:

- `http.response.header.cache-status` — строкове значення заголовка RFC 9211.
- `cdn.purge.target_type` — тип інвалідації (`url`, `tag`, `prefix`, `all`).
- `cdn.purge.keys_count` — кількість ключів, переданих у пакеті очищення.
- `cdn.purge.duration_ms` — час поширення команди до підтвердження крайовими вузлами.
- `cdn.cache.coalesced_requests` — лічильник паралельних потоків, схлопнутих під час ревалідації.

## 15. Очищення сховищ клієнта: Clear-Site-Data (W3C Standard)

Коли реліз містить критичні виправлення вразливостей або зміну схеми зберігання токенів сесії, необхідно гарантувати очищення не лише проміжних CDN, а й дискових та оперативних сховищ браузера користувача. Для цього бекенд додає заголовок `Clear-Site-Data`.

```http
HTTP/1.1 200 OK
Clear-Site-Data: "cache", "cookies", "storage", "executionContexts"
```

Директиви поля `Clear-Site-Data`:
- `"cache"` — очищає внутрішній HTTP-кеш браузера (включно із завантаженими скриптами, картинками, стилями) для даного origin.
- `"cookies"` — видаляє всі файли cookie, прив'язані до поточного домену.
- `"storage"` — повністю очищає `localStorage`, `sessionStorage`, бази даних `IndexedDB` та кеші `CacheStorage` (Service Worker Cache API).
- `"executionContexts"` — перезавантажує всі активні вкладки та фонові воркери (Service Workers) для скидання стану пам'яті JavaScript.
- `"*"` — еквівалентно увімкненню всіх вищезазначених директив одночасно.

Правила безпеки: Заголовок `Clear-Site-Data` обробляється браузерами виключно при передачі через захищене з'єднання HTTPS. Будь-які спроби передати його через відкритий протокол HTTP повністю ігноруються клієнтом.

## 16. Практичне діагностичне тестування через утиліту curl

Перевірка коректності роботи заголовків інвалідації, валідації та наявності службових ключів виконується за допомогою термінальних запитів.

### 1. Перевірка свіжості та наявності діагностичних заголовків
```bash
curl -svo /dev/null https://api.example.com/v1/products/1084 \
  -H "Fastly-Debug: 1" \
  -H "Accept-Encoding: gzip"
```

Очікувані заголовки у виводі:
```http
< HTTP/2 200
< cache-control: public, max-age=3600, stale-while-revalidate=60
< age: 412
< x-cache: HIT
< cache-status: "Edge-PoP"; hit; ttl=3188
```

### 2. Пряма відправка запиту на інвалідацію конкретного URL
```bash
curl -X PURGE https://api.example.com/v1/products/1084 \
  -H "Fastly-Key: sec_token_xxxxxx" \
  -H "Fastly-Soft-Purge: 1"
```

### 3. Тестування умовної ревалідації (304 Not Modified)
```bash
curl -sI https://api.example.com/v1/products/1084 \
  -H 'If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"'
```

Очікуваний статус-код:
```http
HTTP/2 304 Not Modified
cache-control: public, max-age=3600
```
