# 📋 Специфікація протоколів і заголовків APNs, FCM та WebPush

Системні push-шлюзи надають стандартизовані мережеві контракти для відправки повідомлень із бекенда сервісу на кінцеві пристрої. Цей довідник містить точні специфікації протоколів, заголовків, форматів корисного навантаження та кодів помилок для трьох основних екосистем: Apple Push Notification service (APNs), Firebase Cloud Messaging (FCM HTTP v1) та стандарту IETF WebPush (RFC 8030 / RFC 8292).

---

## 1. Специфікація Apple Push Notification service (APNs)

Шлюз APNs приймає вихідні повідомлення виключно через двійковий протокол **HTTP/2** поверх захищеного з'єднання TLS 1.2 або TLS 1.3 із підтримкою мультиплексування потоків у межах однієї TCP-сесії.

### 1.1 Мережеві адреси та автентифікація

| Середовище | Адреса шлюзу | Порт | Механізм автентифікації |
| :--- | :--- | :--- | :--- |
| **Production** | `api.push.apple.com` | `443`, `2197` | JWT (токен провайдера) або mTLS (сертифікат) |
| **Development (Sandbox)** | `api.sandbox.push.apple.com` | `443`, `2197` | JWT (токен провайдера) або mTLS (сертифікат) |

Порт `2197` надається як альтернатива для корпоративних мереж, де вихідний трафік на стандартний порт `443` підлягає глибокій інспекції або блокуванню міжмережевими екранами.

- **Автентифікація на базі токенів (JWT, рекомендовано):** Клієнт надсилає заголовок `authorization: bearer <JWT>`. Токен підписується асиметричним алгоритмом **ES256** (ECDSA на кривій NIST P-256 із гешуванням SHA-256) із використанням закритого ключа розробника (`.p8`). Токен дійсний щонайбільше 60 хвилин і є універсальним: один ключ дозволяє надсилати повідомлення в усі застосунки, зареєстровані за одним Team ID розробника.
- **Заголовок JWT (JOSE Header):**
  ```json
  {
    "alg": "ES256",
    "kid": "8ABC123XYZ"
  }
  ```
  Де `kid` (*Key ID*) — 10-символьний ідентифікатор ключа, виданий у панелі Apple Developer.
- **Тіло JWT (Claims Payload):**
  ```json
  {
    "iss": "DEF4567UVW",
    "iat": 1718900000
  }
  ```
  Де `iss` (*Issuer*) — 10-символьний Team ID команди розробників Apple, а `iat` (*Issued At*) — час генерації токена у форматі Unix Epoch (секунди).
- **Автентифікація за сертифікатами (mTLS, застарілий підхід):** Вимагає встановлення TLS-з'єднання з клієнтським сертифікатом X.509, виданим Apple для конкретного `bundle_id`. Сертифікат потребує щорічного перевипуску, а встановлене з'єднання не може надсилати повідомлення іншим застосункам компанії.

### 1.2 Заголовки HTTP/2 запиту APNs

Кожен push-запит надсилається двійковим методом `POST` на псевдозаголовок шляху `:path: /3/device/<device_token>`, де `<device_token>` — шістнадцятковий рядок (64 або більше символів), виданий операційною системою пристрою.

| Заголовок | Обов'язковий | Опис та допустимі значення |
| :--- | :--- | :--- |
| `authorization` | Так (для JWT) | `bearer <JWT_TOKEN>` |
| `apns-topic` | Так | Bundle ID цільового застосунку (наприклад, `com.example.app`). Для додаткових сервісів формуються суфікси:<br>• `<bundle_id>.voip` — для сповіщень PushKit VoIP;<br>• `<bundle_id>.complication` — для віджетів Apple Watch;<br>• `<bundle_id>.push-type.liveactivity` — для Dynamic Island та Live Activities. |
| `apns-push-type` | Так (з iOS 13) | Тип доставки, що визначає політику енергоспоживання ядра. Допустимі значення:<br>• `alert` — відображення банера / звуку / бейджа в системному UI;<br>• `background` — тихий фоновий пуш із пробудженням застосунку (вимагає `apns-priority: 5`);<br>• `voip` — вхідний аудіо/відеодзвінок через CallKit (вимагає негайної обробки);<br>• `complication` — фонове оновлення циферблата годинника watchOS;<br>• `liveactivity` — оновлення динамічного віджета на екрані блокування;<br>• `location` — запит геопозиції для дозволених системних служб. |
| `apns-priority` | Ні | Пріоритет черги доставки:<br>• `10` — негайна доставка (обов'язково для `alert`, `voip`, розбуджує пристрій);<br>• `5` — енергоощадна доставка з урахуванням системних бюджетів (обов'язково для `background`). |
| `apns-expiration` | Ні | Час закінчення терміну дії повідомлення (Unix Epoch у секундах). Якщо пристрій офлайн, шлюз зберігає повідомлення до вказаного часу. Значення `0` означає спробу негайної доставки без збереження у сховищі. |
| `apns-collapse-id` | Ні | Рядок довжиною до 64 байтів для згортання (*coalescing*) сповіщень. Якщо надходить новий пуш із тим самим ідентифікатором, попередній замінюється в черзі шлюзу та в шторці сповіщень пристрою. |
| `apns-id` | Ні | Канонічний UUID v4 для відстеження запиту. Якщо заголовок не передано, шлюз генерує його автоматично й повертає у заголовку відповіді. |

### 1.3 Мультиплексування та керування потоками в HTTP/2

Шлюз APNs оптимізовано для безперервного потоку сотень тисяч сповіщень через обмежену кількість постійних TCP-сесій:
- **Утилізація потоків (Streams):** Сервер повинен тримати невеликий пул постійних HTTP/2 з'єднань (наприклад, 4–8 з'єднань на процес) і паралельно відкривати до 500 одночасних потоків (*concurrent streams*) у межах однієї сесії. Створення нового TCP-з'єднання на кожен пуш суворо заборонено: шлюз Apple трактує це як атаку на відмову в обслуговуванні.
- **Стиснення заголовків HPACK:** Оскільки заголовки `authorization` та `apns-topic` ідентичні для мільйонів послідовних запитів, алгоритм HPACK передає їх у повному обсязі лише один раз під час відкриття сесії, а в наступних кадрах посилається на індекс у таблиці, скорочуючи розмір заголовків до 2–4 байтів.
- **Обробка кадру `GOAWAY`:** Якщо шлюз APNs планує перезавантаження або технічне обслуговування, він надсилає кадр `GOAWAY` із зазначенням номера останнього успішно обробленого потоку (`Last-Stream-ID`). Сервер зобов'язаний коректно дочекатися відповідей на активні потоки, закрити сокет і відкрити нове з'єднання до іншої IP-адреси кластера.

### 1.4 Формат корисного навантаження JSON (Payload)

Максимальний розмір корисного навантаження становить **4096 байтів** для стандартних сповіщень (`alert`, `background`) та **5120 байтів** для сповіщень типу `voip`.

```json
{
  "aps": {
    "alert": {
      "title": "Нове повідомлення",
      "subtitle": "Робочий чат",
      "body": "Олексій: Звіт готовий до перегляду"
    },
    "badge": 3,
    "sound": "default",
    "thread-id": "chat-room-42",
    "category": "CHAT_MESSAGE_CATEGORY",
    "content-available": 1,
    "mutable-content": 1
  },
  "custom_payload": {
    "message_id": "msg_987654321",
    "chat_id": 42
  }
}
```

**Призначення полів словника `aps`:**
- `alert` — об'єкт або рядок тексту для системного банера;
- `badge` — ціле число, що встановлює лічильник на іконці застосунку (значення `0` очищує бейдж);
- `sound` — назва аудіофайлу в бандлі застосунку або `default`;
- `content-available: 1` — прапорець пробудження застосунку у фоні (для `apns-push-type: background`);
- `mutable-content: 1` — прапорець перехоплення сповіщення системним розширенням `NotificationServiceExtension` для завантаження медіавкладень або розшифрування навантаження;
- `thread-id` — ідентифікатор групування повідомлень у шторці сповіщень;
- `category` — ідентифікатор типу дій (кнопки швидкої відповіді в банері).

### 1.5 Коди відповідей та причини помилок APNs

| HTTP Статус | Причина (`reason` у JSON відповіді) | Опис та обов'язкова дія сервера |
| :--- | :--- | :--- |
| **200 OK** | *(порожнє тіло)* | Повідомлення успішно прийнято шлюзом для доставки. |
| **400 Bad Request** | `BadDeviceToken` | Некоректний формат токена пристрою (довжина або символи). |
| **400 Bad Request** | `DeviceTokenNotForTopic` | Токен пристрою не відповідає вказаному `apns-topic` (інший Bundle ID). |
| **400 Bad Request** | `PayloadEmpty` / `PayloadTooLarge` | Тіло запиту порожнє або перевищує ліміт у 4096 байтів. |
| **403 Forbidden** | `InvalidProviderToken` / `ExpiredProviderToken` | Недійсний або застарілий JWT-токен провайдера. |
| **410 Gone** | `Unregistered` | **Критично:** користувач видалив застосунок або відкликав дозвіл. Бекенд **зобов'язаний негайно видалити** цей токен із бази даних. |
| **429 Too Many Requests** | `TooManyProviderTokenUpdates` | Перевищено ліміт частоти оновлення токенів провайдера для одного ключа. |
| **500 / 503** | `InternalServerError` / `Shutdown` | Тимчасовий збій серверів Apple. Повторити спробу з експоненційним відкотом (exponential backoff). |

## 2. Специфікація Firebase Cloud Messaging (FCM HTTP v1)

Сучасний інтерфейс FCM базується на стандартизованому **REST API v1** з автентифікацією через протокол OAuth 2.0 за допомогою сервісних облікових записів Google Cloud.

### 2.1 Точка входу та авторизація

- **Метод та URL:** `POST https://fcm.googleapis.com/v1/projects/{project_id}/messages:send`
- **Заголовок авторизації:** `Authorization: Bearer <OAUTH2_ACCESS_TOKEN>`
- **Отримання токена:** Бекенд генерує короткоживучий токен OAuth 2.0 (тривалість 1 година) з використанням приватного ключа сервісного акаунта Google (JSON-файл), запитуючи область видимості (*scope*):
  `https://www.googleapis.com/auth/firebase.messaging`

### 2.2 Структура JSON-запиту FCM v1

Максимальний розмір корисного навантаження у словнику `data` становить **4096 байтів**.

```json
{
  "message": {
    "token": "dK_123abcXYZ:APA91bF...",
    "notification": {
      "title": "Знижка 20%",
      "body": "Тільки сьогодні на всі замовлення",
      "image": "https://example.com/promo.png"
    },
    "data": {
      "promo_code": "SUMMER2026",
      "action_url": "app://promo/summer"
    },
    "android": {
      "priority": "HIGH",
      "ttl": "86400s",
      "collapse_key": "promo_campaign",
      "restricted_package_name": "com.example.app",
      "notification": {
        "channel_id": "marketing_alerts",
        "sound": "notification_sound",
        "click_action": "OPEN_PROMO_ACTIVITY",
        "tag": "promo_123"
      }
    },
    "apns": {
      "headers": {
        "apns-priority": "10",
        "apns-push-type": "alert"
      },
      "payload": {
        "aps": {
          "badge": 1,
          "sound": "default"
        }
      }
    },
    "webpush": {
      "headers": {
        "Urgency": "high"
      },
      "notification": {
        "icon": "/icons/icon-192.png",
        "badge": "/icons/badge-72.png"
      }
    }
  }
}
```

### 2.3 Опис полів структури повідомлення FCM v1

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `message.token` | Рядок | Реєстраційний токен цільового пристрою. Взаємовиключний із `topic` та `condition`. |
| `message.topic` | Рядок | Назва тематичного каналу підписки (наприклад, `news_technology`). |
| `message.condition` | Рядок | Логічний вираз для таргетингу на теми (наприклад, `'news' in topics && 'ua' in topics`). |
| `message.notification` | Об'єкт | Кросплатформні поля візуального сповіщення (`title`, `body`, `image`). Відображається системою автоматично. |
| `message.data` | Map<String, String> | Словник довільних ключів і значень (строго рядкових). Передається в обробник коду застосунку. |
| `android.priority` | Enum | `HIGH` (пробудження пристрою в режимі Doze, негайна доставка) або `NORMAL` (пакетна доставка у вікнах обслуговування). |
| `android.ttl` | Рядок | Час життя у форматі секунд із суфіксом `s` (наприклад, `3600s`). Максимум — 28 днів. |
| `android.collapse_key` | Рядок | Ключ для згортання застарілих повідомлень. |
| `android.notification.channel_id` | Рядок | Ідентифікатор Notification Channel (обов'язково для Android 8.0+). |
| `android.direct_boot_ok` | Boolean | Дозвіл на доставку сповіщення до першого розблокування пристрою після перезавантаження (Direct Boot mode). |

### 2.4 Коди помилок FCM v1

| HTTP Статус | Код помилки у `error.details[].errorCode` | Дія сервера провайдера |
| :--- | :--- | :--- |
| **404 Not Found** | `UNREGISTERED` | **Токен недійсний:** застосунок видалено або токен протух. Видалити токен із бази даних. |
| **400 Bad Request** | `INVALID_ARGUMENT` | Помилка валідації полів JSON або структури токена. |
| **403 Forbidden** | `SENDER_ID_MISMATCH` | Токен пристрою належить іншому проєкту Firebase. |
| **403 Forbidden** | `PERMISSION_DENIED` | Сервісний акаунт не має ролі `Firebase Cloud Messaging API Admin`. |
| **429 Too Many Requests** | `QUOTA_EXCEEDED` | Перевищено ліміти викликів API. Увімкнути тротлінг відправки. |
| **500 / 503** | `INTERNAL` / `UNAVAILABLE` | Серверна помилка інфраструктури Google. Застосувати повторну відправку. |

## 3. Специфікація стандарту WebPush (RFC 8030 / RFC 8292)

Стандарт WebPush забезпечує доставку повідомлень у браузери без прив'язки до вендорних SDK за допомогою прямого HTTP POST-запиту на кінцеву точку підписки (*Push Endpoint*).

### 3.1 Структура клієнтської підписки `PushSubscription`

Браузер повертає об'єкт підписки у форматі JSON:

```json
{
  "endpoint": "https://updates.push.services.mozilla.com/wpush/v2/gAAAAABl...",
  "expirationTime": null,
  "keys": {
    "p256dh": "BNcRdreALRFXTkOOUHK1EtK2wtaz5Ry4YwfJUDf3KChNScDH...",
    "auth": "tBHItJI5sv03adhR..."
  }
}
```

- `endpoint` — абсолютний URL шлюзу доставки, згенерований браузером;
- `keys.p256dh` — відкритий ключ клієнта на еліптичній кривій NIST P-256 (65 байтів у форматі Uncompressed Point, закодований у Base64URL);
- `keys.auth` — 16-байтний випадковий спільний секрет для автентифікації шифрування (Base64URL).

### 3.2 Заголовки HTTP POST-запиту WebPush (RFC 8030)

| Заголовок | Обов'язковий | Опис та допустимі значення |
| :--- | :--- | :--- |
| `TTL` | Так | Час життя повідомлення в секундах (ціле число від `0` до `2419200`). При `TTL: 0` повідомлення відкидається, якщо пристрій не на зв'язку. |
| `Urgency` | Ні | Терміновість доставки для оптимізації радіомодема:<br>• `very-low` — фонові нетермінові дані (синхронізація контактів);<br>• `low` — нетермінові сповіщення (новинні дайджести);<br>• `normal` — стандартні повідомлення (за замовчуванням);<br>• `high` — критичні сповіщення (дзвінки, вхідні чати). |
| `Topic` | Ні | Рядок (до 32 символів ASCII) для згортання застарілих повідомлень на шлюзі. |
| `Authorization` | Так (для VAPID) | Схема VAPID: `vapid t=<JWT_TOKEN>, k=<VAPID_PUBLIC_KEY>` або заголовок `WebPush <JWT_TOKEN>`. |
| `Content-Encoding` | Так (при наявності тіла) | Строго `aes128gcm` (за стандартом RFC 8291). |
| `Content-Type` | Так (при наявності тіла) | Строго `application/octet-stream`. |

### 3.3 Структура токена VAPID (RFC 8292)

Токен VAPID підписується алгоритмом **ES256** за допомогою закритого ключа сервера застосунків:

**Заголовок JWT:**
```json
{
  "typ": "JWT",
  "alg": "ES256"
}
```

**Тіло JWT (Claims):**
```json
{
  "aud": "https://updates.push.services.mozilla.com",
  "exp": 1718986400,
  "sub": "mailto:admin@example.com"
}
```
- `aud` (*Audience*) — протокол і доменне ім'я з `endpoint` підписки;
- `exp` (*Expiration*) — термін дії токена (не більше 24 годин від моменту генерації);
- `sub` (*Subject*) — контактна адреса адміністратора сервісу у форматі `mailto:admin@domain.com` або `https://domain.com/contact` на випадок виявлення зловживань.

### 3.4 Коди відповідей шлюзів WebPush (RFC 8030)

| HTTP Код | Опис | Дія сервера |
| :--- | :--- | :--- |
| **201 Created** | Повідомлення успішно прийнято та поставлено в чергу доставки. | Успіх. |
| **400 Bad Request** | Некоректний заголовок, помилка шифрування `aes128gcm` або недійсний VAPID JWT. | Виправити формат даних. |
| **404 Not Found** / **410 Gone** | **Підписка скасована:** користувач відкликав дозвіл у браузері або очистив профіль. | **Обов'язково видалити підписку** з бази даних. |
| **413 Payload Too Large** | Розмір зашифрованого бінарного тіла перевищує ліміт шлюзу (типово 4096 байтів). | Зменшити розмір навантаження. |
| **429 Too Many Requests** | Перевищено ліміт частоти запитів до кінцевої точки. | Зменшити частоту відправки. |
