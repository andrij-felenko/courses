# Ітератор

<preknowlist>
- [Інкапсуляція](root:sf-apps/encapsulation) — приховування внутрішнього устрою об'єкта; ітератор існує саме для того, щоб пройти колекцію, не розкриваючи, як усередині складено її елементи.
- [Інтерфейс проти реалізації](root:sf-apps/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні (дай наступний елемент), і тим, ЯК він це робить (масив, список, дерево).
- [Поліморфізм і динамічне зв'язування](root:sf-lang/polymorphism) — один і той самий цикл працює над будь-якою колекцією через спільний тип ітератора, а виклик у рантаймі йде в потрібну реалізацію.
</preknowlist>

У програмі повно наборів даних, які треба обійти по одному: масив чисел, список користувачів, множина тегів, дерево тек, рядки величезного файлу, результат запиту до бази. Бажання щоразу те саме — торкнутися кожного елемента рівно раз. А от **спосіб** торкнутися — щоразу інший.

Масив обходять індексом: `a[0]`, `a[1]`, і так далі. Але зв'язаний список (ланцюжок вузлів, де кожен тримає значення й посилання на наступний) індексу не має — там `list[i]` або взагалі не існує, або таємно біжить від початку списку щоразу, тобто наївний `for i` над списком тихо перетворюється на [квадратичну складність O(n²)](root:computability/asymptotic-complexity). Множина на хеш-таблиці взагалі не має поняття «елемент номер три». Дерево не лягає в один лінійний індекс — його можна обходити вглиб, вшир або за трьома різними порядками. Виходить, «як пройти» намертво залежить від того, як колекцію збудовано всередині.

І тут вилазить справжня біда. Якщо цикл, що обходить колекцію, мусить знати її внутрішній устрій — тримати індекс для масиву, смикати `.next` у вузла списку, лізти в кошики хеш-таблиці, — то, по-перше, він розриває [інкапсуляцію](root:sf-apps/encapsulation): кишки колекції вивалюються назовні, у кожен цикл. По-друге, змінив спосіб зберігання (був масив, став список) — і кожен такий цикл по всій програмі доводиться переписувати. Знання про форму колекції розтеклося скрізь, і кожна калюжа окремо болить.

## Винести позицію в окремий об'єкт

Ітератор (лат. *iterare* — повторювати, робити знову, від *iterum* — знову) розв'язує це одним рухом: **виносить «позицію в обході» в окремий об'єкт**. Цей об'єкт народжується від колекції, знає її внутрішній устрій (бо йому дозволено) і вміє одне-єдине — просунутися на крок і віддати черговий елемент. А назовні показує крихітний, однаковий для всіх інтерфейс із двох питань:

- «чи є ще?» — `hasNext()`;
- «дай наступний» — `next()`.

Усе. Цикл більше не знає ні масиву, ні списку, ні дерева — він знає лише ці два питання. А те, як насправді перейти від елемента до елемента, заховане всередині ітератора: для масиву він рухає індекс, для списку йде по `.next`, для дерева тримає власний стек напівпройдених вузлів.

Це і є суть, яку «банда чотирьох» (автори канонічної книги про патерни 1994 року — Ерік Ґамма, Річард Гелм, Ральф Джонсон, Джон Вліссідес) сформулювала так: дати спосіб «access the elements of an aggregate object sequentially without exposing its underlying representation» — послідовно дістати елементи набору, не розкриваючи, як він улаштований усередині. Сам прийом старший за GoF: ітератори як конструкцію мови ще в середині 1970-х придумала Барбара Ліскоу для мови CLU — саме звідти згодом Python і Ruby взяли слово `yield`. [Як абстракція обходу пройшла шлях від курсорів баз даних через CLU до C++ STL](root:sf-apps/iterator/hist-clu-liskov-iterator.md) — окрема, повчальна історія.

![Три різні за формою колекції — масив, зв'язаний список, дерево — кожна народжує свій ітератор; усі три ітератори показують назовні той самий інтерфейс hasNext() і next(); єдиний цикл праворуч смикає ці два методи, не знаючи, яка колекція за ними. Між циклом і нутрощами колекцій — стіна незнання.](img/iterator-uniform.svg)
*Форма колекції лишається схованою: один цикл обходить масив, список і дерево однаково, бо бачить лише два методи ітератора, а не внутрішній устрій.*

## Механізм упритул

Візьмімо зв'язаний список і напишімо йому ітератор руками. Спершу — спільний тип, сама обіцянка «мене можна перебирати»:

```ts
interface Iter<T> {
  hasNext(): boolean;
  next(): T;
}
```

Тепер список. Він складається з вузлів, кожен тримає значення й посилання на наступний. Знання про це — приватне; назовні список лише вміє видати свій ітератор:

```ts
class Node<T> {
  constructor(public value: T, public next: Node<T> | null = null) {}
}

class LinkedList<T> {
  private head: Node<T> | null = null;
  // методи додавання вузлів опущено

  iterator(): Iter<T> {
    let cursor = this.head;              // курсор-позиція живе В ітераторі
    return {
      hasNext: () => cursor !== null,
      next: () => {
        const v = cursor!.value;
        cursor = cursor!.next;           // крок по внутрішній структурі
        return v;
      },
    };
  }
}
```

Придивись, де сховане знання. Те, що список — це ланцюжок вузлів через `.next`, знає **тільки** метод `iterator()`. Курсор (поточна позиція обходу) живе всередині ітератора, а не в списку, — і тому можна завести два незалежні ітератори та обходити той самий список двічі водночас, і вони не заважатимуть одне одному.

А цикл, що це споживає, тепер сліпий до форми колекції:

```ts
const it = list.iterator();
while (it.hasNext()) {
  const user = it.next();
  console.log(user);
}
```

І ось головне: цей самий цикл дослівно працюватиме над деревом, хеш-множиною чи рядками файлу — треба лише, щоб вони віддавали свій `Iter`. Заміни `LinkedList` на збалансоване дерево — жоден рядок циклу не зміниться. Через [поліморфізм](root:sf-lang/polymorphism) `it` у рантаймі виявиться потрібним ітератором, і `next()` піде в його реалізацію.

> 🔧 **Навіщо це.** Це те, що дає змогу писати колекцію й код, який її обходить, різним людям і в різний час. Автор бібліотеки може півроку по тому переписати колекцію з масиву на дерево заради швидкості — і жоден із тисяч циклів у чужому коді, що її перебирають, не зламається, бо всі вони бачили лише `hasNext()`/`next()`. Без ітератора будь-яка зміна внутрішнього устрою колекції тягла б за собою правку кожного місця, що її обходить.

Те, що обхід дерева зовні виглядає точно як обхід масиву, — не косметика, а збережена інкапсуляція під час обходу. Колекція далі вільна змінювати свій устрій: сьогодні масив, завтра дерево, післязавтра дані з мережі — а весь код, що її перебирає, лишається незмінним, бо він ніколи й не бачив нутрощів. Це і є та сама «не розкриваючи внутрішнього устрою» з формулювання GoF, тільки вже як відчутна вигода: одне місце знає форму (ітератор), решта програми — ні.

## Хто крутить колесо: зовнішній проти внутрішнього

Досі цикл сам смикав `next()` — крутив колесо власноруч. Такий ітератор називають **зовнішнім** (active): кермо в клієнта. Він вирішує, коли зробити крок, може спинитися посеред дороги (`break` на першому, що підійшов), може вести два ітератори паралельно й порівнювати їхні елементи по черзі.

Є й дзеркальний спосіб — **внутрішня ітерація** (passive). Тут ти не витягуєш елементи, а навпаки — віддаєш колекції функцію, і вона сама пробігає всередині й кличе твою функцію на кожному елементі. Це `forEach`, `map`, Ruby-шне `each`:

```ts
list.forEach(user => console.log(user));
```

Різниця не косметична — вона в тому, **хто керує циклом**. У зовнішнього ітератора кермо в клієнта: легко вийти достроково, поставити на паузу, зчепити дві послідовності й іти ними синхронно. У внутрішньої ітерації кермо в колекції: код коротший, і колекція сама відповідає за ресурс (закрити файл, відпустити замок), зате вирватися з середини чи йти двома наборами водночас незручно — керуєш не ти. Передана всередину функція — це [функція як значення](root:sf-lang/first-class-functions): її кладуть в аргумент і викликають потім. [Чому передавання функції в колекцію математично те саме, що згорнути її згортком, і що робить обхід коректним](root:sf-apps/iterator/math-iterator-fold-duality.md) — окремий погляд на цю дуальність.

![Дві панелі, що показують напрям керування. Ліворуч «зовнішній ітератор»: клієнт у власному циклі тягне next() з ітератора — стрілка керування йде від клієнта до ітератора, клієнт за кермом. Праворуч «внутрішня ітерація»: клієнт віддає колекції функцію, а колекція у власному циклі кличе цю функцію на кожному елементі — стрілка керування йде від колекції до функції клієнта.](img/iterator-control.svg)
*Той самий обхід, але кермо в різних руках: зовнішній ітератор клієнт тягне сам, у внутрішній ітерації цикл крутить колекція й гукає клієнта.*

## Ліниво: потік на витягування

Тепер найцікавіше. Раз елементи витягують по одному через `next()`, то їх не конче мати всі одразу. Ітератор може **виробляти кожен елемент на вимогу, точно в мить запиту**. А це відмикає те, чого звичайним циклом над готовим списком не зробиш.

Можна обходити нескінченне. Послідовність усіх натуральних чисел, чисел Фібоначчі, простих — її не складеш у масив (він безмежний), але можна мати ітератор, що на кожен `next()` рахує наступний член. Береш скільки треба й спиняєшся.

Можна обходити величезне, не вантажачи його в пам'ять. Рядки файлу на десять гігабайтів: ітератор читає по рядку з диска на кожен крок, і в пам'яті одночасно живе один рядок, а не весь файл. Так само курсор бази даних тягне записи порціями, поки ти їх перебираєш.

У цій ролі ітератор перестає бути «гарнішим циклом» і стає **потоком на витягування** (pull-based): джерело буває безмежним чи віддаленим, а споживач бере рівно стільки, скільки з'їсть.

![Нескінченне джерело чисел Фібоначчі ліворуч; посередині ітератор-клапан, що на кожен запит next() пропускає рівно один наступний елемент; праворуч споживач, який просить лише три перші (0, 1, 1) і спиняється. Решта послідовності ніколи не обчислюється — стрілка джерела йде в безмежність.](img/iterator-lazy.svg)
*Ітератор виробляє елементи на вимогу: споживач узяв три перші члени й спинився, а нескінченний «хвіст» послідовності так і не порахувався.*

## Генератори: мову просять написати ітератор за тебе

Писати такий ітератор руками виходить марудно: доводиться самому пам'ятати, «де я спинився», окремими полями стану — а для дерева це цілий стек напівпройдених вузлів. Тому сучасні мови роблять цю роботу за тебе через **генератори** й слово `yield`. Пишеш обхід звичайним кодом, а там, де хочеш віддати черговий елемент, ставиш `yield` — і на цьому місці функція **завмирає**, щоб ожити з того самого рядка на наступний запит:

:::tabs
```py
def fibonacci():
    a, b = 0, 1
    while True:           # нескінченний — і це нормально
        yield a           # віддали a й заснули тут
        a, b = b, a + b   # прокинулись — рахуємо далі

it = fibonacci()
print(next(it), next(it), next(it), next(it))   # 0 1 1 2
```
```js
function* fibonacci() {
  let [a, b] = [0, 1];
  while (true) {           // нескінченний генератор
    yield a;               // віддали a й заснули тут
    [a, b] = [b, a + b];   // прокинулись — рахуємо далі
  }
}

const it = fibonacci();
console.log(it.next().value, it.next().value, it.next().value);   // 0 1 1
```
:::

Мова сама перетворила звичайну функцію на скінченний автомат, що пам'ятає своє місце між викликами, — тобто написала за тебе весь той ручний стан ітератора. По суті генератор — це обчислення, заморожене посеред кроку; ітератор — це обхід, заморожений посеред кроку; те саме явище під двома іменами. Механізм «завмерти й ожити з того ж місця» — це [корутина](root:sys-plang-cpp/coroutines); і ті самі ітератори CLU 1970-х були реалізовані рівно як корутини.

Тому на практиці свій ітератор нині майже ніколи не пишуть класом — пишуть `yield`. Ба більше, майже кожна сучасна мова вбудувала ітератор просто в синтаксис циклу. `for x in колекція` у Python, `for (const x of колекція)` у JavaScript, `for (auto x : колекція)` у C++, `for x in колекція` над трейтом `Iterator` у Rust — усе це під капотом бере в колекції ітератор і крутить `next()`, поки є елементи. Щоб твоя власна колекція працювала у звичайному `for`, ти не пишеш цикл — ти реалізуєш гачок протоколу (`__iter__` у Python, `[Symbol.iterator]` у JS, `begin()`/`end()` у C++, `IntoIterator` у Rust), і мова далі обходить її сама:

```py
class LinkedList:
    def __iter__(self):
        node = self._head
        while node is not None:
            yield node.value          # генератор — і колекція вже перебирається for-ом
            node = node.next

for user in linked_list:              # працює, бо є __iter__
    print(user)
```

## Пастка: недійсний ітератор

Є одна пастка, за яку варто знати одразу. Ітератор тримає позицію **всередині живої колекції**. Якщо колекцію змінити посеред обходу — щось додати чи прибрати, — позиція може поплисти: ітератор перескочить елемент, відвідає його двічі, а то й покаже на вже звільнену пам'ять. Механізм простий: ітератор закешував індекс, покажчик чи внутрішній лічильник — а зміна колекції зробила їх несправжніми (масив перерозподілив пам'ять під більший розмір, вузол списку від'єднали, кошики хеш-таблиці перебудували).

Мови захищаються по-різному. Java кидає `ConcurrentModificationException`, щойно помітить зміну під час обходу (стратегія «падай швидко», fail-fast). Python на зміні розміру словника під час циклу підіймає `RuntimeError`. C++-ітератори просто стають недійсними, і подальше звертання до них — неозначена поведінка (класика: `push_back` у `vector`, що змусив його переїхати в нову пам'ять, знецінює всі старі ітератори). Правило одне: **не міняй те, що саме обходиш**. Треба міняти — або збери зміни в окремий список і застосуй після обходу, або користуйся тим методом видалення, який дає сам ітератор і сам лагодить свою позицію.

Ось як тихо кусає навіть найпростіший випадок:

```py
xs = [1, 2, 4, 5]
for x in xs:
    if x % 2 == 0:
        xs.remove(x)     # міняємо те, що обходимо
print(xs)                # [1, 4, 5] — але 4 мало зникнути! Його проскочило
```

Прибравши `2`, ми зсунули всі наступні елементи на позицію ліворуч; а внутрішній індекс циклу тим часом поповз далі — і `4`, яке стало на місце двійки, проскочило повз перевірку. Жодної помилки, просто тихо неправильний результат — найгірший різновид.

## Коли писати самому, а коли воно вже є

Отже, коли ітератор варто писати руками? Тоді, коли обхід нетривіальний або сам по собі цінний: свій порядок обходу дерева (вглиб, вшир, за зростанням ключа); ліниві чи нескінченні послідовності; зовнішнє керування, де треба зупинятися, ставити на паузу, зчіплювати кілька джерел; ховання складного чи віддаленого джерела (файл, мережа, база) за простим «дай наступний». А для звичайного масиву чи списку думати про це не треба взагалі — мова вже дала для них ітератор, і `for` над ними працює сам.

Саме тому ітератор — рідкісний патерн, який виявився настільки корисним, що мови всмоктали його прямо в синтаксис: ти користуєшся ним у кожному `for x in …`, навіть не називаючи на ім'я. [Робочий лінивий ітератор дерева — обхід за зростанням ключа з явним стеком, крок за кроком, з аналізом складності](root:sf-apps/iterator/proj-lazy-tree-iterator.md) показує весь механізм у дії там, де він справді нетривіальний.
