# 🔌 Порівняння алгоритмів узгодження: Double-Ended проти LIS проти Fiber

Архітектура оновлення користувацького інтерфейсу в сучасних фронтенд-каркасах спирається на принципово різні підходи до пошуку відмінностей та мутації DOM. Нижче наведено технічний аналіз чотирьох провідних стратегій узгодження: двостороннього алгоритму Snabbdom/Vue 2, алгоритму LIS у Vue 3 та Inferno, однопрохідної моделі волокон React Fiber та безвіртуального підходу тонкої реактивності (Solid.js / Svelte 5).

## 1. Двосторонній алгоритм (Double-Ended Diffing) — Snabbdom та Vue 2

Двосторонній алгоритм узгодження оптимізує найбільш поширені сценарії взаємодії користувача зі списками: додавання елементів на початок або в кінець списку, видалення з кінців та дзеркальний розворот (*reverse*).

Алгоритм використовує чотири покажчики: `oldStartIdx`, `oldEndIdx`, `newStartIdx` та `newEndIdx`. На кожній ітерації циклу виконуються чотири евристичні перевірки:

1. **Збіг голів (`oldStart == newStart`):** якщо вузли на початку масивів мають однаковий ключ і тег, викликається `patch`, а покажчики зміщуються вперед (`oldStartIdx++`, `newStartIdx++`). Переміщення в DOM не потрібне.
2. **Збіг хвостів (`oldEnd == newEnd`):** якщо вузли в кінці масивів збігаються, викликається `patch`, покажчики зміщуються назад (`oldEndIdx--`, `newEndIdx--`). Переміщення в DOM не потрібне.
3. **Зсув з голови в хвіст (`oldStart == newEnd`):** вузол перемістився з початку списку в кінець. Рушій викликає `patch` і переміщує реальний DOM-вузол викликом `parent.insertBefore(oldStartVNode.dom, oldEndVNode.dom.nextSibling)`. Покажчики оновлюються: `oldStartIdx++`, `newEndIdx--`.
4. **Зсув з хвоста в голову (`oldEnd == newStart`):** вузол перемістився з кінця на початок. Викликається `patch` та `parent.insertBefore(oldEndVNode.dom, oldStartVNode.dom)`. Покажчики: `oldEndIdx--`, `newStartIdx++`.
5. **Пошук за хеш-таблицею (Fallback):** якщо жодна з чотирьох перевірок не спрацювала, поточний `newStart`-елемент шукається в хеш-карті ключів старих дітей. Знайдений елемент переноситься на початок, новий — монтується, а `newStartIdx++`.

**Переваги:** Мінімальні накладні витрати пам'яті (не потрібні допоміжні масиви зміщень), швидкість роботи на граничних операціях вставки та видалення `O(N)`.

**Недоліки:** Не знаходить глобально оптимальну послідовність переміщень при складних довільних перестановках (*shuffle*), генеруючи зайві виклики `insertBefore`.

## 2. Алгоритм LIS (Longest Increasing Subsequence) — Vue 3 та Inferno

У Vue 3 та рушії Inferno алгоритм узгодження списків розбито на три фази:

1. **Префіксне та суфіксне вирівнювання:** пара покажчиків синхронно зсувається зліва направо, доки ключі збігаються, а потім справа наліво. Це миттєво відсікає незмінні краї списку.
2. **Побудова масиву джерел (Source Map):** для центральної несинхронізованої частини створюється масив цілих чисел `sources` довжиною `newLength`, де кожен елемент містить індекс цього вузла в старому масиві (або `-1`, якщо вузол новий).
3. **Обчислення LIS:** над масивом `sources` за час `O(N log N)` за допомогою бінарного пошуку та відновлення предків обчислюється найдовша монотонно зростаюча підпослідовність індексів.

Вузли, чиї індекси потрапили в LIS, вважаються **нерухомими якорями**: вони вже розташовані у правильному відносному порядку один до одного. Рушій обходить масив справа наліво і викликає `insertBefore` **виключно** для тих елементів, які не входять до знайденої підпослідовності.

**Переваги:** Абсолютно мінімальна кількість DOM-переміщень серед усіх відомих VDOM-алгоритмів.

**Недоліки:** Додаткова алокація пам'яті під масиви `sources` та зв'язки LIS, вища константна складність коду при дрібних змінах.

## 3. Односпрямований Fiber-дифінг — React 16+

React використовує принципово іншу філософію. Замість повноцінного двостороннього порівняння чи LIS, узгодження в React є **однопрохідним зліва направо** над однозв'язним списком волокон (*Fiber Tree*).

Кожне волокно містить посилання `child` (перша дитина), `sibling` (наступний брат) та `return` (батьківський вузол).

Алгоритм узгодження списку дітей виконує два послідовні проходи:
1. **Перший прохід:** ітерація по новому масиву та старому списку `sibling` одночасно. Доки ключі збігаються, волокна оновлюються на місці. Як тільки виявлено перший незбіг ключа — цикл переривається.
2. **Другий прохід:** залишок старих волокон поміщається в хеш-таблицю `Map<key, Fiber>`. Далі алгоритм ітерується по залишку нового масиву, дістає старі волокна за ключем і веде змінну `lastPlacedIndex`. Якщо індекс знайденого старого волокна `< lastPlacedIndex`, це волокно позначається прапорцем `Placement` (вимагає виклику `insertBefore` у фазі фіксації). Якщо `index >= lastPlacedIndex`, елемент залишається на місці, а `lastPlacedIndex = index`.

**Переваги:** Повна сумісність з асинхронним перериваним рендерингом (*Time Slicing / Suspense / Concurrent Mode*). Алгоритм не потребує утримання масивів у пам'яті та працює безпосередньо над графом волокон.

**Недоліки:** Падає у найгірший випадок при простому розвороті списку (`reverse`): елемент із кінця зміщує `lastPlacedIndex` на максимум, змушуючи React викликати `insertBefore` для всіх наступних `N-1` елементів списку.

## 4. Fine-Grained Signals — Solid.js та Svelte 5

Підхід тонкої реактивності повністю відмовляється від Virtual DOM та порівняння дерев на етапі виконання (*zero runtime diffing*).

Компілятор аналізує шаблон компонента і розділяє статичну розмітку та динамічні точки прив'язки:
- Статичний HTML клонується однією нативною операцією `templateNode.cloneNode(true)`.
- Для кожного виразу `<div>{count()}</div>` створюється реактивний ефект (`createEffect`), що підписується безпосередньо на сигнал `count`.

Коли сигнал змінює значення, функція-обробник не перерендерить компонент і не створює нове віртуальне дерево. Вона напряму викликає:

```ts
textNode.data = count();
```

**Переваги:** 
- Нульові витрати оперативної пам'яті на алокацію VNode-об'єктів;
- Часова складність оновлення строго `O(1)` відносно кількості змінених даних, а не `O(N)` від розміру дерева компонента;
- Відсутність навантаження на збирач сміття (GC) рушія V8.

**Недоліки:** Вища складність первинного компілятора, необхідність підтримувати граф підписок сигналів у пам'яті.

## Зведена порівняльна таблиця стратегій

| Характеристика | Double-Ended (Snabbdom / Vue 2) | LIS Diffing (Vue 3 / Inferno) | Fiber Single-Pass (React) | Fine-Grained Signals (Solid / Svelte 5) |
| :--- | :--- | :--- | :--- | :--- |
| **Структура пам'яті** | Дерево VNode об'єктів | Дерево VNode + ShapeFlags | Однозв'язний граф Fiber | Граф підписок сигналів |
| **Складність списків** | `O(N)` | `O(N log N)` | `O(N)` | `O(1)` для значень / LIS для списків |
| **Кількість мутацій DOM** | Середня (субоптимальна при shuffle) | Мінімальна (математичний оптимум) | Висока при reverse списку | Мінімальна (точкові мутації) |
| **Асинхронний тайм-слайсинг** | Ні (синхронна рекурсія) | Ні (синхронний diff) | Так (Concurrent Mode) | Не потрібен (дифінг відсутній) |
| **Алокація пам'яті при рендері** | Нове VNode-дерево щоразу | Нове VNode-дерево + Source map | Нові об'єкти елементів та Fiber | 0 байтів при повторних тиках |
