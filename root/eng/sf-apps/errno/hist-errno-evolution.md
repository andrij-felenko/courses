# 📜 Від PDP-11 до багатопотокового TLS: еволюція errno

У ранніх версіях операційної системи Unix на міні-комп'ютерах PDP-11 мова C та системні інтерфейси будувалися довкола гранично простих угод. Процесор мав лічені регістри загального призначення, пам'ять вимірювалася десятками кілобайтів, а модель виконання була суворо однопотоковою: один процес складався з одного єдиного потоку команд. Коли системний виклик зазнавав невдачі, ядро виставляло прапорець перенесення в апаратному регістрі стану процесора, записувало код помилки в спільну комірку пам'яті процесу, а бібліотечна обгортка переносила це число в глобальну змінну `int errno`.

Ця схема працювала бездоганно майже два десятиліття. Глобальна змінна `errno` була звичайним цілим числом, оголошеним у системній бібліотеці (`extern int errno;`). Програміст перевіряв, чи повернув виклик `open()` або `read()` значення `-1`, і за потреби читав `errno`, щоб вивести повідомлення через `perror()`. Та щойно наприкінці 1980-х та на початку 1990-х років в операційних системах з'явилися легковагі процеси та нитки виконання (англ. *threads*, від латин. *filum* — нитка), проста модель глобальної змінної спричинила архітектурну кризу.

### Криза багатопотоковості та гонитва даних

Уявімо процес із двома нитками, які виконуються паралельно на багатопроцесорній машині або в режимі квантування часу. Нитка А викликає `open("/nonexistent", O_RDONLY)` для перевірки наявності опціонального конфігураційного файлу. Ядро повертає `-1` і записує в пам'ять код `ENOENT` (2). Одразу після цього операційна система перемикає контекст процесора на нитку Б, або нитка Б на сусідньому процесорному ядрі викликає `read(socket_fd, buf, 1024)`. Цей виклик теж зазнає невдачі, наприклад через розрив з'єднання, і записує в ту саму пам'ять код `ECONNRESET` (104).

Коли нитка А відновлює виконання й читає `errno`, вона бачить `ECONNRESET` замість `ENOENT`. Програма робить абсолютно хибний висновок: замість створення нового файлу вона аварійно зупиняється з повідомленням про обрив мережевого з'єднання, якого ніколи не відкривала. Ще гірший сценарій наставав, коли між невдалим викликом у нитці А та читанням `errno` нитка Б виконувала успішний системний виклик, який у деяких старих реалізаціях міг модифікувати допоміжні змінні.

Виникла класична гонитва даних (англ. *race condition*). Помилка однієї нитки непомітно отруювала стан іншої.

### Чому не змінили сигнатури функцій

Коли робоча група POSIX (комітет IEEE 1003) взялася за стандартизацію інтерфейсу ниток виконання у стандарті POSIX.1c-1995 (IEEE Std 1003.1c-1995), інженери розглядали кардинальний крок: змінити сигнатури системних викликів. Замість того, щоб повертати `-1` і виставляти побічний стан у змінну, системні виклики мали б повертати код помилки напряму через значення функції або через результуючу структуру:

```
[Старий виклик]: ssize_t read(int fd, void *buf, size_t count);
[Пропонований]:  int read(int fd, void *buf, size_t count, ssize_t *bytes_read);
```

Такий підхід був відкинутий через колосальну ціну зворотної несумісності. До середини 1990-х років існували мільйони рядків вихідного коду на C для Unix, BSD, SunOS, HP-UX, AIX та Linux. Переписування сигнатур фундаментальних функцій зруйнувало б усю екосистему програмного забезпечення. Потрібно було знайти рішення, яке зберегло б наявний вихідний синтаксис викликів `if (read(...) == -1) { handle(errno); }`, але зробило б збереження коду повністю ізольованим для кожної нитки.

Комітет вирішив розділити функції на дві категорії:
1. **Нові функції багатопотокового API (pthreads)** отримали чистий інтерфейс: вони повертають код помилки (`0` при успіху або додатне число помилки, як-от `EINVAL` чи `EBUSY`) як значення самої функції, взагалі не чіпаючи `errno`. Наприклад, `pthread_mutex_lock()` повертає `0` або `EDEADLK`, а не `-1`.
2. **Історичні системні виклики та стандартна бібліотека C** зберегли свій вигляд, але механізм самого `errno` було фундаментально перевинайдено через препроцесор і компілятор.

### Макрос, що маскує виклик функції

Рішення полягало в тому, щоб перетворити `errno` з назви змінної на макрос препроцесора, що розгортається в розіменування вказівника на локальну пам'ять нитки.

У стандартному заголовному файлі `<errno.h>` компілятор замінив оголошення `extern int errno;` на конструкцію такого вигляду:

:::tabs
```c
#ifdef _REENTRANT
/* Для збірки з підтримкою багатопотоковості */
extern int *__errno_location(void);
#define errno (*__errno_location())
#else
/* Застарілий однопотоковий варіант */
extern int errno;
#endif
```
```cpp
// У сучасній стандартній бібліотеці C++ (<cerrno>)
// макрос завжди розгортається в ізольовану комірку поточної нитки:
#include <cerrno>
// errno -> (*__errno_location()) або (*__error())
```
:::

У різних сімействах Unix-подібних операційних систем внутрішня функція дістала різні назви:
- У **Linux** з бібліотекою GNU C Library (glibc) та musl вона зветься `__errno_location()`.
- У **FreeBSD**, **OpenBSD** та **Apple macOS / iOS** вона зветься `__error()`.
- У **Solaris** та **Illumos** використовувалася назва `___errno()`.
- У **NetBSD** функція називається `__errno()`.
- У **Windows CRT** аналогічний механізм для сумісності з POSIX функціями зветься `_errno()`.

Оскільки макрос розгортається в розіменування адреси `(*__errno_location())`, він поводиться як повноцінний lvalue (вираз, що має адресу в пам'яті). Це означає, що старий код, який присвоював значення змінній:

:::tabs
```c
errno = 0;
```
```cpp
errno = 0; // розгортається у (*__errno_location()) = 0
```
:::

після препроцесора перетворюється на:

:::tabs
```c
(*__errno_location()) = 0;
```
```cpp
(*__errno_location()) = 0; // прямий запис у пам'ять поточної нитки
```
:::

Викликається функція `__errno_location()`, яка дістає адресу комірки `errno` саме тієї нитки, що зараз виконує код, і записує туди нуль. Для компілятора та програміста синтаксис лишився незмінним, а семантична ізоляція стала абсолютною.

### Апаратна оптимізація через регістри сегментів

Виклик окремої функції `__errno_location()` на кожне читання чи запис `errno` міг би створити відчутні накладні витрати у вузьких місцях програм. Тому розробники компіляторів та системних бібліотек інтегрували цей механізм безпосередньо в апаратну підтримку локальної пам'яті ниток (англ. *Thread-Local Storage*, TLS).

На архітектурі x86-64 операційна система виділяє кожній нитці керівний блок (англ. *Thread Control Block*, TCB). Базова адреса цього блоку завантажується в модель-специфічний регістр сегмента `%fs`. Змінна `errno` розміщується за фіксованим зсувом усередині цього блоку.

Сучасний компілятор GCC або Clang за увімкненої оптимізації генерує для операції `errno = 0` не виклик функції через `call`, а одну-єдину апаратну інструкцію:

```
movl  $0, %fs:__errno_location@tpoff
```

Ця інструкція виконується за один такт процесора без звернення до таблиці символів і без збереження регістрів на стеку. Нитка звертається до власної пам'яті зі швидкістю звичайної локальної змінної на стеку.

### Стандартизація в POSIX та C99

Еволюція завершилася повною фіксацією в міжнародних стандартах:
- **POSIX.1-2001 (IEEE Std 1003.1-2001)** остаточно закріпив, що `errno` зобов'язаний бути потокобезпечним макросом у будь-якій сумісній системі. Вимога прапорця `_REENTRANT` пішла в минуле — багатопотоковість стала базовим стандартом поведінки за замовчуванням.
- **C99 (ISO/IEC 9899:1999)** у розділі 7.5 зафіксував, що `errno` є макросом, що розгортається в модифікований lvalue типу `int` із потоковим або статичним часом життя.
- **C11 (ISO/IEC 9899:2011)** та **C++11** додали в мову ключові слова `_Thread_local` та `thread_local`, узагальнивши механізм, створений спеціально для `errno`, на будь-які призначені для користувача змінні.

Шлях `errno` від одинарної комірки в оперативній пам'яті PDP-11 до апаратно-керованого сегмента TLS демонструє головний принцип еволюції системного програмування: збереження стабільності інтерфейсу для прикладного інженера ціною глибинної модернізації внутрішнього механізму в ядрі та компіляторі.
