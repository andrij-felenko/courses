# 🧮 Економічна модель ескалації вартості дефектів

Виправлення архітектурної помилки на етапі тексту коштує хвилини редагування, тоді як те саме виправлення в діючій системі вимагає аварійних міграцій баз даних, компенсацій користувачам і тижнів роботи команди. Математична модель ескалації вартості дефектів пояснює, чому написання технічного документу (Design Doc) дає кратний фінансовий виграш навіть з урахуванням часу на його рев'ю.

## Експоненційне зростання вартості за фазами (модель Боема)

Емпіричні дослідження інженерії програмного забезпечення, започатковані Баррі Боемом (Barry Boehm) у 1970–1980-х роках у TRW та підтверджені аналізом тисяч проектів у NASA та IEEE, встановили: вартість виправлення дефекту зростає експоненційно залежно від стадії життєвого циклу, на якій цей дефект виявлено.

Позначимо фази розробки дискретним індексом `t`:
- `t = 0` — фаза проектування та узгодження (Design Doc / RFC);
- `t = 1` — фаза написання вихідного коду (Implementation);
- `t = 2` — фаза інтеграційного тестування та перевірки на staging (Verification);
- `t = 3` — промислова експлуатація в продакшені (Production).

Вартість виправлення одного архітектурного дефекту `C(t)` описується показниковою залежністю:

```
C(t) = C₀ · kᵗ
```

де:
- `C₀` — базова вартість усунення дефекту на стадії проектування (виправити формулювання в документі, змінити схему зв'язку в діаграмі чи уточнити тип поля);
- `k` — коефіцієнт міжфазової ескалації вартості.

Значення коефіцієнта `k` залежить від природи програмної системи та вартості її розгортання:
- Для веб-сервісів із розвиненою практикою CD (Continuous Delivery): `k ≈ 3.5...5.0`;
- Для розподілених баз даних та високонавантажених сховищ: `k ≈ 6.0...8.0`;
- Для вбудованих систем (embedded), прошивок авіоніки чи медичних приладів: `k ≈ 15.0...25.0`, оскільки відкликання пристрою чи оновлення ROM у польових умовах вимагає колосальних витрат.

Розрахуємо значення вартості для базової вартості `C₀ = 100` доларів (приблизно одна година роботи старшого інженера над правкою тексту) за середнього хмарного коефіцієнта `k = 5.0`:

```
C(0)
= 100 · 5.0⁰       [фаза проектування: t = 0]
= 100 · 1.0        [нульовий степінь: 5.0⁰ = 1]
= 100              [доларів: вартість правки в Design Doc]

C(1)
= 100 · 5.0¹       [фаза кодування: t = 1]
= 100 · 5.0        [перший степінь]
= 500              [доларів: переписування модуля та локальних тестів]

C(2)
= 100 · 5.0²       [фаза тестування на staging: t = 2]
= 100 · 25.0       [квадрат множника]
= 2500             [доларів: блокування релізу, повторне наскрізне тестування]

C(3)
= 100 · 5.0³       [фаза продакшену: t = 3]
= 100 · 125.0      [куб множника]
= 12500            [доларів: аварійна міграція БД, патч, відкат, простій]
```

Один пропущений у продакшен архітектурний дефект (наприклад, стан гонки в протоколі розподіленої реплікації або відсутність інваріанта ідемпотентності) коштує у `125` разів дорожче, ніж його виявлення під час читання документації.

## Очікувана вартість системи з рецензуванням і без нього

Розглянемо проект середньої складності, у якому під час проектування виникає `N = 10` потенційних архітектурних або інтеграційних дефектів.

Позначимо:
- `T_write` — час автора на написання якісного Design Doc (16 інженерних годин);
- `T_rev` — сумарний час рецензентів на читання та обговорення (3 рецензенти по 4 години = 12 годин);
- `S_eng` — середня погодинна ставка інженера (`S_eng = 100` $/год);
- `E_rev` — ефективність виявлення дефектів на рев'ю Design Doc (частка виявлених дефектів, типово `E_rev = 0.70` або `70%`);
- `E_test` — ефективність виявлення дефектів під час розробки й автоматизованого тестування (`E_test = 0.60` або `60%` від залишку);
- частка, що лишається, проривається в продакшен.

### Сценарій 1. Розробка без Design Doc (пряме кодування)

Команда відразу пише код (`t = 1`), оминаючи фазу документації.
На фазі кодування виявляється 0% концептуальних дефектів (бо вони закладені в саму архітектуру). На фазі тестування (`t = 2`) виявляється 60% дефектів, а 40% потрапляють у продакшен (`t = 3`).

Кількість дефектів за фазами:
- `N_test = 10 · 0.60 = 6` дефектів на стадії `t = 2`;
- `N_prod = 10 · 0.40 = 4` дефекти на стадії `t = 3`.

Сумарні витрати на виправлення дефектів `Cost_without`:

```
Cost_without
= N_test · C(2) + N_prod · C(3)
= 6 · 2500 + 4 · 12500          [підстановка вартостей C(2) і C(3)]
= 15000 + 50000                 [проміжне множення витрат]
= 65000                         [доларів: сумарні втрати без Design Doc]
```

### Сценарій 2. Розробка з Design Doc та RFC-рев'ю

Команда витрачає час на написання документа та рев'ю.

Фіксовані витрати на процес проектування `Cost_doc`:

```
Cost_doc
= (T_write + T_rev) · S_eng
= (16 + 12) · 100           [сумарно 28 інженерних годин]
= 28 · 100                  [перемноження годин на ставку]
= 2800                      [доларів: інвестиція в документ]
```

Розподіл дефектів за фазами:
1. На фазі `t = 0` виявляється `10 · 0.70 = 7` дефектів.
2. Залишок становить `10 − 7 = 3` дефекти.
3. На фазі тестування `t = 2` виявляється `3 · 0.60 = 1.8` дефекти (в середньому).
4. У продакшен `t = 3` потрапляє `3 · 0.40 = 1.2` дефекти.

Сумарні витрати в сценарії з Design Doc `Cost_with`:

```
Cost_with
= Cost_doc + N_doc · C(0) + N_test · C(2) + N_prod · C(3)
= 2800 + 7 · 100 + 1.8 · 2500 + 1.2 · 12500               [підстановка значень]
= 2800 + 700 + 4500 + 15000                               [пофазові суми]
= 23000                                                   [доларів: сумарні витрати]
```

### Економічний ефект (ROI)

Чистий фінансовий виграш `Net_Gain`:

```
Net_Gain
= Cost_without − Cost_with
= 65000 − 23000             [різниця сумарних витрат]
= 42000                     [доларів: збережений бюджет]
```

Коефіцієнт окупності інвестицій у проектування `ROI` (англ. *Return on Investment*):

```
ROI
= Net_Gain ÷ Cost_doc
= 42000 ÷ 2800         [відношення виграшу до витрат на рев'ю]
= 15.0                 [коефіцієнт окупності]
= 1500                 [% повернення коштів]
```

Кожен долар, вкладений у години написання та рецензування Design Doc, зберігає компанії 15 доларів на етапі експлуатації системи.

## Критичний поріг складності завдання (N_crit)

Чи вигідно писати Design Doc для абсолютно кожної задачі?
Математична модель дозволяє точно визначити поріг беззбитковості.

Знайдемо критичну кількість латентних архітектурних ризиків `N_crit`, за якої витрати на написання документу точно дорівнюють виграшу від запобігання дефектам:

```
Net_Gain(N) = Cost_without(N) − Cost_with(N) = 0
```

Розпишемо різницю:

```
Cost_without(N) − Cost_with(N)
= N · [ (1 − E_test) · C(3) + E_test · C(2) ] − Cost_doc − N · [ E_rev · C(0) + (1 − E_rev) · E_test · C(2) + (1 − E_rev) · (1 − E_test) · C(3) ]
= N · E_rev · [ (1 − E_test) · C(3) + E_test · C(2) − C(0) ] − Cost_doc
```

Прирівнюючи до нуля:

```
N_crit · E_rev · [ (1 − E_test) · C(3) + E_test · C(2) − C(0) ] = Cost_doc
```

Звідси отримуємо аналітичний вираз для критичної кількості дефектів `N_crit`:

```
N_crit = Cost_doc ÷ ( E_rev · [ (1 − E_test) · C(3) + E_test · C(2) − C(0) ] )
```

Підставимо числові параметри нашого базового прикладу (`Cost_doc = 2800`, `E_rev = 0.70`, `E_test = 0.60`, `C(3) = 12500`, `C(2) = 2500`, `C(0) = 100`):

```
N_crit
= 2800 ÷ ( 0.70 · [ 0.40 · 12500 + 0.60 · 2500 − 100 ] )
= 2800 ÷ ( 0.70 · [ 5000 + 1500 − 100 ] )                 [обчислення виразів у дужках]
= 2800 ÷ ( 0.70 · 6400 )                                  [множення коефіцієнтів]
= 2800 ÷ 4480                                             [розрахунок знаменника]
= 0.625                                                   [одиниць ризику]
```

Значення `N_crit = 0.625` означає: якщо проект має хоча б **один** серйозний архітектурний ризик чи нетривіальну інтеграцію (математичне сподівання кількості концептуальних помилок `N ≥ 1`), написання Design Doc є суворо виправданим і приносить чистий прибуток.

Якщо ж завдання є рутинним (виправлення локального дефекту в 10 рядків коду, де `N ≈ 0.05`), витрати на створення повноцінного RFC призводять до від'ємного ROI. Для таких завдань достатньо звичайного Pull Request або [короткого запису рішення ADR](topic:sf-apps/adr).

## Межа спадної віддачі та оптимальна тривалість рев'ю

Ефективність виявлення дефектів `E_rev` підпорядковується закону спадної віддачі (модель насичення):

```
E_rev(T_rev) = E_max · (1 − e^(−λ · T_rev))
```

де:
- `E_max` — теоретична межа виявлення дефектів рецензентами (`E_max ≈ 0.85...0.90`);
- `λ` — швидкість вичерпання очевидних зауважень (`λ ≈ 0.15...0.25` на годину рев'ю).

Коли час рев'ю `T_rev` перевищує оптимум, вартість затримки виходу продукту на ринок (англ. *Cost of Delay*, `CoD`) починає перевищувати математичне сподівання відловлених дефектів.

Цільова функція сумарних втрат `L(T_rev)`:

```
L(T_rev) = S_eng · T_rev + N · (1 − E_rev(T_rev)) · (1 − E_test) · C(3) + CoD · T_rev
```

Оптимум досягається за умови, коли похідна вартості рев'ю дорівнює граничному зниженню очікуваних збитків:

```
d/dT_rev [S_eng · T_rev + CoD · T_rev]
= − d/dT_rev [N · (1 − E_rev(T_rev)) · (1 − E_test) · C(3)]   [умова рівноваги]
```

Розкриваючи експоненту:

```
S_eng + CoD = N · E_max · λ · e^(−λ · T_rev) · (1 − E_test) · C(3)
```

Логарифмуючи обидві частини, отримуємо формулу оптимального часу рев'ю:

```
T_opt = (1 ÷ λ) · ln ( (N · E_max · λ · (1 − E_test) · C(3)) ÷ (S_eng + CoD) )
```

На практиці для типового проекту це дає **2–4 робочі дні асинхронного рев'ю** (сумарно 8–15 годин уваги рецензентів). Подальше утримання документу в стані рев'ю не знижує кількість дефектів, а перетворюється на [параліч аналізу](topic:sf-apps/design-docs), де команда витрачає ресурс на суперечки про другорядні деталі.
