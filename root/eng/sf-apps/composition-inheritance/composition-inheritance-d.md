Пораду «надавай перевагу композиції об'єктів над спадкуванням класів» переказують так часто, що вона встигла злитися в одну сіру фразу, де обидва слова здаються двома майже однаковими способами перевикористати чужий код. Це найглибша хиба в її розумінні. **Спадкування (англ. *inheritance*)** і **композиція (лат. *compositio* — складання докупи)** — не два інструменти для тієї самої роботи, а два **різні за природою зв'язки**, що живуть у різний час і на різному рівні. Спадкування — зв'язок **між класами**, застиглий **на компіляції**, який компілятор вплавляє в тип нащадка **назавжди**. Композиція — зв'язок **між об'єктами**, що народжується **під час роботи** й тримається на звичайному вказівнику, який можна перепризначити. Майже все, що робить пораду правдивою, витікає рівно з цієї різниці — і саме її варто розкопати до дна.

Тут не переказуватимемо, чому «стек не є вектор» чи чому дерево ворогів вибухає добутком осей — ці два докази лежать на поверхні. Копнемо глибше: у тихі механізми, через які спадкування ламає код навіть тоді, коли зв'язок «є» чесний; у структурні глухі кути, яких у композиції немає в принципі; у чесну ціну в тактах і байтах; і в те, як ця різниця вирішує геть практичні речі — від тестовності до збірки всієї програми.

## Два різні зв'язки, а не два способи те саме

Промовмо обидва зв'язки максимально точно, бо саме тут захована вся подальша механіка.

Коли ти пишеш `class Circle : public Shape`, ти робиш заяву, яку **бачить компілятор і яку вже не відкликати під час роботи**: цей тип, `Circle`, назавжди є різновидом `Shape`. Звʼязок вплавлено в саму сутність типу — у його розкладку в пам'яті, у його таблицю віртуальних методів, у правила, за якими компілятор дозволяє підставляти один тип замість іншого. Змінити цей зв'язок можна лише одним способом: **переписати оголошення класу й перекомпілювати**. Об'єкт класу `Circle` є `Shape` від народження до знищення, і жодна подія під час роботи цього не зрушить.

Коли ти натомість кладеш `Shape* shape` полем усередину об'єкта, ти робиш заяву **іншого ґатунку**: цей конкретний об'єкт **зараз** тримає при собі якийсь `Shape` і вміє до нього достукатися через його публічний інтерфейс. Слово «зараз» тут — ключове. Поле — це змінна; вказівник у ній можна перепризначити наступного рядка, і той самий об'єкт почне користуватися іншою деталлю, не змінивши ні свого типу, ні своєї адреси.

![Ліворуч клас Circle трикутником-стрілкою успадковує Shape, підпис: зв'язок вирішено компілятором, вплавлено в тип, незмінний. Праворуч об'єкт player тримає поле weapon-вказівник, що показує на Sword, а пунктирна стрілка перепризначення веде на Bow, підпис: зв'язок живе під час роботи, перемикається на льоту](img/static-vs-dynamic-bond.svg)

*Той самий намір — «скористатися чужою поведінкою» — двома зв'язками різної природи. Спадкування вирішує зв'язок на компіляції й вплавляє його в тип назавжди. Композиція тримає зв'язок у полі-вказівнику, який під час роботи можна навести на іншу деталь.*

З цієї єдиної відмінності — **коли** і **на якому рівні** зав'язується зв'язок — випливає все інше, ланцюжком. Раз спадкування вирішується на компіляції й вплавляється в тип, нащадок зрощується з базою **такою, якою вона була в мить компіляції** — з її внутрішнім устроєм, порядком викликів, розкладкою полів. Раз композиція живе на вказівнику, деталь доступна лише через **свій публічний інтерфейс** (усе решта — по той бік вказівника, куди власник не сягає) і будь-коли **замінна**. Перша обставина породжує крихкість, про яку далі; друга — гнучкість, за яку доводиться платити непрямістю. Тримаймо цю вісь «застигле на компіляції ⇄ живе під час роботи» в голові — до неї зводитиметься кожен наступний доказ.

## Найтихіша пастка: база кличе саму себе

Найвідоміший закид спадкуванню — що воно протикає крізь межу зайві методи (класика — `Stack`, оголошений нащадком `Vector`, крізь який протекли `get(i)` та `insert(i)`). Але це закид **грубий і видимий**: зайвий метод стирчить в інтерфейсі, його видно оком. Куди підступніша біда виникає тоді, коли зв'язок «є» **абсолютно чесний**, Лісков задоволена, жоден зайвий метод не протік, — і код усе одно ламається. Джерело цієї біди — **самовиклик бази (англ. *self-use*)**: базовий метод усередині кличе інший **перевизначуваний** метод того самого класу.

Розберімо канонічний приклад, який Джошуа Блох (англ. Joshua Bloch — американський інженер, автор «Effective Java» і головний архітектор бібліотеки колекцій Java) поставив у розділ, названий рівно нашою порадою — «Favor composition over inheritance». Задача дитяча: потрібна множина, що рахує, **скільки елементів у неї колись додали**. Найпряміший рефлекс — успадкувати `HashSet` і перевизначити обидва методи додавання, щоб кожен нарощував лічильник:

```java
// Успадкування: лічильник у нащадку HashSet
class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;                    // порахували один
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();          // порахували цілу пачку
        return super.addAll(c);
    }
    public int getAddCount() { return addCount; }
}
```

Зв'язок тут чесний: `InstrumentedHashSet` **справді є** `HashSet` — усюди, де очікують множину, він підійде, LIFO ніхто не ламає, жодного зайвого методу не протекло. І все ж:

```java
var s = new InstrumentedHashSet<String>();
s.addAll(List.of("раз", "два", "три"));
s.getAddCount();   // очікуєш 3 — отримуєш 6
```

Звідки шістка? Простежмо виклик по кроках, бо в цих кроках — уся суть:

```
s.addAll([раз, два, три])
  → InstrumentedHashSet.addAll:  addCount += 3        // addCount = 3
  → super.addAll(...)            // усередині HashSet.addAll кличе add() на КОЖЕН елемент
      → this.add("раз")   // this — наш нащадок! → InstrumentedHashSet.add: addCount++  → 4
      → this.add("два")   //                                                addCount++  → 5
      → this.add("три")   //                                                addCount++  → 6
```

Ось де захована пружина. `HashSet.addAll` усередині **сам кличе `add`** — і кличе не абстрактний «add множини», а `this.add`, який під час роботи динамічно зв'язується з **перевизначеною** версією нащадка. Пачку порахували двічі: раз явно в `addAll`, і ще раз — коли базин `addAll` прокрутив її через наш же `add`.

Тепер найгостріше. Полагодити це, знявши `addCount += c.size()` з `addAll`, — оманлива перемога. Бо факт, що `HashSet.addAll` реалізовано **поверх** `add`, — це **недокументована деталь реалізації**, на яку ти не маєш права спиратися: у наступному випуску бібліотеки її автори можуть переписати `addAll` так, щоб він додавав елементи навпростець, не торкаючись `add`, — і твій нащадок, підігнаний під стару внутрішню механіку, тихо почне рахувати неправильно вже без жодної твоєї правки. Твоя коректність залежить від **графа внутрішніх викликів бази** — а цей граф ти не бачиш, він не входить у контракт, і він може зсунутися під тобою будь-якого релізу. Це і є **проблема крихкого базового класу (англ. *fragile base class problem*)** у своїй найтоншій, семантичній подобі: не зайвий метод протік, а нащадок зрісся з тим, **як саме база кличе сама себе**.

> 🔧 **Навіщо це.** Правило-детектор виводиться прямо звідси: успадковуючи реалізацію, ти мовчки зобов'язуєшся до того, що база **ніколи не змінить свій внутрішній граф самовикликів** — а такої обіцянки тобі ніхто не давав і дати не може, бо це якраз та частина, яку інкапсуляція мала право ховати. Тому й підозрілий будь-який `@Override` методу, чий внутрішній зв'язок з іншими методами тобі невидимий. Спитай себе: «Чи покладаюсь я на те, в якому порядку база кличе власні методи?» Якщо так — ти стоїш на піску.

Композиція прибирає пастку начисто, і механізм цього прибирання варто зрозуміти точно. Замість «рахувальна множина **є** `HashSet`» скажи «рахувальна множина **має** всередині якусь `Set` і **пересилає** їй роботу». Обгортка тримає деталь полем, реалізує той самий інтерфейс `Set`, а кожен метод просто **переадресовує** виклик усередину (така обгортка зветься **пересильним класом**, англ. *forwarding class*). І ось чому це «камінно надійно»: коли пачку додають через обгортку, внутрішній `addAll` **загорнутого** `HashSet` кличе **свій власний** `add` — той, що всередині `HashSet`, а не перевизначений `add` обгортки. Самовиклик замкнувся всередині деталі й **не дотягнувся** до нашого лічильника. Пачку порахували рівно раз. Ба більше: така обгортка працює з **будь-якою** `Set`, а не лише з `HashSet`, і переживе будь-яку зміну нутра бази, бо спирається **тільки на публічний інтерфейс** `Set`. Повний робочий код — розбитий broken-варіант із трасуванням лічильника й пересильний клас, що його лагодить, — розгорнуто в [окремому проєкті про самовиклик і пересилання](topic:sf-apps/composition-inheritance/proj-self-call-fragility.md).

## Ромб, якого в композиції не буває в принципі

Дотепер ішлося про крихкість. Є в спадкування й **структурна** глуха кута — місце, де воно не просто ризиковане, а **математично неоднозначне**, і жодна обережність автора цього не рятує. Це **проблема ромба (англ. *diamond problem*)**, і вона вигулькує, щойно клас пробує успадкувати реалізацію відразу від **двох** предків, що мають спільного прабатька.

Уяви базу `A` з полем і методом `m()`. Від неї успадковано `B` і `C` — кожен по-своєму перевизначив `m()`. А тепер клас `D` хоче бути і `B`, і `C` водночас, тож успадковує обох. Малюнок зв'язків складається в ромб: `A` угорі, `B` і `C` з боків, `D` знизу — і два шляхи від `D` до `A` сходяться у вершині.

![Ромб успадкування: угорі клас A з полем x і методом m, від нього трикутними стрілками успадковують B і C, кожен перевизначає m, а знизу D успадковує і B, і C. Праворуч панель із трьома питаннями неоднозначності та відповідями мов: C++ віртуальна база дає одну копію A, Python C3-лінеаризація впорядковує предків, Java заборонив множинне успадкування класів. Унизу: композиція D просто тримає B і C полями, ромба нема](img/diamond-problem.svg)

*Множинне успадкування реалізації зводить два шляхи до спільного предка — і породжує три неоднозначності: скільки копій полів A всередині D, чий m() успадкувати, як їх упорядкувати. Кожна мова мусила винайти окрему машинерію, щоб цей вузол розв'язати. Композиція вузол не в'яже: об'єкт просто тримає B і C поруч.*

Ромб ставить три незручні питання одразу. Перше — **скільки копій `A`** тепер усередині `D`: одна спільна чи дві, по одній на кожен шлях? Якщо дві, то поле `x` роздвоїлося, і `D` носить два різні `x`, що суперечить самій ідеї «одного спільного прабатька». Друге — **чий `m()`** бачить `D`, якщо `B` і `C` перевизначили його по-різному: виклик стає двозначним. Третє — **в якому порядку** взагалі перебирати предків, шукаючи метод. Це не теоретичні тонкощі: кожна серйозна мова була **змушена** винайти окремий механізм саме під цей вузол.

- **C++** дозволяє множинне успадкування прямо, тож мусив дати ліки від подвоєної бази — **віртуальне успадкування (англ. *virtual inheritance*)**: якщо `B` і `C` успадковують `A` як `virtual`, у `D` лишається **одна спільна** `A`. Ліки не безкоштовні: щоб дотягтися до спільної віртуальної бази, об'єкт носить додатковий вказівник і робить непряме зміщення під час роботи — тобто платить пам'яттю й тактами за розв'язання ромба.
- **Python** множинне успадкування теж дозволяє й розв'язує неоднозначність **порядком розв'язання методів (англ. *method resolution order*, MRO)**, який рахує за алгоритмом **C3-лінеаризації** (з версії 2.3): усі предки шикуються в один несуперечливий лінійний список, і `super()` іде рівно за ним. Ромб не зникає — його **впорядковують** у пряму лінію.
- **Java** зробила найрадикальніший вибір: **заборонила множинне успадкування класів** узагалі. Клас успадковує лише один клас — ромба зі станом просто нема звідки взятися. Множинно успадковувати можна тільки **інтерфейси**, а вони (до певного часу) не мали тіл, тож і конфлікту реалізацій не було. Коли Java 8 додала інтерфейсам **методи за замовчуванням (англ. *default methods*)** з тілом, вузьке віконце ромба прочинилося знову — і мова закрила його жорстким правилом: якщо два інтерфейси дають конфліктні `default`-методи, клас **зобов'язаний** перевизначити метод сам, а до потрібної версії достукатися явно через `Interface.super.m()`.

Три мови — три різні винаходи проти однієї й тієї самої халепи. А тепер подивись, **скільки цієї машинерії потребує композиція**: ніскільки. Якщо `D` хоче поведінку і `B`, і `C`, він просто **тримає** обох полями — `B b; C c;` — і кличе `b.foo()` чи `c.bar()` там, де треба. Двох копій `A` не виникає, бо ніякого спільного прабатька в цій картині нема — є два самостійні об'єкти. Неоднозначності «чий метод» нема, бо кожен виклик явно адресований своїй деталі. Порядок перебору не потрібен, бо нема чого перебирати. Ромб — це проблема **виключно** успадкування реалізації; композиція його не розв'язує краще, вона його **не створює**. *(Статус: усталено — механізми віртуального успадкування C++, C3-MRO Python і правила default-методів Java задокументовані в самих специфікаціях цих мов.)*

## Ціна композиції — і як мови її здешевили

Тепер про чесний видаток, бо його гасла зазвичай замовчують. За гнучкість композиції платять **делегувальними обгортками (лат. *delegare* — доручати, передавати повноваження)**: там, де спадкування дарувало методи предка одним словом `extends`, композиція вимагає **написати руками** пересильний метод на кожну операцію, яку власник прокидає всередину. Багатий інтерфейс на два десятки методів обертається двома десятками нудних однорядкових обгорток. Ось ця економія й є вся спокуса `extends`.

Але подивись, **що зробила з цією ціною індустрія**. Побачивши, що композиція безпечніша, а дорожча лише на шаблонний код пересилання, розробники мов пішли не шляхом «зробити спадкування безпечним», а шляхом «**зробити композицію дешевою**» — і це промовистий вибір, бо він показує, куди схилилася колективна думка.

**Go** увів **вбудовування (англ. *embedding*)**: пишеш тип полем без імені, і його методи **автоматично підіймаються** в зовнішній тип, наче стали його власними. Пересильні обгортки генерує компілятор:

```go
type Engine struct{}
func (Engine) Start() { fmt.Println("двигун заведено") }

type Car struct {
    Engine          // вбудовано — метод Start() підіймається в Car
    plate string
}

func main() {
    c := Car{plate: "AA1234"}
    c.Start()       // працює, хоч Start оголошено на Engine
}
```

Зовні це схоже на успадкування — та по суті це **композиція**, і Go цю різницю тримає суворо: `Car` **не є** `Engine`. Не можна передати `Car` туди, де очікують `Engine`; підіймання методів дає перевикористання й задоволення інтерфейсів (якщо піднятих методів досить, щоб задовольнити інтерфейс, `Car` теж його задовольняє), але **не дає підстановки за типом**. Go свідомо взяв зручність спадкування без його обіцянки «є» — саме те, чого просить наша порада.

**Kotlin** пішов ще пряміше — вбудував делегування в синтаксис через слово `by`:

```kotlin
interface Repository { fun load(id: Int): String }

class CachingRepository(private val inner: Repository) : Repository by inner {
    // усі методи Repository автоматично переслано в inner;
    // перевизначаємо руками ЛИШЕ те, що справді міняємо:
    override fun load(id: Int): String {
        println("спершу глянули б у кеш")
        return inner.load(id)
    }
}
```

`by inner` каже компілятору: усі методи інтерфейсу, яких я не перевизначив, згенеруй як пересилання в `inner`. Двадцять нудних обгорток зникають, лишається рівно те, що ти справді змінюєш. Це буквально «пересильний клас Блоха», але виписаний за тебе компілятором.

Той самий бік — **риси (англ. *traits*)** у Scala й Rust та **домішки (англ. *mixins*, від *mix in* — вмішувати)** у Ruby — це спроби дати керований, безпечніший різновид перевикористання поведінки без класичної крихкості. Rust тут показовий: його риси несуть **поведінку без стану**, тож біда крихкої бази, зрощеної з полями предка, просто не виникає — успадковувати нічого, крім набору обіцянок. Усе це — варіації однієї відповіді: перевикористовуй поведінку, не вплавляючи чужий стан і чужий граф самовикликів у свій тип.

> 🔧 **Навіщо це.** Коли пишеш пересильні обгортки руками, пересилай **не все підряд, а лише те, що зовнішній тип справді має показувати**. Спокуса «прокинути весь інтерфейс деталі назовні» непомітно повертає ту саму протікаючу межу, від якої ти тікав: клієнт знову бачить нутрощі, тепер уже через обгортку. Вибіркове пересилання — це той самий інстинкт, що й [закон Деметри](topic:sf-apps/law-of-demeter): показуй мінімум, не давай клієнтові розмовляти з деталями твоєї деталі.

## «Має» буває двох ґатунків: володіння і посилання

Слово «має» приховує розрізнення, без якого композицію не зрозуміти до кінця, — розрізнення за **правом на життя деталі**. Одна річ, коли ціле **володіє** деталлю й та живе рівно стільки, скільки живе ціле; інша — коли ціле лише **посилається** на деталь, що існує сама по собі. UML навіть малює їх різними ромбами, і ця різниця — не педантизм, а два різні режими управління пам'яттю й відповідальністю.

**Композиція у вузькому сенсі (володіння)** — деталь **народжується й гине разом із цілим**. Двигун створюється всередині машини й зникає, коли машину знищують; жоден інший об'єкт цей двигун не поділяє. UML малює це **суцільним ромбом** біля цілого. У C++ таке володіння виражають прямо — деталь лежить **значенням** або під `unique_ptr`:

```cpp
class Car {
    std::unique_ptr<Engine> engine;   // Car ВОЛОДІЄ двигуном
public:
    Car() : engine(std::make_unique<Engine>()) {}
    // коли Car знищується, engine знищується разом — автоматично
};
```

**Агрегація (лат. *aggregare* — приєднувати до стада, збирати докупи; посилання)** — деталь **живе окремо** від цілого й лише тимчасово при ньому. Університет «має» студентів, але не породжує їх і не вбиває, коли закривається: студенти існували до нього й переживуть його; один студент може бути «при» кількох об'єктах водночас. UML малює це **порожнім ромбом**. У C++ таке невладне посилання виражають сирим вказівником, посиланням або `shared_ptr` — тим, що **не бере на себе знищення**:

```cpp
class University {
    std::vector<Student*> students;   // University лише ПОСИЛАЄТЬСЯ на студентів
public:
    void enrol(Student* s) { students.push_back(s); }
    // коли University знищується, студенти ЖИВУТЬ далі — їх убиває хтось інший
};
```

![Ліворуч композиція-володіння: рамка Car містить усередині рамку Engine, суцільний ромб, а під ними дві смуги життя, що починаються й закінчуються разом, підпис: деталь живе й гине з цілим. Праворуч агрегація-посилання: рамка University з порожнім ромбом і стрілкою назовні до окремої рамки Student, смуга життя студента починається раніше й тягнеться далі за смугу університету, підпис: деталь живе окремо, спільна](img/aggregation-vs-composition.svg)

*Два ґатунки «має» різняться правом на життя деталі. При володінні деталь замкнена в цілому й знищується з ним (суцільний ромб). При агрегації деталь самостійна, ціле лише тримає на неї посилання (порожній ромб) — звідси й ризик завислого посилання, коли деталь уб'ють раніше за того, хто на неї дивиться.*

Розрізняти їх обов'язково, бо від цього залежать реальні баги. Володіння дає прості й безпечні правила: одна деталь — один власник, знищення каскадом, жодного спільного доступу. Агрегація дає гнучкість спільного користування — але тягне за собою класичну небезпеку **завислого посилання (англ. *dangling reference*)**: якщо студента знищать раніше, ніж закриється університет, той тримає вказівник у порожнечу, і перше ж звертання читає сміття. Тому, обираючи «має», щоразу питай не лише «яку деталь тримати», а й «**хто відповідає за її життя**» — і бери володіння всюди, де спільний доступ не потрібен, бо воно радикально простіше й безпечніше.

## Ціна в пам'яті: складати значенням чи вказівником

Є ще один видаток композиції, тонший за обгортки й геть невидимий у вихідному коді, — **розкладка в пам'яті**. Він вартий окремого погляду, бо саме тут ховається найсильніший контраргумент проти «композиції всюди», і чесно його назвати важливіше, ніж замовчати.

Спадкування (і композиція **значенням**) кладе деталь **вбудованою в тіло об'єкта** — поля предка йдуть суцільно перед полями нащадка, усе в одному шматку пам'яті. Прочитати таке поле — один доступ за відомим зміщенням, без жодного стрибка; такий об'єкт зазвичай лягає в одну-дві лінії кешу, і процесор гуляє ним блискавично.

Композиція **вказівником** — та, що тільки й дає підстановку деталі на льоту й віртуальність, — розкладає пам'ять інакше. Об'єкт-власник тримає не саму деталь, а **вказівник** на неї, а сама деталь лежить окремим шматком у купі (heap). Щоб дістатися до неї, процесор мусить **стрибнути за вказівником** — а той шматок цілком може виявитися в геть іншій ділянці пам'яті, повз кеш, і кожен такий стрибок ризикує **промахом кешу**, який коштує сотні тактів. Плюс кожна окрема деталь — це окрема **алокація**.

```
Складання ЗНАЧЕННЯМ (вбудовано):
    [ Enemy: hp | Sword{dmg} | Heavy{def} ]   ← один шматок, 1 алокація
    доступ до dmg: одне зміщення, 0 стрибків, чудова локальність кешу
    ЦІНА: тип деталі зашитий на компіляції — підмінити на льоту НЕ можна

Складання ВКАЗІВНИКОМ (деталь у купі):
    [ Enemy: hp | weapon• | armor• ]
                    │        └────────→ [ Heavy{def} ]   ← окремий шматок
                    └─────────────────→ [ Sword{dmg} ]   ← ще окремий шматок
    доступ до dmg: стрибок за вказівником → ризик промаху кешу; N алокацій
    ВИГРАШ: деталь підмінна на льоту + віртуальний виклик
```

Ось де народжується справедливий закид школи **дата-орієнтованого проєктування**: якщо мільйони об'єктів складено вказівниками, обхід їх у гарячому циклі перетворюється на суцільне блукання пам'яттю з постійними промахами кешу — і жодна елегантність тут не викупить втрачену локальність. Але закид б'є не по композиції як такій, а по **композиції вказівником там, де підстановка не потрібна**. Бо composition має вибір, якого спадкування не має: коли конкретний тип деталі відомий і мінятися не буде, її складають **значенням** — вбудовують у тіло об'єкта, і локальність повертається повністю, а віддаєш ти лише те, чого й не потребував, — підміну на льоту. Тобто справжня вісь вибору не «спадкування проти композиції», а «**значеннєва композиція (швидка, статична) ⇄ вказівникова композиція (гнучка, непряма)**», і на ній ти стоїш там, де диктує задача.

> 🔧 **Навіщо це.** Не плати за поліморфізм, якого не потребуєш. Якщо деталь ніколи не міняється на льоту й тип її відомий — склади її значенням: жодного стрибка, жодної зайвої алокації, повна локальність кешу. Вказівник (і віртуальний виклик за ним) бери свідомо — коли справді потрібна підміна поведінки під час роботи. А коли профіль показав, що гарячий цикл тоне у стрибках за вказівниками, це сигнал не «повернутись до спадкування», а «перекласти цю композицію зі вказівникової на значеннєву».

Скільки коштує вже сам **віртуальний виклик** за таким вказівником — окрема історія: там ідеться не так про наносекунди стрибка через [таблицю віртуальних методів](topic:sf-devices/virtual-dispatch-cpp), як про втрачене вбудовування (inline), і чому на холодному коді це тоне, а на гарячому — міряється [профілювальником](topic:sf-release/profiling). Це чесно пораховано по тактах в [окремому проєкті-рефакторингу](topic:sf-apps/composition-inheritance/proj-strategy-refactor.md); тут доповнимо лише те, що ту вартість дає **вказівникова** композиція, і значеннєва її не платить.

## Тиха винагорода: тестовність і збірка програми

Найпрактичніший наслідок вибору «має» замість «є» показується не в продуктивності, а в тому, як **легко код перевіряти**. І виводиться він прямо з природи двох зв'язків.

Коли об'єкт **має** свої залежності — приймає їх готовими ззовні й тримає полями, — підмінити будь-яку з них у тесті **фальшивкою (англ. *test double*)** тривіально: просто подай на вхід іншу реалізацію того самого інтерфейсу. Об'єкт нічого не помітить, бо він завжди знав деталь лише як інтерфейс:

```typescript
interface Clock { now(): number; }

class Order {
    constructor(private clock: Clock) {}          // залежність ПРИЙНЯТО ззовні
    stamp(): number { return this.clock.now(); }
}

// у тесті підставляємо фальшивий годинник — час стає передбачуваним
const fake: Clock = { now: () => 1_000 };
new Order(fake).stamp();                          // рівно 1000, тест детермінований
```

Коли ж об'єкт **успадкував** поведінку, вона вплавлена в його тип, і **вирізати** її для тесту нема як: щоб підмінити успадкований метод фальшивкою, доводиться городити ще один підклас лише заради тесту, а часом і це не рятує, бо база кличе сама себе. Успадкована поведінка **невід'ємна** — саме тому вона й не ізолюється.

Ця дрібниця розкручується у велике архітектурне питання. Якщо кожен об'єкт **приймає** свої деталі ззовні, а не створює їх сам, то хтось же мусить ці деталі **подати** й пов'язати весь граф об'єктів докупи. Цей «хтось» і ця дисципліна — **впровадження залежностей (англ. *dependency injection*)**: залежності передають об'єктові через конструктор, а всю збірку графа зводять в одне місце — корінь композиції. Так композиція з локального прийому «тримай деталь полем» виростає в спосіб структурувати **весь застосунок**: об'єкти оголошують, **що** їм треба (інтерфейси), а **чим** саме це задовольнити — вирішує зовнішня збірка. Це рівно те, що вимагають [принцип інверсії залежностей](topic:sf-apps/dependency-inversion) і [принцип відкритості-закритості](topic:sf-apps/open-closed): код залежить від обіцянок, не від конкретних реалізацій, і розширюється підстановкою нових деталей без переписування старих. Механіку самої збірки — ручної та через контейнер — розбирає тема про [впровадження залежностей](topic:sf-apps/dependency-injection).

> 🔧 **Навіщо це.** Хочеш знати наперед, чи легко буде тестувати клас, — подивись, **звідки в нього беруться залежності**. Створює їх сам усередині (`new`, або успадкував) — у тесті ти їх не підміниш, доведеться піднімати справжню базу даних чи справжній годинник. Приймає ззовні через конструктор — підставиш фальшивку одним рядком. Тестовність — не окрема робота «додати тести потім», а прямий наслідок того, композицією чи спадкуванням зшито граф; про це докладніше — [тактики тестовності](topic:sf-apps/testability-tactics).

## Дисципліна рішення: гостріше правило

Зберімо всі докази в одну процедуру, яку можна прокрутити в голові над кожним `extends`. Порядок питань не випадковий — кожне відсіює свій клас помилок.

**Перше: чи це чесне, стале «є»?** Нащадок мусить проходити [принцип підстановки Лісков](topic:sf-apps/liskov-substitution) — поводитися як предок **скрізь**, де на предка розраховують, — і залишатися таким надалі. Формально це означає низку умов на сигнатури й контракти (передумови можна лише **послаблювати**, постумови — лише **посилювати**, інваріанти зберігати), виведених у самій темі про Лісков. Не проходить — тобі потрібне «має», крапка.

**Друге: чи база спроєктована під успадкування — або заборонена для нього?** Навіть чесне «є» ще не дає права успадковувати **реалізацію**. Треба, щоб автор бази свідомо вирішив, які методи можна перевизначати, **задокументував свій граф самовикликів** (де база кличе власні перевизначувані методи) і пообіцяв його не ламати. Якщо такого документа нема — база не готова до спадкування, і правильна відповідь автора звучить різко: **проєктуй і документуй під спадкування — або забороняй його** (у Java `final`, у C++ `final`). Спадкувати від класу, що просто «опинився поруч» із зручними методами, — і є та помилка, від якої вся порада застерігає.

**Третє (і майже завжди безпечне): успадковуй ІНТЕРФЕЙС, не реалізацію.** Уся крихкість вище — про успадкування **реалізації** (класу з нутром). Успадкування чисто абстрактного типу — самих обіцянок без жодного тіла — протікати не має чим: нема нутрощів, нема самовикликів, нема крихкої бази. Саме тому повна назва принципу говорить про перевагу композиції над спадкуванням **класів**, а не інтерфейсів; успадкування інтерфейсів — здоровий фундамент, на якому стоять і [поліморфізм](topic:sf-lang/polymorphism), і [стратегія](topic:sf-apps/strategy), і [декоратор](topic:sf-apps/decorator).

**Четверте: що диктує форма задачі?** Кілька незалежних осей уточнення, потреба міняти поведінку на льоту, потреба ізолювати залежності для тестів — усе це прямо тягне композицію. Одна стала вісь, фіксований набір деталей на весь час життя, доведено гарячий цикл із мільйонами викликів — навпаки, схиляють до простішого рішення: проста ієрархія **інтерфейсу** або **значеннєва** композиція без віртуальності.

Що з цієї процедури видно найясніше — так це те, що коротка фраза «надавай перевагу композиції» насправді каже глибше: **надавай перевагу зв'язкам, що живуть під час роботи й тримаються на публічному інтерфейсі, над зв'язками, вплавленими в тип на компіляції**. Бо перші лишають систему змінюваною — деталь підміниш, підробиш у тесті, складеш у новій комбінації, не зачепивши нічого стороннього, — а другі зрощують твій код із чужим нутром, чужим порядком викликів і чужою розкладкою пам'яті так міцно, що кожна правка бази стає лотереєю. Це той самий обмін, яким зважують будь-яке рішення про структуру, зведений до найгострішого випадку: успадкування реалізації — це найтісніше [зчеплення](topic:sf-apps/coupling-cohesion) з можливих, а композиція звужує його до тонкої лінії опублікованого інтерфейсу. Тому й відповідь звучить не «ніколи не успадковуй», а **надавай перевагу**: за замовчуванням тримайся зв'язку, який завтра ще можна буде розв'язати, — і сходь із нього лише туди, де чесне, стале, задокументоване «є» справді того варте.
