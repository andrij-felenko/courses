# 🧮 Оптимальний інтервал контрольних точок (Checkpoint Economics)

Періодичне створення повного знімка стану (англ. *snapshot / checkpoint*) очищає журнал випереджувального запису (WAL), але саме по собі створює відчутне навантаження на підсистему вводу-виводу накопичувача. Якщо скидати знімок надто часто, процесор і диск будуть перевантажені записом однакових мегабайтів базового стану. Якщо ж робити це занадто рідко, журнал безконтрольно розростеться, а час відновлення після збою (англ. *recovery replay time*) стане неприпустимо довгим.

Оптимальний інтервал між знімками виводиться шляхом мінімізації сумарної функції втрат, що поєднує накладні витрати регулярного дискового запису та математичне сподівання часу відновлення при аварійній зупинці процесу.

## Постановка моделі та параметри системи

Розглянемо клієнтський застосунок, що працює з документом обсягом `S` байтів. Користувач генерує безперервний потік правок з інтенсивністю `R` операцій на секунду. Кожна окрема операція має середній розмір `b[op]` байтів і негайно записується в журнал WAL.

Введемо формальні параметри системи:

- `T` — часовий інтервал між послідовними контрольними точками (в секундах);
- `S` — повний розмір серіалізованого знімка документа (в байтах);
- `b[op]` — середній розмір одного запису операції в журналі WAL (в байтах);
- `c[s]` — питома вартість запису одного байта знімка на диск (навантаження на шину вводу-виводу та знос комірок SSD, умовні одиниці / байт);
- `R` — середня швидкість генерації операцій людиною або скриптом (операцій / с);
- `c[r]` — питома вартість парсингу та застосування однієї операції з журналу під час відновлення (секунд / операцію);
- `λ` — середня частота аварійних збоїв системи (збоїв / с), де проміжки часу між збоями розподілені експоненційно з параметром `λ`.

## Функція сумарних витрат

Загальна вартість функціонування підсистеми збереження за одиницю часу `C(T)` складається з двох конкуруючих процесів:

1. **Регулярні накладні витрати на запис контрольних точок (I/O Overhead):**
   За період тривалістю `T` секунд на диск записується рівно один повний знімок обсягом `S` байтів. Середня швидкість генерування дискового трафіку для знімків становить:

```
C_io(T) = (S · c[s]) ÷ T
```

2. **Математичне сподівання втрат від затримки відновлення (Expected Recovery Penalty):**
   Якщо аварійний збій відбувається випадково за пуассонівським процесом із середньою інтенсивністю `λ`, то момент аварії рівномірно розподілений на інтервалі `[0, T]` з моменту останнього знімка. Середня кількість операцій, накопичених у журналі на момент падіння, дорівнює:

```
N_ops = (R · T) ÷ 2
```

   Тоді очікувана затримка перезапуску програми за одиницю часу становить:

```
C_rec(T) = λ · c[r] · N_ops
         = (λ · c[r] · R · T) ÷ 2
```

Сумарна цільова функція вартості:

```
C(T) = C_io(T) + C_rec(T)
     = (S · c[s]) ÷ T + (λ · c[r] · R · T) ÷ 2
```

## Аналітичне виведення оптимального періоду

Для знаходження глобального мінімуму візьмемо першу похідну функції `C(T)` за змінною `T` і прирівняємо її до нуля:

```
dC/dT
= d/dT [(S · c[s]) · T⁻¹ + (1/2 · λ · c[r] · R) · T]     [запис через степінь]
= -(S · c[s]) · T⁻² + 1/2 · λ · c[r] · R                 [взяття похідних від доданків]
= -(S · c[s]) ÷ T² + (λ · c[r] · R) ÷ 2                  [зведення до дробів]
```

Прирівнюємо похідну до нуля для знаходження стаціонарної точки:

```
-(S · c[s]) ÷ T² + (λ · c[r] · R) ÷ 2 = 0
(S · c[s]) ÷ T² = (λ · c[r] · R) ÷ 2                     [перенесення доданків]
T² = (2 · S · c[s]) ÷ (λ · c[r] · R)                     [вираження квадрата періоду]
T* = √[(2 · S · c[s]) ÷ (λ · c[r] · R)]                  [взяття квадратного кореня]
```

Перевіримо достатню умову екстремуму за допомогою другої похідної:

```
d²C/dT²
= d/dT [-(S · c[s]) · T⁻² + (λ · c[r] · R) ÷ 2]
= 2 · (S · c[s]) · T⁻³                                   [похідна від степеневої функції]
= (2 · S · c[s]) ÷ T³ > 0                                [додатна для всіх T > 0]
```

Оскільки друга похідна строго додатна на всій допустимій області `T > 0`, знайдена точка `T*` є єдиним мінімумом функції сумарних витрат.

## Врахування зносу твердотілих накопичувачів (SSD Write Amplification)

У сучасних клієнтських комп'ютерах з твердотілими накопичувачами (SSD) багаторазовий запис великих файлів призводить до деградації комірок флешпам'яті (NAND Flash). Кожна комірка має скінченний ліміт циклів програмування та стирання (P/E Cycles, зазвичай від 1000 до 3000 циклів для TLC/QLC пам'яті).

Якщо знімок розміром `S = 50` МБ записувати кожні 5 секунд, за 8 годин робочого дня диск запише:

```
V_day = (50 · 10⁶ байтів) · (28800 с ÷ 5 с) ≈ 288 ГБ
```

За рік обсяг паразитного запису сягне понад 100 терабайтів (TBW), що здатне повністю вичерпати гарантійний ресурс споживчого накопичувача за рік-два офісної роботи.

З цієї причини коефіцієнт `c[s]` у моделі є не просто абстрактною затримкою шини, а містить штраф за фізичний знос обладнання. Використання швидкого журналу WAL замінює запис 50 МБ знімка записом 100 байтів дельти, знижуючи коефіцієнт посилення запису (Write Amplification Factor, WAF) у тисячі разів.

## Обмеження на максимальний розмір журналу на диску

У реальних операційних системах відновлення має додаткове жорстке обмеження: файл журналу `doc.wal` не повинен перевищувати виділену квоту пам'яті `W[max]`. Оскільки за час `T` журнал зростає на `R · b[op] · T` байтів, виникає нерівність:

```
R · b[op] · T ≤ W[max]
T ≤ W[max] ÷ (R · b[op])
```

Поєднуючи аналітичний мінімум витрат `T*` із граничним дисковим порогом та максимально допустимим часом перезапуску `t[rec_max]`, отримуємо остаточне інженерне правило вибору інтервалу:

```
T_final = min(T*, W[max] ÷ (R · b[op]), (2 · t[rec_max]) ÷ (R · c[r]))
```

## Числовий приклад розрахунку для редактора

Розглянемо параметри типового клієнтського редактора:

- Розмір документа `S = 10` МБ (`10 · 10⁶` байтів);
- Інтенсивність введення `R = 2` операції/с (активне редагування);
- Час накладання однієї операції `c[r] = 0.5` мс (`5 · 10⁻⁴` с);
- Коефіцієнт аварій `λ = 1 / 86400` збоїв/с (в середньому одне аварійне завершення на добу активної роботи);
- Питома ціна запису байта `c[s] = 10⁻⁸` умовних одиниць.

Підставимо значення у формулу:

```
T*
= √[(2 · 10⁷ · 10⁻⁸) ÷ (1.157 · 10⁻⁵ · 5 · 10⁻⁴ · 2)]   [підстановка числових значень]
= √[0.2 ÷ (1.157 · 10⁻⁸)]                               [обчислення чисельника і знаменника]
= √[1.728 · 10⁷]                                        [ділення]
≈ 4157 секунд ≈ 69 хвилин                               [добування квадратного кореня]
```

## Практична адаптація: гібридний тригер за розміром і часом

Теоретична модель показує оптимальний інтервал за умови сталого потоку правок. Проте в реальному застосунку швидкість `R` змінюється від 0 (людина відійшла від комп'ютера) до 50 операцій на секунду (пакетна заміна тексту або вставка таблиці).

Тому на практиці застосовують **двовимірний поріг спрацьовування чекпойнта**:

1. **За часом:** `T_max = 60..120` секунд (захист від старіння журналу під час спокійної роботи);
2. **За накопиченим обсягом WAL:** `N_max = 500..2000` операцій або `WAL_bytes > 5` МБ.

Якщо накопичений розмір журналу `|WAL|` перевищує поріг `N_max`, чекпойнт ініціюється негайно, не чекаючи вичерпання таймера `T_max`. Це гарантує, що відновлення ніколи не триватиме довше кількох десятих часток секунди незалежно від темпу роботи.
