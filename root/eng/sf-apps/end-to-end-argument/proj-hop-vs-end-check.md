# ⚙️ Стенд: зіпсований ретранслятор проти двох перевірок

Найшвидший спосіб перестати вірити перевірці на ділянці — зібрати триланковий стенд, власноруч зіпсувати в ньому ретранслятор і подивитися, як контрольна сума кожної ділянки чесно рапортує «чисто», поки наскрізний геш кричить про розбіжність. Далі — робочий код цього стенда, вимір того, скільки байтів проходить до першої непоміченої помилки, звірка виміру з теорією і другий крок, на якому перевірку доводять не до буфера, а до пластини диска.

## Що будуємо

Ланцюг з трьох ланок: **відправник** ріже потік на кадри по 1024 байти й ставить кожному контрольну суму; **ретранслятор** приймає кадр, перевіряє суму, перекладає дані у свій вихідний буфер і ставить **нову** суму; **отримувач** перевіряє суму й складає дані. Поверх усього цього два кінці — і тільки вони — ведуть геш усього потоку: відправник рахує його від того, що читає, отримувач — від того, що доходить.

Псування вставляємо у три місця, кожне зі своєю частотою на байт:

- **дріт A → R** — після того, як відправник порахував суму, і до того, як ретранслятор її перевірив;
- **копіювання в ретрансляторі** — між перевіркою вхідної суми і обчисленням вихідної;
- **дріт R → B** — після того, як ретранслятор поставив нову суму, і до перевірки отримувачем.

Форма псування одна: **перестановка пари байтів усередині кадру**. Вибір не випадковий. По-перше, це саме та несправність, яку колись мав шлюз у мережі MIT. По-друге, це найввічливіше псування, яке взагалі буває: довжина не змінюється, набір байтів той самий, змінюється тільки порядок. Якщо перевірка не бачить навіть цього, розмова про решту зайва.

Міряти будемо три речі: яку частку реальних псувань ловить кожна перевірка; скільки байтів проходить до першої помилки, яку ділянкові перевірки пропустили; і чи ловиться псування, що сталося вже після того, як мережа зробила свою справу.

## Ділянкова перевірка — справжня, не іграшкова

Беремо не вигадану суму, а ту, що працює в TCP, UDP та IP, — інтернет-контрольну суму з RFC 1071: додавання шістнадцятибітових слів в оберненому коді, де перенос повертається назад у молодший розряд.

```cpp
// stand.cpp — збірка: g++ -O2 -std=c++17 stand.cpp -o stand
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <random>
#include <utility>
#include <vector>

constexpr size_t PAYLOAD = 1024;                 // байтів даних у кадрі

struct Frame {
    uint8_t  data[PAYLOAD];
    uint32_t len;
    uint16_t sum;                                // ділянкова перевірка їде в кадрі
};

// Інтернет-контрольна сума (RFC 1071). Байти складаються парами
// у 16-бітові слова, перенос повертається в молодший розряд.
uint16_t checksum16(const uint8_t* p, size_t n) {
    uint32_t s = 0;
    for (size_t i = 0; i + 1 < n; i += 2)
        s += (uint32_t(p[i]) << 8) | p[i + 1];
    if (n & 1)
        s += uint32_t(p[n - 1]) << 8;       // непарний хвіст — як старший байт
    while (s >> 16)
        s = (s & 0xFFFF) + (s >> 16);       // згортаємо перенос
    return uint16_t(~s);
}
```

Реалізацію варто відразу перевірити на прикладі з самого RFC: послідовність `00 01 f2 03 f4 f5 f6 f7` дає суму `ddf2`, тобто контрольну суму `220d`. Рядок `if (checksum16(vec, 8) != 0x220d) return 2;` на початку `main` рятує від годин полювання на «дивні» результати стенда, причина яких насправді в самій сумі.

Тепер найцікавіше, і саме воно робить цей стенд повчальним. Сума складає байти **з вагою за їхнім місцем**: байт на парному зсуві важить 256, байт на непарному — 1. Порядок усередині кожної з двох груп сумі байдужий — це прямо записано у властивостях самої суми в RFC 1071: доки збережено поділ байтів на парні й непарні, додавати можна в будь-якому порядку. Звідси коротка алгебра перестановки:

```
сума = Σ wᵢ · bᵢ ,   wᵢ = 256 для парного i,  wᵢ = 1 для непарного

переставили байти на місцях i та j:
Δ = (wᵢ − wⱼ) · (bⱼ − bᵢ)

wᵢ = wⱼ  (однакова парність)  →  Δ = 0        сума та сама, перевірка мовчить
wᵢ ≠ wⱼ  (різна парність)     →  |Δ| = 255·|bⱼ − bᵢ| ≤ 65025
```

Другий рядок треба дочитати до кінця. Арифметика оберненого коду працює за модулем 65535, а 65025 менше за 65535 — отже, ненульове Δ ніколи не «обернеться в нуль», і перестановка байтів різної парності ловиться **завжди**, а не з імовірністю 1 − 1/65536, як для випадкового псування. Дві половини одного механізму: одна частина перестановок невидима гарантовано, друга — ловиться гарантовано.

![Дві панелі з чотирма байтами кадру: ліворуч переставлено байти на нульовому й другому місці, обидва парні, і сума 65062 не змінюється; праворуч переставлено байти на нульовому й першому місці, парність різна, і сума падає з 65062 до 58177, тобто на 255·(0x3A − 0x1F) = 6885](img/parity-blindspot.svg)

*Вага байта визначена його місцем, а не сусідством. Поміняти місцями два байти однакової парності — це переставити доданки в тій самій сумі: результат не змінюється, і жодна перевірка ділянки нічого не скаже. Про це й про інші сліпі плями конкретно цієї суми — [інтернет-контрольна сума](root:com-modulation/internet-checksum).*

## Наскрізна перевірка — геш усього потоку

На кінцях потрібна функція з протилежною властивістю — чутлива до порядку й до кожного біта. Щоб стенд не тягнув залежностей, беремо FNV-1a на 64 біти: чотири рядки, кожен байт множить стан на просте число.

```cpp
// Наскрізна перевірка: геш потоку, який ведуть тільки два кінці.
struct Fnv1a {
    uint64_t h = 0xcbf29ce484222325ull;          // початковий стан FNV-1a 64
    void feed(const uint8_t* p, size_t n) {
        for (size_t i = 0; i < n; ++i) {
            h ^= p[i];
            h *= 0x100000001b3ull;               // просте число FNV
        }
    }
};
```

Множення на кожному кроці й робить геш чутливим до порядку: переставлені байти дають інший стан, бо потрапляють у різну кількість наступних множень. Для стенда цього досить — випадкове псування він ловить із запасом. Для бойової системи ні: FNV не тримає удару супротивника, який **добирає** дані під потрібний геш, тож там на кінцях стоїть криптографічний геш ([криптографічний геш](root:sf-security/cryptographic-hash)). Різниця саме в цьому, а не в довжині значення.

## Ретранслятор, що підписує підробку

Ось увесь шлях кадру одним шматком. Найважливіше в ньому — три рядки поспіль усередині ретранслятора: перевірка вхідної суми, копіювання, обчислення вихідної суми. Псування стоїть між першим і третім.

```cpp
// Один прохід кадру через увесь ланцюг.
// true  — ділянкова перевірка підняла тривогу, кадр піде наново;
// false — кадр прийнято (можливо, зіпсованим).
bool carry(Bench& b, const uint8_t* src, size_t n, uint8_t* dst) {
    b.dirty = 0;

    Frame f{};                                   // ── відправник
    std::memcpy(f.data, src, n);
    f.len = uint32_t(n);
    f.sum = checksum16(f.data, n);               // сума народжується ТУТ

    b.corrupt(b.wireA, f.data, n);               // ── дріт A → R

    if (checksum16(f.data, f.len) != f.sum) {    // ── ретранслятор: перевірка ділянки
        b.caught_hop += b.dirty;
        return true;
    }
    Frame g{};
    std::memcpy(g.data, f.data, f.len);          // копіювання всередині ретранслятора
    b.corrupt(b.relay, g.data, f.len);           // ← псування МІЖ перевіркою й сумою
    g.len = f.len;
    g.sum = checksum16(g.data, g.len);           // сума рахується З ТОГО, ЩО ВИЙШЛО

    b.corrupt(b.wireB, g.data, g.len);           // ── дріт R → B

    if (checksum16(g.data, g.len) != g.sum) {    // ── отримувач: перевірка ділянки
        b.caught_hop += b.dirty;
        return true;
    }
    std::memcpy(dst, g.data, g.len);
    b.missed_hop += b.dirty;                     // кадр прийнято — і, можливо, дарма
    return false;
}
```

Зверни увагу на облік. Псування зараховують у `caught_hop`, якщо кадр **відкинуто**, і в `missed_hop`, якщо кадр **прийнято**. Це і є чесне означення «непомічена помилка»: не «сума не збіглася десь колись», а «зіпсовані дані пройшли крізь усі ділянкові перевірки й лягли в буфер отримувача». Кадр, який відкинули, у стенді просто передають наново — інакше два геші розійшлися б через дірку в потоці, а не через псування.

## Інжектор: геометричний проміжок замість монети на кожен байт

Псування рідкісні: одна подія на мільйон байтів. Кидати монету на кожен байт — це витратити 999 999 кидків намарно. Тому тягнемо одразу **довжину чистого проміжку** — скільки байтів пройде до наступної події. Це геометричний розподіл, той самий, з яким потім будемо звіряти вимір ([геометричний розподіл](root:math-probability/geometric-distribution)):

```cpp
// Джерело псувань на одній ділянці.
struct Injector {
    std::mt19937_64 rng;
    std::geometric_distribution<long long> gap;   // чистий проміжок у байтах
    long long countdown;

    Injector(uint64_t seed, double rate) : rng(seed), gap(rate) { countdown = gap(rng); }

    // Пропустити len байтів і скласти зсуви подій, що на них припали.
    void advance(size_t len, std::vector<size_t>& hits) {
        hits.clear();
        size_t pos = 0;
        while (countdown < (long long)(len - pos)) {
            pos += (size_t)countdown;
            hits.push_back(pos);
            ++pos;                                // байт із подією спожито
            countdown = gap(rng);
        }
        countdown -= (long long)(len - pos);      // решту проміжку несемо в наступний кадр
    }
};
```

Лічильник переживає межі кадрів — тож частота псування прив'язана до байтів у дроті, а не до того, як ми нарізали кадри. Сам стенд тримає три такі джерела й перетворює подію на перестановку:

```cpp
struct Bench {
    Injector wireA, relay, wireB;        // три незалежні джерела псування
    std::mt19937_64 pick;                // вибір другого байта в парі
    std::vector<size_t> hits;

    uint64_t bytes = 0;                  // корисних байтів доставлено
    uint64_t caught_hop = 0, missed_hop = 0, resent = 0;
    size_t   dirty = 0;                  // реальних псувань у поточному кадрі

    Bench(uint64_t seed, double rate)
        : wireA(seed + 1, rate), relay(seed + 2, rate),
          wireB(seed + 3, rate), pick(seed + 4) {}

    void corrupt(Injector& src, uint8_t* d, size_t len) {
        src.advance(len, hits);
        std::uniform_int_distribution<size_t> pos(0, len - 1);
        for (size_t i : hits) {
            size_t j = pos(pick);
            while (j == i) j = pos(pick);
            if (d[i] == d[j]) continue;   // байти однакові — зміни не сталося
            std::swap(d[i], d[j]);
            ++dirty;
        }
    }
};
```

Головний цикл тримає два геші й ганяє потік:

```cpp
const double   rate = 1e-6;                       // псувань на байт на КОЖНІЙ ділянці
const uint64_t size = 64ull << 20;                // 64 МіБ потоку

Bench b(20260802, rate);
std::mt19937_64 source(1);                        // «файл», який передаємо
std::vector<uint8_t> in(PAYLOAD), out(PAYLOAD);
Fnv1a tx, rx;

while (b.bytes < size) {
    for (size_t i = 0; i < PAYLOAD; ++i) in[i] = uint8_t(source());
    tx.feed(in.data(), PAYLOAD);                  // кінець A — від того, що читає
    while (carry(b, in.data(), PAYLOAD, out.data())) ++b.resent;
    rx.feed(out.data(), PAYLOAD);                 // кінець B — від того, що дійшло
    b.bytes += PAYLOAD;
}
std::printf("зловила ділянка %llu, пройшло далі %llu, геші %s\n",
            (unsigned long long)b.caught_hop, (unsigned long long)b.missed_hop,
            tx.h == rx.h ? "збіглися" : "РОЗІЙШЛИСЯ");
```

## Дві незалежні причини сліпоти

Прогін на 64 МіБ із частотою 10⁻⁶ на байт на кожній ділянці дає близько двохсот реальних псувань. Ділянкові перевірки ловлять із них приблизно **третину**. Наскрізний геш — усі: щоб він змовчав, потрібен збіг 64-бітових значень, тобто один випадок на 1.8·10¹⁹.

Третина — це не випадкове число, і причин у неї рівно дві, зовсім різних за природою.

```
частка подій, що справді щось міняють (байти в парі різні):
    255/256 = 0.99609

частка перестановок із зсувами різної парності (кадр 1024 байти):
    512·512·2 / (1024·1023) = 0.50049

ділянкова перевірка ПРОПУСКАЄ реальне псування:
    1/3 · 1            (копія в ретрансляторі — невидима завжди)
  + 2/3 · (1 − 0.50049) (дроти — половина перестановок невидима)
  = 0.66634

ловить:  1 − 0.66634 = 0.33366
```

Перший доданок — це діра **в розміщенні**: сума перераховується вже після псування, тому копіювання всередині ретранслятора не покрито взагалі, хоч би якою досконалою була сама функція. Другий — діра **в арифметиці**: сума сліпа до перестановок однакової парності. Другу можна полагодити, замінивши суму на CRC ([контрольні суми](root:com-modulation/checksums)). Першу — нічим, що живе нижче за кінці: після заміни на CRC частка пропущених упаде з 2/3 до рівно 1/3, і ця третина лишиться назавжди, бо це не хиба алгоритму, а місце виклику.

> 🔧 **Навіщо це.** Стенд коштує вечора, а купує звичку читати «перевірка пройшла» правильно. Ділянкова перевірка каже: «те, що я віддаю, збігається з тим, що я підписав». Вона не каже нічого про те, чи те, що вона підписала, збігається з тим, що їй дали. Різниця в один крок міркування — і в дві третини непомічених псувань на цьому стенді.

## Скільки байтів до першого пропуску

Тепер вимір, заради якого все й будувалося. Частота непоміченої помилки на байт потоку:

```
q = 3p · 0.99609 · 0.66634          три ділянки, кожна з частотою p

p = 10⁻⁶  →  q = 1.9912·10⁻⁶

середнє     1/q      = 502 206 байтів ≈ 0.48 МіБ
медіана     ln2 / q  = 348 103 байти
розкид      σ = √(1−q)/q ≈ 1/q
```

Останній рядок — головний. У геометричного розподілу **стандартне відхилення дорівнює середньому**. Це означає, що один прогін стенда не доводить нічого: він може закінчитися і на семистах байтах, і на трьох з половиною мегабайтах.

Дві тисячі незалежних прогонів моделі стенда дають таке: середнє 502 940 байтів (0.480 МіБ) проти теоретичних 502 206; медіана 351 387 проти 348 103; σ = 510 670, тобто справді дорівнює середньому. Найкоротший прогін закінчився на **710 байтах** — перше ж псування виявилося невидимим. Найдовший протягнув **3.42 МіБ**. Кожен п'ятий прогін (19.4 %) закінчився менш ніж за 100 КіБ.

![Гістограма: частка з 2000 прогонів стенда за кількістю мегабайтів, що пройшли до першої непоміченої ділянковою перевіркою помилки; смуги спадають експоненційно від 19 % у першій сотні кілобайтів; вертикальні лінії позначають медіану 0.34 МіБ і середнє 0.48 МіБ; праворуч підпис, що σ дорівнює середньому, тому один прогін нічого не доводить](img/miss-histogram.svg)

*Розподіл без піку: найімовірніший результат — «дуже скоро», а хвіст тягнеться усемеро далі за середнє. Саме тому непомічені псування в реальних системах виглядають як «нічого не було, нічого не було, а тоді раптом три за тиждень».*

Звідси й дисципліна виміру. Похибка середнього — це σ/√R, тож смуга на дві тисячі прогонів виходить 480 600 … 525 300 байтів, і теоретичні 502 206 всередині неї. Щоб дістати точність усього в десять відсотків, треба вже близько чотирьохсот прогонів ([довірчий інтервал](root:math-probability/confidence-interval)). Той, хто прогнав стенд один раз, побачив 3 МіБ і зробив висновок «перевірка на ділянці працює непогано», зміряв не стенд, а власне везіння.

Режим виміру — це десять рядків поверх того самого стенда: кожен прогін бере власне зерно, женеться до першого пропуску й друкує пройдені байти.

```cpp
// Скільки байтів проходить до ПЕРШОГО псування, якого ділянкові
// перевірки не побачили. Кожен прогін — незалежний потік.
uint64_t bytes_to_first_miss(uint64_t seed, double rate) {
    Bench b(seed, rate);
    std::mt19937_64 source(seed ^ 0x9e3779b97f4a7c15ull);
    std::vector<uint8_t> in(PAYLOAD), out(PAYLOAD);
    for (;;) {
        for (size_t i = 0; i < PAYLOAD; ++i) in[i] = uint8_t(source());
        while (carry(b, in.data(), PAYLOAD, out.data())) {}
        b.bytes += PAYLOAD;
        if (b.missed_hop) return b.bytes;
    }
}
```

Прогін і статистику зручно винести в окремий скрипт: стенд у режимі `--runs` друкує по числу на рядок і більше нічого.

```python
#!/usr/bin/env python3
"""Проганяє стенд R разів і звіряє вимір з аналітичним очікуванням."""
import math, statistics, subprocess

RUNS, P, L = 2000, 1e-6, 1024

out = subprocess.run(["./stand", "--runs", str(RUNS), repr(P)],
                     capture_output=True, text=True, check=True).stdout
xs = [int(v) for v in out.split()]

mean, sd = statistics.fmean(xs), statistics.stdev(xs)
se = sd / math.sqrt(len(xs))

p_parity = (L // 2) ** 2 * 2 / (L * (L - 1))     # зсуви різної парності
p_real = 255 / 256                               # байти в парі різні
p_miss = 1 / 3 + 2 / 3 * (1 - p_parity)          # ділянкова перевірка сліпа
q = 3 * P * p_real * p_miss

print(f"прогонів      {len(xs):>12,}")
print(f"середнє       {mean:>12,.0f}   теорія 1/q = {1 / q:,.0f}")
print(f"95 % смуга    {mean - 1.96 * se:>12,.0f} .. {mean + 1.96 * se:,.0f}")
print(f"σ             {sd:>12,.0f}   (у геометричного σ ≈ середнє)")
print(f"медіана       {statistics.median(xs):>12,.0f}   теорія ln2/q = {math.log(2) / q:,.0f}")
print(f"найкоротший   {min(xs):>12,}")
print(f"найдовший     {max(xs):>12,}")
```

## Крок другий: довести перевірку до пластини

Досі наскрізний геш отримувача рахувався з буфера, який приїхав із мережі. Це половина роботи. Задача говорить про **файл на диску**, а між буфером і диском лежить ще один запис, ще одне копіювання і ще один пристрій, який уміє мовчки псувати дані ([тихе псування даних](root:sf-data/bit-flips)).

Довести перевірку до кінця — це рахувати геш не з того, що прийняли, а з того, що **прочиталося назад із файла**:

```cpp
#include <fcntl.h>
#include <unistd.h>

// Записати й дочекатися, поки дані справді підуть на носій.
bool store(const char* path, const uint8_t* d, size_t n) {
    int fd = ::open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return false;
    for (size_t off = 0; off < n; ) {
        ssize_t w = ::write(fd, d + off, n - off);
        if (w <= 0) { ::close(fd); return false; }
        off += size_t(w);
    }
    bool ok = (::fsync(fd) == 0);       // без цього дані ще в кеші сторінок
    return (::close(fd) == 0) && ok;
}

// Геш ІЗ ФАЙЛА, а не з буфера, що лишився в пам'яті.
uint64_t hash_stored(const char* path) {
    int fd = ::open(path, O_RDONLY);
    if (fd < 0) return 0;
    ::posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED);   // спробувати викинути кеш
    Fnv1a h;
    std::vector<uint8_t> buf(1 << 16);
    for (;;) {
        ssize_t got = ::read(fd, buf.data(), buf.size());
        if (got <= 0) break;
        h.feed(buf.data(), size_t(got));
    }
    ::close(fd);
    return h.h;
}
```

Тут ховається пастка, через яку «перевірка з диска» часто виявляється перевіркою пам'яті. Читання одразу після запису найімовірніше віддасть ті самі сторінки з кеша, а не з носія, — і геш збіжиться навіть тоді, коли на пластині лежить сміття. `fsync` перед закриттям робить сторінки чистими (брудні сторінки ядро не викидає взагалі), а `POSIX_FADV_DONTNEED` після цього просить їх викинути — але це **порада, а не гарантія**. Надійніше читати через `O_DIRECT` із вирівняним буфером; на macOS те саме роблять через `fcntl(fd, F_NOCACHE, 1)`. Механіку кеша сторінок і того, що насправді обіцяє `fsync`, розібрано окремо: [кеш сторінок, fsync і довговічність запису](root:sys-unix/page-cache-durability).

Тепер сама демонстрація. Псуємо файл уже після того, як мережа сказала «чисто», — переставляємо в ньому пару байтів однакової парності, тобто рівно те, до чого сліпа будь-яка сума:

```cpp
// Модель тихого псування на носії.
bool rot(const char* path, off_t a, off_t b) {
    int fd = ::open(path, O_RDWR);
    if (fd < 0) return false;
    uint8_t x = 0, y = 0;
    ::pread(fd, &x, 1, a);
    ::pread(fd, &y, 1, b);
    ::pwrite(fd, &y, 1, a);
    ::pwrite(fd, &x, 1, b);
    ::fsync(fd);
    ::close(fd);
    return true;
}
```

І дві перевірки поруч — та, що здається наскрізною, і та, що є:

```cpp
// sink — усе, що отримувач склав із прийнятих кадрів; tx — геш кінця A.
store("copy.bin", sink.data(), sink.size());
rot("copy.bin", 4096, 4098);                 // однакова парність — сумі байдуже

Fnv1a from_buffer;
from_buffer.feed(sink.data(), sink.size());
const uint64_t from_disk = hash_stored("copy.bin");

std::printf("геш із буфера %016llx  %s\n", (unsigned long long)from_buffer.h,
            from_buffer.h == tx.h ? "збігся" : "РОЗБІЖНІСТЬ");
std::printf("геш із файла  %016llx  %s\n", (unsigned long long)from_disk,
            from_disk == tx.h ? "збігся" : "РОЗБІЖНІСТЬ");
```

Перший рядок каже «збігся». Другий — «розбіжність». Різниця між ними — один аргумент у виклику: гешувати те, що в пам'яті, чи те, що на диску. Цей аргумент і є межею того, за що перевірка відповідає.

## Пастки

**Перевірка буфера замість файла.** Найпоширеніша, бо найдешевша: буфер уже в руках, читати файл назад — це зайвий прохід по даних і зайва секунда на гігабайті. Плата за цю секунду — те, що весь шлях «буфер → файлова система → драйвер → носій» лишається поза перевіркою, а система при цьому впевнено каже «скопійовано». Стенд показує ціну одним рядком виводу.

**«Спільний код на кінцях» — не те саме, що «механізм на нижчому рівні».** У цьому стенді обидві перевірки — це дві звичайні функції, `checksum16` і `Fnv1a`. Жодна з них не є «рівнем». Уся різниця в тому, **звідки їх викликають**: одну — сусідні ланки, кожна від свого буфера, другу — два кінці, від джерела й від результату. Спокуса «винесімо перевірку в спільну бібліотеку, щоб не дублювати код» абсолютно законна й нічого не ламає, доки бібліотеку викликають на кінцях. Ламає інше — коли той самий код переносять **униз**, у ланку, і починають вважати її відповідь відповіддю на питання про весь шлях. На діаграмі ці два випадки виглядають однаково, у коді відрізняються місцем виклику, а за наслідками — як «правильно» і «ніколи не правильно».

**Хибне відчуття надійності від суми TCP.** `checksum16` у стенді — не спрощена модель, а буквально та сума, що стоїть у TCP. Її сліпа пляма до перестановок однакової парності — не екзотика, підібрана під демонстрацію, а прямий наслідок того, що сума складає байти з вагою за місцем. Нижче лежить CRC канального рівня, значно сильніший, — але він захищає кадр між двома сусідніми пристроями й нічого не знає про пам'ять ретранслятора, що лежить **вище** за нього. Два добрі механізми, поставлені поруч, покривають дві ділянки, а не шлях.

**Частота стенда не має нічого спільного з твоєю.** 10⁻⁶ на байт — це частота зі старої історії про несправний шлюз, узята, щоб вимір закінчувався за секунди. У твоїй системі вона може бути на шість порядків меншою — і тоді середні півмегабайта до першого пропуску перетворяться на терабайти. Стенд міряє **структуру** сліпоти: які саме класи псувань проходять крізь ділянкові перевірки і чому. Частоту треба міряти у себе, а не приносити звідси.

**Перестановка — найважче псування для суми й цілком звичайне для гешу.** Якщо замінити її на випадковий байт у випадковому місці, дроти почнуть ловити майже все (сума пропускає таке приблизно раз із 65 536), і частка непоміченого впаде з двох третин до однієї. Ця третина — псування в копіюванні ретранслятора — не зникає ні за якої форми помилки й ні за якої контрольної суми. Саме її не видно з жодної точки, крім двох кінців.
