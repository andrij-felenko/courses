# ⚙️ Конвеєр, що тримає кістяк ходячим

Кістяк вартий своєї назви рівно доти, доки **ходить** — доки наскрізний шлях проганяється сам, на кожну зміну, а не «колись пройшов і його закинули». Слово легко вимовити, важче втримати: варто раз забути прогнати нитку — і стики починають нишком розповзатися, бо кожна правка в будь-якому вузлі має шанс зсунути якусь домовленість, а без прогону цей зсув невидимий. Тому «ходити» — це не побажання, а конкретна машинерія: наскрізний **димовий тест**, який жене справжній вхід крізь усі вузли й стверджує справжній вихід, плюс **конвеєр**, що збирає, розгортає й запускає цей тест на кожну зміну й **червонить збірку**, коли нитка не пройшла.

Зберімо цю машинерію на живому. Візьмімо конкретну розподілену нитку — таку, де є справжні межі між процесами: браузер шле число на HTTP-край, `API` кладе його в **брокер повідомлень**, окремий **воркер** вичитує з брокера й пише у сховище, а читання назад повертає збережене. Нас цікавить не логіка вузлів (вона тут навмисне вбога — одне число), а чи домовляться вузли між собою на живому: чи те, що `API` поклав у брокер, воркер вичитав так, як гадав, і поклав туди, де читання його знайде.

## Задача і головна ідея

**Умова: зробити так, щоб на кожну зміну автоматично збиралася вся нитка, розгорталася на прод-подібне середовище, і наскрізний тест доводив — одне справжнє значення пройшло від HTTP-входу крізь брокер і воркера до читання назад; якщо не пройшло — збірка червона, зміну не влито.**

Ідея тесту вся в одному розрізненні, на якому прийом стоїть або падає. Слабкий тест перевіряє, що **кожен вузол зелений**: `API` відповідає, брокер живий, воркер піднявся, сховище доступне. Але вузли можуть бути всі до одного зелені, а нитка — мертва: `API` кладе в брокер big-endian, воркер читає little-endian; воркер пише під ключем `temp`, а читання шукає `temperature`; черга називається `jobs`, а воркер підписаний на `job`. Кожен вузол чесно рапортує «я в порядку» — і кожен у порядку **сам по собі**. Сильний тест перевіряє інше: що **нитка пройшла наскрізь** — подає справжній вхід у перший вузол і стверджує, що справжній вихід з'явився на останньому, не заглядаючи всередину. Він торкається **лише двох країв** — шле на HTTP-вхід, читає з HTTP-виходу, — а всю середину лишає системі, щоб значення справді проїхало крізь **справжній** брокер, справжнього воркера, справжнє сховище. Це, по суті, [виконуваний тест архітектури](topic:sf-apps/fitness-functions): він щоразу перевіряє не одну частину, а що ціле досі складається.

![Ліворуч: чесний димовий тест торкається лише двох країв — шле на POST-вхід і читає з GET-виходу, — а значення мусить пройти крізь справжній брокер і воркера; стверджується сам вихід. Праворуч: та сама зелена галочка, але тест читає сховище напряму, короткозамкнувши брокер і воркера — вузли зелені, стик мертвий, збірка бреше](img/keep-walking.svg)

*Зелений димовий тест не дорівнює живій нитці. Тест вартий чогось, лише коли значення проходить крізь справжні стики, а не коли він торкається країв в обхід їх.*

## Наскрізний димовий тест

Ось цей тест — той, що жене число від HTTP-входу до HTTP-виходу й стверджує саме вихід. Він навмисне примітивний і навмисне **зовнішній**: не імпортує жодної функції системи, а стукає по мережі в **уже розгорнуту** нитку — так само, як стукав би справжній клієнт. Три деталі в ньому несуть усю вагу, і на них варто спинитися після коду.

:::tabs
```ts
// e2e-smoke.ts — жене справжнє значення від HTTP-краю крізь усі вузли й СТВЕРДЖУЄ вихід.
// Стукає ПО МЕРЕЖІ в уже розгорнуту нитку (реальний брокер), не імпортує її функцій.
const BASE = process.env.SMOKE_URL ?? "http://localhost:8080";

// (1) Унікальне значення на КОЖЕН прогін: так ми читаємо СВІЙ запис, а не леглий
// з минулого разу. Якби слали стале число, тест зеленів би й на мертвій нитці.
const sent = String(1000 + Math.floor(Math.random() * 9000));

async function main() {
  // (2) справжній вхід у ПЕРШИЙ вузол — HTTP-край
  const post = await fetch(`${BASE}/temp`, { method: "POST", body: sent });
  if (!post.ok) throw new Error(`POST дав ${post.status}`);

  // (3) ОПИТУЄМО останній край, поки значення пройде API → брокер → воркер → сховище.
  // Опитування з дедлайном, а не фіксований сон: система асинхронна, і час
  // проходу нитки — величина плавуча, а не константа.
  const deadline = Date.now() + 10_000;
  while (Date.now() < deadline) {
    const got = await fetch(`${BASE}/temp`);
    if (got.ok && (await got.text()).trim() === sent) {
      console.log(`нитка пройшла наскрізь: ${sent} повернулось із іншого краю`);
      return; // СТВЕРДЖЕННЯ справдилось: дочекались саме НАШОГО значення
    }
    await new Promise((r) => setTimeout(r, 200));
  }
  throw new Error(`нитка не пройшла: ${sent} не з'явилось на іншому краї`);
}

main().catch((e) => { console.error("ДИМОВИЙ ТЕСТ ЧЕРВОНИЙ:", e.message); process.exit(1); });
```

```go
// e2e_smoke_test.go — жене справжнє значення від HTTP-краю крізь усі вузли й СТВЕРДЖУЄ вихід.
// `go test` ПРОТИ вже розгорнутої нитки (SMOKE_URL); торкається лише двох країв.
package smoke

import (
	"io"
	"math/rand"
	"net/http"
	"os"
	"strconv"
	"strings"
	"testing"
	"time"
)

func base() string {
	if u := os.Getenv("SMOKE_URL"); u != "" {
		return u
	}
	return "http://localhost:8080"
}

func TestThreadWalksEndToEnd(t *testing.T) {
	// (1) Унікальне значення на прогін: читаємо СВІЙ запис, не леглий з минулого разу.
	sent := strconv.Itoa(1000 + rand.Intn(9000))

	// (2) справжній вхід у перший вузол — HTTP-край
	resp, err := http.Post(base()+"/temp", "text/plain", strings.NewReader(sent))
	if err != nil {
		t.Fatalf("POST не пройшов: %v", err)
	}
	resp.Body.Close()
	if resp.StatusCode != 200 {
		t.Fatalf("POST дав код %d", resp.StatusCode)
	}

	// (3) опитуємо останній край з дедлайном (не фіксований сон), поки значення
	// пройде API → брокер → воркер → сховище й виявиться на іншому краї.
	deadline := time.Now().Add(10 * time.Second)
	for time.Now().Before(deadline) {
		if got, err := http.Get(base() + "/temp"); err == nil {
			b, _ := io.ReadAll(got.Body)
			got.Body.Close()
			if strings.TrimSpace(string(b)) == sent {
				return // СТВЕРДЖЕННЯ: повернулось саме наше значення — нитка пройшла
			}
		}
		time.Sleep(200 * time.Millisecond)
	}
	t.Fatalf("нитка не пройшла: %s не з'явилось на іншому краї", sent)
}
```
```python
# e2e_smoke.py — жене справжнє значення від HTTP-краю крізь усі вузли й СТВЕРДЖУЄ вихід.
# Запуск ПРОТИ вже розгорнутої нитки (SMOKE_URL); торкаємось лише двох країв.
import os, random, sys, time, urllib.request

BASE = os.environ.get("SMOKE_URL", "http://localhost:8080")

# (1) Унікальне значення на прогін: читаємо СВІЙ запис, а не леглий з минулого разу.
sent = str(1000 + random.randrange(9000))

def post(v: str) -> int:
    req = urllib.request.Request(f"{BASE}/temp", data=v.encode(), method="POST")
    return urllib.request.urlopen(req, timeout=5).status

def get() -> str:
    with urllib.request.urlopen(f"{BASE}/temp", timeout=5) as r:
        return r.read().decode().strip()

# (2) справжній вхід у перший вузол — HTTP-край
if post(sent) != 200:
    sys.exit("ДИМОВИЙ ТЕСТ ЧЕРВОНИЙ: POST не пройшов")

# (3) опитуємо останній край з дедлайном на МОНОТОННОМУ годиннику (не сон, не
# настінний час), поки значення пройде API → брокер → воркер → сховище.
deadline = time.monotonic() + 10
while time.monotonic() < deadline:
    try:
        if get() == sent:                 # СТВЕРДЖЕННЯ: повернулось саме наше значення
            print(f"нитка пройшла наскрізь: {sent}")
            sys.exit(0)                   # зелено
    except OSError:
        pass                              # система ще підводиться — пробуємо далі
    time.sleep(0.2)

sys.exit(f"ДИМОВИЙ ТЕСТ ЧЕРВОНИЙ: нитка не пройшла, {sent} не з'явилось")
```
:::

Придивися до трьох позначених місць, бо кожне лагодить окрему тиху ваду. **(1) Унікальне значення на кожен прогін.** Спокуса — слати стале `235`. Але тоді у сховищі це число могло лишитися з **минулого** прогону, і тест зазеленіє, навіть якщо цього разу нитка мертва: він прочитає леглий слід, а не свіжий прохід. Свіже випадкове число на кожен старт робить ствердження чесним — ми чекаємо саме **наш** запис, а не будь-який. **(2) Вхід і вихід — тільки HTTP-краї.** Тест нічого не знає про брокер, воркер чи сховище: він шле на той самий `POST`, що й браузер, і читає той самий `GET`. Саме тому значення **мусить** проїхати крізь усі справжні стики — інакше воно не з'явиться на виході. **(3) Опитування з дедлайном, а не сон.** Система асинхронна: між `POST` і появою значення на виході лежить прохід крізь чергу, і його тривалість плаває від міліграма до сотень мілісекунд залежно від навантаження. Фіксований `sleep(1)` тут — або марно повільно, або зрадливо мало; опитування з дедлайном чекає рівно стільки, скільки треба, і падає, лише коли час вичерпано. У Python-версії дедлайн навмисне на [монотонному годиннику](topic:sf-apps/monotonic-vs-wall-time), а не на настінному, щоб стрибок системного часу під час прогону не зсунув межу.

## Конфіг конвеєра

Тепер обв'язка, що робить цей тест **ходячим** — тобто проганяє його сам, на кожну зміну. Це і є [конвеєр неперервної інтеграції](topic:sf-release/ci-cd) у мініатюрі: зібрати всю нитку з нуля, розгорнути на прод-подібне середовище, прогнати наскрізний тест — і, якщо нитка не пройшла, впасти червоним, щоб зміну не влили. Ось робочий конфіг для GitHub Actions; кожен крок підписаний, що саме він стереже.

```yaml
# .github/workflows/skeleton.yml
# На КОЖНУ зміну: зібрати → розгорнути на цільове середовище → прогнати наскрізний
# димовий тест. Нитка не пройшла — job падає, збірка ЧЕРВОНА, зміну не влито.
name: keep-the-skeleton-walking

on: [push, pull_request]

jobs:
  smoke:
    runs-on: ubuntu-24.04             # фіксуємо ОС, а не «-latest»: інакше дрейф середовища
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: "20.11.1"     # ТОЧНА версія рантайму, та сама, що в проді

      # 1) ЗІБРАТИ всю нитку з нуля, без ручних кроків «усі й так знають»
      - run: npm ci                   # відтворна установка з lock-файлу, не «npm install»
      - run: npm run build

      # 2) РОЗГОРНУТИ на прод-подібне: той самий образ, ті самі вузли — і СПРАВЖНІЙ брокер
      - run: docker compose up -d --build   # api + broker + worker + store, як у проді
      - run: ./scripts/wait-healthy.sh      # чекати, поки всі вузли health-ready

      # 3) ПРОГНАТИ наскрізний тест ПРОТИ розгорнутого, крізь справжній брокер
      - run: node dist/e2e-smoke.js
        env:
          SMOKE_URL: http://localhost:8080

      # 4) прибрати ЗАВЖДИ — навіть якщо тест упав, щоб не лишити брудний стан для сусіда
      - if: always()
        run: docker compose down -v
```

Червоніння тут не окремий механізм, а звичайний код виходу: якщо `node dist/e2e-smoke.js` завершиться ненульовим кодом (а він завершується, коли нитка не пройшла), крок падає, `job` падає, коміт помічається червоним — і в налаштованому репозиторії такий коміт не можна злити в основну гілку. Ось і весь замок: щоб зламати наскрізний шлях, треба **свідомо** обійти червону збірку, а не просто забути прогнати тест. Кістяк перестає залежати від людської пам'яті й починає залежати від конвеєра — саме те, чого прийом і потребує, щоб лишатися ходячим довше за перший тиждень захвату.

Зверни увагу, що конфіг **розгортає** нитку по-справжньому (`docker compose up`), а не просто запускає юніт-тести. Це навмисне: саме розгортання майже-порожнього кістяка витягує назовні найгидкіші сюрпризи — права доступу, мережеві межі, змінні середовища, версії рантайму, — ті самі стики, тільки між кодом і **середовищем**. Дешевше зустріти їх, поки система важить три байти, ніж на релізі.

## Складність і пастки

Уся ця машинерія має підступну властивість: вона може **виглядати** справною, будучи мертвою. Зелена галочка гріє душу й присипляє пильність, тож найнебезпечніші вади — саме ті, що лишають галочку зеленою. Розберімо чотири, які трапляються найчастіше; спільний у них корінь один — тест перестає по-справжньому вправляти той стик, заради якого існує.

**Тест б'є в заглушку замість справжнього стику.** Найспокусливіша зручність — щоб тест «швидше й стабільніше» проганявся, підняти нитку з **заглушкою** замість брокера: чергою в пам'яті того самого процесу. Тест зеленіє миттєво й ніколи не блимає — бо він більше не перевіряє те, що мав. Справжній ризик сидів саме на стику з [брокером повідомлень](topic:sf-distributed/message-queue): серіалізація повідомлення, ім'я черги, підтвердження отримання, поведінка під навантаженням, порядок доставки. Черга в пам'яті не має нічого з цього — вона просто передає об'єкт по посиланню. Тест крізь неї доводить, що дві функції в одному процесі викликають одна одну, — те, що й так очевидно, — і мовчить рівно про той стик, який лякав. Правило тут жорстке: **димовий тест ганяється проти того самого розгортання, що поїде в прод, зі справжнім брокером на своєму місці**. Хочеш швидкий тест на функції в пам'яті — пиши його окремо й не називай димовим; димовий цінний саме тим, що повільніший і «справжніший».

**Дрейф середовища.** Друга вада тонша, бо тест може бути бездоганний, а брехати — середовище. Він зеленіє на машині розробника й на конвеєрі, а на цільовому середовищі нитка не проходить — бо там інша версія рантайму (воркер зібрано під Node 20, а прод крутить 18, і якийсь виклик поводиться інакше), бракує змінної середовища (`BROKER_URL` не заданий — воркер тихо підключається до `localhost`, якого в проді нема), або в сервіса нема прав писати в те сховище. Це не хиба коду — це розбіжність **середовищ**, і вона підступна тим, що невидима, поки не збіглися саме ці умови. Ліки — прибрати простір для дрейфу: **фіксувати точні версії** (не `ubuntu-latest` і не `node: 20`, а `ubuntu-24.04` і `20.11.1`), гнати той самий контейнерний образ на конвеєрі й у проді, і [винести весь конфіг у змінні середовища](topic:sf-apps/twelve-factor), щоб різницю між середовищами було видно в одному місці, а не розсипано по коду. Що менше відрізняються машина конвеєра й прод, то менше залишку, у якому дрейф ховається; ідеал — щоб димовий тест бив у **те саме** середовище, що приймає користувачів, або в його точну копію.

**Флейкі-тест і брудне прибирання.** Наскрізний тест асинхронний за природою — між входом і виходом лежить черга, — і саме тут родяться дві близькі біди. Перша: **фіксований сон** замість опитування. Пишеш `sleep(1); assert get() == sent` — і тест то проходить, то падає без зміни коду, бо час проходу нитки плаває, а одна секунда буває то з запасом, то замало. Флейкі-тест гірший за відсутній: команда швидко привчається його «перезапускати», і коли він упаде **по ділу** — на справжньому зламі нитки, — його теж перезапустять і зллють поламане. Ліки вже в коді вище: **опитування з дедлайном**, що чекає рівно до появи значення й падає, лише коли час справді вичерпано. Друга біда — **брудне прибирання**. Якщо тест лишає по собі стан (значення у сховищі, повідомлення в черзі, розгорнуті контейнери), наступний прогін стартує з бруду: прочитає леглий слід і зазеленіє на мертвій нитці, або спіткнеться об чужий недоприбраний контейнер і впаде дарма. Проти першого рятує вже згадане унікальне значення на прогін — свій слід ні з чиїм не сплутаєш; проти другого — прибирання **завжди**, навіть коли тест упав (крок `if: always()` у конфігу вище). Здорове правило — щоб кожен прогін був **герметичний**: піднявся з чистого, лишив по собі чисте.

**Тест, що обходить брокер.** Найпідступніша з чотирьох, бо тут тест ніби наскрізний, а насправді короткозамкнений. Замість слати на HTTP-вхід і читати з HTTP-виходу, він «щоб надійніше» лізе рукою всередину: кладе значення прямо у сховище й звідти ж читає, або гукає функцію воркера напряму, обминаючи чергу. Стверджувати він продовжує щось про «значення пройшло» — але єдиний стик, який ми хотіли перевірити (`API` → брокер → воркер), лишається неторкнутим. Значення ніколи не їхало крізь брокер; воно телепортувалося повз нього. Це рівно та зелена галочка на праворуч у фігурі вище: вузли живі, тест зелений, а стик мертвий і ніхто цього не бачить, поки в проді справжнє повідомлення не загубиться в черзі. Оборона проста на словах і сувора на ділі: **димовий тест торкається лише зовнішніх країв системи** — входу й виходу, доступних справжньому клієнтові, — і **жодного разу** не сягає всередину. Щойно тест починає імпортувати внутрішні функції чи стукати прямо у сховище, він перестає бути тестом нитки й стає тестом вузла в масці наскрізного.

> 🔧 **Навіщо це.** Зелена збірка має означати рівно одне, чесне й перевірюване твердження: «одне справжнє значення щойно пройшло від HTTP-входу крізь справжній брокер і воркера до читання назад». Кожна з чотирьох пасток краде саме це значення зеленого — лишає галочку, вихолостивши те, за що вона ручається. Тому, коли додаєш чи правиш димовий тест, питай не «чи він зелений», а «**що саме** його зелене доводить — і чи це той стик, який справді лякає». Якщо тест може лишитися зеленим, коли брокер мертвий, він не стереже нитку; він стереже власний спокій. А кістяк, чий вартовий стереже власний спокій, тихо перестає ходити — і ти повертаєшся рівно до тієї біди, від якої весь прийом і рятує.
