# ⚙️ Каркас модульного моноліта, збірка якого падає на порушенні межі

Межа, яку не перевіряє машина, — це не межа, а побажання, дописане олівцем на полях діаграми. Тому справжня задача цього каркаса вузька й перевірювана: описати кілька модулів так, щоб **збірка червоніла**, щойно хтось потягнеться в чужі нутрощі повз фасад. Не «домовитися на рев'ю не робити так», не «додати коментар `// приватне, не чіпати`», а зробити порушення межі **технічно неможливим або хоча б неможливим тихо** — таким, що ламає конвеєр і не проходить у гілку.

Візьмемо ту саму крамницю, що й у решті розмови про модульний моноліт: модуль `warehouse` (склад) із фасадом `Warehouse.reserve(id, qty)` і прихованою реалізацією поверх приватної таблиці залишків, і модуль `orders` (замовлення), який хоче зарезервувати товар. Правильна залежність одна: `orders` кличе `warehouse.reserve(...)` через фасад. Усе інше — `orders` імпортує клас `WarehouseServiceImpl`, або `orders` робить `SELECT` прямо зі `stock_db` складу — це і є те порушення, яке ми змушуємо машину ловити.

Розберемо це на трьох рівнях, від найсильнішого до найслабшого: (1) **видимість самої мови** — коли компілятор фізично не показує чуже; (2) **сторож-fitness-function у конвеєрі** — тест архітектури, що червоніє на забороненій залежності там, де мова дозволила зайве; (3) **лінт-правило імпортів** — найдешевший сторож для мов, де публічне все. Наприкінці — дві пастки, на яких така конструкція найчастіше тихо ламається, і покроково те, заради чого межа взагалі варта труду: як відв'язаний модуль механічно виймається в окремий сервіс.

## Ідея: інваріант межі — куди стрілці можна, куди ні

Перш ніж писати сторожа, треба назвати правило, яке він стереже. Воно коротке. **Стрілка залежності має право входити в модуль лише крізь його фасад — ніколи в його клас-реалізацію і ніколи в його таблицю.** З цього єдиного інваріанта випливає геть усе інше.

![Модуль orders ліворуч, модуль warehouse праворуч із зеленою смугою-фасадом; дозволена зелена стрілка входить у фасад через reserve(id, n), дві заборонені штрихові стрілки перекреслені: одна лізе в клас WarehouseImpl повз фасад, друга робить SELECT з чужої таблиці stock_db](img/arrows.svg)

*Дозволена рівно одна стрілка — у фасад. Імпорт чужого класу повз фасад і `SELECT` з чужої таблиці заборонені однаково: обидва — вхід в модуль не крізь двері. Напрям теж не байдужий: у модель предмету стрілки сходяться, з неї самої на технічні дрібниці — ні.*

Зверни увагу, що заборона стосується **напряму й точки входу**, а не просто «двоє модулів не спілкуються». Спілкуватися можна скільки завгодно — але тільки через оголошену поверхню. Тому сторож, який ми будуємо, завжди формулюється однаково: «жоден клас із-поза модуля `warehouse` не має залежати від класів у його внутрішньому пакеті `warehouse.internal`; ззовні дозволено бачити лише `warehouse.api`».

І ось тонкість, через яку рівнів саме три, а не один. Ідеально, коли інваріант тримає **сама мова** — тоді чужий клас просто не існує за іменем, і порушити нема як. Але видимість у мов різна: Java й C# уміють ховати клас у межах пакета/збірки, а Python, TypeScript чи Ruby — ні, там `export`/`public` за замовчуванням відкриває все. Де мова слабша, ту саму заборону доводиться дотягувати зовнішнім сторожем. Тому це не три альтернативи «оберіть одну», а **ешелони**: бери найсильніший, що дає твоя мова, і добудовуй слабші місця наступним.

![Три горизонтальні смуги-ешелони: 1 видимість мови (package-private, internal) ловить на компіляторі але не дістає Python/TS/Ruby; 2 сторож у конвеєрі (ArchUnit, Packwerk) червоніє на забороненій залежності, ловить і непрямі й межу таблиць; 3 лінт імпортів (no-restricted-imports, import-linter) падає на імпорті з чужих нутрощів, найдешевший там де мова слабша](img/enforce-layers.svg)

*Три рівні складаються, а не змагаються. Видимість мови — найдешевша й найнадійніша, але не всюди є. Сторож у конвеєрі — головний ешелон: дістає й непрямі залежності, і межу таблиць. Лінт імпортів латає мови, де публічне все.*

## Рівень 1: видимість мови — чуже просто не існує за іменем

Найсильніша межа не потребує окремого сторожа взагалі, бо порушити її нема чим: компілятор не дає навіть написати ім'я чужого класу. Секрет — розкласти модуль на два пакети: тонкий **`api`** (усе `public`, це фасад) і **`internal`** (усе package-private, це нутрощі). Тоді сусід бачить `api`, а `internal` для нього не існує.

У Java «нема модифікатора» і означає package-private — видно лише в тому самому пакеті. У C# те саме дає `internal` — видно лише в межах тієї самої збірки (assembly). Ось `warehouse` у двох мовах: фасад назовні, реалізація замкнена.

:::tabs
```java
// ── warehouse/api/Warehouse.java — фасад: public, його бачать усі ──
package shop.warehouse.api;

public interface Warehouse {
    Reservation reserve(OrderId id, int qty);   // єдине, що видно ззовні
}

// ── warehouse/internal/WarehouseServiceImpl.java — НЕ public ──
package shop.warehouse.internal;

import shop.warehouse.api.Warehouse;

// зверни увагу: НЕ "public class" — клас package-private.
// Поза пакетом shop.warehouse.internal його не видно взагалі.
class WarehouseServiceImpl implements Warehouse {
    private final StockTable stock;             // StockTable теж НЕ public

    WarehouseServiceImpl(StockTable stock) { this.stock = stock; }

    @Override public Reservation reserve(OrderId id, int qty) {
        return stock.hold(id, qty);
    }
}

// ── orders намагається зрадити межу ──
package shop.orders.internal;

import shop.warehouse.api.Warehouse;                       // ✅ фасад — можна
// import shop.warehouse.internal.WarehouseServiceImpl;    // ❌ НЕ КОМПІЛЮЄТЬСЯ:
//   "WarehouseServiceImpl is not public in shop.warehouse.internal;
//    cannot be accessed from outside package"
```
```csharp
// ── Warehouse.Api/Warehouse.cs — фасад: public ──
namespace Shop.Warehouse.Api;

public interface IWarehouse {
    Reservation Reserve(OrderId id, int qty);   // видно за межами збірки
}

// ── Warehouse.Impl/WarehouseService.cs — internal ──
namespace Shop.Warehouse.Impl;

using Shop.Warehouse.Api;

// internal: клас видно лише в СВОЇЙ збірці Warehouse.Impl.dll.
// Проєкт Orders на нього посилатися не зможе.
internal sealed class WarehouseService : IWarehouse {
    private readonly StockTable _stock;         // internal-нутрощі

    public WarehouseService(StockTable stock) => _stock = stock;

    public Reservation Reserve(OrderId id, int qty) => _stock.Hold(id, qty);
}

// ── Orders намагається зрадити межу ──
namespace Shop.Orders.Impl;

using Shop.Warehouse.Api;                        // ✅ фасад — можна
// using Shop.Warehouse.Impl;                    // ❌ CS0122:
//   "'WarehouseService' is inaccessible due to its protection level"
```
:::

Ось де живе межа в найчистішому вигляді: рядок з імпортом чужого класу **не компілюється**. Не «падає тест», не «сварить лінтер» — а взагалі не існує як програма. Сусід не може зробити помилку, якої мова не дає висловити.

> 🔧 **Навіщо це.** Це найдешевший з усіх сторожів, бо його не треба ні ставити, ні підтримувати — він у компіляторі. Ціна одна: дисципліна розкладки. Клади фасад в `api`, а все решта — в `internal`, і не піддавайся спокусі «зробити цей клас `public` на хвильку, щоб протестувати». Щойно один клас нутрощів став `public`, у стіні з'явилася дірка, крізь яку поповзе зчеплення, — і жоден зовнішній сторож уже не мусить її бачити.

Але одразу три обмеження, через які самою мовою не обійтися. Перше: package-private тримає межу **класів**, але нічого не знає про **таблиці** — ніщо в Java не заважає коду `orders` виконати `SELECT * FROM stock` рядковим запитом до чужої таблиці. Друге: заборона діє **в межах одного пакета**; варто комусь покласти новий клас у `shop.warehouse.internal` ззовні (пакет у Java «відкритий» — будь-хто може оголосити клас у ньому), і він отримає доступ до нутрощів. Третє й головне: у Python, TypeScript, Ruby цього рівня **просто немає** — там `export` відкриває символ усьому світу. Тому переходимо до сторожа, який дістає туди, куди мова не дотяглася.

## Рівень 2: сторож у конвеєрі — тест архітектури, що червоніє на порушенні

Ідея сторожа проста до нахабства: якщо межа — це правило про залежності, зробімо це правило **тестом**, який читає байт-код і перевіряє, хто на кого посилається. Порушив межу — тест червоний, збірка не проходить, гілка не зливається. Правило живе поряд із кодом, у тому самому репозиторії, і виконується щоразу.

Канонічний інструмент цього ешелону в світі Java — **ArchUnit**: бібліотека, яка формулює архітектурні правила звичайним JUnit-тестом. Ти пишеш правило майже людською мовою — «жоден клас, що не в `warehouse`, не має залежати від класів у `warehouse.internal`» — а ArchUnit сканує зібрані класи й перевіряє. Ось той самий інваріант межі у вигляді робочого тесту.

```java
// architecture/ModuleBoundaryTest.java — запускається як звичайний тест у CI
import com.tngtech.archunit.core.domain.JavaClasses;
import com.tngtech.archunit.core.importer.ClassFileImporter;
import com.tngtech.archunit.lang.ArchRule;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;

class ModuleBoundaryTest {

    // сканується один раз: усі класи застосунку
    private final JavaClasses app =
        new ClassFileImporter().importPackages("shop..");

    // ПРАВИЛО 1: нутрощі warehouse — приватні для всіх, крім самого warehouse
    @Test void warehouseInternalsAreHidden() {
        ArchRule rule = noClasses()
            .that().resideOutsideOfPackage("shop.warehouse..")
            .should().dependOnClassesThat().resideInAPackage("shop.warehouse.internal..")
            .because("ззовні дозволено лише фасад shop.warehouse.api");

        rule.check(app);   // ← кине AssertionError зі списком порушників
    }

    // ПРАВИЛО 2: напрям стрілки — orders може знати warehouse, але не навпаки
    @Test void warehouseDoesNotDependOnOrders() {
        ArchRule rule = noClasses()
            .that().resideInAPackage("shop.warehouse..")
            .should().dependOnClassesThat().resideInAPackage("shop.orders..")
            .because("склад нижче замовлень за потоком; зворотна стрілка = цикл");

        rule.check(app);
    }
}
```

Тепер найважливіше — **як це червоніє**. Хтось у `orders` пише `import shop.warehouse.internal.WarehouseServiceImpl;` (уявімо, що межу пакетів обійшли рефлексією або клас таки зробили `public`). Наступний прогін тесту дає не абстрактне «щось не так», а точний акт із місцем злочину:

```
java.lang.AssertionError: Architecture Violation [Priority: MEDIUM] -
Rule 'no classes that reside outside of package 'shop.warehouse..'
should depend on classes that reside in a package 'shop.warehouse.internal..',
because ззовні дозволено лише фасад shop.warehouse.api' was violated (1 times):
Class <shop.orders.internal.OrderService> depends on
  <shop.warehouse.internal.WarehouseServiceImpl>
  in (OrderService.java:14)
```

Рядок `OrderService.java:14`. Автор порушення бачить рівно, де і що, ще до рев'ю — бо збірка вже червона. Оце й є вся мета: перетворити «порушення межі» з теми для дискусії на **зламану збірку**, з якою нема про що дискутувати.

Що цей ешелон дістає такого, чого не дала мова. По-перше, він ловить **непрямі** залежності: якщо `orders` тягне `warehouse.internal` не напряму, а через третій клас-посередник, ArchUnit усе одно бачить ланцюг у графі й червоніє. По-друге — і це критично — ним можна стерегти **межу таблиць**, а не лише класів: правилом «жоден клас поза `warehouse` не має залежати від `StockTable`/`StockRepository`» (або на рівні пакета сховища) ти ловиш саме ту зраду, повз яку package-private проходить мовчки. Спільна база перестає бути дірою, бо доступ до чужого сховища тепер теж порушення архітектурного тесту.

> 🔧 **Навіщо це.** Сторож-fitness-function — головний ешелон саме тому, що він єдиний ловить **обидва** роди зради разом: і чужий клас, і чужу таблицю, і то навіть через посередників. Мова тримає лише клас і лише у своєму пакеті; лінт (нижче) читає текст імпортів, але не бачить непрямих шляхів. ArchUnit читає граф — тому саме він робить інваріант межі по-справжньому нездоланним. У світі Ruby ту саму роль грає `Packwerk` від Shopify: він розкладає застосунок на пакети, а `enforce_privacy: true` робить папку `app/public` єдиною видимою поверхнею — торкнувся приватного, дістав `Packwerk`-порушення на збірці. Механіка інша, ідея та сама: правило межі — це артефакт у репозиторії, який ламає конвеєр.

Ціна цього ешелону — його треба свідомо поставити: додати залежність, написати тест, увімкнути його в конвеєрі так, щоб падіння **блокувало** злиття (а не просто малювало жовте попередження, яке всі навчаються ігнорувати). Правило, яке не блокує, за пів року стає декоративним.

## Рівень 3: лінт імпортів — найдешевший сторож там, де мова відкрита

У TypeScript і Python компілятор чужий клас не сховає — `export`/публічне ім'я видно всім. Тут працює простіший, але дієвий сторож: лінтер читає **текст імпортів** і падає, коли шлях імпорту лізе у внутрішні файли чужого модуля повз його оголошені двері. Це слабше за граф ArchUnit (лінтер бачить лише прямі імпорти, не непрямі), зате дешеве, миттєве і ставиться в першу чергу.

Але лінт працює лише тоді, коли модуль має **одні двері**, повз які видно, що ти зайшов не туди. У TypeScript ці двері — **бар'єр `index.ts`**: єдиний файл, що реекспортує рівно фасад. Усе, що не пройшло через `index.ts`, — це імпорт із глибини, і саме його ловить правило `no-restricted-imports`.

```ts
// ── warehouse/index.ts — ЄДИНІ двері модуля ──
// сусіди повинні імпортувати ТІЛЬКИ звідси
export type { Reservation, OrderId } from "./types";
export { makeWarehouse } from "./service";   // фабрика фасаду
export type { Warehouse } from "./service";
// './stock-table' та './service' навмисне НЕ реекспортовані як внутрішні
```

```jsonc
// .eslintrc.json — правило: у warehouse дозволено входити лише через бар'єр
{
  "rules": {
    "no-restricted-imports": ["error", {
      "patterns": [{
        // будь-який шлях У ГЛИБИНУ warehouse, крім самого бар'єра
        "group": ["**/warehouse/*", "!**/warehouse", "!**/warehouse/index"],
        "message": "warehouse — приватний. Імпортуй лише з 'warehouse' (його index.ts)."
      }]
    }]
  }
}
```

Тепер спроба зайти з чорного ходу гасне на лінті, тобто на збірці:

```ts
// orders/order-service.ts
import { makeWarehouse } from "../warehouse";              // ✅ через бар'єр — ок
import { StockTable }   from "../warehouse/stock-table";   // ❌ ESLint: error
//  no-restricted-imports:
//  "warehouse — приватний. Імпортуй лише з 'warehouse' (його index.ts)."
```

Одна тонкість патерну, на якій спотикаються: у gitignore-стилі порядок і заперечення важать. `"**/warehouse/*"` забороняє всі шляхи в глибину, а два заперечення `"!**/warehouse"` і `"!**/warehouse/index"` **повертають** дозвіл на сам бар'єр — і заперечення мають стояти **після** забороняючого патерну, інакше вони не спрацюють. Тобто «все в глибину — не можна, крім самих дверей».

У Python цю саму роботу робить **`import-linter`** — окремий інструмент, що читає граф імпортів і перевіряє контракти. Двері модуля — його `__init__.py` (реекспорт фасаду), а контракт `forbidden` забороняє одним пакетам залежати від інших.

```python
# warehouse/__init__.py — двері: видно лише фасад
from ._service import Warehouse, make_warehouse
__all__ = ["Warehouse", "make_warehouse"]
# ._service, ._stock — приватні модулі (підкреслення), назовні не для імпорту
```

```ini
# .importlinter — контракт межі, перевіряється в CI командою `lint-imports`
[importlinter]
root_package = shop

[importlinter:contract:warehouse-internals]
name = Нутрощі warehouse приватні для решти застосунку
type = forbidden
# хто НЕ має права:
source_modules =
    shop.orders
    shop.billing
# на що НЕ має права дивитися:
forbidden_modules =
    shop.warehouse._service
    shop.warehouse._stock
```

Контракт `forbidden` перевіряє й **нащадків**, і **непрямі** імпорти: якщо `shop.orders` тягне `shop.warehouse._service` хоч через десять посередників, `import-linter` бачить шлях у графі й повертає ненульовий код виходу — конвеєр червоніє. Це вже ближче до сили ArchUnit, ніж проста текстова заборона ESLint, бо теж читає граф.

> 🔧 **Навіщо це.** Лінт імпортів — це компенсатор слабкості мови. У Java ти б поклався на package-private і навіть не писав би цього правила; у TypeScript і Python його доводиться дописувати руками, бо інакше `import` з будь-якої глибини цілком легальний. Головне тут — **бар'єр** (`index.ts` / `__init__.py`): без єдиних дверей лінту нема за що зачепитися, бо не видно, де «фасад», а де «глибина». Спершу зроби модулю одні двері — і лише тоді сторож стає можливим.

## Складність і пастки

Каркас працює рівно доти, доки живі дві дисципліни, які легко втратити тихо. Розберемо обидві — бо саме на них модульний моноліт найчастіше й розсипається назад у клубок, попри всі сторожі в коді.

### Пастка перша: спільна база — межа, яку сторож класів не бачить

Найпідступніше те, що можна мати ідеальні фасади в коді — package-private, ArchUnit, лінт усе зелене — і водночас клубок на рівні схеми. Причина: усі три сторожі за замовчуванням стережуть **залежності класів**, а таблиця — не клас. Якщо `orders` і `warehouse` ділять одну базу, ніщо в правилі про пакети не заважає коду замовлень виконати:

```sql
-- у надрах orders, «щоб швидше, без зайвого виклику»:
SELECT quantity FROM stock WHERE sku = ?     -- ← читаємо ЧУЖУ таблицю warehouse
```

Це порушення того самого інваріанта — вхід у модуль не крізь фасад, — але текстовий рядок SQL проходить повз сторожа класів непоміченим. І шкода тут гірша, ніж від імпорту класу: тепер схему `stock` не можна змінити, не зламавши `orders`, про існування якого власник складу навіть не знає. Дві таблиці зрослися намертво, і згодом їх не розчепити нізащо — саме спільна база, а не спільний процес, найчастіше й перетворює моноліт на невидимий клубок.

Лікується це двома взаємодоповнюваними ходами. Перший — **розвести схеми або хоча б володіння таблицями**: кожна таблиця належить рівно одному модулю, і на рівні бази прав доступу видно, що `orders` фізично не має `SELECT` на `stock`. Другий — **дотягнути сторожа до сховища**: правилом ArchUnit «жоден клас поза `warehouse` не залежить від `StockRepository`/пакета сховища складу» ти повертаєш межу таблиць під той самий червоний тест. Тоді єдиний шлях `orders` дізнатися залишок — знову `warehouse.reserve(...)` чи `warehouse.availableQty(...)`, тобто фасад.

> 🔧 **Навіщо це.** Правило «модуль — господар своїх таблиць» рівносильне правилу «модуль — господар своїх класів», просто про інший рід нутрощів. Якщо стерегти лише класи, лишається широчезна діра рівнем нижче — і саме в неї найчастіше й провалюється дисципліна, бо `SELECT` з чужої таблиці на вигляд невинніший за `import` чужого класу. Обов'язково закрий обидва входи, інакше зачинив двері, лишивши вікно навстіж.

### Пастка друга: сторож, який попереджає, але не блокує

Другий спосіб втратити межу тихо — залишити сторожа працювати, але **не давати йому валити збірку**. ArchUnit-тест, що позначений як «нестабільний» і пропускається; лінт-правило на рівні `warn`, а не `error`; крок CI, падіння якого не блокує злиття гілки. Кожне таке послаблення здається нешкідливим, і кожне перетворює сторожа на декорацію: попередження, які нічого не блокують, команда навчається не бачити за два тижні.

Наслідок завжди однаковий: список винятків, який тільки росте. Хтось додає «тимчасовий» дозвіл на одне порушення — і оскільки збірка все одно зелена, виняток лишається назавжди, а поряд заводяться нові. За пів року файл винятків довший за самі правила, і межа знову існує лише на діаграмі.

Тому інваріант конвеєра такий самий жорсткий, як інваріант межі: **порушення межі = червона збірка = гілка не зливається**. `no-restricted-imports` — тільки `error`. ArchUnit-тест — у тому самому наборі, що блокує злиття. `import-linter` — крок, ненульовий код якого валить конвеєр. Виняток, якщо вже без нього ніяк, — не тихий рядок ігнорування, а **явний, підписаний і датований** запис, який видно на рев'ю й до якого можна повернутися. Різниця між живою межею й мертвою — рівно в цьому: чи болить її порушення **зараз, автору, автоматично**, чи колись, комусь іншому, коли розчепити вже неможливо.

### Складність рівнів: скільки ешелонів ставити

Не кожному модулю потрібні всі три рівні — надлишок сторожів теж має ціну (їх треба підтримувати, вони гальмують конвеєр). Розумна межа затрат така. Якщо мова вміє ховати (Java, C#) — рівень 1 безкоштовний, став його завжди; він знімає більшість порушень ще на компіляції. Рівень 2 (ArchUnit / Packwerk) додавай там, де межа справді важлива й де треба стерегти **непрямі** залежності та **таблиці** — тобто для головних модулів предмету. Рівень 3 (лінт імпортів) — основний і часто єдиний ешелон у мовах без видимості (TypeScript, Python, Ruby); там він не додаток, а фундамент.

Спільний знаменник усіх трьох — **бар'єр як єдині двері**: `api`-пакет у Java, `index.ts` у TypeScript, `__init__.py` у Python, `app/public` у Packwerk. Без нього жоден сторож не має за що зачепитися, бо не видно, де фасад, а де глибина. Тому найперший крок, ще до будь-якого інструмента, завжди один: **дати кожному модулю рівно одні двері**. Далі сторож лише стежить, щоб крізь них і заходили.

## Заради чого межа: відв'язаний модуль виймається в сервіс майже механічно

Уся ця дисципліна окупається двічі. Перший раз — щодня, чистотою коду. Другий — того рідкісного дня, коли **саме цей** модуль справді має причину жити окремим сервісом: інший профіль навантаження, окрема команда-власник, свої вимоги до доступності. Тоді виявляється, що вимушена межа зробила виймання майже механічним — бо все спілкування з модулем уже й так ішло через одні двері.

Пройдімо це покроково на `warehouse`, який вирішили винести. Ключ у тому, що жоден зовнішній код не знає нутрощів складу — усі кличуть лише фасад `Warehouse`. Отже, змінюється **лише те, що ховається за фасадом**, а не жоден із викликачів.

Крок перший — переконатися, що фасад справді єдина точка входу. Це вже гарантовано сторожем: якби `orders` десь ліз у нутрощі складу повз `Warehouse`, збірка була б червона. Тобто рівень 2–3 ще й **готує ґрунт для виймання**, весь час підтримуючи модуль відв'язаним.

Крок другий — дати фасаду **другу реалізацію**, що ходить по мережі замість локального виклику. Інтерфейс той самий; змінюється тіло. Був локальний `WarehouseServiceImpl` — стає `WarehouseHttpClient`, який кличе виділений сервіс складу.

:::tabs
```ts
// БУЛО: локальна реалізація за бар'єром warehouse/index.ts
export const makeWarehouse = (s: StockTable): Warehouse =>
  new WarehouseService(s);

// СТАЛО: за тим самим бар'єром — клієнт до винесеного сервісу.
// Жоден імпортер 'warehouse' не змінюється: тип Warehouse той самий.
class WarehouseHttpClient implements Warehouse {
  constructor(private baseUrl: string) {}
  async reserve(id: OrderId, qty: number): Promise<Reservation> {
    const r = await fetch(`${this.baseUrl}/reserve`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId: id, qty }),
    });
    if (!r.ok) throw new WarehouseUnavailable(r.status);   // ← НОВЕ: мережа падає
    return (await r.json()) as Reservation;
  }
}
export const makeWarehouse = (base: string): Warehouse =>
  new WarehouseHttpClient(base);
```
```java
// БУЛО: фабрика повертала локальну реалізацію
public final class WarehouseFactory {
    public static Warehouse local(StockTable stock) {
        return new WarehouseServiceImpl(stock);
    }
}

// СТАЛО: та сама фабрика повертає клієнт до сервісу.
// Тип Warehouse не змінився — виклики orders лишаються дослівно ті самі.
public final class WarehouseHttpClient implements Warehouse {
    private final HttpClient http;
    private final URI base;

    public WarehouseHttpClient(HttpClient http, URI base) {
        this.http = http; this.base = base;
    }

    @Override public Reservation reserve(OrderId id, int qty) {
        HttpRequest req = HttpRequest.newBuilder()
            .uri(base.resolve("/reserve"))
            .POST(bodyOf(id, qty))
            .build();
        try {
            HttpResponse<String> res = http.send(req, ofString());
            if (res.statusCode() != 200)                   // ← НОВЕ: мережа падає
                throw new WarehouseUnavailable(res.statusCode());
            return parse(res.body());
        } catch (IOException | InterruptedException e) {
            throw new WarehouseUnavailable(e);             // таймаут, обрив
        }
    }
}
```
:::

Крок третій — **перевести дані**: таблиця `stock` переїжджає у власну базу нового сервісу. Оскільки (пастка перша!) ніхто, крім `warehouse`, до `stock` не звертався, переїзд не зачіпає чужого коду. Якби `orders` колись зробив той `SELECT` повз фасад — саме тут виймання б і застрягло, бо разом зі складом довелося б рвати й замовлення. Ось чому дисципліна таблиць окупається саме в цю мить.

Крок четвертий — **перемкнути трафік поступово**, а не рубанути одним релізом. Модуль обростають новим сервісом і переливають виклики частинами: спершу тінню (сервіс отримує копію запитів, відповідь ще бере локальна реалізація), потім малою часткою, потім усім. Стару локальну реалізацію лишають запасним варіантом, поки новий сервіс не доведе стабільність. Цей акуратний прийом — обрости стару межу новим і поступово задушити стару реалізацію — зветься [«фігове дерево» (strangler fig)](root:sf-apps/strangler-fig): назва від фікуса-душителя, що обплітає дерево-господаря й займає його місце, лишаючи всередині порожнечу у формі старого стовбура.

І ось де ховається справжня ціна рішення — вона не в механіці виймання, а в тому, що фасад **не приховує зміни семантики**. Був виклик функції: миттєвий, або результат, або виняток. Став мережевий: тепер він може зависнути на таймаут, обірватися посеред, відповісти із затримкою, вимагати повтору. Тип `Warehouse` не змінився, і в цьому пастка — код `orders` компілюється як був, але світ під ним інший. Тому в момент виймання неминуче з'являється **нова морока**, якої в моноліті не існувало: обробка `WarehouseUnavailable`, таймаути, повтори, часткові відмови, узгодженість між сервісами замість однієї транзакції бази. Уся [складність розподілених систем](root:sf-apps/microservices), від якої модульний моноліт беріг, вмикається рівно тут.

> 🔧 **Навіщо це.** Мораль каркаса вимушених меж повна саме в цій точці. Логічну межу проводь і стережи завжди — вона дешева й вона тримає код здоровим щодня. А фізичне рознесення по мережі бери **лише коли конкретний модуль має конкретну причину**, і бери свідомо: воно не «наступний рівень зрілості», а обмін дешевого виклику функції на дорогий мережевий разом з усією його мороком. Вимушена межа робить сам **перехід** майже механічним — але не робить дешевим **життя після нього**. Тому переважна більшість модулів так виокремленими ніколи й не будуть: вони чудово живуть за фасадом усередині одного процесу, і це для них не сходинка кудись, а кінцевий, правильний дім.
