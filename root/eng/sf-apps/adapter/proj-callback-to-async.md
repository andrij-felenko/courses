# ⚙️ Перехідник від колбека до async/await: перекласти не підпис, а час

<preknowlist>
- [async/await і проміси](root:sf-tasks/async-await) — що таке `Promise`, які в нього три стани (очікує, виконано, відхилено) і чому він осідає РІВНО раз; що `await` призупиняє функцію, доки проміс не розв'яжеться.
- [Ітератор](root:sf-apps/iterator) — протокол покрокового «дай наступне»; що таке асинхронний ітератор і цикл `for await … of` над ним.
- [Спостерігач](root:sf-apps/observer) — модель «джерело подій і підписані слухачі»; вузловий `EventEmitter` — саме вона, і кожен слухач тримає посилання на себе, доки його не знято.
</preknowlist>

Звичний перехідник підганяє **форму виклику**: інші імена, інші одиниці, інша обгортка аргументів. Але буває невідповідність підступніша, і в асинхронному коді вона трапляється чи не частіше за всі: два справні боки говорять про **той самий результат**, але **розкладають його в часі по-різному**. Стара бібліотека віддає результат тим, що **кличе тебе назад**: ти даєш їй функцію, вона виконає її, коли впорається. Твій сучасний код хоче `await` — написати рівний рядок `const x = await …` і дати рушієві самому призупинити функцію. Обидва способи правильні. Обидва описують «значення, якого ще нема». Але вилка не лізе в розетку: `await` вимагає проміс, а колбек — не проміс.

Переписати стару бібліотеку не можна: це `fs`, це SDK драйвера, це нативний аддон, це модуль зразка 2015 року, на якому все тримається. А тягнути колбекові піраміди в код, який в усьому іншому пласко-асинхронний, не хочеться. Тож між ними ставлять перехідник — але цей перехідник перекладає **керування в часі**, а не лише форму аргументів. Про це вся вставка: як провести успіх і помилку в `resolve`/`reject`, як протягнути скасування й таймаут крізь межу, як зняти слухачі, щоб нічого не текло, і — найглибший розкол — як зважити на те, що проміс осідає **раз**, а джерело подій сипле **багато разів**, тож одноразова операція просить проміс, а потік подій — асинхронний ітератор.

## Задача: два справні світи, що міряють час по-різному

Найконкретніше: у тебе є `fs.readFile(path, (err, data) => …)`. Колбек «помилка спершу» (*error-first*): перший аргумент — помилка (або `null`), другий — значення. А застосунок у тебе всюди `async`, і хочеться `const data = await readFile(path)`. Невідповідність тут **не** в тому, що функція зветься `readFile`, а не `read`. Вона в тому, що один бік віддає результат **через функцію, яку ти йому передав**, а другий хоче **проміс, на якому можна поставити паузу**.

Тепер розширмо. Іноді це не один результат, а **потік**: сокет, що сипле шматки `'data'`, а тоді каже `'end'`; спостерігач за файлом, що стукає без кінця; черга, з якої повідомлення течуть, доки її не закриють. Проміс такого не втримає: він осідає раз і застигає назавжди. Тому те саме бажання «стару подієву стару зробити сучасною async» насправді розколюється на **два різні перехідники**, і зрозуміти, який тобі потрібен, — половина справи.

Отже, крізь межу мусять перейти чотири різні речі, і кожну легко проґавити:

- **вихід** — успіх чи помилка;
- **кратність** — один результат чи багато;
- **скасування** — як перервати очікування ззовні;
- **прибирання** — як зняти за собою слухачі й таймери.

Ліворуч «світ колбеків», праворуч «світ async/await», між ними стрілки-перекладки по рядках: результат cb(null, value) → resolve(value); помилка cb(err) першим аргументом → reject(err)/throw; скільки разів 0…∞ викликів → рівно 1, проміс застигає; скасування власний прапорець → AbortSignal; прибирання removeListener вручну → finally/автозняття](img/time-translation.svg)

*Перехідник парадигми замикає кожен рядок таблиці окремо. Замкнеш лише «вихід» — і скасування, таймаут та прибирання «протечуть» крізь межу: очікування не перервати, слухач лишиться висіти, помилка загубиться.*

## Ідея: проміс — це колбек, вивернутий навиворіт

Уся хитрість в одному реченні: **виконавець** промісу (той колбек, що передається в `new Promise`) дає тобі дві функції — `resolve` і `reject`, — а це рівно форма error-first колбека, розрізаного на дві гілки. Тож перехідник — це: створити проміс, усередині його виконавця покликати стару функцію й спрямувати гілку успіху її колбека в `resolve`, а гілку помилки — у `reject`. Ніякої магії; є лиш перекладання одного роз'єму на інший, тільки цього разу роз'єм — це **спосіб віддати результат у часі**, а не набір параметрів.

Але глянь на таблицю ще раз: `resolve`/`reject` замикають лише перші два рядки. Замкнути треба всі. Проґавиш «кратність» — спробуєш утиснути потік в одноразовий проміс, і всі шматки після першого зникнуть. Проґавиш «скасування» — перерваний запит крутитиметься далі, марно тримаючи ресурси. Проґавиш «прибирання» — і кожен виклик лишатиме за собою висячий слухач. Перехідник підпису перекладає один рядок; перехідник парадигми чесний лише тоді, коли перекладе всі.

## Крок 1. Одноразова операція: обгорнути колбек у проміс

Почнімо з простого боку — операції, що дає **один** результат і завершується. Патерн тут загальний, живе однаково в Node і в Python-asyncio, тож покажу двома мовами:

:::tabs
```ts
import { readFile } from "node:fs";

// Adaptee: класичний err-first колбек
//   readFile(path, (err, data) => ...)
// Target: щось, що можна await-ити
function readFileAsync(path: string): Promise<Buffer> {
  return new Promise((resolve, reject) => {
    readFile(path, (err, data) => {
      if (err) reject(err);   // гілка помилки колбека → reject
      else resolve(data);     // гілка успіху → resolve
    });
  });
}

// стара функція тепер живе у світі await:
const data = await readFileAsync("./config.json");
```
```py
import asyncio

def read_file_async(path):
    loop = asyncio.get_running_loop()
    fut = loop.create_future()          # порожній «проміс»

    def on_done(err, data):             # старий колбек
        if err:
            fut.set_exception(err)      # → reject
        else:
            fut.set_result(data)        # → resolve

    legacy_read(path, on_done)          # чужа колбекова функція
    return fut                          # це awaitable

data = await read_file_async("./config.json")
```
:::

Різниця між мовами тут повчальна. У JS дві функції-виходи тобі **дають** — їх передає `new Promise`. У Python ти сам робиш порожнє майбутнє (`loop.create_future()`) і кличеш на ньому `set_result`/`set_exception`. Форма та сама: два боки одного колбека спрямовані в два методи одного майбутнього. Одна тонкість Python: майбутнє **не потоко-безпечне**, тож якщо чужий колбек стрельне з іншого потоку, замість прямого `set_result` треба `loop.call_soon_threadsafe(fut.set_result, data)` — інакше рушій asyncio зіпсується. У Node такої турботи нема, бо колбек так чи так виконається у [циклі подій](root:sf-tasks/event-loop) того самого потоку — не зараз, а на пізнішому оберті, коли поточний синхронний код добіжить.

Цей візерунок такий частий, що Node носить його готовим — `util.promisify` (з Node 8.0.0, 2017 рік):

```ts
import { promisify } from "node:util";
import { readFile } from "node:fs";

const readFileAsync = promisify(readFile);  // те саме, але для будь-яких аргументів
const data = await readFileAsync("./config.json");
```

Тільки він тримається угоди: функція мусить брати **error-first колбек останнім аргументом** і кликати його рівно як `(err)` чи `(err, value)`. API, що угоду ламають — колбек не останній, успіх повертається кількома значеннями, помилка не першою, — під `promisify` не лягають; для них є `util.promisify.custom` — символ, який чіпляють до функції, щоб вручну сказати, як її загортати. І перше, куди варто глянути: багато стандартних модулів уже возять проміс-версії (`node:fs/promises`, `node:dns/promises`), тож руками промисифікуй лише те, що справді старе чи чуже.

## Крок 2. Провести скасування й таймаут крізь межу

Ось де перехідник парадигми стає дорослим. Хай `await readFileAsync(path)` уже працює. А як його **скасувати**? Як обмежити п'ятьма секундами? Стара колбекова функція може взагалі не вміти скасовуватись — але ти все одно винен тому, хто кличе, спосіб **перестати чекати**, і винен рушієві не лишити сміття.

Сучасне скасування в JS — `AbortController`/`AbortSignal`. Той, хто кличе, передає `signal`; коли він робить `abort()`, твій проміс мусить `reject`. Це API Node/браузера, замкнене на себе, тож тут одна мова — TypeScript:

```ts
import { readFile } from "node:fs";

function readFileAsync(
  path: string,
  opts: { signal?: AbortSignal; timeoutMs?: number } = {},
): Promise<Buffer> {
  const { signal, timeoutMs } = opts;
  return new Promise<Buffer>((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);  // уже скасовано — навіть не починаємо

    let settled = false;

    const timer =
      timeoutMs != null
        ? setTimeout(() => finish(() => reject(new Error(`таймаут ${timeoutMs} мс`))), timeoutMs)
        : null;

    const onAbort = () => finish(() => reject(signal!.reason));
    signal?.addEventListener("abort", onAbort, { once: true });

    // ЄДИНА хвіртка виходу: перший результат виграє, решту глушимо, і ЗАВЖДИ прибираємо
    function finish(settle: () => void) {
      if (settled) return;                              // одноразовість — захист від подвійного виклику
      settled = true;
      if (timer) clearTimeout(timer);                   // прибрати таймер
      signal?.removeEventListener("abort", onAbort);    // зняти слухач — інакше витік
      settle();
    }

    readFile(path, (err, data) => {
      finish(() => (err ? reject(err) : resolve(data)));
    });
  });
}
```

Оця крихітна `finish` — серце всієї вставки. Вона робить три речі, які наївна обгортка забуває, і кожна з них — окремий рядок таблиці з малюнка:

1. **Одноразовість.** `settled` гарантує, що перший з-поміж {результат, таймаут, скасування} виграє, а решту тихо відкинуто. Так, проміс і сам ігнорує другий `resolve`/`reject` — але **прибирання** мусить статися рівно раз, а головне: якщо стара функція раптом покличе колбек двічі й зробить у ньому побічну роботу, то `settled` — твій єдиний захист від того, щоб зробити її двічі.
2. **Прибирання.** Хай яка гілка стрельне, `clearTimeout` і `removeEventListener` спрацюють. Забудеш `removeEventListener` — і кожен виклик лишить замикання `onAbort` висіти на сигналі (а той може жити довго): підручниковий витік слухача. Забудеш `clearTimeout` — і завершений завчасно проміс тримає живий таймер, відтягуючи вихід процесу й пізніше стріляючи мертвим `reject`, який лише тому й нешкідливий, що ти прикрив його через `settled`.
3. **Провести скасування.** `signal.reason` (те, що передали в `abort(reason)`, а без аргументу — це `DOMException` з іменем `AbortError`) стає причиною відхилення. Тож `try/catch` навколо `await` побачить чисте «скасовано», а не таймаут і не справжню помилку читання.

> 🔧 **Навіщо це.** Правило, яке робить перехідник парадигми надійним, коротке: **на кожну підписку — рівно одне гарантоване відписання**, і «гарантоване» означає в `finally` чи в одній спільній хвіртці `finish`, а не на щасливому шляху. Витік слухача не падає й не кричить одразу — він тихо росте, поки Node не почне сипати `MaxListenersExceededWarning: 11 listeners added`, а це вже не шум, це лічильник витоку. Асиметрія «підписався тут, а відписатися забув на он тому шляху» — джерело майже всіх витоків пам'яті на цій межі; симетрія її знімає.

Модерний і чистий спосіб таймауту — не крутити свій таймер, а **скомпонувати сигнали**:

```ts
const signal = AbortSignal.any([
  userSignal ?? new AbortController().signal,
  AbortSignal.timeout(5000),   // сам відхилиться через 5 с
]);
await readFileAsync(path, { signal });
```

`AbortSignal.timeout(ms)` (з Node 17) робить сигнал, що сам себе скасує за час; `AbortSignal.any([...])` (з Node 20) спрацьовує, щойно спрацює перший із кількох. Це згортає «таймаут» у «скасування» — один механізм, один шлях прибирання. Пересторога лишається та сама: композитний сигнал тримає слухачі на вхідних, тож не плоди їх у гарячому циклі.

## Крок 3. Потік подій — це не проміс

Тепер глибший бік. Проміс осідає **раз**. Джерело подій — `EventEmitter`, сокет, спостерігач за файлом — сипле **багато разів**. Промисифікувати потік **не можна**: перше `'data'` розв'язало б проміс і заморозило його, а кожен наступний шматок канув би в ту саму порожнечу «другий resolve — no-op». Правильна Ціль для «багато значень у часі» — **асинхронний ітератор**, який споживають через `for await … of`.

![Дві часові осі одна над одною. Угорі «одноразова операція»: точка «виклик», далі точка «результат — 1 раз», потім напис «далі застигло»; праворуч блок Promise<T> / await p. Унизу «потік подій»: чотири точки «подія» поспіль і точка «end»; праворуч блок AsyncIterable<T> / for await … of](img/oneshot-vs-stream.svg)

*Проміс розв'язується раз і застигає — тому одноразову операцію обгортаємо в нього. Потік триває, доки не скінчиться, — тому багаторазове джерело обгортаємо в асинхронний ітератор. Це не два стилі одного перехідника, а два різні перехідники під два різні виміри часу.*

Тож форма перехідника міняється: замість одного промісу ти будуєш об'єкт із `[Symbol.asyncIterator]`, і кожен `next()` повертає проміс **наступної** події. Складність тут — буферизація: події приходять незалежно від того, чи споживач уже попросив, тож потрібна невелика черга й спосіб **розбудити** `next()`, що чекає. Візерунок знов загальний, тож дві мови:

:::tabs
```ts
import { EventEmitter } from "node:events";

async function* streamToIterable<T>(
  src: EventEmitter,
  dataEvent = "data",
  endEvent = "end",
): AsyncGenerator<T> {
  const queue: T[] = [];
  let done = false;
  let failure: unknown = null;
  let wake: (() => void) | null = null;
  const bump = () => { wake?.(); wake = null; };

  const onData = (v: T) => { queue.push(v); bump(); };
  const onEnd = () => { done = true; bump(); };
  const onErr = (e: unknown) => { failure = e; done = true; bump(); };

  src.on(dataEvent, onData);
  src.once(endEvent, onEnd);
  src.once("error", onErr);       // 'error' БЕЗ слухача кладе процес — мусимо перехопити

  try {
    while (true) {
      while (queue.length) yield queue.shift()!;      // віддати все накопичене
      if (failure) throw failure;
      if (done) return;
      await new Promise<void>((r) => (wake = r));      // поспати до наступної події
    }
  } finally {
    src.off(dataEvent, onData);   // прибрати ВСІ слухачі —
    src.off(endEvent, onEnd);     // finally спрацює й на break споживача,
    src.off("error", onErr);      // і на throw в тілі, і на нормальний кінець
  }
}

// споживання читається як звичайний цикл:
for await (const chunk of streamToIterable<Buffer>(socket)) {
  handle(chunk);
  if (enough) break;   // ← generator.return() → спрацьовує finally → слухачі зняті
}
```
```py
import asyncio

async def stream_to_iter(src, data_event="data", end_event="end"):
    queue: asyncio.Queue = asyncio.Queue()
    _DONE = object()

    def on_data(v): queue.put_nowait(v)
    def on_end():   queue.put_nowait(_DONE)

    src.on(data_event, on_data)
    src.once(end_event, on_end)
    try:
        while True:
            item = await queue.get()      # поспати до наступної події
            if item is _DONE:
                return
            yield item
    finally:
        src.off(data_event, on_data)      # прибрати слухачі й на break, і на кінці
        src.off(end_event, on_end)

# споживання:
async for chunk in stream_to_iter(socket):
    handle(chunk)
    if enough:
        break
```
:::

Той `finally` — вузол безпеки проти витоку. Коли споживач робить `break` у `for await`, рушій кличе в генератора `.return()`, а той виконує `finally`, а той знімає всі слухачі. Без нього `break` (чи `throw` у тілі циклу) лишив би `onData` причепленим назавжди — класичний витік, що з'їдає пам'ять на кожному ранньому виході. Порівняй із Кроком 2: там симетрію тримала хвіртка `finish`, тут — блок `finally`; ідея одна, форма різна.

І знов: Node дає це готовим. `events.on(emitter, 'data')` (з Node 12.16) повертає рівно такий асинхронний ітератор і **сам знімає слухачі**, коли цикл виходить; а `events.once(emitter, 'end')` (з Node 11.13) — одноразова, проміс-подібна версія, що навіть приймає `{ signal }` (з Node 15), аби скасувати очікування. Тож у бойовому коді ти б часто писав просто:

```ts
import { on, once } from "node:events";

for await (const [chunk] of on(socket, "data")) {   // події віддаються МАСИВОМ аргументів
  handle(chunk);
}
```

(зверни увагу: `events.on` віддає масив аргументів події, бо подія може нести їх кілька). Тягнися до цих готових, перш ніж плести своє; своє — лише коли треба власна буферизація чи зліпити кілька подій докупи.

І чесна пастка на завершення Кроку — **зустрічний тиск** (*backpressure*). Ручна черга росте **без межі**, якщо продюсер сипле швидше, ніж споживач устигає `await`-ити. У подій нема вбудованої паузи; проміс чи ітератор не штовхають емітер назад. Для пожежного шланга або бери справжні Node-стріми (вони домовляються про тиск через `pause()`/`resume()` і `highWaterMark`), або обмеж чергу й став джерело на паузу, коли вона повна. Наївний перехідник на нескінченній черзі над швидким сокетом — це витік пам'яті, тільки в кілька рядків складніший.

## Складність і пастки

Три названі пастки цієї межі варто зібрати докупи — бо кожна тиха, і кожна вже майнула вище.

**Подвійний виклик колбека.** Деякі старі API кличуть твій колбек двічі: гілка помилки, що заразом заходить у гілку успіху; повтор, що стріляє обома. Загорнутий у проміс, другий `resolve` тихо відкидається — і це звучить безпечно, але це пастка: помилка стає **невидимою**, а будь-яка робота в тілі колбека поза `resolve` виконується двічі. Прапорець `settled` із Кроку 2 — і є той сторож: перевір його, відкинь другий виклик, і німий подвійний постріл перетвориться на кероване «раз».

**Загублені помилки.** Помилка зникає крізь цю межу трьома способами:

- **`throw` усередині колбека.** У `new Promise((res, rej) => { readFile(p, (err, d) => { if (err) throw err; … }) })` цей `throw` стається на пізнішому оберті циклу, **поза** виконавцем, тож проміс не відхиляється ніколи; ти дістаєш неперехоплений виняток (або й нічого). Усередині колбека — завжди `reject(err)`, ніколи `throw`.
- **`err` як значення.** Забудеш угоду «помилка спершу» й напишеш `resolve(err)` — помилка стане розв'язаним значенням, і `await` успішно поверне сміття.
- **Подія `'error'` без слухача.** У `EventEmitter` подія `'error'`, на яку ніхто не підписаний, не просто губиться — вона **перекидається виняткам і кладе процес**. Тому будь-який перехідник потоку мусить чіпляти слухач `'error'`, що йде в `reject` або кидає у ітератор, — як `onErr` у Кроці 3.

**Витік слухачів.** Кожен `addEventListener`/`.on` — це сильне посилання, яке джерело тримає, доки слухач не знято. В одноразовому перехіднику слухач `abort` переживе операцію, якщо не зняти його на шляху `finish`. У перехіднику потоку слухач `data` переживе цикл, якщо `finally` не зніме його на **кожному** виході — включно з `break` і `throw`. Прикмета — те саме попередження `MaxListenersExceededWarning`. Правило симетрії просте: скільки підписок, стільки й гарантованих відписань.

І чесна ціна наприкінці. Перехідник парадигми — це більше, ніж перекладання імен: він володіє **часом**. Він буферизує, він планує прибирання, він вирішує, хто виграє перегони «результат проти таймауту проти скасування». Це справжня логіка, і її легко тихо зіпсувати — саме тому першими бери стандартні інструменти (`node:fs/promises`, `util.promisify`, `events.on`/`events.once`, `AbortSignal.any`), а свій перехідник пиши лише там, де готового нема. А коли мусиш — дисципліна мала й незмінна: проведи обидва виходи, обери одну кратність, протягни сигнал і відпишися в `finally`. Замкни кожен рядок таблиці — і світ колбеків та світ async клацнуть докупи, як вилка в розетку, тільки цього разу через сам час.
