# ⚙️ Від знекровленого мішка до багатої моделі: рефакторинг поліса крок за кроком

Є код, який працює, проходить тести й щодня заводить нові поліси — і водночас повільно труїть проєкт. Знаєш його з першого погляду: клас `Policy` із десятком публічних полів, поруч `PolicyService` на пів тисячі рядків, а між ними — правило, яке має бути одне, розсипане по трьох різних сервісах. Формально все гаразд: об'єкт названий іменем предмета, поля мають слушні типи, сервіс щось перевіряє. Насправді об'єкт нічого про себе не гарантує, і будь-хто будь-звідки може привести поліс у стан, якого в природі не буває.

Ця вставка — про те, як за кілька акуратних кроків перетворити такий мішок на **багату модель**, яка сама стереже власну коректність, і зробити це на живому коді, не переписуючи все з нуля. Приклад — страховий поліс: у нього є життєвий цикл (чернетка → діє → пільговий період → скасовано), премія, дата платежу й список платежів. Ми пройдемо шлях цілком: спершу подивимося, як виглядає знекровлений варіант і чому він тихо небезпечний; тоді крок за кроком закриємо поля, перенесемо інваріант із сервісу в об'єкт, зробимо єдині двері через метод, виділимо суму в об'єкт-значення й накриємо все коренем агрегату; а наприкінці розберемо, як після цього некоректний стан стає **недосяжним**, як таку модель тестувати й на яких пастках ламаються найчастіше.

Код усюди — справжній TypeScript і Python, бо доменне моделювання лягає на обидві мови ідіоматично, і поруч видно, що суть не в синтаксисі, а в тому, **кому належить правило**. C++ тут навмисно не беремо: доменна модель зі станами й винятками пишеться на ньому важче, а нічого специфічно машинного (регістрів, розкладок пам'яті) у задачі немає, тож дві мови стеку показують ідею чистіше.

## Задача: знекровлений поліс і сервіс-правило

Ось точка старту — так це виглядає в реальному коді, який «просто працює». Поліс — плаский носій даних: усі поля публічні, жодного правила всередині. А правила живуть окремо, у `PolicyService`.

:::tabs
```ts
// Знекровлена модель: сам поліс нічого не вміє, лише тримає поля навстіж
class Policy {
  id: string = "";
  status: string = "draft";        // "draft" | "active" | "grace" | "cancelled"
  premium: number = 0;             // сума внеску, у копійках? у гривнях? хтозна
  currency: string = "UAH";
  dueDate: Date = new Date();
  payments: number[] = [];         // суми платежів, теж голі числа
}

// Правило живе ЗЗОВНІ, у сервісі — і кожен викликач тримає свій уламок
class PolicyService {
  activate(p: Policy): void {
    if (p.status !== "draft") throw new Error("wrong state");
    p.status = "active";
  }

  enterGracePeriod(p: Policy): void {
    // тут ЗАБУЛИ перевірити, що поліс узагалі активний
    p.status = "grace";
  }

  addPayment(p: Policy, amount: number): void {
    p.payments.push(amount);        // жодної перевірки: додасться й від'ємне
  }
}
```
```python
# Знекровлена модель: сам поліс нічого не вміє, лише тримає поля навстіж
class Policy:
    def __init__(self):
        self.id = ""
        self.status = "draft"        # "draft" | "active" | "grace" | "cancelled"
        self.premium = 0             # сума внеску, у копійках? у гривнях? хтозна
        self.currency = "UAH"
        self.due_date = None
        self.payments = []           # суми платежів, теж голі числа


# Правило живе ЗЗОВНІ, у сервісі — і кожен викликач тримає свій уламок
class PolicyService:
    def activate(self, p):
        if p.status != "draft":
            raise ValueError("wrong state")
        p.status = "active"

    def enter_grace_period(self, p):
        # тут ЗАБУЛИ перевірити, що поліс узагалі активний
        p.status = "grace"

    def add_payment(self, p, amount):
        p.payments.append(amount)    # жодної перевірки: додасться й від'ємне
```
:::

Придивись, і хвороба вилазить сама — і вона не про естетику. Правило «увійти в пільговий період можна лише з активного» — це правило самого поліса, частина його природи. Але тут його просто **немає**: `enterGracePeriod` бере будь-який поліс і ставить `"grace"`, бо автор цього методу не тримав у голові весь життєвий цикл і забув перевірку. Правило «внесок не буває від'ємним» теж загубилося. Кожен викликач тримає власний уламок спільного закону, і разом ці уламки не складаються в цілісність.

Наслідок не теоретичний. Ось що цей код цілком дозволяє:

:::tabs
```ts
const p = new Policy();
p.status = "cancelled";            // будь-хто вписує будь-що напряму
p.premium = -5000;                 // від'ємна премія — чому б ні
p.payments.push(-200);             // від'ємний платіж просто додається
new PolicyService().enterGracePeriod(p);  // "cancelled" -> "grace": воскресили скасоване
// поліс тепер у стані, якого не існує в природі
```
```python
p = Policy()
p.status = "cancelled"             # будь-хто вписує будь-що напряму
p.premium = -5000                  # від'ємна премія — чому б ні
p.payments.append(-200)            # від'ємний платіж просто додається
PolicyService().enter_grace_period(p)   # "cancelled" -> "grace": воскресили скасоване
# поліс тепер у стані, якого не існує в природі
```
:::

Об'єкт не володіє власним станом. Стіни немає взагалі: поля публічні, зайти в них можна будь-звідки, зокрема неможливим значенням. Поліс не гарантує про себе нічого — гарантії, якщо вони десь і є, розкидані по викликачах, і кожен новий викликач може або повторити перевірку (дублювання), або, як `enterGracePeriod`, її забути (діра). А тепер уяви найзвичайнішу зміну вимог: доти, доки не сплачено перший внесок, поліс не може стати активним. Скільки місць доведеться відшукати? Усі, де хтось торкається `status`. Це і є калюжа, у яку розтеклося бізнес-правило.

> 🔧 **Навіщо це.** Знекровлена модель небезпечна саме тим, що виглядає невинно й проходить тести на щасливому шляху. Поламається вона тоді, коли якийсь новий викликач забуде перевірку, або коли правило зміниться й один із десятка розкиданих `if` лишиться старим. Найдорожчі баги — не там, де код робить не те, що написано, а там, де він робить рівно те, що написано, але правило було розсипане й одну його копію проґавили. Рефакторинг у багату модель прибирає цей клас помилок у корені: правилу просто нема де розсипатися, бо воно одне й живе в об'єкті.

Історична примітка, щоб бачити межу термінів. Саму назву «знекровлена доменна модель» (англ. *anemic domain model*) увів і розкритикував як анти-патерн Мартін Фаулер (Martin Fowler) 25 листопада 2003 року на своєму блозі, у нотатці «AnemicDomainModel»; його формула — об'єкти, які «навряд чи мають хоч якусь поведінку, лишаючись трохи більше ніж мішками геттерів і сеттерів». Протилежну ідею — **багату модель**, де поведінка живе разом із даними, — Фаулер прямо пов'язує з роботою Еріка Еванса (Eric Evans) над DDD того ж року й зазначає, що спостерігав поширеність анти-патерну спільно з Евансом. Тобто «знекровлена» — термін Фаулера, «багата» виростає з ядра DDD Еванса. *(Статус: усталено — за первинним джерелом, нотаткою Фаулера, і датою її публікації.)*

## Ідея: закривати поле по полю, аж поки некоректний стан стане недосяжним

Рятунок — не «переписати начисто», а низка дрібних, безпечних кроків, кожен з яких закриває одну конкретну діру, лишаючи код робочим після кожного. Порядок тут не випадковий: він іде від найдешевшого й найбезпечнішого до глибшого, і кожен наступний крок спирається на попередній.

![Драбина з п'яти кроків, що піднімається зліва направо: 1 закрити поля, 2 внести інваріант, 3 єдині двері, 4 об'єкт-значення, 5 корінь агрегату; нижні два кроки підписані синім як «прибирають діри», верхні три зеленим як «роблять некоректний стан недосяжним»; стрілки ведуть від кроку до кроку вгору](img/refactor-ladder.svg)

*Рефакторинг — це сходи, а не стрибок. Нижні щаблі прибирають найгрубші діри (відкриті поля, розсипане правило); вищі роблять цілі класи некоректних станів невиразними. Після кожного щабля код робочий — можна зупинитися, якщо далі не окуповується.*

Ключове слово всього шляху — **інваріант**: твердження, яке об'єкт обіцяє тримати істинним **завжди**, у будь-який момент свого життя. Для нашого поліса інваріантів кілька: він завжди в одному з чотирьох законних станів; між станами ведуть лише дозволені переходи; премія невід'ємна; сума платежів не перевищує премії. Поки поля відкриті, а правила зовні, тримати ці інваріанти не може ніхто — об'єкт не контролює власні двері. Уся робота рефакторингу — послідовно передати кожен інваріант під охорону єдиного сторожа, самого об'єкта.

Розберемо межу того, що робимо, чесно: ми **не додаємо нових можливостей** і **не міняємо поведінку щасливого шляху**. Поліс, який і раніше правильно активувався й приймав платежі, робитиме те саме. Змінюється лише одне: те, що раніше було **можливо** зробити неправильно, стане **неможливо**. Це і є суть — звузити множину досяжних станів до самих законних.

## Крок 1: закрити поля

Найдешевший і найбезпечніший крок — прибрати пряму дорогу до полів. Поки `p.status = "cancelled"` компілюється, будь-яка подальша логіка марна: її завжди можна оминути. Тож першим ділом робимо поля приватними, а замість голих сеттерів лишаємо тільки те, що справді потрібно зовні, — переважно читання.

:::tabs
```ts
class Policy {
  // поля закриті: ззовні до них уже не дотягтися напряму
  private _status = "draft";
  private _premium = 0;
  private _payments: number[] = [];

  constructor(
    private readonly _id: string,
    private readonly _currency: string,
    private readonly _dueDate: Date,
  ) {}

  // назовні — лише читання того, що справді потрібне іншим шарам
  get id(): string { return this._id; }
  get status(): string { return this._status; }
  get premium(): number { return this._premium; }
  // ЖОДНОГО set status / set premium: змінити стан ззовні вже не можна
}
```
```python
class Policy:
    def __init__(self, policy_id: str, currency: str, due_date):
        # поля закриті угодою про підкреслення; міняти ззовні — зась
        self._id = policy_id
        self._currency = currency
        self._due_date = due_date
        self._status = "draft"
        self._premium = 0
        self._payments = []

    # назовні — лише читання того, що справді потрібне іншим шарам
    @property
    def id(self) -> str:
        return self._id

    @property
    def status(self) -> str:
        return self._status

    @property
    def premium(self) -> int:
        return self._premium
    # ЖОДНОГО сеттера на status / premium: змінити стан ззовні вже не можна
```
:::

Помітно, що вже цей крок відрізає найгрубшу діру: `p._status = "cancelled"` більше не пройде через звичайний код (у TypeScript це не скомпілюється, у Python `_status` — угода «не чіпай ззовні», яку поважають і люди, і лінтери). Але сам собою крок 1 неповний: поля закриті, а от **правила ще нема** — поліс поки що просто не вміє змінюватися взагалі. Наступний крок дає йому легальні двері з вартовим усередині.

Зверни увагу й на дрібницю, що вже тут зникла: у знекровленому варіанті `id`, `currency` і `dueDate` міг перезаписати будь-хто будь-коли. Ми оголосили їх `readonly` (TS) / поставили лише геттер (Python) — це вже маленький інваріант «особу поліса й валюту не змінюють після створення», який раніше ніхто не тримав.

## Крок 2: внести інваріант із сервісу в об'єкт

Тепер найважливіший перенос. Правило переходу стану — це рішення про власний стан поліса, отже, його місце **всередині** поліса. Беремо логіку з `PolicyService.activate` і `enterGracePeriod` і переселяємо її в методи самого об'єкта, разом із перевіркою, якої раніше бракувало.

Замість голого рядка `status` заведімо перелік (англ. *enum* — тип із фіксованого списку значень): тоді сам тип не дасть з'явитися стану на кшталт `"banana"`, бо поза списком значень просто не існує. Це вже споріднена ідея — [зробити неможливий стан невиразним самим типом](root:sf-apps/type-driven-design); тут вона працює пліч-о-пліч із нашим переносом.

:::tabs
```ts
enum PolicyStatus { Draft, Active, Grace, Cancelled }

class DomainError extends Error {}   // окремий тип — щоб ловити саме порушення правила

class Policy {
  private _status = PolicyStatus.Draft;
  private _premium = 0;
  private _payments: number[] = [];

  constructor(
    private readonly _id: string,
    private readonly _currency: string,
    private readonly _dueDate: Date,
  ) {}

  // КОМАНДА: правило переходу тепер ТУТ, разом зі своїм вартовим
  activate(): void {
    if (this._status !== PolicyStatus.Draft)
      throw new DomainError("активувати можна лише чернетку");
    this._status = PolicyStatus.Active;
  }

  enterGracePeriod(): void {
    if (this._status !== PolicyStatus.Active)      // ← перевірка, якої бракувало
      throw new DomainError("у пільговий період входять лише з активного");
    this._status = PolicyStatus.Grace;
  }

  get status(): PolicyStatus { return this._status; }
}
```
```python
from enum import Enum, auto


class PolicyStatus(Enum):
    DRAFT = auto()
    ACTIVE = auto()
    GRACE = auto()
    CANCELLED = auto()


class DomainError(Exception):
    """Порушення доменного правила поліса."""


class Policy:
    def __init__(self, policy_id, currency, due_date):
        self._id = policy_id
        self._currency = currency
        self._due_date = due_date
        self._status = PolicyStatus.DRAFT
        self._premium = 0
        self._payments = []

    # КОМАНДА: правило переходу тепер ТУТ, разом зі своїм вартовим
    def activate(self) -> None:
        if self._status is not PolicyStatus.DRAFT:
            raise DomainError("активувати можна лише чернетку")
        self._status = PolicyStatus.ACTIVE

    def enter_grace_period(self) -> None:
        if self._status is not PolicyStatus.ACTIVE:      # ← перевірка, якої бракувало
            raise DomainError("у пільговий період входять лише з активного")
        self._status = PolicyStatus.GRACE

    @property
    def status(self) -> PolicyStatus:
        return self._status
```
:::

Дивись, що сталося з тим самим сценарієм, який раніше воскрешав скасований поліс. Тепер `enterGracePeriod` **фізично не може** відпрацювати не з активного стану: вартовий кине `DomainError` у тому ж рядку, де правило порушили. Автор складського чи іншого шару більше не може забути перевірку — вона вбудована в метод, і забути її можна хіба що переписавши сам `Policy`. Правило зібралося з трьох розкиданих уламків в одне місце, назване мовою предмета.

`PolicyService` після цього худне на очах: із нього зникає вся арифметика станів, а лишається хіба оркестрація — дістати поліс зі сховища, сказати йому `activate()`, зберегти. Це нормальний, «тонкий» сервіс-застосунку, що диригує, а не грає; про те, як такий сценарій правильно збирати з транзакцією й портами, є окрема робота на прикладі замовлення — [сценарій-сервіс placeOrder](root:sf-apps/service-layer/proj-place-order-service.md). Тут важливо, що **доменне правило туди більше не належить**.

> 🔧 **Навіщо це.** Різниця «до/після» — це різниця в тому, скільки коду тримає одне бізнес-правило. Поки правило переходів розмазане по викликачах, кожна його зміна — полювання по всьому проєкту з ризиком щось проґавити, а кожен новий викликач — потенційна нова діра. Коли правило зібране в об'єкті, який ним володіє, зміна лягає в одне місце, а привести поліс у неможливий стан ззовні просто нема як. Ти платиш за це трохи більшим об'єктом — і купуєш гарантію, якої раніше не давав ніхто.

## Крок 3: єдині двері через метод

Крок 2 переніс переходи всередину, але лишив тонку щілину, яку легко проґавити. Придивися до платежів: `_payments` — приватне поле, але якщо десь є геттер, що повертає **сам масив**, викликач дістане до нього й додасть від'ємне число в обхід будь-якої перевірки. Приватність поля нічого не варта, якщо назовні тече **посилання на його змінний нутрощ**.

Тому крок 3 — це принцип **єдиних дверей**: усередину агрегату дані заходять і змінюються **лише** через методи-команди, а назовні витікає тільки те, що читач не може зіпсувати. Заведімо команду `addPayment` з повним вартовим і зробімо так, щоб список платежів **не витікав** назовні у вигляді, який можна змінити.

:::tabs
```ts
class Policy {
  private _status = PolicyStatus.Draft;
  private _premium = 0;
  private _payments: number[] = [];
  /* ...конструктор і переходи стану, як у кроці 2... */

  // ЄДИНІ ДВЕРІ для платежу: сюди зайти можна лише правильним значенням
  addPayment(amount: number): void {
    if (this._status !== PolicyStatus.Active && this._status !== PolicyStatus.Grace)
      throw new DomainError("платіж приймають лише за чинним полісом");
    if (amount <= 0)
      throw new DomainError("платіж має бути додатним");
    if (this.paidTotal() + amount > this._premium)
      throw new DomainError("сума платежів не може перевищити премію");
    this._payments.push(amount);
  }

  paidTotal(): number {
    return this._payments.reduce((s, x) => s + x, 0);
  }

  // назовні — КОПІЯ, а не сам масив: читач не дотягнеться до нутрощів
  get payments(): readonly number[] {
    return [...this._payments];
  }
}
```
```python
class Policy:
    # ...конструктор і переходи стану, як у кроці 2...

    # ЄДИНІ ДВЕРІ для платежу: сюди зайти можна лише правильним значенням
    def add_payment(self, amount: int) -> None:

            raise DomainError("платіж приймають лише за чинним полісом")
        if amount <= 0:
            raise DomainError("платіж має бути додатним")
        if self.paid_total() + amount > self._premium:
            raise DomainError("сума платежів не може перевищити премію")
        self._payments.append(amount)

    def paid_total(self) -> int:
        return sum(self._payments)

    # назовні — КОПІЯ, а не сам список: читач не дотягнеться до нутрощів
    @property
    def payments(self) -> tuple:
        return tuple(self._payments)
```
:::

Тут два тонкі місця, кожне з яких — окремий інваріант під охороною. Перше: `addPayment` не просто додає число, а перевіряє **три** умови разом — поліс чинний, сума додатна, і платежі не перебирають премії. Друге, підступніше: геттер `payments` повертає **копію** (`[...]` у TS, `tuple(...)` у Python), а не внутрішній масив. Якби він віддавав сам `_payments`, уся охорона `addPayment` розліталася б — викликач писав би `policy.payments.push(-999)` і клав би що завгодно повз двері. Читання назовні мусить бути **безпечним для нутрощів**: або незмінна копія, або незмінний тип. Це прямий вияв ідеї [«кажи, не питай»](root:sf-apps/tell-dont-ask): не витягуй у поліса змінний список, щоб самому щось із ним зробити, — **скажи** полісу прийняти платіж, а перевірку лиши йому.

> 🔧 **Навіщо це.** Єдині двері — це те, що перетворює «поля начебто приватні» на справжню гарантію. Найчастіша прихована діра багатої моделі — саме витік змінного нутра через геттер: об'єкт стереже свої команди, але наївно віддає назовні власний список чи мапу, і вся охорона знецінюється одним `.push()` ззовні. Правило просте: **усередину — лише через команди; назовні — лише незмінне**. Тоді множина способів змінити об'єкт звужується рівно до тих дверей, які ти сам відчинив і поставив на них вартового.

## Крок 4: суму — в об'єкт-значення

Тепер приберемо ваду, яку легко не помітити за станами: **гроші в нас — голе число**. `premium: number`, `amount: number`, `payments: number[]`. А голе число нічого не знає про себе: у ньому копійки чи гривні? якої валюти? Ніщо не заважає скласти гривневу премію з доларовим платежем — типи однакові, компілятор мовчить, а результат — тихе сміття. І кожна перевірка «сума додатна», «валюти збігаються» доведеться писати щоразу заново там, де торкаються грошей.

Ліки — **об'єкт-значення (англ. *value object*)**: маленький незмінний тип, який визначається **своїм значенням**, а не особою (два записи по 100 грн — це одні й ті самі гроші, їх не треба розрізняти за «ідентичністю»), і який сам стереже власні правила. Заведімо `Money` — суму разом із валютою, що з народження не буває від'ємною й відмовляється складатися з чужою валютою.

:::tabs
```ts
// Об'єкт-значення: незмінний, самоперевірний, порівнюється за значенням
class Money {
  private constructor(
    readonly cents: number,        // тримаємо в копійках — жодних дробових гривень
    readonly currency: string,
  ) {}

  static of(amount: number, currency: string): Money {
    if (!Number.isInteger(amount) || amount < 0)
      throw new DomainError("сума має бути невід'ємним цілим числом копійок");
    return new Money(amount, currency);
  }

  static zero(currency: string): Money { return new Money(0, currency); }

  plus(other: Money): Money {
    this.sameCurrency(other);
    return new Money(this.cents + other.cents, this.currency);
  }

  isGreaterThan(other: Money): boolean {
    this.sameCurrency(other);
    return this.cents > other.cents;
  }

  private sameCurrency(other: Money): void {
    if (this.currency !== other.currency)
      throw new DomainError(`не складаються різні валюти: ${this.currency} і ${other.currency}`);
  }
}
```
```python
from dataclasses import dataclass


@dataclass(frozen=True)   # frozen -> незмінний і порівнюється за значенням "з коробки"
class Money:
    cents: int            # тримаємо в копійках — жодних дробових гривень
    currency: str

    @staticmethod
    def of(amount: int, currency: str) -> "Money":
        if not isinstance(amount, int) or amount < 0:
            raise DomainError("сума має бути невід'ємним цілим числом копійок")
        return Money(amount, currency)

    @staticmethod
    def zero(currency: str) -> "Money":
        return Money(0, currency)

    def plus(self, other: "Money") -> "Money":
        self._same_currency(other)
        return Money(self.cents + other.cents, self.currency)

    def is_greater_than(self, other: "Money") -> bool:
        self._same_currency(other)
        return self.cents > other.cents

    def _same_currency(self, other: "Money") -> None:
        if self.currency != other.currency:
            raise DomainError(f"не складаються різні валюти: {self.currency} і {other.currency}")
```
:::

Три речі, які `Money` дає задарма щоразу, коли він з'являється у сигнатурі. По-перше, **валюта їде разом із сумою**, тож скласти гривні з доларами вже не вийде — `plus` кине `DomainError` замість тихо повернути безглузде число. По-друге, **від'ємних грошей не буває взагалі**: єдині двері до створення — `Money.of`, а вона відкидає від'ємне на вході, отже, жоден `Money` у системі не може бути від'ємним, і перевіряти це в кожному методі вже не треба. По-третє, **незмінність** (`readonly` / `frozen=True`) означає, що `Money` можна вільно передавати, класти в поля й повертати назовні без страху — його ніхто не зіпсує, бо змінити його неможливо, будь-яка операція народжує **новий** `Money`. Про те, чому незмінні типи так спрощують міркування, є окрема тема — [незмінність](root:sf-apps/immutability); тут вона працює як фундамент об'єкта-значення.

Тепер `Policy` починає говорити грошима замість чисел, і половина ручних перевірок зникає, бо переїхала в `Money`:

:::tabs
```ts
class Policy {
  private _premium: Money;
  private _payments: Money[] = [];
  /* ...інше, як раніше... */

  constructor(id: string, dueDate: Date, premium: Money) {
    this._id = id;
    this._dueDate = dueDate;
    this._premium = premium;         // валюта поліса задана раз, тут
  }

  addPayment(amount: Money): void {
    if (this._status !== PolicyStatus.Active && this._status !== PolicyStatus.Grace)
      throw new DomainError("платіж приймають лише за чинним полісом");
    // «додатність» і «та сама валюта» вже гарантує сам Money — тут не дублюємо
    const afterPay = this.paidTotal().plus(amount);      // кине, якщо валюти різні
    if (afterPay.isGreaterThan(this._premium))
      throw new DomainError("сума платежів не може перевищити премію");
    this._payments.push(amount);
  }

  paidTotal(): Money {
    return this._payments.reduce((s, m) => s.plus(m), Money.zero(this._premium.currency));
  }
}
```
```python
class Policy:
    # ...інше, як раніше...

    def __init__(self, policy_id, due_date, premium: Money):
        self._id = policy_id
        self._due_date = due_date
        self._premium = premium          # валюта поліса задана раз, тут
        self._status = PolicyStatus.DRAFT
        self._payments: list[Money] = []

            raise DomainError("платіж приймають лише за чинним полісом")

        after_pay = self.paid_total().plus(amount)       # кине, якщо валюти різні
        if after_pay.is_greater_than(self._premium):
            raise DomainError("сума платежів не може перевищити премію")
        self._payments.append(amount)

        total = Money.zero(self._premium.currency)
        for m in self._payments:
```

:::

Поглянь, як покращала `addPayment`: перевірок стало менше, а гарантій — більше. Ми більше **не перевіряємо** тут ні додатність суми, ні збіг валют — це неможливо порушити, бо `Money` таким не буває й `plus` сам відмовить чужій валюті. Лишилися тільки перевірки, що справді належать **полісу**: чинний стан і межа премії. Кожен інваріант живе там, де йому місце: правила грошей — у `Money`, правила поліса — у `Policy`. Це і є поділ праці, який дає багата модель, — не одна велетенська перевірка, а сторожа, розставлена по своїх дверях.

## Крок 5: корінь агрегату

Останній крок піднімає гарантію на рівень вище. Дотепер ми стерегли **один** об'єкт. Але поліс рідко живе сам: у нього є платежі, у замовлення — позиції, у рахунку — проводки. І тут виникає питання, на яке DDD дає напрочуд практичну відповідь: **де межа шматка, який мусить бути узгоджений завжди-завжди, як одне ціле?**

Такий шматок звуть **агрегатом**, а його головний об'єкт, через який тільки й можна зайти всередину, — **коренем агрегату (aggregate root)**. У нашому випадку поліс і його платежі — один агрегат: інваріант «сума платежів не перевищує премії» має бути істинним **завжди**, ні на мить не розходячись. Отже, платіж не можна додати в обхід поліса — інакше сума на мить розійдеться з премією. `Policy` — корінь; список платежів — його внутрішня частина, до якої зовнішній світ дотягується **лише** через корінь.

![Велика зелена рамка «Агрегат Поліс» охоплює корінь Policy з закритими полями status, premium, payments і методами addPayment, enterGracePeriod, всередині яких тримається інваріант; праворуч три внутрішні частини Payment, до кожної веде стрілка від кореня; ззовні червона перекреслена пунктирна стрілка намагається дотягтися прямо до Payment в обхід кореня й упирається в «зась»](img/aggregate-door.svg)

*Межа агрегату — це межа того, що мусить бути істинним разом. Зовнішній код тримає посилання лише на корінь і всі зміни робить через нього; до внутрішніх платежів напряму не дотягується. Тому інваріант «сума платежів ≤ премія» тримається в одному місці — у команді кореня — і не може розійтися.*

Здебільшого крок 5 не потребує нового коду — він потребує **дисципліни доступу**. Наш `Policy` уже став коренем на кроці 3, щойно ми закрили `_payments` і зробили `addPayment` єдиними дверима. Лишається зафіксувати два правила, які роблять із нього справжній корінь:

- **Зовнішній світ тримає посилання тільки на корінь.** Ніхто ззовні не зберігає окремий `Payment` і не змінює його поза полісом. Хочеш додати платіж — клич `policy.addPayment(...)`, а не колупай масив.
- **Агрегат зберігають і вантажать цілком.** Сховище повертає `Policy` разом із його платежами й записує їх однією транзакцією. Це важливо не лише для охайності: межа агрегату — заразом **межа узгодженості при збереженні**. Агрегат лягає в базу як одне ціле, тож інваріант «сума ≤ премія» ніколи не застає систему в напівстані, де премію вже змінили, а платежі — ще ні.

Ось як виглядає межа в коді, коли платіж стає власною внутрішньою частиною (об'єктом-значенням із датою), а корінь лишається єдиними дверима:

:::tabs
```ts
// Внутрішня частина агрегату — теж незмінна, живе лише всередині поліса
class Payment {
  constructor(readonly amount: Money, readonly at: Date) {}
}

class Policy {                       // ← корінь агрегату
  private _payments: Payment[] = []; // внутрішня частина — закрита
  /* ...стан, премія, переходи — як раніше... */

  // єдині двері: платіж додають ЛИШЕ через корінь, і тут тримається інваріант
  addPayment(amount: Money, at: Date): void {
    if (this._status !== PolicyStatus.Active && this._status !== PolicyStatus.Grace)
      throw new DomainError("платіж приймають лише за чинним полісом");
    // рахуємо суму ДО додавання — і ту саму величину перевіряємо
    const afterPay = this.paidTotal().plus(amount);  // кине, якщо валюти різні
    if (afterPay.isGreaterThan(this._premium))
      throw new DomainError("сума платежів не може перевищити премію");
    this._payments.push(new Payment(amount, at));    // інваріант ≤ премія тут тримається
  }

  paidTotal(): Money {
    return this._payments.reduce((s, p) => s.plus(p.amount),
                                 Money.zero(this._premium.currency));
  }

  // назовні — незмінний знімок, а не жива внутрішня колекція
  get payments(): readonly Payment[] { return [...this._payments]; }
}
```

Чому це важить понад охайність? Бо тепер інваріант «сума ≤ премія» **не може розійтися ні на крок виконання**. Немає жодного шляху додати платіж, оминувши `addPayment`; немає способу дістати живий список і штовхнути туди щось повз перевірку; немає моменту, коли премію змінено, а платежі ще старі, бо весь агрегат зберігають разом. Розмір агрегату — це проєктне рішення з реальною ціною: завеликий робить кожну зміну важкою (блокуємо пів системи заради дрібниці), замалий — не втримає інваріант, який мав тримати. Де саме проводити цю межу, як пов'язувати сусідні агрегати посиланням-на-корінь, а не прямим вкладенням, і чому зв'язок між агрегатами роблять згодом-узгодженим — розібрано окремо в темі про [агрегат і корінь узгодженості](root:sf-apps/aggregates-consistency). Для нашого рефакторингу досить трьох правил: **межа — довкола того, що мусить бути істинним разом; вхід — лише через корінь; одна транзакція — один агрегат.**

## Чому некоректний стан став недосяжним

Складімо докупи, що дала вся драбина, — і сформулюймо це точно, бо саме тут головна винагорода. У знекровленому варіанті множина станів, яких міг набути `Policy`, була **величезна**: будь-який рядок у `status`, будь-яке число в `premium`, будь-які платежі, будь-яка їх сума — усі комбінації, зокрема мільярд безглуздих. Правила, що мали цю множину звузити, жили ззовні й спрацьовували, лише коли викликач не забув їх покликати.

Після рефакторингу множина досяжних станів звузилася рівно до **законних**, і не завдяки дисципліні викликачів, а завдяки **структурі**:

```
що заборонено                          чим саме унеможливлено
─────────────────────────────────────  ──────────────────────────────
статус "banana" чи будь-який поза       enum PolicyStatus — інших значень
переліком                               просто не існує в типі

перехід grace з cancelled               вартовий у enterGracePeriod:
(воскресіння скасованого)               кине DomainError, стан не зміниться

від'ємна премія / від'ємний платіж      Money.of відкидає від'ємне на вході;
                                        від'ємного Money в системі не буває

платіж у чужій валюті                   Money.plus відмовляє різним валютам

сума платежів > премії                  вартовий у addPayment; і він єдині
                                        двері — оминути нема як

зміна платежів повз перевірку           поле закрите, геттер віддає КОПІЮ;
                                        живого списку назовні нема
```

Різниця між лівим і правим стовпцем — це різниця між «ми домовилися так не робити» і «так зробити неможливо». Знекровлена модель тримається на першому: на пам'яті кожного, хто колись торкнеться коду. Багата — на другому: на типах, приватності й вартових, які не можна забути, бо вони на шляху. Це і є сенс фрази «некоректний стан недосяжний» — не «ми його ловимо», а **його нема звідки взяти**.

І тут варто чесно назвати межу цієї сили. Багата модель робить недосяжними стани, які можна виразити **структурно** — типом, приватністю, вартовим на вході. Вона не робить за тебе **бізнес-рішень**: чи правильна ставка премії, чи слушний той чи інший строк — це предметні питання, і код лише тримає їх узгодженими, а не вирішує. Мета скромніша й точна: усунути ту складність, яку ми **самі собі створюємо** поганою структурою, і лишити чесну складність предмета видимою й керованою.

## Як це тестувати

Багата модель дає ще один подарунок, який окупає весь рефакторинг: її **надзвичайно легко тестувати**. Уся логіка тепер усередині об'єкта, не розмазана по сервісах, не зав'язана на базу чи мережу. Тест доменної моделі — це створити об'єкт у пам'яті, сказати йому кілька команд і перевірити, що дозволене відбувається, а заборонене кидає `DomainError`. Ні бази, ні моків, ні підйому середовища.

Тести природно діляться на два роди. Перший — **щасливий шлях**: законна послідовність команд приводить у правильний стан. Другий, важливіший, — **охорона інваріантів**: кожна заборонена дія має кинути, і об'єкт має лишитися **незмінним** (порушена команда не сміє наполовину зіпсувати стан).

:::tabs
```ts
// ── Щасливий шлях: законні переходи ведуть куди слід ──
test("чернетку можна активувати, тоді ввести в пільговий період", () => {
  const p = new Policy("P-1", new Date(), Money.of(120_00, "UAH"));
  p.activate();
  expect(p.status).toBe(PolicyStatus.Active);
  p.enterGracePeriod();
  expect(p.status).toBe(PolicyStatus.Grace);
});

test("платіж у межах премії приймається й додається до суми", () => {
  const p = new Policy("P-2", new Date(), Money.of(100_00, "UAH"));
  p.activate();
  p.addPayment(Money.of(40_00, "UAH"), new Date());
  expect(p.paidTotal().cents).toBe(40_00);
});

// ── Охорона інваріантів: заборонене кидає, стан НЕ псується ──
test("не можна ввести в пільговий період чернетку", () => {
  const p = new Policy("P-3", new Date(), Money.of(100_00, "UAH"));
  expect(() => p.enterGracePeriod()).toThrow(DomainError);
  expect(p.status).toBe(PolicyStatus.Draft);      // стан лишився недоторканим
});

test("платіж понад премію відхиляється, сума не міняється", () => {
  const p = new Policy("P-4", new Date(), Money.of(100_00, "UAH"));
  p.activate();
  p.addPayment(Money.of(80_00, "UAH"), new Date());
  expect(() => p.addPayment(Money.of(30_00, "UAH"), new Date())).toThrow(DomainError);
  expect(p.paidTotal().cents).toBe(80_00);        // невдалий платіж не додався
});

test("платіж у чужій валюті відхиляє сам Money", () => {
  const p = new Policy("P-5", new Date(), Money.of(100_00, "UAH"));
  p.activate();
  expect(() => p.addPayment(Money.of(10_00, "USD"), new Date())).toThrow(DomainError);
});
```
```python
import pytest

# ── Щасливий шлях: законні переходи ведуть куди слід ──
def test_draft_activates_then_enters_grace():
    p = Policy("P-1", None, Money.of(12000, "UAH"))
    p.activate()
    assert p.status is PolicyStatus.ACTIVE
    p.enter_grace_period()
    assert p.status is PolicyStatus.GRACE

def test_payment_within_premium_is_accepted():
    p = Policy("P-2", None, Money.of(10000, "UAH"))
    p.activate()
    p.add_payment(Money.of(4000, "UAH"), None)
    assert p.paid_total().cents == 4000

# ── Охорона інваріантів: заборонене кидає, стан НЕ псується ──
def test_cannot_enter_grace_from_draft():
    p = Policy("P-3", None, Money.of(10000, "UAH"))
    with pytest.raises(DomainError):
        p.enter_grace_period()
    assert p.status is PolicyStatus.DRAFT           # стан лишився недоторканим

def test_payment_over_premium_is_rejected():
    p = Policy("P-4", None, Money.of(10000, "UAH"))
    p.activate()
    p.add_payment(Money.of(8000, "UAH"), None)
    with pytest.raises(DomainError):
        p.add_payment(Money.of(3000, "UAH"), None)
    assert p.paid_total().cents == 8000             # невдалий платіж не додався

def test_payment_in_wrong_currency_is_rejected_by_money():
    p = Policy("P-5", None, Money.of(10000, "UAH"))
    p.activate()
    with pytest.raises(DomainError):
        p.add_payment(Money.of(1000, "USD"), None)
```
:::

Придивись, що саме ловлять ці тести й **чому вони можливі без жодної інфраструктури**. Тести щасливого шляху перевіряють, що законна послідовність дає правильний стан, — звичайна перевірка «вхід → стан». Тести охорони перевіряють дві речі одразу: що заборонена дія **кидає** `DomainError`, і — критично — що після невдачі об'єкт лишився **у попередньому стані** (`p.status` усе ще `Draft`, `paidTotal` усе ще `80_00`). Друга частина не менш важлива за першу: команда, що відмовляє, мусить відмовляти **чисто**, не встигнувши наполовину зіпсувати стан. Наші вартові стоять на **вході**, до будь-якої зміни, тож ця чистота дається сама собою — але перевірити її треба, бо саме тут ховається класична помилка «кинули виняток, але поле вже змінили».

> 🔧 **Навіщо це.** Ось проста лакмусова проба на здоров'я доменної моделі: спробуй написати на неї тест **без бази, без моків, без підйому середовища**. Вдалося — створив об'єкт, покликав команди, перевірив стан і винятки — модель багата й самодостатня, її логіку видно як на долоні. Не вдається, бо всередині захований запит до бази чи виклик зовнішнього сервісу, — це сигнал, що в доменний об'єкт протекла інфраструктура, і її треба звідти прибрати. Тестованість тут — не окрема мета, а **побічний доказ** того, що правила зібрані там, де їм місце.

## Складність і пастки

Рефакторинг простий у задумі, але має кілька країв, об які легко порізатися саме тоді, коли здається, що вже все зроблено. Пройдімося по них чесно.

**Пастка перша: сеттери, що просочуються назад.** Ти закрив поля й завів команди — а через тиждень хтось, кому «терміново треба», додає `set status()` чи публічний `setStatus`, «просто щоб полагодити один випадок». І вся охорона миттю знецінюється: знову є двері в обхід вартових, знову стан можна зіпсувати ззовні. Ця пастка має два обличчя. Явне — власне повернутий сеттер. Приховане, підступніше — **геттер, що віддає живий змінний нутрощ**: масив, мапу, вкладений об'єкт, який можна змінити.

:::tabs
```ts
// ПАСТКА: геттер віддає САМ масив — і вся охорона addPayment знецінена
get payments(): number[] { return this._payments; }   // ← НЕ роби так
// зовні: policy.payments.push(-999)  ← клали що завгодно повз перевірку

// ЯК ТРЕБА: назовні тече лише незмінна копія / незмінний тип
get payments(): readonly Payment[] { return [...this._payments]; }
```
```python
# ПАСТКА: геттер віддає САМ список — і вся охорона add_payment знецінена
@property
def payments(self):
    return self._payments            # ← НЕ роби так
# зовні: policy.payments.append(-999)  ← клали що завгодно повз перевірку

# ЯК ТРЕБА: назовні тече лише незмінний знімок
@property
def payments(self):
    return tuple(self._payments)
```
:::

Правило, що рятує: **усередину — лише через команди, назовні — лише незмінне**. Кожен новий публічний метод питай: він дає зайти в обхід вартового? Кожен геттер колекції питай: він віддає живий об'єкт чи його знімок? Одна протікла деталь — і багата модель знову знекровлена, тільки цього ти вже не побачиш за фасадом методів.

**Пастка друга: агрегат, що розрісся.** Спокуса після вдалого кроку 5 — тягнути в корінь **усе, що якось пов'язане** з полісом: історію змін, документи, листи-сповіщення, дані клієнта, розрахунки актуарія. Агрегат роздувається, і з ним усе гіршає одразу. Зберегти поліс тепер означає підняти й записати пів бази; кожна дрібна зміна блокує велетенський шматок; завантаження важчає; межа транзакції охоплює те, що узгоджувати разом і не треба було. Ознака хвороби проста: **у корені опинилося те, що не бере участі в жодному його інваріанті**. Історія змін не впливає на «сума ≤ премія»; дані клієнта живуть своїм життям. Такі речі — **окремі агрегати**, пов'язані з полісом лише посиланням-на-корінь (по `id`), а не вкладені всередину. Питання-різак: «чи мусить ця частина бути істинною **разом** із рештою, в одній транзакції?» Якщо ні — їй не місце в агрегаті. Тримай агрегат рівно таким, щоб він накривав **один** пучок інваріантів, і ні атомом більшим.

**Пастка третя: спокуса тягти правило назад у сервіс.** Найпідступніша, бо приходить під личиною зручності. З'являється новий випадок — скажімо, «активувати поліс можна лише після першого платежу» — і рука сама тягнеться дописати цю перевірку в `PolicyService.activate`, «бо там же зручно, там уже є доступ і до поліса, і до сховища». Ще одна така поступка, ще одна — і за пів року правила знову розмазані між об'єктом і сервісом, а поліс знову знекровлений наполовину. Розрізняльна лінія, яка не дає з'їхати, одна: **правило про власний стан об'єкта живе в об'єкті; оркестрація кроків живе в сервісі**. «Активувати можна лише після першого платежу» — це правило **про стан поліса**, і його місце в `Policy.activate` (яка сама гляне на свої платежі й вирішить). А от «дістати поліс зі сховища, активувати, зберегти, надіслати лист» — це оркестрація, і вона правильно в сервісі. Проба-різак: якщо перевірку можна сформулювати, дивлячись **лише на поля самого об'єкта**, — вона доменне правило й належить об'єкту; якщо вона потребує кількох об'єктів, сховища чи зовнішнього світу — вона оркестрація й належить сервісу. Тягнути перше в друге — це рівно той рух, який колись і породив знекровлену модель; не повторюй його з новими правилами.

**Край четвертий, тонший: команда, якій справді треба щось повернути.** Здебільшого команда змінює стан і нічого змістовного не повертає (`activate`, `addPayment`), а читання роблять окремі запити (`status`, `paidTotal`) — цей поділ команд і запитів тримає код прозорим. Але зрідка життя вимагає винятку: скажімо, команда реєструє платіж і має одразу повернути квитанцію чи новий баланс, і розбивати це на дві дії гірше, ніж лишити однією. Це відомий компроміс: **тримайся розділення за замовчуванням, а порушуй свідомо й рідко**, коли розділення явно шкодить, — не навпаки. Для нашого поліса потреби порушувати немає, і команди лишаються «мовчазними».

Підіб'ємо. Перетворення знекровленого мішка на багату модель — це не переписування начисто, а низка дрібних безпечних кроків: закрити поля, внести інваріант із сервісу в об'єкт, зробити єдині двері через команду, виділити гроші в об'єкт-значення, накрити пов'язані частини коренем агрегату. Мірило зробленого — не кількість методів і не краса діаграми, а одна перевірна річ: **чи можна тепер привести поліс у стан, якого не існує в його природі**. Коли відповідь стала «ні звідки», і коли перевірити це можна тестом без бази й моків, — рефакторинг досяг мети. Складність, яку знекровлена модель сама собі створювала розсипаним правилом і відкритими полями, просто перестала народжуватися; а та, що лишилася, — чесна складність предмета, і вона тепер зібрана в одному місці, названа мовою страхування й захищена від псування.
