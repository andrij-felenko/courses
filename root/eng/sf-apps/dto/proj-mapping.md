# ⚙️ Маппінг домен ↔ DTO: де патерн подає рахунок

Коли на межі стоїть багатий `Order` з одного боку і плаский `OrderDto` з іншого, хтось мусить перекладати одне на інше. На вихід — зібрати виписку з домену: узяти правила, порахувати підсумок, розкласти рядки замовлення в пласкі структури. На вхід — навпаки, з чужого, «дурного» DTO обережно збудувати або оновити домен, не пустивши всередину нічого, що поламало б його інваріанти. Ця ділянка коду зветься **маппінг** (англ. *mapping* — перекладання, зіставлення), і на перший погляд вона нудна: копіюєш поля з одного об'єкта в інший, що тут думати.

А думати є про що, і саме тут DTO або окупається, або перетворюється на тихий податок, що з'їдає час на кожній зміні. Бо маппінг — це не побічна дрібниця патерну, а **місце, де вся його ціна стає видимою**. Швидкодію й розв'язку сторін DTO обіцяє на межі; платить за них — рядок за рядком — саме тут, у перекладачі. Розберімо цю ділянку так, як вона виглядає в живому коді на C++: спершу задача в усій її незручності, тоді ідея, куди цю роботу подіти, тоді робочий код в обидва боки — і, найважливіше, пастки, через які маппінг із помічника стає найкрихкішим місцем системи.

## Задача: два перекладання, обидва небезпечні

Візьмемо конкретно. Усередині живе домен — рівно той, що в статті-власнику:

:::tabs
```cpp
// Багатий домен: поведінка, приховані поля, інваріанти під замком
class Order {
    OrderId            id_;         // внутрішній ключ бази
    Money              cost_;       // собівартість — назовні не їде
    std::vector<Line>  lines_;      // рядки замовлення (товар, кількість, ціна)
    Status             status_;     // New / Paid / Shipped / Cancelled
public:
    Money  total()  const;         // правило: сума з урахуванням знижок
    bool   canCancel() const;      // правило: коли скасування дозволене
    void   cancel();               // міняє статус, боронячи інваріант
    // ... конструктор, що НЕ дає створити некоректне замовлення
};

struct Line {                       // рядок домену теж багатий: valid-об'єкти
    Sku      sku;                   // код товару (не голий рядок — тип із перевіркою)
    int      qty;                   // кількість > 0 (гарантує конструктор)
    Money    unitPrice;
};
```
```python

class Order:
    def __init__(self, id, cost, lines, status):

    def total(self) -> Money:      # правило: сума з урахуванням знижок
        ...
    def can_cancel(self) -> bool:  # правило: коли скасування дозволене
        ...
    def cancel(self) -> None:      # міняє статус, боронячи інваріант
        ...
    # ... конструктор, що НЕ дає створити некоректне замовлення
```

І пласка виписка, що перетинає межу:

:::tabs
```cpp
struct LineDto {
    std::string sku;                // тут уже голий рядок — DTO «дурний»
    int         qty;
    double      unitPrice;          // гроші як double — на межі так буває
};

struct OrderDto {
    long                    id;
    double                  total;  // готовий результат, не собівартість
    std::string             status; // "new" / "paid" / "shipped" / "cancelled"
    std::vector<LineDto>    lines;
};
```
```python
from dataclasses import dataclass, field

@dataclass
class LineDto:
    sku: str                        # тут уже голий рядок — DTO «дурний»
    qty: int
    unit_price: float               # гроші як float — на межі так буває

@dataclass
class OrderDto:
    id: int
    total: float                    # готовий результат, не собівартість
    status: str                     # "new" / "paid" / "shipped" / "cancelled"
    lines: list[LineDto] = field(default_factory=list)
```
:::

Тепер два напрями, і кожен несе свою халепу.

**Напрям назовні** (`toDto`) виглядає безневинно: читай геттери, клади в поля. Але вже тут ховаються рішення. `total` — це не поле, а **результат правила**: його треба порахувати викликом `order.total()`, а не діставати сирі числа. `status` домену — це enum, а в DTO — рядок: хтось мусить вирішити, як `Status::Shipped` перетворюється на `"shipped"`, і тримати цю відповідність в одному місці, бо клієнт по інший бік читатиме саме ці рядки. `cost_` не їде взагалі — і це не забудькуватість, а рішення дизайну, яке маппер мусить свідомо втілити.

**Напрям усередину** (`fromDto`) — по-справжньому небезпечний. DTO прийшов **іззовні**: з мережі, від клієнта, з черги. Він **дурний за визначенням** — у ньому немає жодного правила, жодної гарантії. Ніщо не заважає, щоб у ньому лежало `qty = -5`, порожній `sku`, статус `"колесо"` замість реального стану, `total`, який не сходиться із сумою рядків. Якщо ти візьмеш ці поля й **просто розкладеш по домену**, ти власноруч затягнеш усередину зіпсований стан і зруйнуєш саме те, заради чого домен існує, — його інваріанти. Тому `fromDto` — це не копіювання полів, а **прохідна через митницю**: кожне поле треба перевірити, і тільки з перевіреного будувати домен через його ж конструктор, який має право сказати «ні».

І поверх цих двох напрямів — третя незручність: **часткове оновлення**. Клієнт хоче змінити в замовленні лише одне — скажімо, кількість в одному рядку, — і шле DTO. Що робити з рештою полів? Якщо тлумачити відсутнє як «стерти», ти знесеш дані, яких клієнт не чіпав. Часткове оновлення — окрема задача зі своєю пасткою, до неї повернемось.

> 🔧 **Навіщо це.** Дві сторони маппінгу — не симетричні, і плутати їх дорого. `toDto` — це показ: помилка тут щонайбільше покаже зайве чи неповне. `fromDto` — це **впуск чужих даних у твоє ядро**, і помилка тут дає зіпсований стан, який спливе через тиждень у зовсім іншому місці. Тому митницю ставлять саме на вході: перевіряти на межі, поки дані ще пласкі й дурні, — набагато дешевше, ніж ловити зруйнований інваріант десь у глибині домену.

## Ідея: перекладач — окрема відповідальність, поза обома світами

Куди подіти цей код? Спокуса — покласти його в один із двох об'єктів, які він зшиває. Обидва варіанти псують дизайн, і варто побачити, **чому саме**.

Покласти в **домен** — дати `Order` метод `toDto()`. Тоді домен знає про існування DTO. Але DTO — це форма **зовнішньої** межі: вона диктується вебклієнтом, схемою повідомлення, чужою командою. Щойно домен знає про неї, він **прикутий до зовнішньої форми**: змінилася схема на межі — довелося чіпати серце застосунку. Це прямо руйнує те, заради чого DTO взагалі заводили. Домен мусить лишатися в блаженному невіданні про те, як його виписки виглядають назовні.

Покласти в **DTO** — дати `OrderDto` конструктор із `Order`. Тоді пласка структура знає про багатий домен, тягне його заголовки, його типи. DTO перестає бути тим, чим має бути, — простою серіалізовною формою без залежностей; тепер він залежить від усього домену, і його вже не можна оголосити в спільному хедері для клієнта, бо клієнт домену не має й мати не повинен.

Отже, код перекладу не належить **жодному** з двох. Він належить **третій відповідальності — перекладачеві**, який єдиний знає про обидві сторони, тоді як **ні домен, ні DTO не знають одне про одного**. Це рівно те, що Мартін Фаулер у «Patterns of Enterprise Application Architecture» (2002) назвав **складачем** — **Data Transfer Object Assembler**: окремий об'єкт із єдиною відповідальністю зіставляти поля агрегату з полями DTO. *(Це усталений канонічний патерн; Фаулер уводить складач саме як окрему сутність, що конвертує дані між DTO й доменними об'єктами, — статус: канон дисципліни.)*

![Ліворуч зелена рамка «Домен: Order, правила, інваріанти» з підписом «не знає про DTO»; праворуч сіра рамка «OrderDto: пласкі поля, без поведінки» з підписом «не знає про домен»; посередині жовта рамка «Assembler (перекладач)» з підписом «єдиний, хто знає про обидва боки»; від неї стрілка ліворуч у домен «fromDto: митниця» і стрілка праворуч у DTO «toDto: показ»](img/assembler.svg)

*Перекладач стоїть третьою стороною між доменом і DTO. Обидва краї лишаються в невіданні одне про одного — знання про переклад зосереджене в одному місці, і саме туди йде будь-яка зміна форми на межі.*

Форма цього перекладача — питання смаку й масштабу. Найпростіше — **вільні функції** в окремому файлі-перекладачі:

:::tabs
```cpp
// order_mapping.h — єдине місце, що знає про обидва боки
OrderDto toDto(const Order& order);
Order    fromDto(const OrderDto& dto);         // кидає, якщо DTO некоректний
```
```python
# order_mapping.py — єдине місце, що знає про обидва боки
def to_dto(order: Order) -> OrderDto: ...
def from_dto(dto: OrderDto) -> Order: ...       # кидає, якщо DTO некоректний
```
:::

Коли перекладів багато або їм потрібен спільний стан (кеш довідників, налаштування формату дат) — той самий код збирають у **клас-складач**:

:::tabs
```cpp
class OrderAssembler {
    const SkuCatalog& catalog_;                // спільний контекст для перекладу
public:
    explicit OrderAssembler(const SkuCatalog& c) : catalog_(c) {}
    OrderDto toDto(const Order&) const;
    Order    fromDto(const OrderDto&) const;
};
```
```python
class OrderAssembler:
    def __init__(self, catalog: SkuCatalog):
        self._catalog = catalog                # спільний контекст для перекладу

    def to_dto(self, order: Order) -> OrderDto: ...
    def from_dto(self, dto: OrderDto) -> Order: ...
```
:::

Функція чи клас — суть одна: **знання про переклад зосереджене в одному місці, і жоден із двох світів не забруднений знанням про інший**. Змінилася форма DTO — правиш перекладач, домен спить. Змінилося правило домену — правиш домен, DTO стоїть. Це і є вся цінність окремої відповідальності: два незалежні світи й одна вузька ділянка, що їх зшиває.

> 🔧 **Навіщо це.** Правило приземлене: **у перекладачі — тільки перекладання, і ніде більше не має бути коду, що знає про обидві форми.** Бачиш `#include "order_dto.h"` усередині доменного класу — це протікання: домен підглянув назовні. Бачиш `#include "order.h"` усередині файлу з DTO — те саме навпаки. Обидва інклюди законні лише в одному файлі — файлі перекладача. Це найдешевший тест на здоров'я межі: полічи, хто знає про обидва боки. Один файл — здорово; більше — DTO вже почав протікати в код.

## Робочий код: обидва напрями чесно

Тепер сам переклад — не псевдокод, а те, що компілюється й працює.

**Напрям назовні — `toDto`.** Тут головне не «скопіювати поля», а **не пропустити рішень**: підсумок рахуємо правилом, статус переводимо через єдину відповідність, приховані поля не чіпаємо, вкладені рядки перекладаємо своїм маленьким маппером.

:::tabs
```cpp
// Єдина відповідність enum ⇄ рядок — в одному місці на обидва напрями
static std::string statusToString(Status s) {
    switch (s) {
        case Status::New:       return "new";
        case Status::Paid:      return "paid";
        case Status::Shipped:   return "shipped";
        case Status::Cancelled: return "cancelled";
    }
    // жодного default: щойно додаси стан у enum — компілятор
    // (з -Wswitch) нагадає дописати переклад тут, а не мовчки збреше
    throw std::logic_error("невідомий Status у statusToString");
}

// Маленький маппер для вкладеного рядка — своя дрібна відповідальність
static LineDto lineToDto(const Line& l) {
    return LineDto{
        l.sku.str(),               // Sku → голий рядок: тип роздягається на межі
        l.qty,
        l.unitPrice.toDouble()     // Money → double: свідома втрата типу-грошей
    };
}

OrderDto toDto(const Order& order) {
    OrderDto dto;
    dto.id     = order.id().value();          // OrderId → long
    dto.total  = order.total().toDouble();    // ПРАВИЛО, не сире поле: рахуємо
    dto.status = statusToString(order.status());
    // cost_ навмисно НЕ їде — рішення дизайну, втілене мовчанням

    dto.lines.reserve(order.lines().size());
    for (const Line& l : order.lines())
        dto.lines.push_back(lineToDto(l));
    return dto;
}
```
```python
# Єдина відповідність enum ⇄ рядок — в одному місці на обидва напрями
_STATUS_TO_STR = {
    Status.NEW:       "new",
    Status.PAID:      "paid",
    Status.SHIPPED:   "shipped",
    Status.CANCELLED: "cancelled",
}

def status_to_string(s: Status) -> str:
    try:
        return _STATUS_TO_STR[s]
    except KeyError:
        # щойно додаси стан у enum, а сюди ні — впаде голосно тут,
        # а не мовчки поверне порожнечу
        raise ValueError(f"невідомий Status у status_to_string: {s}")

# Маленький маппер для вкладеного рядка — своя дрібна відповідальність
def line_to_dto(l: Line) -> LineDto:
    return LineDto(
        sku=l.sku.str(),               # Sku → голий рядок: тип роздягається на межі
        qty=l.qty,
        unit_price=l.unit_price.to_float(),  # Money → float: свідома втрата типу-грошей
    )

def to_dto(order: Order) -> OrderDto:
    return OrderDto(
        id=order.id.value,                     # OrderId → int
        total=order.total().to_float(),        # ПРАВИЛО, не сире поле: рахуємо
        status=status_to_string(order.status),
        # cost навмисно НЕ їде — рішення дизайну, втілене мовчанням
        lines=[line_to_dto(l) for l in order.lines],
    )
```
:::

Зверни увагу на три речі, у яких і є вся суть цього напряму. По-перше, `dto.total = order.total()` — не читання поля, а **виклик правила**: DTO несе назовні *результат*, а не сирі складники, з яких клієнт мусив би сам щось рахувати (та ще й маючи доступ до собівартості, якого йому не можна). По-друге, `statusToString` — **єдина точка** перекладу стану; коли завтра з'явиться `Status::Refunded`, ти хочеш, щоб компілятор змусив тебе дописати рядок тут, а не щоб код тихо повернув порожнечу. По-третє, `cost_` не згадується взагалі — і це найважливіший рядок, якого немає: приховане поле лишається прихованим саме тому, що перекладач свідомо його не бере.

**Напрям усередину — `fromDto`.** Ось де ставимо митницю. Правило одне й непорушне: **спочатку перевір усе, і тільки з перевіреного будуй домен через його конструктор** — той конструктор, що має право відмовити.

:::tabs
```cpp
static Status statusFromString(const std::string& s) {
    if (s == "new")       return Status::New;
    if (s == "paid")      return Status::Paid;
    if (s == "shipped")   return Status::Shipped;
    if (s == "cancelled") return Status::Cancelled;
    throw ValidationError("невідомий статус: '" + s + "'");   // митниця сказала «ні»
}

static Line lineFromDto(const LineDto& d) {
    if (d.qty <= 0)
        throw ValidationError("кількість мусить бути > 0, прийшло " +
                              std::to_string(d.qty));
    if (d.sku.empty())
        throw ValidationError("порожній код товару (sku)");
    // Sku(...) сам ще раз перевірить формат — валідні типи бороняться самі
    return Line{ Sku(d.sku), d.qty, Money::fromDouble(d.unitPrice) };
}

Order fromDto(const OrderDto& dto) {
    // 1) Перевіряємо ВСЕ, поки дані ще пласкі й дурні
    if (dto.lines.empty())
        throw ValidationError("замовлення без жодного рядка");

    std::vector<Line> lines;
    lines.reserve(dto.lines.size());
    for (const LineDto& d : dto.lines)
        lines.push_back(lineFromDto(d));      // кожен рядок крізь митницю

    Status status = statusFromString(dto.status);

    // dto.total НЕ довіряємо: домен порахує суму САМ і не дасть її підмінити.
    // Клієнт міг прислати будь-яке число — воно не має влади над інваріантом.

    // 2) Лише тепер будуємо домен — через конструктор, що боронить інваріанти
    return Order::create(OrderId(dto.id), std::move(lines), status);
    //     ^ якщо комбінація полів усе одно нездорова (напр. Shipped без оплати),
    //       конструктор кине САМ — останній рубіж оборони
}
```
```python
_STATUS_FROM_STR = {
    "new":       Status.NEW,
    "paid":      Status.PAID,
    "shipped":   Status.SHIPPED,
    "cancelled": Status.CANCELLED,
}

def status_from_string(s: str) -> Status:
    try:
        return _STATUS_FROM_STR[s]
    except KeyError:
        raise ValidationError(f"невідомий статус: '{s}'")   # митниця сказала «ні»

def line_from_dto(d: LineDto) -> Line:
    if d.qty <= 0:
        raise ValidationError(f"кількість мусить бути > 0, прийшло {d.qty}")
    if not d.sku:
        raise ValidationError("порожній код товару (sku)")
    # Sku(...) сам ще раз перевірить формат — валідні типи бороняться самі
    return Line(Sku(d.sku), d.qty, Money.from_float(d.unit_price))

def from_dto(dto: OrderDto) -> Order:
    # 1) Перевіряємо ВСЕ, поки дані ще пласкі й дурні
    if not dto.lines:
        raise ValidationError("замовлення без жодного рядка")

    lines = [line_from_dto(d) for d in dto.lines]   # кожен рядок крізь митницю

    status = status_from_string(dto.status)

    # dto.total НЕ довіряємо: домен порахує суму САМ і не дасть її підмінити.
    # Клієнт міг прислати будь-яке число — воно не має влади над інваріантом.

    # 2) Лише тепер будуємо домен — через конструктор, що боронить інваріанти
    return Order.create(OrderId(dto.id), lines, status)
    #      ^ якщо комбінація полів усе одно нездорова (напр. Shipped без оплати),
    #        конструктор кине САМ — останній рубіж оборони
```
:::

Тут кожен рядок — рішення про довіру. `qty <= 0` відсікаємо **до** того, як воно дійде до домену. `dto.total` **свідомо ігноруємо**: сума — це внутрішнє правило, і дати зовнішньому числу владу над нею означало б відчинити двері для шахрайства («замовлення на тисячу, а в total пишу нуль»). Домен рахує сам. І фінальний рубіж — `Order::create`: навіть якщо кожне окреме поле пройшло, їхня **комбінація** може бути хвора (відвантажене, але неоплачене), і тоді відмовляє конструктор. Митниця стоїть у два ешелони: поля перевіряє маппер, їхню сумісність — домен.

> 🔧 **Навіщо це.** Формула здоров'я входу проста: **валідація живе на вході з DTO, бо сам DTO її не має.** Він плаский і дурний — у ньому нема конструктора, що боронить, нема інваріантів. Уся оборона, яку в домені несуть типи й конструктори, на межі мусить робитися **вручну в мапері**. Пропустиш перевірку тут — і зіпсований стан опиниться в ядрі, а спрацює за кілометр звідси. Дешева перевірка на вході економить дорогий розслід згодом.

**Часткове оновлення.** Повертаємось до відкладеної задачі. Клієнт шле DTO, щоб змінити **щось одне**, а не перестворити замовлення. Наївний `fromDto` тут шкідливий: він будує домен **з нуля**, а отже все, чого в DTO нема, буде втрачене або підмінене. Правильний хід — **не будувати наново, а оновити наявний**, і чіпати лише те, що прийшло:

```cpp
// Часткове оновлення: беремо ЖИВЕ замовлення й міняємо тільки надіслане.
// optional-поля кажуть «це поле клієнт справді хотів змінити»,
// а не «тут випадково нуль».
struct OrderPatchDto {
    std::optional<std::string>          status;   // є → міняй статус
    std::optional<std::vector<LineDto>> lines;    // є → заміни рядки
    // чого нема — те не чіпаємо
};

void applyPatch(Order& order, const OrderPatchDto& patch) {
    if (patch.status) {                            // прийшов статус?
        Status s = statusFromString(*patch.status);
        order.changeStatus(s);   // МЕТОД ДОМЕНУ, а не присвоєння поля:
                                 // домен сам вирішить, чи перехід дозволений
    }
    if (patch.lines) {                             // прийшли рядки?
        std::vector<Line> lines;
        for (const LineDto& d : *patch.lines)
            lines.push_back(lineFromDto(d));
        order.replaceLines(std::move(lines));      // теж крізь правило домену
    }
    // status немає в патчі → статус лишився як був. Нічого не знесли.
}
```

Ключ — розрізнити **«поле прийшло зі значенням»** і **«поля не було»**. Плаский DTO цього сам не вміє: у ньому `status = ""` неоднозначне — то клієнт хоче порожній статус чи просто не чіпав його? `std::optional` знімає двозначність: `nullopt` означає «не чіпай», значення — «зміни на це». І кожна зміна йде **через метод домену** (`changeStatus`, `replaceLines`), а не через сире присвоєння поля, бо тільки домен знає, чи дозволений перехід зі стану в стан. Патч-DTO — це список побажань; домен лишається тим, хто каже, які з них законні.

## Складність і пастки: де маппінг стає податком

Тепер найважливіше — пастки, бо саме вони вирішують, окупиться DTO чи стане тягарем. Маппінг легко написати; важко втримати його від переростання в найкрихкіше й найпрожерливіше місце системи.

**Пастка перша — логіка домену заповзає в маппер.** Це стається тихо. Спершу маппер чесно перекладає. Тоді хтось помічає: «а давай прямо тут порахуємо знижку, зручно ж — усі дані під рукою». Потім — «а тут перевіримо ліміт кредиту». За півроку твій `toDto` містить бізнес-правила, яких немає в домені, — і тепер їх **два джерела правди**: одне в `Order`, друге в мапері. Вони розходяться, і ти вже не знаєш, яке з них справжнє. Правило залізне: **маппер тільки перекладає форму; жодного рішення, що є бізнес-правилом, він не приймає**. Порахувати суму? — виклич `order.total()`, не рахуй у мапері. Вирішити, чи можна скасувати? — спитай `order.canCancel()`, не пиши цю умову тут. Щойно в мапері з'явилося `if`, що втілює **правило домену**, а не перевіряє **форму даних**, — правило втекло з дому, і його треба гнати назад. Різниця тонка, але чітка: перевірити, що `qty > 0`, — це форма (валідація входу, місце мапера); вирішити, що при `qty > 100` дається опт-знижка, — це правило (місце домену).

**Пастка друга — вибух ручного коду.** Порахуй чесно. Кожен доменний тип, що перетинає межу, тягне за собою: структуру DTO, `toDto`, `fromDto`, а часто ще й патч-DTO з `applyPatch`. На вкладені типи — свої маленькі маппери (`lineToDto`, `lineFromDto`). Десять сутностей — це десятки функцій **чистого копіювання полів**, яке до того ж треба **правити щоразу**, коли в домені додається поле. Додав `Order::discount` — не забудь чотири місця: поле в `OrderDto`, рядок у `toDto`, рядок у `fromDto`, можливо, у патчі. Забув одне — тихий баг: поле є, а на межу не потрапляє. Це та сама **хвиля правки**, що й у [зчепленні](root:sf-apps/coupling-cohesion): одна зміна б'є по багатьох місцях, і що більше сутностей, то ширша хвиля.

Звідси вічна спокуса — **автоматизувати переклад**, щоб не писати його руками. Три шляхи, і в кожного своя схована ціна.

Перший — **кодогенерація**: описуєш форму в окремій схемі (IDL, `.proto`, анотації), а інструмент **генерує** структури DTO й маппери під час збірки. Так працюють Protocol Buffers, FlatBuffers, Cap'n Proto. Плюс справжній: ручного копіювання нема, схема — єдине джерело, згенерований код швидкий. Ціна схована в **окремому кроці збірки** й у тому, що згенерований код треба **читати й дебажити**, коли щось піде не так, — а він не твій і часто нечитабельний. Ти обміняв ручну працю на залежність від генератора й на непрозорість. Про самі формати серіалізації, поверх яких це будується, — [окрема тема](root:com-protocol/data-serialization).

Другий — **рефлексія-обгортки**: бібліотека сама «дивиться» на поля структури й ганяє їх туди-сюди без ручного мапера. Тут криється особлива для C++ пастка. **У C++ до 26-го стандарту не було рідної рефлексії взагалі** — мова не вміла на етапі компіляції перелічити поля структури. Тому всі «магічні» C++-бібліотеки маппінгу трималися на **макросах і шаблонному фокусництві**: ти мусив або перелічити поля в макросі (`REFLECT(Order, id, total, status)`), або обгорнути кожне поле спеціальним типом. Виходить рефлексія, якої в мові нема, — але ціною макросів, які ховають, що насправді діється, і ламаються з нечитабельними помилками шаблонів на сотні рядків. Це зміниться: **статичну рефлексію ухвалили до C++26** (пропозиція P2996, проголосована в стандарт у червні 2025-го), і компілятор нарешті зможе перелічити поля сам, на етапі компіляції, без макросів і без коштів часу виконання. *(Статус: стандартизовано для C++26; реалізації станом на 2026-й ще експериментальні — гілка Clang, форк Bloomberg. Практичний масовий ужиток — попереду.)* Але й тоді треба пам'ятати головне: **рефлексія не прибирає роботу — вона її ховає.** Автоматичний маппінг «поле-в-поле» добрий, лише коли форми **справді збігаються**. Щойно `total` треба порахувати, `status` перевести enum→рядок, `cost_` не пустити назовні — автомат безсилий, і ти повертаєшся до ручного коду для рівно тих полів, де є хоч якесь рішення. А воно є майже завжди — інакше навіщо був би DTO окремо від домену.

Ось де замикається головна думка. **Маппінг — саме та ділянка, де стає видно, окупається DTO чи ні.** Якщо перекладач виходить майже порожній — форми домену й DTO збігаються поле-в-поле, нема чого рахувати, ховати, перекладати, — то, найпевніше, **DTO тобі не потрібен**: ти зробив плаского двійника домену без різниці між ними й тепер платиш за переклад, що нічого не міняє. Це рівно та шкода «локального DTO», про яку окремо застерігав Фаулер: грубозернистий інтерфейс важче використовувати, а роботу перекладання ти робиш дарма. Якщо ж перекладач **несе вагу** — рахує підсумки правилом, роздягає багаті типи в пласкі, ставить митницю на вході, ховає собівартість, розрулює часткові оновлення, — то кожен його рядок **щось купує**: або швидкодію, або безпеку, або розв'язку сторін. Порожній маппер — це чек за межу, якої нема. Насичений маппер — це доказ, що межа справжня й DTO на ній працює.

**Пастка третя — двонапрямні маппери й цикли.** Остання, підступна саме масштабом. Коли зв'язків багато, з'являється спокуса зробити маппер **«розумним»**: хай сам ходить по посиланнях і перекладає все дерево. Замовлення тягне клієнта, клієнт — його замовлення, замовлення — знову клієнта… якщо маппер сліпо йде за посиланнями в **обидва боки**, він зациклюється — або в нескінченну рекурсію до переповнення стека, або в дублювання одного й того самого об'єкта в кількох місцях DTO. Це не вигадка: будь-який граф із **взаємними посиланнями** (замовлення↔клієнт, вузол↔сусіди, коментар↔тема) ловить маппер у цикл. Оборона проста, коли про неї пам'ятаєш: **DTO — це дерево, а не граф.** Ти свідомо вирішуєш, **де межа виписки**: `OrderDto` несе `customerId` (просто число), а не вкладеного `CustomerDto`. Хочеш і клієнта — це **окремий, явно запитаний** DTO, а не автоматично протягнутий услід за посиланням. Автоматичний двонапрямний маппінг цю межу стирає й тому небезпечний саме тим, що зручний: він з радістю протягне за собою пів бази, поки не впреться в цикл. Ручний маппер натомість змушений на кожному посиланні спитати «а це поле справді їде?» — і саме це питання тримає виписку деревом.

> 🔧 **Навіщо це.** Практичний підсумок трьох пасток одним правилом кожна. Правило домену в мапері — **виганяй**: у перекладачі тільки форма, рішення кличемо в домена. Вибух копіювання — **терпи вручну, поки хвиля мала; автоматизуй, коли велика, але знай, що кодогенерація й рефлексія роботу не прибирають, а ховають** (і на кожному «особливому» полі повертають назад). Цикли — **DTO завжди дерево: межу виписки визнач сам, посилання неси ідентифікатором, а не вкладеним об'єктом.** Три правила — і маппер лишається тонким, чесним і передбачуваним, замість того щоб тихо стати серцем системи, яке ніхто не наважується чіпати.

## Що лишається в руках

Маппінг домен↔DTO — це не нудне копіювання полів, а **вузол, у якому патерн подає рахунок**. Робота розпадається на два несиметричні напрями: `toDto` — показ, де головне не пропустити рішень (рахувати правилом, а не діставати сире; ховати приховане; перекладати стани в одному місці); `fromDto` — митниця, де кожне поле перевіряється **до** входу в домен, бо DTO дурний і своїх інваріантів не має, а останнім рубежем стоїть конструктор домену. Часткове оновлення вимагає розрізняти «поле прийшло» й «поля не було» — і чіпати домен лише через його методи, не через сирі присвоєння.

Живе це все в **третій відповідальності** — перекладачі-складачі, який єдиний знає про обидва боки, тоді як домен і DTO лишаються в невіданні одне про одного. Тримати його тонким допомагають три правила проти трьох пасток: не пускати правила домену в маппер, автоматизувати переклад лише свідомо (пам'ятаючи, що кодогенерація й рефлексія ціну ховають, а не прибирають), і завжди тримати DTO деревом, несучи посилання ідентифікатором.

І головне, що видно саме звідси: **порожній маппер — це знак, що DTO зайвий**, а насичений — доказ, що межа справжня й патерн на ній окупається. Дивись на перекладача, коли сумніваєшся, чи потрібен тобі DTO взагалі: якщо йому нема чого перекладати, ти зробив двійника без різниці й платиш податок; якщо він щоразу щось рахує, ховає й перевіряє — значить, межа справжня, і кожен його рядок купує тобі швидкодію, безпеку або свободу міняти нутрощі.
