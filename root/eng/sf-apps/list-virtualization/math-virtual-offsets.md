# 🧮 Математичний апарат обчислення зміщень та індексації віртуального вікна

Віртуалізація списку зводиться до двох математичних задач: неперервного відображення координати прокрутки у дискретний діапазон індексів елементів під час рендерингу та динамічного перерахунку префіксних сум зі збереженням логарифмічної або сублінійної часової складності при зміні розмірів елементів.

## Формалізація задачі та монотонні префіксні суми

Нехай список містить `N` елементів, кожен з яких має ненульову додатну висоту:

```
h = [h₀, h₁, h₂, …, h_{N-1}],  де ∀i: h_i > 0
```

Повна віртуальна висота контейнера `H_total` визначається як сума висот усіх елементів:

```
H_total = ∑_{i=0}^{N-1} h_i
```

Введемо послідовність префіксних сум зміщень `S`, де елемент `S_k` задає абсолютну вертикальну координату початку `k`-го елемента відносно верхнього краю списку:

```
S₀ = 0
S_k = ∑_{i=0}^{k-1} h_i    для k ∈ {1, 2, …, N}
```

Оскільки висота кожного елемента строго додатна (`h_i > 0`), послідовність `S` є строго монотонно зростаючою:

```
S_{k+1} - S_k = h_k > 0  ⇒  S₀ < S₁ < S₂ < … < S_N = H_total
```

Кожен `i`-й елемент списку займає неперервний напіввідкритий інтервал координат на осі прокрутки:

```
I_i = [S_i, S_{i+1}) = [S_i, S_i + h_i)
```

## Відображення вікна прокрутки на діапазон індексів

Видове вікно (*viewport*) характеризується висотою `H_view` та поточною координатою верхньої межі прокрутки `y = scrollTop`, де `y ∈ [0, H_total - H_view]`. Вікно покриває геометричний інтервал:

```
W(y) = [y, y + H_view]
```

Елемент з індексом `i` перетинає видове вікно тоді й лише тоді, коли перетин його інтервалу `I_i` з вікном `W(y)` не є порожнім:

```
I_i ∩ W(y) ≠ ∅  ⇔  (S_i < y + H_view) ∧ (S_i + h_i > y)
```

Звідси випливає визначення граничних індексів видимого діапазону `[i_start, i_end]`:

```
i_start = max { k ∈ {0, …, N-1} : S_k ≤ y }
i_end   = min { k ∈ {0, …, N-1} : S_{k+1} ≥ y + H_view }
```

### Фіксована висота елементів

Якщо висота всіх елементів однакова (`∀i: h_i = h_const`), послідовність префіксних сум перетворюється на арифметичну прогресію:

```
S_k = k · h_const
```

У цьому випадку пошук граничних індексів обчислюється аналітично за час `O(1)` без виділення додаткової пам'яті:

```
i_start = ⌊ y / h_const ⌋
i_end   = min(N - 1, ⌊ (y + H_view - 1) / h_const ⌋)
```

Зсув верхньої межі рендерингу для позиціонування першого видимого елемента в системі координат контейнера становить:

```
offset_render = i_start · h_const
```

### Довільна фіксована висота: двійковий пошук у масиві префіксних сум

Коли елементи мають різну, але наперед відому висоту, масив префіксних сум `S` займає `O(N)` пам'яті. Оскільки `S` строго монотонний, пошук `i_start` та `i_end` виконується через двійковий пошук (*binary search*, функція `std::lower_bound`):

```
i_start = upper_bound(S, y) - 1
i_end   = lower_bound(S, y + H_view)
```

Кількість операцій порівняння для двійкового поділу інтервалу довжиною `N` становить:

```
T_search(N) = ⌈log₂(N + 1)⌉ = O(log N)
```

Для списку на 100 000 елементів:

```
T_search(100 000) = ⌈log₂(100 001)⌉ = 17 операцій порівняння
```

## Алгебра динамічного оновлення висот

Коли висоти елементів змінюються динамічно під час рендерингу (наприклад, після завантаження зображення або зміни розміру тексту), елемент `k` змінює свою висоту з `h_k` на `h_k + Δ`.

### Вартість оновлення в плоскому масиві префіксних сум

У простому масиві префіксів зміна одного елемента вимагає модифікації всіх наступних елементів:

```
S_j^{new} = S_j^{old} + Δ    для всіх j ∈ {k + 1, k + 2, …, N}
```

Кількість операцій оновлення у найгіршому випадку:

```
T_update_array(N) = N - k = O(N)
```

Якщо під час одного скролу змінюються розміри `M` елементів, сумарна складність становить `O(M · N)`, що при `N = 100 000` та `M = 20` дає 2 000 000 операцій запису в пам'ять на кожен кадр і гарантовано зриває бюджет кадру (16.67 мс).

### Дерево Фенвіка: логарифмічний баланс запиту й оновлення

Для досягнення логарифмічного часу оновлення використовується двійкове індексоване дерево Фенвіка (*Fenwick Tree* / *Binary Indexed Tree*). Дерево зберігається в масиві `T` розміру `N + 1` (з 1-індексацією), де кожен вузол відповідає за інтервал довжиною, рівною молодшому значущому біту свого індексу:

```
LSB(i) = i & (-i)
T[i] = ∑_{j = i - LSB(i) + 1}^{i} h_{j-1}
```

Обчислення префіксної суми `S_k = query(k)` та точкове оновлення `add(k, Δ)` виконуються побітовими переходами:

```
query(k):
  sum = 0
  i = k
  поки i > 0:
    sum += T[i]
    i -= i & (-i)
  повернути sum

add(k, Δ):
  i = k + 1
  поки i ≤ N:
    T[i] += Δ
    i += i & (-i)
```

Часова складність обох операцій обмежена кількістю бітів у двійковому поданні числа `N`:

```
T_query(N)  = ⌊log₂ N⌋ + 1 = O(log N)
T_update(N) = ⌊log₂ N⌋ + 1 = O(log N)
```

Пошук індексу елемента за координатою прокрутки `y` виконується методом двійкового підйому (*binary lifting*) по дереву Фенвіка за один прохід `O(log N)` без вкладеного двійкового пошуку `O(log² N)`.

### Блокова декомпозиція: коренева оптимізація O(√N)

Альтернативою дереву Фенвіка є блокова декомпозиція (*Square Root Decomposition*), яка забезпечує `O(1)` оновлення ціною `O(√N)` запиту або `O(log N)` із двійковим пошуком.

Масив із `N` елементів розбивається на `K = ⌈N / B⌉` блоків фіксованого розміру `B = ⌈√N⌉`. Для кожного блоку `m` підтримується сума висот його елементів:

```
B_sum[m] = ∑_{j = m · B}^{min(N - 1, (m + 1) · B - 1)} h_j
```

1. **Точкове оновлення:** при зміні `h_k` на `Δ` оновлюється лише один елемент і сума одного відповідного блоку `m = ⌊k / B⌋`:
   ```
   h_k ← h_k + Δ
   B_sum[⌊k / B⌋] ← B_sum[⌊k / B⌋] + Δ
   Складність: O(1)
   ```
2. **Префіксний запит:** сумуються повні блоки ліворуч від цільового індексу та окремі елементи всередині неповного блоку:
   ```
   S_k = ( ∑_{m = 0}^{⌊k / B⌋ - 1} B_sum[m] ) + ( ∑_{j = ⌊k / B⌋ · B}^{k - 1} h_j )
   Кількість операцій: ≤ (N / B) + B = 2 · ⌈√N⌉ = O(√N)
   ```

Для `N = 100 000`:
- Розмір блоку `B = ⌈√100 000⌉ = 317`.
- Оновлення: 2 операції запису (`O(1)`).
- Пошук діапазону: двійковий пошук по масиву сум блоків (`⌈log₂ 317⌉ ≈ 9` кроків) + двійковий пошук всередині знайденого блоку (`⌈log₂ 317⌉ ≈ 9` кроків) = разом 18 кроків.

## Динамічний розмір буфера випередження (Overscan)

Під час інерційного гортання користувач надає списку початкову швидкість `v₀` (у пікселях за секунду), яка згасає за експоненційним законом в'язкого тертя з часовою константою `τ`:

```
v(t) = v₀ · e^{-t / τ}
```

Нехай частота оновлення дисплея становить `f_refresh` (наприклад, 60 Гц або 120 Гц), що визначає тривалість одного кадру:

```
t_frame = 1 / f_refresh
```

Зміщення списку за один міжкадровий інтервал становить:

```
Δy_frame(t) = v(t) · t_frame
```

Щоб око користувача ні за яких умов не зафіксувало порожніх непорендерених ділянок (*blank space* / білі спалахи), розмір попереджувального буфера `B_overscan` (у пікселях) повинен перекривати максимальну швидкість зміщення з урахуванням коефіцієнта запасу на затримку виконання JavaScript-обробника `k_latency` (типово `k_latency ∈ [1.5, 2.5]`):

```
B_overscan(v) = B_min + ⌈ |v| · t_frame · k_latency ⌉
```

Кількість елементів буфера `N_overscan`, які необхідно додати до рендерингу зверху та знизу, вираховується через середню або мінімальну висоту елементів `h_min`:

```
N_overscan(v) = ⌈ B_overscan(v) / h_min ⌉
```

### Покроковий числовий приклад розрахунку буфера

**Вхідні параметри:**
- Швидкість швидкого скролу: `v = 4000 px/s`
- Частота дисплея: `120 Гц` (`t_frame = 8.33 мс = 0.00833 с`)
- Коефіцієнт надійності: `k_latency = 2.0` (компенсація затримки черги подій)
- Базовий статичний буфер: `B_min = 100 px`
- Середня висота рядка: `h_avg = 50 px`

```
Δy_frame = 4000 · 0.00833 = 33.32 px
B_overscan = 100 + ⌈33.32 · 2.0⌉ = 100 + 67 = 167 px
N_overscan = ⌈167 / 50⌉ = 4 елементи
```

Отже, при швидкості прокручування 4000 пікселів за секунду на екрані 120 Гц система повинна рендерити рівно по 4 додаткові елементи вище та нижче видимого зрізу для гарантії безперервної 120 FPS-візуалізації без візуальних артефактів.
