# ⚙️ Типостан-автомат: незаконна послідовність не компілюється

Є два різні за природою класи багів. Перший — **не ті дані**: місяць 13, стан «і помилка, і дані одночасно», широта, підставлена замість довготи. Проти нього працює звуження множини значень і згортання розсипаних прапорців у суму — це моделювання **даних**, і робочий C++ для нього, з `std::variant` і новотипами, зібрано [окремим розбором](root:sf-apps/type-driven-design/proj-sum-types-cpp.md). Другий клас — **не той порядок дій**: слати в ще не автентифіковане з'єднання, читати з уже закритого файлу, зібрати запит, забувши обов'язкове поле. Тут дані в кожну мить можуть бути бездоганні — ламається **послідовність**, протокол. І його теж можна вкласти в типи так, щоб незаконна послідовність не компілювалася. Прийом зветься **типостан** (англ. *typestate*).

Термін увів 1986 року Роберт Стром і Шаула Йеміні у статті «Typestate: A Programming Language Concept for Enhancing Software Reliability» (IEEE Transactions on Software Engineering, том SE-12, № 1) — саме щоб компілятор ловив «синтаксично законні, але семантично невизначені послідовності»: читання неініціалізованої змінної, доступ за звільненим вказівником. Це усталений факт із задокументованим першоджерелом. Сорок років по тому найчистіше цю ідею втілює Rust, бо його модель власності дає рівно ту машинерію, якої типостану бракувало в мовах 1980-х, — **афінні типи**. Тому головний код тут — на Rust; поряд, вкладками, той самий автомат на C++ і на TypeScript — три мови дають три різні за силою версії тієї самої гарантії, і саме на контрасті найкраще видно, від чого ця сила залежить.

Розберемо дві задачі, що покривають майже весь щоденний типостан. Перша — **ресурс із протоколом**: з'єднання, що ходить `Closed → Open → Authed → Closed`, де слати запити можна лише автентифікованим. Друга — **будівник з обов'язковими полями**, де `send()` просто не існує, поки не задано URL і метод.

## Задача 1. Ресурс із протоколом: Closed → Open → Authed

**Задача.** Клієнт тримає з'єднання з пристроєм чи сервісом. Протокол жорсткий: спершу під'єднатися, тоді пройти автентифікацію, і лише потім слати запити; закрити можна з будь-якого живого стану. Незаконні послідовності, яких треба не допустити: `request()` до автентифікації, `request()` чи `authenticate()` після `close()`, повторний `connect()` на вже під'єднаному хендлі. У світі одного типу `Connection` з полем-прапорцем `is_open` усе це **записується** й падає щонайраніше в рантаймі — в клієнта, як помилка.

**Ідея.** Зробити стан **частиною типу**. Не один `Connection` із прапорцем, а різні типи `Conn<Closed>`, `Conn<Open>`, `Conn<Authed>` — і кожну операцію визначити **лише на тому стані-типі, де вона законна**. Метод `request` живе тільки на `Conn<Authed>`; викликати його на `Conn<Open>` — не «дістати помилку», а не знайти методу, тобто не зібратися. А перехід між станами **споживає** старий хендл за значенням, тож повернутися до попереднього стану нема як.

### Кістяк: стан у типі

Ось повний автомат — на Rust, C++ і TypeScript. Транспорт (реальний сокет, UART, TLS-сесія) тут — мінімальна заглушка, щоб приклад компілювався сам собою; уся вага — на типах навколо нього.

:::tabs
```rust
use std::marker::PhantomData;

// Стани протоколу — порожні типи-маркери. Даних нема; сенс лише в імені.
struct Closed;
struct Open;
struct Authed;

// Транспорт — заглушка. У житті тут TcpStream, UART, що завгодно.
struct Wire { peer: String, inbox: Vec<u8> }
impl Wire {
    fn dial(peer: &str) -> Wire { Wire { peer: peer.to_owned(), inbox: Vec::new() } }
    fn put(&mut self, bytes: &[u8]) { let _ = bytes; /* запис у канал */ }
    fn take(&mut self) -> Vec<u8> { std::mem::take(&mut self.inbox) }
}

struct AuthError;

// Хендл, параметризований СТАНОМ S.
// PhantomData<S> «вживає» параметр S, не займаючи ні байта в рантаймі.
struct Conn<S> { wire: Wire, _state: PhantomData<S> }

// Приватний перехід-помічник: перекласти транспорт у хендл іншого стану.
// НЕ pub — тільки методи нижче міняють стан, і лише за протоколом.
impl<S> Conn<S> {
    fn retag<T>(self) -> Conn<T> {
        Conn { wire: self.wire, _state: PhantomData }
    }
}

impl Conn<Closed> {
    fn new(peer: &str) -> Conn<Closed> {
        Conn { wire: Wire::dial(peer), _state: PhantomData }
    }
    fn open(self) -> Conn<Open> { self.retag() }        // Closed → Open
}

impl Conn<Open> {
    // Open → Authed. Споживає self; при відмові з'єднання згортається разом із ним.
    fn authenticate(mut self, key: &str) -> Result<Conn<Authed>, AuthError> {
        self.wire.put(key.as_bytes());
        if key.is_empty() { Err(AuthError) } else { Ok(self.retag()) }
    }
    fn close(self) -> Conn<Closed> { self.retag() }     // Open → Closed
}

impl Conn<Authed> {
    // ЛИШЕ тут. &mut self, а не self: у цьому стані можна слати БАГАТО запитів.
    fn request(&mut self, body: &str) -> Vec<u8> {
        self.wire.put(body.as_bytes());
        self.wire.take()
    }
    fn close(self) -> Conn<Closed> { self.retag() }     // Authed → Closed
}
```
```cpp
#include <string>
#include <vector>
#include <utility>
#include <concepts>

// Стани протоколу — порожні типи-маркери. Даних нема; сенс лише в імені.
struct Closed {};
struct Open   {};
struct Authed {};

// Транспорт — заглушка. У житті тут TCP-сокет, UART, TLS-сесія.
class Wire {
    std::string peer_;
    std::vector<unsigned char> inbox_;
    explicit Wire(std::string peer) : peer_(std::move(peer)) {}
public:
    static Wire dial(const std::string& peer) { return Wire{peer}; }
    void put(const std::string& bytes) { (void)bytes; /* запис у канал */ }
    std::vector<unsigned char> take() { return std::move(inbox_); }
};

// Хендл, параметризований СТАНОМ S. Стан живе лише в типі — поля під нього немає.
template <class S>
class Conn {
    Wire wire_;
    explicit Conn(Wire w) : wire_(std::move(w)) {}
    template <class> friend class Conn;   // переходи бачать приватний конструктор сусіда

public:
    Conn(const Conn&)            = delete;   // копіювати НЕ можна — інакше два живі хендли
    Conn& operator=(const Conn&) = delete;
    Conn(Conn&&)                 = default;  // переміщати — можна
    Conn& operator=(Conn&&)      = default;

    static Conn<Closed> start(const std::string& peer)
        requires std::same_as<S, Closed>
    { return Conn<Closed>{Wire::dial(peer)}; }

    // Closed → Open. `&&` — метод лише на rvalue: викликати можна тільки на
    // переміщеному (std::move) чи тимчасовому хендлі. [[nodiscard]] — новий стан не загубиш.
    [[nodiscard]] Conn<Open> open() &&
        requires std::same_as<S, Closed>
    { return Conn<Open>{std::move(wire_)}; }

    // Open → Authed. Теж &&: перехід споживає хендл.
    [[nodiscard]] Conn<Authed> authenticate(const std::string& key) &&
        requires std::same_as<S, Open>
    { wire_.put(key); return Conn<Authed>{std::move(wire_)}; }

    // ЛИШЕ у Authed. `&`, не &&: у цьому стані шлемо БАГАТО запитів, не споживаючи.
    std::vector<unsigned char> request(const std::string& body) &
        requires std::same_as<S, Authed>
    { wire_.put(body); return wire_.take(); }

    // Authed/Open → Closed. && — теж споживає.
    [[nodiscard]] Conn<Closed> close() &&
        requires (std::same_as<S, Open> || std::same_as<S, Authed>)
    { return Conn<Closed>{std::move(wire_)}; }
};
```
```typescript
type Closed = "closed";
type Open   = "open";
type Authed = "authed";

class Wire {
    private constructor(private readonly peer: string) {}
    static dial(peer: string): Wire { return new Wire(peer); }
    put(bytes: string): void { /* запис у канал */ }
    roundtrip(body: string): Uint8Array { this.put(body); return new Uint8Array(); }
}

class Conn<S extends Closed | Open | Authed> {
    // Фантомне поле: несе стан S у ТИПІ. `declare` — у рантаймі поля немає.
    private declare readonly _state: S;
    private constructor(private readonly wire: Wire) {}

    static start(peer: string): Conn<Closed> { return new Conn(Wire.dial(peer)); }

    // `this: Conn<...>` — параметр this: метод доступний лише в цьому стані.
    open(this: Conn<Closed>): Conn<Open> {
        return this as unknown as Conn<Open>;
    }
    authenticate(this: Conn<Open>, key: string): Conn<Authed> {
        this.wire.put(key);
        return this as unknown as Conn<Authed>;   // ТОЙ САМИЙ об'єкт, лише перетипований
    }
    request(this: Conn<Authed>, body: string): Uint8Array {
        return this.wire.roundtrip(body);
    }
    close(this: Conn<Open> | Conn<Authed>): Conn<Closed> {
        return this as unknown as Conn<Closed>;
    }
}
```

Три речі варто вимовити повільно, бо на них тримається вся гарантія Rust-версії.

**Метод живе на стані, а не на об'єкті.** `request` визначено в `impl Conn<Authed>`, і більше ніде. Тому в типі `Conn<Open>` цього методу фізично немає — не «є, але кине», а немає, як немає в `i32` методу `push`. Виклик `open.request(...)` не збереться. Компілятор диспетчеризує за станом-типом на етапі збірки, і забути перевірку «а ми точно автентифіковані?» неможливо: питання зникло разом із можливістю його поставити не в тому стані.

**Перехід споживає `self`.** `open(self)`, `authenticate(self)`, `close(self)` беруть хендл **за значенням** — Rust переміщує (англ. *move*) його всередину методу. Після `let open = closed.open();` змінна `closed` більше недоступна: її вміст переїхав. Це і є [модель власності](root:sf-lang/rust-ownership) у дії — значення тут **афінні** (англ. *affine*, «вжити не більше одного разу»): перехід поглинає попередній стан, і повернутися до нього нема як. Саме тому «вжити хендл після закриття» неможливо не тому, що ми поставили перевірку, а тому, що `close(self)` **спожив** хендл — його вже нема чим вжити.

**Операція в межах стану лише позичає.** `request(&mut self)` бере хендл **у позику**, не споживаючи, — і тому в стані `Authed` можна слати скільки завгодно запитів поспіль. Ось точна межа: **перехід між станами споживає** (`self`), **робота всередині стану позичає** (`&self` / `&mut self`). Ця різниця в одному символі — і є вся різниця між «змінити стан» і «попрацювати в ньому».

> 🔧 **Навіщо це.** Приватний `retag` — не дрібниця, а замок. Якби він був `pub`, будь-хто зміг би перекинути `Conn<Closed>` одразу в `Conn<Authed>`, оминувши автентифікацію, — і вся гарантія протоколу розсипалась би. [Інкапсуляція](root:sf-apps/encapsulation) тут несе те саме навантаження, що й у класичному інваріанті класу: єдині двері зміни стану — публічні методи-переходи, кожен з яких дотримується протоколу. Приватний помічник лише прибирає дублювання спільної механіки «той самий транспорт, новий ярлик стану».

### Що компілюється, а що ні

Тепер найцікавіше — подивитися на happy-path і на кожну спробу порушити протокол поруч, із точними кодами помилок rustc:

```rust
let closed = Conn::<Closed>::new("device.local:6000");

// closed.request("x");    // E0599: у Conn<Closed> немає методу request
let open = closed.open();  // Closed → Open; closed ПЕРЕМІЩЕНО в open

// closed.open();          // E0382: use of moved value `closed`
// open.request("x");      // E0599: у Conn<Open> ще немає request (не автентифіковані)

let mut authed = open.authenticate("s3cr3t").ok().unwrap();  // Open → Authed; open спожито

// open.close();           // E0382: use of moved value `open`
let _r1 = authed.request("GET /telemetry");   // ✓ лише тут request живе
let _r2 = authed.request("GET /status");      // ✓ &mut self — скільки завгодно разів

let _back = authed.close();  // Authed → Closed; authed спожито
// authed.request("x");     // E0382: use of moved value `authed` — стале після close()
```

Придивись, які саме дві помилки стережуть протокол, бо вони різні за походженням. `E0599` (*no method named ... found*) — це «операція **не існує** в цьому стані»: `request` на `Closed` чи `Open`. `E0382` (*use of moved value*) — це «хендл **спожито**, старим уже не скористаєшся»: повторний `open` на з'їденому `closed`, `close` на з'їденому `open`, `request` на з'їденому `authed`. Перша боронить від **виклику не в тому стані**; друга — від **повторного вжитку старого хендла**. Разом вони закривають увесь простір незаконних послідовностей, і закривають на збірці.

![Дві смуги порівняння. Вгорі Rust: хендл open (сірий, «мертвий») стрілкою authenticate(self) переходить у authed (зелений); підпис — open переміщено, будь-який пізніший виклик open.* дає помилку збірки E0382. Внизу TypeScript: open (живий) стрілкою authenticate() переходить у authed, але той самий об'єкт лише перетиповано; підпис — старий open досі живий, після close() виклик old.request() компілюється й падає в рантаймі](img/affine-move.svg)

*Rust споживає хендл при переході — стале значення стає непридатним, і компілятор ловить будь-яку спробу вжити його (E0382). TypeScript лише перетиповує той самий об'єкт: старий хендл лишається живим, тож повторний вжиток після переходу проходить компіляцію.*

### Механіка: фантом нульового розміру

Що таке `PhantomData<S>` і навіщо він узагалі? Спробуй прибрати його — оголоси `struct Conn<S> { wire: Wire }`. Не збереться:

```text
error[E0392]: parameter `S` is never used
help: consider removing `S`, referring to it in a field,
      or using a marker such as `PhantomData`
```

Rust вимагає, щоб кожен параметр типу десь **використовувався** — інакше компілятор не знав би ні його дисперсії (англ. *variance*), ні як він поводиться при знищенні. Але наш `S` — це `Closed`/`Open`/`Authed`, і **даних** за ним нема: стан живе виключно на рівні типів. `PhantomData<S>` — це і є спосіб сказати «я вживаю `S` лише в системі типів»: маркер, який компілятор зараховує за використання параметра, але який **не займає пам'яті**:

```text
size_of::<PhantomData<Open>>()  == 0     // фантом — тип нульового розміру (ZST)
size_of::<Conn<Open>>()         == size_of::<Wire>()   // ярлик стану не додає нічого
```

Стан-тип не коштує **жодного байта** й **жодної інструкції** в рантаймі. Після мономорфізації (англ. *monomorphization* — коли компілятор підставляє конкретний тип і генерує окремий код) `Conn<Open>`, `Conn<Authed>` і голий `Wire` дають **той самий** машинний код. Ти платиш за безпеку послідовності рівно нічим: уся вона згорає на етапі збірки, лишаючи в бінарнику те саме, що написав би без жодних типів-станів. Це рідкісний випадок, коли строгіша гарантія **безкоштовна**.

### C++ посередині: справжнє переміщення, але стале посилання лишається

C++ дає те, чого TypeScript не має, і не дає того, що має Rust, — тому стоїть рівно між ними. Стан і тут живе в типі: `Conn<Closed>`, `Conn<Open>`, `Conn<Authed>` — той самий шаблон із порожніми типами-маркерами. Операцію прив'язують до стану обмеженням `requires std::same_as<S, Authed>` (C++20): `request` існує лише там, де `S` — це `Authed`, а на `Conn<Open>` обмеження не виконується й методу немає — точно як `E0599` у Rust.

Цікаве починається на переходах — вони позначені **rvalue-кваліфікатором** `&&`. Це означає, що метод можна викликати лише на rvalue: на тимчасовому чи переміщеному хендлі. Тому просто `closed.open()` не збереться, бо `closed` — це lvalue; доводиться написати `std::move(closed).open()`. І ось воно, видиме споживання: `std::move` прямо в тексті каже «я віддаю цей хендл». А заборонена копія (`Conn(const Conn&) = delete`) зачиняє чорний хід — двох живих хендлів на один канал зробити не можна, лише перемістити єдиний. Так C++ доходить ближче до Rust, ніж TypeScript: перехід справді споживає, дублікат неможливий.

Але одна межа лишається. Переміщений об'єкт у C++ **не зникає** — після `std::move` він живе далі, у «спустошеному, але дійсному» стані. Тому старий хендл після переходу **компілюється** й далі:

```cpp
auto open = std::move(closed).open();   // closed переміщено в open
std::move(closed).open();               // ⚠ КОМПІЛЮЄТЬСЯ: closed досі дійсний об'єкт,
                                        //   лише спустошений — баг доживе до рантайму
```

Ось точна різниця з Rust. Rust після переміщення оголошує стару змінну недоступною й ловить будь-який дотик до неї (E0382); C++ такої заборони не має — `std::move` не знищує змінну, а лише дозволяє забрати її нутрощі. Спіймати «вжиток після переміщення» тут може статичний аналізатор (clang-tidy, перевірка `bugprone-use-after-move`), але це **лінтер, а не компілятор** — гарантія слабша на один щабель. Підсумок для C++: виклик не в тому стані — заборонено типом; випадковий дублікат — заборонено видаленою копією; стале посилання після переходу — на совісті дисципліни чи лінтера, як і в TypeScript.

### Той самий автомат у TypeScript — і чому гарантія слабша

TypeScript теж уміє тримати стан у типі. Фантомний параметр `S` тут — рядковий літерал (`"open"`), «вжитий» приватним полем `declare readonly _state: S`, а операцію прив'язують до стану через **параметр `this`**: метод із сигнатурою `request(this: Conn<Authed>, ...)` можна викликати лише там, де компілятор **знає**, що отримувач — саме `Conn<Authed>`. Це справді ловить виклик не в тому стані:

```typescript
const open = Conn.start("device.local:6000").open();   // Conn<Open>

open.request("x");    // ✗ упіймано: 'this' типу Conn<Open> не пасує до Conn<Authed>

const authed = open.authenticate("s3cr3t");            // Conn<Authed>
authed.request("GET /telemetry");                      // ✓ у правильному стані — можна
```

Поки що все як у Rust. Але тут ховається діра, і чесно її показати важливіше, ніж красиво замовчати. Rust при переході **споживає** хендл; TypeScript не має чим спожити — у нього немає ні move, ні афінних типів. Тому `authenticate()` повертає **той самий об'єкт**, лише перетипований (`this as unknown as Conn<Authed>`). Старий хендл лишається живим і придатним — і компілятор не знає, що ним уже не можна користуватися:

```typescript
const closed = authed.close();   // Conn<Closed> — але це ТОЙ САМИЙ об'єкт у пам'яті

authed.request("stale");         // ⚠ КОМПІЛЮЄТЬСЯ: authed усе ще Conn<Authed>,
                                 //   хоча канал уже закрито — баг доживе до рантайму
```

Ось точна межа гарантії без афінних типів: TypeScript **боронить від виклику операції не в тому стані** (структурно: у `Conn<Open>` немає доступу до `request`), але **не боронить від повторного вжитку застарілого хендла** після переходу чи закриття. Щоб заборонити «вжити після того, як спожили», потрібна саме [власність із переміщенням](root:sf-lang/rust-ownership) — а її TypeScript не має. Практичний висновок не «TypeScript не годиться», а «знай, докуди сягає його гарантія»: він знімає більшу частину помилок послідовності, але останній їх різновид — стале посилання — лишається на совісті дисципліни, як і без типостану.

> 🔧 **Навіщо це.** Та сама межа проходить через Java, Python, Go — усюди, де об'єкт живе далі після «переходу», а мова не вміє відібрати старий шлях до значення. C++ (вище) підходить близько — `&&`-методи справді споживають, видалена копія боронить від дубліката, — але без статичної заборони на стале посилання; у Swift для того ж є `consuming`-параметри. Правило просте: сила типостану впирається в те, чи вміє мова **знищити старий шлях до значення**. Rust вміє за замовчуванням — тому типостан у ньому ідіоматичний; решта мов дають слабшу, хоч і корисну версію.

## Задача 2. Будівник з обов'язковими полями

**Задача.** Будівник HTTP-запиту (англ. *builder* — об'єкт, що поступово накопичує поля й наприкінці збирає ціль). URL і метод — **обов'язкові**, заголовки — ні. Наївний будівник тримає все в `Option`-полях, а `send()` перевіряє їх у рантаймі й **панікує**, якщо URL забули. Тобто «зібрати запит без URL» знову **записується** й падає в клієнта. Треба зробити так, щоб методу `send()` **не існувало**, поки не задано обидва обов'язкові поля.

**Ідея.** Той самий типостан, лише стан тепер — не «фаза з'єднання», а «які обов'язкові поля вже задано». Заведемо два маркери, `Missing` і `Set`, і два фантомні параметри: `RequestBuilder<U, M>`, де `U` каже про URL, `M` — про метод. `url(...)` переводить `U` з `Missing` у `Set`, `method(...)` — `M`. А `send()` визначимо **лише** на `RequestBuilder<Set, Set>` — коли обидва задано.

```rust
use std::marker::PhantomData;

struct Missing;   // поле ще не задано
struct Set;       // поле задано

struct RequestBuilder<U, M> {
    url: Option<String>,
    method: Option<String>,
    headers: Vec<(String, String)>,
    _u: PhantomData<U>,
    _m: PhantomData<M>,
}

impl RequestBuilder<Missing, Missing> {
    fn new() -> Self {
        RequestBuilder { url: None, method: None, headers: Vec::new(),
                         _u: PhantomData, _m: PhantomData }
    }
}

// url() існує, ЛИШЕ поки URL іще Missing: переставити двічі не вийде.
// M лишаємо яким був — метод це не чіпає.
impl<M> RequestBuilder<Missing, M> {
    fn url(self, u: &str) -> RequestBuilder<Set, M> {
        RequestBuilder { url: Some(u.to_owned()), method: self.method,
                         headers: self.headers, _u: PhantomData, _m: PhantomData }
    }
}

impl<U> RequestBuilder<U, Missing> {
    fn method(self, m: &str) -> RequestBuilder<U, Set> {
        RequestBuilder { url: self.url, method: Some(m.to_owned()),
                         headers: self.headers, _u: PhantomData, _m: PhantomData }
    }
}

// Необов'язкові поля доступні В БУДЬ-ЯКОМУ стані — прапорців не міняють.
impl<U, M> RequestBuilder<U, M> {
    fn header(mut self, k: &str, v: &str) -> Self {
        self.headers.push((k.to_owned(), v.to_owned()));
        self
    }
}

// send() існує ЛИШЕ у вершині <Set, Set>.
impl RequestBuilder<Set, Set> {
    fn send(self) -> String {
        let url = self.url.unwrap();        // <Set, _> — доказ, що тут Some
        let method = self.method.unwrap();  // <_, Set> — доказ, що тут Some
        format!("{method} {url} [{} заголовків]", self.headers.len())
    }
}
```

Використання читається як звичайний ланцюжок, а компілятор мовчки стереже, що ланцюжок повний:

```rust
let resp = RequestBuilder::new()
    .method("GET")
    .url("https://api.dev/v1/ping")
    .header("Accept", "application/json")
    .send();                              // ✓ обидва обов'язкові задано

// RequestBuilder::new().send();               // E0599: send нема на <Missing, Missing>
// RequestBuilder::new().url("u").send();      // E0599: send нема на <Set, Missing>
// RequestBuilder::new().method("GET").send(); // E0599: send нема на <Missing, Set>
```

![Ґратка 2×2 станів будівника RequestBuilder⟨U, M⟩: у лівому-нижньому кутку ⟨Missing, Missing⟩ (старт new()), стрілка url() веде праворуч у ⟨Set, Missing⟩, стрілка method() веде вгору у ⟨Missing, Set⟩; обидві стрілки сходяться у правому-верхньому ⟨Set, Set⟩ — єдиному вузлі, де send() доступний (зелений). У трьох інших вузлах send() немає](img/builder-lattice.svg)

*Кожне обов'язкове поле — окрема вісь. url() рухає по одній, method() — по іншій; send() відмикається лише у вершині, де обидві осі дійшли до Set. Порядок виклику вільний, а «зібрати без обов'язкового поля» просто не має методу.*

Один рядок вартий чесного пояснення — `self.url.unwrap()` усередині `send`. Хіба ми не повернулися до небезпечного розгортання `Option`? Ні, і різниця тут тонка, але принципова. `Option` — це **сховище** значення; параметр типу `<Set, Set>` — це **доказ на етапі збірки**, що сховище не порожнє. `send()` фізично неможливо викликати, поки тип не `<Set, Set>`, а в цей тип неможливо потрапити, не пройшовши `url()` і `method()`, кожен з яких кладе `Some`. Тож `unwrap` тут не «сподіваюся, там щось є», а «тип уже довів, що там `Some`». Це і є шов між компіляцією і рантаймом: значення лежить у рантаймі, а свідчення про його наявність несе тип. (Хто хоче зняти навіть цей `unwrap`, зберігає обов'язкові поля прямо в параметрах-типах — `U` стає або `()`, або самим `String`; так робить бібліотечний підхід *typed-builder*, але ціною складнішого кістяка.)

> 🔧 **Навіщо це.** Це найдорожчий різновид типостану в щоденному коді. `HttpRequest`, у якого `send()` панікує через забутий URL; транзакція, у якій `commit()` без жодної операції; майстер налаштування, де «Далі» доступне до заповнення кроку, — усе це «обов'язкове поле не задано», і всюди типостан прибирає помилку **до першого користувача**: вона гине на збірці розробника, а не в проді. Кожне обов'язкове поле стає окремою віссю стану, і `send`/`commit`/`finish` відмикається лише в спільній вершині.

Помітна й закономірність про ціну. Два обов'язкові поля дали **два** незалежні параметри-типи й ґратку 2×2. Спокусливо злякатися вибуху, але порахуймо чесно:

```text
наївно (окремий тип на кожну комбінацію):  2ᵏ типів
незалежні фантом-параметри:                 k параметрів
```

Параметри **незалежні**, тож `k` обов'язкових полів коштують `k` параметрів, а не 2ᵏ окремих типів — зростання лінійне, і патерн масштабується. Але за це платять інакше: підписи розповзаються (`RequestBuilder<Set, Missing>` у кожному проміжному типі), і повідомлення компілятора довшають. Саме тут починається розмова про межу.

## Складність і пастки

Типостан дає рівно те, що обіцяв: незаконна послідовність не існує як програма. Але сила приходить не задарма, і зрілість — тримати в голові весь список гострих кутів.

**Стан лише в рантаймі — відступ до `enum`.** Типостан вимагає, щоб послідовність була відома **статично, у коді**. Щойно стан вирішують **дані** — байт із дроту, прапорець із конфіга, — обрати тип статично неможливо:

```rust
// НЕ компілюється: гілки дають РІЗНІ типи, а if мусить повернути один.
let conn = if config.secure {
    open.authenticate(&key)?   // тип Conn<Authed>
} else {
    open                       // тип Conn<Open>
};                             // error[E0308]: `if` and `else` have incompatible types
```

Ліки — стягнути обидва статичні типи в **один рантаймний** через `enum`, лишивши одну чесну перевірку переходу на межі:

```rust
enum Link { Open(Conn<Open>), Authed(Conn<Authed>) }

fn from_config(secure: bool, key: &str, c: Conn<Open>) -> Link {
    if secure {
        c.authenticate(key).map(Link::Authed).unwrap_or_else(|_| todo!())
    } else {
        Link::Open(c)
    }
}
// далі — match по Link; гілка Authed має request, гілка Open — ні.
```

Типостан сяє, коли протокол зашитий у **код**; коли він приходить із **даних**, чесніший компроміс — рантаймний `enum` із перевіркою на межі, а не спроба протягнути невідомий стан на рівень типів.

**Вибух сигнатур.** Коли станів багато, а переходів іще більше, типи розростаються в довгі параметризовані підписи. Функція, що приймає «будь-який будівник», мусить бути родовою — `fn tweak<U, M>(b: RequestBuilder<U, M>) -> ...`; а якщо покласти типостан-значення в **поле структури**, стан **запікається** в тип цієї структури, і вона теж стає параметризованою. Пом'якшити можна: псевдоніми типів (`type FreshBuilder = RequestBuilder<Missing, Missing>`), запечатані трейти (англ. *sealed trait*), щоб згрупувати стани, і сувора ощадливість на числі станів-типів. Але за певною межею — понад три-чотири стани або коли стани множаться — ціна читабельності переважує виграш безпеки, і чесніший вибір — рантаймний `enum`.

**Читабельність помилок компілятора.** Тут багато залежить від того, **як** ти закодував стан. Власні методи на конкретних станах-типах (як наш `request` в `impl Conn<Authed>`) дають ясну помилку: `no method named `request` found for struct `Conn<Open>`` — видно і що, і де. А от кодування через межі трейтів (`fn request<S: Authenticated>(...)`) породжує туманне `the trait bound `Open: Authenticated` is not satisfied`, з якого початківець не одразу зрозуміє, що просто рано слати. Відколи стабілізувався атрибут `#[diagnostic::on_unimplemented]` (Rust 1.78, травень 2024), для таких випадків можна почепити на маркер-трейт власний людський текст помилки — «спершу викличте authenticate()». Правило: віддавай перевагу власним методам на конкретних станах (ясні помилки) перед трейт-гімнастикою (туманні), а де без трейтів не обійтися — став `#[diagnostic::on_unimplemented]`.

**Афінне, а не лінійне: тип не змусить закрити.** Rust афінний («вжити **не більше** одного разу»), а не лінійний («вжити **рівно** один раз»). Тому хендл `Conn<Open>` можна просто **впустити** (англ. *drop*), не викликавши `close()`, — типи цього не заборонять. Автозакриття роблять через `Drop` (RAII — звільнення прив'язане до знищення):

```rust
impl<S> Drop for Conn<S> {
    fn drop(&mut self) { /* hangup(): закрити канал автоматично */ }
}
```

Але тут чатує тонка пастка, про яку варто знати заздалегідь. Щойно додаси `impl Drop`, попередній `retag` **перестане компілюватися**:

```text
error[E0509]: cannot move out of type `Conn<S>`, which implements the `Drop` trait
```

Rust не дає «розібрати» на частини тип із власним деструктором, бо це лишило б напівзруйнований об'єкт. Обхід — не рухати поле напряму, а тримати транспорт в `Option<Wire>` і забирати його через `.take()`, або скористатися `ManuallyDrop`. Це реальний конфлікт двох бажань — «споживати при переході» і «автозакривати при знищенні», — і вирішувати його доводиться свідомо; згадуй про нього, тільки-но чіпляєш `Drop` на типостан-хендл.

**Ціна в рантаймі — нульова, і це головний козир.** На відміну від багатьох захисних прийомів, типостан не коштує ні пам'яті, ні швидкодії: фантом — тип нульового розміру, стан згорає на компіляції, бінарник тотожний нетипізованому. Це не абстрактна теорія — так побудовані реальні бібліотеки. Драйвери периферії в екосистемі `embedded-hal` кодують **режим ніжки** мікроконтролера в параметрі типу (`Input<Floating>`, `Output<PushPull>`) із запечатаними трейтами й переходами `into_input`/`into_output`, тож «записати в ніжку, налаштовану на вхід» **не компілюється** — а в прошивку лягає той самий код, що й без типів. Це задокументований патерн (розділ про GPIO в «The Embedded Rust Book»).

**Міра.** Дзеркально до [YAGNI](root:sf-apps/dry-kiss-yagni), тест простий: **назви конкретну помилку, від якої типостан захищає**. Можеш назвати — «слали в закрите з'єднання», «зібрали запит без URL», «зробили commit порожньої транзакції» — і послідовність часта та дорога — прийом вартий заходу. Не можеш («ну… раптом хтось… колись…») — це церемонія, і простий рантаймний прапорець чесніший. Типостан коштує ясності підписів; плати цю ціну там, де «не в тому порядку» — реальний і болючий баг.

Підсумок римується з першою задачею й ширшою розмовою про типи. Сума-тип заморожує законні **дані** — «рівно один із випадків». Типостан заморожує законний **порядок** — «рівно ця послідовність операцій». Прийом один і той самий: **узяти знання, що інакше жило б у коментарі чи в дисципліні — „слати можна лише після автентифікації", „URL обов'язковий" — і вкласти його в тип**, щоб про нього дбав компілятор. Коментар бреше мовчки, тільки-но хтось поряд змінить код; тип не збреше ніколи, бо його перевіряють на кожній збірці. І компілятор із бюрократа, що рахує байти, перетворюється на невтомного рецензента твого **протоколу** — а не лише твоїх даних.
