# 🔌 Порівняння C4 з UML, 4+1 архітектурними видами та ArchiMate

У проєктуванні програмних систем існує кілька конкуруючих методологій опису архітектури. Щоб обрати правильний інструмент під конкретну задачу, архітектор повинен розуміти, чим модель C4 відрізняється від класичного стандарту UML, моделі «4+1» Філіпа Крахтена та корпоративної мови моделювання ArchiMate.

---

## 1. Концептуальна основа та метамодель

Головна відмінність між підходами полягає в тому, як саме структуруються архітектурні проєкції (види): за **рівнями ієрархічного наближення (масштабу)** чи за **ортогональними аспектами системи**.

### Модель 4+1 (Kruchten 4+1 View Model)
Модель 4+1 пропонує чотири ортогональні проєкції на ту саму систему під різними кутами зору:
- **Логічний вид (Logical):** що система робить на рівні об'єктів та бізнес-доменів.
- **Вид процесів (Process):** які процеси/потоки виконуються одночасно і як вони синхронізуються.
- **Вид розгортання (Physical):** на яких серверах і мережевих сегментах запускаються програми.
- **Вид розробки (Development):** як вихідний код структурований у репозиторіях і модулях.
- **Сценарії (+1 Scenarios):** варіанти використання (Use Cases), що пов'язують усі чотири види разом.

*Особливість:* 4+1 не задає глибину наближення всередині окремого виду. Логічний вид може одночасно містити загальний доменний модуль і дрібний допоміжний клас.

### Модель C4
C4 організована як **ієрархічна піраміда масштабування (zoom levels)**:
- Рівень 1 (Context) розкривається у Рівень 2 (Containers).
- Рівень 2 (Containers) розкривається у Рівень 3 (Components).
- Рівень 3 (Components) розкривається у Рівень 4 (Code).

*Особливість:* C4 не є ортогональною декомпозицією. Це вкладена матрьошка: кожен наступний рівень є прямим збільшенням (зумом) конкретного елемента з попереднього рівня. Додаткові види (Deployment і Dynamic) доповнюють ієрархію розгортанням і часовою динамікою.

### UML (Unified Modeling Language)
UML пропонує 14 фіксованих типів діаграм, розділених на структурні (Class, Component, Deployment, Package, Object тощо) та поведінкові (Sequence, Activity, State Machine, Use Case тощо).
- *Особливість:* UML зосереджений на точній формальній типізації об'єктних структур (множинність зв'язків `1..*`, типи видимості `+`, `#`, `-`, види поліморфізму).

### ArchiMate (Стандарт The Open Group)
ArchiMate — це високорівнева мова моделювання корпоративної архітектури (Enterprise Architecture). Вона охоплює три горизонтальні шари:
- **Бізнес-шар (Business Layer):** бізнес-процеси, ролі, послуги та цілі організації.
- **Шар застосунків (Application Layer):** інформаційні системи, компоненти та інтерфейси.
- **Технологічний шар (Technology Layer):** сервери, мережі, хмарні ресурси, сховища.

## 2. Порівняльна таблиця характеристик

| Критерій | C4 Model | UML 2.x | Kruchten 4+1 | ArchiMate 3.x |
| :--- | :--- | :--- | :--- | :--- |
| **Основна парадигма** | Ієрархічний масштаб (Zoom in/out) | Формальна ООП типізація | Ортогональні проєкції | Багатошарова Enterprise-архітектура |
| **Кількість базових понять** | 4 (Person, System, Container, Component) | Понад 50 (метакласи, стереотипи, зв'язки) | 4 види + сценарії | Понад 60 сутностей і зв'язків |
| **Поріг входження для розробника** | Мінімальний (15 хвилин) | Високий (тижні вивчення нотації) | Середній (потребує розуміння точок зору) | Дуже високий (сертифікація TOGAF/ArchiMate) |
| **Моделювання мікросервісів і протоколів** | Ідеальне (контейнери + обов'язковий протокол у зв'язках) | Посереднє (через стереотипи компонентів) | Добре (через Process + Physical View) | Добре (через Application + Technology Layer) |
| **Підтримка «Архітектури як код»** | Рідна (Structurizr DSL, LikeC4, C4-PlantUML) | Обмежена (PlantUML підмножина) | Низька (зазвичай графічні документи) | Низька (Archi, XML Open Exchange) |
| **Цільова аудиторія** | Інженери, архітектори, бізнес-стейкхолдери | Розробники ПЗ, системні аналітики | Системні архітектори, інтегратори | Корпоративні архітектори (Enterprise Architects), CIO |

## 3. Детальний аналіз відмінностей

### Семантика зв'язків та протоколів
У класичному UML стрілка між двома класами чи компонентами позначає або асоціацію, або залежність компіляції (`dependency`). У розподілених системах, де вузли спілкуються через ненадійну мережу за допомогою HTTP, gRPC чи Kafka, UML не надає простого вбудованого способу позначити:
- Синхронний це чи асинхронний виклик.
- Який мережевий протокол і серіалізація використовуються (`JSON/HTTPS`, `gRPC/Protobuf`, `AMQP`).
- Яку дію ініціює запит.

У C4 позначення протоколу та дієслова є обов'язковим правилом метамоделі (`[JSON/HTTPS]`, `[SQL/TCP]`). Без протоколу зв'язок вважається неповним.

### Рівень абстракцій
- **ArchiMate** ідеально підходить для моделювання рівня всього банку або холдингу (як бізнес-процес «Оформлення кредиту» виконується через CRM-систему, яка спирається на сервери в дата-центрі). Але він занадто абстрактний для щоденної роботи продуктової команди розробників: у ньому складно показати внутрішні модулі конкретного Go-мікросервісу.
- **UML** навпаки: ідеально підходить для опису складних патернів усередині коду (патерн «Міст», поліморфна ієрархія класів, переходи станів у state machine), але погано масштабується на рівень взаємодії хмарних сервісів.
- **C4** займає золоту середину: покриває рівні від системного ландшафту (L1) до окремого кодового модуля (L3/L4), надаючи інженерам зрозумілу мову спілкування.

```

               └──────────────────────┬───────────────────────┘
                                      │
         ┌────────────────────────────┼────────────────────────────┐
         │                            │                            │
 ┌───────▼────────┐           ┌───────▼────────┐           ┌───────▼────────┐
 │ Корпоративна   │           │ Розподілені    │           │ Детальний      │
 │ трансформація  │           │ сервіси, хмари │           │ алгоритм,      │
 │ великої фірми  │           │ та веб-системи │           │ патерн у коді  │
 └───────┬────────┘           └───────┬────────┘           └───────┬────────┘
         │                            │                            │
 ┌───────▼────────┐           ┌───────▼────────┐           ┌───────▼────────┐
 │   ArchiMate    │           │   C4 Model     │           │   UML Class /  │
 │  (Enterprise)  │           │ (Structurizr)  │           │ Sequence Diagr │
 └────────────────┘           └────────────────┘           └────────────────┘
```

1. **Обирайте C4**, якщо ви розробляєте сучасні розподілені системи, мікросервіси, веб- чи мобільні платформи, і вам потрібна жива, легко підтримувана документація як код, зрозуміла всій команді.
2. **Обирайте ArchiMate**, якщо ви працюєте корпоративним архітектором у великій організації з сотнями застарілих систем (Legacy), бізнес-департаментами та суворим регуляторним контролем (TOGAF).
3. **Обирайте окремі діаграми UML (Sequence / State Machine)**, якщо вам необхідно задокументувати математично точний порядок викликів методів у пам'яті або алгоритм багатопотокової синхронізації, який неможливо адекватно описати спрощеною стрілкою.
