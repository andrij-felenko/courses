# ⚙️ Оформлення замовлення за одними дверима — робочий рефакторинг

Стаття показала фасад оформлення в найчистішому вигляді: чотири рядки, кожен кличе свій сервіс, порядок замкнено в одному методі. Але той код чесний рівно доти, доки все йде добре. У житті все добре не йде: товар розкуповують саме в ту мить, коли ти клацнув «Купити»; картку відхиляють; поштовий сервер лежить. І щойно ми впустимо в фасад збої, спливе питання, від якого залежить, чи це взагалі фасад: **що робити з уже зробленими кроками, коли черговий крок упав?** Ти вже зарезервував останній товар на складі — а платіж не пройшов. Резерв висить. Товар нікому не дістанеться, бо для складу він «продан», хоча грошей ніхто не отримав.

Розберімо цей рефакторинг до кінця — з реальним кодом, який компілюється й працює, з обробкою збоїв і **відкотом резерву**, коли платіж провалився. Дорогою зробимо дві речі, яких стаття лише торкнулася. По-перше, **виміряємо зчеплення** клієнта числом — до фасаду й після — щоб «менше залежностей» перестало бути гаслом і стало цифрою. По-друге, знайдемо ту межу, за якою фасад із тонких дверей перетворюється на **божественний об'єкт**, і покажемо її не на словах, а на конкретному рядку коду, який цю межу переступає.

## Підсистема: чотири сервіси, кожен зі своїм болем

Спершу — сама підсистема, яку фасад ховатиме. Це чотири незалежні служби, і кожна вміє одне своє. Жодна не знає про решту й не знає про фасад — це важливо, бо саме тому фасадів над ними може бути скільки завгодно, і саме тому кожну можна тестувати окремо.

:::tabs
```ts
// ── Підсистема: чотири служби, кожна робить одне й нічого не знає про сусідів ──

interface CartItem { sku: string; qty: number; price: number; }
interface Cart     { items: CartItem[]; total: number; email: string; }
interface Card     { token: string; }

class OutOfStockError extends Error {}
class PaymentDeclinedError extends Error {}

// 1. Склад: резервує товар і вміє резерв ЗНЯТИ (це стане ключем до відкоту)
class InventoryService {
  reserve(items: CartItem[]): ReservationId {
    for (const it of items) {
      if (!this.hasStock(it.sku, it.qty))
        throw new OutOfStockError(`Немає ${it.qty}× ${it.sku}`);
    }
    return this.hold(items);          // повертає розписку про резерв
  }
  release(id: ReservationId): void { /* повертає товар на полицю */ }

  private hasStock(sku: string, qty: number): boolean { /* ... */ return true; }
  private hold(items: CartItem[]): ReservationId { /* ... */ return "res_1" as ReservationId; }
}

// 2. Платіж: списує гроші; може відхилити картку
class PaymentGateway {
  charge(card: Card, amount: number): Charge {
    const ok = this.callProvider(card.token, amount);   // зовнішній API банку
    if (!ok) throw new PaymentDeclinedError("Картку відхилено");
    return { id: `chg_${Date.now()}`, amount };
  }
  refund(chargeId: string): void { /* повертає гроші, теж компенсація */ }

  private callProvider(token: string, amount: number): boolean { /* ... */ return true; }
}

// 3. Сховище замовлень: створює й зберігає запис замовлення
class OrderRepository {
  create(cart: Cart, chargeId: string): Order {
    return { id: `ord_${Date.now()}`, cart, chargeId, status: "paid" };
  }
}

// 4. Пошта: шле листи; НЕ критична — її збій не має валити замовлення
class EmailService {
  sendConfirmation(order: Order): void { /* SMTP, може бути недоступний */ }
}

type ReservationId = string & { readonly brand: unique symbol };
interface Charge { id: string; amount: number; }
interface Order  { id: string; cart: Cart; chargeId: string; status: string; }
```

Придивись до двох деталей у цій підсистемі — вони вирішать усе далі. Перша: `InventoryService` має не лише `reserve`, а й **`release`** — метод, що знімає резерв. Друга: `PaymentGateway` має не лише `charge`, а й **`refund`**. Ці парні методи — не прикраса. Це те, чим ми відкочуватимемо зроблене, коли черговий крок упаде. Без них відкіт неможливий, і фасад був би приречений лишати систему в перекошеному стані.

## Як живе клієнт БЕЗ фасаду — і скільки він знає

Тепер уяви, що фасаду немає, і всю послідовність тримає сам веб-контролер — той код, що обробляє POST на `/checkout`. Він мусить власноруч і в правильному порядку смикати чотири служби, та ще й сам розрулювати збої.

:::tabs
```ts
// БЕЗ фасаду: контролер сам знає всі 4 служби, порядок і відкіт
class CheckoutController {
  constructor(
    private inventory: InventoryService,   // залежність 1
    private payments: PaymentGateway,      // залежність 2
    private orders: OrderRepository,       // залежність 3
    private mailer: EmailService,          // залежність 4
  ) {}

  handlePost(cart: Cart, card: Card): Response {
    let reservation: ReservationId | null = null;
    try {
      reservation = this.inventory.reserve(cart.items);          // крок 1
      const charge = this.payments.charge(card, cart.total);     // крок 2
      const order  = this.orders.create(cart, charge.id);        // крок 3
      try { this.mailer.sendConfirmation(order); }               // крок 4
      catch { /* лист не критичний — ковтаємо */ }
      return Response.ok(order.id);
    } catch (e) {
      if (reservation) this.inventory.release(reservation);      // відкіт!
      if (e instanceof OutOfStockError)      return Response.conflict("Розкупили");
      if (e instanceof PaymentDeclinedError) return Response.paymentRequired("Відхилено");
      throw e;
    }
  }
}
```

```py
# БЕЗ фасаду: контролер сам знає всі 4 служби, порядок і відкіт
class CheckoutController:
    def __init__(self, inventory, payments, orders, mailer):
        self._inventory = inventory       # залежність 1
        self._payments = payments         # залежність 2
        self._orders = orders             # залежність 3
        self._mailer = mailer             # залежність 4

    def handle_post(self, cart: Cart, card: Card) -> "Response":
        reservation = None
        try:
            reservation = self._inventory.reserve(cart.items)         # крок 1
            charge = self._payments.charge(card, cart.total)          # крок 2
            order = self._orders.create(cart, charge.id)              # крок 3
            try:
                self._mailer.send_confirmation(order)                 # крок 4
            except Exception:
                pass                        # лист не критичний — ковтаємо
            return Response.ok(order.id)
        except OutOfStockError:
            if reservation:
                self._inventory.release(reservation)                  # відкіт!
            return Response.conflict("Розкупили")
        except PaymentDeclinedError:
            if reservation:
                self._inventory.release(reservation)                  # відкіт!
            return Response.payment_required("Відхилено")
```
:::

Зупинися й полічи, що знає цей контролер. Він тримає **чотири** посилання на служби. Він знає, що резерв іде **перед** платежем, платіж **перед** записом, лист **останнім**. Він знає, що при падінні треба **зняти резерв**. І знає, які саме винятки котра служба кидає, щоб перекласти їх у правильні HTTP-відповіді. Це не одна відповідальність — це п'ять переплетених знань про чужі нутрощі, зшиті в одному методі веб-шару.

А тепер найгірше: це не єдине місце, де оформлюють замовлення. Той самий сценарій знадобиться в адмінці (оператор оформлює за клієнта), у мобільному API, у фоновому обробнику відкладених кошиків. **Кожне** з цих місць муситиме повторити ту саму четвірку залежностей, той самий порядок, той самий відкіт. Змінилося правило — скажімо, додали крок «нарахувати бонуси» між платежем і записом — правити доведеться **скрізь**, і десь неминуче забудуть.

## Фасад, що вміє відкочувати

Тепер стягнемо все це за одні двері. Фасад забирає собі і чотири залежності, і порядок, і — головне — **логіку відкоту**. Клієнт більше не знатиме нічого з цього.

:::tabs
```ts
// Фасад: тримає підсистему, порядок і відкіт. Клієнт не знає нічого з цього.
class CheckoutFacade {
  constructor(
    private inventory: InventoryService,
    private payments: PaymentGateway,
    private orders: OrderRepository,
    private mailer: EmailService,
  ) {}

  placeOrder(cart: Cart, card: Card): OrderResult {
    // Крок 1: резерв. Якщо тут упало — відкочувати ще нічого, просто виходимо.
    let reservation: ReservationId;
    try {
      reservation = this.inventory.reserve(cart.items);
    } catch (e) {
      if (e instanceof OutOfStockError) return { ok: false, reason: "out_of_stock" };
      throw e;
    }

    // Крок 2: платіж. Якщо ВІН упав — резерв уже висить: ЗНІМАЄМО його (компенсація).
    let charge: Charge;
    try {
      charge = this.payments.charge(card, cart.total);
    } catch (e) {
      this.inventory.release(reservation);            // ← відкіт кроку 1
      if (e instanceof PaymentDeclinedError) return { ok: false, reason: "declined" };
      throw e;
    }

    // Крок 3: запис замовлення. Якщо впав — треба зняти І резерв, І платіж.
    let order: Order;
    try {
      order = this.orders.create(cart, charge.id);
    } catch (e) {
      this.payments.refund(charge.id);                // ← відкіт кроку 2
      this.inventory.release(reservation);            // ← відкіт кроку 1
      throw e;                                         // це вже наша вина, не клієнтова
    }

    // Крок 4: лист. НЕ критичний — його збій не валить замовлення й не відкочує.
    try { this.mailer.sendConfirmation(order); }
    catch { /* залогувати й забути: гроші взято, товар зарезервовано, запис є */ }

    return { ok: true, orderId: order.id };
  }
}

type OrderResult =
  | { ok: true;  orderId: string }
  | { ok: false; reason: "out_of_stock" | "declined" };
```
```py
# Фасад: тримає підсистему, порядок і відкіт. Клієнт не знає нічого з цього.
class CheckoutFacade:
    def __init__(self, inventory, payments, orders, mailer):
        self._inventory = inventory
        self._payments = payments
        self._orders = orders
        self._mailer = mailer

    def place_order(self, cart: Cart, card: Card) -> "OrderResult":
        # Крок 1: резерв. Якщо тут упало — відкочувати ще нічого, просто виходимо.
        try:
            reservation = self._inventory.reserve(cart.items)
        except OutOfStockError:
            return OrderResult(ok=False, reason="out_of_stock")

        # Крок 2: платіж. Якщо ВІН упав — резерв уже висить: ЗНІМАЄМО (компенсація).
        try:
            charge = self._payments.charge(card, cart.total)
        except PaymentDeclinedError:
            self._inventory.release(reservation)          # ← відкіт кроку 1
            return OrderResult(ok=False, reason="declined")

        # Крок 3: запис замовлення. Якщо впав — знімаємо І резерв, І платіж.
        try:
            order = self._orders.create(cart, charge.id)
        except Exception:
            self._payments.refund(charge.id)              # ← відкіт кроку 2
            self._inventory.release(reservation)          # ← відкіт кроку 1
            raise                                         # це вже наша вина, не клієнтова

        # Крок 4: лист. НЕ критичний — його збій не валить замовлення й не відкочує.
        try:
            self._mailer.send_confirmation(order)
        except Exception:
            pass          # залогувати й забути: гроші взято, товар є, запис є

        return OrderResult(ok=True, order_id=order.id)


@dataclass
class OrderResult:
    ok: bool
    order_id: str | None = None
    reason: str | None = None
```

Оце вже фасад, який витримує реальність. Але перш ніж радіти, чесно спитаймо: чи не порушили ми головне правило — «фасад делегує, не вирішує»? Тут же тепер є логіка: try, catch, `release`, `refund`. Хіба це не «рішення»? Розберімо це прямо, бо тут проходить найтонша межа патерну.

## Чому відкіт — це все ще делегування, а не рішення

Ключ у тому, **що саме** робить фасад у блоках обробки збою. Придивись: він не рахує суму повернення, не вирішує, скільки грошей віддати, не змінює стан складу власними руками. Він робить рівно одне — **кличе назад ту саму підсистему**: `inventory.release`, `payments.refund`. Уся справжня робота — і зняти резерв, і повернути гроші — лежить **у службах**. Фасад лише знає **послідовність компенсації**: якщо крок N упав, треба відкликати кроки N−1, N−2, … у зворотному порядку, і кожне відкликання — це знову виклик служби.

Ось тут і криється точна межа. Порядок кроків та їхніх компенсацій — це **знання про підсистему**, не бізнес-рішення. «Резерв іде перед платежем; якщо платіж упав, резерв знімається» — це факт про те, **як влаштована ця конкретна кухня**, рівно того ж ґатунку, що й «буфер створюють перед кодеком» у відеоприкладі. Фасаду **можна й треба** тримати такий порядок — заради нього фасад часто й ставлять. А от чого фасаду **не можна** — це почати ухвалювати рішення, що **належать бізнесу**, а не топології викликів.

> 🔧 **Навіщо це.** Проведи межу так: якщо код у фасаді описує **послідовність і зв'язки викликів підсистеми** (що за чим, що чим відкотити) — це делегування, місце йому тут. Якщо код починає описувати **бізнес-правило** — скільки нарахувати знижки, чи давати кредит цьому клієнту, як порахувати податок — це рішення, і йому тут не місце, навіть якщо синтаксично це такий самий `if`. Один `if` перекладає виняток підсистеми у відповідь — добре. Інший `if` рахує лояльнісну знижку — це вже не двері, це початок божественного об'єкта. Різниця не в кількості рядків, а в тому, **чиє** це знання: підсистеми чи предметної області.

Формально те, що ми написали, — це навіть не імпровізація, а відомий взірець. Послідовність кроків, кожен з яких має свою компенсацію на випадок відкоту, у 1987 році назвали **сагою** (англ. *saga*): Гектор Гарсія-Моліна (Hector Garcia-Molina) і Кеннет Салем (Kenneth Salem) описали її в статті «Sagas» на конференції ACM SIGMOD того року. Їхня центральна ідея — та сама, що в нас: замість одної великої незламної транзакції взяти **ланцюг дрібних кроків**, а на випадок збою мати для кожного кроку **компенсаційну дію**, яка семантично його скасовує (не обов'язково повертаючи все точнісінько як було — товар на полицю повернувся, але, скажімо, лічильник переглядів уже не відкотиш). Це **усталений факт** — першоджерело, а не переказ. Наш `release` — компенсація для `reserve`, наш `refund` — компенсація для `charge`. Фасад тут якраз і є те місце, де сагу зручно скласти: він знає порядок кроків, отже, знає й зворотний порядок компенсацій.

*Кожен крок має компенсацію — дію, що семантично скасовує зроблене. Коли крок падає, фасад відкликає всі попередні кроки у зворотному порядку: платіж не пройшов — знімається резерв; запис не вдався — повертаються і гроші, і резерв. Лист некритичний: його збій не відкочує нічого, бо гроші вже взято, а товар зарезервовано.*

Зверни увагу ще на одну навмисну асиметрію в коді — вона теж не бізнес-рішення, а класифікація збоїв за наслідком. Збій **резерву** й збій **платежу** — це нормальні, очікувані відповіді клієнту: «розкупили», «картку відхилено». Фасад повертає їх як спокійний результат `{ ok: false, reason }`, бо це не поломка — це законний хід подій. А от збій **запису замовлення** — це вже наша, серверна поломка (база лягла), тому фасад **не ковтає** її, а прокидає виняток нагору, попередньо відкотивши гроші й резерв. І збій **листа** взагалі не чіпає результату: замовлення відбулося, лист — приємний додаток, його відсутність не варта того, щоб скасовувати оплачену покупку. Ці три різні реакції — теж знання про підсистему (котрий крок наскільки критичний), а не про предметну область.

## Вимірюємо зчеплення: 4 проти 1

Тепер обіцяне число. «Фасад зрізає зчеплення» — приємно звучить, але поки це не цифра, це віра. Візьмімо просту, конкретну міру: **скільки різних типів підсистеми згадано в клієнтському модулі**. Це і є пряме структурне зчеплення клієнта з підсистемою — по одному ребру залежності на кожен тип, який клієнт мусить назвати, імпортувати, сконструювати чи впіймати.

Порахуймо чесно, по іменах, для контролера **без фасаду**:

```
Зчеплення контролера БЕЗ фасаду (типи підсистеми, названі в його коді):
  InventoryService      — конструктор, reserve(), release()
  PaymentGateway        — конструктор, charge()
  OrderRepository       — конструктор, create()
  EmailService          — конструктор, sendConfirmation()
  OutOfStockError       — catch і розбір
  PaymentDeclinedError  — catch і розбір
  ─────────────────────────────────────────────
  Разом: 6 типів підсистеми, з якими зчеплений клієнт
         + знання порядку 4 кроків
         + знання логіки відкоту (коли й що release)
```

А тепер той самий контролер **із фасадом**:

:::tabs
```ts
// ІЗ фасадом: контролер знає РІВНО ОДИН тип підсистеми — сам фасад
class CheckoutController {
  constructor(private checkout: CheckoutFacade) {}   // єдина залежність

  handlePost(cart: Cart, card: Card): Response {
    const result = this.checkout.placeOrder(cart, card);
    if (result.ok) return Response.ok(result.orderId);
    switch (result.reason) {
      case "out_of_stock": return Response.conflict("Розкупили");
      case "declined":     return Response.paymentRequired("Відхилено");
    }
  }
}
```
```py

class CheckoutController:
    def __init__(self, checkout: CheckoutFacade):
        self._checkout = checkout        # єдина залежність

    def handle_post(self, cart: Cart, card: Card) -> "Response":
```

```
Зчеплення контролера ІЗ фасадом:
  CheckoutFacade        — конструктор, placeOrder()
  ─────────────────────────────────────────────
  Разом: 1 тип підсистеми
```

Число впало з **6 до 1**. Але цифра «типів» — лише верхівка; справжня економія глибша, і її варто назвати окремо, бо саме вона окупає фасад. Зникли не тільки п'ять імпортів. Зникло **знання порядку** (що резерв перед платежем) і **знання відкоту** (що при збої платежу треба зняти резерв) — а це знання куди підступніше за просте посилання на тип. Тип, який ти забув імпортувати, тобі не скомпілюється; а порядок кроків, який ти переплутав, скомпілюється чудово й вибухне лише в проді, на реальних грошах. Фасад забирає саме **найтендітніший** різновид зчеплення — той, що компілятор не ловить.

І поміряй ще один вимір — **вартість зміни**. Додаємо новий крок: між платежем і записом треба нарахувати бонусні бали через `LoyaltyService`. Без фасаду цей крок (і його компенсацію на випадок відкоту) дописуєш у **кожному** місці оформлення — контролер, адмінка, мобільний API, фоновий обробник. Із фасадом — у **одному** методі `placeOrder`, а всі клієнти навіть не дізнаються, що ланцюг подовшав. Ось де фасад повертає вкладене: не так у момент написання, як у момент **першої зміни**, і тим більше — кожної наступної.

![Порівняння двох стовпчиків-барів. Лівий високий стовпчик підписаний БЕЗ фасаду: 6 типів підсистеми плюс знання порядку плюс знання відкоту, і все це помножене на кількість місць оформлення. Правий низький стовпчик підписаний ІЗ фасадом: 1 тип, нуль знання порядку, нуль знання відкоту, в одному місці. Візуально видно різницю висоти — багато проти одного](img/coupling-before-after.svg)

*Зчеплення клієнта з підсистемою до фасаду й після. Падає не лише число названих типів (6 → 1), а й невидиме зчеплення — знання порядку кроків і логіки відкоту, найтендітніше, бо його не ловить компілятор. І це зчеплення множиться на кожне місце, де оформлюють замовлення: фасад збирає його в одну точку.*

## Де двері стають божественним об'єктом

Найважливіша частина — про межу. Фасад оформлення живе на **найнебезпечнішому місці** застосунку: через нього тече кожна покупка, тобто гроші. Такі місця притягують код, як магніт. «Тут же вже все проходить — доклею й знижку сюди». За рік це «доклею» перетворює тонкі двері на монстра. Покажімо цей сповз конкретно, рядок за рядком, щоб межу було видно на дотик.

Ось **здоровий** фасад — він делегує:

```
placeOrder:
  inventory.reserve(...)        // кличе службу
  payments.charge(...)          // кличе службу
  orders.create(...)            // кличе службу
  mailer.sendConfirmation(...)  // кличе службу
  + порядок і компенсації       // знання про підсистему — ще ОК
```

А ось як він **гниє** — кожен доданий рядок сам собою здається розумним, і саме тому пастка спрацьовує:

:::tabs
```ts
placeOrder(cart: Cart, card: Card): OrderResult {
  // ✗ рахує знижку — це БІЗНЕС-рішення, а не виклик підсистеми
  if (cart.total > 1000) cart.total *= 0.9;

  // ✗ вирішує, чи давати клієнтові кредит — знову бізнес-правило
  if (this.isVip(cart.email) && cart.total < this.creditLimit(cart.email)) { /* ... */ }

  // ✗ сам рахує податок за таблицею регіонів — предметна логіка
  const tax = cart.total * this.taxRateFor(cart.region);

  // ✗ веде власний стан — лічильник, кеш, історія
  this.ordersToday++;
  this.recentCarts.push(cart);

  // ...і десь тут, поміж усім цим, ще й ті чотири виклики служб
}
```
```py
def place_order(self, cart: Cart, card: Card) -> "OrderResult":
    # ✗ рахує знижку — це БІЗНЕС-рішення, а не виклик підсистеми
    if cart.total > 1000:
        cart.total *= 0.9

    # ✗ вирішує, чи давати клієнтові кредит — знову бізнес-правило
    if self._is_vip(cart.email) and cart.total < self._credit_limit(cart.email):
        ...

    # ✗ сам рахує податок за таблицею регіонів — предметна логіка
    tax = cart.total * self._tax_rate_for(cart.region)

    # ✗ веде власний стан — лічильник, кеш, історія
    self._orders_today += 1
    self._recent_carts.append(cart)

    # ...і десь тут, поміж усім цим, ще й ті чотири виклики служб
```

Кожен з цих рядків окремо звучить безневинно. Але разом вони переродили клас. Тепер `CheckoutFacade` **знижку рахує**, **кредит вирішує**, **податок обчислює**, **стан веде** — і десь між усім цим ще й кличе чотири служби. Це вже не двері. Це **[божественний об'єкт](root:sf-apps/anti-patterns)** — клас, крізь який тече й рішення, і стан, і вся логіка, і від якого тепер залежить усе. Спробуй тепер його протестувати: кожен тест мусить підняти всю чотирьохсервісну підсистему **плюс** підсунути VIP-статус, кредитний ліміт, податкову таблицю. Спробуй перевикористати логіку знижки деінде — не вийде, вона замурована в оформленні. Двері, які мали **зменшувати** зчеплення, самі стали найзчепленішою точкою системи.

Ознака переродження — точна, її легко перевірити на рев'ю: **у фасаді з'явився власний стан (`ordersToday`, `recentCarts`) або власне обчислення бізнес-величини (знижка, податок, кредит)**. Чисті двері не мають ні пам'яті, ні власних рішень предметної області — вони лише впускають і складають порядок викликів. Щойно бачиш у фасаді поле, що переживає виклик, або формулу, що рахує **предметну** величину, — фасад переростає себе.

> 🔧 **Навіщо це.** Куди ж діти знижку, податок і кредит, якщо не у фасад? У **саму підсистему** — це нові служби. Знижка → `PricingService`, податок → `TaxService`, кредит → рішення `CreditService`. Тоді фасад лишається тонким і робить те, що вміє найкраще: **складає їх у правильному порядку**. `placeOrder` кличе `pricing.applyDiscounts(cart)`, потім `tax.compute(cart)`, потім свою звичну четвірку — і жодного власного обчислення в ньому нема. Правило-рятівник просте: **коли кортить дописати логіку у фасад, спитай — це нова служба підсистеми чи справді робота фасаду?** Майже завжди це нова служба. Фасад тоді росте вшир (кличе на одну службу більше), але не вглиб (не бере на себе її розум). Вшир фасад може рости скільки завгодно; тонким його тримає те, що він **не думає** — лише диригує.

Так замикається коло цього рефакторингу. Ми взяли чотири служби й крихкий порядок, стягли їх за одні двері, навчили ці двері переживати збої й відкочувати зроблене, поміряли, як зчеплення клієнта впало з шести до одного, і провели межу, за якою двері перестають бути дверима. Головне з усього — одне речення, яке варто забрати з собою: **фасад коштує стільки, скільки коштує тонкий клас, що лише диригує; щойно він починає сам думати — рахувати, вирішувати, пам'ятати — він перестає окупатися й починає коштувати як god object.**
