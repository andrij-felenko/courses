# Фасад

<preknowlist>
- [Інтерфейс проти реалізації](topic:sf-apps/interface-vs-implementation) — різниця між тим, ЩО модуль обіцяє назовні, і тим, ЯК він це робить усередині; фасад — це навмисно вузьке «що», за яким ховається широке «як».
- [Зчеплення і зв'язність](topic:sf-apps/coupling-cohesion) — мірило «наскільки міцно частини зрощені»; фасад беруть саме для того, щоб зрізати зчеплення клієнта з нутрощами підсистеми.
- [Закон Деметри](topic:sf-apps/law-of-demeter) — «розмовляй лише з безпосередніми сусідами, не лізь через них углиб»; фасад — це той сусід, з яким клієнт розмовляє замість того, щоб тягтися до кожної внутрішньої частини.
</preknowlist>

Уяви, що тобі треба конвертувати відео з одного формату в інший, а під рукою — потужна бібліотека, яка це вміє. Ти відкриваєш її й бачиш не одну функцію «конвертуй», а два десятки класів: окремо кодек, окремо демультиплексор, окремо буфер кадрів, окремо аудіодоріжка, окремо контейнер-обгортка, окремо запис на диск. Щоб просто перегнати `.mp4` у `.avi`, ти мусиш створити сім об'єктів, знати, який з них кличеться першим, який другим, що чому передати й у якому порядку закрити. Твоя проста задача — один рядок за змістом — розтяглася на півсотні рядків, у кожному з яких можна помилитися.

І біда не лише в обсязі. Тепер твій код **знає всю внутрішню кухню** цієї бібліотеки. Змінять вони порядок ініціалізації буфера — твій код зламається. Перейменують клас кодека — доведеться правити в тебе. Ти прив'язав себе не до задачі «конвертуй відео», а до конкретного устрою чужих нутрощів. Це зчеплення, якого ти зовсім не хотів, і воно розповзеться по всіх місцях, де ти цю бібліотеку викликаєш.

Фасад — це патерн, придуманий рівно проти цього болю. Ідея до образливого проста: постав перед складною підсистемою **одні прості двері** й пусти всіх ходити тільки через них. Розберімося, чому ці двері коштують так мало, а економлять так багато, чим фасад відрізняється від сусідів, на яких він схожий, і — обов'язково — де його ставити не варто.

## Одні двері замість павутиння

Повернімося до відеобібліотеки й подивимось, що робить фасад. Ми не чіпаємо саму бібліотеку — вона лишається як є, з усіма своїми двадцятьма класами. Ми лише пишемо **один новий клас**, чия єдина робота — сховати за собою типову послідовність:

:::tabs
```ts
// Фасад: один простий метод ховає весь порядок роботи підсистеми
class VideoConverter {
  convert(filename: string, targetFormat: string): File {
    const file = new VideoFile(filename);
    const sourceCodec = new CodecFactory().extract(file);
    const targetCodec = targetFormat === "mp4"
      ? new MPEG4Codec() : new OggCodec();

    const buffer = BitrateReader.read(file, sourceCodec);
    let result = BitrateReader.convert(buffer, targetCodec);
    result = new AudioMixer().fix(result);

    return new File(result);   // клієнт про все це не знає
  }
}

// Уся робота клієнта тепер — один рядок:
const mp4 = new VideoConverter().convert("holiday.ogg", "mp4");
```
```py
# Фасад: один простий метод ховає весь порядок роботи підсистеми
class VideoConverter:
    def convert(self, filename: str, target_format: str) -> "File":
        file = VideoFile(filename)
        source_codec = CodecFactory().extract(file)
        target_codec = MPEG4Codec() if target_format == "mp4" else OggCodec()

        buffer = BitrateReader.read(file, source_codec)
        result = BitrateReader.convert(buffer, target_codec)
        result = AudioMixer().fix(result)

        return File(result)      # клієнт про все це не знає


# Уся робота клієнта тепер — один рядок:
mp4 = VideoConverter().convert("holiday.ogg", "mp4")
```
:::

Оце й є фасад — цілком. Ніякої магії, ніяких хитрих механізмів: звичайний клас, який усередині робить ту саму нудну послідовність викликів, що її раніше мусив писати кожен клієнт, а назовні показує один осмислений метод. Уся складність нікуди не зникла — вона **лишилась**, просто переїхала за двері, у місце, куди більше нікому не треба зазирати.

Дивись, що змінилося для того, хто конвертує відео. Раніше він тримав у голові сім класів і порядок їхніх викликів; тепер — одну назву `convert`. Раніше його код мав сім точок, у яких він зчеплений із нутрощами бібліотеки; тепер — одну. І якщо бібліотека завтра перебудує свою кухню, зламається **лише фасад** — одне місце, яке ти виправиш раз, а всі клієнти навіть не помітять, що щось трусонуло.

![Ліворуч без фасаду: клієнт тягне окрему лінію-залежність до кожної з чотирьох частин підсистеми — кодека, аудіо, тари, файлів — і мусить знати порядок. Праворуч із фасадом: клієнт має одну лінію до фасаду, а вже фасад тримає лінії до частин; порядок і зв'язки сховано в ньому](img/before-after.svg)

*Без фасаду клієнт знає всі частини й порядок їхніх викликів — стільки залежностей, скільки частин. Фасад стягує все в одну точку входу: у клієнта лишається одна залежність, а нова внутрішня частина потребує правки лише у фасаді.*

> 🔧 **Навіщо це.** Найяскравіше цінність фасаду видно, коли підсистема — **чужа бібліотека чи зовнішній сервіс**, який ти не контролюєш. Розкидати прямі виклики платіжного шлюзу по двадцятьох місцях коду — значить прив'язати весь застосунок до конкретного постачальника: захочеш поміняти його — переписуватимеш двадцять місць. Один фасад `Payments` над цим API робить постачальника змінним у **одному** файлі. Фасад — це найдешевший спосіб не дати чужому коду розлитися по всьому твоєму.

## Що фасад дає — і чого він НЕ робить

Тут криється найтонше місце патерну, яке варто проговорити прямо, бо його часто розуміють неправильно.

Фасад **не додає нової поведінки**. Він не вміє нічого, чого не вміла б сама підсистема, — він лише складає докупи виклики того, що вже є. Це принципова риса: якщо ти ловиш себе на тому, що фасад починає **сам** щось обчислювати, ухвалювати бізнес-рішення чи зберігати стан, — це вже не фасад, а щось інше, що переросло свою роль. Чисті двері нічого не виробляють; вони лише впускають.

Друга, ще важливіша риса: фасад **не замуровує** підсистему. Він ставить зручний вхід, але не забирає в тебе прямий доступ до внутрішніх частин. Це двері в стіні, а не глуха стіна. Дев'яносто дев'ять клієнтів зі ста ходитимуть крізь фасад, бо їм досить типового сценарію. Але той сотий, якому треба тонко покрутити рідкісне налаштування кодека, якого фасад не виставляє, — усе одно дотягнеться до потрібного класу підсистеми напряму. Фасад — це **зручність за замовчуванням, а не в'язниця**.

![Велика рамка підсистеми з п'ятьма частинами всередині: кодек, аудіо, тара, буфери, метадані. На межі підсистеми стоїть фасад — прості двері. Звичайний клієнт входить крізь фасад стрілкою, а фасад веде стрілки вглиб до кількох частин. Окремий тонкий клієнт іде стрілкою напряму до внутрішньої частини, повз фасад](img/door-not-wall.svg)

*Фасад — двері, а не мур. Звичайний клієнт іде крізь фасад і не знає нутрощів; але хто справді мусить тонко налаштувати рідкісну частину — усе одно дістає її напряму. Фасад спрощує типовий шлях, не забороняючи винятковий.*

Ця відкритість — не недогляд, а свідома риса. Якби фасад замуровував підсистему, він рано чи пізно почав би **заважати**: кожен рідкісний випадок вимагав би розширювати сам фасад новим методом, і той розпух би до велетня, що знову виставляє півсотні операцій — тобто перетворився б на ту саму складність, від якої ми тікали. Лишаючи прямий доступ відкритим, фасад тримає себе **маленьким**: у ньому живуть лише часті сценарії, а рідкісні йдуть повз.

І ще одна асиметрія, яку легко проґавити: **підсистема не знає про фасад**. Класи всередині нічого не підозрюють про те, що зверху хтось поставив зручні двері; вони працюють однаково, є той фасад чи ні. Залежність тут строго однобічна — фасад знає підсистему, підсистема фасад не знає. Тому фасадів над однією підсистемою може бути **кілька різних**: один — для типової конвертації, другий — для пакетної обробки сотень файлів, третій — для попереднього перегляду. Кожен виставляє свій зручний зріз тієї самої кухні, і жоден не заважає іншим.

## Порядок теж ховається у фасаді

Спрощення інтерфейсу — це половина користі. Друга половина, яку легко недооцінити, — фасад ховає **знання про порядок і зв'язки**.

У живій підсистемі частини майже ніколи не незалежні: буфер треба створити **до** кодека, аудіо звести **після** відео, ресурси закрити у **зворотному** порядку до відкриття. Це знання — «що за чим» — саме по собі є складністю, і без фасаду воно розповзається по кожному клієнту. Кожен, хто користується підсистемою, мусить пам'ятати правильну послідовність, а забуде — дістане тонку помилку, яку важко зловити.

Фасад забирає цю пам'ять собі. Правильний порядок записаний у ньому **один раз**, і клієнт фізично не може його порушити — він же не бачить окремих кроків, лише результат. Це та сама вигода, що й зі спрощенням інтерфейсу, але про інший вимір складності: не «скільки частин», а «в якій послідовності їх смикати». Часто саме це — головна причина ставити фасад: не так поменшити кількість викликів, як **замкнути крихкий порядок** у надійному місці.

Візьмімо приклад, ближчий до звичайного бекенду, ніж відеокодеки, — оформлення замовлення в інтернет-крамниці. За одним натиском «Купити» стоїть чіткий, але крихкий ланцюжок: перевір наявність товару, зарезервуй його, спиши гроші, створи запис замовлення, надішли лист. Порядок тут не декоративний — не можна списати гроші раніше, ніж переконався в наявності, і не варто слати лист про успіх, поки платіж не пройшов.

:::tabs
```ts
// Фасад над підсистемою оформлення: складає крихкий порядок в один метод
class CheckoutFacade {
  constructor(
    private inventory: InventoryService,
    private payments: PaymentGateway,
    private orders: OrderRepository,
    private mailer: EmailService,
  ) {}

  placeOrder(cart: Cart, card: Card): OrderId {
    // порядок кроків — крихкий, і він захований ТУТ, а не в клієнті
    this.inventory.reserve(cart.items);          // 1. спершу резерв
    const charge = this.payments.charge(card, cart.total);  // 2. тоді гроші
    const order = this.orders.create(cart, charge.id);       // 3. запис
    this.mailer.sendConfirmation(order);          // 4. і лише тепер лист
    return order.id;
  }
}

// Клієнт (веб-контролер) не знає ні кроків, ні їхнього порядку:
const id = checkout.placeOrder(cart, card);
```

Веб-контролер, що обробляє натиск кнопки, тепер не тримає в голові ні чотирьох сервісів, ні їхньої послідовності — він каже `placeOrder` і все. А правильний порядок замкнено у фасаді, у місці, куди дивишся, коли думаєш саме про оформлення замовлення. Розгорнутий розбір цього рефакторингу — з обробкою збоїв, відкотом резерву при невдалому платежі й вимірюванням зчеплення до і після — винесено в [окремий приклад-проєкт](topic:sf-apps/facade/proj-facade-checkout.md).

## Сусіди, на яких фасад схожий

Фасад легко сплутати з кількома патернами, бо всі вони **стоять між клієнтом і чимось іншим**. Різниця не в тому, де вони стоять, а **навіщо**. Проговоримо трьох найближчих сусідів — це той рідкісний випадок, коли межа між патернами справді плутає людей на співбесідах і рев'ю.

**Адаптер** теж обгортає щось і теж дає інший інтерфейс — але його мета не спростити, а **перекласти**. Адаптер існує тоді, коли в тебе вже є очікуваний інтерфейс (наприклад, твій код усюди працює з `PaymentProcessor`), а під рукою — клас із **несумісним** інтерфейсом (чужа бібліотека з методом `makeTransaction` замість твого `pay`). Адаптер перекладає чуже на очікуване, один-в-один, не спрощуючи. Фасад же не має «очікуваного інтерфейсу», під який підганяє, — він **вигадує новий, простіший**, якого раніше не існувало, над цілою купою класів. Коротко: [адаптер](topic:sf-apps/adapter) міняє форму інтерфейсу під наявний контракт; фасад створює новий зручний контракт над складністю.

**Посередник** (англ. *Mediator*) теж стягує спілкування в одну точку — але дивиться в інший бік. Фасад стоїть **між клієнтом і підсистемою** й дбає про те, як підсистему кличуть **ззовні**; напрям однобічний — клієнт кличе фасад, фасад кличе частини. Посередник стоїть **між самими частинами** й дбає про те, як вони спілкуються **між собою**: замість того щоб кожна частина знала й смикала всі інші, вони всі звертаються до центра, а він розводить сигнали. Фасад **не втручається** у те, як частини підсистеми говорять одна з одною (вони й далі роблять це напряму); посередник саме для цього й існує. Тому фасад — структурний патерн (про форму доступу), а [посередник](topic:sf-apps/mediator) — поведінковий (про розподіл спілкування).

**Проксі** теж підставляє себе замість об'єкта — але зберігає **той самий інтерфейс**, а вставляється, щоб непомітно щось додати: кеш, перевірку прав, лінивість, лічильник викликів. [Проксі](topic:sf-apps/proxy) прикидається оригіналом; фасад і не думає ним прикидатися — він навмисно виглядає **інакше** й простіше, ніж усе, що за ним.

![Три колонки-порівняння. Фасад: дієслово СПРОСТИТИ, багато частин зводить до простих дверей, структурний, однобічно клієнт до підсистеми. Адаптер: дієслово ПЕРЕКЛАСТИ, чужий інтерфейс на очікуваний, зазвичай одна обгортка, структурний. Посередник: дієслово РОЗВ'ЯЗАТИ, частини спілкуються через центр, поведінковий, двобічно частини й центр](img/three-neighbors.svg)

*Усі троє стоять між клієнтом і рештою, тому й плутаються. Вирішує мета: фасад спрощує доступ до підсистеми ззовні, адаптер перекладає один несумісний інтерфейс, посередник розв'язує спілкування частин між собою.*

## Коли фасад — зайвий шар

Патерн, який так легко поставити, легко й **переставити** — а фасад цим особливо грішить, бо здається завжди доречним. Тож чесно про те, коли він лише додає ваги.

Найперше: якщо підсистема **вже проста**, фасад над нею — це порожня обгортка, яка тільки додає ще один клас і ще один рівень непрямості ні за що. Один клас із трьома зрозумілими методами не потребує фасаду — фасад над ним лише змусить читача стрибати через зайвий файл, щоб дійти до справжньої логіки. Фасад окупається рівно тоді, коли за ним **справжня складність**: багато частин, крихкий порядок, чужий інтерфейс. Немає складності — немає й що ховати.

Друга пастка тонша: фасад, який непомітно перестав бути фасадом. Починається невинно — двері над підсистемою. Потім у нього дописують «трошки логіки»: тут перевірку, там обчислення знижки, отут ще кеш. За півроку це вже не двері, а [божественний об'єкт](topic:sf-apps/anti-patterns) — клас, крізь який тече вся програма, знає й уміє геть усе й тримається на ньому весь застосунок. Ознака, що фасад переріс себе: у нього з'явився **власний стан** і **власні рішення**, а не лише переадресація викликів. Здоровий фасад лишається тонким: він **делегує**, а не **вирішує**.

Практичне правило-фільтр: постав фасад тоді, коли типовий сценарій роботи з підсистемою повторюється в багатьох місцях і тягне за собою знання нутрощів. Якщо сценарій один-єдиний, або підсистема й так тривіальна, або те, що кортить сховати, — насправді бізнес-рішення, а не послідовність викликів, — фасад тут не рятує, а маскує. Найкращий фасад той, після появи якого клієнтський код став коротшим і **дурнішим** (у доброму сенсі — знає менше), а не той, що просто додав ще одну назву в систему.

## Звідки взявся фасад

Назву патерн узяв просто й точно з **архітектури будівель**: фасад (фр. *façade*, від італ. *facciata* — «лице», зрештою від лат. *facies* — «обличчя») — це парадна лицьова стіна дому. Вона показує охайне, задумане обличчя, за яким ховається вся інженерія — труби, проводка, несучі балки. Метафора лягає ідеально: програмний фасад так само показує чисте «лице» підсистеми, лишаючи її нутрощі за стіною.

Як **іменований патерн** фасад канонізувала «банда чотирьох» (англ. *Gang of Four*) — Еріх Гамма, Річард Гелм, Ральф Джонсон і Джон Вліссідс — у книзі 1994 року «Design Patterns: Elements of Reusable Object-Oriented Software». Вони віднесли його до **структурних** патернів і сформулювали намір гранично чітко: «дати уніфікований інтерфейс до набору інтерфейсів у підсистемі; фасад визначає інтерфейс вищого рівня, що робить підсистему простішою у використанні». Це усталений факт — точне формулювання з першоджерела, а не переказ.

Класичний приклад, яким GoF пояснювали патерн, показовий сам по собі: **підсистема компілятора**. Усередині компілятор — це десятки класів (лексер, парсер, генератор коду, оптимізатор, таблиці символів), і для написання власного інструмента вся ця машинерія іноді потрібна в подробицях. Але переважній більшості користувачів треба одне: «скомпілюй ось цей файл». Тому над усією підсистемою ставлять клас `Compiler` з єдиним методом `compile(source)` — фасад, що ховає весь конвеєр за одним викликом, лишаючи знавцям доступ до внутрішніх фаз напряму. Як і чому патерн визрів саме в цьому колі задач, і чому «фасад» виявився серед 23 патернів одним із найпростіших для розуміння, — розгорнуто в [нотатці про народження патерну](topic:sf-apps/facade/hist-facade-origin.md).

Проста ідея — але саме через простоту фасад лишається одним із найчастіше вживаних патернів у справжньому коді, часто навіть тоді, коли пишуть його інтуїтивно, не знаючи назви. Щоразу, коли хтось ховає складну послідовність чужих викликів за одним осмисленим методом, він робить фасад — і тепер має для цього слово.
