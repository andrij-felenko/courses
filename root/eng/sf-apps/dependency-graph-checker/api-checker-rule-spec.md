# 📋 Специфікація мови правил та конфігурації чекера залежностей

У цій специфікації визначено контракт мови конфігурації архітектурних правил, схему файлу базового боргу (храповика), інтерфейс командного рядка (CLI) та формати машинозчитуваних звітів статичного аналізатора графа залежностей.

Специфікація розроблена як технологічно нейтральний стандарт опису архітектури як коду (Architecture-as-Code). Вона однаково застосовується як для аналізу внутрішньої структури монолітних застосунків (пакети, шари, простори імен), так і для валідації мережевих взаємодій у мікросервісних розподілених системах (OpenAPI-специфікації, контракти gRPC/Protobuf, виклики через шину повідомлень).

## 1. Схема та семантика конфігураційного файлу (arch-rules.yaml)

Головний файл конфігурації `arch-rules.yaml` розміщується в корені репозиторію проєкту або передається через прапорець командного рядка. Він містить чотири обов'язкові декларативні секції:

```yaml
version: "1.0"

# 1. Горизонтальні архітектурні шари (ієрархія рівнів)
layers:
  - name: "presentation"
    order: 3
    description: "Шар взаємодії з користувачем та зовнішніми клієнтами"
    match:
      - "src/api/**"
      - "src/controllers/**"
      - "src/grpc/**"

  - name: "application"
    order: 2
    description: "Сервіси оркестрації, сценарії використання та обробники команд"
    match:
      - "src/services/**"
      - "src/workflows/**"
      - "src/handlers/**"

  - name: "domain"
    order: 1
    description: "Чисте доменне ядро: сутності, бізнес-правила та інтерфейси портів"
    match:
      - "src/domain/**"
      - "src/entities/**"
      - "src/policies/**"

  - name: "infrastructure"
    order: 0
    description: "Адаптери баз даних, мережеві клієнти, черги повідомлень та сторонні SDK"
    match:
      - "src/infrastructure/**"
      - "src/db/**"
      - "src/clients/**"

# 2. Вертикальні зрізи / Обмежені контексти (Bounded Contexts)
slices:
  - name: "ordering"
    match: "src/**/ordering/**"
    public_api: "src/domain/ordering/public/**"
    description: "Контекст оформлення та обробки замовлень"

  - name: "billing"
    match: "src/**/billing/**"
    public_api: "src/domain/billing/public/**"
    description: "Контекст платежів, балансів та фінансових транзакцій"

  - name: "inventory"
    match: "src/**/inventory/**"
    public_api: "src/domain/inventory/public/**"
    description: "Контекст управління складськими залишками та резервуванням"

# 3. Набір обов'язкових архітектурних правил
rules:
  # Правило 1: Глобальна заборона циклічних залежностей
  - id: "R01-NO-CYCLES"
    type: "acyclic"
    scope: "global"
    severity: "error"
    description: "Граф залежностей між усіма модулями зобов'язаний бути ациклічним (DAG)"

  # Правило 2: Шарова ієрархія та матриця дозволених переходів
  - id: "R02-STRICT-LAYERING"
    type: "layer_hierarchy"
    allowed_transitions:
      presentation: ["application", "domain"]
      application: ["domain", "infrastructure"]
      domain: []  # Доменне ядро повністю ізольоване від зовнішнього світу
      infrastructure: ["domain"]
    severity: "error"
    description: "Дозволені залежності лише від вищих шарів до нижчих або до інтерфейсів домену"

  # Правило 3: Ізоляція контекстів через публічний інтерфейс
  - id: "R03-CONTEXT-ENCAPSULATION"
    type: "slice_isolation"
    enforce_public_api: true
    severity: "error"
    description: "Міжконтекстна взаємодія дозволена виключно через публічні контракти (public_api)"

# 4. Налаштування механізму архітектурного храповика
ratchet:
  enabled: true
  baseline_file: ".arch-baseline.json"
  fail_on_new_violations: true
  auto_update_on_reduction: true
```

### Деталізація семантики та правил парсингу:

1. **Секція `layers` (Горизонтальні шари):**
   - `name` (рядок): унікальне ім'я шару, що використовується як ідентифікатор у звітах та матрицях переходів;
   - `order` (невід'ємне ціле число): числовий ранг ієрархії. Ранг визначає напрямок дозволеного потоку керування. За замовчуванням система вимагає, щоб будь-яка залежність була спрямована від вищого рангу до нижчого або рівного (`order(джерело) >= order(ціль)`). Зворотна залежність від меншого рангу до більшого вважається дефектом архітектурної інверсії;
   - `match` (масив шаблонів шляхів): набір стандартних glob-патернів. Символ `*` відповідає будь-яким символам у межах одного сегмента шляху, а `**` відповідає довільній кількості вкладених каталогів. Якщо файл підпадає під шаблони кількох шарів одночасно, перевагу має шар із найбільш специфічним (довшим) шляхом.

2. **Секція `slices` (Вертикальні доменні зрізи):**
   - Дозволяє розбити кодову базу на ізольовані бізнес-модулі (Bounded Contexts відповідно до принципів предметно-орієнтованого проєктування DDD);
   - `public_api` (glob-патерн): вказує точне розташування експортованих типів, структур даних та інтерфейсів. Будь-який імпорт із приватних каталогів іншого зрізу (наприклад, пряме підключення внутрішніх сутностей чи допоміжних утиліт) трактується як порушення інкапсуляції міжконтекстної межі.

3. **Секція `rules` (Декларація інваріантів):**
   - `id` (рядок): унікальний стабільний код правила для формування звітів та фільтрації винятків;
   - `type` (перелік): тип аналітичної перевірки:
     - `acyclic`: виконання алгоритму Тар'яна для пошуку сильно зв'язаних компонентів графа розміром більше одиниці;
     - `layer_hierarchy`: перевірка ребер на відповідність матриці дозволених переходів `allowed_transitions`;
     - `slice_isolation`: валідація інкапсуляції між зрізами з перевіркою публічних точок входу;
     - `deny_direct`: пряма заборона будь-яких зв'язків між двома конкретно вказаними модулями чи пакетами;
   - `severity` (перелік `error`, `warning`, `info`): рівень критичності порушення. Збірка в CI завершується аварійно лише за наявності дефектів із рівнем `error`.

4. **Секція `ratchet` (Керування храповиком):**
   - `enabled` (булевий): увімкнення режиму порівняння з базовим знімком боргу;
   - `baseline_file` (рядок): відносний шлях до файлу стану технічного боргу;
   - `fail_on_new_violations` (булевий): блокувати збірку, якщо поточний pull request створює хоча б одне нове порушення, відсутнє у базовому файлі;
   - `auto_update_on_reduction` (булевий): автоматично перезаписувати базовий файл під час проходження збірки в головній гілці (main/master), якщо загальна кількість зафіксованих дефектів зменшилася.

## 2. Специфікація файлу базового боргу (.arch-baseline.json)

Файл `.arch-baseline.json` генерується автоматично командою `record-baseline` і зберігається у системі контролю версій Git. Він фіксує існуючий технічний борг спадкової системи, дозволяючи команді безперервно розробляти нову функціональність без блокування старих дефектів.

Для забезпечення стабільності знімка під час звичайних змін у коді (додавання порожніх рядків чи форматування) кожне порушення ідентифікується стабільним криптографічним відбитком (Fingerprint), який обчислюється як хеш від кортежу: `SHA256(rule_id + from_file + to_file + target_symbol)`. Номер рядка зберігається суто для довідки і не впливає на порівняння відбитків.

```json
{
  "version": "1.0",
  "generated_at": "2026-08-20T12:00:00Z",
  "git_commit": "a1b2c3d4e5f67890",
  "total_violations": 2,
  "violations": [
    {
      "rule_id": "R02-STRICT-LAYERING",
      "fingerprint": "e9b4c81a2f304d5e123456789abcdef0",
      "from_file": "src/domain/ordering/order.go",
      "to_file": "src/infrastructure/db/postgres.go",
      "symbol": "postgres.OrderRepository",
      "line": 42
    },
    {
      "rule_id": "R01-NO-CYCLES",
      "fingerprint": "f8a1c73b9d02e411aabbccddeeff0011",
      "cycle_nodes": [
        "src/services/billing",
        "src/services/shipping",
        "src/services/billing"
      ]
    }
  ]
}
```

## 3. Контракт інтерфейсу командного рядка (CLI)

Аналізатор розповсюджується як автономний виконуваний бінарний файл або контейнерний образ для інтеграції в конвеєри CI/CD:

```bash
depgraph-check [КОМАНДА] [ОПЦІЇ]
```

### Команди:

1. `check` (команда за замовчуванням):
   - Сканує вихідний код проєкту, будує повний граф імпортів та викликів;
   - Перевіряє всі активні правила проти конфігурації `arch-rules.yaml`;
   - Порівнює виявлені дефекти з файлом `.arch-baseline.json`;
   - Завершується з кодом `0` (успіх), якщо нових порушень немає, або `1` (помилка), якщо виявлено хоча б одне нове порушення.
2. `record-baseline`:
   - Виконує повний аудит репозиторію та зберігає всі поточні порушення у файл `.arch-baseline.json`. Застосовується під час первинного налаштування інструменту на діючому проєкті або під час узгодженого оновлення базового рівня боргу.
3. `graph`:
   - Експортує побудований граф залежностей у форматі Graphviz DOT, Mermaid або JSON для візуалізації в інженерних дашбордах.
4. `metrics`:
   - Обчислює та виводить таблицю метрик Роберта Мартіна (`C_a`, `C_e`, `I`, `A`, `D`) для кожного пакета, а також глобальний коефіцієнт циклічної заплутаності `τ(G)`.

### Таблиця прапорців конфігурації:

| Прапорець | Тип | За замовчуванням | Опис |
| :--- | :--- | :--- | :--- |
| `-c, --config <шлях>` | Рядок | `./arch-rules.yaml` | Шлях до головного файлу правил архітектури. |
| `-b, --baseline <шлях>` | Рядок | `./.arch-baseline.json` | Шлях до файлу знімка технічного боргу. |
| `--format <формат>` | Enum | `text` | Формат виводу звіту: `text`, `json`, `junit`, `github`. |
| `--fail-on-warning` | Булевий | `false` | Трактувати попередження (`warning`) як блокуючі помилки. |
| `--ignore-tests` | Булевий | `true` | Автоматично виключати тестові файли з перевірки шарів. |
| `-v, --verbose` | Булевий | `false` | Виводити повний перелік проаналізованих ребер та імпортів. |

### Коди завершення (Exit Codes):

| Код | Символічна назва | Умова виникнення |
| :--- | :--- | :--- |
| `0` | `SUCCESS` | Усі інваріанти виконано; нові архітектурні порушення відсутні. |
| `1` | `VIOLATION` | Виявлено щонайменше одне нове порушення правил або циклічну залежність. |
| `2` | `CONFIG_ERROR` | Помилка парсингу конфігураційного файлу YAML/JSON або некоректні шляхи. |
| `3` | `INTERNAL_ERROR` | Внутрішній збій аналізатора (нестача пам'яті під час побудови графа). |

## 4. Інтеграція зі збірниками та зовнішніми інструментами

Аналізатор підтримує імпорт сирих графів залежностей із різноманітних систем збірки:
- **Bazel:** імпорт дерева через виклик `bazel query 'deps(//...)' --output graph`;
- **CMake:** парсинг графа цілей компіляції `cmake --graphviz=graph.dot .`;
- **Go Modules:** зчитування зв'язків пакетів через `go list -json ./...`;
- **Cargo (Rust):** обробка виводу метаданих `cargo metadata --format-version 1`.

Отримані сирі графи автоматично нормалізуються до канонічного вигляду `G = (V, E)` і зіставляються з конфігурацією шарів та зрізів.

## 5. Специфікація машинозчитуваного звіту (JSON Output)

При виклику аналізатора з прапорцем `--format json` генерується детальний звіт для автоматичної обробки ботами та інструментами автоматизації:

```json
{
  "summary": {
    "status": "FAILED",
    "total_nodes": 450,
    "total_edges": 1820,
    "analyzed_files": 1240,
    "violations_count": 1,
    "baseline_violations_count": 2,
    "new_violations_count": 1,
    "resolved_violations_count": 0
  },
  "metrics": {
    "tangling_ratio": 0.045,
    "edge_density": 0.009
  },
  "violations": [
    {
      "rule_id": "R02-STRICT-LAYERING",
      "severity": "ERROR",
      "is_new": true,
      "message": "Зворотна залежність: шар domain залежить від infrastructure",
      "source": {
        "file": "src/domain/payment/policy.cpp",
        "line": 18,
        "symbol": "Infrastructure::RedisClient"
      },
      "target": {
        "file": "src/infrastructure/cache/redis.hpp"
      }
    }
  ]
}
```

Машинозчитуваний звіт дозволяє автоматично залишати анотації в рядках коду на сторінці Pull Request у GitHub або GitLab, точно вказуючи розробникові, яке саме ребро залежності призвело до порушення архітектурного інваріанту.
