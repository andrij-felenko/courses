# Чисті функції і побічні ефекти

<preknowlist>
- [Незмінність як прийом дизайну](root:sf-apps/immutability) — чому дані, які не міняють після створення, безпечніше передавати й ділити; чиста функція спирається саме на це.
- [Інтерфейс проти реалізації](root:sf-apps/interface-vs-implementation) — різниця між тим, що функція обіцяє сигнатурою, і тим, що вона робить насправді; побічний ефект — це якраз розрив між ними.
- [Перегони даних і замки](root:sf-tasks/data-races-locks) — що трапляється, коли два потоки чіпають ту саму пам'ять без узгодження; половина цінності чистих функцій — у тому, що цієї проблеми в них нема.
</preknowlist>

Уяви функцію в математиці — скажімо, `sin`. Ти пишеш `sin(0)` і знаєш: це `0`. Завжди. О третій ночі, на іншому комп'ютері, після мільйона інших обчислень — усе одно `0`. `sin` нічого не пам'ятає про попередні виклики, нічого не псує довкола себе й нічого не питає у світу. Дай їй те саме число — отримаєш ту саму відповідь, і крапка.

Тепер поглянь на типову функцію з реального коду:

:::tabs
```cpp
int nextId() {
    static int counter = 0;   // пам'ять між викликами
    return ++counter;
}
```
```py
_counter = 0                  # пам'ять між викликами

def next_id():
    global _counter
    _counter += 1
    return _counter
```
:::

Виклич її двічі з тим самим (порожнім) входом — і отримаєш `1`, потім `2`. Різні відповіді на однакове питання. Функція **пам'ятає**. Усередині неї сидить прихований стан, і саме він, а не аргументи, вирішує, що вона поверне. Ось перший, найглибший розлом у всьому програмуванні: функції, які поводяться як `sin`, і функції, які поводяться як `nextId`. Перших звуть **чистими (англ. *pure* — незмішаний, без домішок)**, і з ними працювати так само спокійно, як із шкільною алгеброю. Другі змішані з навколишнім світом, і саме через них програми стають непередбачуваними.

## Дві обіцянки чистої функції

Чиста функція дає дві обіцянки, і обидві прості.

Перша: **той самий вхід — той самий вихід**, завжди. Її результат залежить **лише** від аргументів — ні від годинника, ні від файлу на диску, ні від глобальної змінної, ні від того, скільки разів її вже викликали. Це властивість детермінованості (лат. *determinare* — визначати наперед): вхід повністю визначає вихід.

Друга: **вона не залишає слідів** — жодного **побічного ефекту (англ. *side effect* — побічна дія)**. Побічний ефект — це будь-яка зміна світу поза поверненим значенням: запис у глобальну змінну, друк на екран, рядок у файл, посилка по мережі, зміна об'єкта, який тобі передали за посиланням. Чиста функція бере вхід, обчислює вихід і **все** — навколишній світ до і після виклику незмінний.

Порівняй дві функції, що рахують суму замовлення:

:::tabs
```cpp
// ЧИСТА: залежить лише від аргументів, нічого не чіпає ззовні
double totalPrice(const std::vector<Item>& items, double taxRate) {
    double sum = 0.0;
    for (const Item& it : items) sum += it.price * it.qty;
    return sum * (1.0 + taxRate);
}
```
```py
# ЧИСТА: залежить лише від аргументів, нічого не чіпає ззовні
def total_price(items, tax_rate):
    subtotal = sum(it.price * it.qty for it in items)
    return subtotal * (1.0 + tax_rate)
```
:::

```cpp
// НЕЧИСТА: читає глобальний курс, пише в лог, міняє переданий об'єкт
double g_taxRate;                          // глобальний стан — прихований вхід

double totalPrice(Order& order) {          // Order& — не const, отже може змінитися
    double sum = 0.0;
    for (Item& it : order.items) {
        it.priceWithTax = it.price * (1.0 + g_taxRate);  // мутує вхід
        sum += it.priceWithTax * it.qty;
    }
    std::cout << "computed: " << sum << "\n";  // побічний ефект: вивід
    order.lastTotal = sum;                     // ще одна мутація входу
    return sum;
}
```

Перша — це `sin`. Даси їй той самий вектор і ту саму ставку — отримаєш те саме число, хоч тисячу разів поспіль, і після виклику світ такий, яким був. Друга залежить від глобального `g_taxRate` (хтось міг його змінити між викликами), псує переданий `order` і бруднить консоль. Її результат уже не читається з сигнатури: щоб зрозуміти, що вона поверне й що зіпсує, треба знати стан половини програми.

> 🔧 **Навіщо це.** Сигнатура `double totalPrice(const std::vector<Item>&, double)` — це **чесна обіцянка**: усе, від чого залежить відповідь, стоїть у дужках, і нічого, крім відповіді, не зміниться. Сигнатура `double totalPrice(Order&)` **бреше**: вона мовчить про глобальний курс, який читає, і про поля, які псує. Читаючи чисту функцію, ти тримаєш у голові рівно її аргументи; читаючи нечисту — мусиш тримати весь досяжний їй стан. Це різниця між кодом, який розумієш за секунди, і кодом, у який доводиться залазити з відлагоджувачем.

## Заміна на значення: суть чистоти одним тестом

Є один точний тест, чи функція чиста, і він дає їй справжнє ім'я. Візьми виклик — скажімо, `totalPrice(cart, 0.2)` — обчисли його один раз, отримай `120.0`, і **заміни всюди в коді самий виклик на це число `120.0`**. Якщо програма поводиться абсолютно так само — функція чиста. Якщо ні (десь загубився запис у файл, не оновилась глобальна змінна) — нечиста.

Ця властивість зветься **прозорість за посиланням (англ. *referential transparency*)**: вираз можна без наслідків замінити його ж значенням. Термін не з програмування — його ввів логік Віллард Квайн у книзі «Слово й об'єкт» (*Word and Object*, 1960), а в мови програмування його переніс британець Крістофер Стрейчі в лекціях «Fundamental Concepts in Programming Languages» (1967), назвавши однією з найкорисніших властивостей виразів (це усталений факт; докладніше — у [нарисі про народження поняття](root:sf-apps/pure-functions-side-effects/hist-referential-transparency.md)).

Чому це не просто гра термінами: якщо виклик можна замінити його значенням, то компілятор (і ти) можеш робити з ним що завгодно, не боячись зламати сенс. Обчислити один раз і **запам'ятати** (кешування, мемоізація). Порахувати наперед. Викинути, якщо результат не потрібен. Порахувати **два виклики паралельно** в різних потоках — бо вони не заважають одне одному, їм нема за що битися. Уся ця свобода тримається на єдиному факті: чиста функція нічого не пам'ятає й нічого не псує, тож її виклик — це просто його значення.

![Дві функції поряд. Ліворуч чиста: коробка з єдиним входом-стрілкою (аргументи) і єдиним виходом (значення), навколо чисте біле поле. Праворуч нечиста: така сама коробка, але в неї збоку входять приховані стрілки — годинник, глобальна змінна, файл, — а з боків виходять стрілки назовні: запис у лог, мутація переданого об'єкта, посилка по мережі](img/pure-vs-impure.svg)

*Чиста функція має рівно один вхід і рівно один вихід — усе видно в сигнатурі. Нечиста обвішана прихованими каналами: вона тягне стан збоку й виливає ефекти назовні, і жодного з цих каналів у сигнатурі не видно.*

## Чим платить нечистота: три щоденні болі

Абстрактне «важче міркувати» стає конкретним у трьох місцях, які кусають щодня.

**Тести.** Чисту функцію тестувати — задоволення: дав вхід, звірив вихід, готово. Ніякого налаштування, ніякого прибирання.

```cpp
// Тест чистої функції: увесь тест — це вхід і очікуваний вихід
assert(totalPrice({{10.0, 2}}, 0.2) == 24.0);   // 10·2·1.2
```

А щоб протестувати нечисту `totalPrice(Order&)`, доведеться спершу виставити правильний глобальний `g_taxRate`, потім перевірити не лише повернене число, а й що воно **записало** в `order`, а тоді ще й перехопити вивід у консоль, щоб він не засмічував інші тести. Один рядок перетворюється на десять, і половина з них — боротьба з прихованими каналами. Не випадково кажуть: чистота — це [тестовність](root:sf-apps/testability-tactics), вбудована в саму форму функції.

**Багатопотоковість.** Два потоки можуть викликати ту саму чисту функцію одночасно й ніколи не зіткнуться — їм нема за що битися, бо спільної пам'яті, яку хтось міг би зіпсувати, просто нема. А нечиста функція, що пише в глобальний `g_taxRate` чи в спільний `order`, — це запрошення до [перегонів даних](root:sf-tasks/data-races-locks): два потоки лізуть в одну комірку, і результат залежить від того, хто встиг перший. Половина всієї складності замків і синхронізації зникає там, де стан не діляться, бо його просто нема куди ділити.

> 🔧 **Навіщо це.** Найдешевший спосіб зробити код потокобезпечним — не додати замки, а **прибрати спільний стан**. Функція, що не читає й не пише нічого, крім своїх аргументів і локальних змінних, безпечна в будь-якій кількості потоків **за побудовою**, без жодного м'ютекса. Тому в паралельному коді чистота — не естетика, а прямий шлях позбутися цілого класу найпідступніших багів, які годинами не відтворюються.

**Відтворюваність багів.** Баг у чистій функції відтворити легко: ті самі аргументи дають ту саму поведінку, тож ти зловиш його щоразу. Баг у нечистій може залежати від годинника, від порядку викликів, від умісту файлу, від того, що інший потік устиг записати, — і зникати саме тоді, коли ти вмикаєш відлагоджувач. Детермінованість перетворює лови привида на звичайну роботу.

## Але ж без ефектів програма нікому не потрібна

Тут напрошується наївний висновок: якщо чисте — таке хороше, зробімо всю програму чистою. Але це неможливо, і причина проста до банальності. **Програма без побічних ефектів марна.** Функція, що нічого не пише на екран, нічого не шле по мережі й нічого не зберігає, — це обігрівач, а не програма: вона гріє процесор і не робить нічого спостережуваного. Сенс програми — саме в ефектах: показати картинку, зберегти файл, відповісти по мережі. Ефекти — це **мета**, а не ворог.

Отже, питання не «чисте чи нечисте», а **де провести межу**. І відповідь, яку виробила практика, елегантна: не розмазуй ефекти по всьому коду, а **збери їх на краю**. Нехай серцевина програми — уся логіка, усі рішення, усі обчислення — буде чистою, а весь бруд (читання з диска, запис у базу, вивід на екран) — тонким шаром зовні, який лише **приносить** дані в чисту серцевину й **виносить** її рішення у світ.

```cpp
// НЕЧИСТА оболонка: тонка, лише приносить дані й виносить ефект
void handleCheckout(OrderId id) {
    Order order    = db.load(id);              // ефект: читання ззовні
    double taxRate = config.taxRate();         // ефект: читання ззовні

    double total = totalPrice(order.items, taxRate);  // ← ЧИСТЕ ядро: усе рішення тут

    db.saveTotal(id, total);                   // ефект: запис назовні
    log.info("total for {} = {}", id, total);  // ефект: вивід
}
```

Придивись, що сталося. Уся **логіка** (як саме рахувати суму) живе в чистій `totalPrice` — її легко тестувати, легко розпаралелити, легко зрозуміти. А `handleCheckout` не містить жодного рішення: вона лише тягає дані туди-сюди. Ефекти нікуди не поділися — вони мусять бути, — але їх **зібрано в одному тонкому місці**, замість того щоб розсипати по всьому коду. Тестуючи логіку, ти б'єш у чисте ядро й не чіпаєш ні базу, ні мережу; а тонку оболонку, де майже нема що ламати, перевіряють кількома інтеграційними тестами.

![Дві концентричні кола. Зелене внутрішнє — чисте ядро, у ньому вся логіка й рішення, той самий вхід дає той самий вихід. Червоне зовнішнє кільце — тонка імперативна оболонка. Ефекти показано стрілками, що проходять крізь оболонку: зліва всередину приносять дані (читання з бази, читання конфіга), справа назовні виносять ефекти (запис у базу, вивід у лог). Самі рішення — лише в ядрі](img/core-shell.svg)

*Ефекти зібрані в тонкому зовнішньому кільці, що лише приносить дані в чисте ядро й виносить його рішення у світ. Рішень в оболонці нема — вона нічого не обчислює, тому там майже нема де сховатися помилці.*

Цей поділ — «чисте всередині, брудне зовні» — настільки корисний, що виріс в окремий структурний принцип: [функціональне ядро, імперативна оболонка](root:sf-apps/functional-core-imperative-shell). А те, що чиста функція не міняє переданих даних, спирається на ще один прийом — [незмінність](root:sf-apps/immutability): якщо об'єкт узагалі не можна змінити після створення, то й випадково зіпсувати його чужим побічним ефектом неможливо.

> 🔧 **Навіщо це.** Правило «ефекти — на край» дає прямий орієнтир для щоденних рішень. Бачиш функцію, яка **і** рахує щось складне, **і** пише в базу, — розділи її: винеси обчислення в чисту функцію, а запис лиши зовні. Тоді складне стає легко тестовним, а те, що лишилось назовні, — таке дрібне, що там майже нема де сховатися помилці. Повний покроковий розбір такого розчеплення — з робочим C++ і замірами, наскільки простішають тести й де вмикається мемоізація, — винесено в окремий [проєкт-рефакторинг](root:sf-apps/pure-functions-side-effects/proj-extract-pure-core.md).

## Чистота — це шкала, а не прапорець

Наостанок — одне уточнення, без якого принцип легко довести до абсурду. Побічні ефекти бувають різні за небезпекою, і мірити їх усі однією міркою було б помилкою.

Запис у глобальну змінну чи мутація об'єкта, який хтось іще тримає й читає, — **отруйний** ефект: саме він ламає передбачуваність і породжує перегони. А от локальна змінна всередині функції, яку та ж функція створила, змінила й нікому не показала, — ефект **невидимий назовні**. Функція `totalPrice` вище крутить цикл і накопичує суму в локальній `sum` — технічно це зміна пам'яті, але цієї зміни ніхто ззовні не бачить: до і після виклику світ однаковий, той самий вхід дає той самий вихід. Тому вона **чиста** попри внутрішні присвоєння. Важлива не зміна пам'яті сама собою, а чи **просочується** вона за межі функції.

Так само `assert` чи запис у лог для налагодження — формально ефект (вивід), але він не впливає на **результат** обчислення й не псує чужих даних. Такі ефекти терплять навіть у переважно чистому коді: вони не ламають ні тестовності, ні паралельності. Тому чистота — не двійковий прапорець «так/ні», а **шкала**: від ідеально чистих математичних функцій, через функції з нешкідливим логуванням, до відверто нечистих, що керують глобальним станом. Мета інженера — не досягти ідеальної чистоти всюди (це і неможливо, і непотрібно), а **свідомо тримати ядро логіки на чистому кінці шкали**, а неминучий бруд — зібраним, тонким і відсунутим на край, де він найменше шкодить.

І в цьому вся практична сила поняття. «Чиста функція» — це не академічна цнотливість, а найдешевша відома форма коду: сигнатура, якій можна вірити; тест на два рядки; безпека в багатьох потоках задарма; баг, що ловиться щоразу. Щоразу, коли ти можеш зробити функцію чистою без викрутасів — зроби; а те, що чистим бути не може, бо в ньому й полягає сенс програми, — не бійся, а просто **тримай окремо**, тонким шаром на межі зі світом.
