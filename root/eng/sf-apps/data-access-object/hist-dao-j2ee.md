# 📜 Три імені однієї ідеї: як DAO народився у світі J2EE

Наприкінці 1990-х корпоративний застосунок на Java рідко мав одне-єдине сховище. Замовлення лежали в реляційній базі. Працівники й права доступу — у каталозі LDAP. Баланси клієнтів — на мейнфреймі, до якого ходили через шлюз тридцятирічної давнини. Курси валют щоранку приїжджали пласким файлом. А половину довідників тримала чужа служба, до якої стукалися по мережі. Один діловий сценарій — «оформити замовлення» — міг за одну операцію зачепити три-чотири з цих джерел, кожне зі своєю мовою доступу, своїми помилками й своїм способом відкрити й закрити з'єднання.

Мова Java тоді вже дала стандартний міст до баз — JDBC, — але міст цей був низький і холодний. Щоб дістати рядок, доводилося власноруч узяти з'єднання, скласти `SELECT`, покрутити курсор `ResultSet`, зловити перевірний `SQLException` і не забути закрити з'єднання у `finally`. І весь цей обряд писали **прямо в тілі ділового компонента**. У світі Enterprise JavaBeans це проступало особливо гостро: коли сутність зберігали через bean-managed persistence (BMP), програміст сам заповнював методи `ejbLoad`, `ejbStore`, `ejbCreate` викликами JDBC; а сесійні біни й сервлети, яким треба було просто прочитати дані, тягли SQL у себе без жодного посередника (документований факт про механіку BMP тих років). Наслідок був однаковий: діловий код зростався зі сховищем намертво. Питання «кому дозволено погоджувати закупівлю» не мало жодного стосунку до того, лежать користувачі в таблиці чи в LDAP, — але код відповіді на це питання знав назви колонок і синтаксис драйвера, тож переїзд джерела означав переписати логіку. До цього додавалася й давніша тріщина — [неспівмірність об'єктів і таблиць](topic:sf-data/object-relational-mismatch): рядок бази й об'єкт у пам'яті — різні світи, і склейку між ними теж хтось мусив писати руками.

## Хто це побачив: архітектори Sun Java Center

Людей, які дали цій біді ім'я й ліки, звали **Діпак Алур** (Deepak Alur), **Джон Крупі** (John Crupi) і **Ден Малкс** (Dan Malks). Усі троє працювали в Sun Java Center — консалтинговому підрозділі Sun Microsystems, що будував великі системи на J2EE для реальних замовників на кшталт Ford, E\*TRADE та J.Crew (документований факт). Це важлива деталь: патерни вони не вигадали за столом, а **вичавили з чужого болю**, повторюваного від проєкту до проєкту. Той самий вузол — «діловий компонент, приклеєний до конкретного сховища» — вони бачили в десятках систем поспіль, і саме повторюваність підказала, що це не випадковість окремого проєкту, а патерн.

Каталог визрівав кілька років. Документувати свою практику у формі патернів у Sun Java Center почали близько 1999-го; уперше ці ідеї винесли на люди на конференції JavaOne 2000; навесні 2001-го каталог вийшов як публічна бета версії 1.0, а в червні 2001-го склався в книжку «Core J2EE Patterns: Best Practices and Design Strategies» (документований факт; видавництво Prentice Hall / Sun Microsystems Press). Саме там **Data Access Object** уперше дістав канонічне ім'я й форму. Слова́ Джона Крупі як головного Java-архітектора центру й двох його колег-архітекторів надали цьому імені ваги: це був не блог одного ентузіаста, а дистиляція галузевої практики під маркою Sun.

## Що саме назвали словом DAO

Означення в книзі коротке й точне: використати DAO, щоб «abstract and encapsulate all access to the data source» — тобто **абстрагувати й замкнути весь доступ до джерела даних** (цитата за виданням Core J2EE Patterns). DAO сам керує з'єднанням із джерелом, аби дістати й покласти дані; діловий компонент розмовляє лише з простим інтерфейсом, який DAO виставляє назовні, і **зовсім не бачить**, що там усередині — SQL, LDAP-запит чи виклик по мережі.

Уся сила — у двох половинках цього формулювання. **Абстрагувати** — дати назовні операції мовою даних (`findByRole`, `insert`), не згадуючи механізму. **Замкнути** — не випустити назовні жодної деталі сховища: ні синтаксису, ні назв колонок, ні навіть `SQLException`, який тихо перетворюють на власний виняток на межі DAO. Патерн навмисне будували так, щоб DAO міг пристосуватися до іншої схеми зберігання, не зачепивши тих, хто ним користується (за виданням). Ось чому це працювало саме у світі різнорідних джерел: якщо весь доступ до одного джерела зібрано в одному класі, то замінити джерело — це написати новий клас, а не полювати за SQL по всьому застосунку.

## Фабрика, яка робила заміну джерела дешевою

Одного інтерфейсу мало, якщо реалізацію все одно вибирають руками в сотні місць. Тому в первісному описі DAO ішов не сам, а в парі з **фабрикою**. Автори прямо сперли її на два породжувальні патерни «банди чотирьох»: [фабричний метод](topic:sf-apps/factory-method) — коли сховище одне й не змінюється, і абстрактну фабрику — коли сховищ кілька й їх треба перемикати (документований факт за виданням). Форма з книги виглядала приблизно так:

```java
// абстрактна фабрика: приховує, з якого сховища беруться DAO
abstract class DAOFactory {
    abstract OrderDAO    getOrderDAO();
    abstract CustomerDAO getCustomerDAO();

    static DAOFactory getFactory(int whichStore) {   // RDB, LDAP, …
        switch (whichStore) {
            case RDB:  return new RdbDAOFactory();
            case LDAP: return new LdapDAOFactory();
            default:   return null;
        }
    }
}

// конкретна фабрика під реляційну базу
class RdbDAOFactory extends DAOFactory {
    OrderDAO    getOrderDAO()    { return new RdbOrderDAO(); }
    CustomerDAO getCustomerDAO() { return new RdbCustomerDAO(); }
}
```

Задум прозорий, коли бачиш його на очах. `DAOFactory` — абстрактна фабрика: вона обіцяє видати `OrderDAO` й `CustomerDAO`, але мовчить, звідки ті беруть дані. `RdbDAOFactory` — конкретна фабрика під реляційну базу, що повертає `RdbOrderDAO`; поряд жила б `LdapDAOFactory` зі своїм `LdapOrderDAO`. Увесь застосунок бере DAO **тільки в фабрики** — і тоді перехід на інше джерело зводиться до однієї підміни: попросити іншу фабрику. Це й був той інженерний виграш, заради якого DAO виносили в окремий шар: не абстрактна краса, а дешева заміна сховища на живій системі, де половина даних сьогодні тут, а завтра переїжджає туди.

## Value Object, який довелося перейменувати

Лишалося питання: що саме DAO повертає нагору? Не живе з'єднання й не курсор — а простий носій полів, плаский запис без поведінки. У першому виданні 2001 року цей носій назвали **Value Object** (документований факт). І тут ховається один із найповчальніших конфузів у історії патернів.

Річ у тім, що слово «Value Object» уже мало інший, глибший сенс в об'єктному проєктуванні: об'єкт, який визначають його значення, а не тотожність (класичний приклад — грошова сума чи дата). Коли за два роки поряд визрів словник предметно-орієнтованого проєктування, ця колізія стала нестерпною. Тому в другому виданні книги, що вийшло 2003 року, авторам довелося **перейменувати патерн**: те, що в 2001-му звалося Value Object, стало **Transfer Object** — «об'єктом передавання» (документований факт; друге видання представили на JavaOne 2003). Ім'я змінили саме тому, що стара назва конфліктувала з усталеним поняттям, а не через якусь ваду самого патерна.

Саме цей Transfer Object і є предком того, що сьогодні кличуть [об'єктом передавання даних (DTO)](topic:sf-apps/dto): пласка торбинка полів, яку DAO наповнює з рядка й віддає діловому шарові, щоб той не морочився з `ResultSet`. Ланцюжок імен — Value Object (2001) → Transfer Object (2003) → DTO — це один і той самий носій даних, що тричі міняв табличку на дверях.

## Та сама ідея в іншій книжці: шлюз таблиці

Поки Sun Java Center шліфував J2EE-каталог, зовсім поряд, у листопаді 2002-го, вийшла книга, що дивилася на ту саму проблему з іншого боку — «Patterns of Enterprise Application Architecture» **Мартіна Фаулера** (Martin Fowler) (документований факт; видавництво Addison-Wesley). Фаулер не користувався словом «DAO». У його каталозі місце того самого об'єкта посів [**шлюз таблиці даних**](topic:sf-data/table-data-gateway) (Table Data Gateway): один об'єкт на всю таблицю, що тримає весь SQL для неї — усі `SELECT`, `INSERT`, `UPDATE`, `DELETE` в одному місці. Поряд стояв дрібніший [**шлюз рядка даних**](topic:sf-data/row-data-gateway) (Row Data Gateway) — один об'єкт на окремий рядок.

Форма виходила така сама, що й у DAO: інтерфейс, за яким сховані запити до одного джерела. Тому усталено вважають, що J2EE-шний DAO — це, по суті, Фаулерів шлюз таблиці (а коли DAO працює з окремими рядками — то шлюз рядка); залежно від того, чи DAO ще й перекладає рядок у багатий доменний об'єкт, він схиляється до [Data Mapper](topic:sf-data/data-mapper) (усталена оцінка, а не дослівна цитата Фаулера). Важить тут не хто в кого запозичив — обидві книги виростали паралельно з однієї практики, — а те, що **одна структурна ідея дістала в них дві різні назви**. Уже цього вистачило б, щоб у розмовах про доступ до даних починалася плутанина.

## Репозиторій, що визрів через дорогу

Але імен виявилося не два, а три. У тій самій книзі Фаулера, поряд зі шлюзами, жив ще один патерн — **репозиторій**. І Фаулер прямо зазначив, що поняття домодельного репозиторія доопрацьовує **Ерік Еванс** (Eric Evans), який саме тоді писав книжку про доменні моделі (документований факт). Та книжка — «Domain-Driven Design» — вийшла в серпні 2003-го й дала [репозиторію](topic:sf-apps/repository) його канонічну форму: механізм, що приховує зберігання й пошук так, ніби працюєш зі **звичайною колекцією доменних об'єктів у пам'яті** (парафраз означення Еванса).

Ось де ховається тонка, але засаднича відмінність, з якої й росте вся сумбурність. DAO та шлюз таблиці мислять **джерелом даних**: типово один на таблицю, методи звучать мовою сховища, назовні йдуть пласкі записи. Репозиторій мислить **колекцією доменних об'єктів**: він per-агрегат, методи звучать мовою предметної області (`overdue()`, `forCustomer(...)`), а повертає готові сутності. Структурно — майже близнюки; за наміром — різні речі. І оскільки в реальному коді ту межу мало хто тримає чисто, три імені почали вживати як синоніми.

![Горизонтальна лінія часу з трьома картками-віхами. Зліва картка 2001, Core J2EE Patterns, Sun Java Center Алур Крупі Малкс, зелена плашка Data Access Object, підпис абстрагувати й сховати весь доступ до джерела даних, плюс фабрика DAO і плоский Value Object. Посередині картка 2002, P of EAA, Мартін Фаулер, плашка Table Data Gateway, один об'єкт на таблицю весь її SQL, підпис та сама форма інша назва. Праворуч картка 2002 у 2003, PoEAA до DDD, Фаулер вказав Ерік Еванс розгорнув, плашка Repository, прикидається колекцією доменних об'єктів у пам'яті, підпис виріс поряд зрісся з DAO. Від кожної картки пунктир униз до вузла на осі часу, три вузли сходяться лініями в одну точку, під нею зелена плашка: три роки три імені для майже однієї ідеї сховати доступ до даних за інтерфейсом, звідси плутанина DAO Table Data Gateway Repository донині](img/dao-three-names.svg)

*За три роки — 2001, 2002, 2003 — три різні книги дали майже одній структурній ідеї три різні імені: DAO, шлюз таблиці даних і репозиторій. Усі троє — інтерфейс, за яким сховано доступ до даних; розходяться вони лише в тому, ЩО ставлять у центр абстракції. Звідси й плутанина, що триває донині.*

## Чому три імені плутають досі

Складімо докупи. За неповні три роки — з червня 2001-го по серпень 2003-го — вийшли три впливові книги, і кожна дала майже одній ідеї власне ім'я: DAO у Sun Java Center, шлюз таблиці даних у Фаулера, репозиторій у Фаулера з Евансом. Жодна не переписувала попередню — усі троє незалежно завважили один і той самий корисний хід: сховати механіку доступу до даних за інтерфейсом. Але кожна книга мала свою аудиторію (enterprise-Java, загальна архітектура застосунків, доменне моделювання) і свій словник — і словники не звели воєдино.

Наслідок дожив до сьогодні. Одна команда називає «DAO» рівно те, що інша кличе «репозиторієм»; фреймворки видають клас із іменем `Repository`, а всередині — типовий шлюз таблиці; хтось третій пише «DAO», маючи на думці Data Mapper. Плутанина не з дурного гурту — вона **вросла в саму історію**: три поважні джерела назвали спільного предка трьома різними словами майже одночасно. Тому, зустрівши в чужому коді будь-яке з цих трьох імен, розумніше не довіряти табличці на дверях, а глянути всередину й спитати одне: **навколо чого мислить ця абстракція — джерела даних чи доменної колекції**. Відповідь на це питання значить більше, ніж те, яке з трьох історичних імен випало на цей клас.
