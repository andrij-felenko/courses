# Шаблонний метод

<preknowlist>
- [Спадкування](root:sf-lang/inheritance) — підклас переймає методи предка й може підмінити (override) окремі з них; на цьому тримається весь патерн: каркас живе в предку, а змінні кроки дають нащадки.
- [Поліморфізм і динамічне зв'язування](root:sf-lang/polymorphism) — виклик методу через тип-предок у рантаймі потрапляє в підмінену версію нащадка; це механізм, яким незмінний каркас «провалюється» в конкретний крок.
- [Абстрактний клас і метод](root:sf-lang/abstract-class) — метод, оголошений без тіла, змушує нащадка дати реалізацію; це і є «дірка» в каркасі, яку підклас зобов'язаний заповнити.
</preknowlist>

Уяви, що пишеш імпорт даних. Спершу з CSV: прочитати файл, розбити на рядки, з кожного зробити запис, відкинути биті, зберегти все в базу, записати в лог, скільки завантажив. Працює. За тиждень просять те саме з JSON — ти копіюєш увесь метод і міняєш рівно одне: замість «розбити комами» тепер «розібрати JSON». Ще за тиждень XML — знову копія, знову одна змінена стрічка серед двадцяти однакових. Тепер у тебе три майже тотожні методи. І коли з'ясовується, що лог має ще й рахувати відкинуті рядки, ти правиш це тричі. Забув в одному — і той імпорт мовчки бреше у звітах.

Придивімося, де тут корінь болю. У трьох методах збіглося майже все — крім одного кроку. Спільне (порядок дій, читання, відсів битих, збереження, лог) розмножилося копіюванням, і тепер кожна його зміна вимагає обійти всі копії й не проґавити жодної. Ми дублюємо **стале** заради того, щоб підмінити одне **змінне**, — і саме тому копії з часом розсинхронюються.

Тож розділімо ці дві речі за їхньою природою. Стала — сама послідовність: прочитати → розібрати → відсіяти биті → зберегти → залогувати. Цей порядок однаковий для будь-якого формату; він і є суть операції «імпорт». Змінний — рівно один крок усередині: як саме перетворити сирий текст на записи. Формат не міняє алгоритму — він міняє одну його ланку.

**Шаблонний метод (англ. *Template Method*; шаблон — нім. *Schablone*, трафарет, взірець для відтворення форми)** робить із цього спостереження патерн: **записати незмінний кістяк алгоритму один раз, в одному методі, а на місці змінних кроків лишити виклики методів-заготовок, які заповнять нащадки**. Кістяк — це і є «шаблон»: він задає форму, у яку кожен нащадок вставляє свою деталь. Сам порядок кроків зафіксований у предку й більше ніде не повторюється.

## Каркас, у якому лишили дірки

Патерн має рівно три різновиди частин. Перша — **шаблонний метод**: той самий незмінний кістяк, метод предка, що викликає кроки по черзі. Друга — **примітивні операції**: абстрактні кроки-заготовки, які кожен нащадок мусить реалізувати по-своєму. Третя — **гачки** (англ. *hook* — зачіп): кроки з розумною типовою поведінкою, які нащадок **може** підмінити, коли треба, а може й лишити як є. Ось наш імпорт, зібраний за цим рецептом:

:::tabs
```java
abstract class Importer {
    // ШАБЛОННИЙ МЕТОД: незмінний каркас. final — нащадок його не підмінить.
    public final void importFile(String path) {
        String text   = readFile(path);           // спільний крок
        List<Record> rows = parse(text);           // ← дірка: дає нащадок
        rows.removeIf(r -> !isValid(r));           // гачок із типовою поведінкою
        saveAll(rows);                             // спільний крок
        log(rows.size());                          // спільний крок
    }

    protected abstract List<Record> parse(String text);   // МУСИТЬ дати нащадок

    protected boolean isValid(Record r) { return true; }  // гачок: МОЖЕ підмінити

    private String readFile(String path) { /* однакове для всіх */ return ""; }
    private void   saveAll(List<Record> rows) { /* однакове для всіх */ }
    private void   log(int n) { /* однакове для всіх */ }
}

class CsvImporter extends Importer {
    protected List<Record> parse(String text) { /* рядки, розбиті комами */ return List.of(); }
}

class JsonImporter extends Importer {
    protected List<Record> parse(String text) { /* JSON → записи */ return List.of(); }
    protected boolean isValid(Record r) { return r.id() > 0; }  // цей формат хоче суворіше
}
```
```ts
abstract class Importer {
  // ШАБЛОННИЙ МЕТОД: каркас, який нащадок не чіпає
  importFile(path: string): void {
    const text = this.readFile(path);                     // спільний крок
    const rows = this.parse(text).filter(r => this.isValid(r));  // дірка + гачок
    this.saveAll(rows);                                   // спільний крок
    this.log(rows.length);                                // спільний крок
  }

  protected abstract parse(text: string): Record[];       // мусить дати нащадок
  protected isValid(r: Record): boolean { return true; }  // гачок із типовим «так»

  private readFile(path: string): string { /* однакове */ return ""; }
  private saveAll(rows: Record[]): void  { /* однакове */ }
  private log(n: number): void           { /* однакове */ }
}

class CsvImporter extends Importer {
  protected parse(text: string): Record[] { /* комами */ return []; }
}
class JsonImporter extends Importer {
  protected parse(text: string): Record[] { return JSON.parse(text); }
  protected isValid(r: Record): boolean { return r.id > 0; }  // суворіше
}
```
```py
from abc import ABC, abstractmethod

class Importer(ABC):
    # ШАБЛОННИЙ МЕТОД: каркас; нащадки його не перевизначають
    def import_file(self, path: str) -> None:
        text = self._read_file(path)                       # спільний крок
        rows = [r for r in self.parse(text) if self.is_valid(r)]  # дірка + гачок
        self._save_all(rows)                               # спільний крок
        self._log(len(rows))                               # спільний крок

    @abstractmethod
    def parse(self, text: str) -> list["Record"]: ...      # мусить дати нащадок

    def is_valid(self, r: "Record") -> bool:               # гачок із типовим «так»
        return True

    def _read_file(self, path): ...     # однакове для всіх
    def _save_all(self, rows): ...      # однакове для всіх
    def _log(self, n): ...              # однакове для всіх

class CsvImporter(Importer):
    def parse(self, text): ...          # комами

class JsonImporter(Importer):
    def parse(self, text): ...          # JSON
    def is_valid(self, r):              # суворіше
        return r.id > 0
```

Прочитай `importFile` — це весь алгоритм, і він більше ніде не повторюється. Він викликає `parse`, **не знаючи** формату: у рантаймі виклик потрапить у той клас, екземпляром якого є об'єкт, — звичайне [динамічне зв'язування](root:sf-lang/polymorphism). `CsvImporter` пише **тільки** `parse` і успадковує решту незмінною; `JsonImporter` пише свій `parse` і додатково підмінює гачок `isValid`, бо його формату потрібна суворіша перевірка. Додати XML — це створити ще один нащадок з одним методом; каркаса ніхто не чіпає. Стале лишилося сталим і в одному місці; росте лише те, що й мало рости.

![Незмінний каркас importFile як стовпчик кроків: три кроки замкнені й спільні, крок parse — зелена дірка, яку нащадок мусить дати, крок isValid — синій гачок із типовою поведінкою, який нащадок може підмінити; праворуч два нащадки CsvImport і JsonImport стрілками вставляють свій parse у дірку](img/skeleton-holes.svg)

*Каркас пишемо один раз і фіксуємо порядок кроків у предку. Змінним лишається рівно те, що винесене в дірку; нащадок дає лише свій крок і вставляє його на призначене місце.*

## Хто кого кличе: керування навпаки

Тут ховається справжня глибина патерна, і вона видна, щойно спитати: хто кого викликає? Придивись до `importFile`. Це метод **предка** — коду, який ти для цього формату не писав, який був готовий заздалегідь. І саме він викликає **твій** `parse`. Ти ніколи не кличеш `parse` сам — його кличе каркас, у той момент, який обрав каркас, і в тому порядку, який задав каркас. Керування перевернуте: **загальна, готова частина викликає конкретну, твою**, а не навпаки.

Це і є знаменитий принцип «не телефонуй нам — ми зателефонуємо тобі» (англ. *Hollywood principle*). Він точно проводить межу між двома речами, які початківець плутає, — **бібліотекою** і **каркасом**. Бібліотека — це код, який кличеш **ти**: `sort()`, `parse()` викликаєш звідти, коли тобі треба, керуєш потоком ти. Каркас (англ. *framework*) — це навпаки код, який кличе **тебе**: ти заповнюєш визначені дірки, а хід виконання веде він. Шаблонний метод — найменша клітинка цієї ідеї: предок володіє потоком, а твоя підміна — лише вставлена дірка. Ширше це перевертання залежностей — окрема тема [інверсії керування](root:sf-apps/dependency-inversion); шаблонний метод — його найпростіший конкретний випадок.

![Два способи поєднати свій код із чужим. Ліворуч бібліотека: твій код угорі керує й кличе бібліотеку вниз. Праворуч каркас із шаблонним методом: каркас угорі керує й кличе твій крок вниз; твій код переїхав із позиції того, хто кличе, у позицію того, кого кличуть](img/inverted-control.svg)

*Різниця бібліотеки й каркаса — у напрямку керування. Твій код або зверху (кличе готове), або знизу (готове кличе його). Шаблонний метод ставить твій крок унизу: каркас вирішує, коли й у якому порядку його виконати.*

> 🔧 **Навіщо це.** Саме на цьому перевертанні стоять усі каркаси, з якими ти працюєш щодня. Тестовий рушій (JUnit, pytest) сам кличе твій `setUp`, тіло тесту й `tearDown` у правильному порядку — ти лише заповнюєш кроки. Веб-каркас сам приймає запит і кличе твій обробник між автентифікацією й серіалізацією відповіді. Життєвий цикл екрана в мобільному застосунку — це низка гачків (`onCreate`, `onResume`), які система викликає в потрібні миті. Скрізь ти пишеш **не головний цикл, а вставки в чужий головний цикл**. Розуміти, що каркас кличе тебе, а не ти його, — значить перестати боротися з ним і почати заповнювати саме ті дірки, які він пропонує.

## Три сорти кроків, і як їх обирати

Сила патерна — в тому, що предок наперед вирішує долю кожного кроку, і цих доль рівно три. **Замкнений спільний крок** (`readFile`, `saveAll`, `log`) — приватний, однаковий для всіх, нащадок його не бачить і не міняє: це та частина алгоритму, яку ти хочеш гарантувати незмінною. **Обов'язкова примітивна операція** (`parse`) — абстрактна дірка: нащадок **мусить** її заповнити, і компілятор не дасть створити клас, який цього не зробив; так каркас каже «без цього кроку я не працюю, дай його». **Гачок** (`isValid`) — дірка з типовим тілом: нащадок **може** підмінити, а може мовчки прийняти розумну поведінку за замовчуванням; так каркас пропонує необов'язкову точку втручання, не змушуючи кожного нащадка нею перейматися.

Ця розкладка — і є контракт, який ти вручаєш нащадкам. Зробив крок замкненим — пообіцяв, що він завжди такий. Зробив абстрактним — зажадав його від кожного. Зробив гачком — дав вибір і поставив на замовчуванні щось притомне. Хороший гачок робить типовий випадок безкоштовним: `isValid`, що за замовчуванням повертає «так», означає «більшості форматів фільтр не потрібен, і їм не доведеться писати жодного рядка; кому треба — підмінить». Мистецтво шаблонного методу — не в самому каркасі, а в цьому виборі, які кроки замкнути, які зажадати, а які лише запропонувати.

## Ціна: це спадкування, не композиція

Тепер про зворотний бік, без якого патерн легко застосувати не там. Шаблонний метод веде варіативність **вгору** — у ієрархію типів. `CsvImporter` **є** `Importer` від народження; який саме варіант узяти, вирішується, коли ти створюєш об'єкт, і стосується він цілого об'єкта назавжди. Щоб той самий об'єкт почав розбирати JSON замість CSV, його довелося б **пересотворити** іншим класом.

У шаблонного методу є близький родич, який веде **ту саму** варіативність убік — [Стратегія](root:sf-apps/strategy). Замість підкласу зі вшитим кроком контекст тримає крок **окремим об'єктом у полі** й делегує йому; цей об'єкт підставний будь-коли. Різниця між ними — це і є різниця між двома способами міняти поведінку взагалі.

![Та сама змінність двома способами. Ліворуч шаблонний метод: предок Importer із каркасом і абстрактним parse, під ним два нащадки, привʼязані спадкуванням; варіант — це підтип, обраний при створенні. Праворуч стратегія: контекст Importer тримає в полі обʼєкт-парсер, який підставляють у рантаймі; варіант — обʼєкт у полі](img/template-vs-strategy.svg)

*Обидва відділяють змінний крок від сталого. Шаблонний метод робить це спадкуванням — жорстко, на весь тип, з вибором при створенні. Стратегія робить це композицією — гнучко, підставним обʼєктом, з вибором і заміною в рантаймі.*

Наслідки цієї різниці прямі. Спадкування прив'язує варіант до типу, тож кожна нова вісь варіативності множить підкласи: якби, крім формату, окремо мінявся ще й спосіб збереження, через підкласи довелося б робити клас на **кожну комбінацію** — `CsvToSqlImporter`, `JsonToFileImporter` — комбінаторний вибух. Композиція тримає кожну вісь окремим полем, і будь-яка комбінація складається з них вільно. Тому загальна порада схиляється до [композиції над спадкуванням](root:sf-apps/composition-inheritance), а для змінної поведінки — до стратегії.

Коли ж брати саме шаблонний метод? Коли цінне — сам **спільний кістяк**, а кроки справді нерозривно належать йому й одному місцю, спадкування читається чисто: весь потік видно в одному методі предка, а нащадки короткі. Він природний **у каркасах** (де стабільний життєвий цикл з кількома точками розширення — це саме те, що каркас пропонує) і **в малому**, де одна вісь варіативності й жодного бажання підставляти щось у рантаймі. Додати варіант тут — це дописати нащадок, не чіпаючи каркас: чистий [принцип відкритості-закритості](root:sf-apps/open-closed). До речі, [Фабричний метод](root:sf-apps/factory-method) — це і є шаблонний метод, чия дірка **створює об'єкт**: каркас потребує продукт, але лишає нащадкові вирішити, якого саме класу.

У C++ цей патерн має гострішу, дисциплінованішу форму — **ідіому невіртуального інтерфейсу** (NVI): публічний каркас роблять **не**віртуальним, а кроки-дірки — приватними віртуальними. Тоді нащадок фізично не може ні пропустити каркас, ні змінити порядок кроків — лише заповнити дірки; а предок дістає місце, щоб перевірити передумови й інваріанти навколо кожного кроку. Як це працює й чому «віртуальне роби приватним» — у [окремому розборі](root:sf-apps/template-method/proj-nvi-idiom.md).

## Де він ламається

Патерн, зручний у застосуванні, легко й перегнути, тож чесно назвемо його слабкі місця. Перше й головне — **тісний, невидимий зв'язок предка й нащадка через порядок і момент виклику**. Каркас кличе твій крок у конкретну мить, коли об'єкт у конкретному стані; якщо нащадок не знає, що на той момент уже зроблено, а що ні, його підміна ламається неочевидно. Цей зв'язок — не в сигнатурах, а в припущеннях, і його легко порушити необережною зміною предка: класична **крихкість базового класу**, коли правка каркаса тихо валить нащадків, яких автор правки навіть не бачив.

Друге — нащадок **мусить чесно виконувати контракт кроку**: робити свою роботу, не більше й не менше, і не ламати інваріантів, на які спирається каркас. Крок `parse`, що замість списку записів іноді повертає `null`, зруйнує весь потік, хоч формально сигнатуру дотримано. Це пряма вимога [принципу підстановки Лісков](root:sf-apps/liskov-substitution): підмінений крок має бути придатною заміною очікуваного, інакше каркас, який вірив обіцянці, зробить неправильне.

Третє — **глибина**. Ланцюг шаблонних методів через багато рівнів спадкування («каркас кличе крок, який сам є каркасом, що кличе крок…») перетворює просте питання «куди насправді йде потік» на археологію. Тримай ієрархію мілкою. І, нарешті, **надмір**: не кожна спільна послідовність вартує базового класу. Якщо варіант лише один або кроки насправді не спільні, простіше передати змінний крок звичайною [функцією-значенням](root:sf-lang/first-class-functions) — той самий ефект без цілої ієрархії. Патерн має гасити наявний біль дублювання, а не вводитися наперед про запас.

## Звідки він

Шаблонний метод старший за книжку, що дала йому ім'я: це **механізм повторного використання об'єктних каркасів** — саме так каркас володіє керуванням і кличе твій код у визначених точках. «Банда чотирьох» (Еріх Гамма, Річард Гелм, Ральф Джонсон, Джон Вліссідс, 1994) назвала його й віднесла до **поведінкових** патернів — тих, що впорядковують розподіл обов'язків, а не створення чи склад об'єктів. Як ця ідея визрівала в ранніх каркасах, звідки взялося «не телефонуй нам» і чому воно й відрізняє каркас від бібліотеки — у [нотатці про народження патерна](root:sf-apps/template-method/hist-template-method-frameworks.md).
