# ⚙️ Ідіома невіртуального інтерфейсу (NVI) у C++

Каркас алгоритму, у якому лишили дірки для нащадків, тримається на одній тихій обіцянці: що каркас **виконається цілим**, у своєму порядку, з усіма своїми перевірками, а нащадок заповнить лише дірку. У більшості мов цю обіцянку доводиться сторожити дисципліною й код-рев'ю. У C++ її можна зробити **фізично неможливою до порушення** — самим контролем доступу. Ідіома, що це робить, зветься **невіртуальний інтерфейс** (англ. *Non-Virtual Interface*, NVI; ідіома — гр. *idíōma*, своєрідний зворот): найдисциплінованіша форма шаблонного методу, яку дає система типів C++.

## Задача: коли каркас можна тихо обійти

Почнімо з наївного C++-каркаса й подивімося, де він тріщить. Хай є звіт: спільна голова, спільний хвіст, а всередині — тіло, яке кожен формат малює по-своєму. Перша спокуса — зробити метод, що малює звіт, **публічним віртуальним**, щоб нащадок «підправив тіло», перевизначивши (англ. *override*) його:

```cpp
class Report {
public:
    // публічний ВІРТУАЛЬНИЙ метод: нащадок його перевизначить
    virtual std::string render(const std::vector<Field>& fields) const {
        std::string out = header(fields.size());   // спільна голова
        for (const auto& f : fields)               // типове тіло
            out += f.key + ": " + f.value + "\n";
        out += footer();                            // спільний хвіст
        return out;
    }
    virtual ~Report() = default;
protected:
    std::string header(std::size_t n) const { return "=== REPORT (" + std::to_string(n) + ") ===\n"; }
    std::string footer() const { return "=== END ===\n"; }
};
```

Тепер нащадок хоче лише **інше тіло** — JSON замість «ключ: значення». Але єдина точка, яку йому дали, — це весь `render`. Тож він пише:

```cpp
class JsonReport : public Report {
public:
    std::string render(const std::vector<Field>& fields) const override {
        std::string s = "{";
        for (std::size_t i = 0; i < fields.size(); ++i) {
            if (i) s += ",";
            s += "\"" + fields[i].key + "\":\"" + fields[i].value + "\"";
        }
        return s + "}";           // ← і голова, і хвіст зникли, і ніхто не сказав
    }
};
```

Придивись, що сталося. Програміст хотів підмінити **одну ланку** — тіло. А перевизначив **увесь** метод, бо іншого гачка не існувало. Разом із тілом він мовчки викинув `header()` і `footer()`. Звіт тепер без голови й хвоста; якби в `render` предка була ще й перевірка вхідних даних чи запис у журнал — зникли б і вони. І найгірше: **компілятор не сказав ані слова**. `override` формально коректний, сигнатура збіглася, програма зібралася й запустилася. Каркас обвалився там, де його ніхто не побачить, — у звіті, який комусь ляже на стіл наступного кварталу.

Можна спробувати врятуватися домовленістю: «перевизначаючи `render`, **завжди першим ділом клич `Report::render`**». Але це не гарантія, а прохання. Домовленість живе в коментарі й у голові автора; варто одному нащадкові її забути — і каркас знову зник, знову тихо. Ми поставили вартового, якого можна не покликати. Корінь болю саме тут: **точка, яку нащадок мусить лише заповнити, і точка, яку він може цілком замінити, — це та сама публічна віртуальна функція**. Поки вони збігаються, обіцянка каркаса тримається на честному слові.

## Ідея: розвести «хто може кликати» і «що можна перевизначити»

Розв'язок виростає з однієї особливості C++, повз яку легко пройти: **право доступу і віртуальність — це дві незалежні осі**. `public`/`protected`/`private` кажуть, **хто має право покликати** функцію на ім'я. `virtual` каже, **чий код виконається**, коли її таки покликали, — той, яким об'єкт є насправді. Це різні питання, і C++ дозволяє відповісти на них порізно. На цьому й стоїть уся [інкапсуляція](topic:sf-apps/encapsulation): видимість імені — окремо від того, що за ним ховається.

Звідси разючий, але цілком законний факт: **приватну віртуальну функцію нащадок може перевизначити, хоч і не може її покликати**. Забороняє покликати — `private`; дозволяє підмінити тіло — `virtual`; вони не заважають одна одній. Виклик приватної віртуальної, зроблений зсередини предка, однаково пройде через [таблицю віртуальних методів](topic:sf-devices/virtual-dispatch-cpp) у той клас, яким об'єкт є в рантаймі, — приватність адресує *доступ*, а не *механізм диспетчеризації*.

Ось важіль, якого бракувало. Розведімо ті дві точки, що фатально збіглися:

- **Публічний каркас робимо НЕвіртуальним.** Це «ворота»: єдиний вхід для клієнта, і **ніхто його не перевизначить** — не пропустить, не переставить кроки, не викине перевірки. Немає віртуальності — немає що заміняти.
- **Змінний крок робимо приватним віртуальним.** Це «дірка»: нащадок **мусить** її заповнити (диспетчеризація йде в його код), але **не може** покликати сам і не бачить її як точку входу.

Ворота кличуть дірку. Клієнт кличе тільки ворота. Нащадок дотягується тільки до дірки. І — ключове — **зникає сам «super», який можна забути**: каркас не віртуальний, тож він не заміняється, а виконується завжди й цілим. Немає базової реалізації, яку треба не проґавити покликати, бо базова реалізація — це і є невіртуальні ворота, повз які пройти неможливо. Обіцянка каркаса з прохання перетворилася на властивість системи типів.

## Робочий каркас: ворота з перевірками навколо дірки

Тепер найсмачніше — місце, яке дає предкові NVI, а публічно-віртуальний підхід відбирає. Раз ворота невіртуальні й виконуються завжди, предок може **обгорнути дірку перевірками**: перевірити передумову перед кроком нащадка, перевірити його результат після, і ствердити інваріант цілого. Це прямий вияв [проєктування за контрактом](topic:sf-release/design-by-contract): у кожного кроку є передумова (що йому вільно припускати), післяумова (що він мусить забезпечити) й інваріант (що лишається істинним завжди), і в NVI **предок — той, хто ці умови стереже**, а не сподівається, що нащадок не збреше.

```cpp
#include <string>
#include <vector>
#include <stdexcept>
#include <cassert>

struct Field { std::string key, value; };

class Report {
public:
    // ВОРОТА: публічний НЕвіртуальний каркас. Нащадок його не перевизначить.
    std::string render(const std::vector<Field>& fields) const {
        // — передумова: далі крок нащадка вільно припускає, що список не порожній
        if (fields.empty())
            throw std::invalid_argument("render: порожній список полів");

        std::string out = header(fields.size());     // спільний крок — завжди

        std::string body = renderBody(fields);        // ← ДІРКА: код нащадка

        // — післяумова: перевіряємо те, що нащадок ОБІЦЯВ віддати
        assert(!body.empty()          && "renderBody вернув порожнє тіло");
        assert(body.back() != '\n'    && "тіло не має завершуватись переносом");

        out += body;
        out += footer();                              // спільний крок — завжди

        // — інваріант результату: звіт завжди починається заголовком
        assert(out.rfind(MAGIC, 0) == 0 && "звіт втратив заголовок");
        return out;
    }

    virtual ~Report() = default;   // публічний віртуальний — бо видаляємо через Report*

private:
    // ДІРКА: приватна ВІРТУАЛЬНА. Нащадок МУСИТЬ дати; покликати ззовні не може.
    virtual std::string renderBody(const std::vector<Field>& fields) const = 0;

    // ЗАМКНЕНІ спільні кроки — приватні невіртуальні, однакові для всіх.
    static constexpr const char* MAGIC = "=== REPORT ===";
    std::string header(std::size_t n) const {
        return std::string(MAGIC) + " (fields: " + std::to_string(n) + ")\n";
    }
    std::string footer() const { return "\n=== END ===\n"; }
};
```

Нащадок пише **рівно одну функцію** — дірку — і не має до чого більше дотягтися:

```cpp
class TextReport : public Report {
    // без специфікатора → private за замовчуванням; так і має бути
    std::string renderBody(const std::vector<Field>& fields) const override {
        std::string s;
        for (const auto& f : fields)
            s += f.key + ": " + f.value + "\n";
        s.pop_back();               // прибрати останній перенос — цього вимагає післяумова
        return s;
    }
};

class JsonReport : public Report {
    std::string renderBody(const std::vector<Field>& fields) const override {
        std::string s = "{";
        for (std::size_t i = 0; i < fields.size(); ++i) {
            if (i) s += ",";
            s += "\"" + fields[i].key + "\":\"" + fields[i].value + "\"";
        }
        return s + "}";
    }
};
```

Зверни увагу на дрібницю, що доводить сенс контракту: `TextReport::renderBody` спокійно робить `s.pop_back()`, не перевіряючи, чи є що прибирати. Він **має право** так робити, бо ворота вже стятли порожній список передумовою — до дірки код нащадка добереться лише тоді, коли полів щонайменше одне. Передумова, яку стереже предок, **дає нащадкові право на припущення**; це і є контракт у дії.

**Worked-приклад: що саме виконається на `JsonReport`.**

```cpp
Report* r = new JsonReport();
std::string s = r->render({ {"id", "7"}, {"name", "valve"} });
delete r;
```

```
render() — невіртуальні ворота — веде крок за кроком:
  fields.empty()?            → ні (2 поля) — передумова пройдена
  header(2)                  → "=== REPORT === (fields: 2)\n"
  renderBody(fields)         → диспетчеризація в JsonReport → "{\"id\":\"7\",\"name\":\"valve\"}"
  assert !empty, не '\n'     → тіло непорожнє, кінець '}' — післяумова пройдена
  out += body
  footer()                   → "\n=== END ===\n"
  assert out починається MAGIC → так — інваріант тримається

Результат:
  === REPORT === (fields: 2)
  {"id":"7","name":"valve"}
  === END ===
```

Голова, перевірки й хвіст **виконалися неминуче** — `JsonReport` не мав жодної змоги їх обійти, бо єдине, що він написав, — це тіло дірки. Порядок кроків живе в одному невіртуальному методі й ніде не дублюється; змінне винесене в приватну віртуальну ланку; а навколо неї предок поставив вартових, яких нащадок не роззброїть.

![Структура NVI: великі невіртуальні ворота render() охоплюють вертикальну стрічку кроків — передумова, спільний header, зелена дірка renderBody, післяумова з інваріантом, спільний footer; праворуч два нащадки JsonReport і TextReport стрілками дотягуються лише до дірки renderBody, решта кроків замкнена всередині воріт](img/nvi-gate.svg)

*Публічний невіртуальний метод — це замкнені ворота: усі кроки й перевірки виконуються всередині нього неминуче. Нащадок дотягується лише до приватної віртуальної дірки; голову, хвіст і перевірки він не бачить і не може ні пропустити, ні переставити.*

## Чому нащадок тепер не може схитрувати

Порахуймо чесно, що саме стало неможливим — бо саме перелік неможливостей і є вся сила ідіоми.

**Пропустити каркас — не може.** Клієнт кличе `render`, а `render` невіртуальний; хоч би що написав нащадок, виклик потрапляє у ворота предка. Немає віртуальної точки, куди нащадок міг би вклинитися замість воріт.

**Переставити кроки — не може.** Порядок `header → renderBody → footer` зашитий у тілі невіртуального методу, до якого нащадок не має доступу на перевизначення. Він впливає рівно на вміст `renderBody`, не на його місце в послідовності.

**Викинути перевірки — не може.** Передумова, післяумова й інваріант стоять у воротах, поза досяжністю. Нащадок не може ні прибрати їх, ні прослизнути повз.

**Забути покликати базову реалізацію — ні про що.** Немає «базової реалізації», яку треба не забути покликати. У публічно-віртуальному підході каркас жив у методі, який нащадок заміняв, тож доводилося просити «поклич `Base::render` першим». Тут каркас — це самі невіртуальні ворота: він не заміняється, він **охоплює** крок нащадка. Забути покликати те, що кличе тебе, неможливо.

Ось та сама пара підходів поряд — видно, що змінилося не в іменах, а в тому, до чого нащадок фізично дотягується:

![Порівняння двох підходів. Ліворуч публічний віртуальний render(): нащадок BrokenReport перевизначає ВЕСЬ метод, забув header і footer, каркас зник, компілятор мовчить, червоний хрестик. Праворуч NVI: ворота render() невіртуальні, нащадок дотягується лише до дірки renderBody, каркас виконується завжди, немає super, який можна забути, зелена галочка](img/nvi-vs-public-virtual.svg)

*Публічно-віртуальний каркас нащадок замінює цілком — і мовчки викидає спільні кроки. Невіртуальні ворота NVI замінити не можна: нащадок дістає тільки дірку, а каркас і перевірки лишаються неминучими.*

## Чотири настанови Герба Саттера

Цю дисципліну звів у чотири короткі правила Герб Саттер у статті **«Virtuality»** (колонка *Sutter's Mill*, журнал *C/C++ Users Journal*, вересень 2001, том 19, число 9; згодом зібрана в його книжці «Exceptional C++ Style»). Він виходив із двох простих питань — «якими роду мають бути віртуальні функції?» і «яким має бути деструктор базового класу?» — і відповіді склалися в настанови, що описують саме NVI. Стаття документована, датування усталене.

**Настанова 1 — інтерфейси роби невіртуальними, через шаблонний метод.** Публічна функція — це **контракт із клієнтом**: що станеться, коли її покликати. Зробивши її віртуальною, ти віддаєш контроль над контрактом кожному нащадкові, а він може контракт мовчки зламати (як `JsonReport` вище викинув голову й хвіст). Тому публічний метод лишається невіртуальним і сам веде послідовність — це наші ворота.

**Настанова 2 — віртуальні функції роби приватними.** Точка розширення — це **не** те саме, що точка виклику. Публічна віртуальна функція намагається бути двома речами одразу: і контрактом для клієнта, і гачком для нащадка, — і саме це роздвоєння породжує крихкість. Розділивши їх (публічні невіртуальні ворота — для клієнта, приватна віртуальна дірка — для нащадка), кожна з них робить лише свою роботу. За замовчуванням дірка приватна.

**Настанова 3 — `protected virtual` лише тоді, коли нащадок мусить кликати базову реалізацію.** Іноді крок нащадка природно **надбудовує** базовий: спершу зробити те, що робив предок, а тоді додати своє. Але приватну віртуальну нащадок покликати не може — тож `Base::step()` йому недоступний. Виняток саме для цього випадку: підвищуємо ланку до `protected virtual`, щоб нащадок мав право покликати базу.

```cpp
class Validator {
    // ворота — невіртуальні, як завжди
public:
    void check(const Request& r) const {
        if (r.id == 0) throw std::invalid_argument("check: нема id");  // спільна передумова
        rules(r);                                                       // ← дірка-надбудова
    }
    virtual ~Validator() = default;
protected:
    // protected — саме тому, що нащадок МУСИТЬ надбудувати цю базову перевірку
    virtual void rules(const Request& r) const {
        if (r.size == 0) throw std::invalid_argument("rules: порожній запит");
    }
};

class StrictValidator : public Validator {
protected:
    void rules(const Request& r) const override {
        Validator::rules(r);                       // спершу базові правила — тепер це можна
        if (r.size > MAX) throw std::invalid_argument("rules: завеликий запит");
    }
    static constexpr std::size_t MAX = 4096;
};
```

`protected` тут — **свідомий виняток**, а не типовий стан. Він каже прямо: «ця ланка задумана як точка надбудови, базову версію звати можна». Усе, що такою точкою не задумане, лишається приватним — і нащадок навіть не спокуситься покликати те, чого не бачить.

**Настанова 4 — деструктор базового класу: або публічний віртуальний, або захищений невіртуальний.** Це правило про безпечне знищення, і воно закриває пастку, яку легко проґавити. Якщо об'єкти видаляють **через покажчик на базу** (`Report* r = new JsonReport; delete r;`), деструктор бази мусить бути **публічним і віртуальним** — інакше `delete` крізь базовий покажчик з невіртуальним деструктором — це **невизначена поведінка**: викличеться лише деструктор бази, а деструктор справжнього класу — ні, і його ресурси течуть.

```cpp
struct Bad {
    ~Bad();                     // публічний, але НЕвіртуальний
};
struct Derived : Bad { std::vector<int> big; };

Bad* p = new Derived;
delete p;                       // ⚠️ невизначена поведінка: ~Derived не покличеться
```

Дві безпечні форми. Якщо поліморфне знищення потрібне — **публічний віртуальний** деструктор (як у `Report` вище). Якщо ж крізь базу видаляти **не** передбачено (база — це домішка, політика, інтерфейс без володіння), то деструктор роблять **захищеним невіртуальним**: `protected` **на етапі компіляції забороняє** `delete basePtr` ззовні, а раз видаляти крізь базу заборонено — деструктор не мусить бути віртуальним, і клас економить на таблиці віртуальних методів.

```cpp
struct Policy {                 // крізь Policy* ніхто не видаляє
protected:
    ~Policy() = default;        // захищений невіртуальний: delete policyPtr — помилка компіляції
};
```

Ці правила — не абстракція з підручника: сама стандартна бібліотека C++ побудована так. `std::basic_streambuf` дає публічні невіртуальні `sgetc()`, `sputc()`, `pubseekoff()`, `pubsync()`, а вони кличуть **захищені віртуальні** `underflow()`, `overflow()`, `seekoff()`, `sync()`, які реалізують конкретні буфери (файловий, рядковий). Клієнт кличе ворота; конкретика живе в дірках; це NVI у чистому вигляді, задовго до того, як йому дали ім'я.

## Складність і пастки

**Дві функції на кожну точку розширення.** Ціна дисципліни — багатослів'я: ворота плюс дірка замість однієї віртуальної. У малому це відчутний зайвий шар. Виправдано там, де навколо кроку є що стерегти (перевірки, спільна обгортка, фіксований порядок); де дірка гола й предок навколо неї нічого не робить, зайвий шар — лише церемонія.

**Приватну віртуальну можна перевизначити, але не можна покликати — і це декого збиває.** Новачок дивується: «як я перевизначаю те, до чого не маю доступу?» Відповідь — та сама ортогональність осей: `override` оголошується у власному класі нащадка й підкоряється правилам **перевизначення**, а не **доступу**. Якщо ж нащадкові справді треба покликати базу — це сигнал, що ланка мала бути `protected` (настанова 3), а не мовчазний привід зламати інкапсуляцію.

**Перевірки на `assert` зникають у релізі.** `assert` знімається макросом `NDEBUG`, тож післяумови на `assert` стережуть лише в збірці з зневадженням. Це нормально для тверджень «нащадок дотримав контракту» — вони ловлять помилку **розробника** нащадка на етапі тестів. Але передумови, що залежать від **зовнішніх** даних (порожній список у прикладі), лишай справжньою перевіркою з `throw`: ворота — правильне місце і для дешевих `assert`-тверджень, і для дорогих рантайм-перевірок, головне не плутати, що з них лишиться в релізі.

**Дірка мусить чесно тримати контракт — інакше ворота обдурені.** NVI не рятує від нащадка, який у `renderBody` поверне тіло, що завершується переносом, чи зробить не те, що обіцяв. Він лише дає предкові **місце цей обман зловити** (післяумова). Але сам обов'язок дірки бути придатною заміною очікуваного нікуди не дівся — це [принцип підстановки Лісков](topic:sf-apps/liskov-substitution): якщо крок нащадка порушує обіцянки кроку, каркас, який тим обіцянкам вірив, зробить неправильне. NVI переносить зраду з тихої на гучну (перевірка спрацює), але не скасовує вимоги.

**Ворота невіртуальні — отже, сам інтерфейс за нащадками не змінюється.** Це перевага (контракт стабільний), але й межа: якщо тобі справді потрібно, щоб **сигнатура чи сам публічний контракт** різнилися в нащадках, NVI — не той інструмент, бо він навмисно це й забороняє. Він фіксує інтерфейс і відкриває лише нутро.

**Продуктивність — практично безкоштовна.** Зайвий виклок — це один невіртуальний виклик воріт, який компілятор майже завжди вбудовує (inline); віртуальний виклик дірки — та сама одна диспетчеризація, яку ти мав би й так. Ніякого нового накладу поверх звичайного віртуального виклику NVI не додає.

Що ти виграєш натомість — видно, коли додаєш новий варіант: новий звіт — це новий нащадок з однією написаною дірою, а ворота, перевірки й порядок кроків не змінюються ні на символ. Розширення без правки наявного — це [принцип відкритості-закритості](topic:sf-apps/open-closed) у чистому вигляді, тільки тут його стереже не домовленість, а контроль доступу C++. У цьому й суть NVI: він бере найкрихкіше місце шаблонного методу — обіцянку, що каркас виконається цілим, — і робить її не проханням до нащадка, а властивістю, яку той не має способу порушити.
