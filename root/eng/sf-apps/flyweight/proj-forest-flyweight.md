# ⚙️ Мільйон дерев у пам'яті: робочий легковаговик

Одна річ — намалювати на дошці «важке спільне лежить один раз, легке — окремо». Зовсім інша — зібрати програму, яка справді садить мільйон дерев, і подивитися на лічильник пам'яті. Тут ми це й зробимо: доведемо приклад до коду, який компілюється й запускається, **виміряємо** його слід у пам'яті байт за байтом, а тоді доведемо фабрику до того, чого вимагає реальний рушій, — безпеки на багатьох потоках і роботи з відкритою, наперед невідомою множиною видів. Наприкінці зберемо докупи пастки, кожна з яких у справжньому коді коштує ночі налагодження.

Мова тут — C++, і не з примхи. Уся ця історія — про **байти й потоки**: скільки місця займає поле, коли звільняється об'єкт, хто пише в спільну комірку. C++ показує кожен такий байт очима — `sizeof` не бреше, вказівник видно, час життя об'єкта в руках у програміста. Саме такими мовами й пишуть рушії, де мільйон дерев — буденність.

## Задача: зібрати ліс і виміряти, скільки він важить

Ціль конкретна. Треба структура `Forest`, у якій живе рівно 1 000 000 дерев трьох видів — дуб, сосна, береза. Кожен вид важкий: сітка з десятків тисяч вершин плюс текстура. Кожне дерево має власне місце й розмір. Ми хочемо не оцінку на серветці, а **число з лічильника пам'яті працюючого процесу** — і хочемо розкласти це число на доданки, щоб бачити, куди пішов кожен мегабайт.

І одразу перша чесна перешкода, яка сама по собі — половина уроку. **Наївний варіант виміряти не можна**, бо він не запуститься. Якщо кожне дерево носить власну копію важкого виду, мільйон дерев просить близько терабайта, і `operator new` кине `bad_alloc` ще на першій тисячі. Отже, «вимірювання наївного» — це не число, а **невдале виділення пам'яті**; сам факт, що його не зміряти, і є причина, чому легковаговик тут не оптимізація, а єдиний спосіб існування сцени. Тому наївний бік ми **порахуємо** (арифметика точна), а бік легковаговика — **запустимо й зміряємо**, і зведемо одне з одним.

## Ідея: три ролі — вид, дерево, фабрика

Розв'язок розкладається на три типи, і кожен відповідає на одне питання про стан.

- **`TreeKind`** — вид. Тримає **внутрішній стан**: те, що однакове в усіх дубів (сітка, текстура, колір). Важкий, **спільний**, **незмінний**. Один примірник на вид.
- **`Tree`** — конкретне дерево. Тримає **зовнішній стан**: координати, масштаб — і **вказівник** на свій вид. Крихітний, свій у кожного.
- **`TreeKindFactory`** — фабрика. Стереже єдину обіцянку, на якій усе тримається: **двох об'єктів „дуб" не існує**. Той самий ключ завжди повертає той самий примірник виду.

Далі — покроково збираємо ці три, міряємо, а тоді загартовуємо фабрику проти потоків і відкритих ключів.

## Крок 1. Вид-легковаговик: важкий і незмінний

Почнімо з виду. Головна вимога до нього — **незмінність**: якщо на цей об'єкт указує сто тисяч дубів, то будь-яка зміна поля миттєво зачепить усіх. Тому в C++ ми зашиваємо незмінність прямо в тип — поля `const`, жодного сеттера, назовні лише читання. Компілятор стане на варті: спроба щось присвоїти виду просто не збереться.

```cpp
#include <cstdint>
#include <string>
#include <vector>

struct Vertex {                       // одна вершина сітки
    float px, py, pz;                 // позиція     12 Б
    float nx, ny, nz;                 // нормаль      12 Б
    float u,  v;                      // текстурні    8 Б  → 32 Б на вершину
};

// Внутрішній стан: важкий, СПІЛЬНИЙ, НЕЗМІННИЙ.
class TreeKind {
public:
    TreeKind(std::string name, std::vector<Vertex> mesh,
             uint32_t texture, uint32_t color)
        : name_(std::move(name)), mesh_(std::move(mesh)),
          texture_(texture), color_(color) {}

    const std::string&          name()    const { return name_; }
    const std::vector<Vertex>&  mesh()     const { return mesh_; }
    uint32_t                    texture() const { return texture_; }
    uint32_t                    color()   const { return color_; }

private:
    const std::string           name_;    // "дуб", "сосна", "береза"
    const std::vector<Vertex>   mesh_;     // десятки тисяч вершин ≈ 1 МБ
    const uint32_t              texture_;  // хендл текстури
    const uint32_t              color_;    // RGBA
};
```

Зверни увагу, де насправді лежить вага. Сам об'єкт `TreeKind` — це лише **заголовки**: рядок (кілька десятків байтів), заголовок вектора (вказівник + два розміри, 24 Б), два числа. Разом `sizeof(TreeKind)` — десятки байтів. А весь мегабайт — це **буфер сітки** на купі, на який заголовок вектора лише вказує. Оце розрізнення — «дешевий заголовок проти важкого буфера» — і буде ключем, коли доберемося до вимірювання: рахуючи пам'ять, ми маємо рахувати саме буфери, а не `sizeof` оболонок.

> 🔧 **Навіщо це.** Поля `const` тут не косметика й не «гарний стиль». Вони — **машина безпеки спільного використання**: щойно ти ділиш об'єкт між тисячами власників, єдина твоя гарантія від хаосу — що його ніхто не змінить. Зробивши поля незмінними на рівні типу, ти переклав цю гарантію з дисципліни програміста (яку легко забути) на компілятор (який не забуває ніколи). Ціна такого спокою — нуль байтів і нуль тактів.

## Крок 2. Дерево-контекст і `Forest`

Тепер легка частина — те, що множиться мільйон разів, тож кожен байт тут коштує мегабайт на масштабі. Дерево — це його зовнішній стан плюс вказівник на спільний вид.

```cpp
struct Tree {
    float           x, y, z;      // де стоїть          12 Б
    float           scale;        // який завбільшки     4 Б
    const TreeKind* kind;         // вказівник на СПІЛЬНИЙ вид   8 Б
};                                // sizeof(Tree) == 24 Б

class Forest {
    std::vector<Tree> trees_;
public:
    void reserve(std::size_t n)   { trees_.reserve(n); }
    void plant(float x, float y, float z, float s, const TreeKind* k) {
        trees_.push_back({x, y, z, s, k});
    }
    std::size_t size() const      { return trees_.size(); }
    const std::vector<Tree>& all() const { return trees_; }
};
```

`sizeof(Tree)` дорівнює рівно 24 — три числа позиції, число масштабу, вказівник, і жодного вирівнювального «хвоста», бо все й так лягає на межу восьми байтів. Це важливо тримати в голові: на мільйоні дерев кожні зайві 8 байтів у `Tree` — це +8 МБ до сліду. Тому вказівник (8 Б) — найдешевша можлива форма «належати до виду»; будь-що важче тут окупиться дорого.

Одна деталь про `reserve`. Вектор, доростаючи, час від часу подвоює буфер і **копіює** все на нове місце — на мільйоні це і зайвий сплеск пам'яті (старий і новий буфери на мить існують разом), і зайва робота. `reserve(1'000'000)` виділяє точний буфер **один раз**, тож слід буде рівно `24 × N`, без запасу ємності зверху.

## Крок 3. Фабрика: гарантія одного примірника

Фабрика — це [мапа](root:sf-algorithms/hash-table) «ключ виду → примірник» з однією операцією `get`. Проси «дуб»: є в мапі — повертається той самий об'єкт; нема — фабрика створює його **раз**, кладе в мапу й повертає. Мапа й робить дублікат неможливим.

```cpp
#include <memory>
#include <unordered_map>

class TreeKindFactory {
    std::unordered_map<std::string, std::unique_ptr<TreeKind>> pool_;
public:
    const TreeKind* get(const std::string& name) {
        if (auto it = pool_.find(name); it != pool_.end())
            return it->second.get();               // уже є — той самий примірник
        auto kind = load_tree_kind(name);          // нема — дорого читаємо з диска РАЗ
        const TreeKind* raw = kind.get();
        pool_.emplace(name, std::move(kind));
        return raw;
    }
};
```

Тут варто зупинитися на одному непомітному, але критичному факті: **повернений `const TreeKind*` лишається чинним, доки живий запис у мапі**. `std::unordered_map` — вузловий контейнер: його вузли не рухаються при рехешуванні (переставляються лише зв'язки в кошиках), тож і `unique_ptr` усередині вузла, і `TreeKind` під ним стоять на місці. Це не дрібниця стилю — на цьому тримається вся модель: тисячі дерев тримають сирий вказівник на вид і покладаються, що він не «поїде» під ними. Якби ми поклали `TreeKind` у `std::vector` (де при рості все переїжджає), усі ці вказівники стали б висячими після першого ж перевиділення. Вузлова мапа + виділення на купі через `unique_ptr` дають подвійну стабільність адреси, і саме тому вона тут доречна.

## Крок 4. Виміряти пам'ять по-справжньому

Дійшли до серця проєкту. Заведемо функцію, що читає **резидентний набір** процесу (англ. *resident set size*, RSS) — скільки фізичної пам'яті процес зараз реально займає. На Linux це друге число у `/proc/self/statm`, у сторінках.

```cpp
#include <cstdio>
#include <unistd.h>

// Резидентний набір процесу в кілобайтах.
long resident_kib() {
    long total_pages = 0, rss_pages = 0;
    if (FILE* f = std::fopen("/proc/self/statm", "r")) {
        if (std::fscanf(f, "%ld %ld", &total_pages, &rss_pages) != 2)
            rss_pages = 0;
        std::fclose(f);
    }
    return rss_pages * (sysconf(_SC_PAGESIZE) / 1024);   // сторінки → КБ
}
```

> 🔧 **Навіщо це.** RSS — це не `sizeof` і не «скільки я попросив у `new`». Це **скільки фізичних сторінок ОС справді віддала процесу зараз**. Різниця принципова: пам'ять, яку ти виділив, але ще не торкнувся, може взагалі не мати фізичних сторінок (лінива підкачка), а пам'ять, яку алокатор округлив угору, — навпаки, більша за прошену. Тому єдиний чесний спосіб дізнатися, скільки ліс важить насправді, — зміряти RSS **до** й **після** засадження й узяти різницю; ця різниця відкидає незмінний фон (код, libc) і лишає слід самого лісу. Що таке резидентний набір проти віртуального адресного простору — у темі [віртуальна пам'ять](root:hw-arch/virtual-memory).

Тепер сам експеримент — головна функція, що засаджує мільйон дерев і бере два знімки лічильника.

```cpp
#include <random>

int main() {
    long before = resident_kib();

    TreeKindFactory kinds;
    const TreeKind* species[] = {
        kinds.get("oak"), kinds.get("pine"), kinds.get("birch"),
    };

    Forest forest;
    forest.reserve(1'000'000);                       // точний буфер, без запасу
    std::mt19937 rng(42);
    std::uniform_real_distribution<float> pos(0.f, 10000.f), sc(0.7f, 1.4f);
    for (int i = 0; i < 1'000'000; ++i)
        forest.plant(pos(rng), 0.f, pos(rng), sc(rng), species[i % 3]);

    long after = resident_kib();
    std::printf("дерев: %zu   приріст RSS: %.1f МБ\n",
                forest.size(), (after - before) / 1024.0);
}
```

Перш ніж дивитися на число, **порахуймо, чого чекати** — інакше нема з чим звіряти. Нехай сітка кожного виду — 30 000 вершин по 32 Б.

```
Легковаговик — точний підрахунок «живих» даних:
  дерева:   1 000 000 × sizeof(Tree)=24 Б  = 24 000 000 Б  ≈ 24.0 МБ
  сітки:    3 × (30 000 верш. × 32 Б)       =  2 880 000 Б  ≈  2.9 МБ
  фабрика:  3 заголовки TreeKind + мапа     <      5 000 Б  ≈  0.0 МБ
  ──────────────────────────────────────────────────────────────────
  «живі» дані                                             ≈ 26.9 МБ
```

Двадцять сім мегабайтів «серветкою». А тепер — що покаже запуск.

```
приріст RSS (after − before), типовий 64-бітний Linux:
  ≈ 27–28 МБ    ← майже точно 26.9 + дрібне округлення буферів до сторінки

абсолютний RSS процесу:
  ≈ 31 МБ       ← той самий ліс + ~3–4 МБ незмінного рантайму (код, libc)
```

Зупинімося на цій розбіжності, бо в ній — практичний урок. **Приріст** RSS майже точно збігається із серветковими 26.9 МБ: `sizeof` не бреше, а `reserve` не дав вектору роздутися. Ті кілька зайвих сотень кілобайтів — це округлення буферів угору: алокатор віддає пам'ять не байт-у-байт, а блоками, і великі буфери (сітки, вектор дерев) кладе цілими сторінками по 4 КБ. **Абсолютний** RSS більший ще на 3–4 МБ — це код самої програми й libc, відображені резидентно; цей фон **не залежить від N** і однаковий що для лісу з мільйона дерев, що для порожнього `main`. Ось чому ми міряємо саме різницю: вона ізолює ліс від фону. Чому виміряне завжди трохи більше за пораховане й звідки беруться ці округлення — у темі [внутрішня будова алокатора](root:sf-lang/memory-allocator-internals).

А наївний бік? Його «вимірювання» ми вже знаємо — це виняток.

```
Наївно — порахувати можна, ЗАПУСТИТИ не можна:
  struct FatTree { TreeKind kind;  float x,y,z,scale; };   // вид у ТІЛІ дерева
  sizeof важкої частини кожного FatTree ≈ 0.96 МБ (сітка в тілі)
  1 000 000 × 0.96 МБ ≈ 960 000 МБ ≈ 0.94 ТБ
  → bad_alloc уже на першій тисячі дерев; RSS зміряти нема на чому
```

Порівняння говорить саме за себе: 31 мегабайт **виміряного** проти терабайта **непорахованого-бо-неможливого**. Це не «економія відсотків» — це різниця між програмою, що існує, і програмою, що падає на старті. І весь виграш прийшов з одного розрізу: важке — один раз на вид, легке — окремо на дерево, а між ними — 8-байтовий вказівник.

![Стовпчик виміряної пам'яті легковаговика, розкладений на доданки: великий блок вектора дерев близько 24 МБ, менший блок сіток видів близько 2.9 МБ, тонка смужка фабрики й мапи, і зверху окремим кольором незмінний фон рантайму близько 3.5 МБ; пунктирна лінія позначає серветкові 27 МБ, підпис показує, що приріст RSS збігається з нею, а абсолютний RSS вищий рівно на фон.](img/realmem.svg)

*Виміряний слід лісу майже точно дорівнює серветковому підрахунку; різниця між приростом RSS і абсолютним RSS — це незмінний рантайм, що не залежить від кількості дерев. Рахуючи пам'ять, рахуй буфери на купі, а фон відкидай різницею до/після.*

## Крок 5. Багато потоків: `get()` під навантаженням

Досі фабрика жила в одному потоці. Але рушій завантажує світ **паралельно** — кілька робочих потоків садять дерева одночасно, і кожен смикає `factory.get(...)`. Наївна фабрика тут ламається, і варто побачити точно, як.

Уяви два потоки, обидва вперше просять «дуб». Потік A заходить у `get`, робить `pool_.find("oak")` — не знайшов. Тієї ж миті потік B теж робить `find("oak")` — теж не знайшов, бо A ще нічого не вставив. Тепер **обидва** викликають дороге `load_tree_kind("oak")` і **обидва** вставляють у мапу. У кращому разі ми завантажили важку сітку двічі й тихо втратили половину виграшу. У гіршому — два потоки одночасно пишуть в `unordered_map`, а він до конкурентного запису не готовий: перебудова кошиків з двох потоків руйнує внутрішні зв'язки, і програма падає або псує пам'ять. Це класична [перегони даних](root:sf-tasks/data-races-locks) — два потоки без синхронізації торкаються спільної структури, і принаймні один її змінює.

![Часова стрічка перегонів у get. Угорі два потоки A і B ідуть паралельно: обидва роблять find «дуб» і обидва не знаходять, бо жоден ще не вставив; далі обидва викликають дороге load «дуб» і обидва вставляють у мапу — унизу підпис, що вид завантажено двічі, а конкурентний запис псує мапу. Нижче окрема панель із виправленням: спільний замок на читання пропускає обох у find паралельно, а на промаху береться ексклюзивний замок і робиться ПОВТОРНА перевірка — другий потік бачить уже вставлений вид і не створює дубль.](img/getrace.svg)

*Без синхронізації два потоки бачать однаковий промах і обидва створюють «дуб» — у кращому разі подвійне завантаження, у гіршому — зруйнована мапа. Правильний `get` читає під спільним замком, а на промаху перевіряє ще раз під ексклюзивним, бо між двома замками інший потік міг уже вставити.*

Полагодити можна грубо — обгорнути весь `get` в один `std::mutex`. Це коректно, але марнотратно: після прогріву **всі** виклики — це влучення (три види давно в мапі), тобто чисте читання, а грубий замок серіалізує навіть читачів — тридцять потоків стоять у чергу за операцією, яка нічого не змінює. Тут напрошується точніший інструмент. Фабрика видів — це сховище, яке **читають дуже часто й пишуть дуже рідко** (рівно K разів за все життя, де K — число видів). Саме для такого профілю існує [замок «багато читачів, один письменник»](root:sf-tasks/readers-writer-lock) (`std::shared_mutex`): будь-яка кількість читачів заходить **одночасно**, а письменник — рідкісний і сам-один.

```cpp
#include <shared_mutex>

class TreeKindFactory {
    mutable std::shared_mutex mtx_;
    std::unordered_map<std::string, std::unique_ptr<TreeKind>> pool_;
public:
    const TreeKind* get(const std::string& name) {
        {   // ── швидкий шлях: багато читачів ПАРАЛЕЛЬНО ──
            std::shared_lock read(mtx_);
            if (auto it = pool_.find(name); it != pool_.end())
                return it->second.get();
        }
        // ── промах: рідкісний ЕКСКЛЮЗИВНИЙ запис ──
        std::unique_lock write(mtx_);
        // ПОВТОРНА перевірка: поки ми відпускали read і брали write,
        // інший потік міг уже вставити цей самий вид.
        if (auto it = pool_.find(name); it != pool_.end())
            return it->second.get();
        auto kind = load_tree_kind(name);
        const TreeKind* raw = kind.get();
        pool_.emplace(name, std::move(kind));
        return raw;
    }
};
```

Найтонше місце тут — **повторна перевірка** після взяття ексклюзивного замка, і вона не випадкова. Між тим, як ми відпустили спільний замок (промах) і взяли ексклюзивний, минає час, і саме в цей проміжок інший потік, що теж промахнувся, міг уже створити й вставити «дуб». Якби ми одразу створювали свій — знову дубль. Тому під ексклюзивним замком ми **дивимося ще раз**: якщо вид уже там — беремо чужий і викидаємо намір створювати. Це та сама схема «перевір-замкни-перевір ще раз» (англ. *double-checked locking*), і пропущена друга перевірка — один із найтиповіших багів конкурентних кешів.

А тепер найкрасивіше, і воно пояснює, чому легковаговик так добре лягає на багатопотоковість. Синхронізувати треба **лише `get`** — саме створення. Щойно `get` повернув `const TreeKind*`, тисячі потоків можуть читати цей вид **одночасно й без жодного замка**. Чому? Бо вид **незмінний**: немає запису — немає й перегонів; читати спільні незмінні дані з будь-якої кількості потоків завжди безпечно. Незмінність внутрішнього стану, яку ми ввели заради безпеки спільного використання, дарма дає ще й **безкоштовне** паралельне читання. Загальніше про те, коли спільний доступ безпечний, — у темі [потокобезпека](root:sf-tasks/thread-safety).

> 🔧 **Навіщо це.** Тут видно, як два рішення, ухвалені з різних причин, підсилюють одне одного. Незмінність виду ми взяли, щоб один дуб не перефарбував увесь ліс. А отримали на додачу те, що весь гарячий шлях — читання видів під час малювання кожного кадру — не потребує **ніякої** синхронізації взагалі. Замок лишився тільки на холодному шляху створення, який стається K разів за життя. Це і є ознака доброго дизайну: властивість, узята заради одного, безкоштовно закриває інше.

Для **закритої** множини видів (три відомі наперед) є ще простіший хід, ніж будь-який замок: завантаж усі види **до** старту робочих потоків, одним потоком, а далі мапу лише читай. Тоді синхронізація не потрібна взагалі — немає жодного запису під час паралельної роботи. Замок на `get` потрібен рівно тоді, коли види **відкриваються ліниво**, під час гри, — а це наступний, найцікавіший рівень задачі.

## Крок 6. Відкрита множина ключів: слабкі посилання й витіснення

Три види — це закрита множина: наперед відома й крихітна. Але справжній світ рідко такий охайний. Вид дерева насправді залежить не лише від породи, а й від **сезону** (літній дуб зелений, осінній — рудий), **рівня деталізації** (близький дуб — повна сітка, далекий — спрощена), біома, відтінку. Ключ виду стає складеним, а множина ключів — **відкритою**: не три значення, а сотні чи тисячі комбінацій, більшість з яких у грі й не з'явиться, а які з'являться — заздалегідь невідомо.

І тут закрита фабрика ламається новим, тихим чином. Мапа «ключ → примірник» **ніколи нічого не відпускає**. Гравець пройшов осінню локацію й пішов далі — а всі осінні види досі в мапі, і їхні мегабайтні сітки досі в пам'яті, хоча жодне дерево на них уже не вказує. Кеш, який тільки росте, — це **витік пам'яті в сповільненому темпі**: не помилка в один хибний байт, а повільне, невідворотне сповзання до `bad_alloc` за годину гри. (У мовах зі [збирачем сміття](root:sf-lang/garbage-collection) наслідок той самий, лише механізм інший: мапа **вкорінює** об'єкти, тож збирач не має права їх звільнити, хоч на них ніхто, крім кеша, й не посилається.)

Потрібен кеш, який тримає вид **рівно доти, доки ним хтось користується**, і відпускає, коли останнє дерево того виду зникло. Саме це дає пара «сильне посилання / слабке посилання». Ідея — на [підрахунку посилань](root:sf-lang/reference-counting): у `std::shared_ptr` живе лічильник власників; коли він падає до нуля, об'єкт знищується. `std::weak_ptr` **спостерігає** за об'єктом, **не** додаючи до лічильника, — і чесно каже, живий той ще чи вже ні.

Розподіл ролей стає такий: **дерева тримають сильне** посилання на свій вид (`shared_ptr`), а **фабрика — лише слабке** (`weak_ptr`). Поки бодай одне дерево вказує на «дуб-осінь-LOD2», лічильник власників більший за нуль і вид живий. Зникло останнє таке дерево — лічильник падає до нуля, вид знищується, його важка сітка звільняється, а слабкий запис у фабриці «протухає». Наступний запит того виду побачить мертве слабке посилання й перезавантажить вид заново.

![Життя виду через п'ять стадій зліва направо. Перший запит: вид завантажено за адресою 0xA1, одне дерево тримає сильне посилання, лічильник власників 1, у мапі слабке посилання. Багато дерев: власників N, усі вказують на 0xA1. Дерева зникають: власників меншає. Останнє зникло: власників 0, вид знищено й сітку звільнено, слабке посилання протухло і lock() дає null. Запит знову: вид перезавантажено за НОВОЮ адресою 0xF7, і 0xF7 не дорівнює 0xA1 — старий shared_ptr більше не збігається. Внизу підпис, що слабке посилання не володіє видом, а порівнювати види треба за ключем, не за адресою.](img/weaklife.svg)

*Вид живе рівно доти, доки його тримає хоч одне дерево; коли останнє зникло, він гине разом зі своєю сіткою, а слабкий запис у фабриці протухає. Попросиш знову — вид відродиться за іншою адресою, тому захоплений раніше вказівник із ним уже не збігається: види порівнюй за ключем, а не за адресою.*

```cpp
#include <memory>
#include <shared_mutex>
#include <unordered_map>

struct KindKey {                          // складений ключ відкритої множини
    std::string species;
    uint8_t     season;                   // 0..3
    uint8_t     lod;                      // 0..3
    bool operator==(const KindKey&) const = default;
};
struct KindKeyHash {
    std::size_t operator()(const KindKey& k) const {
        std::size_t h = std::hash<std::string>{}(k.species);
        h = h * 31 + k.season;            // дешево поєднуємо доданки ключа
        h = h * 31 + k.lod;
        return h;
    }
};

class WeakKindFactory {
    std::shared_mutex mtx_;
    std::unordered_map<KindKey, std::weak_ptr<const TreeKind>, KindKeyHash> pool_;
public:
    // Повертає СИЛЬНЕ посилання — його триматиме дерево-власник.
    std::shared_ptr<const TreeKind> get(const KindKey& key) {
        {   // швидкий шлях: читачі паралельно
            std::shared_lock read(mtx_);
            if (auto it = pool_.find(key); it != pool_.end())
                if (auto sp = it->second.lock())      // ще живий?
                    return sp;
        }
        std::unique_lock write(mtx_);
        if (auto it = pool_.find(key); it != pool_.end())
            if (auto sp = it->second.lock())          // повторна перевірка
                return sp;
        auto sp = std::make_shared<const TreeKind>(load_tree_kind(key));
        pool_[key] = sp;                              // фабрика тримає СЛАБКЕ
        return sp;                                    // сильне йде власникові
    }

    // Прибрати «протухлі» записи — інакше ростуть самі ключі.
    void prune() {
        std::unique_lock write(mtx_);
        for (auto it = pool_.begin(); it != pool_.end(); )
            it = it->second.expired() ? pool_.erase(it) : std::next(it);
    }
};
```

Дерево тепер тримає `std::shared_ptr<const TreeKind> kind;` замість сирого вказівника — і за це доводиться платити. `shared_ptr` — це 16 байтів (вказівник на об'єкт + вказівник на керівний блок), тож `Tree` виростає з 24 до 32 байтів, а ліс — з 24 до 32 МБ. Ці +8 МБ — **ціна відкритості**: за гнучкість довільної множини видів кожне дерево доплачує вказівником на керівний блок і трафіком атомарного лічильника. Для закритої множини сирий 8-байтовий вказівник дешевший, тож бери відкриту схему лише тоді, коли множина ключів справді відкрита.

Тепер про **витіснення рідкісних видів** — воно ховає дві пастки, які легко проґавити.

Перша: слабка мапа звільняє **сітку**, але не звільняє **сам запис**. Коли вид помер, `weak_ptr` у мапі протух, але ключ і порожня оболонка досі в мапі — і таких мертвих записів з часом громадяться тисячі. Мало того: `make_shared` кладе об'єкт і керівний блок **одним шматком**, тож поки живий бодай один `weak_ptr`, ця оболонка (хоч і без важкої сітки — її звільнив деструктор вектора при смерті виду) не звільняється зовсім. Тому слабку мапу треба **періодично проріджувати** — саме це робить `prune`, викидаючи протухлі записи; без нього ти проміняв витік мегабайтів на повільніший витік кілобайтів, але витік лишився.

Друга, підступніша: **тремтіння** (англ. *thrashing*). Уяви далеку галявину, якою камера ковзає: дерева одного рідкісного виду щомиті то з'являються, то зникають з поля зору. Якщо вид тримається лише сильними посиланнями від дерев, то в момент, коли зникло останнє дерево, вид помирає — а за кадр його знову просять і **перезавантажують важку сітку з диска**. Той самий дорогий вид завантажується десятки разів на секунду. Ліки — **закріпити гарячі види**: тримати невеликий список останніх використаних видів **сильними** посиланнями, щоб вони не вмирали між кадрами.

```cpp
#include <deque>

class PinnedCache {
    static constexpr std::size_t CAP = 64;               // скільки гарячих тримати
    std::deque<std::shared_ptr<const TreeKind>> hot_;     // СИЛЬНІ пінувальні посилання
public:
    void touch(std::shared_ptr<const TreeKind> k) {
        hot_.push_front(std::move(k));
        if (hot_.size() > CAP) hot_.pop_back();           // найхолодніший втрачає пін
    }
};
```

Механіка проста, а ефект точний. `hot_` тримає сильні посилання на 64 останні види, тож жоден з них не помре, навіть якщо тимчасово жодне дерево на нього не вказує, — гарячий вид не тремтить. Холодний же вид виштовхується з `hot_` найновішими, втрачає своє останнє сильне посилання (якщо його не тримає жодне дерево) і чесно вмирає через слабку мапу — його сітка звільняється, а перезавантажиться він лише як його знову попросять. Виходить рівно те, чого хотіли: **гарячі види резидентні, холодні — витісняються**, і межу між ними проводить частота використання, а не програміст уручну.

> 🔧 **Навіщо це.** Тут легковаговик доростає до справжнього кеша, і видно загальний закон усіх кешів: **тримати треба те, чим користуються, і відпускати те, чим ні, — але вимірювати „користуються" обережно**. Занадто чіпкий кеш (сильна мапа) витікає; занадто швидкий на відпускання (гола слабка мапа без піна) тремтить, знову й знову платячи за дороге завантаження. Правильна відповідь — двошарова: слабкі посилання ловлять «більше не потрібне», а невеликий пін гарячого не дає викинути «щойно було потрібне». Цю ж пару — слабкий кеш плюс пін гарячого — ти зустрінеш у кешах текстур, шрифтів, скомпільованих шейдерів; скрізь, де ключів багато, а гарячих серед них жменя.

## Пастки, що коштують ночей налагодження

Тепер зберемо гострі кути в одному місці. Кожен з них — не гіпотетичний, а реальний баг, що трапляється саме в цьому коді.

**Змінний внутрішній стан — аліасинг.** Найгостріша й найтиповіша. Поклав у спільний вид бодай одне поле, яке комусь захочеться змінити «для цього дерева», — і зміна протече в усіх власників.

```cpp
// НЕ РОБИ ТАК: змінне поле у СПІЛЬНОМУ виді
struct BadTreeKind { uint32_t tint; /* ... сітка, текстура ... */ };

tree.kind->tint = RED;      // ← зафарбували ВЕСЬ ліс: усі дуби вказують на цей вид
```

Один рядок «підфарбуй мій дуб» червонить сто тисяч дубів разом, бо всі вони — той самий об'єкт. Це аліасинг у чистому вигляді: багато імен на одну комірку, і запис через одне ім'я видно крізь усі решта. Ось чому поля `TreeKind` ми зробили `const`: `tint` — це властивість **примірника**, отже, він належить `Tree` (зовнішній стан) або передається в `draw(canvas, x, y, tint)` аргументом, а не живе у спільному виді. Загальніше про те, як спільна змінна комірка під кількома вказівниками породжує загадкові зв'язані зміни, — у темі [аліасинг покажчиків](root:sf-lang/pointer-aliasing).

**Тотожність проти рівності.** З дедуплікувальною фабрикою спокусливо перевіряти «однакового виду?» порівнянням вказівників:

```cpp
bool same_species(const Tree& a, const Tree& b) {
    return a.kind == b.kind;      // ← працює ЛИШЕ тому, що фабрика дедуплікує
}
```

І це **працює** — але лише тому, що фабрика гарантує один примірник на ключ, тож рівність значення («той самий вид») збігається з тотожністю адреси («той самий об'єкт»). Ця рівність — **наслідок інваріанта фабрики**, а не властивість мови, і вона ламається двома шляхами. Перший: хтось створив вид повз фабрику (`new TreeKind{...}`) або завів другу фабрику — і ось уже два різні об'єкти «дуб», між якими `==` хибно каже «різні види». Другий, хитріший, вилазить саме у слабкій схемі з витісненням: вид «дуб-осінь» помер і **перезавантажився за новою адресою** — і `shared_ptr`, який десь захопили **до** витіснення, не дорівнює перезавантаженому, хоча це семантично той самий вид. Правило: порівнюй вказівники на тотожність **лише** там, де інваріант фабрики тримається й записи стабільні; де види можуть витіснятися й відроджуватися — порівнюй **за ключем**, а не за адресою.

**Необмежений кеш — витік.** Уже названо, але варте окремого правила, бо помилка тиха. Закрита мапа на три види — обмежена й безпечна назавжди. Сильна мапа на **відкриту** множину ключів — повільний витік: вона вкорінює кожен вид, який колись бачила. Навіть слабка мапа витікає **самими ключами**, якщо її не проріджувати. Правило по межі: **обмежена множина ключів → проста мапа сильних посилань; відкрита → слабка мапа + `prune` + пін гарячого**. Помилка тут не валить програму одразу — вона з'їдає пам'ять годину, а тоді валить у найгіршу мить.

**Атомарний лічильник теж спільний.** Тонкість відкритої схеми, що змикається з темою потоків. Кожне копіювання чи знищення `shared_ptr` — це **атомарна** зміна спільного лічильника власників. Якщо мільйон дерев створюється й гине на багатьох ядрах, лічильник одного популярного виду стає гарячою спільною коміркою, за яку ядра труться — тим самим коштом когерентності кешів, що й будь-яка спільна змінна. Для здебільшого статичного лісу (посадив раз — малюєш багато кадрів) це пусте: посилання не крутяться. Для світу з бурхливою появою-зникненням дерев — реальна ціна, і це ще один аргумент на користь сирого вказівника й закритої фабрики там, де множина видів насправді закрита.

## Складність і межа доречності

Складність кожного `get` — **амортизовано O(1)**: хеш-пошук у мапі плюс, на промаху, одноразове завантаження. Під `shared_mutex` влучення (майже всі виклики після прогріву) йдуть паралельно, тож на гарячому шляху фабрика читачів не серіалізує зовсім. Пам'ять розкладається так:

```
                 пам'ять                          get()
──────────────────────────────────────────────────────────────────────
наївно       N × S  (S — важкий вид)          не існує: не виділяється
легковаговик N × c  +  K × S                  амортизовано O(1),
             (c — контекст 24–32 Б,           читання паралельні
              K — число видів)                (вид незмінний)
```

Головне число сховане в цій формулі: виграш — це `N·(S − c)` заощаджених байтів, і він великий рівно тоді, коли збігаються три умови. Об'єктів **дуже багато** (велике N), різних видів **мало** (мале K), і сам вид **важкий** (велике S). Прибери будь-яку — і легковаговик втрачає сенс: якщо різних видів майже стільки ж, скільки дерев (K ≈ N), ділити нема чого, і лишається сама накладна вартість фабрики та зайвий вказівник. Ліс із мільйона дерев трьох видів — це N = 10⁶, K = 3, S ≈ 1 МБ: усі три умови на максимумі, тому й виграш у десятки тисяч разів.

Зрештою, весь проєкт — це одне питання, поставлене до важкого об'єкта, якого стало забагато: **що тут про вид, а що про цей конкретний примірник?** — плюс тверда інженерна дисципліна навколо відповіді. Вид зроби незмінним, і спільне використання стане безпечним, а читання — паралельним задарма. Створення сховай за фабрикою, і дублікати стануть неможливими, а `get` — потокобезпечним однією повторною перевіркою. Час життя віддай парі «сильне/слабке», і кеш сам відпускатиме непотрібне, а пін гарячого не дасть йому тремтіти. Кожен крок тут — не трюк, а пряме продовження того першого розрізу стану на «спільне важке» й «окреме легке»; саме він і перетворює терабайт, що не існує, на тридцять мегабайтів, які можна зміряти.
