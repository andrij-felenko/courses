# ⚙️ Заміни розгалужений `switch` на стратегію: рефакторинг крок за кроком

Стратегія рідко приходить у код як задум на чистому аркуші. Куди частіше вона **народжується з болю**: був простий метод з двома гілками, він поволі оброс третьою, п'ятою, десятою, і одного дня ти відкриваєш файл, бачиш `switch` на пів екрана й розумієш, що кожна нова вимога знову жбурне тебе саме сюди. Це найчастіший шлях до стратегії в реальній роботі — не «спроєктувати наперед», а **помітити пахощ і зробити заміну**. Розберімо цю заміну до останнього кроку на наскрізному прикладі, який видно наскрізь: **обчислення вартості доставки залежно від служби**.

Мета — не просто «розкидати гілки по класах», а зробити це так, щоб на виході код став чеснішим: спільне лишилося в одному місці, відмінне роз'їхалося по своїх, а додати нову службу стало **дописуванням збоку, а не хірургією в наявному**. Пройдемо весь шлях: побачимо пахучий метод, витягнемо інтерфейс, винесемо кожну гілку, розберемося, куди подіти спільний і відмінний код, замінимо сам `switch` на мапу «тип → стратегія» — і аж наприкінці чесно скажемо, коли всього цього робити **не** треба.

## Задача

Магазин рахує вартість доставки. Служб спершу було дві, тепер чотири, і кожна лічить по-своєму: одна бере плоску ставку плюс за кілограм, інша — за зони віддалі, третя дає безкоштовно понад поріг суми, кур'єрська — множник на терміновість. Уся ця логіка стеклася в один метод:

:::tabs
```ts
type Carrier = "flat" | "zonal" | "free_over" | "courier";

class Shipment {
  constructor(
    public carrier: Carrier,
    public weightKg: number,
    public distanceKm: number,
    public orderTotal: number,
    public express: boolean,
  ) {}

  shippingCost(): number {
    // ← пахучий метод: усі служби зашиті в один switch
    switch (this.carrier) {
      case "flat":
        return 50 + this.weightKg * 10;

      case "zonal": {
        const zone = Math.ceil(this.distanceKm / 100); // 1 зона = 100 км
        return 40 + zone * 25;
      }

      case "free_over":
        if (this.orderTotal >= 1000) return 0;
        return 60 + this.weightKg * 8;

      case "courier": {
        const base = 80 + this.distanceKm * 1.5;
        return this.express ? base * 1.6 : base;
      }

      default:
        throw new Error(`Невідома служба: ${this.carrier}`);
    }
  }
}
```
```py
from math import ceil
from dataclasses import dataclass

@dataclass
class Shipment:
    carrier: str          # "flat" | "zonal" | "free_over" | "courier"
    weight_kg: float
    distance_km: float
    order_total: float
    express: bool

    def shipping_cost(self) -> float:
        # ← пахучий метод: усі служби зашиті в один if-ланцюг
        if self.carrier == "flat":
            return 50 + self.weight_kg * 10

        if self.carrier == "zonal":
            zone = ceil(self.distance_km / 100)   # 1 зона = 100 км
            return 40 + zone * 25

        if self.carrier == "free_over":
            if self.order_total >= 1000:
                return 0.0
            return 60 + self.weight_kg * 8

        if self.carrier == "courier":
            base = 80 + self.distance_km * 1.5
            return base * 1.6 if self.express else base

        raise ValueError(f"Невідома служба: {self.carrier}")
```
:::

Придивімося, **чому** це болить, — бо без діагнозу лікування наосліп. Тут не одна проблема, а кілька, і вони складаються.

Перше: **метод знає забагато**. `Shipment` — це «що відправляємо»: вага, віддаль, сума. А `shippingCost` замість цього тримає в собі **весь тарифний довідник усіх служб**. Це два різні предмети, силою зшиті в одне тіло. Тарифи міняються часто (маркетинг домовився з новим перевізником, підняли ставку за зону) — і кожна така зміна змушує чіпати клас `Shipment`, який до тарифів стосунку не має.

Друге: **гілки не існують як окремі речі**. Формулу зональної доставки не можна взяти, протестувати ізольовано, повторно вжити деінде чи віддати іншій людині на супровід. Вона не об'єкт і не функція — вона просто шматок усередині чужого `switch`, приклеєний до сусідніх гілок спільною змінною й спільним `return`.

Третє, і найгостріше: **кожна нова служба — правка в цьому самому місці**. Додати «пошту» — знову відкрити `shippingCost`, знову втиснути `case`, знову ризикнути зачепити сусідні гілки. Це прямо суперечить [принципу відкритості-закритості](topic:sf-apps/open-closed): код мав би рости дописуванням нового збоку, а не розрізанням наявного. Файл `Shipment` перетворився на **магніт для змін** — усі дороги ведуть у нього.

Отже, задача рефакторингу вузька й ясна: **розчепити «що відправляємо» і «як рахувати тариф»**, зробити кожну тарифну формулу самостійним об'єктом, а сам `switch` — прибрати зовсім.

## Ідея

Заміна тримається на одному спостереженні: усі чотири гілки — це **та сама операція**, виконана по-різному. Кожна дістає з відправлення потрібні їй поля й повертає число. Значить, у них є спільна форма — контракт `(відправлення) → вартість`, — а різниться лише **тіло**. Рівно те, що стратегія й винесе назовні: спільну форму в **інтерфейс**, кожне тіло — в **окрему конкретну стратегію**, а вибір «яка саме» — з `switch` у **мапу типу на стратегію**.

Роздивимося наперед три речі, які на цьому шляху завжди спантеличують новачка, — щоб дійти до них уже підготованим.

**Куди дінеться спільний код?** У гілках повторюється візерунок «база плюс надбавка». Спокуса — винести його в базовий клас і успадкувати. Але спадкування знову зв'яже стратегії в жорстку ієрархію, а нам потрібна свобода. Тому спільне краще винести **вбік — у чисту функцію-помічник або в поле-константу**, до якої стратегії звертаються за потреби, а не успадковують. Спільне живе поруч як інструмент, а не над ними як предок. Це та сама [перевага композиції над спадкуванням](topic:sf-apps/composition-inheritance), на якій стоїть уся стратегія.

**Куди дінуться дані, яких різним гілкам треба різне?** Зональній потрібна віддаль, вагова бере вагу, кур'єрська — прапорець терміновості. Не роздавати ж кожній стратегії окремий набір аргументів. Рішення: стратегія приймає **все відправлення цілим** і сама бере з нього те, що їй треба. Контракт лишається єдиним для всіх — `discount(shipment)` бере той самий `shipment`, — а всередині кожна вибирає свої поля. (Це один із двох способів годувати стратегію даними; тут він доречніший, бо полів багато й вони в різних стратегій різні.)

**Хто тепер вирішує, яку стратегію взяти?** Раніше — `switch`. Тепер вибір стане **пошуком у таблиці**: тип служби — це ключ, стратегія — значення. Замість «якщо flat, то…, якщо zonal, то…» буде одне звертання `table[carrier]`. Таблиця будується один раз, а `switch`, що розповзався б із кожною новою службою, зникає назавжди.

Тепер зробімо ці кроки по черзі, щоб було видно, як пахучий метод розпадається на чисті частини.

## Робочий код

### Крок 1. Витягнути інтерфейс стратегії

Перше — назвати спільну форму всіх гілок окремим типом. Це один метод: «порахуй вартість цього відправлення». Нічого більше в контракт не кладемо — що вужчий інтерфейс, то легше писати нові стратегії.

:::tabs
```ts
interface ShippingStrategy {
  cost(s: Shipment): number;   // весь контракт: одна операція
}
```
```py
from abc import ABC, abstractmethod

class ShippingStrategy(ABC):
    @abstractmethod
    def cost(self, s: "Shipment") -> float:   # весь контракт: одна операція
        ...
```
:::

Зверни увагу: стратегія бере **все відправлення** `s`, а не окремі поля. Так контракт лишається один на всіх, хоч кожна стратегія всередині візьме своє. Це те саме передавання контексту аргументом, про яке говорять при будь-якій стратегії, — стратегія не знає, звідки взявся `Shipment`, лише що з нього можна прочитати потрібні поля.

### Крок 2. Винести кожну гілку в конкретну стратегію

Тепер механічна, але уважна частина: кожен `case` переїжджає в окремий клас, що реалізує інтерфейс. Тіло гілки стає тілом методу `cost` — майже дослівно, лише `this.carrier` зникає (клас уже *є* цією службою), а решта полів читається з переданого `s`.

:::tabs
```ts
class FlatRate implements ShippingStrategy {
  cost(s: Shipment): number {
    return 50 + s.weightKg * 10;
  }
}

class ZonalRate implements ShippingStrategy {
  cost(s: Shipment): number {
    const zone = Math.ceil(s.distanceKm / 100);
    return 40 + zone * 25;
  }
}

class FreeOverThreshold implements ShippingStrategy {
  cost(s: Shipment): number {
    if (s.orderTotal >= 1000) return 0;
    return 60 + s.weightKg * 8;
  }
}

class CourierRate implements ShippingStrategy {
  cost(s: Shipment): number {
    const base = 80 + s.distanceKm * 1.5;
    return s.express ? base * 1.6 : base;
  }
}
```
```py
from math import ceil

class FlatRate(ShippingStrategy):
    def cost(self, s):
        return 50 + s.weight_kg * 10

class ZonalRate(ShippingStrategy):
    def cost(self, s):
        zone = ceil(s.distance_km / 100)
        return 40 + zone * 25

class FreeOverThreshold(ShippingStrategy):
    def cost(self, s):
        if s.order_total >= 1000:
            return 0.0
        return 60 + s.weight_kg * 8

class CourierRate(ShippingStrategy):
    def cost(self, s):
        base = 80 + s.distance_km * 1.5
        return base * 1.6 if s.express else base
```
:::

Кожна формула тепер — **самостійна річ із іменем**. `ZonalRate` можна імпортувати в тест, згодувати їй три відправлення з різними віддалями й перевірити межі зон — не піднімаючи ні `switch`, ні решти служб. Те, що вчора було приклеєним шматком, сьогодні живе окремо: його видно, його можна назвати, перевірити й віддати іншому.

### Крок 3. Куди подіти спільний і відмінний код

Тут — найтонше місце рефакторингу, і саме тут його найчастіше роблять криво. Придивись до тіл: у трьох стратегіях повторюється візерунок «фіксована база **плюс** щось за вагу». `FlatRate`: `50 + вага·10`. `FreeOverThreshold`: `60 + вага·8`. Різні числа, та сама форма. Рука тягнеться винести це в базовий клас і успадкувати — і це була б помилка, що поверне нас у ту саму пастку жорсткої ієрархії, від якої ми тікали.

Розберімося чесно, **що тут справді спільне, а що лише схоже**. Форма «база плюс за вагу» — спільна. Але числа (`50` і `10` проти `60` і `8`) — відмінні, і, головне, `FreeOverThreshold` має ще й **свою окрему умову** про поріг суми, якої в `FlatRate` нема. Тобто це не «однакова поведінка», а «схожа арифметика з різними параметрами». Такий випадок винесення в предка не любить: щойно одна зі стратегій захоче трохи інакше, ієрархія тріщить.

Правильний хід — винести спільне **вбік як інструмент, а не вгору як предка**. Просту повторювану арифметику робимо звичайною функцією-помічником (чи приватним методом контексту), яку стратегії **кличуть**, коли вона їм до речі:

:::tabs
```ts
// спільна арифметика живе ВБІК — як інструмент, не як предок
function weightFee(base: number, s: Shipment, perKg: number): number {
  return base + s.weightKg * perKg;
}

class FlatRate implements ShippingStrategy {
  cost(s: Shipment): number {
    return weightFee(50, s, 10);            // кличе спільне
  }
}

class FreeOverThreshold implements ShippingStrategy {
  cost(s: Shipment): number {
    if (s.orderTotal >= 1000) return 0;     // СВОЯ, відмінна умова лишається тут
    return weightFee(60, s, 8);             // а спільну частину — переуживає
  }
}
```
```py
# спільна арифметика живе ВБІК — як інструмент, не як предок
def weight_fee(base: float, s: "Shipment", per_kg: float) -> float:
    return base + s.weight_kg * per_kg

class FlatRate(ShippingStrategy):
    def cost(self, s):
        return weight_fee(50, s, 10)            # кличе спільне

class FreeOverThreshold(ShippingStrategy):
    def cost(self, s):
        if s.order_total >= 1000:              # СВОЯ, відмінна умова лишається тут
            return 0.0
        return weight_fee(60, s, 8)            # а спільну частину — переуживає
```
:::

Різниця між «вбік» і «вгору» тонка на вигляд, але вирішальна по суті. Успадкований предок **нав'язує** структуру: стратегія мусить лягти в форму, яку задав базовий клас, і відступити від неї коштує зламаної ієрархії. Функція-помічник **пропонує** послугу: хочеш — клич, не хочеш — рахуй по-своєму. `ZonalRate` і `CourierRate` формулу «за вагу» просто не кличуть — у них інша арифметика, і вони нікому нічого не винні. Стратегії лишаються рівні й незалежні: жодна не предок жодній, спільне між ними — не ланцюг спадкування, а **бібліотечка збоку**, до якої звертаються добровільно.

![Ліворуч колонкою чотири конкретні стратегії — FlatRate, ZonalRate, FreeOverThreshold, CourierRate — усі на одному рівні, жодна не над іншою; праворуч окремим блоком стоїть функція-помічник weightFee(база, вага, ставка); від FlatRate і FreeOverThreshold тягнуться стрілки-виклики до помічника, а ZonalRate і CourierRate стрілок не мають — вони спільне не кличуть; підпис протиставляє «вбік як інструмент» жирним і закреслене «вгору як предок»](img/common-code-sideways.svg)

*Спільна арифметика винесена вбік як помічник, а не вгору як базовий клас. Стратегії рівні між собою й кличуть помічник лише за потреби: `FlatRate` і `FreeOverThreshold` — так, `ZonalRate` і `CourierRate` — ні, у них своя формула. Помічник послугу пропонує, предок структуру нав'язав би — тому спадкування тут відкинуте.*

> 🔧 **Навіщо це.** Правило «спільне — вбік, не вгору» рятує від найдорожчого різновиду правки. Якщо злити повторювану арифметику в базовий клас, то першого ж дня, коли одна служба захоче рахувати «за вагу» трохи інакше (округлити, додати ПДВ лише їй), доведеться **ламати ієрархію** — розщеплювати предка, тягнути прапорці в базовий метод, множити гачки. Помічник цієї біди не має: кожна стратегія бере від нього рівно скільки хоче, а решту лічить сама. Ти платиш за гнучкість крихітним дублюванням виклику — і воно окупається щоразу, коли вимоги розходяться, а вони розходяться завжди.

### Крок 4. Замінити `switch` на мапу «тип → стратегія»

Стратегії готові — лишилося прибрати сам `switch`, той магніт для змін. Ключове усвідомлення: `switch` за типом — це, по суті, **таблиця пошуку, записана від руки**. «Якщо flat, візьми оце; якщо zonal — оте» — це рядки таблиці, лише розписані гілками. Запишімо таблицю прямо — мапою, де ключ це тип служби, а значення — готовий об'єкт-стратегія:

:::tabs
```ts
// мапа «тип → стратегія» замість switch — будується ОДИН раз
const STRATEGIES: Record<Carrier, ShippingStrategy> = {
  flat:      new FlatRate(),
  zonal:     new ZonalRate(),
  free_over: new FreeOverThreshold(),
  courier:   new CourierRate(),
};

class Shipment {
  constructor(
    public carrier: Carrier,
    public weightKg: number,
    public distanceKm: number,
    public orderTotal: number,
    public express: boolean,
  ) {}

  shippingCost(): number {
    const strategy = STRATEGIES[this.carrier];        // пошук замість switch
    if (!strategy) throw new Error(`Невідома служба: ${this.carrier}`);
    return strategy.cost(this);                        // делегуємо, не знаючи, яка саме
  }
}
```
```py
# мапа «тип → стратегія» замість if-ланцюга — будується ОДИН раз
STRATEGIES: dict[str, ShippingStrategy] = {
    "flat":      FlatRate(),
    "zonal":     ZonalRate(),
    "free_over": FreeOverThreshold(),
    "courier":   CourierRate(),
}

@dataclass
class Shipment:
    carrier: str
    weight_kg: float
    distance_km: float
    order_total: float
    express: bool

    def shipping_cost(self) -> float:
        strategy = STRATEGIES.get(self.carrier)       # пошук замість if-ланцюга
        if strategy is None:
            raise ValueError(f"Невідома служба: {self.carrier}")
        return strategy.cost(self)                     # делегуємо, не знаючи, яка саме
```
:::

Порівняй `shippingCost` тепер із тим, з чого починали. Був `switch` на пів екрана, що знав тарифи всіх служб. Стало три рядки, що **не знають жодного тарифу**: дістати стратегію з таблиці за ключем і віддати їй роботу. Метод перетворився з довідника на **диспетчера** — він більше не рахує, він лише скеровує. Це той самий незмінний процес, про який іде мова в стратегії загалом: контекст делегує, не відаючи деталей, а деталі живуть у підставному об'єкті.

Стратегії тут без стану (та сама `FlatRate` годиться всім відправленням), тож розумно створити їх **раз** і покласти в мапу готовими об'єктами — усі відправлення ділять один незмінний екземпляр, зайвих алокацій нема. Якби стратегія носила стан, у мапі тримали б не готовий об'єкт, а спосіб його зробити (функцію-фабрику), і кликали б її під кожне відправлення.

### Крок 5. Додати нову службу — без правок наявного

Тепер найголовніша перевірка, заради якої все й затівалося. Прийшла вимога: підключити «пошту» — плоска ставка плюс невелика надбавка за кілограм. Дивимося, що для цього треба **чіпнути** з написаного.

:::tabs
```ts
// 1. новий клас — ПОРУЧ, окремим файлом, наявне не відкриваємо
class PostalRate implements ShippingStrategy {
  cost(s: Shipment): number {
    return weightFee(30, s, 12);          // переуживає той самий помічник
  }
}

// 2. один рядок у таблиці
const STRATEGIES: Record<Carrier, ShippingStrategy> = {
  flat:      new FlatRate(),
  zonal:     new ZonalRate(),
  free_over: new FreeOverThreshold(),
  courier:   new CourierRate(),
  postal:    new PostalRate(),           // ← усе, що додали
};
// (+ "postal" у тип Carrier)
```
```py
# 1. новий клас — ПОРУЧ, наявне не відкриваємо
class PostalRate(ShippingStrategy):
    def cost(self, s):
        return weight_fee(30, s, 12)      # переуживає той самий помічник

# 2. один рядок у таблиці
STRATEGIES["postal"] = PostalRate()       # ← усе, що додали
```
:::

Ось у чому виграш, доведений до дотику. Жодна з чотирьох наявних стратегій **не відкрита**. Метод `shippingCost` **не змінений** — він і далі просто шукає в таблиці й делегує, йому байдуже, скільки там рядків. Уся зміна — новий клас збоку плюс один рядок реєстрації. Магніт для змін зник: код тепер **відкритий для доповнення** (пиши нову стратегію) й **закритий для правок** (наявного не чіпаєш) — рівно те, чого вимагає [принцип відкритості-закритості](topic:sf-apps/open-closed), і чого пахучий `switch` дати не міг у принципі.

![Дві колонки-«до-і-після» одного й того самого додавання служби. Ліворуч, підпис «switch»: великий блок методу підсвічено червоним увесь — щоб додати рядок, відкривають і перечитують геть усе тіло, ризик зачепити сусідні гілки. Праворуч, підпис «стратегія + мапа»: наявні чотири стратегії й метод сірі й недоторкані, зеленим підсвічено лише два маленькі нові шматки — новий клас збоку й один рядок у таблиці. Внизу підпис: те саме додавання — хірургія в наявному проти дописування збоку](img/add-variant-diff.svg)

*Одне й те саме — додати нову службу — двома способами. Через `switch` доводиться відкрити й перечитати весь метод (червоне), ризикуючи зачепити сусідні гілки. Через стратегію з мапою наявне лишається недоторканим (сіре), а нове — це відособлений клас і один рядок реєстрації (зелене). Стратегія перетворює «дорогу зміну наявного» на «дешеве дописування збоку».*

Помітили дрібницю з першого зразка? Гілка `default` кидала помилку на невідому службу. Мапа цю перевірку зберігає природно: пошук за відсутнім ключем дає порожнечу (`undefined` / `None`), і та сама перевірка «нема стратегії — кинь помилку» лишається на місці. Ми нічого не втратили в надійності — лише прибрали розгалуження.

## Складність і пастки

Рефакторинг простий на вигляд, та кілька місць уміють підставити. Перелічу ті, на яких спотикаються найчастіше.

**Пастка «спільне вгору».** Найспокусливіша помилка вже названа, але повторю, бо вона найдорожча: побачивши схожу арифметику в кількох стратегіях, винести її в **базовий клас** і успадкувати. Це знову зв'язує стратегії в жорстку ієрархію — рівно те, від чого стратегія й тікає. Спільне виноситься **вбік** (функція-помічник, поле-константа), до якого стратегії звертаються добровільно, а не **вгору** предком, що нав'язує форму. Помічник пропонує послугу; предок диктує структуру.

**Пастка «стан у спільній стратегії».** Коли стратегії кладуть у мапу готовими об'єктами й ділять один екземпляр на всі виклики, він **мусить бути без стану** — інакше два паралельні відправлення затруть дані одне одному. Якщо стратегії потрібен стан на конкретний виклик, тримай у мапі не об'єкт, а фабрику (функцію, що робить свіжий екземпляр), і клич її під кожне відправлення. Плутанина тут дає підступні, важко відтворні збої під навантаженням.

**Пастка «неповна мапа».** `switch` із `default` голосно скаржився на невідому службу. Мапа мовчазна: забув рядок — пошук просто дасть порожнечу. Тому перевірку «нема стратегії — кинь помилку» лишай **обов'язково** (як у кроці 4). У TypeScript є ще й статева підмога: тип `Record<Carrier, ShippingStrategy>` змусить компілятор поскаржитися, якщо в мапі бракує ключа з union-типу `Carrier`, — тоді пропущену службу зловлять ще до запуску. У Python такого захисту нема, тож перевірка в рантаймі — єдина сітка.

**Пастка «стратегія-функція, коли операція одна».** Наш інтерфейс має рівно один метод — а це, по суті, функція. Якщо тобі не потрібні ні ім'я-тип на кожен варіант, ні кілька методів, ні складний стан, цілий клас навколо одного методу можна прибрати й класти в мапу **самі функції**. Це та сама стратегія, лише без церемонії: `const STRATEGIES = { flat: (s) => 50 + s.weightKg*10, … }`. Клас лишають, коли варіантам потрібні **власне ім'я-тип** (легше шукати, документувати, тестувати набором) або **більше однієї операції**. Правило межі коротке: одна операція без тяжкого стану — досить функції; кілька пов'язаних операцій або відчутний власний стан — бери клас. Не тягни клас там, де вистачає функції, — але й не соромся класу, коли операцій справді кілька.

**І головна пастка — зробити цей рефакторинг там, де він зайвий.** Стратегія коштує: чотири класи замість одного методу, мапа, шар непрямості. Ця ціна окупається, коли варіантів **багато**, або їх список **активно росте**, або їх треба **комбінувати й тестувати нарізно** — тобто коли біль від `switch` уже реальний. Але якщо гілок **дві, вони прості й стабільні** й новий варіант не з'являвся роками — чесний `if` на два рядки читається легше за розсипаний по чотирьох класах патерн. Порівняй:

:::tabs
```ts
// дві прості СТАБІЛЬНІ гілки — стратегія тут лише зашкодить
function shippingCost(s: Shipment): number {
  return s.express
    ? 80 + s.distanceKm * 1.5 * 1.6      // терміново
    : 80 + s.distanceKm * 1.5;           // звичайно
}
```
```py
# дві прості СТАБІЛЬНІ гілки — стратегія тут лише зашкодить
def shipping_cost(s: "Shipment") -> float:
    base = 80 + s.distance_km * 1.5
    return base * 1.6 if s.express else base   # терміново / звичайно
```
:::

Тут витягати інтерфейс, плодити два класи й мапу заради вибору `express`/не-`express`, який ніколи не розростеться, — це додати шар абстракції, за яким назавжди сидітимуть ті самі дві гілки. Читач стрибатиме через непрямість, нічого за неї не отримавши. Стратегія — ліки від **множинності, що росте**; де множинності нема й не передбачається, ліки шкодять. Спокуса обернути стратегією кожну умовну гілку — відома [хвороба надмірного патернування](topic:sf-apps/anti-patterns): патерн має гасити наявний біль, а не уявний.

Практичне правило, яким варто мірятися перед заміною, коротке. Заміняй `switch` на стратегію, коли справджується хоч одне: гілок уже **багато** (від чотирьох-п'яти) й видно, що прибуватиме; варіанти треба **тестувати чи повторно вживати поодинці**; список варіантів міняє **інша команда чи інший модуль**, і кожна правка в спільному `switch` — це конфлікт і ризик. Якщо ж перед тобою дві-три стабільні гілки, які роками не ворушаться, — лиши `switch` і повертайся до цього рефакторингу тоді, коли (і якщо) множинність справді почне рости.
