# Стратегія

<preknowlist>
- [Інтерфейс проти реалізації](topic:sf-apps/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні, і тим, ЯК він це робить; уся стратегія тримається на тому, що клієнт бачить лише спільний інтерфейс, а тіло алгоритму сховане.
- [Поліморфізм і динамічне зв'язування](topic:sf-lang/polymorphism) — виклик через абстрактний тип, що в рантаймі потрапляє в потрібну реалізацію; це той механізм, яким стратегія в останню мить обирає, який алгоритм виконати.
- [Композиція над спадкуванням](topic:sf-apps/composition-inheritance) — чому поведінку краще тримати всередині окремим об'єктом-полем, ніж зашивати в ієрархію підкласів; стратегія — канонічний приклад цієї заміни.
- [Принцип відкритості-закритості](topic:sf-apps/open-closed) — код має бути відкритий для доповнення й закритий для правок; стратегія дозволяє додати новий алгоритм, не чіпаючи наявний.
</preknowlist>

Уяви функцію, яка сортує список замовлень. Спершу її просять сортувати за датою. Ти пишеш порівняння за датою просто всередині. За тиждень треба ще й за сумою — ти додаєш `if`. Потім за іменем клієнта, потім за пріоритетом, потім «за датою, але спершу термінові». І от твоя функція сортування, яка мала робити одну зрозумілу річ, перетворилася на клубок гілок, де половина коду — не про сортування взагалі, а про те, **яким саме способом** цього разу порівнювати. Кожен новий спосіб — ще одна правка в тому самому місці, ще один ризик зачепити те, що вже працювало.

Придивімося, де тут корінь болю. У задачі сплелися дві зовсім різні речі: **сам процес** (пройтися списком, поміняти елементи місцями, щоб вийшов лад) і **правило порівняння** (що вважати «меншим»). Процес незмінний — він однаковий для будь-якого порядку. А правило — це якраз те, що постійно нове. Коли обидві речі живуть в одному тілі функції, кожна зміна змінного правила змушує чіпати незмінний процес. Ми правимо стабільне заради нестабільного — і саме тому воно ламається.

**Стратегія (англ. *Strategy* — спосіб дії для досягнення мети)** — це патерн, придуманий рівно для того, щоб ці дві речі роз'єднати: **винести змінний алгоритм в окремий об'єкт за спільним інтерфейсом, а процес лишити незмінним і тримати цей об'єкт при собі, підставляючи потрібний**. Функція сортування більше не знає жодного правила порівняння — вона отримує його ззовні як окрему деталь і просто ним користується. Розберімося, як це працює й чому воно куди глибше, ніж «винести код у метод».

## Що саме змінюється: варіант поведінки як окрема річ

Ключ до всього патерна — навчитися бачити в коді **точку варіативності**: місце, де програма робить щось одне, але це «щось» має кілька взаємозамінних версій, і яку саме взяти — вирішується не тут. Порядок сортування. Спосіб стиснути дані. Формула знижки. Політика повторних спроб. Маршрут обчислення податку залежно від країни. У кожному випадку є **стабільний контекст**, якому потрібна певна дія, і **сімейство взаємозамінних алгоритмів**, кожен з яких цю дію виконує по-своєму.

Наївне рішення — тримати всі варіанти в одному місці й вибирати гілкою:

:::tabs
```ts
class Order {
  discountFor(customer: Customer): number {
    // усі знижкові правила зашиті в один метод
    if (customer.tier === "vip")        return this.total * 0.20;
    if (customer.tier === "loyal")      return this.total * 0.10;
    if (customer.isFirstPurchase)       return this.total * 0.05;
    if (this.isBlackFriday())           return this.total * 0.30;
    return 0;
  }
}
```
```py
class Order:
    def discount_for(self, customer: Customer) -> float:
        # усі знижкові правила зашиті в один метод
        if customer.tier == "vip":       return self.total * 0.20
        if customer.tier == "loyal":     return self.total * 0.10
        if customer.is_first_purchase:   return self.total * 0.05
        if self.is_black_friday():       return self.total * 0.30
        return 0.0
```
:::

Поки правил три — читабельно. Але кожне нове правило означає редагувати `Order` — клас, який мав би займатися замовленням, а не знати весь каталог маркетингових акцій. Що гірше, самі правила тепер намертво прив'язані одне до одного й до замовлення: не можна взяти «знижку VIP» окремо, протестувати її ізольовано, повторно використати в іншому місці чи скомбінувати по-новому. Вони не існують як самостійні речі — вони лише гілки в чужому методі. Це прямо суперечить [принципу відкритості-закритості](topic:sf-apps/open-closed): додавання можливості мусило б бути новим кодом збоку, а не хірургією в наявному.

> 🔧 **Навіщо це.** Найгостріше цей клубок ріже там, де правил стає багато й вони живуть власним життям. Тарифи доставки за регіонами, стратегії ранжування у стрічці, формати експорту, платіжні провайдери — усе це сімейства алгоритмів, які додають, прибирають і міняють незалежно від коду, що їх кличе. Коли кожен варіант — окремий об'єкт, нову стратегію пише інша людина в іншому файлі, не торкаючись і не ризикуючи зламати те, що вже в проді. Ізольованість варіантів — не академічна охайність, а можливість безпечно рости.

Отже, мета ясна: кожен варіант поведінки має стати **самостійним об'єктом**, який можна створити, передати, підмінити й перевірити окремо. А контекст має тримати не десяток гілок, а одне поле — «поточний алгоритм» — і звертатися до нього через спільний інтерфейс, не знаючи, який саме варіант там зараз.

## Кістяк патерна: інтерфейс, реалізації, контекст

Стратегія складається рівно з трьох частин, і кожна має чітку роль. Перша — **інтерфейс стратегії**: вузький контракт, що оголошує одну операцію («порівняй двох», «порахуй знижку», «стисни байти»). Друга — **конкретні стратегії**: класи, кожен з яких реалізує цей інтерфейс своїм способом. Третя — **контекст**: об'єкт, якому потрібна операція; він тримає посилання на стратегію полем і делегує їй роботу, сам не знаючи деталей.

Перепишімо знижки через стратегію. Спершу — контракт і кілька реалізацій:

:::tabs
```ts
interface DiscountPolicy {                       // інтерфейс стратегії: одна операція
  discount(order: Order): number;
}

class NoDiscount implements DiscountPolicy {
  discount(order: Order): number { return 0; }
}
class VipDiscount implements DiscountPolicy {
  discount(order: Order): number { return order.total * 0.20; }
}
class SeasonalDiscount implements DiscountPolicy {
  constructor(private rate: number) {}           // стратегія може мати власний стан
  discount(order: Order): number { return order.total * this.rate; }
}
```
```py
from abc import ABC, abstractmethod

class DiscountPolicy(ABC):                        # інтерфейс стратегії: одна операція
    @abstractmethod
    def discount(self, order: "Order") -> float: ...

class NoDiscount(DiscountPolicy):
    def discount(self, order): return 0.0

class VipDiscount(DiscountPolicy):
    def discount(self, order): return order.total * 0.20

class SeasonalDiscount(DiscountPolicy):
    def __init__(self, rate: float):              # стратегія може мати власний стан
        self.rate = rate
    def discount(self, order): return order.total * self.rate
```
:::

Тепер контекст. Замовлення більше не тримає жодного знижкового правила — воно тримає **одну стратегію** й делегує їй:

:::tabs
```ts
class Order {
  constructor(
    public total: number,
    private policy: DiscountPolicy,              // контекст тримає СТРАТЕГІЮ полем
  ) {}

  finalPrice(): number {
    return this.total - this.policy.discount(this); // делегує, не знаючи, яка саме
  }

  setPolicy(policy: DiscountPolicy): void {      // стратегію можна підмінити на льоту
    this.policy = policy;
  }
}

// збірка: хто саме — вирішується ЗЗОВНІ, в одному місці
const order = new Order(1000, new VipDiscount());
order.finalPrice();                              // 800
order.setPolicy(new SeasonalDiscount(0.30));
order.finalPrice();                              // 700
```
```py
class Order:
    def __init__(self, total: float, policy: DiscountPolicy):
        self.total = total
        self._policy = policy                     # контекст тримає СТРАТЕГІЮ полем

    def final_price(self) -> float:
        return self.total - self._policy.discount(self)  # делегує, не знаючи, яка саме

    def set_policy(self, policy: DiscountPolicy) -> None:  # підмінити на льоту
        self._policy = policy

# збірка: хто саме — вирішується ЗЗОВНІ, в одному місці
order = Order(1000, VipDiscount())
order.final_price()               # 800
order.set_policy(SeasonalDiscount(0.30))
order.final_price()               # 700
```
:::

Придивись до `finalPrice()`. Це весь незмінний процес: узяти повну суму, відняти знижку. Він викликає `policy.discount(this)`, **не маючи жодного уявлення**, яке правило спрацює — у рантаймі виклик потрапить у той клас, який зараз лежить у полі `policy`. Це звичайне [динамічне зв'язування](topic:sf-lang/polymorphism), і саме воно робить контекст сліпим до варіантів. Додати нову знижку — це створити новий клас поруч і ніде не чіпнути `Order`. Стабільне лишилося стабільним; росте лише те, що й мало рости.

![Контекст Order тримає одне поле policy типу інтерфейсу DiscountPolicy і викликає через нього discount, не знаючи реалізації; від інтерфейсу вниз відходять три взаємозамінні конкретні стратегії — NoDiscount, VipDiscount, SeasonalDiscount, кожна зі своїм тілом методу; підпис показує, що підстановка іншої стратегії міняє поведінку без правок у контексті](img/strategy-structure.svg)

*Контекст залежить лише від інтерфейсу стратегії й делегує йому роботу. Конкретні алгоритми — взаємозамінні реалізації за одним контрактом; підставити іншу означає змінити поведінку контексту, не торкаючись його коду.*

Зверни увагу на дрібницю, яка насправді важлива: стратегія може приймати дані двома шляхами. Або контекст **передає все потрібне аргументом** (як тут — `order` іде в `discount`), або стратегія **отримує посилання на контекст** і сама витягує з нього те, що треба. Перший шлях робить стратегію чистішою й незалежнішою (вона не знає про контекст нічого, лише про свої аргументи), тому за замовчуванням обирають його. Другий беруть, коли алгоритму потрібно надто багато різних полів контексту, щоб зручно передавати їх поодинці.

## Чому це композиція, а не спадкування

Тут ховається найглибша ідея патерна, і без неї стратегію легко сплутати з простим «винести код». Був би інший, «спадковий» спосіб дати замовленню різні знижки: зробити `VipOrder`, `LoyalOrder`, `SeasonalOrder` — підкласи `Order`, кожен зі своїм `finalPrice()`. На перший погляд теж працює. Але цей шлях заводить у глухий кут, і корисно побачити, чому саме.

Спадкування прив'язує варіант поведінки до **типу об'єкта назавжди, ще на етапі створення**. `VipOrder` є VIP-замовленням від народження й до смерті — щоб замовлення перестало бути VIP і стало сезонним, його довелося б **пересотворити** іншим класом. А стратегія — це поле; його міняють викликом `setPolicy` будь-коли, той самий об'єкт живе далі й лише поводиться інакше. Поведінка стала **даними, які можна замінити**, а не властивістю типу, вилитою в бетон.

Глибша біда спадкування вилазить, щойно осей варіативності стає більше однієї. Уяви, що знижка — не єдине, що варіюється: ще й спосіб доставки має кілька варіантів, і формат рахунка. Через підкласи довелося б робити клас на **кожну комбінацію**: `VipExpressPdfOrder`, `LoyalStandardHtmlOrder`… — добуток усіх варіантів, комбінаторний вибух. Через стратегії — три незалежні поля, кожне зі своїм маленьким сімейством, і будь-яка комбінація складається з них вільно. Саме тому банда чотирьох винесла в окремий принцип гасло [«надавай перевагу композиції об'єктів перед спадкуванням класів»](topic:sf-apps/composition-inheritance): стратегія — його найчистіше втілення. Замість «бути підкласом із зашитою поведінкою» об'єкт «має всередині змінний об'єкт поведінки».

> 🔧 **Навіщо це.** Ця відмінність — не філософія, вона рятує від переписувань. Коли поведінка вкладена спадкуванням, зміна вимог часто означає перебудову ієрархії типів — найдорожчий різновид правки. Коли поведінка — підставний об'єкт, зміна вимог означає написати ще один маленький клас і підставити його. Тому в системах, де правила бізнесу міняються часто (а вони міняються завжди), стратегія перетворює «дорогу зміну структури» на «дешеве додавання варіанта».

## Стратегія-функція: коли клас — це занадто

Класична GoF-стратегія — це інтерфейс і класи, бо книжку писали для мов, де інакше поведінку передати не було як. Але якщо приглянутися, інтерфейс `DiscountPolicy` має рівно **один метод**. А одна операція — це, по суті, функція. У мовах, де [функції можна передавати як звичайні значення](topic:sf-lang/first-class-functions), цілий клас-обгортку навколо єдиного методу часто можна прибрати й передавати саму функцію.

:::tabs
```ts
// стратегія — це просто тип функції
type DiscountPolicy = (order: Order) => number;

const vip: DiscountPolicy        = (o) => o.total * 0.20;
const seasonal = (rate: number): DiscountPolicy => (o) => o.total * rate;

class Order {
  constructor(public total: number, private policy: DiscountPolicy) {}
  finalPrice(): number { return this.total - this.policy(this); }
}

const order = new Order(1000, vip);              // передаємо функцію, не об'єкт
order.finalPrice();                              // 800
new Order(1000, seasonal(0.30)).finalPrice();    // 700
```
```py
from typing import Callable

# стратегія — це просто тип функції: Order -> float
DiscountPolicy = Callable[["Order"], float]

def vip(o: "Order") -> float: return o.total * 0.20
def seasonal(rate: float) -> DiscountPolicy:
    return lambda o: o.total * rate

class Order:
    def __init__(self, total: float, policy: DiscountPolicy):
        self.total = total
        self._policy = policy
    def final_price(self) -> float:
        return self.total - self._policy(self)   # кличемо функцію напряму

order = Order(1000, vip)              # передаємо функцію, не об'єкт
order.final_price()                   # 800
Order(1000, seasonal(0.30)).final_price()   # 700
```
:::

Це та сама стратегія — контекст усе так само тримає змінний алгоритм полем і делегує йому, — тільки без церемонії з інтерфейсом і класами. `seasonal(0.30)` показує, що функція-стратегія теж носить стан: замикання пам'ятає `rate`, як поле пам'ятало б його в об'єкті. Ось чому досвідчений погляд бачить у багатьох «функціях вищого порядку» саме стратегію, названу іншими словами: `array.sort(порівнювач)`, `retry(операція, політика)`, обробник події — усе це контекст, що приймає підставний алгоритм.

Коли ж лишати повноцінний клас? Коли стратегії **більше однієї операції** (інтерфейс із двома-трьома методами функцією вже не заміниш), коли їй потрібен **складний власний стан або життєвий цикл**, або коли важливо, щоб варіанти мали **імена й місце** — окремі типи легше знаходити, документувати й тестувати цілим набором. Правило просте: одна операція без тяжкого стану — функція; кілька пов'язаних операцій або відчутний стан — клас. Мовою на кшталт C, де функцію теж передають (вказівником) — але без замикань, — стан доводиться тягати окремим аргументом-контекстом; це той самий патерн, лише зібраний вручну.

## Родичі, яких плутають зі стратегією

Стратегію легко сплутати з кількома патернами, що структурно на неї схожі. Розрізняє їх не форма, а **намір** — навіщо їх узагалі беруть.

Найближчий двійник — **[Стан (State)](topic:sf-apps/state)**. Структурно вони майже однакові: контекст тримає підставний об'єкт і делегує йому. Але мета інша. Стратегію обирає **хтось іззовні** (клієнт вирішив сортувати за датою), і вибрана стратегія зазвичай не змінюється сама собою. Стан же **перемикає сам себе зсередини** залежно від подій: об'єкт-стан «відкрито», обробивши подію, сам ставить контексту наступний стан «оплачено». Стратегія — це «яким способом робити одне й те саме»; стан — це «в якій я зараз фазі, і що це міняє в поведінці».

Схожий і **[Команда (Command)](topic:sf-apps/command)**: теж загорнута в об'єкт дія. Але команда пакує **конкретний виклик із зафіксованими аргументами**, щоб його зберегти, поставити в чергу, скасувати чи повторити пізніше, — акцент на «дію як запис, що переживе момент виклику». Стратегія ж — це **взаємозамінний спосіб** зробити роботу тут і зараз; її не складають у чергу й не скасовують. Обидва обгортають поведінку об'єктом, але команда — про **відкладене виконання однієї дії**, стратегія — про **вибір з-поміж рівноправних алгоритмів**.

Різниця намірів при однаковій структурі — типова риса поведінкових патернів; що це взагалі означає — «однакова форма, різна мета» — і чому патерни класифікують саме за наміром, розібрано в статті [про поняття патерна](topic:sf-apps/what-is-pattern).

## Коли стратегія зайва

Патерн, який так легко застосувати, легко й **пере**застосувати, тож чесно назвемо, коли його брати не варто. Головна ознака доречності — **справжня множинність варіантів, що живе довше за одну мить**. Якщо алгоритм рівно один і другого на видноколі немає, інтерфейс і клас-стратегія лише додають порожній шар непрямості: клієнт стрибає через абстракцію, за якою завжди та сама реалізація. Пиши логіку прямо; винесеш у стратегію тоді, коли (і якщо) з'явиться другий варіант.

Так само не варто плодити стратегію там, де гілок дві й вони прості та стабільні. Звичайний `if` із двох рядків, який ніколи не росте, читається легше за розсипаний по трьох класах патерн. Стратегія окупається, коли варіантів багато **або** їх список активно змінюється **або** їх треба комбінувати й тестувати нарізно — тобто коли ціна гілок у одному місці вже переважує ціну зайвих класів. Спокуса обернути стратегією кожну умовну гілку — відома [хвороба надмірного патернування](topic:sf-apps/anti-patterns); патерн має розв'язувати наявний біль, а не передбачати уявний.

Практичний хід, з якого стратегія майже завжди й народжується в реальному коді, — це не «спроєктувати наперед», а **помітити біль і зробити заміну**: узяти метод, що розрісся розгалуженим `switch` за типом, і винести кожну гілку в окрему стратегію. Це один із найчастіших рефакторингів у практиці; його покроковий розбір — від «пахучого» умовного до чистих стратегій, з увагою до того, як переносити спільний і відмінний код, — винесено в [окремий приклад](topic:sf-apps/strategy/proj-replace-conditional-with-strategy.md).

## Звідки вона взялася

Стратегія — один із двадцяти трьох патернів каталогу «банди чотирьох» (Еріх Гамма, Річард Гелм, Ральф Джонсон, Джон Вліссідс), книжки «Design Patterns: Elements of Reusable Object-Oriented Software», представленої на конференції OOPSLA в жовтні 1994 року (усталений факт). Автори віднесли її до **поведінкових** патернів — тих, що впорядковують не створення чи склад об'єктів, а **розподіл обов'язків і спосіб їхньої взаємодії**.

Сама ідея відокремлювати змінне правило від сталого процесу старша за книжку й не належить одній людині: у мовах із функціями як значеннями (Lisp, ML) «передай функцію-порівнювач» було природним задовго до GoF, а в C++-спільноті близький підхід згодом викристалізувався в «дизайн на політиках» (англ. *policy-based design*), де взаємозамінну поведінку підставляють ще на етапі компіляції через шаблони. Як ця думка визрівала — від функцій вищого порядку до GoF-класів і далі до параметрів-функцій та політик, і чому «стратегія» і «політика» так часто виявляються тим самим — розгорнуто в [нотатці про народження патерна](topic:sf-apps/strategy/hist-strategy-policy.md).
