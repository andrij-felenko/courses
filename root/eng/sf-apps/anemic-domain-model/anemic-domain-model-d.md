# Анемічна модель предметної області

<preknowlist>
- [Інкапсуляція](topic:sf-apps/encapsulation) — дані й правила над ними живуть за однією стіною; анемія — це коли стіни фактично немає.
- [Інваріант програми](topic:sf-apps/invariants) — твердження, яке об'єкт обіцяє тримати істинним завжди; анемічний об'єкт не тримає жодного.
- [«Кажи, не питай» (Tell, Don't Ask)](topic:sf-apps/tell-dont-ask) — не витягуй стан, щоб вирішити за об'єкт; анемія — масове порушення саме цього.
- [DDD-лайт](topic:sf-apps/domain-driven-design) — ідея багатої моделі, де поведінка живе разом із даними; анемія — її пряма протилежність.
- [Сервісний шар](topic:sf-apps/service-layer) — тонкий шар оркестрації над доменом; при анемії саме туди стікає вся логіка, якій там не місце.
</preknowlist>

Візьми будь-який застосунок і подивися на клас, названий іменем предмета — `Order`, `Account`, `Invoice`. Дуже часто побачиш ось таке: десяток публічних полів, конструктор, а більше нічого. Ні методів, ні правил — сам мішок даних. А поруч живе `OrderService`, `OrderManager` чи `OrderProcessor` на кілька сотень рядків, у якому й сидить уся думка: коли можна знижку, коли замовлення оформлюється, що взагалі означає «замовлення готове». Об'єкт названий річчю, але поводиться як структура з мови без класів — просто набір комірок, які хтось інший наповнює й читає.

Саме таку модель звуть **анемічною (гр. *an-* — «без», *haima* — «кров»; недокрівна, знекровлена)**. Метафора точна до кістки: у медицині анемія — це коли крові наче й достатньо на вигляд, але в ній бракує того, що переносить кисень, тож тіло є, а сили в ньому немає. Так само тут: об'єкт на вигляд повноцінний — правильна назва, слушні типи полів, зв'язки з іншими об'єктами, — але **поведінки в ньому нема, лише кістяк даних**. Кров, що мала б його оживляти — правила, рішення, гарантії, — витекла кудись у сервіси.

## Як це виглядає

Ось замовлення в такому знекровленому стилі. Придивися не до синтаксису, а до того, **де живе думка**.

:::tabs
```ts
// Знекровлена модель: замовлення нічого не вміє, лише тримає поля навстіж
class Order {
  status: string = "new";       // "new" | "paid" | "shipped" | "cancelled"
  items: Item[] = [];
  discount: number = 0;         // відсоток знижки, 0..100 — хтозна, ніхто не стереже
  total: number = 0;
}

// Уся думка — ЗЗОВНІ, у сервісі; кожен викликач тримає свій уламок правил
class OrderService {
  applyDiscount(o: Order, percent: number): void {
    o.discount = percent;        // жодної перевірки: приймуться й 500, і −20
    o.total = o.items.reduce((s, i) => s + i.price, 0) * (1 - o.discount / 100);
  }

  ship(o: Order): void {
    // тут ЗАБУЛИ перевірити, що замовлення взагалі оплачене
    o.status = "shipped";
  }
}
```
```python
# Знекровлена модель: замовлення нічого не вміє, лише тримає поля навстіж
class Order:
    def __init__(self):
        self.status = "new"       # "new" | "paid" | "shipped" | "cancelled"
        self.items = []
        self.discount = 0         # відсоток знижки, 0..100 — ніхто не стереже
        self.total = 0

# Уся думка — ЗЗОВНІ, у сервісі; кожен викликач тримає свій уламок правил
class OrderService:
    def apply_discount(self, o, percent):
        o.discount = percent      # жодної перевірки: приймуться й 500, і −20
        o.total = sum(i.price for i in o.items) * (1 - o.discount / 100)

    def ship(self, o):
        # тут ЗАБУЛИ перевірити, що замовлення взагалі оплачене
        o.status = "shipped"
```
:::

Хвороба вилазить сама. Правило «відвантажити можна лише оплачене замовлення» — це правило самого замовлення, частина його природи. Але тут його **немає**: `ship` бере будь-яке замовлення й ставить `"shipped"`, бо автор цього методу не тримав у голові весь життєвий цикл. Правило «знижка від 0 до 100 відсотків» теж загубилося. Кожен викликач тримає власний уламок спільного закону, і разом ці уламки не складаються в цілісність — а часто й суперечать одне одному.

Наслідок не теоретичний. Ось що цей код цілком дозволяє:

:::tabs
```ts
const o = new Order();
o.status = "shipped";      // будь-хто вписує будь-що напряму, минаючи всякий цикл
o.discount = 500;          // знижка 500% — тепер total від'ємний
new OrderService().ship(o);   // відвантажили неоплачене
// замовлення в стані, якого не існує в природі
```
```python
o = Order()
o.status = "shipped"       # будь-хто вписує будь-що напряму, минаючи всякий цикл
o.discount = 500           # знижка 500% — тепер total від'ємний
OrderService().ship(o)     # відвантажили неоплачене
# замовлення в стані, якого не існує в природі
```
:::

Об'єкт не володіє власним станом. Стіни немає взагалі: поля публічні, зайти в них можна будь-звідки, зокрема неможливим значенням. Замовлення не гарантує про себе **нічого** — гарантії, якщо вони десь і є, розкидані по викликачах.

![Ліворуч знекровлена модель: голий об'єкт Order лише з полями, а правила орбітують зовні в трьох сервісах, звідки червоні стрілки лізуть у поля читати й вписувати назад. Праворуч багата модель: один об'єкт Order, де дані й поведінка (applyDiscount, checkout, cancel) за однією зеленою стіною, а викликач лише надсилає один наказ checkout()](img/anemic-vs-rich.svg)

*Ліворуч правило живе поза даними, і будь-хто крізь відкриті поля може привести об'єкт у неможливий стан. Праворуч правило замкнене всередині разом зі станом, а зовні видно лише наказ — і привести об'єкт у неможливий стан ззовні нема як.*

## Чому Фаулер назвав це анти-патерном

Термін ужив і розкритикував [Мартін Фаулер (Martin Fowler) 25 листопада 2003 року](topic:sf-apps/anemic-domain-model/hist-fowler-anemic.md), помітивши разом з Еріком Евансом (Eric Evans), що такі моделі дедалі поширеніші. Його діагноз — в одному реченні: об'єкти, у яких «навряд чи є хоч якась поведінка, тож вони — трохи більше ніж мішки геттерів і сеттерів» (англ. *bags of getters and setters*). *(Статус: усталено — за первинним джерелом, нотаткою Фаулера, і датою її публікації.)*

Чому це анти-патерн, а не просто інший смак? Бо він, за словами Фаулера, «настільки суперечить базовій ідеї об'єктного дизайну — поєднати дані й поведінку разом, — що по суті це процедурний дизайн, убраний у костюм об'єктів». Ось де корінь. Об'єктне програмування зродилося саме з того, щоб зшити дані з правилами над ними в одне ціле, яке **само вміє діяти**. Анемічна модель це розшиває назад: дані — окремо, в об'єктах-мішках; правила — окремо, у сервісах, що ті мішки порпають. Ти отримуєш усі накладні витрати ООП (класи, об'єкти, мапінг на базу) і жодної його вигоди, бо думаєш ти все одно процедурно — просто розкладеною по класах процедурою.

Наслідок цієї розшивки має власне ім'я — **сценарій-транзакція (англ. *Transaction Script*)**: кожна операція системи стає окремою процедурою, що бере пласкі дані, робить із ними всю роботу від початку до кінця й кладе назад. Це не завжди погано (нижче побачиш, коли якраз добре), але коли предмет насправді багатий на правила, сценарій-транзакція втрачає все, заради чого будують доменну модель: правило розтікається по десятках процедур, і одну його копію рано чи пізно проґавлять.

> 🔧 **Навіщо це.** Питання «де живе рішення» вирішує, скільки місць зачепить майбутня зміна. Уяви найзвичайнішу нову вимогу: доти, доки замовлення не оплачене, знижку міняти не можна. Якщо правило про стан розсіяне по десятку сервісів (кожен сам робить `if o.status == ...`), доведеться знайти й виправити всі десять — і один пропустиш, а він мовчки лишиться зі старою логікою. Якщо ж воно живе в одному методі самого замовлення, зміна лягає в одне місце, а решта коду навіть не помічає, що правило стало іншим. Анемія небезпечна саме тим, що дає правилу розтектися по коду калюжею, яку потім не збереш.

Найковарніше в тому, що анемічний код **працює** і проходить тести на щасливому шляху. Поламається він тоді, коли новий викликач забуде перевірку, або коли правило зміниться й одну з розкиданих копій проґавлять. Найдорожчі баги — не там, де код робить не те, що написано, а там, де він робить рівно те, що написано, але правило було розсипане й одну його копію не оновили.

## Протиотрута — багата модель

Ліки прямо випливають із діагнозу: коли метод у сервісі тільки те й робить, що порпає поля чужого об'єкта, — **пересели його до тих полів**. Правило про власний стан замовлення має стати методом самого замовлення. Тоді викликачеві нема чого питати: він каже одне слово, а вся дрібна робота з полями й перевірками відбувається там, де ці поля рідні.

:::tabs
```ts
class Order {
  private _status = "new";
  private _discount = 0;
  private _items: Item[] = [];

  // правило знижки тепер ТУТ, разом зі своїм вартовим
  applyDiscount(percent: number): void {
    if (this._status !== "new")
      throw new DomainError("знижку міняють лише до оплати");
    if (percent < 0 || percent > 100)
      throw new DomainError("знижка поза межами 0..100");
    this._discount = percent;
  }

  ship(): void {
    if (this._status !== "paid")           // перевірка, якої бракувало
      throw new DomainError("відвантажують лише оплачене");
    this._status = "shipped";
  }
}
```
```python
class Order:
    def __init__(self):
        self._status = "new"
        self._discount = 0
        self._items = []

    # правило знижки тепер ТУТ, разом зі своїм вартовим
    def apply_discount(self, percent):
        if self._status != "new":
            raise DomainError("знижку міняють лише до оплати")
        if percent < 0 or percent > 100:
            raise DomainError("знижка поза межами 0..100")
        self._discount = percent

    def ship(self):
        if self._status != "paid":           # перевірка, якої бракувало
            raise DomainError("відвантажують лише оплачене")
        self._status = "shipped"
```
:::

Різниця не косметична. Поля закриті, тож `o._status = "shipped"` уже не пройде повз цикл. Правило зібралося з розкиданих уламків в одне місце, назване мовою предмета, і забути його не можна — воно на шляху. Сервіс після цього худне до чесної оркестрації: дістати замовлення зі сховища, сказати йому `ship()`, зберегти. Це і є **багата модель** — та, де поведінка живе разом із даними; ідею прямо пов'язують з [DDD Еванса](topic:sf-apps/domain-driven-design), тоді як «анемічна» — термін-антонім Фаулера.

Повне перетворення знекровленого мішка на багату модель — не одна вставка методів, а низка дрібних безпечних кроків: закрити поля, внести інваріант із сервісу в об'єкт, зробити єдині двері через команду, виділити гроші в [об'єкт-значення](topic:sf-apps/entity-value-object), накрити пов'язані частини коренем агрегату. Кожен крок лишає код робочим, а наприкінці некоректний стан стає не «таким, що ми його ловимо», а таким, що **його нема звідки взяти**. Цей шлях розібрано крок за кроком на живому прикладі поліса — [від знекровленого мішка до багатої моделі](topic:sf-apps/domain-driven-design/proj-anemic-to-rich.md), з розбором, як таку модель тестувати без бази й моків і на яких пастках ламаються найчастіше.

## Коли анемія — не хвороба, а вибір

Тепер найважливіше й найчастіше пропущене, бо сліпе винищування всіх пласких об'єктів робить не краще, а гірше. Сам статус «анти-патерн» досі **предметно оспорюють** — і не дарма: у пласкої моделі є реальні переваги, коли предмет для них годиться. Це не пом'якшення заради ввічливості, а суть питання: анемія погана **лише там, де є що знекровлювати**.

Ключ — у **кількості й вазі правил над даними**. Багата модель окуповується там, де є стани, переходи між ними, інваріанти, які треба тримати завжди. Але величезний пласт коду такого предмета просто не має. Форма редагування профілю, довідник валют, адміністративна панель, звіт, що збирає числа звідусіль, шар, який перекладає дані з бази у відповідь HTTP, — тут правил майже нема, є саме перекладання. Насаджувати сюди «багату модель» — це вигадувати інваріанти, яких у предмета немає, і роздувати простий код церемонією.

![Питання-різак угорі: скільки правил над цими даними. Ліва синя гілка майже нема веде до плаского об'єкта як доречного вибору для CRUD-форм, довідників, звітів, перекладання даних. Права червона гілка багато й ростуть веде до знекровлення як анти-патерну, де стани й інваріанти розсипані по сервісах](img/when-anemic-ok.svg)

*Один різак вирішує все. Мало правил над даними — плаский об'єкт із сервісом-процедурою простий і чесний, це не анемія, а доречна форма. Багато правил, що ще й ростуть, — знекровлення стає анти-патерном, бо правилу нема де жити, крім розсипу по сервісах.*

Що конкретно дає пласка модель там, де вона доречна — і що саме перелічують ті, хто заперечує проти ярлика «анти-патерн»:

- **Чистий поділ логіки й даних.** Дані — окремий простий тип; операції — окремі процедури. Для невеликого застосунку `Service.createUser()`, що робить усе — перевірку, збереження, сповіщення, — цілком зрозумілий і легкий.
- **Логіка без стану добре масштабується.** Сервіс-процедура не тримає стану між викликами, тож його легко розкладати на багато машин.
- **Уникнення важкого мапінгу об'єкт-база.** Пласкі об'єкти зі звичайними полями лягають на бібліотеки мапінгу й впровадження залежностей, що саме таких — з простими властивостями — і чекають.

Тут і проходить чесна лінія: **пласка модель — це не діагноз, а інструмент**, доречний рівно там, де правил обмаль. Знекровленою (в поганому сенсі) вона стає тоді, коли предмет **насправді багатий на правила**, а їх усе одно винесли назовні — і тепер стани воскрешаються, знижки виходять за межі, а закон розмазаний по сервісах. Проба-різак одна: **чи є над цими даними інваріанти, які треба тримати завжди?** Немає — пласко й добре, не вигадуй складності. Є, ще й ростуть, — правило шукає дім, і цей дім — сам об'єкт.

> 🔧 **Навіщо це.** Пам'ятай, чого служить правило, а не носи його як прапор. Мета — не «щоб у кожного об'єкта були методи», а щоб **бізнес-правила жили в одному місці й не текли по коду**. Там, де правил майже немає, ця мета вже досягнута сама собою, і насаджений «багатий» об'єкт лише додасть церемонії без вигоди. Там, де правил багато, анемія цю мету зраджує, бо правилу нема де зібратися. Дивись на предмет, а не на ярлик: одному застосунку пласка форма з тонким сервісом — рівно те, що треба; іншому — прихована пастка, яка вистрелить на першій зміні вимог.

## Коротко про головне

Анемічна модель — це коли об'єкт, названий іменем предмета, насправді лише тримає дані, а вся поведінка й правила витекли в сервіси, що ці дані порпають. Об'єкт стає мішком геттерів і сеттерів; будь-хто ззовні може привести його в неможливий стан, бо правил у ньому немає, вони розсипані по викликачах. Фаулер називає це анти-патерном, бо це процедурний дизайн у костюмі ООП: усі витрати на об'єкти й жодної вигоди від них.

Протиотрута — багата модель: пересели правило туди, де живуть його дані, замкни стан за приватністю й пускай зміни лише через методи-команди з вартовими всередині. Тоді правило зібране в одному місці, зміна лягає в один метод, а некоректний стан стає недосяжним.

Але тримай і другий бік у голові, бо він така сама частина правила: **анемія погана лише там, де є що знекровлювати**. Плаский об'єкт із тонким сервісом — цілком доречна, проста й чесна форма для CRUD, довідників, звітів, перекладання даних, де інваріантів обмаль. Різак, що вирішує все, — не «чи є в об'єкта методи», а **чи є над його даними правила, які треба тримати завжди**. Немає — лиши пласким. Є, та ще й ростуть, — оживи об'єкт, бо інакше правило розтечеться калюжею, яку потім не збереш.
