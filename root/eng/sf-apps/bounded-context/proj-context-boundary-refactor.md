# ⚙️ proj: розрізати спільну модель надвоє

У нас є клас `User`. Йому три роки, у ньому сорок два поля, і половина з них у будь-якому конкретному місці коду дорівнює `null`. Народився він охайним — ім'я, пошта, телефон. Потім продажі попросили «а давайте тут ще воронку й ймовірність угоди», бухгалтерія попросила «а нам треба ІПН і кредитний ліміт», хтось дописав поле `source`, щоб розрізняти, «звідки цей юзер», і валідацію, що починається з `if (user.source === "sales")`. Тепер кожен, хто торкається `User`, спершу мусить з'ясувати, **який** це юзер, бо клас однаковий, а правила різні.

Це не вигаданий приклад — це найтиповіша хвороба великих систем, і зветься вона **спільна модель на кілька контекстів**. У цьому проєкті ми візьмемо такий `User` і **розріжемо** його — не перепишемо з нуля, а саме розріжемо: механічно, крок за кроком, з робочим кодом на кожному кроці, так, щоб у будь-який момент система лишалася в купі. Наприкінці замість одного класу-брехуна буде дві маленькі чесні моделі й тонкий перекладач між ними.

Задача звучить оманливо просто: «розділити клас надвоє». Але якщо взятися невправно — витягти половину полів у новий клас і лишити старий поруч, — стане тільки гірше: буде два класи, зчеплені намертво, і ще один шар плутанини. Тому важлива не мета, а **послідовність рухів**. Її й розберемо.

## Що саме болить — розгляньмо пацієнта

Ось цей `User`, трохи скорочений (справжній удвічі довший, але й цього досить, щоб побачити всі симптоми):

:::tabs
```ts
// Один User на всю систему — і продажам, і бухгалтерії
class User {
  id: string;
  name: string;
  email: string;

  // маркер, «звідки» цей юзер — уже симптом
  source: "sales" | "billing";

  // поля продажів (для бухгалтерського юзера — null)
  stage: "new" | "qualified" | "won" | "lost" | null;
  probability: number | null;   // 0..1, шанс закрити угоду
  ownerId: string | null;        // менеджер, що веде

  // поля бухгалтерії (для продажного юзера — null)
  taxId: string | null;          // ІПН / ЄДРПОУ
  creditLimit: number | null;
  iban: string | null;

  // ...ще три десятки полів, половина завжди null

  isValid(): boolean {
    if (this.source === "sales") {
      // продажний юзер валідний, якщо має стадію й менеджера
      return this.stage !== null && this.ownerId !== null;
    } else {
      // бухгалтерський — якщо має ІПН
      return this.taxId !== null;
    }
  }
}
```
```python
# Один User на всю систему — і продажам, і бухгалтерії
from typing import Optional, Literal

class User:
    def __init__(self) -> None:
        self.id: str = ""
        self.name: str = ""
        self.email: str = ""

        # маркер, «звідки» цей юзер — уже симптом
        self.source: Literal["sales", "billing"] = "sales"

        # поля продажів (для бухгалтерського юзера — None)
        self.stage: Optional[str] = None       # new | qualified | won | lost
        self.probability: Optional[float] = None   # 0..1, шанс закрити
        self.owner_id: Optional[str] = None    # менеджер, що веде

        # поля бухгалтерії (для продажного юзера — None)
        self.tax_id: Optional[str] = None      # ІПН / ЄДРПОУ
        self.credit_limit: Optional[float] = None
        self.iban: Optional[str] = None

        # ...ще три десятки полів, половина завжди None

    def is_valid(self) -> bool:
        if self.source == "sales":
            # продажний юзер валідний, якщо має стадію й менеджера
            return self.stage is not None and self.owner_id is not None
        # бухгалтерський — якщо має ІПН
        return self.tax_id is not None
```
:::

Придивімося до трьох місць, бо кожне — окремий діагноз, а не просто «некрасиво».

**Поле `source`.** Воно тут не для бізнесу — жодного клієнта не цікавить, «звідки» він. Воно тут, щоб клас **на ходу згадував, ким йому зараз бути**. Це поле-перемикач самоідентичності, і сама його наявність кричить: у класі живе не одне поняття, а два, які він намагається вдавати по черзі.

**Метод `isValid()` з розвилкою.** Слово «валідний» тут означає **дві різні речі** залежно від `source`. Для продажів валідний юзер — той, що має стадію в воронці; для бухгалтерії — той, що має ІПН. Це не одна перевірка з двома гілками. Це **дві різні перевірки**, силоміць запхані в один метод, бо клас один. І кожен, хто викличе `isValid()`, мусить у голові тримати, який зараз юзер, — інакше відповідь безглузда.

**Половина полів завжди `null`.** Для продажного юзера `taxId`, `creditLimit`, `iban` — завжди порожні. Для бухгалтерського завжди порожні `stage`, `probability`, `ownerId`. Тип каже, що ці поля бувають, — а реальність каже, що для цього конкретного юзера їх ніколи не буде. Тип **бреше**: він обіцяє більше, ніж коли-небудь трапляється, і компілятор через цю брехню не може тебе вберегти.

> 🔧 **Навіщо це.** Ці три симптоми — поле-`source`, `if source == ...` у валідації, вічний `null` для половини полів — і є той самий сигнал, що межа [обмеженого контексту](topic:sf-apps/coupling-cohesion) проходить **всередині** цього класу, а клас її ігнорує. Побачив цю трійцю — не додавай сорок третє поле й не пиши гарніший `switch`. Це запрошення на операцію: клас треба розрізати рівно по тій лінії, де `source` роздвоює його на два.

Мета рефакторингу — на малюнку. Зліва пацієнт, справа результат, посередині — рух, який ми зробимо.

## Ідея рефакторингу — п'ять рухів

Перш ніж торкатися коду, назвемо всю послідовність, бо саме порядок робить операцію безпечною. П'ять рухів, кожен лишає систему робочою:

1. **Знайти слово-вилку.** Те поле чи метод, де `source` (чи будь-який `if type == ...`) роздвоює клас. Воно вже показує, **де** пройде розріз.
2. **Виділити дві локальні моделі.** Кожному контексту — свій клас, лише зі своїми полями й своїм єдиним правилом. Без `source`, без чужих полів, без `null`-«на всяк випадок».
3. **Поставити перекладач на межі.** Одну функцію, що бере одну модель і будує з неї іншу, — але тільки там і тільки тим, що справді перетинає кордон.
4. **Прибрати спільну залежність.** Розвести код по контекстах так, щоб продажі більше **фізично не бачили** бухгалтерського класу, і навпаки. Спільним лишається хіба що вузький канал переносу.
5. **Прибрати старий `User`.** Коли обидва боки живуть на своїх моделях, спільний клас стає нічий — видаляємо, і разом з ним зникає `source`.

Ключове тут — не «переписати», а **послідовно вимкнути** старий клас, лишаючи новий працювати поруч, доки старий не спорожніє сам. Розберемо кожен рух на коді.

## Крок 1 — знайти слово-вилку

Це вже зроблено оком, але зафіксуймо метод, бо на більших класах вилка не завжди на видноті. Шукаємо не «велике поле» й не «негарну назву» — шукаємо **місце, де те саме слово означає різне залежно від різновиду об'єкта**. Практично — три знахідки:

- поле-дискримінатор: `source`, `type`, `kind`, `role` — усе, що клас питає в самого себе, «ким мені зараз бути»;
- будь-яка гілка `if (x.source === ...)` / `switch (x.type)` **у бізнес-логіці** (не в серіалізації — там вона законна);
- групи полів, що вмикаються-вимикаються разом: коли `stage`, `probability`, `ownerId` або всі три заповнені, або всі три `null`.

У нашому `User` усі три знахідки збігаються на одній лінії: `source` ділить поля на дві грона й розводить `isValid()` на дві гілки. Отже, розріз пройде саме тут: **продажі** з одного боку, **бухгалтерія** з другого. Слово-вилка — це «валідний юзер», яке насправді два різні поняття.

> 🔧 **Навіщо це.** Помилка новачка — різати за формальною ознакою: «винесу всі nullable-поля в окремий клас». Так виходить розріз не по шву поняття, а поперек нього, і половина методів починає смикати обидва класи. Різати треба **по слову-вилці**: спершу знайти, де мова роздвоюється, і тільки потім краяти. Лінію проводить мова, а не тип поля.

## Крок 2 — виділити дві локальні моделі

Тепер найприємніше. Народжуємо два класи, кожен — чесний мешканець свого контексту. Головне правило кроку: **новий клас не має жодного поля іншого контексту й жодного `null`-«про запас».** Якщо поле в цьому світі обов'язкове — воно не-nullable, і конструктор не дасть створити об'єкт без нього.

Продажі. Тут юзер — це **потенційна угода в воронці**, тому й назвемо його по-їхньому: не абстрактний `User`, а `Lead` (англ. *lead* — наводка, зачіпка на клієнта). У нього є стадія, ймовірність і менеджер — і все це обов'язкове, бо ліда без стадії у воронці не буває.

:::tabs
```ts
// Контекст ПРОДАЖІВ: юзер — це наводка на угоду
namespace Sales {
  export class Lead {
    constructor(
      readonly id: string,
      readonly name: string,
      readonly stage: "new" | "qualified" | "won" | "lost",  // не null!
      readonly probability: number,                           // не null!
      readonly ownerId: string,                               // не null!
    ) {
      if (probability < 0 || probability > 1)
        throw new Error("ймовірність поза [0, 1]");
    }
    // валідність тепер вбудована: ліда без стадії просто не існує.
    // Жодного taxId, iban — цей світ про них не чув.
  }
}
```
```python
# Контекст ПРОДАЖІВ: юзер — це наводка на угоду
from dataclasses import dataclass
from typing import Literal

Stage = Literal["new", "qualified", "won", "lost"]

@dataclass(frozen=True)
class Lead:
    id: str
    name: str
    stage: Stage        # не None!
    probability: float  # не None!
    owner_id: str       # не None!

    def __post_init__(self) -> None:
        if not 0 <= self.probability <= 1:
            raise ValueError("ймовірність поза [0, 1]")
    # валідність тепер вбудована: ліда без стадії просто не існує.
    # Жодного tax_id, iban — цей світ про них не чув.
```
:::

Бухгалтерія. Тут той самий колись-`User` — це **платник**, тому `Payer` (англ. *payer* — платник). У нього є ІПН, кредитний ліміт і рахунок; стадія й ймовірність тут — порожній звук.

:::tabs
```ts
// Контекст БУХГАЛТЕРІЇ: юзер — це платник за рахунками
namespace Billing {
  export class Payer {
    constructor(
      readonly id: string,
      readonly name: string,
      readonly taxId: string,           // не null: без ІПН платника немає
      readonly creditLimit: number,     // не null
      readonly iban: string,            // не null
    ) {
      if (!/^\d{8,10}$/.test(taxId))
        throw new Error("ІПН має бути 8–10 цифр");
    }
    // Жодного stage, probability — бухгалтерії байдуже до воронки.
  }
}
```
```python
# Контекст БУХГАЛТЕРІЇ: юзер — це платник за рахунками
from dataclasses import dataclass
import re

@dataclass(frozen=True)
class Payer:
    id: str
    name: str
    tax_id: str        # не None: без ІПН платника немає
    credit_limit: float
    iban: str

    def __post_init__(self) -> None:
        if not re.fullmatch(r"\d{8,10}", self.tax_id):
            raise ValueError("ІПН має бути 8–10 цифр")
    # Жодного stage, probability — бухгалтерії байдуже до воронки.
```
:::

Зверни увагу, що сталося з `isValid()`. Він **зник** — і це перемога, а не втрата. У старому класі валідність була окремою перевіркою, бо клас дозволяв створити нісенітницю (ліда без стадії) і мусив потім ту нісенітницю ловити. Тепер створити нісенітницю **неможливо**: `Lead` без стадії не збереться, конструктор не пропустить. Правило переїхало з методу, який треба **не забути викликати**, у конструктор, який **не можна обійти**. Це і є та сама [інкапсуляція інваріанта](topic:sf-apps/interface-vs-implementation): модель, яка може існувати лише в правильному стані, не потребує зовнішнього наглядача за своєю правильністю.

І найважливіше на цьому кроці: обидва класи поки що **живуть поряд зі старим `User`**. Ми нічого не зламали — просто дописали дві нові моделі. Старий код ще працює через `User`; новий уже може працювати через `Lead`/`Payer`. Система в купі.

## Крок 3 — перекладач на межі

Контексти не ізольовані: настає мить, коли бухгалтерії треба виставити рахунок тому, хто в продажах був лідом і угоду закрив. Дані мусять перетнути кордон. І ось тут — найтонше місце всього рефакторингу, бо саме тут народжуються нові витоки, якщо зробити недбало.

Наївний хід — навчити `Lead` віддавати себе як `Payer`: дописати `Lead` метод `toPayer()`. Це помилка, і глибша, ніж здається. Метод `toPayer()` **всередині** `Lead` означає, що клас продажів **знає про існування** класу бухгалтерії. Ми щойно розвели два світи — і тут-таки прорубуємо між ними наскрізну дірку: тепер продажі не скомпілюються без бухгалтерії, і зчеплення, яке ми виганяли дверима, залізло вікном.

Правильно — винести переклад **у окрему функцію на межі**, що не належить жодному з двох класів. Вона бере `Lead` і будує `Payer`; `Lead` про неї не знає, `Payer` про неї не знає, обидва лишаються чистими. Цей перекладач і є найтонший шматок [антикорупційного шару](topic:sf-apps/anti-corruption-layer) — стінки, що впускає чужі дані, але не чужі поняття.

:::tabs
```ts
// Перекладач ЖИВЕ НА МЕЖІ — в окремому модулі, не в Sales і не в Billing.
// Це антикорупційний шар бухгалтерії: приймає чужу модель, віддає свою.
import { Sales } from "./sales";
import { Billing } from "./billing";

export function leadToPayer(
  lead: Sales.Lead,
  taxId: string,        // ІПН прийшов НЕ з ліда — його дає сам платник
  iban: string,
): Billing.Payer {
  // беремо лише те, що справді перетинає кордон: id та ім'я.
  // stage, probability, ownerId ЛИШАЮТЬСЯ за дверима — бухгалтерії вони чужі.
  return new Billing.Payer(
    lead.id,
    lead.name,
    taxId,
    0,          // стартовий кредитний ліміт — правило БУХГАЛТЕРІЇ, не ліда
    iban,
  );
}
```
```python
# Перекладач ЖИВЕ НА МЕЖІ — в окремому модулі, не в sales і не в billing.
# Це антикорупційний шар бухгалтерії: приймає чужу модель, віддає свою.
from sales import Lead
from billing import Payer

def lead_to_payer(lead: Lead, tax_id: str, iban: str) -> Payer:
    # беремо лише те, що справді перетинає кордон: id та ім'я.
    # stage, probability, owner_id ЛИШАЮТЬСЯ за дверима — бухгалтерії чужі.
    return Payer(
        id=lead.id,
        name=lead.name,
        tax_id=tax_id,
        credit_limit=0,   # стартовий ліміт — правило БУХГАЛТЕРІЇ, не ліда
        iban=iban,
    )
```
:::

Тут три рішення, кожне навмисне.

**Перекладач в окремому модулі.** Не метод `Lead`, не метод `Payer`, а вільна функція, що імпортує обидва. Залежність тепер спрямована **всередину** перекладача — обидва класи його не знають. Прибереш бухгалтерію — `Lead` навіть не помітить.

**Перекладач бере не все.** Через кордон переходять тільки `id` і `name` — рівно те, що спільне обом світам. `stage`, `probability`, `ownerId` **не перетинають межу** — вони лишаються в продажах, бо в бухгалтерії не мають сенсу. Перекладач — це фільтр, а не копіювач: що не потрібне на тому боці, те не пускають.

**Чого в ліда немає — те приходить збоку.** `taxId` та `iban` не витягнуто з `Lead`, бо їх там і не було: ІПН людина дає бухгалтерії окремо, коли час платити. А `creditLimit = 0` — це стартове **правило бухгалтерії**, і воно народжується **тут**, на її боці, а не переноситься з ліда. Перекладач не вигадує чужі поля з повітря й не тягне їх звідти, де їх нема, — він чесно позначає: оце народжується в контексті-отримувачі.

> 🔧 **Навіщо це.** Перекладач на межі — це запобіжник від найпідступнішого витоку: коли зручність «та просто переллємо всі поля» протягує поняття продажів у бухгалтерію. Правило залізне: **через кордон переходить лише те, що має сенс по той бік, і будує це модель отримувача, а не віддає модель відправника.** Одна функція — і два світи торкаються, не змішуючись.

## Крок 4 — прибрати спільну залежність

Класи розведено, перекладач стоїть. Лишилося прибрати останню невидиму нитку — місця, де код **обох** контекстів іще смикає старий спільний `User`. Поки хоч один такий виклик є, розріз несправжній: обидва боки прив'язані до спільного класу, і `source` живий.

Пройдімося по викликах. Було десь так — одна функція, що обслуговувала і продажі, і бухгалтерію через `source`:

:::tabs
```ts
// БУЛО: одна функція на два світи, розвилка всередині
function describe(user: User): string {
  if (user.source === "sales") {
    return `Лід ${user.name}: стадія ${user.stage}, шанс ${user.probability}`;
  } else {
    return `Платник ${user.name}: ІПН ${user.taxId}, ліміт ${user.creditLimit}`;
  }
}
```
```python
# БУЛО: одна функція на два світи, розвилка всередині
def describe(user: User) -> str:
    if user.source == "sales":
        return f"Лід {user.name}: стадія {user.stage}, шанс {user.probability}"
    return f"Платник {user.name}: ІПН {user.tax_id}, ліміт {user.credit_limit}"
```
:::

Ця функція — та сама хвороба в мініатюрі: `describe` вдає, що описує «юзера», а насправді описує **дві різні речі** з розвилкою по `source`. Розрізаємо її навпіл, кожну половину — у свій контекст, і жодна більше не питає `source`, бо тип уже все сказав:

:::tabs
```ts
// СТАЛО: у кожного контексту свій опис своєї моделі
namespace Sales {
  export function describe(lead: Lead): string {
    return `Лід ${lead.name}: стадія ${lead.stage}, шанс ${lead.probability}`;
  }
}
namespace Billing {
  export function describe(payer: Payer): string {
    return `Платник ${payer.name}: ІПН ${payer.taxId}, ліміт ${payer.creditLimit}`;
  }
}
```
```python
# СТАЛО: у кожного контексту свій опис своєї моделі
# sales.py
def describe(lead: Lead) -> str:
    return f"Лід {lead.name}: стадія {lead.stage}, шанс {lead.probability}"

# billing.py
def describe(payer: Payer) -> str:
    return f"Платник {payer.name}: ІПН {payer.tax_id}, ліміт {payer.credit_limit}"
```
:::

Дивись, що зникло: `if (user.source === ...)`. Розвилки більше немає **ніде**, бо немає що розвилювати — на вході в `Sales.describe` завжди `Lead`, на вході в `Billing.describe` завжди `Payer`, і тип це стереже. Кожне поле, до якого тягнешся, тут **гарантовано** існує: у `Sales.describe` немає спокуси написати `lead.taxId`, бо в `Lead` такого поля нема й код не скомпілюється. Компілятор із безпорадного свідка перетворився на охоронця межі.

Так само переносимо решту викликів: кожне місце, що читало `user.stage`, — у бік продажів на `Lead`; кожне, що читало `user.taxId`, — у бік бухгалтерії на `Payer`. Робити це варто **по одному виклику за раз**, щоб система лишалася робочою після кожної правки, а не «переллємо все й помолимося». Це ключова властивість усього підходу: рефакторинг іде **дрібними безпечними кроками**, а не одним стрибком — принцип, докладно розібраний у [запахах коду й дрібних кроках](topic:sf-apps/coupling-cohesion/proj-refactor-smells.md).

## Крок 5 — прибрати старий `User`

Коли останній виклик переїхав, спільний `User` стає **нічий**: жоден рядок бізнес-логіки його вже не згадує. Тепер його можна видалити — і разом з ним зникає поле `source`, бо ділити більше нема кого. Це не окрема дія, а природний фінал: клас не «видаляють зусиллям», він **спорожнів сам**, і його прибирають, як прибирають риштування з добудованого дому.

Ось стан ДО і ПІСЛЯ поруч, щоб побачити всю відстань, яку ми пройшли:

:::tabs
```ts
// ДО: один клас, поле source, розвилка у валідації, півполя null
class User {
  source: "sales" | "billing";
  stage: ... | null;   taxId: ... | null;   /* +40 полів */
  isValid(): boolean {
    if (this.source === "sales") return this.stage !== null && this.ownerId !== null;
    return this.taxId !== null;
  }
}

// ПІСЛЯ: два чисті світи + перекладач на межі
namespace Sales   { export class Lead  { /* stage, probability, ownerId — усі обов'язкові */ } }
namespace Billing { export class Payer { /* taxId, creditLimit, iban — усі обов'язкові */ } }
function leadToPayer(lead: Sales.Lead, taxId: string, iban: string): Billing.Payer { /* межа */ }
// source більше немає. isValid() більше немає. null-полів немає.
```
```python
# ДО: один клас, поле source, розвилка у валідації, півполя None
class User:
    source: str
    stage: Optional[str]; tax_id: Optional[str]   # +40 полів
    def is_valid(self) -> bool:
        if self.source == "sales":
            return self.stage is not None and self.owner_id is not None
        return self.tax_id is not None

# ПІСЛЯ: два чисті світи + перекладач на межі
@dataclass(frozen=True)
class Lead:  ...   # stage, probability, owner_id — усі обов'язкові
@dataclass(frozen=True)
class Payer: ...   # tax_id, credit_limit, iban — усі обов'язкові
def lead_to_payer(lead: Lead, tax_id: str, iban: str) -> Payer: ...  # межа
# source більше немає. is_valid() більше немає. None-полів немає.
```
:::

Що ми виграли, крім краси. По-перше, **неможливі стани стали справді неможливими**: не буває `Lead` без стадії, не буває `Payer` без ІПН — тип це гарантує, і цілий клас багів («а тут `stage` виявився `null`») просто зник як явище. По-друге, **зміни перестали розповзатися**: нове правило продажів чіпає лише `Lead` і `Sales.*`, бухгалтерія його навіть не перекомпілює. По-третє, **код нарешті читається як предмет**: у файлі продажів усе про воронку й нічого про ІПН, і новачок, відкривши його, бачить один зв'язний світ, а не сорок полів упереміш.

## Складність і типові пастки

Розріз здається прямолінійним, доки не наступиш на одну з трьох мін. Кожна на вигляд — «дрібне спрощення», а насправді тихо повертає ту саму хворобу.

**Пастка перша: лишити спільний DTO наскрізним.** Найспокусливіша. «Моделі розрізали, добре, — але хай хоч [DTO](topic:sf-apps/dto) буде один спільний, ми ж усе одно ганяємо дані по HTTP». І ось з'являється `UserDTO` на сорок полів, який приймає й продажний ендпойнт, і бухгалтерський, і кожен бере з нього свою половину. Ти щойно вигнав спільну модель через двері — і впустив її назад як «усього лише формат передачі». А DTO — це теж модель, просто на кордоні; спільний DTO на два контексти має рівно ту саму ваду, що спільний клас: половина полів завжди порожня, і `source` неминуче повертається, щоб розрізняти, «який це DTO». Правильно — **свій DTO на кожен контекст**: `LeadDTO` з полями продажів, `PayerDTO` з полями бухгалтерії. Формат передачі підкоряється тим самим межам, що й модель, бо він **і є** модель, вбрана в дорогу.

**Пастка друга: витік чужих понять через перекладач.** Перекладач — саме те місце, де охоронець найлегше засинає. Написати `leadToPayer` і, «щоб не пропало», перенести в `Payer` заразом `stage` і `probability` — «раптом бухгалтерії колись знадобиться, з якої стадії прийшов платник». Не знадобиться — а `Payer` уже носить у собі поняття продажів, і за пів року хтось у бухгалтерії напише логіку «якщо платник прийшов зі стадії won…», і два світи знову зрослися, тепер уже через перекладач. Правило: **перекладач переносить лише те, що має власний сенс у контексті-отримувачі.** `stage` у бухгалтерії сенсу не має — отже, лишається за дверима, хоч би як просилося. Двері в стіні існують, щоб фільтрувати, а не щоб бути завжди навстіж.

**Пастка третя: надто дрібне різання.** Протилежний перегин, і від переляку перед першими двома пастками в нього легко впасти. Розрізали `User` надвоє — сподобалося — і пішло: а розділімо `Lead` на `LeadCore` і `LeadStage`, а `Payer` на `PayerIdentity` і `PayerCredit`… І ось `Lead`, який був одним зв'язним поняттям з одним інваріантом («ймовірність у межах [0,1] при живій стадії»), розірваний на три класи, і щоб зробити просту дію, доводиться щоразу зшивати їх назад через ще жменю перекладачів. Правило [зчеплення і зв'язності](topic:sf-apps/coupling-cohesion) працює в **обидва** боки: різати треба там, де слово роздвоюється (`User` → `Lead` + `Payer` — там воно справді роздвоювалося), і **не різати** там, де поняття одне (`Lead` — це один лід, його ІПН… стоп, у ліда нема ІПН, і це якраз ознака, що всередині `Lead` різати вже нема чого). Ознака перерізу — той самий тест: чи роздвоюється **слово**? Якщо ні — не край.

Спільне в усіх трьох пастках одне: розріз моделей — не разова «нарубаємо класів» акція, а рух точно **по швах мови**, не грубіше й не дрібніше. Провів межу там, де «валідний юзер» означав дві різні речі, — виграв. Провів там, де слово насправді одне, чи лишив спільний канал в обхід межі, — просто розмазав ту саму плутанину тонше. Уся вправність — у тому, щоб різати рівно по слову-вилці: ні на поле більше, ні на поле менше.
