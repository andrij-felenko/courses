# Порожній об'єкт

<preknowlist>
- [Поліморфізм і динамічне зв'язування](topic:sf-lang/polymorphism) — виклик через абстрактний тип у рантаймі потрапляє в потрібну реалізацію; саме цей механізм дає порожньому об'єкту підмінити справжній так, що той, хто кличе, нічого не помічає.
- [Інтерфейс проти реалізації](topic:sf-apps/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні, і тим, ЯК він це робить; порожній об'єкт реалізує той самий інтерфейс, лише з «нічого-не-роблячим» тілом.
</preknowlist>

Уяви клас, що пише події в журнал: «замовлення оформлено», «платіж відхилено». Ти кличеш `logger.write("платіж відхилено")` — і все гаразд, поки логер справді є. Але буває, що його немає: у тесті ти його не підставив, у якомусь режимі логування вимкнене, конфіг не задав файл. Тоді в полі `logger` лежить `null` — «нічого». І щойно ти покличеш `logger.write(...)`, програма впаде: не можна послати повідомлення тому, кого немає.

Ти вивчаєш урок і починаєш захищатися:

```ts
if (this.logger !== null) {
  this.logger.write("платіж відхилено");
}
```

Спершу це здається дрібницею. Але таких місць, де ти щось логуєш, у сервісі десятки — і біля кожного тепер стоїть та сама перевірка. Код розпух удвічі, і половина його — не про справу, а про боязку примовку «якщо ти взагалі є». Гірше за багатослів'я те, що досить **забути** одну перевірку — і в найгірший момент, коли якраз треба записати помилку, програма падає сама. Захист, який мусить рятувати, тримається на людській уважності, а вона підводить.

Придивімося, звідки цей біль росте. Тип поля каже `Logger` — обіцяє, що там логер, здатний прийняти `write`. Але `null` — не логер. Це **діра в типі**: значення, яке не вміє відповісти на жодне повідомлення. Компілятор пообіцяв тобі «тут об'єкт, якому можна писати», а насправді дав «може, об'єкт, а може, порожнеча». І цю невиконану обіцянку тепер вручну добираєш ти — перевіркою перед кожним викликом. Податок за те, що логера **може** не бути, платить кожен, хто логером користується. (Не випадково саму ідею null-посилання її винахідник згодом назвав дорогою помилкою — про це в [нотатці про народження патерна](topic:sf-apps/null-object/hist-null-object-birth.md).)

## Ідея: зробити відсутність повноцінним об'єктом

А що, як «немає логера» перестати зображати дірою й зробити… логером? Не `null`, а справжнім об'єктом того самого типу, який на кожне повідомлення чесно відповідає — просто нічого не робить. Його `write(...)` мовчки нічого не пише й повертає керування. Тоді полю `logger` **ніколи** не треба лежати порожнім: коли логування вимкнене, там лежить цей «тихий» логер. А той, хто кличе `logger.write(...)`, робить це наосліп — і воно завжди безпечно спрацьовує, бо об'єкт є завжди.

Це і є **порожній об'єкт (англ. *Null Object* — об'єкт-заступник «нічого», що має інтерфейс звичайного, але поводиться нейтрально)**: замість `null` підставити об'єкт того самого інтерфейсу, чиї методи виконують безпечну «нічого-дію». Перевірки зникають не тому, що ми їх кудись поховали, а тому, що **перевіряти більше нічого** — діри немає, є значення.

*Порівняння двох світів: ліворуч посилання дивиться в порожнечу, тож кожен виклик мусить спершу спитати «а ти є?»; праворуч воно дивиться на тихий об'єкт, що відповідає на все, тож кличуть наосліп.*

![Ліва колонка «null — діра»: об'єкт-клієнт, від нього три виклики, кожен обгорнутий перевіркою «якщо ≠ null», стрілка веде до пунктирного кружечка null, помеченого хрестиком «не відповідає». Права колонка «порожній об'єкт — значення»: той самий клієнт, три виклики вже без перевірок, стрілка веде до суцільної рамки NullLogger «нічого не робить», помеченої галочкою «відповідає завжди». Нижня плашка: перевірки зникли, бо перевіряти нічого](img/hole-vs-value.svg)

Розберімо це на коді. Спершу — інтерфейс і звичайна реалізація, а поряд — порожня:

:::tabs
```ts
interface Logger {
  write(msg: string): void;
}

class FileLogger implements Logger {
  constructor(private path: string) {}
  write(msg: string): void {
    appendFileSync(this.path, msg + "\n");
  }
}

class NullLogger implements Logger {
  write(_msg: string): void { /* навмисно нічого */ }
}
```
```py
from typing import Protocol

class Logger(Protocol):
    def write(self, msg: str) -> None: ...

class FileLogger:
    def __init__(self, path: str) -> None:
        self._path = path
    def write(self, msg: str) -> None:
        with open(self._path, "a", encoding="utf-8") as f:
            f.write(msg + "\n")

class NullLogger:
    def write(self, msg: str) -> None:
        pass                        # навмисно нічого
```
:::

Тепер той, хто логером користується. Його поле — завжди `Logger`, ніколи порожнє, тож у коді немає жодної перевірки:

:::tabs
```ts
class OrderService {
  constructor(private logger: Logger) {}     // завжди Logger, ніколи null

  place(order: Order): void {
    // ...оформлення замовлення...
    this.logger.write(`замовлення ${order.id} оформлено`);  // без перевірки
  }
}

// логування ввімкнене:
new OrderService(new FileLogger("orders.log"));
// вимкнене — підставляємо ПОРОЖНІЙ об'єкт, а не null:
new OrderService(new NullLogger());
```
```py
class OrderService:
    def __init__(self, logger: Logger) -> None:
        self._logger = logger        # завжди Logger, ніколи None

    def place(self, order: Order) -> None:
        # ...оформлення замовлення...
        self._logger.write(f"замовлення {order.id} оформлено")  # без перевірки

# логування ввімкнене:
OrderService(FileLogger("orders.log"))
# вимкнене — ПОРОЖНІЙ об'єкт, не None:
OrderService(NullLogger())
```
:::

Рішення «є логер чи ні» переїхало **в одне місце** — туди, де сервіс складають. Далі за течією про це вже ніхто не думає: `place`, `cancel`, `refund` кличуть `logger.write(...)` однаково й безпечно. Стабільний код (сам сервіс) став простішим саме тому, що змінне питання «а раптом порожньо?» винесли за його межі.

## Чому підстановка непомітна

Уся магія тут — звичайне [динамічне зв'язування](topic:sf-lang/polymorphism). Виклик `this.logger.write(...)` не знає наперед, у чиє тіло він потрапить: у рантаймі керування піде до того класу, чий об'єкт зараз лежить у полі. Лежить `FileLogger` — запишеться рядок; лежить `NullLogger` — виконається порожнє тіло й керування тихо повернеться. Клієнт бачить лише інтерфейс `Logger` і однаково поводиться з обома, бо обидва **чесно** цей інтерфейс виконують. Порожній об'єкт непомітний саме тому, що він не підробка під логер — він **справжній** логер, просто з нейтральною поведінкою.

![Угорі — інтерфейс Logger із методом write(msg). Від нього вниз рейкою відходять дві рівноправні реалізації: FileLogger «пише рядок у файл» і NullLogger «нічого не робить». Ліворуч — клієнт OrderService, що тримає поле типу Logger і кличе write() наосліп, не розгалужуючись. Підпис унизу: порожній — не виняток зі схеми, а ще одна її реалізація нарівні зі справжньою](img/null-object-skeleton.svg)

*Порожній об'єкт — це не «особливий випадок» поза схемою, а ще одна реалізація інтерфейсу нарівні зі справжньою. Клієнт залежить лише від інтерфейсу й не бачить різниці.*

Є в цьому й глибша, майже алгебрична причина, чому підставляти порожній об'єкт **безпечно**. Його «нічого-дія» грає роль нейтрального елемента: як додавання нуля не змінює суми, так виклик тихого логера не змінює того, що спостерігає решта програми. Підстановка, яка гарантовано нічого не порушує, — це підстановка нейтрального елемента замість активного; чому саме ця властивість робить порожній об'єкт коректним і де вона ламається, розібрано в [математичній нотатці](topic:sf-apps/null-object/math-null-as-neutral-element.md).

> 🔧 **Навіщо це.** Найчастіше порожній об'єкт заводять для необов'язкових співпрацівників — саме таких, як логер: метрики, кеш, аналітика, обробник подій, стратегія повторних спроб. Усе це речі, яких у певному режимі (тест, локальний запуск, урізана редакція) може не бути, а основна логіка мусить працювати без них однаково. Замість того щоб просякнути весь код перевірками «а чи ввімкнено метрики», підставляють тихий об'єкт-заглушку — і гарячий шлях лишається чистим. У тестах це ще й найпростіший спосіб знешкодити побічний ефект: підсунув `NullLogger` — і тест не смітить у файли.

## Не лише «нічого не робити» — ще й «нейтрально відповідати»

Логер зручний, бо його методи нічого не повертають: нейтральна дія — просто промовчати. Але порожній об'єкт корисний і там, де метод мусить **повернути значення**. Тоді його завдання — віддати таку відповідь, з якою решта коду поведеться розважливо й без падіння.

Класичний приклад — пошук клієнта, який міг нічого не знайти:

:::tabs
```ts
interface Customer {
  name(): string;
  discountRate(): number;
}

class RegularCustomer implements Customer {
  constructor(private _name: string, private rate: number) {}
  name(): string { return this._name; }
  discountRate(): number { return this.rate; }
}

class NullCustomer implements Customer {
  name(): string { return "Гість"; }        // нейтральне ім'я
  discountRate(): number { return 0; }      // жодної знижки — розумний типовий стан
}

function findCustomer(id: string): Customer {
  return db.lookup(id) ?? new NullCustomer();  // ніколи не повертаємо null
}
```
```py
class Customer(Protocol):
    def name(self) -> str: ...
    def discount_rate(self) -> float: ...

class RegularCustomer:
    def __init__(self, name: str, rate: float) -> None:
        self._name, self._rate = name, rate
    def name(self) -> str: return self._name
    def discount_rate(self) -> float: return self._rate

class NullCustomer:
    def name(self) -> str: return "Гість"       # нейтральне ім'я
    def discount_rate(self) -> float: return 0.0  # жодної знижки

def find_customer(cid: str) -> Customer:
    return db.lookup(cid) or NullCustomer()      # ніколи не None
```
:::

Тепер `findCustomer(id).discountRate()` працює завжди: знайшли справжнього — повернеться його ставка; не знайшли — повернеться нуль, і ціна порахується без знижки, як для гостя. Виклик не мусить питати «а чи є клієнт» — порожній клієнт **сам знає**, як виглядає розумна відповідь за відсутності. Порожній об'єкт буває двох ґатунків: тихий (метод нічого не робить) і відповідальний (метод віддає нейтральне значення) — але суть одна: замість діри, з якою мусить розбиратися кожен, є об'єкт, який розбирається сам.

## Де мовчання стає небезпечним

Тепер найважливіше застереження, бо саме тут порожній об'єкт з ліки перетворюється на отруту. Він **прибирає перевірку разом із питанням, яке за нею стояло**. Іноді це саме те, чого ми хотіли: логер справді необов'язковий, гість справді має нульову знижку. Але буває, що відсутність — це **симптом помилки**, і тоді тиха підстанова нейтрального значення **ховає баг**, замість того щоб про нього закричати.

Уяви, що клієнт мусив би бути завжди — ми оформляємо замовлення на конкретну людину, — а `findCustomer` не знайшов його через збій у базі. Порожній клієнт слухняно поверне «Гість» і нульову знижку; замовлення тихо оформиться не на того; ніхто нічого не помітить, поки за місяць не зійдеться звітність. Дірка-`null` бодай впала б одразу й показала місце. Порожній об'єкт **проковтнув** проблему.

Звідси проста межа. Порожній об'єкт доречний там, де відсутність — **законний, очікуваний стан** з осмисленою нейтральною поведінкою (немає логера — не логуємо; немає знижки — рахуємо повну ціну). Він недоречний там, де відсутність — це **порушення, яке має спинити виконання**: там мовчати не можна, там треба голосно впасти або повернути помилку. Це той самий принцип, що [жодна помилка не має мовчати](topic:sf-apps/error-handling): порожній об'єкт легалізує лише те «нічого», яке справді дозволене, і не сміє глушити те, яке сигналить про поламане.

## Порожній об'єкт проти Optional

Є й інший спосіб чесно сказати «значення може бути відсутнє» — не ховати відсутність за нейтральним об'єктом, а зробити її **видимою в типі**. Замість `Customer`, що потайки буває порожнім, повертають `Optional<Customer>` (у різних мовах — `Option`, `Maybe`, `Customer | null` під суворою перевіркою): тип прямо каже «тут або клієнт, або нічого», і компілятор **змушує** обробити обидва випадки, перш ніж чіпати вміст.

Це протилежні філософії. Порожній об'єкт каже: «відсутності не існує — усе завжди об'єкт, поводься однаково». `Optional` каже: «відсутність існує й помітна — щоразу свідомо вирішуй, що з нею робити». Перший прибирає розгалуження й тим спрощує код там, де нейтральна поведінка правильна за замовчуванням. Другий, навпаки, розгалуження **вимагає** — і тим не дає забути про випадок, коли відсутність важлива. Тому їх і обирають за різних потреб: порожній об'єкт — коли «немає» майже завжди означає ту саму безпечну дію; `Optional` — коли «немає» щоразу вимагає окремого, свідомого рішення й мовчки проковтнути його було б бідою. Як зробити відсутність частиною типу, а не діркою в ньому, розгорнуто в статті [про типи як дизайн](topic:sf-apps/type-driven-design).

## Коли він зайвий

Порожній об'єкт окупається, коли перевірок на порожнечу **багато** й вони розсипані по коду, а нейтральна поведінка чітка й однакова. Якщо ж перевірка одна-однісінька і в одному місці, окремий клас-заглушка лише додасть церемонії: звичайний `if` там читається легше. Не варто заводити порожній об'єкт і тоді, коли для «немає» немає **осмисленого** нейтрального значення — коли будь-яка вигадана відповідь однаково бреше. Тоді чесніше лишити видиму відсутність (той-таки `Optional`) і змусити код із нею рахуватися.

Найздоровіше порожній об'єкт народжується не з креслення наперед, а з помічений біль: у коді розплодилися однакові `if (x != null)`, усі з тією самою нейтральною гілкою — і ти згортаєш цю гілку в окремий тихий клас. Покроковий розбір такого рефакторингу — від коду, засіяного перевірками, до чистих викликів, з увагою до пасток на кшталт «а як тепер відрізнити порожній об'єкт, коли це раптом знадобилось» — винесено в [окремий приклад](topic:sf-apps/null-object/proj-refactor-null-checks.md).

![Три колонки — три способи зустріти відсутність. Ліва «null + перевірка», підсвічена насторожним кольором: можна забути перевірку, і тоді програма впаде. Середня «порожній об'єкт», зелена з жовтим застереженням: безпечно завжди, розгалужень немає, але може тихо приховати відсутність, що була помилкою. Права «Optional / сума-тип», зелена: тип змушує свідомо обробити обидва випадки, забути неможливо. Під кожною — короткий компроміс](img/three-ways-absence.svg)

*Три відповіді на «значення може бути відсутнє»: перевірка вручну (легко забути), порожній об'єкт (безпечно, але глушить), видима відсутність у типі (змушує обробити). Вибір — за тим, наскільки відсутність важлива й наскільки нейтральна поведінка чесна.*

## Звідки він узявся

Патерн описав Боббі Вулф (Bobby Woolf) — його доповідь «The Null Object Pattern» прозвучала на конференції PLoP 1996 року й вийшла в збірнику «Pattern Languages of Program Design 3» (Addison-Wesley, 1998); це усталений факт. Пізніше Мартін Фаулер у «Patterns of Enterprise Application Architecture» (2002) показав, що порожній об'єкт — окремий випадок ширшого патерна **«особливий випадок» (Special Case)**: клас, що втілює один особливий стан (порожнеча — лише один із них) і тим прибирає перевірки цього стану з усього коду. А тлом усієї історії стоїть та сама діра-`null`, яку Тоні Гоар (Tony Hoare) 1965 року вбудував у мову ALGOL W і через десятиліття привселюдно назвав своєю «помилкою на мільярд доларів». Як ці нитки сплітаються — від винаходу null до патерна, що вчить обходитися без нього, — у [нотатці про народження патерна](topic:sf-apps/null-object/hist-null-object-birth.md).
