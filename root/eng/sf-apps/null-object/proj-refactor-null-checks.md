# ⚙️ Рефакторинг: як однакові `if (x != null)` згорнути в порожній об'єкт

Порожній об'єкт рідко креслять наперед. Куди частіше він народжується з болю: розкриваєш клас, а там одна й та сама перевірка на порожнечу переписана вручну п'ять разів, і в кожній — та сама «нічого-гілка». Це той запах, який лікується прицільно. Розберімо повний рефакторинг на живому прикладі — від коду, засіяного перевірками, до чистих викликів, — а тоді пройдімося по пастках, у які на цьому шляху легко впасти.

## Задача: код, засіяний однією й тією ж перевіркою

Візьмімо акаунт у SaaS-сервісі. У користувача **може** бути платна підписка, а може й не бути — тоді він на вільному тарифі. Розробник зобразив «немає підписки» найпростіше: поле `sub` типу «підписка **або** `null`». І тепер кожен метод, якому підписка потрібна, спершу питає «а вона взагалі є?», і якщо ні — повертає значення вільного тарифу.

:::tabs
```ts
const BASIC = new Set(["export-csv"]);   // що дозволено на вільному тарифі

interface Subscription {
  price(): number;
  storageGb(): number;
  seats(): number;
  includes(feature: string): boolean;
}

class Account {
  constructor(
    readonly name: string,
    private sub: Subscription | null,    // вільні користувачі: null
  ) {}

  monthlyPrice(): number {
    if (this.sub !== null) return this.sub.price();
    return 0;                            // вільний тариф
  }
  storageGb(): number {
    if (this.sub !== null) return this.sub.storageGb();
    return 1;                            // вільний тариф: 1 ГБ
  }
  seats(): number {
    if (this.sub !== null) return this.sub.seats();
    return 1;
  }
  hasFeature(f: string): boolean {
    if (this.sub !== null) return this.sub.includes(f);
    return BASIC.has(f);
  }
}
```
```py
from typing import Optional, Protocol

BASIC = {"export-csv"}                    # що дозволено на вільному тарифі

class Subscription(Protocol):
    def price(self) -> float: ...
    def storage_gb(self) -> int: ...
    def seats(self) -> int: ...
    def includes(self, feature: str) -> bool: ...

class Account:
    def __init__(self, name: str, sub: Optional[Subscription]) -> None:
        self.name = name
        self._sub = sub                   # вільні користувачі: None

    def monthly_price(self) -> float:
        if self._sub is not None:
            return self._sub.price()
        return 0.0                        # вільний тариф

    def storage_gb(self) -> int:
        if self._sub is not None:
            return self._sub.storage_gb()
        return 1                          # вільний тариф: 1 ГБ

    def seats(self) -> int:
        if self._sub is not None:
            return self._sub.seats()
        return 1

    def has_feature(self, f: str) -> bool:
        if self._sub is not None:
            return self._sub.includes(f)
        return f in BASIC
```
:::

Придивімося, що тут насправді написано чотири рази. Не перевірка `!= null` сама по собі — а **ціла політика вільного тарифу**, розмазана по методах: ціна нуль, сховище один гігабайт, одне місце, обмежений набір можливостей. Кожен `else` — крихта цієї політики. Вона не живе ніде як щось цілісне; вона існує лише як чотири уламки, розкидані поміж перевірками.

Звідси й три окремі болі. Перший — багатослів'я: половина тіла кожного методу не про справу, а про боязку примовку «якщо ти взагалі є». Другий, гірший, — крихкість: додаси завтра п'ятий метод (скажімо, `apiRateLimit`) і **забудеш** гілку `else` — акаунт впаде на `null`, а помітиш ти це вже в проді. Третій, найпідступніший, — розповзання правди: захочеш змінити вільне сховище з 1 ГБ на 2 — і мусиш згадати **всі** місця, де вписано «1», нічого не проґавивши. Політику, яка мала б бути однією, доводиться правити в чотирьох.

## Ідея: нейтральну гілку витягти в один клас

Погляньмо на всі чотири `else` разом. Вони не випадково однакові за формою — вони однакові за **суттю**: усі описують поведінку одного й того самого — «підписки немає». А коли кілька шматків коду описують поведінку одного поняття, цьому поняттю просять дати ім'я й тіло. Тобто зробити «немає підписки» **об'єктом**: не діркою `null`, а справжньою підпискою того самого інтерфейсу, яка на кожне запитання чесно відповідає значенням вільного тарифу.

Щойно такий об'єкт існує, поле `sub` більше **ніколи** не мусить бути порожнім: замість `null` там лежить він. А раз поле завжди має значення, перевіряти нема чого — і всі `if (sub !== null)` просто зникають. Не ховаються, а зникають: перевіряти більше нічого.

## Крок за кроком

**Крок 1. Побачити патерн.** Випиши всі місця, де стоїть перевірка. Переконайся, що вони справді **однотипні**: усюди `if (sub != null) → sub.щось()`, а в `else` — стале значення, що залежить лише від «немає підписки», а не від чогось іще. Якщо хоч одна гілка `else` тягне зайвий контекст (наприклад, залежить від імені користувача) — стоп, це вже не проста заміна, повернемося до цього в пастках. У нашому коді всі чотири `else` чисті: 0, 1, 1, `BASIC`.

**Крок 2. Зафіксувати спільний інтерфейс.** Порожній об'єкт мусить бути **невідрізнимим** від справжнього для того, хто його кличе. Отже, він реалізує той самий інтерфейс `Subscription`, що й платна підписка. Інтерфейс у нас уже є (`price`, `storageGb`, `seats`, `includes`) — це і є контракт, на який спираються всі виклики. Якщо в коді інтерфейс досі не виділений, а виклики йдуть на конкретний клас, спершу виділи інтерфейс: без спільного типу підстановка неможлива.

**Крок 3. Написати порожній клас.** Збери всі гілки `else` в один клас, що реалізує інтерфейс. Кожен колишній `else` стає тілом відповідного методу:

:::tabs
```ts
class FreeSubscription implements Subscription {
  price(): number { return 0; }
  storageGb(): number { return 1; }
  seats(): number { return 1; }
  includes(f: string): boolean { return BASIC.has(f); }
}
```
```py
class FreeSubscription:
    def price(self) -> float: return 0.0
    def storage_gb(self) -> int: return 1
    def seats(self) -> int: return 1
    def includes(self, feature: str) -> bool: return feature in BASIC
```
:::

Ось воно — те, чого раніше не було: політика вільного тарифу як **одна річ**. Тепер вона має ім'я, живе в одному місці, і змінити «1 ГБ» на «2 ГБ» означає правку в єдиному рядку.

**Крок 4. Прибрати діру з поля.** Це найважливіший крок, бо саме він робить перевірки зайвими. Треба гарантувати, що в поле `sub` **ніколи** не потрапить `null` — там завжди або платна підписка, або `FreeSubscription`. Рішення «є підписка чи ні» переїжджає в **одне** місце: туди, де акаунт складають (фабрику, завантажувач із бази). Тип поля стає просто `Subscription`, без «або null»:

:::tabs
```ts
const FREE: Subscription = new FreeSubscription();   // спільний, про нього — нижче

class Account {
  constructor(
    readonly name: string,
    private sub: Subscription,          // ніколи не null
  ) {}
  // ...методи — на кроці 5
}

// єдине місце, де вирішуємо: підставити FREE замість null
function accountFor(name: string, sub: Subscription | null): Account {
  return new Account(name, sub ?? FREE);
}
```
```py
FREE: Subscription = FreeSubscription()   # спільний, про нього — нижче

class Account:
    def __init__(self, name: str, sub: Subscription) -> None:
        self.name = name
        self._sub = sub                    # ніколи не None
    # ...методи — на кроці 5

# єдине місце, де вирішуємо: підставити FREE замість None
def account_for(name: str, sub: Optional[Subscription]) -> Account:
    return Account(name, sub or FREE)
```
:::

**Крок 5. Викинути перевірки.** Тепер, коли поле гарантовано має значення, тіла методів згортаються до однорядкового делегування:

:::tabs
```ts
class Account {
  constructor(readonly name: string, private sub: Subscription) {}

  monthlyPrice(): number   { return this.sub.price(); }
  storageGb(): number      { return this.sub.storageGb(); }
  seats(): number          { return this.sub.seats(); }
  hasFeature(f: string): boolean { return this.sub.includes(f); }
}
```
```py
class Account:
    def __init__(self, name: str, sub: Subscription) -> None:
        self.name = name
        self._sub = sub

    def monthly_price(self) -> float:      return self._sub.price()
    def storage_gb(self) -> int:           return self._sub.storage_gb()
    def seats(self) -> int:                return self._sub.seats()
    def has_feature(self, f: str) -> bool: return self._sub.includes(f)
```
:::

## Що змінилося

Полічімо ефект чесно, а не на віру. Розгалужень у `Account` було чотири, стало нуль; єдине розгалуження на весь рефакторинг лишилось в `accountFor` — там, де його місце. Політика вільного тарифу була розсипана чотирма уламками, стала однією річчю з іменем `FreeSubscription`. Зміна вільного сховища з 1 ГБ на 2 була правкою в кількох місцях із ризиком проґавити — стала правкою в одному рядку. Додати нову можливість (той-таки `apiRateLimit`) означало «не забути гілку `else` в новому методі» — тепер означає «додати метод до інтерфейсу й один рядок до `FreeSubscription`», і забути перевірку структурно неможливо: її просто немає.

Тонший виграш — у читанні. Метод `monthlyPrice` тепер каже рівно те, що робить: «ціна підписки». Раніше він казав «ціна підписки, якщо підписка є, а як нема — то нуль» — і читач щоразу мусив тримати в голові обидві гілки, щоб зрозуміти одну думку. Стабільний код (сам `Account`) став простішим саме тому, що змінне питання «а раптом порожньо?» винесли за його межі.

> 🔧 **Навіщо це.** Головна цінність рефакторингу не в тому, що коду стало менше (хоча й це приємно), а в тому, що **політику зібрано в одне місце**. Поки «що робити за відсутності» розмазане по десятках `else`, кожна така крихта — окремий шанс на розбіжність: тут вписали 1 ГБ, там 2 ГБ, а онде забули оновити після зміни правил. Порожній об'єкт робить політику відсутності одиничною сутністю, яку можна прочитати, протестувати й змінити цілком.

## Пастки

Рефакторинг простий на вигляд, але має кілька гострих кутів. Пройдімося по кожному.

### Коли раптом треба відрізнити порожній об'єкт

Ти прибрав усі перевірки — і раптом бухгалтерія просить звіт: «покажи лише платних клієнтів». А в тебе більше немає `if (sub != null)`, яким їх відрізнити. Спокуса — написати `sub instanceof FreeSubscription`. Не роби так: це протягує знання про конкретний клас туди, де його не мало бути, і повертає розгалуження, яке ти щойно виполов, — лише в гіршому, крихкішому вигляді.

Канонічна відповідь патерна — додати до інтерфейсу **детектор**. Часто його звуть `isNull()`, але чесніше — дати йому **семантичне** ім'я, що каже про предметну область, а не про механіку реалізації. Не «чи ти той-порожній», а «чи ти платний»:

:::tabs
```ts
interface Subscription {
  price(): number;
  // ...
  isBillable(): boolean;         // семантичний детектор, не «isNull»
}

class PaidSubscription implements Subscription {
  isBillable(): boolean { return true; }
  // ...
}
class FreeSubscription implements Subscription {
  isBillable(): boolean { return false; }
  // ...
}
```
```py
class Subscription(Protocol):
    def price(self) -> float: ...
    # ...
    def is_billable(self) -> bool: ...   # семантичний детектор, не «is_null»

class PaidSubscription:
    def is_billable(self) -> bool: return True
    # ...
class FreeSubscription:
    def is_billable(self) -> bool: return False
    # ...
```
:::

Але тримай у голові головне застереження: кожен доданий детектор **частково відкочує** рефакторинг — розгалуження повертається, просто тепер його викликають явно там, де воно справді потрібне. Це нормально, поки таких місць одиниці. Якщо ж `isBillable()` розповзається по всьому коду не гірше за колишні `null`-перевірки — це знак, що відсутність тут насправді **важлива** й видима скрізь, і, можливо, чесніше було б лишити її видимою в типі (через `Optional`), а не ховати за порожнім об'єктом. Детектор — виняток, який дозволяєш собі свідомо, а не двері, крізь які старий біль вертається назад.

### Порожні об'єкти в колекціях та ітерації

Порожній об'єкт особливо гарний у колекціях — але саме тут ховається асиметрія, на якій легко обпектися. Порахуймо сумарний місячний дохід по всіх акаунтах:

:::tabs
```ts
const mrr = accounts.reduce((sum, a) => sum + a.monthlyPrice(), 0);
```
```py
mrr = sum(a.monthly_price() for a in accounts)
```
:::

Тут порожній об'єкт працює бездоганно: вільні акаунти повертають `0`, а нуль у сумі нічого не змінює. Не треба ні фільтра, ні перевірки — «нічого-значення» саме собою випадає з результату, бо воно **нейтральне** щодо додавання. Це і є та алгебрична причина, з якої підстановка безпечна: `x + 0 = x`.

А тепер порахуймо **кількість платних** — і тут та сама краса обертається пасткою:

:::tabs
```ts
const paying = accounts.filter(a => a.isBillable()).length;   // правильно
const wrong  = accounts.length;                               // БРЕХНЯ: рахує й вільних
```
```py
paying = sum(1 for a in accounts if a.is_billable())          # правильно
wrong  = len(accounts)                                        # БРЕХНЯ: рахує й вільних
```
:::

Різниця в тому, що для операції «підрахунок» нейтрального елемента **немає** так, як він є для суми: порожній акаунт — не «нуль» лічби, він повноцінний елемент списку, який лічба порахує нарівні з платними. Звідси правило: порожній об'єкт безшовно вливається в ті агрегати, де його «нічого» справді нейтральне (сума, конкатенація, максимум із розумним дном), і **бреше** там, де операція питає «скільки справжніх» чи «чи є хоч один справжній». Для таких — детектор із попереднього пункту.

І ще різкіше: порожньому об'єкту не місце в колекції, яка **за визначенням** містить лише справжні. Список «підписки до виставлення рахунку» не має містити `FreeSubscription` — там відсутність мусить означати «елемента немає в списку», а не «є порожній елемент». Інакше рахунок на нуль гривень поїде вільному користувачеві, і добре, якщо його відсіє валідатор, а не банк.

### Спільний незмінний одинак — один на всіх

Ти, певно, помітив у коді `const FREE = new FreeSubscription()` — **один** екземпляр, який роздають усім вільним акаунтам. Це не випадковість і не мікрооптимізація заради економії пам'яті (хоч і вона тут є). Це можливо тому, що порожній об'єкт **не має власного стану**: усі його відповіді — сталі (0, 1, 1, `BASIC`), однакові для будь-якого акаунта. А раз двом акаунтам він відповідає тотожно, немає жодного сенсу тримати дві його копії — вистачить однієї на всіх.

Передумова тут одна, і вона критична: **незмінність**. Спільний екземпляр безпечний рівно доти, доки його ніхто не може змінити. Варто комусь дописати в `FreeSubscription` поле, яке мутується, — і зміна, зроблена через один акаунт, миттю відгукнеться всім іншим, бо об'єкт у них буквально той самий. Тому порожній об'єкт-одинак тримають [незмінним](topic:sf-apps/immutability): без внутрішнього стану, без сеттерів, лише сталі відповіді. Сам прийом «один спільний екземпляр на всіх» — це [одинак (Singleton)](topic:sf-apps/singleton) у чистому вигляді, і порожній об'єкт — один із небагатьох випадків, де одинак застосовний без застережень саме завдяки незмінності.

Межа проста: **як тільки порожньому об'єкту знадобився власний стан — спільний одинак ламається**. Уяви, що метод мусив би повертати не просто «Гість», а «Гість (акаунт #42)» — тоді відповідь залежить від акаунта, спільний екземпляр більше не годиться, і кожному потрібен свій. Але тут варто зупинитись і спитати себе: якщо «нейтральна» відповідь раптом залежить від контексту — чи вона взагалі нейтральна? Найчастіше потреба в стані всередині порожнього об'єкта — знак, що ти намагаєшся зобразити ним не «немає», а «є, але особливе», і це вже інший патерн.

### Найважливіше: коли відсутність насправді була помилкою

Тепер найгостріший кут, бо саме тут рефакторинг з користі перетворюється на приховану біду. Порожній об'єкт **прибирає перевірку разом із питанням, яке за нею стояло**. Поки була перевірка `if (sub != null)`, у коді залишався слід: «а раптом порожньо?». Порожній об'єкт витирає цей слід — і разом із ним витирає нагоду помітити, що порожнеча буває **різною**.

Придивись до кроку 4, де ми підставляли `FREE` замість `null`. Ми зробили це наосліп: **будь-який** `null` перетворили на вільний тариф. Але звідки той `null` узявся? Варіанти геть різні за змістом:

- користувач справді ніколи не підписувався — тоді вільний тариф **правильна** відповідь;
- запит до бази **впав** — і замість «немає підписки» ти отримав «не вдалося дізнатись», а підставив вільний тариф, ніби відповідь відома;
- у enterprise-акаунта, за який компанія платить тисячі, **зникла** з бази стрічка плану через корупцію даних — і ти мовчки понизив його до вільного тарифу.

Порожній об'єкт **не розрізняє цих трьох** — він на всі однаково відповість «0, 1, 1, BASIC». У перших ролях це рятунок, у двох останніх — катастрофа, яку ніхто не помітить, поки за місяць не зійдеться звітність або поки enterprise-клієнт не подзвонить із питанням, чому в нього раптом одне робоче місце. Дірка-`null` бодай впала б одразу й показала пальцем на місце. Порожній об'єкт **проковтнув** проблему й пішов далі з усмішкою.

![Схема рішення: виклик loadSubscription(userId) веде до розвилки «підписки немає — ЧОМУ?». Ліва гілка, зелена, «дозволена»: користувач справді ніколи не підписувався, підставляємо FreeSubscription. Права гілка, червона, «помилкова»: збій бази або enterprise-акаунт без плану, треба кинути помилку чи підняти тривогу, а не глушити. Унизу: порожній об'єкт легалізує лише дозволену відсутність, помилкову впіймай до підстановки](img/absence-fork.svg)

*Розвилку «чому саме немає підписки» треба пройти на межі — у завантажувачі, ще до того, як вирішувати, підставляти порожній об'єкт чи ні.*

Ліки — провести цю розвилку **на межі**, у тому єдиному місці, куди ми на кроці 4 винесли рішення. Завантажувач мусить розрізнити дозволену відсутність від помилкової **до** того, як підставить порожній об'єкт:

:::tabs
```ts
// ПОГАНО: будь-яка відсутність → FREE, обидва баги проковтнуто
function loadBad(row: Row | null): Subscription {
  return row ? new PaidSubscription(row) : FREE;
}

// ДОБРЕ: розвилку проходимо явно, перш ніж підставляти порожній об'єкт
function loadSubscription(userId: string): Subscription {
  const user = users.get(userId);              // кине, якщо юзера немає — це вже не «вільний»
  const row = plans.find(user.planId);         // find кидає на збій запиту, не повертає null

  if (user.tier === "enterprise" && row === null) {
    // enterprise без плану — порушення інваріанта, а не вільний тариф
    throw new Error(`enterprise-акаунт ${userId} без плану — цілісність порушено`);
  }
  return row === null ? FREE : new PaidSubscription(row);   // рядка нема → законно вільний
}
```
```py
# ПОГАНО: будь-яка відсутність → FREE, обидва баги проковтнуто
def load_bad(row: Optional[Row]) -> Subscription:
    return PaidSubscription(row) if row else FREE

# ДОБРЕ: розвилку проходимо явно, перш ніж підставляти порожній об'єкт
def load_subscription(user_id: str) -> Subscription:
    user = users[user_id]                        # KeyError, якщо юзера немає — це вже не «вільний»
    row = plans.find(user.plan_id)               # find кидає на збій запиту, не повертає None

    if user.tier == "enterprise" and row is None:
        # enterprise без плану — порушення інваріанта, а не вільний тариф
        raise IntegrityError(f"enterprise-акаунт {user_id} без плану — цілісність порушено")

    return FREE if row is None else PaidSubscription(row)   # рядка нема → законно вільний
```
:::

Суть у тому, що порожній об'єкт легалізує лише **дозволену** відсутність — ту, для якої «нічого» є законним, очікуваним станом з осмисленою нейтральною поведінкою. Відсутність, що насправді є [порушенням інваріанта](topic:sf-apps/invariants) («enterprise завжди має план»), мусить голосно спинити виконання, а не тихо перетворитися на вільний тариф. Це той-таки принцип, що [жодна помилка не має мовчати](topic:sf-apps/error-handling): підставляй нейтральне значення тільки там, де ти вже **довів**, що воно правильне для кожного шляху, яким туди можна дійти, — включно зі шляхами-помилками.

Звідси проста перевірка перед рефакторингом. Пробіжи всі гілки `else`, які збираєшся згорнути, і на кожну спитай: «Якщо виконання дійшло сюди **через баг**, а не законно, — цей `else` замаскує баг чи ні?» Якщо замаскує — порожній об'єкт тут не спрощення, а бетон, яким ти замуруєш майбутню помилку так, що її вже не почути. Тоді або лиши видиму відсутність, або спершу розведи законну порожнечу від помилкової на межі — і тільки згорнуту, доведено-законну частину віддавай порожньому об'єктові.
