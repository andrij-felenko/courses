# 📜 Еволюція інтерфейсів за схемою: від XForms і XAML до сучасного Server-Driven UI

У середині 1990-х років ранній Всесвітній павутин працював за абсолютно простою моделлю: сервер надсилав клієнту розмітку HTML, що містила тег `<form>` із набором елементів `<input>`. Браузер був «німим терміналом» — він не знав про типи даних, не мав локального стану й не вмів перевіряти коректність вводу без повного перезавантаження сторінки через HTTP POST. Коли користувач робив друкарську помилку в номері кредитної картки, сервер відхиляв увесь документ, рендерив сторінку наново й повертав її назад мережею.

Це породило першу кризу розділення обов'язків: як дати клієнту декларативний опис інтерфейсу, що містить одночасно структуру полів, правила валідації та зв'язки між даними, але не змушує писати імперативний код перевірки під кожен екран.

## Поява декларативних стандартів: XForms та Mozilla XUL

У 2003 році консорціум W3C опублікував специфікацію **XForms 1.0**. Її автори прагнули виправити обмеження HTML-форм шляхом суворого розділення інтерфейсу на три незалежні шари:
1. **Модель даних (Data Model):** XML-структура (`<xforms:instance>`), що описувала схему документа та типи значень.
2. **Логіка та обмеження (Model Item Properties):** декларативні вирази XPath, що визначали обов'язковість полів (`required`), обмеження типів (`constraint`), доступність для редагування (`readonly`) та залежність видимості (`relevant`).
3. **Елементи керування (User Interface):** абстрактні віджети (`<xforms:input>`, `<xforms:select1>`), які прив'язувалися до вузлів XML-моделі через атрибут `ref`.

```xml
<!-- Приклад декларативної моделі у стандарті W3C XForms -->
<xforms:model>
  <xforms:instance>
    <order xmlns="">
      <paymentMethod>card</paymentMethod>
      <cardNumber/>
      <taxId/>
    </order>
  </xforms:instance>
  <xforms:bind nodeset="cardNumber" 
               relevant="../paymentMethod = 'card'" 
               required="true()" 
               type="xsd:string"/>
</xforms:model>
```

XForms стала першою формальною спробою винести правила поведінки інтерфейсу в абстрактні метадані. Проте технологія випередила свій час: браузери відмовилися вбудовувати складний і важкий XML/XPath-рушій, а веб-індустрія на початку 2000-х пішла шляхом легковагого JavaScript та імперативного маніпулювання DOM.

Паралельно у 2000 році проєкт Mozilla представив **XUL (XML User Interface Language)** для побудови інтерфейсу браузера Firefox. XUL дозволяв описувати вікна, панелі, кнопки й меню у форматі XML, поєднуючи їх із каскадними таблицями стилів (CSS) та скриптами XPCOM. Це довело життєздатність концепції: застосунок міг динамічно завантажувати XUL-пакети («скіни» та розширення) з віддаленого сервера або локального архіву й миттєво перебудовувати свій графічний інтерфейс.

## Корпоративна стандартизація: Microsoft XAML та BAML

У 2006 році Microsoft випустила Windows Presentation Foundation (WPF) у складі .NET Framework 3.0, представивши **XAML (Extensible Application Markup Language)**. XAML здійснив революцію в корпоративній розробці, зв'язавши декларативну розмітку з об'єктно-орієнтованою типізацією:

* Кожен XML-тег у XAML відповідав конкретному CLR-класу (наприклад, `<Button>` інстанціював `System.Windows.Controls.Button`).
* Атрибути відповідали властивостям класу через механізм Dependency Properties.
* Потужна система прив'язки даних `{Binding Path=User.Name, Mode=TwoWay}` дозволила реалізувати архітектурний шаблон MVVM (Model-View-ViewModel), де інтерфейс повністю відокремлювався від логіки стану.

Для оптимізації продуктивності XAML транслювався компілятором у двійковий формат **BAML (Binary Application Markup Language)**. Це усувало накладні витрати на текстовий парсинг XML під час запуску програми та дозволяло завантажувати складні візуальні дерева за мікросекунди.

Однак і XAML/WPF, і кросплатформний плагін Microsoft Silverlight (2007) залишалися прив'язаними до монолітного десктопного чи плагінного середовища виконання. Вони вирішували задачу відокремлення дизайну від коду, але не вирішували проблему динамічної доставки інтерфейсів на мобільні пристрої.

## Мобільний глухий кут: «Стіна магазинів застосунків»

Поява смартфонів і запуск Apple App Store (2008) та Google Play (тоді Android Market) кардинально змінили економіку доставки програмного забезпечення.

У веб-розробці інженер міг знайти баг у формі замовлення, виправити рядок коду й викатити нову версію на сервери за 60 секунд. У мобільній екосистемі нативний інтерфейс (iOS UIKit, Android Views) компілювався в двійковий бінарний пакет (`.ipa` або `.apk`).

Це створило фундаментальний розрив:
* **Затримка рецензування (App Review Latency):** кожне оновлення бінарного пакета проходило ручну або напівавтоматичну модерацію від 24 годин до кількох днів.
* **Фрагментація версій клієнтів (Release Fragmentation):** навіть після публікації в магазині значна частина користувачів відкладала оновлення на тижні або місяці. Бекенд-команда була змушена роками підтримувати десятки застарілих версій API.
* **Неможливість екстрених правок:** критичні юридичні вимоги, зміни податкових правил у різних країнах чи збої в платіжних шлюзах не можна було виправити в реальному часі.
* **Блокування A/B-тестування:** тестування нових гіпотез щодо розташування кнопок або структури оформлення замовлення вимагало окремих релізів на кожній мобільній платформі.

Мобільна індустрія спочатку спробувала вирішити це через вбудовані веб-переглядачі (WebView та гібридні фреймворки на зразок Cordova/PhoneGap). Проте у 2010–2014 роках WebView на мобільних телефонах страждали від повільного скролінгу, відсутності 60 FPS, високого споживання пам'яті та неприродного вигляду елементів керування (непопадання в нативні гайдлайни Human Interface Guidelines та Material Design).

## Народження Server-Driven UI (2016–2020)

Провідні технологічні компанії усвідомили: необхідно поєднати **гнучкість веб-доставки метаданих** із **продуктивністю нативних компонентів**.

### 1. Airbnb: Ghost Platform та Epoxy (2016)
Airbnb зіткнулася з необхідністю відображати сотні різних типів карток житла, цінників, фільтрів та банерів залежно від міста, сезону та типу мандрівника. У 2016 році інженери Airbnb створили внутрішню платформу **Ghost Platform**, яка транслювала конфігурацію сторінок із бекенду в нативні структури даних. Для Android було відкрито бібліотеку **Epoxy**, яка дозволяла будувати складні списки `RecyclerView` із декларативних моделей, керованих сервером.

### 2. Uber: Dynamic UI Frameworks
Uber перевів ключові екрани замовлення поїздок та меню Uber Eats на SDUI. Це дозволило локальним командам у різних містах світу додавати специфічні способи оплати (готівка, місцеві цифрові гаманці, чайові) та змінювати послідовність етапів замовлення без модифікації коду застосунку на телефоні.

### 3. Shopify, Spotify та DoorDash
Spotify побудував домашній екран застосунку (Home Tab) повністю на базі Server-Driven компонентів: кожен блок («Нещодавно прослухане», «Рекомендації для вас», «Нові релізи») надходив як типізований JSON-вузол. Додавання нового аудіо-формату (наприклад, подкастів або аудіокниг) відбувалося виключно на бекенді.

DoorDash та Shopify перевели форми реєстрації водіїв та вітрини магазинів на генерацію за схемами JSON Schema, уніфікувавши веб-, iOS- та Android-клієнти під єдиний бекенд-контракт.

## Сучасний етап: Відкриті рушії та декларативні стандарти

У 2020-х роках концепція Metadata-Driven UI вийшла за межі закритих пропрієтарних розробок технологічних гігантів:

* **DivKit:** кросплатформний SDUI-рушій, вихідний код якого було відкрито як Open Source у серпні 2022 року. Фреймворк надає клієнтські бібліотеки для Android, iOS, Web та Flutter, підтримує динамічні змінні, безпечний обчислювач виразів без виклику JavaScript, вбудовану анімацію та рендеринг 120 FPS.
* **Hyperview:** відкритий стандарт гіпермедіа для мобільних пристроїв, що транслює XML-документи безпосередньо в нативні компоненти React Native.
* **IETF JSON Schema (Draft 2020-12):** став де-факто стандартом опису структури та валідації даних, на базі якого інструменти (React JSON Schema Form, Formik, VeeValidate) автоматично будують складні форми введення.
* **JsonLogic:** стандарт безпечного серіалізованого представлення логічних дерев, що дозволяє виконувати умовні переходи та перевірки на клієнті без ризику Remote Code Execution.

Сучасний Server-Driven UI остаточно утвердився як фундаментальний архітектурний шаблон для масштабних клієнт-серверних систем, де швидкість адаптації бізнес-логіки та незмінність призначеного для користувача досвіду мають найвищий пріоритет.
