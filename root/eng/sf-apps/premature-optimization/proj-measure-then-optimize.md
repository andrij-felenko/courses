# ⚙️ Цикл оптимізації за виміром: як знайти справжнє гаряче місце й не заплатити борг дарма

Тут ми проживемо один повний оберт дисциплінованого циклу оптимізації від початку до кінця, на конкретній задачі прошивки, з реальним C і реальним лічильником тактів. Мета — не абстрактно повторити «спершу зміряй», а **показати руками**, як вимір міняє рішення: де інтуїція каже одне, а лічильник — інше; як та сама година праці, вкладена за фактом, дає п'ятикратний виграш, а вкладена наосліп — лише борг складності й нуль пришвидшення, бо згори її підпирає закон Амдала. Наприкінці буде видно, чому «спершу правильно й ясно, тоді за виміром — точково швидко» — не гасло, а найдешевший спосіб отримати швидкий код.

## Задача

Візьмімо задачу, яку в тій чи іншій формі робить майже кожна прошивка з аналоговим входом. Маємо буфер сирих відліків з АЦП (аналого-цифрового перетворювача) — скажімо, `N = 1024` вимірів струму з давача, кожен 12-бітний, спакований у `uint16_t`. Нам треба перегнати ці сирі числа-«кроки» у фізичну величину — міліампери — і водночас порахувати їхнє **середньоквадратичне** значення (RMS), бо саме воно, а не миттєве, каже, скільки насправді тече. Формула на кожен відлік проста й чесна:

```
mA = (raw − offset) · SCALE_NUM / SCALE_DEN
```

`offset` — нуль давача (те, що АЦП показує за нульового струму), а `SCALE_NUM / SCALE_DEN` — калібрувальний коефіцієнт, який перетворює «кроки АЦП» у міліампери. Він **не сталий на етапі компіляції**: його визначають на калібруванні кожного конкретного пристрою й тримають у пам'яті — саме тому це дріб із двох змінних, а не одне готове число, яке компілятор міг би згорнути. Порахувавши міліампери на кожному відліку, підсумуємо квадрати й наприкінці візьмемо корінь із середнього — класичний RMS.

Ця функція — гаряча. Її кличуть на кожному новому блоці даних з АЦП, скажімо, тисячу разів на секунду, і всередині неї цикл на `N` ітерацій. Тобто мільйон із гаком проходів тіла циклу щосекунди. Якщо тіло циклу важке, воно з'їдає бюджет процесора цілком — і саме тут, і тільки тут, оптимізація має сенс. Але **де саме** всередині тіла ховається вага — заздалегідь не очевидно, і в цьому вся сіль.

> 🔧 **Навіщо це.** Ця задача — не навчальна вигадка: перетворення сирих відліків давача у фізичну величину з калібруванням і згладжуванням є в лічильниках енергії, зарядних контролерах, вимірювачах вібрації, керуванні двигуном. Скрізь той самий візерунок — гарячий цикл на буфері, всередині якого арифметика на кожен елемент. І скрізь та сама пастка: рука тягнеться прискорити те, що **виглядає** складним (корінь, множення), тоді як справжня вага сидить у місці, повз яке око ковзає.

## Наївна реалізація: спершу правильно й ясно

Найперше правило дисципліни — **написати найпростіший код, що правильно робить діло**, і не думати про швидкість, поки не доведено, що вона проблема. Ось він, прямо за формулою, без жодних хитрощів:

```c
#include <stdint.h>
#include <stddef.h>
#include <math.h>

// Калібрування конкретного пристрою — визначене на етапі калібрування,
// у пам'яті як змінні. Тому дріб НЕ згортається компілятором у константу.
static int32_t g_offset    = 2048;   // нуль давача, кроки АЦП
static int32_t g_scale_num = 3300;   // чисельник калібрування
static int32_t g_scale_den = 4095;   // знаменник калібрування

// Порахувати RMS струму (в мА) по буферу сирих 12-бітних відліків.
float compute_rms_mA(const uint16_t *raw, size_t n) {
    uint64_t sum_sq = 0;                       // сума квадратів мА
    for (size_t i = 0; i < n; i++) {
        int32_t centered = (int32_t)raw[i] - g_offset;
        int32_t mA = centered * g_scale_num / g_scale_den;   // ← дріб на КОЖЕН відлік
        sum_sq += (uint64_t)((int64_t)mA * mA);
    }
    float mean_sq = (float)sum_sq / (float)n;
    return sqrtf(mean_sq);                      // корінь — ОДИН раз на весь буфер
}
```

Цей код правильний, читається з першого погляду й правиться за секунди. Якщо змінилася формула калібрування — видно рівно один рядок, який чіпати. Це і є той стан, з якого дисципліна дозволяє рухатися далі: **не раніше**, ніж він працює й ясний.

Тепер погляньмо на нього оком, яке звикло «бачити повільне». Що тут найважче? Майже кожен не вагаючись тицьне на `sqrtf` — корінь, ще й із рухомою комою, на мікроконтролері без FPU це ж мають бути десятки, як не сотні тактів! Друге за підозрілістю — множення `mA * mA` у 64-бітну суму. А от ділення `/ g_scale_den` погляд проскакує, бо «ділення як ділення, одна операція». Запам'ятаймо цей рефлекс — і перевірмо його виміром. Забігаючи наперед: інтуїція тут промахнеться, і промахнеться повчально.

## Крок 1 циклу: виміряти, а не вгадати

Щоб не гадати, потрібен чесний спосіб порахувати такти. На процесорах Cortex-M (а це переважна більшість сучасних 32-бітних МК) для цього є вбудований **лічильник тактів** усередині блоку налагодження DWT (*Data Watchpoint and Trace*) — 32-бітний регістр `CYCCNT`, що клацає рівно раз на такт ядра. Його треба один раз увімкнути, а далі він рахує «безкоштовно» — читання регістра не спотворює вимір так, як спотворював би виклик таймерної функції.

Вмикається він трьома рухами, і адреси тут не магія, а фіксована частина карти пам'яті Cortex-M: спершу вмикаємо весь блок трасування бітом `TRCENA` у регістрі `DEMCR` (за адресою `0xE000EDFC`), тоді (на Cortex-M7 — ще й знімаємо блокування записом ключа `0xC5ACCE55` у `LAR`), обнуляємо лічильник і вмикаємо його рахунок бітом `CYCCNTENA` у `DWT->CTRL` (`0xE0001000`); саме значення живе в `DWT->CYCCNT` (`0xE0001004`). Через CMSIS це виглядає так:

```c
#include "stm32f4xx.h"   // або інший CMSIS-заголовок вашого МК

static inline void cyccnt_enable(void) {
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   // увімкнути DWT/ITM
#ifdef DWT_LAR_KEY                                     // Cortex-M7: зняти замок
    DWT->LAR = 0xC5ACCE55;
#endif
    DWT->CYCCNT = 0;                                   // обнулити
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;              // пустити лічильник
}

static inline uint32_t cyccnt(void) { return DWT->CYCCNT; }
```

Тепер обгорнімо гарячу функцію виміром. Один виклик на реальному буфері — це надто мало й потоне в шумі (переривання, розігрів конвеєра), тож проганяємо її багато разів і ділимо; про це «ділимо» ще буде окрема пастка нижче, а поки що ділимо **поза** гарячим циклом, один раз на весь замір, тому воно нічого не спотворює:

```c
#define REPS  200u

void profile_rms(const uint16_t *raw, size_t n) {
    cyccnt_enable();
    volatile float sink = 0;                 // volatile — щоб компілятор не викинув виклик
    uint32_t t0 = cyccnt();
    for (unsigned r = 0; r < REPS; r++)
        sink += compute_rms_mA(raw, n);
    uint32_t dt = cyccnt() - t0;
    printf("naive: %lu cycles/call, %lu cycles/sample\n",
           (unsigned long)(dt / REPS),
           (unsigned long)(dt / REPS / n));
}
```

> 🔧 **Навіщо це.** `volatile` на `sink` — не забаганка, а рятунок від найпоширенішої брехні мікробенчмарку. Без нього компілятор бачить, що результат `compute_rms_mA` нікуди не йде, і має повне право **викинути весь виклик** — ти зміряєш нуль тактів і зрадієш «неймовірному прискоренню» коду, якого вже нема. Правило заліза: у бенчмарку результат мусить кудись **дітися** так, щоб оптимізатор не довів його непотрібність.

Запускаємо на типовому Cortex-M4 без апаратного поділу з одноциклним множенням — і замість того, що підказувала інтуїція, бачимо приблизно таке:

```
naive: ~14650 cycles/call, ~14 cycles/sample
```

Чотирнадцять тактів на відлік. Тепер розкладімо їх — і тут інтуїцію чекає холодний душ. Корінь `sqrtf`, на який усі показували пальцем, кличеться **один раз на весь буфер із 1024 відліків**, тобто його ціна, хай навіть 100 тактів, розмазується на 1024 ітерації — це соті частки такту на відлік, шум. А `mA * mA` — одноциклне множення, ще одне-два такти. Куди ж ідуть решта? У те єдине місце, повз яке ковзало око: у **ділення `/ g_scale_den` на кожному відліку**. На цьому ядрі поділ двох 32-бітних чисел — це апаратна операція змінної тривалості, від 2 до 12 тактів залежно від операндів, і саме вона з'їдає більшу частину тіла циклу. А якби ми взяли ще дешевший МК — Cortex-M0/M0+, де апаратного дільника **немає взагалі** й поділ робиться підпрограмою через повторне віднімання, — ця сама стрічка коштувала б **десятки** тактів, і поділ панував би над усім рештою беззаперечно.

Ось перший урок циклу, вартий усього іншого: **вимір показав вузьке місце там, де інтуїція його не бачила.** Ми готові були вкладати працю в корінь — операцію, яка на загальний час не впливає ніяк, бо виконується рідко. Вимір повернув нас на землю й тицьнув у справжнього винуватця. Це і є та причина, чому крок «зміряй» стоїть **перед** кроком «прискорюй», а не після: без нього ми б з майже певністю оптимізували холодне.

## Крок 2 циклу: прибрати справжнє гаряче місце

Тепер, коли винуватець названий — поділ на кожному відліку, — питання стає вузьким і чесним: як порахувати `centered · SCALE_NUM / SCALE_DEN` **без** поділу в циклі? Прийом класичний і зветься **множення на обернене** (*reciprocal multiplication*): замість того щоб щоразу ділити на `SCALE_DEN`, ми **один раз**, поза циклом, обчислюємо масштабований обернений коефіцієнт, а в циклі лишаємо тільки множення й зсув — а зсув і множення на цьому ядрі коштують по одному такту.

Ідея тримається на простій рівності. Ділення на `d` — це множення на `1/d`; але `1/d` — дріб, а в цілій арифметиці дробів нема. Тож ми **піднімаємо** обернене на `2^Q` (беремо `Q = 32` зсувних розрядів), рахуємо ціле `recip = (SCALE_NUM · 2^Q) / SCALE_DEN` **раз**, поза гарячим циклом, а в циклі множимо на нього й **зсуваємо назад** на `Q` розрядів праворуч — зсув замість поділу:

```
centered · SCALE_NUM / SCALE_DEN  ≈  (centered · recip) >> Q,
     де  recip = (SCALE_NUM · 2^Q) / SCALE_DEN  порахований ОДИН раз.
```

Поділ нікуди не зник насправді — він **утік із циклу назовні**, з мільйона разів на секунду до одного разу на переналаштування калібрування. А всередині циклу лишилося множення (1 такт) і зсув (1 такт) замість поділу (2–12 тактів). Ось код; зверніть увагу, що обчислення `recip` живе окремо, у функції калібрування, і виконується лише коли калібрування змінюють:

```c
#include <stdint.h>
#include <stddef.h>
#include <math.h>

static int32_t g_offset = 2048;
// Готуємо обернене ОДИН раз при зміні калібрування, а не в гарячому циклі.
static int64_t g_recip  = 0;      // (SCALE_NUM << Q) / SCALE_DEN
#define RECIP_Q  32

void set_calibration(int32_t offset, int32_t scale_num, int32_t scale_den) {
    g_offset = offset;
    // Єдиний поділ на весь час життя цього калібрування:
    g_recip  = ((int64_t)scale_num << RECIP_Q) / scale_den;
}

float compute_rms_mA_fast(const uint16_t *raw, size_t n) {
    uint64_t sum_sq = 0;
    for (size_t i = 0; i < n; i++) {
        int32_t centered = (int32_t)raw[i] - g_offset;
        // Замість ділення — множення на обернене й зсув. Обидва по 1 такту.
        int32_t mA = (int32_t)(((int64_t)centered * g_recip) >> RECIP_Q);
        sum_sq += (uint64_t)((int64_t)mA * mA);
    }
    float mean_sq = (float)sum_sq / (float)n;
    return sqrtf(mean_sq);
}
```

Функція робить **те саме** діло — те саме перетворення, той самий RMS, — але поділ у тілі циклу зник. Перш ніж радіти, спинімося на найважливішому кроці, який передчасна оптимізація завжди пропускає, а дисциплінована — ніколи.

## Крок 3 циклу: перевірити, що поведінка не змінилася

Швидкість, куплена ціною **іншого результату**, — не оптимізація, а новий баг у гарному вбранні. Тому перед повторним виміром треба довести, що обидві функції дають те саме на всьому діапазоні входів. Множення на обернене — не точна, а **наближена** рівність: цілочислове `(SCALE_NUM << 32) / SCALE_DEN` відкидає дробову частину, і на окремих відліках останній міліампер може відрізнятися на одиницю через округлення. Тож перевіряємо не «біт у біт», а «в межах допуску, який задача дозволяє»:

```c
#include <assert.h>
#include <stdlib.h>

void verify_equivalence(void) {
    set_calibration(2048, 3300, 4095);
    uint16_t buf[1024];
    // Прогнати на випадкових і на межових входах (0, макс 12 біт).
    for (int trial = 0; trial < 64; trial++) {
        for (int i = 0; i < 1024; i++)
            buf[i] = (trial == 0) ? 0
                   : (trial == 1) ? 4095
                   : (uint16_t)(rand() & 0x0FFF);
        float a = compute_rms_mA(buf, 1024);       // наївна — еталон
        float b = compute_rms_mA_fast(buf, 1024);  // швидка
        assert(fabsf(a - b) <= 0.5f);              // допуск: пів мА
    }
}
```

Цей крок — не формальність, а частина ремесла. Він ловить дві типові біди наближеного прийому: **округлення** (те, що ми щойно допустили свідомо, обмеживши допуском) і **переповнення** (якби `centered · recip` не вліз у 64 біти — але ми навмисно рахуємо в `int64_t`, тож не переповнюється). Тільки **після** того, як рівність доведено, вимір швидкості взагалі має право щось означати: інакше ми б порівнювали час двох функцій, що роблять **різні** речі, а це порівняння порожнє.

> 🔧 **Навіщо це.** Правило, яке відрізняє інженера від оптимізатора-початківця: **кожна оптимізація супроводжується доказом еквівалентності** — тестом, що старий і новий код дають той самий результат (точно або в заявленому допуску). Без цього доказу «прискорення» — це рулетка: половина виграшів насправді тихо міняють поведінку, і баг спливе за півроку в полі, де його вже вдесятеро дорожче ловити. Швидкий і **неправильний** код гірший за повільний і правильний завжди.

## Крок 4 циклу: виміряти знову й підтвердити виграш

Тепер, коли еквівалентність доведено, повторний вимір нарешті щось значить. Проганяємо `compute_rms_mA_fast` тим самим профайлером — і бачимо:

```
naive: ~14650 cycles/call, ~14 cycles/sample
fast:  ~ 3050 cycles/call, ~ 3 cycles/sample
                                ────────────
прискорення ≈ 4.8×  на гарячому циклі
```

Майже п'ятикратно — і весь виграш прийшов від однієї зміни в одному місці: ми **прибрали поділ із тіла циклу**, лишивши множення й зсув. Жодного розгортання, жодного асемблера, жодної втрати читабельності поза одним поясненим рядком. Це і є замкнений оберт дисциплінованого циклу: **зміряли → знайшли справжнє гаряче місце → змінили лише його → довели, що поведінка та сама → зміряли знову й підтвердили.** Кожен крок спирався на факт, і жодна година не пішла наосліп. Що особливо повчально — виграш прийшов **не туди**, куди спершу тягнулася рука (корінь), а туди, куди показав лічильник (поділ). Без виміру ми б вилизали корінь, лишили поділ і не зрушили загальний час ані на такт.

## Складність: що каже O(...) і де воно сліпе

Тепер порахуймо складність — і одразу побачимо, чому одна лише нотація O(...) тут **недостатня**, хоч і потрібна. За кількістю операцій обидві функції — наївна й швидка — це **O(n)**: один прохід по буферу, стала робота на елемент, час лінійний за `n`. Нотація O(...) міряє, **як росте** час зі зростанням розміру входу, і за цією міркою наші дві функції **однакові**: подвоїш `n` — обидві сповільняться вдвічі.

```
наївна:  O(n),  ≈ 14 тактів на елемент  (поділ 2–12 т. у тілі циклу)
швидка:  O(n),  ≈  3 такти на елемент   (множення + зсув, поділ винесено)
                       ────────────
той самий ПОРЯДОК O(n),  інша СТАЛА при n
```

Ось де O(...) сліпе: воно **навмисно викидає сталий множник**. Обидві O(n) — але константа при `n` впала майже вп'ятеро, і саме ця константа — те, що відчуває користувач, коли прошивка або встигає обробити потік даних у реальному часі, або захлинається. O(...) відповідає на питання «чи вибухне це на великому вході» (тут — ні, лінійно росте) і **мовчить** про питання «скільки це коштує тут і зараз, на моєму `n`». Тому в гарячому коді прошивки, де `n` часто фіксоване й відоме (розмір буфера АЦП), **вирішальна саме стала**, а не порядок росту — і бачить її лише вимір, не нотація.

Це важлива межа двох різних питань. Якби ми міняли **алгоритм** — наприклад, замість повного перерахунку RMS на кожному блоці тримали **ковзну** суму квадратів, оновлюючи її на кожен новий відлік замість перебору всіх `N`, — ми б рухали саме **порядок** складності (з O(n) на блок до O(1) на відлік), і ось **це** вже перемога, яку не з'їсть жодна константа. Але то була б інша задача — зміна форми розв'язку, а не вилизування тіла циклу. Тут же ми свідомо чіпали **сталу**, і чіпали за виміром: різницю між цими двома рівнями оптимізації варто тримати в голові завжди.

## Контр-сценарій: та сама праця, вкладена наосліп

А тепер — найголовніше для теми, ядро всього уроку. Уявімо іншого інженера, що взявся за ту саму функцію, але **без виміру**, за самою інтуїцією «зроблю цикл швидшим». Він бачить простий цикл підсумовування й тягнеться до найвідомішого трюку — **ручного розгортання** (*loop unrolling*): обробляти по чотири відліки за ітерацію, щоб зменшити накладні витрати на лічильник і перевірку межі. Ось що з цього виходить:

```c
// "Оптимізовано" наосліп: ручне розгортання по 4. Поділ у тілі — НЕ ЧІПАЄМО,
// бо око його не помітило. Читати важче, з'явився окремий "хвіст", межу n
// треба обробляти руками — новий шанс на баг саме тут.
float compute_rms_mA_unrolled(const uint16_t *raw, size_t n) {
    uint64_t sum_sq = 0;
    size_t i = 0;
    for (; i + 4 <= n; i += 4) {
        int32_t c0 = (int32_t)raw[i]   - g_offset;
        int32_t c1 = (int32_t)raw[i+1] - g_offset;
        int32_t c2 = (int32_t)raw[i+2] - g_offset;
        int32_t c3 = (int32_t)raw[i+3] - g_offset;
        int32_t m0 = c0 * g_scale_num / g_scale_den;   // ← поділ ЛИШИВСЯ
        int32_t m1 = c1 * g_scale_num / g_scale_den;   // ← і тут
        int32_t m2 = c2 * g_scale_num / g_scale_den;   // ← і тут
        int32_t m3 = c3 * g_scale_num / g_scale_den;   // ← і тут
        sum_sq += (uint64_t)((int64_t)m0*m0) + (uint64_t)((int64_t)m1*m1)
                + (uint64_t)((int64_t)m2*m2) + (uint64_t)((int64_t)m3*m3);
    }
    for (; i < n; i++) {                                // окремий хвіст — новий баг-ризик
        int32_t c = (int32_t)raw[i] - g_offset;
        int32_t m = c * g_scale_num / g_scale_den;
        sum_sq += (uint64_t)((int64_t)m * m);
    }
    float mean_sq = (float)sum_sq / (float)n;
    return sqrtf(mean_sq);
}
```

Праці вкладено **більше**, ніж у правильний варіант: код розрісся вчетверо, з'явився окремий «хвіст» для `n`, не кратного чотирьом (класичне місце помилки на одиницю), читати стало важче, правити — теж. А тепер вимір:

```
naive:    ~14650 cycles/call, ~14 тактів/відлік
unrolled: ~14100 cycles/call, ~14 тактів/відлік   ← майже без різниці
fast:     ~ 3050 cycles/call, ~ 3 такти/відлік
```

Розгортання зрізало жалюгідні відсотки — накладні на лічильник циклу, які й так були дрібними, — і **не торкнулося поділу**, що з'їдав більшість часу. Праці вкладено багато, читабельність програно, «хвіст» додав ризик бага — а пришвидшення практично нема. Це передчасна оптимізація в чистому вигляді: **зусилля не зачеплене за реальність**, бо реальність (де саме час) ніхто не зміряв.

### Чому наосліп не могло вийти: закон Амдала згори

Це не випадковість і не невдача конкретного трюку — це **математична стеля**, і в неї впирається будь-яка оптимізація холодного місця. Її дає [закон Амдала](topic:sf-algorithms/amdahls-law) — прискорення всієї програми обмежене згори тією часткою часу, яку взагалі можна прискорити; хоч зроби ту частку миттєвою, решта лишиться недоторканою. Джин Амдал сформулював це 1967 року для паралельних машин, але важіль універсальний. Кількісно: якщо частина роботи, яку ти прискорюєш, займає частку `p` загального часу, а прискорюєш ти її в `s` разів, то загальне прискорення дорівнює

```
        1
S = ─────────────
    (1 − p) + p/s
```

а в найкращому випадку, зробивши ту частину **миттєвою** (`s → ∞`), ти впираєшся в стелю `S = 1 / (1 − p)`. Уся вага цієї формули — у тому, що `S` обмежене згори часткою `p`, і ніяке зусилля цього не обійде.

Прикладімо її до розгортання. Накладні витрати циклу — інкремент лічильника й перевірка межі — це, скажімо, `p ≈ 0.05` (5%) загального часу тіла; решта 95% — це поділ, множення й підсумовування, яких розгортання не чіпає. Навіть якби розгортання зробило ці 5% **зовсім безкоштовними** (`s → ∞`):

```
       1              1
S = ───────── = ───────── ≈ 1.05  →  щонайбільше 5% швидше.
    1 − 0.05       0.95
```

Стеля — п'ять відсотків, і це **абсолютна межа**, а не «якось так вийшло». Хоч скільки праці вклади в розгортання, більше за ці 5% воно фізично дати не може, бо в решту 95% часу воно не втручається. А тепер прикладімо ту саму формулу до правильного ходу — атаки на поділ. Поділ — це `p ≈ 0.8` (вісімдесят відсотків) часу тіла, і множення на обернене прискорює його разів у `s ≈ 5`:

```
          1                 1            1
S = ──────────────── = ──────────── = ─────── ≈ 2.78×
    (1 − 0.8) + 0.8/5    0.2 + 0.16      0.36
```

(Виміряні ~4.8× помітно вищі за цю грубу прикидку: реальна частка `p` поділу на цьому ядрі була більшою за взяті округло 0.8. Але саме порядок — кілька разів, а не жалюгідні відсотки розгортання — формула передбачила певно.) Ось у чому вся різниця між двома інженерами. Не в тому, хто старанніший — наосліп праці вкладено навіть **більше**. Різниця в тому, що один цілив у частку `p ≈ 0.8`, а другий — у `p ≈ 0.05`, і закон Амдала наперед, ще до єдиного рядка коду, визначив стелю кожного: 2.78× проти 1.05×. Вимір — це і є спосіб дізнатися, яке `p` у якого шматка, **перш ніж** вкладати в нього годину. Без виміру ти вкладаєш працю навмання й з великою ймовірністю потрапляєш у мале `p`, де стеля притиснута до одиниці, — і лишаєшся з боргом складності без пришвидшення.

![Дві однакові «години праці» на терезах закону Амдала. Ліворуч розгортання б'є в холодну частку p≈0.05: стеля прискорення 1.05×, а код-борг (окремий хвіст, гірша читабельність) лишається назавжди. *Однакова година праці на двох різних частках часу. У холодну частку (p≈0.05) закон Амдала притискає стелю до 1.05× — праця майже дарма, а борг складності лишається; у гарячу (p≈0.8) та сама праця має стелю 2.78× і дає реальні ~4.8×. Вимір — єдиний спосіб дізнатися, яке p у шматка, перш ніж у нього вкладатися.*

## Пастки, яких цей цикл навчає стерегтися

Кілька окремих граблів, на які цей приклад натрапляє мимохідь, — кожні варті того, щоб запам'ятати їх з механізмом, а не як список заборон.

**Компілятор часто вже зробив те, за що ти взявся.** Ручне розгортання з попереднього прикладу на сучасному компіляторі з `-O2` — здебільшого марна праця ще й тому, що оптимізатор **сам** розгортає й векторизує прості цикли, розумніше за руки й **без** втрати читабельності вихідного коду. Тобто інженер узяв на себе борг заплутаності заради роботи, яку інструмент зробив би безкоштовно. А от **винесення поділу з циклу** компілятор сам зробити **не може** — бо не знає, що `g_scale_num/g_scale_den` можна замінити множенням на обернене без шкоди для твоєї задачі (він не знає твого допуску на округлення). Ось чіткий орієнтир: те, що компілятор і так владнає (розгортання, вибір інструкцій), чіпати руками майже завжди шкода; те, що вимагає **знання задачі** (допустиме наближення, винесення інваріанта, зміна алгоритму), — робота людини.

**Ділити в бенчмарку теж треба поза гарячим циклом.** Тонка іронія: сам профайлер вище ділив `dt / REPS / n`, щоб дістати такти на відлік, — і робив це **поза** заміряним циклом, один раз. Якби ми з недбалості ділили всередині гарячого шляху, то виміряли б швидкодію разом із власним поділом-накладними й отримали б брехливе число. Той самий принцип, що й в оптимізації, лише прикладений до інструмента: **інваріантну роботу виноси з гарячого циклу** — і в коді, що міряєш, і в коді, що вимірює.

**Мікробенчмарк бреше трьома способами, якщо не встерегтися.** По-перше, **мертвий код**: без `volatile`-приймача оптимізатор викидає весь виклик (про це вже було). По-друге, **розігрів**: перший прогін платить за промахи кеша інструкцій і холодний конвеєр, тож перший результат завжди завищений — тому й `REPS` прогонів, і дивимося на усталене. По-третє, **несправжні дані**: якщо всі відліки в буфері однакові (наприклад, нулі), передбачувач переходів і кеш працюють у нереально тепличних умовах, і вимір виходить оптимістичнішим за життя — тому в перевірці еквівалентності ми брали й випадкові, і межові входи. Вимір, як і код, вимагає чесності: **міряй на тому, що схоже на бойові дані, у сталому режимі, з результатом, який нікуди не подінеться.**

**Ковзне вікно б'є будь-яку константу — коли задача це дозволяє.** Ми чіпали сталу при O(n), і це дало ~5×. Але якщо ту саму RMS треба рахувати на **кожному новому відліку** з ковзним вікном (а не на окремих блоках), то замість перерахунку всіх `N` квадратів щоразу можна тримати **біжучу** суму квадратів: додав квадрат нового відліку, відняв квадрат того, що випав з вікна, — і це **O(1) на відлік** замість O(n). Ось де ховається справді велика перемога: не у вилизуванні тіла циклу, а в зміні **алгоритму**, коли форма задачі це дозволяє. Але — і в цьому дисципліна — на таку зміну теж ідуть **за виміром**: спершу переконайся, що поточний перерахунок справді не встигає, а тоді міняй форму. Інакше це знову оптимізація за здогадом, лише розумніша на вигляд.

## Що лишається в руках

Пройшовши цей оберт цілком, легко назвати те, що відрізняє дисциплінований цикл від передчасної петлі, — і це не старанність. Обидва інженери працювали; той, що наосліп, навіть **більше**. Різниця в тому, **де стояв вимір**. Дисциплінований почав із простого правильного коду, зміряв лічильником тактів, знайшов справжнє гаряче місце (поділ, а не корінь, усупереч інтуїції), змінив **лише** його, довів, що поведінка та сама, зміряв знову й підтвердив ~5× — і закон Амдала пояснив, чому саме стільки. Передчасний вгадав місце за виглядом, вклав більше праці в холодну частку `p ≈ 0.05`, дістав борг складності (окремий «хвіст», гірша читабельність, ризик бага на межі) і майже нуль пришвидшення, бо стеля Амдала в тій частці — 1.05×.

Звідси — робочий порядок, який варто тримати як звичку, а не як гасло:

```
1. Напиши найпростіший ПРАВИЛЬНИЙ код.        ← ясність спершу
2. Вкладається в бюджет? — СТОП, ти переміг.   ← не чіпай те, що й так встигає
3. Не вкладається — ЗМІРЯЙ (лічильник тактів). ← факт, не здогад
4. Знайди СПРАВЖНЄ гаряче місце (велике p).    ← де час, а не де "виглядає складно"
5. Зміни ЛИШЕ його; лиши коментар ЧОМУ.        ← точковий борг під доведену потребу
6. Доведи, що поведінка не змінилася.          ← швидкість без правильності — баг
7. ЗМІРЯЙ знову — підтверди виграш.             ← замкни цикл фактом
```

Найшвидша прошивка виходить не з того, що в кожен рядок укладено найбільше хитрощів, а з того, що **прості ясні рядки скрізь, окрім кількох виміряних гарячих місць**, де складність узято свідомо й вона окупається. Поділ у тілі циклу коштував нам чотирнадцяти тактів на відлік; вимір показав це чорним по білому, і одна точкова зміна за фактом зрізала його майже вп'ятеро. Та сама праця, вкладена туди, куди тицяла інтуїція, не дала б нічого — і в цьому вся різниця між оптимізацією за виміром і оптимізацією за здогадом.
