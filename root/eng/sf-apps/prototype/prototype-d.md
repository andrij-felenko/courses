# Прототип

<preknowlist>
- [Що таке патерн](root:sf-apps/what-is-pattern) — патерн як іменована форма рішення повторюваної задачі; тут ідеться про один конкретний патерн породжувальної родини.
- [Інтерфейс проти реалізації](root:sf-apps/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні, і тим, ЯК він це робить; `clone()` — обіцянка «зроблю ще один такий, як я», яку кожен клас виконує по-своєму.
- [Незмінність як прийом дизайну](root:sf-apps/immutability) — чому об'єкт, який після створення не змінюють, безпечніший; від цього прямо залежить, чи можна робити копію «поверхневою».
</preknowlist>

Уяви, що тобі потрібен новий об'єкт — але не «якийсь», а точно такий самий, як той, що вже стоїть перед тобою. У грі ти щойно налаштував ворога: модель, зброю, набір реакцій, десяток дрібних параметрів — і тепер треба вивести на карту сотню таких самих. У графічному редакторі користувач намалював фігуру й тягне з палітри ще одну — ідентичну. У тесті ти зібрав «правильне замовлення» з дюжиною полів і хочеш дати кожному тесту власну копію, щоб трохи її підправити. Питання щоразу те саме: **як зробити ще один такий?**

Найпряміший шлях — знову покликати конструктор і перелічити всі поля наново. Але він раз по раз упирається в стіну. Іноді це просто **дорого**: об'єкт коштував запиту в базу, розбору файлу чи довгого обчислення, і повторювати всю цю роботу лише заради копії — марнотратство. А іноді це **неможливо**: у тій точці коду, де треба «ще один такий», ти часто **не знаєш конкретного класу** — тримаєш у руках якийсь `Shape`, а який саме, `Circle` чи `Square`, з'ясується аж під час виконання. І тут визріває чесна думка: навіщо будувати з нуля, коли готовий зразок уже є перед очима? **Просто скопіюй його.**

Оце і є патерн прототип (гр. *prōtótypon*, від *prôtos* — перший + *týpos* — відбиток, зразок): нові об'єкти народжуються **копіюванням наявного зразка**, а не викликом конструктора. Об'єкт носить у собі метод — назвімо його `clone()` (гр. *klōn* — живець, пагін, що дає нову рослину, тотожну материнській) — який каже: «зроби ще один такий, як я».

![Ліворуч шлях конструктора: виклик new Shape з довгим переліком усіх полів веде до нового об'єкта, підпис «будуєш з нуля щоразу». Праворуч шлях прототипа: наявний налаштований об'єкт-зразок із кнопкою clone, стрілка від нього до нового незалежного об'єкта, підпис «кажеш: ще один такий самий»](img/create-by-example.svg)

*Два способи народити об'єкт. Конструктор вимагає знати клас і перелічити всі інгредієнти; прототип має лише готовий екземпляр, який сам себе відтворює. Знання «як зробити ще один такий» переїхало з місця виклику всередину об'єкта.*

## Одна заміна, з якої все випливає

Механічно патерн — це одна проста підстановка. Там, де стояло `new ConcreteThing(...)`, тепер стоїть `existing.clone()`. Різниця тонша, ніж видно на око. Конструктор — це **рецепт**: щоб ним скористатися, треба знати клас і всі складники. Клонування — це **відбиток**: усе, що тобі потрібно, — готовий екземпляр, а він уже вміє себе скопіювати. Відповідальність «як зробити ще один такий» пішла з місця виклику й оселилася **всередині самого об'єкта**.

Щоб клонування працювало поліморфно — тобто щоб різні класи вміли клонуватися кожен по-своєму, а клієнт цього не помічав, — `clone()` роблять частиною спільного інтерфейсу:

:::tabs
```ts
interface Shape {
  clone(): Shape;               // «зроблю ще один такий, як я»
  render(): void;
}

class Circle implements Shape {
  constructor(public x: number, public y: number, public r: number) {}
  clone(): Shape {              // повертає новий Circle — того самого класу
    return new Circle(this.x, this.y, this.r);
  }
  render() { /* намалювати коло */ }
}
```
```py
import copy

class Circle:
    def __init__(self, x, y, r):
        self.x, self.y, self.r = x, y, r
    def clone(self):
        return copy.copy(self)   # копія того самого класу
    def render(self):
        ...                      # намалювати коло
```
:::

Тепер найважливіше, заради чого патерн і придумали. Маючи в руках `Shape` невідомого підтипу, ти можеш зробити його копію, **не питаючи, що це за клас**:

:::tabs
```ts
function duplicate(s: Shape): Shape {
  return s.clone();   // Circle дасть Circle, Square дасть Square — без жодного if
}
```
```py
def duplicate(s):
    return s.clone()   # Circle дасть Circle, Square дасть Square — без жодного if
```
:::

Придивися, що тут сталося. `duplicate` — це фактично **конструктор, який працює крізь інтерфейс**: він створює новий об'єкт правильного класу, хоча цей клас у коді ніде не названо. Об'єктні мови не дають викликати конструктор поліморфно — не можна написати «створи ще один такого типу, як цей». А `clone()` саме це й дає. Тому прийом ще звуть «віртуальним конструктором»: конструктор, який можна покликати через базовий тип, а спрацює потрібний.

## Два виграші, заради яких це варте заходу

З цієї заміни випливають дві цілком різні вигоди, і бачити їх треба нарізно, бо застосовують прототип то заради однієї, то заради іншої.

**Перший виграш — копія дешевша за побудову.** Коли створення об'єкта коштує по-справжньому — зчитати конфігурацію з диска, розібрати важкий шаблон, порахувати щось довге, — а тобі потрібні численні майже однакові примірники, кожен новий `new` повторює всю цю дорогу роботу дарма. Клонування вже зібраного зразка її **пропускає**: тяжка частина відбулася раз, під час народження прототипа, а далі ти лише копіюєш готовий результат. Тут прототип стоїть поруч із [пулом об'єктів](root:sf-apps/object-pool), який теж бореться з дорогим створенням, але інакше: пул **повертає в обіг ті самі об'єкти**, а прототип **штампує нові копії**. Потрібні свіжі незалежні примірники — прототип; потрібно позичити й повернути — пул.

**Другий виграш — створення без знання класу.** Це той самий поліморфний `clone()`, але його цінність видно, коли на нього спираються ширше. [Фабричний метод](root:sf-apps/factory-method) розв'язує ту саму задачу «створити, не називаючи конкретний клас» — але ціною **паралельної ієрархії творців**: на кожен продукт напрошується свій клас-фабрика. Прототип обходиться без цієї ієрархії зовсім. Замість «написати ще один клас-творець» ти просто **тримаєш ще один налаштований екземпляр** і клонуєш його. Класи-творці замінено на прості об'єкти-зразки — а їх можна додавати й міняти навіть під час роботи програми, чого з класами не зробиш.

## Уся сіль — у глибині копії

Тепер до місця, де прототип живе або вмирає. Скопіювати об'єкт — звучить просто, поки всі його поля прості: числа, булеві прапорці, незмінні рядки. Але щойно об'єкт **тримає посилання** на інший, змінний об'єкт — список, вкладену структуру, — постає розвилка, і обрати не ту гілку означає посадити підступну помилку.

**Поверхнева копія (англ. *shallow copy*)** копіює сам об'єкт, але його посилання лишає як є — тож копія й оригінал вказують на **той самий** вкладений об'єкт. **Глибока копія (англ. *deep copy*)** проходить углиб рекурсивно й копіює вкладені об'єкти теж, тож копія виходить **повністю незалежною**. Різниця невидима, доки ніхто нічого не чіпає, — і вибухає, щойно хтось змінює вкладене:

:::tabs
```py
import copy
a = {"tags": ["терміново"]}
b = copy.copy(a)             # ПОВЕРХНЕВА копія
b["tags"].append("важливо")  # чіпаємо список копії...
print(a["tags"])             # ['терміново', 'важливо'] — оригінал ТЕЖ змінився!
```
```js
const a = { tags: ["терміново"] };
const b = { ...a };          // ПОВЕРХНЕВА копія (spread)
b.tags.push("важливо");      // чіпаємо масив копії...
console.log(a.tags);         // ['терміново', 'важливо'] — оригінал теж змінився!
```
:::

Копія й оригінал ділять один список, тож правка «копії» тихо псує оригінал. Ти маєш два об'єкти, які поводяться як один, і баг випливе далеко від місця копіювання. Глибока копія цю пастку знімає:

:::tabs
```py
b = copy.deepcopy(a)         # ГЛИБОКА копія — власний список
b["tags"].append("важливо")
print(a["tags"])             # ['терміново'] — оригінал недоторканий
```
```js
const b = structuredClone(a); // ГЛИБОКА копія — власний масив
b.tags.push("важливо");
console.log(a.tags);          // ['терміново'] — оригінал недоторканий
```
:::

![Угорі поверхнева копія: об'єкт-оригінал і об'єкт-копія, обидва стрілками вказують на один спільний список; підпис — правка через будь-кого псує обох. Унизу глибока копія: оригінал вказує на свій список, копія — на власний окремий список; два незалежні списки, підпис — клон повністю самостійний](img/shallow-vs-deep.svg)

*Поверхнева копія ділить із оригіналом вкладені об'єкти — зміна через одного видно й іншому, це і є прихований баг. Глибока копія відтворює вкладене окремо, тож клон стає повністю незалежним. Правильна глибина копії — головне рішення в кожному `clone()`.*

Тут проступає зв'язок із [незмінністю](root:sf-apps/immutability), і він рятівний. Якщо вкладені об'єкти **незмінні** — їх ніхто ніколи не змінить, — то ділити їх **цілком безпечно**: поверхнева копія стає й правильною, і дешевою водночас. Небезпечна не сама по собі спільність, а спільність **змінного** стану. Тому незмінні об'єкти й прототип так добре сходяться: копіювання зводиться до дешевого поверхневого, бо псувати нічого. Повний розбір, що саме копіювати вглиб, як бути з циклічними посиланнями й скільки коштують різні стратегії, — тема [глибокої й поверхневої копії](root:sf-lang/deep-shallow-copy); тут досить твердо знати одне: **у кожному `clone()` глибину копії обирають свідомо**, а мовчазний поверхневий дефолт — найчастіше джерело помилки.

## Реєстр прототипів: другий виграш у повний зріст

Тепер зберемо другий виграш у закінчену конструкцію, яка й робить прототип по-справжньому корисним. Тримай **реєстр** (або менеджер) прототипів — відображення «ключ → налаштований зразок». Щоб створити об'єкт, ти не викликаєш конструктор, а **береш зразок за ключем і клонуєш його**:

:::tabs
```ts
class ShapeRegistry {
  private prototypes = new Map<string, Shape>();

  register(key: string, proto: Shape) {   // покласти зразок під ключем
    this.prototypes.set(key, proto);
  }
  create(key: string): Shape {
    const proto = this.prototypes.get(key);
    if (!proto) throw new Error(`немає прототипу: ${key}`);
    return proto.clone();                  // новий об'єкт — копія зразка
  }
}

const registry = new ShapeRegistry();
registry.register("коло", new Circle(0, 0, 10));   // зразок налаштовано раз
const c = registry.create("коло");                 // далі — лише копії
```
```py
class ShapeRegistry:
    def __init__(self):
        self._prototypes = {}

    def register(self, key, proto):        # покласти зразок під ключем
        self._prototypes[key] = proto
    def create(self, key):
        return self._prototypes[key].clone()   # новий об'єкт — копія зразка

registry = ShapeRegistry()
registry.register("коло", Circle(0, 0, 10))    # зразок налаштовано раз
c = registry.create("коло")                    # далі — лише копії
```
:::

Помітив, що тут зникло? Жодного `if` чи `switch` за типом. Щоб додати новий різновид фігури, ти не чіпаєш ані `create`, ані реєстр — просто **реєструєш ще один екземпляр**. Нова поведінка додається новим *об'єктом* збоку, а наявний код лишається недоторканим — це прямий вияв [принципу відкритості-закритості](root:sf-apps/open-closed), тільки досягнутий **даними, а не класами**. І оскільки зразок — це звичайний об'єкт, реєстрація може відбуватися під час виконання: користувач намалював свою фігуру — і вона одразу в палітрі, без жодного нового класу.

![Реєстр як таблиця: ключ «коло» веде до налаштованого зразка-кола, ключ «квадрат» — до зразка-квадрата, ключ «орк» — до налаштованого орка. Виклик create зі словом «орк» знаходить зразок, кличе clone і віддає новий незалежний об'єкт-орк збоку. Унизу підпис: додати новий вид — зареєструвати ще один екземпляр, не писати клас](img/prototype-registry.svg)

*Реєстр відображає ключі на готові зразки; створення — це пошук зразка й його клонування. Новий різновид додається реєстрацією ще одного екземпляра, а не новим класом і не правкою наявного коду — відкритість до розширення, здобута даними.*

> 🔧 **Навіщо це.** Найчастіше прототип тихо працює там, де його навіть не називають на ім'я. Тестові фікстури: тримаєш один зразок «валідного замовлення» й клонуєш-підправляєш його під кожен тест — не переписуючи дюжину полів щоразу. Ігри й симуляції: один налаштований шаблон сутності, з якого штампуються тисячі копій на сцені. Знімки стану: клонуєш поточний об'єкт, щоб зберегти його для скасування дії чи відкату. Шаблони документів і конфігурацій: заздалегідь зібраний «типовий» об'єкт, від якого відштовхуються всі похідні. Наскрізна нитка одна — коли потрібно **багато майже однакових об'єктів** або варіації від **відомого-доброго зразка**, а будувати кожен з нуля дорого чи незручно.

## Те саме слово, дві різні речі

З цим патерном пов'язана плутанина, яку варто розв'язати одразу, бо вона всюди. Слово «прототип» у програмуванні означає **дві різні речі**, і сплутати їх легко.

Є мови, де копіювання об'єктів — це **сам спосіб їхнього устрою**. У JavaScript кожен об'єкт має посилання на інший об'єкт — свій прототип, — і, не знайшовши властивості в себе, шукає її там. Це не патерн, а вбудована модель: `Object.create(proto)` робить об'єкт, що спирається на `proto`. Родовід цієї ідеї веде до мови Self (Девід Унгар і Рендел Сміт, конференція OOPSLA, 1987) — вона свідомо викинула класи й лишила самі об'єкти, що клонуються й делегують поведінку одне одному; звідти прототипність і перейшла в JavaScript, який Брендан Айк зібрав 1995 року. Але, і це ключове, **прототипне наслідування — це делегування, а не копіювання**: об'єкт тримає **живе посилання** на прототип і зазирає в нього по відсутнє, тимчасом як патерн прототип **копіює стан** у самостійний об'єкт, після чого зв'язку між ними немає. Однакове слово, протилежна механіка.

А в класових мовах прототип — це саме той явний метод `clone()`. У C++ це усталена ідіома «віртуального конструктора»: віртуальний `clone()`, що всередині кличе конструктор копії. У Java спроба стандартизувати це через інтерфейс `Cloneable` вийшла настільки невдалою, що сам Джошуа Блох, автор багатьох бібліотек мови, назвав її «глибоко зламаною» й радить натомість звичайний конструктор копії. Як народилися обидві лінії — і чому «прототипна» гілка мов пішла зовсім іншим шляхом, ніж GoF-патерн, — розібрано в [нотатці з історії](root:sf-apps/prototype/hist-prototype-lineage.md). Робочий реєстр із коректною глибокою копією, ідіому віртуального `clone()` у C++ та типові пастки клонування зібрано в [окремому прикладі з кодом](root:sf-apps/prototype/proj-prototype-registry.md).

## Коли прототип — зайвий

Патерн спокусливий своєю елегантністю, тож чесно назвемо, коли він лише шкодить.

Якщо створення **дешеве, а клас відомий** — просто клич конструктор. `clone()` тут не дає нічого, крім накладних витрат і пастки: кожне нове поле об'єкта треба **не забути** додати в `clone()`, інакше отримаєш напівскопійований об'єкт із тихо загубленими даними — той самий підступний баг, що й ручне копіювання. Метод клонування — це постійний обов'язок тримати його в синхроні з полями класу, і цей обов'язок легко порушити.

Якщо об'єкти **незмінні й дешеві** — тобі, найпевніше, взагалі не потрібні копії: незмінне можна безпечно **ділити**, не копіюючи. Робити багато однакових копій незмінного об'єкта — марнування пам'яті там, де досить одного спільного; саме таку спільність налагоджує [легковаговик](root:sf-apps/flyweight), протилежний за духом до прототипа. Прототип же виправданий рівно тоді, коли справджується хоч одне з трьох: створення **дороге**; конкретний тип у точці створення **невідомий**; потрібні численні **варіації від відомого зразка**.

І остання, тонка засторога. Копія — це новий об'єкт із тим самим **значенням**, але власною **тотожністю**: два клони рівні за вмістом, але це **різні** сутності. Для об'єкта-значення (кольору, координати) це байдуже, а от клонувати [сутність із власною ідентичністю](root:sf-apps/entity-value-object) — скажімо, конкретне замовлення з його номером — часто концептуально неправильно: копія несе той самий номер, наче це те саме замовлення, хоча воно вже інше. Перш ніж штампувати клони, спитай не «чи можу я скопіювати», а «**чи має сенс** ще один об'єкт із таким самим значенням».

Підсумок простий і чесний. Конструктор каже: «ось інгредієнти — збери один». Прототип каже: «ось готовий, зроби ще такий». Уся тонкість патерна — не в самому копіюванні, а в тому, що означає «такий»: наскільки глибоко копія відділяється від зразка. Обереш глибину правильно — дістанеш дешевий, гнучкий спосіб народжувати об'єкти; обереш недбало — двох, що потай лишилися одним.
