# 🧮 Математична модель невизначеності годинника та доведення лінеаризовності

Математичний апарат обмеженої невизначеності часу замінює точкові скалярні мітки відрізками на числовій прямій та визначає строгі умови, за яких порядок таких відрізків гарантує лінеаризовність розподілених транзакцій.

Розподілена система складається з множини незалежних вузлів `N = {1, 2, ..., n}`, кожен з яких функціонує в умовах релятивістської ізоляції: жоден вузол не має прямого доступу до миттєвого стану годинників інших вузлів без затримки передачі сигналу мережею.

## 1. Формалізація шкали часу та інваріант невизначеності

Нехай `t ∈ ℝ` — ідеальний, неперервний і монотонно зростаючий еталонний фізичний час (шкала UTC або TAI), який відраховується від фіксованої початкової епохи.

Кожен розподілений вузол `i ∈ N` володіє власним локальним фізичним годинником, який описується гладкою функцією `C_i(t): ℝ → ℝ`, та динамічною функцією оцінки похибки `ε_i(t) > 0`.

Функція виклику часу на вузлі `i` в абсолютний фізичний момент `t` повертає замкнений часовий інтервал на числовій прямій:

```
I_i(t) = [earliest_i(t), latest_i(t)]
```

де межі інтервалу визначаються через поточні показання локального лічильника та оцінену величину похибки:

```
earliest_i(t) = C_i(t) − ε_i(t)
latest_i(t)   = C_i(t) + ε_i(t)
```

**Фундаментальний інваріант безпеки (TrueTime Invariant):** для будь-якого вузла `i` та для будь-якого абсолютного моменту часу `t` істинне значення фізичного часу гарантовано належить виміряному інтервалу:

```
∀ i ∈ N, ∀ t ∈ ℝ: t ∈ I_i(t)  ⇔  earliest_i(t) ≤ t ≤ latest_i(t)
```

Цей інваріант спирається на апаратне обмеження дрейфу: якщо базова похибка останньої синхронізації дорівнює `ε₀`, максимальний відносний дрейф кварцу становить `ρ` (наприклад, `200 ppm = 2·10⁻⁴`), а час після останньої успішної синхронізації з еталоном дорівнює `Δt`, то поточна похибка монотонно обчислюється як:

```
ε_i(t) = ε₀ + ρ · Δt
```

## 2. Строгий частковий порядок інтервалів часу

Визначимо бінарне відношення строгого часового передування між двома довільними замкненими інтервалами `I_A = [e_A, l_A]` та `I_B = [e_B, l_B]`:

```
I_A ≺ I_B  ⟺  l_A < e_B
```

Інтервал `I_A` строго передує `I_B` тоді й лише тоді, коли їхня права та ліва межі не перетинаються, тобто вся множина точок інтервалу `I_A` лежить лівіше від будь-якої точки інтервалу `I_B` на числовій осі часу.

Якщо `latest(I_A) ≥ earliest(I_B)` і `latest(I_B) ≥ earliest(I_A)`, інтервали називаються **перекритими** (`I_A ∥ I_B`). Для перекритих інтервалів неможливо визначити об'єктивний порядок подій у фізичному часі лише за їхніми локальними вимірюваннями без застосування протоколів узгодження чи додаткового очікування.

## 3. Теорема про гарантію лінеаризовності (зовнішньої узгодженості)

**Умова зовнішньої узгодженості (External Consistency / Linearizability):** якщо транзакція `T₁` завершилася (зафіксована й результат повернено клієнту) у реальний фізичний момент `t_commit(T₁)`, а транзакція `T₂` розпочалася у реальний фізичний момент `t_start(T₂)`, і між ними існує причинний зв'язок у реальному світі:

```
t_commit(T₁) < t_start(T₂)
```

то призначені транзакційні мітки коміту `s₁` та `s₂` мусять строго задовольняти нерівність:

```
s₁ < s₂
```

### Алгоритм призначення міток координатора:
1. Під час фази фіксації транзакції `T₁` координатор опитує локальний годинник у момент `t_prep(T₁)` і обирає мітку коміту `s₁`:
   ```
   s₁ ≥ latest(I(t_prep(T₁)))
   ```
2. **Правило Commit Wait:** координатор затримує повідомлення клієнту про успішний коміт до моменту `t_commit(T₁)`, у який виконується умова:
   ```
   earliest(I(t_commit(T₁))) > s₁
   ```

### Доведення теореми:

Розглянемо ланцюжок нерівностей, спираючись на фундаментальний інваріант TrueTime та правило Commit Wait:

```
s₁ < earliest(I(t_commit(T₁)))      [за правилом Commit Wait]
   ≤ t_commit(T₁)                   [за інваріантом: earliest(I(t)) ≤ t]
   < t_start(T₂)                    [за умовою причинного передування в реальному часі]
   ≤ t_prep(T₂)                     [оскільки підготовка T₂ відбувається після її старту]
   ≤ latest(I(t_prep(T₂)))          [за інваріантом: t ≤ latest(I(t))]
   ≤ s₂                             [за правилом вибору мітки коміту координатором T₂]
```

Згортаючи транзитивний ланцюг нерівностей, одержуємо строгий результат:

```
s₁ < s₂
```

Теорему доведено. Жоден клієнт у розподіленій системі не зможе спостерегти наслідки транзакції `T₂` раніше, ніж наслідки транзакції `T₁`, навіть якщо транзакції виконувалися на протилежних боках планети без прямої мережевої взаємодії між їхніми серверами.

## 4. Виведення мінімальної тривалості Commit Wait

Обчислимо мінімальний час затримки `ΔW`, який координатор транзакції мусить провести у стані очікування, щоб виконати умову `earliest(t_commit) > s₁`.

Нехай у момент виклику `t_prep` поточний локальний лічильник дорівнює `C`, а похибка — `ε`.

```
s₁ = latest(t_prep)
   = C + ε                          [вибір максимальної правої межі інтервалу]
```

У момент часу `t_commit = t_prep + ΔW` локальний лічильник за стабільного ходу збільшиться на `ΔW`:

```
C_new = C + ΔW
```

Нижня межа інтервалу в момент `t_commit` дорівнює:

```
earliest(t_commit) = C_new − ε
                   = C + ΔW − ε     [підстановка нового значення лічильника]
```

Умова спрацьовування бар'єра Commit Wait вимагає:

```
earliest(t_commit) > s₁
C + ΔW − ε > C + ε                  [підстановка значень s₁ та earliest]
ΔW − ε > ε                          [віднімання C з обох частин нерівності]
ΔW > 2·ε                            [додавання ε до обох частин нерівності]
```

Отже, мінімальний час очікування координатора транзакції дорівнює подвоєній максимальній похибці часу:

```
ΔW_min = 2 · ε
```

Якщо `ε = 5 мс`, транзакція запису затримується на `2 · 5 = 10 мс`. При зменшенні похибки до `ε = 20 мкс` (через протокол PTP IEEE 1588) час очікування скорочується до `40 мкс`, що дозволяє здійснювати десятки тисяч лінеаризовних записів за секунду на одному обчислювальному вузлі.

## 5. Безпека читання за знімком (Snapshot Read Safety)

Нехай клієнт ініціює операцію читання без отримання блокувань за міткою часу `t_read`.

Для забезпечення коректного знімка (англ. *Snapshot Isolation*) система повинна гарантувати, що всі транзакції з міткою `s ≤ t_read` уже повністю зафіксовані й збережені у сховищі.

**Критерій безпечного читання:** читання за міткою `t_read` на вузлі `i` дозволено виконувати без блокувань, якщо задовольняється умова:

```
t_read < earliest_i(t_current)
```

### Доведення:
Припустимо від супротивного, що існує активна незафіксована транзакція `T_x`, яка в майбутньому отримає мітку коміту `s_x ≤ t_read`. 

Координатор транзакції `T_x` призначає мітку `s_x ≥ latest_x(t_prep(T_x))`. 
Оскільки транзакція `T_x` ще не завершила фазу вибору мітки в момент `t_current`, маємо `t_prep(T_x) ≥ t_current`.

Тоді:

```
s_x ≥ latest_x(t_prep(T_x))
    ≥ t_prep(T_x)                   [за фундаментальним інваріантом]
    ≥ t_current                     [оскільки фаза вибору мітки ще попереду]
    ≥ earliest_i(t_current)         [за інваріантом для вузла i]
    > t_read                        [за критерієм безпечного читання]
```

Отримуємо строгу суперечність: `s_x > t_read`, що спростовує вихідне припущення `s_x ≤ t_read`.

Отже, жодна майбутня або незафіксована транзакція не зможе отримати мітку `s_x ≤ t_read`. Вузол може негайно видати клієнту всі версії даних із мітками `s ≤ t_read`, не блокуючи таблиці та не узгоджуючи стан із іншими репліками.

## 6. Вплив розбіжності інтервалів на конкурентні транзакції (Abort Rate)

Якщо дві транзакції `T_A` та `T_B` намагаються модифікувати спільний ресурс одночасно, їхні інтервали невизначеності можуть частково перекриватися:

```
I(T_A) ∩ I(T_B) ≠ ∅
```

У цьому випадку транзакційний менеджер використовує традиційний механізм двофазного блокування (2PL) або оптимістичного контролю версій (OCC). Якщо транзакція `T_A` першою захоплює замок і отримує мітку `s_A`, транзакція `T_B` змушена обрати мітку `s_B > s_A`.

Ймовірність конфлікту та необхідності відкату (англ. *transaction abort rate*) при конкурентному доступі прямо пропорційна ширині інтервалу `2·ε`:

```
P_conflict ∝ 2 · ε · λ
```

де `λ` — інтенсивність потоку транзакцій до гарячого ключа бази даних.

Звідси випливає фундаментальний інженерний закон розподілених СУБД: апаратне зменшення невизначеності `ε` не лише скорочує затримку коміту `Commit Wait`, але й експоненційно знижує кількість конфліктів блокувань у високонавантажених шардах.
