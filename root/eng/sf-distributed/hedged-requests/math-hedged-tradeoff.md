# 🧮 Математика геджування: відсікання хвоста розподілу і ціна додаткового навантаження

Математичний апарат геджування запитів описує перетворення важкохвостого розподілу затримок мережевих викликів у компактний розподіл із різко зрізаними перцентилями P99 і P99.9. Нижче наведено точне ймовірнісне виведення функції розподілу часу відповіді для відкладеного геджування, розрахунок коефіцієнта додаткового навантаження на систему та аналіз стійкості черг, що визначає межу між ефективним зрізанням хвоста і метастабільним колапсом кластера.

## Ймовірнісна модель базового виклику

Нехай затримка одного мережевого запиту до окремого вузла є невід'ємною випадковою величиною `X` із неперервною функцією розподілу ймовірностей (англ. *Cumulative Distribution Function*, CDF):

```
F(t) = P(X ≤ t)
```

Функція `F(t)` задає ймовірність того, що сервер надішле повну відповідь за час, не більший за `t`.

Відповідно, функція дожиття (англ. *Survival Function* або *Tail Distribution*) описує ймовірність того, що запит забариться довше за час `t`:

```
S(t) = P(X > t) = 1 − F(t)
```

У розподілених сервісах функція `S(t)` рідко підпорядковується симетричному нормальному розподілу. Через наявність збирача сміття, дискових черг та мережевих колізій хвіст затримок має важкий або логнормальний характер: доки 90% запитів укладаються в короткий проміжок (наприклад, 10 мс), решта 10% розтягуються на сотні мілісекунд або секунди.

## Математична модель відкладеного геджування

Розглянемо клієнт, що застосовує стратегію відкладеного геджування з параметром затримки `t_h` (англ. *hedging delay*):

1. У момент часу `t = 0` клієнт надсилає запит на першу репліку. Її випадковий час відповіді позначимо як `X₁`.
2. Якщо до моменту `t = t_h` відповідь не надійшла (`X₁ > t_h`), клієнт у момент `t = t_h` надсилає ідентичний дублюючий запит на другу репліку. Випадковий час виконання другого запиту позначимо як `X₂`.
3. Загальний час очікування клієнта `T_H` визначається моментом надходження найпершої з двох відповідей:

```
T_H = X₁                     [якщо X₁ ≤ t_h]
T_H = min(X₁, t_h + X₂)      [якщо X₁ > t_h]
```

Припустимо, що затримки `X₁` та `X₂` є незалежними однаково розподіленими випадковими величинами зі спільною функцією розподілу `F(t)` і функцією дожиття `S(t)`.

### Виведення функції розподілу геджованого часу F_H(t)

Знайдемо функцію дожиття геджованого часу `S_H(t) = P(T_H > t)` для двох часових інтервалів:

**Випадок 1: Час до запуску геджу (`t ≤ t_h`)**
Якщо час `t` не перевищує порога геджування `t_h`, дублюючий запит ще не відправлявся. Отже, затримка перевищує `t` тоді й лише тоді, коли перший запит триває довше за `t`:

```
S_H(t) = P(X₁ > t) = S(t)     [для t ≤ t_h]
```

**Випадок 2: Час після запуску геджу (`t > t_h`)**
Клієнт усе ще очікує відповіді в момент `t > t_h` тоді й лише тоді, коли одночасно справджуються дві умови:
1. Перший запит триває довше ніж `t` (`X₁ > t`).
2. Другий запит, відправлений у момент `t_h`, за час `t − t_h`, що минув від його старту, ще не встиг завершитися (`X₂ > t − t_h`).

Оскільки величини `X₁` та `X₂` є незалежними, ймовірність їхнього одночасного невиконання дорівнює добутку відповідних функцій дожиття:

```
S_H(t) = P(X₁ > t) · P(X₂ > t − t_h)
= S(t) · S(t − t_h)
= [1 − F(t)] · [1 − F(t − t_h)]     [для t > t_h]
```

Звідси отримуємо повну формулу результуючої функції розподілу `F_H(t) = 1 − S_H(t)`:

```
F_H(t) = F(t)                                    [при t ≤ t_h]
F_H(t) = 1 − [1 − F(t)] · [1 − F(t − t_h)]       [при t > t_h]
```

### Демонстрація ефекту: розрахунок зрізання P99

Нехай базовий сервіс має такі виміряні перцентилі затримки `X`:
* `P50 = 10` мс (`F(10) = 0.50`, `S(10) = 0.50`)
* `P90 = 20` мс (`F(20) = 0.90`, `S(20) = 0.10`)
* `P95 = 25` мс (`F(25) = 0.95`, `S(25) = 0.05`)
* `P99 = 120` мс (`F(120) = 0.99`, `S(120) = 0.01`)
* `P99.9 = 500` мс (`F(500) = 0.999`, `S(500) = 0.001`)

Встановимо затримку геджування на рівні 95-го перцентилю: `t_h = 25` мс.

Обчислимо ймовірність того, що геджований запит триватиме довше ніж `t = 35` мс (тобто `t_h + P50`):

```
S_H(35)
= S(35) · S(35 − 25)           [формула для t > t_h]
= S(35) · S(10)                [підстановка різниці часу]
≤ S(25) · S(10)                [бо S(t) не зростає, S(35) ≤ S(25)]
= 0.05 · 0.50                  [підстановка табличних значень]
= 0.025                        [тобто 2.5%]
```

Обчислимо затримку для `t = 45` мс (тобто `t_h + P90 = 25 + 20`):

```
S_H(45)
= S(45) · S(45 − 25)           [формула для t > t_h]
= S(45) · S(20)                [підстановка різниці часу 45 − 25 = 20]
≤ S(25) · S(20)                [монотонність: S(45) ≤ S(25)]
= 0.05 · 0.10                  [підстановка значень: S(25)=0.05, S(20)=0.10]
= 0.005                        [добуток: 0.5% повільних запитів]
```

Оскільки `S_H(45) = 0.005 < 0.01`, новий 99-й перцентиль затримки `P99_H` гарантовано становить **менше ніж 45 мс**!

Порівняємо результат:
* Базовий `P99`: **120 мс**
* Геджований `P99`: **~38 мс** (скорочення у 3.2 раза)
* Базовий `P99.9`: **500 мс**
* Геджований `P99.9` (для `t = 25 + 25 = 50` мс): `S_H(50) ≤ 0.05 · 0.05 = 0.0025`, тобто `P99.75 ≤ 50` мс (скорочення затримки в 10 разів!).

## Ціна геджування: коефіцієнт додаткового навантаження

Геджування не є безкоштовним: кожен відправлений дублюючий запит споживає мережевий трафік, пам'ять сокетів і процесорний час серверів.

Імовірність запуску другого запиту `P(Hedge)` дорівнює ймовірності того, що перший запит не завершився до моменту `t_h`:

```
P(Hedge) = P(X₁ > t_h) = 1 − F(t_h) = S(t_h)
```

Якщо вхідний потік становить `R` запитів на секунду, то середня швидкість відправки додаткових запитів дорівнює:

```
R_hedge = R · S(t_h)
```

Коефіцієнт відносного збільшення кількості надісланих запитів `ΔL_req`:

```
ΔL_req = S(t_h)
```

Для порога `t_h = P95` маємо `S(t_h) = 0.05`. Тобто кількість викликів у мережі зростає рівно на **5%**.

### Споживання процесорного часу (Work Overhead) з урахуванням скасування

Кількість надісланих запитів не тотожна кількості виконаної процесорами роботи, якщо в системі налаштовано протокол скасування (англ. *cancellation*).

Нехай виконання одного запиту на сервері вимагає постійної роботи процесора тривалістю `C`.
* Якщо запит завершується на репліці 1 до моменту `t_h`, репліка 2 не викликається: спожито `1 · C`.
* Якщо запит триває довше за `t_h`, репліка 2 стартує. Якщо репліка 2 завершується через час `X₂`, а репліка 1 негайно скасовується, то репліка 1 встигла відпрацювати час `t_h + X₂`.

Якщо скасування на сервері є кооперативним і негайно звільняє ресурси, середня витрачена робота на один клієнтський запит `W_hedged` виражається формулою:

```
W_hedged = W_base + S(t_h) · E[min(X₁ − t_h, X₂)]
```

де `E[...]` — математичне сподівання часу паралельного виконання двох спроб до моменту першого завершення.

Оскільки `X₂` зазвичай завершується за медіанний час `P50`, паралельна робота триває дуже короткий інтервал, і реальне збільшення завантаження процесорів становить лише **1.5–3%**.

## Оптимізація вибору порога t_h

Вибір значення `t_h` являє собою класичний інженерний компроміс:
* Занадто малий `t_h` (`t_h < P50`): геджуються понад 50% запитів. Хвіст зрізається максимально агресивно, але кластер отримує понад 50% зайвого навантаження, що призводить до перегріву черг.
* Занадто великий `t_h` (`t_h > P99`): додаткове навантаження прямує до нуля (`< 1%`), але клієнт змушений чекати дуже довго, перш ніж надіслати дубль, тому затримка на рівні P99.9 практично не покращується.

Формалізуємо задачу оптимізації як мінімізацію штрафної функції `J(t_h)`:

```
J(t_h) = P99_H(t_h) + α · ΔL(t_h)
```

де `α` — ваговий коефіцієнт вартості додаткових обчислювальних ресурсів кластера.

Оптимальний поріг `t_h*` визначається з умови рівності нулю першої похідної:

```
d/dt_h [P99_H(t_h)] + α · d/dt_h [S(t_h)] = 0
```

Оскільки щільність імовірності `f(t) = −d/dt [S(t)]` швидко спадає на відрізку між P90 та P98, оптимальна точка мінімуму в переважній більшості розподілів реальних систем потрапляє в інтервал:

```
t_h* ∈ [P90, P96]
```

Саме тому в промислових системах значення `P95` вважається золотим стандартом конфігурації за замовчуванням.

## Стійкість черг і межа фазового переходу (Overload Collapse)

Найнебезпечніша властивість геджування проявляється при переході системи в режим нестачі обчислювальної потужності.

Розглянемо систему масового обслуговування типу `M/M/1` або `M/G/1`, де середній час обслуговування дорівнює `1/μ`, а вхідний потік запитів має інтенсивність `λ`.

Коефіцієнт завантаження системи:

```
ρ = λ / μ
```

За формулою Поллачека — Хінчина середній час перебування запиту в системі `W` (черга + виконання) дорівнює:

```
W = 1/μ + (λ · E[X²]) / (2 · (1 − ρ))
```

Звернімо увагу на знаменник `1 − ρ`: коли завантаження `ρ` наближається до `1.0`, час перебування запиту в черзі стрімко прямує до нескінченності:

```
lim_{ρ → 1} W = ∞
```

### Механізм позитивного зворотного зв'язку

Нехай у нормальному стані кластер працював при `ρ₀ = 0.80`, а поріг геджування був зафіксований на статичному значенні `t_h = 25` мс (що відповідало `P95` при `ρ = 0.80`).

Нехай вхідний потік `λ` зріс на 15% (наприклад, через ранковий пік трафіку):

1. Завантаження зростає: `ρ₁ = 0.80 · 1.15 = 0.92`.
2. Через зростання черги весь розподіл затримок зсувається праворуч. Нова медіана стає 28 мс.
3. Тепер затримку `t > 25 мс` демонструє не 5% запитів, а **60% запитів**: `S_new(25) = 0.60`.
4. Клієнти, орієнтуючись на фіксований `t_h = 25 мс`, починають надсилати гедж-дублі для 60% всього вхідного потоку!
5. Нова інтенсивність надходження запитів на сервери стає:

```
λ_total = λ_in · (1 + S_new(25))      [формула сумарного потоку з геджами]
= 1.15 · λ₀ · (1 + 0.60)              [підстановка сплеску 15% та S_new = 0.60]
= 1.84 · λ₀                           [сумарне множення: зростання трафіку на 84%]
```

6. Нове розрахункове завантаження системи:

```
ρ_total = 0.80 · 1.84 = 1.472 > 1.0
```

Завантаження перевищило одиницю (`ρ > 1.0`). Черги стають нескінченними, час відповіді перевищує таймаути клієнтів, і система миттєво падає в стан повної відмови (метастабільний колапс).

### Умова абсолютної стійкості

Щоб геджування не провокувало колапс за будь-якого зовнішнього навантаження, сумарний потік із урахуванням геджування ніколи не повинен перевищувати пропускну здатність:

```
λ_in · (1 + S(t_h)) < μ
```

Звідси випливає фундаментальна інваріантна вимога до проектування клієнтів: **коефіцієнт геджування `S(t_h)` повинен бути жорстко обмежений згори клієнтським бюджетом токенів (Token Bucket) незалежно від того, як сильно зросла затримка на бекенді:**

```
ΔL_actual = min(S(t_h), B_max)
```

де `B_max` — максимальна дозволена квота дублювання (як правило, `B_max ≤ 0.10`, тобто не більше 10% від вхідного потоку). Цей захист відсікає фазовий перехід і гарантує математичну стійкість кластера за будь-яких умов.
