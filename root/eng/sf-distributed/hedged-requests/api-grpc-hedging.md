# 📋 Конфігурація геджування: контракт gRPC, Envoy та Cassandra

Інтерфейс налаштування геджування запитів визначає контракт між клієнтським рушієм та інфраструктурою маршрутизації: параметри затримки дублювання, максимальну кількість спроб, допустимі коди стану для продовження очікування та обмеження навантаження. Нижче наведено специфікацію конфігураційних схем трьох стандартизованих промислових реалізацій геджування — gRPC Service Config (RFC A6), Envoy Proxy RouteAction HedgePolicy та Apache Cassandra Speculative Retry — з описом полів, типів, інваріантів валідації та обробки кодів помилок.

## 1. Специфікація gRPC Service Config: HedgingPolicy

У специфікації gRPC клієнтське геджування налаштовується декларативно через JSON-структуру **Service Config** (gRFC A6: *Client-side Retries & Hedging*). Політика прив'язується або до всього сервісу, або до окремих RPC-методів.

### JSON-схема об'єкта MethodConfig

```json
{
  "methodConfig": [
    {
      "name": [
        {
          "service": "order.OrderService",
          "method": "GetOrderDetails"
        }
      ],
      "timeout": "0.200s",
      "hedgingPolicy": {
        "maxAttempts": 3,
        "hedgingDelay": "0.025s",
        "nonFatalStatusCodes": [
          "UNAVAILABLE",
          "RESOURCE_EXHAUSTED"
        ]
      }
    }
  ]
}
```

### Таблиця параметрів HedgingPolicy в gRPC

| Поле | Тип | Обов'язкове | За замовчуванням | Опис і семантика |
| :--- | :--- | :--- | :--- | :--- |
| `maxAttempts` | `integer` | Так | `1` (вимкнено) | Максимальна сумарна кількість одночасно виконуваних спроб для одного виклику (включно з первинною спробою). Допустимий діапазон: від `2` до `5`. |
| `hedgingDelay` | `string` (Duration) | Ні | `0s` | Інтервал очікування перед надсиланням наступного гедж-запиту (наприклад, `"0.025s"` або `"25ms"`). Якщо встановлено `"0s"`, усі `maxAttempts` запитів надсилаються **одночасно** в момент `t = 0`. |
| `nonFatalStatusCodes` | `array<string>` | Ні | `[]` (порожньо) | Список кодів gRPC-помилок, які вважаються «нефатальними». Якщо репліка повертає один із цих статусів, клієнт **не повертає помилку користувачу негайно**, а продовжує очікувати на відповіді інших відправлених реплік або надсилає наступний гедж. |

### Інваріанти та правила валідації gRPC

1. **Взаємне виключення `retryPolicy` та `hedgingPolicy`:** Один і той самий метод у `methodConfig` може містити **або** `retryPolicy`, **або** `hedgingPolicy`, але ніколи обидва одночасно. Спроба передати конфігурацію з обома полями призводить до відхилення Service Config із помилкою `INVALID_ARGUMENT`.
2. **Пріоритет загального таймауту (`timeout`):** Поле `timeout` задає абсолютний наскрізний дедлайн. Якщо `timeout = "0.100s"`, а `hedgingDelay = "0.060s"` при `maxAttempts = 3`, то третій гедж-запит (який мав би стартувати на `0.120s`) ніколи не буде надіслано, оскільки о `0.100s` загальний виклик завершиться з кодом `DEADLINE_EXCEEDED`.
3. **Обробка фатальних статусів:** Якщо будь-яка з активних реплік повертає статус, якого немає в масиві `nonFatalStatusCodes` (наприклад, `NOT_FOUND`, `PERMISSION_DENIED`, `INVALID_ARGUMENT`), клієнт вважає це остаточною бізнес-відповіддю, **миттєво скасовує всі інші паралельні геджі** та повертає статус викликачу.
4. **Клієнтський ліміт ретраїв (Throttling Policy):** gRPC вимагає глобального налаштування `retryThrottling` на рівні каналу (`maxTokens = 10`, `tokenRatio = 0.1`). Якщо доступні токени вичерпано, параметр `hedgingDelay` ігнорується, геджі блокуються, і запит виконується строго в один потік.

### Детальний механізм роботи клієнтського каналу gRPC

У клієнтській бібліотеці gRPC обробка геджування інтегрована безпосередньо у внутрішній конвеєр фільтрів каналу (`Channel Pipeline`). Коли клієнт викликає віддалений метод із налаштованою політикою `hedgingPolicy`, рушій gRPC створює структуру координації виклику (`ClientCall`), яка керує життєвим циклом кількох паралельних потоків даних (`Subchannel Streams`):

1. **Взаємодія з балансувальником навантаження (Load Balancer Integration):** Перша спроба передається активному балансувальнику (наприклад, `round_robin` або `pick_first`). Балансувальник обирає здоровий субканал (підключення до конкретного бекенду) зі статусом `READY`. Коли спливає таймер `hedgingDelay`, клієнт запитує у балансувальника **інший незалежний субканал**. Це гарантує, що дублюючий запит ніколи не потрапить на той самий фізичний сервер, який наразі повільно обробляє перший запит.
2. **Стан субканалів і негайний гедж (Fast-Fail Hedging):** Якщо перший субканал переходить у стан `TRANSIENT_FAILURE` або повертає код зі списку `nonFatalStatusCodes` (наприклад, `UNAVAILABLE`), клієнт **не чекає** вичерпання залишку таймера `hedgingDelay`, а негайно надсилає наступний гедж-запит на альтернативний субканал.
3. **Обмеження пам'яті буферів повідомлень:** Доки триває очікування відповіді, клієнтська бібліотека gRPC зобов'язана утримувати в пам'яті копію вихідного повідомлення запиту (`Request Payload Buffer`), оскільки воно може знадобитися для серіалізації в новий потік при запуску другого чи третього геджу. Для великих потокових повідомлень (понад кілька мегабайтів) геджування вимагає контролю ліміту виділеної оперативної пам'яті каналу (`grpc.max_receive_message_length` та `grpc.max_send_message_length`).

## 2. Специфікація Envoy Proxy: RouteAction.HedgePolicy

У сервісній сітці (Service Mesh) на базі Envoy Proxy геджування налаштовується на рівні L7-маршрутизатора в об'єкті `RouteAction` (`envoy.config.route.v3.HedgePolicy`). Це дозволяє застосовувати геджування прозоро для додатків без модифікації коду сервісів.

### Схема конфігурації Envoy (YAML)

```yaml
routes:
  - match:
      prefix: "/catalog.CatalogService/"
    route:
      cluster: catalog_backend_cluster
      timeout: 0.250s
      hedge_policy:
        initial_requests: 1
        additional_request_chance:
          numerator: 10
          denominator: HUNDRED
        hedge_on_per_try_timeout: true
```

### Таблиця параметрів Envoy HedgePolicy

| Поле | Тип | Обов'язкове | За замовчуванням | Опис і функціональне призначення |
| :--- | :--- | :--- | :--- | :--- |
| `initial_requests` | `UInt32Value` | Ні | `1` | Кількість початкових запитів, що надсилаються одночасно при старті операції в момент `t = 0`. Значення `2` вмикає агресивне подвійне надсилання (Dual-Send). |
| `additional_request_chance` | `FractionalPercent` | Ні | `0%` | Ймовірність відправки додаткового спекулятивного запиту для кожного вхідного виклику. Дозволяє протестувати вплив геджування на 5% або 10% випадкової вибірки реального трафіку. |
| `hedge_on_per_try_timeout` | `bool` | Ні | `false` | Якщо прапорець увімкнено (`true`), то при спрацьовуванні локального таймауту спроби (`per_try_timeout`) Envoy не скасовує першу спробу, а **залишає її працювати паралельно** та надсилає новий гедж-запит до наступного хоста в кластері. |

### Поведінка, пули з'єднань і взаємодія з Circuit Breaker в Envoy

Envoy обробляє геджовані запити як повноцінні незалежні апстрім-транзакції, підпорядковуючи їх загальним правилам захисту кластера:

1. **Виділення ресурсів пулу з'єднань (Connection Pool Allocation):** Кожен відправлений гедж-запит займає один слот активного з'єднання в пулі хоста (`upstream_rq_active`). Якщо цільовий апстрім-кластер досягає ліміту захисного вимикача `max_requests` або `max_pending_requests`, Envoy відмовляється відправляти гедж-дубль і фіксує переповнення в лічильнику `upstream_rq_pending_overflow`.
2. **Співіснування з Retry Budget:** Якщо у маршруті одночасно налаштовано `retry_policy` та `hedge_policy`, Envoy використовує спільний ліміт спроб. Спекулятивні виклики витрачають токени зі спільного бюджету ретраїв (`retry_budget.budget_percent`), гарантуючи, що сумарне навантаження на бекенд не перевищить встановлений відсоток від загального трафіку (наприклад, не більше 20% додаткових викликів).
3. **Логування та прапорці доступу (Access Log Flags):** У журналах доступу Envoy завершені гедж-запити позначаються спеціальними прапорцями:
   * Якщо первинний виклик скасовано через швидшу відповідь геджу, Envoy фіксує для першої спроби прапорець скасування `UT` (Upstream Timeout) або локальне скидання стріму, а в метриках кластера збільшує лічильник `envoy_cluster_upstream_rq_hedged_total`.

## 3. Специфікація Apache Cassandra: Speculative Retry

У розподіленій базі даних Apache Cassandra координатор запитів читає дані з набору реплік відповідно до рівня узгодженості (`ConsistencyLevel`). В опціях таблиці CQL опція `speculative_retry` керує надсиланням спекулятивного читання до альтернативних вузлів реплікації.

### Синтаксис CQL для налаштування таблиці

```sql
CREATE TABLE ecommerce.user_profiles (
    user_id uuid PRIMARY KEY,
    email text,
    name text,
    created_at timestamp
) WITH speculative_retry = '99PERCENTILE';
```

### Допустимі значення директиви `speculative_retry`

| Значення в CQL | Тип семантики | Поведінка координатора Cassandra |
| :--- | :--- | :--- |
| `'99PERCENTILE'` | Динамічний перцентиль | Координатор постійно оновлює ковзну гістограму затримок для таблиці. Гедж-запит надсилається, якщо репліка не відповіла за поточний виміряний `P99` затримки (наприклад, 18 мс). |
| `'95PERCENTILE'` | Динамічний перцентиль | Гедж надсилається після досягнення `P95` затримки. Забезпечує більш агресивне зрізання затримок ціною додаткових 5% внутрішнього трафіку між нодами. |
| `'50MS'` (або `Xms`) | Статичний інтервал часу | Гедж надсилається строго через вказану кількість мілісекунд, якщо первинна репліка не повернула байти. |
| `'ALWAYS'` | Агресивне дублювання | Координатор завжди надсилає запит на всі репліки кворуму одночасно в момент `t = 0`. Максимальна продуктивність читання ціною подвійного дискового навантаження. |
| `'NONE'` | Вимкнено | Геджування вимкнено. Координатор чекає відповіді від обраних реплік до вичерпання повного таймауту `read_request_timeout_in_ms` (за замовчуванням 5000 мс). |

### Механізм взаємодії з Dynamic Snitch та Read Repair

Координатор Cassandra використовує компонент **Dynamic Endpoint Snitch** для ранжування вузлів кластера за швидкістю відповіді:
1. **Вибір первинної репліки:** Запит на читання даних (`Data Request`) надсилається до найшвидшої за оцінкою снітча репліки, тоді як запит контрольної суми (`Digest Request`) надсилається до другої репліки.
2. **Спекулятивне читання (Speculative Trigger):** Якщо вузол даних затримується понад поріг `speculative_retry`, координатор надсилає повноцінний `Data Request` до вузла, який раніше отримав лише `Digest Request`, або до третьої репліки.
3. **Усунення розбіжностей (Read Repair):** Якщо спекулятивна репліка повертає новішу версію рядка, координатор асинхронно ініціює фоновий процес відновлення даних (Read Repair) на застарілих репліках, відновлюючи узгодженість без затримки відповіді клієнту.

### Метрики та телеметрія Cassandra для геджування

Для моніторингу ефективності та запобігання перевантаженню вузлів Cassandra експортує через JMX / Prometheus наступні лічильники на рівні таблиці:
* `org.apache.cassandra.metrics.Table.SpeculativeRetries`: сумарна кількість надісланих спекулятивних запитів читання.
* `org.apache.cassandra.metrics.Table.SpeculativeFailedRetries`: кількість випадків, коли спекулятивний запит також завершився помилкою або таймаутом.
* `org.apache.cassandra.metrics.Table.SpeculativeSampleLatency`: поточний ковзний перцентиль затримки, що використовується як тригер для порога `'XPERCENTILE'`.

## 4. Зведена матриця поведінки статусів і помилок

Таблиця визначає точну реакцію клієнтського інтерфейсу на події життєвого циклу геджованого запиту:

| Подія / Код стану | Поведінка первинного виклику | Поведінка гедж-запиту | Дія клієнтського рушія |
| :--- | :--- | :--- | :--- |
| **Успішна відповідь (`200 OK` / `OK`)** | Отримано валідні дані | Виконується / Очікує | Повертає результат викликачу; негайно відправляє сигнал скасування (`CANCEL` / `RST_STREAM`) для геджу. |
| **Нефатальна помилка (`UNAVAILABLE` / `503`)** | Отримано збій мережі або перевантаження | Не стартував | Якщо гедж ще не стартував, клієнт **негайно запускає гедж**, не чекаючи вичерпання `hedgingDelay`. |
| **Фатальна помилка (`NOT_FOUND` / `404`)** | Отримано остаточну бізнес-відповідь | Виконується | Скасовує всі активні геджі; негайно повертає помилку викликачу (подальше очікування не має сенсу). |
| **Сплив таймер `hedgingDelay`** | Виконується на бекенді | Стартує (якщо є токен) | Якщо бюджет токенів позитивний (`tokens >= 1.0`), списує токен і запускає дубль. Якщо ні — чекає далі. |
| **Сплив глобальний дедлайн (`timeout`)** | Виконується | Виконується | Скасовує обидва виклики; повертає статус `DEADLINE_EXCEEDED` (HTTP `504 Gateway Timeout`). |

## Практичні рекомендації щодо діагностики та тюнінгу

При введенні геджування в експлуатацію рекомендовано дотримуватися наступного протоколу перевірки:
1. **Моніторинг співвідношення геджів (Hedge Ratio):** Відношення кількості відправлених геджів до загальної кількості запитів у нормальному стані має строго дорівнювати `1 − Percentile` (наприклад, 5% при P95). Якщо метрика стрибає вище 10%, це свідчить про системну деградацію бекенду або занижений поріг затримки.
2. **Контроль відсотка скасувань (Cancellation Rate):** Частка геджів, які завершилися успішно швидше за первинну спробу, повинна становити понад 70% від усіх запущених геджів. Якщо первинна спроба встигає відповісти швидше за гедж у 90% випадків після запуску дубля, поріг `hedgingDelay` налаштовано занадто агресивно, і система виконує марне подвійне навантаження.
