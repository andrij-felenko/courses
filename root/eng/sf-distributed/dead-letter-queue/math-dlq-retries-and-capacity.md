# 🧮 Математична модель підбору ліміту спроб та оцінки накопичення мертвої черги

У розподілених асинхронних архітектурах інтуїтивний вибір параметрів черги повторів та мертвої черги (DLQ) неминуче створює системні дисбаланси. Занижений ліміт спроб призводить до того, що тимчасові мережеві коливання викидають валідні замовлення в карантин, штучно занижуючи бізнес-показники доступності. Завищений ліміт спроб змушує систему витрачати обчислювальні ресурси на багаторазове виконання безнадійних отруйних повідомлень, роздуваючи затримку обробки (*tail latency*) та ризикуючи переповнити сховище брокера.

Нижче наведено строгий математичний апарат для розрахунку ймовірностей помилкової ізоляції, оптимізації вартості повторних спроб, моделювання накопичення беклогу під час аварій та обчислення безпечної швидкості відновлення за теорією масового обслуговування.

## 1. Ймовірність помилкового потрапляння в DLQ (False Quarantine Rate)

Нехай вхідний потік повідомлень надходить за пуассонівським процесом з інтенсивністю `λ` (повідомлень на секунду).

Усі помилки обробки поділяються на дві неперетинні підмножини:
1. **Детерміновані отруйні повідомлення (Poison Messages):** складають частку `α` від загального потоку (`0 ≤ α ≤ 1`). Будь-яка спроба їх обробки гарантовано зазнає невдачі: `P(збій | отруйне) = 1.0`.
2. **Перехідні збої інфраструктури (Transient Failures):** складають частку `1 - α`. Кожна спроба зазнає невдачі з імовірністю `p_t` (де `0 < p_t < 1`). Оскільки між повторними спробами застосовується випадкова затримка з джитером, ймовірності збоїв у послідовних спробах вважаються статистично незалежними.

Нехай системний ліміт спроб дорівнює `N` (одна первинна спроба та `N - 1` повторних спроб). Повідомлення перенаправляється в мертву чергу тоді й лише тоді, коли всі `N` спроб поспіль завершилися винятком.

### Виведення повної ймовірності перенаправлення в DLQ:

```
P(DLQ)
= P(DLQ | отруйне)·P(отруйне) + P(DLQ | перехідне)·P(перехідне)   [формула повної ймовірності]
= 1ⁿ·α + (p_t)ⁿ·(1 - α)                                           [підстановка ймовірностей спроб]
= α + (1 - α)·(p_t)ⁿ                                              [спрощення: 1ⁿ = 1]
```

### Ймовірність помилкової ізоляції (False Positive Quarantine):

Помилковою ізоляцією `P_false` називається подія, коли **коректне** (не отруйне) повідомлення через випадковий збіг `N` перехідних збоїв поспіль потрапляє в мертву чергу:

```
P_false = (p_t)ⁿ
```

Якщо інженерний контракт надійності (SLO) вимагає, щоб частка помилково ізольованих валідних задач не перевищувала заданого малого порогу `ε` (наприклад, `ε = 10⁻⁴` або 0.01%), мінімально необхідна кількість спроб `N_min` виводиться шляхом логарифмування:

```
(p_t)ⁿ ≤ ε
= ln((p_t)ⁿ) ≤ ln(ε)               [логарифмування обох частин]
= n·ln(p_t) ≤ ln(ε)                [властивість степеня логарифма]
= n ≥ ln(ε) ÷ ln(p_t)              [ділення на ln(p_t) < 0 змінює знак нерівності]
```

**Числовий приклад розрахунку:**
Припустимо, що під час пікового навантаження мережі ймовірність таймауту запиту до стороннього банку становить `p_t = 0.15` (15%). Вимоги платформи встановлюють ліміт помилкової ізоляції `ε = 10⁻⁴`.

```
N_min
= ln(10⁻⁴) ÷ ln(0.15)              [підстановка значень]
= (-9.2103) ÷ (-1.8971)            [обчислення значень натуральних логарифмів]
= 4.855                            [результат]
```

Оскільки кількість спроб є цілим числом, округлення вгору дає `N = 5` спроб. Це гарантує, що лише одне з 13 000 валідних замовлень ризикує випадково випасти в DLQ через перехідні таймаути.

## 2. Оптимізація компромісу: вартість процесора проти вартості втрат

Збільшення ліміту спроб `N` зменшує ризик помилкової ізоляції, але збільшує математичне сподівання кількості спроб обробки `E[Attempts]`, що веде до додаткових витрат CPU та затримки.

Сформулюємо цільову функцію сумарних витрат на обробку одного повідомлення:

```
Cost_total(N) = C_cpu · E[Attempts](N) + C_loss · P_false(N)
```

де:
- `C_cpu` — вартість однієї спроби обробки (процесорний час, мережевий трафік, ліцензії).
- `C_loss` — бізнес-вартість ручного розбору та затримки у разі потрапляння повідомлення в DLQ (`C_loss ≫ C_cpu`).

Для перехідного повідомлення ймовірність того, що воно успішно завершиться рівно на спробі `k` (де `1 ≤ k ≤ N`):

```
P(успіх на кроці k) = (1 - p_t) · (p_t)ᵏ⁻¹
```

Математичне сподівання кількості виконаних спроб `E[Attempts]` для перехідного повідомлення:

```
E[Attempts](N)
= ∑_{k=1}^{N-1} k·(1 - p_t)·(p_t)ᵏ⁻¹ + N·(p_t)ⁿ⁻¹                 [сума за всіма спробами]
= (1 - (p_t)ⁿ) ÷ (1 - p_t)                                        [згортання скінченної геометричної прогресії]
```

Підставляючи це значення в цільову функцію, отримуємо модель для числової оптимізації `N*`, що мінімізує сумарні витрати інфраструктури.

## 3. Модель накопичення мертвої черги під час системної аварії

Нехай зовнішній залежний сервіс зазнає повної відмови на часовий інтервал тривалістю `T_down` секунд (протягом якого `p_t = 1.0`).

Протягом аварії кожне вхідне повідомлення виконує `N` спроб із середнім сумарним часом затримок `T_backoff_total` перед тим, як потрапити в DLQ.

Динаміка накопичення повідомлень у мертвій черзі `Q_dlq(t)` описується рівнянням:

```
Q_dlq(t) = 0,                                 при t < T_backoff_total
Q_dlq(t) = λ · (t - T_backoff_total),         при T_backoff_total ≤ t ≤ T_down + T_backoff_total
```

Сумарна місткість мертвої черги `C_dlq` (кількість повідомлень), яку брокер повинен гарантовано зберегти без деградації:

```
C_dlq = λ · T_down
```

Необхідний обсяг дискової пам'яті `M_storage` (у байтах) із урахуванням середнього розміру збагаченого діагностичного конверта `S_env` та коефіцієнта запасу `K_safety`:

```
M_storage = λ · T_down · S_env · K_safety
```

**Практичний приклад розрахунку сховища:**
- Вхідний трафік: `λ = 400 msg/s`
- Час усунення великої аварії: `T_down = 7200 s` (2 години)
- Розмір діагностичного конверта зі стеком викликів: `S_env = 3500 байтів`
- Коефіцієнт запасу надійності: `K_safety = 1.6`

```
C_dlq = 400 · 7200 = 2 880 000 повідомлень

M_storage
= 2 880 000 · 3500 · 1.6           [підстановка параметрів]
= 16 128 000 000 байтів            [обчислення]
≈ 15.02 Гігабайтів                 [переведення в Гб]
```

## 4. Безпечна швидкість повторного введення (Safe Redrive Rate)

Коли аварію усунуто, у мертвій черзі накопичилося `Q_total` повідомлень. Повернення беклогу в основну чергу не повинно перевантажити відновлену систему.

Нехай максимальна пропускна здатність системи становить `μ_max` (msg/s), а поточний робочий потік свіжих клієнтських запитів дорівнює `λ_current` (msg/s).

Доступний запас продуктивності (*headroom*):

```
H_available = μ_max - λ_current
```

Максимально допустима швидкість подачі повідомлень із DLQ `R_redrive` з урахуванням коефіцієнта демпфування випадкових сплесків `γ` (`0.2 ≤ γ ≤ 0.4`):

```
R_redrive = H_available · (1 - γ)
```

Час повного відновлення черги `T_recovery`:

```
T_recovery = Q_total ÷ R_redrive
```

## 5. Оцінка затримки в системі масового обслуговування (Модель M/M/1 під час Redrive)

Під час виконання повторного введення беклогу сумарна інтенсивність вхідного потоку, що надходить на вхід обробника, складається зі свіжого трафіку та редрайв-потоку:

```
λ_total = λ_current + R_redrive
```

Якщо час виконання однієї задачі розподілений за експоненційним законом із середнім темпом обслуговування `μ_max`, коефіцієнт завантаження системи `ρ` становить:

```
ρ = λ_total ÷ μ_max
```

Для стабільності системи обов'язково має виконуватися умова Ерланга `ρ < 1.0`.

Середній час очікування повідомлення в черзі `W_q` за класичною формулою теорії черг M/M/1:

```
W_q = ρ ÷ (μ_max · (1 - ρ))
```

Якщо бізнес-вимоги SLO вимагають, щоб середня затримка обробки свіжих замовлень `W_q` під час відновлення не перевищувала критичного порогу `L_max` (наприклад, 80 мілісекунд), граничний коефіцієнт завантаження `ρ_max` виводиться аналітично:

```
W_q ≤ L_max
= ρ ÷ (μ_max · (1 - ρ)) ≤ L_max    [підстановка формули M/M/1]
= ρ ≤ L_max · μ_max · (1 - ρ)      [множення на знаменник]
= ρ · (1 + L_max · μ_max) ≤ L_max · μ_max
= ρ ≤ (L_max · μ_max) ÷ (1 + L_max · μ_max)
```

**Приклад розрахунку ліміту затримки:**
- Продуктивність воркерів: `μ_max = 500 msg/s`
- Поточний трафік: `λ_current = 300 msg/s`
- Допустима затримка в черзі: `L_max = 0.05 s` (50 мс)

```
ρ_max
= (0.05 · 500) ÷ (1 + 0.05 · 500)  [підстановка значень]
= 25 ÷ (1 + 25)                    [обчислення]
= 25 ÷ 26 ≈ 0.9615                 [максимальне завантаження 96.15%]

λ_total_max = 0.9615 · 500 ≈ 480 msg/s
R_redrive_max = 480 - 300 = 180 msg/s
```

Таким чином, математичний розрахунок за моделлю M/M/1 дозволяє вибрати максимальну безпечну швидкість Redrive (180 msg/s), яка гарантує, що середня затримка обробки свіжих клієнтських транзакцій не перевищить 50 мілісекунд навіть під час активного дренажу мертвої черги.
