# 📋 Специфікація діагностичного конверта та інтерфейси управління мертвою чергою

Діагностичний конверт мертвої черги (*Dead Letter Envelope*) визначає строгий інженерний контракт збереження контексту збою в розподіленій системі. Головна мета цього контракту — надати інженерам та автоматизованим службам відновлення повний набір діагностичних даних про причину, місце та час аварії без зміни чи пошкодження первинного бізнес-тіла повідомлення.

Якщо скидати в мертву чергу «голий» вихідний payload, розбір аварій стає неможливим: втрачається назва черги-джерела, стек викликів, кількість виконаних спроб та ідентифікатори розподіленого трасування. 

Нижче наведено вичерпну специфікацію службових заголовків, структуру JSON-схеми, формати конвертів провідних брокерів, інтеграцію зі стандартом CloudEvents, правила санітизації конфіденційних даних, підтримку патерну Claim Check для великих пакетів та REST/CLI-інтерфейси операційного управління DLQ.

## 1. Специфікація стандартизованих заголовків діагностики

Коли клієнтський інтерцептор або диспетчер брокера перенаправляє повідомлення в мертву чергу, він додає до метаданих повідомлення обов'язковий набір діагностичних атрибутів.

| Назва заголовка | Тип даних | Обов'язковість | Опис, призначення та семантичні правила |
| :--- | :--- | :--- | :--- |
| `x-original-queue` | String | Так | Назва первинної черги або топіка, де стався збій (`orders.v1.created`). Дозволяє використовувати єдиний спільний DLQ для кількох джерел. |
| `x-original-exchange` | String | Ні (AMQP) | Назва обмінника, через який продюсер спочатку маршрутизував повідомлення. |
| `x-original-routing-key` | String | Ні (AMQP) | Первинний ключ маршрутизації повідомлення. |
| `x-first-failed-at` | String (ISO-8601) | Так | Часова мітка UTC моменту першої невдалої спроби вичитування (`2026-08-20T14:02:11.104Z`). |
| `x-dead-lettered-at`| String (ISO-8601) | Так | Часова мітка UTC моменту остаточного переміщення в DLQ після вичерпання спроб. |
| `x-retry-count` | Integer | Так | Сумарна кількість виконаних спроб доставки перед ізоляцією (наприклад, `4`). |
| `x-redrive-count` | Integer | Так | Кількість спроб відновлення з DLQ назад в основну чергу (за замовчуванням `0`). Запобігає нескінченному зацикленню. |
| `x-exception-type` | String | Так | Повна канонічна назва класу винятку (`com.shop.validation.SchemaMismatchException` або `DBDeadlockError`). |
| `x-exception-message`| String | Так | Текстовий опис винятку або HTTP-код відповіді зовнішнього сервісу. |
| `x-exception-stacktrace` | String | Ні | Обрізаний текстовий стек викликів (перші 2–4 Кб) для швидкої локалізації рядка коду. |
| `x-failed-by-host` | String | Так | Мережеве ім'я хоста або ID контейнера воркера (`k8s-worker-prod-7b8f-9x2la`). |
| `x-failed-by-service` | String | Так | Назва та версія сервісу-обробника (`billing-processor:v2.4.1`). |
| `traceparent` | String (W3C) | Так | Стандартний контекст розподіленого трейсингу W3C Trace Context (`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`). |
| `x-correlation-id` | String | Так | Наскрізний бізнес-ідентифікатор клієнтського запиту для фільтрації в централізованих логах. |

## 2. Життєвий цикл та семантика діагностичних полів

Кожне поле діагностичного конверта виконує специфічну функцію на різних етапах життєвого циклу інциденту:

- **Часові мітки `x-first-failed-at` та `x-dead-lettered-at`:** різниця між цими двома значеннями визначає загальну тривалість перебування повідомлення в контурі повторних спроб (*retry duration*). Якщо ця тривалість становить 45 секунд для 3 спроб, інженери можуть оцінити коректність налаштування експоненційного уповільнення.
- **Розподіл лічильників `x-retry-count` проти `x-redrive-count`:** лічильник `x-retry-count` фіксує кількість автоматичних спроб у межах одного прогону черги (наприклад, 3 невдачі через таймаут). Лічильник `x-redrive-count` інкрементується оператором або сервісом відновлення під час ручного чи пакетного повторного введення. Якщо повідомлення має `x-redrive-count >= 2`, це вказує на дефект виправлення (хотфікс не вирішив проблему), і таке повідомлення автоматично блокується від подальших автоматичних запусків.
- **Збереження контексту трасування `traceparent`:** за стандартом W3C Trace Context заголовок містить версію, 16-байтний Trace ID, 8-байтний Parent Span ID та прапорці трейсингу. Це дозволяє пов'язати подію в DLQ із конкретним ланцюжком викликів у системах Jaeger, OpenTelemetry або Datadog, показуючи точний HTTP-запит користувача, який породив цю асинхронну задачу.

## 3. JSON-схема діагностичного конверта (DeadLetterEnvelope)

Для брокерів або протоколів, де передача довільних бінарних заголовків обмежена, повідомлення упаковується в структуру уніфікованого JSON-конверта:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "DeadLetterEnvelope",
  "type": "object",
  "required": [
    "envelope_id",
    "dead_lettered_at",
    "original_queue",
    "retry_count",
    "error",
    "payload"
  ],
  "properties": {
    "envelope_id": {
      "type": "string",
      "format": "uuid",
      "description": "Унікальний UUID діагностичного конверта"
    },
    "dead_lettered_at": {
      "type": "string",
      "format": "date-time",
      "description": "Часова мітка ізоляції в DLQ за стандартом ISO-8601 UTC"
    },
    "original_queue": {
      "type": "string",
      "description": "Первинна черга надходження повідомлення"
    },
    "retry_count": {
      "type": "integer",
      "minimum": 1,
      "description": "Кількість невдалих спроб"
    },
    "redrive_count": {
      "type": "integer",
      "default": 0,
      "description": "Кількість виконаних спроб повторного відновлення"
    },
    "trace_context": {
      "type": "object",
      "properties": {
        "trace_id": { "type": "string" },
        "span_id": { "type": "string" },
        "correlation_id": { "type": "string" }
      }
    },
    "error": {
      "type": "object",
      "required": ["type", "message"],
      "properties": {
        "type": { "type": "string" },
        "message": { "type": "string" },
        "stack_trace": { "type": "string" },
        "worker_host": { "type": "string" },
        "service_version": { "type": "string" }
      }
    },
    "payload": {
      "type": ["object", "string", "null"],
      "description": "Оригінальне тіло повідомлення у незмінному вигляді"
    }
  }
}
```

## 4. Інтеграція зі стандартом CloudEvents (Error Extensions)

У сучасних хмарних бессерверних архітектурах (Serverless / Event-Driven) діагностичний конверт формується відповідно до специфікації **CloudEvents v1.0.2** із розширеннями для відмов:

```json
{
  "specversion": "1.0",
  "id": "env-9812-412f-bba3",
  "source": "/services/orders-worker-cluster",
  "type": "com.company.deadletter.event",
  "time": "2026-08-20T14:02:35.892Z",
  "datacontenttype": "application/json",
  "dlqoriginalsource": "/queues/orders-primary",
  "dlqexceptiontype": "com.shop.validation.SchemaMismatchException",
  "dlqretrycount": 4,
  "dlqredrivecount": 0,
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "data": {
    "order_id": "ORD-94102",
    "customer_id": 8104,
    "amount": 450.00
  }
}
```

## 5. Санітизація конфіденційних даних (Security & Data Masking)

Скидання повідомлень у відкритому вигляді створює суттєві загрози безпеці, оскільки доступ до черг DLQ часто мають чергові розробники та аналітики. Формування конверта зобов'язане дотримуватися таких правил:
- **Маскування персональних даних (PII / GDPR):** поля, що містять паролі, номери платіжних карток (PAN/CVV), паспортні дані чи податкові номери, підлягають автоматичному маскуванню регулярними виразами (заміна на `****-****-****-1234`) перед записом у тіло помилки.
- **Очищення змінних оточення в стек-трейсах:** якщо виняток містить роздруківку змінних середовища чи параметрів підключення до бази даних, секретні токени `API_KEY` або `DATABASE_URL` замінюються на `[REDACTED]`.
- **Обмеження розміру стека викликів:** максимальна довжина поля `stack_trace` обмежується 4096 байтами. Якщо повний стек перевищує цей ліміт, зберігаються перші 30 рядків та останній рядок точки викидання помилки, а середина замінюється на позначку `[... truncated 42 frames ...]`.

## 6. Нативні формати провідних брокерів

### 1. RabbitMQ (AMQP Заголовок x-death)
RabbitMQ автоматично створює та оновлює масив асоціативних масивів `x-death` під час проходження повідомлення через Dead Letter Exchange:

```
Заголовок: x-death = [
  {
    "count": 3,
    "reason": "rejected",
    "queue": "orders-primary-queue",
    "time": 1724158940,
    "exchange": "ecommerce.direct",
    "routing-keys": ["orders.create"]
  }
]
```

### 2. Amazon SQS (Redrive Policy та системні атрибути)
Конфігурація черги SQS зв'язується з чергою мертвого сховища через декларативну політику:

```json
{
  "deadLetterTargetArn": "arn:aws:sqs:eu-central-1:123456789012:orders-dlq",
  "maxReceiveCount": "4"
}
```

Під час вичитування з DLQ сервіс AWS SQS надає системні атрибути:
- `ApproximateReceiveCount`: загальна кількість спроб отримання.
- `ApproximateFirstReceiveTimestamp`: часова мітка першого отримання споживачем.
- `SentTimestamp`: часова мітка первинної публікації продюсером.

## 7. Управління великими тілами повідомлень (Claim Check для DLQ)

Коли початкове тіло повідомлення разом із діагностичним конвертом перевищує максимальний ліміт розміру пакетів брокера (наприклад, 256 Кб для AWS SQS або 1 Мб для Apache Kafka), система застосовує патерн квитанції в камері схову (*Claim Check*):

- **Збереження у зовнішньому сховищі:** початковий бінарний або JSON payload записується у хмарне об'єктне сховище (Amazon S3, Ceph, MinIO) за унікальним шляхом: `s3://company-dlq-blobs/2026/08/20/envelope-uuid.bin`.
- **Заміна тіла на посилання:** у полі `payload` діагностичного конверта розміщується посилання на об'єкт, розмір у байтах та контрольна сума SHA-256 для перевірки цілісності.
- **Прозоре відновлення під час Redrive:** контролер відновлення автоматично зчитує вихідний об'єкт зі сховища перед реінжекцією в основну чергу або передає посилання воркерам, унеможливлюючи відмову брокера через переповнення ліміту пам'яті.

## 8. REST API інтерфейси операційного управління DLQ

Платформа управління асинхронними чергами надає набір стандартних HTTP-ендпоінтів для автоматизації та роботи чергової зміни інженерів.

### 1. Перегляд вмісту мертвої черги (Inspection)
- **Запит:** `GET /api/v1/dlq/{queue_name}/messages?limit=20&offset=0&error_type=SchemaMismatch`
- **Коди відповідей:**
  - `200 OK`: повертає масив об'єктів `DeadLetterEnvelope` та загальну кількість записів `total_count`.
  - `404 Not Found`: вказана черга DLQ не існує.

### 2. Запуск процедури безпечного відновлення (Redrive)
- **Запит:** `POST /api/v1/dlq/{queue_name}/redrive`
- **Тіло запиту:**
```json
{
  "target_queue": "orders-primary-queue",
  "batch_size": 1000,
  "rate_limit_per_sec": 50,
  "dry_run": false,
  "filter": {
    "min_failed_at": "2026-08-20T12:00:00Z",
    "max_failed_at": "2026-08-20T14:30:00Z"
  },
  "schema_patch": {
    "set_fields": {
      "currency": "UAH",
      "version": "2.0"
    }
  }
}
```
- **Коди відповідей:**
  - `202 Accepted`: фонова задача відновлення успішно запущена (`{"job_id": "redrive-job-9104", "status": "RUNNING"}`).
  - `400 Bad Request`: помилка у фільтрі або невалідна схема патча.
  - `409 Conflict`: для цієї черги вже виконується інша активна задача Redrive.

### 3. Очищення та скидання в архів (Purge & Archive)
- **Запит:** `POST /api/v1/dlq/{queue_name}/archive`
- **Тіло запиту:**
```json
{
  "archive_target": "s3://company-dlq-cold-archive/orders/2026-08/",
  "purge_after_archive": true,
  "older_than_days": 14
}
```
- **Коди відповідей:**
  - `200 OK`: повертає статус `{"archived_count": 4820, "bytes_written": 19741024}`.

## 9. CLI-інтерфейс утиліти керування (dlq-admin)

Для адміністрування в терміналі розробляється CLI-утиліта `dlq-admin`:

```bash
# Перегляд кількості повідомлень та найстарішого запису
$ dlq-admin inspect --queue orders-dlq --summary

# Експорт перших 10 повідомлень у локальний файл для аналізу
$ dlq-admin export --queue orders-dlq --limit 10 --out ./failed_orders.json

# Запуск безпечного повторного введення зі швидкістю 30 повідомлень/сек
$ dlq-admin redrive --src orders-dlq --dst orders-primary --rate 30 --patch '{"currency":"UAH"}'

# Скидання безнадійних повідомлень у холодний архів S3
$ dlq-admin archive --queue orders-dlq --s3-bucket company-dlq-archive --purge
```
