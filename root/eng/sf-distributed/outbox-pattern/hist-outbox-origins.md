# 📜 Від катастрофи 2PC до ери CDC: як народився патерн Outbox

Наприкінці 1980-х та протягом 1990-х років панівною парадигмою корпоративної інтеграції була ілюзія абсолютної прозорості: розробники прагнули об'єднати реляційні бази даних, черги повідомлень та мейнфрейми в єдиний глобальний транзакційний простір. Стандарт X/Open XA (1991 рік) та протокол двофазної фіксації (*Two-Phase Commit, 2PC*) обіцяли магічне вирішення проблеми узгодженості між різнорідними вузлами. Проте на практиці ця архітектура перетворилася на джерело системних криз і блокувань.

## Ілюзія розподіленої атомарності та глухий кут XA/2PC

У класичній моделі XA сервіс застосунку звертався до зовнішнього координатора транзакцій (*Transaction Manager*, такого як Tuxedo або сервери Java Enterprise Edition із JTA). Координатор пов'язував ресурс реляційної СКБД (наприклад, Oracle або IBM DB2) і ресурс черги повідомлень (IBM MQSeries або JMS) в одну розподілену транзакцію.

Процес складався з двох послідовних фаз:
1. **Фаза голосування (Prepare):** Координатор надсилає всім учасникам команду підготуватися до фіксації. База даних блокує змінені рядки в таблицях на диску і гарантує, що зможе виконати `COMMIT`. Черга повідомлень виділяє місце під пакет і також обіцяє фіксацію. Усі учасники відповідають координатору: `VOTE_COMMIT`.
2. **Фаза виконання (Commit):** Отримавши одностайну згоду, координатор записує рішення у власний локальний журнал і розсилає всім наказ зафіксувати зміни.

```
Клієнт           Координатор           База даних          Черга повідомлень
  |                   |                     |                      |
  |--- Begin Tx ----->|                     |                      |
  |    (UPDATE db,    |                     |                      |
  |     SEND queue)   |                     |                      |
  |                   |                     |                      |
  |--- Commit ------->|                     |                      |
  |                   |--- 1. Prepare ----->|                      |
  |                   |--- 1. Prepare ---------------------------->|
  |                   |<-- VOTE_COMMIT -----|                      |
  |                   |<-- VOTE_COMMIT ----------------------------|
  |                   |                     |                      |
  |                   | [Координатор падає або мережа розривається] |
  |                   |                     |                      |
  |                   |      ???            |          ???         |
  |                   |  (БЛОКУВАННЯ)       |      (БЛОКУВАННЯ)    |
```

Катастрофа 2PC полягає в його **блокуючій природі** (*blocking protocol*). Якщо після успішної фази `Prepare` координатор транзакцій раптово зазнає апаратного збою або втрачає зв'язок із вузлами через розрив мережі, учасники залишаються у підвішеному стані (*in-doubt state*). База даних не має права самостійно відкотити зміни (адже координатор міг встигнути наказати черзі зафіксувати пакет) і не має права самостійно їх зафіксувати (адже координатор міг вирішити відкат).

У результаті табличні блокування на рівні рядків залишалися активними годинами або днями. Будь-які інші користувачі, які намагалися звернутися до заблокованих записів, зависали в черзі очікування. База даних вичерпувала пул з'єднань, і вся корпоративна система зазнавала повного каскадного колапсу (*cascade outage*). Єдиним порятунком було ручне втручання адміністратора бази даних із примусовим розривом блокувань (*heuristic commit/rollback*), що неминуче призводило до втрати або подвоєння фінансових даних.

## Маніфест Пета Гелланда: «Життя за межами розподілених транзакцій»

У 2007 році видатний системний архітектор Пет Гелланд (який працював над архітектурою Tandem NonStop, Microsoft SQL Server та Amazon) опублікував фундаментальну працю під назвою *«Life beyond Distributed Transactions: an Apostate's Opinion»* («Життя за межами розподілених транзакцій: думка віровідступника»).

Гелланд проголосив революційну на той час тезу: у великих масштабованих системах неможливо і шкідливо намагатися забезпечити синхронну узгодженість між незалежними сховищами за допомогою розподілених блокувань. Натомість архітектура повинна спиратися на три фундаментальні принципи:
1. **Ізольовані сутності (Entities):** Кожна бізнес-сутність володіє власним локальним станом і змінює його виключно в межах локальних ACID-транзакцій однієї бази даних.
2. **Асинхронні повідомлення між сутностями:** Взаємодія між різними сутностями та сервісами здійснюється через незмінні повідомлення, які передаються асинхронно.
3. **Кінцева узгодженість та ідемпотентність:** Отримувач повідомлень зобов'язаний бути готовим до дублікатів та порушення порядку доставки, забезпечуючи коректність бізнес-стану через ідемпотентну обробку.

Робота Гелланда остаточно поховала ідею розподілених транзакцій XA для інтернет-масштабу. Проте постало нове гостре інженерне питання: якщо ми змінюємо локальний стан сутності в реляційній базі даних, як гарантувати, що асинхронне повідомлення про цю зміну буде надійно надіслано в транспортну мережу, не порушуючи межі локальної транзакції?

## Кріс Річардсон та каталогізація патернів мікросервісів

На початку 2010-х років індустрія програмного забезпечення масово переходила від монолітних додатків до мікросервісної архітектури (*Microservices Architecture*). Золотим стандартом мікросервісів став принцип *Database-per-Service* (окрема незалежна база даних для кожного сервісу).

Розробники відмовилися від важких серверів застосунків Java EE і перейшли на легковажні брокери повідомлень нового покоління — Apache Kafka, RabbitMQ, AWS SQS. Жоден із цих сучасних брокерів принципово не підтримував протокол XA/2PC заради досягнення колосальної пропускної здатності та горизонтального масштабування.

У 2014–2018 роках Кріс Річардсон (засновник Cloud Foundry та автор книги *«Microservices Patterns»*) формалізував та каталогізував сімейство патернів транзакційного обміну повідомленнями. Саме Річардсон ввів у загальновживаний інженерний лексикон термін **Transactional Outbox** (транзакційна вихідна скринька).

Ідея була напрочуд простою та елегантною: замість спроби одночасно писати у два несумісні мережеві ресурси (базу даних та брокер повідомлень), розробник використовує рідну локальну ACID-транзакцію самої реляційної бази даних. До таблиць бізнес-домену додається допоміжна службова таблиця `outbox`. Зміна стану бізнесу (наприклад, створення замовлення в таблиці `orders`) та запис події про цю зміну в таблицю `outbox` виконуються в межах одного SQL-блоку `BEGIN ... COMMIT`.

Оскільки локальна база даних гарантує атомарність (*Atomicity*) та довговічність (*Durability*), подія записується на диск рівно тоді й тільки тоді, коли зафіксовано бізнес-стан. Далі окремий процес (фоновий опитувач або ретранслятор) зчитує записи з `outbox` і надсилає їх у брокер повідомлень.

## Еволюція ретрансляції: від важкого SQL-опитування до революції CDC

Перше покоління реалізацій патерну Outbox спиралося на метод **періодичного опитування таблиці** (*Polling Publisher*). Фоновий потік виконував запити на кшталт `SELECT * FROM outbox WHERE status = 'PENDING' LIMIT 100 FOR UPDATE` кожні кілька секунд.

Однак у високонавантажених системах підхід з опитуванням швидко вперся в експлуатаційні обмеження:
* **Конфлікти блокувань:** Коли кількість фонових обробників зростала, вони починали конкурувати за одні й ті самі рядки, блокуючи таблицю і спричиняючи взаємні блокування (*deadlocks*). Цю проблему частково пом'якшило впровадження конструкції `FOR UPDATE SKIP LOCKED` у PostgreSQL 9.5 (2016 рік) та MySQL 8.0 (2018 рік).
* **Роздування бази даних (Table Bloat):** Постійні операції `INSERT` та наступні `UPDATE/DELETE` мільйонів повідомлень на добу призводили до колосального навантаження на рушій очищення таблиць (PostgreSQL AutoVacuum), фрагментації дискових сторінок та деградації індексів.
* **Латентність передачі:** Інтервал між фіксацією транзакції та публікацією події був обмежений періодом сну опитувача (зазвичай від 500 мс до кількох секунд).

Відповіддю на ці виклики стала концепція **вилучення змін даних** (*Change Data Capture, CDC*) на основі читання журналів транзакцій (*Transaction Log Tailing*).

Будь-яка промислова СКБД для забезпечення надійності та реплікації записує кожну зміну у послідовний двійковий журнал випереджального запису: **WAL** (*Write-Ahead Log*) у PostgreSQL, **Binlog** у MySQL, **Redo Log** у Oracle. Цей журнал є первинним джерелом правди про всі зафіксовані транзакції.

У 2016 році компанія Red Hat ініціювала відкритий проєкт **Debezium** під керівництвом Гуннара Морлінга (*Gunnar Morling*). Debezium реалізував низькорівневі конектори до журналів транзакцій реляційних баз даних, перетворюючи потік бінарних змін WAL у структуровані події Apache Kafka в режимі реального часу.

У 2019 році команда Debezium представила спеціалізований модуль трансформації **Outbox Event Router** (*Single Message Transform, SMT*). Це остаточно сформувало сучасний вигляд патерну: застосунок просто вставляє рядок у локальну таблицю `outbox`, база даних фіксує його у WAL, а Debezium автоматично вичитує запис із журналу за мілісекунди, маршрутизує його у відповідний топік Kafka і гарантує збереження причинно-наслідкового порядку подій без жодного SQL-навантаження на табличний рушій.

Так інженерна думка пройшла шлях від крихких і блокуючих розподілених транзакцій XA 1990-х років до надійної та масштабованої синергії локальних ACID-транзакцій, журналу WAL та потокової передачі подій CDC.
