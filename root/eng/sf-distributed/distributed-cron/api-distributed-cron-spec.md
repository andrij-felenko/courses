# 📋 Специфікація контракту розподіленого cron: розклад, лізи та політики пропуску

У розподілених системах планування періодичних завдань надійність взаємодії між площиною управління (вузлами планувальника, що обчислюють часові кванти) та площиною даних (виконавчими воркерами, що запускають прикладний код) забезпечується суворим публічним інтерфейсним контрактом. Оскільки планувальник і воркери працюють у різних процесах, на різних фізичних серверах і можуть масштабуватися незалежно, будь-яка невизначеність у форматах або семантиці передачі призводить до дублювання виконання чи мовчазної втрати задач.

Ця специфікація встановлює вичерпні вимоги до синтаксису розкладів, структури опису задач у системному реєстрі, формату конверта повідомлення-тригера, протоколу передачі токенів огорожі, автомата станів виконання та алгоритмічної поведінки при обробці пропущених запусків.

## 1. Синтаксис виразів розкладу (Cron Expression Grammar & Macros)

Планувальник підтримує розширений шестипозиційний формат cron із дискретністю до секунди за шкалою всесвітнього координованого часу (UTC), а також набір стандартних макросів для спрощення конфігурації:

```text
┌───────────── секунди (0 - 59)
│ ┌───────────── хвилини (0 - 59)
│ │ ┌───────────── години (0 - 23)
│ │ │ ┌───────────── день місяця (1 - 31)
│ │ │ │ ┌───────────── місяць (1 - 12 або JAN-DEC)
│ │ │ │ │ ┌───────────── день тижня (0 - 6 або SUN-SAT, 0 = неділя)
│ │ │ │ │ │
* * * * * *
```

### Спеціальні керуючі символи
- Зірочка `*` (будь-яке значення): означає спрацьовування на кожній одиниці виміру відповідного часового поля без обмежень.
- Кома `,` (дискретний перелік): дозволяє вказати фіксований список значень, наприклад `0,15,30,45` у полі секунд або хвилин.
- Дефіс `-` (неперервний діапазон): визначає закритий інтервал включно, наприклад `1-5` у полі дня тижня (з понеділка по п'ятницю).
- Скісна риска `/` (періодичний крок): визначає інтервал повторення, наприклад `*/10` у полі секунд позначає запуск кожні десять секунд починаючи з нульової секунди хвилини.
- Символ `L` (останній день, від англ. *Last*): у полі дня місяця позначає останній календарний день поточного місяця (28, 29, 30 або 31); у полі дня тижня конструкція `5L` інтерпретується як «остання п'ятниця місяця».
- Символ `W` (робочий день, від англ. *Weekday*): знаходить найближчий робочий день (понеділок — п'ятниця) до вказаної дати місяця. Наприклад, якщо `15W` припадає на суботу, тригер спрацює у п'ятницю 14-го; якщо на неділю — у понеділок 16-го.
- Символ решітки `#` (n-й день тижня у місяці): конструкція `5#3` означає третю п'ятницю відповідного місяця.

### Розширені системні макроси розкладу
| Макрос | Еквівалентний вираз cron | Семантика запуску |
| :--- | :--- | :--- |
| `@yearly` або `@annually` | `0 0 0 1 1 *` | Запуск 1 січня о 00:00:00 UTC |
| `@monthly` | `0 0 0 1 * *` | Запуск першого числа кожного місяця о 00:00:00 UTC |
| `@weekly` | `0 0 0 * * 0` | Запуск щонеділі о 00:00:00 UTC |
| `@daily` або `@midnight` | `0 0 0 * * *` | Запуск щоночі о 00:00:00 UTC |
| `@hourly` | `0 0 * * * *` | Запуск на початку кожної астрономічної години |
| `@every <duration>` | N/A (інтервальний таймер) | Фіксований інтервал відліку (наприклад, `@every 30s`, `@every 5m`, `@every 2h`) |
| `@jitter <window>` | N/A (модифікатор розмиття) | Додавання псевдовипадкового часового зміщення до розрахованої точки |

## 2. Схема опису періодичної задачі (Job Definition Schema)

Кожна періодична задача реєструється у розподіленому реєстрі метаданих як незмінний документ із версіонуванням. Реєстр забезпечує атомарність модифікацій та поширює конфігурацію між шардами планувальника.

```json
{
  "job_id": "billing-monthly-settlement",
  "version": 4,
  "partition_key": "tenant-enterprise-eu",
  "schedule": {
    "expression": "0 0 0 1 * *",
    "timezone": "UTC",
    "jitter_seconds": 30
  },
  "misfire_policy": "FIRE_AND_PROCEED",
  "grace_period_ms": 300000,
  "concurrency_policy": "FORBID_CONCURRENT",
  "execution_timeout_ms": 1800000,
  "retry_policy": {
    "max_attempts": 3,
    "initial_backoff_ms": 1000,
    "max_backoff_ms": 30000,
    "backoff_multiplier": 2.0
  },
  "target": {
    "transport": "KAFKA_TOPIC",
    "destination": "cron.triggers.v1",
    "headers": {
      "X-Service-Source": "cron-orchestrator"
    },
    "payload": {
      "action": "RUN_SETTLEMENT",
      "currency": "EUR"
    }
  }
}
```

### Деталізація параметрів конфігурації

- `job_id` (рядок, обов'язковий): глобально унікальний ідентифікатор задачі. Використовується для побудови ключів ідемпотентності, вибору шарду та аудиту журналів.
- `version` (ціле число, обов'язковий): монотонний номер версії конфігурації. При оновленні розкладу номер зростає, що дозволяє воркерам відхиляти завдання, згенеровані за застарілими правилами.
- `partition_key` (рядок, необов'язковий): ключ, за яким обчислюється хеш для прив'язки до консистентного кільця планувальників. Якщо поле пропущено, шардування виконується за значенням `job_id`.
- `schedule.expression` (рядок, обов'язковий): вираз cron або макрос періодичності.
- `schedule.timezone` (рядок, необов'язковий, за замовчуванням `UTC`): часовий пояс із бази назв IANA (наприклад, `Europe/Kyiv`, `America/New_York`). Планувальник самостійно враховує сезонне переведення стрілок для локальних розкладів.
- `schedule.jitter_seconds` (ціле число, необов'язковий, за замовчуванням `0`): максимальна випадкова затримка в секундах, яка додається до розрахованого моменту запуску для запобігання перевантаженню сховищ у момент `00:00:00`.
- `misfire_policy` (перелік, обов'язковий): алгоритм реагування системи на пропущені ітерації у разі збою чи аварійного простою кластера.
- `grace_period_ms` (ціле число, обов'язковий, за замовчуванням `60000`): допустиме вікно запізнення в мілісекундах. Якщо реальний час диспатчу відхиляється від запланованого менше ніж на цей інтервал, запуск вважається штатним і не активує аварійну політику пропусків.
- `concurrency_policy` (перелік, обов'язковий): поведінка планувальника у ситуації, коли настав час чергового запуску, але попередня ітерація задачі ще не завершила роботу у воркері.
- `execution_timeout_ms` (ціле число, обов'язковий): граничний час очікування відповіді від воркера. Якщо воркер не надіслав підтвердження завершення до закінчення дедлайну, задача примусово переводиться у стан помилки або відправляється на повтор.

## 3. Контракт конверта диспатчу та заголовки огорожі (Dispatch Envelope)

Коли часове колесо планувальника фіксує настання запланованого слота, воно створює повідомлення-тригер. Повідомлення передається через брокер черг із суворим набором службових заголовків, які є обов'язковими для обробки на стороні виконавця:

### Службові метадані та заголовки протоколу
- `X-Cron-Job-ID`: унікальний ідентифікатор задачі (`billing-monthly-settlement`).
- `X-Cron-Scheduled-Time-UTC`: канонічний запланований час настання слота у форматі ISO-8601 (`2026-09-01T00:00:00.000Z`).
- `X-Cron-Actual-Dispatch-UTC`: фізичний момент відправки повідомлення вузлом планувальника (`2026-09-01T00:00:00.124Z`).
- `X-Cron-Dispatch-Epoch`: 64-бітне монотонне число епохи володіння шардом (`1844674407370955161`). Видається розподіленим координатором консенсусу. Воркер зобов'язаний зберегти цей токен та відхилити будь-який наступний запит з меншим значенням.
- `X-Cron-Idempotency-Key`: комбінований дедуплікаційний ключ виду `<job_id>:<scheduled_time_utc>`. Забезпечує захист від повторного виконання бізнес-логіки у спільній базі даних.
- `X-Cron-Attempt`: порядковий номер спроби запуску поточної ітерації (починається з `1` та інкрементується механізмом повторів).

## 4. Скінченний автомат станів виконання (Execution State Machine)

Життєвий цикл кожної окремої ітерації періодичної задачі формалізується скінченним автоматом із чіткими правилами переходів між станами:

```text
       ┌──────────────┐
       │  SCHEDULED   │
       └──────┬───────┘
              │ Настав час слота (now >= scheduled_time)
              ▼
       ┌──────────────┐   Відхилення > Grace Period
       │  EVALUATING  ├────────────────────────────┐
       └──────┬───────┘                            │
              │                                    ▼
              │ Відхилення <= Grace Period  ┌──────────────┐
              ▼                             │   MISFIRED   │
       ┌──────────────┐                     └──────┬───────┘
       │  DISPATCHED  │                            │ Обробка за
       └──────┬───────┘                            │ Misfire Policy
              │ Воркер зафіксував задачу           ▼
              ▼                             ┌──────────────┐
       ┌──────────────┐   Помилка / Таймаут │ RETRY_QUEUE  │
       │   RUNNING    ├────────────────────►└──────┬───────┘
       └──────┬───────┘                            │
              │                                    │ Ліміт спроб
              ├─── Успішне завершення ──┐          │ вичерпано
              ▼                         ▼          ▼
       ┌──────────────┐          ┌──────────────┐┌──────────────┐
       │  SUCCEEDED   │          │  CANCELLED   ││ DEAD_LETTER  │
       └──────────────┘          └──────────────┘└──────────────┘
```

### Семантика станів автомата
1. `SCHEDULED` (Заплановано): задача завантажена у відповідний слот ієрархічного часового колеса і чекає просування монотонного лічильника тактів.
2. `EVALUATING` (Оцінка готовності): планувальник перевіряє валідність власної лізи шарду, відсутність конфліктів паралельності та величину запізнення відносно настінного часу.
3. `DISPATCHED` (Відправлено): повідомлення-тригер успішно зафіксоване у буфері брокера черг задач.
4. `RUNNING` (Виконується): воркер перевірив токен огорожі, переконався, що його значення перевищує раніше бачені, встановив транзакційний замок на ключ ідемпотентності та виконує цільовий бізнес-код.
5. `SUCCEEDED` (Успішно завершено): воркер повернув позитивне підтвердження (ACK), зафіксував результати транзакції та звільнив замок конкурентності.
6. `MISFIRED` (Пропущено через аварію): час запуску минув під час простою планувальника або системної недоступності, а затримка перевищила допустиме вікно `grace_period_ms`.
7. `RETRY_QUEUE` (Черга повторів): після збою чи мережевого таймауту задача очікує наступної спроби згідно з правилами експоненційного відтермінування.
8. `CANCELLED` (Скасовано): ітерацію примусово зупинено оператором або заміщено свіжішим тригером відповідно до обраної політики конкурентності.
9. `DEAD_LETTER` (Карантин / Мертва черга): усі спроби виконання завершилися фатальною помилкою; метадані зафіксовані для ручного аналізу інженерами.

## 5. Алгоритмічні правила політик пропуску (Misfire Policies)

Якщо внаслідок масштабної аварії інфраструктури (наприклад, аварійне знеструмлення кластера чи мережевий розрив між ЦОД) планувальник не функціонував протягом кількох годин, накопичується масив пропущених точок запуску. Після відновлення роботи система застосовує одну з трьох строго специфікованих стратегій:

### `FIRE_AND_PROCEED` (Хронологічний наздогін усіх пропусків)
- **Алгоритм**: планувальник сканує весь інтервал від моменту останньої успішної фіксації до поточного часу `now`. Для кожного пропущеного слота генерирується окрема подія-тригер зі збереженням історичної мітки `scheduled_time_utc`. Події надсилаються у чергу послідовно у строгому хронологічному порядку.
- **Гарантія**: жоден квант облікового часу не втрачається. Якщо сервіс був недоступний три дні, щоденна задача виконається рівно три рази поспіль.
- **Сфера застосування**: нарахування відсотків за банківськими депозитами, генерація бухгалтерських проводок, нарізка щоденних партицій баз даних, білінгові взаєморозрахунки.

### `FIRE_ONCE_NOW` (Одноразова актуалізація стану)
- **Алгоритм**: усі пропущені історичні слоти скасовуються без генерації повідомлень. Планувальник миттєво створює рівно одну позачергову подію-тригер із міткою поточного часу `now`, після чого вираховує наступну штатну точку запуску за календарем і переходить у режим очікування.
- **Гарантія**: система актуалізує робочий стан за один прохід, не створюючи лавиноподібного навантаження на базу даних накопиченими тригерами.
- **Сфера застосування**: очищення застарілих кешів, прогрів пошукових індексів, перерахунок агрегованих рейтингів товарів, реплікація довідників.

### `IGNORE_MISFIRES` (Повне ігнорування втрачених інтервалів)
- **Алгоритм**: усі пропущені точки запуску безповоротно відкидаються. Планувальник скидає чергу, знаходить найближчу майбутню точку `next_run_utc > now` і встановлює таймер на неї, не виконуючи жодних компенсаційних дій.
- **Гарантія**: нульове навантаження на інфраструктуру після виходу з аварійного стану.
- **Сфера застосування**: надсилання ранкових вітальних сповіщень користувачам мобільного застосунку, збір поточної телеметрії з IoT-датчиків, щохвилинна перевірка доступності зовнішніх партнерських API.

## 6. Політики ізоляції паралельних запусків (Concurrency Policies)

У ситуаціях, коли тривалість виконання задачі перевищує період її запуску (наприклад, важкий аналітичний звіт виконується сорок хвилин, а розклад вимагає старту кожні тридцять хвилин), планувальник застосовує одне з таких правил:

1. `ALLOW_CONCURRENT` (Паралельний запуск дозволено): новий тригер генерується та відправляється на виконання незалежно від стану попередніх ітерацій. Використовується лише для задач, що оперують незалежними наборами даних і не мають спільних блокувань.
2. `FORBID_CONCURRENT` (Заборона накладання): якщо попередня ітерація все ще перебуває у стані `RUNNING`, планувальник не відправляє новий тригер у чергу, фіксує статус `SKIPPED_CONCURRENT` та чекає наступного слота за розкладом.
3. `REPLACE_CONCURRENT` (Заміщення новою ітерацією): планувальник надсилає сигнал скасування (`CANCEL`) процесу воркера, що виконує стару ітерацію, і негайно диспатчить новий тригер зі свіжими параметрами. Застосовується у задачах побудови snapshot-станів, де старі обчислення втрачають актуальність з появою нових даних.
