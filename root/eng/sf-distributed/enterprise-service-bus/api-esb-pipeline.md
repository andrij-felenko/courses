# 📋 Специфікація контракту інтеграційного конвеєра та нормалізованого повідомлення

Ця довідкова специфікація визначає формальні інтерфейси, структури даних, правила маршрутизації та шаблони взаємодії, які утворюють серцевину інтеграційного конвеєра шини (Normalized Message Router / Mediation Pipeline). Вона регламентує модель нормалізованого конверта, шаблони обміну повідомленнями (MEP), життєвий цикл адаптерів, механізми захисту від збоїв, адміністративні інтерфейси та політику ізоляції аварійних повідомлень.

## 1. Специфікація нормалізованого конверта (Normalized Message Envelope)

Будь-яке повідомлення, що потрапляє в інтеграційний контур через вхідний адаптер, нормалізується у формат внутрішнього конверта — `NormalizedMessage`. Нормалізація усуває специфіку конкретних транспортних протоколів (HTTP/REST, SOAP/XML, JMS/AMQP, Kafka, ISO 8583, плоскі CSV або фіксовані структури мейнфреймів) і приводить повідомлення до єдиної об'єктної моделі з фіксованими семантичними полями.

Нормалізований конверт складається з трьох ізольованих секцій:
1. **Системні заголовки (System Headers)**: метадані маршрутизації, пріоритету, часу життя та унікальної ідентифікації.
2. **Контекст безпеки та аудиту (Security & Trace Context)**: параметри автентифікації суб'єкта, цифрові підписи, наскрізні мітки трасування W3C.
3. **Корисне навантаження (Message Payload & Attachments)**: безпосередні бізнес-дані у вигляді незмінного буфера байтів із метаданими типу вмісту.

### 1.1. Стандартні системні заголовки (System Headers)

Системні заголовки є обов'язковими для забезпечення коректної маршрутизації, наскрізного аудиту та запобігання втраті даних під час розподілених збоїв.

| Назва заголовка | Тип даних | Опис та семантичне призначення |
|:---|:---|:---|
| `X-Message-ID` | `String (UUIDv4)` | Глобально унікальний ідентифікатор цього фізичного примірника повідомлення. Генерується вхідним адаптером у момент захоплення пакета. |
| `X-Correlation-ID` | `String` | Наскрізний ідентифікатор бізнес-транзакції. Зберігається незмінним уздовж усього ланцюжка сервісів від первинного запиту до фінальної відповіді. |
| `X-Causation-ID` | `String (UUIDv4)` | Ідентифікатор попереднього повідомлення, яке безпосередньо спричинило відправку поточного. Використовується для побудови ациклічного графа причинності. |
| `X-Timestamp` | `Int64 (Unix epoch ms)` | Час створення повідомлення або входження в контур шини. Використовується для моніторингу затримок SLA та виявлення застарілих пакетів. |
| `X-TTL-Ms` | `Int32 (Milliseconds)` | Час життя повідомлення (Time To Live). Після закінчення цього часу повідомлення вважається недійсним і перенаправляється в DLQ без виконання бізнес-обробки. |
| `X-Priority` | `Int8 (0..9)` | Пріоритет обробки (0 — фоновий/найнижчий, 4 — стандартний, 9 — критичний/екстрений). Визначає вибір черги в пулах пріоритетної диспетчеризації. |
| `X-Reply-To` | `String (URI)` | Зворотна адреса для відправки асинхронної відповіді (наприклад, `amqp:queue:billing.responses` або `https://api.gateway/v1/callbacks`). |
| `X-Fault-To` | `String (URI)` | Спеціальна адреса для направлення повідомлень про системні збої, якщо вона відрізняється від основної адреси відповіді. |
| `X-Content-Type` | `String (MIME)` | Тип даних корисного навантаження (`application/json`, `application/xml`, `application/octet-stream`, `application/x-protobuf`). |
| `X-Content-Encoding` | `String` | Схема компресії корисного навантаження (`gzip`, `deflate`, `zstd`, `identity`). |
| `X-Routing-Key` | `String` | Логічний ключ маршрутизації, який використовується контентними та префіксними маршрутизаторами для вибору цільового кластера. |
| `X-Fault-Flag` | `Boolean` | Ознака того, що даний конверт несе діагностичну інформацію про збій (Fault Envelope), а не корисний бізнес-результат. |

### 1.2. Контекст безпеки (Security Context)

Контекст безпеки передається паралельно з повідомленням, проте відокремлений від звичайних бізнес-атрибутів для запобігання підміні прав downstream-компонентами:
- `Principal`: ідентифікований суб'єкт запиту (ім'я користувача, системний ID або ідентифікатор клієнтського застосунку).
- `Roles`: масив прав та груп доступу, валідованих на периметрі шини (наприклад, `["PAYMENT_OPERATOR", "FINANCIAL_AUDITOR"]`).
- `Auth-Token`: оригінальний криптографічний токен (JWT, SAML 2.0 Assertion, mTLS Certificate Fingerprint) для наскрізної делегованої автентифікації.
- `Client-IP`: фізична мережева адреса ініціатора виклику для контролю географічних обмежень та застосування лімітів інтенсивності запитів.

### 1.3. Корисне навантаження та Zero-Copy оптимізація

Корисне навантаження в `NormalizedMessage` зберігається як незмінний зріз пам'яті (`std::span<const uint8_t>` у C++ або незмінний буфер байтів). Це забезпечує вирішальну архітектурну оптимізацію: якщо стадія конвеєра виконує лише перевірку прав, валідацію токена або маршрутизацію на основі заголовків, тіло повідомлення взагалі не копіюється і не парситься в пам'яті процесу.

## 2. Шаблони обміну повідомленнями (Message Exchange Patterns — MEP)

Конвеєр посередництва формалізує взаємодію між учасниками обміну через чотири базові шаблони WSDL 2.0 / JBI MEP, визначаючи чіткі гарантії для кожного сценарію:

### 2.1. In-Only (Одностороння подія / Fire-and-Forget)
Клієнт надсилає повідомлення і не очікує бізнес-відповіді. Транспортний рівень шини підтверджує прийом повідомлення (ACK) одразу після збереження його у вхідний буфер або журнал попереднього запису (WAL).
- **Поведінка**: відправник не блокується в очікуванні завершення обробки бізнес-сервісом.
- **Життєвий цикл**: `INITIAL` → `IN_PROGRESS` → `COMPLETED` (або `FAULT_DLQ` у разі аварії).
- **Сфера застосування**: публікація подій зміни стану (Event Sourcing / CDC), логування дій користувача, надсилання телеметрії.

### 2.2. In-Out (Синхронний або асинхронний Request-Reply)
Клієнт відправляє вхідний конверт (`In`) і очікує на отримання результату (`Out`). Конвеєр виконує маршрутизацію до цільового сервісу, отримує вихідні дані, здійснює трансляцію схеми і повертає сформований пакет клієнту.
- **Поведінка**: клієнт або блокує потік очікування до отримання відповіді (синхронний режим), або надає зворотну чергу/webhook (`X-Reply-To`), куди шина асинхронно публікує результат із збереженням `X-Correlation-ID`.
- **Обробка таймаутів**: якщо сервіс не відповів протягом встановленого таймауту (`SLA Timeout`), конвеєр генерує `Fault`-конверт з кодом помилки `GATEWAY_TIMEOUT` і повертає його ініціатору.
- **Сфера застосування**: проведення банківських транзакцій, бронювання місць, перевірка кредитного ліміту в реальному часі.

### 2.3. Robust In-Only (Одностороннє з гарантованим повідомленням про збій)
Клієнт не очікує корисного навантаження у разі успіху, проте вимагає обов'язкового повідомлення, якщо конвеєр зазнав невдачі під час маршрутизації, валідації чи виклику бекенда.
- **Поведінка**: при успішній обробці шина повертає порожнє підтвердження (`Void 202/204`). У разі помилки конвеєр формує детальний `Fault`-конверт і надсилає його за адресою `X-Fault-To`.
- **Сфера застосування**: пакетне завантаження фінансових реєстрів, фонова генерація аналітичних звітів.

### 2.4. In-Optional-Out (Запит з необов'язковою відповіддю)
Клієнт надсилає запит, результатом якого може бути або відповідь із даними (`Out`), або успішне завершення без даних (`Void`), або системна помилка (`Fault`).

### Матриця станів та переходів життєвого циклу Exchange

| Початковий стан | Подія / Тригер | Наступний стан | Системна дія брокера |
|:---|:---|:---|:---|
| `CREATED` | Виклик `pipeline.dispatch()` | `IN_FLIGHT` | Ініціалізація `X-Correlation-ID`, старт таймера SLA. |
| `IN_FLIGHT` | Стадія повернула `STAGE_CONTINUE` | `IN_FLIGHT` | Передача нормалізованого конверта наступній стадії конвеєра. |
| `IN_FLIGHT` | Стадія повернула `STAGE_FILTERED` | `TERMINATED_FILTER` | Безпечне завершення конвеєра (повідомлення відсіяне як нецільове), запис в аудит. |
| `IN_FLIGHT` | Стадія повернула `STAGE_FAULT` | `FAULT_HANDLING` | Перевірка типу помилки (Transient vs Permanent) та ліміту повторів. |
| `FAULT_HANDLING`| Тимчасовий збій та `retry < max_retries` | `RETRY_WAIT` | Постановка в чергу затримки (алгоритм Exponential Backoff). |
| `FAULT_HANDLING`| Постійний збій або `retry >= max_retries` | `DEAD_LETTER` | Запис у сховище DLQ, генерація системного сповіщення, ACK вхідній черзі. |
| `IN_FLIGHT` | Успішна передача у вихідний адаптер | `COMPLETED` | Фіксація метрик тривалості, відправка ACK клієнту або брокеру черги. |

## 3. Контракти інтерфейсів компонентів конвеєра

Усі компоненти конвеєра будуються навколо строго типізованих інтерфейсів. Це гарантує модульність системи, дозволяючи динамічно замінювати або оновлювати адаптери без перезапуску решти контуру.

### 3.1. Життєвий цикл та інтерфейс адаптерів протоколів (IInboundAdapter / IOutboundAdapter)

Адаптери протоколів ізолюють мережевий стек від внутрішньої логіки конвеєра:

- **Вхідний адаптер (Inbound Adapter)**: відкриває мережевий порт або підключається до зовнішнього брокера (`bind`/`subscribe`), слухає потік кадрів, нормалізує їх у `NormalizedMessage` і передає в ядро конвеєра. Після завершення обробки адаптер відправляє підтвердження (`ACK`/`COMMIT`) або сигнал відхилення (`NACK`/`REJECT`) джерелу повідомлення.
- **Вихідний адаптер (Outbound Adapter)**: підтримує пул відкритих з'єднань (Connection Pool), серіалізує `NormalizedMessage` у бінарний або текстовий формат цільового протоколу (наприклад, HTTP POST або AMQP Publish), відправляє пакет і чекає на відповідь або підтвердження доставки від віддаленого сервера.
- **Контракт плавного вимкнення (Graceful Shutdown)**: при отриманні сигналу завершення процесу (`SIGTERM`) вхідні адаптери негайно закривають прийом нових запитів, після чого конвеєр отримує регламентний час (`drain_timeout_ms = 30000`) для доопрацювання всіх уже прийнятих повідомлень. Лише після повного спорожнення черг вихідні адаптери закривають мережеві з'єднання.

### 3.2. Інтерфейс стадії конвеєра (`IPipelineStage`)

```cpp
// C++ контракт інтерфейсу стадії посередництва
enum class StageResult {
    Continue,      // Успішна обробка, передати конверт наступній стадії
    Filtered,      // Повідомлення відсіяно фільтром (нормальне завершення)
    Fault,         // Виникла непереборна помилка обробки
    Retry,         // Тимчасовий збій, запит на повторну спробу
    AsyncSuspend   // Асинхронна пауза (очікування I/O або сигналу події)
};

class IPipelineStage {
public:
    virtual ~IPipelineStage() = default;
    
    // Унікальне ім'я стадії для метрик, трасування та конфігурації
    [[nodiscard]] virtual std::string_view name() const noexcept = 0;
    
    // Ініціалізація внутрішніх ресурсів стадії
    virtual bool initialize(const StageConfig& config) = 0;
    
    // Головний метод обробки повідомлення
    virtual StageResult process(Exchange& exchange) = 0;
    
    // Коректне звільнення ресурсів при зупинці конвеєра (Graceful Shutdown)
    virtual void destroy() noexcept = 0;
};
```

### 3.3. Інтерфейс маршрутизатора за змістом (`IContentBasedRouter`)

Маршрутизатор аналізує поля заголовків або тіло повідомлення і повертає вектор кінцевих адрес призначення:

```cpp
class IContentBasedRouter {
public:
    virtual ~IContentBasedRouter() = default;
    
    // Оцінка правил та повернення списку цільових адрес (Unicast / Multicast)
    [[nodiscard]] virtual std::vector<std::string> route(const NormalizedMessage& message) const = 0;
    
    // Динамічна реєстрація правила маршрутизації без зупинки процесу
    virtual void register_rule(std::string_view rule_expression, std::string_view target_endpoint) = 0;
};
```

### 3.4. Інтерфейс транслятора схем (`IMessageTranslator`)

Транслятор виконує двостороннє семантичне та структурне перетворення корисного навантаження між канонічною моделлю шини та специфічними протокольними форматами інтегрованих систем:

```cpp
class IMessageTranslator {
public:
    virtual ~IMessageTranslator() = default;
    
    // Трансформація корисного навантаження у цільову схему даних
    virtual std::expected<NormalizedMessage, TranslationError> translate(
        const NormalizedMessage& source_message,
        std::string_view target_schema_id
    ) const = 0;
};
```

## 4. Специфікація мови виразів маршрутизації (Routing Expression Language)

Для усунення необхідності жорсткого кодування умов маршрутизації конвеєр підтримує декларативну мову виразів (Expression Language). Вираз обчислюється над нормалізованим конвертом і повертає булеве значення (`true`/`false`).

### 4.1. Синтаксичні конструкції та селектори

- **Селектори заголовків**: `header('X-Message-Type') == 'ORDER_PAYMENT'`
- **JSONPath-селектори тіла**: `jsonpath('$.order.total_amount') > 1000.00`
- **XPath-селектори тіла**: `xpath('/order/customer/@tier') == 'VIP'`
- **Логічні зв'язки**: підтримуються оператори `AND`, `OR`, `NOT`, `IN (...)`, `MATCHES '(regex)'`.

### 4.2. Безпека виконання виразів (Execution Sandbox)

Оскільки вирази маршрутизації можуть конфігуруватися адміністраторами в рантаймі, рушій виразів зобов'язаний дотримуватися правил безпеки:
- **Заборона доступу до системного API**: вираз не має доступу до файлової системи, мережевих сокетів або системних викликів ОС.
- **Обмеження глибини розбору (Parser Depth Limits)**: захист від рекурсивних атак (наприклад, глибина вкладеності JSON/XML обмежена значенням 32).
- **Ліміт часу обчислення (Evaluation Timeout)**: обчислення виразу переривається з помилкою `ROUTING_EVALUATION_TIMEOUT`, якщо воно перевищує 5 мікросекунд (захист від катастрофічного бектрекінгу регулярних виразів — ReDoS).

## 5. Специфікація автоматичного розмикача ланцюга (Circuit Breaker)

Кожен вихідний адаптер конвеєра захищений автоматичним вимикачем (Circuit Breaker) для ізоляції каскадних збоїв при відмові зовнішніх сервісів.

```
       ┌────────────────┐
       │     CLOSED     │ ──(Помилки > 50%)──> ┌────────────────┐
       │ (Нормальний)   │                      │      OPEN      │
       └────────────────┘                      │  (Швидка відмова) │
                ▲                              └────────────────┘
                │                                       │
         (Успішні проби)                          (Таймаут 30с)
                │                                       │
       ┌────────────────┐                               ▼
       │   HALF-OPEN    │ <─────────────────────────────┘
       │  (Пробний рух) │
       └────────────────┘
```

### 5.1. Стани розмикача ланцюга

1. **CLOSED (Замкнений / Нормальний режим)**: усі запити безперешкодно надсилаються до цільового сервісу. Рушій відстежує відсоток помилок у ковзному вікні (Sliding Window розміром 100 запитів). Якщо відсоток помилок перевищує 50%, автомат переходить у стан `OPEN`.
2. **OPEN (Розімкнений / Захисний режим)**: усі вхідні виклики до цього сервісу негайно відхиляються без виконання мережевого запиту з поверненням статусу `SERVICE_UNAVAILABLE` або перенаправленням у резервний канал (Fallback). Цей стан захищає виснажений бекенд від добивання повторними запитами.
3. **HALF-OPEN (Напіврозімкнений / Пробний режим)**: після закінчення періоду охолодження (`Cooldown Period = 30 секунд`) автомат пропускає обмежену кількість тестових запитів (наприклад, 5 запитів). Якщо всі вони завершуються успішно, автомат повертається в стан `CLOSED`. Якщо хоча б один завершується збоєм, автомат повертається в стан `OPEN` ще на 30 секунд.

## 6. Захист інтеграційного периметра (Security Boundary & Sanitization)

Шина є центральним шлюзом корпоративної мережі, тому конвеєр зобов'язаний захищати внутрішні сервіси від спеціально сформованих шкідливих пакетів:

1. **Захист від атак розширення сутностей XML (Billion Laughs / XML Entity Expansion)**: вхідні парсери жорстко вимикають обробку зовнішніх DTD-сутностей (`FEATURE_EXTERNAL_GENERAL_ENTITIES = false`, `FEATURE_DISALLOW_DOCTYPE = true`).
2. **Контроль розміру корисного навантаження (Max Payload Enforce)**: пакети, розмір яких перевищує встановлений ліміт (наприклад, 10 МБ), відхиляються на рівні мережевого сокета до виділення пам'яті в купі (`413 Payload Too Large`).
3. **Санітизація та валідація кодувань**: повідомлення перевіряються на коректність послідовності байтів UTF-8, наявність заборонених управляючих символів та нульових байтів (`\0`), які можуть спричинити уразливості переповнення буфера або ін'єкції в застарілі системи на C/C++.

## 7. Специфікація транзакційного узгодження та Outbox-патерну

Для забезпечення надійної передачі подій між базою даних застосунку та інтеграційною шиною без використання важкого і ненадійного двофазного коміту (2PC / XA) специфікація регламентує використання патерну **Transactional Outbox**:

1. **Таблиця вихідних подій (`outbox_events`)**: застосунок зберігає зміну бізнес-сутності та вихідну подію в одній локальній ACID-транзакції бази даних:
   - `id`: унікальний ідентифікатор події (UUIDv4).
   - `aggregate_type`: ім'я доменної сутності (наприклад, `OrderAggregate`).
   - `aggregate_id`: бізнес-ідентифікатор сутності (`ORD-88192`).
   - `event_type`: назва події (`OrderCreatedEvent`).
   - `payload`: серіалізоване тіло події в форматі JSON або Protocol Buffers.
   - `created_at`: мітка часу запису в базу даних.
   - `published_at`: мітка часу успішної публікації в шину (NULL до моменту відправки).
2. **Механізм публікації (CDC / Debezium)**: фоновий агент або CDC-адаптер (Change Data Capture) читає журнал транзакцій бази даних (PostgreSQL WAL / MySQL Binlog) і публікує події в шину. Це усуває ризик дублювання або втрати подій у разі падіння застосунку в проміжку між записом у базу та відправкою в мережу.

## 8. Динамічне оновлення конфігурацій (Hot Reloading Contract)

У корпоративних середовищах зупинка інтеграційного брокера для оновлення правил маршрутизації є неприпустимою (Zero Downtime SLA). Конвеєр реалізує механізм безпечного гарячого перезавантаження без блокування потоків виконання:

1. **Модель Read-Copy-Update (RCU)**: таблиця правил маршрутизації та конфігурації стадій зберігаються в атомарному покажчику `std::atomic<std::shared_ptr<RoutingTable>>`.
2. **Неблокуюче читання**: робочі потоки, що обслуговують транзакції, захоплюють локальну копію `shared_ptr` і виконують маршрутизацію без захоплення м'ютексів.
3. **Атомарне перемикання**: при надходженні нової конфігурації фоновий потік валідує нове дерево правил, будує нову незмінну структуру `RoutingTable` і атомарно оновлює покажчик. Стара таблиця автоматично знищується після того, як останній активний потік завершить роботу зі своєю копією.

## 9. Специфікація метрик та телеметрії (OpenTelemetry Metrics)

Для операційного моніторингу працездатності конвеєра кожен вузол експортує стандартизовані метрики у форматі Prometheus / OpenTelemetry:

- `pipeline_exchange_duration_seconds` (Гістограма): загальний час обробки обміну від входу до виходу з квантилями p50, p90, p99, p999.
- `pipeline_inbound_messages_total` (Лічильник): кількість отриманих повідомлень із мітками `protocol`, `endpoint`, `status`.
- `pipeline_stage_execution_seconds` (Гістограма): час виконання окремої стадії конвеєра (`stage_name`).
- `pipeline_circuit_breaker_state` (Gauge): поточний стан автомата захисту (0 = CLOSED, 1 = HALF_OPEN, 2 = OPEN).
- `pipeline_dlq_messages_total` (Лічильник): кількість аварійних повідомлень, спрямованих у мертву чергу за кодами помилок.

## 10. Специфікація мертвої черги та адміністративного API (Dead-Letter Management API)

Коли обробка повідомлення остаточно зазнає краху, конвеєр формує конверт помилки та зберігає його в ізольованому репозиторії.

### 10.1. Схема конверта помилки (Fault Envelope Schema)

```json
{
  "$schema": "https://integration.enterprise.org/schemas/v1/fault-envelope.json",
  "fault_id": "flt-948a3b12-581a-42cd-b903-8891ac411082",
  "timestamp": 1771584000000,
  "failed_stage": "SchemaValidatorStage",
  "error_category": "UNRECOVERABLE_DATA_CORRUPTION",
  "error_code": "ERR_INVALID_CURRENCY_CODE",
  "error_message": "Поле currency='XYZ' не відповідає стандарту ISO 4217",
  "retry_attempts_exhausted": 3,
  "execution_node": "esb-worker-prod-04",
  "original_exchange": {
    "message_id": "msg-109283-ac",
    "correlation_id": "corr-tx-881920-55",
    "causation_id": "msg-109280-bb",
    "headers": {
      "X-Message-Type": "ORDER_PAYMENT",
      "X-Client-ID": "mobile-app-ios-v4"
    },
    "payload_base64": "eydhbW91bnQnOiAxNTAuMCwgJ2N1cnJlbmN5JzogJ1hZWid9"
  }
}
```

### 10.2. Алгоритм експоненційного відступу з повним тремтінням (Full Jitter Backoff)

Для тимчасових мережевих збоїв інтервал між повторними спробами розраховується як:

```text
t_sleep = random_uniform(0, min(t_max, t_base * 2^(retry_count)))
```

де `t_base = 100 мс`, `t_max = 30 000 мс`, а `random_uniform` повністю ліквідує ефект синхронної навали повторних запитів.

### 10.3. Адміністративний REST API для керування мертвою чергою

Для ручного втручання та повторної відправки виправлених повідомлень шина надає захищений інтерфейс:
- `GET /api/v1/dlq/messages?page=1&limit=50&status=PENDING`: список повідомлень у черзі збоїв із фільтрацією за часом та кодом помилки.
- `GET /api/v1/dlq/messages/{fault_id}`: отримання детального дампа помилки разом з оригінальними вхідними байтами.
- `POST /api/v1/dlq/messages/{fault_id}/replay`: повторна ін'єкція повідомлення на початок конвеєра після усунення несправності цільового сервісу.
- `POST /api/v1/dlq/messages/{fault_id}/edit-and-replay`: внесення виправлень у корисне навантаження оператором (наприклад, виправлення помилки в полі адреси) та подальший перезапуск конвеєра.
- `DELETE /api/v1/dlq/messages/{fault_id}`: списання та перенесення безнадійно пошкодженого повідомлення в холодний архів аудиту.
