# 📋 Специфікація та контракт життєвого циклу Sidecar у Kubernetes

Контракт супутнього контейнера (Sidecar) у Kubernetes визначає порядок ініціалізації, координацію робочого стану та послідовність вивантаження процесів усередині спільного Pod: від стандартизованих нативних сайдкарів стандарту KEP-753 (`restartPolicy: Always`) до синхронізації блокуючих хуків `preStop`, спільних томів оперативної пам'яті та міжпроцесної взаємодії через простір імен `shareProcessNamespace`.

## 1. Специфікація нативного Sidecar (KEP-753 / Kubernetes 1.28+)

Починаючи з версії Kubernetes 1.28 (Beta в 1.29 та GA в наступних релізах), супутні контейнери отримали офіційну нативну підтримку ядра оркестратора. Вони оголошуються всередині списку `spec.initContainers`, проте, на відміну від звичайних одноразових ініціалізуючих завдань, що завершуються перед стартом застосунку, маркуються директивою `restartPolicy: Always`.

Наявність цієї директиви докорінно змінює логіку роботи керуючого демона `kubelet`: замість очікування завершення процесу, оркестратор чекає лише успішного переходу контейнера у стан готовності (проходження перевірки `startupProbe`), після чого залишає його працювати у фоні протягом усього життя Pod і паралельно запускає наступні контейнери.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-service-pod
  labels:
    app: payment-service
spec:
  terminationGracePeriodSeconds: 30
  shareProcessNamespace: false

  # ── Нативні Sidecar-контейнери (KEP-753) ──────────────────────────────────
  initContainers:
  - name: vault-agent-sidecar
    image: hashicorp/vault:1.15.2
    restartPolicy: Always
    securityContext:
      runAsUser: 1000
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
    resources:
      limits:
        cpu: "200m"
        memory: "128Mi"
      requests:
        cpu: "50m"
        memory: "64Mi"
    startupProbe:
      httpGet:
        path: /v1/sys/health
        port: 8200
      failureThreshold: 30
      periodSeconds: 1
    volumeMounts:
    - name: shared-vault-token
      mountPath: /vault/secrets

  # ── Основні контейнери застосунку (Main Workload) ─────────────────────────
  containers:
  - name: payment-app
    image: company/payment-app:v2.4.1
    ports:
    - containerPort: 8080
      name: http-api
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "/app/scripts/drain-inflight.sh 15"]
    volumeMounts:
    - name: shared-vault-token
      mountPath: /var/run/secrets/vault
      readOnly: true
    - name: shared-logs
      mountPath: /var/log/app

  # ── Супутні томи даних (Shared Volumes) ───────────────────────────────────
  volumes:
  - name: shared-vault-token
    emptyDir:
      medium: Memory
      sizeLimit: 16Mi
  - name: shared-logs
    emptyDir: {}
```

## 2. Формальний контракт черговості запуску та перевірок працездатності

Під час створення Pod оркестратор гарантує суворий детермінований порядок ініціалізації всіх компонентів, що повністю виключає стан гонитви при старті:

Порядок розгортання складається з чотирьох послідовних стадій:

1. **Фаза послідовних Init-завдань:** Kubelet по черзі запускає одноразові ініціалізуючі контейнери, що не мають директиви `restartPolicy: Always` (наприклад, міграції бази даних або налаштування правил iptables утилітою `istio-init`). Кожен наступний контейнер чекає успішного завершення попереднього з нульовим кодом виходу `0`.
2. **Фаза нативних Sidecar-контейнерів:** Kubelet запускає супутні контейнери з директивою `restartPolicy: Always`. Процес запускається у фоні, і Kubelet періодично виконує запити його `startupProbe`. Доки перевірка не поверне успішний статус (HTTP 200 або код 0 для Exec), Kubelet блокує перехід до запуску наступних компонентів.
3. **Фаза основних контейнерів бізнес-логіки:** Як тільки всі сайдкари підтвердили готовність, Kubelet одночасно запускає всі контейнери з масиву `spec.containers`. Застосунок гарантовано має відкриті локальні порти проксі-сервера та змонтовані файли секретів.
4. **Фаза маршрутизації клієнтського трафіку:** Після успішного проходження перевірок `readinessProbe` основного контейнера IP-адреса Pod додається до пулу ендпоінтів сервісу (`EndpointSlice`), відкриваючи доступ зовнішнім клієнтам.

| Фаза запуску | Об'єкт перевірки | Дія Kubelet | Умова переходу до наступного кроку |
|---|---|---|---|
| 1. Init Tasks | Звичайний `initContainer` (без `restartPolicy`) | Виконує послідовно один за одним | Завершення процесу з кодом виходу `0` |
| 2. Native Sidecars | `initContainer` з `restartPolicy: Always` | Запускає процес у фоновому режимі | Успішне проходження `startupProbe` (HTTP 200 / Exec 0) |
| 3. Main Containers | Масив `containers` | Запускає всі робочі навантаження паралельно | Успішне проходження `readinessProbe` |
| 4. Traffic Routing | Сервіс Kubernetes (Endpoints / EndpointSlice) | Додає IP-адресу Pod до пулу маршрутизатора | Повна готовність усіх основних контейнерів |

### Ключові інваріанти надійності старту:
* Якщо `startupProbe` нативного сайдкара зазнає невдачі довше за часовий ліміт `failureThreshold · periodSeconds`, Kubelet вважає запуск зірваним, примусово вбиває процес контейнера сигналом `SIGKILL` і виконує перезапуск відповідно до налаштованої політики `Pod.spec.restartPolicy`.
* Жоден основний контейнер із масиву `spec.containers` за жодних обставин не почне виконання системного виклику `execve()`, доки всі попередні нативні сайдкари в списку `spec.initContainers` не підтвердять свій здоровий стан через `startupProbe`.

## 3. Формальний контракт порядку зупинки та дренажу з'єднань

Під час планового оновлення версії сервісу або масштабування кластера оркестратор ініціює процедуру видалення Pod. Для запобігання втраті даних під час зупинки застосовується зворотний порядок завершення процесів:

1. **Відключення від площини маршрутизації:** Контролер сервісів негайно вилучає IP-адресу Pod із системних списків `EndpointSlice`. Зовнішній балансувальник навантаження перестає направляти нові вхідні запити на цей Pod.
2. **Зупинка основного робочого навантаження:** Kubelet надсилає системний сигнал `SIGTERM` виключно основним контейнерам із масиву `spec.containers`. Якщо для контейнера визначено хук `preStop`, спочатку виконується цей блокуючий скрипт, дозволяючи програмі спокійно завершити активні клієнтські транзакції (дренаж in-flight запитів).
3. **Очікування завершення бізнес-логіки:** Супутні сайдкар-контейнери продовжують повноцінно працювати: Envoy підтримує відкриті вихідні сокети, а Fluentbit збирає фінальні логи помилок, які генерує програма під час закриття пулів з'єднань.
4. **Зупинка нативних сайдкарів:** Тільки після того, як основний контейнер повністю завершив роботу і повернув код виходу `0` (або після вичерпання загального таймера `terminationGracePeriodSeconds`), Kubelet надсилає сигнал `SIGTERM` нативним сайдкар-контейнерам. Сайдкари скидають внутрішні буфери на диск і коректно зупиняються.

```
[Початок видалення Pod]
       │
       ▼
1. Видалення Pod з EndpointSlice сервісу (припинення зовнішнього трафіку)
       │
       ▼
2. Kubelet надсилає SIGTERM основним контейнерам (spec.containers)
   └── Одночасно запускається preStop hook основного застосунку (drain активних транзакцій)
       │
       ▼
3. Основний контейнер завершує процес (код виходу 0)
       │
       ▼
4. Kubelet надсилає SIGTERM нативним сайдкарам (spec.initContainers з restartPolicy: Always)
   └── Сайдкар виконує скидання буферів логів, закриває mTLS-сесії та завершується
       │
       ▼
[Pod повністю знищено та ресурси звільнено]
```

| Параметр специфікації | Тип | За замовчуванням | Призначення |
|---|---|---|---|
| `terminationGracePeriodSeconds` | integer | `30` | Загальний максимальний бюджет часу на виконання всіх `preStop` хуків та коректну зупинку всіх контейнерів Pod перед надсиланням жорсткого `SIGKILL`. |
| `lifecycle.preStop.exec.command` | array | `nil` | Блокуючий скрипт/команда, яка виконується всередині контейнера ДО того, як процес отримає сигнал `SIGTERM`. |
| `lifecycle.preStop.httpGet` | object | `nil` | HTTP-виклик локального ендпоінту дренажу (наприклад, `http://localhost:15000/drain_listeners`). |

## 4. Контракт міжпроцесної взаємодії та спільного простору PID

У специфічних сценаріях, коли сайдкар повинен не просто перехоплювати сокети, а безпосередньо взаємодіяти з процесом основного застосунку — наприклад, надсилати сигнал перезавантаження конфігурації `SIGHUP`, читати пам'ять процесу через `ptrace` або профілювати виконання ядра — у специфікації Pod активується прапорець спільного простору процесів:

```yaml
spec:
  shareProcessNamespace: true
```

### Системні наслідки та інваріанти прапорця `shareProcessNamespace`:
1. **Зміна ролі процесу PID 1:** За замовчуванням кожен контейнер має власний процес із номером 1. При активації спільного простору єдиним процесом `PID 1` у Pod стає легковажний процес службового `pause`-контейнера Kubernetes. Цей процес бере на себе обов'язок збирання процесів-сиріт (*zombie process reaping*), що запобігає витоку слотів у системній таблиці дескрипторів ядра.
2. **Прозорість системної директорії `/proc`:** Кожен контейнер у Pod отримує прямий доступ до файлової структури `/proc/<PID>/` будь-якого іншого контейнера. Сайдкар може вичитувати змінні оточення сусіднього процесу через `/proc/<PID>/environ`, дескриптори відкритих сокетів через `/proc/<PID>/fd/` та стан виділеної пам'яті через `/proc/<PID>/maps`.
3. **Міжпроцесна сигналізація:** Якщо контейнери працюють під спільним користувацьким ідентифікатором UID або мають необхідні привілеї ядра `CAP_KILL`, процес сайдкара може надіслати системний виклик `kill(target_pid, SIGHUP)` процесу застосунку для негайного скидання внутрішнього кешу або перезавантаження сертифікатів без повного перезапуску контейнера.
4. **Ізоляція кореневих файлових систем:** Попри спільний простір номерів процесів, ізоляція кореневих файлових систем (`Mount Namespace`) зберігається. Контейнер сайдкара може отримати доступ до файлів основного контейнера лише через явне монтування спільних томів `emptyDir` або через спеціальне системне посилання ядра `/proc/<PID>/root/`.

## 5. Діагностична таблиця кодів завершення та збоїв

| Код завершення | Сигнал / Помилка | Сценарій у контексті Sidecar | Дія інженера |
|---|---|---|---|
| `0` | `Exit 0` | Успішне штатне завершення процесу. | Нормальна очікувана поведінка. |
| `137` | `SIGKILL` (128 + 9) | Примусове знищення контейнера демоном OOM-Killer через перевищення `resources.limits.memory` або вичерпання загального ліміту часу `terminationGracePeriodSeconds`. | Збільшити ліміти пам'яті у маніфесті або збільшити тривалість `terminationGracePeriodSeconds`. |
| `143` | `SIGTERM` (128 + 15) | Планова зупинка за сигналом оркестратора. | Переконатися, що процес встиг виконати `flush` сокетів і буферів до завершення. |
| `1` | `Application Error` | Помилка конфігурації проксі (некоректний синтаксис конфігураційного файлу або відсутність прав читання секрету). | Перевірити права доступу на змонтованому томі `emptyDir` та валідність `ConfigMap`. |
| `CrashLoopBackOff` | Постійний перезапуск | Падіння сайдкара на старті через недоступність зовнішнього сервера автентифікації Vault або керуючої площини. | Налаштувати збільшений час очікування у перевірці `startupProbe`, щоб запобігти передчасному вбивству процесу Kubelet. |
