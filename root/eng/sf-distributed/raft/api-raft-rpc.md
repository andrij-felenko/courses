# 📋 Специфікація протоколу Raft: стан вузла та інтерфейс RPC

Ця специфікація містить повний технічний контракт розподіленого консенсусного алгоритму Raft: структури внутрішнього стану сервера, формати віддалених викликів процедур (RPC) та точні правила обробки переходів між станами згідно з канонічним описом Дієго Онгаро та Джона Аустерхаута.

## 1. Стан сервера

Кожен вузол кластера підтримує три категорії змінних стану: персистентні (енергонезалежні), леткі загальні та леткі змінні лідера.

### Персистентний стан на всіх серверах
Зберігається на надійному накопичувачі (наприклад, WAL на диску або SSD) перед тим, як вузол надішле відповідь на будь-який вхідний RPC-запит.

| Змінна | Тип | Опис |
| :--- | :--- | :--- |
| `currentTerm` | `uint64` | Останній відомий номер терму (ініціалізується нулем під час першого запуску, монотонно зростає). |
| `votedFor` | `optional<NodeId>` | Ідентифікатор кандидата, за якого даний вузол проголосував у поточному термі (`null`, якщо ще не голосував). |
| `log[]` | `array<LogEntry>` | Послідовність записів журналу; кожен запис містить команду для скінченного автомата та номер терму, коли запис створено лідером. Індексація починається з 1. |

Кожен елемент логу `LogEntry` складається з полів:
- `index` (`uint64`): монотонний порядковий номер запису в лозі (1, 2, 3...);
- `term` (`uint64`): терм лідера, під час якого запис було додано;
- `data` (`bytes`): серіалізована команда для реплікованого скінченного автомата (State Machine).

### Леткий стан на всіх серверах
Зберігається в оперативній пам'яті; відновлюється під час перезапуску вузла.

| Змінна | Тип | Опис |
| :--- | :--- | :--- |
| `commitIndex` | `uint64` | Індекс найвищого запису логу, про який відомо, що він зафіксований більшістю кластера (ініціалізується 0, монотонно зростає). |
| `lastApplied` | `uint64` | Індекс найвищого запису логу, який уже застосовано до локального скінченного автомата (ініціалізується 0, монотонно зростає: `lastApplied ≤ commitIndex`). |

### Леткий стан виключно на лідерах
Повністю переініціалізується щоразу після перемоги кандидата на виборах.

| Змінна | Тип | Опис |
| :--- | :--- | :--- |
| `nextIndex[]` | `map<NodeId, uint64>` | Для кожного сервера — індекс наступного запису логу, який лідер надішле цьому серверу (ініціалізується значенням `leader.lastLogIndex + 1`). |
| `matchIndex[]` | `map<NodeId, uint64>` | Для кожного сервера — індекс найвищого запису логу, про який достеменно відомо, що він успішно реплікований на даний сервер (ініціалізується нулями, монотонно зростає). |

## 2. Віддалені виклики процедур (RPC)

Взаємодія між вузлами в Raft зведена до трьох базових RPC-повідомлень.

### 2.1. RequestVote RPC
Ініціюється кандидатом під час виборів для збору голосів інших вузлів.

#### Аргументи виклику:
- `term` (`uint64`): терм кандидата, який ініціював вибори;
- `candidateId` (`NodeId`): унікальний мережевий ідентифікатор кандидата;
- `lastLogIndex` (`uint64`): індекс останнього запису в лозі кандидата;
- `lastLogTerm` (`uint64`): терм останнього запису в лозі кандидата.

#### Результат повернення:
- `term` (`uint64`): поточний терм вузла-отримувача (для оновлення терму кандидата, якщо він застарів);
- `voteGranted` (`bool`): `true`, якщо вузол віддав свій голос за цього кандидата, інакше `false`.

#### Алгоритм обробки отримувачем:
1. Якщо `term < currentTerm`, повернути `voteGranted = false`.
2. Якщо `term > currentTerm`, оновити `currentTerm = term`, скинути стан до фоловера (`votedFor = null`).
3. Перевірити доступність голосу: `votedFor == null` або `votedFor == candidateId`.
4. Перевірити правило свіжості логу (Election Restriction):
   - Лог кандидата є *не менш свіжим*, ніж лог отримувача, якщо:
     - `lastLogTerm > receiver.lastLogTerm`, **АБО**
     - `(lastLogTerm == receiver.lastLogTerm) AND (lastLogIndex ≥ receiver.lastLogIndex)`.
5. Якщо умови 3 і 4 виконуються — зберегти `votedFor = candidateId` на диск, перезапустити таймер виборів і повернути `voteGranted = true`. Інакше повернути `false`.

### 2.2. AppendEntries RPC
Ініціюється лідером для реплікації записів логу, а також як регулярний сигнал серцебиття (heartbeat), коли масив `entries` порожній.

#### Аргументи виклику:
- `term` (`uint64`): поточний терм лідера;
- `leaderId` (`NodeId`): ідентифікатор лідера (для перенаправлення клієнтських запитів);
- `prevLogIndex` (`uint64`): індекс запису логу, що безпосередньо передує новим записам;
- `prevLogTerm` (`uint64`): терм запису `prevLogIndex`;
- `entries[]` (`array<LogEntry>`): масив нових записів для збереження (порожній для серцебиття; може містити декілька записів для підвищення ефективності);
- `leaderCommit` (`uint64`): поточний `commitIndex` лідера.

#### Результат повернення:
- `term` (`uint64`): `currentTerm` отримувача для оновлення лідера;
- `success` (`bool`): `true`, якщо фоловер містить запис, що відповідає `prevLogIndex` та `prevLogTerm`.

#### Алгоритм обробки отримувачем:
1. **Перевірка терму:** якщо `term < currentTerm`, повернути `success = false`.
2. Якщо `term > currentTerm`, оновити `currentTerm = term`, перейти в роль фоловера (`votedFor = null`).
3. **Скидання таймера:** перезапустити локальний таймер виборів (отримано підтвердження авторитету чинного лідера).
4. **Перевірка відповідності логу (Log Matching Consistency Check):**
   - Якщо локальний лог не містить запису на позиції `prevLogIndex`, повернути `success = false`.
   - Якщо локальний запис на позиції `prevLogIndex` має терм, відмінний від `prevLogTerm`, повернути `success = false`.
5. **Розв'язання конфліктів:** якщо наявний запис конфліктує з новим (однаковий індекс, але різний терм) — видалити цей запис і всі наступні за ним записи з локального логу.
6. **Дописування:** додати будь-які нові записи з масиву `entries`, яких ще немає в локальному лозі, та зафіксувати їх на диску.
7. **Оновлення індексу фіксації:** якщо `leaderCommit > commitIndex`, встановити:
   ```
   commitIndex = min(leaderCommit, index of last new entry)
   ```
8. Повернути `success = true`.

### 2.3. InstallSnapshot RPC
Ініціюється лідером, коли фоловер настільки сильно відстав, що необхідні йому записи логу вже були вилучені з логу лідера в процесі стиснення (Compaction).

#### Аргументи виклику:
- `term` (`uint64`): терм лідера;
- `leaderId` (`NodeId`): ідентифікатор лідера;
- `lastIncludedIndex` (`uint64`): індекс останнього запису, що увійшов у знімок;
- `lastIncludedTerm` (`uint64`): терм останнього запису, що увійшов у знімок;
- `offset` (`uint64`): байтове зміщення фрагмента в бінарному файлі знімка;
- `data[]` (`bytes`): сирі байти фрагмента знімка;
- `done` (`bool`): `true`, якщо це фінальний фрагмент файлу знімка.

#### Результат повернення:
- `term` (`uint64`): поточний терм отримувача.

#### Алгоритм обробки отримувачем:
1. Якщо `term < currentTerm`, негайно повернути відповідь із `currentTerm`.
2. Якщо `offset == 0`, ініціалізувати новий тимчасовий файл знімка.
3. Записати `data[]` у файл знімка за вказаним зміщенням `offset`.
4. Якщо `done == false`, надіслати підтвердження й очікувати наступний фрагмент.
5. Якщо `done == true`:
   - Зберегти файл знімка як актуальний стан;
   - Якщо в локальному лозі існує запис із `index == lastIncludedIndex` та `term == lastIncludedTerm`, зберегти всі записи логу, що йдуть **після** `lastIncludedIndex`, а всі попередні видалити;
   - Якщо такого запису немає — повністю очистити весь локальний лог;
   - Оновити `commitIndex = max(commitIndex, lastIncludedIndex)`;
   - Передати знімок скінченному автомату для повного перезавантаження стану (`lastApplied = lastIncludedIndex`).

## 3. Загальні правила для всіх серверів

### Реакція на терми
- Якщо будь-який RPC-запит або відповідь містить `term T > currentTerm`: встановити `currentTerm = T`, перейти в роль фоловера (`role = Follower`), очистити `votedFor = null`.

### Застосування до скінченного автомата (Apply Loop)
- Якщо `commitIndex > lastApplied`:
  - Інкрементувати `lastApplied`;
  - Передати команду `log[lastApplied].data` реплікованому скінченному автомату;
  - Повернути результат виконання клієнту (якщо запит обслуговується локально).

### Правила для фоловерів
- Відповідати на виклики кандидатів та лідерів.
- Якщо таймаут виборів сплив без отримання `AppendEntries` від чинного лідера або без надання голосу кандидату — перейти в роль Кандидата.

### Правила для кандидатів
- Під час переходу до стану кандидата:
  1. Інкрементувати `currentTerm`;
  2. Проголосувати за себе: `votedFor = selfId`;
  3. Скинути таймер виборів на випадкове значення з діапазону `[T_min, T_max]`;
  4. Розіслати `RequestVote` RPC усім серверам кластера.
- Якщо отримано голоси від більшості серверів кластера (`votesCount > N / 2`) — стати Лідером.
- Якщо отримано `AppendEntries` RPC від нового лідера з `term ≥ currentTerm` — визнати лідера й перейти в роль Фоловера.
- Якщо таймаут виборів сплив знову — розпочати новий раунд виборів (інкрементувати терм, розіслати нові запити).

### Правила для лідерів
- Після обрання: негайно розіслати порожні `AppendEntries` RPC усім серверам для придушення інших виборів; повторювати розсилку серцебиття з інтервалом `T_heartbeat`.
- При отриманні команди від клієнта: додати команду як новий запис у кінець локального логу, розіслати `AppendEntries` усім фоловерам.
- Якщо для певного фоловера `lastLogIndex ≥ nextIndex[peer]`: надіслати `AppendEntries` із записами, починаючи з `nextIndex[peer]`.
  - Якщо виклик успішний: оновити `nextIndex[peer] = prevLogIndex + entries.size() + 1` та `matchIndex[peer] = nextIndex[peer] - 1`.
  - Якщо `AppendEntries` повернув відмову через невідповідність логу: декрементувати `nextIndex[peer]` на 1 (або застосувати оптимізацію швидкого відкочування за конфліктним термом) і повторити спробу.
- **Правило фіксації (§5.4.2):** якщо існує такий індекс `N > commitIndex`, що:
  1. `N > commitIndex`,
  2. Більшість значень `matchIndex[peer] ≥ N`,
  3. Запис логу `log[N].term == currentTerm` (запис належить **поточному** терму лідера),
  то встановити `commitIndex = N`.
