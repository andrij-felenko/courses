# 🧮 Властивості повноти і точності детекторів Чандри — Туега

Ця вставка містить формалізацію аксіоматичних властивостей повноти і точності класів детекторів відмов Чандри — Туега, доведення неможливості ідеального детектора в асинхронній мережі та аналіз консенсусу на базі детектора ◇S. Формальна модель розподіленої системи задається скінченною множиною процесів:

```
Π = {p₁, p₂, ..., pₙ},   де n = |Π| ≥ 2   [скінченна множина вузлів]
```

Дискретний час моделюється множиною невід'ємних цілих чисел `T = {0, 1, 2, ...}`. Цей час використовується виключно зовнішнім спостерігачем для формального аналізу поведінки системи; самі процеси доступу до глобального фізичного часу не мають.

## 1. Патерн відмов і класифікація процесів

Патерн відмов `F` є функцією від часу `T`, яка повертає множину процесів, що зазнали аварійної зупинки (*crash-stop*) до моменту `t`:

```
F: T → 2^Π
∀ t ≤ t': F(t) ⊆ F(t')   [властивість незворотності аварійної зупинки]
```

Множини аварійних та справних процесів для заданого прогону `F` визначаються співвідношеннями:

```
Crashed(F) = ⋃_{t ∈ T} F(t)       [множина аварійних процесів]
Correct(F) = Π \ Crashed(F)       [множина справних процесів]
```

Модуль детектора відмов на кожному процесі `p` у кожен момент часу `t` виводить локальну множину підозрюваних процесів:

```
D_p(t) ⊆ Π                         [поточний список підозрюваних вузлів]
```

## 2. Аксіоматичні властивості повноти (Completeness)

Повнота описує здатність детектора виявляти реальні аварії (властивість живучості, *liveness*).

### Сильна повнота (Strong Completeness, `S_C`)
Кожен аварійний процес зрештою потрапляє у список підозр кожного справного процесу назавжди:

```
∀ p ∈ Crashed(F), ∀ q ∈ Correct(F):
∃ t ∈ T: ∀ t' ≥ t ⇒ p ∈ D_q(t')   [вимога сильної повноти]
```

### Слабка повнота (Weak Completeness, `W_C`)
Кожен аварійний процес зрештою потрапляє у список підозр принаймні одного справного процесу назавжди:

```
∀ p ∈ Crashed(F):
∃ q ∈ Correct(F), ∃ t ∈ T: ∀ t' ≥ t ⇒ p ∈ D_q(t')   [вимога слабкої повноти]
```

## 3. Редукція слабкої повноти до сильної

Будь-який детектор `D` зі слабкою повнотою можна детерміністично перетворити на детектор `D*` із сильною повнотою за допомогою протоколу періодичної розсилки повідомлень.

Процедура на процесі `p`:

```
Ініціалізація на процесі p:
  output_D*_p = ∅

Фоновий цикл розсилки кожні Δ одиниць часу:
  broadcast [SUSPECTS, D_p(now)] до всіх процесів q ∈ Π

Обробка вхідного повідомлення від процесу q:
  suspects_from[q] = S_q
  output_D*_p = ⋃_{k ∈ Π} suspects_from[k]   [об'єднання списків підозр]
```

### Доведення коректності перетворення:
1. Нехай `p ∈ Crashed(F)`. За умовою слабкої повноти `W_C`, існує справний процес `q ∈ Correct(F)`, який після моменту `t₁` постійно має `p ∈ D_q(t)`.
2. Оскільки процес `q` справний, він нескінченно довго надсилає періодичні повідомлення `[SUSPECTS, D_q]` усім процесам.
3. Усі канали зв'язку між справними процесами в асинхронній моделі є надійними, тому кожен справний процес `r ∈ Correct(F)` отримає це повідомлення в деякий момент `t₂ ≥ t₁`.
4. Після моменту `t₂` процес `r` додасть `p` до свого об'єднаного виходу `output_D*_r`, забезпечуючи сильну повноту `S_C`.
5. Якщо початковий детектор `D` не робив помилкових підозр щодо справного процесу `x` на всіх вузлах (сильна точність), то жоден вузол не надішле `x` у своєму повідомленні, і редукований детектор `D*` збереже початковий клас точності.

## 4. Аксіоматичні властивості точності (Accuracy)

Точність обмежує кількість помилкових підозр щодо здорових процесів (властивість безпеки, *safety*).

### 1. Сильна точність (Strong Accuracy, `S_A`)
Жоден справний процес ніколи не підозрюється жодним вузлом:

```
∀ p ∈ Correct(F), ∀ q ∈ Π, ∀ t ∈ T:
p ∉ D_q(t)                         [вимога сильної точності]
```

### 2. Слабка точність (Weak Accuracy, `W_A`)
Існує хоча б один справний процес, який ніколи не підозрюється жодним вузлом:

```
∃ p ∈ Correct(F): ∀ q ∈ Π, ∀ t ∈ T:
p ∉ D_q(t)                         [вимога слабкої точності]
```

### 3. Зрештою сильна точність (Eventually Strong Accuracy, `◇S_A`)
Існує момент стабілізації `t_GST ∈ T` (*Global Stabilization Time*), після якого жоден справний процес не підозрюється жодним справним вузлом:

```
∃ t_GST ∈ T: ∀ t ≥ t_GST, ∀ p ∈ Correct(F), ∀ q ∈ Correct(F):
p ∉ D_q(t)                         [вимога зрештою сильної точності]
```

### 4. Зрештою слабка точність (Eventually Weak Accuracy, `◇W_A`)
Існує момент `t_GST ∈ T` та існує принаймні один справний процес `p`, який після цього моменту ніколи не підозрюється жодним справним процесом:

```
∃ t_GST ∈ T, ∃ p ∈ Correct(F): ∀ t ≥ t_GST, ∀ q ∈ Correct(F):
p ∉ D_q(t)                         [вимога зрештою слабкої точності]
```

## 5. Простір класів детектора Чандри — Туега

Комбінація повноти та точності формує вісім класів:

```
┌───────────────────────────────┬───────────────────────────────┬───────────────────────────────┐
│ Точність / Повнота            │ Сильна повнота (S_C)          │ Слабка повнота (W_C)          │
├───────────────────────────────┼───────────────────────────────┼───────────────────────────────┤
│ Сильна точність (S_A)         │ P  (Perfect — Ідеальний)      │ Q                             │
│ Слабка точність (W_A)         │ S  (Strong — Сильний)         │ W  (Weak — Слабкий)           │
│ Зрештою сильна точність (◇S_A)│ ◇P (Eventually Perfect)       │ ◇Q                            │
│ Зрештою слабка точність (◇W_A)│ ◇S (Eventually Strong)        │ ◇W                            │
└───────────────────────────────┴───────────────────────────────┴───────────────────────────────┘
```

Завдяки алгоритму редукції слабкої повноти до сильної, класи в кожному рядку є еквівалентними:

```
P ≡ Q,    S ≡ W,    ◇P ≡ ◇Q,    ◇S ≡ ◇W
```

## 6. Теорема про неможливість детектора класу P в асинхронній мережі

Чому ідеальний детектор `P` неможливо збудувати в асинхронній моделі?

Нехай існує алгоритм детектора `A`, який гарантує клас `P` (`S_C ∧ S_A`).
1. Розглянемо прогін системи, де вузол `p` зазнав аварії в момент `t = 0`. За умовою сильної повноти `S_C`, через скінченний час `t_crash` справний вузол `q` зобов'язаний вивести `p ∈ D_q(t_crash)`.
2. Тепер побудуємо інший прогін, у якому вузол `p` абсолютно здоровий, але всі його вихідні повідомлення затримуються мережею на час `t_delay > t_crash` (що повністю дозволено асинхронною моделлю).
3. Оскільки стан вузла `q` до моменту `t_crash` залежить лише від отриманих повідомлень, а в обох прогонах від `p` до `q` не надійшло жодного байта, локальні стани вузла `q` в обох прогонах є ідентичними (*нерозрізнюваність станів*).
4. Отже, у другому прогоні алгоритм `A` також виведе `p ∈ D_q(t_crash)`. Проте у другому прогоні `p ∈ Correct(F)`, що прямо порушує умову сильної точності `S_A` (`p ∉ D_q(t)`).
5. Отримане протиріччя доводить, що в асинхронній моделі клас `P` нереалізовний.

## 7. Консенсус за допомогою детектора ◇S: Алгоритм обертового координатора

Алгоритм Чандри — Туега розв'язує задачу консенсусу в асинхронній системі з детектором `◇S` за умови, що кількість відмов менша за більшість вузлів:

```
f < n / 2                          [вимога більшості кворуму]
```

Алгоритм виконується раундами `r = 1, 2, 3, ...`. У кожному раунді `r` процес `c = (r mod n) + 1` призначається координатором.

Фази кожного раунду:

```
Фаза 1: Усі процеси надсилають координатору c свої поточні оцінки (estimate, timestamp).

Фаза 2: Координатор c очікує (n - f) відповідей більшості,
        обирає значення з найбільшою міткою часу ts і розсилає пропозицію [PROPOSE, v_max].

Фаза 3: Процеси паралельно очікують пропозицію від c або включення c у список підозр D_p:
        - Якщо пропозиція надійшла:
            Процес фіксує оцінку v_p = v_max, ts_p = r
            Надсилає координатору c повідомлення [ACK]
        - Якщо координатор c потрапив у детектор підозр D_p:
            Процес надсилає [NACK] і переходить до наступного раунду.

Фаза 4: Якщо координатор c отримав більшість [ACK], він розсилає остаточне рішення [DECIDE, v_max].
```

### Інваріанти коректності (Safety) та завершення (Liveness):

* **Інваріант безпеки (Agreement):** Навіть якщо детектор робить нескінченно багато помилок до моменту `t_GST`, два процеси ніколи не приймуть різні рішення. Це гарантується перетином кворумів більшості: якщо координатор зафіксував рішення `v` у раунді `r`, будь-який наступний координатор у раунді `r' > r` обов'язково отримає у Фазі 1 мітку часу `ts ≥ r` хоча б від одного вузла з кворуму Фази 4 і буде змушений запропонувати те саме значення `v`.
* **Інваріант завершення (Liveness):** За визначенням класу `◇S`, після моменту `t_GST` існує справний процес `p* ∈ Correct(F)`, якого **жоден справний процес більше ніколи не підозрює**. Коли номер раунду досягне `r*`, де координатором стане `p*`, усі справні процеси у Фазі 3 дочекаються його пропозиції `[PROPOSE, v]`, координатор збере більшість `[ACK]` і кластер успішно зафіксує консенсус.
