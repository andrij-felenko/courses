# 📜 Від порятунку LiveJournal до серверів структур даних: історія Memcached та Redis

У 2003 році блог-платформа LiveJournal зіткнулася з кризою масштабування: реляційна база даних MySQL на одному сервері захлиналася від потоку читань. Кожне оновлення стрічки новин вимагало десятків складних SQL-запитів із вибірками та з'єднаннями таблиць. Апаратні диски не встигали переміщати магнітні головки, дискові черги зростали експоненційно, а час відповіді сторінок перевищував десятки секунд. Збільшення кількості серверів застосунків лише погіршувало ситуацію: додаткові процеси створювали ще більше паралельних з'єднань до єдиної бази даних.

Бред Фіцпатрік (англ. *Brad Fitzpatrick*), засновник LiveJournal і компанії Danga Interactive, зрозумів, що більшість даних на читання є незмінними між редагуваннями, але повторно обчислюються щомиті. Додавання окремих локальних кешів у пам'ять кожного вебсервера не рятувало: кеші швидко розсинхронізовувалися, пам'ять дублювалася, а коефіцієнт влучання (англ. *cache hit ratio*) стрімко падав зі зростанням пулу вебсерверів.

```
Криза архітектури LiveJournal (2003):
[Вебсервер 1] ──┐
[Вебсервер 2] ──┼── (сотні SQL-запитів/с) ──► [Центральна БД MySQL] ──► [Дисковий вузький перешийок]
[Вебсервер N] ──┘                                                          (I/O Bottleneck: 100% Disk Busy)
```

## Народження Memcached: тріумф тупого сервера й розумного клієнта

Фіцпатрік сформулював радикальний архітектурний принцип: сервер кешу має бути максимально простим, ненадійним за задумом (англ. *ephemeral*) і повністю позбавленим знань про топологію системи. Сервер не повинен знати про інші сервери, не повинен реплікувати дані та не повинен витрачати процесорний час на координацію чи консенсус.

Перша версія Memcached була написана Фіцпатріком мовою Perl за кілька днів у травні 2003 року. Вона довела життєздатність концепції, але інтерпретатор Perl споживав забагато пам'яті на службові структури та не витримував десятків тисяч мережевих пакетів на секунду. Невдовзі Анатолій Воробей та Бред Фіцпатрік переписали Memcached мовою C, використавши бібліотеку `libevent` для неблокувального введення-виведення на основі системних викликів `epoll` та `kqueue`.

Уся інтелектуальна робота з шардингу даних була перенесена на рівень клієнтської бібліотеки. Клієнт брав ключ, обчислював хеш і самостійно обирав TCP-з'єднання з конкретним вузлом. Якщо вузол падав, система сприймала це як звичайний промах кешу (англ. *cache miss*), забирала свіжі дані з реляційної бази й записувала їх на доступні сервери. Ця модель згодом лягла в основу концепції [стратегій кешування](topic:sf-data/caching-strategies), зокрема патерну Cache-Aside.

Memcached вирішив проблему ефективного використання оперативної пам'яті за допомогою власного аллокатора фіксованих блоків (англ. *slab allocator*), що повністю ліквідував зовнішню фрагментацію пам'яті під час мільйонів операцій перезапису.

```
Архітектурний зсув Memcached:
[Клієнтський застосунок] ── (Кільце хешів Ketama) ──┬──► [Memcached Вузол 1 (RAM)]
                                                    ├──► [Memcached Вузол 2 (RAM)]
                                                    └──► [Memcached Вузол 3 (RAM)]
(Жодної реплікації, жодного зв'язку між вузлами кешу)
```

## Обмеження Memcached та межа простих рядків

До кінця 2000-х років Memcached став стандартом де-факто для індустрії. Його впровадили Facebook, Twitter, YouTube, Wikipedia та Reddit. Facebook створив найбільшу у світі інсталяцію Memcached, що об'єднувала тисячі серверів і обслуговувала мільярди запитів на секунду.

Проте разом із масштабуванням оголилися фундаментальні обмеження моделі «непрозорий ключ — сирий бінарний блоб» (англ. *opaque string/blob*):

1. **Неможливість часткової модифікації.** Щоб додати один елемент до списку з 1000 друзів користувача, застосунок мусив вичитати всі 100 КБ серіалізованого масиву по мережі, десеріалізувати його в пам'яті вебсервера, додати запис, знову серіалізувати та відправити всі 100 КБ назад через мережу.
2. **Мережевий оверхед та гонки оновлень.** Масові операції читання-модифікації-запису породжували стан гонитви (англ. *race conditions*), що вимагало складних протоколів оптимістичного блокування на основі CAS (англ. *Check-And-Set*).
3. **Відсутність збереження на диск.** Перезапуск вузла кешу спричиняв миттєве зникнення всіх даних («холодний старт»), що провокувало лавинний ефект [гримучої отари](topic:sf-distributed/thundering-herd) на первинні бази даних.

## 2009 рік: Сальваторе Санфіліппо та створення Redis

У 2009 році італійський розробник Сальваторе Санфіліппо (відомий під псевдонімом *antirez*) працював над сервісом веб-аналітики в реальному часі LLOOGG. Йому було потрібно зберігати журнал останніх дій відвідувачів для тисяч сайтів. Реляційні бази даних не встигали виконувати постійні операції вставки та підрізання списків (SQL `INSERT` та `DELETE`), а Memcached не дозволяв ефективно підтримувати впорядковані списки фіксованого розміру без пересилання всього обсягу даних по мережі.

Санфіліппо вирішив створити спеціалізований мережевий сервер, який працював би в оперативній пам'яті, але оперував не просто сирими рядками, а повноцінними структурами даних: списками (Lists), хеш-таблицями (Hashes), множинами (Sets) та впорядкованими множинами (Sorted Sets). Так народився Redis (акронім від *REmote DIctionary Server*).

```
Еволюція абстракції кешування:

Memcached (2003):
Ключ "user:123:friends" ──► [ 0x1F 0x8B 0x08 ... (Непрозорий бінарний стиснений блоб) ]

Redis (2009):
Ключ "user:123:friends" ──► Sorted Set (ZSET):
                            ├── ("alice", score=1692538400)
                            ├── ("bob",   score=1692538420)
                            └── ("carol", score=1692538490)
                            (Атомарна команда ZADD виконується на боці сервера за O(log N))
```

## Ключові концептуальні інновації Redis

1. **Однопотоковий цикл обробки подій (Single-threaded Event Loop).** Санфіліппо відмовився від багатопотокової моделі з м'ютексами на користь єдиного швидкого циклу `aeEvent` на основі `epoll`. Оскільки всі дані трималися в пам'яті й доступ займав частки мікросекунди, один потік процесора без накладних витрат на синхронізацію та перемикання контексту обробляв понад 100 000 операцій на секунду. Кожна команда стала строго атомарною за самою природою виконання.
2. **Асинхронна персистентність (RDB та AOF).** Redis надав можливість скидати знімки пам'яті на диск через `fork()` (RDB) або вести журнал додавання операцій (AOF — *Append Only File*), що вирішило проблему холодного старту.
3. **Вбудована реплікація та еволюція кластеризації.** Від простої топології [лідер-фоловер](topic:sf-distributed/replication-leader-follower) із ручним перемиканням Redis пройшов шлях до автоматичного моніторингу через Redis Sentinel (2012) і повноцінного шардованого Redis Cluster (2015), що розділив простір ключів на 16384 дискретні хеш-слоти.

## Порівняльний підсумок еволюції

Історія розподілених кешів демонструє дві різні інженерні відповіді на виклик продуктивності:

| Властивість | Memcached (2003) | Redis (2009+) |
| :--- | :--- | :--- |
| **Архітектурна філософія** | Shared-Nothing, гранично простий сервер без стану топології | Сервер структур даних із розвиненими типами та сервісами |
| **Модель багатопотоковості** | Багатопотоковий сервер (окремі воркери на з'єднання) | Однопотокове ядро виконання + багатопотоковий I/O |
| **Керування пам'яттю** | Власний Slab Allocator (захист від фрагментації) | `jemalloc` / `libc malloc` з активною дефрагментацією |
| **Маршрутизація ключів** | Виключно клієнтська (Ketama Consistent Hashing) | Серверний кластер (16384 хеш-слоти) або проксі |
| **Персистентність і реплікація** | Відсутні (чистий ефемерний кеш) | Асинхронна реплікація, RDB-знімки, AOF-журнал |

Обидві системи витримали перевірку часом: Memcached залишається неперевершеним за простотою та швидкістю вибірки сирих об'єктів у багатопотокових середовищах із гігантськими обсягами пам'яті, тоді як Redis став фундаментом для складної бізнес-логіки в оперативній пам'яті, лічильників реального часу, лімітерів запитів та розподілених блокувань.
