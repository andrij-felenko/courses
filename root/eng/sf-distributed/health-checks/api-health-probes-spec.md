# 📋 Специфікація контрактів перевірки: IETF HTTP Health Draft, gRPC Health Checking Protocol v1 та Kubernetes Probes

У розподілених системах стандартизація форматів і протоколів перевірки працездатності є критичною умовою сумісності між мікросервісами, хмарними балансувальниками та оркестраторами. Якщо кожен сервіс повертає власний довільний формат JSON або використовує нестандартні коди помилок, інфраструктурні інструменти не можуть автоматизувати маршрутизацію трафіку та ізоляцію збоїв.

Кожен протокол взаємодії висуває власні вимоги до швидкості, формату серіалізації даних та накладних витрат. Нижче наведено вичерпну технічну специфікацію чотирьох загальноприйнятих галузевих стандартів перевірки здоров'я: проекту IETF для HTTP REST API, протоколу gRPC Health Checking v1, схеми конфігурації Kubernetes Probes та специфікації Envoy Outlier Detection.

## 1. IETF HTTP Health Check Response Format (draft-inadarei-api-health-check-06)

Специфікація IETF визначає стандартизований MIME-тип `application/health+json` та структуру JSON-відповіді для HTTP REST API. Головна мета цього стандарту — надати машинам та операторам єдиний синтаксис для розрізнення повного здоров'я, попередження про деградацію та критичної відмови.

### Семантика HTTP-заголовків та кодів стану

Ендпоінт перевірки здоров'я зобов'язаний суворо керувати кешуванням відповідей. Оскільки стан вузла динамічно змінюється кожні кілька секунд, проміжні проксі-сервери, CDN або локальні клієнтські кеші в жодному разі не повинні зберігати застарілі відповіді.

Застосунок повинен повертати такі обов'язкові HTTP-заголовки:
```http
HTTP/1.1 200 OK
Content-Type: application/health+json
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
Expires: 0
```

Мапінг внутрішнього статусу на числові коди HTTP-відповіді виконується за такими суворими правилами:
1. **Статус `pass` (HTTP `200 OK`):** усі локальні компоненти функціонують у межах норми. Вузол готовий приймати 100% номінального навантаження.
2. **Статус `warn` (HTTP `200 OK`):** вузол працездатний, проте окремі метрики наблизилися до критичних меж (наприклад, дисковий простір заповнено на 85% або час відповіді локальної пам'яті зріс). Повернення коду `200` гарантує, що балансувальник не відключить вузол аварійно, але системи моніторингу зможуть згенерувати попереджувальне сповіщення (Alert).
3. **Статус `fail` (HTTP `503 Service Unavailable`):** критичний збій локальної підсистеми. Балансувальник зобов'язаний негайно вилучити екземпляр із пулу маршрутизації. Заборонено повертати коди `500 Internal Server Error` або `404 Not Found`, оскільки код `503` однозначно вказує на тимчасову неготовність сервісу до обслуговування.

### Схема кореневого об'єкта відповіді

```json
{
  "status": "pass",
  "version": "1.4.2",
  "releaseId": "2026.08.15-rel42",
  "notes": ["Система працює в штатному режимі"],
  "output": "All internal subsystems operational",
  "serviceId": "orders-service-eu-west-1a-pod-89bf",
  "description": "Сервіс обробки та валідації замовлень",
  "details": {
    "memory:heap": [
      {
        "componentType": "system",
        "observedValue": 256,
        "observedUnit": "MB",
        "status": "pass",
        "time": "2026-08-20T12:00:00Z"
      }
    ],
    "storage:local_disk": [
      {
        "componentType": "system",
        "observedValue": 82,
        "observedUnit": "percent",
        "status": "warn",
        "output": "Дисковий простір заповнено на 82%",
        "time": "2026-08-20T12:00:00Z"
      }
    ]
  },
  "links": {
    "about": "https://api.internal/orders/v1/docs",
    "metrics": "https://api.internal/orders/v1/metrics"
  }
}
```

### Поля специфікації IETF

| Поле | Тип | Обов'язкове | Опис та допустимі значення |
| :--- | :--- | :--- | :--- |
| `status` | `string` | **Так** | Загальний статус вузла (`pass`, `fail`, `warn`). |
| `version` | `string` | Ні | Семантична версія публічного API або сервісу (наприклад, `1.4.2`). |
| `releaseId` | `string` | Ні | Ідентифікатор конкретного білду/релізу (хеш коміту Git або номер релізу). |
| `serviceId` | `string` | Ні | Унікальний ідентифікатор запущеного екземпляра в кластері. |
| `description`| `string` | Ні | Людинозрозумілий опис призначення сервісу. |
| `details` | `object` | Ні | Словник перевірок внутрішніх підсистем. Ключ формується як `<ім'я>:<тип>`. |
| `output` | `string` | Ні | Додатковий текстовий вивід (повідомлення про помилку чи діагностика). |

### Структура елемента підсистеми (`details`)

Об'єкт `details` дозволяє передавати структуровану діагностику за окремими векторами: пам'ять, файлові дескриптори, черги та локальні сховища.

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `componentType` | `string` | Тип ресурсу: `system`, `datastore`, `component`, `network`. |
| `status` | `string` | Статус підсистеми: `pass`, `fail`, `warn`. |
| `observedValue` | `number` / `string` | Виміряне числове або строкове значення метрики. |
| `observedUnit` | `string` | Одиниця вимірювання (`MB`, `percent`, `ms`, `connections`). |
| `time` | `string` | Мітка часу ISO 8601 у форматі UTC (`YYYY-MM-DDTHH:MM:SSZ`). |

## 2. gRPC Health Checking Protocol v1

Для високопродуктивних міжсервісних комунікацій на базі протоколу HTTP/2 та бінарної серіалізації Protocol Buffers використання звичайного тексту JSON породжує невиправдані накладні витрати на парсинг. Офіційний стандарт **gRPC Health Checking Protocol v1** стандартизує бінарний сервіс під системною назвою `grpc.health.v1.Health`.

### Специфікація Protocol Buffers (IDL)

```protobuf
syntax = "proto3";

package grpc.health.v1;

enum ServingStatus {
  UNKNOWN = 0;
  SERVING = 1;
  NOT_SERVING = 2;
  SERVICE_UNKNOWN = 3;
}

message HealthCheckRequest {
  string service = 1;
}

message HealthCheckResponse {
  ServingStatus status = 1;
}

service Health {
  // Одноразова перевірка здоров'я (Unary RPC)
  rpc Check(HealthCheckRequest) returns (HealthCheckResponse);

  // Потокове спостереження за зміною статусу в реальному часі (Server Streaming)
  rpc Watch(HealthCheckRequest) returns (stream HealthCheckResponse);
}
```

### Механіка взаємодії: Check проти Watch

Протокол надає два взаємодоповнюючі методи:

1. **Метод `Check` (Unary RPC):**
   * Клієнт надсилає повідомлення `HealthCheckRequest`. 
   * Якщо поле `service` містить порожній рядок (`""`), сервер оцінює загальний стан процесу в цілому.
   * Якщо поле `service` містить повне кваліфіковане ім'я пакета та сервісу (наприклад, `ecommerce.v1.OrderProcessing`), сервер повертає статус готовності виключно цієї бізнес-сутності.
   * Якщо запитаний сервіс не зареєстрований на сервері, метод повертає канонічний код помилки gRPC `NOT_FOUND` (код 5), а не статус `NOT_SERVING`.
2. **Метод `Watch` (Server Streaming RPC):**
   * Клієнт відкриває довгоживучий односпрямований потік повідомлень. Сервер негайно надсилає поточний статус `ServingStatus`, після чого утримує потік відкритим.
   * Щойно стан сервера змінюється (наприклад, під час граційного вимкнення сервер перемикається з `SERVING` на `NOT_SERVING`), сервер асинхронно пушить нове повідомлення `HealthCheckResponse` у відкритий потік.
   * Це повністю усуває необхідність постійного опитування (polling), зменшує споживання процесорного часу та знижує час реакції клієнтів на збої до часток мілісекунди.

### Інтеграція з клієнтським балансуванням gRPC

Статуси `ServingStatus` безпосередньо керують внутрішнім автоматом станів клієнтських підканалів (SubChannels) у бібліотеці gRPC:
* Отримання `SERVING` переводить підканал у стан `READY`, дозволяючи алгоритму балансування (Round Robin або Pick First) призначати на нього виклики.
* Отримання `NOT_SERVING` переводить підканал у стан `TRANSIENT_FAILURE`, тимчасово виключаючи сокет із вибору без фізичного розриву базового TCP-з'єднання HTTP/2.

## 3. Схема Kubernetes Probes (v1.Probe PodSpec)

В оркестраторі Kubernetes життєвий цикл контейнера регулюється трьома типами проб, описаними у декларативній структурі `v1.Probe`. Кожна проба виконується локальним демоном `kubelet` на тому самому фізичному вузлі, де запущено под.

### Механізми зондування та їх системна ціна

`kubelet` підтримує чотири механізми перевірки, які суттєво відрізняються за впливом на системні ресурси:

1. **`httpGet`:** `kubelet` відкриває TCP-з'єднання на вказаний порт пода і надсилає HTTP GET-запит. Коди від `200` до `399` трактуються як успіх. Це найефективніший і найпоширеніший метод для вебзастосунків.
2. **`tcpSocket`:** виконується спроба відкриття сокета на рівні Layer 4. Якщо TCP 3-way handshake завершено успішно, проба зараховується.
3. **`grpc`:** нативна перевірка за стандартом `grpc.health.v1.Health`. `kubelet` встановлює gRPC-з'єднання та викликає метод `Check`.
4. **`exec`:** запуск довільної команди всередині простору назв контейнера через механізм ядра `cgroups` та `namespaces`.
   * ⚠️ **Архітектурне застереження:** виклик `exec` є надзвичайно ресурсомістким. Кожна перевірка змушує ядро Linux викликати системні виклики `fork()` та `execve()`, виділяти новий простір процесів PID, завантажувати бінарний файл (наприклад, `/bin/sh` або утиліту `curl`) і створювати таблицю сторінок пам'яті. При періоді опитування 2 секунди для 50 контейнерів на одній машині ядро витрачатиме до 30% CPU виключно на порожнє створення короткоживучих процесів.

### Повний YAML-маніфест та параметри

```yaml
spec:
  containers:
    - name: backend-api
      image: registry.internal/backend:v2.1.0
      
      # 1. Проба запуску: блокує liveness/readiness під час старту
      startupProbe:
        httpGet:
          path: /healthz/startup
          port: 8080
          httpHeaders:
            - name: X-Probe-Type
              value: startup
        initialDelaySeconds: 2
        periodSeconds: 3
        timeoutSeconds: 2
        failureThreshold: 30    # Дозволяє стартувати до 30 * 3 = 90 секунд
        successThreshold: 1

      # 2. Проба живості: виявляє deadlock і вбиває процес (SIGKILL)
      livenessProbe:
        httpGet:
          path: /healthz/liveness
          port: 8080
        initialDelaySeconds: 0
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 3     # Рестарт після 3 послідовних збоїв (30 секунд)
        successThreshold: 1

      # 3. Проба готовності: вмикає/вимикає трафік на балансувальнику
      readinessProbe:
        httpGet:
          path: /healthz/readiness
          port: 8080
        initialDelaySeconds: 0
        periodSeconds: 5
        timeoutSeconds: 2
        failureThreshold: 2     # Вилучення з ендпоінтів після 2 збоїв (10 с)
        successThreshold: 2     # Повернення в ротацію після 2 успіхів поспіль
```

### Таблиця параметрів налаштування проб

| Параметр | Тип | За замовчуванням | Опис і рекомендовані межі |
| :--- | :--- | :--- | :--- |
| `initialDelaySeconds` | `int` | `0` | Затримка перед першим запуском проби після старту контейнера. При наявності `startupProbe` встановлюється в `0`. |
| `periodSeconds` | `int` | `10` | Інтервал між послідовними запусками проби. Для readiness рекомендується `3–5 с`, для liveness `10–15 с`. |
| `timeoutSeconds` | `int` | `1` | Час очікування відповіді. Якщо сервер не відповів за цей час, спроба вважається проваленою. Рекомендовано `1–3 с`. |
| `failureThreshold` | `int` | `3` | Кількість послідовних збоїв для переходу у стан `Unhealthy`. |
| `successThreshold` | `int` | `1` | Кількість послідовних успіхів для повернення у стан `Healthy`. Для liveness та startup завжди строго `1`. |
| `terminationGracePeriodSeconds` | `int` | `30` | Час у секундах, який дається процесу на коректне завершення роботи після збою liveness-проби. |

## 4. Специфікація Envoy Outlier Detection (Пасивне спостереження)

У високопродуктивному проксі-сервері Envoy конфігурація пасивного виявлення аномалій задається на рівні опису кластера цільових бекендів (`envoy.config.cluster.v3.OutlierDetection`).

### Специфікація конфігурації

```yaml
clusters:
  - name: payment_service_cluster
    connect_timeout: 0.25s
    type: STRICT_DNS
    lb_policy: ROUND_ROBIN
    outlier_detection:
      # Послідовні помилки 5xx для евікції
      consecutive_5xx: 5
      enforcing_consecutive_5xx: 100
      
      # Період оцінки стану
      interval: 10s
      
      # Базовий час ізоляції (охолодження)
      base_ejection_time: 30s
      
      # Максимальний відсоток вилучених екземплярів
      max_ejection_percent: 50
      
      # Поріг паніки для кластера
      common_lb_config:
        healthy_panic_threshold:
          value: 50.0
```

### Поля конфігурації Envoy Outlier Detection

| Поле | Тип | Опис та поведінка |
| :--- | :--- | :--- |
| `consecutive_5xx` | `uint32` | Кількість послідовних відповідей із кодом `5xx`, після якої екземпляр негайно вилучається з таблиці маршрутизації (типово `5`). |
| `enforcing_consecutive_5xx` | `uint32` | Відсоток випадків (0–100%), коли правило `consecutive_5xx` реально вилучає вузол. Значення менше 100 дозволяє тестувати правила в тіньовому режимі. |
| `interval` | `Duration` | Періодичність перевірки статистики аномалій (за замовчуванням `10s`). |
| `base_ejection_time` | `Duration` | Базова тривалість ізоляції вузла (за замовчуванням `30s`). При повторних порушеннях час множиться на лічильник попередніх евікцій. |
| `max_ejection_percent` | `uint32` | Максимальний відсоток вузлів кластера, які дозволено одночасно ізолювати (за замовчуванням `10%`, у критичних кластерах піднімають до `50%`). |
| `healthy_panic_threshold` | `Percent` | Поріг паніки: якщо відсоток здорових вузлів опускається нижче цього значення (наприклад, 50%), Envoy ігнорує статуси здоров'я і балансує запити на всі хости кластера. |
