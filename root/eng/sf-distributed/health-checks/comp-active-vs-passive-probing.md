# 🔌 Активне зондування проти пасивного спостереження (Outlier Detection): порівняння механізмів виявлення несправностей

У розподілених системах балансувальник навантаження або сервісна сітка (Service Mesh) мають вирішувати, на які саме екземпляри бекенда безпечно спрямовувати запити користувачів. Якщо спрямувати запит на екземпляр, що завис або повертає помилки, користувач отримає збій, а загальна доступність системи (SLA) знизиться.

Для прийняття цього рішення інфраструктура використовує два діаметрально протилежні підходи: **активне зондування (Active Probing / Synthetic Polling)** та **пасивне спостереження (Passive Probing / Outlier Detection)**.

Розгляньмо внутрішні механізми обох підходів, їхню математичну ціну для мережі та правила їх гібридного поєднання.

## 1. Активне зондування (Active Probing)

Активне зондування працює за моделлю періодичного опитування (Pull Model): зовнішній агент моніторингу, балансувальник навантаження (HAProxy, Nginx, AWS ALB) або оркестратор (Kubernetes Kubelet) за таймером надсилає штучні (синтетичні) запити до кожного зареєстрованого екземпляра.

```
[Балансувальник] ──(HTTP GET /healthz кожні 5 с)──> [Бекенд-екземпляр]
[Балансувальник] <──(200 OK / 503 Service Unavail)── [Бекенд-екземпляр]
```

### Механіка роботи
1. **Періодичний таймер (`interval` / `periodSeconds`):** кожні `T` секунд балансувальник формує тестовий пакет (TCP SYN, HTTP GET або gRPC Health Check).
2. **Очікування відповіді (`timeout` / `timeoutSeconds`):** якщо бекенд не відповів за час `t_timeout`, спроба вважається проваленою.
3. **Лічильник послідовних збоїв (`failureThreshold`):** щоб випадковий сплеск латентності не спричинив хибне вилучення, статус змінюється на `Unhealthy` лише після `k` невдалих перевірок поспіль (зазвичай `k = 3`).
4. **Лічильник відновлення (`successThreshold`):** після відновлення бекенд не повертається в ротацію миттєво; він має відповісти успішно `m` разів поспіль (зазвичай `m = 2`), що запобігає флапінгу (миготінню статусу).

### Проблема шторму перевірок (Probe Storm)
Головний архітектурний недолік активного зондування виявляється при масштабуванні кількості клієнтів або балансувальників.

Якщо в системі працює `N` клієнтських проксі або балансувальників, які опитують `M` бекендів з інтервалом `T` секунд, сумарна кількість синтетичних запитів на секунду (`RPS_probes`) становить:

```
RPS_probes = (N · M) / T
```

При 200 проксі-вузлах Envoy, 100 бекенд-інстансах і періоді опитування 2 секунди:
```
RPS_probes = (200 · 100) / 2 = 10 000 запитів/с
```
Бекенди змушені витрачати 10 000 RPS обчислювальних ресурсів CPU та пам'яті виключно на обробку синтетичних перевірок здоров'я, ще до надходження першого реального запиту користувача.

### Сліпа зона: фальшивий позитив (False Positive Health)
Синтетичний запит `/healthz` зазвичай є легкою операцією, яка повертає статичний рядок. Проте реальні бізнес-маршрути застосунку виконують складну логіку, виділяють великі обсяги пам'яті та використовують пул потоків.

Якщо пул потоків обробки бізнес-логіки повністю заблокований у Deadlock, а легкодоступний системний ендпоінт `/healthz` обслуговується окремим системним потоком, активна проба повертатиме статус `200 OK`. Балансувальник вважатиме вузол абсолютно здоровим і продовжуватиме спрямовувати на нього користувачів, чиї запити зависатимуть назавжди.

## 2. Пасивне спостереження (Passive Probing / Outlier Detection)

Пасивне спостереження (виявлення викидів або аномалій) працює без створення жодного штучного мережевого пакета. Балансувальник навантаження або Sidecar-проксі аналізує виключно потік *реальних запитів клієнтів*, які проходять крізь нього в процесі нормальної експлуатації системи.

```
[Клієнт] ──(Реальний RPC)──> [Envoy Proxy] ──(Реальний RPC)──> [Бекенд 1] (200 OK)
                                            ──(Реальний RPC)──> [Бекенд 2] (500 Error!)
                                                                  └─> [Лічильник 5xx++]
```

### Алгоритми виявлення аномалій

Сучасні проксі (Envoy, Traefik, Nginx Plus) реалізують кілька стратегій пасивного аналізу:

#### А. Послідовні помилки сервера (Consecutive 5xx / Gateway Errors)
Проксі підраховує кількість поспіль отриманих помилок класу `5xx` (або розривів TCP-з'єднань `ECONNRESET`) від конкретного бекенда. Щойно лічильник досягає порогового значення (наприклад, `consecutive_5xx = 5`), екземпляр негайно виштовхується (**Ejection**) з пулу маршрутизації.

#### Б. Послідовні помилки шлюзу (Consecutive Gateway Errors)
Фільтруються лише помилки мережевого рівня та таймаутів: `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`. Це дозволяє відрізнити помилки бізнес-логіки (наприклад, невалідні вхідні дані, які повернули `500`) від реального падіння самого сервера.

#### В. Статистичний аналіз частки успіху (Success Rate Outlier Detection)
Проксі агрегує статистику за фіксований ковзний інтервал (наприклад, кожні 100 запитів). Якщо середній відсоток успішних відповідей по всьому кластеру становить 99%, а один конкретний екземпляр повертає лише 85% успішних відповідей (його показник відхиляється від середнього значення кластера на `k` стандартних відхилень), цей екземпляр класифікується як аномальний і тимчасово вилучається.

### Механіка виштовхування (Ejection Algorithm)
1. **Вилучення з ротації:** вага аномального екземпляра у таблиці балансування встановлюється в 0. Нові запити користувачів на нього не надходять.
2. **Базовий час охолодження (`base_ejection_time`):** екземпляр залишається ізольованим протягом визначеного часу (за замовчуванням 30 секунд).
3. **Експоненційне штрафування:** якщо після повернення в ротацію екземпляр повторно фіксується як аномальний, час його ізоляції множиться на кількість попередніх вилучень:
```
T_ejection = base_ejection_time · Ejection_Count
```
4. **Обмеження максимальної частки вилучення (`max_ejection_percent`):** щоб захистити кластер від повного спустошення, пасивний механізм має жорстке обмеження: сумарно не може бути вилучено більше ніж певний відсоток екземплярів (зазвичай максимум 10–50%).

## 3. Порівняльний аналіз характеристик

| Критерій | Активне зондування (Active Probing) | Пасивне спостереження (Outlier Detection) |
| :--- | :--- | :--- |
| **Накладні витрати на мережу** | Високі: генерує постійний штучний трафік `(N · M) / T` | Нульові: аналізує лише реальний клієнтський трафік |
| **Швидкість виявлення збою** | Повільна: затримка дорівнює інтервалу перевірки `T · k` | Миттєва: спрацьовує одразу після `k` помилкових відповідей |
| **Виявлення «сірих відмов»** | Сліпе: легкий `/healthz` може працювати при зависанні бізнесу | Бездоганне: фіксує деградацію реальних користувацьких RPC |
| **Поведінка без навантаження** | Працює стабільно: статус відомий навіть без клієнтів | Неактивне: за відсутності запитів не може оцінити здоров'я |
| **Ціна для користувача** | 0 помилок у користувачів (якщо збій виявлено заздалегідь) | Перші `k` запитів користувачів зазнають помилки перед евікцією |
| **Перевірка відновлення** | Прозора: успішні синтетичні проби повертають статус | Потребує періоду охолодження та подачі пробного трафіку |

## 4. Гібридна архітектура: сучасний еталон надійності

Жоден із двох методів не є самодостатнім на 100%. Тому в сучасних високонавантажених системах (Envoy Proxy, Kubernetes з Istio/Linkerd, Nginx Plus) використовується **гібридна модель**:

1. **Активне зондування низької частоти:** 
   * Використовується оркестратором Kubernetes (`startupProbe`, `readinessProbe`) для верифікації первинної ініціалізації контейнера перед відкриттям трафіку.
   * Використовується балансувальником із великим періодом (наприклад, кожні 15–30 секунд) як фоновий контроль фонової доступності вузлів за відсутності живого трафіку.
2. **Пасивне виявлення викидів високої швидкості:**
   * Працює на рівні зворотного проксі для захисту від раптових деградацій у режимі реального часу.
   * Миттєво виштовхує екземпляри, які почали повертати `502/503` або повільні відповіді, не чекаючи наступного раунду активного опитування.

Така комбінація гарантує, що нові контейнери не отримають трафік до повного прогріву, а робочі вузли будуть захищені від раптових каскадних помилок без перевантаження мережі штормом синтетичних перевірок.
