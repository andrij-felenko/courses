# 🧮 Математичний аналіз складності та колізій у деревах Меркла

Без кількісного аналізу комунікаційної складності, ймовірності колізій, розподілу розбіжностей за урновими моделями, багатостороннього звіряння та порівняння з іншими алгебраїчними структурами неможливо математично обґрунтувати параметри анти-ентропійного відновлення та розрахувати мережеві й дискові витрати кластера.

---

## 1. Постановка задачі та формальна модель

Нехай дві репліки `A` та `B` відповідають за спільний діапазон простору токенів, у якому сумарно зберігається `N` записів (`|S_A| ≈ |S_B| ≈ N`). Кожен елемент `e ∈ S` є кортежем із трьох компонентів:
- `k` — первинний ключ (або токен ключа в числовому просторі `[0, 2⁶⁴ - 1]`);
- `v` — значення або набір колонок даних;
- `t` — монотонна часова мітка останньої модифікації (timestamp) або векторна версія.

Множина неузгоджених записів (симетрична різниця) позначається через `Δ`:

```
Δ = (S_A \ S_B) ∪ (S_B \ S_A)
d = |Δ|
```

де `d` — точна кількість несинхронізованих або відсутніх записів (`0 ≤ d ≤ 2N`). Відносна частка неузгодженості позначається як `p = d / N` (`0 ≤ p ≤ 1`).

Для усунення розбіжностей система має вирішити дві взаємопов'язані задачі:
1. **Задача діагностики (Localization):** знайти підмножину ключів або діапазонів токенів, що містять елементи з `Δ`, мінімізувавши кількість переданих мережею службових байтів метаданих `C_diag`.
2. **Задача передачі даних (Streaming):** передати реальні записи для знайдених діапазонів, витративши `C_data` байтів.

Загальні мережеві витрати синхронізації становлять `C_total = C_diag + C_data`.

## 2. Комунікаційна складність: наївний обмін проти дерева Меркла

### 2.1. Наївний підхід (Full Digest Exchange)

У наївній схемі репліка `A` формує впорядкований масив пар `(k_i, Hash(e_i))` для всіх `N` локальних записів і передає його репліці `B`.

Нехай розмір ключа становить `S_key` байтів, а розмір хешу — `b` байтів (для Murmur3-128 `b = 16`, для SHA-256 `b = 32`).

Тоді обсяг переданих діагностичних метаданих дорівнює:

```
C_diag_naive = N · (S_key + b)
```

При `N = 50 000 000` рядків, `S_key = 32` Б та `b = 16` Б:

```
C_diag_naive = 50 000 000 · 48 байтів = 2 400 000 000 байтів ≈ 2.4 ГБ
```

Передавати 2.4 ГБ метаданих на кожну пару реплік для кожного діапазону токенів під час регулярного фонового відновлення є неприпустимим марнотратством мережевого каналу.

---

### 2.2. Двійкове дерево Меркла (Binary Merkle Tree)

Простір токенів розбивається на `M = 2^h` ливарних діапазонів (листя), де `h` — глибина дерева. Над цими листками будується повне збалансоване двійкове дерево висоти `h`.

#### Теорема про комунікаційну складність

Нехай дві репліки мають `d` несинхронізованих записів, розподілених між листками дерева.

Тоді обсяг переданих байтів хешів `C_diag_merkle` при покроковому спуску обмежується зверху:

```
C_diag_merkle ≤ 2 · b · d · h = 2 · b · d · log₂(M)
```

Якщо дані повністю узгоджені (`d = 0`), комунікаційна складність становить строго `O(1)`:

```
C_diag_merkle = 2 · b
```

#### Доведення

1. **Базовий крок (Корінь):** Репліки `A` і `B` обмінюються кореневими хешами `Root_A` та `Root_B`. Витрати становлять `2 · b` байтів.
   - Якщо `Root_A = Root_B`, за властивістю стійкості хеш-функції до колізій `S_A = S_B`. Процес завершується за 1 раунд обміну.

2. **Індукційний крок (Рівень `j`):** Якщо на рівні `j` (`0 ≤ j < h`) хеші вузла `u` не збігаються, координатор надсилає запит на отримання хешів двох його нащадків `Left(u)` та `Right(u)` від обох реплік.
   - На рівні `j` передаються 2 хеші від репліки `A` та 2 хеші від репліки `B` (сумарно `4 · b` байтів на кожен розбіжний вузол).
   - Кожен із `d` розбіжних записів належить рівно одному ливарному діапазону. Шлях від кореня до цього листка має довжину `h`.

3. **Сумування за рівнями:** У найгіршому випадку, коли всі `d` розбіжностей потрапляють у `d` абсолютно різних листків, дерево активує `d` неперетинних шляхів. На кожному з `h` рівнів досліджується не більше `d` розбіжних пар вузлів:

```
C_diag_merkle = 2 · b · [1 + ∑ (j=1..h) (кількість розбіжних вузлів на рівні j)]
C_diag_merkle ≤ 2 · b + 2 · b · d · h
C_diag_merkle ≈ 2 · b · d · log₂(M)
```

Коефіцієнт прискорення діагностики `K_speedup` проти наївного підходу:

```
K_speedup = C_diag_naive / C_diag_merkle = (N · (S_key + b)) / (2 · b · d · log₂ M)
```

При `N = 50 000 000`, `h = 15` (`M = 32 768`), `d = 200` розбіжних ключів, `S_key = 32` Б, `b = 16` Б:

```
C_diag_merkle = 2 · 16 · 200 · 15 = 96 000 байтів = 96 КБ
K_speedup = 2 400 000 000 / 96 000 = 25 000 разів!
```

Замість передачі 2.4 ГБ даних система знаходить точні несинхронізовані діапазони, передавши лише 96 кілобайтів службових хешів.

## 3. Багатостороннє звіряння для фактора реплікації `N ≥ 3`

У реальних безлідерних кластерах реплікація виконується на `N = 3` або `N = 5` серверів. Координатор сесії збирає кореневі хеші від усіх `N` вузлів одночасно.

Розглянемо випадок трьох реплік `A`, `B` та `C`:

```
1. Випадок ідеальної узгодженості (Root_A == Root_B == Root_C):
   • Усі три репліки ідентичні;
   • Витрати трафіку: 3 · b байтів;
   • Процес завершується негайно за 1 раунд.

2. Випадок локалізованого відставання (Root_A == Root_B != Root_C):
   • Репліки A і B мають спільний узгоджений кворумний стан;
   • Відсталою є виключно репліка C;
   • Координатор запускає спуск дерева Меркла лише між парою (A, C),
     повністю виключаючи репліку B з діагностичного обміну;
   • Витрати трафіку: 2 · b · d · h байтів.

3. Випадок тристоронньої розбіжності (Root_A != Root_B != Root_C):
   • Усі три репліки містять відмінні набори мутацій;
   • Координатор виконує тристоронній спуск: порівнюються трійки хешів
     (Hash_A[u], Hash_B[u], Hash_C[u]);
   • Сумарна комунікаційна складність: C_diag ≤ 3 · b · d_max · h.
```

Така оптимізація гарантує, що при збої одного вузла кластер витрачає рівно стільки ж мережевого трафіку на ремонт, скільки у двовузловій системі, не завантажуючи здорові сервери повторними передачами.

## 4. Імовірнісний розподіл розбіжностей по листках (Урнова модель)

У реальних кластерах розбіжності розподіляються по простору ключів випадково. Для точного розрахунку кількості активованих листків `U` застосуємо класичну **урнову модель (Occupancy Problem)**, де `d` кульок (неузгоджених ключів) випадково і незалежно кидаються у `M` скриньок (листків дерева).

### Теорема про математичне сподівання кількості розбіжних листків

Нехай `d` неузгоджених ключів рівномірно розподіляються по `M` листках. Тоді математичне сподівання кількості листків `E[U]`, у яких буде виявлено бодай одну розбіжність, дорівнює:

```
E[U] = M · [ 1 - (1 - 1/M)^d ]
```

### Доведення

1. Введемо індикаторну випадкову величину `I_i` для листка `i` (`1 ≤ i ≤ M`):
   - `I_i = 1`, якщо листок `i` містить хоча б один несинхронізований ключ;
   - `I_i = 0`, якщо листок `i` не містить жодного несинхронізованого ключа.
2. Загальна кількість активованих листків дорівнює `U = ∑ (i=1..M) I_i`.
3. Імовірність того, що конкретний несинхронізований ключ НЕ потрапить у листок `i`, становить `1 - 1/M`.
4. Оскільки ключі розподіляються незалежно, ймовірність того, що жоден із `d` ключів не потрапить у листок `i`, дорівнює `(1 - 1/M)^d`.
5. Отже, ймовірність того, що листок `i` отримає хоча б один ключ:
   ```
   P(I_i = 1) = 1 - (1 - 1/M)^d
   ```
6. За лінійністю математичного сподівання:
   ```
   E[U] = E[ ∑ (i=1..M) I_i ] = ∑ (i=1..M) E[I_i] = M · [ 1 - (1 - 1/M)^d ]
   ```

### Аналіз граничних режимів

```
1. Режим низької ентропії (d << M):
   Застосовуючи біноміальний розклад першого порядку (1 - 1/M)^d ≈ 1 - d/M:
   E[U] ≈ M · [ 1 - (1 - d/M) ] = d
   Майже кожен несинхронізований ключ потрапляє в окремий листок.
   Дерево Меркла працює з максимальною теоретичною ефективністю.

2. Режим насичення (d >> M):
   Оскільки (1 - 1/M)^d ≈ e^(-d/M) → 0:
   E[U] ≈ M
   Майже всі листки дерева містять розбіжності.
```

### Точка зламу ефективності (Crossover Point)

Якщо ступінь ентропії в кластері настільки високий, що `E[U] ≈ M`, репліки змушені передати майже всі SSTables. У цій точці побудова дерева Меркла стає зайвими накладними витратами.

Критична межа виникає, коли сумарні витрати на діагностику плюс передачу перевищують пряму передачу всього діапазону токенів:

```
C_merkle_total = 2 · b · E[U] · h + E[U] · (N / M) · S_rec
C_direct_stream = N · S_rec
```

Прирівнюючи витрати, отримуємо, що при частці пошкоджених листків `E[U] / M > 0.40–0.50` (понад 40–50% розбіжних листків) системі вигідніше відмовитися від побудови дерева Меркла та виконати пряму потокову реплікацію діапазону цілком.

## 5. Узагальнення на `k`-арні дерева Меркла та оптимальний коефіцієнт розгалуження

Розглянемо випадок, коли кожен внутрішній вузол дерева має `k` нащадків (`k ≥ 2`).

Для фіксованої кількості ливарних діапазонів `M` висота дерева дорівнює:

```
h_k = log_k(M) = ln(M) / ln(k)
```

Коли у вузлі виявлено розбіжність, репліки мусять передати хеші всіх його `k` нащадків. Обсяг трафіку для проходження одного несинхронізованого шляху від кореня до листка дорівнює:

```
C_path(k) = k · b · h_k = k · b · (ln(M) / ln(k)) = b · ln(M) · [ k / ln(k) ]
```

Дослідимо поведінку функції `f(k) = k / ln(k)` для знаходження значення `k`, що мінімізує обсяг трафіку:

```
df/dk = d/dk [ k · (ln k)⁻¹ ]
df/dk = 1 · (ln k)⁻¹ + k · (-1) · (ln k)⁻² · (1/k)
df/dk = (ln k - 1) / (ln k)²
```

Прирівнюємо похідну до нуля:

```
ln(k) - 1 = 0
ln(k) = 1
k = e ≈ 2.71828
```

Оскільки коефіцієнт розгалуження `k` мусить бути цілим числом, порівняємо найближчі дискретні значення `k = 2`, `k = 3` та `k = 4`:

```
f(2) = 2 / ln(2) ≈ 2 / 0.6931 = 2.885
f(3) = 3 / ln(3) ≈ 3 / 1.0986 = 2.730   [Глобальний дискретний мінімум]
f(4) = 4 / ln(4) ≈ 4 / 1.3863 = 2.885
f(8) = 8 / ln(8) ≈ 8 / 2.0794 = 3.847
f(16) = 16 / ln(16) ≈ 16 / 2.7726 = 5.771
```

Значення `k = 2` (двійкове дерево) та `k = 4` (четвіркове дерево) дають однаковий коефіцієнт `2.885`, який лише на 5.6% поступається теоретичному `k = 3`. Проте двійкові та четвіркові дерева є значно ефективнішими з точки зору бітових операцій комп'ютерної архітектури (зсуви бітів `>> 1` або `>> 2`), тому промислові системи використовують саме двійкові дерева `k = 2`.

## 6. Ймовірнісний аналіз колізій та надійність звіряння

Головний теоретичний ризик хеш-дерева — це виникнення **фальшиво-негативного результату (False Negative)**: коли дані на двох репліках у піддереві відрізняються, але через колізію хеш-функції їхні хеші збіглися (`Root_A = Root_B`). У такому разі система пропустить розбіжність, і дані залишаться неузгодженими.

### Теорема про верхню межу ймовірності колізії

Нехай для побудови дерева використовується стійка до колізій хеш-функція з довжиною виходу `B` бітів (`B = 8b`). Двійкове дерево висоти `h` містить сумарну кількість вузлів `V = 2^(h+1) - 1`.

Тоді за припущенням про випадковий оракул (Random Oracle Model) сумарна ймовірність виникнення бодай однієї колізії в усьому дереві `P_tree_collision` обмежується зверху:

```
P_tree_collision ≤ (2^(h+1) - 1) · 2^(-B)
```

### Доведення

1. Для будь-якого фіксованого вузла `u` ймовірність того, що два різних набори вхідних байтів дадуть однаковий `B`-бітний хеш, дорівнює:
   ```
   P(u) = 1 / 2^B = 2^(-B)
   ```
2. Подія виникнення колізії в дереві є об'єднанням подій колізій у кожному окремому вузлі `u ∈ V`.
3. За нерівністю Буля (Union Bound), ймовірність об'єднання подій не перевищує суми їхніх індивідуальних ймовірностей:
   ```
   P_tree_collision = P( ⋃ [u ∈ V] Collision(u) )
   P_tree_collision ≤ ∑ [u ∈ V] P(Collision(u))
   P_tree_collision ≤ |V| · 2^(-B) = (2^(h+1) - 1) · 2^(-B)
   ```

### Розрахунок числових меж надійності

Для типової глибини дерева `h = 15` кількість вузлів дорівнює `V = 2¹⁶ - 1 = 65 535 ≈ 6.55 · 10⁴`:

```
1. Для 64-бітного хешу (FNV-1a / Murmur64, B = 64):
   P_tree_collision ≤ 65 535 · 2⁻⁶⁴ ≈ 6.55 · 10⁴ · 5.42 · 10⁻²⁰ ≈ 3.55 · 10⁻¹⁵

2. Для 128-бітного хешу (Murmur3-128, B = 128):
   P_tree_collision ≤ 65 535 · 2⁻¹²⁸ ≈ 6.55 · 10⁴ · 2.93 · 10⁻³⁹ ≈ 1.93 · 10⁻³⁴

3. Для 256-бітного хешу (SHA-256, B = 256):
   P_tree_collision ≤ 65 535 · 2⁻²⁵⁶ ≈ 5.66 · 10⁻⁷³
```

Для порівняння: ймовірність непоміченого апаратного спотворення біта в оперативній пам'яті через космічне випромінювання (DRAM Soft Error Rate) становить близько `10⁻¹²` на гігабайт на годину.

Імовірність `1.93 · 10⁻³⁴` для 128-бітного хешу є на 22 порядки меншою за апаратну надійність кремнієвих мікросхем. Отже, 128-бітний хеш гарантує абсолютну математичну надійність звіряння.

## 7. Порівняння схем хешування листків: XOR-хешування проти криптографічного дерева

При наповненні листків дерева постає вибір математичної операції агрегації записів:

```
+-------------------------------------------------------------------------------+
| Схема A: Адитивне XOR-хешування (MSet-XOR)                                    |
| Leaf_Hash = Hash(e₁) ⊕ Hash(e₂) ⊕ ... ⊕ Hash(e_k)                             |
| • Перевага: комутативність і асоціативність (порядок записів не має значення).|
| • Вразливість: парні колізії (X ⊕ X = 0). Якщо на обох репліках змінено       |
|   парну кількість записів з однаковим зсувом хешу, розбіжність знищиться.     |
+-------------------------------------------------------------------------------+
                                      против
+-------------------------------------------------------------------------------+
| Схема B: Каскадне впорядковане хешування (Ordered Merkle)                     |
| Leaf_Hash = Hash( Sort(Key₁) || Value₁ || ... || Sort(Key_k) || Value_k )     |
| • Перевага: повна криптографічна строгість, захист від будь-яких колізій.     |
| • Вимога: необхідність попереднього сортування записів за первинним ключем.   |
+-------------------------------------------------------------------------------+
```

Оскільки в сховищах на базі LSM-дерев записи всередині SSTable вже зберігаються у строго відсортованому порядку, промислові рушії використовують саме впорядковане каскадне хешування, що виключає вразливості схеми XOR.

## 8. Моделювання мережевої затримки (RTT Latency Model)

У георозподілених кластерах час завершення діагностики визначається не лише швидкістю каналу, а й мережевою затримкою між датацентрами (Round-Trip Time, `RTT`).

При покроковому двійковому спуску репліки виконують `h` послідовних мережевих раундів. Загальний час діагностики `T_diag` описується моделлю:

```
T_diag = h · RTT + (C_diag_merkle / Bandwidth)
```

При затримці між Європою та США `RTT = 120` мс та глибині дерева `h = 15`:

```
T_diag_step = 15 · 120 мс = 1800 мс = 1.8 секунди
```

Щоб скоротити цей час, сучасні розподілені протоколи передають дерево **цілими зрізами рівнів (Level-Batching)**. Замість покрокового запиту на кожному рівні вузол надсилає всі хеші перших `m` рівнів за один раунд (`RTT`), що скорочує кількість мережевих ітерацій з `h` до `h / m`, знижуючи затримку діагностики у 3–5 разів.

## 9. Альтернативні структури узгодження множин (IBLT та Negentropy)

Окрім дерев Меркла, у теорії розподілених систем розроблено альтернативні алгебраїчні підходи до виявлення розбіжностей:

```
+-------------------------------------------------------------------------------+
| 1. Інвертовані фільтри Блума (Invertible Bloom Lookup Tables, IBLT):          |
|    • Принцип: таблиця комірок (KeySum, Count, HashSum), куди елементи          |
|      додаються через k хеш-функцій.                                           |
|    • Складність: O(d) — трафік пропорційний лише розміру розбіжності d,        |
|      незалежно від загального розміру N!                                      |
|    • Межа: якщо реальне d перевищує ємність IBLT, декодування повністю        |
|      провалюється (Decoding Failure) і не повертає жодного ключа.             |
+-------------------------------------------------------------------------------+
                                      против
+-------------------------------------------------------------------------------+
| 2. Дерева Меркла (Merkle Trees):                                              |
|    • Складність: O(d · log M).                                                |
|    • Перевага: детермінізм — відсутність ризику decoding failure;              |
|      гарантована локалізація розбіжностей за будь-якого d.                    |
+-------------------------------------------------------------------------------+
```

| Характеристика | Дерева Меркла (Merkle Trees) | Інвертовані фільтри Блума (IBLT) | Діапазонне узгодження (Negentropy) |
| :--- | :--- | :--- | :--- |
| **Комунікаційна складність** | `O(d · log M)` | `O(d)` | `O(d · log(N/d))` |
| **Стійкість до великих `d`** | 100% гарантована локалізація | Повний провал при перевищенні ємності | 100% гарантована локалізація |
| **Витрати пам'яті на вузлі** | `2^(h+1) · b` байтів | `O(d_max)` байтів | `O(log N)` байтів |
| **Потреба у відсортованих даних** | Бажана (для швидкості сканування) | Не потрібна (хешування в масив) | Обов'язкова (бінарний поділ діапазонів) |

## 10. Обчислювальна та енергетична складність хешування (CPU Cost Model)

Побудова дерева Меркла вимагає обчислення хешу від кожного байта збережених даних. Вибір алгоритму хешування визначає споживання процесорного часу та енергетичну ефективність відновлення:

```
1. FNV-1a (Non-cryptographic 64-bit):
   • 1 інструкція XOR + 1 інструкція IMUL на байт (~1.2 такта на байт);
   • Пропускна здатність: ~2.5 ГБ/с на ядро CPU (Intel Xeon @ 3.0 ГГц).

2. Murmur3-128 (Non-cryptographic 128-bit, галузевий стандарт):
   • Векторизація через AVX2/SSE4 (~0.3 такта на байт);
   • Пропускна здатність: ~3.8 ГБ/с на ядро CPU.

3. SHA-256 з підтримкою Intel SHA-NI (Hardware Accelerated):
   • Апаратні інструкції sha256rnds2 (~1.1 такта на байт);
   • Пропускна здатність: ~1.4 ГБ/с на ядро CPU.

4. SHA-256 без апаратного прискорення (Software fallback):
   • Чисте програмне обчислення (~8.5 такта на байт);
   • Пропускна здатність: ~350 МБ/с на ядро CPU.
```

Для таблиці обсягом 1 терабайт обчислення дерев Меркла на Murmur3-128 займає всього `1000 ГБ / 3.8 ГБ/с ≈ 263 секунди` процесорного часу ядра, що дозволяє проводити анти-ентропійний ремонт без помітної деградації продуктивності основних клієнтських транзакцій.

## 11. Виведення формули оптимальної глибини дерева `h*`

Вибір глибини дерева `h` визначає компроміс між двома протилежними факторами:
1. **Витрати на діагностику `C_diag(h)`:** зростають лінійно з ростом `h` як `2 · b · d · h`.
2. **Витрати на потокову передачу даних `C_data(h)`:** коли розбіжність знайдено в листку, репліка вичитує та передає всі записи цього листка. Кількість записів у листку дорівнює `N / 2^h`. При середньому розмірі запису `S_rec` байтів витрати на передачу даних становлять `d · (N / 2^h) · S_rec`.
3. **Витрати оперативної пам'яті `M_mem(h)`:** дерево зберігається в пам'яті під час сесії і вимагає `2^(h+1) · b` байтів.

Загальна функція сумарного мережевого трафіку для `d` несинхронізованих ключів має вигляд:

```
C_total(h) = C_diag(h) + C_data(h)
C_total(h) = 2 · b · d · h + d · N · S_rec · 2^(-h)
```

Знайдемо екстремум функції `C_total(h)`, обчисливши її похідну за змінною `h`:

```
d/dh [ C_total(h) ] = d/dh [ 2 · b · d · h + d · N · S_rec · 2^(-h) ]
d/dh [ C_total(h) ] = 2 · b · d + d · N · S_rec · (-ln 2) · 2^(-h) ]
```

Прирівнюємо похідну до нуля для пошуку точки мінімуму:

```
2 · b · d - d · N · S_rec · ln(2) · 2^(-h) = 0
2 · b = N · S_rec · ln(2) · 2^(-h)                   [скоротили на d]
2^h = (N · S_rec · ln 2) / (2 · b)
h* = log₂ [ (N · S_rec · ln 2) / (2 · b) ]
```

### Комплексний інженерний розрахунок

Розглянемо практичний сегмент таблиці бази даних:
- Загальна кількість записів у діапазоні: `N = 10 000 000` (10 мільйонів рядків);
- Середній розмір рядка: `S_rec = 512` байтів;
- Загальний дисковий обсяг сегмента: `10 000 000 · 512 Б = 5.12 ГБ`;
- Розмір хешу: `b = 16` байтів (Murmur3-128).

Розрахуємо теоретичну глибину `h*`:

```
h* = log₂ [ (10 000 000 · 512 · 0.693147) / (2 · 16) ]
h* = log₂ [ 3 548 912 640 / 32 ]
h* = log₂ [ 110 903 520 ]
h* ≈ 26.7
```

Теоретичний мінімум трафіку досягається при `h = 27`. Проте дерево глибини 27 містило б `2²⁷ ≈ 134` мільйони листків і вимагало б `2²⁸ · 16 Б ≈ 4.29 ГБ` оперативної пам'яті лише на зберігання хешів одного дерева.

Тому інженерний оптимум встановлюється за обмеженням доступної оперативної пам'яті (Memory Budget per Repair Session, типово `≤ 2 МБ` на дерево):

```
При h = 15:
• Кількість листків: M = 2¹⁵ = 32 768
• Пам'ять дерева: 2¹⁶ · 16 Б = 1 048 576 Б = 1 МБ
• Середня кількість записів у листку: 10 000 000 / 32 768 ≈ 305 записів
• Розмір даних одного листка: 305 · 512 Б ≈ 156 КБ
```

При глибині `h = 15` дерево споживає лише 1 МБ RAM, а на кожну знайдену розбіжність репліки передають усього 156 КБ даних, що забезпечує ідеальний баланс між швидкістю мережі та споживанням пам'яті сервера.

Якщо розмір бази даних невпинно зростає до сотень мільярдів рядків, інженерні команди не збільшують параметр глибини `h` до екстремальних значень, а пропорційно дроблять фізичний розмір vnode-діапазонів у процесі динамічного репартиціювання (resharding). Це надійно зберігає розмір кожного активного дерева строго в межах комфортного 1 мегабайта пам'яті для кожної незалежної сесії відновлення.

Такий аналітично обґрунтований компроміс між сублінійною складністю діагностики `O(d · log M)` та лінійним часом послідовного сканування накопичувачів робить дерева Меркла неперевершеним стандартом для розподілених сховищ довільного масштабу. Це дає строгий математичний доказ того, що комунікаційні витрати анти-ентропії масштабуються сублінійно відносно розміру сховища, гарантуючи надійну стійкість та передбачувану затримку при будь-яких промислових навантаженнях кластера.
