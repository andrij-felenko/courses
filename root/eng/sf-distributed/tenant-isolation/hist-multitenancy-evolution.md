# 📜 Від мейнфреймів до SaaS: історія мультиарендності

У середині 1960-х років вартість оренди обчислювального комплексу IBM System/360 Model 65 сягала п'ятдесяти тисяч доларів щомісяця за екземпляр із 512 кілобайтами пам'яті. Жодне окреме підприємство або дослідницька лабораторія не могли завантажити такий дорогий процесор на повну потужність лише власними пакетними завданнями (batch processing). Коли програма очікувала введення з перфокарт або магнітної стрічки, процесор простоював, спалюючи кошти замовників.

Ця економічна безвихідь змусила інженерів Массачусетського технологічного інституту (MIT) у рамках проєкту MAC розробити систему сумісного використання часу — Compatible Time-Sharing System (CTSS), а згодом систему Multics. Ідея полягала в тому, щоб надати кожному користувачеві ілюзію персональної машини: центральний процесор перемикався між задачами сотні терміналів кожні кілька мілісекунд, а апаратні регістри захисту пам'яті гарантували, що збій або шкідливий код одного терміналу не зможе прочитати байти сусідньої програми.

У 1967 році лабораторія IBM у Кембриджі створила операційну систему CP-40 (а згодом CP-67) для мейнфрейма IBM System/360-67. Це була перша повноцінна система апаратної віртуалізації: кожен клієнт отримував повноцінну віртуальну машину (Virtual Machine), на якій працювала власна операційна система CMS. Це заклало фундаментальний інженерний шаблон ізоляції — **силосну модель (Silo Model)**, де спільним є лише фізичне залізо, а програмний стек кожного клієнта ізольовано до рівня віртуальних регістрів процесора.

## Пастка 1990-х: криза провайдерів додатків (ASP)

Наприкінці 1990-х років, із бурхливим розвитком комерційного інтернету, виник ринок постачальників прикладних послуг — Application Service Providers (ASP). Компанії на кшталт USinternetworking, Corio та Breakaway Solutions пропонували корпоративним клієнтам оренду складного корпоративного програмного забезпечення (ERP-систем SAP, PeopleSoft, Siebel) через мережу замість розгортання власних серверних кімнат.

Проте архітектура ASP повністю спиралася на традиційну модель розгортання окремих екземплярів:

```
ASP-модель кінця 1990-х (Окремий силос на кожного клієнта):
┌─────────────────────────────────────────────────────────┐
│ Клієнт 1: Окремий сервер + Окрема ОС + Окремий Siebel  │
├─────────────────────────────────────────────────────────┤
│ Клієнт 2: Окремий сервер + Окрема ОС + Окремий Siebel  │
├─────────────────────────────────────────────────────────┤
│ Клієнт 3: Окремий сервер + Окрема ОС + Окремий Siebel  │
└─────────────────────────────────────────────────────────┘
Собівартість масштабування O(N): 1000 клієнтів = 1000 інсталяцій.
```

Цей підхід зазнав нищівного економічного краху з трьох причин:
1. **Лінійне зростання операційних витрат:** Для кожного нового клієнта системні адміністратори мусили вручну виділяти фізичний сервер, встановлювати операційну систему, налаштовувати СУБД та запускати окремий екземпляр програми.
2. **Кошмар оновлень:** Коли вендор випускав критичне оновлення безпеки, інженери підтримки мусили накатувати патчі на тисячі окремих серверів по черзі. Якщо кілька клієнтів кастомізували свої схеми баз даних, автоматизоване оновлення ставало неможливим, консервуючи застарілі версії роками.
3. **Жахлива утилізація заліза:** 90% серверів уночі та у вихідні дні завантажували процесор менш ніж на 3%, але провайдер продовжував сплачувати за живлення, охолодження та ліцензії на кожне процесорне ядро.

До 2001 року більшість перших ASP збанкрутували або були поглинені за безцінь. Галузь усвідомила: орендувати інфраструктуру поштучно економічно невигідно — програма повинна сама вміти обслуговувати мільйони користувачів із єдиного спільного екземпляра.

## Революція Salesforce: метадані та спільні таблиці

У 1999 році Марк Беніофф, Паркер Гарріс, Дейв Мелленгофф та Френк Домінгес заснували компанію Salesforce із радикальною місією: «Кінець програмному забезпеченню» (The End of Software). Замість продажу дисків із дистрибутивом вони запропонували концепцію Software-as-a-Service (SaaS), у центрі якої стояла **пулова мультиарендність (Pool Multi-Tenancy)**.

Головним технічним викликом Salesforce була реляційна база даних. Запуск окремої бази Oracle для кожного з десятків тисяч клієнтів призвів би до тієї ж кризи ASP через обмеження пулів пам'яті SGA та системні ресурси СУБД. З іншого боку, створення динамічних таблиць (`CREATE TABLE`) для кожного клієнта в єдиній базі вичерпувало системний каталог Oracle і блокувало словник даних під час модифікацій схем.

Паркер Гарріс і команда розробили революційну **багатоорендну архітектуру, керовану метаданими (Metadata-Driven Multi-Tenant Architecture)**:

```
Логічне представлення орендаря       Фізичне збереження в універсальній таблиці
┌───────────────────────────────┐   ┌─────────────────────────────────────────────────┐
│ Tenant: "Acme Corp" (ID=101)  │   │ Table: MT_Data (Спільна для всіх)              │
│ Schema: CustomObject_Invoice  │   ├───────────┬────────────┬───────────┬────────────┤
│ Field1 (String): InvoiceNum   │   │ tenant_id │ obj_id     │ val_char0 │ val_num0   │
│ Field2 (Number): Amount       │   ├───────────┼────────────┼───────────┼────────────┤
└───────────────────────────────┘   │ 101       │ obj_inv_01 │ "INV-99"  │ 1500.00    │
                                    │ 202       │ obj_usr_99 │ "John"    │ 42.00      │
                                    └───────────┴────────────┴───────────┴────────────┘
```

Замість фізичних таблиць під кожного клієнта вся інформація зберігалася в кількох гігантських денормалізованих універсальних таблицях (`MT_Data`, `MT_Clustered_Index`). Усі записи містили обов'язковий ідентифікатор `tenant_id`. Визначення того, які поля належать конкретному клієнту, зберігалося в окремих таблицях метаданих.

Коли користувач надсилав запит, рушій Salesforce динамічно генерував оптимізований SQL-запит, підставляючи умови фільтрації за `tenant_id` на рівні абстракції доступу до даних. Це дозволило розгортати одне оновлення коду на єдиний кластер, миттєво роблячи нові функції доступними для всіх клієнтів одночасно, знизивши собівартість обслуговування клієнта на два порядки.

## Епоха хмарних платформ і повернення до апаратної ізоляції

У 2006 році запуск Amazon Web Services (AWS) із сервісами S3 та EC2 започаткував еру Infrastructure-as-a-Service (IaaS). Хмарні провайдери зіткнулися з мультиарендністю на зовсім іншому рівні масштабу: на одному фізичному сервері одночасно працювали віртуальні машини банків, конкурентів у сфері електронної комерції та випадкових публічних сервісів.

Гіпервізори Xen та KVM спиралися на апаратну віртуалізацію Intel VT-x та AMD-V. Проте розвиток контейнеризації на базі просторів імен Linux (namespaces) та контрольних груп (cgroups) у 2013 році через Docker повернув маятник у бік максимальної щільності розміщення процесів на спільному ядрі ОС.

У 2018 році індустрію сколихнуло відкриття вразливостей спекулятивного виконання процесорів — Meltdown, Spectre та Foreshadow. Вони довели, що процеси різних орендарів, які виконуються на одному фізичному ядрі процесора зі спільним кешем інструкцій та блоком передбачення переходів, можуть читати пам'ять одне одного в обхід будь-яких програмних і навіть ядерних бар'єрів операційної системи.

Це змусило інженерів хмарних платформ створити нове покоління технологій ізоляції:
* **MicroVM (AWS Firecracker, Cloud Hypervisor):** Мінімалістичні віртуальні машини на базі KVM, які завантажуються за 5–10 мілісекунд і споживають лише 5 мегабайтів пам'яті, поєднуючи швидкість контейнерів із захистом апаратного гіпервізора.
* **Пісочниці на рівні системних викликів (Google gVisor):** Перехоплення системних викликів додатку через віртуальне ядро, написане на безпечній до пам'яті мові Go, без надання прямого доступу до ядра Linux хоста.
* **Row-Level Security (RLS) у сучасних СУБД:** Вбудовування політик фільтрації за орендарями безпосередньо в рушії PostgreSQL та MySQL на рівні планувальника запитів, що усунуло потребу писати громіздкі абстракції над універсальними таблицями метаданих.

Сьогодні мультиарендність пройшла повне діалектичне коло: від апаратного розподілу часу на мейнфреймах 1960-х через повністю спільні структури реляційних даних у 2000-х до сучасних гібридних архітектур, де ізоляція гарантується на рівні ядра, мережевих проксі та криптографічних ключів.
