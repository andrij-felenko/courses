# 🧮 Аналіз вартості фільтрації: селективність, пропускна здатність і поріг вигідності

Вибір архітектурного місця для фільтрації повідомлень — на боці центрального брокера чи локально всередині кожного споживача — завжди є строгим математичним компромісом між обчислювальними ресурсами та пропускною здатністю мережі. Якщо споживач відкидає 99% вхідного потоку, передача сирих даних через мережу стає руйнівною. Якщо ж споживач приймає 95% потоку, витрата процесорного часу брокера на обчислення фільтрів для кожного підписника створює штучне вузьке місце.

Цей розділ формалізує модель вартості фільтрації, виводить аналітичний вираз для критичного порогу селективності, аналізує поведінку черг споживача засобами теорії масового обслуговування, доводить теорему про оптимальний порядок ланцюга фільтрів, досліджує динаміку фільтра обмеження частоти (Rate Limiting) за моделлю маркерного кошика, порівнює складність алгоритмів зіставляння підписок та обґрунтовує ймовірнісні межі для фільтрів дедуплікації зі станом.

## Формальна модель потоку та параметри системи

Розглянемо потік вхідних повідомлень, що надходить у розподілену шину з інтенсивністю `λ` (повідомлень на секунду).

Кожне повідомлення має загальний розмір `M` байтів, який складається з розміру заголовків `H` та розміру корисного навантаження (тіла) `B`:

```
M = H + B
```

Ключовим параметром фільтра є його **селективність** `s` (англ. *selectivity*), яка визначає ймовірність того, що випадкове повідомлення задовольнить умову предикату `P(m)`:

```
s = P(P(m) = TRUE) ∈ [0, 1]
```

* Коли `s = 0`, фільтр відкидає всі повідомлення (повне відсікання).
* Коли `s = 1`, фільтр пропускає всі повідомлення (жодне повідомлення не відсіюється).
* Коли `s = 0.05`, фільтр пропускає лише 5% повідомлень, а 95% відкидає.

Позначимо питомі часові та обчислювальні витрати:
* `C_b_hdr` — час процесора брокера на перевірку заголовків одного повідомлення (секунд/повідомлення).
* `C_b_body` — час процесора брокера на парсинг та оцінку тіла повідомлення (секунд/повідомлення).
* `C_c_parse` — час процесора споживача на повну десеріалізацію тіла повідомлення та бізнес-обробку (секунд/повідомлення).
* `C_c_flt` — час процесора споживача на локальну перевірку фільтра, якщо повідомлення вже доставлене в пам'ять процесу.
* `T_net` — питома затримка передачі одного байта через мережевий стек (секунд/байт).

## Порівняльний баланс витрат ресурсів

Розглянемо дві протилежні архітектурні моделі для системи з одним брокером та `K` незалежними споживачами, кожен з яких має власний фільтр із середньою селективністю `s`.

### Модель А: Клієнтська фільтрація (Client-Side Filtering)

Брокер сліпо транслює всі `λ` повідомлень кожному з `K` споживачів. Кожен споживач самостійно приймає потік, оцінює предикат і відкидає невідповідні повідомлення.

Сумарне навантаження на систему:
1. **Вихідний мережевий трафік брокера:**
```
Net_client = K · λ · M      [байтів/с]
```

2. **Завантаження процесора одного споживача:**
```
CPU_consumer_A = λ · C_c_flt + s · λ · C_c_parse      [секунд обчислень на секунду часу]
```

3. **Завантаження процесора брокера:**
```
CPU_broker_A = K · λ · C_tx_raw      [де C_tx_raw — мінімальний час передачі батчу через sendfile]
```

### Модель Б: Серверна фільтрація заголовків (Broker-Side Header Filtering)

Брокер самостійно оцінює предикат над заголовком для кожного з `K` підписників і передає в мережу лише ті повідомлення, де умова повернула `TRUE`.

Сумарне навантаження на систему:
1. **Вихідний мережевий трафік брокера:**
```
Net_broker = K · s · λ · M      [байтів/с]
```

2. **Завантаження процесора одного споживача:**
```
CPU_consumer_B = s · λ · C_c_parse      [споживач взагалі не витрачає час на відкинуті події]
```

3. **Завантаження процесора брокера:**
```
CPU_broker_B = K · λ · C_b_hdr + K · s · λ · C_tx_raw
```

## Виведення критичного порогу селективності

Щоб з'ясувати, коли саме серверна фільтрація вигідніша за клієнтську, сформулюємо умову ефективності за загальними витратами ресурсів клієнтського вузла та мережі.

Серверна фільтрація є безумовно вигідною для споживача, якщо заощаджений час процесора клієнта та мережевої передачі перевищує накладні витрати брокера.

Знайдемо різницю у використанні пропускної здатності мережі `ΔNet`:

```
ΔNet = Net_client - Net_broker           [різниця мережевого трафіку моделей]
= K·λ·M - K·s·λ·M                       [підстановка формул трафіку]
= K·λ·M · (1 - s)                       [винесення спільного множника K·λ·M]
```

Знайдемо різницю в навантаженні на процесор споживача `ΔCPU_c`:

```
ΔCPU_c = CPU_consumer_A - CPU_consumer_B        [різниця витрат часу CPU клієнта]
= (λ·C_c_flt + s·λ·C_c_parse) - (s·λ·C_c_parse)  [підстановка формул навантаження]
= λ · C_c_flt                                   [взаємне скорочення s·λ·C_c_parse]
```

Брокер бере на себе додаткові витрати процесора:

```
ΔCPU_b = CPU_broker_B - CPU_broker_A            [різниця витрат часу CPU брокера]
= K·λ·C_b_hdr - K·(1 - s)·λ·C_tx_raw            [додатковий парсинг мінус зекономлена відправка]
```

Оскільки вартість передачі пакета `C_tx_raw` зазвичай співмірна з вартістю швидкої перевірки заголовка `C_b_hdr`, додаткове навантаження на брокер компенсується тим, що брокер не витрачає системні виклики на відправку відкинутих повідомлень.

Визначимо **граничну точку беззбитковості мережі** (англ. *network breakeven point*). Якщо канал зв'язку споживача обмежений смугою `B_max` (байтів/с), то максимальна допустима частота вхідного потоку `λ_max` при клієнтській фільтрації дорівнює:

```
λ_max_client = B_max / M
```

При серверній фільтрації споживач витримує потік продюсерів, який у `1/s` разів більший:

```
λ_max_server = B_max / (s · M) = λ_max_client / s
```

Якщо селективність становить `s = 0.02` (2%), поріг витривалості системи за мережею зростає рівно в `50 разів`.

## Покроковий числовий приклад розрахунку системи

Розглянемо практичний інженерний розрахунок для кластера електронної комерції з такими параметрами:
* Вхідний потік: `λ = 100 000` повідомлень/с.
* Кількість зацікавлених мікросервісів: `K = 8`.
* Розмір заголовка: `H = 200` байтів.
* Розмір корисного навантаження (JSON): `B = 1 800` байтів (`M = 2 000` байтів = 2 КБ).
* Селективність споживача: `s = 0.05` (5% цільових подій).
* Час десеріалізації JSON на споживачі: `C_c_parse = 40` мкс (`40 · 10⁻⁶` с).
* Час швидкої перевірки заголовка: `C_b_hdr = 0.2` мкс (`0.2 · 10⁻⁶` с).

### Крок 1. Розрахунок мережевого навантаження

```
Net_client
= K · λ · M                                      [формула повного широкомовного трафіку]
= 8 · 100 000 · 2 000                           [підстановка: 8 споживачів по 100k под/с по 2 КБ]
= 1 600 000 000 байтів/с                         [множення]
= 1.6 ГБ/с = 12.8 Гбіт/с                         [переведення в гігабіти: мережа перевантажена]

Net_broker
= K · s · λ · M                                  [формула відфільтрованого трафіку]
= 8 · 0.05 · 100 000 · 2 000                    [підстановка: відсів 95% повідомлень]
= 80 000 000 байтів/с                            [множення]
= 80 МБ/с = 640 Мбіт/с                           [переведення: штатне навантаження для 1GbE/10GbE]
```

**Висновок за кроком 1:** Серверний фільтр зменшує навантаження на комутатори дата-центру на 12.16 Гбіт/с (економія 95%).

### Крок 2. Розрахунок процесорних ядер споживача

Обчислимо необхідну кількість ядер процесора (`N_cores`) для одного споживача:

```
N_cores_client
= λ · (C_c_flt + s · C_c_parse)                  [загальний час обчислень на секунду]
= 100 000 · (5·10⁻⁶ + 0.05 · 40·10⁻⁶)           [підстановка: 5 мкс на парсинг заголовка JSON + 40 мкс]
= 100 000 · (5·10⁻⁶ + 2·10⁻⁶)
= 100 000 · 7·10⁻⁶
= 0.7 ядра CPU на розбір + сокетні витрати

N_cores_server_filtered
= s · λ · C_c_parse                              [споживач парсить лише валідні повідомлення]
= 0.05 · 100 000 · 40·10⁻⁶
= 5 000 · 40·10⁻⁶
= 0.2 ядра CPU
```

## Теорема про оптимальний порядок ланцюга фільтрів (Filter Chaining)

У складних конвеєрах повідомлення проходить крізь послідовність із `N` незалежних фільтрів `F₁, F₂, ..., F_N`. Кожен окремий фільтр `F_i` характеризується двома величинами:
* `c_i` — середня вартість (час процесора) перевірки умови `P_i(m)` над одним повідомленням.
* `s_i` — індивідуальна ймовірність успішного проходження фільтра (селективність, `0 ≤ s_i ≤ 1`).

Якщо предикати поєднані логічним оператором «І» (`AND`), конвеєр працює за правилом скороченого обчислення (*short-circuit evaluation*): повідомлення відкидається негайно, щойно перший-ліпший фільтр повертає `FALSE`.

Очікувана середня вартість обробки одного повідомлення ланцюгом становить:

```
E[C] = c₁ + s₁·c₂ + s₁·s₂·c₃ + ... + (∏_{j=1}^{N-1} s_j) · c_N
```

### Доведення критерію оптимального впорядкування

Розглянемо два сусідні фільтри в ланцюзі: `F_A` (з вартістю `c_A` та селективністю `s_A`) і `F_B` (з вартістю `c_B` та селективністю `s_B`). Припустимо, перед ними потік уже пройшов кілька попередніх стадій із сумарним коефіцієнтом пропуску `S_prev`.

Порівняємо очікувані витрати для двох варіантів черговості:
1. Порядок `(A, B)`:
```
Cost(A, B) = S_prev · c_A + S_prev · s_A · c_B
```

2. Порядок `(B, A)`:
```
Cost(B, A) = S_prev · c_B + S_prev · s_B · c_A
```

Порядок `(A, B)` є строго вигіднішим за `(B, A)`, коли:

```
Cost(A, B) < Cost(B, A)
S_prev · c_A + S_prev · s_A · c_B < S_prev · c_B + S_prev · s_B · c_A
c_A + s_A · c_B < c_B + s_B · c_A
c_A - s_B · c_A < c_B - s_A · c_B
c_A · (1 - s_B) < c_B · (1 - s_A)
```

Поділивши обидві частини на додатний добуток `(1 - s_A) · (1 - s_B)`, отримуємо фундаментальний інваріант:

```
c_A / (1 - s_A) < c_B / (1 - s_B)
```

Величина `(1 - s_i)` являє собою **силу відсікання** (англ. *rejection power* — частку потоку, яку фільтр знищує). Відношення `c_i / (1 - s_i)` позначає **ціну одиниці відсікання**.

**Теорема:** *Для мінімізації загальних процесорних витрат конвеєра послідовні фільтри повинні бути впорядковані за зростанням показника `c_i / (1 - s_i)`: найдешевші фільтри з найвищим відсотком відсікання повинні стояти першими.*

### Числовий приклад оптимізації ланцюга:

Нехай є три фільтри:
1. `F_hdr`: перевірка заголовка регіону (`c₁ = 0.1` мкс, відсікає 80% → `s₁ = 0.2`).
   `Ratio₁ = 0.1 / (1 - 0.2) = 0.1 / 0.8 = 0.125` мкс.
2. `F_sec`: перевірка HMAC-підпису орендаря (`c₂ = 2.0` мкс, відсікає 50% → `s₂ = 0.5`).
   `Ratio₂ = 2.0 / (1 - 0.5) = 2.0 / 0.5 = 4.000` мкс.
3. `F_body`: повний парсинг JSON і перевірка бізнес-правила (`c₃ = 30.0` мкс, відсікає 90% → `s₃ = 0.1`).
   `Ratio₃ = 30.0 / (1 - 0.1) = 30.0 / 0.9 = 33.333` мкс.

* **Оптимальний порядок `(1 → 2 → 3)`:**
  `E[C] = 0.1 + 0.2 · 2.0 + 0.2 · 0.5 · 30.0 = 0.1 + 0.4 + 3.0 = 3.5` мкс на повідомлення.
* **Неправильний інтуїтивний порядок `(3 → 1 → 2)` (спочатку перевірити складне бізнес-правило, бо воно відсікає 90%):**
  `E[C] = 30.0 + 0.1 · 0.1 + 0.1 · 0.2 · 2.0 = 30.0 + 0.01 + 0.04 = 30.05` мкс на повідомлення.

Математично коректний порядок зменшує завантаження CPU рівно у **8.5 раза**.

## Динаміка фільтра обмеження швидкості (Rate-Limiting Filter: Token Bucket)

У багатьох сценаріях фільтр повідомлень функціонує не як статичний булевий вираз, а як динамічний обмежувач пропускної здатності потоку для захисту споживача від сплесків. Класична математична модель такого фільтра базується на алгоритмі **маркерного кошика** (англ. *Token Bucket*).

Нехай кошик має максимальну ємність `B` маркерів (tokens) і поповнюється з постійною швидкістю `r` маркерів на секунду. Кожне вхідне повідомлення вимагає 1 маркер для проходження крізь фільтр. Якщо маркерів у кошику недостатньо, повідомлення або відкидається (Drop), або перенаправляється в чергу очікування.

### 1. Тривалість поглинання сплеску (Burst Duration)

Якщо на вхід фільтра раптово надходить сплеск інтенсивністю `λ_burst > r`, кошик починає спустошуватися зі швидкістю `(λ_burst - r)` маркерів/с.

Час `T_burst`, протягом якого фільтр здатний пропускати 100% повідомлень без жодних втрат:

```
T_burst = B / (λ_burst - r)
```

Загальна кількість повідомлень `N_pass`, пропущених за час сплеску:

```
N_pass = B + r · T_burst = B · (λ_burst / (λ_burst - r))
```

### 2. Ймовірність відкидання при тривалому перевантаженні

Якщо перевантаження `λ_in > r` триває значно довше за `T_burst`, кошик залишається порожнім, а фільтр пропускає рівно `r` повідомлень на секунду.

Стаціонарна частка відкинутих повідомлень (ймовірність скидання `P_drop`) становить:

```
P_drop = (λ_in - r) / λ_in = 1 - (r / λ_in)
```

Якщо `λ_in = 50 000` под/с, а ліміт налаштовано на `r = 10 000` под/с, динамічний фільтр стабілізує вихідний потік на рівні 10 000 под/с, відсікаючи рівно `80%` надлишкового навантаження.

## Теорія черг: стабільність споживача та хвостова затримка (M/M/1)

Розглянемо споживача як систему масового обслуговування **M/M/1** (найпростіша модель із пуассонівським вхідним потоком та експоненційним часом обслуговування).

Нехай `λ_in` — частота надходження повідомлень у вхідну чергу сокета споживача, а `μ` — середня продуктивність обробника (повідомлень/с).

Коефіцієнт завантаження системи `ρ` визначається як:

```
ρ = λ_in / μ
```

Умова ергодичності (стаціонарного режиму без нескінченного росту черги):

```
ρ < 1  (тобто λ_in < μ)
```

Середня кількість повідомлень у черзі `L_q` та середня повна затримка повідомлення `W` (час очікування в буфері сокета + час обробки) виражаються класичними формулами Хінчина-Поллячека:

```
L_q = ρ² / (1 - ρ)

W = 1 / (μ - λ_in) = 1 / (μ · (1 - ρ))
```

### Порівняння поведінки черги під час сплеску трафіку

Нехай продуктивність споживача обмежена `μ = 10 000` повідомлень/с.
При штатному навантаженні продюсери генерують `λ = 8 000` под/с, а під час сплеску (Black Friday) потік зростає в 5 разів: `λ_burst = 40 000` под/с.
Селективність фільтра споживача: `s = 0.1` (10% цільових подій).

#### 1. За клієнтської фільтрації:
* У штатному режимі:
  `λ_in = 8 000` под/с, `ρ = 8 000 / 10 000 = 0.8`.
  Середня затримка: `W = 1 / (10 000 - 8 000) = 1 / 2 000 = 0.5` мс.
* Під час сплеску:
  `λ_in = 40 000` под/с.
  Оскільки `λ_in = 40 000 > μ = 10 000`, коефіцієнт завантаження `ρ = 4.0 >> 1`.
  **Наслідок:** Вхідний буфер сокета миттєво переповнюється, виникає втрата пакетів (TCP drops), черга зростає лінійно зі швидкістю `30 000` повідомлень/с, а затримка прагне до нескінченності. Споживач зазнає каскадного краху.

#### 2. За серверної фільтрації:
* У штатному режимі:
  `λ_in = s · λ = 0.1 · 8 000 = 800` под/с.
  `ρ = 800 / 10 000 = 0.08`.
  Середня затримка: `W = 1 / (10 000 - 8 000) = 1 / 9 200 ≈ 0.108` мс.
* Під час сплеску:
  `λ_in = s · λ_burst = 0.1 · 40 000 = 4 000` под/с.
  `ρ = 4 000 / 10 000 = 0.40 < 1`.
  Середня затримка: `W = 1 / (10 000 - 4 000) = 1 / 6 000 ≈ 0.166` мс.

**Математичний висновок:** Серверна фільтрація повністю ізолює споживача від сплесків небажаного трафіку, утримуючи чергу в стаціонарній зоні `ρ < 1` навіть при 5-кратному перевантаженні продюсерів.

## Алгоритмічна складність зіставляння підписок: сканування проти дерев

Коли брокер обслуговує `K` незалежних підписників, наївний підхід вимагає послідовної оцінки кожного фільтра для кожного вхідного повідомлення:

```
T_naive = O(K · D)
```

де `D` — середня кількість умов у предикаті. При `K = 10 000` підписників цей підхід паралізує брокер.

Для масштабування серверної фільтрації застосовують дві структури індексації:

### 1. Префіксне дерево (Trie) для рядкових атрибутів
Для ієрархічних тем та префіксів заголовків (наприклад, `region=EU.*`, `service=billing.*`):
* Час пошуку збігів для одного повідомлення: `O(L)`, де `L` — довжина рядка ключа в повідомленні.
* Час пошуку **не залежить від кількості підписників `K`**.

### 2. Дерево відрізків (Interval Tree) для числових діапазонів
Якщо `K` підписників фільтрують за числовими діапазонами (наприклад, `priority >= 5`, `amount BETWEEN 100 AND 500`):
* Замість лінійної перевірки `K` інтервалів, точки запиту шукаються в дереві інтервалів.
* Складність знаходження всіх `m` задоволених підписників:

```
T_interval = O(log K + m)
```

де `m = s_avg · K` — кількість підписників, для яких умова виявилася істинною.

## Математичні межі фільтрів дедуплікації зі станом (Bloom Filter)

Окремим випадком є фільтри повідомлень зі станом, які відкидають дублікати подій у межах ковзного часового вікна тривалістю `W` секунд.

Щоб не зберігати всі `N` ідентифікаторів у важкій хеш-таблиці пам'яті, застосовують імовірнісний **фільтр Блума** (англ. *Bloom Filter*) розміром `m` бітів із `k` незалежними хеш-функціями.

### Ймовірність хибнопозитивного спрацьовування (False Positive)

Якщо елемент відсутній у множині, фільтр Блума може помилково повернути `TRUE` (хибно вважати, що повідомлення вже було отримано), внаслідок чого фільтр повідомлень **безпідставно відкине унікальну подію** (*False Drop*).

Ймовірність хибного спрацьовування `p` після додавання `n` унікальних ключів виражається формулою:

```
p ≈ (1 - e^(-k·n / m))^k
```

Оптимальна кількість хеш-функцій `k_opt`, яка мінімізує `p` для фіксованого відношення `m/n`:

```
k_opt = (m / n) · ln(2) ≈ 0.693 · (m / n)
```

Підставивши `k_opt` у вираз для `p`, отримуємо мінімальну ймовірність помилки:

```
p_min = (1/2)^k_opt = 2^(-k_opt) = e^(- (m/n) · (ln 2)²)
```

### Розрахунок мінімального розміру пам'яті для нульових втрат

Виведемо необхідний обсяг бітового масиву `m` для забезпечення допустимої ймовірності втрати повідомлення `p_target`:

```
ln(p) = - (m / n) · (ln 2)²                      [логарифмування мінімальної ймовірності]

m = - (n · ln(p)) / (ln 2)²                      [вираження m]
```

Оскільки `(ln 2)² ≈ 0.480453`, отримуємо робочу інженерну формулу:

```
m ≈ - 2.081 · n · ln(p)      [бітів]
```

### Числовий розрахунок дедуплікатора:

Припустимо, вікно дедуплікації становить `W = 60` секунд, швидкість потоку `λ = 100 000` под/с, а допустима ймовірність хибного відкидання становить не більше однієї події на 1 000 000 (`p = 10⁻⁶`).

1. Кількість ключів у вікні:
```
n = λ · W = 100 000 · 60 = 6 000 000 ключів
```

2. Необхідний розмір бітового масиву `m`:
```
m = - 2.081 · 6 000 000 · ln(10⁻⁶)       [підстановка n та p у формулу розміру]
= - 2.081 · 6 000 000 · (-13.8155)       [обчислення натурального логарифма ln(10⁻⁶)]
= 172 500 000 бітів                      [множення коефіцієнтів]
= 21.56 МБ                               [переведення бітів у мегабайти (ділення на 8·1024²)]
```

3. Оптимальна кількість хеш-функцій `k`:
```
k = (172 500 000 / 6 000 000) · 0.693    [підстановка m і n у формулу оптимального k]
= 28.75 · 0.693                          [ділення бітів на кількість ключів]
≈ 20 хеш-функцій                         [округлення до найближчого цілого]
```

### Двопоколінний фільтр Блума для ковзного вікна (Generational Bloom Filter)

Оскільки стандартний фільтр Блума не підтримує операцію видалення застарілих ключів, для реалізації нескінченного ковзного вікна застосовують **два паралельні фільтри Блума** однакового розміру `m`:
* `B_active` (активне покоління, у яке записуються нові ключі поточної епохи `T`).
* `B_passive` (попереднє покоління за епоху `T - 1`).

Алгоритм перевірки та ротації:
1. Перевірка наявності: `exists(key) = B_active.contains(key) OR B_passive.contains(key)`.
2. Якщо ключ відсутній: `B_active.add(key)`.
3. Кожні `W` секунд відбувається ротація:
   `B_passive.clear()`
   `SWAP(B_passive, B_active)`

Сумарна ймовірність хибного відкидання для двох фільтрів обмежена сумою їхніх індивідуальних ймовірностей:

```
p_total ≤ p_active + p_passive ≈ 2 · p_min
```

Це дозволяє утримувати константне споживання пам'яті (рівно `43.1 МБ` для 6 мільйонів ключів) без зупинок на очищення та без ризику деградації точності фільтрації з часом.
