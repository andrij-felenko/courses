# 📋 Специфікація протоколу SWIM та бінарний формат Memberlist

Протокол взаємодії вузлів кластера на основі SWIM (Scalable Weakly-consistent Infection-style Process Group Membership) визначає бінарний формат дейтаграм у мережі, таблицю пріоритетів вирішення конфліктів станів членства, правила обробки крайових випадків та програмний інтерфейс для керування кластерними подіями.

---

## Бінарна модель дейтаграми та кодування повідомлень

Усі регулярні повідомлення протоколу передаються через ненадійний транспорт UDP. Для збереження сумісності з гетерогенними мережевими топологіями та гарантованого запобігання фрагментації IP-пакетів на проміжних маршрутизаторах сумарний розмір корисної дейтаграми не повинен перевищувати стандартний безпечний ліміт корисного навантаження у 1400 байтів. Якщо обсяг накопичених у черзі пліток перевищує цей поріг, протокол формує кілька незалежних пакетів або відкладає решту повідомлень на наступний раунд зондування.

Кожна UDP-дейтаграма складається з двох послідовних логічних блоків:
1. **Заголовок зонда (Probe Header)** — обов'язкова частина, що обслуговує пряме або непряме виявлення збоїв, містить монотонні ідентифікатори раундів та прапорці стану відправника.
2. **Буфер подій пліток (Piggybacked Gossip Buffer)** — змінна кількість упакованих повідомлень про зміну стану інших учасників кластера, які «наїздом» поширюються разом із запитом чи відповіддю.

```
+-------------------------------------------------------------------------------+
|                       Заголовок зонда (18..26 байтів)                         |
|  Magic (2B) | MsgType (1B) | Flags (1B) | SeqNo (8B) | TargetAddr (6..18B)    |
+-------------------------------------------------------------------------------+
|                 Буфер пліток: N упакованих повідомлень                        |
|  Count (1B) | Msg_1 [Len, Type, Data] | Msg_2 [Len, Type, Data] | ...         |
+-------------------------------------------------------------------------------+
```

Усі багатобайтові цілі числа в заголовках та корисних навантаженнях передаються виключно в мережевому порядку байтів (*big-endian* або порядок від старшого до молодшого). Будь-який вузол-одержувач зобов'язаний валідувати магічне число `Magic` перед обробкою тіла пакета; пакети з невідомим магічним числом або несумісною версією протоколу мають негайно відкидатися без генерації відповідей для захисту від атак підробки та сміттєвого трафіку.

### Таблиця кодів операцій (Message Types)

| Код типу | Назва повідомлення | Призначення та поведінка учасників |
| :--- | :--- | :--- |
| `0x01` | `PING` | Прямий запит перевірки доступності від вузла-ініціатора до вузла-цілі. Вимагає негайної генерації дейтаграми `ACK` з тим самим `SeqNo`. |
| `0x02` | `ACK` | Підтвердження живості у відповідь на прямий `PING` або транзитний `PING_REQ`. Переносить актуальну інкарнацію цілі. |
| `0x03` | `PING_REQ` | Непрямий запит: прохання до випадкового посередника виконати перевірку третього вузла та переслати отриманий результат ініціатору. |
| `0x04` | `SUSPECT` | Подія плітки: вузол переведено в підозрілий стан через відсутність відповідей на прямий і непрямі зонди. Запускає локальний таймер. |
| `0x05` | `ALIVE` | Подія плітки: вузол доступний, підключився до мережі або успішно спростував підозру шляхом монотонного підвищення інкарнації. |
| `0x06` | `DEAD` | Подія плітки: таймаут підозри вичерпано без отримання спростування. Вузол остаточно визнано аварійним і вилучено з топології. |
| `0x07` | `LEAVE` | Подія плітки: вузол добровільно та коректно завершує роботу (*graceful shutdown*), що дозволяє видалити його без періоду підозри. |
| `0x08` | `USER_MSG` | Користувацькі прикладні дані довільного формату, що розповсюджуються через епідемічний буфер кластера. |

### Поля заголовка повідомлень зондування

Заголовок зонда має фіксовану структуру полів, оптимізовану для швидкого розбору безпосередньо в буфері отримання ядра:

:::tabs
```c
#pragma pack(push, 1)
struct swim_probe_header {
    uint16_t magic;          /* Магічне число протоколу: 0x5357 ("SW") */
    uint8_t  msg_type;       /* Тип повідомлення: PING (0x01), ACK (0x02), PING_REQ (0x03) */
    uint8_t  flags;          /* Бітові прапорці: [0-3] LHM рівень, [4] IPv6, [5-7] резерв */
    uint64_t seq_no;         /* Монотонний номер послідовності зонду для точного матчингу Ack */
    uint32_t target_ip;      /* IPv4-адреса цілі (використовується в PING_REQ, інакше 0) */
    uint16_t target_port;    /* Порт цілі (використовується в PING_REQ, інакше 0) */
};
#pragma pack(pop)
```
```cpp
#pragma pack(push, 1)
struct alignas(1) SwimProbeHeader {
    uint16_t magic{0x5357};  // Магічне число протоколу ("SW")
    uint8_t  msg_type{0};    // Код операції
    uint8_t  flags{0};       // Рівень LHM та службові прапорці
    uint64_t seq_no{0};      // Монотонний ідентифікатор зонду
    uint32_t target_ip{0};   // IPv4 адреса цілі
    uint16_t target_port{0}; // Порт цілі
};
#pragma pack(pop)
```
:::

Поле `flags` дозволяє передавати метадані про стан здоров'я відправника. Молодші 4 біти містять поточне значення локального множника здоров'я (Local Health Multiplier, LHM) у діапазоні від 0 до 8. Якщо одержувач бачить, що відправник має високий LHM, він автоматично коригує свої очікування щодо часу затримки зворотного зв'язку.

### Формат елемента буфера пліток (Gossip Update Payload)

Після заголовка зонда розташовується один байт кількості упакованих повідомлень `Count`, за яким слідує масив елементів пліток. Кожен елемент має динамічну довжину:

:::tabs
```c
#pragma pack(push, 1)
struct swim_gossip_item {
    uint8_t  item_type;      /* Тип події: ALIVE (0x05), SUSPECT (0x04), DEAD (0x06), LEAVE (0x07) */
    uint32_t node_ip;        /* IPv4-адреса вузла, стан якого змінився */
    uint16_t node_port;      /* Порт вузла */
    uint64_t incarnation;    /* Номер інкарнації вузла (лічильник спростувань) */
    uint8_t  payload_len;    /* Довжина додаткових метаданих або імені вузла */
};
#pragma pack(pop)
```
```cpp
#pragma pack(push, 1)
struct alignas(1) SwimGossipItem {
    uint8_t  item_type{0};   // Тип події членства
    uint32_t node_ip{0};     // IPv4 адреса вузла
    uint16_t node_port{0};   // Порт вузла
    uint64_t incarnation{0}; // Номер інкарнації
    uint8_t  payload_len{0}; // Довжина метаданих
};
#pragma pack(pop)
```
:::

Така упаковка гарантує, що кожна дейтаграма зондування одночасно просуває інформацію про зміну стану десятків інших вузлів без відкриття додаткових мережевих з'єднань і без генерації окремих пакетів.

## Матриця вирішення конфліктів станів (State Resolution Matrix)

Оскільки інформація в розподіленій системі поширюється асинхронно та різними маршрутами, вузол регулярно отримує повідомлення, що суперечать його поточному локальному стану або містять застарілі дані.

Для кожного відомого учасника кластера локальна таблиця зберігає запис виду `{стан, інкарнація, таймер_підозри}`.
При отриманні вхідного оновлення `{новий_стан, нова_інкарнація}` автомат переходу станів застосовує детерміновану матрицю вирішення конфліктів:

```
+-------------------+-----------------------------------------------------------+
| Співвідношення    | Результат обробки вхідного оновлення                      |
+-------------------+-----------------------------------------------------------+
| inc_new > inc_loc | ПРИЙНЯТИ: Оновити локальний стан на новий, встановити     |
|                   | нову інкарнацію. Новіша інкарнація завжди перемагає.      |
+-------------------+-----------------------------------------------------------+
| inc_new < inc_loc | ВІДХИЛИТИ: Ігнорувати як застаріле повідомлення.          |
|                   | Вузол має право відправити у відповідь актуальну плітку.  |
+-------------------+-----------------------------------------------------------+
| inc_new == inc_loc| ВИРІШЕННЯ ЗА ПРІОРИТЕТОМ СТАНІВ:                          |
|                   | 1. DEAD > SUSPECT > ALIVE                                 |
|                   | 2. Якщо локально ALIVE, а прийшло SUSPECT → стати SUSPECT.|
|                   | 3. Якщо локально SUSPECT, а прийшло ALIVE → ІГНОРУВАТИ    |
|                   |    (Alive не може зняти підозру тієї самої інкарнації!).  |
|                   | 4. Якщо локально SUSPECT, а прийшло DEAD → стати DEAD.    |
|                   | 5. Якщо локально DEAD, а прийшло ALIVE/SUSPECT → ІГНОР.   |
+-------------------+-----------------------------------------------------------+
```

### Алгоритм спростування власної підозри (Self-Refutation Contract)

Якщо сервер `A` отримує через буфер пліток повідомлення про те, що інший учасник вважає його `SUSPECT` з інкарнацією `i`, де `i >= inc_local(A)`:
1. Вузол `A` діагностує, що в мережі виникла помилкова підозра щодо його доступності (наприклад, через тимчасову втрату пакетів або затримку планувальника ОС).
2. Вузол `A` негайно інкрементує власну монотонну інкарнацію: `inc_local(A) = i + 1`.
3. Вузол генерує нове власне повідомлення `ALIVE(A, inc_local(A))` і вміщує його в початок черги ретрансляції з найвищим пріоритетом.
4. Оскільки `i + 1 > i`, будь-який інший вузол у кластері при отриманні цієї плітки автоматично скасує стан підозри та поверне вузол `A` у статус `ALIVE`.

## Обробка крайових випадків та відмовних сценаріїв

Протокол SWIM розрахований на роботу в умовах постійних мережевих збоїв, тому реалізація повинна коректно обробляти специфічні сценарії деградації:

### 1. Асиметрична втрата зв'язку (Asymmetric Partition)
Якщо комутатор пропускає пакети від вузла `A` до `B`, але блокує зворотний напрямок від `B` до `A`:
* Прямий зонд від `A` до `B` зазнає невдачі через відсутність відповіді `ACK`.
* Непрямий запит `PING_REQ`, надісланий через посередника `C`, успішно досягає мети, якщо зв'язок `C ↔ B` та `C ↔ A` не порушено.
* Це запобігає ізоляції та помилковому виключенню вузла `B` з кластера лише через локальну несправність одного каналу.

### 2. Захист від штормів спростувань (Flapping & Refutation Throttling)
Якщо зв'язок між вузлами періодично переривається на кілька мілісекунд кожні кілька секунд, вузол може нескінченно підвищувати інкарнацію у відповідь на хвилі підозр. Щоб уникнути переповнення числових типів та дестабілізації реєстру:
* Інкарнація зберігається як 64-бітне беззнакове число (`uint64_t`), що унеможливлює переповнення в реальних умовах.
* Вузол обмежує максимальну частоту генерації спростувань (rate limiting) — не більше одного спростування за період `T_ack`.

### 3. Перезапуск процесу без збереження стану на диску (Crash-Recovery)
Якщо вузол аварійно перезавантажується і втрачає свій лічильник інкарнацій (скидаючи його до 0), решта кластера пам'ятає його попередню інкарнацію (наприклад, `inc = 42`).
* Перший надісланий вузлом пакет `ALIVE(inc = 0)` буде проігноровано кластером як застарілий.
* Сусіди, вважаючи вузол все ще підозрілим або мертвим, надішлють йому плітку `SUSPECT(inc = 42)`.
* Отримавши це повідомлення, щойно перезапущений вузол виконає стандартне правило спростування: встановить локальну інкарнацію `inc = 42 + 1 = 43` і розішле `ALIVE(inc = 43)`, миттєво відновивши свій статус у кластері без ручного втручання.

## Протокол повної анти-ентропійної синхронізації (TCP Full-Sync)

Хоча епідемічний транспорт через UDP гарантує швидке розповсюдження подій у нормальних умовах, тривале розділення мережі (Network Partitioning) або катастрофічні втрати пакетів можуть призвести до того, що окремі вузли пропустять серію оновлень.

Для захисту від накопичення розбіжностей протокол реалізує фоновий механізм повної синхронізації (Anti-Entropy Repair) через надійний TCP-протокол:
1. Раз на період `SyncInterval` (типово 30–60 секунд) вузол випадковим чином обирає одного партнера з активного списку членів.
2. Вузол відкриває короткоживуче TCP-з'єднання з обраним партнером.
3. Сторони обмінюються повними списками відомих учасників із їхніми поточними інкарнаціями та станами.
4. Кожен учасник зіставляє отриманий список зі своєю локальною таблицею, застосовуючи стандартну матрицю вирішення конфліктів. Будь-які пропущені вузли чи свіжіші інкарнації миттєво додаються до локальної бази.
5. TCP-з'єднання коректно закривається.

Цей механізм гарантує, що після відновлення зв'язку між ізольованими сегментами дата-центру кластер повертається до абсолютно узгодженого стану протягом одного-двох циклів повної синхронізації.

## Таблиця параметрів конфігурації протоколу

| Параметр | Типове значення (LAN) | Типове значення (WAN) | Опис та вплив на поведінку |
| :--- | :--- | :--- | :--- |
| `ProbeInterval` (`T_probe`) | `1000 мс` | `5000 мс` | Періодичність вибору випадкового вузла для прямого зондування |

## Публічний інтерфейс бібліотеки (C/C++ API Contract)

### Структури конфігурації та представлення вузла

:::tabs
```c
typedef enum {
    SWIM_NODE_ALIVE   = 0,
    SWIM_NODE_SUSPECT = 1,
    SWIM_NODE_DEAD    = 2,
    SWIM_NODE_LEFT    = 3
} swim_node_status_t;

typedef struct {
    uint32_t ip;                    /* Мережева IPv4-адреса у форматі Network Byte Order */
    uint16_t port;                  /* UDP-порт для обміну дейтаграмами */
    uint64_t incarnation;           /* Поточний номер інкарнації вузла */
    swim_node_status_t status;      /* Поточний статус членства */
    uint64_t state_change_time_ms;  /* Монотонна часова мітка останньої зміни стану */
    uint8_t  suspect_confirmations; /* Кількість незалежних підтверджень підозри */
} swim_member_t;

typedef struct {
    uint32_t bind_ip;               /* Локальна адреса для прив'язки сокета */
    uint16_t bind_port;             /* Локальний порт */
    uint32_t probe_interval_ms;     /* Інтервал між раундами зондування (T_probe) */
    uint32_t probe_timeout_ms;      /* Таймаут прямої відповіді (T_ack) */
    uint32_t indirect_checks_k;     /* Кількість посередників для непрямих перевірок */
    uint32_t suspicion_multiplier;  /* Множник розрахунку максимального часу підозри */
    uint32_t retransmit_multiplier; /* Множник кількості повторних передач плітки */
    
    /* Колбеки сповіщення прикладного коду про зміну топології */
    void (*on_node_join)(const swim_member_t *member, void *userdata);
    void (*on_node_leave)(const swim_member_t *member, void *userdata);
    void (*on_node_failed)(const swim_member_t *member, void *userdata);
    void (*on_user_message)(const uint8_t *data, size_t len, void *userdata);
    void *userdata;                 /* Користувацький контекст для передачі в колбеки */
} swim_config_t;
```
```cpp
#include <cstdint>
#include <chrono>
#include <functional>
#include <string_view>
#include <span>

namespace swim {

enum class NodeStatus : uint8_t {
    Alive   = 0,
    Suspect = 1,
    Dead    = 2,
    Left    = 3
};

struct Member {
    uint32_t ip{0};
    uint16_t port{0};
    uint64_t incarnation{0};
    NodeStatus status{NodeStatus::Alive};
    std::chrono::steady_clock::time_point state_change_time;
    uint8_t suspect_confirmations{0};
};

struct Config {
    uint32_t bind_ip{0};
    uint16_t bind_port{0};
    std::chrono::milliseconds probe_interval{1000};
    std::chrono::milliseconds probe_timeout{200};
    uint32_t indirect_checks_k{3};
```

```c
/*
 * swim_create - ініціалізує екземпляр вузла, прив'язує неблокуючий UDP-сокет.
 * Повертає вказівник на створений контекст або NULL у разі помилки виділення пам'яті чи сокета.

 * swim_join - підключає поточний вузол до кластера через відому адресу сіда (seed node).
 * Надсилає пакет прямого зондування із прапорцем Join. Повертає 0 у разі успіху, -1 у разі помилки.

 * swim_step - головна ітерація протокольного циклу.
 * Виконує обробку черги вхідних дейтаграм, відправку зондів за розкладом,
 * перевірку спливання таймерів підозр та пакування пліток у вихідні дейтаграми.

void swim_step(swim_context_t *ctx);

 * swim_broadcast_user_message - публікує прикладне повідомлення через буфер пліток.

 * swim_leave - ініціює коректний вихід вузла з кластера.
```
