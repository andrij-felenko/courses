# 🧮 Математика кредитного вікна, гістерезису водяних знаків та динаміки черг

Ця вставка містить аналітичне виведення формул розрахунку розміру кредитного вікна, порогів водяних знаків (High/Low Watermarks), теорії черг кінцевої місткості та часових характеристик стабільності буферів у розподілених системах керування потоком.

Без точного математичного розрахунку розміру вікна розподілений конвеєр або захлинається від переповнення пам'яті через запізнілу реакцію на зворотний зв'язок, або страждає від простою обчислювальних ядер (англ. *pipeline starvation*) через надто малий виданий кредит.

---

## 1. Динаміка переповнення некерованого буфера

Нехай вхідний потік повідомлень надходить із середньою інтенсивністю `λ` (повідомлень/с), а обробник вичитує та записує результати з інтенсивністю `μ` (повідомлень/с).

Якщо `λ > μ`, буфер місткістю `B` накопичує невідпрацьовані повідомлення. Швидкість зміни кількості елементів у буфері `Q(t)` у часі описується диференціальним рівнянням неперервності:

```
dQ(t)/dt
= λ - μ          [баланс вхідного та вихідного потоків]
```

Інтегруючи за початкових умов `Q(0) = 0`, отримуємо залежність заповнення черги від часу:

```
Q(t)
= ∫ (λ - μ) dt   [інтегрування постійного дефіциту швидкості]
= (λ - μ)·t      [лінійне зростання черги]
```

Час до повного переповнення буфера `T_overflow`, коли `Q(t) = B`, становить:

```
B
= (λ - μ)·T_overflow   [рівняння насичення ємності]

T_overflow
= B ÷ (λ - μ)          [час до вичерпання виділеної пам'яті]
```

### Числовий розрахунок катастрофи пам'яті

Нехай сервер виділяє під буфер черги пам'ять на `B = 50 000` повідомлень. Вхідний потік через сплеск трафіку зріс до `λ = 25 000` повідомлень/с, тоді як база даних уповільнилася до `μ = 5 000` повідомлень/с:

```
T_overflow
= 50 000 ÷ (25 000 - 5 000)
= 50 000 ÷ 20 000
= 2.5 с          [через 2.5 секунди процес зазнає аварії або почне скидати дані]
```

Будь-який фіксований локальний буфер без наскрізного регулювання джерела лише відкладає аварію на час `T_overflow`.

## 2. Модель системи масового обслуговування M/M/1/K з обмеженим буфером

Розглянемо чергу з пуассонівським вхідним потоком інтенсивності `λ`, експоненційним часом обслуговування з параметром `μ` та жорстким обмеженням на максимальну кількість вимог у системі `K` (включно з тією, що обслуговується).

Коефіцієнт завантаження системи `ρ` (rho) визначається відношенням:

```
ρ
= λ ÷ μ          [інтенсивність навантаження системи]
```

Ймовірність перебування системи в стані `k` (наявність рівно `k` елементів у буфері) задається розподілом стаціонарного процесу Маркова:

```
p_0
= (1 - ρ) ÷ (1 - ρ^(K + 1))   [нормалізуючий множник для ρ ≠ 1]

p_k
= p_0 · ρ^k
= ((1 - ρ) · ρ^k) ÷ (1 - ρ^(K + 1))   [ймовірність накопичення k елементів]
```

Ймовірність блокування нового вхідного повідомлення `p_loss` (коли буфер повністю заповнений `k = K`):

```
p_loss
= p_K
= ((1 - ρ) · ρ^K) ÷ (1 - ρ^(K + 1))   [ймовірність відмови за відсутності протитиску]
```

Якщо система не має зворотного зв'язку, при `ρ > 1` (перевантаження) ймовірність відмови асимптотично прямує до:

```
lim_{K→∞} p_loss
= (ρ - 1) ÷ ρ    [частка втрачених запитів у стаціонарному режимі]
```

Для `λ = 25 000` та `μ = 5 000` маємо `ρ = 5.0`. Без протитиску частка втрат становитиме `(5 - 1) / 5 = 0.8` (80% всього вхідного трафіку скидається).

## 3. Розрахунок мінімального кредитного вікна (Bandwidth-Delay Product)

Щоб обчислювальний конвеєр не простоював у стані очікування дозволу на передачу, обсяг виданого споживачем кредиту `W` (Credit Window) повинен покривати час кругового обігу сигналу (англ. *Round-Trip Time*, `RTT`).

`RTT` складається з часу передачі даних від відправника до одержувача `T_fwd`, часу обробки та генерації зворотного кредиту `T_proc`, і часу доставки кадру оновлення вікна назад відправнику `T_rev`:

```
RTT
= T_fwd + T_proc + T_rev   [сумарна затримка кругового циклу зворотного зв'язку]
```

Добуток пропускної здатності на затримку (Bandwidth-Delay Product, `BDP`) визначає обсяг даних, який повинен перебувати «у польоті» (in-flight) для 100% завантаження споживача:

```
BDP
= RTT · μ        [необхідний запас повідомлень у дорозі]
```

Для запобігання голодуванню конвеєра кредитне вікно `W` повинно задовольняти нерівність:

```
W_min
= BDP
= RTT · μ        [мінімальний кредит для неперервного потоку]
```

Якщо `W < W_min`, відправник вичерпає кредит за час `T_transmit = W ÷ μ < RTT` і буде змушений заблокувати потік на час `T_idle = RTT - (W ÷ μ)`.

Ефективна пропускна здатність системи `μ_eff` у такому разі падає:

```
μ_eff
= W ÷ RTT        [обмеження пропускної здатності за малого кредиту]
```

## 4. Розрахунок High Watermark з урахуванням стохастичного джиттеру

У реальних IP-мережах час доставки зворотного сигналу не є константою, а розподілений стохастично із середнім `RTT_avg` та стандартним відхиленням `σ_RTT` (джиттер затримки).

Для гарантії запобігання переповненню з імовірністю `99.7%` (правило трьох сигм `3σ`), розрахунковий час затримки сигналу зупинки `T_stop_max` становить:

```
T_stop_max
= (RTT_avg + 3·σ_RTT) ÷ 2   [максимальна затримка сигналу паузи в мережі]
```

Обсяг даних, що надійде після перетину порогу:

```
V_inflight_max
= T_stop_max · λ_max
= ((RTT_avg + 3·σ_RTT) ÷ 2) · λ_max   [верхня межа обсягу пакетів у польоті]
```

Повний безпечний поріг High Watermark (`HWM`):

```
HWM
= B_total - V_inflight_max
= B_total - ((RTT_avg + 3·σ_RTT) ÷ 2) · λ_max   [поріг з урахуванням джиттеру]
```

## 5. Гістерезис водяних знаків та частота осциляцій

Якщо поріг відновлення читання (Low Watermark, `LWM`) встановити надто близько до `HWM` (`LWM ≈ HWM`), буфер потрапляє в режим паразитного високочастотного перемикання (англ. *chatter / flapping*). Кожне вичитане повідомлення вмикає прийом, а наступне вхідне — миттєво його вимикає.

Розрахуємо тривалість циклу коливань `T_cycle` як суму часу заповнення від `LWM` до `HWM` (`T_fill`) та часу спорожнення від `HWM` до `LWM` (`T_drain`):

```
T_fill
= (HWM - LWM) ÷ (λ - μ)    [час росту черги за активного джерела]

T_drain
= (HWM - LWM) ÷ μ          [час розвантаження черги за зупиненого джерела]

T_cycle
= T_fill + T_drain
= (HWM - LWM)·(1 ÷ (λ - μ) + 1 ÷ μ)
= (HWM - LWM)·(λ ÷ (μ·(λ - μ)))   [повний період перемикання станів]
```

Частота спрацьовування системних викликів керування сокетом `f_switch` (перемикання `EPOLLIN`):

```
f_switch
= 1 ÷ T_cycle
= (μ·(λ - μ)) ÷ (λ·(HWM - LWM))   [частота навантаження на планувальник ОС]
```

Щоб обмежити частоту перемикань безпечним рівнем `f_max` (наприклад, не більше 50 перемикань/с для мінімізації накладних витрат на системні виклики), ширина вікна гістерезису `Δ_h = HWM - LWM` повинна задовольняти умову:

```
Δ_h
= HWM - LWM
≥ (μ·(λ - μ)) ÷ (λ·f_max)   [мінімальна ширина зони гістерезису]
```

Типове інженерне емпіричне правило для розподілених шлюзів:
* `HWM = 0.8 · B_total` (80% місткості);
* `LWM = 0.3 · B_total` (30% місткості).

## 6. Багатоланковий конвеєр: кумулятивна затримка поширення протитиску

У розподіленому конвеєрі з `M` послідовних вузлів (наприклад, `Клієнт → Шлюз → Сервіс A → Сервіс B → База даних`) кожен проміжний перехід `i` має власну затримку зв'язку `RTT_i` та власний локальний буфер `B_i`.

Загальний час розповсюдження сигналу протитиску від бази даних до клієнта `T_prop_total`:

```
T_prop_total
= ∑_{i=1}^{M-1} (RTT_i ÷ 2 + T_proc_i)   [сумарний час зворотного зв'язку]
```

Сумарний обсяг повідомлень, накопичений у всіх проміжних буферах конвеєра під час гальмування:

```
V_pipeline_total
= ∑_{i=1}^{M-1} B_i   [загальна місткість розподіленого конвеєра]
```

Закон Літтла для стаціонарної системи пов'язує середню кількість повідомлень у черзі `L`, середню інтенсивність надходження `λ` та середній час очікування в системі `W_q`:

```
L
= λ · W_q        [закон Літтла]

W_q
= L ÷ λ          [середня затримка очікування в черзі]
```

Коли система застосовує наскрізний кредитний протитиск, довжина черги `L` суворо обмежена сумарним пулом виданих кредитів `L ≤ W_credit`.

Звідси максимальний гарантований час очікування повідомлення в конвеєрі `W_q_max` становить:

```
W_q_max
= W_credit ÷ μ   [детермінована верхня межа затримки]
```

## 7. Оптимальний розмір пачки поповнення кредитів (Credit Replenishment Batching)

Якщо надсилати кадр оновлення кредиту (`WINDOW_UPDATE` / `REQUEST_N`) на кожне окреме вичитане повідомлення, мережа перевантажується службовими заголовками TCP/IP (40–60 байтів заголовка на 4 байти корисного навантаження). Якщо ж оновлювати кредит надто рідко (великими пачками), відправник простоюватиме в очікуванні дозволу.

Нехай:
* `C_overhead` — накладні витрати на передачу одного службового кадру (в байтах або процесорних тактах);
* `C_delay` — ціна затримки простою конвеєра на одиницю часу;
* `G` — розмір пачки поповнення кредиту (Grant Size).

Сумарна функція втрат `Cost(G)` на одиницю часу:

```
Cost(G)
= (μ ÷ G) · C_overhead + (G ÷ (2·μ)) · C_delay   [баланс накладних витрат мережі та очікування]
```

Мінімізуючи функцію втрат за `G` (`dCost/dG = 0`):

```
dCost/dG
= - (μ · C_overhead) ÷ G² + C_delay ÷ (2·μ)
= 0              [умова екстремуму функції витрат]

G_optimal
= √((2 · μ² · C_overhead) ÷ C_delay)   [оптимальний розмір порції поповнення кредитів]
```

Для більшості високонавантажених мережевих сервісів оптимальним є поповнення кредиту порціями розміром `G = 0.25 · W_credit` (чверть повного кредитного вікна), що скорочує кількість керуючих пакетів на 75% без ризику зупинки конвеєра.
