# 📜 Крах розподілених об'єктів та народження патерну Remote Facade

Ідея створення розподілених систем у 1980-х та 1990-х роках розвивалася під впливом об'єктно-орієнтованої парадигми. Мови C++ та Smalltalk продемонстрували надзвичайну потужність інкапсуляції: програміст оперував абстракціями об'єктів, викликаючи методи та приховуючи внутрішні структури даних за дрібнозернистими сетерами й гетерами. Інженерам здавалося природним зробити наступний логічний крок — поширити цю модель на всю комп'ютерну мережу, створивши ілюзію єдиного глобального простору об'єктів.

Так народилася концепція «прозорості розташування» (*Location Transparency*). Її головна теза стверджувала: розробник бізнес-логіки не повинен знати, де фізично розташований об'єкт — у сусідній комірці оперативної пам'яті, на сусідньому комп'ютері в локальній стійці чи на сервері за океаном. Синтаксис виклику мав залишатися ідентичним: `customer.getAddress().getCity()`.

### Епоха розподілених брокерів: CORBA, DCOM та Java RMI

Для реалізації цієї ідеї провідні технологічні консорціуми та компанії створили складні інфраструктурні стандарти:
1. **CORBA (Common Object Request Broker Architecture):** створена у 1991 році консорціумом OMG (*Object Management Group*), що об'єднував понад 700 компаній (включно з IBM, Sun, HP, DEC). CORBA запровадила мову опису інтерфейсів IDL (*Interface Definition Language*) та брокери об'єктних запитів (ORB), які автоматично генерували клієнтські заглушки (*stubs*) та серверні скелетони (*skeletons*).
2. **DCOM (Distributed Component Object Model):** відповідь Microsoft у 1996 році, яка інтегрувала віддалені виклики в саму операційну систему Windows через протокол MS-RPC.
3. **Java RMI (Remote Method Invocation) та EJB (Enterprise JavaBeans):** представлені Sun Microsystems у 1997–1999 роках. Специфікація EJB 1.0/2.0 ввела концепцію «сутностей» (*Entity Beans*), де кожен рядок таблиці реляційної бази даних проектувався у віддалений об'єкт.

У підручниках і презентаціях того часу це виглядало тріумфом архітектури. Щоб відобразити список замовлень клієнта, розробник писав звичний цикл:

```text
Customer customer = customerHome.findByPrimaryKey(customerId);
List<Order> orders = customer.getOrders();
for (Order order : orders) {
    String orderId = order.getId();
    Money total = order.calculateTotal();
    Address shipTo = order.getShippingAddress();
    String city = shipTo.getCity();
    printOrder(orderId, total, city);
}
```

### Зіткнення з фізикою: катастрофа N+1 та мережеве перевантаження

Коли ці системи вийшли за межі демонстраційних стендів у реальну промислову експлуатацію на каналах корпоративних мереж і раннього інтернету, сталася катастрофа продуктивності.

У наведеному фрагменті коду один логічний екран користувача ініціював:
* 1 виклик `findByPrimaryKey` для завантаження об'єкта клієнта;
* 1 виклик `getOrders` для отримання списку ідентифікаторів замовлень;
* Для кожного з 50 замовлень — окремі виклики `getId`, `calculateTotal`, `getShippingAddress` та `getCity`.

Разом один показ сторінки виконував:
```
1 + 1 + 50 × 4 = 202 віддалених виклики
```

У локальній пам'яті 202 виклики функцій виконуються за `202 × 5 нс ≈ 1 мкс` — час, який людина не здатна відчути. Проте через мережу WAN із круговою затримкою (RTT) у 50 мс сумарний час виконання становив:
```
202 × 50 мс = 10 100 мс = 10.1 секунди!
```

Сервери баз даних і мережеві комутатори були паралізовані мільйонами дрібних TCP-пакетів. Кожен пакет ніс 40–60 байтів службових заголовків (IP + TCP + CORBA GIOP / RMI header) заради передачі 4 байтів корисних даних (наприклад, суми знижки чи назви міста).

### Маніфест Вольдо: чому локальне не може бути віддаленим

У 1994 році дослідники Sun Microsystems Laboratories — Джим Вольдо (*Jim Waldo*), Джефф Вайант (*Geoff Wyant*), Енн Воллрат (*Ann Wollrath*) та Сем Кендалл (*Sam Kendall*) — опублікували фундаментальну наукову статтю під назвою **«A Note on Distributed Computing»** (Технічний звіт SMLI TR-94-29).

Ця праця стала поворотним моментом в історії комп'ютерних наук. Автори математично та інженерно довели, що спроба уніфікувати локальну та розподілену обчислювальні моделі приречена на провал через чотири нездоланні фізичні розбіжності:
1. **Затримка (Latency):** різниця між доступом до RAM і мережевим викликом становить від 4 до 6 порядків величини (мікросекунди проти мілісекунд). Локальний дизайн заохочує дрібні методи; мережевий вимагає мінімізації кількості викликів.
2. **Пам'ять (Memory Access):** локальний об'єкт спирається на спільний адресний простір і передачу вказівників. Розподілений об'єкт вимагає серіалізації всього графа стану.
3. **Паралелізм (Concurrency):** у розподіленій системі клієнт і сервер виконуються на різних фізичних процесорах без єдиного тактового генератора та механізмів атомарного блокування шини.
4. **Часткова відмова (Partial Failure):** локальна програма падає повністю при апаратній аварії (спільна доля). У розподіленій системі сервер може вийти з ладу після отримання команди, залишивши клієнта в стані невизначеності.

Вольдо та співавтори підсумували: інтерфейс, спроєктований для локального використання, принципово непридатний для віддаленого доступу, а приховування мережі є найнебезпечнішою архітектурною помилкою.

### Формулювання Remote Facade та DTO Мартіном Фаулером

У 2002 році Мартін Фаулер (*Martin Fowler*) у фундаментальній книзі **«Patterns of Enterprise Application Architecture»** (PoEAA) узагальнив гіркий досвід індустрії та формалізував два ключові патерни, що стали стандартом сучасної розподіленої інженерії:

1. **Remote Facade (Віддалений фасад):**
   Грубозернистий інтерфейс, розміщений на межі мережі, який перетворює безліч дрібних операцій внутрішньої доменної моделі на один великий композитний виклик. Фасад виконується всередині адресного простору сервера, де доступ до сутностей займає наносекунди, і повертає клієнту повністю зібраний зліпок даних за один круговий рейс.

2. **Data Transfer Object (DTO, Об'єкт передачі даних):**
   Простий серіалізовний контейнер даних без жодної бізнес-логіки та без методів-поведінки. DTO містить рівно ті поля, які потрібні клієнту для виконання конкретного сценарію (наприклад, рендерингу сторінки або обробки форми), що ліквідує як N+1 виклики, так і передачу надлишкових байтів.

Перехід від дрібнозернистих розподілених об'єктів до грубозернистих фасадів і DTO започаткував еру сучасної сервісно-орієнтованої архітектури (SOA), веб-сервісів REST/JSON, протоколів gRPC та GraphQL. Сьогодні концепція грубозернистої віддаленої межі є базовим правилом проектування будь-якої масштабованої системи.
