# 🧮 Математика топології шини: комбінаторика зв'язності n×m, надійність системи та затримки конвеєра в теорії масового обслуговування

Вибір між прямою попарною інтеграцією сервісів і впровадженням централізованої шини повідомлень не є питанням смаку чи моди: це суворе математичне співвідношення між кількістю вузлів системи, швидкістю зростання комбінаторних зв'язків, ланцюговою теорією надійності, законами розподілу черг у теорії масового обслуговування та статистикою нерівномірного навантаження.

Якщо побудувати математичні моделі обох архітектур, стає очевидним, чому попарні зв'язки неминуче колапсують при зростанні числа вузлів, як асинхронний буфер шини рятує ймовірність успішного завершення транзакцій, в якій саме точці завантаження центральний диспетчер шини сам стає джерелом вибухового зростання затримок та як нерівномірність розподілу ключів партиціонування породжує ефект «гарячого вузла».

## 1. Теорія графів і комбінаторика зв'язності: квадратичний глухий кут проти лінійної магістралі

Розглянемо розподілену систему з `N` незалежних взаємодіючих сервісів (вузлів).

У моделі прямої попарної інтеграції кожен сервіс для повноцінної взаємодії повинен мати встановлений двосторонній канал зв'язку з кожним іншим сервісом. У термінах теорії графів така топологія є повним неорієнтованим графом `K_N` (або повним орієнтованим графом з двома дугами на кожне ребро).

Кількість ребер `E_p2p` у повному неорієнтованому графі з `N` вершинами визначається біноміальним коефіцієнтом вибору 2 елементів з `N`:

```
E_p2p = C(N, 2)
      = N! / (2! · (N − 2)!)          [означення числа комбінацій]
      = (N · (N − 1) · (N − 2)!) / (2 · (N − 2)!)  [скорочення факторіала]
      = N · (N − 1) / 2               [квадратична складність O(N²)]
```

Якщо канали зв'язку є орієнтованими (клієнт надсилає запити до сервера за власним API-контрактом), загальна кількість спрямованих каналів `C_p2p` становить:

```
C_p2p = 2 · E_p2p
      = 2 · (N · (N − 1) / 2)         [підстановка E_p2p]
      = N · (N − 1)                   [розкриття дужок]
      = N² − N                        [напрямлені зв'язки між усіма парами]
```

На противагу цьому топологія шини повідомлень організована як зіркоподібний / двочастковий граф з одним виділеним центральним вузлом магістралі `B`. Кожен із `N` периферійних сервісів підключається виключно до центральної шини. Кількість фізичних каналів підключення `E_bus` зростає суворо лінійно:

```
E_bus = N                             [лінійна складність O(N)]
```

### Комбінаторика адаптерів і трансляторів форматів даних

Найбільш руйнівним наслідком попарної інтеграції є не кількість мережевих сокетів, а кількість програмних трансляторів форматів даних (патерн *Message Translator*). Нехай кожен із `N` сервісів володіє власним локальним форматом даних (схемою сутностей, типами серіалізації, діалектом помилок).

1. **У системі без канонічної моделі (попарна адаптація):**
   Для того щоб сервіс `i` міг передати структуровані дані сервісу `j`, необхідно написати функцію прямої трансляції `T(i → j)`. Загальна кількість необхідних функцій-адаптерів `T_p2p(N)` дорівнює кількості орієнтованих пар:

```
T_p2p(N) = N · (N − 1) = N² − N
```

2. **У системі з канонічною моделлю даних (Canonical Data Model, CDM) на шині:**
   Визначається єдина загальносистемна канонічна схема `S_canon`. Кожен сервіс `i` реалізує рівно дві функції трансляції:
   - Вхідний адаптер (Inbound): `T_in(i): S_local(i) → S_canon` (експорт у шину);
   - Вихідний адаптер (Outbound): `T_out(i): S_canon → S_local(i)` (імпорт із шини).

Загальна кількість адаптерів у системі на основі шини `T_bus(N)` становить:

```
T_bus(N) = 2 · N
```

Виведемо формулу абсолютної економії трансляторів `ΔT(N)` та відносного коефіцієнта скорочення складності `η(N)`:

```
ΔT(N) = T_p2p(N) − T_bus(N)
      = (N² − N) − 2 · N              [підстановка формул]
      = N² − 3 · N                    [зведення подібних]
      = N · (N − 3)                   [винесення спільного множника]
```

Відносний коефіцієнт скорочення інженерної складності `η(N)`:

```
η(N) = ΔT(N) / T_p2p(N)
     = (N² − 3·N) / (N² − N)          [відношення економії до базового обсягу]
     = (N · (N − 3)) / (N · (N − 1))  [факторизація чисельника й знаменника]
     = (N − 3) / (N − 1)              [скорочення на N ≠ 0]
     = ((N − 1) − 2) / (N − 1)        [виділення цілої частини]
     = 1 − (2 / (N − 1))              [канонічний вигляд коефіцієнта економії]
```

Порівняймо ці величини для різних масштабів системи:

| Кількість сервісів `N` | Попарні канали `E_p2p` | Попарні адаптери `T_p2p` | Канали шини `E_bus` | Адаптери шини `T_bus` | Економія адаптерів `ΔT` | Коефіцієнт скорочення `η` |
|---|---|---|---|---|---|---|
| **3** | 3 | 6 | 3 | 6 | 0 | 0.0% |
| **5** | 10 | 20 | 5 | 10 | 10 | 50.0% |
| **10** | 45 | 90 | 10 | 20 | 70 | 77.8% |
| **20** | 190 | 380 | 20 | 40 | 340 | 89.5% |
| **50** | 1225 | 2450 | 50 | 100 | 2350 | 95.9% |
| **100** | 4950 | 9900 | 100 | 200 | 9700 | 98.0% |

При зростанні кількості сервісів до 50 попарна інтеграція вимагає розробки та підтримки 2450 окремих конвертерів коду, тоді як архітектура шини вимагає лише 100 адаптерів, скорочуючи обсяг інтеграційного коду на 95.9%.

## 2. Теорія надійності: чому синхронні ланцюги викликів прямують до нульової доступності

Розглянемо розподілений бізнес-процес (наприклад, оформлення замовлення), який вимагає участі ланцюжка з `k` окремих мікросервісів.

Нехай кожен сервіс `i` має незалежну ймовірність доступності (коефіцієнт готовності) `A_i = P(Сервіс_i працює та відповідає)`, де `0 < A_i < 1`.

### Синхронний ланцюг викликів (послідовна модель надійності)

У синхронній попарній архітектурі (HTTP/gRPC) для успішного виконання транзакції **усі `k` сервісів повинні бути доступними, працездатними та мати стабільне з'єднання одночасно в один і той самий момент часу**:

```
R_sync(k) = P(A₁ ∩ A₂ ∩ ... ∩ A_k)
          = A₁ · A₂ · ... · A_k       [правило множення для незалежних подій]
          = ∏[i=1..k] A_i
```

Якщо припустити, що всі сервіси мають типовий промисловий рівень доступності трьох дев'яток `A = 0.999` (недоступність 8.76 годин на рік) або двох дев'яток `A = 0.99` (недоступність 3.65 днів на рік):

```
R_sync(k) = A^k
```

Обчислимо надійність синхронного ланцюга для різної довжини `k`:

```
Для A = 0.99 (99.0% доступності кожного компонента):
k = 1:  R = 0.9900  (простій 3.65 днів/рік)
k = 3:  R = 0.99³  = 0.9703  (простій 10.84 днів/рік)
k = 5:  R = 0.99⁵  = 0.9510  (простій 17.89 днів/рік)
k = 10: R = 0.99¹⁰ = 0.9044  (простій 34.90 днів/рік — система лежить більше місяця на рік!)
k = 20: R = 0.99²⁰ = 0.8179  (простій 66.46 днів/рік)
```

Синхронний ланцюг із 10 сервісів знижує загальну доступність платформи з 99% до 90.4%, перетворюючи систему на постійне джерело каскадних відмов.

### Асинхронна шина повідомлень (модель часового розчеплення)

Шина повідомлень ліквідує часову зв'язаність завдяки проміжному збереженню (патерн *Transactional Outbox* та стійкий дисковий буфер брокера).

Для того щоб клієнт успішно ініціював транзакцію, потрібна працездатність лише двох компонентів: локальної бази даних клієнта (для фіксації стану та запису в outbox) та вхідного вузла шини повідомлень. Нехай `A_local = 0.9999` та `A_bus_in = 0.9999`.

Ймовірність успішного прийому повідомлення клієнта становить:

```
R_async_accept = A_local · A_bus_in
               = 0.9999 · 0.9999      [добуток локальних імовірностей]
               = 0.99980001           [99.98% доступності для користувача]
```

Доставка повідомлення до решти `k − 1` споживачів відбувається асинхронно з необмеженою кількістю повторних спроб (*retries*). Якщо споживач `j` перебуває в стані тимчасового збою протягом інтервалу часу `Δt`, повідомлення очікує в черзі шини.

Ймовірність втрати повідомлення дорівнює ймовірності безповоротного одночасного руйнування всіх реплік дискового журналу шини `P_loss = 1 − A_durability`. Для розподіленого журналу з трикратною реплікацією `A_durability > 0.999999999` (дев'ять дев'яток), що гарантує кінцеву доставку транзакції незалежно від простоїв окремих мікросервісів.

## 3. Масштабування мережевої пропускної здатності та коефіцієнт мультиплікації (Fan-Out)

Централізація потоків повідомлень змінює структуру мережевого трафіку датацентру. Необхідно враховувати ефект розмноження трафіку при публікації подій за моделлю «один-до-багатьох» (Fan-Out).

Нехай у системі щосекунди публікується `M` класів повідомлень. Для кожного класу `j` інтенсивність генерації становить `λ_j` повідомлень на секунду, а середній розмір серіалізованого конверта дорівнює `S_j` байтів.

Нехай на подію типу `j` підписано `K_j` незалежних сервісів-споживачів.

1. **Вхідний потік у шину (Ingress Bandwidth):**

```
BW_in = ∑[j=1..M] (λ_j · S_j)         [сумарний потік від усіх продюсерів]
```

2. **Вихідний потік із шини (Egress Bandwidth):**
   Шина зобов'язана клонувати або транслювати кожне повідомлення всім зареєстрованим підписникам `K_j`:

```
BW_out = ∑[j=1..M] (λ_j · S_j · K_j)  [сумарний потік роздачі споживачам]
```

Визначимо загальний коефіцієнт мультиплікації трафіку шини `β_fanout`:

```
β_fanout = BW_out / BW_in
         = (∑[j=1..M] λ_j · S_j · K_j) / (∑[j=1..M] λ_j · S_j)
```

Якщо середній розмір повідомлення `S_j` та інтенсивність `λ_j` приблизно однакові для всіх типів, формула спрощується до зваженого середнього числа підписників:

```
β_fanout ≈ (1 / M) · ∑[j=1..M] K_j = K_avg
```

Якщо в корпоративній системі кожна подія створення замовлення чи зміни статусу цікавить у середньому `K_avg = 6` сервісів (склад, білінг, доставка, CRM, аналітика, антифрод), то при вхідному потоці продюсерів `BW_in = 50 МБ/с` вихідний мережевий інтерфейс шини зобов'язаний витримувати:

```
BW_out = β_fanout · BW_in
       = 6 · 50 МБ/с
       = 300 МБ/с = 2.4 Гбіт/с
```

Звідси випливає важливий математичний висновок для архітектури даних: **передача «важких» корисних навантажень (великих бінарних файлів, сканів документів, масивів зображень) безпосередньо через шину спричиняє вибухове зростання мережевого трафіку `O(K_avg · Size)`**. Для оптимізації застосовують патерн Claim Check, де тіло розміром `Size` зберігається у сховищі об'єктів S3 рівно один раз, а шиною передається лише компактне посилання розміром `S_ref ≈ 500 байтів`.

## 4. Теорія масового обслуговування конвеєра шини: модель M/M/1 та поріг насичення

Централізація потоків повідомлень через шину створює концентрацію навантаження. Необхідно точно розрахувати час затримки повідомлення в конвеєрі обробки та умови виникнення нескінченних черг.

Змоделюємо ядро шини повідомлень (або окремий топік / чергу) за допомогою класичної теорії масового обслуговування (черга Кендалла `M/M/1`).

### Вхідний потік і час обслуговування

Нехай `N` сервісів-продюсерів генерують повідомлення у шину. Кожен сервіс `i` генерує пуассонівський потік повідомлень з інтенсивністю `λ_i` (повідомлень/секунду). За теоремою про суперпозицію незалежних пуассонівських процесів сумарний вхідний потік у шину `λ` також є пуассонівським:

```
λ = ∑[i=1..N] λ_i                     [сумарна інтенсивність надходження]
```

Конвеєр шини виконує послідовність операцій над кожним повідомленням: десеріалізація заголовків `t_deser`, перевірка авторизації `t_auth`, валідація схеми в Schema Registry `t_val`, дедуплікація `t_dedup`, маршрутизація `t_route` та запис у буфер `t_write`.

Сумарний середній час обслуговування одного повідомлення диспетчером становить:

```
E[t_proc] = t_deser + t_auth + t_val + t_dedup + t_route + t_write
```

Припустимо експоненційний розподіл часу обслуговування із середньою інтенсивністю `μ = 1 / E[t_proc]` (повідомлень/секунду, які диспетчер здатний обробити).

### Коефіцієнт завантаження та час перебування в системі

Коефіцієнт завантаження ядра шини `ρ` (утилізація) визначається як:

```
ρ = λ / μ                             [безрозмірна величина завантаження]
```

**Критична умова стабільності системи:** для того щоб черга не зростала до нескінченності, обов'язково має виконуватися нерівність `ρ < 1` (тобто `λ < μ`). Якщо `ρ ≥ 1`, довжина черги прямує до нескінченності `L_q → ∞`.

Виведемо середній час перебування повідомлення в шині `W` (загальна латентність: очікування в черзі + безпосередня обробка) через середню довжину черги `L` та закон Літтла `L = λ · W`:

Ймовірність наявності `k` повідомлень у системі `P_k` для процесу народження і загибелі в системі `M/M/1` дорівнює:

```
P_k = (1 − ρ) · ρ^k                   [розподіл геометричної прогресії]
```

Середня кількість повідомлень у системі `L`:

```
L = ∑[k=0..∞] k · P_k
  = ∑[k=0..∞] k · (1 − ρ) · ρ^k       [підстановка P_k]
  = (1 − ρ) · ρ · ∑[k=1..∞] k · ρ^(k−1) [винесення (1 − ρ) · ρ]
  = (1 − ρ) · ρ · d/dρ (∑[k=0..∞] ρ^k) [похідна нескінченної геометричної прогресії]
  = (1 − ρ) · ρ · d/dρ (1 / (1 − ρ))  [сума геометричної прогресії для ρ < 1]
  = (1 − ρ) · ρ · (1 / (1 − ρ)²)      [обчислення похідної (1−ρ)⁻²]
  = ρ / (1 − ρ)                       [скорочення (1 − ρ)]
```

Застосовуємо закон Літтла `W = L / λ` для знаходження середнього повного часу `W`:

```
W = L / λ
  = (ρ / (1 − ρ)) / λ                 [підстановка L = ρ / (1 − ρ)]
  = ((λ / μ) / (1 − ρ)) / λ           [підстановка ρ = λ / μ]
  = (λ / (μ · (1 − ρ))) / λ           [перенесення μ в знаменник]
  = 1 / (μ · (1 − ρ))                 [скорочення на λ ≠ 0]
  = 1 / (μ − λ)                       [розкриття дужок: канонічна формула латентності M/M/1]
```

Середній час очікування повідомлення безпосередньо в буферній черзі `W_q` (до початку обробки процесором шини):

```
W_q = W − (1 / μ)                     [віднімання чистого часу обслуговування]
    = (1 / (μ − λ)) − (1 / μ)         [підстановка W]
    = (μ − (μ − λ)) / (μ · (μ − λ))   [зведення до спільного знаменника]
    = λ / (μ · (μ − λ))               [спрощення чисельника]
    = (λ / μ) / (μ · (1 − λ / μ))     [ділення чисельника і знаменника на μ]
    = ρ / (μ · (1 − ρ))               [підстановка ρ = λ / μ]
```

### Нелінійний стрибок затримок при наближенні до насичення

Проаналізуємо відношення повної затримки `W` до мінімального часу обробки `E[t_proc] = 1 / μ`:

```
W / E[t_proc] = (1 / (μ · (1 − ρ))) / (1 / μ)
              = 1 / (1 − ρ)
```

Поведінка фактора зростання затримки `1 / (1 − ρ)` має гіперболічний характер:

```
ρ = 0.00 (нульове навантаження):  W = 1.00 · E[t_proc]
ρ = 0.50 (завантаження 50%):      W = 1 / (1 − 0.50) = 2.00 · E[t_proc]
ρ = 0.75 (завантаження 75%):      W = 1 / (1 − 0.75) = 4.00 · E[t_proc]
ρ = 0.80 (завантаження 80%):      W = 1 / (1 − 0.80) = 5.00 · E[t_proc]
ρ = 0.90 (завантаження 90%):      W = 1 / (1 − 0.90) = 10.0 · E[t_proc]
ρ = 0.95 (завантаження 95%):      W = 1 / (1 − 0.95) = 20.0 · E[t_proc]
ρ = 0.99 (завантаження 99%):      W = 1 / (1 − 0.99) = 100.0 · E[t_proc]
```

Звідси випливає фундаментальне інженерне правило: **робоча точка шини повідомлень ніколи не повинна перевищувати `ρ = 0.70...0.75`**. Перехід завантаження з 80% до 95% збільшує затримку доставки повідомлень у 4 рази (з 5 до 20 інтервалів обробки), а при короткочасному сплеску до 99% затримка злітає у 20 разів, викликаючи масові таймаути клієнтів.

## 5. Партиціонування та нерівномірність розподілу навантаження: закон Ціпфа

Для горизонтального масштабування пропускної здатності черги шини розділяють на `P` паралельних партицій (секцій), де кожне повідомлення призначається до партиції за хешем ключа сутності (наприклад, `partition = hash(user_id) % P`). Це забезпечує суворий порядок обробки подій одного користувача при паралельній роботі `P` споживачів.

Однак на практиці розподіл активності користувачів або ключів сутностей не є рівномірним, а підпорядковується степеневому закону розподілу Ціпфа (англ. *Zipf's Law*):

```
P(k; s, C) = (1 / k^s) / ∑[n=1..C] (1 / n^s)
```

де `C` — загальна кількість унікальних ключів, `k` — ранг популярності ключа (`1 ≤ k ≤ C`), а `s` — показник ступеня нерівномірності (типово `s ≈ 0.8...1.2` у реальних електронних комерціях і соцмережах).

Нехай система має `P = 8` партицій та сумарний потік `λ = 10 000 msg/s`. При ідеально рівномірному розподілі навантаження на кожну партицію становило б:

```
λ_ideal = λ / P = 10000 / 8 = 1250 msg/s
```

При степеневому законі розподілу з «гарячим» ключем (наприклад, великий оптовий клієнт або акційний товар маркетплейса генерує 30% усіх транзакцій) партиція, на яку хешується цей ключ, отримує навантаження:

```
λ_hot = (0.30 · λ) + ((1 − 0.30) · λ / P) [гарячий ключ 30% плюс частка фонового трафіку]
      = 3000 + (7000 / 8)                 [підстановка λ = 10000 та P = 8]
      = 3000 + 875                        [ділення фонового потоку на 8 партицій]
      = 3875 msg/s                        [підсумок: потік на гарячу партицію]
```

Якщо кожна партиція обслуговується воркером із продуктивністю `μ_part = 2000 msg/s`:
- Для 7 звичайних партицій утилізація становить `ρ_norm = 875 / 2000 = 0.4375` (безпечні 43.7%);
- Для 1 гарячої партиції утилізація `ρ_hot = 3875 / 2000 = 1.9375 > 1.0`!

Оскільки `ρ_hot > 1`, черга цієї партиції **монотонно зростає до нескінченності зі швидкістю `ΔL = λ_hot − μ_part = 1875 msg/s`**, блокуючи обробку замовлень усіх інших користувачів, чий `user_id` випадково потрапив у ту саму секцію.

Математичний висновок: **вибір ключа партиціонування на шині повинен максимізувати ентропію розподілу**, а за наявності аномально гарячих сутностей застосовують техніку розсіювання (*Salting*), додаючи псевдовипадковий суфікс до ключа (`user_id + "_" + random(0..3)`), щоб розмазати потік на кілька партицій.

## 6. Практичний розрахунковий приклад: проектування шини для платіжної платформи

**Умова задачі:**
Платіжна платформа об'єднує `N = 12` мікросервісів.
Сумарний потік повідомлень від усіх сервісів становить `λ = 4000` повідомлень/секунду.
Виміри профілю обробки повідомлення на одному ядрі диспетчера дали такі показники:
- Десеріалізація заголовків: `t_deser = 25 мкс`;
- Перевірка токена й сигнатури: `t_auth = 40 мкс`;
- Валідація схеми за кешем Schema Registry: `t_val = 30 мкс`;
- Розрахунок хешу дедуплікації: `t_dedup = 15 мкс`;
- Зіставлення теми в дереві підписок: `t_route = 30 мкс`;
- Запис у внутрішній кільцевий буфер виводу: `t_write = 60 мкс`.

Необхідно розрахувати:
1. Загальний час обслуговування `E[t_proc]` та максимальну пропускну здатність одного диспетчерського ядра `μ_core`.
2. Коефіцієнт завантаження `ρ` та середній час перебування повідомлення `W` при використанні однопотокового диспетчера.
3. Мінімальну кількість паралельних ядер `m` для забезпечення завантаження `ρ_m ≤ 0.60` та середньої затримки конвеєра `W ≤ 0.5 мс`.

### Розрахунок:

**Крок 1. Обчислення середнього часу обробки та пропускної здатності одного ядра:**

```
E[t_proc] = 25 + 40 + 30 + 15 + 30 + 60   [сума інтервалів обробки етапів конвеєра]
          = 200 мкс                       [результат у мікросекундах]
          = 0.000200 секунди              [переведення в одиниці СІ]

μ_core = 1 / E[t_proc]                    [формула інтенсивності обслуговування]
       = 1 / 0.000200                     [підстановка часу E[t_proc]]
       = 5000 повідомлень / секунду        [гранична пропускна здатність ядра]
```

**Крок 2. Оцінка для однопотокового ядра:**

```
ρ = λ / μ_core                            [коефіцієнт завантаження системи]
  = 4000 / 5000                           [підстановка інтенсивностей]
  = 0.80                                  [завантаження 80%]

W = 1 / (μ_core − λ)                      [канонічна формула латентності M/M/1]
  = 1 / (5000 − 4000)                     [підстановка значень μ та λ]
  = 1 / 1000                              [обчислення різниці]
  = 0.001000 секунди                      [результат у секундах]
  = 1.00 мілісекунда                      [переведення в мілісекунди]
```

При завантаженні 80% середня затримка становить 1.0 мс (у 5 разів більше за чистий час обробки 0.2 мс), а будь-який сплеск трафіку понад 5000 msg/s переповнить буфери.

**Крок 3. Багатопотоковий диспетчер (система M/M/m з пулом із `m` ядер):**

Загальна продуктивність пулу `μ_total = m · μ_core`.
Сумарний коефіцієнт завантаження на одне ядро: `ρ_core = λ / (m · μ_core)`.

З умови `ρ_core ≤ 0.60`:

```
λ / (m · μ_core) ≤ 0.60                   [критерій цільової утилізації ядра]
m ≥ λ / (0.60 · μ_core)                   [множення на m та ділення на 0.60]
m ≥ 4000 / (0.60 · 5000)                  [підстановка числових значень]
m ≥ 4000 / 3000                           [спрощення знаменника]
m ≥ 1.333                                 [округлення до найближчого більшого цілого: m = 2]
```

Перевіримо показники для `m = 2` та `m = 4`:
Для `m = 2`: `ρ_core = 4000 / (2 · 5000) = 4000 / 10000 = 0.40 (40%)`.
Для черги `M/M/2` за формулою Ерланга-C ймовірність очікування становить:

```
P_wait = (2 · ρ_core)² / (2! · (1 − ρ_core) · (1 + 2·ρ_core + (2·ρ_core)² / (2·(1 − ρ_core)))) [формула Ерланга-C для M/M/2]
       = (0.80)² / (2 · (0.60) · (1 + 0.80 + 0.64 / 1.20))  [підстановка ρ_core = 0.40]
       = 0.64 / (1.20 · (1.80 + 0.5333))                    [обчислення знаменника]
       = 0.64 / (1.20 · 2.3333)                             [зведення доданків]
       = 0.64 / 2.80                                        [множення коефіцієнтів]
       ≈ 0.2285                                             [ймовірність очікування 22.8%]

W_q = P_wait / (m · μ_core − λ)                             [формула середнього часу очікування в черзі]
    = 0.2285 / (10000 − 4000)                               [підстановка значень пулу]
    = 0.2285 / 6000                                         [ділення на залишковий ресурс]
    ≈ 0.0000381 секунди                                     [результат у секундах]
    = 38.1 мікросекунд                                      [переведення в мікросекунди]

W = W_q + E[t_proc]                                         [сума часу очікування та обробки]
  = 38.1 мкс + 200 мкс                                      [підстановка виміряних значень]
  = 238.1 мікросекунд                                       [загальний час у мікросекундах]
  = 0.238 мілісекунди                                       [фінальна середня затримка в системі]
```

**Висновок розрахунку:**
Виділення пулу з `m = 2` обчислювальних ядер для диспетчера шини знижує робочу утилізацію ядер до безпечних `40%`, а середню наскрізну латентність проходження шини — з `1.00 мс` до `0.238 мс` (скорочення затримки більш ніж у 4 рази), гарантуючи стабільну роботу системи під час пікових сплесків трафіку.
