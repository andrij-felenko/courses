# 🧮 Математична модель витрат на індексування тегів, лагу реплікації та радіусу ураження

Вибір стратегії інвалідації визначається кількісним співвідношенням між витратами оперативної пам'яті на підтримку індексів, затримкою виконання запитів та ймовірністю отруєння кешу за наявності асинхронної реплікації.

## 1. Модель пам'яті інвертованого індексу тегів

Нехай у системі зберігається `|K|` кешованих ключів та `|T|` унікальних тегів (сурогатних ключів).
Кожен ключ асоційовано в середньому з `t̄` тегами, а кожен тег посилається в середньому на `k̄` ключів. За законом збереження зв'язків у двочастковому графі:

```
|K| · t̄ = |T| · k̄ = E      [загальна кількість ребер графа зв'язків]
```

Для забезпечення безпечного видалення ключів за `O(1)` та автоматичного розриву зворотних посилань система підтримує два індекси:
1. Прямий індекс `Key -> Set<Tag>` для утилізації посилань під час видалення або витіснення ключа.
2. Інвертований індекс `Tag -> Set<Key>` для виконання операції `PURGE TAG`.

Позначимо:
* `s_ptr` — розмір вказівника в пам'яті (8 байтів для 64-бітної архітектури);
* `s_node` — оверхед службового заголовка вузла динамічної структури (хеш-таблиці або дерева, зазвичай 24–32 байти);
* `s_key` — середня довжина рядка ключа;
* `s_tag` — середня довжина рядка тегу.

Загальний обсяг пам'яті `M_index`, необхідний суто для збереження зв'язків індексації:

```
M_index 
= M_forward + M_inverted                                  [сума прямого та інвертованого індексів]
= (|K| · s_node + E · (s_ptr + s_tag)) + (|T| · s_node + E · (s_ptr + s_key))  [розгортання вузлів і зв'язків]
= (|K| + |T|) · s_node + E · (2·s_ptr + s_tag + s_key)    [групування спільних доданків]
```

**Числовий приклад розрахунку:**
Нехай `|K| = 1 000 000` сторінок, `|T| = 50 000` сутностей, `t̄ = 4` теги на сторінку.
Звідси `E = 10⁶ · 4 = 4 000 000` зв'язків, `k̄ = 4·10⁶ / 50 000 = 80` сторінок на тег.
При `s_node = 32`, `s_ptr = 8`, `s_tag = 16`, `s_key = 32` байти:

```
M_index
= (10⁶ + 50 000) · 32 + 4·10⁶ · (2·8 + 16 + 32)           [підстановка числових параметрів]
= 1 050 000 · 32 + 4 000 000 · 64                         [обчислення виразів у дужках]
= 33 600 000 + 256 000 000                                [множення компонентів]
= 289 600 000 байтів ≈ 276.18 МБ                          [переведення в мегабайти: 289.6·10⁶ / 1024²]
```

Оверхед пам'яті на підтримку двосторонніх тегів становить близько 276 МБ на 1 мільйон ключів. Це доводить, що інвертовані індекси залишаються компактними в пам'яті RAM сучасних серверів порівняно з розміром корисних даних.

## 2. Нижня межа затримки для відкладеного подвійного видалення

Розглянемо архітектуру з одним майстром бази даних `DB_m`, множиною асинхронних реплік для читання `DB_r` та розподіленим кешем `C`.

Нехай:
* `t_0` — момент фіксації транзакції запису на майстрі `DB_m`;
* `L_repl` — максимальний лаг реплікації між майстром та найповільнішою реплікою;
* `RTT_rc` — час мережевого кругового обігу між сервером застосунку та кешем;
* `RTT_rd` — час мережевого кругового обігу між сервером застосунку та реплікою бази;
* `σ_jitter` — дисперсія затримок обробки планувальника операційної системи.

Хай паралельний читач стикається з промахом кешу після першого видалення ключа в момент `t_read`. Якщо запит читача потрапляє на репліку, яка ще не отримала оновлення (тобто `t_read < t_0 + L_repl`), читач отримує застаріле значення `v_old`.

Час, коли запізнілий читач здійснить зворотний запис застарілого значення `v_old` у кеш:

```
t_poison ≤ t_0 + L_repl + RTT_rd + 1/2 · RTT_rc + σ_jitter
```

Щоб друге видалення гарантовано стерло застарілий запис, момент другого видалення `t_del2 = t_0 + T_delay` повинен строго переважати найпізніший можливий момент отруєння `t_poison`:

```
t_0 + T_delay > t_0 + L_repl + RTT_rd + 1/2 · RTT_rc + σ_jitter
```

Звідси отримуємо фундаментальну нерівність мінімальної затримки відкладеного видалення:

```
T_delay ≥ L_repl + RTT_rd + 1/2 · RTT_rc + σ_jitter
```

Якщо в датацентрі `RTT_rd = 4` мс, `RTT_rc = 1` мс, максимальний 99.9-й процентиль лагу реплікації `L_repl = 250` мс, а `σ_jitter = 20` мс:

```
T_delay 
≥ 250 + 4 + 0.5 + 20                                      [підстановка виміряних затримок]
= 274.5 мс                                                [підсумок мінімального порогу]
```

Отже, безпечний тайм-аут другого видалення для даної конфігурації повинен становити не менше 300–500 мілісекунд. Встановлення меншого значення призводить до того, що друге видалення виконається **раніше**, ніж запізнілий читач отруїть кеш, і застарілий стан зафіксується назавжди.

## 3. Радіус ураження та ймовірність лавини запитів (Stampede)

Під час інвалідації за тегом `tag_i` одночасно анулюється `k̄` ключів. Якщо ці ключі мають спільну інтенсивність читання `λ_total = ∑ λ_j`, виникає одночасний сплеск запитів до первинної бази даних.

Нехай:
* `D_query` — середній час виконання важкого SQL-запиту генерації сторінки (в секундах);
* `C_pool` — місткість пулу з'єднань бази даних.

Потік запитів на відновлення за відсутності координації (Single-Flight) моделюється пуассонівським розподілом. Кількість одночасних звернень до БД протягом часу генерації `D_query`:

```
N_concurrent ~ Poisson(μ)
де μ = λ_total · D_query
```

Ймовірність вичерпання пулу з'єднань і відмови бази даних `P(collapse)`:

```
P(collapse) 
= P(N_concurrent > C_pool)                                [умова перевищення місткості пулу]
= 1 - ∑_{n=0}^{C_pool} (μⁿ · e^{-μ}) / n!                 [доповнення кумулятивної ймовірності Пуассона]
```

**Розрахунок критичного навантаження:**
Нехай `λ_total = 500` запитів/с, `D_query = 0.08` с (80 мс), `C_pool = 30` з'єднань.

```
μ = 500 · 0.08 = 40
```

Оскільки середнє очікуване число запитів `μ = 40` строго перевищує ліміт пулу `C_pool = 30`, за формулою Пуассона:

```
P(N_concurrent > 30) ≈ 0.941   [ймовірність колапсу БД становить 94.1%]
```

Цей результат математично доводить, що групова інвалідація за тегами високочастотних сутностей без застосування блокувань Single-Flight або фонового розігріву гарантовано призводить до відмови первинного сховища.

## 4. Математична оптимізація ймовірнісного випереджального оновлення (XFetch)

Для усунення лавинного навантаження під час інвалідації або закінчення `TTL` застосовують алгоритм ймовірнісного дострокового оновлення (Probabilistic Early Expiration / XFetch).

Клієнт, що зчитує дані з кешу в момент `t_now`, приймає рішення про асинхронне оновлення запису в базі даних, якщо виконується нерівність:

```
t_now - β · δ · ln(U) > t_expiry
```

де:
* `t_expiry` — абсолютний час закінчення дії ключа в кеші;
* `δ` — час, необхідний для обчислення / завантаження значення з первинної бази даних (в секундах);
* `β` — конфігураційний коефіцієнт агресивності оновлення (`β > 0`, за замовчуванням `β = 1`);
* `U` — випадкова величина з рівномірним розподілом `U ~ Uniform(0, 1)`.

Оскільки `U ∈ (0, 1)`, величина `ln(U)` завжди від'ємна (`ln(U) < 0`), а вираз `-β · δ · ln(U)` набуває додатних значень від `0` до `+∞`.

Ймовірність того, що випадковий запит на читання за час `Δt = t_expiry - t_now` до планового закінчення терміну дії ініціює дострокове фонове оновлення `P(refresh | Δt)`:

```
P(refresh | Δt)
= P(t_now - β · δ · ln(U) > t_expiry)                      [початкова умова алгоритму]
= P(-β · δ · ln(U) > t_expiry - t_now)                     [перенесення t_now вправо]
= P(ln(U) < -Δt / (β · δ))                                 [ділення на додатний множник -β·δ з інверсією знаку]
= P(U < e^{-Δt / (β · δ)})                                 [експоненціювання обох частин]
= e^{-Δt / (β · δ)}                                        [кумулятивна функція для U ~ Uniform(0,1)]
```

Аналіз отриманої ймовірнісної функції демонструє:
1. Коли до закінчення терміну дії ще далеко (`Δt ≫ β·δ`), ймовірність `e^{-∞} → 0` — ресурси бази даних не витрачаються.
2. У міру наближення до моменту застарівання (`Δt → 0`), ймовірність експоненціально зростає: `e^0 = 1`.
3. За секунду до інвалідації перший-ліпший випадковий клієнт із високою ймовірністю запустить фоновий перерахунок, оновивши значення в кеші до того, як ключ буде витіснено. Це повністю нівелює ризик виникнення промахів читання.

## 5. Оптимальний баланс між частотою інвалідації та ціною застарілості

При виборі між пасивною інвалідацією за таймером `TTL` та активною подієвою інвалідацією сукупна вартість системи `C_total(T)` моделюється цільовою функцією:

```
C_total(T) = c_comp · (λ_read / T) + c_stale · (1/2 · λ_write · λ_read · T)
```

де `c_comp` — вартість одного запиту відновлення кешу, `c_stale` — штраф за одиницю часу віддачі застарілих даних, `T` — інтервал життя кешу.

Диференціюючи за `T` і прирівнюючи похідну до нуля:

```
d C_total / dT 
= -c_comp · λ_read / T² + 1/2 · c_stale · λ_write · λ_read   [взяття першої похідної]
= 0                                                        [умова точки екстремуму]
```

Звідси отримуємо теоретичний оптимум часу життя кешу `T_opt`:

```
T_opt = √( (2 · c_comp) / (c_stale · λ_write) )
```

Формула доводить: при зростанні інтенсивності змін `λ_write` або штрафу за застарілість `c_stale` оптимальний інтервал `T_opt` скорочується обернено пропорційно до кореня квадратного, що робить активну подієву інвалідацію (CDC / Surrogate Keys) безальтернативно вигіднішою за звичайний `TTL`.
