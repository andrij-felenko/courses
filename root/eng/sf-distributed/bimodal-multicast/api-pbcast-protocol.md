# 📋 Специфікація бінарного протоколу та конфігураційний контракт pbcast

Ця специфікація визначає бінарний формат мережевих дейтаграм, правила упакування Gossip-дайджестів, конфігураційні інваріанти та протокольний контракт для реалізації Bimodal Multicast (pbcast) поверх транспортного протоколу UDP/IP.

Документ призначений для системних розробників мережевих рушіїв, інженерів розподілених систем, авторів клієнтських бібліотек та операторів систем моніторингу.

---

## 1. Загальний формат мережевих дейтаграм

Усі повідомлення pbcast передаються у стандартних UDP-дейтаграмах. Для забезпечення повної кросплатформної сумісності між різними апаратними архітектурами (x86_64, ARM64, RISC-V, POWER) усі цілочисельні поля передаються у мережевому порядку байтів (Big-Endian / Network Byte Order).

Кожен пакет pbcast обов'язково починається з фіксованого базового заголовка розміром 16 байтів:

| Зміщення (байт) | Розмір (байт) | Тип | Назва поля | Опис |
|---|---|---|---|---|
| `0x00` | 4 | `uint32_t` | `Magic` | Фіксована сигнатура протоколу: `0x50424354` (ASCII: `"PBCT"`) |
| `0x04` | 1 | `uint8_t` | `Version` | Версія формату протоколу (поточна версія: `0x01`) |
| `0x05` | 1 | `uint8_t` | `Type` | Тип повідомлення (`0x01`–`0x04`) |
| `0x06` | 2 | `uint16_t` | `Flags` | Бітові прапорці керування (див. структуру прапорців нижче) |
| `0x08` | 8 | `uint64_t` | `SenderId` | Унікальний 64-бітний числовий ідентифікатор вузла-відправника |

### Структура бітових прапорців (`Flags`)
Поле `Flags` (2 байти) містить керуючі біти оптимізації передачі:
- `Bit 0 (0x0001)`: `FLAG_COMPRESSED` — корисне навантаження стиснуто алгоритмом LZ4 або ZSTD.
- `Bit 1 (0x0002)`: `FLAG_HIGH_PRIORITY` — термінове системне повідомлення (наприклад, зміна членства або аварійний сигнал).
- `Bit 2 (0x0004)`: `FLAG_WAN_ROUTED` — пакет пройшов через міжрегіональний міст.
- `Bits 3..15`: Зарезервовано для майбутніх розширень (повинні бути встановлені в `0`).

## 2. Специфікація типів повідомлень

Протокол pbcast визначає чотири типи керуючих та інформаційних повідомлень:

```
0x01: PBCAST_DATA       — Оптимістична трансляція даних у групу (Фаза 1)
0x02: PBCAST_DIGEST     — Gossip-дайджест стану для анти-ентропії (Фаза 2)
0x03: PBCAST_SOLICIT    — Запит на ретрансляцію відсутніх пакетів (Pull-NAK)
0x04: PBCAST_REPAIR     — Одноадресна доставка відновленого пакета
```

### 2.1. Пакет даних: `PBCAST_DATA` (Type = 0x01)
Транслюється первинним джерелом у групу мовлення через апаратний IP Multicast або Unicast-дерево.

| Зміщення | Розмір | Тип | Назва поля | Опис |
|---|---|---|---|---|
| `0x10` | 8 | `uint64_t` | `SeqNum` | Монотонно зростаючий номер послідовності джерела |
| `0x18` | 8 | `uint64_t` | `TimestampNs` | Часова мітка генерації (UNIX-час у наносекундах) |
| `0x20` | 4 | `uint32_t` | `PayloadLen` | Довжина корисного навантаження у байтах |
| `0x24` | 4 | `uint32_t` | `ChecksumCRC32` | Контрольна сума CRC-32 (поліном IEEE 802.3 `0xEDB88320`) |
| `0x28` | N | `uint8_t[]` | `Payload` | Байти корисних даних прикладного застосунку |

### 2.2. Пакет дайджесту стану: `PBCAST_DIGEST` (Type = 0x02)
Надсилається періодично обраним пірам під час фонового циклу анти-ентропії. Містить стислий звіт про стан буферів усіх відомих джерел.

| Зміщення | Розмір | Тип | Назва поля | Опис |
|---|---|---|---|---|
| `0x10` | 4 | `uint32_t` | `RoundNumber` | Монотонний номер епідемічного раунду відправника |
| `0x14` | 2 | `uint16_t` | `NumEntries` | Кількість джерел у цьому дайджесті |
| `0x16` | 2 | `uint16_t` | `Reserved` | Вирівнювання (заповнюється нулями) |
| `0x18` | 24 × K | `Entry[]` | `SourceEntries` | Масив записів про окремі джерела |

Кожен елемент масиву `SourceEntry` має фіксований розмір 24 байти:
1. `SourceSenderId` (`uint64_t`, 8 байтів): числовий ідентифікатор первинного джерела.
2. `LowWatermark` (`uint64_t`, 8 байтів): номер пакета, до якого всі повідомлення отримано підряд без пропусків.
3. `ReceivedMask` (`uint64_t`, 8 байтів): бітова маска отриманих пакетів у вікні `[LowWatermark + 1, LowWatermark + 64]`.

### 2.3. Запит на ретрансляцію: `PBCAST_SOLICIT` (Type = 0x03)
Надсилається безпосередньо тому піру, який у своєму дайджесті повідомив про наявність пакетів, відсутніх у локальному буфері.

| Зміщення | Розмір | Тип | Назва поля | Опис |
|---|---|---|---|---|
| `0x10` | 8 | `uint64_t` | `SourceSenderId` | Ідентифікатор джерела, чиї пакети запитуються |
| `0x18` | 2 | `uint16_t` | `RequestedCount` | Кількість запитуваних номерів пакетів |
| `0x1A` | 2 | `uint16_t` | `Reserved` | Вирівнювання |
| `0x1C` | 8 × M | `uint64_t[]` | `SeqNumbers` | Масив конкретних номерів `SeqNum` для ремонту |

### 2.4. Пакет відновлення: `PBCAST_REPAIR` (Type = 0x04)
Одноадресна дейтаграма (Unicast UDP), яка надсилається у відповідь на `PBCAST_SOLICIT`. Структура тіла пакета повністю ідентична `PBCAST_DATA`, проте поле `Type` у базовому заголовку дорівнює `0x04`. Це дозволяє приймачу відрізнити оптимістичний трафік фази 1 від ремонтного трафіку фази 2 для збору метрик.

## 3. Конфігураційний контракт параметрів

Таблиця обов'язкових та рекомендованих параметрів для налаштування вузла pbcast:

| Параметр | Тип | За замовчуванням | Допустимий діапазон | Одиниця | Опис |
|---|---|---|---|---|---|
| `round_interval_ms` | `uint32_t` | `50` | `10 .. 500` | мс | Базовий період запуску циклу анти-ентропії |
| `fanout_k` | `uint32_t` | `3` | `2 .. 8` | піри | Кількість випадкових партнерів на один раунд пліток |
| `jitter_pct` | `uint32_t` | `20` | `0 .. 50` | % | Відсоток випадкового відхилення інтервалу таймера |
| `buffer_retention_ms`| `uint32_t` | `600` | `200 .. 5000` | мс | Час утримання пакета в буфері перед видаленням |
| `max_solicit_per_round`| `uint32_t`| `8` | `1 .. 64` | шт. | Ліміт запитів на ретрансляцію за один раунд |
| `max_repair_rate_pps`| `uint32_t` | `1000` | `100 .. 50000`| пак/с | Обмеження швидкості надсилання ремонтних пакетів |

## 4. Сценарії обробки крайових випадків у мережевому протоколі

Для забезпечення надійної експлуатації у виробничих середовищах протокольний рушій pbcast реалізує спеціальні алгоритмічні тактики для крайових випадків:

### 4.1. Придушення повторних запитів (Solicitation Suppression)
Якщо вузол виявив дефіцит пакета `#105` і надіслав запит `PBCAST_SOLICIT` вузлу `A`, він не повинен дублювати аналогічний запит вузлу `B` у тому самому раунді. Вузол запускає локальний таймер придушення тривалістю `T_suppress = 1.5 · RTT_estimated`. Повторний запит іншому піру дозволяється лише в разі, якщо протягом цього часу відповідь `PBCAST_REPAIR` не надійшла.

### 4.2. Обмеження пропускної здатності ретрансляцій (Token Bucket Rate Limiting)
Якщо вузол отримує велику кількість запитів на відновлення від різних сусідів (наприклад, після локального збою мережевого комутатора), вихідний потік ремонтних дейтаграм обмежується алгоритмом маркерного кошика (Token Bucket) відповідно до параметра `max_repair_rate_pps`. Це запобігає виснаженню мережевого інтерфейсу та захищає основний трафік фази 1.

### 4.3. Відновлення після тривалої ізоляції (State Snapshot Transfer)
Якщо вузол був відключений від мережі на час, що перевищує вікно утримання `buffer_retention_ms`, його відставання перевищить місткість кільцевого буфера (`remote_watermark - local_watermark > PBCAST_BUFFER_CAPACITY`). У такому разі відновлення окремих дейтаграм через pbcast стає неможливим. Вузол переходить у режим завантаження повного знімка стану (State Snapshot) через прикладний протокол консистентності або TCP-потік.

## 5. Коди помилок та обробка виключних ситуацій

При валідації вхідних дейтаграм мережевий стек pbcast використовує стандартизовані числові коди результатів:

| Код | Символічна назва | Значення | Дія вузла |
|---|---|---|---|
| `0x00` | `PBCAST_OK` | Пакет успішно валідовано та прийнято | Передати в буфер або обробити |
| `0x01` | `ERR_BAD_MAGIC` | Невірна сигнатура Magic (не `"PBCT"`) | Мовчки відкинути пакет (захист від шуму) |
| `0x02` | `ERR_BAD_VERSION` | Непідтримувана версія протоколу | Зафіксувати в журналі та відкинути |
| `0x03` | `ERR_CRC_MISMATCH` | Невідповідність контрольної суми CRC32 | Збільшити лічильник пошкоджень і скинути |
| `0x04` | `ERR_PAYLOAD_OVERFLOW`| Розмір Payload перевищує ліміт MTU | Відкинути пакет як потенційну атаку |
| `0x05` | `ERR_BUFFER_OVERFLOW` | Номер SeqNum за межами вікна буфера | Зафіксувати пропуск і запустити ремонт |
| `0x06` | `ERR_RATE_LIMITED` | Перевищено ліміт запитів ретрансляцій | Тимчасово відкласти надсилання Solicit |

## 6. Метрики та спостережуваність (Telemetry Contract)

Для моніторингу працездатності та діагностики мережевих аномалій кожен вузол pbcast експортує стандартизований набір метрик у форматі Prometheus/OpenTelemetry:

1. **`pbcast_packets_received_total{type="data|repair"}` (Counter):** загальна кількість отриманих дейтаграм із розділенням за фазою доставки (фаза 1 проти фази 2).
2. **`pbcast_loss_detected_total` (Counter):** кількість зафіксованих пропусків у номерах послідовностей до запуску анти-ентропії.
3. **`pbcast_loss_repaired_total` (Counter):** кількість успішно затягнутих дейтаграм через епідемічний механізм відновлення.
4. **`pbcast_gossip_rounds_total` (Counter):** кількість виконаних раундів анти-ентропії.
5. **`pbcast_buffer_utilization_ratio` (Gauge):** відсоток зайнятих слотів у кільцевому буфері ретрансляції (значення `0.0` .. `1.0`).
6. **`pbcast_digest_exchange_duration_seconds` (Histogram):** розподіл затримок обміну дайджестами та отримання ремонтних дейтаграм від сусідів.

## 7. Інваріанти протоколу та гарантії безпеки

1. **Інваріант монотонності водяної лінії:**
   Показник `LowWatermark` для конкретного джерела може лише монотонно зростати в часі:
   ```
   LowWatermark(t + 1) >= LowWatermark(t)
   ```
2. **Інваріант непорушності джерела:**
   Жоден вузол за жодних обставин не надсилає пакет `PBCAST_SOLICIT` на адресу первинного джерела `SourceSenderId`, якщо це джерело не було обрано випадковим генератором пірів серед загальної популяції.
3. **Обмеження поширення (Unicast Repair):**
   Пакет `PBCAST_REPAIR` завжди надсилається виключно одноадресним (Unicast UDP) повідомленням запитуючому вузлу і ніколи не ретранслюється в групу мовлення, що гарантує локалізацію навантаження.
4. **Захист від фрагментації IP:**
   Загальний розмір будь-якої дейтаграми pbcast (разом із базовим заголовком та IP/UDP заголовками) не повинен перевищувати стандартний розмір MTU мережі (1472 байти для стандартного Ethernet або 8972 байти для Jumbo Frames) для запобігання фрагментації пакетів на рівні IP.
