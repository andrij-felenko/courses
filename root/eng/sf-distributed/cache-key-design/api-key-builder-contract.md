# 📋 Специфікація контракту побудовника ключів кешування та політики просторів імен

Цей нормативний документ визначає архітектурний та інтерфейсний контракт, формальну граматику, правила валідації, гарантії безпеки пам'яті та протокол обробки помилок для клієнтських бібліотек побудови ключів розподіленого кешування, забезпечуючи сувору ізоляцію орендарів, сумісність із хеш-слотами кластерів Redis, детермінізм серіалізації та захист від збоїв десеріалізації при еволюції схем даних.

## 1. Архітектурне призначення та принципи проектування

У розподілених сервісно-орієнтованих системах ключ кешу є єдиним ідентифікатором, за яким мережеві клієнти, проксі-шари та вузли зберігання знаходять закешовані об'єкти. Відсутність єдиного стандарту побудови ключів призводить до чотирьох системних дефектів:

1. **Міжсервісні колізії (Key Collisions):** коли два незалежні мікросервіси (наприклад, `billing` та `auth`) використовують однакові некваліфіковані ідентифікатори `user:1001`, перезаписуючи дані один одного.
2. **Витік даних між орендарями (Tenant Data Leak):** у багатокористувацьких (SaaS) системах відсутність обов'язкового префікса організації призводить до того, що користувач компанії А отримує доступ до фінансового звіту компанії Б.
3. **Збої десеріалізації при розгортанні (Schema Drift Crash):** оновлення внутрішньої структури DTO без зміни префікса версії призводить до аварійного завершення старих екземплярів сервісу при спробі прочитати оновлений бінарний або JSON-формат.
4. **Нерівномірний розподіл за хеш-слотами:** некоректне розміщення фігурних дужок хеш-тегів `{...}` збирає мільйони різнорідних сутностей в один фізичний слот Redis Cluster, руйнуючи горизонтальне масштабування.

Бібліотека побудови ключів покликана інкапсулювати правила валідації, форматування та санітизації, надаючи розробникам нуль-видільний (англ. *zero-allocation*) інтерфейс швидкої генерації канонічних рядків.

## 2. Формальна граматика ключа кешування (EBNF)

Кожен згенерований ключ кешу повинен строго відповідати такій розширеній формі Бекуса — Наура (EBNF):

```ebnf
CacheKey         ::= Namespace ":" Tenant ":" Entity ":" EntityId [ HashTag ] ":" Version [ Digest ] [ Salt ]
Namespace        ::= Identifier
Tenant           ::= Identifier
Entity           ::= Identifier
EntityId         ::= [a-zA-Z0-9_\-]+
HashTag          ::= ":{" TagContent "}"
TagContent       ::= [a-zA-Z0-9_\-]+
Version          ::= "v" [1-9][0-9]*
Digest           ::= ":" [0-9a-f]{16}
Salt             ::= "#" [0-9]+

Identifier       ::= [a-z][a-z0-9_]{1,31}
```

### Семантика обов'язкових та опціональних сегментів

1. **`Namespace` (Простір імен сервісу):** буквений рядок нижнього регістру (від 2 до 32 символів), що однозначно ідентифікує сервіс-власник даних (наприклад, `orders`, `catalog`, `identity`). Заборонено створення ключів без зазначення простору імен.
2. **`Tenant` (Ідентифікатор орендаря):** унікальний буквено-числовий код клієнта або системного контексту (`client_ua`, `global`, `system`). Для публічних загальносистемних даних використовується зарезервоване значення `global`.
3. **`Entity` (Тип сутності):** назва доменної моделі в однині (`product`, `invoice`, `account`).
4. **`EntityId` (Ідентифікатор екземпляра):** первинний ключ сутності в базі даних (ціле число або UUID).
5. **`HashTag` (Хеш-тег слота):** опціональний сегмент у фігурних дужках `{...}`, призначений для фіксації зв'язаних сутностей в одному хеш-слоті Redis Cluster (наприклад, для забезпечення атомарності транзакцій `MULTI/EXEC`).
6. **`Version` (Версія схеми):** номер релізу схеми серіалізації (`v1`, `v2`). При будь-якій несумісній зміні полів DTO номер версії обов'язково інкрементується.
7. **`Digest` (Дайджест параметрів):** 16-символьний шістнадцятковий хеш (64 біти), отриманий шляхом згортання нормалізованого рядка фільтрів вибірки через MurmurHash3 або xxHash64.
8. **`Salt` (Індекс розщеплення):** числовий суфікс `#0..#(K-1)`, який динамічно додається для розподілу навантаження на гарячі ключі між різними вузлами кластера.

### Реєстр прикладів валідації ключів

| Згенерований рядок ключа | Статус | Причина валідності або порушення |
| :--- | :--- | :--- |
| `billing:ua_corp:invoice:849201:v2` | Валідний | Канонічний ключ базової сутності з версією схеми. |
| `orders:eu_retail:order:102:{user_102}:v1:a4f91c0b8e23d154` | Валідний | Ключ із закріпленням слота `{user_102}` та 64-бітним хешем параметрів. |
| `catalog:global:product:9901:v2#3` | Валідний | Розщеплений гарячий ключ із числовим індексом солі `#3`. |
| `orders:user:123` | Невалідний | Відсутній префікс орендаря та обов'язковий індикатор версії. |
| `app:tenant:item:42:{tag1}:{tag2}:v1` | Невалідний | Виявлено множинні блоки фігурних дужок (заборонено стандартом Redis). |
| `auth:tenant:user:1:v1:secret_token_123` | Невалідний | Порушення безпеки: передача конфіденційних токенів у відкритому ключі. |
| `catalog:tenant:product:9901:v0` | Невалідний | Номер версії схеми повинен бути більшим або рівним 1 (`v1`, `v2`). |

## 4. Правила екранування, санітизації та інваріанти валідації

Для запобігання пошкодженню структури ключа та усунення векторів атак типу Cache Injection бібліотека реалізує наступні строгі інваріанти:

1. **Екранування розділювача просторів імен (`:`):** Символ двокрапки зарезервовано як структурний розділювач сегментів. Якщо символ `:` міститься всередині користувацьких даних (`entity_id` або `tenant_id`), він повинен бути заекранований зворотним слешем (`\:`) або замінений на нижнє підкреслення (`_`).
2. **Канонізація параметрів запиту:** Перед обчисленням хеш-дайджесту вхідний рядок фільтрації нормалізується:
   - Пари `ключ=значення` сортуються за зростанням назв ключів (`a=1&b=2&c=3`).
   - Усі пробільні символи та URL-кодування приводяться до єдиного формату (`%20` замість `+`).
   - Числові значення форматуються без незначущих нулів (`42` замість `42.0`).
3. **Обмеження довжини та захист від переповнення:** Довжина будь-якого сегмента ключа не може перевищувати 64 байти, а сумарна довжина згенерованого ключа обмежена 256 байтами. Якщо рядок фільтрів перевищує ліміт, використання 64-бітного дайджесту є обов'язковим.
4. **Валідація хеш-тегів Redis Cluster:**
   - Ключ може містити щонайбільше одну пару дужок `{` та `}`.
   - Заборонено порожні теги виду `{}` або вкладені структури `{{tag}}`.
   - Вміст тега повинен складатися виключно з латинських літер, цифр та дефісів.

## 5. Матриця помилок та правила їх обробки

| Код помилки | Умова спрацьовування | Дія системи |
| :--- | :--- | :--- |
| `CACHE_KEY_ERR_NULL_PARAM` | Дескриптор або вказівник на вихідний буфер дорівнює `NULL`. | Негайне повернення коду помилки без запису в пам'ять. |
| `CACHE_KEY_ERR_INVALID_CHARS` | Виявлено керівні символи ASCII (`0x00..0x1F`), пробіли або символи перенесення рядків (`\r`, `\n`). | Відхилення запиту; логування попередження безпеки. |
| `CACHE_KEY_ERR_OVERFLOW` | Розмір сформованого рядка перевищує наданий буфер `buffer_size` або системний ліміт 256 байтів. | Переривання генерації; повернення необхідного розміру пам'ять. |
| `CACHE_KEY_ERR_EMPTY_FIELD` | Пропущено одне з обов'язкових полів (`namespace`, `tenant`, `entity`, `id`). | Відхилення операції (анонімні сутності заборонені). |
| `CACHE_KEY_ERR_INVALID_VERSION` | Значення `schema_version` дорівнює 0 або перевищує `1 000 000`. | Відхилення операції. |
| `CACHE_KEY_ERR_INVALID_TAG` | Непарні фігурні дужки, множинні блоки тегів або невалідні символи в тегу. | Відхилення операції з фіксацією помилки маршрутизації. |

## 6. Життєвий цикл схем даних та міграція версій ключів

Еволюція бізнес-моделей у розподілених системах вимагає контрольованого переходу між версіями серіалізації (`v1` → `v2`) без простоїв сервісу (Zero-Downtime Migration). Контракт визначає чотири фази життєвого циклу:

1. **Фаза одноосібної версії (Single Version):** система працює виключно з префіксом `v1`. Читання та запис відбуваються в просторі `orders:tenant:invoice:101:v1`.
2. **Фаза подвійного запису (Dual Write):** при розгортанні нової моделі `v2` сервіс-продюсер оновлює базу даних та синхронно записує обидва ключі — `...:v1` та `...:v2`. Це гарантує, що старі екземпляри мікросервісу продовжують читати валідні дані `v1`, а оновлені інстанси вже використовують оптимізований формат `v2`.
3. **Фаза пріоритетного читання (Primary Read v2 with Fallback):** клієнтські застосунки спочатку намагаються отримати ключ `...:v2`. У разі промаху (якщо запис було створено до старту подвійного запису) клієнт виконує резервне читання `...:v1`, десеріалізує стару модель, перетворює її на структуру `v2` та асинхронно записує оновлений ключ.
4. **Фаза виведення з експлуатації (Deprecation & Prune):** після повного перемикання трафіку на нову версію підтримка читання `v1` видаляється з коду. Старі ключі `v1` самостійно видаляються з пам'яті Redis за механізмом вичерпання TTL без необхідності виконання блокуючих операцій сканування.

## 7. Багатопотокова безпека та нуль-алокаційні гарантії

Функції побудови ключів виконуються в критичній секції обробки кожного мережевого запиту (на частотах понад 500 000 викликів на секунду на один сервер застосунку). Реалізація інтерфейсу повинна забезпечувати суворі системні гарантії:

- **Повна реентерабельність (Reentrancy):** функції `cache_key_build` у C та методи класу `IKeyBuilder` у C++ не повинні використовувати спільний глобальний стан, статичні буфери чи нелокальні змінні. Виклик функції є потокобезпечним без необхідності захоплення м'ютексів.
- **Відсутність алокацій у динамічній купі (Zero-Heap Allocation):** функція для мови C записує результат безпосередньо у наданий користувачем масив на стеку. У C++ застосування `std::string_view` у поєднанні з попереднім резервуванням пам'яті (`key.reserve(128)`) унеможливлює фрагментацію системного алокатора `malloc`/`new`.
- **Константна часова складність:** час генерації ключа становить `O(L + P)`, де `L` — сумарна довжина ідентифікаторів, а `P` — довжина рядка фільтрів, що забезпечує виконання операції менш ніж за 150 наносекунд на сучасних процесорах x86-64 та ARM64.
