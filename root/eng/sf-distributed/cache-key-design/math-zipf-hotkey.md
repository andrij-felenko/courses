# 🧮 Математичний аналіз гарячих ключів: степеневі розподіли Ціпфа, розщеплення навантаження та ймовірності колізій хешів

Математичне моделювання поведінки розподіленого кешу дозволяє кількісно розрахувати нерівномірність навантаження за законом Ціпфа, визначити необхідний коефіцієнт розщеплення гарячого ключа для повернення системи в безпечний режим та строго оцінити ймовірність колізій при скороченні довжини ключів через хеш-функції.

## 1. Модель нерівномірності трафіку за законом Ціпфа

У реальних розподілених системах популярність об'єктів (товарів в інтернет-магазині, новин, профілів користувачів) підпорядковується не рівномірному розподілу, а степеневому закону Ціпфа (англ. *Zipf's law*).

Нехай у просторі існує `N` унікальних ключів, упорядкованих за спаданням частоти звернень: `k = 1, 2, ..., N`, де `k = 1` відповідає найпопулярнішому ключу системи.

Ймовірність `P(k)` того, що випадковий вхідний запит буде адресований `k`-му за популярністю ключу, визначається формулою:

```
P(k; s, N) = (1 / kˢ) / H(N, s)
```

де `s ≥ 0` — параметр експоненційного схилу (показник концентрації популярності), а `H(N, s)` — узагальнене гармонійне число порядку `s`:

```
H(N, s) = ∑_{j=1}^{N} (1 / jˢ)
```

### Граничні випадки та значення параметра схилу

1. При `s = 0` розподіл перетворюється на строго рівномірний: `P(k) = 1 / N`. Кожен ключ отримує однакову частку запитів.
2. При `s = 1.0` (класичний розподіл Ціпфа) гармонійне число апроксимується натуральним логарифмом: `H(N, 1) ≈ ln(N) + γ`, де `γ ≈ 0.5772` — стала Ейлера — Маскероні.
3. При `s > 1.0` (супер-ціпфівський розподіл, характерний для вірусних трендів та розпродажів) ряд збігається до дзета-функції Рімана: `lim_{N→∞} H(N, s) = ζ(s)`.

### Покроковий розрахунок навантаження на топ-1 ключ

Розглянемо систему з `N = 1 000 000` унікальних ключів та сумарним вхідним трафіком `T = 100 000` запитів на секунду (req/s). Обчислимо навантаження на найпопулярніший ключ (`k = 1`) для різних значень показника схилу `s`.

**Випадок А: Помірна концентрація (`s = 0.8`)**

```
H(10⁶, 0.8)
≈ ∫₁^{10⁶} x⁻⁰˙⁸ dx                 [інтегральне наближення суми гармонійного ряду]
= [x⁰˙² / 0.2]₁^{10⁶}               [первісна степеневої функції: ∫ xⁿ dx = xⁿ⁺¹/(n+1)]
= 5 · ((10⁶)⁰˙² - 1)                [підстановка меж інтегрування Ньютона — Лейбніца]
= 5 · (15.8489 - 1)                 [обчислення степеня: 10^{1.2} = 15.8489]
= 5 · 14.8489                       [обчислення різниці]
= 74.2445                           [множення]

P(1; 0.8, 10⁶)
= (1 / 1⁰˙⁸) / 74.2445              [формула розподілу Ціпфа для k=1]
= 1 / 74.2445                       [спрощення чисельника: 1⁰˙⁸ = 1]
≈ 0.01347                           [ділення: 1.35% трафіку]

Навантаження на топ-1 = 100 000 · 0.01347 = 1347 req/s
```

**Випадок Б: Висока концентрація (`s = 1.0`)**

```
H(10⁶, 1.0)
≈ ln(10⁶) + 0.5772                  [асимптотична формула Ейлера — Маскероні]
= 6 · ln(10) + 0.5772               [властивість логарифма: ln(10⁶) = 6 ln(10)]
= 6 · 2.302585 + 0.5772             [підстановка значення ln(10)]
= 13.8155 + 0.5772                  [множення]
= 14.3927                           [додавання]

P(1; 1.0, 10⁶)
= 1 / 14.3927                       [формула Ціпфа при k=1 та s=1]
≈ 0.06948                           [ділення: 6.95% трафіку]

Навантаження на топ-1 = 100 000 · 0.06948 = 6948 req/s
```

**Випадок В: Екстремальна концентрація / Флеш-сейл (`s = 1.3`)**

```
H(10⁶, 1.3)
≈ ζ(1.3)                            [наближення рядом Рімана при s > 1]
≈ 3.9319                            [табличне значення дзета-функції ζ(1.3)]

P(1; 1.3, 10⁶)
= (1 / 1¹˙³) / 3.9319               [формула Ціпфа при k=1]
= 1 / 3.9319                        [спрощення чисельника]
≈ 0.2543                            [ділення: 25.43% трафіку]

Навантаження на топ-1 = 100 000 · 0.2543 = 25 430 req/s
```

Якщо кластер складається з `M = 64` вузлів, то за ідеального балансу кожен вузол мав би отримувати `100 000 / 64 ≈ 1562` req/s. Проте у випадку `s = 1.3` один єдиний вузол, якому призначено хеш-слот ключа `k = 1`, отримує понад `25 430` req/s — тобто у 16.3 раза більше середньокластерного навантаження.

## 2. Математика розщеплення ключа (Key Salting) та редукція дисперсії

Розщеплення полягає у заміні єдиного гарячого ключа множиною з `K` незалежних ключів із суфіксом:

```
Ключі = { key#0, key#1, key#2, ..., key#(K-1) }
```

Кожен клієнт генерує псевдовипадковий числовий суфікс `i ∈ {0, 1, ..., K-1}` з рівномірним розподілом `P(i) = 1 / K`.

Оскільки хеш-функція шардування (наприклад, `CRC16(key#i) mod 16384`) має властивість рівномірного лавинного розсіювання, кожен із `K` ключів потрапляє у випадковий хеш-слот і, з високою ймовірністю, на різні фізичні вузли кластера.

### Статистичний розподіл навантаження на підключі

Нехай до гарячого ключа надходить `L` незалежних запитів за одиницю часу. Кількість запитів `X_i`, що потрапляють на конкретний підключ `key#i`, є випадковою величиною з біноміальним розподілом:

```
X_i ~ Binomial(L, p),  де p = 1 / K
```

Математичне сподівання `E[X_i]` та дисперсія `Var(X_i)` становлять:

```
E[X_i] = L · p = L / K

Var(X_i) = L · p · (1 - p) = L · (1 / K) · (1 - 1 / K) = (L · (K - 1)) / K²
```

Стандартне відхилення `σ_i`:

```
σ_i = √(Var(X_i)) = (√(L · (K - 1))) / K
```

### Оцінка флуктуацій навантаження

За теоремою Муавра — Лапласа при великих `L` біноміальний розподіл наближається до нормального `N(μ, σ²)`. За правилом трьох сигм із ймовірністю 99.73% навантаження на будь-який розщеплений вузол не перевищить величини:

```
X_max ≤ E[X_i] + 3 · σ_i = (L / K) + 3 · (√(L · (K - 1))) / K
```

Обчислимо для пікового навантаження `L = 100 000` req/s при виборі коефіцієнта розщеплення `K = 16`:

```
E[X_i] = 100 000 / 16 = 6250 req/s

σ_i = √(100 000 · 15) / 16 = √(1 500 000) / 16 = 1224.74 / 16 ≈ 76.55 req/s

X_max ≤ 6250 + 3 · 76.55 = 6250 + 229.65 = 6479.65 req/s
```

Відносне відхилення пікового навантаження від ідеального середнього:

```
Δ = (229.65 / 6250) · 100% ≈ 3.67%
```

Розщеплення на `K = 16` знизило навантаження на один сокет з `100 000` до максимум `6480` req/s (редукція навантаження у 15.4 раза) з мінімальним дисбалансом менше чотирьох відсотків.

## 3. Ймовірність колізій компактних хешів ключів (Парадокс днів народження)

Для економії оперативної пам'яті довгі складені рядкові ключі (наприклад, `search:catalog:category=shoes&brand=nike&size=42&color=red&sort=price_asc`) згортають у компактні числові хеші за допомогою швидких некриптографічних алгоритмів (MurmurHash3, xxHash64, CityHash).

Скорочення ключа породжує ризик колізії (англ. *hash collision*), коли два різних запити отримають однаковий хеш і один клієнт побачить чужі закешовані дані.

### Формула ймовірності колізії

Нехай простір хеш-значень містить `M = 2^b` можливих станів (де `b` — бітова розрядність хешу), а в кеші одночасно зберігається `n` унікальних записів.

Згідно з парадоксом днів народження (англ. *birthday problem*), точна ймовірність `P_coll` того, що серед `n` ключів виникне хоча б одна колізія, дорівнює:

```
P_coll(n, M) = 1 - ∏_{i=0}^{n-1} (1 - i / M)
```

Застосовуючи експоненційне наближення `1 - x ≈ e⁻ˣ` для малих `x = i / M`, отримуємо ланцюг перетворень:

```
∏_{i=0}^{n-1} (1 - i / M)
≈ ∏_{i=0}^{n-1} exp(-i / M)          [експоненційне наближення: 1 - x ≈ exp(-x)]
= exp(- (∑_{i=0}^{n-1} i) / M)       [властивість добутку степенів: ∏ exp(a_i) = exp(∑ a_i)]
= exp(- (n · (n - 1)) / (2 · M))     [сума арифметичної прогресії: ∑_{i=0}^{n-1} i = n(n-1)/2]
≈ exp(- n² / (2 · M))                [апроксимація: n(n-1) ≈ n² для n ≫ 1]
```

Звідси наближена формула ймовірності виникнення хоча б однієї колізії:

```
P_coll(n, M) ≈ 1 - exp(- n² / (2 · M))
```

Якщо `n² ≪ 2M`, застосовуємо розклад у ряд Тейлора `1 - exp(-y) ≈ y`:

```
P_coll(n, M)
≈ 1 - (1 - n² / (2 · M))             [розклад експоненти в ряд Тейлора: exp(-y) ≈ 1 - y]
= n² / (2 · M)                       [спрощення різниці]
= n² / 2^{b + 1}                     [підстановка простору станів M = 2ᵇ]
```

### Порівняльний аналіз 32-, 64- та 128-бітних хешів

**1. 32-бітний хеш (`b = 32`, `M = 2³² ≈ 4.29 × 10⁹`):**

Для кешу на `n = 100 000` (`10⁵`) записів:

```
P_coll ≈ (10⁵)² / (2 · 4.294967 · 10⁹)
       = 10¹⁰ / (8.589934 · 10⁹)
       ≈ 1.164 (тобто P_coll ≈ 1 - exp(-1.164) ≈ 0.6877 -> 68.77%)
```

32-бітний хеш абсолютно непридатний для кешування параметрів: імовірність псування даних перевищує 68% вже на ста тисячах записів.

**2. 64-бітний хеш (`b = 64`, `M = 2⁶⁴ ≈ 1.844674 × 10¹⁹`):**

Для системи з `n = 10 000 000` (`10⁷`) ключів:

```
P_coll ≈ (10⁷)² / (2 · 1.844674 · 10¹⁹)
       = 10¹⁴ / (3.689348 · 10¹⁹)
       ≈ 2.7105 × 10⁻⁶ (0.000271%)
```

Для системи з `n = 1 000 000 000` (`10⁹`) ключів:

```
P_coll ≈ (10⁹)² / (2 · 1.844674 · 10¹⁹)
       = 10¹⁸ / (3.689348 · 10¹⁹)
       ≈ 0.027105 (2.71%)
```

64-бітний хеш (xxHash64) є повністю безпечним для розмірів кешу до кількох десятків мільйонів ключів, проте при досягненні мільярда записів ризик стає помітним (2.7%).

**3. 128-бітний хеш (`b = 128`, `M = 2¹²⁸ ≈ 3.402823 × 10³⁸`):**

Для екстремального сховища з `n = 10¹²` (один трильйон записів):

```
P_coll ≈ (10¹²)² / (2 · 3.402823 · 10³⁸)
       = 10²⁴ / (6.805646 · 10³⁸)
       ≈ 1.4693 × 10⁻¹⁵
```

Ймовірність колізії 128-бітного хешу (MurmurHash3_x64_128 або CityHash128) при одному трильйоні ключів менша, ніж ймовірність апаратного збою комірки оперативної пам'яті під дією космічних променів.

## 4. Теоретичні межі похибки лічильника Count-Min Sketch

Для онлайн-виявлення гарячих ключів у потоці запитів неможливо зберігати точний лічильник для кожного ключа через обмеження пам'яті. Застосовують ймовірнісну структуру даних **Count-Min Sketch**.

Структура являє собою матрицю розміром `d × w`, де `d` — кількість незалежних хеш-функцій `h_1, h_2, ..., h_d`, а `w` — ширина масиву лічильників.

### Параметри конфігурації за похибкою

Нехай задано допустиму похибку `ε` (частка від загального обсягу потоку запитів `||a||₁`) та ймовірність перевищення цієї похибки `δ`. Тоді параметри матриці обираються за формулами:

```
w = ⌈e / ε⌉ ≈ ⌈2.71828 / ε⌉

d = ⌈ln(1 / δ)⌉
```

де `e` — основа натурального логарифма.

### Оцінка частоти та доведення меж похибки

Нехай `f_x` — точна кількість звернень до ключа `x`, а `f̂_x` — оцінка, отримана з Count-Min Sketch:

```
f̂_x = min_{1 ≤ j ≤ d} { Count[j][h_j(x)] }
```

Оскільки лічильники лише інкрементуються і хеш-колізії можуть лише додавати значення інших ключів, оцінка завжди є мажорантою точного значення (відсутні хибно-негативні результати):

```
f̂_x ≥ f_x
```

Оцінимо математичне сподівання колізійного шуму в `j`-му рядку для інших ключів `y ≠ x`:

```
E[Count[j][h_j(x)] - f_x] = ∑_{y ≠ x} f_y · P(h_j(y) = h_j(x))
                          = (1 / w) · ∑_{y ≠ x} f_y
                          ≤ ||a||₁ / w
                          = (ε / e) · ||a||₁
```

За нерівністю Маркова (для невід'ємної випадкової величини `P(Y ≥ α) ≤ E[Y] / α`):

```
P(Count[j][h_j(x)] - f_x ≥ ε · ||a||₁) ≤ ( (ε / e) · ||a||₁ ) / ( ε · ||a||₁ )
                                       = 1 / e
```

Оскільки всі `d` хеш-функцій взаємно незалежні, ймовірність того, що **всі** `d` лічильників перевищать похибку `ε · ||a||₁`, дорівнює:

```
P(f̂_x - f_x ≥ ε · ||a||₁) = ∏_{j=1}^{d} P(Count[j][h_j(x)] - f_x ≥ ε · ||a||₁)
                           ≤ (1 / e)ᵈ
                           = exp(-d)
                           = exp(- ⌈ln(1 / δ)⌉)
                           ≤ δ
```

### Числовий приклад розрахунку пам'яті для детектора

Нехай потік запитів становить `||a||₁ = 10 000 000` запитів на вікно, ми хочемо детектувати ключі з похибкою не більше `0.05%` (`ε = 0.0005`, тобто похибка лічильника не більше 5000 запитів) з надійністю 99.9% (`δ = 0.001`):

```
w = ⌈2.71828 / 0.0005⌉ = 5437 колонок

d = ⌈ln(1 / 0.001)⌉ = ⌈ln(1000)⌉ = ⌈6.9077⌉ = 7 рядків
```

Загальна кількість 32-бітних лічильників:

```
Загальна пам'ять = 7 · 5437 · 4 байти = 152 236 байтів ≈ 148.7 КБ
```

Усього 149 КБ оперативної пам'яті достатньо для точного відстеження та виявлення гарячих ключів серед десятків мільйонів запитів із гарантованою математичною строгістю.
