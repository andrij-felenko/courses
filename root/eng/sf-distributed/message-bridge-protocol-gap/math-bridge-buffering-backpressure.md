# 🧮 Математична модель буферизації та протитиску в мостах шин

<preknowlist>
- [Черга повідомлень](topic:sf-distributed/message-queue) — передача повідомлень через буфер з обмеженою ємністю.
- [Наскрізний протитиск](topic:sf-distributed/backpressure-end-to-end) — узгодження швидкості джерела та споживача для запобігання переповненню.
- [Таймаути і бюджет часу](topic:sf-distributed/timeouts-deadlines) — обмеження часу очікування мережевих операцій.
</preknowlist>

Архітектурна надійність мосту повідомлень (Store-and-Forward Bridge) спирається на точний аналітичний розрахунок параметрів проміжного буфера, пропускної здатності каналів, динаміки пакетування, хвостових затримок, векторного відстеження підтверджень та часових затримок поширення сигналу протитиску (англ. *backpressure*). Якщо буфер мосту замалий, будь-який сплеск трафіку або короткочасне уповільнення цільової шини призводить до відкидання повідомлень (Buffer Overflow Drop) або аварійної зупинки джерела. Якщо ж буфер надмірно великий, при збоях накопичуються гігабайти застарілих даних, що спричиняє неприпустиме зростання наскрізної затримки (Bufferbloat) та ризик вичерпання оперативної пам'яті.

## 1. Розрахунок стаціонарного обсягу буфера за законом Літтла

У стаціонарному режимі роботи міст вичитує повідомлення з вхідної шини А з середньою інтенсивністю `λ` (повідомлень/с) та транслює їх у вихідну шину Б з інтенсивністю обслуговування `μ` (повідомлень/с).

Кожне повідомлення перебуває в конвеєрі мосту протягом середнього часу транзиту `W`, який складається з чотирьох послідовних складових:
* `t_decode` — час десеріалізації та перевірки схеми корисного навантаження;
* `t_transform` — час модифікації заголовків, перевірки хопів та маршрутизації;
* `t_network` — час передачі пакета через мережевий канал до цільового брокера (Round-Trip Time, RTT);
* `t_dest_ack` — час фіксації на диску та підтвердження запису цільовим брокером (Egress ACK latency).

```
W = t_decode + t_transform + t_network + t_dest_ack
```

Згідно з законом Літтла (Little's Law), середня кількість повідомлень `L`, які одночасно перебувають у стані транзиту («в польоті», in-flight) всередині мосту, дорівнює добутку інтенсивності вхідного потоку на повний середній час перебування в системі:

```
L = λ · W
```

**Приклад розрахунку для трансконтинентального мосту:**
* Вхідний потік з локального заводського брокера: `λ = 10 000` повідомлень/с.
* Внутрішня обробка мостом: `t_decode + t_transform = 0.5` мс (`0.0005` с).
* Мережева затримка WAN (Франкфурт ↔ Орегон): `t_network = 120` мс (`0.120` с).
* Затримка підтвердження дискового запису кластером Kafka (`acks=all`): `t_dest_ack = 9.5` мс (`0.0095` с).

Повний середній час транзиту:

```
W = 0.0005 + 0.120 + 0.0095
  = 0.130 с      [сума складових затримки: 130 мс]
```

Мінімальна кількість слотів пам'яті в конвеєрі для забезпечення безперервної передачі без простоїв:

```
L = 10 000 · 0.130
  = 1300 повідомлень      [закон Літтла: L = λ · W]
```

Якщо розмір вікна паралельних запитів (`max_in_flight_requests`) мосту буде меншим за 1300, міст штучно обмежить пропускну здатність вхідного каналу, недовантажуючи доступну мережеву смугу.

## 2. Добуток смуги пропускання на затримку (BDP) та розмір вікна ковзання

Для підтримки максимальної утилізації каналу зв'язку міст повинен тримати в мережі обсяг даних, пропорційний добутку пропускної здатності на затримку кругового обігу (Bandwidth-Delay Product, BDP):

```
BDP_bytes = C_bandwidth · RTT
```

де `C_bandwidth` — доступна пропускна здатність каналу у байтах за секунду, а `RTT` — час кругового обігу пакетів.

Якщо середній розмір повідомлення дорівнює `S_msg` байтів, оптимальний розмір ковзного вікна паралельних непідтверджених повідомлень `N_window` становить:

```
N_window = BDP_bytes ÷ S_msg
         = (C_bandwidth · RTT) ÷ S_msg
```

**Доведення колапсу пропускної здатності при замалому вікні:**

Нехай виділений канал WAN забезпечує швидкість `C_bandwidth = 100` Мбіт/с (`12.5` МБ/с = `12 500 000` байтів/с), затримка `RTT = 80` мс (`0.080` с), а розмір повідомлення `S_msg = 1000` байтів.

```
BDP_bytes = 12 500 000 · 0.080
          = 1 000 000 байтів      [1 МБ даних у польоті]

N_optimal = 1 000 000 ÷ 1000
          = 1000 повідомлень      [оптимальний розмір вікна]
```

Якщо конфігурація мосту обмежує розмір вікна значенням `N_actual = 100` повідомлень (у 10 разів менше оптимального), фактична досяжна пропускна здатність `R_actual` впаде пропорційно:

```
R_actual = (N_actual · S_msg) ÷ RTT
         = (100 · 1000) ÷ 0.080
         = 100 000 ÷ 0.080
         = 1 250 000 байтів/с
         = 10 Мбіт/с              [використовується лише 10% смуги пропускання]
```

Висновок: міст із жорстким синхронним підтвердженням кожного окремого повідомлення (`N_window = 1`) на каналі з `RTT = 80` мс здатний передати щонайбільше `1 / 0.080 = 12.5` повідомлень/с незалежно від фізичної гігабітної швидкості лінії.

## 3. Оптимізація мікропакетування (Micro-batching Trade-off)

Для подолання накладних витрат мережевих заголовків (TCP/IP + TLS + заголовки брокера `H_overhead`) міст об'єднує окремі вхідні повідомлення в пакети (Batches) розміром `B` штук перед відправкою у вихідну шину.

Корисна пропускна здатність каналу зростає зі збільшенням розміру пакета `B`, оскільки накладні витрати розподіляються між багатьма повідомленнями. Проте накопичення пакета вводить додаткову середню затримку очікування `t_linger`:

```
t_linger = (B - 1) ÷ (2 · λ)      [середній час накопичення B повідомлень при інтенсивності λ]
```

Накладні витрати каналу на одне повідомлення `Cost_msg(B)` виражаються як:

```
Cost_msg(B) = (H_overhead ÷ B) + S_payload      [байтів на одне корисне повідомлення]
```

Повна затримка доставки повідомлення `T_total(B)`:

```
T_total(B) = t_linger + t_transit
           = [(B - 1) ÷ (2 · λ)] + [(H_overhead + B · S_payload) ÷ C_bandwidth] + RTT
```

**Оптимізація за критерієм максимізації пропускної здатності за фіксованого бюджету затримки:**

Нехай максимальна допустима затримка буферизації мосту становить `T_budget` секунд. Максимальний допустимий розмір пакета `B_max`, який не порушує регламент затримки (SLA):

```
[(B_max - 1) ÷ (2 · λ)] ≤ T_budget

B_max ≤ 1 + 2 · λ · T_budget      [верхня межа розміру пакета]
```

**Числовий розрахунок:**
* Вхідний потік: `λ = 20 000` msg/s.
* Бюджет затримки накопичення пакета: `T_budget = 5` мс (`0.005` с).

```
B_max = 1 + 2 · 20 000 · 0.005
      = 1 + 200
      = 201 повідомлення      [максимальний розмір мікропакета]
```

Налаштування мосту `batch.size = 200` та `linger.ms = 5` забезпечує оптимальний компроміс: максимальну утилізацію каналу без порушення ліміту затримки.

## 4. Хвостові затримки, джитер та блокування початку черги

У реальних розподілених системах час мережевого транзиту `t_network` та час дискової фіксації `t_dest_ack` не є константами, а підпорядковуються логнормальному розподілу з «важким хвостом» (Heavy-Tail Distribution).

Якщо затримка описується випадковою величиною `T` з середнім значенням `E[T] = W` та дисперсією `Var(T) = σ²`, для забезпечення безперервної роботи конвеєра з імовірністю 99.9% (перцентиль `P99.9`) розмір вікна `L_p99` повинен розраховуватися не за середнім `W`, а за перцентилем `W_p99.9`:

```
L_p99 = λ · W_p99.9
```

За наближенням Чебишова або для логнормального розподілу з параметрами масштабу `m` і форми `s`:

```
W_p99.9 = exp(m + 3.090 · s)      [де 3.090 — квантиль стандартного нормального розподілу для 0.999]
```

**Ефект блокування початку черги (Head-of-Line Blocking):**

Якщо міст вимагає суворого збереження послідовності комітів у вихідний partitioned log або вхідну чергу, одне зависле повідомлення з хвостовою затримкою `W_tail = W_p99.9` блокує просування вікна коміту `Offset_commit` для всіх наступних `K` успішно доставлених повідомлень:

```
Offset_commit = min(Uncommitted_Inflight_Offsets) - 1
```

Кількість повідомлень `Q_blocked`, що накопичуються в оперативній пам'яті під час очікування одного завислого запиту:

```
Q_blocked = λ · (W_tail - W_avg)
```

**Приклад розрахунку:**
* `λ = 15 000` msg/s.
* Середня затримка: `W_avg = 20` мс (`0.020` с).
* Хвостова затримка P99.9 через ретрай пакетів або дискове зависання fsync: `W_tail = 1200` мс (`1.200` с).

```
Q_blocked = 15 000 · (1.200 - 0.020)
          = 15 000 · 1.180
          = 17 700 повідомлень      [обсяг оперативної пам'яті для утримання черги блокування]
```

Якщо внутрішній масив стану мосту не розрахований на утримання 17 700 дескрипторів, міст зупинить вхідне зчитування, викликавши хвилю хибного протитиску на вхідну шину.

## 5. Векторне відстеження непідтверджених зміщень (Bitset Window Commit)

Коли міст використовує паралельний пул воркерів для вихідної відправки, повідомлення завершуються в довільному порядку (Out-of-Order ACK). Якщо вхідна шина вимагає монотонного зміщення коміту (наприклад, Apache Kafka `commitSync` або AMQP `multiple=true`), міст веде ковзну бітову карту (Bitset Sliding Window).

Нехай `Offset_base` — це останній неперервно підтверджений зсув. При отриманні підтвердження для зсуву `Offset_k` встановлюється біт у позиції `idx = Offset_k - Offset_base`:

```
Bitmap[Offset_k - Offset_base] = 1
```

Новий монотонний зсув коміту `Offset_new_base` визначається довжиною неперервного префікса одиничних бітів `P_ones`:

```
Offset_new_base = Offset_base + CountLeadingOnes(Bitmap)
```

Після оновлення бітова карта зсувається вліво на `CountLeadingOnes(Bitmap)` позицій. Необхідний обсяг пам'яті бітової карти `M_bitset` для вікна розміром `W_max` становить:

```
M_bitset = ⌈W_max ÷ 64⌉ · 8 байтів      [масив 64-бітних слів]
```

Для вікна `W_max = 65 536` повідомлень розмір бітової карти становить лише 8192 байти (8 КБ), що повністю поміщається в кеш процесора L1d, забезпечуючи час обчислення коміту `O(1)` за допомогою апаратних процесорних інструкцій пошуку першого нульового біта (CTZ/CLZ).

## 6. Буферизація під час мережевих розривів (WAN Outages)

Глобальні канали зв'язку зазнають періодичних аварій та затримок відновлення маршрутизації BGP. Нехай максимальний очікуваний час повної ізоляції мосту від цільової шини до автоматичного перемикання становить `T_outage` секунд.

Протягом цього інтервалу вихідний потік повністю припиняється (`μ = 0`), тоді як джерело продовжує генерувати повідомлення з постійною середньою інтенсивністю `λ`.

Мінімальний розмір енергонезалежного буфера аварійного накопичення (Write-Ahead Log або дисковий Ring Buffer) `B_outage` для уникнення втрат:

```
B_outage = ∫[0 до T_outage] λ(t) dt
         = λ · T_outage      [за умови стаціонарного вхідного потоку λ = const]
```

Необхідний обсяг дискового сховища `M_disk`:

```
M_disk = B_outage · S_msg
       = λ · T_outage · S_msg
```

**Розрахунок дискового простору для промислового IoT-мосту:**
* Інтенсивність потоку телеметрії датчиків: `λ = 25 000` повідомлень/с.
* Середній розмір серіалізованого повідомлення: `S_msg = 512` байтів.
* Розрахунковий час відновлення стільникового зв'язку: `T_outage = 600` секунд (10 хвилин).

```
B_outage = 25 000 · 600
         = 15 000 000 повідомлень      [ємність буфера за кількістю записів]

M_disk = 15 000 000 · 512 байтів
       = 7 680 000 000 байтів
       ≈ 7.15 ГБ                       [необхідний обсяг дискового пулу]
```

## 7. Ймовірність втрати повідомлень у скінченній системі M/M/1/K

Коли оперативна пам'ять мосту обмежена фіксованим буфером на `K` повідомлень, а вхідне джерело не підтримує протокол протитиску (наприклад, відкритий UDP або датчики IoT без зворотного зв'язку), система моделюється чергою масового обслуговування типу `M/M/1/K`.

Параметри моделі:
* `λ` — інтенсивність надходження повідомлень (пуассонівський потік);
* `μ` — інтенсивність відправки та підтвердження цільовою шиною (експоненційний розподіл обслуговування);
* `ρ = λ / μ` — коефіцієнт навантаження системи (Traffic Intensity);
* `K` — максимальна місткість буфера мосту.

Стаціонарна ймовірність того, що буфер мосту повністю заповнений (у черзі перебуває рівно `K` повідомлень), визначає **ймовірність відкидання вхідного повідомлення** `P_loss`:

```
P_loss = P_K
       = [(1 - ρ) · ρ^K] ÷ [1 - ρ^(K + 1)]      [для випадку ρ ≠ 1]
```

Якщо інтенсивність надходження збігається з інтенсивністю виходу (`ρ = 1`), формулу обчислюють як:

```
P_loss = 1 ÷ (K + 1)      [для випадку балансу потоків ρ = 1]
```

**Аналіз поведінки системи при деградації цільової шини:**

Нехай цільовий брокер починає тротлити з'єднання: `λ = 1000` msg/s, `μ = 800` msg/s (`ρ = 1.25`), розмір оперативної черги `K = 50`.

```
ρ = 1000 ÷ 800
  = 1.25                    [коефіцієнт перевантаження системи]

P_loss = [(1 - 1.25) · 1.25^50] ÷ [1 - 1.25^51]
       = [-0.25 · 70 064.9] ÷ [1 - 87 581.1]
       = [-17 516.2] ÷ [-87 580.1]
       ≈ 0.200                      [20% вхідних повідомлень безповоротно втрачаються]
```

Висновок: при `ρ > 1` у буфері без зворотного зв'язку частка втрат прямує до асимптотичного значення `1 - (1/ρ) = 1 - (1/1.25) = 0.20` незалежно від збільшення ємності `K`. Буфер лише відтерміновує момент початку втрат, але не рятує від переповнення.

## 8. Динаміка протитиску та затримка розповсюдження сигналу

Для запобігання втратам міст застосовує схему керування двома водяними знаками (Watermarks):
* `H` (High Watermark) — верхній поріг (наприклад, 80% буфера): момент активації сигналу гальмування вхідного каналу;
* `L` (Low Watermark) — нижній поріг (наприклад, 40% буфера): момент відновлення зчитування.

Між моментом досягнення порогу `H` і моментом, коли вхідний потік фізично зупиняється на стороні джерела, минає час реакції контуру протитиску `τ_bp` (Backpressure Propagation Delay):

```
τ_bp = t_detect + t_signal + t_drain_inflight
```

де `t_detect` — квант перевірки буфера, `t_signal` — затримка передачі команди паузи джерелу, а `t_drain_inflight` — час дочитування пакетів, які вже перебували в сокетах операційної системи.

Протягом часу `τ_bp` вхідні повідомлення продовжують надходити з інтенсивністю `λ`, тоді як міст відправляє їх у сповільнену вихідну шину зі швидкістю `μ_degraded`.

Величина додаткового переповнення черги (Queue Overshoot) `ΔQ`:

```
ΔQ = (λ - μ_degraded) · τ_bp
```

**Умова проєктування безпечного буфера без переповнення:**

Загальний розмір буфера `B_total` повинен гарантовано вміщувати високий поріг `H` плюс максимальний динамічний викид `ΔQ`:

```
B_total ≥ H + ΔQ
B_total ≥ H + (λ - μ_degraded) · τ_bp
```

**Числовий приклад розрахунку:**
* Максимальний вхідний потік: `λ = 20 000` msg/s.
* Швидкість виходу при деградації: `μ_degraded = 2 000` msg/s.
* Час затримки зворотного зв'язку: `τ_bp = 150` мс (`0.150` с).
* Обраний високий поріг: `H = 50 000` повідомлень.

```
ΔQ = (20 000 - 2 000) · 0.150
   = 18 000 · 0.150
   = 2 700 повідомлень      [динамічний викид черги]

B_total ≥ 50 000 + 2 700
B_total ≥ 52 700 повідомлень
```

При виборі ємності буфера `B_total = 60 000` повідомлень конвеєр гарантовано уникає переповнення та втрати даних під час перехідних процесів.

## 9. Ймовірність дублювання в моделі Dual-Ack при аварійних крахах

При реалізації семантики At-Least-Once міст підтверджує повідомлення у вхідній шині лише після успішної фіксації у вихідній. Якщо міст зазнає аварійного перезапуску у вразливому часовому вікні `Δt_vuln = t_commit_ingress - t_ack_egress`, повідомлення повторно вичитується після рестарту і транслюється вдруге.

Нехай інтенсивність апаратних або програмних збоїв вузла мосту описується пуассонівським процесом з параметром `λ_fail` (збоїв/с). Ймовірність того, що конкретне повідомлення буде продубльоване:

```
P_dup = 1 - exp(-λ_fail · Δt_vuln)
      ≈ λ_fail · Δt_vuln      [для малих значень λ_fail · Δt_vuln << 1]
```

Очікувана середня частота генерації дублікатів у потоці `R_dup` (дублікатів/с):

```
R_dup = λ · P_dup
      ≈ λ · λ_fail · Δt_vuln
```

**Розрахунок місткості фільтра дедуплікації на боці цільової шини:**

Якщо цільова система або міст використовує ковзний фільтр Блума (Bloom Filter) з бітовим масивом розміром `m` бітів та `k` незалежними хеш-функціями для відстеження `n` унікальних повідомлень протягом вікна `T_dedup_window`, ймовірність хибнопозитивного спрацьовування `P_fp` (хибне відкидання нового повідомлення як нібито дубліката) визначається формулою:

```
P_fp ≈ (1 - exp(-k · n ÷ m))^k
```

Оптимальна кількість хеш-функцій `k_opt`, що мінімізує `P_fp` для заданого співвідношення пам'яті:

```
k_opt = (m ÷ n) · ln(2)
      ≈ 0.693 · (m ÷ n)
```

Мінімальний розмір пам'яті `m` для забезпечення допустимої ймовірності помилки `P_fp ≤ 10^(-6)` (не більше одного хибного відкидання на мільйон повідомлень):

```
m = - [n · ln(P_fp)] ÷ (ln(2))^2
  ≈ n · 28.75 бітів      [близько 3.6 байта пам'яті на один ідентифікатор]
```

Для потоку `λ = 10 000` msg/s та вікна дедуплікації `T_dedup_window = 300` с кількість повідомлень `n = λ · T_dedup_window = 3 000 000`. Необхідний розмір бітового масиву становить лише `m = 3 000 000 · 3.6 ≈ 10.8` МБ, що забезпечує мікросекундну перевірку дублікатів без звернення до зовнішніх баз даних.

## 10. Математика експоненційного відступу з повним джитером

Коли вихідне мережеве з'єднання падає, воркери мосту ініціюють цикл повторних підключень. Щоб уникнути резонансного шторму запитів (Thundering Herd / Resonance Effect), інтервал між спробами `k` обчислюється за алгоритмом експоненційного відступу з повним рандомізованим джитером (Full Jitter Exponential Backoff):

```
T_cap(k) = min(T_max, T_base · 2^k)
T_sleep(k) = Uniform(0, T_cap(k))
```

Математичне сподівання часу затримки `E[T_sleep(k)]`:

```
E[T_sleep(k)] = T_cap(k) ÷ 2
              = min(T_max, T_base · 2^k) ÷ 2
```

Дисперсія інтервалу повторів `Var(T_sleep(k))`:

```
Var(T_sleep(k)) = [T_cap(k)]^2 ÷ 12
```

Завдяки рівномірному розподілу `Uniform(0, T_cap)` пікова щільність повторних з'єднань від `M` паралельних потоків мосту зменшується в `T_cap / T_slot` разів порівняно з детермінованим відступом, унеможливлюючи повторне падіння цільового брокера при відновленні зв'язку.

## 11. Час відновлення після ліквідації затору (Drain Time)

Після усунення мережевого збою або відновлення працездатності цільової шини її пропускна здатність зростає до номінального пікового значення `μ_max > λ`.

Якщо під час збою в буфері мосту накопичилося `Q_backlog` повідомлень, час повного спустошення черги до стаціонарного стану `T_drain` обчислюється як:

```
T_drain = Q_backlog ÷ (μ_max - λ)
```

**Приклад розрахунку:**
* Накопичений беклог: `Q_backlog = 1 500 000` повідомлень.
* Вхідний потік: `λ = 10 000` msg/s.
* Пікова швидкість цільового брокера: `μ_max = 25 000` msg/s.

```
T_drain = 1 500 000 ÷ (25 000 - 10 000)
        = 1 500 000 ÷ 15 000
        = 100 секунд      [час повної ліквідації черги]
```

Різниця `(μ_max - λ)` є запасом пропускної здатності відновлення (Recovery Headroom). Якщо `μ_max ≤ λ`, накопичене відставання ніколи не буде ліквідоване без примусового скидання вхідного навантаження.
