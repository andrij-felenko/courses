На початку 1990-х років корпоративні інформаційні системи зіткнулися з кризою несумісності. Фінансові транзакції банківських мейнфреймів оброблялися через IBM MQSeries (згодом WebSphere MQ), біржові торговельні термінали транслювали ринкові котирування через асинхронні демони TIBCO Rendezvous і The Information Bus (TIB), а телекомунікаційні білінгові платформи спиралися на DEC MessageQ. Кожен постачальник проміжного програмного забезпечення, орієнтованого на повідомлення (Message-Oriented Middleware, MOM), використовував власний закритий бінарний протокол передачі, специфічні структури мережевих пакетів і несумісні семантики підтвердження доставки.

Інтеграція двох таких систем змушувала інженерів писати нестабільні кастомні демони-конвертери мовою C. Ці програми вручну зчитували байти з сокета однієї системи, перепаковували їх у внутрішній формат іншої та записували у вихідний дескриптор. Будь-який мережевий збій або перезапуск процесу призводив або до мовчазної втрати критичних транзакцій, або до лавиноподібного дублювання фінансових проводок через відсутність скоординованого підтвердження доставки між двома незалежними чергами.

## Спроба уніфікації через API та криза мережевого протоколу

У 1998 році консорціум компаній на чолі з Sun Microsystems представив специфікацію Java Message Service (JMS). JMS запропонувала розробникам єдиний уніфікований об'єктний інтерфейс для роботи з чергами (`Queue`) та темами підписки (`Topic`). Проте стандартизація API вирішила проблему лише на рівні програмного коду всередині однієї віртуальної машини JVM:
* JMS не стандартизувала мережевий протокол (wire protocol): клієнт IBM WebSphere MQ не міг відправити бінарний TCP-пакет брокеру Progress SonicMQ або TIBCO EMS, оскільки протоколи передачі залишалися закритими.
* Програми, написані мовами C++, COBOL чи Perl, залишалися за межами екосистеми Java і вимагали окремих проміжних шлюзів.
* Для з'єднання двох різних JMS-провайдерів знадобився виділений архітектурний компонент — **міст повідомлень** (англ. *JMS Bridge*), який одночасно ініціалізував два клієнтські контексти JNDI, споживав повідомлення з вхідної фабрики з'єднань і транслював їх у вихідну.

Перші промислові мости намагалися гарантувати надійність через двофазну фіксацію (Two-Phase Commit, 2PC) за стандартом XA під управлінням транзакційного монітора (Transaction Processing Monitor, наприклад Tuxedo або WebLogic JTA). Архітектурний розрахунок полягав у тому, що транзакційний координатор об'єднував вилучення з черги А та запис у чергу Б в єдину розподілену транзакцію.

Хоча XA гарантував теоретичну атомарність перенесення («повідомлення видалено з черги А тоді й лише тоді, коли воно зафіксоване в черзі Б»), плата за розподілене блокування виявилася надто високою. Координація фаз підготовки (`prepare`) та фіксації (`commit`) через глобальні мережі (WAN) призводила до експоненційного зростання затримок: пропускна здатність мостів падала до 50–100 повідомлень на секунду. Будь-який розрив зв'язку або затримка відповіді залишали транзакції в невизначеному стані (in-doubt state), блокуючи системні ресурси та заморожуючи черги на обох кінцях. Стало очевидно: розподілені транзакції непридатні для асинхронного зв'язку через нестабільні канали зв'язку.

## Патерн Messaging Bridge та епоха відкритого AMQP

У 2003 році Ґреґор Гоп (Gregor Hohpe) та Боббі Вулф (Bobby Woolf) у фундаментальній книзі «Enterprise Integration Patterns» канонізували **міст повідомлень** (англ. *Messaging Bridge*) як системний патерн розподіленої архітектури:

```
[Шина А (напр. JMS)] ---> [Вхідний адаптер] ---> [Транслятор/Буфер] ---> [Вихідний адаптер] ---> [Шина Б (напр. AMQP)]
                                            \________ МІСТ ________/
```

Автори підкреслили, що завдання мосту полягає не просто в перекачуванні байтів, а в повному розчепленні двох незалежних просторів обміну повідомленнями при збереженні їхньої автономії, внутрішньої топології та механізмів авторизації. Замість важких розподілених транзакцій міст повинен використовувати патерн збереження і пересилання (Store-and-Forward) з локальним буфером та подвійним підтвердженням (Dual-Ack).

Поява у 2006 році відкритого бінарного протоколу AMQP (Advanced Message Queuing Protocol) і брокера RabbitMQ ознаменувала відмову від пропрієтарних шлюзів. Замість громіздких ESB-мостів розробники RabbitMQ реалізували два автономні легковажні плагіни, які стали еталоном для брокерів черг:
1. **RabbitMQ Shovel:** автономний компонент, що виконує безперервний цикл: «вичитати пакет із черги джерела → переслати у вузол призначення → дочекатися вихідного підтвердження `basic.ack` → надіслати підтвердження вхідній черзі». Shovel отримав механізми адаптивного розміру вікна вичитування (`prefetch_count`) та експоненційного відступу при обривах зв'язку, дозволяючи з'єднувати брокери через міжконтинентальні канали без ризику переповнення пам'яті.
2. **RabbitMQ Federation:** федеративний міст, що транслює повідомлення між географічно віддаленими брокерами за вимогою: повідомлення передаються через глобальну мережу лише тоді, коли на віддаленому вузлі з'являється активний споживач, який підписався на відповідну тему.

Паралельно розвивалися інтеграційні фреймворки (Apache Camel, Spring Integration), де концепція мосту отримала декларативний опис маршрутів (Enterprise Integration DSL), дозволяючи інженерам налаштовувати трансляцію між десятками протоколів (JMS, AMQP, TCP, HTTP) кількома рядками конфігурації без написання низькорівневого мережевого коду.

## Стримінгова революція: від черг до розподілених логів

З появою Apache Kafka у 2011 році парадигма обміну даними змістилася від деструктивних черг до незмінних розподілених журналів подій (англ. *event logs*). Це створило фундаментальний розрив у семантиці мостів:
* У класичній черзі одиницею прогресу є індивідуальне підтвердження повідомлення (`message ACK`), а прочитане повідомлення безповоротно видаляється з брокера.
* У лозі подій повідомлення зберігаються на диску днями або роками, а одиницею прогресу є монотонно зростаючий числовий [зсув у журналі подій](topic:sf-distributed/event-log) всередині розділу (partition offset).

Для міжкластерної реплікації інженери LinkedIn створили інструмент **Kafka MirrorMaker** (MirrorMaker 1). Перша версія була простим з'єднанням стандартного Kafka Consumer та Kafka Producer: споживач вичитував повідомлення з вихідного кластера, а продюсер записував їх у цільовий.

Проте MirrorMaker 1 страждав від трьох фундаментальних недоліків, які роками викликали масштабні збої в розподілених системах:
1. **Шторми перебалансування (Rebalance Storms):** використання стандартних груп споживачів призводило до того, що тимчасове зависання мережі на одному з воркерів ініціювало повне перебалансування всіх розділів кластера, зупиняючи передачу трафіку на кілька хвилин.
2. **Втрата відповідності зсувів (Offset Inconsistency):** цільовий кластер призначав реплікованим подіям нові локальні зсуви, відмінні від вихідних. Під час аварійного перемикання на резервний дата-центр (Disaster Recovery) споживачі не могли зрозуміти, з якого зміщення продовжувати читання, що спричиняло повторну обробку гігабайтів старих даних.
3. **Небезпека луни (Echo Loops):** у двонаправлених конфігураціях «актив-актив» репліковане повідомлення потрапляло в контур зворотного мосту, що викликало нескінченне циклічне множення повідомлень і миттєве вичерпання дискового простору.

У 2019 році з виходом Kafka 2.4 інженери представили **MirrorMaker 2.0 (MM2)**, повністю перероблений на базі розподіленого фреймворку Kafka Connect:
* **Динамічне розділення просторів імен:** кожна реплікована тема автоматично отримує префікс джерела (наприклад, `us-east.orders`), що фізично унеможливлює зациклення без інспекції тіла повідомлення.
* **Автоматична трансляція зсувів:** міст веде спеціальний службовий топік `offset-syncs`, записуючи пари `(source_offset ↦ target_offset)`. Спеціальний транслятор контрольних точок (Checkpoint Connector) дозволяє клієнтам миттєво перемикатися на резервний кластер зі збереженням точної позиції споживання.
* **Ізоляція завдань:** кожен розділ обслуговується незалежним таском, завдяки чому збій одного каналу не впливає на інші потоки даних.

## Сучасний ландшафт: Edge-to-Cloud та Serverless Event Pipes

Сьогодні мости шин повідомлень розвиваються у двох домінуючих напрямках:

```
+-----------------------------------------------------------------------------------+
| 1. Edge-to-Cloud Мости (IoT)                                                      |
| Сенсори/Контролери ---> [EMQX / VerneMQ (MQTT)] ===(WAN-Міст)===> [Cloud Kafka]   |
|                                                                                   |
| 2. Хмарні безсерверні конвеєри (Cloud Event Pipes)                               |
| DynamoDB Streams / SQS =====(AWS EventBridge Pipes)=====> Kinesis / EventBus       |
+-----------------------------------------------------------------------------------+
```

1. **Edge-to-Cloud мости (IoT):** сучасні брокери промислового Інтернету речей (EMQX, Eclipse Mosquitto, VerneMQ) містять високоефективні рушії мостів на мовах C, Rust та Erlang. Вони оптимізовані для роботи в умовах нестабільного стільникового зв'язку: міст накопичує телеметрію в локальному енергонезалежному журналі (Write-Ahead Log) під час обриву зв'язку, а після відновлення з'єднання вивантажує дані в хмарний кластер Kafka або Pulsar пакетними порціями з контролем протитиску.
2. **Безсерверні шинні конвеєри (Serverless Event Pipes):** хмарні платформи (AWS EventBridge Pipes, GCP Eventarc, Azure Event Grid) перетворили міст на керовану інфраструктурну послугу. Інженерам більше не потрібно адмініструвати віртуальні машини чи демони реплікації: хмарний міст декларативно з'єднує потоки змін баз даних (DynamoDB Streams, CDC), черги та журнальні шини, автоматично виконуючи фільтрацію, перетворення форматів і захист від перевантаження цільових систем.
3. **Стандартизація метаданих (CloudEvents):** створення під егідою CNCF стандарту CloudEvents дало змогу уніфікувати контекстні заголовки повідомлень (ідентифікатор, джерело, тип події, часова мітка). Завдяки цьому сучасні мости здійснюють трансляцію між несумісними брокерами без десеріалізації бізнес-корисного навантаження, забезпечуючи нульове копіювання (Zero-Copy) і максимальну швидкість пересилання.
