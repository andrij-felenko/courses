# 📜 Від перфокарт і EDIFACT до реактивних потоків: еволюція розбиття повідомлень

Перехід від нічних монолітних пакетних файлів на магнітних стрічках до безперервних розподілених потоків подій є однією з найглибших трансформацій в історії програмної інженерії. Проблема декомпозиції складених пакетів даних — виділення окремих бізнес-одиниць із масивного масиву для їхньої незалежної обробки — виникла задовго до появи терміна «мікросервіси» чи концепції брокерів повідомлень. Розуміння того, як інженерна думка долала обмеження обчислювальної пам'яті, мережевої пропускної здатності та надійності передачі, пояснює фундаментальні інваріанти сучасного патерну розділювача повідомлень (*Message Splitter*).

## Епоха мейнфреймів і пакетної обробки (1960–1970-ті роки)

На світанку комерційних обчислень комп'ютери класу IBM System/360 не мали постійного мережевого підключення до філій підприємств. Дані фінансових транзакцій, складських переміщень чи табелів обліку робочого часу накопичувалися протягом робочого дня на перфокартах або паперових стрічках. Увечері ці колоди перфокарт завантажувалися у зчитувачі, формуючи послідовний масив записів фіксованої довжини (англ. *fixed-width records*), зазвичай по 80 байтів на рядок (відповідно до стандарту перфокарти IBM).

Ці записи переносилися на бобіни з магнітною стрічкою шириною пів дюйма. Обчислювальний центр запускав так зване «нічне пакетне вікно» (англ. *nightly batch window*). Програма на мові COBOL чи Assembler послідовно зчитувала файл блок за блоком. Оскільки оперативна пам'ять на магнітних осердях (англ. *core memory*) вимірювалася кілобайтами (типово від 32 до 512 КБ), завантажити весь файл транзакцій у пам'ять було фізично неможливо.

Саме тут виник прототип потокового розділювача: програма зчитувала з магнітної стрічки один блок даних (англ. *physical record block*), виділяла з нього окремі логічні записи транзакцій (англ. *logical records*), валідувала контрольні суми й передавала кожен запис у відповідну підпрограму оновлення головної книги. Якщо один запис усередині 10 000-елементного файла містив синтаксичну помилку або некоректний рахунок, мейнфрейм не мав можливості ізолювати збійний елемент на льоту: уся нічна обробка зупинялася з кодом аварійного завершення *ABEND* (англ. *abnormal end*), а черговий оператор був змушений вручну виправляти збійну перфокарту й перезапускати багатопогодинний прогін стрічки спочатку.

Ця фундаментальна вада пакетної обробки — спільна відмова всього масиву через одиничний збій та колосальна затримка між створенням події та її обробкою — сформувала перший інженерний запит на декомпозицію та ізоляцію елементів.

## Поява електронного обміну даними: стандарти EDIFACT та ANSI X12 (1980-ті роки)

У 1980-х роках глобалізація торгівлі, морських перевезень та автомобільної промисловості вимагала автоматизації обміну комерційними документами між різнорідними корпоративними системами. Організація Об'єднаних Націй розробила стандарт UN/EDIFACT (англ. *United Nations / Electronic Data Interchange for Administration, Commerce and Transport*), а в США набув поширення стандарт ANSI ASC X12.

Архітектура повідомлень EDI базувалася на ієрархічній структурі конвертів:
1. `UNB` / `UNZ` — службовий конверт обміну (Interchange Envelope), що містив ідентифікатори відправника й одержувача та загальний контрольний номер.
2. `UNG` / `UNE` — функціональна група документів (Functional Group), наприклад, пакет рахунків-фактур чи каталог замовлень.
3. `UNH` / `UNT` — заголовок і кінцевик окремого комерційного повідомлення (Transaction Set), наприклад, ордер на поставку `ORDERS` або податковий інвойс `INVOIC`.
4. Сегменти даних усередині документа (наприклад, `LIN` для товарної позиції, `QTY` для кількості, `MOA` для грошових сум).

Підприємства надсилали одне одному гігантські складені файли EDI через мережі з доданою вартістю (англ. *Value-Added Networks*, VAN), де тарифікація нараховувалася за кожен переданий кілобайт. Тому компаніям було вигідно запаковувати тисячі замовлень від різних магазинів в один масивний пакетний файл обміну.

Проте всередині корпоративного контуру підприємства-одержувача цей масивний пакет був непридатним для безпосереднього використання. Складській системі потрібні були лише позиції фізичного відвантаження, бухгалтерії — платіжні реквізити та податкові ставки, а відділу закупівель — інформація про дефіцитні залишки.

Саме в цей період комерційні інтеграційні шлюзи (шлюзи EDI-трансляції) вперше реалізували спеціалізований функціональний вузол — *декомпозер повідомлень*. Він парсив вхідний складений конверт `UNB`, перевіряв цілісність структури, розщеплював файл на множину індивідуальних XML- або плоских документів `UNH..UNT`, генерував функціональні підтвердження прийому `CONTRL` / `997 Functional Acknowledgment` і розкладав індивідуальні транзакції по локальних чергах підсистем. З'явилася перша строга потреба зберігати контекст батьківського пакета: кожен виділений документ маркувався номером початкового обміну `UNB-Ref` та порядковим номером у групі.

## Корпоративні шини та формалізація патернів інтеграції (1990–2003 роки)

У 1990-х роках на зміну передачі файлів прийшли системи обміну повідомленнями проміжного шару (англ. *Message-Oriented Middleware*, MOM): IBM MQSeries (пізніше WebSphere MQ), TIBCO Rendezvous, Microsoft MSMQ та стандарт Java Message Service (JMS).

Програмні системи почали переходити до архітектур на основі сервісів (SOA). Повідомлення передавалися через канали «точка-точка» та топіки публікації-підписки. Однак бізнес-процеси за своєю природою залишалися складеними: замовлення клієнта в інтернет-магазині чи заявка на туристичний тур складалися з множини гетерогенних кроків (бронювання квитка на літак, резервування номера в готелі, оренда автомобіля, оформлення страховки).

Якщо монолітний сервіс намагався виконати всі ці операції синхронно в єдиному виклику, загальна надійність системи падала за експоненційним законом: якщо ймовірність успішного виклику кожного з чотирьох зовнішніх партнерів становить 95%, то ймовірність успіху всієї складеної операції дорівнює:

```
0.95 · 0.95 · 0.95 · 0.95
= 0.95⁴               [незалежні події: піднесення до степеня]
≈ 0.8145              [надійність складеної операції: ~81.5%]
```

Майже кожна п'ята складена транзакція зазнавала аварії, блокуючи ресурси й вимагаючи складних механізмів розподілених двохфазних транзакцій (2PC / XA), які створювали колосальні затримки блокування бази даних.

У 2003 році Ґреґор Гоп (англ. *Gregor Hohpe*) та Боббі Вулф (англ. *Bobby Woolf*) опублікували фундаментальну працю *«Enterprise Integration Patterns: Designing, Building, and Deploying Messaging Solutions»*. У цій книзі вперше було проведено строгу каталогізацію та формалізацію архітектурних шаблонів обробки повідомлень. Патерн **Message Splitter** зайняв центральне місце в категорії шаблонів трансформації та маршрутизації (англ. *Message Routing / Transformation*).

Гоп і Вулф визначили канонічні правила роботи спліттера:
* Спліттер приймає одне складене повідомлення, корисне навантаження якого містить повторювані елементи або список різнорідних сутностей.
* Спліттер генерує послідовність окремих атомарних повідомлень, кожне з яких містить рівно одну логічну частину початкового документа.
* Спліттер збагачує кожне вихідне повідомлення спеціальними службовими заголовками кореляції: `Correlation ID` (ідентифікатор початкового складеного повідомлення), `Sequence Number` (номер поточного елемента) та `Sequence Size` (загальна кількість елементів у серії).

Ця тріада заголовків створила математичну основу для симетричного патерну — **Message Aggregator** (агрегатор повідомлень), що дозволило будувати циклічні розподілені конвеєри: складений пакет розбивається спліттером, елементи паралельно обробляються пулом воркерів на різних вузлах кластера, а результати збираються агрегатором в єдину фінальну відповідь.

## Інтеграційні каркаси: від Apache Camel до Spring Integration (2000–2010-ті роки)

З появою відкритого коду та стандартизації Enterprise JavaBeans патерн розділювача отримав готові декларативні реалізації у провідних інтеграційних фреймворках:

* **Apache Camel (2007):** запровадив декларативну мову опису маршрутів (DSL). Вираз `from("direct:bulkOrders").split(xpath("/order/item")).to("activemq:queue:items")` дозволив інженерам розбивати XML-документи за допомогою XPath-виразів або колекції об'єктів Java в один рядок коду. Camel реалізував підтримку паралельного виконання (`parallelProcessing()`), потокової ітерації (`streaming()`) для уникнення завантаження великих файлів у пам'ять, а також вбудовану стратегію агрегації для збору результатів.
* **Spring Integration (2008):** надав анотації `@Splitter` та XML-конфігурацію `<int:splitter>`, стандартизувавши автоматичне розгортання колекцій, масивів та ітераторів у черги Spring Messaging з автоматичною ін'єкцією стандартних заголовків `sequenceNumber` та `sequenceSize`.

У цей період головним викликом лишалася робота з пам'яттю: ранні реалізації часто десеріалізували весь вхідний XML-документ у дерево DOM (англ. *Document Object Model*), що викликало катастрофічні падіння через переповнення пам'яті (англ. *Out Of Memory*, OOM) при спробі обробити файли розміром понад 50–100 МБ. Відповіддю індустрії став перехід до потокових парсерів StAX (англ. *Streaming API for XML*) та Jackson Streaming API для JSON, де спліттер читає вхідний потік токен за токеном і відправляє виділені об'єкти в чергу, утримуючи константний обсяг пам'яті `O(1)`.

## Хмарна ера, журнал подій та реактивні потоки (2015-ті роки — теперішній час)

Поява Apache Kafka, розподілених журналів подій та парадигми Reactive Streams кардинально змінила масштаби розбиття даних:

1. **Трансформація flatMap у потокових процесорах:** У Kafka Streams, Apache Flink та Apache Spark Streaming операція розбиття повідомлень стала базовим оператором `flatMap(record -> Iterable<OutRecord>)`. Потоковий процесор споживає подію з одного топіка Kafka, розгортає її внутрішній масив у множину дискретних подій і записує їх у вихідний партиціонований топік.
2. **Наскрізний протитиск (Reactive Backpressure):** У специфікації Reactive Streams (яку реалізують Project Reactor, RxJava, Akka Streams та Java 9 Flow API) розділювач повідомлень більше не може безконтрольно засипати чергу мільйонами згенерованих об'єктів. Спліттер генерує рівно стільки вихідних елементів, скільки запросив споживач через сигналізацію `request(n)`, запобігаючи переповненню черг та падінню воркерів.
3. **Хмарні обмеження розміру (Message Size Limits):** У сучасних хмарних чергах (AWS SQS — ліміт 256 КБ, Azure Service Bus — 1 МБ, Apache Kafka — за замовчуванням 1 МБ) спліттер став обов'язковим інструментом для технічної фрагментації великих бінарних блоків (зображень, відеофрагментів, масивів телеметрії IoT), дозволяючи передавати гігабайтні масиви через стандартні легковажні брокери без необхідності використання важких зовнішніх сховищ на кшталт Amazon S3.

Еволюція від фіксованих рядків перфокарт до реактивних потоків подій довела: патерн Message Splitter є не просто зручною абстракцією, а фундаментальним законом декомпозиції складності, що забезпечує паралелізм, ізоляцію помилок та еластичність сучасних розподілених систем.
