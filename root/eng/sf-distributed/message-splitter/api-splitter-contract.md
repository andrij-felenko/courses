# 📋 Контракт метаданих, специфікація заголовків і протокол фрагментації розділювача

У розподілених асинхронних архітектурах патерн розділювача повідомлень (*Message Splitter*) виконує роль структурного перетворювача: він трансформує єдине складене або надвелике вхідне повідомлення у послідовність незалежних дискретних повідомлень. Щоб подальші компоненти конвеєра — фільтри, маршрутизатори, пули конкуруючих споживачів та агрегатори — могли коректно маршрутизувати, дедуплікувати та повторно збирати ці частини, розділювач зобов'язаний дотримуватися суворого контракту метаданих.

Нижче наведено формальну нормативну специфікацію заголовків конверта повідомлень, схеми серіалізації (JSON Schema та Protocol Buffers v3), протокол двійкової фрагментації блоків та матрицю переходів скінченного автомата життєвого циклу декомпозиції.

## 1. Специфікація стандартизованих заголовків метаданих

Під час декомпозиції розділювач збагачує кожне вихідне повідомлення набором метаданих. Заголовки розділені на три функціональні категорії: ідентифікація сесії та порядку, технічна фрагментація та контекст розподіленого трасування.

| Ключ заголовка (Canonical Key) | Тип даних | Обов'язковість | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `x-correlation-id` | `String (UUIDv4 / Hex)` | Обов'язковий | Унікальний ідентифікатор батьківського складеного пакета. Спільний для всіх виділених елементів однієї сесії розбиття. |
| `x-parent-message-id` | `String` | Опціональний | Фізичний ідентифікатор вхідного повідомлення в транспортній черзі брокера (наприклад, JMSMessageID або SQS MessageId). |
| `x-sequence-number` | `Integer (uint64)` | Обов'язковий | Порядковий номер елемента в серії. Нумерація починається з `1` і строго монотонно зростає (`1, 2, 3, ...`). |
| `x-sequence-size` | `Integer (uint64)` | Умовно-обов'язковий | Загальна кількість елементів у початковому пакеті. Якщо загальний розмір невідомий під час потокового читання, передається `0`. |
| `x-is-last-element` | `Boolean` | Обов'язковий | Прапорець завершення серії (`true` для фінального елемента, `false` для всіх попередніх). Обов'язковий при потоковому розборі. |
| `x-split-timestamp-utc` | `String (ISO 8601)` | Обов'язковий | Точний час створення дискретного повідомлення розділювачем у форматі `YYYY-MM-DDTHH:mm:ss.sssZ`. |
| `x-chunk-offset-bytes` | `Integer (uint64)` | Специфічний (Chunking) | Байт-зміщення поточного фрагмента відносно початку вихідного бінарного файлу (використовується при нарізці великих блоків). |
| `x-chunk-total-bytes` | `Integer (uint64)` | Специфічний (Chunking) | Загальний розмір вихідного нефрагментованого бінарного навантаження в байтах. |
| `x-chunk-checksum-sha256` | `String (Hex)` | Опціональний | Контрольна сума SHA-256 поточного фрагмента для верифікації цілісності на рівні додатка. |
| `traceparent` | `String (W3C)` | Обов'язковий | Заголовок розподіленого трасування W3C (`version-trace_id-parent_span_id-trace_flags`). |
| `tracestate` | `String` | Опціональний | Стан маршрутизації вендор-специфічного контексту трасування OpenTelemetry. |

### Детальний аналіз семантики та інваріантів заголовків

1. **Кореляційний ідентифікатор (`x-correlation-id`):**
   Слугує первинним ключем групування для симетричного патерну [агрегатора](topic:sf-distributed/message-aggregator). Усі повідомлення, отримані в результаті розбиття одного складеного пакета, зобов'язані мати ідентичне значення `x-correlation-id`. Якщо вхідне повідомлення вже містило власний ідентифікатор кореляції від клієнта, спліттер зберігає його в цьому полі; якщо ж заголовок був відсутній, спліттер самостійно генерує псевдовипадковий UUID версії 4 або 64-бітний монотонний числовий ідентифікатор (Snowflake ID).
2. **Монотонна послідовність (`x-sequence-number`):**
   Порядковий номер елемента є строго позитивним цілим числом (`sequence_number ≥ 1`). Пропуски номерів усередині однієї серії неприпустимі, за винятком випадків, коли пошкоджений елемент було відправлено до мертвої черги (DLQ). Якщо елемент відправляється у DLQ, його номер фіксується у події помилки, дозволяючи агрегатору зафіксувати неповноту сесії.
3. **Розмірність серії (`x-sequence-size`) проти прапорця завершення (`x-is-last-element`):**
   При повній буферизації (коли спліттер знає точну кількість елементів наперед) поле `sequence_size` містить число `N`, а `is_last_element` виставляється в `true` на `N`-му повідомленні. У режимі потокового розбору (Streaming / StAX), коли загальний розмір пакета невідомий аж до моменту зустрічі кінцевого тегу файлу або закриття сокета, спліттер передає `sequence_size: 0` у всіх проміжних повідомленнях, а на останньому елементі встановлює `is_last_element: true` та оновлює `sequence_size` до фінального підрахованого значення.
4. **Контекст розподіленого трасування (W3C Trace Context):**
   Спліттер зобов'язаний виступати коректним вузлом трасування OpenTelemetry. Він витягує батьківський контекст `traceparent`, генерує унікальний новий `Span ID` для кожної виділеної частки та записує оновлений рядок `traceparent` у вихідний конверт. Це дозволяє системі APM (New Relic, Datadog, Jaeger) візуалізувати розгалуження батьківського пакетного запиту на паралельні дочірні спани.

### Відображення заголовків на транспортні протоколи

* **Apache Kafka:** Заголовки передаються в колекції `RecordHeaders` у вигляді пар ключ-значення `byte[]`. Числові значення кодуються в порядку байтів Big-Endian (Network Byte Order).
* **AMQP 1.0 / RabbitMQ:** Заголовки мапляться у секцію `application-properties` або стандартні поля `message-annotations`.
* **AWS SQS / SNS:** Заголовки передаються через словник `MessageAttributes` з типами даних `String` та `Number`.
* **CloudEvents v1.0:** Заголовки записуються як розширення атрибутів (англ. *extension attributes*): `correlationid`, `sequencenumber`, `sequencesize`.

## 2. Схеми даних та контракти (JSON Schema та Protobuf)

### Контракт повідомлення у форматі Protocol Buffers v3

```protobuf
syntax = "proto3";

package messaging.splitter.v1;

// Метадані кореляції та послідовності елементів
message SplitMetadata {
  string correlation_id = 1;
  string parent_message_id = 2;
  uint64 sequence_number = 3;
  uint64 sequence_size = 4;
  bool is_last_element = 5;
  int64 split_timestamp_unix_ms = 6;
  
  // Додаткові параметри для технічної фрагментації (Chunking)
  optional uint64 chunk_offset_bytes = 7;
  optional uint64 chunk_total_bytes = 8;
  optional string chunk_checksum_sha256 = 9;
  
  // W3C Trace Context
  string traceparent = 10;
  string tracestate = 11;
}

// Дискретний конверт повідомлення
message DiscreteMessageEnvelope {
  SplitMetadata metadata = 1;
  string content_type = 2; // наприклад, "application/json", "application/protobuf"
  bytes payload = 3;       // серіалізоване тіло атомарного повідомлення
}

// Подія для мертвої черги (Dead Letter Queue) при частковому збої
message SplitErrorEvent {
  string correlation_id = 1;
  uint64 sequence_number = 2;
  string failure_stage = 3; // "STREAM_PARSING", "CHECKSUM_VALIDATION", "SERIALIZATION"
  string error_code = 4;    // "CORRUPTED_FRAME", "CRC_MISMATCH", "SCHEMA_INVALID"
  string error_message = 5;
  int64 failure_timestamp_unix_ms = 6;
  bytes raw_corrupted_payload = 7;
}

// Керуючий сигнал координації розбиття (Control Plane Signal)
enum SplitControlSignalType {
  SIGNAL_UNSPECIFIED = 0;
  SIGNAL_BATCH_STARTED = 1;
  SIGNAL_BATCH_COMPLETED = 2;
  SIGNAL_BATCH_ABORTED = 3;
}

message SplitControlSignal {
  string correlation_id = 1;
  SplitControlSignalType signal_type = 2;
  uint64 total_emitted_items = 3;
  uint64 total_error_items = 4;
  int64 timestamp_unix_ms = 5;
  string reason = 6;
}
```

## 3. Протокол технічної фрагментації великих бінарних блоків

Коли розмір вхідного артефакту (наприклад, архіву, скану документа або відеозапису) перевищує граничний ліміт брокера повідомлень (наприклад, 256 КБ в AWS SQS або 1 МБ в Kafka), розділювач активує режим технічної фрагментації (*Payload Chunking Protocol*).

### Математичні правила розрахунку параметрів фрагментації

Нехай розмір вихідного бінарного об'єкта становить `S` байтів, а максимальний допустимий розмір корисного навантаження брокера дорівнює `L_max`. Розмір одного чанка `C` розраховується з урахуванням запасу на службові заголовки `H_meta` (зазвичай 4 КБ):

```
C = L_max - H_meta
```

Загальна кількість фрагментів `N` визначається як результат ділення з округленням до більшого цілого:

```
N = ⌈ S / C ⌉
```

Для кожного фрагмента з індексом `k ∈ [1, N]`:
* Зміщення початку чанка відносно старту файлу: `Offset(k) = (k - 1) · C`.
* Фактична довжина даних поточного чанка: `Len(k) = min(C, S - Offset(k))`.
* Прапорець завершення серії: `is_last_element = (k == N)`.

### Порядок відновлення бінарного об'єкта агрегатором

1. При отриманні першого фрагмента сесії (`sequence_number == 1` або будь-якого першого отриманого повідомлення з невідомим раніше `correlation_id`) агрегатор зчитує заголовок `x-chunk-total-bytes` і виділяє в оперативній пам'яті або на швидкому NVMe-накопичувачі суцільний буфер розміром `S` байтів.
2. Кожен отриманий чанк копіюється безпосередньо за адресою `Buffer + chunk_offset_bytes`. Завдяки наявності явного зміщення `chunk_offset_bytes` агрегатор здатний коректно збирати файл навіть за умови невпорядкованої доставки фрагментів мережею (англ. *Out-of-Order Delivery*).
3. Агрегатор веде бітову карту отриманих фрагментів (англ. *Bitset / Bitmap*). Коли всі `N` бітів встановлено в `1`, агрегатор обчислює геш-суму SHA-256 від зібраного буфера і порівнює її із заголовком `x-chunk-checksum-sha256`. У разі збігу бінарний файл вважається успішно реконструйованим і передається споживачам.

## 4. Скінченний автомат життєвого циклу декомпозиції

Розділювач повідомлень функціонує як детермінований скінченний автомат (*Finite State Machine*, FSM). Життєвий цикл сесії розбиття включає вісім станів:

```
                  ┌──────────────────────┐
                  │     INITIALIZED      │
                  └──────────┬───────────┘
                             │ StartParsing
                             ▼
                  ┌──────────────────────┐
            ┌────►│   BUFFERING_STREAM   │◄───┐
            │     └──────────┬───────────┘    │
            │                │ FrameExtracted │ ResumeFromThrottling
            │                ▼                │
            │     ┌──────────────────────┐    │
            │     │   EMITTING_ELEMENTS  ├────┘
            │     └────┬────────────┬────┘
            │          │            │
            │          │ QueueFull  │ ChecksumMismatch
            │          ▼            ▼
            │   ┌─────────────┐   ┌──────────────────────┐
            └───┤ THROTTLED   │   │  PARTIAL_ERROR_DLQ   │
                │(Backpressure│   └──────────┬───────────┘
                └─────────────┘              │ SkipAndContinue
                                             ▼
                                  ┌──────────────────────┐
                                  │   DRAINING_BUFFER    │
                                  └──────────┬───────────┘
                                             │ EndOfStream / Fatal
                             ┌───────────────┴───────────────┐
                             ▼                               ▼
                  ┌──────────────────────┐        ┌──────────────────────┐
                  │      COMPLETED       │        │       ABORTED        │
                  └──────────────────────┘        └──────────────────────┘
```

### Матриця переходів станів автомата

| Початковий стан | Подія / Тригер | Цільовий стан | Виконувана дія | Інваріанти та передумови |
| :--- | :--- | :--- | :--- | :--- |
| `INITIALIZED` | `StartParsing(stream)` | `BUFFERING_STREAM` | Виділення фіксованого буфера 64 КБ, генерація `correlation_id`. | Вхідний дескриптор дійсний. |
| `BUFFERING_STREAM` | `FrameExtracted(raw_bytes)` | `EMITTING_ELEMENTS` | Валідація сигнатури, розрахунок CRC32, пакування метаданих. | У буфері є повний кадр. |
| `BUFFERING_STREAM` | `EndOfStream(EOF)` | `COMPLETED` | Відправка керуючого сигналу `SIGNAL_BATCH_COMPLETED`. | Усі кадри вичитано без помилок. |
| `BUFFERING_STREAM` | `FatalCorruptedStream` | `ABORTED` | Відправка сигналу `SIGNAL_BATCH_ABORTED`, запис у лог аудиту. | Сигнатура пакета пошкоджена. |
| `EMITTING_ELEMENTS`| `ChannelPushOk` | `BUFFERING_STREAM` | Інкремент `sequence_number`, зміщення курсору `offset`. | Черга має вільні слоти. |
| `EMITTING_ELEMENTS`| `QueueHighWatermark` | `THROTTLED` | Блокування читання сокета (`pthread_cond_wait`), старт таймера. | Черга заповнена до High Watermark. |
| `EMITTING_ELEMENTS`| `ChecksumMismatch` | `PARTIAL_ERROR_DLQ` | Формування `SplitErrorEvent`, відправка кадру в DLQ. | Збій CRC32 окремого кадру. |
| `THROTTLED` | `QueueLowWatermark` | `BUFFERING_STREAM` | Розблокування читання (`pthread_cond_signal`), скидання таймера. | Черга розвантажилася до Low Watermark. |
| `PARTIAL_ERROR_DLQ` | `SkipAndContinue` | `BUFFERING_STREAM` | Інкремент лічильника помилок, пропуск збійного діапазону байтів. | Наступний кадр має валідну сигнатуру. |
| `DRAINING_BUFFER` | `BufferEmpty` | `COMPLETED` | Фіксація метрик тривалості, звільнення дескрипторів. | Усі валідні елементи доставлено. |

### Опис інваріантів станів автомата

* **Інваріант стану `BUFFERING_STREAM`:** Обсяг пам'яті, зайнятий буфером, строго обмежений константою `BUFFER_CAPACITY`. Жодна операція виділення пам'яті в купі не виконується всередині цього стану.
* **Інваріант стану `EMITTING_ELEMENTS`:** Порядковий номер `sequence_number` монотонно збільшується на одиницю при кожному успішному переході. Заборонено повторне використання одного й того самого значення `sequence_number` у межах однієї сесії.
* **Інваріант стану `THROTTLED`:** Потік читання гарантовано зупинено на транспортному рівні (жоден системний виклик `recv` не виконується). Стан триває доти, доки черга не спорожніє нижче порогу низької ватерлінії.
* **Інваріант стану `PARTIAL_ERROR_DLQ`:** Пошкоджений елемент не знищується мовчки. Вся доступна інформація (байт-зміщення, початкові байти, код помилки) упаковується в структуру `SplitErrorEvent` та негайно публікується в тему DLQ.

## 5. Контракт ідемпотентності споживача

Оскільки в розподілених мережах розділювач може зазнати збою посеред процесу розбиття (наприклад, після емісії 350-го елемента з 1000) і перезапуститися брокером спочатку, кожен кінцевий споживач зобов'язаний гарантувати ідемпотентність обробки дискретних елементів.

Формула складеного ключа дедуплікації (*Idempotency Key*):

```
IdempotencyKey = "dedup:msg:" + metadata.correlation_id + ":" + metadata.sequence_number
```

### Алгоритм взаємодії споживача зі сховищем стану (Redis / SQL):

```
1. Отримано DiscreteMessageEnvelope msg.
2. key = ConstructKey(msg.metadata.correlation_id, msg.metadata.sequence_number)
3. status = Redis.SET(key, "PROCESSING", NX=true, EX=86400)
4. IF status == NULL (ключ вже існує):
     Log("Дублікат елемента проігноровано", key)
     ACK_BROKER(msg) // Підтверджуємо отримання без повторного виконання бізнес-дії
     RETURN
5. TRY:
     ExecuteBusinessLogic(msg.payload)
     Redis.SET(key, "DONE", XX=true, EX=86400)
     ACK_BROKER(msg)
   CATCH Error e:
     Redis.DEL(key) // Дозволяємо повтор при тимчасовому збої
     NACK_BROKER(msg)
```

Цей контракт гарантує, що навіть при багаторазових збоях мережі та аварійних перезапусках спліттера кінцевий стан бізнес-домену залишиться строго узгодженим без дублювання записів чи транзакцій.

## 6. Безпека, автентифікація та цілісність даних

При передачі розділених повідомлень через відкриті або ненадійні канали зв'язку контракт метаданих передбачає підтримку криптографічного захисту цілісності:

1. **Криптографічний підпис конверта (HMAC-SHA256):**
   У фінансових та чутливих корпоративних контурах розділювач обчислює криптографічний код автентифікації повідомлення HMAC від конкатенації службових полів та корисного навантаження:
   ```
   HMAC_Signature = HMAC_SHA256(SecretKey, correlation_id || sequence_number || payload)
   ```
   Підпис записується в заголовок `x-signature-hmac-sha256`. Споживач верифікує цей підпис перед виконанням бізнес-логіки, що унеможливлює підміну елементів або ін'єкцію фальшивих транзакцій зловмисником у проміжній черзі.
2. **Захист від атак повторного відтворення (Replay Attack Prevention):**
   Завдяки комбінації заголовків `x-split-timestamp-utc` та `x-correlation-id` споживач відхиляє будь-які повідомлення, часова мітка яких відрізняється від поточного системного часу більш ніж на допустиме вікно дрейфу годинника (зазвичай 5 хвилин), або чий `correlation_id` належить уже закритій та підтвердженій сесії клірингу.
3. **Обмеження розміру корисного навантаження (Payload Size Enforcement):**
   Контракт вимагає від розділювача суворо перевіряти поле `payload_len`. Якщо заголовок вказує розмір елемента, що перевищує максимально допустимий ліміт безпеки (наприклад, понад 10 МБ для одного елемента), такий кадр негайно блокується як потенційна атака на вичерпання пам'яті (Memory Exhaustion DoS).

## 7. Програмний інтерфейс (SDK API Signatures)

Для інтеграції розділювача в мови програмування високого рівня контракт визначає єдиний набір сигнатур функцій зворотного виклику та обробників подій:

```cpp
// Контракт C++ SDK для інтеграції користувацьких обробників
class ISplitterEventHandler {
public:
    virtual ~ISplitterEventHandler() = default;
    
    // Викликається перед початком розбиття пакета
    virtual void on_batch_start(const std::string& correlation_id, uint64_t total_items) = 0;
    
    // Викликається для кожного успішно виділеного елемента
    virtual void on_item_emitted(const DiscreteMessageEnvelope& envelope) = 0;
    
    // Викликається при виявленні пошкодженого кадру
    virtual void on_item_error(const SplitErrorEvent& error_event) = 0;
    
    // Викликається після успішної емісії всіх елементів пакета
    virtual void on_batch_complete(const std::string& correlation_id, uint64_t emitted_count) = 0;
    
    // Викликається при виникненні фатального збою структури потоку
    virtual void on_batch_abort(const std::string& correlation_id, std::string_view reason) = 0;
};
```

## 8. Політики повторних спроб, тайм-аутів та ізоляції у Dead Letter Queue

Контракт взаємодії спліттера з транспортним брокером та мертвою чергою визначає суворі часові правила та алгоритми обробки збоїв:

### 1. Стратегія обробки транзиторних збоїв мережі брокера (Transient Broker Failures)

Якщо черга брокера повертає помилку переповнення буфера або тимчасової недоступності вузла кластера (`BrokerUnavailableException`), спліттер не скидає обробку пакета, а застосовує алгоритм експоненційного відступу з додаванням випадкового шуму (Exponential Backoff with Full Jitter):

```
WaitTime = min(MaxBackoff, BaseInterval · 2^(attempt)) · random(0.5, 1.5)
```

Де:
* `BaseInterval = 50 ms` — базова затримка першої повторної спроби.
* `MaxBackoff = 2000 ms` — максимальна стеля затримки повтору.
* `MaxRetries = 5` — гранична кількість спроб публікації конкретного дискретного повідомлення.

Якщо після п'яти спроб брокер не приймає повідомлення, сесія розбиття переходить у стан `ABORTED`, фіксуючи критичний інцидент інфраструктури.

### 2. Критерії маршрутизації до Dead Letter Queue (DLQ Routing Policy)

Елемент безумовно перенаправляється в тему `DLQ` без зупинки основного конвеєра у наступних випадках:
* **Незбіг контрольної суми CRC32:** Тіло повідомлення спотворено при передачі.
* **Порушення схеми серіалізації:** Корисне навантаження елемента не відповідає зареєстрованій схемі в [Schema Registry](topic:com-protocol/schema-registry) (наприклад, відсутні обов'язкові бізнес-поля `account_id` або `currency`).
* **Логічна помилка бізнес-валідації:** Значення полів порушують доменні інваріанти (наприклад, від'ємна ціна або некоректна дата транзакції).

Кожне повідомлення в DLQ містить заголовок `x-dlq-original-offset`, що дозволяє адміністраторам локалізувати точне положення збійного запису у вихідному файлі.

## 9. Управління станом сесії та транзакційні чекпоінти

Для великомасштабних пакетів (понад 1 000 000 елементів) розбиття може тривати хвилини. Якщо в цей період сервер спліттера перезавантажується, повний повторний прогін створює надмірне навантаження. Для оптимізації застосовується протокол транзакційного чекпоінтування:

1. **Періодичний запис контрольної точки:** Через кожні 5 000 успішно емітованих елементів спліттер записує у розподілене сховище (PostgreSQL / DynamoDB / Redis) структуру стану:
   ```
   Checkpoint {
     correlation_id: "batch-8941",
     last_committed_seq: 35000,
     stream_byte_offset: 45219800,
     state: "IN_PROGRESS"
   }
   ```
2. **Відновлення після збою (Resume From Checkpoint):** Після перезапуску процесу спліттер перевіряє наявність активного чекпоінта для даного `correlation_id`. Якщо чекпоінт існує, спліттер зміщує покажчик вхідного файлу за допомогою `fseek()` / `lseek()` безпосередньо на `stream_byte_offset`, встановлює початковий номер чергового елемента `sequence_number = last_committed_seq + 1` і продовжує потоковий розбір без дублювання перших 35 000 повідомлень.
3. **Очищення дедуплікаційного кешу:** Записи ключів ідемпотентності у сховищі споживача мають встановлений час життя (Time-To-Live, TTL), який за замовчуванням становить 7 діб (`604 800 секунд`). Цього часу достатньо для завершення всіх розподілених саг, проведення звірок та ручного розбору інцидентів у мертвої черзі.

## 10. Контракт потокового керування (Reactive Streams Specification)

При інтеграції розділювача в середовища JVM (Project Reactor, Akka Streams, RxJava) або C++ (Rsocket, libunifex) взаємодія між спліттером та споживачами підпорядковується стандарту **Reactive Streams**:

* **Модель за запитом (Pull-based Demand):** Розділювач реалізує інтерфейс `Publisher<DiscreteMessageEnvelope>`. Споживач підписується через інтерфейс `Subscriber` та надсилає явний запит на отримання `n` повідомлень (`Subscription.request(n)`).
* **Суворий інваріант емісії:** Спліттер не має права викликати метод `onNext(msg)` більше ніж `n` разів без отримання нового сигналу `request(m)`. Якщо лічильник доступного попиту (*Demand Counter*) стає рівним нулю, спліттер негайно призупиняє десеріалізацію вхідного джерела.
* **Каскадне завершення сесії:** При успішному прочитанні останнього елемента спліттер спочатку відправляє фінальне повідомлення через `onNext()`, після чого викликає термінальний метод `onComplete()`. Якщо під час розбору сталася невідновна помилка структури файлу, викликається метод `onError(throwable)`.

## 11. Правила еволюції схем та зворотна сумісність

У міру розвитку корпоративних систем формат заголовків та тіла повідомлень може змінюватися. Контракт визначає три обов'язкові правила еволюції схем:

1. **Зворотна сумісність метаданих (Backward Compatibility):** Додавання нових заголовків (наприклад, прапорця географічного регіону `x-geo-region` або мітки пріоритету `x-priority-level`) не повинно ламати існуючих споживачів. Усі нові поля зобов'язані бути опціональними. Споживач зобов'язаний ігнорувати будь-які невідомі йому службові заголовки.
2. **Заборона зміни семантики існуючих полів:** Зміна формату `x-correlation-id` (наприклад, перехід від UUIDv4 до довільного рядка) або зміна бази відліку `x-sequence-number` (наприклад, нумерація з 0 замість 1) вважається неприпустимою мажорною несумісною зміною, яка вимагає реєстрації нового типу повідомлення або зміни суфіксу версії пакета Protobuf (`messaging.splitter.v2`).
3. **Відокремлення службового конверта від бізнес-даних:** Корисне навантаження (`payload`) передається як непрозорий масив байтів (`bytes`). Це дозволяє використовувати незалежні схеми валідації [Schema Registry](topic:com-protocol/schema-registry) для бізнес-даних (Avro / Protobuf) без потреби оновлення коду самого розділювача повідомлень.

Цей контракт гарантує абсолютну взаємозамінність компонентів: будь-який сервіс-споживач або агрегатор, розроблений за цією специфікацією, може безшовно взаємодіяти з довільною реалізацією розділювача незалежно від мови програмування чи використовуваного брокера повідомлень.
