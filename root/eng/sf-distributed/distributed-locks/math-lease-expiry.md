# 🧮 Безпечне вікно лізи та межі розбіжності годинників

Коли сервер видає клієнту розподілений замок у формі лізи (оренди на строк `L`), обидві сторони намагаються самостійно відраховувати час її закінчення. Оскільки у розподіленій системі немає єдиного фізичного годинника, а передача повідомлень мережею займає ненульовий і непередбачуваний час, клієнт не може вважати замок дійсним протягом усіх `L` секунд від моменту отримання відповіді. Математичний розрахунок часових меж лізи визначає, який саме проміжок часу клієнт може безпечно використовувати для виконання критичної секції, яка ймовірність передчасного випаровування оренди через мережеві втрати, і чому в асинхронній моделі часові гарантії неминуче поступаються детермінованій огорожі.

## Модель часу, затримок та дрейфу

Позначимо абсолютний фізичний час як `t` (умовний ідеальний еталонний час у секундах). Кожен вузол розподіленої системи має власний апаратний генератор тактових імпульсів (кварцовий резонатор) і системний лічильник часу операційної системи.

Швидкість ходу локального годинника вузла відрізняється від ідеального фізичного часу через температурний дрейф кристала, старіння напівпровідників та мікроколивання напруги живлення. Максимальну швидкість дрейфу позначають безрозмірною константою `ρ` (зазвичай вимірюється в мільйонних частках — англ. *parts per million*, ppm, де 1 ppm = `10⁻⁶`). Типовий несинхронізований кварцовий резонатор у серверній стійці має дрейф у діапазоні від 10 до 100 ppm (від 0.86 до 8.6 секунди на добу).

Для будь-якого інтервалу реального часу `Δt` показники локального монотонного годинника `C(t)` змінюються у межах:

```
Δt·(1 − ρ) ≤ ΔC ≤ Δt·(1 + ρ)
```

Введемо параметри мережевої взаємодії, виконання та синхронізації:
- `L` — початкова тривалість лізи, узгоджена протоколом (наприклад, 10.0 с за годинником сервера).
- `d_req` — час доставки запиту на захоплення замка від клієнта до сервера (`d_min ≤ d_req ≤ d_max`).
- `d_resp` — час доставки відповіді про надання замка від сервера до клієнта (`d_min ≤ d_resp ≤ d_max`).
- `RTT = d_req + d_resp` — повний час кругового обігу повідомлення (англ. *Round-Trip Time*).
- `Δ_pause` — непередбачувана пауза процесу клієнта (зупинка потоку збирачем сміття, переривання гіпервізором чи затримка сторінкового обміну пам'яті).
- `W_safe` — безпечне вікно виконання (тривалість за локальним таймером клієнта, протягом якої клієнт гарантовано має ексклюзивний доступ).

## Виведення безпечного вікна клієнта `W_safe`

Розглянемо послідовність подій у реальному фізичному часі `t`:

1. Сервер у момент реального часу `t_grant` фіксує надання лізи на тривалість `L` за своїм локальним годинником `C_s`.
2. За годинником сервера ліза діє до значення `C_s(t_grant) + L`. У найгіршому для клієнта випадку годинник сервера йде з максимально можливою швидкістю `(1 + ρ)`. Тоді реальний фізичний момент закінчення лізи на сервері `t_expire` дорівнює:

```
t_expire
= t_grant + L / (1 + ρ)                    [визначення максимальної швидкості ходу годинника сервера]
```

3. Відповідь про надання лізи доходить до клієнта через час `d_resp`. Клієнт дізнається про отримання замка у реальний момент часу:

```
t_recv
= t_grant + d_resp                         [затримка доставки пакета відповіді клієнту]
```

4. Фізичний запас часу, що залишився у лізи на момент її отримання клієнтом, становить різницю `t_expire − t_recv`:

```
Δt_remain
= t_expire − t_recv                        [реальний залишок часу дії лізи на сервері]
= (t_grant + L / (1 + ρ)) − (t_grant + d_resp) [підстановка формул t_expire та t_recv]
= L / (1 + ρ) − d_resp                     [скорочення спільного початкового моменту t_grant]
```

5. Клієнт не знає точного значення `d_resp` у момент прийому, але він знає повний час `RTT`, який минув від відправлення запиту до отримання відповіді. Оскільки `d_resp ≤ RTT − d_min`, у найгіршому випадку затримка відповіді може сягати `RTT − d_min`. Якщо ж мінімальна затримка невідома (або `d_min ≈ 0`), найгірша затримка обмежується повним `RTT`.

6. Під час виконання критичної секції локальний годинник клієнта `C_c` може відставати від фізичного часу, тобто йти з мінімальною швидкістю `(1 − ρ)`. Отже, щоб фізичний час не перевищив `Δt_remain`, тривалість інтервалу за таймером клієнта `W_safe` повинна задовольняти умову:

```
W_safe / (1 − ρ) ≤ Δt_remain               [переведення фізичного часу в інтервал годинника клієнта]
```

7. Об'єднаємо формули для обчислення максимального безпечного вікна клієнта:

```
W_safe
= (1 − ρ) · Δt_remain                      [множення на швидкість ходу клієнтського таймера]
= (1 − ρ) · (L / (1 + ρ) − d_resp)         [підстановка виразу для Δt_remain]
= L · (1 − ρ) / (1 + ρ) − d_resp · (1 − ρ) [розкриття дужок]
```

Оскільки дрейф `ρ ≪ 1`, дріб `(1 − ρ) / (1 + ρ)` розкладається в ряд Тейлора:

```
(1 − ρ) / (1 + ρ)
= (1 − ρ) · (1 − ρ + ρ² − …)               [розклад геометричної прогресії 1/(1+ρ)]
≈ 1 − 2·ρ                                  [нехтування членами порядку ρ²]
```

Враховуючи, що `d_resp · (1 − ρ) ≈ d_resp`, отримуємо робоче інженерне рівняння для безпечного вікна клієнта:

```
W_safe ≈ L·(1 − 2·ρ) − d_resp
```

Якщо в процесі роботи клієнт додатково зазнає внутрішньої паузи `Δ_pause`, корисний час, що залишається на виконання самої операції запису `W_work`, зменшується на тривалість цієї паузи:

```
W_work = W_safe − Δ_pause = L·(1 − 2·ρ) − d_resp − Δ_pause
```

## Вплив механізмів підлаштування часу: стрибок проти дисципліни частоти

Важливим чинником є поведінка системного демона синхронізації часу (NTP або PTP). Існують два принципово різні способи коригування локального часу:

1. **Стрибкове підлаштування (Step adjustment)**: годинник миттєво переводиться на значення `C_new = C_old + Δt_step`. Якщо годинник переводиться вперед на величину `Δt_step > W_safe`, замок для локального коду спливає миттєво. Якщо ж клієнт використовує системний настінний час (`CLOCK_REALTIME`), а годинник стрибає назад, клієнт може помилково вважати замок дійсним набагато довше за реальний строк лізи на сервері.
2. **Дисципліна частоти (Slew adjustment)**: демон NTP плавно змінює частоту таймера через системний виклик `adjtime()` або `ntp_adjtime()`. Стандартний ліміт підлаштування частоти в ядрі Linux становить `s_max = 500` ppm (`0.05 %`).

При плавному підлаштуванні ефективний дрейф годинника `ρ_eff` обмежений сумою апаратного дрейфу та максимальної корекції NTP:

```
ρ_eff ≤ ρ_hardware + s_max = 100·10⁻⁶ + 500·10⁻⁶ = 600·10⁻⁶ (0.06 %)
```

Це демонструє, що при використанні монотонного годинника (`CLOCK_MONOTONIC_RAW` або `CLOCK_MONOTONIC`) дрейф годинника забирає лише частки відсотка тривалості лізи. Основну загрозу несуть мережеві затримки та паузи самого процесу.

## Розрахунок реальних сценаріїв

Проаналізуємо поведінку розподіленої системи з параметрами: строк лізи `L = 10.0` с, похибка годинника `ρ_eff = 600` ppm (`0.0006`), мережевий час `RTT = 100` мс (з них `d_resp = 50` мс).

### Сценарій 1: Штатний режим без аномальних пауз

```
L_drift_loss  = L · 2 · ρ_eff              [втрата часу через розбіжність двох годинників]
              = 10.0 · 2 · 0.0006          = 0.012 с (12 мс)

d_resp_loss   = 0.050 с                    [втрата часу на доставку повідомлення]

W_safe        = 10.0 − 0.012 − 0.050       = 9.938 с

Δ_pause       = 0 с                        [процес виконується безперервно]
W_work        = 9.938 − 0                  = 9.938 с
```

У штатному режимі безпечне вікно становить понад 99.3 % від початкового строку лізи. Клієнт має достатній запас часу для виконання операції.

### Сценарій 2: Мережевий джитер і перевантаження комутатора

Припустимо, що запит і відповідь застрягли в буфері комутатора під час сплеску трафіку, і затримка доставки `d_resp` зросла до 1.500 с:

```
W_safe        = 10.0 − 0.012 − 1.500       = 8.488 с
```

Безпечне вікно скоротилося до 8.49 с. Якщо клієнт відраховує строк роботи від моменту відправлення свого запиту `t_send`, він автоматично враховує повний `RTT` і зберігає безпеку.

### Сценарій 3: Глибока пауза збирача сміття (GC Pause)

Припустимо, що після отримання відповіді клієнт розпочав обробку, але віртуальна машина потрапила в паузу збирання сміття тривалістю `Δ_pause = 12.0` с (що нерідко трапляється у високонавантажених сервісах із десятками гігабайтів пам'яті):

```
W_safe        = 9.938 с                    [розраховане безпечне вікно]
W_work        = W_safe − Δ_pause           [залишок корисного часу після паузи]
              = 9.938 − 12.0               = −2.062 с
```

Корисний час став **від'ємним**: `W_work < 0`.

Це означає, що коли потік клієнта нарешті відновив роботу, ліза на сервері вже спливла 2 секунди тому. Сервер замків мав повне право передати замок іншому клієнту. Якщо перший клієнт зараз спробує виконати запис у спільне сховище, покладаючись лише на свій локальний таймер, станеться незворотне пошкодження даних.

## Ймовірнісна модель надійності фонового оновлення

Щоб утримувати замок безперервно для тривалих завдань, клієнт запускає фоновий потік — сторожовий таймер (англ. *watchdog*), який періодично надсилає запит на подовження лізи.

Нехай `T_renew` — період між спробами подовження. Якщо запит на подовження втрачається мережею з імовірністю `p_loss`, а втрати пакетів є незалежними подіями, то замок буде втрачено лише тоді, коли всі `k` спроб подовження поспіль зазнають невдачі до моменту вичерпання строку `W_safe`.

Кількість спроб `k`, які клієнт встигає здійснити у межах безпечного вікна:

```
k = floor((W_safe − RTT_max) / T_renew)
```

Імовірність помилкової втрати лізи живим клієнтом протягом одного циклу оновлення:

```
P_loss_cycle = (p_loss)^k
```

Кількість циклів оновлення за добу (24 години = 86400 с):

```
N_cycles_day = 86400 / T_renew
```

Середній час між помилковими втратами замка (англ. *Mean Time Between Failures*, MTBF) у днях:

```
MTBF_days = 1 / (N_cycles_day · P_loss_cycle) = T_renew / (86400 · (p_loss)^k)
```

### Порівняння конфігурацій оновлення лізи

Розрахуємо надійність утримання замка для лізи тривалістю `L = 15.0` с при безпечному вікні `W_safe = 14.0` с, максимальному `RTT_max = 0.5` с та ймовірності втрати окремого пакета `p_loss = 0.01` (1 % втрат у завантаженій мережі):

```
Конфігурація A: T_renew = 7.0 с (k = floor((14.0 − 0.5) / 7.0) = 1 спроба)
  P_loss_cycle = 0.01¹ = 0.01 (1 %)
  N_cycles_day = 86400 / 7.0 ≈ 12342 циклів
  Очікуваних втрат за добу = 12342 · 0.01 ≈ 123.4
  MTBF = 7.0 / (86400 · 0.01) ≈ 0.008 доби (близько 11 хвилин!)

Конфігурація B: T_renew = 5.0 с (L / 3, k = floor((14.0 − 0.5) / 5.0) = 2 спроби)
  P_loss_cycle = 0.01² = 10⁻⁴ (0.01 %)
  N_cycles_day = 86400 / 5.0 = 17280 циклів
  Очікуваних втрат за добу = 17280 · 10⁻⁴ ≈ 1.73
  MTBF = 5.0 / (86400 · 10⁻⁴) ≈ 0.58 доби (близько 14 годин)

Конфігурація C: T_renew = 3.0 с (L / 5, k = floor((14.0 − 0.5) / 3.0) = 4 спроби)
  P_loss_cycle = 0.01⁴ = 10⁻⁸
  N_cycles_day = 86400 / 3.0 = 28800 циклів
  Очікуваних втрат за добу = 28800 · 10⁻⁸ = 2.88·10⁻⁴
  MTBF = 3.0 / (86400 · 10⁻⁸) ≈ 3472 доби (понад 9.5 років!)
```

Розрахунок наочно показує, чому вибір періоду оновлення `T_renew ≤ L / 3` (а найкраще `L / 4` або `L / 5`) є критичним: перехід від 1 до 4 спроб перетворює нестійку систему, яка падає щогодини, на промисловий сервіс із роками безперебійної роботи.

## Динамічний розкид (Jitter) та запобігання синхронізації запитів

Коли кластер із `N` робочих вузлів одночасно стартує або переживає перезапуск координатора, усі клієнти одночасно захоплюють свої лізи у момент часу `t = 0`. Якщо кожен сторожовий таймер оновлює лізу строго через фіксований інтервал `T_renew`, координатор стикається з явищем резонансної хвилі: кожні `T_renew` секунд на нього обрушується піковий сплеск із `N` одночасних запитів.

Якщо координатор здатний обробити не більше `C_max` запитів за секунду, а тривалість обробки сплеску перевищує ліміт очікування клієнтів, частина запитів зазнає таймауту, що провокує каскадну втрату ліз.

Щоб розмити пікове навантаження, період оновлення рандомізують за допомогою випадкового відхилення (джитера):

```
T_actual = T_renew · (1 + Uniform(−J, +J))
```

де `J` — коефіцієнт розкиду (зазвичай `J = 0.20`, тобто `±20 %`).

При рівномірному розподілі на інтервалі `[T_renew·(1 − J), T_renew·(1 + J)]` пікова інтенсивність надходження запитів `λ_peak` зменшується від імпульсу `N / Δt_burst` до рівномірної щільності:

```
λ_avg = N / (2 · J · T_renew)
```

Для кластера з `N = 1000` замків при `T_renew = 5.0` с та розкиді `J = 0.20`:

```
Ширина вікна розкиду = 2 · 0.20 · 5.0 = 2.0 с
Середнє навантаження = 1000 / 2.0     = 500 запитів / с
```

Без рандомізації 1000 запитів приходили б у вузькому вікні 50 мс, створюючи миттєве навантаження 20 000 запитів/с, що призвело б до переповнення черги сокетів та штучних таймаутів.

## Асинхронна реплікація та ризик втрати замка під час аварії

Якщо замок зберігається у первинно-вторинній системі з асинхронною реплікацією (наприклад, Redis Sentinel або типова реплікація БД), виникає ймовірність розщеплення стану під час аварійного перемикання (англ. *failover*).

Нехай `λ_crash` — інтенсивність аварій основного вузла (подій за секунду, пуассонівський потік), а `t_lag` — лаг реплікації (час між записом на основному вузлі та фіксацією на репліці).

Імовірність того, що основний вузол впаде саме в інтервалі між наданням замка та його реплікацією:

```
P_split = 1 − e^(−λ_crash · t_lag) ≈ λ_crash · t_lag
```

Якщо для датацентра з 1000 серверів середній час напрацювання на відмову одного сервера становить 3 роки (`MTBF_server ≈ 9.46·10⁷` с, `λ_crash ≈ 1.05·10⁻⁸` 1/с), а реплікаційний лаг через завантаження мережі складає `t_lag = 100` мс (`0.1` с):

```
P_split на одну операцію захоплення = 1.05·10⁻⁸ · 0.1 = 1.05·10⁻⁹
```

Якщо в системі здійснюється `M = 10 000` захоплень замків на секунду (понад 860 мільйонів на добу), очікувана кількість конфліктів подвійного захоплення становить:

```
N_conflicts_year = (10000 · 86400 · 365) · 1.05·10⁻⁹ ≈ 0.33 конфлікту на рік
```

Це доводить, чому для фінансових транзакцій та критичних баз даних асинхронні сховища замків є неприйнятними: третина аварійних конфліктів на рік за масштабу означає гарантоване пошкодження реальних грошей або балансів. Для систем із нульовою толерантністю до помилок координатор зобов'язаний використовувати синхронний кворум консенсусу (Raft або Paxos), де час реплікації входить у синхронний шлях підтвердження операції.

## Хвостовий розподіл затримок і теорема неможливості

У реальних датацентрах розподіл затримок мережі `d_resp` та пауз процесів `Δ_pause` не є нормальним (гаусовим). Він має **важкі хвости** (англ. *heavy-tailed distribution*, типово описується розподілом Парето або логнормальним розподілом).

Імовірність того, що тривалість випадкової паузи перевищить значення `x`, спадає повільно (поліноміально):

```
P(Δ_pause > x) ~ x^(−α),  де 1 < α < 2
```

Через це для будь-якої скінченної тривалості лізи `L` інтегральний ризик виходу за межі безпечного вікна залишається строго більшим за нуль:

```
P(W_work < 0) = P(Δ_pause + d_resp > L·(1 − 2·ρ)) > 0
```

Спроба зробити лізу «дуже великою» (наприклад, `L = 300` с) знижує ймовірність збою, але різко збільшує час відновлення системи після справжньої аварії вузла: новий клієнт не зможе отримати замок протягом усіх 5 хвилин, поки триває стара ліза мертвого процесу.

## Інженерний чекліст розрахунку параметрів лізи

При проектуванні розподіленого блокування вибір числових параметрів спирається на компроміс між швидкістю відновлення після аварії та надійністю утримання замка:

1. **Цільовий час виявлення аварії (`T_failover`)**: визначає верхню межу тривалості лізи `L ≤ T_failover`. Якщо бізнес вимагає, щоб новий лідер піднявся не пізніше ніж через 15 секунд після смерті старого, обирають `L = 15.0` с.
2. **Період оновлення сторожем (`T_renew`)**: обирають як `L / 4` (для `L = 15.0` с це `3.75` с). Це дає 3 повноцінні повторні спроби до вичерпання строку.
3. **Таймаут одного запиту оновлення (`T_timeout`)**: обирають як `(L − W_min) / k` або `1.0` с. Якщо відповідь не надійшла за цей час, клієнт не чекає TCP-таймауту сокета (який може тривати десятки секунд), а негайно скасовує спробу й відкриває нове з'єднання.
4. **Поріг екстреного скасування (`Abort Threshold`)**: якщо до кінця безпечного вікна `W_safe` залишається менше ніж `RTT_max + Δ_grace` (наприклад, 1.0 с), клієнт зобов'язаний виставити прапорець скасування (англ. *cancellation token*) для робочого потоку та перервати виконання критичної секції ще до того, як ліза офіційно спливе на сервері.

## Чому математика часу вимагає монотонної огорожі

Неможливість гарантувати `P(W_work < 0) = 0` виключно за допомогою таймерів доводить фундаментальне правило проектування розподілених систем:

> **Часові лізи призначені для відновлення живості (Liveness), а не для забезпечення безпеки (Safety).**

- **Живість** забезпечується лізою: якщо клієнт помер, ресурс гарантовано звільниться через час `L`, запобігаючи вічному дедлоку.
- **Безпека** забезпечується огорожею (англ. *fencing*): кожна видача замка супроводжується монотонно зростаючим цілим числом — токеном огорожі `token_{n+1} > token_n`.

Спільне сховище відкидає будь-який запит із токеном `token_req`, якщо воно вже бачило більший токен:

```
token_req ≥ highest_seen_token
```

Ця алгебраїчна нерівність оперує дискретним монотонним порядком цілих чисел і повністю усуває залежність безпеки даних від фізичного часу, мережевого джитера та пауз збирача сміття.
