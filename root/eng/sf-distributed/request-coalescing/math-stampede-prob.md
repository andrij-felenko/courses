# 🧮 Кількісна оцінка шторму запитів: імовірність промаху та алгоритм XFetch

Під час проектування розподілених сховищ та кешувальних шарів виникає потреба кількісно розрахувати ризик відмови та оцінити динаміку навантаження на систему в момент вичерпання терміну дії гарячих ключів. На відміну від рівномірного фонового навантаження, збій під час промаху кешу розгортається за мілісекунди і має вибуховий нелінійний характер.

Розглянемо формальну математичну модель навантаження на систему кешування під час вичерпання часу життя ключа. Клієнтські запити на отримання ресурсу за ключем `K` надходять у систему як стаціонарний найпростіший пуассонівський потік з інтенсивністю `λ` (кількість клієнтських запитів за одну секунду).

Тривалість виконання важкого обчислення, генерації аналітичного звіту або SQL-запиту до вихідної реляційної бази даних є випадковою величиною `T` із математичним сподіванням `E[T] = δ` (де `δ` — середній час відповіді бекенду, виміряний у секундах, наприклад `δ = 0.05` с) та скінченною дисперсією `Var(T) = σ²`.

## Вікно вразливості та математичне сподівання дублікатів

Нехай ключ у кеші має фіксований детермінований час життя `TTL`. У момент часу `t_exp` термін придатності запису в оперативній пам'яті вичерпується, і кеш інвалідує або видаляє об'єкт. Перший клієнтський запит `R₁`, який надходить у систему в момент `t₁ ≥ t_exp`, фіксує промах кешу (англ. *cache miss*) та ініціює обчислення на бекенді, яке триватиме протягом випадкового часу `T`.

Проміжок часу `[t₁, t₁ + T]` утворює **вікно вразливості** (англ. *vulnerability window*). Оскільки кеш у цей період лишається порожнім, кожен новий клієнтський запит, що потрапляє у цей часовий інтервал, також фіксує промах кешу і самостійно вирушає до бази даних.

Кількість запитів `N`, що надходять у розподілену систему за випадковий часовий інтервал тривалістю `T`, підпорядковується розподілу Пуассона з параметром `λ · T`:

```
P(N = k | T) = ((λ·T)ᵏ ÷ k!) · e⁻⁽λ·ᵀ⁾
```

Застосовуючи закон повного математичного сподівання та теорему про повну дисперсію для складеного пуассонівського процесу, обчислюємо очікувану кількість дублюючих запитів `E[N]` та їхню дисперсію `Var(N)`, які одночасно надійдуть до бази даних без використання механізмів об'єднання:

```
E[N] = E[ E[N | T] ] = E[ λ · T ] = λ · E[T] = λ · δ
Var(N) = E[ Var(N | T) ] + Var( E[N | T] ) = λ · δ + λ² · σ²
```

### Практичний розрахунок для реального навантаження

Розглянемо високонавантажений мікросервіс електронної комерції. Нехай інтенсивність потоку звернень до популярної картки товару під час акції становить `λ = 800` запитів/с, а тривалість виконання важкого SQL-запиту з агрегацією залишків становить `δ = 60` мс (`0.06` с) зі стандартним відхиленням `σ = 0.01` с:

```
E[N]
= λ · δ                               [теорема про середню кількість подій]
= 800 · 0.06                          [підстановка інтенсивності потоку 800 req/s та затримки 0.06 s]
= 48 запитів                          [очікувана кількість дублюючих викликів]
```

Обчислимо точну ймовірність того, що база даних отримає удар щонайменше з 30 одночасних важких операцій під час єдиного промаху одного ключа:

```
P(N ≥ 30) = 1 − ∑ₖ₌₀²⁹ (((48)ᵏ ÷ k!) · e⁻⁴⁸) ≈ 0.9972  (99.72%)
```

З імовірністю понад 99.7% база даних миттєво отримує 48 важких паралельних з'єднань. Якщо пул з'єднань пулу баз даних обмежений розміром 50 з'єднань, один єдиний промах кешу для одного популярного ключа монополізує `96%` усієї пропускної здатності бази, повністю паралізуючи обробку платежів та авторизацію користувачів.

За законом Літтла (англ. *Little's Law*), середня кількість паралельних запитів у черзі бази даних `L` дорівнює добутку інтенсивності вхідного потоку на середній час перебування запиту в системі `W`. Коли база даних перевантажується дублікатами, час обробки `W` зростає через дискову конкуренцію від `60` мс до `3000` мс, що спричиняє вибухове зростання довжини черги `L = 800 · 3 = 2400` запитів, переповнюючи пам'ять сервера.

## Зіставлення Single-Flight та імовірнісного оновлення XFetch

Для ліквідації навалу запитів у розподілених архітектурах застосовують два принципово різні підходи: детерміноване блокування в польоті (**Single-Flight**) та імовірнісне завчасне фонове оновлення (**XFetch**).

Алгоритм **XFetch** (запропонований дослідниками В. Л. Леонгом та співавторами у праці для VLDB 2015) перевіряє необхідність оновлення запису в кеші ще **до** моменту настання `t_exp`. Під час кожного клієнтського читання застосунок оцінює залишок часу життя ключа `Δ = t_exp − t_now`.

Клієнт ініціює асинхронне фонове оновлення запису в кеші, якщо випадкова величина перевершує залишок часу життя:

```
−β · δ · ln(U) > Δ
```

де:
- `Δ` — залишок часу життя ключа в секундах (`t_exp − t_now`);
- `δ` — час виконання обчислення значення (виміряний бекендом під час попереднього запису в кеш);
- `β` — коефіцієнт агресивності оновлення (`β > 0`, за замовчуванням `β = 1.0`);
- `U` — випадкова величина, рівномірно розподілена на неперервному інтервалі `(0, 1]`.

Оскільки для `U ∈ (0, 1]` натуральний логарифм `ln(U) ∈ (−∞, 0]`, величина `−β · δ · ln(U)` є строго додатною випадковою величиною, яка підпорядковується показниковому (експоненційному) розподілу з параметром масштабу `θ = β · δ`.

### Виведення ймовірності раннього фонового оновлення

Знайдемо ймовірність того, що довільний клієнтський запит, який надійшов за `Δ` секунд до закінчення TTL, ініціює фонове оновлення даних:

```
P(оновлення | Δ)
= P(−β · δ · ln(U) > Δ)               [підстановка умови спрацьовування XFetch]
= P(ln(U) < −Δ ÷ (β · δ))             [ділення на від'ємний множник зі зміною знака нерівності]
= P(U < e⁻Δ/⁽β·δ⁾)                    [потенціювання експонентою за основою e]
= e⁻Δ/⁽β·δ⁾                           [інтеграл від густини рівномірного розподілу на (0, 1]]
```

Аналіз отриманої експоненційної функції показує:
1. Якщо `Δ` велике (`Δ ≫ β · δ`), тобто до закінчення TTL лишається багато часу, показник `−Δ / (β·δ) → −∞`, а ймовірність оновлення прямує до нуля (`e⁻∞ → 0`). Ресурс не оновлюється завчасно без потреби.
2. У міру наближення до закінчення TTL (`Δ → 0`), показник степеня прямує до нуля, а ймовірність оновлення експоненційно зростає до `e⁰ = 1`.

Обчислимо математичне сподівання сумарної кількості оновлень, які будуть згенеровані пуассонівським потоком клієнтів за весь інтервал наближення до закінчення терміну дії ключа:

```
E[N_updates]
= ∫₀^∞ λ · e⁻Δ/⁽β·δ⁾ dΔ               [інтегрування інтенсивності пуассонівського потоку за часом Δ]
= λ · [−β · δ · e⁻Δ/⁽β·δ⁾]₀^∞         [первісна експоненційної показникової функції]
= λ · β · δ · (1 − 0)                 [обчислення визначеного інтеграла на межах 0 та нескінченності]
= β · (λ · δ)                         [остаточне спрощення формули]
```

Щоб гарантувати, що за весь цикл відбудеться в середньому рівно **одне** фонове оновлення (`E[N_updates] ≈ 1`), параметр `β` слід динамічно обирати обернено пропорційним очікуваному навантаженню:

```
β_optimal = 1 ÷ (λ · δ)
```

Проте алгоритм XFetch вимагає точного збереження тривалості обчислення `δ` поруч із кожним значенням у кеші та є чутливим до похибок оцінки `λ`. Якщо в системі трапляється раптовий сплеск трафіку, XFetch може ініціювати кілька паралельних фонових оновлень.

## Математичне порівняння надійності та витрат ресурсів

Порівняємо характеристики трьох підходів до організації кешування:

| Критерій оцінки | Традиційний кеш (без захисту) | XFetch (імовірнісне оновлення) | Single-Flight (об'єднання) |
|---|---|---|---|
| Пікове навантаження на БД при промаху | `O(λ · δ)` важких запитів | `O(1)` при коректному `β` | Рівно `1` запит детерміновано |
| Необхідність збереження тривалості `δ` | Не потрібна | **Обов'язкова** для кожного ключа | Не потрібна |
| Витрати пам'яті на вузлі | `O(1)` | `O(1)` додаткових байтів на ключ | `O(K_active)` структур очікування |
| Затримка для паралельних клієнтів | `δ + T_queue` (деградація) | `0.5` мс (постійний Cache Hit) | `δ` (очікування завершення рейсу) |
| Чутливість до раптових сплесків `λ` | Катастрофічна (Stampede) | Можливий дубльований старт | **Повна стійкість** |

Single-Flight надає сувору математичну інваріантність: скільки б клієнтських запитів `N` не надійшло у вікно вразливості `δ`, кількість звернень до бази даних тотожно дорівнює одиниці:

```
N_backend_singleflight ≡ 1,  ∀ λ > 0
```

Ця інваріантність перетворює функцію навантаження на бекенд під час промаху кешу з лінійно зростаючої залежності від клієнтського трафіку `f(λ) = λ · δ` на константну величину `f(λ) = 1`, забезпечуючи абсолютну стійкість розподіленої системи до будь-яких сплесків конкурентності.
