# 📋 Контракти інтерфейсів Single-Flight: Go, Envoy, NGINX та DataLoader

Об'єднання однакових паралельних запитів реалізується на різних рівнях розподіленого стека — від внутрішньопроцесних бібліотек конкурентності до зворотних проксі-серверів та клієнтських резолверів. Щоб уникнути помилок конфігурації, блокувань та витоків пам'яті, кожен інструмент визначає свій контракт взаємодії, гарантії безпеки та поведінку при таймаутах.

Розуміння точних семантичних гарантій кожного інтерфейсу дозволяє інженеру обрати правильний рівень дедуплікації: внутрішньопроцесний у пам'яті мікросервісу, на рівні зворотного проксі перед групою бекендів або на рівні батчингу запитів у клієнтських бібліотеках.

Кожен шар стека має власну специфіку життєвого циклу запитів. На прикладному рівні важливо правильно обробляти контексти скасування та неперехоплені паніки. На рівні проксі-серверів критично налаштовувати часові обмеження очікування лідера та правила повернення застарілого кешу, щоб уникнути блокування робочих пулів з'єднань.

## Інтерфейс Go: пакет golang.org/x/sync/singleflight

Пакет `singleflight` є стандартом де-факто для мови програмування Go і надає потокобезпечну структуру `Group`, яка керує синхронізацією функцій, що повертають результат `(any, error)`.

```go
type Group struct {
    // Внутрішні неекспортовані поля: sync.Mutex та map[string]*call
}

func (g *Group) Do(key string, fn func() (any, error)) (v any, err error, shared bool)
func (g *Group) DoChan(key string, fn func() (any, error)) <-chan Result
func (g *Group) Forget(key string)
```

Внутрішня структура `call` містить примітив `sync.WaitGroup`, збережені значення результату та помилки, лічильник очікувачів та прапорець каналу сповіщення. Синхронізація доступу до таблиці активних рейсів здійснюється через взаємне блокування `sync.Mutex`.

### Специфікація методів та параметрів

| Метод | Параметри | Повертає | Поведінка та синхронізація |
|---|---|---|---|
| `Do` | `key string` — ключ рейсу;<br>`fn func() (any, error)` — функція виконання. | `v any` — результат;<br>`err error` — помилка;<br>`shared bool` — чи результат був спільним. | Блокує поточну горутину до повного завершення виконання функції `fn`. Якщо для вказаного `key` рейс уже активний, горутина не викликає `fn`, а очікує результату першої горутини. Повертає `shared = true`, якщо результат отримано від чужого виклику. |
| `DoChan` | `key string` — ключ рейсу;<br>`fn func() (any, error)` — функція виконання. | `<-chan Result` — неблокуючий канал результату (`Result{Val, Err, Shared}`). | Повертає канал із буфером розміром 1 одразу після виклику, не блокуючи горутину. Дозволяє викликачу інтегрувати очікування рейсу в конструкцію `select` разом із таймаутами контексту `ctx.Done()`. |
| `Forget` | `key string` — ключ активного або завершеного рейсу. | — | Атомарно видаляє `key` із внутрішньої таблиці активних рейсів групи. Якщо рейс ще виконується, наступні виклики `Do` для цього ж ключа запустять новий паралельний рейс, не чекаючи завершення старого. |

### Контракт обробки помилок, панік та скасування

Розглянемо детальні правила взаємодії компонентів під час виконання викликів у Go:

1. **Гарантії видимості пам'яті:** Повернені значення `v` та помилка `err` стають доступними для читання очікувачами лише після того, як лідер викликає `wg.Done()`. Оскільки всі очікувачі блокуються на `wg.Wait()`, операційна система гарантує встановлення бар'єра пам'яті (англ. *memory barrier*), забезпечуючи коректну видимість записаних полів без додаткових атомарних операцій.
2. **Трансляція аварійних ситуацій:** Якщо користувацька функція `fn` генерує паніку, внутрішній обробник `Group` перехоплює її через `recover()`, коректно очищає таблицю активних викликів від даного ключа, розблоковує всіх очікувачів і повторно викидає паніку в кожній підписаній горутині. Це унеможливлює зависання системи в стані вічного блокування.
3. **Неблокуючий запис у канал:** Канал результату в методі `DoChan` створюється з буфером місткістю в один елемент (`make(chan Result, 1)`). Це критично важливо для запобігання витоку горутин: якщо клієнт скасовує свій виклик через спрацьовування таймауту і перестає слухати канал, фонова горутина Single-Flight успішно записує результат у буфер і завершує роботу, не зависаючи назавжди на операції запису в канал.
4. **Використання методу Forget:** Метод `Forget` застосовують у сценаріях оптимістичного фонового оновлення. Щойно лідер завершив читання з бази, він викликає `Forget(key)`, щоб наступні звернення не читали застарілий об'єкт рейсу, а мали змогу негайно запустити новий свіжий запит за потреби.

### Приклад використання з контролем таймауту

Нижче наведено ідіоматичний шаблон обробки паралельних запитів із захистом від клієнтських обривів та контролем дедлайнів:

```go
package main

import (
    "context"
    "fmt"
    "time"
    "golang.org/x/sync/singleflight"
)

var sf singleflight.Group

func fetchUserData(ctx context.Context, userID string) (string, error) {
    ch := sf.DoChan(userID, func() (any, error) {
        // Важке звернення до бази даних або мікросервісу
        time.Sleep(100 * time.Millisecond)
        return fmt.Sprintf("Data for %s", userID), nil
    })

    select {
    case <-ctx.Done():
        // Клієнтський таймаут: не блокуємо поточного викликача
        return "", ctx.Err()
    case res := <-ch:
        if res.Err != nil {
            return "", res.Err
        }
        return res.Val.(string), nil
    }
}
```

## Конфігурація NGINX: директиви proxy_cache_lock

У зворотному проксі-сервері NGINX об'єднання запитів реалізовано як механізм блокування дискового кешу `proxy_cache_lock`. Цей механізм координує роботу десятків незалежних процесів-робітників NGINX через спільну пам'ять (англ. *shared memory zone*).

Коли запит зазнає промаху кешу, перший процес-робітник захоплює блокування в зоні пам'яті `keys_zone` і починає завантаження відповіді від бекенду. Усі наступні процеси-робітники, які отримують запити з таким самим кеш-ключем, виявляють блокування і стають у чергу очікування створення дискового кеш-файлу.

```nginx
http {
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m max_size=1g inactive=60m;

    server {
        listen 80;
        location /api/ {
            proxy_pass http://backend_upstream;
            proxy_cache my_cache;
            proxy_cache_key "$request_method$request_uri";

            # Активація блокування паралельних промахів
            proxy_cache_lock on;
            proxy_cache_lock_timeout 5s;
            proxy_cache_lock_age 5s;

            # Віддача застарілого кешу очікувачам під час оновлення
            proxy_cache_use_stale updating error timeout invalid_header http_500 http_502 http_503;
        }
    }
}
```

### Параметри конфігурації NGINX

| Директива | Типове значення | Призначення та механізм дії |
|---|---|---|
| `proxy_cache_lock` | `off` | Якщо встановлено `on`, лише один запит надсилається до вихідного бекенду при промаху кешу. Усі інші запити з таким самим `proxy_cache_key` блокуються в черзі очікування створення кеш-файлу. |
| `proxy_cache_lock_timeout` | `5s` | Максимальний ліміт часу, протягом якого очікувачі чекають, поки лідер завантажить відповідь від бекенду. Після вичерпання таймауту очікувач розблоковується і сам надсилає запит до бекенду, запобігаючи вічному зависанню клієнтів при падінні лідера. |
| `proxy_cache_lock_age` | `5s` | Якщо лідер не встиг повністю записати відповідь у кеш за цей проміжок часу, наступний запит із черги очікувачів отримує право ініціювати новий паралельний запит до бекенду як новий лідер. |
| `proxy_cache_use_stale updating` | — | Дозволяє NGINX миттєво повертати застарілу копію ресурсу з кешу (stale cache) тим запитам, які надійшли в момент, коли лідер оновлює дані на бекенді. Це зводить затримку для очікувачів до нуля. |

Особливу увагу слід звертати на взаємодію директив `proxy_cache_lock_timeout` та `proxy_cache_use_stale updating`. Якщо бекенд не встигає відповісти за 5 секунд, увімкнена директива `updating` дозволяє NGINX негайно віддати очікувачам застарілий кеш, не перевантажуючи бекенд каскадом нових з'єднань.

## Конфігурація Envoy Proxy: request_coalescing

У сучасних хмарних інфраструктурах балансувальник навантаження Envoy реалізує об'єднання запитів безпосередньо на рівні L7-фільтрів у модулі HTTP Cache Filter (`envoy.filters.http.cache`).

```yaml
typed_config:
  "@type": type.googleapis.com/envoy.extensions.filters.http.cache.v3.CacheConfig
  typed_config:
    "@type": type.googleapis.com/envoy.extensions.cache.simple_http_cache.v3.SimpleHttpCacheConfig
  # Активація дедуплікації однакових запитів під час промаху кешу
  coalesce_requests: true
```

Коли прапорець `coalesce_requests` увімкнено, Envoy перевіряє таблицю активних вихідних з'єднань до бекенду. Якщо запит із таким самим хешем кешу вже перебуває у стані передавання байтів (англ. *in-flight upstream stream*), Envoy не створює нового HTTP/2 або HTTP/3 потоку. Замість цього він приєднує новий клієнтський потік до активного з'єднання і транслює байти тіла відповіді паралельно всім підписаним клієнтам (англ. *response body fan-out*).

При налаштуванні Envoy важливо пам'ятати про безпеку заголовків: якщо клієнти надсилають різні заголовки `Authorization` або `Cookie`, запити не повинні об'єднуватися, якщо тільки відповідні заголовки явно не виключені з розрахунку кеш-ключа у фільтрі конфігурації.

Крім того, Envoy дозволяє обмежувати максимальний розмір тіла відповіді, який зберігається в пам'яті для паралельної роздачі очікувачам. Якщо відповідь перевершує ліміт пам'яті, Envoy відключає об'єднання для даного ресурсу і переходить у режим індивідуального проксіювання.

## Інтерфейс Facebook DataLoader (JavaScript / TypeScript)

Бібліотека `DataLoader` вирішує задачу об'єднання та пакетування однакових запитів у середовищах із циклом подій (англ. *event loop*), зокрема в серверах GraphQL на базі Node.js. Вона координує асинхронні звернення, групуючи індивідуальні виклики в один пакетний запит протягом одного такту черги мікротасок.

```typescript
import DataLoader from 'dataloader';

interface User {
    id: string;
    name: string;
}

// Функція пакетного завантаження
async function batchGetUsers(ids: readonly string[]): Promise<(User | Error)[]> {
    const users = await db.users.findMany({ where: { id: { in: [...ids] } } });
    const userMap = new Map(users.map(u => [u.id, u]));
    return ids.map(id => userMap.get(id) || new Error(`User ${id} not found`));
}

const userLoader = new DataLoader<string, User>(batchGetUsers, {
    cache: true,              // Дедуплікація однакових ключів у межах одного такту
    maxBatchSize: 100,        // Максимальна кількість ключів в одному SQL-запиті
    batchScheduleFn: callback => setTimeout(callback, 5) // Часове вікно збирання 5 мс
});
```

### Контракт методів DataLoader

| Метод | Аргументи | Повертає | Опис та семантика |
|---|---|---|---|
| `load(key)` | `key: K` | `Promise<V>` | Реєструє ключ для завантаження в поточному такті черги мікротасок (`process.nextTick`). Повертає індивідуальний проміс. Якщо ключ викликано кілька разів у межах одного кадру, створюється один спільний запит. |
| `loadMany(keys)` | `keys: K[]` | `Promise<(V \| Error)[]>` | Пакетний виклик для масиву ключів. Повертає масив результатів або об'єктів помилок, зберігаючи точний порядок та довжину вхідного масиву ключів. |
| `clear(key)` | `key: K` | `this` | Очищає внутрішній кеш мемоізації для конкретного ключа, змушуючи наступний `load` виконати новий запит до джерела даних. |
| `clearAll()` | — | `this` | Повне очищення кешу поточного екземпляра DataLoader. |
| `prime(key, value)` | `key: K, value: V` | `this` | Завчасно наповнює внутрішню таблицю готовим об'єктом, уникаючи подальших викликів пакетного завантаження для цього ключа. |

**Критичне правило ізоляції контексту:** Екземпляр `DataLoader` має локальний життєвий цикл і зобов'язаний створюватися заново для кожного вхідного HTTP-запиту. Створення глобального довгоживучого екземпляра DataLoader є грубою помилкою безпеки, оскільки призводить до кешування персональних даних одного користувача та їх випадкової віддачі іншим користувачам без перевірки прав доступу.
