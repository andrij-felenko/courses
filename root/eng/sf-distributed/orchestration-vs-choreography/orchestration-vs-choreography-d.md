# Оркестрація проти хореографії: хто веде багатокроковий процес

<preknowlist>
- [Омани розподілених обчислень](root:sf-distributed/distributed-fallacies) — чому повідомлення в мережі затримуються, дублюються або губляться.
- [Патерн «Сага»](root:sf-distributed/saga-pattern) — координація розподілених кроків через послідовність локальних транзакцій та компенсаційних дій.
- [Ідемпотентність](root:sf-distributed/idempotency) — властивість повторного виконання операції без зміни кінцевого стану системи.
- [Transactional outbox](root:sf-distributed/outbox-pattern) — атомарне збереження локальних змін і публікація доменних подій у брокер.
- [Довговічні робочі процеси](root:sf-distributed/durable-workflows) — збереження стану розподіленого процесу та детерміноване відновлення при збоях.
- [Журнал подій](root:sf-distributed/event-log) — незмінний список фактів як першоджерело правди для аудиту та відновлення стану.
</preknowlist>

Клієнт інтернет-магазину оформлює замовлення на потужну графічну станцію вартістю 180 000 гривень. Процес обробки цієї транзакції вимагає злагодженої взаємодії чотирьох незалежних мікросервісів: сервісу замовлень (`OrderService`), складської системи обліку (`InventoryService`), платіжного шлюзу (`PaymentService`) та служби кур'єрської логістики (`LogisticsService`). О 14:02:11 користувач натискає кнопку оплати. Складський сервіс успішно резервує конкретний серійний номер комп'ютера на полиці B-14, а платіжний шлюз успішно списує з банківської картки покупця 180 000 гривень. Але коли черга доходить до третього кроку — призначення кур'єра в логістичній системі — сервіс логістики повертає HTTP 503 через вичерпання ліміту доступних автомобілів на поточну добу.

Якщо система не має чіткої інженерної стратегії координації багатокрокового процесу, розподілена транзакція розвалюється в невизначений аварійний стан. 180 000 гривень списано з рахунку клієнта, дорогий комп'ютер заблоковано на складі й приховано з вітрини для інших покупців, а доставка так і не створилася. Жоден із сервісів не знає, хто саме зобов'язаний повернути кошти, хто має зняти бронь із полиці B-14, і в якому фінальному статусі перебуває замовлення.

У класичних монолітних архітектурах подібну задачу вирішував механізм двофазної фіксації (Two-Phase Commit, 2PC) на рівні реляційної бази даних. Проте в сучасних розподілених мікросервісних середовищах розподілені блокування на час мережевих затримок паралізують продуктивність СКБД, а тимчасове падіння будь-якого з учасників заморожує ресурси всієї платформи. Єдиним життєздатним інженерним рішенням стає розбиття глобальної транзакції на послідовність локальних кроків — патерн [Сага](root:sf-distributed/saga-pattern). Але тут постає фундаментальне архітектурне питання: **хто саме відповідає за просування саги вперед і запуск відкату при аварії?**

![Порівняння двох парадигм координації: централізований диригент проти децентралізованого ланцюга подій](/root/eng/sf-distributed/orchestration-vs-choreography/img/orchestration-vs-choreography-flow.svg)

*Оркестрація використовує центрального координатора для прямого керування кроками процесу; хореографія спирається на реактивну передачу доменних подій між автономними сервісами.*

## Дві парадигми координації: механіка та сутність

Для керування розподіленим процесом існують дві протилежні за своєю філософією архітектурні парадигми:

1. **Реактивна реакція на події:** Сервіси не отримують прямих наказів від зовнішнього центру. Кожен компонент слухає потік фактів про те, що сталося в системі, самостійно вирішує, чи стосується цей факт його домену, виконує свою локальну транзакцію й публікує у спільний брокер новий факт. Таку парадигму взаємодії називають **хореографією** (від грец. *χορεία* — хороводний танець + *γράφω* — записувати). Подібно до танцюристів на сцені, які знають свої рухи за музичним тактом і позиціями партнерів без постійних вигуків режисера, сервіси координуються виключно за рахунок узгодженої реакції на доменні події.
2. **Централізоване спрямування дій:** Окремий виділений компонент бере на себе повну відповідальність за життєвий цикл бізнес-транзакції. Він зберігає граф виконання процесу, явно надсилає цільовим сервісам команди на виконання дій, очікує результатів і вирішує, який крок має бути наступним. Таку парадигму називають **оркестрацією** (від англ. *orchestration*, що походить від грец. *ὀρχήστра* — напівкруглий майданчик перед сценою античного театру для хору й музикантів). Подібно до диригента, який керує партіями кожного музиканта в оркестрі, координатор явно спрямує кожен виклик і тримає загальну картину виконання у своїх руках.

Детальний аналіз історичної еволюції обох підходів — від ранніх стандартів WS-BPEL та корпоративних шин ESB до сучасної кодоцентричної оркестрації — викладено в [історичному нарисі еволюції координації](root:sf-distributed/orchestration-vs-choreography/hist-orchestration-vs-choreography.md).

## Реактивна хореографія: архітектура та механіка

У хореографічній архітектурі взаємодія між сервісами будується за принципом «Розумні кінцеві точки та дурні труби» (англ. *Smart endpoints and dumb pipes*). Сервіси спілкуються асинхронно через шину повідомлень або брокер подій (наприклад, Apache Kafka, RabbitMQ чи NATS JetStream).

### Прямий потік виконання (The Happy Path)

Прямий хід обробки замовлення розгортається у вигляді послідовного ланцюжка доменних подій:

```
[ Клієнт ] → POST /orders → [ OrderService ] 
                                  ↓ публікує
                       Подія: OrderCreatedEvent
                                  ↓ слухає
                          [ InventoryService ]
                                  ↓ резервує товар і публікує
                       Подія: StockReservedEvent
                                  ↓ слухає
                           [ PaymentService ]
                                  ↓ списує кошти й публікує
                       Подія: PaymentCapturedEvent
                                  ↓ слухає
                          [ LogisticsService ]
                                  ↓ замовляє доставку й публікує
                       Подія: DeliveryBookedEvent
```

Кожен сервіс знає лише дві речі:
* Яку вхідну подію він очікує з брокера.
* Яку вихідну подію він зобов'язаний опублікувати після успішного завершення власної локальної транзакції бази даних.

Щоб події не змішувалися між тисячами паралельних користувачів, кожне повідомлення маркується наскрізним ідентифікатором — **слідчим ідентифікатором** (англ. *Correlation ID*). Коли `OrderService` генерує замовлення `ORD-9810`, це значення передається в метаданих усіх наступних подій, дозволяючи системам розподіленого трасування (OpenTelemetry, Jaeger) відтворити ланцюг викликів.

Критично важливим елементом тут є патерн [Transactional Outbox](root:sf-distributed/outbox-pattern). Сервіс не може спочатку записати зміну в базу даних, а потім викликати `kafkaProducer.send()`, оскільки падіння процесу між цими двома операціями призведе до подвійного запису: зміна в базі залишиться, а подія ніколи не надійде іншим учасникам хореографії.

### Переваги хореографії

* **Висока часова автономія та слабке зв'язування:** Сервіси не знають мережевих адрес та інтерфейсів один одного. `OrderService` навіть не підозрює, чи існує в системі склад або аналітичний сервіс — він просто констатує факт: «Замовлення створено».
* **Легкість розширення для спостерігачів (Fan-out):** Якщо бізнес вирішує надсилати клієнту привітальний лист або нараховувати бонуси лояльності за факт створення замовлення, новий сервіс `LoyaltyService` просто підписується на вже існуючий топік `OrderCreatedEvent`. Жоден рядок коду існуючих систем не змінюється.
* **Відсутність єдиної точки відмови (SPOF) на рівні застосунку:** Немає центрального сервера-координатора, падіння якого зупинило б обробку всіх бізнес-процесів організації.

### Зворотний бік хореографії: де ламається реактивна модель

Хоча хореографія виглядає елегантно на простих схемах, її масштабування у великих комерційних системах породжує комплекс важких інженерних проблем.

![Каскадний колапс компенсацій у реактивній хореографії](/root/eng/sf-distributed/orchestration-vs-choreography/img/choreography-compensation-chaos.svg)

*У хореографії аварія на пізньому кроці вимагає складного зворотного ланцюга подій; затримка чи втрата компенсаційного повідомлення спричиняє розсинхронізацію та фантомні блокування.*

#### 1. Архітектурна сліпота та «пінбольна архітектура» (Pinball Architecture)
У системі з чистою хореографією немає жодного файлу конфігурації, діаграми чи рядка коду, де було б описано повний бізнес-процес. Потік керування є прихованою властивістю (англ. *emergent behavior*), розмазаною між десятками репозиторіїв та SQL-баз даних.

Щоб зрозуміти, що станеться при натисканні користувачем кнопки на сайті, інженер змушений провести детективне розслідування: відкрити код п'яти мікросервісів, перевірити назви топіків у конфігураціях Terraform і зіставити схеми серіалізації JSON. Подія стрибає між сервісами, наче кулька в автоматі пінболу, і передбачити кінцеву траєкторію стає практично неможливо.

#### 2. Комбінаторний вибух компенсаційних топіків
Якщо на останньому кроці (доставка) стається збій, система має виконати відкат. У хореографії це означає запуск зустрічної хвилі подій:
1. `LogisticsService` публікує `DeliveryFailedEvent`.
2. `PaymentService` має слухати `DeliveryFailedEvent`, виконати повернення коштів на карту й опублікувати `PaymentRefundedEvent`.
3. `InventoryService` має слухати `PaymentRefundedEvent`, зняти резерв із полиці й опублікувати `StockReleasedEvent`.
4. `OrderService` має слухати `StockReleasedEvent` і перевести статус замовлення в `CANCELLED`.

А якщо платіжний сервіс зазнав збою раніше, ніж дійшов до логістики? Тоді `InventoryService` має додатково слухати подію `PaymentFailedEvent`! 
Кожен сервіс змушений знати про всі можливі типи помилок усіх наступних сервісів у ланцюжку. Зв'язність за схемами подій між мікросервісами зростає квадратично за формулою:

```
Зв'язків = N · (N - 1)
```

де `N` — кількість кроків у процесі.

#### 3. Стан перегонів компенсацій (Out-of-order Compensation Race)
Через асинхронну природу черг подія відкату може обігнати подію прямого ходу. Уявімо ситуацію: через мережеве зависання повідомлення `OrderCreatedEvent` затрималося на 5 секунд по дорозі до `PaymentService`. Тим часом `InventoryService` вже встиг зарезервувати товар, намагався викликати доставку, отримав швидку відмову через перевантаження й негайно вистрілив подію `InventoryReleaseTriggeredEvent`.

Платіжний сервіс отримує команду на скасування платежу **раніше**, ніж повідомлення про необхідність його списати! Сервіс перевіряє свою базу, бачить, що транзакції ще немає, і ігнорує компенсацію. За мить надходить запізніле пряме повідомлення `OrderCreatedEvent`, і платіжний сервіс списує гроші з картки назавжди. Це класична пастка фантомного списання.

#### 4. Мовчазні зависання (Silent Stalls)
У хореографії немає супервізора. Якщо в платіжному сервісі стався фатальний виняток, повідомлення потрапило в чергу отруйних листів ([Dead Letter Queue](root:sf-distributed/dead-letter-queue)), а подія `PaymentCapturedEvent` ніколи не була опублікована, замовлення просто тихо зависає. Складський резерв лишається заблокованим нескінченно, оскільки склад не отримує ані підтвердження, ані сигналу скасування.

#### 5. Партиціонування в Kafka та блокування початку черги (Head-of-Line Blocking)
Для збереження послідовності подій одного замовлення розробники використовують `order_id` як ключ партиції в Apache Kafka. Проте якщо одне конкретне замовлення викликає аварійний збій обробника (наприклад, пошкоджений JSON), консьюмер зупиняється на зміщенні (Offset) цієї партиції. Усі інші замовлення, які випадково потрапили в ту саму партицію за хешем ключа, виявляються заблокованими, що викликає каскадну деградацію затримки.

## Аномалії ізоляції саги: чому компенсації складніші за SQL Rollback

Оскільки сага складається з окремих локальних транзакцій, проміжні зміни стають видимими для зовнішнього світу ще до того, як весь процес буде успішно завершено. Сага жертвує властивістю повної ізоляції (літера **I** в абревіатурі ACID).

Це породжує три критичні розподілені аномалії:

### 1. Брудне читання (Dirty Read)
Поки замовлення проходить кроки оплати, сторонній фоновий звіт читає стан складу і бачить, що залишок товару зменшився на 1 одиницю. Якщо через хвилину оплата відхиляється і товар розблоковується, звіт оперував недійсними даними.

### 2. Втрачене оновлення (Lost Update)
Дві паралельні саги одночасно читають залишок на складі (наприклад, 10 одиниць). Сага A резервує 4 штуки (залишок 6), Сага B резервує 5 штук (залишок 1). Якщо Сага A згодом відкочується і просто записує у поле значення `10 - 5 = 5` без відносного додавання (`balance = balance + 4`), вона знищує результат роботи паралельної Саги B.

### 3. Неповторюване читання (Non-repeatable Read)
Між початком процесу та його фіналом сторонній процес встигає змінити ціну товару або валютний курс. Якщо компенсація спирається на повторне зчитування ціни замість збереженого знімка контексту, сума повернення на карту відрізнятиметься від початково списаної суми.

### Захисні інженерні патерни
Для подолання цих аномалій інженери застосовують такі підходи:
* **Семантичне блокування (Semantic Lock):** Рядок у базі даних не просто модифікується, а позначається статусом `PENDING_RESERVATION`. Інші процеси знають, що ресурс заблоковано незавершеною сагою, і або чекають, або відхиляють конкуруючі операції.
* **Песимістичні оновлення замість перезапису:** Усі компенсації оперують відносними дельтами (`UPDATE balance SET count = count + :refunded_qty`), а не абсолютними значеннями.
* **Перевірка версій (Version Epochs):** Використання оптимістичного блокування з числовим полем `version` унеможливлює перезапис стану застарілою транзакцією.

## Централізована оркестрація: детермінізм та керованість

Оркестрація змінює парадигму: замість розмазування логіки між подіями, весь сценарій виконання зосереджується в явному координаторі — **оркестраторі процесу** (англ. *Workflow Orchestrator*).

Сучасні рушії оркестрації (такі як Temporal, Cadence, Zeebe, AWS Step Functions або Camunda) базуються на концепції довговічного виконання ([Durable Workflows](root:sf-distributed/durable-workflows)) та журналу подій ([Event Log](root:sf-distributed/event-log)).

![Автомат станів оркестратора та LIFO стек компенсаційних дій](/root/eng/sf-distributed/orchestration-vs-choreography/img/orchestrator-state-machine-rollback.svg)

*Оркестратор фіксує кожен успішний крок у незмінному журналі й реєструє компенсаційну дію у стеку; при збої рушій детерміновано розмотує стек у зворотному порядку.*

### Команди проти подій: принципова семантична різниця

Оркестратор оперує не загальними подіями, а адресними **командами** (англ. *Commands*):
* **Подія (Event):** «Замовлення створено» (`OrderCreated`) — констатація факту в минулому часі. Джерело не знає, хто її прочитає і чи зробить хтось щось у відповідь.
* **Команда (Command):** «Списати 180 000 грн з карти X» (`ChargePaymentCommand`) — чітка директива в наказовому способі, надіслана конкретному виконавцю з очікуванням явного результату (`OK` або помилка).

### Механізм компенсаційного стека (LIFO Rollback)

Головна сила оркестратора проявляється при обробці аварій. Оркестратор динамічно веде стек виконаних дій за принципом `LIFO` (Last-In, First-Out):

```
1. Виклик: ReserveInventory() → Успіх
   Стек компенсацій: [ ReleaseInventory ]

2. Виклик: ChargePayment(180 000 грн) → Успіх
   Стек компенсацій: [ ReleaseInventory, RefundPayment(180 000 грн) ]

3. Виклик: BookDelivery() → ЗБІЙ (HTTP 503)
   
[ Початок керованого відкату ]
-> Pop: RefundPayment(180 000 грн) → Виклик PaymentService.Refund()
-> Pop: ReleaseInventory()          → Виклик InventoryService.Release()
```

Оркестратор точно знає поточний стан. Якщо аварія сталася на кроці 3, він гарантовано викличе компенсації для кроків 2 та 1, але **ніколи не викликатиме компенсацію для кроку 3**, оскільки той не завершився успіхом.

### Вбудована стійкість до відмов: повтори, таймери та виведення зі стану сну

Оркестратор бере на себе низькорівневу рутину розподіленої надійності:
* **Експоненційні повтори (Retries with Backoff):** Якщо виклик платіжного шлюзу завершився мережевим тайм-аутом, оркестратор автоматично повторює запит через 1 с, 2 с, 4 с із додаванням випадкового шуму ([Retries and Jitter](root:sf-distributed/retries-backoff)), використовуючи ключ [ідемпотентності](root:sf-distributed/idempotency).
* **Довговічні таймери:** Якщо бізнес-вимога говорить: «Якщо клієнт не підтвердив замовлення протягом 48 годин, скасувати бронь», в оркестраторі це записується простим викликом `workflow.sleep(48 * hours)`. Процес засинає, не споживаючи пам'яті чи процесорного часу, а через 48 годин рушій точно відновлює його роботу.
* **Детерміноване відтворення журналу (Deterministic Replay):** При падінні вузла воркер перечитує журнал історії від початку. Якщо крок 1 уже зафіксовано як виконаний, рушій не викликає зовнішній сервіс вдруге, а миттєво підставляє збережений результат із журналу.
* **Централізований аудит:** Будь-якої миті адміністратор або інженер підтримки може відкрити панель керування та побачити точний графічний стан замовлення: які кроки вже пройдено, на якій секунді стався збій, скільки спроб повтору було здійснено і які значення змінних були на кожному етапі.

Специфікацію контрактів взаємодії оркестратора та форматів конвертів наведено у [довідці інтерфейсів оркестратора та контрактів подій](root:sf-distributed/orchestration-vs-choreography/api-orchestrator-contracts.md).

## Порівняльна інженерна матриця: Оркестрація проти Хореографії

Вибір між двома підходами вимагає зіставлення фундаментальних архітектурних компромісів:

| Інженерний критерій | Реактивна хореографія | Централізована оркестрація |
|---|---|---|
| **Видимість потоку керування** | Низька. Потік розмазаний між обробниками та чергами. | Абсолютна. Повний граф процесу зафіксовано в одному місці. |
| **Зв'язність сервісів (Coupling)** | Слабке зв'язування за адресами, але сильне за схемами подій. | Пряме зв'язування з оркестратором; воркери ізольовані один від одного. |
| **Складність відкату (Rollback)** | Експоненційно складна. Ризик гонок та втрати компенсацій. | Детермінована. Автоматичне розмотування стека `LIFO`. |
| **Обробка довгих тайм-аутів** | Складна. Вимагає зовнішніх планувальників чи DLQ з TTL. | Нативна. Підтримка довговічних таймерів (`sleep`) на місяці. |
| **Додавання спостерігачів (Fan-out)** | Ідеально. Новий сервіс просто підключається до топіка. | Потребує додавання нового кроку в код або виклику підпроцесу. |
| **Єдина точка відмови (SPOF)** | Відсутня на рівні коду сервісів (але брокер Kafka лишається SPOF). | Рушій оркестратора є центральним вузлом (вимагає кластеризації). |
| **Мережеві затримки (Latency)** | Мінімальні. Пряма передача подій від сервісу до сервісу. | Додатковий стрибок (Hop) через оркестратор на кожному кроці. |
| **Налагодження та моніторинг** | Складне. Вимагає збору розподілених слідів (Distributed Tracing). | Просте. Повна історія виконання доступна в єдиному інтерфейсі. |
| **Інфраструктурна складність** | Потрібен лише надійний брокер повідомлень (Kafka / RabbitMQ). | Потрібен спеціалізований кластер рушія (Temporal / Zeebe / DB). |

## Гібридна архітектура: Мікро-оркестрація та Макро-хореографія

У зрілих розподілених системах великого масштабу спроба вирішити всі задачі виключно одним інструментом є помилкою. Сучасна інженерна практика використовує комбінований підхід: **оркестрація всередині обмеженого контексту (Bounded Context) та хореографія між різними доменами**.

![Гібридна координація: макро-хореографія між доменами та мікро-оркестрація всередині контексту](/root/eng/sf-distributed/orchestration-vs-choreography/img/hybrid-coordination-topology.svg)

*Мікро-оркестрація гарантує транзакційну надійність кроків у межах одного домену; макро-хореографія забезпечує автономію та слабке зв'язування між бізнес-контекстами через глобальну шину подій.*

### Як працює гібридна топологія на практиці

1. **Макро-рівень (Хореографія між доменами):** 
   Домен замовлень (`Orders`), домен платежів (`Billing`) та домен логістики (`Logistics`) належать різним командам і мають повністю автономні бази даних. Вони спілкуються через глобальну корпоративну шину подій (Apache Kafka). Коли замовлення оформлено, домен замовлень публікує високорівневу подію `OrderReadyForBillingEvent`.
2. **Мікро-рівень (Оркестрація всередині домену):**
   Отримавши цю подію, платіжний домен запускає внутрішній локальний робочий процес під керуванням Temporal. Цей оркестратор виконує суто внутрішні кроки: перевірка антифрод-скорингу (3D Secure), списання грошей з банківського шлюзу, нарахування кешбеку на внутрішній рахунок та генерація фіскального чека. Якщо антифрод блокує операцію, локальний оркестратор сам відкочує транзакцію і публікує в глобальну шину підсумковий факт: `PaymentRejectedEvent`.

Такий розподіл обов'язків дає найкраще з обох світів:
* Кожна команда зберігає повну автономію розгортання своїх мікросервісів.
* Складні транзакційні ланцюжки з компенсаціями та тайм-аутами захищені надійною детермінованою оркестрацією всередині домену.
* Глобальна шина не засмічується низькорівневими технічними командами.

## Зіставлення в коді: Реалізація оркестратора проти реактивних обробників

Щоб побачити різницю в інженерній складності, зіставимо дві реалізації одного й того самого процесу обробки замовлення.

### Оркестратор саги з детермінованим стеком відкату

:::tabs
```c
#include <stdio.h>
#include <stdbool.h>
#include <string.h>

#define MAX_STEPS 4

typedef enum { STEP_OK = 0, STEP_ERR = 1 } StepResult;

typedef struct {
    char order_id[32];
    double price;
    bool force_logistics_error;
} OrderCtx;

typedef StepResult (*StepFunc)(OrderCtx *ctx);
typedef void (*CompFunc)(OrderCtx *ctx);

typedef struct {
    const char *title;
    StepFunc forward;
    CompFunc compensate;
} StepDef;

/* Прямі дії та компенсації */
StepResult act_inventory(OrderCtx *c) { printf(" [Склад] Резерв товару... [OK]\n"); return STEP_OK; }
void comp_inventory(OrderCtx *c) { printf(" [Склад] ВІДКАТ: Зняття резерву товару.\n"); }

StepResult act_payment(OrderCtx *c) { printf(" [Оплата] Списання %.2f грн... [OK]\n", c->price); return STEP_OK; }
void comp_payment(OrderCtx *c) { printf(" [Оплата] ВІДКАТ: Повернення коштів на карту.\n"); }

StepResult act_logistics(OrderCtx *c) {
    if (c->force_logistics_error) {
        printf(" [Доставка] АВАРІЯ: Немає вільних кур'єрів!\n");
        return STEP_ERR;
    }
    printf(" [Доставка] Кур'єра призначено... [OK]\n");
    return STEP_OK;
}
void comp_logistics(OrderCtx *c) { printf(" [Доставка] ВІДКАТ: Скасування кур'єра.\n"); }

bool run_orchestrator(OrderCtx *ctx) {
    StepDef pipeline[MAX_STEPS] = {
        {"Inventory", act_inventory, comp_inventory},
        {"Payment", act_payment, comp_payment},
        {"Logistics", act_logistics, comp_logistics}
    };
    size_t total_steps = 3;
    CompFunc rollback_stack[MAX_STEPS];
    size_t stack_ptr = 0;

    printf("=== СТАРТ ОРКЕСТРАЦІЇ: %s ===\n", ctx->order_id);
    for (size_t i = 0; i < total_steps; ++i) {
        printf("-> Виконання кроку: %s\n", pipeline[i].title);
        if (pipeline[i].forward(ctx) == STEP_OK) {
            rollback_stack[stack_ptr++] = pipeline[i].compensate;
        } else {
            printf("\n[!] Збій на кроці %s. Оркестратор запускає LIFO відкат:\n", pipeline[i].title);
            while (stack_ptr > 0) {
                rollback_stack[--stack_ptr](ctx);
            }
            printf("=== ПРОЦЕС СКАСОВАНО ТА СТАБІЛІЗОВАНО ===\n");
            return false;
        }
    }
    printf("=== ВСІ КРОКИ УСПІШНО ЗАВЕРШЕНО ===\n");
    return true;
}
```
```cpp
#include <iostream>
#include <string>
#include <vector>
#include <functional>
#include <expected>
#include <format>

struct OrderCtx {
    std::string order_id;
    double price{0.0};
    bool force_logistics_error{false};
};

enum class WorkflowError {
    InventoryUnavailable,
    PaymentFailed,
    LogisticsUnavailable
};

struct StepDef {
    std::string title;
    std::function<std::expected<void, WorkflowError>(OrderCtx&)> forward;
    std::function<void(OrderCtx&)> compensate;
};

class SagaOrchestrator {
public:
    void register_step(StepDef step) {
        steps_.push_back(std::move(step));
    }

    std::expected<void, WorkflowError> execute(OrderCtx& ctx) {
        std::cout << std::format("=== СТАРТ C++ ОРКЕСТРАЦІЇ: {} ===\n", ctx.order_id);
        std::vector<std::function<void(OrderCtx&)>> rollbacks;

        for (const auto& step : steps_) {
            std::cout << std::format("-> Виконання кроку: {}\n", step.title);
            auto res = step.forward(ctx);
            if (res.has_value()) {
                if (step.compensate) {
                    rollbacks.push_back(step.compensate);
                }
            } else {
                std::cout << std::format("\n[!] Збій на етапі {}. Запуск LIFO компенсацій:\n", step.title);
                for (auto it = rollbacks.rbegin(); it != rollbacks.rend(); ++it) {
                    (*it)(ctx);
                }
                std::cout << "=== ПРОЦЕС СКАСОВАНО ТА СТАБІЛІЗОВАНО ===\n";
                return std::unexpected(res.error());
            }
        }

        std::cout << "=== ВСІ КРОКИ УСПІШНО ЗАВЕРШЕНО ===\n";
        return {};
    }

private:
    std::vector<StepDef> steps_;
};
```

> 🔧 **Навіщо це.** 
> Обирайте **Оркестрацію**, якщо:
> * Бізнес-процес містить понад три послідовні кроки, розгалуження або умови скасування.
> * Потрібно підтримувати довгі очікування (дні, тижні) та чіткі тайм-аути.
> * Критично мати єдиний інтерфейс аудиту та можливість перезапустити процес із місця аварії.
>
> Обирайте **Хореографію**, якщо:
> * Процес дуже короткий (1–2 кроки) та не вимагає складних зворотних компенсацій.
> * Потрібна гранично низька затримка без проміжних вузлів-координаторів.
> * Архітектура будується навколо розсилки фактів багатьом незалежним сервісам-слухачам (аналітика, сповіщення, аудит).
>
> Для масштабних enterprise-систем стандартним золотим правилом є **гібридна модель**: мікро-оркестрація всередині бізнес-доменів та макро-хореографія між ними.
