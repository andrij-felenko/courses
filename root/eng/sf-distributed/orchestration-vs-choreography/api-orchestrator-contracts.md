# 📋 Інтерфейси оркестратора та контракти подій розподілених процесів

Для забезпечення надійної взаємодії компонентів у розподілених бізнес-транзакціях потрібні суворі стандартизовані інтерфейси. Будь-яка неоднозначність у типах даних, семантиці ідемпотентності чи структурі заголовків призводить до розсинхронізації станів, втрати компенсацій та накопичення «завислих» процесів.

Нижче наведено вичерпну специфікацію програмних інтерфейсів оркестратора довговічних процесів (Workflow Orchestration Engine), механіки взаємодії з чергами задач та відкритий контракт доменних подій на базі стандарту CloudEvents 1.0 для реактивної хореографії.

---

## 1. Програмні структури та інтерфейси оркестратора

Оркестратор взаємодіє з воркерами активностей (Activity Workers) через детерміновані структури задач, черги команд та протоколи підтвердження виконання.

### Метадані активності (Activity Definition)

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    char step_id[64];
    char activity_name[64];
    char queue_name[64];
    uint32_t timeout_seconds;
    uint32_t heartbeat_timeout_seconds;
    uint32_t max_retries;
    double backoff_coefficient;
    bool is_compensation;
} ActivityMetadata;

typedef struct {
    char execution_id[64];
    char workflow_id[64];
    uint32_t attempt_number;
    const char *payload_json;
    size_t payload_len;
} ActivityTaskContext;
```
```cpp
#include <string>
#include <chrono>
#include <cstdint>
#include <string_view>

struct ActivityMetadata {
    std::string step_id;
    std::string activity_name;
    std::string queue_name;
    std::chrono::seconds timeout{30};
    std::chrono::seconds heartbeat_timeout{5};
    uint32_t max_retries{5};
    double backoff_coefficient{2.0};
    bool is_compensation{false};
};

struct ActivityTaskContext {
    std::string execution_id;
    std::string workflow_id;
    uint32_t attempt_number{1};
    std::string_view payload_json;
};
```
:::

#### Опис полів метаданих активності:
* `step_id`: детермінований ідентифікатор вузла в графі саги. Використовується рушієм для розпізнавання вже виконаних кроків під час повторного відтворення журналу історії.
* `activity_name`: зареєстроване ім'я функції або мікросервісу, що виконує конкретну операцію (наприклад, `ReserveInventoryTask`).
* `queue_name`: ім'я черги задач (Task Queue), яку опитують цільові воркери.
* `timeout_seconds`: граничний час від моменту захоплення задачі воркером до повернення результату. Якщо час вичерпано, рушій переводить задачу в статус `TIMEOUT` та ініціює повтор.
* `heartbeat_timeout_seconds`: інтервал надсилання контрольних сигналів пульсу (Heartbeat) від довготривалої активності. Дозволяє оркестратору виявити раптову загибель процесу воркера (OOM-killer або перезапуск ноди) до спливання глобального таймауту.
* `backoff_coefficient`: множник експоненційного збільшення паузи між невдалими спробами виконання (типово `2.0`).
* `is_compensation`: позначка, яка визначає дану дію як компенсаційну (відкатну). Для таких дій оркестратор зазвичай застосовує нескінченні повтори (`max_retries = ∞`), оскільки відмова компенсації вимагає ручного аварійного втручання.

## 2. Статусна модель життєвого циклу саги

Кожен розподілений процес має скінченний набір станів, переходи між якими фіксуються в незмінному журналі подій:

| Стан (WorkflowState) | Числовий код | Опис стану та правила переходу |
|---|---|---|
| `WORKFLOW_PENDING` | `0` | Запит на запуск саги отримано та записано в чергу планування. |
| `WORKFLOW_RUNNING` | `1` | Процес активно виконує прямі кроки графа активностей. |
| `WORKFLOW_COMPLETED` | `2` | Усі кроки прямого графа успішно виконано без винятків. Термінальний успіх. |
| `WORKFLOW_FAILED` | `3` | Один із прямих кроків повернув непоправну помилку. Ініційовано відкат. |
| `WORKFLOW_COMPENSATING` | `4` | Рушій послідовно розмотує стек компенсацій у зворотному напрямку (`LIFO`). |
| `WORKFLOW_ROLLED_BACK` | `5` | Усі компенсаційні операції успішно виконано. Термінальне скасування. |
| `WORKFLOW_STALLED` | `6` | Стався збій виконання самої компенсаційної дії. Процес заморожено для оператора. |

### Правила переходів між станами
Перехід зі стану `WORKFLOW_RUNNING` у `WORKFLOW_COMPLETED` можливий лише тоді, коли всі зареєстровані в графі прямі активності повернули статус успіху. 

Якщо хоча б одна активність повертає бізнес-відмову (наприклад, `InventoryOutOfStock`), оркестратор фіксує подію `WorkflowExecutionFailed` у журналі історії та переводить процес у стан `WORKFLOW_COMPENSATING`.

У стані `WORKFLOW_COMPENSATING` рушій послідовно призначає відкатні задачі воркерам. Якщо компенсаційна дія зазнає мережевого збою, рушій не переходить до наступного кроку, а повторює спробу з експоненційним інтервалом. Лише після успішного підтвердження всіх компенсацій процес переходить у термінальний стан `WORKFLOW_ROLLED_BACK`. Якщо компенсація повертає невідновну помилку (наприклад, банківський рахунок клієнта заблоковано назавжди), процес переводиться в стан `WORKFLOW_STALLED` та надсилає сповіщення черговому інженеру підтримки.

## 3. Протокол опитування черг задач (Task Queue Polling)

Оркестратор не здійснює прямих вихідних викликів на HTTP-ендпоінти мікросервісів (Push-модель). Прямий Push створює ризик перевантаження сервісів запитами під час пікових навантажень. 

Замість цього застосовується модель довгого опитування (Long Polling Pull-модель):
1. **Ініціалізація воркера:** Воркер активності встановлює постійне gRPC-з'єднання з сервером оркестратора та надсилає запит `PollActivityTaskQueueRequest`.
2. **Очікування на сервері:** Якщо черга задач порожня, сервер оркестратора тримає HTTP/2 стрім відкритим до 60 секунд. Щойно в робочому процесі з'являється задача для відповідної черги, сервер миттєво відправляє задачу воркеру.
3. **Виконання та відповідь:** Воркер виконує локальну транзакцію й повертає `RespondActivityTaskCompleted` або `RespondActivityTaskFailed` разом із результатом серіалізованого JSON.

Така тягнуча архітектура автоматично забезпечує протитиск (Backpressure): сервіс бере в роботу рівно стільки задач, скільки потоків виділено в його внутрішньому пулі обробників.

## 4. Контракт ідемпотентності та захист від дублікатів

Оскільки мережевий транспорт у розподілених системах забезпечує семантику доставки «щонайменше один раз» (англ. *At-Least-Once Delivery*), кожна активність зобов'язана підтримувати сувору ідемпотентність.

### Життєвий цикл ключа ідемпотентності (Idempotency Key Protocol)

Кожен виклик містить складений ключ:
```
IdempotencyKey = WorkflowID + "_" + StepID + "_" + AttemptID
```

Протокол взаємодії воркера зі сховищем стану:
1. **Етап блокування:** Воркер перед початком роботи виконує атомарну перевірку в реляційній базі або сховищі ключ-значення:
   ```sql
   INSERT INTO idempotency_records (key, status, created_at)
   VALUES ('ORD-9810_step_payment_1', 'PROCESSING', NOW())
   ON CONFLICT (key) DO NOTHING;
   ```
2. **Аналіз результату вставки:**
   * Якщо вставка успішна (рядків оновлено = 1): воркер має ексклюзивне право на виконання дії.
   * Якщо ключ уже існує зі статусом `PROCESSING`: паралельний процес уже виконує цю задачу. Поточний запит відхиляється або очікує завершення першого.
   * Якщо ключ уже існує зі статусом `COMPLETED`: воркер миттєво повертає раніше збережений результат із колонки `response_payload` без повторного списання коштів чи блокування складу.
3. **Фіксація результату:** Після завершення локальної транзакції статус переводиться в `COMPLETED` в тій самій транзакції бази даних:
   ```sql
   UPDATE idempotency_records 
   SET status = 'COMPLETED', response_payload = '{"tx_id": "TX-77881"}'
   WHERE key = 'ORD-9810_step_payment_1';
   ```

## 5. Специфікація подій хореографії (CloudEvents 1.0)

У реактивній хореографії всі повідомлення, що транслюються через Apache Kafka або RabbitMQ, стандартизуються згідно зі специфікацією **CNCF CloudEvents v1.0**.

Для забезпечення суворого порядку обробки подій одного замовлення в Apache Kafka обов'язково налаштовується ключ партиціонування (Partition Key). Як ключ партиції завжди передається `correlationid` (`order_id`). Це гарантує, що всі події конкретного замовлення потрапляють у ту саму партицію брокера й вичитуються консьюмером у суворо послідовному порядку без перегонів.

### Обов'язкові атрибути конверта події

| Поле | Формат | Опис | Призначення в сазі |
|---|---|---|---|
| `specversion` | String | `"1.0"` | Версія стандарту конверта. |
| `id` | UUIDv4 | `"a1b2c3d4-e5f6-7890-abcd-1234567890ab"` | Унікальний ідентифікатор конкретного фізичного повідомлення. |
| `source` | URI-Reference | `"/services/inventory-cluster-eu"` | Джерело походження події. |
| `type` | DNS-Prefix | `"com.shop.order.stock.reserved.v1"` | Доменне ім'я події, що визначає схему поля `data`. |
| `time` | RFC 3339 | `"2026-08-25T14:02:11.450Z"` | Час виникнення факту на вузлі-емітері. |
| `correlationid` | String | `"ORD-2026-9810"` | Наскрізний ідентифікатор інстансу бізнес-процесу. |
| `causationid` | String | `"cmd-reserve-inv-001"` | Ідентифікатор команди або події, яка спричинила цей факт. |
| `traceparent` | W3C Trace | `"00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"` | Наскрізний контекст розподіленого трасування (OpenTelemetry). |

## 6. Класифікатор кодів помилок та поведінковий протокол

Під час координації активностей сервіс-виконавець зобов'язаний явно класифікувати тип помилки, щоб оркестратор або шина подій обрали правильну поведінкову стратегію:

| Категорія помилки | Числовий діапазон | Опис природи збою | Дія рушія координації |
|---|---|---|---|
| `SUCCESS` | `2000–2999` | Операцію успішно виконано в повному обсязі. | Перехід до наступного кроку прямого графа. |
| `RETRYABLE_NETWORK` | `5001–5010` | Мережевий таймаут, тимчасова недоступність бази даних. | Експоненційний повтор із додаванням джитеру до вичерпання ліміту. |
| `BUSINESS_REJECT` | `4001–4020` | Недостатньо коштів на рахунку, залишки на складі вичерпано. | Негайне зупинення прямого ходу та запуск компенсаційного відкату. |
| `FATAL_ARG_ERROR` | `4021–4050` | Помилка валідації схеми JSON, невідомий формат даних. | Зупинення процесу без повторів. Позначення як `FAILED`. |
| `COMPENSATION_ERROR` | `5090–5099` | Збій самої відкатної дії (наприклад, платіжний шлюз недоступний). | Нескінченний повтор або ескалація в чергу ручного втручання (`DLQ`). |

Цей набір правил гарантує, що тимчасові транспортні дефекти мережі лікуються автоматичними повторами без запуску дорогих бізнес-компенсацій, тоді як реальні доменні відмови (наприклад, відсутність товару) негайно переводять систему в режим гарантованого відновлення балансу.
