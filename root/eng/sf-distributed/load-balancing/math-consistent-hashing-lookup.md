# 🧮 Таблиця Maglev: математика рівномірного розподілу зі стійкістю до випадання вузлів

У розподілених системах балансування 4-го рівня (L4) не має можливості координувати стан з'єднань між десятками паралельних машин-балансувальників через мережу: координаційний протокол створив би неприпустимі затримки й швидко перетворився б на вузьке місце системи. Натомість кожен вузол балансувальника мусить незалежно приймати пакети будь-якого TCP-потоку й детерміновано направляти їх на один і той самий цільовий сервер із множини бекендів.

Найпростіший підхід — пряме взяття залишку від ділення хешу на кількість серверів `hash(5-tuple) mod N` — зазнає повної катастрофи при зміні конфігурації. Щойно один із `N` серверів виходить із ладу або додається новий, знаменник змінюється на `N - 1` або `N + 1`. Це призводить до того, що майже 100% існуючих TCP-з'єднань змінюють свій цільовий бекенд, отримують пакет `TCP RST` і миттєво обриваються у клієнтів.

Алгоритм консистентного хешування Maglev розв'язує цю задачу через побудову фіксованої таблиці підстановки розміром `M`, де `M` — велике просте число (`M >> N`, де `N` — кількість доступних бекендів).

### Математична постановка задачі

Нехай маємо множину з `N` працездатних серверів:

```
S = { s₀, s₁, s₂, ..., s_{N-1} }
```

Необхідно побудувати масив підстановки `T` довжиною `M`, де кожен елемент `T[k] ∈ S` для всіх `k ∈ [0, M - 1]`, що задовольняє три фундаментальні математичні вимоги:
1. **Рівномірність навантаження:** кожен сервер `sᵢ` має займати приблизно однакову частку комірок `M / N ± 1`.
2. **Мінімальне порушення зв'язків (Minimal Disruption):** у разі відмови одного сервера або додавання нового, перепризначається лише частка `1 / N` записів таблиці; решта потоків залишаються на своїх первинних бекендах.
3. **Детермінізм генерації:** будь-який балансувальник, маючи однаковий список активних вузлів `S`, обчислює абсолютно ідентичний масив `T` без передачі повідомлень.

### Генерація псевдовипадкових перестановок

Для кожного сервера `sᵢ` генерується детермінована перестановка чисел від `0` до `M - 1`. Для цього застосовуються дві незалежні 32-бітні хеш-функції `h₁` та `h₂`, які обчислюють початкове зміщення (`offset`) та крок стрибка (`skip`):

```
offset[i] = h₁(sᵢ) mod M
skip[i]   = (h₂(sᵢ) mod (M - 1)) + 1
```

Оскільки `M` — просте число, а значення `skip[i]` лежить у діапазоні `1 ≤ skip[i] ≤ M - 1`, число `skip[i]` гарантовано є взаємно простим із `M` (тобто найбільший спільний дільник `НСД(skip[i], M) = 1`).

Послідовність бажаних індексів для сервера `sᵢ` задається арифметичною прогресією за модулем `M`:

```
P[i][j] = (offset[i] + j · skip[i]) mod M      [де j = 0, 1, ..., M - 1]
```

Оскільки `skip[i]` та `M` взаємно прості, елемент `skip[i]` є твірним елементом адитивної групи лишків `ℤ / Mℤ`. Тому послідовність `P[i][0], P[i][1], ..., P[i][M-1]` є повною бієкцією (перестановкою) множини `{0, 1, ..., M - 1}` без жодного повторення значень до завершення повного циклу довжини `M`. Якби число `M` було складеним (наприклад, парним числом `M = 8`, а `skip = 2`), прогресія замкнулася б у підгрупу парних чисел `{0, 2, 4, 6}`, так і не покривши непарні комірки, що порушило б алгоритм заповнення таблиці.

### Алгоритм заповнення таблиці (Round-Robin Filling)

Таблиця `T` розміром `M` заповнюється змагальним круговим обходом усіма доступними серверами:

1. Ініціалізувати всі комірки `T[0 ... M-1] = ∅` (порожні).
2. Ініціалізувати вказівники вибору `next[i] = 0` для всіх `i ∈ [0, N - 1]`.
3. Лічильник заповнених комірок `count = 0`.
4. Доки `count < M`:
   - Для кожного сервера `i` від `0` до `N - 1`:
     - Знайти індекс `c = P[i][next[i]]`.
     - Збільшувати `next[i]`, доки комірка `T[c]` не буде порожньою (`T[c] == ∅`).
     - Записати `T[c] = sᵢ`.
     - Збільшити `next[i] = next[i] + 1` та `count = count + 1`.
     - Якщо `count == M`, перервати процес.

### Покроковий приклад обчислення

Нехай розмір таблиці `M = 7` (просте число), а кількість серверів `N = 3`: `S = { s₀, s₁, s₂ }`.

Припустимо, хеш-функції згенерували такі параметри `offset` та `skip`:

* Сервер `s₀`: `offset = 3`, `skip = 4`
* Сервер `s₁`: `offset = 0`, `skip = 2`
* Сервер `s₂`: `offset = 3`, `skip = 1`

Обчислюємо перестановки `P[i][j]` для кожного сервера:

```
P₀:
P₀[0] = (3 + 0·4) mod 7 = 3 mod 7 = 3
P₀[1] = (3 + 1·4) mod 7 = 7 mod 7 = 0
P₀[2] = (3 + 2·4) mod 7 = 11 mod 7 = 4
P₀[3] = (3 + 3·4) mod 7 = 15 mod 7 = 1
P₀[4] = (3 + 4·4) mod 7 = 19 mod 7 = 5
P₀[5] = (3 + 5·4) mod 7 = 23 mod 7 = 2
P₀[6] = (3 + 6·4) mod 7 = 27 mod 7 = 6
Послідовність P₀ = [3, 0, 4, 1, 5, 2, 6]

P₁:
P₁[0] = (0 + 0·2) mod 7 = 0
P₁[1] = (0 + 1·2) mod 7 = 2
P₁[2] = (0 + 2·2) mod 7 = 4
P₁[3] = (0 + 3·2) mod 7 = 6
P₁[4] = (0 + 4·2) mod 7 = 1
P₁[5] = (0 + 5·2) mod 7 = 3
P₁[6] = (0 + 6·2) mod 7 = 5
Послідовність P₁ = [0, 2, 4, 6, 1, 3, 5]

P₂:
P₂[0] = (3 + 0·1) mod 7 = 3
P₂[1] = (3 + 1·1) mod 7 = 4
P₂[2] = (3 + 2·1) mod 7 = 5
P₂[3] = (3 + 3·1) mod 7 = 6
P₂[4] = (3 + 4·1) mod 7 = 0
P₂[5] = (3 + 5·1) mod 7 = 1
P₂[6] = (3 + 6·1) mod 7 = 2
Послідовність P₂ = [3, 4, 5, 6, 0, 1, 2]
```

**Процес заповнення таблиці `T` довжини 7:**

**Раунд 1:**
* Сервер `s₀`: `P₀[0] = 3` → `T[3]` вільна → `T[3] = s₀`, `next[0] = 1`.
* Сервер `s₁`: `P₁[0] = 0` → `T[0]` вільна → `T[0] = s₁`, `next[1] = 1`.
* Сервер `s₂`: `P₂[0] = 3` (зайнята `s₀`!). `next[2]` зростає до 1 → `P₂[1] = 4` → `T[4]` вільна → `T[4] = s₂`, `next[2] = 2`.
Стан таблиці після раунду 1: `T = [ s₁, ∅, ∅, s₀, s₂, ∅, ∅ ]` (заповнено 3).

**Раунд 2:**
* Сервер `s₀`: `P₀[1] = 0` (зайнята). Пробуємо `P₀[2] = 4` (зайнята). Пробуємо `P₀[3] = 1` → `T[1] = s₀`, `next[0] = 4`.
* Сервер `s₁`: `P₁[1] = 2` → `T[2]` вільна → `T[2] = s₁`, `next[1] = 2`.
* Сервер `s₂`: `P₂[2] = 5` → `T[5]` вільна → `T[5] = s₂`, `next[2] = 3`.
Стан таблиці після раунду 2: `T = [ s₁, s₀, s₁, s₀, s₂, s₂, ∅ ]` (заповнено 6).

**Раунд 3:**
* Сервер `s₀`: `P₀[4] = 5` (зайнята). Пробуємо `P₀[5] = 2` (зайнята). Пробуємо `P₀[6] = 6` → `T[6] = s₀`, `next[0] = 7`.
* Усі 7 комірок заповнено (`count = 7 == M`). Процес завершено.

**Остаточна таблиця маршрутизації:**

```
Індекс k:  0    1    2    3    4    5    6
Сервер T: s₁   s₀   s₁   s₀   s₂   s₂   s₀
```

Підрахунок часток:
* Сервер `s₀`: 3 комірки (індекси 1, 3, 6) → 42.8%
* Сервер `s₁`: 2 комірки (індекси 0, 2) → 28.6%
* Сервер `s₂`: 2 комірки (індекси 4, 5) → 28.6%

### Властивості стійкості та мінімального зміщення

Розглянемо, що відбувається, якщо сервер `s₁` виходить із ладу. Усі сервери перераховують таблицю для множини `S' = { s₀, s₂ }`:
1. Послідовності пріоритетів `P₀` та `P₂` залишаються абсолютно незмінними, оскільки вони залежать лише від імені/адреси самих серверів `s₀` та `s₂`.
2. Комірки, які раніше були захоплені `s₀` та `s₂` у перших раундах, у більшості випадків залишаються за ними.
3. Комірки, які раніше належали `s₁` (індекси 0 та 2), стають вільними і тепер дістаються наступним претендентам із черги `P₀` та `P₂`.
4. Частка перепризначених ключів строго обмежена величиною `1 / N`. Решта `(N - 1) / N` трафіку продовжує обслуговуватися тими самими серверами, що запобігає масовому розриву сесій.

### Підтримка вагових коефіцієнтів (Weighted Consistent Hashing)

У гетерогенних кластерах, де сервери мають різну потужність (наприклад, старі машини з 16 ядрами та нові з 64 ядрами), таблиця Maglev дозволяє легко призначати ваги `wᵢ`.

Для цього кожному серверу `sᵢ` у кожному раунді алгоритму надається право захопити не одну комірку, а `wᵢ` комірок поспіль із власної послідовності `P[i]`. У результаті частка комірок, яку займає сервер `sᵢ` у фінальній таблиці `T`, буде пропорційною значенню `wᵢ / ∑ wₖ`.

### Порівняння з кільцем консистентного хешування (Consistent Hash Ring)

Класичне кільце консистентного хешування (алгоритм Каргера) вимагає розміщення віртуальних вузлів на кільці `[0, 2³² - 1]` та бінарного пошуку цільового сервера за `O(log(N · V))` операцій, де `V` — кількість віртуальних вузлів (зазвичай 100–500 на сервер). Це створює помітні витрати процесорного часу та випадкові звернення до оперативної пам'яті.

Таблиця Maglev досягає часу вибору цільового сервера `O(1)`:

```
flow_hash = MurmurHash3(src_ip, src_port, dst_ip, dst_port, protocol)
index = flow_hash mod M
target_server = T[index]
```

Оскільки `T` є простим плоским масивом у кеші процесора L1/L2, вибір бекенда для кожного пакета займає менше 5–10 наносекунд. Це дозволяє реалізовувати Maglev-хешування безпосередньо у BPF-програмах драйвера мережевої карти (XDP).
