# 🧮 Математична модель затримок, каскадної деградації та витрат пам'яті в сервісній сітці

Впровадження сервісної сітки фундаментально змінює кількісні характеристики розподіленої системи: додавання проксі-вузлів на шляху проходження мережевих пакетів вносить детерміновані та стохастичні затримки, змінює розподіл хвостів затримок (Tail Latency) у графах викликів і вимагає точного розрахунку споживання оперативної пам'яті.

## 1. Адитивна модель затримки одного мережевого виклику (RPC)

У традиційній архітектурі без сервісної сітки вихідний HTTP/gRPC-запит передається безпосередньо з сокета клієнта у фізичну мережу:

```
T_direct = T_client_app + T_net + T_server_app
```

У сервісній сітці з сайдкар-проксі на шляху запиту з'являються дві обов'язкові проміжні ланки: вихідний проксі (Egress Sidecar) на стороні відправника та вхідний проксі (Ingress Sidecar) на стороні отримувача. Повна затримка виклику `T_mesh` розкладається на такі складові:

```
T_mesh = T_client_app + T_egress + T_net + T_ingress + T_server_app
```

Розгорнемо час обробки вихідного сайдкара `T_egress` та вхідного сайдкара `T_ingress`:

```
T_egress  = 2·T_ctx + T_parse + T_route + T_tls_enc + T_queue
T_ingress = 2·T_ctx + T_tls_dec + T_authz + T_parse + T_queue
```

Детерміновані та стохастичні складові моделі мають таку фізичну природу:
* `T_ctx` — затримка перемикання контексту ядра (User Space ↔ Kernel Space) при читанні/запису в сокет loopback (`lo`). Запит двічі перетинає простір ядра на клієнті і двічі на сервері. На сучасних процесорах x86_64 перемикання контексту коштує близько `0.005..0.02` мс.
* `T_parse` — час серіалізації та десеріалізації заголовків HTTP/2 або HTTP/3 і фреймів gRPC. Залежить від розміру заголовків і кількості метаданих (`0.05..0.2` мс).
* `T_tls_enc`, `T_tls_dec` — час криптографічного перетворення симетричного шифрування (AES-128-GCM, AES-256-GCM або ChaCha20-Poly1305) у протоколі mTLS. На процесорах з апаратною підтримкою інструкцій Intel/AMD AES-NI шифрування пакета розміром 4 КБ займає `0.08..0.25` мс.
* `T_route` — час обчислення префіксного дерева або хеш-таблиці маршрутизації RDS (`0.01..0.05` мс).
* `T_authz` — час перевірки локальних списків контролю доступу (RBAC / SPIFFE ID).
* `T_queue` — час очікування в черзі неблокуючого циклу обробки подій (Event Loop) проксі.

Сумарна додаткова затримка `ΔT_overhead`, яку сітка додає до кожного мережевого стрибка (Hop):

```
ΔT_overhead = T_egress + T_ingress
            ≈ 4·T_ctx + 2·T_parse + T_route + T_authz + (T_tls_enc + T_tls_dec) + 2·T_queue
```

При використанні сучасного C++/Rust проксі (Envoy, Linkerd2) на процесорах із підтримкою інструкцій AES-NI базовий накладний час без урахування черг становить:

```
ΔT_base ≈ 0.8..2.5 мс на один міжсервісний виклик
```

## 2. Модель черг у неблокуючому циклі подій проксі (M/G/1)

Сайдкар-проксі використовує пул робочих потоків із неблокуючим мультиплексуванням вводу-виводу (`epoll`/`kqueue`). Якщо вхідний потік запитів має інтенсивність `λ` (запитів/сек) з Пуассонівським розподілом прибуття, а час обслуговування одним воркером є випадковою величиною `S` із загальним розподілом, середнім значенням `E[S] = 1/μ` та дисперсією `Var(S) = σ²`, система моделюється системою масового обслуговування **M/G/1**.

Коефіцієнт завантаження воркера `ρ`:

```
ρ = λ / μ = λ · E[S]
```

За формулою Полячека — Хінчина середній час очікування запиту в черзі `W_q`:

```
W_q = (λ · E[S²]) / (2 · (1 − ρ))
```

Враховуючи, що другий момент часу обслуговування `E[S²] = Var(S) + (E[S])² = σ² + 1/μ²`:

```
W_q = (λ · (σ² + 1/μ²)) / (2 · (1 − λ/μ))     [підстановка E[S²] = σ² + 1/μ²]
    = (ρ · (1 + μ²·σ²)) / (2·μ · (1 − ρ))     [множення на μ та заміна ρ = λ/μ]
```

Для експоненційного часу обслуговування (модель **M/M/1**, де `σ² = 1/μ²`):

```
W_q = ρ / (μ · (1 − ρ))
```

### Вплив варіативності розміру запитів

З формули Полячека — Хінчина видно, що дисперсія часу обробки `σ²` прямо збільшує затримку черги. Якщо в сервісну сітку надходять неоднорідні запити (наприклад, 95% дрібних запитів по 500 байтів і 5% важких запитів по 10 Мегабайтів), коефіцієнт варіації `C_v² = σ² / (E[S])²` різко зростає. 

Навіть при помірному завантаженні процесора `ρ = 0.6` важкі запити блокують цикл обробки подій, що призводить до сплеску затримок для дрібних легких запитів.

### Покрокове виведення нелінійної затримки при зростанні навантаження

Нехай середній час обробки запиту проксі `E[S] = 1/μ = 0.5` мс (`μ = 2000` запитів/с на ядро):

```
W_q = 0.5 / (2000 · (1 − 0.5))       [підстановка для навантаження ρ = 0.5]
    = 0.5 / 1000                      [обчислення знаменника 2000 · 0.5]
    = 0.0005 с                        [ділення чисельника на знаменник]
    = 0.5 мс                          [переведення секунд у мілісекунди]
```

При зростанні навантаження до 80% (`ρ = 0.8`):

```
W_q = 0.8 / (2000 · (1 − 0.8))       [підстановка для навантаження ρ = 0.8]
    = 0.8 / 400                       [обчислення знаменника 2000 · 0.2]
    = 0.0020 с                        [ділення чисельника на знаменник]
    = 2.0 мс                          [переведення секунд у мілісекунди]
```

При критичному навантаженні 95% (`ρ = 0.95`):

```
W_q = 0.95 / (2000 · (1 − 0.95))     [підстановка для навантаження ρ = 0.95]
    = 0.95 / 100                      [обчислення знаменника 2000 · 0.05]
    = 0.0095 с                        [ділення чисельника на знаменник]
    = 9.5 мс                          [переведення секунд у мілісекунди]
```

Графік залежності затримки від завантаження `W_q(ρ)` має вертикальну асимптоту при `ρ → 1`. Це пояснює, чому при перевищенні порогу утилізації процесора сайдкара у 85–90% мережева затримка сітки зростає експоненційно, посилюючи черги на всіх наступних ланках мікросервісного ланцюга.

## 3. Деградація хвостових затримок (Tail Latency) у графах викликів

Клієнтський запит на верхньому рівні (API Gateway) породжує деревоподібний граф залежностей глибиною `d`, що складається з `k` послідовних і паралельних викликів мікросервісів.

Нехай кожен окремий міжсервісний виклик має ймовірність виконання в межах нормативного часу (SLA):

```
P(T_single ≤ SLA) = 1 − p
```

Де `p` — імовірність потрапляння окремого виклику у «хвіст» затримки (наприклад, для 99-го перцентиля `p = 0.01`).

Якщо виклики у графі з `k` компонентів є взаємно незалежними, то ймовірність того, що **весь користувацький запит** виконається без єдиної хвостової затримки:

```
P(T_graph ≤ SLA_total) = (1 − p)ᵏ
```

Імовірність `P_tail_incident`, що користувач відчує хвостову деградацію хоча б на одному сервісі:

```
P_tail_incident = 1 − (1 − p)ᵏ
```

### Розрахунок деградації графа для різних масштабів системи

Застосуємо формулу для `p = 0.01` (99-й перцентиль) при зростанні кількості викликів `k`:

```
P_tail(1)   = 1 − (0.99)¹   = 0.0100   [1% користувачів бачать хвіст]
P_tail(10)  = 1 − (0.99)¹⁰  = 0.0956   [9.56% запитів сповільнюються]
P_tail(30)  = 1 − (0.99)³⁰  = 0.2603   [26.03% запитів сповільнюються]
P_tail(100) = 1 − (0.99)¹⁰⁰ = 0.6340   [63.40% запитів сповільнюються]
```

Цей розрахунок демонструє парадокс розподілених систем: навіть якщо кожен окремий сервіс має високу доступність 99%, загальний запит із 100 викликів деградуватиме у 63.4% випадків. 

Сервісна сітка вирішує цю проблему за допомогою трьох математичних механізмів:
1. **Виявлення викидів (Outlier Detection):** виключення інстансів, чия затримка перевищує `μ + 3·σ`.
2. **Хеджовані запити (Hedged Requests):** надсилання повторного паралельного запиту на інший вузол при перевищенні 95-го перцентиля затримки першого запиту.
3. **Адаптивні ліміти конкурентності (Adaptive Concurrency Limits):** динамічне регулювання розміру вікна запитів на основі формули TCP Vegas / Gradient, що запобігає перевантаженню воркерів бекенда.

## 4. Модель масштабування оперативної пам'яті (Memory Footprint)

Загальний обсяг пам'яті `M_cluster`, який споживає площина даних усього кластера з `N` подів, що обслуговують `S` різних сервісів:

```
M_cluster = ∑_{i=1}^{N} M_proxy(i)
```

Обсяг оперативної пам'яті одного сайдкар-проксі `M_proxy`:

```
M_proxy = M_base + M_routes(S) + M_clusters(S) + M_endpoints(N) + M_connpool
```

Де:
* `M_base` — базовий розмір процесу проксі в пам'яті (бінарний код, структури ядра, буфери `epoll`) ≈ `30..50` МБ.
* `M_routes` — розмір таблиць маршрутизації RDS = `S · S_route_entry` (де `S_route_entry ≈ 2..5` КБ).
* `M_clusters` — опис кластерів CDS = `S · S_cluster_entry` (де `S_cluster_entry ≈ 4..8` КБ).
* `M_endpoints` — перелік усіх кінцевих точок EDS = `N · S_endpoint_entry` (де `S_endpoint_entry ≈ 1..2` КБ).
* `M_connpool` — буфери активних TCP-з'єднань, TLS-сесій і пулів потоків = `C_active · S_buffer`.

### Порівняння моделей повної сітки (Full Mesh) та обмеженої видимості

У наївній конфігурації за замовчуванням (Full Mesh) кожен проксі підписується на всі сервіси й усі endpoints кластера. Тоді сумарна пам'ять кластера `M_total`:

```
M_total = N · (M_base + S · (S_route + S_cluster) + N · S_endpoint)
        = N · M_base + N·S · S_meta + N² · S_endpoint
```

Член `N² · S_endpoint` призводить до **квадратичного зростання** споживання пам'яті:

```
Розрахунок для великого кластера з N = 5000 подів та S = 500 сервісів:
M_endpoints = 5000 · (5000 · 1.5 КБ) = 5000 · 7.5 МБ = 37.5 ГБ (лише на таблиці EDS!)
M_total ≈ 5000 · (40 МБ + 500 · 10 КБ + 7.5 МБ)
        = 5000 · 52.5 МБ = 262.5 Гігабайтів RAM
```

При переході до селективної видимості через ресурси обмеження просторів імен (`Istio Sidecar CRD`) або переходу на безсайдкарний **Ambient Mesh (ztunnel)** кожен проксі завантажує лише `S_local` суміжних сервісів (`S_local ≪ S`):

```
M_ambient_node = M_base_daemon + N_local_pods · S_l4_state
```

Це скорочує споживання пам'яті кластера з квадратичної складності `O(N²)` до строго лінійної `O(N)`, знижуючи загальні витрати інфраструктури на 70–85%.
