# 📜 Історія еволюції топологій пліток: від пласких списків Xerox PARC до Astrolabe, Cassandra та Consul

У 1987 році група дослідників науково-дослідного центру Xerox PARC у Пало-Альто (Алан Демерс, Ден Грін, Карл Гаузер, Вес Айріш, Джон Ларсон, Скотт Шенкер, Говард Стерджис, Ден Свайнгарт та Даг Террі) опублікувала фундаментальну працю про епідемічні алгоритми для підтримки узгодженості бази даних Clearinghouse. У тогочасній архітектурі локальної мережі Ethernet корпоративного кампусу всі сервери перебували в єдиному широкомовному домені з симетричними затримками передачі в межах кількох мілісекунд. Демерс із колегами сформулювали класичну модель однорідного випадкового вибору (*Uniform Random Gossip*): кожен вузол володіє повним плаським списком усіх учасників системи (`N`) і в кожному раунді обирає партнера для обміну даними строго рівномірно з імовірністю `1 / (N - 1)`.

Ця проста топологічна модель повного зв'язку бездоганно функціонувала для кількох сотень машин у межах одного офісного приміщення. Однак на початку 1990-х років корпоративні мережі почали об'єднувати географічно віддалені філії через повільні телефонні та супутникові канали глобальної мережі (WAN, англ. *Wide Area Network*).

## 1990-ті: Відкриття бімодального колапсу та протокол pbcast

У Корнелльському університеті дослідницька група під керівництвом Кеннета Бірмана розробляла надійні широкомовні системи для розподілених фінансових бірж та центрів керування повітряним рухом (проект Isis). Спроба застосувати класичний епідемічний алгоритм Демерса у глобальних мережах призвела до несподіваної кризи продуктивності, яку Бірман описав у 1999 році як явище «бімодальної збіжності» (*Bimodal Multicast / pbcast*).

```
+-------------------------------------------------------------------------------+
|  ПРОБЛЕМА ПЛАСКОГО GOSSIP У ГЛОБАЛЬНІЙ МЕРЕЖІ (WAN 1990-х)                   |
|                                                                               |
|  Кампус Нью-Йорк (LAN: 10 Мбіт/с)            Кампус Лондон (LAN: 10 Мбіт/с)   |
|  [ Вузол A ] <--- 0.5 мс ---> [ Вузол B ]    [ Вузол C ] <--- 0.5 мс ---> [D]|
|          \                                     /                              |
|           \                                   /                               |
|            =====> [ Трансатлантичний канал ] <=====                           |
|                   Затримка: 120 мс, Пропускна здатність: 64 Кбіт/с            |
|                   РЕЗУЛЬТАТ: 90% трафіку пліток іде через вузький WAN!        |
+-------------------------------------------------------------------------------+
```

Коли плаский протокол запускався на кластері з 500 серверів, розділених між Нью-Йорком та Лондоном, випадковий вибір цілі призводив до того, що половина всіх дейтаграм намагалася пройти крізь трансатлантичний канал пропускною здатністю 64 Кбіт/с із затримкою 120 мс. Канал миттєво переповнювався, втрати пакетів досягали 40%, а затримка поширення пліток зростала в геометричній прогресії.

Бірман, Марк Гайден та їхні співавтори запропонували першу топологічно-чутливу модифікацію:
1. Вузол віддає перевагу партнерам у локальній підмережі з імовірністю `0.9`.
2. Лише з імовірністю `0.1` обирається випадковий вузол із віддаленого сегмента.
3. Це зберегло експоненційне поширення інформації, зменшивши навантаження на дорогі зовнішні канали у дев'ять разів.

## 2000-ті: Дерева зон Astrolabe та криза обсягу пам'яті

На початку 2000-х років поява масштабних хмарних інфраструктур і peer-to-peer мереж виявила інше фундаментальне обмеження повного графа: кожен вузол мусив зберігати в оперативній пам'яті повний список адрес і станів усіх інших `N` учасників. Для систем на 100 000 серверів підтримання повного каталогу членства на дешевих машинах вимагало гігабайтів пам'яті та генерувало гігабайти службових оновлень щохвилини.

У 2003 році Робберт ван Ренессе, Кеннет Бірман та Вернер Фогельс (який згодом став технічним директором Amazon) опублікували систему **Astrolabe**.

```
                           [ Глобальна зона / ]
                                  ▲       ▲
                                 /         \
              [ Зона US-East /us-east ]   [ Зона EU-West /eu-west ]
                     ▲         ▲                  ▲         ▲
                    /           \                /           \
             [ Стійка R1 ]  [ Стійка R2 ]  [ Стійка R3 ]  [ Стійка R4 ]
              (8 серверів)   (8 серверів)   (8 серверів)   (8 серверів)
```

Astrolabe запропонував структурувати систему у вигляді ієрархічного дерева зон:
- Вузли пліткують безпосередньо лише всередині свого найнижчого листка (наприклад, однієї серверної стійки).
- На кожному рівні ієрархії вузли обчислюють агреговані зведення (наприклад, середнє завантаження процесора, кількість живих серверів, версію схеми) через спеціальні SQL-подібні агрегатні функції.
- На вищі рівні передаються виключно стислі зведені дані зон, завдяки чому споживання пам'яті та мережевий трафік на один вузол скоротилися з `O(N)` до `O(log N)`.

Одночасно для однорангових однорідних P2P-мереж дослідники розробили випадкові оверлеї на базі служб вибірки сусідів (*Peer Sampling Service*): алгоритми **SCAMP** (2001), **Cyclon** (2005) та **HyParView** (2007). Вони довели, що навіть без жорсткої ієрархії вузол може підтримувати частковий список сусідів фіксованого розміру (наприклад, 10–20 адрес), а динамічне перемішування зв'язків утворює випадковий регулярний граф із високим коефіцієнтом розширення (*Expander Graph*), який неможливо розділити на ізольовані острови навіть за масових аварій.

## 2010-ті: Промисловий ренесанс у Cassandra та Consul

Коли компанія Amazon опублікувала опис архітектури сховища Dynamo у 2007 році, епідемічні протоколи остаточно перейшли з академічних лабораторій у промислові дата-центри. Створена на базі ідей Dynamo та BigTable розподілена NoSQL-база даних **Apache Cassandra** зіткнулася з проблемою розгортання в кількох центрах обробки даних одночасно.

Для вирішення проблеми затримок інженери Cassandra реалізували топологічно-адаптивний компонент `Gossiper`, підсилений детекторами `EndpointSnitch` (такими як `RackInferringSnitch` та `PropertyFileSnitch`):
- Кожен сервер раз на секунду ініціює раунд пліток.
- З імовірністю `0.9` сервер обирає випадкового сусіда зі свого локального дата-центру.
- З імовірністю `0.1` сервер надсилає дейтаграму випадковому представнику віддаленого дата-центру.
- Якщо у віддаленому дата-центрі є живі вузли, але вони давно не виходили на зв'язок, `Gossiper` примусово обирає так звані «вузли-насіння» (*seed nodes*) для гарантованого пробиття міжрегіональних тунелів.

У 2014 році компанія HashiCorp випустила інструменти **Serf** та **Consul**, створені Арманом Дадгаром та Мітчеллом Хашімото на базі протоколу SWIM. Вони розділили топологію на два незалежні шари:
1. **LAN Serf Pool:** Повнозв'язний оверлей у межах одного дата-центру або стійки, де тисячі агентів обмінюються станом через швидкий UDP з періодом 200–500 мс.
2. **WAN Serf Pool:** Окремий федеративний пул, у якому беруть участь виключно сервери-делегати Consul (по 3–5 машин на регіон). Вони використовують більші тайм-аути (1000–3000 мс) і транслюють лише критичні події між регіонами.

Ця двошарова федеративна топологія стала стандартом для виявлення сервісів у сучасних хмарних кластерах, захищаючи дорогі міжконтинентальні канали від широкомовного шторму дейтаграм.
