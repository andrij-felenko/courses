# 📋 Специфікація та конфігурація механізмів захисту від навали на кеш

Для забезпечення стійкості розподіленої системи компоненти захисту від навали на кеш потребують точного узгодження протоколів взаємодії, форматів метаданих та інфраструктурних директив проксі-серверів.

## Структура метаданих кешованого запису

Усі розподілені та локальні кеші, що підтримують алгоритми завчасного оновлення (XFetch та Stale-While-Revalidate), зберігають дані у вигляді бінарного або серіалізованого конверта.

Збереження сирого бінарного значення без часових міток позбавляє систему можливості приймати динамічні рішення про оновлення. Тому запис завжди огортається в структуру з метаданими:

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `payload` | `bytes / string` | Корисне навантаження (серіалізований об'єкт DTO). |
| `created_at` | `int64` | Час створення запису (UNIX epoch у мілісекундах). |
| `soft_ttl_ms` | `int64` | Тривалість м'якого життя до початку фонового оновлення. |
| `hard_ttl_ms` | `int64` | Тривалість жорсткого життя до повного видалення зі сховища. |
| `delta_ms` | `float64` | Виміряна тривалість останнього розрахунку значення у мілісекундах. |
| `fence_token` | `int64` | Монотонно зростаючий лічильник версії для захисту від гонитви запису. |

### Серіалізація та накладні витрати пам'яті

Для мінімізації накладних витрат у високонавантажених сервісах рекомендується використовувати компактні бінарні формати серіалізації (Protocol Buffers, FlatBuffers або MessagePack) замість текстового JSON.

Поле `delta_ms` вимірюється на стороні вузла-виконавця як різниця монотонного системного годинника (`CLOCK_MONOTONIC`) між початком звернення до первинного джерела та моментом отримання повної відповіді. Це захищає метрику від стрибків системного часу, спричинених синхронізацією через протокол NTP.

Поле `fence_token` генерується централізованим лічильником або монотонною послідовністю транзакцій бази даних. Воно запобігає ситуації «пізнього запису» (*late write*), коли повільний фоновий потік намагається перезаписати кеш застарілими даними після того, як інший потік уже зберіг свіжішу версію.

## Протокол оренди замка в Redis (Distributed Lock Lease)

Для запобігання навалі на рівні кластера застосовується протокол оренди розподіленого замка через атомарні Lua-скрипти.

Використання простих неатомарних команд `GET` і `SET` створює вікна стану перегонів. Тому всі операції управління замком виконуються через атомарне виконання скриптів на стороні рушія Redis.

### 1. Атомарне захоплення замка (Acquire Lock)

Захоплення виконується з обов'язковим зазначенням унікального ідентифікатора клієнта (`token`) та ліз-таймауту в мілісекундах:

```lua
-- KEYS[1]: ключ замка (наприклад, "lock:cache:product:7821")
-- ARGV[1]: унікальний токен клієнта (UUID + ID горутини/потоку)
-- ARGV[2]: таймаут оренди в мілісекундах (lease TTL, наприклад 5000)

local acquired = redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2])
if acquired then
    return 1
else
    return 0
end
```

Якщо ключ замка вже існує, Redis повертає `nil`, і скрипт завершується з результатом `0`. Клієнтський застосунок, отримавши `0`, переходить у режим очікування або повертає попереднє застаріле значення.

### 2. Безпечне подовження оренди (Heartbeat Lease Renewal)

Якщо обчислення складного агрегату затримується через блокування в СУБД або мережеві затримки, фоновий таймер власника подовжує термін оренди, обов'язково перевіряючи збіг токена:

```lua
-- KEYS[1]: ключ замка
-- ARGV[1]: токен клієнта
-- ARGV[2]: додатковий час оренди в мілісекундах

if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
else
    return 0
end
```

Перевірка значення `GET(key) == token` є критично важливою: якщо термін попередньої оренди вже сплив і інший вузол кластера встиг захопити цей замок зі своїм токеном, скрипт відмовить у подовженні, запобігаючи несанкціонованому перехопленню чужого блокування.

### 3. Атомарне звільнення замка (Safe Release)

Звільнення гарантує, що потік не видалить замок чужого процесу, якщо термін його власної оренди закінчився під час виконання роботи:

```lua
-- KEYS[1]: ключ замка
-- ARGV[1]: токен клієнта

if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

## HTTP-директиви кешування (RFC 5861)

Клієнти, шлюзи API та мережі доставки контенту (CDN) керують навалою на кеш за допомогою стандартних розширень заголовка `Cache-Control`, визначених у специфікації RFC 5861.

Ці директиви дозволяють проміжним проксі-серверам розв'язувати конфлікт між високою швидкістю відповіді та строгістю актуальності контенту:

| Директива | Приклад значення | Призначення |
| :--- | :--- | :--- |
| `max-age` | `max-age=60` | Номінальний час свіжості кешу (у секундах). |
| `stale-while-revalidate` | `stale-while-revalidate=300` | Часове вікно, протягом якого дозволено миттєво повертати старий кеш клієнту, поки у фоні виконується асинхронний запит за свіжими даними. |
| `stale-if-error` | `stale-if-error=86400` | Часове вікно, протягом якого дозволено повертати застарілий кеш, якщо бекенд відповідає помилкою (5xx) або таймаутом. |

### Повний приклад HTTP-відповіді з діагностичними заголовками

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: public, max-age=120, stale-while-revalidate=600, stale-if-error=86400
ETag: "w/9b1c5d82f3a"
Age: 145
X-Cache-Status: STALE-UPDATING
X-Cache-Lookup: HIT from edge-proxy-04
```

У наведеному прикладі об'єкт має вік 145 секунд, що перевищує `max-age=120`. Проте, оскільки 145 входить у вікно `stale-while-revalidate` (120 + 600 = 720 секунд), крайовий сервер негайно повертає наявний об'єкт із прапорцем `STALE-UPDATING` і паралельно запускає запит до джерела даних.

## Конфігураційні директиви зворотних проксі-серверів

### 1. Nginx: блокування та дедуплікація запитів

Nginx підтримує вбудоване злиття однакових запитів під час промаху кешу через директиву `proxy_cache_lock`.

Коли вмикається `proxy_cache_lock`, тільки перший запит з однаковим ключем кешування пропускається до бекенд-сервісу. Усі наступні паралельні запити очікують на появу даних у кеші або завершення таймауту:

```nginx
http {
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=BACKEND_CACHE:64m 
                     max_size=10g inactive=60m use_temp_path=off;

    server {
        listen 80;

        location /api/ {
            proxy_pass http://backend_upstream;
            proxy_cache BACKEND_CACHE;
            proxy_cache_key "$request_method$scheme$host$request_uri";

            # Вмикає злиття однакових запитів: лише один запит іде на бекенд
            proxy_cache_lock on;
            
            # Максимальний час очікування для підписників рейсу
            proxy_cache_lock_timeout 2s;
            
            # Якщо лідер не зберіг кеш за 2 с — наступний запит іде в бекенд
            proxy_cache_lock_age 2s;

            # Віддавати старий кеш під час фонового оновлення та аварій
            proxy_cache_use_stale updating error timeout invalid_header http_500 http_502 http_503;
            
            # Додавання статусу кешу у відповідь
            add_header X-Cache-Status $upstream_cache_status;
        }
    }
}
```

Директива `proxy_cache_use_stale updating` є критично важливою: вона дозволяє Nginx негайно повертати попередню версію файлу тим клієнтам, які прийшли в момент оновлення кешу лідером, повністю усуваючи затримку очікування.

### 2. Varnish Cache (VCL): пільговий період (Grace Mode)

У кешувальному проксі Varnish керування навалою здійснюється через спеціальні пільгові інтервали `beresp.grace` та `beresp.keep` мовою VCL (Varnish Configuration Language):

```vcl
vcl 4.1;

sub vcl_backend_response {
    # Номінальний термін життя кешу
    set beresp.ttl = 2m;

    # Пільговий період (Grace): віддавати старі дані до 10 хвилин, 
    # поки перший запит асинхронно оновлює кеш на бекенді
    set beresp.grace = 10m;

    # Зберігати об'єкт у пам'яті 24 години для обслуговування при падінні бекенду
    set beresp.keep = 24h;
}

sub vcl_hit {
    if (obj.ttl >= 0s) {
        # Свіжий об'єкт — миттєва віддача
        return (deliver);
    }
    if (obj.ttl + obj.grace > 0s) {
        # Об'єкт застарів, але діє Grace: віддаємо клієнту застаріле значення,
        # а Varnish автоматично генерує асинхронний фоновий запит на оновлення
        return (deliver);
    }
    # Об'єкт повністю вичерпав Grace-період — прямуємо за свіжими даними
    return (restart);
}
```

### 3. Envoy Proxy: Request Coalescing Filter

У сервісній сітці (Service Mesh) Envoy запобігає навалі між мікросервісами за допомогою фільтра кешування HTTP:

```yaml
name: envoy.filters.http.cache
typed_config:
  "@type": type.googleapis.com/envoy.extensions.filters.http.cache.v3.CacheConfig
  typed_config:
    "@type": type.googleapis.com/envoy.extensions.cache.simple_http_cache.v3.SimpleHttpCacheConfig
  allowed_vary_headers:
    - accept-encoding
    - accept-language
  key_creator_params:
    exclude_scheme: false
    exclude_host: false
  max_cache_entry_size: 1048576 # 1 MB
```

Envoy автоматично об'єднує запити до upstream-кластерів за однаковим URI та заголовками, запобігаючи перевантаженню внутрішніх сервісів системи.

## Моніторинг та телеметрія навали на кеш

Для завчасного виявлення ризику навали та оцінки ефективності алгоритмів захисту система експортує стандартизований набір метрик у форматі Prometheus / OpenTelemetry:

| Метрика | Тип | Опис та інтерпретація |
| :--- | :--- | :--- |
| `cache_stampede_in_flight_gauge` | `Gauge` | Кількість рейсів, що одночасно виконуються в Single-Flight. Різке зростання свідчить про сповільнення первинного джерела даних. |
| `cache_stampede_xfetch_total` | `Counter` | Кількість завчасних оновлень, ініційованих алгоритмом XFetch до вичерпання TTL. |
| `cache_stampede_lock_wait_seconds` | `Histogram` | Час, проведений потоками в очікуванні звільнення розподіленого замка або завершення лідера. |
| `cache_stampede_stale_hits_total` | `Counter` | Кількість відповідей, виданих клієнтам із застарілого кешу у вікні Stale-While-Revalidate. |

Якщо метрика `cache_stampede_in_flight_gauge` перевищує критичний поріг (наприклад, понад 100 паралельних рейсів на один інстанс), система повинна автоматично задіяти механізм скидання навантаження (Load Shedding), відкидаючи низькопріоритетні виклики до відновлення нормальної продуктивності бази даних.

Параметри захисту від навали на кеш повинні ретельно калібруватися під характеристики робочого навантаження системи:

| Параметр | Рекомендоване значення | Одиниці | Вплив заниження | Вплив завищення |
| :--- | :--- | :--- | :--- | :--- |
| `beta` (XFetch) | `1.0 – 1.5` | Коефіцієнт | Зростає ризик синхронного промаху. | Кеш оновлюється занадто рано, зростає постійний QPS. |
| `ttl_jitter_pct` | `10% – 20%` | Відсотки | Синхронізовані хвилі згоряння ключів. | Складно передбачити точний час інвалідації. |
| `lock_lease_timeout` | `2.0 · δ` | Секунди | Передчасне зняття замка та стан гонитви. | Тривале зависання очікувачів у разі падіння лідера. |
| `singleflight_timeout` | `2.0 – 5.0` | Секунди | Відхилення швидких клієнтів. | Масове накопичення завислих горутин/потоків. |
| `stale_grace_window` | `3 · ttl` | Секунди | Клієнти бачать затримку під час промаху. | Клієнти занадто довго бачать застарілі дані. |

## Інтеграція зі стратегіями деградації сервісу

У разі повної відмови первинного джерела даних (наприклад, аварії кластера бази даних) рушій кешу переходить у режим захисної деградації:
1. Забороняється видалення застарілих ключів із кешу, навіть якщо їхній `Hard TTL` повністю вичерпано (політика *Fail-Open Caching*).
2. Усі вхідні клієнтські виклики обслуговуються наявними застарілими копіями з додаванням попереджувального HTTP-заголовка `Warning: 110 "Response is Stale"`.
3. Спроби оновлення даних блокуються запобіжником (Circuit Breaker), що захищає базу даних від штурму запитів у момент її відновлення після перезапуску.
