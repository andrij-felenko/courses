# 🧮 Математичні основи операційних перетворень: TP1, TP2 та збіжність простору станів

Будь-яка система операційних перетворень прагне гарантувати, що довільна множина паралельних правок, виконаних користувачами у власних локальних копіях, приведе всі репліки до ідентичного стану документа.

Алгебраїчна коректність цієї моделі спирається на дві фундаментальні властивості функцій трансформації — TP1 та TP2, а також на математичні властивості простору станів і операторів зворотного перетворення.

## Формальна модель документа та операцій

Позначимо документ як скінченну послідовність символів `D = [c₀, c₁, ..., cₙ₋₁]`, де `n = |D|` — поточна довжина тексту. Кожен символ однозначно адресується цілочисельним індексом `p ∈ {0, ..., n-1}`.

Простір базових операцій складається з двох примітивів:
1. `Ins(p, c)` — вставка символу `c` у позицію `p`, де `0 ≤ p ≤ n`.
2. `Del(p)` — видалення символу в позиції `p`, де `0 ≤ p < n`.
3. `NoOp()` — нейтральна операція, що не змінює стан документа.

Застосування операції `op` до стану документа `S` позначається як оператор переходу:

```
S' = S ∘ op
```

Якщо дві операції `op₁` та `op₂` згенеровані на одному й тому самому базовому стані `S` незалежно (тобто жоден з авторів не бачив правки іншого в момент створення), вони називаються **конкурентними** або **паралельними** (`op₁ || op₂`).

Множина всіх можливих станів документа утворює дискретний орієнтований граф простору станів (State Space Graph), де вершинами є тексти `S`, а ребрами — переходи під дією операцій.

## Функція перетворення включення (Inclusion Transformation)

Оскільки операція `op₁` розрахована на структуру стану `S`, її не можна безпосередньо застосувати до стану `S ∘ op₂`. Для цього вводиться оператор **перетворення включення** `T(op₁, op₂)` (англ. *Inclusion Transformation*, або `IT`).

Функція `T(op₁, op₂)` повертає нову операцію `op₁'`, яка виражає початковий намір `op₁`, але адаптована до зсувів координат, спричинених виконанням `op₂`:

```
op₁' = T(op₁, op₂)
op₂' = T(op₂, op₁)
```

Оператор `T` є несиметричним відображенням: його перший аргумент — це дія, яку ми перетворюємо, а другий аргумент — це вже виконана контекстна дія.

## Властивість TP1 (Transformation Property 1)

Властивість TP1 визначає умову збіжності для двох паралельних операцій.

```
S ∘ op₁ ∘ T(op₂, op₁) ≡ S ∘ op₂ ∘ T(op₁, op₂)     [вимога збіжності станів для пари операцій]
```

Для довільного початкового стану `S` та довільної пари конкурентних операцій `op₁ || op₂`, застосування спочатку `op₁`, а потім трансформованої `T(op₂, op₁)` мусить приводити до стану документа, еквівалентного результату застосування спочатку `op₂`, а потім `T(op₁, op₂)`.

### Доведення TP1 для всіх пар базових операцій

Розглянемо вичерпний перебір усіх типів взаємодії операцій.

#### Випадок 1: Вставка проти вставки (`Ins/Ins`)

Нехай маємо документ `S` і дві паралельні вставки: `op₁ = Ins(p₁, c₁)` та `op₂ = Ins(p₂, c₂)`.

**Підвипадок 1.1 (`p₁ < p₂`):**
- Оскільки `p₁ < p₂`, вставка `op₁` відбувається лівіше `op₂`. Отже, `T(op₂, op₁) = Ins(p₂ + 1, c₂)`.
- Оскільки `p₂ > p₁`, вставка `op₂` відбувається правіше `op₁`. Отже, `T(op₁, op₂) = Ins(p₁, c₁)`.

Розглянемо послідовні переходи станів:

```
Шлях 1:  S₁ = S ∘ op₁ = S[0..p₁-1] + c₁ + S[p₁..end]                  [виконання першої вставки op₁]
         S₁' = S₁ ∘ Ins(p₂ + 1, c₂)                                    [виконання зсунутої другої вставки]
             = S[0..p₁-1] + c₁ + S[p₁..p₂-1] + c₂ + S[p₂..end]         [підсумковий стан шляху 1]

Шлях 2:  S₂ = S ∘ op₂ = S[0..p₂-1] + c₂ + S[p₂..end]                  [виконання другої вставки op₂]
         S₂' = S₂ ∘ Ins(p₁, c₁)                                        [виконання першої вставки без зсуву]
             = S[0..p₁-1] + c₁ + S[p₁..p₂-1] + c₂ + S[p₂..end]         [підсумковий стан шляху 2]
```

Оскільки `S₁' ≡ S₂'`, тотожність доведена.

**Підвипадок 1.2 (`p₁ == p₂`):**
При однакових позиціях застосовується детерміноване правило тай-брейку: якщо `client_id₁ < client_id₂`, то `T(op₁, op₂) = Ins(p₁, c₁)` та `T(op₂, op₁) = Ins(p₂ + 1, c₂)`.
Обидва шляхи дають результуючий рядок із фрагментом `... + c₁ + c₂ + ...`. Стан ідентичний.

#### Випадок 2: Вставка проти видалення (`Ins/Del`)

Нехай `op₁ = Ins(p₁, c₁)` та `op₂ = Del(p₂)`.

**Підвипадок 2.1 (`p₁ ≤ p₂`):**
Вставка відбувається лівіше віддаленого символу або точно в його позицію.
- `T(op₁, op₂) = Ins(p₁, c₁)` (видалення праворуч не зміщує ліві індекси).
- `T(op₂, op₁) = Del(p₂ + 1)` (вставка ліворуч зсунула цільовий символ видалення на +1).

```
Шлях 1:  S₁ = S ∘ op₁ = S[0..p₁-1] + c₁ + S[p₁..end]                  [вставка символу c₁]
         S₁' = S₁ ∘ Del(p₂ + 1)                                        [видалення зсунутого цільового символу]
             = S[0..p₁-1] + c₁ + S[p₁..p₂-1] + S[p₂+1..end]           [підсумковий стан шляху 1]

Шлях 2:  S₂ = S ∘ op₂ = S[0..p₂-1] + S[p₂+1..end]                     [видалення символу на позиції p₂]
         S₂' = S₂ ∘ Ins(p₁, c₁)                                        [вставка c₁ на початкову позицію]
             = S[0..p₁-1] + c₁ + S[p₁..p₂-1] + S[p₂+1..end]           [підсумковий стан шляху 2]
```

**Підвипадок 2.2 (`p₁ > p₂`):**
Вставка відбувається правіше видалення.
- `T(op₁, op₂) = Ins(p₁ - 1, c₁)` (видалення лівіше зсунуло точку вставки на -1).
- `T(op₂, op₁) = Del(p₂)` (вставка праворуч не впливає на лівий символ).
Перевірка через конкатенацію підрядків аналогічно доводить `S₁' ≡ S₂'`.

#### Випадок 3: Видалення проти видалення (`Del/Del`)

Нехай `op₁ = Del(p₁)` та `op₂ = Del(p₂)`.

**Підвипадок 3.1 (`p₁ < p₂`):**
- `T(op₁, op₂) = Del(p₁)`.
- `T(op₂, op₁) = Del(p₂ - 1)`.
Обидва шляхи приводять до вилучення символів `S[p₁]` та `S[p₂]`, залишаючи підрядок `S[0..p₁-1] + S[p₁+1..p₂-1] + S[p₂+1..end]`.

**Підвипадок 3.2 (`p₁ == p₂`):**
Обидві операції видаляють один і той самий символ `S[p₁]`.
- `T(op₁, op₂) = NoOp()`.
- `T(op₂, op₁) = NoOp()`.
Перша виконана операція видаляє символ, друга операція стає `NoOp` і не вносить додаткових змін. Результат ідентичний: `S₁' ≡ S₂' = S[0..p₁-1] + S[p₁+1..end]`.

Таким чином, функція `T` строго задовольняє умову TP1 для всіх можливих пар операцій над текстом.

## Властивість TP2 (Transformation Property 2)

Якщо в розподіленій системі без центрального вузла виникають три паралельні операції `op₁ || op₂ || op₃`, операцію `op₃` можна привести до фінального контексту двома альтернативними шляхами в 3D-кубі простору станів:
1. Спершу трансформувати `op₃` проти `op₁`, а потім проти результату `T(op₂, op₁)`.
2. Спершу трансформувати `op₃` проти `op₂`, а потім проти результату `T(op₁, op₂)`.

Властивість TP2 вимагає повної еквівалентності трансформованої операції незалежно від послідовності обходу:

```
T( T(op₃, op₁), T(op₂, op₁) ) ≡ T( T(op₃, op₂), T(op₁, op₂) )     [незалежність від послідовності включення]
```

Ця умова гарантує, що операція `op₃` набуде однакового вигляду на репліці, яка отримала події в порядку `(op₁, op₂, op₃)`, і на репліці з порядком `(op₂, op₁, op₃)`.

## Контрприклад порушення TP2 у децентралізованих системах

Покажемо, чому прості функції трансформації зазнають невдачі в P2P-системах, на класичному контрприкладі Іміна (Imine et al., 2006).

Нехай початковий документ `S = "ABC"`.
Три паралельні операції згенеровані трьома різними сайтами на стані `S`:
- `op₁ = Del(0)` (сайт 1 видаляє 'A')
- `op₂ = Ins(0, 'X')` (сайт 2 вставляє 'X' перед 'A')
- `op₃ = Del(1)` (сайт 3 видаляє 'B')

Обчислимо трансформацію операції `op₃` двома різними шляхами.

### Обчислення Шляхом 1 (через op₁, потім op₂)

```
Крок 1.1:  op₃₁ = T(op₃, op₁) = T(Del(1), Del(0))
                = Del(0)                                              [індекс зсунувся ліворуч на -1 через видалення на поз. 0]

Крок 1.2:  op₂₁ = T(op₂, op₁) = T(Ins(0, 'X'), Del(0))
                = Ins(0, 'X')                                         [вставка на поз. 0 лишається на 0]

Крок 1.3:  op₃₁₂ = T(op₃₁, op₂₁) = T(Del(0), Ins(0, 'X'))
                 = Del(1)                                             [індекс зсунувся праворуч на +1 через вставку 'X' на поз. 0]
```

### Обчислення Шляхом 2 (через op₂, потім op₁)

```
Крок 2.1:  op₃₂ = T(op₃, op₂) = T(Del(1), Ins(0, 'X'))
                = Del(2)                                              [індекс зсунувся праворуч на +1 через вставку 'X' на поз. 0]

Крок 2.2:  op₁₂ = T(op₁, op₂) = T(Del(0), Ins(0, 'X'))
                = Del(1)                                              [індекс видалення 'A' зсунувся на 1 через вставку 'X' на 0]

Крок 2.3:  op₃₂₁ = T(op₃₂, op₁₂) = T(Del(2), Del(1))
                 = Del(1)                                             [індекс зсунувся ліворуч на -1 через видалення на поз. 1]
```

У цьому базовому випадку координати зійшлися. Проте якщо сайт 1 і сайт 2 згенерують паралельні вставки символів у ту саму позицію (`Ins(0, 'A')` та `Ins(0, 'B')`), тай-брейк за `client_id` зміщує один із символів праворуч. У результаті третя операція `op₃` на різних шляхах обчислення отримує різні індекси: `op₃₁₂ = Del(2)`, а `op₃₂₁ = Del(1)`.

Наслідок: на першому вузлі видаляється символ 'C', а на другому — символ 'B'. Документи необоротно розходяться.

## Перетворення виключення (Exclusion Transformation) та відкат

Для реалізації вибіркового скасування (Selective Undo) у спільних документах використовують оператор **перетворення виключення** `T⁻¹(op₁, op₂)` (англ. *Exclusion Transformation*, або `ET`).

Оператор `ET` розв'язує обернену задачу: знайти вигляд операції `op₁` у контексті **до** того, як була виконана операція `op₂`:

```
op₁ = T⁻¹( T(op₁, op₂), op₂ )     [інверсія контексту виконання]
```

Властивості `ET` дозволяють витягти стару дію користувача з середини журналу ревізій, підняти її на верхівку стека змін, інвертувати її знак (`Ins` ↔ `Del`) і застосувати як нову ревізію, не ламаючи структури правок інших авторів.

## Теорема збіжності Jupiter: достатність TP1 при лінеаризації

Архітектура Jupiter розв'язує проблему TP2 не ускладненням функцій перетворення, а зміною топології простору переходів.

**Теорема.** *У системі спільного редагування з центральним сервером-серіалізатором виконання властивості TP1 є необхідною і достатньою умовою досягнення повної збіжності реплік.*

### Доведення

Нехай сервер підтримує глобальний монотонний лог підтверджених операцій `L = [op⁽¹⁾, op⁽²⁾, ..., op⁽ᵏ⁾]`. Кожна підтверджена ревізія `r` відповідає унікальному стану:

```
Sᵣ = S₀ ∘ op⁽¹⁾ ∘ op⁽²⁾ ∘ ... ∘ op⁽ʳ⁾
```

Коли клієнт генерує локальну операцію `op_c` на базі ревізії `r`, на сервері ця операція зустрічає послідовність нових правок `[op⁽ʳ⁺¹⁾, ..., op⁽ʳ⁺ᵐ⁾]`.

Сервер виконує послідовну попарну трансформацію:

```
op_c⁽⁰⁾ = op_c                                                        [початкова операція клієнта]
op_c⁽¹⁾ = T(op_c⁽⁰⁾, op⁽ʳ⁺¹⁾)                                         [трансформація відносно першої серверної правки]
op_c⁽²⁾ = T(op_c⁽¹⁾, op⁽ʳ⁺²⁾)                                         [трансформація відносно другої серверної правки]
...
op_c⁽ᵐ⁾ = T(op_c⁽ᵐ⁻¹⁾, op⁽ʳ⁺ᵐ⁾)                                       [фінальна трансформована операція для ревізії r+m+1]
```

Оскільки на сервері існує **єдиний лінійний порядок** серіалізації, будь-яка конкурентність між двома операціями розв'язується в точці їх фізичного прибуття на сервер:
1. Операція, що прибула першою, стає ревізією `r+1`.
2. Операція, що прибула другою, трансформується попарно проти першої за правилом TP1 і стає ревізією `r+2`.

У цій системі простір станів редукується з N-вимірного гіперкуба до пласкої драбини послідовних ревізій. Багатосторонні ромби TP2 фізично ніколи не обчислюються. Отже, виконання властивості TP1 строго гарантує досягнення сильної кінцевої узгодженості (Strong Eventual Consistency) на всіх вузлах мережі.
