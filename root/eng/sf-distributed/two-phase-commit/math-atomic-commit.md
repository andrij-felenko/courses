# 🧮 Неможливість неблокувального атомарного коміту та теорема Скіна

Задача розподіленого атомарного коміту (англ. *Atomic Commit Problem*, ACP) формулює фундаментальні математичні умови, за яких множина незалежних процесів зобов'язана узгодити спільне бінарне рішення — зафіксувати транзакцію (`Commit`) або скасувати її (`Abort`).

На відміну від загальної задачі консенсусу, де процеси можуть обрати будь-яке із запропонованих значень більшістю голосів, атомарний коміт вимагає абсолютної одностайності: транзакція може бути зафіксована тоді й тільки тоді, коли кожен без винятку учасник проголосував ствердно.

## Формальна постановка задачі

Нехай у системі функціонує скінченна множина із `n` процесів-учасників:

```
P = {p₁, p₂, ..., pₙ}
```

Кожен процес `pᵢ` має початковий голос `vᵢ ∈ {Yes, No}`, який відображає його локальну здатність зафіксувати транзакцію (відсутність порушень цілісності, успішне блокування ресурсів та запис журналу на диск).

Кожен процес `pᵢ` в процесі виконання протоколу має ухвалити остаточне незворотне рішення:

```
dᵢ ∈ {Commit, Abort}
```

Коректний протокол атомарного коміту зобов'язаний задовольняти чотири інваріанти безпеки (англ. *Safety*) та умову живучості (англ. *Liveness*):

1. **Одностайна узгодженість (Uniform Agreement):** усі процеси, які ухвалили рішення, ухвалюють одне й те саме значення. Для будь-яких двох процесів `pᵢ` та `pⱼ`:

```
dᵢ = dⱼ
```

2. **Слабка валідність (Weak Validity):** якщо хоча б один процес проголосував `No`, остаточне рішення не може бути `Commit`:

```
(∃ pᵢ ∈ P : vᵢ = No) ⇒ (∀ pⱼ ∈ P : dⱼ = Abort)
```

3. **Сильна валідність (Strong Validity / Non-Triviality):** якщо всі процеси проголосували `Yes` і в системі не сталося жодних збоїв (ані падінь вузлів, ані втрати повідомлень), остаточне рішення зобов'язане бути `Commit`:

```
(∀ pᵢ ∈ P : vᵢ = Yes) ∧ (Failures = ∅) ⇒ (∀ pⱼ ∈ P : dⱼ = Commit)
```

4. **Незворотність (Irreversibility):** щойно процес переходить у термінальний стан `Commit` або `Abort`, його стан більше ніколи не змінюється:

```
dᵢ(t) = Commit ⇒ ∀ t' > t : dᵢ(t') = Commit
dᵢ(t) = Abort  ⇒ ∀ t' > t : dᵢ(t') = Abort
```

5. **Завершеність (Termination / Liveness):** кожен справний процес врешті-решт ухвалює термінальне рішення `dᵢ ∈ {Commit, Abort}` за скінченний час.

## Скінченно-автоматна модель та вікно невизначеності

У 1981 році Дейл Скін (англ. *Dale Skeen*) запропонував модель аналізу протоколів атомарного коміту через графи переходів станів локальних автоматів.

Стан кожного процесу `pᵢ` належить до однієї з чотирьох категорій:
* **Початковий стан `q₀` (Initial / Working):** процес виконує операції, ще не голосував.
* **Стан невизначеності `q_u` (Uncertain / Prepared / In-Doubt):** процес проголосував `Yes`, але ще не отримав глобального рішення. Процес не має права самостійно ухвалити ані `Commit`, ані `Abort`.
* **Стан фіксації `q_c` (Commit):** процес перейшов у термінальний стан `Commit`.
* **Стан скасування `q_a` (Abort):** процес перейшов у термінальний стан `Abort`.

Визначимо множину станів, сумісних із рішенням. Стан `s` процесу називається **сумісним із Commit** (англ. *commit-compatible*), якщо існує хоча б одна глобальна конфігурація системи, в якій деякий процес ухвалив рішення `Commit`. Аналогічно стан `s` називається **сумісним із Abort** (англ. *abort-compatible*).

Стан `s` називається **станом невизначеності** (англ. *uncertain state*), якщо він одночасно є сумісним як із `Commit`, так і з `Abort`.

У протоколі 2PC стан `Prepared` для учасника є строго невизначеним:
* Якщо всі інші учасники також проголосували `Yes`, координатор міг ухвалити `Commit` і надіслати повідомлення іншим. Отже, стан `Prepared` є сумісним із `Commit`.
* Якщо інший учасник проголосував `No` або впав до відправки голосу, координатор ухвалив `Abort`. Отже, стан `Prepared` є сумісним із `Abort`.

## Теорема Скіна про неблокувальні протоколи

**Теорема (Скін, 1981).** Якщо в протоколі розподіленого коміту локальний автомат процесу містить стан невизначеності `q_u`, який безпосередньо суміжний у графі станів як зі станом `Commit`, так і зі станом `Abort`, то протокол принципово **не може бути неблокувальним** за наявності одночасного падіння координатора та відмови каналів зв'язку (мережевого розрізу).

### Доведення через розгляд нерозрізненності конфігурацій

Нехай у системі є координатор `C` та два учасники `p₁`, `p₂`. Розглянемо дві конфігурації виконання протоколу, які для процесу `p₁` є локально нерозрізненними:

**Сценарій 1 (Глобальний Commit):**
1. Усі учасники `p₁` та `p₂` надсилають голоси `v₁ = Yes`, `v₂ = Yes`.
2. Процес `p₁` переходить у стан `Prepared` і чекає на рішення.
3. Координатор `C` отримує обидва голоси, записує `COMMIT` у свій журнал і встигає доставити повідомлення `GLOBAL_COMMIT` до `p₂`.
4. Процес `p₂` фіксує транзакцію `d₂ = Commit`.
5. У цей момент координатор `C` зазнає аварійного падіння, а зв'язок між `p₁` та `p₂` обривається через мережевий розріз.

**Сценарій 2 (Глобальний Abort):**
1. Процес `p₁` голосує `v₁ = Yes` і переходить у стан `Prepared`.
2. Процес `p₂` голосує `v₂ = No` або аварійно падає ще до відправки голосу.
3. Координатор `C` фіксує відмову, записує `ABORT` у свій журнал і встигає повідомити `p₂` (або `p₂` відкочується локально: `d₂ = Abort`).
4. Координатор `C` зазнає аварійного падіння, а мережа розрізається.

У обох сценаріях локальний стан та історія спостережень процесу `p₁` є абсолютно тотожними:

```
History(p₁) = [Received: PREPARE, Sent: VOTE_COMMIT, State: PREPARED]
```

Процес `p₁` не отримує жодної відповіді від `C` (через його падіння) і не може зв'язатися з `p₂` (через мережевий розріз).

Припустимо, що існує алгоритм локального завершення (англ. *independent recovery protocol*), який дозволяє процесу `p₁` ухвалити рішення самостійно після закінчення таймауту `T_timeout`, не блокуючи ресурси:

1. Якщо алгоритм наказує `p₁` ухвалити `d₁ = Abort`, то у Сценарії 1 ми отримуємо порушення інваріанту одностайності:

```
d₁ = Abort ∧ d₂ = Commit ⇒ d₁ ≠ d₂     [порушення Uniform Agreement]
```

2. Якщо алгоритм наказує `p₁` ухвалити `d₁ = Commit`, то у Сценарії 2 ми отримуємо порушення інваріанту одностайності та слабкої валідності:

```
d₁ = Commit ∧ v₂ = No                  [порушення Weak Validity]
d₁ = Commit ∧ d₂ = Abort ⇒ d₁ ≠ d₂     [порушення Uniform Agreement]
```

Оскільки процес `p₁` не має способу розрізнити Сценарій 1 та Сценарій 2 без отримання додаткової інформації мережею, будь-яке самостійне рішення з ненульовою ймовірністю призводить до розриву цілісності.

Єдиним безпечним вибором для `p₁` є **заблокуватися** (англ. *block*) — залишатися в стані `Prepared` і утримувати блокування ресурсів до відновлення зв'язку з координатором.

## Зведення до задачі двох генералів

Неможливість гарантувати завершення атомарного коміту в асинхронній мережі з ненадійними каналами є прямим наслідком нерозв'язності **задачі двох генералів** (англ. *Two Generals' Problem*, Джим Грей, 1978).

Нехай два вузли повинні погодити атаку. Останнє підтвердження завжди потребує підтвердження на підтвердження:

```
Повідомлень у ланцюгу = k
Ймовірність доставки = p < 1
Ймовірність узгодження
= 1 - (1 - p)ᵏ               [зростає з k, але строго < 1 для будь-якого скінченного k]
```

Оскільки жоден скінченний протокол обміну повідомленнями через ненадійний канал зв'язку не здатен на 100% гарантувати спільне знання (англ. *common knowledge*), будь-який протокол атомарного коміту в умовах ненадійних каналів змушений обирати між блокуванням (безпека ціною живучості) або ризиком розриву узгодженості (живучість ціною безпеки).
