# 🧮 Математична модель отруйного каскаду: вичерпання пулу воркерів та динаміка блокування черги

У розподілених чергах повідомлень збій одного запису не залишається локальною подією: за відсутності карантинного контуру детерміновано отруйне повідомлення циркулює між воркерами, виснажуючи обчислювальні ресурси та викликаючи вибухоподібне зростання глибини черги.

Нижче наведено формальний математичний аналіз трьох ключових процесів:
1. Час до повного паралічу пулу споживачів (Mean Time to Worker Pool Exhaustion).
2. Імовірність блокування початку черги (Head-of-Line Blocking) у секціонованих журналах подій.
3. Динаміка накопичення черги та допустима швидкість безпечного спуску карантину (Safe Quarantine Drain Rate).

---

## 1. Модель пулу споживачів та час до вичерпання ресурсів

Розглянемо систему обробки повідомлень із пулом паралельних воркерів:
- `W` — кількість паралельних воркерів (потоків або процесів-споживачів).
- `λ_v` — вхідна інтенсивність потоку валідних повідомлень (повідомлень на секунду, msg/s).
- `μ_v` — інтенсивність обробки одного валідного повідомлення одним воркером, тобто середній час обробки `T_v = 1 / μ_v`.
- `λ_p` — інтенсивність надходження отруйних повідомлень (`λ_p ≪ λ_v`).
- `R` — ліміт повторних спроб обробки (Retry Budget), тобто одне отруйне повідомлення перед відкиданням або переміщенням генерує `R` послідовних збоїв.
- `T_p` — тривалість спроби обробки отруйного повідомлення до виникнення аварії або таймауту (`T_p = T_crash` або `T_p = T_timeout`).
- `T_backoff` — середня затримка між повторними спробами (Backoff Delay).

### Захоплення ресурсу воркера отруйним повідомленням

Одне валідне повідомлення займає обчислювальний ресурс воркера на час:

```
E[Time_valid] = T_v = 1 / μ_v
```

Одне отруйне повідомлення, яке повторюється `R` разів, займає активний процесорний час воркерів сумарно на:

```
E[Time_poison] = R · T_p
```

Загальне завантаження пулу воркерів `ρ` визначається як відношення сумарної роботи, що надходить за одиницю часу, до максимальної пропускної здатності пулу `W`:

```
ρ = (λ_v · T_v + λ_p · R · T_p) / W
```

Якщо `ρ ≥ 1`, черга стає нестабільною: кількість повідомлень у буфері починає монотонно зростати до нескінченності.

### Критична частка отруйних повідомлень

Визначимо критичну частку отруйних повідомлень у вхідному потоці `p_crit = λ_p / (λ_v + λ_p)`, яка призводить до перевантаження системи (`ρ = 1`), вважаючи, що початкова система була завантажена валідним трафіком на рівні `ρ_0 = (λ_v · T_v) / W`:

```
1 - ρ_0 = (λ_p · R · T_p) / W
λ_p,crit = W · (1 - ρ_0) / (R · T_p)
```

Звідси частка отруйних повідомлень, достатня для повного колапсу:

```
p_crit = (1 - ρ_0) / ( (1 - ρ_0) + (R · T_p / T_v) · ρ_0 )
```

**Числовий приклад:**
- Нехай `W = 50` воркерів.
- Валідне повідомлення обробляється за `T_v = 0.02` с (20 мс), тобто `μ_v = 50` msg/s на воркер. Максимальна ємність системи `W · μ_v = 2500` msg/s.
- Поточне навантаження `λ_v = 2000` msg/s, отже `ρ_0 = 2000 / 2500 = 0.80` (80% завантаження).
- Отруйне повідомлення спричиняє таймаут `T_p = 2.0` с.
- Кількість повторів `R = 5`.

Розрахуємо `λ_p,crit`:

```
λ_p,crit
= 50 · (1 - 0.80) / (5 · 2.0)    [підстановка параметрів]
= 50 · 0.20 / 10.0               [множення]
= 10.0 / 10.0                    [ділення]
= 1.0 msg/s                      [результат]
```

При потоці валідних замовлень 2000 msg/s поява лише **1 отруйного повідомлення на секунду** (0.05% трафіку) повністю паралізує весь пул із 50 воркерів.

## 2. Середній час до паралічу пулу (MTTE)

Нехай у момент часу `t = 0` у системі виникає пачка з `K` отруйних повідомлень без затримки між спробами (`T_backoff ≈ 0`, негайний requeue). Кожне отруйне повідомлення миттєво захоплює один вільний воркер.

Середній час до захоплення всіх `W` воркерів отруйними повідомленнями (Mean Time to Exhaustion, `MTTE`) за умови, що нові отруйні повідомлення надходять за законом Пуассона з інтенсивністю `λ_p`, а отруйне повідомлення залишає систему лише після виконання `R` спроб (сумарний час життя `L = R · T_p`):

Ймовірність того, що в системі одночасно перебуває `k` активних циклів отруйних повідомлень, описується розподілом Ерланга або Пуассона для системи `M/G/W/W`:

```
P(k отрут у системі) = ( (λ_p · L)^k / k! ) / ( ∑_{j=0}^{W} (λ_p · L)^j / j! )
```

Коли `k = W`, усі воркери зайняті обробкою отрути, і пропускна здатність для валідних повідомлень падає до нуля:

```
W_eff = 0
```

## 3. Блокування початку черги (Head-of-Line Blocking) у секціонованому журналі подій

У таких системах, як Apache Kafka або Apache Pulsar, черга розбита на `M` незалежних секцій (партицій). У межах однієї партиції споживач читає повідомлення строго послідовно за зростанням зміщення (Offset).

Якщо на зміщенні `Offset = X` виникає отруйне повідомлення, споживач не може зафіксувати зміщення `X` (Commit Offset), доки воно не буде успішно оброблене.

### Ймовірність паралічу партицій

Нехай у системі є `M` партицій. Отруйні повідомлення розподіляються між партиціями рівномірно з імовірністю `1 / M` для кожної партиції.

Якщо в потік надійшло `N_p` отруйних повідомлень, імовірність того, що конкретна партиція `i` містить хоча б одне отруйне повідомлення і тому заблокована:

```
P(Partition_i заблокована) = 1 - (1 - 1 / M)^(N_p)
```

Загальна частка заблокованих партицій `E[Blocked / M]`:

```
E[Fraction_Blocked] = 1 - (1 - 1 / M)^(N_p)
```

При великій кількості партицій `M` та співвідношенні `α = N_p / M`:

```
lim_{M → ∞} (1 - 1 / M)^(N_p)
= lim_{M → ∞} ( (1 - 1 / M)^M )^(N_p / M)    [властивість степеня: перегрупування показників]
= lim_{M → ∞} ( (1 - 1 / M)^M )^α            [заміна відношення: N_p / M = α]
= (e^(-1))^α                                 [друга чудова границя: lim (1 - 1/M)^M = e^(-1)]
= e^(-α)                                     [піднесення до степеня: (e^(-1))^α = e^(-α)]
```

Отже:

```
E[Fraction_Blocked] ≈ 1 - e^(-N_p / M)
```

**Аналіз залежності:**
- Якщо кількість отруйних повідомлень дорівнює кількості партицій (`N_p = M`, тобто `α = 1`):
  `E[Fraction_Blocked] = 1 - e^(-1) ≈ 1 - 0.368 = 0.632` (63.2% партицій заблоковано).
- Якщо `N_p = 3 · M` (всього 3 отруйні повідомлення на партицію в середньому):
  `E[Fraction_Blocked] = 1 - e^(-3) ≈ 1 - 0.0498 = 0.9502` (**95% партицій повністю паралізовано**).

Усі валідні повідомлення, що потрапляють у ці 95% партицій позаду отруйного запису, накопичуються без обробки.

## 4. Динаміка накопичення черги під час аварії

Нехай `Q(t)` — кількість валідних повідомлень, що очікують у черзі в момент часу `t`. Швидкість зміни довжини черги задається диференціальним балансовим рівнянням:

```
dQ(t) / dt = λ_v - W_eff(t) · μ_v
```

де `W_eff(t)` — кількість воркерів, вільних від обробки отруйних повідомлень:

```
W_eff(t) = max( 0, W - N_poison_active(t) )
```

Якщо система працює **без карантину**, і всі воркери захоплені отрутою (`W_eff(t) = 0`):

```
dQ(t) / dt = λ_v
Q(t) = Q(0) + λ_v · t
```

Довжина черги зростає строго лінійно зі швидкістю повного вхідного потоку. Затримка доставки (End-to-End Latency) для нового повідомлення, що надходить у момент часу `t`:

```
Latency(t) = Q(t) / (W · μ_v)
```

Після відновлення системи (коли отруту нарешті ізольовано вручну в момент часу `T_fix`), час, необхідний для повної ліквідації накопиченого відставання (Queue Evacuation Time, `T_evac`):

```
T_evac
= Q(T_fix) / (W · μ_v - λ_v)                   [баланс швидкості спорожнення: час = об'єм / швидкість]
= (λ_v · T_fix) / (W · μ_v - λ_v)              [підстановка накопиченого об'єму Q(T_fix) = λ_v · T_fix]
= ( (λ_v / (W · μ_v)) · T_fix ) / (1 - λ_v / (W · μ_v)) [ділення чисельника і знаменника на W · μ_v]
= T_fix · ( ρ_0 / (1 - ρ_0) )                  [заміна коефіцієнта завантаження ρ_0 = λ_v / (W · μ_v)]
```

**Числовий приклад ліквідації наслідків:**
- Нехай `ρ_0 = 0.85` (система завантажена на 85%).
- Інцидент з отруйним повідомленням тривав `T_fix = 10` хвилин (600 секунд) до втручання інженера.

Розрахуємо час ліквідації затору `T_evac`:

```
T_evac
= 600 · ( 0.85 / (1 - 0.85) )    [підстановка]
= 600 · ( 0.85 / 0.15 )          [віднімання знаменника]
= 600 · 5.6667                   [ділення часток]
= 3400 секунд ≈ 56.6 хвилин      [підсумок]
```

Простій тривалістю 10 хвилин змушує систему ліквідувати чергу протягом майже **одної години**, протягом якої користувачі відчувають критичні затримки.

## 5. Безпечна швидкість повторного спуску карантину (Safe Redrive Rate)

Коли баг у коді виправлено або схему даних оновлено, у карантинному сховищі залишається `N_quarantine` накопичених повідомлень. Якщо запустити їхній повторний спуск (Redrive) миттєво з необмеженою швидкістю, вони створять вторинний сплеск навантаження (Thundering Herd), який знову перевантажить базу даних або споживачів.

Для запобігання вторинній аварії швидкість спуску карантину `λ_drain` повинна жорстко обмежуватися регулятором пропускної здатності (Token Bucket / Rate Limiter):

```
λ_drain ≤ W · μ_v · (1 - ρ_0) · (1 - Safety_Margin)
```

де `Safety_Margin` — коефіцієнт безпеки (зазвичай 0.20–0.30, тобто 20–30% резерву пропускної здатності).

Мінімальний безпечний час спуску карантину `T_drain_safe`:

```
T_drain_safe = N_quarantine / λ_drain
```

**Критерій стійкості:**
Система залишається стабільною під час очищення карантину тоді і тільки тоді, коли сумарне навантаження не перевищує 100% ємності:

```
(λ_v + λ_drain) / (W · μ_v) ≤ 1 - Safety_Margin
```

Ці співвідношення доводять: наявність миттєвої автоматичної ізоляції (карантину) зводить `T_fix` для основного потоку до нуля мілісекунд, захищаючи 99.95% валідних повідомлень від затримок та блокування.
