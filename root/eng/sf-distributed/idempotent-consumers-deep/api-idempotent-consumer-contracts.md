# 📋 Контракти, метадані та схеми ідемпотентного консюмера

Цей довідник містить повну специфікацію інтерфейсів, схем реляційних баз даних, бінарних та мережевих заголовків повідомлень, телеметричних метрик і протоколів обробки помилок, необхідних для промислової реалізації відмовостійких ідемпотентних споживачів.

## 1. Схема реляційного сховища (PostgreSQL DDL)

Для підтримки трифазного виконання, транзакційної дедуплікації, обліку спроб доставки та оренди обробки використовується єдина схема таблиць.

```sql
-- Таблиця станів вхідних повідомлень (Transactional Inbox)
CREATE TABLE consumer_inbox (
    message_id VARCHAR(128) NOT NULL,
    consumer_group VARCHAR(64) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    partition_id INTEGER NOT NULL,
    message_offset BIGINT NOT NULL,
    
    -- Стан обробки: PENDING, IN_PROGRESS, COMPLETED, QUARANTINED
    status VARCHAR(24) NOT NULL DEFAULT 'PENDING',
    
    -- Детермінований ключ для зовнішніх викликів (SHA-256)
    outbound_idempotency_key VARCHAR(128) NOT NULL,
    
    -- Зовнішній ідентифікатор транзакції (наприклад, stripe_charge_id)
    external_reference VARCHAR(128),
    
    -- Облік спроб доставки та захист від отруйної петлі
    delivery_attempts INTEGER NOT NULL DEFAULT 1,
    last_error_message TEXT,
    
    -- Оренда обробки (Lease) для запобігання гонкам воркерів
    worker_lease_id UUID,
    lease_expires_at TIMESTAMPTZ,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at TIMESTAMPTZ,
    
    PRIMARY KEY (consumer_group, message_id)
);

-- Індекс для фонового очищення застарілих ключів за вікном TTL
CREATE INDEX idx_consumer_inbox_ttl ON consumer_inbox (created_at)
WHERE status = 'COMPLETED';

-- Індекс для виявлення завислих орендованих повідомлень (Lease Timeout)
CREATE INDEX idx_consumer_inbox_lease ON consumer_inbox (lease_expires_at)
WHERE status = 'IN_PROGRESS';

-- Таблиця огорожі епох для захисту від зомбі-воркерів при ребалансах
CREATE TABLE partition_epoch_fences (
    consumer_group VARCHAR(64) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    partition_id INTEGER NOT NULL,
    current_generation_epoch BIGINT NOT NULL DEFAULT 1,
    active_worker_id VARCHAR(128) NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    
    PRIMARY KEY (consumer_group, topic, partition_id)
);
```

### Семантика та інваріанти полів схеми

Складений первинний ключ `(consumer_group, message_id)` забезпечує строгу ізоляцію між різними групами споживачів: якщо одну й ту саму чергу або топік вичитують незалежні сервіси (наприклад, `billing-consumer` та `analytics-consumer`), кожен сервіс веде власний незалежний облік дедуплікації без конфліктів унікальності.

Поле `outbound_idempotency_key` обчислюється на Фазі 1 до здійснення будь-яких зовнішніх викликів. Збереження цього токена безпосередньо в рядку inbox гарантує, що при перезапуску процесу після аварії новий воркер не буде повторно генерувати випадковий ідентифікатор, а прочитає раніше зафіксований стабільний токен і передасть його сторонньому API.

Поля `worker_lease_id` та `lease_expires_at` формують механізм оптимістичного блокування без використання важких блокувань рядків бази даних `SELECT FOR UPDATE`. Коли воркер бере повідомлення в роботу, він генерує унікальний ідентифікатор екземпляра (UUIDv4) і встановлює час оренди на 30–60 секунд уперед. Якщо воркер зависає або зазнає аварії, інший воркер має право перехопити повідомлення лише за умови `lease_expires_at < NOW()`, що унеможливлює паралельне виконання однієї дії двома живими процесами.

Часткові індекси `idx_consumer_inbox_ttl` та `idx_consumer_inbox_lease` мають предикати `WHERE status = 'COMPLETED'` та `WHERE status = 'IN_PROGRESS'`. Завдяки цьому розмір індексів становить менше 5% від повного розміру таблиці, що запобігає деградації кешу оперативної пам'яті сервера PostgreSQL при мільярдних обсягах оброблених подій.

## 2. Специфікація заголовків повідомлення (Message Envelope)

Кожне повідомлення, що надходить у чергу або топік брокера (Apache Kafka, RabbitMQ, Amazon SQS, NATS JetStream), повинно містити стандартизовані метадані в бінарних або протокольних заголовках:

| Заголовок (Header) | Тип | Обов'язковість | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `Idempotency-Key` | String (UUIDv7) | Обов'язковий | Унікальний токен вихідної події, що генерується джерелом. |
| `Correlation-Id` | String (UUIDv4) | Обов'язковий | Наскрізний ідентифікатор трасування розподіленої операції. |
| `Producer-Id` | String (URI) | Обов'язковий | Ідентифікатор сервісу-емітера (наприклад, `service://billing-api`). |
| `Producer-Epoch` | Int64 | Опціональний | Монотонна епоха життя продюсера для відсікання старих сесій. |
| `Sequence-Number` | Int64 | Опціональний | Монотонний порядковий номер повідомлення в межах продюсера. |
| `Delivery-Attempt` | Int32 | Обов'язковий | Лічильник спроб доставки, що інкрементується брокером/воркером. |
| `Timestamp-Utc` | Int64 (Unix MS) | Обов'язковий | Точний час створення повідомлення на стороні відправника. |
| `Deduplication-TTL` | Int32 (Seconds) | Опціональний | Рекомендоване вікно зберігання ключа споживачем (дефолт: 604800). |

### Вимоги до структури ключів джерела

Як первинний ідентифікатор `Idempotency-Key` наполегливо рекомендується використання формату UUIDv7. На відміну від повністю випадкового UUIDv4, стандарт UUIDv7 містить у перших 48 бітах мітку часу Unix у мілісекундах. Це забезпечує монотонне зростання ключів, усуває фрагментацію індексних B-Tree сторінок у базі даних і зменшує кількість операцій розщеплення сторінок (Page Splits) на 80%.

Заголовок `Producer-Epoch` використовується для виявлення застарілих екземплярів сервісів-відправників: якщо споживач уже зафіксував повідомлення з епохою 5 від даного `Producer-Id`, будь-які запізнілі повідомлення з епохою 4 автоматично відхиляються як застарілі фантомні пакети.

## 3. Контракт виклику зовнішніх сторонніх систем (Downstream API)

При виклику зовнішніх API (платіжних шлюзів, сторонніх мікросервісів, поштових провайдерів) на Фазі 2 консюмер зобов'язаний транслювати детерміновані заголовки дедуплікації відповідно до чернетки стандарту IETF:

```http
POST /v1/charges HTTP/1.1
Host: api.stripe.com
Authorization: Bearer sk_live_...
Content-Type: application/json
Idempotency-Key: idemp_charge_8f1b9a2c_step1
X-Correlation-ID: 7d2e4f6a-9b1c-4e8a-b3d2-1c5e6f7a8b9c
X-Consumer-Attempt: 2

{
  "amount": 25000,
  "currency": "uah",
  "source": "tok_visa_ua",
  "description": "Payment for Order #1042"
}
```

### Формування вихідного ключа та захист від підміни корисного навантаження

Ключ для зовнішнього виклику ніколи не генерується випадковим `randomUUID()`. Він обчислюється як детермінований криптографічний хеш від комбінації вхідного `message_id`, назви дії та індексу кроку:

```
outbound_key = "idemp_" + SHA256(inbound_message_id + ":" + action_name + ":" + step_index)
```

Це гарантує, що скільки б разів консюмер не падав і не перезапускався під час обробки одного й того самого повідомлення, він завжди передаватиме зовнішньому сервісу абсолютно однаковий токен.

Якщо зовнішній сервіс отримує повторний запит із тим самим `Idempotency-Key`, але з іншим тілом запиту (Payload Mismatch), він зобов'язаний повернути клієнту помилку `422 Unprocessable Entity` або `409 Conflict`, сигналізуючи про спробу підміни даних з повторним використанням старого ключа.

Для gRPC-взаємодії ті самі метадані передаються через бінарні заголовки контексту (gRPC Metadata Context):
* `x-idempotency-key`: детермінований ключ операції.
* `x-correlation-id`: наскрізний ідентифікатор трасування.
* `x-consumer-generation`: поточна епоха групи споживача.

## 4. Матриця переходів автомата станів споживача

Обробка кожного вхідного повідомлення керується суворим кінцевим автоматом:

| Початковий стан | Подія | Перевірки / Умови | Дія споживача | Наступний стан |
| :--- | :--- | :--- | :--- | :--- |
| `NEW` | Отримано повідомлення | Ключа немає в `consumer_inbox` | Вставка запису з `status='IN_PROGRESS'`, взяття оренди `lease` | `IN_PROGRESS` |
| `NEW` | Отримано повідомлення | Ключ є, `status='COMPLETED'` | Пропуск бізнес-дії, відправка ACK брокеру | `COMPLETED` |
| `NEW` | Отримано повідомлення | Ключ є, `status='IN_PROGRESS'`, `lease_expires_at > NOW()` | Інший воркер обробляє. Пропуск або NACK з відкладенням | `IN_PROGRESS` |
| `NEW` | Отримано повідомлення | Ключ є, `status='IN_PROGRESS'`, `lease_expires_at <= NOW()` | Попередній воркер помер. Перехоплення оренди `lease_id` | `IN_PROGRESS` |
| `IN_PROGRESS` | Сайд-ефект успішний | Отримано відповідь `200 OK` / `201 Created` | Запис результату, переведення стану в `COMPLETED`, ACK | `COMPLETED` |
| `IN_PROGRESS` | Тимчасова помилка (503/429/Timeout) | `delivery_attempts < MAX_ATTEMPTS` | Інкремент `delivery_attempts`, зняття оренди, повтор | `PENDING` |
| `IN_PROGRESS` | Фатальна помилка / Poison | `delivery_attempts >= MAX_ATTEMPTS` | Запис у DLQ, `status='QUARANTINED'`, ACK брокеру | `QUARANTINED` |

### Інваріанти переходів станів

Перехід зі стану `IN_PROGRESS` у стан `COMPLETED` є незворотним термінальним переходом. Жодна подія в системі не має права повторно перевести запис зі статусу `COMPLETED` у будь-який інший стан. Якщо після досягнення статусу `COMPLETED` у чергу надходить дублікат повідомлення, споживач зобов'язаний виконати ідемпотентний пропуск (No-Op) і надіслати підтвердження зсуву брокеру.

Перехід у стан `QUARANTINED` здійснюється виключно після вичерпання ліміту спроб. У цьому стані запис зберігає повний діагностичний контекст: текст останнього винятку, стек викликів, кількість виконаних спроб та ідентифікатор збійного воркера.

У разі аварійного перемикання бази даних на репліку (Primary-Replica Failover) споживач зобов'язаний перевіряти статус готовності запису (`pg_is_in_recovery()`). Якщо нова репліка відстає у часі, споживач тимчасово зупиняє обробку (pause consumer), запобігаючи виконанню повторних дій на застарілому зрізі даних.

## 5. Специфікація метрик спостережуваності (Prometheus / OpenTelemetry)

Для моніторингу працездатності, виявлення витоків ключів та фіксації отруйних петель визначаються такі метрики:

| Ім'я метрики | Тип | Мітки (Labels) | Опис та призначення |
| :--- | :--- | :--- | :--- |
| `consumer_messages_processed_total` | Counter | `topic`, `group`, `status` | Загальна кількість оброблених повідомлень. |
| `consumer_deduplication_hits_total` | Counter | `topic`, `group` | Кількість відфільтрованих дублікатів (Save operations). |
| `consumer_side_effects_total` | Counter | `service`, `endpoint`, `result` | Кількість виконаних зовнішніх мережевих викликів. |
| `consumer_poison_loops_detected_total` | Counter | `topic`, `group`, `reason` | Кількість повідомлень, що перевищили ліміт спроб і пішли в DLQ. |
| `consumer_lease_stolen_total` | Counter | `topic`, `group` | Кількість перехоплень завислих оренд після краху воркерів. |
| `consumer_dedup_window_lag_seconds` | Gauge | `topic`, `group` | Різниця між поточним часом і найстарішим ключем в активному вікні. |
| `consumer_processing_duration_seconds` | Histogram | `topic`, `group`, `phase` | Тривалість кожної з трьох фаз обробки (Phase 1, Phase 2, Phase 3). |

### Правила налаштування сповіщень (Alerting Rules)

Критичне попередження рівня `P1 / Page` повинно спрацьовувати у випадках:
* Якщо швидкість наростання метрики `consumer_poison_loops_detected_total` перевищує 5 подій за хвилину.
* Якщо гістограма `consumer_processing_duration_seconds` для Фази 2 показує 99-й перцентиль затримки понад 5000 мс протягом 3 хвилин поспіль.
* Якщо значення `consumer_dedup_window_lag_seconds` перевищує 90% від налаштованого розміру вікна TTL, що свідчить про зупинку фонового процесу очищення або критичне переповнення дискового простору.
* Якщо коефіцієнт відфільтрованих дублікатів `consumer_deduplication_hits_total / consumer_messages_processed_total` раптово перевищує 50%, що сигналізує про зациклення продюсера або збій таймерів підтвердження в кластері брокера.
