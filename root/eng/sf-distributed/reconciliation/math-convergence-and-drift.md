# 🧮 Математична модель дрейфу стану та стійкості збіжності контролерів

Безперервне узгодження стану базується на математичному апараті теорії динамічних систем, метричних просторів та процесів відновлення. У цій вставці наведено строгий формальний аналіз простору станів, доведено умови монотонної збіжності циклу звірки за функцією Ляпунова, розраховано математичне сподівання накопиченого дрейфу за пуассонівського потоку аварій та виведено залежність часу відновлення кластера від характеристик коалесценції у черзі завдань.

---

## 1. Метричний простір станів та оператор узгодження

Розглянемо множину можливих станів керованої розподіленої системи як метричний простір `(S, d)`, де `S` — простір станів, а `d: S × S → ℝ⁺` — метрична функція відстані, що задовольняє три класичні аксіоми:

```
1. d(A, B) ≥ 0, причому d(A, B) = 0 тоді й лише тоді, коли A = B  [Невід'ємність та тотожність]
2. d(A, B) = d(B, A)                                             [Симетричність]
3. d(A, C) ≤ d(A, B) + d(B, C)                                   [Нерівність трикутника]
```

Нехай `S* ∈ S` — заданий користувачем **бажаний стан** (Desired State / Spec), а `S(t) ∈ S` — **фактичний спостережуваний стан** фізичного середовища в момент часу `t` (Observed State / Status).

Функція відхилення (похибки) системи в момент часу `t` визначається як відстань від поточного стану до цільового:

```
D(t) = d(S(t), S*)
```

Для складних гетерогенних об'єктів, що складаються з дискретної множини іменованих ресурсів `E = {e₁, e₂, ..., eₙ}`, відстань визначається через потужність симетричної різниці множин фактичних та бажаних сутностей:

```
[Метрика симетричної різниці ресурсів]
d_set(E_actual, E_desired)
= |E_actual ∖ E_desired| + |E_desired ∖ E_actual|
= |Зомбі-ресурси| + |Відсутні ресурси|
```

Визначимо **дискретний оператор узгодження** `R: S → S`, який зіставляє спостережуваному стану `S` новий стан після виконання коригувальних мутацій контролера.

---

## 2. Умова асимптотичної стійкості та монотонної збіжності за Ляпуновим

Щоб система гарантовано відновлювалася після довільних збоїв і не входила в стан незатухаючих автоколивань (флепінгу), оператор узгодження `R` повинен задовольняти критерій дискретної стійкості Ляпунова.

Виберемо функцію похибки `V(S) = d(S, S*)` як дискретну функцію Ляпунова:

```
1. V(S*) = 0
2. V(S) > 0 для всіх S ≠ S*
```

Оператор `R` забезпечує **суворе монотонне зведення розбіжностей**, якщо приріст функції Ляпунова `ΔV(S) = V(R(S)) - V(S)` є строго від'ємним для будь-якого нецільового стану:

```
[Умова монотонного збігання до бажаного стану]
V(R(S)) - V(S) < 0              [Зменшення похибки за один крок звірки]
d(R(S), S*) < d(S, S*)          [Відстань до мети монотонно спадає]
```

Для цільового стану `S*` оператор `R` є нерухомою точкою:

```
R(S*) = S*                       [Нерухома точка: за відсутності розбіжностей дій немає]
```

Крім того, оператор `R` зобов'язаний бути **ідемпотентним**:

```
R(R(S))
= R(S)                          [Ідемпотентність: повторне виконання не змінює досягнутий стан]
```

Якщо оператор `R` зменшує похибку принаймні на коефіцієнт стиску `γ ∈ [0, 1)`:

```
d(R(S), S*) ≤ γ · d(S, S*)
```

то за теоремою Банаха про стискуючі відображення послідовність станів `Sₖ₊₁ = R(Sₖ)` експоненційно сходиться до єдиної нерухомої точки `S*` за `k` ітерацій:

```
d(Sₖ, S*) ≤ γᵏ · d(S₀, S*)
```

Якщо ж у системі діють два неузгоджені контролери з взаємно протилежними операторами `R₁` та `R₂`, виникає циклічна траєкторія:

```
[Умова осциляції при конфлікті контролерів]
R₁(S_A) = S_B
R₂(S_B) = S_A
d(S_A, S*) = d(S_B, S*) > 0     [Система не сходиться, генеруючи нескінченні мутації]
```

Для запобігання такій осциляції простір полів розділяється на неперетинні зони володіння (Field Ownership), гарантуючи, що для будь-якого поля існує рівно один оператор `R`, уповноважений здійснювати мутації.

## 3. Моделювання накопичення дрейфу за пуассонівського потоку збоїв

У реальному розподіленому середовищі фактичний стан постійно зазнає випадкових зовнішніх збурень: аварії вузлів, збої живлення, мережеві переривання, ручні втручання адміністраторів.

Змоделюємо потік одиничних аварійних подій як гомогенний процес Пуассона з інтенсивністю `λ` (середня кількість відмов за одиницю часу). Кожна відмова збільшує відстань `D(t)` на випадкову величину `δ ≥ 1` із середнім значенням `μ_δ = E[δ]`.

Якщо система здійснює повну звірку періодично з фіксованим інтервалом `T_sync`, накопичений дрейф на проміжку між двома послідовними запусками `t ∈ [0, T_sync)` зростає лінійно за математичним сподіванням:

```
[Очікуване значення похибки в момент часу t всередині вікна синхронізації]
E[D(t)]
= D(0) + E[N(t)] · μ_δ          [Де N(t) — кількість пуассонівських подій за час t]
= D(0) + λ · t · μ_δ            [Оскільки для процесу Пуассона E[N(t)] = λ · t]
```

Якщо контролер повністю усуває похибку наприкінці кожного періоду (`D(0) = 0`), середнє інтегральне значення невідповідності системи (інтегральний дрейф `D_avg`) обчислюється як середнє за період:

```
[Розрахунок середнього інтегрального дрейфу системи]
D_avg
= (1 / T_sync) · ∫₀^{T_sync} E[D(t)] dt        [Визначення середнього значення інтеграла]
= (1 / T_sync) · ∫₀^{T_sync} (λ · t · μ_δ) dt  [Підстановка лінійної функції похибки]
= (λ · μ_δ / T_sync) · [t² / 2]₀^{T_sync}      [Інтегрування степеневої функції]
= (λ · μ_δ / T_sync) · (T_sync² / 2)           [Обчислення первісної на межах]
= 0.5 · λ · μ_δ · T_sync                       [Фінальне значення середнього дрейфу]
```

**Практичний висновок**: середній дрейф системи прямо пропорційний інтервалу періодичної звірки `T_sync`. Збільшення частоти опитування вдвічі скорочує середню кількість розбіжностей у кластері вдвічі.

## 4. Гібридна модель: подійні сповіщення з фоновим запобіжником

Реальні контролери поєднують миттєву реакцію на події (Watch/Push) із періодичною фоновою звіркою (Resync).

Нехай подійний механізм успішно доставляє сповіщення про зміну стану з імовірністю `p_event ∈ [0, 1]`, а затримка реакції на подію становить `t_react ≈ 0`. Якщо ж повідомлення втрачено (з імовірністю `1 - p_event`), розбіжність залишається непоміченою до настання чергового фонового циклу `T_resync`.

Тоді середній час виявлення та ліквідації одиничного збою `E[T_repair]` становить:

```
[Середній час усунення поодинокої розбіжності]
E[T_repair]
= p_event · t_react + (1 - p_event) · (0.5 · T_resync)    [Зважена сума часу реакції]
```

Якщо `p_event = 0.95`, `t_react = 0.1` с, а `T_resync = 1800` с (30 хвилин):

```
[Числовий приклад розрахунку середнього часу ліквідації]
E[T_repair]
= 0.95 · 0.1 + (1 - 0.95) · (0.5 · 1800)       [Підстановка параметрів системи]
= 0.095 + 0.05 · 900                           [Обчислення затримки фонового вікна]
= 0.095 + 45                                   [Внесок подійного та фонового каналів]
= 45.095 с                                     [Підсумковий середній час відновлення]
```

Цей розрахунок доводить: навіть за 95% надійності подійного каналу саме періодичний фоновий інтервал `T_resync` визначає верхню межу часу виправлення прихованого дрейфу.

## 5. Ймовірнісна модель повторних спроб: експоненційний бекоф із джитером

Коли ітерація узгодження завершується помилкою через перевантаження зовнішнього API чи тимчасовий мережевий розрив (імовірність невдачі `p_fail`), контролер відкладає наступний виклик за алгоритмом експоненційного відступу.

Базова затримка на кроці спроби `k` визначається як:

```
T_backoff(k) = min( T_max, T_base · 2ᵏ )
```

Щоб запобігти синхронізації тисяч контролерів після масового збою (явище Thundering Herd), до затримки додається випадковий шум (повний джитер, Full Jitter):

```
[Затримка з повним джитером]
T_actual(k) = Uniform(0, min( T_max, T_base · 2ᵏ ))
```

Математичне сподівання загального часу очікування `E[T_wait]` до першої успішної спроби за геометричного розподілу невдач обчислюється як сума нескінченного ряду:

```
[Математичне сподівання загального часу затримок при відновленні]
E[T_wait]
= ∑_{k=0}^{∞} (p_fail)ᵏ · (1 - p_fail) · E[T_actual(k)]
= ∑_{k=0}^{∞} (p_fail)ᵏ · (1 - p_fail) · 0.5 · min(T_max, T_base · 2ᵏ)
```

Якщо `T_base = 0.2` с, `p_fail = 0.3`, а `T_max = 60` с, для перших трьох кроків отримуємо:

```
k=0: E[T₀] = 0.5 · 0.2 = 0.10 с
k=1: E[T₁] = 0.5 · 0.4 = 0.20 с
k=2: E[T₂] = 0.5 · 0.8 = 0.40 с

E[T_wait] ≈ 0.7 · 0.10 + 0.3 · 0.7 · 0.20 + (0.3)² · 0.7 · 0.40
          = 0.070 + 0.042 + 0.025
          = 0.137 с
```

## 6. Динаміка черги завдань: коалесценція та захист від лавиноподібних навантажень

Під час масових апаратних збоїв (наприклад, вимкнення стійки серверів) контролер отримує одночасний сплеск із `M` подій щодо одного й того самого ресурсу `K`.

Якщо черга не підтримує коалесценцію (об'єднання подій за ключем), обчислювальне навантаження зростає лінійно `O(M)`. У черзі з коалесценцією на базі множини ключів `DirtySet` функція стиснення перетворює сплеск `M` оновлень у єдиний виклик:

```
[Коефіцієнт стиснення навантаження в черзі з коалесценцією]
C(M) = 1 / M                                   [Зменшення кількості викликів Reconcile]
```

Нехай кластер містить `K_total` унікальних ресурсів, які зазнали збою, а пул воркерів має розмір `W` потоків. Кожна ітерація `Reconcile()` займає середній час `T_exec` (мережевий RTT до API та виконання операцій).

Якщо виклики API обмежуються алгоритмом маркерного кошика (Token Bucket) з ємністю спалаху `B` та постійною швидкістю поповнення `r` токенів/с, час повної ліквідації масового дрейфу `T_total_drain` розраховується як:

```
[Час повного зведення розбіжностей при масовому збої]
T_total_drain
= max( (K_total · T_exec) / W , (K_total - B) / r )   [Обмеження за воркерами та за рейтом API]
```

Якщо `K_total = 5000` ресурсів, `W = 20` воркерів, `T_exec = 0.05` с (50 мс), `B = 500`, а ліміт API хмарного провайдера `r = 100` запитів/с:

```
[Розрахунок часу відновлення кластера після аварії 5000 вузлів]
Час за пулом воркерів:
T_workers = (5000 · 0.05) / 20 = 250 / 20 = 12.5 с

Час за лімітом маркерного кошика API:
T_api = (5000 - 500) / 100 = 4500 / 100 = 45.0 с

T_total_drain = max(12.5, 45.0) = 45.0 с       [Вузьким місцем виступає ліміт викликів API]
```

Отже, математична модель дозволяє заздалегідь розрахувати параметри черги та пулу воркерів, гарантуючи, що контролер приведе систему до бажаного стану за строго визначений часовий бюджет без перевантаження керованої інфраструктури.
