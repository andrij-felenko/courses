# 📋 Архітектурний контракт та інтерфейс контролера узгодження

Контролер узгодження є стандартизованим компонентом розподілених систем керування. Щоб забезпечити надійну інтеграцію між декларативним сховищем стану, чергою завдань та зовнішніми підсистемами, кожен реконсилятор (Reconciler) реалізує суворий архітектурний контракт. У цій вставці наведено повний опис сигнатур інтерфейсів, структур керуючих повідомлень, семантики кодів результатів, формату умов стану (Conditions), протоколу володіння полями (Field Ownership), механізму виборів лідера (Leader Election), контракту підресурсу масштабування (`/scale`) та метрик спостережуваності.

---

## 1. Сигнатура ядра узгодження (Reconciler Interface)

Фундаментальний інтерфейс обробника визначає єдиний метод `Reconcile`, який викликається пулом воркерів під час вилучення ключа з черги:

```go
type Reconciler interface {
    Reconcile(ctx context.Context, req Request) (Result, error)
}
```

### Структура запиту (`Request`)

На відміну від систем обробки подій, які передають у повідомленні весь об'єкт або дельту змін, запит до контролера передає виключно **ідентифікатор об'єкта**:

```
┌─────────────────┬──────────┬────────────────────────────────────────────────────────┐
│ Поле            │ Тип      │ Призначення                                            │
├─────────────────┼──────────┼────────────────────────────────────────────────────────┤
│ Namespace       │ string   │ Логічний простір імен або орендар (пусто для глобальних)│
│ Name            │ string   │ Унікальне ім'я екземпляра керованого ресурсу           │
└─────────────────┴──────────┴────────────────────────────────────────────────────────┘
```

**Чому запит не містить вміст об'єкта**: передача копії ресурсу в запиті порушує принцип level-triggered. Поки повідомлення очікує в черзі, стан об'єкта в базі даних може змінитися кілька разів. Контролер завжди зобов'язаний виконати свіже читання зі сховища (або актуального локального кешу) на початку фази Observe.

## 2. Семантика результатів виконання (`Result`) та класифікація помилок

Метод `Reconcile` повертає кортеж `(Result, error)`, значення якого детерміновано визначають поведінку черги завдань:

```
┌──────────────┬──────────────┬──────────────┬────────────────────────────────────────────────────┐
│ Result       │ error        │ Поведінка    │ Типовий сценарій застосування                      │
├──────────────┼──────────────┼──────────────┼────────────────────────────────────────────────────┤
│ Requeue: false│ nil          │ Завершено    │ Стан повністю узгоджено (Δ = 0), помилок немає.    │
│ Requeue: true │ nil          │ Повтор зараз │ Конфлікт CAS або двоетапна дія (потрібен крок 2).  │
│ RequeueAfter │ nil          │ Відкладено   │ Періодичний поллінг (наприклад, очікування IP).    │
│ Будь-який    │ non-nil      │ Бекоф-повтор │ Тимчасовий збій (мережевий таймаут, помилка 503).  │
└──────────────┴──────────────┴──────────────┴────────────────────────────────────────────────────┘
```

### Класифікація помилок: тимчасові проти термінальних

Контролер зобов'язаний розрізняти два класи помилок:

1. **Тимчасові помилки (Transient Errors)**:
   - Мережевий розрив або таймаут під час виклику API хмарного провайдера.
   - Перевантаження зовнішнього сервісу (HTTP 429 Too Many Requests, HTTP 503 Service Unavailable).
   - Конфлікт версій при оптимістичному блокуванні (CAS Conflict).
   - *Дія*: повертається `error` або `Result{Requeue: true}`. Черга активує експоненційний бекоф із випадковим джитером.

2. **Термінальні помилки (Terminal / Permanent Errors)**:
   - Синтаксична помилка або невалідне значення в полі `spec` (наприклад, невідомий тип віртуальної машини `cpu: -5`).
   - Відсутність прав доступу (HTTP 401 Unauthorized, HTTP 403 Forbidden).
   - Відсутність обов'язкового зв'язаного ресурсу (наприклад, вказано неіснуючу підмережу VPC).
   - *Дія*: метод повертає `Result{Requeue: false}, nil`. Помилка записується в масив `status.conditions` ресурсу, сигналізуючи користувачеві про необхідність ручного виправлення конфігурації. Повернення `error` у цьому випадку заборонено, оскільки нескінченні повтори безглуздо перевантажують систему.

## 3. Специфікація структури керованого ресурсу

Кожен декларативний ресурс складається з чотирьох стандартизованих розділів:

```yaml
apiVersion: infra.example.com/v1alpha1
kind: ComputeCluster
metadata:
  name: analytics-prod
  namespace: data-platform
  generation: 4
  resourceVersion: "1098234"
  deletionTimestamp: null
  finalizers:
    - infra.example.com/cluster-protection
spec:
  targetReplicas: 10
  instanceType: "m5.2xlarge"
status:
  observedGeneration: 4
  availableReplicas: 10
  phase: "Ready"
  conditions:
    - type: "Ready"
      status: "True"
      lastTransitionTime: "2026-08-20T10:00:00Z"
      reason: "ReconciliationSuccess"
      message: "Усі 10 вузлів успішно створені та готові до навантаження"
```

### Словник метаданих (`metadata`)

```
┌────────────────────┬──────────┬────────────────────────────────────────────────────────┐
│ Поле               │ Тип      │ Призначення та інваріанти                              │
├────────────────────┼──────────┼────────────────────────────────────────────────────────┤
│ generation         │ int64    │ Монотонний лічильник мутацій блоку spec користувачем.  │
│ resourceVersion    │ string   │ Внутрішній маркер транзакції сховища (CAS token).      │
│ deletionTimestamp  │ ISO8601  │ Час ініціації видалення об'єкта (якщо встановлено).    │
│ finalizers         │ []string │ Список активних блокувальників видалення метаданих.    │
└────────────────────┴──────────┴────────────────────────────────────────────────────────┘
```

### Семантика поколінь: `generation` проти `observedGeneration`

Співвідношення між цими двома числовими полями є математичним індикатором завершеності узгодження:

- **`metadata.generation`**: монотонно інкрементується сховищем кожного разу, коли користувач або сторонній клієнт змінює будь-яке поле всередині секції `spec`. Зміна секції `status` або метаданих це поле не змінює.
- **`status.observedGeneration`**: записується контролером після успішного завершення фази Act і відображає покоління специфікації, яке було фактично реалізоване.

Якщо `generation > observedGeneration`, зовнішні спостерігачі та клієнтські інтерфейси розуміють, що контролер ще не завершив обробку останніх змін користувача (система перебуває в процесі переходу). Рівність `generation == observedGeneration` гарантує, що значення в блоці `status` відповідають поточним вимогам `spec`.

### Модель умов стану (`status.conditions`)

Масив умов є стандартним протоколом передачі статусу підсистем:

```
┌────────────────────┬──────────┬────────────────────────────────────────────────────────┐
│ Поле умови         │ Тип      │ Опис                                                   │
├────────────────────┼──────────┼────────────────────────────────────────────────────────┤
│ type               │ string   │ Назва аспекту (Ready, NetworkConfigured, StorageBound) │
│ status             │ string   │ Стан виконання: "True", "False", "Unknown"             │
│ observedGeneration │ int64    │ Значення generation, для якого обчислено цю умову      │
│ lastTransitionTime │ ISO8601  │ Момент часу, коли поле status змінило своє значення    │
│ reason             │ CamelCase│ Машиночитний код причини (ClusterDegraded, QuotaExceeded)│
│ message            │ string   │ Текстове пояснення для людини-оператора                │
└────────────────────┴──────────┴────────────────────────────────────────────────────────┘
```

## 4. Предикати фільтрації подій (Event Predicates)

Щоб уникнути надлишкових спрацьовувань циклу звірки, інформери застосовують предикати фільтрації перед додаванням ключа в чергу:

1. **`GenerationChangedPredicate`**: пропускає подію оновлення (`UpdateEvent`) лише за умови, що `oldObject.metadata.generation != newObject.metadata.generation`. Якщо оновлення стосувалося лише внутрішніх службових міток чи секції `status`, виклик `Reconcile` блокується, запобігаючи нескінченним автогенераціям подій.
2. **`LabelSelectorPredicate`**: ігнорує ресурси, мітки яких не відповідають масці відповідальності поточного контролера.
3. **`AnnotationChangedPredicate`**: використовується, коли контролер очікує спеціальні керуючі анотації (наприклад, `reconcile.infra.example.com/force-resync: "true"`).

## 5. Контракт відмовостійкості: вибори лідера (Leader Election)

У високодоступних середовищах контролер розгортається у кількох екземплярах (репліках). Проте паралельне виконання циклів звірки над спільними фізичними ресурсами без координації спричиняє гонки стану та взаємні перезаписи.

Для забезпечення ексклюзивності застосовується контракт розподіленої оренди (Lease Contract):

```
┌───────────────────────────┬──────────┬────────────────────────────────────────────────┐
│ Поле оренди (Lease)       │ Тип      │ Призначення                                    │
├───────────────────────────┼──────────┼────────────────────────────────────────────────┤
│ holderIdentity            │ string   │ Унікальний ID поточного лідера (наприклад, Pod)│
│ leaseDurationSeconds      │ int32    │ Час дії оренди (типово 15 секунд)              │
│ acquireTime               │ ISO8601  │ Момент первинного захоплення лідерства         │
│ renewTime                 │ ISO8601  │ Момент останнього успішного оновлення оренди   │
│ leaseTransitions          │ int32    │ Загальна кількість змін лідерів                │
└───────────────────────────┴──────────┴────────────────────────────────────────────────┘
```

- Активний лідер зобов'язаний періодично оновлювати поле `renewTime` кожні `T_renew` (типово кожні 2–4 секунди).
- Якщо лідер зазнав аварії і не оновив запис протягом `leaseDurationSeconds` (15 с), резервний екземпляр перехоплює оренду через атомарну CAS-операцію і запускає свій пул воркерів.

## 6. Контракт масштабування (Підресурс `/scale` та HPA)

Для забезпечення автоматичного горизонтального масштабування ресурс зобов'язаний підтримувати стандартний підресурс `/scale`. Цей контракт відокремлює логіку автоскейлера від внутрішньої структури конкретного оператора:

```
┌───────────────────────────┬──────────┬────────────────────────────────────────────────┐
│ Поле підресурсу Scale     │ Шлях     │ Призначення                                    │
├───────────────────────────┼──────────┼────────────────────────────────────────────────┤
│ specReplicasPath          │ string   │ JSONPath до бажаної кількості (.spec.replicas) │
│ statusReplicasPath        │ string   │ JSONPath до поточної кількості (.status.replicas)│
│ labelSelectorPath         │ string   │ JSONPath до селектора для збору метрик         │
└───────────────────────────┴──────────┴────────────────────────────────────────────────┘
```

Завдяки цьому контракту сторонній контролер автоскейлера (наприклад, Horizontal Pod Autoscaler) може зчитувати завантаження CPU та мутувати лише одне числове поле бажаних копій, залишаючи всю фізичну реалізацію запуску та зупинки серверів основному контролеру узгодження.

## 7. Протокол володіння полями (Server-Side Apply та Field Ownership)

Коли одним об'єктом маніпулюють кілька незалежних суб'єктів (наприклад, людина-оператор через GitOps, автоскейлер HPA та контролер інфраструктури), виникає ризик конфлікту модифікацій.

Протокол Server-Side Apply фіксує менеджера для кожного окремого листового поля в блоці `metadata.managedFields`:

```json
{
  "manager": "gitops-argocd",
  "operation": "Apply",
  "apiVersion": "infra.example.com/v1alpha1",
  "fieldsType": "FieldsV1",
  "fieldsV1": {
    "f:spec": {
      "f:instanceType": {}
    }
  }
}
```

```json
{
  "manager": "cluster-autoscaler",
  "operation": "Apply",
  "apiVersion": "infra.example.com/v1alpha1",
  "fieldsType": "FieldsV1",
  "fieldsV1": {
    "f:spec": {
      "f:targetReplicas": {}
    }
  }
}
```

### Правила розв'язання конфліктів володіння

1. **Суверенітет менеджерів**: контролер інфраструктури не має права перезаписувати поле `instanceType`, якщо воно належить `gitops-argocd`.
2. **Конфлікт примусу (Force Apply)**: якщо менеджер бажає перехопити володіння полем, він надсилає запит із прапорцем `force=true`, що перезаписує запис у `managedFields`.
3. **Розділення Spec і Status**: контролери мають ексклюзивне право на оновлення підресурсу `/status`, тоді як зовнішні клієнти мають право мутувати лише `/spec`.

## 8. Метрики та телеметрія циклу узгодження

Кожен промисловий контролер експортує стандартизований набір метрик Prometheus для моніторингу продуктивності та надійності:

```
┌──────────────────────────────────────┬───────────┬───────────────────────────────────────────┐
│ Назва метрики                        │ Тип       │ Опис та цільове призначення              │
├──────────────────────────────────────┼───────────┼───────────────────────────────────────────┤
│ controller_reconcile_total           │ Counter   │ Загальна кількість виконаних ітерацій     │
│ controller_reconcile_errors_total    │ Counter   │ Кількість ітерацій, що завершилися збоєм  │
│ controller_reconcile_time_seconds    │ Histogram │ Гістограма тривалості виконання Reconcile │
│ workqueue_depth                      │ Gauge     │ Поточна кількість ключів у черзі          │
│ workqueue_adds_total                 │ Counter   │ Кількість доданих ключів у чергу          │
│ workqueue_queue_duration_seconds     │ Histogram │ Час перебування ключа в черзі до обробки  │
│ workqueue_work_duration_seconds      │ Histogram │ Час фактичної обробки воркером            │
│ workqueue_retries_total              │ Counter   │ Кількість повторних відправлень через збій│
└──────────────────────────────────────┴───────────┴───────────────────────────────────────────┘
```

Цей контракт гарантує повну прозорість функціонування контролера, дозволяючи системним адміністраторам оперативно виявляти затримки у черзі, сплески помилок API та аномалії дрейфу керованої інфраструктури.
