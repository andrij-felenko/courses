# 📋 Програмні примітиви та контракт систем довговічного виконання

Системи довговічного виконання (Durable Execution) спираються на строгий програмний контракт, який розділяє детерміновану логіку координації та недетерміновані операції введення-виведення. Цей довідник описує фундаментальні програмні примітиви, типи таймаутів, політику повторних спроб, механізми скасування та міжпроцесної взаємодії, спільні для сучасних рушіїв (Temporal, Cadence, Azure Durable Task Framework).

## 1. Робочий процес (Workflow Definition)

Робочий процес — це точка входу детермінованого бізнес-сценарію. Він визначає послідовність викликів, обробку розгалужень, стан та реакцію на зовнішні події.

### Інваріанти виконання коду Workflow
1. **Абсолютна детермінованість:** однаковий вхідний журнал історії зобов'язаний завжди приводити до однакових команд і послідовності викликів.
2. **Заборона прямого I/O:** всередині функції процесу заборонено виконувати сирі мережеві сокети, запити до баз даних чи читання файлової системи. Всі подібні дії виносяться в Activity.
3. **Ізоляція системного часу та генераторів випадковості:** заборонено викликати `time.Now()`, `Date.now()`, `rand()` або читати глобальні змінні оточення. Для роботи з часом використовується контекстний метод `workflow.Now()`, який повертає детермінований час поточної події з журналу.
4. **Заборона некерованої багатопоточності:** запуск нативних потоків операційної системи заборонено, оскільки порядок їхнього планування не піддається детермінованому відтворенню. Дозволено лише корутини або структуровані асинхронні задачі, керовані рушієм.

## 2. Активність (Activity Definition)

Активність — це одиниця виконання побічних ефектів. Вона інкапсулює реальну взаємодію із зовнішніми системами: виклики REST API, SQL-транзакції, генерацію PDF чи надсилання push-сповіщень.

### Конфігурація запуску Activity

| Параметр | Тип | Обов'язковий | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `TaskQueue` | `string` | Так | Назва черги задач, яку опитують відповідні Activity-воркери. |
| `ScheduleToCloseTimeout` | `Duration` | Ні | Максимальний загальний час від моменту створення задачі до її остаточного завершення (включно з чергою та всіма повторами). |
| `ScheduleToStartTimeout` | `Duration` | Ні | Максимальний час очікування задачі в черзі до взяття вільним воркером. |
| `StartToCloseTimeout` | `Duration` | Так | Ліміт часу на виконання однієї окремої спроби активності. |
| `HeartbeatTimeout` | `Duration` | Ні | Максимальний інтервал між сигналами живості (heartbeat) від воркера для тривалих операцій. |
| `RetryPolicy` | `RetryPolicy` | Ні | Політика автоматичних повторів при виникненні помилок. |

## 3. Чотири виміри таймаутів Activity

У розподілених системах класичний єдиний таймаут призводить або до передчасного переривання операцій, або до нескінченного зависання черг. Модель довговічного виконання впроваджує 4 ортогональні виміри:

```
[Подія: ScheduleActivity]
   |
   | <--- ScheduleToStart Timeout ---> (Час у черзі задач)
   v
[Воркер взяв задачу в роботу: ActivityStarted]
   |
   | <--- StartToClose Timeout ---> (Час 1 спроби виконання)
   | <--- Heartbeat Timeout ---> (Інтервал контролю живості)
   v
[Помилка спроби 1] -> [Пауза Backoff] -> [Спроба 2] ...
   |
   v
[Остаточний успіх або вичерпання спроб: ActivityCompleted/Failed]

|<------------------------ ScheduleToClose Timeout ------------------------>|
```

### Призначення кожного таймауту
1. **ScheduleToStart Timeout:** запобігає ситуаціям, коли воркери черги впали, а задачі накопичуються в пам'яті й втрачають актуальність. Якщо таймаут сплив, задача не передається на виконання, а процес отримує помилку таймауту черги.
2. **StartToClose Timeout:** захищає від зависання однієї спроби (наприклад, невідповідаючий сокет HTTP). Якщо спроба не вклалася в ліміт, воркер вважається збійним, і рушій запускає повторну спробу за політикою.
3. **Heartbeat Timeout:** критичний для задач, що тривають годинами (наприклад, кодування відео чи навчання ML-моделі). Воркер періодично викликає `activity.RecordHeartbeat(ctx, progress)`. Якщо воркер помре або його контейнер вб'є OOM-killer, рушій помітить відсутність пульсу за лічені секунди (не чекаючи закінчення тривалого `StartToClose`) і негайно перезапустить задачу на іншому вузлі.
4. **ScheduleToClose Timeout:** глобальний запобіжник. Він встановлює максимальну планку тривалості всього циклу з урахуванням усіх збоїв і пауз бекофу.

## 4. Політика повторних спроб (RetryPolicy)

Автоматичний механізм відновлення при тимчасових інфраструктурних збоях.

| Поле | Тип | За замовчуванням | Опис |
| :--- | :--- | :--- | :--- |
| `InitialInterval` | `Duration` | `1s` | Початкова пауза перед першою повторною спробою. |
| `BackoffCoefficient` | `float64` | `2.0` | Множник експоненційного зростання інтервалу. |
| `MaximumInterval` | `Duration` | `100 × Initial` | Верхня межа паузи між спробами. |
| `MaximumAttempts` | `int` | `0` (безлімітно) | Максимальна кількість спроб (`0` або `1` = без обмежень, доки діє таймаут). |
| `NonRetryableErrorTypes` | `[]string` | `[]` | Список типів бізнес-помилок, які заборонено повторювати. |

### Формула обчислення інтервалу повтору
Для спроби з номером `k` (де `k ≥ 1`) інтервал затримки з повним джитером обчислюється як:

```
Базовий інтервал:  T[k] = min(InitialInterval · BackoffCoefficient^(k - 1), MaximumInterval)
Реальна затримка:  Затримка = UniformRandom(0.8 · T[k], 1.2 · T[k])
```

## 5. Примітиви синхронізації та взаємодії

Крім послідовного виклику активностей, рушій надає спеціальні асинхронні примітиви для координації процесів:

### 1. Довговічні таймери (Durable Timers / Sleep)
* **Сигнатура:** `workflow.Sleep(ctx, duration)` або `workflow.NewTimer(ctx, duration)`.
* **Семантика:** призупиняє виконання процесу на заданий проміжок часу (від 1 секунди до кількох років).
* **Поведінка:** не утримує пам'ять чи ресурси процесора на воркері. Рушій записує подію в базу даних і активує задачу, коли спливе час.

### 2. Сигнали (Signals)
* **Сигнатура:** `workflow.GetSignalChannel(ctx, "signalName")` (приймання) / `client.SignalWorkflow(id, "signalName", data)` (відправка).
* **Семантика:** асинхронне надсилання зовнішнього повідомлення у працюючий процес (наприклад, підтвердження оплати від платіжного шлюзу або скасування замовлення користувачем).
* **Властивість:** сигнали буферизуються в історії процесу та не губляться, навіть якщо процес у цей момент виконує іншу дію.

### 3. Запити (Queries)
* **Сигнатура:** `workflow.SetQueryHandler(ctx, "queryName", handlerFunc)` (обробник) / `client.QueryWorkflow(id, "queryName")` (виклик).
* **Семантика:** синхронне зчитування поточного внутрішнього стану процесу (наприклад, прогрес обробки чи перелік виконаних кроків).
* **Властивість:** запит є строго *read-only*. Він не додає жодних подій в історію, виконується локально в пам'яті воркера через replay і не створює навантаження на базу даних історії.

### 4. Оновлення (Updates)
* **Сигнатура:** `workflow.SetUpdateHandler(ctx, "updateName", handler, validatorFunc)` / `client.UpdateWorkflow(...)`.
* **Семантика:** синхронна мутація стану процесу з гарантією доставки та отриманням поверненого результату.
* **Властивість:** поєднує надійність сигналу та синхронність запиту: спочатку викликається валідатор, і якщо дані коректні, мутація фіксується в історії подій, а клієнт отримує підтвердження.

## 6. Скасування та компенсація (Cancellation Scopes)

Коли клієнт ініціює скасування процесу через `client.CancelWorkflow(...)`, рушій генерує подію `WorkflowExecutionCancelRequested`.

1. **Контекст скасування:** поточний контекст процесу `ctx` отримує сигнал переривання, перериваючи активні очікування таймерів або виконання задач.
2. **Незнищенне завершення (Cleanup & Compensation):** для виконання компенсаційних дій (наприклад, повернення коштів чи розблокування товару) розробник створює відокремлений контекст:
   ```go
   disconnectedCtx, _ := workflow.NewDisconnectedContext(ctx)
   ctx.ExecuteActivity(disconnectedCtx, "RefundPayment", paymentID)
   ```
   Відокремлений контекст ігнорує сигнал скасування батьківського процесу, гарантуючи, що компенсаційні активності виконаються до кінця.

## 7. Дочірні процеси (Child Workflows)

Для декомпозиції складних систем процес може запускати інші довговічні процеси як дочірні:
* **Батьківський зв'язок:** дочірній процес має власну ізольовану історію подій, що запобігає переповненню історії головного процесу.
* **Політика завершення (ParentClosePolicy):** визначає поведінку дочірнього процесу при завершенні батька:
  * `TERMINATE` — негайно примусово знищити дочірній процес.
  * `REQUEST_CANCEL` — надіслати дочірньому процесу сигнал скасування для коректного згортання.
  * `ABANDON` — залишити дочірній процес працювати автономно у фоні.

## 8. Керування версіями (Workflow Versioning)

Оскільки процеси можуть тривати тижні чи місяці, зміна вихідного коду може зламати replay для вже запущених екземплярів. Для безпечного оновлення застосовується примітив версіонування:

```go
// Приклад виклику workflow.GetVersion у середовищі Go/Temporal
version := workflow.GetVersion(ctx, "ChangeID_AddFraudCheck", workflow.DefaultVersion, 1)
if version == workflow.DefaultVersion {
    // Стара поведінка для процесів, що стартували до релізу
    ctx.ExecuteActivity("ProcessPayment", orderID)
} else {
    // Нова логіка для всіх нових процесів
    ctx.ExecuteActivity("CheckFraudScore", orderID)
    ctx.ExecuteActivity("ProcessPayment", orderID)
}
```

* **DefaultVersion:** спеціальне значення (`-1`), яке повертається під час replay, якщо у збереженій історії ще не було запису про цю зміну коду.
* **Семантика:** `GetVersion` записує маркер версії в журнал історії при першому проході. Наступні replay гарантовано повертають зафіксовану версію, забезпечуючи детермінізм.

## 9. Продовження як новий процес (Continue-As-New)

Для нескінченних або циклічних процесів (наприклад, моніторинг пристрою IoT, що опитує датчик щохвилини) журнал історії не може рости безкінечно.

* **Сигнатура:** `workflow.NewContinueAsNewError(ctx, newWorkflowFunc, newArgs...)`.
* **Семантика:** завершує поточний життєвий цикл процесу та атомарно створює новий екземпляр із тим самим `WorkflowID`, очищеною історією подій та переданим оновленим станом як аргументом.
* **Рекомендація:** виконувати `ContinueAsNew`, коли кількість подій в історії наближається до 2000–5000 подій або розмір історії перевищує 10–20 МБ.
