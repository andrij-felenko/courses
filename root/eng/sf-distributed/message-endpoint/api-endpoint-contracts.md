# 📋 Контракти та інтерфейси Message Endpoint: шлюзи, слухачі та контроль потоку

Архітектурна надійність кінцевої точки повідомлень (Message Endpoint) спирається на строгу типізацію контрактів взаємодії між прикладним доменом і транспортною інфраструктурою черг. Цей довідник визначає канонічні інтерфейси, структури даних конверта повідомлення, протоколи підтвердження доставки, конфігураційні параметри контролю потоку та формати службових метаданих розподіленого трасування.

У розподіленій системі кінцева точка виступає єдиним швом між двома принципово різними середовищами: світом високорівневої об'єктної бізнес-моделі та світом асинхронного двійкового транспорту. Якщо контракти цього шва розмиті або визначені неповністю, інфраструктурні деталі брокера (мережеві фрейми, мітки доставки, коди помилок з'єднання) неминуче просочуються в доменну логіку, руйнуючи модульність і унеможливлюючи ізольоване тестування. Наведені нижче інтерфейси та структури формують повний технологічно нейтральний каркас кінцевої точки.

## 1. Специфікація конверта повідомлення (Message Envelope)

Конверт повідомлення є фундаментальною структурою даних, яка розділяє службові системні метадані транспорту та прикладне тіло корисного навантаження. Завдяки цій структурі проміжні вузли маршрутизації, фільтри та диспетчери можуть приймати рішення щодо обробки пакета (наприклад, перевіряти ключ партиції, час життя чи заголовки трасування), не витрачаючи ресурси процесора на десеріалізацію всього бізнес-документа.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    СТРУКТУРА КОНВЕРТА MESSAGE ENVELOPE                      │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. Ідентифікатори та кореляція:                                             │
│    • id (UUIDv7): Унікальний ідентифікатор повідомлення з міткою часу.     │
│    • correlation_id (UUID): Ідентифікатор початкового запиту (Request-Reply)│
│    • causation_id (UUID): ID повідомлення-причини, що породило цю подію.    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. Маршрутизація та адресація:                                              │
│    • partition_key (String): Ключ партиції для збереження послідовності.    │
│    • reply_to (String): Адреса тимчасового каналу для повернення відповіді. │
│    • destination (String): Назва цільової черги або топіка.                 │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. Службові атрибути та життєвий цикл:                                      │
│    • timestamp (int64_t): Час генерації (мс від початку UTC Epoch).         │
│    • expires_at (int64_t): Абсолютний час інвалідації (TTL повідомлення).   │
│    • content_type (String): MIME-тип ("application/json", "application/x-protobuf")│
│    • schema_version (uint16_t): Номер версії схеми для мапера.              │
├─────────────────────────────────────────────────────────────────────────────┤
│ 4. Розподілене трасування (W3C Trace Context):                              │
│    • traceparent (String): "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01" │
│    • tracestate (String): Вендор-специфічні пари ключ-значення.             │
├─────────────────────────────────────────────────────────────────────────────┤
│ 5. Стан доставки та надійності:                                             │
│    • delivery_attempt (uint32_t): Лічильник спроб обробки (1 для першої).   │
│    • redelivered (bool): Ознака повторної доставки після аварії споживача.  │
├─────────────────────────────────────────────────────────────────────────────┤
│ 6. Бізнес-тіло (Payload):                                                   │
│    • payload (T / binary_buffer): Типізований об'єкт або сирий масив байтів.│
└─────────────────────────────────────────────────────────────────────────────┘
```

### Детальний опис полів заголовків та їхнє інженерне призначення

- **`id` (Ідентифікатор повідомлення):** канонічно використовує формат UUID версії 7 (UUIDv7). На відміну від випадкового UUIDv4, перші 48 бітів UUIDv7 містять мітку часу Unix у мілісекундах. Це забезпечує природне сортування за часом створення та дозволяє базам даних ефективно індексувати вхідні таблиці `inbox` без фрагментації B-дерева на диску.
- **`correlation_id` (Ідентифікатор кореляції):** зв'язує ланцюжок повідомлень у шаблоні «Запит-Відповідь» або розподіленій сазі. Відправник генерує унікальний ідентифікатор і передає його в запиті; сервіс-відповідач копіює це значення у відповідне поле свого вихідного повідомлення, дозволяючи шлюзу знайти заблокований клієнтський потік.
- **`causation_id` (Ідентифікатор причинності):** фіксує ідентифікатор повідомлення, прямим наслідком якого стала поточна подія. Наприклад, якщо повідомлення `OrderPlaced` спричинило відправку команди `ReserveStock`, поле `causation_id` команди містить `id` події замовлення. Це дає змогу будувати повні графи причинно-наслідкових зв'язків під час аудиту розподілених бізнес-процесів.
- **`partition_key` (Ключ партиції):** використовується для збереження строгого порядку доставки подій, що стосуються одного бізнес-агрегата. Кінцева точка хешує це поле для вибору конкретної черги або партиції брокера (наприклад, партиції топіка Apache Kafka), гарантуючи послідовне виконання без гонок стану.
- **`expires_at` (Час життя / TTL):** абсолютна мітка часу, після настання якої повідомлення втрачає бізнес-актуальність. Якщо черга була перевантажена й повідомлення пролежало в буфері довше за вказаний термін, канальний адаптер відкидає його без виклику доменної логіки.
- **`traceparent` та `tracestate` (W3C Trace Context):** стандартизовані заголовки розподіленого трасування (специфікація W3C Recommendation). Поле `traceparent` кодує версію протоколу, 16-байтний ідентифікатор розподіленого сліду (Trace ID), 8-байтний ідентифікатор батьківського спану (Parent Span ID) та прапорці трасування (Trace Flags). Кінцева точка витягує цей заголовок і автоматично активує контекст OpenTelemetry перед викликом бізнес-методу.

### Оголошення структур мовою C++20

```cpp
#include <string>
#include <optional>
#include <unordered_map>
#include <cstdint>

struct MessageHeaders {
    // Ідентифікатори та кореляція
    std::string id;                                     // UUIDv7
    std::optional<std::string> correlation_id;
    std::optional<std::string> causation_id;
    
    // Адресація та маршрутизація
    std::string partition_key;                          // Ключ сутності
    std::optional<std::string> reply_to;                // Адреса відповіді
    std::string destination;                            // Цільовий топік/черга
    
    // Метадані вмісту та часу
    std::string content_type = "application/json";
    int64_t timestamp_utc_ms = 0;
    int64_t expires_at_utc_ms = 0;                      // 0 = без обмеження
    uint16_t schema_version = 1;
    
    // Стан надійності
    uint32_t delivery_attempt = 1;
    bool redelivered = false;
    
    // Розподілене трасування W3C
    std::string traceparent;
    std::string tracestate;
    
    // Користувацькі додаткові атрибути
    std::unordered_map<std::string, std::string> custom_attributes;
};

template <typename TPayload>
struct Message {
    MessageHeaders headers;
    TPayload payload;
};
```

## 2. Інтерфейс вихідного шлюзу (Messaging Gateway)

Шлюз повідомлень надає прикладному коду синхронні та асинхронні методи відправки повідомлень. Його головна відповідальність — повністю приховати від доменного коду факт використання конкретного мережевого протоколу, сокетів, пулів з'єднань і форматів серіалізації.

```cpp
#include <future>
#include <chrono>

template <typename TRequest, typename TResponse = void>
class IMessagingGateway {
public:
    virtual ~IMessagingGateway() = default;

    // Асинхронна одностороння публікація події (Fire-and-Forget)
    // Повертає future, який виконується після передачі в локальний буфер або Outbox.
    virtual std::future<void> sendAsync(const Message<TRequest>& message) = 0;

    // Синхронна відправка з очікуванням підтвердження від брокера
    // Блокує викликальний потік до отримання мережевого Publisher Confirm.
    virtual void sendSync(
        const Message<TRequest>& message,
        std::chrono::milliseconds timeout
    ) = 0;

    // Асинхронний запит-відповідь (Request-Reply)
    // Створює тимчасову чергу відповідей і повертає майбутній результат.
    virtual std::future<Message<TResponse>> sendAndReceiveAsync(
        const Message<TRequest>& request,
        std::chrono::milliseconds timeout
    ) = 0;
};
```

### Поведінкові вимоги та контракти методів вихідного шлюзу

- **Володіння пам'яттю та копіювання:** шлюз приймає повідомлення за константним посиланням або переміщенням (`std::move`). Якщо повідомлення передається у фонову нитку відправки, шлюз виконує переміщення ресурсів без глибокого копіювання корисного навантаження.
- **Обробка таймаутів у `sendSync`:** якщо брокер не надсилає мережеве підтвердження запису протягом інтервалу `timeout`, метод кидає виняток `GatewayTimeoutException`. При цьому викликальний код зобов'язаний вважати стан повідомлення невизначеним (воно могло зберегтися в брокері, але підтвердження втрачено через обрив сокета).
- **Механіка `sendAndReceiveAsync`:** шлюз автоматично створює тимчасову ексклюзивну чергу (або використовує спільну чергу відповідей із фільтрацією за `Correlation-Id`), вписує її адресу в заголовок `Reply-To`, генерує унікальний `Correlation-Id` і реєструє обіцянку `std::promise` у внутрішній таблиці очікування. Після надходження відповіді відповідний `promise` заповнюється даними, а тимчасовий запис видаляється з пам'яті.

## 3. Інтерфейс вхідного слухача та активатора (Service Activator & Listener)

Вхідна кінцева точка перетворює потік повідомлень із черги на виклики бізнес-методів. Ключовим елементом контракту є розділення самої бізнес-обробки та керування життєвим циклом підтвердження доставки через об'єкт `IAcknowledgmentHandle`.

```cpp
#include <memory>
#include <string>
#include <exception>

// Дескриптор явного підтвердження обробки повідомлення
class IAcknowledgmentHandle {
public:
    virtual ~IAcknowledgmentHandle() = default;

    // Успішна фіксація: видалити повідомлення з черги брокера (Commit/ACK)
    virtual void ack() = 0;

    // Тимчасова відмова: повернути повідомлення в чергу для повторної спроби (NACK/Requeue)
    virtual void nack(bool requeue, const std::string& reason) = 0;

    // Фатальна помилка (отруйний пакет): перемістити повідомлення в Dead-Letter Queue (DLQ)
    virtual void rejectToDlq(const std::string& error_code, const std::string& error_details) = 0;
};

// Інтерфейс зворотного виклику для вхідних бізнес-повідомлень
template <typename TPayload>
class IMessageListener {
public:
    virtual ~IMessageListener() = default;

    // Викликається воркером при успішній десеріалізації вхідного повідомлення
    virtual void onMessage(
        const Message<TPayload>& message,
        std::unique_ptr<IAcknowledgmentHandle> ack_handle
    ) = 0;

    // Викликається при пошкодженні даних, невідомому форматі або помилці схеми
    virtual void onSystemError(
        const std::string& raw_payload_bytes,
        const MessageHeaders& raw_headers,
        const std::exception& error,
        std::unique_ptr<IAcknowledgmentHandle> ack_handle
    ) = 0;
};
```

### Інваріанти безпеки та обробка аварійних ситуацій у слухачі

1. **Одноразовість завершення дескриптора:** над об'єктом `IAcknowledgmentHandle` дозволено викликати рівно одну дію — або `ack()`, або `nack()`, або `rejectToDlq()`. Будь-який повторний виклик методу на тому самому дескрипторі повинен ігноруватися або кидати виняток `IllegalStateException`.
2. **Захист від витоку непідтверджених повідомлень (RAII-гарантія):** якщо бізнес-код у методі `onMessage()` кидає необроблений виняток і аварійно виходить зі стека, не викликавши підтвердження, розумний деструктор реалізації `IAcknowledgmentHandle` зобов'язаний автоматично викликати `nack(true, "Worker exception leak")`. Це запобігає «зависанню» заблокованого повідомлення в буфері брокера до моменту завершення таймауту сесії.
3. **Обробка системних помилок через `onSystemError`:** якщо вхідне повідомлення не вдається десеріалізувати через пошкоджений JSON або несумісність версій Protobuf, кінцева точка не повинна кидати аварійний виняток у потік сокета. Вона передає сирі байти та заголовки методу `onSystemError`, який типово викликає `ack_handle->rejectToDlq(...)`, відправляючи зіпсований пакет в ізолятор DLQ та зберігаючи безперервну роботу черги.

## 4. Життєвий цикл канального адаптера (Channel Adapter Lifecycle)

Канальний адаптер управляє фізичним мережевим з'єднанням, реєстрацією споживачів у брокері та внутрішніми потоками опитування. Він функціонує як детермінований скінченний автомат станів (State Machine).

```
       ┌──────────────┐
       │   STOPPED    │ ◄──────────────────────────────┐
       └──────┬───────┘                                │
              │ start()                                │
              ▼                                        │
       ┌──────────────┐                                │
       │  CONNECTING  │ ──( Помилка з'єднання )──┐      │
       └──────┬───────┘                          │     │
              │ успішний Handshake               ▼     │
              ▼                           ┌───────────┐│
       ┌──────────────┐                   │ BACKOFF   ││
  ┌──► │   RUNNING    │                   │ RECONNECT ││
  │    └──────┬───────┘                   └─────┬─────┘│
  │           │ pause()                         │      │
  │ resume()  ▼                                 │      │ stop()
  │    ┌──────────────┐                         │      │
  └─── │    PAUSED    │                         │      │
       └──────┬───────┘                         │      │
              │                                 │      │
              └───────────────( stop() )────────┴──────┘
```

```cpp
enum class AdapterState {
    STOPPED,        // Адаптер ініціалізовано, але з'єднання не відкриті
    CONNECTING,     // Триває встановлення TCP-сесії, TLS та аутентифікація
    RUNNING,        // Активне вичитування повідомлень і передача воркерам
    PAUSED,         // Тимчасова зупинка вичитування через протитиск або спрацювання запобіжника
    RECONNECTING,   // Втрата зв'язку: триває експоненційне очікування перед новою спробою
    DRAINING        // Зупинка: нові пакети не приймаються, триває завершення активних задач
};

class IChannelAdapterLifecycle {
public:
    virtual ~IChannelAdapterLifecycle() = default;

    // Відкриття з'єднань, реєстрація споживачів та запуск диспетчера
    virtual void start() = 0;

    // Тимчасове призупинення вичитування сокета (Backpressure / Circuit Breaker)
    virtual void pause() = 0;

    // Відновлення вичитування після нормалізації черг або відновлення БД
    virtual void resume() = 0;

    // Безпечне дренування активних завдань і плавне закриття ресурсів
    virtual void stop(std::chrono::milliseconds drain_timeout) = 0;

    // Отримання поточного стану автомата
    virtual AdapterState getState() const = 0;
};
```

### Опис фаз життєвого циклу

- **Фаза `CONNECTING` та `RECONNECTING`:** адаптер намагається встановити з'єднання з брокером. Якщо мережа недоступна, адаптер не блокує викликальний потік запуску програми, а переходить у режим фонового відновлення зв'язку з випадковим експоненційним відтермінуванням (Full Jitter Backoff).
- **Фаза `PAUSED`:** застосовується при досягненні верхнього порогу пам'яті (High Watermark) або при переході внутрішнього запобіжника у стан `OPEN`. Адаптер припиняє читання сокета (у протоколі AMQP відкликає кредит або перестає викликати `basic.get`, у Kafka перестає викликати `poll()`), змушуючи брокер зберігати повідомлення у власних чергах на диску.
- **Фаза `DRAINING`:** активується при отриманні сигналу завершення роботи застосунку (`SIGTERM`). Адаптер негайно скасовує реєстрацію споживача в брокері, щоб запобігти надходженню нових повідомлень, і надає вже запущеним воркерам інтервал `drain_timeout` для коректного збереження транзакцій у базі даних та відправки фінальних ACK.

## 5. Конфігураційні параметри контролю потоку та QoS

Налаштування поведінки кінцевої точки здійснюється через типізовану структуру конфігурації. Ці параметри визначають пропускну здатність, споживання пам'яті процесу та стійкість до відмов.

```cpp
struct EndpointConfig {
    // 1. Мережевий транспорт та брокер
    std::string broker_endpoint_url;
    std::string queue_or_topic_name;
    std::string consumer_group_id;
    
    // 2. Якість обслуговування (QoS) та префетч
    uint16_t prefetch_count = 50;           // Максимум непідтверджених повідомлень
    bool enable_auto_ack = false;           // Суворо заборонено для надійних систем
    
    // 3. Пул воркерів та шардування
    uint16_t worker_threads_count = 8;      // Кількість паралельних ниток обробки
    size_t worker_queue_capacity = 1000;    // Максимальна глибина черги одного воркера
    
    // 4. Пороги протитиску (Backpressure Watermarks)
    double high_watermark_ratio = 0.80;     // При 80% заповнення буферів -> pause()
    double low_watermark_ratio = 0.20;      // При спаді заповнення до 20% -> resume()
    
    // 5. Політика повторів (Retry Policy)
    uint32_t max_retry_attempts = 5;
    std::chrono::milliseconds initial_retry_interval{100};
    std::chrono::milliseconds max_retry_interval{30000};
    double backoff_multiplier = 2.0;
    bool enable_full_jitter = true;
    
    // 6. Мертва черга (DLQ)
    std::string dlq_topic_name = "dead_letter_queue";
    
    // 7. Безпечне завершення (Graceful Shutdown)
    std::chrono::milliseconds drain_timeout{25000};
};
```

### Інженерне обґрунтування та правила вибору параметрів

| Параметр | Тип | За замовчуванням | Інженерний вплив та правила налаштування |
| :--- | :--- | :--- | :--- |
| `prefetch_count` | `uint16_t` | `50` | Визначає розмір непідтвердженого вікна доставки в сокеті. Занизьке значення (`1`) створює простої через час мережевого обходу (RTT); зависоке (`10 000`) призводить до вичерпання RAM при надходженні сплеску великих повідомлень. |
| `worker_threads_count` | `uint16_t` | `std::thread::hardware_concurrency()` | Кількість потоків у пулі обробки. Для операцій з інтенсивним I/O (звернення до БД) призначають `2 · CPU_cores`, для обчислювальних задач — строго `CPU_cores`. |
| `worker_queue_capacity` | `size_t` | `1000` | Максимальна кількість повідомлень, які можуть очікувати обробки в пам'яті черги одного воркера перед активацією сигналів протитиску. |
| `high_watermark_ratio` | `double` | `0.80` | Відносний поріг заповненості буферів воркерів (80%), досягнення якого змушує адаптер викликати `pause()`, зупиняючи прийом трафіку з мережі. |
| `low_watermark_ratio` | `double` | `0.20` | Нижній поріг гістерезису (20%), при досягненні якого вичитування сокета відновлюється. Гістерезис запобігає шкідливому миготінню паузи при коливанні черги навколо одного значення. |
| `max_retry_attempts` | `uint32_t` | `5` | Гранична кількість спроб повторної обробки при тимчасових збоях. Після вичерпання спроб повідомлення перенаправляється в мертву чергу (DLQ). |

## 6. Контракт сховища ідемпотентності (Idempotency Store / Inbox Contract)

Сховище ідемпотентності забезпечує дедуплікацію повідомлень на вході доменної логіки. Інтерфейс підтримує протокол двоетапного захоплення (Two-Phase Claim), що запобігає як повторній обробці вже виконаних подій, так і блокуванню повідомлень при раптовому падінні воркера посеред виконання.

```cpp
enum class ClaimResult {
    ACQUIRED_NEW,       // Повідомлення нове: блокування захоплено, виконати бізнес-домен
    DUPLICATE_RESOLVED, // Повідомлення вже було успішно оброблено раніше -> негайний ACK
    IN_FLIGHT_CONFLICT  // Повідомлення прямо зараз обробляється іншим воркером -> відкласти
};

class IIdempotencyStore {
public:
    virtual ~IIdempotencyStore() = default;

    // Спроба атомарно захопити право на обробку Message-ID
    // lock_ttl захищає від вічного зависання при падінні процесу
    virtual ClaimResult tryClaim(
        const std::string& message_id,
        std::chrono::milliseconds lock_ttl
    ) = 0;

    // Фіксація успішної обробки з тривалим часом зберігання запису
    virtual void markProcessed(
        const std::string& message_id,
        std::chrono::milliseconds record_ttl
    ) = 0;

    // Звільнення блокування при помилці для дозволу повторних спроб
    virtual void releaseClaim(const std::string& message_id) = 0;
};
```

### Механіка взаємодії активатора зі сховищем ідемпотентності

1. **Етап 1: Захоплення блокування (`tryClaim`):** перед викликом бізнес-методу активатор звертається до сховища (Redis або локальної SQL-таблиці `inbox`). Якщо запис відсутній, сховище створює тимчасовий запис зі статусом `PROCESSING` і повертає `ACQUIRED_NEW`.
2. **Етап 2: Обробка дублікатів:** якщо сховище бачить статус `COMPLETED`, повертається `DUPLICATE_RESOLVED`. Активатор пропускає виконання доменної логіки і негайно надсилає `ack()`, підтверджуючи видалення надлишкової копії. Якщо статус `PROCESSING` (подія прямо зараз виконується сусіднім вузлом), повертається `IN_FLIGHT_CONFLICT`, і повідомлення відкладається з повтором через невеликий інтервал.
3. **Етап 3: Фіксація успіху (`markProcessed`):** після успішного коміту транзакції в основній базі даних активатор переводить статус запису в `COMPLETED` із тривалим часом життя (наприклад, 7 днів), гарантуючи захист від запізнілих дублікатів.

## 7. Селективний споживач та фільтрація заголовків (Selective Consumer Contract)

Патерн **Селективний споживач** (англ. *Selective Consumer*) дозволяє кінцевій точці фільтрувати потік повідомлень на рівні заголовків, відсікаючи нецікаві події до моменту виділення пам'яті під бізнес-об'єкт.

```cpp
class IMessageSelector {
public:
    virtual ~IMessageSelector() = default;

    // Повертає true, якщо повідомлення відповідає критеріям підписки
    virtual bool matches(const MessageHeaders& headers) const = 0;
    
    // Текстовий вираз селектора у форматі SQL-92 (наприклад: "country = 'UA' AND amount > 100")
    virtual std::string getExpression() const = 0;
};
```

### Рівні фільтрації в розподіленому конвеєрі

- **Фільтрація на стороні брокера (Broker-Side Filtering):** підтримується протоколами JMS та AMQP (Header Exchanges). Брокер порівнює атрибути пакета з виразом селектора і пересилає в сокет клієнта лише релевантні пакети. Це заощаджує мережеву пропускну здатність і розвантажує клієнтську машину.
- **Фільтрація на стороні кінцевої точки (Client-Side Endpoint Filtering):** застосовується в системах на кшталт Apache Kafka, де брокер не розбирає довільні користувацькі заголовки. Канальний адаптер читає конверт, викликає `selector->matches(headers)`, і якщо результат `false`, негайно фіксує зміщення (commit offset), не передаючи пакет у пул воркерів і не навантажуючи бізнес-сервіси.

## 8. Контракт квитанції у камері схову (Claim Check Integration)

Коли розмір корисного навантаження перевищує ліміт брокера повідомлень (наприклад, 1 МБ у Kafka або 256 КБ у RabbitMQ/AWS SQS), шлюз та активатор кінцевої точки автоматично підключають механізм **Claim Check** (Квитанція у камері схову).

```cpp
class IClaimCheckPayloadStore {
public:
    virtual ~IClaimCheckPayloadStore() = default;

    // Збереження великого бінарного об'єкта в S3/Blob Storage
    // Повертає URI збереженого ресурсу (квитанцію)
    virtual std::future<std::string> uploadPayloadAsync(
        const std::string& payload_bytes,
        std::chrono::milliseconds timeout
    ) = 0;

    // Завантаження бінарного об'єкта за URI квитанції
    virtual std::future<std::string> downloadPayloadAsync(
        const std::string& claim_check_uri,
        std::chrono::milliseconds timeout
    ) = 0;
};
```

### Протокол прозорої підміни тіла повідомлення

1. **На стороні вихідного шлюзу:**
   - Шлюз перевіряє розмір серіалізованого корисного навантаження.
   - Якщо `size > threshold_bytes` (наприклад, 500 КБ), шлюз асинхронно відправляє байти в об'єктне сховище (Amazon S3 / MinIO).
   - Отриманий URI (наприклад, `s3://payload-store/orders/2026/08/uuid-7.bin`) записується в заголовок `x-claim-check-uri`, а саме тіло повідомлення очищується або замінюється коротким покажчиком.
   - Повідомлення з розміром у кілька сотень байтів відправляється в стандартну чергу брокера.

2. **На стороні вхідного активатора:**
   - Активатор перевіряє наявність заголовка `x-claim-check-uri`.
   - Якщо заголовок присутній, адаптер звертається до `IClaimCheckPayloadStore`, прозоро завантажує повне бінарне тіло документа, десеріалізує його в об'єкт домену і передає методу `onMessage()`.
   - Доменний сервіс отримує повноцінний бізнес-об'єкт, взагалі не знаючи про факт вивантаження даних у зовнішнє сховище.

## 9. Метрики спостережливості кінцевої точки (Observability & Metrics)

Кожна промислова кінцева точка повинна експортувати стандартизовані метрики у форматі OpenMetrics / Prometheus. Це дозволяє команді експлуатації виявляти аномалії, лаги та перевантаження черг до настання аварії.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    КЛЮЧОВІ МЕТРИКИ MESSAGE ENDPOINT                         │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. Лічильники подій (Counters):                                             │
│    • endpoint_messages_received_total{destination, status}                  │
│    • endpoint_messages_sent_total{destination, status}                      │
│    • endpoint_retries_total{destination, exception_class}                   │
│    • endpoint_dlq_routed_total{destination, reason}                         │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. Гістограми тривалості (Histograms):                                      │
│    • endpoint_processing_duration_seconds{destination}                      │
│    • endpoint_queue_wait_duration_seconds{destination}                      │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. Миттєві показники стану (Gauges):                                        │
│    • endpoint_active_workers_count{destination}                             │
│    • endpoint_buffer_utilization_ratio{destination}                         │
│    • endpoint_circuit_breaker_state{destination} (0=Closed, 1=Half, 2=Open) │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **`endpoint_queue_wait_duration_seconds`:** час, який повідомлення провело у черзі воркера перед початком виконання. Зростання цього показника є первинним сигналом нестачі потоків або деградації швидкості бази даних.
- **`endpoint_buffer_utilization_ratio`:** відношення поточної кількості завдань у пам'яті до `worker_queue_capacity`. Якщо показник наближається до `0.80`, це свідчить про наближення спрацювання механізму зворотного протитиску (Backpressure).

## 10. Контракт динамічної реконфігурації та безпечної ротації ключів

У промислових хмарних середовищах кінцева точка повинна підтримувати зміну параметрів (розмір пулу воркерів, префетч, ліміти таймаутів) без перезапуску процесу (Zero-Downtime Reconfiguration).

```cpp
class IEndpointConfigListener {
public:
    virtual ~IEndpointConfigListener() = default;

    // Викликається при зміні конфігурації у зовнішньому джерелі (Consul / Spring Cloud Config)
    virtual void onConfigUpdated(const EndpointConfig& new_config) = 0;
};
```

При отриманні оновленої структури `EndpointConfig` канальний адаптер виконує плавне масштабування пулу воркерів:
- Якщо кількість потоків збільшується, адаптер ініціалізує нові структури `WorkerQueue` і додає їх у масив диспетчера.
- Якщо кількість потоків зменшується, адаптер маркує зайві воркери прапорцем `running = false`, чекає дренування їхніх локальних черг завдань і викликає `thread.join()`, після чого оновлює дільник за модулем `worker_count_`.
- При ротації ключів доступу (TLS-сертифікатів або токенів OAuth2) канальний адаптер відкриває паралельне TCP-з'єднання з новими креденшелами, перемикає активний потік публікації на новий канал і плавно закриває старе з'єднання після підтвердження всіх відправлених пакетів.

## 11. Специфікація метаданих мертвої черги (DLQ Metadata Contract)

При вичерпанні ліміту повторних спроб або при виявленні непоправної помилки формату (отруйний пакет) кінцева точка зобов'язана збагатити вихідне повідомлення службовими заголовками діагностики перед перенаправленням у мертву чергу (DLQ).

```json
{
  "headers": {
    "x-original-message-id": "018e3a5b-9d41-7890-a1b2-c3d4e5f60789",
    "x-original-destination": "orders.v1.incoming",
    "x-original-partition-key": "customer-9941",
    "x-original-timestamp": 1787220000000,
    "x-death-reason": "DESERIALIZATION_SCHEMA_MISMATCH",
    "x-death-timestamp": 1787220005420,
    "x-death-host": "worker-node-prod-eu-west-4b",
    "x-death-service": "payment-fulfillment-service",
    "x-death-exception-class": "nlohmann::json::out_of_range",
    "x-death-exception-message": "key 'amount_cents' not found in payload JSON",
    "x-death-retry-count": 5,
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
  },
  "payload_base64": "eyAib3JkZXJJZCI6IDQyLCB4X2JhZCI6IHRydWUgfQ=="
}
```

### Вимоги до полів діагностичного конверта DLQ

- **Збереження вихідного бінарного тіла (`payload_base64`):** кінцева точка ніколи не модифікує пошкоджене тіло повідомлення. Воно зберігається в оригінальному незмінному вигляді для подальшого аналізу та можливості повторного відтворення (Replay).
- **Службові діагностичні заголовки `x-death-*`:** містять точну назву класу винятку, текстове повідомлення про помилку, назву хоста та сервісу, що зафіксував збій, а також кількість витрачених спроб повтору.
- **Зв'язок із трасуванням (`traceparent`):** дозволяє системі моніторингу (Jaeger / Zipkin / OpenTelemetry Collector) зв'язати аварійне потрапляння в DLQ з повним ланцюжком попередніх HTTP-запитів і операцій бази даних, які привели до формування некоректної події.
