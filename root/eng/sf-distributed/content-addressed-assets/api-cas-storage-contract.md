# 📋 Специфікація контрактів CAS: HTTP, маніфести, OCI та CID

Контентна адресація стандартизована у низці промислових протоколів, стандартів IETF та інфраструктурних специфікацій. Нижче наведено формальні контракти заголовків HTTP, архітектуру життєвого циклу кешу, конфігурації периферійних веб-серверів, схему маніфесту збирача асетів, дескриптор OCI-образів та двійкову структуру ідентифікатора CID.

---

### 1. HTTP-контракт кешування: стандарти RFC 8246 та RFC 9111

Розподілена доставка статичних ресурсів базується на моделі суворого розмежування двох взаємодоповнюючих типів HTTP-відповідей сервера: мутабельних точок входу та незмінних контентно-адресованих асетів.

Специфікація RFC 9111 визначає алгоритм обчислення свіжості (*Freshness Lifetime*). Для будь-якої відповіді браузер або проміжний проксі-сервер обчислює поточний вік ресурсу (*Age*) та зіставляє його з лімітом `max-age`. Якщо ресурс вважається свіжим, кеш повертає його негайно. Проте за замовчуванням примусове оновлення сторінки користувачем змушує клієнт надсилати умовні запити валідації.

| Тип ресурсу | Приклади | Цільовий заголовок Cache-Control | Додаткові заголовки | Поведінка клієнта та CDN |
| :--- | :--- | :--- | :--- | :--- |
| **Точка входу (Entrypoint)** | `index.html`, `manifest.json`, `/sw.js` | `public, max-age=0, must-revalidate` (або `no-cache`) | `ETag: "w/3f8a..."`, `Vary: Accept-Encoding` | Браузер і CDN **завжди** запитують сервер перед використанням; 0 мс затримки для перемикання релізів. |
| **Незмінний асет (Asset)** | `app.8f4a1c.js`, `style.9e3b.css`, `logo.7a2d.svg` | `public, max-age=31536000, immutable` | `ETag: "8f4a1c..."`, `Cross-Origin-Resource-Policy: cross-origin` | Повне блокування повторних запитів. Браузер бере файл із пам'яті/диска навіть при F5 / Reload. |
| **Динамічний API** | `/api/v1/user`, `/api/orders` | `no-store, no-cache, max-age=0` | `Pragma: no-cache`, `Expires: 0` | Повна заборона збереження в будь-яких проміжних або клієнтських кешах. |

#### Детальна семантика директив стандарту `Cache-Control`
- `immutable` (RFC 8246): вказує клієнту та проміжним проксі-серверам, що тіло відповіді **ніколи** не зміниться протягом періоду `max-age`. Рушій браузера зобов'язаний повністю ігнорувати стандартні процедури перевірки свіжості (умовні запити з заголовками `If-None-Match` та `If-Modified-Since`) під час навігації, перезавантаження сторінки користувачем або повернення назад в історії переглядів. Це усуває шторми 304-запитів і знижує час відображення сторінки до мінімуму.
- `max-age=<seconds>`: задає максимальний час у секундах, протягом якого відповідь вважається свіжою без звернення до сервера-джерела. Для контентно-адресованих асетів встановлюється `max-age=31536000` (один рік).
- `no-cache`: вказує, що ресурс **може** зберігатися в кеші браузера або CDN, але **зобов'язаний** пройти ревалідацію на сервері джерела перед кожним використанням. Це ключова директива для мутабельних HTML-файлів.
- `no-store`: категорично забороняє будь-якому кешу (клієнтському чи проміжному) зберігати будь-яку частину запиту або відповіді на постійних носіях інформації (застосовується для захисту банківських транзакцій, авторизаційних токенів та персональних даних).
- `must-revalidate`: забороняє кешу повертати застарілу копію ресурсу (*stale data*), якщо сплив термін `max-age` і зв'язок із сервером-джерелом тимчасово втрачено.
- `stale-while-revalidate=<seconds>` (RFC 5861): дозволяє клієнту миттєво використати наявну в кеші застарілу версію, одночасно запустивши фоновий асинхронний HTTP-запит для оновлення кешу на наступний раз.

### 2. Конфігурація веб-серверів для контентно-адресованої роздачі

Для коректної взаємодії браузера, CDN та бекенд-сервера маршрутизація запитів на рівні зворотної проксі (Nginx або Caddy) має чітко розмежовувати шляхи з хешами та мутабельні HTML-сторінки.

Веб-сервер повинен вимикати журнал доступу (`access_log off`) для статичних асетів, оскільки мільйони запитів створюють непотрібне навантаження на дискову підсистему. Крім того, заголовки стиснення (Gzip, Brotli, Zstandard) мають застосовуватися так, щоб не змінювати контентний відбиток сирого файлу: хеш у назві завжди відповідає нестисненому або оригінально зібраному файлу, тоді як стиснення виконується на транспортному рівні з заголовком `Content-Encoding`.

#### Конфігурація Nginx
```nginx
server {
    listen 443 ssl http2;
    server_name example.com;
    root /var/www/dist;

    # 1. Незмінна статика з відбитками в назві файлу
    location /assets/ {
        # Відповідність шаблону: ім'я.хеш_від_8_до_64_символів.розширення
        location ~* \.[a-f0-9]{8,64}\.(js|css|wasm|png|jpg|jpeg|gif|svg|woff2|woff|ttf)$ {
            expires 1y;
            add_header Cache-Control "public, max-age=31536000, immutable";
            add_header Access-Control-Allow-Origin "*";
            add_header Timing-Allow-Origin "*";
            access_log off;
            try_files $uri =404;
        }
    }

    # 2. Мутабельні точки входу: SPA HTML та маніфести
    location / {
        add_header Cache-Control "public, max-age=0, must-revalidate";
        add_header Vary "Accept-Encoding";
        try_files $uri $uri/ /index.html;
    }

    # 3. Службовий Service Worker (завжди перевіряється на свіжість)
    location = /sw.js {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        expires 0;
    }
}
```

### 3. Специфікація схеми маніфесту асетів (Asset Manifest JSON Schema)

Сучасні системи збирання веб-додатків (Vite, Webpack, Turbopack, Rollup) створюють файл маніфесту, який фіксує мапування вихідних шляхів модулів на контентно-адресовані файли та відповідні хеші цілісності SRI.

Маніфест використовується серверним рендерингом (SSR) для генерації тегів `<link rel="modulepreload">` та `<link rel="stylesheet">` з точними хешованими шляхами, що дозволяє браузеру завантажувати критичні ресурси паралельно ще до повного виконання кореневого JavaScript.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "AssetManifest",
  "type": "object",
  "additionalProperties": {
    "type": "object",
    "required": ["file", "src"],
    "properties": {
      "file": {
        "type": "string",
        "description": "Кінцевий шлях до згенерованого контентно-адресованого файлу на CDN",
        "pattern": "^assets/.+\\.[a-f0-9]{8,64}\\.(js|css|wasm|png|jpg|woff2)$"
      },
      "src": {
        "type": "string",
        "description": "Початковий шлях до вихідного модуля у вихідному коді"
      },
      "isEntry": {
        "type": "boolean",
        "description": "Чи є файл точкою входу сторінки"
      },
      "isDynamicEntry": {
        "type": "boolean",
        "description": "Чи завантажується чанк динамічно через import()"
      },
      "imports": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Список прямих статичних залежностей модуля"
      },
      "dynamicImports": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Список відкладених залежностей"
      },
      "css": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Список пов'язаних CSS-бандлів"
      },
      "integrity": {
        "type": "string",
        "description": "Криптографічний підпис SRI (Subresource Integrity)",
        "pattern": "^sha(256|384|512)-[A-Za-z0-9+/=]+$"
      }
    }
  }
}
```

### 4. Специфікація OCI Image Content-Addressable Storage

Контейнерні реєстри, сумісні зі специфікацією OCI (Open Container Initiative Image & Distribution Spec v1.1), адресують кожен шар файлової системи (*Layer*) та конфігураційний маніфест за його криптографічним дайджестом.

Кожен дескриптор містить точний тип медіа (`mediaType`), розмір у байтах та рядок дайджесту виду `алгоритм:шістнадцятковий_хеш`. Це гарантує, що клієнт (наприклад, containerd або CRI-O) може перевірити шар на льоту під час розпакування в кореневу файлову систему контейнера.

#### Структура OCI Content Descriptor (JSON)
```json
{
  "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
  "digest": "sha256:7f8a9e1d2c3b4a5f6e7d8c9b0a1f2e3d4c5b6a7f8e9d0c1b2a3f4e5d6c7b8a9f",
  "size": 32849201,
  "urls": [
    "https://cdn.registry.example.com/blobs/sha256/7f/7f8a9e1d..."
  ],
  "annotations": {
    "org.opencontainers.image.title": "rootfs-base-layer.tar.gz"
  }
}
```

#### Протокол завантаження та читання блобів у реєстрі (OCI Distribution Spec)
1. **Ініціалізація сесії завантаження:**
   Клієнт запитує відкриття потоку завантаження, надсилаючи порожній POST-запит.
   ```http
   POST /v2/<name>/blobs/uploads/ HTTP/1.1
   Host: registry.example.com
   
   HTTP/1.1 202 Accepted
   Location: /v2/<name>/blobs/uploads/<upload-session-id>
   Range: bytes=0-0
   ```
2. **Атомарне фіксування за криптографічним дайджестом:**
   Після передачі потоку клієнт закриває сесію запитом PUT із зазначенням фінального SHA-256 хешу. Реєстр обчислює хеш отриманого файлу, перевіряє збіг і переміщує блоб у CAS-сховище.
   ```http
   PUT /v2/<name>/blobs/uploads/<upload-session-id>?digest=sha256:7f8a9e1d... HTTP/1.1
   Host: registry.example.com
   Content-Length: 32849201
   Content-Type: application/octet-stream
   
   <двійковий потік байтів tar.gz>
   
   HTTP/1.1 201 Created
   Location: /v2/<name>/blobs/sha256:7f8a9e1d...
   ```
3. **Міжрепозиторійне монтування без копіювання (Cross-Repository Mount):**
   Якщо шар із таким дайджестом уже завантажено в інший репозиторій того самого реєстру, реєстр виконує миттєве монтування без повторного передавання байтів через мережу:
   ```http
   POST /v2/<target-name>/blobs/uploads/?mount=sha256:7f8a9e1d...&from=<source-name> HTTP/1.1
   Host: registry.example.com
   
   HTTP/1.1 201 Created
   Location: /v2/<target-name>/blobs/sha256:7f8a9e1d...
   ```
4. **Читання блобу за контентною адресою:**
   ```http
   GET /v2/<name>/blobs/sha256:7f8a9e1d... HTTP/1.1
   Host: registry.example.com
   
   HTTP/1.1 200 OK
   Content-Type: application/vnd.oci.image.layer.v1.tar+gzip
   Cache-Control: public, max-age=31536000, immutable
   ```

### 5. Специфікація IPFS Content Identifier (CID v1)

У децентралізованих однорангових мережах адресація здійснюється через самоописовий ідентифікатор CID v1, закодований у двійковому форматі або як рядок Multibase.

Самоописова природа CID дозволяє оновлювати криптографічні алгоритми системи без порушення зворотної сумісності: якщо протокол перейде з SHA-256 на BLAKE3, старі й нові ідентифікатори співіснуватимуть у тій самій мережі, оскільки код алгоритму явно вбудовано в кожен ідентифікатор.

#### Двійкова розкладка CID v1
```
+---------------+-------------------+--------------------+--------------------+-----------------------+
|  CID Version  |  Content Multicodec | Multihash Function |  Multihash Length  |  Raw Hash Digest Bytes|
|   (Varint)    |     (Varint)      |      (Varint)      |      (Varint)      |       (N bytes)       |
+---------------+-------------------+--------------------+--------------------+-----------------------+
| 0x01 (CIDv1)  |   0x70 (dag-pb)   |  0x12 (sha2-256)   |    0x20 (32 байт)  |  32 байти SHA-256 ... |
+---------------+-------------------+--------------------+--------------------+-----------------------+
```

Кожен заголовок двійкового представлення серіалізується як ціле число змінної довжини (*unsigned varint* за стандартом LEB128). Перший байт `0x01` позначає версію CIDv1. Наступний varint кодує тип вмісту (Multicodec), третій — ідентифікатор хеш-функції (Multihash Function), четвертий — довжину дайджесту у байтах, після чого слідують самі сирі байти хешу.

#### Таблиця кодів Multicodec для типів контенту
| Код (Hex) | Назва кодека | Призначення |
| :--- | :--- | :--- |
| `0x55` | `raw` | Сирий бінарний потік байтів без додаткових метаданих |
| `0x70` | `dag-pb` | Вузол графа розподіленої файлової системи UnixFS (Merkle DAG) |
| `0x71` | `dag-cbor` | Структурований формат IPLD (InterPlanetary Linked Data) |
| `0x0129` | `git-raw` | Нативний об'єкт репозиторію Git (Blob, Tree, Commit) |

#### Префікси Multibase для рядкового представлення CID
| Символ префікса | Назва бази | Опис та алфавіт кодування |
| :--- | :--- | :--- |
| `b` | `base32` | RFC 4648 без регістрозалежності (`a-z2-7`); стандарт для DNS-сумісних імен та URL піддоменів |
| `z` | `base58btc` | Алфавіт Bitcoin Base58 (без неоднозначних символів `0`, `O`, `I`, `l`); компактний формат для читання |
| `f` | `base16` | Шістнадцятковий нижній регістр (`0-9a-f`) для низькорівневого налагодження |

Приклад CID v1 для статичного файлу додатку `app.js` у кодуванні Base32:
```
bafybeic56t6nn7r3zvd5jkvvj4e6k3o2p2l5b2p3j5e5d3c2b1a0f9e8d7
```

Кожен вузол мережі, розібравши цей рядок, детерміновано визначає версію протоколу, алгоритм хешування (SHA-256), тип серіалізації даних (UnixFS) та точний криптографічний відбиток байтів для локальної верифікації без звернення до центрального сервера.
