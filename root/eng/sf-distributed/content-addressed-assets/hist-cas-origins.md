# 📜 Еволюція контентної адресації: від Venti та Centera до незмінного вебу

Концепція адресації даних за їхнім вмістом, а не за довільним місцем у файловій ієрархії, виникла як інженерна відповідь на дві фундаментальні кризи комп'ютерних систем: кризу надійності довготривалого архівування на початку 2000-х років та кризу затримок оновлення веб-ресурсів на початку 2010-х.

---

### Народження Venti: Plan 9 та незмінний архів блоків (2002)

На межі століть корпоративні архіви спиралися на оптичні диски та магнітні стрічки класу WORM (англ. *Write Once, Read Many* — одноразовий запис, багаторазове читання). Стрічкові бібліотеки були повільними, вимагали механічних маніпуляторів для зміни касет, а магнітні носії страждали від деградації при тривалому зберіганні. Коли ж архіви пробували перенести на жорсткі диски зі звичайними файловими системами (як-от UFS чи FAT), з'являлася загроза випадкового переписування, пошкодження файлових таблиць (*inode corruption*) та колосального перевитрачання простору через дублювання однакових файлів.

У 2002 році дослідники лабораторій Bell Labs Шон Квінлан (англ. *Sean Quinlan*) та Шон Дорвард (англ. *Sean Dorward*) представили систему Venti для операційної системи Plan 9. Автори сформулювали радикальну парадигму: жорсткі диски розглядаються не як мутабельний простір, де блоки перезаписуються, а як бездонний журнал, що може лише доповнюватися (*append-only write-once storage*).

Замість того щоб дозволяти користувачам або операційній системі призначати блоку сектор чи назву файлу, Venti обчислювала криптографічний хеш вмісту блоку за алгоритмом SHA-1 (160 біт, 20 байтів):

```
Адреса_блоку = SHA1(Тіло_блоку)
```

Цей 20-байтний відбиток ставав єдиним ідентифікатором, за яким блок можна було прочитати. Якщо програма намагалася записати блок, який уже існував у системі, Venti просто повертала його наявний хеш, не виконуючи повторного запису на диск. Так уперше на системному рівні було об'єднано три властивості:
1. **Абсолютна дедуплікація:** ідентичні дані займали фізичне місце рівно один раз.
2. **Гарантія цілісності:** неможливо було непомітно змінити дані, адже будь-яка мутація змінювала хеш, що призводило до звернення за іншою адресою або виявлення невідповідності.
3. **Імутабельність:** адреса стала функціональним посиланням на конкретне значення, перетворивши сховище на модель чистих математичних значень.

### Корпоративні масиви: EMC Centera та медичні архіви

У тому ж 2002 році компанія EMC випустила перший комерційний апаратний масив контентно-адресованого сховища — EMC Centera. Це обладнання створювалося під жорсткі вимоги регуляторів (зокрема закону Sarbanes-Oxley у США та медичних стандартів HIPAA), які вимагали доведеної незмінності фінансових транзакцій і медичних знімків PACS протягом десятиліть.

Centera запровадила термін **CAS** (англ. *Content-Addressable Storage*, від лат. *continere* — містити та *ad* + *dirigere* — спрямовувати). Коли медичний томограф зберігав знімок, система повертала клініці рядок-ідентифікатор (Content Address), сформований із хешу знімка та його метаданих. Лікарняні бази даних зберігали лише цей компактний відбиток. Якщо рентгенолог відкривав знімок через десять років, масив Centera на апаратному рівні підтверджував, що кожен байт збігається з первинним відбитком.

### Git (2005): контентно-адресований граф версій

У квітні 2005 року Лінус Торвальдс (англ. *Linus Torvalds*), розчарований пропрієтарною системою BitKeeper, за два тижні написав ядро нової розподіленої системи контролю версій Git.

Попередники Git — CVS, Subversion, Perforce — мислили категоріями відмінностей між файлами (*file-based diffs*) та лінійними номерами ревізій (r1, r2, r3). Торвальдс відкинув цю модель і побудував Git як просту контентно-адресовану файлову систему поверх звичайної ОС. У Git кожен об'єкт отримує заголовок типу та довжини, після чого хешується за алгоритмом SHA-1:

```
Заголовок = "blob " + Розмір_у_байтах + "\0"
Хеш_об'єкта = SHA1(Заголовок + Вміст_файлу)
```

Об'єкти зберігалися в каталозі `.git/objects/` за першими двома символами хешу: наприклад, об'єкт із хешем `8f4a1c...` зберігався у файлі `.git/objects/8f/4a1c...`. 

Дерева каталогів (*trees*) та зліпки комітів (*commits*) також стали контентно-адресованими об'єктами. Коміт містить хеш кореневого дерева каталогу та хеші батьківських комітів. У результаті вся історія проекту перетворилася на спрямований ациклічний граф Меркла (*Merkle DAG*). Ця архітектура усунула потребу в центральному сервері блокувань: якщо два розробники створили ідентичний файл, він автоматично дедуплікувався, а зміна хоча б одного байта в далекому минулому змінювала хеші всіх наступних комітів, унеможливлюючи приховану фальсифікацію коду.

### Веб-розробка: боротьба з кешем браузера (2007–2012)

Поки системні інженери застосовували CAS для цілісності дисків і репозиторіїв, веб-індустрія опинилася в пастці HTTP-кешування.

У 2007 році Стів Саудерс (англ. *Steve Souders*), провідний інженер з продуктивності в Yahoo!, опублікував фундаментальну працю «High Performance Web Sites». Його головне правило для статики звучало так: *«Add an Expires or a Cache-Control Header with a far future date»*. 

Якщо встановити час життя кешу (`max-age`) на один рік, браузер користувача завантажує `styles.css` або `app.js` лише один раз і більше не звертається до мережі. Але виникала дилема: як оновити клієнтський код після релізу нової версії? Якщо URL залишався мутабельним (`/scripts/app.js`), браузери користувачів продовжували виконувати старий скрипт із локального диска до завершення терміну кешу.

Розробники намагалися вирішити це параметрами запиту (*query strings*):
```
/scripts/app.js?v=2.1.0
/scripts/app.js?t=1392847291
```

Цей підхід зазнав краху. Багато корпоративних проксі-серверів, шлюзів та ранніх CDN згідно зі старими специфікаціями HTTP/1.0 взагалі відмовлялися кешувати ресурси, що містили символ `?`, вважаючи їх динамічними скриптами. Інші проксі ігнорували параметри запиту й віддавали один і той самий кеш різним версіям клієнтів.

У 2011 році фреймворк Ruby on Rails 3.1 інтегрував конвеєр асетів *Sprockets* (англ. *Asset Pipeline*). Sprockets автоматизував перенесення відбитка (хешу MD5 від вмісту файлу) безпосередньо в тіло назви файлу:
```
application-4858e3835e5d32b5368a52936894c9f5.css
```

Це стало переломним моментом для вебу: URL перестав бути просто адресою розміщення на диску і став контентним ідентифікатором.

### Ера збирачів: Webpack та каскадна проблема хешів (2014–2016)

З появою Single Page Applications (SPA) та модульних збирачів (Webpack, Browserify, Rollup) веб-додатки почали розбиватися на десятки й сотні окремих фрагментів (*chunks*).

Виникла проблема «каскадного тремтіння хешів» (*hash churn*). Якщо розробник змінював один рядок у глибокому допоміжному модулі `utils.js`, збирач змінював його хеш. Але модуль вищого рівня `dashboard.js` містив прямий текстовий виклик `import('./utils.7a8b.js')`. Відповідно, змінювався вміст `dashboard.js`, що змінювало його власний хеш, і ця хвиля доходила до кореневого файлу `main.js`. У результаті найменша правка призводила до повної інвалідації кешу всього додатку на мільйонах клієнтських пристроїв.

Команда Webpack вирішила цю проблему розділенням хешів:
- `[fullhash]` (раніше `[hash]`) — загальний хеш усієї компіляції.
- `[chunkhash]` — хеш конкретної точки входу та її залежностей.
- `[contenthash]` — строгий хеш виключно байтів результуючого файлу після мінімізації та вилучення динамічного маніфесту.

Винесення таблиці відповідності модулів (маніфесту виконання) у крихітний скрипт точки входу або безпосередньо в HTML дозволило локалізувати зміни: оновлення одного модуля нарешті змінювало хеш лише цього конкретного файлу, залишаючи гігабайти бібліотек вендорів у недоторканому клієнтському кеші.

### RFC 8246: директива `immutable` від Facebook та Mozilla (2017)

Незважаючи на впровадження хешів у назвах файлів, протокол HTTP/1.1 містив вроджену неефективність у поведінці браузерів.

Коли користувач натискав кнопку перезавантаження сторінки (F5 / `Cmd+R`), браузер вважав, що користувач сумнівається у свіжості даних. Навіть якщо файл мав заголовок `Cache-Control: max-age=31536000`, рушій браузера надсилав умовний HTTP-запит `GET` із заголовком `If-None-Match: "хеш"` або `If-Modified-Since`. Сервер або CDN повертали статус `304 Not Modified`, але клієнт витрачав повний цикл мережевої затримки (RTT, 50–200 мс) на кожен ресурс сторінки.

У 2015 році інженери Facebook (зокрема Бен Маурер, англ. *Ben Maurer*) та Mozilla (Ніколас Герлі, англ. *Nicholas Hurley*) проаналізували статистику трафіку. З'ясувалося, що понад 60% усіх HTTP-запитів до Facebook становили повторні умовні перевірки незмінних статичних файлів при перезавантаженні сторінки, що створювало терабайти марного мережевого трафіку та перевантажувало CDN-шлюзи.

Результатом співпраці стала публікація стандарту **RFC 8246: HTTP Immutable Responses** у червні 2017 року. Нова директива заголовка відповідей:

```http
Cache-Control: public, max-age=31536000, immutable
```

Директива `immutable` прямо повідомила браузеру: вміст за цим URL за жодних обставин не зміниться протягом зазначеного `max-age`. Браузер зобов'язаний брати файл із локального дискового кешу без надсилання умовних запитів 304, навіть якщо користувач примусово оновлює сторінку.

Так контентна адресація замкнула коло: математичний принцип зв'язування адреси з відбитком байтів, закладений у Venti та Git для дисків, став офіційним стандартом глобальної веб-інфраструктури, перетворивши мережу на розподілене дедупліковане сховище нульової латентності.
