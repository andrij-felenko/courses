# 🧮 Математика бюджетів часу, компромісів корисності та черг при деградації

Коли розподілена система обробляє вхідний запит шляхом паралельного звернення до кількох залежних сервісів, її поведінка підпорядковується законам теорії ймовірностей та теорії масового обслуговування. Якщо система проєктується за бінарним принципом «все або нічого», її надійність стрімко деградує зі збільшенням кількості компонентів, а черги запитів під час сплесків трафіку входять у режим експоненційного вибуху. Математичне моделювання показує, чому заміна бінарної моделі на багаторівневу функцію корисності та динамічне скорочення часу обслуговування перетворює нестійку систему на стабільну.

## 1. Функція корисності та спектр деградації

У класичній архітектурі якість відповіді розглядається як булева величина: 1 (успіх) або 0 (помилка 500). У моделі керованої деградації результат операції описується **функцією корисності** (англ. *utility function*, лат. *utilitas* — користь, придатність).

Нехай відповідь агрегатора формується з `N` компонентів (наприклад: залишки на складі, розрахунок знижки, персональні рекомендації, відгуки). Кожен компонент `i` має ваговий коефіцієнт важливості для бізнесу `w[i] ≥ 0` та рівень повноти даних `q[i] ∈ [0, 1]`, де `q[i] = 1` відповідає повноцінному свіжому результату, `q[i] = 0.5` — результату з кешу або спрощеній евристиці, а `q[i] = 0` — повній відсутності блоку.

Загальна корисність відповіді для користувача визначається зваженою сумою:

```
U(q) = ∑ (w[i] · q[i]) / ∑ w[i]
```

Для типової сторінки оформлення замовлення вагові коефіцієнти розподіляються нерівномірно:
- Ядро замовлення та оплата (Tier-0): `w[0] = 100` (без нього операція неможлива);
- Каталог цін та перевірка складу (Tier-1): `w[1] = 20`;
- Персональні рекомендації (Tier-2): `w[2] = 5`;
- Живі відгуки та соціальні лічильники (Tier-3): `w[3] = 1`.

Якщо під час пікового навантаження сервіси Tier-2 та Tier-3 відмовляють (`q[2] = 0`, `q[3] = 0`), а ціна береться з кешу (`q[1] = 0.8`), сумарна корисність відповіді становить:

```
U_degraded
= (100 · 1.0 + 20 · 0.8 + 5 · 0 + 1 · 0) / (100 + 20 + 5 + 1)  [підстановка вагових коефіцієнтів]
= (100 + 16 + 0 + 0) / 126                                      [обчислення зважених сум]
= 116 / 126                                                     [частка збереженої цінності]
≈ 0.9206                                                        [92.1 % корисності для бізнесу]
```

У традиційній системі падіння будь-якого з цих компонентів перериває виклик винятком `NullPointerException` або таймаутом, даючи `U = 0`. Деградація зберігає 92 % бізнес-цінності при нульових витратах на недоступні другорядні підсистеми.

## 2. Імовірність доступності: кон'юнкція проти ізольованого ядра

Припустимо, шлюз робить `N = 20` незалежних мережевих RPC-викликів для формування однієї сторінки. Нехай кожен окремий сервіс має високу індивідуальну доступність `p = 0.999` (три дев'ятки, тобто близько 8.76 годин простою на рік).

Якщо для успіху потрібна відповідь **усіх** 20 сервісів (жорстка кон'юнкція подій), сумарна доступність системи `A_conj` обчислюється як добуток імовірностей:

```
A_conj
= p²⁰                                  [правило множення для незалежних подій]
= (0.999)²⁰                            [підстановка надійності окремого вузла]
= (1 − 0.001)²⁰                        [перехід до ймовірності відмови]
≈ 1 − 20 · 0.001 + 190 · 0.001²        [перші члени біноміального розкладу]
≈ 1 − 0.020 + 0.00019                  [арифметичне спрощення]
≈ 0.98019                              [доступність 98.02 %]
```

Річний час простою такої системи зростає катастрофічно:

```
T_down_conj
= 8760 · (1 − 0.98019)                 [множення річного фонду годин на ймовірність збою]
= 8760 · 0.01981                       [частка часу недоступності]
≈ 173.54 години                        [понад 7.2 доби простою на рік]
```

Тепер розділимо 20 сервісів на дві категорії:
- `K = 2` критичні жорсткі залежності (Tier-0: білінг і база замовлень);
- `M = 18` м'яких залежностей (Tier-1..Tier-3), кожна з яких має детермінований локальний фолбек з надійністю `p_fb = 1.0` (статична структура або локальна пам'ять).

Доступність ядра системи за такої архітектури залежить лише від критичних вузлів:

```
A_tiered
= pᴷ · (p + (1 − p) · p_fb)ᴹ           [ймовірність успіху ядра та деградації м'яких вузлів]
= (0.999)² · (0.999 + 0.001 · 1.0)¹⁸   [підстановка повної надійності локального фолбеку]
= 0.999² · 1.0¹⁸                       [спрощення виразу для фолбеку]
= 0.998001                             [доступність 99.80 %]
```

```
T_down_tiered
= 8760 · (1 − 0.998001)                [розрахунок річного простою для деградованої моделі]
= 8760 · 0.001999                      [частка часу відмови ядра]
≈ 17.51 годин на рік                   [скорочення річного простою в 10 разів]
```

Ізоляція м'яких залежностей повертає системі її природний рівень доступності, усуваючи комбінаторний обвал надійності.

## 3. Динаміка черги M/M/c/K при деградації часу обслуговування

Розглянемо пул обробників запитів із `c` потоків та чергою місткістю `K`. Вхідний потік запитів має інтенсивність `λ` (запитів за секунду), а час обробки одного запиту в повному режимі має середнє значення `E[T_full] = 1 / μ_full = 50 мс` (`μ_full = 20 с⁻¹`).

Коефіцієнт завантаження системи:

```
ρ = λ / (c · μ_full)                   [відношення інтенсивності приходу до пропускної здатності]
```

Поки `ρ < 1`, черга стабільна. Але під час сплеску трафіку (наприклад, маркетингової акції) інтенсивність зростає втричі: `λ_surge = 3 · λ_nom`, унаслідок чого `ρ_surge ≥ 2.5`.

За законами теорії масового обслуговування, при `ρ > 1` довжина черги `L_q` зростає лінійно з часом, а середній час очікування `W_q` вибухає до місткості буфера `K / (c · μ)` і спричиняє масове скидання з'єднань за таймаутом.

Застосуймо **деградацію часу обслуговування**: при виявленні зростання завантаження `ρ > 0.85` система примусово вимикає повільні етапи (важкий ML-ранжир за 40 мс замінюється на вибірку зі статичного масиву за 0.1 мс). Новий час обробки становить `E[T_deg] = 1 / μ_deg = 5 мс` (`μ_deg = 200 с⁻¹`, прискорення в 10 разів).

Розрахуємо нове завантаження системи під час того самого трикратного шквалу `λ_surge`:

```
ρ_deg
= λ_surge / (c · μ_deg)                [означення завантаження при сплеску та деградації]
= (3 · λ_nom) / (c · 10 · μ_full)      [підстановка 3x трафіку та 10x прискорення обслуговування]
= 0.3 · (λ_nom / (c · μ_full))         [винесення постійного коефіцієнта розвантаження]
= 0.3 · ρ_nom                          [згортання виразу через номінальне завантаження]
```

Якщо в штатному режимі `ρ_nom = 0.7`, то під час піку в деградованому стані:

```
ρ_deg = 0.3 · 0.7 = 0.21               [нове завантаження навіть при потрійному шквалі]
```

Середня довжина черги в системі M/M/1 (для одного потоку) при цьому падає:

```
L_q_nom = 0.7² / (1 − 0.7) = 0.49 / 0.3 ≈ 1.63 запити    [довжина черги в штатному режимі]
L_q_deg = 0.21² / (1 − 0.21) = 0.0441 / 0.79 ≈ 0.056     [довжина черги в деградованому режимі]
```

Замість паралічу та переповнення черг система миттєво повертається в зону майже нульового очікування, безпечно пропускаючи 100 % вхідного потоку через швидкий деградований тракт.

## 4. Розподіл бюджету дедлайну при паралельному Scatter-Gather

При паралельному надсиланні запитів до `N` сервісів загальний час виконання операції `T_total` визначається найповільнішим із них:

```
T_total = max(T₁, T₂, ..., T_N)        [визначення тривалості паралельного бар'єра]
```

Нехай час відповіді кожного сервісу `T_i` підпорядковується логнормальному розподілу з медіаною 15 мс та довгим хвостом (`P(T_i ≤ 100 мс) = 0.96`).

Імовірність того, що всі `N = 10` паралельних викликів вкладуться в жорсткий клієнтський дедлайн `T_client = 100 мс`:

```
P(T_total ≤ 100 мс)
= ∏ P(T_i ≤ 100 мс)                    [добуток імовірностей для 10 незалежних сервісів]
= 0.96¹⁰                               [піднесення до 10-го степеня]
≈ 0.6648                               [лише 66.5 % запитів встигають до дедлайну]
```

Третина всіх користувацьких запитів (33.5 %) зазнає помилки через затримку хоча б одного компонента.

Введемо правило **проактивного часового відсікання** (англ. *deadline-driven shedding*):
1. Жорсткий дедлайн клієнта: `T_client = 100 мс`.
2. Проміжний поріг для другорядних сервісів Tier-2: `T_thresh = 40 мс`.

Якщо до моменту `t = 40 мс` відповідь від сервісу Tier-2 не надійшла, його виклик асинхронно скасовується, і в результуючий об'єкт підставляється статичний фолбек за `0.02 мс`.

Імовірність успіху в деградованій системі:

```
P_success
= P(T_crit1 ≤ 100 мс) · P(T_crit2 ≤ 100 мс) · P_fallback_available  [незалежність ядра і фолбеку]
= 0.96 · 0.96 · 1.0                                                 [числові значення ймовірностей]
= 0.9216                                                            [підсумкова доступність 92.16 %]
```

А якщо для критичних сервісів закласти оптимізований бюджет `P(T_crit ≤ 100 мс) = 0.999`, сумарна успішність паралельного збору становить:

```
P_success_opt
= 0.999 · 0.999 · 1.0                  [множення оптимізованих імовірностей ядра та фолбеку]
= 0.998001                             [підсумкова доступність 99.80 %]
```

Математичний висновок однозначний: обмежуючи час очікування м'яких залежностей жорстким раннім порогом, ми запобігаємо деградації загального квантиля `P99` всієї системи.
