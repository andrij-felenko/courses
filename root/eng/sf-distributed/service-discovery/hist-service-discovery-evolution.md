# 📜 Від /etc/hosts і DNS до ZooKeeper, Eureka, Consul та Envoy xDS

Щоб один комп'ютер міг надіслати мережевий пакет іншому, йому потрібна точна числова адреса призначення. На світанку комп'ютерних мереж у мережі ARPANET на початку 1970-х років цю задачу вирішували найпростішим можливим способом: єдиним текстовим файлом `HOSTS.TXT`, який централізовано вела Елізабет Фейнлер (англ. *Elizabeth Feinler*) у Стенфордському дослідницькому інституті (SRI-NIC). Адміністратори систем раз на тиждень завантажували оновлену версію файлу через FTP на свої мейнфрейми та записували в `/etc/hosts`.

Ця схема працювала бездоганно, поки в усій світовій мережі налічувалося кілька сотень статичних вузлів з постійними іменами на кшталт `SRI-NIC`, `MIT-AI` або `UTAH-10`. Проте щойно кількість машин перетнула позначку в кілька тисяч, щотижневе ручне розповсюдження монолітного файлу перетворилося на інфраструктурний глухий кут: колізії імен, колосальне навантаження на один сервер завантаження та неможливість оновити адресу без участі людини.

## 1983: Народження DNS та межі статичної маршрутизації

У 1983 році Пол Мокапетріс (англ. *Paul Mockapetris*) розробив систему доменних імен (**Domain Name System, DNS**, RFC 882 / RFC 883). DNS запропонувала революційну на той час ідею: розподілену ієрархічну базу даних із делегуванням зон відповідальності та локальним кешуванням відповідей на клієнтських резолверах на час `TTL` (англ. *Time to Live*).

Протягом майже трьох десятиліть DNS залишалася безальтернативним стандартом виявлення вузлів. Для класичної серверної архітектури — коли вебсервер звертався до виділеного сервера бази даних за постійною IP-адресою `192.168.1.50`, закріпленою статично мережевим інженером, — DNS покривала 100% потреб.

Але з початком ери сервісно-орієнтованої архітектури (SOA) на межі 1990-х і 2000-х років з'ясувалося, що DNS має три вроджені фізичні обмеження:
1. **Відсутність динамічних портів:** DNS-записи типу `A` повертають лише 32-бітну IP-адресу вузла. Якщо на одній потужній машині працює 10 різних сервісів на різних TCP-портах, DNS не здатна повідомити клієнту, до якого саме порту підключатися.
2. **Агресивне та некероване кешування:** Клієнтські операційні системи, бібліотеки мов програмування (наприклад, віртуальна машина Java Virtual Machine з її налаштуванням `networkaddress.cache.ttl = -1` за замовчуванням) та проміжні провайдерські DNS-сервери кешують адреси на хвилини або години, повністю ігноруючи реальний стан цільового вузла.
3. **Відсутність інформації про стан працездатності (Health Status):** DNS повертає адресу навіть тоді, коли процес за нею вже дві хвилини як зазнав аварійного завершення (англ. *crash*), перетворюючи клієнтський трафік на чорну діру.

## 1990-ті та 2000-ні: Служби каталогів CORBA, JNDI та крах UDDI

У 1990-х роках консорціум OMG (Object Management Group) представив стандарт розподілених об'єктів **CORBA (Common Object Request Broker Architecture)**. Для вирішення проблеми пошуку віддалених об'єктів було створено службу імен **CORBA CosNaming (Naming Service)**. Сервери публікували свої об'єктні посилання (Interoperable Object Reference, IOR), що містили IP, порт та внутрішній ідентифікатор об'єкта, у централізоване дерево імен. 

Паралельно у світі Java з'явився стандарт **JNDI (Java Naming and Directory Interface)** та протоколи RMI-IIOP для пошуку Enterprise JavaBeans (EJB) у серверах застосунків (WebLogic, WebSphere, JBoss). 

Проте ці ранні служби каталогів страждали від трьох важких вад:
* Вони були жорстко прив'язані до конкретних бінарних рантаймів і мов програмування (C++ та Java IDL).
* Каталоги не вміли автоматично виявляти падіння віддалених процесів: клієнт отримував об'єктне посилання IOR, намагався викликати метод і падав із важким виключенням `CORBA::COMM_FAILURE` або `java.rmi.RemoteException`.
* Служби імен були статичними базами даних без розподіленого консенсусу, перетворюючись на єдину точку відмови (SPOF) для всього підприємства.

На хвилі захоплення протоколами XML-RPC та SOAP консорціум великих вендорів (IBM, Microsoft, Ariba) у 2000 році представив стандарт **UDDI (Universal Description, Discovery and Integration)**. Ідея полягала у створенні глобального публічного та корпоративного реєстру вебслужб — своєрідних «жовтих сторінок» для бізнесу.

UDDI зазнав нищівного фіаско. Стандарт був надзвичайно переускладненим: щоб зареєструвати або знайти сервіс, програма мала надсилати багатокілобайтні SOAP/XML-документи, проходити складну авторизацію та оперувати абстракціями `tModel` і `businessEntity`. Реєстр був статичним, повільним і не підтримував автоматичного відстеження життєвого циклу процесів. До 2006 року IBM, Microsoft та SAP закрили свої публічні UDDI-вузли, а проект перетворився на хрестоматійний антипатерн архітектури.

## 2008–2011: ZooKeeper та ера консенсусу

Паралельно з розвитком розподілених систем обробки великих даних (Hadoop, HBase) у компанії Yahoo! з'явився проект **Apache ZooKeeper** (2008). 

ZooKeeper запропонував модель ієрархічного дерева вузлів (**znodes**) у пам'яті, узгодженого за допомогою суворого алгоритму консенсусу Zab (англ. *ZooKeeper Atomic Broadcast*). Для виявлення сервісів ZooKeeper запропонував фундаментальну концепцію: **ефемерні вузли (ephemeral znodes)** та **механізм сповіщень (Watches)**.

```
/services
   └── /payment
          ├── /instance-001 (ephemeral: 10.0.1.12:8080)
          └── /instance-002 (ephemeral: 10.0.1.15:8080)
```

Коли екземпляр сервісу запускався, він відкривав TCP-сесію до кластера ZooKeeper і створював ефемерний вузол. Якщо процес падав або мережевий зв'язок обривався, сесія ZooKeeper спливала за таймаутом (англ. *heartbeat timeout*), і сервер консенсусу автоматично видаляв ефемерний вузол. Клієнти, які підписалися через `watch` на гілку `/services/payment`, миттєво отримували оновлений список адрес.

Проте ZooKeeper належав до суворих CP-систем (за CAP-теоремою). Під час мережевих розділень (англ. *network partition*) або втрати кворуму лідера кластер ZooKeeper повністю відмовлявся приймати будь-які оновлення статусів, блокуючи реєстрацію нових екземплярів і паралізуючи динамічну інфраструктуру.

## 2012: Хмарна революція Netflix та народження Eureka

У 2011–2012 роках компанія Netflix здійснювала масштабну міграцію зі своїх приватних дата-центрів у публічну хмару Amazon Web Services (AWS EC2). У динамічному хмарному середовищі віртуальні машини запускалися й знищувалися щогодини під дією автоскейлінгу або інструментів хаос-інжинірингу (Chaos Monkey).

Штатний балансувальник Amazon Elastic Load Balancer (ELB) першого покоління не справлявся з міжсервісним навантаженням: він додавав зайву затримку, не підтримував прямий gRPC/TCP роутинг і часто ставав вузьким місцем під час різких сплесків трафіку.

Команда Netflix під керівництвом Едріана Кокрофта (англ. *Adrian Cockcroft*) дійшла ключового висновку: **для маршрутизації міжсервісних викликів доступність реєстру сервісів набагато важливіша за його миттєву строгу консистентність**.

Так народився **Netflix Eureka** (2012) — відкритий реєстр сервісів, побудований за AP-моделлю (висока доступність):
* Сервери Eureka не використовують алгоритмів розподіленого консенсусу (Raft або Paxos). Натомість вони об'єднані в peer-to-peer кластер і реплікують дані між собою асинхронно.
* Якщо між дата-центрами обривається мережевий лінк, кожен сервер Eureka продовжує реєструвати нові сервіси та відповідати на запити клієнтів локальними даними.
* Якщо сервер фіксує масовий пропуск пульсу (більше 15% екземплярів не надіслали heartbeat за 15 хвилин), він вмикає **режим самозбереження (Self-Preservation Mode)**: припиняє видаляти неактивні інстанси, захищаючи систему від масового помилкового видалення здорових сервісів через короткочасний мережевий збій.

У зв'язці з бібліотекою клієнтського балансування **Netflix Ribbon** схема Eureka дозволила клієнтам кешувати список екземплярів локально та виконувати маршрутизацію безпосередньо до бекендів з нульовою додатковою затримкою.

## 2014: HashiCorp Consul — поєднання консенсусу та Gossip

Хоча Eureka чудово вирішувала задачу для Java-стеку Netflix, вона вимагала включення важких клієнтських бібліотек у кожен мікросервіс і була малопридатною для поліглотних середовищ (C++, Go, Python, Node.js).

У 2013 році Армон Дадгар та Мітчелл Хашимото розробили бібліотеку **Serf** на базі децентралізованого протоколу SWIM Gossip, а в 2014 році представили повноцінний реєстр **Consul**. Consul запропонував двоетапну гібридну архітектуру:
1. **Протокол пліткування (Gossip Protocol / Serf):** На кожному фізичному вузлі чи віртуальній машині працює локальний легкий агент Consul. Усі агенти кластера обмінюються швидкими UDP-повідомленнями за алгоритмом SWIM, миттєво виявляючи падіння вузлів без навантаження на центральну базу даних.
2. **Raft Consensus для збереження стану:** Центральний кластер серверів Consul підтримує суворо консистентний каталог сервісів і ключ-значення сховище через протокол Raft.
3. **Універсальні інтерфейси:** Consul надав доступ до каталогу не лише через HTTP REST API, але й через **вбудований DNS-сервер** (наприклад, звернення до `payment.service.consul` автоматично повертало IP-адреси здорових вузлів через записи SRV/A), що дозволило будь-якій legacy-програмі без зміни жодного рядка коду користуватися перевагами динамічного виявлення.

## 2016–дотепер: Kubernetes EndpointSlices та Envoy xDS

З перемогою контейнерної оркестрації Kubernetes архітектура виявлення сервісів зробила наступний крок. Kubernetes увів декларативну абстракцію `Service` та ресурс `Endpoints`. Оркестратор сам відстежує життєвий цикл Pod через Kubelet, звільняючи застосунки від необхідності самостійно реєструватися де б то не було.

Коли кількість Pod у великих кластерах перетнула десятки тисяч, оновлення монолітного об'єкта `Endpoints` спричинило колосальне навантаження на `etcd` (O(N^2) трафіку під час перезапуску одного поду). У відповідь у 2020 році в Kubernetes з'явився контролер **EndpointSlice**, що розбиває каталог адрес на невеликі фрагменти по 100 ендпоінтів, зменшуючи мережевий трафік на порядки.

Одночасно розвиток сервісних сіток (Service Mesh) та проксі **Envoy** (створеного Меттом Клейном у Lyft у 2016 році) вивів виявлення сервісів на протокол **xDS (Discovery Service API)**. Через постійний потоковий gRPC-канал (EDS — Endpoint Discovery Service) площина управління миттєво передає зміни топології сотням тисяч проксі-сайдкарів, усуваючи необхідність у товстих клієнтських бібліотеках і зводячи затримку оновлення маршрутів до мілісекунд.
