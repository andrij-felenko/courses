Дві армії під командуванням двох генералів розташовані на протилежних пагорбах і готуються до штурму укріпленого міста, що лежить у долині між ними. Військо кожного генерала окремо поступається силам міського гарнізону: якщо в атаку піде лише одна армія, вона зазнає нищівної поразки й буде знищена. Якщо ж обидві армії атакують одночасно, вони здобудуть беззаперечну перемогу. Єдиний спосіб зв'язку між пагорбами — піші посланці через ворожу долину, де кожного кур'єра можуть перехопити або ліквідувати з деякою ненульовою ймовірністю `p > 0`. Перший генерал надсилає повідомлення: «Атакуємо завтра рівно о 06:00». Він відправляє кур'єра у долину й опиняється перед смертельною невизначеністю: чи дійшов лист?

Якщо Перший генерал вирішить піти в атаку без отримання підтвердження, а посланця було схоплено в лісі, Перший генерал атакуватиме на самоті й загине разом зі своєю армією. Отже, діяти без отримання відповіді смертельно небезпечно.

Другий генерал отримує лист, читає наказ і радіє скоординованому плану. Він негайно відправляє кур'єра назад із відповіддю: «Наказ отримав, згоден атакувати о 06:00». Але тепер перед дзеркальною дилемою опиняється Другий генерал. Чи може він вийти на штурм о 06:00, щойно відправив свого посланця? Якщо зворотного кур'єра перехоплять у дорозі, Перший генерал так і не дізнається, чи дійшов перший лист, тому Перший генерал розсудливо залишиться у своєму таборі. Якщо Другий генерал піде в атаку сам, він так само загине під мурами міста.

## Нескінченна драбина квитування

Щоб убезпечити себе від загибелі, Другий генерал вимагає додаткової гарантії: він піде в бій лише тоді, коли отримає від Першого генерала підтвердження того, що зворотний лист із підтвердженням успішно дійшов до адресата (квитанцію на квитанцію, `ACK2`).

Перший генерал успішно зустрічає другого кур'єра, дізнається про згоду колеги та відправляє третього посланця: «Отримав твоє підтвердження, підтверджую атаку». Проте тепер у пастку невизначеності знову потрапляє Перший генерал: він не знає, чи добіжить третій кур'єр до Другого генерала. Якщо третій кур'єр загине, Другий генерал не отримає `ACK2` і залишиться на пагорбі, а Перший генерал загине на самоті.

Першому генералу тепер потрібне підтвердження на його третій лист (`ACK3`). Другому знадобиться `ACK4`, Першому — `ACK5`, і цей процес ніколи не досягне логічного завершення.

![Нескінченна драбина квитування (ACK ladder) у задачі двох генералів](/root/eng/sf-distributed/two-generals-problem/img/two-generals-ack-ladder.svg)

*Нескінченна драбина квитування: кожен наступний рівень підтвердження залишає останнього відправника в стані невизначеності.*

Цей уявний експеримент демонструє фундаментальний закон природи розподілених систем: **останній відправник у будь-якому ланцюжку повідомлень завжди залишається у стані абсолютної невизначеності** щодо того, чи було доставлено його останній пакет.

Оскільки будь-яке повідомлення може бути останнім, жодна скінченна послідовність обміну квитанціями не здатна гарантувати стовідсотково синхронізованої дії двох вузлів через ненадійний комунікаційний канал.

Ця класична дилема комп'ютерних наук називається **задачею двох генералів** (англ. *Two Generals' Problem*).

## Історичний контекст і сутність проблеми

Уперше цю проблему під назвою «парадокс двох банд» сформулювали дослідники Е. А. Аккоюнлу, К. Еканадхам та Р. В. Губер у 1975 році під час аналізу надійності міжпроцесної взаємодії в операційних системах. Автори прагнули зрозуміти, які мінімальні обмеження накладає фізичне середовище передачі даних на можливість досягнення узгодженого стану між двома віддаленими комп'ютерами.

Широку популярність і канонічну військову метафору про генералів задачі надав видатний вчений у галузі баз даних Джим Грей (Jim Gray) у 1978 році у праці «Notes on Data Base Operating Systems». Грей досліджував транзакційну надійність розподілених систем керування базами даних (зокрема проєкту IBM System R). Він шукав протокол, який дозволив би двом незалежним серверам гарантувати атомарність спільної транзакції за будь-яких умов роботи мережі.

Грей звернув увагу на те, що наївна віра розробників у можливість створення «ідеального протоколу підтвердження» розбивається об математичну структуру каналу зв'язку. Докладніше про розвиток ідей та наукові дискусії навколо цієї моделі читайте у матеріалі: [історію відкриття проблеми від систем зв'язку 1975 року до робіт Джима Грея та епістемічної логіки](root:sf-distributed/two-generals-problem/hist-two-generals.md).

Зв'язок між генералами через долину є точною аналогією передачі IP-пакетів через фізичну мережу:
* Генерали — це незалежні обчислювальні процеси (вузли), кожен зі своєю локальною оперативною пам'яттю та диском.
* Ворожа долина — це комунікаційна мережа (Ethernet, оптоволокно, Wi-Fi, глобальний Internet).
* Перехоплення кур'єра — це втрата пакета через переповнення черги комутатора, скидання буфера операційною системою або пошкодження контрольної суми CRC.
* Одночасна атака — це атомарна дія (узгоджена фіксація транзакції, перехід у новий стан розподіленого автомата або запуск синхронного обчислення).

Головна властивість, якої прагнуть досягти вузли, — це **консенсус** (лат. *consensus* — згода, одностайність), тобто узгоджене прийняття однакового термінального рішення за наявності локальних входів і можливих збоїв середовища.

## Доведення неможливості детермінованого консенсусу

Доведемо строге твердження: **не існує детермінованого протоколу, який гарантує консенсус між двома вузлами через ненадійний канал зв'язку за скінченну кількість кроків**.

Для доведення застосуємо класичний метод математичної індукції від супротивного.

### Формалізація умов
Нехай система складається з двох вузлів `p_1` та `p_2`. Кожен вузол `p_i` виконує детермінований алгоритм.
Вузли приймають рішення `decide_i ∈ {0, 1}`, де `1` означає атаку (коміт транзакції), а `0` — відступ (відхилення або скасування операції).
Канал зв'язку може успішно доставити пакет або стерти його з імовірністю `p ∈ (0, 1)`.

Протокол вважається коректним, якщо він задовольняє три обов'язкові властивості:
1. **Одностайність (Agreement):** у будь-якому виконанні `decide_1 = decide_2`.
2. **Слушність (Validity):** якщо всі пакети втрачено з самого початку, вузли вирішують `0`. Якщо зв'язок ідеальний і обидва хочуть атакувати, вони вирішують `1`.
3. **Завершуваність (Termination):** за скінченну кількість кроків обидва вузли приймають остаточне рішення.

### Індуктивний перехід
Припустимо від супротивного, що такий надійний детермінований протокол існує.

За умовою існує деяке успішне виконання `E`, у якому обидва генерали атакують (`decide_1 = 1` та `decide_2 = 1`), обмінявшись скінченною послідовністю з `k` успішно доставлених повідомлень:

```
M(E) = ⟨m_1, m_2, m_3, ..., m_k⟩
```

Оберемо з усіх можливих успішних протоколів такий, що потребує **мінімальної кількості повідомлень** `k ≥ 1`.

Нехай останнє повідомлення `m_k` надсилається від генерала `p_1` до генерала `p_2`.

Тепер розглянемо альтернативне виконання `E'`, яке повністю ідентичне `E`, за винятком однієї деталі: останнє повідомлення `m_k` **втрачається в дорозі й ніколи не доходить до `p_2`**.

```
M(E') = ⟨m_1, m_2, m_3, ..., m_{k-1}⟩
```

Проаналізуємо стан генерала-відправника `p_1` у виконанні `E'`:
Генерал `p_1` надіслав повідомлення `m_k` у мережу. Оскільки генерал не має миттєвого каналу зворотного зв'язку про стан пакета в польоті, його локальний внутрішній стан у момент відправки та прийняття рішення абсолютно не відрізняється від його стану у виконанні `E`. Алгоритм детермінований, тому `p_1` зобов'язаний прийняти те саме рішення:

```
decide_1(E') = decide_1(E) = 1
```

Оскільки протокол за нашим припущенням є бездоганним і гарантує одностайність (Agreement) для будь-якої поведінки мережі, генерал `p_2` у виконанні `E'` також **зобов'язаний вирішити `1`**, інакше станеться неузгоджена атака:

```
decide_2(E') = decide_1(E') = 1
```

Але зверніть увагу: у виконанні `E'` повідомлення `m_k` не було доставлено, отже, обидва генерали успішно домовилися про атаку, використавши всього `k - 1` повідомлень!

Це означає, що повідомлення `m_k` було **абсолютно непотрібним** для прийняття рішення.

Повторюючи цей індуктивний крок далі, ми можемо викреслити повідомлення `m_{k-1}`, потім `m_{k-2}`, і так далі, аж поки не отримаємо протокол із `0` повідомлень.

Проте за властивістю Validity протокол без жодного повідомлення зобов'язаний залишати генералів у таборі (`decide_1 = decide_2 = 0`), оскільки вони не знають про наміри один одного. Ми отримали формальну суперечність: `1 = 0`.

Отже, вихідне припущення було хибним: детермінованого алгоритму консенсусу над ненадійним каналом не існує в природі.

Повний алгебраїчний виклад із графами переходів станів та структурами Кріпке наведено у вставці: [формальне математичне доведення теореми через індукцію та граф нерозрізненності станів](root:sf-distributed/two-generals-problem/math-two-generals-proof.md).

## Епістемічна логіка та концепція спільного знання

Чому саме виникає цей бар'єр? Фундаментальну відповідь на це питання у 1984–1990 роках надали дослідники Джозеф Гальперн та Йорам Мозес, застосувавши апарат **епістемічної логіки** (грец. *episteme* — знання + *logos* — вчення, слово), яка вивчає міркування агентів про знання одне одного.

У розподіленій системі існує чітка якісна градація станів поінформованості.

Нехай `m` — це твердження «Атакуємо о 06:00».
Позначимо через `K_i(m)` факт того, що процес `i` знає твердження `m`.

### Ієрархія рівнів знання

1. **Індивідуальне знання (`K_1(m)`):**
Перший генерал знає час атаки. Другий генерал не підозрює про плани першого. Спільні дії неможливі.

2. **Взаємне знання першого порядку (`E^1(m)`):**
Перший генерал надіслав лист, другий його отримав. Обидва генерали індивідуально знають твердження `m`:
```
E^1(m) ≡ K_1(m) ∧ K_2(m)
```
Проте Перший генерал не знає, чи дійшов лист, тобто `¬K_1(K_2(m))`. У системі немає впевненості у партнері.

3. **Взаємне знання другого порядку (`E^2(m)`):**
Другий генерал надіслав квитанцію `ACK`, і Перший генерал її отримав. Тепер Перший генерал знає, що Другий генерал знає про атаку:
```
E^2(m) ≡ K_1(K_2(m)) ∧ K_2(K_1(m))
```
Але тепер Другий генерал не знає, чи дійшла його квитанція, тобто `¬K_2(K_1(K_2(m)))`.

4. **Взаємне знання порядку `k` (`E^k(m)`):**
Кожен наступний рівень квитування додає ще один рівень вкладеності оператора знання: «я знаю, що ти знаєш, що я знаю, що ти знаєш...».

5. **Спільне знання (Common Knowledge, `C(m)`):**
Спільне знання визначається як нескінченна кон'юнкція всіх можливих рівнів взаємного знання:
```
C(m) ≡ ⋀_{k=1}^∞ E^k(m) = E^1(m) ∧ E^2(m) ∧ E^3(m) ∧ ...
```

![Ієрархія станів знання у розподіленій системі](/root/eng/sf-distributed/two-generals-problem/img/common-knowledge-hierarchy.svg)

*Ієрархія епістемічного знання: перехід від індивідуального до спільного знання, що є недосяжним через ненадійний канал.*

Гальперн і Мозес довели фундаментальну теорему: **будь-яка узгоджена детермінована дія двох або більше незалежних вузлів можлива тоді й лише тоді, коли стан готовності до дії є спільним знанням `C(m)`**.

Але в будь-якій системі, де повідомлення можуть губитися (`p > 0`) або затримуватися на невідомий час, стан `C(m)` є **математично недосяжним** за скінченну кількість повідомлень.

Кожне надіслане повідомлення піднімає рівень знання системи лише на одну сходинку вгору (з `E^k` до `E^{k+1}`), але ніколи не сягає нескінченності `C(m)`. Саме тому генерали принципово не можуть домовитися.

## Спектр проблем узгодженості: порівняльний аналіз

У розподілених системах часто виникає плутанина між трьома фундаментальними результатами про неможливість. Розставимо акценти між ними:

| Параметр | Задача двох генералів (1975/1978) | Візантійські генерали (1982) | Теорема неможливості FLP (1985) |
|---|---|---|---|
| **Модель каналу** | Ненадійний (пакети губляться, `p > 0`) | Абсолютно надійний (пакети не губляться) | Надійний (кожен пакет рано чи пізно дійде) |
| **Модель вузлів** | Чесні (не падають, не брешуть) | Візантійські (частина вузлів бреше й шкодить) | Crash-Stop (чесні, але можуть впасти назавжди) |
| **Модель часу** | Будь-яка (синхронна або асинхронна) | Синхронна раундова модель | Строго асинхронна (затримка не обмежена) |
| **Мінімальний кворум** | Неможливо навіть для `N = 2` при `f = 0` збоїв | Розв'язна за умови `N ≥ 3f + 1` | Неможливо для `N ≥ 3` навіть при `f = 1` аварії |
| **Причина заборони** | Недосяжність спільного знання `C(m)` | Неможливість відрізнити правду від брехні | Нерозрізненність повільного вузла від мертвого |

Задача двох генералів є найбільш фундаментальним і жорстким обмеженням: вона забороняє консенсус навіть для двох ідеально працюючих серверів, якщо між ними лежить ненадійний дріт.

## Межа між задачею двох генералів та кворумним консенсусом (Paxos, Raft)

Виникає закономірне питання: чому сучасні протоколи розподіленого консенсусу, такі як Paxos та Raft, успішно працюють над ненадійними IP-мережами, якщо задача двох генералів забороняє консенсус?

Секрет криється в переході від парної взаємодії (`N = 2`) до мажоритарних кворумів (`N ≥ 3`):

1. **Кворум більшості замість одностайності:**
У задачі двох генералів потрібна **100% одностайність** обох вузлів (`2` з `2`). Якщо один вузол відрізано, система втрачає працездатність. У Raft або Paxos система з `2f + 1` вузлів вимагає згоди лише **простої більшості** (`f + 1` вузлів). Система продовжує фіксувати записи в журнал навіть тоді, коли `f` вузлів повністю відрізані мережевим розривом або зазнали аварії.

2. **Редукція до двох генералів при симетричному розколі (Split-Brain):**
Щойно мережевий розрив ділить кластер на дві рівні половини (наприклад, кластер із 2 вузлів розпався на `1` і `1`, або кластер із 4 вузлів розпався на `2` і `2`), жодна половина не може зібрати сувору більшість голосів. У цей момент протокол консенсусу миттєво редукується до задачі двох генералів і зупиняє прийом операцій запису, щоб запобігти розколу мозку.

Саме тому всі відмовостійкі розподілені сховища (ZooKeeper, etcd, Consul) вимагають **непарної кількості вузлів** (3, 5 або 7).

## Чому двофазний коміт (2PC) є вразливим до двох генералів

Протокол [двофазного коміту](root:sf-distributed/two-phase-commit) (2PC) є класичним прикладом того, як спроба реалізувати атомарне підтвердження над ненадійним каналом стикається з обмеженням двох генералів:

1. **Фаза голосування (Prepare Phase):** Координатор надсилає учасникам запит `PREPARE`. Учасники блокують локальні рядки в базі даних і відповідають `VOTE_COMMIT`.
2. **Фаза фіксації (Commit Phase):** Координатор, отримавши всі голоси, записує рішення `COMMIT` у свій журнал і надсилає наказ `GLOBAL_COMMIT` учасникам.

Але що відбувається, якщо координатор надіслав наказ `GLOBAL_COMMIT` першому учаснику, а потім мережевий канал між координатором і другим учасником обірвався?

Другий учасник залишається у стані `PREPARED` із заблокованими рядками таблиць. Він не знає:
* Чи координатор вирішив зафіксувати транзакцію (`COMMIT`)?
* Чи координатор вирішив скасувати транзакцію через таймаут (`ABORT`)?

Другий учасник не має права самостійно відкотити транзакцію, бо перший учасник міг уже застосувати зміни. Другий учасник також не має права самостійно зафіксувати транзакцію, бо координатор міг упасти до прийняття рішення.

Система повністю блокується (англ. *blocking protocol*). Учасник змушений нескінченно тримати блокування замків, очікуючи відновлення зв'язку, саме через фундаментальну неможливість перевірити стан координатора через ненадійний канал.

## Чому TCP 3-Way Handshake не порушує теорему

Часто інженери запитують: «Якщо консенсус над ненадійним IP-каналом неможливий, як працює тристороннє рукостискання (3-Way Handshake) протоколу TCP (`SYN` → `SYN-ACK` → `ACK`)? Хіба клієнт і сервер не домовляються про відкриття з'єднання за 3 повідомлення?»

Відповідь полягає в тому, що **TCP не вирішує задачу розподіленого консенсусу**.

TCP розв'язує набагато простішу інженерну задачу — узгодження початкових номерів послідовностей (Initial Sequence Numbers, ISN) для потоку байтів за принципом прагматичного наближення (best-effort):
1. Клієнт надсилає `SYN` (пропонує свій номер `ISN_c`).
2. Сервер відповідає `SYN-ACK` (підтверджує `ISN_c` і пропонує свій номер `ISN_s`).
3. Клієнт надсилає `ACK` (підтверджує `ISN_s`) і одразу починає передавати корисні дані.

Що станеться, якщо третій пакет `ACK` загубиться? Клієнт уже вважає з'єднання відкритим (`ESTABLISHED`), а сервер усе ще чекає в стані `SYN-RECEIVED`.

TCP не вимагає одностайного атомарного штурму фортеці. Якщо клієнт надішле наступний пакет із даними, цей пакет міститиме прапорець `ACK`, який автоматично переведе сервер у стан `ESTABLISHED`. Якщо ж клієнт нічого не надішле, сервер через певний таймаут повторно надішле `SYN-ACK`.

### Закриття з'єднання у TCP та стан TIME_WAIT
Справжній прояв задачі двох генералів у протоколі TCP виникає під час **закриття з'єднання** (Connection Teardown):
1. Вузол A надсилає `FIN` («Я закінчив передачу даних»).
2. Вузол B відповідає `ACK`, а згодом надсилає власний `FIN`.
3. Вузол A зобов'язаний надіслати фінальний `ACK`.

Але як вузол A може дізнатися, що вузол B отримав цей фінальний `ACK`? Вузол A не може чекати підтвердження на свій `ACK`, бо це знову запустило б нескінченну драбину двох генералів!

Інженери TCP вирішили цю проблему за допомогою фізичного таймера: вузол A після відправки останнього `ACK` не закриває сокет негайно, а переходить у стан `TIME_WAIT` рівно на час:

```
T_wait = 2 · MSL
```
де `MSL` (англ. *Maximum Segment Lifetime*) — максимальний час життя пакета в інтернеті (за стандартом RFC 793 становить 2 хвилини, в Linux за замовчуванням — 60 секунд).

Якщо фінальний `ACK` загубився, вузол B повторно надішле `FIN`. Вузол A, перебуваючи в стані `TIME_WAIT`, зловить цей повторний `FIN`, повторно надішле `ACK` і перезапустить таймер. Якщо ж протягом `2 · MSL` жодних повідомлень не надійшло, вузол A мовчки й безпечно звільняє ресурси сокета.

Тут ми бачимо перший фундаментальний інженерний прийом обходу задачі двох генералів: **використання фізичного часу (таймаутів) замість нескінченного обміну повідомленнями**.

## Практичні інженерні підходи до обходу проблеми

Оскільки подолати теоретичну межу двох генералів неможливо, сучасна інженерія розподілених систем використовує три взаємодоповнюючі стратегії адаптації.

![Практичні інженерні стратегії обходу задачі двох генералів](/root/eng/sf-distributed/two-generals-problem/img/two-generals-practical-patterns.svg)

*Практичні інженерні патерни: заміна неможливого детермінованого консенсусу на ідемпотентні повтори, часові оренди та саги.*

### 1. Ідемпотентність і повторні спроби (Retries with Idempotency)
Якщо ми не знаємо, чи дійшов запит або відповідь через мережу, клієнт застосовує політику повторних спроб (англ. *retries*). Проте повторний запит без додаткового захисту неминуче призведе до подвійного списання коштів, повторного створення замовлення або дублювання записів у базі даних.

Рішення полягає у наданні сервісному обробнику властивості **ідемпотентності** (лат. *idem* — той самий + *potens* — здатний, могутній): виконання однієї й тієї самої операції один раз або сто разів призводить до абсолютно однакового кінцевого стану системи:

```
f(f(x)) = f(x)
```

#### Механізм роботи ключа ідемпотентності
1. Клієнт генерує криптографічно стійкий унікальний ідентифікатор запиту (англ. *Idempotency Key*, наприклад UUID v4 або SHA-256 від бізнес-параметрів операції).
2. Клієнт надсилає запит на сервер, передаючи ключ у заголовку (наприклад, `Idempotency-Key: 7b9c...`).
3. Сервер починає транзакцію в базі даних:
   * Перевіряє таблицю `idempotency_keys` на наявність запису з цим ключем.
   * Якщо запис відсутній, сервер вставляє рядок зі статусом `IN_PROGRESS`, виконує бізнес-дію (списання коштів), оновлює статус на `COMPLETED` і зберігає результат відповіді у форматі JSON.
   * Якщо запис уже існує зі статусом `COMPLETED`, сервер пропускає виконання бізнес-логіки та миттєво повертає клієнту збережену відповідь із кешу.
   * Якщо запис існує зі статусом `IN_PROGRESS` (паралельний повтор), сервер повертає статус `409 Conflict` або блокується на замку до завершення первинного запиту.

Це перетворює ненадійний канал передачі з гарантією «at-least-once» на безпечну прикладну семантику «effectively-once».

#### Час життя ключів (TTL)
Ключі ідемпотентності не можна зберігати вічно через вичерпання дискового простору. Їм призначають час життя (англ. *Time-To-Live*, TTL — зазвичай 24–72 години). Якщо клієнт надішле повтор після вичерпання TTL, сервер сприйме операцію як нову. Тому клієнтський ліміт повторних спроб завжди зобов'язаний бути на порядки меншим за TTL ключів на сервері.

### 2. Часові оренди (Time-bounded Leases) та монотонний час
Замість спроби домовитися про точний момент завершення дії через нескінченний ланцюг підтверджень, координатор видає вузлу **оренду** (англ. *lease*, від лат. *laxare* — відпускати, послаблювати) на строго визначений проміжок фізичного часу `Δt` (наприклад, на 10 секунд).

Вузол отримує ексклюзивне право на виконання дій у проміжку:
```
[t_grant, t_grant + Δt]
```
Вузол зобов'язується самостійно зупинити будь-яку діяльність після настання часу `t_grant + Δt`. Координатор знає: щойно за його власним годинником мине час `t_grant + Δt + ε` (де `ε` — максимальний дрейф годинників), він може гарантовано передати ресурс іншому вузлу без жодного фінального підтвердження від попереднього власника.

#### Розрахунок безпечного вікна оренди
Оскільки пакети витрачають час на політ мережею (`RTT`), а локальні генератори частоти процесорів дрейфують, корисний час оренди `T_safe` на боці клієнта завжди менший за номінальний:

```
T_safe = Δt - 2 · δ_max - RTT_max
```
де `δ_max` — максимальна похибка розсинхронізації фізичних годинників, а `RTT_max` — максимальний час кругової затримки передачі пакета.

#### Монотонний час проти астрономічного
Для безпечної реалізації ліз критично використовувати монотонні таймери процесора (у Linux — системний виклик `clock_gettime(CLOCK_MONOTONIC)` або `std::chrono::steady_clock` у C++), а не астрономічний годинник реального часу (`CLOCK_REALTIME`), який може раптово стрибати назад через синхронізацію по протоколу NTP або введення високосної секунди (leap second).

### 3. Оптимістичні Саги та компенсаційні дії
У розподіленій мікросервісній архітектурі сервіси відмовляються від синхронного блокуючого двофазного коміту на користь патерна **Сага**.

Замість спроб досягти миттєвого глобального консенсусу система розбиває велику операцію на послідовність локальних транзакцій:
1. Сервіс замовлень створює запис зі статусом `PENDING`.
2. Сервіс оплати списує кошти.
3. Сервіс складу резервує товар.

Якщо будь-який крок зазнає невдачі або обривається за мережевим таймаутом, оркестратор саги запускає зворотну послідовність **компенсаційних транзакцій** (англ. *compensating transactions*): повертає гроші клієнту на карту, знімає бронь зі складу та переводить замовлення в статус `CANCELLED`.

Система жертвує миттєвою узгодженістю (ACID) заради доступності та надійності, сходячись до кінцевої узгодженості (англ. *eventual consistency*) з часом.

> 🔧 **Навіщо це на практиці.**
> Розуміння задачі двох генералів рятує від створення фатальних архітектурних рішень: спроб побудувати «ідеально синхронне» списання грошей між двома дата-центрами через HTTP без таймаутів, спроб реалізувати розподілене блокування без часових ліз, або очікування підтвердження на підтвердження в критичних чергах повідомлень.

## Практична симуляція протоколу підтвердження замовлення

Проілюструємо проблему та її практичне вирішення на реальному прикладі взаємодії між сервісом замовлень інтернет-магазину (Order Service) та сервісом платіжного шлюзу банку (Payment Gateway).

Мережа між ними моделюється як ненадійний канал із випадковою втратою пакетів (`DROP_RATE = 30%`).

У коді нижче реалізовано дві моделі:
1. **Наївний протокол нескінченного квитування:** показує, як спроба досягти стовідсоткової впевненості через ланцюг ACK призводить до блокування та неможливості прийняти фінальне рішення.
2. **Прагматичний інженерний протокол на базі часової оренди та ідемпотентного токена:** показує, як комбінація таймаутів, унікальних ключів та локальних монотонних таймерів забезпечує безпечну та стійку роботу системи.

:::tabs
```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>
#include <time.h>

#define DROP_RATE_PERCENT 30
#define LEASE_DURATION_MS 500
#define MAX_RETRIES 5

typedef enum {
    MSG_ORDER_REQ,
    MSG_PAYMENT_ACK,
    MSG_ACK_TO_ACK,
    MSG_ACK_TO_ACK_TO_ACK
} MsgType;

typedef struct {
    MsgType type;
    uint64_t order_id;
    uint64_t idempotency_key;
    uint64_t timestamp_ms;
    bool committed;
} Packet;

/* Допоміжна функція отримання монотонного часу в мілісекундах */
static uint64_t get_monotonic_ms(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint64_t)ts.tv_sec * 1000ULL + (uint64_t)ts.tv_nsec / 1000000ULL;
}

/* Симуляція ненадійного мережевого каналу */
static bool send_network_packet(const Packet *pkt, const char *sender, const char *receiver) {
    int roll = rand() % 100;
    if (roll < DROP_RATE_PERCENT) {
        printf("  [МЕРЕЖА: ВТРАТА] Пакет типу %d від %s до %s загублено в каналі!\n",
               pkt->type, sender, receiver);
        return false;
    }
    printf("  [МЕРЕЖА: ДОСТАВЛЕНО] Пакет типу %d від %s успішно дійшов до %s.\n",
           pkt->type, sender, receiver);
    return true;
}

/* 1. Демонстрація наївного протоколу нескінченних квитанцій */
static void run_naive_ack_ladder(uint64_t order_id) {
    printf("\n=== 1. НАЇВНИЙ ПРОТОКОЛ: Нескінченна драбина квитування ===\n");
    
    Packet req = { .type = MSG_ORDER_REQ, .order_id = order_id, .committed = false };
    printf("Крок 1: Магазин надсилає запит на оплату замовлення #%lu...\n", order_id);
    
    if (!send_network_packet(&req, "Магазин", "Банк")) {
        printf("Магазин не знає, чи отримав Банк наказ. Магазин блокується.\n");
        return;
    }

    Packet ack1 = { .type = MSG_PAYMENT_ACK, .order_id = order_id, .committed = true };
    printf("Крок 2: Банк провів оплату та надсилає ACK1 Магазину...\n");
    if (!send_network_packet(&ack1, "Банк", "Магазин")) {
        printf("Банк списав кошти, але Магазин не отримав ACK1! Банк не знає, що робити.\n");
        return;
    }

    Packet ack2 = { .type = MSG_ACK_TO_ACK, .order_id = order_id, .committed = true };
    printf("Крок 3: Магазин отримав ACK1 і надсилає ACK2 (підтвердження на підтвердження)...\n");
    if (!send_network_packet(&ack2, "Магазин", "Банк")) {
        printf("ACK2 загубився! Банк не впевнений, чи Магазин знає про оплату. Глухий кут.\n");
        return;
    }

    printf("Результат: Обидва вузли отримали по пакету, але останній відправник усе одно не має 100%% гарантії!\n");
}

/* 2. Прагматичний інженерний протокол: Часова оренда + Ідемпотентний токен */
typedef struct {
    uint64_t idempotency_key;
    bool is_paid;
    uint64_t lease_expiry_ms;
} BankRecord;

static void run_pragmatic_lease_protocol(uint64_t order_id, uint64_t key) {
    printf("\n=== 2. ПРАГМАТИЧНИЙ ПРОТОКОЛ: Часова оренда та ідемпотентність ===\n");
    
    BankRecord bank_db = { .idempotency_key = key, .is_paid = false, .lease_expiry_ms = 0 };
    bool order_completed = false;
    
    for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
        uint64_t now = get_monotonic_ms();
        printf("Спроба #%d: Магазин відправляє запит (Ключ=%lu, Оренда=%d мс)...\n",
               attempt, key, LEASE_DURATION_MS);
        
        Packet req = {
            .type = MSG_ORDER_REQ,
            .order_id = order_id,
            .idempotency_key = key,
            .timestamp_ms = now + LEASE_DURATION_MS
        };

        if (send_network_packet(&req, "Магазин", "Банк")) {
            /* Обробка на боці Банку з перевіркою ідемпотентності */
            if (!bank_db.is_paid) {
                bank_db.is_paid = true;
                bank_db.lease_expiry_ms = req.timestamp_ms;
                printf("  [Банк]: Нова транзакція. Кошти зарезервовано за орендою до t=%lu мс.\n",
                       bank_db.lease_expiry_ms);
            } else {
                printf("  [Банк]: Повторний запит із відомим ключем %lu. Повертаємо кешований успіх.\n", key);
            }

            Packet ack = {
                .type = MSG_PAYMENT_ACK,
                .order_id = order_id,
                .idempotency_key = key,
                .committed = true
            };

            if (send_network_packet(&ack, "Банк", "Магазин")) {
                printf("  [Магазин]: Отримано квитанцію про успішну оплату! Замовлення видано клієнту.\n");
                order_completed = true;
                break;
            } else {
                printf("  [Магазин]: Відповідь від банку загубилася. Магазин чекає таймаут для повтору...\n");
            }
        } else {
            printf("  [Магазин]: Запит не дійшов до банку. Очікування таймауту...\n");
        }
    }

    if (order_completed) {
        printf("\nУспіх: Протокол успішно завершив узгодження без нескінченних квитанцій.\n");
    } else {
        printf("\nТаймаут: Вичерпано всі %d спроб. Запуск компенсаційної процедури саги.\n", MAX_RETRIES);
    }
}
```

```cpp
namespace distributed {

using namespace std::chrono_literals;

enum class MessageType {
    OrderRequest,
    PaymentAck,
    AckToAck
};

struct Packet {
    MessageType type;
    uint64_t order_id;
    uint64_t idempotency_key;
    std::chrono::steady_clock::time_point lease_deadline;
    bool committed{false};
};

/* Клас імітації ненадійного мережевого середовища */
class UnreliableChannel {
public:
    explicit UnreliableChannel(int drop_percentage)
        : drop_rate_(drop_percentage), rng_(1337) {}

    bool transmit(const Packet& pkt, std::string_view from, std::string_view to) {
        std::uniform_int_distribution<int> dist(0, 99);
        if (dist(rng_) < drop_rate_) {
            std::cout << "  [МЕРЕЖА: ВТРАТА] Пакет від " << from << " до " << to << " загублено!\n";
            return false;
        }
        std::cout << "  [МЕРЕЖА: ДОСТАВЛЕНО] Пакет від " << from << " до " << to << " успішно дійшов.\n";
        return true;
    }

private:
    int drop_rate_;
    std::mt19937 rng_;
};

/* Банківський платіжний сервіс із захистом через ідемпотентність та оренди */
class PaymentGateway {
public:
    struct TransactionState {
        bool paid{false};
        std::chrono::steady_clock::time_point lease_expiry;
    };

    std::optional<Packet> handle_request(const Packet& req) {
        auto now = std::chrono::steady_clock::now();
        auto& record = ledger_[req.idempotency_key];

        if (!record.paid) {
            record.paid = true;
            record.lease_expiry = req.lease_deadline;
            std::cout << "  [Банк]: Первинна обробка замовлення #" << req.order_id 
                      << ". Оренда зафіксована.\n";
        } else {
            std::cout << "  [Банк]: Виявлено дублікат запиту (ключ " << req.idempotency_key 
                      << "). Повертаємо збережений статус оплати.\n";
        }

        return Packet{
            .type = MessageType::PaymentAck,
            .order_id = req.order_id,
            .idempotency_key = req.idempotency_key,
            .lease_deadline = record.lease_expiry,
            .committed = true
        };
    }

private:
    std::unordered_map<uint64_t, TransactionState> ledger_;
};

/* Сервіс замовлень із підтримкою повторів та дедлайнів */
class OrderServiceClient {
public:
    OrderServiceClient(UnreliableChannel& channel, PaymentGateway& gateway)
        : channel_(channel), gateway_(gateway) {}

    bool execute_order(uint64_t order_id, uint64_t idempotency_key) {
        constexpr int max_retries = 5;
        constexpr auto lease_time = 500ms;

        for (int attempt = 1; attempt <= max_retries; ++attempt) {
            auto now = std::chrono::steady_clock::now();
            auto deadline = now + lease_time;

            std::cout << "Спроба #" << attempt << ": Відправка запиту на оплату замовлення #" 
                      << order_id << "...\n";

            Packet req{
                .type = MessageType::OrderRequest,
                .order_id = order_id,
                .idempotency_key = idempotency_key,
                .lease_deadline = deadline,
                .committed = false
            };

            if (channel_.transmit(req, "Магазин", "Банк")) {
                auto response = gateway_.handle_request(req);
                if (response.has_value() && channel_.transmit(*response, "Банк", "Магазин")) {
                    std::cout << "  [Магазин]: Отримано успішне підтвердження! Замовлення видано клієнту.\n";
                    return true;
                }
                std::cout << "  [Магазин]: Зворотний ACK втрачено. Очікування таймауту перед повтором...\n";
            } else {
                std::cout << "  [Магазин]: Запит втрачено в дорозі. Очікування таймауту...\n";
            }
        }
        std::cout << "  [Магазин]: Вичерпано ліміт спроб. Запуск компенсаційної саги.\n";
        return false;
    }

private:
    UnreliableChannel& channel_;
    PaymentGateway& gateway_;
};

} // namespace distributed

    return 0;
}
```

## Головні висновки

Задача двох генералів встановлює непорушний теоретичний фундамент для розуміння розподілених систем:

1. **Детермінований консенсус над ненадійним каналом неможливий:** Жоден алгоритм обміну повідомленнями не може гарантувати стовідсотково узгоджених дій, якщо хоча б одне повідомлення може бути стерте мережею.
2. **Спільне знання недосяжне за скінченний час:** Будь-яка скінченна кількість квитанцій залишає останнього відправника в повній невизначеності щодо стану партнера.
3. **Практика спирається на прагматичні наближення:** Замість нескінченного квитування реальні інженерні системи використовують часові таймаути (`TIME_WAIT`), ідемпотентні повтори (At-Least-Once + дедуплікація), часові оренди (Leases) та компенсаційні транзакції (Саги).
