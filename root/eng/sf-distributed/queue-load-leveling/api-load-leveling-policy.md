# 📋 Специфікація та контракт політики демпфування навантаження (Load Leveling Policy)

Специфікація визначає конфігураційну схему, правила регулювання вхідного потоку, параметри обмеження споживання та HTTP/gRPC контракт взаємодії клієнта зі шлюзом демпфування (*Queue Load Leveler*).

Інтерфейс демпфування навантаження виконує роль регулятора пропускної здатності між ненадійним зовнішнім середовищем та чутливими внутрішніми сервісами зберігання даних. Головне завдання цієї специфікації — надати прозорий, машинно-інтерпретований контракт, який одночасно керує поведінкою вхідного шлюзу прийому повідомлень, внутрішнього брокера буферизації та пулу воркерів-виконавців.

## 1. Схема конфігурації політики (Load Leveling Policy Schema)

Конфігурація визначається у декларативному форматі YAML або JSON і завантажується інфраструктурним рушієм шлюзу та диспетчером пулу споживачів під час старту або динамічно через механізм гарячого перезавантаження (*hot reload*).

```yaml
apiVersion: resilience.distributed/v1
kind: LoadLevelingPolicy
metadata:
  name: order-processing-leveler
  namespace: checkout
spec:
  # ── 1. Параметри буфера черги ─────────────────────────────────────────────
  buffer:
    max_capacity: 100000              # Максимальна місткість черги в повідомленнях
    high_watermark_ratio: 0.85        # Поріг 85%: увімкнення адаптивного відхилення
    low_watermark_ratio: 0.50         # Поріг 50%: повернення до прийому 100% трафіку
    storage_type: "persistent_wal"    # "in_memory" | "persistent_wal"
    sync_mode: "async_flush"          # "strict_fsync" | "async_flush"

  # ── 2. Параметри пулу споживачів та обмеження темпу ───────────────────────
  consumer:
    concurrency_pool_size: 40         # Кількість паралельних потоків/воркерів
    rate_limiter:
      algorithm: "token_bucket"       # "token_bucket" | "leaky_bucket"
      rate_limit_rps: 400             # Максимальний темп звернень до бази даних
      burst_capacity: 50              # Максимальний миттєвий сплеск токенів
    visibility_timeout_ms: 30000      # Ліза блокування повідомлення (30 секунд)
    heartbeat_interval_ms: 5000       # Інтервал оновлення оренди воркером

  # ── 3. Політика життєвого циклу повідомлень і DLQ ──────────────────────────
  lifecycle:
    message_ttl_ms: 300000            # Граничний час життя задачі (5 хвилин)
    max_delivery_attempts: 3          # Максимум 3 спроби обробки перед DLQ
    dead_letter_queue:
      enabled: true
      target_topic: "orders-processing-dlq"
      retention_days: 14

  # ── 4. Стратегія зворотного тиску (Backpressure & Shedding) ───────────────
  backpressure:
    rejection_strategy: "http_429"    # "http_429" | "drop_oldest" | "drop_newest"
    dynamic_retry_after: true         # Автоматичний розрахунок затримки Retry-After
    retry_after_min_seconds: 5
    retry_after_max_seconds: 60
```

## 2. Глибокий розбір параметрів політики та інженерні обмеження

Кожен розділ конфігурації відповідає за ізольовану зону відповідальності в ланцюжку обробки. Неправильне узгодження цих параметрів між собою може призвести до прихованих дефектів — від вичерпання дискового простору брокера до блокування черги отруйними повідомленнями.

### Секція керування буфером (Buffer Management)

Параметр `buffer.max_capacity` встановлює жорстку стелю кількості елементів, які черга має право утримувати в оперативній пам'яті та на диску. Ця величина розраховується з огляду на середній розмір корисного навантаження повідомлення та доступний обсяг дискового розділу під журнал випереджального запису (*Write-Ahead Log*). Якщо середній розмір задачі становить 4 кілобайти, буфер на 100 000 елементів потребує щонайменше 400 мегабайтів дискової пам'яті лише під тіла повідомлень без урахування службових індексів.

Параметри `high_watermark_ratio` та `low_watermark_ratio` реалізують гістерезис керування зворотним тиском. Коли черга заповнюється до 85% від максимальної ємності (верхній поріг), шлюз прийому перестає приймати нові задачі й починає повертати клієнтам помилку відхилення. Якщо система просто вимикала б блокування в момент зниження заповнення до 84.9%, шлюз зазнавав би високочастотного тремтіння (*flapping*), вмикаючи й вимикаючи прийом щосекунди. Завдяки нижньому порогу 50% шлюз тримає блокування активним доти, доки воркери не розвантажать чергу наполовину, забезпечуючи гарантований запас міцності для прийому наступного сплеску.

Режим `storage_type` та `sync_mode` визначає компроміс між надійністю збереження та пропускною здатністю. Значення `persistent_wal` у поєднанні з `async_flush` дозволяє операційній системі скидати сторінки пам'яті на диск фоново кожні 500 мілісекунд, забезпечуючи швидкість запису до сотень тисяч операцій на секунду з мінімальним ризиком втрати лише останніх часток секунди даних при раптовому вимкненні живлення.

### Секція регулювання споживання (Consumer Throttling)

Розділ `consumer` налаштовує темп, з яким пул воркерів звертається до захищеного бекенду (реляційної бази даних PostgreSQL/MySQL або зовнішнього платіжного API).

Параметр `concurrency_pool_size` визначає максимальну кількість одночасно активних потоків або процесів-виконавців. Цей параметр повинен суворо узгоджуватися з пулом з'єднань бази даних. Якщо пул з'єднань БД обмежений 50 клієнтами, значення `concurrency_pool_size` не може перевищувати 40–45, щоб залишити резерв для адміністративних запитів, системного моніторингу та інтерактивних транзакцій.

Алгоритм `rate_limiter` (за замовчуванням `token_bucket`) забезпечує математичне обмеження сумарного вихідного потоку запитів. Параметр `rate_limit_rps` встановлює стабільну швидкість поповнення кошика токенами, а `burst_capacity` дозволяє короткочасне перевищення темпу, якщо база даних перебуває в ненавантаженому стані. Кожен воркер перед відправкою важкої транзакції до бази даних зобов'язаний отримати токен з лімітера. Якщо токенів немає, воркер переходить у стан очікування, утримуючи повідомлення в черзі.

Параметр `visibility_timeout_ms` задає тривалість лізи блокування повідомлення. Якщо воркер забрав повідомлення з черги, але завис або впав через вичерпання пам'яті, брокер чекає рівно 30 секунд. Після завершення цього інтервалу повідомлення автоматично повертається у стан готовності й стає видимим для інших воркерів. Для довгих бізнес-задач воркер зобов'язаний надсилати періодичні сигнали продовження оренди з інтервалом `heartbeat_interval_ms`.

### Секція життєвого циклу повідомлень (Message Lifecycle & DLQ)

Параметр `lifecycle.message_ttl_ms` запобігає «синдрому застарілих задач». У системах замовлення таксі або бронювання квитків запит, що пролежав у черзі понад 5 хвилин, повністю втрачає актуальність: користувач уже закрив додаток або пішов на інший сервіс. Обробка такого запиту через 20 хвилин лише безглуздо навантажить базу даних і призведе до конфліктів у бізнес-логіці. Задачі, чий вік перевищує `message_ttl_ms`, негайно списуються шлюзом або воркером без виконання бізнес-транзакції.

Параметр `max_delivery_attempts` ізолює так звані «отруйні пігулки» (*Poison Pills*) — некоректно сформовані повідомлення, які викликають неперехоплюваний виняток або аварійне завершення воркера при кожній спробі десеріалізації. Якщо повідомлення тричі призвело до збою, брокер переміщує його в ізольований канал `dead_letter_queue.target_topic` для подальшого ручного розслідування інженерами, звільняючи основну чергу для нормального проходження здорового трафіку.

## 3. Клієнтський HTTP-контракт шлюзу прийому

Шлюз демпфування реалізує асинхронний протокол прийому задач відповідно до стандартів REST та RFC 7231.

### Прийом задачі у штатному режимі (`HTTP 202 Accepted`)

Коли черга функціонує в межах безпечної ємності, шлюз валідує заголовки, генерує унікальний ідентифікатор задачі, записує її в буфер черги та повертає статус `202 Accepted` без очікування завершення реальної бізнес-обробки.

**Приклад вхідного HTTP-запиту:**
```http
POST /api/v1/orders HTTP/1.1
Host: api.store.internal
Content-Type: application/json
Idempotency-Key: 7b8c2d89-983a-4e2b-a19c-3677e5621aef

{
  "customer_id": "usr_99182",
  "items": [
    {"sku": "SKU-4401", "quantity": 2, "price_cents": 1499}
  ],
  "payment_token": "tok_visa_live_8839"
}
```

**Відповідь шлюзу:**
```http
HTTP/1.1 202 Accepted
Location: /api/v1/orders/tasks/tsk_01HX4A7B8Z
Retry-After: 15
Content-Type: application/json

{
  "task_id": "tsk_01HX4A7B8Z",
  "status": "QUEUED",
  "created_at": "2026-08-20T12:00:00.124Z",
  "estimated_processing_delay_seconds": 12.4,
  "links": {
    "status": "/api/v1/orders/tasks/tsk_01HX4A7B8Z",
    "cancel": "/api/v1/orders/tasks/tsk_01HX4A7B8Z/abort"
  }
}
```

Заголовок `Location` надає клієнту URI для періодичного опитування статусу виконання (*polling endpoint*). Заголовок `Retry-After` рекомендує клієнту не турбувати сервер повторними опитуваннями щонайменше 15 секунд, запобігаючи створенню додаткового паразитного навантаження на шлюз статусів.

### Відхилення задачі при переповненні буфера (`HTTP 429 Too Many Requests`)

Коли глибина черги досягає верхнього порогу `buffer.high_watermark_ratio` або максимальної місткості `buffer.max_capacity`, шлюз припиняє прийом нових операцій, захищаючи себе та брокер від відмови за ресурсами пам'яті чи диска.

**Відповідь шлюзу при перевантаженні:**
```http
HTTP/1.1 429 Too Many Requests
Retry-After: 45
X-RateLimit-Current-Backlog: 85200
X-RateLimit-Max-Capacity: 100000
Content-Type: application/json

{
  "error": "QUEUE_CAPACITY_EXCEEDED",
  "message": "Вхідна черга заповнена на 85.2%. Будь ласка, зачекайте перед повторною відправкою.",
  "retry_after_seconds": 45,
  "queue_utilization_ratio": 0.852
}
```

Шлюз динамічно розраховує значення заголовка `Retry-After` за поточною кількістю задач у черзі `Q(t)` та сталою швидкістю спорожнення `μ`:

```
Retry-After = clamp(ceil(Q_current / μ), retry_after_min, retry_after_max)
```

## 4. Специфікація метрик телеметрії (Prometheus Metrics)

Для автоматизованого контролю стану демпфера та підключення горизонтального автоскейлінгу (KEDA) експортуються такі ключові метрики:

```
# Поточна кількість повідомлень у буфері черги
leveler_queue_depth_messages{policy="order-processing-leveler", buffer="primary"} 12450

# Лічильник вхідних запитів за статусами відповіді
leveler_ingress_requests_total{policy="order-processing-leveler", status="accepted"} 941020
leveler_ingress_requests_total{policy="order-processing-leveler", status="rejected_429"} 540

# Поточна швидкість вичитування задач пулом воркерів (запитів на секунду)
leveler_drain_rate_rps{policy="order-processing-leveler"} 398.5

# Вік найстарішого невиконаного повідомлення на початку черги (у секундах)
leveler_queue_lag_seconds{policy="order-processing-leveler"} 31.2

# Кількість задач, відправлених у мертву чергу (DLQ)
leveler_dlq_routed_total{policy="order-processing-leveler", reason="max_retries"} 14
leveler_dlq_routed_total{policy="order-processing-leveler", reason="expired_ttl"} 82

# Кількість активних воркерів у пулі
leveler_worker_pool_active{policy="order-processing-leveler"} 38
```

Ці метрики дозволяють системі спостереження миттєво виявляти аномалії: якщо `leveler_queue_lag_seconds` безперервно зростає при стабільному `leveler_drain_rate_rps`, це сигналізує про надходження тривалого сплеску, що вимагає втручання оператора або розширення допустимого ліміту швидкості бекенду.
