# 🧮 Математична модель вирівнювання навантаження: гідродинаміка сплеску, закон Літтла та формула Кінгмана

Математичний аналіз патерну вирівнювання навантаження чергою описує перетворення нерівномірного вхідного стохастичного потоку задач на стабільний вихідний потік фіксованої інтенсивності. Для повного розрахунку системи використовуються два математичні апарати:
1. **Детермінована гідродинамічна модель неперервної рідини (*Fluid Flow Model*):** розраховує пікову глибину накопичення задач, час повного розвантаження черги (*Drain Time*) та максимальну затримку відгуку під час різких прямокутних чи трикутних сплесків трафіку.
2. **Стохастична теорія черг і наближення Кінгмана (*Kingman's Heavy-Traffic Formula*):** доводить, чому синхронна система без буфера зазнає експоненційного колапсу латентності при наближенні навантаження до граничної ємності, і як черга ізолює бекенд у зоні безпечної утилізації.

## 1. Детермінована модель сплеску: баланс маси та час розвантаження

Розглянемо систему, де вхідний потік завдань має інтенсивність `λ(t)` (запитів на секунду), а захищений бекенд (пул воркерів і база даних) має максимальну безпечну швидкість обробки `μ` (запитів на секунду).

У будь-який момент часу швидкість зміни кількості повідомлень у черзі `Q(t)` визначається фундаментальним рівнянням балансу:

```
dQ(t) / dt = λ(t) - μ(t)    [якщо Q(t) > 0 або λ(t) ≥ μ]
```

### Параметри прямокутного сплеску (Flash Crowd)

Нехай у системі діють такі умови:
- Базовий фоновий трафік: `λ₀` запитів/с.
- У момент `t = 0` починається рекламний сплеск інтенсивністю `λ_p` запитів/с, де `λ_p > μ`.
- Тривалість сплеску становить `T_burst` секунд.
- Після моменту `t = T_burst` інтенсивність вхідного потоку миттєво повертається до базового рівня `λ₀`, де `λ₀ < μ`.
- Пропускна здатність воркерів підтримується на максимальному рівні `μ`.

### 1. Розрахунок пікової глибини черги `Q_max`

Протягом інтервалу `[0, T_burst]` швидкість наповнення черги є додатною і дорівнює `λ_p - μ`. Піковий розмір беклогу досягається в момент завершення сплеску `t = T_burst`:

```
Q_max = ∫₀^{T_burst} (λ_p - μ) dt
      = (λ_p - μ) · T_burst      [інтегрування константи]
```

### 2. Розрахунок часу зливу черги `T_drain`

Після завершення сплеску (`t > T_burst`) вхідний потік зменшується до `λ₀`. Швидкість спорожнення черги стає від'ємною і дорівнює `-(μ - λ₀)`. Час `T_drain`, необхідний для повного обнулення черги `Q(t) = 0`, розраховується з умови:

```
Q_max - (μ - λ₀) · T_drain = 0
(μ - λ₀) · T_drain = Q_max              [перенесення доданка]
T_drain = Q_max / (μ - λ₀)              [ділення на швидкість зливу]
T_drain = T_burst · (λ_p - μ) / (μ - λ₀) [підстановка виразу для Q_max]
```

Загальний час повернення системи до стаціонарного стану:

```
T_total = T_burst + T_drain
```

### 3. Максимальний час очікування задачі в черзі `W_max`

Повідомлення, що надійшло в чергу наприкінці сплеску (у момент `t = T_burst`), застане перед собою повний беклог розміром `Q_max`. Час його очікування в черзі до моменту взяття в обробку:

```
W_max = Q_max / μ
```

### Числовий приклад розрахунку системи

**Вхідні інженерні параметри:**
- Базовий трафік: `λ₀ = 50` req/s.
- Пропускна здатність бекенду: `μ = 400` req/s.
- Піковий сплеск: `λ_p = 4400` req/s.
- Тривалість сплеску: `T_burst = 30` секунд.

**Покроковий розрахунок:**

```
1. Пікова глибина черги:
   Q_max = (4400 - 400) · 30
         = 4000 · 30
         = 120 000 повідомлень

2. Час повного розвантаження черги після сплеску:
   T_drain = 120 000 / (400 - 50)
           = 120 000 / 350
           ≈ 342.86 секунд (≈ 5.7 хвилин)

3. Загальний час повернення системи до спокою:
   T_total = 30 + 342.86 = 372.86 секунд (≈ 6.2 хвилини)

4. Максимальна затримка очікування для останнього повідомлення сплеску:
   W_max = 120 000 / 400
         = 300 секунд (5 хвилин)
```

**Інженерний висновок:** черга накопичує 120 000 повідомлень, повністю захищаючи базу даних від перевантаження 4400 RPS. Клієнти, що надіслали запити на піку, отримають результат через 5 хвилин (через опитування або webhook), але жодна операція не буде втрачена, і бекенд не впаде.

## 2. Закон Літтла та стаціонарний стан

У стаціонарному режимі зв'язок між середньою кількістю повідомлень у системі `L`, середнім часом перебування повідомлення в системі `W` та інтенсивністю надходження `λ` описується законом Літтла (*Little's Law*):

```
L = λ · W
```

Для системи демпфування закон Літтла розділяється на дві складові: очікування в черзі та безпосередню обробку воркером:

```
W = W_q + W_s
```
- `W_q` — середній час очікування в черзі.
- `W_s = 1 / μ` — середній час виконання запиту на бекенді.
- `L_q = λ · W_q` — середня довжина черги.

## 3. Стохастичний колапс синхронних систем: наближення Кінгмана

Чому пряма синхронна взаємодія без буфера зазнає аварії задовго до того, як середнє навантаження досягне 100% ємності сервера?

У реальних системах інтервали між надходженням запитів та час їх обробки є випадковими величинами з коефіцієнтами варіації `c_a` (варіація інтервалів надходження) та `c_s` (варіація часу виконання).

Для довільної чергової системи типу `G/G/1` середній час очікування в черзі описується **формулою Кінгмана** (*Kingman's Formula for Heavy Traffic*):

```
W_q ≈ (ρ / (1 - ρ)) · ((c_a² + c_s²) / 2) · (1 / μ)
```
де:
- `ρ = λ / μ` — коефіцієнт утилізації ресурсу (від 0.0 до 1.0).
- `c_a = σ_a / E[a]` — коефіцієнт варіації інтервалів між запитами.
- `c_s = σ_s / E[s]` — коефіцієнт варіації часу обслуговування.
- `1 / μ` — середній час обробки одного запиту.

### Аналіз множників формули Кінгмана

Формула Кінгмана складається з трьох критичних факторів:

1. **Множник утилізації `ρ / (1 - ρ)`:**
   Коли навантаження системи наближається до максимуму (`ρ → 1.0`), знаменник прямує до нуля, і час очікування стрімко зростає до нескінченності:
   - При `ρ = 0.50` множник дорівнює `0.5 / 0.5 = 1.0`.
   - При `ρ = 0.80` множник дорівнює `0.8 / 0.2 = 4.0`.
   - При `ρ = 0.95` множник дорівнює `0.95 / 0.05 = 19.0`.
   - При `ρ = 0.99` множник дорівнює `0.99 / 0.01 = 99.0`.

2. **Множник стохастичної варіативності `(c_a² + c_s²) / 2`:**
   У синхронних системах вхідний потік є нерівномірним сплесковим (*bursty*), що дає `c_a >> 1`. Якщо час виконання запитів у базі даних також коливається через блокування таблиць (`c_s > 1`), затримка додатково зростає в рази навіть при невисокій середній утилізації.

### Механізм захисту за допомогою черги

Патерн Queue-Based Load Leveling розв'язує конфлікт Кінгмана у два етапи:
1. **Зниження варіативності на боці споживача:** воркери вичитують задачі з постійною регулярною швидкістю, що зводить коефіцієнт варіації надходження до бази даних практично до нуля (`c_a ≈ 0`).
2. **Штучне обмеження утилізації бекенду:** кількість паралельних воркерів підбирається так, щоб утилізація бази даних ніколи не перевищувала безпечний поріг `ρ_safe ≤ 0.75–0.80`.

У результаті час відгуку безпосередньо бази даних лишається стабільно низьким і детермінованим, а вся нестабільність та затримка сплеску ізолюються всередині пружного буфера черги повідомлень.
