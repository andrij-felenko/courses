# 📋 Специфікація та конфігурація перебірок: Envoy, Resilience4j та хмарні шлюзи

Цей довідник містить технічні інтерфейсні контракти, параметри конфігурації, семантику поведінки, схеми телеметрії та формати повідомлень про помилки для реалізації перебірок на рівнях хмарних проксі-сервісів (Envoy Proxy), бібліотек прикладного рівня (Resilience4j) та розподілених API-шлюзів.

## 1. Специфікація перебірки на рівні Envoy Proxy (Service Mesh / Gateway)

У проксі-сервері Envoy налаштування перебірок інтегровані в секцію `circuit_breakers` конфігурації кластера (`envoy.config.cluster.v3.CircuitBreakers`). Кожен параметр діє як ізольований бар'єр на відповідному транспортному рівні (TCP-з'єднання, черга очікування пулу або HTTP/2-потоки).

```yaml
static_resources:
  clusters:
  - name: service_recommendations
    connect_timeout: 0.25s
    type: STRICT_DNS
    lb_policy: ROUND_ROBIN
    circuit_breakers:
      thresholds:
      - priority: DEFAULT
        max_connections: 50        # Перебірка L2: максимум відкритих TCP-з'єднань
        max_pending_requests: 10   # Перебірка L1: черга очікування пулу з'єднань
        max_requests: 100          # Перебірка L1: максимум активних паралельних HTTP/2 запитів
        max_retries: 3             # Максимум паралельних повторних спроб
        track_remaining: true      # Додавання телеметричних лічильників залишку
```

### Семантика параметрів та механізм спрацьовування Envoy

Кожен параметр секції `thresholds` захищає специфічний ресурс проксі-сервера та цільового вузла:

1. **`max_connections` (uint32, за замовчуванням 1024):**
   Визначає максимальну сумарну кількість одночасно відкритих TCP-з'єднань, які Envoy може тримати з усіма екземплярами цього кластера. Якщо бекенд не підтримує мультиплексування (наприклад, чистий HTTP/1.1), кожен паралельний запит вимагає окремого з'єднання. Досягнення цього порогу запобігає вичерпанню сокетних дескрипторів операційної системи (`file descriptors`, ліміт `ulimit -n`) та пам'яті буферів сокетів ядра Linux (`SO_RCVBUF`, `SO_SNDBUF`). Будь-яка спроба відкрити додаткове з'єднання блокується, і запит переводиться у стан очікування в черзі `pending_requests`.

2. **`max_pending_requests` (uint32, за замовчуванням 1024):**
   Визначає максимальну кількість запитів, які можуть очікувати на вільне TCP-з'єднання у внутрішньому пулі Envoy. Цей параметр вимагає особливої уваги: значення за замовчуванням (1024) є небезпечно високим для більшості мікросервісів, оскільки затримка очікування в черзі додається до загального часу запиту. У високонавантажених системах цей ліміт встановлюють на рівні 5–20 запитів, забезпечуючи швидке скидання навантаження (англ. *fast load shedding*) замість роздуття пам'яті.

3. **`max_requests` (uint32, за замовчуванням 1024):**
   Максимальна кількість паралельних активних запитів, які можуть одночасно оброблятися всіма бекендами кластера. Для протоколів HTTP/2, HTTP/3 та gRPC, де через одне TCP-з'єднання мультиплексуються сотні незалежних потоків, саме цей параметр виступає головним лімітером внутрішньої конкурентності. Якщо кількість активних потоків сягає `max_requests`, Envoy негайно повертає клієнту помилку без створення мережевого навантаження на бекенд.

4. **`max_retries` (uint32, за замовчуванням 3):**
   Обмежує кількість одночасно виконуваних повторних спроб (ретраїв). Це запобігає виникненню «шторму повторів» (англ. *retry storm*), коли тимчасово перевантажений сервіс отримує подвійну лавину повторних пакетів.

5. **`track_remaining` (bool, за замовчуванням false):**
   Якщо встановлено в `true`, Envoy починає генерувати динамічні метрики `cx_open` та `rq_open`, які показують точну кількість вільних слотів, доступних у даний момент часу.

### Контракт HTTP-відповіді та діагностичні заголовки

Коли будь-який із лімітів перебірки вичерпано, Envoy негайно розриває з'єднання або повертає HTTP-відповідь із внутрішнім прапорцем причини скидання:

```http
HTTP/1.1 503 Service Unavailable
content-length: 91
content-type: text/plain
date: Thu, 20 Aug 2026 12:00:00 GMT
server: envoy
x-envoy-overloaded: true
x-envoy-upstream-overflow: true

upstream connect error or disconnect/overflow before headers. reset reason: overflow
```

Прапорець `x-envoy-upstream-overflow: true` дозволяє клієнтським шлюзам однозначно визначити, що помилка виникла через спрацьовування внутрішньої перебірки Envoy, а не через падіння цільового бекенду.

## 2. Специфікація Resilience4j Bulkhead (Java / Kotlin / JVM)

Фреймворк Resilience4j надає дві взаємодоповнюючі реалізації перебірки: легковагову синхронну **SemaphoreBulkhead** та асинхронну **ThreadPoolBulkhead**.

### Конфігурація через `application.yml`

```yaml
resilience4j:
  bulkhead:
    instances:
      paymentService:
        maxConcurrentCalls: 40             # Ліміт одночасних викликів на семафорі
        maxWaitDuration: 10ms              # Час блокування потоку в очікуванні слота
        writableStackTraceEnabled: false   # Оптимізація пам'яті: вимкнення запису стек-трейсу
      recommendationService:
        maxConcurrentCalls: 15
        maxWaitDuration: 0ms               # Швидке скидання (Zero wait, Fast-fail)
  
  thread-pool-bulkhead:
    instances:
      orderExportService:
        coreThreadPoolSize: 4              # Базовий розмір виділеного пулу
        maxThreadPoolSize: 8               # Максимальний розмір пулу при сплесках
        queueCapacity: 20                  # Обмежена черга завдань
        keepAliveDuration: 20ms            # Час життя надлишкових потоків
        writableStackTraceEnabled: false
```

### Повна семантика параметрів Resilience4j

1. **`maxConcurrentCalls` (int, за замовчуванням 25):**
   Задає початкову кількість дозволів атомарного семафора. Кожен потік, що викликає захищений метод, повинен успішно декрементувати цей лічильник. Якщо лічильник дорівнює нулю, потік переходить у стан очікування або генерує виняток `io.github.resilience4j.bulkhead.BulkheadFullException`.

2. **`maxWaitDuration` (Duration, за замовчуванням 0):**
   Максимальний проміжок часу, протягом якого викликаючий потік може бути заблокований на методі `tryAcquirePermission()` в очікуванні звільнення слота іншим потоком. Значення `0` реалізує політику негайного відхилення (англ. *fail-fast*), що є обов'язковим для неблокуючих реактивних конвеєрів WebFlux / Project Reactor.

3. **`writableStackTraceEnabled` (bool, за замовчуванням true):**
   При високому навантаженні генерація повного стек-трейсу для тисяч винятків `BulkheadFullException` на секунду створює відчутні накладні витрати на процесор і пам'ять. Вимкнення цього прапорця генерує «легкий» виняток без заповнення трасування стека, зменшуючи затримку обробки відмов на порядок.

4. **`coreThreadPoolSize` та `maxThreadPoolSize` (int, за замовчуванням CPU cores):**
   Керують внутрішнім пулом потоків `ThreadPoolExecutor`. Дозволяють виділити фіксовану кількість ядер процесора виключно для фонових або важких завдань (наприклад, формування PDF-звітів), унеможливлюючи захоплення робочих потоків вебсервера.

5. **`queueCapacity` (int, за замовчуванням 100):**
   Місткість внутрішньої черги `ArrayBlockingQueue`. Переповнення черги призводить до негайного виклику зареєстрованого обробника відхилення (англ. *rejection handler*).

## 3. Специфікація метрик та телеметрії (Prometheus / OpenTelemetry)

Для безперервного спостереження за станом перебірок у виробничому середовищі експортуються стандартизовані метрики.

### Метрики Envoy Proxy

- `envoy_cluster_circuit_breakers_default_cx_open` (Gauge): приймає значення `1`, якщо досягнуто ліміт відкритих TCP-з'єднань `max_connections`, і `0` у звичайному стані.
- `envoy_cluster_circuit_breakers_default_rq_pending_open` (Gauge): приймає значення `1`, якщо черга очікування пулу `max_pending_requests` заповнена.
- `envoy_cluster_circuit_breakers_default_rq_open` (Gauge): приймає значення `1`, якщо вичерпано ліміт активних HTTP/2 запитів `max_requests`.
- `envoy_cluster_upstream_rq_pending_overflow` (Counter): сумарна кількість запитів, відхилених через переповнення черги очікування.

### Метрики Resilience4j

- `resilience4j_bulkhead_available_concurrent_calls{name="paymentService"}` (Gauge): поточна кількість вільних дозволів у семафорі.
- `resilience4j_bulkhead_max_allowed_concurrent_calls{name="paymentService"}` (Gauge): встановлений конфігураційний ліміт перебірки.
- `resilience4j_bulkhead_calls_total{name="paymentService", kind="permitted"}` (Counter): кількість успішно пропущених викликів.
- `resilience4j_bulkhead_calls_total{name="paymentService", kind="rejected"}` (Counter): кількість запитів, відхилених через брак слотів.

### Приклад запиту Prometheus для алертингу

```promql
# Відсоток утилізації перебірки за останні 5 хвилин
(1 - (resilience4j_bulkhead_available_concurrent_calls / resilience4j_bulkhead_max_allowed_concurrent_calls)) * 100 > 85

# Швидкість відхилення запитів перебіркою (RPS)
rate(resilience4j_bulkhead_calls_total{kind="rejected"}[1m]) > 10
```

## 4. Стандартні коди помилок та заголовки клієнтського протоколу

У разі спрацьовування перебірки сервіс зобов'язаний повернути клієнту стандартизований HTTP-код із відповідними службовими заголовками:

1. **`429 Too Many Requests`:**
   Застосовується, якщо перебірка налаштована на рівні облікового запису користувача, ідентифікатора орендаря (tenant) або клієнтського токена. Вказує, що конкретний клієнт вичерпав свій персональний ліміт паралельних операцій.

2. **`503 Service Unavailable`:**
   Застосовується, якщо вичерпано внутрішній пул з'єднань або потоків до конкретного підсервісу чи бази даних. Сигналізує шлюзам і балансувальникам про тимчасове локальне перевантаження інфраструктури.

### Обов'язкові заголовки відповіді:
- `Retry-After: <seconds>` — рекомендує клієнту інтервал очікування перед повторенням запиту (наприклад, `Retry-After: 2`).
- `X-RateLimit-Bulkhead-Limit: <number>` — загальний розмір відсіку перебірки.
- `X-RateLimit-Bulkhead-Remaining: 0` — індикація нульового залишку дозволів.
- `X-RateLimit-Bulkhead-Reset: <timestamp>` — орієнтовний час вивільнення заблокованих слотів.
