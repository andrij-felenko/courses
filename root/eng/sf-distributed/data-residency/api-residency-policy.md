# 📋 Специфікація політик резидентності та розміщення даних

Специфікація формалізує декларативний контракт визначення правил розміщення даних, класифікації полів, обмежень консенсусних кворумів та транскордонних шлюзів у гео-розподілених системах. Вона визначає точні правила взаємодії між прикладними мікросервісами, проксі-маршрутизаторами, криптографічними сховищами та вузлами баз даних для гарантованого дотримання суверенних юрисдикцій.

---

## Призначення та архітектурна роль контракту

У гео-розподіленому кластері прикладний код не повинен самостійно приймати рішення про вибір фізичного сервера чи IP-адреси дата-центра для виконання SQL-запитів. Ручна маршрутизація неминуче призводить до людських помилок, випадкових витоків чутливих даних через кордон та неможливості централізованого аудиту. 

Декларативна специфікація політики резидентності виступає єдиним джерелом правди для всієї розподіленої платформи. Вона завантажується у захищену площину управління (Control Plane), транслюється у бінарні таблиці правил у пам'яті шлюзів (Data Plane) та примусово валідує кожну транзакцію на трьох рівнях:
1. **Рівень вхідного трафіку (Ingress Routing):** Перевірка прав клієнта та скеровування HTTP/gRPC виклику до суверенного дата-центру відповідного регіону.
2. **Рівень обробки даних (Application & Database Plane):** Розрізання рядків таблиць, закріплення партицій за географічними шардами та обмеження консенсусних груп Raft лише вузлами в межах юрисдикції.
3. **Рівень вихідного трафіку та аналітики (Egress & Analytics Plane):** Примусова токенізація прямих ідентифікаторів перед будь-якою транскордонною передачею подій чи звітів.

## 1. Схема декларативної конфігурації

Політика резидентності описується у форматі декларативного маніфесту (YAML або JSON) і підписується криптографічним ключем офіцера безпеки або автоматизованого конвеєра CI/CD.

```yaml
version: "residency.v1"
metadata:
  policy_id: "eu-banking-gdpr-strict"
  description: "Політика розміщення банківських даних клієнтів у межах Європейської Економічної Зони"
  last_updated: "2026-08-20T00:00:00Z"
  enforcement_mode: "BLOCKING"

jurisdictions:
  - id: "EU_EEA"
    name: "European Economic Area"
    regulations: ["GDPR", "BDSG", "FADP"]
    allowed_regions: ["eu-central-1", "eu-west-1", "eu-west-3"]
    hsm_cluster: "hsm-frankfurt-fips140"
    cross_border_egress: "FORBIDDEN"

  - id: "US_FEDERAL"
    name: "United States (CCPA/HIPAA)"
    regulations: ["CCPA", "HIPAA", "SOC2"]
    allowed_regions: ["us-east-1", "us-east-2", "us-west-2"]
    hsm_cluster: "hsm-virginia-kms"
    cross_border_egress: "PERMITTED_PSEUDONYMIZED"

table_placement_policies:
  - table_name: "customers"
    strategy: "ROW_LEVEL_GEO_PARTITIONED"
    partition_column: "jurisdiction_code"
    rules:
      - match_value: "EU_EEA"
        target_locality: "region=eu-central-1:region=eu-west-1:region=eu-west-3"
        raft_quorum_zone: "EU_EEA_STRICT"
        encryption_key_id: "kms-eu-customer-master-v1"
      - match_value: "US_FEDERAL"
        target_locality: "region=us-east-1:region=us-east-2:region=us-west-2"
        raft_quorum_zone: "US_FEDERAL_STRICT"
        encryption_key_id: "kms-us-customer-master-v1"

column_classifications:
  - table_name: "customers"
    columns:
      - name: "full_name"
        classification: "PII_RESTRICTED"
        tokenization_vault: "vault.eu.internal:8200"
        masking_strategy: "DET_TOKEN_UUID"
      - name: "tax_identifier"
        classification: "PII_RESTRICTED"
        tokenization_vault: "vault.eu.internal:8200"
        masking_strategy: "RAND_TOKEN_STRING"
      - name: "account_balance"
        classification: "FINANCIAL_LOCAL_ONLY"
        exportable_to_analytics: false
      - name: "created_at"
        classification: "PUBLIC_METRIC"
        exportable_to_analytics: true
```

## 2. Секція `jurisdictions`: Визначення суверенних юрисдикцій

Цей блок маніфесту встановлює географічні та юридичні межі для кожної правової зони, що підтримується платформою. Він зв'язує абстрактні регуляторні вимоги із конкретною хмарною та мережевою топологією.

Кожна юрисдикція містить такі параметри:

* `id` — унікальний текстовий ідентифікатор юрисдикції (наприклад, `EU_EEA` для країн Європейської Економічної Зони, `US_FEDERAL` для США, `CH_CONF` для Швейцарії). Цей ідентифікатор використовується як ключ при маршрутизації та шардуванні.
* `name` — офіційна людиночитана назва правової зони.
* `regulations` — масив регуляторних актів і стандартів комплаєнсу, які регулюють обробку даних у цій зоні (наприклад, `GDPR`, `BDSG`, `HIPAA`, `PCI-DSS`).
* `allowed_regions` — строгий білий список фізичних дата-центрів, зон доступності або хмарних регіонів. Розміщення будь-якого байта даних за межами цього списку вважається критичним порушенням безпеки.
* `hsm_cluster` — мережевий дескриптор локального кластера апаратних модулів безпеки (Hardware Security Module). Використовується для генерації та зберігання майстер-ключів шифрування, які ніколи не експортуються за межі регіону.
* `cross_border_egress` — фундаментальний режим виходу даних за межі юрисдикції. Може набувати значень:
  * `FORBIDDEN` — повна заборона будь-якої передачі даних за межі вказаних регіонів (навіть у зашифрованому вигляді);
  * `PERMITTED_PSEUDONYMIZED` — дозволено експорт подій за умови, що всі поля класу персональних даних замінені на незворотні криптографічні токени;
  * `UNRESTRICTED` — вільний транскордонний обмін (застосовується виключно для публічних метаданих).

## 3. Секція `table_placement_policies`: Стратегії розміщення таблиць

Секція визначає поведінку розподіленої СКБД щодо кожної сутності бізнес-домену. Система підтримує кілька взаємовиключних стратегій розміщення даних:

```
+-----------------------------+-------------------------------------------------------------+
| Стратегія (strategy)        | Фізична поведінка в кластері баз даних                      |
+-----------------------------+-------------------------------------------------------------+
| ROW_LEVEL_GEO_PARTITIONED   | Рядки таблиці динамічно розрізаються за значенням стовпчика |
|                             | partition_column і закріплюються за локальним шардом.       |
| GLOBAL_READ_EVERYWHERE      | Таблиця повністю реплікується на всі вузли світу.           |
|                             | (Заборонено для PII; дозволено для довідників валют/країн).|
| REGIONAL_PINNED             | Уся таблиця цілком існує лише в одному вказаному регіоні.   |
| DUAL_SOVEREIGN_MIRROR       | Таблиця реплікується виключно між двома юрисдикціями        |
|                             | з синхронним шлюзом токенізації.                            |
+-----------------------------+-------------------------------------------------------------+
```

### Механізм локалізації консенсусних груп Raft

При використанні стратегії `ROW_LEVEL_GEO_PARTITIONED` база даних формує незалежні консенсусні групи для кожного географічного діапазону. Параметр `raft_quorum_zone` накладає суворі обмеження на склад реплік:

1. **Голосуючі репліки (Voting Replicas):** Усі вузли, які беруть участь у виборах лідера та підтвердженні записів у журнал попереджувального запису (WAL), зобов'язані знаходитися у списку `allowed_regions` відповідної юрисдикції. Завдяки цьому жоден транскордонний збій мережі чи затримка на трансатлантичному кабелі не здатні зупинити локальні операції запису.
2. **Репліки-спостерігачі (Non-Voting Observers / Learners):** Вузли у віддалених регіонах, які асинхронно отримують потік змін виключно після проходження фільтра десенсибілізації (вилучення персональних даних). Вони не беруть участі у кворумі та не можуть стати лідерами для європейських партицій.

## 4. Секція `column_classifications`: Класифікація стовпчиків та маскування

Цей розділ специфікації визначає детальні правила гранулярної обробки кожного окремого поля реляційної таблиці чи документа NoSQL.

### Категорії чутливості даних

* **`PII_RESTRICTED` (Персональні дані):** Будь-яка інформація, що дозволяє прямо чи опосередковано ідентифікувати фізичну особу (прізвище, ім'я, адреса електронної пошти, номер телефону, IP-адреса, паспортні дані, біометрія). Такі поля підлягають фізичному зберіганню виключно в локальному юрисдикційному шарді. Експорт за межі юрисдикції можливий лише за умови обов'язкової заміни на криптографічний токен.
* **`FINANCIAL_LOCAL_ONLY` (Суворо регульовані фінансові дані):** Номери банківських рахунків, баланси, дані платіжних карток стандарту PCI DSS. Заборонено передавати за межі регіонального контуру в будь-якому вигляді (навіть у вигляді токенів).
* **`TELEMETRY_ANONYMIZED` (Діагностичні події):** Часові мітки, тривалість виконання операцій, коди помилок. Дозволено вільний експорт у глобальні системи моніторингу за умови попереднього вилучення ідентифікаторів користувача.
* **`PUBLIC_METRIC` (Загальні агрегати):** Числові лічильники, загальні суми продажів за категоріями. Вільний транскордонний рух без обмежень.

### Стратегії токенізації та псевдонімізації

Для полів класу `PII_RESTRICTED` специфікація вимагає зазначення точного алгоритму трансформації:

* `DET_TOKEN_UUID` (Детермінований токен): Алгоритм генерує постійний сурогатний ідентифікатор для однакового вхідного значення (наприклад, через HMAC-SHA256 із локальним ключем). Це дозволяє центральній аналітичній системі виконувати операції об'єднання (`JOIN`) та когортного аналізу без доступу до реального імені клієнта.
* `RAND_TOKEN_STRING` (Випадковий токен): Кожен запис отримує випадковий унікальний рядок. Зв'язок між токеном і початковим значенням зберігається у захищеному сховищі Token Vault, а доступ до зворотного перетворення надається лише авторизованому персоналу за суворим аудитом.
* `DIFFERENTIAL_PRIVACY_NOISE` (Диференційна приватність): До числових результатів додається випадковий шум розподілу Лапласа для запобігання атакам відновлення ідентичності при аналізі малих груп.

## 5. Специфікація кодів помилок та поведінка відмови

Коли запит порушує конфігурацію політики резидентності, маршрутизатор або ядро бази даних негайно перериває операцію та формує структуровану відповідь про помилку.

| Код помилки | HTTP статус | Причина виникнення та наслідки |
| :--- | :--- | :--- |
| `ERR_JURISDICTION_MISMATCH` | `403 Forbidden` | Спроба записати дані резидента ЄС у шард іншої країни. Транзакцію скасовано, стан кластера не змінено. |
| `ERR_CROSS_BORDER_PII_LEAK` | `422 Unprocessable` | Спроба експортувати поле з класом `PII_RESTRICTED` без токенізації. Запит заблоковано на рівні Egress-шлюзу. |
| `ERR_CONSENSUS_LOCALITY_BREACH` | `500 Internal` | Конфігурація Raft-групи містить голосуючі вузли поза межами юрисдикції. Запис заблоковано для уникнення витоку WAL. |
| `ERR_VAULT_DECRYPT_FORBIDDEN` | `401 Unauthorized` | Запит на де-токенізацію надійшов від неавторизованого сервісу або з-за меж суверенного анклаву. |
| `ERR_ANALYTICS_K_ANONYMITY_VIOLATION` | `400 Bad Request` | Федеративний аналітичний запит повернув вибірку розміром менше ніж `k = 5` осіб, що загрожує деанонімізацією. |

## 6. Приклад повного контракту обміну повідомленнями

Нижче наведено структуру вхідного запиту на створення банківського клієнта, що надходить до шлюзу API:

```json
{
  "request_id": "req_88fbc910-1a22-4d51",
  "client_jurisdiction": "EU_EEA",
  "tenant_id": "tenant_deutschland_gmbh",
  "payload": {
    "jurisdiction_code": "EU_EEA",
    "user_id": "usr_de_49102",
    "full_name": "Maximilian Weber",
    "email": "m.weber@example.de",
    "iban": "DE89370400440532013000"
  },
  "placement_contract": {
    "enforce_strict_locality": true,
    "require_hsm_encryption": true,
    "reject_cross_border_fallback": true
  }
}
```

Після валідації політики, збереження сирих даних у локальному шарді та генерації знеособленого експортного пакета шлюз повертає квитанцію фіксації:

```json
{
  "status": "COMMITTED_LOCAL",
  "applied_jurisdiction": "EU_EEA",
  "assigned_shard": "shard_eu_central_frankfurt_01",
  "raft_commit_index": 1048576,
  "tokenized_export_payload": {
    "jurisdiction_code": "EU_EEA",
    "user_id": "usr_de_49102",
    "full_name_token": "tok_9f8a41c2-881a-4e2b",
    "email_token": "tok_3b7c11f0-99c1-482a",
    "iban_token": "tok_a712e091-bb21-4190"
  },
  "audit_trail": {
    "hsm_key_id": "kms-eu-customer-master-v1",
    "vault_transaction_id": "vtx_77192a00"
  }
}
```

Контракт гарантує, що прикладні клієнти за межами суверенного анклаву оперують виключно токенами `tok_*`, повністю унеможливлюючи транскордонний витік персональної інформації.
