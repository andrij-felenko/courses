# 📋 Специфікація API: розподілений колектор знімків (Snapshot Engine API)

Розподілений рушій знімків надає програмний інтерфейс для ініціалізації контрольних точок (англ. *checkpoints*), координації маркерів між асинхронними каналами зв'язку та агрегації глобального стану розподіленої системи. Специфікація стандартизує структури даних, життєвий цикл епохи знімка, конфігураційні параметри, правила керування пам'яттю транзитних каналів, бінарний формат експорту, вимоги до потокобезпечності та протоколи обробки виняткових ситуацій.

## Архітектура та життєвий цикл знімка

Рушій знімків функціонує як проміжний шар між транспортним рівнем мережі (TCP/IP, UDP або RDMA) та прикладною бізнес-логікою вузла. Його робота складається з п'яти послідовних фаз:

1. **Фаза простою (Idle Phase):** Вузол обробляє звичайні прикладні повідомлення без накладних витрат на моніторинг каналів. Лічильники маркерів перебувають у початковому стані.
2. **Фаза ініціації або активації (Trigger/Activation):** За локальною подією таймера, сигналом зовнішнього координатора або після отримання першого вхідного маркера вузол викликає функцію збереження локального стану пам'яті (`on_save_local_state`) та негайно емітує маркер у всі вихідні канали зв'язку.
3. **Фаза запису транзитних каналів (Channel Recording):** Вузол продовжує виконання бізнес-логіки в штатному режимі. Усі звичайні прикладні повідомлення, які прибувають із каналів, де маркер ще не був отриманий, дублюються у внутрішній транзитний буфер каналу.
4. **Фаза змикання бар'єрів (Barrier Alignment):** Коли маркер прибуває з певного вхідного каналу, запис для нього зупиняється. Вузол очікує прибуття маркерів від усіх зареєстрованих сусідів.
5. **Фаза публікації маніфесту (Commit & Export):** Після отримання маркерів від усіх вхідних каналів вузол формує цілісний маніфест локального знімка та передає його центральному координатору або записує в асинхронне розподілене сховище (Amazon S3, Ceph або HDFS).

## Структури даних та моделі станів

Нижче наведено структури даних та переліки станів мовами C та C++.

### Перелік станів знімка вузла (`SnapshotState`)

:::tabs
```c
typedef enum {
    SNAPSHOT_IDLE,          /* Вузол не бере участі в активній епосі знімка */
    SNAPSHOT_RECORDING,     /* Вузол зафіксував стан і записує транзитні канали */
    SNAPSHOT_COMPLETED,     /* Усі маркери отримано, стан вузла повністю зібрано */
    SNAPSHOT_FAILED         /* Збій через таймаут або розрив мережевого з'єднання */
} SnapshotState;
```
```cpp
enum class SnapshotState : uint8_t {
    Idle,          // Вузол не бере участі в активній епосі знімка
    Recording,     // Вузол зафіксував стан і записує транзитні канали
    Completed,     // Усі маркери отримано, стан вузла повністю зібрано
    Failed         // Збій через таймаут або розрив мережевого з'єднання
};
```
:::

### Дескриптор повідомлення маркера (`SnapshotMarker`)

Повідомлення маркера є службовим мережевим пакетом, який транспортується каналами разом із даними:

| Поле | Тип | Опис призначення |
|---|---|---|
| `snapshot_id` | `uint64_t` | Глобально унікальний монотонний ідентифікатор епохи знімка. |
| `initiator_node_id` | `uint32_t` | Числовий ідентифікатор вузла, що ініціював знімок. |
| `source_node_id` | `uint32_t` | Ідентифікатор вузла-відправника конкретного примірника маркера. |
| `logical_epoch` | `uint64_t` | Логічний штамп часу Лампорта на момент генерації маркера. |
| `flags` | `uint16_t` | Бітові прапорці (наприклад, терміновий знімок або примусовий скид буферів). |

:::tabs
```c
typedef struct {
    uint64_t snapshot_id;
    uint32_t initiator_node_id;
    uint32_t source_node_id;
    uint64_t logical_epoch;
    uint16_t flags;
} SnapshotMarker;
```
```cpp
struct SnapshotMarker {
    uint64_t snapshot_id{0};
    uint32_t initiator_node_id{0};
    uint32_t source_node_id{0};
    uint64_t logical_epoch{0};
    uint16_t flags{0};
};
```
:::

### Дескриптор стану каналу зв'язку (`ChannelSnapshot`)

typedef struct {

struct ChannelSnapshot {
    uint32_t source_node_id{0};

## Конфігураційні параметри рушія (`SnapshotConfig`)

Перед запуском рушія вузол конфігурує параметри буферизації, ліміти часу та політики збереження:

| Параметр | Тип | За замовчуванням | Призначення та вплив |
|---|---|---|---|
| `timeout_ms` | `uint32_t` | `30000` (30 с) | Максимальний час очікування маркерів з усіх каналів до анулювання знімка. |
| `max_channel_buffer_bytes` | `size_t` | `67108864` (64 МБ) | Ліміт пам'яті для буферизації повідомлень у польоті на один канал. |
| `enable_compression` | `bool` | `true` | Стиснення транзитних повідомлень алгоритмом Zstandard перед експортом. |
| `spill_to_disk` | `bool` | `true` | Дозвіл скидати буфер повідомлень на локальний NVMe у разі переповнення RAM. |

:::tabs
```c
typedef struct {
    uint32_t timeout_ms;
    size_t max_channel_buffer_bytes;
    bool enable_compression;
    bool spill_to_disk;
} SnapshotConfig;
```
```cpp
struct SnapshotConfig {
    uint32_t timeout_ms{30000};
    std::size_t max_channel_buffer_bytes{64 * 1024 * 1024};
    bool enable_compression{true};
    bool spill_to_disk{true};
};
```
:::

## Функціональний інтерфейс рушія

### 1. Ініціалізація рушія (`snapshot_engine_init`)

Функція реєструє топологію мережевих з'єднань, виділяє буфери для запису повідомлень та ініціалізує таймери очікування.

:::tabs
```c
int snapshot_engine_init(
    SnapshotEngine* engine,
    uint32_t local_node_id,
    const uint32_t* incoming_peers,
    size_t num_incoming,
    const uint32_t* outgoing_peers,
    size_t num_outgoing,
    const SnapshotConfig* config
);
```
```cpp
class SnapshotEngine {
public:
    int init(
        uint32_t local_node_id,
        std::span<const uint32_t> incoming_peers,
        std::span<const uint32_t> outgoing_peers,
        const SnapshotConfig& config
    );
};
```
:::

**Параметри:**
- `local_node_id` — унікальний числовий ідентифікатор поточного сервера в топології.
- `incoming_peers` — перелік ідентифікаторів вузлів, які мають вхідні канали до цього процесу.
- `outgoing_peers` — перелік ідентифікаторів вузлів, куди процес надсилає вихідні повідомлення.
- `config` — структура налаштувань, що задає максимальний таймаут очікування маркерів (`timeout_ms`) та ліміт розміру буфера транзитних повідомлень (`max_channel_buffer_bytes`).

### 2. Ініціація нового знімка (`snapshot_trigger`)

Запускає процедуру створення глобальної контрольної точки за ініціативою поточного вузла.

:::tabs
```c
int snapshot_trigger(
    SnapshotEngine* engine,
    uint64_t* out_snapshot_id
);
```
```cpp
class SnapshotEngine {
public:
    std::expected<uint64_t, int> trigger();
};
```
:::

**Поведінка:**
1. Генерує новий монотонний ідентифікатор `snapshot_id`.
2. Викликає зареєстрований колбек для збереження локального стану процесу.
3. Формує повідомлення `SnapshotMarker` та надсилає його в усі вихідні канали перед будь-якими наступними прикладними даними.
4. Переводить усі вхідні канали в стан активного запису `SNAPSHOT_RECORDING`.

### 3. Обробка маркера (`snapshot_on_receive_marker`)

Викликається транспортним рівнем мережі щоразу, коли з вхідного каналу надходить повідомлення маркера.

:::tabs
```c
int snapshot_on_receive_marker(
    SnapshotEngine* engine,
    uint32_t from_node_id,
    const SnapshotMarker* marker
);
```
```cpp
class SnapshotEngine {
public:
    int on_receive_marker(
        uint32_t from_node_id,
        const SnapshotMarker& marker
    );
};
```
:::

**Внутрішня логіка:**
- **Якщо маркер отримано вперше в цій епосі:**
  1. Вузол негайно зберігає свій локальний стан оперативної пам'яті.
  2. Вхідний канал `from_node_id` позначається як закритий із нульовим транзитним станом (`0` повідомлень).
  3. Маркер негайно ретранслюється в усі зареєстровані вихідні канали.
  4. Вмикається запис прикладних повідомлень для решти вхідних каналів.
- **Якщо маркер отримано повторно з іншого каналу:**
  1. Запис для каналу `from_node_id` зупиняється.
  2. Накопичений буфер повідомлень фіксується як остаточний транзитний стан каналу.
  3. Якщо всі вхідні канали надіслали маркери, стан вузла переходить у `SNAPSHOT_COMPLETED`.

### 4. Перехоплення та фільтрація даних (`snapshot_on_receive_data`)

:::tabs
```c
void snapshot_on_receive_data(
    SnapshotEngine* engine,
    uint32_t from_node_id,
    const void* data,
    size_t length
);
```
```cpp
class SnapshotEngine {
public:
    void on_receive_data(
        uint32_t from_node_id,
        std::span<const uint8_t> data
    );
};
```
:::

Якщо для каналу `from_node_id` наразі активний режим запису, копія корисного навантаження додається до буфера знімка каналу, після чого повідомлення негайно передається прикладній програмі без затримок.

## Модель багатопотоковості та потокобезпечність

У багатоядерних серверах прикладні обробники та мережевий транспорт функціонують у різних потоках виконання (англ. *worker threads*). Рушій підтримує дві моделі потокобезпечності:

- **Модель прив'язки до потоку (Thread-Affinity / Run-to-Completion):** Кожен мережевий сокет закріплений за окремим ядром процесора через черги `epoll` / `io_uring`. Рушій знімків не використовує блокуючих м'ютексів (англ. *lock-free*), а стан запису каналу оновлюється виключно потоком-власником сокета.
- **Модель спільного стану з м'ютексами (Mutex-Guarded State):** Для багатопотокових обробників спільний стан вузла захищається оптимістичними блокуваннями читання-запису (англ. *Reader-Writer Spinlocks*), мінімізуючи затримки під час штатної передачі пакетів без знімка.

## Керування пам'яттю, контрольні суми та бінарний формат

Під час високого навантаження на систему обсяг транзитних повідомлень, що надходять між фіксацією локального стану та отриманням маркера, може сягати значних розмірів. Рушій реалізує багаторівневу стратегію захисту та збереження цілісності:

1. **Буфер у RAM:** Повідомлення накопичуються у кільцевому буфері оперативної пам'яті до досягнення порога `max_channel_buffer_bytes`.
2. **Скидання на NVMe-диск (Disk Spilling):** Якщо пам'ять вичерпано, рушій відкриває тимчасовий асинхронний файл на локальному швидкому накопичувачі та скидає транзитний трафік через прямий ввід-вивід `O_DIRECT` / `io_uring`.
3. **Зворотний тиск (Backpressure):** Якщо дискова підсистема не встигає зберігати потік даних, рушій тимчасово сповільнює вичитування пакетів із сокета TCP, змушуючи відправника зменшити вікно передачі.
4. **Контрольні суми та валідація:** Кожен блок локального стану та стан каналів підписується 64-бітною контрольною сумою XXH64 / CRC32C. Під час відновлення знімка рушій перевіряє цілісність даних перед відновленням черг.

## Коди помилок та протокол анулювання знімка

Якщо під час виконання знімка стається аварія мережі або зависання одного з вузлів, рушій застосовує протокол анулювання епохи (англ. *snapshot abort*), повертаючи відповідний від'ємний код помилки:

| Код помилки | Символічна назва | Причина виникнення та рекомендація |
|---|---|---|
| `-101` | `ERR_SNAPSHOT_TIMEOUT` | Маркери не надійшли з усіх вхідних каналів протягом ліміту `timeout_ms`. Епоха анулюється, буфери звільняються. |
| `-102` | `ERR_FIFO_VIOLATION` | Отримано маркер із застарілим номером епохи або порушено черговість доставки пакетів у каналі. |
| `-103` | `ERR_CHANNEL_OVERFLOW` | Перевищено ліміт пам'яті та дискового простору на збереження транзитних повідомлень. |
| `-104` | `ERR_ALREADY_IN_PROGRESS` | Спроба ініціювати новий знімок до завершення або повного скидання попереднього. |
| `-105` | `ERR_STORAGE_IO` | Помилка запису маніфесту знімка у віддалене об'єктне сховище (AWS S3 / Ceph). |
| `-106` | `ERR_CHECKSUM_MISMATCH` | Невідповідність контрольної суми при зчитуванні транзитного буфера каналу. |
