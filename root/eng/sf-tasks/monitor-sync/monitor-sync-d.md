Сервер відеоспостереження обробляє вхідний потік кадрів високої роздільної здатності: мережевий потік захоплює байти з камери та записує їх у спільний буфер пам'яті, а чотири робочі потоки вилучають кадри з буфера для розпізнавання об'єктів нейромережею. Коли інтенсивність руху в кадрі падає, камера надсилає менше даних, і буфер швидко спорожнюється. Робочий потік звертається до спільного буфера, бере м'ютекс для захисту списку, бачить, що кількість елементів `count == 0`, і опиняється перед фундаментальним глухим кутом.

Якщо робочий потік застигне у простому очікуванні, не відпускаючи м'ютекс (`while (count == 0);`), мережевий потік ніколи не зможе захопити замок, щоб покласти новий кадр, — виникає безповоротний дедлок. Якщо потік відпускатиме м'ютекс і тут же намагатиметься захопити його знову в нескінченному циклі опитування (`while (count == 0) { unlock(); lock(); }`), він завантажить ядро процесора на 100%, викличе постійне скидання кеш-ліній на між'ядерній шині пам'яті та завадить іншим задачам отримати процесорний час. А якщо додати паузу через виклик `usleep(1000)`, система отримає неприпустимі затримки у передачі відеопотоку та все одно здійснюватиме марні пробудження, коли кадрів немає.

Програмі потрібен механізм, який дозволяє потоку **атомарно звільнити м'ютекс і перейти в стан глибокого сну за одну неподільну операцію**, а потім бути гарантовано розбудженим іншим потоком саме в ту мікросекунду, коли дані з'являться в буфері, причому повернутися з очікування потік зобов'язаний **знову утримуючи захоплений замок**.

Ця комбінація взаємного виключення та керованого засинання/пробудження потоків лежить в основі високорівневої моделі синхронізації, що отримала назву **монітора** (англ. *monitor*, від лат. *monitor* — той, хто наглядає, нагадує, застерігає, від *monere* — попереджати, радити).

## Анатомія монітора: структура та компоненти

Концепцію монітора розробили 1973–1974 років дослідники Пер Брінч Хансен та Тоні Хоар як структурований тип даних, що інкапсулює спільний змінюваний стан і надає методи для безпечної конкурентної роботи з ним.

Монітор об'єднує три невіддільні складові:
1. **Спільні дані**: внутрішній стан, захищений від прямого доступу ззовні (наприклад, масив елементів кільцевого буфера, лічильники, вказівники голови й хвоста).
2. **М'ютекс** (англ. *mutex*, скорочення від *mutual exclusion*, від лат. *mutuus* — взаємний, спільний та *excludere* — вимикати, відгороджувати): замок, що гарантує суворе взаємне виключення. У будь-який момент часу всередині монітора може виконуватися **щонайбільше один потік**. Усі інші потоки, які намагаються викликати методи монітора, блокуються у зовнішній вхідній черзі замка.
3. **Умовні змінні** (англ. *condition variable*, від лат. *condicio* — умова, домовленість, угода): спеціальні координаційні примітиви, що являють собою внутрішні черги потоків, які тимчасово призупинили роботу, оскільки певний **предикат** (англ. *predicate*, від лат. *praedicatum* — заявлене, стверджуване, від *praedicare* — проголошувати) стану для них наразі є хибним.

![Архітектура монітора: вхідна черга до м'ютексу, критична секція зі спільним станом та внутрішні черги очікування умовних змінних](/root/eng/sf-tasks/monitor-sync/img/monitor-architecture.svg)
*Архітектура монітора: потік захоплює м'ютекс на вході, працює зі спільним станом, а за потреби очікування атомарно відпускає замок і переходить до черги умовної змінної.*

Умовна змінна не є звичайною змінною пам'яті: вона не містить чисел, лічильників чи булевих прапорців. Вона не має значення, яке можна прочитати чи записати. Умовна змінна — це виключно **іменована черга очікування**, прив'язана до конкретного м'ютексу. Увесь стан системи (кількість елементів, прапорець закриття черги, готовність буфера) зберігається у звичайних змінних програми, а умовна змінна служить лише засобом сповіщення про зміну цього стану.

> 🔧 **Навіщо це.** Без умовних змінних синхронізація зводиться або до блокуючих спинлоків із перевантаженням процесора, або до семафорів Дейкстри. Проте семафори поєднують у собі лічильник і чергу, що робить їх використання схильним до помилок: забутий виклик `V()` або подвійний `P()` ламає всю систему. Монітор відокремлює захист даних (м'ютекс) від логіки очікування стану (умовні змінні), гарантуючи цілісність структури даних компілятором або архітектурним шаблоном.

Як розвивалася ця концепція від перших семафорів Дейкстри до праць Хоара та впровадження у промислові системи розкриває [історія зародження моніторів та семантики очікування](root:sf-tasks/monitor-sync/hist-hoare-mesa.md).

## Механіка умовних змінних: wait, signal та broadcast

Робота з умовною змінною спирається на три базові операції, що надаються системними бібліотеками (зокрема POSIX Threads та стандартом C++):

```
Фундаментальні операції умовної змінної:
1. wait(cond, mutex)      → атомарно відпустити mutex і заснути в черзі cond;
                            після сигналу знову захопити mutex перед поверненням.
2. signal(cond)           → розбудити щонайменше один потік із черги cond.
3. broadcast(cond)        → розбудити всі потоки, що чекають у черзі cond.
```

### 1. Операція очікування: `wait`

Операція `wait` — найскладніша і найважливіша в усій підсистемі синхронізації. Вона вимагає обов'язкового дотримання контракту: потік зобов'язаний утримувати м'ютекс перед викликом `wait`.

Виклик `pthread_cond_wait(&cond, &mutex)` або `cv.wait(lock)` у C++ виконує чотири кроки строго за протоколом:
1. **Реєстрація в черзі**: дескриптор поточного потоку додається до черги очікування умовної змінної `cond`.
2. **Атомарне відпускання замка**: м'ютекс `mutex` звільняється одночасно з переведенням потоку в стан очікування. Атомарність тут критична: між відпусканням замка і фактичним засинанням не існує часового зазору, в який інший потік міг би вклинитися, надіслати сигнал і втратити його.
3. **Блокування в ядрі**: потік виключається планувальником із черги готових до виконання задач (у Linux переходить у стан `TASK_UNINTERRUPTIBLE` або `TASK_INTERRUPTIBLE` через системний виклик `futex`) і не споживає жодного такту процесора.
4. **Пробудження та повторне взяття замка**: коли інший потік надсилає сигнал, заблокований потік прокидається, але **не повертається негайно з функції `wait`**. Він переходить у чергу очікування м'ютексу `mutex` і знову бореться за право захопити замок. Лише тоді, коли м'ютекс успішно захоплено знову, керування повертається в точку після виклику `wait`.

![Життєвий цикл виклику wait: атомарне відпускання замка, сон у ядрі, пробудження за сигналом та повторне захоплення м'ютексу перед виходом](/root/eng/sf-tasks/monitor-sync/img/cond-wait-lifecycle.svg)
*Фази виконання wait: засинання з атомарним звільненням замка, перебування в черзі очікування та обов'язкове повторне взяття м'ютексу після отримання сигналу.*

Звідси випливає фундаментальна гарантія: **будь-який код після повернення з `wait` завжди виконується під захистом м'ютексу**. Потік не може опинитися всередині монітора без володіння замком.

### 2. Операція точкового сповіщення: `signal` (notify_one)

Операція **сигналу** (англ. *signal*, від лат. *signalis*, від *signum* — знак, позначка) або `notify_one()` перевіряє чергу умовної змінної:
- Якщо на змінній чекає один або кілька потоків, рівно один із них обирається планувальником (зазвичай за принципом FIFO або за пріоритетом), вилучається з черги умовної змінної та переводиться в чергу змагання за м'ютекс.
- Якщо в черзі немає жодного сплячого потоку, операція `signal` просто нічого не робить. Вона не запам'ятовує факт виклику на майбутнє: умовна змінна не має пам'яті (на відміну від семафора, який збільшив би внутрішній лічильник). Сигнал, надісланий у порожню чергу, безслідно розчиняється.

### 3. Операція широкомовного сповіщення: `broadcast` (notify_all)

Операція **трансляції** або **широкомовного сповіщення** (англ. *broadcast*, від давньоангл. *brad* — широкий та *casten* — кидати, розкидати) або `notify_all()` переводить **усі** заблоковані на цій умовній змінній потоки з черги сну в чергу очікування м'ютексу.

Усі розбуджені потоки починають по черзі захоплювати замок, виконувати свою роботу і передавати м'ютекс наступному розбудженому побратиму.

Повний перелік параметрів, кодів повернення функцій POSIX та методів C++ наведено у [довіднику інтерфейсу умовних змінних POSIX та C++](root:sf-tasks/monitor-sync/api-posix-cond.md).

## Семантика передачі керування: Хоар проти Mesa

Коли потік `A` викликає `signal(cond)`, у системі виникає дилема: умовний предикат щойно став істинним, і в черзі є розбуджений потік `B`. Але всередині монітора може працювати лише один потік. Хто саме має виконуватися в наступну мить?

Історично склалися дві принципово різні моделі розв'язання цього конфлікту:

```
Два світи моніторів:
1. Семантика Хоара (Signal-and-Wait):
   Потік A викликав signal() → негайно зупиняється й віддає замок потоку B.
   Потік B негайно виконується; предикат гарантовано істинний.
   У коді: if (!predicate) wait();

2. Семантика Mesa (Signal-and-Continue):
   Потік A викликав signal() → продовжує утримувати замок і працює далі.
   Потік B прокидається, але чекає звільнення замка потоком A.
   У коді: while (!predicate) wait();  [ОБОВ'ЯЗКОВО!]
```

![Порівняння семантики сигналізації: семантика Хоара з негайною передачею замка проти семантики Mesa із відкладеним змаганням за м'ютекс](/root/eng/sf-tasks/monitor-sync/img/hoare-vs-mesa.svg)
*У семантиці Хоара потік, що сигналізує, поступається замком негайно; у семантиці Mesa він продовжує роботу, тому розбуджений потік мусить перевіряти умову в циклі.*

### 1. Семантика Хоара (Signal-and-Wait)

У класичній теоретичній моделі Тоні Хоара (1974) передача керування є абсолютно жорсткою та атомарною:
1. Потік `A`, викликавши `signal`, миттєво віддає м'ютекс і призупиняє виконання.
2. Розбуджений потік `B` негайно захоплює м'ютекс і починає виконання безпосередньо з точки після `wait`.
3. Оскільки між надсиланням сигналу та виконанням потоку `B` жоден інший потік не може вклинитися в монітор, потік `B` застає стан системи в точності таким, яким його створив потік `A`.

За семантики Хоара розробнику було б достатньо написати звичайну умовну конструкцію:

:::tabs
```c
/* Допустимо ТІЛЬКИ в семантиці Хоара (1974) */
if (queue_is_empty()) {
    wait(&cond, &mutex);
}
/* Тут черга гарантовано не порожня, можна без перевірки брати елемент */
item = queue_pop();
```
```cpp
// У семантиці Хоара умовного оператора було б достатньо
if (queue.empty()) {
    cv.wait(lock);
}
auto item = queue.pop();
```
:::

Проте семантика Хоара вимагала обов'язкового негайного перемикання контексту процесора (*context switch*) під час кожного виклику `signal`, що на реальному залізі призводило до катастрофічної втрати продуктивності та конфліктувало з витісняльними планувальниками ОС.

### 2. Семантика Mesa (Signal-and-Continue)

1980 року інженери лабораторії Xerox PARC Батлер Лемпсон та Девід Ределл під час створення мови Mesa та ОС Pilot відмовилися від прямої передачі керування на користь схеми **Signal-and-Continue**:
1. Потік `A`, що викликав `signal`, **не зупиняється і не віддає замок**. Він спокійно продовжує виконувати свою критичну секцію до природного виходу та явного виклику `unlock`.
2. Потік `B` переводиться зі стану сну у звичайну чергу очікування м'ютексу.
3. Коли потік `A` зрештою відпускає м'ютекс, потік `B` змагається за замок на загальних підставах з іншими активними потоками.

Саме семантика Mesa стала стандартом для всіх сучасних мов та операційних систем: **POSIX Threads (C), C++11, Java, C#, Go, Rust, Python**.

Математичне обґрунтування інваріантів та трійок Хоара для обох моделей детально розібрано у [формальних інваріантах та математичній верифікації моніторів](root:sf-tasks/monitor-sync/math-monitor-safety.md).

## Чому Mesa вимагає циклу while: вікно перехоплення та хибні пробудження

Головним наслідком семантики Mesa є виникнення часового вікна між моментом відправки сигналу `signal()` потоком `A` та моментом, коли розбуджений потік `B` реально захопить м'ютекс і почне виконувати інструкції.

Розглянемо хрестоматійний сценарій аварії, якщо в семантиці Mesa необачно використати `if`:

```
Хронологія перехоплення ресурсу в семантиці Mesa:

1. Стан черги: count = 0.
2. Потік B (споживач): бере замок, бачить count == 0, викликає wait(), засинає.
3. Потік A (виробник): бере замок, кладе елемент (count = 1), викликає signal(),
   проте продовжує роботу і тримає замок ще 2 мілісекунди.
4. Потік C (інший споживач на сусідньому ядрі): звертається за замком.
5. Потік A відпускає замок.
6. Планувальник вирішує віддати замок потоку C, бо він уже гарячий на своєму ядрі!
7. Потік C захоплює замок, бачить count == 1, забирає елемент (count = 0), відпускає замок.
8. Лише тепер потік B нарешті виграє м'ютекс і виходить із wait().
9. Якщо потік B використав "if", він без перевірки звертається до порожньої черги:
   відбувається звернення за нульовим вказівником або читання сміття (Segmentation Fault)!
```

Оскільки потік `C` «викрав» ресурс у проміжку між сигналом і активацією `B`, потік `B` зобов'язаний після кожного пробудження **заново перевірити стан предикату**.

### Хибні пробудження (Spurious Wakeups)

Крім перехоплення стану третіми потоками, існує явище **хибних пробуджень** (англ. *spurious wakeup*, від лат. *spurius* — фальшивий, несправжній, підроблений).

Хибне пробудження — це ситуація, коли потік повертається з виклику `wait()`, хоча жоден інший потік не викликав `signal()` або `broadcast()`, а предикат узагалі не ставав істинним.

Фізичні причини виникнення хибних пробуджень у ядрах операційних систем:
1. **Переривання системних викликів сигналами ОС**: у Linux надходження POSIX-сигналу (наприклад, `SIGALRM` чи `SIGUSR1`) перериває блокуючий системний виклик `futex()`, змушуючи його повернути код помилки `EINTR`. Бібліотека `glibc` всередині `pthread_cond_wait` у відповідь знову бере м'ютекс і повертає керування користувацькому коду.
2. **Оптимізація Wait Morphing у ядрі**: для зменшення навантаження на планувальник ядро може масово переносити задачі між чергами футексів у багатопроцесорних системах.
3. **Апаратні перегони кеш-пам'яті**: на архітектурах із багатоядерними процесорами оптимізації атомарних інструкцій процесора у просторі користувача можуть іноді генерувати короткочасні сплески прапорців готовності.

Звідси формулюється **залізне правило багатопотокового програмування**:

:::tabs
```c
/* ЄДИНА КОРЕКТНА ФОРМА ОЧІКУВАННЯ УМОВНОЇ ЗМІННОЇ */
while (!condition_is_met()) {
    pthread_cond_wait(&cond, &mutex);
}
```
```cpp
// У C++ стандартний метод wait інкапсулює цикл перевірки
cv.wait(lock, [this] { return condition_is_met(); });
```
:::

У C++ стандартна бібліотека захищає розробника від цієї помилки, надаючи перевантаження методу `wait`, що приймає лямбда-предикат:
```cpp
cv.wait(lock, [this] { return !queue.empty(); });
```
Усередині ця функція розгортається у той самий цикл `while (!pred()) wait(lock);`.

## Проблема втрачених пробуджень (Lost Wakeups)

Іншою небезпечною пасткою є **втрачене пробудження** (англ. *lost wakeup*). Це стан системи, коли потік надіслав сповіщення, але жоден очікуючий потік його не отримав і заснув навічно, що призводить до повного зависання підсистеми.

Втрачене пробудження виникає у двох типових випадках:

### 1. Сигналізація без зміни або фіксації стану
Якщо розробник надсилає `signal()`, не змінивши булевий прапорець стану або викликавши `signal()` до того, як споживач увійшов у критичну секцію, сигнал губиться в порожнечі. Коли споживач згодом викликає `wait()`, він засинає назавжди, бо повторного сигналу ніхто не надішле.

### 2. Помилкове використання `signal` замість `broadcast`
Уявімо чергу, в якій одночасно заблоковані споживачі (чекають на дані) та виробники (чекають на вільне місце). Якщо всі вони чекають на **одній спільній** умовній змінній, і виробник додає елемент та викликає `signal()`, планувальник може помилково розбудити не споживача, а іншого виробника! Розбуджений виробник бачить, що місця немає, засинає назад, а дані так і залишаються лежати в черзі, бо жоден споживач не був розбуджений.

```
Критерії вибору між signal() та broadcast():

Використовуйте signal() (notify_one), якщо одночасно виконуються дві умови:
1. Однорідність: усі потоки в черзі CV очікують на ОДИНАКОВИЙ предикат стану.
2. Одиничний ресурс: зміна стану дозволяє зробити корисну роботу РІВНО ОДНОМУ потоку.

Використовуйте broadcast() (notify_all), якщо:
- Потоки очікують на різні умови (наприклад, читачі й письменники або запити різного розміру).
- Одне сповіщення створює ресурс для багатьох потоків (наприклад, додано пачку завдань).
- Надійшов сигнал завершення роботи (shutdown/terminate), який мають отримати всі потоки.
```

## Внутрішній устрій у ядрі Linux: механіка Futex

Щоб до кінця зрозуміти, як умовні змінні та м'ютекси перетворюються на команди процесора, простежимо шлях системних викликів у ядрі Linux.

Коли потік звертається до `pthread_cond_wait(&cond, &mutex)`, бібліотека `glibc` виконує такий алгоритм:

1. **Інкремент внутрішнього лічильника умовної змінної**: у просторі користувача оновлюється послідовний номер очікування (*sequence counter*).
2. **Звільнення м'ютексу**: викликається `pthread_mutex_unlock(mutex)`, що скидає 32-бітне значення замка у пам'яті. Якщо на м'ютексі були заблоковані інші задачі, робиться виклик `sys_futex(..., FUTEX_WAKE, 1)`.
3. **Засинання на умовній змінній**: потік викликає системний виклик:
```
sys_futex(&cond->__data.__futex, FUTEX_WAIT_PRIVATE, seq_val, NULL)
```
4. **Робота ядра Linux**:
   - Ядро знаходить відповідний хеш-кошик черг футексів `struct futex_hash_bucket` та захоплює його спінлок `hb->lock`.
   - Перевіряє, чи значення в пам'яті за адресою `&cond` усе ще дорівнює `seq_val`. Якщо значення змінилося (поки потік входив у ядро, інший потік уже встиг надіслати `signal`), системний виклик негайно повертає помилку `EWOULDBLOCK`, запобігаючи втраті сигналу!
   - Якщо значення не змінилося, дескриптор задачі потоку додається до черги очікування `futex_q`.
   - Поточний стан задачі переводиться у `TASK_INTERRUPTIBLE`.
   - Спінлок кошика відпускається, і ядро викликає диспетчер `schedule()`, який перемикає процесорне ядро на інший потік.

Коли інший потік виконує `pthread_cond_signal(&cond)`:
1. Збільшується лічильник послідовності `__futex`.
2. Викликається `sys_futex(&cond->__data.__futex, FUTEX_WAKE_PRIVATE, 1)`.
3. Ядро бере спінлок кошика, вилучає перший дескриптор `futex_q` зі списку і викликає функцію `wake_up_state(task, TASK_NORMAL)`, повертаючи задачу в чергу планувальника.
4. Прокинувшись у просторі користувача всередині `pthread_cond_wait`, потік відразу викликає `pthread_mutex_lock(mutex)`, щоб знову отримати монопольний доступ, перш ніж повернути керування користувацькій програмі.

## Оптимізація ядра: Requeuing футексів проти завалу натовпом

Коли викликається `pthread_cond_broadcast()`, виникає загроза так званого **завалу натовпом** (англ. *thundering herd*): якщо на змінній спало 64 потоки, ядро ОС пробуджує всі 64 задачі на всіх ядрах процесора. Усі 64 потоки одночасно кидаються захоплювати єдиний м'ютекс. Лише один потік успішно бере замок, а решта 63 потоки миттєво знову блокуються і засинають у черзі м'ютексу.

Це спричиняє 63 непотрібних перемикання контексту, навантажує шину пам'яті кеш-інвалідаціями та сповільнює роботу системи.

Щоб подолати цю проблему, сучасне ядро Linux надає спеціальну операцію системного виклику:
```
sys_futex(uaddr_cond, FUTEX_CMP_REQUEUE_PRIVATE, 1, INT_MAX, uaddr_mutex, val_cond)
```

Внутрішній алгоритм перекидання черг (*Wait Morphing / Requeuing*) у ядрі:
1. Ядро Linux пробуджує **рівно один** потік із черги умовної змінної (`uaddr_cond`), щоб він безпосередньо змагався за звільнений м'ютекс.
2. Решту 63 сплячих потоків ядро **прямо в пам'яті ядра**, не пробуджуючи і не перемикаючи контекст процесора, переносить зі списку очікування умовної змінної до списку очікування м'ютексу (`uaddr_mutex`).
3. Коли перший потік виконає роботу й викличе `pthread_mutex_unlock`, ядро послідовно та плавно пробудить наступного претендента без жодного шторму перемикань.

## Проблема вкладених моніторів (Nested Monitor Problem)

Ще однією тонкою класичною проблемою, відкритою Девідом Парнасом 1978 року, є **проблема вкладених викликів моніторів** (англ. *Nested Monitor Problem*).

Уявімо два окремі монітори `Outer` та `Inner`:
1. Потік входить у метод зовнішнього монітора `Outer::operation()` і захоплює його м'ютекс `mutex_outer`.
2. Усередині цього методу потік викликає метод внутрішнього монітора `Inner::wait_event()`, який захоплює `mutex_inner`.
3. Всередині `Inner` потік бачить, що умова не готова, і викликає `wait(&cond_inner, &mutex_inner)`.

Згідно з контрактом, функція `wait` звільняє `mutex_inner`. Проте вона **нічого не знає про `mutex_outer` і залишає його захопленим**!

Якщо для настання потрібної умови інший потік повинен викликати метод зовнішнього монітора `Outer::set_data()`, він виявляється заблокованим на `mutex_outer`. Виникає незворотний перехресний дедлок: перший потік спить в очікуванні події, утримуючи зовнішній замок, а другий потік не може створити цю подію, бо не може пройти крізь зовнішній замок.

Архітектурне правило боротьби з цією вразливістю: **ніколи не викликати блокуючий `wait()` у внутрішньому об'єкті, утримуючи замок зовнішнього монітора**. Замки слід захоплювати послідовно або відпускати зовнішній замок перед переходом у вкладені очікування.

## Монітори у різних мовах програмування

Концепція монітора знайшла різне синтаксичне втілення в сучасних мовах:

### 1. Java: Вбудовані об'єктні монітори та `j.u.c.locks`
У мові Java кожен об'єкт класу `Object` неявно має вбудований м'ютекс та **рівно одну** анонімну умовну змінну. Блокування активується ключовим словом `synchronized(obj)`, а очікування — методами `obj.wait()`, `obj.notify()`, `obj.notifyAll()`.
- **Головний недолік базової моделі Java**: наявність лише однієї умовної змінної на об'єкт змушує розробників у чергах виробників і споживачів постійно викликати `notifyAll()`, оскільки неможливо розбудити лише споживачів окремо від виробників.
- **Рішення**: починаючи з Java 5, пакет `java.util.concurrent.locks` надав явні класи `ReentrantLock` та інтерфейс `Condition`, що дозволяє створювати довільну кількість умовних змінних (`lock.newCondition()`) для одного замка.

### 2. C++: Стандартна бібліотека `<condition_variable>`
У C++ монітори будуються як композиція класів: об'єкт користувацького класу містить поле `std::mutex` та одне чи кілька полів `std::condition_variable`. Захоплення замка контролюється RAII-обгорткою `std::unique_lock<std::mutex>`, що гарантує розблокування м'ютексу навіть при виникненні винятків.

### 3. Rust: Примусова безпека на рівні типів
У Rust тип `std::sync::Condvar` працює в парі з `std::sync::Mutex<T>`. На відміну від C/C++, у Rust м'ютекс інкапсулює дані всередині себе. Метод `condvar.wait(guard)` споживає `MutexGuard<T>`, тимчасово звільняє замок і повертає новий `MutexGuard<T>` після пробудження, що робить неможливим доступ до захищених даних без захопленого замка на рівні перевірки типів компілятором.

### 4. Go: `sync.Cond`
У стандартній бібліотеці Go є тип `sync.Cond`, що створюється викликом `sync.NewCond(&mutex)`. У практиці Go умовні змінні застосовуються рідко (перевага надається каналам `chan`), проте для патерну широкомовного сповіщення 1-до-N без виділення буферів пам'яті `sync.Cond.Broadcast()` залишається найефективнішим інструментом.

## Практична реалізація: обмежена черга на C та C++

Об'єднаємо всі викладені принципи у класичний патерн — **потокобезпечну обмежену блокувальну чергу** (англ. *Bounded Blocking Queue*).

Щоб повністю уникнути взаємних конфліктів між виробниками і споживачами, ми використовуємо **дві окремі умовні змінні**:
- `not_empty`: на ній засинають споживачі, коли черга порожня (`count == 0`).
- `not_full`: на ній засинають виробники, коли черга заповнена (`count == capacity`).

:::tabs
```c
#include <pthread.h>
#include <stdbool.h>
#include <stdlib.h>

typedef struct {
    int* data;
    size_t capacity;
    size_t head;
    size_t tail;
    size_t count;

    pthread_mutex_t lock;
    pthread_cond_t not_empty;
    pthread_cond_t not_full;
} queue_t;

queue_t* queue_create(size_t capacity) {
    queue_t* q = (queue_t*)malloc(sizeof(queue_t));
    if (!q) return NULL;

    q->data = (int*)malloc(sizeof(int) * capacity);
    if (!q->data) {
        free(q);
        return NULL;
    }

    q->capacity = capacity;
    q->head = 0;
    q->tail = 0;
    q->count = 0;

    pthread_mutex_init(&q->lock, NULL);
    pthread_cond_init(&q->not_empty, NULL);
    pthread_cond_init(&q->not_full, NULL);

    return q;
}

void queue_push(queue_t* q, int value) {
    pthread_mutex_lock(&q->lock);

    /* Захист Mesa: перевірка місткості тільки в циклі while */
    while (q->count == q->capacity) {
        pthread_cond_wait(&q->not_full, &q->lock);
    }

    q->data[q->tail] = value;
    q->tail = (q->tail + 1) % q->capacity;
    q->count++;

    /* Будимо рівно одного очікуючого споживача */
    pthread_cond_signal(&q->not_empty);

    pthread_mutex_unlock(&q->lock);
}

int queue_pop(queue_t* q) {
    pthread_mutex_lock(&q->lock);

    /* Захист Mesa: перевірка наявності тільки в циклі while */
    while (q->count == 0) {
        pthread_cond_wait(&q->not_empty, &q->lock);
    }

    int value = q->data[q->head];
    q->head = (q->head + 1) % q->capacity;
    q->count--;

    /* Будимо рівно одного очікуючого виробника */
    pthread_cond_signal(&q->not_full);

    pthread_mutex_unlock(&q->lock);
    return value;
}

void queue_destroy(queue_t* q) {
    if (!q) return;
    pthread_mutex_destroy(&q->lock);
    pthread_cond_destroy(&q->not_empty);
    pthread_cond_destroy(&q->not_full);
    free(q->data);
    free(q);
}
```
```cpp
#include <mutex>
#include <condition_variable>
#include <vector>
#include <stdexcept>

template <typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(size_t capacity)
        : capacity_(capacity), head_(0), tail_(0), count_(0), buffer_(capacity) {
        if (capacity == 0) {
            throw std::invalid_argument("Capacity must be positive");
        }
    }

    void push(T item) {
        std::unique_lock<std::mutex> lock(mutex_);
        /* Лямбда гарантує перевірку умови у циклі while */
        not_full_.wait(lock, [this] { return count_ < capacity_; });

        buffer_[tail_] = std::move(item);
        tail_ = (tail_ + 1) % capacity_;
        ++count_;

        not_empty_.notify_one();
    }

    T pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        /* Безпечне очікування з автоматичним повторним взяттям замка */
        not_empty_.wait(lock, [this] { return count_ > 0; });

        T item = std::move(buffer_[head_]);
        head_ = (head_ + 1) % capacity_;
        --count_;

        not_full_.notify_one();
        return item;
    }

private:
    const size_t capacity_;
    size_t head_;
    size_t tail_;
    size_t count_;
    std::vector<T> buffer_;

    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
};
```
