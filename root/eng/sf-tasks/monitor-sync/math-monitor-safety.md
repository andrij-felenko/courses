# 🧮 Формальні інваріанти та верифікація коректності моніторів

Коректність багатопотокових програм неможливо перевірити звичайним тестуванням через недетермінізм планувальника та астрономічну кількість можливих чергувань інструкцій (*interleavings*). Єдиним надійним методом гарантії того, що монітор ніколи не пошкодить спільний стан і не заблокується назавжди, є формальна верифікація за допомогою інваріантів стану, логіки Хоара та темпоральних властивостей живучості.

Ця математична модель формалізує правила безпеки (*safety properties*), стійкості інваріантів, збереження об'єму даних, гарантій справедливості черг та відсутності дедлоків (*deadlock freedom*) для абстракції монітора.

## Формальна модель стану монітора

Нехай стан пам'яті, що контролюється монітором, описується вектором змінних `S = (v₁, v₂, ..., vₖ)`.

Монітор визначається кортежем `M = (S, I, Ops, C)`:
- `S` — простір внутрішніх станів монітора.
- `I(S)` — **інваріант монітора** (англ. *monitor invariant*), булевий предикат над змінними `S`, який визначає узгодженість та цілісність даних.
- `Ops = {op₁, op₂, ..., opₘ}` — множина відкритих процедур (методів) монітора.
- `C = {c₁, c₂, ..., cᵣ}` — множина умовних змінних, кожній з яких відповідає свій предикат очікування `P_{cᵢ}(S)`.

### Теорема взаємного виключення (Safety)

Нехай `Active(M, t)` — множина потоків, які одночасно виконують інструкції всередині процедур монітора `M` у фізичний момент часу `t`.

Фундаментальна властивість безпеки монітора полягає у дотриманні обмеження взаємного виключення, яке в лінійній темпоральній логіці (LTL) записується як інваріант для всіх станів траси виконання:

```
|Active(M, t)| ≤ 1    [для будь-якого моменту часу t ≥ 0]
```

Це означає, що в моніторі або взагалі немає активних потоків (`|Active| = 0`), або працює рівно один потік (`|Active| = 1`). Усі інші потоки перебувають або у вхідній черзі до м'ютексу, або у чергах сну умовних змінних `cᵢ ∈ C`.

## Інваріант монітора та трійки Хоара

Інваріант `I(S)` має зберігатися у всі критичні моменти життя системи. Згідно з аксіоматичною семантикою, коректність монітора вимагає виконання трьох обов'язкових умов:

1. **Ініціалізація**: Початковий стан системи `S₀` після створення об'єкта зобов'язаний задовольняти інваріант:
```
{true} Init() {I(S₀)}    [інваріант істинний відразу після конструювання]
```

2. **Збереження інваріанта процедурами**: Кожна відкрита процедура `op ∈ Ops` має право розраховувати на істинність `I(S)` на вході, і зобов'язана відновити `I(S)` перед виходом:
```
{I(S) ∧ Pre_op(S)} op(args) {I(S) ∧ Post_op(S)}
```
Усередині процедури інваріант `I(S)` може тимчасово порушуватися під час проміжних обчислень, але жоден інший потік не може спостерігати цей стан завдяки монопольному утриманню замка.

3. **Точки очікування (wait)**: Перед тим як заснути на умовній змінній `c`, потік звільняє м'ютекс. Отже, стан `S` перед викликом `wait` зобов'язаний бути узгодженим:
```
{I(S)} wait(c) {I(S)}    [інваріант має бути відновлено перед відпусканням замка]
```

## Семантика передачі стану: Хоар проти Mesa

Критична математична різниця між двома моделями моніторів полягає у предикаті, який гарантується *після* повернення з операції `wait(c)`.

Нехай `P_c(S)` — цільова умова, на настання якої чекає потік (наприклад, `count > 0`). Потік-виробник перед викликом `signal(c)` встановлює цю умову в стан `true`.

### 1. Семантика Хоара (Signal-and-Wait)

Оскільки сигналізатор негайно передає замок розбудженому потоку без проміжних дій сторонніх процесів, предикат `P_c(S)` не може змінитися між моментами `signal` і поверненням із `wait`:

```
Аксіома очікування Хоара:
{I(S)} wait_Hoare(c) {I(S) ∧ P_c(S)}    [предикат гарантовано істинний при пробудженні]
```

Звідси випливає доведення коректності простого умовного оператора:
```
{I(S)}
if (!P_c(S)) {
    {I(S) ∧ ¬P_c(S)}
    wait_Hoare(c);
    {I(S) ∧ P_c(S)}
}
{I(S) ∧ P_c(S)}    [цільова умова виконується безумовно]
```

### 2. Семантика Mesa (Signal-and-Continue)

У семантиці Mesa між викликом `signal(c)` та реальним захопленням м'ютексу розбудженим потоком існує довільний інтервал часу `Δt > 0`, протягом якого інші потоки можуть змінювати стан `S`. Тому єдиною гарантією на виході з `wait_Mesa` є загальний інваріант `I(S)`, але не сам предикат `P_c(S)`:

```
Аксіома очікування Mesa:
{I(S)} wait_Mesa(c) {I(S)}    [гарантовано лише загальний інваріант, предикат P_c не гарантований]
```

Якщо використати конструкцію `if (!P_c(S)) wait_Mesa(c)`, після блоку умова `P_c(S)` може виявитися хибною, що призведе до порушення логіки програми.

Для відновлення коректності застосовується правило циклу з інваріантом циклу `I(S)`:

```
{I(S)}
while (!P_c(S)) {
    {I(S) ∧ ¬P_c(S)}
    wait_Mesa(c);
    {I(S)}
}
{I(S) ∧ P_c(S)}    [умова виходу з циклу гарантує істинність P_c(S)]
```

Ланцюг виведення коректності циклу очікування:
```
  Стан на початку: I(S)
= I(S) ∧ (P_c(S) ∨ ¬P_c(S))       [закон виключеного третього]
= (I(S) ∧ P_c(S)) ∨ (I(S) ∧ ¬P_c) [дистрибутивність кон'юнкції]
  Після виходу з while (!P_c):
= (I(S) ∧ ¬(¬P_c(S)))             [заперечення умови продовження циклу]
= I(S) ∧ P_c(S)                   [подвійне заперечення: стан строго узгоджений]
```

## Практичний приклад: верифікація обмеженого буфера

Розглянемо класичний монітор обмеженого буфера місткістю `N` елементів (`N > 0`).

Вектор стану:
```
S = (count, head, tail, buffer)
```
де `count ∈ ℤ` — поточна кількість елементів, `buffer` — масив довжини `N`.

### Інваріант буфера:
```
I(S) ≡ (0 ≤ count ≤ N) ∧ (0 ≤ head < N) ∧ (0 ≤ tail < N)
```

Предикати умовних змінних:
- `not_empty` (для читання): `P_{not_empty}(S) ≡ (count > 0)`
- `not_full` (для запису): `P_{not_full}(S) ≡ (count < N)`

### Верифікація операції Push(item):

```
Pre_push  ≡ true
Post_push ≡ count = count_old + 1

1. Вхід у метод:
   {I(S)}
2. Очікування вільного місця:
   while (count == N) {
       {I(S) ∧ (count == N)}
       wait(not_full);
       {I(S)}
   }
   {I(S) ∧ (count < N)}   [гарантія виходу з циклу: 0 ≤ count < N]

3. Модифікація стану:
   buffer[tail] = item;
   tail = (tail + 1) % N;
   count = count + 1;

   Перевірка збереження інваріанта:
   count_new = count + 1
   Оскільки count < N, маємо: count_new ≤ N.
   Оскільки count ≥ 0, маємо: count_new > 0 ≥ 0.
   Звідси: 0 ≤ count_new ≤ N — інваріант I(S) збережено!

4. Сигналізація споживачам:
   signal(not_empty);     [оскільки count_new > 0, предикат P_{not_empty} став істинним]

5. Вихід із методу:
   {I(S) ∧ Post_push}
```

### Верифікація операції Pop():

```
Pre_pop  ≡ true
Post_pop ≡ (item = buffer_old[head_old]) ∧ (count = count_old - 1)

1. Вхід у метод:
   {I(S)}
2. Очікування наявності даних:
   while (count == 0) {
       {I(S) ∧ (count == 0)}
       wait(not_empty);
       {I(S)}
   }
   {I(S) ∧ (count > 0)}   [гарантія виходу з циклу: 0 < count ≤ N]

3. Вилучення даних та модифікація стану:
   item = buffer[head];
   head = (head + 1) % N;
   count = count - 1;

   Перевірка збереження інваріанта:
   count_new = count - 1
   Оскільки count ≤ N, маємо: count_new < N ≤ N.
   Оскільки count > 0, маємо: count_new ≥ 0.
   Звідси: 0 ≤ count_new ≤ N — інваріант I(S) збережено!

4. Сигналізація виробникам:
   signal(not_full);      [оскільки count_new < N, предикат P_{not_full} став істинним]

5. Вихід із методу:
   {I(S) ∧ Post_pop}
```

### Закон збереження об'єму даних

Для будь-якого інтервалу часу `[0, T]` нехай `TotalPushed(T)` — загальна кількість елементів, успішно доданих усіма виробниками, а `TotalPopped(T)` — загальна кількість елементів, вилучених споживачами.

Фундаментальний закон збереження стверджує:

```
TotalPushed(T) = TotalPopped(T) + count(T)
```

де `0 ≤ count(T) ≤ N`. Це гарантує повну відсутність витоку даних, дублювання або втрати елементів усередині монітора.

## Гарантії справедливості черг (Fairness) та відсутність голодування

Живучість монітора також визначається дисципліною обслуговування черг:
- **Сувора справедливість FIFO**: якщо черга умовної змінної та черга вхідного м'ютексу організовані за принципом «першим прийшов — першим пішов» (FIFO), то час очікування будь-якого потоку обмежений кількістю запитів, які надійшли раніше:
```
WaitTime(Tᵢ) ≤ k · MaxExecutionTime(Ops)    [де k — позиція потоку в черзі]
```
- **Слабка справедливість планувальника**: у сучасних ОС типу Linux черги футексів не гарантують строгого порядку FIFO через пріоритети задач та оптимізації багатоядерного планувальника CFS/EEVDF. Проте за умови слабкої чесності жоден потік не залишається заблокованим назавжди, якщо подія генерується нескінченно часто.

## Доведення відсутності дедлоків (Deadlock Freedom)

Теорема живучості стверджує, що замкнене блокування всередині монітора неможливе, якщо виконуються умови взаємної сигналізації.

Нехай `Consumers` — множина потоків, заблокованих на `not_empty`, а `Producers` — множина потоків, заблокованих на `not_full`.

Припустимо від супротивного, що система потрапила у стан глобального глухого кута, коли всі потоки заблоковані у чергах умовних змінних:
```
Усі активні потоки сплять ⇔ (Consumers ≠ ∅) ∧ (Producers ≠ ∅)
```

Розглянемо значення лічильника `count`:
1. Потоки з `Consumers` сплять лише тоді, коли `count == 0` (буфер порожній).
2. Потоки з `Producers` сплять лише тоді, коли `count == N` (буфер заповнений).
3. Оскільки місткість буфера `N > 0`, отримуємо суперечність:
```
count = 0 ∧ count = N ⇒ 0 = N    [суперечність із умовою N > 0]
```

Отже, буфер не може бути одночасно і порожнім, і повним. Принаймні одна з груп потоків (`Consumers` або `Producers`) гарантовано має істинний предикат і продовжує виконання. За умови слабкої чесності (*weak fairness*) планувальника система монітора завжди забезпечує прогрес виконання.
