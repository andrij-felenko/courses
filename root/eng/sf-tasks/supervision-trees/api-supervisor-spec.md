# 📋 Специфікація дочірніх процесів та конфігурація наглядача

Наглядач процесів працює на основі суворого декларативного контракту. Він не містить розмитої логіки евристичного відновлення, а керується двома чіткими структурами даних: загальними прапорцями поведінки самого наглядача (*supervisor flags*) та списком специфікацій дочірніх задач (*child specifications*).

Цей контракт визначає, як система запускається, кого вона перезапускає у разі збоїв, як обмежує лавину аварій, як взаємодіє з підсистемою гарячого оновлення коду та в якому порядку звільняє ресурси під час планової чи аварійної зупинки.

## Прапорці наглядача (Supervisor Flags)

Конфігурація наглядача описує глобальну політику управління підпорядкованими процесами та визначає параметри відмовостійкості для всієї локальної гілки дерева.

```
Складові прапорців наглядача:
┌──────────────────┬──────────────────────┬────────────────────────────────────────────────────────┐
│ Поле             │ Тип                  │ Призначення                                            │
├──────────────────┼──────────────────────┼────────────────────────────────────────────────────────┤
│ strategy         │ atom / enum          │ Стратегія перезапуску: one_for_one, one_for_all,      │
│                  │                      │ rest_for_one, simple_one_for_one (динамічний)          │
│ max_restarts     │ ціле ≥ 0             │ Максимальна кількість перезапусків (MaxR) за період    │
│ max_seconds      │ ціле > 0 (секунди)   │ Тривалість ковзного часового вікна (MaxT)             │
│ auto_shutdown    │ atom / enum          │ Політика зупинки наглядача при виході ключових дітей:  │
│                  │                      │ never, any_significant, all_significant               │
└──────────────────┴──────────────────────┴────────────────────────────────────────────────────────┘
```

### Значення стратегій перезапуску

- `one_for_one`: при збої нащадка наглядач перезапускає виключно той процес, що впав. Решта дочірніх процесів продовжують роботу без найменшої паузи. Ця стратегія є базовою для незалежних обчислювачів.
- `one_for_all`: при збої будь-якого нащадка наглядач послідовно зупиняє всіх інших дітей у зворотному порядку, після чого перезапускає весь набір процесів з нуля у прямому порядку. Застосовується для тісно пов'язаних процесів зі спільними інваріантами.
- `rest_for_one`: при збої процесу з індексом `k` наглядач зупиняє і перезапускає всі процеси з індексами `i > k` (ті, що були оголошені пізніше й лінійно залежать від нього). Процеси з індексами `i < k` залишаються недоторканими.

### Політика автоматичної зупинки (auto_shutdown)

У сучасних версіях систем нагляду (зокрема в OTP 24+) введено механізм значущих дочірніх процесів (*significant children*). Якщо тимчасова або перехідна задача завершує свою роботу, вона може сигналізувати наглядачеві про необхідність згорнути всю підсистему:
- `never` (за замовчуванням): завершення будь-якого нащадка не призводить до зупинки наглядача.
- `any_significant`: якщо хоча б один процес із прапорцем `significant: true` завершується успішно, наглядач ініціює коректну зупинку всіх інших дітей і завершується сам.
- `all_significant`: наглядач завершується лише після того, як усі значущі нащадки завершили своє виконання.

## Специфікація дочірнього процесу (Child Specification)

Кожен процес, що передається під опіку наглядача, описується декларативною структурою зі сталими полями. Цей словник фіксує ідентифікатор, точку входу, політику відновлення та граничні тайм-аути.

```
Специфікація нащадка (child_spec):
┌──────────────────┬──────────────────────┬────────────────────────────────────────────────────────┐
│ Поле             │ Тип                  │ Призначення                                            │
├──────────────────┼──────────────────────┼────────────────────────────────────────────────────────┤
│ id               │ atom / string        │ Унікальний ідентифікатор вузла в межах цього наглядача │
│ start            │ {M, F, Args} / fn    │ Точка входу: модуль, функція та аргументи запуску      │
│ restart          │ atom / enum          │ Правило перезапуску: permanent, transient, temporary   │
│ shutdown         │ timeout / brutal_kill│ Ліміт часу на коректну зупинку перед примусовим kill   │
│ type             │ worker | supervisor  │ Роль вузла в дереві (листок чи проміжний наглядач)    │
│ modules          │ list (module names)  │ Список модулів для гарячого оновлення коду             │
│ significant      │ boolean (true/false) │ Чи є процес значущим для auto_shutdown наглядача       │
└──────────────────┴──────────────────────┴────────────────────────────────────────────────────────┘
```

### Режими життєвого циклу (restart)

1. `permanent` (постійний):
   - Процес перезапускається **завжди**, незалежно від причини зупинки (як у разі паніки чи необробленого винятку, так і у разі штатного виходу з кодом `0` або `:normal`).
   - *Типове призначення:* Фоновые сервіси, пули постійних з'єднань з базою даних, драйвери апаратних шин, мережеві демони слухання портів.

2. `transient` (перехідний):
   - Процес перезапускається **виключно у разі аварії** (завершення з ненульовим кодом, отримання сигналу падіння, виняток під час виконання).
   - Якщо процес завершився успішно (`:normal`, `exit(0)`), він вважається таким, що повністю виконав своє функціональне завдання. Наглядач переводить його у стан `stopped` і не робить спроб перезапуску.
   - *Типове призначення:* Задачі міграції схем баз даних під час старту застосунку, генератори періодичних звітів, обробники фонових завдань із черги.

3. `temporary` (тимчасовий):
   - Процес **ніколи не перезапускається наглядачем**, хай би якою була причина його смерті.
   - *Типове призначення:* Короткоживучі діагностичні виклики, одноразові збирачі метрик пам'яті, з'єднання, повторна спроба яких не має сенсу без участі зовнішнього клієнта.

### Стратегії та тайм-аути зупинки (shutdown)

Під час зупинки дочірнього процесу наглядач зобов'язаний гарантувати, що процес не зависне назавжди, заблокувавши все дерево:
- `brutal_kill`: наглядач не дає процесу часу на очищення, а негайно надсилає безумовний сигнал знищення (`SIGKILL` у POSIX або `exit(Pid, kill)` у середовищі BEAM). Застосовується виключно для процесів без внутрішнього стану, які не тримають відкритих файлів на запис.
- `Timeout` (додатне число мілісекунд, наприклад `5000`): наглядач надсилає сигнал м'якої зупинки (`SIGTERM` або повідомлення виходу) і запускає локальний таймер. Якщо дочірній процес встигає зберегти стан і вийти самостійно до спливу таймера, наглядач продовжує роботу. Якщо таймер вичерпано, а процес усе ще активний, наглядач надсилає примусовий `SIGKILL`.
- `infinity`: наглядач очікує завершення нащадка без обмеження за часом. Це обов'язкове налаштування, коли дочірній вузол сам є наглядачем (`type: :supervisor`), оскільки вкладене піддерево повинно мати достатньо часу, щоб рекурсивно зупинити всі свої власні рівні знизу вгору.

### Інтеграція з гарячим оновленням коду (modules)

Поле `modules` містить список модулів, які виконуються дочірнім процесом. Під час виконання процедури оновлення релізу (*release upgrade*) без перезавантаження вузла менеджер коду опитує наглядача, знаходить активні процеси за списком `modules`, надсилає їм повідомлення про призупинення виконання (*suspend*), викликає функцію трансформації стану `code_change/3`, оновлює байт-код у пам'яті та відновлює роботу (*resume*).

## Програмний інтерфейс керування (Control API)

Наглядач надає формальний набір викликів для програмного моніторингу та динамічної зміни структури піддерева:

### 1. Ініціалізація та старт наглядача

```erlang
Supervisor:start_link(Module, Args) -> {ok, Pid} | {error, Reason}
```
- Створює новий процес наглядача, прив'язує його через двосторонній зв'язок до викликаючого процесу та ініціалізує список дочірніх задач.
- Послідовно запускає нащадків зліва направо. Якщо хоча б один дочірній процес повертає помилку ініціалізації (`{error, Reason}` або `ignore`), наглядач негайно зупиняє вже запущених дітей у зворотному порядку і повертає помилку запуску.

### 2. Опитування поточного стану дітей

```erlang
Supervisor:which_children(SupRef) -> [{Id, Child, Type, Modules}]
```
- Повертає зріз поточного стану всіх зареєстрованих специфікацій:
  - `Id`: ідентифікатор нащадка.
  - `Child`: поточний `Pid` процесу, або `undefined` (якщо процес тимчасово впав і очікує перезапуску), або `restarting` (якщо процес перебуває в стадії ініціалізації).
  - `Type`: `:worker` або `:supervisor`.
  - `Modules`: список пов'язаних модулів.

### 3. Динамічне додавання та видалення нащадків

```erlang
Supervisor:start_child(SupRef, ChildSpec) -> {ok, ChildPid} | {error, Reason}
Supervisor:terminate_child(SupRef, Id)     -> ok | {error, not_found}
Supervisor:delete_child(SupRef, Id)        -> ok | {error, running | not_found}
Supervisor:restart_child(SupRef, Id)       -> {ok, ChildPid} | {error, running | not_found}
```
- `start_child`: додає нову специфікацію та негайно стартує процес.
- `terminate_child`: коректно зупиняє процес за правилом `shutdown`, зберігаючи специфікацію в пам'яті наглядача для можливого наступного ручного запуску.
- `delete_child`: видаляє збережену специфікацію. Працює лише для попередньо зупинених процесів.

## Порядок ініціалізації та інваріанти надійності

```
Порядок запуску (Depth-first, Forward):
[Корінь] ──> [Підсистема A] ──> [Worker 1] ──> [Worker 2] ──> [Підсистема B] ──> [Worker 3]

Порядок планової зупинки (Strict Reverse):
[Worker 3] ──> [Підсистема B] ──> [Worker 2] ──> [Worker 1] ──> [Підсистема A] ──> [Корінь]
```

1. **Інваріант випереджальної залежності:** Базовий ресурс завжди стартує раніше за його споживача. Якщо `Worker 2` потребує відкритого сокета або пулу пам'яті, що створюється у `Worker 1`, `Worker 1` зобов'язаний стояти вище у списку специфікацій.
2. **Інваріант безпечного вимкнення:** Споживач ресурсу завжди зупиняється першим. При отриманні команди на вимкнення наглядач гарантує, що `Worker 2` встигне завершити всі поточні операції до того, як `Worker 1` закриє дескриптори доступу чи звільнить пам'ять.
