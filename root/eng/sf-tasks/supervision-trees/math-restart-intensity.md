# 🧮 Інтенсивність перезапусків, ковзні вікна та ймовірність ескалації

Головна інженерна дилема наглядача процесів полягає у розрізненні двох принципово різних типів відмов:
1. **Транзієнтні (перехідні) збої:** поодинокі збої через рідкісний збіг обставин, тимчасові тайм-аути в мережі, сплески навантаження або поодинокі пошкоджені пакети. Такі аварії лікуються миттєвим перезапуском процесу в чистому початковому стані, оскільки ймовірність повторення збою в наступну мілісекунду є мізерно малою.
2. **Системні (перманентні) збої:** пошкодження файлу конфігурації на диску, фізична відмова апаратної шини або помилка підключення до неіснуючої бази даних. Перезапуск процесу в цьому випадку є безсилим, оскільки під час кожної наступної ініціалізації процес гарантовано впаде знову.

Якщо наглядач буде без обмежень перезапускати процес, що гине щоразу при старті, система увійде в нескінченний шторм аварій (*crash loop*), споживаючи 100% процесорного часу та забиваючи системні журнали гігабайтами сміття. Якщо ж наглядач здаватиметься після першого-ліпшого збою, система втратить здатність до автоматичного самовідновлення після випадкових перехідних коливань. Математичним інструментом вирішення цієї дилеми є **правило інтенсивності перезапусків** `(MaxR, MaxT)`: допустима кількість аварій `MaxR` за часове вікно тривалістю `MaxT`.

## Імовірнісна модель випадкових збоїв

У стабільно функціонуючій системі поява поодиноких перехідних збоїв підпорядковується законам стаціонарного пуассонівського процесу. Ми припускаємо, що аварії виникають незалежно одна від одної з постійною середньою інтенсивністю `λ` (кількість випадкових відмов за одиницю часу).

Ймовірність того, що за проміжок часу тривалістю `T` трапиться рівно `k` аварійних зупинок процесу, описується класичним розподілом Пуассона:

```
P(k, T) = ((λ·T)ᵏ · e^(−λ·T)) / k!
```

Наглядач процесів веде безперервний облік аварійних подій і ухвалює рішення про ескалацію (власне аварійне завершення та передачу збою на рівень вище), якщо сумарна кількість зафіксованих аварій `k` усередині ковзного вікна тривалістю `T = MaxT` строго перевищує встановлений ліміт `R = MaxR`.

Ймовірність помилкової ескалації під дією суто випадкових перехідних шумів обчислюється як сума ймовірностей знаходження у хвості розподілу:

```
P(escalate) = P(k > R) = 1 − ∑ [k = 0 .. R] P(k, T)
```

## Покроковий розрахунок для типових параметрів

Розглянемо стандартну конфігурацію наглядача, прийняту за замовчуванням у більшості промислових розподілених систем:
- Максимально допустима кількість перезапусків: `R = 3`
- Тривалість ковзного часового вікна: `T = 10` секунд

### Сценарій 1: Стабільна робота з рідкісними перехідними збоями

Припустимо, що в системі виникає в середньому одна випадкова транзієнтна помилка на кожні 100 секунд нормальної роботи (`λ = 0.01` с⁻¹ або середній час між збоями `MTBF = 100` с). Обчислимо математичне сподівання кількості подій у вікні тривалістю `T = 10` секунд:

```
μ = λ·T
= 0.01 · 10       [підстановка інтенсивності λ=0.01 та вікна T=10]
= 0.1             [середнє число випадкових збоїв за 10 секунд]
```

Значення базової експоненти для `μ = 0.1`:
```
e^(−0.1) ≈ 0.904837
```

Обчислимо точні ймовірності появи від нуля до трьох аварій усередині 10-секундного інтервалу:

```
P(0, 10)
= (0.1⁰ · 0.904837) / 0!   [k = 0: жодної аварії]
= 1 · 0.904837 / 1         [розкриття нульового степеня і факторіала]
= 0.9048374                [90.48% ймовірності повної відсутності аварій]

P(1, 10)
= (0.1¹ · 0.904837) / 1!   [k = 1: рівно один збій]
= 0.1 · 0.904837 / 1       [розкриття першого степеня]
= 0.0904837                [9.05% ймовірності одного збою]

P(2, 10)
= (0.1² · 0.904837) / 2!   [k = 2: рівно два збої]
= 0.01 · 0.904837 / 2      [розкриття квадрата та факторіала 2!=2]
= 0.0045242                [0.45% ймовірності двох збоїв]

P(3, 10)
= (0.1³ · 0.904837) / 3!   [k = 3: рівно три збої]
= 0.001 · 0.904837 / 6     [розкриття куба та факторіала 3!=6]
= 0.0001508                [0.015% ймовірності трьох збоїв]
```

Сумарна ймовірність того, що кількість випадкових збоїв не вийде за межі встановленого бюджету `R = 3`:

```
P(k ≤ 3)
= P(0) + P(1) + P(2) + P(3)                                 [сума взаємовиключних станів]
= 0.9048374 + 0.0904837 + 0.0045242 + 0.0001508             [підстановка розрахованих значень]
= 0.9999961                                                 [ймовірність безпечної роботи]
```

Ймовірність помилкової ескалації та падіння наглядача через випадковий збіг транзієнтних збоїв:

```
P(escalate)
= 1 − P(k ≤ 3)             [ймовірність протилежної події]
= 1 − 0.9999961            [віднімання безпечної ймовірності]
= 0.0000039                [≈ 3.9·10⁻⁶ або 1 випадок на 256 000 часових вікон]
```

Цей розрахунок демонструє, що за нормальних умов наглядач майже ніколи не робить помилкових ескалацій. Він надійно локалізує та поглинає транзієнтні збої, забезпечуючи коефіцієнт готовності понад 99.999%.

## Ефективний середній час безвідмовної роботи (MTBF)

Введення наглядача кардинально змінює надійність системи. Якщо сирий процес має середній час безвідмовної роботи `MTBF_raw = 1 / λ`, то для зовнішнього користувача процес виглядає працездатним доти, доки локальний збій успішно маскується перезапуском.

Система як ціле зазнає простою лише тоді, коли стається ескалація. Ефективний середній час до системної аварії `MTBF_eff` обчислюється як тривалість часового вікна `T`, поділена на ймовірність ескалації у цьому вікні:

```
MTBF_eff = T / P(escalate)
= 10 с / 0.0000039         [ділення вікна на ймовірність ескалації]
= 2564102 с                [переведення в секунди]
≈ 29.68 доби               [майже місяць безперервної роботи]
```

Таким чином, наглядач із простим правилом `(MaxR=3, MaxT=10s)` збільшує надійність компонента зі 100 секунд до майже 30 діб, приховуючи від користувачів 99.9996% поодиноких перехідних збоїв.

### Сценарій 2: Перманентний системний збій

Тепер проаналізуємо поведінку системи у випадку фатальної незворотної помилки (наприклад, пошкоджений заголовок файлу даних на диску). Кожного разу, коли наглядач перезапускає процес, той негайно намагається зчитати пошкоджений файл і падає за 50 мілісекунд.

Реальна інтенсивність спроб перезапуску обмежується виключно швидкістю ініціалізації та становить `λ = 1 / 0.05 = 20` збоїв за секунду.

Обчислимо очікувану кількість подій для 10-секундного вікна:

```
μ = λ·T
= 20 · 10                  [підстановка інтенсивності λ=20 та T=10]
= 200                      [очікувана кількість аварійних циклів]
```

Ймовірність того, що кількість аварій якимось чином не перевищить бюджет `R = 3`:

```
P(k ≤ 3)
= ∑ [k=0..3] (200ᵏ · e^(−200)) / k!       [сума за формулою Пуассона]
≈ e^(−200) · (1 + 200 + 20000 + 1333333)   [винесення e^(-200) за дужки]
≈ 1.38·10^(−87) · 1.35·10⁶                 [обчислення експоненти та суми]
≈ 1.86·10^(−81)                            [практично абсолютний нуль]
```

Ймовірність миттєвої детермінованої ескалації:

```
P(escalate)
= 1 − 1.86·10^(−81)        [віднімання залишкової ймовірності]
≈ 1.0                      [100% гарантована ескалація]
```

Час до спрацьовування ескалації та передачі аварії на рівень вище:

```
t_escalate = R · t_crash
= 3 · 0.05 с               [три послідовні цикли падіння по 50 мс]
= 0.15 с                   [150 мілісекунд до зупинки наглядача]
```

Математичний апарат доводить: якщо помилка є перманентною, наглядач не витрачає процесорний час даремно. Уже за 150 мілісекунд бюджет аварій вичерпується, наглядач зупиняє шквал рестартів і передає проблему вище — батьківському наглядачеві, який може перезапустити всю підсистему разом із дисковим сховищем.

## Багаторівнева ескалація в ієрархічних деревах

У дереві глибиною `H` рівнів потік збоїв фільтрується на кожному ярусі. Якщо нижній наглядач має ймовірність ескалації `P_esc_1`, то для наглядача другого рівня потік аварійних подій формується не прямими збоями воркерів, а рідкісними подіями ескалації з першого рівня.

Інтенсивність вхідного потоку аварій для наглядача рівня `m+1` виражається через інтенсивність нижнього рівня:

```
λ_(m+1) = λ_m · P_esc_m
```

Завдяки геометричній прогресії згасання потоку аварійних подій, ймовірність того, що аварія дійде до кореневого наглядача застосунку (`m = H`), дорівнює добутку ймовірностей ескалації на всіх проміжних рівнях:

```
P_root_crash = ∏ [m = 1 .. H] P_esc_m
```

Якщо на кожному з трьох рівнів дерева ймовірність помилкової ескалації становить `10⁻⁵`, то ймовірність неконтрольованого падіння кореня системи складає `(10⁻⁵)³ = 10⁻¹⁵`, що гарантує абсолютну стійкість розподіленого комплексу до стохастичних шумів.

## Порівняння алгоритмів фільтрації інтенсивності

В інженерній практиці для програмного контролю правила `(MaxR, MaxT)` використовуються два основних підходи:

```
Порівняння алгоритмів обліку аварій:
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┐
│ Параметр                     │ Ковзне кільцеве вікно        │ Алгоритм дірявого відра      │
│                              │ (Sliding Ring Buffer)        │ (Leaky Bucket / Token Bucket)│
├──────────────────────────────┼──────────────────────────────┼──────────────────────────────┤
│ Витрати пам'яті              │ O(MaxR) — масив таймстемпів  │ O(1) — лічильник і мітка часу│
│ Точність вікна               │ Абсолютна хронологічна       │ Наближена експоненційна      │
│ Обчислювальна складність     │ O(1) амортизована            │ O(1) сувора                  │
│ Реакція на пачку аварій      │ Миттєва при виході за R      │ Залежить від швидкості витоку│
└──────────────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

У класичному наглядачі Erlang/OTP застосовується **ковзне кільцеве вікно**: наглядач зберігає список часових позначок останніх аварій `[t₁, t₂, ..., t_k]`. При кожному новому збої часові позначки, старіші за `current_time − MaxT`, відкидаються. Якщо довжина списку, що залишився, перевищує `MaxR`, наглядач миттєво ініціює процедуру самоліквідації та ескалації.
