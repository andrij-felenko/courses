Автономний логер вібрацій промислового насоса на базі мікроконтролера STM32L4 живиться від літієвої дискової батареї CR2032 номінальною ємністю 225 мА·год. Прилад працює під керуванням операційної системи реального часу FreeRTOS: раз на 10 секунд вимірювальна задача опитує цифровий акселерометр по шині SPI, фільтрує вибірку й записує блок даних у FLASH-пам'ять. Активна робота триває рівно 5 мілісекунд при середньому споживанні струму 16 мА. Решту 9995 мілісекунд задача очікує наступного циклу, викликаючи системну затримку `vTaskDelay(pdMS_TO_TICKS(9995))`. Теоретичний розрахунок обіцяє понад 4 роки безперервної роботи від одного елемента живлення, якщо мікроконтролер у моменти очікування перебуває в режимі глибокого сну Stop 1 зі струмом 1.5 мкА. Проте вимірювання на готовому стенді показують стабільне середнє споживання на рівні 1.2 мА, а свіжа батарея повністю виснажується лише за тиждень.

Головна причина криється в конфлікті між базовим серцебиттям планувальника RTOS та апаратною організацією енергозбереження сучасних процесорів. Стандартний таймер SysTick генерує виняткове переривання кожну мілісекунду (1000 Гц), щоб перевірити готовність задач та перемкнути кванти часу. За кожні 10 секунд очікування контролер здійснює 9995 абсолютно порожніх пробуджень ядра. Кожен такий вихід зі сну запускає перехідні процеси у внутрішньому стабілізаторі напруги, розганяє кварцові генератори та фіксує фазу помножувача частоти PLL, спалюючи енергетичний заряд батареї в рази швидше, ніж корисні прикладні алгоритми.

### Інваріант активного процесора: чому планувальнику потрібна задача простою

Будь-яка витісняюча операційна система реального часу спирається на фундаментальний архітектурний інваріант: у домені ядра процесора в будь-який момент часу мусить виконуватися хоча б одна активна задача. Диспетчер контексту планувальника не здатний працювати з порожнім вказівником: змінна `pxCurrentTCB` (вказівник на блок керування поточною задачею, *Task Control Block*) ніколи не може дорівнювати `NULL`.

Коли в системі виникає переривання перемикання контексту (наприклад, виняток `PendSV` в архітектурі ARM Cortex-M), апаратне забезпечення та низькорівневий асемблерний обробник виконують фіксовану послідовність збереження стану:
1. Апаратний блок процесора автоматично скидає базовий набір регістрів (`R0`–`R3`, `R12`, `LR`, `PC`, `xPSR`) у стек поточної задачі, на який вказує покажчик процесорного стеку `PSP` (*Process Stack Pointer*).
2. Ядерний обробник планувальника домахує програмні регістри (`R4`–`R11`, а за наявності плаваючої крапки — розширений блок `FPU`), після чого зберігає поточне значення `PSP` безпосередньо у перше поле структури `pxCurrentTCB`.
3. Планувальник обирає найвищу за пріоритетом готову задачу зі списків `pxReadyTasksLists`, записує її адресу в `pxCurrentTCB`, вичитує новий покажчик стеку та відновлює регістровий стан.

Якби в момент, коли всі прикладні задачі перейшли у стан `Blocked` (очікування таймаутів, семафорів або повідомлень із черг), планувальник не мав задачі для виконання, спроба збереження або відновлення контексту через нульовий покажчик призвела б до розіменування адреси `0x00000000` і миттєвого апаратного збою `HardFault` або `MemManage Fault`.

Щоб виключити цю ситуацію, під час запуску планувальника функцією `vTaskStartScheduler()` операційна система автоматично створює спеціальну фонову задачу — **Idle Task** (`prvIdleTask`). Вона має найнижчий можливий пріоритет у системі:

```c
#define tskIDLE_PRIORITY ((UBaseType_t)0U)
```

Задача простою отримує власний мінімальний стек розміром `configMINIMAL_STACK_SIZE` слів і поміщається у список готових задач `pxReadyTasksLists[0]`. Оскільки її пріоритет дорівнює нулю, будь-яка прикладна задача з пріоритетом 1 або вище миттєво витісняє Idle Task, як тільки стає готовою до роботи. Коли ж у системі панує повний штиль, планувальник завжди знаходить у списку задачу простою і передає керування їй.

### Внутрішній цикл `prvIdleTask`: обов'язки «задачі, що нічого не робить»

Назва «задача простою» створює хибне враження, нібито весь її код зводиться до порожнього нескінченного циклу `while(1)`. На практиці `prvIdleTask` виконує життєво важливі обов'язки з підтримки цілісності динамічної пам'яті ядра, координації низькопріоритетних процесів та переводу апаратного кристала в енергозберігаючий стан.

Детальний перелік сигнатур функцій, конфігураційних макросів та параметрів хуків наведено у вставці [Довідник системних контрактів та інтерфейсів енергозбереження](root:sf-tasks/son-pid-rtos/api-tickless-idle-contracts.md).

Розглянемо послідовність кроків, які виконуються всередині нескінченного циклу `prvIdleTask`:

```c
static portTASK_FUNCTION(prvIdleTask, pvParameters)
{
    (void)pvParameters;

    for (;;)
    {
        // 1. Звільнення динамічної пам'яті видалених задач
        prvCheckTasksWaitingTermination();

        #if (configUSE_PREEMPTION == 1)
        {
            // 2. Кооперативна поступка часу задачам однакового пріоритету
            #if (configIDLE_SHOULD_YIELD == 1)
            {
                if (listCURRENT_LIST_LENGTH(&(pxReadyTasksLists[tskIDLE_PRIORITY])) > (UBaseType_t)1)
                {
                    taskYIELD();
                }
            }
            #endif
        }
        #endif

        #if (configUSE_IDLE_HOOK == 1)
        {
            // 3. Виклик користувацького зворотного виклику
            vApplicationIdleHook();
        }
        #endif

        #if (configUSE_TICKLESS_IDLE != 0)
        {
            // 4. Розрахунок інтервалу простою та безтиковий сон
            TickType_t xExpectedIdleTime = prvGetExpectedIdleTime();

            if (xExpectedIdleTime >= configEXPECTED_IDLE_TIME_BEFORE_SLEEP)
            {
                vTaskSuspendAll();
                {
                    if (prvGetExpectedIdleTime() >= configEXPECTED_IDLE_TIME_BEFORE_SLEEP)
                    {
                        portSUPPRESS_TICKS_AND_SLEEP(xExpectedIdleTime);
                    }
                }
                (void)xTaskResumeAll();
            }
        }
        #else
        {
            // 5. Звичайне низькорівневе очікування переривання
            portTASK_FUNCTION_ENTER_LOW_POWER_MODE(); // Типово виконує __WFI()
        }
        #endif
    }
}
```

#### 1. Очищення пам'яті та механізм `prvCheckTasksWaitingTermination`

Коли задача створюється динамічно функцією `xTaskCreate()`, планувальник виділяє з купи FreeRTOS два блоки пам'яті: структуру керування `TCB_t` та масив під стек задачі. Коли задача завершує свою роботу, вона має бути видалена викликом `vTaskDelete()`.

Якщо задача видаляє іншу задачу (`vTaskDelete(xOtherTaskHandle)`), процес вивільнення ресурсів тривіальний: викликаюча задача вилучає цільовий TCB з усіх черг планувальника й негайно повертає його пам'ять у купу викликом `vPortFree()`.

Проте найпоширенішим патерном є самовидалення задачі:

```c
void vWorkerTask(void *pvParameters)
{
    // Виконання одноразової роботи...
    vTaskDelete(NULL); // Самовидалення
}
```

У цій точці виникає апаратний парадокс: задача, що виконує інструкції функції `vTaskDelete(NULL)`, фізично використовує власний процесорний стек для зберігання локальних змінних, адрес повернення та контексту виклику. Вона не може викликати `vPortFree(pxCurrentTCB->pxStack)` і видалити свій стек з купи прямо зараз, оскільки наступні асемблерні інструкції самої функції `vPortFree` мають виконуватися на цьому ж самому стеку! Якби пам'ять стеку була позначена як вільна, будь-яке асинхронне переривання або паралельна алокація миттєво перезаписали б стек виконуваного коду, спричинивши хаотичне руйнування пам'яті.

![Самовидалення задач і пастка голодування Idle Task](/root/eng/sf-tasks/son-pid-rtos/img/idle-memory-starvation.svg)
*Механіка самовидалення задач у FreeRTOS: перенесення TCB у список очікування термінації та небезпека виснаження купи в разі позбавлення Idle Task процесорного часу.*

Рішення FreeRTOS полягає у відкладеному звільненні:
1. `vTaskDelete(NULL)` вилучає поточну задачу зі списку `pxReadyTasksLists` і додає її в спеціальний ядерний список `xTasksWaitingTermination`.
2. Планувальник примусово ініціює витіснення контексту (`portYIELD_WITHIN_API()`).
3. Коли процесор нарешті стає вільним і керування переходить до `prvIdleTask`, функція `prvCheckTasksWaitingTermination()` інспектує список видалених потоків.
4. Оскільки `prvIdleTask` виконується на власному незалежному стеку, вона безпечно викликає `vPortFree()` для структури `TCB` та стекового масиву кожної видаленої задачі, остаточно повертаючи пам'ять у систему.

#### Небезпека голодування задачі простою (Idle Task Starvation)

З цього механізму випливає критично важливе правило архітектури вбудованих систем: **якщо застосунок динамічно створює і самовидаляє задачі, задачі вищих пріоритетів обов'язково повинні періодично блокуватися, віддаючи кванти часу задачі Idle Task.**

Якщо в системі є хоча б одна задача з пріоритетом `>= 1`, яка перебуває в нескінченному обчислювальному циклі без викликів затримок чи очікування подій (`vTaskDelay`, `xQueueReceive`), планувальник ніколи не передасть керування на рівень пріоритету 0. Як наслідок, список `xTasksWaitingTermination` буде безконтрольно розростатися з кожною завершеною задачею. За кілька годин або діб безперервної роботи купа мікроконтролера буде повністю вичерпана «зомбі-стеками», а черговий виклик `pvPortMalloc()` поверне `NULL`, спричинивши аварійне падіння прошивки.

#### 2. Кооперативні поступки: `configIDLE_SHOULD_YIELD`

Якщо розробник створює власні низькопріоритетні задачі з пріоритетом `tskIDLE_PRIORITY` (0), вони ділять процесорний час із задачею Idle Task. За замовчуванням у FreeRTOS увімкнено квантування часу (Time Slicing): задачі однакового пріоритету виконуються почергово, змінюючи одна одну з кожним системним тиком.

Проте якщо макрос `configIDLE_SHOULD_YIELD` встановлено в `1`, задача Idle Task поводиться максимально ввічливо: якщо в списку готових задач нульового пріоритету присутня користувацька задача, Idle Task після виконання очищення пам'яті негайно віддає залишок свого мілісекундного кванту через виклик `taskYIELD()`. Це гарантує, що фонові задачі користувача отримають максимум процесорного часу без затримок на системні очікування ядра.

#### 3. Користувацький хук: `vApplicationIdleHook`

Якщо в конфігурації активовано макрос `configUSE_IDLE_HOOK == 1`, на кожній ітерації циклу простою викликається функція `vApplicationIdleHook()`. Це офіційне вікно для виконання непридатних до реального часу фонових операцій:
- Фонове обчислення контрольних сум (CRC32) секторів Flash-пам'яті для виявлення деградації кремнію.
- Скидання апаратного сторожового таймера (Watchdog), якщо всі критичні підсистеми відзвітували про працездатність.
- Підрахунок статистики завантаження центрального процесора (через інкремент фонового 64-бітного лічильника).
- Збір та утилізація внутрішніх діагностичних логів.

> ⚠️ **Залізне обмеження хука простою.** Функція `vApplicationIdleHook()` ні за яких обставин не має права викликати функції RTOS API, які можуть призвести до переходу в стан `Blocked` (наприклад, `vTaskDelay()`, `xQueueReceive()` із ненульовим таймаутом, `xSemaphoreTake()` із очікуванням). Якщо задача Idle заблокується, планувальник втратить єдину готову задачу в системі, порушить інваріант непорожнього `pxCurrentTCB` і викличе Kernel Panic через розрив ланцюжка диспетчеризації.

### Ціна системного серцебиття: чому 1000 Гц вбивають батарею

Коли розробник не налаштовує глибокі режими сну, стандартна задача простою виконує найпростішу інструкцію зупинки ядра:

```c
#define portTASK_FUNCTION_ENTER_LOW_POWER_MODE() __WFI()
```

Інструкція `__WFI()` (*Wait For Interrupt*) переводить процесорне ядро ARM Cortex-M у базовий режим **Sleep**. У цьому режимі конвеєр інструкцій процесора зупиняється, але всі внутрішні високочастотні генератори (HSI, HSE), помножувачі PLL, шини AHB/APB та периферійні контролери продовжують тактуватися на повній робочій частоті (наприклад, 80 МГц).

![Спектр енергозберігаючих режимів та поведінка тактування](/root/eng/sf-tasks/son-pid-rtos/img/sleep-modes-spectrum.svg)
*Порівняння енергетичних станів мікроконтролера: співвідношення споживання струму, стану тактових генераторів, збереження вмісту SRAM та часу відновлення системи.*

Порівняємо струми споживання сучасного енергоефективного мікроконтролера (STM32L4, Silicon Labs EFM32 або NXP Kinetis) у різних апаратних станах:

```
Режим Run (80 МГц, ядро активне, виконання з Flash):    12.0 – 20.0 мА
Режим Sleep (WFI, ядро стоїть, PLL/HSI активні):         2.5 –  5.0 мА
Режим Stop 1/2 (Deep Sleep, PLL/HCLK вимкнено, LSE/LPTIM): 1.2 –  2.0 мкА
Режим Standby (живлення ядра знято, лише Backup RTC):   0.3 –  0.8 мкА
```

Різниця між неглибоким сном Sleep (до якого призводить звичайний `__WFI()`) та глибоким сном Stop становить понад три порядки величини (у 2000–3000 разів).

Чому процесор не може просто увійти в режим глибокого сну Stop всередині задачі Idle при звичайній роботі RTOS?

Головна перешкода — системний таймер **SysTick**. Він є невіддільною частиною ядра Cortex-M і тактується від основної системної шини процесора `HCLK`. Перехід у режим Stop вимагає повної зупинки основних високочастотних генераторів та переведення внутрішнього стабілізатора напруги (LDO/SMPS) у режим наднизького споживання. Щойно зупиняється `HCLK`, таймер SysTick завмирає. Якщо операційна система засне в Stop-режимі зі зупиненим SysTick, вона назавжди втратить хід системного часу `xTickCount` і ніколи не зможе самостійно прокинутися для запуску заблокованих задач.

#### Енергетичний рахунок пробуджень

Навіть якщо ядро намагається заснути в режимі Stop на короткі проміжки між тиками SysTick (1 мс), кожне пробудження процесора супроводжується значними динамічними втратами на перехідні процеси:

1. **Пробудження стабілізатора напруги:** Внутрішній регулятор перемикається з мікропотужного стану Low-Power Regulator у високопродуктивний Main Regulator (затримка 5–15 мкс).
2. **Розгін тактових генераторів та PLL:** Внутрішній швидкісний RC-генератор (HSI16) або кварцовий резонатор (HSE) потребує часу на вихід на стабільну амплітуду. Схема помножувача PLL вимагає від 40 до 100 мкс для захоплення фази та стабілізації частоти 80 МГц. У цей інтервал схема вже споживає струм 8–12 мА, хоча процесорне ядро ще заблоковане апаратною логікою скидання тактування.
3. **Виконання інструкцій ISR:** Процесор витрачає 2–4 мкс на вхід у виняток SysTick, інкремент лічильника `xTickCount`, перевірку списку заблокованих задач і повернення у стан сну.

Сумарна тривалість перехідного процесу та виконання обробника складає близько `t_wake = 100 мкс` при середньому струмі `I_wake = 10 мА`.

Розрахуємо заряд, що витрачається на одне порожнє пробудження:

```
Q_wake = I_wake · t_wake
       = 10 мА · 100 мкс
       = 1 мкКл                [заряд одного порожнього циклу пробудження]
```

При частоті системного тику `f_tick = 1000 Гц` сумарний середній струм споживання мікроконтролера становить:

```
I_avg = Q_wake · f_tick + I_stop
      = 1 мкКл · 1000 с⁻¹ + 1.5 мкА
      = 1.000 мА + 0.0015 мА
      = 1.0015 мА             [середній струм у режимі очікування]
```

Замість розрахункових 1.5 мкА пристрій безперервно споживає 1 мА. Для дискового елемента живлення CR2032 ємністю 225 мА·год це означає катастрофічне падіння терміну служби:

```
T_life = 225 мА·год / 1.0015 мА
       = 224.6 години
       ≈ 9.3 доби              [реальний термін служби замість 4 років]
```

Саме тому концепція регулярного періодичного тактування непридатна для автономних пристроїв тривалої дії.

### Архітектура Tickless Idle: рівні конфігурації та розрахунок інтервалу

Вирішенням проблеми є безтиковий режим очікування — **Tickless Idle Mode**. Його ідея полягає у відмові від фіксованого періодичного переривання під час простою системи. Якщо всі задачі заблоковані на відомий час, операційній системі немає потреби прокидатися щомілісекунди. Замість цього планувальник обчислює точний час до найближчого дедлайну, зупиняє системний таймер SysTick, налаштовує низькоспоживаючий периферійний таймер на один довгий інтервал і занурює мікроконтролер у режим Stop.

У FreeRTOS поведінка безтикового режиму задається конфігураційним макросом `configUSE_TICKLESS_IDLE`:

#### `configUSE_TICKLESS_IDLE == 0` (Вимкнено)
Класичний режим роботи. Генератор SysTick працює безперервно. Задача Idle Task виконує базову інструкцію `__WFI()`, споживаючи міліампери в неглибокому стані Sleep.

#### `configUSE_TICKLESS_IDLE == 1` (Вбудований порт ARM Cortex-M)
Штатна реалізація ядра FreeRTOS для процесорів Cortex-M (`vPortSuppressTicksAndSleep` у файлі `port.c`). Працює виключно на базі вбудованого 24-бітного таймера SysTick:
- Планувальник перепрограмовує регістр перезавантаження SysTick на розраховану кількість тактів (максимум до ємності 24 біт, тобто `2^24 / 80 МГц ≈ 209 мс`).
- Процесор занурюється в неглибокий сон Sleep (WFI).
- Головне обмеження: оскільки SysTick зупиняється в Stop-режимі, цей режим не дозволяє перевести мікроконтролер у глибокий сон зі споживанням 1.5 мкА. Він заощаджує енергію на усуненні виконання інструкцій обробника тику, але струм залишається на рівні 2–4 мА.

#### `configUSE_TICKLESS_IDLE == 2` (Користувацький низькоспоживаючий режим)
Професійний режим для автономних систем. Ядро FreeRTOS повністю вимикає стандартний код обробки простою і передає керування користувацькій функції:

```c
extern void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime);
```

У цій функції розробник отримує повний контроль над апаратурою: зупиняє SysTick, запускає апаратний низькоспоживаючий таймер **LPTIM** (*Low-Power Timer*) або **RTC**, тактований від зовнішнього кварцового генератора 32.768 кГц (**LSE**), і переводить кристал у повноцінний режим глибокого сну **Stop 1/2** або **Deep Sleep**.

#### Алгоритм розрахунку очікуваного часу сну

Коли планувальник перемикається на задачу простою, функція `prvGetExpectedIdleTime()` інспектує список заблокованих задач `pxDelayedTaskList`. Усі заблоковані задачі в цьому списку впорядковані за зростанням абсолютного системного часу їхнього пробудження.

Очікуваний час простою `xExpectedIdleTime` (у системних тактах) обчислюється як різниця між дедлайном першої задачі в списку та поточним значенням лічильника часу:

```c
xExpectedIdleTime = xNextTaskUnblockTime - xTickCount;
```

Якщо жодна задача в системі не очікує на кінцевий таймаут (наприклад, усі потоки заблоковані на семафорах без обмеження часу `portMAX_DELAY` або переведені у стан `Suspended`), функція повертає максимальне значення типу `TickType_t` (для 32-бітних систем — `0xFFFFFFFF`).

#### Поріг доцільності сну `configEXPECTED_IDLE_TIME_BEFORE_SLEEP`

Вхід у режим глибокого сну та вихід із нього мають фіксовану апаратну ціну за часом та енергією. Якщо найближча задача має прокинутися вже через 1 або 2 системні такти (1–2 мс), накладні витрати на налаштування периферійних таймерів, маскування переривань і розгін генератора PLL виявляться більшими, ніж зекономлена за 1 мс енергія.

Щоб запобігти збитковим мікропереходам, FreeRTOS використовує конфігураційний поріг:

```c
#define configEXPECTED_IDLE_TIME_BEFORE_SLEEP 3
```

Якщо `xExpectedIdleTime < configEXPECTED_IDLE_TIME_BEFORE_SLEEP`, планувальник не викликає функцію глибокого придушення тактів, а обмежується звичайним коротким очікуванням `__WFI()`.

### Атомарність, стан перегонів та апаратна поведінка `__WFI`

Найтоншим моментом реалізації безтикового режиму є запобігання стану перегонів (Race Condition) між рішенням ядра заснути та надходженням зовнішньої апаратної події.

Розглянемо небезпечний сценарій за відсутності належного блокування переривань:
1. Задача Idle Task перевіряє стан планувальника й обчислює час сну `xExpectedIdleTime = 5000` (5 секунд).
2. За мікросекунду до виконання інструкції сну апаратний компаратор або радіомодуль генерує зовнішнє переривання.
3. Контролер переривань негайно призупиняє виконання коду Idle Task і передає керування в обробник `EXTI_IRQHandler`.
4. Обробник переривання надсилає семафор критично важливій задачі обробки аварії (`xSemaphoreGiveFromISR`), переводячи її зі стану `Blocked` у стан `Ready`.
5. Обробник переривання завершується. Процесор повертається до перерваного коду задачі Idle Task.
6. Idle Task, не підозрюючи про появу готової задачі, спокійно виконує інструкцію глибокого сну `__WFI()` і засинає на 5 секунд!
7. Термінова задача аварійного захисту зависає в очікуванні процесора на 5 секунд, що для системи реального часу є фатальною відмовою.

#### Як розв'язується конфлікт: маскування переривань і прапорець Pending

Щоб унеможливити цей стан перегонів, підготовка до сну обов'язково виконується всередині критичної секції з глобально замаскованими перериваннями ядра процесора:

```c
__disable_irq(); // Встановлення біта PRIMASK або BASEPRI в ядрі ARM Cortex-M
__DSB();         // Data Synchronization Barrier: завершення всіх транзакцій пам'яті
__ISB();         // Instruction Synchronization Barrier: скидання конвеєра інструкцій
```

Після маскування переривань викликається ядерна функція перевірки:

```c
eSleepModeStatus eTaskConfirmSleepModeStatus(void);
```

Якщо під час попередніх обчислень якась задача була розблокована, функція поверне статус `eAbortSleep`. У цьому випадку хук сну зобов'язаний негайно перезапустити SysTick, увімкнути переривання викликом `__enable_irq()` і вийти, дозволивши планувальнику миттєво передати процесор готовій задачі.

#### Апаратна поведінка Cortex-M при виконанні `__WFI`

Тут виникає природне запитання: якщо ми виконали `__disable_irq()` і замаскували переривання, як мікроконтролер взагалі зможе прокинутися від таймера або зовнішнього датчика під час виконання `__WFI()`?

> 🔧 **Фундаментальний апаратний контракт Cortex-M.** Архітектура ARM Cortex-M спеціально спроєктована для безпечного переходу в сон. Коли переривання замасковані через `PRIMASK = 1` або `BASEPRI`, контролер переривань NVIC **продовжує апаратно фіксувати вхідні сигнали периферії**. 
> 
> Як тільки на лінію переривання надходить сигнал, NVIC виставляє відповідний біт у регістрі очікування (Pending Register) і генерує внутрішній сигнал пробудження ядра (Wakeup Event). Інструкція `__WFI()` **негайно розблоковує конвеєр процесора**, і ядро продовжує послідовне виконання наступної інструкції коду! Проте сам вектор обробника переривання (ISR) **не викликається**, оскільки глобальні переривання все ще замасковані.

Це дозволяє програмі абсолютно надійно виконати таку послідовність:
1. Замаскувати переривання (`__disable_irq()`).
2. Перевірити, що немає готових задач (`eTaskConfirmSleepModeStatus()`).
3. Налаштувати таймер LPTIM і виконати `__WFI()`.
4. Якщо переривання виникло до `__WFI()`, прапорець Pending вже встановлено: інструкція `__WFI()` виконається як порожня операція NOP, не вводячи ядро в сон.
5. Якщо переривання прийшло під час сну, ядро прокидається й продовжує виконання коду хука.
6. Хук спочатку відновлює частоту PLL, зчитує фактичний час сну, компенсує системний час RTOS через `vTaskStepTick()`, перезапускає SysTick, і лише наприкінці викликає `__enable_irq()`.
7. Щойно переривання демаскуються, NVIC негайно передає керування в обробник ISR. Оскільки системний час RTOS на цей момент вже повністю актуалізований, будь-які виклики `FromISR` коректно взаємодіють із планувальником.

### Синхронізація часу: планове та асинхронне пробудження

Під час перебування у глибокому безтиковому сні можливі два принципово різні сценарії виходу системи з енергозберігаючого режиму.

![Синхронізація системного часу RTOS у режимі Tickless Idle](/root/eng/sf-tasks/son-pid-rtos/img/tickless-timing-sync.svg)
*Два сценарії відновлення системного часу RTOS: планове пробудження за таймаутом лічильника LPTIM та передчасне пробудження асинхронною подією зовнішнього датчика.*

#### Сценарій А: Планове пробудження за таймаутом LPTIM

Якщо під час очікування жодних зовнішніх подій не сталося, низькоспоживаючий таймер LPTIM відраховує запрограмовані йому `N` тактів і генерує переривання переповнення/порівняння:
1. Ядро прокидається зі стану Stop.
2. Хук відновлює високочастотні тактові генератори (HSE/PLL).
3. Оскільки сон тривав повний запланований строк `N` тактів, системний лічильник RTOS відстає від реального астрономічного часу рівно на `N` одиниць.
4. Хук викликає функцію компенсації часу:
   ```c
   vTaskStepTick(xExpectedIdleTime);
   ```
5. Лічильник SysTick скидається в 0 і запускається.
6. Переривання відкриваються викликом `__enable_irq()`. Планувальник оцінює черги таймаутів: оскільки `xTickCount` збільшився на `N`, дедлайн першої заблокованої задачі настав. Задача вилучається зі списку заблокованих і переходить до виконання.

#### Сценарій Б: Передчасне асинхронне пробудження

У реальних вбудованих пристроях мікроконтролер часто прокидається раніше запланованого строку `N`. Наприклад, спрацював пороговий сигнал переривання акселерометра на лінії GPIO (EXTI), надійшов байт по інтерфейсу UART або спрацював таймер аварійного датчика.

У цьому випадку зовнішнє переривання виводить ядро з режиму Stop у момент часу `M < N` (наприклад, планувалося спати 5000 мс, а кнопка була натиснута через 1200 мс).

Якщо в цьому випадку помилково викликати `vTaskStepTick(5000)`, системний час RTOS миттєво стрибне на 5 секунд уперед. Це призведе до фальшивого дострокового спрацьовування всіх системних таймерів, затримок та таймаутів мережевих протоколів!

Тому хук виконує прецизійну процедуру вимірювання фактично прожитого часу:
1. Зупиняється рахунок периферійного таймера LPTIM.
2. Зчитується поточне значення його апаратного лічильника `LPTIM_CNT`.
3. Розраховується кількість повних системних тактів RTOS, які система фактично провела в режимі сну:
   ```c
   uint32_t ulActualTicks = (ulElapsedLPTIMCounts * configTICK_RATE_HZ) / LPTIM_COUNTS_PER_SEC;
   ```
4. Здійснюється крок часу строго на фактичну величину:
   ```c
   vTaskStepTick(ulActualTicks);
   ```
5. Запускається SysTick, відкриваються переривання.
6. Процесор негайно заходить в обробник зовнішнього переривання (наприклад, `EXTI0_IRQHandler`), передає дані в прикладну задачу, а системний час залишається ідеально точним і монотонним.

### Повна реалізація користувацького безтикового керування на C та C++

Нижче наведено повну, перевірену на практиці реалізацію підсистеми Tickless Idle для мікроконтролера STM32L4 (ARM Cortex-M4, 80 МГц) з використанням таймера LPTIM1, що тактується від кварцового генератора LSE 32.768 кГц.

Код представлено у двох взаємодоповнюючих стилях: низькорівневий процедурний C (класичний стиль портів FreeRTOS) та сучасний об'єктно-орієнтований C++20 із застосуванням RAII для блокування переривань, строго типізованих констант та шаблонних контролерів живлення.

:::tabs
```c
#include "FreeRTOS.h"
#include "task.h"
#include "stm32l4xx.h"

// Параметри низькочастотного тактування
#define LSE_FREQUENCY_HZ            32768UL
#define LPTIM_PRESCALER_DIV         32UL
#define LPTIM_COUNTS_PER_SECOND     (LSE_FREQUENCY_HZ / LPTIM_PRESCALER_DIV) // 1024 Гц

// Розрахунок максимального допустимого інтервалу сну (16-бітний лічильник LPTIM)
#define LPTIM_MAX_COUNTS            0xFFFFUL
#define MAXIMUM_SUPPRESSED_TICKS    ((LPTIM_MAX_COUNTS * configTICK_RATE_HZ) / LPTIM_COUNTS_PER_SECOND)

// Апаратна компенсація часу пробудження стабілізатора й PLL (у тактах LPTIM)
#define WAKEUP_OVERHEAD_LPTIM_TICKS 3UL

// Прототип функції відновлення тактового дерева після виходу з режиму Stop 1
extern void SystemClock_RestoreAfterStop(void);

void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime)
{
    uint32_t ulLPTIMTargetCounts;
    uint32_t ulCompletedSysTicks;
    uint32_t ulLPTIMElapsedCounts;
    eSleepModeStatus eSleepStatus;

    // 1. Обмежуємо час сну максимальною розрядністю 16-бітного апаратного таймера
    if (xExpectedIdleTime > MAXIMUM_SUPPRESSED_TICKS)
    {
        xExpectedIdleTime = MAXIMUM_SUPPRESSED_TICKS;
    }

    // 2. Зупиняємо SysTick, щоб унеможливити переривання під час налаштувань
    SysTick->CTRL &= ~SysTick_CTRL_ENABLE_Msk;

    // 3. Обчислюємо цільову кількість імпульсів LPTIM із врахуванням апаратної затримки
    ulLPTIMTargetCounts = (xExpectedIdleTime * LPTIM_COUNTS_PER_SECOND) / configTICK_RATE_HZ;
    if (ulLPTIMTargetCounts > WAKEUP_OVERHEAD_LPTIM_TICKS)
    {
        ulLPTIMTargetCounts -= WAKEUP_OVERHEAD_LPTIM_TICKS;
    }
    else
    {
        ulLPTIMTargetCounts = 1UL;
    }

    // 4. Входимо в критичну секцію ядра (маскуємо переривання)
    __disable_irq();
    __DSB();
    __ISB();

    // 5. Переконуємося, що планувальник все ще дозволяє перехід у сон
    eSleepStatus = eTaskConfirmSleepModeStatus();
    if (eSleepStatus == eAbortSleep)
    {
        // З'явилася готова задача: відновлюємо SysTick і негайно виходимо
        SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
        __enable_irq();
        return;
    }

    // 6. Програмуємо таймер LPTIM1 в однократному режимі (Single Mode)
    LPTIM1->CR |= LPTIM_CR_ENABLE;
    LPTIM1->ICR = LPTIM_ICR_ARRMCF | LPTIM_ICR_CMPMCF; // Очищення попередніх прапорців
    LPTIM1->ARR = ulLPTIMTargetCounts;
    LPTIM1->IER |= LPTIM_IER_ARRMIE;                    // Дозвіл переривання за автоперезавантаженням
    LPTIM1->CR |= LPTIM_CR_SNGSTRT;                     // Старт відліку

    // 7. Налаштовуємо енергозберігаючий стан Stop 1 у контролері PWR
    PWR->CR1 = (PWR->CR1 & ~PWR_CR1_LPMS) | PWR_CR1_LPMS_STOP1;
    SCB->SCR |= SCB_SCR_SLEEPDEEP_Msk;                  // Біт глибокого сну ядра

    // 8. Перехід у глибокий енергозберігаючий сон
    __WFI();

    // =========================================================================
    // ПРОБУДЖЕННЯ ЯДРА (від переривання LPTIM або зовнішньої периферії EXTI)
    // =========================================================================

    // 9. Скидаємо прапорець глибокого сну та відновлюємо тактову частоту 80 МГц PLL
    SCB->SCR &= ~SCB_SCR_SLEEPDEEP_Msk;
    SystemClock_RestoreAfterStop();

    // 10. Зчитуємо фактично відрахований час із регістра LPTIM_CNT.
    // Оскільки LPTIM працює від асинхронного генератора LSE, використовуємо подвійну вибірку
    uint32_t val1 = LPTIM1->CNT;
    uint32_t val2 = LPTIM1->CNT;
    while (val1 != val2)
    {
        val1 = val2;
        val2 = LPTIM1->CNT;
    }
    ulLPTIMElapsedCounts = val1;

    // Зупиняємо таймер LPTIM1
    LPTIM1->CR &= ~LPTIM_CR_ENABLE;

    // 11. Розраховуємо кількість повних системних тактів RTOS, проведених у сні
    ulCompletedSysTicks = ((ulLPTIMElapsedCounts + WAKEUP_OVERHEAD_LPTIM_TICKS) * configTICK_RATE_HZ)
                          / LPTIM_COUNTS_PER_SECOND;

    if (ulCompletedSysTicks > xExpectedIdleTime)
    {
        ulCompletedSysTicks = xExpectedIdleTime;
    }

    // 12. Компенсуємо системний час у планувальнику FreeRTOS
    vTaskStepTick(ulCompletedSysTicks);

    // 13. Перезапускаємо системний таймер SysTick
    SysTick->VAL = 0UL;
    SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;

    // 14. Відкриваємо глобальні переривання: накопичені переривання обробляються негайно
    __enable_irq();
}
```

```cpp
#include "FreeRTOS.h"
#include "task.h"
#include "stm32l4xx.h"
#include <cstdint>
#include <concepts>

namespace rtos::power {

// RAII-менеджер критичної секції ядра
class KernelInterruptLock {
public:
    KernelInterruptLock() noexcept {
        __disable_irq();
        __DSB();
        __ISB();
    }

    ~KernelInterruptLock() noexcept {
        __enable_irq();
    }

    KernelInterruptLock(const KernelInterruptLock&) = delete;
    KernelInterruptLock& operator=(const KernelInterruptLock&) = delete;
    KernelInterruptLock(KernelInterruptLock&&) = delete;
    KernelInterruptLock& operator=(KernelInterruptLock&&) = delete;
};

// Апаратний драйвер низькоспоживаючого таймера LPTIM1
class LowPowerTimer {
public:
    static constexpr std::uint32_t LseFrequencyHz = 32768UL;
    static constexpr std::uint32_t Prescaler = 32UL;
    static constexpr std::uint32_t CountsPerSec = LseFrequencyHz / Prescaler; // 1024 Гц
    static constexpr std::uint32_t MaxRawCounts = 0xFFFFUL;
    static constexpr std::uint32_t MaxSleepTicks = (MaxRawCounts * configTICK_RATE_HZ) / CountsPerSec;
    static constexpr std::uint32_t WakeupOverheadCounts = 3UL;

    static void init() noexcept {
        RCC->APB1ENR1 |= RCC_APB1ENR1_LPTIM1EN;
        LPTIM1->CFGR = LPTIM_CFGR_PRESC_2; // Дільник частоти /32
    }

    static void startTimeout(std::uint32_t counts) noexcept {
        LPTIM1->CR |= LPTIM_CR_ENABLE;
        LPTIM1->ICR = LPTIM_ICR_ARRMCF | LPTIM_ICR_CMPMCF;
        LPTIM1->ARR = counts;
        LPTIM1->IER |= LPTIM_IER_ARRMIE;
        LPTIM1->CR |= LPTIM_CR_SNGSTRT;
    }

    static std::uint32_t stopAndReadElapsedCounts() noexcept {
        // Подвійне зчитування для усунення метастабільності асинхронного домену LSE
        std::uint32_t sample1 = LPTIM1->CNT;
        std::uint32_t sample2 = LPTIM1->CNT;
        while (sample1 != sample2) {
            sample1 = sample2;
            sample2 = LPTIM1->CNT;
        }
        LPTIM1->CR &= ~LPTIM_CR_ENABLE;
        return sample1;
    }
};

// Контролер конфігурації енергозберігаючих режимів кристала
class PowerController {
public:
    static void configureStopMode() noexcept {
        PWR->CR1 = (PWR->CR1 & ~PWR_CR1_LPMS) | PWR_CR1_LPMS_STOP1;
        SCB->SCR |= SCB_SCR_SLEEPDEEP_Msk;
    }

    static void clearSleepDeep() noexcept {
        SCB->SCR &= ~SCB_SCR_SLEEPDEEP_Msk;
    }

    static void enterSleep() noexcept {
        __WFI();
    }
};

// Головний диспетчер безтикового режиму
class TicklessManager {
public:
    static void processSleep(TickType_t expectedIdleTicks) noexcept {
        const std::uint32_t boundedTicks = (expectedIdleTicks > LowPowerTimer::MaxSleepTicks)
            ? LowPowerTimer::MaxSleepTicks
            : static_cast<std::uint32_t>(expectedIdleTicks);

        // Зупиняємо системний таймер ядра
        SysTick->CTRL &= ~SysTick_CTRL_ENABLE_Msk;

        std::uint32_t targetCounts = (boundedTicks * LowPowerTimer::CountsPerSec) / configTICK_RATE_HZ;
        targetCounts = (targetCounts > LowPowerTimer::WakeupOverheadCounts)
            ? (targetCounts - LowPowerTimer::WakeupOverheadCounts)
            : 1UL;

        {
            KernelInterruptLock lock;

            if (eTaskConfirmSleepModeStatus() == eAbortSleep) {
                SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
                return;
            }

            LowPowerTimer::startTimeout(targetCounts);
            PowerController::configureStopMode();
            PowerController::enterSleep();

            // ЯДРО ПРОКИНУЛОСЯ
            PowerController::clearSleepDeep();
            SystemClock_RestoreAfterStop();

            const std::uint32_t elapsedCounts = LowPowerTimer::stopAndReadElapsedCounts();
            std::uint32_t completedTicks = ((elapsedCounts + LowPowerTimer::WakeupOverheadCounts) * configTICK_RATE_HZ)
                / LowPowerTimer::CountsPerSec;

            if (completedTicks > boundedTicks) {
                completedTicks = boundedTicks;
            }

            vTaskStepTick(completedTicks);

            SysTick->VAL = 0UL;
            SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
        }
    }
};

} // namespace rtos::power

extern "C" void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime) {
    rtos::power::TicklessManager::processSleep(xExpectedIdleTime);
}
```

### Інженерні тонкощі, крайові випадки та апаратні пастки

Створення надійного безтикового режиму на практиці вимагає врахування низки системних нюансів на стику мікроконтролерної схемотехніки та поведінки ядра.

#### 1. Налагодження через SWD під час глибокого сну
За замовчуванням при переході ядра процесора в стан Stop 1/2 мікроконтролер знеструмлює апаратний блок внутрішньосхемного налагодження CoreSight. Це призводить до миттєвого обриву зв'язку з апаратним програматором-налагоджувачем (ST-Link, J-Link) та зупинки налагоджувальної сесії.

Щоб зберегти можливість покрокового налагодження у сні, перед запуском планувальника активують спеціальні біти налагодження:

```c
DBGMCU->CR |= DBGMCU_CR_DBG_STOP | DBGMCU_CR_DBG_STANDBY;
```

> ⚠️ **Пастка вимірювання струму на стенді.** Увімкнені біти `DBG_STOP` забороняють апаратній частині вимикати внутрішні джерела опорної напруги під час інструкції `__WFI()`. Як наслідок, споживання кристала на стенді з підключеним налагоджувачем становитиме 1.5–2.5 мА замість 1.5 мкА. Для проведення контрольних вимірювань енергоспоживання біти `DBGMCU->CR` мають бути обнулені, а кабель SWD фізично від'єднаний від плати.

#### 2. Несумірність частот та накопичення похибки (Clock Drift)
Кварцовий резонатор LSE 32.768 кГц із апаратним дільником на 32 забезпечує частоту лічильника LPTIM рівно 1024 Гц. Якщо системний тик RTOS налаштований на класичну круглу частоту 1000 Гц (`configTICK_RATE_HZ = 1000`), один такт LPTIM триває:

```
T_lptim = 1 / 1024 с ≈ 0.9765625 мс
```

При перерахунку між шкалами виникає постійна похибка округлення близько 2.34%. Під час тривалих серій засинань по 5–10 секунд системний годинник RTOS помітно відставатиме від реального астрономічного часу.

Для усунення накопичення похибки застосовують один із двох підходів:
- **Апаратне узгодження частот:** Налаштування частоти тику FreeRTOS на `configTICK_RATE_HZ = 1024`. У цьому випадку співвідношення тактів стає строго цілочисельним `1:1`, а похибка зводиться до нульового рівня.
- **Дробовий акумулятор:** Ведення дробового залишку тактів у статичній змінній хука `vPortSuppressTicksAndSleep` та компенсація накопиченого цілого такту при переході залишку через одиницю.

#### 3. Висячі виводи GPIO та витоки струму
Найпоширеніша помилка схемотехніки автономних систем — залишення невикористаних виводів мікроконтролера в стані цифрового входу без підтяжки (Floating Input).

У режимі глибокого сну напруга на висячому виводі через перешкоди дрейфує в районі половини напруги живлення (VDD / 2). Це призводить до відкриття обох транзисторів вхідного КМОН-інвертора (тригера Шмітта) і виникнення наскрізного струму витоку від 50 до 200 мкА на кожен висячий пін. Десяток невдалих пінів здатні збільшити споживання в стані сну з 1.5 мкА до 2 мА.

Перед входом у безтиковий режим усі непідключені або невикористовувані виводи GPIO мають бути переведені в аналоговий режим високого опору:

```c
// Переведення пінів порту в аналоговий режим (найнижчий струм)
GPIOB->MODER = 0xFFFFFFFF;
```

#### 4. Тактування фонової периферії та робота DMA
Якщо в системі налаштовано фоновий прийом даних по UART або SPI через контролер прямого доступу до пам'яті (DMA), перехід у Stop Mode зупинить тактування шин APB/AHB, що призведе до втрати перших байтів вхідного пакета.

Для таких вузлів застосовують механізм Wakeup-on-Start-Bit: приймач UART перемикається на тактування від внутрішнього низькоспоживаючого генератора HSI16 і самостійно виводить мікроконтролер зі стану сну Stop при фіксації спадного фронту стартового біта на лінії `RX`.

### Підсумок

Фонова задача простою Idle Task та безтиковий режим Tickless Idle перетворюють операційну систему реального часу з марнотратного генератора мілісекундних переривань на високоефективну подійно-орієнтовану платформу. Звільнення динамічної пам'яті самовидалених задач утилізує ресурси без ризику руйнування стеків, атомарне маскування переривань усуває стан перегонів, а перемикання контролю часу на низькочастотний таймер LPTIM знижує енергоспоживання кристала у тисячі разів, забезпечуючи роки стабільної автономної служби від мініатюрної батареї.
