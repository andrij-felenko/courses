# 📜 Історія стандартизації розривного читання й розриву слів

Коли в 1990-х роках симетричні багатопроцесорні системи (SMP) вийшли з лабораторій суперкомп'ютерів на масовий серверний ринок, мови програмування не мали формального поняття паралельних потоків виконання. Компілятори C, C++ та середовище виконання ранньої Java вважали, що пам'ять належить єдиній послідовній програмі. Зіткнення 32-розрядних апаратних шин із 64-розрядними типами даних швидко перетворило апаратне розщеплення звернень на фундаментальну кризу комп'ютерних наук.

## Компроміс 1996 року: 64-бітні типи у специфікації Java

У першій версії специфікації мови Java (*Java Language Specification*, JLS 1.0, 1996 рік), створеній Джеймсом Ґослінгом і Біллом Джоєм, віртуальна машина Java (JVM) проектувалася з гарантією безпеки типів і пам'яті (*Memory Safety*). Програма на Java за жодних умов не повинна була отримувати доступ до довільних адрес або пошкоджувати внутрішні покажчики віртуальної машини.

Проте автори зіткнулися з жорстким апаратним обмеженням: більшість тогочасних масових процесорів — Intel Pentium, Sun SPARC, MIPS R4000 — мали 32-розрядні регістри загального призначення та 32-бітні шини даних. Виконання операцій над 64-розрядними цілими числами (`long`) і числами з рухомою комою подвійної точності (`double`) вимагало двох окремих машинних інструкцій навантаження (`load`) або збереження (`store`).

Якщо вимагати від віртуальної машини атомарності кожного читання й запису `long` та `double`, JIT-компілятори були б змушені обрамляти кожне звернення до звичайних полів важкими апаратними замками або шинними блокуваннями. Це знизило б швидкодію чисельних обчислень у два-чотири рази на всіх 32-бітних процесорах.

Розробники пішли на свідомий компроміс, зафіксований у параграфі JLS §17.7 (*Non-atomic Treatment of double and long*):

> «Для цілей моделі пам'яті Java окреме зчитування або запис не-volatile значення `long` або `double` розглядається як дві окремі операції: кожна над 32-бітною половиною. Якщо кілька потоків записують у таке поле без синхронізації, підсумкове значення може скластися з молодших 32 бітів одного запису та старших 32 бітів іншого».

Цей пункт узаконив апаратне розривне читання (*torn read*) у мові високого рівня заради продуктивності. Проте плата виявилася високою: розривне читання 64-розрядного покажчика об'єкта (коли Java згодом перейшла на 64-бітні архітектури або використовувала складені структури) могло породити фальшиву адресу й зруйнувати базову ізоляцію віртуальної машини.

## Проблема розриву слів та ревізія JSR-133

На початку 2000-х років дослідник Вільям П'ю (*William Pugh*) з Університету Меріленду виявив глибшу ваду початкової моделі пам'яті, яку назвав «розривом слів» (*word tearing*).

Проблема виникала при спробі паралельного запису в суміжні байти масиву `byte[]` або сусідні 8-бітні поля структури. 32-розрядний процесор не міг записати один окремий байт без зчитування всього 32-бітного машинного слова:

```
[ Потік 1: запис у byte[0] ]           [ Потік 2: запис у byte[1] ]
1. Читає 32 біти [0..3]                1. Читає 32 біти [0..3]
2. Модифікує byte[0]                   2. Модифікує byte[1]
3. Записує 32 біти назад               3. Записує 32 біти назад (перетирає byte[0]!)
```

У результаті Потік 2 випадково перезаписував сусідній байт `byte[0]`, у який паралельно писав Потік 1, хоча логічно змінні були абсолютно різними елементами.

Під керівництвом Вільяма П'ю, Дага Лі (*Doug Lea*) та Джеремі Менсона (*Jeremy Manson*) було створено робочу групу JSR-133 (*Java Memory Model and Thread Specification Revision*), яка повністю переписала модель пам'яті для Java 5.0 (2004 рік). Специфікація JSR-133 ввела суворе правило: апаратура та компілятор зобов'язані гарантувати відсутність розриву слів (*word tearing freedom*). Навіть якщо два поля мають розмір 1 байт, середовище зобов'язане забезпечити незалежність їхнього оновлення.

## Стандартизація C++11: Ганс Бем і принцип «потоки — це не бібліотека»

У світі мов C та C++ ситуація тривалий час залишалася ще драматичнішою. До стандарту C++11 (і C11) багатопотоковість реалізовувалася виключно зовнішніми бібліотеками, такими як POSIX Threads (`pthreads`) або Windows Win32 API. Компілятор взагалі не знав про існування інших потоків і вважав за законне переставляти чи вигадувати операції запису.

У 2004–2007 роках дослідник Ганс Бем (*Hans-J. Boehm*) опублікував низку фундаментальних праць, зокрема класичну статтю *«Threads Cannot be Implemented as a Library»* (2004) та пропозицію WG21 N2177. Бем показав, що компілятори C/C++, оптимізуючи код під одне ядро, породжують розривні записи й вигадані операції запису (*store tearing* та *speculative stores*).

Наприклад, компілятор міг розбити запис 32-бітної константи на дві 16-бітні інструкції, якщо це економило байти коду, або записати проміжне значення в спільну пам'ять із наступним відновленням.

Бем і комітет WG21 дійшли висновку: мова повинна мати формальну математичну модель пам'яті (*Memory Model*). Було обрано модель, що спирається на концепцію *Data Race Freedom* (DRF-SC):

1. Будь-який несинхронізований паралельний доступ, де хоча б один потік виконує запис, оголошується невизначеною поведінкою (*Undefined Behavior*, UB).
2. Для запобігання розривному читанню та розриву слів введено стандартизовані типи `std::atomic<T>` (C++) та `_Atomic` (C11).
3. Компілятору категорично заборонено вигадувати операції запису у змінні або дробити збереження атомарних типів.

На відміну від Java, яка з міркувань безпеки мусила гарантувати відсутність розриву об'єктів навіть для некоректно синхронізованих програм, C++11 поклав усю відповідальність за відсутність гонок даних на програміста через механізм UB, що дозволило зберегти максимальну глибину машинних оптимізацій.

## Ядро Linux: розкол між LKMM та абстракцією компілятора

Розробники ядра Linux на чолі з Лінусом Торвальдсом і Полом Маккенні (*Paul E. McKenney*) зайняли особливу позицію. Ядро Linux ніколи не спиралося на стандартизовані `_Atomic` з C11, оскільки ядро вимагало контролю над кожною асемблерною інструкцією та спиралося на неформальні властивості вирівняного доступу до процесора.

Торвальдс категорично заперечував проти передачі контролю над паралелізмом абстрактним оптимізаторам GCC і Clang. Проте з розвитком агресивних міжпроцедурних оптимізацій (LTO) компілятори почали «розривати» навіть звичайні вирівняні присвоєння у ядрі. Компілятор міг прочитати ту саму спільну комірку двічі замість одного разу (*load tearing* / *load fusing*) або розбити запис на частини.

Для захисту від розривного читання та непередбачуваних оптимізацій у ядрі Linux було стандартизовано макроси `READ_ONCE()` та `WRITE_ONCE()` (раніше `ACCESS_ONCE()`). Вони примусово приводять адресу до покажчика на `volatile`, забороняючи компілятору дробити або вигадувати звернення. Разом із формалізованою у 2018 році моделлю пам'яті ядра (*Linux Kernel Memory Model*, LKMM) це створило самостійну системну парадигму, що поєднує низькорівневу апаратну атомарність із захистом від прихованого розриву слів на рівні транслятора.
