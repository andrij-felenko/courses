Коли процесорне ядро записує 64-розрядне число `0x00000001_00000000` у спільну змінну пам'яті на системі з 32-розрядною шиною даних або над невирівняною адресою, фізичний контролер пам'яті не здатний передати всі вісім байтів за один такт. Апаратний блок навантаження та збереження (*Load/Store Unit*) вимушено розщеплює операцію на два послідовні 32-бітні шинні цикли: спершу записуються молодші чотири байти `0x00000000`, а в наступному такті — старші чотири байти `0x00000001`. Якщо в часовому проміжку між цими двома транзакціями інше процесорне ядро зчитує цю саму комірку, воно отримує оновлену молодшу половину та застарілу старшу половину, утворюючи в регістрах гібридне фантомне значення, яке ніколи не записувалося жодним потоком програми.

## Апаратна анатомія розривного доступу

Фізична природа розривного доступу коріниться в невідповідності між розрядністю програмного типу даних та шириною апаратного тракту передачі інформації.

Оперативна пам'ять і процесорні кеші організовані у вигляді матриць із фіксованою шириною шини зв'язку. Якщо розрядність регістра або шини даних дорівнює 32 бітам (4 байти), процесор фізично має 32 лінії даних (`D0..D31`). Будь-яка спроба опрацювати 64-розрядний тип `uint64_t` або покажчик подвійної розрядності змушує компілятор згенерувати дві незалежні інструкції переміщення даних.

Розглянемо покроковий стан пам'яті при паралельній роботі двох процесорних ядер:

```
Час   Ядро 0 (Письменник)           Пам'ять [addr+4 : addr+0]     Ядро 1 (Читач)
T0    Ініціалізація                 0x00000000_00000000           Очікує
T1    Запис молодших: MOV [addr], 0xFFFFFFFF  ->  0x00000000_FFFFFFFF   —
T2    [Зміна контексту шини]        0x00000000_FFFFFFFF           Читає молодші: MOV R0, [addr] (=0xFFFFFFFF)
T3    —                             0x00000000_FFFFFFFF           Читає старші: MOV R1, [addr+4] (=0x00000000)
T4    Запис старших: MOV [addr+4], 0x00000001 ->  0x00000001_FFFFFFFF   —
```

У момент часу T2–T3 Ядро 1 виконало зчитування посеред незавершеної транзакції Ядра 0. У результаті Ядро 1 отримало значення `0x00000000_FFFFFFFF` (число 4 294 967 295), тоді як початковим значенням був 0, а фінальним — 8 589 934 591 (`0x00000001_FFFFFFFF`). Програма зафіксувала хибний сплеск лічильника на 4 мільярди одиниць.

![Апаратний механізм розривного читання (Torn Read) на 32-бітній шині](/root/eng/sf-tasks/torn-reads/img/torn-read-bus-split.svg)
*Апаратний поділ 64-розрядного запису на дві 32-розрядні транзакції пам'яті створює часове вікно розриву, де паралельне зчитування захоплює гібридне значення.*

Розривний доступ проявляється у двох взаємодоповнювальних формах:

1. **Розривне читання (*Torn Read*):** Потік-читач виконує складене зчитування над змінною, яка одночасно змінюється іншим потоком, і фіксує суміш фрагментів старого й нового значень.
2. **Розривний запис (*Torn Write* або *Store Tearing*):** Два потоки-письменники одночасно виконують складений запис за однією адресою. Перший потік встигає записати молодше слово, після чого його випереджає другий потік і записує обидва слова, а потім перший потік дописує своє старше слово. У пам'яті залишається мутантний стан: молодша частина від другого письменника, а старша — від першого.

### Термінологічний апарат та етимологія

* **Розривне читання та запис (*torn read / torn write*)** — термін походить від дієслова англійської мови *to tear* (дієприкметник минулого часу *torn* — «розірваний, подертий»), яке сходить до давньоанглійського *teran* та прагерманського *\*teraną* («роздирати, рвати на шматки»). У системному програмуванні термін позначає порушення неподільності операції пам'яті, коли єдине значення розрізається на окремі фрагменти.
* **Розрив слова (*word tearing*)** — корінь *word* походить від прагерманського *\*wurdą* («слово, вислів»), що в комп'ютерній архітектурі стало назвою базової одиниці адресації регістрів (машинне слово). Описує явище, коли модифікація одного поля призводить до небажаного апаратного перезапису або пошкодження сусідніх байтів через блоковий характер шинного обміну.
* **Атомарність (*atomicity*)** — походить від давньогрецького прикметника *ἄтоμος* (*atomos* — «неподільний»), утвореного поєднанням заперечної частки *ἀ-* («не-») та дієслова *τέμνω* (*temnō* — «різати, розтинати»). У багатопотоковому середовищі означає властивість операції виконуватися цілісно — так, ніби вона відбувається миттєво в один неподільний момент часу відносно всіх інших ядер системи.
* **Вирівнювання (*alignment*)** — термін сформувався від давньофранцузького *aligner* («вишиковувати в пряму лінію»), що сходить до латинського *linea* («льняна нитка, лінія»). Означає кратність адреси змінної у байтах її власному фізичному розміру.
* **Спліт-лок (*split lock*)** — складений термін від середньоанглійського *split* («розколювати, ділити навпіл», запозиченого з середньонижньонімецького *splitten*) та давньоанглійського *loc* («замок, запор»). Позначає апаратний стан, коли блокування шини розщеплюється між двома лініями кешу.

## Розбіжності архітектур: 32 біти проти 64 бітів

Масштаб проблеми розривного читання безпосередньо залежить від розрядності системи команд (*Instruction Set Architecture*, ISA) та організації шин процесора.

### Архітектури x86-32 та класичний ARM32

На 32-розрядних процесорах сімейства x86 (IA-32) інструкції `MOV` працюють із 32-бітними регістрами `EAX`, `EBX`, `ECX`, `EDX`. Для запису 64-розрядного цілого числа компілятор GCC генерує пару інструкцій:

```
; Запис 64-бітного значення EDX:EAX за адресою [ebp-8] на x86-32
mov  DWORD PTR [ebp-8], eax   ; Запис молодших 32 бітів
mov  DWORD PTR [ebp-4], edx   ; Запис старших 32 бітів
```

Між цими двома командами процесор може отримати апаратне переривання (*IRQ*), виконати перемикання контексту операційної системи або надати шину пам'яті іншому ядру в симетричній багатопроцесорній конфігурації (*SMP*). Жодної апаратної гарантії нероздільності між двома інструкціями `MOV` не існує.

На архітектурі ARM32 (ARMv7-A) існує пара інструкцій `LDRD` (*Load Dual Register*) та `STRD` (*Store Dual Register*), які навантажують або зберігають пару 32-бітних регістрів (наприклад, `R0` і `R1`) за 64-розрядною адресою:

```
; Зчитування 64-бітного значення за адресою R2 в пару R0:R1
ldrd  r0, r1, [r2]
```

Незважаючи на те, що `LDRD`/`STRD` є однією асемблерною інструкцією, вона **не є атомарною** за замовчуванням. На рівні шини AXI (*Advanced eXtensible Interface*) або внутрішнього конвеєра ядра ARM інструкція `LDRD` транслюється у дві послідовні 32-бітні передачі. Більше того, якщо під час виконання `LDRD` виникає переривання або промах кешу (*cache miss*), процесор має право перервати виконання інструкції посередині. Атомарність `LDRD`/`STRD` гарантується лише на новіших ядрах з розширенням LPAE (*Large Physical Address Extension*) за умови, що адреса строго вирівняна на 8 байтів, а пам'ять позначена як кешована з когерентністю.

### Архітектури x86-64 та ARM64

На 64-розрядних процесорах регістри загального призначення мають ширину 64 біти (`RAX`, `RBX` у x86-64 або `X0..X30` в ARM64). Зчитування або запис 64-розрядного значення виконується єдиною машинною інструкцією:

```
; Архітектура x86-64
mov  rax, QWORD PTR [rdi]     ; 64-бітне зчитування вирівняного слова

; Архітектура ARM64
ldr  x0, [x1]                 ; 64-бітне зчитування з адреси X1
```

Проте перехід на 64-розрядну архітектуру усуває розривне читання **виключно за умови природного вирівнювання** даних у пам'яті.

## Перетин межі кеш-ліній та апаратні Split Locks

Сучасні процесори організовують підсистему кеш-пам'яті L1/L2 лініями фіксованого розміру — зазвичай 64 байти (512 бітів). Усі протоколи апаратної когерентності (MESI, MOESI, MESIF) оперують виключно цілими лініями кешу.

Якщо 64-розрядна змінна розташована за адресою, кратною 8 байтам (природне вирівнювання), вона гарантовано цілком укладається в межі однієї 64-байтової кеш-лінії:

```
Зсув адреси (байти): 0x00 ... 0x38 .. 0x3F | 0x40 ...
Кеш-лінія 0:         [  ...  |  8 байтів  ] |
Кеш-лінія 1:                                | [  ...  ]
```

Якщо ж розробник створив упаковану структуру даних (`__attribute__((packed))` або `alignas(1)`) чи виконав некоректне приведення покажчиків, змінна може перетнути межу між двома суміжними лініями кешу. Наприклад, 8-байтне число, розташоване за зсувом 61 байт від початку лінії, займає 3 байти в Кеш-лінії N та 5 байтів у Кеш-лінії N+1.

![Невирівняний доступ до пам'яті через межу кеш-ліній (Split Lock)](/root/eng/sf-tasks/torn-reads/img/unaligned-cache-line-split.svg)
*Розташування 64-розрядної змінної на стику двох 64-байтових ліній кешу L1 змушує контролер виконувати два окремі звернення до кешу або активувати важке шинне блокування.*

Коли процесор звертається до такої невирівняної змінної, виникають дві принципово різні апаратні поведінки залежно від типу доступу:

### 1. Неатомарний невирівняний доступ

Блок керування кешем розбиває одне звернення на два окремі мікроопераційні запити:
1. Запит до Кеш-лінії N для отримання байтів 61..63.
2. Запит до Кеш-лінії N+1 для отримання байтів 64..68.

Між цими двома мікроопераціями інше процесорне ядро може змінити стан другої кеш-лінії. Читач знову зазнає розривного читання (*torn read*), навіть працюючи на найсучаснішому 64-розрядному процесорі.

### 2. Атомарний невирівняний доступ (Split Lock)

Якщо програма намагається виконати атомарну інструкцію над адресою, що перетинає межу двох ліній кешу (наприклад, `LOCK CMPXCHG` на x86), процесор стикається з апаратним тупиком: протокол MESI не дозволяє захопити стан `Exclusive` або `Modified` для двох різних кеш-ліній одночасно через ризик виникнення взаємного блокування (*deadlock*) у контролері кешу.

Процесор змушений відмовитися від швидкого кеш-блокування (*Cache Line Lock*) і вдатися до апаратного шинного блокування — **Split Lock**:

1. Ядро CPU виставляє низькорівневий сигнал `#LOCK` на зовнішній системній шині або надсилає блокувальні пакети через магістралі Ultra Path Interconnect (UPI) чи AMD Infinity Fabric.
2. Системний контролер пам'яті заморожує будь-які транзакції для **всіх інших ядер процесора, сокетів і контролерів прямого доступу до пам'яті (DMA)** на час виконання обох звернень.
3. Затримка виконання операції зростає з 10–20 тактів до 300–1000 тактів (з одиниць наносекунд до сотень наносекунд).

Через катастрофічний вплив невирівняних блокувань на продуктивність сучасні версії ядра Linux (починаючи з версії 5.7) мають спеціальний механізм сповільнення або аварійного завершення процесів, що генерують split locks, який контролюється через файл `/proc/sys/kernel/split_lock_mitigate` або параметр завантаження ядра `split_lock_detect=fatal`.

На архітектурах RISC (ARM64, RISC-V) невирівняний атомарний доступ узагалі апаратно заборонений: спроба виконати `LDXR`/`STXR` над невирівняною адресою генерує апаратне виключення невідповідності вирівнювання (*Alignment Fault Exception*), що призводить до падіння програми з сигналом `SIGBUS`.

Детальний аналіз еволюції моделей пам'яті та комітетських дискусій навколо 64-бітних типів викладено в [Історія стандартизації розривного читання й розриву слів](root:sf-tasks/torn-reads/hist-word-tearing.md).

## Перетин межі сторінок пам'яті та системні виключення

Ще важчим крайовим випадком невирівняного доступу є перетин межі 4-кілобайтової віртуальної сторінки пам'яті (*Page Boundary Crossing*).

Якщо 64-розрядна змінна розташована за адресою `0x...FFF` (останній байт сторінки 0), її перші байти лежать у Сторінці 0, а решта — у Сторінці 1. У цьому випадку апаратний блок трансляції адрес (*Memory Management Unit*, MMU) стикається з подвійною складністю:

1. **Подвійний прохід таблиць сторінок (*Page Table Walk*):** Процесор змушений паралельно або послідовно транслювати дві різні віртуальні адреси у фізичні через буфер асоціативної трансляції (*TLB*).
2. **Розщеплена відмова сторінки (*Split Page Fault*):** Якщо Сторінка 0 завантажена в оперативну пам'ять, а Сторінка 1 скинута на диск у файл підкачки (*swap*) або захищена правами доступу, перша половина інструкції виконується успішно, після чого ядро операційної системи генерує виключення `#PF` (*Page Fault*) для другої половини. Конвеєр процесора змушений повністю відкотити стан регістра й повторити інструкцію після завантаження сторінки.

У багатопотоковому середовищі без синхронізації такий розщеплений доступ гарантовано призводить до тривалого часового розриву, протягом якого змінна перебуває у пошкодженому стані протягом мільйонів тактів CPU, поки диск або гіпервізор обробляє відмову сторінки.

## Явище розриву слів (Word Tearing)

Розривне читання виникає не лише тоді, коли змінна занадто велика для шини, але й тоді, коли кілька малих незалежних змінних розташовані занадто близько одна до одної.

Розглянемо структуру, що містить два незалежні 8-бітні поля:

:::tabs
```c
#include <stdint.h>

struct device_flags {
    uint8_t link_ready;   // Змінюється потоком мережевого стека
    uint8_t power_state;  // Змінюється потоком керування живленням
};
```
```cpp
#include <cstdint>

struct DeviceFlags {
    uint8_t link_ready;   // Змінюється потоком мережевого стека
    uint8_t power_state;  // Змінюється потоком керування живленням
};
```
:::

На ранніх процесорах RISC (таких як DEC Alpha 21064) апаратура взагалі не підтримувала інструкції побайтового запису (`store byte`). Процесор умів записувати в пам'ять виключно 32-бітні або 64-бітні вирівняні слова.

Щоб записати 1 байт у поле `link_ready`, компілятор генерував таку послідовність дій (*Read-Modify-Write* машинного слова):

1. Прочитати все 32-бітне слово, що містить обидва поля `link_ready` та `power_state`, у регістр CPU.
2. Поставити маску й змінити значення байта `link_ready` всередині регістра.
3. Записати все 32-бітне слово назад у пам'ять.

Якщо одночасно з цим інший потік на сусідньому ядрі виконував аналогічну послідовність для оновлення байта `power_state`, виникав класичний **розрив слова (*word tearing*)**: потік, який завершив свій запис останнім, випадково перезаписував і знищував нове значення сусіднього байта застарілими даними, прочитаними на кроці 1.

Сучасні компілятори та специфікації стандартів C11, C++11, Java та Rust категорично забороняють компілятору генерувати код із розривом слів для окремих змінних або полів структур, що мають виділені типи, вимагаючи використання апаратних побайтових інструкцій запису (`movb` на x86, `STRB` на ARM). Проте при використанні бітових полів (`unsigned int flag_a: 1; unsigned int flag_b: 1;`) розрив слів є неминучим на рівні мови, тому бітові поля категорично заборонено модифікувати з паралельних потоків без зовнішнього взаємного виключення (*mutex*).

## Формальна модель пам'яті: гонка даних як Undefined Behavior

У стандартах ISO C11 (розділ 5.1.2.4) та ISO C++11 (розділ [intro.multithread]), а також у правилах мови Rust визначено суворе математичне поняття **гонки даних (*Data Race*)**:

> Гонка даних виникає, якщо два вирази в різних потоках звертаються до однієї комірки пам'яті одночасно, принаймні одне зі звернень є записом, і жодне з них не є атомарною операцією або не синхронізоване відношенням передування (*happens-before*).

Будь-яка гонка даних над неатомарними типами в C, C++ та Rust є **невизначеною поведінкою (*Undefined Behavior*, UB)**.

Поширеною помилкою програмістів є переконання, що гонка даних спричиняє лише отримання розривного або застарілого значення. Насправді семантика невизначеної поведінки розв'язує руки оптимізатору компілятора. Компілятор оптимізує програму, виходячи з фундаментальної аксіоми: *коректна програма не містить гонок даних* (*Data-Race-Free assumption, DRF*).

Якщо гонка даних присутня в коді, оптимізатор може виконати такі агресивні перетворення:

### 1. Дроблення збережень (Store Tearing)

Якщо функція записує 32-бітну або 64-бітну константу, компілятор для економії розміру машинного коду або збереження регістрів має право розбити запис на дві короткі інструкції:

:::tabs
```c
#include <stdint.h>

void update_flags(uint32_t *flags) {
    // Компілятор може розбити запис 0x00010002 на дві 16-бітні команди
    *flags = 0x00010002;
}
```
```cpp
#include <cstdint>

void update_flags(uint32_t *flags) {
    // Компілятор може розбити запис 0x00010002 на дві 16-бітні команди
    *flags = 0x00010002;
}
```
:::

Для однопотокової програми цей код абсолютно коректний. Але для паралельного читача звичайний 32-бітний запис на 32-розрядному процесорі перетворився на джерело розривного читання.

### 2. Вигадування операцій запису (Store Invention)

Оптимізатор може перемістити операцію запису за межі умовного блоку для векторизації або ліквідації розгалуження:

:::tabs
```c
extern int global_status;

void set_status_if(int condition) {
    if (condition) {
        global_status = 42;
    }
}
```
```cpp
extern int global_status;

void set_status_if(bool condition) {
    if (condition) {
        global_status = 42;
    }
}
```
```asm
; Оптимізований компілятором еквівалент (Store Invention):
mov  eax, DWORD PTR [global_status]  ; Прочитали старе значення
test edi, edi                       ; Перевірка condition
cmovne eax, 42                      ; Якщо true — EAX = 42
mov  DWORD PTR [global_status], eax  ; БЕЗУМОВНИЙ запис назад у пам'ять!
```
:::

Якщо умова хибна, однопотокова логіка не порушується: змінна `global_status` переписується власним старим значенням. Проте для сусіднього ядра цей фіктивний запис перезаписує актуальні дані, створені іншим потоком, руйнуючи цілісність пам'яті.

### 3. Вилучення перевірок безпеки

Компілятор, аналізуючи діапазони значень (*Value Range Propagation*), вважає, що змінна переходить лише між легітимними станами. Отримання розривного значення, якого фізично немає в коді, порушує граф потоку керування (*Control Flow Graph*). Компілятор може викинути захисні гілки `if (ptr == NULL)` або вийти за межі масиву у перемикачах `switch`.

## Апаратне розривне читання проти компіляторного

Необхідно чітко розмежовувати два незалежні рівні розриву даних:

| Характеристика | Апаратне розривне читання | Компіляторне розривне читання |
|---|---|---|
| **Рівень виникнення** | Системна шина, контролер пам'яті, лінії кешу | Оптимізатор компілятора, генератор асемблерного коду |
| **Причина** | Вузька шина даних, перетин межі 64-байтової кеш-лінії | Дроблення інструкцій (*Store Tearing*), перезавантаження регістрів (*Load Tearing*) |
| **Вплив `volatile`** | **Не захищає:** 64-розрядний тип на 32-бітній шині все одно ділиться на два `MOV` | **Захищає:** забороняє компілятору дробити або вигадувати звернення |
| **Повний захист** | Природне вирівнювання + апаратні атомарні типи | `std::atomic<T>` або ядерні макроси `READ_ONCE()` / `WRITE_ONCE()` |

### Чому `volatile` не рятує від апаратного розриву

Ключове слово `volatile` у мовах C та C++ вказує компілятору, що значення змінної може змінитися ззовні (наприклад, через апаратний регістр контролера вводу-виводу). Компілятор зобов'язаний генерувати реальне читання або запис у пам'ять при кожному зверненні і не має права кешувати значення в регістрі CPU чи викидати операції.

:::tabs
```c
#include <stdint.h>

// volatile забороняє кешування в регістрах, але НЕ дає атомарності!
volatile uint64_t g_sensor_telemetry;
```
```cpp
#include <cstdint>

// volatile забороняє кешування в регістрах, але НЕ дає атомарності!
volatile uint64_t g_sensor_telemetry;
```
:::

Однак `volatile` **не надає жодних гарантій атомарності на рівні заліза**. На 32-розрядному процесорі x86-32 або ARM Cortex-M4 компілятор чесно згенерує два послідовні зчитування `MOV` чи `LDR`. Кожне з цих двох зчитувань звернеться до фізичної пам'яті, але між ними виникне часовий розрив, у якому сусіднє ядро або обробник переривання змінить стан змінної. Читач гарантовано отримає розривне значення.

### Макроси `READ_ONCE()` та `WRITE_ONCE()` в ядрі Linux

У просторі ядра Linux для доступу до спільних змінних без блокувань замість мовних атоміків C11 використовуються оптимізаційні бар'єри `READ_ONCE()` та `WRITE_ONCE()` (`#include <linux/compiler.h>`):

:::tabs
```c
#define __READ_ONCE(x)  (*(const volatile typeof(x) *)&(x))
#define READ_ONCE(x)    __READ_ONCE(x)

#define __WRITE_ONCE(x, val) do { *(volatile typeof(x) *)&(x) = (val); } while (0)
#define WRITE_ONCE(x, val)   __WRITE_ONCE(x, val)
```
```cpp
template <typename T>
inline T read_once(const T& x) noexcept {
    return static_cast<T>(*static_cast<const volatile T*>(&x));
}

template <typename T>
inline void write_once(T& x, const T& val) noexcept {
    *static_cast<volatile T*>(&x) = val;
}
```
:::

Макрос `READ_ONCE()` виконує приведення адреси змінної до покажчика на `volatile`. Це гарантує:
1. Компілятор згенерує рівно одну інструкцію зчитування машинного слова.
2. Компілятор не об'єднає два зчитування в одне (*load fusing*) і не прочитає комірку двічі (*load tearing*).
3. Компілятор не переставить звернення відносно бар'єрів компілятора.

Проте документація ядра Linux (`Documentation/memory-barriers.txt`) суворо застерігає: макроси `READ_ONCE()` та `WRITE_ONCE()` гарантують атомарність **лише для змінних, розмір яких не перевищує розмір машинного слова процесора (`sizeof(long)`), і які мають природне вирівнювання в пам'яті**. Для 64-бітних змінних на 32-бітних ядрах використання `READ_ONCE()` призведе до розривного читання.

У сучасній розробці ядра для верифікації моделей пам'яті та виявлення прихованих розривів застосовують інструменти формального моделювання LKMM на базі верифікатора `herd7`, а динамічний аналіз у runtime виконується інструментом **KCSAN (*Kernel Concurrency Sanitizer*)**, який автоматично фіксує неатомарні паралельні зчитування спільних змінних пам'яті.

## Апаратні гарантії одиничної атомарності (Single-Copy Atomicity)

Архітектурні специфікації процесорів чітко визначають, які саме звернення до пам'яті гарантуються апаратурою як неподільні без застосування інструкцій блокування (`LOCK` або `LL/SC`). Ця властивість називається **одиничною атомарністю (*Single-Copy Atomicity*)**.

### Гарантії архітектури Intel 64 та IA-32 (Intel SDM, Vol. 3A, Section 8.1.1)

Процесори архітектури x86/x86-64 апаратно гарантують неподільність таких операцій читання й запису:
1. Читання або запис одного байта (8 бітів).
2. Читання або запис 16-бітного слова (*word*), вирівняного на межу 2 байтів.
3. Читання або запис 32-бітного подвійного слова (*doubleword*), вирівняного на межу 4 байтів.
4. Читання або запис 64-бітного чотирикратного слова (*quadword*), вирівняного на межу 8 байтів (на процесорах починаючи з Intel Pentium).
5. Читання або запис 16-, 32- або 64-бітних даних, які повністю укладаються в межі однієї 64-байтової кеш-лінії, навіть якщо вони не мають суворого вирівнювання за розміром (починаючи з процесорів Intel Core 2 і новіших).

Усі звернення, що перетинають межу 64-байтової кеш-лінії, **не є атомарними** без явного префікса `LOCK`.

### Гарантії архітектури ARMv8-A (ARM Architecture Reference Manual)

Архітектура ARM64 гарантує одиничну атомарність для:
1. Звичайних інструкцій навантаження та збереження (`LDR`, `STR`) для розмірів 1, 2, 4 та 8 байтів, якщо адреса строго вирівняна на відповідний розмір (1, 2, 4 або 8 байтів).
2. Інструкцій парного навантаження й збереження `LDP`/`STP` над двома 64-бітними регістрами (128-бітний доступ) — лише за наявності процесорного розширення ARMv8.4-LSE (*Large System Extensions*) або при зверненні до кешованої пам'яті з підтримкою 128-бітної атомарності шини.

### Атомарність операцій над числами з рухомою комою

Операції над типами `float` (32 біти) та `double` (64 біти) підпорядковуються тим самим апаратним правилам вирівнювання. На x86-64 інструкції `MOVSS` (зчитування 32-бітного float у регістр `XMM`) та `MOVSD` (зчитування 64-бітного double у регістр `XMM`) є одинично атомарними при вирівнюванні на 4 та 8 байтів відповідно.

Однак використання застарілого стекового математичного співпроцесора x87 (інструкції `FLD` та `FSTP`) на 32-розрядних системах для 80-бітних чисел (`long double`) гарантовано породжує розривне читання, оскільки 80-бітне значення завжди передається через шину кількома транзакціями.

## Коректні методи усунення розривного читання

Для гарантованого захисту від розривного читання в сучасному програмному забезпеченні застосовують кілька рівнів архітектурних рішень.

### 1. Стандартизовані атомарні типи: `std::atomic<T>`

Основним інструментом у мовах C++ та C є використання спеціалізованих атомарних типів (`std::atomic<T>` у C++, `_Atomic(T)` у C11):

:::tabs
```c
#include <stdatomic.h>
#include <stdint.h>

_Atomic uint64_t telemetry_counter = 0;

void producer(uint64_t val) {
    atomic_store_explicit(&telemetry_counter, val, memory_order_relaxed);
}

uint64_t consumer(void) {
    return atomic_load_explicit(&telemetry_counter, memory_order_relaxed);
}
```
```cpp
#include <atomic>
#include <cstdint>

std::atomic<uint64_t> telemetry_counter{0};

void producer(uint64_t val) {
    telemetry_counter.store(val, std::memory_order_relaxed);
}

uint64_t consumer() {
    return telemetry_counter.load(std::memory_order_relaxed);
}
```
:::

Якщо програмі потрібен лише захист від розривного читання без накладання суворих бар'єрів упорядкування інших інструкцій, використовується модель пам'яті `memory_order_relaxed`. На 64-розрядному процесорі це транслюється у звичайну інструкцію `MOV`/`LDR`, не несучи жодних накладних витрат у порівнянні з неатомарним кодом, але водночас зобов'язуючи компілятор вирівняти змінну та забороняючи розривні оптимізації.

### 2. Перевірка безблокувальної підтримки: `is_lock_free()`

Якщо розмір атомарного типу перевищує максимальну розрядність апаратних атомарних інструкцій цільового процесора (наприклад, `std::atomic<struct large_data>` розміром 32 байти або `std::atomic<uint64_t>` на 32-розрядному мікроконтролері), компілятор не може застосувати єдину машинну команду.

У цьому випадку компілятор непомітно підключає бібліотеку `libatomic`, яка огортає кожне звернення до змінної внутрішнім прихованим замком (*spinlock*). Перевірити, чи виконується операція апаратно без замків, дозволяють методи:

:::tabs
```c
#include <stdatomic.h>
#include <stdbool.h>
#include <stdint.h>

_Atomic uint64_t counter;

bool check_hardware_support(void) {
    return atomic_is_lock_free(&counter);
}
```
```cpp
#include <atomic>
#include <cstdint>

// Перевірка на етапі компіляції:
static_assert(std::atomic<uint64_t>::is_always_lock_free);

bool check_hardware_support() {
    std::atomic<uint64_t> counter{0};
    return counter.is_lock_free();
}
```
:::

### 3. Замки послідовностей (Sequence Locks / Seqlock)

Коли необхідно неподільно оновлювати та зчитувати складні структури даних, що складаються з багатьох полів (наприклад, 64-розрядні координати `x`, `y`, `z` та часову мітку `timestamp`), використання окремих атоміків для кожного поля не рятує від розриву: читач може прочитати нову координату `x`, але старі координати `y` і `z`.

Класичним системним рішенням без важких м'ютексів є **Seqlock** (замок послідовностей), що активно застосовується в ядрі Linux для обліку системного часу (`jiffies` та підсистема `xtime`):

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    uint32_t sequence;
    uint64_t x;
    uint64_t y;
    uint64_t z;
} telemetry_record_t;

void read_telemetry(const volatile telemetry_record_t *src, telemetry_record_t *dst) {
    uint32_t seq;
    do {
        seq = src->sequence;
        while (seq & 1) { // Непарний лічильник — триває запис
            seq = src->sequence;
        }
        dst->x = src->x;
        dst->y = src->y;
        dst->z = src->z;
    } while (src->sequence != seq);
}
```
```cpp
#include <atomic>
#include <cstdint>

struct TelemetryRecord {
    std::atomic<uint32_t> sequence{0};
    uint64_t x{0};
    uint64_t y{0};
    uint64_t z{0};

    TelemetryRecord read_snapshot() const noexcept {
        TelemetryRecord result;
        uint32_t seq = 0;
        do {
            seq = sequence.load(std::memory_order_acquire);
            while (seq & 1) { // Непарний стан — іде активний запис
                seq = sequence.load(std::memory_order_acquire);
            }
            result.x = x;
            result.y = y;
            result.z = z;
        } while (sequence.load(std::memory_order_acquire) != seq);
        return result;
    }
};
```
:::

Якщо під час читання письменник змінив структуру, лічильник `sequence` зміниться, і читач повторить спробу. Це повністю ліквідує розривне читання багатослівних структур без блокування потоку-письменника.

## Практичний стрес-тест виявлення розривного читання

Розглянемо повноцінний тест на мовах C та C++, який наочно демонструє руйнування даних при неатомарному паралельному доступі та підтверджує надійність атомарного розв'язання.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <pthread.h>
#include <inttypes.h>

#define TEST_ITERATIONS 50000000ULL

// Невирівняна структура, що примусово перетинає межу кеш-лінії
typedef struct {
    char offset_padding[60];
    uint64_t counter;
} __attribute__((packed)) shared_payload_t;

static shared_payload_t g_payload;
static volatile bool g_active = true;
static uint64_t g_total_torn_reads = 0;

void *producer_worker(void *arg) {
    (void)arg;
    const uint64_t pattern_low = 0x0000000000000000ULL;
    const uint64_t pattern_high = 0xFFFFFFFFFFFFFFFFULL;

    for (uint64_t i = 0; i < TEST_ITERATIONS && g_active; ++i) {
        g_payload.counter = (i & 1) ? pattern_low : pattern_high;
    }
    g_active = false;
    return NULL;
}

void *consumer_worker(void *arg) {
    (void)arg;
    const uint64_t pattern_low = 0x0000000000000000ULL;
    const uint64_t pattern_high = 0xFFFFFFFFFFFFFFFFULL;
    uint64_t local_torn_hits = 0;

    while (g_active) {
        uint64_t val = g_payload.counter;
        if (val != pattern_low && val != pattern_high) {
            local_torn_hits++;
        }
    }

    __sync_fetch_and_add(&g_total_torn_reads, local_torn_hits);
    return NULL;
}

int main(void) {
    pthread_t writer_thread;
    pthread_t reader_threads[4];

    printf("Запуск перевірки неатомарного доступу...\n");

    pthread_create(&writer_thread, NULL, producer_worker, NULL);
    for (int i = 0; i < 4; ++i) {
        pthread_create(&reader_threads[i], NULL, consumer_worker, NULL);
    }

    pthread_join(writer_thread, NULL);
    for (int i = 0; i < 4; ++i) {
        pthread_join(reader_threads[i], NULL);
    }

    printf("Виявлено розривних станів пам'яті: %" PRIu64 "\n", g_total_torn_reads);
    return 0;
}
```

```cpp
#include <iostream>
#include <thread>
#include <vector>
#include <atomic>
#include <cstdint>

struct alignas(64) BenchmarkContext {
    struct alignas(1) UnalignedTarget {
        char padding[60];
        uint64_t data_field;
    } target;

    std::atomic<uint64_t> safe_atomic_target{0};
    std::atomic<bool> is_running{true};
    std::atomic<uint64_t> torn_event_counter{0};
};

void execute_writer(BenchmarkContext& ctx, uint64_t limit) {
    constexpr uint64_t mask_zero = 0x0000000000000000ULL;
    constexpr uint64_t mask_full = 0xFFFFFFFFFFFFFFFFULL;

    for (uint64_t i = 0; i < limit && ctx.is_running.load(std::memory_order_relaxed); ++i) {
        ctx.target.data_field = (i & 1) ? mask_zero : mask_full;
    }
    ctx.is_running.store(false, std::memory_order_relaxed);
}

void execute_reader(BenchmarkContext& ctx) {
    constexpr uint64_t mask_zero = 0x0000000000000000ULL;
    constexpr uint64_t mask_full = 0xFFFFFFFFFFFFFFFFULL;
    uint64_t thread_torn_count = 0;

    while (ctx.is_running.load(std::memory_order_relaxed)) {
        uint64_t snapshot = ctx.target.data_field;
        if (snapshot != mask_zero && snapshot != mask_full) {
            thread_torn_count++;
        }
    }

    ctx.torn_event_counter.fetch_add(thread_torn_count, std::memory_order_relaxed);
}

int main() {
    BenchmarkContext ctx{};
    constexpr uint64_t total_iterations = 50'000'000ULL;
    constexpr size_t total_readers = 4;

    std::cout << "Запуск багатопотокового аналізу розривного читання..." << std::endl;

    std::vector<std::jthread> readers;
    readers.reserve(total_readers);
    for (size_t i = 0; i < total_readers; ++i) {
        readers.emplace_back(execute_reader, std::ref(ctx));
    }

    std::jthread writer(execute_writer, std::ref(ctx), total_iterations);
    writer.join();

    for (auto& reader : readers) {
        reader.join();
    }

    std::cout << "Підсумок: зафіксовано розривних читань: "
              << ctx.torn_event_counter.load() << std::endl;

    return 0;
}
```
