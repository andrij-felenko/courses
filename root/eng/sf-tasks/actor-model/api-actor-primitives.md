# 📋 Довідник примітивів та інтерфейсів моделі акторів

Модель акторів спирається на компактний і строгий контракт базових операцій. Незалежно від конкретної мови реалізації чи рантайму (Erlang/OTP, Akka, Microsoft Orleans чи системні бібліотеки C/C++), взаємодія між акторами зводиться до фіксованого набору примітивів керування життєвим циклом, відправки повідомлень, перемикання поведінки та обробки аварійних ситуацій.

Нижче наведено структурний довідник універсального прикладного інтерфейсу (API) моделі акторів.

---

### 1. Керування життєвим циклом і породження (`spawn`)

Примітив створення породжує новий незалежний екземпляр актора в системі, виділяє йому унікальну адресу (PID / `ActorRef`), ініціалізує поштову скриньку та реєструє його в планувальнику.

```
spawn(BehaviorFunction, InitialArguments, Options) -> ActorRef
```

| Параметр | Тип | Опис |
| :--- | :--- | :--- |
| `BehaviorFunction` | `Function / Callable` | Початкова функція обробки повідомлень або клас актора. |
| `InitialArguments` | `Tuple / Struct` | Початковий стан або аргументи конструктора актора. |
| `Options` | `Map / Flags` | Конфігурація: розмір скриньки, пріоритет, прив'язка до ядра (*CPU affinity*). |
| **Результат** | `ActorRef` | Непрозора адреса актора (PID) для асинхронної взаємодії. |

**Апаратні та часові характеристики:**
- **Часова складність:** `O(1)` амортизована (виділення вузла дескриптора в купі та генерація унікального ID).
- **Пам'ять:** від ~300 байтів (Erlang BEAM) до ~2–4 КБ у JVM / нативних рантаймах (структура дескриптора + черга).
- **Помилки:** `OutOfMemoryError` (вичерпано системну пам'ять), `MaxActorsExceeded` (перевищено ліміт таблиці дескрипторів).

---

### 2. Асинхронна доставка повідомлень (`send` / `!`)

Базовий примітив відправки (*tell* / *fire-and-forget*). Відправник поміщає повідомлення у поштову скриньку отримувача й повертає керування негайно, не очікуючи на початок обробки чи відповідь.

```
send(TargetRef, MessagePayload) -> void
TargetRef ! MessagePayload
```

| Параметр | Тип | Опис |
| :--- | :--- | :--- |
| `TargetRef` | `ActorRef / PID` | Адреса отримувача. Може вказувати на локальний або віддалений вузол. |
| `MessagePayload` | `Any / Struct` | Незмінні (*immutable*) дані або серіалізований конверт повідомлення. |
| **Результат** | `void` | Успішне додавання повідомлення в чергу (або відправка в мережевий сокет). |

**Гарантії та правила поведінки:**
- **Неблокувальність:** виклик ніколи не переводить потік відправника у стан очікування (*sleep/wait*).
- **Порядок доставки (FIFO per pair):** якщо актор `A` надсилає повідомлення `M1`, а потім `M2` одному й тому самому актору `B`, то `B` гарантовано отримає `M1` раніше за `M2`. Між різними відправниками порядок не детермінований.
- **Мертві листи (*Dead Letters*):** якщо адресат завершив роботу до надходження повідомлення, воно перенаправляється в системний журнал мертвих листів без падіння відправника.

---

### 3. Зміна внутрішнього стану та логіки (`become` / `unbecome`)

Примітив динамічної зміни поведінки замінює поточну функцію обробки повідомлень новою функцією для всіх наступних повідомлень з черги.

```
become(NewBehaviorFunction, DiscardOld = true) -> void
unbecome() -> void
```

| Примітив | Аргументи | Дія |
| :--- | :--- | :--- |
| `become` | `(NewBehavior, DiscardOld)` | Встановлює нову функцію поведінки. Якщо `DiscardOld = false`, стара поведінка зберігається у стеку поведінок. |
| `unbecome` | `void` | Відновлює попередню поведінку зі стека (повернення до попереднього стану скінченного автомата). |

**Сценарії використання:**
- Реалізація скінченних автоматів (FSM): перехід між станами `Connected`, `Authenticating`, `Disconnected`.
- Тимчасове накопичення (*stash*): відкладення повідомлень, непридатних для обробки в поточному стані.

---

### 4. Запит-відповідь з таймаутом (`ask` / `?`)

Шаблон взаємодії, що імітує синхронний виклик через асинхронні повідомлення. Рантайм неявно створює тимчасовий одноразовий актор-проксі, генерує кореляційний ідентифікатор (*correlation ID*) і повертає об'єкт майбутнього результату (*Future / Promise*).

```
ask(TargetRef, RequestMessage, TimeoutDuration) -> Future<ResponseMessage>
```

| Параметр | Тип | Опис |
| :--- | :--- | :--- |
| `TargetRef` | `ActorRef` | Адреса цільового актора. |
| `RequestMessage` | `Any` | Запит із автоматично вкладеною адресою тимчасового актора (`reply_to`). |
| `TimeoutDuration` | `Duration / ms` | Граничний час очікування відповіді. |
| **Результат** | `Future<T>` | Асинхронний результат або виняток `TimeoutException`. |

**Інженерні застереження:**
- Заборонено використовувати нескінченний таймаут (`Timeout = Infinity`), оскільки збій або зависання цільового актора призводить до вічного витоку пам'яті та дедлоку запитувача.
- Зловживання патерном `ask` нівелює переваги асинхронної моделі, перетворюючи систему на повільну імітацію блокуючих RPC.

---

### 5. Відмовостійкість: Зв'язування (`link`) та Моніторинг (`monitor`)

Механізми виявлення збоїв та побудови ієрархій нагляду.

```
link(TargetRef) -> void
unlink(TargetRef) -> void
monitor(TargetRef) -> MonitorRef
demonitor(MonitorRef) -> void
```

| Механізм | Тип зв'язку | Реакція на падіння цілі | Призначення |
| :--- | :--- | :--- | :--- |
| **Link (`link`)** | Двосторонній симетричний | Падіння одного актора генерує невідпорний сигнал аварійного виходу `EXIT` для другого (якщо актор не перехоплює сигнали через `trap_exit`). | Об'єднання групи акторів, які не можуть існувати один без одного (фатальна спільна доля). |
| **Monitor (`monitor`)** | Односторонній асиметричний | Падіння цілі надсилає звичайне інформаційне повідомлення `{'DOWN', Ref, process, Pid, Reason}` у скриньку спостерігача. Спостерігач не падає. | Нагляд за клієнтами, сервісні координатори, балансувальники навантаження. |

---

### 6. Вибірковий прийом та збереження черги (`selective receive` / `stash`)

У багатьох сценаріях актор не може обробити повідомлення, що лежить на верхівці черги, оскільки перебуває в іншому стані (наприклад, повідомлення на зміну даних надійшло під час ініціалізації з'єднання).

```
stash() -> void
unstash_all() -> void
```

| Примітив | Дія | Наслідки для поштової скриньки |
| :--- | :--- | :--- |
| `stash()` | Вилучає поточне повідомлення з основної скриньки й поміщає його в допоміжну чергу очікування (*stash queue*). | Черга розблоковується для наступних повідомлень; поточне повідомлення не губиться. |
| `unstash_all()` | Переміщує всі накопичені повідомлення зі *stash queue* назад у голову основної скриньки в оригінальному порядку. | Актор опрацьовує відкладені запити одразу після переходу в цільовий стан (`become`). |

**Інженерний механізм вибіркового прийому:**
В Erlang/OTP вибірковий прийом реалізовано на рівні рантайму: оператор `receive` послідовно сканує поштову скриньку від голови до хвоста, зіставляючи повідомлення за шаблоном (*pattern matching*). Повідомлення, що не відповідають шаблону, пропускаються й залишаються у скриньці, доки не знайдеться збіг.
*Застереження щодо продуктивності:* Якщо скринька містить тисячі невідповідних повідомлень, кожен вибірковий прийом має часову складність `O(N)` сканування зв'язного списку, що призводить до катастрофічної деградації CPU. Для захисту від цього рекомендується використовувати явний патерн `stash` з фіксованою місткістю замість неконтрольованого сканування.

### 7. Політики обмеження скриньок і зворотного тиску (Backpressure Policies)

У відкритих системах швидкість надходження зовнішніх повідомлень може перевищувати пропускну здатність актора. Для запобігання вичерпанню пам'яті (*OOM*) рантайми підтримують конфігурацію обмежених поштових скриньок (*bounded mailboxes*):

| Політика переповнення | Поведінка при досягненні ліміту | Сфера застосування |
| :--- | :--- | :--- |
| **Drop Newest** | Нове вхідне повідомлення безшумно відкидається; скринька не змінюється. | Потокові метрики, телеметрія сенсорів, оновлення котирувань (де свіже значення замінює старе). |
| **Drop Oldest** | Найстаріше повідомлення в голові черги видаляється, а нове додається в хвіст. | Системи реального часу, де актуальні лише свіжі команди керування. |
| **Fail / Exception** | Відправник отримує виняток `MailboxOverflowException` або повідомлення повертається відправнику. | Фінансові транзакції, де втрата даних неприпустима й вимагає негайного реагування. |
| **Block / Suspend** | Робочий потік відправника блокується до звільнення місця у скриньці отримувача. | Пакетна обробка на одному вузлі (створює ризик лавиноподібного блокування пулу потоків). |

---

### 8. Контракт нагляду та ліміти перезапусків (Supervision Restart Limits)

Наглядач (*Supervisor*) керує життєвим циклом дочірніх акторів відповідно до декларативних правил відновлення.

```
init_supervisor(Strategy, MaxRestarts, TimeWindowSeconds) -> SupervisorRef
```

| Стратегія | Поведінка при аварії дочірнього актора `Worker_K` |
| :--- | :--- |
| **`one_for_one`** | Перезапускається виключно аварійний актор `Worker_K`. Решта дочірніх процесів продовжують роботу без зупинки. |
| **`one_for_all`** | При падінні `Worker_K` наглядач примусово зупиняє й перезапускає **всіх** своїх дочірніх акторів. Застосовується, якщо стан групи є неподільно зв'язаним. |
| **`rest_for_one`** | Зупиняються й перезапускаються лише ті актори, які були створені **після** `Worker_K` у порядку ініціалізації (лінійний каскад залежностей). |

**Захист від нескінченного циклу аварій (Restart Storms):**
Якщо актор містить дефект коду (наприклад, помилку парсингу, яка стабільно падає на певному типі повідомлень), наївний наглядач потрапить у нескінченний цикл перезапусків, споживаючи 100% CPU.
Контракт нагляду визначає жорсткі пороги: `MaxRestarts` (наприклад, 3) протягом `TimeWindowSeconds` (наприклад, 5 секунд). Якщо кількість падінь перевищує ліміт, наглядач визнає себе неспроможним вирішити проблему, примусово зупиняє всіх потомків і сам аварійно завершується, ескалуючи збій до вищого рівня ієрархії.

### 9. Структура конверта повідомлення (Message Envelope)

У розподілених та промислових системах кожне повідомлення огортається в стандартизований системний заголовок:

| Поле конверта | Тип | Призначення |
| :--- | :--- | :--- |
| `message_id` | `UUID / uint64` | Унікальний ідентифікатор повідомлення для трасування та дедуплікації. |
| `sender_ref` | `ActorRef` | Адреса відправника для надсилання відповіді (`reply_to`). |
| `recipient_ref`| `ActorRef` | Фінальна адреса отримувача. |
| `correlation_id`| `UUID / uint64` | Ідентифікатор транзакційного ланцюжка для патерну `ask` або розподіленого трасування. |
| `timestamp` | `int64` | Часова мітка відправки (UTC epoch nanoseconds). |
| `payload` | `Bytes / Variant` | Серіалізоване тіло корисного навантаження. |

### 10. Хуки життєвого циклу актора (Lifecycle Callbacks)

| Хук / Метод | Момент виклику | Типова дія |
| :--- | :--- | :--- |
| `pre_start()` | Одразу після створення дескриптора актора до початку вилучення повідомлень зі скриньки. | Відкриття мережевих з'єднань, ініціалізація внутрішніх структур, запуск дочірніх акторів. |
| `post_stop()` | Після отримання команди зупинки або аварійного завершення, коли скринька закрита. | Звільнення дескрипторів файлів, закриття сокетів, збереження контрольної точки стану. |
| `pre_restart(reason)`| Викликається перед перезапуском актора наглядачем у разі збою. | Скидання пошкодженого тимчасового стану, надсилання повідомлень про вибачення клієнтам. |
| `post_restart()` | Викликається на новому екземплярі після завершення процедури відновлення наглядачем. | Повторний виклик `pre_start()` для відновлення стандартного робочого циклу. |

### 11. Розподілена прозорість локації та мережева резолюція адрес

Однією з ключових переваг моделі акторів є прозорість локації (*location transparency*): синтаксис відправки `send(TargetRef, Msg)` залишається ідентичним незалежно від того, чи живе актор-отримувач у тому самому процесі, на сусідньому ядрі CPU чи на віддаленому сервері в іншому датацентрі.

```
actor_selection("proto://SystemName@Host:Port/user/Supervisor/Worker") -> ActorSelection
resolve_one(ActorSelection, Timeout) -> Future<ActorRef>
```

| Компонент адреси | Приклад | Призначення |
| :--- | :--- | :--- |
| `Protocol` | `akka.tcp`, `dist_erlang` | Мережевий транспортний протокол (TCP/TLS/QUIC). |
| `SystemName` | `ClusterService` | Логічне ім'я кластера або вузла акторної системи. |
| `Host:Port` | `10.0.1.42:2552` | Фізична IP-адреса та мережевий порт віддаленого вузла. |
| `ActorPath` | `/user/orders/processor-7` | Ієрархічний шлях в дереві нагляду локального вузла. |

**Контракт детекції мережевих відмов (Phi Accrual Failure Detector):**
У розподіленому середовищі віддалені актори не можуть миттєво сповістити про раптове знеструмлення машини чи розрив оптоволокна. Рантайм використовує адаптивний детектор відмов на основі розрахунку метрики `Phi` (ймовірнісної оцінки підозри на збій):
- Вузли регулярно обмінюються пульсовими повідомленнями (*heartbeats*) з часовими мітками.
- Якщо затримка відповіді перевищує статистичний поріг, віддалений `ActorRef` маркується як `Terminated`.
- Усім локальним акторам, які встановили `monitor` за віддаленим PID, автоматично надсилається повідомлення `{'DOWN', Ref, process, RemotePid, noconnection}`.
- Це дозволяє кластеру вчасно ізолювати несправний сегмент мережі та запобігти розколу кластера (*split-brain*).
