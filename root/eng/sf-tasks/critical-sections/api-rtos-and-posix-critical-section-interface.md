## Початкові концепції та фізичні принципи

Коли декілька автономних обчислювальних процесів — наприклад, основний потік виконання та апаратне @@en|переривання@@ (від англ. *interrupt*, з лат. *interruptus* — перерваний) або декілька процесорних ядер — одночасно звертаються до спільної комірки пам'яті, фізична архітектура центрального процесора втрачає детермінованість. Будь-яка високорівнева операція модифікації даних, навіть звичайне інкрементування глобального лічильника `counter++`, у машинному коді перетворюється на послідовність із трьох окремих процесів: зчитування значення з оперативної пам'яті в процесорний регістр (англ. *Load*), виклик арифметико-логічного пристрою для обчислення нової суми (англ. *Add*) та зворотний запис результату за адресою в пам'яті (англ. *Store*). Якщо у проміжку між виконанком інструкції зчитування та запису контролер переривань зупиняє поточний конвеєр і передає управління обробнику апаратного сигналу, який модифікує той самий лічильник, виникають незворотні [перегони даних при записі](root:sf-tasks/data-races-locks). Обробник переривання працює зі застарілим значенням, а після повернення процесора до перерваного коду інструкція збереження перезаписує зміни, зроблені апаратурою. Фізична причина цього збою полягає у відсутності атомарності нерозривного виконання всієї послідовності інструкцій на шині даних.

Щоб гарантувати @@en|атомарність@@ (від англ. *atomicity*, з грец. *ἄτομος* — неподільний) в одноядерних мікроконтролерах, розробники обчислювальних ядер впровадили апаратні прапори керування станом процесора. На фізичному рівні ізоляція критичних ділянок коду досягається маскуванням лінії апаратних переривань безпосередньо у ядрах. У мікроконтролерах архітектури @@en|ARM Cortex-M@@ це реалізовано через спеціальні регістри `PRIMASK` та `BASEPRI`. Запис одиниці в регістр `PRIMASK` блокує всі апаратні переривання з регульованим пріоритетом, залишаючи активними лише немасковане переривання `NMI` та системне виключення `HardFault`. Регістр `BASEPRI` діє гнучкіше: він приймає порогове значення пріоритету і блокує лише ті переривання, пріоритет яких дорівнює або нижчий за вказаний рівень, дозволяючи критичним апаратним подіям реального часу продовжувати обробку. Завдяки цьому проста ділянка коду отримує монопольний доступ до системних ресурсів шини, а процесорний конвеєр виконує послідовність інструкцій без будь-яких зовнішніх переривань потоку керування.

У багатьохядерних обчислювальних системах або складних процесорах із позачерговим виконанням інструкцій (англ. *out-of-order execution*) звичайне вимкнення переривань на одному ядрі не захищає оперативну пам'ять від одночасного звернення з боку іншого ядра. Фізична шина пам'яті та кеш-пам'ять процесів вимагають апаратних механізмів узгодження. Для забезпечення виключного доступу на рівнях шин даних застосовуються спеціалізовані апаратні інструкції атомарного зчитування з блокуванням або моніторингом адреси — такі як `LDREX`/`STREX` у ядрах ARM або `LR`/`SC` (Load-Reserved / Store-Conditional) в архітектурі RISC-V. На основі таких інструкцій будується [апаратний спін-замок](root:sf-tasks/spinlock), який циклево перевіряє стан пам'яті між ядрами. Одночасно з цим процесорний конвеєр та ієрархія кешів можуть довільно переставляти інструкції читання й запису для оптимізації швидкодії. Для запобігання виходу інструкцій за межі захищеної зони застосовуються апаратні бар'єри пам'яті (англ. *memory barriers*). Інструкція `DMB` (Data Memory Barrier) гарантує, що всі операції з пам'яттю, вказані до бар'єра, фізично завершаться у шинах до виконання будь-яких наступних операцій з пам'яттю, створюючи апаратну межу безпеки.

Фізична оптимізація критичних секцій вимагає жорсткого компромісу між цілісністю даних та системним детермінізмом. Тривалість часу, протягом якого апаратні переривання залишаються замаскованими, безпосередньо збільшує @@en|затримка переривання@@ (від англ. *interrupt latency*, з лат. *lateo* — приховуюсь). Якщо процесор виконує тривалі обчислення всередині маскованого блоку, реакція мікроконтролера на зовнішню фізичну подію — таку як сигнал від датчика, завершення передачі DMA або спрацювання аварійного таймера — відкладається на весь час перебування у секції. Якщо затримка перевищує припустимий допуск системи реального часу, виникає втрата апаратних подій або порушення часового детермінізму. Тому @@en|критична секція@@ (від англ. *critical section*, з лат. *criticus* — вирішальний, та *sectio* — розріз) на апаратному рівні повинна зводитися до мінімально можливої кількості машинних тактів ядра, виконуючи лише невідкладні атомарні пересилання або оновлення вказувачів.

## Внутрішня будова та алгоритми роботи

На рівні операційних систем реального часу (@@en|RTOS@@, від англ. *Real-Time Operating System*) програмний інтерфейс критичних секцій абстрагує апаратні регістри процесора у зручні та детерміновані виклики API. Основною проблемою при розробці системного ПЗ є забезпечення вкладеності викликів. Якщо функція верхнього рівня входить у критичну секцію, вимикаючи переривання, і всередині викликає допоміжну функцію, яка також створює критичну секцію і при виході з неї просто вмикає переривання назад, верхньорівневий код втратить захист до завершення своєї роботи. Для розв'язання цієї проблеми RTOS використовує лічильник вкладеності (наприклад, `uxCriticalNesting` у @@en|FreeRTOS@@). При першому виклику `taskENTER_CRITICAL()` система зберігає поточний стан регістрів маскування переривань у стек або глобальний лічильник ядра та блокує переривання. Кожен наступний вкладений виклик лише збільшує значення лічильника на одиницю без повторного звернення до апаратури. Виклик `taskEXIT_CRITICAL()` зменшує лічильник, і лише коли його значення досягає нуля, операційна система відновлює початковий стан маски переривань процесора.

У контексті обробників переривань (@@en|ISR@@, від англ. *Interrupt Service Routine*) стандартний алгоритм збереження стану в контексті задачі не працює, оскільки обробник переривання виконується на окремому системному стеку і не прив'язаний до структури керування задачею `TCB` (Thread Control Block). Тому для обробників переривань операційні системи надають окремі макроси та функції, такі як `taskENTER_CRITICAL_FROM_ISR()` та `taskEXIT_CRITICAL_FROM_ISR(uxSavedInterruptStatus)`. Макрос входу повертає локальну змінну, яка містить точну копію регістра стану переривань (наприклад, значення `BASEPRI` або `PRIMASK`) на момент виклику. При виході з критичної секції ця збережена змінна передається у виклик виходу, який явним чином відновлює апаратний регістр у стан, що передував входженню. Такий підхід робить обробники переривань повністю повторно входжуваними (@@en|повторна входжуваність@@, англ. *reentrancy*).

У високорівневих операційних системах та операційних системах стандарту @@en|POSIX@@ (від англ. *Portable Operating System Interface*) вимкнення апаратних переривань у просторі користувача заборонене з міркувань безпеки та захисту пам'яті. Замість маскування переривань критичні секції будуються на основі об'єктів взаємного виключення — @@en|м'ютекс@@ (від англ. *mutex*, скорочення від *mutual exclusion* — взаємне виключення). Коли потік викликає `pthread_mutex_lock()`, операційна система перевіряє стан атомарної змінної замка у пам'яті. Якщо м'ютекс вільний, потік захоплює його за один атомарний крок на рівні користувача без переключення в режим ядра (використовуючи системні виклики на кшталт @@en|futex@@ у Linux). Якщо м'ютекс зайнятий, потік переводиться у стан блокування, а @@en|планувальник задач@@ (від англ. *task scheduler*) виконує @@en|контекст перемикання@@ (від англ. *context switch*) на іншу готову задачу. Щоб уникнути ситуації, коли потік із низьким пріоритетом утримує м'ютекс і блокує потік із високим пріоритетом, POSIX м'ютекси підтримують протокол @@en|успадкування пріоритету@@ (від англ. *priority inheritance*), який тимчасово піднімає пріоритет утримувача м'ютексу до рівня найвищого чекаючого потоку, запобігаючи виникненню [інверсії пріоритетів у системі](root:sf-tasks/rtos-priority-inversion-inheritance).

Нижче наведено практичну реалізацію роботи з критичними секціями для RTOS та POSIX середовищ мовами C та C++. У коді C++ застосовано ідіому RAII (Resource Acquisition Is Initialization) для автоматичного звільнення критичної секції при виході з області видимості, що унеможливлює витік замка при розгалуженнях або поверненні з функції.

```c|freertos
typedef struct {

    uint32_t errors;

void increment_network_tx(uint32_t bytes_sent) {

    taskENTER_CRITICAL();
    
    g_net_stats.tx_packets++;
    /* Вкладений виклик критичної секції перевіряє лічильник uxCriticalNesting */
```

```cpp|freertos
#include "FreeRTOS.h"
#include "task.h"
#include <cstddef>
#include <cstdint>

/* RAII-обгортка для критичної секції FreeRTOS */
class CriticalSectionGuard {
public:
    CriticalSectionGuard() {
        taskENTER_CRITICAL();
    }
    
    ~CriticalSectionGuard() {
        taskEXIT_CRITICAL();
    }
    
    /* Заборона копіювання та переміщення для безпеки */
    CriticalSectionGuard(const CriticalSectionGuard&) = delete;
    CriticalSectionGuard& operator=(const CriticalSectionGuard&) = delete;
};

struct HardwareBuffer {
    uint8_t data[256];
    size_t head;
    size_t tail;

    bool write_byte(uint8_t byte) {
        /* Автоматичний вхід у критичну секцію при створенні об'єкта */
        CriticalSectionGuard guard;
        
        size_t next_head = (head + 1) % sizeof(data);
        if (next_head == tail) {
            return false; /* Буфер повний, деструктор guard безпечно відновить переривання */
        }
        
        data[head] = byte;
        head = next_head;
        return true;
        /* Деструктор CriticalSectionGuard викликається автоматично при виході з функції */
    }
};
```

При виборі конкретного механізму критичних секцій розробник повинен чітко розрізняти сфери застосування. Якщо задача вимагає атомарного оновлення декількох регістрів периферії або короткої послідовності байтів у спільному буфері між обробником переривання `ISR` та потоком, слід використовувати маскування переривань `taskENTER_CRITICAL()` / `taskENTER_CRITICAL_FROM_ISR()`. Цей підхід виконується за лічені цикли процесора і не створює накладних витрат на переключення контексту. Проте, якщо тривалість обробки даних у критичній секції перевищує кілька десятків машинних тактів або вимагає очікування зовнішньої події, маскування переривань неприпустиме. У такому разі критична секція повинна реалізовуватись через [програмний м'ютекс](root:sf-tasks/readers-writer-lock) або [апаратно-програмний спін-замок](root:sf-tasks/spinlock), які зберігають чутливість системи до апаратних подій реального часу та забезпечують плавний перерозподіл ресурсів процесора.

## Апаратна реалізація та низькорівневий C/C++ код

Робота з периферією в мікроконтролерах вимагає прямого модифікування системних регістрів та спільних структур даних. Коли пристрою необхідно оновити багаторівневу конфігурацію таймера чи вставити елемент у кільцевий буфер, апаратне @@en|переривання@@ (англ. *interrupt*, від латинського *interruptus* — перерваний) може виникнути між окремими машинами інструкціями процесора. Якщо це переривання звертається до тих самих регістрів чи пам'яті, виникають [непередбачувані перегони даних](root:sf-tasks/data-races-locks), які спотворюють стан прошивки. Опосередковані виклики функцій системних операційних систем занадто повільні для швидкої периферії, тому вбудоване ядро надає прямі важелі апаратного керування через системний @@en|регістр@@ (англ. *register*, від пізньолатинського *registrum* — список, внесок) процесора.

Головним механізмом низькорівневого захисту ділянок коду є @@en|маскування переривань@@ (англ. *interrupt masking*, від арабського *maskhara* — маска, личина). У мікроконтролерній архітектурі @@en|ARM Cortex-M@@ для цього застосовують спеціалізовані регістри @@en|PRIMASK@@ та @@en|BASEPRI@@. Регістр @@en|PRIMASK@@ дозволяє повністю вимкнути всі апаратні переривання з регульованим пріоритетом, залишаючи активним лише немасковане переривання NMI та виклики винятків ядра. Натомість регістр @@en|BASEPRI@@ пропонує гнучкіший механізм: він блокує лише ті переривання, чий пріоритет є чисельно рівним або нижчим за встановлений поріг. Це дозволяє критично важливим системним обробникам (наприклад, аварійній зупинці силової автоматики) виконуватися без жодних затримок, поки ззвичайні задачі модифікують спільний буфер.

При реалізації низькорівневих критичних секцій виникає фундаментальна архітектурна проблема — вкладеність викликів. Якщо функція першого рівня вимикає переривання, а потім викликає допоміжну функцію, яка також утворює критичну секцію, наївне ввімкнення переривань при виході з допоміжної функції призведе до катастрофи. Переривання стануть активними завчасно, поки функція першого рівня все ще виконує захищені операції.

Щоб забезпечити коректне збереження стану, алгоритм входу в критичну секцію обов'язково зчитує поточне значення маски переривань у локальну змінну стек-кадру, і лише після цього модифікує системний регістр. Під час виходу з секції функція відновлює в регістр саме збережене значення маски, а не просто вмикає переривання.

![Збереження стану регістра BASEPRI та відновлення маски переривань при вкладених критичних секціях](img/nested-critical-section-registers.svg)
*Вкладені критичні секції зберігають поточний рівень маскування переривань у локальну змінну стек-кадру, запобігаючи передчасному ввімкненню переривань у зовнішньому блоці.*

Окрім апаратного маскування сигналів переривання, сучасні обчислювальні ядра вимагають явного керування порядком виконання інструкцій у конвеєрі. Сучасний компілятор @@en|GCC@@ та суперскалярні процесорні ядра з оптимізацією виконання можуть переставляти операції зчитування та запису в пам'ять, якщо між ними немає видимої залежності за даними. Це означає, що запис у спільну змінну може фізично відбутися після того, як переривання будуть повторно ввімкнені.

Для запобігання цьому використовують компіляційні паркани пам'яті `asm volatile("" ::: "memory")` та апаратні інструкції-бар'єри. Спеціалізований @@en|бар'єр пам'яті@@ (англ. *memory barrier*, від французького *barrière* — перерада) гарантує детермінований порядок операцій:
- Інструкція DMB (Data Memory Barrier) гарантує завершення всіх попередніх операцій доступу до пам'яті перед виконанням наступних.
- Інструкція DSB (Data Synchronization Barrier) припиняє виконання наступних інструкцій процесора до повного завершення всіх поточних шинних транзакцій та скидання буферів запису.
- Інструкція ISB (Instruction Synchronization Barrier) повністю очищує конвеєр процесора, гарантуючи, що наступні інструкції будуть зчитані з пам'яті з урахуванням усіх попередніх змінених регістрів конфігурації.

У двоядерних та багатоядерних системах, таких як @@en|ESP32@@ чи двоядерні конфігурації Cortex-M7, звичайне маскування переривань на одному ядрі не зупиняє виконання коду на сусідньому ядрі. Якщо обидва ядра мають доступ до одного регістру периферії, для коротких секцій застосовують [активне очікування на спін-замку](root:sf-tasks/spinlock), яке поєднує логічне вимкнення локальних переривань із атомарними інструкціями LDREX/STREX або атомарними апаратними регістрами типу Compare-And-Swap (CAS).

Нижче наведено практичні реалізації низькорівневого маскування переривань із збереженням стану вкладеності для мов C та C++.

```c|esp-idf
#include <stdint.h>
#include <stdbool.h>

// Структура збереження апаратного стану маски переривань
typedef struct {
    uint32_t saved_mask;
} critical_section_state_t;

// Вхід у критичну секцію із збереженням регістра BASEPRI
static inline critical_section_state_t hardware_critical_enter(void) {
    critical_section_state_t state;
    // Зчитуємо BASEPRI, встановлюємо нову маску та виконуємо бар'єр ISB
    __asm__ __volatile__(
        "mrs %0, basepri \n\t"
        "msr basepri, %1 \n\t"
        "isb             \n\t"
        : "=r" (state.saved_mask)
        : "r" (0x20) // Маскуємо переривання з пріоритетом 0x20 і нижче
        : "memory"
    );
    return state;
}

// Вихід із критичної секції з відновленням попереднього стану
static inline void hardware_critical_exit(const critical_section_state_t *state) {
    __asm__ __volatile__(
        "msr basepri, %0 \n\t"
        "isb             \n\t"
        :
        : "r" (state->saved_mask)
        : "memory"
    );
}

// Автоматичне викликанная очищення при виході з області видимості
static inline void auto_critical_exit(critical_section_state_t *state) {
    hardware_critical_exit(state);
}

// Макрос для створення автоматичної критичної секції C
#define CRITICAL_SECTION_C() \
    critical_section_state_t __cs_state __attribute__((cleanup(auto_critical_exit))) = hardware_critical_enter()

// Структура кільцевого буфера
typedef struct {
    uint8_t buffer[64];
    volatile uint32_t head;
    volatile uint32_t tail;
} ring_buffer_t;

// Потокобезпечна вставка даних у буфер
bool ring_buffer_push(ring_buffer_t *ring, uint8_t byte) {
    CRITICAL_SECTION_C(); // Апаратний захист секції
    
    uint32_t next_head = (ring->head + 1) % 64;
    if (next_head == ring->tail) {
        return false; // Буфер переповнено
    }
    
    ring->buffer[ring->head] = byte;
    ring->head = next_head;
    return true;
}
```

## Практичне застосування та відлагодження

Правильне проєктування низькорівневих критичних секцій вимагає глибокого розуміння системних обмежень реального часу. Навіть якщо маскування переривань написано без помилок у синтаксисі, зловживання цим механізмом створює приховані апаратні пастки, які призводять до відмов системи в реальній експлуатації.

Найнебезпечнішим наслідком тривалого перебування в критичній секції є зростання такої характеристики, як @@en|затримка переривання@@ (англ. *interrupt latency*, від латинського *latens* — прихований). Поки процесор виконує код із вимкненими перериваннями, апаратні події від периферії накопичуються у підсистемі контролера переривань. Якщо критична секція виконується занадто довго, виникає часовий @@en|джитер@@ (англ. *jitter*, від англійського *jitter* — тремтіння, коливання) — непередбачувані коливання часу реакції на зовнішні події. В критичних системах (наприклад, керуванні безколекторними двигунами або обробці високошвидкісного шинного потоку CAN) це призводить до втрати пакетів даних або падіння силового інвертора. Головне правило створення критичних секцій — виконання має бути детермінованим та займати фіксований час складністю $O(1)$ без використання циклів зі змінною кількістю ітерацій.

Другою критичною пасткою є виклик системних функцій @@en|RTOS@@ або @@en|POSIX@@ всередині блоку з вимкненими перериваннями. Якщо розробник спробує викликати затримку `vTaskDelay()`, виділити динамічну пам'ять через `malloc()` або виконати очікування на семафорі всередині апаратної критичної секції, відбудеться фатальна помилка ядра (RTOS Kernel Panic) або невідворотний @@en|дедлок@@ (англ. *deadlock*, від англійського *dead* — мертвий, та *lock* — замок). Механізм перемикання контексту задач у системі @@en|FreeRTOS@@ спирається на програмні переривання (наприклад, PendSV у Cortex-M). Коли переривання вимкнені, планувальник задач втрачає здатність перемикати потоки, і процесорне ядро назавжди застрягає в стані очікування.

Окрему увагу слід приділяти відмінностям між контекстом звичайної задачі та обробником переривань ISR. Для обробників переривань не можна використовувати стандартні функції входу в критичну секцію, призначені для задач. У системі FreeRTOS для цього передбачено спеціалізовані макроси із суфіксом `FromISR`, які використовують власні лічильники вкладеності та не порушують роботу внутрішнього планувальника.

Також важливо пам'ятати про системні наслідки блокування: маскування переривань тимчасово піднімає пріоритет поточного коду вище за всі задачі та більшість апаратних обробників. Якщо операція оновлення даних є тривалою, замість апаратного маскування слід застосовувати @@en|м'ютекс@@ (англ. *mutex*, від *mutual exclusion* — взаємне виключення; лат. *mutuus* — взаємний, *exclusio* — виключення) або реалізувати [протокол межі пріоритетів](root:sf-tasks/priority-ceiling-protocol), який запобігає класичній ситуації, котра викликає [небезпечну інверсію пріоритетів](root:sf-tasks/data-races-locks). Якщо ж критичні секції потрібні виключно для зчитування великих масивів даних кількома потоками, набагато ефективніше застосувати [шаблон багатьох читачів](root:sf-tasks/readers-writer-lock).

Для виявлення та діагностики помилок часових затримок у критичних секціях застосовують як апаратні, так і програмні методи відлагодження:
1. **Апаратний осцилографічний вимір:** На початку критичної секції подається високий логічний рівень на вільний вивід GPIO мікроконтролера, а при виході рівень скидається в нуль. За допомогою логічного аналізатора або осцилографа можна з точністю до наносекунд виміряти максимальну тривалість блокування переривань та частоту сплесків затримки.
2. **Апаратний лічильник циклів DWT (Data Watchpoint and Trace):** У ядрах ARM Cortex-M присутній модуль DWT, який містить 32-бітний лічильник циклів `CYCCNT`. Вимірюючи різницю значень `CYCCNT` між входом та виходом із секції, можна прямо в коді обчислити точну тривалість виконання у тактах процесора.
3. **Автоматизований моніторинг затримок у коді:** Розробка діагностичних обгорток, які порівнюють тривалість виконання із критичним порогом і генерують сповіщення у разі його перевищення.

```c|esp-idf
#include <stdint.h>
#include <stdbool.h>

// Адреси регістрів модуля DWT для ARM Cortex-M
#define DWT_CTRL    (*(volatile uint32_t*)0xE0001000)
#define DWT_CYCCNT  (*(volatile uint32_t*)0xE0001004)
#define DEMCR       (*(volatile uint32_t*)0xE000EDFC)

// Поріг затримки у тактах (наприклад, 800 тактів = 5 мкс при 160 МГц)
#define LATENCY_THRESHOLD_CYCLES 800U

typedef struct {
    uint32_t saved_mask;
    uint32_t start_cycles;
    const char *file;
    uint32_t line;
} diag_critical_state_t;

// Ініціалізація апаратного лічильника циклів DWT
static inline void dwt_counter_init(void) {
    DEMCR |= (1U << 24);   // Вмикаємо трасування TRCENA
    DWT_CTRL |= (1U << 0);  // Вмикаємо лічильник CYCCNT
}

// Діагностичний вхід у критичну секцію
static inline diag_critical_state_t diag_critical_enter(const char *file, uint32_t line) {
    diag_critical_state_t state;
    state.file = file;
    state.line = line;
    
    __asm__ __volatile__(
        "mrs %0, basepri \n\t"
        "msr basepri, %1 \n\t"
        "isb             \n\t"
        : "=r" (state.saved_mask)
        : "r" (0x20)
        : "memory"
    );
    
    state.start_cycles = DWT_CYCCNT; // Фіксуємо початковий такт
    return state;
}

// Діагностичний вихід із перевіркою часового ліміту
static inline void diag_critical_exit(diag_critical_state_t *state) {
    uint32_t elapsed = DWT_CYCCNT - state->start_cycles;
    
    __asm__ __volatile__(
        "msr basepri, %0 \n\t"
        "isb             \n\t"
        :
        : "r" (state->saved_mask)
        : "memory"
    );
    
    // Якщо тривалість перевищує допустимий поріг, фіксуємо затримку
    if (elapsed > LATENCY_THRESHOLD_CYCLES) {
        // Запис у системний журнал або активація точки зупинки
        (void)state->file;
        (void)state->line;
    }
}

static inline void auto_diag_exit(diag_critical_state_t *state) {
    diag_critical_exit(state);
}

// Макрос автоматичної діагностичної критичної секції
#define DIAG_CRITICAL_SECTION_C() \
    diag_critical_state_t __diag_cs __attribute__((cleanup(auto_diag_exit))) = \
        diag_critical_enter(__FILE__, __LINE__)
```

```cpp|esp-idf
namespace sys::diag {

constexpr std::uint32_t kLatencyThresholdCycles = 800U;

// Діагностичний RAII-контролер затримок критичних секцій
class DiagnosticCriticalGuard final {
public:
    DiagnosticCriticalGuard(const char* file, std::uint32_t line) noexcept
        : file_(file), line_(line) {
        __asm__ __volatile__(
            "mrs %0, basepri \n\t"
            "msr basepri, %1 \n\t"
            "isb             \n\t"
            : "=r"(saved_mask_)
            : "r"(0x20)
            : "memory"
        );
        start_cycles_ = read_cyccnt();
    }

    ~DiagnosticCriticalGuard() noexcept {
        std::uint32_t elapsed = read_cyccnt() - start_cycles_;
        
        __asm__ __volatile__(
            "msr basepri, %0 \n\t"
            "isb             \n\t"
            :
            : "r"(saved_mask_)
            : "memory"
        );

        if (elapsed > kLatencyThresholdCycles) {
            on_latency_exceeded(file_, line_, elapsed);
        }
    }

    DiagnosticCriticalGuard(const DiagnosticCriticalGuard&) = delete;
    DiagnosticCriticalGuard& operator=(const DiagnosticCriticalGuard&) = delete;
    DiagnosticCriticalGuard(DiagnosticCriticalGuard&&) = delete;
    DiagnosticCriticalGuard& operator=(DiagnosticCriticalGuard&&) = delete;

private:
    static std::uint32_t read_cyccnt() noexcept {
        volatile std::uint32_t* cyccnt = reinterpret_cast<volatile std::uint32_t*>(0xE0001004);
        return *cyccnt;
    }

    static void on_latency_exceeded(const char* file, std::uint32_t line, std::uint32_t cycles) noexcept {
        // Обробка виявленого сплеску затримки
        (void)file;
        (void)line;
        (void)cycles;
    }

    const char* file_;
    std::uint32_t line_;
    std::uint32_t start_cycles_{0};
    std::uint32_t saved_mask_{0};
};

} // namespace sys::diag
```
