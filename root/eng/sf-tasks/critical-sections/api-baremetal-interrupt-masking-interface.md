## Початкові концепції та фізичні принципи

Уявімо мікроконтролер, який керує силовим інвертором трифазного електродвигуна і щосекунди обчислює тривалість керуючих імпульсів за допомогою двох 16-бітних регістрів системного таймера. Основна програма послідовно записує старше та молодше слово в оперативну пам'ять, формуючи нове 32-бітне значення вихідного сигналу широтно-імпульсної модуляції. Якщо саме між цими двома окремими операціями запису виникає апаратне переривання від аналогово-цифрового перетворювача, процесор миттєво зупиняє виконання основного коду та переходить до обробника. Обробник читає з пам'яті значення, у якому старша частина вже оновлена новою величиною, а молодша частина все ще містить старі дані з попереднього обчислювального циклу. Внаслідок цього виникає спотворення командного значення, через що вихідний силовий транзистор отримує помилковий сигнал, оскільки [виникають перегони даних](root:sf-tasks/data-races-locks), що порушують детермінованість роботи всієї вбудованої системи.

Ця фундаментальна проблема зумовлена фізичною організацією апаратної шини даних та шини команд мікроконтролера. Більшість мікропроцесорних ядер виконують запис або зчитування складених структур даних за кілька послідовних тактів системної частоти. Коли зовнішня подія на фізичній ніжці мікроконтролера змінює логічний рівень напруги, периферійний модуль генерує апаратний запит переривання. Контролер векторних переривань фіксує цей запит і примусово скидає поточний конвеєр інструкцій центрального процесора. Процесорне ядро автоматично зберігає поточний стан робочих регістрів у системний стек та завантажує адресу відповідного обробника з вектору переривань. Оскільки момент виникнення зовнішнього сигналу є асинхронним відносно основного потоку виконання, переривання може статися між будь-якими двома інструкціями асемблера. Для забезпечення цілісності структури даних розробник мусить тимчасово блокувати здатність процесорного ядра реагувати на такі події.

Ділянку програмного коду, під час виконання якої спільний ресурс не повинен модифікуватися іншими джерелами виконання або обробниками подій, називають @@en|критична секція@@ (від англ. *critical section*, з лат. *criticus* — вирішальний, та *sectio* — розріз). Для гарантування її недоторканності використовується @@en|маскування переривань@@ (від англ. *interrupt masking*, з лат. *interruptus* — перерваний, та фр. *masque* — маска). Під @@en|маскування переривань@@ розуміють програмну зміну стану спеціального системного регістру процесорного ядра, яка змушує ядро ігнорувати запити на переривання від периферійних модулів. При цьому апаратні блоки продовжують фіксувати події та встановлювати відповідні прапорці запросів у своїх регістрах, проте процесор не виконує переходів до обробників до моменту зняття маски. Важливо розрізняти звичайні масковані переривання та немасковані переривання (від англ. *Non-Maskable Interrupt*, NMI), які мають найвищий апаратний пріоритет і виконуються навіть при заблокованій системі звичайних переривань.

Апаратний механізм @@en|маскування переривань@@ базується на прапорцях керування у системному регістрі процесорного ядра, такому як `CPSR` в архітектурі ARM7 або `PRIMASK` в архітектурі ARM Cortex-M. Коли програма записує одиницю у відповідний біт маскування, лінія апаратного сигналу переривання від контролера векторних переривань блокується безпосередньо на вході конвеєра інструкцій. Це гарантує @@en|атомарність@@ (від грец. *atomos* — неділимий) виконання послідовності програмних команд. Під @@en|атомарність@@ розуміють властивість операції виконуватися повністю і неподільно без можливості спостереження її проміжних станів іншими потоками або обробниками.

Проте тривале @@en|маскування переривань@@ створює суттєве обмеження для систем реального часу, оскільки збільшує підсумковий час реакції на критичні події навколишнього середовища. Параметр, що визначає максимальний проміжок часу від моменту виникнення апаратного сигналу на ніжці мікроконтролера до початку виконання першої інструкції обробника переривання, називають @@en|затримка переривання@@ (від англ. *interrupt latency*, з лат. *latens* — прихований).

Загальний час затримки реакції системи на зовнішню подію обчислюється як сума максимального часу маскування та апаратної затримки входження в обробник:

    T_latency = T_mask_max + T_entry_max
    = T_mask_max + T_push + T_vector      [декомпозиція апаратної затримки входження]

У цьому виразі символ `T_latency` позначає підсумковий час @@en|затримка переривання@@, `T_mask_max` — тривалість найдовшої @@en|критична секція@@ в системі, `T_entry_max` — тривалість апаратного збереження контексту, `T_push` — час заштовхування регістрів у стек, а `T_vector` — час зчитування адреси з вектора переривань. З наведеного виразу чітко видно, що максимальна @@en|затримка переривання@@ напряму залежить від тривалості найдовшої @@en|критична секція@@.

Якщо час @@en|маскування переривань@@ `T_mask_max` перевищує допустимий інтервал обслуговування периферійного модуля, у системі відбудеться переповнення апаратних FIFO-буферів або втрата важливих сигналів від датчиків. З цієї причини фундаментальним правилом проєктування прошивок є мінімізація кількості інструкцій, що виконуються всередині @@en|критична секція@@ при маскованих перериваннях.

## Внутрішня будова та алгоритми роботи

Архітектура модуля @@en|маскування переривань@@ базується на керуванні регістрами процесорного ядра та збереженні логічного стану системних прапорців у стеку. У найпростішій реалізації маскування виконується викликом інструкцій глобального вимкнення та ввімкнення переривань. Проте така спрощена схема має фундаментальний недолік: вона позбавлена властивості, яка називається @@en|реентерабельність@@ (від англ. *reentrancy*, з фр. *rentrer* — повторно входити). Якщо функція з @@en|критична секція@@ викликає іншу допоміжну функцію, яка також створює @@en|критична секція@@, вкладений вихід з внутрішньої секції глобально увімкне переривання. В результаті зовнішня функція опиниться у незахищеному стані ще до того, як завершить виконання власних критичних операцій з пам'яттю.

Для розв'язання проблеми вкладеності застосовується алгоритм збереження та відновлення стану маски переривань. Перед вимкненням переривань програма зчитує поточне значення системного регістру `PRIMASK` і зберігає його у локальній змінній на стеку поточного виклику. Після збереження стану виконується апаратна інструкція маскування. При виході з @@en|критична секція@@ замість безумовного увімкнення переривань програма записує збережене значення назад у системний регістр `PRIMASK`. Якщо переривання були вже вимкнені до входу у внутрішню секцію, вони залишаться вимкненими і після виходу з неї, що повністю зберігає контекст виконання.

![Послідовність зміни прапорця переривань PRIMASK при вкладених викликах критичних секцій](img/critical-section-nesting.svg)
*Діаграма станів збереження та відновлення контексту переривань у вкладених критичних секціях.*

Сучасні мікроконтролери з контролерами векторних переривань `NVIC` додатково підтримують вибіркове @@en|маскування переривань@@ за рівнем пріоритету через регістр `BASEPRI`. Це дозволяє блокувати лише ті переривання, пріоритет яких нижчий або дорівнює заданому пороговому значенню. Високопріоритетні переривання критичних вузлів системної безпеки продовжують обслуговуватися без жодних затримок, тоді як доступ до спільних структур даних для системних задач захищається від конфліктів.

Особливу увагу при розробці низькорівневого коду слід приділяти бар'єрам оптимізації компілятора. Компілятор мови C/C++ може переупорядкувати інструкції читання та запису пам'яті задля підвищення швидкодії, винісши операції за межі @@en|критична секція@@. Щоб запобігти такому переупорядкуванню, всередині функцій маскування обов'язково встановлюється програмний бар'єр пам'яті (від англ. *compiler memory barrier*).

У багатоядерних вбудованих системах або симетричних мультипроцесорних конфігураціях @@en|маскування переривань@@ на одному ядрі не захищає оперативну пам'ять від одночасного доступу з боку іншого ядра. У таких архітектурах застосовується комбінований підхід, де локальне @@en|маскування переривань@@ поєднується з апаратними атомарними інструкціями перевірки зі встановленням, для чого використовується [застосування спін-замка](root:sf-tasks/spinlock).

На програмному рівні у мовах C та C++ вхід і вихід з @@en|критична секція@@ реалізуються через низькорівневі інтринсики компілятора або асемблерні вставки. У мові C++ для автоматичного та надійного управління станом @@en|критична секція@@ застосовується патерн RAII (від англ. *Resource Acquisition Is Initialization* — отримання ресурсу є ініціалізацією).

:::tabs
@tab C (Bare-Metal)
```c|baremetal
#include <stdint.h>
#include "core_cm4.h"

// Структура даних для збереження стану критичної секції
typedef struct {
    uint32_t primask_state;
} critical_section_t;

// Вхід у критичну секцію із збереженням стану
static inline critical_section_t critical_section_enter(void) {
    critical_section_t cs;
    cs.primask_state = __get_PRIMASK();
    __disable_irq();
    // Бар'єр пам'яті для запобігання переупорядкуванню компілятором
    __asm__ __volatile__("" ::: "memory");
    return cs;
}

// Вихід з критичної секції з відновленням стану
static inline void critical_section_exit(critical_section_t cs) {
    __asm__ __volatile__("" ::: "memory");
    __set_PRIMASK(cs.primask_state);
}

// Приклад безпечного оновлення системного буфера
void safe_buffer_update(uint32_t *buffer, uint32_t data) {
    critical_section_t cs = critical_section_enter();
    buffer[0] = data;
    buffer[1] = ~data;
    critical_section_exit(cs);
}
```
@tab C++ (Bare-Metal)
```cpp|baremetal
#include <cstdint>
#include <atomic>
#include "core_cm4.h"

// RAII-клас для автоматичного захисту критичної секції
class CriticalSectionGuard {
public:
    CriticalSectionGuard() noexcept 
        : m_primask(__get_PRIMASK()) {
        __disable_irq();
        std::atomic_signal_fence(std::memory_order_seq_cst);
    }

    ~CriticalSectionGuard() noexcept {
        std::atomic_signal_fence(std::memory_order_seq_cst);
        __set_PRIMASK(m_primask);
    }

    // Заборона копіювання та переміщення об'єкта
    CriticalSectionGuard(const CriticalSectionGuard&) = delete;
    CriticalSectionGuard& operator=(const CriticalSectionGuard&) = delete;
    CriticalSectionGuard(CriticalSectionGuard&&) = delete;
    CriticalSectionGuard& operator=(CriticalSectionGuard&&) = delete;

private:
    uint32_t m_primask;
};

// Приклад використання RAII в об'єктно-орієнтованому коді
void safe_buffer_update_cpp(uint32_t *buffer, uint32_t data) {
    CriticalSectionGuard lock;
    buffer[0] = data;
    buffer[1] = ~data;
    // Деструктор lock автоматично відновить PRIMASK при виході
}
```

Алгоритм виконання даного інтерфейсу забезпечує повністю детермінований захист критичних ресурсів. При виклику функції `critical_section_enter()` процесор спочатку зчитує поточний стан регістру `PRIMASK`, після чого виконує асемблерну інструкцію `CPSID i` (`Change Processor State, Disable Interrupts`), яка встановлює біт маскування за один такт. Після завершення модифікації даних функція `critical_section_exit()` повертає збережене значення в регістр за допомогою інструкції `MSR PRIMASK, reg`.

У системах під керуванням операційних систем реального часу RTOS цей базовий апаратний механізм лежить в основі системних викликів `taskENTER_CRITICAL()` та `taskEXIT_CRITICAL()`. Він запобігає асинхронному перемиканню контексту задач під час оновлення черг повідомлень та системних семафорів, забезпечуючи високу надійність роботи вбудованого програмного забезпечення.

## Апаратна реалізація та низькорівневий C/C++ код

Коли програміст викликає функцію маскування, системні прапорці процесорного ядра змінюються за один такт, проте оперативна пам'ять та периферійні модулі не завжди миттєво переходять у узгоджений стан. Сучасні мікроконтролери використовують суперскалярні або багатостадійні конвеєри інструкцій, а також буфери відкладеного запису пам'яті (від англ. *write buffer*). Якщо процесорне ядро виконує асемблерну інструкцію вимкнення переривань, наступні інструкції з @@en|критична секція@@ можуть потрапити на стадію декодування та виконання ще до того, як апаратний шинний контролер остаточно заблокує обробку ліній апаратних запитів. В результаті периферійний модуль може згенерувати переривання прямо в момент виконання першої команди критичної ділянки, порушуючи її @@en|атомарність@@.

Для розв'язання цієї проблеми на апаратному рівні застосовуються спеціальні примусові апаратні інструкції синхронізації конвеєра та шини даних, які узагальнено називають @@en|бар'єр пам'яті@@ (від англ. *memory barrier*, з лат. *memoria* — пам'ять, та фр. *barrière* — перерада). В архітектурі ARM Cortex-M після зміни прапорця `PRIMASK` за допомогою інструкції `CPSID i` додається інструкція `DSB` (від англ. *Data Synchronization Barrier*). Вона призупиняє виконання наступних команд процесора до повного завершення всіх попередніх операцій зчитування та запису в оперативну пам'яті чи регістри периферії. Одразу після неї виконується інструкція `ISB` (від англ. *Instruction Synchronization Barrier*), яка повністю очищає та перезавантажує @@en|конвеєр інструкцій@@ процесора. Це гарантує, що жодна інструкція з @@en|критична секція@@ не розпочнеться до того, як маска переривань буде остаточно активована в апаратних регістрах ядра.

Подібні механізми діють і в інших мікропроцесорних архітектурах. Наприклад, у ядрах RISC-V вимкнення переривань виконується атомною зміною регістру керування та стану `mstatus` через команду `csrc mstatus, MIE`. Щоб запобігти спекулятивному переупорядкуванню доступу до пам'яті шинним контролером, після команди маскування вставляється апаратна інструкція `fence`. У 8-бітних мікроконтролерах AVR з модифікацією регістру `SREG` через інструкцію `CLI` конвеєр має просту одностадійну структуру, проте компілятор все одно вимагає програмного бар'єру пам'яті для запобігання оптимізаціям перестановки виразів під час компіляції.

Загальний час виконання інтерфейсу @@en|маскування переривань@@ та самої захищеної ділянки обчислюється з урахуванням накладних витрат процесорного ядра та апаратних бар'єрів:

    T_exec = N_inst × T_cyc + T_barrier
    = N_inst × T_cyc + (T_dsb + T_isb)      [декомпозиція часових затримок синхронізації]

У цій формулі символ `T_exec` позначає повний час виконання @@en|критична секція@@, `N_inst` — кількість корисних команд усередині секції, `T_cyc` — тривалість одного такту процесорної частоти, `T_barrier` — сумарний час виконання бар'єрів, а `T_dsb` та `T_isb` — кількість тактів, необхідних для очищення шинного буфера та перезавантаження конвеєра інструкцій.

З наведеного розрахунку видно, що накладні витрати на виклик процедур маскування мають бути мінімальними. Виклики стандартних функцій з інших модулів створюють додаткові інструкції збереження регістрів у стеку `PUSH` та відновлення `POP`, що значно збільшує сумарну затримку. Тому низькорівневий інтерфейс маскування реалізують виключно у вигляді вбудованих подібних функцій (від англ. *inline functions*) або компіляторних інтринсиків.

Розглянемо практичну реалізацію низькорівневого маскування з урахуванням апаратних бар'єрів для архітектур ARM Cortex-M та RISC-V на мовах C та C++.

:::tabs
@tab C (Bare-Metal)
```c|baremetal
#include <stdint.h>

// Базові визначення регістрів для ARM Cortex-M та RISC-V
#if defined(__ARM_ARCH)
#include "core_cm4.h"
#elif defined(__riscv)
#include <riscv_encoding.h>
#endif

typedef struct {
    uint32_t saved_mask;
} critical_section_t;

// Вхід у критичну секцію з повним апаратним бар'єром
static inline critical_section_t critical_section_enter(void) {
    critical_section_t cs;
#if defined(__ARM_ARCH)
    cs.saved_mask = __get_PRIMASK();
    __disable_irq();
    __DSB();
    __ISB();
#elif defined(__riscv)
    // Зчитати та очистити біт MIE в регістрі mstatus
    cs.saved_mask = __read_and_clear_mstatus_mie();
    __asm__ __volatile__("fence" ::: "memory");
#else
    #error "Непідтримувана апаратна архітектура"
#endif
    return cs;
}

// Вихід з критичної секції з відновленням апаратного стану
static inline void critical_section_exit(critical_section_t cs) {
#if defined(__ARM_ARCH)
    __DSB();
    __set_PRIMASK(cs.saved_mask);
    __ISB();
#elif defined(__riscv)
    __asm__ __volatile__("fence" ::: "memory");
    __restore_mstatus_mie(cs.saved_mask);
#endif
}

// Приклад безпечного атомарного оновлення конфігурації периферії
void hardware_register_update(volatile uint32_t *reg, uint32_t mask, uint32_t val) {
    critical_section_t cs = critical_section_enter();
    uint32_t current = *reg;
    current &= ~mask;
    current |= (val & mask);
    *reg = current;
    critical_section_exit(cs);
}
```
@tab C++ (Bare-Metal)
```cpp|baremetal
#include <cstdint>
#include <atomic>

// Оболочка RAII для апаратного маскування переривань
class [[nodiscard]] HardwareCriticalSection {
public:
    HardwareCriticalSection() noexcept {
#if defined(__ARM_ARCH)
        m_saved_mask = __get_PRIMASK();
        asm volatile ("cpsid i" ::: "memory");
        asm volatile ("dsb\nisb" ::: "memory");
#elif defined(__riscv)
        m_saved_mask = clear_csr_mie();
        asm volatile ("fence" ::: "memory");
#endif
    }

    ~HardwareCriticalSection() noexcept {
#if defined(__ARM_ARCH)
        asm volatile ("dsb" ::: "memory");
        __set_PRIMASK(m_saved_mask);
        asm volatile ("isb" ::: "memory");
#elif defined(__riscv)
        asm volatile ("fence" ::: "memory");
        restore_csr_mie(m_saved_mask);
#endif
    }

    // Видалення конструкторів копіювання та переміщення
    HardwareCriticalSection(const HardwareCriticalSection&) = delete;
    HardwareCriticalSection& operator=(const HardwareCriticalSection&) = delete;
    HardwareCriticalSection(HardwareCriticalSection&&) = delete;
    HardwareCriticalSection& operator=(HardwareCriticalSection&&) = delete;

private:
    uint32_t m_saved_mask{0};

#if defined(__riscv)
    static inline uint32_t clear_csr_mie() noexcept {
        uint32_t res;
        asm volatile ("csrrci %0, mstatus, 8" : "=r"(res) :: "memory");
        return res;
    }

    static inline void restore_csr_mie(uint32_t mask) noexcept {
        if (mask & 8) {
            asm volatile ("csrrs x0, mstatus, 8" ::: "memory");
        }
    }
#endif
};

// Приклад використання C++ оболонки для захисту лічильника системних подій
void increment_system_counter(volatile uint64_t &counter) {
    HardwareCriticalSection guard;
    counter++; // Атомарне інкрементування 64-бітного значення на 32-бітній архітектурі
}
```

У наведеній С++ реалізації атрибут `[[nodiscard]]` запобігає поширеній помилці розробника, коли об'єкт `HardwareCriticalSection` створюється як тимчасовий без присвоєння імені змінній. У випадку безіменного створення деструктор об'єкта спрацьовує негайно у тому ж рядку коду, і @@en|критична секція@@ залишається повністю незахищеною для наступних операцій.

## Практичне застосування та відлагодження

Налагодження коду з маскуванням переривань вимагає глибокого розуміння граничних випадків, оскільки помилки в критичних секціях проявляються несистематично під час високого навантаження на систему. Найбільш розповсюдженою деструктивною пасткою є перевищення допустимої тривалості вимкненого стану переривань. Якщо всередині захищеного блоку розробник розміщує складні обчислювальні цикли або функції обробки масивів, тривалість `T_mask_max` починає перевищувати інтервал обслуговування системного таймера. В результаті мікроконтролер пропускає тактові переривання операційної системи реального часу RTOS, через що порушується відлік системного часу, а апаратний @@en|сторожовий таймер@@ (від англ. *watchdog timer*, з англ. *watchdog* — сторожовий собака, та *timer* — вимірювач часу) не отримує сигналу скидання і примусово перезавантажує мікроконтролер.

Другою критичною пасткою є @@en|інверсія пріоритетів@@ (від англ. *priority inversion*, з лат. *inversio* — перевертання, та *prior* — первинний). Коли низькопріоритетна задача входить у критичну секцію шляхом глобального вимкнення переривань, вона тимчасово блокує виконання навіть найважливіших обробників апаратних аварійних сигналів, таких як захист силових ключів від перевантаження за струмом. Поки триває глобальне маскування, високопріоритетні переривання чекають у черзі контролера `NVIC`, викликаючи часовий тремтіння сигналів, який називають @@en|джиттер@@ (від англ. *jitter* — тремтіння).

Третя поширена помилка пов'язана з викликом плануючих функцій RTOS або затримуючих системних викликів усередині маскованого блоку. Якщо програма викликає функцію перемикання контексту задач при заблокованих перериваннях, системний планировщик передає управління іншій задачі, зберігаючи прапорець `PRIMASK` у заблокованому стані. В результаті нова задача запускається при вимкнених перериваннях, зупиняючи обробку будь-яких зовнішніх подій, що викликає повне @@en|взаємне блокування@@ (від англ. *deadlock*, з англ. *dead* — мертвий, та *lock* — замок) системи.

Особливе місце посідають немасковані переривання NMI. Оскільки апаратне ядро не може заблокувати NMI через регістри `PRIMASK` чи `BASEPRI`, спроба захистити спільний ресурс звичайним маскуванням виявиться марною: якщо обробник NMI прочитає структуру даних під час її оновлення в основній програмі, [виникають перегони даних](root:sf-tasks/data-races-locks), що призведуть до пошкодження пам'яті. Для захисту від NMI розробники застосовують безблокові структури даних або [застосування спін-замка](root:sf-tasks/spinlock) з апаратними атомарними прапорцями.

Для точного вимірювання тривалості критичних секцій та виявлення небезпечних затримок у реальному часі застосовують метод апаратного трасування через лінії GPIO та логічний аналізатор. На початку критичної секції програма встановлює високий логічний рівень на вільній ніжці мікроконтролера, а при виході скидає її в нуль.

*Осцилограма сигналів керування GPIO та апаратного переривання, що показує збільшення затримки реакції.*

Як видно з діаграми, тривалість імпульсу на лінії GPIO відповідає реальному часу `T_mask`. Якщо апаратне переривання виникає під час високого рівня сигнальної лінії, обробник не може розпочати виконання до моменту її спаду, що наочно демонструє природу @@en|затримка переривання@@.

Окрім зовнішнього осцилографа, у прошивку вбудовують програмні діагностичні захисні блоки (від англ. *debug assertions*), які використовують лічильники тактів процесора `DWT->CYCCNT` (від англ. *Data Watchpoint and Trace*). Якщо виміряна тривалість секції перевищує заданий поріг, система фіксує помилку.

@tab C (Diagnostic Profiler)
```c|baremetal
#include <stdint.h>
#include <stdbool.h>
#include "core_cm4.h"

// Порогове значення максимальної тривалості критичної секції в тактах процесора
#define MAX_ALLOWED_CRITICAL_CYCLES 500U

typedef struct {
    uint32_t saved_primask;
    uint32_t start_cycles;
} diag_critical_section_t;

// Вхід у діагностичну критичну секцію
static inline diag_critical_section_t diag_critical_enter(void) {
    diag_critical_section_t cs;
    cs.saved_primask = __get_PRIMASK();
    __disable_irq();
    __DSB();
    
    // Зчитування поточного значення лічильника тактів DWT
    cs.start_cycles = DWT->CYCCNT;
    return cs;
}

// Вихід з перевіркою тривалості виконання
static inline void diag_critical_exit(diag_critical_section_t cs) {
    uint32_t elapsed_cycles = DWT->CYCCNT - cs.start_cycles;
    __set_PRIMASK(cs.saved_primask);
    __ISB();
    
    // Якщо тривалість перевищила поріг, зупиняємо систему для відлагодження
    if (elapsed_cycles > MAX_ALLOWED_CRITICAL_CYCLES) {
        // Фіксація аварійної події в системному журналі
        __asm__ __volatile__("bkpt #0");
    }
}

// Приклад використання відлагоджувальної критичної секції
void process_critical_telemetry(uint32_t *sensor_data, uint32_t len) {
    diag_critical_section_t cs = diag_critical_enter();
    for (uint32_t i = 0; i < len; ++i) {
        sensor_data[i] = sensor_data[i] * 2U;
    }
    diag_critical_exit(cs);
}
```

@tab C++ (Diagnostic Guard)
```cpp|baremetal
#include <cstdint>
#include "core_cm4.h"

// C++ RAII Guard з автоматичною діагностикою часових затримок
template <uint32_t MaxCycles = 500U>
class [[nodiscard]] DiagnosticCriticalGuard {
public:
    DiagnosticCriticalGuard() noexcept 
        : m_saved_primask(__get_PRIMASK()),
          m_start_cycles(DWT->CYCCNT) {
        __disable_irq();
        __DSB();
        __ISB();
    }

    ~DiagnosticCriticalGuard() noexcept {
        uint32_t elapsed = DWT->CYCCNT - m_start_cycles;
        __DSB();
        __set_PRIMASK(m_saved_primask);
        __ISB();

        if (elapsed > MaxCycles) {
            on_threshold_exceeded(elapsed);
        }
    }

    DiagnosticCriticalGuard(const DiagnosticCriticalGuard&) = delete;
    DiagnosticCriticalGuard& operator=(const DiagnosticCriticalGuard&) = delete;

private:
    uint32_t m_saved_primask;
    uint32_t m_start_cycles;

    void on_threshold_exceeded(uint32_t elapsed) noexcept {
        // Обробити ситуацію перевищення ліміту часу (наприклад, викликом тригера відлагодження)
        (void)elapsed;
        asm volatile ("bkpt #1");
    }
};

// Приклад безпечного використання діагностичного об'єкта
void safe_telemetry_update(uint32_t &value) {
    DiagnosticCriticalGuard<300U> guard; // Максимум 300 тактів для цієї операції
    value += 42U;
}
```
