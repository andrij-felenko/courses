Коли програма виконується в одному потоці, функції спираються на непорушну аксіому: пам'ять процесу належить виключно поточному потоку інструкцій, а будь-які проміжні зміни змінних між рядками коду залишаються недоторканими. Проте, коли в спільний адресний простір одночасно входять кілька потоків виконання на різних процесорних ядрах, ця послідовна інтуїція руйнується. Якщо функція змінює спільні змінні в купі чи сегменті статичних даних без спеціальної координації, апаратні інструкції різних ядер довільно чергуються в часі. Результатом стають спотворені структури даних, втрачені оновлення, пошкодження вказівників і раптові аварійні збої, які неможливо відтворити у звичайному покроковому налагодженні.

Властивість програмного модуля, функції або структури даних функціонувати коректно, передбачувано та відповідно до своєї специфікації під час довільного одночасного виклику з багатьох паралельних потоків називають **потоковою безпекою** (від англ. *thread safety* — безпека ниток виконання).

### Природа проблеми: як паралелізм руйнує контракт функцій

Щоб зрозуміти, чому функції втрачають працездатність у багатопотоковому середовищі, необхідно розглянути розподіл пам'яті процесу на апаратному та системному рівнях.

Кожен потік виконання операційної системи володіє власним незалежним стеком викликів і власним набором процесорних регістрів (включно із вказівником стека `RSP` та лічильником команд `RIP`). Усі локальні змінні, передані за значенням аргументи та адреси повернення, що розміщуються у стековому фреймі, є фізично ізольованими: потік A не може випадково затерти локальну змінну функції у стеку потоку B, оскільки їхні стеки розташовані за різними віртуальними адресами.

Проте всі потоки одного процесу ділять спільні сегменти пам'яті:
1. **Динамічна пам'ять (Купа / Heap):** об'єкти, виділені через `malloc` або `new`.
2. **Сегмент ініціалізованих даних (`.data`):** глобальні змінні та статичні змінні функцій із початковими значеннями.
3. **Сегмент неініціалізованих даних (`.bss`):** глобальні та статичні змінні, ініціалізовані нулем.
4. **Системні ресурси:** спільні файлові дескриптори, мережеві сокети, обробники сигналів.

```
+-------------------------------------------------------------------------------+
| АДРЕСНИЙ ПРОСТІР БАГАТОПОТОКОВОГО ПРОЦЕСУ                                      |
+-------------------------------------------------------------------------------+
|  +---------------------+   +---------------------+   +---------------------+  |
|  | Стек Потоку 1       |   | Стек Потоку 2       |   | Стек Потоку 3       |  |
|  | [Локальні змінні]   |   | [Локальні змінні]   |   | [Локальні змінні]   |  |
|  | [Адреси повернення] |   | [Адреси повернення] |   | [Адреси повернення] |  |
|  | (ІЗОЛЬОВАНО)        |   | (ІЗОЛЬОВАНО)        |   | (ІЗОЛЬОВАНО)        |  |

|  +-------------------------------------------------------------------------+  |
|  | СПІЛЬНІ СЕГМЕНТИ ПАМ'ЯТІ (СПІЛЬНИЙ ДОСТУП УСІХ ПОТОКІВ)                 |  |
|  |                                                                         |  |
|  |  • Динамічна купа (Heap): об'єкти malloc() / new                       |  |
```

Потокова небезпека виникає тоді, коли функція порушує межі свого ізольованого стека і звертається до неконстантного спільного стану без протоколу координації. Стан, який одночасно доступний для кількох потоків і може змінюватися хоча б одним із них, називають **спільним мутабельним станом** (від англ. *shared mutable state*).

Розглянемо класичний приклад генератора унікальних ідентифікаторів:

:::tabs
```c
/* Потоконебезпечний генератор ідентифікаторів */
static unsigned long g_next_id = 1;

unsigned long generate_id_unsafe(void) {
    return g_next_id++;
}
```
```cpp
/* Потоконебезпечний генератор ідентифікаторів */
namespace unsafe_generator {

static unsigned long g_next_id = 1;

unsigned long generate_id() noexcept {
    return g_next_id++;
}

} // namespace unsafe_generator
```
:::

Для програміста `g_next_id++` — це один вираз. Проте процесор виконує його як послідовність із трьох кроків:
1. Зчитування значення `g_next_id` з оперативної пам'яті в регістр процесора.
2. Додавання одиниці до регістра в арифметико-логічному пристрої (АЛП).
3. Запис оновленого значення з регістра назад у спільну пам'ять.

Якщо два потоки на різних ядрах одночасно зчитають початкове значення `100`, обидва обчислять `101` і обидва запишуть `101`. У результаті два різні клієнти отримають однаковий ідентифікатор транзакції, а одне збільшення лічильника буде втрачено. У програмі виникла **гонка даних** (від англ. *data race*).

> 🔧 **Навіщо це розуміти.** Потокова безпека — це не абсолютна бінарна властивість коду («безпечний» або «небезпечний»), а сукупність чітких контрактів між автором компонента та його користувачем. Розуміння рівнів безпеки дозволяє обирати мінімально достатній рівень синхронізації, уникаючи як катастрофічних аварій пам'яті, так і надмірних накладних витрат на блокування.

### Спектр і рівні потокової безпеки (Thread Safety Levels)

В інженерній практиці програмні компоненти класифікують за шкалою гарантій, які вони надають щодо паралельного виконання. Загальновизнана класифікація (формалізована в бібліотеках POSIX, Windows API, Qt та стандартизована в C++) виділяє п'ять рівнів безпеки.

![Спектр і рівні потокової безпеки коду](/root/eng/sf-tasks/thread-safety/img/thread-safety-levels.svg)
*Класифікація рівнів потокової безпеки: від повної ізоляції локального стека до несинхронізованих глобальних мутацій.*

#### 1. Потоконебезпечний код (Thread-Unsafe)
Компонент містить несинхронізовані звернення до спільного стану. Одночасний виклик функцій або методів об'єкта з кількох потоків призводить до гонок даних, руйнування внутрішньої структури та невизначеної поведінки (Undefined Behavior).
*Приклади:* застарілі функції C `strtok()`, `asctime()`, `rand()`, несинхронізовані глобальні структури даних.

#### 2. Прив'язаний до потоку / Локалізований (Thread-Affinity / Thread-Confined)
Об'єкт або функція спроектовані так, що коректно працюють лише всередині одного конкретного потоку (наприклад, того, де об'єкт було створено). Звернення до такого об'єкта з будь-якого іншого потоку є неприпустимим, навіть якщо в цей момент перший потік нічого не викликає.
*Приклади:* графічні віджети (GUI-компоненти в Qt, GTK, Win32), контексти візуалізації OpenGL/Vulkan, однопотокові апартаменти COM (Single-Threaded Apartments), цикл подій `libuv`.

#### 3. Умовно потокобезпечний код (Conditionally Thread-Safe / Basic Safety)
Різні потоки можуть одночасно та безпечно працювати з **різними екземплярами** об'єкта без будь-якої синхронізації. Проте, якщо кілька потоків одночасно звертаються до **одного й того самого екземпляра**, і хоча б один із них викликає модифікуючий метод, викликач зобов'язаний самостійно організувати зовнішню синхронізацію (наприклад, захопити зовнішній м'ютекс). Одночасне читання одного екземпляра багатьма потоками (виклики `const`-методів) є повністю безпечним.
*Приклади:* контейнери стандартної бібліотеки C++ (`std::vector`, `std::string`, `std::map`), класи стандартних бібліотек більшості мов програмування.

#### 4. Потокобезпечний код (Thread-Safe / Strong Safety)
Об'єкт самостійно керує всією необхідною внутрішньою синхронізацією. Довільна кількість потоків може паралельно викликати будь-які операції (як читання, так і запис) над одним екземпляром об'єкта, не потребуючи зовнішніх замків з боку користувача.
*Приклади:* черги завдань із внутрішнім блокуванням (`concurrent_queue`), атомарні типи (`std::atomic<T>`), потокобезпечні пули з'єднань із базами даних.

#### 5. Реентрабельний код (Reentrant)
Функція не має жодного внутрішнього стану, не звертається до неконстантних глобальних чи статичних змінних і оперує виключно даними, наданими викликачем через стек та аргументи. Функцію можна в будь-який момент перервати посеред виконання (іншим потоком, рекурсивним викликом або асинхронним сигналом операційної системи), увійти в неї знову з іншими параметрами і після повернення безпечно продовжити виконання першого виклику.
*Приклади:* чисті математичні функції (`sin`, `sqrt`), функції копіювання пам'яті (`memcpy`), реентрабельні двійники POSIX (`strtok_r`, `gmtime_r`).

### Реентрабельність проти потокової безпеки: принципова відмінність

У літературі поняття потокової безпеки та реентрабельності часто помилково ототожнюють. Проте між ними існує глибока алгоритмічна та архітектурна межа, закладена фундаментальним визначенням терміна.

Властивість алгоритму або підпрограми бути безпечно перерваною в будь-якій точці виконання з можливістю повторного входу в цю саму функцію до завершення попереднього виклику називають **реентрабельністю** або **повторною вхідністю** (від лат. *re-* — знову та *intra-* — входити, англ. *reentrancy*).

Головна відмінність полягає в **джерелі конкурентності**:
- **Потокова безпека** вирішує проблему *паралельного* виконання коду кількома потоками на різних ядрах процесора у спільній пам'яті.
- **Реентрабельність** вирішує проблему *асинхронного переривання* виконання всередині **одного й того самого потоку** (наприклад, коли ядро ОС надсилає процесу сигнал `SIGINT` або спрацьовує апаратне переривання таймера).

![Матриця відмінностей: реентрабельність та потокобезпечність](/root/eng/sf-tasks/thread-safety/img/reentrancy-vs-thread-safety.svg)
*Взаємозв'язок реентрабельності та потокової безпеки: вплив джерел стану та безпека щодо сигналів.*

Розглянемо чотири можливі комбінації цих властивостей:

```
+-----------------------------------+-----------------------------------+
| НЕ РЕЕНТРАБЕЛЬНИЙ                 | ПОТОКОБЕЗПЕЧНИЙ                   |
| НЕ ПОТОКОБЕЗПЕЧНИЙ                | АЛЕ НЕ РЕЕНТРАБЕЛЬНИЙ             |
|                                   |                                   |
| • Функція: strtok(), asctime()    | • Функція: malloc(), syslog()     |
| • Стан: спільний статичний буфер  | • Стан: внутрішній м'ютекс        |
| • Сигнали: руйнують проміжний стан| • Сигнали: САМОБЛОКУВАННЯ (DEADLOCK)
+-----------------------------------+-----------------------------------+
| РЕЕНТРАБЕЛЬНИЙ                    | РЕЕНТРАБЕЛЬНИЙ І                  |
| АЛЕ УМОВНО ПОТОКОБЕЗПЕЧНИЙ        | ПОВНІСТЮ ПОТОКОБЕЗПЕЧНИЙ          |
|                                   |                                   |
| • Функція: swap(a, b), strtok_r() | • Функція: sin(x), strlen()       |
| • Стан: лише аргументи викликача  | • Стан: чиста функція / const     |

|   один вказівник з 2 потоків      | • Сигнали: 100% безпека           |
+-----------------------------------+-----------------------------------+
```

#### Чому потокобезпечна функція може бути НЕ реентрабельною (Пастка м'ютекса)
Уявімо функцію ведення системного журналу, яка захищає запис у файл внутрішнім замком (м'ютексом):

:::tabs
```c
#include <pthread.h>
#include <stdio.h>

static pthread_mutex_t g_log_lock = PTHREAD_MUTEX_INITIALIZER;

void log_message_safe(const char *msg) {
    pthread_mutex_lock(&g_log_lock);
    /* Критична секція запису в лог */
    printf("[LOG]: %s\n", msg);
    pthread_mutex_unlock(&g_log_lock);
}
```
```cpp
#include <mutex>
#include <iostream>
#include <string_view>

namespace safe_logger {

static std::mutex g_log_mutex{};

void log_message(std::string_view msg) {
    std::lock_guard<std::mutex> guard(g_log_mutex);
    /* Критична секція запису в лог */
    std::cout << "[LOG]: " << msg << '\n';
}

} // namespace safe_logger
```
:::

Ця функція є **потокобезпечною**: якщо десять потоків одночасно викличуть `log_message()`, м'ютекс вишикує їх у чергу, і записи не перемішаються.

Тепер припустимо, що Потік 1 викликає `log_message()`, успішно захоплює м'ютекс `g_log_lock` і входить у критичну секцію. У цей самий момент ядро операційної системи доставляє цьому потоку асинхронний сигнал (наприклад, `SIGUSR1`). Виконання коду негайно призупиняється, і процесор перемикається на виконання функції-обробника сигналу (`signal handler`).

Якщо обробник сигналу також спробує викликати `log_message("Signal received")`, функція спробує захопити м'ютекс `g_log_lock`. Проте цей замок уже належить Потоку 1, який зараз призупинений і чекає на завершення обробника сигналу! Виникає миттєве невідворотне самоблокування — **дедлок** (від англ. *deadlock*). Програма зависає назавжди.

Саме тому стандарт POSIX суворо розрізняє поняття потокової безпеки та **безпеки щодо асинхронних сигналів** (англ. *async-signal safety*). Усередині обробників сигналів дозволено викликати виключно обмежений перелік реентрабельних системних викликів (`write`, `_exit`), і категорично заборонено використовувати замки та функції розподілу пам'яті (`malloc`, `free`).

### Апаратний рівень: моделі пам'яті, буфери запису та перевпорядкування

Багато інженерів помилково вважають, що потокова небезпека вичерпується лише чергуванням високорівневих рядків коду. Проте сучасні процесори та оптимізуючі компілятори вносять значно тонші та небезпечніші аномалії: **перевпорядкування пам'яті** (англ. *memory reordering*).

#### Буфери збереження (Store Buffers) та черги інвалідації
Коли процесорне ядро записує дані в комірку пам'яті, воно не чекає підтвердження віддалених кешів інших ядер через між'ядерну шину. Ядро поміщає запис у власний внутрішній апаратний буфер запису (Store Buffer) і миттєво переходить до виконання наступних інструкцій.

Через це виникає фізичний ефект:
- Ядро 1 виконує запис у змінну `A`, а потім запис у змінну `B`.
- Ядро 2 на сусідньому сокеті може прочитати нове значення `B`, але все ще бачити старе значення `A`!

Без спеціальних апаратних інструкцій бар'єрів пам'яті (Memory Barriers / Fences) процесор із слабкою моделлю пам'яті (наприклад, ARM64, POWER або RISC-V) не гарантує однакового порядку спостереження операцій між різними ядрами. Навіть на архітектурі x86-64 з відносно строгою моделлю TSO (Total Store Order) апаратні буфери запису допускають перевпорядкування типу `Store-Load` (запис може затриматися відносно наступного читання іншої комірки).

#### Оптимізації компілятора
Оптимізуючий компілятор (GCC або Clang із прапорцем `-O2` / `-O3`) перевпорядковує інструкції, видаляє «зайві» на його погляд операції читання та кешує змінні в реєстрах процесора. Якщо змінна не оголошена як атомарна або не захищена бар'єрами, компілятор розглядає функцію так, ніби вона виконується в одному потоці. Класичний цикл очікування прапорця `while (!flag) {}` компілятор може оптимізувати в нескінченний цикл `if (!flag) while (true) {}`, якщо він не бачить модифікацій прапорця всередині тіла циклу.

### Двохетапна ініціалізація та пастка Double-Checked Locking (DCLP)

Найвідомішим прикладом того, як перевпорядкування інструкцій руйнує очевидну потокову безпеку, є пастка блокування з подвійною перевіркою (Double-Checked Locking Pattern, DCLP).

У спробі уникнути накладних витрат на захоплення м'ютекса під час кожного звернення до єдиного об'єкта (патерн Singleton), розробники тривалий час використовували таку ідіому:

:::tabs
```cpp
/* ІСТОРИЧНО ЗЛАМАНА РЕАЛІЗАЦІЯ DOUBLE-CHECKED LOCKING (C++03) */
class BrokenSingleton {
public:
    static BrokenSingleton* get_instance() {
        if (instance_ == nullptr) { // Перша перевірка (без замка)
            std::lock_guard<std::mutex> lock(mutex_);
            if (instance_ == nullptr) { // Друга перевірка (під замком)
                instance_ = new BrokenSingleton(); // НЕБЕЗПЕКА!
            }
        }
        return instance_;
    }
private:
    static BrokenSingleton* instance_;
    static std::mutex mutex_;
};
```
```c
/* ІСТОРИЧНО ЗЛАМАНА РЕАЛІЗАЦІЯ ДВОХЕТАПНОЇ ІНІЦІАЛІЗАЦІЇ */
typedef struct {
    int data;
} Resource;

static Resource *g_resource = NULL;
static pthread_mutex_t g_init_lock = PTHREAD_MUTEX_INITIALIZER;

Resource *get_resource_broken(void) {
    if (g_resource == NULL) {
        pthread_mutex_lock(&g_init_lock);
        if (g_resource == NULL) {
            Resource *res = (Resource *)malloc(sizeof(Resource));
            res->data = 42; // Ініціалізація полів
            g_resource = res; // Публікація вказівника
        }
        pthread_mutex_unlock(&g_init_lock);
    }
    return g_resource;
}
```
:::

#### Анатомія катастрофи:
Вираз `instance_ = new BrokenSingleton()` складається з трьох послідовних кроків:
1. Виділення пам'яті під об'єкт `operator new(sizeof(BrokenSingleton))`.
2. Виклик конструктора `BrokenSingleton()` для ініціалізації полів.
3. Присвоєння адреси виділеної пам'яті змінній `instance_`.

Оскільки процесор та компілятор мають право перевпорядковувати кроки, крок 3 може виконатися **раніше** за крок 2! Вказівник `instance_` вже не дорівнює `nullptr`, але конструктор об'єкта ще не завершився.

Якщо в цей мікросекундний інтервал інший потік викликає `get_instance()`, він бачить, що `instance_ != nullptr` на першій перевірці, пропускає захоплення замка і повертає вказівник на **напівсконструйований об'єкт**. Перша ж спроба прочитати поля цього об'єкта призводить до читання сміття або фатального збою.

#### Сучасне розв'язання в C++11 та C:
У сучасному стандарті C++11 цю проблему вирішено на рівні мови завдяки потокобезпечній ініціалізації локальних статичних змінних (так звані «магічні статики» Мейєрса):

:::tabs
```cpp
/* ПОВНІСТЮ ПОТОКОБЕЗПЕЧНИЙ SINGLETON (C++11 Meyer's Singleton) */
class ModernSingleton {
public:
    static ModernSingleton& get_instance() {
        // Стандарт C++11 гарантує потокобезпечну ініціалізацію під час першого виклику
        static ModernSingleton instance;
        return instance;
    }
private:
    ModernSingleton() = default;
};
```
```c
#include <pthread.h>
#include <stdlib.h>

/* КОРЕКТНА ІНІЦІАЛІЗАЦІЯ ЧЕРЕЗ pthread_once */
static pthread_once_t g_init_once = PTHREAD_ONCE_INIT;
static Resource *g_safe_resource = NULL;

static void init_resource_routine(void) {
    g_safe_resource = (Resource *)malloc(sizeof(Resource));
    g_safe_resource->data = 42;
}

Resource *get_resource_safe(void) {
    pthread_once(&g_init_once, init_resource_routine);
    return g_safe_resource;
}
```
:::

### Джерела проблем: приховані статичні буфери та спадщина C

Історично мова C створювалася в епоху однопотокових операційних систем на комп'ютерах з украй обмеженим обсягом пам'яті. Щоб не витрачати ресурси на копіювання великих структур через стек, творці стандартної бібліотеки повертали вказівники на статичні масиви всередині бібліотеки.

Найвідомішим прикладом такої архітектурної пастки є функція розбиття рядка на лексеми `strtok()`:

![Анатомія гонки у strtok проти ізоляції в strtok_r](/root/eng/sf-tasks/thread-safety/img/strtok-race-vs-reentrant.svg)
*Порівняння виконання strtok() зі спільним статичним буфером та strtok_r() з ізольованими стековими вказівниками.*

Під час першого виклику `strtok(str, delim)` функція зберігає адресу залишку рядка у прихованій статичній змінній `static char* last_ptr`. Під час наступних викликів `strtok(NULL, delim)` функція читає цю приховану змінну.

Якщо два потоки починають розбирати різні рядки одночасно:
1. Потік 1 викликає `strtok("user/admin/root", "/")`. Змінна `last_ptr` починає вказувати на `"admin/root"`.
2. Потік 2 на сусідньому ядрі викликає `strtok("192.168.1.1", ".")`. Змінна `last_ptr` перезаписується адресою `"168.1.1"`.
3. Потік 1 робить наступний крок `strtok(NULL, "/")`. Замість власного рядка він зчитує залишок IP-адреси Потоку 2!

Стандарт POSIX.1c-1995 подолав цю кризу, ввівши реентрабельний аналог `strtok_r()`, де параметр `saveptr` передається явно як вказівник на локальну змінну викликача на стеку:

:::tabs
```c
#include <string.h>
#include <stdio.h>

void parse_tokens_reentrant(char *input_str) {
    char *saveptr = NULL;
    char *token = strtok_r(input_str, " ", &saveptr);
    while (token != NULL) {
        printf("Лексема: %s\n", token);
        token = strtok_r(NULL, " ", &saveptr);
    }
}
```
```cpp
#include <string_view>
#include <iostream>

void parse_tokens_reentrant(std::string_view input) {
    size_t start = 0;
    while (start < input.size()) {
        auto end = input.find(' ', start);
        if (end == std::string_view::npos) {
            end = input.size();
        }
        std::string_view token = input.substr(start, end - start);
        if (!token.empty()) {
            std::cout << "Лексема: " << token << '\n';
        }
        start = end + 1;
    }
}
```
:::

Детальний аналіз історичних передумов, суперечок навколо стандартизації та еволюції змінної `errno` від глобальної пам'яті до потоково-локального макросу наведено у вставці [Еволюція потокової безпеки в стандарті POSIX](root:sf-tasks/thread-safety/hist-posix-r-evolution.md). Повну матрицю небезпечних викликів libc та їхніх сучасних реентрабельних замін наведено у довідці [Порівняльна довідка потокобезпечних і реентрабельних функцій POSIX](root:sf-tasks/thread-safety/api-posix-reentrant-matrix.md).

### Фундаментальні стратегії забезпечення потокової безпеки

Для побудови надійної багатопотокової системи інженери використовують чотири базові стратегії керування станом. Кожна з них пропонує власний компроміс між складністю проектування, витратами пам'яті та максимальною пропускною здатністю.

![Фундаментальні стратегії забезпечення потокової безпеки](/root/eng/sf-tasks/thread-safety/img/thread-safety-strategies.svg)
*Чотири архітектурні підходи до безпеки стану: незмінність, локалізація, блокування та безблоковість.*

#### Стратегія 1: Незмінність (Immutability)
Найпростіший і найбільш ефективний спосіб забезпечити потокову безпеку — це повна заборона модифікації даних після їх створення.

Властивість об'єкта не змінювати свій внутрішній стан протягом усього часу життя після завершення конструктора називають **незмінністю** (від лат. *immutabilis* — незмінний, англ. *immutability*).

Якщо дані доступні лише для читання (`const` або `readonly`), будь-яка кількість потоків може паралельно звертатися до них без жодних замків, атомарних інструкцій чи бар'єрів пам'яті. Це дає 100% масштабованість та ідеальну утилізацію кешів процесора (стан кеш-ліній `Shared` у протоколі MESI без інвалідацій). Якщо стан необхідно оновити, створюється новий незмінний об'єкт, а вказівник на нього замінюється атомарно (патерн *Copy-on-Write*).

Парадигма Read-Copy-Update (RCU), поширена в ядрі Linux та високонавантажених базах даних, розвиває цю ідею: читачі взагалі не виконують жодних синхронізуючих записів у пам'ять, а письменники створюють копію структури, оновлюють її і підміняють вказівник, відкладаючи звільнення старої пам'яті до моменту, коли всі активні читачі завершать роботу (пільговий період / grace period).

#### Стратегія 2: Локалізація в потоці (Thread-Local Storage / Confinement)
Якщо стан не можна зробити незмінним, його можна повністю розділити: кожен потік отримує власний ізольований екземпляр змінної.

Механізм операційної системи та компілятора, який виділяє окрему ділянку пам'яті для кожної змінної індивідуально для кожного потоку виконання, називають **локальною пам'яттю потоку** (від англ. *Thread-Local Storage*, *TLS*).

У мові C для цього використовують специфікатор `_Thread_local`, у C++ — ключове слово `thread_local`. Звернення до таких змінних відбувається через пряме зміщення від спеціального сегментного регістра процесора (`FS` на архітектурі x86-64), що не створює жодного між'ядерного трафіку і не потребує замків.

#### Стратегія 3: Взаємне виключення (Mutual Exclusion / Synchronization)
Якщо кілька потоків зобов'язані читати та модифікувати єдиний спільний екземпляр об'єкта, доступ до нього захищають примітивами синхронізації.

Пристрій синхронізації, що гарантує доступ до захищеного ресурсу лише одному потоку одночасно, називають **м'ютексом** або **замком** (від лат. *mutua exclusio* — взаємне виключення, англ. *mutex*).

Сучасна дисципліна синхронізації вимагає суворого дотримання патерну **RAII** (Resource Acquisition Is Initialization), коли замок захоплюється в конструкторі спеціального охоронця (`std::lock_guard` або `std::unique_lock`) і автоматично гарантовано звільняється в деструкторі при виході з блоку видимості.

При виборі між ексклюзивним м'ютексом та замком читачів-письменників (`std::shared_mutex`) слід враховувати: RW-замок дає виграш лише тоді, коли частка читачів перевищує 90%, а тривалість читання є значною. В іншому випадку накладні витрати на атомарний лічильник читачів роблять RW-замок повільнішим за простий м'ютекс.

#### Стратегія 4: Безблокові атомарні операції (Lock-Free Atomics)
Для базових типів даних (числа, вказівники) сучасні процесори надають неподільні апаратні інструкції читання-модифікації-запису (наприклад, `LOCK CMPXCHG` на x86).

Операцію, яка виконується процесором як єдиний неподільний крок, що не може бути перерваний іншим ядром або перемиканням контексту, називають **атомарною операцією** (від грец. *ἄτομος* — неподільний, англ. *atomic operation*).

Застосування атомарних типів (`std::atomic<T>`) дозволяє змінювати стан без блокування потоків у ядрі ОС, що усуває небезпеку дедлоків та гарантує системний прогрес.

Кількісний аналіз накладних витрат блокувань, моделювання черг затримок та оцінку падіння продуктивності за законом Гюнтера розкрито у вставці [Математична модель ціни синхронізації та закон Амдала](root:sf-tasks/thread-safety/math-safety-contention.md).

### Апаратні пастки: помилкове розділення (False Sharing)

Під час проектування високопродуктивних потокобезпечних структур даних існує прихована апаратна пастка, яка може сповільнити паралельну програму в десятки разів, навіть якщо в ній немає жодних м'ютексів.

Цей дефект називають **помилковим розділенням пам'яті** (англ. *false sharing*).

Процесор обмінюється даними з оперативною пам'яттю не окремими байтами чи числами, а блоками фіксованого розміру — **кеш-лініями** (типово 64 байти на сучасних архітектурах x86 та ARM).

```
+-------------------------------------------------------------------------------+
| АНАТОМІЯ ПОМИЛКОВОГО РОЗДІЛЕННЯ (FALSE SHARING) У КЕШ-ЛІНІЇ                   |
+-------------------------------------------------------------------------------+
|  КЕШ-ЛІНІЯ (64 БАЙТИ):                                                         |
|  [ Лічильник Потоку 1 (8 байт) ] [ Лічильник Потоку 2 (8 байт) ] [ ...інше ]  |
|                                                                               |
|  Ядро 1 (Потік 1)                   Між'ядерна шина (MESI)      Ядро 2 (Потік 2)|
|  Запис у Лічильник 1  ───────────>  Сигнал RFO (Invalidate) ──> Кеш-лінія стає |
|  (Кеш-лінія: Modified)                                          INVALID!      |
|                                                                               |
|  Кеш-лінія стає       <───────────  Сигнал RFO (Invalidate) <── Запис у         |
|  INVALID!                           (Шина перевантажена)        Лічильник 2   |
+-------------------------------------------------------------------------------+
```

Якщо незалежні лічильники двох потоків розміщені в пам'яті поруч (наприклад, сусідні елементи масиву або сусідні поля однієї структури), вони потрапляють в одну спільну 64-байтну кеш-лінію. Коли Ядро 1 оновлює свій лічильник, апаратний протокол когерентності MESI надсилає сигнал інвалідації (`Invalidate`) у кеш Ядра 2. Коли Ядро 2 оновлює свій лічильник, воно інвалідує кеш Ядра 1.

Ядра не мають конфлікту за даними (кожен потік змінює своє незалежне число), але вони безперервно воюють за спільну кеш-лінію, змушуючи шину пам'яті передавати кеш-лінію туди й назад на кожній ітерації.

*Розв'язання:* вирівнювання незалежних змінних за межею кеш-лінії за допомогою специфікатора вирівнювання (`alignas(64)` у C++11 або `__attribute__((aligned(64)))` у C):

:::tabs
```cpp
#include <new>

// Запобігання помилковому розділенню пам'яті
struct alignas(64) PaddedCounter {
    uint64_t value{0};
};

// Кожен лічильник гарантовано займає власну 64-байтну кеш-лінію
PaddedCounter g_thread_counters[MAX_THREADS];
```
```c
#include <stdint.h>

/* Вирівнювання структури під розмір кеш-лінії 64 байти */
typedef struct {
    uint64_t value;
    uint8_t pad[56]; // Заповнення до 64 байтів
} __attribute__((aligned(64))) PaddedCounter;

PaddedCounter g_thread_counters[64];
```
:::

### Пастки проектування потокобезпечних інтерфейсів (API Design Pitfalls)

Навіть якщо всі окремі методи класу захищені замками, загальний інтерфейс може бути небезпечним через фундаментальні вади проектування. Розглянемо найпоширеніші архітектурні пастки.

#### 1. Ілюзія композиції (Composition Fallacy / Check-Then-Act)
Уявімо потокобезпечну чергу, де методи `empty()`, `size()`, `push()` та `pop()` індивідуально захищені м'ютексом:

:::tabs
```c
/* Помилкова композиція потокобезпечних викликів */
if (!thread_safe_queue_is_empty(q)) {
    /* Небезпека! Інший потік може забрати елемент прямо тут! */
    item_t item = thread_safe_queue_pop(q);
}
```
```cpp
/* Помилкова композиція потокобезпечних викликів */
if (!safe_queue.empty()) {
    // Небезпека! Інший потік може викликати pop() між цими двома рядками!
    auto item = safe_queue.pop();
}
```
```go
// Помилкова композиція двох потокобезпечних операцій
if !safeQueue.IsEmpty() {
    // Інший потік встигає забрати елемент між перевіркою та читанням
    item := safeQueue.Pop()
    _ = item
}
```
:::

Хоча кожен метод окремо є потокобезпечним, між викликом `empty()` та викликом `pop()` існує часовий інтервал, у якому замок звільнено. Якщо сусідній потік забере останній елемент у цей проміжок, виклик `pop()` завершиться аварійним збоєм через спробу зняти елемент із порожньої черги.

*Правильне рішення:* об'єднання перевірки та дії в одну неподільну операцію з атомарним контрактом:

:::tabs
```c
bool thread_safe_queue_try_pop(queue_t *q, item_t *out_item) {
    pthread_mutex_lock(&q->lock);
    if (q->head == NULL) {
        pthread_mutex_unlock(&q->lock);
        return false;
    }
    *out_item = dequeue_internal(q);
    pthread_mutex_unlock(&q->lock);
    return true;
}
```
```cpp
#include <optional>
#include <mutex>
#include <queue>

template <typename T>
class SafeQueue {
public:
    std::optional<T> try_pop() {
        std::lock_guard<std::mutex> guard(mutex_);
        if (data_.empty()) {
            return std::nullopt;
        }
        T item = std::move(data_.front());
        data_.pop();
        return item;
    }
private:
    std::mutex mutex_;
    std::queue<T> data_;
};
```
:::

#### 2. Витік незахищених посилань (Leaky Abstraction)
Якщо метод потокобезпечного класу повертає неконстантне посилання, вказівник або ітератор на внутрішнє поле, захищене замком, клієнтський код отримує прямий доступ до пам'яті в обхід усіх замків.

:::tabs
```c
/* Небезпечний витік внутрішнього буфера */
char *thread_safe_buffer_get_raw(buffer_t *b) {
    pthread_mutex_lock(&b->lock);
    char *ptr = b->internal_data; // Витік вказівника!
    pthread_mutex_unlock(&b->lock);
    return ptr; // Користувач читатиме пам'ять без замка!
}
```
```cpp
/* Небезпечний витік внутрішнього стану */
class LeakyConfig {
public:
    std::string& get_database_url() {
        std::lock_guard<std::mutex> guard(mutex_);
        return db_url_; // Повернення посилання в обхід м'ютекса!
    }
private:
    std::mutex mutex_;
    std::string db_url_;
};
```
:::

*Правильне рішення:* повертати копію значення або приймати функціональний об'єкт (зворотний виклик), який виконує потрібну дію безпосередньо всередині критичної секції під замком.

#### 3. Виклик зовнішнього коду під замком (Alien Methods Trap)
Якщо всередині критичної секції викликається віртуальний метод, зворотний виклик (callback) або обробник подій користувача, виникає небезпека взаємного блокування (дедлоку). Чужий код може спробувати захопити інший замок, порядок взяття якого суперечить глобальній ієрархії замків системи, або знову викликати методи цього самого об'єкта.

*Правило проектування:* критична секція повинна містити виключно мінімальні, детерміновані операції з власними полями; будь-які сповіщення підписників та виклики зовнішніх функцій мають виконуватися **після** звільнення замка.

### Інженерний рефакторинг: практична трансформація модуля

Розглянемо практичну трансформацію реального потоконебезпечного модуля накопичення статистики подій у реентрабельний та повністю синхронізований потокобезпечний компонент.

Повний покроковий розбір коду від однопотокових статичних структур до версій на базі TLS наведено у вставці [Рефакторинг потоконебезпечного модуля: від глобального буфера до reentrant і thread-safe](root:sf-tasks/thread-safety/proj-thread-safe-refactoring.md).

Нижче наведено зразок кінцевої промислової реалізації потокобезпечного агрегатора з можливістю отримання узгодженого знімка метрик:

:::tabs
```c
#include <pthread.h>
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    pthread_mutex_t lock;
    uint64_t total_requests;
    uint64_t total_errors;
} RequestAggregator;

int aggregator_init(RequestAggregator *agg) {
    if (!agg) return -1;
    agg->total_requests = 0;
    agg->total_errors = 0;
    return pthread_mutex_init(&agg->lock, NULL);
}

void aggregator_record(RequestAggregator *agg, bool is_error) {
    if (!agg) return;
    pthread_mutex_lock(&agg->lock);
    agg->total_requests++;
    if (is_error) {
        agg->total_errors++;
    }
    pthread_mutex_unlock(&agg->lock);
}

void aggregator_read_snapshot(RequestAggregator *agg, uint64_t *out_req, uint64_t *out_err) {
    if (!agg) return;
    pthread_mutex_lock(&agg->lock);
    if (out_req) *out_req = agg->total_requests;
    if (out_err) *out_err = agg->total_errors;
    pthread_mutex_unlock(&agg->lock);
}

void aggregator_destroy(RequestAggregator *agg) {
    if (agg) {
        pthread_mutex_destroy(&agg->lock);
    }
}
```
```cpp
#include <mutex>
#include <cstdint>

struct AggregatorSnapshot {
    uint64_t total_requests{0};
    uint64_t total_errors{0};
};

class RequestAggregator {
public:
    void record(bool is_error) noexcept {
        std::lock_guard<std::mutex> guard(mutex_);
        ++total_requests_;
        if (is_error) {
            ++total_errors_;
        }
    }

    [[nodiscard]] AggregatorSnapshot snapshot() const noexcept {
        std::lock_guard<std::mutex> guard(mutex_);
        return {total_requests_, total_errors_};
    }

private:
    mutable std::mutex mutex_{};
    uint64_t total_requests_{0};
    uint64_t total_errors_{0};
};
```

### Інструменти верифікації: динамічний та статичний контроль

Виявлення дефектів потокової безпеки за допомогою звичайного тестування є вкрай неефективним через недетермінізм планувальника ОС. Для гарантії коректності в сучасній системній інженерії застосовують спеціалізовані інструменти.

#### 1. Динамічний аналіз: ThreadSanitizer (TSan)
**ThreadSanitizer** — це інструмент динамічного аналізу, інтегрований у компілятори Clang та GCC (прапорець `-fsanitize=thread`). Він перехоплює всі операції звернення до пам'яті та виклики синхронізації під час виконання програми, будуючи граф причинно-наслідкових зв'язків (відношення *happens-before*). Якщо TSan виявляє два звернення до однієї комірки пам'яті без синхронізації, де хоча б одне є записом, він миттєво генерує детальний звіт із повними стеками викликів обох конфліктуючих потоків.

#### 2. Статичний аналіз: Анотації Clang Thread Safety Analysis
Компілятор Clang містить механізм статичної перевірки блокувань на етапі компіляції. За допомогою спеціальних атрибутів розробник декларує, який саме м'ютекс захищає кожне конкретне поле структури даних:

:::tabs
```cpp
#include <mutex>

class GuardedAccount {
public:
    void deposit(double amount) {
        std::lock_guard<std::mutex> lock(mu_);
        balance_ += amount; // OK: замок mu_ захоплено
    }

    double get_balance_unsafe() const {
        // Помилка компіляції: спроба читання balance_ без захоплення mu_!
        // return balance_; 
        std::lock_guard<std::mutex> lock(mu_);
        return balance_;
    }

private:
    mutable std::mutex mu_;
    // Атрибут guarded_by вказує компілятору на зв'язок поля із замком
    double balance_ [[clang::guarded_by(mu_)]] {0.0};
};
```
```c
#include <pthread.h>

/* Специфікація захисту пам'яті для C (Clang attributes) */
struct SafeCounter {
    pthread_mutex_t lock;
    int value __attribute__((guarded_by(lock)));
};
```
:::

Якщо розробник спробує звернутися до поля `balance_` або `value` без попереднього захоплення відповідного замка, компілятор відхилить збирання програми на етапі статичного аналізу, запобігаючи потраплянню гонок даних у готовий бінарний файл.

### Підсумковий синтез: інженерні правила безпечного проектування

Побудова надійних багатопотокових систем спирається на прості, але непорушні принципи:
1. **Ізоляція за замовчуванням:** Найкраща синхронізація — це її відсутність. Передавайте дані через стек, робіть структури незмінними (Immutability) або використовуйте локальну пам'ять потоків (TLS).
2. **Чітке розмежування реентрабельності:** Пам'ятайте, що м'ютекси роблять функцію потокобезпечною, але роблять її небезпечною для виклику всередині обробників сигналів.
3. **Інкапсуляція стану:** Ніколи не випускайте незахищені посилання чи вказівники на поля, захищені замками, та уникайте ілюзії композиції, об'єднуючи перевірки й дії в єдині атомарні операції.
4. **Уникнення помилкового розділення:** Розділяйте незалежні гарячі лічильники різних ядер вирівнюванням `alignas(64)`, щоб уникнути війни за кеш-лінії.
5. **Автоматичний контроль:** Завжди тестуйте багатопотоковий код під інструментом ThreadSanitizer та використовуйте атрибути статичного контролю компілятора.
