# 🔌 Довідник бар'єрів пам'яті в ядрі Linux

Примітивів упорядкування в ядрі Linux помітно більше, ніж три класичні `smp_wmb()`, `smp_rmb()` і `smp_mb()`, а плутанина між їхніми групами коштує дорого. Найдорожча з помилок — поставити `smp_`-бар'єр там, де потрібен бар'єр введення-виведення: на однопроцесорній збірці ядра (`CONFIG_SMP=n`) він тихо зникне разом із гарантією, на яку розраховував драйвер, і DMA-передача піде з незаповненого дескриптора. Нижче зведено всі групи — бар'єри компілятора, симетричні SMP-бар'єри, семантику Acquire-Release, обов'язкові бар'єри MMIO та правила контрольних залежностей — із розгортанням у код x86-64 і ARM64 та матрицею спарювання.

Усі макроси та функції впорядкування пам'яті ядра оголошені в заголовочних файлах `<linux/compiler.h>`, `<asm/barrier.h>` та `<linux/atomic.h>`.

## 1. Бар'єри компілятора та примітиви доступу до пам'яті

Бар'єри компілятора регулюють поведінку оптимізатора GCC/Clang під час генерації машинних інструкцій. Вони забороняють компілятору переставляти інструкції читання й запису місцями у C-коді та змушують повторно зчитувати змінні з оперативної пам'яті замість збереження їх у регістрах CPU.

| Примітив ядра | Сигнатура / Визначення | Опис поведінки та машинний код |
| :--- | :--- | :--- |
| `barrier()` | `#define barrier() __asm__ __volatile__("": : :"memory")` | Повний бар'єр компілятора. Не генерує жодної інструкції CPU. Маркує весь обсяг оперативної пам'яті як модифікований (`clobber memory`), змушуючи компілятор скинути змінні з регістрів у RAM до межі бар'єра та заново прочитати їх після нього. |
| `READ_ONCE(x)` | `READ_ONCE(x)` | Гарантує виконання одного атомарного читання змінної `x`. Перетворює доступ на `*(volatile typeof(x) *)&x`. Запобігає видаленню читань компілятором (Dead Read Elimination), розщепленню доступу (Byte Tearing), злиттю сусідніх читань (Load Fusing) та вигаданим читанням (Invented Loads). |
| `WRITE_ONCE(x, val)` | `WRITE_ONCE(x, val)` | Гарантує виконання одного атомарного запису значення `val` у змінну `x`. Перетворює доступ на `*(volatile typeof(x) *)&x = val`. Запобігає злиттю сусідніх записів (Store Fusing) та вигаданим записам (Invented Stores), яких у C-коді не було. |
| `barrier_data(ptr)` | `__asm__ __volatile__("": :"r"(ptr) :"memory")` | Спеціальний бар'єр компілятора, який прив'язується до конкретної адреси вказівника `ptr`. Використовується для запобігання оптимізаційному видаленню очищення чутливих даних (наприклад, криптографічних ключів у буфері) перед викликом `kfree()`. |

### Механізм роботи `barrier()` та `clobber memory`

Макрос `barrier()` працює через порожню асемблерну вставку GCC з ключовим словом `__volatile__` та директивою `"memory"` у списку зіпсованих регістрів (clobber list). 

Коли компілятор бачить директиву `"memory"`, він припускає, що вхідна інструкція асемблера читає або записує довільні комірки оперативної пам'яті. З огляду на це, компілятор змушений повністю зупинити міжінструкційні оптимізації через дану точку:
- Усі змінні, які зберігалися у вихідних регістрах CPU (наприклад, `%rax`, `%rbx`), мусять бути записані назад у стек або оперативну пам'ять (Register Spilling).
- Жодне зчитування з пам'яті, оголошене у C-коді *після* виклику `barrier()`, не може бути виконане вище бар'єра з використанням закешованого значення з регістра.

### Захист від Dead Store Elimination через `barrier_data()`

У системному програмуванні та криптографічних модулях ядра поширеною помилкою є заповнення буфера нулями перед його звільненням:

```c
void wipe_sensitive_data(char *secret_key, size_t len)
{
    memset(secret_key, 0, len);
    // Якщо далі немає звернень до secret_key, компілятор видалить memset як Dead Store!
    kfree(secret_key);
}
```

Компілятор бачить, що пам'ять за вказівником `secret_key` більше ніде не читається перед деалокацією `kfree()`, і повністю видаляє виклик `memset()`. Щоб запобігти цьому, у ядрі використовується функція `memzero_explicit()`, яка спирається на `barrier_data()`:

```c
void memzero_explicit(void *s, size_t count)
{
    memset(s, 0, count);
    barrier_data(s); // Повідомляє компілятору, що secret_key був прочитаний асемблером
}
```

## 2. Симетричні бар'єри пам'яті для SMP-систем

SMP-бар'єри (`smp_*`) призначені для впорядкування доступу до звичайної оперативної пам'яті між різними ядрами багатопроцесорної системи. На однопроцесорних збірках ядра (конфігурація `CONFIG_SMP=n`) апаратні SMP-бар'єри автоматично оптимізуються і розгортаються у звичайні компіляторні бар'єри `barrier()`.

| Примітив ядра | Область дії впорядкування | Асемблер x86_64 | Асемблер ARM64 |
| :--- | :--- | :--- | :--- |
| `smp_mb()` | Повний двосторонній бар'єр. Забороняє будь-яке перевпорядкування читань і записів до і після бар'єра (`Store-Store`, `Load-Load`, `Load-Store`, `Store-Load`). | `lock addl $0, -4(%rsp)` (дешевша за `MFENCE`, яку лишено для `mb()`) | `DMB ISH` (Data Memory Barrier Inner Shareable) |
| `smp_rmb()` | Бар'єр читання. Гарантує, що всі операції читання (`Load->Load`), оголошені до бар'єра, завершаться до виконання будь-якого читання після бар'єра. | `barrier()` (оскільки x86 не переставляє читання) | `DMB ISHLD` (DMB Load-Load / Load-Store) |
| `smp_wmb()` | Бар'єр запису. Гарантує, що всі операції запису (`Store->Store`), оголошені до бар'єра, стануть видимими іншим ядрам раніше будь-якого запису після бар'єра. | `barrier()` (оскільки x86 не переставляє записи) | `DMB ISHST` (DMB Store-Store) |

### Спеціалізовані контекстні бар'єри ядра

Ядро Linux надає високопродуктивні контекстні бар'єри, які використовуються у поєднанні з атомарними операціями, спінлоками та SRCU:

- `smp_mb__before_atomic()`: Вставляє повний апаратний бар'єр *перед* атомарною операцією, яка за замовчуванням не має впорядкування (наприклад, `atomic_inc()`, `set_bit()`). На x86-64 не дає жодної інструкції CPU — атомарні операції там і так виконано з префіксом `LOCK`, тобто вони вже серіалізують; на ARM64 розгортається у `DMB ISH`.
- `smp_mb__after_atomic()`: Вставляє повний апаратний бар'єр *після* атомарної операції, яка сама не має семантики впорядкування. Разом із самою операцією це дає ефект повного бар'єра.
- `smp_mb__after_spinlock()`: Доводить захоплення спінлока до повного бар'єра — це потрібно там, де під замком одразу читають чуже поле (класичний випадок — планувальник у `try_to_wake_up()`). На x86-64 макрос порожній, бо `spin_lock()` уже виконано `LOCK`-операцією; на ARM64, де замок беруть парою `LDAXR`/`STXR` лише з семантикою Acquire, він додає справжній `DMB ISH`.
- `smp_mb__after_srcu_read_unlock()`: Забезпечує збереження порядку фаз виходу з критичних секцій Sleepable RCU.

## 3. Семантика впорядкування Acquire / Release

Примітиви семантики Acquire-Release є сучасним стандартом ядра Linux для побудови причинно-наслідкових зв'язків (Happens-Before Relationship). Вони працюють значно швидше за повні бар'єри `smp_mb()`, оскільки блокують перевпорядкування лише в одному напрямку.

```
[Попередній код]
       │
       ▼
smp_store_release(ptr, val) ─── Бар'єр ЗВЕРХУ, перед записом: жоден попередній запис/читання
       │                        не може опуститися нижче цієї точки!
       ▼
[Наступний код]

─────── INTERCONNECT / BUS SYNCHRONIZATION ───────

[Попередній код]
       │
       ▼
smp_load_acquire(ptr) ───────── Бар'єр ЗНИЗУ, після читання: жодне наступне читання/запис
       │                        не може піднятися вище цієї точки!
       ▼
[Наступний код]
```

### Детальний опис Acquire-Release функцій ядра

| Функція ядра | Опис семантики | Реалізація x86_64 | Реалізація ARM64 |
| :--- | :--- | :--- | :--- |
| `smp_store_release(p, v)` | Виконує збереження значення `v` за адресою `p` із семантикою Release. Усі операції читання та запису перед викликом фіксуються в пам'яті до виконання збереження. | `barrier(); WRITE_ONCE(*p, v);` | `STLR` (Store-Release Register) |
| `smp_load_acquire(p)` | Виконує завантаження значення за адресою `p` із семантикою Acquire. Жодна операція читання або запису після виклику не може бути виконана спекулятивно до завершення завантаження. | `typeof(*p) v = READ_ONCE(*p); barrier(); return v;` | `LDAR` (Load-Acquire Register) |
| `smp_cond_load_acquire(p, cond)` | Очікує у циклі опитування (з `cpu_relax()` на x86 і `WFE` на ARM), поки умова `cond` над зчитаним значенням `*p` не стане істинною, після чого прикладає бар'єр Acquire. | Цикл читання `READ_ONCE()` + `cpu_relax()` + `barrier()` | Цикл очікування на `LDXR` + `WFE` (Low Power State) із завершальним `LDAR` |
| `smp_store_mb(var, val)` | Присвоює `var = val` і виконує повний апаратний бар'єр пам'яті `smp_mb()`. Використовується при зміні стану процесів (`set_current_state()`). | `xchg(&var, val)` (атомарний обмін з `LOCK`) | `STR` + `DMB ISH` (загальна реалізація `WRITE_ONCE()` + `smp_mb()`) |

### Механізм `smp_cond_load_acquire()`

Функція `smp_cond_load_acquire(ptr, cond)` розроблена для оптимізації спин-циклів очікування прапорців. Вона запобігає перевантаженню шини інтерконнекту постійними опитуваннями пам'яті. 

На архітектурі ARM64 очікування будується на парі інструкцій: ексклюзивному читанні `LDXR`, яке ставить на адресу апаратний монітор, і `WFE` (Wait For Event), яка переводить ядро у стан зниженого енергоспоживання. Ядро не спалює такти в циклі опитування доти, доки інше ядро не запише щось за цією адресою — запис знімає монітор і будить чекальника подією `SEV`. Acquire-бар'єр прикладається вже після виходу з циклу, окремим `LDAR`.

## 4. Апаратні бар'єри для роботи з периферією та MMIO (I/O Barriers)

При взаємодії з апаратними пристроями через шину PCIe та регістри MMIO (Memory-Mapped I/O) використання звичайних `smp_*` бар'єрів є категоричною помилкою. 

Шинні мости (Host Bridges) та контролери шини PCIe мають власні апаратні буфери перевпорядкування (Posted Writes Buffer). Запис у MMIO-регістр пристрою виконується асинхронно, і процесор вважає його завершеним у той момент, коли дані потрапили у мостовий буфер шини, а не в реальний регістр мережевої карти або NVMe-накопичувача.

Для гарантування послідовності I/O операцій використовуються обов'язкові (mandatory) апаратні бар'єри, які діють навіть у конфігураціях з одним процесорним ядром (`CONFIG_SMP=n`):

| Примітив I/O | Призначення | Поведінка на шині |
| :--- | :--- | :--- |
| `wmb()` | Апаратний бар'єр запису I/O. | Гарантує, що всі попередні записи у звичайну пам'ять (наприклад, підготовка DMA-буферів в RAM) стануть видимими для пристрою раніше, ніж наступний запис у MMIO-регістр тригера (Doorbell Register). |
| `rmb()` | Апаратний бар'єр читання I/O. | Гарантує, що всі зчитування з MMIO-регістрів пристрою завершаться до того, як процесор почне зчитувати оновлені пристроєм DMA-дані з RAM. |
| `mb()` | Повний апаратний бар'єр I/O. | Повний двосторонній апаратний бар'єр для пам'яті та MMIO-простору. На x86_64 розгортається в `MFENCE`. |
| `mmiowb()` — **вилучено з ядра у 5.2 (2019)** | Історичний бар'єр впорядкування MMIO між критичними секціями спінлока. | Упорядковував MMIO-записи, видані різними ядрами під захистом того самого спінлока. Драйверам його більше не пишуть: потрібну дію вбудували в `spin_unlock()` на тих архітектурах, яким вона потрібна. |

### Приклад коректної послідовності запуску DMA-передачі

```c
// 1. Заповнюємо DMA дескриптор у оперативній пам'яті (RAM)
ring->desc[idx].addr = dma_handle;
ring->desc[idx].len  = bytes;

// 2. Гарантуємо, що дані дескриптора повністю записані у RAM
wmb();

// 3. Сповіщаємо пристрій через MMIO-регістр Doorbell
writel(idx, dev->mmio_bar + REGISTER_DOORBELL);
```

Якщо пропустити виклик `wmb()`, шинний мост PCIe може відправити MMIO-запис `writel` на мережеву карту раніше, ніж контролер пам'яті скине вміст дескриптора з кешу L3 у RAM. Пристрій негайно почне читати DMA-адресу і зчитає з RAM незаповнене сміття.

## 5. Контрольні залежності (Control Dependencies)

Контрольна залежність виникає тоді, коли виконуваний запис у пам'ять знаходиться всередині умовного блоку `if`, умова якого залежить від попереднього читання через `READ_ONCE()`:

```c
q = READ_ONCE(a);
if (q) {
    WRITE_ONCE(b, 1); // Контрольна залежність: READ a -> WRITE b
}
```

### Критичні правила контрольних залежностей

1. **Контрольна залежність впорядковує ЛИШЕ Читання->Запис (`Load->Store`).** Вона **НЕ** впорядковує залежності Читання->Читання (`Load->Load`)! Якщо всередині `if (q)` виконується `READ_ONCE(c)`, процесор має повне право прочитати `c` спекулятивно ще до перевірки `q`. Для впорядкування читань необхідно обов'язково використовувати `smp_rmb()` або `smp_load_acquire()`.
2. **Заборона оптимізації умовних гілок компілятором:** Якщо обидві гілки `if` та `else` містять однаковий запис `WRITE_ONCE(b, 1)`, компілятор винесе запис за межі `if`, і контрольна залежність буде повністю знищена:

```c
// НЕКОРЕКТНО! Компілятор винесе WRITE_ONCE(b, 1) вище умовного переходу
q = READ_ONCE(a);
if (q) {
    WRITE_ONCE(b, 1);
} else {
    WRITE_ONCE(b, 1);
}
```

## 6. Зведена матриця правил спарювання бар'єрів (Pairing Rules)

Бар'єри пам'яті у багатопотокових програмах майже ніколи не працюють поодинці. Бар'єр запису у одному потоці **завжди повинен мати пару** у вигляді бар'єра читання у іншому потоці.

| Операція у Потоці 1 (Producer) | Коректний бар'єр у Потоці 2 (Consumer) | Результат синхронізації | Статус коректності |
| :--- | :--- | :--- | :--- |
| `smp_wmb()` | `smp_rmb()` | Гарантує впорядкування `Write->Write` у Producer та `Read->Read` у Consumer. | **Коректно (Класична пара)** |
| `smp_store_release()` | `smp_load_acquire()` | Створює зв'язок Synchronizes-With. Потік 2 бачить усі записи Потоку 1 до `release`. | **Коректно (Рекомендовано)** |
| `smp_wmb()` | `READ_ONCE()` (без бар'єра) | Потік 1 впорядкував записи, але Потік 2 зчитав дані спекулятивно до прапорця. | **ДЕФЕКТ (Гонка за даними!)** |
| `smp_store_release()` | `READ_ONCE()` (без бар'єра) | Виробник опублікував дані коректно, але споживач не поставив бар'єр Acquire. | **ДЕФЕКТ (Прочитає сміття)** |
| `smp_mb()` | `smp_mb()` | Повна двостороння синхронізація обох потоків. | **Коректно (Найвища ціна)** |
