# 📜 Історія позапорядкового виконання та моделей пам'яті CPU

Майже два десятиліття в ядрі Linux жив макрос `smp_read_barrier_depends()`, який на x86, ARM і PowerPC розгортався у порожнечу. Він існував заради однієї-єдиної архітектури — DEC Alpha, — де процесор дозволяв собі те, чого не дозволяє більше ніхто: прочитати поле структури раніше, ніж прочитано вказівник на цю структуру. Історія бар'єрів пам'яті — це історія того, як гонитва за тактовою частотою відсувала апаратуру дедалі далі від інтуїтивної моделі пам'яті, а операційні системи змушені були надолужувати відрив формальними правилами впорядкування.

## 1. Ера 1990-х років: Фізичний бар'єр пам'яті та суперскалярність

У середині 1990-х років розробники апаратного забезпечення зіткнулися з явищем, яке в інженерній спільноті отримало назву «Стіна пам'яті» (Memory Wall). Тактова частота обчислювальних ядер процесорів зростала експоненціально, досягаючи сотень мегагерц і пізніше гігагерц, тоді як затримка вибірки даних із динамічної оперативної пам'яті (DRAM) зменшувалася надзвичайно повільно. Якщо на кожній інструкції читання (`MOV reg, [mem]`) або запису процесор змушений чекати 100–300 тактів на завершення транзакції на шині, обчислювальні блоки конвеєра простоятимуть понад 90% робочого часу.

Щоб подолати цей розрив продуктивності, інженери компаній DEC, Intel, IBM та AMD впровадили у кристали процесорів три ключові апаратні оптимізації:

1. **Буфери відкладеного запису (Store Buffers):** Процесорне ядро більше не чекає підтвердження запису даних у кеш-пам'ять L1/L2. Запис негайно розміщується у локальний масив швидких регістрових буферів ядра (Store Buffer), і конвеєр продовжує виконання наступних інструкцій коду.
2. **Черги інвалідації кешу (Invalidate Queues):** Коли одне ядро змінює кеш-рядок, воно надсилає іншим ядрам через інтерконнект шинний запит інвалідації (Invalidate). Щоб не затримувати обробку шинного трафіку, приймаюче ядро складає ці запити в апаратну чергу інвалідації та одразу відповідає підтвердженням (Invalidate Acknowledge) — ще до того, як реальний кеш-рядок буде фактично позначений як недійсний (Invalid) у таблиці тегів MESI.
3. **Позапорядкове (Out-of-Order / OoO) та спекулятивне виконання:** Конвеєр процесора аналізує потік асемблерних інструкцій у вікні перевпорядкування (Reorder Buffer, ROB). Якщо поточна інструкція читання блокується через очікування даних із RAM, конвеєр знаходить нижче за кодом незалежні інструкції читання чи обчислень і виконує їх наперед (спекулятивно).

Для однопотокового коду ці механізми повністю прозорі: апаратура зобов'язана зберегти результат, який дав би строго послідовний порядок у межах одного потоку. Якщо потік пише за адресою `A`, а потім читає з адреси `A`, ядро зчитує свіже значення з власного Store Buffer завдяки схемі Store-to-Load Forwarding. Проте у багатопроцесорних (SMP) системах, де кілька ядер працюють зі спільними структурами даних у пам'яті, це призвело до виникнення тонких і небезпечних апаратних перевпорядкувань.

## 2. DEC Alpha: Найслабша модель пам'яті в історії обчислювальної техніки

Архітектура DEC Alpha (представлена компанією Digital Equipment Corporation у 1992 році) стала підручниковим прикладом процесора з найагресивнішою та найслабшою моделлю когерентності пам'яті. Конструктори DEC Alpha поставили собі за мету досягти найвищої тактової частоти за рахунок максимального спрощення апаратних логічних схем синхронізації кешів.

На процесорах DEC Alpha апаратура могла переставляти місцями навіть ті інструкції читання з пам'яті, між якими існувала явна дата-залежність за адресою (Address Data Dependency). 

Розглянемо класичний приклад передачі вказівника на нову структуру:

```
[Початковий стан: global_ptr = NULL, payload = 0]

Core 0 (Producer):                        Core 1 (Consumer):
new_node->data = 42;                      p = READ_ONCE(global_ptr);
smp_wmb();                                if (p) {
WRITE_ONCE(global_ptr, new_node);             val = p->data; // Читання вмісту за вказівником
                                          }
```

На будь-якій сучасній архітектурі (x86, ARM64, RISC-V) читання `p->data` залежить від зчитаного значення `p`, тому процесор фізично не може зчитати `p->data` раніше, ніж дізнається адресу `p`. Однак на DEC Alpha кеш-пам'ять була розділена на два незалежні банки (Bank 0 та Bank 1). Якщо оновлене значення `new_node->data` потрапляло в Банк 0, а оновлений вказівник `global_ptr` — у Банк 1, Core 1 могло отримати оновлений вказівник `global_ptr` із Банку 1, але при цьому зчитати застаріле значення `p->data` із Банку 0, в якому запит інвалідації застряг у черзі!

У результаті Core 1 зчитувало новий вказівник `p`, але розіменовувало його і отримувало `p->data == 0` (сміття або старі дані).

Через унікальну апаратну поведінку DEC Alpha у ядрі Linux майже два десятиліття існував спеціалізований примітив бар'єра пам'яті:

```c
smp_read_barrier_depends()
```

На x86, ARM та PowerPC цей макрос розгортався у порожній рядок (`do {} while (0)`), оскільки ці архітектури гарантують впорядкування залежних читань на рівні заліза. І лише для архітектури DEC Alpha він генерував важку апаратну інструкцію `mb`, яка повністю опорожняла черги інвалідації кеш-банків.

Позбувалися його у два кроки. У ядрі Linux 4.15 (січень 2018 року) семантику залежного читання вклали безпосередньо в макрос `READ_ONCE()`: на Alpha він додатково видає бар'єр, на решті архітектур не змінюється нічого. Після цього явні виклики в коді ядра стали зайвими, і в наступних версіях серії 5.x сам примітив прибрали остаточно — сьогодні впорядкування за адресною залежністю дають `READ_ONCE()` та `rcu_dereference()`, а окремого API для нього в ядрі немає.

## 3. Табори архітектур: Строгий x86 TSO проти слабких RISC-моделей

З розвитком мікропроцесорної індустрії апаратні моделі пам'яті розділилися на два фундаментальних класи:

### Total Store Order (TSO) — архітектури Intel x86-64 та AMD64

Intel та AMD зберегли для x86-64 строгу модель Total Store Order, у якій єдине дозволене апаратне перевпорядкування — `Store->Load`, та й те як побічний ефект локального Store Buffer (сам поділ моделей і його наслідки для коду розібрано в основній статті). Прикметно, що ця модель довго взагалі не мала формального опису: окремий документ про впорядкування пам'яті Intel опублікувала аж 2007 року, коли багатоядерні процесори стали масовими. Двадцять років до того розробники спиралися на спостережену поведінку заліза — і саме накопичений за ці роки код зафіксував модель остаточно. Драйвери, серверні застосунки й бази даних писалися без жодних явних бар'єрів, мовчазно розраховуючи на строге впорядкування; послабити його означало б зламати їх усі водночас.

Для Linux наслідок виявився вигідним. На x86-64 примітиви `smp_rmb()` та `smp_wmb()` не коштують жодної машинної інструкції й розгортаються у самий лише компіляторний `barrier()`. Реальна апаратна робота лишилася тільки за повним бар'єром `smp_mb()`, який мусить дочекатися скидання Store Buffer: ядро реалізує його атомарною операцією з префіксом `LOCK` над вершиною стека, а важку `MFENCE` лишили для бар'єра введення-виведення `mb()`.

### Weakly-Ordered Memory — архітектури ARM, POWER, RISC-V

На противагу x86, процесори архітектур ARM (ARMv7-A, ARMv8-A, ARMv9-A), IBM POWER та RISC-V реалізують слабку модель пам'яті (Weakly-Ordered Memory Model). Для досягнення енергоефективності та максимальної паралельності конвеєра ці процесори мають право вільно переставляти місцями будь-які інструкції читання та запису (`Load->Load`, `Store->Store`, `Load->Store`, `Store->Load`), якщо між ними немає прямої дата-залежності в межах одного ядра.

На слабких архітектурах без використання апаратних бар'єрів пам'яті неможливо побудувати жодну коректну багатопотокову структуру даних. У перших версіях архітектури ARM для цього застосовувалися важкі бар'єрні інструкції:
- `DMB` (Data Memory Barrier) — гарантує впорядкування доступу до пам'яті.
- `DSB` (Data Synchronization Barrier) — чекає повного завершення всіх шинних операцій та інструкцій керування пам'яттю.
- `ISB` (Instruction Synchronization Barrier) — скидає конвеєр вибірки інструкцій CPU.

Однак у версії **ARMv8.0-A** (2011 рік) інженери ARM зробили революційний крок вперед: вони запровадили апаратну підтримку семантики Acquire-Release безпосередньо на рівні системи інструкцій ISA (Instruction Set Architecture), додавши інструкції `LDAR` (Load-Acquire Register) та `STLR` (Store-Release Register). Це дозволило усунути потребу у важких бар'єрах `DMB` у більшості алгоритмів синхронізації.

## 4. Від апаратних фенсів до стандартизації C11, C++11 та LKMM

До початку 2010-х років розробка паралельного системного коду на C/C++ перебувала у стані невизначеності. Мова C стандарту C99 взагалі не містила поняття багатопотоковості або моделей пам'яті: потоки розглядалися як зовнішній API (POSIX Threads), а компілятори мали повне право оптимізувати код так, ніби він виконується в одному потоці.

Фундаментальну роботу зі стандартизації моделей пам'яті виконали Ганс Бем (Hans Boehm), Пол МакКенні (Paul McKenney), Герб Саттер (Herb Sutter) та Марк Батті (Mark Batty). У результаті в стандарти **ISO C11** та **ISO C++11** було вперше впроваджено строгу математичну модель пам'яті (C11 Memory Model). 

Модель C11/C++11 запровадила поняття Data Race (гонка за даними) як невизначену поведінку (Undefined Behavior) та ввела шість рівнів впорядкування через `std::memory_order`:
1. `memory_order_relaxed` — атомарність без впорядкування.
2. `memory_order_consume` — впорядкування за залежністю (data dependency).
3. `memory_order_acquire` — бар'єр читання для споживача.
4. `memory_order_release` — бар'єр запису для виробника.
5. `memory_order_acq_rel` — суміщений Acquire-Release бар'єр.
6. `memory_order_seq_cst` — строге послідовне впорядкування (Sequential Consistency).

Паралельно у спільноті розробників ядра Linux формувалася власна, ще більш деталізована модель — **LKMM (Linux Kernel Memory Model)**. Ядро Linux не використовувало стандартні атоми C11/C++11 через специфічні вимоги до продуктивності, підтримку старіших компіляторів та наявність власної інфраструктури (RCU, `READ_ONCE`/`WRITE_ONCE`, `smp_mb()`).

У 2018 році академічна група дослідників (Jade Alglave, Luc Maranget) разом з провідними інженерами ядра створила офіційну математичну формалізацію LKMM у вигляді набору правил для інструменту комп'ютерного аналізу `herd7`. Скрипти формальної верифікації ядра, що знаходяться у вихідному коді Linux у каталозі `tools/memory-model/`, дозволяють математично довести коректність або наявність гонок у будь-якому фрагменті безблокувального коду ядра Linux ще до його виконання на реальному залізі.
