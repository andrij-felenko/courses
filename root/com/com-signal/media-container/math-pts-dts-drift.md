# 🧮 Математика часових штампів PTS/DTS, часових шкал та індексації зсувів

Обслуговування потоку медіаданих вимагає від демультиплексора суворого математичного обчислення трьох величин: реального часу відображення відліків, порядку перевпорядкування кадрів у пам'яті та байтових зсувів зразків у файловій системі.

При обробці мультимедіа кожна з цих задач описується власною системою цілочисельних рівнянь, оскільки використання чисел із плаваючою крапкою (`float` або `double`) неминуче призводить до накопичення похибок округлення IEEE-754 при тривалому відтворенні відео.

## 1. Математика часових шкал та запобігання переповненню

Кожен трек у медіаконтейнері має власну дискретну часову шкалу `R` (Timescale), виражену в тактах на секунду (Гц). Для відео часто використовують `R_video = 90000` Гц (стандарт MPEG) або `R_video = 1000` Гц (мілісекунди); для аудіо шкала зазвичай дорівнює частоті дискретизації прямого відліку сигналу, наприклад `R_audio = 48000` Гц або `44100` Гц.

Математичний зв'язок між дискретним часовим штампом `T_ticks` та реальним фізичним часом `t_seconds` виражається прямою пропорційною залежністю:

```
t_seconds = T_ticks / R
```

При виконанні демультиплексування виникає задача переведення часового штампа із часової шкали джерела `R_src` у часову шкалу приймача `R_dst` (наприклад, із шкали 90000 Гц у шкалу системного таймера 1000000 Гц).

Пряма формула масштабування з округленням до найближчого цілого має вигляд:

```
T_dst = floor((T_src · R_dst + R_src / 2) / R_src)
```

### Проблема переповнення 32-бітних регістрах та її математичне розв'язання

Якщо обчислення виконуються у 32-бітному цілочисельному просторі (`uint32_t`), добуток `T_src · R_dst` може викликати арифметичне переповнення. 

Наприклад, при `T_src = 900000` (10 секунд відео у шкалі 90 ГГц) та `R_dst = 1000000` Гц добуток дорівнює `900000000000`, що перевищує максимальне значення `2^32 - 1 = 4294967295`.

Для усунення переповнення обчислення виконують через 64-бітну intermediate-арифметику (`uint64_t`) або через розкладання дробу `R_dst / R_src` на цілу частину та остачу. 

Формула розкладання дробу через цілочисельне ділення:

```
Q = R_dst / R_src                     [ціла частина відношення шкал]
M = R_dst mod R_src                   [остача від ділення шкал]
T_dst = T_src · Q + (T_src · M) / R_src
```

Цей математичний підхід гарантує точність маскування до 1 тика без ризику втрати старших бітів.

### Обчислення тривалості кадру для стандартів кадрової частоти

Якщо відеопотік має частоту кадрів `FPS` (наприклад `FPS = 30000 / 1001 ≈ 29.97003` кадра/с для стандарту NTSC), тривалість одного кадру `Delta_ticks` у шкалі `R = 90000` Гц обчислюється аналітично:

```
Delta_ticks
= R / FPS                             [визначення тривалості кадру через частоту]
= 90000 / (30000 / 1001)              [підстановка значення шкали 90 ГГц та NTSC FPS]
= 90000 · 1001 / 30000                [ділення на дріб: множення на обернене значення]
= 3003                                [обчислення цілочисельної тривалості у тактах]
```

При частоті 29.97 кадрів/с кожен наступний кадр отримує штамп, більший за попередній рівно на 3003 такти (у шкалі 90 ГГц).

Для швидкості 59.94 кадрів/с тривалість становить:

```
Delta_ticks
= 90000 · 1001 / 60000                [підстановка дробу 60000/1001]
= 1501.5                              [неціле значення]
```

Оскільки тривалість кадру є дробовою (`1501.5`), мультиплексор застосовує чергування інтервалів: один кадр отримує приріст `1501` тактик, а наступний `1502` тактики. Сумарна тривалість двох кадрів становить строго `3003` такти, що повністю ліквідує накопичення часової похибки.

## 2. Розрахунок перевпорядкування кадрів (PTS проти DTS)

З появою двонаправлених B-кадрів порядок передачі кадрів у файлі (Decode Time Stamp — `DTS`) перестає збігатися з порядком їх показу на екрані (Presentation Time Stamp — `PTS`).

Нехай маємо послідовність кадрів у порядку відображення (PTS): `I0`, `B1`, `B2`, `P3`, `B4`, `P5`. Тривалість одного кадру становить `Delta = 3000` тактів.

Порядок відображення на екрані (PTS):

```
Frame 0 (I0):  PTS[0] = 0 · Delta = 0
Frame 1 (B1):  PTS[1] = 1 · Delta = 3000
Frame 2 (B2):  PTS[2] = 2 · Delta = 6000
Frame 3 (P3):  PTS[3] = 3 · Delta = 9000
Frame 4 (B4):  PTS[4] = 4 · Delta = 12000
Frame 5 (P5):  PTS[5] = 5 · Delta = 15000
```

Оскільки B-кадри `B1` та `B2` посилаються на майбутній опорний кадр `P3`, декодер повинен отримати та розпакувати `P3` **раніше**, ніж почне обчислювати `B1`.

Формула перевпорядкування визначає порядок декодування (DTS):

```
DTS[I0] = 0 · Delta = 0         (PTS = 0)
DTS[P3] = 1 · Delta = 3000      (PTS = 9000)   <- Опорний P3 закодовано першим!
DTS[B1] = 2 · Delta = 6000      (PTS = 3000)
DTS[B2] = 3 · Delta = 9000      (PTS = 6000)
DTS[P5] = 4 · Delta = 12000     (PTS = 15000)
DTS[B4] = 5 · Delta = 15000     (PTS = 12000)
```

Різниця між PTS та DTS утворює затримку у буфері розпакованих кадрів (Composition Time Offset — `CTTS` у MP4):

```
CTTS[i] = PTS[i] - DTS[i] >= 0
```

Для кадру `P3`: `CTTS[P3] = 9000 - 3000 = 6000` тактів. Усі значення `CTTS` є строго невід'ємними цілими числами.

Математичне обмеження глибини буфера розпакованих кадрів (DPB Buffer Size):

```
Max_DPB_Delay = max(PTS[i] - DTS[i]) / Delta
```

Якщо у відеопотоці максимальна кількість підряд ідучих B-кадрів дорівнює `N_B`, мінімально необхідна затримка буфера декодера становить `N_B + 1` кадрів.

## 3. Моделювання накопичення розсинхронізації (Audio/Video Drift)

Розглянемо проблему дрейфу часу між аудіо- та відеопотоками при довготривалому відтворенні.

Нехай відео розбито на кадри з частотою 25.0 кадрів/с (тривалість кадру `t_v = 1 / 25 = 0.040` с = 40 мс).
Аудіопотік AAC має частоту дискретизації `F_a = 44100` Гц, а один фрейм AAC містить `N_samples = 1024` відліки.

Тривалість одного аудіофрейму в секундах:

```
t_a 
= N_samples / F_a                     [визначення тривалості: кількість відліків ділена на частоту]
= 1024 / 44100                        [підстановка розміру фрейму 1024 та частоти 44100 Гц]
= 0.0232199545                        [обчислення тривалості у секундах]
```

Неможливо підібрати таке ціле число кадрів відео `K_v` та ціле число фреймів аудіо `K_a`, щоб їхні тривалості збігалися ідеально без остачі.

Обчислимо накопичений дрейф часових штампів через 24 години безперервної трансляції (`t_target = 86400` секунд):

```
Кількість кадрів відео:
K_v = floor(86400 / 0.040) = 2160000 кадрів.
Точний обчислений час відео = 2160000 · 0.040 = 86400.000000 с.

Кількість фреймів аудіо:
K_a = floor(86400 / 0.0232199545) = 3720938 фреймів.
Точний обчислений час аудіо = 3720938 · (1024 / 44100) = 86399.988426 с.

Сумарний накоплений дрейф аудіо відносно відео:
Delta_drift = 86400.000000 - 86399.988426 = 0.011574 секунди (11.57 мс).
```

Хоча за 24 години дрейф становить лише 11.57 мс, при безперервному мовленні впродовж місяців ця похибка зростає до секунд і руйнує синхронізацію губ диктора із звуком (Lip Sync Failure).

Для ліквідації дрейфу мультиплексор використовує метод компенсації часової шкали: кожні `N` кадрів часовий штамп аудіо коригується на +1 тик, підтримуючи абсолютне значення розсинхронізації в межах `|Delta_drift| < 1` мс.

## 4. Математика індексації зсувів у ISOBMFF (`stbl`)

Для знаходження байтового зсуву `Offset(sample_i)` кадру `i` у файлі MP4 використовується трирівнева система індексних таблиць:

1. `stsz` (Sample Size Table): масив `Size[1..N]` розмірів кожного кадру у байтах.
2. `stsc` (Sample-to-Chunk Table): таблиця відповідності кадрів до блоків (чанків).
3. `stco` / `co64` (Chunk Offset Table): масив `ChunkOffset[1..M]` абсолютних байтових зсувів початку кожного чанку у файлі.

Таблиця `stsc` зберігається в стисненому формати RLE (Run-Length Encoding) і містить записи вигляду:

```
(first_chunk, samples_per_chunk, sample_description_index)
```

### Алгоритм декодування адреси кадру

Нехай потрібно знайти байтовий зсув кадру з номером `i`.

Крок 1. Скануванням таблиці `stsc` знаходимо індекс чанку `j`, у якому знаходиться кадр `i`.

Крок 2. Обчислюємо порядковий номер першого кадру `first_sample` всередині цього чанку `j`:

```
first_sample = 1 + ∑_{m = 1}^{j-1} samples_per_chunk[m]
```

Крок 3. Обчислюємо внутрішній зсув `k` кадру всередині чанку:

```
k = i - first_sample
```

Крок 4. Знаходимо підсумкову абсолютну байтову адресу кадру у файлі:

```
Offset(sample_i) = ChunkOffset[j] + ∑_{m = 0}^{k-1} Size[first_sample + m]
```

Цей прямий математичний розрахунок дозволяє медіапрогравачу обчислити точний байтовий зсув будь-якого кадру у файлі обсягом у сотні гігабайтів за час `O(1)` з використання мінімального обсягу RAM.
