# 📋 Інтерфейс V4L2 Mem-to-Mem для апаратних кодеків

Довідник описує детальний програмний контракт взаємодії програмного забезпечення користувацького простору Linux із драйвером апаратного кодека через підсистему Video4Linux2 Memory-to-Memory (V4L2 M2M).

## Принцип архітектури Memory-to-Memory (M2M)

Апаратні кодеки H.264 у Linux реалізуються як M2M-пристрої у каталозі `/dev/videoX`. На відміну від пристроїв захоплення (камер) або виводу (дисплеїв), M2M-кодек оперує як обчислювальний перетворювач: він приймає буфери вихідних даних на вхідному порту та видає стиснений або декодований потік на вихідному порту.

З точки зору підсистеми V4L2, кодер H.264 керує двома абсолютно незалежними чергами буферів у пам'яті:

1. **Черга `OUTPUT` (Raw Frame Queue):** програма передає сюди нестиснені YUV-кадри від камери або графічного прискорювача. Поширеними форматами є `V4L2_PIX_FMT_YUV420` (планарний YUV 4:2:0) та `V4L2_PIX_FMT_NV12` (напівпланарний YUV із суміщеною площиною колірності UV).
2. **Черга `CAPTURE` (Compressed Stream Queue):** програма отримує звідси сформовані апаратним кодеком одиниці NAL (Network Abstraction Layer) H.264 у кодуванні `V4L2_PIX_FMT_H264`.

У випадку апаратного декодера ролики черг міняються місцями: черга `OUTPUT` приймає байтовий NAL-потік H.264, а черга `CAPTURE` віддає відновлені нестиснені кадри YUV.

## Послідовність викликів ioctl для налаштування кодування

Конфігурація та виконання кодування здійснюється через послідовні системні виклики `ioctl()`. Порушення порядку викликів призводить до помилок ініціалізації (`EINVAL` або `EBUSY`).

| Послідовність | Системний виклик `ioctl` | Докладний опис та призначення |
| :--- | :--- | :--- |
| **1** | `VIDIOC_S_FMT` (`OUTPUT`) | Задає роздільну здатність (ширину та висоту в пікселях), піксельний формат (наприклад, NV12) та розмір кроку рядків (stride) для вхідного YUV-кадру. |
| **2** | `VIDIOC_S_FMT` (`CAPTURE`) | Задає вихідний кодований формат `V4L2_PIX_FMT_H264` та розмір вихідного буфера в байтах. |
| **3** | `VIDIOC_S_EXT_CTRLS` | Встановлює додаткові параметри стиснення H.264: профіль, рівень, цільовий бітрейт, розмір GOP, режим ентропійного кодування (CAVLC/CABAC). |
| **4** | `VIDIOC_REQBUFS` | Запитує виділення певної кількості буферів у ядрі або пам'яті VRAM (зазвичай 4–8 буферів для забезпечення неперервного конвеєра). |
| **5** | `VIDIOC_QUERYBUF` / `mmap` | Зчитує параметри виділених буферів (зсуви та розміри) і відображає їх у віртуальний адресний простір процесу. |
| **6** | `VIDIOC_QBUF` (`OUTPUT` & `CAPTURE`) | Ставить підготовлені YUV-буфери та порожні вихідні буфери в робочі черги апаратного прискорювача. |
| **7** | `VIDIOC_STREAMON` | Активує обробку в ядрі. Апаратне IP-ядро починає вибірку кадрів через DMA та кодування. |
| **8** | `VIDIOC_DQBUF` | Очікує закінчення кодування кадру та вилучає заповнений NAL-буфер з черги `CAPTURE`. |

## Ключові елементи керування H.264 (V4L2 Controls)

Параметри стиснення задаються через структуру розширеного керування `struct v4l2_ext_control` з використанням ідентифікаторів `V4L2_CID_MPEG_VIDEO_...`.

### Профілі та рівні стандарту H.264

Профіль обмежує набір алгоритмічних інструментів (Intra, Inter, B-frames, CABAC), а рівень задає максимальну обчислювальну складність та швидкість передачі даних.

```text
// Вибір профілю стандарту H.264
V4L2_CID_MPEG_VIDEO_H264_PROFILE : enum v4l2_mpeg_video_h264_profile
    V4L2_MPEG_VIDEO_H264_PROFILE_BASELINE            = 0, // Без B-кадрів та CABAC (для низьких затримок)
    V4L2_MPEG_VIDEO_H264_PROFILE_MAIN                = 1, // Підтримка CABAC та B-кадрів
    V4L2_MPEG_VIDEO_H264_PROFILE_HIGH                = 2, // Підтримка 8x8 цілочисельного перетворення та матриць квантування

// Вибір рівня стандарту H.264
V4L2_CID_MPEG_VIDEO_H264_LEVEL : enum v4l2_mpeg_video_h264_level
    V4L2_MPEG_VIDEO_H264_LEVEL_3_0                   = 6,  // HD 720p30
    V4L2_MPEG_VIDEO_H264_LEVEL_3_1                   = 8,  // 720p60 / 1080p30
    V4L2_MPEG_VIDEO_H264_LEVEL_4_0                   = 10, // Full HD 1080p30 (високий бітрейт)
    V4L2_MPEG_VIDEO_H264_LEVEL_4_1                   = 11, // Full HD 1080p60
    V4L2_MPEG_VIDEO_H264_LEVEL_5_1                   = 14, // 4K UHD 2160p60
```

### Керування бітрейтом, структурою GOP та ентропією

Налаштування регулятора бітрейту визначає поведінку апаратного прискорювача під час зміни складності сцени.

```text
// Режим керування бітрейтом
V4L2_CID_MPEG_VIDEO_BITRATE_MODE : enum v4l2_mpeg_video_bitrate_mode
    V4L2_MPEG_VIDEO_BITRATE_MODE_VBR                 = 0, // Змінний бітрейт (Variable Bitrate)
    V4L2_MPEG_VIDEO_BITRATE_MODE_CBR                 = 1, // Постійний бітрейт (Constant Bitrate)
    V4L2_MPEG_VIDEO_BITRATE_MODE_CQ                  = 2, // Постійний параметр квантування (Constant Quality)

// Цільова швидкість передачі даних у бітах на секунду (наприклад, 8000000 для 8 Мбіт/с)
V4L2_CID_MPEG_VIDEO_BITRATE : int32_t

// Піковий бітрейт при режимі VBR у бітах на секунду
V4L2_CID_MPEG_VIDEO_BITRATE_PEAK : int32_t

// Інтервал між ключовими I-кадрами (GOP Size)
V4L2_CID_MPEG_VIDEO_GOP_SIZE : int32_t

// Кількість послідовних B-кадрів між P-кадрами (0 для мінімізації затримки)
V4L2_CID_MPEG_VIDEO_B_FRAMES : int32_t

// Алгоритм ентропійного кодування
V4L2_CID_MPEG_VIDEO_H264_ENTROPY_MODE : enum v4l2_mpeg_video_h264_entropy_mode
    V4L2_MPEG_VIDEO_H264_ENTROPY_MODE_CAVLC          = 0, // Табличне кодування з низьким споживанням
    V4L2_MPEG_VIDEO_H264_ENTROPY_MODE_CABAC          = 1, // Арифметичне кодування (вищий ступінь стиснення)
```

### Параметри квантування та деблокінг-фільтра

```text
// Діапазон параметра квантування (QP від 0 до 51)
V4L2_CID_MPEG_VIDEO_H264_I_FRAME_QP : int32_t
V4L2_CID_MPEG_VIDEO_H264_P_FRAME_QP : int32_t
V4L2_CID_MPEG_VIDEO_H264_B_FRAME_QP : int32_t
V4L2_CID_MPEG_VIDEO_H264_MIN_QP : int32_t
V4L2_CID_MPEG_VIDEO_H264_MAX_QP : int32_t

// Режим контурного деблокінг-фільтра
V4L2_CID_MPEG_VIDEO_H264_LOOP_FILTER_MODE : enum v4l2_mpeg_video_h264_loop_filter_mode
    V4L2_MPEG_VIDEO_H264_LOOP_FILTER_MODE_ENABLED    = 0, // Фільтр увімкнено
    V4L2_MPEG_VIDEO_H264_LOOP_FILTER_MODE_DISABLED   = 1, // Фільтр вимкнено
    V4L2_MPEG_VIDEO_H264_LOOP_FILTER_MODE_DISABLED_AT_SLICE_BOUNDARY = 2,
```

## Структури обміну буферами та Zero-Copy через DMA-BUF

Передача кадрів між пам'яттю програми та апаратним прискорювачем виконується за допомогою системної структури `struct v4l2_buffer`.

```text
struct v4l2_buffer {
    uint32_t            index;        // Індекс буфера в черзі (0..N-1)
    uint32_t            type;         // V4L2_BUF_TYPE_VIDEO_OUTPUT або CAPTURE
    uint32_t            bytesused;    // Обсяг фактично записаних даних у байтах
    uint32_t            flags;        // Прапорці статусу (V4L2_BUF_FLAG_KEYFRAME тощо)
    uint32_t            field;        // Режим розгортки (V4L2_FIELD_NONE)
    struct timeval      timestamp;    // Точна позначка часу кадру
    enum v4l2_memory    memory;       // Тип пам'яті (MMAP, USERPTR, DMABUF)
    union {
        uint32_t        offset;       // Зсув пам'яті для mmap()
        unsigned long   userptr;      // Вказівник пам'яті у просторі користувача
        int             fd;           // Файловий дескриптор DMA-BUF (Zero-Copy)
    } m;
    uint32_t            length;       // Загальний виділений розмір буфера в байтах
};
```

### Технологія нульового копіювання (Zero-Copy DMA-BUF)

При звичайному копіюванні зображення з камери у пам'ять кодека центральний процесор виконує кілька послідовних операцій `memcpy()`, зчитуючи та записуючи гігабайти даних на секунду через кеш-пам'ять CPU. Це створює колосальне навантаження на системну шину.

Використання режиму `V4L2_MEMORY_DMABUF` дозволяє уникнути копіювання. Програма запитує файловий дескриптор DMA-буфера від сенсора камери або прискорювача GPU та передає його безпосередньо у поле `m.fd` структури `v4l2_buffer` апаратного кодека. Кодек налаштовує свої внутрішні DMA-контролери на роботу з цими фізичними адресами оперативної пам'яті. В результаті кадри протікають від сенсора до кодека безпосередньо через шину AXI/AHB без залучення CPU.

## Державні (Stateful) проти Бездержавних (Stateless) кодеків

У Linux підсистема V4L2 розділяє апаратні кодеки на дві категорії:

- **Stateful (Державні кодеки):** апаратний модуль містить власний мікрокод та прошивку. Програма передає лише сирий YUV-кадр та загальні параметри (бітрейт, GOP), а кодек самостійно будує заголовки SPS, PPS, Slice Header і керує буфером DPB. Прикладами є Nvidia NVENC, Raspberry Pi VideoCore, Qualcomm Venus.
- **Stateless (Бездержавні кодеки):** апаратний блок позбавлений мікрокоду і являє собою чистий прискорювач обчислень макроблоків. Програма користувацького простору повинна самостійно повністю розпарсити заголовки NAL, сформувати таблиці опорних кадрів DPB, обчислити вектори руху та передати у ядро спеціальні структури керування (`V4L2_CID_STATELESS_H264_SPS`, `V4L2_CID_STATELESS_H264_DECODE_PARAMS`). Прикладами є відкриті драйвери Allwinner Cedrus та Rockchip VPU.

## Динамічна зміна параметрів під час кодування потоку

Під час трансляції відео у реальному часі (наприклад, при погіршенні пропускної здатності радіоканалу) програма може динамічно змінювати бітрейт без зупинки обробки (`STREAMOFF`/`STREAMON`).

Зміна бітрейту виконується шляхом виклику `VIDIOC_S_EXT_CTRLS` із новим значенням `V4L2_CID_MPEG_VIDEO_BITRATE` безпосередньо у процесі роботи. Апаратний регулятор швидкості (Rate Control Engine) підхоплює нове значення з наступного макроблока або кадру. Також програма може надіслати команду вимушеної генерації ключового кадру через виклики контролю `V4L2_CID_MPEG_VIDEO_FORCE_KEY_FRAME`, що викликає негайну вставку IDR-кадру (Instantaneous Decoder Refresh) для швидкого відновлення картинки у приймача.
