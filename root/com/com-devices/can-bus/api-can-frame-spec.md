# 📋 Специфікація кадру CAN та SocketCAN API

Цей довідник містить точний опис бітових полів кадру CAN (для специфікацій CAN 2.0A стандартного та CAN 2.0B розширеного), кодування коду довжини даних DLC, математичний розбір полінома CRC-15, а також специфікацію системних структур даних і прапорців інтерфейсу SocketCAN у системі Linux для мов C та C++.

---

## 1. Послідовний аналіз бітових полів кадру CAN 2.0A та 2.0B

У таблиці нижче наведено повну хронологічну послідовність передачі бітів у кадрі даних CAN. Для кожного поля вказано його функціональне призначення, розрядність у бітах, логічний рівень за замовчуванням у стані спокою та приналежність до зони дії апаратного біт-стафінгу.

| Назва поля | Абревіатура | Довжина (CAN 2.0A) | Довжина (CAN 2.0B) | Полярність / Логічний рівень | Застосування Bit Stuffing |
| :--- | :--- | :---: | :---: | :--- | :---: |
| **Start of Frame** | SOF | 1 біт | 1 біт | Домінантний («0») | Так |
| **Base Identifier** | Base ID | 11 бітів | 11 бітів | MSB першим (`ID[10..0]`) | Так |
| **Substitute Remote Request** | SRR | — | 1 біт | Рецесивний («1») у 2.0B | Так |
| **Identifier Extension Flag** | IDE | 1 біт («0») | 1 біт («1») | «0» = 11-біт ID, «1» = 29-біт ID | Так |
| **Extended Identifier** | Extended ID | — | 18 бітів | `ID[17..0]` у 2.0B | Так |
| **Remote Transmission Request**| RTR | 1 біт | 1 біт | «0» = Data Frame, «1» = Remote Frame | Так |
| **Reserved Bits** | r0 / r1 | 1 біт (`r0`) | 2 біти (`r1`, `r0`) | Домінантні («0») | Так |
| **Data Length Code** | DLC | 4 біти | 4 біти | `0x0` .. `0x8` (кількість байтів) | Так |
| **Data Field** | Data | 0 .. 8 байтів | 0 .. 8 байтів | Корисне навантаження (MSB first) | Так |
| **CRC Sequence** | CRC | 15 бітів | 15 бітів | Поліном `0x4599` | Так |
| **CRC Delimiter** | CRC Del | 1 біт | 1 біт | Рецесивний («1») | Ні |
| **Acknowledge Slot** | ACK Slot | 1 біт | 1 біт | Передавач: «1»; Приймачі: «0» | Ні |
| **Acknowledge Delimiter** | ACK Del | 1 біт | 1 біт | Рецесивний («1») | Ні |
| **End of Frame** | EOF | 7 бітів | 7 бітів | Рецесивні («1111111») | Ні |
| **Interframe Space** | IFS | ≥ 3 біти | ≥ 3 біти | Рецесивні («111») | Ні |

### Детальна функціональна роль бітових полів

- **SOF (Start of Frame):** Один домінантний біт. Спадаючий фронт на початку SOF використовується всіма приймачами мережі для первинної жорсткої синхронізації внутрішніх таймерів.
- **Base ID (11 бітів):** Визначає пріоритет кадру в процесі арбітражу. Чим менше значення ID, тим раніше в ньому з'явиться домінантний біт «0», який переважить рецесивну «1» конкурента.
- **SRR (Substitute Remote Request):** Заміщальний біт у розширеному кадрі. Передається завжди рецесивним («1»). При порівнянні стандартного кадру (де на цьому місці передається домінантний біт RTR=0) та розширеного кадру з однаковим Base ID, стандартний кадр перемагає в арбітражі.
- **IDE (Identifier Extension Flag):** Розрізняє формат кадру. Домінантна «0» позначає стандартний 11-бітний ідентифікатор CAN 2.0A, а рецесивна «1» — розширений 29-бітний ідентифікатор CAN 2.0B.
- **Extended ID (18 бітів):** Додаткові 18 бітів розширеного ідентифікатора. Разом із 11 бітами Base ID вони утворюють повне 29-бітне число, що дає понад 536 мільйонів унікальних комбінацій ID.
- **RTR (Remote Transmission Request):** Вказує тип кадру. Домінантний «0» позначає кадр даних (Data Frame), а рецесивна «1» — кадр запиту (Remote Frame).
- **CRC Sequence (15 бітів):** Обчислюється за поліномом `x¹⁵ + x¹⁴ + x¹⁰ + x⁸ + x⁷ + x⁴ + x³ + 1` (шістнадцятковий коефіцієнт `0x4599`). Цей поліном математично оптимізовано для виявлення пачок помилок довжиною до 15 бітів та упевненого виявлення до 5 випадкових інверсій бітів при довжині кадру менше 127 бітів.
- **ACK Slot (1 біт):** Інтервал квитування. Передавач надсилає рецесивний біт («1»). Будь-який приймач, який успішно декодував кадр і підтвердив збіг CRC, активно притягує шину до домінантного стану («0»). Якщо відправник бачить у ACK Slot домінантний «0», кадр вважається доставленим.

## 2. Кодування поля DLC (Data Length Code)

Поле DLC складається з 4 бітів. У класичному стандарті CAN 2.0 значення від `0` до `8` визначають точну кількість байтів у полі даних. Значення від `9` до `15` у CAN 2.0 також інтерпретуються як 8 байтів даних, тоді як у специфікації CAN FD вони відображаються на розширені обсяги кадру.

| DLC (Hex) | DLC (Binary) | Розмір у CAN 2.0 (Байтів) | Розмір у CAN FD (Байтів) |
| :---: | :---: | :---: | :---: |
| `0x0` | `0b0000` | 0 | 0 |
| `0x1` .. `0x8` | `0b0001` .. `0b1000` | 1 .. 8 | 1 .. 8 |
| `0x9` | `0b1001` | 8 (max) | 12 |
| `0xA` | `0b1010` | 8 (max) | 16 |
| `0xB` | `0b1011` | 8 (max) | 20 |
| `0xC` | `0b1100` | 8 (max) | 24 |
| `0xD` | `0b1101` | 8 (max) | 32 |
| `0xE` | `0b1110` | 8 (max) | 48 |
| `0xF` | `0b1111` | 8 (max) | 64 |

## 3. Системні структури даних SocketCAN uapi у Linux

У системі Linux системний стек SocketCAN надає доступ до CAN-контролера через мережеві сокети домену `AF_CAN`. Нижче наведено порівняння специфікації структур даних для мов C та C++.

### Класичний кадр CAN (`struct can_frame`)

:::tabs
```c
/* C: системний заголовок <linux/can.h> */
#include <linux/can.h>

struct can_frame {
    can_id_t can_id;  /* 32-бітний ID + служебні прапорці (EFF, RTR, ERR) */
    __u8     can_dlc; /* Довжина корисної підкладки (0..8) */
    __u8     __pad;   /* Падінг для вирівнювання за межею 32 бітів */
    __u8     __res0;  /* Резервний байт */
    __u8     len8_dlc;/* Спеціальний параметр для некоректних DLC */
    __u8     data[8] __attribute__((aligned(8))); /* Буфер даних 8 байтів */
};
```
```cpp
// C++: Ідіоматична обгортка класичного кадру CAN
#include <cstdint>
#include <array>
#include <span>

namespace can {

struct Frame {
    std::uint32_t id{0};                           // 11/29-біт ID та прапорці
    std::uint8_t  dlc{0};                          // Фактичний розмір (0..8)
    std::array<std::uint8_t, 8> data{};            // Фіксований буфер даних

    [[nodiscard]] constexpr std::span<const std::uint8_t> payload() const noexcept {
        return std::span<const std::uint8_t>{data.data(), dlc};
    }
};

} // namespace can
```
:::

### Маски прапорців ідентифікатора `can_id`

Поле `can_id` містить 32-бітне число, у якому найвищі біти відведено під системні прапорці стану кадру, а молодші біти — під самий ідентифікатор.

:::tabs
```c
/* C: визначення масок прапорців у <linux/can.h> */
#define CAN_EFF_FLAG 0x80000000U /* 1 = Розширений кадр (29-біт ID) */
#define CAN_RTR_FLAG 0x40000000U /* 1 = Кадр запиту даних (Remote Frame) */
#define CAN_ERR_FLAG 0x20000000U /* 1 = Кадр помилки (Error Frame) */

#define CAN_SFF_MASK 0x000007FFU /* Маска для виділення 11-бітного ID */
#define CAN_EFF_MASK 0x1FFFFFFFU /* Маска для виділення 29-бітного ID */
#define CAN_ERR_MASK 0x1FFFFFFFU /* Маска типів помилок шини */
```
```cpp
// C++: Типізовані бітові константи та enum class
#include <cstdint>

namespace can {

enum class Flag : std::uint32_t {
    Extended  = 0x80000000U, // 29-бітний розширений ID
    Remote    = 0x40000000U, // Запит передачі Remote Frame
    Error     = 0x20000000U  // Повідомлення про помилку шини
};

enum class Mask : std::uint32_t {
    StandardId = 0x000007FFU, // Маска 11-бітного ID
    ExtendedId = 0x1FFFFFFFU, // Маска 29-бітного ID
    ErrorId    = 0x1FFFFFFFU  // Маска коду помилки
};

} // namespace can
```
:::

### Апаратна фільтрація `struct can_filter`

Для налаштування апаратних acceptance-фільтрів у CAN-контролері використовують маски `can_filter`.

:::tabs
```c
/* C: структура маски фільтра в <linux/can.h> */
struct can_filter {
    can_id_t can_id;   /* Цільове значення ідентифікатора */
    can_id_t can_mask; /* Маска перевірки (1 = порівнювати біт, 0 = ігнорувати) */
};
```
```cpp
// C++: Структура фільтра з методикою конструювання
#include <cstdint>

namespace can {

struct Filter {
    std::uint32_t id{0};   // Цільовий ID
    std::uint32_t mask{0}; // Маска перевірки бітів

    [[nodiscard]] constexpr bool matches(std::uint32_t input_id) const noexcept {
        return (input_id & mask) == (id & mask);
    }
};

} // namespace can
```

## 4. Розширений кадр CAN FD (`struct canfd_frame`)

Для підтримки високоефективного протоколу CAN FD у системі Linux створено структуру `canfd_frame`, яка вміщує до 64 байтів корисного навантаження та прапорці перемикання швидкості BRS.

:::tabs
```c
/* C: структура кадру CAN FD у <linux/can.h> */
#include <linux/can.h>

struct canfd_frame {
    can_id_t can_id;  /* 32-бітний ID та прапорці (EFF, RTR, ERR) */
    __u8     len;     /* Фактична довжина навантаження (від 0 до 64) */
    __u8     flags;   /* Прапорці CAN FD (CANFD_BRS, CANFD_ESI) */
    __u8     __res0;  /* Зарезервовано */
    __u8     __res1;  /* Зарезервовано */
    __u8     data[64] __attribute__((aligned(8))); /* Буфер 64 байти */
};

#define CANFD_BRS 0x01 /* Bit Rate Switch: перемикання на високу швидкість */
#define CANFD_ESI 0x02 /* Error State Indicator: 0 = Active, 1 = Passive */
```
```cpp
// C++: Обгортка кадру CAN FD
#include <cstdint>
#include <array>
#include <span>

namespace can {

struct FdFrame {
    std::uint32_t id{0};                           // ID та прапорці
    std::uint8_t  len{0};                          // Довжина (0..64)
    std::uint8_t  flags{0};                        // Прапорці BRS / ESI
    std::array<std::uint8_t, 64> data{};           // Розширений буфер

    [[nodiscard]] constexpr bool has_brs() const noexcept {
        return (flags & 0x01) != 0;
    }

    [[nodiscard]] constexpr std::span<const std::uint8_t> payload() const noexcept {
        return std::span<const std::uint8_t>{data.data(), len};
    }
};

} // namespace can
```

## 5. Системне керування параметрами CAN через iproute2

У системі Linux налаштування швидкості шини (Bit Timing), включення режимів CAN FD та керування автоповтором після стану Bus-Off виконується через утиліту `ip` (пакет iproute2) з використанням системного інтерфейсу Netlink:

```bash
# Встановлення швидкості 500 кбіт/с для класичного CAN
sudo ip link set can0 type can bitrate 500000

# Включення CAN FD: номінальна швидкість 500 кбіт/с, швидкість даних 2 Мбіт/с
sudo ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on

# Автоматичне відновлення зі стану Bus-Off через 100 мс
sudo ip link set can0 type can restart-ms 100

# Активація мережевого інтерфейсу
sudo ip link set can0 up
```
