# ⚙️ Обмін байтом по SPI: від `transfer()` до читання регістра давача

**Задача.** Маємо мікроконтролер-ведучий і периферійний чіп на SPI — скажімо, давач, у якого треба прочитати один внутрішній регістр і записати один. Треба: правильно налаштувати шину (швидкість і режим), обміняти один байт у повному дуплексі, а тоді скласти з цих обмінів осмислені операції «прочитати регістр» і «записати регістр». Усе — на реальному C, без псевдокоду.

**Ідея.** Уся робота зі SPI стоїть на **одній** операції — обмін одним байтом. Ведучий виставляє байт у свій зсувний регістр, видає 8 тактів — і за ті самі 8 тактів забирає байт, що прийшов від веденого. Тобто фундаментальна функція не «надіслати» й не «прийняти», а **обміняти**: дав байт — отримав байт. Усе інше (читання регістра, запис, потокова передача) — це послідовність таких обмінів, обрамлена опусканням і підняттям лінії вибору.

---

## Крок 1. Найголовніша функція: `spi_transfer`

Майже всі мікроконтролери реалізують обмін через апаратний блок із двома регістрами: регістр даних (куди кладеш байт на відсилання й звідки забираєш прийнятий) і регістр стану (де є прапорець «обмін завершено»). Алгоритм незмінний: поклав байт — дочекався прапорця — забрав байт.

```c
#include <stdint.h>

// Обмін одним байтом: повертає те, що прийшло від веденого,
// поки ми висували tx. Це і пише, і читає за одну операцію.
uint8_t spi_transfer(uint8_t tx) {
    SPI_DATA = tx;                       // покласти байт у зсувний регістр → пішли 8 тактів
    while (!(SPI_STATUS & SPI_DONE)) {   // чекати, поки апарат прокрутить усі 8 біт
        ;
    }
    return SPI_DATA;                      // у тому самому регістрі вже лежить прийнятий байт
}
```

Тут видно суть SPI у трьох рядках: записали в `SPI_DATA` — і той самий регістр після обміну **містить** відповідь веденого. Запис і читання — це фізично один зсув, тож і в коді вони злиті в одну функцію. Звідси два звичних узори:

```c
uint8_t spi_read(void)            { return spi_transfer(0xFF); } // вислати пусте, узяти відповідь
void    spi_write(uint8_t b)      { (void)spi_transfer(b);     } // вислати дані, відкинути прийняте
```

Щоб «лише прочитати», все одно треба щось висунути (тут 0xFF) — інакше кільце не прокрутиться. Щоб «лише записати», висуваємо дані й **ігноруємо** повернене. Жодного окремого «режиму читання» в SPI немає: є тільки обмін, а напрямок, який нас не цікавить, ми просто не використовуємо.

## Крок 2. Налаштувати шину: швидкість і режим

Перш ніж обмінюватися, треба домовитися з веденим про дві речі: **як швидко** цокати і в якому **режимі**. Швидкість обмежена тим, що витримує конкретний чіп (з даташита); режим — це пара (CPOL, CPHA), і вона мусить **збігатися** в ведучого й веденого, інакше приймач знімає біти не в той момент і дані перетворюються на сміття. Самі ці два параметри й чотири режими 0–3 докладно розібрані окремо — тут лише задаємо потрібний.

> 🔌 Що означають CPOL і CPHA, чому їх рівно чотири комбінації й як визначити потрібний режим за даташитом — у темі [режими CPOL/CPHA](topic:com-devices/spi-mode-selection). Коротко: CPOL задає рівень такту в спокої, CPHA — на якому з двох фронтів знімати біт; найпоширеніші режими — 0 і 3.

```c
// Налаштування блока SPI: ведучий, режим 0 (CPOL=0, CPHA=0), дільник такту.
void spi_init_mode0(void) {
    SPI_CTRL  = 0;                 // чистий старт
    SPI_CTRL |= SPI_MASTER;        // ми — ведучий, ми генеруємо SCK
    SPI_CTRL |= SPI_CPOL_0;        // такт у спокої низький
    SPI_CTRL |= SPI_CPHA_0;        // біт знімаємо на першому (наростальному) фронті
    SPI_CTRL |= SPI_CLK_DIV8;      // напр., 8 МГц ядра / 8 = 1 МГц SCK
    SPI_CTRL |= SPI_ENABLE;        // увімкнути блок
}
```

Прапорці тут — умовні імена бітів керування (у кожного сімейства мікроконтролерів вони звуться по-своєму, але зміст той самий). Головне видно прямо в коді: **режим — це два біти**, CPOL і CPHA. Зміна режиму на 3 — це лише `SPI_CPOL_1 | SPI_CPHA_1` замість нулів:

```c
void spi_init_mode3(void) {
    SPI_CTRL  = SPI_MASTER | SPI_CPOL_1 | SPI_CPHA_1 | SPI_CLK_DIV8 | SPI_ENABLE;
}                                  // такт у спокої високий, біт — на наростальному фронті
```

## Крок 3. Обрамити обмін лінією CS

Окрема операція з веденим завжди обрамлена лінією вибору: опустив CS — почав, підняв CS — завершив. Поки CS опущена, ведений активний; піднята — він «відпускає» шину (зокрема, переводить свій вихід MISO у високий імпеданс, щоб не заважати іншим). Зробимо дві дрібні помічні функції й одну для всієї транзакції.

```c
static inline void cs_low(void)  { CS_PORT &= ~CS_PIN; }  // 0 → обрали веденого
static inline void cs_high(void) { CS_PORT |=  CS_PIN; }  // 1 → відпустили

// Обмін блоком байтів за одне опускання CS: дзеркалимо tx[i] ↔ rx[i].
void spi_xfer_block(const uint8_t *tx, uint8_t *rx, uint16_t n) {
    cs_low();
    for (uint16_t i = 0; i < n; i++) {
        uint8_t in = spi_transfer(tx ? tx[i] : 0xFF);  // нема даних на відсил → шлемо пусте
        if (rx) {
            rx[i] = in;                                // нема куди приймати → просто відкидаємо
        }
    }
    cs_high();
}
```

Зверни увагу на одну тонкість: **CS опускаємо один раз на всю транзакцію**, а не на кожен байт. Для більшості чіпів підняття CS між байтами означало б «команда скінчилась, скинь стан» — і багатобайтова операція розпалася б. (Є чіпи, що навпаки вимагають імпульс CS на кожне слово, — це знов-таки питання даташита.)

## Крок 4. Скласти осмислені операції: регістри давача

Тепер з голого обміну збираємо те, заради чого все й робилося, — читання й запис внутрішнього регістра чіпа. Типова домовленість (її тримається безліч SPI-давачів): перший байт — це **адреса регістра**, у якій старший біт каже напрямок (1 — читати, 0 — писати); далі йдуть байти даних. Конкретні біти беруться з даташита, але узор майже завжди такий:

```c
#define READ_BIT  0x80     // старший біт адреси: 1 = читання

// Прочитати один регістр: шлемо адресу з READ_BIT, на другому байті
// висуваємо пусте й забираємо вміст регістра.
uint8_t sensor_read_reg(uint8_t reg) {
    uint8_t tx[2] = { (uint8_t)(reg | READ_BIT), 0x00 };
    uint8_t rx[2];
    spi_xfer_block(tx, rx, 2);
    return rx[1];          // rx[0] прийшов під час адреси — він нам не потрібен
}

// Записати один регістр: адреса без READ_BIT, тоді байт даних.
void sensor_write_reg(uint8_t reg, uint8_t val) {
    uint8_t tx[2] = { (uint8_t)(reg & ~READ_BIT), val };
    spi_xfer_block(tx, NULL, 2);   // приймати нічого — rx не потрібен
}
```

Уся «магія» давача звелася до двох обмінів по два байти. У `sensor_read_reg` важлива деталь: відповідь приходить **зі зсувом** — поки ми висуваємо адресу (перший байт), назад іде ще «старий» вміст MISO, тож корисний байт опиняється **другим** (`rx[1]`). Це пряма дія повного дуплексу: ведений не встигає відповісти на тому ж байті, у якому ще тільки дізнається, що саме в нього просять.

Складемо все в коротку перевірку зв'язку — прочитати «хто я» (більшість чіпів мають реєстр-ідентифікатор зі сталим значенням):

```c
int sensor_probe(uint8_t whoami_reg, uint8_t expected_id) {
    spi_init_mode0();                         // шина: ведучий, режим 0
    cs_high();                                // CS у спокої високий
    uint8_t id = sensor_read_reg(whoami_reg); // один обмін 2 байти
    return (id == expected_id) ? 0 : -1;      // 0 — чіп озвався як треба
}
```

Варто одразу побачити **ціну** такого простого `spi_transfer`: він **активно чекає** (крутить порожній цикл, поки апарат прокрутить байт). Для короткої перевірки зв'язку це дрібниця, але якщо треба перелити в дисплей чи флеш цілий кадр — тисячі байтів, — процесор увесь цей час стоятиме в `while`, не роблячи нічого корисного. Грубо порахуймо: на такті 1 МГц один байт — це 8 мікросекунд, тож кадр у 10 кілобайт з'їсть близько 80 мілісекунд **суцільного чекання**. Тому для великих потоків той самий обмін байтом виносять із циклу-чекання: або вмикають **переривання** «байт відіслано» й віддають час іншим задачам, або доручають перекачування **DMA** — апаратному перекладачеві пам'ять↔SPI, що жене блок без участі процесора. Кістяк при цьому не змінюється: усе одно це послідовність обмінів одним байтом, лише чекання на кожен віддане апарату.

## Пастки

- **Неправильний режим (CPOL/CPHA).** Найчастіша причина «нічого не працює, хоч усе з'єднано». Дроти правильні, а на виході сміття — майже завжди різні режими в ведучого й веденого. Перша перевірка — звірити режим із даташита; деталі в темі [CPOL/CPHA](topic:com-devices/spi-mode-selection).
- **Забув висунути байт на читанні.** `spi_read()`, що не висуває нічого, не прокрутить кільце — читати треба, **висуваючи** пусте (0xFF чи 0x00). Це не формальність, а фізика зсуву.
- **Зсув відповіді на байт.** Очікуєш дані в `rx[0]`, а вони в `rx[1]`. Поки висувається адреса, назад іде ще не та інформація — корисне приходить на **наступному** байті. Класична причина «читаю чіп, а там попереднє значення».
- **CS смикається не так, як треба чіпу.** Підняв CS між байтами багатобайтової команди — і чіп скинув стан; або, навпаки, тримав опущеним там, де чіп чекає імпульс на кожне слово. Робота з CS — строго за даташитом конкретного пристрою; це другий за частотою глюк SPI після режиму.
- **Зашвидкий такт.** Поставив дільник на максимум, а чіп (або довгі доріжки/дроти) стільки не тягне — фронти «розмазуються», біти зчитуються хибно. Починай з помірної частоти, піднімай, коли впевнився, що базовий обмін надійний.
- **MISO не у високому імпедансі.** Якщо на спільному MISO висить ведений, який не вміє відпускати вихід, два пристрої змагаються за лінію — «кожен поодинці працює, разом ні». Перевір у даташиті, що ведений переводить MISO у Z за CS = 1.

Зібравши ці шматки — `spi_transfer` як єдина основа, налаштування режиму двома бітами, обрамлення лінією CS і складання операцій «адреса + дані», — дістаєш повний робочий каркас для будь-якого SPI-чіпа. Далі змінюються лише номери регістрів і формат команд із даташита, а кістяк лишається тим самим.
