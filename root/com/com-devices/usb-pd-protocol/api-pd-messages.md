# 📋 Довідник протоколу USB PD 3.1: структури кадрів, типи повідомлень та таймери

Цей довідник містить повний звід бітових полів, структур заголовків, форматів об'єктів даних, числових кодів керівних і розширених повідомлень, а також часових нормативів рівня протоколу USB Power Delivery (USB PD 3.1). Документ слугує інженерною специфікацією для розробки низькорівневих драйверів контролерів портів (TCPC — Type-C Port Controller), стеків керування живленням (TCPM — Type-C Port Manager) та вбудованого мікропрограмного забезпечення вбудованих систем.

---

### 1. Бітова структура та розбір 16-бітного Message Header

Заголовок повідомлення (Message Header) передається по лінії конфігураційного каналу CC молодшим байтом уперед (little-endian) безпосередньо після стартової 4-символьної послідовності K-кодів SOP/SOP'/SOP''. Заголовок є обов'язковою частиною абсолютно кожного кадру USB PD і містить критично важливу інформацію для первинної класифікації пакета, перевірки сумісності ролей та детектування дублікатів.

Заголовок упаковано в 16 бітів. Розташування полів оптимізовано для швидкого апаратного декодування простими масками регістрів. Молодший байт (біти 0..7) несе тип повідомлення, ревізію стандарту та ролі передавача, тоді як старший байт (біти 8..15) визначає лічильник транзакцій, розмір корисного навантаження та ознаку розширеного протоколу.

| Біти | Поле | Тип | Опис, бітові маски та значення |
| :--- | :--- | :--- | :--- |
| **15** | `Extended` | `bool` | **Тип структури повідомлення:**<br>`0` = Стандартне повідомлення (керівне або даних із розміром корисного навантаження 0..28 байтів).<br>`1` = Розширене повідомлення (Extended Message, розмір даних до 260 байтів, супроводжується полем `Extended Message Header`). |
| **14:12** | `NumDataObjects` | `uint3` | **Кількість 32-бітних об'єктів даних (Data Objects):**<br>`000b` (0) = Керівне повідомлення (Control Message), тіло даних відсутнє (розмір корисного навантаження — 0 байтів).<br>`001b`–`111b` (1..7) = Повідомлення даних (Data Message), розмір тіла становить `4 × NumDataObjects` байтів (від 4 до 28 байтів).<br>Якщо `Extended = 1`, це поле визначає розмір поточного чанка в режимі фрагментації. |
| **11:9** | `MessageID` | `uint3` | **Циклічний лічильник транзакцій (діапазон 0..7):**<br>Інкрементується відправником на одиницю для кожного нового сформованого повідомлення. При повторних спробах відправки (Retry) у разі відсутності підтвердження значення залишається незмінним. |
| **8** | `PortPowerRole` / `CablePlug` | `uint1` | **Роль живлення порту або адресація кабелю:**<br>**У пакетах SOP:** Поточна силова роль порту-відправника:<br>`0` = Стік (Sink / споживач енергії).<br>`1` = Джерело (Source / постачальник живлення).<br>**У пакетах SOP' / SOP'':** Походження повідомлення щодо кабелю:<br>`0` = Повідомлення надіслано портом DFP або UFP до кабелю.<br>`1` = Повідомлення згенеровано вбудованим штекером кабелю (Cable Plug e-Marker). |
| **7:6** | `SpecRevision` | `uint2` | **Версія специфікації протоколу USB Power Delivery:**<br>`00b` = Ревізія 1.0 (застаріла передача FSK по VBUS).<br>`01b` = Ревізія 2.0 (базовий стандарт BMC по лінії CC).<br>`10b` = Ревізія 3.0 / 3.1 (підтримка розширених повідомлень, PPS, EPR, FRS).<br>`11b` = Зарезервовано для майбутніх стандартів. |
| **5** | `PortDataRole` | `uint1` | **Роль передачі даних USB (для пакетів SOP):**<br>`0` = UFP (Upstream Facing Port — підлеглий пристрій / USB Device).<br>`1` = DFP (Downstream Facing Port — головний контролер / USB Host).<br>Для пакетів SOP'/SOP'' цей біт зарезервовано і передається як `0`. |
| **4:0** | `MessageType` | `uint5` | **Числовий ідентифікатор типу повідомлення:**<br>Визначає команду або структуру переданих даних. Інтерпретація 5-бітного коду залежить від комбінації бітів `NumDataObjects` та `Extended`. |

Порядок слідування бітів у фізичному каналі організовано за правилом «молодший біт нульового байта — першим». Тобто біт 0 (`MessageType`) виходить на лінію CC одразу за останнім бітом K-коду маркера SOP, а біт 15 (`Extended`) завершує передачу заголовка.

Поле `SpecRevision` є критичним для зворотної сумісності. Коли пристрій стандарту PD 3.0 надсилає перше повідомлення, він виставляє ревізію `10b`. Якщо підключений адаптер підтримує лише старіший стандарт PD 2.0, він відповість кадром із ревізією `01b`. Обидві сторони негайно адаптують свої автомати станів, блокуючи використання розширених функцій (Extended Messages, Fast Role Swap або PPS), які не підтримуються ревізією 2.0.

Поле `MessageID` утворює основу надійного зв'язку в напівдуплексному каналі. Воно працює як 3-бітний кільцевий лічильник (від 0 до 7 із переходом від 7 до 0). Передавач збільшує це значення виключно тоді, коли попередня транзакція була успішно завершена прийомом валідного підтвердження GoodCRC або після виконання процедури програмного скидання Soft_Reset (яка примусово скидає `MessageID` в 0). Якщо відправник не отримав GoodCRC і повторює відправку кадру через таймаут, він зобов'язаний зберегти старе значення `MessageID`. Приймач, побачивши повторення вже обробленого номера, розуміє, що це дублікат, і не передає дані рушію політики вдруге, але негайно повертає GoodCRC.

### 2. Бітова структура 16-бітного Extended Message Header

Поле розширеного заголовка з'являється у структурі кадру одразу після основного `Message Header` (байти 2 та 3 пакета) тоді й лише тоді, коли в основному заголовку встановлено біт `Extended = 1`. Воно керує фрагментацією великих блоків пам'яті (до 260 байтів) для контролерів з обмеженими буферами FIFO.

Розширений заголовок розв'язує фундаментальну апаратну проблему: мікроконтролери початкового рівня мають апаратні буфери прийому розміром усього 32 або 64 байти, тоді як передача криптографічних сертифікатів безпеки або блоків прошивки вимагає пересилання масивів по 260 байтів. Механізм фрагментації розбиває велике повідомлення на серію компактних пакетів, які вкладаються у стандартні часові рамки фізичного рівня.

| Біти | Поле | Тип | Функціональне призначення |
| :--- | :--- | :--- | :--- |
| **15** | `Chunked` | `bool` | **Режим передачі даних:**<br>`1` = Режим фрагментації (Chunked Mode). Масив розбивається на частини розміром до 26 байтів даних (+ 2 байти Extended Header = 28 байтів тіла).<br>`0` = Нефрагментований режим (Unchunked Mode). Передається монолітний блок корисного навантаження (до 260 байтів). |
| **14:11** | `ChunkNumber` | `uint4` | **Номер поточного фрагмента даних (діапазон 0..15):**<br>Нумерація чанків починається з `0` для початкового блоку даних розширеного повідомлення й послідовно зростає. |
| **10** | `RequestChunk` | `bool` | **Напрямок транзакції фрагмента:**<br>`0` = Пакет містить фрагмент корисних даних.<br>`1` = Пакет є запитом наступного фрагмента від приймача (`ChunkNumber` вказує номер запитуваної частини). |
| **9** | `Reserved` | `uint1` | Зарезервовано консорціумом USB-IF. Під час передачі записується `0`, під час прийому значення ігнорується. |
| **8:0** | `DataSize` | `uint9` | **Повний розмір масиву корисного навантаження (діапазон 0..260 байтів):**<br>Вказує сумарний обсяг байтів усього розширеного повідомлення без урахування 2 байтів розширеного заголовка. |

Робота в режимі фрагментації підпорядковується чіткому протоколу рукостискання. Відправник формує перший кадр, записуючи в нього `ChunkNumber = 0`, загальний розмір масиву в поле `DataSize` та перші 26 байтів даних. Отримавши цей кадр і відповівши апаратним GoodCRC, приймач аналізує поле `DataSize`. Якщо передано не всі дані, приймач надсилає розширене керівне повідомлення з бітом `RequestChunk = 1` та `ChunkNumber = 1`. Відправник у відповідь надсилає другий шматок даних. Цей покроковий процес захищає черги мікроконтролера від переповнення.

Якщо обидва кінцеві пристрої мають сучасні високопродуктивні контролери з прямим доступом до пам'яті (DMA), вони домовляються про роботу в режимі `Unchunked` (біт 15 скинуто в `0`). У цьому випадку весь масив до 260 байтів передається одним безперервним пакетом із єдиною фінальною контрольною сумою CRC-32, що істотно знижує накладні витрати протоколу при оновленні прошивки або взаємній автентифікації.

### 3. Реєстр керівних повідомлень (Control Messages)

Керівні повідомлення ідентифікуються значенням `NumDataObjects = 000b` та `Extended = 0`. Вони мають фіксовану довжину кадру (рівно 6 байтів: 2 байти заголовка плюс 4 байти CRC-32) і призначені для забезпечення надшвидкого квитування, перемикання станів силових автоматів та синхронізації протоколу.

Завдяки відсутності об'єктів даних керівні повідомлення обробляються з найвищим пріоритетом. Більшість із них безпосередньо керує поведінкою апаратних блоків джерела живлення та споживача.

| Код (4:0) | Шістнадц. | Назва повідомлення | Допустимі джерела | Опис та системна поведінка |
| :--- | :--- | :--- | :--- | :--- |
| `00001b` | `0x01` | `GoodCRC` | Source, Sink, Cable | **Апаратне квитування цілісності кадру.** Надсилається приймачем протягом не більше ніж 195 мкс (`tTransmitSOP`) після перевірки валідності CRC-32 вхідного пакета. Містить ідентичне значення `MessageID`. Ніколи не квитується у відповідь. |
| `00010b` | `0x02` | `GotoMin` | Source | **Команда екстреного зниження навантаження.** Джерело вимагає від споживача негайно зменшити струм споживання до мінімального рівня, узгодженого в діючому контракті (використовується при перегріві джерела або підключенні другого порту). |
| `00011b` | `0x03` | `Accept` | Source, Sink, Cable | **Підтвердження готовності виконати запит.** Надсилається джерелом у відповідь на `Request`, або партнером у відповідь на запити зміни ролей (`PR_Swap`, `DR_Swap`, `VCONN_Swap`) чи програмного перезапуску (`Soft_Reset`). |
| `00100b` | `0x04` | `Reject` | Source, Sink, Cable | **Відмова у виконанні запиту.** Вказує, що надісланий запит не може бути задоволений. Усі поточні параметри живлення, конфігурація ліній та контракти залишаються без змін. |
| `00101b` | `0x05` | `Ping` | Source | **Перевірка активності лінії.** Періодичний сигнал опитування споживача (у специфікації PD 3.0 вилучений для транзакцій SOP і застосовується виключно в специфічних кабельних сценаріях). |
| `00110b` | `0x06` | `PS_RDY` | Source, new Source | **Готовність силового джерела (Power Supply Ready).** Сигналізує, що напруга шини VBUS успішно досягла цільового значення й стабілізувалася. Лише після цього сигналу споживач має право збільшити струм навантаження. |
| `00111b` | `0x07` | `Get_Source_Cap` | Sink, DFP | **Запит меню джерела.** Вимагає від підключеного джерела живлення повторно надіслати повний перелік його силових можливостей `Source_Capabilities`. |
| `01000b` | `0x08` | `Get_Sink_Cap` | Source, DFP | **Запит характеристик споживача.** Опитує підключений пристрій щодо переліку профілів напруг і струмів, які він здатен приймати (`Sink_Capabilities`). |
| `01001b` | `0x09` | `DR_Swap` | DFP, UFP | **Запит зміни ролі ліній даних (Data Role Swap).** Ініціює передачу ролі USB-хоста (DFP ↔ UFP) між портами без розриву контракту живлення. |
| `01010b` | `0x0A` | `PR_Swap` | Source, Sink | **Запит зміни ролі живлення (Power Role Swap).** Ініціює реверс напрямку передачі електроенергії (Source ↔ Sink) зі збереженням логічного з'єднання USB. |
| `01011b` | `0x0B` | `VCONN_Swap` | VCONN Source / Sink | **Запит передачі живлення активного кабелю.** Передає функцію подачі напруги 5 В на лінію VCONN від одного порту до іншого. |
| `01100b` | `0x0C` | `Wait` | Source, Sink | **Тимчасова затримка обробки.** Сповіщає партнера, що пристрій зайнятий виконанням внутрішніх перехідних процесів і просить повторити запит пізніше (через час `tSinkRequest` ≥ 100 мс). |
| `01101b` | `0x0D` | `Soft_Reset` | Source, Sink | **Програмне скидання протоколу.** Скидає лічильники `MessageID` в 0 на обох кінцях з'єднання та повертає кінцеві автомати в початковий стан без відключення напруги VBUS. Обов'язкова відповідь — `Accept`. |
| `01110b` | `0x0E` | `Data_Reset` | DFP | **Скидання шини передачі даних USB.** Апаратне скидання стану контролерів USB 2.0 / USB3 / USB4 (PD 3.1). |
| `01111b` | `0x0F` | `Data_Reset_Complete`| UFP | **Підтвердження скидання даних.** Сповіщає DFP про завершення процедури очищення та реініціалізації логіки передачі даних. |
| `10000b` | `0x10` | `Not_Supported` | Source, Sink, Cable | **Команда не підтримується.** Офіційна відповідь на будь-яке отримане повідомлення або запит, функціонал якого не реалізований у даному пристрої. |
| `10001b` | `0x11` | `Get_Source_Cap_Extended` | Sink | **Запит розширеного паспорта джерела.** Вимагає надіслати повідомлення `Source_Capabilities_Extended` (детальні параметри теплових обмежень та пікових потужностей). |
| `10010b` | `0x12` | `Get_Status` | Source, Sink | **Опитування операційного стану.** Запит на отримання розширеного звіту про поточну температуру, помилки, прапори подій та стан акумулятора. |
| `10011b` | `0x13` | `FR_Swap` | Fast Role Swap Sink | **Швидка екстрена зміна ролі живлення.** Завершальне повідомлення процедури Fast Role Swap після апаратної сигналізації на лінії CC (займає менше 150 мкс). |
| `10100b` | `0x14` | `Get_PPS_Status` | Sink | **Запит стану PPS.** Запит до джерела щодо фактично виміряної вихідної напруги, струму навантаження та прапорів теплового захисту в режимі PPS. |
| `10101b` | `0x15` | `Get_Country_Codes` | DFP, UFP | **Запит регіональних кодів.** Опитування переліку альфа-2 кодів країн (ISO 3166-1) для застосування специфічних норм регулювання радіо- та силових трактів. |
| `10110b` | `0x16` | `Get_Sink_Cap_Extended` | Source | **Запит розширеного паспорта споживача.** Опитує споживач щодо його теплових характеристик та обмежень завантаження. |

Особливу увагу слід звернути на семантичну різницю між повідомленнями `Reject` та `Wait`. Якщо пристрій відповідає `Reject`, переговори вважаються завершеними невдачею, і споживач повинен або лишитися на поточному контракті, або спробувати запросити менш вимогливий профіль. Якщо ж джерело відповідає `Wait`, це не є відмовою: перетворювач джерела в даний момент зайнятий (наприклад, виконує плавний перехід напруги для іншого порту або калібрує вимірювальні ланцюги) і просить споживача зачекати встановлений таймаут `tSinkRequest` перед тим, як повторити той самий запит ще раз.

Повідомлення `PS_RDY` є ключовим бар'єром безпеки силового тракту. Під час переходу з 5 на 20 вольтів джерело спочатку надсилає `Accept`, вмикає внутрішню петлю зворотного зв'язку DC-DC перетворювача та плавно нарощує напругу. Споживач у цей інтервал зобов'язаний тримати своє внутрішнє навантаження відключеним або обмеженим безпечним струмом холостого ходу (до 2.5 Вт). Лише коли напруга досягла 20 вольтів і повністю стабілізувалася в межах допуску ±5%, джерело надсилає `PS_RDY`. Отримання `PS_RDY` є єдиним законним дозволом для споживача замкнути силовий ключ навантаження.

### 4. Реєстр повідомлень даних (Data Messages)

Повідомлення даних мають значення `NumDataObjects` у діапазоні `001b`–`111b` (від 1 до 7) та `Extended = 0`. Корисне навантаження складається з одного або кількох 32-бітних слів (Data Objects). Ці структури переносять меню напруг, запити параметрів, діагностичні дані та розширення виробника.

Кожне 32-бітне слово передається у форматі little-endian (молодший байт слова виходить у лінію першим). Загальна довжина пакета на фізичному рівні становить `2 + 4 × NumDataObjects + 4` байти.

| Код (4:0) | Шістнадц. | Назва повідомлення | К-сть DO | Призначення та передані структури |
| :--- | :--- | :--- | :--- | :--- |
| `00001b` | `0x01` | `Source_Capabilities` | 1..7 | **Меню силових профілів джерела.** Масив об'єктів `Power Data Object` (PDO). Описує всі фіксовані напруги (5, 9, 15, 20 В), змінні джерела, батарейні профілі та діапазони PPS APDO. |
| `00010b` | `0x02` | `Request` | 1 | **Запит обраного профілю споживачем.** Містить один 32-бітний об'єкт `Requested Data Object` (RDO) із зазначенням номера бажаного рядка PDO, робочого та граничного струму. |
| `00011b` | `0x03` | `BIST` | 1 | **Вбудоване самотестування (Built-In Self-Test).** Задає тестові режими фізичного рівня: генерацію псевдовипадкових бітових послідовностей PRBS, перевірку очей сигналів PHY або тест тривалої несучої. |
| `00100b` | `0x04` | `Sink_Capabilities` | 1..7 | **Паспортні можливості споживача.** Перелік профілів напруг і струмів, які пристрій здатен споживати, що дозволяє джерелу оптимізувати розподіл загальної потужності. |
| `00101b` | `0x05` | `Battery_Status` | 1 | **Динамічний статус акумулятора.** 32-бітний об'єкт стану батареї (BSDO): розрахунковий залишковий заряд (SOC), стан заряду/розряду, критичні прапори несправностей. |
| `00110b` | `0x06` | `Alert` | 1 | **Асинхронне сповіщення про аварії та події.** Об'єкт Alert Data Object (ADO): бітові прапори спрацювання захистів від перенапруги (OVP), перевантаження за струмом (OCP), перегріву (OTP) або зміни стану акумулятора. |
| `00111b` | `0x07` | `Get_Country_Info` | 1 | **Запит регуляторних даних країни.** Передає 32-бітний об'єкт Country Data Object (CDO) для вибору географічного регіону. |
| `01000b` | `0x08` | `Enter_USB` | 1 | **Перехід у режим тунелювання USB4.** 32-бітний об'єкт Enter_USB Data Object (EUDO): конфігурує швидкість шини USB4 (20/40/80 Гбіт/с), підтримку PCIe та тунелювання DisplayPort. |
| `01001b` | `0x09` | `EPR_Request` | 1..2 | **Запит розширеного профілю живлення EPR (до 48 В).** Передає EPR RDO з вибором високовольтного профілю живлення (до 240 Вт) або напруги AVS. |
| `01010b` | `0x0A` | `EPR_Mode` | 1 | **Керування режимом EPR.** Об'єкт EPR Mode Data Object (EPMDO): узгодження безпечного входу, виходу та підтвердження готовності кабелю до роботи за напруг понад 20 В. |
| `01011b` | `0x0B` | `Source_Info` | 1 | **Специфікація джерела живлення.** Описує порт джерела (виділений адаптер, багатопортовий хаб, прохідний порт живлення Pass-Through). |
| `01100b` | `0x0C` | `Revision` | 1 | **Узгодження версії стандарту.** Передає найвищу підтримувану пристроєм ревізію специфікації USB Power Delivery. |
| `01111b` | `0x0F` | `Vendor_Defined` | 1..7 | **Повідомлення виробника (VDM).** Передає заголовок VDM Header та масив об'єктів VDO: опитування e-Marker кабелів, узгодження режимів DisplayPort / Thunderbolt Alternate Modes, калібрування. |

Повідомлення `BIST` (Built-In Self-Test) використовується виключно на виробничих лініях та в сертифікаційних лабораторіях. За допомогою 32-бітного об'єкта BDO тестер може наказати контролеру генерувати безперервний потік тестових шаблонів (BIST PRBS), увімкнути режим перевірки маски ока сигналу фізичного рівня (BIST Eye Pattern) або перевірити поріг чутливості приймача BMC (BIST Receiver Mode).

Повідомлення `Vendor_Defined` (VDM) утворюють універсальний транспортний рівень поверх USB PD. Завдяки VDM хост опитує мікросхеми e-Marker у кабелях (використовуючи маркери SOP'), дізнається про максимальну допустиму напругу та струм шнура, а також проводить узгодження альтернативних режимів роботи роз'єму Type-C, таких як DisplayPort Alternate Mode для виведення відеопотоку на зовнішній монітор.

У структурованих VDM консорціум VESA регламентує три базові конфігурації розподілу високошвидкісних пар контактів роз'єму USB Type-C:
* **Pin Assignment C:** Усі 4 диференційні пари SuperSpeed (TX1/RX1, TX2/RX2) виділяються під 4 лінії відеопотоку DisplayPort (Main Link 0..3), що забезпечує максимальну роздільну здатність (наприклад, 4K/120 Гц або 8K/60 Гц). Передача даних USB 3.0 при цьому вимикається, залишаючи активним лише канал USB 2.0 (D+/D−).
* **Pin Assignment D:** 2 диференційні пари віддаються під DisplayPort (Main Link 0..1), а решта 2 пари залишаються для передачі даних USB 3.2 Gen 2 зі швидкістю 10 Гбіт/с. Це типовий режим роботи багатофункціональних офісних док-станцій (одночасний вивід монітора 4K/60 Гц та робота гігабітної мережі з дисками).
* **Pin Assignment E:** Режим прямого підключення до спеціалізованих моніторів із передачею додаткових службових сигналів AUX/HPD крізь лінії SBU1/SBU2.

### 5. Бітові формати об'єктів живлення PDO та запиту RDO

Кожен 32-бітний об'єкт усередині повідомлень даних розбивається на функціональні бітові поля. Розглянемо найважливіші структури, що визначають параметри силового контракту.

#### 5.1. Фіксований профіль джерела (Fixed Supply PDO)

Фіксований профіль є базовим для стандарту. Перший рядок меню `Source_Capabilities` завжди є фіксованим профілем на 5 вольтів (vSafe5V) і містить глобальні системні прапори порту джерела.

| Біти | Поле | Опис і одиниці виміру |
| :--- | :--- | :--- |
| **31:30** | `SupplyType` | `00b` = Фіксоване джерело напруги (Fixed Supply). |
| **29** | `DualRolePower` | `1` = Порт здатний змінювати роль живлення (підтримує `PR_Swap`). |
| **28** | `USBSuspend` | `1` = Пристрій вимагає дотримання правил енергозбереження USB Suspend. |
| **27** | `UnconstrainedPower` | `1` = Джерело живиться від стаціонарної електромережі (не розряджає власну батарею). |
| **26** | `USBCommunications` | `1` = Пристрій підтримує передачу даних по лініях USB (D+/D− або SuperSpeed). |
| **25** | `DualRoleData` | `1` = Порт підтримує зміну ролей передачі даних (`DR_Swap`). |
| **24** | `UnchunkedExtended` | `1` = Контролер підтримує нефрагментовані розширені повідомлення. |
| **23** | `EPRSupported` | `1` = Джерело підтримує розширений діапазон живлення EPR (до 48 В). |
| **21:20** | `PeakCurrent` | Допустиме пікове перевантаження за струмом (100–200% протягом 1–10 мс). |
| **19:10** | `Voltage` | Вихідна напруга в одиницях **50 мВ** (діапазон 0..1023 ➔ 0..51.15 В). Наприклад, 5 В = `100` (`0x064`), 20 В = `400` (`0x190`). |
| **9:0** | `MaxCurrent` | Максимальний постійний струм в одиницях **10 мА** (діапазон 0..1023 ➔ 0..10.23 А). Наприклад, 3 А = `300` (`0x12C`), 5 А = `500` (`0x1F4`). |

#### 5.2. Програмований профіль PPS (Augmented PDO / APDO)

Програмовані профілі живлення PPS дозволяють споживачу динамічно підлаштовувати напругу зарядки акумулятора з високою точністю, мінімізуючи теплові втрати у внутрішніх перетворювачах пристрою.

| Біти | Поле | Опис і одиниці виміру |
| :--- | :--- | :--- |
| **31:30** | `SupplyType` | `11b` = Розширений профіль (Augmented Power Data Object). |
| **29:28** | `APDOType` | `00b` = SPR Programmable Power Supply (PPS). |
| **27** | `PPSPowerLimited` | `1` = Вихідна потужність джерела обмежена кривою спаду за високих напруг. |
| **24:17** | `MaxVoltage` | Максимальна напруга діапазону в одиницях **100 мВ** (наприклад, 11 В = `110`, 21 В = `210`). |
| **15:8** | `MinVoltage` | Мінімальна напруга діапазону в одиницях **100 мВ** (наприклад, 3.3 В = `33`). |
| **6:0** | `MaxCurrent` | Граничний струм джерела в одиницях **50 мА** (діапазон 0..127 ➔ 0..6.35 А). Наприклад, 3 А = `60` (`0x3C`), 5 А = `100` (`0x64`). |

#### 5.3. Запит споживача (Fixed / Variable RDO)

Об'єкт `RDO` є єдиним навантаженням повідомлення `Request`. У ньому споживач посилається на номер обраного рядка з отриманого раніше списку PDO та декларує свої струмові вимоги.

| Біти | Поле | Опис і значення |
| :--- | :--- | :--- |
| **31** | `Reserved` | `0`. |
| **30:28** | `ObjectPosition` | Порядковий номер обраного PDO з меню `Source_Capabilities` (індексація починається з `1`). |
| **27** | `GiveBack` | `1` = Споживач підтримує функцію `GotoMin` і згоден зменшити струм за вимогою джерела. |
| **26** | `CapabilityMismatch` | `1` = Жоден профіль джерела не задовольняє реальні потреби споживача за потужністю. |
| **25** | `USBCommunications` | `1` = Споживач задіює лінії передачі даних USB. |
| **24** | `NoUSBSuspend` | `1` = Запит не зупиняти живлення при переході шини USB в стан Suspend. |
| **23** | `UnchunkedExtended` | `1` = Споживач підтримує нефрагментовані розширені повідомлення. |
| **22** | `EPRCapable` | `1` = Споживач готовий до роботи в режимі підвищеної напруги EPR. |
| **19:10** | `OperatingCurrent` | Робочий струм у сталому режимі в одиницях **10 мА**. |
| **9:0** | `MaxOperatingCurrent` | Максимальний струм у піку в одиницях **10 мА** (або мінімальний струм, якщо встановлено прапор GiveBack). |

Якщо споживач обирає рядок PPS APDO, формат RDO дещо змінюється: біти 19:9 задають цільову вихідну напругу з кроком **20 мВ**, а біти 6:0 — робочий ліміт струму з кроком **50 мА**.

### 6. Реєстр розширених повідомлень (Extended Messages, Ext = 1)

Розширені повідомлення обслуговують системні функції конфігурації пристроїв, криптографічного захисту від підробок та моніторингу працездатності акумуляторних батарей.

| Код (4:0) | Шістнадц. | Назва розширеного повідомлення | Макс. розмір | Функціональне призначення |
| :--- | :--- | :--- | :--- | :--- |
| `00001b` | `0x01` | `Source_Capabilities_Extended` | 24 байти | **Розширений паспорт джерела.** Описує гарантовану вихідну потужність (PDP), діапазони температур спрацювання захисту, коефіцієнти пікового струму та підтримку сенсорів торкання. |
| `00002b` | `0x02` | `Status` | 7 байтів | **Операційний звіт пристрою.** Передає виміряну внутрішню температуру (°C), стан вхідних/вихідних ключів, прапори спрацювання теплового тротлінгу та активні помилки. |
| `00003b` | `0x03` | `Get_Battery_Cap` | 1 байт | **Запит паспорта батареї.** Передає числовий індекс акумулятора (0..3) для зчитування його характеристик. |
| `00004b` | `0x04` | `Get_Battery_Status` | 1 байт | **Запит динамічного стану батареї.** Опитує поточний заряд та напругу акумулятора за вказаним індексом. |
| `00005b` | `0x05` | `Battery_Capabilities` | 9 байтів | **Паспорт акумулятора.** Розрахункова ємність батареї у ват-годинах (мВт·год), напруга повного заряду, напруга відсічки та тип електрохімічної системи. |
| `00006b` | `0x06` | `Get_Manufacturer_Info` | 2 байти | **Запит даних виробника.** Передає сектор пам'яті компонента (пристрій, кабель, батарея). |
| `00007b` | `0x07` | `Manufacturer_Info` | 26 байтів | **Інформація про виробника.** 16-бітний код USB-IF Vendor ID (VID), 16-бітний Product ID (PID) та текстовий рядок назви пристрою. |
| `00010b` | `0x08` | `Security_Request` | До 260 Б | **Запит автентифікації безпеки (Type-C Authentication).** Передає запит на зчитування ланцюжка X.509 сертифікатів або генерацію криптографічного цифрового підпису nonce. |
| `00011b` | `0x09` | `Security_Response` | До 260 Б | **Відповідь автентифікації безпеки.** Містить сертифікат відкритого ключа пристрою/кабелю або сформований ECDSA підпис. |
| `00012b` | `0x0A` | `Firmware_Update_Request` | До 260 Б | **Запит оновлення прошивки.** Передає черговий бінарний блок мікропрограми для запису у флеш-пам'ять контролера порту або кабелю. |
| `00013b` | `0x0B` | `Firmware_Update_Response`| До 260 Б | **Результат прошивки.** Повертає статус верифікації контрольної суми записаного блоку прошивки та лічильник помилок. |
| `00014b` | `0x0C` | `PPS_Status` | 4 байти | **Звіт вимірювань PPS.** Передає реальну вихідну напругу з точністю до 20 мВ, виміряний струм із точністю до 50 мА та прапор переходу в режим стабілізації струму. |
| `00015b` | `0x0D` | `Country_Info` | До 260 Б | **Регіональні обмеження.** Таблиця допустимих рівнів випромінюваної потужності та обмежень струму згідно із законодавством країни. |
| `00016b` | `0x0E` | `Country_Codes` | До 260 Б | **Список країн.** Масив підтримуваних 2-буквених кодів географічних зон. |
| `00017b` | `0x0F` | `Sink_Capabilities_Extended`| 48 байтів | **Розширений паспорт споживача.** Детальний опис допустимих температурних режимів, кривих імпедансу навантаження та динаміки споживання. |
| `00022b` | `0x12` | `EPR_Source_Capabilities` | 4..40 байтів | **Меню високовольтних профілів EPR (до 48 В).** Список фіксованих профілів EPR (28 В, 36 В, 48 В) та діапазонів регулювання EPR AVS. |
| `00023b` | `0x13` | `EPR_Sink_Capabilities` | 4..40 байтів | **Можливості споживача в режимі EPR.** Перелік підтримуваних високовольтних діапазонів споживання енергії. |

Повідомлення автентифікації `Security_Request` та `Security_Response` формують захищений криптографічний контур. Хост вимагає від зарядного адаптера або швидкісного кабелю пред'явити цифровий сертифікат, підписаний закритим ключем консорціуму USB-IF. Якщо підпис не сходиться або сертифікат відсутній (дешева несертифікована підробка), хост відмовляється укладати високовольтні контракти й обмежує струм безпечним рівнем 5 В / 3 А, рятуючи пристрій від можливого загоряння чи пробою VBUS.

Розширені повідомлення високовольтного режиму `EPR_Source_Capabilities` та `EPR_Sink_Capabilities` регламентують передачу енергії до 240 Вт (напруга 48 В при струмі 5 А). Перед надсиланням цих повідомлень джерело зобов'язане виконати процедуру перевірки кабелю: опитати e-Marker за допомогою пакета SOP' і переконатися, що кабель містить апаратну позначку `50V/5A EPR Capable`. Якщо кабель розрахований лише на стандартні 20 В, перехід в EPR блокується на рівні рушія політики.

Під час активного контракту EPR діє спеціальний сторожовий таймер `tEPRKeepAlive` (інтервал 375–500 мс). Споживач зобов'язаний періодично надсилати повідомлення оновлення стану або запиту. Якщо джерело не отримує жодного пакета протягом 1 секунди, воно аварійно розмикає високовольтні ключі й повертає шину VBUS до безпечних 5 вольтів, унеможливлюючи неконтрольоване живлення на високих напругах.

### 7. Стартові та службові послідовності K-кодів (Ordered Sets)

На фізичному рівні кадри та аварійні команди виділяються з загального бітового потоку за допомогою комбінацій спеціальних 5-бітних символів таблиці 4b5b — K-кодів. Таблиця 4b5b кодує кожні 4 біти даних 5 бітами на дроті так, щоб виключити довгі послідовності однакових нулів чи одиниць. Символи, що не відповідають жодному 4-бітному ніблу, зарезервовані як K-коди (`Sync-1`, `Sync-2`, `Sync-3`, `RST-1`, `RST-2`, `EOP`).

| Впорядкований набір | Послідовність 4 K-кодів | Адресація та системне призначення |
| :--- | :--- | :--- |
| **SOP** | `Sync-1` + `Sync-1` + `Sync-1` + `Sync-2` | **Start of Packet:** Прямий обмін між контролерами портів Source ↔ Sink. |
| **SOP'** | `Sync-1` + `Sync-1` + `Sync-3` + `Sync-3` | **SOP Prime:** Обмін між портом та мікросхемою e-Marker ближнього штекера кабелю. |
| **SOP''** | `Sync-1` + `Sync-3` + `Sync-1` + `Sync-3` | **SOP Double Prime:** Обмін між портом та мікросхемою e-Marker дальнього штекера кабелю. |
| **Hard_Reset** | `RST-1` + `RST-1` + `RST-1` + `RST-2` | **Апаратне аварійне скидання:** Негайне відключення напруги VBUS до 0 В (vSafe0V), скидання всіх параметрів портів до початкового стану. |
| **Cable_Reset** | `RST-1` + `Sync-1` + `RST-1` + `Sync-3` | **Скидання мікросхеми кабелю:** Перезавантаження контролера e-Marker у кабелі без скидання живлення VBUS між основними портами. |

Стартові послідовності володіють високою кодовою відстанню Хеммінга. Навіть якщо в процесі передачі стартового маркера один із бітів спотвориться завадою, приймач зможе однозначно розпізнати тип адресації пакета або зафіксувати аварійний сигнал Hard_Reset.

Апаратна реалізація приймача BMC виконує безперервний зсув 20-бітного вікна (4 символи по 5 бітів). Щойно комбінація бітів збігається з маскою одного з маркерів SOP, приймач скидає свій внутрішній акумулятор CRC-32 в початковий стан `0xFFFFFFFF` і починає записувати наступні байти безпосередньо в FIFO-буфер Message Header. Отримання символу `EOP` зупиняє запис, фіксує статус готовності кадру та генерує апаратне переривання для процесора.

### 8. Таймери, лічильники та часові допуски USB PD 3.1

Порушення будь-якої з наведених часових меж призводить до скидання автомата переговорів живлення та ініціації процедури Soft_Reset або Hard_Reset. Програмування таймерів у прошивках контролерів портів повинно виконуватися з урахуванням дрейфу тактових генераторів мікроконтролерів (типово ±1..2%).

| Символ таймера | Номінал | Межі стандарту | Опис, правила запуску та реакція системи |
| :--- | :--- | :--- | :--- |
| `CRCReceiveTimer` | **1.0 мс** | **0.9 .. 1.1 мс** | **Таймер очікування квитування GoodCRC.** Запускається відправником у момент передачі останнього біта маркера EOP. Якщо таймер спливає до отримання валідного GoodCRC, відправник інкрементує лічильник повторів `nRetryCount` і здійснює повторну передачу. |
| `tTransmitSOP` | **150 мкс** | **≤ 195 мкс** | **Час реакції приймача для генерації GoodCRC.** Максимально допустимий інтервал від моменту прийому останнього біта EOP вхідного повідомлення до початку генерації першого біта преамбули кадру GoodCRC. |
| `tSenderResponse` | **27 мс** | **24 .. 30 мс** | **Час очікування змістовної відповіді від партнера.** Інтервал після успішної відправки запиту `Request`, `PR_Swap` або `DR_Swap`, протягом якого партнер зобов'язаний надіслати повідомлення `Accept`, `Reject` або `Wait`. |
| `tReceiverResponse`| **12 мс** | **≤ 15 мс** | **Час підготовки відповіді приймачем.** Граничний інтервал для генерації повідомлень `Accept`/`Reject`/`Wait` рушієм політики після прийому запиту. |
| `tPSTransition` | **500 мс** | **450 .. 550 мс** | **Час перехідного процесу джерела живлення VBUS.** Максимальний інтервал від моменту надсилання повідомлення `Accept` до відправки `PS_RDY`. За цей час перетворювач напруги джерела зобов'язаний повністю стабілізувати нову напругу на шині VBUS. |
| `tPSSourceOn` | **440 мс** | **390 .. 480 мс** | **Час активації виходу джерела при PR_Swap.** Інтервал, за який новий Source повинен увімкнути силові ключі, подати 5 В на VBUS та надіслати `PS_RDY`. |
| `tPSSourceOff` | **820 мс** | **750 .. 920 мс** | **Час зняття напруги при PR_Swap.** Інтервал, за який старий Source повинен розімкнути силові ключі, розрядити шину нижче 0.8 В та надіслати `PS_RDY`. |
| `tSinkRequest` | **100 мс** | **≥ 100 мс** | **Пауза повторного запиту після повідомлення Wait.** Мінімальний час очікування споживача перед повторною відправкою `Request` у разі отримання відстрочки `Wait`. |
| `tSafe0V` | **650 мс** | **≤ 650 мс** | **Час аварійного розряду VBUS при Hard_Reset.** Максимальний час, за який джерело зобов'язане розрядити вихідні конденсатори VBUS нижче порогу безпечної напруги `vSafe0V` (0.8 В). |
| `tSrcRecover` | **760 мс** | **660 .. 1000 мс** | **Захисна пауза джерела перед перезапуском VBUS.** Час утримання нульової напруги після сигналу Hard_Reset перед повторною подачею 5 В (`vSafe5V`). |
| `nRetryCount` | **2** | **2 повтори (3 спроби)** | **Максимальна кількість спроб повторної передачі.** Якщо після 3 спроб відправки кадру GoodCRC не отримано, рівень протоколу фіксує фатальну помилку й запускає процедуру скидання. |

Дотримання таймінгу `tTransmitSOP` (не більше 195 мкс) є критичним критерієм сертифікації USB-IF. Якщо розробник застосовує повільний обробник переривань або неоптимізований алгоритм розрахунку CRC, контролер не встигатиме видати GoodCRC у відведене вікно. Відправник зафіксує таймаут `CRCReceiveTimer` (1.0 мс) і почне надсилати повторні пакети, що зрештою призведе до вичерпання лічильника `nRetryCount` та аварійного відключення порту.

Окремим важливим параметром є часове вікно перехідного процесу `tPSTransition` (450–550 мс). Якщо силовий блок джерела містить занадто великі вихідні фільтрувальні ємності (понад 100–200 мкФ) або має повільну петлю зворотного зв'язку за напругою, напруга 20 В може наростати занадто довго. Якщо джерело не встигне надіслати `PS_RDY` до вичерпання 550 мс, споживач зафіксує таймаут протоколу й ініціює Hard_Reset, знеструмивши порт. Тому динаміка DC-DC перетворювача повинна точно узгоджуватися з часовими константами стека протоколу.

Для екстреної процедури Fast Role Swap (FRS) часові допуски є ще більш жорсткими:
* Сигнал виявлення FRS на лінії CC формується аналоговим замиканням опору протягом **60–120 мкс** (параметр `tFRSwapTx`).
* Приймач зобов'язаний зафіксувати цей спад напруги компаратором за час менше ніж **150 мкс** (`tFRSwapRx`).
* Резервне джерело живлення зобов'язане замкнути свої силові ключі й вийти на стабілізацію 5 В не пізніше ніж через **150 мкс** після фіксації сигналу.

Така мікросекундна швидкість гарантує, що напруга шини VBUS на блокувальних конденсаторах споживача не встигне просісти нижче порогу аварійного перезавантаження процесора (4.5 В).
