# 📜 Народження CoAP: як робоча група IETF CoRE перенесла REST у 6LoWPAN

Цей історичний нарис відтворює інженерний конфлікт кінця 2000-х років довкола веб-технологій для автономних сенсорних мереж, який призвів до створення протоколу CoAP. Матеріал розкриває, чому спроби прямого портування HTTP/1.1 та TCP на бездротові мікроконтролери зазнали краху, і як робоча група IETF CoRE сформулювала бінарну альтернативу класичному вебу.

### Контекст: перемога IPv6 у 6LoWPAN та глухий кут прикладного рівня

У 2007 році робоча група IETF під керівництвом Джеффа Монгола (англ. *Geoff Mulligan*) опублікувала стандарт RFC 4944 (6LoWPAN — *IPv6 over Low-Power Wireless Personal Area Networks*). Це був фундаментальний прорив: 128-бітні адреси IPv6 вдалося стиснути й упакувати в крихітні 127-байтові кадри радіостандарту IEEE 802.15.4. Мережевий рівень отримав повну сумісність із глобальним Інтернетом — кожен крихітний бездротовий датчик температури тепер міг мати власну публічну IP-адресу.

Проте щойно інженери спробували побудувати прикладний рівень, система вперлася в непереборну стіну. Інтернет того часу тримався на двох китах: протоколі TCP та текстовому HTTP/1.1 з даними у форматі XML.

Спроби запустити цей стек на типових тоді мікроконтролерах класу Texas Instruments MSP430 (8–16 КБ Flash, 512 байтів – 2 КБ RAM) чи Atmel ATmega1284P показали повну непридатність архітектури:
1. **Накладні витрати TCP.** Встановлення з'єднання через тристороннє рукостискання (SYN, SYN-ACK, ACK) вимагало тривалих радіосеансів, які миттєво висаджували дискову батарейку CR2032. Таймери повторної передачі TCP та стан `TIME_WAIT` вимагали виділення дескрипторів і буферів пам'яті, яких на кристалі з 2 КБ оперативної пам'яті просто не було.
2. **Текстова надмірність HTTP.** Навіть найкоротший запит `GET /sensor/temp HTTP/1.1` разом із обов'язковими заголовками `Host`, `User-Agent`, `Accept` та порожнім рядком займав 150–300 байтів. Оскільки корисний простір кадру 802.15.4 після вирахування заголовків канального та мережевого рівнів становив усього 60–80 байтів, один HTTP-запит примусово фрагментувався на 3–5 радіопакетів. Втрата бодай одного фрагмента в зашумленому радіоефірі призводила до скидання всього TCP-сегмента.

### Заснування CoRE WG та суперечка про парадигму (2009–2010)

У 2009 році на зустрічах IETF у Стокгольмі та Хіросімі група інженерів — Карстен Борманн (англ. *Carsten Bormann*, Бременський університет), Зак Шелбі (англ. *Zach Shelby*, компанія Sensinode), Каллен Дженнінгс (англ. *Cullen Jennings*, Cisco) та Ярі Аркко (англ. *Jari Arkko*, Ericsson) — висунула ідею створення спеціалізованого веб-протоколу для обмежених вузлів.

У березні 2010 року IETF офіційно затвердила статут робочої групи **CoRE** (англ. *Constrained RESTful Environments*). Перед групою стояло фундаментальне архітектурне питання: яку парадигму обрати основою інтерфейсу?

На той час уже існував протокол MQTT від IBM, який пропонував модель брокерної публікації/підписки поверх TCP. Проте CoRE WG свідомо відкинула MQTT як єдиний стандарт для польових сенсорних мереж через три ключові причини:
- **Відсутність децентралізації.** Модель MQTT жорстко прив'язана до центрального брокера. Якщо два сусідні польові давачі на стовпах вуличного освітлення хочуть передати один одному сигнал тривоги без виходу в Інтернет, їм однаково потрібен запущений брокер.
- **Неможливість REST-адресації ресурсів.** Концепція семантичного Вебу (REST) спирається на універсальні ідентифікатори URI, безпечні методи (`GET`, `PUT`, `DELETE`) та ідемпотентність. MQTT оперував лише непрозорими топіками.
- **Важкість TCP для сплячих вузлів.** Давач, що прокидається раз на годину на 10 мілісекунд для надсилання одного виміру, не може дозволити собі утримувати TCP-сесію або щоразу заново підключатися до брокера.

### Проектування двійкового REST (2010–2014)

Команда Карстена Борманна та Зака Шелбі пішла шляхом переосмислення REST: зберегти семантику HTTP, але радикально переробити транспортний і двійковий рівні.

Головними архітектурними знахідками стали:
1. **Двошарова модель.** Розділення абстракцій: нижній шар відповідає за надійність передачі датаграм через UDP (повідомлення `CON`, `ACK`, `NON`, `RST` з 16-бітним `Message ID`), а верхній шар реалізує чистий REST (методи, коди відповідей та токени `Token`). Це дало змогу надсилати відповідь прямо всередині підтвердження доставки (попутна відповідь, англ. *piggybacked response*) усього за одну транзакцію туди й назад (1 RTT).
2. **4-байтовий фіксований заголовок.** Усі критичні службові поля вклали рівно в 32 біти. Запит `GET` без додаткових параметрів став займати всього 4 байти замість кількох сотень у HTTP.
3. **Дельта-кодування опцій.** Замість передачі текстових рядків на кшталт `Content-Type: application/json` або `Max-Age: 60` було створено числовий реєстр опцій та форматів (Content-Format ID), які пакуються з компактним дельта-зсувом (1 байт на опцію у більшості випадків).
4. **Асинхронний REST (Observe).** Замість безперервного опитування (polling), яке вбивало батареї, розробили механізм RFC 7641: клієнт надсилає звичайний `GET` з прапорцем спостереження, і сервер сам надсилає оновлення під час зміни фізичного стану ресурсу.

У червні 2014 року робота групи увінчалася публікацією стандарту **RFC 7252: The Constrained Application Protocol (CoAP)**. Протокол миттєво став основою для міжнародних індустріальних консорціумів: Open Mobile Alliance обрав CoAP фундаментальним транспортом для протоколу керування пристроями **LwM2M**, а альянс Thread та протокол Zigbee IP інтегрували його у свої специфікації розумного будинку та промислової автоматизації.
