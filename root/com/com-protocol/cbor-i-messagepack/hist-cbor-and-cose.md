# 📜 Від MessagePack до CBOR і COSE: як бінарний JSON став стандартом IETF

У 2008 році інженер Садаюкі Фурухаші (Sadayuki Furuhashi, творець проекту Fluentd) зіткнувся з фундаментальною проблемою розподілених систем: формат JSON вимагав надто багато процесорного часу на парсинг і створював гігабайти текстового оверхеду під час логування та міжсерверної взаємодії. Постійне переведення чисел з текстового представлення у бінарне (`strtod`, `strtol`) та екранування лапок навантажували вузли кластера сильніше, ніж сама бізнес-логіка. Відповіддю Фурухаші став формат MessagePack — проста схема пакування об'єктної моделі JSON у бінарні маркери з гаслом «Це як JSON, але швидкий і компактний».

MessagePack швидко здобув популярність у сервісах на кшталт Redis, Fluentd та сховищах ключ-значення, оскільки дозволяв без переписування коду замінити текстовий серіалізатор на бінарний. Проте коли на початку 2010-х років робоча група IETF CoRE (Constrained RESTful Environments) розпочала розробку протоколів для Інтернету речей (IoT), сенсорних мереж 6LoWPAN та протоколу CoAP (RFC 7252), виявилося, що MessagePack у початковому вигляді не підходить на роль глобального відкритого інтернет-стандарту.

### Проблема двовладдя типів і криза сумісності MessagePack

Перша версія специфікації MessagePack містила фатальну для вбудованих систем двозначність: вона не розрізняла сирі послідовності байтів (`raw bytes`) та текстові рядки UTF-8. Був присутній лише єдиний тип `raw`. Кожна мова програмування трактувала його по-своєму: у Ruby чи C він читався як масив байтів, а в JavaScript чи Python — як рядок UTF-8. Якщо клієнт надсилав скомпільований бінарний образ прошивки або вектор ініціалізації шифру, приймач на динамічній мові міг спробувати валідувати його як текст, що призводило до помилок декодування або спотворення даних.

У 2013 році специфікацію MessagePack було оновлено: з'явилися окремі типи `bin` (сирі байти) та `str` (UTF-8 текст), а також механізм розширень `ext`. Проте стара екосистема бібліотек уже була фрагментована: пристрої зі старими парсерами MessagePack не могли читати пакети від нових, а нові бібліотеки ламалися на старих потоках.

Крім того, кодова матриця MessagePack формувалася історично та ітеративно. Маркери типів були розподілені нерівномірно: під фіксовані цілі виділялися окремі діапазони, під масиви — інші, а логіка заголовків не мала єдиної симетричної бітової структури. Для мікроконтролерів із кількома кілобайтами пам'яті програм (Flash) це вимагало великих таблиць переходів `switch-case` у парсері, що роздувало машинний код.

### Народження CBOR: математична симетрія Carsten Bormann

Інженери Карстен Борманн (Carsten Bormann, Бременський університет) та Пол Гоффман (Paul Hoffman, VPN Consortium) запропонували принципово інший підхід. Замість довільного набору бінарних тегів вони заклали в основу формату CBOR (Concise Binary Object Representation, спочатку RFC 7049 у 2013 році, згодом актуалізований у RFC 8949) сувору ортогональну матрицю:

1. **3 біти старшого типу (Major Type)** визначають один із рівно 8 базових класів даних.
2. **5 бітів додаткової інформації (Additional Information)** уніфіковано для всіх 8 типів кодують або пряме коротке значення (0..23), або розмір наступного поля довжини (1, 2, 4, 8 байтів), або маркер потокового режиму.

Завдяки цьому базовий цикл декодера CBOR на асемблері або C займає лічені десятки байтів коду: зсув `byte >> 5` дає тип, а маска `byte & 0x1F` одразу запускає уніфікований автомат зчитування довжини для будь-якого контейнера, рядка чи числа.

Борманн також додав до стандарту системні можливості, яких критично бракувало попередникам:
- **Major Type 6 (Semantic Tags)** — стандартизовані префікси для розширення семантики без модифікації парсера (мітки часу UNIX та ISO 8601, великі числа `bignum`, дроби з фіксованою комою, географічні координати WGS84, UUID та хеш-суми).
- **Половинна точність чисел з комою (IEEE 754 Float16)** — значення температури, тиску чи напруги на IoT-давачах передаються лише двома байтами замість чотирьох чи восьми без втрати практичної точності вимірювання.
- **Підтримка невизначеної довжини (Indefinite-Length Streams)** — можливість передавати потокові дані шматками (`chunked transfer`) у режимі реального часу без попереднього знання повного розміру масиву чи рядка.

### Від JSON Web Tokens (JWT) до криптографії COSE

У веб-розробці для підпису та шифрування структурованих даних домінував стек JOSE (Javascript Object Signing and Encryption) та формат токенів JWT (RFC 7519). Проте структура JWT побудована на текстовому JSON, упакованому в Base64URL:

```
eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.c2lnbmF0dXJl...
```

Для обмежених пристроїв (мікроконтролери з радіомодулями Bluetooth Low Energy, IEEE 802.15.4, Thread, LoRaWAN) такий стек був катастрофічно важким. По-перше, текстовий JSON вимагав парсингу рядків. По-друге, кодування Base64 додавало 33% зайвого обсягу на радіоканалі, де кожен байт виснажує батарею. По-третє, криптографічні підписи (наприклад, ECDSA або Ed25519) працюють із сирими байтами, тому пристрою доводилося декодувати Base64 у пам'ять, а це вимагало динамічної купи (RAM).

У 2017 році робоча група IETF представила стандарт COSE (CBOR Object Signing and Encryption, RFC 8152, оновлений у RFC 9052 та RFC 9053). COSE став прямим бінарним дзеркалом JOSE:
- `COSE_Sign1` замінив підписані токени JWS;
- `COSE_Encrypt0` замінив шифровані конверти JWE;
- `COSE_Key` замінив структури відкритих і закритих ключів JWK.

Замість текстових ключів у мапах (`"alg"`, `"typ"`, `"iss"`) у COSE використовуються цілі числа від'ємного та додатного діапазону CBOR (наприклад, алгоритм ES256 позначається числом `-7`, а ідентифікатор ключа `kid` — числом `4`). Повний криптографічний конверт авторизації з підписом зменшився з 250–400 байтів у форматі JWT до 60–90 байтів у форматі COSE_Sign1, що дозволило вміщувати криптографічно підписані команди в один-єдиний кадр протоколів BLE чи 6LoWPAN.

### Стандартизація dCBOR та FIDO2

З появою апаратних ключів безпеки FIDO2 / WebAuthn та захищеного протоколу CoAP (OSCORE, RFC 8613) виникла потреба у суворій детермінованості серіалізації: криптографічний підпис обчислюється над хешем байтового масиву, тому два пристрої, серіалізуючи однакові дані, повинні генерувати абсолютно ідентичний побітовий результат.

Специфікація RFC 8949 формалізувала розділ детермінованого кодування (Deterministic Encoding), а пізніше робоча група IETF оформила суворий профіль dCBOR (Deterministic CBOR). Він вимагає обов'язкового лексикографічного сортування ключів словників, кодування цілих чисел у найкоротший можливий бінарний вигляд, заборону потокових маркерів невизначеної довжини та єдине канонічне представлення чисел з плаваючою комою.

Сьогодні CBOR є де-факто фундаментом безпеки сучасних бездротових екосистем: від смарт-замків Matter (де всі конфігураційні структури передаються у CBOR) та апаратних токенів YubiKey до супутникових протоколів і телеметрії авіоніки.
