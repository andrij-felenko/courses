Коли бездротовий сенсор у мережі LoRaWAN чи 6LoWPAN відправляє стан давача на сервер через радіоканал, кожен байт корисного навантаження має пряму ціну в міліампер-годинах заряду батареї та часі зайнятості ефіру (Time on Air). Якщо запакувати вимірювання температури, ідентифікатор вузла та мітку часу в текстовий JSON, повідомлення `{"sensor_id":42,"temp":23.5,"time":1714560000}` займе 47 байтів. У протоколі LoRaWAN на максимальній дальності (Spreading Factor SF12) граничний розмір корисного навантаження в одному пакеті становить лише 51 байт. Текстовий формат вичерпує майже весь бюджет кадру на службові символи: лапки, фігурні дужки, двокрапки та запис чисел у вигляді ASCII-символів.

Ба більше, на приймальному мікроконтролері з 8 або 16 КБ оперативної пам'яті розбір цього текстового повідомлення вимагає перетворення рядків у числа за допомогою функцій `strtod` чи `strtol`, обробки екранування символів і часто побудови проміжного об'єктного дерева в динамічній купі (heap).

Бінарні безсхемні формати CBOR (Concise Binary Object Representation, RFC 8949) та MessagePack вирішують цю проблему: вони зберігають гнучку модель даних JSON (числа, рядки, списки, словники), але кодують типи та значення компактними бінарними маркерами. Той самий пакет телеметрії у бінарному представленні зменшується з 47 до 9–15 байтів, розбирається за один лінійний прохід без виділення динамічної пам'яті й безпосередньо вміщується в один радіокадр.

### Анатомія бінарного заголовка CBOR (RFC 8949)

Формат CBOR (RFC 8949, що прийшов на заміну RFC 7049) побудований навколо строгої ортогональної матриці типів. На відміну від довільного набору тегів, кожен інформаційний елемент у CBOR починається з одного початкового байта (Initial Byte), який ділиться на дві бітові зони:

1. **3 старші біти (біти 7..5)** задають старший тип даних (`Major Type`, значення від 0 до 7).
2. **5 молодших бітів (біти 4..0)** містять додаткову інформацію (`Additional Information`, значення від 0 до 31).

![Анатомія початкового байта CBOR](/root/com/com-protocol/cbor-i-messagepack/img/cbor-type-byte-layout.svg)
*Анатомія початкового байта CBOR: 3 біти старшого типу та 5 бітів уніфікованої шкали додаткової інформації.*

Додаткова інформація інтерпретується за єдиним математичним правилом для всіх типів даних:
- **0 .. 23 (0x00 .. 0x17):** безпосереднє значення. Якщо це ціле число — саме число зберігається у цих 5 бітах; якщо це рядок або масив — це його довжина. Увесь елемент разом із типом і значенням займає рівно 1 байт.
- **24 (0x18):** наступний 1 байт несе беззнакове 8-бітне число (`uint8_t`), діапазон значень 24 .. 255.
- **25 (0x19):** наступні 2 байти містять 16-бітне число (`uint16_t`) у порядку байтів Big-Endian, діапазон 256 .. 65 535.
- **26 (0x1A):** наступні 4 байти містять 32-бітне число (`uint32_t`) Big-Endian, діапазон до 4 294 967 295.
- **27 (0x1B):** наступні 8 байтів містять 64-бітне число (`uint64_t`) Big-Endian, діапазон до 2⁶⁴ - 1.
- **28 .. 30:** зарезервовано для майбутніх розширень стандарту.
- **31 (0x1F):** спеціальний маркер невизначеної довжини (Indefinite-Length), що відкриває потоковий режим передачі.

Стандарт визначає рівно 8 старших типів (Major Types 0..7):

#### Major Type 0: Беззнакове ціле число (Unsigned Integer)
Значення обчислюється безпосередньо зі шкали додаткової інформації:
- Число `0` кодується як байт `0x00` (`(0 << 5) | 0`).
- Число `10` кодується як `0x0A` (`(0 << 5) | 10`).
- Число `100` кодується двома байтами: `0x18 0x64` (заголовок `24` + `0x64`).
- Число `1000` кодується трьома байтами: `0x19 0x03 0xE8` (заголовок `25` + `0x03E8`).

#### Major Type 1: Від'ємне ціле число (Negative Integer)
CBOR кодує від'ємні числа за формулою `-1 - n`, де `n` — беззнакове ціле число, закодоване за правилами додаткової інформації:
- Число `-1` кодується як `n = 0` → байт `0x20` (`(1 << 5) | 0`).
- Число `-10` кодується як `n = 9` → байт `0x29` (`(1 << 5) | 9`).
- Число `-500` кодується як `n = 499` (`0x01F3`) → байти `0x39 0x01 0xF3`.

Такий підхід усуває проблему знакового біта у компліментарному коді (two's complement) і дозволяє однаково компактно упаковувати симетричний діапазон від `-2⁶⁴` до `+2⁶⁴ - 1`.

#### Major Type 2: Масив сирих байтів (Byte String, `bstr`)
Сира послідовність байтів довільного вмісту (наприклад, криптографічний ключ, хеш SHA-256 або стиснене зображення). Додаткова інформація задає довжину масиву в байтах, після чого безпосередньо слідують самі байти:
- Масив із 4 байтів `[0xDE, 0xAD, 0xBE, 0xEF]` кодується як `0x44 0xDE 0xAD 0xBE 0xEF` (байт `0x44` = `(2 << 5) | 4`).

#### Major Type 3: Текстовий рядок (Text String, `tstr`)
Рядок символів у кодуванні UTF-8. Додаткова інформація задає довжину рядка в байтах (не в кількості символів Unicode):
- Рядок `"temp"` (4 байти) кодується як `0x64 0x74 0x65 0x6D 0x70` (байт `0x64` = `(3 << 5) | 4`).

#### Major Type 4: Масив елементів (Array)
Список довільних елементів будь-яких типів. Додаткова інформація задає кількість елементів у масиві:
- Масив із двох чисел `[1, 2]` кодується як `0x82 0x01 0x02` (байт `0x82` = `(4 << 5) | 2`).

#### Major Type 5: Словник пар ключ-значення (Map)
Колекція асоціативних пар. Додаткова інформація задає кількість пар (тобто кількість елементів у потоці дорівнює `2 × count`):
- Словник `{"a": 1}` містить 1 пару і кодується як `0xA1 0x61 0x61 0x01` (`0xA1` = `(5 << 5) | 1`, далі ключ `"a"` і значення `1`).
- На відміну від JSON, ключами в мапі CBOR можуть бути не лише рядки, а й цілі числа, сирі байти або вкладені масиви.

#### Major Type 6: Семантичний тег (Semantic Tag)
Механізм розширення семантики базових типів. Додаткова інформація задає номер тегу з глобального реєстру IANA, який модифікує значення наступного елемента:
- Тег `0` (RFC 3339 дата-час у форматі рядка): `0xC0 0x74 "2026-08-27..."`.
- Тег `1` (UNIX Epoch timestamp у секундах як число): `0xC1 0x1A 0x66 0xCD 0x14 0x00`.
- Тег `2` та `3` (великі цілі числа довільної розрядності `bignum` у вигляді байтових рядків).
- Тег `4` (десятковий дріб із фіксованою комою).
- Тег `24` (вкладений CBOR-документ `CBOR-in-CBOR`, де значення передається як `bstr` для відкладеного або ізольованого парсингу).
- Тег `37` (двійковий UUID).
- Теги `64 .. 87` (типізовані числові масиви: вектори `uint8_t`, `int16_t`, `float32` без накладних витрат окремого заголовка на кожне число).

#### Major Type 7: Прості значення та числа з плаваючою комою (Simple Values / Floats)
Використовується для булевих констант, нульових покажчиків та чисел IEEE 754:
- `20 (0xF4):` `false`.
- `21 (0xF5):` `true`.
- `22 (0xF6):` `null`.
- `23 (0xF7):` `undefined`.
- `25 (0xF9):` число з плаваючою комою половинної точності IEEE 754 Float16 (2 байти корисного навантаження).
- `26 (0xFA):` число одинарної точності IEEE 754 Float32 (4 байти).
- `27 (0xFB):` число подвійної точності IEEE 754 Float64 (8 байтів).
- `31 (0xFF):` маркер завершення `Break` для потоків невизначеної довжини.

### Механізм стиснення чисел з комою: IEEE 754 Float16 (Half-Precision)

Однією з ключових переваг CBOR над іншими безсхемними форматами є нативна підтримка 16-бітних чисел з плаваючою комою (Float16, стандарт IEEE 754-2008). 

У класичному форматі Float32 число займає 4 байти (32 біти): 1 біт знака, 8 бітів експоненти зі зсувом 127 і 23 біти мантиси. Для IoT-давачів, які вимірюють температуру з точністю до десятих часток градуса, передача 4 байтів надлишкова, а запис у вигляді ASCII-рядка `"23.5"` займає 4–5 байтів.

Формат Float16 стискає значення у 16 бітів:
- **1 біт знака (`s`):** біт 15.
- **5 бітів експоненти (`e`):** біти 14..10, зсув експоненти (bias) становить `15`.
- **10 бітів мантиси (`m`):** біти 9..0, неявна одиниця перед комою (`1.m`).

Формула розрахунку значення:

```
Value = (-1)^s · 2^(e - 15) · (1 + m / 1024)
```

Розглянемо побітову конвертацію числа `23.5` у Float16:
1. Двійкове представлення числа: `23.5 = 16 + 4 + 2 + 1 + 0.5 = 10111.1_2 = 1.01111_2 × 2⁴`.
2. Знак додатний: `s = 0`.
3. Експонента: `e = 4 + 15 = 19 = 10011_2`.
4. Дробова частина мантиси (10 бітів): `0111100000_2`.
5. Результуючий 16-бітний кадр: `0_10011_0111100000_2 = 0x51E0`.

У бінарному потоці CBOR це значення передається лише трьома байтами: `0xF9 0x51 0xE0` (заголовок `0xF9` вказує на Major Type 7 та додаткове інфо 25). Діапазон значень Float16 покриває числа від приблизно `6.1 × 10⁻⁵` до `65504` із відносною точністю близько 0.1%, що ідеально відповідає фізичній точності більшості промислових і споживчих давачів.

> 🔧 **Навіщо це вбудованим пристроям:** Використання Float16 зменшує радіокадр на 2 байти на кожну виміряну величину порівняно з Float32 і на 5–6 байтів порівняно з Float64 чи рядковим JSON. У пакетах із вимірюваннями триосьового акселерометра (`x, y, z`) та гіроскопа економія сягає 18–24 байтів на кожне опитування, що подовжує автономну роботу сенсора від батареї на 20–35%.

### Потоковий режим невизначеної довжини (Indefinite-Length Streaming)

У традиційних форматах серіалізації передавач зобов'язаний заздалегідь знати повний розмір масиву, словника або рядка, щоб записати його в заголовок кадру. Якщо мікроконтролер записує аудіопотік з мікрофона чи збирає серію вимірювань акселерометра в реальному часі, йому довелося б спочатку зібрати всі дані в оперативній пам'яті (буфері SRAM), підрахувати загальний розмір і лише потім формувати пакет.

CBOR дозволяє відкривати масиви, словники та рядки без фіксованої довжини за допомогою коду додаткової інформації `31` (`0x1F`):
- Потоковий масив відкривається байтом `0x9F` (`(4 << 5) | 31`).
- Пристрій передає елементи по мірі їх надходження: `0x01`, `0x02`, `0x03`...
- Коли потік завершується, відправляється єдиний термінальний байт `0xFF` (`Break`).

Потоковий текстовий рядок відкривається байтом `0x7F` і складається з послідовності фрагментів `tstr` фіксованої довжини, що завершуються маркером `0xFF`:

```
0x7F                   [відкриття потокового рядка]
  0x63 0x66 0x6F 0x6F  [фрагмент 1: tstr(3) "foo"]
  0x63 0x62 0x61 0x72  [фрагмент 2: tstr(3) "bar"]
0xFF                   [маркер завершення Break]
```

Приймач збирає шматки безпосередньо під час передачі без необхідності попереднього виділення гігантського буфера під весь обсяг. Історичні передумови виникнення цього механізму та еволюцію стандарту розібрано у вставці [Від MessagePack до CBOR і COSE: як бінарний JSON став стандартом IETF](root:com-protocol/cbor-i-messagepack/hist-cbor-and-cose.md).

### MessagePack: структура маркерів та відмінності від CBOR

Формат MessagePack з'явився раніше за CBOR і ставив за мету максимальне спрощення бінарного представлення JSON для веб-серверів і розподілених баз даних (Redis, Fluentd).

Замість фіксованої матриці з 3 бітів типу і 5 бітів довжини MessagePack використовує набір байтових діапазонів (Type Markers):

| Діапазон маркерів | Тип даних у MessagePack | Розмір заголовка |
|---|---|---|
| `0x00 .. 0x7F` | Позитивне фіксоване ціле (`positive fixint`, 0..127) | 1 байт (значення всередині) |
| `0x80 .. 0x8F` | Фіксований словник (`fixmap`, до 15 пар) | 1 байт |
| `0x90 .. 0x9F` | Фіксований масив (`fixarray`, до 15 елементів) | 1 байт |
| `0xA0 .. 0xBF` | Фіксований рядок (`fixstr`, довжина до 31 байта) | 1 байт |
| `0xC0` | `nil` (null) | 1 байт |
| `0xC2 .. 0xC3` | `false` / `true` | 1 байт |
| `0xC4 .. 0xC6` | Бінарні дані `bin8`, `bin16`, `bin32` | 2, 3, 5 байтів |
| `0xCA .. 0xCB` | Числа з плаваючою комою `float32`, `float64` | 5, 9 байтів |
| `0xCC .. 0xCF` | Цілі беззнакові `uint8`, `uint16`, `uint32`, `uint64` | 2, 3, 5, 9 байтів |
| `0xD0 .. 0xD3` | Цілі знакові `int8`, `int16`, `int32`, `int64` | 2, 3, 5, 9 байтів |
| `0xD4 .. 0xD8` | Фіксовані розширення `fixext1`, `fixext2`, `4`, `8`, `16` | 2, 3, 5, 9, 17 байтів |
| `0xE0 .. 0xFF` | Від'ємне фіксоване ціле (`negative fixint`, -32..-1) | 1 байт |

Головні архітектурні відмінності між CBOR та MessagePack визначаються вимогами стандартизації та системного програмування:

1. **Симетрія декодування:** У CBOR декодеру достатньо зробити один бітовий зсув `byte >> 5`, щоб отримати один із 8 типів, і операцію `byte & 0x1F`, щоб отримати код довжини. У MessagePack маркери розкидані по всій таблиці байтів, що вимагає великої таблиці `switch-case` на 256 станів або каскаду умов `if-else`, що збільшує розмір скомпільованого коду парсера на мікроконтролері.
2. **Типи ключів у словниках:** За специфікацією MessagePack ключі словників майже завжди очікуються рядковими (успадковано від JSON). У CBOR мапи нативно підтримують цілочисельні ключі. Заміна рядкового ключа `"temperature"` (12 байтів) на ціле число `1` (1 байт) зменшує накладні витрати словника у понад 10 разів.
3. **Підтримка Float16:** MessagePack підтримує лише Float32 (4 байти) та Float64 (8 байтів). У CBOR є нативний 2-байтний Float16.
4. **Потокове кадрування:** MessagePack не підтримує маркери невизначеної довжини (Indefinite Length), тому не дозволяє передавати потокові дані шматками без попереднього знання розміру.
5. **Стандартизація IANA:** CBOR є офіційним інтернет-стандартом IETF з єдиним відкритим реєстром семантичних тегів. MessagePack розвивається як незалежна специфікація спільноти.

### Порівняння розмірів та накладних витрат

Розглянемо конкретний приклад телеметричного кадру давача розумного будинку:
- Ідентифікатор давача: `1`
- Виміряна температура: `23.5` °C
- Прапорець готовності: `true`

![Порівняння упаковки у форматах даних](/root/com/com-protocol/cbor-i-messagepack/img/cbor-vs-msgpack-wire.svg)
*Порівняння структури корисного навантаження одного й того ж повідомлення у чотирьох форматах представлення.*

Проведемо побайтовий розбір кожного варіанта кодування:

#### 1. Текстовий JSON (RFC 8259)
```json
{"temp":23.5,"id":1,"ok":true}
```
Послідовність символів ASCII:
`7B 22 74 65 6D 70 22 3A 32 33 2E 35 2C 22 69 64 22 3A 31 2C 22 6F 6B 22 3A 74 72 75 65 7D`
Загальний розмір: **30 байтів** (без пробілів) або **42 байти** (з типовим форматуванням).

#### 2. MessagePack (з рядковими ключами)
- `0x83`: `fixmap(3)` — словник із 3 пар
- `0xA4 0x74 0x65 0x6D 0x70`: `fixstr(4)` `"temp"`
- `0xCA 0x41 0xBC 0x00 0x00`: `float32` `23.5`
- `0xA2 0x69 0x64`: `fixstr(2)` `"id"`
- `0x01`: `pos fixint` `1`
- `0xA2 0x6F 0x6B`: `fixstr(2)` `"ok"`
- `0xC3`: `true`
Загальний розмір: **20 байтів**.

#### 3. CBOR (з цілочисельними ключами та Float16)
Використовуємо угоду: ключ `1` = `temp`, ключ `2` = `id`, ключ `3` = `ok`.
- `0xA3`: `map(3)` — словник із 3 пар
- `0x01`: `uint(1)` — ключ 1
- `0xF9 0x51 0xE0`: `float16` `23.5` (`0x51E0` у форматі IEEE 754 Half)
- `0x02`: `uint(2)` — ключ 2
- `0x01`: `uint(1)` — значення 1
- `0x03`: `uint(3)` — ключ 3
- `0xF5`: `true`
Загальний розмір: **9 байтів**.

#### 4. Сира C-структура в пам'яті (Raw binary struct)
:::tabs
```c
struct __attribute__((packed)) RawTelemetry {
    float temp;     // 4 байти
    uint8_t id;     // 1 байт
    uint8_t ok;     // 1 байт
};
```
```cpp
#pragma pack(push, 1)
struct RawTelemetry {
    float temp;     // 4 байти
    uint8_t id;     // 1 байт
    uint8_t ok;     // 1 байт
};
#pragma pack(pop)
```
:::
Загальний розмір: **6 байтів** (або 8 байтів без атрибута `packed` через вирівнювання пам'яті).

Таблиця зведених системних характеристик:

| Формат | Розмір повідомлення | Накладні метадані | Потрібна схема? | Виділення динамічної купи (RAM) | Стійкість до зміни версії |
|---|---|---|---|---|---|
| **JSON** | 30–42 байти | ~70% байтів — синтаксис | Ні (самоописний) | Так (DOM-дерево рядків) | Висока (ігнорування невідомих ключів) |
| **MessagePack** | 20 байтів | ~50% байтів | Ні (самоописний) | Можливий Zero-Copy | Висока |
| **CBOR (рядкові ключі)** | 19 байтів | ~48% байтів | Ні (самоописний) | Можливий Zero-Copy | Висока |
| **CBOR (цілочисельні ключі)** | **9 байтів** | **~25% байтів** | Часткова (таблиця ID ключів) | **0 байтів (Zero-Copy)** | **Висока (додавання нових ID)** |
| **Raw C Struct** | 6–8 байтів | 0% метаданих | Жорстка (скомпільований C код) | 0 байтів | Нульова (зміна структури ламає сумісність) |

CBOR із цілочисельними ключами забезпечує оптимальний компроміс: розмір пакета лише на 1–3 байти перевищує сирий двійковий дамп пам'яті, проте дані залишаються повністю самоописними. Якщо нова версія прошивки додасть у словник поле з ключем `4` (наприклад, заряд батареї), старий приймач безпечно пропустить невідомий ключ і продовжить коректну роботу. На відміну від жорстких бінарних форматів на зразок [Protocol Buffers і схемні формати](root:com-protocol/protocol-buffers-i-skhemni-formaty), CBOR не вимагає попередньої кодогенерації та скомпільованих файлів схем `.proto`.

### Робота з пам'яттю на MCU: архітектура Zero-Copy

Головна небезпека використання динамічної пам'яті (`malloc`/`free`) на мікроконтролерах без блоку захисту пам'яті (MPU/MMU) полягає у фрагментації купи: після кількох тисяч циклів виділення та звільнення пам'яті різного розміру вільна пам'ять розбивається на дрібні ізольовані шматки. Наступний виклик `malloc(64)` повертає `NULL`, навіть якщо сумарно в купі вільно кілька кілобайт.

![Модель пам'яті Zero-Copy декодера CBOR](/root/com/com-protocol/cbor-i-messagepack/img/zero-copy-token-stream.svg)
*Модель нуль-копіювального декодера: зрізи даних посилаються безпосередньо на вхідний кільцевий буфер DMA в SRAM.*

Архітектура нуль-копіювального (Zero-Copy) декодера повністю усуває алокації:

1. **Вхідний буфер:** Байти надходять від апаратного периферійного модуля (UART DMA, SPI або SPI-Ethernet) безпосередньо у фіксований статичний масив `uint8_t rx_buf[256]`.
2. **Ітеративний розбір (Pull Parser):** Декодер не будує дерево об'єктів. Функція `cbor_read_next()` зчитує черговий токен із буфера, просуває внутрішній зсув `offset` і повертає структуру зрізу:
:::tabs
```c
typedef struct {
    const uint8_t *ptr;
    size_t len;
} cbor_slice_t;
```
```cpp
struct Slice {
    std::span<const uint8_t> bytes;

    [[nodiscard]] std::string_view as_text() const noexcept {
        return {reinterpret_cast<const char*>(bytes.data()), bytes.size()};
    }
};
```
:::
3. **Представлення тексту та байтів:** Для текстових рядків `tstr` та масивів байтів `bstr` поле `ptr` вказує на відповідну адресу всередині `rx_buf`, а `len` містить розпарсовану довжину. Жоден байт не копіюється.
4. **Ідіоматичний C++:** У C++ для безпечної роботи з такими зрізами використовуються стандартні типи `std::string_view` (для тексту) та `std::span<const uint8_t>` (для бінарних даних).

Повна практична реалізація легковажного кодека для вбудованих систем наведена у вставці [Легковажний потоковий кодек CBOR на C та C++](root:com-protocol/cbor-i-messagepack/proj-cbor-stream-codec.md).

#### Обробка вирівнювання пам'яті (Memory Alignment) на Cortex-M

Під час зчитування чисел безпосередньо з вхідного буфера виникає важливий апаратний нюанс: у бінарному потоці CBOR 16-, 32- та 64-бітні цілі числа можуть розташовуватися за непарними (невирівняними) адресами.

На ядрах ARM Cortex-M0/M0+ (архітектура ARMv6-M) спроба прочитати 32-бітне число через пряме приведення типу `*(uint32_t*)(ptr)` викликає апаратне переривання помилки `UsageFault` / `HardFault`. На ядрах Cortex-M3/M4/M7 невирівняний доступ підтримується апаратно, але коштує додаткових тактів шини.

Тому переносний потоковий декодер CBOR зчитує багатобайтні числа побайтово зі зсувом:

:::tabs
```c
// Безпечне побайтове зчитування Big-Endian uint32
uint32_t val = ((uint32_t)ptr[0] << 24) |
               ((uint32_t)ptr[1] << 16) |
               ((uint32_t)ptr[2] << 8)  |
               ((uint32_t)ptr[3]);
```
```cpp
// Безпечне зчитування Big-Endian uint32 у C++20 / C++23
#include <bit>
#include <cstring>
#include <span>

inline uint32_t read_be32(std::span<const uint8_t, 4> bytes) noexcept {
    uint32_t val;
    std::memcpy(&val, bytes.data(), sizeof(val));
    if constexpr (std::endian::native == std::endian::little) {
        return std::byteswap(val);
    }
    return val;
}
```
:::

Сучасні компілятори GCC та Clang оптимізують цей побайтовий шаблон в одну апаратну інструкцію зміни порядку байтів `REV` (Byte Reverse) на архітектурах, що підтримують невирівняне читання, забезпечуючи максимальну швидкість без ризику апаратних винятків.

### Канонічний CBOR (dCBOR) та криптографічні підписи COSE

У багатьох бездротових протоколах (наприклад, FIDO2/WebAuthn ключі безпеки, стандарти смарт-будинку Matter, захищений протокол CoAP/OSCORE) повідомлення підписуються електронним цифровим підписом (Ed25519 або ECDSA P-256).

Криптографічний підпис обчислюється над криптографічним хешем (наприклад, SHA-256) від послідовності байтів:

```
Signature = Sign(PrivateKey, SHA256(EncodedBytes))
```

Тут виникає фундаментальна проблема: базовий стандарт CBOR дозволяє закодувати одні й ті самі дані багатьма різними способами.

![Детерміноване кодування CBOR для COSE](/root/com/com-protocol/cbor-i-messagepack/img/dcbor-canonical-sorting.svg)
*Вимоги детермінованого CBOR (dCBOR) для формування однозначного криптографічного гешу в COSE.*

Джерела недетермінізму у стандартному CBOR:
1. **Неоптимальна довжина чисел:** Число `10` можна закодувати 1 байтом (`0x0A`), 2 байтами (`0x18 0x0A`), 3 байтами (`0x19 0x00 0x0A`) або 5 байтами (`0x1A 0x00 0x00 0x00 0x0A`). Усі ці варіанти семантично валідні.
2. **Порядок ключів у словниках:** Словник `{"a": 1, "b": 2}` можна серіалізувати у порядку `a, b` або `b, a`.
3. **Формат представлення чисел з плаваючою комою:** Число `1.0` можна записати у форматі Float16 (`0xF9 0x3C 0x00`), Float32 (`0xFA 0x3F 0x80 0x00 0x00`) або Float64. Ба більше, значення `NaN` (Not a Number) мають безліч бітових масок мантиси.
4. **Невизначена довжина:** Масив `[1, 2]` можна записати як фіксований (`0x82 0x01 0x02`) або потоковий (`0x9F 0x01 0x02 0xFF`).

Якщо клієнт згенерує підпис для словника з порядком ключів `a, b`, а сервер під час проміжної обробки перепакує словник у порядок `b, a`, побайтовий хеш SHA-256 зміниться, і перевірка підпису завершиться аварійною помилкою.

#### Правила Deterministic CBOR (RFC 8949 Section 4.2.1 та профіль dCBOR)

Щоб гарантувати, що однакові дані завжди продукують 100% ідентичний масив байтів, введено суворий набір правил:

1. **Найкоротше представлення цілих чисел:** Будь-яке ціле число зобов'язане кодуватися у мінімально можливу кількість байтів. Значення `0..23` — виключно в початковий байт, `24..255` — рівно у 2 байти і так далі.
2. **Лексикографічне сортування ключів словника (Canonical Key Ordering):** Ключі всередині мапи повинні бути відсортовані за їхнім побайтовим серіалізованим представленням:
   - Спершу порівнюється довжина закодованого ключа в байтах: коротший ключ завжди передує довшому.
   - Якщо довжини однакові, виконується побайтове порівняння значень (`memcmp`).
   - Наприклад, цілочисельний ключ `10` (`0x0A`, 1 байт) йде перед ключем `100` (`0x18 0x64`, 2 байти), а ключ `"a"` (`0x61 0x61`, 2 байти) йде перед ключем `"b"` (`0x61 0x62`, 2 байти).
3. **Заборона невизначеної довжини:** Використання маркерів `0x1F` та `0xFF` заборонено; усі рядки, масиви та словники повинні мати явно вказану довжину.
4. **Канонізація чисел з плаваючою комою:** Застосовується або єдиний фіксований формат (наприклад, завжди Float64), або правило редукції до найменшого формату без втрати точності (якщо Float64 вміщується у Float32 або Float16 без спотворення значення, використовується найкоротший). Усі нечислові значення `NaN` нормалізуються до єдиної канонічної бітової маски `0x7E00` (Float16) або `0x7FC00000` (Float32).
5. **Заборона дублювання ключів:** Словники з повторюваними ключами вважаються невалідними й відхиляються парсером.

#### Структура криптографічного конверта COSE_Sign1 (RFC 9052)

У стандарті COSE (CBOR Object Signing and Encryption, RFC 9052) підписане повідомлення `COSE_Sign1` представляється як фіксований CBOR-масив із 4 елементів:

```
COSE_Sign1 = [
    protected:   bstr,        // серіалізовані захищені параметри (bstr-wrapped)
    unprotected: map,         // незахищені службові параметри (наприклад, kid)
    payload:     bstr / null, // корисне навантаження
    signature:   bstr         // сирий бінарний підпис (наприклад, 64 байти Ed25519)
]
```

Особливістю COSE є використання `bstr-wrapped` захищених заголовків: карта параметрів (наприклад, алгоритм `alg: -7` для ECDSA ES256) спочатку серіалізується в бінарний масив за правилами dCBOR, і лише потім вкладається як `bstr`. Це гарантує, що жоден проміжний маршрутизатор не зможе перепакувати чи змінити порядок байтів заголовка без порушення криптографічного підпису.

Завдяки dCBOR стандарт COSE став компактною, надійною та повністю апаратно-оптимізованою заміною стеку JWT/JOSE для всього сучасного Інтернету речей.

### Практичний інженерний вибір: CBOR, MessagePack, JSON чи Protobuf?

Вибір формату серіалізації для вбудованої системи або мережевого сервісу визначається компромісом між трьома параметрами: обмеженням пропускної здатності каналу зв'язку, наявністю та стабільністю схеми даних і доступними обчислювальними ресурсами мікроконтролера.

```
Вимога до формату
├── Потрібна читабельність людиною під час відлагодження у браузері/терміналі?
│   └── ТАК ──► Текстовий JSON (RFC 8259)
└── НІ (критичний розмір пакета або пам'ять MCU)
    ├── Схема строго зафіксована, є можливість компілювати .proto файли?
    │   └── ТАК ──► Protocol Buffers / FlatBuffers (найменший розмір, 0 метаданих)
    └── Дані динамічні, схема еволюціонує, потрібна самоописність
        ├── Потрібні криптографічні підписи (COSE), IEEE Float16 або IETF-стандарти (CoAP)?
        │   └── ТАК ──► CBOR / dCBOR (RFC 8949)
        └── Проста заміна JSON у високонавантаженому бекенді (Redis, RPC)?
            └── ТАК ──► MessagePack
```

CBOR є безальтернативним вибором, коли у вузькому каналі зв'язку потрібна гнучка самоописна структура з підтримкою сирих бінарних масивів, чисел із плаваючою комою низької розрядності та детермінованих криптографічних підписів.
