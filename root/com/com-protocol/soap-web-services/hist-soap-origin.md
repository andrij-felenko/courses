# 📜 Від обходу фаєрволів до стандарту: як народився SOAP

Наприкінці 1990-х років корпоративні комп'ютерні мережі зіткнулися з глухим кутом розподілених обчислень. Усередині локальних серверних кімнат панували бінарні протоколи виклику віддалених процедур: [DCOM](topic:com-protocol/corba-object-broker) від корпорації Microsoft та [CORBA](topic:com-protocol/corba-object-broker) від консорціуму Object Management Group (OMG). Обидві технології спиралися на одну й ту саму архітектурну модель: клієнтський об'єкт-замінник (стаб) пакував виклик методу у двійковий формат, відкривав пряме TCP-з'єднання до сервера на динамічно виділеному порті й очікував на двійкову відповідь.

Поки обчислення відбувалися всередині одного дата-центру з довіреною мережею, схема працювала надійно. Проте щойно підприємства спробували об'єднати інформаційні системи різних філій, банківських партнерів чи постачальників через глобальну мережу Інтернет, інфраструктура розсипалася. Корпоративні мережеві екрани (брандмауери) та вузли перетворення мережевих адрес (NAT) блокували будь-який вхідний і вихідний трафік на довільних портах. Системні адміністратори з міркувань безпеки тримали відкритими лише два стандартні мережеві порти: 80 для незахищеного вебтрафіку HTTP та 443 для захищеного HTTPS.

У результаті мільйонні інвестиції в об'єктні брокери CORBA та інфраструктуру DCOM виявилися заблокованими на межі внутрішнього периметра компаній. Щоб викликати метод віддаленого сервера іншої організації, доводилося або відкривати дірки у фаєрволах, наражаючи мережу на небезпеку, або створювати складні тунельні рішення.

### Народження ідеї: XML-RPC і союз UserLand із Microsoft

Навесні 1998 року розробник Дейв Вайнер (Dave Winer), засновник компанії UserLand Software і творець системи публікацій Frontier, шукав спосіб зв'язати свій редактор із віддаленими серверами через стандартний веб. Вайнер вирішив піти шляхом найменшого опору: якщо мережеві екрани безперешкодно пропускають HTTP-запити до вебсерверів, виклик віддаленої процедури слід передавати всередині звичайного HTTP-запиту методом POST. Замість двійкового маршалінгу параметри функції записувалися у вигляді текстового документа нещодавно затвердженого стандарту XML (Extensible Markup Language).

У березні 1998 року Вайнер зустрівся з інженерами Microsoft Бобом Аткінсоном (Bob Atkinson) і Мохсеном Аль-Ґосейном (Mohsen Al-Ghosein). Команда Microsoft якраз шукала спосіб адаптувати DCOM до вебсередовища, оскільки складність двійкового протоколу Object RPC (ORPC) гальмувала поширення технологій компанії за межі операційної системи Windows. Об'єднавши зусилля, вони за кілька місяців створили специфікацію протоколу **XML-RPC**.

Структура XML-RPC була гранично прямолінійною: клієнт відправляв HTTP POST на адресу сервера, де в тілі лежав XML-документ із тегом `<methodCall>`, ім'ям методу `<methodName>` і типізованими параметрами `<params>`. Сервер відповідав документом із тегом `<methodResponse>`. Протокол не знав нічого про класи, об'єктні посилання чи розподілений збирач сміття — це був чистий процедурний виклик, упакований у текст. Завдяки стандартному порту 80 пакети XML-RPC проходили крізь будь-які корпоративні фаєрволи без додаткових налаштувань.

### Від процедур до об'єктів: розробка SOAP 0.9 та 1.1

Попри успіх XML-RPC, інженери Microsoft вважали протокол занадто простим і обмеженим для великих корпоративних завдань. У ньому були відсутні розширювані метадані (заголовки автентифікації, маршрутизації, транзакцій), не було механізму суворої типізації через схеми, а сама модель залишалася жорстко прив'язаною до виклику однієї процедури.

До команди розробників приєднався Дон Бокс (Don Box), відомий експерт з архітектури COM і автор класичних підручників з системного програмування. Бокс запропонував абстрагуватися від конкретної мови та платформи й побудувати протокол обміну повідомленнями, який складався б із двох логічних частин: зовнішнього «конверта» (Envelope) з метаданими та внутрішнього корисного навантаження (Body).

Новий протокол отримав назву **SOAP** — акронім від *Simple Object Access Protocol* («простий протокол доступу до об'єктів»). У 1999 році автори опублікували чернетку SOAP 0.9. Однак всередині самої Microsoft точилася запекла боротьба: традиціоналісти з підрозділу Windows вимагали розвивати DCOM і вважали перехід на текстовий XML зрадою продуктивності та двійкових стандартів компанії. Дон Бокс, Боб Аткінсон і віцепрезидент Microsoft Боб Маглія (Bob Muglia) наполягли на відкритості стандарту й залучили до співпраці зовнішніх партнерів.

У травні 2000 року Microsoft, IBM, DevelopMentor, UserLand Software та Lotus спільно подали специфікацію **SOAP 1.1** на розгляд міжнародного консорціуму World Wide Web Consortium (W3C). Публікація SOAP 1.1 стала точкою відліку ери так званих «вебсервісів» (Web Services): союз Microsoft та IBM змусив усю індустрію програмного забезпечення визнати XML і HTTP головними рейками для міжсистемної інтеграції.

### Стандартизація W3C та SOAP 1.2

Під егідою робочої групи XML Protocol Working Group у консорціумі W3C почалася ґрунтовна переробка специфікації. У червні 2003 року W3C затвердив **SOAP 1.2** як офіційну рекомендацію.

У версії 1.2 консорціум зробив показовий крок: офіційно відмовився від розшифрування акроніма SOAP. Назва залишилася власним ім'ям, оскільки протокол більше не вважався ані простим (специфікація розрослася на сотні сторінок), ані суто об'єктним (він передавав довільні XML-документи, а не керував життєвим циклом віддалених об'єктів).

SOAP 1.2 уніфікував роботу з просторами імен (`http://www.w3.org/2003/05/soap-envelope`), запровадив власний MIME-тип `application/soap+xml` замість загального `text/xml`, переробив структуру помилок (замінивши теги `faultcode` і `faultstring` на ієрархічні `Code` і `Reason`) та формалізував зв'язування з різними транспортними протоколами (HTTP, SMTP, TCP).

### Вибух стандартів WS-* і криза сумісності

З появою базового протоколу SOAP та мови опису контрактів WSDL корпоративні гіганти — Microsoft, IBM, Sun Microsystems, Oracle, BEA Systems, SAP — почали нарощувати навколо нього інфраструктурні стандарти. Цей стек отримав назву **WS-*** (WS-Star) і розроблявся одночасно в консорціумах W3C та OASIS:

- **WS-Security (WSS):** цифровий підпис і шифрування окремих частин XML-конверта;
- **WS-Addressing:** незалежна від транспорту адресація кінцевих точок і зворотних маршрутів;
- **WS-ReliableMessaging:** гарантована доставка повідомлень через ненадійні мережеві канали;
- **WS-AtomicTransaction / WS-Coordination:** розподілені двофазні транзакції між гетерогенними базами даних;
- **WS-Policy / WS-Trust / WS-Federation:** правила безпеки та федеративна ідентифікація.

Кількість специфікацій перевищила пів сотні. Кожен вендор реалізовував ці стандарти у своїх стеках: Microsoft у .NET (ASMX, а згодом Windows Communication Foundation — WCF), IBM у WebSphere, Sun Microsystems у Java JAX-RPC і Metro, Apache у проєкті Axis.

Однак на практиці виникла катастрофічна криза сумісності. Через нечіткість формулювань у початкових стандартах SOAP 1.1 і WSDL 1.1 різні системи по-різному кодували складні типи даних (масиви, поліморфні об'єкти, порожні значення `null`). Клієнт на C# під .NET не міг викликати метод сервісу, написаного на Java під Apache Axis, якщо той використовував кодування за секцією 5 (RPC/Encoded). Розробники знову опинилися в ситуації, коли формально відкритий протокол вимагав ручного підганяння коду під кожного конкретного постачальника сервісу.

### Порятунок інтероперабельності: організація WS-I

Щоб зупинити розпад екосистеми на ізольовані табори, у лютому 2002 року лідери індустрії створили організацію **WS-I** (Web Services Interoperability Organization). Метою WS-I було не написання нових специфікацій, а відбір наявних стандартів і створення жорстких правил їх узгодженого використання — так званих «профілів сумісності» (Profiles).

У 2004 році WS-I опублікувала фундаментальний документ — **WS-I Basic Profile 1.0** (а згодом версію **1.1**). Профіль ввів суворі обмеження:
1. Повністю заборонив використання кодування RPC/Encoded (SOAP Section 5 Encoding), визнавши єдиним допустимим підходом використання явних XSD-схем (Document/Literal або Document/Literal Wrapped).
2. Зафіксував обов'язкові правила для HTTP-заголовків `SOAPAction` та кодів повернення.
3. Уніфікував синтаксис опису типів у WSDL.

Поява WS-I Basic Profile нарешті дозволила досягти справжньої інтероперабельності: починаючи з середини 2000-х років корпоративні клієнти на будь-якій мові програмування могли згенерувати типізований стаб за WSDL-файлом і без помилок спілкуватися з віддаленим сервером іншого виробника.

### Маятник хитається: поява REST і спадщина SOAP

На хвилі успіху вебсервісів архітектура Enterprise Service Bus (ESB) і концепція сервісно-орієнтованої архітектури (SOA) стали домінантним стандартом у великому бізнесі. Однак надмірна складність стека WS-*, багатослівність XML-документів і високі накладні витрати на обробку DOM-дерев у пам'яті викликали спротив серед веброзробників нового покоління.

У 2000 році Рой Філдінг опублікував дисертацію з описом архітектурного стилю [REST](topic:com-protocol/rest-api), який запропонував використовувати природні дієслова та статуси HTTP замість тунелювання RPC через POST-запити. З появою легкого формату JSON і бумом веброзробки у другій половині 2000-х років публічні вебсервіси масово мігрували на REST-архітектуру, а високопродуктивні внутрішні сервіси згодом обрали двійковий [gRPC](topic:com-protocol/rpc).

Попри втрату позицій у масовій веброзробці, SOAP залишився непорушним фундаментом там, де потрібні гарантована безпека на рівні повідомлення (WS-Security), суворі формальні контракти та розподілені транзакції: у світових банківських мережах (SWIFT), державних реєстрах, телеком-білінгу та авіаційному бронюванні.
