# 📜 Від локальної ілюзії до нульового копіювання: як еволюціонував RPC

У 1984 році дослідники дослідницького центру Xerox PARC Ендрю Біррелл (англ. *Andrew Birrell*) та Брюс Нельсон (англ. *Bruce Jay Nelson*) опублікували фундаментальну працю «Implementing Remote Procedure Calls» в журналі ACM Transactions on Computer Systems. Їхня мета виглядала оманливо простою: зробити взаємодію між програмами на різних комп'ютерах настільки ж природною й прозорою для програміста, як звичайний виклик функції всередині одного процесу. Саме ця праця сформулювала канонічну архітектуру RPC, що складається з клієнтського стаба, серверного скелетона, механізму маршалінгу параметрів та диспетчера викликів.

Ідея негайно захопила індустрію, проте перші ж практичні реалізації зіткнулися з тим, що локальна функція та мережевий виклик мають фундаментально різну природу відмов і продуктивності.

### Перше покоління: Sun RPC, XDR та ера Unix

Наприкінці 1980-х років компанія Sun Microsystems розробляла мережеву файлову систему NFS (англ. *Network File System*). Для забезпечення її роботи інженери створили систему Open Network Computing RPC (ONC RPC, пізніше стандартизовану як RFC 1057) разом із мовою опису даних XDR (англ. *External Data Representation*, RFC 1014).

Sun RPC розв'язав проблему несумісності архітектур: XDR приводив усі цілі числа до фіксованого мережевого порядку байтів (big-endian) та вирівнював кожне поле за 4-байтовою межею. Компілятор `rpcgen` читав файл визначення інтерфейсу `.x` і автоматично генерував код мовою C для пакування структур і відправлення датаграм через UDP або потоків через TCP. Це був колосальний крок уперед: розробникам більше не доводилося вручну вираховувати зміщення байтів у буферах сокетів. Проте Sun RPC залишався процедурним, прив'язаним до мови C і вимагав окремої служби `portmapper` (порт 111) для динамічної трансляції номерів програм у порти TCP/UDP.

### Епоха об'єктного максималізму: DCE, CORBA та DCOM

На початку 1990-х років парадигма об'єктно-орієнтованого програмування досягла піку популярності, і консорціуми спробували перенести в мережу не просто процедури, а живі екземпляри об'єктів.

Консорціум Open Software Foundation створив стандарт DCE RPC (англ. *Distributed Computing Environment*), де вперше з'явилися глобально унікальні ідентифікатори UUID та розширений протокол узгодження контексту безпеки. На базі DCE корпорація Microsoft побудувала власний стек DCOM (англ. *Distributed Component Object Model*), тісно інтегрований у ядро Windows NT. Водночас консорціум Object Management Group (OMG) представив CORBA (англ. *Common Object Request Broker Architecture*) з мовою IDL і брокерами об'єктних запитів ORB.

CORBA та DCOM обіцяли повну прозорість: об'єкт у пам'яті C++ на платформі Solaris міг викликати метод об'єкта в Smalltalk або Java на Windows, передаючи поліморфні інтерфейси як параметри. Однак ця складність стала для них фатальною. Специфікація CORBA налічувала понад тисячу сторінок, брокери ORB від різних постачальників не взаємодіяли між собою через несумісність двійкових протоколів IIOP, а передача стану об'єктів і віддаленого збирання сміття (Distributed Garbage Collection) створювала непередбачувані затримки та витоки ресурсів. Будь-який міжмережевий екран блокував динамічні порти CORBA та DCOM, що унеможливлювало їхнє використання за межами локальних мереж підприємств.

### Текстовий відкат: XML-RPC, SOAP та REST

У відповідь на складність двійкових об'єктних систем на зламі тисячоліть виник рух за максимальну простоту й сумісність із веб-інфраструктурою. Дейв Вайнер (англ. *Dave Winer*) разом із Microsoft розробив XML-RPC у 1998 році, який згодом еволюціонував у стандарт W3C SOAP (англ. *Simple Object Access Protocol*).

Ідея полягала в передачі викликів у вигляді структурованого XML-тексту поверх стандартного порту 80 протоколу HTTP. Це вирішило проблему проходження крізь брандмауери й дозволило зв'язувати будь-які мови програмування без специфічних двійкових компіляторів. Але ціна виявилася катастрофічною: розмір повідомлень через надмірні XML-теги збільшився в 10–50 разів, а парсинг тексту на сервері споживав до 80% процесорного часу під навантаженням. Спроба повернути строгу типізацію через схеми XSD та WSDL перетворила SOAP на таку ж громіздку систему, якою раніше була CORBA.

Як реакція на надмірність SOAP з'явився підхід REST (англ. *Representational State Transfer*, описаний Роєм Філдінгом у 2000 році), що спирався на стандартні методи HTTP (GET, POST, PUT, DELETE) та легковагіший текстовий формат JSON. REST на роки став домінуючим стандартом для публічних веб-інтерфейсів, проте для внутрішньої взаємодії десятків тисяч мікросервісів у дата-центрах накладні витрати на парсинг рядків JSON та нетипізовані поля швидко стали критичним бар'єром масштабування.

### Внутрішні протоколи гігантів: Stubby та народження Protobuf

Всередині компанії Google ще з 2001 року зростала власна інфраструктура розподілених обчислень (MapReduce, Bigtable, GFS). Використання текстових форматів чи важких об'єктних брокерів на масштабах сотень тисяч серверів виключалося. Інженери Google розробили внутрішню систему RPC під назвою **Stubby** та двійковий формат серіалізації **Protocol Buffers** (Protobuf).

Ключовими принципами Protobuf стали:
- Компактне кодування за схемою TLV (Tag-Length-Value) без передачі імен полів;
- Стиснення числових значень через байти змінної довжини (Varint);
- Строга сумісність схеми вперед і назад без втрати невідомих полів;
- Генерація високоефективного коду на мовах C++, Java та Python.

У 2008 році Google відкрила вихідний код Protocol Buffers (версія Proto2, а згодом Proto3). Проте сам RPC-рушій Stubby залишався тісно прив'язаним до внутрішньої інфраструктури Google і не міг бути оприлюднений як є.

### Новий стандарт індустрії: gRPC та HTTP/2

У 2015 році Google представила **gRPC** — переосмислення Stubby, побудоване повністю на відкритих стандартах. Замість власного транспортного рівня gRPC використав протокол **HTTP/2**, стандартизований IETF того ж року (RFC 7540).

HTTP/2 надав RPC саме те, чого не вистачало попередникам:
- Двійкове кадрування замість текстових заголовків;
- Мультиплексування сотень незалежних викликів в одному TCP-з'єднанні без блокування черги на прикладному рівні;
- Двостороннє потокове передавання (Bidirectional Streaming);
- Стиснення метаданих через таблиці HPACK;
- Стандартні трейлери (Trailers) для повернення статусів помилок після передачі тіла повідомлення.

gRPC став де-факто стандартом комунікації в екосистемі хмарних технологій Cloud Native (Kubernetes, Envoy, Prometheus), об'єднавши сувору типізацію контрактів IDL з ефективністю двійкового транспорту.

### Рух за нульове копіювання: Cap'n Proto та FlatBuffers

Поки gRPC і Protobuf оптимізували передачу по мережах 1 GbE та 10 GbE, пропускна здатність мережевих адаптерів у дата-центрах зросла до 40, 100 та 400 GbE. На таких швидкостях час процесора вже не лімітувався мережею: вузьким місцем стала сама десеріалізація — циклічний розбір байтів Varint, виділення пам'яті в купі під кожен рядок чи вкладену структуру та копіювання байтів із буфера сокета в об'єкти мови.

У 2013 році Кентон Варда (англ. *Kenton Varda*), провідний розробник версії Protocol Buffers v2 у Google, залишив компанію і представив проєкт **Cap'n Proto**. Одночасно інженери Google створили подібний проєкт **FlatBuffers** для ігор та мобільних пристроїв.

Фундаментальна інновація Cap'n Proto полягала в концепції **нульового копіювання** (Zero-Copy Serialization): формат повідомлення в двійковому буфері збігається з його розкладкою в оперативній пам'яті. Замість циклу розпакування програма просто накладає покажчик структури на отриманий блок байтів і звертається до полів за прямими зміщеннями за час `O(1)`. Крім того, Cap'n Proto реалізував конвеєризацію обіцянок (англ. *Promise Pipelining*, концепція з мови E та протоколу CapTP), що дозволяє відправляти наступний RPC-виклик, використовуючи майбутній результат попереднього виклику ще до того, як той повернувся клієнту, скорочуючи кількість мережевих затримок RTT.

Еволюція RPC пройшла повне коло: від наївного сподівання зробити мережевий виклик невідрізненним від локального — до глибокого усвідомлення апаратних меж процесора й пам'яті, де кожен такт десеріалізації та кожне виділення пам'яті в купі підпорядковані законам двійкової ефективності.
