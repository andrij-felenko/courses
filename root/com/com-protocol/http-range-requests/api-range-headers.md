# 📋 Специфікація інтерфейсу HTTP Range: заголовки, граматика ABNF та матриця відповідей

Механізм часткових запитів HTTP стандартизовано в специфікаціях IETF RFC 9110 (розділ 14 «Range Requests») та RFC 7233. Документ визначає відкритий протокольний контракт взаємодії між клієнтами (веб-браузерами, мультимедійними плеєрами, менеджерами завантажень), проміжними проксі-серверами й мережами доставки вмісту (CDN), а також серверами походження (origin servers) для адресації та вибіркової передачі довільних байтових діапазонів.

Нижче наведено формальну граматику, вичерпну специфікацію заголовків, покроковий алгоритм валідації та нормалізації, матрицю статус-кодів, структуру MIME-контейнерів, розрахунок довжини багаточастинних відповідей, конфігурацію проксі-серверів, підтримку клієнтськими бібліотеками, модель загроз безпеки, поведінку в Service Workers та діагностику через Wireshark, tcpdump і cURL.

## Формальна граматика ABNF (RFC 9110 §14)

Синтаксис запитів та відповідей діапазонів описується розширеною формою Бекуса — Наура (ABNF, RFC 5234):

```abnf
;; Запит клієнта
Range                     = byte-ranges-specifier / other-ranges-specifier
byte-ranges-specifier     = bytes-unit "=" byte-range-set
bytes-unit                = "bytes"
byte-range-set            = 1#( byte-range-spec / suffix-byte-range-spec )
byte-range-spec           = first-byte-pos "-" [ last-byte-pos ]
first-byte-pos            = 1*DIGIT
last-byte-pos             = 1*DIGIT
suffix-byte-range-spec    = "-" suffix-length
suffix-length             = 1*DIGIT
other-ranges-specifier    = other-range-unit "=" other-range-set
other-range-unit          = token
other-range-set           = 1*VCHAR

;; Умовний заголовок If-Range
If-Range                  = entity-tag / HTTP-date

;; Оголошення сервера
Accept-Ranges             = 1#range-unit
range-unit                = bytes-unit / other-range-unit
                          / "none"

;; Заголовок відповіді з частковим вмістом
Content-Range             = byte-content-range / other-content-range
byte-content-range        = bytes-unit SP ( byte-range-resp / unsatisfied-range )
byte-range-resp           = byte-range "/" ( complete-length / "*" )
byte-range                = first-byte-pos "-" last-byte-pos
unsatisfied-range         = "*/" complete-length
complete-length           = 1*DIGIT
other-content-range       = other-range-unit SP other-range-resp
other-range-resp          = *CHAR
```

## Специфікація заголовків запиту (Request Headers)

### 1. `Range`

Вказує серверу один або кілька піддіапазонів ресурсу, які клієнт бажає отримати замість повного тіла сутності.

* **Семантичний контекст:** Використовується виключно в безпечних та ідемпотентних методах отримання представлення (`GET`, `HEAD`). Використання в методах модифікації стану (`POST`, `PUT`, `PATCH`, `DELETE`) не має стандартизованої семантики і повинно ігноруватися сервером відповідно до RFC 9110 §14.2.
* **Синтаксичні форми та правила обчислення меж:**
  * **Замкнений інтервал `bytes=first_byte_pos-last_byte_pos`:**
    * Індексація починається з `0`.
    * Обидва значення є включними: запит `bytes=0-499` адресує рівно перші `500` байтів файлу (зміщення від `0` до `499`).
    * Кількість байтів у фрагменті обчислюється за формулою: `Кількість = last_byte_pos - first_byte_pos + 1`.
    * Умова валідності: `first_byte_pos <= last_byte_pos` та `first_byte_pos < complete_length`. Якщо `last_byte_pos >= complete_length`, сервер зобов'язаний автоматично скоригувати `last_byte_pos` до значення `complete_length - 1`.
  * **Напіввідкритий інтервал `bytes=first_byte_pos-`:**
    * Адресує всі байти від `first_byte_pos` до кінця файлу (`complete_length - 1`) включно.
    * Приклад: для ресурсу довжиною 10 000 байтів заголовок `Range: bytes=9500-` повертає байти з `9500` по `9999` (разом `500` байтів).
    * Умова валідності: `first_byte_pos < complete_length`.
  * **Суфіксний інтервал `bytes=-suffix_length`:**
    * Адресує останні `suffix_length` байтів сутності.
    * Початковий байт обчислюється як `first_byte_pos = max(0, complete_length - suffix_length)`, а кінцевий — `last_byte_pos = complete_length - 1`.
    * Приклад: для файлу розміром 10 000 байтів заголовок `Range: bytes=-500` повертає байти з `9500` по `9999`. Якщо `suffix_length >= complete_length`, повертається весь файл цілком від байта `0`.
    * Умова валідності: `suffix_length > 0`.
  * **Множинні діапазони (Multipart Range) `bytes=range1, range2, ...`:**
    * Перелік кількох зрізів через кому: `Range: bytes=0-99, 1000-1099, -200`.
    * Сервер пакує результат у спеціальний MIME-контейнер `multipart/byteranges`.

### 2. `If-Range`

Перетворює частковий запит на умовну транзакцію. Запобігає пошкодженню даних, коли клієнт намагається продовжити завантаження файлу, але ресурс на сервері був змінений між запитами.

* **Значення:**
  * Сильний ETag ресурсу у подвійних лапках: `If-Range: "686897696a7c876b7e"`.
  * HTTP-дата з моменту попередньої відповіді: `If-Range: Wed, 21 Oct 2025 07:28:00 GMT`.
* **Правило обов'язкового сильного валідатора (Strong Validator Requirement):**
  * Специфікація RFC 9110 категорично **забороняє** використання слабких валідаторів (Weak ETags, що починаються з префікса `W/`) у заголовку `If-Range`.
  * Причина: слабкий ETag гарантує лише семантичну еквівалентність сутності (наприклад, однаковий візуальний зміст HTML або однакові дані після переформатування), але не гарантує побайтної ідентичності бінарних зміщень. Склеювання частин на основі слабкого валідатора призводить до пошкодження двійкових файлів.
  * Якщо клієнт передає слабкий ETag у `If-Range`, сервер розцінює перевірку як негативну і повертає повний новий ресурс зі статусом `200 OK`.
* **Логіка обробки:**
  * Валідатор збігається з поточним станом сутності → сервер повертає `206 Partial Content` із запитаним діапазоном.
  * Валідатор не збігається (ресурс оновився) → сервер ігнорує заголовок `Range` і негайно повертає `200 OK` з усім тілом нового представлення.

## Специфікація заголовків відповіді (Response Headers)

### 1. `Accept-Ranges`

Оголошує підтримку сервером часткових запитів для цільового ресурсу.

* **Значення:**
  * `Accept-Ranges: bytes` — сервер здатний приймати та обробляти запити з позиціюванням у байтах.
  * `Accept-Ranges: none` — сервер явно інформує клієнта, що часткові запити для цього ресурсу не підтримуються (наприклад, при небуферизованій потоковій генерації аудіо в реальному часі).
* **Контекст:** Рекомендується повертати в усіх відповідях на запити `HEAD` та `GET`, щоби клієнти заздалегідь знали про можливість паралельного завантаження або відновлення сесій.

### 2. `Content-Range`

Повідомляє клієнту точні межі переданого блоку байтів та загальний розмір сутності на момент формування відповіді.

* **Синтаксичні варіанти:**
  * **Успішна відповідь 206 (відомий повний розмір):**
    `Content-Range: bytes first_byte_pos-last_byte_pos/complete_length`
    Приклад: `Content-Range: bytes 1048576-2097151/52428800`.
  * **Успішна відповідь 206 (невідомий повний розмір):**
    `Content-Range: bytes first_byte_pos-last_byte_pos/*`
    Приклад: `Content-Range: bytes 0-65535/*` (використовується, коли сервер передає фрагмент динамічного файлу, повна довжина якого ще не обчислена).
  * **Відповідь про помилку 416 (Unsatisfied Range):**
    `Content-Range: bytes */complete_length`
    Приклад: `Content-Range: bytes */10485760`. Повідомляє клієнту дійсний розмір ресурсу для корекції наступного запиту.
* **Взаємозв'язок з `Content-Length`:**
  * Для одиночного діапазону заголовок `Content-Length` **повинен** точно дорівнювати кількості переданих байтів тіла відповіді: `Content-Length: (last_byte_pos - first_byte_pos + 1)`.
  * Заборонено вказувати в `Content-Length` повний розмір вихідного файлу при статусі 206.

### 3. `Content-Type: multipart/byteranges`

Формат тіла відповіді, коли клієнт запитує кілька неперервних діапазонів в одному HTTP-запиті.

* **Параметр межі (`boundary`):** Обов'язковий у заголовку: `Content-Type: multipart/byteranges; boundary=4bf9a38f32c`.
* **Правила формування рядка межі (MIME Boundary Rules, RFC 2046):**
  * Довжина рядка межі становить від 1 до 70 символів.
  * Дозволені символи: цифри `0-9`, латинські літери `a-z`, `A-Z` та спеціальні знаки `()'+_,-./:=?`. Пробіли в кінці заборонені.
  * Сервер зобов'язаний генерувати рядок із достатньою ентропією (наприклад, 16 випадкових шістнадцяткових байтів), щоби виключити випадковий збіг роздільника з корисними двійковими даними всередині файлу.
* **Структура кожної MIME-частини:**
  1. Рядок роздільника: `--4bf9a38f32c\r\n`
  2. Заголовок типу контенту частини: `Content-Type: application/octet-stream\r\n`
  3. Заголовок діапазону частини: `Content-Range: bytes 0-99/1000\r\n`
  4. Порожній рядок-роздільник: `\r\n`
  5. Сирі байти діапазону (рівно `100` байтів).
  6. Символи переведення рядка `\r\n`.
* **Завершення відповіді:** Фінальний рядок роздільника з двома дефісами наприкінці: `--4bf9a38f32c--\r\n`.

```http
HTTP/1.1 206 Partial Content
Date: Wed, 20 Aug 2026 10:00:00 GMT
Server: custom-media-server/1.0
Content-Type: multipart/byteranges; boundary=sep_98a76f2
Content-Length: 428

--sep_98a76f2
Content-Type: video/mp4
Content-Range: bytes 0-99/50000000

[... 100 байтів від 0 до 99 ...]
--sep_98a76f2
Content-Type: video/mp4
Content-Range: bytes 500000-500099/50000000

[... 100 байтів від 500000 до 500099 ...]
--sep_98a76f2--
```

## Точний розрахунок Content-Length для multipart/byteranges

При формуванні відповіді з кількома частинами сервер зобов'язаний заздалегідь обчислити точний заголовок `Content-Length`. Формула сумарної довжини тіла:

```
Content-Length = ∑ (ДовжинаРоздільника + ДовжинаЗаголовківЧастини + ДовжинаТілаЧастини + 2) + ДовжинаФінальногоРоздільника
```

Де для кожної частини `i`:
* `ДовжинаРоздільника` = `2 + len(boundary) + 2` (символи `--` + рядок межі + `\r\n`).
* `ДовжинаЗаголовківЧастини` = довжина рядків `Content-Type: ...\r\nContent-Range: bytes S-E/N\r\n\r\n`.
* `ДовжинаТілаЧастини` = `E_i - S_i + 1`.
* `+ 2` = завершальне переведення рядка `\r\n` після корисних байтів.
* `ДовжинаФінальногоРоздільника` = `2 + len(boundary) + 2 + 2` (символи `--` + рядок межі + `--\r\n`).

### Приклад покрокового розрахунку:

Нехай клієнт запитує 2 діапазони для текстового файлу `text/plain` довжиною 10 000 байтів: `Range: bytes=0-9, 50-59` (по 10 байтів кожен), з роздільником `boundary=abc123`:

1. Роздільник частини: `--abc123\r\n` (10 байтів).
2. Заголовки частини 1:
   `Content-Type: text/plain\r\n` (26 байтів)
   `Content-Range: bytes 0-9/10000\r\n` (31 байт)
   `\r\n` (2 байти)
   Разом заголовки: `59` байтів.
3. Тіло частини 1: 10 байтів даних + `\r\n` (2 байти) = `12` байтів.
4. Сума частини 1: `10 + 59 + 12 = 81` байт.
5. Заголовки частини 2:
   `Content-Type: text/plain\r\n` (26 байтів)
   `Content-Range: bytes 50-59/10000\r\n` (33 байти)
   `\r\n` (2 байти)
   Разом заголовки: `61` байт.
6. Тіло частини 2: 10 байтів даних + `\r\n` (2 байти) = `12` байтів.
7. Сума частини 2: `10 + 61 + 12 = 83` байти.
8. Фінальний роздільник: `--abc123--\r\n` (12 байтів).
9. **Загальний Content-Length** = `81 + 83 + 12 = 176` байтів.

## Алгоритм валідації та нормалізації діапазонів на сервері

Для захисту від атак вичерпання пам'яті (CVE-2011-3192) та некоректних клієнтів сервер зобов'язаний виконувати детерміновану обробку вхідного заголовка `Range`:

```
Вхідні дані:
  RangeHeader: рядок заголовка Range
  CompleteLength: повний розмір ресурсу в байтах
  IfRangeHeader: значення заголовка If-Range (якщо є)

Крок 1: Перевірка умовного If-Range
  Якщо IfRangeHeader присутній:
    Якщо IfRangeHeader містить сильний ETag і він збігається з поточним ETag:
      Перейти до Кроку 2
    Якщо IfRangeHeader містить HTTP-дату і вона >= дати Last-Modified ресурсу:
      Перейти до Кроку 2
    Інакше (валідатор не збігся або є слабким ETag):
      Повернути статус 200 OK з повним тілом ресурсу

Крок 2: Синтаксичний розбір одиниці
  Якщо RangeHeader не починається з "bytes=":
    Повернути статус 200 OK (невідома одиниця виміру)

Крок 3: Розбір та валідація окремих специфікаторів
  Для кожного сегмента, розділеного комою:
    Якщо форма "start-end":
      Якщо start > end або start >= CompleteLength:
        Позначити діапазон як незадоволений
      Інакше:
        last = min(end, CompleteLength - 1)
        Додати [start, last] до списку валідних
    Якщо форма "start-":
      Якщо start >= CompleteLength:
        Позначити діапазон як незадоволений
      Інакше:
        Додати [start, CompleteLength - 1] до списку валідних
    Якщо форма "-suffix":
      Якщо suffix <= 0:
        Позначити як некоректний
      Інакше:
        start = max(0, CompleteLength - suffix)
        Додати [start, CompleteLength - 1] до списку валідних

Крок 4: Оцінка результату
  Якщо список валідних діапазонів порожній:
    Повернути статус 416 Range Not Satisfiable з заголовком Content-Range: bytes */CompleteLength
  
Крок 5: Коалесценція (злиття та дедуплікація)
  1. Посортувати діапазони за зростанням початкового зміщення start.
  2. Об'єднати перекриті та суміжні діапазони:
     Якщо поточний start <= попередній end + 1:
       попередній end = max(попередній end, поточний end)
  
Крок 6: Перевірка накладних витрат
  Якщо кількість частин > ЛімітСервера (наприклад, 1 або 5) або
     розмір MIME-заголовків перевищує економію трафіку:
    Повернути статус 200 OK з повним тілом ресурсу
  
Крок 7: Формування відповіді
  Якщо залишився 1 діапазон:
    Повернути 206 Partial Content з Content-Range: bytes S-E/CompleteLength
  Якщо залишилося > 1 діапазонів:
    Повернути 206 Partial Content з Content-Type: multipart/byteranges
```

## Матриця статус-кодів та поведінки системи

| Сценарій запиту та стан ресурсу | Очікуваний HTTP-статус | Заголовки у відповіді | Тіло відповіді |
| :--- | :--- | :--- | :--- |
| Валідний одиночний Range, ресурс не змінювався | `206 Partial Content` | `Content-Range: bytes S-E/N`<br>`Content-Length: (E-S+1)`<br>`Accept-Ranges: bytes` | Запитаний зріз `[S..E]` |
| Валідний множинний Range, ресурс не змінювався | `206 Partial Content` | `Content-Type: multipart/byteranges; boundary=...`<br>`Content-Length: L`<br>`Accept-Ranges: bytes` | Послідовність MIME-частин |
| `If-Range` містить сильний ETag, що збігається | `206 Partial Content` | `Content-Range: bytes S-E/N`<br>`ETag: "strong-hash"` | Запитаний зріз `[S..E]` |
| `If-Range` валідатор застарів (ресурс змінено) | `200 OK` | `ETag: "new-hash"`<br>`Content-Length: N`<br>`Accept-Ranges: bytes` | Повне тіло нового ресурсу |
| `If-Range` містить слабкий ETag (`W/"..."`) | `200 OK` | `ETag: W/"hash"`<br>`Content-Length: N` | Повне тіло ресурсу |
| Помилка меж: `first_byte_pos >= complete_length` | `416 Range Not Satisfiable` | `Content-Range: bytes */N`<br>`Content-Length: 0` | Порожнє тіло або JSON помилки |
| Ресурс має нульову довжину (`0` байтів) | `416 Range Not Satisfiable` | `Content-Range: bytes */0` | Порожнє тіло (неможливо адресувати байти) |
| Синтаксично некоректний заголовок Range | `200 OK` | `Content-Length: N`<br>`Accept-Ranges: bytes` | Повне тіло ресурсу |
| Сервер не підтримує позиціювання | `200 OK` | `Accept-Ranges: none`<br>`Content-Length: N` | Повне тіло ресурсу |
| Кількість діапазонів перевищує безпечний ліміт | `200 OK` | `Content-Length: N` | Повне тіло ресурсу (захист від DoS) |

## Взаємодія з проміжними кешами, CDN та стисненням

### 1. Проблема узгодження зі стисненням (`Content-Encoding: gzip/br`)

Архітектурна пастка виникає, коли клієнт надсилає одночасно `Range: bytes=0-499` та `Accept-Encoding: gzip`.

* Заголовок `Range` завжди адресує байти **конкретної форми сутності**, яка передається по дроту. Якщо сервер зберігає файл у сирому вигляді (наприклад, 10 МБ), а потім стискає його на льоту через gzip до 2 МБ, зміщення в сирому файлі не відповідають зміщенням у стисненому потоці.
* **Канонічне правило:** Сервер зобов'язаний вимикати стиснення на льоту (`Content-Encoding`) при відповіді на запити `Range` над нестисненими файлами, або зберігати попередньо стиснену сутність з окремим унікальним ETag і застосовувати `Range` безпосередньо до стисненого бінарного образу.

### 2. Стратегії кешування на рівні CDN (Cloudflare, CloudFront, Fastly)

1. **Кешування повного файлу (Complete Entity Caching).** Вузол CDN викачує повний файл з origin-сервера один раз (`200 OK`), зберігає його на локальному NVMe-накопичувачі та самостійно нарізає байтові зрізи (`206 Partial Content`) для мільйонів клієнтів.
2. **Сегментоване кешування (Byte-Range Slice Caching).** Для файлів розміром у десятки гігабайтів (4K-відео, образи дисків) CDN розбиває простір адрес на рівні чанки (наприклад, по 2 або 5 МБ). При отриманні запиту клієнта на діапазон CDN генерує фонові підзапити лише до тих чанків, які перетинаються з запитом користувача.
3. **Заборона збереження 206 як повного ресурсу.** Проксі-сервери суворо перевіряють статус 206 і ніколи не використовують його для задоволення звичайних запитів `GET` без заголовка `Range`.

## Конфігурація реверс-проксі та вебсерверів

### NGINX (модуль ngx_http_slice_module та обмеження)

```nginx
http {
    # Захист від Range DoS: обмежуємо запит лише 1 діапазоном
    max_ranges 1;

    # Зона кешування для великих медіафайлів
    proxy_cache_path /var/cache/nginx/media levels=1:2 keys_zone=media_cache:50m
                     max_size=20g inactive=7d use_temp_path=off;

    server {
        listen 80;
        server_name cdn.example.com;

        location /videos/ {
            # Сегментуємо вхідні запити на блоки по 2 МБ
            slice             2m;
            
            # Формуємо унікальний ключ кешування з урахуванням зрізу
            proxy_cache       media_cache;
            proxy_cache_key   $uri$is_args$args$slice_range;
            
            # Передаємо обчислений піддіапазон на origin-сервер
            proxy_set_header  Range $slice_range;
            
            # Кешуємо часткові та повні відповіді на 30 днів
            proxy_cache_valid 200 206 30d;
            
            # Підтримка паралельних фонових довантажень
            proxy_cache_use_stale updating;
            proxy_cache_background_update on;
            
            proxy_pass        http://storage_backend;
        }
    }
}
```

## Підтримка в популярних клієнтських бібліотеках

| Мова / Бібліотека | Синтаксис відправки Range | Автоматичне докачування | Особливості |
| :--- | :--- | :--- | :--- |
| **cURL (CLI)** | `curl -r 0-499 URL` або `-C -` | Прапорець `-C -` (автоматичне зміщення) | Автоматично порівнює розмір наявного локального файлу |
| **JavaScript Fetch** | `headers: { 'Range': 'bytes=0-499' }` | Ручна реалізація через `ReadableStream` | Браузерний `fetch` не розбирає `multipart/byteranges` автономно |
| **Python `requests` / `httpx`** | `headers={'Range': f'bytes={offset}-'}` | Ручне відкриття файлу в режимі `'ab'` | Необхідно передавати `stream=True` для запобігання вичитки в RAM |
| **Go `net/http`** | `req.Header.Set("Range", "bytes=0-499")` | Вбудована функція `http.ServeContent` | Пакет `net/http` автоматично парсить `Range` та генерує `206` |
| **Rust `reqwest`** | `req.header(header::RANGE, "bytes=0-499")` | Через `tokio_util::io::StreamReader` | Підтримує zero-copy запис на асинхронний файл `tokio::fs::File` |

## Підтримка в хмарних об'єктних сховищах (S3, GCS, Azure, R2)

Усі провідні хмарні платформи підтримують заголовок `Range` у своїх REST API:

| Платформа | Підтримуваний синтаксис | Поведінка при оновленні | Специфічні особливості |
| :--- | :--- | :--- | :--- |
| **Amazon S3** | `Range: bytes=S-E` | Підтримує `If-Match` та `If-Unmodified-Since` | Підтримує лише одиночні діапазони; повертає `416` при виході за межі |
| **Google Cloud Storage** | `Range: bytes=S-E`, `bytes=S-`, `bytes=-N` | Підтримує генераційні мітки `x-goog-if-generation-match` | Підтримує прямий стрімінг зрізів великих об'єктів |
| **Azure Blob Storage** | `x-ms-range: bytes=S-E` або стандартний `Range` | Підтримує `If-Match` | Дозволяє одночасне читання зрізів до 4 МіБ у транзакційних бакетах |
| **Cloudflare R2** | Стандартний RFC 9110 `Range` | Підтримує сильні ETags | Безкоштовний вихідний трафік для часткових запитів |

## Особливості поведінки в HTTP/2 та HTTP/3

У бінарних мультиплексованих протоколах HTTP/2 (RFC 9113) та HTTP/3 QUIC (RFC 9114) семантика заголовків `Range` залишається незмінною, проте змінюється модель транспорту:

1. **Мультиплексування байтових потоків.** Клієнт може відкрити кілька паралельних HTTP/2-потоків (Streams) в межах єдиного TLS/TCP-з'єднання, надіславши в кожному потоці свій запит `Range` (наприклад, потік 3 запитує байти `0-1048575`, потік 5 запитує байти `1048576-2097151`). Це повністю усуває блокування початку черги (Head-of-Line Blocking) на рівні HTTP без відкриття множинних TCP-сокетів.
2. **Фреймування `DATA`.** Сервер передає запитаний зріз у послідовності бінарних фреймів `DATA`. Прапорець `END_STREAM` виставляється на останньому фреймі запитаного діапазону. Заголовок `Content-Length` точно вказує очікувану суму байтів у корисних навантаженнях фреймів `DATA`.
3. **Пріоритезація потоків.** Відеоплеєри призначають вищий пріоритет потокам, що несуть метадані (`moov` atom) та перші кадри відеопотоку, щоби мінімізувати затримку запуску відтворення (Time-to-First-Frame).

## Специфіка обробки Range у Service Workers (PWA)

У прогресивних веб-застосунках (PWA) браузерний фоновий воркер `ServiceWorker` перехоплює всі мережеві виклики через подію `fetch`. Якщо застосунок відтворює відео через тег `<video src="/media/movie.mp4">`, браузер Safari та Chrome генерують Range-запити.

Якщо Service Worker наївно перехоплює запит і повертає `caches.match(event.request)`, кеш браузера Cache Storage API зберігає лише монолітний об'єкт зі статусом `200 OK`. Браузерний відеоплеєр очікує статус `206 Partial Content` та заголовок `Content-Range`. Якщо воркер повертає `200 OK` замість `206`, відеоплеєр Safari на iOS повністю блокує відтворення та вимикає повзунок перемотування.

Для коректної роботи Service Worker зобов'язаний зчитати двійковий буфер збереженого файлу через `response.arrayBuffer()`, вручну розібрати вхідний заголовок `event.request.headers.get('range')`, витягнути зріз байтів через `arrayBuffer.slice(start, end + 1)` та сформувати синтетичну відповідь `new Response(slicedBuffer, { status: 206, statusText: 'Partial Content', headers: { 'Content-Range': ..., 'Content-Length': ... } })`.

## Чому Range не застосовується у WebSocket та gRPC

Попри універсальність, байтові діапазони HTTP не використовуються в протоколах WebSocket (RFC 6455) та gRPC:

* **WebSocket:** Працює як неструктурований двонаправлений потік повідомлень над єдиним TCP-сокетом. Позиціювання за зміщенням не має стандартизованої семантики на рівні кадру WebSocket, тому фрагментація реалізується на рівні прикладного протоколу (наприклад, передача JSON-структур із номерами чанків).
* **gRPC поверх HTTP/2:** Використовує виключно метод `POST` та потоки повідомлень у форматі Protocol Buffers (`Content-Type: application/grpc`). Оскільки за специфікацією RFC 9110 метод `POST` забороняє застосування заголовків `Range`, часткове читання реалізується через пагінацію в полях gRPC-повідомлень (`page_token`, `offset_bytes`).

## Модель загроз та захист від атак (Threat Model)

При реалізації обробників Range розробники зобов'язані враховувати три вектори вразливостей:

1. **Атака на вичерпання ресурсів через підсилення діапазонів (Range Amplification DoS).** Передача тисяч розрізнених діапазонів змушує сервер генерувати великі обсяги MIME-заголовків, що багаторазово перевищують розмір вихідного файлу. *Захист:* обмеження кількості зрізів до 1–5 та обов'язкова коалесценція суміжних інтервалів.
2. **Отруєння кешу (Cache Poisoning через Range).** Якщо реверс-проксі зберігає відповідь 206 як повне представлення для звичайного GET-запиту, інші користувачі отримають обрізаний файл. *Захист:* перевірка статусів відповідей перед записом у спільний кеш та використання модуля `slice`.
3. **Обхід авторизації мультиарендних сховищ (Multi-tenant Offset Bypass).** Якщо система зберігає дані кількох клієнтів в одному агрегованому файлі й перевіряє права лише на рівні файлу, зловмисник може зчитати конфіденційні байти сусіднього орендаря через заголовок `Range`. *Захист:* авторизація на рівні зміщень або повна ізоляція файлів на диску.

## Діагностика через Wireshark, tcpdump та cURL

Для детального аналізу протокольної взаємодії використовуються стандартні фільтри мережевого трафіку:

### Фільтри Wireshark

* Пошук усіх часткових відповідей: `http.response.code == 206`
* Пошук помилок виходу за межі: `http.response.code == 416`
* Пошук запитів із заголовком Range: `http.range`
* Пошук багаточастинних відповідей: `http.content_type contains "multipart/byteranges"`

### Захоплення пакетів через tcpdump у Linux

```bash
# Перехоплення заголовків Range та Content-Range у реальному часі на порту 80/8080
sudo tcpdump -nn -s 0 -A -i eth0 'tcp port 80 and (tcp[((tcp[12:1] & 0xf0) >> 2):4] = 0x47455420)' | grep -E -i 'Range:|Content-Range:|HTTP/1.[01] 206'
```

### Діагностичні команди cURL

```bash
# 1. Перевірка підтримки Accept-Ranges (запит заголовків)
curl -I https://cdn.example.com/video.mp4

# Очікувана відповідь:
# HTTP/2 200
# accept-ranges: bytes
# content-length: 52428800
# etag: "a89bc34-32"

# 2. Запит першого мегабайта (0 - 1048575 включно)
curl -i -H "Range: bytes=0-1048575" https://cdn.example.com/video.mp4

# Очікувана відповідь:
# HTTP/2 206
# content-range: bytes 0-1048575/52428800
# content-length: 1048576

# 3. Умовне докачування з правильним ETag (повертає 206)
curl -i -H "Range: bytes=1048576-" -H 'If-Range: "a89bc34-32"' https://cdn.example.com/video.mp4

# 4. Умовне докачування зі застарілим ETag (сервер повертає 200 і повний файл)
curl -i -H "Range: bytes=1048576-" -H 'If-Range: "outdated-etag"' https://cdn.example.com/video.mp4

# 5. Тест виходу за межі файлу (повертає 416 Range Not Satisfiable)
curl -i -H "Range: bytes=999999999-1000000000" https://cdn.example.com/video.mp4

# Очікувана відповідь:
# HTTP/2 416
# content-range: bytes */52428800
# content-length: 0
```

Ця специфікація забезпечує повний практичний та нормативний довідник для інженерів, які проєктують надійні сервіси обробки та передачі даних у сучасному веб-стеку.
