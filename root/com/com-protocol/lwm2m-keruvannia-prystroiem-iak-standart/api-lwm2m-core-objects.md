# 📋 Стандартні об'єкти та ресурси OMA LwM2M та IPSO

Об'єктно-ресурсна модель протоколу OMA Lightweight M2M стандартизує адресний простір, типи даних та операції над вузлами вбудованих систем для забезпечення повної сумісності обладнання різних виробників із хмарними серверами керування. Стандарт усуває потребу в розробці специфічних трансляторів і драйверів для кожного типу мікроконтролера, створюючи єдиний семантичний простір для телеметрії, діагностики та конфігурації.

Нижче наведено розгорнуту специфікацію обов'язкових та ключових базових об'єктів ядра LwM2M (Core Objects, числовий діапазон `0..1023`), а також стандартного об'єкта сенсора температури з реєстру IPSO Smart Objects (діапазон `3300..3399`). Для кожного ресурсу вказано числовий ідентифікатор ID, тип дозволених операцій (`R` — читання, `W` — запис, `E` — виконання), кратність (`Single` — одиничний, `Multiple` — множинний масив), статус присутності (`Mandatory` — обов'язковий, `Optional` — необов'язковий) та тип значення у двійковому протоколі.

---

### Об'єкт 0: Безпека (LwM2M Security Object, ID = 0)

Об'єкт 0 зберігає параметри безпеки, необхідні клієнту для встановлення зашифрованого з'єднання через протокол DTLS або зв'язки ключів OSCORE з сервером початкового завантаження (Bootstrap Server) та робочими серверами LwM2M. Для кожного сервера створюється окремий екземпляр об'єкта (наприклад, `/0/0` для Bootstrap-сервера та `/0/1` для основного сервера телеметрії).

Фундаментальне правило стандарту LwM2M полягає в тому, що всі ресурси Об'єкта 0 є суворо закритими для читання (`R`-операції заборонені для всіх інтерфейсів, окрім локального внутрішнього коду клієнта). Сервер керування не має технічної можливості зчитати вміст цього об'єкта, що унеможливлює витік закритих криптографічних ключів чи сертифікатів через відкриту протокольну взаємодію. Запис у ресурси Об'єкта 0 дозволено здійснювати виключно серверу Bootstrap під час фази початкової конфігурації пристрою.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | LwM2M Server URI | `W` | Single | Mandatory | String | Мережевий URI сервера у форматі `coaps://hostname:port` або `coap://hostname:port` |
| `1` | Bootstrap Server | `W` | Single | Mandatory | Boolean | Прапорець ролі сервера: `true` — сервер ініціалізації Bootstrap; `false` — робочий сервер |
| `2` | Security Mode | `W` | Single | Mandatory | Integer | Режим автентифікації: `0` = Pre-Shared Key (PSK), `1` = Raw Public Key (RPK), `2` = X.509 Certificate, `3` = NoSec |
| `3` | Public Key or Identity | `W` | Single | Mandatory | Opaque | Відкритий ідентифікатор PSK Identity (для режиму 0) або сертифікат / відкритий ключ клієнта (для режимів 1 та 2) |
| `4` | Server Public Key | `W` | Single | Mandatory | Opaque | Відкритий ключ сервера або кореневий сертифікат CA для верифікації справжності сервера |
| `5` | Secret Key | `W` | Single | Mandatory | Opaque | Секретний симетричний ключ PSK (для режиму 0) або закритий приватний ключ клієнта (для режимів 1 та 2) |
| `10` | Short Server ID | `W` | Single | Optional | Integer | Унікальний 16-бітний ідентифікатор сервера (`1..65534`), що пов'язує екземпляр Об'єкта 0 із відповідним екземпляром Об'єкта 1 |
| `11` | Client Hold Off Time | `W` | Single | Optional | Integer | Час очікування у секундах після ввімкнення пристрою до початку відправлення першого запиту до Bootstrap-сервера |

Ресурс `Client Hold Off Time` (ID `11`) запобігає перевантаженню мережі: якщо тисячі лічильників одночасно вмикаються після масштабного відновлення електроживлення на підстанції, клієнти витримують псевдовипадкову паузу, уникаючи шторму запитів на сервері ініціалізації.

### Об'єкт 1: Сервер (LwM2M Server Object, ID = 1)

Об'єкт 1 визначає параметри сесії прикладного рівня та правила обміну даними з конкретним робочим LwM2M-сервером. Кожен екземпляр Об'єкта 1 відповідає одному серверу та прив'язується до облікових даних Об'єкта 0 за допомогою спільного числового значення `Short Server ID`.

Цей об'єкт регулює частоту оновлення реєстрації та поведінку сповіщень. Ресурс `Lifetime` визначає максимальний інтервал мовчання, після якого сервер вважатиме клієнт відключеним і видалить його зі своєї бази активних маршрутів. Якщо пристрій працює у сплячому режимі, він зобов'язаний прокинутися до завершення часу `Lifetime` і надіслати запит оновлення реєстрації.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | Short Server ID | `R` | Single | Mandatory | Integer | Унікальний 16-бітний номер сервера, що зіставляється з ресурсом `/0/x/10` |
| `1` | Lifetime | `RW` | Single | Mandatory | Integer | Час життя реєстрації клієнта на сервері в секундах (типово від `3600` до `86400` секунд) |
| `2` | Default Minimum Period | `RW` | Single | Optional | Integer | Значення `pmin` за замовчуванням: мінімальний інтервал між сповіщеннями Observe |
| `3` | Default Maximum Period | `RW` | Single | Optional | Integer | Значення `pmax` за замовчуванням: максимальний інтервал між періодичними звітами |
| `6` | Notification Storing | `RW` | Single | Mandatory | Boolean | Режим збереження черги сповіщень під час тимчасової відсутності радіозв'язку |
| `7` | Binding | `RW` | Single | Mandatory | String | Транспортна прив'язка: `U` (UDP), `UQ` (UDP з чергою), `S` (SMS), `T` (TCP), `N` (Non-IP) |
| `8` | Registration Update Trigger | `E` | Single | Mandatory | Executable | Виклик ресурсу змушує клієнта негайно ініціювати відправлення запиту оновлення реєстрації |

Ресурс `Binding` (ID `7`) має критичне значення для автономних систем: значення `UQ` (UDP with Queue mode) сигналізує серверу, що пристрій підтримує буферизацію команд. Сервер знає, що клієнт більшу частину часу спить, тому складає всі запити на запис та конфігурацію у чергу, передаючи їх пачкою лише у моменти пробудження пристрою.

### Об'єкт 2: Контроль доступу (Access Control Object, ID = 2)

Об'єкт 2 реалізує модель розмежування прав доступу (Access Control Lists, ACL) у сценаріях, коли один пристрій обслуговує кількох незалежних операторів або хмарні сервери різних постачальників послуг (Multi-Server Deployment).

Кожен екземпляр Об'єкта 2 прив'язується до конкретного екземпляра цільового об'єкта на пристрої (ресурс `Target ObjectID` та `Target Object Instance ID`) і визначає, який саме сервер має право зчитувати, змінювати чи видаляти цей екземпляр.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | Target ObjectID | `R` | Single | Mandatory | Integer | Ідентифікатор захищеного об'єкта (наприклад, `3303`) |
| `1` | Target Object Instance ID | `R` | Single | Mandatory | Integer | Ідентифікатор захищеного екземпляра (наприклад, `0`) |
| `2` | ACL | `RW` | Multiple | Optional | Integer | Масив прав доступу, де індекс — це Short Server ID, а значення — бітова маска |
| `3` | Access Control Owner | `RW` | Single | Mandatory | Integer | Ідентифікатор сервера-власника (Short Server ID), який має повні права на керування цим списком ACL |

Бітова маска ресурсу `ACL` (ID `2`) кодує такі права:
- Bit 0 (`0x01`): Read — читання даних;
- Bit 1 (`0x02`): Write — запис та модифікація;
- Bit 2 (`0x04`): Execute — виконання команд;
- Bit 3 (`0x08`): Delete — видалення екземпляра;
- Bit 4 (`0x10`): Create — створення підлеглих об'єктів.

### Об'єкт 3: Пристрій (Device Object, ID = 3)

Об'єкт 3 надає вичерпну діагностичну інформацію про апаратну платформу, виробника, системний час, стан живлення та дозволяє виконати дистанційне перезавантаження або скидання параметрів до заводських налаштувань. На пристрої завжди існує рівно один екземпляр цього об'єкта (`/3/0`).

Ресурс `Reboot` (ID `4`) є обов'язковим для всіх платформ: отримання CoAP-запиту `POST /3/0/4` викликає безпечне перезавантаження мікроконтролера через системний сторожовий таймер (Watchdog) після завершення відправлення підтвердження `2.04 Changed`.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | Manufacturer | `R` | Single | Optional | String | Текстова назва компанії-виробника обладнання |
| `1` | Model Number | `R` | Single | Optional | String | Номер моделі або комерційна назва продукту |
| `2` | Serial Number | `R` | Single | Optional | String | Унікальний заводський серійний номер вузла |
| `3` | Firmware Version | `R` | Single | Optional | String | Поточна версія активного мікрокоду (наприклад, `v2.1.0-release`) |
| `4` | Reboot | `E` | Single | Mandatory | Executable | Команда перезавантаження мікроконтролера |
| `5` | Factory Reset | `E` | Single | Optional | Executable | Скидання конфігурації до початкового заводського стану |
| `6` | Available Power Sources | `R` | Multiple | Optional | Integer | Джерела живлення: `0` = DC, `1` = Internal Battery, `2` = External Battery, `4` = PoE, `5` = USB |
| `7` | Power Source Voltage | `R` | Multiple | Optional | Integer | Напруга джерела живлення у мілівольтах (мВ) |
| `8` | Power Source Current | `R` | Multiple | Optional | Integer | Струм споживання вузла у міліамперах (мА) |
| `9` | Battery Level | `R` | Single | Optional | Integer | Рівень заряду вбудованого акумулятора або батареї у відсотках (`0..100`) |
| `10` | Memory Free | `R` | Single | Optional | Integer | Обсяг вільної динамічної пам'яті RAM у кілобайтах |
| `11` | Error Code | `R` | Multiple | Mandatory | Integer | Масив поточних кодів апаратних та системних помилок |
| `13` | Current Time | `RW` | Single | Optional | Time | Поточний системний час у форматі Unix Epoch (секунди з 1 січня 1970 року) |
| `14` | UTC Offset | `RW` | Single | Optional | String | Зсув локального часу відносно UTC у форматі ISO 8601 (наприклад, `+02:00`) |

Ресурс `Error Code` (ID `11`) є множинним: якщо на пристрої одночасно виникло кілька несправностей (наприклад, низький заряд батареї та збій зовнішнього АЦП), клієнт формує масив екземплярів ресурсу `/3/0/11/0`, `/3/0/11/1`. Стандартні коди помилок включають: `0` (No error), `1` (Low battery power), `2` (External power supply off), `3` (GPS module failure), `4` (Low received signal strength), `5` (Out of memory).

### Об'єкт 4: Моніторинг зв'язку (Connectivity Monitoring, ID = 4)

Об'єкт 4 відображає параметри та якість фізичного каналу передачі даних. Він дозволяє оператору оцінювати покриття мережі, виявляти деградацію радіосигналу та контролювати призначені IP-адреси.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | Network Bearer | `R` | Single | Mandatory | Integer | Технологія радіодоступу: `0` = GSM, `6` = LTE, `7` = NB-IoT, `21` = Wi-Fi, `41` = Ethernet |
| `1` | Available Network Bearer | `R` | Multiple | Optional | Integer | Список усіх підтримуваних пристроєм резервних каналів зв'язку |
| `2` | Radio Signal Strength | `R` | Single | Mandatory | Integer | Потужність прийнятого радіосигналу RSSI у дБм (наприклад, `-85` дБм) |
| `3` | Link Quality | `R` | Single | Optional | Integer | Показник якості зв'язку LQI або відношення сигнал/шум SNR |
| `4` | IP Addresses | `R` | Multiple | Mandatory | String | Призначені пристрою мережеві адреси IPv4 або IPv6 |
| `5` | Router IP Addresses | `R` | Multiple | Optional | String | IP-адреса шлюзу за замовчуванням (Default Gateway) |
| `8` | Cell ID | `R` | Single | Optional | Integer | Глобальний ідентифікатор активної стільникової вишки базової станції (E-UTRAN Cell ID) |

Ресурс `Radio Signal Strength` (ID `2`) є критично важливим для налаштування адаптивного розміру блоків при оновленні прошивки: при погіршенні RSSI нижче `-105` дБм розмір блоку передачі зменшується до 128 байтів для запобігання втратам пакетів.

### Об'єкт 5: Оновлення прошивки (Firmware Update Object, ID = 5)

Об'єкт 5 стандартизує повний цикл дистанційного оновлення прошивки (FOTA): від завантаження бінарного файлу до валідації криптографічного підпису та запуску низькорівневого завантажувача.

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `0` | Package | `W` | Single | Mandatory | Opaque | Потік бінарного образу прошивки, переданий методом Push через CoAP Block1 |
| `1` | Package URI | `RW` | Single | Mandatory | String | URI для завантаження клієнтом образу методом Pull (`coaps://`, `https://`) |
| `2` | Update | `E` | Single | Mandatory | Executable | Команда запуску процедури прошивання та перезавантаження мікроконтролера |
| `3` | State | `R` | Single | Mandatory | Integer | Поточний стан автомата: `0` = Idle, `1` = Downloading, `2` = Downloaded, `3` = Updating |
| `5` | Update Result | `R` | Single | Mandatory | Integer | Результат операції: `0` = Default, `1` = Success, `2` = Out of Flash, `3` = Out of RAM, `4` = Connection Lost, `5` = Integrity Failed, `6` = Bad Package Type, `7` = Invalid URI, `8` = Flash Write Failed |
| `6` | PkgName | `R` | Single | Optional | String | Текстова назва пакета оновлення |
| `7` | PkgVersion | `R` | Single | Optional | String | Версія цільової прошивки (наприклад, `v2.2.0`) |
| `9` | Delivery Method | `R` | Single | Mandatory | Integer | Підтримувані способи доставки: `0` = Лише Pull (за URI), `1` = Лише Push, `2` = Обидва |

Ресурс `Update Result` (ID `5`) дозволяє оператору точно визначити причину збою у разі невдалої спроби FOTA. Якщо завантажений образ не пройшов верифікацію цифрового підпису, клієнт встановлює код `5` (Integrity check failure), повертається у стан `Idle` і не запускає потенційно небезпечне прошивання.

### Об'єкт 3303: IPSO Сенсор температури (Temperature Object, ID = 3303)

Створений консорціумом IPSO (IP for Smart Objects) об'єкт 3303 стандартизує представлення температурних вимірювань для будь-яких фізичних сенсорів (термопар, терморезисторів NTC, цифрових мікросхем I2C/SPI).

| ID | Назва ресурсу | Операції | Кратність | Статус | Тип даних | Опис та семантика |
|:---|:---|:---:|:---:|:---:|:---|:---|
| `5700` | Sensor Value | `R` | Single | Mandatory | Float | Поточне миттєве значення температури, зняте з датчика |
| `5601` | Min Measured Value | `R` | Single | Optional | Float | Мінімальне зареєстроване значення температури за період спостереження |
| `5602` | Max Measured Value | `R` | Single | Optional | Float | Максимальне зареєстроване значення температури |
| `5603` | Min Range Value | `R` | Single | Optional | Float | Нижня фізична межа вимірювання датчика (наприклад, `-40.0`) |
| `5604` | Max Range Value | `R` | Single | Optional | Float | Верхня фізична межа вимірювання датчика (наприклад, `+125.0`) |
| `5605` | Reset Min and Max Values | `E` | Single | Optional | Executable | Команда скидання екстремумів `5601` та `5602` до поточного значення `5700` |
| `5701` | Sensor Units | `R` | Single | Optional | String | Одиниця вимірювання (за стандартом UCUM: `"Cel"` для Цельсія, `"K"` для Кельвіна) |

Ресурс `Sensor Value` (ID `5700`) є головною ціллю для підписки Observe. Сервер може налаштувати атрибути сповіщення `pmin=30`, `pmax=3600`, `st=0.5`, і клієнт передаватиме новий звіт лише у тому разі, якщо температура змінилася щонайменше на `0.5` градуса Цельсія, або якщо минула одна година з моменту останнього сеансу зв'язку.
