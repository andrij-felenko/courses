# LwM2M: керування пристроєм як стандарт

<preknowlist>

</preknowlist>

Розгортання промислової телеметричної мережі з 50 000 автономних лічильників води чи газу на базі стільникового зв'язку NB-IoT стикається з кризою сумісності та надійності, щойно кожен постачальник обладнання намагається реалізувати власний бінарний протокол. Якщо датчик тиску передає байти у пропрієтарному порядку без стандартизованої моделі даних, серверна хмара перетворюється на хаос із десятків несумісних парсерів. Коли пристрій вимагає зміни частоти опитування сенсорів, оператор змушений писати специфічні скрипти для кожної ревізії плати. Найбільша загроза виникає під час дистанційного оновлення прошивки (FOTA): відсутність стандартизованого автомата станів завантаження та валідації призводить до того, що після збою радіоканалу мікроконтролер перетворюється на «цеглину» під шаром асфальту, змушуючи виїжджати ремонтні бригади для фізичної заміни модуля.

Стандарт OMA Lightweight M2M (LwM2M, розроблений альянсом Open Mobile Alliance SpecWorks) вирішує цю фундаментальну проблему, перетворюючи все керування вбудованим пристроєм — від зняття показань сенсорів до криптографічного оновлення прошивки та моніторингу заряду батареї — на уніфіковану об'єктно-орієнтовану RESTful-модель поверх легкого протоколу CoAP. Докладно про те, як індустрія перейшла від важких телеком-стандартів OMA-DM до сучасного легкомовного стеку, викладено в історичному нарисі про те, як розгорталася [еволюція протоколів керування пристроями від OMA-DM до LwM2M](root:com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/hist-oma-lwm2m-evolution.md).

### Архітектура OMA LwM2M: клієнт-серверна модель, стек протоколів та безпека

Архітектура LwM2M будується на клієнт-серверній моделі. Клієнт LwM2M (LwM2M Client) виконується безпосередньо на мікроконтролері або комунікаційному модулі кінцевого IoT-пристрою і представляє всі апаратні ресурси та сенсори у вигляді стандартизованого дерева об'єктів. Сервер LwM2M (LwM2M Server) розміщується у хмарі або локальному шлюзі оператора та здійснює моніторинг, конфігурацію і збір телеметрії. Окрему роль відіграє сервер початкового завантаження (LwM2M Bootstrap Server), який відповідає за безпечне введення щойно увімкненого вузла в експлуатацію.

![Архітектура OMA LwM2M: 4 логічні інтерфейси, стек протоколів та взаємодія клієнта із серверами Bootstrap і Server](/root/com/com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/img/lwm2m-architecture-interfaces.svg)
*Архітектура OMA LwM2M: чотири логічні інтерфейси (Bootstrap, Registration, Device Management, Information Reporting), що працюють поверх протоколу CoAP із захистом через DTLS або OSCORE.*

Стек протоколу LwM2M має виражену шарувату структуру:
1. **Фізичний і канальний рівні (Physical & Link Layers):** енергоефективні бездротові радіомережі (NB-IoT, LTE-M, LoRaWAN через шар адаптації, IEEE 802.15.4 / 6LoWPAN), а також дротові інтерфейси Ethernet або RS-485.
2. **Транспортний рівень (Transport Layer):** основним транспортом є протокол ненадійних датаграм **UDP** (порт за замовчуванням `5683` для відкритого та `5684` для зашифрованого трафіку). Для мереж із блокуванням UDP або жорсткими корпоративними фаєрволами стандарт LwM2M 1.1+ підтримує транспорт **TCP** (порти `5685` та `5686` для TLS). Для пробудження пристроїв із глибокого сну може застосовуватися канал коротких повідомлень **SMS**, а для стільникових мереж 3GPP — не-IP доставка даних **NIDD** (англ. *Non-IP Data Delivery*).
3. **Рівень безпеки (Security Layer):**
   - **DTLS 1.2 / 1.3 (RFC 6347):** шифрування на рівні датаграм «хоп-за-хопом». Підтримує три стандартні режими автентифікації: спільний симетричний ключ (**PSK**, *Pre-Shared Key*), сирі асиметричні відкриті ключі (**RPK**, *Raw Public Key* за стандартом RFC 7250) та повні цифрові сертифікати **X.509**.
   - **OSCORE (RFC 8613):** об'єктна безпека для обмежених веб-середовищ (англ. *Object Security for Constrained RESTful Environments*). Забезпечує наскрізне шифрування корисного навантаження та опцій запиту безпосередньо всередині повідомлення CoAP на прикладному рівні. Це дозволяє безпечно передавати дані через проміжні шлюзи, проксі чи операторські транслятори адрес без розкриття вмісту третім сторонам.
4. **Рівень прикладного обміну CoAP (RFC 7252):** забезпечує транспортну семантику REST (методи `GET`, `POST`, `PUT`, `DELETE`), контроль надійності доставки через типи `CON` / `ACK` / `RST`, блокову передачу великих масивів даних **Blockwise Transfer** (RFC 7959) та асинхронне підписування на події **Observe / Notify** (RFC 7641).
5. **Рівень увімкнення сервісів LwM2M (LwM2M Enabler):** визначає логічні інтерфейси, об'єктну модель, бінарні формати даних (TLV, SenML CBOR) та алгоритми керування пристроєм.

> 🔧 **Навіщо це.** Поєднання CoAP та DTLS дає колосальну економію енергії у порівнянні з HTTP/TLS. Завдяки механізму відновлення сесії DTLS Session Resumption (із використанням ідентифікаторів Session ID або квитків Session Tickets RFC 5077), пробуджений із режиму глибокого сну PSM лічильник витрачає на надсилання виміру та отримання підтвердження лише 1–2 датаграми замість повного 4-етапного криптографічного рукостискання.

### Об'єктно-ресурсна модель: ієрархія та простори імен

В основі уніфікації LwM2M лежить сувора чотирирівнева ієрархічна адресація ресурсів. Будь-яка сутність у системі — від сертифіката сервера до напруги на внутрішньому АЦП — однозначно адресується за допомогою числового шляху URI:

```
/{Object ID} / {Object Instance ID} / {Resource ID} / {Resource Instance ID}
```

![Об'єктно-ресурсна ієрархія OMA LwM2M та IPSO Smart Objects: структура URI та базові об'єкти](/root/com/com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/img/lwm2m-object-tree.svg)
*Об'єктно-ресурсне дерево LwM2M: універсальний простір імен URI із числовими ідентифікаторами об'єктів (Object ID), екземплярів (Instance ID) та ресурсів (Resource ID).*

Розглянемо рівні ієрархії:
- **Об'єкт (Object, `Object ID`):** логічне групування споріднених функцій або сенсорів. Діапазон `0..1023` зарезервовано альянсом OMA для базових об'єктів ядра (Core Objects). Діапазон `1024..2047` виділено для стандартів сторонніх телеком-організацій. Діапазон `2048..10240` (зокрема `3300..3399`) закріплено за сенсорами та актуаторами реєстру IPSO Smart Objects. Простір `10241..65535` відкритий для приватних об'єктів виробників обладнання.
- **Екземпляр об'єкта (Object Instance, `Instance ID`):** конкретне фізичне або логічне втілення об'єкта на пристрої (індексація від `0`). Якщо пристрій підтримує з'єднання з двома незалежними LwM2M-серверами, він створює два екземпляри об'єкта сервера: `/1/0` та `/1/1`. Якщо на платі розпаяно три термодатчики, вони відображаються як екземпляри `/3303/0`, `/3303/1` та `/3303/2`.
- **Ресурс (Resource, `Resource ID`):** атомарний елемент даних або точка керування всередині екземпляра об'єкта. Ресурс може бути призначений для читання (`R`), запису (`W`) чи виконання команди (`E`).
- **Екземпляр ресурсу (Resource Instance, `Resource Instance ID`):** використовується виключно для множинних ресурсів (Multiple Resources), які зберігають масиви однотипних значень (наприклад, перелік поточних кодів системних помилок `/3/0/11/0`, `/3/0/11/1`).

Повний довідник обов'язкових числових ідентифікаторів, форматів та бітових масок для базових об'єктів ядра доступний у спеціальній довідковій специфікації [стандартні об'єкти та ресурси OMA LwM2M та IPSO](root:com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/api-lwm2m-core-objects.md).

#### Базові об'єкти ядра OMA LwM2M

1. **Об'єкт 0 (LwM2M Security):** зберігає конфіденційні параметри з'єднання з серверами Bootstrap та робочими LwM2M серверами (URI, режим автентифікації PSK/RPK/X.509, відкриті сертифікати та закриті ключі). Цей об'єкт є повністю закритим від зчитування сервером (`R`-операції заборонені стандартом задля унеможливлення витоку ключів).
2. **Об'єкт 1 (LwM2M Server):** зберігає параметри протокольної сесії з конкретним сервером: час життя реєстрації `Lifetime` (`/1/x/1`), мінімальний період спостереження `Default Min Period` (`/1/x/2`), максимальний період `Default Max Period` (`/1/x/3`) та виконуваний ресурс вимушеного оновлення реєстрації `Registration Update Trigger` (`/1/x/8`).
3. **Об'єкт 3 (Device):** надає діагностичну інформацію про вузол: виробник (`/3/0/0`), модель (`/3/0/1`), серійний номер (`/3/0/2`), поточна версія прошивки (`/3/0/3`), залишок батареї у відсотках (`/3/0/9`), обсяг вільної пам'яті RAM (`/3/0/10`) та ресурс перезавантаження мікроконтролера `Reboot` (`/3/0/4`).
4. **Об'єкт 5 (Firmware Update):** керує станом та процесом оновлення прошивки пристрою за повітрям (FOTA).

#### IPSO Smart Objects: уніфікація сенсорних даних

Альянс IPSO стандартизував структуру сенсорів для усунення розбіжностей в одиницях та форматах вимірювання. Розглянемо об'єкт сенсора температури **Object 3303 (Temperature)**:
- `/3303/0/5700` (`Sensor Value`, Float, `R`, Mandatory) — поточне значення виміряної температури;
- `/3303/0/5601` (`Min Measured Value`, Float, `R`, Optional) — мінімальна зареєстрована температура з моменту запуску чи останнього скидання;
- `/3303/0/5602` (`Max Measured Value`, Float, `R`, Optional) — максимальна зареєстрована температура;
- `/3303/0/5701` (`Sensor Units`, String, `R`, Optional) — одиниця вимірювання (за міжнародним стандартом UCUM: `"Cel"` для градусів Цельсія);
- `/3303/0/5605` (`Reset Min/Max`, Executable, `E`, Optional) — команда скидання екстремумів.

### Формати даних: від бінарного TLV до SenML CBOR

Для передачі структурованих об'єктів та окремих ресурсів через CoAP стандарт LwM2M підтримує кілька форматів представлення (Content-Formats), узгодження яких відбувається через опції CoAP `Content-Format` (код `12`) та `Accept` (код `17`).

| Назва формату | Content-Format ID | Версія LwM2M | Опис та застосування |
|:---|:---:|:---:|:---|
| **Plain Text** | `0` (`text/plain`) | 1.0+ | Простий ASCII-текст для передачі одного ресурсу (наприклад, числа `"23.5"` чи рядка) |
| **Opaque** | `42` (`application/octet-stream`) | 1.0+ | Сирий бінарний масив (використовується для прошивок `/5/0/0` та ключів) |
| **LwM2M TLV** | `11542` (`application/vnd.oma.lwm2m+tlv`) | 1.0+ | Двійковий формат для передачі повних об'єктів, екземплярів або ресурсів |
| **LwM2M JSON** | `11543` (`application/vnd.oma.lwm2m+json`) | 1.0+ | Текстовий JSON-масив записів із числовими шляхами та значеннями |
| **SenML JSON** | `110` (`application/senml+json`) | 1.1+ | Стандартизований RFC 8428 JSON із базовим часом `bt` та базовим ім'ям `bn` |
| **SenML CBOR** | `112` (`application/senml+cbor`) | 1.1+ | Компактний двійковий CBOR еквівалент SenML (найефективніший для LwM2M 1.1/1.2) |

#### Анатомія бінарного кодування LwM2M TLV

Формат TLV (Type-Length-Value) оптимізований для розбору на 8/16/32-бітних процесорах без використання динамічної пам'яті. Кожен елемент потоку починається з 1 байта заголовка `Type`, за яким слідують ідентифікатор `Identifier`, поле довжини `Length` та саме значення `Value`.

![Будова двійкового формату LwM2M TLV: 8-бітний заголовок Type, Identifier, Length та Value](/root/com/com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/img/lwm2m-tlv-format.svg)
*Двійкова структура LwM2M TLV: розкладка бітів у байті заголовка Type та послідовність полів у бінарному потоці.*

Розглянемо бітову карту заголовка типу:
- **Bits 7–6 (Тип елемента):**
  - `00` — Object Instance (екземпляр об'єкта, що містить вкладені TLV ресурсів);
  - `01` — Resource Instance (екземпляр значення всередині множинного ресурсу);
  - `10` — Multiple Resource (множинний ресурс, що містить вкладені Resource Instance);
  - `11` — Resource with Value (одиничний ресурс із безпосереднім значенням).
- **Bit 5 (Довжина ID):**
  - `0` — ідентифікатор займає 8 бітів (1 байт);
  - `1` — ідентифікатор займає 16 бітів (2 байти Big-Endian).
- **Bits 4–3 (Тип довжини Length):**
  - `00` — поле Length відсутнє, а довжина значення (від 0 до 7 байтів) закодована безпосередньо в бітах 2–0;
  - `01` — поле Length становить 1 байт (довжина до 255 байтів);
  - `10` — поле Length становить 2 байти (довжина до 65 535 байтів);
  - `11` — поле Length становить 3 байти (довжина до 16,7 МБ).
- **Bits 2–0 (Довжина значення або біти резерву):** якщо Bits 4–3 == `00`, ці біти містять розмір корисного навантаження `Value`.

Детальний алгоритм побудови енергоефективного парсера без динамічного виділення пам'яті наведено в описі проекту [двійковий кодек LwM2M TLV для мікроконтролерів](root:com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/proj-lwm2m-tlv-codec.md).

#### Приклад двійкового декодування TLV пакету

Припустимо, клієнт надсилає відповідь на запит читання екземпляра пристрою `/3/0`, що містить заряд батареї `/3/0/9` (`95%`) та поточний час `/3/0/13` (`1700000000` Unix Timestamp). Бінарний дамп корисного навантаження у шістнадцятковому вигляді:

```
C1 09 5F C4 0D 65 53 95 00
```

Розберемо байти покроково:
1. `0xC1` — байт типу `Type` для першого ресурсу:
   - біти 7-6 мають значення `11` (Resource with Value, звичайний ресурс);
   - біт 5 дорівнює `0` (однобайтовий 8-бітний ідентифікатор ID);
   - біти 4-3 дорівнюють `00` (довжина значення закодована безпосередньо у бітах 2-0);
   - біти 2-0 мають значення `001` (довжина корисного навантаження становить 1 байт).
2. `0x09` — числовий ідентифікатор ресурсу `Resource ID` зі значенням `9` (рівень заряду батареї `Battery Level`).
3. `0x5F` — значення поля `Value`, що становить `0x5F` (десяткове число `95` у відсотках).
4. `0xC4` — байт типу `Type` для другого ресурсу:
   - біти 7-6 мають значення `11` (Resource with Value);
   - біт 5 дорівнює `0` (8-бітний ідентифікатор ID);
   - біти 4-3 дорівнюють `00` (довжина у молодших бітах);
   - біти 2-0 мають значення `100` (довжина корисного навантаження становить 4 байти).
5. `0x0D` — числовий ідентифікатор ресурсу `Resource ID` зі значенням `13` (системний час `Current Time`).
6. `0x65 0x53 0x95 0x00` — 4-байтове ціле число у порядку Big-Endian зі значенням `1700000000` (мітка часу Unix).

Увесь пакет із двома повноцінними полями зайняв рівно 9 байтів. Для порівняння, еквівалентний JSON-документ зайняв би понад 50 байтів.

#### Формат SenML (Sensor Measurement Lists, RFC 8428)

У стандартах LwM2M 1.1 та 1.2 основним форматом передачі серій вимірювань став формат SenML. Він дозволяє об'єднувати часові ряди від кількох сенсорів у компактний список записів. Базове ім'я `bn` (Base Name) задає спільний префікс шляху URI, базовий час `bt` (Base Time) — спільну мітку часу Unix, а окремі записи містять відносне ім'я `n`, відносний час `t` та виміряне числове значення `v` або рядок `vs`:

```json
[
  {"bn": "/3303/0/", "bt": 1700000000, "bu": "Cel"},
  {"n": "5700", "v": 21.4, "t": -60},
  {"n": "5700", "v": 21.8, "t": 0}
]
```

При серіалізації цього масиву в бінарний формат **SenML CBOR** (Content-Format `112`) текстові ключі замінюються цілими числовими тегами, скорочуючи розмір телеметричного повідомлення з кількома точками вимірювань до 25–35 байтів.

### Чотири логічні інтерфейси OMA LwM2M

Усі комунікації між клієнтом та серверами суворо розмежовані на 4 функціональні інтерфейси.

```
       ┌───────────────────────────────────────────────────────────┐
       │                   LwM2M Bootstrap Server                  │
       └─────────────────────────────┬─────────────────────────────┘
                                     │ 1. Bootstrap Interface
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                               LwM2M Client                               │
└──────────────┬─────────────────────────────┬─────────────────────────────┘
               │ 2. Registration             │ 3. Device Management &
               │    Interface                │    Service Enablement
               │                             │ 4. Information Reporting
               ▼                             ▼
       ┌───────────────────────────────────────────────────────────┐
       │                       LwM2M Server                        │
       └───────────────────────────────────────────────────────────┘
```

#### 1. Інтерфейс початкового завантаження (Bootstrap Interface)

Забезпечує первинну ініціалізацію нового або скинутого до заводських налаштувань пристрою. Клієнт отримує від сервера Bootstrap мережеві адреси робочих LwM2M-серверів та відповідні криптографічні ключі DTLS.
- **Client-Initiated Bootstrap:** Клієнт надсилає CoAP `POST` запит на фіксований URI `/bs` сервера Bootstrap із зазначенням свого унікального імені кінцевої точки (Endpoint Name, `ep`):
  ```
  POST /bs?ep=urn:imei:860123456789012 CoAP CON [MID=0x0100]
  ```
  Сервер Bootstrap відповідає `2.04 Changed`, після чого надсилає серію команд запису `PUT` / `POST` у локальні екземпляри об'єктів `/0` (Security) та `/1` (Server) клієнта. Завершується процес командою `POST /bs` (Bootstrap Finish).
- **Server-Initiated Bootstrap:** Сервер сам надсилає команди запису конфігурації, якщо пристрій доступний у мережі за статичною IP-адресою або через SMS-тригер.
- **Factory Bootstrap:** Ключі та сертифікати робочих серверів прошиваються у пам'ять мікроконтролера на заводі під час виробництва; звернення до сервера Bootstrap не виконується.

#### 2. Інтерфейс реєстрації (Registration Interface)

Дозволяє клієнту повідомити робочий LwM2M-сервер про свою присутність у мережі, зареєструвати підтримувані об'єкти та підтримувати активний сеанс зв'язку.

```
Клієнт                                                 Сервер LwM2M
  │                                                         │
  │─── 1. POST /rd?ep=meter-01&lt=86400&b=U (CON) ────────────>│  (Реєстрація)
  │    Payload: </1/0>,</3/0>,</5/0>,</3303/0>              │
  │<── 2. 2.01 Created [Location-Path: /rd/42a] (ACK) ──────│
  │                                                         │
  │    ... час роботи (через ~80 000 с або зміну IP) ...    │
  │                                                         │
  │─── 3. POST /rd/42a (CON) ──────────────────────────────>│  (Оновлення)
  │<── 4. 2.04 Changed (ACK) ───────────────────────────────│
  │                                                         │
  │─── 5. DELETE /rd/42a (CON) ────────────────────────────>│  (Дереєстрація)
  │<── 6. 2.02 Deleted (ACK) ───────────────────────────────│
```

- **Реєстрація (Register):** Клієнт шле `POST /rd` із параметрами запиту:
  - `ep` (Endpoint Name) — унікальне глобальне ім'я пристрою (наприклад, `urn:imei:...` або `urn:uuid:...`);
  - `lt` (Lifetime) — час життя реєстрації в секундах (наприклад, `86400`);
  - `lwm2m` — версія протоколу (`1.0`, `1.1`);
  - `b` (Binding) — підтримуваний транспорт (`U` для UDP, `UQ` для UDP з підтримкою черги повідомлень, `T` для TCP).
  Тіло запиту містить перелік наявних об'єктів у стандартному форматі CoRE Link Format (RFC 6690): `</1/0>,</3/0>,</4/0>,</5/0>,</3303/0>`.
  Сервер зберігає стан і повертає `2.01 Created` із заголовком `Location-Path` (наприклад, `/rd/42a`).
- **Оновлення реєстрації (Update):** До завершення терміну `Lifetime` клієнт зобов'язаний надіслати `POST /rd/42a`. Якщо змінилася IP-адреса, прошивка чи список об'єктів, нові параметри додаються у тіло запиту.
- **Дереєстрація (Deregister):** При плановому вимкненні чи переході в тривалу консервацію клієнт відправляє `DELETE /rd/42a`.

#### 3. Інтерфейс керування пристроєм та активації сервісів (Device Management & Service Enablement)

Сервер виконує активні операції над об'єктами та ресурсами клієнта за допомогою стандартних REST-методів CoAP:
- **Read (`GET`):** зчитування значення окремого ресурсу (`GET /3303/0/5700`), повного екземпляра (`GET /3/0`) або цілого об'єкта (`GET /3303`). Відповідь повертається у коді `2.05 Content`.
- **Write (`PUT` або `POST`):**
  - `PUT` — повна заміна значення ресурсу чи екземпляра;
  - `POST` — частковий запис окремих ресурсів всередині екземпляра (Partial Write).
- **Execute (`POST`):** запуск виконуваного ресурсу без корисного навантаження (наприклад, `POST /3/0/4` для перезавантаження мікроконтролера чи `POST /5/0/2` для старту FOTA). При успіху клієнт повертає `2.04 Changed`.
- **Create (`POST`):** створення нового екземпляра об'єкта (наприклад, `POST /3303` для додавання нового віртуального датчика).
- **Delete (`DELETE`):** видалення динамічного екземпляра об'єкта (`DELETE /3303/1`).
- **Discover (`GET` із заголовком `Accept: application/link-format`):** опитування списку доступних ресурсів та їхніх поточних атрибутів спостереження.
- **Write-Attributes (`PUT` із параметрами запиту Query):** встановлення умов сповіщення для Information Reporting (наприклад, `PUT /3303/0/5700?pmin=10&pmax=300&gt=45.0`).

#### 4. Інтерфейс звітування інформації (Information Reporting Interface)

Реалізує механізм реактивної доставки телеметрії на базі протоколу CoAP Observe (RFC 7641). Замість постійного опитування датчиків із боку сервера (Polling), клієнт сам асинхронно надсилає дані, щойно вони змінюються відповідно до заданих критеріїв.

Параметри спостереження (Notification Attributes) задаються сервером:
- `pmin` (Minimum Period) — мінімальний інтервал у секундах між двома послідовними сповіщеннями (захист від шторму пакетів при швидких коливаннях сигналу);
- `pmax` (Maximum Period) — максимальний інтервал (серцебиття, Heartbeat): якщо значення не змінювалося, звіт однаково буде надісланий після вичерпання `pmax` секунд;
- `gt` (Greater Than) — поріг спрацьовування «більше ніж» (сповіщення надсилається, якщо температура перевищила вказане значення);
- `lt` (Less Than) — поріг «менше ніж»;
- `st` (Step) — мінімальний крок зміни значення (сповіщення генерується лише якщо абсолютна різниця між новим та старим значенням перевищує або дорівнює кроку `st`).

```
Сервер LwM2M                                           Клієнт (MCU)
  │                                                         │
  │─── 1. GET /3303/0/5700 [Observe=0] (CON) ──────────────>│ (Підписка)
  │<── 2. 2.05 Content [Observe=101, Val=22.4] (ACK) ───────│ (Початкове значення)
  │                                                         │
  │    ... температура змінюється незначно (< st) ...       │ (Мовчання радіотракту)
  │                                                         │
  │    ... стрибок температури до 25.1°C (> st) ...         │
  │<── 3. 2.05 Content [Observe=102, Val=25.1] (CON) ───────│ (Асинхронний звіт)
  │─── 4. Empty ACK (ACK) ─────────────────────────────────>│
```

### Складені операції (Composite Operations) у LwM2M 1.1 та 1.2

У ранній версії LwM2M 1.0 для зчитування трьох незв'язаних параметрів — наприклад, заряду батареї `/3/0/9`, потужності сигналу RSSI `/4/0/2` та температури `/3303/0/5700` — сервер був змушений відправляти три окремі CoAP-запити `GET` або зчитувати цілі об'єкти з надлишковими даними.

Версія LwM2M 1.1 вирішила цю проблему за допомогою трьох стандартизованих складених операцій, що використовують кодування SenML CBOR (Content-Format `112`):
1. **Read-Composite (CoAP `FETCH`, метод `0.05`):** Сервер надсилає в тілі запиту `FETCH` масив цільових шляхів SenML: `[{"n":"/3/0/9"}, {"n":"/4/0/2"}, {"n":"/3303/0/5700"}]`. Клієнт формує єдину компактну CBOR-відповідь, що містить значення лише цих трьох ресурсів.
2. **Write-Composite (CoAP `iPATCH`, метод `0.07`):** Дозволяє серверу виконати атомарний запис одразу в кілька ресурсів різних об'єктів в межах єдиної транзакції (наприклад, одночасно оновити `pmin` в Об'єкті 1 та поріг температури в Об'єкті 3303). Якщо запис хоча б одного ресурсу зазнає невдачі, вся операція скасовується без зміни стану пристрою.
3. **Observe-Composite:** Дозволяє оформити єдину комбіновану підписку на довільний набір параметрів з єдиним лічильником Observe.

### Стандартизований життєвий цикл оновлення прошивки (Object 5 FSM)

Оновлення програмного забезпечення по радіоканалу (FOTA, *Firmware Over-The-Air*) — найвідповідальніша функція системи керування пристроєм. Помилка під час запису образу або втрата живлення в процесі стирання секторів флеш-пам'яті може призвести до незворотної відмови обладнання. Стандарт LwM2M фіксує суворий скінченний автомат станів для **Об'єкта 5 (Firmware Update)**.

![Скінченний автомат стану оновлення прошивки LwM2M Object 5 FSM](/root/com/com-protocol/lwm2m-keruvannia-prystroiem-iak-standart/img/lwm2m-firmware-update-fsm.svg)
*Скінченний автомат LwM2M Object 5: переходи між станами Idle, Downloading, Downloaded та Updating із кодами результатів помилок.*

#### Чотири стани автомата (Ресурс `/5/0/3` State)
1. **`0: IDLE` (Очікування):** пристрій працює у штатному режимі, завантаження не відбувається.
2. **`1: DOWNLOADING` (Завантаження):** клієнт отримує бінарні блоки прошивки або завантажує їх із зовнішнього сервера.
3. **`2: DOWNLOADED` (Завантажено):** образ повністю отримано у буферну пам'ять (зовнішню SPI Flash чи резервний банк вбудованої Flash), перевірено контрольну суму CRC32/SHA-256 та криптографічний підпис (ECDSA/Ed25519).
4. **`3: UPDATING` (Оновлення):** запущено процедуру прошивання; завантажувач перемикає банки пам'яті або копіює новий образ у робочу область і перезавантажує мікроконтролер.

#### Коди результатів оновлення (Ресурс `/5/0/5` Update Result)
- `0` — Default (початковий стан);
- `1` — Firmware updated successfully (успішно оновлено);
- `2` — Not enough storage for new firmware image (недостатньо вільного місця у Flash);
- `3` — Out of memory (RAM) during downloading (вичерпано оперативну пам'ять);
- `4` — Connection lost during firmware downloading (обрив радіозв'язку);
- `5` — Integrity check failure for new firmware image (помилка хешу або підпису);
- `6` — Unsupported package type (несумісний формат або архітектура образу);
- `7` — Invalid URI (некоректний протокол чи адреса сервера завантаження);
- `8` — Firmware update failed (збій завантажувача під час запису флеш-пам'яті);
- `9` — Unsupported protocol.

#### Механізми доставки: Push проти Pull та протокол CoAP Blockwise

Стандарт підтримує дві взаємодоповнюючі моделі доставки:
1. **Модель прямої передачі (Package Push):** Сервер LwM2M передає образ прошивки безпосередньо у ресурс `/5/0/0` за допомогою механізму CoAP Block1 (RFC 7959). Кожна датаграма містить опцію `Block1` (номер блоку `NUM`, прапорець наявності наступних блоків `M` та експоненту розміру `SZX`, де розмір блоку обчислюється як `2^(SZX + 4)` байтів). Клієнт зберігає блоки у Flash і підтверджує отримання квитанцією `ACK` із кодом `2.31 Continue`.
2. **Модель завантаження за посиланням (Package Pull):** Сервер LwM2M записує текстовий URL у ресурс `/5/0/1` (наприклад, `coaps://fota.server.com/firmware_v2.bin` або `https://cdn.iot.com/fw.bin`). Клієнт переходить у стан `DOWNLOADING`, самостійно встановлює з'єднання із зазначеним хостом, викачує образ блоками, а після завершення перевіряє цілісність і переходить у стан `DOWNLOADED`.

#### Двобанкова архітектура та захист від збоїв (Dual-Bank Flash Architecture)

Для забезпечення відмовостійкості на рівні заліза мікроконтролер конфігурується з двома незалежними банками флеш-пам'яті (Slot 0 та Slot 1) під керуванням надійного завантажувача (наприклад, MCUboot):

```
+-----------------------------------------------------------+
|               Bootloader (Захищений сектор)                |
+-----------------------------------------------------------+
| Slot 0 (Active Flash Bank):  Поточна робоча прошивка v1.0 |
+-----------------------------------------------------------+
| Slot 1 (Secondary Flash Bank): Буфер завантаження v2.0    |
+-----------------------------------------------------------+
| Scratch / NVM: Таблиця статусів, лічильники епохи, ключі  |
+-----------------------------------------------------------+
```

1. Під час фази `DOWNLOADING` клієнт LwM2M записує вхідні блоки CoAP Block1 безпосередньо у `Slot 1`. Робочий код у `Slot 0` продовжує виконуватися без зупинки сенсорних задач.
2. Коли завантаження завершено, клієнт обчислює криптографічний хеш SHA-256 та перевіряє асиметричний цифровий підпис (ECDSA P-256 або Ed25519) зашитим відкритим ключем виробника. Якщо підпис коректний, клієнт переходить у стан `DOWNLOADED (2)`.
3. Отримавши команду `Execute /5/0/2`, клієнт записує у сектор Scratch прапорець `BOOT_TEST_IMAGE` і викликає апаратне перезавантаження.
4. Завантажувач Bootloader перевіряє образ у `Slot 1` і виконує атомарну перестановку блоків (In-place Swap) або перемикає стартову адресу на `Slot 1`.
5. Після старту нової прошивки клієнт LwM2M запускає процедуру самодіагностики периферії. Якщо все працює коректно, клієнт підтверджує успіх записом у завантажувач прапорця `BOOT_OK`, встановлює стан `State = 0 (IDLE)` та результат `Update Result = 1 (Success)`. Якщо ж прошивка зависає або скидається за сторожовим таймером до виставлення прапорця `BOOT_OK`, завантажувач автоматично відкочує систему назад на стабільний образ зі `Slot 0`.

### Реалізація LwM2M клієнтського рушія на мікроконтролері

Розглянемо практичну реалізацію ядра клієнта LwM2M на C та C++ для вбудованої платформи. Програма реалізує реєстр об'єктів, диспетчеризацію REST-запитів CoAP до відповідних ресурсів та автомат перевірки умов спостереження Observe.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>
#include <string.h>

#define LWM2M_URI_MAX_DEPTH 4

/* Типи операцій над ресурсом */
typedef enum {
    LWM2M_OP_READ    = 0x01,
    LWM2M_OP_WRITE   = 0x02,
    LWM2M_OP_EXECUTE = 0x04
} lwm2m_operation_t;

/* Типи даних ресурсу */
typedef enum {
    LWM2M_TYPE_STRING,
    LWM2M_TYPE_INTEGER,
    LWM2M_TYPE_FLOAT,
    LWM2M_TYPE_BOOLEAN,
    LWM2M_TYPE_OPAQUE,
    LWM2M_TYPE_EXEC
} lwm2m_data_type_t;

/* Структура опису ресурсу */
typedef struct lwm2m_resource_s {
    uint16_t id;
    uint8_t operations; /* Бітова маска lwm2m_operation_t */
    lwm2m_data_type_t type;
    union {
        int64_t integer;
        float float_val;
        bool boolean;
        const char *string;
        struct {
            const uint8_t *data;
            size_t length;
        } opaque;
        void (*exec_handler)(void);
    } value;
} lwm2m_resource_t;

/* Структура екземпляра об'єкта */
typedef struct lwm2m_instance_s {
    uint16_t instance_id;
    size_t resource_count;
    lwm2m_resource_t *resources;
} lwm2m_instance_t;

/* Структура об'єкта LwM2M */
typedef struct lwm2m_object_s {
    uint16_t object_id;
    size_t instance_count;
    lwm2m_instance_t *instances;
} lwm2m_object_t;

/* Приклад обробника команди перезавантаження */
static void reboot_hardware(void) {
    /* Виклик системного скидання або запуск Watchdog */
}

/* Статична ініціалізація ресурсів Об'єкта 3 (Device) */
static lwm2m_resource_t device_resources[] = {

    for (size_t o = 0; o < REGISTRY_SIZE; o++) {
        if (client_registry[o].object_id != obj_id) continue;
        for (size_t i = 0; i < client_registry[o].instance_count; i++) {
            if (client_registry[o].instances[i].instance_id != inst_id) continue;
            for (size_t r = 0; r < client_registry[o].instances[i].resource_count; r++) {
                lwm2m_resource_t *res = &client_registry[o].instances[i].resources[r];
                if (res->id == res_id) {
                    if (res->operations & LWM2M_OP_READ) {
                        *out_res = *res;
                        return true;
                    }
                    return false; /* Заборонено для читання */
                }
            }
        }
    }
    return false; /* Не знайдено */
}

    for (size_t o = 0; o < REGISTRY_SIZE; o++) {
        if (client_registry[o].object_id != obj_id) continue;
        for (size_t i = 0; i < client_registry[o].instance_count; i++) {
            if (client_registry[o].instances[i].instance_id != inst_id) continue;
            for (size_t r = 0; r < client_registry[o].instances[i].resource_count; r++) {
                lwm2m_resource_t *res = &client_registry[o].instances[i].resources[r];
                if (res->id == res_id) {
                    if ((res->operations & LWM2M_OP_EXECUTE) && res->value.exec_handler) {
                        res->value.exec_handler();
                        return true;
                    }
                    return false;
                }
            }
        }
    }
    return false;
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <string_view>
#include <span>
#include <optional>
#include <variant>
#include <functional>
#include <array>

namespace lwm2m {

enum class Operation : uint8_t {
    Read    = 0x01,
    Write   = 0x02,
    Execute = 0x04
};

constexpr Operation operator|(Operation a, Operation b) noexcept {
    return static_cast<Operation>(static_cast<uint8_t>(a) | static_cast<uint8_t>(b));
}

constexpr bool has_op(Operation mask, Operation query) noexcept {
    return (static_cast<uint8_t>(mask) & static_cast<uint8_t>(query)) != 0;
}

using ExecHandler = void(*)();

using ResourceValue = std::variant<
    int64_t,
    float,
    bool,
    std::string_view,
    std::span<const uint8_t>,
    ExecHandler
>;

struct Resource {
    uint16_t id{0};
    Operation ops{Operation::Read};
    ResourceValue value{};
};

struct Instance {
    uint16_t id{0};
    std::span<Resource> resources{};
};

struct Object {
    uint16_t id{0};
    std::span<Instance> instances{};
};

class ClientEngine {
public:
    explicit constexpr ClientEngine(std::span<Object> registry) noexcept : registry_(registry) {}

    [[nodiscard]] std::optional<ResourceValue> read(uint16_t obj_id, uint16_t inst_id, uint16_t res_id) const noexcept {
        const auto* res = find_resource(obj_id, inst_id, res_id);
        if (res != nullptr && has_op(res->ops, Operation::Read)) {
            return res->value;
        }
        return std::nullopt;
    }

    [[nodiscard]] bool execute(uint16_t obj_id, uint16_t inst_id, uint16_t res_id) const noexcept {
        const auto* res = find_resource(obj_id, inst_id, res_id);
        if (res != nullptr && has_op(res->ops, Operation::Execute)) {
            if (std::holds_alternative<ExecHandler>(res->value)) {
                auto handler = std::get<ExecHandler>(res->value);
                if (handler != nullptr) {
                    handler();
                    return true;
                }
            }
        }
        return false;
    }

private:
    [[nodiscard]] const Resource* find_resource(uint16_t obj_id, uint16_t inst_id, uint16_t res_id) const noexcept {
        for (const auto& obj : registry_) {
            if (obj.id != obj_id) continue;
            for (const auto& inst : obj.instances) {
                if (inst.id != inst_id) continue;
                for (const auto& res : inst.resources) {
                    if (res.id == res_id) return &res;
                }
            }
        }
        return nullptr;
    }

    std::span<Object> registry_;
};

} // namespace lwm2m
```

### Практичні пастки, безпека та оптимізація енергоспоживання

При розгортанні клієнтів LwM2M на реальних об'єктах виникає низка специфічних апаратних та мережевих викликів:

1. **Режими сну PSM та eDRX у стільникових мережах:**
   У мережах NB-IoT/Cat-M1 пристрій може переходити у режим енергозбереження PSM (Power Saving Mode) на години чи дні, повністю вимикаючи радіомодем. У цьому стані сервер не може надіслати `GET` чи `POST` запит до клієнта. Для цього стандарт LwM2M вводить параметр зв'язування з чергою (`Binding = UQ`): сервер буферизує всі команди керування та скидає їх клієнту лише тоді, коли клієнт сам прокидається і надсилає пакет оновлення реєстрації `Registration Update`. Синхронізація часу життя реєстрації `Lifetime` із таймером періодичного оновлення зони 3GPP Periodic TAU (таймер T3412) дозволяє об'єднувати службовий мережевий трафік LTE з пакетом `Registration Update` в один сеанс передачі, що радикально знижує витрати енергії.
2. **Зношення флеш-пам'яті (Flash Wear-out):**
   Частий запис динамічних параметрів спостереження (`pmin`, `pmax`, `Token`, `Message ID`) у внутрішню Flash-пам'ять мікроконтролера швидко вичерпує її ресурс (зазвичай 10 000 – 100 000 циклів стирання). Поточний стан спостережень слід утримувати в енергонезалежній RAM або акумулювати записи з використанням алгоритмів вирівнювання зносу (Wear Leveling).
3. **Захист від спуфінгу та втрата контексту DTLS:**
   Якщо мікроконтролер перезавантажується після апаратного збою за сторожовим таймером, таблиця активних ключів та лічильників епохи DTLS у RAM втрачається. Клієнт зобов'язаний надіслати запит перереєстрації з повним або скороченим рукостисканням DTLS ClientHello. Якщо сервер отримує нерозшифровану датаграму з невідомим контекстом, він надсилає CoAP `RST`, що змушує клієнта ініціювати процедуру відновлення сесії.
4. **Контроль розміру блоку Blockwise при FOTA:**
   У зашумлених радіоканалах розмір блоку `Block1` чи `Block2` слід динамічно адаптувати: спроба передавати 1024-байтові блоки при слабкому сигналі RSSI спричиняє масові втрати та нескінченні повторні передачі, що виснажує батарею. Зменшення розміру блоку до 128 чи 256 байтів знижує ймовірність помилки кадру та стабілізує процедуру FOTA.
