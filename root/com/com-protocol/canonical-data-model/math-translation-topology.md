# 🧮 Математика топології трансформацій: комбінаторика, латентність і межі вигоди

Інтеграція розподілених підсистем є дискретною оптимізаційною задачею на зв'язних графах. Вибір між прямою інтеграцією «кожен-із-кожним» (Point-to-Point Full Mesh), централізованою канонічною моделлю (Canonical Hub) та федеративною кластерною топологією (Federated Context Hubs) визначається двома конфліктуючими факторами: комбінаторною вартістю підтримки адаптерів та сумарною мережевою і обчислювальною латентністю подвійної трансформації.

Нижче наведено строгий математичний аналіз складності зв'язків у графах інтеграції, виведення критичного порогу беззбитковості канонічної моделі для повнозв'язних та випадкових графів, аналіз затримок у чергах за Законом Літтла та оптимізацію розміру кластерів у федеративній архітектурі.

## Графова модель та комбінаторна складність топологій

Розглянемо систему як орієнтований граф `G = (V, E)`, де множина вершин `V` представляє автономні підсистеми (`|V| = N`), а множина орієнтованих ребер `E` представляє односпрямовані канали передачі даних. Кожне ребро `e = (u, v) ∈ E` вимагає наявності спеціалізованого програмного транслятора, який перетворює вихідний формат вершини `u` у вхідний формат вершини `v`.

### 1. Повнозв'язна топологія прямої інтеграції (Point-to-Point Mesh)

У класичній моделі прямих зв'язків кожна підсистема безпосередньо взаємодіє з кожною іншою підсистемою. Граф `G_mesh` є повним орієнтованим графом без петель (Complete Directed Graph).

Кількість спрямованих адаптерів `K_mesh` дорівнює кількості орієнтованих пар вершин:

```
K_mesh
= N · (N − 1)        [кількість впорядкованих пар (u, v) для u ≠ v]
= N² − N            [розкриття дужок: асимптотична складність O(N²)]
```

Аналіз чутливості при масштабуванні: якщо до наявної системи з `N` вузлів додається один новий `(N + 1)`-й сервіс, кількість нових адаптерів, які інженери повинні створити та протестувати, становить:

```
ΔK_mesh
= K_mesh(N + 1) − K_mesh(N)          [приріст кількості адаптерів]
= (N + 1) · N − (N² − N)             [підстановка формули]
= N² + N − N² + N                    [зведення подібних доданків]
= 2N                                 [додавання нової системи вимагає 2N адаптерів]
```

Приклад: для `N = 10` систем у роботі перебуває `90` конвертерів. Підключення 11-ї системи вимагає розробки ще `20` нових адаптерів, що створює експоненційне зростання трудовитрат інженерних команд.

### 2. Зіркоподібна топологія канонічної моделі (Canonical Hub)

У канонічній архітектурі вводиться центральна віртуальна вершина-хаб `v_cdm`, яка представляє канонічний контракт даних. Прямі зв'язки між прикладними вершинами відсутні. Кожна вершина `v_i ∈ V` має рівно два зв'язки з хабом: вхідний адаптер (Local → Canonical) та вихідний адаптер (Canonical → Local).

Граф `G_cdm` є дводольним зіркоподібним деревом (Star Tree) із діаметром `D = 2`.

Загальна кількість адаптерів у системі:

```
K_cdm
= 2 · N             [рівно 2 адаптери на кожну з N систем: лінійна складність O(N)]
```

Приріст кількості адаптерів при додаванні нового сервісу стає константною величиною, незалежною від поточного масштабу системи:

```
ΔK_cdm
= K_cdm(N + 1) − K_cdm(N)            [приріст кількості адаптерів]
= 2 · (N + 1) − 2 · N                [підстановка формули]
= 2                                  [константна складність O(1)]
```

### 3. Строге виведення точки беззбитковості (Threshold N)

Знайдемо критичне число систем `N*`, за якого витрати на розробку та підтримку канонічної моделі стають строго меншими за витрати на пряму інтеграцію.

Нехай вартість розробки та супроводу одного адаптера становить `c_a`, а додаткові фіксовані витрати на проектування та управління канонічною схемою становлять `C_schema`.

Функції сумарної вартості:
- Для прямої інтеграції: `Cost_mesh(N) = c_a · (N² − N)`
- Для канонічної моделі: `Cost_cdm(N) = c_a · 2N + C_schema`

Розв'яжемо нерівність `Cost_mesh(N) > Cost_cdm(N)`:

```
c_a · (N² − N) > c_a · 2N + C_schema
N² − N > 2N + (C_schema / c_a)       [ділення на вартість адаптера c_a]
N² − 3N − (C_schema / c_a) > 0       [перенесення всіх доданків ліворуч]
```

Для випадку, коли витрати на проектування схеми порівнянні з розробкою кількох адаптерів (`C_schema / c_a ≈ 0`):

```
N · (N − 3) > 0                      [факторизація за C_schema = 0]
N > 3                                [оскільки N > 0 для реальних систем]
```

Висновки для різного масштабу систем:
- **`N = 2`**: `K_mesh = 2`, `K_cdm = 4`. Пряма інтеграція вигідніша вдвічі. Створення канонічної моделі для двох систем є надлишковим ускладненням.
- **`N = 3`**: `K_mesh = 6`, `K_cdm = 6`. Точка паритету складності.
- **`N = 4`**: `K_mesh = 12`, `K_cdm = 8`. Канонічна модель скорочує кількість адаптерів на 33%.
- **`N = 10`**: `K_mesh = 90`, `K_cdm = 20`. Зменшення кількості адаптерів у 4.5 раза (економія 78% зусиль).
- **`N = 50`**: `K_mesh = 2450`, `K_cdm = 100`. Зменшення кількості адаптерів у 24.5 раза.

## Модель несиметричної випадкової зв'язності (Erdős–Rényi Random Graph)

У реальних корпоративних ландшафтах зв'язки рідко утворюють повний граф: не кожен сервіс спілкується з кожним іншим. Розглянемо модель випадкового графа Ердьоша–Реньї `G(N, p)`, де кожне потенційне спрямоване ребро між двома підсистемами існує з незалежною ймовірністю `p ∈ (0, 1]`.

Математичне сподівання кількості необхідних адаптерів у прямому меші:

```
E[K_mesh(p)]
= p · N · (N − 1)    [математичне сподівання кількості ребер у графі G(N, p)]
```

У канонічній моделі кожен із `N` сервісів повинен мати 2 адаптери для підключення до шини:

```
K_cdm = 2 · N
```

Знайдемо критичну щільність зв'язків `p*`, починаючи з якої впровадження канонічної моделі стає вигіднішим за пряму інтеграцію:

```
E[K_mesh(p)] > K_cdm
p · N · (N − 1) > 2 · N              [підстановка математичних сподівань]
p · (N − 1) > 2                      [ділення на N за умови N > 0]
p > 2 / (N − 1)                      [ділення на (N − 1)]
```

### Аналіз критичної щільності для різної кількості сервісів:

```
p*(N) = 2 / (N − 1)
```

- При `N = 5`: `p* = 2 / 4 = 0.500` (достатньо, щоб 50% систем взаємодіяли між собою);
- При `N = 10`: `p* = 2 / 9 ≈ 0.222` (якщо більше 22.2% систем спілкуються, CDM вигідніша);
- При `N = 20`: `p* = 2 / 19 ≈ 0.105` (поріг становить лише 10.5% зв'язків);
- При `N = 100`: `p* = 2 / 99 ≈ 0.020` (якщо хоча б 2% систем мають спільні потоки даних, канонічна модель дає колосальну економію інженерних ресурсів).

Це доводить: чим більша система, тим менша зв'язність потрібна для того, щоб канонічна модель стала абсолютно домінуючим рішенням.

## Федеративна кластеризована топологія (DDD Bounded Contexts)

Коли кількість сервісів перевищує кілька десятків (`N > 30`), єдина глобальна канонічна модель стає організаційним вузьким місцем. Оптимальним рішенням є розбиття системи на `C` кластерів (обмежених контекстів Bounded Contexts), де кожен кластер `j` містить `M_j` споріднених сервісів (`∑ M_j = N`).

Усередині кожного кластеру діє локальна канонічна модель (Published Language домену), а між кластерами обмін відбувається через міждоменні антикорупційні мости.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                   КЛАСТЕРНА ТОПОЛОГІЯ ФЕДЕРАТИВНОЇ CDM                      │
├─────────────────────────────────────────────────────────────────────────────┤
│ Кількість контекстів: C                                                     │
│ Розмір контекстів   : M_1, M_2, ..., M_C (сума M_j = N)                     │
│                                                                             │
│ Внутрішньодоменні адаптери  : K_intra = 2 · ∑ M_j = 2 · N                   │
│ Міждоменні мости (Full Mesh): K_inter = C · (C − 1)                         │
│                                                                             │
│ Загальна кількість зв'язків : K_fed = 2 · N + C · (C − 1)                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Оптимізація кількості кластерів

Якщо припустити симетричний поділ на `C` однакових кластерів по `M = N / C` сервісів у кожному, то сумарна складність системи дорівнює:

```
K_fed(C) = 2 · N + C² − C
```

Для системи з `N = 100` мікросервісів, розбитих на `C = 8` предметних доменів:
- Пряма інтеграція: `100 · 99 = 9900` адаптерів (інженерний колапс);
- Єдина глобальна модель: `200` адаптерів (семантичний колапс схеми);
- Федеративна модель: `2 · 100 + 8 · 7 = 200 + 56 = 256` адаптерів.

Федеративна топологія вимагає лише на 28% більше адаптерів, ніж глобальна модель, але повністю усуває блокування команд та забезпечує повну автономію предметних областей.

## Модель латентності та теорія масового обслуговування

Перевага канонічної моделі в обслуговуванні компенсується додатковими обчислювальними накладними витратами часу виконання. У прямій взаємодії відбувається одна серіалізація та одна десеріалізація. У канонічній моделі повідомлення проходить подвійну трансформацію.

Сумарна затримка наскрізної доставки повідомлення:

```
T_direct = T_ser(Src) + T_net + T_deser(Dst)

T_cdm = T_deser(Src) + T_map(Src→CDM) + T_val(CDM) + T_ser(CDM) + T_broker + T_deser(CDM) + T_map(CDM→Dst) + T_ser(Dst)
```

Де:
- `T_deser(Src)` — час парсингу вихідного формату джерела (розбір JSON/XML: `20–150 мкс`);
- `T_map(Src→CDM)` — час роботи антикорупційного мапінгу в пам'яті (`5–15 мкс`);
- `T_val(CDM)` — час перевірки схеми та інваріантів у пам'яті (`10–30 мкс`);
- `T_ser(CDM)` — час пакування в канонічний бінарний Protobuf/Avro (`5–15 мкс`);
- `T_broker` — затримка збереження та вичитування в брокері повідомлень (Kafka/RabbitMQ: `500–2500 мкс`);
- `T_deser(CDM)` — час десеріалізації канонічного формату одержувачем (`5–15 мкс`);
- `T_map(CDM→Dst)` — час проекції на цільовий контракт клієнта (`5–15 мкс`);
- `T_ser(Dst)` — час фінальної серіалізації або збереження (`10–50 мкс`).

### Затримка в чергах масового обслуговування (Модель M/M/1 та Закон Літтла)

Якщо централізований вузол трансляції або брокер обробляє вхідний потік повідомлень з інтенсивністю `λ` (повідомлень на секунду), а середня швидкість обробки процесором становить `μ` (повідомлень на секунду), то коефіцієнт завантаження системи становить:

```
ρ = λ / μ            [коефіцієнт завантаження каналу обслуговування]
```

Середній час очікування повідомлення в черзі до початку трансляції `W_q` за формулою Хінчина-Поллачека для системи `M/M/1`:

```
W_q
= ρ / (μ · (1 − ρ))  [середній час у черзі перед обробкою]
= λ / (μ · (μ − λ))  [підстановка ρ = λ / μ]
```

За Законом Літтла середня кількість повідомлень у черзі `L_q`:

```
L_q = λ · W_q = ρ² / (1 − ρ)
```

Коли інтенсивність навантаження наближається до пропускної здатності хабу (`ρ → 1`), час очікування в черзі зростає гіперболічно (`W_q → ∞`).

Саме тому в сучасних архітектурах вхідну та вихідну трансляцію виконують децентралізовано — безпосередньо на вузлах продюсерів та консюмерів (у пам'яті процесів або через локальні Sidecar-контейнери), уникаючи концентрації обчислень у єдиному центральному вузлі.

### Дисперсія затримки (Jitter) та хвостові перцентилі (P99)

У розподілених системах критичною метрикою є не середній час відгуку, а затримка 99-го перцентиля (P99 Latency). За теоремою про дисперсію суми незалежних випадкових величин:

```
Var(T_cdm) = Var(T_deser1) + Var(T_map1) + Var(T_val) + Var(T_ser1) + Var(T_broker) + Var(T_deser2) + Var(T_map2) + Var(T_ser2)
```

Оскільки обчислення в пам'яті (C++ мапінг та валідація) мають практично детермінований час виконання (`Var(T_map) ≈ 0`), основний внесок у варіативність вносить брокер повідомлень (`Var(T_broker)`). Використання швидких бінарних форматів (Protobuf) знижує навантаження на мережу та Garbage Collector, зменшуючи хвостові затримки P99 у кілька разів.

### Підсумок компромісу латентності

Накладна затримка децентралізованого канонічного перетворення `ΔT_overhead`:

```
ΔT_overhead ≈ 2 · T_map + T_val + T_ser(CDM) + T_deser(CDM) ≈ 35–90 мкс
```

Для типових бізнес-додатків, де мережевий RTT становить `2–20 мс`, додаткові `50 мкс` становлять менше `0.5–2%` загального часу відгуку, що робить канонічну модель оптимальним інженерним вибором для будь-яких корпоративних систем із кількістю вузлів `N ≥ 4`.
