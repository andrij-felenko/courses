# 📋 Специфікація канонічного конверта й контрактів схеми

У розподілених корпоративних системах та подієво-орієнтованих архітектурах успіх інтеграції залежить від чіткого розмежування транспортних метаданих та прикладного корисного навантаження. Ця специфікація визначає структуру канонічного конверта повідомлення (англ. *Canonical Message Envelope*), уніфіковану таксономію полів трасування, протокол валідації сумісності схем та інтерфейси двосторонніх трансляторів.

Специфікація сумісна з міжнародним промисловим стандартом **CloudEvents v1.0** і оптимізована для використання з бінарними протоколами (Protocol Buffers v3, Apache Avro) та людиночитними форматами (JSON Schema).

## Архітектурне призначення канонічного конверта

Канонічний конверт є стандартизованою обгорткою, яка інкапсулює будь-яке доменне повідомлення (подію, команду чи документ) під час його передачі через розподілену інтеграційну шину, брокери повідомлень або мережеві шлюзи. Головна мета конверта полягає в тому, щоб надати інфраструктурним компонентам системи всю необхідну інформацію для безпечного транспортування, маршрутизації, фільтрації, аудиту та дедуплікації без необхідності десеріалізації та аналізу внутрішнього бізнес-навантаження.

Коли брокер повідомлень (наприклад, Apache Kafka чи RabbitMQ) отримує пакет розміром у кілька кілобайтів, розбір всього внутрішнього дерева об'єктів для зчитування ідентифікатора замовлення чи типу події призвів би до колосального падіння пропускної здатності. Конверт розміщує критичні маршрутизаційні метадані у фіксованій структурі заголовків, дозволяючи фільтрам та маршрутизаторам ухвалювати рішення за константний час `O(1)`.

Канонічне повідомлення складається з двох суворо ізольованих секцій:
1. **Канонічний заголовок (`headers`)**: обов'язкові інваріантні метадані для маршрутизації, дедуплікації, аудиту, трасування та перевірки версії схеми. Заголовки обробляються інфраструктурними компонентами без звернення до бізнес-полів.
2. **Канонічне корисне навантаження (`payload`)**: типізований доменний об'єкт бізнес-події або команди, що інтерпретується виключно кінцевими прикладними сервісами.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    КАНОНІЧНИЙ КОНВЕРТ ПОВІДОМЛЕННЯ (CDM)                    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. СЕКЦІЯ ЗАГОЛОВКІВ (CANONICAL HEADERS)                                    │
│    ├── message_id        : UUIDv7 (унікальний ідентифікатор із часовим сортуванням)
│    ├── correlation_id    : UUIDv4 (наскрізний ідентифікатор ланцюжка запитів)
│    ├── causation_id      : UUIDv7 / string (ідентифікатор повідомлення-причини)
│    ├── schema_version    : string SemVer ("2.1.0")                          │
│    ├── schema_urn        : string URI ("urn:proto:billing.order.created:v2")│
│    ├── timestamp_utc_ms  : int64 (Unix Epoch у мілісекундах)                │
│    ├── producer_id       : string ("service:checkout-api:eu-west-1")        │
│    ├── tenant_id         : string (ідентифікатор клієнта мультиаренди)      │
│    └── traceparent       : string (W3C Trace Context 16-byte/8-byte hex)    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. СЕКЦІЯ КОРИСНОГО НАВАНТАЖЕННЯ (CANONICAL PAYLOAD)                        │
│    ├── aggregate_id      : string (ключ партиціонування в Kafka / брокері)  │
│    ├── event_type        : string ("OrderCreated", "PaymentCaptured")       │
│    └── data              : Strongly-Typed Domain Entity (JSON / Protobuf)   │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Таксономія метаданих конверта

Кожне поле заголовка виконує строго визначену інженерну функцію в розподіленому середовищі:

### 1. Ідентифікація та причинно-наслідковий зв'язок (Causality Graph)

У складних асинхронних системах обробка одного запиту користувача породжує дерево пов'язаних подій. Для відновлення повної картини взаємодії використовуються три взаємодоповнюючі ідентифікатори:
- **`message_id`**: глобально унікальний ідентифікатор конкретного фізичного повідомлення. Рекомендується генерація за стандартом UUIDv7, де старші 48 біт кодують час створення. Це забезпечує природне сортування за часом у сховищах та журналах. Слугує первинним ключем для сховищ ідемпотентності та фільтрів дедуплікації споживачів.
- **`correlation_id`**: незмінний ідентифікатор наскрізної бізнес-операції. Створюється точкою входу (API Gateway або клієнтським додатком) і без змін передається через усі наступні сервіси, черги та фонові задачі. Дозволяє знайти всі логи операції в системі централізованого моніторингу (Elasticsearch, OpenSearch, Loki).
- **`causation_id`**: ідентифікатор безпосереднього повідомлення-попередника. Якщо мікросервіс складського обліку отримав подію `OrderPaid` з `message_id = A` і у відповідь згенерував подію `InventoryReserved` з `message_id = B`, то в новому повідомленні `causation_id` буде встановлено у значення `A`. Це дозволяє автоматично реконструювати орієнтований граф причинності всього бізнес-процесу при аудиті.

### 2. Версіонування схеми та ідентифікація контракту

- **`schema_version`**: семантична версія контракту у форматі `MAJOR.MINOR.PATCH` за правилами SemVer. Споживач перевіряє `MAJOR` версію для швидкого визначення можливості коректного розбору вмісту.
- **`schema_urn`**: глобальний унікальний ідентифікатор схеми в корпоративному Реєстрі схем (Schema Registry). Має вигляд `urn:schemas:domain:entity:version`. Дозволяє динамічним консюмерам завантажити відповідний дескриптор схеми для десеріалізації.

### 3. Часові мітки та походження

- **`timestamp_utc_ms`**: точний час фіксації події продюсером у мілісекундах від початку епохи Unix (1 січня 1970 року, UTC). Використання абсолютного цілочисельного значення ліквідує будь-які помилки парсингу локальних текстових рядків часу та забезпечує коректність математичних порівнянь.
- **`producer_id`**: службовий ідентифікатор сервісу-відправника з зазначенням екземпляра або географічного регіону розгортання (наприклад, `svc:order-checkout:eu-central-1a`).
- **`tenant_id`**: необов'язковий рядок, що визначає приналежність даних конкретному орендарю в мультиарендних архітектурах (Multi-Tenancy), що критично для ізоляції даних та маршрутизації за політиками безпеки.

### 4. Наскрізне розподілене трасування

- **`traceparent`**: стандартний заголовок контексту трасування згідно зі специфікацією W3C Trace Context. Має фіксований шістнадцятковий формат із чотирьох полів: `version-trace_id-parent_id-trace_flags` (наприклад, `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`). Забезпечує безшовну інтеграцію з системами розподіленого трасування (OpenTelemetry, Jaeger, Zipkin, AWS X-Ray) незалежно від того, якою мовою написані окремі сервіси.

## Відображення на стандарт CloudEvents v1.0

Для забезпечення сумісності з міжнародними хмарними екосистемами (Knative, AWS EventBridge, Azure Event Grid, Google Cloud Eventarc) канонічний конверт прямо відображається на атрибути специфікації CloudEvents v1.0:

| Канонічне поле CDM | Атрибут CloudEvents v1.0 | Опис відображення |
| :--- | :--- | :--- |
| `message_id` | `id` | Пряме копіювання унікального ідентифікатора події |
| `producer_id` | `source` | URI джерела події (`urn:service:checkout-api`) |
| `schema_version` | `specversion` / `dataschema` | `specversion = "1.0"`, версія контракту в `dataschema` |
| `event_type` | `type` | Назва бізнес-події (`ua.enterprise.order.created.v2`) |
| `timestamp_utc_ms` | `time` | Перетворення мілісекунд у рядок ISO 8601 UTC (`RFC 3339`) |
| `schema_urn` | `dataschema` | Посилання на дескриптор у Schema Registry |
| `traceparent` | `traceparent` (extension) | Розширення розподіленого трасування W3C |
| `payload` | `data` | Бінарне або структуроване тіло доменного повідомлення |

Така уніфікація дозволяє використовувати стандартні хмарні брокери та серверлесс-тригери без написання проміжних шлюзів перекодування.

## Стандарти канонічного доменного навантаження (Payload)

Під час проектування типізованого тіла канонічного повідомлення слід керуватися непохитними правилами доменної семантики:

### 1. Моделювання грошових значень (Money Pattern)
Використання дробів із плаваючою комою суворо заборонено. Усі грошові суми моделюються або складеним об'єктом, що містить цілі одиниці та копійки окремо, або єдиним цілим 64-бітним числом у мінімальних одиницях валюти (наприклад, копійки для гривні, центи для долара США). Код валюти обов'язково передається як строге типізоване перерахування за стандартом ISO 4217.

### 2. Моделювання статусів і відкритих перерахувань (Open Enums)
При передачі перерахувань у канонічній моделі нульове значення перерахування завжди резервується під `UNSPECIFIED` або `UNKNOWN`. Це запобігає випадковому встановленню дефолтного значення через помилку ініціалізації пам'яті та забезпечує коректну обробку нових статусів старими консюмерами.

### 3. Моделювання ідентифікаторів користувачів і сутностей
У канонічному повідомленні неприпустимо використовувати локальні первинні ключі реляційних баз даних конкретного сервісу (наприклад, автоінкрементний цілочисельний `id = 1042` з таблиці `users`). Усі посилання на сутності повинні містити глобальні бізнес-ідентифікатори (глобальні UUID, податкові коди ЄДРПОУ, стандартизовані SKU товарів).

## Контракт канонічної схеми в синтаксисі Protocol Buffers v3

Protocol Buffers є рекомендованим еталонним форматом для внутрішньокластерної передачі канонічних повідомлень завдяки мінімальному розміру серіалізованого бінарного пакету та суворій контрольній типізації полів:

```protobuf
syntax = "proto3";

package canonical.integration.v2;

enum CurrencyCode {
  CURRENCY_UNSPECIFIED = 0;
  CURRENCY_UAH = 1;
  CURRENCY_USD = 2;
  CURRENCY_EUR = 3;
  CURRENCY_GBP = 4;
}

enum OrderState {
  ORDER_STATE_UNSPECIFIED = 0;
  ORDER_STATE_PENDING_PAYMENT = 1;
  ORDER_STATE_PAID = 2;
  ORDER_STATE_PROCESSING = 3;
  ORDER_STATE_SHIPPED = 4;
  ORDER_STATE_DELIVERED = 5;
  ORDER_STATE_CANCELLED = 6;
}

message CanonicalMoney {
  int64 units = 1;          // Ціла частина суми (наприклад, гривні)
  int32 cents = 2;          // Дробова частина (копійки, діапазон 0..99)
  CurrencyCode currency = 3;
}

message CanonicalLineItem {
  string sku = 1;
  uint32 quantity = 2;
  CanonicalMoney unit_price = 3;
  CanonicalMoney total_discount = 4;
}

message CanonicalCustomerInfo {
  string customer_id = 1;
  string email = 2;
  string phone_e164 = 3;    // Номер телефону в міжнародному стандарті E.164 (+380...)
  string tax_id = 4;        // ЄДРПОУ / ІПН за наявності
}

message CanonicalOrderPayload {
  string order_id = 1;
  CanonicalCustomerInfo customer = 2;
  OrderState state = 3;
  repeated CanonicalLineItem items = 4;
  CanonicalMoney grand_total = 5;
  int64 created_at_ms = 6;
}

message CanonicalEnvelope {
  // 1. Метадані конверта
  string message_id = 1;
  string correlation_id = 2;
  string causation_id = 3;
  string schema_version = 4;
  string schema_urn = 5;
  int64 timestamp_utc_ms = 6;
  string producer_id = 7;
  string tenant_id = 8;
  string traceparent = 9;

  // 2. Бізнес-навантаження
  CanonicalOrderPayload payload = 10;
}
```

## Контракт канонічної схеми в синтаксисі JSON Schema (Draft 2020-12)

Для зовнішніх REST API, Webhook-інтеграцій та клієнтських додатків використовується еквівалентний JSON Schema контракт, який валідує як обов'язкові метадані, так і обмеження на допустимі діапазони значень:

    },

      "type": "string",

## Інтерфейс трансляторів антикорупційного шару (ACL Contract)

Вхідні та вихідні транслятори повинні реалізовувати суворий інтерфейс обробки, де результат операції повертається у вигляді контейнера помилок або успішного результату (Result / Expected), виключаючи неконтрольовані падіння процесу через винятки або паніку:

```cpp
#include <string>
#include <string_view>
#include <expected>
#include <vector>
#include <cstdint>

enum class TranslationErrorCode {
    MalformedSourceSyntax,     // Помилка парсингу (битий JSON/XML/Protobuf)
    MissingRequiredField,      // Відсутній обов'язковий атрибут джерела
    SemanticTypeMismatch,      // Неможливо перетворити рядок у число/дату
    UnknownEnumerationValue,   // Статус або код не підтримується словником
    SchemaViolation,           // Порушення інваріантів схеми
    ValidationConstraintFailed // Бізнес-помилка (наприклад, від'ємна сума)
};

struct TranslationError {
    TranslationErrorCode code;
    std::string field_path;
    std::string message;
    std::string raw_value;
};

template <typename TSource, typename TTarget>
class ICanonicalTranslator {
public:
    virtual ~ICanonicalTranslator() = default;

    // Пряма трансляція: Джерело -> Канонічна модель
    virtual std::expected<TTarget, TranslationError>
    translate(const TSource& source, std::string_view correlation_id) = 0;
};
```

## Таксономія помилок трансляції та карантин

Коли вхідний транслятор стикається з пошкодженими чи невалідними даними, обробка помилки повинна відбуватися за суворим регламентом:
1. **Синтаксичні помилки (`MalformedSourceSyntax`)**: якщо пакет містить незакриті XML-теги або синтаксично некоректний JSON, повторне читання (Retry) не має сенсу. Таке повідомлення негайно відправляється в Мертву чергу (Dead Letter Queue, DLQ) із зазначенням причини відмови в діагностичних заголовках.
2. **Семантичні розбіжності (`SemanticTypeMismatch`, `UnknownEnumerationValue`)**: якщо сторонній партнер передав новий невідомий статус або невалідний формат дати, транслятор формує структуровану помилку `TranslationError`. Якщо статус не є критичним для поточної операції, адаптер може встановити значення `OrderStatus::UNKNOWN` (деградація згідно з принципом толерантності) або заблокувати обробку замовлення до ручного втручання оператора підтримки.
3. **Бізнес-порушення інваріантів (`ValidationConstraintFailed`)**: якщо сума замовлення дорівнює нулю або масив товарів є порожнім, повідомлення відхиляється як потенційна спроба шахрайства або збій логіки джерела.

## Управління життєвим циклом схеми та політика депрекації

Еволюція канонічної схеми в довгоживучих підприємствах вимагає чіткого регламенту виведення застарілих полів із експлуатації:
1. **Позначення застарілих атрибутів**: у Protobuf застосовується опція `[deprecated = true]`, а в JSON Schema — атрибут `"deprecated": true`. Це генерує попередження компілятора при збірці клієнтських додатків.
2. **Аудит споживання (Telemetry Tracking)**: за допомогою логів шлюзів та Schema Registry вимірюється кількість звернень до застарілого поля. Фізичне видалення дозволяється лише після того, як лічильник запитів упаде до нуля.
3. **Вікно виведення (Sunset Window)**: мінімальний гарантований період підтримки застарілого поля становить 180 календарних днів або 2 мажорних релізи інтеграційної шини.

## Безпека та маскування конфіденційних даних (PII)

Канонічні повідомлення проходять через спільні брокери, тому захист персональних даних (GDPR, PCI-DSS) реалізується на рівні конверта:
- Поля `phone_e164`, `email` та `tax_id` у відкритих топіках маскуються (наприклад, `+380******123`);
- Якщо сервісу потрібні повні дані для фіскалізації, використовується шифрування на рівні полів (Field-Level Encryption) із передачею сесійного ключа `encrypted_dek` у захищеному заголовку конверта.

## Правила сумісності та еволюції канонічної схеми

Усі зміни в канонічній схемі даних підлягають автоматичній перевірці в Реєстрі схем під час складання проекту (CI/CD) за трьома режимами сумісності:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                 МАТРИЦЯ ПРАВИЛ ЕВОЛЮЦІЇ КАНОНІЧНОЇ СХЕМИ                    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. ПРАВИЛО ЗВОРОТНОЇ СУМІСНОСТІ (BACKWARD COMPATIBILITY):                  │
│    • Новий код споживача (v2) зобов'язаний коректно читати старі події (v1).│
│    • Дозволено: додавати нові необов'язкові поля з дефолтним значенням.     │
│    • ЗАБОРОНЕНО: видаляти обов'язкові поля з контракту або змінювати їх тип.│
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. ПРАВИЛО ПРЯМОЇ СУМІСНОСТІ (FORWARD COMPATIBILITY):                       │
│    • Старий код споживача (v1) зобов'язаний читати нові повідомлення (v2).  │
│    • Реалізація: патерн Tolerant Reader — старий код просто ігнорує нові    │
│      незнайомі йому XML-теги, JSON-ключі чи нові Protobuf-теги.             │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. ПОВНА СУМІСНІСТЬ (FULL COMPATIBILITY):                                   │
│    • Одночасне дотримання зворотної та прямої сумісності. Гарантує, що      │
│      сервіси можна розгортати та оновлювати в довільному порядку без зупинки│
│      інтеграційної шини та без створення аварійного стану.                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

Будь-яка незворотна зміна (Breaking Change), наприклад зміна семантики поля `order_id` з простого рядка на складений об'єкт, вимагає обов'язкового створення нової мажорної версії схеми (`v3.0.0`), відкриття нового окремого топіка в шині повідомлень та паралельної роботи обох версій протягом усього періоду міграції підсистем.
