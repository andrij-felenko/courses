# 📜 Від DDE та OLE до COM, DCOM і WinRT: як народжувалася компонентна архітектура

Наприкінці 1980-х років корпорація Microsoft зіткнулася з проблемою, яка загрожувала зупинити розвиток операційної системи Windows як платформи для складного прикладного програмного забезпечення. Користувачі вимагали безшовної інтеграції між додатками: електронна таблиця мала вбудовуватися в текстовий документ і автоматично перераховувати підсумки, коли змінювалися вихідні клітинки. Проте в архітектурі Windows 2.0 і 3.0 не існувало жодного уніфікованого механізму взаємодії між незалежними бінарними модулями.

Першою спробою розв'язати цю проблему став протокол **DDE** (англ. *Dynamic Data Exchange*), впроваджений 1987 року в Windows 2.0. DDE використовував систему віконних повідомлень Windows (`WM_DDE_INITIATE`, `WM_DDE_DATA`, `WM_DDE_ACK`) та спільні блоки оперативної пам'яті (Global Atom Table) для передачі текстових рядків між вікнами. Протокол страждав від фатальних архітектурних вад:
- **Асинхронний хаос:** Оскільки виклики проходили крізь спільну чергу повідомлень графічного інтерфейсу, зависання одного процесу або модальне діалогове вікно повністю блокувало передачу даних усій системі.
- **Відсутність типізації:** Дані передавалися як сирі текстові буфери, що вимагало ручного парсингу та призводило до частих помилок приведення типів.
- **Взаємні блокування (Deadlocks):** Кільцеві залежності між двома додатками, що надсилали один одному синхронні DDE-повідомлення, неминуче спричиняли зависання обох програм.

## Поява складених документів та глухий кут OLE 1.0

1991 року Microsoft випустила специфікацію **OLE 1.0** (англ. *Object Linking and Embedding*). OLE 1.0 зосередилася на концепції складеного документа (Compound Document): документ Word міг містити «об'єкт» таблиці Excel. Коли користувач двічі клацав на таблицю, операційна система запускала окреме вікно Excel, блокуючи редагування Word.

Фундаментальна слабкість OLE 1.0 полягала в тому, що її було побудовано поверх того самого нестабільного механізму DDE. Архітектура не мала чіткого розмежування на інтерфейси, а вся логіка спиралася на складні макроси та приватні угоди між розробниками Microsoft Office. Інженерні команди всередині самої Microsoft дійшли висновку, що OLE 1.0 неможливо масштабувати за межі простого вбудовування графіки.

## Революція Тоні Вільямса: народження чистого бінарного стандарту

У грудні 1988 року архітектор Microsoft **Тоні Вільямс** (Tony Williams) спільно з Бобом Аткінсоном (Bob Atkinson) написав внутрішній дослідницький документ під назвою *«Object Architecture: Dealing with the Unknown – or – Type Safety in a Dynamically Extensible Class Library»* (звідки виникло ім'я `IUnknown`). Вільямс сформулював принципово нову для індустрії ідею:
1. **Інтерфейс — це чистий бінарний контракт у пам'яті**, а не клас конкретної мови програмування.
2. Об'єкт може реалізовувати **декілька незалежних інтерфейсів**, кожен з яких відповідає за окремий аспект поведінки.
3. Клієнтський код ніколи не працює з екземпляром об'єкта напряму, а лише отримує вказівник на **віртуальну таблицю методів (vtable)**.
4. Життєвий цикл об'єкта має контролюватися самим об'єктом за допомогою **підрахунку посилань**.

Цей маніфест заклав підґрунтя інтерфейсу `IUnknown` з його трьома фундаментальними методами: `QueryInterface`, `AddRef` та `Release`. Специфікація отримала назву **COM** (англ. *Component Object Model*) і була офіційно представлена 1993 року разом із релізом OLE 2.0.

У релізі OLE 2.0 вбудовування об'єктів стало безшовним (In-Place Editing / Visual Editing): подвійний клік на таблицю Excel всередині документа Word більше не відкривав нове вікно, а безпосередньо замінював панелі інструментів і меню у вікні Word на елементи керування Excel. Це стало можливим завдяки прямим бінарним викликам через vtable між модулями в пам'яті, що працювали зі швидкістю виклику звичайної функції C++.

## Проєкт Cairo та вихід у розподілений світ: DCOM

У середині 1990-х років Microsoft розробляла амбітний проєкт операційної системи наступного покоління під кодовою назвою **Cairo**. Ключовою метою Cairo було створення повністю розподіленого об'єктно-орієнтованого середовища, де файлова система (OFs), мережеві ресурси та прикладні модулі мали спільну об'єктну модель.

Хоча проєкт Cairo так і не вийшов як окрема операційна система, його технології стали фундаментом для Windows NT 4.0. Головним досягненням стала поява 1996 року технології **DCOM** (англ. *Distributed COM*).

Архітектори Крейґ Віттенберг (Craig Wittenberg) та Дон Бокс (Don Box, автор фундаментальної праці *«Essential COM»*) реалізували в DCOM ідею **прозорості розташування (Location Transparency)**. За основу мережевого протоколу було взято стандарт DCE-RPC (Distributed Computing Environment / Remote Procedure Call), адаптований під об'єктну парадигму (MS-RPCE). Клієнт викликав методи через той самий вказівник на інтерфейс, не знаючи, де саме виконується компонент:
- у тому ж адресному просторі як DLL (In-Process);
- в іншому процесі на тій самій машині як EXE (Local Out-of-Process);
- на віддаленому сервері через локальну мережу (Remote DCOM).

Генератор коду MIDL автоматично створював проксі-бібліотеки на боці клієнта та стаби на боці сервера, які брали на себе всю серіалізацію параметрів у бінарний формат NDR (Network Data Representation).

## Ера Windows 2000 та COM+

Наприкінці 1990-х років стрімкий розвиток корпоративних веб-серверів та транзакційних систем виявив межі чистого COM. Створення надійного сервера вимагало від розробника написання величезної кількості службового коду: пулів потоків, транзакцій бази даних, авторизації ролей та керування станом.

1997 року Microsoft випустила **MTS** (англ. *Microsoft Transaction Server*), який запровадив парадигму декларативного сервісного програмування: розробник писав чисту бізнес-логіку компонента, а runtime автоматично вставляв транзакційні перехоплювачі (Context Interceptors) під час створення екземпляра.

2000 року в складі Windows 2000 технології COM та MTS були об'єднані в **COM+**. COM+ ввів:
- **Атрибутивне програмування:** Налаштування безпеки, транзакцій та черг викликів через реєстр каталогів COM+.
- **Пули екземплярів (Object Pooling):** Повторне використання важких серверних об'єктів без витрат на повторну ініціалізацію.
- **Queued Components:** Асинхронне виконання викликів через черги повідомлень MSMQ, що гарантувало доставку виклику навіть у разі падіння сервера.
- **Thread-Neutral Apartment (TNA):** Модель нейтральних апартаментів, яка усунула накладні витрати на перемикання контексту потоків під час виклику компонентів із пулу.

## Відлуння у .NET та ренесанс у WinRT

З появою 2002 року платформи .NET Framework кероване середовище CLR (Common Language Runtime) замінило сирий COM у більшості прикладних задач. Проте ядро операційної системи Windows, DirectX, аудіо-підсистема WASAPI, оболонка Windows Shell та сервери баз даних SQL Server залишилися побудованими на COM.

Для інтеграції нового та старого світів архітектори .NET розробили двосторонній міст маршалінгу:
- **RCW (Runtime Callable Wrapper):** Дозволяє коду C# викликати COM-компоненти через автоматично згенеровані проксі.
- **CCW (COM Callable Wrapper):** Перетворює будь-який керований клас .NET на повноцінний COM-об'єкт із підтримкою vtable та `IUnknown`.

2012 року в Windows 8 технологія COM пережила повноцінний ренесанс у вигляді **Windows Runtime (WinRT)**. Архітектори відмовилися від громіздких типів `VARIANT` та OLE Automation, побудувавши сучасний системний API Windows безпосередньо на фундаменті бінарного vtable ABI COM:
- Базовий інтерфейс `IInspectable` розширив `IUnknown`, додавши методи рефлексії та отримання імені типу.
- Метадані інтерфейсів стали зберігатися у компактному форматі ECMA-335 (`.winmd`).
- Моделі сучасних бібліотек C++/WinRT замінили застарілі макроси ATL на чисті шаблони C++17/20, дозволивши розробникам створювати та споживати бінарні COM-компоненти без жодних накладних витрат.

Принципи, закладені в COM понад тридцять років тому — чіткий бінарний ABI, незмінність контрактів, відокремлення інтерфейсу від реалізації та безпечний життєвий цикл — і сьогодні залишаються основою бінарної взаємодії в системному програмуванні та надихають сучасні відкриті стандарти, такі як WebAssembly Component Model.
