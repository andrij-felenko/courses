# 📋 Довідник заголовків і статус-кодів узгодження вмісту

Узгодження вмісту в архітектурі HTTP спирається на строгу граматику полів заголовків запиту та відповіді, формалізовану стандартом RFC 9110 («HTTP Semantics»). Заголовки цієї групи визначають обов'язковий контракт між клієнтом, проміжними вузлами (проксі-серверами, кешами, шлюзами безпеки, балансувальниками) та сервером-джерелом щодо формату даних, мовних локалей, алгоритмів компресії та правил формування ключів кешування.

Цей довідник містить повний опис синтаксису ABNF, правил інтерпретації параметрів, класифікації дерев медіа-типів за стандартами IANA та RFC 6838, відмінностей між наскрізними та покроковими заголовками, а також детальний аналіз відповідних статус-кодів.

---

## 1. Клієнтські заголовки переваг (Request Negotiation Headers)

Клієнтські поля заголовків передають серверу інформацію про технічні можливості програмного середовища (браузера, мобільного додатку, фонового демона) та відносні пріоритети обробки різних форм представлення.

### Accept

Визначає множину допустимих типів носіїв (MIME-типів) для тіла відповіді.

```http
Accept = #( media-range [ accept-params ] )
media-range = ( "*/*"
              / ( type "/" "*" )
              / ( type "/" subtype )
              ) *( OWS ";" OWS parameter )
accept-params = weight *( OWS ";" OWS parameter )
weight = OWS ";" OWS "q=" qvalue
qvalue = ( "0" [ "." 0*3DIGIT ] ) / ( "1" [ "." 0*3("0") ] )
```

#### Семантика параметрів та діапазонів

- **Діапазон `*/*`**: Має нульову базову специфічність. Означає готовність клієнта прийняти будь-який формат, який здатний згенерувати сервер. Використовується як універсальний запобіжник для отримання хоча б якогось результату.
- **Діапазон `type/*`**: Охоплює будь-який підтип у межах зазначеної родини медіа (наприклад, `image/*` дозволяє серверу обрати між JPEG, PNG, AVIF або WebP; `text/*` дозволяє вибір між plain, html, csv).
- **Точний тип `type/subtype`**: Максимальна точність формату (наприклад, `application/json`, `application/xml`, `text/html`).
- **Коефіцієнт якості (`q`)**: Число з плаваючою комою у діапазоні від `0.000` до `1.000` (до трьох знаків після десяткової крапки). Визначає відносну вагу переваги клієнта:
  - `q=1.0` (або відсутність параметра): Найвища пріоритетність.
  - `0 < q < 1`: Знижений пріоритет (альтернативний або запасний формат).
  - `q=0`: Категорична заборона. Якщо сервер не має інших варіантів, окрім формату з `q=0`, він зобов'язаний повернути статус `406 Not Acceptable`.
- **Параметри типу проти параметрів розширення**: Пари `key=val`, розташовані **до** параметра `q`, є параметрами самого MIME-типу (наприклад, `charset=utf-8` або `version=2`). Пари, розташовані **після** `q`, є розширеннями узгодження протоколу (accept-extension).

```http
Accept: text/html, application/xhtml+xml, application/xml;q=0.9, image/avif, image/webp, */*;q=0.8
Accept: application/vnd.company.report+json; version=2; q=1.0, application/json; q=0.5
```

### Дерева типів медіа за RFC 6838

Стандарт RFC 6838 організовує підтипи медіа у чотири ієрархічні дерева (Media Type Trees), що позначаються префіксами у назві підтипу:

1. **Стандартне дерево (Standards Tree)**: Без префікса. Типи, зареєстровані та стандартизовані IETF/IANA (наприклад, `application/json`, `text/html`, `image/png`).
2. **Вендорне дерево (Vendor Tree — `vnd.`)**: Використовується комерційними компаніями та відкритими проектами для власних спеціалізованих форматів або версіонування API (наприклад, `application/vnd.github.v3+json`, `application/vnd.ms-excel`, `application/vnd.api+json`).
3. **Персональне дерево (Personal Tree — `prs.`)**: Для експериментальних або внутрішніх некомерційних продуктів (наприклад, `application/prs.custom-data`).
4. **Незареєстроване дерево (Unregistered Tree — `x.`)**: Історичний префікс для нестандартних форматів (наприклад, `application/x-www-form-urlencoded`, `image/x-icon`). Стандартом RFC 6838 створення нових `x.` типів заборонено.

### Accept-Language

Визначає список природних мов і регіональних діалектів, зрозумілих користувачеві, за стандартом BCP 47 (RFC 5646).

```http
Accept-Language = #( language-range [ weight ] )
language-range  = ( 1*8ALPHA *( "-" 1*8ALPHANUM ) ) / "*"
```

#### Структура мовних тегів

- **Первинна мова**: 2–3 літерний код за стандартом ISO 639 (наприклад, `uk` — українська, `en` — англійська, `pl` — польська).
- **Субтеги розширення**: Додаткові кваліфікатори через дефіс:
  - Субтег регіону за ISO 3166-1 (`uk-UA`, `en-US`, `en-GB`, `pt-BR`);
  - Субтег писемності за ISO 15924 (`zh-Hant` — традиційна китайська, `zh-Hans` — спрощена китайська);
  - Субтег діалекту або варіанта (`de-CH-1996`).
- **Спеціальний символ `*`**: Відповідає будь-якій мові, не вказаній явно в інших частинах заголовка.

```http
Accept-Language: uk-UA, uk;q=0.9, en-US;q=0.8, en;q=0.7, *;q=0.1
```

### Accept-Encoding

Оголошує підтримувані клієнтом алгоритми кодування вмісту (content coding), насамперед методи компресії даних.

```http
Accept-Encoding = #( ( codings / "*" ) [ weight ] )
codings         = content-coding / "identity"
```

| Кодування | Стандарт | Характеристики та застосування |
| :--- | :--- | :--- |
| **`zstd`** | RFC 8878 | Алгоритм Zstandard від Meta. Забезпечує надзвичайно високу швидкість декомпресії при високому ступені стиснення. Сучасний стандарт для API та високонавантажених сервісів. |
| **`br`** | RFC 7932 | Алгоритм Brotli від Google. Використовує спеціалізований статичний словник для текстових ресурсів вебу (HTML, JavaScript, CSS, JSON). Працює виключно поверх захищених з'єднань HTTPS у веб-браузерах. |
| **`gzip`** | RFC 1952 | Стиснення DEFLATE у форматі GNU zip з 32-бітним заголовком і контрольною сумою CRC-32. Універсальний сумісний стандарт для всіх платформ. |
| **`deflate`** | RFC 1950 / 1951 | Стиснення zlib. Історично мав проблеми сумісності через різночитання специфікації авторами ранніх браузерів. У сучасній розробці витіснений gzip та br. |
| **`identity`** | RFC 9110 | Відсутність будь-якої компресії або трансформації (сирі байти). Вважається прийнятним за замовчуванням (`q=1.0`), якщо явно не заборонено виразом `identity;q=0`. |

```http
Accept-Encoding: zstd, br, gzip;q=0.8, *;q=0.1
```

### Відмінність між Accept-Encoding та TE

Часто виникає плутанина між заголовками `Accept-Encoding` та `TE` (Transfer-Encoding):

- **`Accept-Encoding` (наскрізне кодування, End-to-End)**: Стискає тіло представлення ресурсу на сервері джерела. Байти залишаються стисненими під час проходження через усі проміжні проксі-сервери, зберігаються в кешах і розпаковуються лише кінцевим клієнтом. Метадані фіксуються в заголовку відповіді `Content-Encoding`.
- **`TE` / `Transfer-Encoding` (покрокове кодування, Hop-by-Hop)**: Застосовується до транспортного потоку між двома безпосередніми вузлами мережі (наприклад, між клієнтом і найближчим проксі). Прикладом є блокова передача `Transfer-Encoding: chunked`. Проміжний проксі має право зняти або змінити Transfer-Encoding перед пересилкою наступному вузлу.

### Клієнтські підказки (Client Hints: Accept-CH)

Сучасним розширенням проактивного узгодження є стандарт **Client Hints** (RFC 8942). Сервер може надіслати заголовок `Accept-CH`, повідомивши клієнту, які додаткові параметри пристрою його цікавлять для адаптації контенту:

```http
Accept-CH: Sec-CH-Width, Sec-CH-DPR, Sec-CH-Viewport-Width, Sec-CH-Prefers-Color-Scheme
```

У наступних запитах браузер передає ці параметри:
- `Sec-CH-Width: 640` — ширина контейнера для зображення в пікселях;
- `Sec-CH-DPR: 2.0` — коефіцієнт щільності пікселів екрана;
- `Sec-CH-Prefers-Color-Scheme: dark` — перевага темної теми оформлення.

Сервер використовує ці підказки для динамічного масштабування зображень або генерації теми оформлення, обов'язково додаючи відповідні поля до заголовка `Vary: Sec-CH-Width, Sec-CH-DPR`.

---

### Accept-Post та Accept-Patch

Оголошують формати документів, які сервер готовий прийняти від клієнта під час надсилання змін через методи `POST` (RFC 9110) та `PATCH` (RFC 5789).

```http
Accept-Post: application/json, multipart/form-data
Accept-Patch: application/json-patch+json, application/merge-patch+json
```

Ці заголовки зазвичай повертаються сервером у відповідь на запит методу `OPTIONS` або у складі відповіді помилки `415 Unsupported Media Type`, допомагаючи клієнту обрати правильний формат тіла запиту.

## 2. Серверні заголовки метаданих представлення (Response Headers)

Ці поля заголовків супроводжують корисне навантаження відповіді, описуючи властивості обраного представлення та правила його обробки проміжними кешами.

### Content-Type

Вказує тип носія надісланого корисного навантаження та параметри його декодування.

```http
Content-Type = media-type
media-type   = type "/" subtype *( OWS ";" OWS parameter )
```

- **Параметр `charset`**: Для текстових форматів (`text/html`, `text/plain`, `application/json`) вказує кодову сторінку символів. У сучасному вебі обов'язковим значенням є `charset=utf-8`.
- **Параметр `boundary`**: Для складених багаточастинних повідомлень `multipart/form-data` визначає унікальний розділювач між блоками даних.

```http
Content-Type: application/json; charset=utf-8
Content-Type: text/html; charset=utf-8
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXyZ123
```

---

### Content-Language

Описує природну мову або мови, призначені для цільової аудиторії цього представлення.

```http
Content-Language = #language-tag
```

Заголовок вказує на мовну аудиторію всього документа в цілому. Якщо ресурс містить фрагменти іншими мовами (наприклад, підручник французької мови для україномовних студентів), значенням буде `Content-Language: uk`, оскільки цільовою аудиторією є українські читачі.

```http
Content-Language: uk-UA
Content-Language: uk, en
```

---

### Content-Encoding

Перелічує алгоритми стиснення або трансформації, застосовані до корисного навантаження.

```http
Content-Encoding = #content-coding
```

Якщо до документа було послідовно застосовано кілька алгоритмів (наприклад, стиснення tar-архіву gzip), вони перелічуються у порядку застосування, а клієнт повинен розпаковувати їх у зворотному порядку.

```http
Content-Encoding: zstd
Content-Encoding: br
Content-Encoding: gzip
```

---

### Content-Location

Містить прямий прямий ідентифікатор (URI) конкретного представлення, надісланого у відповіді.

```http
Content-Location = absolute-URI / partial-URI
```

Якщо користувач надіслав запит на загальну абстрактну адресу ресурсу `/reports/current`, а сервер виконав узгодження і віддав конкретний файл, він вказує `Content-Location: /reports/2026-q2.uk.json`. Це дозволяє клієнту дізнатися пряму постійну адресу саме цього знімка даних.

---

### Vary

Критично важливий заголовок для збереження цілісності та ізоляції проміжних кешів і мереж доставки вмісту (CDN).

```http
Vary = "*" / #( field-name )
```

- **Призначення**: Повідомляє кешувальним вузлам, які саме поля заголовків вхідного запиту вплинули на алгоритм вибору цього представлення на сервері.
- **Вплив на ключ кеша**: Кеш формує складений ідентифікатор збереження згідно з RFC 9111 (розділ 4.1):
  
  ```
  Cache-Key = ( Request-URI,  Header-1-Value,  Header-2-Value,  ... )
  ```

- **Спеціальне значення `*`**: `Vary: *` сигналізує про те, що на вибір представлення вплинули не стандартизовані HTTP-заголовки, а внутрішні непередбачувані фактори сервера (наприклад, IP-адреса, час доби, випадковий A/B тест). Таку відповідь заборонено віддавати наступним клієнтам без повторної валідації на сервері джерела.
- **Заборонені значення у Vary**: До списку `Vary` ніколи не включаються покрокові заголовки (`Connection`, `Transfer-Encoding`, `Keep-Alive`) або заголовок `Host`, оскільки вони стосуються транспорту або вже входять до базового ключа кеша.

```http
Vary: Accept
Vary: Accept-Encoding
Vary: Accept-Language, Accept-Encoding
Vary: Accept, Accept-Language, Accept-Encoding
```

## 3. Статус-коди узгодження вмісту

| Статус-код | Назва за стандартом | Роль та поведінка в узгодженні вмісту |
| :---: | :--- | :--- |
| **`200 OK`** | Успішна відповідь | Проактивне узгодження успішно виконано. Сервер обрав представлення, розмістив його в тілі відповіді та заповнив метадані (`Content-Type`, `Content-Language`, `Content-Encoding`, `Vary`). |
| **`300 Multiple Choices`** | Множинний вибір | Реактивне узгодження. Сервер повертає список доступних представлень ресурсу. Тіло містить посилання на варіанти, а заголовок `Link` може містити машиночитані посилання `rel="alternate"`. Клієнт обирає один із варіантів і робить повторний запит. |
| **`406 Not Acceptable`** | Неприйнятно | Сервер не здатний згенерувати жодне представлення, яке б задовольняло строгі обмеження заголовків `Accept-*` клієнта (і клієнт явно заборонив інші типи або не вказав `*/*`). Сервер повинен надати перелік підтримуваних форматів у тілі або заголовках. |
| **`415 Unsupported Media Type`** | Непідтримуваний тип носія | Сервер відхиляє тіло запиту клієнта (`POST`, `PUT`, `PATCH`), оскільки формат у `Content-Type` або кодування в `Content-Encoding` не підтримується кінцевим обробником. Сервер повертає `Accept-Post` або `Accept-Patch`. |

## 4. Матриця пріоритетів і специфічності (Matching Rules)

Стандарт RFC 9110 визначає чіткий алгоритм розрахунку специфічності виразів у заголовку `Accept`:

```
Базова специфічність = Кількість точних елементів шляху MIME + Наявність параметрів
```

### Таблиця ієрархії специфічності

| Ранг | Структура виразу | Приклад у заголовку Accept | Специфічність |
| :---: | :--- | :--- | :---: |
| **4** | Точний тип із параметрами | `application/json; version=2; charset=utf-8` | **3** |
| **3** | Точний тип і підтип | `application/json`, `text/html` | **2** |
| **2** | Родина підтипів (wildcard) | `text/*`, `image/*` | **1** |
| **1** | Глобальний шаблон (wildcard) | `*/*` | **0** |

### Правила вирішення суперечностей:
1. Якщо `q₁ ≠ q₂`, перемагає правило з вищим значенням `q`.
2. Якщо `q₁ == q₂`, перемагає правило з вищою базовою специфічністю.
3. Якщо `q` і специфічність збігаються, пріоритет визначається внутрішнім порядком серверної конфігурації (server preference ordering).
