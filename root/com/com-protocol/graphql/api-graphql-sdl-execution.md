# 📋 Специфікація GraphQL: синтаксис SDL, фази виконання та інтерфейс резолверів

GraphQL — це формальна специфікація мови визначення схем, граматики клієнтських запитів та алгоритму їхнього виконання на сервері. На відміну від неформальних архітектурних конвенцій, GraphQL має математично строгий стандарт, що визначає кожен крок життєвого циклу запиту: від лексичного парсингу та статичної валідації абстрактного синтаксичного дерева до структури об'єкта відповіді, спливання помилок (null propagation), правил приведення типів вхідних змінних, інтроспекції та мережевих підпротоколів реального часу.

Нижче розгорнуто формальний контракт специфікації GraphQL: правила валідації, сигнатуру функцій-резолверів, структуру AST-вузлів та потоковий протокол інкрементальної доставки даних.

---

### 1. Мова опису схем: SDL (Schema Definition Language)

Схема GraphQL визначає повний простір типів, полів та операцій, доступних клієнту. SDL — це строго типізована, людиночитабельна мова для опису графа сутностей і зв'язків між ними.

#### Базові та користувацькі скалярні типи

Скалярні типи (англ. *scalar types*, від лат. *scalaris* — «ступінчастий», базове неподільне значення) представляють листки дерева запиту. Вони не мають власних дочірніх полів і серіалізуються в примітивні значення JSON.

У специфікації визначено п'ять стандартних вбудованих скалярів:

| Скаляр | Опис і серіалізація в JSON | Приклад | Семантичні обмеження |
|---|---|---|---|
| `Int` | 32-бітне ціле число зі знаком | `42`, `-100` | Діапазон від `-2^31` до `2^31 - 1`. Дробова частина заборонена. |
| `Float` | Число з плаваючою комою подвійної точності | `3.14159`, `-0.5` | Стандарт IEEE 754. Значення `NaN` та `Infinity` заборонені в JSON. |
| `String` | Послідовність символів | `"Олена"`, `"Привіт"` | Неперервний рядок символів у кодуванні UTF-8. |
| `Boolean` | Логічне значення | `true`, `false` | Суворо бінарний тип. Числові `0`/`1` або рядки `"true"` не приводяться. |
| `ID` | Унікальний ідентифікатор сутності | `"usr_98a7c"`, `"1024"` | Серіалізується виключно як `String`. Призначений для машинної ідентифікації. |

Користувацькі скаляри оголошуються ключовим словом `scalar`. Для кожного власного скаляра розробник зобов'язаний реалізувати три функції валідації та приведення типів:
1. `serialize(value)`: перетворює внутрішній тип бекенду (наприклад, `std::chrono::system_clock::time_point` або об'єкт `Date`) у валідне JSON-значення.
2. `parseValue(jsonValue)`: перетворює сире значення з JSON-змінних запиту у внутрішній доменний тип.
3. `parseLiteral(astNode)`: парсить синтаксичний AST-вузол літерала безпосередньо з тексту запиту.

```graphql
scalar DateTime
scalar JSON
scalar BigDecimal
scalar URL
```

#### Модифікатори типів: обов'язковість і списки

За замовчуванням усі поля, аргументи та типи у GraphQL є **необов'язковими (nullable)**: вони можуть приймати значення `null`.

Специфікація визначає два модифікатори типів:
- Знак оклику `!` (Non-Null) — забороняє значення `null`.
- Квадратні дужки `[ ]` (List) — огортає тип у масив.

Модифікатори комбінуються для вираження чотирьох фундаментальних інваріантів списків:

```graphql
# 1. Поле може бути null, елементи списку можуть бути null: [ "a", null, "b" ] або null
fieldA: [String]

# 2. Поле може бути null, але якщо масив існує, всі його елементи гарантовано не-null: [ "a", "b" ] або null
fieldB: [String!]

# 3. Список завжди присутній (хоча б пустий []), але його елементи можуть бути null: [ "a", null ]
fieldC: [String]!

# 4. Найсуворіший інваріант: список завжди присутній і не містить жодного null-елемента: [ "a", "b" ] або []
fieldD: [String!]!
```

#### Об'єктні типи (Object Types)

Об'єктний тип моделює сутність графа, що містить одне або більше іменованих полів:

```graphql
type User {
  id: ID!
  name: String!
  email: String
  avatarUrl(size: Int = 64): String!
  posts(limit: Int = 10, offset: Int = 0, status: PostStatus): [Post!]!
}
```

Кожне поле може приймати список іменованих аргументів зі значеннями за замовчуванням. Аргументи поля не можуть бути об'єктними типами чи інтерфейсами — дозволені лише скаляри, переліки та вхідні типи (Input Objects).

#### Інтерфейси (Interfaces) та Об'єднання (Unions)

GraphQL підтримує поліморфізм через дві різні семантичні конструкції:

**Інтерфейс** — це абстрактний тип, що визначає обов'язковий набір спільних полів для типів, які його реалізують:

```graphql
interface Node {
  id: ID!
  createdAt: DateTime!
}

interface Timestamped {
  updatedAt: DateTime!
}

type Article implements Node & Timestamped {
  id: ID!
  createdAt: DateTime!
  updatedAt: DateTime!
  title: String!
  body: String!
}

type Comment implements Node {
  id: ID!
  createdAt: DateTime!
  content: String!
}
```

**Об'єднання (Union)** — абстрактний тип, що об'єднує кілька об'єктних типів, які не мають обов'язкових спільних полів:

```graphql
union SearchResult = User | Article | Comment
```

Правило специфікації: членами `union` можуть бути лише об'єктні типи (не інтерфейси, не інші юніони, не скаляри). Клієнт запитує поліморфні поля за допомогою вбудованих фрагментів (англ. *inline fragments*):

```graphql
query GlobalSearch($query: String!) {
  search(query: $query) {
    __typename
    ... on User {
      id
      name
    }
    ... on Article {
      id
      title
      updatedAt
    }
    ... on Comment {
      id
      content
    }
  }
}
```

#### Переліки (Enums) та Вхідні типи (Input Objects)

**Перелік (Enum)** обмежує можливі значення фіксованим набором рядкових ідентифікаторів без лапок:

```graphql
enum PostStatus {
  DRAFT
  PENDING_REVIEW
  PUBLISHED
  ARCHIVED
}
```

**Вхідний об'єкт (Input Object)** використовується виключно як тип аргументів у запитах і мутаціях:

```graphql
input CreatePostInput {
  title: String!
  body: String!
  status: PostStatus = DRAFT
  tagIds: [ID!]
}
```

Правило: поля вхідного об'єкта не можуть мати власних аргументів, не можуть бути вихідними об'єктами, інтерфейсами чи об'єднаннями.

#### Директиви (Directives)

Директива (лат. *directio* — «напрям, вказівка») додає декларативні метадані для рушія виконання, шлюзів або клієнтських компіляторів.

Вбудовані директиви специфікації:
- `@include(if: Boolean!)` — додає поле чи фрагмент у вибірку, лише якщо значення умови `true`.
- `@skip(if: Boolean!)` — виключає поле чи фрагмент із вибірки, якщо значення умови `true`.
- `@deprecated(reason: String = "No longer supported")` — позначає поле чи значення enum як застаріле.
- `@specifiedBy(url: String!)` — посилання на URL специфікації для кастомного скаляра.

Оголошення власних директив у SDL:

```graphql
directive @auth(requires: Role = USER) on FIELD_DEFINITION | OBJECT
directive @cacheControl(maxAge: Int, scope: CacheScope) on FIELD_DEFINITION | OBJECT
directive @defer(label: String, if: Boolean = true) on FRAGMENT_SPREAD | INLINE_FRAGMENT
directive @stream(label: String, initialCount: Int = 0, if: Boolean = true) on FIELD
```

#### Кореневі типи операцій (Root Operation Types)

Кожна схема GraphQL має явну точку входу — декларацію кореневих типів для трьох видів операцій:

```graphql
schema {
  query: Query
  mutation: Mutation
  subscription: Subscription
}

type Query {
  user(id: ID!): User
  feed(limit: Int = 20): [Post!]!
  node(id: ID!): Node
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): Boolean!
}

type Subscription {
  postAdded: Post!
  commentAdded(postId: ID!): Comment!
}
```

### 2. Фрагменти та правила підстановки (Fragments)

Фрагменти — це багаторазові блоки вибірки полів, прив'язані до конкретного типу. Вони усувають дублювання коду в запитах і дозволяють клієнтським UI-компонентам декларувати власні потреби в даних.

#### Іменовані фрагменти (Named Fragments)

```graphql
fragment UserAvatar on User {
  id
  name
  avatarUrl(size: 64)
}

query GetFeed {
  feed {
    id
    title
    author {
      ...UserAvatar
    }
  }
}
```

Правила валідації фрагментів:
1. **Відповідність типу (Type Condition):** Фрагмент, оголошений `on TypeA`, може розгортатися лише всередині вибірки, тип якої сумісний із `TypeA` (той самий тип, реалізація інтерфейсу або член юніону).
2. **Відсутність циклів:** Заборонені взаємні рекурсивні включення фрагментів.
3. **Усі оголошені фрагменти мають використовуватись:** Якщо в документі оголошено фрагмент, але його не включено в жодну операцію, валідатор повертає помилку `UnusedFragment`.

### 3. Структура мережевого обміну (Wire Protocol)

#### Формат запиту через HTTP POST

Стандартним транспортом для GraphQL є HTTP `POST` із заголовком `Content-Type: application/json`.

Тіло JSON-запиту містить такі поля:

```json
{
  "query": "query GetUserPosts($userId: ID!, $limit: Int!) { user(id: $userId) { name posts(limit: $limit) { id title } } }",
  "variables": {
    "userId": "42",
    "limit": 5
  },
  "operationName": "GetUserPosts"
}
```

| Ключ | Тип | Обов'язковість | Призначення |
|---|---|---|---|
| `query` | `String` | Обов'язкове | Текст GraphQL-документа (операції та фрагменти) |
| `variables` | `Object` | Необов'язкове | Словник значень змінних, переданих у запит |
| `operationName` | `String` | Необов'язкове | Назва конкретної операції для виконання, якщо документ містить кілька операцій |

Для операцій читання (`Query`) дозволено використання методу `HTTP GET`, де параметри кодуються в рядку запиту URL:

```http
GET /graphql?query=query%20%7B%20me%20%7B%20name%20%7D%20%7D HTTP/1.1
Host: api.example.com
```

#### Правила приведення типів змінних (Variable Coercion)

Коли клієнт передає змінні у JSON-об'єкті `variables`, рушій виконує процедуру приведення типів:
- Якщо змінна оголошена як `Int!`, а в JSON передано число `42` — значення валідне.
- Якщо передано число з плаваючою комою `42.5` для типу `Int` — виникає помилка валідації типів.
- Якщо змінна необов'язкова (`Int = 10`) і не передана в об'єкті змінних — рушій підставляє значення за замовчуванням `10`.
- Якщо змінна явно передана як `null` (`{ "limit": null }`) — значення за замовчуванням **не застосовується**, а поле отримує значення `null`.

#### Формат відповіді (HTTP Response)

Сервер завжди повертає JSON-об'єкт із трьома зарезервованими ключами верхнього рівня:

```json
{
  "data": {
    "user": {
      "name": "Олена",
      "posts": [
        { "id": "101", "title": "Введення в архітектуру" }
      ]
    }
  },
  "errors": [
    {
      "message": "Не вдалося отримати статистику постів",
      "locations": [{ "line": 4, "column": 7 }],
      "path": ["user", "posts", 0, "stats"],
      "extensions": {
        "code": "UNAUTHENTICATED",
        "timestamp": "2026-08-20T01:23:45Z"
      }
    }
  ],
  "extensions": {
    "tracing": {
      "version": 1,
      "duration": 14205000
    }
  }
}
```

| Ключ | Присутність і поведінка | Опис |
|---|---|---|
| `data` | Присутній, якщо хоча б одне поле успішно обчислене. Має значення `null`, якщо виникла фатальна помилка до виконання або в Non-Null кореневому полі. | Дзеркальне дерево результатів запиту |
| `errors` | Відсутній, якщо запит виконано без жодних помилок. Присутній як непорожній масив об'єктів помилок у разі збоїв. | Список виявлених помилок |
| `extensions` | Необов'язковий ключ верхнього рівня. | Довільні службові метадані сервера (трейсинг, метрики, вартість запиту) |

#### Структура об'єкта помилки (GraphQLError)

Кожен елемент масиву `errors` має чітко специфіковану форму:

1. `message` (`String`, обов'язкове): Людиночитабельний опис помилки.
2. `locations` (`Array<{ line: Int, column: Int }>`, необов'язкове): Координати символу в тексті запиту, де сталася помилка.
3. `path` (`Array<String | Int>`, необов'язкове): Точний шлях у результуючому JSON-дереві від кореня до поля, резолвер якого згенерував виняток (індекси масивів позначаються цілими числами).
4. `extensions` (`Object`, необов'язкове): Машиночитабельний словник метаданих помилки (доменний код помилки, HTTP-еквівалент, часова мітка).

#### HTTP-коди стану для GraphQL-відповідей

Оскільки GraphQL-запит може виконатися частково (частина полів повертає дані, а одне поле повертає помилку), протокол має усталену конвенцію щодо HTTP-кодів стану:
- **200 OK:** Запит синтаксично коректний і пройшов валідацію. Навіть якщо окремі резолвери згенерували винятки (помилки бізнес-логіки), відповідь повертається з кодом 200, заповненим об'єктом `data` та масивом `errors`.
- **400 Bad Request:** Запит містить синтаксичні помилки парсингу (невалідна граматика) або не пройшов статичну валідацію схеми (запитано неіснуюче поле, не передано обов'язковий аргумент). Поле `data` відсутнє.
- **500 Internal Server Error:** Критичний збій інфраструктури самого GraphQL-сервера (падіння рушія, помилка парсингу схеми).

### 4. Фази обробки та алгоритм виконання запиту

Кожен GraphQL-документ проходить через три строго послідовні фази на сервері:

```
Текст запиту ──► [ 1. Парсинг ] ──► AST-дерево
                        │
                        ▼
                  [ 2. Валідація ] ◄── Схема SDL
                        │
                        ▼
                  [ 3. Виконання ] ──► Резолвери ──► JSON-відповідь
```

#### Фаза 1: Парсинг (Lexing & Parsing)

Текст запиту розбивається на токени та перетворюється в абстрактне синтаксичне дерево (AST, англ. *Abstract Syntax Tree*).

Специфікація визначає точні типи вузлів AST:
- `DocumentNode`: корінь усього розпарсеного документа.
- `OperationDefinitionNode`: опис операції (`query`, `mutation` або `subscription`).
- `FieldNode`: конкретне поле у вибірці з його псевдонімом (alias), аргументами та директивами.
- `ArgumentNode`: аргумент, переданий полю.
- `SelectionSetNode`: набір дочірніх полів складеного об'єкта.
- `InlineFragmentNode` / `FragmentSpreadNode`: вбудовані та іменовані фрагменти вибірки.
- `VariableDefinitionNode`: оголошення змінної у сигнатурі операції.

Якщо документ містить синтаксичну помилку, виконання негайно переривається на фазі 1 із кодом HTTP 400 Bad Request і масивом `errors`.

#### Фаза 2: Валідація (Validation)

Рушій валідує побудоване AST відносно схеми SDL. Валідація відбувається **до виклику будь-якого резолвера** і гарантує виконання таких інваріантів:
1. Усі запитані поля існують у відповідних типах схеми.
2. Скалярні поля є листками (не мають власного `selectionSet`).
3. Складені типи (об'єкти, інтерфейси, юніони) обов'язково мають непорожній `selectionSet`.
4. Усі обов'язкові аргументи полів передані й сумісні за типом.
5. Оголошені змінні запиту використовуються і відповідають типам аргументів полів.
6. Фрагменти не утворюють циклічних залежностей (`FragmentA` включає `FragmentB`, а `FragmentB` включає `FragmentA`).
7. Імена операцій у документі є унікальними.

#### Фаза 3: Виконання (Execution) та контракт резолверів

Виконання починається з вибору операції за параметром `operationName`.

**Відмінність у порядку виконання:**
- `Query`: Усі поля одного рівня ієрархії обчислюються **паралельно та асинхронно**. Порядок виклику резолверів не детермінований.
- `Mutation`: Кореневі поля мутації виконуються **суворо послідовно одне за одним**. Наступне поле мутації викликається лише після повного завершення проміса попереднього. Це захищає базу даних від станів перегонів (race conditions). Дочірні поля всередині поверненого мутацією об'єкта обчислюються паралельно.

#### Сигнатура та контракт функції-резолвера

Резолвер (англ. *resolver*, від *resolve* — «розв'язувати, обчислювати») — це функція, яка повертає значення для конкретного поля конкретного типу.

Стандартна сигнатура функції-резолвера:

```typescript
function resolveField(
  source: any,
  args: Record<string, any>,
  context: ExecutionContext,
  info: GraphQLResolveInfo
): Value | Promise<Value>
```

| Параметр | Призначення та вміст |
|---|---|
| `source` (або `parent`) | Об'єкт, повернутий резолвером батьківського поля. Для кореневих полів `Query`/`Mutation` це `rootValue` (зазвичай початковий стан або `undefined`). |
| `args` | Словник аргументів, переданих цьому полю у запиті (після валідації та підстановки значень змінних). |
| `context` | Глобальний об'єкт, спільний для всіх резолверів одного HTTP-запиту. Створюється на початку запиту і містить дані автентифікації (`currentUser`), екземпляри `DataLoader`, пул підключень до БД та контекст трейсингу. |
| `info` | Метадані виконання: поточний AST-вузол поля, шлях у дереві відповіді (`info.path`), посилання на повну схему `info.schema`, набір запитаних дочірніх полів. |

#### Алгоритм завершення значення (CompleteValue) та спливання Null (Null-Bubbling)

Коли резолвер повертає сире значення, рушій виконує процедуру `CompleteValue`:
1. Якщо поле скалярне — викликається функція `serialize()` відповідного скаляра.
2. Якщо поле спискове — процедура `CompleteValue` рекурсивно викликається для кожного елемента списку.
3. Якщо поле об'єктне — для кожного поля із дочірнього `selectionSet` викликається відповідний резолвер.
4. Якщо поле є інтерфейсом або юніоном — викликається метод `__resolveType(source, context, info)`, який повертає строкову назву конкретного об'єктного типу (`String`), після чого обчислюються його поля.

**Правило спливання помилок (Null Propagation / Null-Bubbling):**
Якщо резолвер поля викидає виняток або повертає `null`:
- Якщо тип поля є **nullable** (`User`), у результуючий JSON записується `null`, а в масив `errors` додається опис помилки. Решта сусідніх полів обчислюються в штатному режимі.
- Якщо тип поля є **Non-Null** (`User!`), `null` є неприпустимим значенням за контрактом схеми. Рушій знищує об'єкт батьківського рівня і передає `null` на щабель вище. Якщо батьківське поле теж позначене як `!`, `null` спливає далі вгору до першого nullable-предка. Якщо всі поля аж до кореня були Non-Null — ключ `data` у фінальній відповіді стає `null`.

### 5. Інкрементальна доставка: директиви @defer та @stream

Сучасна специфікація GraphQL включає протокол інкрементальної доставки (Incremental Delivery), що дозволяє серверу повертати початкову частину відповіді негайно, а повільні вкладені поля досилати в міру їхньої готовності через єдине HTTP-з'єднання.

#### Семантика директив @defer та @stream

- `@defer`: застосовується до фрагментів вибірки. Вказує серверу відкласти обчислення цього фрагмента і надіслати початковий JSON без нього.
- `@stream`: застосовується до спискових полів. Вказує серверу віддати перші `initialCount` елементів списку негайно, а решту елементів досилати по одному в міру генерації.

```graphql
query ProductPage($id: ID!) {
  product(id: $id) {
    id
    title
    price
    ... on Product @defer(label: "ProductReviews") {
      reviews {
        id
        author
        rating
        text
      }
    }
  }
}
```

#### Транспорт multipart/mixed

Відповідь з `@defer` передається протоколом HTTP зі спеціальним заголовком `Content-Type: multipart/mixed; boundary="-"`.

Клієнт отримує початковий чанк (payload):

```http
---
Content-Type: application/json

{
  "data": {
    "product": {
      "id": "prod_1",
      "title": "Ноутбук",
      "price": 1200
    }
  },
  "hasNext": true
}
```

Після обчислення важкого резолвера відгуків сервер досилає наступний чанк у той самий потік:

```http
---
Content-Type: application/json

{
  "incremental": [
    {
      "label": "ProductReviews",
      "path": ["product"],
      "data": {
        "reviews": [
          { "id": "rev_1", "author": "Іван", "rating": 5, "text": "Чудово!" }
        ]
      }
    }
  ],
  "hasNext": false
}
---
```

### 6. Протокол підписок (Subscriptions Protocol)

Підписки (Subscriptions) забезпечують двосторонню передачу подій у реальному часі від сервера до клієнта.

Підписка зазвичай реалізується поверх протоколу WebSocket за допомогою стандартного підпротоколу `graphql-transport-ws`.

Життєвий цикл повідомлень підписки:

```
Клієнт                               Сервер
  │                                     │
  │─── { type: "connection_init" } ────►│
  │◄── { type: "connection_ack" } ─────│
  │                                     │
  │─── { type: "subscribe", ───────────►│ (Реєстрація потоку подій)
  │      id: "1", payload: { query } }  │
  │                                     │
  │◄── { type: "next", id: "1", ────────│ (Подія 1: нове повідомлення)
  │      payload: { data: { ... } } }   │
  │◄── { type: "next", id: "1", ────────│ (Подія 2: нове повідомлення)
  │      payload: { data: { ... } } }   │
  │                                     │
  │─── { type: "complete", id: "1" } ──►│ (Відписка клієнта)
```

Резолвер підписки складається з двох частин:
1. `subscribe`: повертає асинхронний ітератор (`AsyncIterator`), який генерує сирі події з черги або шини повідомлень (Redis Pub/Sub, Kafka).
2. `resolve`: функція-резолвер, яка перетворює згенеровану подію у форму, визначену вибіркою клієнтського запиту.

### 7. Інтроспекція (Introspection API)

Специфікація GraphQL вимагає від кожного сумісного сервера підтримки вбудованих полів метаданих, що дозволяють клієнтам запитати повну структуру схеми через сам GraphQL.

#### Стандартні системні поля

- `__schema`: Кореневе поле для отримання списку всіх типів, директив і точок входу схеми.
- `__type(name: String!)`: Поле для детального дослідження структури конкретного типу за його іменем.
- `__typename`: Метаполе, доступне на будь-якому об'єктному типі, інтерфейсі чи юніоні. Повертає строкову назву фактичного типу в рантаймі.

#### Запит інтроспекції структури типу

```graphql
query IntrospectUserType {
  __type(name: "User") {
    name
    kind
    description
    fields {
      name
      type {
        name
        kind
        ofType {
          name
          kind
        }
      }
      args {
        name
        type {
          name
        }
        defaultValue
      }
    }
  }
}
```

Можливі значення переліку `__TypeKind` у системі типів інтроспекції:
- `SCALAR`: Базовий скалярний тип.
- `OBJECT`: Складений об'єктний тип із полями.
- `INTERFACE`: Інтерфейсний тип.
- `UNION`: Тип-об'єднання.
- `ENUM`: Перелік константних значень.
- `INPUT_OBJECT`: Вхідний тип аргументів.
- `LIST`: Обгортка списку над іншим типом (`ofType`).
- `NON_NULL`: Обгортка обов'язковості над іншим типом (`ofType`).

Інтроспекція забезпечує функціонування всієї сучасної екосистеми інструментів: інтерактивних середовищ виконання запитів (GraphiQL, Apollo Studio), компіляторів кодогенерації статичних типів (GraphQL Code Generator, Relay Compiler) та плагінів для середовищ розробки з автодоповненням і валідацією запитів під час написання коду.
