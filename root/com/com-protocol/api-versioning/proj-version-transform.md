# ⚙️ Кістяк шару перекладу версій

Уяви, що в тебе живуть три версії API нараз: торішні клієнти сидять на першій, частина партнерів переповзла на другу, нові інтеграції одразу беруть третю. Тобі треба додати ще одну зламну зміну — і тут стає видно, який спосіб обслуговувати версії ти обрав рік тому. Якщо різниця версій розсипана по коду умовами «якщо версія 1 … інакше якщо версія 2 …», то нова зламна зміна означає ще одне галуження в кожному такому місці, а їх десятки. Логіка кожного ендпойнта потроху перетворюється на клубок, у якому ніхто вже не певен, що саме отримає старий клієнт. Це не гіпотеза — це типовий фінал наївного підходу, і множиться він не додаванням, а добутком: версій × місць, де вони розходяться.

Задача цієї вставки — показати робочий кістяк, який цей клубок розплутує. Ідея одна: **ядро пише лише сьогоднішній код**, знати не знаючи про жодну стару версію, а вся різниця між версіями живе на **краях**, у тонкому шарі перекладу. Вхідний запит старого клієнта на вході **піднімають** (upcast) до поточної форми; відповідь ядра на виході **опускають** (downcast) назад до тієї форми, якою клієнт говорить. Кожна зламна зміна за цим підходом — окремий маленький модуль, а не гілка в десятьох файлах. Саме так побудований платіжний сервіс Stripe; варто чесно зазначити, що в їхньому відомому описі перекладають насамперед **відповідь** (модуль зміни несе перетворення, яке відкочує відповідь на крок назад), а підняття запиту — дзеркальна половина, яка потрібна щойно старий клієнт починає й **надсилати** дані в старій формі. Тут ми зберемо обидві половини, бо повний кістяк складається саме з них.

## Ідея: одна зміна — один модуль із двома напрямками

Кожну зламну зміну ми загортаємо в окремий об'єкт — назвімо його **зміна-версія** (version-change). Він знає рівно дві речі: **коли** набув чинності (дату випуску) і **як перетворити** дані в обидва боки через межу цієї зміни. «Угору» (up) — узяти форму, яка була *до* зміни, і привести її до форми *після*; цим піднімають запит уперед у часі. «Униз» (down) — навпаки, узяти форму *після* й повернути до форми *до*; цим опускають відповідь назад. Один модуль — одна зламна зміна — обидва напрямки поряд, а не розмазані по коду.

Тепер найтонше місце, від якого залежить, працюватиме воно чи тихо брехатиме, — **порядок**. Зміни лежать у реєстрі, відсортовані від найстарішої до найновішої. Коли приходить запит клієнта, прив'язаного до якоїсь давньої версії, ми беремо **не всі** зміни, а лише ті, що вийшли **пізніше** за його версію (усе, що з'явилося після дати клієнта, для нього — майбутнє, якого він не знає), і застосовуємо їхнє «угору» **від найстарішої до найновішої**, крок за кроком підіймаючи запит до сьогодні. Відповідь іде тим самим набором змін, але у **зворотному** порядку — «униз», від найновішої до найстарішої, — доки форма не опуститься рівно до версії клієнта. Два проходи — дзеркальні: той самий список, обернений напрям.

![Ланцюжок перетворень з конкретними значеннями. Угорі запит клієнта v1 у формі amount 500 підіймається зліва направо: зміна VC_rename робить із нього total 500, зміна VC_cents — total 50000, і в такій поточній формі він доходить до ядра. Унизу відповідь ядра total 50000 опускається справа наліво тими самими змінами у зворотному порядку: VC_cents повертає total 500, VC_rename — amount 500, і клієнт отримує рідну стару форму](img/transform-chain.svg)
*Той самий набір змін, зворотний порядок. Запит підіймають уперед у часі — від старих змін до нових, доки не дійдуть поточної форми, яку розуміє ядро. Відповідь опускають назад — від нових змін до старих, доки не повернуться до форми клієнта. Ядро посередині бачить лише сьогоднішні дані й гадки не має, що по краях хтось перекладає.*

Чому саме дзеркало, а не той самий порядок в обидва боки? Бо зміни не незалежні — пізніша часто спирається на форму, яку залишила давніша. У нашому прикладі спершу поле `amount` перейменували на `total`, а вже потім суму перевели з доларів у центи, працюючи саме з полем `total`. Піднімаючи запит, треба спочатку зробити перейменування (давніша зміна), щоб пізніша знайшла поле під новою назвою. Опускаючи відповідь, усе навпаки: спершу відкотити центи в долари (пізніша зміна), а вже тоді перейменувати назад. Переплутаєш напрям — і пізніший крок шукатиме поле, якого в цей момент ще (або вже) немає під потрібною назвою, тихо його не знайде й нічого не зробить. Нічого не впаде; просто в числі з'явиться зайвий нуль. До цієї пастки ми ще повернемося з конкретним трасуванням.

## Робочий код

Зберемо кістяк. Дві прості форми — запит (параметри плюс тіло) і відповідь (код стану плюс тіло), — інтерфейс зміни-версії з двома необов'язковими напрямками, і реєстр із двома реальними змінами: перейменування `amount → total` і переведення суми з доларів у центи.

:::tabs
```ts
// Ядро розуміє лише СЬОГОДНІШНЮ форму; будь-які старі форми живуть на краях.
type Req = { params: Record<string, string>; body: any };
type Res = { status: number; body: any };

interface VersionChange {
  version: string;               // дата, коли зміна набула чинності (ISO)
  description: string;
  upRequest?(r: Req): Req;       // форма ДО → форма ПІСЛЯ  (підіймаємо запит)
  downResponse?(r: Res): Res;    // форма ПІСЛЯ → форма ДО  (опускаємо відповідь)
}

// Реєстр змін, відсортований від НАЙСТАРІШОЇ до найновішої.
const changes: VersionChange[] = [
  {
    version: "2024-02-20",
    description: "поле amount перейменовано на total",
    upRequest(r) {
      if (r.body && "amount" in r.body) { r.body.total = r.body.amount; delete r.body.amount; }
      return r;
    },
    downResponse(r) {
      if (r.body && "total" in r.body) { r.body.amount = r.body.total; delete r.body.total; }
      return r;
    },
  },
  {
    version: "2024-11-05",
    description: "суму переведено з доларів у центи",
    upRequest(r) {
      if (r.body && typeof r.body.total === "number") r.body.total *= 100;
      return r;
    },
    downResponse(r) {
      if (r.body && typeof r.body.total === "number") r.body.total = Math.round(r.body.total / 100);
      return r;
    },
  },
];
```
```python
from dataclasses import dataclass
from typing import Callable, Optional

Req = dict   # {"params": {...}, "body": {...}}
Res = dict   # {"status": int, "body": {...}}

@dataclass
class VersionChange:
    version: str                 # дата набуття чинності (ISO)
    description: str
    up_request: Optional[Callable[[Req], Req]] = None    # форма ДО → форма ПІСЛЯ (запит)
    down_response: Optional[Callable[[Res], Res]] = None  # форма ПІСЛЯ → форма ДО (відповідь)


def _rename_up(r: Req) -> Req:
    b = r["body"]
    if "amount" in b:
        b["total"] = b.pop("amount")
    return r

def _rename_down(r: Res) -> Res:
    b = r["body"]
    if "total" in b:
        b["amount"] = b.pop("total")
    return r

def _cents_up(r: Req) -> Req:
    b = r["body"]
    if isinstance(b.get("total"), (int, float)):
        b["total"] *= 100
    return r

def _cents_down(r: Res) -> Res:
    b = r["body"]
    if isinstance(b.get("total"), (int, float)):
        b["total"] = round(b["total"] / 100)
    return r

# Від найстарішої до найновішої.
changes = [
    VersionChange("2024-02-20", "amount → total", _rename_up, _rename_down),
    VersionChange("2024-11-05", "долари → центи", _cents_up, _cents_down),
]
```

type Req struct {
	Params map[string]string
	Body   map[string]any
}
type Res struct {
	Status int
	Body   map[string]any
}

type VersionChange struct {
	Version      string        // дата набуття чинності (ISO)
	Description  string
	UpRequest    func(Req) Req // форма ДО → форма ПІСЛЯ (запит); nil, якщо не стосується
	DownResponse func(Res) Res // форма ПІСЛЯ → форма ДО (відповідь); nil, якщо не стосується
}

// Від найстарішої до найновішої.
var changes = []VersionChange{
	{
		Version:     "2024-02-20",
		Description: "amount → total",
		UpRequest: func(r Req) Req {
			if v, ok := r.Body["amount"]; ok {
				r.Body["total"] = v
				delete(r.Body, "amount")
			}
			return r
		},
		DownResponse: func(r Res) Res {
			if v, ok := r.Body["total"]; ok {
				r.Body["amount"] = v
				delete(r.Body, "total")
			}
			return r
		},
	},
	{
		Version:     "2024-11-05",
		Description: "долари → центи",
		UpRequest: func(r Req) Req {
			if v, ok := r.Body["total"].(float64); ok {
				r.Body["total"] = v * 100
			}
			return r
		},

Тепер два проходи й склейка. Уся хитрість — у двох рядках циклів: запит іде реєстром **уперед**, відповідь — **назад**, і в обох випадках беруться лише зміни, датовані **пізніше** за версію клієнта.

:::tabs
```ts
// Запит підіймаємо УПЕРЕД: зміни, випущені ПІСЛЯ версії клієнта,
// від найстарішої до найновішої — доки не отримаємо поточну форму.
function upcast(req: Req, from: string): Req {
  for (const c of changes)
    if (c.version > from && c.upRequest) req = c.upRequest(req);
  return req;
}

// Відповідь опускаємо НАЗАД: той самий набір, але у ЗВОРОТНОМУ порядку,
// від найновішої до найстарішої — доки не дійдемо до версії клієнта.
function downcast(res: Res, to: string): Res {
  for (let i = changes.length - 1; i >= 0; i--) {
    const c = changes[i];
    if (c.version > to && c.downResponse) res = c.downResponse(res);
  }
  return res;
}

// Увесь прохід: версія клієнта → підняти → ядро → опустити → назад клієнтові.
function handle(clientVersion: string, params: Record<string, string>, body: any): Res {
  const coreReq = upcast({ params, body }, clientVersion);
  const coreRes = core(coreReq);          // ядро говорить ЛИШЕ поточною
  return downcast(coreRes, clientVersion);
}

// Ядро знає тільки сьогоднішню форму: total у центах.
function core(r: Req): Res {
  return { status: 200, body: { id: "or_42", total: r.body.total } };
}

// Клієнт, прив'язаний до 2023-05-10, шле стару форму й чекає стару назад:
handle("2023-05-10", {}, { amount: 500 });
// → { status: 200, body: { id: "or_42", amount: 500 } }
```

	for _, c := range changes { // від старих до нових
		if c.Version > from && c.UpRequest != nil {
			req = c.UpRequest(req)
		}
	}
	return req
}

func downcast(res Res, to string) Res {
	for i := len(changes) - 1; i >= 0; i-- { // від нових до старих
		c := changes[i]

			res = c.DownResponse(res)
		}
	}
	return res
}

	return downcast(coreRes, clientVersion)

> 🔧 **Навіщо це.** Порівняння `c.version > from` — не випадкове. Дати у форматі ISO 8601 (`2024-02-20`) впорядковані так, що звичайне порівняння рядків збігається з порівнянням у часі: пізніша дата — лексикографічно «більший» рядок. Тому і в TypeScript, і в Python, і в Go те саме `>` на рядках дає правильний хронологічний відбір без жодної роботи з датами. І ще тонкість про **межу**: порівняння **суворе** (`>`, не `>=`). Клієнт, прив'язаний рівно до дати якоїсь зміни, цю зміну вже *має* — вона для нього не майбутнє, а сьогодення, тож застосовувати її вдруге не можна. Помилка на цій межі не впаде голосно — вона зайвий раз перейменує чи помножить, і побачиш ти це аж у чужих даних.

Простежмо повний прохід на конкретному числі, щоб побачити, як форма їде туди й назад.

**Клієнт на 2023-05-10 створює замовлення на 500 доларів.** Він живе до обох змін, тож обидві застосовуються.

```
запит:  { amount: 500 }                    ← стара форма: поле amount, долари

підняти (уперед, від старих змін до нових):
  VC_rename ↑ :  amount → total            →  { total: 500 }
  VC_cents  ↑ :  500 · 100 = 50000         →  { total: 50000 }

ядро бачить:  { total: 50000 }             ← поточна форма: total, центи
ядро віддає:  { id: "or_42", total: 50000 }

опустити (назад, від нових змін до старих):
  VC_cents  ↓ :  50000 / 100 = 500         →  { total: 500 }
  VC_rename ↓ :  total → amount            →  { amount: 500 }

відповідь:  { id: "or_42", amount: 500 }   ← знову рідна стара форма
```

Ядро ні на мить не дізналося, що по той бік — клієнт 2023 року. Воно прочитало `total` у центах, повернуло `total` у центах, і вся біографія цього поля — перейменування й зміна одиниць — лишилася за межами ядра, у двох маленьких модулях. Додасться колись третя зламна зміна — з'явиться третій модуль із датою, і жодного рядка в ядрі чіпати не доведеться.

## Складність і пастки

**Порядок перетворень — головна пастка, і мовчазна.** Повернімося до обіцяного трасування. Припустимо, хтось написав `downcast` тим самим прямим циклом, що й `upcast` — від старих змін до нових, забувши обернути. Синтаксично все правильно, тести на новій версії проходять (там ланцюжок порожній). А на старому клієнті стається таке:

```
ядро віддає:  { total: 50000 }

опустити ХИБНО (від старих до нових):
  VC_rename ↓ :  total → amount            →  { amount: 50000 }
  VC_cents  ↓ :  шукає поле total — його вже нема  →  нічого не робить

відповідь:  { amount: 50000 }              ← 50000 замість 500, у сто разів більше
```

Нічого не впало. Клієнт отримав валідний JSON із полем `amount`, як і чекав, — тільки число в ньому в сто разів завелике. Перейменування спрацювало першим і забрало поле `total`, а перетворення центів, яке мало б відпрацювати першим, прийшло до порожнього місця, тихо його не знайшло (пам'ятаєш охоронну умову `typeof r.body.total === "number"`?) і ввічливо промовчало. Ось чому напрям — не стильова дрібниця: у грошах переплутаний порядок означає рахунок, більший у сто разів, і жодного винятку в логах. Єдиний захист — тримати правило «запит уперед, відповідь назад» священним і перевіряти його тестом, а не оком.

**Перекладати треба не лише тіло.** Легко забути, що версія клієнта фарбує **весь** запит і **всю** відповідь, а не тільки JSON-тіло. Тому й форми в кістяку ширші, ніж просто тіло: `Req` несе ще й `params`, а `Res` — код стану `status`. Зміна, що перейменувала параметр фільтра, живе в тому самому реєстрі й чіпає лише параметри:

```ts
{
  version: "2024-09-01",
  description: "параметр списку ?status=… → ?state=…",
  upRequest(r) {
    if ("status" in r.params) { r.params.state = r.params.status; delete r.params.status; }
    return r;
  },
  // відповіді ця зміна не стосується — downResponse просто немає
}
```

А зміна формату помилки перекладає **і код стану, і тіло помилки** — теж однією функцією, бо `downResponse` бачить усю відповідь:

```ts
{
  version: "2024-07-15",
  description: "помилка відсутнього ресурсу: 404/type → 400/code",
  downResponse(r) {
    const e = r.body?.error;
    if (e && e.type === "resource_missing") {
      r.status = 400;                 // старий клієнт чекав саме 400
      e.code = "not_found";           // і поле code, а не type
      delete e.type;
    }
    return r;
  },
}
```

Обидва модулі просто лягають у той самий масив `changes` між своїми за датою сусідами й підхоплюються тими самими двома циклами. Ніщо в ядрі про них не знає. Мораль: **зміна-версія — це не «перетворювач тіла», а перетворювач межі версії**, хоч що через цю межу проходить: поля тіла, параметри запиту, коди стану, форма помилки. Забудеш перекласти код помилки — і клієнт, який роками ловив `400`, раптом почне бачити `404` і зламає свою обробку так само надійно, як від перейменованого поля.

**Тестувати треба ланцюжок, а не окремі ланки.** Кожна зміна поодинці може бути бездоганною, а зібраний ланцюжок — брехати (як у прикладі з порядком вище). Тому перевіряти варто на трьох рівнях. По-перше, кожну зміну окремо: підняти й одразу опустити ті поля, яких вона торкається, і переконатися, що повернулося те саме. По-друге — і це найдешевший тест, що ловить найбільше, — **золоті зразки**: зафіксований вхід і очікуваний вихід на **кожну живу версію**, прогнані крізь увесь `handle`.

```ts
const golden = [
  { v: "2023-05-10", in: { amount: 500 },  out: { id: "or_42", amount: 500 } },
  { v: "2024-02-20", in: { total: 500 },   out: { id: "or_42", total: 500 } },
  { v: "2024-11-05", in: { total: 50000 }, out: { id: "or_42", total: 50000 } },
];
for (const g of golden) {
  const res = handle(g.v, {}, structuredClone(g.in));   // свіжа копія на кожен виклик!
  assert.deepEqual(res.body, g.out);
}
```

По-третє, окремо варто закріпити **інваріант тотожності**: для клієнта на поточній версії і `upcast`, і `downcast` мусять бути порожні — жодна зміна не датована пізніше за сьогодні, тож ланцюжок ні до чого не торкається, і `handle` віддає рівно те, що зробило ядро. Щойно цей тест почервонів — десь завелася зайва зміна або зміну неправильно датовано в майбутнє. Оскільки весь цей шар — стик між тобою і клієнтами, яких ти не контролюєш, найнадійніше закріпити пари «запит/відповідь на версію» як [контрактні тести](topic:sf-release/contract-testing) — зафіксувати очікувані форми для кожної живої версії й ганяти їх у CI, щоб випадкова правка ядра не поламала тихо старого клієнта.

**Перетворення мутують — пильнуй спільні посилання.** Помітив `structuredClone` у тесті? Він там не для краси. Наші перетворення міняють дані **на місці** (`delete`, присвоєння в те саме тіло) — так коротше й швидше, але це означає, що після `handle` вхідний об'єкт уже понівечено. Якщо десь вище ти тримаєш посилання на початкове тіло (скажімо, щоб залогувати сирий запит), то залогуєш уже перекладену форму, а не те, що справді надіслав клієнт. Два виходи: або клонувати на межі, перш ніж пускати в ланцюжок, або писати перетворення **чистими** — щоб повертали новий об'єкт, не чіпаючи вхідний. Для гарячого шляху з великими тілами дешевша мутація з одним клоном на вході; для спокою душі — чисті функції. Головне — обрати свідомо, а не наткнутися на здивування в логах.

**І остання, зворотна пастка: не заводь зміну там, де її не треба.** Шар перекладу — для **зламних** змін. Додав нове необов'язкове поле у відповідь? Це адитивна зміна, старі клієнти її й не помітять — жодного модуля не потрібно, просто віддавай нове поле всім. Спокуса «про всяк випадок» загорнути в зміну-версію кожну правку швидко перетворює чистий реєстр на звалище, де половина модулів нічого не робить. Реєстр має лишатися точним літописом справжніх зламів: скільки в ньому записів — стільки разів ти по-справжньому порушив контракт, ні на один більше. У цьому й краса підходу: «сьогоднішній» код лишається чистим, а вся історія несумісностей стоїть окремо, датована й прочитна, готова відкотити будь-яку відповідь рівно на стільки років назад, скільки живе твій найстаріший клієнт.
