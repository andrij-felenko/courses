# Згорткові коди

<preknowlist>
- [Лінійні блокові коди](topic:com-modulation/generator-and-parity-check-matrices) — що таке кодове слово й надлишок; блоковий підхід, з яким згорткові коди контрастують.
- [Біт парності](topic:com-modulation/parity-bit) — XOR (додавання за модулем 2) як спосіб згорнути групу бітів в один контрольний.
- [Зсувний регістр](topic:hw-digital/shift-register) — ланцюжок комірок, крізь який біти марширують по одному на кожен такт.
- [Відстань Геммінга](topic:com-modulation/hamming-distance) — лічба позицій, у яких два слова різняться; на ній тримається вибір найближчого кодового слова.
</preknowlist>

Блоковий код працює як конвеєр коробок: бере рівно k бітів даних, додає перевірочні, запечатує в кодове слово завдовжки n — і забуває про нього; наступний блок кодується з чистого аркуша, ні на що не оглядаючись. Так влаштовані [код Геммінга](topic:com-modulation/hamming-code), [Рід — Соломон](topic:com-modulation/reed-solomon), будь-який [лінійний блоковий код](topic:com-modulation/generator-and-parity-check-matrices). Це чудово лягає на дані, що вже поділені на пакети чи сектори. Але багато каналів несуть не коробки, а **потік** — безперервний струмінь бітів: голос у радіоканалі, телеметрія із зонда за мільярд кілометрів, кадри супутникового мовлення. Різати такий потік на незалежні блоки означає раз по раз ставити межі, синхронізуватися по них і губити захист рівно на стиках.

Згортковий код ставить питання інакше: а що, як не запечатувати дані в коробки, а **розмазати** вплив кожного вхідного біта на цілу низку сусідніх вихідних — щоб надлишок був вплетений у потік безперервно, без стиків? Тоді кожен переданий біт нестиме на собі відбиток кількох попередніх, і навіть якщо канал зіпсує кілька бітів, сусіди, у яких лишився той самий відбиток, дозволять їх відновити. Ім'я коду — саме про це: латинське *convolvere* (від *con-* — «разом» — і *volvere* — «котити, звивати») означає «згортати», бо вихід тут буквально є [згорткою](topic:com-signal/convolution) вхідного потоку з коротким фіксованим візерунком.

## Кодер — це зсувний регістр із відводами

Уся конструкція кодера вміщається в один [зсувний регістр](topic:hw-digital/shift-register) на кілька комірок і кілька суматорів XOR. Візьмімо найпростіший робочий приклад — код зі швидкістю 1/2 (на кожен вхідний біт кодер видає два вихідні). Регістр має три позиції: щойно надійшлий біт uₖ і два попередні, u₍ₖ₋₁₎ та u₍ₖ₋₂₎. Два суматори знімають XOR певних позицій:

```
v1 = uₖ ⊕ u₍ₖ₋₁₎ ⊕ u₍ₖ₋₂₎      (знімає всі три позиції)
v2 = uₖ ⊕ u₍ₖ₋₂₎               (знімає крайні дві)
```

Візерунок відводів — які саме позиції XOR-ить кожен суматор — і є **породжувальним многочленом** (generator polynomial). Його зручно записувати одним числом: 111 у двійковому = 7 у вісімковому для першого суматора, 101 = 5 для другого. Тож цей код коротко звуть «(7, 5)». Кількість позицій регістра — це **довжина обмеження** (constraint length) K; у нас K = 3. Два з трьох бітів вікна — це пам'ять кодера: рівно вони переносять «відбиток» минулого на майбутні виходи.

![Кодер згорткового коду (7,5): вхідний потік заходить у триклітинний зсувний регістр зліва; два суматори XOR знімають відводи (верхній — усі три клітини, нижній — крайні дві) і дають два вихідні біти v1, v2 на кожен вхідний біт; вихід чергується у потік подвоєної швидкості](img/encoder.svg)
*Один вхідний біт, два вихідні — швидкість 1/2. Кожен вихідний біт залежить не лише від поточного входу, а й від двох попередніх: у цьому й полягає «пам'ять» коду.*

На залізі це кілька зсувів і XOR — тому кодер тривіальний і швидкий; уся хитрість згорткових кодів на боці приймача. Ось той самий кодер у коді — стан тримає два біти пам'яті, дві маски задають відводи:

```c
// генератори (K=3): g1 = 111₂ = 7, g2 = 101₂ = 5 (вісімкові 7 і 5)
// вікно w = [uₖ u₍ₖ₋₁₎ u₍ₖ₋₂₎]; state тримає два біти пам'яті
void encode_bit(int u, unsigned *state, int *v1, int *v2) {
    unsigned w = (u << 2) | *state;      // зібрати трибітове вікно
    *v1 = __builtin_parity(w & 0b111);   // відвід g1 = 7: усі три
    *v2 = __builtin_parity(w & 0b101);   // відвід g2 = 5: крайні
    *state = w >> 1;                      // зсув: найстаріший біт випадає
}
```

**Приклад: закодуймо потік 1 0 1 1 0 0.** Регістр стартує порожнім (стан 00). На кожному кроці рахуємо v1, v2 за формулами вище й зсуваємо:

```
крок  вхід  вікно (uₖ u₍ₖ₋₁₎ u₍ₖ₋₂₎)   v1 v2   стан після
  0     1        1 0 0              1  1        1 0
  1     0        0 1 0              1  0        0 1
  2     1        1 0 1              0  0        1 0
  3     1        1 1 0              0  1        1 1
  4     0        0 1 1              0  1        0 1
  5     0        0 0 1              1  1        0 0
```

Вхід 1 0 1 1 0 0 перетворився на вдвічі довший потік **11 10 00 01 01 11**. Два останні нулі не випадкові: вони «виштовхують» пам'ять назад у нуль (це хвостові біти, tail bits), і кодер повертається у стартовий стан — так приймач знатиме, де кінець.

## Стан і ґратка

Придивімося до колонки «стан» у таблиці. Кодер щомиті перебуває в одному з чотирьох станів (00, 01, 10, 11 — усі можливі пари бітів пам'яті), а вхідний біт переводить його в наступний стан і водночас диктує пару виходів. Це в чистому вигляді [скінченний автомат](topic:hw-digital/finite-state-machines): скінченна пам'ять, детерміновані переходи. Станів завжди 2^(K−1); у нас 2² = 4.

Автомат зручно розгорнути в часі — намалювати чотири стани як чотири горизонтальні доріжки й показати, куди веде кожен такт. Виходить **ґратка** (trellis — англ. «садова решітка», від латинського *trilicium*, «зіткане з трьох ниток»; діаграма й справді нагадує ґратку для витких рослин). Кожне ребро ґратки — це один такт: воно виходить зі стану, входить у наступний і несе на собі пару вихідних бітів. Суцільне ребро — вхідний 0, штрихове — вхідний 1.

![Ґратка коду (7,5): чотири горизонтальні доріжки — це стани 00, 01, 10, 11, а кожен стовпець — один такт; тонкі ребра показують усі можливі переходи автомата (суцільні на вхід 0, штрихові на вхід 1), а підсвічений зелений шлях — кодування прикладу 1 0 1 1 0 0 з підписами пар виходів на ребрах](img/trellis.svg)
*Будь-яке повідомлення — це єдиний шлях крізь ґратку зліва направо; закодований потік — це підписи ребер уздовж нього. Кодування — прогулянка обраним шляхом, а декодування — його пошук.*

Ось ключова думка: будь-яке повідомлення — це **рівно один шлях** крізь ґратку від старту до кінця, а закодований потік — це послідовність підписів на його ребрах. Кодування — прогулянка обраним шляхом. А декодування — це пошук шляху.

## Декодування: знайти найближчий шлях

Канал псує кілька бітів у потоці. Приймач тримає в руках понівечену послідовність пар — це вже не обов'язково підпис якогось справжнього шляху; це шлях «повз ребра», що місцями зіскакує з ґратки. Задача декодера: знайти той **справжній** шлях крізь ґратку, підписи ребер якого найближчі до прийнятого — тобто відрізняються від нього в найменшій кількості позицій ([відстань Геммінга](topic:com-modulation/hamming-distance)). Найближчий шлях — найправдоподібніший переданий; його ребра-нулі-й-одиниці і є відновленим повідомленням.

Перебрати всі шляхи наосліп неможливо: для повідомлення з L бітів їх 2ᴸ. Але тут спрацьовує проста, майже нахабна економія, яку відкрив 1967 року [Ендрю Вітербі](topic:com-modulation/convolutional-codes/hist-elias-viterbi.md). Погляньмо на будь-який стан у якийсь момент часу. До нього веде кілька часткових шляхів із різними накопиченими відстанями. Але **майбутнє** — усе, що станеться після цього стану, — залежить лише від самого стану, не від того, як ми в нього потрапили. Отже, з усіх шляхів, що сходяться в один стан, гірший (з більшою відстанню) уже ніколи не зможе перемогти: хай що буде далі, той самий «хвіст» додасться до обох, і відставання не надолужити. Гірший шлях можна викинути одразу.

Тому декодер веде крізь ґратку рівно по **одному вцілілому шляху** (survivor path) на кожен стан. На кожному такті для кожного стану він робить три дії — «додати, порівняти, вибрати» (add-compare-select): додає відстань нового ребра до кожного з вхідних вцілілих, порівнює двох претендентів і лишає меншого. Наприкінці — обирає стан із найменшою відстанню й простежує його вцілілий шлях назад до старту. Це класичне [динамічне програмування](topic:sf-algorithms/dynamic-programming): робота на такт стала сталою (2^(K−1) станів), тож загальна вартість росте **лінійно** з довжиною повідомлення, а не як 2ᴸ.

![Декодування Вітербі: прийнято 11 11 00 01 01 11 з одним перевернутим бітом (виділено); зелений — справжній шлях крізь ґратку, розходиться з прийнятим лише в одній позиції; червоний — найближчий хибний повний шлях, розходиться у п'ятьох; сумарні відстані 1 проти 5, менша перемагає](img/viterbi.svg)
*Обидва шляхи стартують і фінішують у нульовому стані — тож обидва легальні. Прийняте лежить за один крок від справжнього й за п'ять від найближчого суперника: декодер обирає ближчий і тим стирає помилку.*

**Приклад: одна помилка гине.** Ми надіслали 11 10 00 01 01 11. Канал перевернув один біт у другій парі: приймач бачить 11 **11** 00 01 01 11. Декодер міряє відстані. Справжній шлях (той, що дає 11 10 00 01 01 11) розходиться з прийнятим рівно в одній позиції. Найближчий інший повний шлях крізь ґратку — той, що теж стартує й завершується в нульовому стані, — розходиться аж у п'ятьох. 1 проти 5, тож вцілілим лишається справжній шлях, і декодер упевнено повертає 11 10 00 01 01 11 — помилку стерто. Повний робочий декодер із простеженням назад — у [короткій реалізації](topic:com-modulation/convolutional-codes/proj-viterbi-decoder.md).

Досі декодер оперував голими бітами «0 чи 1» — це **жорстке рішення** (hard decision). Та канал зазвичай дає більше: не просто «радше 1», а «1, і доволі впевнено» чи «майже нуль, ледь схиляється до 1». Якщо годувати Вітербі цією аналоговою впевненістю замість зрізаних нулів-одиниць — **м'яке рішення** (soft decision), — той самий код виграє близько 2 дБ потужності задарма. Алгоритм не міняється: лише відстань Геммінга поступається місцем зваженій відстані.

## Вільна відстань і сила коду

Наскільки надійний код? Для блокових кодів усе вирішувала мінімальна відстань між кодовими словами. Тут — її пряма родичка: **вільна відстань** (free distance, d_free) — найменша відстань Геммінга між двома різними шляхами ґратки, що розходяться в одному стані й пізніше знову сходяться. Саме звідси взялася п'ятірка в прикладі декодування: два різні повні шляхи цього коду просто не вміють розійтися менше ніж на п'ять позицій. Дві помилки можуть заплутати декодер лише тоді, коли зіштовхнуть його на такий сусідній шлях; тож код упевнено виправляє до ⌊(d_free − 1)/2⌋ помилок на кожному прольоті розходження. Наш (7, 5) має d_free = 5 — виправляє дві помилки на прольоті.

Хочете сильніший код — беріть довший регістр. Стандарт далекого космосу від NASA — код (171, 133) із довжиною обмеження K = 7: він має d_free = 10 і дає близько 5 дБ виграшу на рівні помилок 10⁻⁵. Але за силу платять декодером: станів 2^(K−1), тож у K = 7 їх уже 64, а не 4, і кожен такт Вітербі мусить оновити всі 64 вцілілі шляхи. Це і є головний компроміс згорткових кодів — сила коду проти вартості декодування, обидві ростуть як 2 в степені пам'яті.

> 🔧 **Навіщо це.** Згорткові коди десятиліттями були робочим конем прямого виправлення помилок (FEC) там, де дані течуть потоком, а не пакетами, і де приймач може дозволити собі трохи заліза на декодер: голосовий канал GSM, Wi-Fi 802.11a/g, супутникове мовлення, і — найзнаменитіше — зв'язок із зондами «Вояджер» і «Галілео» за межами Сонячної системи. Формула вибору проста: короткий регістр (K = 7) плюс Вітербі з м'яким рішенням витискає з каналу кілька децибелів надійності при мізерній затримці й без величезних блоків, яких вимагають сучасні коди-рекордсмени. Там, де кожен ват передавача коштує роками польоту, ці децибели вирішують.

## Слабке місце: пакети помилок

Вітербі мовчазно припускає, що помилки **розсипані** по потоку поодинці. Щільний **пакет** помилок (burst) — коли канал на мить провалюється й псує довгу низку сусідніх бітів — здатен зіштовхнути вцілілий шлях із правди на цілий проліт, і код не витягне. Проти цього є два класичні прийоми, і обидва згорткові коди носять із собою.

Перший — [перемішування](topic:com-modulation/interleaving) (interleaving): перед передачею біти тасують за фіксованим правилом, а на прийомі повертають на місце. Пакет, який у каналі був щільним, після зворотного тасування розсипається тонким шаром поодиноких помилок — саме таких, які Вітербі любить. Другий — [конкатенація](topic:com-modulation/concatenated-codes): згортковий код ставлять усередину, а ззовні обгортають символьним [кодом Ріда — Соломона](topic:com-modulation/reed-solomon), який добиває рідкі пакети, що прориваються крізь внутрішній декодер. Саме так побудовано стандарт далекого космосу CCSDS: внутрішній (171, 133) із Вітербі, зовнішній (255, 223) Рід — Соломон, перемішування між ними. Разом вони дають понад 7 дБ виграшу — це різниця між сигналом, який чути, і тишею.

## Що з них виросло

1993 року французькі інженери зробили просту, майже зухвалу річ: узяли **два** згорткові кодери, зв'язали їх через перемішувач і змусили два декодери по черзі підказувати один одному, ітерація за ітерацією. Так народилися [турбокоди](topic:com-modulation/turbo-codes) — перші практичні коди, що впритул підійшли до [межі Шеннона](topic:math-information/bandwidth-capacity). Згортковий код не помер — він став будівельним блоком. Сьогодні на високошвидкісних каналах панують турбокоди й [LDPC](topic:com-modulation/ldpc), але самі згорткові коди досі живуть там, де блок мусить бути коротким, затримка — мізерною, а живлення — ощадливим: канали керування стільникового зв'язку, IoT-лінки, службові поля, де на довгий код просто немає бітів.

Підсумок: **згортковий код** обробляє не блоки, а потік — пропускає його крізь короткий [зсувний регістр](topic:hw-digital/shift-register) із відводами-XOR, і кожен вхідний біт лишає відбиток на кількох сусідніх вихідних. Кодер — це [скінченний автомат](topic:hw-digital/finite-state-machines), а всі його можливі шляхи — **ґратка**; декодування зводиться до пошуку шляху крізь ґратку, найближчого за [відстанню Геммінга](topic:com-modulation/hamming-distance) до прийнятого, що [алгоритм Вітербі](topic:com-modulation/convolutional-codes/proj-viterbi-decoder.md) робить лінійно швидко. Сила коду тримається на його [вільній відстані](topic:com-modulation/convolutional-codes/math-generator-polynomials.md) й росте разом із довжиною регістра — а з нею росте й ціна декодера. У парі з [перемішуванням](topic:com-modulation/interleaving) і [Рід — Соломоном](topic:com-modulation/reed-solomon) згорткові коди тримали далекий космос і мобільний зв'язок десятиліттями, а зчеплені по двоє — дали світові [турбокоди](topic:com-modulation/turbo-codes).
