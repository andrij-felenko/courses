# ⚙️ Зібрати декодер Вітербі: код (7,5), K = 3, і одна побита пара

**Задача.** Кодер уже є: він жене потік бітів крізь [зсувний регістр](root:hw-digital/shift-register) на три позиції з двома відводами-XOR і на кожен вхідний біт видає два вихідні. Повідомлення 1 0 1 1 0 0 перетворюється на потік 11 10 00 01 01 11. Тепер найцікавіше — приймач. Канал десь у дорозі перевернув один біт: замість 11 10 00 01 01 11 приймач тримає 11 **11** 00 01 01 11 (друга пара з 10 стала 11). Треба написати робочий декодер, який із цієї побитої послідовності відновить рівно ті 1 0 1 1 0 0, що ми надіслали, — не «приблизно», не «менше помилок», а точний оригінал. Усе на коді, який можна запустити: закодувати потік, внести помилку в канал, декодувати назад.

**Ідея.** Наївно декодер мав би перебрати всі можливі передані повідомлення й вибрати те, чий закодований вигляд найближчий до прийнятого. Для L бітів це 2ᴸ варіантів — безнадійно. Уся хитрість Вітербі в тому, що перебирати не треба. Кодер має лише 2^(K−1) = 4 стани (пара бітів пам'яті — це вміст регістра), і майбутнє залежить тільки від поточного стану, не від того, як ми в нього прийшли. Тож декодер тримає для **кожного** з чотирьох станів рівно **один** найкращий частковий шлях (вцілілий, survivor) і його накопичену відстань до прийнятого (метрику шляху, path metric). На кожному такті він для кожного стану пробує обидва можливі входи, додає відстань нового ребра, і в кожному стані-призначенні лишає **дешевший** з двох приходів — а звідки прийшов переможець, запам'ятовує вказівником назад. Наприкінці бере стан із найменшою метрикою й іде вказівниками додому. Це чисте [динамічне програмування](root:sf-algorithms/dynamic-programming): оптимальний шлях до стану будується з оптимальних шляхів до його попередників, тож робота на такт стала, а весь декодер — лінійний за довжиною повідомлення.

> 🔧 **Навіщо це.** Цей самий цикл — «додати, порівняти, вибрати» плюс простеження назад — крутиться всередині кожного стільникового модема, кожного Wi-Fi-чипа й кожного приймача далекого космосу. У ньому вся суть: декодер, оптимальний за максимумом правдоподібності, який **ніколи не вертається назад** по ходу роботи й укладається в лінійний час. Хто розуміє add-compare-select і traceback, той розуміє кістяк майже будь-якого практичного декодера прямого виправлення помилок — і того, з чого пізніше виросли ітеративні декодери турбокодів і LDPC.

## Ґратка — одна таблиця на весь код

Перш ніж декодувати, треба один раз описати кодер як таблицю переходів. Для коду (7, 5) з K = 3 стан — це два біти пам'яті, тож станів чотири. Для кожної пари (стан, вхідний біт) нам потрібні дві речі: яку пару виходів кодер видасть і в який стан перейде. Порахуємо це наперед — далі декодер лише читатиме таблицю.

```python
G = (0b111, 0b101)        # генератори g1 = 7₈, g2 = 5₈
K = 3
NSTATE = 1 << (K - 1)     # 2^(K−1) = 4 стани

def parity(x):            # XOR усіх бітів числа: 0 або 1
    return bin(x).count("1") & 1

# Ґратку рахуємо раз: для кожного (стан, вхід) — пара виходів і наступний стан.
TRELLIS = {}
for s in range(NSTATE):
    for u in (0, 1):
        w = (u << (K - 1)) | s            # трибітове вікно [uₖ u₍ₖ₋₁₎ u₍ₖ₋₂₎]
        out = (parity(w & G[0]), parity(w & G[1]))
        TRELLIS[(s, u)] = (out, w >> 1)   # (виходи, наступний стан)
```

Ключ до всієї арифметики — рядок `w = (u << (K−1)) | s`, тобто для K = 3 просто `(u << 2) | s`. Стан `s` тримає два біти пам'яті, свіжий вхід `u` стає старшим бітом — виходить трибітове вікно [uₖ u₍ₖ₋₁₎ u₍ₖ₋₂₎]. Генератор — це просто маска відводів: 7 = 111₂ знімає всі три позиції, 5 = 101₂ — крайні дві; парність вибраних бітів і є вихід. Зсув `w >> 1` виштовхує найстаріший біт — це вже наступний стан. Ось що лежить у таблиці:

```
стан 00: вхід 0 → вихід 00, стан 00   |  вхід 1 → вихід 11, стан 10
стан 01: вхід 0 → вихід 11, стан 00   |  вхід 1 → вихід 00, стан 10
стан 10: вхід 0 → вихід 10, стан 01   |  вхід 1 → вихід 01, стан 11
стан 11: вхід 0 → вихід 01, стан 01   |  вхід 1 → вихід 10, стан 11
```

Кодер на цій таблиці — три рядки: іди від стану до стану, дописуючи виходи в потік.

```python
def encode(bits):
    state, stream = 0, []
    for u in bits:
        out, state = TRELLIS[(state, u)]
        stream += out
    return stream
```

## Канал: вносимо помилку навмисне

Щоб декодер було що виправляти, змоделюймо канал у найгрубшому вигляді — **двійковий симетричний канал**, який із певною ймовірністю перевертає біт. Для наскрізного прикладу нам досить перевернути один конкретний біт руками:

```python
def corrupt(stream, positions):
    noisy = stream[:]
    for i in positions:
        noisy[i] ^= 1     # перевернути біт на позиції i
    return noisy
```

Позиція 3 — це другий біт другої пари. Чиста пара 10 стане 11 — рівно та єдина помилка, яку декодер має стерти.

## Серце декодера: add-compare-select

Тепер сам Вітербі. Формально на кожному такті для кожного нового стану s′ ми шукаємо мінімум по всіх ребрах, що в нього входять:

```
Mₜ(s′) = min       [ Mₜ₋₁(s) + d(вихід(s,u), rₜ) ]
        s,u: s→s′
```

де Mₜ(s′) — найменша накопичена відстань до стану s′ на такті t, rₜ — прийнята пара, а d — **відстань між очікуваною й прийнятою парою**. Для жорсткого рішення це [відстань Геммінга](root:com-modulation/hamming-distance): скільки з двох бітів не збіглося. Три слова алгоритму — прямо з цієї формули: **add** (Mₜ₋₁(s) + d) рахує претендента, **compare** порівнює двох претендентів, що сходяться в s′, **select** лишає меншого. І одне слово поза формулою, без якого нічого не відновиш: запам'ятати, звідки прийшов переможець.

```python
INF = float("inf")

def viterbi(recv):
    T = len(recv) // 2
    metric = [0] + [INF] * (NSTATE - 1)      # старт відомий — стан 00
    survivor = []                            # survivor[t][s′] = (попередник, вхід)
    for t in range(T):
        r = (recv[2 * t], recv[2 * t + 1])
        nm = [INF] * NSTATE                  # нові метрики
        nb = [None] * NSTATE                 # нові вказівники назад
        for s in range(NSTATE):
            if metric[s] == INF:             # у цей стан ще не дійшли
                continue
            for u in (0, 1):
                out, ns = TRELLIS[(s, u)]
                branch = (out[0] ^ r[0]) + (out[1] ^ r[1])   # ADD: відстань Геммінга
                cand = metric[s] + branch
                if cand < nm[ns]:                            # COMPARE + SELECT
                    nm[ns], nb[ns] = cand, (s, u)
        metric = nm
        survivor.append(nb)
    # простеження назад від стану з найменшою метрикою
    best = min(range(NSTATE), key=lambda s: metric[s])
    s, bits = best, []
    for nb in reversed(survivor):
        ps, u = nb[s]
        bits.append(u)
        s = ps
    bits.reverse()
    return bits, metric[best]
```

Три частини варто прочитати окремо. Ініціалізація `metric = [0, ∞, ∞, ∞]` каже, що ми **точно** стартуємо в стані 00, а решта станів на початку недосяжні — саме тому хвостові нулі, що заганяють кодер назад у 00, так спрощують життя приймачеві. Внутрішній подвійний цикл — це і є add-compare-select: одна перевірка `cand < nm[ns]` робить і порівняння, і вибір. І `survivor` — це вся пам'ять декодера про минуле: на кожному такті для кожного стану один запис «попередник + вхідний біт». Простеження назад просто читає цей журнал з кінця.

## Проганяємо приклад

Складаємо конвеєр і дивимося:

```python
msg  = [1, 0, 1, 1, 0, 0]
sent = encode(msg)                 # 11 10 00 01 01 11
recv = corrupt(sent, [3])          # 2-га пара 10 → 11
out, dist = viterbi(recv)
# надіслано:  11 10 00 01 01 11
# прийнято :  11 11 00 01 01 11
# декодовано: [1, 0, 1, 1, 0, 0]   метрика: 1
```

Декодер повернув точний оригінал, а метрика переможця — 1: справжній шлях розійшовся з прийнятим рівно в одному біті, тому саме там, де канал напаскудив. Щоб побачити, як він до цього дійшов, розгорнімо `metric` на кожному такті — це та сама таблиця, яку декодер заповнює зліва направо:

```
такт t      t0    t1    t2    t3    t4    t5    t6
стан 00      0     2     4     3     3     3   [1]   ← переможець
стан 01      ∞     ∞     1     2     2     1     4
стан 10      ∞     0     2     1     3     3     3
стан 11      ∞     ∞     1     2     1     3     4
```

Читається клітина так: метрика стану 00 на t6 дорівнює 1, бо в нього входять два ребра — з 01 (метрика 1) з виходом 11 і з 00 (метрика 3) з виходом 00. Прийнята пара — 11. Перше ребро додає 0 (11 збігається), друге додає 2: 1 + 0 = 1 проти 3 + 2 = 5. Compare-select лишає 1 і запам'ятовує, що прийшли з 01. Так само рахується кожна клітина таблиці — чотири стани на такт, і не більше. Наприкінці найменша метрика (1) — у стані 00; ідемо його вказівниками назад крізь стовпці й вичитуємо вхідні біти: 1 0 1 1 0 0.

## ACS-ядро: те, що на залізі крутиться мільйони разів

Python вище прозорий, але на реальному приймачі 2 Мбіт/с внутрішній цикл ACS виконується мільйони разів на секунду — і саме він визначає, чи встигне декодер за потоком. Тому на DSP, ПЛІС чи в прошивці це ядро пишуть на C, де кожен такт стану — кілька регістрових операцій без жодних словників і кортежів. Таблиці переходів і виходів згортаються в масиви, а пара виходів пакується у два біти (v1<<1)|v2:

:::tabs
```python
# Один такт ACS для 4 станів (жорстке рішення).
# pm — метрики зараз; повертає нові метрики й вказівники назад.
def acs_step(pm, r0, r1):
    nm = [INF] * NSTATE
    nb = [None] * NSTATE
    for s in range(NSTATE):
        if pm[s] == INF:
            continue
        for u in (0, 1):
            out, ns = TRELLIS[(s, u)]
            bm = (out[0] ^ r0) + (out[1] ^ r1)   # відстань Геммінга
            cand = pm[s] + bm                     # ADD
            if cand < nm[ns]:                     # COMPARE + SELECT
                nm[ns], nb[ns] = cand, (s << 1) | u
    return nm, nb
```
```c
#include <limits.h>

// Наступний стан і пара виходів (v1<<1)|v2 для коду (7,5), K=3.
static const int NXT[4][2] = {{0,2},{0,2},{1,3},{1,3}};
static const int OUT[4][2] = {{0b00,0b11},{0b11,0b00},{0b10,0b01},{0b01,0b10}};

// Один такт add-compare-select. pm — метрики зараз, npm — нові;
// back[s′] = (попередник<<1)|вхід. r0,r1 — прийнята пара (0/1).
void acs_step(const int pm[4], int npm[4], int back[4], int r0, int r1) {
    for (int ns = 0; ns < 4; ns++) npm[ns] = INT_MAX;
    for (int s = 0; s < 4; s++) {
        if (pm[s] == INT_MAX) continue;
        for (int u = 0; u < 2; u++) {
            int o    = OUT[s][u];
            int bm   = ((o >> 1) ^ r0) + ((o & 1) ^ r1);   // відстань Геммінга
            int cand = pm[s] + bm;                         // ADD
            int ns   = NXT[s][u];
            if (cand < npm[ns]) {                          // COMPARE + SELECT
                npm[ns]  = cand;
                back[ns] = (s << 1) | u;
            }
        }
    }
}
```
:::

Той самий алгоритм, той самий результат — але C-версія не тримає жодного об'єкта в купі, працює на масивах фіксованого розміру й лягає прямо на регістри. Для довших кодів (скажімо, K = 7 із 64 станами) саме тут вмикають бітову паралельність і SIMD: чотири-вісім станів рахують ACS одночасно, бо всі вони незалежні. Ця незалежність — не випадковість, а прямий наслідок того, що майбутнє стану не залежить від його минулого.

## Від жорсткого рішення до м'якого — 2 дБ задарма

Досі декодер отримував голі нулі й одиниці. Але демодулятор зазвичай знає більше: не просто «це 1», а «це радше 1, і доволі впевнено» чи «майже нуль, ледь схиляється до 1». Викидати цю впевненість, зрізаючи вибірку до жорсткого біта, — марнотратство. **М'яке рішення** (soft decision) годує Вітербі саму аналогову вибірку, і на [гаусовому каналі з адитивним білим шумом](root:math-information/awgn-channel) той самий код виграє близько 2 дБ потужності — це майже дарова надійність, вимірювана десятиліттями досліджень.

Найкраще те, що алгоритм не міняється **ні на йоту**. Міняється рівно одна функція — метрика гілки. Замість відстані Геммінга беремо, наскільки вибірка корелює з очікуваною парою ±1 (логічна 1 → −1, логічний 0 → +1); що більша кореляція, то ближче, тож беремо її зі знаком мінус, щоб і далі шукати **мінімум**:

```python
def branch_soft(expected, r):
    e = (1 - 2 * expected[0], 1 - 2 * expected[1])   # біт 0 → +1, біт 1 → −1
    return -(e[0] * r[0] + e[1] * r[1])              # −кореляція: менше = ближче
```

У `viterbi` рядок `branch = (out[0]^r[0]) + (out[1]^r[1])` замінюємо на `branch = branch_soft(out, r)` — і все. Add-compare-select, вцілілі шляхи, простеження назад лишаються буква в букву. На практиці аналогову вибірку квантують у 3 біти (вісім рівнів) — цього вистачає, щоб зібрати майже весь виграш, а метрики лишити цілочисловими й дешевими.

## Складність і три пастки

Порахуймо ціну. На кожному такті — 2^(K−1) станів по дві гілки, тобто стала робота, що не залежить від довжини повідомлення. Звідси головна властивість Вітербі:

```
робота на такт = 2^(K−1) станів × 2 гілки       — стала
усього         = O(L · 2^(K−1))                  — лінійно за довжиною L
пам'ять traceback (наївно) = L · 2^(K−1) записів
```

Лінійність за L — це те, що робить згорткові коди практичними: подвоїш повідомлення — удвічі більше роботи, а не в 2ᴸ разів. Але за 2^(K−1) у формулі ховається жорстка розплата: кожна додана комірка пам'яті **подвоює** число станів. Наш K = 3 — це 4 стани; космічний K = 7 — уже 64; K = 9 у деяких стандартах — 256. Сила коду й ціна декодера ростуть однією й тією ж експонентою. І три місця, де наївний код ламається на реальному потоці.

**Пастка перша: пам'ять простеження назад.** Наш `survivor` росте на кожному такті — для повідомлення на мільйон бітів це мільйон записів на всі чотири стани. Для нескінченного потоку (телеметрія, що йде роками) так не можна. Рятує тонка властивість: якщо відступити назад досить далеко, усі чотири вцілілі шляхи **зливаються** в один — бо давнє минуле в них однакове. Тож декодер не тримає всю історію: він веде **вікно** глибиною D тактів, і на кожному кроці видає найдавніший біт, у якому шляхи вже зійшлися, а старіше забуває. Скільки саме тримати? Практичне правило — приблизно 5·(K−1), тобто п'ять довжин пам'яті коду (для коду швидкості 1/2 воно точне; загальна оцінка — 2.5·(K−1)/(1−r) для швидкості r). Для K = 3 це десяток-півтора тактів. Глибше тримати марно — шляхи вже злилися, а пам'ять і затримка ростуть.

> 🔧 **Навіщо це.** Ця властивість злиття — те, що взагалі робить потокове декодування можливим. Без неї Вітербі мусив би дочекатися кінця повідомлення, щоб почати простеження, — а нескінченний потік не має кінця. Саме глибина злиття ≈ 5·(K−1) перетворює «знайти оптимальний шлях цілком» на «видавати оптимальні біти на льоту із сталою затримкою й сталою пам'яттю». Уся інженерія реального декодера крутиться навколо цього числа.

**Пастка друга: хвостові біти проти усічення.** Наш приклад закінчувався двома нулями, що заганяли кодер назад у стан 00, — тому простеження стартувало з **відомого** стану, і кінець повідомлення захищений так само добре, як середина. Ціна — ці K−1 зайвих бітів на кожен блок, чистий програш швидкості на коротких блоках. Альтернатива — **усічення** (truncation): не гнати хвіст, а просто почати простеження зі стану з найменшою метрикою (шляхи ж однаково злилися). Швидкість не втрачаємо, але останні кілька бітів блоку захищені гірше. Компроміс між цими крайнощами — **хвостозамкнені коди** (tail-biting): кодер стартує зі стану, у якому й закінчить, тож жодного зайвого біта, а обидва кінці рівноправні; ними користуються LTE й WiMAX, платячи трохи складнішим декодером, що пробує кілька стартових станів.

**Пастка третя: переповнення метрик.** На нескінченному потоці метрики шляхів ростуть без упину — рано чи пізно ціле число переповниться. Але декодера цікавлять не самі метрики, а їхні **різниці**, і різниця між найкращим і найгіршим вцілілим шляхом завжди обмежена (для коду швидкості 1/2 вона не перевищує кількох одиниць). Два виходи: або на кожному такті віднімати від усіх метрик поточний мінімум (перенормування), або скористатися тим, що різниця обмежена, і порівнювати метрики за модульною арифметикою — тоді переповнення саме «загортається» й нічому не шкодить. Апаратні декодери майже завжди беруть другий шлях: він безкоштовний, бо порівняння з обгортанням — це та сама віднімання, що вже стоїть у compare.

---

Ось і весь декодер: одна таблиця переходів, цикл add-compare-select на чотири стани, журнал вцілілих шляхів і простеження назад — трохи більше сотні рядків, які виправляють помилки оптимально й у лінійний час. Наш побитий біт зник, бо справжній шлях крізь ґратку відрізнявся від прийнятого всього на одиницю, а найближчий самозванець — на цілих п'ять. Той самий каркас, лише з ширшим регістром і м'якою метрикою, десятиліттями тримав зв'язок із зондами за межами Сонячної системи — і досі тримає керувальні канали у вашій кишені.
