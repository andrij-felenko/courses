# 📋 Параметрична модель Rocksoft: повний каталог параметрів CRC

Параметрична модель Рока Вільямса (Rocksoft^tm Model, запропонована у 1993 році у праці *A Painless Guide to CRC Error Detection Algorithms*) усуває неоднозначність інженерних специфікацій, задаючи повний математичний контракт для будь-якої реалізації циклічного надлишкового коду за допомогою шести фіксованих параметрів.

Якщо два мережеві пристрої використовують однаковий твірний поліном, але розходяться хоча б в одному налаштуванні (наприклад, початковому значенні чи порядку слідування бітів у шині), їхні контрольні суми не зійдуться. Модель Rocksoft формалізує конфігурацію CRC як уніфікований набір параметрів, що дозволяє однаково точно описувати як побітні апаратні схеми, так і швидкі табличні алгоритми для систем будь-якої розрядності.

### Шість параметрів специфікації та їхнє фізичне призначення

Кожен параметр моделі Rocksoft був введений не як математична забаганка, а для компенсації конкретних апаратних обмежень фізичних ліній зв'язку та особливостей архітектури процесорів.

| Параметр | Тип | Опис та інженерне призначення |
| :--- | :--- | :--- |
| **`Width`** | Ціле число | Розрядність регістра CRC у бітах (степінь твірного полінома `n`, наприклад 8, 16, 32, 64). Визначає розмір контрольної суми та апаратного регістра. |
| **`Poly`** | Шістнадцяткове | Незвідний твірний поліном `G(x)` у нереверсивній (MSB-first) формі без старшого біта `xⁿ` (який завжди дорівнює 1). Наприклад, для `x¹⁶ + x¹² + x⁵ + 1` значення дорівнює `0x1021`. |
| **`Init`** | Шістнадцяткове | Початковий стан регістра перед обробкою першого байта. «Чисте» ділення зі стартовим нулем `0x00` не здатне виявити додавання довільної кількості нульових байтів на початку кадру (оскільки `0 mod G(x) = 0`). Ініціалізація значенням `0xFF..FF` робить будь-які нулі на початку значущими. |
| **`RefIn`** | Булеве (`true`/`false`) | Якщо `true`, кожен вхідний байт перед обробкою реверсується (біти подаються LSB-first: молодший біт 0 стає старшим 7). Це властиво апаратурі послідовних шин UART, Ethernet та USB, де молодший біт фізично передається першим у часі. |
| **`RefOut`** | Булеве (`true`/`false`) | Якщо `true`, результуючий `Width`-бітний регістр повністю дзеркально реверсується перед фінальним накладанням маски `XorOut`. Дозволяє передавати байти контрольної суми в лінію безпосередньо в порядку їх формування. |
| **`XorOut`** | Шістнадцяткове | Значення, з яким виконується операція XOR над фінальним регістром. Дозволяє виявляти втрату або приписування нульових байтів у кінець повідомлення. |

### Фізична природа та інженерні тонкощі параметрів

1. **Проблема початкових нулів (`Init`):** Якщо регістр починає роботу зі значенням нуль, будь-яка послідовність нульових байтів на вході залишає регістр у нульовому стані (`0 << 1 = 0`, `0 ^ 0 = 0`). Якщо в каналі зв'язку зникне або додасться кілька нульових байтів на початку кадру, «голий» алгоритм взагалі не помітить змін. Заповнення регістра одиницями (`Init = 0xFFFFFFFF`) змушує навіть перший нульовий біт змінювати внутрішній стан через механізм зворотного зв'язку.
2. **Апаратний порядок бітів (`RefIn` та `RefOut`):** Послідовні інтерфейси зв'язку (RS-232, UART, Ethernet, USB) історично передають байти молодшим бітом уперед (LSB-first). Якби програмний алгоритм вимагав подачі старшого біта (MSB-first), процесору доводилося б дзеркально розвертати кожен байт окремими інструкціями. Встановлення `RefIn = true` та `RefOut = true` дозволяє алгоритму працювати безпосередньо з реверсивним поліномом (наприклад, `0xEDB88320` замість `0x04C11DB7`), зсуваючи регістр вправо без додаткових накладних витрат.
3. **Захист від кінцевих нулів (`XorOut`):** Якщо повідомлення закінчується серією нульових байтів, фінальний стан регістра без маски може випадково збігтися з нулем для певних пошкоджених пакетів. Інверсія кінцевого результату (`XorOut = 0xFFFFFFFF`) гарантує, що результуючий код буде рівномірно розподілений у просторі значень.

### Три форми запису полінома в документації

Під час читання технічних описів мікроконтролерів (STM32, NXP, Microchip) та стандартів зв'язку інженери часто стикаються з трьома різними шістнадцятковими числами для одного й того самого математичного полінома:

- **Нормальна форма (Normal / MSB-first):** Коефіцієнти записуються у прямому порядку від старшого біта `xⁿ⁻¹` до молодшого `x⁰`. Для полінома Ethernet CRC-32 це значення `0x04C11DB7`.
- **Реверсивна форма (Reversed / LSB-first / Reflected):** Біти коефіцієнтів дзеркально обертаються всередині `n`-бітного слова (біт `i` переходить у позицію `n - 1 - i`). Для Ethernet CRC-32 це дає константу `0xEDB88320`. Саме це число використовують у таблицях швидких драйверів.
- **Взаємна форма (Reciprocal / Koopman):** Старший біт `xⁿ` зберігається, а молодший одиничний біт `x⁰` відкидається. У нотації Філіпа Купмана (Philip Koopman) цей самий поліном записується як `0x82608EDB`.

Плутанина між цими трьома формами запису є найпоширенішою причиною несумісності коду під час інтеграції апаратних модулів. Завжди звіряйте поліном за верифікаційним полем `Check`.

### Верифікаційні поля: Check та Residue

Для перевірки коректності будь-якої реалізації алгоритму модель Rocksoft визначає два стандартизовані тестові значення:

1. **`Check`**: Контрольна сума для стандартного тестового вектора ASCII `"123456789"` (що у шістнадцятковому вигляді відповідає послідовності байтів `0x31 0x32 0x33 0x34 0x35 0x36 0x37 0x38 0x39`). Якщо ваша функція видає вказане в таблиці число для рядка `"123456789"`, конфігурація параметрів налаштована правильно.
2. **`Residue` (Магічна константа)**: Фіксована остача, яку отримує приймач, якщо пропускає через алгоритм весь пакет разом із дописаним у кінець кодом CRC. Для схем без фінального `XorOut` остача дорівнює `0x00`, а для стандартного CRC-32 (IEEE 802.3) вона завжди строго дорівнює `0xDEBB20E3` (у реверсивному вигляді) або `0xC704DD7B` (у прямому вигляді).

### Покроковий приклад простеження обчислення

Розглянемо покроковий розрахунок CRC-16/CCITT-FALSE для перших трьох байтів тестового рядка `"123"` (байти `0x31`, `0x32`, `0x33`):

1. **Старт:** Регістр завантажується значенням `Init = 0xFFFF`.
2. **Байт 1 (`0x31`):** Змішується у старший байт: `0xFFFF ^ 0x3100 = 0xCEFF`. Після 8 побітних зсувів з поліномом `0x1021` стан регістра стає `0x772B`.
3. **Байт 2 (`0x32`):** Змішується: `0x772B ^ 0x3200 = 0x452B`. Після 8 зсувів стан регістра переходить у `0x7179`.
4. **Байт 3 (`0x33`):** Змішується: `0x7179 ^ 0x3300 = 0x4279`. Після 8 зсувів стан стає `0x5BEE`.
5. **Фінал:** Оскільки `XorOut = 0x0000`, кінцеве значення дорівнює `0x5BEE`.

Цей простий тест дозволяє легко локалізувати помилку у власному побітному чи табличному коді на етапі юніт-тестування.

### Покроковий алгоритмічний конвеєр моделі Rocksoft

Під час програмного чи апаратного розрахунку контрольного залишку для вхідного блоку байтів алгоритм моделі Rocksoft строго дотримується наступного порядку дій:

1. **Ініціалізація:** Регістр CRC шириною `Width` бітів завантажується початковим значенням `Init`.
2. **Обробка потоку:** Для кожного вхідного байта з буфера:
   - Якщо `RefIn == true`, біти вхідного байта дзеркально обертаються (0-й біт стає 7-м).
   - Байт змішується з поточним станом регістра (у старші або молодші розряди залежно від напрямку зсуву).
   - Виконується 8 побітних тактів ділення або пряма вибірка залишку з 256-елементної таблиці LUT.
3. **Фіналізація:** Після обробки останнього байта:
   - Якщо `RefOut == true`, всі `Width` бітів отриманого регістра реверсуються від старшого до молодшого.
   - Виконується фінальна операція побітового додавання `XOR` зі значенням `XorOut`.
   - Отримане беззнакове ціле число повертається як результуюча контрольна сума кадру.
