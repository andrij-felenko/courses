# 📋 Специфікація команд ISO 14443-3, ISO 14443-4 та розрахунок CRC-16

Даний довідник описує формат байтів команд, бітових кадрів та протокольних блоків нижнього рівня стандарта ISO/IEC 14443 (Type A та Type B), а також містить C та C++ реалізації розрахунку контрольної суми CRC-16 (ISO 14443-A).

## 1. Кадри нижнього рівня (Bit Frame Formats)

Обмін даними на фізичному рівні ISO 14443-3 поділяється на три типи бітових кадрів:

1. **Короткий кадр (Short Frame):** Складається з 7 бітів даних без паритету та бітів старт/стоп. Використовується виключно для початкового опитування `REQA` (0x26) та `WUPA` (0x52).
2. **Стандартний кадр (Standard Frame):** Складається з послідовності байтів, де кожен байт супроводжується бітом парності (Odd Parity Bit). Закінчується бітом стоп. Використовується для передачі команд каскадування, SELECT, RATS та кадрів ISO-DEP.
3. **Біт-орієнтований кадр (Bit-Oriented Frame):** Кадр спеціального формату, який дозволяє відправляти нецілу кількість байтів (наприклад, 2 байти та 3 біти). Використовується у процесі антиколізії, коли зчитувач відправляє частково заповнений UID.

Декодування поля `NVB` (Number of Valid Bits) у біт-орієнтованому кадрі:
- Старші 4 біти `NVB[7:4]` задають кількість повних цілих байтів у кадрі.
- Молодші 4 біти `NVB[3:0]` задають кількість додаткових дробових бітів (0..7).
- Значення `NVB = 0x20` вказує на 2 повних байти (`SEL` + `NVB`), без бітів колізії. Значення `NVB = 0x70` означає повний кадр вибору з 7 байтів (5 байтів UID + 2 байти `SEL` і `NVB`).

## 2. Часові параметри та інтервали кадрування (Timings)

Стандарт ISO 14443-3 жорстко регламентує часові затримки між командами та відповідями:

- **FDT (Frame Delay Time):** Час затримки кадру між останнім паузовим фронтом сигналу зчитувача PCD та першим фронтом піднесучої мітки PICC. Залежно от того, чи є останній біт `1` чи `0`, FDT становить `1172 / f_c` (приблизно `86.43 мкс`) або `1236 / f_c` (`91.15 мкс`).
- **EGT (Extra Guard Time):** Додатковий захисний інтервал між байтами кадру в Type B (від 0 до 19 бітових інтервалів `ETU`).
- **TR0 (Guard Time):** Мінімальний інтервал між закінченням передачі PCD та початком модуляції PICC у Type B (`16 / f_s ≈ 18.88 мкс`).
- **TR1 (Synchronization Time):** Інтервал синхронізації піднесучої Type B перед початком даних (від `32 / f_s` до `256 / f_s`).

## 3. Таблиця базових команд ISO 14443-3 Type A

У таблиці нижче зведено команди каскадного рівня антиколізії Type A:

| Байт команди | Назва команди | Розмір (байти) | Опис та відповідь PICC |
| :--- | :--- | :--- | :--- |
| `0x26` | REQA (Request A) | 7 біт | Запит активації міток у стані IDLE. Відповідь ATQA (2 байти). |
| `0x52` | WUPA (Wake-Up A) | 7 біт | Пробудження міток у станах IDLE та HALT. Відповідь ATQA (2 байти). |
| `0x93 0x20` | ANTICOLLISION CL1 | 2 байти | Запит 4 байтів UID каскаду 1 (SEL=0x93, NVB=0x20). |
| `0x93 0x70` | SELECT CL1 | 9 байтів | Вибір мітки за UID CL1 + CRC. Відповідь SAK (1 байт + CRC). |
| `0x95 0x20` | ANTICOLLISION CL2 | 2 байти | Запит 4 байтів UID каскаду 2 (SEL=0x95, NVB=0x20). |
| `0x95 0x70` | SELECT CL2 | 9 байтів | Вибір мітки за UID CL2 + CRC. Відповідь SAK (1 байт + CRC). |
| `0x97 0x20` | ANTICOLLISION CL3 | 2 байти | Запит 4 байтів UID каскаду 3 (SEL=0x97, NVB=0x20). |
| `0x97 0x70` | SELECT CL3 | 9 байтів | Вибір мітки за UID CL3 + CRC. Відповідь SAK (1 байт + CRC). |
| `0x50 0x00` | HLTA (Halt A) | 2 байти + CRC | Переведення обраної мітки у стан HALT. Відповіді немає. |
| `0xE0` | RATS | 2 байти + CRC | Запит активації ISO-DEP (Request for Answer to Select). |

## 4. Стан HALT та особливості повторної активації

Команда `HLTA` (`0x50 0x00`) переводить обрану мітку зі стану `ACTIVE` або `PROTO` у стан `HALT`. У стані HALT мітка припиняє відповідати на звичайні запити опитування `REQA`. Це дозволяє зчитувачу по черзі опитувати та обробляти кілька міток, розташованих у спільному магнітному полі.

Для виведення мітки зі стану `HALT` зчитувач повинен відправити команду `WUPA` (`0x52`), яка пробуджує як мітки у стані `IDLE`, так і мітки у стані `HALT`. Якщо мітка отримує повторний `REQA`, перебуваючи в стані `HALT`, вона ігнорує запит і залишається мовчазною.

## 5. Деталізація відповіді ATQA (Answer To Request A)

Відповідь `ATQA` передається міткою у відповідь на команду `REQA` або `WUPA`. Вона складається з 2 байтів (`ATQA[0]` та `ATQA[1]`), бітова структура яких несе інформацію про підтримувану антиколізію та довжину UID:

```
ATQA Byte 0: [ b8 | b7 | b6 | b5 | b4 | b3 | b2 | b1 ]
  - b8..b7: Зарезервовані біти (мусять бути 00).
  - b6..b5: Індикатор підтримки bit-frame антиколізії.
  - b4..b1: Зарезервовані.

ATQA Byte 1: [ b8 | b7 | b6 | b5 | b4 | b3 | b2 | b1 ]
  - b8..b7: Індикатор розміру UID:
      00 — Single UID (4 байти)
      01 — Double UID (7 байтів)
      10 — Triple UID (10 байтів)
```

## 6. Деталізація байта SAK (Select Acknowledge)

Байт `SAK` повертається міткою після успішного виконання команди `SELECT` відповідного каскадного рівня. Нижче наведено повну розшифровку бітів SAK:

| Біт SAK | Маска | Функція та зміст |
| :--- | :--- | :--- |
| **b6** | `0x40` | Якщо 1 — пристрій працює у режимі Peer-to-Peer (NFC-DEP / ISO 18092). |
| **b5** | `0x20` | Якщо 1 — мітка сумісна з ISO/IEC 14443-4 (ISO-DEP). |
| **b2** | `0x04` | Якщо 1 — UID незавершений (потрібна команда `ANTICOLLISION` наступного CL). |
| **b0** | `0x01` | Якщо 1 — сигналізує про нестандартний пропетарний кадр. |

- **Біт 3 (`0x04`):** Індикатор незавершеності UID. Якщо `SAK & 0x04 == 1`, це означає, що прочитаний 4-байтовий блок містить байт каскадної мітки `CT = 0x88`, і зчитувач повинен виконати команду `ANTICOLLISION` наступного каскадного рівня (CL2 або CL3).
- **Біт 6 (`0x20`):** Індикатор сумісності з ISO/IEC 14443-4 (ISO-DEP). Якщо `SAK & 0x20 == 1`, мітка є смарт-картою з підтримкою кадрів APDU (наприклад, MIFARE DESFire або банківська карта EMV), і зчитувач повинен відправити команду `RATS`. Якщо `SAK & 0x20 == 0`, мітка є простим накопичувачем пам'яті (наприклад, MIFARE Classic або NTAG213).

## 7. Покроковий сеанс дозволу колізій 7-байтового UID (Double Size UID)

Розглянемо повну послідовність обміну для 7-байтового UID (`UID = 0x04 0xA2 0xB3 0xC4 0xD5 0xE6 0xF7`):

1. **PCD -> PICC:** `REQA` (7 біт, `0x26`).
2. **PICC -> PCD:** `ATQA` (`0x00 0x44` — індикатор Double UID).
3. **PCD -> PICC:** `ANTICOLLISION CL1` (`0x93 0x20`).
4. **PICC -> PCD:** `CT` + `UID0` + `UID1` + `UID2` + `BCC1` (`0x88 0x04 0xA2 0xB3 0x3D`).
5. **PCD -> PICC:** `SELECT CL1` (`0x93 0x70` + 5 байт даних + 2 байти CRC).
6. **PICC -> PCD:** `SAK CL1` (`0x04` + 2 байти CRC — прапор `UID Incomplete`).
7. **PCD -> PICC:** `ANTICOLLISION CL2` (`0x95 0x20`).
8. **PICC -> PCD:** `UID3` + `UID4` + `UID5` + `UID6` + `BCC2` (`0xC4 0xD5 0xE6 0xF7 0x88`).
9. **PCD -> PICC:** `SELECT CL2` (`0x95 0x70` + 5 байт даних + 2 байти CRC).
10. **PICC -> PCD:** `SAK CL2` (`0x20` + 2 байти CRC — прапор `UID Complete`, підтримує ISO-DEP).

## 8. Деталізація команди RATS (Request for Answer to Select)

Команда `RATS` відправляється зчитувачем для узгодження параметрів кадру та таймінгу ISO-DEP:

- **Байт 0 (RATS Header):** `0xE0`.
- **Байт 1 (Parameter Byte FSDI/CID):** 
  - Біти 7..4: `FSDI` (Frame Size Device Integer) — максимальний розмір кадру, який зчитувач може прийняти (від 0 = 16 байт до 8 = 256 байт).
  - Біти 3..0: `CID` (Card Identifier) — логічний номер каналу карти (від `0` до `14`).

У відповідь мітка повертає каскадну відповідь `ATS` (Answer to Select), яка містить байти параметрів `TA(1)`, `TB(1)`, `TC(1)` з вказівкою очікуваного часу розігріву (Frame Waiting Time, FWT = `(256 * 16 / f_c) * 2^FWI`) та підтримкою вищих швидкостей.

## 9. Таблиця команд ISO 14443-3 Type B та формат ATTRIB

На відміну від Type A, у Type B відсутні короткі кадри, а антиколізія спирається на команди опитування слотів (Slotted ALOHA):

| Байт команди | Назва команди | Опис та відповідь PICC |
| :--- | :--- | :--- |
| `0x05 0x00 0x00` | REQB / WUPB | Опитування поля з вказуванням кількості слотів N. Відповідь ATQB (12 байтів). |
| `0x1D ...` | ATTRIB | Вибір мітки за її 4-байтовим ідентифікатором PUPI. Відповідь Answer to ATTRIB. |
| `0x50 ...` | HLTB | Переведення мітки Type B у стан HALT. |

Команда `ATTRIB` містить такі основні поля (загалом 9 байтів + 2 байти CRC):
- `Header` (`0x1D`).
- `Identifier` (4 байти `PUPI`, отримані з `ATQB`).
- `Param 1` (1 байт): Таймінг та підтвердження `SOF`/`EOF`.
- `Param 2` (1 байт): Швидкість передачі даних (`DSI`/`DRI`) та розмір кадру `FSDI`.
- `Param 3` (1 байт): Підтримка протоколів вищого рівня.
- `Param 4` (1 байт): Номер каналу `CID`.

Таблиця декодування значень `FSDI` та `FSCI` (розмір кадру):

| Значення FSDI/FSCI | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Максимальний розмір кадру (байт)** | 16 | 24 | 32 | 40 | 48 | 64 | 96 | 128 | 256 |

## 10. Переговір швидкості PPS (Protocol and Parameter Selection)

Після активації ISO-DEP зчитувач може підвищити швидкість обміну даними з базової `106 кбіт/с` до `212`, `424` або `848 кбіт/с` за допомогою команди `PPS`:

- **Байт 0 (PPSS):** `0xD0 | CID` (індикатор виклику PPS).
- **Байт 1 (PPS0):** Прапори наявності PPS1 (`0x11`).
- **Байт 2 (PPS1):** Кодування швидкості:
  - `DSI` (біти 3..2): Швидкість від зчитувача до мітки (PCD -> PICC).
  - `DRI` (біти 1..0): Швидкість від мітки до зчитувача (PICC -> PCD).
  Значення: `00` = 106 кбіт/с, `01` = 212 кбіт/с, `10` = 424 кбіт/с, `11` = 848 кбіт/с.

## 11. Структура кадрів транспортного протоколу ISO 14443-4 (ISO-DEP) та APDU

Після вибору мітки (отримання SAK із встановленим бітом 5) передача керування переходить до протоколу ISO-DEP. Блок даних ISO-DEP починається з байта керування протоколом PCB (Protocol Control Byte):

```
+-------------------------------------------------------------------+
|                           ISO-DEP Frame                           |
+--------------+---------------+-------------------+----------------+
|  PCB (1 B)   | CID/NAD (1 B) | INF (Payload N B) |  EDC / CRC-16  |
+--------------+---------------+-------------------+----------------+
```

Типи блоків PCB визначаються двома старшими бітами 7..6:

1. **Інформаційний блок (I-Block, `PCB[7:6] = 00`):** Передає прикладні кадри APDU (Application Protocol Data Unit ISO/IEC 7816-4). Кадр APDU складається з заголовка `CLA INS P1 P2`, довжини даних `Lc`, масиву даних `Data` та очікуваної довжини відповіді `Le`.
   - Приклад відповіді смарт-карти (Response APDU): Тіло даних + 2 байти статусу `SW1 SW2` (наприклад, `0x90 0x00` вказує на успішне виконання).
2. **Блок квитування (R-Block, `PCB[7:6] = 10`):** Передає підтвердження прийому ACK (`PCB[4] = 0`) або вимогу повторного передавання NACK (`PCB[4] = 1`).
3. **Супервізорний блок (S-Block, `PCB[7:6] = 11`):** Використовується для службових команд:
   - `DESELECT` (`PCB = 0xC2`): Деактивація карти без вимкнення поля.
   - `WTX` (`PCB = 0xF2`): Запит розширення часу очікування (Wait Time Extension), коли смарт-карта виконує складне криптографічне обчислення.

При виникненні помилок зв'язку (помилка CRC або таймаут відповіді `FWT`) стек ISO-DEP виконує повторну спробу передавання шляхом надсилання R-Block(NACK) з поточним номером блоку. Якщо після 3 повторних спроб відповідь відсутня, сеанс вважається обірваним (Transmission Error).

## 12. Алгоритм та код розрахунку контрольної суми CRC-16 (ISO 14443-A)

Усі команди ISO 14443-A довжиною понад 1 байт супроводжуються 2 байтами контрольної суми CRC-16. Специфікація ISO/IEC 14443-3 визначає такі параметри алгоритму CRC-16 A:
- Початкове значення (Initial Value): `0x6363` (в HEX) / `25443` (у DEC).
- Поліном (Polynomial): `0x8408` (реверсований поліном `x^16 + x^12 + x^5 + 1`).
- Завершальна інверсія: відсутня.
- Порядок байтів у кадрі: Спочатку передається молодший байт CRC (LSB), потім старший (MSB).

Нижче наведено практичну реалізацію розрахунку CRC-16 ISO 14443-A мовами C та C++.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

uint16_t iso14443a_crc16(const uint8_t *data, size_t len) {
    uint16_t w_crc = 0x6363; // Початкове значення за ISO 14443-A

    for (size_t i = 0; i < len; i++) {
        uint8_t byte = data[i];
        byte ^= (uint8_t)(w_crc & 0x00FF);
        byte ^= (byte << 4);
        w_crc = (w_crc >> 8) ^ ((uint16_t)byte << 8) ^ ((uint16_t)byte << 3) ^ ((uint16_t)byte >> 4);
    }

    return w_crc;
}

void iso14443a_append_crc(uint8_t *buffer, size_t *len) {
    uint16_t crc = iso14443a_crc16(buffer, *len);
    buffer[*len] = (uint8_t)(crc & 0xFF);         // LSB першим
    buffer[*len + 1] = (uint8_t)((crc >> 8) & 0xFF); // MSB другим
    *len += 2;
}

bool iso14443a_check_crc(const uint8_t *buffer, size_t len) {
    if (len < 2) return false;
    uint16_t calc_crc = iso14443a_crc16(buffer, len - 2);
    uint16_t recv_crc = (uint16_t)buffer[len - 2] | ((uint16_t)buffer[len - 1] << 8);
    return calc_crc == recv_crc;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <vector>

namespace iso14443 {

class Crc16 {
public:
    static constexpr uint16_t INITIAL_VALUE = 0x6363;

    static uint16_t calculate(std::span<const uint8_t> data) noexcept {
        uint16_t w_crc = INITIAL_VALUE;

        for (uint8_t byte : data) {
            byte ^= static_cast<uint8_t>(w_crc & 0x00FF);
            byte ^= static_cast<uint8_t>(byte << 4);
            w_crc = (w_crc >> 8) ^
                    (static_cast<uint16_t>(byte) << 8) ^
                    (static_cast<uint16_t>(byte) << 3) ^
                    (static_cast<uint16_t>(byte) >> 4);
        }

        return w_crc;
    }

    static bool verify(std::span<const uint8_t> buffer) noexcept {
        if (buffer.size() < 2) return false;
        size_t payload_size = buffer.size() - 2;
        uint16_t calc_crc = calculate(buffer.subspan(0, payload_size));
        uint16_t recv_crc = static_cast<uint16_t>(buffer[payload_size]) |
                           (static_cast<uint16_t>(buffer[payload_size + 1]) << 8);
        return calc_crc == recv_crc;
    }

    static void append(std::vector<uint8_t>& buffer) {
        uint16_t crc = calculate(buffer);
        buffer.push_back(static_cast<uint8_t>(crc & 0xFF));
        buffer.push_back(static_cast<uint8_t>((crc >> 8) & 0xFF));
    }
};

} // namespace iso14443
```

## 13. Алгоритм та відмінності CRC-16 (ISO 14443-B)

Алгоритм обчислення контрольної суми для ISO 14443 Type B відрізняється початковим значенням та підсумковою інверсією:
- Початкове значення (Initial Value): `0xFFFF`.
- Поліном: `0x8408` (реверсований).
- Завершальне перетворення: Результат інвертується (XOR з `0xFFFF`).
- Порядок байтів: LSB першим, MSB другим.

Різниця у початкових значеннях CRC запобігає помилковому сприйняттю кадрів Type B зчитувачем Type A та навпаки на самому нижньому фізичному рівні детектування контролера. Точний контроль перевірки CRC гарантує захист від спотворення кадрів завадами.
