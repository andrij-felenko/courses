# 📜 Трикрокове рукостискання: як Томлінсон вирішив проблему ненадійної синхронізації

У перших експериментах із мережами пакетної комутації ранньої ARPANET протокол NCP (*Network Control Program*, лат. *protocolum*, грец. *πρωτόκολλον* — первісний запис) виходив із припущення, що фізичний канал зв'язку між вузлами або працює надійно, або повністю розірваний. NCP не мав наскрізної нумерації кожного байта даних. Натомість він покладався на механізм квитування окремих повідомлень через керуючі службові сигнали RFNM (*Ready for Next Message*): вузол-відправник міг передати лише одне повідомлення фіксованого розміру й мусив повністю зупинятися в очікуванні підтвердження від інтерфейсного процесора IMP (*Interface Message Processor*).

Коли мережа почала об'єднувати різнорідні сегменти через супутникові канали Atlantic Packet Satellite Network (SATNET), пакетизовані радіолінії Packet Radio Network (PRNET) та наземні лінії з динамічною маршрутизацією, модель NCP виявилася принципово непридатною. Пакети отримали можливість блукати різними маршрутами, затримуватися в чергах проміжних комутаторів на десятки секунд, дублюватися на рівні ретрансляторів і прибувати до отримувача через довільні проміжки часу з порушенням первинного порядку. Виникла фундаментальна проблема: як двом незалежним комп'ютерам у ненадійному розподіленому середовищі узгодити початок і кінець передачі даних так, щоб старий запізнілий пакет не пошкодив новий потік і не змусив вузол відкрити з'єднання-привид.

У вересні 1974 року комп'ютерний науковець Рей Томлінсон (*Raymond Samuel Tomlinson*, дослідницька корпорація BBN, творець мережевої пошти ARPANET та ініціатор вжитку символу `@`) представив результати дослідження *«Selecting Sequence Numbers»* (документ INWG Protocol Note #2, опублікований у матеріалах конференції ACM SIGCOMM/SIGOPS 1975). Його математичні моделі стали концептуальним ядром перших специфікацій TCP (RFC 675 Вінтона Серфа, Йогена Далала та Карла Саншайна, грудень 1974 року) і канонічного стандарту RFC 793 Джона Постела (1981). Томлінсон довів, що в розподіленій системі з ненульовою ймовірністю втрати та довільною затримкою пакетів безпечна синхронізація стану неможлива без трьох фаз взаємного квитування.

## Чому двокликовий обмін зазнає краху

Інтуїтивне уявлення про встановлення зв'язку, запозичене з комутованих телефонних ліній, пропонує двокрокову схему: сторона A надсилає стороні B запит «з'єднаймось», а сторона B відповідає «згоден, з'єднання встановлено». У телефонній мережі з виділеними фізичними ланцюгами це працює, оскільки комутатор створює неперервний електричний тракт. Проте в мережі з комутацією пакетів цей підхід породжує непереборну вразливість перед запізнілими дублікатами.

Розглянемо послідовність подій, що призводить до відмови двокликового протоколу:

1. Вузол A надсилає запит на відкриття з'єднання з початковим номером послідовності `ISN = x`.
2. Пакет потрапляє в перевантажений проміжний маршрутизатор і застрягає в буферній черзі інтерфейсу на кілька секунд або хвилин через затор чи тимчасову зміну таблиць маршрутизації.
3. Вузол A не отримує відповіді за власним локальним таймаутом передачі, вважає спробу невдалою, закриває локальний сокет або генерує новий запит на іншому номері порту.
4. Через деякий час запізнілий перший пакет нарешті виходить із черги маршрутизатора й дістається вузла B.
5. У двокликовій моделі вузол B, отримавши запит, не має жодного способу дізнатися, чи цей пакет є актуальним і свіжим, чи це «фантом» із минулого. Вузол B виділяє пам'ять під системні буфери, створює структуру з'єднання (*Transmission Control Block*, TCB), переходить у стан повної готовності приймати дані й відправляє підтвердження вузлу A.
6. Вузол A отримує підтвердження на запит, про який він уже давно забув (або для сокета, якого більше не існує в операційній системі), і просто відкидає цю неочікувану відповідь.

У результаті на вузлі B виникає «напіввідкрите з'єднання-привид» (*half-open connection*). Сервер тримає заблоковані системні ресурси й марно очікує передачі даних від клієнта, який навіть не підозрює про існування цього з'єднання. Якщо ж услід за цим запізнілим запитом із мережі прибудуть старі запізнілі пакети даних від минулої сесії, вузол B прийме їх як свіжі корисні дані нового сеансу, спричинивши непоправне спотворення файлу чи командного потоку застосунку.

## Механізм трьох повідомлень Томлінсона

Рей Томлінсон запропонував розірвати це замкнене коло через додавання обов'язкової третьої фази — підтвердження з боку ініціатора. Тільки той вузол, який ініціював з'єднання, володіє повним контекстом і може достовірно підтвердити, що він справді очікує відповіді на надісланий ним номер послідовності.

```
Вузол A (Клієнт)                         Вузол B (Сервер)
      |                                         |
      | -------- 1. SYN (SEQ = x) ------------> |  (Запит ініціатора)
      |                                         |
      | <------- 2. SYN-ACK (SEQ = y, -------- |  (Відповідь + зустрічний запит)
      |                      ACK = x + 1)       |
      |                                         |
      | -------- 3. ACK (ACK = y + 1) --------> |  (Фінальне підтвердження)
      |                                         |
[ESTABLISHED]                             [ESTABLISHED]
```

Принципова роль кожного з трьох повідомлень полягає в суворому розподілі обов'язків:

- **Перше повідомлення (`SYN`, англ. *synchronize* — синхронізувати)**: Вузол A обирає власний початковий номер послідовності `x` (*Initial Sequence Number*, ISN) і пропонує його вузлу B як базис відліку байтів у прямому напрямку A → B. Вузол A переходить у стан очікування підтвердження `SYN_SENT`.
- **Друге повідомлення (`SYN-ACK`)**: Вузол B підтверджує отримання номера `x` (виставляючи квитанцію `ACK = x + 1`) і **одночасно** генерує власний незалежний номер послідовності `y` для зворотного напрямку передачі B → A. Вузол B переходить у стан `SYN_RCVD`, але ще не вважає з'єднання повноцінно відкритим для передачі корисних даних застосунку — він лише фіксує намір і очікує доказу легітимності від клієнта.
- **Третє повідомлення (`ACK`, англ. *acknowledge* — підтверджувати)**: Вузол A отримує квитанцію на свій номер `x`. Тепер клієнт A точно знає, що сервер B почув саме актуальний запит. Вузол A підтверджує отримання номера `y` від сервера (`ACK = y + 1`) і переходить у робочий стан `ESTABLISHED`. Тільки після отримання цього третього пакета вузол B остаточно переводить з'єднання у стан `ESTABLISHED` і передає готовий сокет у чергу на вичитку процесу користувача.

### Як три кроки нейтралізують запізнілий дублікат

Якщо до вузла B дійде запізнілий дублікат `SYN` з номером `x_old`:

1. Вузол B відповідає пакетом `SYN-ACK` з номером підтвердження `ACK = x_old + 1` та новим випадковим `SEQ = y`.
2. Вузол A отримує цей пакет `SYN-ACK` і перевіряє поле квитанції: воно містить значення `x_old + 1`, тоді як клієнт A або перебуває в стані `CLOSED`, або очікує підтвердження для зовсім іншого номера `x_current`.
3. Виявивши невідповідність номерів послідовностей, клієнт A не відправляє фінальний `ACK`, а негайно надсилає у відповідь пакет зі скиданням прапорця `RST` (*Reset*) з номером `SEQ = x_old + 1`.
4. Вузол B, отримавши `RST`, миттєво знищує створену чернетку структури TCB і безслідно вивільняє пам'ять. Жодне хибне з'єднання не залишається заблокованим у системі.

## Синхронізація годинників та розрахунок швидкості таймера

Окрім протоколу трьох повідомлень, Томлінсон сформулював концепцію прив'язки вибору початкових номерів послідовності до монотонного таймера (*Clock-Driven ISN Generation*). Головна мета полягала в тому, щоб гарантувати, що значення ISN для нового з'єднання ніколи не потрапить у діапазон номерів послідовностей, які все ще можуть циркулювати в мережі від попереднього сеансу з тим самим 4-кортежем сокетів (`src_ip`, `src_port`, `dst_ip`, `dst_port`).

Для цього було введено фундаментальну константу мережі — максимальний час життя сегмента MSL (*Maximum Segment Lifetime*, час, протягом якого будь-який пакет або буде доставлений, або буде знищений маршрутизаторами через вичерпання лічильника TTL/Hop Limit). За RFC 793 теоретичне значення MSL було визначено як 2 хвилини (120 секунд).

Томлінсон запропонував, щоб глобальний лічильник ISN збільшувався на 1 кожні 4 мікросекунди (тактова частота генератора 250 кГц). Оскільки поле номера послідовності в заголовку TCP є 32-бітним цілим числом (`2³² = 4 294 967 296` значень), повний оберт лічильника займає:

```
Час_повного_оберту = 2³² × 4 мкс
                    = 4 294 967 296 × 0.000004 с
                    ≈ 17 179.86 с
                    ≈ 4.77 години
```

Оскільки 4.77 години значно перевищують подвійний час життя пакета в мережі (`2·MSL = 240` секунд), будь-який старий дублікат сегмента гарантовано зникав із мережі задовго до того, як генератор ISN міг повернутися до того самого числового діапазону.

## Криптографічний злам та еволюція до RFC 6528

Вінтон Серф (*Vinton Gray Cerf*) та Роберт Кан (*Robert Elliot Kahn*) включили алгоритм Томлінсона до специфікації протоколу TCP у RFC 675 (грудень 1974 року), а у вересні 1981 року він був стандартизований як обов'язковий канон у RFC 793.

Протягом майже півтора десятиліття класична лінійна схема вибору ISN вважалася абсолютно надійною. Проте вона враховувала лише випадкові збої середовища передачі даних і не передбачала наявності активного зловмисника в мережі.

У 1989 році Роберт Морріс (*Robert Tappan Morris*), а в 1995 році Стівен Белловін (*Steven M. Bellovin*, публікація Bell Labs *«Defending Against Sequence Number Attacks»*) виявили критичну вразливість лінійного таймера. Оскільки генератор ISN у більшості реалізацій BSD Unix просто збільшував лічильник на константу кожну секунду (наприклад, додавав 250 000 кожні 1000 мс) та додавав фіксоване зміщення для кожного нового виклику `connect()`, зловмисник міг легко передбачити наступне значення `ISN_s` сервера.

Найвідомішим практичним застосуванням цієї вразливості стала атака на Різдво 1994 року, здійснена Кевіном Мітніком проти комп'ютера фахівця з кібербезпеки Цутому Сімомури (*Tsutomu Shimomura*):

1. Зловмисник вивів з ладу довірений сервер аутентифікації за допомогою SYN-флуду, щоб той не міг надіслати `RST`.
2. Потім зловмисник надіслав `SYN` на цільовий сервер від імені IP-адреси виведеного з ладу довіреного хоста.
3. Цільовий сервер відповів пакетом `SYN-ACK`, який пішов на адресу довіреного хоста (і був ним проігнорований). Зловмисник не міг бачити цей пакет у мережі.
4. Проте, на основі попередніх вимірювань затримки та кроку генератора ISN, зловмисник наосліп розрахував значення `ISN_s`, згенерував фіктивний `ACK` з точно передбаченим номером підтвердження і відкрив повноцінне з'єднання через сервіс `rsh`, виконавши довільні команди з правами суперкористувача.

Для ліквідації цього класу атак Стів Белловін у RFC 1948 (1996 рік), а згодом IETF у RFC 6528 затвердили сучасний стандарт генерації ISN. У сучасних операційних системах початковий номер послідовності формується як сума монотонного таймера високої точності та криптографічної псевдовипадкової функції (*Pseudo-Random Function*, PRF), яка обчислює геш (SipHash або HMAC-MD5) від 4-кортежу сокета та секретного рандомізованого ключа, що генерується ядром операційної системи під час завантаження:

```
ISN = (Таймер_мкс) + PRF(src_ip, src_port, dst_ip, dst_port, Secret_Key) (mod 2³²)
```

Завдяки цьому рішенню кожен новий сеанс між хостами отримує повністю непередбачуваний для зовнішнього спостерігача номер послідовності, тоді як сам математичний каркас трикрокового рукостискання, винайдений Реєм Томлінсоном, залишається незмінним фундаментом надійності Інтернету вже понад півстоліття.
