# 📋 Системні параметри та параметри сокетів для керування життєвим циклом TCP

Усі етапи життєвого циклу TCP-з'єднання — від початкового трьохетапного рукостискання й черг очікування ядра до таймаутів напівзакритого стану та переробки сокетів у стані `TIME_WAIT` — регулюються двома рівнями конфігурації в операційній системі Linux. Перший рівень — це локальні параметри окремого дескриптора сокета через системні виклики `setsockopt()` та `getsockopt()`. Другий рівень — це глобальні параметри мережевого стека ядра, доступні через інтерфейс `sysctl` та псевдофайлову систему `/proc/sys/net/`.

Нижче наведено повний інженерний довідник параметрів сокетів, системних структур, значень за замовчуванням, граничних умов та архітектурних наслідків їхнього застосування.

## 1. Системний виклик `setsockopt` та параметри сокетів

Конфігурація поведінки окремого сокета виконується через системний виклик POSIX `setsockopt()`, який приймає дескриптор сокета, рівень протоколу (`SOL_SOCKET` для загальних опцій сокетів або `IPPROTO_TCP` для специфічних опцій транспортного рівня), назву опції та вказівник на структуру зі значенням.

### Опція `SO_REUSEADDR` (Рівень `SOL_SOCKET`)

Опція `SO_REUSEADDR` приймає цілочисельний булевий прапорець (`int`, `0` або `1`). Її головне призначення — дозволити локальному процесу прив'язати сокет до локальної IP-адреси та порту за допомогою виклику `bind()`, навіть якщо на цьому ж 5-кортежі вже існує сокет у стані `TIME_WAIT` від попереднього сеансу.

За замовчуванням (`SO_REUSEADDR = 0`) операційна система Linux блокує будь-яку спробу прив'язки до порту, якщо в системній таблиці сокетів присутній хоча б один запис у стані `TIME_WAIT` з цією ж адресою, повертаючи помилку `EADDRINUSE` (*Address already in use*). Це захищає від ситуації, коли старий процес перезапустився, але мережа ще містить запізнілі сегменти від попереднього сеансу.

Увімкнення `SO_REUSEADDR = 1` дозволяє серверним процесам миттєво перезапускатися після аварійного завершення або планового оновлення без вимушеного очікування протягом 60 секунд (тривалість `2 * MSL`). Якщо на порт надходить новий пакет `SYN`, ядро створює нове з'єднання, безпечно витісняючи старий стан `TIME_WAIT`, за умови, що нові номери послідовностей не перетинаються зі старими.

Окрім цього, `SO_REUSEADDR` дозволяє прив'язувати конкретну IP-адресу (наприклад, `192.168.1.10:80`), якщо раніше інший сокет уже був прив'язаний до універсальної адреси `INADDR_ANY:80` (`0.0.0.0:80`), за умови, що обидва сокети виставили цей прапорець.

### Опція `SO_REUSEPORT` (Рівень `SOL_SOCKET`, Linux 3.9+)

Опція `SO_REUSEPORT` приймає булевий прапорець (`int`) і дозволяє кільком незалежним сокетам (наприклад, у різних процесах-воркерах веб-сервера Nginx або пулі потоків програми на C++) одночасно викликати `bind()` та `listen()` на абсолютно однаковій комбінації IP-адреси та порту.

Усі сокети, що використовують `SO_REUSEPORT`, повинні належати процесам з однаковим ефективним ідентифікатором користувача (`effective UID`), що виключає можливість перехоплення портів неавторизованими локальними користувачами.

Ядро формує масив слухаючих сокетів (`struct sock_reuseport`) і при надходженні кожного нового пакета `SYN` автоматично розподіляє вхідні з'єднання між цими сокетами за допомогою детерміністичного 4-кортежного гешування (`hash(src_ip, src_port, dst_ip, dst_port) % N`). Це повністю вирішує проблему «стадного ефекту» (*thundering herd problem*), зменшує блокування системних черг і забезпечує лінійне масштабування обробки запитів на багатоядерних процесорах без необхідності передачі дескрипторів через UNIX domain sockets.

### Опція `SO_LINGER` (Рівень `SOL_SOCKET`)

Опція `SO_LINGER` керує поведінкою системного виклику `close()` у ситуації, коли в системному буфері відправки сокета все ще залишаються непередані або непідтверджені дані застосунку. Опція налаштовується за допомогою структури `struct linger` (`int l_onoff; int l_linger;`): `l_onoff` визначає активність режиму (`0` — вимкнено, `1` — увімкнено), а `l_linger` задає таймаут блокування в секундах.

Розрізняють три принципові режими роботи цієї структури:

1. **`l_onoff = 0` (Штатний асинхронний режим за замовчуванням):** Виклик `close()` повертає керування миттєво (`0`). Ядро бере на себе повну відповідальність за залишок даних у буфері передачі, фоново намагається доставити їх отримувачу, після чого ініціює стандартну процедуру чотирикрокового розриву з'єднання (відправляє `FIN` і переходить у `FIN_WAIT_1`). Процес користувача не блокується, але не має можливості дізнатися, чи були дані фактично доставлені, чи виникла мережева помилка.
2. **`l_onoff = 1, l_linger > 0` (Синхронне блокуюче закриття):** Системний виклик `close()` блокує викликаючий потік доти, доки всі дані з буфера відправки не будуть передані й підтверджені віддаленою стороною за допомогою квитанцій `ACK`, або доки не спливе вказаний інтервал у `l_linger` секунд. Якщо дані успішно доставлено, `close()` повертає `0`. Якщо таймаут вичерпався, а підтвердження не отримано, `close()` повертає `-1`, встановлюючи змінну `errno` у значення `EWOULDBLOCK` (або `ETIMEDOUT`). Якщо сокет було переведено в неблокуючий режим (`O_NONBLOCK`), виклик `close()` завершується з помилкою `EWOULDBLOCK` негайно, а процес фонового закриття продовжується в ядрі.
3. **`l_onoff = 1, l_linger = 0` (Аварійне скидання з'єднання / Abortive Release):** Системний виклик `close()` миттєво знищує структуру сокета, очищає черги прийому та відправки, відкидаючи всі непередані та непрочитані байти, і надсилає віддаленій стороні пакет зі скиданням `RST`. Сокет **повністю оминає стан `TIME_WAIT`** і відразу переходить у стан `CLOSED`. Віддалена сторона при спробі читання або запису отримує помилку `ECONNRESET` (*Connection reset by peer*). Цей режим використовується в системах екстремального навантаження для миттєвого звільнення пам'яті та ефемерних портів, проте він порушує надійність доставки TCP і повинен застосовуватися лише за суворої архітектурної необхідності.

### Опція `TCP_NODELAY` (Рівень `IPPROTO_TCP`)

Опція `TCP_NODELAY` приймає цілочисельний прапорець (`int`, `0` або `1`) і безпосередньо керує роботою алгоритму Нейгла (*Nagle's algorithm*, RFC 896).

Алгоритм Нейгла призначений для запобігання перевантаженню мережі надмірною кількістю дрібних пакетів (наприклад, поодиноких натискань клавіш у сесіях Telnet або SSH). Якщо застосунок записує в сокет порції даних, менші за максимальний розмір сегмента (`MSS`), ядро затримує відправку наступного пакета доти, доки від отримувача не надійде підтвердження `ACK` на попередній переданий сегмент або доки буфер не заповниться до розміру `MSS`.

У поєднанні з механізмом відкладених підтверджень (*Delayed ACK*, де отримувач чекає до 40–200 мс перед відправкою квитанції, сподіваючись об'єднати її з відповіддю застосунку), алгоритм Нейгла спричиняє штучні затримки у 40–200 мс на кожен запит. Увімкнення `TCP_NODELAY = 1` повністю вимикає алгоритм Нейгла, примушуючи стек TCP відправляти сегменти будь-якого розміру негайно, що є критично важливим для RPC-систем (gRPC), веб-сокетів та баз даних.

### Опція `TCP_DEFER_ACCEPT` (Рівень `IPPROTO_TCP`)

Опція `TCP_DEFER_ACCEPT` приймає ціле число секунд (`int`). Вона дозволяє оптимізувати роботу високонавантажених серверів протоколів із моделлю «клієнт говорить першим» (наприклад, HTTP або TLS).

У класичній моделі TCP після завершення трьохетапного рукостискання (клієнт надіслав фінальний `ACK`) сокет переходить у стан `ESTABLISHED` і негайно переміщується в чергу готових з'єднань, пробуджуючи серверний процес через виклик `accept()` або подію `epoll`. Проте якщо клієнт повільний або ініціює атаку типу Slowloris, серверний процес виділяє пам'ять і блокується в очікуванні корисних даних.

При встановленні `TCP_DEFER_ACCEPT = N` ядро утримує з'єднання в черзі `SYN_RCVD` і не сповіщає процес користувача через `accept()`, доки від клієнта не надійдуть перші корисні дані запиту. Якщо протягом `N` секунд клієнт не надіслав даних, ядро повторно надсилає пакети `SYN-ACK`, а після вичерпання таймауту розриває з'єднання без залучення процесу користувача.

### Опція `TCP_USER_TIMEOUT` (Рівень `IPPROTO_TCP`, RFC 5482)

Опція `TCP_USER_TIMEOUT` приймає беззнакове ціле число в мілісекундах (`unsigned int`). Вона задає максимальний часовий інтервал, протягом якого надіслані корисні дані можуть залишатися без підтвердження квитанцією `ACK`, перш ніж ядро операційної системи примусово розірве з'єднання й поверне процесу помилку `ETIMEDOUT`.

На відміну від стандартних повторних передач (*retransmissions*), де кількість спроб регулюється глобальним параметром ядра `tcp_retries2` і може розтягуватися на 15–20 хвилин за наявності експоненційного відкату таймера, `TCP_USER_TIMEOUT` дозволяє застосунку чітко обмежити час очікування відповіді на рівні сокета (наприклад, 5000 мс), що є життєво необхідним для мікросервісних архітектур та систем виявлення збоїв.

## 2. Глобальні параметри ядра Linux (`sysctl`)

Глобальні параметри мережевого стека визначають поведінку черг ядра, тривалість станів FSM та ліміти виділення пам'яті. Вони налаштовуються у файлі `/etc/sysctl.conf` або через запис у псевдофайли каталогу `/proc/sys/net/ipv4/`.

### Параметр `net.ipv4.tcp_tw_reuse`

Параметр `tcp_tw_reuse` регулює можливість повторного використання сокета, що перебуває в стані `TIME_WAIT`, для створення нового вихідного клієнтського з'єднання через системний виклик `connect()`.

- **Значення `0` (Вимкнено):** Сокет у стані `TIME_WAIT` не може бути використаний для нового підключення. При спробі відкрити з'єднання з тим самим 5-кортежем виклик `connect()` повертає помилку `EADDRNOTAVAIL` (*Cannot assign requested address*).
- **Значення `1` (Увімкнено для локальних з'єднань):** Дозволяє ядру повторно виділяти 5-кортеж, зайнятий станом `TIME_WAIT`, якщо виконуються дві суворі умови протоколу: (1) обидві сторони підтримують опцію протокольних міток часу TCP Timestamps (RFC 7323, параметр `net.ipv4.tcp_timestamps = 1`); (2) поточна мітка часу нового пакета `SYN` (`TSval`) монотонно більша за останню мітку часу, зафіксовану в попередньому сеансі. Завдяки алгоритму PAWS (*Protection Against Wrapped Sequences*) ядро надійно відрізняє нові пакети від запізнілих дублікатів старого сеансу.
- **Значення `2` (Увімкнено для всіх напрямків у Linux 5.x+):** Розширює дію механізму на всі зовнішні та внутрішні мережеві маршрути з суворою валідацією міток часу.

### Чому параметр `net.ipv4.tcp_tw_recycle` було видалено

У старих версіях ядра Linux (до версії 4.11 включно) існував агресивний параметр `net.ipv4.tcp_tw_recycle`. Він намагався прискорити переробку сокетів `TIME_WAIT` як для вхідних, так і для вихідних з'єднань, зберігаючи останню мітку часу `TSval` для кожної віддаленої IP-адреси у глобальній таблиці маршрутизації.

Це призводило до катастрофічних наслідків у реальному Інтернеті: якщо кілька незалежних клієнтських комп'ютерів виходили в мережу через один спільний корпоративний або операторський шлюз трансляції мережевих адрес (NAT), їхні внутрішні апаратні таймери не були синхронізовані. Коли клієнт A з більшим значенням локального таймера відкривав з'єднання, сервер фіксував його мітку часу. Коли через мілісекунду клієнт B з меншим локальним таймером намагався підключитися через той самий NAT (з тієї ж зовнішньої IP-адреси), сервер бачив, що `TSval_B < TSval_A`, вважав пакет `SYN` запізнілим фантомним дублікатом і **мовчки відкидав його**. Клієнти за NAT стикалися з періодичною повною недоступністю сайтів. Через це в ядрі Linux 4.12 параметр `tcp_tw_recycle` було остаточно видалено.

### Параметр `net.ipv4.tcp_fin_timeout`

Параметр `tcp_fin_timeout` (типове значення — 60 секунд) задає максимальний час очікування для осиротілих сокетів (*orphaned sockets*), які перебувають у стані `FIN_WAIT_2`.

Осиротілим вважається сокет, який процес користувача повністю закрив через системний виклик `close()`, але віддалена сторона отримала `FIN`, відповіла `ACK` (перейшовши у стан `CLOSE_WAIT`) і з якихось причин (зависання процесу, помилка в коді) не надсилає власний зустрічний `FIN`.

Оскільки дескриптора сокета в просторі користувача більше не існує, застосунок не може вплинути на ситуацію. Щоб запобігти вічному витоку пам'яті ядра на утримання таких сокетів, таймер `tcp_fin_timeout` відраховує вказану кількість секунд, після чого ядро примусово знищує структуру з'єднання й надсилає віддаленому вузлу пакет `RST`.

### Параметр `net.ipv4.tcp_max_tw_buckets`

Параметр `tcp_max_tw_buckets` (типово від 65536 до 262144) встановлює жорсткий системний ліміт на сукупну кількість сокетів, які можуть одночасно перебувати в стані `TIME_WAIT` у всій операційній системі.

Цей механізм є захистом від атак на вичерпання пам'яті ядра (*Denial of Service*). Якщо вхідний потік з'єднань, що швидко закриваються, перевищує значення `tcp_max_tw_buckets`, ядро не виділяє нових слотів `TIME_WAIT`. Натомість воно миттєво знищує найстаріший сокет у черзі `TIME_WAIT`, виводить попередження в системний журнал ядра (`dmesg`):

```
TCP: time wait bucket table overflow
```

і закриває сокет без очікування `2 * MSL`. Хоча це рятує сервер від браку оперативної пам'яті, це створює ризик пошкодження даних запізнілими дублікатами в мережах із високою затримкою.

### Параметр `net.ipv4.ip_local_port_range`

Параметр `ip_local_port_range` містить два цілих числа, розділених пробілом або табуляцією (наприклад, `32768 60999`), що визначають нижню та верхню межу пулу ефемерних портів.

Ці порти операційна система автоматично призначає вихідним з'єднанням, коли клієнт викликає `connect()` без попереднього явного виклику `bind()`. За замовчуванням доступно $60999 - 32768 + 1 = 28232$ порти. Для високонавантажених зворотних проксі-серверів (Nginx, HAProxy, Envoy), які встановлюють десятки тисяч з'єднань на секунду до одного бекенду, цей діапазон розширюють до максимального дозволеного значення:

```bash
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

Це збільшує пул до $64512$ портів, суттєво відсуваючи поріг вичерпання вільних 5-кортежів.

### Параметри черг `net.ipv4.tcp_max_syn_backlog` та `net.core.somaxconn`

Слухаючий сокет у Linux використовує архітектуру двох окремих черг ядра:

1. **Черга напіввідкритих з'єднань (`SYN Queue` або `syn_backlog`):** Зберігає структури запитів клієнтів, які надіслали `SYN`, отримали від сервера `SYN-ACK`, але ще не надіслали фінальний `ACK` (стан `SYN_RCVD`). Розмір цієї черги обмежується параметром `net.ipv4.tcp_max_syn_backlog` (типово 1024–4096). При її переповненні нові запити на підключення відкидаються, або вмикається механізм криптографічних квитанцій `SYN Cookies` (`net.ipv4.tcp_syncookies = 1`).
2. **Черга повністю встановлених з'єднань (`Accept Queue`):** Зберігає готові з'єднання в стані `ESTABLISHED`, які пройшли трикрокове рукостискання й очікують, поки процес викличе функцію `accept()`. Максимальна довжина цієї черги визначається як мінімум між значенням аргументу `backlog` у системному виклику `listen(fd, backlog)` та глобальним обмеженням ядра `net.core.somaxconn` (типово 4096 у сучасних дистрибутивах). Якщо черга переповнена через те, що застосунок не встигає викликати `accept()`, ядро за замовчуванням ігнорує нові пакети `ACK`, змушуючи клієнта повторювати спроби підключення.

## 3. Діагностика станів сокетів утилітами ядра

Основним інструментом інспекції життєвого циклу TCP в сучасних дистрибутивах Linux є утиліта `ss` (*Socket Statistics*, підсистема `iproute2`), що взаємодіє з ядром через швидкісний бінарний інтерфейс Netlink (`NETLINK_INET_DIAG`).

### Ключові команди моніторингу станів

```bash
# Підрахунок кількості сокетів у кожному стані FSM
ss -s

# Вибірка всіх з'єднань у стані TIME_WAIT з числовими адресами
ss -tan state time-wait

# Вибірка сокетів, що очікують закриття процесом (CLOSE_WAIT)
ss -tan state close-wait

# Інспекція черг слухаючого сокета (Send-Q = somaxconn, Recv-Q = поточна accept_queue)
ss -ltn '( sport = :80 or sport = :443 )'

# Перегляд внутрішніх таймерів TCP (таймаути TIME_WAIT, Keepalive, Retransmission)
ss -tano state time-wait
```

### Структура внутрішньої статистики `/proc/net/sockstat`

Файл `/proc/net/sockstat` надає миттєвий глобальний зріз використання пам'яті та кількості структур сокетів у ядрі:

```
TCP: inuse 142 orphan 0 tw 852 alloc 160 mem 18
```

- `inuse` — кількість відкритих сокетів у станах `LISTEN`, `SYN_SENT`, `SYN_RCVD`, `ESTABLISHED`, `CLOSE_WAIT`, `FIN_WAIT_1`, `FIN_WAIT_2`, `LAST_ACK`.
- `orphan` — осиротілі з'єднання (сокет закрито процесом користувача через `close()`, але ядро все ще утримує структуру в пам'яті для завершення передачі або очікування `FIN` у `FIN_WAIT_2`).
- `tw` — кількість легковажних структур сокетів у стані `TIME_WAIT` (обслуговуються спеціальним міні-контролером ядра без виділення повного дескриптора сокета).
- `alloc` — загальна кількість алокованих структур `struct sock`.
- `mem` — обсяг сторінок оперативної пам'яті ядра (розміром по 4 КБ), задіяних під буфери прийому й передачі TCP.

## 4. Приклад програмного налаштування життєвого циклу сокета

Нижче наведено приклад створення та налаштування серверного сокета з використанням параметрів `SO_REUSEADDR`, `TCP_NODELAY` та `TCP_USER_TIMEOUT`.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

int configure_server_socket(int port) {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) {
        perror("socket");
        return -1;
    }

    /* 1. Дозволити миттєвий перезапуск сервера на порту у TIME_WAIT */
    int reuse_addr = 1;
    if (setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &reuse_addr, sizeof(reuse_addr)) < 0) {
        perror("setsockopt SO_REUSEADDR");
        close(fd);
        return -1;
    }

    /* 2. Вимкнути затримку алгоритму Нейгла для швидкої реакції */
    int nodelay = 1;
    if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay)) < 0) {
        perror("setsockopt TCP_NODELAY");
        close(fd);
        return -1;
    }

    /* 3. Встановити користувацький таймаут доставки даних у 10 секунд */
    unsigned int user_timeout_ms = 10000;
    if (setsockopt(fd, IPPROTO_TCP, TCP_USER_TIMEOUT, &user_timeout_ms, sizeof(user_timeout_ms)) < 0) {
        perror("setsockopt TCP_USER_TIMEOUT");
        close(fd);
        return -1;
    }

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof(addr));
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons((uint16_t)port);

    if (bind(fd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("bind");
        close(fd);
        return -1;
    }

    if (listen(fd, 1024) < 0) {
        perror("listen");
        close(fd);
        return -1;
    }

    return fd;
}
```

```cpp
#include <iostream>
#include <string_view>
#include <expected>
#include <system_error>
#include <memory>
#include <cstring>
#include <unistd.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

class SafeSocket {
private:
    int fd_{-1};

public:
    explicit SafeSocket(int fd) noexcept : fd_{fd} {}
    ~SafeSocket() noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

    SafeSocket(const SafeSocket&) = delete;
    SafeSocket& operator=(const SafeSocket&) = delete;

    SafeSocket(SafeSocket&& other) noexcept : fd_{other.fd_} {
        other.fd_ = -1;
    }

    SafeSocket& operator=(SafeSocket&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) {
                ::close(fd_);
            }
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }

    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] bool valid() const noexcept { return fd_ >= 0; }
};

[[nodiscard]] std::expected<SafeSocket, std::error_code>
create_configured_server(uint16_t port) noexcept {
    int raw_fd = ::socket(AF_INET, SOCK_STREAM, 0);
    if (raw_fd < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    SafeSocket sock(raw_fd);

    // 1. Дозволити швидкий bind при TIME_WAIT
    const int reuse_addr = 1;
    if (::setsockopt(sock.get(), SOL_SOCKET, SO_REUSEADDR, &reuse_addr, sizeof(reuse_addr)) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    // 2. Вимкнути алгоритм Нейгла
    const int nodelay = 1;
    if (::setsockopt(sock.get(), IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay)) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    // 3. Встановити таймаут непідтверджених даних (10 000 мс)
    const unsigned int timeout_ms = 10000;
    if (::setsockopt(sock.get(), IPPROTO_TCP, TCP_USER_TIMEOUT, &timeout_ms, sizeof(timeout_ms)) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons(port);

    if (::bind(sock.get(), reinterpret_cast<const sockaddr*>(&addr), sizeof(addr)) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    if (::listen(sock.get(), 1024) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }

    return sock;
}
```
