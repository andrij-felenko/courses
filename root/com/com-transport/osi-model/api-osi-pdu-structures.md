# 📋 Специфікація двійкових структур PDU та протоколів стеку OSI

Цей технічний довідник містить побайтову специфікацію двійкових форматів блоків протокольних даних (PDU, англ. *Protocol Data Unit*), схеми адресації точок доступу до послуг (SAP) та правила серіалізації даних, що утворюють канонічний протокольний стек архітектури **OSI** (ISO/IEC 7498-1). Наведені структури визначають протокол мережевого рівня **CLNP** (ISO 8473), транспортний протокол класу 4 **TP4** (ISO 8073 / ITU-T X.224), структури сеансового рівня **SPDU** (ISO 8327 / ITU-T X.225), прикладні сервісні елементи **ACSE / ROSE**, ієрархічні мережеві адреси **NSAP** та синтаксис представлення даних **ASN.1 / BER** (ISO/IEC 8825-1).

---

## 1. Мережевий рівень: заголовок пакета CLNP (ISO 8473)

Протокол **CLNP** (*Connectionless Network Protocol*, ISO 8473 / ITU-T X.233) є безз'єднувальним мережевим протоколом стека OSI, функціональним еквівалентом IPv4/IPv6. На відміну від фіксованого 20-байтного заголовка IPv4, заголовок CLNP має змінну довжину через використання адрес змінної довжини (до 20 байтів на кожну адресу) та механізм необов'язкових параметрів TLV (*Type-Length-Value*).

### 1.1. Фіксована частина заголовка (Fixed Part)

Фіксована частина заголовка CLNP займає рівно 9 байтів (октетів) і розміщується на самому початку мережевого пакета:

| Зміщення (байт) | Поле | Розмір | Опис та допустимі значення |
|---|---|---|---|
| `0` | **Network Layer Protocol ID (NLPID)** | 1 байт | Ідентифікатор протоколу мережевого рівня. Для повнофункціонального CLNP завжди дорівнює `0x81`. Для спрощеного протоколу Inactive Subnetwork Protocol — `0x00`, для ES-IS — `0x82`, для IS-IS — `0x83`. |
| `1` | **Length Indicator (LI)** | 1 байт | Загальна довжина заголовка CLNP в байтах (включно з адресами, полями сегментації та опціями). Максимальне значення — 254 байти. |
| `2` | **Version / Protocol Extension** | 1 байт | Номер версії протоколу. Стандартне значення — `0x01`. |
| `3` | **Lifetime (PDU Lifetime)** | 1 байт | Час життя пакета. Вимірюється в одиницях по 500 мс (півсекунди). Кожен маршрутизатор зменшує це значення щонайменше на 1 одиницю (або на час обробки пакета). Коли поле досягає `0`, пакет відкидається. |
| `4` | **Flags / Type** | 1 байт | Бітові прапорці керування та 5-бітний тип пакета (розкрито нижче). |
| `5..6` | **Segment Length** | 2 байти | Загальна довжина поточного сегмента (заголовок + дані) у байтах (Big-Endian / Network Byte Order). |
| `7..8` | **Checksum** | 2 байти | 16-бітна контрольна сума Флетчера (Fletcher-16), розрахована виключно по всьому заголовку CLNP. Значення `0x0000` означає, що перевірка суми вимкнена. |

### 1.2. Бітова розкладка байта прапорців і типу (Flags/Type Byte, зміщення 4)

Байт зі зміщенням 4 складається з трьох 1-бітних прапорців у старших розрядах та 5-бітного коду типу PDU у молодших розрядах:

```
  Біт 7    Біт 6    Біт 5    Біт 4   Біт 3   Біт 2   Біт 1   Біт 0
┌────────┬────────┬────────┬───────┬───────┬───────┬───────┬───────┐
│   SP   │   MS   │   E/R  │              Type (тип PDU)           │
└────────┴────────┴────────┴───────┴───────┴───────┴───────┴───────┘
```

- **SP (Segmentation Permitted, біт 7):**
  `1` — сегментація дозволена (проміжним маршрутизаторам дозволено ділити пакет при невідповідності MTU);
  `0` — сегментація заборонена (якщо пакет не вміщується в MTU вихідного каналу, він відкидається).
- **MS (More Segments, біт 6):**
  `1` — поточний пакет є проміжним фрагментом (після нього будуть наступні фрагменти);
  `0` — останній фрагмент або неподілений пакет.
- **E/R (Error Report, біт 5):**
  `1` — відправляти пакет звіту про помилку (Error Report PDU) вихідному відправнику при відкиданні пакета;
  `0` — відкидати пакет мовчки без генерації повідомлень про помилку.
- **Type (біти 4..0):**
  `0b11100` (`28` або `0x1C`) — **Data PDU (DT)** (звичайний пакет із корисними даними);
  `0b00001` (`1` або `0x01`) — **Error Report PDU (ER)** (пакет звіту про помилку, еквівалент ICMP Error).

### 1.3. Адресна частина заголовка (Address Part)

Адресна частина слідує безпосередньо за полем контрольної суми (починаючи зі зміщення 9):

| Поле | Розмір | Опис |
|---|---|---|
| **Destination Address Length (DAL)** | 1 байт | Довжина адреси призначення в байтах (від 1 до 20 октетів). |
| **Destination Address (DA)** | `DAL` байтів | Мережева адреса точки доступу призначення (Destination NSAP). |
| **Source Address Length (SAL)** | 1 байт | Довжина адреси джерела в байтах (від 1 до 20 октетів). |
| **Source Address (SA)** | `SAL` байтів | Мережева адреса точки доступу джерела (Source NSAP). |

### 1.4. Частина сегментації (Segmentation Part)

Якщо у прапорцях встановлено біт `SP = 1`, за адресною частиною слідує обов'язковий 6-байтний блок керування сегментацією:

| Поле | Розмір | Опис |
|---|---|---|
| **Data Unit Identifier (DUID)** | 2 байти | Унікальний числовий ідентифікатор вихідного неподіленого пакета (еквівалент поля Identification в IPv4). |
| **Segment Offset** | 2 байти | Зміщення початку корисних даних цього сегмента відносно початку вихідного нефрагментованого блоку даних (у байтах, Big-Endian). |
| **Total Length** | 2 байти | Повна довжина вихідного неподіленого блоку даних (заголовок + корисне навантаження) у байтах. |

### 1.5. Блок опцій (Options Part)

Опції кодуються у форматі TLV (*Type-Length-Value*) до кінця заголовка (визначається полем `Length Indicator`):

- **Security (Код `0xC5`):** Рівень секретності та політика безпеки пакета.
- **Source Routing (Код `0xC8`):** Маршрутизація від джерела (повний перелік проміжних NSAP або псевдонімів).
- **Route Recording (Код `0xCB`):** Запис пройденого маршруту (список проміжних адрес вузлів).
- **Quality of Service Maintenance (Код `0xC3`):** Пріоритет, допустима затримка, надійність та вартість транзиту.
- **Priority (Код `0xCD`):** 1-байтний рівень пріоритету пакета (від `0` — найнижчий до `31` — найвищий).

## 2. Структура мережевих адрес NSAP (ISO/IEC 8348)

Мережева адреса **NSAP** (*Network Service Access Point*) є ієрархічним ідентифікатором вузла в мережі OSI. Довжина адреси є змінною і може становити від **7 до 20 байтів** (від 14 до 40 напівбайтів-ніблів).

Адреса NSAP ділиться на дві основні логічні зони:
1. **IDP (Initial Domain Part):** Задає орган реєстрації та глобальний простір адресації.
2. **DSP (Domain Specific Part):** Локальна ієрархія маршрутизації всередині організації чи домену.

```
┌───────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
│         Initial Domain Part (IDP)             │              Domain Specific Part (DSP)                │
├───────────────┬───────────────────────────────┼──────────────────────┬───────────────────────┬─────────┤
│      AFI      │              IDI              │   High-Order DSP     │       System ID       │  N-SEL  │
│    (1 байт)   │         (до 10 байтів)        │    (Area / Домен)    │        (6 байтів)     │ (1 байт)│
└───────────────┴───────────────────────────────┴──────────────────────┴───────────────────────┴─────────┘
```

### Поля структури адреси NSAP:

1. **AFI (Authority and Format Identifier, 1 байт):**
   Визначає організацію, яка виділила номерний простір, та формат подання наступних полів (двійковий або десятковий BCD):
   - `0x39` — міжнародний стандарт ISO DCC (Data Country Code, двійковий);
   - `0x47` — міжнародний стандарт ISO ICD (International Code Designator, двійковий);
   - `0x49` — локально адміністрований приватний простір адресації (Local/Private AFI, аналог RFC 1918).
2. **IDI (Initial Domain Identifier, змінна довжина):**
   Ідентифікує конкретну країну (для DCC), міжнародну організацію (для ICD) або мережевого провайдера.
3. **High-Order DSP (HO-DSP, змінна довжина):**
   Ієрархія маршрутизації всередині домену: код регіону, номер автономної системи та ідентифікатор зони (Area ID). Використовується протоколом IS-IS для маршрутизації між різними областями (Level-2 Routing).
4. **System ID (рівно 6 байтів / 48 бітів):**
   Унікальний ідентифікатор конкретного мережевого вузла всередині області (Area). Зазвичай як System ID призначають апаратну MAC-адресу Ethernet-інтерфейсу маршрутизатора (наприклад, `00:1A:2B:3C:4D:5E` записується як `001a.2b3c.4d5e`).
5. **N-SEL (NSAP Selector, 1 байт):**
   Селектор мережевого рівня. Визначає конкретну кінцеву службу чи процес, якому призначений пакет:
   - `0x00` — позначає сам вузол маршрутизатора або маршрутизуючий процес (NET — Network Entity Title);
   - `0x01` — транспортний протокол (TP4 або TP0);
   - `0xFE` — службовий процес керування.

## 3. Транспортний рівень: протокол TP4 (ISO 8073 / ITU-T X.224)

Транспортний протокол OSI поділяється на 5 класів (Class 0..4). **TP4** (*Transport Protocol Class 4*) — найпотужніший клас, призначений для роботи поверх ненадійних мереж дейтаграмного типу (CLNS/CLNP). Він забезпечує наскрізний контроль помилок, відновлення втрат через ковзне вікно ARQ, впорядкування сегментів та керування потоком.

Усі блоки транспортного рівня називаються **TPDU** (*Transport Protocol Data Unit*).

### 3.1. Загальний формат TPDU

Заголовок будь-якого TPDU складається з:
1. Байта довжини заголовка `LI` (Length Indicator);
2. Фіксованої частини (Fixed Part) з обов'язковими полями;
3. Змінної частини (Variable Part) з необов'язковими параметрами у форматі TLV;
4. Поля корисних даних (Data Field).

### 3.2. Типи блоків TPDU

Код типу TPDU кодується у старших 4 бітах другого байта заголовка:

| Шістнадцятковий код | Мнемоніка | Повна назва | Призначення |
|---|---|---|---|
| `0xE0` | **CR** | Connection Request | Запит на встановлення транспортного з'єднання |
| `0xD0` | **CC** | Connection Confirm | Підтвердження встановлення з'єднання |
| `0x80` | **DR** | Disconnect Request | Запит на розрив з'єднання |
| `0xC0` | **DC** | Disconnect Confirm | Підтвердження розриву з'єднання |
| `0xF0` | **DT** | Data | Передача блоку даних користувача |
| `0x70` | **AK** | Data Acknowledge | Підтвердження отримання даних (ACK) |
| `0x10` | **RJ** | Reject | Негативне підтвердження (NACK / перевідправлення) |
| `0x60` | **ER** | TPDU Error | Повідомлення про помилку структури заголовка |

### 3.3. Структура заголовка передачі даних (DT-TPDU)

Блок даних **DT-TPDU** у звичайному (нормальному) форматі адресації послідовностей (7-бітний лічильник `TPDU-NR`):

```
  Байт 0          Байт 1          Байт 2..3       Байт 4
┌───────────────┬───────────────┬───────────────┬───────────────────┐
│      LI       │   Type / Ro   │   DST-REF     │ EOT ¦   TPDU-NR   │
│   (довжина)   │ 1 1 1 1 0 0 0 │ (Destination) │ (1) ¦   (7 біт)   │
└───────────────┴───────────────┴───────────────┴───────────────────┘
```

- **LI (Length Indicator, 1 байт):** Довжина заголовка TPDU без урахування самого байта `LI` (для простого DT-TPDU дорівнює `3` або `4`).
- **Type / Ro (1 байт):** `0xF0` — старші 4 біти `1111` означають тип **DT**, молодші 4 біти зарезервовані (`0000`).
- **DST-REF (Destination Reference, 2 байти):** 16-бітний унікальний числовий ідентифікатор з'єднання на стороні приймача (аналог номера сокета / сесії).
- **EOT (End of TSDU, біт 7 байта 4):**
  `1` — поточний TPDU є останнім у поточному повідомленні транспортної служби (Transport Service Data Unit);
  `0` — повідомлення фрагментоване і продовжується в наступному TPDU.
- **TPDU-NR (біти 6..0 байта 4):** 7-бітний порядковий номер пакета в ковзному вікні (у розширеному форматі Extended Format поле послідовності розширюється до 31 біта).

### 3.4. Структура заголовка підтвердження (AK-TPDU)

Блок підтвердження **AK-TPDU** використовується для підтвердження отримання даних та оновлення розміру вікна кредиту:

```
  Байт 0          Байт 1          Байт 2..3       Байт 4          Байт 5..6
┌───────────────┬───────────────┬───────────────┬───────────────┬───────────────┐
│      LI       │   Type / CDT  │   DST-REF     │    YR-TU-NR   │      CDT      │
│   (довжина)   │ 0 1 1 1 ¦ CDT │ (Destination) │ (номер очік.) │ (якщо розшир) │
└───────────────┴───────────────┴───────────────┴───────────────────────────────┘
```

- **CDT (Credit Allocation):** Кількість TPDU, яку відправнику дозволено надіслати без отримання додаткових підтверджень (керування потоком на базі кредитів).
- **YR-TU-NR (Your Turn Number, 1 байт):** Номер наступного очікуваного TPDU (підтверджує отримання всіх попередніх номерів `0 .. YR-TU-NR - 1`).

## 4. Сеансовий рівень: протокол ISO 8327 / ITU-T X.225 (SPDU)

Сеансовий рівень (L5) організовує та структурує діалог між двома прикладними процесами. Службові блоки сеансового рівня називаються **SPDU** (*Session Protocol Data Unit*).

### 4.1. Типи та ідентифікатори SPDU (SI-код)

Кожен SPDU починається з 1-байтного ідентифікатора типу (Session Identifier, `SI`):

| SI-код (Hex) | Мнемоніка | Повна назва | Призначення в діалозі |
|---|---|---|---|
| `0x0D` | **CN** | Connect SPDU | Запит на встановлення сеансового діалогу |
| `0x0E` | **AC** | Accept SPDU | Згода на встановлення сеансу з узгодженням токенів |
| `0x0C` | **RF** | Refuse SPDU | Відхилення запиту на встановлення сеансу |
| `0x19` | **FN** | Finish SPDU | Запит на планове завершення сеансового діалогу |
| `0x1A` | **DN** | Disconnect SPDU | Підтвердження планового закриття діалогу |
| `0x01` | **DT** | Data Transfer SPDU | Передача сеансових даних користувача |
| `0x31` | **MIP** | Minor Sync Point | Встановлення проміжної точки синхронізації (без блокування) |
| `0x30` | **MAP** | Major Sync Point | Встановлення головної точки синхронізації (із підтвердженням) |
| `0x35` | **RS** | Resynchronize | Відкіт діалогу назад до зазначеного номера синхроточки |
| `0x05` | **GIVE TOKEN** | Give Tokens SPDU | Передача права ініціативи (токена передачі) співрозмовнику |

### 4.2. Механізм токенів та функціональні блоки сеансу

Сеансовий протокол OSI визначає 4 незалежні розподілені маркери (токени), наявність яких надає вузлу виключне право на виконання операцій:
1. **Data Token (Токен даних):** Керує напівдуплексним режимом (передавати дані може лише володар токена).
2. **Synchronize-Minor Token (Токен малих точок):** Дозволяє генерувати проміжні контрольні мітки `MIP`.
3. **Major/Activity Token (Токен великих точок):** Дозволяє розділяти діалог на незалежні великі фази (активності).
4. **Release Token (Токен завершення):** Право ініціювати плавне закриття з'єднання.

## 5. Прикладний рівень: сервісні елементи ACSE та ROSE

У моделі OSI прикладний рівень (L7) структурований на стандартні службові модулі — сервісні елементи ASE (*Application Service Elements*), які комбінуються прикладними протоколами (FTAM, X.400, X.500):

### 5.1. ACSE (Association Control Service Element, ISO 8650 / X.227)
Керує життєвим циклом прикладного зв'язку (прикладні асоціації):
- **AARQ (A-ASSOCIATE-REQUEST):** Запит на відкриття прикладної асоціації із зазначенням контексту прикладного протоколу (Application Context Name OID).
- **AARE (A-ASSOCIATE-RESPONSE):** Підтвердження або відхилення асоціації з кодом результату (`accepted`, `rejected-permanent`, `rejected-transient`).
- **RLRQ (A-RELEASE-REQUEST):** Запит на коректне звільнення асоціації.
- **RLRE (A-RELEASE-RESPONSE):** Підтвердження закриття прикладної асоціації.

### 5.2. ROSE (Remote Operations Service Element, ISO 9072 / X.229)
Забезпечує парадигму віддаленого виклику процедур (RPC) для каталогів X.500 та систем керування мережами CMIP:
- **ROIV-apdu (RO-INVOKE):** Виклик віддаленої операції з унікальним номером `invokeID`, кодом операції `operationCode` та аргументами.
- **RORS-apdu (RO-RESULT):** Успішний результат виконання операції `invokeID` із поверненими даними.
- **ROER-apdu (RO-ERROR):** Повідомлення про помилку виконання операції з кодом помилки та параметрами.
- **ROJR-apdu (RO-REJECT):** Відхилення некоректно сформованого або невідомого запиту.

## 6. Точки доступу до послуг (SAP) та сервісні примітиви

Взаємодія між суміжними рівнями стека OSI здійснюється через **точки доступу до послуг** (SAP, англ. *Service Access Point*). Кожен рівень `(N)` надає сервіс рівню `(N+1)` через відповідну точку `(N)-SAP`:

| Рівень | Назва точки SAP | Селектор / Формат | Призначення |
|---|---|---|---|
| **L7 Прикладний** | **ASAP** (Application SAP) | Назва прикладного контексту (OID) | Доступ користувацьких програм до стандартних служб |
| **L6 Представницький** | **PSAP** (Presentation SAP) | `P-Selector` (до 16 байтів) | Ідентифікація контексту синтаксису представлення даних |
| **L5 Сеансовий** | **SSAP** (Session SAP) | `S-Selector` (до 16 байтів) | Ідентифікація сеансового з'єднання та діалогу |
| **L4 Транспортний** | **TSAP** (Transport SAP) | `T-Selector` (від 1 до 32 байтів) | Аналог порту TCP/UDP; ідентифікує процес у хості |
| **L3 Мережевий** | **NSAP** (Network SAP) | `N-Selector` / Адреса NSAP | Мережевий адресний простір для маршрутизації хоста |
| **L2 Канальний** | **LSAP** (Link SAP) | Байт LLC SAP (`DSAP`/`SSAP`) | Визначає мережевий протокол над канальним кадром (IEEE 802.2) |

### Сервісні примітиви обміну

Обмін запитами та відповідями між суміжними рівнями відбувається за допомогою чотирьох уніфікованих сервісних примітивів:

```
Рівень (N+1)                                     Рівень (N+1)
      │                                                ▲
      │ (1) Request                     (2) Indication │
      ▼                                                │
┌───────────┐      Мережевий протокол      ┌───────────┐
│ Рівень(N) │ ───────────────────────────► │ Рівень(N) │
└───────────┘                              └───────────┘
      ▲                                                │
      │ (4) Confirm                       (3) Response │
      │                                                ▼
Рівень (N+1)                                     Рівень (N+1)
```

1. **Request (`.request`):** Рівень `(N+1)` викликає сервіс рівня `(N)` (наприклад, `T-CONNECT.request` — запит на встановлення транспортного з'єднання).
2. **Indication (`.indication`):** Рівень `(N)` повідомляє віддалений рівень `(N+1)` про подію або вхідний пакет (`T-CONNECT.indication`).
3. **Response (`.response`):** Рівень `(N+1)` надсилає відповідь на подію (`T-CONNECT.response`).
4. **Confirm (`.confirm`):** Рівень `(N)` підтверджує ініціатору успішне завершення операції (`T-CONNECT.confirm`).

## 7. Представницький рівень: мова ASN.1 та правила кодування BER

Для подолання відмінностей у внутрішньому представленні даних на різних процесорних архітектурах (порядок байтів Big-Endian / Little-Endian, вирівнювання структур, кодування рядків ASCII / EBCDIC) рівень представлення OSI (L6) використовує мову **ASN.1** (*Abstract Syntax Notation One*, ISO/IEC 8824) та двійкові правила серіалізації **BER** (*Basic Encoding Rules*, ISO/IEC 8825-1).

### 7.1. Структура елемента BER: трійка TLV (Tag-Length-Value)

Кожне поле даних у потоці BER серіалізується у вигляді трьох послідовних компонентів:

```
┌─────────────────────────┬─────────────────────────┬─────────────────────────┐
│      Tag (Тег типу)     │     Length (Довжина)    │  Value (Значення поля)  │
│      (1..N байтів)      │      (1..N байтів)      │      (L байтів даних)   │
└─────────────────────────┴─────────────────────────┴─────────────────────────┘
```

### 7.2. Структура байта тегу (Tag Identifier)

Байт тегу визначає клас типу даних, прапорець простого або складеного типу та числовий номер типу:

```
  Біт 7    Біт 6    Біт 5    Біт 4   Біт 3   Біт 2   Біт 1   Біт 0
┌────────┬────────┬────────┬───────┬───────┬───────┬───────┬───────┐
│     Class       │  P/C   │             Tag Number (0..30)        │
└────────┴────────┴────────┴───────┴───────┴───────┴───────┴───────┘
```

- **Class (біти 7..6):**
  `00` — **Universal** (стандартні базові типи ASN.1);
  `01` — **Application** (типи, специфічні для конкретного прикладного протоколу);
  `10` — **Context-specific** (типи, сенс яких залежить від позиції у структурі SEQUENCE чи SET);
  `11` — **Private** (приватні типи організації).
- **P/C (Primitive / Constructed, біт 5):**
  `0` — **Primitive** (простий атомарний тип: ціле число, бітовий рядок, булеве значення);
  `1` — **Constructed** (складений тип, що містить всередині інші елементи TLV: SEQUENCE, SET).
- **Tag Number (біти 4..0):**
  Номер типу від `0` до `30`. Якщо номер типу `≥ 31`, у бітах 4..0 записується `0b11111`, а сам номер кодується у наступних октетах у форматі змінної довжини VLQ (7 бітів на байт із бітом продовження MSB).

### 7.3. Стандартні універсальні теги ASN.1 (Universal Class)

| Номер тегу | Шістнадцятковий код (Primitive) | Тип даних ASN.1 | Опис |
|---|---|---|---|
| `1` | `0x01` | **BOOLEAN** | Булеве значення: `0x00` — FALSE, будь-яке інше (`0xFF`) — TRUE |
| `2` | `0x02` | **INTEGER** | Ціле знакове число довільної довжини у форматі доповнення до двійки (Two's Complement, Big-Endian) |
| `3` | `0x03` | **BIT STRING** | Послідовність бітів (перший байт значення задає кількість невикористаних бітів у кінці) |
| `4` | `0x04` | **OCTET STRING** | Довільний двійковий масив байтів |
| `5` | `0x05` | **NULL** | Порожнє значення (довжина завжди `0x00`) |
| `6` | `0x06` | **OBJECT IDENTIFIER** | Ієрархічний числовий ідентифікатор стандарту / об'єкта (OID, наприклад `1.3.6.1.4.1...`) |
| `16` | `0x30` *(Constructed)* | **SEQUENCE** | Впорядкований список полів фіксованої структури (аналог `struct` у C) |
| `17` | `0x31` *(Constructed)* | **SET** | Невпорядкована множина полів довільної послідовності |
| `19` | `0x13` | **PrintableString** | Текстовий рядок обмеженого набору символів (латиниця, цифри, пробіл, базові розділові знаки) |
| `22` | `0x16` | **IA5String** | Текстовий рядок у повному стандарті ASCII (7-біт) |
| `23` | `0x17` | **UTCTime** | Формат запису часу та дати (`YYMMDDhhmmssZ`) |

### 7.4. Кодування довжини (Length Encoding)

1. **Коротка форма (Short Form):**
   Використовується, якщо довжина значення `L ≤ 127` байтів.
   Поле займає рівно 1 байт, старший біт `MSB = 0`, а решта 7 бітів містять точну довжину:
   - `0x05` = 5 байтів;
   - `0x7F` = 127 байтів.
2. **Довга форма (Long Form):**
   Використовується, якщо довжина значення `L ≥ 128` байтів.
   У першому байті біт `MSB = 1`, а біти 6..0 задають **кількість наступних байтів**, які містять число довжини:
   - `0x81 0xC8` — 1 байт довжини, значення = `200` байтів (`0xC8`);
   - `0x82 0x01 0x00` — 2 байти довжини, значення = `256` байтів (`0x0100`).

### 7.5. Приклад двійкової серіалізації структури в BER

Розглянемо опис структури передачі ідентифікатора користувача та його прав доступу мовою ASN.1:

```asn1
UserAccess ::= SEQUENCE {
    userId      INTEGER,
    isSuperuser BOOLEAN
}
```

Для значень `userId = 1000` (`0x03E8`) та `isSuperuser = TRUE` двійковий потік BER матиме такий вигляд:

```
Побайтовий дамп: 30 08 02 02 03 E8 01 01 FF
```

**Поелементний розбір дампу:**
1. `0x30` — Тег типу `SEQUENCE` (Class Universal `00`, Constructed `1`, Tag `16` = `0b00110000`).
2. `0x08` — Довжина всього вмісту послідовності (8 байтів далі).
3. `0x02` — Тег поля 1: `INTEGER` (Universal `00`, Primitive `0`, Tag `2`).
4. `0x02` — Довжина поля `INTEGER` (2 байти).
5. `0x03 0xE8` — Значення числа `1000` у форматі Big-Endian.
6. `0x01` — Тег поля 2: `BOOLEAN` (Universal `00`, Primitive `0`, Tag `1`).
7. `0x01` — Довжина поля `BOOLEAN` (1 байт).
8. `0xFF` — Значення `TRUE`.
