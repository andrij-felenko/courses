<preknowlist>

- [Багатоадресна розсилка й виявлення вузлів](root:com-transport/multicast-and-discovery) — членство в групах multicast, IGMP, адреси 224.0.0.0/24 та сокетні опції.
- [Записи DNS SRV і NAPTR](root:com-transport/dns-srv-naptr) — відокремлення імені служби від імені хоста, пріоритет, вага та порт.
- [MAC, IP і ARP](root:com-transport/mac-ip-arp) — два поверхи адрес, канальний рівень та розв'язання конфліктів адрес.
- [Сокети TCP/UDP](root:sf-os/sockets-tcp-udp) — робота з датаграмними сокетами, системні виклики та прапорці повторного використання порту.
</preknowlist>

Коли мікроконтролер сенсора або мережевий принтер підключають патч-кордом до звичайного некерованого комутатора в ізольованій лабораторії, класичний мережевий стек негайно опиняється в глухому куті. Сервер DHCP відсутній — пристрій не може отримати IP-адресу та маску підмережі. DNS-сервер відсутній — жоден комп'ютер у мережі не може перетворити ім'я `sensor.local` на адресу. Реєстр служб відсутній — клієнтська програма не знає, на якому саме TCP-порті відкритий веб-інтерфейс або API телеметрії. Спроба виконати `getaddrinfo("sensor", ...)` повертає системну помилку `EAI_NONAME`, а ручне призначення статичних адрес вимагає підключення сервісного консольного кабелю або спеціалізованого дисплея.

Автономне виявлення пристроїв у локальній мережі розв'язує цю проблему без централізованої інфраструктури, перетворюючи розрізнені вузли на самоорганізовану розподілену систему.

## 1. Концепція ZeroConf: три опори автономної мережі

Архітектура безконфігураційних мереж (*Zero-Configuration Networking*, ZeroConf) об'єднує три незалежні протокольні рівні, кожен з яких усуває потребу в окремому центральному сервері:

![Три опори ZeroConf](/root/com/com-transport/mdns-dns-sd/img/zeroconf-three-pillars.svg)
*Три опори архітектури Zero-Configuration Networking: динамічна адресація Link-Local, децентралізоване розв'язання імен mDNS та семантичний пошук служб DNS-SD.*

1. **Адресація канального рівня (*Link-Local Addressing*)**: Пристрій самостійно генерує собі IP-адресу зі спеціального зарезервованого діапазону та за допомогою зондувальних широкомовних запитів перевіряє, що ця адреса не зайнята іншими пристроями в сегменті.
2. **Багатоадресне розв'язання імен (*Multicast DNS, mDNS*)**: Пристрій обирає собі доменне ім'я в зоні `.local` і відповідає на локальні мультикаст-запити інших вузлів без участі авторитетного DNS-сервера.
3. **Виявлення служб на базі DNS (*DNS-Based Service Discovery, DNS-SD*)**: Пристрій публікує структуровану інформацію про доступні сервіси (тип протоколу, номер порту, шлях до кінцевої точки, метадані) у форматі стандартних DNS-записів `PTR`, `SRV` та `TXT`.

Кожен наступний рівень спирається на функціональність попереднього: для роботи mDNS потрібна готова IP-адреса, а для роботи DNS-SD потрібен транспорт mDNS.

## 2. Автоматична адресація Link-Local та розв'язання конфліктів (RFC 3927, RFC 4862)

Коли вузол не отримує відповіді на запити DHCPDISCOVER, він перемикається в режим Link-Local. Для IPv4 цей механізм стандартизовано в RFC 3927 (*Dynamic Configuration of IPv4 Link-Local Addresses*), а для IPv6 — у RFC 4862 (*Stateless Address Autoconfiguration, SLAAC*).

### Простір адрес IPv4 Link-Local
Згідно з RFC 3927, для автоматичного призначення виділено блок **`169.254.0.0/16`** (від `169.254.0.0` до `169.254.255.255`).

Із цього діапазону виключено перші 256 адрес (`169.254.0.0/24`) та останні 256 адрес (`169.254.255.0/24`), оскільки вони зарезервовані IETF для майбутніх розширень протоколу. Ефективний робочий діапазон становить **65 024 адреси**:

```
[169.254.1.0]  <------------ Доступний діапазон ------------>  [169.254.254.255]
```

Вузол обирає початкову адресу псевдовипадковим чином, використовуючи як сид апаратну MAC-адресу мережевого адаптера:

```
Хеш MAC-адреси -> 16 бітів псевдовипадкового числа -> 169.254.X.Y
```

### Зондування адреси (ARP Probing)
Перед тим як призначити обрану IP-адресу на мережевий інтерфейс, вузол зобов'язаний перевірити, що жоден інший пристрій у цьому широкомовному домені її не використовує. Для цього використовується спеціальний кадр **ARP Probe**:

```
+---------------------------------------------------------------+
|                      ARP Probe Packet                         |
|  Hardware Type: Ethernet (1)       Protocol Type: IPv4 (0x800) |
|  Opcode: ARP Request (1)                                      |
|  Sender MAC: MAC_вузла             Sender IP: 0.0.0.0          |
|  Target MAC: 00:00:00:00:00:00     Target IP: 169.254.X.Y      |
+---------------------------------------------------------------+
```

Поле `Sender IP` обов'язково заповнюється нулями (`0.0.0.0`). Це критично важливо: якби вузол вказав там ще не підтверджену адресу `169.254.X.Y`, інші комп'ютери в мережі передчасно оновили б свої внутрішні ARP-таблиці та надіслали б наступні пакети на чужий пристрій.

Стандарт RFC 3927 вимагає надіслати **3 пакети ARP Probe** з випадковими інтервалами від 250 до 2000 мілісекунд (орієнтир `PROBE_NUM = 3`, `PROBE_MIN = 1s`, `PROBE_MAX = 2s`).

Якщо протягом часу зондування вузол:
- Отримує **ARP Reply** на свою запропоновану адресу, або
- Отримує **ARP Probe** від іншого вузла з тим самим значенням `Target IP`,

фіксується колізія. Вузол негайно припиняє зондування, обирає нову псевдовипадкову адресу та повторює процедуру з початку. Якщо в мережі виникає понад 10 колізій поспіль, вузол обмежує частоту спроб (*rate limiting*), очікуючи щонайменше 5 секунд перед наступним циклом.

### Анонсування адреси (ARP Announcement)
Якщо після надсилання трьох зондів протягом 250 мс заперечень не надійшло, адреса вважається закріпленою за вузлом. Вузол негайно надсилає **2 широкомовні пакети ARP Announcement** (також відомі як *Gratuitous ARP*):

```
+---------------------------------------------------------------+
|                   ARP Announcement Packet                     |
|  Opcode: ARP Request (1)                                      |
|  Sender MAC: MAC_вузла             Sender IP: 169.254.X.Y      |
|  Target MAC: 00:00:00:00:00:00     Target IP: 169.254.X.Y      |
+---------------------------------------------------------------+
```

Ці пакети змушують усі інші вузли в підмережі оновити свої ARP-кеші, зв'язавши `169.254.X.Y` з MAC-адресою нового пристрою.

### Захист адреси (Address Defending)
Після конфігурації інтерфейсу вузол продовжує слухати весь ARP-трафік у сегменті. Якщо сторонній вузол надсилає ARP Probe або ARP Request на вже зайняту адресу:
1. Законний власник негайно надсилає у відповідь власний пакет ARP Announcement.
2. Новачок, почувши заперечення, відступає та обирає іншу IP-адресу.
3. Якщо конфліктні ARP-пакети продовжують надходити частіше одного разу на 10 секунд (наприклад, через аномалію комутатора чи некоректний пристрій), законний власник зобов'язаний звільнити адресу, обрати нову та переналаштувати стек, щоб уникнути блокування мережі.

В **IPv6** процедура спрощена: кожен інтерфейс автоматично генерує Link-Local адресу з префіксом `fe80::/10` (на основі EUI-64 або криптографічно стійкого ідентифікатора інтерфейсу) і виконує перевірку дублікатів (*Duplicate Address Detection, DAD*) за допомогою протоколу ICMPv6 Neighbor Discovery.

## 3. Багатоадресний DNS (Multicast DNS, RFC 6762)

Маючи робочу IP-адресу, пристрої можуть зв'язуватися за числовими IP, але взаємодія прикладних програм вимагає сталих доменних імен. Multicast DNS (RFC 6762) реалізує розв'язання імен без використання виділеного DNS-сервера.

### Мережевий транспорт та домен `.local`
mDNS використовує протокол UDP та спеціально виділені IANA групові адреси:

- **IPv4**: `224.0.0.251` (порт `5353`)
- **IPv6**: `ff02::fb` (порт `5353`)
- **IP TTL**: обов'язково встановлюється у `255`. Пакети з меншим TTL відкидаються.

Усі mDNS-імена зобов'язані завершуватися суфіксом **`.local`** (наприклад, `printer.local`, `smart-plug.local`). Відповідно до RFC 6761, домен верхнього рівня `.local` офіційно зарезервований виключно для link-local mDNS. Системні резолвери операційних систем (Linux, macOS, Windows, iOS, Android) перехоплюють будь-який DNS-запит із суфіксом `.local` і скеровують його на локальний мультикаст-порт 5353 замість публічних або корпоративних DNS-серверів.

### Двійкова анатомія повідомлення mDNS
mDNS повністю сумісний із класичним двійковим форматом повідомлень DNS (RFC 1035), але перевизначає окремі поля заголовка та секцій:

![Анатомія mDNS](/root/com/com-transport/mdns-dns-sd/img/mdns-packet-structure.svg)
*Анатомія mDNS-повідомлення: розширення DNS-формату бітами одноадресної відповіді (QU/QM) та скидання кешу (Cache-Flush).*

1. **Transaction ID (16 бітів)**: У групових mDNS-відповідях встановлюється в `0x0000`. Оскільки групове повідомлення надсилається всім пристроям у мережі, одержувачі зіставляють дані за іменем у секції відповідей, а не за ідентифікатором транзакції.
2. **Прапорець AA (Authoritative Answer)**: У відповідях mDNS завжди встановлюється в `1`, сигналізуючи, що респондер є повним господарем власних записів.
3. **Прапорець RD (Recursion Desired)**: Завжди встановлюється в `0` (рекурсія в одноранговій мережі відсутня).

Детальний побайтовий розбір двійкових структур, полів та зміщень наведено у вставці [довідка з бінарного формату пакетів mDNS і DNS-SD](root:com-transport/mdns-dns-sd/api-dns-sd-records.md).

### Біт одноадресної відповіді (QU/QM) у запитах
Класичне 16-бітне поле `QCLASS` у секції Question розширено старшим бітом 15:

```
 15 14                                                         0
+--+------------------------------------------------------------+
|QU|                        QCLASS (15)                         |
+--+------------------------------------------------------------+
```

- **`QU` (Unicast-Response, біт 15 = 1)**: Запитувач просить респондера надіслати відповідь безпосередньо на його IP-адресу та порт через unicast UDP. Це застосовується новопідключеними пристроями для первинного наповнення свого внутрішнього кешу без створення зайвого навантаження на бездротовий ефір.
- **`QM` (Multicast-Response, біт 15 = 0)**: Відповідь має бути надіслана на групову адресу `224.0.0.251:5353`, щоб усі пристрої в мережі змогли оновити свій локальний кеш.

### Біт очищення кешу (Cache-Flush Bit) у записах відповідей
У полі `CLASS` секції Resource Record старший біт 15 визначає семантику кешування:

- **`Cache-Flush = 1` (маска `0x8001` для класу IN)**: Позначає **унікальний запис (*Unique Record*)**, який належить лише одному хосту (наприклад, адреси `A`, `AAAA`, служба `SRV`, параметри `TXT`). Отримавши такий запис, клієнт повинен **видалити** всі старі записи цього типу для даного імені та замінити їх новим.
- **`Cache-Flush = 0` (значення `0x0001` для класу IN)**: Позначає **спільний запис (*Shared Record*)**, який можуть одночасно публікувати десятки пристроїв (наприклад, покажчики `PTR` на спільний тип служби `_http._tcp.local`). Клієнт додає запис до свого списку екземплярів без витирання записів від сусідніх вузлів.

## 4. Зондування, анонсування та захист імен хостів (Probing, Announcing, Defending)

Як і IP-адреса, доменне ім'я хоста в зоні `.local` не може дублюватися двома пристроями. mDNS визначає чіткий трифазний життєвий цикл імені:

![Життєвий цикл імені mDNS](/root/com/com-transport/mdns-dns-sd/img/probing-and-announcing.svg)
*Життєвий цикл імені mDNS: послідовність фаз зондування (Probing), анонсування (Announcing) та активного захисту (Defending).*

### Фаза 1: Зондування імені (Probing)
Коли пристрій хоче зареєструвати ім'я (наприклад, `mydevice.local`):
1. Він надсилає **3 групові mDNS-запити** з інтервалом 250 мс.
2. Секція Question містить запит типу `ANY` (255) або `A` (1) для імені `mydevice.local` з бітом `QM` (multicast response).
3. Секція Authority (`NSCOUNT > 0`) містить запропоновані записи хоста (його передбачувану адресу `A`/`AAAA`), що сигналізує іншим про намір зареєструвати це ім'я.

#### Розв'язання конфліктів (Tie-Breaking)
Якщо два пристрої одночасно вмикаються в мережу й намагаються зареєструвати однакове ім'я `mydevice.local`, вони отримують зондувальні запити один одного. Щоб уникнути нескінченного циклу відступів, діє детерміністичне правило **Tie-Breaking**:
- Вузли порівнюють RDATA своїх запропонованих записів у секції Authority побайтово у лексикографічному порядку (як масиви беззнакових байтів).
- Вузол з **лексикографічно більшим** записом продовжує зондування без змін (він виграв суперечку).
- Вузол з **меншим** записом поступається: він скидає лічильник зондування, автоматично модифікує своє ім'я (додаючи числовий суфікс `mydevice-2.local`) і розпочинає новий цикл зондування.

### Фаза 2: Оголошення (Announcing)
Якщо протягом 250 мс після третього зонду заперечень не надійшло, ім'я вважається офіційно зареєстрованим. Вузол переходить у стан оголошення:
1. Надсилаються **2 групові авторські відповіді** (*Authoritative Responses*) з інтервалом в 1 секунду.
2. Відповіді містять усі записи хоста (`A`, `AAAA`) та його служб із встановленим бітом `Cache-Flush = 1`.
3. Записи надсилаються з номінальним значенням TTL: **120 секунд** для записів адрес хоста та **4500 секунд** для служб.

Сусідні пристрої, отримавши ці пакети, миттєво заповнюють свої внутрішні mDNS-кеші.

### Фаза 3: Захист імені (Defending)
Після завершення анонсування вузол переходить у робочий стан захисту імені. Якщо новачок у мережі надсилає Probe-запит на вже зайняте ім'я `mydevice.local`:
- Законний власник негайно генерує групову відповідь з бітом `Cache-Flush = 1` та повним TTL.
- Новачок, побачивши готову авторську відповідь від власника, перериває власне зондування і перейменовується.
- **Обмеження шторму захисту (*Defend Rate Limiting*)**: вузол не має права надсилати захисні пакети частіше одного разу на секунду.

## 5. Виявлення служб на базі DNS (DNS-SD, RFC 6763)

Знання імені комп'ютера `printer-room.local` є недостатнім для додатків: операційній системі потрібно знайти *всі мережеві принтери* в будівлі, дізнатися їхні мережеві порти та підтримувані протоколи без опитування кожного хоста вручну.

DNS-SD (RFC 6763) відокремлює тип функціоналу від конкретного імені комп'ютера за допомогою трирівневої ієрархії DNS-записів:

![Ієрархія резолвінгу DNS-SD](/root/com/com-transport/mdns-dns-sd/img/dns-sd-lookup-hierarchy.svg)
*Триступенева ієрархія DNS-SD: від типу служби через покажчик PTR до екземпляра, портів у SRV, метаданих у TXT та IP-адреси в A/AAAA.*

### Структура найменування служби
Повне ім'я екземпляра служби (*Service Instance Name*) формується за схемою:

```
<Екземпляр> . <Тип_Служби> . <Транспорт> . <Домен>
```

- `<Екземпляр>`: Зрозуміла людині назва пристрою у кодуванні UTF-8 (наприклад, `Головний Принтер` або `Датчик Вітальні`).
- `<Тип_Служби>`: Зареєстрований в IANA ідентифікатор прикладного протоколу з префіксом підкреслення (наприклад, `_http`, `_ipp`, `_airplay`, `_ssh`).
- `<Транспорт>`: `_tcp` або `_udp`.
- `<Домен>`: `local` (для локального mDNS) або глобальне доменне ім'я (для Wide-Area DNS).

Приклад повного імені екземпляра:
```
Датчик Клімату._http._tcp.local
```

### Триада записів DNS-SD

1. **Запис PTR (Покажчик типу служби)**:
   - **Ім'я**: `_http._tcp.local` (тип служби).
   - **Дані (RDATA)**: `Датчик Клімату._http._tcp.local` (ім'я екземпляра).
   - **Біт Cache-Flush**: **`0` (Shared Record)**. Клієнт, який виконує пошук усіх веб-серверів, запитує `PTR _http._tcp.local` і отримує список усіх доступних пристроїв.
2. **Запис SRV (Хост і порт служби, RFC 2782)**:
   - **Ім'я**: `Датчик Клімату._http._tcp.local`.
   - **Дані**: `Priority=0`, `Weight=0`, `Port=80`, `Target=esp-node.local`.
   - **Біт Cache-Flush**: **`1` (Unique Record)**. Вказує канонічне ім'я хоста та порт.
3. **Запис TXT (Метадані служби)**:
   - **Ім'я**: `Датчик Клімату._http._tcp.local`.
   - **Дані**: масив пар `key=value` (наприклад, `txtvers=1`, `model=BME280`, `path=/api/v1`).
   - **Біт Cache-Flush**: **`1` (Unique Record)**. Передає параметри без встановлення TCP-з'єднання.

### Однопакетне агрегування (One-Packet Discovery)
Головна оптимізація DNS-SD полягає в тому, що респондер ніколи не надсилає ці записи окремо. Коли клієнт надсилає запит на пошук `PTR _http._tcp.local`:
- Респондер вкладає `PTR` у секцію **Answer**.
- У секцію **Additional** респондер одночасно пакує зв'язані записи `SRV`, `TXT` та адресні записи `A` і `AAAA`.

Клієнт отримує всю інформацію — від назви служби до IP-адреси та порту — **в єдиному UDP-пакеті** за один мережевий RTT.

### Перерахування типів служб та підтипи
- **Мета-пошук усіх служб у мережі**: Клієнт може надіслати запит `PTR _services._dns-sd._udp.local`. Усі респондери повернуть типи зареєстрованих ними служб (наприклад, `_http._tcp.local`, `_ipp._tcp.local`).
- **Підтипи (*Subtypes*)**: Дозволяють фільтрувати служби за ознаками (наприклад, пошук кольорових принтерів `_color._sub._ipp._tcp.local`).

## 6. Кешування, оптимізація трафіку та придушення мультикаст-штормів

Групова розсилка накладає високе навантаження на комутатори та бездротові мережі Wi-Fi, де мультикаст транслюється на мінімальній базовій швидкості (наприклад, 1–6 Мбіт/с). RFC 6762 визначає три обов'язкові алгоритми запобігання штормам:

![Контроль трафіку в mDNS](/root/com/com-transport/mdns-dns-sd/img/suppression-and-goodbye.svg)
*Механізми оптимізації mDNS-трафіку: придушення відомих відповідей, випадкова затримка для запобігання колізіям та пакети Good-bye.*

### 1. Придушення відомих відповідей (Known-Answer Suppression)
Коли клієнту потрібно оновити інформацію про служби, він вкладає в секцію Answer свого mDNS-запиту всі записи, які вже зберігаються в його локальному кеші, разом із їхнім залишком TTL.

Респондер, отримавши такий запит, порівнює RDATA та залишковий TTL клієнта зі своїми поточними даними. Якщо клієнт уже має коректний запис із залишком TTL **понад 50%** від номіналу, респондер **утримується від відповіді**. Це запобігає переповненню ефіру дубльованими пакетами.

### 2. Випадкова затримка відповіді (Random Response Delay)
Якщо в мережі працює 50 однакових принтерів, на спільний запит `PTR _ipp._tcp.local` усі 50 пристроїв спробували б відповісти в один і той самий момент, що призвело б до масової колізії на канальному рівні.

Стандарт вимагає:
- Для спільних записів (*Shared Records*) респондер перед відправленням обирає випадкову затримку від **20 до 120 мілісекунд**.
- **Придушення дублікатів (*Duplicate Answer Suppression*)**: Якщо під час очікування таймера респондер фіксує в ефірі відповідь від іншого вузла, яка містить точно такі самі дані, він негайно **скасовує власну заплановану відповідь**.

### 3. Оновлення кешу (Cache Refreshing)
Клієнт не чекає повного вичерпання TTL запису (120 с або 4500 с). Щоб уникнути перерв у доступі, клієнт надсилає запит на підтвердження при досягненні **80%**, **85%**, **90%** та **95%** часу життя запису (з випадковим зміщенням таймера ±2%). Якщо до 100% відповіді не надійшло, запис видаляється з кешу.

### 4. Оголошення про вихід (Good-bye Packet)
Якщо пристрій вимикається штатно, клієнти без спеціального сповіщення тримали б його запис у кеші до 75 хвилин.

Перед закриттям сокетів пристрій надсилає фінальний пакет mDNS, у якому встановлює **`TTL = 0`** для всіх власних записів (`PTR`, `SRV`, `TXT`, `A`, `AAAA`). Клієнти, отримавши запис з `TTL = 0`, негайно видаляють пристрій зі списків доступних служб без очікування тайм-аутів.

### 5. Специфіка Wi-Fi та IGMP Snooping
У бездротових мережах 802.11 пакети мультикасту передаються без підтвердження на рівні MAC (ACK), що при високому рівні завад викликає часті втрати пакетів. Сучасні точки доступу застосовують **Multicast-to-Unicast конверсію**: точка доступу аналізує IGMP-звіти про членство в групах і транслює групові mDNS-пакети як серію надійних одноадресних фреймів на підвищеній швидкості модуляції для кожного активного клієнта.

## 7. Реалізація легковажного респондера у вбудованих системах

У мікроконтролерних системах (наприклад, ESP32 на базі ESP-IDF або FreeRTOS з lwIP) mDNS респондер реалізується у вигляді фонової задачі, яка слухає UDP-порт 5353 через єдиний сокет:

```
+-------------------------------------------------------------+
|                      Вбудований MCU                         |
|                                                             |
|  [ lwIP Network Stack ]                                     |
|           |                                                 |
|  [ UDP Socket: bind 0.0.0.0:5353, join 224.0.0.251 ]        |
|           |                                                 |
|  [ State Machine ]: PROBING -> ANNOUNCING -> RUNNING        |
|           |                                                 |
|  [ Packet Builder ]: Zero-Heap Fixed Buffer (1472 bytes)    |
|                      DNS Name Compression (0xC000)          |
+-------------------------------------------------------------+
```

Ключові інженерні вимоги до реалізації:
- **Zero Heap Allocation**: Відсутність динамічного виділення пам'яті (`malloc`/`new`) під час обробки трафіку для запобігання фрагментації heap у тривалому режимі роботи 24/7.
- **Багатоінтерфейсні хости (*Multi-Homed Hosts*)**: Якщо пристрій має одночасно Ethernet та Wi-Fi, кожен інтерфейс повинен мати власний сокет з прив'язкою до відповідної IP-адреси через опцію `imr_interface`, щоб mDNS-відповіді містили коректну адресу саме того сегмента, звідки надійшов запит.
- **Підтримка компресії DNS-імен**: Використання зміщень `0xC000 | offset` для пакування повного анонсу служби в один кадр MTU.

Повний вихідний код автономного респондера мовами C та сучасним C++20 наведено у вставці [практична реалізація респондера mDNS/DNS-SD для вбудованих систем](root:com-transport/mdns-dns-sd/proj-mdns-responder.md).

## 8. Межі технології, маршрутизація та історія стандарту

### Проблема межі L2-сегмента (VLAN Boundary)
Пакети mDNS надсилаються на адресу `224.0.0.251` з полем `IP TTL = 255`. Оскільки адреси блоку `224.0.0.0/24` є локальними для канального рівня (*Link-Local Multicast*), маршрутизатори за замовчуванням **не пересилають** mDNS-пакети між різними VLAN та підмережами.

У корпоративних мережах (наприклад, коли смартфони співробітників перебувають у гостьовому Wi-Fi VLAN, а принтери — у сервісному VLAN) застосовують одне з трьох рішень:
1. **mDNS Gateway / Reflector**: Функція корпоративних комутаторів/маршрутизаторів (або демона `avahi-daemon` з опцією `enable-reflector=yes`), яка перехоплює mDNS-запити в одному VLAN та ретранслює їх в інший.
2. **Wide-Area DNS-SD (RFC 6763 §11)**: Використання стандартного ієрархічного Unicast DNS. Служби реєструються на звичайному DNS-сервері підприємства через протокол Dynamic DNS Update (RFC 2136), що дозволяє клієнтам шукати сервіси в доменах `corp.example.com` через стандартні одноадресні DNS-запити без мультикасту.
3. **Discovery Proxy (RFC 8766)**: Спеціалізований проксі-сервер, який слухає mDNS у локальних сегментах і транслює їх у відповіді для клієнтів з інших підмереж.

Детальний опис зародження концепції ZeroConf, історичного маніфесту Стюарта Чешира, протистояння з UPnP/SSDP та інтеграції в сучасний стандарт Matter/Thread наведено у вставці [історія появи ZeroConf та стандартів mDNS/DNS-SD](root:com-transport/mdns-dns-sd/hist-zeroconf.md).
