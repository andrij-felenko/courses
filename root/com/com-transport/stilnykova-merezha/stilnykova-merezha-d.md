Автомобіль чи швидкісний потяг, що рухається зі швидкістю 120 км/год, кожні кілька сотень метрів перетинає межу радіопокриття чергової базової станції. Потужність передавача мобільного модему фізично обмежена типовим значенням 200 мВт (+23 dBm), тому встановити прямий радіозв'язок із віддаленим сервером або єдиною центральною антеною на відстані в десятки кілометрів неможливо: напруженість електромагнітного поля згасає пропорційно четвертому степеню відстані в умовах міської забудови. Якби кожна базова станція працювала як ізольована точка доступу без узгодженого частотного плану та розподіленого протоколу синхронізації, радіоефір перетворився б на суцільний хаос інтерференції, пакети активної сесії TCP чи UDP губилися б під час кожної зміни щогли, а комутаційне ядро оператора витрачало б секунди на повторний пошук пристрою.

Розв'язанням цієї фундаментальної проблеми є стільникова архітектура (cellular network). Вона спирається на розбиття території на геометрично впорядковані зони (соти), сувору координацію частотних ресурсів, стандартизовану послідовність початкового входу в ефір (Random Access Procedure) та механізм безрозривної естафетної передачі обслуговування (Handover) між базовими станціями без розриву транспортних з'єднань.

## Топологія мережі: соти, секторизація та координація інтерференції

Фізичний радіус дії радіопередавача визначається бюджетом каналу (Link Budget): вихідною потужністю, коефіцієнтом підсилення антен, втратами на трасі поширення (Path Loss) та порогом чутливості приймача. Щоб забезпечити безперервне покриття великої географічної зони обмеженим радіочастотним спектром, територію покривають мережею базових станцій малої та середньої потужності.

Математичною моделлю такого покриття є гексагональна решітка. Правильний шестикутник — це геометрична фігура, яка найкраще апроксимує кругову діаграму випромінювання всеспрямованої антени та дозволяє повністю замостити площину без взаємних накладань і мертвих зон (порожнеч). Кожна вершина або центр шестикутника відповідає фізичному розташуванню антенної щогли.

### Повторне використання частот (Frequency Reuse)

Радіочастотний спектр — це вичерпний і дорогий ресурс. Якщо виділити кожній базовій станції унікальну смугу частот, оператору вистачило б ліцензованого діапазону лише на кілька десятків станцій у межах міста. Тому той самий набір частот використовується повторно на певній відстані між станціями.

Відношення повторного використання частот позначається коефіцієнтом `N` (розмір кластера сот). У класичних мережах 2G застосовувався фактор `N = 3`, `4` або `7`. У системі з `N = 3` доступна смуга частот ділиться на три рівні піддіапазони (`f1`, `f2`, `f3`). Сусідні соти використовують різні піддіапазони, а сота з частотою `f1` повторюється лише на безпечній відстані `D`, де сигнал віддаленої станції затухає настільки, що не створює відчутних завад:

```text
D = R · √(3 · N)
```

де `R` — радіус соти, а `N` — розмір кластера.

У мережах LTE (4G) та 5G NR для досягнення максимальної швидкості передачі даних застосовується повнозв'язне повторне використання частот із коефіцієнтом `N = 1`. Це означає, що кожна базова станція та кожен сектор використовують усю доступну ширину спектру (наприклад, 20 МГц). Однак на межі між двома сусідніми сотами виникає тяжка міжсотова інтерференція (Inter-Cell Interference, ICI), оскільки корисний сигнал від станції `A` та завадовий сигнал від станції `B` надходять на одних і тих самих піднесучих частотах OFDMA з однаковою потужністю.

Для боротьби з міжсотовою інтерференцією в сучасних стандартах реалізовано комплекс координаційних алгоритмів:
1. **Дробове повторне використання частот (Fractional Frequency Reuse, FFR):** у центрі соти біля вежі випромінюється весь спектр на зниженій потужності, а на межах суміжних сот пристроям призначаються неперетинні піддіапазони на максимальній потужності.
2. **Міжсотова координація завад (ICIC / eICIC):** базові станції обмінюються повідомленнями через прямий міжстанційний інтерфейс X2/Xn. У розширеній схемі eICIC (enhanced ICIC) макростанція періодично виділяє так звані «майже порожні субфрейми» (Almost Blank Subframes, ABS), у яких вимикає передачу даних користувача, дозволяючи розташованим поруч мікросотам (Small Cells) обслуговувати абонентів на межі без завад.
3. **Координована багатоточкова передача (Coordinated Multi-Point, CoMP):** дві сусідні станції одночасно передають один і той самий блок даних одному пристрою на межі сот, перетворюючи деструктивну інтерференцію на конструктивне підсилення сигналу.

### Секторизація та формування Physical Cell ID

Всеспрямовані антени (Omnidirectional) випромінюють радіохвилі на 360°, рівномірно створюючи завади в усіх напрямках. Для збільшення ємності мережі на щоглах встановлюють секторні панельні антени зі звуженою діаграмою спрямованості (типово 65° за рівнем половинної потужності).

Стандартом стільникового будівництва є трисекторна сайтова конфігурація: щогла розбиває простір довкола себе на три сектори з азимутами 0° (Північ), 120° (Південний Схід) та 240° (Південний Захід). Кожен такий сектор є з точки зору протоколів автономною логічною сотою зі своїм передавачем, приймачем, пулом радіоресурсів та ідентифікатором. Секторизація знижує сумарний рівень завад у просторі приблизно втричі.

У радіоканалі LTE/5G кожен сектор однозначно визначається фізичним ідентифікатором соти — Physical Cell ID (PCI). Загалом у LTE існує 504 унікальні значення PCI (у 5G NR — 1008 значень). Ідентифікатор формується комбінацією двох складових:

```text
PCI = 3 · N_ID^(1) + N_ID^(2)
```

де `N_ID^(1)` у межах [0..167] — номер групи фізичних сот (визначається за вторинним синхросигналом SSS), а `N_ID^(2)` у межах [0..2] — номер сектора всередині групи (визначається за первинним синхросигналом PSS). Такий поділ дозволяє всім трьом секторам однієї базової станції мати однаковий номер групи `N_ID^(1)`, відрізняючись лише індексом `N_ID^(2)` (0, 1 або 2).

### Еволюція вузлів: від BTS до eNodeB та gNodeB

У мережах другого покоління (2G GSM) базова станція (Base Transceiver Station, BTS) була «тупим» радіотрансивером. Усім керуванням радіоканалами, виділенням таймслотів та хендоверами займався централізований контролер базових станцій (Base Station Controller, BSC), що стояв у серверній оператора за десятки кілометрів і керував сотнями BTS.

У мережах 4G LTE архітектуру було кардинально спрощено для зниження затримок: контролер RNC було ліквідовано, а всі функції радіопротоколів (PHY, MAC, RLC, PDCP, RRC) інтегровано безпосередньо у вузол на щоглі — **eNodeB** (evolved Node B). Станції eNodeB з'єднані між собою відкритим сітчастим інтерфейсом **X2** (поверх IP/SCTP) і підключені до ядра мережі (Evolved Packet Core, EPC) через інтерфейс **S1**.

У мережах 5G NR базова станція **gNodeB** отримала модульну декомпозицію:
* **RU (Radio Unit):** антена та цифро-аналоговий радіотракт на щоглі;
* **DU (Distributed Unit):** обробка рівнів PHY та MAC у реальному часі (інтерфейс eCPRI/Open RAN F1);
* **CU (Central Unit):** вищі рівні PDCP, SDAP, RRC, які можуть працювати у вигляді віртуалізованого контейнера в хмарному датацентрі.

Сусідні станції gNodeB взаємодіють через інтерфейс **Xn**, а з ядром 5GC — через інтерфейси **N2** (сигналізація AMF) та **N3** (трафік користувача UPF).

## Процедура підключення пристрою: від ефіру до ядра мережі

Коли мобільний модем подає живлення на радіочастотний тракт, він не має інформації про точну частоту, таймінги передачі та доступні канали. Процес входу в мережу (Cell Search, Attach & Registration) проходить через сувору послідовність із чотирьох етапів.

![Послідовність RACH та реєстрації в ядрі](/root/com/com-transport/stilnykova-merezha/img/rach-and-attach-sequence.svg)
*Послідовність процедур початкового доступу: синхронізація, 4-кроковий RACH та реєстрація NAS у ядрі мережі*

### Етап 1: Пошук і частотно-часова синхронізація (PSS / SSS)

Пристрій сканує радіочастотні канали згідно з сіткою каналів (EARFCN у LTE або NR-ARFCN у 5G) і шукає специфічні послідовності в центрі смуги пропускання:
1. **Первинний синхросигнал (Primary Synchronization Signal, PSS):** передається кожні 5 мс у 0-му та 5-му субфреймах радіокадру. Складається з послідовності Задова-Чу (Zadoff-Chu) довжиною 62 символи. Приймач обчислює ковзну автокореляцію з трьома еталонними послідовностями і знаходить точні межі OFDM-символів у часі, підстроює опорний генератор частоти та визначає індекс сектора `N_ID^(2)` (значення 0, 1 або 2).
2. **Вторинний синхросигнал (Secondary Synchronization Signal, SSS):** передається в тому ж субфреймі, що й PSS, але на один символ раніше. Складається з псевдовипадкових бінарних m-послідовностей довжиною 62 символи. Декодування SSS дозволяє визначити межу 10-мілісекундного радіокадру та індекс групи соти `N_ID^(1)` у межах [0..167].

Об'єднавши ці два значення, модем обчислює `PCI = 3 · N_ID^(1) + N_ID^(2)`, що дає змогу визначити точне просторове розташування опорних пілот-сигналів соти (Cell-specific Reference Signals, CRS) у сітці ресурсних елементів.

### Етап 2: Зчитування системної інформації (MIB та SIB)

Знаючи PCI та межі кадрів, модем переходить до декодування широкомовних блоків системної інформації:

1. **Master Information Block (MIB):** передається на фізичному каналі PBCH (Physical Broadcast Channel) у першому субфреймі кадру з періодичністю 40 мс (повторюється кожні 10 мс). MIB містить життєво необхідні параметри:
   * Ширину низхідної смуги пропускання каналу (DL Bandwidth: 1.4, 3, 5, 10, 15 або 20 МГц);
   * Конфігурацію каналу індикації гібридного ARQ (PHICH);
   * Старші 8 біт номера системного радіокадру (System Frame Number, SFN).

2. **System Information Block Type 1 (SIB1):** передається на каналі даних PDSCH кожні 80 мс (повтори кожні 20 мс). SIB1 несе параметри допуску до мережі:
   * Список ідентифікаторів оператора PLMN ID (MCC + MNC);
   * Код зони відстеження (Tracking Area Code, TAC);
   * Глобальний 28-бітний ідентифікатор соти (Cell Identity);
   * Критерії мінімальної потужності для входу в соту (`Q_rxlevmin`).

3. **System Information Block Type 2 (SIB2):** містить спільні конфігурації радіоканалів:
   * Розподіл частотних ресурсів та конфігурацію преамбул для каналу випадкового доступу PRACH;
   * Параметри керування потужністю передавача пристрою (`P_0`, альфа);
   * Таймери протоколів вищих рівнів (T300, T301, T310).

Якщо сота відповідає математичному S-критерію придатності за потужністю та якістю (детальний вивід наведено у вставці [math-handover-hysteresis.md](root:com-transport/stilnykova-merezha/math-handover-hysteresis.md)), модем переходить до процедури фізичного підключення.

### Етап 3: Процедура випадкового доступу (RACH 4-Step Contention-Based)

Оскільки відстань від модему до базової станції невідома, час поширення радіосигналу (Propagation Delay) вносить розсинхронізацію. Якщо модем почне передавати дані довільно, його сигнал накладеться в часі на передачу інших пристроїв біля вежі. Для вирівнювання часу висхідного каналу (Uplink Timing Alignment) застосовується процедура RACH:

```text
[UE] ───── Msg1: PRACH Preamble (Zadoff-Chu) ─────> [eNodeB]
[UE] <──── Msg2: Random Access Response (RAR) ────── [eNodeB]
[UE] ───── Msg3: RRCSetupRequest (UE Identity) ────> [eNodeB]
[UE] <──── Msg4: RRCSetup (Contention Resolution) ── [eNodeB]
```

1. **Msg1 (PRACH Preamble):** модем випадковим чином обирає одну з 64 ортогональних послідовностей Задова-Чу (доступних у соті згідно з SIB2) і випромінює її у визначеному часо-частотному слоті каналу PRACH.
2. **Msg2 (Random Access Response, RAR):** базова станція фіксує отримання преамбули та точно вимірює затримку її надходження відносно власної шкали часу. eNodeB відповідає на каналі PDSCH (адресуючись тимчасовим ідентифікатором RA-RNTI). RAR містить:
   * **Timing Advance (TA):** 11-бітне значення випередження передачі, яке вказує модему, на скільки мікросекунд раніше він повинен випромінювати свої радіоімпульси, щоб вони приходили на вежу синхронно з іншими абонентами;
   * **Uplink Grant:** виділення ресурсних блоків у каналі PUSCH для передачі наступного повідомлення;
   * **Temporary C-RNTI (TC-RNTI):** тимчасовий мережевий ідентифікатор пристрою.
3. **Msg3 (RRCSetupRequest):** застосувавши отриманий Timing Advance, модем передає на виділених ресурсах запит на встановлення RRC-з'єднання. Повідомлення містить унікальний ідентифікатор пристрою (S-TMSI, якщо пристрій раніше був зареєстрований, або випадкове 40-бітне число Random Value) та причину встановлення з'єднання (establishmentCause: mo-Signalling, mo-Data, emergency).
4. **Msg4 (RRCSetup / Contention Resolution):** якщо два пристрої одночасно відправили однакову преамбулу в Msg1, виникає колізія. Базова станція транслює відповідь, яка містить точну копію ідентифікатора з Msg3 того пристрою, який вона успішно декодувала. Модем порівнює цей ідентифікатор зі своїм: при збігу колізію вирішено, TC-RNTI стає постійним **C-RNTI** (Cell Radio Network Temporary Identifier), а RRC-з'єднання переходить у встановлений стан.

### Етап 4: Аутентифікація в ядрі та створення носіїв (Attach & Bearer Setup)

Після встановлення RRC-каналу модем надсилає повідомлення `RRCSetupComplete`, усередині якого запаковано контейнер протоколу нерадіодоступу — `NAS Attach Request` (або `Registration Request` у 5G) з ідентифікатором абонента IMSI або тимчасовим GUTI.

Базова станція транслює цей запит контролеру ядра **MME** (Mobility Management Entity) у 4G або **AMF** у 5G через протокол S1-AP / NG-AP:
1. MME надсилає запит до бази абонентів **HSS** (Home Subscriber Server) / **UDM**.
2. HSS генерує аутентифікаційний вектор (Authentication Vector), який містить випадкове число `RAND`, токен автентифікації мережі `AUTN`, очікувану відповідь `XRES` та кореневий сесійний ключ `K_ASME` (`K_AMF`).
3. Мережа відправляє модему `Authentication Request` (`RAND`, `AUTN`). SIM-карта всередині модему перевіряє `AUTN` (взаємна автентифікація мережі) за допомогою секретного майстер-ключа `K`, обчислює відповідь `RES` і сесійні ключі. Модем повертає `RES`.
4. MME перевіряє `RES == XRES`. При збігу запускається процедура безпеки `SecurityModeCommand`, яка активує шифрування (SNOW 3G, AES або ZUC) та контроль цілісності сигналізації RRC і трафіку користувача.
5. Ядро виділяє пристрою IP-адресу, створює GTP-U тунелі (GPRS Tunneling Protocol) між базовою станцією та шлюзами **SGW/PGW** (або **UPF** у 5G) і налаштовує радіоносій за замовчуванням (Default EPS Bearer). Пристрій отримує повний доступ до передачі IP-пакетів.

## Стани керування радіоресурсами (RRC States)

Протокол керування радіоресурсами RRC (Radio Resource Control, 3GPP TS 36.331 / TS 38.331) керує роботою радіоінтерфейсу на рівні L3 між модемом (UE) та базовою станцією (eNodeB/gNodeB).

![Автомат станів RRC](/root/com/com-transport/stilnykova-merezha/img/rrc-state-machine.svg)
*Автомат станів керування радіоресурсами RRC: переходи між IDLE, CONNECTED та INACTIVE*

| Параметр порівняння | RRC_IDLE | RRC_CONNECTED | RRC_INACTIVE (5G / LTE-A) |
|:---|:---|:---|:---|
| **Радіопередавач (TX)** | Вимкнено | Активний за розкладом | Вимкнено |
| **Енергоспоживання** | Мінімальне (мікроампери) | Високе (десятки/сотні мА) | Мінімальне (як в IDLE) |
| **Ідентифікатор у соті** | Немає (лише TAC у ядрі) | Виділений C-RNTI | I-RNTI (збережено в RAN) |
| **Контекст безпеки та носіїв** | Відсутній у базі станції | Активний в eNodeB/gNodeB | Збережений у gNodeB (RAN) |
| **Зв'язок з ядром (N2/N3)** | Розірвано | Активний тунель | Залишається активним |
| **Керування мобільністю** | Автономне (Cell Reselection) | Контрольоване мережею (Handover) | Зона RNA (RAN Notification Area) |
| **Затримка відновлення даних** | ~100–150 мс (повний RACH+Core) | 0 мс (< 1–4 мс на виділення слота) | < 10–15 мс (2-step Resume) |

### Режим очікування: RRC_IDLE та механізм Paging

У стані `RRC_IDLE` модем не має виділених радіоресурсів і вимикає більшість вузлів радіотракту для заощадження заряду батареї. Модем прокидається лише періодично у власні часові слоти циклу переривчастого прийому DRX (Discontinuous Reception, тривалістю від 320 мс до 2.56 с, або до годин у режимі eDRX):
* Модем вимірює рівень сигналу поточної та сусідніх сот і автономно обирає найкращу станцію (Cell Reselection) без сповіщення базової станції;
* Модем зчитує канал виклику **Paging**. Якщо надходить вхідний виклик або IP-пакет з інтернету, ядро мережі транслює повідомлення Paging по всій зоні відстеження TAC (Tracking Area). Виявивши свій ідентифікатор S-TMSI у пейджинговому повідомленні, модем ініціює процедуру RACH і переходить у `RRC_CONNECTED`.

### Активний режим: RRC_CONNECTED

У стані `RRC_CONNECTED` станція виділяє пристрою ідентифікатор C-RNTI. Модем постійно слухає канал керування PDCCH, приймає й передає блоки даних на каналах PDSCH/PUSCH, надсилає вимірювання якості каналу (CQI, PMI, RI) та здійснює естафетні переходи за прямими командами базової станції.

Якщо пристрій не передає дані протягом певного часу (Inactivity Timer, типово 5–10 секунд), базова станція відправляє команду `RRCRelease`, переводячи пристрій назад у стан `RRC_IDLE` для звільнення радіоресурсу соти.

### Енергоефективний проміжний стан: RRC_INACTIVE

Класичний перехід `RRC_IDLE -> RRC_CONNECTED` вимагає 10–15 повідомлень сигналізації між пристроєм, базовою станцією та ядром мережі, що займає понад 100 мс і марнує батарею пристроїв Інтернету речей (IoT), які відправляють невеликі пакети кожні кілька хвилин.

У стандарті 5G NR та LTE-Advanced (Release 13/15) запроваджено проміжний стан **RRC_INACTIVE**:
* Модем спить і споживає енергію на рівні `RRC_IDLE`;
* Однак базова станція gNodeB **не видаляє** контекст пристрою (UE Context), конфігурацію радіоносіїв та ключі шифрування;
* Тунелі інтерфейсу N2/N3 до ядра мережі 5GC залишаються активними.

Коли з'являються нові дані, модем надсилає короткий 2-кроковий запит `RRCResumeRequest` з ідентифікатором **I-RNTI** (Inactive RNTI) і токеном перевірки автентичності. Станція миттєво повертає `RRCResume`, і обмін даними відновлюється менш ніж за 10–15 мс без участі ядра мережі.

## Естафетна передача (Handover): вимірювання та безрозривне перемикання

Естафетна передача (Handover) — це процес передачі активного з'єднання мобільного пристрою від поточної соти (Serving Cell) до цільової соти (Target Cell) без розриву призначеної IP-адреси та без зупинки потоку даних.

### Метрики оцінки якості стільникового сигналу

Оцінка радіоканалу в стільникових мережах базується на чотирьох фізичних метриках:

```text
RSSI  = P_total (Signal + Interference + Noise)  [dBm]
RSRP  = P_RE (Cell-specific Reference Symbol)   [dBm]
RSRQ  = N_RB · (RSRP / RSSI)                    [dB]
SINR  = P_signal / (P_interference + P_noise)   [dB]
```

1. **RSSI (Received Signal Strength Indicator):** сумарна виміряна широкосмугова потужність у всій смузі частот каналу. Включає корисний сигнал, тепловий шум та інтерференцію всіх сусідніх станцій. Високий RSSI не гарантує якісний зв'язок, якщо він створений завадами.
2. **RSRP (Reference Signal Received Power):** середня потужність, виміряна на одному ресурсному елементі (Resource Element, RE), що несе опорний пілотний символ конкретної соти. Це головний абсолютний показник рівня сигналу соти (діапазон від -140 dBm до -44 dBm; значення вище -80 dBm вважається відмінним, нижче -115 dBm — граничним).
3. **RSRQ (Reference Signal Received Quality):** співвідношення потужності опорних символів до загальної потужності смуги, масштабоване на кількість ресурсних блоків `N`. Відображає рівень завантаженості соти та радіозавад (діапазон від -20 dB до -3 dB; чим ближче до -3 dB, тим менше завад у каналі).
4. **SINR (Signal-to-Interference-plus-Noise Ratio):** співвідношення потужності корисного сигналу до суми інтерференції від інших сот і теплового шуму. Безпосередньо визначає допустиму схему модуляції (QPSK, 16QAM, 64QAM, 256QAM) та бітову швидкість.

### Події вимірювань мобільності (Measurement Events)

У стані `RRC_CONNECTED` базова станція конфігурує модем на моніторинг певних радіоподій. Модем фільтрує вимірювання на рівні L3 і при виконанні умов генерує звіт `MeasurementReport`:

| Подія | Умова спрацьовування | Практичне призначення в мережі |
|:---|:---|:---|
| **A1** | `M_s > Threshold` | Serving сота стала кращою за поріг. Модем зупиняє міжчастотний пошук для економії енергії. |
| **A2** | `M_s < Threshold` | Serving сота впала нижче порогу. Станція наказує модему ввімкнути сканування суміжних частот. |
| **A3** | `M_n - Hys > M_s + Off` | Сусідня сота стала кращою за поточну. **Головний тригер внутрішньочастотного хендоверу.** |
| **A4** | `M_n > Threshold` | Сусідня сота перевищила абсолютний поріг якості. |
| **A5** | `M_s < Thresh_1 AND M_n > Thresh_2` | Поточна сота непридатна, а сусідня задовільна (міжчастотний перехід). |
| **B1/B2** | Міжсистемні критерії (Inter-RAT) | Перехід між різними технологіями: з LTE на 3G/2G при виході з зони покриття, або з LTE на 5G NR. |

![Часова діаграма естафети](/root/com/com-transport/stilnykova-merezha/img/handover-a3-event-timeline.svg)
*Часова діаграма естафетної передачі: виникнення події A3, таймер Time-to-Trigger та виконання безрозривного перемикання*

### Усунення ефекту «пінг-понгу» (Hysteresis та Time-to-Trigger)

Якщо автомобіль рухається вздовж межі сот, рівень сигналу коливається через дифракційні тіні та багатопроменеве поширення. Якби перемикання відбувалося в точці точної рівності сигналів (`RSRP1 = RSRP2`), модем щосекунди перемикався б туди й назад між станціями (ефект «пінг-понгу»), що перевантажило б сигналізаційні канали мережі та призвело б до втрати пакетів.

Для стабілізації процесу в рівняння події A3 вводяться три захисні бар'єри:
1. **Гістерезис (`Hys`):** штучний запас потужності (типово 1.5–3.0 dB), на який цільова сота має перевищити поточну.
2. **Індивідуальне зміщення соти (Cell Individual Offset, CIO):** програмне коригування меж сот для вирівнювання трафіку між перевантаженими та недовантаженими секторами.
3. **Час утримання умови (Time-to-Trigger, TTT):** таймер затримки (типово 100–320 мс). Подія A3 реєструється лише в тому разі, якщо нерівність перевищення сигналу безперервно виконується протягом усього інтервалу TTT.

Повне математичне виведення рівнянь входу й виходу події A3 та формули фільтрації шару L3 подано у вставці [math-handover-hysteresis.md](root:com-transport/stilnykova-merezha/math-handover-hysteresis.md).

### Фази виконання безрозривного хендоверу (X2-Based Handover)

Процес естафетної передачі між станціями eNodeB складається з чотирьох послідовних фаз:
1. **Фаза підготовки (Handover Preparation):** отримавши `MeasurementReport` з подією A3, вихідна базова станція (Source eNodeB) надсилає цільовій станції (Target eNodeB) через прямий інтерфейс X2 повідомлення `Handover Request`. Цільова станція виділяє ресурси, резервує новий ідентифікатор C-RNTI та призначає виділену вільну преамбулу для безконфліктного доступу (Non-Contention RACH).
2. **Фаза виконання (Handover Execution):** Source eNodeB передає пристрою команду `RRCConnectionReconfiguration` з інформаційним елементом `mobilityControlInfo`. Модем розриває зв'язок зі старою сотою, переналаштовує синтезатор частоти на цільову соту і без затримок відправляє виділену преамбулу RACH (без колізій Msg1–Msg4). Отримавши Timing Advance, модем підтверджує перемикання повідомленням `RRCConnectionReconfigurationComplete`.
3. **Переадресація даних (Data Forwarding):** під час перемикання радіоканалу Source eNodeB пересилає всі недоставлені та буферизовані пакети PDCP до Target eNodeB через прямий тунель X2-U. Цільова станція зберігає чергу пакетів і передає їх пристрою одразу після завершення радіопереходу, гарантуючи нульову втрату пакетів.
4. **Перемикання шляху в ядрі (Path Switch & Completion):** Target eNodeB відправляє до ядра мережі (MME / SGW) повідомлення `Path Switch Request`. Шлюз SGW перемикає низхідний тунель GTP-U на нову базову станцію. Source eNodeB отримує команду `UE Context Release` і звільняє старі радіоресурси.

## Діагностика соти та параметрів сигналу через AT-команди

Для вбудованих систем, модемів IoT та діагностичних утиліт єдиним стандартизованим інтерфейсом моніторингу стану соти, реєстрації та радіометрик є командний інтерфейс AT (3GPP TS 27.007).

### Базові та розширені команди 3GPP

1. **AT+CSQ (Signal Quality):** повертає індекси `<rssi>` (0..31) та `<ber>` (0..7, 99). Розрахунок фізичного рівня потужності у dBm виконується за лінійною формулою:

```text
P_dBm = -113 + 2 · rssi    (при rssi <= 31)
```

2. **AT+CESQ (Extended Signal Quality):** розширена команда для мереж LTE/5G. Повертає 6 значень: `<rxlev>,<ber>,<rscp>,<ecno>,<rsrq>,<rsrp>`.
   * **RSRP (індекс 0..97):** перераховується у dBm як `RSRP = -140 + rsrp`.
   * **RSRQ (індекс 0..34):** перераховується у dB як `RSRQ = -19.5 + 0.5 · rsrq`.

3. **AT+CEREG? (EPS Network Registration Status):** повертає статус реєстрації модему в мережі пакетообміну LTE:
   * `0` — не зареєстровано, пошук вимкнено;
   * `1` — успішно зареєстровано в домашній мережі;
   * `2` — пошук мережі / сканування ефіру;
   * `3` — реєстрацію відхилено оператором (Registration Denied);
   * `5` — зареєстровано в роумінгу.
   У режимі URC (`AT+CEREG=2`) модем автоматично виводить повідомлення при зміні зони:
   `+CEREG: 1,"1A2F","05B2A01",7`, де `"1A2F"` — Tracking Area Code (TAC), а `"05B2A01"` — 28-бітний E-UTRAN Cell Identifier.

Повний синтаксис команд, бітові маски, розширені формати операторів `+COPS` та інженерні режими наведено у вставці [api-cellular-at-diagnostics.md](root:com-transport/stilnykova-merezha/api-cellular-at-diagnostics.md).

### Програмна реалізація парсингу параметрів соти

Нижче наведено приклад обробки відповідей модему на C та ідіоматичному C++, що демонструє виділення метрик сигналу та детекцію хендоверу при зміні ідентифікатора соти.

:::tabs
@tab C
```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

typedef struct {
    int16_t rsrp_dbm;
    float rsrq_db;
    uint32_t cell_id;
    bool valid;
} radio_cell_info_t;

bool parse_cesq_response(const char *response, radio_cell_info_t *info) {
    if (!response || !info) return false;
    const char *tag = "+CESQ: ";
    const char *pos = strstr(response, tag);
    if (!pos) return false;

    int rxlev, ber, rscp, ecno, rsrq_raw, rsrp_raw;
    if (sscanf(pos + strlen(tag), "%d,%d,%d,%d,%d,%d",
               &rxlev, &ber, &rscp, &ecno, &rsrq_raw, &rsrp_raw) == 6) {
        if (rsrp_raw >= 0 && rsrp_raw <= 97) {
            info->rsrp_dbm = (int16_t)(-140 + rsrp_raw);
            info->valid = true;
        }
        if (rsrq_raw >= 0 && rsrq_raw <= 34) {
            info->rsrq_db = -19.5f + (float)rsrq_raw * 0.5f;
        }
        return true;
    }
    return false;
}
```
@tab C++
```cpp
#include <iostream>
#include <string_view>
#include <optional>
#include <charconv>
#include <vector>

struct RadioCellInfo {
    int16_t rsrp_dbm{-140};
    float rsrq_db{-20.0f};
    uint32_t cell_id{0};
    bool valid{false};
};

class CellMetricsParser {
public:
    static std::optional<RadioCellInfo> parseCesq(std::string_view response) {
        constexpr std::string_view tag = "+CESQ: ";
        const auto tag_pos = response.find(tag);
        if (tag_pos == std::string_view::npos) return std::nullopt;

        const auto payload = response.substr(tag_pos + tag.size());
        std::vector<std::string_view> tokens;
        size_t start = 0;
        while (start < payload.size()) {
            const size_t end = payload.find(',', start);
            if (end == std::string_view::npos) {
                tokens.push_back(payload.substr(start));
                break;
            }
            tokens.push_back(payload.substr(start, end - start));
            start = end + 1;
        }

        if (tokens.size() < 6) return std::nullopt;

        int rsrq_raw = 255, rsrp_raw = 255;
        std::from_chars(tokens[4].data(), tokens[4].data() + tokens[4].size(), rsrq_raw);
        std::from_chars(tokens[5].data(), tokens[5].data() + tokens[5].size(), rsrp_raw);

        RadioCellInfo info;
        if (rsrp_raw >= 0 && rsrp_raw <= 97) {
            info.rsrp_dbm = static_cast<int16_t>(-140 + rsrp_raw);
            info.valid = true;
        }
        if (rsrq_raw >= 0 && rsrq_raw <= 34) {
            info.rsrq_db = -19.5f + static_cast<float>(rsrq_raw) * 0.5f;
        }
        return info;
    }
};
```
