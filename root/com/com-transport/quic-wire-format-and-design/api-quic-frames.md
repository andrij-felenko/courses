# 📋 Специфікація двійкових фреймів та типів пакетів QUIC

Для розробки мережевого стеку QUIC, написання низькорівневих аналізаторів трафіку або діагностики протокольних збоїв необхідна вичерпна специфікація бінарного формату. Корисне навантаження кожного пакета QUIC після зняття криптографічного захисту є строгою послідовністю двійкових фреймів, кожен з яких кодує конкретну операцію транспортного чи керуючого рівня. Нижче наведено детальний опис кодування цілих чисел змінної довжини, двійкової структури пакетів, транспортних параметрів рукостискання, правил роботи кінцевого автомата потоків, процедури розкриття захисту заголовків та повної таблиці типів фреймів згідно з RFC 9000, RFC 9001 та RFC 9114.

## 1. Кодування цілих чисел змінної довжини (Variable-Length Integer)

Протокол QUIC відмовляється від полів фіксованої розрядності на користь компактного префіксного кодування змінної довжини (RFC 9000 §16). Це дозволяє заощаджувати байти в заголовках невеликих пакетів, зберігаючи здатність адресувати терабайтні обсяги даних у зсувах потоків. Розмір числа у байтах кодується двома старшими бітами найпершого октету:

- **Префікс `00` (`0x00`):** 1 байт. Для корисного значення відведено 6 молодших бітів. Діапазон значень: від `0` до `63` (`2⁶ - 1`).
- **Префікс `01` (`0x40`):** 2 байти. Для корисного значення відведено 14 бітів. Діапазон значень: від `0` до `16 383` (`2¹⁴ - 1`).
- **Префікс `10` (`0x80`):** 4 байти. Для корисного значення відведено 30 бітів. Діапазон значень: від `0` до `1 073 741 823` (`2³⁰ - 1`).
- **Префікс `11` (`0xC0`):** 8 байтів. Для корисного значення відведено 62 біти. Діапазон значень: від `0` до `4 611 686 018 427 387 903` (`2⁶² - 1`).

Усі цілі числа змінної довжини передаються у мережевому порядку байтів (англ. big-endian, від старшого до молодшого). Специфікація вимагає від реалізацій декодувати будь-яке число, закодоване в межах дозволеного синтаксису, проте забороняє генерувати числа, що перевищують максимальне значення `2⁶² - 1`. Якщо парсер зустрічає нестачу байтів у буфері для зчитування вказаної довжини, пакет відкидається з помилкою `FRAME_ENCODING_ERROR`.

## 2. Структура пакетів QUIC та захист заголовків

Транспортні пакети QUIC поділяються на два класи: пакети з довгим заголовком (Long Header), що обслуговують встановлення з'єднання, та пакети з коротким заголовком (Short Header), оптимізовані для передачі робочого навантаження з мінімальним оверхедом.

### 2.1. Пакети з довгим заголовком (Long Header)

Довгий заголовок використовується на етапах, коли вузли ще не мають спільних робочих ключів шифрування 1-RTT або коли потрібна явна узгоджувальна інформація. Перший байт містить біт форми заголовка (`Header Form = 1`), біт фіксації (`Fixed Bit = 1`), двобітний тип пакета та 4 зарезервовані біти (що маскуються захистом заголовка).

Типи пакетів Long Header:
1. **`Initial` (тип `0x00`):** перший пакет клієнта або сервера. Містить поле `Token Length` та сам токен валідації адреси (для запобігання підсиленню DDoS), а також довжину корисного навантаження. Усередині несе фрейми `CRYPTO` з блоком `ClientHello`.
2. **`0-RTT` (тип `0x01`):** пакет клієнта, що надсилає ранні прикладні дані до завершення повного рукостискання на основі Pre-Shared Key (PSK) з попередньої сесії.
3. **`Handshake` (тип `0x02`):** пакети обміну сертифікатами сервера, параметрами автентифікації та фінальними криптографічними підтвердженнями `Finished`.
4. **`Retry` (тип `0x03`):** незашифрований пакет сервера, який надсилається у відповідь на `Initial` без виділення пам'яті. Містить криптографічний токен повтору, що зобов'язує клієнта повторити `Initial` із цим токеном, підтверджуючи справжність своєї IP-адреси.

Поля довгого заголовка включають: 32-бітну версію протоколу (`0x00000001` для QUIC v1), довжину Destination Connection ID (DCIL, 1 байт), значення DCID (від 0 до 20 байтів), довжину Source Connection ID (SCIL, 1 байт) та значення SCID.

### 2.2. Пакети з коротким заголовком (Short Header 1-RTT)

Після завершення рукостискання використовується короткий заголовок. Перший байт має біт форми `Header Form = 0`, біт `Fixed Bit = 1`, біт вимірювання затримок `Spin Bit`, два зарезервовані біти, біт поточної фази ключів `Key Phase` та два біти довжини номера пакета (`00` — 1 байт, `01` — 2 байти, `10` — 3 байти, `11` — 4 байти). За першим октетом слідує Destination Connection ID узгодженої довжини, усічений номер пакета (1..4 байти) та зашифроване навантаження з тегом автентичності AEAD (16 байтів).

### 2.3. Алгоритм зняття захисту заголовка (Header Protection)

Щоб запобігти зняттю цифрових відбитків трафіку проміжними маршрутизаторами, номер пакета та прапорці першого байта маскуються криптографічною маскою (RFC 9001 §5.4):
1. Отримувач зчитує незашифровані поля (Connection ID) і знаходить потрібний контекст ключів.
2. З зашифрованого навантаження (Payload), відступивши на 4 байти від передбачуваного початку номера пакета, береться 16-байтний блок-зразок (Sample).
3. Зразок шифрується алгоритмом AES-128-ECB, AES-256-ECB або ChaCha20 за допомогою спеціального ключа захисту заголовків `hp_key`, згенерованого під час рукостискання.
4. Перші 5 байтів згенерованої маски накладаються операцією XOR:
   - Для Long Header: маскуються 4 молодші біти першого байта (`байт_0 ^= (маска[0] & 0x0F)`).
   - Для Short Header: маскуються 5 молодших бітів першого байта (`байт_0 ^= (маска[0] & 0x1F)`).
   - За відновленими бітами довжини зчитується 1, 2, 3 або 4 байти номера пакета і маскується відповідними байтами `маска[1..4]`.
5. Повний 62-бітний номер пакета реконструюється з переданого усіченого значення на основі найбільшого раніше підтвердженого номера пакета (`largest_acked`).
6. Формується 12-байтний Nonce (`IV XOR Packet Number`), після чого навантаження розшифровується алгоритмом AEAD (AES-GCM або ChaCha20-Poly1305).

## 3. Специфікація фреймів транспортного рівня QUIC

Після успішного розшифрування корисне навантаження пакета розбирається як послідовність фреймів від першого байта до кінця буфера.

### 3.1. Керування пакетами: PADDING (`0x00`) та PING (`0x01`)

- **`PADDING` (`0x00`):** складається з одного нульового байта. Використовується для штучного збільшення розміру датаграми (наприклад, для заповнення пакета `Initial` клієнта до обов'язкового мінімального розміру 1200 байтів) або для приховування справжнього розміру прикладних повідомлень від аналізаторів трафіку.
- **`PING` (`0x01`):** не містить додаткових полів. Змушує віддалений вузол згенерувати та надіслати фрейм `ACK`. Застосовується для підтримки активності NAT-трансляцій у періоди тиші та для перевірки доступності мережевого шляху.

### 3.2. Підтвердження доставки: ACK (`0x02`) та ACK_ECN (`0x03`)

Фрейм `ACK` передає повну картину отриманих пакетів і містить такі поля:
- `Largest Acknowledged` (Varint): найбільший номер пакета, отриманий вузлом у цьому просторі номерів.
- `ACK Delay` (Varint): час у мікросекундах (масштабований за експонентою `ack_delay_exponent`), що минув між отриманням пакета `Largest Acknowledged` та відправкою цього кадру `ACK`.
- `ACK Range Count` (Varint): кількість додаткових блоків пропусків (`Gaps`) та діапазонів підтвердження.
- `First ACK Range` (Varint): кількість послідовних пакетів, що передують `Largest Acknowledged`, які також успішно отримані (діапазон від `Largest Acknowledged - First ACK Range` до `Largest Acknowledged`).
- Послідовність пар `[Gap (Varint), ACK Range Length (Varint)]`:
  - `Gap`: кількість втрачених або ще не отриманих пакетів перед попереднім блоком.
  - `ACK Range Length`: кількість послідовних отриманих пакетів перед цим пропуском.
- Для `ACK_ECN` (`0x03`): додатково передаються три лічильники прапорців явної сигналізації перевантаження мережі — `ECT(0) Count`, `ECT(1) Count` та `ECN-CE Count` (Varint).

### 3.3. Передача даних: STREAM (`0x08` – `0x0F`)

Фрейми сімейства `STREAM` кодують передачу фрагмента даних у конкретний потік. Молодші біти визначають наявність опційних полів:
- Біт `0x04` (`OFF`): присутнє поле `Offset` (Varint). Якщо біт скинуто, дані передаються з нульового зсуву (початок потоку).
- Біт `0x02` (`LEN`): присутнє поле `Length` (Varint). Якщо біт скинуто, довжина корисних даних визначається як уся решта пакета до кінця захищеного навантаження.
- Біт `0x01` (`FIN`): завершення потоку передавачем. Останній байт корисних даних у цьому кадрі має зсув `Offset + Length - 1` і визначає фінальний розмір потоку (`Final Size`).

Структура полів:
1. `Type` (1 байт, значення від `0x08` до `0x0F`).
2. `Stream ID` (Varint): числовий ідентифікатор потоку.
3. `Offset` (Varint, опційно за наявності біта `OFF`).
4. `Length` (Varint, опційно за наявності біта `LEN`).
5. `Stream Data` (послідовність байтів заданої довжини).

### 3.4. Керування криптографією: CRYPTO (`0x06`) та NEW_TOKEN (`0x07`)

- **`CRYPTO` (`0x06`):** містить поля `Offset` (Varint), `Length` (Varint) та `Crypto Data`. Забезпечує надійне впорядковане передавання байтового потоку повідомлень TLS 1.3 окремо для кожного криптографічного рівня (Initial, Handshake, 1-RTT).
- **`NEW_TOKEN` (`0x07`):** надсилається сервером у стані 1-RTT. Містить довжину `Token Length` (Varint) та непрозорий бінарний масив `Token`. Клієнт зберігає цей токен і вставляє його в майбутній пакет `Initial` для проходження швидкої валідації адреси при повторних підключеннях.

### 3.5. Аварійне скидання: RESET_STREAM (`0x04`) та STOP_SENDING (`0x05`)

- **`RESET_STREAM` (`0x04`):** одностороннє скасування потоку передавачем.
  - `Stream ID` (Varint).
  - `Application Protocol Error Code` (Varint): код помилки прикладного протоколу (наприклад, `H3_REQUEST_CANCELLED = 0x010C` у HTTP/3).
  - `Final Size` (Varint): точна кількість байтів, надісланих у потік до скидання. Дозволяє приймачу скоригувати лічильники загального контролю потоку `MAX_DATA`.
- **`STOP_SENDING` (`0x05`):** прохання отримувача до джерела даних негайно припинити відправку.
  - `Stream ID` (Varint).
  - `Application Protocol Error Code` (Varint).
  При отриманні `STOP_SENDING` передавач зобов'язаний згенерувати у відповідь кадр `RESET_STREAM`.

### 3.6. Контроль потоку даних (Flow Control Frames)

QUIC реалізує дворівневий кредитний механізм контролю потоку: на рівні всього з'єднання та на рівні кожного окремого потоку.

1. **`MAX_DATA` (`0x10`):** містить `Maximum Data` (Varint). Встановлює новий сумарний ліміт байтів, який вузол дозволяє надіслати у всіх потоках з'єднання разом.
2. **`MAX_STREAM_DATA` (`0x11`):** містить `Stream ID` (Varint) та `Maximum Stream Data` (Varint). Збільшує кредит на передачу байтів у конкретний потік.
3. **`MAX_STREAMS` (`0x12` для двоспрямованих, `0x13` для односпрямованих):** містить `Maximum Streams` (Varint). Встановлює сумарну кількість потоків відповідного типу, яку дозволено відкрити віддаленому вузлу за весь час існування сесії.
4. **`DATA_BLOCKED` (`0x14`):** містить `Data Limit` (Varint). Надсилається передавачем, коли він вичерпав загальний ліміт з'єднання і не може відправляти нові дані, сповіщаючи приймача про потребу збільшити кредит.
5. **`STREAM_DATA_BLOCKED` (`0x15`):** містить `Stream ID` (Varint) та `Stream Data Limit` (Varint). Сигналізує про вичерпання ліміту конкретного потоку.
6. **`STREAMS_BLOCKED` (`0x16` для двоспрямованих, `0x17` для односпрямованих):** містить `Stream Limit` (Varint). Сповіщає про спробу відкрити потік понад дозволений ліміт.

### 3.7. Мобільність та валідація шляху: Connection ID та Path Frames

- **`NEW_CONNECTION_ID` (`0x18`):** видача нового ідентифікатора для міграції з'єднання на нову IP-адресу.
  - `Sequence Number` (Varint): порядковий номер ідентифікатора.
  - `Retire Prior To` (Varint): вказівка відкликати всі ідентифікатори з меншим номером.
  - `Length` (1 байт): довжина нового Connection ID (1..20).
  - `Connection ID`: бінарне значення (1..20 байтів).
  - `Stateless Reset Token` (16 байтів): криптографічний маркер для аварійного скидання з'єднання без збереження стану.
- **`RETIRE_CONNECTION_ID` (`0x19`):** містить `Sequence Number` (Varint). Сповіщає віддалений вузол, що вказаний Connection ID більше не використовуватиметься і може бути видалений з пам'яті.
- **`PATH_CHALLENGE` (`0x1A`):** містить 8 байтів непередбачуваних псевдовипадкових даних (`Data`). Використовується для перевірки доступності нової пари IP:Port при міграції.
- **`PATH_RESPONSE` (`0x1B`):** містить 8 байтів `Data`. Надсилається у відповідь на `PATH_CHALLENGE` з точним повторенням отриманого значення.
- **`HANDSHAKE_DONE` (`0x1E`):** не містить полів. Надсилається виключно сервером для сповіщення клієнта про те, що рукостискання остаточно завершено, а всі ранні ключі та токени валідовано.

### 3.8. Закриття з'єднання: CONNECTION_CLOSE (`0x1C` та `0x1D`)

- **`CONNECTION_CLOSE` транспортного рівня (`0x1C`):**
  - `Error Code` (Varint): код помилки з таблиці RFC 9000 §20.1.
  - `Frame Type` (Varint): тип фрейму, обробка якого викликала критичний збій (або 0, якщо помилка загальна).
  - `Reason Phrase Length` (Varint): довжина текстового опису в байтах.
  - `Reason Phrase` (рядок UTF-8): діагностичне повідомлення для логів.
- **`CONNECTION_CLOSE` прикладного рівня (`0x1D`):**
  - `Error Code` (Varint): прикладний код помилки (наприклад, HTTP/3).
  - `Reason Phrase Length` (Varint).
  - `Reason Phrase` (рядок UTF-8).

## 4. Транспортні параметри QUIC (Transport Parameters)

Під час фази криптографічного рукостискання клієнт і сервер обмінюються транспортними параметрами всередині спеціального розширення TLS 1.3 `quic_transport_parameters` (код типу `0x39`). Параметри кодуються у форматі `Type (Varint) + Length (Varint) + Value`:

- `original_destination_connection_id` (`0x00`): значення DCID з найпершого пакета `Initial` клієнта (захист від підміни сервера посередником).
- `max_idle_timeout` (`0x01`): максимальний час неактивності з'єднання в мілісекундах до автоматичного закриття.
- `stateless_reset_token` (`0x02`): 16-байтний токен для скидання з'єднання сервером у разі втрати стану (краху процесу).
- `max_udp_payload_size` (`0x03`): максимальний розмір UDP-датаграми, яку вузол здатний прийняти (за замовчуванням 65 527 байтів, мінімум 1200 байтів).
- `initial_max_data` (`0x04`): початковий кредит контролю потоку для всього з'єднання в байтах.
- `initial_max_stream_data_bidi_local` (`0x05`): кредит для двоспрямованих потоків, відкритих локальним вузлом.
- `initial_max_stream_data_bidi_remote` (`0x06`): кредит для двоспрямованих потоків, відкритих віддаленим вузлом.
- `initial_max_stream_data_uni` (`0x07`): початковий кредит для односпрямованих потоків.
- `initial_max_streams_bidi` (`0x08`): початкова максимальна кількість дозволених двоспрямованих потоків.
- `initial_max_streams_uni` (`0x09`): початкова максимальна кількість дозволених односпрямованих потоків.
- `ack_delay_exponent` (`0x0A`): експонента для масштабування поля `ACK Delay` у фреймах `ACK` (за замовчуванням 3, множник `2³ = 8` мікросекунд).
- `max_ack_delay` (`0x0B`): максимальний час у мілісекундах, на який вузол може затримати відправку `ACK` (за замовчуванням 25 мс).
- `disable_active_migration` (`0x0C`): заборона клієнту ініціювати міграцію з'єднання на інші мережеві інтерфейси (порожнє значення, наявність прапорця означає заборону).
- `active_connection_id_limit` (`0x0E`): максимальна кількість одночасно дійсних Connection ID, яку готовий підтримувати вузол (мінімум 2).
- `initial_source_connection_id` (`0x0F`): SCID із найпершого пакета відправника.
- `retry_source_connection_id` (`0x10`): SCID із пакета `Retry` (якщо сервер надсилав `Retry`).

## 5. Кінцевий автомат станів потоків QUIC

Кожен потік у QUIC має незалежний життєвий цикл і керується парою кінцевих автоматів (для передавальної та приймальної сторін):

### 5.1. Автомат передавача (Send Stream States)
1. **`Ready`:** потік створено застосунком, дані готові до відправки.
2. **`Send`:** відправлено перший кадр `STREAM`. Відбувається потокова передача даних у межах лімітів `MAX_STREAM_DATA`.
3. **`Data Sent`:** відправлено кадр `STREAM` із прапорцем `FIN`. Усі байти передано, очікується їх підтвердження.
4. **`Data Recvd`:** отримано `ACK` на всі передані байти потоку включно з `FIN`. Потік успішно завершено.
5. **`Reset Sent`:** надіслано кадр `RESET_STREAM`. Передачу припинено аварійно.
6. **`Reset Recvd`:** отримано `ACK` на кадр `RESET_STREAM`. Стан потоку остаточно звільняється з пам'яті.

### 5.2. Автомат отримувача (Receive Stream States)
1. **`Recv`:** отримано перший кадр `STREAM` для цього `Stream ID`. Виділяються буфери прийому.
2. **`Size Known`:** отримано кадр `STREAM` із прапорцем `FIN` або кадр `RESET_STREAM`. Отримувач тепер знає точний підсумковий розмір `Final Size`.
3. **`Data Recvd`:** усі байти від зсуву 0 до `Final Size` успішно прийнято та зібрано в буфері.
4. **`Data Read`:** застосунок прочитав усі байти потоку через системний виклик або API. Потік закрито штатно.
5. **`Reset Recvd`:** отримано `RESET_STREAM`. Усі незібрані дані відкидаються, застосунку передається код помилки.
6. **`Reset Read`:** застосунок сповіщено про скидання потоку.

## 6. Кадрування прикладного рівня HTTP/3 (RFC 9114)

Поверх транспортних потоків QUIC протокол HTTP/3 передає власні двійкові кадри прикладного рівня. Кожен кадр HTTP/3 має формат `Type (Varint) + Length (Varint) + Payload`:

- **`DATA` (`0x00`):** корисні байти тіла HTTP-запиту або відповіді.
- **`HEADERS` (`0x01`):** стиснений за допомогою QPACK блок заголовків HTTP (методи, шляхи, статус-коди, MIME-типи, cookies).
- **`CANCEL_PUSH` (`0x03`):** скасування серверного виштовхування ресурсу за його `Push ID`.
- **`SETTINGS` (`0x04`):** передача конфігураційних параметрів HTTP/3 (наприклад, максимальний розмір динамічної таблиці QPACK `QPACK_MAX_TABLE_CAPACITY` або максимальний розмір списку заголовків `MAX_FIELD_SECTION_SIZE`). Передається у виділеному односпрямованому потоці керування `Control Stream`.
- **`PUSH_PROMISE` (`0x05`):** анонс відправки серверного ресурсу.
- **`GOAWAY` (`0x07`):** плавне закриття прикладного з'єднання з вказівкою найбільшого обробленого `Stream ID`.
- **`MAX_PUSH_ID` (`0x0D`):** ліміт кількості серверних push-повідомлень, дозволених клієнтом.
