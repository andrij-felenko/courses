# 🧮 Математична модель оцінки RTT та алгоритми детекції втрат у QUIC

Оцінка часу кругового обігу сигналу в мережі (англ. Round-Trip Time, RTT) є наріжним каменем будь-якого транспортного протоколу з гарантованою доставкою. Від точності вимірювання RTT безпосередньо залежать своєчасність виявлення втрачених пакетів, реакція алгоритмів контролю перевантаження та запобігання надлишковим повторним передачам. У традиційному протоколі TCP оцінка затримок суттєво ускладнювалася фундаментальною неоднозначністю повторів, яка вимагала евристичних компромісів. Протокол QUIC (RFC 9002) вирішує цю проблему за допомогою строго монотонного простору номерів пакетів. Нижче наведено повний математичний апарат оцінки затримок, розрахунку згладженого RTT, таймера зондування втрат (Probe Timeout, PTO), порогових критеріїв детекції втрат пакетів за часом і номерами, детальні моделі адаптації вікна перевантаження (NewReno, CUBIC, BBR), правила стійкого перевантаження (Persistent Congestion), обробку сигналів ECN та ліміти антипідсилення атак.

## 1. Проблема неоднозначності повторів: TCP проти QUIC

У протоколі TCP кожен сегмент адресується номером послідовності байтів (`Sequence Number`). Коли сегмент втрачається або затримується в черзі маршрутизатора, передавач після спрацьовування таймауту надсилає той самий блок даних із тим самим номером послідовності. Коли від отримувача нарешті надходить підтвердження `ACK`, передавач не має математичної можливості визначити, до якої саме спроби передачі належить це підтвердження:

1. Якщо `ACK` надійшов у відповідь на **першу** (оригінальну) спробу, яка просто сильно затрималася в буфері мережі, справжній RTT дорівнює повному інтервалу від першої відправки до прийому `ACK` (`t_ack - t_send1`).
2. Якщо `ACK` надійшов у відповідь на **другу** (повторну) спробу, справжній RTT дорівнює короткому інтервалу (`t_ack - t_send2`).

Помилка у визначенні інтервалу призводить або до катастрофічного штучного завищення розрахункового RTT (якщо взяти `t_ack - t_send1`, хоча відповіла друга спроба), або до небезпечного заниження та наступного шквалу передчасних повторних передач. Через це алгоритм Карна–Партріджа (Karn's Algorithm, RFC 6298) у TCP вимагає повністю відкидати вимірювання затримок для будь-яких повторно переданих сегментів:

```
Зразок RTT у TCP:
  Якщо (пакет передавався повторно):
      RTT_sample = INVALID   [вимірювання відкидається за правилом Карна]
  Інакше:
      RTT_sample = t_ack - t_send
```

В умовах зашумлених бездротових каналів Wi-Fi або мобільного зв'язку 4G/5G, де втрати пакетів можуть сягати 2–5%, правило Карна позбавляє TCP свіжих оцінок RTT саме в ті моменти, коли мережа змінює свій стан і точна інформація про затримку є найбільш критичною.

У протоколі QUIC номер пакета (`Packet Number`, `PN`) належить виключно фізичному транспортному пакету й монотонно зростає з кожною наступною датаграмою:

```
∀ k ∈ ℕ: PN(k + 1) > PN(k)
```

Коли фрейм корисних даних `STREAM` потребує повторного надсилання, він пакується в абсолютно **новий** пакет із новим монотонним номером `PN_new > PN_old`. Отримувач у фреймі `ACK` вказує саме той `Packet Number`, який він щойно отримав. Таким чином, неоднозначність повторів усувається математично:

```
latest_RTT = t_ack_received - t_packet_sent(ACK.LargestAcknowledged)
```

Кожен надісланий пакет QUIC формує валідне, точне вимірювання затримки без винятків і евристик.

## 2. Математична модель оцінки RTT (RFC 9002 §5)

Протокол QUIC підтримує три ключові змінні стану затримки:
- `latest_RTT`: останній обчислений сирий зразок затримки між відправкою пакета та отриманням `ACK`.
- `SRTT` (Smoothed Round-Trip Time): експоненційно згладжене середнє значення RTT.
- `RTTVAR` (Round-Trip Time Variation): оцінка дисперсії (середнього абсолютного відхилення) затримок.
- `min_RTT`: мінімальний RTT, зафіксований за час з'єднання (або за ковзне часове вікно тривалістю 30–60 секунд), що відображає фізичну затримку поширення сигналу в каналі без урахування черг.

### 2.1. Корекція затримки на стороні отримувача (ACK Delay)

Фрейм `ACK` передає поле `ACK Delay` — інтервал часу `t_delay`, який пакет провів у буфері приймача до моменту відправки підтвердження (наприклад, через групування кількох ACK в одну датаграму).

Щоб отримати чисту мережеву затримку каналу, сирий зразок коригується:

```
adjusted_RTT = latest_RTT - min(ack_delay, max_ack_delay)
```

Корекція на `ack_delay` застосовується лише за виконання умови:

```
latest_RTT ≥ min_RTT + min(ack_delay, max_ack_delay)
```

Це обмеження гарантує, що неправдиве або пошкоджене значення `ack_delay` від отримувача не зробить `adjusted_RTT` меншим за фізично можливий мінімум `min_RTT`.

### 2.2. Формули експоненційного згладжування

При отриманні найпершого підтвердження в з'єднанні змінні ініціалізуються напряму:

```
SRTT = latest_RTT
RTTVAR = latest_RTT / 2
min_RTT = latest_RTT
```

Для всіх наступних вимірювань оновлення виконується за алгоритмом зваженого експоненційного згладжування з коефіцієнтами `α = 1/8` (вага згладжування середнього) та `β = 1/4` (вага варіації):

```
RTTVAR_новий = (1 - β) · RTTVAR_старий + β · |SRTT_старий - adjusted_RTT|
             = 3/4 · RTTVAR_старий + 1/4 · |SRTT_старий - adjusted_RTT|

SRTT_новий   = (1 - α) · SRTT_старий + α · adjusted_RTT
             = 7/8 · SRTT_старий + 1/8 · adjusted_RTT

min_RTT_новий = min(min_RTT_старий, latest_RTT)
```

### 2.3. Покроковий числовий розрахунок оновлення RTT

**Приклад розрахунку:** Нехай поточний стан `SRTT = 80 мс`, `RTTVAR = 12 мс`, `min_RTT = 60 мс`, `max_ack_delay = 25 мс`. Надійшов `ACK` із параметрами: час відправки пакета `t_send = 1000 мс`, час прийому `ACK` `t_recv = 1110 мс`, передане значення `ack_delay = 10 мс`.

```
latest_RTT
= 1110 - 1000                                 [визначення сирої затримки]
= 110 мс

ack_delay_actual
= min(10, 25)                                 [обмеження ack_delay лімітом max_ack_delay]
= 10 мс

adjusted_RTT
= 110 - 10                                    [віднімання затримки обробки на приймачі]
= 100 мс                                      [перевірка: 110 ≥ 60 + 10 = 70 — умова виконана]

RTTVAR_оновлення:
= 3/4 · 12 + 1/4 · |80 - 100|                 [формула варіації: 3/4 попереднього + 1/4 похибки]
= 9 + 1/4 · 20                                [модуль похибки |80 - 100| = 20 мс]
= 9 + 5
= 14 мс

SRTT_оновлення:
= 7/8 · 80 + 1/8 · 100                        [формула згладженого середнього]
= 70 + 12.5
= 82.5 мс

min_RTT_оновлення:
= min(60, 110)
= 60 мс
```

У результаті згладжений RTT плавно зріс з `80 мс` до `82.5 мс`, а варіація адаптивно розширилася з `12 мс` до `14 мс`, врахувавши тимчасовий сплеск затримки в каналі.

## 3. Розрахунок таймера зондування втрат (Probe Timeout, PTO)

На відміну від класичного протоколу TCP, який у разі відсутності підтверджень використовує агресивний таймер повторної передачі (Retransmission Timeout, RTO) і при його спрацьовуванні обвалює вікно перевантаження до 1 пакета та блокує відправку даних, QUIC застосовує механізм зондування шляху (Probe Timeout, PTO).

Таймер PTO обчислюється за формулою (RFC 9002 §6.2.1):

```
PTO = SRTT + max(4 · RTTVAR, kGranularity) + max_ack_delay
```

де:
- `4 · RTTVAR` — чотириразове стандартне відхилення, що охоплює понад 99% очікуваних випадкових коливань затримки.
- `kGranularity` — мінімальна системна дискретність системного годинника таймерів операційної системи (типово `1 мс`).
- `max_ack_delay` — максимальна узгоджена затримка формування підтвердження на віддаленому кінці.

Якщо за час `PTO` від віддаленого вузла не надійшло жодного підтвердження, передавач не зупиняє роботу і не очищує вікно. Він генерує один або два спеціальні пакети-зонди (Probe Packets), що містять фрейми з новими номерами (`PING` або повтор найстаріших непідтверджених даних `STREAM`), змушуючи отримувача негайно повернути `ACK`.

У разі послідовних невдач зондування інтервал експоненційно подвоюється (експоненційний відкат, англ. exponential backoff):

```
PTO_k = 2^k · PTO_0
```

де `k` — кількість послідовних непідтверджених спроб зондування.

## 4. Алгоритми виявлення втрат пакетів

QUIC використовує два паралельні взаємодоповнюючі критерії для констатації факту втрати пакета: **пороговий критерій за номерами пакетів** (Packet Threshold) та **пороговий критерій за часом** (Time Threshold).

### 4.1. Детекція за порогом номерів пакетів (Packet Threshold)

Якщо отримувач надіслав підтвердження на пакет з номером `PN_highest_acked`, а деякі пакети з меншими номерами все ще залишаються непідтвердженими, виникає питання: вони втрачені чи просто змінили порядок у мережі (reordering)?

QUIC визначає константу порогової розбіжності (RFC 9002 §6.1.1):

```
kPacketThreshold = 3
```

**Правило:** Пакет із номером `PN_unacked` вважається остаточно втраченим, якщо виконується умова:

```
PN_highest_acked - PN_unacked ≥ kPacketThreshold
```

**Приклад:** Якщо передавач отримав підтвердження на пакет `PN = 45`, то всі непідтверджені пакети з номерами `PN ≤ 45 - 3 = 42` (тобто пакети `40`, `41`, `42`) негайно оголошуються втраченими і ставляться в чергу на повторне кадрування.

### 4.2. Детекція за порогом часу (Time Threshold)

Якщо відправка була невеликою (наприклад, передано всього 2 пакети `PN = 10` і `PN = 11`), і пакет `10` загубився, пороговий критерій за номерами не спрацює, оскільки `PN_highest_acked = 11`, а різниця `11 - 10 = 1 < 3`.

Для таких випадків QUIC використовує часовий поріг втрати (RFC 9002 §6.1.2):

```
kTimeThreshold = 9/8 = 1.125

time_threshold = max(kTimeThreshold · max(SRTT, latest_RTT), kGranularity)
```

**Правило:** Непідтверджений пакет вважається втраченим, якщо з моменту його відправки минув час, що перевищує момент відправки найновішого підтвердженого пакета плюс часовий поріг:

```
t_loss = t_send(PN_unacked) + time_threshold

Якщо t_current ≥ t_loss → пакет PN_unacked вважається ВТРАЧЕНИМ.
```

Коефіцієнт `9/8 = 1.125` (додаткові 12.5% запасу до RTT) вибрано як математичний оптимум на основі симуляцій інтернет-трафіку: він забезпечує 99.8% стійкості до типового перевпорядкування пакетів у бездротових мережах LTE/Wi-Fi та магістральних маршрутизаторах, водночас скорочуючи затримку повторної передачі втричі порівняно з класичним RTO у TCP.

## 5. Моделі контролю перевантаження у QUIC

Протокол QUIC має модульну архітектуру контролю перевантаження: оскільки він працює у просторі користувача, алгоритми можна оновлювати без модифікації ядра операційної системи.

### 5.1. Початкове вікно та фази NewReno

Початкове вікно перевантаження (Initial Window, `IW`) розраховується згідно з RFC 9002 §7.2:

```
IW = min(10 · max_datagram_size, max(2 · max_datagram_size, 14720 байтів))
```

При стандартному розмірі MTU в 1280 байтів `IW` становить приблизно 10 пакетів (14 720 байтів).

- **Повільний старт (Slow Start):** вікно зростає експоненційно. На кожен підтверджений байт `acked_bytes`:
  ```
  cwnd_новий = cwnd_старий + acked_bytes
  ```
- **Уникнення перевантаження (Congestion Avoidance):** вікно зростає лінійно, додаючи приблизно один повний пакет за один RTT:
  ```
  cwnd_новий = cwnd_старий + (max_datagram_size · acked_bytes) / cwnd_старий
  ```
- **Реакція на втрату (Multiplicative Decrease):**
  ```
  ssthresh = cwnd · kLossReductionFactor    [де kLossReductionFactor = 0.5]
  cwnd     = ssthresh
  ```

### 5.2. Модель алгоритму CUBIC у QUIC (RFC 8312)

Алгоритм CUBIC замінює лінійне зростання вікна кубічною функцією від часу `t`, що минув від останньої зафіксованої втрати. За стандартом RFC 8312 розрахунок ведеться в одиницях пакетів (сегментів розміру `S = max_datagram_size = 1280` байтів) або масштабується на розмір сегмента:

```
W_cubic(t) = C · (t - K)³ + W_max
```

де:
- `W_max` — розмір вікна `cwnd` безпосередньо перед останньою подією втрати пакета (у пакетах: `W_max = 64 000 / 1280 = 50` пакетів).
- `C = 0.4` — безрозмірна константа масштабування кубічної кривої.
- `β = 0.7` — мультиплікативний фактор зменшення вікна при втраті (вікно скидається до `β · W_max = 0.7 · 50 = 35` пакетів, тобто `44 800` байтів).
- `K` — точка перегину функції (час у секундах, необхідний для виходу на попередній максимум `W_max`):
  ```
  K = ∛(W_max · (1 - β) / C) = ∛(50 · 0.3 / 0.4) = ∛(37.5) ≈ 3.347 с
  ```

**Покроковий числовий приклад динаміки CUBIC:** Нехай до втрати вікно було `W_max = 50 пакетів` (`64 000` байтів при `S = 1280` байтів).

```
Розрахунок точки перегину K:
K = ∛(50 · 0.3 / 0.4)
  = ∛(37.5)
  ≈ 3.347 с

1. Стан при t = 0 с (момент втрати):
W_cubic(0) = 0.4 · (0 - 3.347)³ + 50
           = 0.4 · (-37.5) + 50
           = -15 + 50
           = 35 пакетів (44 800 байтів)         [вікно скинуто рівно до 0.7 · 50 = 35 пакетів]

2. Стан при t = 1.674 с (половина часу до точки K):
t - K = 1.674 - 3.347 = -1.673 с
(t - K)³ = (-1.673)³ ≈ -4.683
W_cubic(1.674) = 0.4 · (-4.683) + 50
               = -1.873 + 50
               = 48.127 пакетів (61 603 байти)  [швидке відновлення 87.5% втраченого вікна]

3. Стан при t = 3.347 с (вирівнювання на плато K):
W_cubic(K) = 0.4 · (0)³ + 50
           = 50 пакетів (64 000 байтів)         [вікно плавно досягло колишнього піку]

4. Стан при t = 5.0 с (зондування нової пропускної здатності):
t - K = 5.0 - 3.347 = 1.653 с
(t - K)³ = (1.653)³ ≈ 4.516
W_cubic(5.0) = 0.4 · 4.516 + 50
             = 1.806 + 50
             = 51.806 пакетів (66 312 байтів)   [нарощування понад колишній максимум]
```

**Аналіз динаміки CUBIC:**
1. Коли `t < K`, функція опукла вгору — вікно швидко зростає після скидання, повертаючись до безпечної зони.
2. Коли `t ≈ K`, похідна `dW/dt ≈ 0` — вікно стабілізується поблизу `W_max`, обережно зондуючи мережу на наявність вільної смуги (зона плато).
3. Коли `t > K`, функція опукла вниз — якщо втрат немає, CUBIC починає агресивно нарощувати вікно у пошуку нової пропускної здатності.

### 5.3. Модель BBR (Bottleneck Bandwidth and RTT)

Алгоритм BBR (розроблений Нілом Кардвеллом і Ван Якобсоном) відмовляється від реакції на випадкові втрати пакетів, моделюючи мережевий шлях через дві фундаментальні фізичні характеристики:
1. `BtlBw` (Bottleneck Bandwidth) — максимальна пропускна здатність найвужчого місця каналу (оцінюється як максі-фільтр за останні 10 RTT).
2. `RTprop` (Round-Trip Propagation Time) — мінімальний фізичний час поширення сигналу в середовищі без урахування затримок у чергах маршрутизаторів (міні-фільтр за останні кілька секунд).

Добуток цих величин визначає ємність каналу (Bandwidth-Delay Product, `BDP`):

```
BDP = BtlBw · RTprop
```

QUIC-рушій підтримує обсяг даних у польоті (`inflight`) на рівні:

```
inflight_target = BDP + pacing_headroom
```

а темп відправки датаграм (Pacing Rate) регулюється формулою:

```
pacing_rate = pacing_gain · BtlBw
```

**Приклад розрахунку:** Канал має виміряну пропускну здатність `BtlBw = 100 Мбіт/с` (`12.5 Мбайт/с`) та фізичну затримку `RTprop = 40 мс` (`0.04 с`).

```
Ємність каналу BDP:
BDP = 12.5 Мбайт/с · 0.04 с
    = 0.5 Мбайт
    = 500 000 байтів                      [близько 390 пакетів по 1280 байтів]

Темп відправки (Pacing Rate у фазі PROBE_BW, gain = 1.25):
pacing_rate = 1.25 · 12.5 Мбайт/с
            = 15.625 Мбайт/с
            = 125 Мбіт/с

Інтервал між пакетами (Pacing Interval для пакета 1280 B):
interval = 1280 байтів / 15 625 000 байтів/с
         ≈ 81.92 мікросекунди
```

Завдяки ізоляції кожного потоку у просторі користувача, QUIC забезпечує роботу пейсингу з мікросекундною точністю, усуваючи пакетні сплески (bursts), які у традиційному TCP переповнювали буфери комутаторів (явище bufferbloat).

### 5.4. Реакція на сигнали явної сигналізації перевантаження (ECN)

Окрім втрати пакетів, QUIC підтримує явну сигналізацію перевантаження (Explicit Congestion Notification, RFC 3168 та RFC 9002 §7.1). Коли проміжний маршрутизатор фіксує накопичення черги, він не відкидає IP-пакет, а виставляє у його заголовку прапорець `CE` (Congestion Experienced).

Приймач QUIC підраховує кількість пакетів з прапорцем `CE` і повертає лічильник `ECN-CE Count` у фреймі `ACK_ECN` (`0x03`). Коли передавач бачить зростання лічильника `ECN-CE`, він реагує на цю подію точно так само, як на втрату пакета:

```
ssthresh = cwnd · kLossReductionFactor
cwnd     = ssthresh
```

Математична перевага ECN у QUIC полягає в тому, що вікно перевантаження зменшується **до** того, як черга маршрутизатора переповниться й виникне реальна втрата пакета. Це запобігає затримкам на повторну передачу та зберігає плавність потокового трафіку.

### 5.5. Математичний критерій стійкого перевантаження (Persistent Congestion)

Якщо мережевий канал зазнав тривалого розриву (наприклад, перемикання базової станції), поодиноке зменшення вікна `cwnd` не рятує від колапсу черг. RFC 9002 (§7.6) вводить поняття стійкого перевантаження (Persistent Congestion).

Стан стійкого перевантаження оголошується, якщо всі пакети, надіслані протягом інтервалу часу `T_congestion`, виявилися втраченими:

```
T_congestion = PTO · kPersistentCongestionThreshold
```

де константа порогу `kPersistentCongestionThreshold = 3`.

Якщо втрати охоплюють проміжок між найпершим втраченим пакетом `t_send_first` та останнім втраченим `t_send_last`, такий що:

```
t_send_last - t_send_first ≥ 3 · PTO
```

рушій QUIC вважає мережевий шлях повністю заблокованим і виконує жорстке скидання:

```
cwnd = kMinimumWindow = 2 · max_datagram_size
```

Це дозволяє протоколу миттєво припинити навантажувати зламаний канал без розриву криптографічної сесії TLS та без необхідності переузгодження ключів шифрування.

## 6. Математика ліміту антипідсилення атак (Anti-Amplification Limit)

Датаграми UDP можуть надсилатися зі сфальшованою IP-адресою джерела (IP Spoofing). Зловмисник може надіслати короткий пакет `Initial` розміром 1200 байтів, вказавши як зворотну адресу жертву атаки. Якщо сервер відповість повним ланцюжком сертифікатів TLS розміром 10–15 кілобайтів, це створить десятикратне підсилення розподіленої атаки на відмову в обслуговуванні (DRDoS).

Для запобігання цій загрозі RFC 9000 (§8.1) встановлює строгий закон антипідсилення:

```
bytes_sent(unvalidated_path) ≤ 3 · bytes_received(unvalidated_path)
```

**Математичне обмеження:** Доти, доки клієнт не підтвердить володіння своєю IP-адресою (надіславши підтвердження `ACK` або пройшовши перевірку `PATH_RESPONSE` / `Retry`), сервер має право відправити у відповідь **максимум утричі більше байтів**, ніж він сумарно отримав від цієї IP-адреси.

Якщо клієнт надіслав `Initial` розміром `1200 байтів`, сервер може надіслати у відповідь не більше `3600 байтів`. Якщо сертифікат сервера перевищує цей ліміт, сервер зобов'язаний зупинити відправку й очікувати наступного пакета `Initial` або `Handshake` від клієнта.
