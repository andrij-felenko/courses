# 📜 Від закритих плагінів до відкритого стандарту: як народився WebRTC

До появи стандарту WebRTC у 2011 році передача живого голосу та відео у веббраузері вимагала встановлення сторонніх бінарних модулів або використання власницьких плагінів. Архітектура Всесвітньої павутини будувалася довкола клієнт-серверної парадигми поверх протоколу TCP: браузер надсилав HTTP-запит і очікував на повне завантаження статичного документа або файлу. Спроби реалізувати двостороннє спілкування реального часу з затримкою менше ніж 200 мілісекунд у межах стандартного пісочника браузера розбивалися об фундаментальні обмеження: відсутність прямого доступу JavaScript до апаратних засобів захоплення аудіо й відео (мікрофонів, вебкамер), відсутність підтримки датаграм UDP та неможливість прямого з'єднання двох браузерів без посередництва центрального сервера.

У 2000-х роках ринок інтернет-комунікацій був повністю фрагментований. Кожна система голосового чи відеозв'язку — Skype, Yahoo! Messenger, AOL Instant Messenger, ICQ, WebEx — використовувала власні закриті мережеві протоколи, специфічні аудіокодеки та несумісні клієнтські програми.

## Епоха плагінів: ActiveX, NPAPI та монополія Adobe Flash

Перші спроби інтегрувати відеозв'язок у браузери спиралися на технологію плагінів: ActiveX для Microsoft Internet Explorer та NPAPI (Netscape Plugin Application Programming Interface) для браузерів сімейства Mozilla й Netscape. Сторонні розробники писали нативні динамічні бібліотеки на C/C++, які завантажувалися у спільний адресний простір браузера та отримували необмежений доступ до системних викликів операційної системи Windows або macOS.

Такий підхід спричиняв хронічні проблеми безпеки та стабільності. Будь-яке переповнення буфера або помилка адресації пам'яті всередині плагіна призводили до аварійного завершення всього браузера, а вразливості нульового дня дозволяли зловмисникам виконувати довільний машинний код на комп'ютері користувача.

У другій половині 2000-х років монопольне становище у вебмедіа зайняла платформа Adobe Flash Player. Завдяки протоколу RTMP (Real-Time Messaging Protocol) та серверному середовищу Flash Media Server (FMS) розробники отримали можливість транслювати відео з вебкамери у вікно браузера. Проте RTMP базувався на протоколі TCP, що у разі навіть незначних втрат пакетів у бездротових мережах спричиняло ефект блокування початку черги (Head-of-Line Blocking) і примушувало плеєр збільшувати буфер відтворення до 2–5 секунд. Інтерактивна розмова ставала неможливою через неприйнятне відставання звуку від реального часу. Крім того, Flash не підтримував пряме пірингове з'єднання (Peer-to-Peer): увесь медіатрафік мусив проходити через дорогі ретрансляційні медіасервери.

## Спадок Global IP Solutions (GIPS)

Технічний фундамент сучасного WebRTC було закладено компанією Global IP Solutions (початкова назва — Global IP Sound), заснованою у 1999 році шведськими науковцями та інженерами Руаром Гагеном (Roar Hagen) і Бастіаном Клейном (Bastiaan Kleijn) у Стокгольмі. GIPS зосередилася на розв'язанні найскладніших математичних задач цифрової обробки сигналів (DSP) у ненадійних IP-мережах із високим джиттером та втратами пакетів.

Команда GIPS створила стек програмних модулів, які визначили галузевий стандарт обробки аудіо та відео:

1. **NetEQ (Network Equalizer)** — адаптивний конвеєр обробки мовлення, що об'єднував адаптивний буфер джиттера, алгоритми конкатенації мовленнєвих пакетів та механізм маскування втрат пакетів (Packet Loss Concealment, PLC) за допомогою часового масштабування сигналу (Time-Scale Modification) без спотворення висоти тону.
2. **Акустичне відлуння (Acoustic Echo Cancellation, AEC)** — адаптивні цифрові фільтри, які усували сигнал колонок, що потрапляв назад у чутливий мікрофон користувача під час гучномовного зв'язку.
3. **iSAC та iLBC** — власні широкосмугові та вузькосмугові мовленнєві кодеки, оптимізовані для передачі через модемні та перші широкосмугові інтернет-лінії.
4. **VoiceEngine та VideoEngine** — оптимізовані нативні C++ рушії захоплення, кодування, синхронізації та рендерингу мультимедійних потоків для операційних систем Windows, Linux, macOS, iOS та Android.

Стек GIPS був настільки досконалим, що його ліцензували майже всі лідери комунікаційного ринку: Skype використовував аудіорушій GIPS на етапі свого бурхливого зростання, Google інтегрував його у Google Talk, а компанії Cisco, WebEx, Yahoo! та AOL спиралися на бібліотеки GIPS у власних месенджерах.

## Поглинання Google та відкриття вихідного коду (2010–2011)

Наприкінці 2000-х років корпорація Google вела активний розвиток браузера Google Chrome та поштової служби Gmail. Для створення інтегрованого відеочату компанія залежала від ліцензованого коду GIPS. У травні 2010 року Google оголосила про придбання компанії Global IP Solutions за 68,2 мільйона доларів США. Угода була завершена в липні 2010 року.

Замість того, щоб перетворити технології GIPS на власницьку конкурентну перевагу Chrome, команда Google під керівництвом інженерів Гаральда Альвестранда (Harald Alvestrand) та Джастіна Уберті (Justin Uberti) ухвалила стратегічне рішення: повністю відкрити вихідний код рушія GIPS і передати його світовій спільноті для створення єдиного відкритого інтернет-стандарту.

1 червня 2011 року Google випустила відкритий проєкт `libwebrtc` під ліцензією BSD. Водночас компанія подала пропозиції до двох провідних міжнародних органів стандартизації:

- **Консорціум W3C (World Wide Web Consortium)** — формування робочої групи WebRTC 1.0 Working Group для розробки об'єктної моделі JavaScript API (`RTCPeerConnection`, `MediaStream`, `RTCDataChannel`).
- **IETF (Internet Engineering Task Force)** — створення робочої групи RTCWEB (Real-Time Communication in WEB-browsers) для стандартизації протоколів передачі даних у мережі: захищеного транспорту SRTP, узгодження ключів DTLS, проходження NAT через ICE/STUN/TURN та адаптивного керування бітрейтом.

## Битва кодеків у IETF: H.264 проти VP8

Спроба стандартизувати WebRTC у період 2011–2014 років наштовхнулася на гостре протистояння виробників довкола обов'язкового для реалізації відеокодека (Mandatory to Implement, MTI).

Google та Mozilla наполягали на кодеку VP8 (а згодом VP9), вихідний код якого Google також відкрила після поглинання компанії On2 Technologies. Головним аргументом була відсутність роялті та відкрита ліцензія, що дозволяло будь-якому незалежному розробнику реалізовувати браузер без виплати патентних зборів пулу MPEG LA.

Натомість компанії Cisco, Apple та Microsoft виступали за кодек H.264 (AVC). Аргументація базувалася на колосальній установленій базі апаратних декодерів: мобільні процесори смартфонів (Qualcomm Snapdragon, Apple A-series) та відеокарти містили кремнієві блоки апаратного декодування H.264. Програмне декодування VP8 на мобільних пристроях тих років призводило до швидкого розряджання батареї та перегрівання корпусу.

Компроміс було знайдено завдяки безпрецедентному кроку компанії Cisco. У жовтні 2013 року старший віцепрезидент Cisco Ровен Троллоп (Rowan Trollope) оголосив про відкриття модуля OpenH264: Cisco взяла на себе сплату всіх ліцензійних відрахувань пулу MPEG LA за попередньо зібрані бінарні модулі, які Mozilla Firefox та інші програми могли динамічно завантажувати під час першого запуску.

У листопаді 2014 року IETF RTCWEB ухвалила історичний компроміс (зафіксований у RFC 7742): усі WebRTC-сумісні браузери зобов'язані підтримувати **як VP8, так і H.264 Constrained Baseline Profile**. Це відкрило шлях до глобальної інтероперабельності.

## Архітектурний конфлікт: Plan B проти Unified Plan

Після вирішення питання щодо відеокодеків спільнота розробників браузерів зіткнулася з новою проблемою, яка ледь не розколола екосистему WebRTC: як описувати декілька медіапотоків (наприклад, вебкамеру та трансляцію екрана або відео кількох учасників конференції) усередині єдиного SDP-документа.

Команда Google Chrome ще у 2013 році реалізувала підхід, відомий як **Plan B**. За цією схемою у документі SDP створювалася лише одна медіасекція `m=video`, всередині якої за допомогою специфічних атрибутів `a=ssrc` перелічувалися всі доступні відеопотоки. Такий підхід був швидким у реалізації, проте він порушував стандартну модель Offer/Answer (RFC 3264), де кожна медіасекція `m=` мала відповідати окремому каналу транспорту або порту.

Mozilla Firefox відмовилася підтримувати Plan B і реалізувала строгий стандарт IETF — **Unified Plan** (RFC 8829). У Unified Plan кожен окремий відеотрек чи джерело отримує власну незалежну секцію `m=video`, яка пов'язується через групування BUNDLE на єдиному транспортному порту. Це призвело до ситуації, коли SDP, сформований Chrome, не міг бути коректно розібраний Firefox без складних JavaScript-адаптерів (бібліотеки `adapter.js`).

Перехід усієї індустрії на Unified Plan тривав майже п'ять років. Google Chrome остаточно оголосив Plan B застарілим і повністю видалив його підтримку лише у 2021 році, що дозволило звести всі реалізації браузерів до єдиного строгого парсера сесій.

## Перший міжбраузерний дзвінок і фінальна стандартизація

У лютому 2013 року відбулася подія, що довела життєздатність концепції: інженери Джастін Уберті (Google) та Роберт Нюман разом із Філіпом Ганке (Mozilla) здійснили перший в історії прямий відеодзвінок між двома різними браузерами — Google Chrome та Mozilla Firefox — без використання будь-яких сторонніх серверів транскодування чи плагінів.

Шлях до повної міжбраузерної підтримки тривав ще кілька років:
- У 2015 році Microsoft представила альтернативну об'єктну модель ORTC (Object Real-Time Communications) для перших версій Microsoft Edge, проте згодом перейшла на кодову базу Chromium та узгодила свої API з WebRTC 1.0.
- У вересні 2017 року Apple інтегрувала WebRTC у рушій WebKit та браузер Safari 11 для iOS та macOS, ліквідувавши останню білу пляму на карті мобільних та настільних платформ.

26 січня 2021 року консорціум W3C та інженерна група IETF офіційно оголосили про присвоєння специфікаціям WebRTC 1.0 статусу офіційної рекомендації (W3C Recommendation) та публікацію пакету стандартів RFC 8825 – RFC 8874. Технологія пройшла десятирічний шлях від закритого комерційного пакета обробки сигналів до фундаментальної інфраструктури сучасного інтернету, що забезпечує роботу глобальних сервісів відеоконференцій, телемедицини, хмарного геймінгу та дистанційного керування безпілотними апаратами.
