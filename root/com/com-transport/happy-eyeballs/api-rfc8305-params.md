# 📋 Специфікація параметрів і конфігурація Happy Eyeballs

Довідник параметрів таймерів, станів кінцевого автомата RFC 8305 та конфігураційних інтерфейсів у системних бібліотеках (libcurl, Go net, Apple Network.framework, Chromium, Envoy, Rust reqwest).

## Специфікація нормативних таймерів RFC 8305

Стандарт IETF RFC 8305 регламентує поведінку мережевих клієнтів за допомогою набору часових параметрів, які забезпечують баланс між швидкістю відкриття з'єднання для користувача та навантаженням на сервери й проміжне мережеве обладнання.

| Параметр | Значення за замовчуванням | Допустимий діапазон | Опис та призначення |
| :--- | :--- | :--- | :--- |
| **Resolution Delay** | 50 мс | 10–100 мс | Час очікування відповіді DNS AAAA після отримання відповіді DNS A. Якщо запис IPv4 прибуває першим, клієнт чекає 50 мс, щоб дати запиту IPv6 шанс прибути й розпочати гонку з пріоритетом IPv6. |
| **Connection Attempt Delay** | 250 мс | 100–500 мс | Інтервал між послідовним запуском паралельних спроб `connect()`. Якщо перший сокет (IPv6) не завершує TCP 3-way handshake за 250 мс, запускається наступний сокет (IPv4). |
| **Minimum Connection Timeout** | 10–30 с | 5–60 с | Загальний максимальний час очікування встановлення з'єднання для хоста до повернення системної помилки таймауту (`ETIMEDOUT`). |
| **Stateful Deprecation Interval** | 10–30 хв | 5–60 хв | Час збереження інформації про збій зв'язку до цільового префікса IP. Протягом цього часу непрацююча родина адрес тимчасово опускається в кінець черги спроб. |
| **Max Concurrent Sockets** | 2–4 сокети | 2–8 сокетів | Максимальна кількість сокетів, які можуть одночасно перебувати в активній фазі встановлення з'єднання (стан SYN_SENT), для захисту серверів від перевантаження запитами. |

## Детальний інженерний аналіз таймерів

### 1. Таймер затримки резолвінгу DNS (Resolution Delay = 50 мс)

Під час паралельного надсилання DNS-запитів типу AAAA (IPv6) та типу A (IPv4) відповіді майже ніколи не повертаються абсолютно одночасно. У реальних мережах авторитетні сервери імен часто обробляють запити AAAA дещо довше через більший розмір записів, додаткову криптографічну верифікацію DNSSEC або складнішу структуру зони.

Якщо клієнт починає встановлення TCP-з'єднання негайно після отримання найпершого пакета DNS-відповіді, виникає небезпечна асиметрія:
* Відповідь A (IPv4) прибуває через 15 мс.
* Відповідь AAAA (IPv6) прибуває через 22 мс (лише на 7 мс пізніше).
* Якщо затримка відсутня, клієнт стартує з'єднання через IPv4 у момент `t = 15 мс`. Коли о 22 мс надходить запис IPv6, пріоритет протоколу нового покоління вже втрачено — з'єднання IPv4 стартувало першим і виграє гонку.

Таймер `Resolution Delay` (50 мс) запобігає цій проблемі. Коли клієнт отримує запис A першим, він не починає підключення, а запускає таймер на 50 мс. Якщо за цей короткий проміжок надходить відповідь AAAA, черга з'єднань стартує з IPv6, як того вимагає стандарт RFC 6724. Якщо ж відповідь AAAA не приходить за 50 мс (сервер не має записів IPv6 або шлях IPv6 зазнає збою), клієнт починає роботу з IPv4, не змушуючи користувача чекати повного таймауту DNS.

### 2. Таймер затримки спроби з'єднання (Connection Attempt Delay = 250 мс)

Таймер `Connection Attempt Delay` регулює часовий інтервал між запуском послідовних паралельних сокетів у черзі чергування. 

Вибір значення 250 мс базується на детальних статистичних дослідженнях мережевих затримок у масштабах світового інтернету:
* **Захист від SYN Flood на стороні серверів:** Якби клієнти запускали підключення до IPv6 та IPv4 одночасно в момент `t = 0` (так звана агресивна гонка 50/50), навантаження на сервери за кількістю вхідних SYN-пакетів та відкритих сокетів зросло б рівно вдвічі. Для масштабних веб-сервісів (Google, Cloudflare, Meta) це означало б генерацію сотень мільйонів зайвих запитів на секунду.
* **Перекриття типового RTT:** Медіанний час кругового обігу пакетів (Round-Trip Time) для континентального інтернет-трафіку становить 20–80 мс, а для міжконтинентального — 120–180 мс. Інтервал 250 мс дає справному з'єднанню IPv6 достатньо часу, щоб завершити тристороннє рукостискання (SYN → SYN-ACK → ACK) без запуску резервного з'єднання IPv4.
* **Зниження затримки для користувача при збоях:** Якщо шлях IPv6 потрапив у «чорну діру», 250 мс — це майже непомітна затримка для людського ока під час завантаження веб-сторінки, що в сотні разів краще за стандартний 30-секундний таймаут операційної системи.

### 3. Кешування працездатності адрес (RDA Cache та Statefulness)

Стандарт RFC 8305 заохочує збереження історичного стану працездатності адрес (Round-Trip and Destination Address Statefulness). Клієнтський мережевий стек підтримує невелику таблицю в оперативній пам'яті (зазвичай на 256–1024 записи), де ключем є префікс цільової мережі (наприклад, `/48` або `/64` для IPv6 та `/24` для IPv4).

Якщо під час попередніх спроб протягом останніх 10–30 хвилин підключення до певного префікса IPv6 постійно зазнавали збою або завершувалися таймаутом, рушій тимчасово модифікує алгоритм чергування для цього домену:
1. Адреси дефектного префікса IPv6 опускаються в кінець черги або отримують збільшений штрафний таймер затримки.
2. Перша спроба підключення відправляється на надійну адресу IPv4 негайно в момент `t = 0`.
3. Періодично (раз на 10–15 хвилин) клієнт виконує фонове зондування шляху IPv6, щоб автоматично відновити його первинний пріоритет у разі відновлення працездатності каналу зв'язку.

Кеш стану прив'язується до поточного мережевого інтерфейсу та ідентифікатора мережі (SSID Wi-Fi або підмережі DHCP). Щойно пристрій змінює точку доступу (наприклад, смартфон перемикається з Wi-Fi на стільникову мережу LTE), кеш працездатності повністю анулюється, оскільки новий провайдер може мати бездоганну маршрутизацію IPv6.

Крім того, у багатоінтерфейсних системах (Multi-homed Hosts) рушій Happy Eyeballs зобов'язаний враховувати ідентифікатор зони дії інтерфейсу (Scope ID або `sin6_scope_id` для канальних адрес `fe80::/10`). Спроба підключення до канальної адреси без явної вказівки правильного числового індексу адаптера завершується миттєвою системною помилкою `EINVAL`, що вимагає від сокетного рушія фільтрації некоректних адрес ще на етапі сортування.

## Стани та переходи кінцевого автомата RFC 8305

Керування змаганням з'єднань описується кінцевим автоматом із чітко визначеними подіями, умовами переходу (Guards) та результуючими діями.

```
       [ ПОЧАТОК ]
            │
            ▼
    ┌───────────────┐
    │  DNS_RESOLVE  │ <── Одночасне надсилання запитів A та AAAA
    └───────┬───────┘
            │
            ├────────────────────────────────────────┐
            ▼ (прибув AAAA першим)                   ▼ (прибув A першим)
    ┌───────────────┐                        ┌───────────────┐
    │ SORT_INTERLV  │                        │  WAIT_RESOLV  │ (старт таймера 50 мс)
    └───────┬───────┘                        └───────┬───────┘
            │                                        │
            │ <── (прибув AAAA або сплив 50 мс) ─────┘
            ▼
    ┌───────────────┐
    │ SCHED_CONNECT │ <── Відкриття сокета #N (неблокуючий connect)
    └───────┬───────┘
            │
            ▼
    ┌───────────────┐
    │ RACING_POLL   │ <── Очікування POLLOUT та відлік таймера 250 мс
    └───────┬───────┘
            │
            ├──────────────────────────┐
            ▼ (сплив 250 мс)           ▼ (успішний SYN-ACK: SO_ERROR == 0)
    ┌───────────────┐          ┌───────────────┐
    │ SCHED_CONNECT │          │ CONNECTED_WIN │
    │ (наступний N) │          └───────┬───────┘
    └───────────────┘                  │
                                       ▼
                               ┌───────────────┐
                               │ CLEANUP_RST   │ <── Закриття невдалих сокетів
                               └───────────────┘
```

| Поточний стан | Подія / Тригер | Умова (Guard) | Результуюча дія | Новий стан |
| :--- | :--- | :--- | :--- | :--- |
| `DNS_RESOLVE` | Прибуття відповіді AAAA | Відповідь містить дійсні IP-адреси | Зберегти адреси IPv6; якщо A вже є або таймер вичерпано — виконати чергування | `SORT_INTERLV` |
| `DNS_RESOLVE` | Прибуття відповіді A | AAAA ще не надійшов | Зберегти адреси IPv4; запустити таймер `Resolution Delay` (50 мс) | `WAIT_RESOLV` |
| `WAIT_RESOLV` | Спливання таймера 50 мс | AAAA так і не надійшов | Сформувати чергу лише з IPv4-адрес | `SORT_INTERLV` |
| `WAIT_RESOLV` | Прибуття відповіді AAAA | До спливання таймера 50 мс | Скасувати таймер; об'єднати списки за алгоритмом чергування | `SORT_INTERLV` |
| `SORT_INTERLV` | Черга сформована | Список адрес непорожній | Запустити першу спробу підключення; звести таймер `Attempt Delay` (250 мс) | `SCHED_CONNECT` |
| `SCHED_CONNECT`| Виклик `connect()` | Повернено `EINPROGRESS` | Додати сокет до пулу опитування `poll()` | `RACING_POLL` |
| `SCHED_CONNECT`| Виклик `connect()` | Миттєва системна помилка (`ENETUNREACH`) | Закрити сокет; спробувати наступну адресу черги негайно | `SCHED_CONNECT` |
| `RACING_POLL`  | Спливання таймера 250 мс | У черзі є неперевірені адреси | Запустити спробу для наступної адреси паралельно | `SCHED_CONNECT` |
| `RACING_POLL`  | Сигнал `POLLOUT` | `getsockopt(SO_ERROR) == 0` | Оголосити сокет переможцем; надіслати `close()` усім іншим сокетам пулу | `CONNECTED_WIN` |
| `RACING_POLL`  | Сигнал `POLLOUT` | `getsockopt(SO_ERROR) != 0` | Закрити дефектний сокет; видалити з пулу опитування | `RACING_POLL` |
| `RACING_POLL`  | Спливання `Total Timeout`| Жоден сокет не підключився | Закрити всі відкриті сокети; повернути додатку помилку `ETIMEDOUT` | `FAILED` |

## Конфігурація Happy Eyeballs у системних бібліотеках та середовищах виконання

### 1. Бібліотека C libcurl

У бібліотеці `libcurl` алгоритм Happy Eyeballs v2 реалізований на рівні внутрішнього рушія передачі даних і керується низкою стандартних опцій `curl_easy_setopt`.

:::tabs
```c
#include <curl/curl.h>

CURL *curl = curl_easy_init();
if (curl) {
    curl_easy_setopt(curl, CURLOPT_URL, "https://example.com");

    /* Встановлення затримки між спробами Happy Eyeballs (за замовчуванням 200 мс) */
    curl_easy_setopt(curl, CURLOPT_HAPPY_EYEBALLS_TIMEOUT_MS, 250L);

    /* Дозволити використання обох родин адрес (CURL_IPRESOLVE_WHATEVER) */
    curl_easy_setopt(curl, CURLOPT_IPRESOLVE, CURL_IPRESOLVE_WHATEVER);

    /* Загальний таймаут на встановлення TCP-з'єднання */
    curl_easy_setopt(curl, CURLOPT_CONNECTTIMEOUT_MS, 10000L);

    CURLcode res = curl_easy_perform(curl);
    curl_easy_cleanup(curl);
}
```
```cpp
#include <curl/curl.h>
#include <memory>
#include <stdexcept>

struct CurlDeleter {
    void operator()(CURL* handle) const noexcept {
        if (handle) curl_easy_cleanup(handle);
    }
};

void fetch_url(const char* url) {
    std::unique_ptr<CURL, CurlDeleter> curl(curl_easy_init());
    if (!curl) throw std::runtime_error("Не вдалося ініціалізувати curl");

    curl_easy_setopt(curl.get(), CURLOPT_URL, url);
    curl_easy_setopt(curl.get(), CURLOPT_HAPPY_EYEBALLS_TIMEOUT_MS, 250L);
    curl_easy_setopt(curl.get(), CURLOPT_IPRESOLVE, CURL_IPRESOLVE_WHATEVER);
    curl_easy_setopt(curl.get(), CURLOPT_CONNECTTIMEOUT_MS, 10000L);

    CURLcode res = curl_easy_perform(curl.get());
    if (res != CURLE_OK) {
        throw std::runtime_error(curl_easy_strerror(res));
    }
}
```
:::

* `CURLOPT_HAPPY_EYEBALLS_TIMEOUT_MS`: Задає тривалість затримки перед запуском спроби для наступної адреси. Встановлення значення `0L` вимикає затримку й змушує curl запускати всі адреси одночасно.
* `CURLOPT_IPRESOLVE`: Визначає режим резолвінгу адрес: `CURL_IPRESOLVE_WHATEVER` (Dual-Stack Happy Eyeballs), `CURL_IPRESOLVE_V4` (лише IPv4), `CURL_IPRESOLVE_V6` (лише IPv6).

### 2. Мова програмування Go (пакет `net`)

У стандартній бібліотеці Go структура `net.Dialer` містить внутрішній механізм паралельного змагання goroutines під час виклику `DialContext`:

```go
package main

import (
	"context"
	"net"
	"net/http"
	"time"
)

func createHappyEyeballsClient() *http.Client {
	dialer := &net.Dialer{
		Timeout:       10 * time.Second, /* Загальний ліміт часу на підключення */
		KeepAlive:     30 * time.Second,
		FallbackDelay: 250 * time.Millisecond, /* Інтервал старту паралельної goroutine */
	}

	transport := &http.Transport{
		DialContext:           dialer.DialContext,
		ForceAttemptHTTP2:     true,
		MaxIdleConns:          100,
		IdleConnTimeout:       90 * time.Second,
		TLSHandshakeTimeout:   10 * time.Second,
		ExpectContinueTimeout: 1 * time.Second,
	}

	return &http.Client{
		Transport: transport,
		Timeout:   15 * time.Second,
	}
}
```

У середовищі Go функція `dialParallel` запускає первинне підключення в окремій goroutine. Якщо через інтервал `FallbackDelay` результат не отримано, запускається друга goroutine для резервної адреси. Результати змагання передаються через спільний канал `chan dialResult`, а контекст goroutine, що програла, скасовується через `context.CancelFunc()`, що спричиняє негайне закриття невдалого сокета.

### 3. Apple Network.framework (macOS, iOS, iPadOS)

Операційні системи Apple мають вбудовану низькорівневу реалізацію Happy Eyeballs v2 безпосередньо в мережевому демоні ядра `networkd`. Розробникам доступний високорівневий API `Network.framework`:

```swift
import Network

let parameters = NWParameters.tcp
// Дозволити автоматичне змагання інтерфейсів та родин адрес
parameters.multipathServiceType = .handover

let endpoint = NWEndpoint.hostPort(host: "example.com", port: 443)
let connection = NWConnection(to: endpoint, using: parameters)

connection.stateUpdateHandler = { state in
    switch state {
    case .ready:
        print("З'єднання встановлено через найшвидший доступний шлях")
    case .failed(let error):
        print("Помилка підключення: \(error)")
    case .waiting(let error):
        print("Очікування відновлення зв'язку: \(error)")
    default:
        break
    }
}

connection.start(queue: .global())
```

Системний стек Apple підтримує розширену версію змагання: якщо пристрій підключений одночасно до Wi-Fi та стільникової мережі Cellular, рушій змагається не лише між родинами адрес IPv6/IPv4, але й між різними фізичними мережевими інтерфейсами, обираючи найшвидший шлях із найменшим RTT.

### 4. Chromium Network Stack (Google Chrome)

У мережевому стеку проекту Chromium клас `net::TransportConnectJob` реалізує розширений варіант Happy Eyeballs:
* `kHappyEyeballsDelayMs`: Базова константа затримки між спробами родин (за замовчуванням 250 мс у сучасних версіях рушія).
* `kMaxConcurrentConnects`: Обмеження на максимальну кількість одночасних з'єднань для одного хоста (зазвичай 4).
* Підтримка **TLS Handshake Racing**: якщо активовано прапорці оптимізації, гонка продовжується крізь криптографічну фазу TLS.

### 5. Envoy Proxy та Nginx у хмарних архітектурах

У хмарних мікросервісних архітектурах Happy Eyeballs застосовується на рівні шлюзів Ingress та сервісних сіток Service Mesh для з'єднань Upstream:

У конфігурації проксі Envoy секція кластера налаштовується таким чином:
```yaml
clusters:
- name: upstream_service
  connect_timeout: 0.25s
  type: STRICT_DNS
  dns_lookup_family: ALL_EXTERNAL
  load_assignment:
    cluster_name: upstream_service
    endpoints:
    - lb_endpoints:
      - endpoint:
          address:
            socket_address:
              address: service.internal.net
              port_value: 443
```
Параметр `dns_lookup_family: ALL_EXTERNAL` змушує Envoy запитувати одночасно A та AAAA записи і застосовувати асинхронне чергування адрес під час балансування запитів.

## Метрики спостережуваності та експорт OpenTelemetry

Для моніторингу ефективності Happy Eyeballs у виробничому середовищі мережеві сервіси експортують такі стандартні лічильники Prometheus:

* `happy_eyeballs_attempts_total{family="ipv6|ipv4"}` — загальна кількість ініційованих спроб підключення.
* `happy_eyeballs_winners_total{family="ipv6|ipv4"}` — кількість з'єднань, що перемогли в гонці.
* `happy_eyeballs_fallback_total` — кількість випадків, коли спрацював таймер 250 мс і було запущено з'єднання IPv4.
* `happy_eyeballs_handshake_duration_seconds` — гістограма часу встановлення з'єднання для кожної родини адрес.

Якщо відношення `happy_eyeballs_winners_total{family="ipv6"}` до загальної кількості спроб падає нижче 80% на Dual-Stack інфраструктурі, це слугує сигналом тривоги для чергових інженерів SRE про виникнення проблем із маршрутизацією IPv6 або помилок у конфігурації фаєрволів.

## Інтеграція з QUIC, HTTP/3 та записами DNS SVCB/HTTPS

З появою транспортного протоколу QUIC (RFC 9000) та протоколу прикладного рівня HTTP/3 архітектура Happy Eyeballs зазнала значного розширення: змагання перейшло від потокових сокетів TCP до датаграмних сокетів UDP та нових форматів записів DNS.

### 1. Змагання з'єднань у протоколі QUIC (UDP Concurrency)
На відміну від TCP, протокол QUIC не використовує тристороннє рукостискання на рівні операційної системи. Створення UDP-сокета є миттєвою локальною операцією, яка не надсилає жодних пакетів у мережу.

У протоколі QUIC алгоритм Happy Eyeballs працює на рівні пакетів `Initial`:
* **Старт спроби:** Клієнт створює неблокуючий сокет UDP, генерує криптографічний пакет QUIC `Initial` (що містить кадр `CRYPTO` з даними TLS 1.3 `ClientHello`) і відправляє його на першу адресу IPv6.
* **Таймер затримки QUIC (100–250 мс):** Якщо за цей час віддалений сервер не повертає пакет `Initial` (що містить `ServerHello` або відповідь `ACK`), рушій відправляє паралельний пакет QUIC `Initial` на резервну адресу IPv4.
* **Визначення переможця:** Перший сокет, що отримує валідний пакет від сервера і розшифровує криптографічні ключі сесії (рівень Handshake або 1-RTT), перемагає в гонці. Усі інші сокети UDP видаляються.

### 2. Записи DNS SVCB та HTTPS (RFC 9460)
Нові типи записів DNS SVCB (Service Binding) та HTTPS дозволяють клієнту отримати всі параметри підключення в єдиній DNS-відповіді:
* Параметр `alpn`: перелік підтримуваних протоколів (наприклад, `h3,h2`).
* Параметри `ipv4hint` та `ipv6hint`: готові списки IP-адрес сервера, що усуває необхідність надсилання окремих запитів A та AAAA.
* Параметр `ech`: конфігурація зашифрованого розширення `Encrypted Client Hello` (ECH) для приховування імені цільового домену від систем інспекції трафіку.

Рушій Happy Eyeballs v2 використовує параметри `ipv6hint` та `ipv4hint` для миттєвого формування черги чергування, повністю минаючи фазу очікування `Resolution Delay`.

## Системні параметри ядра Linux та взаємодія з сокетами

Поведінка алгоритму Happy Eyeballs тісно пов'язана з низькорівневими налаштуваннями мережевого стека операційної системи.

### Параметри sysctl підсистеми TCP/IP у Linux

* `net.ipv4.tcp_syn_retries = 6`: Визначає кількість повторних спроб відправлення пакета TCP SYN перед поверненням системної помилки `ETIMEDOUT`. При значенні за замовчуванням `6` загальний час очікування становить приблизно `1 + 2 + 4 + 8 + 16 + 32 = 63` секунди. Саме через цей параметр наївний послідовний перебір адрес паралізував роботу браузерів.
* `net.ipv6.bindv6only = 0`: Регулює поведінку сокетів IPv6 (`AF_INET6`). При значенні `0` сокет IPv6 може приймати з'єднання як по IPv6, так і по IPv4 (через IPv4-Mapped IPv6 адреси виду `::ffff:192.0.2.1`). При значенні `1` сокети IPv6 працюють суворо ізольовано.
* `net.ipv4.tcp_metrics_min_rtt = 0`: Керує кешуванням метрик TCP (RTT, вариація RTT, поріг повільного старту CWND) у внутрішній таблиці ядра `tcp_metrics`.

Для перегляду та очищення накопичених ядром метрик маршрутизації застосовують утиліту `ip`:
```bash
# Перегляд кешованих параметрів з'єднань до віддалених префіксів
ip tcp_metrics show

# Примусове скидання системного кешу при діагностиці збоїв зв'язку
ip tcp_metrics flush all
```

## Трасування гонки з'єднань у реальному часі через eBPF

Найбільш точним методом діагностики Happy Eyeballs у ядрі Linux є динамічне трасування системних викликів та функцій протокольного стека за допомогою інструменту `bpftrace`.

Наведений нижче скрипт фіксує моменти виклику функцій `tcp_v4_connect` та `tcp_v6_connect`, вимірює інтервал між спробами та фіксує генерацію пакетів скидання `TCP RST` для сокетів, що програли в гонці:

```text
#!/usr/bin/env bpftrace

kprobe:tcp_v6_connect
{
    @start[tid] = nsecs;
    printf("[t = %u ms] [PID %d: %s] Старт спроби 1: TCP SYN [IPv6]\n", 
           elapsed / 1000000, pid, comm);
}

kprobe:tcp_v4_connect
{
    printf("[t = %u ms] [PID %d: %s] Старт спроби 2: TCP SYN [IPv4] (Happy Eyeballs Fallback)\n", 
           elapsed / 1000000, pid, comm);
}

kprobe:tcp_send_active_reset
{
    printf("[t = %u ms] [PID %d: %s] Генерація TCP RST: скасування сокета, що програв гонку\n", 
           elapsed / 1000000, pid, comm);
}
```

Під час запуску цього скрипту на комп'ютері з дефектним маршрутом IPv6 у терміналі відображається точна послідовність подій:
1. `[t = 120 ms]` — старт `tcp_v6_connect` (спроба 1).
2. `[t = 370 ms]` — рівно через 250 мс стартує `tcp_v4_connect` (спроба 2).
3. `[t = 412 ms]` — через 42 мс надходить SYN-ACK для IPv4, і ядро генерує подію `tcp_send_active_reset` для закриття дескриптора IPv6.

## Діагностика та простеження поведінки Happy Eyeballs

Для верифікації коректності роботи алгоритму на робочих станціях та шлюзах застосовують інструменти мережевого аналізу:

### 1. Фільтри Wireshark для відстеження гонки
Для виявлення паралельних запитів TCP SYN у дампах трафіку `pcap` використовують вираз:
```
(tcp.flags.syn == 1 && tcp.flags.ack == 0) && (ipv6 || ip)
```
Якщо клієнт використовує Happy Eyeballs v2, у журналі пакетів спостерігається відправлення пакета TCP SYN на адресу IPv6 у момент `t = 0`, а через 250 мс — відправлення пакета TCP SYN на адресу IPv4. Після прибуття SYN-ACK від IPv4 на графіку з'являється вихідний пакет TCP RST у напрямку адреси IPv6.

### 2. Профілювання таймінгів за допомогою утиліти curl
Створіть текстовий файл формату `curl-format.txt`:
```
    Час DNS-резолвінгу:    %{time_namelookup} с\n
    Час TCP-з'єднання:     %{time_connect} с\n
    Час TLS-рукостискання: %{time_appconnect} с\n
    Загальний час:         %{time_total} с\n
    Підключено до IP:      %{remote_ip}\n
```
Виконайте тестовий запит:
```bash
curl -w "@curl-format.txt" -o /dev/null -s "https://example.com"
```
Якщо IPv6-маршрут заблоковано, значення `time_connect` становитиме приблизно `0.290` с (250 мс затримки таймера + 40 мс RTT IPv4) замість системного таймауту `21.000` с, що слугує прямим доказом коректного спрацьовування Happy Eyeballs.
