# 📋 Протокол коротких пакетів Iridium SBD: AT-команди, двійковий кадр і коди статусів

Супутниковий протокол Iridium Short Burst Data (SBD) — це двійковий пакетний інтерфейс обміну короткими транзакціями між абонентським трансивером (ISU — *Iridium Subscriber Unit*, моделі 9602, 9603, 9603N) та супутниковою мережею через асинхронний послідовний інтерфейс UART.

## 1. Апаратний інтерфейс та електричні сигнали (Модуль 9603N)

Трансивер Iridium 9603N взаємодіє з хост-мікроконтролером через роз'єм із кроком 0.5 мм (DF18G-20DP-0.4V) за рівнями 3.3 В CMOS:

| Пін | Назва сигналу | Напрямок | Опис функції та електричні вимоги |
|---|---|---|---|
| 1, 2 | `EXT_PWR` | Живлення | Вхід нерегульованого живлення 5.0 В ± 0.2 В або 3.2…5.5 В. Піковий струм 1.5…2.0 А. |
| 3, 4 | `GND` | Живлення | Спільна маса живлення та цифрових сигналів. |
| 5 | `ON_OFF` | Вхід | Апаратне керування живленням: логічна `1` (3.3 В) вмикає модуль, логічний `0` вимикає. |
| 6 | `TXD` | Вхід | Дані від MCU до модема (3.3 В LVCMOS). |
| 7 | `RXD` | Вихід | Дані від модема до MCU (3.3 В LVCMOS). |
| 8 | `RTS` | Вхід | Апаратний контроль потоку (Ready To Send): `0` = MCU готовий приймати. |
| 9 | `CTS` | Вихід | Апаратний контроль потоку (Clear To Send): `0` = модем готовий приймати дані. |
| 10 | `DTR` | Вхід | Data Terminal Ready: переведення модуля у режим низького енергоспоживання. |
| 11 | `DCD` | Вихід | Data Carrier Detect: індикація наявності встановленої супутникової сесії. |
| 12 | `RI` (Ring Indicator)| Вихід | Індикатор виклику: переходить у `0` при надходженні вхідного пакета через Ring Alert. |
| 13 | `NET_AVAIL` | Вихід | Network Available: логічна `1` — модуль бачить сигнал сузір'я з рівнем `CSQ ≥ 1`. |

Параметри UART за замовчуванням: `19200 бод`, `8 бітів даних`, `без паритету (None)`, `1 стоп-біт`, апаратне керування потоком `RTS/CTS`.

## 2. Формат двійкових фреймів обміну

Для завантаження вихідних даних (MO — *Mobile Originated*) у внутрішній буфер трансивера та зчитування вхідних даних (MT — *Mobile Terminated*) застосовується кадрування з 16-бітною контрольною сумою.

### 2.1. Завантаження вихідного повідомлення: `AT+SBDWB`

Процедура завантаження складається з двох етапів:

1. MCU надсилає команду з вказанням довжини корисного навантаження:
   `AT+SBDWB=<довжина_в_байтах>\r` (наприклад, `AT+SBDWB=42\r`).
2. Модем відповідає рядком: `READY\r\n`.
3. MCU передає сирий двійковий потік довжиною `довжина + 4` байти у форматі:

```
+-------------------+-----------------------------------+-------------------+
| Довжина (2 байти) | Корисне навантаження (N байтів)   | Чексума (2 байти) |
| Big-Endian MSB..LSB| Двійкові дані пакету (1..340 байт)| 16-біт сума (MSB) |
+-------------------+-----------------------------------+-------------------+
```

Контрольна сума є простим 16-бітним арифметичним сумуванням усіх байтів поля корисного навантаження (без переповнення):

```
Checksum = (∑ Payload[i]) mod 65536    [для i від 0 до N-1]
```

4. Модем повертає двійковий код результату (один символ + `\r\n`):
   - `0\r\n` — Успіх: буфер MO успішно заповнено.
   - `1\r\n` — Помилка тайм-ауту передачі даних (MCU передавав дані повільніше ніж за 60 секунд).
   - `2\r\n` — Помилка контрольної суми (обчислена чексума не збіглася з переданою).
   - `3\r\n` — Неприпустимий розмір повідомлення (перевищено ліміт 340 байтів для 9603N).

### 2.2. Зчитування вхідного повідомлення: `AT+SBDRB`

1. MCU надсилає команду: `AT+SBDRB\r`.
2. Модем повертає потік без текстового заголовка:

```
+-------------------+-----------------------------------+-------------------+
| Довжина (2 байти) | Прийняте навантаження (M байтів)  | Чексума (2 байти) |
| Big-Endian MSB..LSB| Двійкові дані (1..270 байтів)     | 16-біт сума (MSB) |
+-------------------+-----------------------------------+-------------------+
```

3. Після передачі останнього байта чексуми модем додає завершальний текстовий рядок `OK\r\n`.

## 3. Повний набір AT-команд керування підсистемою SBD

| AT-команда | Параметри | Очікувана відповідь | Призначення та інженерна поведінка |
|---|---|---|---|
| `AT` | немає | `OK` | Базова перевірка працездатності порту UART та синхронізації швидкості. |
| `AT+CSQ` | немає | `+CSQ:<рівень>` | Запит рівня сигналу антени. Повертає значення від `0` (немає сигналу) до `5` (максимальний сигнал `SNR > 15 дБ`). |
| `AT+CGSN` | немає | `<IMEI>\r\nOK` | Запит 15-значного серійного номера IMEI модуля для авторизації на сервері. |
| `AT+CGMR` | немає | `<ревізія>\r\nOK` | Запит версії вбудованого програмного забезпечення (Firmware Revision). |
| `AT+SBDWT` | `=<текст>` | `OK` або `ERROR` | Запис текстового повідомлення у вихідний буфер MO (корисно для простих налагоджувальних маяків). |
| `AT+SBDRT` | немає | `<текст>\r\nOK` | Зчитування текстового повідомлення з вхідного буфера MT. |
| `AT+SBDWB` | `=<довжина>` | `READY` | Ініціація двійкового завантаження в буфер MO із контролем суми. |
| `AT+SBDRB` | немає | `<двійкові дані>` | Вичитування вмісту двійкового буфера MT. |
| `AT+SBDIX` | немає | `+SBDIX: <mo_st>, <momsn>, <mt_st>, <mtmsn>, <mt_len>, <mt_queued>` | **Головна команда**: ініціація розширеної радіосесії обміну з супутником. |
| `AT+SBDSX` | немає | `+SBDSX: <mo_flag>, <momsn>, <mt_flag>, <mtmsn>, <ra_flag>, <msg_waiting>` | Локальний стан буферів модема без виходу в ефір (не витрачає енергію батареї). |
| `AT+SBDD` | `=<тип>` | `0` (OK) | Очищення внутрішніх буферів модема: `0` — очистити MO, `1` — очистити MT, `2` — очистити обидва буфери. |
| `AT+SBDREG` | немає | `+SBDREG:<стан>` | Примусова реєстрація у локальній соті супутника. Дозволяє шлюзу дізнатися поточне розташування термінала для доставки вхідних викликів Ring Alert. |
| `AT+SBDMTA` | `=<режим>` | `OK` | Керування індикацією виклику Ring Alert: `0` — вимкнено, `1` — увімкнено (модем генерує рядок `+SBDRING` та смикає пін `RI` при появі вхідного пакету). |
| `AT&K0` / `AT&K3` | немає | `OK` | Керування апаратним контролем потоку: `&K0` — вимкнено, `&K3` — увімкнено апаратні лінії RTS/CTS (рекомендовано). |
| `AT&W0` | немає | `OK` | Збереження поточної конфігурації модема у постійну енергонезалежну пам'ять (NVRAM). |

## 4. Структура відповіді розширеної сесії `+SBDIX`

Команда `AT+SBDIX` надсилає накопичений буфер MO через супутник у наземний шлюз Iridium Gateway та одночасно перевіряє наявність вхідної черги MT для цього модуля.

Формат відповіді:
```
+SBDIX: <MO status>, <MOMSN>, <MT status>, <MTMSN>, <MT length>, <MT queued>
```

### 4.1. Коди стану вихідного повідомлення (`<MO status>`)

| Значення `<MO status>` | Класифікація | Трактування інженерного драйвера |
|---|---|---|
| `0` | Успіх | Пакет успішно передано з модуля на супутник та підтверджено шлюзом. |
| `1` | Успіх | Пакет передано, але черга повідомлень на шлюзі занадто велика. |
| `2` | Успіх | Пакет передано, але шлюз скинув сесію за тайм-аутом. |
| `3..4` | Успіх | Пакет передано на супутник, але підтвердження від шлюзу затрималося. |
| `32` | Помилка радіоканалу | Не вдалося встановити радіозв'язок із супутником (немає прямої видимості або низький сигнал). Повторити спробу через інтервал бекофу. |
| `33` | Тайм-аут зв'язку | Зв'язок обірвався під час передачі пакета (супутник зайшов за горизонт). |
| `34` | Системна помилка | Помилка протоколу радіодоступу. Необхідно перереєструвати модуль (`AT+SBDREG`). |
| `35` | Блокування каналу | Трансивер заблокований геофенсингом або відсутністю ліцензії на передачу на даній території. |
| `36` | Помилка черги | Черга трансивера переповнена або заблокована попередньою незавершеною транзакцією. |

### 4.2. Коди стану вхідного повідомлення (`<MT status>`)

| Значення `<MT status>` | Опис результату прийому |
|---|---|
| `0` | У черзі шлюзу не було вхідних повідомлень для цього пристрою. |
| `1` | Вхідне повідомлення успішно прийнято з супутника та збережено в буфері MT модема. Розмір у байтах вказано в полі `<MT length>`. |
| `2` | Помилка передачі вхідного повідомлення через збій контрольної суми на радіолінії. |

Поле `<MT queued>` показує кількість повідомлень, які все ще очікують на доставку в черзі Iridium Gateway. Якщо `<MT queued> > 0`, драйвер повинен повторно викликати `AT+SBDIX` з порожнім MO-буфером для витягування наступного пакету з черги.

## 5. Механізм доставки вхідних викликів (SBD Ring Alert)

Оскільки супутниковий модем IoT більшу частину часу спить для економії батареї, наземний сервер не може надіслати йому дані в довільний момент часу. Для доставки вхідних пакетів (MT) реалізовано механізм Ring Alert:

1. **Реєстрація модуля:** Термінал періодично надсилає команду `AT+SBDREG`, фіксуючи свій поточний супутниковий бім (соту) у реєстрі шлюзу Iridium.
2. **Трансляція пейджингового сигналу:** Коли сервер відправляє вхідний пакет, шлюз передає широкомовне пейджингове сповіщення на спеціальній частоті Ring Channel (1626.27 МГц) через відповідний супутник.
3. **Реакція трансивера:** Якщо модем перебуває в режимі прийому маяків (`AT+SBDMTA=1`), він фіксує виклик, переводить апаратну лінію `RI` (Ring Indicator) у низький рівень (імпульс 100 мс) та надсилає в порт UART повідомлення `+SBDRING`.
4. **Завершення транзакції:** Мікроконтролер, отримавши переривання від піна `RI`, надсилає команду `AT+SBDIX` (із порожнім буфером MO), після чого супутник скидає накопичений MT-пакет у приймальний буфер модема.

## 6. Серверний мережевий протокол Iridium DirectIP

На боці хмарного сервера прийом та відправка повідомлень SBD відбувається через TCP-сокет (порт за замовчуванням `10800`), який обслуговує Iridium Gateway Subsystem (GSS).

Кожен DirectIP-пакет складається з заголовка та набору інформаційних елементів (IE — *Information Elements*):

```
+--------------------------+------------------------------------------------+
| Загальна довжина (2B MSB)| Набір контейнерів IE: [IEI (1B)] [Len (2B)] [Data] |
+--------------------------+------------------------------------------------+
```

### Основні типи інформаційних елементів (IEI):

1. **MO Header (IEI = 0x01, довжина 28 байтів):**
   - `CDR Reference` (4 байти): унікальний ідентифікатор транзакції в білінговій системі;
   - `IMEI` (15 байтів ASCII): ідентифікатор трансивера 9603;
   - `Session Status` (1 байт): код результату доставки шлюзом (0 = успіх);
   - `MOMSN` (2 байти Big-Endian): порядковий номер пакета пристрою;
   - `MTMSN` (2 байти Big-Endian): порядковий номер відповідного MT-пакета;
   - `Time of Session` (4 байти UNIX timestamp): час фіксації пакета шлюзом.
2. **MO Payload (IEI = 0x02, довжина змінна 1..340 байтів):**
   - Двійкові дані, передані пристроєм через `AT+SBDWB`.
3. **MO Location Information (IEI = 0x03, довжина 11 байтів):**
   - Оцінка географічних координат пристрою за допомогою доплерівської тріангуляції сузір'я (широта, довгота та радіус похибки CEP у кілометрах, корисний бекап на випадок відмови GNSS-приймача пристрою).
4. **MT Header (IEI = 0x41, довжина 21 байт):**
   - Використовується сервером для постановки пакета у вхідну чергу термінала за його IMEI.
5. **MT Confirmation (IEI = 0x44, довжина 25 байтів):**
   - Квитанція підтвердження прийому вхідного повідомлення абонентом із зазначенням статусу успіху транзакції.

## 7. Алгоритм викачування черги вхідних повідомлень (MT Queue Draining)

Якщо сервер відправив терміналу кілька послідовних команд (наприклад, оновлення конфігурації або зміну періоду відправки), шлюз накопичує їх у черзі FIFO. За одну сесію `AT+SBDIX` супутник передає лише одне MT-повідомлення.

Для повного очищення черги драйвер реалізує наступну логіку:

```
[Початок сесії] ──► AT+SBDIX ──► Відповідь: +SBDIX: 0, 102, 1, 45, 32, 2
                                                         │            │
                                                (Прийнято 32 байти)   (У черзі ще 2 пакети)
                                                         │
                                                         ▼
                                            Зчитування: AT+SBDRB
                                                         │
                                                         ▼
                                            Очищення MO: AT+SBDD0
                                                         │
                                                         ▼
                                            Повторна сесія: AT+SBDIX
                                                         │
                                                         ▼
                                            Відповідь: +SBDIX: 0, 103, 1, 46, 18, 1
                                                         │
                                                         ▼
                                            (Повторювати, доки MT queued != 0)
```

Такий підхід запобігає застряганню критичних команд керування у черзі шлюзу Iridium на тривалий час.

## 8. Розширені коди помилок та діагностика апаратного стану

При виникненні апаратних проблем модем повертає стандартні коди розширених помилок `+CME ERROR:<код>`:

| Код `+CME ERROR` | Опис несправності | Причина виникнення та рекомендація щодо відновлення |
|---|---|---|
| `50` | Incompatible state | Модем зайнятий внутрішнім процесом (синтезатор частоти калібрується або триває реєстрація). Зачекати 1 секунду та повторити запит. |
| `51` | Buffer overflow | Довжина введеного рядка AT-команди перевищила розмір внутрішнього буфера UART (понад 256 символів). |
| `52` | Hardware failure | Апаратна несправність внутрішньої шини або флеш-пам'яті трансивера. Вимагає апаратного перезапуску лінією `ON_OFF`. |
| `53` | RF component disabled | Радіочастотний тракт вимкнено через перегрів або спрацювання захисту за напругою (напруга нижче 3.0 В). |
