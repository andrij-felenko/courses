# 📋 Довідник інкапсуляції, накладних витрат тунелів та конфігурації MTU/MSS

Цей довідник містить детальні технічні специфікації, побайтові розрахунки накладних витрат протоколів канального, мережевого, транспортного рівнів та оверлейних мереж, повну матрицю узгодження MTU і TCP MSS для стеків IPv4 та IPv6, алгоритми обчислення криптографічного паддінгу, а також верифіковані інструкції з конфігурації інтерфейсів і правил MSS Clamping на мережевих операційних системах Linux, Cisco IOS/IOS-XE, Juniper Junos та MikroTik RouterOS.

### 1. Побайтова анатомія заголовків та накладних витрат інкапсуляції

Кожен рівень мережевої інкапсуляції додає власні службові заголовки, які відбирають корисний простір усередині фіксованого кадру канального рівня (L2 Frame). Якщо сумарний розмір службових заголовків разом із даними перевищує ліміт вихідного інтерфейсу, пакет або підлягає примусовій фрагментації, або відкидається мережевим обладнанням.

```
Загальна структура кадру на фізичному носії:
[ Преамбула (7 Б) + SFD (1 Б) ]
  └── [ Заголовок L2 (14 Б) + Теги 802.1Q / QinQ / MPLS (0–12 Б) ]
        └── [ Зовнішній заголовок тунелю (Outer IP + L4 + Оверлей) ]
              └── [ Внутрішній IP-пакет (Inner IP + L4 + Дані) ]
  └── [ Контрольна сума FCS / CRC-32 (4 Б) ]
[ Міжпакетний інтервал IFG (12 байт-часів) ]
```

#### 1.1. Канальний рівень, тегування VLAN та комутація міток MPLS

Базовий кадр Ethernet II (DIX) визначає стандартну структуру заголовка канального рівня:
* **Заголовок Ethernet II:** 14 байтів (6 байтів `Destination MAC` + 6 байтів `Source MAC` + 2 байти `EtherType`).
* **Контрольна послідовність кадру (FCS):** 4 байти полінома `CRC-32`.
* **Сумарний базовий L2 оверхед:** **18 байтів** (без урахування преамбули та IFG). За максимального розміру корисного навантаження 1500 байтів повний кадр L2 становить 1518 байтів.

При проходженні через корпоративні та провайдерські магістралі до кадру додаються додаткові теги:
* **IEEE 802.1Q (VLAN Tag):** додає **4 байти** між MAC-адресою джерела та полем EtherType. Складається з поля `TPID` (2 байти, значення `0x8100`) та поля `TCI` (2 байти, що містить 3 біти пріоритету `PCP`, 1 біт `DEI` та 12 бітів ідентифікатора віртуальної мережі `VLAN ID`). Розмір повного L2-кадру зростає до 1522 байтів.
* **IEEE 802.1ad (QinQ / Provider Bridging):** додає два послідовні 4-байтові теги — зовнішній службовий тег провайдера (`S-Tag`, TPID `0x88A8`) та внутрішній тег клієнта (`C-Tag`, TPID `0x8100`). Сумарний оверхед тегування становить **8 байтів** (повний L2-кадр — 1526 байтів).
* **IEEE 802.1ah (Provider Backbone Bridges / Mac-in-Mac):** додає повний зовнішній заголовок Ethernet (14 Б) та службовий тег сервісу I-TAG (6 Б) — сумарно **24 байти** оверхеду канального рівня.
* **MPLS (Multiprotocol Label Switching, RFC 3032):** кожна мітка MPLS займає рівно **4 байти** (32 біти): 20 бітів значення мітки (`Label Value`), 3 біти класу трафіку (`Traffic Class / EXP`), 1 біт позначки дна стека (`Bottom of Stack, S`) та 8 бітів часу життя (`TTL`). У типових схемах операторів зв'язку (L3VPN або MPLS Traffic Engineering) використовується стек із 2–3 міток (транспортна мітка LDP/RSVP-TE + сервісна мітка VPN), що створює оверхед у **8–12 байтів**.

#### 1.2. Протоколи тунелювання Point-to-Point, GRE та VPN

* **PPPoE (Point-to-Point Protocol over Ethernet, RFC 2516):**
  Використовується широкосмуговими інтернет-провайдерами (FTTH, ADSL, GPON) для автентифікації та білінгу користувачів.
  * Заголовок PPPoE: 6 байтів (`Version` 4 біти, `Type` 4 біти, `Code` 8 бітів, `Session ID` 16 бітів, `Payload Length` 16 бітів).
  * Ідентифікатор протоколу PPP: 2 байти (`0x0021` для IPv4, `0x0057` для IPv6).
  * **Сумарний оверхед:** **8 байтів**.
  * **Ефективний IP MTU:** `1500 - 8 = 1492` байти.
  * **Ефективний TCP MSS:** `1492 - 40 = 1452` байти (IPv4) або `1492 - 60 = 1432` байти (IPv6).

* **GRE (Generic Routing Encapsulation, RFC 2784 / RFC 2890):**
  Універсальний протокол інкапсуляції довільних мережевих протоколів усередину IP-пакетів.
  * Зовнішній заголовок IPv4: 20 байтів (або 40 байтів для зовнішнього IPv6).
  * Базовий заголовок GRE: 4 байти (16 бітів прапорців і версії + 16 бітів типу протоколу `Protocol Type`, наприклад `0x0800` для внутрішнього IPv4).
  * Опційні поля GRE (RFC 2890): контрольна сума `Checksum` (+2 Б + 2 Б резерву), ключ автентифікації `Key` (+4 Б), лічильник послідовності `Sequence Number` (+4 Б).
  * **Сумарний оверхед (базовий GRE над IPv4):** `20 + 4 = 24 байти`. Ефективний `IP MTU = 1476` байтів, `TCP MSS = 1436` байтів.
  * **Сумарний оверхед (базовий GRE над IPv6):** `40 + 4 = 44 байти`. Ефективний `IP MTU = 1456` байтів, `TCP MSS = 1416` байтів.

* **IPsec ESP в тунельному режимі (Encapsulating Security Payload, RFC 4303):**
  Шифрує весь оригінальний IP-пакет (разом із внутрішнім заголовком) і додає криптографічні поля автентифікації.
  * Зовнішній IP-заголовок: 20 байтів (IPv4) або 40 байтів (IPv6).
  * Опційний заголовок UDP (для механізму NAT-Traversal / NAT-T, RFC 3948): 8 байтів (порт `4500`).
  * Заголовок ESP: 8 байтів (4 байти `Security Parameters Index, SPI` + 4 байти `Sequence Number`).
  * Вектор ініціалізації (IV): 8 байтів (для шифрів CBC) або 16 байтів (для сучасних AEAD-шифрів AES-GCM / ChaCha20-Poly1305).
  * Вирівнювальний паддінг (ESP Padding): від 0 до 15 байтів (для блокових шифрів вирівнює зашифровані дані до кратності 16 байтів; розраховується за формулою `pad_len = (16 - (payload_len + 2) % 16) % 16`).
  * Трейлер ESP: 2 байти (1 байт `Pad Length` + 1 байт `Next Header`).
  * Автентифікаційний тег / перевірочний код (ICV / Integrity Check Value): 12 байтів (HMAC-SHA1-96), 16 байтів (AES-GCM-128/256, HMAC-SHA256-128) або 32 байти (HMAC-SHA256-256).
  * **Сумарний розрахунковий оверхед (IPv4 + NAT-T + AES-256-GCM):** `20 + 8 (UDP) + 8 (ESP) + 16 (IV) + 2 (Trailer) + 16 (ICV) = 70 байтів` (без врахування паддінгу).
  * **Рекомендований робочий профіль IPsec MTU:** **1420–1440 байтів**, `TCP MSS = 1380–1400` байтів.

* **WireGuard (Сучасний VPN на базі протоколу Noise та криптографії NoiseIK):**
  * Зовнішній IP-заголовок: 20 байтів (IPv4) або 40 байтів (IPv6).
  * Зовнішній UDP-заголовок: 8 байтів.
  * Заголовок пакета даних WireGuard: 16 байтів (1 байт `Type = 0x04` + 3 байти індексу отримувача `Receiver Index` + 8 байтів лічильника `Counter` + 4 байти вирівнювання).
  * Автентифікаційний тег Poly1305 (AEAD ChaCha20-Poly1305): 16 байтів.
  * **Сумарний оверхед над IPv4:** `20 + 8 + 16 + 16 = 60 байтів`.
  * **Сумарний оверхед над IPv6:** `40 + 8 + 16 + 16 = 80 байтів`.
  * **Стандартний інтерфейсний MTU:** WireGuard за замовчуванням встановлює `MTU = 1420` байтів (`1500 - 80`), забезпечуючи безперебійну роботу як через IPv4, так і через IPv6-андерлей без ризику фрагментації.

#### 1.3. Оверлейні протоколи ЦОД: VXLAN, VXLAN-GPE та GENEVE

У сучасних хмарних дата-центрах та SDN-фабриках (Software-Defined Networking) віртуальні машини та контейнери спілкуються через ізольовані віртуальні L2/L3-мережі, інкапсульовані в пакети фізичної IP-мережі (Underlay).

* **VXLAN (Virtual Extensible LAN, RFC 7348):**
  Інкапсулює повний оригінальний кадр Ethernet (починаючи з внутрішнього MAC отримувача) у датаграму UDP.
  * Зовнішній заголовок Ethernet (Underlay L2): 14 байтів.
  * Зовнішній IP-заголовок (Underlay L3): 20 байтів (IPv4) або 40 байтів (IPv6).
  * Зовнішній UDP-заголовок: 8 байтів (стандартний порт IANA `4789`).
  * Заголовок VXLAN: 8 байтів (8 бітів прапорців [I-flag = 1] + 24 біти резерву + 24 біти ідентифікатора віртуальної мережі `VNI` + 8 бітів резерву).
  * **Сумарний оверхед інкапсуляції (L2 + L3 + UDP + VXLAN):** рівно **50 байтів** (над IPv4) або **70 байтів** (над IPv6).
  * *Вимога до фізичної мережі (Underlay Fabric):* щоб віртуальні машини могли прозоро передавати стандартні кадри розміром 1514 байтів без фрагментації, усі фізичні порти комутаторів Spine та Leaf, а також мережеві карти гіпервізорів повинні бути налаштовані на фізичний `MTU >= 1550` байтів (зазвичай у ЦОД одразу встановлюють `MTU = 9000` або `9216`).

* **VXLAN-GPE (Generic Protocol Extension, RFC 8926 / IETF Draft):**
  Розширення VXLAN, що дозволяє інкапсулювати не лише L2-кадри Ethernet, а й чисті L3 IP-пакети, NSH (Network Service Header) та MPLS без внутрішнього заголовка Ethernet. Використовує порт UDP `4790` та 8-байтовий заголовок із полем `Next Protocol` (1 байт). Оверхед становить **50 байтів** (над IPv4).

* **GENEVE (Generic Network Virtualization Encapsulation, RFC 8926):**
  Сучасний стандарт оверлею, прийнятий IETF для заміни VXLAN та NVGRE у середовищах VMware NSX-T, Open Virtual Network (OVN) та Red Hat OpenShift.
  * Зовнішній Ethernet: 14 байтів.
  * Зовнішній IP: 20 байтів (IPv4) або 40 байтів (IPv6).
  * Зовнішній UDP: 8 байтів (порт IANA `6081`).
  * Базовий заголовок GENEVE: 8 байтів (`Ver`, `Option Length`, `OAM`, `Critical Bit`, `Protocol Type`, `VNI`).
  * Опції змінної довжини TLV (Type-Length-Value): `4 × N` байтів (використовуються для передачі контексту безпеки, телеметрії та ідентифікаторів маршрутизації SDN).
  * **Сумарний оверхед:** від **50 байтів** (базовий без опцій) до **100+ байтів** (із повним набором TLV-метаданих).

### 2. Математика криптографічного вирівнювання (IPsec ESP Padding)

При використанні блокових алгоритмів шифрування (наприклад, AES-CBC з розміром блоку 128 бітів / 16 байтів) довжина корисного навантаження перед шифруванням повинна бути кратна розміру блоку `B = 16`. 

Структура даних, що шифруються:
```
[ Внутрішній IP-пакет (L байтів) ] + [ ESP Padding (P байтів) ] + [ Pad Length (1 Б) ] + [ Next Header (1 Б) ]
```

Сумарна довжина цих чотирьох компонентів повинна ділитися на 16 без залишку:
```
(L + P + 2) mod 16 = 0
```

Звідси формула обчислення кількості байтів заповнення `P`:
```
P = (16 - ((L + 2) mod 16)) mod 16
```

#### Приклад покрокового розрахунку:
Нехай оригінальний IPv4-пакет має розмір `L = 1400` байтів.
1. Додаємо 2 службові байти трейлера: `1400 + 2 = 1402` байти.
2. Знаходимо залишок від ділення на 16: `1402 mod 16 = 10` байтів.
3. Обчислюємо необхідну довжину паддінгу: `P = 16 - 10 = 6` байтів.
4. Довжина зашифрованої частини: `1400 + 6 + 2 = 1408` байтів (ділиться на 16: `1408 / 16 = 88` блоків).
5. Повна довжина вихідного IPsec-пакета на дроті (разом із заголовками):
```
Total = 20 (Outer IP) + 8 (ESP Hdr) + 16 (IV) + 1408 (Payload+Pad+Trailer) + 16 (ICV) = 1468 байтів.
```

### 3. Матриця розрахунку параметрів MTU та TCP MSS

Для запобігання фрагментації та виключення проблеми Path MTU Black Hole значення TCP MSS розраховується за формулами:

```
Для IPv4: TCP_MSS = IP_MTU - 20 (IPv4 Header) - 20 (TCP Header) = IP_MTU - 40
Для IPv6: TCP_MSS = IP_MTU - 40 (IPv6 Header) - 20 (TCP Header) = IP_MTU - 60
```

*(Якщо вузли узгодили використання опції тимчасових міток TCP Timestamps [RFC 7323], заголовок TCP розширюється на 12 байтів, і реальний обсяг даних зменшується на відповідну величину).*

| :--- | :--- | :--- | :--- | :--- | :--- |
| **Базовий Ethernet II** | 0 Б (L3) / 18 Б (L2) | **1500** | **1460** | **1440** | Глобальний інтернет за замовчуванням |
| **802.1Q VLAN Trunk** | +4 Б (L2) | **1500** | **1460** | **1440** | Локальні корпоративні мережі (L2 frame 1522 Б) |
| **802.1ad QinQ Provider** | +8 Б (L2) | **1500** | **1460** | **1440** | Провайдерський доступ (Baby Giant L2 frame 1526 Б) |
| **PPPoE (Провайдери)** | 8 Б (PPPoE + PPP) | **1492** | **1452** | **1432** | Абонентський доступ FTTH / GPON / ADSL |

### 4. Механізм інкрементного оновлення контрольної суми TCP (RFC 1624)

Коли маршрутизатор або брандмауер виконує функцію MSS Clamping, він повинен змінити 16-бітове поле опції MSS у заголовку TCP. Якщо просто переписати байти, контрольна сума сегмента `TCP Checksum` стане невалідною, і приймач відкине пакет.

Повний перерахунок контрольної суми над усім TCP-пакетом вимагав би читання всієї пам'яті сегмента, що надмірно навантажує процесор мережевого пристрою. Замість цього апаратні комутатори та драйвери ядра застосовують алгоритм швидкого інкрементного перерахунку контрольної суми відповідно до стандарту **RFC 1624**.

Формула оновлення 16-бітної контрольної суми у зворотному коді:
```
HC' = ~(~HC + ~m + m')
```
де:
* `HC` — стара контрольна сума TCP;
* `HC'` — нова контрольна сума TCP;
* `m` — старе 16-бітне значення опції MSS (наприклад, `1460 = 0x05B4`);
* `m'` — нове 16-бітне значення опції MSS (наприклад, `1380 = 0x0564`).

Ця операція виконується за кілька тактів процесора на рівні бітових інверсій і додавання, дозволяючи обробляти мільйони TCP-рукостискань на секунду без падіння продуктивності шлюзу.

### 5. Програмування правил затискання MSS через eBPF / tc у Linux

Окрім класичних модулів netfilter (`iptables`/`nftables`), у сучасних хмарних інфраструктурах та високонавантажених балансувальниках (наприклад, Cilium чи Katran) затискання MSS виконується безпосередньо в ядрі на рівні підсистеми Traffic Control (tc) або XDP за допомогою програм eBPF.

Програма eBPF перевіряє наявність прапорця SYN, знаходить зміщення опції `TCP_OPT_MSS` (код 2, довжина 4 байти), зчитує поточне значення через функцію прямого доступу до пакету, порівнює з пороговим значенням MTU і виконує прямий інкрементний перезапис із викликом функції `bpf_l4_csum_replace()`. Це усуває накладні витрати на проходження стеків Netfilter і забезпечує лінійну швидкість обробки на швидкостях 100+ Гбіт/с.

Крім того, на рівні eBPF можливе динамічне затискання MSS на основі інформації з BGP-таблиці маршрутизації ядра (FIB Lookup): програма перевіряє вихідний інтерфейс для конкретного префікса і затискає MSS лише для тих маршрутів, де присутні тунелі або вузькі канали зв'язку.

### 6. Конфігурація мережевого обладнання та операційних систем

#### 6.1. Linux (iproute2, iptables, nftables, sysctl)

* **Управління MTU інтерфейсів через утиліту `ip`:**
```bash
# Встановлення стандартного або зменшеного MTU
sudo ip link set dev eth0 mtu 1500
sudo ip link set dev wg0 mtu 1420
sudo ip link set dev vxlan100 mtu 1450

# Увімкнення підтримки Jumbo Frames на серверному інтерфейсі 10G/25G
sudo ip link set dev eth1 mtu 9000
```

* **Налаштування MSS Clamping через `iptables`:**
Правило перехоплює всі прохідні пакети TCP з виставленим прапорцем `SYN` і перезаписує поле опції MSS у заголовку TCP, якщо воно перевищує Path MTU вихідного маршруту:
```bash
# Автоматичний розрахунок і затискання MSS відповідно до PMTU вихідного інтерфейсу
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --clamp-mss-to-pmtu

# Примусове встановлення фіксованого значення MSS для конкретного VPN-інтерфейсу
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -o wg0 -j TCPMSS --set-mss 1380

# Аналогічні правила для транзитного трафіку IPv6
sudo ip6tables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --clamp-mss-to-pmtu
```

* **Налаштування MSS Clamping через `nftables`:**
Утиліта `nftables` виконує затискання MSS на рівні хука `forward`:
```nftables
table inet filter {
    chain forward {
        type filter hook forward priority 0; policy accept;
        
        # Автоматичне затискання MSS для всіх транзитних з'єднань
        tcp flags syn tcp option maxseg size set rt mtu
    }
}
```

* **Тюнінг параметрів ядра Linux (sysctl):**
```ini
# /etc/sysctl.d/99-network-mtu.conf

# Дозвіл генерації ICMP Fragmentation Needed при роботі в режимі маршрутизатора
net.ipv4.ip_no_pmtu_disc = 0

# Увімкнення зондування чорних дір MTU на транспортному рівні (RFC 4821 PLPMTUD)
# 1 = автоматично вмикати зондування при виявленні частих тайм-аутів і повторів
net.ipv4.tcp_mtu_probing = 1

# Базовий початковий розмір MSS для зондування за алгоритмом RFC 4821
net.ipv4.tcp_base_mss = 1024
```

#### 6.3. Juniper Junos OS

* **Фізичний та протокольний рівні MTU:**
У Junos параметр `mtu` на рівні фізичного інтерфейсу (`interfaces ge-0/0/0`) задає розмір L2-кадру (разом із заголовком Ethernet), а `family inet mtu` визначає L3 IP MTU:
```junos
# Встановлення максимального фізичного кадру L2
set interfaces ge-0/0/0 mtu 9216

# Встановлення протокольного IP MTU для юніта
set interfaces ge-0/0/0 unit 0 family inet mtu 1500
set interfaces ge-0/0/0 unit 0 family inet6 mtu 1500

# Конфігурація тунельного інтерфейсу gr-0/0/0
set interfaces gr-0/0/0 unit 0 family inet mtu 1476
set interfaces gr-0/0/0 unit 0 family inet6 mtu 1456
```

* **Автоматичний TCP MSS Clamping на міжмережевих екранах Juniper SRX:**
```junos
# Глобальне затискання MSS для всіх транзитних сесій обробки потоків (Flow Processing)
set security flow tcp-mss all-tcp mss 1380
set security flow tcp-mss ipsec-vpn mss 1360
```

#### 6.4. MikroTik RouterOS (v7)

* **Конфігурація MTU та L2MTU:**
RouterOS розділяє параметри `mtu` (програмний IP MTU) та `l2mtu` (апаратний ліміт буфера комутаційного чипа):
```routeros
# Налаштування апаратного L2MTU комутатора (дозволяє кадри Baby Giant та VLAN без фрагментації)
/interface ethernet set [ find default-name=ether1 ] mtu=1500 l2mtu=1598

# Конфігурація тунелю WireGuard
/interface wireguard add name=wg-corporate listen-port=51820 mtu=1420
```

* **Налаштування MSS Clamping через таблицю Mangle фаєрвола:**
```routeros
# Затискання MSS до Path MTU для всіх транзитних з'єднань за NAT
/ip firewall mangle add chain=forward action=change-mss \
    protocol=tcp tcp-flags=syn tcp-mss=!0-1460 new-mss=clamp-to-pmtu \
    comment="Clamp TCP MSS to Path MTU"

# Фіксоване затискання MSS для PPPoE-клієнтів (MTU 1492 -> MSS 1452)
/ip firewall mangle add chain=forward action=change-mss \
    protocol=tcp tcp-flags=syn out-interface=pppoe-out1 \
    new-mss=1452 passthrough=yes comment="Clamp MSS for PPPoE Uplink"

# Правило для IPv6 трафіку
/ipv6 firewall mangle add chain=forward action=change-mss \
    protocol=tcp tcp-flags=syn new-mss=clamp-to-pmtu \
    comment="Clamp IPv6 MSS"
```

### 7. Діагностика та усунення несправностей MTU/MSS у продакшені

Для швидкої діагностики розривів сесій, зависання завантаження TLS-сертифікатів або аномальних повторних передач TCP використовуються такі практичні інструменти:

1. **Трасування Path MTU через утиліту `tracepath` (Linux):**
```bash
# Зондування маршруту з визначенням вузького місця MTU на кожному хопі
tracepath -n 1.1.1.1
```
*Утиліта надсилає UDP-пакети із забороною фрагментації та фіксує отримані повідомлення `ICMP Type 3 Code 4`, виводячи точний MTU для кожного проміжного маршрутизатора.*

2. **Перевірка кешу Path MTU в ядрі Linux:**
```bash
# Перегляд вивченого значення Path MTU для конкретного маршруту
ip route get 1.1.1.1
```
*У виводі шукайте рядок `pmtu 1420`, який свідчить про те, що ядро тимчасово зменшило MTU для цього хоста на основі отриманого ICMP-повідомлення.*

3. **Аналіз захоплення пакетів через `tcpdump` на предмет фрагментації та MSS:**
```bash
# Захоплення TCP SYN пакетів для перевірки узгодженого MSS
sudo tcpdump -nn -i any "tcp[tcpflags] & (tcp-syn) != 0" -v

# Захоплення фрагментованих IP-пакетів
sudo tcpdump -nn -i any "ip[6:2] & 0x3fff != 0"
```
