# 🧮 Модульна арифметика RFC 1982 та оцінка джиттера за RFC 3550

У цифрових протоколах передачі даних порядкові номери пакетів не можуть зростати нескінченно, оскільки розрядність полів у мережевих заголовках обмежена апаратними регістрами (`8`, `16`, `32` або `64` біти). Коли лічильник досягає максимального значення, наступний крок повертає його до нуля — явище, відоме як переповнення або обертання лічильника (англ. *Wrap-around* або *Rollover*).

Щоб коректно визначати втрати, дублікати та перевпорядкування пакетів в умовах циклічного обертання, мережеві протоколи спираються на **арифметику порядкових номерів** (англ. *Serial Number Arithmetic*, стандартизовану в RFC 1982) та **рекурсивні фільтри оцінки варіації затримки** (RFC 3550).

## 1. Простір номерів за модулем 2^N та аксіоматика RFC 1982

Нехай розрядність лічильника послідовності становить `N` бітів. Множина можливих значень номерів утворює скінченне кільце лишків за модулем `M = 2^N`:

```
S_N = {0, 1, 2, ..., 2^N - 1}
```

Для 8-бітного лічильника (`N = 8`) простір містить `256` чисел (`0..255`), для 16-бітного (`N = 16`) — `65 536` чисел (`0..65535`), для 32-бітного (`N = 32`) — `4 294 967 296` чисел.

Додавання будь-якого цілого числа `k` до поточного номера послідовності `s` визначається як операція за модулем `2^N`:

```
(s + k) mod 2^N
```

### Відношення порядку та горизонт невизначеності

На відміну від звичайної числової прямої `ℝ`, де для будь-яких двох чисел `a ≠ b` завжди виконується або `a < b`, або `b < a`, у кільці `S_N` лінійного порядку не існує: рухаючись за годинниковою стрілкою, після найбільшого числа `2^N - 1` ми знову повертаємося до `0`.

Щоб визначити, який із двох номерів є «новішим» (був відправлений пізніше), стандарт RFC 1982 вводить відношення часткового строгого порядку `s1 < s2` на основі відстані у напрямку зростання.

**Означення (RFC 1982 §3.2).** Номер `s1` вважається меншим за `s2` (`s1 < s2`), якщо і тільки якщо виконується подвійна нерівність:

```
0 < (s2 - s1) mod 2^N < 2^(N-1)
```

Номер `s1` вважається більшим за `s2` (`s1 > s2`), якщо:

```
0 < (s1 - s2) mod 2^N < 2^(N-1)
```

Номери рівні (`s1 = s2`), якщо `s1 = s2`.

```
           s1 < s2 (s2 новіший за s1)
      ◄──────────────────────────────────►
      0                             2^(N-1)                        2^N - 1
──────┬─────────────────────────────┬──────────────────────────────┬─────►
      0                             │                              │
      └─── Допустимий інтервал ─────┘                              │
           випередження (напівпростір) └─── Інтервал запізнення ───┘
                                            (s2 старіший за s1)
```

### Теорема про антиподальну точку та максимальне вікно

Якщо різниця між двома номерами становить рівно половину числового простору:

```
(s2 - s1) mod 2^N = 2^(N-1)
```

то відношення між ними **не визначене**: неможливо встановити, чи `s2` випередив `s1` на `2^(N-1)` кроків уперед, чи `s1` випередив `s2` на `2^(N-1)` кроків уперед, оскільки:

```
(s1 - s2) mod 2^N = (2^N - (s2 - s1)) mod 2^N  [властивість віднімання за модулем]
                  = (2^N - 2^(N-1)) mod 2^N    [підстановка (s2 - s1) = 2^(N-1)]
                  = 2^(N-1)                    [спрощення: 2^N - 2^(N-1) = 2^(N-1)]
```

**Наслідок.** Будь-який мережевий протокол з розміром лічильника `N` бітів може однозначно відстежувати стан черги лише за умови, що максимальна кількість пакетів у польоті (розмір ковзного вікна `W`) строго менша за напівпростір:

```
W_max ≤ 2^(N-1) - 1
```

Якщо в каналі одночасно затримується `2^(N-1)` або більше пакетів, протокол втрачає здатність розрізняти нові пакети від запізнілих дублікатів.

### Теорема про час обертання та максимальний час життя пакета (MSL)

Щоб запобігти помилковому склеюванню старого запізнілого пакета з новим пакетом того самого номера після повного циклу обертання, простір номерів `2^N` повинен задовольняти **критерій часу обертання**.

Нехай передавач транслює пакети з максимальною інтенсивністю `R_pps` пакетів за секунду (англ. *packets per second*). Час повного обороту лічильника послідовності `T_wrap` дорівнює:

```
T_wrap = 2^N / R_pps
```

Якщо в мережі максимальний час життя пакета становить `MSL` (англ. *Maximum Segment Lifetime*, у класичному IP зафіксований як `120` с, у радіолініях телеметрії — від `500` мс до кількох секунд), то для гарантованої відсутності колізій час обертання половини числового простору (напівпростору однозначності) повинен строго перевищувати `MSL`:

```
T_half_wrap = 2^(N-1) / R_pps > MSL
```

Звідси випливає фундаментальне обмеження на мінімальну розрядність лічильника `N` для заданої швидкості передачі та затримки середовища:

```
2^(N-1) > R_pps · MSL
N > 1 + ⌈log₂(R_pps · MSL)⌉
```

**Приклад розрахунку для 100 Гбіт/с магістралі.**
Нехай розмір пакета `L = 1500` байтів (`12 000` бітів), швидкість лінії `100` Гбіт/с (`10¹¹` біт/с), `MSL = 60` с:
```
R_pps = 10¹¹ / 12 000 ≈ 8 333 333 пакетів/с
R_pps · MSL = 8 333 333 · 60 = 500 000 000 пакетів
N > 1 + ⌈log₂(500 000 000)⌉ = 1 + ⌈28.89⌉ = 1 + 29 = 30 бітів
```
Для байтової нумерації TCP (де лічильник рахує кожен байт):
```
R_bps = 100 Гбіт/с = 12.5 ГБ/с = 1.25·10¹⁰ байт/с
T_wrap_32bit = 2³² / 1.25·10¹⁰ ≈ 4 294 967 296 / 1.25·10¹⁰ ≈ 0.344 с
```
Оскільки `0.344` с `<< 120` с (`MSL`), 32-бітний лічильник TCP на швидкості 100 Гбіт/с вичерпується за третину секунди, що математично доводить неминучу необхідність 64-бітних розширень (PAWS / ESN / QUIC).

## 2. Знакова модульна дистанція та додатковий двійковий код

Для практичної програмної реалізації тріажу пакетів на приймачі зручно обчислювати **знакову відстань** `Δ(s_new, s_exp)` між щойно отриманим номером `s_new` та очікуваним номером `s_exp`.

Знакова відстань відображає кільце `S_N` на симетричний інтервал цілих чисел зі знаком:

```
Δ ∈ [-2^(N-1), +2^(N-1) - 1]
```

* Якщо `Δ = 0` — пакет прийшов строго за чергою.
* Якщо `0 < Δ < 2^(N-1)` — пакет є майбутнім (випередження), у потоці виник пропуск із `Δ` пакетів (детекція втрат).
* Якщо `-2^(N-1) < Δ < 0` — пакет є минулим (запізнілим або дублікатом), який відстав від черги на `|Δ|` позицій.

### Тотожність апаратного перетворення типів

В обчислювальній техніці цілі числа зі знаком подаються у **двійковому додатковому коді** (англ. *Two's Complement*). Завдяки математичній структурі додаткового коду, операція віднімання двох беззнакових `N`-бітних чисел із подальшим приведенням результату до знакового `N`-бітного типу **точно дорівнює знаковій модульній відстані**:

```
Δ = (intN_t)((uintN_t)s_new - (uintN_t)s_exp)
```

**Доведення.** Нехай `a, b ∈ {0, 1, ..., 2^N - 1}`. 

1. Беззнакове віднімання в апаратному регістрі процесора виконується за модулем `2^N`:
```
u = (a - b) mod 2^N
```

2. Інтерпретація `N`-бітного числа `u` як знакового числа `s` у додатковому коді визначається функцією:
```
s = u,               якщо 0 ≤ u < 2^(N-1)
s = u - 2^N,         якщо 2^(N-1) ≤ u < 2^N
```

3. Якщо `0 ≤ (a - b) mod 2^N < 2^(N-1)`, то `s = (a - b) mod 2^N > 0`, що строго відповідає випадку `a > b` за RFC 1982.

4. Якщо `2^(N-1) < (a - b) mod 2^N < 2^N`, позначимо `k = 2^N - ((a - b) mod 2^N) = (b - a) mod 2^N`. Оскільки `0 < k < 2^(N-1)`, маємо:
```
s = u - 2^N = -k = -((b - a) mod 2^N) < 0
```
що строго відповідає випадку `a < b` за RFC 1982 зі знаковим значенням `-k`.

Це означає, що перевірка черговості, виявлення переповнення та розрахунок дистанції виконуються за **1 машинний такт** без розгалужень `if / else`.

### Покроковий числовий приклад для 8-бітного лічильника (N = 8)

Розгляньмо роботу 8-бітного лічильника (`uint8_t`), де `M = 256`, а напівпростір `2^(N-1) = 128`.

**Випадок 1: Звичайне зростання без переповнення.**
Очікується `s_exp = 45`, надійшов `s_new = 48`:
```
s_new - s_exp = 48 - 45 = 3
(int8_t)(3) = +3  [0 < +3 < 128: випередження на 3 пакети, втрачено 45, 46, 47]
```

**Випадок 2: Перехід через межу обертання (Wrap-around).**
Очікується `s_exp = 254`, надійшов `s_new = 2`:
```
s_new - s_exp
= (2 - 254) mod 256                  [беззнакове віднімання в uint8_t]
= (-252) mod 256                     [арифметика цілих чисел]
= 4                                  [результат у регістрі uint8_t: 0x04]

(int8_t)(4) = +4                     [приведення до int8_t: 0x04 = +4]
```
Висновок: пакет `2` випереджає `254` на `+4` позиції (пропущено пакети `254`, `255`, `0`, `1`).

**Випадок 3: Запізнілий пакет через межу обертання.**
Очікується `s_exp = 2`, надійшов старий запізнілий пакет `s_new = 255`:
```
s_new - s_exp
= (255 - 2) mod 256                  [беззнакове віднімання в uint8_t]
= 253                                [результат у регістрі uint8_t: 0xFD]

(int8_t)(253)
= 253 - 256                          [інтерпретація int8_t: старший біт 1]
= -3                                 [знаковий результат: -3]
```
Висновок: пакет `255` запізнився рівно на `3` позиції відносно очікуваного `2`.

## 3. Математика метрик втрати пакетів (Packet Loss Rate та RTCP Fraction Lost)

Кількісна оцінка надійності каналу зв'язку базується на двох взаємодоповнювальних величинах: сукупній кількості втрачених пакетів та ковзному коефіцієнті втрат за звітний інтервал.

### Розрахунок розширеного лічильника пакетів (Extended Sequence Number)

При роботі з 16-бітним лічильником послідовності (як у протоколі RTP) переповнення настає кожні `65 536` пакетів. Щоб розрахувати точну кількість відправлених пакетів за тривалий час сесії, приймач підтримує **лічильник повних обертів** `ROC` (англ. *RollOver Counter* або `cycles`):

```
v_extended = ROC · 65536 + s_max
```

Коли новий прийнятий номер `s_new` здійснює обертання відносно попереднього максимуму `s_max` (тобто `s_max > 65536 - W` та `s_new < W`), значення `ROC` збільшується на одиницю:

```
ROC = ROC + 1      [якщо зафіксовано перехід 65535 → 0]
```

Загальна кількість **очікуваних пакетів** (англ. *Expected Packets*, `N_exp`) від початку з'єднання до поточного моменту визначається як різниця між поточним розширеним максимумом та початковим номером першого прийнятого пакета `s_base`:

```
N_exp = (ROC · 65536 + s_max) - s_base + 1
```

Якщо приймач веде суворий облік загальної кількості фізично отриманих унікальних пакетів `N_recv`, то **сукупна кількість втрачених пакетів** `N_lost` становить:

```
N_lost = N_exp - N_recv
```

Якщо через початкові перевпорядкування чи дублікати виникає тимчасова ситуація `N_recv > N_exp`, значення `N_lost` обмежується нулем: `N_lost = max(0, N_exp - N_recv)`.

### Розрахунок інтервального коефіцієнта втрат (Fraction Lost за RFC 3550)

У протоколах моніторингу якості (RTCP, RTMP, SIP) передача абсолютного числа `N_lost` не дає уявлення про поточну динаміку каналу. Тому стандарт RFC 3550 визначає 8-бітну метрику **частки втрат** (англ. *Fraction Lost*, `F_lost`), яка відображає відсоток втрат у фіксованому точковому форматі `Q0.8` (діапазон `0..255`, де `255` відповідає `100%` втрат, а `0` — `0%`).

Нехай за звітний інтервал між двома відправленнями звітів `Receiver Report` очікувана кількість пакетів збільшилася на `ΔN_exp`:

```
ΔN_exp = N_exp(t_current) - N_exp(t_prev)
```

А кількість фактично прийнятих пакетів зросла на `ΔN_recv`:

```
ΔN_recv = N_recv(t_current) - N_recv(t_prev)
```

Інтервальна кількість втрачених пакетів:

```
ΔN_lost = ΔN_exp - ΔN_recv
```

Тоді значення `Fraction Lost` розраховується за формулою:

```
F_lost = 0,                                                    якщо ΔN_exp ≤ 0 або ΔN_lost ≤ 0
F_lost = ⌊(ΔN_lost · 256) / ΔN_exp⌋,                           якщо 0 < ΔN_lost < ΔN_exp
F_lost = 255,                                                  якщо ΔN_lost ≥ ΔN_exp
```

**Приклад розрахунку.** За інтервал моніторингу очікувалося `ΔN_exp = 500` пакетів, а надійшло `ΔN_recv = 475` пакетів.
```
ΔN_lost = 500 - 475 = 25 втрачених пакетів
Дійсний коефіцієнт втрат = 25 / 500 = 0.05 (5.0%)
F_lost = ⌊(25 · 256) / 500⌋ = ⌊6400 / 500⌋ = ⌊12.8⌋ = 12

Відновлений відсоток на стороні сервера:
PLR = 12 / 256 ≈ 0.046875 (4.69%)
```

## 4. Довільна розрядність лічильників та побітові маски

У багатьох спеціалізованих протоколах розрядність лічильника послідовності `N` не збігається зі стандартними машинними типами процесора (8, 16, 32, 64 біти). Наприклад:
* **DTLS Epoch:** 16 бітів, а порядковий номер всередині епохи — **48 бітів**.
* **Кадри систем керування та супутників:** часто використовуються компактні поля на **12 бітів** або **24 біти**.

### Універсальна формула знакового зсуву для N бітів

Для довільної розрядності `N` (де `N ≤ 64`), нехай `MASK_N = 2^N - 1 = (1ULL << N) - 1`, а ваговий коефіцієнт старшого знакового біта становить `SIGN_BIT = 1ULL << (N - 1)`.

Знакова відстань між двома `N`-бітними номерами `s1` та `s2` у середовищі стандартного 64-бітного цілого типу обчислюється у два кроки:

1. **Беззнакова модульна різниця:**
```
diff_unsigned = (s1 - s2) & MASK_N
```

2. **Знакове розширення (Sign Extension):**
Якщо результат перевищує або дорівнює напівпростору `SIGN_BIT` (тобто старший `N`-й біт встановлений в `1`), від результату віднімається повний модуль `2^N`:

```
diff_signed = (diff_unsigned ^ SIGN_BIT) - SIGN_BIT
```

```
Пояснення побітової операції Sign Extension:
1. diff_unsigned ^ SIGN_BIT     [інвертує старший біт числа]
2. ... - SIGN_BIT                [здійснює знакове розширення у верхні 64 розряди]
```

Цей метод дозволяє миттєво обчислювати відстань для будь-якої нестандартної розрядності (`12`, `24`, `48` бітів) без умовних операторів розгалуження.

## 5. Математика розрахунку мережевого джиттера за стандартом RFC 3550

У мультимедійних протоколах (RTP/RTCP) та системах передачі телеметрії критичною метрикою якості зв'язку є не лише відсоток втрат, але й **джиттер** (англ. *jitter* — тремтіння, флуктуація) — варіація часу доставки пакетів мережею.

### Різниця часу транзиту пакетів

Нехай пакет з номером `i` відправляється джерелом у момент часу `S_i` (зафіксований у заголовку пакета відправника) і прибуває на приймач у момент часу `R_i` (зафіксований локальним годинником приймача).

Час перебування пакета `i` в мережі становить:

```
T_transit(i) = R_i - S_i
```

Для двох послідовних пакетів `i` та `j` (де `j` відправлено після `i`) **відносна різниця часу транзиту** `D(i, j)` визначається як:

```
D(i, j) = T_transit(j) - T_transit(i)  [різниця часу транзиту двох пакетів]
        = (R_j - S_j) - (R_i - S_i)    [визначення часу транзиту: T = R - S]
        = (R_j - R_i) - (S_j - S_i)    [перегрупування за годинниками RX та TX]
```

```
               S_i                        S_j
TX ─────────────┬──────────────────────────┬──────────────────────►
                │                          │
                 \                          \
                  \ T_transit(i)             \ T_transit(j)
                   \                          \
                    ▼                          ▼
RX ─────────────────┴──────────────────────────┴──────────────────►
                   R_i                        R_j

   D(i, j) = (R_j - R_i) - (S_j - S_i) = T_transit(j) - T_transit(i)
```

Зауважмо важливу математичну властивість: різниця `D(i, j)` не вимагає синхронізації абсолютних годинників між TX та RX. Якщо годинник приймача зсунутий відносно передавача на сталу величину `ΔT_clock`, вона взаємно знищується при відніманні:

```
(R_j + ΔT_clock - S_j) - (R_i + ΔT_clock - S_i) = (R_j - S_j) - (R_i - S_i)
```

Єдина вимога — щоб генератори частоти годинників TX та RX працювали з однаковою швидкістю ходу (однакова часова шкала).

### Рекурсивний фільтр експоненційного згладжування (EMA)

Середній інтервальний джиттер `J` розраховується для кожного щойно отриманого пакета `j` за рекурсивною формулою першого порядку (RFC 3550 §6.4.1):

```
J(j) = J(j-1) + (|D(j-1, j)| - J(j-1)) / 16
```

Перегрупуємо доданки для виявлення структури **експоненційного ковзного середнього** (англ. *Exponential Moving Average*, EMA):

```
J(j) = J(j-1) · (1 - 1/16) + |D(j-1, j)| · (1/16)
     = (15/16) · J(j-1) + (1/16) · |D(j-1, j)|
```

У загальному вигляді лінійного фільтра першого порядку з коефіцієнтом згладжування `α = 1/16 = 0.0625`:

```
J(j) = (1 - α) · J(j-1) + α · |D(j-1, j)|
```

### Аналіз фільтра в Z-області та ефективне вікно пам'яті

Застосуємо Z-перетворення до рівняння фільтра:

```
J(z) = (1 - α) · z⁻¹ · J(z) + α · |D(z)|
```

Звідси передавальна характеристика фільтра:

```
H(z) = J(z) / |D(z)| = α / (1 - (1 - α) · z⁻¹)
```

Полюс системи розташований у точці `z_p = 1 - α = 15/16 = 0.9375`. Оскільки `|z_p| < 1`, фільтр є строго стійким і діє як **дискретний фільтр низьких частот** (англ. *Low-Pass Filter*), згладжуючи короткочасні сплески затримки й відстежуючи повільні тренди зміни характеристик каналу.

Ефективне вікно пам'яті фільтра (час зменшення ваги в `e` разів) становить:

```
N_eff = 1 / α = 16 пакетів
```

## 6. Математичне моделювання розміру буфера перевпорядкування (Jitter Buffer)

Буфер перевпорядкування затримує передачу пакетів застосунку на фіксований або адаптивний інтервал часу `T_playout_delay`, щоб запізнілі пакети встигли прибути й стати на свої місця в черзі.

### Ймовірнісна модель затримки та відсоток пізніх втрат

Нехай випадкова величина часу транзиту пакета `T_transit` підпорядковується статистичному розподілу із середнім значенням `μ` та середньоквадратичним відхиленням `σ` (у реальних IP-мережах це зазвичай зміщений логнормальний або гамма-розподіл).

Якщо пакет затримується довше, ніж розмір буфера очікування `T_buf`, він оголошується **запізнілим** (англ. *Late Packet*) і викидається, оскільки його часовий слот відтворення вже минув.

Ймовірність втрати пакета через запізнення становить:

```
P_late = P(T_transit > μ + T_buf) = ∫_{μ + T_buf}^{∞} f(t) dt
```

Для нормального наближення розподілу затримки розмір буфера розраховується за правилом квантилів (правило трьох сигм):

```
T_buf ≥ k · σ,      де k = 3 (для P_late ≤ 0.0013, тобто 99.87% надійності)
```

Оскільки за формулою RFC 3550 розрахунковий джиттер `J` пропорційний середньому абсолютному відхиленню `MAD = E[|T_transit - μ|]`, а для нормального розподілу відоме співвідношення `σ = √(π/2) · MAD ≈ 1.253 · J`, оптимальний розмір буфера адаптивно встановлюється як:

```
T_buf_optimal = 3 · √(π/2) · J ≈ 3.76 · J
```

У більшості інженерних систем реального часу розмір адаптивного джиттер-буфера встановлюється в діапазоні:

```
T_buf = clamp(3 · J, T_min, T_max)
```

де `T_min` (наприклад, `20` мс) запобігає спустошенню черги при мікрофлуктуаціях, а `T_max` (наприклад, `200` мс для голосу або `50` мс для автопілота) обмежує максимальну інтерактивну затримку.

## 7. Комплексний числовий розрахунок: втрати, перевпорядкування та джиттер

Простежимо проходження серії з 5 пакетів через радіоканал. Частота дискретизації часових міток становить `1000` Гц (`1` тік = `1` мс). 

Початковий стан: `s_exp = 100`, `J = 0.0` мс.

| Номер пакета `seq` | Час TX `S` (мс) | Час RX `R` (мс) | `Δ = (int8_t)(seq - s_exp)` | Класифікація пакета | `T_transit = R - S` (мс) | `D = ΔT_transit` (мс) | Поточний джиттер `J` (мс) |
|---|---|---|---|---|---|---|---|
| **#100** | `1000` | `1040` | `0` | **In-Order** (вчасно) | `40` | — (базовий) | `0.00` |
| **#102** | `1040` | `1075` | `+2` | **Gap** (пропущено #101) | `35` | `35 - 40 = -5` | `0 + (5 - 0)/16 = 0.31` |
| **#101** | `1020` | `1085` | `-2` | **Reordered** (знайдено #101) | `65` | `65 - 35 = +30` | `0.31 + (30 - 0.31)/16 = 2.17` |
| **#103** | `1060` | `1098` | `0` | **In-Order** (після черги) | `38` | `38 - 65 = -27` | `2.17 + (27 - 2.17)/16 = 3.72` |
| **#103** | `1060` | `1120` | `-1` | **Duplicate** (відкинути) | — | — (ігнорується) | `3.72` |

### Аналіз отриманих результатів

1. Пакет `#100` прибув із затримкою `40` мс, встановивши початкову точку відліку.
2. Пакет `#102` випередив чергу на `+2` позиції: алгоритм зафіксував пропуск пакета `#101` і скоригував очікуваний номер на `103`. Його час транзиту становив `35` мс (`D = -5` мс), джиттер зріс до `0.31` мс.
3. Запізнілий пакет `#101` прибув наступним (`Δ = -2` відносно очікуваного `103`): його затримка склала `65` мс. Різниця затримок `D = +30` мс призвела до різкого стрибка розрахункового джиттера до `2.17` мс.
4. Пакет `#103` повернув потік до штатної затримки `38` мс, а розрахунок згладив попередній сплеск.
5. Повторний прихід пакета `#103` був миттєво відсіяний як дублікат і не вплинув на метрики черги.
