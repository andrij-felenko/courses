# 📋 Специфікація PDU та керівних процедур Link Layer у Bluetooth Low Energy

Цей довідник містить повну структуру бітових полів пакетів канального рівня (Link Layer PDU), параметри ініціалізації з'єднання та формат керівних повідомлень (LL Control PDU) згідно зі специфікацією **Bluetooth Core Specification v5.4**.

---

## 1. Загальна структура пакета канального рівня (LE Uncoded PHY)

На фізичному рівні LE 1M та LE 2M кожен переданий радіокадр складається з чотирьох послідовних сегментів:

```
┌──────────────┬────────────────────────┬─────────────────────────┬────────────────────────┐
│   Preamble   │     Access Address     │     Link Layer PDU      │         CRC-24         │
│ (1 / 2 байт) │        (4 байти)       │     (2 .. 257 байтів)   │       (3 байти)        │
└──────────────┴────────────────────────┴─────────────────────────┴────────────────────────┘
 ◄──────────── Порядок передачі бітів у радіоефір: LSB першим (від молодшого до старшого) ──►
```

### Поля пакета:
* **Preamble (Преамбула):** 1 байт (для 1M PHY) або 2 байти (для 2M PHY). Послідовність чергування бітів `01010101b` (якщо молодший біт Access Address дорівнює `0`) або `10101010b` (якщо молодший біт Access Address дорівнює `1`). Призначена для захоплення несучої частоти та синхронізації ФАПЧ демодулятора приймача.
* **Access Address (Адреса доступу):** 32-бітне поле.
  * Для рекламних каналів (37, 38, 39): фіксоване значення `0x8E89BED6`.
  * Для каналів передачі даних (0–36): унікальне псевдовипадкове 32-бітне число, згенероване ведучим під час створення сесії.
* **Link Layer PDU:** канальний блок даних, що містить 16-бітний заголовок та корисне навантаження.
* **CRC-24:** 24-бітна контрольна сума, обчислена над усім полем PDU за генераторним поліномом `x²⁴ + x¹⁰ + x⁹ + x⁶ + x⁴ + x³ + x + 1`.

## 2. Структура Advertising Channel PDU

Рекламні пакети транслюються на каналах 37, 38 та 39 і мають наступний формат 16-бітного заголовка:

```
 0       3   4   5   6   7   8                              15
┌───────────┬───┬───┬───┬───┬─────────────────────────────────┐
│ PDU Type  │RFU│ChS│TxA│RxA│          Length (8 біт)         │
│  (4 біти) │(1)│(1)│(1)│(1)│            (0 .. 255)           │
└───────────┴───┴───┴───┴───┴─────────────────────────────────┘
```

### Розкладка бітів заголовка Advertising PDU:
* **PDU Type (біти 0..3):** тип рекламного повідомлення.
* **RFU (біт 4):** зарезервовано для майбутнього використання (встановлюється в `0`).
* **ChS (біт 5 — Channel Selection):** вибір алгоритму стрибків (`0` = CSA #1, `1` = CSA #2).
* **TxAdd (біт 6):** тип адреси відправника (`0` = Public, `1` = Random).
* **RxAdd (біт 7):** тип адреси отримувача (`0` = Public, `1` = Random).
* **Length (біти 8..15):** довжина корисного навантаження Payload у байтах (від 6 до 37 байтів для спадщини Bluetooth 4.x, до 255 для Bluetooth 5.0+).

### Основні типи Advertising PDU (PDU Type):

1. **`ADV_IND` (`0000b`, `0x00`) — Connectable Undirected Advertising:**
   Основний тип підключуваного ненаправленого рекламування. Тіло кадру містить 6-байтну адресу рекламодавця `AdvA` та від 0 до 31 байта прикладних рекламних структур `AdvData` (ім'я пристрою, UUID сервісів, дані виробника). Після передачі пристрій переходить у режим прийому на 150 мкс для очікування `SCAN_REQ` або `CONNECT_IND`.

2. **`ADV_DIRECT_IND` (`0001b`, `0x01`) — Connectable Directed Advertising:**
   Підключуване направлене рекламування на конкретний віддалений вузол. Кадр складається лише з 6 байтів адреси рекламодавця `AdvA` та 6 байтів адреси цільового ініціатора `TargetA`. Існує у двох режимах: High Duty Cycle (з інтервалом менше 3.75 мс та тривалістю сеансу до 1.28 с) для надшвидкого відновлення зв'язку та Low Duty Cycle для збереження енергії.

3. **`ADV_NONCONN_IND` (`0010b`, `0x02`) — Non-connectable Undirected Advertising:**
   Непідключувана широкомовна реклама. Використовується автономними маячками (iBeacon, Eddystone) та сенсорами телеметрії. Пристрій передає дані `AdvA` та `AdvData` (до 31 байта), після чого негайно повертається в режим глибокого сну Standby, не відкриваючи приймач.

4. **`SCAN_REQ` (`0011b`, `0x03`) — Scan Request:**
   Запит додаткової інформації від сканера (Observer або Central). Кадр містить 6-байтну адресу сканера `ScanA` та 6-байтну адресу рекламодавця `AdvA`.

5. **`SCAN_RSP` (`0100b`, `0x04`) — Scan Response:**
   Відповідь мовника на отриманий `SCAN_REQ`. Передає додатковий блок даних `ScanRspData` (до 31 байта), дозволяючи транслювати повне текстове ім'я або довгі списки сервісів без підключення.

6. **`CONNECT_IND` (`0101b`, `0x05`) — Connect Indication:**
   Команда ініціалізації з'єднання від Central до Peripheral. Кадр містить адреси `InitA`, `AdvA` та 22 байти критичних параметрів зв'язку `LLData`.

7. **`ADV_SCAN_IND` (`0110b`, `0x06`) — Scannable Undirected Advertising:**
   Сканована непідключувана реклама, яка дозволяє надсилати відповіді `SCAN_RSP`, але відхиляє спроби з'єднання `CONNECT_IND`.

8. **`ADV_EXT_IND` (`0111b`, `0x07`) — Extended Advertising (Bluetooth 5.0+):**
   Розширене рекламування на первинних каналах, що містить покажчик `AuxPtr` на вторинний канал даних (0–36), де транслюється великий блок даних розміром до 254 байтів.

9. **`AUX_ADV_IND` та `AUX_CHAIN_IND` (Вторинні рекламні пакети):**
   Пакети, що передаються на каналах даних 0–36 для транспортування розширеного корисного навантаження. Поле `AdvDataInfo` (ADI) містить 12-бітний ідентифікатор `DID` (*Data ID*) для фільтрації повторів та 4-бітний `SID` (*Set ID*). Поле `AuxPtr` містить 6-бітний номер вторинного каналу, 1-бітний індикатор точності кварцу CA, 1-бітну одиницю зсуву Offset Units (30 мкс або 300 мкс), 13-бітний числовий зсув Aux Offset та 3-бітний покажчик фізичного рівня Aux PHY (1M, 2M, Coded).

## 3. Деталізація кадру CONNECT_IND (Ініціалізація з'єднання)

Кадр `CONNECT_IND` є найважливішим повідомленням канального рівня, оскільки саме він передає веденому всі базові параметри зв'язку та синхронізації:

```
┌─────────────────┬─────────────────┬────────────────────────────────────────────────────────┐
│  InitA (6 байт) │  AdvA (6 байт)  │                  LLData (22 байти)                     │
│  Адреса Central │ Адреса периферії│                Параметри з'єднання                     │
└─────────────────┴─────────────────┴────────────────────────────────────────────────────────┘
```

### Поля структури LLData (22 байти):

```
 0               3   4               7   8               9   10             11
┌───────────────────┬───────────────────┬───────────────────┬───────────────────┐
│     AA (4 байти)  │   CRCInit (3 байти│ WinSize (1 байт)  │ WinOffset (2 байти│
│   Access Address  │   Початковий стан │ Розмір вікна      │ Зсув першого      │
│   для каналів даних│      CRC-24       │  (N · 1.25 мс)    │  Anchor Point     │
├───────────────────┼───────────────────┼───────────────────┼───────────────────┤
│ Interval (2 байти)│ Latency (2 байти) │ Timeout (2 байти) │   ChM (5 байтів)  │
│  connInterval     │  connSlaveLatency │ connSupervision   │  Бітова маска     │
│   (N · 1.25 мс)   │   (0 .. 499)      │    Timeout        │  Channel Map      │
├───────────────────┼───────────────────┴───────────────────┴───────────────────┘
│ Hop (5 біт) / SCA │
│  Інкремент стрибка│
└───────────────────┘
```

### Детальний опис та інваріанти полів LLData:

1. **AA (Access Address, 4 байти):** 
   Унікальний 32-бітний псевдовипадковий ідентифікатор сесії для каналів даних. Повинен мати не менше 6 переходів між бітами 0 і 1 та не містити послідовностей із понад 6 однакових бітів підряд. Не може дорівнювати фіксованій рекламній адресі `0x8E89BED6`.

2. **CRCInit (3 байти):** 
   24-бітне початкове значення для ініціалізації апаратного регістру LFSR контрольної суми CRC-24. Генерується ведучим випадково для кожної нової сесії.

3. **WinSize (1 байт — transmitWindowSize):** 
   Розмір вікна передачі першої події зв'язку, що обчислюється як `WinSize · 1.25 мс`. Допустимі значення від 1 до `connInterval / 1.25 мс`. Визначає діапазон часу, протягом якого ведучий має право надіслати перший пакет після з'єднання.

4. **WinOffset (2 байти — transmitWindowOffset):** 
   Часовий зсув моменту початку першого вікна передачі відносно завершення пакету `CONNECT_IND`. Обчислюється як `WinOffset · 1.25 мс`. Забезпечує веденому необхідний час (від 1.25 мс до кількох мілісекунд) для переналаштування частотних синтезаторів та переходу з режиму реклами в режим з'єднання.

5. **Interval (2 байти — connInterval):** 
   Період між послідовними точками прив'язки `Anchor Points`. Розраховується як `Interval · 1.25 мс`. Діапазон значень: від 6 (7.5 мс) до 3200 (4000.0 мс).

6. **Latency (2 байти — connSlaveLatency):** 
   Кількість подій з'єднання, які ведений має право пропустити за відсутності нових даних. Діапазон значень: від 0 до 499 подій.

7. **Timeout (2 байти — connSupervisionTimeout):** 
   Граничний час відсутності валідного обміну до розірвання зв'язку. Розраховується як `Timeout · 10 мс`. Діапазон значень: від 10 (100 мс) до 3200 (32000 мс).

8. **ChM (Channel Map, 5 байтів):** 
   37-бітна маска дозволених каналів даних (біти 0..36 вказують активність каналів 0–36, біти 37..39 зарезервовані). Має містити щонайменше 2 одиничні біти.

9. **Hop (5 бітів — Hop_Increment):** 
   Випадковий крок лінійної конгруенції для алгоритму стрибків CSA #1 (значення від 5 до 16).

10. **SCA (Sleep Clock Accuracy, 3 біти):** 
    Клас точності низькочастотного кварцового генератора ведучого:
    * `000b` — 251 .. 500 ppm
    * `001b` — 151 .. 250 ppm
    * `010b` — 101 .. 150 ppm
    * `011b` — 76 .. 100 ppm
    * `100b` — 51 .. 75 ppm
    * `101b` — 31 .. 50 ppm
    * `110b` — 21 .. 30 ppm
    * `111b` — 0 .. 20 ppm

## 4. Структура Data Channel PDU

Пакети, що передаються всередині з'єднання на каналах даних 0–36, мають такий формат заголовка:

```
 0     1   2     3    4    5     7   8                              15
┌─────────┬─────┬────┬────┬───────┬─────────────────────────────────┐
│  LLID   │NESN │ SN │ MD │CP/RFU │          Length (8 біт)         │
│ (2 біти)│ (1) │(1) │(1) │  (3)  │            (0 .. 251)           │
└─────────┴─────┴────┴────┴───────┴─────────────────────────────────┘
```

### Семантика полів заголовка Data PDU:

1. **LLID (Logical Link Identifier, біти 0..1):**
   * `01b` (`0x01`): Фрагмент продовження пакету вищого рівня L2CAP або порожній пакет підтвердження (*Empty PDU* при `Length == 0`).
   * `10b` (`0x02`): Початок нового повідомлення вищого рівня L2CAP (Start of L2CAP packet).
   * `11b` (`0x03`): Керуюче повідомлення канального рівня (*LL Control PDU*).

2. **NESN (Next Expected Sequence Number, біт 2):**
   Номер послідовності наступного кадру, який очікує отримати приймач. Зміна цього біта слугує позитивним підтвердженням (ACK) для відправника.

3. **SN (Sequence Number, біт 3):**
   Номер послідовності поточного кадру (0 або 1), який відправник інвертує для кожного нового успішно підтвердженого блоку.

4. **MD (More Data, біт 4):**
   Прапорець наявності додаткових даних для передачі в межах поточного Connection Event. Якщо обидва вузли виставляють `MD = 1`, вони продовжують обмін наступною парою пакетів через інтервал `T_IFS = 150 мкс`.

5. **CP / CTEInfo / RFU (біти 5..7):**
   Поле розширення для пеленгації та визначення кута приходу/відходу сигналу (*Angle of Arrival / Angle of Departure* у Bluetooth 5.1+).

6. **Length (8 бітів):**
   Довжина поля Payload у байтах (від 0 до 251 байта при увімкненому DLE).

## 5. Специфікація керівних процедур LL Control PDU

Коли `LLID == 11b`, корисне навантаження інтерпретується як керівне повідомлення канального рівня. Перший байт визначає код операції **Opcode**:

1. **`LL_CONNECTION_UPDATE_IND` (`0x00`):**
   Оновлює параметри зв'язку (`WinSize`, `WinOffset`, `Interval`, `Latency`, `Timeout`) та передає 16-бітний лічильник моменту активації `Instant`. Нові таймінги синхронно набувають чинності, коли `connEventCounter == Instant`. Значення `Instant` обов'язково встановлюється щонайменше на 6 подій уперед від моменту відправки кадру, щоб компенсувати можливі втрати пакетів у радіоефірі.

2. **`LL_CHANNEL_MAP_IND` (`0x01`):**
   Передає оновлену 37-бітну маску активних частот `usedChannelMap` та момент застосування `Instant`. До настання `Instant` обидва пристрої використовують стару маску каналів, а на кроці `Instant` синхронно перемикаються на нову сітку частот.

3. **`LL_TERMINATE_IND` (`0x02`):**
   Миттєве розірвання з'єднання з передачею коду помилки `ErrorCode` (наприклад, `0x13` — розірвано користувачем, `0x3B` — неприйнятні параметри зв'язку). Після передачі або прийому цього повідомлення вузол негайно повертається в стан Standby.

4. **`LL_ENC_REQ` (`0x03`) та `LL_ENC_RSP` (`0x04`):**
   Запуск 4-етапного узгодження апаратного шифрування AES-128 CCM. Сторони обмінюються 64-бітними випадковими векторами `Rand`, ідентифікатором ключа `EDIV` та векторами диверсифікації ключів `SKDm` / `SKDs` і `IVm` / `IVs`.

5. **`LL_START_ENC_REQ` (`0x05`) та `LL_START_ENC_RSP` (`0x06`):**
   Підтвердження початку передачі зашифрованих пакетів із 32-бітним кодом перевірки автентичності повідомлень MIC (*Message Integrity Check*).

6. **`LL_FEATURE_REQ` (`0x08`) та `LL_FEATURE_RSP` (`0x09`):**
   Обмін 64-бітними масками підтримуваних апаратних можливостей контролера. Кожен біт маски `FeatureSet` відповідає за окрему опцію стандарту:
   * Біт 0: `LE Encryption` (підтримка AES-128 CCM).
   * Біт 1: `Connection Parameters Request Procedure` (запит зміни таймінгів з боку Slave).
   * Біт 5: `LE Data Packet Length Extension` (DLE, підтримка пакетів до 251 байта).
   * Біт 6: `LL Privacy` (апаратне розпізнавання RPA-адрес за допомогою AES-128 IRK).
   * Біт 8: `LE 2M PHY` (підтримка швидкості 2 Мбіт/с).
   * Біт 11: `LE Coded PHY` (підтримка далекобійного режиму S=2 / S=8).
   * Біт 12: `LE Extended Advertising` (розширені рекламні ланцюжки).
   * Біт 14: `Channel Selection Algorithm #2` (підтримка псевдовипадкових стрибків CSA #2).

7. **`LL_LENGTH_REQ` (`0x14`) та `LL_LENGTH_RSP` (`0x15`):**
   Процедура розширення довжини даних (DLE). Сторони узгоджують параметри `MaxRxOctets`, `MaxTxOctets` (від 27 до 251 байта) та час передачі `MaxRxTime`, `MaxTxTime` (від 328 до 2120 мкс).

8. **`LL_PHY_REQ` (`0x16`), `LL_PHY_RSP` (`0x17`) та `LL_PHY_UPDATE_IND` (`0x18`):**
   Процедура перемикання фізичного рівня. Ведучий та ведений узгоджують симетричний або асиметричний режим передачі (наприклад, LE 2M для передавача і LE 1M для приймача) та вказують лічильник `Instant` моменту перемикання частотних модуляторів.

9. **`LL_PING_REQ` (`0x12`) та `LL_PING_RSP` (`0x13`):**
   Періодична перевірка цілісності автентифікованого каналу зв'язку за допомогою криптографічного MIC. Запобігає атакам перехоплення сесії без відома хоста.

10. **`LL_VERSION_IND` (`0x0C`):**
    Обмін інформацією про версію стека: 8-бітний код версії `CompanyIdentifier` (призначений Bluetooth SIG) та 16-бітний номер субверсії розробника `SubversionNumber`.

## 6. Базові коди помилок Link Layer (Error Codes)

При аварійному розірванні сесії або відхиленні процедури оновлення параметрів контролер Link Layer формує подію розриву з одним із наступних стандартизованих кодів помилок:

1. **`0x08` — Connection Timeout:**
   Таймаут нагляду зв'язку `connSupervisionTimeout` минув без отримання жодного валідного кадру з правильною контрольною сумою CRC.
2. **`0x13` — Remote User Terminated Connection:**
   Зв'язок розірвано за ініціативою користувача на віддаленій стороні (наприклад, вимкнення Bluetooth у меню смартфона).
3. **`0x14` — Remote Device Terminated Connection due to Low Resources:**
   Віддалений пристрій вичерпав ресурси оперативної пам'яті для утримання буферів зв'язку.
4. **`0x15` — Remote Device Terminated Connection due to Power Off:**
   Віддалений вузол ініціював планове знеструмлення (розряд акумулятора або вимкнення живлення).
5. **`0x22` — LL Response Timeout:**
   Віддалений контролер не надав відповіді на відправлений пакет керування `LL Control PDU` протягом 32.0 секунд.
6. **`0x28` — Instant Passed:**
   Момент застосування нових параметрів `Instant` настав до того, як керівне повідомлення було підтверджене (наслідок масивних завад в ефірі). З'єднання негайно розривається через ризик втрати частотної синхронізації.
7. **`0x3B` — Unacceptable Connection Parameters:**
   Запропоновані параметри зв'язку порушують інваріанти узгодженості або апаратні обмеження веденого.
8. **`0x3D` — MIC Failure:**
   Невідповідність коду автентичності повідомлення при розшифруванні пакету AES-128 CCM (спроба підміни пакету або розсинхронізація лічильника пакетів).

## 7. Базові часові константи та інваріанти канального рівня

```
Параметр                      Символ           Діапазон / Значення              Одиниця виміру
──────────────────────────────────────────────────────────────────────────────────────────────
Міжкадровий інтервал          T_IFS            150 ± 1                          мікросекунди (мкс)
Інтервал з'єднання            connInterval     7.5 .. 4000.0 (крок 1.25)        мілісекунди (мс)
Затримка веденого             connSlaveLatency 0 .. 499                         подій з'єднання
Таймаут нагляду зв'язку       connSupervision  100 .. 32000 (крок 10)           мілісекунди (мс)
                               Timeout
Тривалість преамбули 1M       t_preamble_1m    8.0 (1 байт)                     мікросекунди (мкс)
Тривалість преамбули 2M       t_preamble_2m    8.0 (2 байти)                    мікросекунди (мкс)
Тривалість передачі AA        t_access_addr    32.0 (4 байти на 1M PHY)         мікросекунди (мкс)

```

### Головний математичний інваріант узгодженості:
Для запобігання передчасному розриву сесії під час дозволеного сну веденого, таймаут нагляду повинен суворо задовольняти нерівність:

```
connSupervisionTimeout > (1 + connSlaveLatency) · connInterval · 2
```

Якщо під час узгодження нових параметрів через `LL_CONNECTION_UPDATE_IND` значення порушують це правило, контролер Link Layer веденого зобов'язаний відхилити запит із кодом помилки `0x3B` (*Unacceptable Connection Parameters*).
