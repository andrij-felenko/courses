# ⚙️ Stop-and-wait ARQ у коді: номери, повтори, дублікати

[Надійний обмін](topic:com-transport/reliable-link) тримається на одному циклі: відправ команду, дочекайся підтвердження, не дочекався — повтори. Найпростіше робоче втілення цього циклу зветься **stop-and-wait ARQ** (англ. *Automatic Repeat reQuest*, «автоматичний запит повтору»; *stop-and-wait* — «спинись і чекай»): шлемо **один** пакет і **спиняємось**, поки не прийде **ACK** (англ. *acknowledgement*, «підтвердження»). Прийшов — шлемо наступний; не прийшов за відведений час — шлемо той самий ще раз. Звучить як три рядки коду, та в ньому ховаються три тонкощі, на яких новачок спотикається: що нумерувати, як не виконати команду двічі й коли здатися.

**Задача буденна, але критична.** На борту є команди, втрата яких небезпечна: «роззброїти мотори», «увімкнути запис», «перемкнути режим польоту». Їх не можна слати best-effort, як [телеметрію](topic:sys-dron/telemetry-stream) — одне старе значення висоти нічого не варте, а одна загублена команда «роззброїти» лишає мотори крутитися. Тож такі команди шлють з підтвердженням і повтором. Але щойно з'являється повтор, з'являється й нова небезпека: команда може дійти, а загубитися вже **ACK** — і відправник, не дочекавшись його, пошле команду **вдруге**. Якщо приймач виконає її двічі, наслідки бувають гірші за саму втрату. Тому stop-and-wait — це не «шли, поки не дійде», а «шли так, щоб дублікат був безпечним і щоб було коли спинитися».

## Що нумерувати й навіщо

Перша тонкість — **номер послідовності** (англ. *sequence number*) на кожній команді. Без нього приймач не відрізнить свіжу команду від повтору вже виконаної. З ним усе стає на місця: відправник вішає на команду номер і **не міняє** його на повторах; приймач пам'ятає останній виконаний номер і виконує лише те, що **новіше**.

Звідси одразу й захист від дубліката. Уяви: команда `#7` «роззброїти» дійшла, приймач її виконав і послав `ACK #7`, але цей ACK загубився в ефірі. Відправник чекав, не дочекався, повторив `#7`. Приймач бачить `#7` удруге, розуміє «це я вже робив», команду **не виконує знову**, але **повторно шле `ACK #7`** — щоб відправник нарешті почув підтвердження й заспокоївся. Так дублікат стає нешкідливим: команда виконується рівно раз, скільки б разів не прийшла.

NACK (англ. *negative acknowledgement*, «заперечне підтвердження») — необов'язкове доповнення. Якщо приймач отримав пакет, але з **зіпсованою** контрольною сумою, він може одразу попросити повтор сигналом NACK, не змушуючи відправника чекати таймауту. Це пришвидшує відновлення на каналі, де пакети частіше псуються, ніж зникають; там, де пакет або дійшов цілим, або не дійшов зовсім, вистачає й самого таймауту.

Важливо одразу бачити межу самої схеми. Stop-and-wait по самій своїй будові тримає **рівно один** непідтверджений пакет «у польоті»: відправник стоїть, поки не почує ACK, тож канал між посилкою й підтвердженням простоює. Для рідкісних критичних команд це байдуже — вони й так нечасті, а простій у пів-затримки нікому не муляє. Але натягнути цю схему на потік телеметрії означало б слати по одному значенню за повний оберт «туди й назад», марнуючи майже всю пропускну здатність каналу. Саме тому потокові протоколи переходять до інших схем ARQ, де в польоті одночасно багато пакетів (ковзне вікно); stop-and-wait же лишається там, де його простота — перевага, а не вада: на поодиноких командах, втрату яких треба надолужити напевно.

## Ідея: скінченний автомат на дві дії

Stop-and-wait зручно бачити як крихітний скінченний автомат відправника з двома станами: **IDLE** (нема чого слати) і **WAIT_ACK** (команду послано, чекаю підтвердження). У WAIT_ACK можливі рівно три події: прийшов потрібний ACK (успіх, назад в IDLE), вичерпався `ACK_TIMEOUT` (повтор тієї самої команди), або повторів стало забагато (здаюся, кажу про обрив назовні).

Ключове рішення — **стеля повторів**. «Шли, поки не дійде» на бездротовому каналі означає «шли вічно, якщо зв'язок мертвий» — а мертвий зв'язок треба **визнати** й передати керування у failsafe, а не молотити в порожнечу. Тому повтори лічать, і після `MAX_TRIES` марних спроб функція чесно повертає «не вдалося». Скільки саме спроб і з яким таймаутом — компроміс: добуток `ACK_TIMEOUT × MAX_TRIES` задає, **скільки часу** система готова боротися за команду, перш ніж оголосити обрив.

## Робочий код

Спершу синхронний кістяк — він найясніше показує логіку (а нижче зробимо неблокуючий варіант для головного циклу прошивки):

:::tabs
```cpp
#include <stdint.h>

struct Cmd { uint8_t op; int16_t arg; };

// Шлю критичну команду stop-and-wait. true — підтверджено, false — зв'язок мертвий.
bool sendReliable(uint8_t seq, const Cmd& cmd) {
    for (int tries = 0; tries < MAX_TRIES; tries++) {
        sendPacket(seq, cmd);                  // 1) передаю (чи повторно — той самий seq)
        uint32_t t0 = millis();
        while (millis() - t0 < ACK_TIMEOUT) {  // 2) чекаю ACK саме з цим номером
            if (gotAckFor(seq)) return true;   //    дійшло й підтверджено
        }
        // 3) тиша до таймауту → наступна ітерація повторить той самий seq
    }
    return false;                              // 4) MAX_TRIES марно → обрив
}
```
```python
# Шлю критичну команду stop-and-wait. True — підтверджено, False — зв'язок мертвий.
def send_reliable(seq, cmd):
    for _ in range(MAX_TRIES):
        send_packet(seq, cmd)                  # 1) передаю (чи повторно — той самий seq)
        t0 = millis()
        while millis() - t0 < ACK_TIMEOUT:     # 2) чекаю ACK саме з цим номером
            if got_ack_for(seq):
                return True                    #    дійшло й підтверджено
        # 3) тиша до таймауту → наступна ітерація повторить той самий seq
    return False                               # 4) MAX_TRIES марно → обрив
```
:::

Бік приймача — дзеркальний, і саме тут живе захист від дубліката:

:::tabs
```cpp
static int16_t lastSeq = -1;                   // останній виконаний номер (−1 = ще жодного)

void onPacket(uint8_t seq, const Cmd& cmd) {
    if ((int16_t)seq != lastSeq) {             // новий номер — це нова команда
        execute(cmd);                          //   виконати РІВНО раз
        lastSeq = seq;
    }
    sendAck(seq);                              // ACK шлемо ЗАВЖДИ — і на дублікат теж,
}                                              //   бо попередній ACK міг загубитися
```
```python
last_seq = -1                                  # останній виконаний номер (−1 = ще жодного)

def on_packet(seq, cmd):
    global last_seq
    if seq != last_seq:                        # новий номер — це нова команда
        execute(cmd)                           #   виконати РІВНО раз
        last_seq = seq
    send_ack(seq)                              # ACK шлемо ЗАВЖДИ — і на дублікат теж,
                                               #   бо попередній ACK міг загубитися
```
:::

Те, що `sendAck` стоїть **поза** перевіркою номера, — не випадковість, а суть схеми: повторний ACK на дублікат і є тим, що дає відправникові нарешті вийти з WAIT_ACK, коли перший ACK не дійшов.

## Worked-приклад: ACK загубився

Простежмо найпідступніший випадок — коли зникає не команда, а підтвердження.

**Умова.** `ACK_TIMEOUT = 200` мс, `MAX_TRIES = 5`. Команда `#7` «роззброїти» доходить з першого разу, приймач її виконує, але `ACK #7` губиться в ефірі. Що станеться?

```text
t=0 мс    відправник: sendPacket(#7)        приймач: ще нічого
t=8 мс    приймач отримав #7 (новий) → execute() → роззброєно, lastSeq=7
          приймач: sendAck(#7)  ← цей ACK гине в ефірі
t=200 мс  відправник: ACK не дочекався → повтор sendPacket(#7)   (спроба 2)
t=206 мс  приймач отримав #7 (== lastSeq) → НЕ виконує знову
          приймач: sendAck(#7)  ← цього разу доходить
t=210 мс  відправник: gotAckFor(7) == true → return true
```

Команда виконана **рівно один раз**, хоча пакет `#7` прилетів двічі, а перший ACK зник. Без номера послідовності приймач роззброїв би мотори, тоді з повтору спробував би роззброїти вже роззброєне — у нешкідливому випадку дарма, а для команди на кшталт «крокнути на +10» це був би подвійний крок. Номер плюс «ACK завжди» прибирають цей клас помилок цілком.

А тепер протилежний випадок — зв'язок справді мертвий:

```text
t=0 мс    спроба 1 → тиша 200 мс
t=200 мс  спроба 2 → тиша 200 мс
t=400 мс  спроба 3 → тиша 200 мс
t=600 мс  спроба 4 → тиша 200 мс
t=800 мс  спроба 5 → тиша 200 мс
t=1000 мс 5 спроб марно → return false → викликаємо failsafe()
```

Рівно **1 секунда** боротьби (`200 × 5`), після чого система не вдає, ніби команда дійде, а передає керування [безпечній реакції](topic:com-transport/reliable-link). Це і є сенс стелі повторів: межа між «борюся» і «визнаю обрив» — не випадкова, а порахована.

## Неблокуючий варіант для головного циклу

Синхронний `sendReliable` має одну хибу для прошивки: цикл `while` усередині **блокує** головний цикл на час очікування ACK, а він зайнятий стабілізацією й блокуватися не сміє. Тому в реальному коді stop-and-wait розгортають у той самий автомат, але **без очікування** — на перевірці часу через `millis()`, як [неблокуючий патерн](topic:sf-devices/nonblocking-time):

:::tabs
```cpp
enum LinkState { IDLE, WAIT_ACK };
LinkState st = IDLE;
uint8_t   curSeq;
Cmd       curCmd;
uint32_t  sentAt;
int       tries;

void startSend(uint8_t seq, const Cmd& cmd) {  // поставити команду в чергу
    curSeq = seq; curCmd = cmd; tries = 0;
    sendPacket(curSeq, curCmd); sentAt = millis(); tries = 1;
    st = WAIT_ACK;
}

void linkTick() {                              // викликати щотакту з головного циклу
    if (st != WAIT_ACK) return;
    if (gotAckFor(curSeq)) { st = IDLE; return; }          // підтверджено
    if (millis() - sentAt >= ACK_TIMEOUT) {
        if (tries >= MAX_TRIES) { st = IDLE; failsafe(); return; }  // здаюся
        sendPacket(curSeq, curCmd); sentAt = millis(); tries++;     // повтор
    }
}
```
```python
IDLE, WAIT_ACK = 0, 1

st = IDLE
cur_seq = 0
cur_cmd = None
sent_at = 0
tries = 0

def start_send(seq, cmd):                      # поставити команду в чергу
    global st, cur_seq, cur_cmd, sent_at, tries
    cur_seq, cur_cmd = seq, cmd
    send_packet(cur_seq, cur_cmd); sent_at = millis(); tries = 1
    st = WAIT_ACK

def link_tick():                               # викликати щотакту з головного циклу
    global st, sent_at, tries
    if st != WAIT_ACK:
        return
    if got_ack_for(cur_seq):                   # підтверджено
        st = IDLE; return
    if millis() - sent_at >= ACK_TIMEOUT:
        if tries >= MAX_TRIES:                 # здаюся
            st = IDLE; failsafe(); return
        send_packet(cur_seq, cur_cmd); sent_at = millis(); tries += 1  # повтор
```
:::

Логіка та сама — номер незмінний, повтори лічаться, стеля веде у failsafe, — але `linkTick()` повертається миттєво, лишаючи головному циклу час на все інше. Це той варіант, що справді живе в прошивці.

## Граблі

Помилки тут тихі: код «майже працює», а лінк поводиться дивно або небезпечно.

- **Міняти номер на повторі.** Якщо кожна спроба отримує новий `seq`, приймач вважатиме повтор новою командою й виконає її **двічі**. Номер фіксують на час доставки однієї команди.
- **Слати ACK лише на нову команду.** Якщо ACK не повторюється на дублікат, втрата ACK заганяє відправника у вічні повтори (поки не вичерпає стелю) при цілком живому зв'язку. ACK шлють **завжди**, коли пакет прийнято.
- **Нема стелі повторів.** «Поки не дійде» на мертвому каналі — це нескінченний цикл і відкладений failsafe. Завжди є `MAX_TRIES` і вихід у безпечну реакцію.
- **Блокувати головний цикл.** Синхронне очікування ACK через `while` зупиняє стабілізацію на сотні мілісекунд. У прошивці — лише неблокуючий автомат на `millis()`.
- **Stop-and-wait на потоці.** Чекати ACK після кожного пакета вбиває пропускну здатність: на швидкому потоці телеметрії канал простоює, поки летить підтвердження. Stop-and-wait — для рідкісних **критичних** команд; потік шлють best-effort, без підтверджень.
- **Переповнення номера.** `uint8_t seq` по колу повертається з 255 на 0 — порівняння «новіший» має враховувати це загортання (модульна арифметика), інакше після обороту лічильника свіжа команда здасться старою.
