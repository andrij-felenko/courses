# 🧮 Арифметика зворотного коду та інкрементний перерахунок контрольних сум

Кожен транслятор мережевих адрес NAT щомиті розв'язує фундаментальну обчислювальну задачу. Підміна хоча б одного біта в заголовку IP-дейтаграми або транспортного сегмента (TCP/UDP) робить початкову контрольну суму недійсною. Якщо маршрутизатор буде перераховувати контрольну суму заново по всьому тілу пакета (а довжина пакета може досягати 1500 байтів для стандартного Ethernet або 9000 байтів для Jumbo-кадрів), обчислювальна складність обробки кожного пакета складе `O(N)` операцій. На гігабітних і 100-гігабітних магістралях, де маршрутизатор обробляє десятки мільйонів пакетів за секунду, повний перерахунок створює неприпустиме навантаження на процесорні конвеєри.

Мережеві протоколи стеку TCP/IP (IPv4, ICMP, IGMP, TCP, UDP) використовують спеціальний алгоритм цілісності — **контрольну суму Інтернету (англ. *Internet Checksum*)**, стандартизовану в **RFC 1071**. Її математична структура спирається на **арифметику зворотного коду (англ. *one's complement arithmetic*)**, що має унікальну властивість лінійності: зміну окремих полів заголовка можна скомпенсувати за фіксований час `O(1)` без повторного читання корисного навантаження.

---

### 1. Алгебраїчні основи арифметики зворотного коду

В обчислювальній техніці зворотний код (1's complement) є способом представлення цілих чисел фіксованої розрядності `k` (у мережевих протоколах `k = 16` бітів). На відміну від звичного додаткового коду (2's complement), де заперечення числа формується інверсією бітів із додаванням одиниці (`-x = ~x + 1`), у зворотному коді заперечення є чистою порозрядною інверсією всіх бітів:

```
-x = ~x = (2ᵏ - 1) - x      [для 16-бітних слів: 2¹⁶ - 1 = 65535 = 0xFFFF]
```

#### Властивість двох нулів
В арифметиці зворотного коду існують два математичні представлення нуля:
1. **Позитивний нуль (`+0`)**: двійковий вектор `0000 0000 0000 0000` (`0x0000`).
2. **Негативний нуль (`-0`)**: двійковий вектор `1111 1111 1111 1111` (`0xFFFF`).

З погляду модульної теорії чисел операції додавання та віднімання у зворотному коді є ізоморфними кільцю лишків за складеним модулем `(2ᵏ - 1)` (тобто за модулем `65535` для 16-бітних слів):

```
x + y ≡ z (mod 65535)
```

Єдина практична відмінність полягає в тому, що число `0` може набувати форми `65535` (`0xFFFF`). Усі ненульові елементи `1, 2, ..., 65534` мають єдине представлення.

#### Циклічне перенесення розряду (End-Around Carry)
Коли два 16-бітні слова додаються у стандартному процесорному суматорі, переповнення 16-го розряду формує 17-й біт переносу (англ. *carry out*). Оскільки база модуля становить `2¹⁶ - 1`, вага цього 17-го біта дорівнює:

```
2¹⁶ = (2¹⁶ - 1) + 1 ≡ 1 (mod 2¹⁶ - 1)
```

Отже, біт переносу зі старшого розряду математично еквівалентний додаванню одиниці до наймолодшого розряду (LSB). Цей механізм має назву **циклічного перенесення розряду (англ. *end-around carry*)**.

#### Доведення коректності згортання 32-бітного акумулятора
Під час програмної або апаратної реалізації вигідно накопичувати суму 16-бітних слів у звичайному 32-бітному або 64-бітному регістрі без перевірки прапорця переповнення на кожному кроці:

```
Sum₃₂ = ∑ wᵢ
```

Нехай масив містить `n` слів по 16 бітів. Максимальне значення суми для стандартного IP-пакета (довжиною до 65535 байтів, тобто `n ≤ 32768` слів) становить:

```
Sum_max = 32768 · 65535 = 2 147 450 880 < 2³¹ - 1
```

Це гарантовано вміщується у беззнаковий 32-бітний регістр. Згортання 32-бітного акумулятора до 16-бітної форми виконується операцією:

```
Sum₁₆ = (Sum₃₂ & 0xFFFF) + (Sum₃₂ >> 16)
```

**Теорема про число кроків згортання:** Для будь-якого 32-бітного числа `S ≤ 0xFFFFFFFF` операція `(S & 0xFFFF) + (S >> 16)` зменшує результат до величини, що не перевищує `0x1FFFE`. Отже, рівно **одне повторне додавання** переносу `Sum₁₆ = (Sum₁₆ & 0xFFFF) + (Sum₁₆ >> 16)` гарантовано зводить результат до строго 16-бітного діапазону `[0x0000, 0xFFFF]`.

*Доведення:*
1. Максимальне значення `S = 0xFFFFFFFF`.
2. Старша частина `S >> 16 = 0xFFFF`, молодша частина `S & 0xFFFF = 0xFFFF`.
3. Перший крок: `0xFFFF + 0xFFFF = 0x1FFFE`.
4. Для числа `0x1FFFE`: старша частина `0x1FFFE >> 16 = 0x0001`, молодша частина `0x1FFFE & 0xFFFF = 0xFFFE`.
5. Другий крок: `0xFFFE + 0x0001 = 0xFFFF ≤ 0xFFFF`. Теорему доведено.

#### Комутативність, асоціативність та незалежність від порядку байтів
Додавання у зворотному коді є строго комутативним і асоціативним:
- `A + B = B + A`
- `(A + B) + C = A + (B + C)`
- `~(A + B) = ~A + ~B`

Надзвичайно важливою для мережевої інженерії є властивість **незалежності від порядку байтів (англ. *byte-order independence*)**: якщо поміняти місцями старший і молодший байти в кожному 16-бітному слові вхідного масиву, підсумкова 16-бітна сума у зворотному коді також матиме дзеркально переставлені байти:

```
SwappedSum(SwapBytes(w₁), SwapBytes(w₂), ...) = SwapBytes(Sum(w₁, w₂, ...))
```

Це дозволяє мережевим процесорам (NPU) підсумовувати 16-бітні слова в порядку байтів процесора (Little-Endian або Big-Endian) без постійного виклику конверсійних інструкцій `ntohs()` на кожному слові.

### 2. Порівняння з іншими алгоритмами контролю цілісності

Вибір 1's complement для заголовків Інтернету у 1970-1980-х роках був компромісом між швидкістю обчислення та надійністю виявлення помилок:
1. **Поліноміальні коди CRC-32 (Ethernet L2)**: мають високу здатність виявлення групових помилок (англ. *burst errors*), але операція ділення многочленів за модулем 2 не є лінійно-адитивною для зміни довільного 16-бітного слова без перерахунку всього кадру.
2. **Алгоритм Адлера Adler-32 (Zlib)**: комбінує дві 16-бітні суми за модулем 65521 (просте число). Він швидший за CRC, проте складніший за 1's complement через необхідність ділення на 65521.
3. **Internet Checksum (RFC 1071)**: найпростіший з усіх можливих алгоритмів, що реалізується на будь-якому мікропроцесорі за кілька тактів і дозволяє інкрементну компенсацію `O(1)` при маршрутизації та NAT.

### 3. Визначення та алгоритм контрольної суми (RFC 1071)

Згідно з RFC 1071, **контрольна сума Інтернету `C`** для масиву 16-бітних слів `[w₁, w₂, ..., wₙ]` визначається як побітова інверсія суми всіх слів у зворотному коді:

```
C = ~(w₁ + w₂ + w₃ + ... + wₙ)      [сумування в 1's complement]
```

Під час формування пакета відправник обнуляє поле контрольної суми (`C = 0x0000`), обчислює суму всіх слів заголовка (а для TCP/UDP — заголовка, псевдозаголовка та корисних даних) і записує інвертований результат у поле `checksum`.

Отримувач пакета підсумовує всі слова повідомлення, **включаючи саме поле отриманої контрольної суми**:

```
S_total
= (w₁ + w₂ + ... + wₙ) + C                  [повна сума слів із контрольною сумою]
= (w₁ + w₂ + ... + wₙ) + ~(w₁ + ... + wₙ)   [підстановка означення C = ~S]
= X + ~X                                    [позначення X = w₁ + ... + wₙ]
= 0xFFFF                                    [сума прямого та інверсного коду: -0]
```

Якщо пакет не пошкоджений під час передачі фізичним каналом, фінальна сума у зворотному коді обов'язково дорівнює `0xFFFF` (усі одиниці). Інверсія цієї перевірочної суми дає `~0xFFFF = 0x0000`, що сигналізує стеку протоколів про цілісність даних.

#### Обробка непарної довжини корисного навантаження
Якщо довжина масиву даних у байтах є непарною (наприклад, UDP-дейтаграма довжиною 257 байтів), останній байт розглядається як старший байт віртуального 16-бітного слова, молодший байт якого доповнюється нулем (`0x00`). Цей віртуальний нульовий байт не передається мережею, але бере участь у розрахунку суми.

### 4. Інкрементний перерахунок при підміні полів (RFC 1624)

Припустімо, що початковий пакет мав контрольну суму `C`, утворену з суми 16-бітних слів `S`:

```
S = w₁ + w₂ + ... + m + ... + wₙ
C = ~S  ⇒  ~C = S
```

Маршрутизатор NAT замінює одне 16-бітне поле `m` (наприклад, частину IP-адреси або номер порту) на нове 16-бітне значення `m'`. Нова сума слів `S'` становить:

```
S'
= S - m + m'      [вилучення старого слова та додавання нового]
= S + ~m + m'     [заміна віднімання на інверсію: -m = ~m в 1's complement]
```

Підставимо `S = ~C` та візьмемо фінальну інверсію для отримання нової контрольної суми `C' = ~S'`:

```
~C' = ~C + ~m + m'
C'  = ~(~C + ~m + m')
```

Це фундаментальне рівняння **RFC 1624 (Equation 3)**. Воно стверджує: щоб отримати нову контрольну суму `C'`, достатньо взяти початкову суму `C`, інвертувати її, додати інвертоване старе значення `~m`, додати нове значення `m'`, врахувати циклічні перенесення й інвертувати результат.

#### Чому проста формула RFC 1141 містила дефект
У ранньому стандарті **RFC 1141** пропонувалася спрощена формула: `C' = C + m + ~m'`. Ця формула коректно працювала для більшості випадків, але містила дефект граничного значення: коли проміжна сума перетворювалася на `0x0000` або `0xFFFF`, формула RFC 1141 генерувала значення `0x0000` замість `0xFFFF`.

У протоколах IPv4 та TCP значення контрольної суми `0x0000` є неприпустимим (оскільки негативний нуль `0xFFFF` інвертується у звичайний нуль лише при перевірці). У протоколі UDP значення `0x0000` зарезервоване і має спеціальний сенс: «контрольна сума не обчислювалася відправником і не перевіряється». Якщо інкрементний перерахунок помилково запише `0x0000` у заголовок UDP, отримувач взагалі вимкне захист цілісності. Стандарт RFC 1624 повністю усунув цей крайовий дефект завдяки симетричній інверсії `C' = ~(~C + ~m + m')`.

### 5. Оновлення 32-бітних полів (IPv4-адрес)

IPv4-адреса складається з 32 бітів, тобто з двох 16-бітних слів: старшої половини `m_hi` та молодшої половини `m_lo`. При підміні повної адреси `m = (m_hi, m_lo)` на `m' = (m'_hi, m'_lo)` формула RFC 1624 розширюється за рахунок асоціативності додавання:

```
~C' = ~C + ~m_hi + ~m_lo + m'_hi + m'_lo
C'  = ~(~C')
```

Обчислення виконується за один прохід: 32-бітний акумулятор підсумовує всі компоненти дельти, після чого старші біти переносу додаються до молодших 16 бітів.

### 6. Покроковий числовий приклад розрахунку для IPv4

Розглянемо практичний приклад трансляції адреси джерела (SNAT) у реальному пакеті:
- **Початкова IP-адреса джерела**: `192.168.1.50`
- **Нова публічна IP-адреса**: `203.0.113.5`
- **Початкова контрольна сума заголовка IPv4**: `C = 0x4A2B`

#### Крок 1. Переведення адрес у 16-бітні шістнадцяткові слова

Для початкової адреси `192.168.1.50`:
```
192.168  =  192 · 256 + 168  =  49320  =  0xC0A8  (m_hi)
1.50     =  1 · 256 + 50     =  306    =  0x0132  (m_lo)
```

Для нової адреси `203.0.113.5`:
```
203.0    =  203 · 256 + 0    =  51968  =  0xCB00  (m'_hi)
113.5    =  113 · 256 + 5    =  28933  =  0x7105  (m'_lo)
```

#### Крок 2. Обчислення побітових інверсій
```
~C       =  ~0x4A2B  =  0xB5D4
~m_hi    =  ~0xC0A8  =  0x3F57
~m_lo    =  ~0x0132  =  0xFECD
```

#### Крок 3. Підсумовування компонентів у 32-бітному суматорі
Складемо всі доданки у звичайній 32-бітній арифметиці беззнакових чисел:

```
  0xB5D4   (~C)
+ 0x3F57   (~m_hi)
+ 0xFECD   (~m_lo)
+ 0xCB00   (m'_hi)
+ 0x7105   (m'_lo)
────────
= 0x32FFD
```

#### Крок 4. Згортання циклічного переносу (End-Around Carry)
Сума `0x32FFD` містить перенос у старших розрядах (число `0x0003` у бітах 16..31). Складемо старшу частину з молодшою:

```
Сума
= (0x32FFD & 0xFFFF) + (0x32FFD >> 16)      [виділення 16 бітів та бітів переносу]
= 0x2FFD + 0x0003                           [додавання перенесеного розряду до LSB]
= 0x3000                                    [результат 16-бітного згортання]
```

Оскільки отримана сума `0x3000` не перевищує `0xFFFF`, вторинного переносу немає.

#### Крок 5. Фінальна інверсія результату
```
C' = ~0x3000 = 0xCFFF
```

Нова контрольна сума IPv4-заголовка становить `0xCFFF`. Обчислення зайняло лише п'ять операцій додавання та дві бітові інверсії, що виконалося за декілька тактів процесора без звернення до інших полів пакета.

### 7. Оновлення контрольних сум транспортного рівня (TCP і UDP)

Транспортні протоколи TCP і UDP під час розрахунку своєї контрольної суми додають до сегмента спеціальний віртуальний блок — **псевдозаголовок IPv4 (англ. *IPv4 Pseudo-Header*)**, що складається з таких полів:
1. IP-адреса джерела (Source IP) — 32 біти (2 слова по 16 бітів);
2. IP-адреса призначення (Destination IP) — 32 біти (2 слова по 16 бітів);
3. Нульовий байт + номер протоколу (наприклад, 6 для TCP, 17 для UDP) — 16 бітів;
4. Довжина транспортного сегмента (TCP/UDP Length) — 16 бітів.

```
┌────────────────────────────────────────────────────────┐
│               IPv4 Source Address (32 біти)            │
├────────────────────────────────────────────────────────┤
│            IPv4 Destination Address (32 біти)          │
├───────────────┬───────────────┬────────────────────────┤
│   Zero (8)    │  Protocol (8) │    TCP/UDP Length (16) │
└───────────────┴───────────────┴────────────────────────┘
```

Коли маршрутизатор NAT виконує трансляцію портів (NAPT), він одночасно змінює:
- IP-адресу джерела (SNAT) або призначення (DNAT) — 2 слова;
- Номер порту TCP/UDP — 1 слово.

Оскільки IP-адреси входять до псевдозаголовка, заміна IP на рівні L3 автоматично порушує контрольну суму транспортного рівня L4.

Інкрементна формула RFC 1624 застосовується до поля `tcp->check` або `udp->check` абсолютно ідентично, приймаючи одразу 3 пари 16-бітних слів (дві половини IP-адреси та порт):

```
~C_l4' = ~C_l4 + ~ip_hi + ~ip_lo + ~port + ip'_hi + ip'_lo + port'
C_l4'  = ~(~C_l4')
```

#### Покроковий приклад для TCP-сегмента
Припустимо, клієнт надсилає TCP-сегмент із внутрішнього сокета `192.168.1.50:51234` на вебсервер `93.184.216.34:80`.
Транслятор підміняє джерело на `203.0.113.5:40001`.
Початкова контрольна сума TCP: `C_tcp = 0x821A`.

1. Старий порт: `51234 = 0xC822`  ⇒  `~0xC822 = 0x37DD`.
2. Новий порт: `40001 = 0x9C41`.
3. Підсумовування компонентів:
```
  0x7DE5   (~C_tcp = ~0x821A)
+ 0x3F57   (~old_ip_hi)
+ 0xFECD   (~old_ip_lo)
+ 0x37DD   (~old_port)
+ 0xCB00   (new_ip_hi)
+ 0x7105   (new_ip_lo)
+ 0x9C41   (new_port)
────────
= 0x3CC2C
```
4. Згортання переносу:
```
Сума_tcp
= (0x3CC2C & 0xFFFF) + (0x3CC2C >> 16)      [виділення 16 бітів та переносу]
= 0xCC2C + 0x0003                           [додавання 3 одиниць переносу до LSB]
= 0xCC2F                                    [результат згортання]
```
5. Фінальна інверсія:
```
C_tcp' = ~0xCC2F = 0x33D0
```

Контрольна сума TCP скоригована за `O(1)` операцій без перечитування гігабайтів корисних даних у буфері пакета.

#### Специфіка протоколу UDP
Для UDP діє критичне правило:
1. Якщо початкове поле контрольної суми `udp->check == 0x0000`, відправник вимкнув перевірку контрольної суми. Маршрутизатор NAT **не повинен** її обчислювати й зобов'язаний залишити значення `0x0000`.
2. Якщо ж початкове значення ненульове, маршрутизатор виконує інкрементний перерахунок. Якщо в результаті обчислення нова контрольна сума стає рівною `0x0000` (тобто інверсія від `0xFFFF`), стандарт вимагає зберегти значення `0xFFFF`, щоб отримувач не сприйняв її як вимкнену перевірку.

### 8. Специфіка пакетів ICMP та подвійне оновлення

Особливий випадок для транслятора NAT становлять керуючі повідомлення протоколу ICMP (RFC 792):
1. **Інформаційні повідомлення (Echo Request / Echo Reply — `ping`)**: замість номерів портів ICMP містить 16-бітне поле ідентифікатора `icmp->id`. Транслятор NAPT підміняє `icmp->id` на унікальний ідентифікатор сесії аналогічно до TCP/UDP портів та оновлює контрольну суму `icmp->checksum` за стандартною формулою RFC 1624.
2. **Повідомлення про помилки (Destination Unreachable, Time Exceeded, Fragmentation Needed)**: тіло повідомлення ICMP про помилку містить **копію початкового IP-заголовка та перші 8 байтів корисного навантаження** пакета, який спричинив збій.
   
Коли маршрутизатор NAT обробляє вхідне повідомлення про помилку ICMP:
- Він повинен знайти сесію за внутрішнім вкладеним заголовком (IP + порти у корисних даних ICMP);
- Здійснити зворотну трансляцію внутрішнього IP-заголовка;
- Інкрементно оновити контрольну суму внутрішнього IP-заголовка;
- Інкрементно оновити контрольну суму самого зовнішнього ICMP-повідомлення.

Таке «подвійне оновлення» є критичним для коректної роботи алгоритму визначення максимального розміру блоку MTU на шляху — **Path MTU Discovery (PMTUD)**.

### 9. Апаратне розвантаження (Hardware Checksum Offloading)

У сучасних мережевих картах (NIC) операції перевірки та розрахунку контрольних сум перенесені на апаратний рівень мережевого чипа (англ. *Hardware Checksum Offloading*):
- **Rx Checksum Offload**: мережева карта підсумовує слова під час отримання кадру з фізичного середовища DMA-контролером і виставляє прапорець `CHECKSUM_UNNECESSARY` у структурі `sk_buff` ядра Linux.
- **Tx Checksum Offload**: операційна система не підраховує контрольну суму корисного навантаження, а передає мережевій карті значення `CHECKSUM_PARTIAL` разом із відступом (offset) поля контрольної суми. Карта самостійно дораховує суму безпосередньо перед відправкою сигналу в кабель.

Проте при проходженні пакета крізь підсистему NAT програмного ядра Linux, якщо мережевий інтерфейс не підтримує розвантаження трансляції або пакет пересилається між віртуальними мостами (`veth`, `bridge`), ядро спирається саме на математику інкрементного розрахунку RFC 1624 у функціях `inet_proto_csum_replace4()` та `csum_replace2()`.
