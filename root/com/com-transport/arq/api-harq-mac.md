# 📋 Інтерфейс та структури керування HARQ у стеках 3GPP (MAC/PHY)

Специфікація структур даних, реєстрів стану та програмного інтерфейсу (API) сутності керування гібридним повтором (HARQ Entity) на стику рівнів MAC і PHY у стандартах LTE та 5G NR визначає параметри процесів софт-комбінування, індексацію версій надлишковості (RV), прапорці нового блоку (NDI) та правила розподілу пам'яті буфера м'яких рішень (LLR).

---

## Архітектура взаємодії MAC-PHY у стандартах 3GPP

У стеках мобільного зв'язку 3GPP (LTE / 5G New Radio) керування повторною передачею розділено на два рівні з різними часовими бюджетами:
1. **Рівень RLC (Radio Link Control):** повільний протокол Selective Repeat ARQ (режим RLC AM), який оперує логічними кадрами та працює з затримкою `20–50` мс поверх протоколу PDCP;
2. **Рівень MAC / PHY:** надшвидкий гібридний ARQ (HARQ) на базі паралельних процесів Stop-and-Wait із софт-комбінуванням у буфері LLR, який працює на масштабі кожного слота радіокадру (затримка зворотного зв'язку `0.5–4` мс).

```
                      Рівень MAC (Керування)
           ┌───────────────────────────────────────────┐
           │      Сутність керування HARQ (Entity)     │
           │  ┌───────────┐ ┌───────────┐ ┌─────────┐  │
           │  │Процес #0  │ │Процес #1  │ │... #15  │  │
           └──┴─────┬─────┴─┴─────┬─────┴─┴────┬────┴──┘
                    │             │            │
          Службові команди через інтерфейс SCF FAPI
                    │             │            │
           ┌────────▼─────────────▼────────────▼───────┐
           │      Апаратний модем PHY (L1 Baseband)    │
           │  - LDPC / Polar декодер                   │
           │  - Буфер м'яких бітів LLR (Soft Buffer)   │
           └───────────────────────────────────────────┘
```

Для одночасного забезпечення безперервного завантаження радіоканалу та збереження простоти логіки Stop-and-Wait протокол HARQ реалізує **багатопроцесну структуру** (англ. *Multi-Process Stop-and-Wait*):
- Поки Процес #0 очікує відповіді `ACK`/`NACK` від приймача, передавач послідовно використовує Процеси #1, #2, ..., #15 у наступних слотах часу;
- Кількість паралельних процесів `N_proc` розраховується так, щоб повністю покрити час кругового циклу `RTT` фізичного рівня:
```
N_proc ≥ ⌈ RTT_phy / T_slot ⌉
```
У LTE FDD використовується фіксовано `8` процесів HARQ (затримка `8` субкадрів по `1` мс). У 5G NR для гнучкої нумерології піднесучих (SCS від 15 до 120 кГц) підтримується до `16` незалежних процесів HARQ на одну компонентну несучу (CC).

## Структури даних дескрипторів HARQ

Уніфікований інтерфейс обміну між рівнями L2 (MAC) та L1 (PHY) за стандартом Small Cell Forum FAPI (Femto Application Platform Interface) використовує дескриптори транспортних блоків.

Нижче наведено базові C та C++ структури опису стану процесу HARQ передавача та приймача.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

/* Версія надлишковості (Redundancy Version) */
typedef enum {
    HARQ_RV_0 = 0,  /* Систематичні біти + базовий паритет */
    HARQ_RV_2 = 2,  /* Перша порція додаткового паритету */
    HARQ_RV_3 = 3,  /* Друга порція додаткового паритету */
    HARQ_RV_1 = 1   /* Залишкова порція паритету / високі частоти */
} HarqRedundancyVersion;

/* Стан процесу HARQ */
typedef enum {
    HARQ_STATE_IDLE = 0,
    HARQ_STATE_ACTIVE_TX,
    HARQ_STATE_WAITING_FEEDBACK,
    HARQ_STATE_MAX_RETRIES_EXCEEDED
} HarqProcessState;

/* Результат декодування фізичного рівня */
typedef enum {
    HARQ_FEEDBACK_NACK = 0,
    HARQ_FEEDBACK_ACK  = 1,
    HARQ_FEEDBACK_DTX  = 2  /* Discontinuous Transmission: база не почула відповіді */
} HarqFeedback;

/* Дескриптор процесу HARQ передавача (TX) */
typedef struct {
    uint8_t process_id;             /* ID процесу: 0..15 */
    HarqProcessState state;         /* Поточний стан автомата */
    bool ndi;                       /* New Data Indicator (0 або 1) */
    HarqRedundancyVersion rv;       /* Поточний індекс RV */
    uint8_t transmission_count;     /* Лічильник спроб (1..MAX_HARQ_RETRIES) */
    uint8_t mcs_index;              /* Індекс модуляції та кодування (0..31) */
    uint32_t transport_block_size;  /* Розмір корисних даних у байтах (TBS) */
    uint32_t code_bits_len;         /* Довжина кодового блоку після кодера */
    uint8_t *payload_ptr;           /* Покажчик на корисне навантаження в пам'яті */
} HarqTxProcessDescriptor;

/* Дескриптор софт-буфера процесу HARQ приймача (RX) */
typedef struct {
    uint8_t process_id;             /* ID процесу: 0..15 */
    bool last_ndi;                  /* Останній зафіксований стан NDI */
    uint8_t combined_transmissions; /* Кількість об'єднаних копій у буфері */
    uint32_t soft_buffer_size;      /* Кількість виділених LLR комірок */
    int8_t *llr_buffer;             /* Масив логарифмічних відношень (8-біт квантування) */
    bool crc_pass;                  /* Прапорець успішного проходження CRC */
} HarqRxBufferDescriptor;
```
```cpp
#include <cstdint>
#include <vector>
#include <span>
#include <memory>

enum class HarqRedundancyVersion : uint8_t {
    Rv0 = 0,  // Систематичні біти + базовий паритет
    Rv2 = 2,  // Перша порція додаткового паритету
    Rv3 = 3,  // Друга порція додаткового паритету
    Rv1 = 1   // Залишкова порція паритету
};

enum class HarqProcessState : uint8_t {
    Idle = 0,
    ActiveTx,
    WaitingFeedback,
    MaxRetriesExceeded
};

enum class HarqFeedback : uint8_t {
    Nack = 0,
    Ack = 1,
    Dtx = 2  // Discontinuous Transmission
};

struct HarqTxProcessDescriptor {
    uint8_t process_id = 0;
    HarqProcessState state = HarqProcessState::Idle;
    bool ndi = false;
    HarqRedundancyVersion rv = HarqRedundancyVersion::Rv0;
    uint8_t transmission_count = 0;
    uint8_t mcs_index = 0;
    uint32_t transport_block_size = 0;
    uint32_t code_bits_len = 0;
    std::span<const uint8_t> payload;
};

struct HarqRxBufferDescriptor {
    uint8_t process_id = 0;
    bool last_ndi = false;
    uint8_t combined_transmissions = 0;
    std::vector<int8_t> llr_buffer;  // Квантовані значення LLR (від -127 до +127)
    bool crc_pass = false;
};
```

## Семантика керуючих полів заголовка DCI

Керування процесами HARQ здійснюється базовою станцією (gNodeB в 5G або eNodeB в LTE) шляхом передачі службових повідомлень у форматі інформації керування низхідним каналом (англ. *Downlink Control Information*, DCI) по фізичному каналу PDCCH.

Поля DCI, що безпосередньо керують HARQ:

| Поле DCI | Розрядність | Призначення та поведінка |
| :--- | :--- | :--- |
| **HARQ Process Number** | 4 біти | Ідентифікатор паралельного процесу (значення `0..15`). Визначає, який саме софт-буфер на стороні приймача повинен використовуватись для прийому або комбінування. |
| **New Data Indicator (NDI)** | 1 біт | Прапорець нового блоку даних. **Принцип інверсії:** якщо біт `NDI` змінив значення порівняно з попередньою передачею в цьому ж `Process Number` (`0 → 1` або `1 → 0`), приймач **очищає софт-буфер** і сприймає дані як новий пакет. Якщо `NDI` не змінився, дані додаються до наявного LLR-буфера (повторна спроба). |
| **Redundancy Version (RV)** | 2 біти | Вказівник точки початку зчитування з кругового буфера (значення `0, 1, 2, 3`). Визначає, яка саме порція паритетних бітів міститься в цьому слоті. |
| **MCS Index** | 5 бітів | Індекс модуляції та кодування (`0..31`). Задає розмір транспортного блоку (TBS) та порядок модуляції (QPSK, 16QAM, 64QAM, 256QAM). |
| **PDSCH-to-HARQ_feedback timing indicator** | 3 біти | (Тільки в 5G NR, параметр `K_1`). Задає кількість слотів затримки між прийомом блоку PDSCH та моментом передачі `ACK`/`NACK` у каналі PUCCH. |

## Таблиця послідовностей версій надлишковості (RV Mapping)

У схемі інкрементальної надлишковості (HARQ-IR) порядок вибору версій надлишковості `RV` на кожній повторній спробі має вирішальне значення для продуктивності декодера LDPC або Turbo.

Стандарт 3GPP TS 38.214 регламентує рекомендовані послідовності RV для 4 послідовних спроб:

| Послідовність RV | Спроба 1 | Спроба 2 | Спроба 3 | Спроба 4 | Сфера застосування та властивості |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Основна (Default IR)** | `RV0` | `RV2` | `RV3` | `RV1` | **Стандартний вибір 5G NR / LTE:** `RV0` містить усі систематичні біти. `RV2` та `RV3` додають найважливіші паритетні перевірки, що дає максимальний кодовий виграш при першому повторі. |
| **Альтернативна** | `RV0` | `RV3` | `RV0` | `RV3` | Використовується в каналах із високою швидкістю коду (`R > 2/3`) для збалансованого накопичення систематичної та паритетної енергії. |
| **Chase Combining** | `RV0` | `RV0` | `RV0` | `RV0` | Спрощена схема (HARQ-CC). Застосовується в режимах ультранадійного зв'язку з низькою затримкою (URLLC) або при обмеженому розмірі буфера термінала. |

## Організація кругового буфера узгодження швидкостей (Circular Buffer Rate Matching)

Після кодування канальним кодером (LDPC у 5G NR або Turbo-кодером у LTE) сформовані систематичні та паритетні біти записуються в апаратний кільцевий буфер розміром `N_cb` бітів.

```
       ┌─────────────────────────────────────────────────────────┐
       │     Кільцевий буфер узгодження швидкості (N_cb біт)     │
       └─────────────────────────────────────────────────────────┘
       ├──────────────┬──────────────┬──────────────┬────────────┤
       │     RV0      │     RV2      │     RV3      │    RV1     │
       │(Систематичні)│  (Паритет 1) │  (Паритет 2) │(Паритет 3) │
       └──────────────┴──────────────┴──────────────┴────────────┘
       ▲              ▲              ▲              ▲
       │              │              │              │
     k_0 = 0      k_0 = 2·N_cb/4  k_0 = 3·N_cb/4  k_0 = 1·N_cb/4
```

Позиція початкового біта `k_0` для кожного значення `RV` розраховується за формулою:

```
k_0 = ⌊ (RV · N_cb) / 4 ⌋                      [для LDPC Base Graph 1/2 у 5G NR]
```

Передавач вичитує з кільця рівно `E` бітів (де `E` — місткість виділених ресурсних блоків у слоті), переходячи по колу через кінець масиву `N_cb` на початок. Приймач записує прийняті м'які рішення LLR за тими самими циклічними адресами, накопичуючи енергію перекритих бітів.

## Розрахунок вимог до пам'яті софт-буфера термінала (UE Soft Buffer)

Загальний обсяг пам'яті LLR, який користувацький термінал (UE) зобов'язаний виділити під усі паралельні процеси HARQ, жорстко обмежений категорією пристрою (UE Category).

Сумарна кількість м'яких бітів термінала `N_soft` ділиться між активними процесами HARQ:

```
N_soft_per_process = ⌊ N_soft / (K_MIMO · min(N_proc, M_limit)) ⌋
```
де:
- `N_soft` — повна апаратна пам'ять LLR чіпсета (наприклад, `25 344 000` бітів для 5G UE Cat 20);
- `K_MIMO` — коефіцієнт просторових шарів (`2` для 2x2 MIMO, `4` для 4x4 MIMO);
- `N_proc` — кількість сконфігурованих процесів HARQ (типово `16`);
- `M_limit` — константа обмеження (типово `8` у специфікаціях 3GPP).

Якщо розмір закодованого транспортного блоку `N_cb` перевищує `N_soft_per_process`, термінал переходить у режим **обмеженого буфера** (англ. *Limited Buffer Rate Matching*, LBRM), де надлишкові паритетні біти відкидаються, що запобігає переповненню SRAM чіпсета ціною незначної втрати кодового виграшу на 3-й та 4-й спробах.

## Сигнатури функцій програмного інтерфейсу (API)

Для інтеграції сутності HARQ з планувальником MAC (MAC Scheduler) та апаратним драйвером фізичного рівня (PHY Driver) стандартний стек реалізує такий набір функцій керування:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

/* Коди результатів виконання функцій HARQ API */
typedef enum {
    HARQ_OK = 0,
    HARQ_ERR_INVALID_PROCESS_ID,
    HARQ_ERR_NO_FREE_PROCESS,
    HARQ_ERR_BUFFER_OVERFLOW,
    HARQ_ERR_OUT_OF_SYNC_NDI,
    HARQ_ERR_MAX_RETRIES_REACHED
} HarqResult;

/* Ініціалізація сутності HARQ для конкретного користувацького термінала (UE) */
HarqResult harq_entity_init(uint16_t rnti, uint8_t num_processes, uint32_t total_soft_buffer_bytes);

/* Виділення вільного процесу HARQ для передачі нового блоку */
HarqResult harq_tx_allocate_process(uint16_t rnti, uint8_t *allocated_pid);

/* Підготовка дескриптора передачі (оновлює RV, інвертує NDI за потреби) */
HarqResult harq_tx_prepare_pdu(uint16_t rnti, uint8_t process_id, bool is_new_data, 
                              const uint8_t *payload, uint32_t tbs, HarqTxProcessDescriptor *out_desc);

/* Обробка отриманого сигналу зворотного зв'язку ACK/NACK/DTX від приймача */
HarqResult harq_tx_handle_feedback(uint16_t rnti, uint8_t process_id, HarqFeedback feedback);

/* Виконання софт-комбінування на приймачі (PHY LLR Combining) */
HarqResult harq_rx_combine_and_decode(uint16_t rnti, uint8_t process_id, bool received_ndi,
                                      HarqRedundancyVersion rv, const int8_t *rx_llr, 
                                      uint32_t llr_count, uint8_t *out_payload, bool *out_crc_pass);

/* Примусове скидання та очищення буфера процесу */
HarqResult harq_process_reset(uint16_t rnti, uint8_t process_id);
```
```cpp
#include <cstdint>
#include <span>
#include <expected>
#include <vector>

enum class HarqError : uint8_t {
    InvalidProcessId,
    NoFreeProcess,
    BufferOverflow,
    OutOfSyncNdi,
    MaxRetriesReached
};

class HarqEntity {
public:
    explicit HarqEntity(uint16_t rnti, uint8_t num_processes, uint32_t total_soft_buffer_bytes);

    // Виділення вільного процесу HARQ для передачі нового блоку
    [[nodiscard]] std::expected<uint8_t, HarqError> allocate_tx_process();

    // Підготовка дескриптора передачі
    [[nodiscard]] std::expected<HarqTxProcessDescriptor, HarqError> prepare_tx_pdu(
        uint8_t process_id, bool is_new_data, std::span<const uint8_t> payload, uint32_t tbs);

    // Обробка отриманого зворотного зв'язку від фізичного рівня
    [[nodiscard]] std::expected<void, HarqError> handle_feedback(uint8_t process_id, HarqFeedback feedback);

    // Софт-комбінування та запуск апаратного декодера
    [[nodiscard]] std::expected<bool, HarqError> combine_and_decode(
        uint8_t process_id, bool received_ndi, HarqRedundancyVersion rv,
        std::span<const int8_t> rx_llr, std::span<uint8_t> out_payload);

    // Скидання буфера
    void reset_process(uint8_t process_id);
};
```

## Формування звіту зворотного зв'язку (HARQ-ACK Codebook)

У сучасних системах зв'язку термінал часто приймає кілька транспортних блоків одночасно (через агрегацію несучих Carrier Aggregation, подвійні транспортні блоки в MIMO 2x2/4x4 або динамічне планування кількох слотів PDSCH поспіль).

Для ефективної передачі статусів усіх блоків в одному короткому повідомленні каналу PUCCH або PUSCH стандарт 3GPP визначає механізм **кодових книг підтверджень** (англ. *HARQ-ACK Codebook*):

### 1. Напівстатична кодова книга (Type-1 HARQ-ACK Codebook)
- Розмір бітового поля фіксований і визначається виключно конфігурацією RRC (кількістю несучих, максимальною кількістю MIMO-шарів та діапазоном затримок `K_1`);
- Термінал формує бітову карту (bitmap), де кожна позиція строго відповідає потенційному слоту PDSCH у часовому вікні;
- Якщо в певному слоті базова станція не передавала даних, термінал записує в цю позицію значення `NACK`;
- **Перевага:** абсолютна стійкість до втрат керуючих повідомлень DCI (базова станція завжди знає точну довжину та структуру звіту);
- **Недолік:** надлишкові витрати пропускної здатності зворотного каналу на порожні `NACK`.

### 2. Динамічна кодова книга (Type-2 HARQ-ACK Codebook)
- Розмір звіту динамічно підлаштовується під кількість реально призначених блоків PDSCH за допомогою **індикатора призначення низхідного каналу** (англ. *Downlink Assignment Index*, DAI);
- Поле DCI містить лічильник `cDAI` (Counter DAI, який рахує порядковий номер блоку в поточному вікні) та загальний лічильник `tDAI` (Total DAI, який повідомляє сумарну кількість переданих блоків);
- Термінал передає рівно стільки бітів `ACK`/`NACK`, скільки вказано в `tDAI`;
- Якщо термінал виявляє розрив у послідовності `cDAI` (наприклад, прийняв `cDAI = 1` та `cDAI = 3`, пропустивши `cDAI = 2`), він точно знає, що другий DCI був втрачений, і вставляє `NACK` у пропущену позицію.

## Таймінги зворотного зв'язку в дуплексі TDD (Time Division Duplex)

У системах із часовим розділенням каналів (TDD) прямий (DL) і зворотний (UL) канали розділені в часі на одній частоті.

```
Часовий кадр 5G NR TDD (Шаблон DDDSU):
Слот 0: [  DL  ] -> PDSCH (Процес HARQ #0)
Слот 1: [  DL  ] -> PDSCH (Процес HARQ #1)
Слот 2: [  DL  ] -> PDSCH (Процес HARQ #2)
Слот 3: [  S   ] -> Гнучкий слот (Спеціальний / Guard Period)
Слот 4: [  UL  ] -> PUCCH: Груповий звіт HARQ-ACK для процесів #0, #1, #2 (K_1 = 4, 3, 2)
```

Правила взаємодії:
1. Параметр DCI `K_1` динамічно призначає кожному процесу DL найближчий доступний слот UL;
2. Термінал повинен встигнути завершити демодуляцію, софт-комбінування та перевірку CRC до початку випромінювання слота `UL`. Мінімальний час обробки на стороні UE позначається `N_1` (залежить від нумерології піднесучих та обчислювальної спроможності чіпсета, типово `N_1 = 8–13` OFDM-символів);
3. Якщо час між кінцем PDSCH та початком PUCCH менший за `N_1`, термінал не встигає згенерувати валідний `ACK`/`NACK` і зобов'язаний виставити статус `DTX`.

## Адаптація каналу на основі статистики HARQ (Outer Loop Link Adaptation)

Статистика підтверджень HARQ використовується планувальником базової станції для безперервного автоматичного підстроювання схеми модуляції та кодування (MCS) під мінливі умови завад.

Цей алгоритм має назву **зовнішнього контуру адаптації лінії** (англ. *Outer Loop Link Adaptation*, OLLA):

```
                      ┌────────────────────────┐
                      │    Вхідний звіт CQI    │
                      └───────────┬────────────┘
                                  ▼
                     SNR_effective = CQI_SNR + Δ_OLLA
                                  │
                 ┌────────────────┴────────────────┐
                 │          Вибір MCS              │
                 │   (PDSCH випромінюється в ефір) │
                 └────────────────┬────────────────┘
                                  │
                       Зворотний зв'язок HARQ
                                  │
                 ┌────────────────┴────────────────┐
          ACK    ▼                                 ▼   NACK
     ┌───────────────────────┐         ┌───────────────────────┐
     │ Δ_OLLA += Step_Up     │         │ Δ_OLLA -= Step_Down   │
     │ (+0.05 дБ)            │         │ (-0.45 дБ)            │
     └───────────────────────┘         └───────────────────────┘
```

Розрахунок кроків зміни зміщення `Δ_OLLA`:

Цільова ймовірність блокової помилки (Target BLER) на першій спробі передачі вибирається рівною `Target_BLER = 10%` (`0.10`). Для забезпечення стаціонарного балансу кроки адаптації пов'язані формулою:

```
Step_Up · (1 - Target_BLER) = Step_Down · Target_BLER
Step_Up = Step_Down · (Target_BLER / (1 - Target_BLER))
```

Якщо `Step_Down = 0.45` дБ, то:
```
Step_Up = 0.45 · (0.10 / 0.90) = 0.45 · (1/9) = 0.05 дБ
```

Завдяки цьому співвідношенню 9 послідовних `ACK` піднімають оцінку якості каналу рівно на `+0.45` дБ, а один випадковий `NACK` миттєво знижує її на `-0.45` дБ, що утримує систему точно на межі 10% первинних помилок, оптимізуючи спектральну ефективність радіоінтерфейсу.

## Специфікація інтерфейсу Wi-Fi 802.11 Block Ack (BA)

У стандартах бездротових локальних мереж IEEE 802.11e/n/ac/ax/be для усунення накладних витрат на надсилання окремого `ACK` на кожен кадр MPDU застосовується механізм **блокового підтвердження** (англ. *Block Acknowledgment*, Block Ack):

```
       TX                                                      RX
       │                  MPDU #0 (Data)                       │
       ├──────────────────────────────────────────────────────►│
       │                  MPDU #1 (Data)                       │
       ├──────────────────────────────────────────────────────►│
       │                  MPDU #2 (Data)                       │
       ├──────────────────────────────────────────────────────►│
       │               ... до 64 MPDU в A-MPDU                 │
       │                  BlockAckReq (BAR)                    │
       ├──────────────────────────────────────────────────────►│
       │◄──────────────────────────────────────────────────────┤
       │             BlockAck (BA: 64-bit Bitmap)              │
```

### Структура кадру Block Ack у стеку Linux mac80211

Нижче наведено визначення структур дескрипторів Block Ack, які використовуються в ядрі Linux (підсистема `mac80211`):

:::tabs
```c
#include <stdint.h>

/* Керуючий заголовок кадру Block Ack */
typedef struct {
    uint16_t ba_control;        /* Біти: [0..0] Ack Policy, [1..4] Multi-TID, [5..15] Compressed */
    uint16_t starting_seq_ctrl; /* Біти: [0..3] Номер фрагмента (завжди 0), [4..15] Starting Seq Num */
    uint64_t ba_bitmap;         /* 64-бітова маска підтверджень: біт k = 1 означає успішний прийом MPDU (SSN + k) */
} __attribute__((packed)) Ieee80211BlockAckFrame;

/* Запит блокового підтвердження (Block Ack Request - BAR) */
typedef struct {
    uint16_t bar_control;       /* Керуючі прапорці TID та політики */
    uint16_t starting_seq_ctrl; /* Початковий номер послідовності (Starting Sequence Number - SSN) */
} __attribute__((packed)) Ieee80211BlockAckReqFrame;
```
```cpp
#include <cstdint>
#include <bitset>

struct Ieee80211BlockAckFrame {
    uint16_t ba_control = 0;
    uint16_t starting_seq_ctrl = 0;
    uint64_t ba_bitmap = 0;

    [[nodiscard]] uint16_t starting_sequence_number() const noexcept {
        return (starting_seq_ctrl >> 4) & 0x0FFF;
    }

    [[nodiscard]] bool is_mpdu_acked(uint16_t seq_num) const noexcept {
        uint16_t ssn = starting_sequence_number();
        uint16_t diff = (seq_num - ssn) & 0x0FFF;
        if (diff < 64) {
            return (ba_bitmap & (1ULL << diff)) != 0;
        }
        return false;
    }
};
```
:::

Семантика полів:
- `Starting Sequence Control`: 12-розрядне поле визначає початковий номер послідовності `SSN`, від якого відраховуються біти карти;
- `Block Ack Bitmap`: 64-розрядна бітова маска (у режимі Compressed BlockAck). Біт із номером `i` (від 0 до 63) встановлюється в `1`, якщо кадр із номером `(SSN + i) mod 4096` успішно прийнятий і пройшов перевірку CRC-32 (FCS).

## Регістровий інтерфейс апаратного прискорювача HARQ (Baseband SoC)

У сучасних телекомунікаційних процесорах та FPGA (Xilinx Zynq UltraScale+ RFSoC, NXP Layerscape) функції софт-комбінування та декодування LDPC винесені в апаратні прискорювачі (Hardware Accelerator Engines).

Драйвер взаємодіє з апаратним блоком через відображені в пам'ять регістри введення-виведення (MMIO):

| Зміщення регістру | Назва регістру | Бітова ширина | Призначення та бітові поля |
| :--- | :--- | :--- | :--- |
| `0x00` | `HARQ_CTRL_REG` | 32 біти | **Регістр керування:** біт [0] `ENABLE` (запуск блоку), біт [1] `START_COMBINE` (початок додавання LLR), біт [2] `CLEAR_BUFFER` (скидання при інверсії NDI), біти [4..7] `PROCESS_ID` (номер процесу 0..15). |
| `0x04` | `HARQ_RV_REG` | 32 біти | **Регістр версії надлишковості:** біти [0..1] `RV_INDEX` (значення 0, 1, 2, 3), біти [8..15] `MCS_INDEX` (схема модуляції для масштабування LLR). |
| `0x08` | `HARQ_LLR_ADDR_REG` | 32 біти | **Фізична адреса DMA буфера LLR:** вказівник у спільній пам'яті (SRAM), звідки апаратний блок зчитує вхідні м'які біти від демодулятора. |
| `0x0C` | `HARQ_OUT_ADDR_REG` | 32 біти | **Фізична адреса результату:** вказівник у пам'яті, куди записуються декодовані корисні байти після проходження перевірки CRC. |
| `0x10` | `HARQ_STATUS_REG` | 32 біти | **Регістр стану:** біт [0] `BUSY` (триває обчислення), біт [1] `CRC_PASS` (1 = успіх, 0 = помилка), біт [2] `MAX_ITER_REACHED` (декодер не зійшовся за ліміт ітерацій), біти [8..15] `ITER_COUNT` (фактична кількість ітерацій LDPC). |
| `0x14` | `HARQ_IRQ_MASK_REG` | 32 біти | **Маска переривань:** біт [0] `IRQ_DECODE_DONE` (генерація апаратного переривання CPU після завершення обробки). |

## Діагностика критичних збоїв сигналізації HARQ

При реалізації стека протоколів виділяють три типи критичних аномалій взаємодії MAC/PHY:

### 1. Помилка NACK-to-ACK (Критичне пошкодження даних)
- **Симптом:** Приймач не зміг декодувати блок і відправив `NACK` (або перебував у стані `DTX`), але через глибоке шумування базової станції сигнал у зворотному каналі був помилково розпізнаний як `ACK`.
- **Наслідок:** Рівень MAC базової станції вважає пакет доставленим, інвертує `NDI` і переходить до наступного транспортного блоку. Попередній пакет втрачається безповоротно на рівні L1/L2.
- **Відновлення:** Виявляється виключно вищим рівнем (RLC AM або TCP) за відсутністю порядкового номера, що викликає затримку відновлення на рівні RLC RTT (`20–50` мс).

### 2. Помилка ACK-to-NACK (Хибний повтор)
- **Симптом:** Приймач успішно декодував блок і відправив `ACK`, але базова станція прочитала його як `NACK`.
- **Наслідок:** Базова станція надсилає повторну версію надлишковості (наприклад, `RV2`) із тим самим `NDI`.
- **Відновлення:** Приймач бачить, що біт `NDI` не змінився, розуміє, що це дублікат уже виданого блоку, ігнорує дані, але повторно відправляє `ACK`, запобігаючи зацикленню.

### 3. Зависання процесу через втрату гранту (DTX State)
- **Симптом:** Термінал узагалі не зміг виявити свій DCI у каналі PDCCH (наприклад, через глибоке інтерференційне завмирання) і не передав жодного сигналу у відповідь (стан `DTX` — Discontinuous Transmission).
- **Наслідок:** Базова станція не фіксує енергії в каналі зворотного зв'язку і повинна повторити передачу з підвищеною потужністю PDCCH або змінити схему кодування MCS.

## Повторна передача на рівні груп кодових блоків (CBG-Based HARQ)

У стандартах 5G NR для гігабітних швидкостей передачі (eMBB) розмір одного транспортного блоку TBS сягає понад 1 Мбіт. Перед кодуванням такий велетенський блок розбивається на десятки незалежних кодових блоків LDPC (англ. *Code Blocks*, CB), кожен із яких захищений власною 24-бітною контрольною сумою CRC-24B.

У класичному TB-based HARQ пошкодження навіть одного біта в єдиному кодовому блоці змушує базову станцію повторно надсилати **весь гігабітний транспортний блок**, що призводить до колосального марнування смуги частот.

Для усунення цієї проблеми в 5G NR впроваджено механізм **CBG-based HARQ** (Code Block Group):

```
Транспортний блок TBS (наприклад, 32 кодових блоки CB):
┌───────────┬───────────┬───────────┬───────────┐
│   CBG #0  │   CBG #1  │   CBG #2  │   CBG #3  │
│ (CB 0..7) │ (CB 8..15)│(CB 16..23)│(CB 24..31)│
└─────┬─────┴─────┬─────┴─────┬─────┴─────┬─────┘
      │           │           │           │
     PASS       FAIL!        PASS        PASS
      │           │           │           │
      ▼           ▼           ▼           ▼
Звіт HARQ: [ 1 ]      [ 0 ]       [ 1 ]       [ 1 ]  (4-бітний вектор)
                  │
Повторна передача:  └─► Передається ТІЛЬКИ CBG #1 (економія 75% смуги!)
```

Конфігурація CBG в інформації DCI:
1. Параметр RRC `maxCodeBlockGroupsPerTransportBlock` задає поділ блоку на 2, 4, 6 або 8 груп CBG;
2. Поле DCI **CBGTI** (CBG Transmission Information) містить бітову маску, де кожен біт вказує, які саме групи CBG передаються в поточному слоті;
3. Поле DCI **CBGFI** (CBG Flushing Information) повідомляє приймачеві, чи потрібно очищати буфер LLR для кожної окремої групи CBG;
4. Зворотний звіт PUCCH містить індивідуальні біти `ACK`/`NACK` окремо для кожної групи CBG.

## Арифметична логіка софт-комбінування LLR та запобігання насиченню

При апаратному додаванні логарифмічних відношень правдоподібності `LLR_total = LLR_prev + LLR_new` значення квантуються фіксованою розрядністю (типово 8-бітний знаковий формат `int8_t` у діапазоні від `-128` до `+127`).

Звичайне цілочисельне переповнення (Integer Overflow) є катастрофічним: якщо сума двох сильних негативних LLR (`-80 + -70 = -150`) переповнить 8-бітний регістр, вона перетвориться на позитивне число `+106`, що призведе до інверсії рішення демодулятора з надійного «1» на хибний «0».

Апаратні та програмні блоки софт-комбінування зобов'язані використовувати **арифметику з насиченням** (англ. *Saturating Arithmetic*):

:::tabs
```c
#include <stdint.h>

/* Безпечне додавання LLR із насиченням у діапазоні [-127, +127] */
static inline int8_t harq_llr_saturating_add(int8_t prev, int8_t current) {
    int16_t sum = (int16_t)prev + (int16_t)current;
    if (sum > 127) return 127;
    if (sum < -127) return -127;
    return (int8_t)sum;
}
```
```cpp
#include <cstdint>
#include <algorithm>

// Безпечне додавання LLR із насиченням у діапазоні [-127, +127]
[[nodiscard]] constexpr int8_t harq_llr_saturating_add(int8_t prev, int8_t current) noexcept {
    const int16_t sum = static_cast<int16_t>(prev) + static_cast<int16_t>(current);
    return static_cast<int8_t>(std::clamp<int16_t>(sum, -127, 127));
}
```
:::

Використання симетричного діапазону `[-127, +127]` (з виключенням асиметричного значення `-128`) запобігає зсуву нульової точки рішень декодера та гарантує точне збереження енергетичного виграшу `+3 дБ` на кожній ітерації Chase Combining.
