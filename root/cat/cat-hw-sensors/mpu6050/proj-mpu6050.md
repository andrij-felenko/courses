# ⚙️ Драйвер MPU-6050: від сирих байтів до чесного кута нахилу

Читати з MPU-6050 сирі числа легко — розбудив, попросив чотирнадцять байтів, поділив на чутливість. Але сирі числа нахилу **не дають**. Акселерометр знає, де низ, лише коли плата стоїть; ворухнули її — і його «низ» стрибає від кожного поштовху. Гіроскоп дає гладку швидкість обертання, але сам по собі кута не тримає: його доводиться інтегрувати, а інтеграл повільно спливає. Тож справжня задача драйвера не «прочитати регістр», а **звести два недосконалі давачі в один чесний кут** — крен і тангаж, які не тремтять у спокої й не спливають у русі.

Тут три робочі шляхи, і всі три варто вміти. Найпростіший — покласти злиття **на сам чип**: усередині сидить DMP, який сам змішає осі й віддасть готову орієнтацію, треба лише навчитися дістати її з FIFO. Найпрозоріший — **комплементарний фільтр** на своєму мікроконтролері: п'ять рядків арифметики, і ти бачиш кожну цифру наскрізь. І окремо — **калібрування нуля гіроскопа** та **перевірка, що під тобою справжній чип, а не клон**, бо без цих двох дрібниць решта коду бреше тихо й переконливо.

Пройдемо всі три — з робочою прошивкою, яку можна залити й побачити результат.

> 🔧 **Навіщо драйвер, а не просто читання.** Кінцева мета MPU-6050 в 99 % проєктів — це **кут**: наскільки плата нахилена вперед-назад (тангаж, pitch) і вліво-вправо (крен, roll). Дрон утримує горизонт по цих двох кутах; самобалансний робот падав би без них щосекунди; стабілізатор камери жив саме ними. Сирі g і °/s — лише сировина; уся робота драйвера — перетворити її на кут, якому можна вірити і в спокої, і в русі.

## Шлях перший: бібліотека замість голого Wire

Голий `Wire` навчає механіки, але в реальному проєкті ніхто не пише адреси регістрів руками — беруть бібліотеку **MPU6050 Джеффа Роуберґа** (Jeff Rowberg), частину його збірки `i2cdevlib`. Це фактичний стандарт де-факто для цього чипа: вона ховає весь I2C-трафік за іменованими методами, знає карту всіх регістрів і — головне — вміє заряджати й читати DMP, що голим `Wire` зробити майже нереально (образ прошивки DMP — це понад тисяча байтів, які треба залити в особливому порядку).

Той самий сирий пакет, але вже через бібліотеку, виглядає так:

:::tabs

```cpp
#include <Wire.h>
#include <MPU6050.h>     // бібліотека Джеффа Роуберґа (i2cdevlib)

MPU6050 mpu;             // адреса за замовчуванням 0x68 (AD0 на землі)

int16_t ax, ay, az;      // сирі значення акселерометра
int16_t gx, gy, gz;      // сирі значення гіроскопа

void setup() {
    Serial.begin(115200);
    Wire.begin();

    mpu.initialize();    // будить чип і ставить типові діапазони (±2g, ±250°/s)

    // Перше, що робимо ЗАВЖДИ — питаємо, чи це взагалі наш чип.
    if (mpu.testConnection()) {
        Serial.println(F("MPU-6050 на місці"));
    } else {
        Serial.println(F("MPU-6050 НЕ відповідає — перевір пайку/адресу/клон"));
        while (1) { }    // далі йти немає сенсу
    }
}

void loop() {
    // Один виклик читає всі шість осей одним пакетом по I2C.
    mpu.getMotion6(&ax, &ay, &az, &gx, &gy, &gz);

    float accX = ax / 16384.0f;    // g   (при діапазоні ±2g)
    float gyrX = gx / 131.0f;      // °/s (при діапазоні ±250°/s)

    Serial.print(accX); Serial.print('\t');
    Serial.println(gyrX);
    delay(20);
}
```

```python
from machine import I2C, Pin
from time import sleep_ms
from struct import unpack_from

MPU = 0x68          # адреса за замовчуванням (AD0 на землі)
PWR_MGMT_1 = 0x6B
WHO_AM_I   = 0x75
ACCEL_XOUT = 0x3B   # звідси йдуть 14 байтів: 6 акс + 2 темп + 6 гіро

i2c = I2C(0, scl=Pin(22), sda=Pin(21))   # ніжки — під свою плату

def setup():
    i2c.writeto_mem(MPU, PWR_MGMT_1, b'\x00')   # розбудити (зняти біт SLEEP)
    sleep_ms(100)
    # Перше, що робимо ЗАВЖДИ — питаємо, чи це взагалі наш чип.
    if i2c.readfrom_mem(MPU, WHO_AM_I, 1)[0] == 0x68:
        print("MPU-6050 на місці")
    else:
        raise RuntimeError("MPU-6050 НЕ відповідає — перевір пайку/адресу/клон")

def loop():
    # Одне читання забирає всі шість осей одним пакетом по I2C.
    b = i2c.readfrom_mem(MPU, ACCEL_XOUT, 14)
    # >hhh h hhh — big-endian int16: ax,ay,az, temp, gx,gy,gz
    ax, ay, az = unpack_from(">hhh", b, 0)
    gx, gy, gz = unpack_from(">hhh", b, 8)

    acc_x = ax / 16384.0    # g   (при діапазоні ±2g)
    gyr_x = gx / 131.0      # °/s (при діапазоні ±250°/s)
    print(acc_x, gyr_x)
    sleep_ms(20)

setup()
while True:
    loop()
```

Порівняйте з голим варіантом — зникли `beginTransmission`, ручні зсуви байтів, `requestFrom`. Один `getMotion6()` робить усе те саме: посилає адресу регістра `ACCEL_XOUT_H`, робить повторний старт, забирає чотирнадцять байтів і розкладає їх на шість `int16_t` у правильному порядку (старший байт уперед). Це не «магія» — усередині той самий трафік, просто написаний раз і назавжди. Ділити на чутливість усе одно доводиться самому: бібліотека віддає **сирі** числа, бо не знає, який діапазон вам треба (за замовчуванням `initialize()` ставить ±2g і ±250 °/s, звідси константи 16384 і 131).

> 🔧 **Чому `testConnection()` — перший рядок, а не окраса.** Метод усередині читає регістр `WHO_AM_I` (0x75) і звіряє його з очікуваним 0x68. Дешеві модулі GY-521 масово підробляють, і клон може відповідати на I2C, але віддавати сміття або мовчати на половині регістрів. Якщо `testConnection()` повернув `false` — далі йти безглуздо: ви читатимете нулі або випадкові числа й годинами шукатимете «баг у коді», якого немає. Один `if` економить вечір.

## Шлях другий: готові кути з DMP через FIFO

Тепер найцікавіше — **DMP** (Digital Motion Processor). Це співпроцесор усередині MPU-6050, якому можна віддати всю чорну роботу зі злиття осей. Ви заливаєте в чип бінарний образ його прошивки, вмикаєте — і далі DMP **сам**, на власному такті, змішує акселерометр із гіроскопом і складає готову орієнтацію у **FIFO** (буфер «першим прийшов — першим пішов»). Ваш мікроконтролер лише витягує звідти готовий пакет і дістає з нього кути. Жодного фільтра писати не треба — злиття вже зроблене на кристалі.

DMP віддає орієнтацію як **кватерніон** — чотири числа `[w x y z]`, що описують поворот у просторі без вад кутів Ейлера (кватерніон не має «замка кардана» — виродження, коли дві осі збігаються й одна свобода обертання зникає). З кватерніона бібліотека рахує вектор «куди тяжіння» (`gravity`), а з нього — три звичні кути **yaw / pitch / roll** (курс / тангаж / крен).

Порядок роботи фіксований, і його варто знати напам'ять: `dmpInitialize()` заливає образ → задаємо зсуви нуля → калібруємо → `setDMPEnabled(true)` → у циклі тягнемо пакети:

```cpp
#include <Wire.h>
#include <MPU6050_6Axis_MotionApps20.h>   // варіант бібліотеки З підтримкою DMP

MPU6050 mpu;

uint8_t  fifoBuffer[64];   // сюди читаємо один пакет FIFO
uint16_t packetSize;       // розмір пакета DMP — дізнаємось у чипа
Quaternion q;              // кватерніон [w, x, y, z]
VectorFloat gravity;       // напрям тяжіння, відновлений із кватерніона
float ypr[3];              // yaw, pitch, roll — у РАДІАНАХ

void setup() {
    Serial.begin(115200);
    Wire.begin();
    Wire.setClock(400000);     // DMP любить швидку шину (400 кГц)

    mpu.initialize();
    if (!mpu.testConnection()) { Serial.println(F("немає чипа")); while (1); }

    // Заливаємо образ DMP у чип. Повертає 0, якщо все гаразд.
    uint8_t status = mpu.dmpInitialize();

    // Зсуви нуля — конкретні для КОЖНОГО екземпляра (див. розділ про калібрування).
    // Ці числа беруться з калібрувального прогону; тут — приклад.
    mpu.setXGyroOffset(220);
    mpu.setYGyroOffset(76);
    mpu.setZGyroOffset(-85);
    mpu.setZAccelOffset(1788);

    if (status == 0) {
        // Автоматичне тонке калібрування нуля (6 ітерацій — компроміс точність/час).
        mpu.CalibrateAccel(6);
        mpu.CalibrateGyro(6);
        mpu.setDMPEnabled(true);           // з цієї миті DMP сам пише у FIFO
        packetSize = mpu.dmpGetFIFOPacketSize();   // дізнаємось розмір пакета
        Serial.println(F("DMP готовий"));
    } else {
        // status 1 — не завантажилась память, 2 — не запустились налаштування DMP
        Serial.print(F("DMP не стартував, код ")); Serial.println(status);
        while (1);
    }
}

void loop() {
    // Тягнемо найсвіжіший цілий пакет із FIFO. Повертає true, якщо пакет є.
    // Ця функція сама впорається з переповненням FIFO (див. пастку нижче).
    if (mpu.dmpGetCurrentFIFOPacket(fifoBuffer)) {
        mpu.dmpGetQuaternion(&q, fifoBuffer);      // байти → кватерніон
        mpu.dmpGetGravity(&gravity, &q);           // кватерніон → напрям низу
        mpu.dmpGetYawPitchRoll(ypr, &q, &gravity); // → yaw/pitch/roll (радіани)

        // Переводимо в градуси: 180/π радіан у градусі.
        float yaw   = ypr[0] * 180.0f / M_PI;
        float pitch = ypr[1] * 180.0f / M_PI;
        float roll  = ypr[2] * 180.0f / M_PI;

        Serial.print(F("yaw "));   Serial.print(yaw, 1);
        Serial.print(F("  pitch ")); Serial.print(pitch, 1);
        Serial.print(F("  roll "));  Serial.println(roll, 1);
    }
}
```

Кілька речей тут навмисне не очевидні, і кожна — вистраждана.

**Пакет DMP — 42 байти, але не вгадуйте.** У класичному образі `MotionApps20` пакет займає рівно 42 байти (перші 16 — кватерніон, решта — сирі акселерометр і гіроскоп). Але ви **не пишете 42 у коді** — ви питаєте `dmpGetFIFOPacketSize()`, бо в інших версіях образу розмір інший, і зашите число одного дня мовчки зламається. Буфер `fifoBuffer[64]` беруть із запасом.

**`ypr` віддаються в радіанах.** DMP-функції рахують у радіанах — байдуже, зручно вам це чи ні. Множник `180/π ≈ 57.2958` переводить у градуси; тримайте його як `180.0f / M_PI`, а не як магічне «57.3», щоб намір читався з коду.

**Порядок yaw-pitch-roll фіксований масивом.** `ypr[0]` — завжди yaw (курс, обертання навколо вертикалі), `ypr[1]` — pitch (тангаж, ніс угору-вниз), `ypr[2]` — roll (крен, завал набік). Переплутати індекси легко, а наслідок — плата, що «нахиляється» не туди; підписуйте змінні одразу, як вище.

> 🔧 **Пастка переповнення FIFO.** DMP пише у FIFO **безперервно**, на своєму такті (типово 100–200 Гц). Якщо ваш `loop()` читає рідше, ніж DMP пише, буфер (усього 1024 байти) переповнюється — і далі йде **сміття**: пакети «зсуваються», кути починають смикатися й брехати. Старий код це ловив уручну (`getFIFOCount()`, `resetFIFO()`); сучасний `dmpGetCurrentFIFOPacket()` **сам** відкидає застарілі пакети й повертає лише найсвіжіший цілий — тому його й використовують. Головне правило все одно лишається: **не тримайте `delay()` у циклі з DMP** — будь-яка довга затримка переповнить FIFO.

Плюси DMP очевидні: злиття безкоштовне для головного процесора, кут стабільний «з коробки». Мінуси теж реальні: образ прошивки — закрита, реверс-інженерна «магія» (InvenSense офіційно її не документувала), налаштування примхливе, а yaw без магнетометра однаково спливає (бо курс нема від чого «прив'язати» — тяжіння не вказує на північ). Тому багато хто злиття робить **сам** — і це другий великий шлях.

## Шлях третій: комплементарний фільтр власноруч

DMP — чорна скринька. Якщо хочеться **розуміти**, звідки береться кут, і мати повний контроль — злиття пишуть на своєму мікроконтролері. Найпростіший і напрочуд ефективний спосіб — **комплементарний фільтр** (від «complementary» — доповняльний: дві частини доповнюють одна одну до цілого). Він робить рівно те, чого потребує пара «акселерометр + гіроскоп», і робить це одним рядком арифметики.

Ідея — двоходова. Спершу два способи дістати кут, кожен зі своєю вадою:

**Кут із акселерометра** — з розкладу вектора тяжіння по осях. Якщо плата нахилена, тяжіння (сталий 1g униз) проєктується на осі по-різному, і кут відновлюється через арктангенс. Для крену (roll, завал набік) і тангажа (pitch, ніс угору-вниз):

```
roll_acc  = atan2( ay, az ) · 180/π      // °, з проєкцій тяжіння
pitch_acc = atan2( -ax, √(ay² + az²) ) · 180/π
```

Цей кут **абсолютний і без дрейфу** — тяжіння нікуди не дінеться, тож у спокої він точний назавжди. Але він **шумить** і **бреше під час руху**: будь-яке прискорення (поштовх, гальмування) додається до тяжіння, і `atan2` дає хибний нахил.

**Кут із гіроскопа** — інтегруванням кутової швидкості. Гіроскоп каже, **як швидко** плата повертається (°/s); помноживши на крок часу `dt`, дістаємо приріст кута й додаємо до попереднього:

```
roll_gyro = roll_попередній + gx · dt      // gx у °/s, dt у секундах
```

Цей кут **гладкий і не боїться поштовхів** (гіроскоп байдужий до лінійного прискорення). Але він **повільно спливає**: крихітна стала похибка нуля, накопичуючись інтегралом, за хвилини перетворює кут на нісенітницю.

Тепер сама злука — **важена сума** двох оцінок:

```
кут = α · (кут_попередній + gx · dt)  +  (1 − α) · roll_acc
       └──── гіроскоп веде коротко ────┘    └─ акселерометр підправляє повільно ─┘
```

Уся суть — у коефіцієнті **α** (типово 0.98). Він робить фільтр **частотним розділювачем**: гіроскопу віддають **швидкі, короткі** зміни (98 % ваги — його гладкий приріст), а акселерометру лишають **повільне підтягування** до справжнього «низу» (2 % ваги на кожному кроці). Швидкий шум акселерометра гаситься його малою вагою; повільний дрейф гіроскопа гаситься тим, що акселерометр раз у раз тягне кут назад до правди. Кожен закриває слабину іншого — рівно те, задля чого в чипі два давачі.

Ось робоча прошивка комплементарного фільтра на голому `Wire` (щоб було видно кожну цифру), із вимірюванням реального `dt`:

:::tabs

```cpp
#include <Wire.h>
#include <MPU6050.h>

MPU6050 mpu;

int16_t ax, ay, az, gx, gy, gz;

float roll = 0, pitch = 0;      // поточні злиті кути, °
float gyroBiasX = 0, gyroBiasY = 0;   // нуль гіроскопа (з калібрування)
uint32_t tPrev = 0;

const float ALPHA = 0.98f;      // вага гіроскопа у злитті

void setup() {
    Serial.begin(115200);
    Wire.begin();
    mpu.initialize();
    if (!mpu.testConnection()) { Serial.println(F("немає чипа")); while (1); }

    calibrateGyro();            // виміряти нуль гіроскопа (див. нижче)
    tPrev = micros();
}

void loop() {
    mpu.getMotion6(&ax, &ay, &az, &gx, &gy, &gz);

    // Реальний крок часу в секундах (micros() — мікросекунди).
    uint32_t now = micros();
    float dt = (now - tPrev) * 1e-6f;
    tPrev = now;

    // --- кут з акселерометра (абсолютний, шумний) ---
    float axg = ax / 16384.0f, ayg = ay / 16384.0f, azg = az / 16384.0f;
    float rollAcc  = atan2f(ayg, azg) * 180.0f / M_PI;
    float pitchAcc = atan2f(-axg, sqrtf(ayg*ayg + azg*azg)) * 180.0f / M_PI;

    // --- кутова швидкість з гіроскопа, з відрахованим нулем (°/s) ---
    float rateX = (gx - gyroBiasX) / 131.0f;
    float rateY = (gy - gyroBiasY) / 131.0f;

    // --- комплементарне злиття ---
    roll  = ALPHA * (roll  + rateX * dt) + (1.0f - ALPHA) * rollAcc;
    pitch = ALPHA * (pitch + rateY * dt) + (1.0f - ALPHA) * pitchAcc;

    Serial.print(F("roll "));  Serial.print(roll, 1);
    Serial.print(F("  pitch ")); Serial.println(pitch, 1);
    // БЕЗ delay(): точність фільтра залежить від частого, рівного циклу.
}
```

```python
from machine import I2C, Pin
from time import ticks_us, ticks_diff
from struct import unpack_from
from math import atan2, sqrt, pi

MPU = 0x68
ACCEL_XOUT = 0x3B

i2c = I2C(0, scl=Pin(22), sda=Pin(21))

roll = 0.0
pitch = 0.0
gyro_bias_x = 0.0
gyro_bias_y = 0.0     # нуль гіроскопа (з калібрування)

ALPHA = 0.98          # вага гіроскопа у злитті

def read6():
    b = i2c.readfrom_mem(MPU, ACCEL_XOUT, 14)
    ax, ay, az = unpack_from(">hhh", b, 0)
    gx, gy, gz = unpack_from(">hhh", b, 8)
    return ax, ay, az, gx, gy, gz

calibrate_gyro()          # виміряти нуль гіроскопа (див. нижче)
t_prev = ticks_us()

while True:
    ax, ay, az, gx, gy, gz = read6()

    # Реальний крок часу в секундах (ticks_us() — мікросекунди).
    now = ticks_us()
    dt = ticks_diff(now, t_prev) * 1e-6
    t_prev = now

    # --- кут з акселерометра (абсолютний, шумний) ---
    axg, ayg, azg = ax / 16384.0, ay / 16384.0, az / 16384.0
    roll_acc  = atan2(ayg, azg) * 180.0 / pi
    pitch_acc = atan2(-axg, sqrt(ayg*ayg + azg*azg)) * 180.0 / pi

    # --- кутова швидкість з гіроскопа, з відрахованим нулем (°/s) ---
    rate_x = (gx - gyro_bias_x) / 131.0
    rate_y = (gy - gyro_bias_y) / 131.0

    # --- комплементарне злиття ---
    roll  = ALPHA * (roll  + rate_x * dt) + (1.0 - ALPHA) * roll_acc
    pitch = ALPHA * (pitch + rate_y * dt) + (1.0 - ALPHA) * pitch_acc

    print("roll", round(roll, 1), " pitch", round(pitch, 1))
    # БЕЗ sleep: точність фільтра залежить від частого, рівного циклу.
```

:::

**Приклад: як фільтр гасить поштовх.** Плата лежить рівно (`roll ≈ 0`), і хтось стукнув по столу. Акселерометр на мить показав, ніби плата хитнулась на 30° (`rollAcc = 30`), хоча вона не рухалась. Гіроскоп при цьому мовчить (`rateX ≈ 0`), бо реального обертання не було.

```c
// Один крок фільтра під час хибного стрибка акселерометра:
//   roll_попередній = 0.0
//   rateX · dt      = 0.0   (гіроскоп каже: обертання нема)
//   rollAcc         = 30.0  (акселерометр збрехав від поштовху)
//   α = 0.98
//
//   roll = 0.98 · (0.0 + 0.0) + 0.02 · 30.0
//        = 0.6°
//
// Замість стрибка на 30° кут ворухнувся лише на 0.6° — і наступними
// кроками, коли акселерометр заспокоївся, тихо повернувся до нуля.
```

Хибний стрибок на 30° перетворився на ледь помітні 0.6° — бо акселерометру віддали лише 2 % ваги. А якби плата **справді** повільно нахилялась, гіроскоп вів би кут точно, і ті самі 2 % акселерометра лише не давали б йому спливти. Оце й є магія одного коефіцієнта.

> 🔧 **DMP чи свій фільтр — що обрати.** DMP — коли треба «щоб просто працювало» і шкода тактів головного процесора: залив, увімкнув, читай кути. Свій комплементарний фільтр — коли треба **розуміти й керувати**: підкрутити α, додати свою логіку, портувати на будь-який мікроконтролер без реверс-інженерного образу. Комплементарний фільтр здається грубішим за DMP чи фільтр Калмана, але на практиці для нахилу дає майже той самий результат за незрівнянно меншу складність — тому з нього й починають. [Сенсорне злиття](root:com-signal/sensor-fusion) як загальний принцип — окрема глибша тема; тут — його найпростіше робоче втілення.

## Калібрування нуля гіроскопа: чому без нього дрейф швидший

У всіх прикладах вище була рядок `gx - gyroBiasX` або виклик `calibrateGyro()`. Це не формальність — це те, без чого гіроскопний кут спливає **в рази** швидше.

Проблема ось у чім. Ідеальний гіроскоп у спокої показує рівно нуль. Реальний — показує маленьке **стале зміщення** (bias, зсув нуля): наприклад, `gx ≈ +18` навіть коли плата нерухома. Саме по собі число дрібне — це ≈ 0.14 °/s хибної «швидкості». Але фільтр його **інтегрує**: 0.14 °/s, накопичуючись, дає **8° дрейфу за хвилину** нізвідки. Відняли зсув — і дрейф падає до частки градуса.

Знайти зсув просто: покласти плату **нерухомо**, зняти сотні-тисячі зразків і **усереднити** — те, що лишилось, і є нуль, який треба віднімати завжди.

:::tabs

```cpp
void calibrateGyro() {
    const int N = 2000;              // скільки зразків усереднити
    long sumX = 0, sumY = 0, sumZ = 0;

    Serial.println(F("Калібрую гіроскоп — НЕ РУХАЙ плату 5 секунд..."));
    delay(1000);                     // дати руці прибратись, платі — заспокоїтись

    for (int i = 0; i < N; i++) {
        mpu.getMotion6(&ax, &ay, &az, &gx, &gy, &gz);
        sumX += gx;  sumY += gy;  sumZ += gz;
        delay(2);                    // ~2 мс між зразками
    }

    gyroBiasX = sumX / (float)N;     // середнє = сталий зсув нуля
    gyroBiasY = sumY / (float)N;
    // gyroBiasZ = sumZ / (float)N;  // за потреби

    Serial.print(F("Зсув нуля гіроскопа: "));
    Serial.print(gyroBiasX); Serial.print(' ');
    Serial.println(gyroBiasY);
}
```

```python
def calibrate_gyro():
    global gyro_bias_x, gyro_bias_y
    N = 2000                          # скільки зразків усереднити
    sum_x = sum_y = sum_z = 0

    print("Калібрую гіроскоп — НЕ РУХАЙ плату 5 секунд...")
    sleep_ms(1000)                    # дати руці прибратись, платі — заспокоїтись

    for _ in range(N):
        _, _, _, gx, gy, gz = read6()
        sum_x += gx;  sum_y += gy;  sum_z += gz
        sleep_ms(2)                   # ~2 мс між зразками

    gyro_bias_x = sum_x / N           # середнє = сталий зсув нуля
    gyro_bias_y = sum_y / N
    # gyro_bias_z = sum_z / N         # за потреби

    print("Зсув нуля гіроскопа:", gyro_bias_x, gyro_bias_y)
```

:::

Три застереження, кожне з крові:

- **Плата мусить бути справді нерухома.** Усереднюємо в припущенні «істинна швидкість = 0». Ворухнули під час калібрування — і в зсув затесається реальне обертання, після чого фільтр «знатиме» хибний нуль і дрейфуватиме гірше, ніж без калібрування взагалі.
- **Гіроскоп калібрують після прогріву й повторюють.** Зсув нуля **пливе з температурою** — холодний щойно ввімкнений чип має один зсув, теплий за десять хвилин — інший. Для точних задач калібрують уже прогрітий чип, а іноді й час від часу переміряють.
- **Акселерометр так не калібрують.** У акселерометра нуль по вертикалі — **не нуль, а 1g** (тяжіння). Усереднивши його «в спокої» й віднявши, ви прибрали б саме тяжіння — тобто те, чим міряється нахил. Для акселерометра калібрують інакше (шість положень граней), і це окрема історія; тут — тільки гіроскоп.

У DMP-шляху те саме роблять методи `CalibrateGyro()` / `setXGyroOffset()` — ідея точно та ж, лише зсуви заряджають прямо в чип, а не віднімають у коді. Числа зсувів у прикладі DMP (`220, 76, -85, 1788`) — саме результат такого прогону для конкретного екземпляра; **чужі числа не підходять**, для кожної плати свої.

## Пастка клонів: WHO_AM_I, який бреше

Ринок GY-521 наводнений клонами. Чип коштує копійки, попит величезний — і під виглядом MPU-6050 продають то стару ревізію, то зовсім інший кристал у тому ж корпусі. Зовні не відрізнити; коштує драйверу — годин.

Перша лінія оборони — **WHO_AM_I** (регістр 0x75). Справжній MPU-6050 віддає рівно **0x68**. Це і робить `testConnection()` усередині. Але тут криється підступ, вартий окремого слова.

> 🔧 **Чому 0x68 у WHO_AM_I — не гарантія оригіналу.** У MPU-6050 регістр `WHO_AM_I` за проєктом віддає лише **біти 6:1** адреси, а біти 0 і 7 зафіксовані нулем. Через це **різні** чипи родини (і MPU-6000, і частина клонів на кшталт поширеного двійника, що маскується під оригінал) віддають те саме 0x68 — тобто підробка може **пройти** просту перевірку. Тому 0x68 означає лише «щось із родини на місці й відповідає», а не «це справжній InvenSense MPU-6050». Значення `0x98`, `0x72`, `0x7F` чи `0x00` — це вже явний клон або зовсім інший чип; а от 0x68 сам по собі оригінальність не доводить.

Що з цим робити на практиці:

:::tabs

```cpp
uint8_t who = mpu.getDeviceID();   // читає біти 6:1 регістра WHO_AM_I (0x75)

if (who == 0x34) {                 // getDeviceID повертає саме ці 6 біт → 0x34
    Serial.println(F("WHO_AM_I збігся — чип родини на місці"));
} else {
    Serial.print(F("WHO_AM_I підозрілий: 0x"));
    Serial.println(who, HEX);      // 0x00 → мертвий/непідключений; інше → клон
}
```

```python
# Повний байт WHO_AM_I у MicroPython читаємо напряму — тут це 0x68.
who = i2c.readfrom_mem(MPU, 0x75, 1)[0]   # регістр WHO_AM_I (0x75)

if who == 0x68:                    # повний байт регістра справжнього чипа
    print("WHO_AM_I збігся — чип родини на місці")
else:
    # 0x00 → мертвий/непідключений; інше → клон
    print("WHO_AM_I підозрілий: 0x{:02X}".format(who))
```

:::

Тут іще одна тонкість неймінгу, на якій спотикаються: метод `getDeviceID()` бібліотеки повертає **не** 0x68, а **0x34** — бо він віддає ті самі біти 6:1 **вирівняними праворуч** (0x68 зсунуте на один біт: 0x68 = `0110 1000`, біти 6:1 = `011 0100` = 0x34). А `testConnection()` порівнює саме з цим 0x34 усередині. Тобто «0x68» — це повний байт регістра, а «0x34» — та ж інформація, вже зсунута; обидва числа правильні, просто в різних місцях бібліотеки.

Практичні ознаки, що під вами клон, навіть якщо WHO_AM_I «збігся»:

- **Мовчазні або дзеркальні регістри.** Клон часто ігнорує запис у частину регістрів або віддає одне й те саме на різні адреси. Записали діапазон ±8g, а числа поводяться як на ±2g — верхнім давачем підробки.
- **DMP не заводиться.** Багато клонів не мають робочого DMP: `dmpInitialize()` повертає ненульовий код або кути з FIFO — сміття. Оригінал заводиться стабільно.
- **Дикий шум або зміщений нуль**, який не прибирається калібруванням.
- **Температурний канал бреше** — віддає сталу або абсурдну величину.

Мораль проста, і вона наскрізна для дешевого заліза: **не довіряйте платі наосліп**. Читайте WHO_AM_I на старті, звіряйте поведінку з даташитом, а якщо кути «майже працюють, але дивно» — перш ніж годинами копати код, спитайте себе, чи справжній під вами чип. Драйвер, написаний бездоганно, однаково бреше, якщо кристал під ним — не той.

## Що з усього цього складається

Три шляхи — не альтернативи «або-або», а сходинки розуміння. **Голий `Wire`** показує механіку: адреса, повторний старт, порядок байтів. **Бібліотека Роуберґа** прибирає рутину й відкриває DMP. **DMP** дає готовий кут майже безкоштовно, але як чорна скринька. **Комплементарний фільтр** повертає контроль і робить злиття прозорим до останньої цифри. А **калібрування** й **перевірка WHO_AM_I** — це той дрібний фундамент, без якого будь-який із трьох шляхів тихо бреше.

Спільна нитка одна: сирі числа з MPU-6050 — лише сировина, а корисний вихід — **чесний кут**, зведений із двох недосконалих давачів. Хто це зрозумів, той однаково впевнено дістане кут і з DMP через FIFO, і п'ятьма рядками власного фільтра — а трапиться клон, помітить його на першому ж читанні WHO_AM_I, а не на третій годині відлагодження.
