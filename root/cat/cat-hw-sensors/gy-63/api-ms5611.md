# 📋 MS5611 напряму: команди, PROM, CRC-4 і формули компенсації

<preknowlist>
- [Шина I2C](topic:com-devices/i2c-bus) — дві лінії SDA/SCL, ведучий шле адресу й байти, ведений відповідає ACK/NACK: на цьому стоїть кожен рядок обміну нижче.
- [Адресація I2C](topic:com-devices/i2c-addressing) — 7-бітна адреса пристрою, читання проти запису; MS5611 сидить на `0x76` або `0x77` залежно від піна `CSB`.
- [CRC — циклічний надлишковий код](topic:com-modulation/crc) — як кілька байтів згортають у контрольне число, щоб зловити зіпсований біт; калібрувальна пам'ять давача несе таку 4-бітну суму.
- [Переповнення цілих](topic:sf-lang/overflow-wraparound) — чому 32-бітна змінна тихо «завертається» на великому добутку і що дає перехід на 64 біти: без цього компенсація MS5611 бреше.
</preknowlist>

MS5611 — не «прочитав тиск і готово». Давач віддає два сирих 24-бітних числа й шість заводських коефіцієнтів, а мілібари ви **обчислюєте самі** — у цілій арифметиці, частину якої **обов'язково** тримати 64-бітною, інакше проміжний добуток переповнюється й тиск виходить безглуздий. Це довідник по тому, як розмовляти з мікросхемою напряму: які однобайтові команди вона розуміє, як влаштована її калібрувальна пам'ять (PROM) і як перевірити її цілість, у якому порядку приходять байти, і за якими формулами сирі `D1`, `D2` та `C1…C6` перетворюються на градуси й мілібари.

Сирий обмін потрібен, коли готова бібліотека не підходить: не влазить у пам'ять крихітного МК, ви пишете під ядро без Arduino-обгортки (ESP-IDF, RTOS, голий регістровий доступ), працюєте по SPI або хочете власну перевірку контрольної суми пам'яті при старті. Якщо ж завдання — просто підняти робочий барометр на готовій бібліотеці, почніть із [прикладу коду для GY-63](topic:cat-hw-sensors/gy-63/proj-ms5611.md); сюди повертайтесь, коли захочете розуміти й лагодити кожен байт на шині.

Весь код — справжній C. Сама послідовність байтів на шині однакова на будь-якому мікроконтролері: та сама адреса, ті самі команди, та сама пауза; різняться лише виклики, якими конкретне середовище шле байт, чекає й забирає відповідь. Тому кожен приклад дано трьома вкладками — Arduino-ядро (`Wire`), ESP-IDF (`driver/i2c.h`) і STM32 HAL (`HAL_I2C_*`); беріть свою, логіка в усіх трьох та сама. Це не псевдокод для ілюстрації — його можна скопіювати в проєкт і зібрати.

## Протокол крок за кроком: скид, PROM, АЦП, компенсація

Уся робота вкладається в кілька дій, і їхній порядок фіксований: **при старті** — скид і одноразове читання коефіцієнтів; **у циклі** — запуск перетворення, пауза, читання АЦП, обчислення.

### Команди й адреса

MS5611 розуміє маленький набір однобайтових команд. Ось ті, що нам потрібні:

```
0x1E                 — Reset (скид; перезавантажує калібрувальну пам'ять у робочі регістри)
0x40 + OSR·2         — запуск перетворення тиску   D1  (Convert D1)
0x50 + OSR·2         — запуск перетворення темпер.  D2  (Convert D2)
0x00                 — читання результату АЦП (24 біти)
0xA0                 — читання слова PROM #0 (заводські дані + CRC-4)
0xA2, 0xA4, … 0xAC   — читання коефіцієнтів C1…C6 (слова #1…#6)
0xAE                 — читання слова PROM #7 (містить CRC-4 у молодшому ніблі)
```

Дрібниця, на якій легко спіткнутися: код OSR у команді запуску йде **зсунутим на біт**, тобто множиться на 2. П'ять режимів кодуються як `0, 2, 4, 6, 8`, тому команда запуску тиску пробігає значення `0x40, 0x42, 0x44, 0x46, 0x48`, а температури — `0x50 … 0x58`. Це видно і в бібліотеці: вона будує команду як `0x40 | (bits)`, де `bits` уже парне.

Адреса давача на шині — `0x76` або `0x77`, і вирішує це пін `CSB`: вільний або на землі → `0x77`, на живлення → `0x76`. Жодного джампера в самій мікросхемі немає; це просто рівень на ніжці, який читається як молодший біт адреси.

### Крок 0 — скид і читання калібрувальної пам'яті

При старті ведучий шле байт скиду `0x1E` і чекає близько 3 мс, поки давач перекладе калібрувальну пам'ять (PROM) у робочі регістри. Далі — читання шести коефіцієнтів. Кожне слово PROM — це **16 бітів**, тому на команду `0xA2` давач віддає **два байти** (старший, потім молодший), які треба скласти в `uint16_t`. Коефіцієнти незмінні, тож це робиться **раз** за все життя прошивки.

:::tabs
```arduino
#include <Wire.h>

static const uint8_t MS5611_ADDR = 0x77;   // 0x76, якщо CSB на VCC

static const uint8_t CMD_RESET    = 0x1E;
static const uint8_t CMD_CONV_D1  = 0x40;   // тиск;  до цього додається OSR·2
static const uint8_t CMD_CONV_D2  = 0x50;   // темпер.; до цього додається OSR·2
static const uint8_t CMD_ADC_READ = 0x00;
static const uint8_t CMD_PROM_BASE= 0xA0;   // A0..AE — 8 слів по 16 біт

// Тут зберігатимемо весь PROM: [0]=reserved+CRC-nibble, [1..6]=C1..C6, [7]=serial+CRC.
uint16_t g_prom[8];

// Скид давача.
static bool ms5611_reset() {
  Wire.beginTransmission(MS5611_ADDR);
  Wire.write(CMD_RESET);
  bool ok = (Wire.endTransmission() == 0);
  delay(3);            // ~2.8 мс на перезавантаження PROM у регістри
  return ok;
}

// Прочитати одне 16-бітне слово PROM за індексом 0..7.
static bool ms5611_read_prom_word(uint8_t index, uint16_t *out) {
  Wire.beginTransmission(MS5611_ADDR);
  Wire.write(CMD_PROM_BASE + index * 2);      // A0, A2, A4, ... AE
  if (Wire.endTransmission() != 0) return false;

  if (Wire.requestFrom((int)MS5611_ADDR, 2) != 2) return false;
  uint8_t hi = Wire.read();
  uint8_t lo = Wire.read();
  *out = ((uint16_t)hi << 8) | lo;            // старший байт першим
  return true;
}

// Прочитати весь PROM (8 слів) у g_prom[]. Викликається раз при старті.
static bool ms5611_read_prom() {
  for (uint8_t i = 0; i < 8; i++) {
    if (!ms5611_read_prom_word(i, &g_prom[i])) return false;
  }
  return true;
}
```

```esp-idf
#include "driver/i2c.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

#define I2C_PORT      I2C_NUM_0
#define MS5611_ADDR   0x77          // 0x76, якщо CSB на VCC
#define I2C_TMO       pdMS_TO_TICKS(100)

#define CMD_RESET      0x1E
#define CMD_CONV_D1    0x40         // тиск;   до цього додається OSR·2
#define CMD_CONV_D2    0x50         // темпер.; до цього додається OSR·2
#define CMD_ADC_READ   0x00
#define CMD_PROM_BASE  0xA0         // A0..AE — 8 слів по 16 біт

// Тут зберігатимемо весь PROM: [0]=reserved+CRC-nibble, [1..6]=C1..C6, [7]=serial+CRC.
uint16_t g_prom[8];

// Скид давача.
static esp_err_t ms5611_reset(void) {
    uint8_t cmd = CMD_RESET;
    esp_err_t err = i2c_master_write_to_device(I2C_PORT, MS5611_ADDR, &cmd, 1, I2C_TMO);
    vTaskDelay(pdMS_TO_TICKS(5));   // ~2.8 мс на перезавантаження PROM у регістри
    return err;
}

// Прочитати одне 16-бітне слово PROM за індексом 0..7.
// write_read_device = запис команди, повторний старт, читання — один виклик.
static esp_err_t ms5611_read_prom_word(uint8_t index, uint16_t *out) {
    uint8_t cmd = CMD_PROM_BASE + index * 2;    // A0, A2, A4, ... AE
    uint8_t buf[2];
    esp_err_t err = i2c_master_write_read_device(I2C_PORT, MS5611_ADDR,
                                                 &cmd, 1, buf, 2, I2C_TMO);
    if (err != ESP_OK) return err;
    *out = ((uint16_t)buf[0] << 8) | buf[1];    // старший байт першим
    return ESP_OK;
}

// Прочитати весь PROM (8 слів) у g_prom[]. Викликається раз при старті.
static esp_err_t ms5611_read_prom(void) {
    for (uint8_t i = 0; i < 8; i++) {
        esp_err_t err = ms5611_read_prom_word(i, &g_prom[i]);
        if (err != ESP_OK) return err;
    }
    return ESP_OK;
}
```

```stm32
// HAL чекає 8-бітну адресу: 7-бітну зсуваємо вліво, молодший біт — R/W.
#define MS5611_ADDR   (0x77 << 1)           // (0x76 << 1), якщо CSB на VCC
#define I2C_TMO       100                   // мс на транзакцію

#define CMD_RESET      0x1E
#define CMD_CONV_D1    0x40                 // тиск;   до цього додається OSR·2

uint16_t g_prom[8];

// Скид давача.
static bool ms5611_reset(void) {
  uint8_t cmd = CMD_RESET;
  if (HAL_I2C_Master_Transmit(&hi2c1, MS5611_ADDR, &cmd, 1, I2C_TMO) != HAL_OK) return false;
  HAL_Delay(5);            // ~2.8 мс на перезавантаження PROM у регістри
  return true;
}

  uint8_t cmd = CMD_PROM_BASE + index * 2;  // A0, A2, A4, ... AE
  uint8_t buf[2];
  if (HAL_I2C_Master_Transmit(&hi2c1, MS5611_ADDR, &cmd, 1, I2C_TMO) != HAL_OK) return false;
  if (HAL_I2C_Master_Receive(&hi2c1, MS5611_ADDR, buf, 2, I2C_TMO) != HAL_OK) return false;
  *out = ((uint16_t)buf[0] << 8) | buf[1];  // старший байт першим
  return true;
}

// Прочитати весь PROM (8 слів) у g_prom[]. Викликається раз при старті.
static bool ms5611_read_prom(void) {
  for (uint8_t i = 0; i < 8; i++) {
    if (!ms5611_read_prom_word(i, &g_prom[i])) return false;
  }
  return true;
}
```

Порядок байтів тут — не дрібниця, а перша з класичних пасток. MS5611 віддає **старший байт першим** (big-endian), і якщо скласти навпаки (`lo << 8 | hi`), коефіцієнти вийдуть спотворені, а тиск — безглуздий. Та сама увага знадобиться при читанні 24-бітного АЦП.

### Серце надійності: перевірка CRC-4 калібрувальної пам'яті

Ми прочитали вісім слів PROM, але звідки певність, що прочитали **правильно**? Довгі дроти на макетній платі, наведення від мотора поряд — і один біт у коефіцієнті перевернеться. Спотворений коефіцієнт не дасть помилки й не дасть нуля: він дасть **правдоподібний, але хибний** тиск, який ви прийматимете за правду до кінця сесії, бо коефіцієнти читаються раз і більше не перечитуються. Саме тому виробник зашив у PROM **4-бітну контрольну суму** (CRC-4): вона обчислена на заводі з семи слів, лежить у молодшому ніблі восьмого слова, і ведучий може порахувати її сам і звірити. Зійшлося — пам'ять ціла; ні — читання пошкоджене, і працювати з такими коефіцієнтами не можна.

Алгоритм TE Connectivity канонічний і виглядає незвично: він рахує CRC не побайтово, а прокручує всі **16 байтів** восьми слів через 16-бітний регістр із поліномом `0x3000`, попередньо занулив ніблі самої суми у восьмому слові (інакше сума рахувалася б «сама від себе»). Ось він, слово в слово з довідкового драйвера виробника, лише з українськими коментарями:

```cpp
// CRC-4 для PROM MS5611 (алгоритм TE Connectivity, AN520).
// Приймає масив 8 слів; повертає true, якщо обчислена сума збіглася із зашитою.
bool ms5611_prom_crc_ok(uint16_t *prom) {
  uint16_t n_rem = 0x00;               // робочий 16-бітний залишок (CRC-регістр)
  uint16_t crc_read = prom[7];         // запам'ятати слово з зашитою сумою
  uint8_t  crc_expected = prom[7] & 0x000F;   // сама CRC-4 — молодший нібл

  prom[7] = prom[7] & 0xFF00;          // занулити нібл суми ПЕРЕД обчисленням

  for (uint8_t cnt = 0; cnt < 16; cnt++) {     // 16 байтів = 8 слів
    if (cnt % 2 == 1)
      n_rem ^= (uint16_t)(prom[cnt >> 1] & 0x00FF);   // непарний крок — молодший байт
    else
      n_rem ^= (uint16_t)(prom[cnt >> 1] >> 8);       // парний крок — старший байт

    for (uint8_t bit = 8; bit > 0; bit--) {
      if (n_rem & 0x8000)
        n_rem = (n_rem << 1) ^ 0x3000;    // старший біт = 1 → зсув + XOR з поліномом
      else
        n_rem = (n_rem << 1);             // інакше просто зсув
    }
  }

  n_rem = (n_rem >> 12) & 0x000F;      // готова CRC-4 — старші 4 біти залишку
  prom[7] = crc_read;                  // відновити слово (ми його псували маскою)

  return (n_rem == crc_expected);
}
```

Три місця варті окремого слова, бо саме на них плутаються при переписуванні.

**Занулення нібла перед обчисленням.** Рядок `prom[7] = prom[7] & 0xFF00` — не косметика: якщо лишити молодший байт восьмого слова як є, у розрахунок увійде сама контрольна сума, і результат не збіжиться ніколи. Тому суму спершу дістаємо (`& 0x000F`), потім затираємо той байт нулями, а наприкінці слово відновлюємо — щоб не зіпсувати `g_prom` для наступних викликів.

**Порядок байтів у циклі.** Парні кроки беруть старший байт слова (`>> 8`), непарні — молодший (`& 0x00FF`). Це прямий наслідок того, що давач шле big-endian: CRC на заводі рахували саме в цьому порядку, і будь-яка перестановка дасть іншу суму.

**Витяг результату.** Після 16 байтів корисні 4 біти — це `(n_rem >> 12) & 0x000F`, старший нібл регістра, а не молодший. Помилитися тут — і функція «щось рахуватиме», навіть іноді проходитиме, але систематично відкидатиме справні давачі.

> 🔧 **Навіщо це.** Перевіряти CRC пам'яті варто саме тому, що коефіцієнти читаються **один раз**. Помилка в них — не тимчасовий стрибок, а систематичне зміщення на весь час роботи: барометр покаже, скажімо, стабільні, але хибні 990 мбар замість 1013, і жодне усереднення цього не виправить. Ціна перевірки — кількадесят операцій один раз при старті; ціна пропуску — прилад, що тихо бреше всю сесію. Бібліотека RobTillaart дає це через `getCRC()` і `getProm()`, тож перевірку можна зробити і з нею.

### Крок 1–3: запуск, пауза, читання АЦП

Тепер цикл вимірювання. Щоб дістати сирий тиск `D1`, шлемо команду запуску перетворення тиску (`0x40 + OSR·2`), **чекаємо** час перетворення, а тоді командою `0x00` забираємо 24 біти. Так само окремо запускаємо перетворення температури (`0x50 + OSR·2`) і читаємо `D2`. Один повний вимір — це **два** перетворення, кожне зі своєю паузою.

Час паузи залежить від OSR — його беруть із таблиці даташита (той самий ряд, що зашитий у бібліотеці як мікросекунди):

```
OSR  256  (код 0)  →  ~0.6 мс
OSR  512  (код 2)  →  ~1.2 мс
OSR 1024  (код 4)  →  ~2.3 мс
OSR 2048  (код 6)  →  ~4.6 мс
OSR 4096  (код 8)  →  ~9.1 мс   ← найвища роздільність, «10 см»
```

Пауза критична: прочитаєте АЦП **раніше**, ніж перетворення завершилось, — дістанете попереднє або сміттєве значення. Тому витримуємо час із таблиці із запасом.

:::tabs
```arduino
// Обраний режим згладжування (код OSR: 0,2,4,6,8) і його пауза в мілісекундах.
static uint8_t g_osr_cmd = 8;        // 8 = OSR 4096 (найвища роздільність)

static uint16_t osr_delay_ms() {
  switch (g_osr_cmd) {
    case 0: return 1;   // ~0.6 мс, округляємо вгору
    case 2: return 2;   // ~1.2 мс
    case 4: return 3;   // ~2.3 мс
    case 6: return 5;   // ~4.6 мс
    default:return 10;  // ~9.1 мс (OSR 4096)
  }
}

// Запустити одне перетворення (start = CMD_CONV_D1 або CMD_CONV_D2),
// витримати паузу за OSR і прочитати 24-бітний результат АЦП.
static bool ms5611_convert_read(uint8_t start_cmd, uint32_t *out) {
  // -- запуск перетворення --
  Wire.beginTransmission(MS5611_ADDR);
  Wire.write(start_cmd + g_osr_cmd);       // напр. 0x40 + 8 = 0x48 для тиску @OSR4096
  if (Wire.endTransmission() != 0) return false;

  // -- пауза, поки АЦП рахує --
  delay(osr_delay_ms());

  // -- команда читання результату --
  Wire.beginTransmission(MS5611_ADDR);
  Wire.write(CMD_ADC_READ);                // 0x00
  if (Wire.endTransmission() != 0) return false;

  // -- забрати рівно 3 байти: 24 біти, старший першим --
  if (Wire.requestFrom((int)MS5611_ADDR, 3) != 3) return false;
  uint32_t b2 = Wire.read();               // старший
  uint32_t b1 = Wire.read();               // середній
  uint32_t b0 = Wire.read();               // молодший
  *out = (b2 << 16) | (b1 << 8) | b0;      // 24-бітне число

  // нульовий результат = давач не встиг/не відповів як слід
  return (*out != 0);
}
```

### Крок 4: повна компенсація у 64-бітній арифметиці

І ось серце теми — як `D1`, `D2` і `C1…C6` перетворюються на градуси й мілібари. Сам сенс формул (звідки береться `dT`, чому зсув і чутливість «пливуть» із температурою) розібрано в самій статті про барометр; тут — **робочий код**, і головна його вимога одна: правильна розрядність проміжних величин. Ключова пастка MS5611 живе саме тут.

Подивіться на добуток `D1 · SENS`. Сирий тиск `D1` — це число до 2²⁴ ≈ 1.6·10⁷. Чутливість `SENS` після масштабування — близько 2³¹ ≈ 2·10⁹. Їхній добуток — близько **3·10¹⁶**, а це далеко за межу 32-бітного цілого (≈ 4.3·10⁹ для беззнакового). У 32 бітах він **тихо переповниться** — обчислення не впаде, не дасть помилки, а поверне обрізане молодше слово, тобто цілком випадковий тиск. Тому `SENS`, `OFF`, `P`, а з ними й проміжні добутки **мусять бути 64-бітними** (`int64_t`). Це не перестраховка — це різниця між правильним барометром і генератором випадкових чисел.

```cpp
// Результати останнього виміру (у людських одиницях).
float g_temperature_C;    // °C
float g_pressure_hPa;     // мбар = гПа

// Повний вимір: D1, D2, компенсація 1-го і 2-го порядку. true — успіх.
bool ms5611_measure() {
  uint32_t D1, D2;                              // сирі тиск і температура
  if (!ms5611_convert_read(CMD_CONV_D1, &D1)) return false;
  if (!ms5611_convert_read(CMD_CONV_D2, &D2)) return false;

  // Коефіцієнти для читабельності:
  uint16_t C1 = g_prom[1];   // чутливість (SENS_T1)
  uint16_t C2 = g_prom[2];   // зсув (OFF_T1)
  uint16_t C3 = g_prom[3];   // температурний коеф. чутливості (TCS)
  uint16_t C4 = g_prom[4];   // температурний коеф. зсуву (TCO)
  uint16_t C5 = g_prom[5];   // опорна температура (T_REF)
  uint16_t C6 = g_prom[6];   // температурний коеф. температури (TEMPSENS)

  // -- 1) температура (у сотих градуса) --
  int32_t dT   = (int32_t)D2 - ((int32_t)C5 << 8);            // D2 − C5·2⁸
  int32_t TEMP = 2000 + (int32_t)(((int64_t)dT * C6) >> 23);  // 20.00 °C = 2000

  // -- 2) зсув і чутливість, виправлені на температуру (ОБОВ'ЯЗКОВО 64 біти!) --
  int64_t OFF  = ((int64_t)C2 << 16) + (((int64_t)C4 * dT) >> 7);
  int64_t SENS = ((int64_t)C1 << 15) + (((int64_t)C3 * dT) >> 8);

  // -- 3) компенсація другого порядку (для холоду) --
  if (TEMP < 2000) {                                  // нижче 20 °C
    int64_t dT64 = dT;
    int64_t T2   = (dT64 * dT64) >> 31;
    int64_t d    = (int64_t)TEMP - 2000;
    int64_t OFF2  = (5 * d * d) >> 1;                 // 5·(TEMP−2000)² / 2
    int64_t SENS2 = (5 * d * d) >> 2;                 // 5·(TEMP−2000)² / 4
    if (TEMP < -1500) {                               // нижче −15 °C — ще сильніше
      int64_t e = (int64_t)TEMP + 1500;
      OFF2  += 7 * e * e;                             // + 7·(TEMP+1500)²
      SENS2 += (11 * e * e) >> 1;                     // + 11·(TEMP+1500)² / 2
    }
    TEMP -= (int32_t)T2;
    OFF  -= OFF2;
    SENS -= SENS2;
  }

  // -- 4) тиск (у сотих мілібара) --
  int32_t P = (int32_t)(((( (int64_t)D1 * SENS) >> 21) - OFF) >> 15);

  g_temperature_C = TEMP / 100.0f;      // 2007 → 20.07 °C
  g_pressure_hPa  = P    / 100.0f;      // 100009 → 1000.09 гПа
  return true;
}
```

Три моменти, де плутаються найчастіше:

**Множники `2⁸` і `2²³`.** У формулі температури `dT = D2 − C5·2⁸`, а не просто `D2 − C5`. Коефіцієнт `C5` зберігається у своєму масштабі, і забутий зсув на 8 бітів дає температуру в десятки тисяч градусів. Так само `TEMP` рахується з масштабом `2²³` — саме тому добуток `dT · C6` уже треба тримати 64-бітним, хоч `TEMP` наприкінці й влазить у 32 біти.

**64 біти на зсуві й чутливості.** `OFF` і `SENS` оголошені `int64_t` **до** будь-яких множень. Якщо оголосити їх `int32_t`, переповниться вже `C2 << 16` (у деяких давачів), а `D1 · SENS` — гарантовано. Помітьте `(int64_t)` перед кожним добутком: без явного приведення компілятор [порахує множення у 32 бітах](topic:sf-lang/integer-promotion) і **тоді** розширить результат — тобто вже після переповнення. (Просування типів у C бере ширший з двох операндів; `uint16_t · uint16_t` рахується у `int`, а не в 64 бітах, поки ви не приведете хоча б один множник.)

**Гілку холоду в теплі пропускають.** Умова `TEMP < 2000` означає «нижче 20 °C». У теплій кімнаті цей блок не виконується взагалі, і код працює трохи швидше; вмикається він лише на морозі, де без нього похибка стає помітною. Саме тому баг у цій гілці підступний: він проявляється лише коли ви винесли дрон на холод.

Розгляньмо повний рахунок на конкретних числах — це той самий приклад із даташита, зручний для перевірки власного коду.

**Давач повернув `D1 = 9085466`, `D2 = 8569150`, а з PROM прочитано `C1=40127, C2=36924, C3=23317, C4=23282, C5=33464, C6=28312`.**
```c
dT   = 8569150 − 33464·256 = 8569150 − 8566784 = 2366
TEMP = 2000 + (2366·28312) / 2²³ = 2000 + 66986192/8388608 ≈ 2000 + 7 = 2007   → 20.07 °C

OFF  = 36924·2¹⁶ + (23282·2366)/2⁷ = 2420113408 + 430472  = 2420543880
SENS = 40127·2¹⁵ + (23317·2366)/2⁸ = 1314682368 + 215516  = 1314897884

// TEMP = 2007 ≥ 2000 → гілку другого порядку пропускаємо
P = ((9085466·1314897884)/2²¹ − 2420543880) / 2¹⁵ ≈ 100009   → 1000.09 мбар
```

Отже, ці сирі числа означають **20.07 °C** і **1000.1 мбар**. Підставте ті самі коефіцієнти й `D`-значення у свій код — і мусите дістати рівно ці числа; якщо вийшло інше, шукайте помилку в порядку байтів, у множниках `2⁸`/`2²³` або в розрядності (32 замість 64). Це найшвидший спосіб знайти саме ту помилку, що дає «правдоподібний, але хибний» тиск.

> 🔧 **Навіщо це.** Дві похибки з цього розділу дають майже всі скарги на MS5611. Переповнення в 32 бітах — тиск скаче на сотні мілібар або застигає безглуздою константою. Забутий множник при `C5` — температура в десятки тисяч градусів, а з нею й тиск. Прогнавши даташитний приклад, ви ловите обидві за хвилину, не паяючи нічого. А знаючи, звідки береться роздільність, ви свідомо обираєте OSR: гнатися за 9-мілісекундною паузою є сенс лише там, де ті 10 см справді потрібні.

**Дрібниця про константи другого порядку.** Ви можете зустріти в чужому коді трохи інші числа: `OFF2 = 61·(TEMP−2000)²/16`, `SENS2 = 29·(TEMP−2000)²/16` (так у довідковому драйвері TE Connectivity). Це той самий фізичний зміст, лише з округленням коефіцієнтів під іншу форму запису; різниця в кінцевому тиску — соті мілібара, нижче роздільності давача. Datasheet-версія (`5·…/2`, `5·…/4`, `7·…`, `11·…/2`) — канонічна, її й наведено вище; обидві прийнятні.

## Пастки, на яких обпікаються навіть із робочим кодом

Код може бути майже бездоганним, а показ — брехати. Ось речі, що дають більшість скарг «числа якісь дивні» саме на MS5611.

**32-бітне переповнення в компенсації.** Найпоширеніша й найпідступніша. Добуток `D1 · SENS` — близько 3·10¹⁶, у 32 бітах він тихо переповнюється, і тиск виходить безглуздий (стрибки на сотні мілібар, застигла константа). Проміжні `OFF`, `SENS`, `P` **мусять** бути `int64_t`, і кожен добуток треба явно приводити до 64 бітів **перед** множенням, а не після. Ознака: тиск «дикий» і не тримається реальності, тоді як температура (вона в 32 бітах порахована коректно) виглядає нормально.

**Пропущена або закоротка пауза після команди.** Прочитали АЦП раніше, ніж перетворення завершилось, — і замість виміру дістали нулі або старе значення. Витримуйте час із таблиці OSR із запасом; при `OSR 4096` це аж ~9 мс, і зекономити на них не вийде. Перевірка «результат не нуль» ловить цей випадок.

**Переплутаний порядок байтів.** І в PROM (два байти), і в АЦП (три байти) MS5611 шле **старший байт першим**. Складете навпаки — коефіцієнти чи сире значення спотворяться, і тиск буде фантастичний. Це те, що перевіряється даташитним прикладом за хвилину.

**Забутий множник `2⁸` при `C5`.** Класична друкарська помилка: написати `dT = D2 − C5` замість `dT = D2 − C5·2⁸`. Результат — температура в десятки тисяч градусів і зруйнований тиск. Даташитний приклад ловить і це.

**Плутанина адрес `0x76` / `0x77`.** Пін `CSB` вирішує адресу: вільний або на GND → `0x77`, на VCC → `0x76`. Задали в коді не ту — давач просто не виставить ACK, і перша ж транзакція (скид, а з нею й будь-яка функція ініціалізації) поверне невдачу. Якщо не певні, яка адреса, — проженіть I2C-сканер: він покаже реальну. Приємний бік цієї пари: два GY-63 живуть на одній шині, якщо одному дати `0x76`, іншому `0x77`; але третього не буде — інших адрес немає.
