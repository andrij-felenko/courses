# Поглиблений аналіз матриці шин, AXI QoS та розрахунку латентності

Побудова стабільного відеотракту високої чіткості на базі мікроконтролерів STM32 (серій F469, F769, H743/H747) вимагає суворого розрахунку бюджету пропускної здатності шин та максимального часу реакції арбітра матриці. Будь-яка неврахована мікросекундна затримка під час доступу DMA до пам'яті неминуче призводить до апаратного переповнення буфера FIFO цифрового інтерфейсу камери (DCMI) або виникнення смуг мерехтіння на екрані (Underflow контролера LTDC).

У цьому розділі наведено математичний розрахунок латентностей, конфігурацію арбітражу AXI QoS, правила налаштування MPU для потокового відео та оптимізовану виробничу реалізацію драйвера.

---

## 1. Розрахунок бюджету пропускної здатності та критичної латентності FIFO

Розглянемо типову мультимедійну систему реального часу: камера OV2640 передає потік роздільної здатності SVGA (800x600 пікселів) у форматі RGB565 (2 байти на піксель) із частотою 30 кадрів/с, а дисплейний контролер LTDC виводить інтерфейс на панель 800x480 RGB565 із частотою оновлення 60 Гц.

### Розрахунок смуги пропускання відеотракту

1. **Потік захоплення камери (DCMI Ingestion):**
```text
BW_dcmi = Width * Height * Bpp * FPS
BW_dcmi = 800 * 600 * 2 * 30 = 28 800 000 байт/с ≈ 27.47 МБ/с
```

2. **Потік виводу на дисплей (LTDC Refresh):**
```text
BW_ltdc = Width * Height * Bpp * Refresh_Rate
BW_ltdc = 800 * 480 * 2 * 60 = 46 080 000 байт/с ≈ 43.95 МБ/с
```

3. **Потік 2D-блендингу та копіювання (DMA2D Chrom-ART):**
Під час оновлення графічного інтерфейсу та накладання кадру камери DMA2D зчитує вхідний кадр і записує його у вихідний буфер:
```text
BW_dma2d = 2 * BW_dcmi = 2 * 27.47 МБ/с = 54.94 МБ/с
```

**Сумарне пікове навантаження на підсистему пам'яті:**
```text
BW_total = BW_dcmi + BW_ltdc + BW_dma2d = 27.47 + 43.95 + 54.94 = 126.36 МБ/с
```

Якщо до цього додати трафік ядра процесора (вибірка інструкцій та стек) і передачу даних по Ethernet, сумарне навантаження може перевищувати 200 МБ/с.

## 2. Критичний час до переповнення FIFO камери (Time-to-Overrun)

Внутрішній FIFO периферійного модуля DCMI має апаратний обсяг усього:
```text
FIFO_DCMI = 4 слова по 32 біти = 16 байтів
```

Камера видає байти синхронно з тактовим сигналом PCLK. При стандартній частоті піксельного тактування `F_pclk = 24 МГц` тривалість надходження одного байта становить:
```text
T_byte = 1 / F_pclk = 1 / 24 000 000 с ≈ 41.67 нс
```

Час повного заповнення 16-байтового апаратного FIFO від порожнього стану до переповнення:
```text
T_max_stall = FIFO_DCMI * T_byte = 16 * 41.67 нс = 666.7 наносекунд
```

> **Критичний ліміт арбітражу:** Якщо шина пам'яті виявиться заблокованою іншим майстром довше ніж на **666 наносекунд**, виникає апаратне переривання помилки DCMI `FOVR (FIFO Overrun Flag)`, і кадр незворотно спотворюється. На частоті шини AHB/AXI 200 МГц (період такту 5 нс) це відповідає всього **133 тактам шини**!

## 3. Внутрішня структура матриці AXI Interconnect та AXI QoS (STM32H7)

У сімействі мікроконтролерів STM32H7 замість класичної матриці Multi-AHB застосовано 64-бітний інтерконект **ARM CoreLink NIC-400 (AXI Interconnect)**, що працює на тактовій частоті до 200–240 МГц. Теоретична пропускна здатність 64-бітної шини AXI:

```text
BW_axi_peak = Bus_Width_Bytes * F_axi
BW_axi_peak = 8 байтів (64 біти) * 240 000 000 Гц = 1 920 000 000 байт/с = 1.92 ГБ/с!
```

### Регістри Quality of Service (AXI QoS)

Для гарантії того, що критичні до латентності потоки отримають обслуговування раніше за менш важливі транзакції, кожен майстер інтерконекту AXI супроводжує свої транзакції 4-бітним сигналом пріоритету `AxQOS[3:0]` (значення від 0 до 15):

```text
Рівень QoS  |  Пріоритет арбітражу  |  Призначений системний майстер
------------+-----------------------+------------------------------------------
15 (0xF)    |  Критичний реальний час|  DCMI (Камера через MDMA / DMA2)
14 (0xE)    |  Високий реальний час |  LTDC (Контролер дисплея — захист FIFO)
10 .. 12    |  Підвищений           |  DMA2D Chrom-ART графічний прискорювач
6 .. 8      |  Середній             |  Cortex-M7 ядро процесора (D-Cache AXI)
2 .. 4      |  Фоновий              |  Ethernet MAC / USB OTG
0 (0x0)     |  Мінімальний          |  Низькошвидкісні периферійні DMA потоки
```

В мікроконтролерах STM32H7 рівні QoS для шинних майстрів налаштовуються через внутрішні регістри інтерконекту (AXI Target Function Modification Registers):

```c
/* Налаштування найвищого пріоритету AXI QoS для порту DMA камери */
#define AXI_TARG1_FN_MOD   (*(volatile uint32_t *)(0x51001000 + 0x108))
#define AXI_TARG2_FN_MOD   (*(volatile uint32_t *)(0x51002000 + 0x108))

void configure_axi_qos_priorities(void) {
    /* Встановлення QoS = 15 (0x0F) для камери та дисплея */
    AXI_TARG1_FN_MOD |= (0x0F << 0); /* Порт DCMI DMA */
    AXI_TARG2_FN_MOD |= (0x0E << 0); /* Порт LTDC */
}
```

## 4. Конфігурація Memory Protection Unit (MPU) для DMA буферів

Ядра ARM Cortex-M7 оснащені роздільними кешами першого рівня (L1 16 КБ I-Cache та 16 КБ D-Cache). За замовчуванням уся внутрішня оперативна пам'ять SRAM налаштовується як кешована пам'ять із відкладеним записом (Write-Back, Write-Allocate).

Це створює дві фатальні проблеми під час роботи з потоковим DMA камери:
1. **Проблема когерентності пам'яті (Cache Coherency):** Коли контролер DMA записує новий рядок пікселів у фізичний ОЗП, кеш-пам'ять ядра процесора про це не знає. Якщо процесор спробує прочитати пікселі, він прочитає старі дані з L1 D-Cache.
2. **Продуктивність інвалідації кешу:** Постійний виклик функцій `SCB_InvalidateDCache_by_Addr()` для кожного кадру з'їдає до 25–35% продуктивності процесора та засмічує шину AXI паразитарними запитами очищення ліній кешу.

### Рішення: Конфігурація регіону MPU як Non-Cacheable

Виділена область пам'яті в `SRAM1`, куди контролер DMA камери складає байти, повинна бути явно налаштована через апаратний модуль MPU як **Device Memory** або **Normal Non-Cacheable, Shareable**:

```c
void mpu_config_dcmi_buffer(uint32_t base_address, uint32_t size) {
    MPU_Region_InitTypeDef MPU_InitStruct;

    /* Вимикаємо MPU перед конфігурацією */
    HAL_MPU_Disable();

    /* Використовуємо регіон 1 для буфера камери */
    MPU_InitStruct.Enable = MPU_REGION_ENABLE;
    MPU_InitStruct.Number = MPU_REGION_NUMBER1;
    MPU_InitStruct.BaseAddress = base_address;
    MPU_InitStruct.Size = MPU_REGION_SIZE_64KB; /* Розмір буфера */
    MPU_InitStruct.SubRegionDisable = 0x00;
    
    /* Доступ: повний доступ для ядра і периферії */
    MPU_InitStruct.AccessPermission = MPU_REGION_FULL_ACCESS;
    
    /* КРИТИЧНО: Вимикаємо кешування та буферизацію для гарантії когерентності */
    MPU_InitStruct.TypeExtField = MPU_TEX_LEVEL1;
    MPU_InitStruct.IsCacheable = MPU_ACCESS_NOT_CACHEABLE;
    MPU_InitStruct.IsBufferable = MPU_ACCESS_NOT_BUFFERABLE;
    MPU_InitStruct.IsShareable = MPU_ACCESS_SHAREABLE;

    HAL_MPU_ConfigRegion(&MPU_InitStruct);

    /* Вмикаємо MPU з підтримкою стандартних правил для фонової пам'яті */
    HAL_MPU_Enable(MPU_PRIVILEGED_DEFAULT);
}
```

## 5. Виробничий контрольний чек-лист усунення колізій шин

Якщо у камерному проекті на базі STM32 виникають спорадичні збої або артефакти:

1. **Перевірте прапорець FOVR:** Зареєструйте функцію зворотного виклику `HAL_DCMI_ErrorCallback()`. Якщо встановлено біт `DCMI_FLAG_OVRI`, проблема на 100% полягає в перевантаженні матриці шин або затримці DMA.
2. **Перевірте налаштування Burst у DMA:** Переконайтеся, що для потоку DMA2 увімкнено FIFO (`FIFOMode = ENABLE`, поріг `FULL`) та встановлено режим пакетної передачі `MemBurst = DMA_MBURST_INC4`. Пакетний трансфер із 4 слів утримує шину набагато ефективніше, ніж поодинокі звернення.
3. **Розділіть фізичні банки пам'яті:** Ніколи не розміщуйте буфер камери `DCMI_Buffer[]` та буфер відображення `LTDC_Buffer[]` в одному банку внутрішнього ОЗП. Використовуйте `SRAM1` для камери, а зовнішню `SDRAM` — для дисплея.
4. **Використовуйте DTCM для ядра:** Перенесіть стек FreeRTOS та найбільш навантажені змінні ядра процесора в пам'ять `DTCM (0x20000000)`, звільнивши матрицю шин AHB/AXI для обслуговування відеопотоків.
