## Математика розподілу 4-кілобайтних секторів Flash

Фізична енергонезалежна пам'ять @@en|SPI Flash@@ у мікроконтролерах @@en|ESP8266@@ має секторну структуру. Мінімальною одиницею стирання даних є один сектор розміром 4096 байтів (`0x1000` у шістнадцятковій системі). Через цю апаратну особливість будь-який розподіл адресового простору для схеми бездротового оновлення @@en|FOTA@@ (en|Firmware Over-The-Air, від англ. @@en|firmware@@ — прошивка та @@en|over-the-air@@ — по повітрю) повинен суворо дотримуватися правила вирівнювання меж розділів по кратності сектору `0x1000`.

Математично умова вирівнювання початкової адреси `P_start` та довжини розділу `P_size` виражається через операцію остачі від ділення:

P_start mod 0x1000 = 0                 [умова вирівнювання початкової адреси]
P_size mod 0x1000 = 0                  [умова вирівнювання розміру розділу]
P_end = P_start + P_size - 1           [формула кінцевої адреси розділу]

При порушенні цієї умови процедура стирання сектору під час запису нової прошивки неминуче пошкодить суміжні дані або виконуваний код сусіднього розділу.

Для мікросхеми Flash обсягом 4 МБ (`0x400000` байтів = 1024 сектори) стандартна геометрія двобанківської системи FOTA описується такою топологією:
* Сектор 0 (`0x000000`–`0x000FFF`): апаратний первинний завантажувач (4 КБ).
* Слот 1 (`user1.bin`): адреси `0x001000`–`0x0FBFFF` (розмір 1004 КБ = 251 сектор = `0xFB000` байтів).
* Слот 2 (`user2.bin`): адреси `0x101000`–`0x1FBFFF` (розмір 1004 КБ = 251 сектор = `0xFB000` байтів).
* Верхні сектори пам'яті резервуються під системні налаштування @@en|SDK@@: сектор `0x3FC000` зберігає базову конфігурацію ініціалізації, а сектори `0x3FE000`–`0x3FFFFF` призначені для системних параметрів бездротового зв'язку.

Розглянемо арифметичний приклад обчислення початкової адреси розділу Слот 2 та перевірки кінцевої адреси `P_end` на приналежність до недопустимого системного діапазону. Знаючи розмір первинного завантажувача та розмір першого слота, початкова адреса другого слота обчислюється як сума їхніх секторних довжин:

```
P_start = 0x001000 + 0x0FB000           [додавання зсуву завантажувача та слота user1.bin]
        = 0x101000                      [початкова адреса слота user2.bin]
P_size  = 251 × 4096                    [251 сектор розміром по 4096 байтів]
        = 1028096                       [переведення в десяткові байти]
        = 0x0FB000                      [конвертація у шістнадцятковий формат]
P_end   = P_start + P_size - 1          [загальна формула кінцевої адреси]
        = 0x101000 + 0x0FB000 - 1       [підстановка обчислених зсувів]
        = 0x1FCFFF                      [підсумкова кінцева адреса слота user2.bin]
```

Отримана кінцева адреса `0x1FCFFF` строго менша за початкову адресу системного сектора ініціалізації `0x3FC000` (`0x1FCFFF < 0x3FC000`), що арифметично доводить відсутність накладання розділу `user2.bin` на зарезервовану системну область контролера бездротового зв'язку.

Детальний опис того, як [архітектура завантажувача ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture) опитує первинні сектори при старті, визначає точні початкові зсуви для завантаження коду.

## Розрахунок доступних слотів двобанківського оновлення

При організації безпечного оновлення прошивки по повітрю система використовує двобанківську схему (англ. @@en|dual-bank update@@). Новий бінарний образ записується у неактивний слот пам'яті, поки з активного слота виконується поточна програма. Математичний розрахунок гранично допустимого розміру слота `Slot_Max_Size` вимагає врахування загального обсягу чипа `Chip_Size`, резервованих системних секторів та файлової системи @@en|SPIFFS@@ (en|SPI Flash File System, від англ. @@en|flash file system@@ — файлова система Flash) або @@en|LittleFS@@.

Загальна формула розрахунку корисного обсягу одного слота оновлення має вигляд:

Usable_Space = Chip_Size - System_Reserved - Filesystem_Size  [доступна пам'ять]
Slot_Raw = Usable_Space ÷ 2                                    [сирий обсяг слота]
Slot_Max_Size = Slot_Raw - (Slot_Raw mod 0x1000)              [вирівняний розмір слота]

Розглянемо приклад обчислення для модуля з 4 МБ Flash (`4 194 304` байти) та файловою системою розміром 1 МБ (`1 048 576` байтів):

**Умова:** Загальний обсяг = 4 194 304 байти, Завантажувач = 4 096 байтів, Системні сектори = 16 384 байти, Файлова система = 1 048 576 байтів.

Usable_Space = 4 194 304 - 4 096 - 16 384 - 1 048 576
             = 3 125 248 байтів        [загальний простір для двох слотів]

Slot_Raw = 3 125 248 ÷ 2 = 1 562 624 байтів  [381.5 секторів]

Slot_Max_Size = 1 562 624 - (1 562 624 mod 4096)
              = 1 562 624 - 2048
              = 1 560 576 байтів       [381 сектор = 1524 КБ]

Таким чином, максимальний розмір бінарного образу для кожного з двох слотів становить точно 1 560 576 байтів (`0x17D000` байтів). Другий слот розташовується зі зсувом `0x101000`. При успішній верифікації завантажувач @@en|rboot@@ змінює заголовок активного банку, виконуючи [оновлення прошивки по повітрю](root:cat-hw-boards/esp8266-fota-update) без ризику втрати працездатності.

У граничному випадку, коли довільний розмір файлової системи @@en|LittleFS@@ створює дробову остачу при діленні на 4096, вкрай важливо виконати вирівнювання нижньої межі. Наприклад, якщо користувач виділяє під файлову систему `1 000 000` байтів, пряме застосування цього значення порушить 4-кілобайтне вирівнювання сусідніх слотів FOTA. Обчислення коректного розміру з округленням до нижньої межі сектору виконується за схемою:

```
FS_Raw     = 1000000                    [початково виділений обсяг LittleFS]
FS_Rem     = 1000000 mod 4096           [обчислення некратної остачі]
           = 576                        [дробовий лишок у байтах]
FS_Aligned = FS_Raw - FS_Rem            [формула округлення до нижньої межі]
           = 1000000 - 576              [віднімання остачі]
           = 999424                     [244 повних сектори = 0xF4000 байтів]
```

Округлення розміру файлової системи до `999 424` байтів гарантує, що початкова адреса наступного розділу потрапить точно на межу сектору `0x1000`, відсікаючи 576 байтів дробового лишку та усуваючи загрозу пошкодження коду під час стирання.

## Алгоритм побайтового обчислення контрольної суми CRC32

Передача даних бездротовими каналами зв'язку піддається впливу завад і втрат пакетів. Для швидкого математичного контролю цілісності отриманого бінарного блоку застосовується алгоритм циклічного надлишкового коду @@en|CRC32@@ (en|Cyclic Redundancy Check, від англ. @@en|cyclic redundancy@@ — циклічний надлишок).

В основі алгоритму лежить ділення двійкового многочлена даних на фіксований генераторний поліном IEEE 802.3 у полі Ґалуа GF(2):

P(x) = x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1

У шістнадцятковій формі зі зсувом бітів праворуч поліном відповідає константі `0xEDB88320`. Покроковий розрахунок значення контрольної суми для кожного зчитаного байта `B_k` виражається математичним ланцюжком:

CRC₀ = 0xFFFFFFFF                      [ініціалізація регістра]
CRC_temp = CRCₖ₋₁ ⊕ Bₖ                  [побайтовий XOR з молодшим байтом]
CRCₖ = Process_Bits(CRC_temp)          [8 зсувів праворуч з умовним XOR на 0xEDB88320]
CRC_final = CRCₙ ⊕ 0xFFFFFFFF          [інверсія підсумкового результату]

Розглянемо покрокове обчислення @@en|CRC32@@ для одного байта `0x01`:

CRC₀ = 0xFFFFFFFF                      [початковий стан]
CRC_temp = 0xFFFFFFFF ⊕ 0x01 = 0xFFFFFFFE [XOR з байтом 0x01]

Після виконання 8 циклів зсуву праворуч та застосування полінома `0xEDB88320`:

CRC₁_raw = 0x77073096                  [значення після 8 зсувів]
CRC_final = 0x77073096 ⊕ 0xFFFFFFFF = 0x88F8CF69 [інвертований хеш]

Якщо розраховане значення `CRC_final` не збігається зі значенням у кінці прийнятого образу, процедура запису у Flash скасовується. Детальніше апаратну обробку шинного доступу розглядає [огляд мікроконтролера та архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).

## Криптографічний розрахунок хешу SHA-256 для FOTA

Захист системи FOTA від умисної підміни або модифікації коду вимагає використання криптографічно стійких функцій хешування. Контрольна сума @@en|CRC32@@ запобігає випадковим помилкам, але не захищає від зловмисного втручання. Для гарантії автентичності прошивки використовується алгоритм @@en|SHA-256@@ (en|Secure Hash Algorithm, від англ. @@en|secure hash@@ — безпечний хеш), який перетворює вхідний бінарний образ довільної довжини у фіксований 256-бітний (32-байтний) відбиток.

Математична обробка бінарного файлу поділяється на три послідовні етапи:

1. **Доповнення повідомлення (Padding):** До кінця файлу додається біт `1`, за яким слідують `K` нульових бітів, після чого записується 64-бітне значення вихідної довжини файлу `L_bits`. Кількість нулів `K` обчислюється з умови вирівнювання блока до 512 бітів (64 байти):

(L_bits + 1 + K + 64) mod 512 = 0     [умова вирівнювання блока SHA-256]

2. **Розширення блока:** Кожен 512-бітний блок розділяється на 16 32-бітних слів `W₀`–`W₁₅`, які розширюються до 64 слів `W₀`–`W₆₃` за формулами нелінійного зсуву:

σ₀(x) = (x ⋙ 7) ⊕ (x ⋙ 18) ⊕ (x ≫ 3)    [функція малого зсуву sigma 0]
σ₁(x) = (x ⋙ 17) ⊕ (x ⋙ 19) ⊕ (x ≫ 10)  [функція малого зсуву sigma 1]
Wₜ = σ₁(Wₜ₋₂) + Wₜ₋₇ + σ₀(Wₜ₋₁₅) + Wₜ₋₁₆   [розширення для t = 16..63]

3. **Стиснення та оновлення стану:** Протягом 64 раундів 8 робочих змінних `a, b, c, d, e, f, g, h` модифікуються з використанням констант `K_t` та функцій вибору `Ch(e,f,g)` і більшості `Maj(a,b,c)`.

Після обробки останнього блока підсумковий 256-бітний хеш звіряється з підписаним хешем на сервері оновлень. У разі неспівпадіння хоч одного з 64 шістнадцяткових символів завантажувач відхиляє образ. Спільне використання хешування та безпечних каналів зв'язку розглядає [оновлення прошивки та прошивання ESP-01](root:cat-hw-boards/esp01-firmware-flashing) при організації надійного протоколу розгортання.
