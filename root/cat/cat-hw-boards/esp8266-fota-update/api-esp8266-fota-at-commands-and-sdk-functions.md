## Ризики розриву з'єднання під час оновлення

Завантаження нової прошивки в автономні пристрої Інтернету речей через бездротові мережі пов'язане з ризиками фатальних апаратних збоїв. Раптове відключення живлення або втрата Wi-Fi-пакета під час запису секторів безпосередньо в єдиний завантажувальний банк призводить до пошкодження системного образу та перетворення пристрою на несправний модуль ("цеглину"). 

Для усунення цього ризику в [архітектурі завантажувача ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture) реалізовано технологію @@en|FOTA@@ (від англ. *Flash Over-The-Air* — бездротове оновлення прошивки). Архітектура спирається на поділ Flash-пам'яті на два робочих слоти `user1.bin` та `user2.bin`. Під час бездротового передавання поточний виконуваний код продовжує працювати з першого слота, а отримані кадри нового образу записуються в другий, неактивний слот. Оскільки фізична Flash-пам'ять ділиться на сектори розміром `S_sector = 4096 байтів` (4 КБ), межі розділів обов'язково вирівнюються за секторною сіткою. На чипах обсягом 1 МБ це накладає суворе обмеження на максимальний розмір кожного слота `user1.bin` та `user2.bin` до 480 КБ (120 секторів), щоб уникнути перекриття сусіднього банку чи зарезервованої області системних параметрів. Зміна активного банку відбувається через атомарне защеплення прапорців цілісності у спеціалізованому секторі конфігурації завантажувача (rBoot / eBoot sector). Лише після підтвердження контрольної суми та хешу нового образу SDK перезаписує структуральний прапорець активного слота, а в разі будь-якого збою живлення до моменту защеплення завантажувач ігнорує пошкоджений слот і запускає перевірену прошивку з попереднього банку.

## Інтерфейс AT-команди AT+CIUPDATE

Для зовнішніх хост-контролерів, які керують модулем через [послідовний порт UART](root:cat-hw-boards/esp8266-at-gpio-control), у стандартній AT-прошивці передбачено високорівневу команду `AT+CIUPDATE`. Вона автоматизує весь цикл встановлення HTTP-з'єднання з сервером, визначення активного слота, завантаження бінарного кадру та перемикання прапорців завантажувача.

Команда підтримує п'ять послідовних проміжних відповідей, які надсилаються в текстовий потік:

1. `+CIPUPDATE:1` — виявлення серверного ресурсу та перевірка наявності оновлення.
2. `+CIPUPDATE:2` — встановлення з'єднання з віддаленим сервером.
3. `+CIPUPDATE:3` — отримання заголовків образу та початок запису у неактивний слот.
4. `+CIPUPDATE:4` — успішне завершення завантаження та верифікація контрольної суми.
5. `OK` — фіксація нового завантажувального слота у конфігураційній пам'яті та перезавантаження.

![Схема послідовності обміну даними між хост-контролером, ESP8266 та сервером оновлень під час виконання AT+CIUPDATE](img/esp8266-fota-at-command-sequence.svg)
*Схема послідовності обміну даними між хост-контролером, ESP8266 та сервером оновлень під час виконання AT+CIUPDATE.*

При виникненні тайм-ауту або невідповідності розміру кадру модуль повертає відповідь `ERROR`, зберігаючи вихідний робочий слот недоторканим. Для успішного виконання завантаження система вимагає достатнього обсягу динамічної пам'яті @@en|Heap@@ (понад 15 КБ вільного простору) для виділення мережевих буферів прийому стеків TCP/IP та системних заголовочних компонентів; при дефіциті RAM команда негайно завершується з помилкою без спроби з'єднання. За замовчуванням виклик без параметрів `AT+CIUPDATE` здійснює запит до стандартного хмарного сервера Espressif. Проте за потреби розгортання власної локальної чи корпоративної інфраструктури FOTA команда підтримує додаткові параметри конфігурації: `AT+CIUPDATE="<domain_or_ip>",<port>,"<path_to_file>"`. Параметр `<domain_or_ip>` визначає доменне ім'я @@en|domain@@ чи IP-адресу власного сервера оновлень, цілочисельний параметр `<port>` задає TCP-порт (за замовчуванням `80`), а параметр `<path_to_file>` вказує точний шлях @@en|path@@ до бінарного файлу образа на сервері. Це дозволяє гнучко інтегрувати модуль із довільним HTTP-сервером без зміни внутрішнього коду AT-прошивки, зберігаючи гарантії безпечного відновлення системи у разі помилки зв'язку.

## Системні функції та структури SDK API

При розробці автономної прошивки в середовищі Non-OS SDK для керування процесом завантаження застосовують системні виклики комплекту розробника (@@en|SDK@@, від англ. *Software Development Kit* — комплект розробника ПЗ).

Перед початком запису функція `system_upgrade_userbin_check()` визначає поточний активний банк і повертає константу `UPGRADE_FW_BIN1` або `UPGRADE_FW_BIN2`. Це дає змогу сформувати правильний HTTP-запит до сервера на отримання протилежного образу (`user2.bin` або `user1.bin`).

Параметри з'єднання передаються через системну структуру `struct upgrade_server_info`, після чого процес задіює функцію `system_upgrade_start()`. Ключовим полем цієї структури є вказівник на функцію зворотного виклику @@en|callback@@ `check_cb`, який передає асинхронний статус оновлення після завершення завантаження або виникнення помилки. Поле `check_times` задає граничний тайм-аут у мілісекундах і обчислюється на основі максимального розміру образу `S_binary` та найгіршої швидкості мережі `R_min` (наприклад, `120000` мс для 500 КБ прошивки). Мережевий стек фоново обробляє прийом пакетів і запис у Flash, а після закінчення перевірки цілісності або при спрацюванні тайм-ауту викликає `check_cb(void *arg)`. Усередині цього виклику розробник перевіряє прапорець `upgrade_flag`: значення `true` свідчить про успішну верифікацію образу і вимагає виклику `system_upgrade_reboot()` для автоматичного перезавантаження завантажувача @@en|bootloader@@ у новий слот. Якщо ж `upgrade_flag` дорівнює `false`, callback-функція аналізує асинхронні коди помилок (розрив TCP-з'єднання, помилка HTTP 404/500 чи неспівпадіння CRC), скасовує транзакцію та вимагає обов'язкового звільнення пам'яті структури через `os_free()`:

## Асинхронний OTA-інтерфейс в RTOS SDK

У багатозадачному середовищі ESP8266 RTOS SDK пряме блокування виконання недопустиме, оскільки воно може призвести до спрацьовування апаратного сторожового таймера. Для забезпечення фонового завантаження використовується прикладний прикладний інтерфейс (@@en|API@@, від англ. *Application Programming Interface* — прикладний програмний інтерфейс) `esp_ota_ops`.

Асинхронна процедура завантаження поділяється на три основні кроки:

1. `esp_ota_begin()` — знаходить наступний неактивний слот у таблиці розділів, стирає необхідну кількість секторів Flash-пам'яті та повертає дескриптор `esp_ota_handle_t`.
2. `esp_ota_write()` — побайтово записує отримані через сокет HTTP-пакети у фоновому потоці операційної системи @@en|FreeRTOS@@.
3. `esp_ota_end()` та `esp_ota_set_boot_partition()` — завершують запис, верифікують цілісність заголовочних структур та оновлюють запис стану в спеціалізованій області пам'яті @@en|otadata@@ (від англ. @@en|OTA Data@@, дані бездротового оновлення).

Механізм підтвердження цілісності в `esp_ota_set_boot_partition()` спирається на дубльовану структуру з двох секторів по `4 КБ` в області `otadata`. При виклику функція зчитує лічильник послідовності `seq`, обчислює контрольне значення CRC32 нової конфігурації та виконує атомарний запис у неактивний сектор `otadata`. Завантажувач @@en|bootloader@@ під час старту порівнює CRC32 обох секторів і обирає слот із більшим значенням `seq`. Якщо під час запису стався збій живлення чи виявлено пошкодження контрольної суми, завантажувач автоматично ігнорує зіпсований сектор і запускає попередню працездатну версію відповідно до опису в [архітектурі завантажувача ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture).

1. `esp_ota_begin()` — знаходить наступний неактивний слот у таблиці розділів, стирає потрібний обсяг секторів і повертає дескриптор `esp_ota_handle_t`.
2. `esp_ota_write()` — побайтово записує отримані з мережевих сокетів HTTP-пакети в Flash-пам'яті у фоновій задачі операційної системи @@en|FreeRTOS@@.
3. `esp_ota_end()` та `esp_ota_set_boot_partition()` — верифікують заголовок образу й переписують вказівник активного тому в конфігураційній області `otadata`.

Функція `esp_ota_set_boot_partition()` відіграє вирішальну роль не лише під час активації нового образу, але й при реалізації механізму відкочення @@en|rollback@@ на попередній банк. Якщо після перезавантаження новоприйнята прошивка не проходить самодіагностику чи виявляє помилки ініціалізації периферії, повторний виклик `esp_ota_set_boot_partition()` із передачею вказівника на попередній робочий розділ `esp_ota_get_running_partition()` миттєво повертає конфігураційний сектор завантажувача @@en|bootloader@@ у вихідний стан. Це гарантує відновлення працездатності пристрою без додаткових мережевих записів у пам'ять.

1. `esp_ota_begin()` — знаходить наступний неактивний слот у таблиці розділів, стирає потрібний обсяг секторів і повертає дескриптор `esp_ota_handle_t`.
2. `esp_ota_write()` — побайтово записує отримані з мережевих сокетів HTTP-пакети в Flash-пам'ять у фоновій задачі операційної системи @@en|FreeRTOS@@.
3. `esp_ota_end()` та `esp_ota_set_boot_partition()` — верифікують заголовок і перезаписують конфігураційний сектор завантажувача.

Такий підхід дозволяє обробляти мережеві події через [захищені SSL/TLS з'єднання в AT-прошивці ESP8266](root:cat-hw-boards/esp8266-at-ssl-tls) паралельно з виконанням основної логіки пристрою.

## Обробка помилок та перевірка цілісності

Для захисту від виконання пошкодженого коду перед зміною активного слота обов'язково виконується перевірка контрольних сум та MD5/SHA256-хешів отриманого образу. 

Якщо під час завантаження виникає мережевий тайм-аут, незбіг хешу або помилка стирання Flash-пам'яті, системна функція повертає код помилки, а завантажувальний сектор зберігає вказівник на попередній стабільний банк. Щоб забезпечити перевірку цілісності без надлишкових витрат оперативної пам'яті, верифікація хешу @@en|SHA256@@ (від англ. *Secure Hash Algorithm 256-bit* — безпечний алгоритм хешування 256 біт) виконується інкрементально у потоковому режимі. Математичний алгоритм покрокового оновлення контексту спирається на буферизацію вхідного потоку байтів до блоків розміром `64 байти` (512 біт) та оновлення восьми 32-бітних робочих регістрів `H₀ .. H₇`. Для кожного чергового фрагмента даних `M_i`, отриманого з мережевого сокета, обчислювальний крок описується послідовними перетвореннями розширення слів `W_t` та функції стиснення:

W_t = M_t                                           [для перших 16 слів блоку, t = 0..15]
W_t = σ₁(W_{t-2}) + W_{t-7} + σ₀(W_{t-15}) + W_{t-16} [генерація графіку для t = 16..63]
H_t = Compression(H_{t-1}, W_t)                     [інкрементальне оновлення стан-вектора]

Завдяки цьому кожен новий мережевий чанк одночасно передається у функцію трансформації контексту та записується в сектори Flash-пам'яті. Після зчитування останнього блоку додається вирівнювальний наповнювач @@en|padding@@ із 64-бітним довжинним кодом, підраховується підсумковий 32-байтовий дайджест `D` та зіставляється з еталонним хешем `D_ref` із заголовка образу. При виявленні будь-якої невідповідності або обриві зв'язку прапор підтвердження оновлення не встановлюється, і при наступному апаратному перезавантаженні вторинний завантажувач (eBoot або rBoot) виявить незавершений статус оновлення та викличе [автоматичне відновлення прошивки](root:cat-hw-boards/esp8266-bootloader-architecture) зі старого робочого слота.
