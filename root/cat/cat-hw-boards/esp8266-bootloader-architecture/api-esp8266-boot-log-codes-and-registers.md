## Діагностична роль логу ROM-завантажувача

Під час апаратного скидання чи подачі живлення на мікроконтролер ESP8266 первинний масочний завантажувач у постійному запам'ятовувальному пристрої (@@en|Read-Only Memory@@, від англ. *Read-Only Memory* — постійний запам'ятовувальний пристрій) виводить первинний відлагоджувальний потік у послідовний порт @@en|UART@@ (від англ. *Universal Asynchronous Receiver-Transmitter* — універсальний асинхронний трансивер) `UART0` (вивід `TXD0` / `GPIO1`). Особливістю цього логу є використання нетипової швидкості передачі (@@en|baud rate@@, від англ. *baud rate* — швидкість передавання в бодах), яка становить `74880 бод`. Після завершення зчитування образу з Flash-пам'яті та передачі управління вторинному завантажувачу або користувацькій прошивці відбувається динамічне переналаштування апаратного дільника в регістрі `UART_CLKDIV`: системний код ініціалізації SDK перезаписує значення дільника відповідно до реальної частоти резонатора та обраної користувачем швидкості (наприклад, `115200 бод`), що призводить до миттєвої зміни швидкості послідовного порту безпосередньо під час переходу до виконання функції `user_init`.

Виникнення цієї швидкості зумовлене тим, що дільник частоти у регістрі `UART_CLKDIV` за замовчуванням запрограмований під опорний кварцовий резонатор `40 МГц` із цільовою швидкістю `115200 бод`, що дає фіксоване значення дільника `347.222`. Коли на платі [модуля ESP-01 (Wi-Fi, ESP8266)](root:cat-hw-boards/esp-01) встановлено поширений резонатор частотою `26 МГц`, фактична швидкість передачі пропорційно знижується до `74880 бод`, спричиняючи відхилення `-35.0%` відносно стандартного термінала. Для рідкісних нестандартних резонаторів ця похибка змінюється пропорційно частоті кварцу: при використанні резонатора `13 МГц` швидкість становить `37440 бод` із похибкою `-67.5%`, а при `52 МГц` зростає до `149760 бод` із відхиленням `+30.0%`. Фактична швидкість передачі пропорційно залежить від резонатора та обчислюється наступним чином:

Baud_actual
= f_xtal ÷ (f_nominal ÷ Baud_target)
= 26000000 ÷ (40000000 ÷ 115200)      [підстановка частоти кварцю 26 МГц]
= 26000000 ÷ 347.222                  [ділення на дільник із регістру UART_CLKDIV]
= 74880                               [фактична швидкість у бодах]

Спроба прийому цього потоку терміналом, налаштованим на `115200 бод`, призводить до розсинхронізації точок стробування 10-бітового кадру `8N1` на `53.8%` і появі хаотичних нечитабельних символів. Налаштування термінального софту на швидкість `74880 бод` дає змогу прочитати первинні системні рядки та встановити причину перезавантаження й стан системної периферії.

## Декодування причин скидання rst cause

Першим важливим параметром системного логу є числове значення `rst cause:N`, яке вказує на точне джерело ініціалізації перезапуску процесора. Це дозволяє миттєво відрізнити нормальні операційні події від апаратних збоїв живлення або програмних зависань. Зокрема, для діагностики зависань система розрізняє апаратний сторожовий таймер @@en|Hardware WDT@@ (від англ. *Hardware Watchdog Timer* — апаратний сторожовий таймер) та програмний @@en|Software WDT@@ (від англ. *Software Watchdog Timer* — програмний сторожовий таймер). При блокуванні системного циклу спочатку спрацьовує програмний таймер, який ґенерує немасковане переривання @@en|NMI@@ (від англ. *Non-Maskable Interrupt* — немасковане переривання) для збереження дампу регістрів перед скиданням. Якщо ж процесорне ядро повністю блокується на рівні переривань і не здатне обробити NMI, спрацьовує апаратний таймер Hardware WDT, який примусово перезапускає мікроконтролер на рівні кремнію. Окремо від первинної подачи живлення (`rst cause:0`) та пробудження зі сну (`rst cause:5`), код `rst cause:6` фіксує зовнішнє апаратне скидання підтягнутим до землі піном `RST` при збереженій напрузі 3.3 В. У разі ж фатального краху ядра (`rst cause:2`) системний лог дає номер винятку з регістру `EXCCAUSE` ядра Xtensa: код `N=0` вказує на виконання пошкодженої інструкції (`IllegalInstruction`), `N=9` — на невирівняний доступ до пам'яті (`LoadStoreAlignment`), а `N=28` чи `N=29` — на спробу читання або запису за нульовим вказівником (`LoadProhibited` / `StoreProhibited`).

Параметр `rst cause` виражає стан системного контролера скидання:

Параметр `rst cause` | Опис джерела скидання | Причина виникнення та апаратна поведінка
`0` | Power-on reset | Первинне підключення джерела живлення 3.3 В
`1` | Hardware WDT reset | Спрацьовування апаратного сторожового таймера (@@en|Watchdog Timer@@) через зависання коду понад 1.5 с
`2` | Fatal exception | Фатальне падіння процесорного ядра Xtensa через некоректну інструкцію чи звернення до пам'яті
`3` | Software WDT reset | Спрацьовування програмного сторожового таймера при блокуванні системного циклу
`4` | Software restart | Програмна ініціалізація викликом функції `system_restart()`
`5` | Deep-sleep wake-up | Пробудження з режиму глибокого сну (@@en|Deep Sleep@@) через короткий імпульс на лінії `RST` від `GPIO16`

*Схема алгоритму визначення джерела перезавантаження за параметром rst cause та станами системних регістрів.*

При виникненні збою `rst cause:2` системний завантажувач додатково транслює номер фатального винятку `fatal exception (N):`, де `N=28` вказує на спробу зчитування за нульовим вказівником, а `N=9` — на помилку невирівняного доступу до пам'яті.

## Значення режимів завантаження boot mode

Слідом за причиною скидання завантажувач виводить рядок `boot mode:(x,y)`, де двозначний код визначає апаратний режим роботи чипа та стан його конфігурації. Перший параметр `x` являє собою 3-бітову маску логічних рівнів на [конфігураційних виводах завантаження ESP8266](root:cat-hw-boards/esp8266-boot-strapping-pins) (@@en|strapping pins@@, від англ. *strapping pins* — конфігураційні виводи завантаження) в момент зняття сигналу скидання. Фіксація низького логічного рівня `0` на виводі `GPIO15` (старший біт 2 у масці `x`) є критичною умовою для вибору конфігурації шини @@en|SPI Flash@@ і завантаження прошивки зі зовнішньої пам'яті; якщо ж на `GPIO15` подати високий рівень `1`, чип ігнорує флешпам'ять і перемикається у режим завантаження через інтерфейс @@en|SDIO@@ (від англ. *Secure Digital Input Output* — послідовний ввід-вивід) або тестовий режим. Другий параметр `y` також є 3-бітовим числом, що кодує налаштування живлення та ревізію напівпровідникового кристала чипа ESP8266EX. У той час як старший біт 2 відповідає за напругу живлення флешпам'яті (1 для 3.3 В і 0 для 1.8 В), молодші біти 0 та 1 відображають апаратну ревізію кристала й стан внутрішніх одноразових запобіжників @@en|eFuse@@. Зокрема, комбінація бітів 0 та 1 (значення 0, 1, 2 або 3) дозволяє ROM-завантажувачу визначити версію кремнієвого релізу SoC і коректно встановити внутрішні часові затримки шини SPI та ініціалізаційні константи системи відповідно до конкретного випуску кристала.

![Структура бітових полів параметра boot mode з прив'язкою до strapping-виводів та опцій ревізії чипа](img/esp8266-boot-mode-bit-field-structure.svg)
*Структура бітових полів параметра boot mode з прив'язкою до strapping-виводів та опцій ревізії чипа.*

У параметрі `x` біт 2 відповідає виводу `GPIO15`, біт 1 — `GPIO0`, а біт 0 — `GPIO2`:

Параметр `x` | Двійковий код (`GPIO15, GPIO0, GPIO2`) | Апаратний режим | Опис призначення
`3` | `011` | Flash Boot | Виконання користувацької прошивки зі зовнішньої флешпам'яті (@@en|SPI Flash@@)
`1` | `001` | UART Download | Перехід у режим оновлення прошивки через `UART0` за допомогою [інструментів прошивання ESP-01](root:cat-hw-boards/esp01-firmware-flashing)
`7` або `5` | `111` / `101` | SDIO Boot | Спроба завантаження через інтерфейс SDIO
`0` або `2` | `000` / `010` | Заборонений стан | Блокування запуску через низький логічний рівень на `GPIO2`

Другий параметр `y` розшифровує конфігурацію напруги живлення флешпам'яті та ревізію напівпровідникового кристала: старший біт 2 зі значенням `1` задає напругу `3.3 В` (код `y=6`), тоді як `0` перемикає регулятор на `1.8 В` (код `y=2` або `y=4`).

## Аналіз регістрів винятків процесорного ядра

При виникненні апаратних збоїв `rst cause:2` процесорне ядро Xtensa LX106 зберігає стан конвеєра в системних регістрах винятків. Особливо критичною є ситуація повторного виняткового стану @@en|Double Exception@@ (від англ. *Double Exception* — подвійний виняток), коли новий збій виникає безпосередньо під час обробки попереднього переривання. Оскільки в цей момент лічильник `epc1` вже зайнятий первинною адресою, ядро зберігає точну адресу інструкції повторного падіння в спеціалізованому регістрі `depc` (від англ. *Double Exception Program Counter* — лічильник програм подвійного винятку). Під час системної діагностики завантажувач виводить значення регістрів `epc1`, `epc2`, `epc3`, `depc`, `excvaddr` та `excsave1`:

1. `epc1` (Exception Program Counter 1): утримує точну адресу інструкції ассемблера, на якій сталося фатальне переривання першого рівня.
2. `excvaddr` (Exception Virtual Address): містить целеву віртуальну адресу пам'яті, звернення до якої викликало збій (наприклад, `0x00000000` при розіменуванні `NULL`).
3. `excsave1` (Exception Save 1): зберігає вміст регістра повернення `a0` перед переходом у векторну таблицю.
4. `epc2` та `epc3`: утримують лічильники інструкцій для винятків другого та третього рівнів пріоритету відповідно.

Зіставивши значення регістра `epc1` із файлом дизасемблювання прошивки `.out.S` (згенерованим інструментом `xtensa-lx106-elf-objdump -d`), розробник визначає точний рядок сирцевого коду C/C++, який спричинив падіння системи.

## Програмне зчитування стану через SDK та RTC

Для побудови відмовостійкої логіки додаток може програмно зчитати причину останнього перезавантаження після старту. В офіційному [наборі розробника ПЗ](root:cat-hw-boards/esp8266-soc-architecture-overview) (@@en|SDK@@) використовується функція `system_get_rst_info()`, яка повертає вказівник на структуру `struct rst_info`.

Нижче наведено приклад зчитування причин скидання та виводу діагностики:

:::tabs
```c|esp-sdk
#include "user_interface.h"

void check_reset_reason(void) {
    struct rst_info *rtc_info = system_get_rst_info();
    
    os_printf("Reset reason: %d\n", rtc_info->reason);
    if (rtc_info->reason == REASON_EXCEPTION_RST) {
        os_printf("Fatal exception (%d):\n", rtc_info->exccause);
        os_printf("epc1=0x%08x, excvaddr=0x%08x, depc=0x%08x\n",
                  rtc_info->epc1, rtc_info->excvaddr, rtc_info->depc);
    }
}
```
:::code api-esp8266-boot-log-codes-and-registers/cpp/arduino/rst-info.cpp
:::

Дані про причину скидання зберігаються у системних регістрах пам'яті годинника реального часу (@@en|RTC@@, від англ. *Real-Time Clock* — годинник реального часу) `RTC_STATE` та `SYS_BOOT`. Ця пам'ять зберігає свій вміст під час програмних перезапусків та спрацьовувань сторожового таймера, що дозволяє додатку верифікувати причину збою й виконувати безпечну повторну ініціалізацію периферії. Для практичного розширення системної діагностики розробники використовують функції SDK `system_rtc_mem_write` та `system_rtc_mem_read`, які дозволяють зберігати власні структури даних або дамп аварійного стану @@en|crash dump@@ у користувацькій області RTC-пам'яті (починаючи з 64-го 4-байтового блоку). Запис прапорців падіння, лічильників циклів фатальних перезавантажень або збережених регістрів безпосередньо перед скиданням дає змогу після перезапуску зчитати ці дані й прийняти рішення про перехід у безпечний режим або відправку діагностичного звіту на сервер.
