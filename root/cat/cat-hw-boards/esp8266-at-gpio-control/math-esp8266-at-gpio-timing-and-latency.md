## Затримка передачі пакета по UART

Коли зовнішній мікроконтролер відправляє текстову команду керування до [модуля ESP-01](root:cat-hw-boards/esp-01), першим фізичним бар'єром часу є передача електричних імпульсів через асинхронний послідовний інтерфейс (англ. @@en|UART@@, від Universal Asynchronous Receiver-Transmitter — універсальний асинхронний приймач-передавач). Кожен символ текстової @@en|AT-команди@@ перетворюється послідовним адаптером на часовий ряд логічних рівнів, де тривалість кожного біта `t_bit = 1 / B` жорстко визначена швидкістю передачі (англ. @@en|baud rate@@) `B`. Оскільки передача відбувається без спільного тактового сигналу, кожен байт обгортається службовими бітами для синхронізації приймача. Через неузгодженість фаз кварцових генераторів хоста та мікроконтролера приймач використовує апаратний 16-кратний оверсемплінг @@en|oversampling@@ з тактовим інтервалом дискретизації `T_sample = t_bit / 16 = 1 / (16 × B)`. Момент спадного фронту старт-біта може припадати на довільний момент усередині інтервалу дискретизації, що створює початковий часовий розкид фази зчитання `Δt_phase = T_sample = t_bit / 16`. Крім того, апаратний мажоритарний фільтр виконує стробування за правилом більшості ("2 з 3") на 7-му, 8-му та 9-му відліках `T_sample` від зафіксованого фронту, що додає фіксовану затримку підтвердження старт-біта `t_detect = 7 × T_sample = (7/16) × t_bit` з невизначеністю вибірки `±0.5 × T_sample` (±1/32 тривалості біта) ще до початку декодування даних кадру.

Структура одного кадру (англ. @@en|frame@@) містить один стартовий біт (англ. @@en|start bit@@), інформаційні біти даних, опціональний біт парності (англ. @@en|parity bit@@) та один або два стопові біти (англ. @@en|stop bit@@). Загальна кількість бітів `N_bits` для передачі одного байта обчислюється як сума всіх складників кадру:

```
N_bits = N_start + N_data + N_parity + N_stop
= 1 + 8 + 0 + 1      [стандартний режим 8N1]
= 10                 [бітів на один байт]
```

Час передачі одного біта `t_bit` обернено пропорційний бодовій швидкості `B` у бітах за секунду. Для знаходження часу передачі одного байта `t_byte` тривалість біта множиться на повну кількість бітів у кадрі `N_bits`:

```
t_byte = N_bits / B
= 10 / 115200        [для швидкості 115200 біт/с]
≈ 8.6806 × 10⁻⁵      [секунди]
≈ 86.81              [мікросекунди]
```

Текстова команда складається з послідовності символів заданої довжини `L_str` та завершується обов'язковим маркером повернення каретки й переведення рядка `\r\n` (двобайтовий термінатор). Отже, загальна кількість байтів у пакеті `N_bytes` дорівнює `L_str + 2`. Повна фізична затримка передачі пакета по шині `t_UART` обчислюється як добуток кількості байтів на тривалість передачі одного байта:

```
t_UART = N_bytes × t_byte
= (L_str + 2) × (N_bits / B)
```

Розглянемо типовий приклад команди зміни цифрового рівня виводу `AT+SYSGPIOWRITE=12,1\r\n`. Довжина текстового рядка без термінатора становить 20 символів, що разом із маркером `\r\n` дає 22 байти. При цьому порівняльний аналіз синтаксичних розширень AT-команд демонструє пропорційне зростання фізичної затримки `t_UART`: від 1.22 мс для короткої форми `AT+CIO=12,1\r\n` (14 байтів) і 1.65 мс для стандартної `AT+PINWRITE=12,1\r\n` (19 байтів) до 2.08 мс для повноформатної інструкції `AT+SYSGPIOWRITE=12,1,1\r\n` (24 байти). Якщо конфігурація послідовного порту використовує не стандартний формат `8N1` (`N_bits = 10`), а режим підвищеної надійності `8E2` з бітом парності `Parity` та двома стоповими бітами, то розмір одного кадру `N_bits_8E2` зростає до 12 бітів:

```
N_bits_8E2 = N_start + N_data + N_parity + N_stop
= 1 + 8 + 1 + 2      [режим 8E2: біт парності й два стопові біти]
= 12                 [бітів на один байт]
```

У цьому разі час передачі одного байта `t_byte_8E2` при швидкості `B = 115200` біт/с становить `12 / 115200 ≈ 104.17 мкс`. Для повного пакета з 22 байтів затримка передачі складає:

```
t_UART_8E2 = N_bytes × t_byte_8E2
= 22 × (12 / 115200) [перемноження 22 байтів на час байта в 8E2]
≈ 2.2917 × 10⁻³      [секунди]
≈ 2.29               [мілісекунди]
```

Порівняно зі стандартним режимом `8N1` (`t_UART ≈ 1.91 мс`), застосування конфігурації `8E2` створює додаткову затримку `Δt_UART`:

```
Δt_UART = t_UART_8E2 - t_UART_8N1
= 2.2917 - 1.9097    [різниця часу передачі пакета в мс]
≈ 0.3820             [мілісекунди]
= 382                [мікросекунди]
```

Таким чином, додавання контролю парності та другого стопового біта збільшує фізичну затримку пересилання пакета по шині `@@en|UART@@` на 20% (на 382 мкс), додаючи відчутний часовий оверхед під час високочастотного керування виводами `@@en|GPIO@@`.

**Обчислення часового порогу передачі для швидкості 115200 біт/с:**

```
t_UART = 22 × 86.81 × 10⁻⁶
= 1.9098 × 10⁻³      [перемноження кількості байтів на час байта]
≈ 1.91               [мілісекунди]
```

Зі зменшенням бодової швидкості до застарілого значення 9600 біт/с час передачі того самого пакета зростає пропорційно зменшенню частоти тактування бітів:

```
t_UART = 22 × (10 / 9600)
= 22 × 1.0417 × 10⁻³ [час одного байта становить 1.042 мс]
≈ 22.92              [мілісекунди]
```

Однак у реальних системах, де керуючий хост-мікроконтролер формує символи програмним шляхом або працює під управлінням операційної системи, між сусідніми байтами виникають додаткові міжсимвольні паузи (англ. @@en|inter-byte gap@@ — міжсимвольна пауза) `t_gap`. Модель реального часу передачі `t_UART_real` враховує сумарний внесок `(N_bytes - 1)` пауз між `N_bytes` байтами кадру:

```
t_UART_real = t_UART + (N_bytes - 1) × t_gap
= 22.92 мс + (22 - 1) × 0.5 мс
= 22.92 мс + 10.50 мс
= 33.42              [мілісекунди]
```

Якщо хост-контролер додає міжсимвольну паузу всього 0.5 мс (наприклад, через квантування системного таймера або обробку переривань), підсумкова фізична затримка передачі пакета зростає з 22.92 мс до 33.42 мс. Навіть при швидкості 115200 біт/с наявність міжсимвольних пауз `t_gap = 100 мкс` збільшує час доставки з 1.91 мс до 4.01 мс, подвоюючи фізичну латентність шини.

```
t_UART = 22 × (10 / 9600)
= 22 × 1.0417 × 10⁻³ [час одного байта становить 1.042 мс]
≈ 22.92              [мілісекунди]
```

Отже, лише фізична доставка текстового пакета по шині @@en|UART@@ на швидкості 115200 біт/с створює непоборний нижній поріг затримки близько 1.91 мс. Застосування нижчих швидкостей передачі перетворює послідовну шину на головне вузьке місце системи, додаючи понад 20 мс затримки ще до початку обробки команди мікроконтролером.

## Затримка AT-інтерпретатора та MMIO

Після того як останній біт стопового інтервалу передано по фізичній лінії, обробка команди переходить у внутрішні обчислювальні структури мікроконтролера [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). Приймач @@en|UART@@ генерує переривання (англ. @@en|interrupt service routine@@, @@en|ISR@@), яке копіює байти з апаратного буфера @@en|FIFO@@ у кільцевий буфер (англ. @@en|ring buffer@@) текстового інтерпретатора. Під час розбору командного рядка виконання коду інтерпретатора зазнає додаткових затримок вибірки інструкцій через промахи кешу @@en|ICACHE@@ (англ. @@en|cache miss@@), коли відсутні в оперативній пам'яті ділянки коду парсера підвантажуються з флеш-пам'яті по шині SPI. Кожен промах лінії кешу розміром 16 байтів викликає апаратний простій процесора тривалістю `N_miss_cycles = 12..40` тактів ядра. При здійсненні `M_miss = 20` промахів під час виконання довгої гілки розбору символів сумарний часовий штраф кешу `t_ICACHE` розраховується як `t_ICACHE = (M_miss × N_miss_cycles) / f_CPU = (20 × 32) / 80000000 = 8.0 мкс`, збільшуючи тривалість фази розбору. Загальна підсумкова затримка реакції виводу (англ. @@en|latency@@, від лат. lateo — ховатися) складається з трьох послідовних етапів.

Математична модель повної затримки `t_total` виражається сумою фізичного часу передачі по шині та трьох фаз внутрішньої обробки:

```
t_total = t_UART + t_ISR + t_parse + t_exec
```

Фаза обробки переривань `t_ISR` складається з часу входу в контекст обробника та переміщення байтів у пам'ять (зазвичай 5–15 мкс). При спрацьовуванні апаратного переривання приймача @@en|UART@@ процесорне ядро Xtensa L106 витрачає додаткові такти на збереження регістрового контексту — примусовий скид поточного стану апаратного конвеєра та збереження вмісту загальних регістрів `a0`–`a15`, регістра адреси повернення та регістра зсуву `SAR` у стек. Оскільки ядро L106 не має апаратного віконного механізму регістрів, збереження та подальше відновлення контексту виконується програмно інструкціями `s32i`/`l32i`. Кількісний розклад цього перемикання становить 28 тактів на збереження контексту (4 такти на скид конвеєра й векторний стрибок, 16 тактів `s32i` для регістрів `a0`–`a15` і 8 тактів `rsr`/`s32i` для спеціальних регістрів `SAR`, `EPC1`, `EXCCAUSE`) та 28 тактів на його відновлення (16 тактів `l32i`, 8 тактів завантаження спецрегістрів і 4 такти інструкції повернення `rfe`). Сумарний фіксований обчислювальний штраф становить `N_context_cycles = 56` тактів ядра (близько 0.7 мкс при 80 МГц) при кожному виклику @@en|ISR@@ перед початком копіювання байтів із буфера @@en|FIFO@@. Фаза розбору рядка `t_parse` вимагає лексичного аналізу тексту, порівняння командних лексем, виділення параметрів із символьного вигляду в цілі числа та перевірки синтаксису. Оскільки програмний код інтерпретатора виконує багаторазові виклики функцій порівняння рядків та декодування десяткових значень, час `t_parse` залежить від частоти процесора `f_CPU` та кількості інструкцій розбору `N_inst`:

```
t_parse = N_inst / f_CPU
= 40000 / 80000000   [при 40 тисячах інструкцій на розбір базової команди й 80 МГц тактування]
= 5.0 × 10⁻⁴         [секунди]
= 500                [мікросекунди]
```

Для складних або розширених команд із кількома десятковими параметрами та виділенням рядкових аргументів у лапках (наприклад, `AT+CIPSTART=0,"TCP","192.168.1.100",8080\r\n`) кількість інструкцій парсера `N_inst_ext` зростає до 120 000 через додатковий пошук роздільників, перевірку меж буферів та конвертацію IP-адреси. Порівняльний розрахунок часу розбору розширеної команди показує трикратне зростання затримки парсингу:

```
t_parse_ext = N_inst_ext / f_CPU
= 120000 / 80000000  [при 120 тисячах інструкцій на розбір багатопараметричної команди]
= 1.5 × 10⁻³         [секунди]
= 1.5                [мілісекунди]
```

Таким чином, розбір текстового рядка розширеної команди триває 1.5 мс, що втричі перевищує затримку розбору простої команди прямого запису виводу (`500 мкс`). Це підтверджує, що складність лексичного аналізу текстового протоколу є основним обчислювальним бар'єром під час роботи інтерпретатора.

```
t_parse = N_inst / f_CPU
= 40000 / 80000000   [при 40 тисячах інструкцій на розбір команди й 80 МГц тактування]
= 5.0 × 10⁻⁴         [секунди]
= 500                [мікросекунди]
```

Фаза безпосереднього виконання `t_exec` включає виклик функції системного драйвера виводів (англ. @@en|GPIO@@, від General-Purpose Input/Output — цифровий порт загального призначення) та оновлення регістра стану. Підсумковий розрахунок повної затримки для команди на швидкості 115200 біт/с при `t_parse = 500 мкс`, `t_ISR = 10 мкс` та `t_exec = 10 мкс`:

```
t_total = t_UART + t_ISR + t_parse + t_exec
= 1.91 мс + 0.01 мс + 0.50 мс + 0.01 мс
= 2.43               [мілісекунди]
```

Для оцінки ефективності порівняємо цей результат із прямим доступом до регістрів введення-виведення (англ. @@en|memory-mapped I/O@@, @@en|MMIO@@ — введення-виведення, відображене в адресний простір). У разі прямого виконання прошивки на самому мікроконтролері зміна стану виводу здійснюється одною інструкцією запису в регістр встановлення `GPIO_OUT_W1TS` або скидання `GPIO_OUT_W1TC`. Час прямого виконання `t_MMIO` визначається лише періодом тактування ядра `T_CPU = 1 / f_CPU`:

```
t_MMIO = 1 / f_CPU
= 1 / 80000000       [при частоті ядра 80 МГц]
= 1.25 × 10⁻⁸        [секунди]
= 12.5               [наносекунди]
```

Коефіцієнт накладних витрат `K_overhead`, який показує уповільнення реакції при використанні @@en|AT-команд@@ порівняно з прямим @@en|MMIO@@, обчислюється як відношення підсумкових затримок:

```
K_overhead = t_total / t_MMIO
= 2.43 × 10⁻³ / 12.5 × 10⁻⁹
= 194400             [разів]
```

Максимальна теоретична частота перемикання цифрового виводу `f_max` при постійній відправці команд встановлення й скидання рівня обмежується подвійною повною затримкою:

```
f_max = 1 / (2 × t_total)
= 1 / (2 × 2.43 × 10⁻³)
≈ 205.76             [Герц]
```

Такий розрахунок демонструє, що текстовий інтерпретатор створює понад 190 000-кратне обчислювальне уповільнення порівняно з прямим керуванням регістрами, обмежуючи граничну частоту пульсації виводів значенням близько 205 Гц. Це робить керування через @@en|AT-команди@@ непридатним для високошвидкісних імпульсних протоколів і вимагає чіткого врахування часового бюджету в системних розрахунках.

## Формула джитера та фазового зсуву

Навіть якщо швидкість передачі по шині та середня затримка розбору команд зафіксовані, реальний інтервал між послідовними комутаціями виводів піддається випадковим часовим коливанням — фазовому джитеру (англ. @@en|jitter@@ — тремтіння, коливання). У мікроконтролерах [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) джерелом цієї нестабільності є недетерміновані затримки обробки радіочастотного стеку Wi-Fi, фонові калібрування трансивера, конкуренція за доступ до оперативної пам'яті, а також температурний дрейф @@en|thermal drift@@ внутрішніх RC-генераторів тактування. Під час імпульсних сплесків споживання Wi-Fi передавача кристал розігрівається, викликаючи температурну нестабільність частоти генератора `Δf_RC / f_RC` до 0.5–1.5%, що додатково модулює тривалість програмних та таймерних інтервалів. За умов тривалого мережевого обміну статистичний розподіл затримок підпорядковується нормальному закону `N(μ_jitter, σ_jitter²)` із середнім зсувом `μ_jitter = 0.5 мс` та середньоквадратичним відхиленням `σ_jitter = 0.8 мс`. Ймовірність виникнення критичного фазового зсуву `P(Δt > Δt_limit)` для порогу `Δt_limit = 2.0 мс` обчислюється через функцію нормованого відхилення `z = (Δt_limit - μ_jitter) / σ_jitter = (2.0 - 0.5) / 0.8 = 1.875`, що дає ймовірність одиничної збійної команди `P ≈ 3.04%`. При тривалій серії з `M = 1000` перемикань ймовірність хоча б одного перевищення припустимого допуску становить `P_fail = 1 - (1 - P)ᴹ = 1 - (1 - 0.0304)¹⁰⁰⁰ ≈ 99.99%`, роблячи зрив детермінованого таймінгу неминучим.

Кожен очікуваний момент зміни стану виводу `t_exp` відхиляється на додаткову часову величину `Δt`, утворюючи фактичний момент спрацьовування `t_act`. Модель фазової нестабільності враховує три незалежні компоненти часового відхилення:

```
t_act = t_exp + Δt_wifi + Δt_host + Δt_uart
```

Де `Δt_wifi` — варіація затримки, викликана високопріоритетними перериваннями стеку Wi-Fi (до 2–5 мс під час передачі пакетів або фонового сканування); `Δt_host` — джитер буферизації та квантування часу у внутрішньому циклі хост-контролера; `Δt_uart` — джитер апаратного розкладання кадру на бодові інтервали. Размах джитера від піку до піку (англ. @@en|peak-to-peak jitter@@) `J_pp` визначається як різниця між найпізнішим та найранішим моментом виконання:

```
J_pp = Δt_max - Δt_min
```

Для статистичного оцінювання стабільності керування використовують середньоквадратичне відхилення (англ. @@en|root mean square@@, @@en|RMS@@) джитера `J_rms` для серії з `N` вимірів відносно середнього часу затримки `t_avg`:

```
J_rms = √( (1 / N) × ∑ (t_act,i - t_avg)² )
```

Часове тремтіння викликає фазовий зсув (англ. @@en|phase shift@@ — зсув фази) `Δφ` у градусах для згенерованого періодичного сигналу заданої частоти `f_signal`:

```
Δφ = 360° × f_signal × J_pp
```

**Обчислення фазової похибки для сигналу частотою 50 Герц при розмаху джитера 2.5 мілісекунди:**

```
Δφ = 360° × 50 × 2.5 × 10⁻³
= 18000 × 2.5 × 10⁻³ [перемноження частоти на кутовий коефіцієнт]
= 45°                [градусів]
```

Фазове відхилення у 45° означає спотворення чверті напівперіоду сигналу, що унеможливлює точне фазове керування (наприклад, тиристорними регуляторами потужності).

У системах реального часу відносна припустима похибка часового інтервалу `ε_rel = J_pp / T_exp` не повинна перевищувати встановлений технологічний допуск (типово `ε_rel ≤ 0.05`, тобто 5%). Звідси виводиться максимальна частота детермінованої комутації `f_realtime_max` для [модулів ESP-01S](root:cat-hw-boards/esp-01s):

Під час пікових затримок радіочастотного стеку @@en|Wi-Fi@@ обробка вхідних текстових інструкцій в @@en|ESP8266@@ призупиняється на тривалість `Δt_wifi_max` (до 5–10 мс), що вимагає розрахунку мінімального обсягу кільцевого буфера (англ. @@en|ring buffer@@, від англ. @@en|ring@@ — кільце та @@en|buffer@@ — пом'якшувач поштовху; @@en|кільцевий буфер ring buffer@@) хост-процесора та оцінки наповнення внутрішнього апаратного буфера @@en|UART RX FIFO@@. Оскільки кристал ESP8266 має апаратний приймальний буфер ємністю `N_fifo = 128` байтів, при бодовій швидкості `R_baud = 115200` біт/с надходження даних зі швидкістю `R_byte = 115200 ÷ 10 = 11520` байтів/с заповнює весь буфер за час `t_overflow = N_fifo ÷ R_byte = 128 ÷ 11520 ≈ 11.11` мс. За відсутності апаратного контролю потоку @@en|RTS/CTS@@ та при встановленому пороговому рівні переривання (англ. @@en|watermark threshold@@, від @@en|watermark@@ — рівень води та @@en|threshold@@ — поріг) `N_thresh = 100` байтів часовий запас до повного переповнення становить лише `Δt_margin = (N_fifo - N_thresh) ÷ R_byte = (128 - 100) ÷ 11520 ≈ 2.43` мс; якщо затримка обробки `Δt_wifi_max` перевищує цей інтервал, вхідний FIFO переповнюється і символи `AT-команд` губляться. Якщо хост продовжує передавати кадри @@en|AT-команд@@ зі швидкістю `R_baud = 115200` біт/с без використання апаратного контролю потоку `RTS/CTS`, необхідна ємність буфера `B_buf` у байтах визначається з виразу:

```
B_buf = ⌈ (R_baud × Δt_wifi_max) / N_bits_per_byte ⌉
```

Де `N_bits_per_byte = 10` біт/байт для кадру 8N1.

**Обчислення ємності буфера хоста для компенсації затримки 10 мілісекунд:**

```
B_buf = ⌈ (115200 × 10 × 10⁻³) / 10 ⌉
= ⌈ (115200 × 10⁻²) / 10 ⌉           [перемноження часу на швидкість]
= ⌈ 1152 / 10 ⌉                       [обчислення кількості переданих бітів]
= 116                                 [байтів]
```

Для запобігання втратам пакетів даних у [мережевих сокетах TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets) вихідний буфер хост-контролера повинен вміщувати не менше 116 байтів неперервного потоку команд.

```
f_realtime_max = ε_rel / J_pp
= 0.05 / (2.5 × 10⁻³)
= 20                 [Герц]
```

Математичний аналіз показує, що через високий размах джитера Wi-Fi стеку (до 2.5 мс) гранична частота детермінованого керування виводами без втрати фазової точності становить лише 20 Гц. Для задач із суворішими вимогами до часу необхідно відмовлятися від текстових @@en|AT-команд@@ на користь прямого апаратного ШІМ чи генерації імпульсів на боці хост-процесора.
