## Чому неконтрольовані сокети спричиняють аварійні перезавантаження

Коли керуючий @@en|host@@-мікроконтролер ініціалізує бездротовий модуль та почергово відкриває мережеві з'єднання для опитування серверів, обмін трафіком спочатку проходить успішно. Проте після чергової команди відкриття сокета модуль раптом перестає відповідати на командні рядки, виводить у порт службове сміття та самовільно перезавантажується. Хост-контролер втрачає контекст сесій, а пристрій потрапляє у цикл безкінечних перезапусків.

Причина такої поведінки полягає у фізичних обмеженнях оперативної пам'яті @@en|RAM@@ (від англ. *Random Access Memory* — пам'ять з довільним доступом) мікроконтролера. Як описує [апаратна архітектура SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), із 80 КБ статичної пам'яті @@en|DRAM@@ більша частина зарезервована під Wi-Fi стек і системні потреби. Для динамічного виділення в прошивці @@en|ESP-AT@@ залишається область купи (англ. *heap* — купа, динамічна пам'ять) обсягом лише 20–35 КБ.

Кожен відкритий мережевий сокет (англ. *socket* — гніздо, роз'єм) є складною динамічною структурою даних у пам'яті. Як демонструє [мережевий стек lwIP у ESP8266](root:cat-hw-boards/lwip-architecture-esp8266), для підтримки кожного @@en|TCP@@-з'єднання система виділяє блок керування протоколом (@@en|PCB@@, від англ. *Protocol Control Block*), масиви пакетних буферів (@@en|pbuf@@, від англ. *packet buffer*) та буфери ковзного вікна (@@en|TCP Window@@). Одиночний @@en|TCP@@-сокет потребує від 3 до 6 КБ оперативної пам'яті лише для збереження стану та проміжних кадрів.

Використання шифрованих з'єднань критично ускладнює ситуацію. Коли модуль встановлює захищену сесію, [криптографічний стек mbedTLS у вбудованих](root:cat-hw-boards/mbedtls-embedded-crypto-library) системах вимагає виділення буферів під час рукостискання (@@en|handshake@@). Обробка записів @@en|TLS Record Layer@@ та сертифікатів потребує від 16 до 24 КБ неперервного простору в купі. Спроба відкрити @@en|SSL/TLS@@ сокет без перевірки пам'яті призводить до відмови функції malloc().

Через вичерпання ресурсу купи або її дрібнення (англ. *memory fragmentation* — розбиття суцільного масиву пам'яті на дрібні фрагменти) виклик malloc() повертає нульовий вказівник. Відсутність перевірки меж пам'яті в мережевому стеку спричиняє розіменування нульового вказівника (@@en|NULL pointer dereference@@) та системну помилку ядра (@@en|Fatal exception 28@@). Апаратний сторожовий таймер (@@en|Watchdog Timer@@ / @@en|WDT@@) негайно перезавантажує кристал, виводячи у порт рядок wdt reset або 
st cause:2.

Щоб запобігти нештатним ситуаціям, хост-мікроконтролер зобов'язаний виконувати суворий моніторинг вільних системних ресурсів. Діагностика доступного обсягу купи та системних сповіщень модуля перед кожною ініціалізацією сокета є єдиним надійним способом уникнути аварійних відмов.

## Діагностика системної пам'яті та повідомлень

Контроль стану внутрішніх ресурсів прошивки @@en|ESP-AT@@ починається з оцінки залишкового обсягу оперативної пам'яті в купі опитувальною командою `AT+SYSRAM?`. Цей запит повертає хост-мікроконтролеру точну кількість вільних байтів у динамічній пам'яті модуля перед викликом ресурсоємних мережевих операцій.

Синтаксис команди відповідає стандартній опитувальній формі `AT+<Name>?` ([огляд базового командного інтерфейсу ESP-AT](root:cat-hw-boards/esp-at-command-set-overview)). При надсиланні запиту через послідовний порт модуль негайно повертає обсяг вільних байтів:

```
AT+SYSRAM?
+SYSRAM:28416

OK
```

Числове значення (тут `28416` байтів) показує розмір вільного простору купи для сокетів і системних структур. Хост-контролер порівнює його з мінімально допустимим порогом оперативної пам'яті (англ. *RAM threshold* — граничний розмір пам'яті). Для відкриття звичайного @@en|TCP@@ або @@en|UDP@@ сокета безпечний поріг становить 6–8 КБ, а для захищеної @@en|SSL/TLS@@ сесії — не менше 24–28 КБ. Якщо залишок менший за поріг, хост мусить відкласти відкриття з'єднання або закрити неактивні сокети.

Другим інструментом діагностики є команда керування системними повідомленнями `AT+SYSMSG`. Вона налаштовує рівень деталізації службових сповіщень, які модуль виводить у послідовний порт при виникненні подій або помилок:

```
AT+SYSMSG=<mode>
```

Параметр `<mode>` задає рівень відображення інформації:
- `0` — режим за замовчуванням (лише стандартні відповіді `OK`, `ERROR` та `BUSY`);
- `1` — виведення розширених сповіщень про стан системи та вичерпання ресурсів.

Поточний режим зчитують опитувальною формою `AT+SYSMSG?`. При активованому розширеному режимі (`AT+SYSMSG=1`) під час дефіциту пам'яті модуль висилає сповіщення про вичерпання купи або помилки мережевого стека. Як зазначає [мережевий стек LwIP 2.x у вбудованих](root:cat-hw-boards/lwip-stack-architecture-in-embedded) системах, аналіз цих повідомлень дозволяє відокремити помилки мережевого рівня від апаратного вичерпання пам'яті.

Приклад реалізації перевірки доступної пам'яті перед відкриттям мережевої сесії:

:::tabs


Систематичний моніторинг пам'яті перед зміною мережевої конфігурації готує систему до налаштування режимів мультиплексування та безпечного керування з'єднаннями.

## Керування з'єднаннями та режимами мультиплексування

Конфігурування мережевих сокетів починається з вибору режиму мультиплексування (англ. *multiplexing* — поєднання кількох каналів в один) за допомогою команди `AT+CIPMUX`. Вона визначає, чи працюватиме модуль із єдиним з'єднанням, чи підтримуватиме кілька паралельних сокетів:

- `0` — режим одиночного з'єднання (англ. *single connection*), необхідний для активації наскрізного режиму передачі даних (англ. *pass-through mode* або *unvarnished mode*);
- `1` — режим мультиплексованого з'єднання (англ. *multiple connections*), що дозволяє одночасно відкривати до 5 сокетів із ідентифікаторами з'єднання (англ. *link ID*) від `0` до `4`.

Важливим системним інваріантом є те, що зміна режиму `AT+CIPMUX` можлива лише тоді, коли всі сокети закриті. Якщо хост спробує виконати `AT+CIPMUX=1` за наявності активного з'єднання, прошивка відхилить команду й поверне статус `ERROR`.

Для відкриття сесії викликом `AT+CIPSTART` використовується наступний синтаксис:

У режимі одиночного з'єднання (`AT+CIPMUX=0`):
```
AT+CIPSTART=<type>,<addr>,<port>[,<keepalive>]
```

У режимі мультиплексування (`AT+CIPMUX=1`):
```
AT+CIPSTART=<link_id>,<type>,<addr>,<port>[,<keepalive>]
```

Параметри включають ідентифікатор `<link_id>` (`0`–`4`), тип протоколу `<type>` (`"TCP"`, `"UDP"` або `"SSL"`), IP-адресу чи домен `<addr>` та віддалений порт `<port>`. Використання шифрування висвітлюють [захищені SSL/TLS з'єднання в AT-прошивці](root:cat-hw-boards/esp8266-at-ssl-tls).

Завершення мережевого з'єднання виконується командою `AT+CIPCLOSE`. У режимі одиночного з'єднання команда надсилається без параметрів (`AT+CIPCLOSE`), а у режимі мультиплексування вказується ідентифікатор: `AT+CIPCLOSE=<link_id>`. Передавання значення `AT+CIPCLOSE=5` примусово закриває всі відкриті сокети одночасно.

Для опитування поточного стану активних з'єднань слугує команда `AT+CIPSTATUS`. У відповідь модуль повертає загальний статус мережевого стека та перелік відкритих сокетів:

```
STATUS:<stat>
+CIPSTATUS:<link_id>,<type>,<addr>,<port>,<local_port>,<tetype>
```

Код стану `<stat>` інтерпретується кінцевим автоматом (@@en|finite state machine@@ / @@en|FSM@@) хоста:
- `2` — модуль отримав IP-адресу у Wi-Fi мережі, але сокети закриті;
- `3` — щонайменше один сокет у підключеному стані;
- `4` — усі сокети закриті, з'єднання відсутнє;
- `5` — Wi-Fi з'єднання з точкою доступу втрачено.

Накладання цих команд на життєвий цикл сокета демонструє представлена нижче схема станів.

*Діаграма станів мережевого сокета ESP8266 AT: послідовність переходів між ініціалізацією режиму мультиплексування, відкриттям, моніторингом та закриттям з'єднання.*

Додатково команда `AT+CIPMODE=<mode>` задає режим передачі даних. Звичайний режим (`AT+CIPMODE=0`) вимагає явних команд передачі та асинхронних кадрів прийому, а перемикання у наскрізний режим (`AT+CIPMODE=1`) перетворює послідовний порт на прозорий тунель до віддаленого сокета. ## Прийом та передавання буферизованого трафіку

Обмін мережевим трафіком через послідовний порт у прошивці @@en|ESP-AT@@ здійснюється кількома механізмами, які відрізняються ступенем буферизації та навантаженням на хост-мікроконтролер.

Ззвичайне передавання через `AT+CIPSEND` описує [протокол двофазної передачі даних AT+CIPSEND](root:cat-hw-boards/esp8266-at-cipsend-handshake). Хост вказує довжину масиву, чекає на запрошення `>` і надсилає корисне навантаження (англ. *payload* — корисні дані). Однак `AT+CIPSEND` блокує програму хоста до отримання статусу `SEND OK`, що знижує продуктивність.

Для оптимізації передачі застосовують асинхронне буферизоване надсилання `AT+CIPSENDBUF`:

```
AT+CIPSENDBUF=<link_id>,<length>
```

На відміну від `AT+CIPSEND`, `AT+CIPSENDBUF` виділяє сегмент у черзі передачі @@en|lwIP@@ та негайно повертає ідентифікатор `><segment_id>,` після завантаження даних у буфер модуля, не чекаючи підтвердження (@@en|TCP ACK@@) від сервера. Хост відправляє наступні порції даних без простоїв інтерфейсу.

Прийом трафіку здійснюється асинхронно або пасивно.

За замовчуванням діє **асинхронний режим прийому** (`AT+CIPRECVMODE=0`). Отримавши @@en|TCP@@-пакет, модуль виводить його вміст у порт як незапитане сповіщення (@@en|URC@@, від англ. *Unsolicited Result Code*):

```
+IPD,<link_id>,<len>:<data>
```

Правила його опрацювання розкриває [потоковий розбір асинхронних кадрів IPD](root:cat-hw-boards/esp8266-at-ipd-parser). Кадр `+IPD` може надійти у порт у довільний момент, наприклад під час обробки іншої AT-команди. Якщо хост не встигає зчитувати потік, [апаратні FIFO-буфери інтерфейсу UART](root:cat-hw-boards/esp8266-uart-hardware-fifo) переповнюються, спричиняючи втрату символів і руйнування меж кадрів.

Для запобігання втратам вмикають **пасивний режим прийому** (англ. *passive receive*) командою `AT+CIPRECVMODE=1`. Модуль накопичує вхідні пакети у буферах @@en|lwIP@@ і відправляє лише коротке сповіщення:

```
+IPD,<link_id>,<len>
```

Отримавши його, хост за потреби вичитує накопичені байти командою `AT+CIPRECVDATA`:

```
AT+CIPRECVDATA=<link_id>,<max_len>
```

У відповідь модуль повертає обсяг зчитаних даних і сам масив:

```
+CIPRECVDATA:<actual_len>,<data>

OK
```

Розподіл потоків даних між буферами та послідовним портом зображено на архітектурній схемі.

*Архітектурний потік даних при обміні мережевим трафіком: порівняння прямих асинхронних сповіщень +IPD та пасивного вичитування буферів через AT+CIPRECVDATA.*

Пасивний прийом повністю усуває загрозу переповнення прийомних буферів хоста та розриву синтаксичних відповідей у послідовному порту.

## Аналіз статусів відповідей та помилок

Обмін через прошивку @@en|ESP-AT@@ зазнає збоїв через мережеві таймаути, вичерпання пам'яті чи розрив сокетів. Без обробки статусів і сповіщень кінцевий автомат (@@en|FSM@@) хоста зависає в очікуванні відповіді.

Відповіді модуля поділяють на три типи:
1. **Фінальні статуси** — `OK` підтверджує виконання, а `ERROR` вказує на синтаксичну помилку, некоректний параметр або відмову мережевого стека. 2. **Статуси зайнятості** — рядки `BUSY p...` (обробка системної задачі) та `BUSY s...` (надсилання даних) вимагають часової паузи — @@en|retry backoff@@ (від англ. *retry* — повторювати + *backoff* — відступати) перед новим запитом. 3. **Асинхронні події** — сповіщення про зміну стану сокетів, як-от `<link_id>,CONNECT` (сокет відкрито) чи `<link_id>,CLOSED` (сокет закрито віддаленою стороною або за таймаутом).

При мережевих збоях модуль повертає розширений код помилки — @@en|extended error code@@ (від англ. *extended* — розширений + *error* — помилка + *code* — код) у форматі `+CME ERROR: <code>` або відмови:
- `+CME ERROR: 50` — брак пам'яті купи (недостатньо @@en|RAM@@ для об'єкта сокета);
- `+CME ERROR: 52` — таймаут з'єднання для `AT+CIPSTART`;
- `+CME ERROR: 54` — відмова у з'єднанні (сервер скинув прапор @@en|TCP RST@@ або порт зачинено);
- `link is not valid` — звернення за неіснуючим або закритим `<link_id>`.

Для захисту від зависань алгоритм @@en|FSM@@ хоста обробляє операції з неблокуючими таймаутами згідно з [базовою системою AT-команд](root:cat-hw-boards/esp8266-at-command-set-overview). Якщо маркер `OK` чи `ERROR` не надходить за визначений інтервал (наприклад, 10 секунд для `AT+CIPSTART`), @@en|FSM@@ скасовує стан і запускає відновлення.

При сповіщенні `CLOSED` хост ініціює автовідновлення сесії — @@en|session auto-recovery@@. При повторних помилках або відсутності відповіді на `AT` застосовують скид через [виводи завантаження ESP8266](root:cat-hw-boards/esp8266-boot-strapping-pins) (вивід @@en|RST@@) або команду `AT+RST`.
