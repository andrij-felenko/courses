## Втрата даних у ланцюжку UART-Wi-Fi

Під час розробки пристроїв на базі [мікроконтролера ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), що взаємодіють з хостом через [прошивку ESP-AT](root:cat-hw-boards/esp-at-command-set-overview), розробники часто стикаються зі спорадичною втратою даних та неочікуваними стрибками затримок. Типова ситуація виникає під час передачі інтенсивних сплесків трафіку в режимі [двофазної передачі даних](root:cat-hw-boards/esp8266-at-cipsend-handshake) `AT+CIPSEND` або в прозорому режимі (від англ. @@en|passthrough mode@@ — режим наскрізної передачі). Інженер, прагнучи прискорити обмін, підвищує швидкість послідовного порту до максимальних значень і виділяє великий приймальний буфер на хості, однак пакети все одно втрачаються, а TCP-з'єднання періодично розривається через таймаути.

Причина цієї проблеми полягає в принциповій відмінності фізичної природи двох середовищ передачі. Послідовний інтерфейс @@en|UART@@ (від англ. @@en|Universal Asynchronous Receiver-Transmitter@@ — універсальний асинхронний приймач-передавач) подає дані як безперервний детермінований потік байтів зі сталою швидкістю надходження (від англ. @@en|throughput@@ — пропускна здатність). Натомість мережевий тракт @@en|Wi-Fi@@ передає дані дискретними пакетами через спільне радіосередовище, де виникають затримки повторного доступу до каналу, перепідтвердження кадрів та обробка протокольних заголовков [мережевого стека lwIP](root:cat-hw-boards/lwip-architecture-esp8266).

Усередині прошивки ESP8266 дані проходять крізь послідовний ланцюжок з чотирьох послідовних буферних каскадів:
1. Апаратний приймальний буфер @@en|UART RX FIFO@@ обсягом 128 байтів. 2. Кільцевий буфер оперативної пам'яті (від англ. @@en|ring buffer@@ — кільцевий буфер), керований операційною системою @@en|FreeRTOS@@. 3. Пакетні буфери (від англ. @@en|packet buffer@@ — пакетний буфер, @@en|pbuf@@) мережевого стека lwIP. 4. Апаратна черга передавача мережевого контролера @@en|Wi-Fi MAC@@.

Кожен із цих каскадів характеризується власним темпом наповнення `R_in` (у байтах за секунду) та темпом розвантаження `R_out`. Якщо на будь-якому проміжному етапі вхідний темп перевищує вихідний, виникає динамічне накопичення даних. Загальний обсяг накопичених байтів у системі `N_total(t)` у момент часу `t` описується інтегральним балансом потоків:

```
N_total(t)
= ∫₀ᵗ (R_in(τ) - R_out(τ)) dτ      [інтегральний баланс накопичення]
```

Значення `N_total(t)` показує поточну кількість байтів, що перебувають у буферній мережі між приймачем UART та випромінювачем Wi-Fi. Якщо сумарний обсяг байтів перевищує доступну ємність пам'яті `C_total`, виникає переповнення буфера (від англ. @@en|buffer overflow@@ — переповнення буфера), і всі наступні байти безповоротно втрачаються. Щоб запобігти втраті трафіку, необхідно побудувати точну математичну модель кожного етапу буферизації, починаючи з фізичних параметрів UART.

## Математика фізичної пропускної здатності UART

Для кількісної оцінки темпу надходження даних `R_in` необхідно врахувати структуру фізичного кадру UART. Швидкість лінії задається бодрейтом (від англ. @@en|baud rate@@ — швидкість передачі сигналів) `B`, який визначає кількість фізичних бітових інтервалів за одну секунду. Проте кожен байт корисного навантаження (від англ. @@en|payload@@ — корисне навантаження) обгортається службовими розрядами: стартовим бітом `N_start`, бітом парності `N_parity` та стоповими бітами `N_stop`.

Загальна кількість бітів `N_frame`, необхідна для передачі одного байта корисних даних, обчислюється як сума розрядів фізичного кадру:

```
N_frame
= N_start + N_data + N_parity + N_stop      [сума розрядів кадру]
```

У стандартній конфігурації 8N1 (8 бітів даних, без парності, 1 стоповий біт) значення складають `N_start = 1`, `N_data = 8`, `N_parity = 0`, `N_stop = 1`, що дає `N_frame = 10` бітів на кожен байт. Тривалість передачі одного кадру `T_frame` у секундах є оберненою величиною до бодрейту, помноженої на довжину кадру:

```
T_frame
= N_frame ÷ B      [тривалість одного кадру]
```

Оскільки з `N_frame` бітів лише `N_data` містять інформацію, ефективний коефіцієнт використання фізичного каналу (від англ. @@en|framing overhead@@ — кадрові накладні витрати) `η_uart` показує частку корисного трафіку:

```
η_uart
= N_data ÷ N_frame      [частка корисних даних]
```

Для режиму 8N1 ефективність становить `η_uart = 8 / 10 = 0.8` (або 80%), тобто 20% смуги пропускання витрачається на кадрування. Реальний темп надходження корисних байтів `R_in` на вхід мікроконтролера становить:

```
R_in
= B ÷ N_frame      [темп надходження корисних байтів]
```

Ці байти потрапляють у приймальний [апаратні FIFO-буфери UART](root:cat-hw-boards/esp8266-uart-hardware-fifo) ESP8266, який має фіксовану ємність `C_fifo = 128` байтів. Якщо обробник переривань не розвантажує буфер, час його повного заповнення `T_fifo_full` розраховується діленням ємності на темп надходження:

```
T_fifo_full
= C_fifo ÷ R_in      [час повного заповнення FIFO]
= (C_fifo × N_frame) ÷ B      [підстановка темпу надходження]
```

**Обчислення часу заповнення FIFO при швидкості 921600 бод**

```
B = 921600 Baud, N_frame = 10 bit, C_fifo = 128 byte
R_in = 921600 ÷ 10 = 92160 byte/s
T_fifo_full = 128 ÷ 92160 ≈ 0.001389 s [1.389 ms]
```

На швидкості 921600 бод апаратний FIFO заповнюється всього за 1.389 мс. Якщо затримка обслуговування переривань операційною системою перевищить це значення, виникне помилка переповнення приймача (від англ. @@en|overrun error@@ — помилка переповнення приймача). Це вимагає аналізу передачі даних із FIFO до кільцевого буфера FreeRTOS.

## Моделювання затримок кільцевих буферів FreeRTOS

Після заповнення апаратного FIFO UART до заданого порогу `N_thresh` (або за таймаутом простою лінії) генерується системне переривання. Процедура обробки переривань (від англ. @@en|interrupt service routine@@, @@en|ISR@@) копіює накопичені байти з FIFO в системний кільцевий буфер FreeRTOS `RxBuffer`, розташований в системній пам'яті DRAM [архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). Докладніше про апаратну реалізацію та механізм обробки переривань у FreeRTOS читайте у статті про [кільцеві буфери UART у FreeRTOS на ESP8266](root:cat-hw-boards/esp8266-uart-rx-ring-buffer).

*Схема ланцюжка буферизації даних від апаратного UART FIFO через кільцевий буфер FreeRTOS та pbuf-структури lwIP до передавача Wi-Fi з позначенням темпів наповнення й розвантаження R_in, R_out та часових затримок.*

Вилучення байтів із кільцевого буфера виконує фонова задача обробки AT-команд із темпом `R_task`. Динаміка зміни кількості байтів у кільцевому буфері `N_ring(t)` підпорядковується рівнянню балансу потоків:

```
dN_ring ÷ dt
= R_in - R_task      [швидкість зміни кількості байтів]
```

Згідно з теорією масового обслуговування та законом Літтла (від англ. @@en|Little's law@@ — закон Літтла), для забезпечення стабільності буфера без безмежного зростання черги вихідний темп обробки повинен перевищувати або дорівнювати вхідному темпу надходження даних:

```
R_in ≤ R_task      [умова відсутності безмежного накопичення]
```

Коефіцієнт завантаження буферної системи `ρ` визначається як відношення темпу входу до темпу обслуговування:

```
ρ
= R_in ÷ R_task      [коефіцієнт завантаження системи]
```

Якщо `ρ > 1`, кільцевий буфер ємністю `C_ring` монотонно заповнюється. Затримка перебування (час очікування) байта в буфері `W_ring` при стаціонарному темпі дорівнює:

```
W_ring
= N_ring ÷ R_in      [затримка перебування в буфері]
```

Максимально допустимий час затримки обробки задачею `W_ring_max` до моменту виникнення переповнення кільцевого буфера обчислюється діленням повного обсягу буфера `C_ring` на темп входу `R_in`:

```
W_ring_max
= C_ring ÷ R_in      [граничний час затримки обробки]
```

**Обчислення критичної затримки обробки в кільцевому буфері**

```
C_ring = 2048 byte, B = 115200 Baud (N_frame = 10 bit)
R_in = 11520 byte/s
W_ring_max = 2048 ÷ 11520 ≈ 0.1778 s [177.8 ms]
```

Якщо перемикання контексту (від англ. @@en|context switch@@ — перемикання контексту) задач FreeRTOS або високе завантаження процесора заблокують AT-задачу більше ніж на 177.8 мс при швидкості 115200 бод, кільцевий буфер обсягом 2048 байтів переповниться. Потік `R_task`, вилучений із кільцевого буфера, стає вхідним навантаженням для наступної ланки — мережевого стека lwIP.

## Розрахунок балансу пропускної здатності lwIP

Під час вилучення байтів фоновою задачею з кільцевого буфера дані потрапляють до третього каскаду буферизації — мережевого стека @@en|lwIP@@ (від англ. @@en|Lightweight IP@@ — полегшений мережевий протокол). Розробники часто припускають, що після вилучення з кільцевого буфера дані миттєво відправляються в радіоефір. Проте у реальній мережі швидкість розвантаження обмежується продуктивністю бездротового тракту, затримками поширення сигналу та механізмами гарантованої доставки протоколу @@en|TCP@@ (від англ. @@en|Transmission Control Protocol@@ — протокол керування передачею). Якщо темп вилучення з кільцевого буфера перевищує реальну пропускну здатність мережі, виникає небезпечний дефіцит системної пам'яті в [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).

Усередині [структури стека lwIP](root:cat-hw-boards/lwip-architecture-esp8266) потік байтів упаковується у динамічні пакетні буфери @@en|pbuf@@ (від англ. @@en|packet buffer@@ — пакетний буфер). З окремих @@en|pbuf@@ формуються @@en|TCP@@-сегменти з максимальним розміром корисного навантаження @@en|MSS@@ (від англ. @@en|Maximum Segment Size@@ — максимальний розмір сегмента), який обчислюється як різниця між розміром максимального блоку передачі @@en|MTU@@ (від англ. @@en|Maximum Transmission Unit@@ — максимальний блок передачі) та довжиною протокольних заголовків @@en|IP@@ і @@en|TCP@@. У стандартних бездротових мережах при `MTU = 1500` байтів значення `MSS` зазвичай становить 1460 байтів.

Темп виходу даних `R_out` із буферів @@en|pbuf@@ у радіоефір визначається не лише фізичною швидкістю @@en|Wi-Fi@@, а й розміром ковзного вікна @@en|TCP Window@@ `W_tcp` та часом кругової затримки @@en|RTT@@ (від англ. @@en|Round-Trip Time@@ — час кругової затримки сигналу). Вихідна пропускна здатність мережевого тракту `R_out` описується формулою:

```
R_out
= min(R_wifi_phy, W_tcp ÷ RTT)      [гранична пропускна здатність TCP]
```

Значення `R_wifi_phy` показує реальну фізичну швидкість бездротового зв'язку, `W_tcp` — обсяг даних у байтах, який приймач дозволяє відправити без отримання підтвердження @@en|ACK@@, а `RTT` — інтервал часу від моменту відправки сегмента до надходження відповідного квитанційного кадру. Якщо мережевий канал має високу затримку `RTT`, максимізація швидкості @@en|UART@@ не прискорить передачу, оскільки `R_out` обмежиться величиною `W_tcp ÷ RTT`.

Коли вхідний темп з @@en|UART@@ `R_in` перевищує вихідний мережевий темп `R_out`, надлишкові байти накопичуються у черзі сегментів @@en|lwIP@@. Динаміка витрати оперативної пам'яті @@en|DRAM@@ (від англ. @@en|Dynamic Random-Access Memory@@ — динамічна пам'ять із довільним доступом) на збереження структур @@en|pbuf@@ `M_lwip(t)` описується рівнянням накопичення:

```
M_lwip(t)
= ∫₀ᵗ (R_in(τ) - R_out(τ)) · (1 + S_head ÷ MSS) dτ      [накопичення пам'яті pbuf]
```

Символ `S_head` позначає сумарний обсяг накладних витрат службових заголовков @@en|pbuf@@, @@en|TCP@@ та @@en|IP@@ (близько 54 байтів на кожен сегмент). Оскільки доступний обсяг @@en|heap@@-пам'яті в ESP8266 обмежений (зазвичай близько 32 кілобайтів), виснаження пам'яті призводить до відмови виділення нових @@en|pbuf@@ і втрати даних.

Сумарна часова затримка скрізного ланцюжка `T_total` від моменту подачі першого біта на ніжку @@en|RX@@ @@en|UART@@ до отримання підтвердження по @@en|Wi-Fi@@ складається із затримок усіх чотирьох каскадів:

```
T_total
= T_frame + t_isr + W_ring + T_lwip + T_wifi      [скрізна затримка ланцюжка]
```

де `T_frame = N_frame ÷ B` — час фізичного прийому кадру @@en|UART@@, `t_isr` — лаг реакції переривання @@en|ISR@@, `W_ring = N_ring ÷ R_in` — час очікування в кільцевому буфері @@en|FreeRTOS@@, `T_lwip` — час пакетизації та очікування у черзі @@en|lwIP@@, а `T_wifi = RTT ÷ 2` — затримка поширення в мережі.

**Обчислення затримки та межі пам'яті lwIP при мережевій затримці**

```
B = 921600 Baud (N_frame = 10 bit, R_in = 92160 byte/s)
W_tcp = 5840 byte, RTT = 0.080 s [80 ms]
R_out = 5840 ÷ 0.080 = 73000 byte/s
ΔR = R_in - R_out = 92160 - 73000 = 19160 byte/s
Available_DRAM = 32768 byte [32 KB]
T_overflow = 32768 ÷ 19160 ≈ 1.710 s [1.71 s]
```

При затримці `RTT = 80` мс та вікні 5840 байтів вихідна швидкість @@en|TCP@@ складає лише 73000 байтів/с. На швидкості @@en|UART@@ 921600 бод різниця темпів у 19160 байтів/с повністю вичерпає 32 кілобайти доступної оперативної пам'яті ESP8266 за 1.71 секунди. Це доводить необхідність оптимізації таймаутів пакетизації та застосування керування потоком.

## Часові таймаути пакетизації прозорого режиму

У режимі наскрізної передачі даних (від англ. @@en|passthrough mode@@ — прозорий режим передачі), що активується конфігурацією `CIPMODE=1`, хост-мікроконтролер передає сирий потік байтів без попереднього оголошення довжини кадру в [протоколі двофазної передачі](root:cat-hw-boards/esp8266-at-cipsend-handshake) `AT+CIPSEND`. У цьому стані перед прошивкою ESP8266 постає математична дилема: коли саме слід закривати поточний буфер і формувати @@en|TCP@@-сегмент для відправки в стек @@en|lwIP@@? Якщо відправляти кожен байт окремим пакетом, мережа перевантажиться службовими заголовками, а якщо чекати повного заповнення пакета, виникнуть неприпустимі затримки у передачі короткометражних команд контролю.

Для збалансування затримок та накладних витрат прошивка ESP8266 AT використовує гібридний критерій пакетизації, який спирається на два незалежних тригери: обсяг накопичених байтів `N_accum` та міжсимвольний таймаут простою лінії `T_timeout` (від англ. @@en|inter-character timeout@@ — міжсимвольний таймаут простою). Пакетизація відбудеться негайно при виконанні хоча б однієї з двох умов:

```
Condition_1: N_accum ≥ MSS      [тригер за обсягом накопичених даних]
Condition_2: t_idle ≥ T_timeout [тригер за часовим простоєм лінії]
```

Параметр @@en|MSS@@ визначає граничну ємність @@en|TCP@@-сегмента (1460 байтів). Якщо хост подає безперервний потік даних зі швидкістю `R_in`, час заповнення одного пакета `T_fill` обчислюється як:

```
T_fill
= MSS ÷ R_in      [час накопичення повного сегмента]
= (MSS × N_frame) ÷ B      [підстановка параметрів кадру UART]
```

Якщо ж передача переривається (наприклад, між окремими пакетами протоколу Modbus RTU або JSON-запитами), прошивка відраховує час простою лінії `t_idle` від моменту надходження останнього байта. Щойно `t_idle` сягає значення `T_timeout` (у стандартній прошивці ESP8266 AT цей поріг дорівнює 20 мс), накопичений обсяг `N_accum` примусово упаковується в @@en|pbuf@@ і відправляється в [асинхронний обробник IPD](root:cat-hw-boards/esp8266-at-ipd-parser).

Максимальна затримка пакетизації `T_pack_delay` для неопрацьованої порції даних обмежується значенням налаштованого таймауту `T_timeout`. Проте для запобігання переповненню кільцевого буфера `C_ring` під час паузи обробки мережевим стеком, критичне верхнє значення міжсимвольного таймауту `T_timeout_crit` розраховується з умови збереження залишкової ємності:

```
T_timeout_crit
= (C_ring - N_accum) ÷ R_in      [критичний таймаут пакетизації]
```

Якщо обрати `T_timeout` занадто малим (наприклад, менше 2–3 мс), то при повільній передачі кадри будуть дробитися на множину дрібних @@en|TCP@@-пакетів, що спричинить зростання накладних витрат заголовків @@en|IP@@/@@en|TCP@@ до 400% від обсягу корисного навантаження (від англ. @@en|payload@@ — корисне навантаження). Натомість надто великий таймаут збільшує затримку відгуку в інтерактивних сценаріях.

**Обчислення оптимального таймауту пакетизації для потоку 115200 бод**

```
B = 115200 Baud, N_frame = 10 bit, MSS = 1460 byte, C_ring = 2048 byte
R_in = 115200 ÷ 10 = 11520 byte/s
T_fill = 1460 ÷ 11520 ≈ 0.1267 s [126.7 ms]
If N_accum = 512 byte accumulated:
T_timeout_crit = (2048 - 512) ÷ 11520 = 1536 ÷ 11520 ≈ 0.1333 s [133.3 ms]
Standard T_timeout = 0.020 s [20 ms] < 126.7 ms
```

Оскільки стандартний таймаут 20 мс значно менший за час накопичення повного кадру (126.7 мс на швидкості 115200 бод), повнокадрові @@en|TCP@@-сегменти будуть формуватися лише при безперервному потоці, а поодинокі повідомлення надсилатимуться з гарантованою затримкою не більше 20 мс. Якщо ж вихідний мережевий тракт заблокується, навіть правильні таймаути не врятують буфери від переповнення без апаратного керування потоком.

## Розрахунок порогів RTS/CTS і буферів

Навіть при точних налаштуваннях таймаутів пакетизації та виділенні ємних буферів у стеку @@en|lwIP@@, радіоефір @@en|Wi-Fi@@ піддається спорадичним завадам, колізіям та тимчасовим розривам зв'язку. У такі моменти вихідний темп `R_out` падає до нуля, а вхідний потік @@en|UART@@ `R_in` продовжує безперервно наповнювати кільцевий буфер @@en|FreeRTOS@@. Єдиним способом запобігти втраті байтів є примусове зупинення передачі на стороні хоста за допомогою апаратного керування потоком @@en|RTS/CTS@@ (від англ. @@en|Request to Send / Clear to Send@@ — запит на відправку / готовий до прийому). Проте простого підключення сигнальних ліній недостатньо: якщо виставити поріг зупинки занадто близько до верхньої межі буфера, затримка реакції хоста призведе до неминучого переповнення.

Лінія @@en|RTS@@ (активний низький рівень) керується мікроконтролером ESP8266 і повідомляє хосту про готовність до прийому даних. Коли кількість байтів у кільцевому буфері `N_ring(t)` досягає верхнього порогового рівня `N_rts_high` (від англ. @@en|high watermark@@ — верхня порогова позначка), ESP8266 переводить лінію @@en|RTS@@ у високий стан, вимагаючи припинення передачі.

Однак хост-мікроконтролер не може зупинити потік миттєво. З моменту зміни стану сигнальної лінії @@en|RTS@@ до повної зупинки видачі бітів на лінії @@en|TX@@ проходить час реакції хоста `t_lag` (часовий лаг). Упродовж цього інтервалу хост встигає передати додаткову кількість байтів `N_skid` (від англ. @@en|skid bytes@@ — байти проскоку/інерційного вибігу):

```
N_skid
= R_in · t_lag + N_host_fifo      [обсяг байтів інерційного вибігу]
```

де `R_in` — вхідний темп @@en|UART@@, `t_lag` — часовий лаг обробки переривання та виконання програмного коду на хості, а `N_host_fifo` — обсяг байтів, які вже завантажені в апаратний передавальний буфер @@en|FIFO@@ хоста і не можуть бути відкликані.

Щоб запобігти виникненню переповнення буфера ємністю `C_ring`, максимальний рівень накопичення `N_peak = N_rts_high + N_skid` не повинен перевищувати розраховану об'ємну межу. Звідси виводиться математична формула для верхнього порогу спрацьовування @@en|RTS@@:

```
N_rts_high
≤ C_ring - N_skid      [верхня межа порогу RTS]
= C_ring - (R_in · t_lag + N_host_fifo)      [розгортання лагу хоста]
```

Для відновлення прийому даних лінія @@en|RTS@@ знову переводиться в активний низький стан лише тоді, коли рівень заповнення буфера знижується до нижнього порогу `N_rts_low` (від англ. @@en|low watermark@@ — нижня порогова позначка). Різниця між порогами ΔN_hyst = N_rts_high - N_rts_low створює гістерезис (від грец. @@en|hysteresis@@ — відставання), що запобігає високочастотному брязканню сигналу (від англ. @@en|chattering@@ — швидке перемикання лінії) при коливанні рівня байтів біля межі.

**Обчислення порогового рівня RTS для швидкості 921600 бод**

```
C_ring = 2048 byte, B = 921600 Baud (R_in = 92160 byte/s)
t_lag = 0.003 s [3 ms], N_host_fifo = 16 byte
N_skid = 92160 × 0.003 + 16 = 276.48 + 16 ≈ 293 byte
N_rts_high = 2048 - 293 = 1755 byte
Setting N_rts_low (with ΔN_hyst = 1024 byte):
N_rts_low = 1755 - 1024 = 731 byte
```

При швидкості 921600 бод та затримці реакції хоста всього 3 мс, проскок складає 293 байти. Поріг `N_rts_high` повинен бути встановлений не вище 1755 байтів (85.7% від ємності буфера 2048 байтів). Налаштування апаратного керування потоком у прошивці ESP8266 за допомогою [команд налаштування UART](root:cat-hw-boards/esp-at-command-set-overview) та [конфігурації GPIO](root:cat-hw-boards/esp8266-at-gpio-control) гарантує абсолютну безвтратність обміну даними на будь-яких швидкостях послідовного порту.
