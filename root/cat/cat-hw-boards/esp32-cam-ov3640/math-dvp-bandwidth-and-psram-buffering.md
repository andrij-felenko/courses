## Проблема втрати кадрів у шині DVP

Захоплення відеопотоку високої роздільності часто дає збій: замість стабільних 30 кадрів за секунду мікроконтролер видає викривлені зображення або зазнає переповнення буфера. У [модулі ESP32-CAM](root:cat-hw-boards/esp32-cam) зображення від сенсора передається через паралельну 8-бітну шину @@en|DVP@@ (англ. @@en|DVP@@, від @@en|Digital Video Port@@ — цифровий відеопорт). Вона є повністю синхронною і не має апаратного керування потоком, як-от @@en|RTS@@ (англ. @@en|RTS@@, від @@en|Request to Send@@ — запит на передачу) чи @@en|CTS@@ (англ. @@en|CTS@@, від @@en|Clear to Send@@ — готовність до прийому). Розпочавши кадр, сенсор беззупинно витактовує байти на кожному імпульсі піксельної частоти @@en|PCLK@@ (англ. @@en|PCLK@@, від @@en|Pixel Clock@@ — піксельний такт).

Контролер камери приймає потік через буфер @@en|FIFO@@ (англ. @@en|FIFO@@, від @@en|First In, First Out@@ — першим прийшов, першим пішов) і спрямовує його каналами @@en|DMA@@ (англ. @@en|DMA@@, від @@en|Direct Memory Access@@ — прямий доступ до пам'яті) у зовнішню пам'ять @@en|PSRAM@@ (англ. @@en|PSRAM@@, від @@en|Pseudo Static RAM@@ — псевдостатична оперативна пам'ять). Шина @@en|PSRAM@@ є спільним ресурсом кристала @@en|SoC@@ (англ. @@en|SoC@@, від @@en|System on Chip@@ — система на кристалі), що обслуговує також процесорні ядра та стек @@en|Wi-Fi@@. Як розкрито у [сімействах плат ESP32-CAM](root:cat-hw-boards/esp32-cam-camera-module-family), затримка арбітражу шини змушує контролер @@en|DMA@@ призупинити запис.

Через обмежену ємність буфера @@en|FIFO@@ затримка шини @@en|PSRAM@@ спричиняє його переповнення та скидання байтів шини @@en|DVP@@. У нестиснених кадрах це зміщує пікселі, а у форматі @@en|JPEG@@ (англ. @@en|JPEG@@, від @@en|Joint Photographic Experts Group@@ — об'єднана група експертів у галузі фотографії) втрата байтів руйнує маркери ентропійного кодування, роблячи кадр непридатним для декодування. Запобігти втратам дозволяє математична модель тактування шини @@en|DVP@@ та розрахунок параметрів буферизації.

## Математична модель тактування шини DVP

Головний контролер, такий як [мікроконтролер ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller), генерує для сенсора зовнішню опорну частоту @@en|XCLK@@ (англ. @@en|XCLK@@, від @@en|External Clock@@ — зовнішня опорна частота), яка зазвичай становить від `10.0` до `24.0` МГц. Всередині сенсора ця частота надходить на схему фазового автопідлаштування частоти @@en|PLL@@ (англ. @@en|PLL@@, від @@en|Phase-Locked Loop@@ — фазове автопідлаштування частоти), множиться та ділиться внутрішніми регістровими дільниками, формуючи підсумкову піксельну частоту @@en|PCLK@@.

Швидкість генерації піксельного такту обчислюється через дільники сенсора. Позначимо опорну частоту через `f_{XCLK}`, коефіцієнт множення @@en|PLL@@ через `m`, дільник входу @@en|PLL@@ через `n`, а системний дільник піксельного такту через `d_{pclk}`.

Значення піксельної частоти `f_{PCLK}` визначається формулою:

```
f_{PCLK}
= f_{XCLK} × m / (n × d_{pclk})      [залежність піксельного такту від дільників сенсора]
```

На кожному такті сигналу @@en|PCLK@@ по 8-бітній шині @@en|DVP@@ передається один байт. Цикл кадру складається з активної передачі `W_{act} × H_{act}` пікселів та службового гасіння. Кількість байтів на піксель `N_{bpp}` становить `2` для форматів @@en|RGB565@@ (англ. @@en|RGB565@@, від @@en|Red Green Blue 565@@ — формат кольору з розрядністю 5-6-5 бітів) та @@en|YUV422@@ (англ. @@en|YUV422@@, від @@en|YUV 4:2:2@@ — формат кольоровості з субдискретизацією 4:2:2), і `1` для монохромного @@en|Grayscale@@ (англ. @@en|Grayscale@@ — відтінки сірого).

Під час передачі рядка сигнал горизонтальної синхронізації @@en|HREF@@ (англ. @@en|HREF@@, від @@en|Horizontal Reference@@ — опорна горизонтальна синхронізація) перебуває у високому стані `W_{act} × N_{bpp}` тактів, а під час гасіння @@en|HBLANK@@ — у низькому протягом `N_{hblank}` тактів @@en|PCLK@@. Загальна кількість тактів `N_{line\_cycles}`, необхідна для передачі одного повного рядка, становить:

```
N_{line\_cycles}
= W_{act} × N_{bpp} + N_{hblank}      [сума активних та гасячих тактів рядка]
```

Після передачі `H_{act}` активних рядків сигнал вертикальної синхронізації @@en|VSYNC@@ (англ. @@en|VSYNC@@, від @@en|Vertical Synchronization@@ — вертикальна синхронізація) виконує паузу вертикального гасіння @@en|VBLANK@@ тривалістю `N_{vblank}` рядків. Повна кількість рядків кадру `H_{total}` дорівнює:

```
H_{total}
= H_{act} + N_{vblank}                [сума активних та гасячих рядків кадру]
```

Загальне число тактів піксельної частоти `N_{frame\_cycles}` для формування одного кадру обчислюється як добуток тактів рядка на кількість рядків:

```
N_{frame\_cycles}
= N_{line\_cycles} × H_{total}         [загальна кількість тактів PCLK на один кадр]
= (W_{act} × N_{bpp} + N_{hblank}) × (H_{act} + N_{vblank}) [розгортання формули через геометрію]
```

Тривалість одного кадру `T_{frame}` у секундах обчислюється діленням кількості тактів кадру на піксельну частоту `f_{PCLK}`, а гранична частота кадрів @@en|FPS@@ є оберненою величиною:

```
T_{frame}
= N_{frame\_cycles} / f_{PCLK}        [тривалість кадру в секундах]

FPS
= 1 / T_{frame}                       [визначення частоти кадрів]
= f_{PCLK} / N_{frame\_cycles}        [підстановка тривалості кадру]
```

**Розрахунок граничної частоти кадрів для кадру SVGA у форматі RGB565:**
Для роздільності `800 × 600` пікселів (`W_{act} = 800`, `H_{act} = 600`), формату @@en|RGB565@@ (`N_{bpp} = 2`), гасіння `N_{hblank} = 160` тактів, `N_{vblank} = 25` рядків та частоти `f_{PCLK} = 20.0` МГц (`20000000` Гц) обчислення має вигляд:

```
N_{line\_cycles}
= 800 × 2 + 160
= 1760                                 [тактив на один рядок]

H_{total}
= 600 + 25
= 625                                  [рядків на один кадр]

N_{frame\_cycles}
= 1760 × 625
= 1100000                              [тактів PCLK на один кадр]

FPS
= 20000000 / 1100000
= 18.18                                [кадрів за секунду]
```

Отже, при частоті `20.0` МГц фізичне обмеження шини @@en|DVP@@ з урахуванням гасіння обмежує швидкість до `18.18` кадрів за секунду.

## Обчислення потоку даних і коефіцієнтів стиснення

Пропускна здатність шини @@en|DVP@@ має дві характеристики: пікову швидкість під час передачі активного рядка та середню швидкість за період кадру. Паралельна 8-бітна шина передає один байт на кожному активному такті сигналу @@en|PCLK@@, тому пікова швидкість потоку `B_{peak}` залежить лише від піксельної частоти:

```
B_{peak}
= f_{PCLK} × 1                         [пікова швидкість передачі по 8-бітній шині]
```

При піксельній частоті `f_{PCLK} = 20.0` МГц піковий потік даних під час активного стану сигналу @@en|HREF@@ досягає `20.0` МБ/с.

Середня швидкість `B_{avg}` враховує паузи гасіння через коефіцієнт корисного використання часу шини `η_{active}` — частку активних тактів у кадровому циклі:

```
η_{active}
= (W_{act} × N_{bpp} × H_{act}) / N_{frame\_cycles} [коефіцієнт використання часу шини]

B_{avg}
= B_{peak} × η_{active}               [середня швидкість через пікову]
= W_{act} × H_{act} × N_{bpp} × FPS   [розрахунок через частоту кадрів]
```

Для масивів високої роздільності, таких як @@en|UXGA@@ (англ. @@en|UXGA@@, від @@en|Ultra Extended Graphics Array@@ — ультрарозширений графічний масив) з розміром кадру `1600 × 1200` пікселів, нестиснений потік у форматі @@en|YUV422@@ створює надмірне навантаження. Обсяг одного сирого кадру `S_{raw}` становить:

```
S_{raw}
= 1600 × 1200 × 2
= 3840000                              [байтів на кадр (3.84 МБ)]
```

Передача таких обсягів перевищує можливості мікроконтролера, тому сенсор виконує апаратне стиснення у формат @@en|JPEG@@. Коефіцієнт стиснення `K_{cmp}` показує, у скільки разів обсяг стисненого кадру `S_{jpeg}` менший за `S_{raw}`:

```
K_{cmp}
= S_{raw} / S_{jpeg}                  [визначення коефіцієнта стиснення]
```

Залежно від налаштувань якості, `K_{cmp}` для @@en|UXGA@@ варіюється від `6.0` (розмір кадру ~`640` КБ) до `16.0` (розмір кадру ~`240` КБ).

**Розрахунок середнього потоку для UXGA JPEG при 15 FPS:**
Приймемо `S_{raw} = 3.84` МБ, середній коефіцієнт стиснення `K_{cmp} = 12.0` та частоту кадрів `FPS = 15.0`.

```
S_{jpeg}
= 3.84 / 12.0
= 0.32                                 [МБ на один кадр (320 КБ)]

B_{avg\_jpeg}
= S_{jpeg} × 15.0
= 0.32 × 15.0
= 4.80                                 [МБ/с середнього потоку даних]
```

Обчислення показують, що стиснення зменшує середній потік до `4.80` МБ/с. Однак передача стисненого кадру @@en|JPEG@@ відбувається короткими сплесками: під час виведення кожного блоку сигнал @@en|HREF@@ активується, і байти виходять із піковою швидкістю `B_{peak} = f_{PCLK}`. Тому периферійний контролер повинен приймати вхідні байти на повній піковій швидкості `20.0` МБ/с під час кожного сплеску @@en|HREF@@.

## Розрахунок кадрових буферів у PSRAM

Для відтворення та передачі відеопотоку без розривів кадрів у системі виділяють подвійну кадрову буферизацію `fb_count = 2`. Поки контролер @@en|DMA@@ здійснює запис поточного кадру N у перший буфер пам'яті @@en|PSRAM@@, процесор або мережевий модуль передає попередньо захоплений кадр N-1 із другого буфера.

Необхідний загальний обсяг пам'яті @@en|PSRAM@@ `V_{psram}` обчислюється через розмір одного кадрового буфера `V_{fb}`:

```
V_{psram}
= 2 × V_{fb}                          [обсяг пам'яті для подвійної кадрової буферизації]
```

Для нестиснених форматів розмір буфера дорівнює активному обсягу кадру `V_{fb} = W_{act} × H_{act} × N_{bpp}`. Для формату @@en|JPEG@@ розмір буфера `V_{fb}` обирають з урахуванням найгіршого випадку ентропії зображення при мінімальному коефіцієнті стиснення `K_{cmp\_min}` з додаванням 15% технологічного запасу `V_{margin}` на вирівнювання заголовочних блоків:

```
V_{fb}
= (S_{raw} / K_{cmp\_min}) × 1.15     [розмір JPEG-буфера з технологічним запасом]
```

Як вказано в огляді, який описує [родина плат ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview), плати з конфігурацією пам'яті, як-от [Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare), мають від `2` до `8` МБ зовнішньої пам'яті @@en|PSRAM@@. Подвійна буферизація нестисненого кадру @@en|UXGA@@ @@en|RGB565@@ вимагає `V_{psram} = 2 × 3.84 = 7.68` МБ, що займає майже весь обсяг 8-мегабайтної чип-пам'яті. Натомість для формату @@en|JPEG@@ при `V_{fb} = 512` КБ потрібна пам'ять становить лише `V_{psram} = 2 × 512 \text{ КБ} = 1.024` МБ, що дозволяє вільно працювати навіть на модулях із `2` МБ @@en|PSRAM@@.

Математична умова запобігання переповненню внутрішнього буфера @@en|FIFO@@ контролера камери визначається балансом між вхідним потоком шини @@en|DVP@@ та вихідною швидкістю запису @@en|DMA@@ у пам'ять. Під час сплеску @@en|HREF@@ вхідна швидкість дорівнює піковій `B_{in} = f_{PCLK}`. Якщо шина @@en|PSRAM@@ заблокована іншою периферією на час затримки `t_{stall}`, вихідна швидкість запису падає до нуля (`B_{out} = 0`).

Обсяг накопичених у буфері даних `ΔV_{fifo}` за час затримки `t_{stall}` становить:

```
ΔV_{fifo}
= f_{PCLK} × t_{stall}                [обсяг даних, накопичений у FIFO під час затримки]
```

Для запобігання втраті байтів накопичений обсяг `ΔV_{fifo}` не повинен перевищувати фізичну ємність внутрішнього буфера `V_{fifo}`:

```
ΔV_{fifo} ≤ V_{fifo}                  [умова відсутності переповнення буфера]
```

Звідси виводиться гранично допустимий час затримки арбітражу шини пам'яті `t_{stall\_max}`:

```
t_{stall\_max}
= V_{fifo} / f_{PCLK}                 [граничний час затримки арбітражу шини пам'яті]
```

**Обчислення критичної затримки шини PSRAM:**
Приймемо ємність внутрішнього апаратного буфера @@en|FIFO@@ контролера камери `V_{fifo} = 512` байтів, а піксельну частоту шини `f_{PCLK} = 20.0` МГц (`20000000` байтів за секунду).

```
t_{stall\_max}
= 512 / 20000000
= 0.0000256                           [секунд]
= 25.6                                [мікросекунд]
```

Розрахунок доводить: якщо системна шина пам'яті @@en|PSRAM@@ заблокована обміном @@en|Wi-Fi@@ або кешуванням процесора на час понад `25.6` мікросекунд, апаратний буфер @@en|FIFO@@ переповнюється, і кадр зазнає незворотних спотворень.

Додатково має виконуватися умова середнього запасу пропускної здатності шини. Середня реальна швидкість запису у пам'ять `B_{psram\_avg}` повинна перевищувати середній потік даних камери `B_{avg}` з коефіцієнтом запасу `K_{safe} ≥ 1.5`:

```
B_{psram\_avg} ≥ K_{safe} × B_{avg}   [запас пропускної здатності шини пам'яті]
```

На 4-бітній шині @@en|QSPI@@ (англ. @@en|QSPI@@, від @@en|Quad Serial Peripheral Interface@@ — чотирирозрядний послідовний периферійний інтерфейс) @@en|PSRAM@@ при частоті `80` МГц реальна середня швидкість запису обмежена значенням `20.0` МБ/с, що при наявності фонового трафіку @@en|Wi-Fi@@ падає до `10.0` МБ/с. Це пояснює, чому нестиснені відеопотоки високої роздільності на стандартній шині @@en|QSPI@@ втрачають кадрові буфери. Перехід на 8-бітну шину @@en|OPI@@ (англ. @@en|OPI@@, від @@en|Octal Serial Peripheral Interface@@ — восьмирозрядний послідовний периферійний інтерфейс) у сучасних модулях збільшує швидкість запису до `40.0`–`80.0` МБ/с, повністю усуваючи затримки арбітражу та забезпечуючи стабільне захоплення зображення.
