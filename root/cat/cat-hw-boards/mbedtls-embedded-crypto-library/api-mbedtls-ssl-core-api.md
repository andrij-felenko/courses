## Проблеми захисту даних на мікроконтролерах

Передача даних відкритим текстом через незахищені мережеві з'єднання створює критичні ризики для вбудованих систем. Будь-який проміжний вузол у мережі може перехопити сенсорні показники, аутентифікаційні токени або командні кадри, які надсилає чи отримує @@en|мікроконтролер@@ (грецьк. *micro* — малий, *controllere* — перевіряти, керувати). Наївна спроба вирішити цю проблему шляхом додавання шифрування безпосередньо в код обробки сокетів швидко призводить до фатальних збоїв пристрою. Розробники зіштовхуються з тим, що стандартна прошивка починає спонтанно перезавантажуватися через переповнення @@en|купи@@ (англ. *heap* — купа, довільна оперативна пам'ять) або зависати в нескінченних операціях очікування мережевих пакетів, викликаючи спрацювання апаратного сторожового таймера.

Головна причина таких деградацій полягає у високій складності криптографічних протоколів захисту транспортного рівня. Процедура криптографічного @@en|рукостискання@@ (англ. *handshake* від *hand* — рука, *shake* — тиснути) вимагає обчислення асиметричних ключів, перевірки цифрових підписів, розгортання симетричних ключів сесії та динамічного виділення транзитних буферів для обробки мережевих кадрів. На мікроконтролерах із суворо обмеженим обсягом @@en|RAM@@, таких як чипи з [архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), спроба об'єднати алгоритми шифрування, зберігання ключів та мережеве введення-виведення в єдиний монолітний модуль створює жорстку зв'язаність компонентів. Будь-яка зміна мережевого транспорту або параметрів шифрування вимагає повної перебудови всього стека, а відсутність чіткої межі між статичними налаштуваннями та динамічним станом призводить до дублювання структур у пам'яті.

Для подолання цих обмежень у системній бібліотеці @@en|mbedTLS@@ реалізовано чітке архітектурне розділення відповідальностей. Замість монолітного блоку захищена мережева взаємодія розбивається на три незалежні рівні:
1. Зберігання статичних параметрів безпеки та політик шифрування.
2. Обслуговування поточного динамічного стану конкретного з'єднання.
3. Абстрагування низькорівневого мережевого транспорту від криптографічних обчислень.

Такий підхід дозволяє створювати єдиний екземпляр конфігурації для багатьох з'єднань, ізолювати змінний стан сесії та підключати криптографічне ядро до довільних фізичних каналів зв'язку — від [мережевих сокетів TCP](root:cat-hw-boards/esp01-tcp-udp-sockets) до послідовних інтерфейсів @@en|UART@@.

## Розділення конфігурації та стану з'єднання

Архітектура ядра @@en|mbedTLS@@ розділяє статичний опис параметрів шифрування та динамічний перебіг мережевої сесії між двома ключовими структурами C API: `mbedtls_ssl_config` та `mbedtls_ssl_context`. Це розділення вирішує проблему раціонального використання пам'яті, оскільки статична @@en|конфігурація@@ (лат. *configuratio* від *con-* — разом, *figurare* — надавати форми) налаштовується один раз і може безпечно використовуватися кількома паралельними з'єднаннями, тоді як @@en|контекст@@ (лат. *contextus* від *con-* — разом, *texere* — ткати) утримує лише поточні ключі, послідовні номери кадрів та асинхронний стан процедури захищеного з'єднання.

Структура `mbedtls_ssl_config` містить незмінні правила роботи криптографічного стека: обраний режим (клієнт або сервер), версії протоколів @@en|TLS@@ або @@en|DTLS@@, списки дозволених наборів шифрів (ciphersuites), вказівники на джерела ентропії та генератори випадкових чисел, а також налаштування верифікації сертифікатів. Для її ініціалізації використовується функція `mbedtls_ssl_config_init()`, після чого структура заповнюється базовими значеннями через `mbedtls_ssl_config_defaults()`. Обов'язковим кроком є прив'язка генератора псевдовипадкових чисел за допомогою `mbedtls_ssl_conf_rng()`, оскільки без надійного джерела випадкових даних криптографічні операції неможливі. Детальніше про правильну ініціалізацію генератора CTR-DRBG та підключення апаратних джерел ентропії дивіться у статті про [генератори випадкових чисел та джерела ентропії в mbedTLS](root:sf-security/mbedtls-entropy-rng).

Динамічний стан конкретного з'єднання описується структурою `mbedtls_ssl_context`. Вона ініціалізується функцією `mbedtls_ssl_init()`. На цьому етапі пам'ять під внутрішні I/O-буфери ще не виділяється. Пов'язування сесії з параметрами конфігурації здійснюється викликом `mbedtls_ssl_setup()`. Саме під час виконання `mbedtls_ssl_setup()` бібліотека звертається до конфігураційного об'єкта та динамічно виділяє з @@en|купи@@ оперативну пам'ять під вхідні та вихідні буфери записів. Модифікація об'єкта `mbedtls_ssl_config` після того, як його було прив'язано до активного `mbedtls_ssl_context` через `mbedtls_ssl_setup()`, заборонена, оскільки це призведе до неузгодженості внутрішніх розмірів буферів та станів шифрування.

## Абстрагування транспорту через I/O-коллбеки

Криптографічне ядро @@en|mbedTLS@@ навмисно позбавлене прямої залежності від системних викликів операційної системи або конкретної апаратної реалізації мережевого стека. Для передачі та прийому шифрованих кадрів бібліотека використовує шар абстракції @@en|BIO@@ (англ. *Basic I/O* — базове введення-виведення). Зв'язування об'єкта `mbedtls_ssl_context` із реальним транспортним каналом виконується за допомогою функції `mbedtls_ssl_set_bio()`.

Синтаксис функції `mbedtls_ssl_set_bio()` приймає п'ять аргументів:
```c
void mbedtls_ssl_set_bio( mbedtls_ssl_context *ssl,
                          void *p_bio,
                          mbedtls_ssl_send_t *f_send,
                          mbedtls_ssl_recv_t *f_recv,
                          mbedtls_ssl_recv_timeout_t *f_recv_timeout );
```
Вказівник `p_bio` є довільним контекстом користувача (наприклад, дескриптором сокета `int` або вказівником на структуру мережевого з'єднання). Ядро mbedTLS не інтерпретує значення `p_bio`, а лише передає його першим параметром у вказані @@en|коллбеки@@ (англ. *callback* від *call* — викликати, *back* — назад) `f_send` та `f_recv`.

![Схема демонструє зв'язок між mbedtls_ssl_context та мережевим сокетом через I/O-коллбеки f_send і f_recv](img/mbedtls-bio-transport-callbacks.svg)
*Взаємодія криптографічного контексту mbedTLS з мережевим сокетом lwIP через абстрагований шар транспортних коллбеків BIO.*

Коллбеки введення-виведення повинні відповідати суворим сигнатурам і правильно обробляти стани неблокуючого сокета:
- `f_send(void *ctx, const unsigned char *buf, size_t len)` — викликається для відправки байтів у мережу. При успішній відправці повертає кількість реально переданих байтів.
- `f_recv(void *ctx, unsigned char *buf, size_t len)` — викликається для зчитування байтів із мережевого буфера.

При роботі з [мережевим стеком lwIP](root:cat-hw-boards/lwip-architecture-esp8266) сокети можуть перебувати в неблокуючому режимі. Якщо в момент виклику коллбека в сокеті немає вхідних даних або вихідний буфер заповнений, коллбек не повинен блокувати виконання потоку. Замість цього він має повернути спеціальний код помилки mbedTLS: `MBEDTLS_ERR_SSL_WANT_READ` (якщо прийом даних неможливий без очікування) або `MBEDTLS_ERR_SSL_WANT_WRITE` (якщо мережевий сокет не готовий прийняти дані на відправку).

## Рукостискання та асинхронний обмін даними

Після налаштування транспорту BIO захищене з'єднання переходить до фази встановлення криптографічних ключів та перевірки автентичності. Процедура виконується функцією `mbedtls_ssl_handshake()`. У неблокуючому режимі мережевого сокета функція `mbedtls_ssl_handshake()` не виконує операцію за один виклик. Вона реалізує внутрішній автомат станів: при виконанні кожного кроку ядро робить спроби зчитування або відправки мережевих пакетів через зареєстровані BIO-коллбеки.

![Діаграма станів неблокуючого рукостискання та обміну даними з обробкою кодів MBEDTLS_ERR_SSL_WANT_READ і MBEDTLS_ERR_SSL_WANT_WRITE](img/mbedtls-handshake-state-machine.svg)
*Автомат станів асинхронного рукостискання та обміну даними у mbedTLS з обробкою некритичних кодів очікування I/O.*

Якщо під час рукостискання мережевий сокет повертає `EWOULDBLOCK`, виклик `mbedtls_ssl_handshake()` переривається і повертає код `MBEDTLS_ERR_SSL_WANT_READ` або `MBEDTLS_ERR_SSL_WANT_WRITE`. Ці коди є некритичними (некопирсальними) сигнальними прапорцями. Вони інформують програму, що процедура @@en|рукостискання@@ не завершена і її виклик необхідно повторити, як тільки сокет стане доступним для читання чи запису відповідно. Спроба інтерпретувати `MBEDTLS_ERR_SSL_WANT_READ` як фатальну помилку є поширеною помилкою, яка призводить до передчасного розриву з'єднання.

Після успішного завершення рукостискання (повернення коду `0`) передача та прийом захищених прикладних даних здійснюються викликами `mbedtls_ssl_write()` та `mbedtls_ssl_read()`. Обидві функції працюють аналогічно:
- `mbedtls_ssl_write(ssl, buf, len)` — шифрує прикладні дані в кадри TLS та передає їх у BIO. Повертає кількість записаних байтів або `MBEDTLS_ERR_SSL_WANT_WRITE`.
- `mbedtls_ssl_read(ssl, buf, len)` — дешифрує отримані кадри TLS. Повертає кількість дешифрованих байтів прикладних даних, код `MBEDTLS_ERR_SSL_WANT_READ` при відсутності повного кадру або від'ємне значення при виникненні помилки.

Окремої уваги потребує процедура коректного закриття сесії. Коли сервер або клієнт ініціює завершення роботи, у канал передається спеціальний сповіщувальний кадр @@en|close notify@@ (англ. *close notify* — сповіщення про закриття). При отриманні цього кадру функція `mbedtls_ssl_read()` повертає специфічний код `MBEDTLS_ERR_SSL_PEER_CLOSE_NOTIFY`. Це сигналізує про легітимне закриття SSL-сесії протилежною стороною, що дозволяє відрізнити впорядковане відключення від аварійного розриву мережевого сокета. Для ініціалізації закриття зі свого боку пристрій викликає `mbedtls_ssl_close_notify()`.

## Оптимізація буферів та оперативної пам'яті

Використання протоколів захищеного зв'язку на ресурсно-обмежених мікроконтролерах висуває жорсткі вимоги до розміру динамічної пам'яті. Згідно зі специфікацією TLS, максимальний розмір незашифрованого фрагмента запису (record content length) становить 16384 байти (16 КБ). З урахуванням додаткових заголовків протоколу, вектора ініціалізації та коду автентифікації повідомлень (MAC), повний розмір одного кадру може досягати 16704 байтів. Для повнодуплексного обміну mbedTLS за умовчанням виділяє два таке буфери — вхідний та вихідний, що вимагає понад 33 КБ купової пам'яті.

Для мікроконтролерів [сімейства ESP8266](root:cat-hw-boards/esp8266-family-overview), де загальний обсяг вільної @@en|купи@@ після завантаження мережевого стека lwIP нерідко становить лише 20–36 КБ, спроба виділити стандартні буфери під час виклику `mbedtls_ssl_setup()` призводить до повернення помилки `MBEDTLS_ERR_SSL_ALLOC_FAILED`. Пристрій втрачає можливість встановити захищене з'єднання через фатальний збій виділення пам'яті.

Першим ефективним методом розв'язання цієї проблеми є використання розширення @@en|MFLN@@ (англ. *Maximum Fragment Length Negotiation* — узгодження максимальної довжини фрагмента, RFC 6066). Цей механізм дозволяє клієнту під час рукостискання попросити сервер зменшити максимальний розмір кадрів TLS, які надсилатимуться у з'єднанні. В бібліотеці mbedTLS функція `mbedtls_ssl_conf_mfl_code()` задає бажаний розмір фрагмента в об'єкті конфігурації:
```c
int mbedtls_ssl_conf_mfl_code( mbedtls_ssl_config *conf, unsigned char mfl_code );
```
Допустимі константи `mfl_code`:
- `MBEDTLS_SSL_MAX_FRAG_LEN_512` (записи до 512 байт, буфер близько 1 КБ);
- `MBEDTLS_SSL_MAX_FRAG_LEN_1024` (записи до 1024 байт, буфер близько 1.5 КБ);
- `MBEDTLS_SSL_MAX_FRAG_LEN_2048` (записи до 2048 байт, буфер близько 2.5 КБ);
- `MBEDTLS_SSL_MAX_FRAG_LEN_4096` (записи до 4096 байт, буфер близько 4.5 КБ).

Завдяки зниженню розміру фрагмента до 512 або 1024 байт витрати RAM на I/O-буфери зменшуються з 33 КБ до 2–3 КБ, що дозволяє стабільно виконувати TLS-з'єднання навіть на [модулях ESP-01](root:cat-hw-boards/esp-01).

:::tabs
```c|esp-idf
#include "mbedtls/ssl.h"

// Налаштування MFLN та асиметричних буферів mbedTLS для мінімізації RAM
int configure_memory_optimization(mbedtls_ssl_config *conf) {
    int ret;

    // Запит до сервера на обмеження розміру фрагмента до 1024 байт
    ret = mbedtls_ssl_conf_mfl_code(conf, MBEDTLS_SSL_MAX_FRAG_LEN_1024);
    if (ret != 0) {
        return ret; // Сервер або конфігурація не підтримує обраний код MFLN
    }

    return 0;
}
```
```cpp|esp-idf
#include "mbedtls/ssl.h"

class MemoryOptimizer {
public:
    static bool applyMfln(mbedtls_ssl_config *conf, uint8_t mflCode) {
        int ret = mbedtls_ssl_conf_mfl_code(conf, mflCode);
        return (ret == 0);
    }
};
```
:::

Другим механізмом є статичне коригування розмірів буферів у файлі конфігурації збірки `mbedtls_config.h`. Макроси `MBEDTLS_SSL_IN_CONTENT_LEN` та `MBEDTLS_SSL_OUT_CONTENT_LEN` задають жорсткі верхні межі вхідного та вихідного буферів відповідно. У багатьох IoT-сценаріях застосовується асиметрична оптимізація: пристрій надсилає лише короткі запити Telemetry (наприклад, 256 байт), але приймає великі відповіді або FOTA-оновлення. У такому разі вихідний буфер `MBEDTLS_SSL_OUT_CONTENT_LEN` можна зменшити до 512 байт, зберігши вхідний буфер потрібного розміру, що забезпечує додаткову економію оперативної пам'яті без втрати функціональності.
