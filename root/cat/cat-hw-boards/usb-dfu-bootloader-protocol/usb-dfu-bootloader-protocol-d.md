## Проблема оновлення прошивки через USB

Перезапис прошивки мікроконтролера у вбудованій системі безпосередньо в місці її експлуатації стає критичною точкою відмови. Коли хостовий комп'ютер передає новий бінарний образ через класичний послідовний інтерфейс, обмін відбувається у вигляді неперервного байтового потоку. У такій системі відсутні апаратні засоби контролю фаз перезапису Flash-пам'яті та транзакційний захист від раптових розривів з'єднання. Якщо під час передачі даних виникне збій живлення, фізичне від'єднання USB-кабелю або затримка у буфері прийому хоста, мікроконтролер залишиться у невизначеному стані з частково перезаписаною пам'яттю програм. При наступній подачі живлення вектор скидання вказуватиме на пошкоджену таблицю переривань або недописаний блок коду, що робить повторний запуск пристрою неможливим без підключення зовнішнього програматора.

Багато розробників намагаються розв'язати цю проблему формуванням власного програмного протоколу поверх класичного @@en|UART@@ або при [налаштуванні віртуального COM-порту](root:cat-hw-boards/vcp-virtual-com-port-setup) (англ. @@en|Virtual COM Port@@, @@en|VCP@@) на базі класу @@en|CDC@@ (від англ. @@en|Communication Device Class@@ — клас комунікаційних пристроїв). Подібні підходи, які застосовують спеціалізовані [прошивачі для плат ESP](root:cat-hw-boards/flashing-tools-esptool-and-nodemcu-pyflasher), успішно працюють у межах вузькоспеціалізованих екосистем, але вимагають додаткових сигнальних ліній для апаратного скидання та унікального хостового ПЗ. Для мікроконтролерів @@en|STM32@@ відсутність уніфікованого стандарту створює ризик фатальних колізій: наприклад, хост надсилає чергову порцію даних, коли внутрішній контролер Flash-пам'яті ще не завершив повільний процес посторінкового стирання. Оскільки стандартний послідовний порт не має апаратно зафіксованих станів зворотного зв'язку, хост продовжує передачу в переповнений буфер, спричиняючи втрату пакетів і фатальне пошкодження образу прошивки.

Головна причина непіддатливості «сирих» потокових протоколів полягає у відсутності транзакційного узгодження на низькому рівні USB-протоколу. При використанні класичних кастомних завантажувачів передача здійснюється через потокові кінцеві точки (англ. @@en|BULK Endpoints@@), які не інтегровані у внутрішню логіку керування пам'яттю мікроконтролера. Якщо хостове ПЗ не отримає явного підтвердження про завершення фізичного циклу запису сектору Flash, виникає розсинхронізація: хост вважає дані доставленими, а мікроконтролер ще перебуває у стані блокування системної шини.

Для усунення цих ризиків організація @@en|USB-IF@@ (від англ. @@en|USB Implementers Forum@@ — форум упроваджувачів USB) затвердила стандартизовану специфікацію @@en|DFU@@ (від англ. @@en|Device Firmware Upgrade@@ — оновлення мікропрограми пристрою) класу `0xFE` та підкласу `0x01`. Головна архітектурна перевага DFU полягає у повній відмові від концепції «сирого» послідовного порту на користь жорстко детермінованого скінченного автомата станів (англ. @@en|Finite State Machine@@, @@en|FSM@@). Базовий протокол реалізується виключно через нульову управляючу кінцеву точку (англ. @@en|Control Endpoint 0@@, @@en|EP0@@, від англ. @@en|endpoint 0@@ — нульова кінцева точка), що усуває потребу у виділенні додаткових апаратних конекторів і буферів пам'яті. Вбудований автомат станів гарантує чіткий розподіл процедури оновлення на строго послідовні фази: перехід із робочого режиму застосунку в завантажувач, підготовка пам'яті, поблочне приймання даних, верифікація цілісності та фінальне виконання нової прошивки.

Процес ініціалізації оновлення з робочого режиму програмується за допомогою спеціального управляючого запиту `DFU_DETACH`. Коли пристрій працює в режимі виконаної програми (англ. @@en|Run-Time Mode@@), він оголошує підтримку DFU у своєму дескрипторі. Отримавши запит `DFU_DETACH` із вказаним інтервалом таймауту `wDetachTimeOut`, застосунок зупиняє виконання основних циклів, вимикає периферифійні переривання та ініціює програмне скидання USB-з'єднання (наприклад, шляхом короткочасного підтягування лінії Data- до землі). Після цього мікроконтролер перезапускається в режимі bootloader і повторно енумерується на шині як повноцінний DFU-пристрій. Як пояснює [первинне прошивання завантажувача](root:cat-hw-boards/usb-dfu-bootloader-flashing), переведення пристрою у режим DFU гарантує, що завантажувач перехоплює управління USB-шиною ще до запуску користувацького коду. При цьому внутрішня [архітектура системної пам'яті](root:hw-arch/stm32-system-memory-bootloader-architecture) мікроконтролерів STM32 містить заводський завантажувач у ROM-зоні, який виконує обробку DFU-запитів на апаратному рівні. Сигнальні рівні на виводах конфігурації завантаження визначає [залізний інтерфейс USB](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-stm32-usb-dfu-hardware-interface.md), забезпечуючи успішну енумерацію пристрою навіть за умови повного пошкодження робочого сектору Flash-пам'яті.

Специфікація @@en|USB DFU@@ версій 1.0 та 1.1 розроблялася організацією @@en|USB-IF@@ як універсальний протокол оновлення пристроїв без потреби у пропреітарних драйверах. Проте базовий стандарт мав істотне обмеження для мікроконтролерів: він розглядав пам'ять як єдиний суцільний масив і не містив команд для явного адресування Flash-пам'яті, стирання окремих секторів різного розміру або вибору конкретного банку пам'яті. Для подолання цих обмежень компанія @@en|STMicroelectronics@@ розробила розширення @@en|DfuSe@@ (від англ. @@en|DFU STMicroelectronics Extension@@ — розширення протоколу DFU від компанії STMicroelectronics). Це розширення ввело спеціалізовані командні префікси у управляючі пакети, розширений синтаксис текстових дескрипторів та контейнерний формат файлів `.dfu` (який загортає сирий `.bin` у структуру з заголовками адрес та підсумковим значенням @@en|CRC32@@). Завдяки збереженню сумісності на рівні базових USB-запитів, хостові інструменти еволюціонували від перших графічних утиліт DfuSe Demo та DFUTester до універсального консольного рішення [утиліти dfu-util](root:sys-ide/dfu-util-command-line-tool-usage) та кросплатформеного середовища @@en|STM32CubeProgrammer@@.

Використання протоколу DFU та його розширення DfuSe усуває невизначеність під час відновлення пристрою після збоїв. Кожна транзакція запису або стирання контролюється чіткими таймаутами опитування стану, що унеможливлює переповнення внутрішніх буферів мікроконтролера. Точні математичні розрахунки меж секторів реалізують [математичні алгоритми адресації](root:cat-hw-boards/usb-dfu-bootloader-protocol/math-dfuse-address-mapping-and-crc32-calculation.md), забезпечуючи вирівнювання блоків перед початком сесії прошивання. Детальний перелік команд і структури управляючих пакетів визначає [специфікація протоколу DFU](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-usb-dfu-dfuse-protocol-specification.md). Практичне застосування протоколу на стороні персонального комп'ютера демонструє [хостова утиліта Python](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-usb-dfuse-python-host-flasher.md), а створення власного рішення у мікроконтролері розкриває [власний завантажувач DFU](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-stm32-custom-dfu-bootloader-implementation.md).

## Дескриптори DFU та картка пам'яті

Для коректної організації обміну даними хостове ПЗ повинно отримати повну інформацію про характеристики DFU-завантажувача та фізичну топологію пам'яті мікроконтролера. Ця процедура виконується під час підключення пристрою до шини, коли стандартний [процес енумерації пристроїв](root:com-devices/usb-enumeration) запитує ієрархію дескрипторів. Пристрій віддає стандартний дескриптор пристрою (англ. @@en|Device Descriptor@@), де зазначаються ідентифікатори виробника та продукту (@@en|VID@@/@@en|PID@@, наприклад `0x0483`/`0xDF11` для системного bootloader STM32). Далі надсилається конфігураційний дескриптор (англ. @@en|Configuration Descriptor@@), у якому пристрій оголошує спеціалізований інтерфейс DFU.

Дескриптор DFU-інтерфейсу має поле класу `bInterfaceClass` зі значенням `0xFE` (англ. @@en|Application Specific@@ — специфічний для застосунку) та підклас `bInterfaceSubClass` зі значенням `0x01` (англ. @@en|Device Firmware Upgrade@@). Поле протоколу `bInterfaceProtocol` визначає поточний фазовий стан пристрою: значення `0x01` відповідає робочому режиму виконаної програми (англ. @@en|Run-Time Mode@@), тоді як значення `0x02` сигналізує про повний перехід у режим завантажувача (англ. @@en|DFU Mode@@). Важливою особливістю DFU-інтерфейсу є поле `bNumEndpoints = 0`: завантажувач не виділяє жодних додаткових апаратних конекторів чи потокових кінцевих точок, оскільки увесь керований обмін виконується виключно через нульовий управляючий канал @@en|EP0@@.

Безпосередньо за дескриптором DFU-інтерфейсу в єдиному бінарному пакеті конфігурації передається специфічний функціональний дескриптор (англ. @@en|DFU Functional Descriptor@@, від англ. @@en|functional descriptor@@ — функціональний описувач). Цей дескриптор має фіксовану довжину 9 байтів (`bLength = 0x09`) та тип `0x21` (`bDescriptorType`). Його структура визначає базові апаратні можливості завантажувача за допомогою бітового поля прапорів `bmAttributes`:

- `bitCanDNLOAD` (`bit 0`, значення `0x01`) — підтверджує здатність завантажувача приймати та записувати блоки прошивки від хоста;
- `bitCanUPLOAD` (`bit 1`, значення `0x02`) — дозволяє хосту зчитувати вміст пам'яті мікроконтролера для верифікації або створення резервної копії;
- `bitManifestationTolerant` (`bit 2`, значення `0x04`) — визначає, чи здатний пристрій зберегти USB-з'єднання після завершення фази запису та переходу до маніфестації без примусового апаратного скидання;
- `bitWillDetach` (`bit 3`, значення `0x08`) — вказує, що пристрій самостійно ініціює процедуру від'єднання від шини після отримання відповідного запиту від хоста.

Окрім апаратних прапорів, функціональний дескриптор містить важливе двобайтове поле `wTransferSize`. Воно визначає максимальний обсяг даних у байтах (наприклад, `1024` або `2048`), який буфер завантажувача здатний прийняти в межах одного управляючого запиту `DFU_DNLOAD`. Поле `wDetachTimeOut` задає інтервал очікування скидання шини у мілісекундах, а поле `bcdDFUVersion` зберігає версію протоколу у кодованому десятковому форматі (`0x0110` відповідає стандарту DFU 1.1, а `0x011A` — специфікації ST DfuSe).

Мікроконтролери STM32 містять кілька незалежних областей пам'яті: основну Flash-пам'ять програм, системну ROM-пам'ять завантажувача, байти конфігурації (англ. @@en|Option Bytes@@, від англ. @@en|option bytes@@ — байти налаштування варіантів), а також одноразово програмовану область OTP. Для опису цієї гетерогенної структури в межах одного DFU-інтерфейсу використовується механізм альтернативних конфігурацій (англ. @@en|Alternate Setting@@, від англ. @@en|alternate setting@@ — альтернативна конфігурація). Кожна область пам'яті прив'язується до власного індексу `bAlternateSetting` (0, 1, 2, ...), якому відповідає текстовий дескриптор рядка `iInterface`.

Розширення ST DfuSe регламентує чіткий синтаксис текстового рядка дескриптора `iInterface` для автоматичного парсингу карти пам'яті хостовими утилітами. Формат рядка має наступну структуру:

```text
@<Назва пам'яті> /<Початкова адреса>/<Кількість секторів>*<Розмір секторів><Код доступу>,...
```

Для прикладу, у мікроконтролерах родини STM32F4 з нерівномірним розподілом секторів Flash-пам'яті рядок дескриптора альтернативної конфігурації `bAlternateSetting = 0` має вигляд:

```text
@Internal Flash  /0x08000000/04*016Ka,01*064Kb,07*128Kc
```

Розшифровка елементів цього рядка пояснює фізичну карту адресації:
- `@Internal Flash` — текстова назва області для відображення в інтерфейсі хостової утиліти;
- `/0x08000000/` — початкова шестнадцяткова адреса Flash-пам'яті у фізичному адресному просторі ARM Cortex-M;
- `04*016Ka` — 4 сектори розміром по 16 Кілобайтів кожен (позначка `K`), де буква `a` визначає тип доступу та розмірний множник;
- `01*064Kb` — 1 сектор розміром 64 Кілобайти з кодом доступу `b`;
- `07*128Kc` — 7 секторів розміром по 128 Кілобайтів з кодом доступу `c`.

Буквені коди `a`..`g` визначають допустимі операції над секторами та множники одиниць виміру:
- `a` — розмір сектору у Кілобайтах (`1024` байти), дозвіл лише на зчитання;
- `b` — розмір у Кілобайтах, дозвіл на стирання та запис;
- `c` — розмір у Кілобайтах, повний доступ на зчитання, стирання та запис;
- `d` — розмір у байтах, доступ на зчитання;
- `e` — розмір у байтах, доступ на запис та стирання (використовується для Option Bytes);
- `f` — розмір у байтах, повний доступ;
- `g` — виконання коду у System ROM та зчитання.

Наприклад, у мікроконтролерах родини STM32F1 з рівномірною посторінковою організацією Flash-пам'яті рядок дескриптора має вигляд `@Internal Flash  /0x08000000/128*001Ka` (128 сторінок по 1 Кілобайту), тоді як для Option Bytes використовується альтернативний індекс `bAlternateSetting = 1` із рядком `@Option Bytes  /0x1FFF7800/01*016e`. Як розкриває фізична [архітектура пам'яті STM32](root:hw-arch/stm32-flash-memory-architecture-and-protection), Flash-сектори вимагають обов'язкового стирання перед записом, оскільки осередки пам'яті можуть змінювати свій стан лише з логічної '1' у '0'.

![Структура дескрипторів USB DFU з відображенням індексів Alternate Settings у фізичні адреси Flash та System ROM STM32](img/dfu-descriptors-and-alternate-settings.svg)
*Ієрархія дескрипторів DFU декларує параметри обміну та пов'язує індекси Alternate Settings із фізичними адресами Flash, Option Bytes та System ROM.*

Зіставляючи текстові рядки Alternate Settings з базовою адресою, хостове ПЗ розраховує точні фізичні границі кожного сектору. Наприклад, для досягнення сектору 5 у пам'яті STM32F4 хост додає сумарний розмір перших чотирьох секторів по 16 Кілобайтів (`4 × 16384 = 65536` байтів чи `0x10000`) та п'ятого сектору 64 Кілобайти (`65536` байтів чи `0x10000`) до початкового вказівника `0x08000000`, отримуючи абсолютну початкову адресу `0x08020000`.

Перед початком читання чи запису конкретного банку пам'яті хостове ПЗ надсилає стандартний управляючий запит `SET_INTERFACE`, вказуючи потрібний номер `bAlternateSetting`. Перемикання альтернативної конфігурації перенаправляє внутрішній вказівник адресації DFU-завантажувача на відповідний фізичний сегмент пам'яті мікроконтролера. Виконавши розбір дескрипторів, хост застосовує [аналіз низькорівневого трафіку](root:sys-ide/usb-traffic-analysis-wireshark-usbpcap) для верифікації структури пакетів і переконується у відповідності задекларованих секторів фактичній карті мікроконтролера.

## Автомат станів та базові запити

Приймання бінарних даних без безпосереднього підтвердження готовності апаратного накопичувача призводить до пошкодження пам'яті мікроконтролера. Узгодження фаз оновлення прошивки у протоколі @@en|DFU@@ покладено на скінченний автомат станів (англ. @@en|Finite State Machine@@, @@en|FSM@@), який виконується в мікроконтролері та керується виключно через нульову кінцеву точку @@en|EP0@@. Автомат станів гарантує, що хостовий комп'ютер не зможе надіслати наступну порцію даних до того часу, поки внутрішній контролер пам'яті не завершить фізичну операцію запису або стирання.

Життєвий цикл DFU-автомата охоплює одинадцять послідовних станів, які жорстко регламентують допустимі дії хоста та пристрою на кожному етапі оновлення:

- `appIDLE` (стан `0`) — пристрій виконує основну програму користувача (робочий режим). Отримавши запит `DFU_DETACH`, автомат переходить у транзитний стан `appDETACH` (стан `1`), чекає на програмне скидання USB-шини та перезапускається у режим завантажувача. - `dfuIDLE` (стан `2`) — пристрій перебуває у режимі завантажувача та готовий до виконання операцій стирання, запису чи зчитування пам'яті. Це базовий стан для початку будь-якої сесії оновлення. - `dfuDNLOAD-SYNC` (стан `3`) та `dfuDNLUSYNC` (стан `4`) — проміжні стани очікування після відправки управляючого пакета з даними. У цих станах мікроконтролер перевіряє готовність до збереження блоку в пам'ять. - `dfuDNLOAD-IDLE` (стан `5`) — пристрій успішно прийняв блок даних і очікує на наступний запит `DFU_DNLOAD` або завершення процедури завантаження. - `dfuMANIFEST-SYNC` (стан `6`), `dfuMANIFEST` (стан `7`) та `dfuMANIFEST-WAIT-RESET` (стан `8`) — фази маніфестації, під час яких мікроконтролер скидає тимчасові буфери, виконує верифікацію записаного образу, контролює конфігураційні байти та ініціює перезапуск для переходу до виконання нового коду. - `dfuUPLOAD-IDLE` (стан `9`) — стан очікування чергового запиту `DFU_UPLOAD` при зчитуванні прошивки з мікроконтролера на хост. - `dfuERROR` (стан `10`) — фатальний стан збою, у який автомат потрапляє при виникненні помилок стирання, запису, виході за межі адресної карти чи порушенні апаратного захисту пам'яті.

![Граф станів автомата DFU ідемпетентно відображає транзакційні переходи між appIDLE, dfuIDLE, dfuDNLOAD-EXECUTE, dfuMANIFEST та dfuERROR за управляючими запитами хоста](img/dfu-state-machine-transitions.svg)
*Граф станів автомата DFU фіксує переходи між робочим режимом, фазами завантаження та станами помилок.*

Керування автоматом станів здійснюється через стандартні управляючі запити класу (англ. @@en|Class-Specific Control Requests@@), які надсилаються у формі 8-байтового пакета @@en|SETUP@@ на кінцеву точку @@en|EP0@@. Поле `bmRequestType` визначає напрямок передачі: значення `0x21` використовується для команд від хоста до пристрою, а `0xA1` — для запиту статусу й стану від пристрою до хоста. Основний набір специфікації містить такі запити:

- `DFU_DETACH` (`bRequest = 0x00`) — запит на ініціалізацію переходу з робочого застосунку у завантажувач з параметром таймауту `wDetachTimeOut`. - `DFU_DNLOAD` (`bRequest = 0x01`) — передача порції даних прошивки від хоста до мікроконтролера. Номер блоку передається у полі `wValue`. При `wLength > 0` передається блок прошивки, а запит з `wLength = 0` сигналізує про завершення фази завантаження та початок маніфестації. - `DFU_UPLOAD` (`bRequest = 0x02`) — зчитування блоку даних з пам'яті мікроконтролера на хост з метою верифікації чи створення резервної копії. - `DFU_GETSTATUS` (`bRequest = 0x03`) — критично важливий запит, за допомогою якого хост запитує поточний стан автомата, код помилки та обсяг таймауту опитування. - `DFU_CLRSTATUS` (`bRequest = 0x04`) — скидання прапорця помилки, виведення автомата зі стану `dfuERROR` та повернення у стан `dfuIDLE`. - `DFU_GETSTATE` (`bRequest = 0x05`) — експрес-запит для отримання однобайтового коду поточного стану без додаткових полів статусу. - `DFU_ABORT` (`bRequest = 0x06`) — скасування поточної послідовності операцій та примусове повернення автомата в `dfuIDLE`.

Для забезпечення надійного опитування пристрою без ризику передчасного від'єднання за таймаутом хост повинен обов'язково викликати запит `DFU_GETSTATUS` після кожного запиту `DFU_DNLOAD` з ненульовим корисним навантаженням. У відповідь мікроконтролер повертає 6-байтову структуру даних:

```text
[bStatus (1 байт)] [bwPollTimeout (3 байти)] [bState (1 байт)] [iString (1 байт)]
```

Поле `bStatus` містить код результату виконання останньої операції (`0x00` відповідає `OK`). Поле `bwPollTimeout` розшифровується як 24-бітове ціле число без знаку у форматі @@en|Little-Endian@@ і задає мінімальний інтервал у мілісекундах, який хост зобов'язаний зачекати перед відправкою наступного запиту `DFU_GETSTATUS` або пакету даних. Значення `bwPollTimeout` динамічно розраховується завантажувачем: для швидких операцій запису у буфер воно становить `0`–`1` мс, тоді як для повільного стирання Flash-сектору мікроконтролер повертає таймаут у `100`–`500` мс. Ігнорування цього параметра хостовим ПЗ призводить до повторних запитів у момент, коли завантажувач ще не завершив фізичну операцію, що спричиняє обрив транзакції на USB-шині.

Яку саме інформацію повертає 6-байтовий пакет статусу під час опитування, показує покроковий розбір структури відповіді:

```text
байтовий масив статусу
= bStatus (0x00 - OK)                                [стан виконання операції]
+ bwPollTimeout (0x64, 0x00, 0x00 -> 100 мс)          [інтервал паузи хоста]
+ bState (0x05 - dfuDNLOAD-IDLE)                    [поточний стан FSM]
+ iString (0x00 - немає опису помилки)               [індекс дескриптора рядка]
```

Якщо під час прошивання виникає апаратна помилка (наприклад, спроба запису у незастережений або захищений сектор), завантажувач встановлює `bStatus` у відповідне значення (наприклад, `errWRITE` `0x03` або `errPROT` `0x09`) і переводить FSM у стан `dfuERROR`. Перебуваючи у стані `dfuERROR`, завантажувач відхиляє будь-які нові запити `DFU_DNLOAD` або `DFU_UPLOAD`, повертаючи типом `STALL` на рівні нульової кінцевої точки.

![Блок-схема алгоритму діагностики та виведення пристрою зі стану dfuERROR за допомогою DFU_CLRSTATUS і DFU_ABORT показує логіку скидання помилок та відновлення синхронізації](img/dfu-error-recovery-flowchart.svg)
*Блок-схема алгоритму виведення пристрою зі стану dfuERROR ілюструє послідовність дій для відновлення синхронізації хоста з завантажувачем.*

Для відновлення працездатності хостове ПЗ реалізує алгоритм діагностики: надсилає запит `DFU_GETSTATUS`, фіксує код помилки у початковому байті, після чого викликає `DFU_CLRSTATUS`. Цей запит очищає внутрішній регістр помилок мікроконтролера та переводить автомат станів у `dfuIDLE`, дозволяючи повторити спробу завантаження. Якщо ж потрібно перервати поточну процедуру без очищення помилок, хост надсилає `DFU_ABORT`, що негайно скидає незавершену фазу завантаження. Специфічні нюанси програмного інтерфейсу регламентує [специфікація програмного протоколу DFU](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-usb-dfu-dfuse-protocol-specification.md), а параметри підключення сигнальних ліній визначає [залізний інтерфейс USB](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-stm32-usb-dfu-hardware-interface.md). Для перевірки правильності обміну хостове ПЗ використовує [аналіз низькорівневого трафіку](root:sys-ide/usb-traffic-analysis-wireshark-usbpcap), контролюючи інтервали опитування та стан кінцевої точки.

## Командні розширення протоколу ST DfuSe

Базовий стандарт @@en|USB DFU 1.1@@ не передбачає механізмів передачі довільних фізичних адрес або посторінкового стирання Flash-пам'яті, розглядаючи пристрій як послідовну стрічку даних. Компанія @@en|STMicroelectronics@@ вирішила це обмеження у розширенні @@en|DfuSe@@ за допомогою командних префіксів. Командні префікси передаються у першому пакеті завантаження `DFU_DNLOAD` із номером блоку `wBlockNum = 0` (або `wValue = 0x0000`), коли автомат станів перебуває у стані `dfuIDLE`.

Коли завантажувач отримує запит `DFU_DNLOAD` з `wBlockNum = 0`, він парсить перший байт корисного навантаження як код спеціалізованої команди DfuSe, а наступні байти — як її параметри:

1. **Команда встановлення вказівника адреси (Set Address Pointer):**
   - Код команди: `0x21`. - Структура пакета: `0x21` + `4 байти адреси` у форматі @@en|Little-Endian@@ (разом 5 байтів). - Механізм дії: запит встановлює внутрішній 32-бітовий вказівник адреси запису/зчитання у RAM-пам'яті завантажувача на вказану абсолютну адресу (наприклад, `0x08000000` для початкового сектору Flash). Усі наступні запити `DFU_DNLOAD` із номерами блоків `wBlockNum >= 2` записують дані починаючи з цієї адреси, автоматично збільшуючи вказівник на обсяг прийнятого блоку `wTransferSize`.

2. **Команда стирання сторінки або сектору (Page/Sector Erase):**
   - Код команди: `0x41`. - Структура пакета: `0x41` + `4 байти адреси` будь-якого байта в межах цільового сектору у форматі @@en|Little-Endian@@ (разом 5 байтів). - Механізм дії: завантажувач визначає фізичний сектор Flash-пам'яті, якому належить вказана адреса, і запускає апаратну процедуру стирання. Оскільки фізичне стирання сектору у мікроконтролерах STM32 вимагає значного часу, мікроконтролер у наступному запиті `DFU_GETSTATUS` повертає стан `dfuDNLOAD-BUSY` та велике значення `bwPollTimeout` (до `500` мс).

3. **Команда повного стирання пам'яті (Mass Erase):**
   - Код команди: `0x41` без додаткових адресних байтів (або спеціальний запит зняття захисту). - Механізм дії: ініціює одночасне стирання усіх масивів користувацької Flash-пам'яті. Ця команда застосовується перед оновленням усього масиву прошивки або при розблокуванні пристрою.

Принципи обчислення адрес та вирівнювання розмірів секторів детально розкривають [математичні алгоритми адресації DfuSe](root:cat-hw-boards/usb-dfu-bootloader-protocol/math-dfuse-address-mapping-and-crc32-calculation.md).

![Часова діаграма послідовності управляючих пакетів DfuSe при записі блоку пам'яті ілюструє почергове надсилання команд встановлення адреси, стирання та поблочного запису з паузами опитування](img/dfuse-command-execution-sequence.svg)
*Часова діаграма виконання команд DfuSe показує послідовність пакетів DFU_DNLOAD та паузи опитування bwPollTimeout.*

Оновлення прошивки мікроконтролера STM32 за протоколом DfuSe виконується як детермінований алгоритм з декількох послідовних фаз:

```text
фаза 1: встановити вказівник адреси Flash
= DFU_DNLOAD(wBlockNum=0, payload=[0x21, 0x00, 0x00, 0x00, 0x08])  [команда Set Address Pointer]
= DFU_GETSTATUS() -> bwPollTimeout=1ms, state=dfuDNLOAD-IDLE        [опитування завершення команди]

фаза 2: вибіркове стирання сектору
= DFU_DNLOAD(wBlockNum=0, payload=[0x41, 0x00, 0x00, 0x00, 0x08])  [команда Sector Erase]
= DFU_GETSTATUS() -> bwPollTimeout=100ms, state=dfuDNLOAD-BUSY      [фіксація тривалого стирання]
= pause(100ms) -> DFU_GETSTATUS() -> state=dfuDNLOAD-IDLE            [підтвердження готовності]

фаза 3: поблочне завантаження прошивки
= DFU_DNLOAD(wBlockNum=2, payload=[data_chunk_1])                  [запис першого блоку даних]
= DFU_GETSTATUS() -> bwPollTimeout=10ms, state=dfuDNLOAD-IDLE        [опитування завершення запису]
= DFU_DNLOAD(wBlockNum=3, payload=[data_chunk_2])                  [запис другого блоку даних]
= DFU_GETSTATUS() -> bwPollTimeout=10ms, state=dfuDNLOAD-IDLE        [опитування завершення запису]

фаза 4: фіналізація завантаження
= DFU_DNLOAD(wBlockNum=0, payload=[])                               [порожній пакет завершення]
= DFU_GETSTATUS() -> state=dfuMANIFEST                              [перехід до маніфестації]
```

На доступність операцій запису та стирання безпосередньо впливають апаратні захисти пам'яті мікроконтролера. У мікроконтролерах STM32 застосовується механізм захисту від зчитування (англ. @@en|Readout Protection@@, @@en|RDP@@). Якщо у барах конфігурації (Option Bytes) активовано рівень захисту `RDP Level 1`, системний завантажувач блокує доступ до Flash-пам'яті через зневаджувальні інтерфейси та забороняє виконання запитів `DFU_UPLOAD`. 

При спробі виконати команду стирання чи запису DfuSe без попереднього зняття захисту завантажувач STM32 повертає статус `errPROT` (`0x09`) у запиті `DFU_GETSTATUS` і блокує виконання транзакції. Щоб відновити доступ до пристрою, хостове ПЗ повинно виконати процедуру зняття захисту шляхом перезапису Option Bytes у значення `0xAA` (RDP Level 0). Як розкриває фізична [архітектура Flash-пам'яті та RDP](root:hw-arch/stm32-flash-memory-architecture-and-protection), апаратний контролер STM32 при зміні рівня RDP з 1 на 0 автоматично виконує повне масове стирання (англ. @@en|Mass Erase@@) всієї користувацької Flash-пам'яті для запобігання несанкціонованому зчитуванню прошивки.

Практичну реалізацію хостової утиліти для надсилання розглянутих команд DfuSe описує [розробка утиліти на Python](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-usb-dfuse-python-host-flasher.md). Якщо ж виникає потреба підтримати специфічний протокол DfuSe у власному вторинному завантажувачі, застосовується [реалізація власного bootloader](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-stm32-custom-dfu-bootloader-implementation.md). Для виконання операцій прошивання через командний рядок підходить [утиліта dfu-util](root:sys-ide/dfu-util-command-line-tool-usage), яка автоматично формує префікси `0x21` та `0x41` на основі вказаного бінарного файлу прошивки та адреси призначення.

## Апаратний захист RDP та системний bootloader

Вбудовані системи на базі мікроконтролерів @@en|STM32@@ потребують надійного захисту інтелектуальної власності від несанкціонованого зчитування коду прошивки через апаратні зневаджувальні інтерфейси. Для цього компанія @@en|STMicroelectronics@@ інтегрувала в контролер Flash-пам'яті механізм апаратного захисту зчитування (англ. @@en|Readout Protection@@, @@en|RDP@@, від англ. @@en|readout@@ — зчитування та @@en|protection@@ — захист). Стан захисту визначається конфігураційним байтом у спеціальній енергонезалежній області (англ. @@en|Option Bytes@@). Проте активація захисту RDP безпосередньо впливає на функціонування системного фабричного завантажувача (англ. @@en|System ROM Bootloader@@), який виконує обробку запитів протоколу @@en|USB DFU@@. Якщо хостове ПЗ не враховує поточний рівень RDP, спроба оновлення прошивки призводить до фатальних помилок обміну на шині USB або незворотного апаратного блокування пристрою.

Апаратний контролер пам'яті STM32 підтримує три рівні захисту зчитування, кожен з яких накладає чіткі обмеження на доступність команд протоколів @@en|DFU@@ та @@en|DfuSe@@:

- `RDP Level 0` (базове значення `0xAA`) — апаратний захист повністю вимкнено. Зневаджувальні порти @@en|SWD@@/@@en|JTAG@@, а також системний завантажувач мають повний прямий доступ до всього фізичного адресопростору: основного масиву Flash-пам'яті, системної ROM, @@en|SRAM@@ та конфігураційних байтів. Завантажувач без обмежень виконує зчитування (`DFU_UPLOAD`), посторінкове чи секторне стирання (команда DfuSe `0x41`), встановлення вказівника адреси (команда DfuSe `0x21`) та поблочний запис (`DFU_DNLOAD`).

- `RDP Level 1` (будь-яке значення конфігураційного байта, відмінне від `0xAA` та `0xCC`, наприклад `0x55`) — увімкнено апаратний захист від зчитування. Фізичні порти @@en|SWD@@ та @@en|JTAG@@ повністю блокуються контролером шини при спробі доступу до Flash-пам'яті або @@en|SRAM@@. При переведенні мікроконтролера у режим системного завантажувача (через виводи конфігурації або системні байти) USB-пристрій успішно енумерується на шині та віддає свої дескриптори. Проте обробник команд завантажувача вбудовує апаратні фільтри: запит `DFU_UPLOAD` повністю блокується (пристрій повертає відповідь @@en|STALL@@ на контрольний канал або повертає код помилки `errPROT` зі значенням `0x09`). Окрім цього, прямі операції запису `DFU_DNLOAD` та стирання секторів `0x41` у масив користувацької Flash-пам'яті також відхиляються. Це унеможливлює як несанкціоноване дампання прошивки, так і впровадження стороннього шкідливого коду у захищену пам'ять. Єдиною дозволеною операцією запису для хоста лишається модифікація самих конфігураційних байтів Option Bytes через альтернативну конфігурацію `bAlternateSetting = 1`.

- `RDP Level 2` (значення конфігураційного байта `0xCC`) — максимальний рівень захисту (англ. @@en|Chip Protection@@ — апаратне замикання кристала). На цьому рівні інтерфейси @@en|SWD@@/@@en|JTAG@@ деактивуються назавжди на кремнієвому рівні. Запуск системної ROM-пам'яті bootloader стає фізично неможливим: апаратний логічний блок завантаження ігнорує стан виводів конфігурації та завжди спрямовує вектор скидання на виконання коду з внутрішньої Flash-пам'яті. Перехід у `RDP Level 2` є незворотною операцією: знизити рівень захисту до `Level 1` або `Level 0` неможливо навіть за допомогою спеціалізованого обладнання. Якщо пристрій переведено у `RDP Level 2`, оновлення через системний USB DFU завантажувач стає недоступним назавжди.

Для відновлення можливості прошивати пристрій або для відкатних робіт хостове ПЗ повинно перевести мікроконтролер із `RDP Level 1` у `RDP Level 0`. Ця процедура реалізується шляхом відправки команди DfuSe для запису значення `0xAA` у байт захисту Option Bytes. Для захисту інтелектуальної власності апаратний контролер Flash-пам'яті STM32 містить жорстко зашиту логіку: у момент запису значення `0xAA` замість `RDP Level 1` контролер автоматично ініціює повне масове стирання (англ. @@en|Mass Erase@@) усієї користувацької Flash-пам'яті, операційної пам'яті @@en|SRAM@@ та користувацьких налаштувань.

Механізм автостирання гарантує, що жоден байт захищеного коду чи секретних ключів не залишиться у пам'яті після зняття захисту. З точки зору часової діаграми протоколу DFU, операція стирання при зміні RDP виконується як тривалий асинхронний процес:

```text
фаза 1: відправка запиту зняття захисту (RDP Level 1 -> Level 0)
= DFU_DNLOAD(wBlockNum=0, payload=[0x92]) або запис 0xAA в Option Bytes    [команда Read Unprotect]
= DFU_GETSTATUS() -> bwPollTimeout=1000ms, state=dfuDNLOAD-BUSY          [фіксація запуску Mass Erase]

фаза 2: апаратне стирання та автоперезапуск Option Bytes
= pause(1000ms) -> DFU_GETSTATUS() -> bStatus=OK, state=dfuDNLOAD-IDLE     [завершення фізичного стирання]
= DFU_DNLOAD(wBlockNum=0, payload=[]) -> DFU_GETSTATUS()                   [ініціалізація скидання]
= перезавантаження мікроконтролера -> перезавантаження Option Bytes       [зміна RDP на Level 0]
```

Під час виконання апаратного стирання мікроконтролер повертає у запиті `DFU_GETSTATUS` стан `dfuDNLOAD-BUSY` та тривалий інтервал опитування `bwPollTimeout` (від `500` до `2000` мілісекунд). Хостове ПЗ зобов'язане витримати цю паузу перед надсиланням наступних пакетів. Після завершення стирання та перезавантаження Option Bytes пристрій виконує скидання системи (англ. @@en|System Reset@@). Внаслідок скидання пристрій короткочасно втрачає з'єднання з USB-шиною та перезапускається в режимі `dfuIDLE` з незахищеною порожньою пам'яттю, після чого стають доступними усі стандартні команди DfuSe.

Безпечне конфігурування Option Bytes вимагає суворого дотримання правил адресації та формування масок. У багатьох родинах STM32 (наприклад, STM32F0/F1/F3) кожен байт налаштувань у пам'яті супроводжується своїм інверсним комплементом (англ. @@en|Complement Byte@@), де кожен біт заінвертовано. Якщо хостове ПЗ запише значення RDP без коректного інверсного байта, при наступному скиданні апаратний блок перевірки Option Bytes виявить розбіжність і заблокує запуск мікроконтролера у циклічному генераторі помилок скидання.

Повну карту конфігураційних регістрів та фізичні границі секторів описує [архітектура Flash-пам'яті STM32](root:hw-arch/stm32-flash-memory-architecture-and-protection), а детальний алгоритм старту системного ROM-завантажувача за виводами BOOT висвітлює [архітектура системної пам'яті](root:hw-arch/stm32-system-memory-bootloader-architecture). Для безпечного оновлення хостова утиліта повинна спочатку зчитувати конфігурацію через альтернативну конфігурацію дескрипторів, перевіряти статус `errPROT` за допомогою [специфікації протоколу DFU](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-usb-dfu-dfuse-protocol-specification.md) і лише після цього здійснювати покрокове стирання та запис. Практичні приклади керування прапорцями захисту в хостових скриптах наведено в [розробці утиліти на Python](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-usb-dfuse-python-host-flasher.md), а процедуру первинної активації завантажувача детально розкриває [первинне прошивання DFU](root:cat-hw-boards/usb-dfu-bootloader-flashing).

## Діагностика помилок та відновлення синхронізації

Низькорівневе зневадження протоколу @@en|USB DFU@@ базується на аналізі обміну управляючими транзакціями на нульовій кінцевій точці (англ. @@en|Control Endpoint 0@@, @@en|EP0@@). Оскільки стандарт DFU не використовує додаткових потокових конекторів, усі збої синхронізації, порушення часових інтервалів та колізії команд відображаються у структурі управляючих пакетів @@en|SETUP@@. Для виявлення причин збоїв застосовується інструментальний [аналіз низькорівневого трафіку](root:sys-ide/usb-traffic-analysis-wireshark-usbpcap) за допомогою аналізаторів @@en|Wireshark@@ та драйвера @@en|USBPcap@@, які дозволяють захоплювати дампи байтів безпосередньо на USB-контролері хоста.

Аналіз трафіку дозволяє локалізувати найпоширеніші категорії збоїв при взаємодії з системним завантажувачем:

1. **Порушення таймауту опитування (`bwPollTimeout`):**
   - Симптом: хостове ПЗ надсилає новий запит `DFU_DNLOAD` або `DFU_GETSTATUS` до закінчення інтервалу `bwPollTimeout`, повернутого пристроєм у попередньому пакеті статусу. - Низькорівневий механізм: мікроконтролер ще перебуває у стані виконання апаратної операції (наприклад, стирання Flash-сектору у стані `dfuDNLOAD-BUSY`). Отримавши передчасний пакет на конекторі @@en|EP0@@, обробник переривань завантажувача відхиляє транзакцію, повертаючи апаратну відповідь @@en|STALL@@. Скінченний автомат станів (англ. @@en|Finite State Machine@@, @@en|FSM@@) негайно фіксує колізію, встановлює байт статусу `bStatus = errWRITE` (`0x03`) або `errERASE` (`0x04`) і переходить у фатальний стан `dfuERROR` (стан `10`).

2. **Невірно вирівняні адреси та вихід за межі карти пам'яті:**
   - Симптом: команда DfuSe `Set Address Pointer` (`0x21`) або `Sector Erase` (`0x41`) передає адресу, яка не відповідає фізичним границям секторів або знаходиться у незахищеному адресопросторі. - Низькорівневий механізм: при отриманні команди завантажувач порівнює надіслану 32-бітову адресу зі строковим дескриптором конфігурації `iInterface` (Alternate Settings). Якщо адреса попадає у незадіяний діапазон (наприклад, між Flash та системною ROM) або адреса стирання не вирівняна по початку сектору, мікроконтролер відхиляє виконання, встановлює статус `errADDRESS` (`0x08`) або `errTARGET` (`0x01`) і блокує FSM у стані `dfuERROR`.

3. **Невідповідність розміру блоку (`wTransferSize`):**
   - Симптом: хост надсилає корисне навантаження у запиті `DFU_DNLOAD` з довжиною `wLength`, яка перевищує граничне значення `wTransferSize`, задеклароване у функціональному дескрипторі DFU. - Низькорівневий механізм: відбувається переповнення внутрішнього буфера RAM завантажувача. Для запобігання пошкодженню стеків USB-драйвер мікроконтролера скидає конектор у @@en|STALL@@, встановлює `bStatus = errUNKNOWN` (`0x0E`) та фіксує помилку.

Для швидкого декодування причин зупинки обміну хостове ПЗ використовує таблицю стандартизованих кодів помилок `bStatus`, які повертаються у першому байті відповіді на запит `DFU_GETSTATUS`:

```text
код статусу (bStatus) -> розшифровка та першопричина
= 0x00 (OK)           -> Операція виконана успішно, помилки відсутні
= 0x01 (errTARGET)    -> Указана адреса чи параметр не належать даному пристрою
= 0x02 (errFILE)      -> Прийнятий бінарний файл пошкоджений або має невірну структуру
= 0x03 (errWRITE)     -> Апаратний збій запису у комірки Flash-пам'яті
= 0x04 (errERASE)     -> Помилка апаратного стирання сектору чи сторінки
= 0x05 (errCHECK_ERASED)-> Перевірка чистоти сектору після стирання виявила нестереті біти
= 0x06 (errPROG)      -> Порушення послідовності програмування контролера Flash
= 0x07 (errVERIFY)    -> Зчитані після запису дані не збігаються з надісланим блоком
= 0x08 (errADDRESS)   -> Адреса знаходиться поза допустимими межами Alternate Setting
= 0x09 (errPROT)      -> Спроба запису чи зчитування в області з активованим RDP/WRP
= 0x0B (errUNKNOWN)   -> Невідома внутрішня помилка завантажувача
= 0x0C (errSTALLEDPKT)-> Пристрій отримав непідтримуваний або спотворений управляючий пакет
```

Перебуваючи у стані `dfuERROR` (стан `10`), завантажувач STM32 блокує обробку будь-яких нових пакетів `DFU_DNLOAD` та `DFU_UPLOAD`. Усі наступні спроби відправки даних без попереднього скидання прапорців помилки завершуються відхиленням на рівні контрольної кінцевої точки. Для відновлення синхронізації фаз обміну без застосування апаратного скидання мікроконтролера (англ. @@en|Hard Reset@@) хостове ПЗ застосовує алгоритми скидання через спеціалізовані управляючі запити `DFU_CLRSTATUS` та `DFU_ABORT`.

Вибір алгоритму відновлення залежить від характеру виниклої колізії:

1. **Алгоритм виведення з колізії `dfuERROR` через `DFU_CLRSTATUS`:**
   - Коли хост виявляє стан `bState = 10` (`dfuERROR`), він відправляє управляючий запит `DFU_CLRSTATUS` (`bRequest = 0x04`, `bmRequestType = 0x21`). - Отримавши цей запит, мікроконтролер очищає внутрішній регістр помилок, скидає байт `bStatus` у `0x00` (`OK`) і переводить автомат станів FSM із `dfuERROR` у базовий стан `dfuIDLE` (стан `2`). - Хост робить повторний запит `DFU_GETSTATUS` для підтвердження переходу в `dfuIDLE`, після чого може скоригувати параметри (наприклад, вирівняти адресу чи збільшити паузи) і повторити спробу завантаження блоку.

2. **Алгоритм примусового скасування фази через `DFU_ABORT`:**
   - Запит `DFU_ABORT` (`bRequest = 0x06`, `bmRequestType = 0x21`) застосовується у випадках, коли пристрій не перебуває у стані помилки, але хосту потрібно перервати поточну сесію (наприклад, при розсинхронізації номерів блоків `wBlockNum` у станах `dfuDNLOAD-IDLE` чи `dfuUPLOAD-IDLE`). - Запит `DFU_ABORT` негайно скасовує незавершену фазу приймання чи зчитування, скидає внутрішній лічильник блоків завантажувача у початковий стан і повертає FSM у стан `dfuIDLE`. Це дозволяє хосту заново встановити вказівник адреси через команду DfuSe `0x21` без перепідключення пристрою.

Логіку програмної обробки помилок та відновлення фаз узгодження ілюструє алгоритмічна схема розгалуження:

```text
спроба виконання транзакції DFU_DNLOAD / DFU_UPLOAD
|
+--> перевірка статусу через DFU_GETSTATUS()
|    |
|    +--> [bState == dfuERROR (10)]:
|    |    1. зчитування коду bStatus (наприклад, 0x08 errADDRESS)
|    |    2. надсилання запиту DFU_CLRSTATUS (bRequest 0x04)
|    |    3. повторний DFU_GETSTATUS() -> підтвердження bState == dfuIDLE (2)
|    |    4. корекція адреси чи вирівнювання розміру блоку
|    |    5. повторна відправка перерваного блоку
|    |
|    +--> [виявлено розсинхронізацію порядкового номера wBlockNum]:
|         1. надсилання запиту DFU_ABORT (bRequest 0x06)
|         2. повторний DFU_GETSTATUS() -> підтвердження bState == dfuIDLE (2)
|         3. повторне надсилання DfuSe Set Address Pointer (0x21)
|         4. перезапуск циклу передачі з блоку wBlockNum = 2
```

Дотримання розрахованих меж секторів регламентують [математичні алгоритми адресації DfuSe](root:cat-hw-boards/usb-dfu-bootloader-protocol/math-dfuse-address-mapping-and-crc32-calculation.md). Формат усіх запитів діагностики містить [специфікація програмного протоколу DFU](root:cat-hw-boards/usb-dfu-bootloader-protocol/api-usb-dfu-dfuse-protocol-specification.md). Практичну обробку `DFU_CLRSTATUS` та `DFU_ABORT` у коді прошивачів розкриває [розробка утиліти на Python](root:cat-hw-boards/usb-dfu-bootloader-protocol/proj-usb-dfuse-python-host-flasher.md), а для автоматизації скриптів оновлення у командному рядку використовується консольна [утиліта dfu-util](root:sys-ide/dfu-util-command-line-tool-usage), яка самостійно обробляє виходи з колізій `dfuERROR`.
