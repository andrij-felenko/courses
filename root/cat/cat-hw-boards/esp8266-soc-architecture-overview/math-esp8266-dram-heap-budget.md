## Чому ESP8266 перезавантажується під навантаженням

Розробники мікроконтролерних систем на базі системи на кристалі (від англ. @@en|SoC@@ — system on chip) @@en|ESP8266@@ часто стикаються з раптовими апаратними скиданнями пристрою. У моменти, коли пристрій отримує сплеск мережевих пакетів або намагається відкрити кілька паралельних з'єднань, спрацьовує сторожовий таймер (від англ. @@en|WDT@@ — watchdog timer), викликаючи перезавантаження ядра. Початкова інтуїція підказує шукати помилку в користувацькому коді або припускати брак живлення, адже в специфікації @@en|SoC@@ вказано 80 КБ оперативної пам'яті @@en|DRAM@@ (від англ. @@en|Data Random-Access Memory@@ — пам'ять даних з довільним доступом). Здається, що весь цей обсяг належить програмі й доступний для створення глобальних масивів та об'єктів.

Однак реальний розподіл пам'яті істотно відрізняється від теоретичного обсягу. З наявних 80 КБ оперативної пам'яті @@en|DRAM@@ значна частина виділяється ще на етапі компіляції та завантаження прошивки. Секція ініціалізованих змінних @@en|Data@@ (від англ. @@en|data segment@@) та секція неініціалізованих даних @@en|BSS@@ (від англ. @@en|Block Started by Symbol@@) поглинають статичні буфери системного стека, службові структури драйвера @@en|Wi-Fi@@ та глобальний контекст операційної системи. Коли розробник розгортає [мережеві сокети TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets), залишок фізичної пам'яті автоматично передається під управління динамічної купи (від англ. @@en|Heap@@ — купа).

Під час підключення до мережі родина бездротових модулів, яку описує [огляд сімейства Wi-Fi модулів](root:cat-hw-boards/esp-01-module-family-overview), починає асинхронно виділяти оперативну пам'ять під пакети. Якщо динамічна купа @@en|Heap@@ вичерпується або розбивається на дрібні фрагменти, чергова спроба мережевого стека виділити пам'ять під вхідний кадр зазнає невдачі. Внутрішні обробники переривань втрачають можливість зберегти дані, стек викликів зациклюється у очікуванні ресурсу, і пристрій скидається сторожовим таймером @@en|WDT@@. Щоб упередити такі аварійні зупинки, необхідно побудувати кількісну математичну модель статичних та динамічних витрат пам'яті @@en|DRAM@@.

## Математика накладних витрат lwIP та TLS

Мережева взаємодія в системі спирається на легкий стек протоколів (від англ. @@en|lwIP@@ — lightweight IP), який управляє виділенням пакетних буферів (від англ. @@en|pbuf@@ — packet buffer). Кожен відкритий сокет вимагає виділення двох черг пам'яті: буфера прийому `B_rx` та буфера передачі `B_tx`. Окремий пакетний буфер @@en|pbuf@@ складається зі службового заголовка структури `S_pbuf` (16 байт), заголовків протоколів мережевого та транспортного рівнів `S_hdr` (54 байти для @@en|TCP@@/@@en|IP@@ та @@en|Ethernet@@) та корисного навантаження, яке обмежується параметром максимального розміру сегмента (від англ. @@en|MSS@@ — Maximum Segment Size). Як показує [архітектура мережевого стека](root:cat-hw-boards/lwip-architecture-esp8266), для досягнення стабільного зв'язку розмір вікна прийому й передачі налаштовують щонайменше на 2 сегменти.

Обчислимо сукупний бюджет оперативної пам'яті `B_socket` для одного стандартного сокета @@en|TCP@@ при максимальному сегменті `S_mss = 1460` байт.

```
B_socket = B_rx + B_tx
         = (N_rx × (S_pbuf + S_mss + S_hdr)) + (N_tx × (S_pbuf + S_mss + S_hdr))      [сума буферів прийому та передачі]
         = (2 × (16 + 1460 + 54)) + (2 × (16 + 1460 + 54))                            [підстановка стандартних розмірів пакетів]
         = 3060 + 3060                                                                [обчислення обсягу одного сокета]
         = 6120                                                                       [підсумковий розмір пам'яті в байтах]
```

З виведеної формули видно, що один відкритий сокет @@en|TCP@@ поглинає понад 6 КБ оперативної пам'яті @@en|DRAM@@ лише на підтримку транспортного вікна. Якщо ж програма встановлює сесію через захищені протоколи (від англ. @@en|TLS@@ — Transport Layer Security), витрати зростають у кілька разів. Стандартний специфікований розмір фрейму @@en|TLS@@ вимагає буфера в 16 КБ для вхідних і 16 КБ для вихідних даних. Для обмежених ресурсів мікроконтролера використовують [криптографічний стек mbedTLS](root:cat-hw-boards/mbedtls-embedded-crypto-library) із механізмом узгодження максимальної довжини фрагмента (від англ. @@en|MFLN@@ — Maximum Fragment Length Negotiation).

Застосування оптимізації @@en|MFLN@@ дозволяє зменшити розмір буфера фрагмента `S_frag` до 2048 байт. Сукупний розмір криптографічного контексту `S_tls` складається з буферів прийому, передачі та внутрішнього стану ключів шифрування `S_crypto` (близько 4096 байт). Розрахуємо витрати пам'яті під захищене з'єднання з використанням [захищених SSL/TLS з'єднань](root:cat-hw-boards/esp8266-at-ssl-tls):

```
S_tls = S_frag_in + S_frag_out + S_crypto
      = 2048 + 2048 + 4096              [підстановка розмірів при MFLN 2 КБ]
      = 8192                            [сумарний обсяг TLS контексту в байтах]
```

Таким чином, одне захищене з'єднання вимагає `B_socket + S_tls = 6120 + 8192 = 14312` байт (понад 14 КБ). Це фіксовані накладні витрати, які віднімаються від вільної купи @@en|Heap@@ при відкритті сокета. Проте крім прямих витрат на сокети, операційна система вимагає прихованого резерву пам'яті.

## Обчислення критичного порогу вільної пам'яті

Оцінка прямих витрат на буфери не гарантує стабільності системи, оскільки мережевий драйвер @@en|Wi-Fi@@ та закриті компоненти програмної платформи (від англ. @@en|SDK@@ — Software Development Kit) виконують асинхронні алокації під час обробки переривань. Коли радіомодуль приймає кадр з ефіру, процедура обробки переривання (від англ. @@en|ISR@@ — Interrupt Service Routine) повинна миттєво виділити пам'ять під пакет у купі @@en|Heap@@. Якщо вільний залишок купи опускається нижче критичного значення `H_crit`, обробник переривання не може зберегти кадр, що призводить до втрати синхронізації каналу та перезавантаження пристрою.

Критичний поріг вільної пам'яті `H_crit` формується з трьох незамінних системних компонентів: резерву обробника переривань `S_wifi_isr` (4096 байт), внутрішніх структур контрольних блоків стека `S_lwip_sys` (2048 байт) та резерву виконання системних завдань @@en|SDK@@ `S_sdk_res` (2048 байт). Як зазначає [мережевий стек LwIP 2.x](root:cat-hw-boards/lwip-stack-architecture-in-embedded), брак системних керуючих блоків призводить до блокування сесій.

Обчислимо критичний поріг вільної купи `H_crit` за формулою:

```
H_crit = S_wifi_isr + S_lwip_sys + S_sdk_res
       = 4096 + 2048 + 2048              [сума критичних системних резервів]
       = 8192                            [мінімальний безпечний поріг вільної купи в байтах]
```

З обчислення видно, що показник вільної купи `H_free` ніколи не повинен опускатися нижче 8192 байт (8 КБ). Якщо залишок купи досягає цієї позначки, застосунок зобов'язаний блокувати створення нових сокетів та відхиляти вхідні запити. Навіть при передачі даних через [апаратні FIFO-буфери UART](root:cat-hw-boards/esp8266-uart-hardware-fifo), затримки обробки можуть спричинити накопичення пакетів у пам'яті. Проте наявність 8 КБ вільної купи не гарантує успішного виділення пам'яті, якщо купа піддалася фрагментації.

## Алгоритм розрахунку коефіцієнта фрагментації купи

У процесі тривалої роботи пристрою динамічні алокації та звільнення буферів різного розміру розбивають суцільний простір купи на безліч ізольованих ділянок. Утворюється ситуація, коли загальний сумарний обсяг вільної пам'яті `H_free` формально достатній для виділення нового блоку запитуваного розміру `S_req`, але жоден із наявних безперервних блоків не має необхідного розміру.

Для кількісної оцінки деградації структури пам'яті вводиться коефіцієнт фрагментації купи `K_frag`. Він обчислюється на основі співвідношення між розміром найбільшого суцільного вільного блоку `M_max` (від англ. @@en|largest free block@@) та загальним обсягом вільної пам'яті `H_free`.

```
K_frag = 1 - (M_max ÷ H_free)
       = 1 - (14336 ÷ 29696)             [підстановка поточного стану купи у байтах]
       = 1 - 0.4828                      [обчислення частки найбільшого блоку]
       = 0.5172                           [значення коефіцієнта фрагментації]
```

Значення `K_frag` змінюється в межах від `0` (абсолютно суцільна купа, де `M_max = H_free`) до значень, близьких до `1` (критична фрагментація). З формули випливає пряма залежність для розрахунку граничного блоку `M_max`, який система здатна виділити в поточний момент:

```
M_max = H_free × (1 - K_frag)
      = 29696 × (1 - 0.5172)             [перевірка зворотного розрахунку]
      = 14336                            [максимальний доступний суцільний блок у байтах]
```

Наочне уявлення про розподіл статичних секцій, pbuf-буферів сокетів та виділення найбільшого суцільного блоку в умовах фрагментованої купи надає наступна діаграма.

Як бачимо з діаграми, при сумарному вільному залишку `H_free = 29` КБ і коефіцієнті `K_frag = 0.5172`, найбільший суцільний блок становить лише `M_max = 14` КБ. Якщо програма намагається виділити буфер `S_req = 16` КБ під новий криптографічний контекст, виділення зазнає невдачі, що призведе до помилки вичерпання пам'яті та перезавантаження ядра сторожовим таймером @@en|WDT@@.

## Розрахунок межевих буферів та тайм-аутів

Для забезпечення безвідмовної роботи пристрою в умовах граничних мережевих навантажень необхідно об'єднати отримані вирази в цілісну математичну модель керування пам'яттю. Загальний баланс оперативної пам'яті @@en|DRAM@@ визначається рівнянням:

```
S_dram_total = S_static + H_heap_total
             = (S_data + S_bss) + (H_used + H_free)                       [загальне рівняння балансу DRAM]
```

Щоб гарантувати можливість успішної алокації мережевого буфера розміром `S_req` з урахуванням поточного коефіцієнта фрагментації `K_frag`, сумарна вільна купа повинна задовольняти нерівності:

```
H_free_min = H_crit + (S_req ÷ (1 - K_frag))
           = 8192 + (8192 ÷ (1 - 0.5172))   [підстановка порогу H_crit та запиту TLS 8 КБ]
           = 8192 + (8192 ÷ 0.4828)         [врахування втрат через фрагментацію]
           = 8192 + 16968                   [розрахунок потрібного запасу купи]
           = 25160                          [необхідний вільний залишок купи в байтах]
```

Отже, для безпечного відкриття захищеного з'єднання з буфером 8 КБ при рівні фрагментації 51.7%, загальний вільний залишок купи на момент виклику має становити не менше 25.1 КБ.

Крім того, критичним чинником є час затримки при обробці пакетів. Сторожовий таймер @@en|WDT@@ мікроконтролера @@en|ESP8266@@ ініціалізує скидання ядра, якщо виконання коду в одному циклі без віддачі управління операційній системі перевищує поріг `T_wdt_limit = 1.5` секунди. При обробці вхідних даних через [потоковий розбір асинхронних кадрів +IPD](root:cat-hw-boards/esp8266-at-ipd-parser) або виконанні команд через [протокол двофазної передачі даних AT+CIPSEND](root:cat-hw-boards/esp8266-at-cipsend-handshake), затримка очікування сокета `T_socket` повинна розраховуватися за умовою:

```
T_socket < T_wdt_limit - T_proc
         = 1.5 - 0.3                       [віднімання часу обробки кадру T_proc = 0.3 с]
         = 1.2                             [максимально припустимий тайм-аут сокета в секундах]
```

Дотримання розрахованих межевих параметрів буферів та тайм-аутів забезпечує стійкість системи навіть під час виконання таких ємних процедур, як [оновлення прошивки ESP8266 по повітрю (FOTA)](root:cat-hw-boards/esp8266-fota-update), запобігаючи аварійним скиданням та втраті зв'язку.
