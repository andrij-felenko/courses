## Архітектура системних викликів ESP8266 SDK

Розробка автономного програмного забезпечення для [огляду мікроконтролера та архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) вимагає розуміння специфіки його системної архітектури. На відміну від класичних 8-бітних мікроконтролерів, де виконавча програма володіє процесорним часом монопольно, кристал @@en|ESP8266@@ функціонує під керуванням подійного системного каркаса (англ. @@en|Software Development Kit@@, @@en|SDK@@, від *software* — програмний, *development* — розробка, *kit* — набір). Операційна система або низькорівнева фонова задача реалізують концепцію кооперативної багатозадачності в середовищах @@en|Non-OS SDK@@ та @@en|FreeRTOS SDK@@.

Усі процедури взаємодії з апаратною периферією, системою тактування та блоками живлення винесені в групу низькорівневих системних функцій з префіксом `system_*`. Системний стек постійно виконує фонові процедури обслуговування мережевого стека @@en|Wi-Fi@@, проходження тайм-аутів та обробки переривань. У середовищі @@en|Non-OS SDK@@ обробка користувацьких подій будується на асинхронній черзі за допомогою системних викликів `system_os_task` та `system_os_post`, де завдання виконуються послідовно без витіснення (англ. @@en|non-preemptive scheduling@@, від *non* — не, *preemptive* — витісняючий та *scheduling* — планування). Натомість у @@en|FreeRTOS SDK@@ системний диспетчер спирається на витісняльний планувальник задач (англ. @@en|preemptive RTOS scheduler@@, від *preemptive* — витісняючий та *scheduler* — планувальник), який автоматично перемикає контекст потоків за пріоритетами й передає процесорне ядро фоновим Wi-Fi задачам при квантуванні часу. Якщо в обох середовищах користувацький код захоплює процесорне ядро у нескінченному блокуючому циклі й не повертає керування в системну чергу подій або не поступається квантом часу фоновим задачам, внутрішній апаратний сторожовий таймер (англ. @@en|Watchdog Timer@@, @@en|WDT@@, від *watchdog* — вартовий пес та *timer* — таймер) примусово скидає мікроконтролер. Правильна організація архітектури прошивки спирається на регулярне використання викликів аналізу стану системи та періодичні виклики функцій скидання сторожового таймера, як це передбачає загальна [архітектура завантажувача та режими старту ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture).

Зокрема, системна функція `system_os_post()` відповідає за відправку повідомлення в чергу визначеної задачі за її пріоритетом (від `0` до `2`), де вищий номер визначає першочерговість виконання обробника. Якщо системний диспетчер перевантажений або черга сигналів заповнена, виклик повертає відмову `false`, що вимагає перевірки статусу в коді прошивки для запобігання втраті подій при обробці [мережевих сокетів TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets). Оскільки обробники подій у середовищі @@en|Non-OS SDK@@ не можуть переривати один одного, функція `system_os_post()` виступає головним інструментом винесення тривалих обчислень з переривань у фонові черги відповідного рівня пріоритету.

## Динамічна частота та сторожовий таймер WDT

Тактова частота процесорного ядра @@en|Tensilica Xtensa L106@@ за замовчуванням становить `80` МГц, проте системний API дозволяє програмно подвоювати обчислювальну потужність до `160` МГц. Перемикання частоти здійснюється системною функцією `system_update_cpu_freq(uint8 freq)`, яка приймає значення `80` або `160`. Збільшення частоти дозволяє прискорити виконання математичних розрахунків чи обробку криптографічних підписів, проте пропорційно підвищує струм споживання процесорного ядра.

Динамічна зміна частоти ядра також впливає на периферійні модулі чипа, оскільки тактування шини @@en|APB@@ (англ. *Advanced Peripheral Bus* — розширена шина периферії) прив'язане до тактової частоти процесора. Під час виклику `system_update_cpu_freq()` системна бібліотека @@en|SDK@@ автоматично перераховує дільники регістрів контролера @@en|UART@@ (англ. *Universal Asynchronous Receiver-Transmitter* — універсальний асинхронний приймач-передавач), завдяки чому швидкість послідовного обміну даними не збивається і залишається стабільною на обох частотах. Проте низькорівневі апаратні таймери `hw_timer`, які спираються на пряме підрахування тактів шини або системного регістру `CCOUNT`, після подвоєння частоти до `160` МГц починають відлічувати інтервали вдвічі швидше. Для збереження точності часових затримок прошивка мусить програмно корегувати коефіцієнти дільників апаратних таймерів або використовувати високорівневі програмні таймери SDK, які автоматично адаптують свої інтервали під поточну частоту ядра.

:::tabs
```c|esp-idf
// Динамічне перемикання тактової частоти ядра на 160 МГц
if (system_get_cpu_freq() != 160) {
    system_update_cpu_freq(160);
}
```

```cpp
// Перемикання частоти на 80 МГц для економії енергії
if (system_get_cpu_freq() != 80) {
    system_update_cpu_freq(80);
}
```
:::

Для захисту від зациклення прошивки в апаратурі чипа інтегровано двостадійний таймер @@en|WDT@@. Перша стадія реалізована програмним таймером @@en|Software WDT@@ (з тайм-аутом близько `1.5` секунди), а друга — жорстким апаратним таймером @@en|Hardware WDT@@ (з тайм-аутом близько `3.2` секунди). Під час виконання тривалих обчислювальних операцій прошивка мусить періодично скидати таймер викликом `system_soft_wdt_feed()`. Тимчасове вимкнення програмного сторожового таймера виконується функцією `system_wdt_disable()`, а його повторне ввімкнення — викликом `system_wdt_enable()`. Проте пряме вимкнення викликом `system_wdt_disable()` деактивує лише програмну стадію захисту, через що тривала затримка обробки без виходу в системний цикл спричиняє спрацьовування другої апаратної стадії та беззастережне примусове скидання чипа через [режими завантаження ESP8266](root:cat-hw-boards/esp8266-boot-modes). Для надійного запобігання збоям у ресурсомістких циклах обробки даних виклик `system_soft_wdt_feed()` розміщують безпосередньо всередині ітерацій алгоритму через кожні кілька сотень мілісекунд, що підтримує неперервний скид лічильника тайм-ауту й гарантує стабільне виконання обчислень без блокування системних задач.

![Блок-схема взаємодії системного коду з апаратним сторожовим таймером WDT та перемиканням тактової частоти 80/160 МГц з вказівкою безпечних точок скидання.](img/esp8266-system-wdt-cpu-freq-flow.svg)
*Схема взаємодії системного коду з апаратним сторожовим таймером WDT та перемиканням тактової частоти 80/160 МГц.*

Слід враховувати, що виклик `system_wdt_disable()` деактивує лише програмну стадію захисту; якщо процесор не повертає керування системному циклу понад `3.2` секунди, апаратний блок @@en|Hardware WDT@@ безумовно генерує сигнал скидання чипа.

## Моніторинг купи та системне перезавантаження

Стабільність роботи обчислювальної системи значною мірою залежить від стану динамічної пам'яті (англ. @@en|heap@@, від *heap* — купа). Усі мережеві буфери стека @@en|LwIP@@ та динамічні об'єкти прошивки виділяються з обмеженого обсягу оперативної пам'яті @@en|DRAM@@. Для оперативної самодіагностики SDK надає функцію `system_get_free_heap_size()`, яка повертає поточний обсяг вільної купи в байтах. Проте неперервний обсяг вільної купи не гарантує успішного виділення пам'яті: часті послідовні виклики функцій `os_malloc()` та `os_free()` неоднакового розміру призводять до фрагментації динамічної купи (англ. @@en|Heap fragmentation@@, від *fragmentation* — поділ на фрагменти). Через утворення дрібних незв'язаних блоків спроба виділити суцільний буфер для [мережевих сокетів TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets) завершується помилкою `NULL`, навіть коли сумарний обсяг вільної купи залишається значним. Для запобігання фатальним витокам пам'яті та аварійним перезавантаженням розробники відмовляються від динамічного виділення в робочих циклах на користь стабільного перевикористання статично резервованих буферів або застосовують виклики пул-алокаторів фіксованого розміру.

Глибинна відмінність у поведінці системних функцій виділення пам'яті полягає в будові пулу пам'яті (англ. @@en|memory pool@@, від *memory* — пам'ять, *pool* — пул) конкретного середовища розробки. Традиційний виклик `os_malloc()` у середовищі @@en|Non-OS SDK@@ звертається до спрощеного однорідного алокатора з мінімальним заголовком метаданих блоків (англ. @@en|block metadata@@, від *block* — блок, *metadata* — метадані), що мінімізує накладні витрати на кожен виділений фрагмент, але прискорює фрагментацію при частих операціях. Натомість виклик `pvPortMalloc()` у середовищі @@en|FreeRTOS SDK@@ спирається на алгоритми керування купою `Heap_4`, де суміжні вільні блоки автоматично об'єднуються при звільненні пам'яті викликом `vPortFree()`, вимагаючи дещо більшого розміру системного службового заголовка перед кожною ділянкою.

:::tabs
```c|esp-idf
uint32 free_bytes = system_get_free_heap_size();
if (free_bytes < 4096) {
    // Попередження про критичний рівень вільної пам'яті
    system_restart();
}
```

```cpp
uint32 free_bytes = system_get_free_heap_size();
if (free_bytes < 4096) {
    // Безпечна підготовка та примусове перезавантаження
    system_restart();
}
```
:::

Поточну тактову частоту процесора дозволяє отримати функція `system_get_cpu_freq()`, що повертає числове значення у мегагерцах (`80` або `160`). Якщо програма виявляє невідновлюваний збій, витоки пам'яті або завершує процедуру [оновлення прошивки ESP8266 по повітрю (FOTA)](root:cat-hw-boards/esp8266-fota-update), вона викликає функцію примусового перезавантаження `system_restart()`. Цей виклик скидає цифрове ядро та передає керування первинному завантажувачу. Перш ніж викликати `system_restart()`, розробник мусить деактивувати активні таймери та коректно закрити мережеві сокети, щоб запобігти пошкодженню системних секторів flash-пам'яті.

## Керування режимом сну RTC Deep Sleep

Для автономних пристроїв інтернет-речей (англ. @@en|Internet of Things@@, @@en|IoT@@, від *internet* — інтернет та *things* — речі) критичним параметром є енергоефективність. Найбільш глибоким режимом збереження енергії у ESP8266 є режим глибокого сну (англ. @@en|Deep Sleep@@, від *deep* — глибокий та *sleep* — сон). У цьому стані знеструмлюється процесорне ядро, вимикається радіочастотний тракт і зупиняється основна частина системних периферійних блоків, а струм споживання мікроконтролера знижується до `20` мкА.

Перехід у режим сну виконується системною функцією `system_deep_sleep(uint64 time_in_us)`, яка приймає тривалість сну в мікросекундах. Єдиним активним блоком залишається таймер реального часу @@en|RTC@@ (англ. @@en|Real-Time Clock@@, від *real-time* — реальний час та *clock* — годинник). По закінченню відліку часу блок RTC видає низький імпульс на вивід `GPIO16` (XPD_DCDC). Для забезпечення апаратного пробудження вивід `GPIO16` має бути фізично з'єднаний з лінією скидання `EXT_RSTB` (`RESET`). Оскільки при виході зі сну відбувається апаратне перезавантаження процесора зі втратою оперативної пам'яті, збереження робочих змінних, лічильників та стану системних прапорців здійснюється у спеціальній енергонезалежній 512-байтній пам'яті @@en|RTC USER MEMORY@@. Запис даних у цю пам'ять виконується викликом `system_rtc_mem_write(uint16 des_addr, const void *src_addr, uint16 save_size)`, а зчитування після пробудження — за допомогою `system_rtc_mem_read(uint16 src_addr, void *des_addr, uint16 load_size)`. Адресація в обох функціях вимірюється в 4-байтних блоках, де для користувацьких даних відведено блоки з 64 по 127, а розміри вирівнюються по межі 4 байтів.

*Схема часового циклу та послідовності сигналів входу й апаратного виходу чипа з режиму Deep Sleep через GPIO16 та RESET.*

Конфігурація поведінки бездротового модуля при наступному виході зі сну задається функцією `system_deep_sleep_set_option(uint8 option)` перед викликом `system_deep_sleep`:

1. `Option 0` — при виході зі сну виконується калібрування радіочастотного тракту відповідно до конфігурації `esp_init_data_default.bin`;
2. `Option 1` — примусове повне RF-калібрування при кожному пробудженні (збільшує споживання струму та час виходу в робочий режим);
3. `Option 2` — вихід зі сну без RF-калібрування (мінімальне споживання енергії та найшвидший старт);
4. `Option 4` — пробудження з повністю вимкненим радіомодулем Wi-Fi (режим для автономних вимірювальних датчиків без мережевої передачі).

Правильне програмування варіантів пробудження дозволяє будувати енергоефективні сенсорні вузли, зважаючи на апаратні [режими завантаження мікроконтролера ESP8266](root:cat-hw-boards/esp8266-boot-modes).
