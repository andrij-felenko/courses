## Чому ESP8266 спонтанно перезавантажується та зависає

Уявіть типову розробницьку ситуацію: прошивка для бездротового модуля [ESP-01 (Wi-Fi, ESP8266)](root:cat-hw-boards/esp-01) успішно проходить компіляцію, пристрій запускається й стабільно працює кілька годин, виконуючи мережеві запити. Проте під час тривалого обчислення математичного масиву або інтенсивної обробки зовнішніх сигналів пристрій раптово перезавантажується або повністю перестає реагувати на зовнішні команди. Повторна спроба відтворити помилку показує, що збій виникає хаотично. Спроба писати прикладний код для системи на кристалі (@@en|SoC@@, від англ. *System on Chip* — система на кристалі) так само, як для звичайного однопотокового мікроконтролера, неминуче призводить до нестабільності.

Головна причина цих спонтанних збоїв криється в архітектурних особливостях обчислювального ядра та системної операційної концепції пристрою. [Огляд сімейства ESP8266](root:cat-hw-boards/esp8266-family-overview) показує, що модуль побудований на базі одноядерного 32-бітного процесора @@en|Tensilica L106@@. У середовищі @@en|Non-OS SDK@@ (від англ. *Non-Operating System Software Development Kit* — комплект розробки без операційної системи) відсутнє витісняльне ядро операційної системи реального часу, таке як @@en|FreeRTOS@@. Натомість усі системні й прикладні задачі виконуються у спільному контексті на основі кооперативного планування подій.

Процесорне ядро змушене постійно ділити свій процесорний час між прикладним кодом користувача та фоновими задачами бездротового мережевого стека. Фоновий процес обробляє фізичний @@en|Wi-Fi@@-радіотракт, відстежує бекони базових станцій та керує обміном пакетами через [мережевий стек lwIP](root:cat-hw-boards/lwip-architecture-esp8266). Якщо прикладний код заблокує процесор тривалим циклом `while(1)`, виконання затримуючих викликів `os_delay_us()` понад 10–20 мілісекунд або очікуванням даних через [апаратний FIFO-буфер UART](root:cat-hw-boards/esp8266-uart-hardware-fifo), фонова задача @@en|Wi-Fi@@ втрачає процесорний час. Мережевий стек втрачає синхронізацію з точкою доступу, а внутрішній сторожовий таймер розцінює це як повне зависання системи.

У мікроконтролері інтегровано двостійновий сторожовий таймер @@en|WDT@@ (від англ. *Watchdog Timer* — вартівничий таймер), який запобігає зацикленню прошивки:
- Перший рівень — програмний сторожовий таймер (@@en|Soft WDT@@). Якщо прикладний код утримує процесор без повернення керування системному планувальнику понад ~1.6 секунди, @@en|Soft WDT@@ генерує програмне скидання чипа зі статусом `rst cause: 3`.
- Другий рівень — апаратний сторожовий таймер (@@en|Hard WDT@@). Якщо програмний сторожовий таймер заблоковано або відключено, а процесор не скидає лічильник понад ~3.2 секунди, апаратна схема примусово перезавантажує @@en|SoC@@ зі статусом `rst cause: 1`.

Другою поширеною причиною аварійних зупинок є крихітний обсяг та фрагментація оперативної пам'яті. Фізична оперативна пам'ять даних @@en|DRAM@@ (від англ. *Data RAM* — оперативна пам'ять даних) мікроконтролера становить 80 КБ. Проте значна частина цього обсягу статично розподіляється під внутрішні структури [архітектури завантажувача ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture), системні буфери `pbuf` мережевого стека та змінні прошивки. Доступна розробникові динамічна пам'ять @@en|Heap@@ (купа, від англ. *heap* — купа/нагромадження) зазвичай не перевищує 30–40 КБ. Коли прошивка динамічно виділяє пам'ять під мережеві пакети або текстові буфери й не перевіряє вказівники на `NULL`, виникає апаратна помилка (@@en|Fatal exception@@) через спробу зчитування за некоректною адресою.

Третя причина аварійних збоїв пов'язана з виконанням інструкцій із зовнішньої пам'яті. Основний обсяг виконуваного коду зберігається у зовнішній мікросхемі @@en|SPI Flash@@ (від англ. *Serial Peripheral Interface Flash* — послідовна флеш-пам'ять). Процесор зчитує інструкції з флеш-пам'яті через блок керування пам'яттю @@en|MMU@@ (від англ. *Memory Management Unit* — блок керування пам'яттю) та швидкий кеш @@en|ICACHE@@ обсягом 32 КБ. Під час запису у флеш-пам'ять або при виклику обробників переривань (@@en|ISR@@, від англ. *Interrupt Service Routine* — процедура обробки переривань), котрих розміщено у кешованих секторах Flash замість внутрішньої оперативної пам'яті інструкцій @@en|IRAM@@ (від англ. *Instruction RAM* — оперативна пам'ять інструкцій), кеш флеш-пам'яті блокується, викликаючи негайне фатальне перезавантаження чипа.

Системний програмний інтерфейс @@en|ESP8266 SDK@@ надає розробникові набір інструментів для моніторингу залишку пам'яті, точного розподілу коду між пам'яттю інструкцій та флеш-пам'яттю, обслуговування сторожового таймера й розбору причин перезавантаження пристрою.

## Оцінка динамічної пам'яті та запобігання витокам

У середовищі @@en|Non-OS SDK@@ динамічне виділення оперативної пам'яті є однією з найкритичніших операцій. Під час активної роботи мережевих сокетів пристрій постійно створює та знищує динамічні об'єкти. Зауважте, що відсутність повноцінної системи захисту пам'яті у мікроконтролері робить будь-яке переповнення або неконтрольований витік пам'яті фатальним для всього пристрою.

Фізична пам'ять @@en|DRAM@@ ділиться на декілька функціональних областей: статичні секції коду `.data` та `.bss`, системний стек викликів та вільний динамічний пул — @@en|Heap@@. Для маніпуляції з об'єктами у @@en|Heap@@ системний інтерфейс розробника надає функції `os_malloc(size_t size)` та `os_free(void *ptr)`.

Для оцінки поточного стану динамічної пам'яті SDK надає виклик `system_get_free_heap_size(void)`. Функція повертає обсяг вільної оперативної пам'яті у байтах як 32-бітне беззнакове ціле число (`uint32`).

Розглянемо математичний приклад оцінки динамічної пам'яті під час обробки мережевого пакета. Нехай після ініціалізації системних модулів початковий доступний обсяг кучі становить $H_{\text{init}} = 36864$ байтів (36 КБ). Під час роботи програма виділяє буфер під обробку JSON-структури розміром $S_{\text{json}} = 4096$ байтів та буфер мережевого кадру $S_{\text{net}} = 8192$ байти. Загальний вільний залишок кучі $H_{\text{free}}$ розраховується наступним чином:

```
H_free = H_init - (S_json + S_net)
       = 36864 - (4096 + 8192)          [підстановка вхідних параметрів виділення]
       = 36864 - 12288                  [обчислення суми виділених блоків]
       = 24576 байтів                   [доступний залишок кучі Heap]
```

Отриманий залишок у 24576 байтів показує безпечний рівень пам'яті для подальшої обробки запитів. Проте в реальних умовах розробник стикається з двома основними загрозами:
1. **Витік пам'яті** (англ. *Memory Leak*): виникає, коли програма викликом `os_malloc()` виділяє блок пам'яті всередині обробника події, але через розгалуження умови `if-else` або вихід з функції забуває викликати `os_free()`. При багаторазовому повторенні події значення `system_get_free_heap_size()` послідовно зменшується до нуля.
2. **Фрагментація купи** (англ. *Heap Fragmentation*): виникає при частих виділеннях та звільненнях блоків різного розміру. Пам'ять розбивається на дрібні фрагменти. Наприклад, якщо `system_get_free_heap_size()` повертає загалом 10 КБ вільної пам'яті, спроба виділити один суцільний блок у 4 КБ для виконання інспекції в [криптографічному стеку mbedTLS](root:cat-hw-boards/mbedtls-embedded-crypto-library) закінчиться помилкою `NULL`, оскільки найбільший неперервний фрагмент може становити лише 2 КБ.

Для запобігання збоям розробник повинен суворо перевіряти результат виділення пам'яті та проводити періодичний моніторинг станом кучі.

## Керування розміщенням коду через макрос ICACHE_FLASH_ATTR

Опанувавши контроль динамічної оперативної пам'яті даних, розробник стикається з обмеженнями пам'яті інструкцій. Фізично чип містить швидку внутрішню оперативну пам'ять інструкцій @@en|IRAM@@ обсягом близько 32 КБ, доступну для користувацького коду. Оскільки розмір скомпільованої прошивки зазвичай вимірюється сотнями кілобайтів, розмістити всі функції у внутрішній @@en|IRAM@@ неможливо.

Основним місцем збереження програмного коду є зовнішня мікросхема @@en|SPI Flash@@. Виконання інструкцій із флеш-пам'яті відбувається апаратно через блок @@en|MMU@@ та кеш @@en|ICACHE@@ обсягом 32 КБ. 

За замовчуванням компілятор @@en|GCC@@ у середовищі SDK поміщає весь скомпільований код у секцію `.text`, яка під час завантаження системи копіюється безпосередньо у швидку пам'ять @@en|IRAM@@. Якщо розробник пише стандартний код без спеціальних атрибутів, пам'ять @@en|IRAM@@ швидко переповнюється, викликаючи помилку лінкувальника `iram1_0_seg overflow`.

Для винесення коду функцій у зовнішню флеш-пам'ять застосовується спеціальний системний макрос `ICACHE_FLASH_ATTR`. Цей макрос розміщує інструкції функції у секції `.irom0.text`, яка залишається у @@en|SPI Flash@@ і підвантажується в процесор через кеш @@en|ICACHE@@ лише під час виклику.

```c
// Визначення функції з атрибутом розміщення у SPI Flash
void ICACHE_FLASH_ATTR calculate_sensor_data(void) {
    // Код виконується з Flash-пам'яті через MMU-кеш
}
```

Проте використання макроса `ICACHE_FLASH_ATTR` приховує критичну небезпеку. Під час обробки апаратних переривань або виконання операцій запису й стирання у @@en|SPI Flash@@ системний контролер тимчасово відключає кеш @@en|ICACHE@@ та блокує шину Flash-пам'яті. Якщо в цей момент спрацьовує переривання, а його обробник @@en|ISR@@ позначений атрибутом `ICACHE_FLASH_ATTR`, процесор намагається прочитати інструкції з заблокованої флеш-пам'яті. Це спричиняє фатальне апаратне перезавантаження чипа (@@en|Fatal exception 0@@ — недійсна інструкція, або @@en|Fatal exception 3@@ — помилка завантаження/збереження).

Сформулюємо жорстке правило розміщення коду:
1. **Усі обробники переривань ISR** та функції, які викликаються безпосередньо всередині переривань, **НЕ ПОВИННІ мати атрибута `ICACHE_FLASH_ATTR`**. Вони мусять знаходитися виключно в оперативній пам'яті @@en|IRAM@@.
2. **Звичайні прикладні функції**, фонові задачі, алгоритми обробки даних та ініціалізаційні процедури **ОБОВ'ЯЗКОВО позначаються макросом `ICACHE_FLASH_ATTR`** для економії цінної пам'яті @@en|IRAM@@.

## Обслуговування та відключення сторожового таймера WDT

Навіть при правильному розподілі коду між @@en|IRAM@@ та @@en|SPI Flash@@ тривала обчислювальна задача може викликом заблокувати виконання фонових системних процесів. Як ми вже з'ясували, блокування процесора понад ~1.6 секунди викликає автоматичне скидання системи сторожовим таймером @@en|Soft WDT@@.

У системному API SDK передбачено три основні функції для маніпуляції сторожовим таймером:
- `system_soft_wdt_feed()`: виконує "годування" (скидання лічильника) програмного сторожового таймера @@en|Soft WDT@@, повертаючи часовий відлік на початок.
- `system_wdt_disable()`: тимчасово відключає програмний сторожовий таймер @@en|Soft WDT@@.
- `system_wdt_enable()`: повторно вмикає програмний сторожовий таймер @@en|Soft WDT@@.

Розглянемо математичний розрахунок часових інтервалів виконання обчислювального циклу. Нехай алгоритм обробки масиву містить $N_{\text{iter}} = 20000$ ітерацій. Час виконання однієї ітерації становить $t_{\text{iter}} = 150 \text{ мкс} = 0.00015 \text{ с}$. Сумарний час виконання циклу $T_{\text{total}}$ без скидання сторожового таймера розраховується як:

```
T_total = N_iter × t_iter
        = 20000 × 0.00015 с              [підстановка кількості ітерацій та часу]
        = 3.0 с                          [загальний час виконання обчислювального циклу]
```

Оскільки сумарний час $3.0 \text{ с}$ перевищує граничний ліміт @@en|Soft WDT@@ ($1.6 \text{ с}$), без обслуговування таймера чип перезавантажиться на середині виконання. Якщо здійснювати виклик `system_soft_wdt_feed()` кожні $K_{\text{feed}} = 5000$ ітерацій, то інтервал скидання $T_{\text{feed}}$ становитиме:

```
T_feed = K_feed × t_iter
       = 5000 × 0.00015 с                [підстановка кроку виклику feed]
       = 0.75 с                          [період скидання лічильника Soft WDT]
```

Значення $0.75 \text{ с}$ є безпечним, оскільки воно значно менше за поріг у $1.6 \text{ с}$.

*Часова діаграма роботи сторожових таймерів WDT: своєчасний виклик system_soft_wdt_feed запобігає програмному та апаратному скиданню чипа.*

Зверніть увагу на критичну пастку при використанні `system_wdt_disable()`: відключення програмного таймера @@en|Soft WDT@@ **НЕ ВІДКТЮЧАЄ апаратний таймер @@en|Hard WDT@@**! Якщо розробник викличе `system_wdt_disable()` і заблокує процесор обчисленнями понад ~3.2 секунди, апаратний лічильник @@en|Hard WDT@@ примусово перезавантажить мікроконтролер (`rst cause: 1`).

Тому відключення таймера через `system_wdt_disable()` допускається лише на коротких критичних ділянках коду, з обов'язковим негайним відновленням через `system_wdt_enable()`.

## Системна діагностика та аналіз причин перезавантаження

Навіть у ретельно протестованих пристроях під час експлуатації можуть виникати аварійні ситуації: імпульсні просідання напруги живлення, зовнішні електромагнітні завади чи виключні програмні ситуації. Для швидкого встановлення причин збою системний інтерфейс SDK пропонує функції діагностичної інспекції.

Під час подачі живлення або перезавантаження чипа [архітектура завантажувача ESP8266](root:cat-hw-boards/esp8266-bootloader-architecture) надсилає первинний діагностичний лог у [апаратний FIFO-буфер UART](root:cat-hw-boards/esp8266-uart-hardware-fifo) на нестандартній швидкості 74880 бод. Проте прикладний код може програмно зчитати точну структуру причини останнього скидання безпосередньо під час старту прошивки за допомогою виклику `system_get_rst_info()`.

Функція `system_get_rst_info()` повертає вказівник на системну структуру `struct rst_info`, яка містить детальні дані про стан процесора в момент перезавантаження:

```c
struct rst_info {
    uint32 reason;   // Код причини перезавантаження (enum rst_reason)
    uint32 exccause; // Код винятку CPU (якщо reason == REASON_EXCEPTION_RST)
    uint32 epc1;     // Програмний лічильник PC під час виклику винятку
    uint32 epc2;     // Вторинний лічильник PC
    uint32 epc3;     // Третинний лічильник PC
    uint32 excvaddr; // Віртуальна адреса пам'яті, що викликала збій
    uint32 depc;     // Програмний лічильник відлагодження
};
```

Поле `reason` приймає значення з переліку `enum rst_reason`:
- `DEFAULT_RST` (0): нормальне подання живлення (Power-on reset).
- `WDT_RST` (1): апаратне перезавантаження сторожовим таймером @@en|Hard WDT@@.
- `EXCEPTION_RST` (2): фатальна виключна ситуація процесора (@@en|Fatal exception@@).
- `SOFT_WDT_RST` (3): програмне перезавантаження сторожовим таймером @@en|Soft WDT@@.
- `SOFT_RESTART` (4): програмне перезавантаження викликом `system_restart()`.
- `DEEP_SLEEP_AWAKE` (5): пробудження з режиму глибокого сну (Deep Sleep).
- `EXT_SYS_RST` (6): зовнішнє скидання через фізичний вивід `RST`.

Окрім аналізу причин перезавантаження, для реєстрації конфігурації пристрою використовуються додаткові інспекційні виклики:
- `system_get_sdk_version()`: повертає вказівник на рядок із версією прошивки SDK (наприклад, `"3.0.5(b29dcd3)"`).
- `system_get_cpu_freq()`: повертає поточну тактову частоту процесорного ядра у мегагерцах (80 або 160 МГц). Перемикання частоти здійснюється викликом `system_update_cpu_freq(160)`.
