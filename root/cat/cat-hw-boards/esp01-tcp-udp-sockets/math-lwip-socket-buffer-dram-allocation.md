## Обмеження DRAM та виклики пам'яті

Мережева обробка на мікроконтролерах вимагає жорсткого контролю ресурсів пам'яті, адже вичерпання кучі призводить до раптових збоїв та перезавантажень пристрою. У [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) загальний обсяг оперативної пам'яті даних @@en|DRAM@@ (від англійського @@en|Data Random Access Memory@@ — оперативна пам'ять даних) становить 80 КБ. Проте доступний для розробника залишок динамічної пам'яті @@en|heap@@ (від англійського @@en|heap@@ — купа) є значно меншим, оскільки значна частина @@en|DRAM@@ статично зарезервована під глобальні змінні прошивки, системні структури @@en|SDK@@ та внутрішні буфери драйвера @@en|Wi-Fi@@.

Після ініціалізації бездротового з'єднання та запуску мережевого стека @@en|lwIP@@ (від англійського @@en|lightweight IP@@ — легковаговий мережевий стек) обсяг вільної кучі на компактному модулі [ESP-01](root:cat-hw-boards/esp-01) зазвичай становить лише від 20 до 30 КБ (від 20480 до 30720 байтів). Таке суттєве обмеження пояснюється математичним розкладом статичних резервів загального обсягу оперативної пам'яті даних @@en|DRAM@@ у 80 КБ (81920 байтів). З цієї загальної суми статичні секції @@en|.data@@ та @@en|.bss@@ (глобальні змінні та константи) вилучають близько 10–12 КБ (11264 байти), системні стеки задач та черги операційної системи забирають 8–10 КБ (9216 байтів), а апаратні кільцеві буфери приймання й передачі драйвера @@en|Wi-Fi@@ разом із таблицями @@en|PHY@@, дескрипторами @@en|DMA@@ та внутрішніми масивами @@en|SDK@@ займають від 38 до 45 КБ (41984 байти). У результаті початковий залишок вільної кучі розраховується за формулою `H_init = 81920 - (11264 + 9216 + 41984) = 19456` байтів (близько 19 КБ), що узгоджується з практичним діапазоном 20–30 КБ залежно від точних налаштувань прошивки. Під час пікових навантажень — при відкритті кількох мережевих сокетів або прийомі великих пакетів даних — стек @@en|lwIP@@ динамічно виділяє пам'ять із цієї залишкової кучі. Якщо обсяг запитаної пам'яті перевищує поточний залишок, виникає критична помилка @@en|Out of Memory@@ (від англійського @@en|out of memory@@ — вичерпання пам'яті), яка спричиняє втрату пакетів, розрив сокетів або аварійне скидання мікроконтролера через спрацювання таймера @@en|WDT@@.

Для побудови математичної моделі стабільної системи необхідно чітко розрахувати межі споживання @@en|DRAM@@ для кожного типу сокета та визначити критичний поріг вільної кучі, за якого стек @@en|lwIP@@ зберігає працездатність.

Математичний розрахунок необхідного обсягу оперативної пам'яті базується на сумуванні фіксованих системних структур та динамічних буферів, що виділяються при відкритті кожного мережевого з'єднання. Ключовими складовими цього балансу виступають блоки керування протоколами @@en|PCB@@ (від англійського @@en|Protocol Control Block@@ — блок керування протоколом), системна черга пакетових буферів @@en|pbuf@@ (від англійського @@en|packet buffer@@ — пакетовий буфер) та службові масиви сокетних дескрипторів. Розуміння алгебраїчної залежності між налаштуваннями стека `lwIP` та фактичною витратою кучі дозволяє інженеру заздалегідь обчислити граничну кількість одночасних сесій `N_max`, упереджуючи ситуації нестачі пам'яті ще на етапі проєктування системи.

## Математична модель структур даних lwIP

Споживання пам'яті мережевим стеком @@en|lwIP@@ складається зі статичних накладних витрат на блоки керування протоколами та динамічних витрат на пакетові буфери. Основним елементом обліку стану з'єднання є блок керування протоколом @@en|PCB@@ (від англійського @@en|Protocol Control Block@@ — блок керування протоколом). Для протоколу @@en|TCP@@ розмір структури `struct tcp_pcb`, яку позначимо як `S_pcb_tcp`, становить 160 байтів. Ця структура зберігає таймери, номери послідовностей, стан з'єднання та параметри вікон. Для протоколу @@en|UDP@@ розмір структури `struct udp_pcb`, позначений як `S_pcb_udp`, становить лише 32 байти, оскільки @@en|UDP@@ не потребує збереження стану сесії.

Передавання та прийом даних виконуються через пакетові буфери @@en|pbuf@@ (від англійського @@en|packet buffer@@ — пакетовий буфер). Кожен буфер містить системний заголовок `struct pbuf` розміром `S_pbuf_hdr = 16` байтів, який зберігає вказівники на наступний буфер у ланцюжку, корисне навантаження та службові прапорці. Повний обсяг пам'яті для одного буфера `S_pbuf` обчислюється як сума заголовка та довжини корисного навантаження `L_payload`.

Для прийому даних за протоколом @@en|TCP@@ стек виділяє ковзне вікно прийому @@en|TCP_WND@@ (від англійського @@en|TCP Window@@ — вікно прийому TCP), розмір якого у байтах позначимо як `TCP_WND`. Максимальний розмір відрізка позначимо як @@en|MSS@@ (від англійського @@en|Maximum Segment Size@@ — максимальний розмір відрізка) зі значенням `MSS`. Кількість буферів прийому `N_rx` розраховується як частка від ділення розміру вікна на `MSS`, округлена до більшого цілого.

Загальні витрати пам'яті `M_tcp` на один активний сокет @@en|TCP@@ обчислюються як сума розміру `S_pcb_tcp`, пам'яті буферів прийому `M_rx` та буфера передачі `M_tx`.

Обчислимо витрати пам'яті для одного @@en|TCP@@ сокета за типових параметрів стека `MSS = 1460` байтів, `TCP_WND = 2920` байтів та `TCP_SND_BUF = 1460` байтів:

```
N_rx = ceil(TCP_WND / MSS)
     = ceil(2920 / 1460)              [ділення вікна прийому на максимальний розмір відрізка]
     = 2                              [кількість необхідних пакетових буферів прийому]

M_rx = TCP_WND + N_rx × S_pbuf_hdr
     = 2920 + 2 × 16                  [додавання накладних витрат заголовків pbuf]
     = 2952                           [загальний обсяг буферів прийому у байтах]

M_tcp = S_pcb_tcp + M_rx + TCP_SND_BUF
      = 160 + 2952 + 1460             [підстановка витрат PCB, буферів прийому та передачі]
      = 4572                          [підсумовування загального обсягу DRAM на один TCP сокет]
```

З обчислення видно, що один активний @@en|TCP@@ сокет із дефолтними налаштуваннями забирає з кучі 4572 байти (понад 4.4 КБ) @@en|DRAM@@, де левову частку становить буферизація даних.

## Розрахунок вікон TCP та ліміту сокетів

Пропускна здатність мережевого з'єднання обмежена математичним добутком BDP @@en|BDP@@ (від англійського @@en|Bandwidth-Delay Product@@ — добуток пропускної здатності на затримку), який визначає кількість даних у дорозі. Значення `BDP` розраховується як добуток пропускної здатності каналу `C` (байтів за секунду) на час круглого проходження пакета `RTT` (секунд): `BDP = C × RTT`. Для повного завантаження каналу розмір вікна прийому `TCP_WND` повинен відповідати `BDP`. Проте у мікроконтролері @@en|ESP8266@@ обсяг кучі є вузьким місцем, тому розмір `TCP_WND` обирають виходячи з жорстких лімітів @@en|DRAM@@, а не максимальної швидкості каналу.

Щоб визначити максимальну кількість одночасних з'єднань `N_max`, необхідно врахувати загальний наявний залишок кучі `H_avail` та мінімальний системний резерв `M_reserve`, необхідний для внутрішніх потреб @@en|SDK@@ і запобігання фатальним помилкам. Корисна пам'ять `H_net` обчислюється як різниця `H_avail - M_reserve`.

Припустимо, що після підключення до мережі вільна куча становить `H_avail = 24576` байтів (24 КБ), а системний резерв прийнято рівним `M_reserve = 8192` байти (8 КБ). Визначимо максимальне число @@en|TCP@@ з'єднань `N_max` при витраті `M_tcp = 4572` байти на сокет:

```
H_net = H_avail - M_reserve
      = 24576 - 8192                  [віднімання системного резерву від доступної кучі]
      = 16384                         [корисна пам'ять для розміщення мережевих сокетів]

N_max = floor(H_net / M_tcp)
      = floor(16384 / 4572)           [ділення корисної пам'яті на витрату одного сокета]
      = 3                             [математична межа одночасних TCP з'єднань]
```

Отже, при стандартній конфігурації стека спроба відкрити більше ніж 3 одночасні @@en|TCP@@ сесії призведе до вичерпання кучі та помилки @@en|Out of Memory@@.

Для порівняння, сокет @@en|UDP@@ без буферизації сесії вимагає лише `M_udp = S_pcb_udp + S_pbuf_hdr + L_payload`. При розмірі корисного навантаження `L_payload = 512` байтів витрата становить `32 + 16 + 512 = 560` байтів. У таком разі математичний ліміт каналів @@en|UDP@@ обчислюється як `floor(16384 / 560) = 29` з'єднань, що робить @@en|UDP@@ значно ефективнішим за витратами пам'яті для простих датчиків.

## Оптимізація конфігурації для запобігання аваріям

Для збільшення кількості одночасних з'єднань або збереження кучі під інші задачі необхідно оптимізувати параметри стека @@en|lwIP@@. Основним важелем оптимізації є зменшення розміру вікна прийому `TCP_WND` та максимального відрізка `MSS`. Для малих пакетів інтернету речей (наприклад, телеметрії @@en|MQTT@@) недоцільно тримати `MSS = 1460` байтів. Зменшення `MSS` до 536 байтів та `TCP_WND` до 536 байтів дозволяє скоротити буферні витрати сокета в кілька разів.

Розрахуємо оптимізовані витрати пам'яті `M_tcp_opt` при `MSS = 536` байтів, `TCP_WND = 536` байтів та `TCP_SND_BUF = 536` байтів:

```
N_rx_opt = ceil(TCP_WND / MSS)
         = ceil(536 / 536)            [розрахунок кількості буферів для зменшеного MSS]
         = 1                          [необхідний один пакетовий буфер]

M_rx_opt = TCP_WND + N_rx_opt × S_pbuf_hdr
         = 536 + 1 × 16               [обчислення обсягу оптимізованого буфера прийому]
         = 552                        [загальний обсяг буфера прийому у байтах]

M_tcp_opt = S_pcb_tcp + M_rx_opt + TCP_SND_BUF
          = 160 + 552 + 536           [підстановка оптимізованих параметрів]
          = 1248                      [підсумовування витрат оптимізованого TCP сокета]
```

Після оптимізації витрата пам'яті на один @@en|TCP@@ сокет зменшується з 4572 до 1248 байтів (у 3.6 раза). Здійснимо розрахунок нового ліміту сокетів при наявній корисній кучі `H_net = 16384` байти:

```
N_max_opt = floor(H_net / M_tcp_opt)
          = floor(16384 / 1248)       [ділення корисної кучі на оптимізовані витрати сокета]
          = 13                        [новітня математична межа з'єднань]
```

Оптимізація параметрів `TCP_WND` та `MSS` дозволяє розширити межу одночасних з'єднань з 3 до 13 без загрози вичерпання кучі. Додатково в конфігурації @@en|lwIP@@ слід обмежити параметри статичних пулів `MEMP_NUM_PBUF` та `MEMP_NUM_TCP_PCB` відповідно до розрахованого ліміту `N_max_opt`, що гарантує захист системи від фрагментації пам'яті та критичних аварій під час мережевих сплесків. Навіть при використанні додаткових рівнів безпеки, таких як [шифровані SSL/TLS з'єднання](root:cat-hw-boards/esp8266-at-ssl-tls), цей обчислювальний підхід дозволяє заздалегідь оцінити накладні витрати й уникнути збоїв.
