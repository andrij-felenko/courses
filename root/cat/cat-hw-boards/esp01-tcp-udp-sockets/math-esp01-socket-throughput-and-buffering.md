## Обмеження швидкості шини UART

Під час передачі мережевих пакетів через прошивку @@en|ESP-AT@@ модуля [платі ESP-01](root:cat-hw-boards/esp-01) фізичний послідовний інтерфейс @@en|UART@@ (англ. @@en|Universal Asynchronous Receiver-Transmitter@@, від @@en|universal@@ — універсальний, @@en|asynchronous@@ — асинхронний, @@en|receiver@@ — приймач та @@en|transmitter@@ — передавач) найчастіше стає головним вузьким місцем усієї системи. Перш ніж потік даних потрапить до Wi-Fi трансивера або до обробника хост-контролера, кожен байт обгортається в апаратний кадр послідовного обміну.

У стандартній конфігурації кадру `8N1` (8 бітів даних, без біта парності, 1 стартовий біт та 1 стоповий біт) загальна кількість переданих бітів `N_bits` на один корисний байт складається з трьох компонентів:

```
N_bits = 1 + 8 + 1
= 10 біт                    [кадр 8N1: 1 start, 8 data, 1 stop]
```

Проте вибір більш захищених форматів кадру безпосередньо збільшує обсяг `N_bits` і знижує підсумкову корисну пропускну здатність шини. Додавання біта парності для контролю парності чи непарності (конфігурації `8E1` або `8O1`) розширює кадр до 11 бітів, а конфігурація з двома стоповими бітами та бітом парності (`8E2` або `8O2`) збільшує кадр до 12 бітів:

```
N_bits_parity = 1 + 8 + 1 + 1
= 11 біт                    [кадр 8E1/8O1: додавання 1 біта парності parity]
N_bits_max = 1 + 8 + 1 + 2
= 12 біт                    [кадр 8E2/8O2: додавання біта парності та 2 стопових бітів]
```

Збільшення довжини кадру `N_bits` з 10 до 11 або 12 бітів призводить до пропорційного зниження швидкості передачі даних на 9.1% та 16.7% відповідно при тому самому значенні @@en|baud rate@@.

Знаючи фізичну швидкість лінії `B` у бодах (англ. @@en|baud rate@@, швидкість передачі бітів за секунду), максимальний сирий потік байтів `R_raw` у байтах за секунду (Б/с) обчислюється як відношення швидкості шини до повної довжини кадру:

```
R_raw = B ÷ N_bits
= B ÷ 10                    [пропускна здатність UART у Б/с]
```

Для базвої швидкості `B = 115200` бод обчислення максимального фізичного потоку виконується кроками:

```
R_raw = 115200 ÷ 10
= 11520 Б/с                 [фізична швидкість вибірки байтів]
= 11520 ÷ 1024
≈ 11.25 КБ/с                [переведення в кілобайти за секунду]
```

Якщо ж перемикнути шину на підвищену швидкість `B = 921600` бод, гранична пропускна здатність зростає пропорційно:

```
R_raw = 921600 ÷ 10
= 92160 Б/с                 [потік байтів при 921600 бод]
= 92160 ÷ 1024
= 90.0 КБ/с                 [переведення в КБ/с]
```

Таким чином, фізична межа байтового потоку шини @@en|UART@@ безпосередньо обмежена коефіцієнтом `0.1 × B` Б/с. Будь-які мережеві протоколи вищого рівня можуть лише зменшувати цей показник через додаткові заголовочні накладні витрати (англ. @@en|overhead@@, від англ. @@en|over@@ — понад та @@en|head@@ — голова).

Для запобігання втраті даних на максимальних швидкостях передачі розробник мусить враховувати не лише суху математичну межу пропускної здатності, а й апаратні механізми синхронізації. При роботі на швидкостях понад `115200` бод виникає ризик переповнення пристійного апаратного буфера @@en|FIFO@@ та виникнення помилок кадрування (англ. @@en|framing error@@), якщо процесор @@en|ESP8266@@ заповнений службовими завданнями Wi-Fi. З математичного боку, апаратне переривання @@en|UART@@ спрацьовує при досягненні порогу заповнення буфера `N_thresh` (наприклад, 112 байтів із загального обсягу `N_fifo = 128` байтів у [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview)). Гранично припустимий час затримки реакції обробника переривань `t_lat_max` обчислюється як час заповнення залишку буфера `(N_fifo - N_thresh) × (N_bits / B)`. При швидкості `B = 921600` бод та резерві у 16 байтів цей часовий інтервал становить `16 × (10 / 921600) ≈ 173.6` мкс. Якщо системні переривання Wi-Fi блокують процесор на час, що перевищує 173.6 мкс, апаратний буфер переповнюється і байти втрачаються. У таких режимах обов'язковим стає використання апаратного керування потоком (англ. @@en|Hardware Flow Control@@) через лінії @@en|RTS/CTS@@, яке фізично призупиняє передачу байтів хост-контролером на час обробки накопиченого кадру у внутрішньому кільцевому буфері прошивки.

## Розрахунок пропускної здатності TCP та UDP

Отриманий потік `R_raw` передає не лише корисний вміст застосунку (англ. @@en|payload@@), а й супровідні заголовки мережевих протоколів стека @@en|LwIP@@ (англ. @@en|Lightweight IP@@, легковагий протокол IP). При формуванні кадру кожен рівень мережевої моделі додає власні службові поля.

Службові накладні витрати складаються із заголовка мережевого рівня IP (20 байтів) та заголовка транспортного рівня @@en|TCP@@ (англ. @@en|Transmission Control Protocol@@, 20 байтів) або @@en|UDP@@ (англ. @@en|User Datagram Protocol@@, 8 байтів). Сумарні витрати заголовків `H_tcp` для TCP становлять 40 байтів, а `H_udp` для UDP — 28 байтів.

При максимальному розмірі кадру @@en|MTU@@ (англ. @@en|Maximum Transmission Unit@@, 1500 байтів) граничний розмір корисного сегмента @@en|TCP MSS@@ (англ. @@en|Maximum Segment Size@@) обчислюється як:

```
MSS = MTU - 20 - 20
= 1500 - 40
= 1460 байт                 [максимальний корисний обсяг TCP]
```

Коефіцієнт ефективності корисного навантаження `E_tcp` визначається як частка корисних даних у загальному розмірі пакета:

```
E_tcp = MSS ÷ (MSS + H_tcp)
= 1460 ÷ (1460 + 40)
= 1460 ÷ 1500
≈ 0.9733                    [ефективність TCP ~ 97.33%]
```

Для протоколу UDP з максимальним навантаженням 1472 байти коефіцієнт `E_udp` становить:

```
E_udp = 1472 ÷ (1472 + 28)
= 1472 ÷ 1500
≈ 0.9813                    [ефективність UDP ~ 98.13%]
```

Реальна пропускна здатність корисних даних `S_payload` при обмеженні з боку шини @@en|UART@@ визначається добутком фізичної швидкості на коефіцієнт ефективності:

```
S_payload = R_raw × E_tcp
= 11520 × 0.9733
≈ 11212 Б/с                 [корисна швидкість TCP при 115200 бод]
≈ 10.95 КБ/с
```

Окрім мережевих заголовків, під час прийому даних через Wi-Fi прошивка додає текстовий префікс `+IPD,<id>,<len>:`. Для блоку розміром 1460 байтів довжина текстового службового префікса `K_at` складає 13 байтів, що додає ще близько 0.9% накладних витрат під час вичитування даних хост-контролером. Однак при зміні розміру кадру набагато меншим значенням, наприклад для малого пакета у 64 байти, відносний вплив оверхеду кардинально змінюється: префікс `+IPD,0,64:` довжиною 11 байтів створює вже 17.19% додаткових витрат лише на рівні AT-команд. Разом із 40 байтами заголовків IP та TCP сумарний обсяг службових полів досягає 51 байта на 64 байти даних, через що корисна ефективність каналу падає з 96.5% для кадру MSS до 55.65%, а мережева шина перевитрачає понад 44% смуги на передачу службової інформації.

## Буферизація LwIP та парсинг префіксів

Обмежений обсяг динамічної оперативної пам'яті (англ. @@en|Dynamic RAM@@, @@en|DRAM@@) в [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) вимагає суворого розрахунку буферів під час прийому спалахів даних з мережі Wi-Fi. Якщо вхідна швидкість Wi-Fi `R_in` перевищує швидкість вичитування через @@en|UART@@ `R_out`, у оперативній пам'яті накопичуються невідпрацьовані пакети.

Швидкість накопичення байтів у кільцевому буфері (англ. @@en|ring buffer@@) `ΔR` під час активного спалаху обчислюється як різниця входження та виходження:

```
ΔR = R_in - R_out
```

Мінімально необхідний обсяг буферної пам'яті `M_buf` для безвтратного прийому спалаху тривалістю `t_burst` визначається формулою:

```
M_buf ≥ (R_in - R_out) × t_burst
```

За умови, що мережевий потік Wi-Fi забезпечує `R_in = 100000` Б/с (100 КБ/с) протягом `t_burst = 0.05` с (50 мс), а послідовний порт працює на швидкості `115200` бод (`R_out = 11520` Б/с):

```
ΔR = 100000 - 11520
= 88480 Б/с                 [швидкість заповнення буфера]

M_buf ≥ 88480 × 0.05
= 4424 Б                    [необхідний розмір буфера в DRAM ~ 4.32 КБ]
```

За наявності виділеного буфера розміром `M_buf = 2048` байтів критичний час тривалості спалаху `t_max` до моменту переповнення пам'яті обчислюється як відношення обсягу буфера до швидкості накопичення. Окрім обмежень на прийом, передача даних хост-контролером також вимагає розрахунку мінімального часового інтервалу `t_interval` між послідовними командами `AT+CIPSEND`. Якщо надсилати нову порцію раніше, ніж стек @@en|LwIP@@ відправить попередній кадр у мережу та звільнить передавальний буфер `TCP_SND_BUF`, сокет блокується з відповіддю `BUSY` або `ERROR`. Для порції корисного навантаження `L_chunk` мінімальна затримка між викликами розраховується як сума часу передачі кадру по послідовному порту `t_tx = (L_chunk + L_cmd) ÷ R_uart` та часу очікування мережевої підтверджувальної відповіді (англ. @@en|Round-Trip Time@@, @@en|RTT@@, `t_rtt`): `t_interval ≥ t_tx + t_rtt`. При швидкісних параметрах `115200` бод і `L_chunk = 1460` байтів (`t_tx ≈ 128` мс) та середній мережевій затримці `t_rtt ≈ 20` мс безпечна пауза між командами становить не менше `148` мс, що гарантує стабільне вичищення буферів без блокування сокета.

```
t_max = M_buf ÷ ΔR
= 2048 ÷ 88480
≈ 0.0231 с                  [переповнення виникає через 23.1 мс]
```

Для надсилання даних через команду `AT+CIPSEND` вибір оптимального розміру порції `L_chunk = 1460` байтів гарантує передачу одним кадром без фрагментації. Детальніше про синтаксис команд та режимів вводу-виводу описано в статті про [Керування GPIO виводами ESP8266 через AT-команди](root:cat-hw-boards/esp8266-at-gpio-control). Час передачі кадру `t_send` через послідовний порт при 115200 бод становить:

```
t_send = (1460 + 15) ÷ 11520
= 1475 ÷ 11520
≈ 0.128 с                   [часова затримка передачі ~ 128 мс]
```

Підвищення швидкості @@en|UART@@ до 921600 бод зменшує затримку передачі одного кадру `t_send` до 16 мс, що розвантажує буфери пам'яті @@en|DRAM@@ та упереджує вичерпання ресурсів стека @@en|LwIP@@.
