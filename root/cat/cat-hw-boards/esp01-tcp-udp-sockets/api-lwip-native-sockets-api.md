## Архітектура сокетів lwIP та подійний механізм

Розробка мережевого програмного забезпечення для систем з обмеженими ресурсами вимагає відходу від класичної моделі @@en|BSD Sockets@@. У традиційних операційних системах кожен сокет блокує виклик виконання в окремому потоці, що вимагає виділення власного стеку викликів обсягом від 2 до 4 КБ в оперативній пам'яті. Для мікроконтролера у [модулі ESP-01](root:cat-hw-boards/esp-01), де вільний залишок системи динамічної пам'яті @@en|DRAM@@ (від англ. *@@en|Data RAM@@* — оперативна пам'ять даних) часто становить лише від 20 до 30 КБ, створення кількох паралельних потоків призводить до миттєвого вичерпання ресурсів.

Для розв'язання цієї проблеми в середовищі розробки мікроконтролера застосовують мережевий стек @@en|lwIP@@ (від англ. *@@en|Lightweight IP@@* — полегшений протокол IP), який пропонує низькорівневий асинхронний інтерфейс @@en|lwIP RAW API@@. Замість блокування потоків виконання обробка мережевих подій відбувається в єдиному циклі через механізм зворотно-викликових функцій — @@en|callback@@. Ядром цієї архітектури є управляючий блок протоколу @@en|PCB@@ (від англ. *@@en|Protocol Control Block@@* — блок керування протоколом), який зберігає стан з'єднання, адреси та вказівники на функції обробки.

![Схема взаємодії керуючого блоку tcp_pcb із мережевим стеком lwIP та асинхронними кольбеками показує потік обробки подій accept, recv та sent](img/lwip-raw-api-pcb-callbacks-flow.svg)
*Схема асинхронної обробки подій та керування блоком tcp_pcb у lwIP RAW API.*

Такий підхід повністю усуває витрати пам'яті на окремі стеки потоків і запобігає блокуванню процесорного ядра. Усі події надходження даних, встановлення з'єднання чи виникнення помилок передаються системою в зареєстровані користувацькі функції, що дозволяє досягти максимальної продуктивності в [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).

Усередині системного циклу обробки подій (від англ. *@@en|SDK main loop@@* — головний цикл розробницького комплекту) передача мережевих даних починається з апаратного переривання (від англ. *@@en|interrupt@@* — сигнальне переривання процесора) від Wi-Fi трансивера. Отримавши фізичний кадр на рівні @@en|Wi-Fi MAC layer@@, контролер формує системну задачу в черзі подій @@en|event queue@@, не виконуючи обробку даних безпосередньо усереднені обробника переривань. Головний потік системи послідовно вибирає події з черги, викликає стек @@en|lwIP@@ для аналізу заголовків пакетів і лише після цього передає керування у зареєстрований користувацький @@en|callback@@. Такий двостадійний механізм запобігає тривалому запереченню переривань, гарантує стабільну роботу радіомодуля та усуває накладні витрати на перемикання контексту (від англ. *@@en|context switch@@* — зміна контексту виконання).

Оскільки в однопотоковому режимі розробницького комплекту користувацький код та фонові системні процеси радіомодуля виконуються в єдиному контексті ядра [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), тривалість виконання асинхронного кольбека стає критичним фактором стабільності. Якщо користувацька функція виконує тривалі обчислення або затримує повернення керування, системний цикл втрачає можливість вчасно опрацьовувати фонові Wi-Fi процедури та надсилати службові кадри підтримки зв'язку (від англ. *@@en|keep-alive@@* — підтримка активності з'єднання). Це призводить до примусового розриву зв'язку точкою доступу або спрацьовування сторожового таймера (від англ. *@@en|watchdog timer@@* — сторожовий таймер) з подальшим перезавантаженням мікроконтролера. Тому обробники подій @@en|lwIP RAW API@@ розробляють як короткі неподільні операції, які лише копіюють вхідні дані або оновлюють прапорці стану, делегуючи складну обробку фоновим задачам через системний таймер.

## Життєвий цикл TCP-з'єднання та блоки PCB

Керування з'єднанням @@en|TCP@@ у низькорівневому C-інтерфейсі виконується через структуру `struct tcp_pcb`. Процес починається зі створення нового блоку за допомогою функції `tcp_new()`, яка виділяє оперативну пам'ять із динамічної кучі. Для сервера створений блок прив'язується до локального порту через `tcp_bind()`, після чого переводиться в стан очікування викликом `tcp_listen()`.

Для обробки вхідних підключень застосовують функцію `tcp_accept()`, яка реєструє користувацький @@en|callback@@. Під час ініціалізації вихідного з'єднання використовують функцію `tcp_connect()`, яка приймає вказівник на функцію підтвердження встановлення зв'язку.

:::tabs
@tab C (ESP-SDK)
```c|esp8266-sdk
struct tcp_pcb *server_pcb = tcp_new();
if (server_pcb != NULL) {
    err_t err = tcp_bind(server_pcb, IP_ADDR_ANY, 80);
    if (err == ERR_OK) {
        server_pcb = tcp_listen(server_pcb);
        tcp_accept(server_pcb, http_accept_cb);
    }
}
```
@tab C++
```cpp|esp8266-sdk
struct tcp_pcb *server_pcb = tcp_new();
if (server_pcb != nullptr) {
    err_t err = tcp_bind(server_pcb, IP_ADDR_ANY, 80);
    if (err == ERR_OK) {
        server_pcb = tcp_listen(server_pcb);
        tcp_accept(server_pcb, [](void *arg, struct tcp_pcb *newpcb, err_t err) -> err_t {
            // Обробка вхідного з'єднання
            return ERR_OK;
        });
    }
}
```
:::

Після встановлення з'єднання обмін даними здійснюється через реєстрацію обробників `tcp_recv()` та `tcp_sent()`. Передача даних вимагає виклику `tcp_write()` для розміщення байтів у вихідній черзі та `tcp_output()` для їх негайного відправлення в мережу. Для відстеження підтвердження доставки віддаленим вузлом стек @@en|lwIP@@ викликає обробник `tcp_sent_fn`, передаючи параметр `len` — кількість байтів, підтверджених пакетом @@en|ACK@@. Оскільки вихідна черга обмежена обсягом `tcp_sndbuf()` та розміром передавального вікна віддаленого сокета, надсилання великих масивів даних вимагає порційного виклику `tcp_write()`. Отримання сповіщення у кольбеку `tcp_sent` означає, що стек деалокував підтверджені сегменти з вихідної черги та розширив вільне вікно відправки, сигналізуючи програмі про можливість передати наступний блок байтів без ризику переповнення буфера. Для приймання даних @@en|lwIP@@ викликає зареєстровану функцію `tcp_recv_fn`, передаючи вказівник на ланцюжок буферів `struct pbuf`. Якщо шар мережі передав пакет (`p != NULL`), програма зчитує вміст, після чого вивільняє пам'ять через `pbuf_free()` та обов'язково викликає `tcp_recved()`, сповіщаючи стек про обсяг прочитаних байтів для зсуву ковзного вікна. При успішній обробці кольбек повертає значення `ERR_OK`. В умовах обмеженої оперативної пам'яті [мікроконтролера ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), якщо приймальне вікно або черги додатку насичені і новий пакет неможливо опрацювати, повернення помилки `ERR_MEM` інформує стек про брак пам'яті, призупиняючи підтвердження кадру та створюючи зворотний тиск (від англ. *backpressure* — зворотний тиск) на віддалений вузол. Завершення сесії виконується функцією `tcp_close()`, яка надсилає пакет із прапорцем @@en|FIN@@ та вивільняє структуру `struct tcp_pcb`.

## Управління буферами pbuf та передача UDP

Усі мережеві пакети в стеку @@en|lwIP@@ описуються через структури буферів пакетів @@en|pbuf@@ (від англ. *@@en|Packet Buffer@@* — буфер пакета). Залежно від призначення буфери виділяються з різних областей пам'яті: `PBUF_RAM` розміщується в динамічній кучі для передачі даних, `PBUF_POOL` виділяється з фіксованого пулу для швидкого приймання перериваннями, а `PBUF_ROM` та `PBUF_REF` посилаються на статичні дані в Flash-пам'яті або зовнішніх буферах без копіювання.

![Двобічнозв'язаний ланцюжок структур pbuf у RAM показує виділення та послідовне вивільнення пам'яті через pbuf_free](img/lwip-pbuf-chain-memory-structure.svg)
*Структура ланцюжка буферів pbuf у пам'яті DRAM.*

Для передачі датаграм без встановлення постійного з'єднання використовується протокол @@en|UDP@@. Створення та прив'язка здійснюються функціями `udp_new()` та `udp_bind()`, а приймання даних налаштовується викликом `udp_recv()`.

:::tabs
@tab C (ESP-SDK)
:::code api-lwip-native-sockets-api/c/esp8266-sdk/udp-pcb.c
@tab C++
```cpp|esp8266-sdk
void send_udp_packet_cpp() {
    struct udp_pcb *upcb = udp_new();
    struct pbuf *p = pbuf_alloc(PBUF_TRANSPORT, 12, PBUF_RAM);
    if (p != nullptr) {
        std::memcpy(p->payload, "Hello UDP", 10);
        ip_addr_t dest_ip;
        IP4_ADDR(&dest_ip, 192, 168, 1, 100);
        udp_sendto(upcb, p, &dest_ip, 1234);
        pbuf_free(p);
    }
    udp_remove(upcb);
}
```
:::

Критичним інваріантом роботи з `pbuf` є суворе управління лічильником посилань `p->ref`. Функція `pbuf_free()` зменшує лічильник посилань на одиницю і вивільняє пам'ять блоку (а також рекурсивно обходить і вивільняє зв'язані вузли в ланцюжку `p->next`) лише тоді, коли значення лічильника досягає нуля. При об'єднанні сегментів у ланцюжок через `pbuf_chain()` або передачі пакета на нижній рівень мережевого інтерфейсу в обробник `netif->output`, стек @@en|lwIP@@ викликає `pbuf_ref()`, збільшуючи значення `p->ref` для утримання буфера під час асинхронного відправлення драйвером. Це дозволяє прикладному коду безпечно викликати `pbuf_free()` одразу після виклику відправки, адже фізичне зняття буфера з кучі станеться лише після завершення передачі драйвером `netif`. Окрему економію пам'яті забезпечують типи буферів `PBUF_ROM` та `PBUF_REF`, які виключають дублювання даних у кучі: тип `PBUF_ROM` спрямовує вказівник `p->payload` безпосередньо на константи у Flash-пам'яті, а `PBUF_REF` посилається на зовнішні статичні буфери в RAM. Для цих типів функція `pbuf_alloc()` виділяє лише саму структуру `struct pbuf`, реалізуючи передачу без копіювання корисного навантаження. Критичною вимогою при використанні `PBUF_ROM` та `PBUF_REF` є гарантія незмінності вихідних даних увесь час, поки лічильник `p->ref` більший за нуль, оскільки модифікація чи вивільнення зовнішнього буфера до завершення відправки призведе до пошкодження кадру. Проте забутий виклик `pbuf_free()` після обробки пакета призводить до незворотного витоку пам'яті у динамічній кучі [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).

## Обробка мережевих помилок та розривів зв'язку

Асинхронний характер @@en|lwIP RAW API@@ вимагає окремого механізму інформування програми про мережеві збої, такі як скидання з'єднання тайм-аутом, втрата носія або примусовий розрив пакетом @@en|TCP RST@@. Для цього використовується функція `tcp_err()`, яка реєструє обробник помилок для вказаного блоку `tcp_pcb`.

Особливістю функціонування обробника помилок `tcp_err()` є те, що під час його виклику стек @@en|lwIP@@ вже самостійно деалокував відповідну структуру `struct tcp_pcb` і вивільнив її пам'ять.

:::tabs
@tab C (ESP-SDK)
```c|esp8266-sdk
void tcp_error_cb(void *arg, err_t err) {
    // Вказівник на pcb вже недійсний!
    // Дозволено лише очищати користувацькі структури за вказівником arg
    my_conn_state_t *state = (my_conn_state_t *)arg;
    if (state != NULL) {
        state->is_connected = 0;
        free(state);
    }
}
```
@tab C++
```cpp|esp8266-sdk
void tcp_error_cb_cpp(void *arg, err_t err) {
    auto *state = static_cast<my_conn_state_t *>(arg);
    if (state != nullptr) {
        state->is_connected = false;
        delete state;
    }
}
```
:::

Спроба викликати `tcp_close()` або звернутися до полів `pcb` усередині кольбека `tcp_err()` призводить до повторного вивільнення вже вільної пам'яті (англ. *double free*) та негайного перезавантаження мікроконтролера. Правильна обробка помилок передбачає перевірку стану з'єднувального прапорця, вивільнення лише користувацьких структур даних та ініціалізацію асинхронних повторних спроб підключення.

Щоб безпечно відновити втрачений зв'язок без ризику зациклення або виклику у контексті обробника помилки, ініціалізацію нового сокета виносять у програмний таймер (від англ. *@@en|software timer@@* — системний програмний запізнювач) за допомогою структури `os_timer_t`. Усередині кольбека `tcp_err()` програма лише скидає прапорці стану, вивільняє користувацькі ресурси та запускає одноразовий таймер через `os_timer_arm()` із витримкою часу (від англ. *@@en|backoff delay@@* — затримка перед повторною спробою, зазвичай від 1000 до 5000 мс). Коли системний таймер спрацьовує в окремому виклику основного циклу SDK, його обробник створює новий керуючий блок через `tcp_new()`, наново реєструє кольбеки й викликає `tcp_connect()`, повністю розриваючи зв'язок між моментом помилки та створенням нових мережевих ресурсів.
