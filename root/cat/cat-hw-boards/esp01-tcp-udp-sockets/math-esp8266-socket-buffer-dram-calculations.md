## Обмеження DRAM та ризики OOM сокетів

Побудова мережевих пристроїв на базі популярного [модуля ESP-01](root:cat-hw-boards/esp-01) вимагає суворого обліку доступних апаратних ресурсів. Хоча фізичний кристал чипа містить 80 КБ пам'яті @@en|Data Random-Access Memory@@ (від англ. @@en|Data Random-Access Memory@@ — оперативна пам'ять даних, @@en|DRAM@@), значна її частина зарезервована під глобальні змінні системного стека, системну купу та системний буфер бездротового зв'язку. У реальних умовах розробникові залишається не більше ніж `30`–`36` КБ вільної оперативної пам'яті для динамічного розміщення мережевих сокетів. Додаткову загрозу становить розпухання системних буферів при тимчасових розривах @@en|Wi-Fi@@ зв'язку: під час повторної авторизації бінарний драйвер виділяє додаткові 6–8 КБ кучі під структури сканування ефіру та хендшейку WPA2:

RAM_free_reconnect = RAM_free_initial - ΔRAM_wifi
                   = 32768 - 8192         [віднімання витрат на сканування ефіру та хендшейк WPA2]
                   = 24576                [залишок вільної купи у байтах (24 КБ)]

Спроба відкрити додаткове сокетне з'єднання під час такого перепідключення без попереднього розрахунку викликає помилку вичерпання купи @@en|Out of Memory@@ (від англ. @@en|Out of Memory@@ — вичерпання пам'яті, @@en|OOM@@). У разі нульового залишку пам'яті системний інтерпретатор втрачає можливість обробляти внутрішні події та очищати черги, що призводить до спрацьовування апаратного сторожового таймера @@en|Watchdog Timer@@ (від англ. @@en|Watchdog Timer@@ — сторожовий таймер, @@en|WDT@@) і фатального аварійного перезавантаження чипа.

Особливості розподілу внутрішніх областей оперативної пам'яті висвітлює [огляд архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). При відкритті мережевого сокета в прошивці виділяються два типи оперативної пам'яті: статичні структурні блоки керування з'єднанням та динамічні буфери прийому й передачі. Якщо застосування використовує [захищені SSL/TLS з'єднання](root:cat-hw-boards/esp8266-at-ssl-tls), десеріалізація криптографічних ключів додатково відбирає до `15`–`20` КБ оперативної пам'яті на кожен сеанс, роблячи паралельне обслуговування кількох захищених сокетів неможливим без детального обчислення балансу пам'яті.

## Математична модель витрат пам'яті LwIP

Мережевий стек @@en|Lightweight IP@@ (від англ. @@en|Lightweight IP@@ — полегшений мережевий стек, @@en|LwIP@@) оперує двома основними типами об'єктів у купі DRAM: структурою блоку керування протоколом @@en|Protocol Control Block@@ (від англ. @@en|Protocol Control Block@@ — блок керування протоколом, @@en|PCB@@) та структурами пакетних буферів @@en|Packet Buffer@@ (від англ. @@en|Packet Buffer@@ — пакетний буфер, @@en|pbuf@@). Базовий розмір керуючої структури для протоколу @@en|Transmission Control Protocol@@ (від англ. @@en|Transmission Control Protocol@@ — протокол керування передачею, @@en|TCP@@) становить `S_pcb_tcp = 196` байт, тоді як для простішого протоколу @@en|User Datagram Protocol@@ (від англ. @@en|User Datagram Protocol@@ — протокол користувацьких датаграм, @@en|UDP@@) структура займає `S_pcb_udp = 32` байти.

Кожен пакетний буфер `pbuf` складається зі службового заголовка обсягом `S_pbuf_hdr = 16` байт та зарезервованого місця під мережеві заголовки й корисне навантаження. Загальний обсяг пам'яті `M_conn`, необхідний для обслуговування одного активного TCP-з'єднання з розміром вікна прийому `W_tcp` та максимальним розміром сегмента `MSS`, обчислюється як сума статичної структури `S_pcb_tcp` та динамічної черги пакетних буферів, розрахованої з урахуванням вирівнювання пам'яті по `4`-байтній межі:

```
M_conn
= S_pcb_tcp + N_pbuf · (S_pbuf_hdr + MSS + S_align)      [додавання статичної PCB та динамічних буферів pbuf]
= 196 + 2 · (16 + 1460 + 4)                              [підстановка стандартних параметрів MSS=1460 і N_pbuf=2]
= 196 + 2960                                              [перемноження розміру бувера на кількість пакетів]
= 3156                                                    [підсумковий обсяг у байтах]
```

Таким чином, одне стандартне TCP-з'єднання з розміром `MSS = 1460` байт і буферизацією на `2` сегменти вимагає щонайменше `3156` байт оперативної пам'яті. Для UDP-сокета з корисним навантаженням `N_bytes` обсяг `M_udp` розраховується аналогічно: `M_udp = S_pcb_udp + S_pbuf_hdr + N_bytes`. Отриманий математичний результат показує, що навіть без урахування проміжної буферизації AT-інтерпретатора відкриття кожного нового сокета вилучає фіксований квант динамічної пам'яті з вільної купи.

Окрім власного обсягу структури, динамічний розподільник пам'яті LwIP додає накладні витрати на вирівнювання адреси `S_align` та службові елементи обліку блоків купи. Архітектура 32-бітного ядра Xtensa L106 вимагає вирівнювання вказівників по 4-байтній межі (`MEM_ALIGNMENT = 4`), через що величина вирівнювання розраховується за залежністю `S_align = (4 - (B mod 4)) mod 4` для довільного блоку розміром `B` байт. Додатково кожен виділений фрагмент у глобальному пулі `MEM_SIZE` супроводжується службовим заголовком `struct mem` обсягом `S_mem_hdr = 8` байт, який містить вказівники зв'язаного списку суміжних блоків та прапорці стану. Загальна підсумкова витрата пам'яті пулу `M_pool` для обслуговування з'єднання з урахуванням накладних витрат обчислюється так:

M_pool
= M_conn + S_mem_hdr                     [додавання службового заголовка блоку купи]
= 3156 + 8                                [підстановка розрахованого обсягу з'єднання та 8-байтного заголовка]
= 3164                                    [підсумкова витрата пам'яті пулу MEM_SIZE у байтах]

Такий розрахунок показує, що через накладні витрати вирівнювання та службові поля `struct mem` фактичний витік пам'яті з пулу `MEM_SIZE` перевищує сумарний розмір корисних буферів, додатково зменшуючи доступну купку DRAM при кожній сесії.

## Баланс вікна TCP та швидкості UART

У прошивці мікроконтролера передача даних із мережевого сокета до зовнішнього хост-контролера здійснюється через асинхронний послідовний порт @@en|Universal Asynchronous Receiver-Transmitter@@ (від англ. @@en|Universal Asynchronous Receiver-Transmitter@@ — універсальний асинхронний приймаче-передавач, @@en|UART@@). Для запобігання переповненню вхідних буферів швидкість надходження даних із мережі не повинна перевищувати пропускну здатність шини UART з урахуванням накладних витрат текстового парсера AT-команд та обгортки асинхронних повідомлень `+IPD`.

Пропускна здатність шини `B_uart` у байтах за секунду залежить від встановленої швидкості в бодах `Baud` та кількості біт у кадрі `N_bits = 10` (1 стартовий біт, 8 біт даних, 1 стоповий біт). Мережева швидкість з'єднання обмежується відношенням розміру вікна прийому `W_tcp` до часу кругового затримання @@en|Round-Trip Time@@ (від англ. @@en|Round-Trip Time@@ — час кругового затримання, @@en|RTT@@). Умова апаратної стабільності без ризику вичерпання пам'яті описується нерівністю, де коефіцієнт накладних витрат `k_overhead ≈ 1.15` враховує формування префікса `+IPD,<id>,<len>:`:

```
W_tcp / RTT ≤ B_uart / k_overhead                        [умова балансу пропускної здатності]
W_tcp ≤ (Baud / 10) · RTT / 1.15                         [вираження максимального розміру TCP-вікна]
```

![Залежність споживання DRAM від розміру TCP-вікна та швидкості UART з позначенням зони апаратної стабільності](img/esp8266-dram-tcp-uart-throughput-balance.svg)
*Залежність споживання оперативної пам'яті від конфігурації TCP-вікна та швидкості послідовної шини.*

При швидкості UART `Baud = 115200` біт/с та середній затримці мережі `RTT = 50` мс (`0.05` с) максимальне стійке вікно `W_tcp` обчислюється наступним чином:

**Умова розрахунку:** швидкість UART `115200` біт/с, затримка `RTT = 0.05` с, коефіцієнт витрат `1.15`.

```
B_uart
= 115200 ÷ 10                                             [ділення частоти на 10 біт кадру]
= 11520 B/s                                               [байтів за секунду]

W_max
= 11520 · 0.05 ÷ 1.15                                     [множення на RTT та ділення на коефіцієнт витрат]
= 576 ÷ 1.15                                              [проміжний розрахунок]
≈ 500 B                                                   [підсумкове обмеження розміру вікна]
```

Якщо розмір TCP-вікна перевищує обчислене значення `500` байт при такій швидкості UART, мережевий стек LwIP отримуватиме байти швидше, ніж чип встигатиме передавати їх по послідовній лінії. Це призводить до накопичення пакетів у буферах `pbuf`, вичерпання DRAM і спрацьовування апаратних обмежень, як висвітлює розбір [керування GPIO виводами через AT-команди](root:cat-hw-boards/esp8266-at-gpio-control). На [модулях ESP-01S](root:cat-hw-boards/esp-01s) для вирішення цього розсинхронізму застосовують апаратний контроль потоку RTS/CTS.

## Розрахунок граничного числа сокетів

Для забезпечення довготривалої відмовостійкості системи розробник повинен розраховувати максимально припустиму кількість одночасних відкритих сокетів `N_max`. Розрахунок спирається на загальний обсяг вільної динамічної пам'яті `M_free`, фіксовані накладні витрати операційної системи та резервний технологічний буфер пам'яті `M_reserve ≈ 4096` байт, необхідний для запобігання фатальним @@en|OOM@@-збоям. Проте загальний обсяг `M_free` є лише необхідною, але не достатньою умовою успішного виділення ресурсів під новий сокет. Через хаотичне динамічне створення й видалення мережевих пакетних буферів різної довжини виникає фрагментація купи (від лат. fragmentum — фрагмент; @@en|heap fragmentation@@), яка розбиває вільний простір на безліч розрізнених малих блоків. Оскільки керуючі структури з'єднання та неперервні масиви пам'яті у @@en|DRAM@@ вимагають монолітного розподілу байтів, фактичне відкриття сокета обмежується критерієм мінімального нерозривного блоку `M_block_max ≥ M_conn`, де `M_block_max` — обсяг найбільшої суцільної ділянки вільної купи, а `M_conn` — повний розмір пам'яті під один сокет. Для врахування деградації структури пам'яті до математичної моделі вводиться коефіцієнт фрагментації `k_frag` (`0 < k_frag ≤ 1`), що визначає частку реально доступної пам'яті `M_free_eff = k_frag · M_free`. З урахуванням цього критерію підсумкова формула граничної кількості сокетів набуває вигляду `N_max = ⌊ (k_frag · M_free - M_reserve) / M_conn ⌋`, що запобігає відмовам у виділенні пам'яті під час тривалої експлуатації пристрою.

Формула граничної кількості однакових сокетних з'єднань з індивідуальним споживанням пам'яті `M_conn` виводиться з умови збереження недоторканного резерву купи:

```
M_free - N_max · M_conn ≥ M_reserve                       [умова збереження системного резерву пам'яті]
N_max · M_conn ≤ M_free - M_reserve                       [перенесення резерву у праву частину]
N_max = ⌊ (M_free - M_reserve) / M_conn ⌋                [округлення до меншого цілого]
```

Обчислимо граничну кількість сокетів для реального сценарію роботи чипа.

**Умова розрахунку:** вільна купа після ініціалізації Wi-Fi `M_free = 24576` байт (24 КБ), споживання сокета `M_conn = 3156` байт, резерв `M_reserve = 4096` байт.

```
M_avail
= 24576 - 4096                                            [віднімання технологічного резерву]
= 20480 B                                                 [доступна пам'ять під сокети]

N_max
= 20480 ÷ 3156                                            [ділення доступного обсягу на витрати сокета]
≈ 6.48                                                    [дробове значення]
= 6                                                       [округлення до меншого цілого]
```

Розрахунок показує, що при вільній купі `24` КБ система здатна безпечно утримувати не більше ніж `6` паралельних TCP-сокетів. При спробі відкрити 7-й сокет залишок пам'яті впаде нижче за критичний поріг `4096` байт, викликаючи дефрагментацію купи та перезавантаження WDT при першому ж мережевому сплеску.

Практичні інструкції з вибору режимів та конфігурації прошивки для утримання сокетних з'єднань наведені у матеріалі про [оновлення прошивки ESP-01](root:cat-hw-boards/esp01-firmware-flashing) та довіднику з [режимів завантаження ESP8266](root:cat-hw-boards/esp8266-boot-modes).
