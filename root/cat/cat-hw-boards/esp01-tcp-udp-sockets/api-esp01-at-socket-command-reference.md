## Призначення та режими сокетної підсистеми

Мережева підсистема прошивки ESP-AT перетворює послідовний порт мікроконтролера на повнофункціональний мережевий адаптер TCP/IP. Завдяки цьому хост-контролер керує бездротовими сокетами за допомогою підмножини команд `AT+CIP`, не витрачаючи власні ресурси RAM на обчислення мережевих заголовків чи обробку повторних передач пакетів.

Перед створенням сокетних з'єднань інтерпретатор вимагає вибору системних режимів мультиплексування та тунелювання:
1. Режим мультиплексування (від англ. @@en|Multiplexing@@, @@en|MUX@@ — мультиплексування): команда `AT+CIPMUX=<mode>` визначає кількість одночасних з'єднань. У режимі `AT+CIPMUX=0` (одиночне з'єднання) доступний лише один мережевий канал, але підтримується прозоре тунелювання. У режимі `AT+CIPMUX=1` (багатоканальний режим) стек LwIP дозволяє відкривати до 5 паралельних сокетів, кожен з яких отримує числовий ідентифікатор каналу `link_id` у діапазоні від `0` до `4`.
2. Режим передачі даних (від англ. @@en|Mode@@ — режим): команда `AT+CIPMODE=<mode>` обирає формат трансляції. Значення `AT+CIPMODE=0` вмикає нормальний режим із префіксами та вказуванням довжини пакетів. Значення `AT+CIPMODE=1` активує прозорий режим (англ. @@en|passthrough mode@@), у якому байтовий потік із послідовного порту напряму тунелюється в активний TCP-сокет без текстового кодування.

Вибір конфігурації `AT+CIPMUX` та `AT+CIPMODE` безпосередньо визначає обсяг оперативної пам'яті, що деталізує [архітектура SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). У мультиплексному режимі `AT+CIPMUX=1` мережевий стек LwIP резервує у системній динамічній пам'яті (англ. @@en|DRAM@@, @@en|Dynamic RAM@@ — динамічна пам'ять) додаткові блоки керування протоколом (англ. @@en|PCB@@, @@en|Protocol Control Block@@ — блок керування протоколом) та приймальні буфери для 5 потенційних каналів, що підвищує навантаження на купу. Через це зміна режимів дозволяється лише за відсутності активних сокетних сесій: якщо хост-контролер спробує виконати команду конфігурації під час відкритого з'єднання або працюючого сервера, інтерпретатор відхилить її відповіддю `link is builded` або `ERROR`, запобігаючи руйнуванню вказівників пам'яті LwIP. У випадку ж аварійного обриву фізичного зв'язку, коли у таблицях LwIP залишаються завислі сесії, закриття всіх каналів командою `AT+CIPCLOSE=5` з наступною перемикальною реініціалізацією `AT+CIPMUX=0` примусово звільняє заблоковані структури PCB та очищає бітову карту (англ. @@en|bitmap@@ — бітова карта) сокетів, відновлюючи купу без повного перезавантаження модуля.

| Команда | Варіанти параметрів | Опис та обмеження |
| :--- | :--- | :--- |
| `AT+CIPMUX?` | `+CIPMUX:0` або `+CIPMUX:1` | Зчитування поточного режиму мультиплексування |
| `AT+CIPMUX=0` | Одиночне з'єднання | Одне активне з'єднання; підтримує `AT+CIPMODE=1` |
| `AT+CIPMUX=1` | Мультиплексний режим | До 5 сокетів (`link_id` 0–4); `AT+CIPMODE=1` недоступний |
| `AT+CIPMODE?` | `+CIPMODE:0` або `+CIPMODE:1` | Запит поточного режиму трансляції |
| `AT+CIPMODE=0` | Нормальний режим | Пакети супроводжуються префіксом `+IPD` та `AT+CIPSEND` |
| `AT+CIPMODE=1` | Прозорий тунель | Пряма трансляція RX/TX; вимагає `AT+CIPMUX=0` |

## Управління з'єднаннями та сервером

Створення та завершення мережевих сесій здійснюється групою команд ініціалізації. Формат викликів залежить від встановленого режиму мультиплексування `AT+CIPMUX`.

Ініціалізація активного сокета виконується командою `AT+CIPSTART`:
- У режимі `AT+CIPMUX=0`: `AT+CIPSTART=<type>,<addr>,<port>[,<keep-alive>]`
- У режимі `AT+CIPMUX=1`: `AT+CIPSTART=<link_id>,<type>,<addr>,<port>[,<keep-alive>]`

Параметр `<type>` приймає рядкові значення `"TCP"`, `"UDP"` або `"SSL"`. Параметр `<addr>` вказує IP-адресу або доменне ім'я цільового сервера, а `<port>` — номер віддаленого порту (1–65535). Для протоколу TCP опціональний параметр `<keep-alive>` вказує інтервал зондування активності (1–7200 секунд). Підключення через шифрований канал вимагає налаштування параметрів, що розкривають [захищені SSL/TLS з'єднання](root:cat-hw-boards/esp8266-at-ssl-tls).

Для закриття сокета використовується команда `AT+CIPCLOSE`:
- В одиночному режимі: `AT+CIPCLOSE`
- У мультиплексному режимі: `AT+CIPCLOSE=<link_id>` (де `<link_id>` від `0` до `4`, або значення `5` для примусового закриття всіх активних сокетів).

Створення локального TCP-сервера виконується командою `AT+CIPSERVER=<mode>[,<port>]`. Параметр `<mode>=1` активує сервер на вказаному порту (за замовчуванням `333`), а `<mode>=0` деактивує його. Створення сервера можливе виключно після попереднього виконання `AT+CIPMUX=1`. Кожному новому вхідному клієнтському підключенню прошивка автоматично виділяє найменший вільний ідентифікатор `link_id` у діапазоні від `0` до `4` та виводить асинхронне сповіщення `<link_id>,CONNECT`. Гранична кількість одночасних вхідних сесій обмежена 5 каналами за вирахуванням вже відкритих вихідних сокетів. Якщо всі слоти зайняті, нові спроби підключення відхиляються мережевим стеком LwIP із надсиланням кадру `RST` (від англ. @@en|RST@@, @@en|Reset@@ — скидання з'єднання). Для запобігання вичерпанню вільних ідентифікаторів та утриманню завислих з'єднань використовується команда встановлення таймауту серверного сокета `AT+CIPSTO=<time>`, де `<time>` вказує час інактивації клієнта в секундах (0–7200). Для підсистеми @@en|UDP@@ (від англ. @@en|User Datagram Protocol@@ — протокол користувацьких датаграм) реалізовано розширений алгоритм конфігурування за допомогою параметрів `AT+CIPSTART=[<link_id>,]"UDP",<addr>,<port>[,<local_port>,<mode>]`. Задання локального порту `<local_port>` здійснює апаратне перенаправлення вхідних пакетів на зафіксований канал сокета, а параметр режиму `<mode>=2` активує двонаправлене широкомовне мовлення (англ. @@en|broadcast@@; від *broad* — широкий та *cast* — кидати, транслювати). При встановленні адреси призначення `"255.255.255.255"` та порту мовлення сокет одночасно розсилає датаграми всім вузлам локальної мережі й приймає відповіді з довільних IP-адрес на локальний порт без їх блокування фаєрволом прошивки.

```text
// Приклад 1: Відкриття TCP-клієнта у багатоканальному режимі (link_id = 0)
AT+CIPMUX=1
OK
AT+CIPSTART=0,"TCP","192.168.1.100",8080
0,CONNECT
OK

// Приклад 2: Запуск локального TCP-сервера на порту 80 з таймаутом 60 секунд
AT+CIPMUX=1
OK
AT+CIPSERVER=1,80
OK
AT+CIPSTO=60
OK
```

## Передача даних та прозорий мост

Надсилання даних через відкриті сокети виконується командою `AT+CIPSEND`. Її синтаксис регламентується поточним станом режимів `AT+CIPMUX` та `AT+CIPMODE`.

В одиночному нормальному режимі (`AT+CIPMUX=0`, `AT+CIPMODE=0`) команда приймає довжину кадру: `AT+CIPSEND=<length>`. У відповідь інтерпретатор повертає символ запрошення `>`, після чого хост-контролер надсилає рівно `<length>` байтів. У мультиплексному режимі додається ідентифікатор сокета: `AT+CIPSEND=<link_id>,<length>`.

![Схема автоматів станів переходу та виходу з прозорого режиму тунелювання AT+CIPMODE=1 через комбінацію +++](img/passthrough-tunnel-state-machine.svg)
_*Схема переходу станів між командним режимом, прозорим тунелем AT+CIPMODE=1 та виходом через захисний інтервал комбінації +++.*_

У прозорому режимі (`AT+CIPMUX=0`, `AT+CIPMODE=1`) після встановлення TCP-з'єднання виконується команда `AT+CIPSEND` без параметрів. Інтерпретатор видає символ запрошення `>`, після чого переходить у стан прямих транзитних тунелей. Усі наступні байти з шини UART беззастережно запаковуються в TCP-сегменти та відправляються у мережу.

Для повернення з прозорого тунелю в командний режим без розриву сокетного з'єднання використовується спеціальна послідовність виходу (англ. @@en|escape sequence@@ — послідовність виходу) із трьох символів `+++` без символів переведення рядка `\r\n`. Інтерпретатор вимагає суворого дотримання часових захисних інтервалів (англ. @@en|guard time@@ — захисний інтервал): протягом 1000 мс до надсилання `+++` та 1000 мс після нього на шині UART мусить утримуватися повна тиша. Спроба передати будь-які байти у межах захисного вікна призведе до сприйняття `+++` як звичайного корисного навантаження. Проте при передачі довільних двійкових даних (стиснутих архівів, зашифрованих пакетів чи образів прошивок) у прозорому режимі виникає ризик фатального хибного спрацьовування. Якщо двійковий масив містить коди `0x2B 0x2B 0x2B` (символи `+++`), а хост-контролер робить вимушені технологічні паузи тривалістю понад 1000 мс до та після цього фрагмента (наприклад, через затримку зчитування з Flash-пам'яті чи обробку переривань), інтерпретатор модулів [ESP-01 (Wi-Fi, ESP8266)](root:cat-hw-boards/esp-01) випадково сприйме байти даних як команду виходу з тунелю. У результаті модуль мимовільно переходить у командний режим, а наступна порція бінарних даних потрапляє в парсер AT-команд, викликаючи відповіді `ERROR` та розрив потоку передачі. Щоб уникнути хибного розпізнавання `+++` при передачі бінарних масивів, хост-програма повинна або запевнити безперервний потік байтів без часових розривів у 1000 мс, або використовувати нормальний режим із вказуванням фіксованої довжини кадру (`AT+CIPMODE=0` та `AT+CIPSEND=<length>`), де аналіз послідовності виходу повністю вимкнено. Якщо ж розрив сесії ініціює віддалений сервер (надсиланням пакетів із прапорами @@en|FIN@@ або @@en|RST@@), модуль автоматично закриває сокет, перериває режим прозорого моста та видає на шину UART текстове сповіщення `CLOSED`, негайно повертаючи інтерпретатор у стандартний стан очікування команд.

```text
// Процедура входження та виходу з прозорого тунелю
AT+CIPMUX=0
OK
AT+CIPMODE=1
OK
AT+CIPSTART="TCP","192.168.1.50",9000
CONNECT
OK
AT+CIPSEND
>
[Потокова передача даних без командного оверхеду...]

[Пауза 1000 мс] -> +++ -> [Пауза 1000 мс]
AT
OK
```

## Структура вхідного потоку +IPD

Отримання мережевих даних від віддалених вузлів відбувається в асинхронному режимі. Стек LwIP формує сповіщення з префіксом `+IPD` (від англ. @@en|IP Data@@ — вхідні IP-дані) і видає його в послідовний порт мережевого модуля.

![Формат асинхронного кадру +IPD із позначенням префікса, ідентифікатора каналу, довжини та межі корисних даних](img/ipd-stream-frame-structure.svg)
_*Структура асинхронного кадру +IPD із розбиттям на префікс, номер сокета link_id, довжину len та корисний вантаж.*_

Формат сповіщення залежить від конфігурації мультиплексора:
- В одиночному режимі (`AT+CIPMUX=0`): `+IPD,<len>:<data>`
- У мультиплексному режимі (`AT+CIPMUX=1`): `+IPD,<link_id>,<len>:<data>`

Поле `<len>` вказує точний обсяг прийнятого блоку в байтах, після якого йде розділова двокрапка `:` та безпосередній масив корисного навантаження `<data>`. Якщо увімкнено вивід розширеної інформації командою `AT+CIPDINFO=1`, заголовок розширюється IP-адресою та портом відправника: `+IPD,<link_id>,<len>,<ip>,<port>:<data>`.

Для стабільного парсингу в хост-контролері слід зчитувати заголовок посимвольно до двокрапки, виділяти значення `<len>`, після чого зчитувати строго вказану кількість байтів у приймальний буфер. Спроба парсити корисний вантаж як текстові стрічки призводить до збоїв при передачі бінарних даних, що описують специфікації [модуля ESP-01](root:cat-hw-boards/esp-01). Якщо ж обсяг кадру `<len>` перевищує розмір оперативного буфера хоста, парсер реалізує порційну обробку через кільцевий буфер (англ. @@en|ring buffer@@ — кільцевий буфер): зберігає значення `<len>` у лічильнику залишку, вичищає байти блоками до заповнення буфера, передає їх цільовому приладу та зменшує лічильник до нуля. Лише після зчитування всіх `<len>` байтів автомат станів хоста відновлює пошук нового префікса `+IPD`, що запобігає переповненню шини UART при прийомі великих TCP-сегментів.

```text
// Приклад 1: Вхідний кадр в одиночному режимі (25 байтів корисних даних)
+IPD,25:Hello from remote server!

// Приклад 2: Вхідний кадр у мультиплексному режимі (сокет 0, 12 байтів)
+IPD,0,12:Data payload
```

## Статусні відповіді та помилки

Усі AT-команди сокетного інтерпретатора повертають текстовий вердикт виконання, який хост-контролер аналізує для керування автоматом станів.

Основні синхронні відповіді інтерпретатора:
- `OK`: команда успішно розпарсена та виконана.
- `ERROR`: синтаксична помилка у команді, некоректні параметри або виконання команди у забороненому режимі (наприклад, спроба виклику `AT+CIPSERVER=1` при `AT+CIPMUX=0`).
- `FAIL`: мережева операція завершилася збоєм (наприклад, віддалений сервер відхилив TCP-з'єднання).
- `ALREADY CONNECTED`: спроба відкрити сокет на вже зайнятому ідентифікаторі `link_id`.

Асинхронні повідомлення про зміну стану сокетів:
- `<link_id>,CONNECT`: віддалений клієнт успішно підключився до локального сервера або встановлено вихідне з'єднання.
- `<link_id>,CLOSED`: сокет закритий за ініціативою віддаленого вузла або через таймаут інактивації `AT+CIPSTO`.
- `SEND OK`: підтвердження успішної передачі кадру за допомогою `AT+CIPSEND`.
- `SEND FAIL`: виникнення помилки при передачі даних (втрата зв'язку чи переповнення буфера).

При отриманні відповідей `ERROR` або `CLOSED` алгоритм хост-контролера повинен переводити автомат станів у фазу повторної ініціалізації, очищати буфери та повторювати спробу відкриття сокета через часовий інтервал затримки у межах 1000–5000 мс (англ. @@en|backoff@@ — затримка повтору). Якщо після 3–5 послідовних спроб підключення інтерпретатор продовжує видавати помилки або не відповідає через вичерпання ресурсів пам'яті стека, хост-контролер ініціює [оновлення прошивки ESP-01](root:cat-hw-boards/esp01-firmware-flashing) або надсилає команду примусового перезавантаження `AT+RST` (або подає низький рівень на вивід RST). Після появи асинхронного повідомлення `ready` хост-програма заново встановлює режими `AT+CIPMUX` та повторює повний цикл конфігурації мережевого середовища.
