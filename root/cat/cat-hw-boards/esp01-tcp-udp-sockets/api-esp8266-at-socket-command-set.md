## Обмеження звичайного UART та мережеві сокети

Послідовний інтерфейс @@en|UART@@ (англ. @@en|UART@@ від @@en|Universal Asynchronous Receiver-Transmitter@@ — універсальний асинхронний приймач-передавач) призначений для передачі безперервного двійкового потоку байтів між двома пристроями. У цьому каналі відсутні вбудовані засоби адресації віддалених вузлів, розбиття даних на мережеві кадри та перевірки доставки. Під час спроби передати мережевий трафік через простий послідовний порт хост-мікроконтролер зіштовхується з проблемою: двійкові дані зливаються в суцільний потік, а розрив зв'язку чи втрата пакета призводять до повного розсинхронізації обміну.

Фірмова прошивка мікроконтролера ESP8266 розв'язує цю проблему шляхом створення програмного інтерфейсу AT-команд, який реалізує абстракцію сокетів (англ. @@en|socket@@ — заглиблення, точка підключення) поверх програмного стека @@en|LwIP@@. Текстові @@en|AT-команди@@ дають змогу керувати з'єднаннями за протоколами @@en|TCP@@ (англ. @@en|TCP@@ від @@en|Transmission Control Protocol@@ — протокол керування передачею) та @@en|UDP@@ (англ. @@en|UDP@@ від @@en|User Datagram Protocol@@ — протокол користувацьких датаграм). Хост-контролер надсилає текстові рядки через послідовний порт модуля [ESP-01](root:cat-hw-boards/esp-01) або [ESP-01S](root:cat-hw-boards/esp-01s), де апаратний контролер @@en|UART@@ приймає байти у внутрішній буфер @@en|FIFO@@ (англ. @@en|FIFO@@ від @@en|First In, First Out@@ — першим прийшов, першим пішов) об'ємом 128 байтів. Обмежений розмір цього буфера безпосередньо впливає на максимальну швидкість обміну: при високих бітрейтах без апаратного контролю потоку прошивка мусить встигати переносити байти з @@en|FIFO@@ у кільцевий буфер (англ. @@en|ring buffer@@) в оперативній пам'яті @@en|RAM@@ до його переповнення, інакше виникає втрата даних. При досягненні межі сегмента @@en|MSS@@ (англ. @@en|MSS@@ від @@en|Maximum Segment Size@@ — максимальний розмір сегмента) або закінченні інтервалу очікування стек пакує цей буфер у мережевий TCP-сегмент із заголовочними полями, виконує повторні спроби відправки й контролює стан каналу.

Завдяки такій архітектурі хост-контролер звільняється від складної обробки протоколів мережевого та транспортного рівнів. Для роботи із сокетами використовується базовий апаратний зв'язок, детально описаний в [огляді SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).

## Конфігурація каналів та режимів мультиплексування

Перед початком створення мережевих з'єднань необхідно налаштувати режим мультиплексування (англ. @@en|multiplexing@@ — поєднання багатьох каналів). Команда `AT+CIPMUX` визначає, скільки паралельних сокетів може обслуговувати модуль одночасно.

Запит `AT+CIPMUX=<mode>` приймає один із двох параметрів:
* `0` — одноканальний режим (англ. @@en|single connection mode@@), у якому модуль може відкрити лише один сокет;
* `1` — багатоканальний режим (англ. @@en|multiple connections mode@@), що дозволяє відкривати до п'яти паралельних з'єднань із числовими ідентифікаторами `link_id` від 0 до 4.

Режим передачі даних конфігурується командою `AT+CIPMODE=<mode>`:
* `0` — звичайний режим (англ. @@en|normal mode@@), де перед кожною відправкою надсилається команда `AT+CIPSEND`, а вхідні дані отримуються з префіксом `+IPD`;
* `1` — прозорий режим (англ. @@en|transparent passthrough mode@@), у якому лінія UART перетворюється на прямий мост із сокетом без використання AT-префіксів.

Зміна режиму `AT+CIPMUX` дозволена лише тоді, коли всі сокети закриті й локальний сервер зупинений. Якщо спробувати виконати команду конфігурації `AT+CIPMUX` за наявності активних з'єднань, прошивка не здійснює автоматичного скидання сокетів, а відхиляє запит помилкою `ERROR` (або `link is builded`), захищаючи цілісність поточного мережевого контексту від раптового розриву. Хост-програма зобов'язана попередньо примусово закрити всі канали командою `AT+CIPCLOSE` або виконати скидання стека, і лише після цього змінювати режим мультиплексування. Увімкнення прозорого режиму `AT+CIPMODE=1` можливе виключно в одноканальному режимі `AT+CIPMUX=0` при встановленому TCP-клієнтському з'єднанні. Якщо спробувати активувати `AT+CIPMODE=1` під час відкритого сокета @@en|UDP@@ (англ. @@en|UDP@@ від @@en|User Datagram Protocol@@), прошивка повертає помилку `ERROR`, оскільки безперервний двійковий потік UART вимагає чітко визначеного єдиного адресата. Для роботи прозорого режиму через @@en|UDP@@ сокет повинен бути попередньо ініціалізований командою `AT+CIPSTART` із фіксованою віддаленою IP-адресою та портом призначення (параметр відправки `2`), інакше модуль блокує перехід у режим прямого мосту для запобігання втраті меж датаграм.

## Встановлення з'єднань та відправка даних

Для відкриття сокета використовується команда `AT+CIPSTART`. У багатоканальному режимі передається ідентифікатор каналу `link_id`, тип протоколу, IP-адреса та номер порту:

`AT+CIPSTART=<link_id>,"<type>","<ip_address>",<port>`

У разі успішного з'єднання модуль повертає рядок `CONNECT` та підтвердження `OK`.

Відправка даних у звичайному режимі відбувається в два етапи. Спочатку надсилається команда `AT+CIPSEND=<link_id>,<length>`, де `length` вказує кількість байтів (максимум 2048 байтів за один кадр). Модуль відповідає символом готовності `>` (символ заглавного вводу), після чого хост-контролер надсилає сирий масив байтів. Якщо хост-мікроконтролер затримує передачу або передає менше байтів, ніж було заявлено у параметрі `length`, прошивка очікує закінчення внутрішнього тайм-ауту прийому (англ. @@en|UART receive timeout@@ — тайм-аут прийому послідовного порту). Після вичерпання цього ліміту модуль скасовує формування мережевого сегмента, повертає помилку `ERROR` або `SEND FAIL` та повертає командний інтерпретатор у стандартний стан очікування AT-запитів.

![Часова діаграма обміну AT-командами для відкриття сокету, надсилання даних і прийому підтвердження](img/esp8266-at-socket-data-flow.svg)
*Послідовність команд AT+CIPSTART та AT+CIPSEND із реакцією модуля ESP8266 у відповідь на передачу даних хост-контролером.*

Після успішної передачі пакета в мережу модуль повертає статус `SEND OK`. Для закриття активного сокета використовується команда `AT+CIPCLOSE=<link_id>`. Під час ініціалізації сокета командою `AT+CIPSTART` хост-мікроконтролер зобов'язаний послідовно обробляти дворядкову відповідь модуля: спочатку приходить асинхронний рядок `<link_id>,CONNECT` (або `CONNECT` у режимі `AT+CIPMUX=0`), після чого виводиться статусне підтвердження `OK`. Парсер хоста має фіксувати факт відкриття каналу за повідомленням `CONNECT`, але вважати з'єднання остаточно готовим до відправки даних лише після отримання фінального `OK`. Якщо ж замість підтвердження виводиться `CONNECT FAIL` або `CLOSED` з наступним `ERROR`, сокет вважається невідкритим, і програма має переходити до процедури повторної спроби.

## Прийом асинхронних кадрів та створення сервера

Коли віддалений вузол надсилає дані на сокет ESP8266, прошивка виводить через UART асинхронне сповіщення `+IPD`. Формат цього кадру залежить від налаштованого режиму мультиплексування.

![Схема розбору структури асинхронного кадру +IPD у багатоканальному режимі](img/esp8266-ipd-frame-parsing-structure.svg)
*Структура префікса кадру +IPD із виділенням ідентифікатора сокета link_id, довжини корисного навантаження len та баферного масиву даних.*

У багатоканальному режимі кадр має префікс `+IPD,<link_id>,<len>:<data>`, де `len` визначає кількість байтів корисного навантаження після двоеточія. Хост-мікроконтролер повинен зчитати з UART вказану кількість байтів `len`, перш ніж повертатися до розбору AT-команд. Якщо віддалені вузли надсилають пакети високою щільністю з кількох сокетів одночасно, прошивка виводить декілька кадрів `+IPD` поспіль без проміжних статусних відповідей. У разі надходження наступного заголовочного кадру під час обробки поточного масиву парсер зобов'язаний точково зчитати з послідовного порту рівно `len` байтів корисного навантаження, після чого негайно відновити пошук нових префіксів, інакше наступне сповіщення `+IPD` буде злито з двійковими даними попереднього кадру.

Модуль ESP8266 може працювати в режимі TCP-сервера. Команда `AT+CIPSERVER=<mode>[,<port>]` приймає `mode=1` для запуску сервера та `mode=0` для його зупинки. За замовчуванням використовується порт 333. Створення сервера вимагає попереднього ввімкнення багатоканального режиму `AT+CIPMUX=1`.

Для керування тривалістю неактивних клієнтських сесій використовується команда `AT+CIPSTO=<time>`, яка задає тайм-аут у секундах (від 0 до 7200). Якщо клієнт не надсилає даних протягом цього часу, модуль автоматично закриває сокет. При цьому відкритий локальний TCP-сервер зберігає автозакріплення за вказаним портом незалежно від динамічної зміни IP-адреси модуля (наприклад, при повторному отриманні адреси через @@en|DHCP@@ після перепідключення Wi-Fi). Оскільки серверний стек прив'язується до локального порту на всіх мережевих інтерфейсах, зовнішні клієнти можуть одразу підключатися за новою IP-адресою без необхідності повторного виклику `AT+CIPSERVER=1`, доки сервер не буде примусово зупинений командою `AT+CIPSERVER=0`.

## Обробка тайм-аутів та мережевих помилок

Під час роботи з AT-сокетами хост-програма повинна обробляти специфічні коди відповідей та мережеві збої. Якщо модуль зайнятий обробкою попереднього запиту, він повертає рядок `BUSY p...` або `BUSY s...`, під час якого нові AT-команди надсилати заборонено.

При розриві зв'язку з ініціативи віддаленого вузла прошивка виводить асинхронне повідомлення `<link_id>,CLOSED` або `UNLINK`. Якщо команда `AT+CIPSEND` завершується статусом `SEND FAIL` або не повертає `SEND OK` протягом визначеного тайм-ауту, хост-контролер повинен примусово закрити сокет командою `AT+CIPCLOSE` та повторити спробу підключення. Для запобігання переповненню вхідного кільцевого буфера під час інтенсивного прийому даних слід застосовувати апаратний контроль потоку (англ. @@en|hardware flow control@@) за допомогою ліній @@en|CTS@@ (англ. @@en|CTS@@ від @@en|Clear To Send@@ — готовий до відправки) та @@en|RTS@@ (англ. @@en|RTS@@ від @@en|Request To Send@@ — запит на відправку). При наближенні буфера приймача до межі переповнення лінія @@en|RTS@@ тимчасово призупиняє передачу байтів на фізичному рівні @@en|UART@@, гарантуючи збереження цілісності двійкового масиву без втрати байтів.

Для надійної роботи парсер UART хост-мікроконтролера повинен реалізовувати автомат станів (англ. @@en|state machine@@). Він відокремлює службові текстові відповіді від двійкового масиву даних після двоеточія у сповіщенні `+IPD`, запобігаючи помилковому розпізнаванню символів `OK` чи `ERROR` у тілі мережевого пакета. При виникненні критичних помилок або зависанні буфера послідовного порту рекомендується виконати програмне скидання модуля командою `AT+RST`.
