## Проблема конфігурації шин пам'яті та USB

Невідповідність програмної конфігурації прошивки справжньому апаратному оснащенню мікросхеми призводить до того, що пристрій зациклюється в постійних циклічних перезавантаженнях або взагалі втрачає можливість зв'язку через послідовний порт. На етапі завантаження системи первинний завантажувач фреймворку @@en|ESP-IDF@@ (від англ. *@@en|Espressif IoT Development Framework@@* — середовище розробки Espressif) зчитує бінарний заголовок та конфігураційний файл `sdkconfig`. Якщо у файлі обрано восьмилінійну шину пам'яті, а на платі встановлено модуль з чотирилінійною пам'яттю, або якщо вивід консольного логування спрямовано у фізичний @@en|UART@@ замість вбудованого контролера USB, мікроконтролер стає «цеглиною» без жодних повідомлень про помилку. Причиною такого безмовного зависання є апаратний механізм обробки паніки (англ. @@en|panic handler@@): при виникненні апаратного винятку завантажувач намагається провайдерити зліпок регістрів процесора у сконфігурований канал виводу. Якщо цей канал спрямований на фізичний @@en|UART@@, до якого не підключено перетворювач рівнів, або на непроініціалізований USB-контролер, обробник паніки нескінченно блокується на спробах витіснення буфера логування, спричиняючи спрацьовування сторожового таймера @@en|RTC Watchdog@@ та циклічне перезавантаження чипа.

У сучасних платах розробки, таких як [мікроконтролер ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller), зовнішня флеш-пам'ять та псевдостатична оперативна пам'ять @@en|PSRAM@@ (від англ. *@@en|Pseudo Static Random Access Memory@@*) підключаються через високошвидкісні шини. На відміну від давніших родин чипів, де конфігурація шини була фіксованою, ESP32-S3 підтримує як чотирилінійний режим @@en|Quad SPI@@, так і восьмилінійний @@en|Octal SPI@@ з тактовими частотами від 40 до 120 МГц. Крім того, нативні виводи `GPIO19` та `GPIO20` можуть працювати як апаратний порт @@en|USB-CDC@@ (від англ. *@@en|Communication Device Class@@*) або мост налагодження @@en|USB-JTAG@@ (від англ. *@@en|Joint Test Action Group@@*). Відмінності між цими режимами виходять далеко за межі розрядності даних: шина @@en|Quad SPI@@ використовує 4 лінії даних із можливістю гнучкого перенаправлення сигналів, тоді як @@en|Octal SPI@@ задіює 8 ліній даних плюс сигнали стробування `DQS` та тактування, вимагаючи апаратного обходу мультиплексора виводів @@en|IO MUX@@ (від англ. *@@en|Input/Output Multiplexer@@*). При високих частотах обміну в режимі @@en|DDR@@ (від англ. *@@en|Double Data Rate@@*) це накладає суворі вимоги до схемотехніки друкованої плати — усі траси восьми бітів та сигналів тактування мусять мати однакову фізичну довжину для вирівнювання фазових затримок, а виводи від `GPIO33` до `GPIO37` повністю блокуються для стороннього використання. Щоб система працювала стабільно, розробник мусить чітко узгодити параметри системи конфігурації @@en|Kconfig@@ (від англ. *@@en|Kernel Configuration System@@*) із топологією конкретної плати, зокрема для [модулів Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare) чи [компактних плат ESP32-S3-Zero](root:cat-hw-boards/esp32-s3-zero).

## Налаштування режимів Flash та PSRAM у menuconfig

Перехід від вибору типу пам'яті до її безпосередньої конфігурації здійснюється через утиліту `menuconfig` або прямою вказівкою прапорів у файлі `sdkconfig`. Для налаштування підсистеми зовнішньої пам'яті у меню `Component config ---> SPI Flash driver` та `ESP32S3-Specific` визначаються ключові макроси: `CONFIG_FLASHMODE_QUAD`, `CONFIG_FLASHMODE_OCT`, `CONFIG_SPIRAM_MODE_QUAD` або `CONFIG_SPIRAM_MODE_OCT`.

При виборі восьмилінійного режиму @@en|Octal SPI@@ контролер зовнішньої пам'яті здійснює обмін даними через виводи `GPIO33`–`GPIO37`, а апаратний блок управління пам'яттю @@en|MMU@@ (від англ. *@@en|Memory Management Unit@@*) відображає фізичні сторінки у віртуальний адресний простір. Ці виводи підключаються напряму через обхідний тракт мультиплексора виводів @@en|IO MUX@@ (від англ. *@@en|Input/Output Multiplexer@@*), минаючи внутрішню матрицю @@en|GPIO Matrix@@ для досягнення мінімальної затримки. Якщо у `sdkconfig` помилково ввімкнути режим `Octal SPI` для плати з `Quad SPI`, апаратні лінії вибору чипа й тактування розсинхронізуються, що викличе критичну помилку кешу при спробі зчитати першу ж інструкцію. Більше того, при розгоні шини Octal SPI до частоти 120 МГц вкрай критичним стає механізм фазового підстроювання тактування (англ. @@en|timing tuning@@). На такій частоті період тактового сигналу становить лише 8.33 нс, тому завантажувач використовує вбудовану затримкову лінію контролера SPI для калібрування фазового зсуву сигналу стробування `DQS`: під час старт-апу система зчитує тестовий паттерн, визначає часове «вікно даних» та фіксує оптимальну затримку вибірки. Без апаратного фазового підстроювання найдрібніша розбіжність затримок призводить до зчитування викривлених бітів та фатального збою роботи кешу.

Частота шини замовчуванням становить 80 МГц у режимі @@en|SDR@@ (від англ. *@@en|Single Data Rate@@*) або @@en|DDR@@ (від англ. *@@en|Double Data Rate@@*). Спроба підвищити частоту до 120 МГц вимагає обов'язкового ввімкнення розгортання фазового зсуву тактового сигналу та підтримки з боку кристала пам'яті. У разі неспівпадіння параметрів система падає у перезавантаження на етапі роботи завантажувача.

## Інтеграція PSRAM у менеджер пам'яті ESP-IDF

Після ініціалізації фізичної шини постає завдання ефективного використання обсягу @@en|PSRAM@@ в застосунку. Менеджер пам'яті фреймворку @@en|ESP-IDF@@ дозволяє інтегрувати зовнішню пам'ять у системне купу (англ. @@en|heap allocator@@) через опцію `CONFIG_SPIRAM_USE`. Існує три основні стратегії інтеграції: виділення пам'яті виключно за явним запитом, автоматичне перенаправлення великих блоків у @@en|PSRAM@@ та повна інтеграція у загальний пул.

При виборі режимів `CONFIG_SPIRAM_USE_CAPS_ALLOC` або `CONFIG_SPIRAM_USE_MALLOC`, виділення здійснюється за допомогою спеціалізованих функцій API виділення пам'яті:

Усі запити `malloc()`, обсяг яких перевищує цей поріг, автоматично задовольняються з @@en|PSRAM@@, зберігаючи швидку внутрішню статичну оперативну пам'ять @@en|SRAM@@ для системних стеків завдань та переривань. Поряд із динамічним виділенням слід враховувати апаратні обмеження зовнішньої пам'яті: покажчики у @@en|PSRAM@@ вимагають обов'язкового 4-байтового вирівнювання адрес, а периферійні контролери прямого доступу до пам'яті @@en|DMA@@ (від англ. *@@en|Direct Memory Access@@*) не здатні безпосередньо зчитувати дані з зовнішньої шини через кеш-ізоляцію. Для транзакцій периферії (наприклад, периферійних шин @@en|SPI@@ чи мережевих периферійних буферів) фреймворк вимушений проміжно копіювати дані між @@en|PSRAM@@ та внутрішньою пам'яттю @@en|SRAM@@ через проміжні буфери відскоку (англ. @@en|bounce buffer@@), що спричиняє додаткові витрати процесорного часу при інтенсивному обміні.

## Конфігурація нативного інтерфейсу USB-CDC та USB-JTAG

Паралельно з налаштуванням шини пам'яті, ESP32-S3 надає гнучкі можливості конфігурації вбудованого контролера USB. Нативні лінії `GPIO19` (`USB_D-`) та `GPIO20` (`USB_D+`) можуть функціонувати у двох основних режимах: вбудований пристроєвий контролер USB-Serial/JTAG або повноцінний контролер @@en|USB-OTG@@ (від англ. *@@en|On-The-Go@@*).

![Діаграма потоку конфігурації вбудованого USB-контролера, що демонструє вибір між нативним USB-CDC/JTAG та зовнішнім USB-OTG PHY.](img/esp32s3-usb-cdc-jtag-config-flow.svg)
*Схема перемикання режимів нативного USB між USB-CDC/JTAG та USB-OTG в залежності від прапорів sdkconfig.*

Для виводу логів та консольного налагодження у `menuconfig` обирають опцію `Component config ---> ESP System Settings ---> Channel for console output`. Перемикання на `USB Serial/JTAG Controller` вмикає віртуальний послідовний порт @@en|USB-CDC@@ без потреби у зовнішніх мікросхемах типу CP2102 чи CH340, якими обладнані класичні плати типу [ESP32-CAM](root:cat-hw-boards/esp32-cam). При цьому режим `USB-JTAG` дозволяє проводити апаратне покрокове налагодження через `openocd` без зовнішнього програмного адаптера. Якщо ж застосунок вимагає реалізації USB-хоста або нестандартних пристроїв (@@en|HID@@, @@en|MSC@@), конфігурацію перемикають на драйвер `USB-OTG`, який використовує власну стек-бібліотеку `tinyusb`. Апаратне перемикання між цими контролерами відбувається на рівні внутрішнього трансивера фізичного рівня @@en|USB-PHY@@ (від англ. *@@en|Physical Layer Controller@@*): вбудований трансивер підключається безпосередньо до виводів `GPIO19` та `GPIO20`, але в один момент часу може обслуговувати лише один блок. Якщо у `sdkconfig` ввімкнути повноцінний пристроєвий режим `USB-OTG` з внутрішнім PHY, апаратний блок `USB Serial/JTAG` відключається від виводів, а для використання зовнішнього High-Speed PHY (через інтерфейс @@en|ULPI@@) периферію `USB-OTG` перенаправляють через матрицю виводів на зовнішню мікросхему трансивера.

## Діагностика збоїв ініціалізації та конфліктів шини

Некоректна конфігурація `sdkconfig` проявляється під час первинного завантаження системи специфічними помилками завантажувача (англ. @@en|bootloader@@). Найпоширенішим збоєм є помилка `Cache Error: Core paniced`, яка виникає під час спроби процесора виконати інструкцію з адреси у зовнішній пам'яті, коли шина @@en|Octal SPI@@ або кеш не ініціалізовані.

Інший критичний випадок — `Flash read err, 1000` або `CRC Error`. Це свідчить про перевищення максимально припустимої частоти шини (наприклад, 120 МГц замість 80 МГц) або про порушення фазового зсуву тактування. При роботі з Octal PSRAM також поширений конфлікт виводів: якщо застосунок спробує ініціалізувати `GPIO33` як звичайний дискретний вихід або шину @@en|I2C@@, апаратний обхідний тракт шини пам'яті миттєво блокує процесорне ядро. На низькому рівні помилка `CRC Error` є висновком механізму контролю цілісності: первинний завантажувач зчитує бінарний заголовок кожної секції прошивки та розраховує підсумкову контрольну суму @@en|CRC32@@ (від англ. *@@en|Cyclic Redundancy Check 32-bit@@* — циклічний надлишковий код), порівнюючи її із записаним еталоном. У разі неспівпадіння через неякісний запис або спотворення бітів на високій частоті завантаження зупиняється; якщо в прошивці ввімкнено механізм відкату @@en|OTA rollback@@ (від англ. *@@en|Over-The-Air rollback@@* — бездротовий відкат), завантажувач автоматично перемикається на резервний затінений розділ пам'яті, а при пошкодженні сам чип переводять у режим завантаження ROM (шляхом замикання `GPIO0` на землю) для повторного прошивання. Ретельна перевірка файлу `sdkconfig` та логів первинного завантаження через консольний порт USB є основними інструментами діагностики таких конфліктів.
