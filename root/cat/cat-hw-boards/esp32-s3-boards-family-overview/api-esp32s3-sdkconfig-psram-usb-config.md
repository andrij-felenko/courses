## Призначення sdkconfig та нативна периферія ESP32-S3

При розробці прошивок у середовищі фреймворку ESP-IDF (англ. @@en|Espressif IoT Development Framework@@) головним інструментом керування апаратною конфігурацією є файл `sdkconfig`. Цей файл генерується з макета за замовчуванням `sdkconfig.defaults` або створюється інтерактивною утилітою `menuconfig` і містить макровизначення препроцесора `CONFIG_*`, які визначають спосіб ініціалізації периферійних модулів та підсистеми пам'яті під час завантаження ядра.

Сучасний [мікроконтролер ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) оснащений вбудованими вузлами, якими не володіли чипи попередніх поколінь: контролером розширеної псевдостатичної пам'яті (англ. @@en|Pseudo-Static RAM@@, @@en|PSRAM@@) з підтримкою 8-бітної шини Octal SPI та нативним периферійним блоком USB CDC/JTAG. Якщо прошивка компілюється зі стандартним конфігураційним файлом без спеціальних прапорців, ядро ініціалізує лише внутрішню пам'ять (512 кБ SRAM), а спроба виділення великих масивів викликає збій адресації. Подібно до цього, виведення системних логів за замовчуванням спрямовується на виводи UART0, через що консоль на пристроях без зовнішнього моста USB-UART залишається глухою. Під час збірки проєкту система Kconfig трансформує параметри `sdkconfig` у згенерований заголовковий файл `build/config/sdkconfig.h`. Цей файл містить прямі макроси препроцесора виду `#define CONFIG_SPIRAM_SUPPORT 1` та `#define CONFIG_ESP_CONSOLE_USB_CDC 1`, які керують умовною компіляцією драйверів ядра та системних компонентів фреймворку.

Налаштування `sdkconfig` дає змогу розробникові на рівні компіляції вказати точні апаратні параметри конкретної плати, активувати автоматичне монтування PSRAM у загальний простір адресації та переспрямувати виведення консолі на внутрішній контролер USB.

При первинному збиранні проєкту система збірки обробляє базовий конфігураційний шаблон `sdkconfig.defaults` та його цільові розширення вида `sdkconfig.defaults.esp32s3`. Визначені у цих файлах ключі автоматично копіюються у підсумковий файл `sdkconfig`, який стає єдиним джерелом конфігурації для системи Kconfig. Якщо файл `sdkconfig` вже існує, ручні зміни параметрів через утиліту `menuconfig` мають вищий пріоритет і не перезаписуються базовим шаблоном при повторних збірках. Для повного скидання робочих конфігурацій до версійних параметрів проєкту розробник видаляє локальний `sdkconfig`, примушуючи систему збірки повторно згенерити його з шаблонів `sdkconfig.defaults`.

## Конфігурація PSRAM, Quad SPI та Octal SPI

Підключення зовнішньої пам'яті PSRAM до кристала виконується за допомогою послідовного периферійного інтерфейсу (англ. @@en|Serial Peripheral Interface@@, @@en|SPI@@) у двох физичних режимних конфігураціях: 4-бітній Quad SPI (англ. @@en|QSPI@@) або 8-бітній Octal SPI (англ. @@en|OPI@@, від англ. @@en|Octal Peripheral Interface@@).

![Схема порівняння ліній даних та фаз тактування шин Quad SPI та Octal SPI PSRAM, що ілюструє різницю у пропускній здатності та розводці](img/esp32s3-psram-qspi-opi-bus-modes.svg)
*Схема порівняння ліній даних та фаз тактування шин Quad SPI та Octal SPI PSRAM.*

Для увімкнення підтримки зовнішньої пам'яті у файлі `sdkconfig` додають ключ `CONFIG_SPIRAM=y`. Вибір типу шини визначається параметром режимів `CONFIG_SPIRAM_MODE`:

```kconfig
# Увімкнення підтримки зовнішньої PSRAM
CONFIG_SPIRAM=y
CONFIG_SPIRAM_TYPE_AUTO=y

# Режим 8-бітної шини Octal SPI (OPI DDR 80 МГц)
CONFIG_SPIRAM_MODE_OCT=y
CONFIG_SPIRAM_SPEED_80M=y
```

Якщо на платі встановлено модуль з 4-бітною пам'яттю, замість Octal SPI обирають параметр `CONFIG_SPIRAM_MODE_QUAD=y`. Прикладом плати з 8-бітною шиною пам'яті є [Waveshare ESP32-S3R2 з Octal PSRAM](root:cat-hw-boards/esp32-s3r2-waveshare), де використання `CONFIG_SPIRAM_MODE_OCT=y` на частоті 80 МГц забезпечує пропускну здатність до 160 МБ/с. Для виконання об'ємного коду безпосередньо з зовнішнього масиву використовують параметр `CONFIG_SPIRAM_FETCH_INSTRUCTIONS=y`, який дозволяє шині та MMU завантажувати інструкції процесора безпосередньо з PSRAM. Це вивільняє внутрішню Flash-пам'ять і SRAM під обчислювальні буфери, однак підвищує затримки вибірки інструкцій при промахах кешу, тому критичні до часу виконання обробники переривань все одно необхідно позначати атрибутом `IRAM_ATTR`. Крім виконання коду, зовнішню пам'ять задіюють для розвантаження мережевого стека за допомогою ключа `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`. Цей параметр дозволяє драйверу Wi-Fi та мережевому стеку (англ. @@en|LwIP@@) виділяти буфери прийому й передачі пакетів у PSRAM при вичерпанні вбудованого масиву SRAM. Таке перенаправлення зберігає внутрішню оперативну пам'ять під задачі реального часу, хоча й дещо збільшує накладні витрати CPU на обробку кожного мережевого кадру.

Критичним параметром є узгодження фази тактового сигналу шини. На частоті 80 МГц невідповідність параметрів вирівнювання затримки тактування (англ. @@en|clock sampling delay@@) призводить до зсуву бітів та спотворення даних при читанні сторінок пам'яті. Прапорець `CONFIG_SPIRAM_SPEED_80M=y` автоматично вмикає алгоритм динамічного калібрування фази при старті системи.

## Параметри L1-кешу та розподіл пам'яті через heap_caps

Зовнішня PSRAM підключається через блок керування пам'яттю (англ. @@en|Memory Management Unit@@, @@en|MMU@@) і кешується кеш-пам'яттю першого рівня (англ. @@en|L1 cache@@, @@en|L1-кеш@@). Розмір кешу даних регулюється в `sdkconfig` за допомогою параметрів `CONFIG_ESP32S3_DATA_CACHE_16KB`, `32KB` або `64KB`. Збільшення розміру кешу до 64 кБ суттєво зменшує затримки при повторному доступі до кадрових буферів.

Для виділення оперативної пам'яті у зовнішньому масиві PSRAM стандартний виклик `malloc()` не завжди підходить, оскільки за замовчуванням динамічна купа (англ. @@en|heap@@) використовує внутрішню SRAM. Для явного виділення пам'яті з PSRAM використовують API фреймворку `heap_caps_malloc()` із прапорцем `MALLOC_CAP_SPIRAM`.

Якщо виділення пам'яті через `heap_caps_malloc` повертає `NULL`, перевірте, чи активовано параметри `CONFIG_SPIRAM_USE_MALLOC` або `CONFIG_SPIRAM_USE_CAPS_ALLOC` у файлі `sdkconfig`. Прапорчик `MALLOC_CAP_SPIRAM` примусово виділяє блок у зовнішній пам'яті, тоді як `MALLOC_CAP_DEFAULT` за замовчуванням використовує лише швидку внутрішню оперативну пам'ять (англ. @@en|SRAM@@). При виборі конфігурації `CONFIG_SPIRAM_USE_MALLOC` система автоматично об'єднує пули й спрямовує запити з `MALLOC_CAP_DEFAULT` у PSRAM при перевищенні заданого порогу обсягу. Натомість параметр `CONFIG_SPIRAM_USE_CAPS_ALLOC` виключає PSRAM із загального пулу `MALLOC_CAP_DEFAULT`, залишаючи її доступною виключно за прапорцем `MALLOC_CAP_SPIRAM`. Явне вказування `MALLOC_CAP_SPIRAM` захищає від обмежень внутрішньої SRAM і гарантує розміщення великих буферів у зовнішньому масиві.

## Конфігурування нативного USB CDC та JTAG контролера

Мікроконтролер ESP32-S3 містить вбудований апаратний вузол USB CDC/JTAG, який підключається безпосередньо до фізичних виводів `GPIO19` (D-) та `GPIO20` (D+). Це позбавляє потреби використовувати зовнішні чіпи мостів USB-UART (`CP2102` або `CH340`).

![Структурна схема вбудованого контролера USB CDC/JTAG у складі ESP32-S3, що показує зв'язок між апаратною консоллю, JTAG-відлагоджувачем та інтерфейсом USB](img/esp32s3-usb-cdc-jtag-architecture.svg)
*Структурна схема вбудованого контролера USB CDC/JTAG у складі ESP32-S3.*

Щоб переспрямувати системну консоль логування `ESP_LOG` на вбудований порт USB CDC, у файлі `sdkconfig` вказують параметри консолі:

```kconfig
# Використання нативного USB CDC для виведення логів
CONFIG_ESP_CONSOLE_USB_CDC=y
CONFIG_ESP_CONSOLE_SECONDARY_NONE=y
CONFIG_ESP_CONSOLE_USB_CDC_SUPPORT_ETS_PRINTF=y
```

Компактні розробницькі платформи на кшталт [ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini) або [ESP32-S3-Zero з Type-C](root:cat-hw-boards/esp32-s3-zero) виводять лінійки USB прямо на роз'єм Type-C. При використанні ключів `CONFIG_ESP_CONSOLE_USB_CDC=y` консоль з'являється у системі як віртуальний послідовний COM-порт одразу після підключення кабелю. Для запобігання втраті перших повідомлень під час перезавантаження пристрою використовують ключ `CONFIG_ESP_CONSOLE_USB_CDC_BEFORE_BOOT=y`. Цей параметр змушує завантажувач ядра затримувати запуск програми до моменту повторного встановлення з'єднання з хостом через USB. Завдяки цьому розробник бачить повний дамп ініціалізації периферії, хоча при автономному живленні платформи від акумулятора це викликає фіксовану затримку старту.

Крім того, вбудований контролер реалізує протокол JTAG безпосередньо через інтерфейс USB. Це дає змогу виконувати покрокове апаратне налагодження (англ. @@en|hardware debugging@@) прошивки у середовищі GDB без підключення додаткових відлагоджувачів JTAG. На відміну від класичного UART, зміна віртуальної швидкості передавання (англ. *baud rate*; @@en|бодрейт@@) у терміналі не обмежує пропускну здатність. Шина USB CDC завжди передає логи пакетами Full-Speed на швидкості до 12 Мбіт/с. Для керування перезавантаженням контролер обробляє лінії готовності термінала (англ. *Data Terminal Ready*; @@en|сигнал DTR@@) та запиту на відправлення (англ. *Request to Send*; @@en|сигнал RTS@@). Перепади рівнів на цих лініях викликають внутрішнє переривання для скидання ядра чи переходу в режим прошивання ROM без зовнішньої транзисторної обв'язки. Блокування або відсутність підтвердження @@en|сигнал DTR@@ терміналом зупиняє виведення логів через вичерпання буфера CDC.

## Діагностика паніки ядра та крайових збоїв адресації

При роботі з розширеною пам'яттю та периферійними шинами найпоширенішими причинами паніки ядра (англ. @@en|kernel panic@@) є некоректне вирівнювання адрес і переповнення вбудованого масиву SRAM при спробі виділення пам'яті під DMA-передачі.

Контролер DMA в ESP32-S3 не може читати чи писати безпосередньо у зовнішній масив PSRAM у деяких режимах або вимагає суворого вирівнювання буфера по межі 32 байти. Якщо передати в буфер камери або Wi-Fi вказівник на PSRAM без прапорця `MALLOC_CAP_DMA`, виникає виняткова ситуація розриву адресації (англ. @@en|LoadStoreAlignment Cause@@).

Для перехоплення та діагностики помилок у `sdkconfig` налаштовують обробник паніки ядра (англ. @@en|panic handler@@):

```kconfig
# Налаштування обробника системної паніки ядра
CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y
CONFIG_ESP_SYSTEM_ENABLE_BACKTRACE=y
CONFIG_ESP_SYSTEM_CHECK_INT_LEVEL_5=y
```

При виникненні збою система виводить у консоль USB CDC трасування викликів (англ. @@en|backtrace@@). Використання утиліти `idf.py monitor` автоматично декодує адреси стека у номери рядків вихідного коду C/C++, даючи змогу швидко локалізувати джерело збою. Інструмент виконує таке перетворення через крос-компіляторну утиліту (від англ. *Address to Line*; @@en|addr2line@@), зіставляючи шістнадцяткові адреси з таблицею символів файлу ELF. Для аналізу збереженого текстового лога дамп декодують у консолі командою `xtensa-esp32s3-elf-addr2line -pfiaC -e build/app.elf <адреса_зі_стека>`, де параметр `-e` вказує на зкомпільований файл прошивки. Завдяки цьому розробник отримує точний файл, назву функції та номер рядка коду, на якому виникла помилка вирівнювання чи переповнення пам'яті.
