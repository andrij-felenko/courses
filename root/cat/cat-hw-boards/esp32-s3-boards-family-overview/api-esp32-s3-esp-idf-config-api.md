## Системні виклики та конфігурування sdkconfig

Під час розробки прошивок для плати на базі мікроконтролера розробник стикається з потребою жорсткого узгодження системного програмного середовища з фізичною конфігурацією кристала. Нерозпізнаний обсяг зовнішньої пам'яті, занижена частота процесора або неправильний режим тактування шини призводят до критичних помилок перезавантаження @@en|panic@@ під час виконання програми. У фреймворку @@en|ESP-IDF@@ (англ. @@en|Espressif IoT Development Framework@@) централізованим інструментом адаптації операційної системи до заліза є конфігураційний файл `sdkconfig`, який генерується системою @@en|Kconfig@@ (від англ. @@en|kernel configuration@@ — конфігурація ядра).

Файл `sdkconfig` визначає препроцесорні макроси, які керують компіляцією ядра @@en|FreeRTOS@@ та драйверів периферії. Базове налаштування починається з вибору тактової частоти ядра `CONFIG_ESP32S3_DEFAULT_CPU_FREQ_240`, яка встановлює максимальну продуктивність двоядерного процесора 240 МГц для високонавантажених задач. Коректна робота з периферією вимагає також узгодження частоти системного тика `CONFIG_FREERTOS_HZ` (зазвичай 1000 Гц), що задає квантування часу для планувальника задач. Наявний опис про [мікроконтролер ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) показує, що без увімкнення відповідних прапорців у `sdkconfig` системи аналізу пам'яті не бачать апаратних блоків прискорення.

Для перевірки стеку конфігурації у вихідному коді використовуються макроси умовного захисту компіляції та системні функції зчитування параметрів тактування.

Під час збірки проєкту система компіляції автоматично обробляє `sdkconfig` і ґенерує заголовочний файл `sdkconfig.h`, який містить препроцесорні визначення з префіксом `CONFIG_`. Механізм цієї ґенерації виконується внутрішньою утилітою `kconfgen`, яка сканує дерева файлів `Kconfig` з усіх підключених компонентів фреймворку та зчитує початкові значення з `sdkconfig.defaults`. Системні пріоритети працюють послідовно: базові дефолтні значення з `sdkconfig.defaults` накладаються на дерево залежностей `Kconfig`, а інтерактивний інструмент `menuconfig` (викликається командою `idf.py menuconfig`) дозволяє розробникові візуально налаштовувати системні опції @@en|Kconfig@@ та перезаписувати підсумкові параметри в файл `sdkconfig`. Далі утиліта трансформує типи даних з `Kconfig` у відповідні конструкції мови C: булеві прапорці перетворюються на макроси виду `#define CONFIG_SPIRAM 1` у разі активації або лишаються незафіксованими `#undef` при вимкненні, тоді як числові та рядкові значення розгортаються в константи, такі як `#define CONFIG_ESP32S3_DEFAULT_CPU_FREQ_MHZ 240`. У коді на C/C++ використання цих заголовочних прапорців спирається на макроперевірки `#if defined(CONFIG_...)` або `#if CONFIG_...` для виключення невикористовуваних модулів із бінарного файлу ще на етапі препроцесингу. При розробці сучасною мовою C++17 макроси із `sdkconfig.h` огортають у статичні константи `constexpr`, що дозволяє застосовувати конструкцію `if constexpr` для умовного виділення обчислювальних ресурсів під конкретні модифікації плат на кшталт [Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare) без додаткових витрат часу на перевірки у циклі виконання.

## Керування PSRAM у QSPI та OSPI

Організація оперативної пам'яті у системах із високим споживанням ресурсів вимагає використання зовнішньої псевдостатичної пам'яті @@en|PSRAM@@ (англ. @@en|Pseudo Static Random Access Memory@@). Мікроконтролер підтримує два режими фізичного підключення зовнішньої пам'яті: чотирилінійний @@en|QSPI@@ (англ. @@en|Quad Serial Peripheral Interface@@) та восьмилінійний @@en|OSPI@@ (англ. @@en|Octal Serial Peripheral Interface@@). Режим @@en|QSPI@@ забезпечує ширину шини в 4 біти та є сумісним із більшістю компактних плат, тоді як @@en|OSPI@@ подвоює пропускну здатність шини завдяки 8 лініям даних, але вимагає виділення фіксованих виводів `GPIO33`–`GPIO37`, що унеможливлює їх використання для іншої периферії.

![Схема розділення внутрішнього DRAM та зовнішнього PSRAM через розподільник heap_caps у режимах QSPI та OSPI](img/esp32s3-psram-qspi-ospi-heap-caps-architecture.svg)
*Розподіл системних доменів пам'яті ESP32-S3 між внутрішнім SRAM та зовнішньою пам'яттю PSRAM під керуванням менеджеру heap_caps.*

Розподіл пам'яті між внутрішнім доменом @@en|DRAM@@ (англ. @@en|Dynamic Random Access Memory@@) та зовнішньою пам'яттю здійснюється через підсистему @@en|heap_caps@@. Для виділення блоку пам'яті у зовнішній @@en|PSRAM@@ використовується функція `heap_caps_malloc()` з прапорцем `MALLOC_CAP_SPIRAM`. Для передачі даних через прямий доступ до пам'яті @@en|DMA@@ (англ. @@en|Direct Memory Access@@) пам'ять у @@en|PSRAM@@ має дотримуватися суворого байтового вирівнювання (зазвичай 4 або 16 байтів), інакше апаратний контролер шини згенерує помилку вибірки даних. Поряд із вирівнюванням суттєвий вплив на продуктивність має апаратний механізм мапування через блок керування пам'яттю @@en|MMU@@ (англ. *Memory Management Unit*). Доступ процесора до @@en|PSRAM@@ відбувається через кеш-пам'ять із розміром кеш-ліній 32 або 64 байти, який задається опцією `CONFIG_ESP32S3_DATA_CACHE_LINE_SIZE` у `sdkconfig`: вибір 64-байтової лінії прискорює послідовну вибірку відеокадрів за рахунок попередньої підкачки даних, але збільшує штрафні затримки при промахах кешу під час довільного читання поодиноких байтів, що знижує швидкість до 10–15 разів порівняно із внутрішнім @@en|SRAM@@. Натомість при послідовному прокачуванні великогабаритних масивів через периферійний @@en|DMA@@ контролер виконує пакетні вичитування (англ. *burst transfer*), повністю утилізуючи смугу пропускання шини без затримок на перезавантаження кеш-ліній MMU. Особливу увагу слід приділяти опції `CONFIG_SPIRAM_USE_MALLOC`, яка автоматично перенаправляє стандартні виклики `malloc()` понад заданий поріг обсягу у зовнішню пам'ять. При вичерпанні доступного обсягу @@en|PSRAM@@ викликувач `heap_caps_malloc()` із прапорцем `MALLOC_CAP_SPIRAM` повернув би `NULL`, тоді як опція `CONFIG_SPIRAM_USE_MALLOC` змушує менеджер пам'яті здійснювати каскадну підмінутну вибірку з внутрішньої @@en|DRAM@@. Це викликає приховане вичерпання внутрішнього ОЗП критично важливих системних задач FreeRTOS та призводить до падіння контролера з помилкою `ESP_ERR_NO_MEM`. Плати на кшталт [Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare) критично залежать від правильного вибору прапорців виділення буферів під час роботи з відеопотоками чи графікою, тоді як [ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini) використовує внутрішній DRAM через відсутність зовнішнього кристала PSRAM.

## Прискорення обчислень інструкціями векторного розширення

Потокова обробка сигналів, фільтрація аудіо або виконання нейромережевих моделей на скалярних обчислювальних блоках потребує значної кількості циклів процесора для послідовного перебору елементів масивів. Для усунення цього вузького місця ядра Xtensa LX7 мікроконтролера оснащені прискорювачем @@en|PIE@@ (від англ. @@en|Processor Instruction Extension@@ — розширення інструкцій процесора). Векторне розширення додає набір 128-бітних регістрів та підтримує інструкції @@en|SIMD@@ (англ. @@en|Single Instruction Multiple Data@@), які дозволяють виконувати паралельні операції множення та додавання над векторними даними за один такт.

![Блок-схема роботи векторного розширення PIE у ядрах Xtensa LX7 та механізм збереження контексту векторних регістрів у FreeRTOS](img/esp32s3-vector-pie-dsp-acceleration-flow.svg)
*Векторний конвеєр PIE процесора Xtensa LX7 та динамічне збереження контексту 128-бітних регістрів при перемиканні задач.*

Використання векторних регістрів створює додаткове навантаження на систему під час збереження контексту переривань та перемикання задач планувальником @@en|FreeRTOS@@. Апаратне розширення [мікроконтролера ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) включає вісім 128-бітних регістрів `q0`–`q7`, кожен з яких може пакувати чотири 32-бітних числа з плаваючою комою, вісім 16-бітних або шістнадцять 8-бітних цілочисельних значень. Завантаження даних для @@en|SIMD@@-інструкцій вимагає обов'язкового вирівнювання буферів у @@en|DRAM@@ по 16-байтовій межі, що дозволяє зчитувати повний 128-бітний вектор у регістри `q0`–`q7` за один процесорний такт без виникнення винятків вирівнювання шини. Щоб уникнути зайвих витрат пам'яті SRAM, операційна система виділяє додатковий стек під 128-бітні регістри лише для тих задач, у яких явно викликано інструкції прискорювача @@en|PIE@@, реалізуючи механізм лінивого збереження контексту (англ. @@en|lazy coprocessor save@@) через системний регістр `CPENABLE`. Під час входження в обробник переривань ISR (англ. @@en|Interrupt Service Routine@@) або при виклику функцій із прапорцями автоматичної векторизації компілятора `-mext-pie` та `-O3`, апаратне ядро перевіряє активність копроцесора: якщо задача виконувала векторні інструкції, регістри `q0`–`q7` та маска зсуву `SAR` зберігаються у спеціальну область стека задачі, а при виходу з ISR повертаються назад. Це унеможливлює псування векторного стану фонових обчислень, але додає затримку перемикання контексту у 16–24 такти, через що векторний код усередині високоефективних ISR обмежують або виокремлюють у спеціальні обробники. Впровадження векторних інструкцій у вихідний код здійснюється трьома шляхами: через автоматичну векторизацію (англ. @@en|auto-vectorization@@, від латинського *vector* — той, що несе) прапорцями компілятора `-mext-pie` та `-O3`, ручною вставкою первинних асемблерних інструкцій ядра @@en|Xtensa LX7@@ (таких як `EE.VLD.128.IP` або `EE.VMUL.S16`) або через виклики вищого рівня бібліотеки @@en|esp-dsp@@. На відміну від прямих асемблерних вставок, які вимагають вручну стежити за вирівнюванням адреси та розгортанням циклів, високорівнева бібліотека @@en|esp-dsp@@ містить оптимізовані C/C++ функції для швидкого перетворення Фур'є та скалярного добутку векторів з автоматичною перевіркою вирівнювання буферів, безпечним завантаженням і розкриттям потенціалу векторного конвеєра без ризику пошкодження контексту регістрів.

class VectorMathEngine {
public:

## Відлагодження через вбудований USB Serial JTAG

Традиційне програмування та відлагодження мікроконтролерів вимагає підключення зовнішніх мікросхем-перехідників USB-UART для зчитування системних логів та окремих апаратних адаптерів JTAG. Вбудований периферійний контролер @@en|USB Serial/JTAG@@ (англ. @@en|Universal Serial Bus Serial and Joint Test Action Group@@) усуває потребу в додаткових конвертерах, дозволяючи підключати виводи `GPIO19` (D-) та `GPIO20` (D+) безпосередньо до роз'єму USB.

Контролер одночасно реалізує два віртуальних пристрої: послідовний порт @@en|CDC@@ (англ. @@en|Communications Device Class@@) для виведення тексту через `printf` та інтерфейс відлагодження для сервера @@en|OpenOCD@@ (англ. @@en|Open On-Chip Debugger@@). Завдяки цьому плати на зразок [Waveshare ESP32-S3-Pico](root:cat-hw-boards/esp32-s3-pico) та [ESP32-S3-Zero](root:cat-hw-boards/esp32-s3-zero) дозволяють прошивати кристали, зчитувати crash-дампи та встановлювати точки зупинки у коді через єдиний фізичний кабель USB. Перенаправлення консолі логів на цей периферійний модуль налаштовується опцією `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` у файлі `sdkconfig`.

Проте робота через нативний USB-контролер має важливі схемотехнічні та програмні особливості. Оскільки пропускна здатність віртуального @@en|CDC@@-порту обмежена специфікацією USB Full-Speed на рівні 12 Мбіт/с, вибір програмної швидкості бод у налаштуваннях термінала є умовним і не впливає на фактичну швидкість передачі пакетів. Водночас системна шина ОС надає доступ до віртуального COM-порту виключно в монопольному режимі: якщо до портів логування вже підключений активний монітор консолі, спроба паралельного запуску сервера відлагодження викликає конфлікт доступу. Крім того, під час апаратного скидання чипа фізичний USB-контролер повністю вимикається, спричиняючи скидання USB-з'єднання з боку ОС та процедуру повторного розпізнавання пристрою (від англ. *@@en|re-enumeration@@* — повторна ініціалізація пристрою шиною). Для відновлення сесії @@en|CDC@@ утиліти розробки застосовують фоновий цикл повторних опитувань системного COM-порту з невеликою затримкою, поки операційна система ПК заново монтує пристрій, що дозволяє уникнути втрати стартових логів ROM-завантажувача. У випадку фатальних збоїв системи механізм фіксації дампу пам'яті (англ. @@en|coredump@@ — аварійний знімок оперативної пам'яті) перехоплює обробник паніки `PanicHandler`: фреймворк утримує фізичний USB-контролер у робочому стані без скидання PHY-рівня та передає двійкові кадри регістрів і стека задач безпосередньо у FIFO-буфер виводу, дозволяючи утиліті `espcoredump.py` витягти дамп без зовнішніх логерів. При розширенні відлагодження сеанс @@en|GDB@@ (англ. @@en|GNU Debugger@@) підключається до сервера @@en|OpenOCD@@ через локальний мережевий порт `target remote :3333`, дозволяючи покроково аналізувати стан ядра [мікроконтролера ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) під час системних помилок.

## Енергозбереження та виклик режиму Deep Sleep

Автономні бездротові вузли вимагають мінімізації струму споживання у стані спокою до одиниць мікроампер. У [мікроконтролері ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) це досягається переходом у режим @@en|Deep Sleep@@ (англ. *Deep Sleep* — глибокий сон), під час якого знеструмлюються обидва ядра Xtensa LX7, більшість периферійних блоків та внутрішня шина пам'яті. Однак при використанні зовнішніх мікросхем пам'яті, як-от на [платі Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare), значний струм витоку може зберігатися через незнеструмлений домен живлення @@en|PSRAM@@ та невизначений стан виводів загального призначення. Для усунення витоків системне середовище ESP-IDF надає спеціальне API автоматичного вимкнення живлення регулятора VDD_SPI та керування енергетичними доменами RTC.

Перед переходом у режим глибокого сну критично важливо зафіксувати логічний стан зовнішніх виводів, щоб запобігти плаваючим потенціалам та небажаному спрацьовуванню периферії. Для цього застосовують механізм @@en|RTC IO pin hold@@ (англ. *RTC IO pin hold* — фіксація стану виводів RTC), який замикає поточний логічний рівень на виводі на час вимкнення основного процесора. Паралельно підсистема живлення переводить зовнішню мікросхему @@en|PSRAM@@ у режим наднизького споживання @@en|Half-Sleep@@ або повністю знімає напругу з лінії VDD_SPI через виклик функції `esp_deep_sleep_start()`.

*Діаграма ілюструє відключення доменів VDD_SPI та збереження стану виводів через RTC IO pin hold перед входом у Deep Sleep.*

Для збереження контексту обчислень між сесіями сну використовують збереження змінних у спеціальних областях пам'яті @@en|RTC SLOW Memory@@ та @@en|RTC FAST Memory@@. Дані, позначені макросом `RTC_DATA_ATTR`, залишаються під напругою від низьковольтного внутрішнього регулятора і не втрачаються після перезапуску процесора. При переході в режим @@en|Deep Sleep@@ основний внутрішній регулятор повністю знеструмлює ядра процесора та основну оперативну пам'ять @@en|DRAM@@, однак енергетичний домен RTC перемикається на живлення від внутрішнього регулятора низького споживання (англ. *low-power regulator*), який підтримує напругу на комірках статичної пам'яті @@en|SRAM@@ (англ. *Static RAM*) обсягом 8 КБ у @@en|RTC SLOW Memory@@. Компонувальник поміщає позначені змінні у спеціальну секцію `.rtc.data`, тому їхні значення зберігаються в комірках упродовж усього періоду сну, а при настанні події пробудження первинний завантажувач виявляє збережений вектор і свідомо пропускає обнулення цієї області. Для налаштування джерел пробудження застосовують функції таймера RTC, системних кнопок на виводах RTC GPIO або подій від низькочастотного @@en|ULP-копроцесора@@ (англ. *Ultra-Low-Power coprocessor* — копроцесор ультранизького споживання). При налаштуванні зовнішніх переривань режим `ext0` дозволяє прив'язати пробудження до одного виводу RTC GPIO із фіксацією визначеного логічного рівня функцією `esp_sleep_enable_ext0_wakeup()`, тоді як режим `ext1` за допомогою `esp_sleep_enable_ext1_wakeup()` підтримує маску з кількох виводів із можливістю вибору логічної умови поєднання каналів за побітовим «АБО» (поява логічної одиниці на будь-якому з виводів) або «ТАК» (зміна станів усіх вказаних виводів). Після спрацьовування тригера та виходу зі сну виникає проблема відновлення доступу до зовнішньої пам'яті: оскільки під час сну напругу з лінії VDD_SPI було знято чи мікросхему переведено в режим сну, спроба прямого звернення до її віртуальних адрес спровокує системний панічний збій за відсутності таблиць трансляції. Щоб уникнути цього, під час старту прошивки системний ініціалізатор викликає функцію `esp_spiram_init()`, яка подає командні послідовності скидання через шину SPI, зчитує ідентифікатор кристала та конфігурує режим тактування. Одразу після цього системний драйвер перераховує та завантажує сторінки в апаратний блок MMU (від англ. @@en|Memory Management Unit@@ — блок керування пам'яттю), прописуючи фізичні адреси блоків RAM у віртуальні вікна процесорних ядер Xtensa, завдяки чому [плати з розширеною пам'яттю](root:cat-hw-boards/esp32-s3r2-waveshare) відновлюють прозорий доступ до зовнішніх буферів у домені @@en|PSRAM@@ ще до виконання основних задач користувача.
