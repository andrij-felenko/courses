## Обмеження внутрішньої SRAM та потреба розширення

У системах на базі [мікроконтролера ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller) обсяг внутрішньої статичної оперативної пам'яті @@en|SRAM@@ (англ. @@en|Static Random-Access Memory@@ — статична оперативна пам'ять) обмежений фізичною ємністю кристала і становить `512 КБайт`. На практиці для довільного динамічного розподілу під купу додатку доступно лише близько `300–400 КБайт`, оскільки значна частина пам'яті резервується під системні потреби фреймворку @@en|ESP-IDF@@, обробку переривань, стек бездротових протоколів Wi-Fi/Bluetooth та системний стек задач операційної системи FreeRTOS.

При розробці складних пристроїв — наприклад, під час обробки відеопотоків з камери [ESP32-CAM](root:cat-hw-boards/esp32-cam), буферизації графічних кадрів високої роздільної здатності для кольорових TFT-дисплеїв або обчислення тензорів у завданнях машинного навчання — ємності внутрішньої пам'яті виявляється критично недостатньо. Спроба виділити один суцільний буфер розміром `614.4 КБайт` (необхідний для кадру VGA у форматі RGB565) у внутрішній пам'яті призводить до неминучої помилки виділення динамічної пам'яті, повернення нульового вказівника `NULL` та аварійного перезавантаження мікроконтролера через збій `ESP_ERR_NO_MEM`.

Розв'язанням цієї проблеми є підключення зовнішньої псевдостатичної оперативної пам'яті @@en|PSRAM@@ (англ. @@en|Pseudo Static Random-Access Memory@@ — псевдостатична оперативна пам'ять) обсягом від `2 МБайт` до `16 МБайт`. Апаратний контролер пам'яті та блок управління пам'яттю @@en|MMU@@ (англ. @@en|Memory Management Unit@@ — блок управління пам'яттю) всередині SoC @@en|ESP32-S3@@ прозоро відображають зовнішні адреси у єдину 32-бітну віртуальну шину даних процесора, дозволяючи ядру виконувати вибірку інструкцій та операції читання/запису.

Таке відображення базується на поділі фізичного обсягу зовнішньої мікросхеми на фіксовані сторінки розміром `64 КБайт`, які апаратний блок @@en|MMU@@ комутує у віртуальні вікна 32-бітного адресного простору центрального процесора @@en|CPU@@ (англ. @@en|Central Processing Unit@@ — центральний процесор). Апаратна структура складається з таблиці 32-бітних регістрів відображення @@en|MMU@@, у яких кожен запис зберігає індекс фізичного блоку @@en|PSRAM@@, прапорець дійсності сторінки та атрибути доступу для системних модулів на кшталт [плати Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare). Будь-яке звернення ядра за адресою із цього діапазону проходить через внутрішній кеш даних @@en|DCache@@ (англ. @@en|Data Cache@@ — кеш даних). При виникненні промаху кешу (англ. @@en|cache miss@@) апаратний контролер ініціює замирання конвеєра (англ. @@en|pipeline stall@@ від @@en|pipe@@ — труба та @@en|stall@@ — затримка, призупинення виконання інструкцій), після чого @@en|MMU@@ зчитує конфігураційний регістр сторінки, обчислює фізичну адресу в пам'яті та виконує пакетну транзакцію завантаження 32-байтового рядка в кеш без залучення програмного коду.

## Конфігурація шин QSPI та OSPI у menuconfig

Для забезпечення зв'язку з мікросхемами зовнішньої пам'яті в @@en|ESP32-S3@@ застосовують високошвидкісні послідовні шини двох типів: 4-бітну @@en|QSPI@@ (англ. @@en|Quad Serial Peripheral Interface@@ — чотирибітний послідовний периферійний інтерфейс) або 8-бітну @@en|OSPI@@ (англ. @@en|Octal Serial Peripheral Interface@@ — восьмибітний послідовний периферійний інтерфейс). Налаштування режиму роботи шин, тактових частот і таймінгів зчитування виконується на етапі компіляції проєкту через графічну утиліту конфігурації @@en|menuconfig@@ (викликом `idf.py menuconfig`) та зберігається у конфігураційному файлі @@en|Kconfig@@ (`sdkconfig`).

Для вибору фізичного інтерфейсу PSRAM у розділі `Component config` -> `ESP32S3-Specific` -> `SPI RAM config` задають параметр режиму шини: `CONFIG_SPIRAM_MODE_QUAD` для 4-бітних мікросхем або `CONFIG_SPIRAM_MODE_OCT` для 8-бітних мікросхем (наприклад, на платі [Waveshare ESP32-S3R2 (16 МБ Flash, 2 МБ PSRAM)](root:cat-hw-boards/esp32-s3r2-waveshare)). Крім того, визначається пропускна здатність шини шляхом вибору тактової частоти — `40 МГц`, `80 МГц` або `120 МГц` (`CONFIG_SPIRAM_SPEED_80M` чи `CONFIG_SPIRAM_SPEED_120M`). Для шини @@en|OSPI@@ додатково може активуватися режим @@en|DDR@@ (англ. @@en|Double Data Rate@@ — подвійна швидкість передачі даних), за якого зчитування даних відбувається як по наростаючому, так і по спадному фронту тактового сигналу, на відміну від стандартного режиму @@en|SDR@@ (англ. @@en|Single Data Rate@@ — одинарна швидкість передачі даних).

Паралельно з налаштуванням оперативної пам'яті, у меню `Component config` -> `SPI Flash config` визначають параметри тактування та живлення для основної мікросхеми @@en|Flash@@. Частоту шини зчитування інструкцій обирають між `40 МГц` (`CONFIG_FLASH_FREQ_40M`) та `80 МГц` (`CONFIG_FLASH_FREQ_80M`), оскільки завищення цього значення без урахування затримок мікросхеми призведе до збоїв зчитування коду програми. Не менш критичним є вибір рівня напруги живлення через параметри `CONFIG_ESP_FLASH_VOLTAGE_3_3V` або `CONFIG_ESP_FLASH_VOLTAGE_1_8V`, які керують внутрішнім стабілізатором @@en|LDO@@ (англ. @@en|Low Dropout regulator@@ — стабілізатор із малою різницею напруг). Оскільки швидкісні мікросхеми @@en|OSPI@@ вимагають живлення `1.8 В`, а стандартні модулі @@en|QSPI@@ працюють від `3.3 В`, помилка у конфігурації може спричинити або неможливість розпізнавання логічних рівнів, або незворотний апаратний пробій кристала пам'яті.

Невірно вказана конфігурація в `sdkconfig` — наприклад, вибір режиму @@en|OSPI@@ для плати з 4-бітною пам'яттю на кшталт [ESP32-S3-Zero (Type-C, 4 МБ)](root:cat-hw-boards/esp32-s3-zero) або встановлення граничної частоти `120 МГц` без увімкнення апаратного калібрування затримок сигналів @@en|timing tuning@@ (англ. @@en|timing tuning@@ — налаштування таймінгів) — призводить до викривлення даних на шині, помилок перевірки цілісності кешу та циклічних перезавантажень процесора під час старту. При роботі 8-бітної шини @@en|OSPI@@ @@en|PSRAM@@ на частоті `120 МГц` у режимі @@en|DDR@@ тривалість тактів вибірки зменшується до одиниць наносекунд, що робить передачу даних чутливою до джиттеру та розбіжностей у довжині друкованих провідників. Для компенсації цих зсувів системний завантажувач під час старту запускає апаратну процедуру підстроювання: модуль контролера пам'яті @@en|MSPI@@ записує у @@en|PSRAM@@ тестовий еталонний паттерн даних, після чого сканує фазові зсуви вбудованої лінії затримки @@en|delay line@@ (англ. @@en|delay line@@ — лінія затримки). Визначаючи безпечний часовий проміжок між межами часових порушень @@en|setup/hold time@@ (англ. @@en|setup/hold time@@ — час встановлення та утримання) для кожного з бітів даних, апаратний декодер автоматично обирає точку вибірки у центрі стабільного вікна й записує знайдене значення у конфігураційні регістри фази защеплення.

## Динамічне виділення пам'яті через heap_caps_malloc

У фреймворку @@en|ESP-IDF@@ для керування неоднорідною оперативною пам'яттю використовують системний аллокатор пам'яті з підтримкою властивостей (англ. @@en|capabilities@@ — властивості/можливості). Стандартний виклик `malloc()` за замовчуванням виділяє пам'ять із внутрішньої @@en|SRAM@@. Щоб явно вказати системі, у якому саме фізичному типі пам'яті слід виділити буфер, застосовують функцію `heap_caps_malloc()` з заголовочного файла `esp_heap_caps.h`.

Головними прапорцями апаратних властивостей пам'яті є:
- `MALLOC_CAP_SPIRAM` — вимагає виділення блоку пам'яті виключно у зовнішній мікросхемі @@en|PSRAM@@. Це дозволяє зберігати великі масиви даних, не виснажуючи внутрішній heap.
- `MALLOC_CAP_INTERNAL` — гарантує виділення пам'яті у швидкій внутрішній @@en|SRAM@@. Цей прапорець є обов'язковим для буферів переривань та периферійних модулів, які потребують прямого доступу до пам'яті @@en|DMA@@ (англ. @@en|Direct Memory Access@@ — прямий доступ до пам'яті), оскільки зовнішня шина PSRAM не підтримує прямі апаратні транзакції DMA.
- `MALLOC_CAP_8BIT` — вказує, що виділена пам'ять має підтримувати побайтову адресацію.

Для оперативної діагностики доступних ресурсів у фреймворку @@en|ESP-IDF@@ передбачено допоміжні функції моніторингу кучі: `heap_caps_get_free_size()` повертає сумарний обсяг вільних байтів для вказаного типу пам'яті (наприклад, `MALLOC_CAP_SPIRAM`), а `heap_caps_get_largest_free_block()` повертає розмір найбільшого суцільного фрагмента. Порівняння результатів цих двох викликів дозволяє виявити небезпечну фрагментацію купи @@en|heap fragmentation@@ (від англ. @@en|heap fragmentation@@ — фрагментація оперативної пам'яті): якщо загальний обсяг вільної пам'яті у зовнішній @@en|PSRAM@@ становить кілька мегабайтів, але найбільший суцільний блок виявляється значно меншим (наприклад, лише `64 КБайт`), спроба виділити один великий буфер для кадру камери чи графічного екрана зазнає помилки, що вимагає реструктуризації алгоритмів розподілу пам'яті у додатку.

## Перенаправлення системного логування на USB CDC

У мікроконтролері @@en|ESP32-S3@@ інтегровано апаратний контролер USB Serial/JTAG, який підтримує стандартний клас пристроїв @@en|USB CDC@@ (англ. @@en|Communications Device Class@@ — клас комунікаційних пристроїв USB) та абстрактну модель керування @@en|CDC ACM@@ (англ. @@en|Abstract Control Model@@ — абстрактна модель керування). Це дозволяє передавати системний консольний вивід `stdout`, `stderr` та макроси відлагодження `ESP_LOGI()` безпосередньо через нативний порт USB Type-C на платах на кшталт [ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini) або [Waveshare ESP32-S3-Pico](root:cat-hw-boards/esp32-s3-pico) без використання проміжних зовнішніх мікросхем-конвертерів USB-UART.

Перенаправлення консолі у фреймворку @@en|ESP-IDF@@ конфігурується у розширенні @@en|menuconfig@@ у розділі `Component config` -> `ESP System Settings` -> `Channel for console output`. Замість значення за замовчуванням `UART0` вибирають опцію `USB Serial/JTAG Controller` (`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG`). При такій конфігурації віртуальна файлова система @@en|VFS@@ (англ. @@en|Virtual File System@@ — віртуальна файлова система) фреймворку прив'язує файлові описувачі стандартного виводу до вбудованого USB-драйвера.

При підключенні пристрою до комп'ютера операційна система розпізнає віртуальний послідовний порт (наприклад, `/dev/ttyACM0` у Linux або `COMx` у Windows). Для запобігання втраті перших рядків консольних логів під час старту мікроконтролера (поки операційна система ПК завершує ініціалізацію та опитування USB-дескрипторів) у `sdkconfig` можна додатково активувати затримку ініціалізації консолі `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG_INIT_DEF`, що гарантує надійне перехоплення повідомлень на етапі відлагодження пристрою у польових умовах.

Для складних апаратних стендів фреймворк @@en|ESP-IDF@@ надає альтернативний режим дубльованого логування за допомогою опції `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG`. За такої схеми основним каналом консольного виводу залишається апаратний `UART0` (`CONFIG_ESP_CONSOLE_UART_DEFAULT`), тоді як вбудований інтерфейс @@en|USB Serial/JTAG Controller@@ підключається як додатковий вторинний канал. Повідомлення `ESP_LOGI()`, `stdout` та `stderr` одночасно дублюються в обидва порти [мікроконтролера ESP32-S3](root:cat-hw-boards/esp32s3-microcontroller), що гарантує збереження діагностичного потоку через фізичний послідовний інтерфейс навіть при несподіваному скиданні сесії @@en|USB CDC@@ чи відключенні кабелю Type-C від комп'ютера.
