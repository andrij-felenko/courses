# Математичні розрахунки швидкостей UART, SLIP-кадрування та контрольних сум у протоколі esptool

## Апаратна синхронізація UART та розрахунок бодрейту

Послідовний інтерфейс @@en|UART@@ (від англ. *Universal Asynchronous Receiver-Transmitter* — універсальний асинхронний приймач-передавач) є асинхронним і не містить окремої лінії тактування. Приймач визначає початок кадру за спадним фронтом старт-біта і стробує логічний рівень кожного наступного біта в точці, що відповідає середині його тривалості `t_sample = (N + 0.5) · T_bit`. Якщо частоти генераторів тактування передавача `B_tx` та приймача `B_rx` не збігаються, виникає відносне відхилення швидкостей `ε = (B_tx - B_rx) / B_tx`, що призводить до накопичення фазового зсуву протягом кадру з 10 бітів (1 старт-біт, 8 бітів даних, 1 стоп-біт).

![На часовій діаграмі показано накопичення фазового зсуву UART та вибіркові точки осцилятора](img/uart-baudrate-phase-error-calculation.svg)
*На часовій діаграмі показано накопичення фазового зсуву UART та вибіркові точки осцилятора.*

Для уникнення помилок зчитування накопичений фазовий зсув на останньому біті кадру не повинен перевищувати 50% тривалості біта `T_bit`, що обмежує сумарне допустиме відхилення величиною `|ε_total| < 5%`. На практиці для надійного обміну даними утиліти @@en|esptool@@ з первинним завантажувачем @@en|ROM Bootloader@@ відхилення не має перевищувати `|ε| < 2.5%`. Розрахунок бодрейту в контролерах ESP виконується дільником системної частоти `CLKDIV = f_clk / B_target`, який складається з 12-бітової цілої частини `CLKDIV_INT` та 4-бітової дробової частини `CLKDIV_FRAC`.

Розглянемо обчислення параметрів для нестандартної частоти 74880 бод при тактуванні від кварцового резонатора `f_clk = 26` МГц та для високошвидкісного режиму 921600 бод при частоті шини `f_clk = 80` МГц. При підвищенні швидкості понад 1.5 Мбод накопичення фазового зсуву стає критичним критерієм стабільності зв'язку: оскільки тривалість біта `T_bit` зменшується до сотень наносекунд, сумарний зсув фази за час передачі пакета довжиною `L_pkt` бітів становить `Δt_drift = L_pkt · |ε| · T_bit`. Для збереження точного стробування в межах вікна допуску з урахуванням апаратних затримок фільтрація сигналу вимагає виконання умови `L_pkt · |ε| < 0.25`, що виводить математичну залежність максимально припустимого відхилення швидкості `|ε_max| < 1 / (4 · L_pkt)`. З цієї залежності видно, що при збільшенні довжини безперервного кадру вимоги до точності дільника розрахунку бодрейту зростають гіперболічно, вимагаючи зменшення похибки `|ε|` нижче 0.1% для відмовостійної роботи з [архітектурою програматора DAPLink](root:cat-hw-boards/daplink-programmer-architecture):

        CLKDIV_real_74880 = 26000000 / 74880
        = 347.2222                                         [розрахунок ідеального дільника]
        CLKDIV_INT = 347                                    [ціла частина дільника]
        CLKDIV_FRAC = round(0.2222 · 16)
        = 4                                                 [переведення дробу в 4-бітове значення]
        CLKDIV_actual_74880 = 347 + 4 / 16
        = 347.25                                            [фактичний коефіцієнт дільника]
        B_actual_74880 = 26000000 / 347.25
        = 74874.01 бод                                      [реальна швидкість передачі]
        ε_74880 = (74880 - 74874.01) / 74880
        = 0.00008 = 0.008%                                  [похибка швидкості]

Для швидкості 921600 бод обчислення виконуються аналогічно:

        CLKDIV_real_921600 = 80000000 / 921600
        = 86.8055                                          [розрахунок ідеального дільника]
        CLKDIV_INT = 86                                     [ціла частина дільника]
        CLKDIV_FRAC = round(0.8055 · 16)
        = 13                                                [переведення дробу в 4-бітове значення]
        CLKDIV_actual_921600 = 86 + 13 / 16
        = 86.8125                                           [фактичний коефіцієнт дільника]
        B_actual_921600 = 80000000 / 86.8125
        = 921526.29 бод                                     [реальна швидкість передачі]
        ε_921600 = (921600 - 921526.29) / 921600
        = 0.00008 = 0.008%                                  [похибка швидкості]

Похибка в обох випадках становить всього 0.008%, що гарантує точну синхронізацію при роботі з [архітектурою програматора DAPLink](root:cat-hw-boards/daplink-programmer-architecture) або стандартними конвертерами USB-UART.

## Математика SLIP-кадрування та байт-стаффінгу

Для надійної передачі бінарних пакетів утиліта @@en|esptool@@ використовує протокол @@en|SLIP@@ (від англ. *Serial Line Internet Protocol* — послідовний мережевий протокол). Оскільки корисне навантаження може містити довільні байтові значення, межі кадрів позначаються службовим байтом `END = 0xC0`. Щоб запобігти помилковому розпізнаванню байта `0xC0` у середині даних, застосовується алгоритм байт-стаффінгу (заміни службових байтів).

![На схемі зображено трансформацію бінарного пакета у SLIP-кадр із заміною байтів 0xC0 та 0xDB](img/slip-framing-and-byte-stuffing-expansion.svg)
*На схемі зображено трансформацію бінарного пакета у SLIP-кадр із заміною байтів 0xC0 та 0xDB.*

Згідно з правилами SLIP, заміна виконується за двома правилами:
1. Байт `0xC0` замінюється двобайтовою послідовністю `ESC ESC_END` (`0xDB 0xDC`).
2. Байт `0xDB` замінюється двобайтовою послідовністю `ESC ESC_ESC` (`0xDB 0xDD`).

Обов'язкові накладні витрати кадру складають 2 байти (`0xC0` на початку та в кінці пакета). Якщо початковий пакет містить `N` байтів, з яких `k` байтів потребують екранування (`0xC0` або `0xDB`), підсумковий розмір кадру обчислюється за формулою `N_trans = N + 2 + k`. 

Для рівномірно розподілених випадкових бінарних даних ймовірність натрапити на байт `0xC0` або `0xDB` становить `p = 2 / 256 = 1 / 128 ≈ 0.78125%`. Розрахуємо математичне сподівання розміру кадру та граничні значення для блоку даних `N = 1024` байти:

        N_trans_min = 1024 + 2
        = 1026 байтів                                       [випадок без службових байтів]
        E[k] = 1024 · (2 / 256)
        = 8 байтів                                          [очікувана кількість замінених байтів]
        E[N_trans] = 1024 + 8 + 2
        = 1034 байти                                        [середній розмір SLIP-кадру]
        N_trans_max = 2 · 1024 + 2
        = 2050 байтів                                       [найгірший випадок при масиві з 0xC0 або 0xDB]

Проте у реальних виконних бінарних файлах структури даних не є вибірково випадковими. Зокрема, у заголовочному блоці @@en|ELF@@-файла (розміром `N_ELF = 52` байти) базові адреси сегментів ОЗП ESP32 (наприклад, `0x3FC00000`) детерміновано містять байтові значення `0xC0`. Якщо заголовок містить `k_fixed = 2` фіксованих байти `0xC0`, математичне сподівання кількості замін екранування обчислюється так:

        E[k_ELF] = k_fixed + (N_ELF - k_fixed) · (2 / 256)
        = 2 + (52 - 2) · (1 / 128)                          [врахування фіксованих адрес та решти байтів]
        = 2 + 50 · 0.0078125                                [обчислення ймовірності для решти 50 байтів]
        ≈ 2.39 байта                                        [очікувана кількість екранованих байтів]

Отже, через детерміновану наявність системних адрес із байтом `0xC0` щільність екранування у заголовках досягає `2.39 / 52 ≈ 4.6%`, що майже в 6 разів перевищує середній рівень `0.78%` для випадкових масивів.

Таким чином, середня величина накладних витрат SLIP-кадрування становить лише ~0.98%, але в найгіршому теоретичному випадку розмір кадру може подвоїтися, що слід враховувати при виділенні буферів приймача в RAM.

## Адресна арифметика вирівнювання флеш-секторів

Спроба записати байтовий масив за довільною адресою у флеш-пам'ять без попереднього очищення призводить до спотворення даних: фізичні комірки @@en|NOR Flash@@ здатні лише змінювати логічні одиниці на нулі під час запису. Для перезапису комірки необхідно відновити в усі її біти значення 1, що здійснюється процедурою стирання. Однак мікроконтролерний завантажувач @@en|ROM Bootloader@@ не витирає поодинокі байти — стирання відбувається виключно фізичними блоками фіксованого розміру: секторами по 4 КБ (4096 байтів) або блоками по 64 КБ (65536 байтів).

При формуванні команд утиліти @@en|esptool@@ обраховуються межі стирання для довільної початкової адреси запису `A_start` та довжини бінарного образу `L`. Математично початкова адреса першого вирівняного сектора `A_aligned_start` обчислюється відкиданням молодших бітів адреси:

A_aligned_start
= floor(A_start / 4096) × 4096      [округлення до меншого кратного 4096]
= A_start - (A_start mod 4096)       [побітова маска адреси]

Кінцева адреса даних `A_end` утворює межу `A_end = A_start + L`. Оскільки останній байт образу може припадати на середину сектора, кінцева адреса стирання `A_aligned_end` мусить заокруглюватися до верхньої межі сектора:

A_aligned_end
= ceil(A_end / 4096) × 4096                       [округлення до більшого кратного 4096]
= floor((A_end + 4096 - 1) / 4096) × 4096         [цілочисельне вирівнювання]

Загальний обсяг флеш-пам'яті під стирання `S_erase` та кількість необхідних секторів `N_sectors` визначаються різницею вирівняних меж `S_erase = A_aligned_end - A_aligned_start` та `N_sectors = S_erase / 4096`. При підготовці до запису кількох суміжних бінарних файлів або фрагментів прошивки утиліта @@en|esptool@@ об'єднує окремі діапазони стирання в єдиний безперервний блок, якщо виконуються дві математичні умови: по-перше, відсутній незаповнений проміжок між вирівняним кінцем першого образу та початком другого (`A_aligned_end_1 = A_aligned_start_2`), а по-друге, об'єднана початкова адреса вирівняна за межею 64 КБ (`A_merged_start mod 65536 = 0`) при сумарному обсязі `S_merged ≥ 65536` байтів. У такому разі замість надсилання `N_sectors` окремих команд стирання секторів по 4 КБ протокол @@en|ROM Bootloader@@ випромінює єдину високошвидкісну команду стирання блоку 64 КБ (команда `0xD8`), що зменшує накладні часові витрати на узгодження пакетів по шині @@en|SPI Flash@@ у 16 разів.

S_erase
= A_aligned_end - A_aligned_start                 [різниця вирівняних меж]
= N_sectors × 4096                                [сумарний обсяг секторів]

Якщо обрахована початкова адреса `A_aligned_start` вирівняна за межею 64 КБ (`A_aligned_start mod 65536 = 0`), а обсяг `S_erase` перевищує 65536 байтів, @@en|ROM Bootloader@@ оптимізує процес: замість шестнадцяти окремих команд стирання секторів по 4 КБ виконується одна команда стирання блоку 64 КБ.

Коли розмір бінарного кадру не кратний розміру сторінки запису флеш-пам'яті, невикористаний простір у кінці сектора доповнюється байтами `0xFF`. Доповнювальні байти (від англійського *@@en|padding bytes@@* — заповнювальні байти) обчислюються як:

L_pad
= A_aligned_end - A_end                           [довжина доповнення]

Заповнення байтами `0xFF` безпечне для [архітектури флеш-пам'яті](root:hw-components/spi-flash): оскільки витерта комірка вже містить байт `0xFF` (усі біти дорівнюють 1), запис байта `0xFF` не змінює стан транзисторів і не зношує кристал пам'яті.

**Приклад обчислення секторів стирання для бінарного образу.**

Потрібно записати файл прошивки розміром `L = 10000` байтів за адресовим зміщенням `A_start = 0x1800` (6144 у десятковій системі).

S_size = 4096                                      [розмір сектора 4 КБ]
A_start = 6144                                     [початкова адреса]
A_aligned_start
= floor(6144 / 4096) × 4096                        [округлення вниз]
= 1 × 4096 = 4096 (0x1000)                         [вирівняний початок]

A_end = 6144 + 10000 = 16144                       [фактичний кінець даних]
A_aligned_end
= floor((16144 + 4096 - 1) / 4096) × 4096          [цілочисельне округлення вгору]
= floor(20239 / 4096) × 4096
= 4 × 4096 = 16384 (0x4000)                        [вирівняний кінець]

S_erase = 16384 - 4096 = 12288 байтів              [загальний обсяг стирання]
N_sectors = 12288 / 4096 = 3 сектори               [кількість секторів]
L_pad = 16384 - 16144 = 240 байтів 0xFF            [обсяг заповнення]

Таким чином, @@en|esptool@@ витирає 3 послідовні сектори у діапазоні адрес від `0x1000` до `0x4000`, зберігаючи цілісність сусідніх даних.

## Верифікація цілісності дампа за CRC32 та MD5

Передача бінарного образу через послідовний інтерфейс @@en|UART@@ піддається ризику виникнення завад, викликаних джиттером системної частоти чи індукованими наводками на лініях зв'язку. Для виявлення спотворень бітів у протоколі @@en|esptool@@ застосовується дворівнева верифікація: побайтовий контрольний суматор на рівні окремих кадрових пакетів даних та криптографічні й циклічні алгоритми перевірки для всього файлу прошивки.

На рівні транспортування кожен пакет `FLASH_DATA` містить однобайтне поле контрольної суми, яке розраховується за алгоритмом послідовного виключного АБО (@@en|XOR@@). Початкове значення суматора ініціалізується константним вектором `C_0 = 0xEF`. Під час обробки кожного нового байта кадру `B_k` поточний стан суматора обчислюється за рекурентною формулою:

C_k
= C_(k-1) ⊕ B_k                                   [побітове виключне АБО]

Кінцевий байт `C_n` додається до заголовочного пакета. Якщо під час передачі в одного з байтів `B_m` змінюється `j`-й біт (помилка інверсії біта), кінцевий результат `C_n'` неминуче інвертує свій `j`-й біт:

C_n'
= C_n ⊕ 2ʲ                                         [інверсія j-го біта суматора]

Це гарантує виявлення будь-якої поодинокої бітової помилки в межах одного кадру. Проте при одночасній інверсії парної кількості бітів у тотожних позиціях різних байтів пакетна контрольна сума `@@en|XOR@@` повертає хибно-позитивний результат.

Математичний розрахунок ймовірності пропускання двобітової помилки пояснює, чому побайтовий суматор неефективний для великих пакетів. Нехай кадр даних `@@en|FLASH_DATA@@` містить `N` байтів (загалом `8N` бітів). Загальна кількість способів розмістити 2 бітові помилки серед `8N` бітів становить комбінаторне число `C_(8N)² = (8N · (8N - 1)) / 2`. 8-бітний суматор `@@en|XOR@@` не виявить спотворення лише тоді, коли обидві помилки потраплять у той самий бітовий розряд `j` (де `j ∈ {0, 1, ..., 7}`), але у різні байти. Оскільки у кожному з 8 розрядів є `N` бітів, кількість невиявлених парних помилок `N_miss` дорівнює `8 · C_N² = 4N · (N - 1)`. Ймовірність `P_miss` пропускання такої двобітової помилки обчислюється як відношення кількості невиявлених комбінацій до загального числа парних спотворень `N_total`:

P_miss
= N_miss / N_total                                [відношення невиявлених пар до загальних]
= (8 · C_N²) / C_(8N)²                           [підстановка комбінаторних пар]
= (4N · (N - 1)) / (4N · (8N - 1))               [розкриття комбінацій для 8N бітів]
= (N - 1) / (8N - 1)                              [скорочення спільного множника 4N]

Для стандартного пакета розміром `N = 1024` байти ймовірність пропускання двобітової помилки становить `P_miss = 1023 / 8191 ≈ 0.1249` (або `12.49%`), а при зростанні `N` граничне значення прямує до `1/8` (абсолютний ліміт `12.5%`). Саме через таку високу ймовірність пропуску критичних спотворень для захисту від групових помилок та верифікації прошитого образу флеш-пам'яті використовується алгоритм циклічного надлишкового контролю `@@en|CRC32@@` (від англійського *@@en|Cyclic Redundancy Check 32-bit@@* — 32-бітна циклічна перевірка надлишковості) та криптографічний дайджест `@@en|MD5@@` (від англійського *@@en|Message Digest 5@@* — п'яте дайджест-повідомлення).

Алгоритм `@@en|CRC32@@` трактує послідовність байтів прошивки як коефіцієнти двійкового полінома `M(x)` над скінченним полем Galois `GF(2)`. Залишок від ділення полінома `M(x) · x³²` на канонічний твірний поліном `G(x) = x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1` утворює 32-бітний код контрольної суми:

R(x)
= (M(x) · x³²) mod G(x)                           [ділення поліномів у GF(2)]

Отримане значення `R(x)` дозволяє виявляти всі одиночні й подвійні помилки, а також сплески спотворень (від англійського *@@en|burst errors@@* — сплескові помилки) довжиною до 32 бітів.

Після завершення циклу запису @@en|ROM Bootloader@@ виконує зчитування записаних секторів флеш-пам'яті й обчислює глобальний 128-бітний дайджест `@@en|MD5@@`. Алгоритм ділить потік даних на блоки по 512 бітів і проганяє їх через 64 нелінійні операції зсуву та логічного змішування над чотирма 32-бітними регістрами станом `A, B, C, D`:

F(B, C, D) = (B ∧ C) ∨ (¬B ∧ D)                    [логічна функція першого раунду]
A_(k+1)
= B + ((A + F(B, C, D) + X_k + T_i) <<< s)        [покрокове оновлення регістра]

Порівняння розрахованого дайджеста `@@en|MD5@@` із локальним хешем файлу на ПК гарантує відсутність незапобіжних помилок запису на фізичному рівні пам'яті без потреби завантажувати повний дамп прошивки назад через повільний інтерфейс UART або [зовнішній програматор DAPLink](root:cat-hw-boards/daplink-programmer-architecture).
