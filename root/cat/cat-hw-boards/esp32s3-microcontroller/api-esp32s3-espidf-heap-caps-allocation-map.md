## Проблема витоків та обмежень внутрішньої DRAM

Розробка складних мобільних застосунків на базі [родини плат на ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview) часто зіштовхується із жорсткими апаратними межами внутрішньої динамічної оперативної пам'яті @@en|DRAM@@ (англ. *@@en|Dynamic RAM@@* — динамічна оперативна пам'ять). Фізичний обсяг внутрішньої пам'яті @@en|SRAM@@ у 512 КБ розділено на три блоки: @@en|SRAM0@@ (32 КБ) зарезервовано під інструкції @@en|IRAM@@ та кеш @@en|ICache@@, @@en|SRAM1@@ (256 КБ) використовується як спільний простір для інструкцій і даних, а @@en|SRAM2@@ (200 КБ) виділено виключно під дані @@en|DRAM@@ та кеш @@en|DCache@@. Значна частина цього ресурсу зарезервована під системні потреби ROM-завантажувача, стеки бездротових протоколів @@en|Wi-Fi@@ та @@en|Bluetooth@@, а також таблиці операційної системи реального часу @@en|FreeRTOS@@. У результаті для прикладної купи (англ. @@en|heap@@) лишається лише 300–350 КБ безперервного адресного простору. Якщо застосунок запитує виділення некритичного або занадто великого буфера, а вільного регіону з відповідною бітовою маскою немає, підсистема викликає хук `heap_caps_alloc_failed()`. За замовчуванням цей виклик передає керування системному обробнику аварійної зупинки (англ. @@en|Panic Handler@@), який виводить дамп стану купи зі вказівкою розміру й запитаних прапорців та перезавантажує чип, запобігаючи непередбачуваній поведінці й пошкодженню пам'яті.

Спроба виділити великі масиви даних — наприклад, кадровий буфер роздільної здатності UXGA (1600×1200 пікселів у форматі RGB565 обсягом 3.84 МБ) або великі таблиці FFT для обробки звуку — за допомогою стандартного виклику `malloc()` завершується поверненням вказівника `NULL`. Навіть при наявності сумарно 200 КБ вільного ОЗП інтенсивне створення й знищення динамічних об'єктів викликає фрагментацію пам'яті, коли суцільного фрагмента потрібного розміру немає в наявності. Для розв'язання цієї проблеми фреймворк @@en|ESP-IDF@@ надає підсистему розподілу пам'яті за атрибутами @@en|heap_caps@@ (англ. *heap capabilities* — можливості купи), яка реєструє кожну область пам'яті з бітовою маскою фізичних властивостей. Під час виклику `heap_caps_malloc(size, caps)` системний арбітр почекально оцінює зареєстровані регіони пам'яті, фільтруючи лише ті, які одночасно відповідають усім запитаним прапорцям (як-от `MALLOC_CAP_INTERNAL`, `MALLOC_CAP_SPIRAM` чи `MALLOC_CAP_DMA`). Арбітр спочатку шукає нефрагментований блок у внутрішній швидкій пам'яті, але при явній вказівці зовнішнього домену перенаправляє запит до шини пам'яті, унеможливлюючи виснаження критичних ресурсів операційної системи.

## Виділення пам'яті PSRAM через heap_caps

Для розширення доступної оперативної пам'яті платформи ESP32-S3 використовують зовнішньо підключену псевдостатичну оперативну пам'ять @@en|PSRAM@@ (англ. *@@en|Pseudo-Static RAM@@* — псевдостатична оперативна пам'ять), яка підключається через високошвидкісну 8-лінійну шину @@en|Octal SPI@@. Розподіл пам'яті у зовнішньому домені виконується через системні виклики `heap_caps_malloc()` або `heap_caps_aligned_alloc()` із передачею бітової маски прапорців @@en|MALLOC_CAP_SPIRAM@@.

![Діаграма розподілу пам'яті між внутрішньою SRAM та зовнішньою PSRAM через підсистему heap_caps з картою адрес та масками атрибутів](img/esp32-s3-heap-caps-psram-allocation-diagram.svg)
*Розподіл оперативної пам'яті між внутрішніми блоками DRAM та зовнішньою PSRAM підсистемою heap_caps.*

При роботі з контролером прямого доступу до пам'яті @@en|DMA@@ (англ. *@@en|Direct Memory Access@@*) критичною вимогою є вирівнювання початкової адреси буфера по 16-байтовій або 32-байтовій межі (прапорець `MALLOC_CAP_DMA`), що запобігає помилкам кеш-когерентності та апаратним збоям шини (англ. @@en|Alignment Error@@). Стандартний виклик `heap_caps_malloc()` гарантує базове 4-байтове вирівнювання вказівників у PSRAM, тоді як для жорсткої прив'язки буферів до специфічних вимог шини DMA застосовують `heap_caps_aligned_alloc()`, де першим аргументом передають необхідну кратність вирівнювання (16 або 32 байти). На коректність обміну суттєво впливає обрана кеш-політика доступу до @@en|PSRAM@@: режим наскрізного запису @@en|Write-Through@@ (англ. *Write-Through* — наскрізний запис) негайно транслює будь-які зміни процесора у зовнішню пам'ять, що гарантує цілісність даних перед стартом передачі DMA без додаткових системних викликів, але знижує швидкість виконання обчислень ядра. Натомість режим зворотного запису @@en|Write-Back@@ (англ. *Write-Back* — зворотний запис) прискорює роботу процесора шляхом тимчасового затримання модифікованих даних у швидкій кеш-пам'яті, проте вимагає обов'язкового примусового скидання та інвалідації кеш-ліній через системний виклик `esp_cache_msync()` із прапорцями напрямку синхронізації перед запуском периферійного DMA-конвеєра, інакше периферійний пристрій вичитає застарілі дані з фізичної комірки. Практична реалізація плат на кшталт [Waveshare ESP32-S3R2](root:cat-hw-boards/esp32-s3r2-waveshare) спирається на регулярне виділення кадрових масивів саме у зоні PSRAM із чітким узгодженням кеш-політики під конкретний режим роботи периферії.

:::tabs
:::code api-esp32s3-espidf-heap-caps-allocation-map/c/esp-idf/allocate-frame-buffer.c
```cpp|arduino
#include "esp_heap_caps.h"

void* allocateFrameBufferArduino(size_t size) {
    // Виділення динамічного масиву в зовнішній PSRAM
    void *ptr = heap_caps_malloc(size, MALLOC_CAP_SPIRAM);
    if (!ptr) {
        Serial.println("Не вдалося виділити буфер у PSRAM");
        return nullptr;
    }
    return ptr;
}
```

## Векторизація обчислень PIE та esp-dsp

Ядро @@en|Xtensa LX7@@ у мікроконтролері ESP32-S3 містить спеціалізований векторний розширювач інструкцій @@en|PIE@@ (англ. *@@en|Processor Instruction Extension@@*), що оперує 128-бітними регістрами `Q0`–`Q7` для прискорення паралельних обчислень @@en|SIMD@@. Для спрощення використання векторного апаратного прискорювача у програмах мовами C/C++ фреймворк містить оптимізовану бібліотеку @@en|esp-dsp@@.

Використання процедур бібліотеки `esp-dsp` (наприклад, `dsps_dotprod_f32` для векторного скалярного множення або `dsps_fft2r_fc32` для швидкого перетворення Фур'є) прискорює математичні обчислення у 4–7 разів порівняно зі звичайними циклами C. Операційна система @@en|FreeRTOS@@ автоматично зберігає та відновлює стан векторних регістрів при перемиканні контексту задач, що гарантує ізоляцію обчислень у мультизадачному середовищі на таких пристроях, як [модуль ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini). Для мінімізації накладних витрат CPU операційна система застосовує ліниве збереження (англ. @@en|lazy context saving@@ — відкладене збереження контексту) співпроцесорного блоку. Коли задача вперше виконує векторну інструкцію, порт ядра динамічно виділяє у її стековому фреймі 128-байтовий розширений блок контексту під регістри `Q0`–`Q7` та спеціальний регістр `SAR`. Під час переривання тактів RTOS перевіряє прапорець активності співпроцесора, і якщо задача задіювала векторний прискорювач, низькорівнева процедура `xthal_save_cp0` дампить стан `Q0`–`Q7` у її стекову область, а процедура `xthal_restore_cp0` відновлює його при поверненні управління.

## Конфігурація периферійного контролера LCD_CAM

Мікроконтролер ESP32-S3 оснащено апаратним периферійним модулем @@en|LCD_CAM@@, який об'єднує незалежні канали передачі даних для паралельних графічних дисплеїв (режим LCD) та зчитування відеопотоку з фотоматриць (режим CAM). Блок прямо передає дані у кадрові буфери PSRAM через підсистему DMA без навантаження центрального процесора.

![Схема потоку даних периферійного блоку LCD_CAM із кільцевими буферами DMA у PSRAM, що показує конвеєр передачі кадрів між камерою та дисплеєм](img/esp32-s3-lcd-cam-dma-pipeline.svg)
*Конвеєр переміщення кадрових буферів через контролер LCD_CAM та DMA у зовнішній пам'яті PSRAM.*

Організація подвійної чи потрійної буферизації запобігає розривам зображення (англ. @@en|tearing effect@@, від *to tear* — рвати) та дає змогу паралельно зчитувати новий кадр із камери, поки попередній виводиться на дисплей. Приймання та відправка даних контролюються апаратними перериваннями завершення кадру (англ. @@en|EOF interrupt@@, від @@en|End Of Frame@@ — кінець кадру), які ґенеруються модулем @@en|LCD_CAM@@ у момент передачі останнього пікселя. Обробник переривання миттєво перемикає покажчик активного дескриптора на наступний вільний елемент кільцевого списку @@en|DMA@@ у пам'яті @@en|PSRAM@@ та надсилає сповіщення черзі задач операційної системи @@en|FreeRTOS@@. Така безперервна синхронізація через кільцеві буфери усуває простої процесора та виключає гонки даних (англ. @@en|race condition@@) між фоновим наповненням шини та прикладним кодом обробки. Оглядові характеристики сімейства планок та модулів описує [родина плат і модулів на ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview).

## Відлагодження та обробка помилок esp_err_t

Надійна робота систем із динамічним розподілом пам'яті вимагає безперервного контролю стану купи та обробки статусного типу @@en|esp_err_t@@. Для моніторингу обсягу вільної пам'яті застосовують функції `heap_caps_get_free_size()` та `heap_caps_get_minimum_free_size()`, що дає змогу виявляти витоки на ранніх етапах розробки.

Макрос `ESP_ERROR_CHECK()` перевіряє повертуваний код системних викликів і при виникненні помилки (наприклад, `ESP_ERR_NO_MEM`) зупиняє виконання програми із виводом дампа регістрів. Завдяки вбудованому контролеру @@en|USB Serial/JTAG@@ розробник виконує покрокове відлагодження через середовище @@en|OpenOCD@@ без зовнішніх конвертерів, що спрощує роботу з модулями на кшталт [ESP32-CAM](root:cat-hw-boards/esp32-cam). Для налаштування віртуального порту у меню конфігурації Kconfig вмикають опцію `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`, після чого апаратний трансивер на виводах `GPIO19` та `GPIO20` створює на ПК два віртуальних пристрої: послідовний консольний порт CDC та інтерфейс GDB-відлагодження. Під час запуску утиліти `openocd -f board/esp32s3-builtin.cfg` сервер зв'язується з JTAG TAP-контролером ядра через протокол `esp_usb_jtag`, надаючи прямий доступ до регістрів `PC`, `SP` та `EXCVADDR`. У момент спрацьовування системного панічного обробника panic handler ядро зупиняє конвеєр, фіксує значення лічильника інструкцій та передає стек викликів через інтегровану вибірку OpenOCD, що дає змогу миттєво локалізувати точну адресу витоку чи невірного звернення до пам'яті. Для глибокого аналізу фрагментації та локалізації прихованих витоків застосовують функцію `heap_caps_dump_all()`, яка виводить у консоль повний список вільних і зайнятих блоків із їхніми адресами та атрибутами пам'яті. Якщо виток відбувається динамічно під час виконання складного алгоритму, вмикають підсистему @@en|Heap Trace@@: викликом `heap_trace_init_standalone()` реєструють буфер запису, після чого функція `heap_trace_start(HEAP_TRACE_LEAKS)` починає фіксувати кожне виділення пам'яті з вказівниками на адреси інструкцій, які його ініціювали. Після завершення цільової операції викликом `heap_trace_stop()` та `heap_trace_dump()` розробник отримує точний перелік незвільнених блоків із прив'язкою до конкретних рядків коду.

:::tabs
```c|esp-idf
#include "esp_heap_caps.h"
#include "esp_log.h"
#include "esp_err.h"

static const char *TAG = "diag";

void check_memory_status(void) {
    size_t internal_free = heap_caps_get_free_size(MALLOC_CAP_INTERNAL);
    size_t spiram_free = heap_caps_get_free_size(MALLOC_CAP_SPIRAM);
    
    ESP_LOGI(TAG, "Вільна DRAM: %u байт, вільна PSRAM: %u байт", 
             (unsigned int)internal_free, (unsigned int)spiram_free);
}
```
```cpp|arduino
#include "esp_heap_caps.h"

void printHeapDiagnostics() {
    uint32_t freeDram = heap_caps_get_free_size(MALLOC_CAP_INTERNAL);
    uint32_t freePsram = heap_caps_get_free_size(MALLOC_CAP_SPIRAM);
    
    Serial.printf("DRAM: %u B, PSRAM: %u B\n", freeDram, freePsram);
}
```
