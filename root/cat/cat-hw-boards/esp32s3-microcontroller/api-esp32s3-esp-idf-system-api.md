## Проблема раціонального управління ресурсами ESP32-S3

Сучасні мікроконтролерні системи обробки відеопотоків, сигналів та штучного інтелекту вимагають одночасної роботи з гігабітними масивами даних, векторними прискорювачами та зовнішніми мікросхемами пам'яті. Мікроконтролер ESP32-S3 володіє багатим апаратним потенціалом, але його обчислювальна архітектура ставить перед розробником складні виклики щодо управління пам'яттю.

Класичний розподіл пам'яті за допомогою стандартної функції `malloc` виділяє блоки виключно у внутрішній оперативній пам'яті @@en|DRAM@@ (англ. *dynamic random-access memory*, від грецьк. *dynamis* — сила, рух + англ. *random-access memory* — оперативна пам'ять). *dynamis* — сила, рух + англ. *random-access memory* — оперативна пам'ять). Оскільки обсяг внутрішньої пам'яті кристала обмежений приблизно 512 кБ (частина з яких задействується під системний стек, змінні @@en|FreeRTOS@@ та кодовий сегмент @@en|IRAM@@), спроба створити кадрові буфери камери або тензори нейромереж через стандартний виклик `malloc` швидко призводить до її повного вичерпання та аварійного завершення програми. Додатково ситуацію ускладнює фрагментація динамічної купи @@en|heap@@: при частих виділеннях і звільненнях масивів різного розміру пам'ять розбивається на безліч дрібних розрізнених фрагментів. У результаті, навіть за наявності сумарно кількох десятків кілобайт вільної DRAM, спроба виділити один суцільний блок великого розміру зазнає невдачі, оскільки системний розподільник не здатний виконати дефрагментацію фізичних адрес розставлених вказівників.

Крім того, апаратні периферійні блоки вимагають чітко визначених властивостей пам'яті: контролери прямого доступу @@en|DMA@@ (англ. *direct memory access*, від лат. *directus* — прямий) вимагають фізичної сумісності адреси, а векторний копроцесор @@en|PIE@@ (англ. *processor instruction extension*) потребує обов'язкового 16-байтного вирівнювання адресного вказівника для запобігання фатальним виняткам апаратного вирівнювання. Для розв'язання цих проблем фреймворк @@en|ESP-IDF@@ надає системний інструментарій управління ресурсами купи `heap_caps`, макроси атрибутів пам'яті та прискорені бібліотеки.

## Конфігурування PSRAM та атрибути пам'яті

Для розширення доступної оперативної пам'яті мікроконтролер ESP32-S3 підтримує підключення зовнішньої псевдостатичної пам'яті @@en|PSRAM@@ (англ. *pseudo-static random-access memory*) обсягом до 32 МБ. Першим кроком її використання є конфігурування файлу налаштувань @@en|sdkconfig@@. У розділі конфігурації увімкнення підсистеми `CONFIG_SPIRAM=y` дозволяє ініціалізувати зовнішню шину, де прапорець `CONFIG_SPIRAM_MODE_OCTAL` активує високошвидкісний 8-бітний режим шини @@en|Octal SPI@@, реалізований на платах на зразок [Waveshare ESP32-S3R2 (16 МБ Flash, 2 МБ PSRAM)](root:cat-hw-boards/esp32-s3r2-waveshare) та описаний у матеріалі [Родина плат і модулів на ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview).

Для точного управління виділенням блоків пам'яті в середовищі @@en|ESP-IDF@@ використовується функція `heap_caps_malloc()`. Вона приймає прапорці можливостей купи, що визначають фізичне розташування масиву:
- `MALLOC_CAP_SPIRAM` — примусово виділяє пам'ять у зовнішньому чіпі @@en|PSRAM@@;
- `MALLOC_CAP_INTERNAL` — гарантує виділення пам'яті у високошвидкісній внутрішній @@en|SRAM@@ для критичних затримками задач;
- `MALLOC_CAP_DMA` — виділяє блок пам'яті, фізично доступний для периферійних контролерів прямого доступу.

Прямий доступ ядра процесора до адресного простору PSRAM забезпечується апаратною трансляцією віртуальних адрес через кеш-матрицю блоку керування пам'яттю @@en|MMU@@ (від англ. @@en|Memory Management Unit@@ — блок керування пам'яттю). Під час старту системний завантажувач відображає фізичні сторінки зовнішнього ОЗП розміром 64 кБ у віртуальний діапазон адрес процесора, передаючи обробку шинних транзакцій кеш-контролеру L1. При послідовному читанні кеш-контролер автоматично завантажує суцільні лінійки пам'яті по 32 байти, забезпечуючи високу ефективну пропускну здатність. Проте при хаотичному вибірковому доступі виникають часті промахи кешу (від англ. @@en|cache miss@@ — промах кешу), що змушує MMU ініціювати додаткові цикли перезавантаження рядків по шині SPI. Це затримує виконання інструкцій ядра на 12–20 тактів на кожну вибірку та знижує реальну пропускну здатність шини PSRAM порівняно із прямою адресацією внутрішньої SRAM.

![Архітектурна схема розподілу адресного простору ESP32-S3 між внутрішньою SRAM та зовнішньою PSRAM у фреймворку ESP-IDF.](img/esp32s3-esp-idf-memory-heap-allocation-architecture.svg)
*_Структура розділення обчислювальної пам'яті та механізми виділення ресурсів купи за допомогою атрибутів та прапорців heap_caps._*

Статичне розміщення змінних на етапі компіляції регулюється спеціальними макросами атрибутів: `EXT_RAM_ATTR` розміщує глобальні масиви у зовнішній @@en|PSRAM@@, тоді як `RTC_DATA_ATTR` зберігає значення змінних у внутрішній енергонезалежній пам'яті @@en|RTC SRAM@@ під час режиму глибокого сну.

## Векторне прискорення обчислень бібліотекою ESP-NN

Апаратна мікроархітектура ядра @@en|Xtensa LX7@@ у мікроконтролері ESP32-S3 містить 128-бітне векторне розширення @@en|PIE@@, проте пряме написання інструкцій ассемблера ускладнює підтримку коду. Для автоматичного залучення векторних інструкцій фреймворк @@en|ESP-IDF@@ надає оптимізовану C/C++ бібліотеку @@en|ESP-NN@@ (англ. *Espressif Neural Network*).

Бібліотека @@en|ESP-NN@@ містить набір низькорівневих математичних операторів, які під час компіляції під ESP32-S3 автоматично розгортаються у векторні SIMD-інструкції (англ. *single instruction, multiple data*):
- `esp_nn_conv_s8()` — оптимізована 2D-згортка 8-бітних квантованих тензорів для нейронних мереж;
- `esp_nn_add_s8()` — поелементне векторне додавання масивів значущих цілих чисел;
- `esp_nn_depthwise_conv_s8()` — глибинна згортка для компактних архітектур машинного навчання.

Критичною вимогою для досягнення максимальної швидкодії векторних обчислень є 16-байтне вирівнювання адресних буферів. Для виділення вирівняної пам'яті використовується функція `heap_caps_aligned_alloc(16, size, MALLOC_CAP_SPIRAM)`. Вирівняний виклик дозволяє за один процесорний такт завантажувати 128-бітні вектори в регістри `Q0`–`Q7` без затримок на вирівнювання. Якщо ж довжина оброблюваного масиву не кратна 16 байтам (наприклад, при згортці тензорів із непарною кількістю каналів чи пікселів), внутрішня реалізація `esp_nn_conv_s8()` розбиває виконання на два етапи: основними векторними інструкціями опрацьовується максимальний вирівняний блок розміром `N - (N % 16)` байтів, а залишок із кількості від 1 до 15 байтів дораховується послідовним скалярним хвостовим циклом (від англ. @@en|scalar tail loop@@ — скалярний хвостовий цикл) або доповнюється нулями (від англ. @@en|zero padding@@ — заповнення нулями) до кратності 16 байтам для запобігання виходу за межі виділеної пам'яті та уникнення затримок розгалуження.

## Конфігурування шинного периферійного драйвера LCD_CAM

Для неблокуючого зчитування даних із відеосенсорів та виведення зображення на дисплеї в мікроконтролері ESP32-S3 впроваджено апаратний периферійний модуль @@en|LCD_CAM@@. Цей модуль поєднує паралельний вхідний інтерфейс камери та вихідну паралельну шину дисплея (протоколи RGB, 8080).

Робота драйвера @@en|LCD_CAM@@ у середовищі @@en|ESP-IDF@@ будується на використанні загального контролера прямого доступу до пам'яті @@en|GDMA@@ (англ. *general direct memory access*). Завдяки цьому зчитування кадру з камери чи передача масиву пікселів на дисплей здійснюється у фоновому режимі, звільняючи процесорні ядра для обчислень. У практичних застосунках на базі модулів [ESP32-CAM (OV2640 + microSD)](root:cat-hw-boards/esp32-cam) або [ESP32-CAM з камерою OV3640 (2 МП)](root:cat-hw-boards/esp32-cam-ov3640) це дозволяє захоплювати кадрові буфери високої роздільної здатності без пропусків кадрів.

![Схема конвеєра передачі даних периферійного модуля LCD_CAM через контролер GDMA між пам'яттю PSRAM та дисплеєм або камери.](img/esp32s3-lcd-cam-dma-pipeline.svg)
*_Конвеєр фонового обміну кадровими буферами в режимі прямого доступу до пам'яті GDMA через модуль LCD_CAM._*

Програмна конфігурація здійснюється через створення дескриптора шини викликом `esp_lcd_new_i80_bus()` та керування панеллю через інтерфейс `esp_lcd_panel_io_handle_t`. Виклик функції `esp_lcd_panel_draw_bitmap()` ініціює фонову передачу кольорового буфера з @@en|PSRAM@@ на фізичну шину без залучення ресурсів CPU.

Проте при зчитуванні масивних кадрових буферів безпосередньо з @@en|PSRAM@@ існує ризик апаратного збою опустіння буфера @@en|underrun@@ (від англ. @@en|buffer underrun@@ — вичерпання даних у транзитному буфері). У разі затримок на шині, викликаних міжядерною конкуренцією чи промахами кешу L1, периферійний модуль @@en|LCD_CAM@@ опустошує свій внутрішній @@en|FIFO@@-буфер раніше, ніж @@en|GDMA@@ встигає підкачати наступну порцію пікселів, що призводить до зміщення рядків або зриву синхронізації дисплея. Для усунення цього ефекту в драйвері налаштовують двобуферну схему @@en|ping-pong buffer@@ (від англ. @@en|ping-pong buffer@@ — почергове перемикання транзитних буферів) у швидкій внутрішній пам'яті @@en|SRAM@@. Поки контролер @@en|GDMA@@ безперервно передає перший транзитний буфер на фізичну шину, фоновий потік перезаповнює другий буфер свіжими даними з PSRAM, гарантуючи стійкий потік кадрів на пристроях із [родини плат і модулів на ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview) навіть при високому піковому навантаженні на системну шину.

## Налаштування нативного порту USB Serial/JTAG

Мікроконтролер ESP32-S3 містить вбудований апаратний контролер @@en|USB Serial/JTAG@@, виведений на виводи `GPIO19` (лінія `D-`) та `GPIO20` (лінія `D+`). На платах формфактора [ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini) або [ESP32-S3-Zero (Type-C, 4 МБ)](root:cat-hw-boards/esp32-s3-zero) це дозволяє підключати пристрій напряму до роз'єму @@en|USB Type-C@@ без використання зовнішніх мостів @@en|USB-UART@@.

Для активації виводу системної консолі через нативний порт у файлі конфігурації @@en|sdkconfig@@ встановлюється параметр `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`. Після цього стандартні виклики виводу `printf()` та системні логи `ESP_LOGI()` автоматично перенаправляються в нативний порт @@en|CDC ACM@@ (англ. *communications device class abstract control model*).

Головною перевагою нативного блоку є збереження каналу зв'язку під час фатальних помилок паніки ядра @@en|Panic Handler@@ та підтримка апаратного відлагодження @@en|JTAG@@ через @@en|OpenOCD@@ без необхідності підключення зовнішніх програмних адаптерів. Окремою важливою специфікою є поведінка нативного порту при переході мікроконтролера в режим легкого сну @@en|Light Sleep@@: на відміну від класичного зовнішнього моста USB-UART, який живиться від роз'єму незалежно від стану кристала, внутрішній @@en|USB PHY@@ інтегрованого контролера вимагає утримання системної тактової частоти шини @@en|APB@@ для збереження активного USB-з'єднання з операційною системою хоста. Якщо в налаштуваннях `sdkconfig` не дозволено утримання тактування периферії під час сну, хост-комп'ютер зафіксує обрив USB-зв'язку та від'єднання пристрою від шини.
