## Проблема конфігурації ресурсів у ESP32-S3

Розробка складних пристроїв на базі мікроконтролера ESP32-S3 нерідко зіштовхується зі збоями, причина яких криється у некоректному налаштуванні підсистем пам'яті та периферії на рівні прошивки. Коли проєкт виходить за межі простих тестових скетчів і вимагає обробки потокового відео, роботи з нейромережами чи активного мережевого обміну, стандартна конфігурація середовища розробки перестає забезпечувати необхідну продуктивність. Виклики функцій виділення пам'яті починають повертати нульові вказівники, периферийні контролери втрачають прямий доступ до пам'яті, а система раптово перезавантажується без збереження дампів помилок.

Специфіка архітектури, яку має [Родина плат і модулів на ESP32-S3](root:cat-hw-boards/esp32-s3-boards-family-overview), полягає у гнучкій організації зовнішніх шин та наявності вбудованого USB-контролера. Проте некоректно вибраний режим зв'язку з флеш-пам'яттю ускладнює виконання коду, а неправильний тип оперативної пам'яті у викликах динамічного розподілу призводить до вичерпання внутрішньої кучі. Суттєву роль тут відіграє підсистема кєш-пам'яті L1 (обсягом 32 КБ на ядро), яка згладжує затримки звернення до зовнішньої PSRAM через шину SPI: при промаху кєшу (від англ. @@en|cache miss@@ — промах кєшу) процесор потрапляє у паузу очікування тривалістю в десятки тактів. Особливо гостро це проявляється на компактних платах на кшталт [Waveshare ESP32-S3R2 (16 МБ Flash, 2 МБ PSRAM)](root:cat-hw-boards/esp32-s3r2-waveshare) чи [ESP32-S3-Zero (Type-C, 4 МБ)](root:cat-hw-boards/esp32-s3-zero), де тип підключеної пам'яті та частота шини вимагають точного узгодження програмних параметрів з апаратними лініями для мінімізації штрафів за промахи L1 кєшу.

Усунення цих проблем досягається через тонке налаштування середовища @@en|ESP-IDF@@ (від англ. @@en|Espressif IoT Development Framework@@ — фреймворк розробки Espressif IoT). Опис конфігурації системи зберігається у конфігураційній системі @@en|Kconfig@@ та файлі @@en|sdkconfig@@. Саме тут визначаються тактові частоти шин, алгоритми керування кучею пам'яті та режими роботи нативного USB, що дозволяє адаптувати прошивку під вимоги конкретного апаратного рішення.

## Конфігурація шин Flash та PSRAM

Зовнішня флеш-пам'ять та розширена оперативна пам'ять @@en|PSRAM@@ (від англ. @@en|Pseudo Static RAM@@ — псевдостатична оперативна пам'ять) підключаються до ядра ESP32-S3 через високошвидкісні послідовні інтерфейси SPI. Залежно від модифікації чипа та розведення друкованої плати, зв'язок здійснюється через 4-бітну шину @@en|Quad SPI@@ (від англ. @@en|Quad Serial Peripheral Interface@@ — чотириниточний послідовний периферійний інтерфейс) або 8-бітну шину @@en|Octal SPI@@ (від англ. @@en|Octal Serial Peripheral Interface@@ — восьминиточний послідовний периферійний інтерфейс).

Передача даних по шині SPI може відбуватися у режимі одинарної швидкості @@en|SDR@@ (від англ. @@en|Single Data Rate@@ — одинарна швидкість передачі даних), коли сигнал зчитується по одному фронту тактового імпульсу, або у режимі подвійної швидкості @@en|DDR@@ (від англ. @@en|Double Data Rate@@ — подвійна швидкість передачі даних), де дані передаються по обидвох фронтах. Вибір режиму безпосередньо впливає на пропускну здатність шини та рівень електромагнітних завад.

![Схема конфігурації шин Quad SPI та Octal SPI у режимах SDR і DDR для флеш-пам'яті та PSRAM](img/esp32s3-spi-bus-modes.svg)
*Конфігурації сигнальних ліній та варіанти ширини шини даних для з'єднання з зовнішньою пам'яттю Flash та PSRAM у ESP32-S3.*

У середовищі @@en|ESP-IDF@@ параметри роботи шини конфігуруються у файлі @@en|sdkconfig@@ за допомогою відповідних макросів @@en|Kconfig@@:

Окрім виділення буферів даних, середовище підтримує розміщення самого виконуваного коду у зовнішній пам'яті через опцію `CONFIG_SPIRAM_FETCH_INSTRUCTIONS=y`. Активація цього параметра доручає кєш-контролеру завантажувати й виконувати інструкції програмних функцій безпосередньо з PSRAM, що вивільняє дорогоцінну внутрішню SRAM та флеш-пам'ять для критичних задач реального часу. Разом із макросом `CONFIG_SPIRAM_RODATA=y` для константних даних це розширює доступний обсяг коду додатка, проте вимагає врахувати додаткові затримки зчитування інструкцій при промахах кєшу в обробниках переривань.

- `CONFIG_ESP32S3_SPIRAM_SUPPORT=y` — вмикає підтримку зовнішньої PSRAM;
- `CONFIG_SPIRAM_MODE_QUAD=y` або `CONFIG_SPIRAM_MODE_OCT=y` — визначає розрядність шини PSRAM (4 або 8 бітів);
- `CONFIG_SPIRAM_SPEED_40M=y`, `80M=y` або `120M=y` — задає тактову частоту шини PSRAM у мегагерцах;
- `CONFIG_FLASHMODE_QIO=y` або `CONFIG_FLASHMODE_OCT=y` — налаштовує режим роботи флеш-пам'яті.

Підвищення частоти шини до 120 МГц або перехід на Octal DDR збільшує швидкість зчитування текстур і зображень, але вимагає стабільного живлення 3.3 В або 1.8 В відповідно до специфікації мікросхеми пам'яті. Якщо вкажеться режим Octal SPI для плати з фізичним розведенням Quad SPI, мікроконтролер увійде у безкінечний цикл перезавантаження через неможливість прочитати первинний завантажувач.

## Управління пам'яттю через heap caps

Адресний простір ESP32-S3 розділений між швидкою внутрішньою пам'яттю SRAM (обсягом до 512 КБ) та об'ємною зовнішньою PSRAM (до 16 МБ). Внутрішня SRAM підтримує прямолінійний доступ для периферійних контролерів у режимі @@en|DMA@@ (від англ. @@en|Direct Memory Access@@ — прямий доступ до пам'яті), тоді як зовнішня PSRAM підключається через кєш-контролер і має обмеження щодо виконання DMA-транзакцій певними периферійними модулями.

![Карта розподілу адресованості внутрішньої SRAM та зовнішньої PSRAM з позначенням масок MALLOC_CAP_INTERNAL та MALLOC_CAP_SPIRAM](img/esp32s3-heap-caps-memory-map.svg)
*Розподіл адресованості кучі та придатність фізичних блоків пам'яті для швидких обчислень та транзакцій DMA.*

Для керування цим неоднорідним масивом у @@en|ESP-IDF@@ використовується спеціалізований API виділення кучі за властивостями — `heap_caps_malloc()`. Замість стандартної функції `malloc()`, розробник вказує бітові маски вимог до пам'яті. Особливу роль відіграє прапорець `MALLOC_CAP_EXEC`, який виділяє ділянку пам'яті з дозволом на виконання інструкцій процесором (англ. @@en|executable memory@@ — виконувана пам'ять): це необхідно при динамічному завантаженні бінарного коду або реалізації інтерпретаторів із JIT-компіляцією (від англ. @@en|Just-In-Time@@ — вчасно). Оскільки підсистема шини інструкцій IRAM дозволяє виконання коду лише з внутрішньої SRAM, спроба комбінувати `MALLOC_CAP_EXEC` із виділенням у зовнішній PSRAM повернує нульовий вказівник. Загалом у викликах `heap_caps_malloc()` застосовують такі ключові бітові маски:

- `MALLOC_CAP_SPIRAM` — виділяє блок у зовнішній PSRAM. Підходить для об'ємних буферів кадрів камери, аудіоданих та масивів нейромереж;
- `MALLOC_CAP_INTERNAL` — гарантує розміщення блоку виключно у внутрішній SRAM. Використовується для стека критичних задач FreeRTOS та обробників переривань;
- `MALLOC_CAP_DMA` — виділяє внутрішню пам'ять, яка вирівняна по межах слів і доступна для апаратних транзакцій DMA (наприклад, для SPI або I2S);
- `MALLOC_CAP_8BIT` — забезпечує побайтову адресацію виділеної ділянки.

## Налаштування нативного USB та консолі

Мікроконтролер ESP32-S3 оснащений вбудованим апаратним контролером Full-Speed USB, який підтримує два основних режими роботи без використання зовнішніх мікросхем конвертерів USB-UART:

1. Режим @@en|USB-CDC@@ (від англ. @@en|USB Communication Device Class@@ — клас пристроїв зв'язку USB) — емулює віртуальний послідовний порт для виводу консольних логів та обміну даними з комп'ютером;
2. Режим @@en|USB-JTAG@@ (від англ. @@en|USB Joint Test Action Group@@ — вбудований інтерфейс відлагодження USB-JTAG) — забезпечує апаратне відлагодження прошивки через OpenOCD, встановлення точок зупинки та читання регістрів ядра без зовнішнього відлагоджувальника.

Налаштування поведінки USB-контролера та перенаправлення системного виводу здійснюється через параметри @@en|Kconfig@@ у файлі @@en|sdkconfig@@:

При конфігуруванні віртуального порту USB-CDC із кількома кінцевими точками (англ. @@en|endpoints@@ — кінцеві точки USB) системний драйвер @@en|ESP-IDF@@ розмежовує передачу консольних логів та користувальницьких даних. Вхідний та вихідний буфери кінцевих точок шини USB (за замовчуванням EP1 для IN/OUT даних та EP2 для повідомлень про стан CDC) вимагають чіткої синхронізації та узгодження розміру кадру: якщо основний потік даних блокує кінцеву точку, консольний вивід призупиняється до звільнення буфера. Для запобігання втраті повідомлень логування драйвер налаштовує кільцевий буфер (англ. @@en|ring buffer@@ — кільцевий буфер) в оперативній пам'яті, що гарантує незалежне проходження системної діагностики без порушення роботи основного користувальницького USB-протоколу.

- `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` — перенаправляє системний вивід логів (`ESP_LOGI`, `printf`) через вбудований USB Serial/JTAG контролер;
- `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y` — вимикає резервний консольний порт UART0 для економії виводів GPIO;
- `CONFIG_USB_OTG_SUPPORTED=y` — вмикає підтримку режиму USB Host/Device через контролер USB OTG.

Завдяки цьому плати типу [ESP32-S3 SuperMini](root:cat-hw-boards/esp32-s3-supermini) прошиваються, відлагоджуються та виводять налагоджувальні повідомлення через один фізичний роз'єм Type-C.

## Діагностика збоїв та panic handler

При виникненні фатальних помилок у роботі програми (наприклад, звернення за недійсним вказівником, спроба виконання неозначеної інструкції або вихід за межі масиву) управління передається у системний @@en|panic handler@@ (від англ. @@en|panic handler@@ — обробник фатальних винятків). Його завдання — зафіксувати стан регістрів процесора та надати розробнику інформацію для діагностики.

За замовчуванням обробник формує дамп регістрів та трасування викликів (від англ. @@en|backtrace@@). Конфігурація у @@en|sdkconfig@@ визначає подальшу поведінку системи:

- `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y` — друкує інформацію про помилку у консоль та виконує автоматичне перезавантаження чипа;
- `CONFIG_ESP_SYSTEM_PANIC_PRINT_HALT=y` — зупиняє ядро після виводу помилки для аналізу стану через відлагоджувальник;
- `CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH=y` — зберігає повний зліпок оперативної пам'яті (від англ. @@en|core dump@@) у спеціальний розділ флеш-пам'яті.

При використанні нативного USB важливо впевнитися, що `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` активовано для виводу повідомлень про паніку, інакше при критичному збої повідомлення не потраплять у монітор послідовного порту. Завдяки правильно налаштованому panic handler розробник може швидко виявити лінійку коду, яка спричинила збій, та відновити нормальне функціонування пристрою.
