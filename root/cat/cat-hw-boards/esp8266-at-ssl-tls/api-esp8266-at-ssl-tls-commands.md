## Виклики безпеки та обмеження пам'яті ESP8266

При передачі чутливих даних у мережах Інтернету речей відкриті TCP-з'єднання піддаються ризикам перехоплення та підміни трафіку. Для захисту інформаційного обміну застосовують криптографічний протокол захисту транспортного рівня (англ. @@en|Transport Layer Security@@, далі @@en|TLS@@, від *transport* — транспорт, *layer* — рівень, *security* — безпека). Проте на [модулях ESP-01](root:cat-hw-boards/esp-01) реалізація шифрування ускладнюється суворими апаратними ресурсами: обсяг доступної оперативної пам'яті кристала статичної оперативної пам'яті (англ. @@en|Static RAM@@, далі @@en|SRAM@@) для користувацьких буферів становить менше 40 КБ.

Стандартний розмір кадрового фрагмента в протоколі @@en|TLS@@ сягає 16 КБ. Для виконання захищеного рукостискання та двонаправленого шифрування мережевому стеку пристрою потрібно одночасно утримувати в оперативній пам'яті два таких буфери (для вхідного та вихідного потоку даних), що вимагає понад 32 КБ кучі. Якщо пристрій намагається встановити захищене з'єднання з довільним веб-сервером через базові [мережеві сокети TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets) без попередньої оптимізації криптографічних буферів, дефіцит оперативної пам'яті призводить до вичерпання кучі та раптового перезавантаження мікроконтролера.

Офіційна @@en|AT-прошивка@@ чипа [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) інтегрує компактну бібліотеку криптографії @@en|mbedTLS@@. Для забезпечення стабільної роботи пристрою інтерфейс @@en|AT-команд@@ надає спеціалізований програмний API для вибіркового виділення пам'яті під сертифікати, керування довжиною фрагментів та налаштування рівня перевірки довіри до серверів.

Для оптимізації використання ресурсів прошивка розподіляє криптографічні дані між фізичною пам'яттю та оперативною кучею. Збереження кореневих сертифікатів і приватних ключів здійснюється в енергонезалежній флеш-пам'яті (англ. @@en|Flash memory@@), де під криптографічні структури виділяються фіксовані сектори обсягом 4 КБ. Бібліотека @@en|mbedTLS@@ зчитує ці дані з @@en|Flash@@ лише за потреби під час рукостискання, не утримуючи їх постійно в оперативній пам'яті. Водночас обсяг доступної оперативної пам'яті (англ. @@en|DRAM@@, від *dynamic* — динамічний, *random-access* — з довільним доступом, *memory* — пам'ять) обмежений статичними буферами мережевого стека @@en|lwIP@@, який обробляє [мережеві сокети TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets). Ці буфери виділяються одразу під час ініціалізації системи й зменшують вільну кучу (англ. @@en|heap@@, від *heap* — купа). Коли пристрій починає сеанс шифрування, @@en|mbedTLS@@ намагається виділити власні динамічні буфери кадрів із залишку цієї кучі. Якщо сума статичних витрат стека @@en|TCP/IP@@ та динамічних буферів @@en|TLS@@ перевищує наявний обсяг вільної кучі, виклики виділення пам'яті повертають помилку й з'єднання зривається.

Для упередження фатальних помилок браків пам'яті розробник повинен попередньо налаштовувати криптографічний контекст до моменту виконання запиту ініціалізації сокета. Командний інтерфейс @@en|AT-прошивки@@ надає набір конфігураційних викликів, серед яких ключовою є команда `AT+CIPSSLCCFG`, що регулює режим верифікації сертифікатів, версію протоколу та максимальну довжину фрагмента даних (англ. @@en|Max Fragment Length Negotiation@@, далі @@en|MFLN@@). Примусове обмеження розміру кадрового буфера з дефолтних 16 КБ до 2048 чи 1024 байтів зменшує пікові витрати оперативної купи @@en|heap@@ з 33 КБ до 3...5 КБ, що дозволяє стабільно утримувати шифрований канал зв'язку та відкривати кілька паралельних сокетів навіть на ресурсно обмежених модулях [ESP-01S](root:cat-hw-boards/esp-01s).

## Параметри конфігурації TLS та режими верифікації

Для запобігання помилкам переповнення пам'яті та гнучкого налаштування параметрів шифрування перед відкриттям сокета використовується команда статичної конфігурації SSL/TLS клієнта `AT+CIPSSLCCFG`. Вона дозволяє встановити рівень перевірки автентичності сертифіката, версію протоколу @@en|TLS@@ та обмежити максимальну довжину фрагмента даних (англ. @@en|Max Fragment Length@@, далі @@en|MFLN@@).

Формат команди налаштування конфігурації SSL/TLS клієнта:

Для перевірки поточного стану конфігурації перед відкриттям мережевого сокета застосовують запитальну форму команди `AT+CIPSSLCCFG?`. Прошивка повертає рядок у форматі `+CIPSSLCCFG:<link_id>,<auth_mode>,<tls_version>,<mfln>` з наступним кодом `OK`, що дозволяє програмно верифікувати встановлений режим перевірки сертифікатів та ліміти буферів [модулів ESP-01S](root:cat-hw-boards/esp-01s). Якщо пристрій працює в режимі багатьох підключень (`AT+CIPMUX=1`), запит виводить поточні значення для кожного активного сокета окремими рядками.

```text
AT+CIPSSLCCFG=<link_id>,<auth_mode>,<tls_version>,<mfln>
```

Параметри команди конфігурації:
- `<link_id>` — номер мережевого з'єднання (0–4) при багатопідключенній роботі; при однопідключенному режимі параметр ігнорується або дорівнює `0`;
- `<auth_mode>` — режим перевірки сертифікатів:
  - `0` — без перевірки (англ. @@en|no verify@@); з'єднання шифрується, але сертифікат сервера не валідується (мінімальне використання пам'яті);
  - `1` — перевірка серверного сертифіката (англ. @@en|verify server@@); вимагає наявності кореневого сертифіката у пам'яті;
  - `2` — взаємна верифікація (англ. @@en|mutual authentication@@); вимагає перевірки як сервера, так і надання клієнтського сертифіката;
- `<tls_version>` — версія протоколу шифрування: `1` (TLS 1.0), `2` (TLS 1.1), `3` (TLS 1.2, рекомендовано);
- `<mfln>` — обмеження розміру кадрового буфера в байтах: `512`, `1024`, `2048` або `4096`.

![Схема конфігурування режимів верифікації TLS та параметрів Max Fragment Length перед встановленням захищеного з'єднання.](img/esp8266-at-ssl-tls-configuration-flow.svg)
*Схема конфігурування режимів верифікації TLS та параметрів Max Fragment Length перед встановленням захищеного з'єднання.*

Зменшення розміру фрагмента `<mfln>` до значення `2048` або `1024` дає змогу скоротити витрати кучі вдвічі, що є критично важливим для стабільної роботи на модулях [роду ESP-01S](root:cat-hw-boards/esp-01s).

Приклад відправки команди конфігурації TLS у термінал:

```text
AT+CIPSSLCCFG=0,1,3,2048
OK
```

## Передача SNI та збереження сертифікатів у Flash

Сучасні хмарні сервери та веб-хостинги часто розміщують декілька захищених доменних імен на одній фізичній IP-адресі. Для того щоб сервер міг відправити правильний криптографічний сертифікат під час рукостискання, клієнт повинен повідомити доменне ім'я до моменту встановлення шифрованого каналу за допомогою розширення індикації імені сервера (англ. @@en|Server Name Indication@@, далі @@en|SNI@@).

В @@en|AT-прошивці@@ ім'я хоста для @@en|SNI@@ налаштовується командою `AT+CIPSSLCSNI`:

```text
AT+CIPSSLCSNI=<link_id>,"<hostname>"
```

Приклад встановлення імені домену для першого сокета:

```text
AT+CIPSSLCSNI=0,"api.example.com"
OK
```

Для роботи в режимі суворої верифікації (`<auth_mode>` = 1 або 2) кореневі сертифікати центрів сертифікації (англ. @@en|Certificate Authority@@, далі @@en|CA@@), а також приватні ключі клієнта повинні бути заздалегідь збережені в системні сектори енергонезалежної флеш-пам'яті (англ. @@en|Flash@@). Для завантаження бінарних або PEM-сертифікатів використовується команда `AT+SYSSTORE`.

Синтаксис завантаження сертифіката у сховище:

```text
AT+SYSSTORE=<type>,<length>
```

Деталізація типів сертифікатів вимагає дотримання форматів даних: параметром `<type>` вибирають тип запису (`0` — кореневий CA-сертифікат, `1` — власний сертифікат клієнта, `2` — приватний ключ клієнта), а параметр `<length>` позначає точний розмір файлу в байтах. При цьому критичною вимогою для успішного збереження у сховищі є попереднє перетворення текстових сертифікатів формату @@en|PEM@@ (англ. @@en|Privacy-Enhanced Mail@@) у бінарний формат @@en|DER@@ (англ. @@en|Distinguished Encoding Rules@@). Вбудований парсер `AT+SYSSTORE` приймає виключно бінарне кодування, що економить оперативну пам'ять при розборі. Для конвертації файлу `cert.pem` у DER-формат на хост-системі використовують інструмент @@en|OpenSSL@@ викликом `openssl x509 -in cert.pem -outform DER -out cert.der`, а для приватного ключа — `openssl rsa -in key.pem -outform DER -out key.der`. Передача сирого текстового файлу PEM без попереднього перетворення у DER викликає відмову парсера або пошкодження структури ключів у Flash-пам'яті модулів [ESP-01](root:cat-hw-boards/esp-01).

Після надсилання команди прошивка повертає символ запрошення `>` для побайтної передачі вмісту сертифіката, після чого зберігає його у Flash. При наступних оновленнях ПЗ через [прошивання ESP-01](root:cat-hw-boards/esp01-firmware-flashing) завантажені ключі зберігаються у відведених секторах.

## Ініціалізація захищених сокетів командою AT+CIPSTART

Після завершення попередньої конфігурації параметрів SSL/TLS та завантаження необхідних сертифікатів мікроконтролер готовий до відкриття шифрованого мережевого з'єднання. Ініціалізація захищеного сокета виконується універсальною командою управления підключеннями `AT+CIPSTART`.

Синтаксис виклику команди `AT+CIPSTART` для з'єднання SSL/TLS:

```text
// Для однопідключенного режиму (AT+CIPMUX=0)
AT+CIPSTART="SSL","<remote_host>",<remote_port>[,<local_port>]

// Для багатопідключенного режиму (AT+CIPMUX=1)
AT+CIPSTART=<link_id>,"SSL","<remote_host>",<remote_port>[,<local_port>]
```

Опис аргументів виклику:
- `"SSL"` — вказує прошивці на використання криптографічного транспорту SSL/TLS замість незахищеного `"TCP"`;
- `<remote_host>` — IP-адреса або доменне ім'я віддаленого сервера;
- `<remote_port>` — порт призначення (стандартний порт HTTPS — `443`, MQTTS — `8883`).

Після успішного встановлення захищеного з'єднання надсилання шифрованого корисного навантаження здійснюється командою `AT+CIPSEND=<length>` (або `AT+CIPSEND=<link_id>,<length>` у багатопідключенному режимі). При отриманні команди модуль перевіряє активність сокета й повертає символ запрошення `>`, після чого очікує на відправку точної кількості байтів `<length>`. Передані дані прозоро зашифровуються криптографічним стеком `mbedTLS` та відправляються у TLS-канал, після чого прошивка виводить підтвердження `SEND OK`. Опис режимів роботи [мережевих сокетів TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets) детально розглядає загальну механіку буферизації AT-команд.

Приклад встановлення захищеного з'єднання з віддаленим сервером:

```text
AT+CIPSTART="SSL","api.example.com",443
CONNECT

OK
```

Якщо конфігурація режиму верифікації вимагає перевірки сертифіката, модуль перед виводом `CONNECT` виконує апаратне рукостискання, виділяє буфери пам'яті та валідує підпис. У разі успіху сокет переходить у прозорий режим або режим командного обміну даними через [керування AT-командами](root:cat-hw-boards/esp8266-at-gpio-control).

## Діагностика помилок рукостискання та коди mbedTLS

Процес встановлення захищеного з'єднання SSL/TLS може завершитися відмовою через вичерпання пам'яті, недійсний термін дії сертифіката або невідповідність шифрів. У випадку збою рукостискання @@en|AT-прошивка@@ повертає повідомлення `ERROR` або `CLOSED`, а також виводить від'ємний десятичний код помилки бібліотеки @@en|mbedTLS@@.

![Діаграма послідовності рукостискання TLS з відображенням точок виникнення помилок mbedTLS та кодів відповідей AT-прошивки.](img/esp8266-at-ssl-handshake-error-diagnostics.svg)
*Діаграма послідовності рукостискання TLS з відображенням точок виникнення помилок mbedTLS та кодів відповідей AT-прошивки.*

Нижче наведено зведену таблицю поширених кодів помилок mbedTLS при роботі з AT-командами:

| Код помилки mbedTLS | Системна константа mbedTLS | Причина відмови та метод усунення |
| :--- | :--- | :--- |
| `-0x7080` (`-28800`) | `MBEDTLS_ERR_SSL_ALLOC_FAILED` | Помилка виділення пам'яті кучі. Необхідно зменшити MFLN у `AT+CIPSSLCCFG` до 1024/2048 або вимкнути верифікацію. |
| `-0x7780` (`-30592`) | `MBEDTLS_ERR_SSL_FATAL_ALERT_MESSAGE` | Сервер відхилив рукостискання (наприклад, через відсутність SNI). Налаштувати `AT+CIPSSLCSNI`. |
| `-0x2700` (`-9984`) | `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` | Сертифікат сервера не пройшов перевірку автентичності. Перевірити завантажений CA-сертифікат або системний час. |
| `-0x7280` (`-29312`) | `MBEDTLS_ERR_SSL_INVALID_RECORD` | Отримано некоректний або пошкоджений кадри TLS. Перевірити стабільність Wi-Fi зв'язку та налаштування порту. |

Діагностика кодів дозволяє точно встановити рівень збою — від апаратного дефіциту SRAM на [модулі ESP-01](root:cat-hw-boards/esp-01) до помилок у ланцюжку сертифікатів довіри.

Якщо рукостискання завершується критичною відмовою пам'яті чи фрагментацією динамічної купи, повторні спроби виклику `AT+CIPSTART` можуть зазнавати постійних невдач через залишкові об'єкти в оперативній пам'яті. У таких випадках для повного очищення системної купи та скидання криптографічних контекстів бібліотеки @@en|mbedTLS@@ застосовують виклик команди `AT+RST`. Після виконання процедури перезавантаження чипа прошивка наново ініціалізує мережевий стек @@en|LwIP@@, дефрагментує область @@en|SRAM@@ та повертає статус @@en|ready@@, що дає змогу повторно розпочати процедуру встановлення захищеного з'єднання з максимальним обсягом вільної пам'яті на [модулі ESP-01](root:cat-hw-boards/esp-01).
