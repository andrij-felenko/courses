## Обмеження DRAM та причини OOM при TLS

Під час розробки пристроїв на базі [ESP-01](root:cat-hw-boards/esp-01) звичайне оброблення даних через незашифровані [мережеві сокети TCP/UDP на модулі ESP-01](root:cat-hw-boards/esp01-tcp-udp-sockets) виконується стабільно. Однак спроба переходу на захищений протокол HTTPS або шифроване з'єднання за допомогою протоколу @@en|Transport Layer Security@@ (від англійського @@en|Transport Layer Security@@; @@en|TLS@@, де англійське @@en|security@@ означає безпеку) часто супроводжується миттєвим аварійним перезавантаженням мікроконтролера або спонтанною відмовою в наданні системних ресурсів з помилкою вичерпання пам'яті (англ. @@en|Out of Memory@@; @@en|OOM@@, де англійське @@en|memory@@ означає пам'ять).

Причина цього явища полягає у фізичному обмеженні внутрішньої пам'яті чипа. Згідно з матеріалом [Огляд мікроконтролера та архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview), весь обсяг оперативної пам'яті для даних (англ. @@en|Data Random-Access Memory@@; @@en|DRAM@@, де англійське @@en|random@@ означає довільний) становить лише 80 КБ. Після завантаження ядра операційної системи, ініціалізації драйверів Wi-Fi та виділення статичних буферів під системні змінні в розпорядженні користувача для динамічного виділення в купі (англ. @@en|heap@@) залишається від 36 КБ до 45 КБ вільного простору.

Згідно зі специфікацією TLS 1.2, максимальний розмір одного шифрованого кадру (англ. @@en|payload@@ — корисне навантаження) становить 16384 байтів (16 КБ). Для забезпечення обміну даними класичний криптографічний стек мусить одночасно утримувати в купі буфер приймача на 16 КБ, буфер передавача на 16 КБ, а також динамічні структури стану сесії. Окремим критичним піком споживання є обробка ланцюжка сертифікатів @@en|X.509@@ під час фази рукостискання: збереження, розбір парсером @@en|ASN.1@@ та перевірка 2–3 цифрових сертифікатів у ланцюжку (кореневий, проміжний та сертифікат домену) додає від 4 КБ до 8 КБ тимчасових витрат пам'яті `M_cert`. Додатковий сплеск споживання створює формування та збереження розпарсених таблиць відкритих розширень пакета @@en|ClientHello@@ (англ. @@en|TLS extensions@@, як-от @@en|SNI@@, @@en|ALPN@@, параметри еліптичних кривих та списки допустимих підписів): кешування дескрипторів розширень додає від 1.5 КБ до 2.5 КБ тимчасових алокацій у купі. Нарешті, накладні витрати створює підтримка кількох альтернативних наборів шифрів (англ. @@en|cipher suite@@ — набір шифрів). Зберігання та аналіз списку з `N_suites` наборів шифрів вимагає виділення пам'яті `M_ciphers = N_suites × S_suite` під таблиці функціональних покажчиків і описувачів алгоритмів:

```
M_ciphers = N_suites × S_suite
= 12 × 160           [при 12 альтернативних наборах шифрів по 160 байтів на дескриптор]
= 1920               [байтів]
```

Ураховуючи `M_ciphers ≈ 1.9` КБ для 12 наборів шифрів, сумарні вимоги щодо виділення пам'яті досягають 38–42 КБ, що критично перекриває наявний залишок DRAM (36–45 КБ) і гарантовано призводить до помилки OOM на етапі фази рукостискання (англ. @@en|handshake@@).

## Математична модель бюджету пам'яті mbedTLS

Для запобігання фатальним помилкам вичерпання пам'яті необхідно провести точний розрахунок загального бюджету DRAM `M_total`, який складається зі статичних витрат мережевого стека та динамічного споживання криптографічної бібліотеки mbedTLS.

Загальне споживання пам'яті `M_total` під час активної SSL/TLS сесії обчислюється як сума п'яти основних компонентів:

```
M_total = M_tcp + M_ctx + M_in + M_out + M_crypto
```

Де:
· `M_tcp` — обсяг пам'яті для кешування блоків керування протоколу @@en|Transmission Control Protocol@@ (від англійського @@en|Transmission Control Protocol@@; @@en|TCP@@) LwIP та кілець буферизації;
· `M_ctx` — статичний розмір системної структури керування сесією mbedTLS;
· `M_in` — розмір вхідного буфера кадрів з урахуванням службових заголовків;
· `M_out` — розмір вихідного буфера кадрів з урахуванням заголовочних даних та вирівнювання;
· `M_crypto` — тимчасова оперативна пам'ять для збереження ключів RSA/ECC та проміжних результатів криптографічних обчислень.

Розмір вхідного та вихідного буферів обчислюється на основі розміру корисного навантаження фрагмента `S_frag` з урахуванням апаратних накладних витрат заголовочних даних та вирівнювання блокового шифру @@en|AES-CBC@@ (від англ. @@en|Cipher Block Chaining@@ — зчеплення блоків шифру). Для блокового шифрування з розміром блока 16 байтів структура накладних витрат кадру `P_cipher` складається з явного вектора ініціалізації `IV = 16` байтів, хешу підпису `HMAC` та вирівнювального падінгу (англ. @@en|padding@@ — заповнення) до кратного 16-байтового рубежу, що сумарно додає `P_cipher = 29` байтів. Разом із 5 байтами апаратного заголовка запису @@en|TLS@@ загальний обсяг службових байтів визначається рівнянням:

```
M_in = S_frag_in + H_tls + P_cipher
= S_frag_in + 5 + 29                     [додавання 5 байтів заголовка TLS та 29 байтів MAC/padding]
= S_frag_in + 34                         [підсумковий розмір вхідного буфера в байтах]
```

Аналогічно обчислюється вихідний буфер: `M_out = S_frag_out + 34`.

Звівши сталі значення системних контекстів (`M_tcp ≈ 3.5` КБ, `M_ctx ≈ 3.2` КБ, `M_crypto ≈ 7.5` КБ), підставимо їх у загальне рівняння бюджету пам'яті (у кілобайтах). При повному @@en|TLS@@-рукостисканні (від англійського @@en|handshake@@) пікове споживання кучі обмежується тимчасовою виділеною пам'яттю `M_crypto ≈ 7.5` КБ для генерації асиметричних ключів @@en|RSA@@ або @@en|ECC@@:

```
M_total = M_tcp + M_ctx + M_in + M_out + M_crypto
= 3.5 + 3.2 + (S_frag_in + 34) / 1024 + (S_frag_out + 34) / 1024 + 7.5      [підстановка параметрів для повного рукостискання]
= 14.2 + (S_frag_in + S_frag_out) / 1024                                [зведення сталих величин]
```

Однак при використанні механізму сесійного відновлення (від англійського @@en|Session Resumption@@; через сесійні квитки @@en|Session Tickets@@ або ідентифікатор сесії @@en|Session ID@@) клієнт і сервер повторно застосовують раніше узгоджені симетричні ключі. Це дає змогу виконати скорочене рукостискання без обчислення асиметричної криптографії, завдяки чому тимчасові витрати падають до `M_crypto_resumed ≈ 0.0` КБ. Застосування зашифрованих сесійних квитків @@en|Session Tickets@@ передає збереження стану сесії клієнту у вигляді закриптографічного контейнера розміром `S_ticket ≈ 256` байтів (`0.25` КБ), усуваючи потребу у виділенні буфера сесійного кешу на боці сервера `M_cache ≈ 1.2` КБ. Алгебраїчна економія оперативної пам'яті `ΔM_ticket` обчислюється як різниця між піковими витратами повного рукостискання `M_crypto` та накладними витратами зберігання квитка `S_ticket`:

```
ΔM_ticket = M_crypto - (S_ticket / 1024)
= 7.5 - (256 / 1024)                    [підстановка пікових витрат криптографії 7.5 КБ та розміру квитка 256 байтів]
= 7.5 - 0.25                            [переведення байтів квитка у кілобайти]
= 7.25                                  [підсумкова економія кучі в кілобайтах]
```

Зняття навантаження з динамічної купи у розмірі `7.25` КБ дозволяє мікроконтролеру утримувати сесійний контекст у межах доступних `36–45` КБ @@en|DRAM@@ без ризику фатального розриву сокета.

```
M_total_resumed = M_tcp + M_ctx + M_in + M_out + M_crypto_resumed
= 3.5 + 3.2 + (S_frag_in + 34) / 1024 + (S_frag_out + 34) / 1024 + 0.0      [підстановка M_crypto ≈ 0 для скороченого рукостискання]
= 6.7 + (S_frag_in + S_frag_out) / 1024                                [зведення сталих величин при Session Resumption]
```

Порівняльний розрахунок показує, що виключення повторного фатального піка пам'яті за допомогою @@en|Session Resumption@@ економить `7.5` КБ оперативної пам'яті @@en|DRAM@@ під час ініціалізації з'єднання, знижуючи базову сталу складову з `14.2` КБ до `6.7` КБ.

```
M_total = M_tcp + M_ctx + M_in + M_out + M_crypto
= 3.5 + 3.2 + (S_frag_in + 34) / 1024 + (S_frag_out + 34) / 1024 + 7.5      [підстановка параметрів]
= 14.2 + (S_frag_in + S_frag_out) / 1024                                [зведення сталих величин]
```

![Схема розподілу DRAM кучі між LwIP TCP буферами, контекстом mbedTLS та вхідним/вихідним буферами кадру](img/esp8266-dram-tls-memory-allocation.svg)
*Розподіл DRAM кучі при встановленні TLS-з'єднання: перевищення наявного обсягу вільної пам'яті вимогами стандартного буфера 16 КБ.*

**Розрахунок бюджету для стандартного TLS-кадру 16 КБ:**

```
M_total = 14.2 + (16384 + 16384) / 1024      [підстановка S_frag_in = 16384 та S_frag_out = 16384]
= 14.2 + 32.0                                [обчислення розміру двох кадрів у кілобайтах]
= 46.2                                       [загальна потреба в пам'яті в кілобайтах]
```

Отримане значення `M_total = 46.2` КБ перевищує наявний обсяг вільної кучі (36–45 КБ), що аналітично доводить неможливість використання стандартних TLS-буферів без додаткових оптимізаційних механізмів.

## Оптимізація Max Fragment Length та розрахунок

Стандартна специфікація криптографічного протоколу передбачає максимальний розмір кадру 16384 байти (16 КБ), що приводить до дефіциту динамічної пам'яті @@en|DRAM@@ (від англійського @@en|Dynamic Random-Access Memory@@, де грецьке @@el|динамічний@@ означає силовий) у мікроконтролері. Для усунення цієї проблеми застосовують розширення протоколу @@en|Max Fragment Length@@ (від англійського @@en|maximum@@ — найбільший, @@en|fragment@@ — уривок, та @@en|length@@ — довжина; @@en|MFL@@), яке дозволяє узгодити менший розмір фрагмента `S_frag` між клієнтом та сервером. Стандарт описує фіксовані дискретні значення `S_frag`: 512, 1024, 2048 та 4096 байтів.

Загальне споживання кучі @@en|heap@@ (від англійського @@en|heap@@ — купа) для однієї шифрованої сесії `M_session` обчислюється як сума подвоєного розміру SSL-фрагмента з апаратними накладними витратами `H_tls` (512 байтів), системних буферів стеку @@en|LwIP@@ (від англійського @@en|Lightweight IP@@, де англійське @@en|lightweight@@ означає легковаговий) `M_tcp` (5760 байтів) та контексту криптографічної бібліотеки @@en|mbedTLS@@ `M_mbed` (4096 байтів):

```
M_session = 2 × (S_frag + H_tls) + M_tcp + M_mbed
```

**Обчислення витрат кучі для розміру фрагмента MFL 2048 байтів:**

```
M_session = 2 × (2048 + 512) + 5760 + 4096
= 2 × 2560 + 5760 + 4096                [додавання накладних витрат кадру]
= 5120 + 5760 + 4096                    [подвоєння для вхідного та вихідного буферів]
= 14976                                 [байтів]
```

Порівняльний розрахунок показує, що при скороченні `S_frag` з 4096 байтів (`M_session = 19072` байти) до 512 байтів (`M_session = 11904` байти) виграш вільної кучі становить 7168 байтів (7.1 КБ).

![Графік залежності доступного залишку вільної кучі від обраного розміру фрагмента MFL (512, 1024, 2048, 4096 байтів).](img/esp8266-mfl-vs-heap-consumption-chart.svg)
*Залежність вільного залишку кучі DRAM від обраного параметра Max Fragment Length (MFL).*

Значне зменшення розміру фрагмента вивільняє ресурси пам'яті, що дозволяє відкривати кілька паралельних шифрованих з'єднань на [мережевих сокетах TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets). Гранична кількість паралельних сесій `N_max` при доступному обсязі кучі `M_heap = 36864` байти (36 КБ) обчислюється округленням до меншого цілого:

```
N_max = ⌊ M_heap / M_session ⌋
```

**Обчислення максимальної кількості SSL-сесій при MFL 512 байтів:**

```
N_max = ⌊ 36864 / 11904 ⌋
= ⌊ 3.096 ⌋                             [ділення доступного обсягу на витрати сесії]
= 3                                     [паралельні сесії]
```

Вибір `S_frag = 512` байтів дає змогу утримувати до 3 сесій поспіль, однак збільшує накладні витрати передачі корисного навантаження @@en|payload@@ (від англійського @@en|payload@@ — корисне навантаження) через частішу передачу криптографічних заголовків.

Зменшення `S_frag` призводить до додаткових втрат ефективної смуги передачі (англ. @@en|throughput penalty@@, від *throughput* — пропускна здатність та *penalty* — втрата, штраф; @@en|втрата пропускної здатності throughput penalty@@) через відносне зростання частки фіксованого заголовка кадру `H_hdr = 29` байтів (заголовок запису TLS, вектори ініціалізації та MAC-автентифікація). Ефективна частка корисного навантаження в кадрі `η` визначається відношенням `S_frag` до повного розміру TLS-запису `S_frag + H_hdr`. Окрім того, поділ корисного навантаження на малі фрагменти суттєво збільшує загальну кількість пакетів, що на нестабільних Wi-Fi з'єднаннях призводить до частіших повторних передач (англ. @@en|TCP retransmission@@, від *re-* — повторно та *transmission* — передача; @@en|повторна передача TCP retransmission@@). Кожна повторна спроба надсилання малогабаритного кадру змушує знову передавати повний комплект заголовків, що додатково перевантажує мережевий канал і погіршує його продуктивність.

Обчислення втрати пропускної здатності для розширення MFL 512 байтів:

```
P_penalty = 1 - (S_frag / (S_frag + H_hdr))
= 1 - (512 / (512 + 29))                [підстановка розміру фрагмента та заголовка]
= 1 - (512 / 541)                       [обчислення загального розміру TLS-кадру]
≈ 1 - 0.9464                            [обчислення частки корисного навантаження]
= 0.0536                                [або 5.36% накладних витрат]
```

Порівняно з масивними фрагментами 4096 байтів, де накладні витрати становлять лише 0.70% (`P_penalty = 0.0070`), використання значення 512 байтів знижує корисну швидкість передачі даних на 5.36%, що є ціною за можливість підтримки трьох одночасних з'єднань у рамках обмеженої кучі [SoC ESP8266EX](root:cat-hw-boards/esp8266-soc-architecture-overview).

Порівняно з масивними фрагментами 4096 байтів, де накладні витрати становлять лише 0.70% (`P_penalty = 0.0070`), використання значення 512 байтів знижує корисну швидкість передачі даних на 5.36%, що є ціною за можливість підтримки трьох одночасних з'єднань у рамках обмеженої кучі [SoC ESP8266EX](root:cat-hw-boards/esp8266-soc-architecture-overview). Для аналітичної оцінки підсумкової пропускної здатності каналу `R_eff` відносно номінальної фізичної швидкості лінії `R_raw` використовують формулу масштабування з урахуванням втрати пропускної здатності (англ. @@en|throughput penalty@@, від *throughput* — пропускна здатність та *penalty* — втрата, штраф; @@en|втрата пропускної здатності throughput penalty@@):

```
R_eff = R_raw × (1 - P_penalty)
= R_raw × (1 - 0.0536)                  [підстановка штрафу накладних витрат MFL 512]
= 0.9464 × R_raw                        [коефіцієнт корисного використання фізичного каналу]
```

Таким чином, при номінальній швидкості послідовного порту `R_raw = 115200` бод реальна пропускна здатність передачі корисних даних становитиме лише `R_eff = 115200 × 0.9464 ≈ 109025` бод, що показує неминучу втрату 6175 бод на службовий оверхед при збереженні стабільності оперативної пам'яті.

## Межа вичерпання кучі та запобігання помилкам

Навіть якщо розраховане значення `M_session` є меншим за загальний вільний обсяг пам'яті, пристрій може раптово зазнати аварійного перезавантаження через помилку @@en|Out of Memory@@ (від англійського @@en|out@@ — поза, та @@en|memory@@ — пам'ять; @@en|OOM@@). Головною причиною таких збоїв є динамічна фрагментація кучі під час процедури рукостискання @@en|handshake@@ (від англійського @@en|handshake@@ — рукостискання), коли система виділяє й звільняє тимчасові блоки для парсингу ключів @@en|RSA@@ (від прізвищ розробників @@en|Rivest-Shamir-Adleman@@) та арифметики великих чисел @@en|BigNum@@ (від англійського @@en|big number@@ — велике число).

Коефіцієнт фрагментації пам'яті `F_heap` визначає відношення найбільшого суцільного блоку `S_block_max` до загальної вільної кучі `M_free`. Суттєвий вплив на вільний простір має розмір ключів @@en|RSA@@ (від прізвищ розробників @@en|Rivest-Shamir-Adleman@@), який безпосередньо масштабує пікові витрати обчислювального буфера `M_bignum` під час виконання модульного піднесення до степеня над багаторозрядними числами у криптографічному стеку @@en|mbedTLS@@. Для ключа @@en|RSA-2048@@ кожен об'єкт `BigNum` потребує `2048 ÷ 8 = 256` байтів під розряди та `32` байти під дескриптор, що при виділенні 6–8 тимчасових структур дає `M_bignum(RSA-2048) ≈ 2048` байтів (2 КБ). Використання ж ключів @@en|RSA-4096@@ подвоює розмір числа до `4096 ÷ 8 = 512` байтів, збільшуючи обсяг математичного буфера до `M_bignum(RSA-4096) ≈ 4096–6144` байтів (4–6 КБ) і додатково виїдаючи з `M_free` 2–4 КБ кучі безпосередньо в момент обчислень рукостискання. Математична модель відновлення кучі при послідовному звільненні тимчасових буферів `S_free_i` визначає новий максимальний суцільний блок `S_block_max_new = S_free_adj + S_free_i` лише за умови апаратної суміжності з сусіднім вільним блоком `S_free_adj`; якщо ж між звільненими масивами `mbedTLS` утримуються дрібні мережеві дескриптори `pbuf`, злиття блоків блокується, через що коефіціент `F_heap_new = 1 - (S_block_max_new ÷ M_free_new)` залишається високим навіть при зростанні загальної вільної пам'яті. Математичний механізм такого вилучення полягає у тому, що під час мережевої активності драйвери з'єднань стеку @@en|LwIP@@ асинхронно виділяють точкові дрібні масиви `S_lwip` (32–128 байтів) під дескриптори пакетів та структури керування сокетами в проміжках між великогабаритними блоками `mbedTLS`. Утворювана топологія пам'яті розбиває вихідний неперервний інтервал `S_block_max` на підмножину розсічених суцільних відрізків `S_span_k < S_block_max`, де найбільший доступний елемент визначається як `S_block_max_new = max(S_span_k)`. Оскільки неперервна вибірка `S_alloc` вимагає єдиного суцільного масиву, вилучення навіть одного дрібного блоку `S_lwip` посередині суцільного простору фіксує верхню межу `S_block_max_new` на рівні найдовшого з утворених залишків, що викликає штучний дефіцит неперервної пам'яті та прискорює зростання `F_heap`.

```
F_heap = 1 - (S_block_max / M_free)
```

Критична умова виникнення помилки `OOM` настає тоді, коли розмір чергової динамічної вибірки пам'яті `S_alloc` перевищує максимальний суцільний блок, тобто `S_alloc > S_block_max`. Для запобігання фатальним помилкам розраховують запас безпеки кучі `M_margin` (від латинського @@en|margo@@ — край, межа):

```
M_margin = M_free - M_handshake_peak
```

Де `M_handshake_peak = M_session + M_cert_parse + M_bignum` — пікове споживання пам'яті під час перевірки сертифіката сервера (`M_cert_parse ≈ 4096` байтів, `M_bignum ≈ 2048` байтів).

**Розрахунок запасу безпеки при вільній кучі 36 КБ та MFL 2048 байтів:**

```
M_margin = 36864 - (14976 + 4096 + 2048)
= 36864 - 21120                         [обчислення пікового навантаження рукостискання]
= 15744                                 [байтів]
```

Отриманий запас `M_margin = 15744` байтів (15.3 КБ) перевищує мінімальний технологічний допуск `M_margin_min = 8192` байти (8 КБ), що гарантує стабільну роботу на [платах ESP-01S](root:cat-hw-boards/esp-01s) без ризику `OOM`. Для забезпечення надійності в [архітектурі SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) рекомендовано зафіксувати `S_frag ≤ 2048` байтів та обмежити максимальну глибину ланцюжка сертифікатів.
