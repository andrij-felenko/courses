## Принципи підсистеми SSL в AT-прошивці

При розробці бездротових пристроїв відкрита передача даних у [TCP/UDP сокетах](root:cat-hw-boards/esp01-tcp-udp-sockets) створює загрозу перехоплення та підміни трафіку. Для захисту мережевого обміну у прошивці Espressif AT реалізовано підсистему шифрування на базі компактної криптографічної бібліотеки @@en|mbedTLS@@ (від англійського @@en|embedded Transport Layer Security@@, де *embedded* — вбудований, та *security* — безпека; @@en|криптографічний стек mbedTLS@@), інтегрованої із мережевим стеком @@en|LwIP@@ (англ. @@en|Lightweight IP@@). Цей шар забезпечує шифрування каналу за протоколами @@en|SSL/TLS@@ (від англійського @@en|Secure Sockets Layer / Transport Layer Security@@; @@en|криптографічні протоколи SSL/TLS@@) під час роботи з HTTPS-серверами та захищеними MQTT-брокерами.

![Схема взаємодії шару AT-команд, стека mbedTLS, LwIP та Flash-пам'яті сертифікатів у прошивці ESP8266.](img/esp8266-at-ssl-subsystem-architecture-diagram.svg)
*Схема взаємодії шару AT-команд, криптографічної бібліотеки mbedTLS, мережевого стека LwIP та Flash-пам'яті сертифікатів у мікроконтролері ESP8266.*

Встановлення шифрованого з'єднання вимагає суттєвих ресурсів оперативної пам'яті @@en|DRAM@@ (англ. @@en|Dynamic Random-Access Memory@@). Під час рукостискання TLS криптографічний стек виділяє динамічні буфери введення-виведення розміром від 2 до 16 КБ для обробки фрагментів записів, збереження сесійних ключів та декодування сертифікатів. На компактних [модулях ESP-01](root:cat-hw-boards/esp-01) із початковим обсягом вільної купи `M_free_initial ≈ 28` КБ спроба виділити стандартні буфери прийому `B_rx = 16` КБ, передачі `B_tx = 16` КБ та контексту сесії `M_ctx ≈ 8` КБ вимагає сумарно `M_req = B_rx + B_tx + M_ctx = 16 + 16 + 8 = 40` КБ пам'яті. Оскільки потрібний обсяг `M_req = 40` КБ перевищує наявний запас `28` КБ, спроба `malloc` повертає помилку вичерпання купи, що спричиняє аварійне скидання сокета. Зменшення розміру фрагмента до 4 КБ за допомогою попередньої конфігурації знижує запит до `M_req_tuned = 4 + 4 + 8 = 16` КБ, залишаючи у купі не менше `M_free_rem = 28 - 16 = 12` КБ вільного простору для стабільного функціонування стека. З цієї причини підсистема SSL вимагає чіткого попереднього налаштування параметрів шифрування до моменту виклику команд встановлення з'єднання.

Ключовою передумовою для генерації криптографічних ключів та унікальних векторів ініціалізації є отримання стійких випадкових даних. Криптографічний стек `@@en|mbedTLS@@` задіює апаратний генератор випадкових чисел (англ. *True Random Number Generator*, `@@en|TRNG@@` — справжній генератор випадкових чисел), який у мікроконтролері ESP8266 формує ентропію (від грец. @@el|ἐντροπία@@ — зворотність; `@@en|entropy source@@` — джерело ентропії) шляхом зчитування шуму з фізичного радіочастотного модуля Wi-Fi. Під час ініціалізації сесії стек збирає випадкові байти для первинного посіву псевдовипадкової послідовності. Для гарантії надійності ключового обміну підсистема AT-команд автоматично підтримує активність радіотракту під час виклику криптографічних процедур: якщо Wi-Fi модуль перебуває у стані зниженого енергоспоживання, перед запуском `@@en|TLS-рукостискання@@` підсистема короткочасно активує фонове аналогове зчитування RF-шуму, запобігаючи збоям заповнення буфера ентропії та забезпечуючи математичну непередбачуваність згенерованих шифрувальних ключів.

![Карта розподілу секторів Flash-пам'яті для збереження кореневих сертифікатів CA, клієнтських сертифікатів та RSA-ключів.](img/flash-memory-map-for-ssl-certificates.svg)
*Розподіл фізичних секторів Flash-пам'яті для зберігання SSL-сертифікатів та криптографічних ключів.*

Для перевірки автентичності вузлів прошивка використовує кореневі сертифікати центру сертифікації @@en|CA@@ (англ. @@en|Certificate Authority@@), клієнтські сертифікати та приватні ключі @@en|RSA/ECC@@, які заздалегідь прошиваються у виділені фізичні сектори Flash-пам'яті. У стандартній карті пам'яті (англ. @@en|Flash memory map@@) AT-прошивки під захищені дані виділяються фіксовані блоки розміром по 4 КБ: два сектори (8 КБ) відводяться під списки довірених сертифікатів CA, два сектори (8 КБ) — під клієнтський сертифікат та ще два сектори (8 КБ) — під приватний ключ, що утворює сумарний криптографічний розділ обсягом 24 КБ. Під час ініціалізації з'єднання внутрішні механізми [архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview) та стек @@en|mbedTLS@@ зчитують структури сертифікатів безпосередньо з фізичних адрес Flash через пряме відображення пам'яті, формуючи сесійний контекст (англ. @@en|session context@@) лише з покажчиків і мінімальних хеш-сум та запобігаючи виділенню громіздких масивів під сирі криптографічні дані у RAM. Водночас обробка потоку даних наражається на апаратні обмеження мікроконтролера, який позбавлений виділених блоків прискорення симетричного шифрування @@en|AES@@ (англ. @@en|Advanced Encryption Standard@@, від *advanced* — розширений, *encryption* — шифрування, та *standard* — стандарт; @@en|симетричний шифр AES@@) та обчислення криптографічних хеш-функцій @@en|SHA@@ (англ. @@en|Secure Hash Algorithm@@, від *secure* — безпечний, *hash* — хеш, та *algorithm* — алгоритм; @@en|алгоритм хешування SHA@@). Через це стек @@en|mbedTLS@@ виконує кодування блоків і перевірку цілісності суто програмним шляхом на процесорному ядрі, що створює значне обчислювальне навантаження та обмежує граничну пропускну здатність шифрованого каналу.

## Команди налаштування параметрів SSL та SNI

Конфігурування режимів автентифікації та джерела сертифікатів здійснюється інструкцією `AT+CIPSSLCCONF`. Вона визначає правила перевірки підписів та тип використаних ключів до ініціалізації мережевої сесії:

```
AT+CIPSSLCCONF=<auth_mode>[,<path_type>]
```

Параметр `<auth_mode>` задає рівень перевірки: `0` вимикає валідацію сертифіката сервера (режим без перевірки), `1` вмикає односторонню автентифікацію сервера за кореневим сертифікатом CA, `2` активує автентифікацію клієнта на сервері, а `3` встановлює двосторонню взаємну автентифікацію (англ. @@en|mutual authentication@@). Параметр `<path_type>` вказує на джерело сертифікатів: `0` для читання із зарезервованої Flash-зони або `1` для динамічно завантажених даних. У розширеному синтаксисі `AT+CIPSSLCCONF=<auth_mode>[,<path_type>][,<buffer_len>]` третій параметр `<buffer_len>` дозволяє явно задати максимальний розмір фрагмента буфера записів SSL (англ. @@en|SSL record buffer@@) у діапазоні від 2048 до 4096 байтів (за замовчуванням `4096`). Обмеження цього значення зменшує розмір динамічних масивів, які mbedTLS виділяє під час обробки криптографічних кадрів, що критично для збереження вільної купи. При успішному застосуванні параметрів модуль повертає `OK`, а при передачі недопустимих значень або некоректній кількості аргументів — `ERROR`. Якщо ж під час узгодження параметрів сесії у відповіді на стартовий пакет @@en|ClientHello@@ віддалений сервер вимагає непідтримувані криптографічні шифрувальні набори (англ. @@en|cipher suites@@, від *cipher* — шифр та *suite* — набір) або алгоритми з ключами понад 128 біт, вилучені з прошивки ESP8266 заради економії пам'яті, стек mbedTLS перериває рукостискання з кодом фатального сповіщення `handshake failure` (`-0x7180` MBEDTLS_ERR_SSL_NO_CIPHER_MATCH) та автоматично закриває сокет з виводом `ERROR`.

![Послідовна діаграма викликів AT-команд від AT+CIPSSLCCONF до AT+CIPSTART та AT+CIPSEND із відображенням стадій TLS-рукостискання.](img/at-ssl-connection-handshake-sequence-chart.svg)
*Послідовність виконання AT-команд під час ініціалізації та встановлення шифрованого з'єднання TLS.*

Для встановлення SSL-з'єднань із віртуальними серверами, де на одній IP-адресі розміщено кілька доменів, застосовується команда передачі імені хоста `AT+CIPSSLCSNI` (англ. @@en|Server Name Indication@@, від *server* — сервер, *name* — ім'я та *indication* — вказування; @@en|розширення імені сервера SNI@@):

Крім базових параметрів автентифікації та буферизації, інструкція `AT+CIPSSLCCONF` підтримує додавання додаткових аргументів для звуження списку дозволених шифрувальних наборів (англ. @@en|cipher suites@@): `AT+CIPSSLCCONF=<auth_mode>,<path_type>,<buffer_len>[,<cipher_suite>]`. Параметр `<cipher_suite>` приймає шістнадцятковий ідентифікатор шифру (наприклад, `0xC02F` для `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`) або декілька комбінацій через кому, що дозволяє примусово обмежити списки криптографічних алгоритмів у пакеті @@en|ClientHello@@. Тонке налаштування переліку дозволених шифрів запобігає виділенню додаткової пам'яті під непріоритетні алгоритми та виключає ресурсомісткі шифри з 4096-бітними ключами, спрощуючи фазу рукостискання на модулях із обмеженим обсягом динамічної купи, таких як [модулях серії ESP-01](root:cat-hw-boards/esp-01). Особливої уваги добір наборів шифрів вимагає при переході на сертифікати криптографії еліптичних кривих @@en|ECC@@ (англ. @@en|ECC@@, від *elliptic curve cryptography* — криптографія на еліптичних кривих; @@en|криптографія на еліптичних кривих ECC@@) та підписи @@en|ECDSA@@ (англ. @@en|ECDSA@@, від *elliptic curve digital signature algorithm* — алгоритм цифрового підпису на еліптичних кривих; @@en|алгоритм цифрового підпису ECDSA@@). У такому разі у параметрі `<cipher_suite>` необхідно явно вказувати ідентифікатори шифрів із перевіркою підпису на еліптичних кривих (наприклад, `0xC02B` для `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` замість RSA-комбінацій). Використання ключів ECDSA довжиною 256 біт дає еквівалентний 3072-бітному RSA рівень захисту при суттєво меншому розмірі сесійного контексту mbedTLS, однак помилковий вибір RSA-шифрів для ECC-сертифіката унеможливлює узгодження параметрів і призводить до відмови рукостискання.

```
AT+CIPSSLCSNI=<link_ID>,"<host_name>"
```

Параметр `<link_ID>` визначає номер сокета у мульти-підключенні (від `0` до `4`), а `<host_name>` містить текстовий домен (наприклад, `"api.example.com"`). Ця команда змушує стек mbedTLS додавати розширення SNI у стартовий пакет @@en|ClientHello@@, дозволяючи віддаленому серверу вибрати правильний SSL-сертифікат на етапі рукостискання. Якщо доменне ім'я перевищує допустиму довжину буфера або містить заборонені символи, модуль видає відповідь `ERROR`.

## Завантаження сертифікатів та приватних ключів

Для виконання двосторонньої автентифікації підсистема шифрування вимагає наявності сертифіката клієнта та приватного ключа. Оскільки збереження сертифікатів у файловій системі споживає дефіцитну оперативну пам'ять, прошивка ESP8266 виділяє окремі фізичні сектори Flash-пам'яті для зберігання бінарних структур під час [оновлення прошивки ESP-01](root:cat-hw-boards/esp01-firmware-flashing). Запис криптографічних даних у призначені сектори здійснюється інструкцією робіт із пам'яттю `AT+SYSFLASH`:

```
AT+SYSFLASH=<operation>,<partition_name>,<offset>,<length>
```

Параметр `<operation>` набуває значення `0` для зчитування або `1` для запису, `<partition_name>` вказує назву розділу (наприклад, `"client_ca"`, `"client_cert"` або `"client_key"`), `<offset>` задає зсув від початку розділу, а `<length>` — розмір масиву в байтах. Для підготовки текстових сертифікатів у форматі @@en|PEM@@ (англ. @@en|Privacy-Enhanced Mail@@, від *privacy* — приватність, *enhanced* — розширений та *mail* — пошта) до запису у Flash їх заздалегідь конвертують у компактну бінарну структуру @@en|DER@@ (англ. @@en|Distinguished Encoding Rules@@, від *distinguished* — розрізнений, *encoding* — кодування та *rules* — правила). Процедура конвертації вимагає видалення текстових заголовків `-----BEGIN CERTIFICATE-----` та `-----END CERTIFICATE-----`, очищення символів переведення рядків та декодування кодованого @@en|Base64@@-тексту у сирий байтовий масив @@en|ASN.1@@, що зменшує розмір криптографічного файла приблизно на 25–33% і позбавляє прошивку накладних витрат на текстовий парсинг. Після отримання від модуля символу-запрошення `>` підготовлений бінарний потік у форматі @@en|DER@@ передається по послідовній шині байт за байтом. Для гарантії цілісності завантаженої структури хост виконує контрольне зчитування інструкцією `AT+SYSFLASH=0,<partition_name>,0,<length>` та покроково перевіряє заголовки кодування @@en|TLV@@ (англ. @@en|Type-Length-Value@@, від *type* — тип, *length* — довжина та *value* — значення): перший байт мусить відповідати тегу послідовності `0x30`, а наступні байти довжини — точній кількості зчитаних байтів. Якщо перевірка виявляє розходження заголовочних октетів або команда запису повертає `ERROR` через збій шини @@en|UART@@ чи пошкодження секторів пам'яті, запускається процедура відновлення: хост повторно перезаписує розділ зсувом 0, передаючи нульовий масив або заново ініціалізує запис `AT+SYSFLASH=1,<partition_name>,0,<length>` для повного заміщення пошкодженого блоку свіжим байтовим потоком.

Для прив'язки завантажених у Flash сертифікатів до конкретного мережевого контексту використовується комбінація вказаних розділів із налаштуваннями `AT+CIPSSLCCONF`. Якщо бінарний ключ @@en|RSA@@ має пошкоджену структуру або розмір Flash-розділу менший за довжину сертифіката, команда запису повертає `ERROR`, а подальше встановлення сокета зупиняється на стадії перевірки ключів.

При роботі з мережевими вузлами, чиї сертифікати підписані проміжними центрами сертифікації, виникає потреба збереження цілісного ланцюжка сертифікатів (англ. @@en|certificate chain@@, від *certificate* — сертифікат та *chain* — ланцюг; @@en|ланцюжок сертифікатів CA@@). Для пакування кількох проміжних сертифікатів Центру Автентифікації (англ. @@en|Certificate Authority@@, @@en|CA@@) в єдиний розділ Flash-пам'яті кожен сертифікат ланцюжка спочатку окремо конвертують із текстового формату в бінарне кодування @@en|DER@@. Отримані байтові масиви об'єднуються у єдиний послідовний файл шляхом конкатенації без міжсекційних розділювачів чи заповнювальних байтів. Під час ініціалізації SSL-контексту стек @@en|mbedTLS@@ почергово зчитує бінарний масив із Flash, послідовно розбираючи структури @@en|ASN.1@@ від кореневого до проміжного сертифіката, що дозволяє успішно валідувати підписи віддалених серверів без додаткових витрат оперативної пам'яті на [модулях серії ESP-01](root:cat-hw-boards/esp-01).

## Встановлення захищених сокетів та обмін

Після завершення конфігурування шифрувальних параметрів та завантаження сертифікатів модуль ініціює з'єднання із закладеними правилами безпеки. Відкриття захищеного сокета здійснюється командним викликом `AT+CIPSTART` із вказуванням типу протоколу `"SSL"`:

```
AT+CIPSTART=<link_ID>,"SSL","<remote_host>",<remote_port>[,<keep_alive>]
```

Параметри `<remote_host>` та `<remote_port>` вказують на адресу HTTPS-сервера або порт MQTTS-брокера (типово 8883). Після відправки команди стек підсистеми розпочинає фазу TLS-рукостискання. У разі успішного узгодження шифрів та перевірки підписів модуль відповідає `CONNECT` та `OK`. При збоях автентифікації або невідповідності алгоритмів шифрування видається повідомлення `+CIPSTART:ERROR` з наступним закриттям каналу `CLOSED`.

Передача шифрованих даних виконується інструкцією `AT+CIPSEND`:

```
AT+CIPSEND=<link_ID>,<length>
```

Після відправки команди хост очікує символ підтвердження `>` та передає корисне навантаження заданої довжини `<length>`. Підсистема шифрування автоматично розбиває масив на SSL-фрагменти, обчислює контрольні коди @@en|MAC@@ (англ. @@en|Message Authentication Code@@) та надсилає їх через [мережеві сокети TCP/UDP](root:cat-hw-boards/esp01-tcp-udp-sockets).

Для неперервного потокового обміну без необхідності вказування довжини кожного кадру застосовується наскрізний режим (англ. @@en|passthrough mode@@, від *pass* — проходити, *through* — наскрізь; @@en|наскрізний режим passthrough mode@@). Він вмикається командою `AT+CIPMODE=1` до виклику `AT+CIPSTART`. У цьому режимі всі дані з послідовного порту напряму шифруються та надсилаються в сокет до отримання комбінації виходу `+++`. Для штатного виходу з наскрізного режиму без розриву з'єднання управляючий хост мусить виконати чіткий таймінговий алгоритм: витримати паузу тиші тривалістю щонайменше 1 секунду (1000 мс) без передачі жодного байта через @@en|UART@@, відправити три послідовні символи `+++` без термінуючої послідовності `\r\n`, а потім витримати ще одну 1-секундну паузу тиші. Передавання будь-яких символів під час захисних інтервалів порушує розпізнавання виходу, і модуль сприймає `+++` як звичайні корисні дані, шифруючи їх для відправки в мережу. Під час тривалих пауз у передачі даних для запобігання мовчазному розриву шифрованої сесії мережевими маршрутизаторами задіюється механізм підтримки активності (англ. @@en|keep-alive@@, від *keep* — тримати та *alive* — живим; @@en|пакети підтримки активності keep-alive@@). При заданні опціонального параметра `<keep_alive>` у команді `AT+CIPSTART` стек @@en|LwIP@@ апаратно надсилає фонові зондувальні пакети TCP з інтервалом від 1 до 7200 секунд; якщо віддалений HTTPS-сервер чи MQTT-брокер не відповідає підтвердженням за встановлений таймаут, стек автоматично завершує TLS-сесію, виходить із наскрізного режиму та сповіщає хост повідомленням `CLOSED`. Після такого обриву зв'язку апаратний контекст @@en|mbedTLS@@ та кеш ключів очищаються, тому відновлення обміну потребує процедури повторної ініціалізації: хост переводить стек у командний режим інструкцією `AT+CIPMODE=0`, скидає внутрішній стан сокета та заново виконує повний цикл ініціалізації через `AT+CIPSTART="SSL",...` для проведення свіжого @@en|TLS-рукостискання@@.

При раптовому погіршенні радіозв'язку чи розриві мережевої сесії під час роботи у наскрізному режимі критично важливим є захист від втрати даних у буфері послідовного порту, що досягається активацією апаратного керування потоком @@en|CTS/RTS@@ (англ. @@en|Clear to Send / Request to Send@@). Коли стек @@en|LwIP@@ призупиняє відправку каскадів TLS-пакетів через затримки підтверджень у мережі, внутрішній приймальний буфер @@en|UART@@ модуля швидко заповнюється. За наявності апаратного зв'язку лінія @@en|RTS@@ апаратно піднімається в високий логічний рівень, примусово зупиняючи передачу з боку зовнішнього мікроконтролера та запобігаючи переповненню шини до моменту закриття сокета чи відновлення обміну на [модулях серії ESP-01](root:cat-hw-boards/esp-01).

## Коди помилок mbedTLS та діагностика

Під час встановлення захищеного з'єднання рукостискання @@en|Handshake@@ (з англ. handshake — рукостискання) криптографічний стек @@en|mbedTLS@@ може повертати від'ємні шістнадцяткові коди помилок у разі відмови авторизації або дефіциту ресурсів пам'яті. Розшифровка цих кодів дозволяє точно встановити причину збою без підключення зовнішнього відлагоджувальника.

Найчастіші коди помилок підсистеми @@en|SSL/TLS@@ та методи їх усунення наведені в таблиці. При цьому критичною передумовою для запобігання хибному спрацюванню помилки `-0x2700` (`MBEDTLS_ERR_X509_CERT_VERIFY_FAILED`) є попереднє налаштування точного системного часу. Після апаратного скидання мікроконтролер не має збереженої часової мітки та за замовчуванням ініціалізує годинник з нульової епохи Unix (1 січня 1970 року), через що криптографічний стек відхиляє будь-які сучасні сертифікати як прострочені або ще не дійсні. Для автоматичної синхронізації часу перед встановленням з'єднання виконують процедуру конфігурації протоколу `@@en|SNTP@@` (від англ. *Simple Network Time Protocol* — простий мережевий протокол часу; `@@en|SNTP@@`) за допомогою команди `AT+CIPSNTPCFG=1,2,"pool.ntp.org"`, що забезпечує коректну перевірку атрибутів `notBefore` та `notAfter` у ланцюжку сертифікатів `@@en|CA@@`.

| Код помилки | Константа mbedTLS | Причина відмови | Метод вирішення |
| :--- | :--- | :--- | :--- |
| `-0x2700` | `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` | Помилка перевірки ланцюжка сертифікатів @@en|CA@@ | Перевірити актуальність часової мітки системи, відповідність імені хоста та цілісність завантаженого кореневого сертифіката. |
| `-0x7200` | `MBEDTLS_ERR_SSL_ALLOC_FAILED` | Вичерпання динамічної купи @@en|DRAM@@ під час алокації буферів | Зменшити розмір фрагмента фрагментації записів або вивантажити невикористовувані мережеві сокети. |
| `-0x7780` | `MBEDTLS_ERR_SSL_FATAL_ALERT_MESSAGE` | Фатальне сповіщення від сервера (англ. @@en|fatal alert@@) | Звірити підтримувані набори шифрів (англ. @@en|cipher suites@@) та версії протоколу TLS. |
| `-0x7080` | `MBEDTLS_ERR_SSL_CANNOT_READ_RECORD` | Помилка зчитування записи шифрованого кадру | Перевірити стабільність фізичного зв'язку та розміри вхідного буфера зчитування. |

Основною апаратною проблемою модуля [ESP-01](root:cat-hw-boards/esp-01) при роботі з @@en|mbedTLS@@ є обчислювальний дефіцит оперативної пам'яті на [архітектурі ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). Якщо розмір вхідного шифрованого кадру сервера перевищує доступний обсяг вільної купи, виникає помилка `-0x7200`. При виникненні цього збою розробник реалізує алгоритм динамічної адаптації: після фіксації відмови `-0x7200` хост-контролер закриває поточну сесію інструкцією `AT+CIPCLOSE`, після чого викликає команду зменшення розміру SSL-фрагмента `AT+CIPSSLCCONF=0,2048` (знижуючи ліміт буфера з 4096 до 2048 або 1024 байтів) і виконує повторне підключення через `AT+CIPSTART`. Для гарантії стабільності рукостискання слід також закривати незадіяні некриптовані сокети перед викликом ініціалізації з'єднання, вивільняючи додаткові байти купи DRAM.

У ситуаціях критичної фрагментації динамічної купи, коли тривала робота системи не дозволяє виділити суцільний блок пам'яті понад 2 КБ, застосовують граничне обмеження буфера інструкцією `AT+CIPSSLCCONF=0,1024`. Налаштування параметра буферизації на рівень 1024 байти зменшує вимоги до неперервного блоку @@en|DRAM@@ під час обробки шифрованих записів з 4.5 КБ до 1.5 КБ, дозволяючи провести рукостискання навіть при високій розрізненості пам'яті. Проте використання ліміту 1024 байти вимагає обов'язкової підтримки віддаленим HTTPS-сервером розширення узгодження максимальної довжини фрагмента (англ. @@en|Maximum Fragment Length Negotiation@@, @@en|MFLN@@): якщо сервер не підтримує розширення @@en|MFLN@@ та надсилає кадр стандартного розміру 4096 байтів, стек @@en|mbedTLS@@ перериває сесію з кодом `-0x7080` (`MBEDTLS_ERR_SSL_CANNOT_READ_RECORD`), що слід враховувати під час розробки надійних пристроїв на базі [SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview).
