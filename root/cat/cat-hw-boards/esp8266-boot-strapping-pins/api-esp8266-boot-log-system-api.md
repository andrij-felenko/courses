## Проблема невизначеності причин перезавантаження ESP8266

Під час розробки та експлуатації систем на базі [модуля ESP-01](root:cat-hw-boards/esp-01) розробники регулярно зустрічаються з ситуацією, коли мікроконтролер раптово перезавантажується або потрапляє в безкінечний аварійний цикл перезапусків (англ. *@@en|reboot loop@@* — цикл перезавантажень). Зовнішні прояви таких збоїв абсолютно однакові: зв'язок переривається, а пристрій перестає реагувати на зовнішні команди. Проте фізична причина відмови може критися в одному з двох протилежних рівнів: апаратному або програмному. До апаратних причин належать просідання напруги живлення, імпульсні перешкоди на виводі скидання `RST` або некоректні логічні рівні на виводах вибору режиму старту. До програмних причин — звернення за нульовим вказівником, переповнення стека або блокування головного потоку, яке викликає спрацьовування сторожового таймера @@en|watchdog@@ (від англ. *@@en|watchdog timer@@* — сторожовий таймер).

Діагностика таких станів ускладнюється особливістю первинного завантажувача, зашитого у внутрішню постійну пам'ять @@en|ROM@@ (від англ. *@@en|Read-Only Memory@@* — постійний запам'ятовувальний пристрій) [архітектури SoC ESP8266](root:cat-hw-boards/esp8266-soc-architecture-overview). Відразу після подачі живлення або скидання процесорний сердечник починає виконання базового коду ROM, який тактується від опорного кварцового резонатора частотою 26 МГц. При цьому апаратний модуль @@en|UART@@ (від англ. *@@en|Universal Asynchronous Receiver-Transmitter@@* — універсальний асинхронний приймач-передавач) ініціалізується на системну швидкість передачі @@en|baud rate@@ (від англ. *@@en|baud rate@@* — швидкість передачі символів) 74880 біт/с.

Якщо термінальна програма на ПК налаштована на стандартну робочу швидкість користувацької прошивки 115200 біт/с, початковий лог завантаження відображається у вигляді хаотичних збійних символів. Розробник часто сприймає ці символи як апаратне пошкодження лінії зв'язку і втрачає цінну системну інформацію. Перемикання термінала на швидкість 74880 біт/с дозволяє зчитати службовий рядок завантажувача, у якому зафіксовано апаратний режим старту та кодовий номер причини скидання.

Для відображення цього логу в популярних термінальних програмах (таких як PuTTY, Serial Monitor у PlatformIO або minicom) слід вручну вказати значення швидкості 74880 біт/с у полі налаштування послідовного порту. Якщо середовище розробки підтримує лише стандартний набір швидкостей (наприклад, окремі версії Arduino IDE), переключення досягається викликом спеціальних утиліт системного драйвера або використанням зовнішніх налагоджувальних терміналів з підтримкою довільної швидкості тактування @@en|UART@@.

Причина виникнення такої нестандартної швидкості полягає у фізичній роботі апаратного дільника тактування контролера @@en|UART@@. У момент старту ROM-завантажувач спирається на базову частоту кварцового резонатора 26 МГц і зашитий дільник тактової частоти, що дає точну швидкість 74880 біт/с. Більшість мікросхем конвертерів USB-UART (таких як CH340, CP2102 чи FT232) апроксимують цей параметр за допомогою власних внутрішніх регістраційних дільників: якщо драйвер операційної системи не здатний обчислити дільник із розходженням менше 2.5–3%, виникає асинхронний зсув бітових інтервалів, і термінал отримує збійні кадри замість читабельного логу.

## Формат логу ROM та кортеж boot mode

Службове сповіщення ROM-завантажувача надсилається в лінію TXD0 відразу після подачі імпульсу скидання і має наступний стандартний вигляд:

```
ets Jan  8 2013,rst cause:2, boot mode:(3,6)
```

Ключовим параметром для аналізу конфігурації виводів є кортеж @@en|boot mode@@ (від англ. *@@en|boot mode@@* — режим завантаження), який у загальному вигляді записується як `boot mode:(m,n)` або `boot mode:(sdm,gpio0,gpio2)`. Перше число `m` описує внутрішнє кодування системного контролера, а друге число `n` являє собою 3-бітове значення, утворене фізичними логічними рівнями на виводах конфігурації @@en|bootstrapping@@ (від англ. *@@en|bootstrapping pins@@* — виводи конфігурації старту) у момент зчитування стану по фронту сигналу скидання.

Для розшифровки значення `n` його необхідно подати у двійковому вигляді, де біти відповідають трьом службовим виводам:

```
Біт 2 (MSB): GPIO15
Біт 1:       GPIO0
Біт 0 (LSB): GPIO2
```

*Схема декодування текстового логу ROM-завантажувача та визначення режимів завантаження.*

Кожна комбінація визначає конкретний апаратний режим, у якому мікроконтролер розпочинає виконання коду:

- `boot mode:(3,6)` — значення `6` у двійковій системі дорівнює `110₂` (`GPIO15=0`, `GPIO0=1`, `GPIO2=1`). Це штатний режим виконання програми з зовнішньої Flash-пам'яті (SPI Flash Boot).
- `boot mode:(1,7)` або `boot mode:(3,7)` — значення `7` дорівнює `111₂` (`GPIO15=1`, `GPIO0=1`, `GPIO2=1`). При підтяжці `GPIO15` до високого рівня завантажувач переходить у режим завантаження з SDIO, що блокує запуск прошивки з Flash.
- `boot mode:(1,1)` або `boot mode:(3,1)` — значення `1` дорівнює `001₂` (`GPIO15=0`, `GPIO0=0`, `GPIO2=1`). Це режим програмування через послідовний порт (UART Download Mode).

Якщо через наведення або відсутність зовнішніх резисторів підтяжки виводи залишаються у підвішеному стані, лог у терміналі покаже відхилення від значення `6`. Нетипова проблема виникає при наявності паразитного живлення: якщо до виводів `GPIO0` або `GPIO15` підключено периферійні датчики чи конвертери USB-UART, струм може протікати через їхні внутрішні захисні діоди прямо в лінію живлення мікроконтролера, штучно підтягуючи потенціал виводу до високого рівня і спотворюючи значення `boot mode`. Для швидкої діагностики при зависанні завантаження вимірюють напругу на виводах конфігурування мультиметром у момент утримання лінії `RST` на землі: потенціал `GPIO0` та `GPIO2` має бути близьким до `3.3` В, а на `GPIO15` — суворо дорівнювати `0` В. Це дозволяє швидко відрізнити апаратну помилку розведення плати або витік струму від програмних збоїв прошивки без використання осцилографа. Детальний опис комбінацій рівнів наведено у статті про [режими завантаження ESP8266](root:cat-hw-boards/esp8266-boot-modes), а етапи передачі управління розкрито в описі [архітектури завантажувача](root:cat-hw-boards/esp8266-bootloader-architecture).

## Реєстри та класифікація причин скидання

Значення @@en|rst cause@@ (від англ. *@@en|reset cause@@* — причина скидання) у первинному логу вказує на подію, яка згенерувала сигнал скидання процесорного ядра. Значення цього параметра зберігаються у спеціалізованих регістрах контролера системного керування RTC та класифікуються числовими кодами:

- `rst cause:0` — нормальне включення живлення (Power-On Reset, POR). Напруга живлення зросла від нуля до робочого рівня.
- `rst cause:1` — апаратне скидання від сторожового таймера (Hardware Watchdog Reset). Викликається апаратним таймером системного модуля при повній зупинці процесора.
- `rst cause:2` — програмний виняток @@en|exception@@ (від англ. *@@en|exception@@* — виняток). Виникає при спробі виконання некоректної інструкції, некратному вирівнюванні адрес у пам'яті або зверненні за нульовим вказівником.
- `rst cause:3` — програмне скидання від сторожового таймера (Software Watchdog Reset). Викликається системною операційною системою SDK, якщо головний потік не віддає управління процесору понад встановлений ліміт часу (типово 1.5–3 секунди).
- `rst cause:4` — програмна команда перезавантаження @@en|software reset@@ (від англ. *@@en|software reset@@* — програмне скидання), викликана з коду прошивки викликом функції `system_restart()`.
- `rst cause:5` — плановий вихід з режиму глибокого сну @@en|deep-sleep@@ (від англ. *@@en|deep sleep@@* — режим глибокого сну) при подачі короткого імпульсу з виводу `GPIO16` на лінію `RST`.
- `rst cause:6` — зовнішнє апаратне скидання. Виникає при примусовому заземленні виводу `RST` кнопкою або зовнішнім мікроконтролером.

У випадку виникнення програмного винятку (`rst cause:2`) лог ROM-завантажувача доповнюється регістрами аварійного дампа процесора Xtensa:

```
Fatal exception (28): 
epc1=0x40211d28, epc2=0x00000000, epc3=0x00000000, excvaddr=0x00000000, depc=0x00000000
```

Значення `epc1` містить вказівник лічильника інструкцій в оперативній або Flash-пам'яті, на якій сталося критичне збійне звернення. Зіставивши цю адресу з файлом таблиці символів `.map` під час компіляції прошивки, розробник може встановити точний рядок вихідного коду C/C++, що спричинив падіння системи.

Додатково при апаратних винятках, викликаних помилками вирівнювання адрес @@en|alignment fault@@ (від англ. *@@en|alignment fault@@* — збій вирівнювання адрес) або некоректним разименуванням вказівників, ключову роль відіграє регістр `excvaddr` (від англ. *@@en|exception target virtual address@@* — віртуальна адреса призначення винятку). Він зберігає точну 32-бітну адресу пам'яті, до якої процесор спробував звернутися в момент збою. Наприклад, якщо код намагається виконати читання 32-бітного слова за некратною чотирьом адресою на кшталт `0x40200001` або звернутися за порожнім вказівником `0x00000000`, значення `excvaddr` у дампі прямо вкаже на збійне місце в адресному просторі, дозволяючи відрізнити помилку структури даних від банального виходу за межі масиву.

## Використання system_get_rst_info у прошивці

Для аналізу джерела перезавантаження всередині програми розробнику не потрібно вичитувати текстовий потік UART. Середовище ESP8266 SDK надає програмний інтерфейс аналізу системних регістрів через виклики API. Головною функцією для отримання інформації про скидання є `system_get_rst_info()`.

При виклику ця функція повертає вказівник на системну структуру `struct rst_info`, яка має наступний вигляд:

```c
struct rst_info {
    uint32 reason;      // Код причини скидання (0..6)
    uint32 exccause;    // Код винятку Xtensa (при reason == REASON_EXCEPTION_RST)
    uint32 epc1;        // Вказівник інструкції, на якій стався виняток
    uint32 epc2;        // Вказівник інструкції винятку другого рівня
    uint32 epc3;        // Вказівник інструкції винятку третього рівня
    uint32 excvaddr;    // Некоректна адреса пам'яті, яка викликала збій
    uint32 depc;        // Лічильник інструкцій під час налагодження
};
```

Практичне застосування `system_get_rst_info()` полягає у веденні лічильника аварійних ребутів в енергонезалежній RTC-пам'яті @@en|RTC memory@@ (від англ. *@@en|Real-Time Clock memory@@* — пам'ять годинника реального часу), яка зберігає вміст під час м'яких перезавантажень та глибокого сну, але очищається лише при повному відключенні живлення. Виклики API записують структуру `rst_info` у зарезервований системний RTC-буфер (блоки `0`–`63`, кожен по `4` байти), завдяки чому після виходу з глибокого сну або WDT-скидання прошивка може зчитати збережені регістри `exccause`, `epc1` та `excvaddr` без пошкодження даних. Це дозволяє прошивці виявити потрапляння в аварійний цикл і примусово перейти в безпечний режим (англ. *@@en|safe mode@@* — безпечний режим) або запустити процедуру [прошивання модуля](root:cat-hw-boards/esp01-firmware-flashing).
