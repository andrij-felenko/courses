## Падіння пропускної здатності та вичерпання DRAM

Розробник вбудованих систем на базі мікроконтролера @@en|ESP8266@@ часто зіштовхується з аномальною поведінкою мережевого обміну: реальна швидкість передачі даних через бездротовий зв'язок @@en|Wi-Fi@@ виявляється в десятки разів нижчою за потенційну смугу пропускання радіоканалу, або ж пристрій раптово перезавантажується через фатальну помилку вичерпання купи (англ. @@en|Heap@@) пам'яті @@en|Out-of-Memory@@ (скорочено @@en|OOM@@). На перший погляд здається, що розміри мережевих буферів та параметри вікна передачі можна обирати довільно або залишати конфігурацію за замовчуванням, яку пропонує операційна система чи фреймворк. Проте системна причина падіння продуктивності полягає у фізичному конфлікті між мережевою затримкою поширення сигналу та розміром ковзного вікна (англ. @@en|TCP Window@@, позначуваного @@en|TCP_WND@@).

Під час передачі інформації за протоколом @@en|TCP@@ відправник випускає порцію даних і змушений чекати на підтвердження прийому (англ. @@en|Acknowledgement@@, скорочено @@en|ACK@@) від віддаленого вузла. Часовий інтервал між відправкою пакета та надходженням зворотного підтвердження називається затримкою кругового обігу (англ. @@en|Round-Trip Time@@, скорочено @@en|RTT@@). Якщо зарезервований розмір вікна @@en|TCP_WND@@ менший за обсяг даних, який фізичне середовище здатне перемістити за час @@en|RTT@@, конвеєр передавача спорожніє: пристрій вичерпає ліміт непідтверджених байтів і вимушено зупиниться в очікуванні квитанції. Намагання розв'язати проблему простоїв шляхом бездумного збільшення розміру вікна та буферних масивів у [мережевому стеку LwIP](root:cat-hw-boards/lwip-stack-architecture-in-embedded) неминуче впирається в апаратний бар'єр системи пам'яті.

Апаратна специфіка [архітектури оперативної пам'яті](root:cat-hw-boards/esp8266-soc-architecture-overview) @@en|DRAM@@ у чипі @@en|ESP8266@@ обмежує загальний обсяг оперативної пам'яті величиною 80 КБ. Після розміщення статичних даних системних компонентів, стеків зв'язку та робочих буферів драйвера @@en|Wi-Fi@@ під динамічну купу прикладного застосунку залишається всього близько 30–40 КБ. Кожна активна асинхронна сесія вимагає виділення оперативної пам'яті під керуючий блок з'єднання (англ. @@en|TCP Control Block@@, скорочено @@en|TCB@@), буфери повторної передачі та черги пакетів у формі структур @@en|pbuf@@. Мережевий стек @@en|lwIP@@ використовує кілька типів пакетних буферів: `PBUF_RAM` виділяється динамічно з неперервної купи, а `PBUF_POOL` резервується у вигляді фіксованих блоків. Коли прикладний код паралельно створює об'єкти в купі, виникає фрагментація пам'яті. У разі спроби відкрити кілька паралельних [сокетів асинхронного обміну](root:cat-hw-boards/esp01-tcp-udp-sockets) пристрій вичерпує суцільні блоки пам'яті й повертає помилку виділення `ERR_MEM`. Для побудови надійної системи розробник повинен вміти математично розраховувати баланс між затримкою мережі, смугою пропускання та обмеженим бюджетом @@en|DRAM@@.

## Математика BDP та ковзного вікна TCP

Фізична спроможність мережевого каналу утримувати дані в процесі транспортування розраховується через добуток смуги пропускання на затримку (англ. @@en|Bandwidth-Delay Product@@, скорочено @@en|BDP@@). Величина @@en|BDP@@ виражає обсяг інформації у байтах, який перебуває «у польоті» між передавачем та приймачем у будь-який момент часу за умови повного завантаження каналу. Затримка @@en|RTT@@ складається з часу передачі кадру в ефір, затримки поширення сигналу, чергування пакетів у маршрутизаторі та обробки стеком отримувача. Якщо пропускну здатність каналу позначити через `C` (у байтах за секунду), а затримку кругового обігу через `RTT` (у секундах), то математична залежність описується формулою:

```
BDP = C × RTT
```

Розглянемо покрокове обчислення на практичному прикладі. Нехай [параметри модулів ESP-01](root:cat-hw-boards/esp-01) забезпечують ефективну пропускну здатність бездротового зв'язку `C = 2 Мбіт/с = 250000 байт/с`, а виміряна затримка до віддаленого сервера через хмарний маршрут становить `RTT = 100 мс = 0.1 с`.

```
BDP = C × RTT
    = 250000 × 0.1       [множення швидкості у байтах за секунду на час затримки у секундах]
    = 25000              [необхідний обсяг даних у польоті у байтах]
```

Вираховане значення @@en|BDP@@ встановлює математичний поріг для конфігураційного параметра @@en|TCP_WND@@. Згідно з механікою ковзного вікна, передавач може відправити не більше ніж `TCP_WND` непідтверджених байтів. Якщо розмір вікна встановлено меншим за @@en|BDP@@, передавач надсилає `TCP_WND` байтів за час `t_send = TCP_WND ÷ C` і зупиняється на тривалий інтервал `RTT - t_send`, чекаючи на підтвердження @@en|ACK@@. Гранична ефективна швидкість `C_eff` у такому режимі обмежується виразом:

```
C_eff = TCP_WND ÷ RTT
```

За умови використання стандартного значення `TCP_WND = 2048 байт` та затримки `RTT = 0.1 с` обчислимо граничну пропускну здатність:

```
C_eff = 2048 ÷ 0.1
      = 20480            [гранична швидкість у байтах за секунду]
```

Результат свідчить, що реальна швидкість обмежена значенням 20.48 КБ/с (приблизно 163.8 Кбіт/с), що становить менше 9% від потенціалу фізичного каналу. Для локальної мережі @@en|Wi-Fi@@ з затримкою `RTT = 5 мс = 0.005 с` величина @@en|BDP@@ становить лише `250000 × 0.005 = 1250 байт`, тому вікна 2048 байт виразисто вистачає для досягнення повної швидкості. Проте при виході в глобальну мережу мале вікно створює жорстке вузьке місце.

Як видно з діаграми, лише за умови `TCP_WND ≥ BDP` досягається безперервний потік даних без простоїв transmission pipe. Коефіцієнт використання каналу `η` визначається співвідношенням:

```
η = TCP_WND ÷ BDP        [для випадків TCP_WND < BDP]
```

Проте у стеку @@en|lwIP@@ розмір вікна @@en|TCP_WND@@ кратний максимальному розміру сегмента (англ. @@en|Maximum Segment Size@@, скорочено @@en|TCP_MSS@@), який для стандартного протоколу @@en|TCP@@ становить 536 або 1460 байт. Отже, вибір `TCP_WND` вимагає узгодження математичних вимог продуктивності із наявними ресурсами пам'яті.

## Розрахунок статичних і динамічних витрат DRAM

Архітектура стека @@en|lwIP@@ розділяє споживання оперативної пам'яті @@en|DRAM@@ на статичний пул, який резервується під час ініціалізації системи, та динамічні буфери, що виділяються з купи під час відкриття кожного нового з'єднання. Пам'ять розподіляється між двома підсистемами: статичними пулами `MEMP` та динамічним розподілювачем `MEM`. Статичні витрати складаються з масивів керуючих блоків та заздалегідь зконфігурованого пулу пакетних буферів @@en|pbuf@@. Сумарне статичне споживання `RAM_static` описується виразом:

```
RAM_static = (MEMP_NUM_TCP_PCB × S_pcb) + (PBUF_POOL_SIZE × S_pbuf)
```

де `MEMP_NUM_TCP_PCB` — гранична кількість керуючих блоків @@en|TCB@@ у пам'яті, `S_pcb ≈ 160 байт` — розмір однієї структури `tcp_pcb`, `PBUF_POOL_SIZE` — кількість буферів у пулі, а `S_pbuf` — розмір одного елемента пулу, який включає заголовок `struct pbuf` (16 байт), вирівнювання, транспортні заголовки та корисне навантаження (англ. @@en|payload@@). При `TCP_MSS = 1460 байт` розмір одного буфера в пулі становить `S_pbuf ≈ 1536 байт`. Обсяг `PBUF_POOL_SIZE` визначає, скільки вхідних пакетів стек може утримати до обробки: вибір `PBUF_POOL_SIZE = 16` вимагає `16 × 1536 = 24576 байт` статичної пам'яті, що забирає понад 60% вільної купи.

Динамічні витрати оперативної пам'яті на одну активну сесію `RAM_session` складаються з керуючої структури з'єднання, буфера передачі `TCP_SND_BUF`, приймального вікна `TCP_WND` та накладних витрат дескрипторів черги відправки:

```
RAM_session = S_pcb + TCP_SND_BUF + TCP_WND + (N_qelem × S_qhdr)
```

де `N_qelem` — кількість елементів черги передачі (`TCP_SND_QUEUELEN`), а `S_qhdr ≈ 32 байт` — розмір заголовка чергового дескриптора. Необхідно враховувати, що параметр `TCP_SND_BUF` визначає максимальну кількість байтів корисного навантаження в черзі відправки: якщо `TCP_SND_BUF < TCP_WND`, передавач не зможе повністю заповнити ковзне вікно навіть за дозволу від приймача.

Проведемо розрахунок динамічних витрат для однієї сесії з вихідними даними: `TCP_MSS = 1460 байт`, `TCP_WND = 2920 байт` (`2 × TCP_MSS`), `TCP_SND_BUF = 2920 байт`, `S_pcb = 160 байт` та накладними витратами черги `N_qelem × S_qhdr = 8 × 32 = 256 байт`.

```
RAM_session = 160 + 2920 + 2920 + 256
            = 6256       [обсяг динамічної пам'яті на одну активну сесію у байтах]
```

Отже, одна асинхронна сесія із вікном 2.9 КБ вимагає виділення понад 6.25 КБ оперативної пам'яті @@en|DRAM@@. Якщо застосунок відкриває [криптографічні сесії mbedTLS](root:cat-hw-boards/mbedtls-embedded-crypto-library), додаткові накладні витрати на контексти шифрування, буфери ключів та кадри TLS (які мають внутрішній розмір до 16 КБ) додають ще від 16 до 32 КБ на кожен сокет.

## Умови вичерпання пам'яті під навантаженням

Аналіз стійкості мікроконтролера @@en|ESP8266@@ при обробці паралельних TCP-з'єднань спирається на нерівність системного балансу оперативної пам'яті. Щоб уникнути помилок виділення пам'яті @@en|Out-of-Memory@@ та збоїв роботи системи, сумарний обсяг статичних і динамічних буферів @@en|lwIP@@ та прикладного коду не повинен перевищувати доступний розмір купи @@en|Heap@@:

```
RAM_static + (N × RAM_session) ≤ RAM_free_heap - RAM_app
```

де `N` — кількість одночасно активних сесій, `RAM_free_heap` — доступний обсяг вільної купи при запускi, а `RAM_app` — гарантований резерв пам'яті, необхідний прикладному коду для формування об'єктів, обробки буферів та виконання системних задач.

З цієї нерівності виводиться алгебраїчна формула для розрахунку гранично допустимої кількості одночасних з'єднань `N_max`:

```
N_max = ⌊ (RAM_free_heap - RAM_app - RAM_static) ÷ RAM_session ⌋
```

Проведемо обчислення `N_max` для типових умов роботи чипа: доступна купа `RAM_free_heap = 36000 байт`, резерв прикладного застосунку `RAM_app = 10000 байт`, статичні витрати стека `RAM_static = 4000 байт`, а динамічні витрати однієї сесії `RAM_session = 6256 байт`.

```
N_max = ⌊ (36000 - 10000 - 4000) ÷ 6256 ⌋
      = ⌊ 22000 ÷ 6256 ⌋ [ділення доступної пам'яті на витрати однієї сесії]
      = ⌊ 3.51 ⌋         [округлення до меншого цілого числового значення]
      = 3                [максимальна кількість стабільних сесій]
```

Розрахунок показує, що спроба встановити 4-те паралельне з'єднання неминуче призведе до вичерпання купи та виникнення помилки @@en|OOM@@. Для захисту системи у файлі конфігурації `lwipopts.h` використовують параметр `MEMP_NUM_TCP_PCB`: якщо його значення дорівнює 3, стек відхилить 4-й запит підключення прапорцем `RST`, зберігши стабільність купи. Для серверних застосунків або систем, що працюють через [командний інтерфейс ESP-AT](root:cat-hw-boards/esp-at-command-set-overview) і обслуговують багатовузлові мережі, слід застосовувати оптимізований профіль: зменшити `TCP_MSS` до 536 байт, а `TCP_WND` — до 1072 байт. Це знизить значення `RAM_session` до ~2500 байт і дозволить збільшити `N_max` до 7–8 одночасних з'єднань у межах того самого бюджету @@en|DRAM@@.
