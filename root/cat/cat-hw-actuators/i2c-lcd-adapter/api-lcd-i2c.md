# ⚙️ I2C-дисплей у коді: сканер адрес, «Hello, world» і живі цифри

<preknowlist>
- [Шина I2C](root:com-devices/i2c-bus) — дві лінії SDA/SCL, ведучий шле адресу, ведений відповідає ACK/NACK; на цьому стоїть увесь сканер.
- [Адресація I2C](root:com-devices/i2c-addressing) — 7-бітна адреса, молодші біти від ніжок; звідси й «чому 0x27» та «чому 0x3F».
</preknowlist>

Плата впаяна, чотири дроти під'єднані — а екран мовчить чорним. Це нормальний старт: між «підключено правильно» і «показує текст» лежить рівно один шар — код. Причому код обманливо короткий: три рядки, і на екрані слова. Обманливо — бо ці три рядки мовчки припускають, що ви **вгадали адресу**, **завели шину на правильних ніжках** і **не спалили входи мікроконтролера п'ятьма вольтами**. Не вгадали — і замість тексту буде ряд чорних прямокутників або мертва темрява. Тож розберімо весь шлях по-справжньому, від першого запуску до цифр, що оновлюються на очах, справжнім C/C++ під Arduino-ядро (він однаково збирається під класичну Arduino й під ESP32), а не псевдокодом «для ілюстрації».

Три задачі підряд, кожна відповідає на одне питання, що з'їдає перший вечір:

1. **Хто на шині і за якою адресою?** — сканер.
2. **Як вивести перший рядок?** — мінімальний «Hello, world».
3. **Як оновлювати показ, не гальмуючи програму?** — живий лічильник із перемальовуванням лише зміненого.

А наприкінці — розбір п'яти пасток, що дають майже всі скарги «не працює»: ряд прямокутників, блідий екран, тиша на 3.3-вольтовій платі, каша замість тексту, миготіння.

## Задача 1: знайти адресу — сканер шини

Почнімо не з дисплея, а з питання, без відповіді на яке дисплей не оживити: **за якою адресою відгукується ваш конкретний адаптер?** Бібліотеці цю адресу треба сказати числом, а вона в різних екземплярів різна. Стандартний адаптер на PCF8574 сидить на `0x27`. Але якщо на платі стоїть різновид PCF8574**A** — адреса вже `0x3F`. А якщо хтось до вас накинув краплю припою на площадки `A0`/`A1`/`A2`, вона може бути будь-де між `0x20` і `0x27` (чи `0x38`–`0x3F` для варіанта «A»). Гадати — марна трата вечора. Правильно — **спитати саму шину**.

### Ідея: перебрати всі адреси й послухати, хто відповість ACK

[Шина I2C](root:com-devices/i2c-bus) улаштована так, що будь-який обмін починається з того, що ведучий кидає в лінію 7-бітну адресу й один такт слухає: якщо пристрій із такою адресою на шині є, він притягує лінію даних до нуля — це **підтвердження** (ACK, від *acknowledge*); якщо ніхто не озвався, лінія лишається у високому — **відмова** (NACK). Оце й уся механіка сканера: перебрати всі можливі адреси й на кожній подивитися, чи прийшов ACK.

В Arduino-бібліотеці `Wire` це виходить майже дослівно. `Wire.beginTransmission(addr)` готує звертання до адреси, а `Wire.endTransmission()` фактично виставляє її на шину й повертає код результату: **0 означає, що хтось відповів ACK** — тобто за цією адресою пристрій є. Ненульові коди — різні варіанти «ніхто не озвався» (найчастіше 2, коли на адресу-байт прийшов NACK). Ключова тонкість: ми **не пишемо жодного байта даних** — лише адресу. Нам не потрібно нічого передавати, тільки з'ясувати, хто на шині.

### Робочий сканер

:::tabs
```cpp
#include <Wire.h>

void setup() {
  Serial.begin(115200);
  while (!Serial && millis() < 2000) { }   // дочекатись термінала, але не вічно

  // На ESP32/STM32/Pico тут ЗАДАЙТЕ свої ніжки, напр. Wire.begin(21, 22);
  // На класичній Arduino (UNO/Nano) пін жорсткий (A4/A5) — просто Wire.begin();
  Wire.begin();

  Serial.println(F("\nСканую шину I2C..."));
}

void loop() {
  uint8_t found = 0;

  for (uint8_t addr = 0x08; addr <= 0x77; addr++) {   // валідні 7-бітні адреси
    Wire.beginTransmission(addr);
    uint8_t err = Wire.endTransmission();             // 0 = ACK, пристрій є

    if (err == 0) {
      Serial.printf("  знайдено пристрій за 0x%02X", addr);
      // підкажемо, схоже це на дисплей чи ні:
      if (addr >= 0x20 && addr <= 0x27) Serial.print(F("  (схоже на PCF8574 — I2C-LCD)"));
      if (addr >= 0x38 && addr <= 0x3F) Serial.print(F("  (схоже на PCF8574A — I2C-LCD)"));
      Serial.println();
      found++;
    }
  }

  if (found == 0)
    Serial.println(F("  нічого. Перевір живлення, дроти SDA/SCL і підтяжки."));
  else
    Serial.printf("Разом пристроїв: %u\n", found);

  delay(3000);   // повторюємо кожні 3 с, щоб бачити, як щось зникає/з'являється
}
```
```micropython
from machine import I2C, Pin
import time

# На ESP32/STM32/Pico ЗАДАЙТЕ свої ніжки, напр. sda=21, scl=22.
i2c = I2C(0, sda=Pin(21), scl=Pin(22))

print("\nСканую шину I2C...")

while True:
    found = 0

    # i2c.scan() сам перебирає валідні 7-бітні адреси й вертає тих, хто дав ACK
    for addr in i2c.scan():
        print("  знайдено пристрій за 0x{:02X}".format(addr), end="")
        # підкажемо, схоже це на дисплей чи ні:
        if 0x20 <= addr <= 0x27:
            print("  (схоже на PCF8574 — I2C-LCD)", end="")
        if 0x38 <= addr <= 0x3F:
            print("  (схоже на PCF8574A — I2C-LCD)", end="")
        print()
        found += 1

    if found == 0:
        print("  нічого. Перевір живлення, дроти SDA/SCL і підтяжки.")
    else:
        print("Разом пристроїв: {}".format(found))

    time.sleep(3)   # повторюємо кожні 3 с, щоб бачити, як щось зникає/з'являється
```
:::

Залийте, відкрийте термінал на 115200 — і в ньому з'явиться рядок на кшталт `знайдено пристрій за 0x27`. Оце число й піде далі в конструктор дисплея. Якщо друкує `0x3F` — у вас варіант «A», нічого страшного, просто інша адреса. Якщо не друкує **нічого** — це вже не про адресу, а про залізо: або немає живлення, або переплутані `SDA`/`SCL`, або немає підтяжок на шині (про це — в пастках).

> 🔧 **Навіщо це.** Половина всіх «дисплей не працює» — це просто неправильна адреса, вбита в код наосліп. Тридцять секунд зі сканером назавжди знімають це питання: ви не гадаєте «мабуть 0x27», а точно знаєте адресу свого екземпляра. І той самий сканер — універсальний детектор «а чи взагалі жива шина»: якщо він мовчить, проблема не в дисплеї й не в бібліотеці, а нижче — у дротах чи живленні.

Ще одна причина тримати сканер під рукою: він показує **весь** ужиток шини. Побачите разом `0x27` (дисплей) і, скажімо, `0x76` (давач тиску) — переконаєтесь, що два пристрої мирно живуть на одній парі дротів. А якщо адреса раптом зникла з переліку — фізичний контакт відійшов, і це видно негайно, без здогадів.

## Задача 2: перший рядок — мінімальний «Hello, world»

Адресу знаємо. Тепер найкоротша програма, що виводить текст. Уся арифметика з ніблами й стробами `Enable` захована в бібліотеці — стандарт де-факто для цих адаптерів зветься `LiquidCrystal_I2C`. Її ставлять через менеджер бібліотек середовища (шукати «LiquidCrystal I2C»; поширена — від Frank de Brabander / johnrickman). Далі ви працюєте не байтами, а зрозумілими викликами.

### Ідея: створити об'єкт з адресою й геометрією, ініціалізувати, писати

Модель роботи проста. Ви **описуєте свій дисплей** одним об'єктом: яка в нього адреса на шині і яка геометрія — скільки стовпців і рядків. Для 1602 це `16` стовпців на `2` рядки (для 2004 було б `20×4`). Тоді викликаєте ініціалізацію — і далі ставите курсор та друкуєте, як на будь-якому символьному екрані.

:::tabs
```cpp
#include <Wire.h>
#include <LiquidCrystal_I2C.h>

// (адреса, стовпці, рядки). Адресу взяли зі сканера!
LiquidCrystal_I2C lcd(0x27, 16, 2);

void setup() {
  // ВАЖЛИВО на ESP32/STM32/Pico: свою шину піднімаємо САМІ, до дисплея,
  // бо lcd.init() усередині кличе Wire.begin() БЕЗ аргументів (дефолтні ніжки).
  Wire.begin(21, 22);            // SDA=21, SCL=22 — приклад для ESP32
  // На класичній Arduino цей рядок не потрібен — там ніжки жорсткі.

  lcd.init();                    // ініціалізація контролера HD44780 через розширювач
  lcd.backlight();               // увімкнути підсвітку (без неї екран темний!)

  lcd.setCursor(0, 0);           // стовпець 0, рядок 0 (відлік із нуля)
  lcd.print("Hello, world!");

  lcd.setCursor(0, 1);           // другий рядок
  lcd.print("I2C LCD 1602");
}

void loop() {
  // усе вже на екрані — циклу нічого робити
}
```
```micropython
from machine import I2C, Pin
from lcd_api import LcdApi
from i2c_lcd import I2cLcd            # драйвер PCF8574-адаптера для HD44780

# На ESP32/STM32/Pico свою шину піднімаємо САМІ: задаємо ніжки прямо тут.
i2c = I2C(0, sda=Pin(21), scl=Pin(22))   # SDA=21, SCL=22 — приклад для ESP32

# (шина, адреса, рядки, стовпці). Адресу взяли зі сканера!
lcd = I2cLcd(i2c, 0x27, 2, 16)           # конструктор сам робить init + backlight

lcd.move_to(0, 0)                        # стовпець 0, рядок 0 (відлік із нуля)
lcd.putstr("Hello, world!")

lcd.move_to(0, 1)                        # другий рядок
lcd.putstr("I2C LCD 1602")

# усе вже на екрані — далі скрипту нічого робити
```
:::

Залили — і в двох рядках напис. Якщо замість напису **ряд світлих прямокутників на темному тлі** — майже завжди неправильна адреса (спробуйте `0x3F`) або пропущена ініціалізація. Якщо екран **є, підсвітка горить, а тексту не видно** — крутіть синій потенціометр контрасту. Обидва випадки розберемо детально в пастках.

Кілька моментів, які варто зрозуміти, а не просто скопіювати.

**Чому `Wire.begin(21, 22)` окремим рядком і саме перед `lcd.init()`.** Це найпідступніша дрібниця на ESP32. Популярна `LiquidCrystal_I2C` усередині `init()` викликає `Wire.begin()` **без аргументів** — тобто на **дефолтних** ніжках ядра. На ESP32 дефолт — `GPIO21`/`GPIO22`, і якщо ваш дисплей саме там, усе випадково спрацює навіть без окремого рядка. Але щойно ви повісите дисплей на інші ніжки (а на дрібних платах як-от ESP32-C3/C6 дефолти інші), мовчазний `Wire.begin()` усередині бібліотеки перекриє ваш вибір своїм. Рятунок — підняти шину **самому й першим**: викликати `Wire.begin(SDA, SCL)` до `lcd.init()`. Тоді шина вже сконфігурована на ваших ніжках, і повторний безаргументний виклик усередині бібліотеки нічого не зіпсує. На класичній Arduino цієї турботи немає — там I2C прибитий до конкретних ніжок (`A4`=SDA, `A5`=SCL на UNO/Nano), задати інші не можна.

**Чому `backlight()` — окремо.** Підсвітка керується восьмим бітом розширювача (`P3`) через транзистор; при старті бібліотека не зобов'язана її вмикати. Забули `lcd.backlight()` — і навіть правильний текст буде ледь видно на тлі без підсвітки, у сутінках його взагалі не розгледіти. Це частий фальшивий переляк: «залив, а нічого немає», хоча текст на місці — просто темний.

**`init()` проти `begin()`.** У цій бібліотеці є обидва: `init()` — коротке ім'я, `begin(cols, rows)` — повне з повторним заданням геометрії. Роблять по суті те саме (`init()` — тонка обгортка над `begin()` з уже переданими в конструктор розмірами). Плутанина йде від того, що **інша**, класична паралельна `LiquidCrystal` знає лише `begin()`, і люди переносять звичку. Для I2C-версії досить `lcd.init()` — геометрію ви вже задали в конструкторі.

> 🔧 **Навіщо це.** Порядок «спершу `Wire.begin(мої ніжки)`, тоді `lcd.init()`» — не забобон, а прямий наслідок того, що бібліотека мовчки конфігурує шину за вас. Знаючи це, ви за півхвилини заводите дисплей на будь-яких вільних ніжках ESP32, а не проклинаєте «глючну плату», що показує порожнечу, коли I2C насправді висить на чужих виводах.

### Трохи більше, ніж рядок: курсор, вирівнювання, свої символи

Символьний екран — це сітка знайомісць: 1602 має рівно **32** (16×2), кожне — матриця 5×8 крапок. Ви не малюєте пікселі, ви ставите курсор у клітинку й друкуєте туди знак. `setCursor(col, row)` — обидва з нуля: `(0,0)` — верхній лівий кут, `(15,1)` — нижній правий. `print()` пише від курсора вправо, автоматично зсуваючи його; за край рядка текст **не переноситься** сам — просто зникає за межею (курсор іде в «невидиму» частину пам'яті контролера).

Кілька виразних дрібниць, які роблять показ охайним:

:::tabs
```cpp
lcd.clear();                 // стерти весь екран, курсор → (0,0)
lcd.home();                  // курсор → (0,0), НЕ стираючи (швидше за clear())

lcd.setCursor(11, 0);        // праве вирівнювання: рахуємо позицію самі
lcd.print("OK");

// свій символ (напр. градус) — 8 рядків по 5 біт, малюнок 5×8:
byte degree[8] = {
  0b00110,
  0b01001,
  0b01001,
  0b00110,
  0b00000,
  0b00000,
  0b00000,
  0b00000
};
lcd.createChar(0, degree);   // зберегли у слот 0 (усього слотів 8: 0..7)
lcd.setCursor(0, 1);
lcd.print("Temp: 25");
lcd.write((uint8_t)0);       // вивести свій символ зі слота 0
lcd.print("C");              // -> "Temp: 25°C"
```
```micropython

lcd.move_to(0, 0)              # курсор → (0,0), НЕ стираючи (швидше за clear())

lcd.move_to(11, 0)            # праве вирівнювання: рахуємо позицію самі
lcd.putstr("OK")

# свій символ (напр. градус) — 8 рядків по 5 біт, малюнок 5×8:

    0b00000,

    0b00000,

lcd.custom_char(0, degree)    # зберегли у слот 0 (усього слотів 8: 0..7)
```

Тут варто спинитись на двох речах. По-перше, **`clear()` повільний**. Він шле дисплею команду очищення, а її контролер HD44780 виконує помітно довше за звичайний запис (близько 1.5–2 мс проти десятків мікросекунд). Викликати `clear()` у кожному проході циклу — вірний спосіб зробити показ млявим і миготливим. Майже завжди замість `clear()` треба `home()` плюс перезапис потрібних клітинок (до цього — наступна задача). По-друге, **свої символи (`createChar`) обмежені вісьма** — стільки комірок під користувацькі знаки має контролер. Градус, стрілку, значок батареї — будь ласка; шрифт цілком не перевизначиш.

## Задача 3: живі цифри — оновлювати лише те, що змінилося

Тепер найпрактичніше. Реальна програма не пише рядок один раз — вона **оновлює показ**: секунди тікають, температура повзе, смужка прогресу росте. І тут вилазить фізична природа цього дисплея: він **повільний**. Кожен символ — це кілька байтів по I2C (нібли плюс строби `Enable`), а сама шина типово 100 кГц. Перемальовувати весь екран щокадру — це щоразу гнати 32 символи × кілька посилок крізь вузьке горло, і програма починає відчутно спотикатися, а екран — мерехтіти.

### Ідея: не чіпати екран задарма

Рецепт випливає прямо з причини гальмування: **надсилай на дисплей рівно те, що змінилося, і рівно тоді, коли змінилося**. Дві прості звички роблять усю різницю. Перша — не викликати `clear()` у циклі; замість нього перевести курсор на потрібну клітинку й переписати саме її. Друга — **не чіпати шину, поки значення те саме**: тримати останнє показане число й порівнювати; збіглося — не робимо жодної посилки взагалі.

Ось лічильник секунд, що оновлює на екрані **лише цифри**, і то лише коли секунда справді змінилась:

:::tabs
```cpp
#include <Wire.h>
#include <LiquidCrystal_I2C.h>

LiquidCrystal_I2C lcd(0x27, 16, 2);

long lastShown = -1;         // яке число вже на екрані (-1 = «ще нічого»)

void setup() {
  Wire.begin(21, 22);        // свої ніжки — до init() (див. задачу 2)
  lcd.init();
  lcd.backlight();

  // СТАТИЧНУ частину малюємо РАЗ, тут, а не в циклі:
  lcd.setCursor(0, 0);
  lcd.print("Uptime:");
  lcd.setCursor(0, 1);
  lcd.print("sec = ");
}

void loop() {
  long sec = millis() / 1000;

  if (sec != lastShown) {        // змінилось? тільки тоді чіпаємо екран
    lcd.setCursor(6, 1);         // одразу після "sec = "
    lcd.print(sec);
    lcd.print("   ");            // затерти «хвіст» від коротшого числа
    lastShown = sec;
  }

  // тут може крутитися будь-яка інша робота — екран її не гальмує
}
```
```micropython
from machine import I2C, Pin
from i2c_lcd import I2cLcd
import time

i2c = I2C(0, sda=Pin(21), scl=Pin(22))   # свої ніжки — до конструктора (див. задачу 2)
lcd = I2cLcd(i2c, 0x27, 2, 16)

last_shown = -1                # яке число вже на екрані (-1 = «ще нічого»)

# СТАТИЧНУ частину малюємо РАЗ, тут, а не в циклі:
lcd.move_to(0, 0)
lcd.putstr("Uptime:")
lcd.move_to(0, 1)
lcd.putstr("sec = ")

while True:
    sec = time.ticks_ms() // 1000

    if sec != last_shown:          # змінилось? тільки тоді чіпаємо екран
        lcd.move_to(6, 1)          # одразу після "sec = "
        lcd.putstr("{}   ".format(sec))   # число + пробіли, щоб затерти «хвіст»
        last_shown = sec

    # тут може крутитися будь-яка інша робота — екран її не гальмує
```
:::

Три ідеї в цих рядках варті того, щоб їх побачити окремо.

**Статичне — раз, динамічне — за зміною.** Підписи `Uptime:` і `sec =` намальовані в `setup()` **один раз**. У циклі оновлюється тільки число, і тільки коли `sec != lastShown`. Поки секунда та сама, `loop()` крутиться скільки завгодно швидко, **не торкаючись шини взагалі** — уся смуга I2C вільна для інших пристроїв, а програма не буксує.

**Затерти хвіст.** Символьний дисплей не «стирає» старе за вас: якщо було `100`, а стало `99`, третя позиція так і триматиме `0` — вийде `990`. Тому після короткого числа домальовуємо кілька пробілів (`"   "`), які затирають залишок довшого попереднього. Це типова околична пастка «на екрані сміття з попереднього значення»: не забувайте про хвіст або тримайте поле фіксованої ширини.

**Курсор точно на клітинку.** `setCursor(6, 1)` ставить друк рівно туди, де закінчується `sec = ` (шість знаків: `s`,`e`,`c`,` `,`=`,` `). Ми не перемальовуємо підпис — лише накладаємо число поверх старого числа в тій самій позиції. Це і є суть «оновлюй лише змінене».

> 🔧 **Навіщо це.** Різниця не косметична. Наївний цикл із `lcd.clear()` і повним перемальовуванням на 100 кГц дає видиме миготіння й «важкий», лаговий інтерфейс, бо щокадру жене всю сітку по повільній шині. Точковий перезапис зайнятий шиною лічені такти на секунду — екран оновлюється чисто, а процесор вільний. Той самий прийом рятує, коли дисплей ділить шину з давачем, який треба часто опитувати: не забивайте канал показом того, що не змінилось.

### Коли треба ще швидше — підняти частоту шини

Якщо оновлень справді багато (кілька змінних, смужки, анімація стрілки), навіть точковий перезапис на 100 кГц може муляти. Тоді підніміть **тактову частоту шини** до 400 кГц (режим *fast mode*) — вийде вчетверо жвавіше, якщо і плата, і адаптер це тягнуть (короткі дроти, не надто велика підтяжка):

:::tabs
```cpp
Wire.begin(21, 22);
Wire.setClock(400000);     // 400 кГц замість типових 100 000
lcd.init();
lcd.backlight();
```
```micropython
# у MicroPython частота задається прямо в конструкторі I2C:
i2c = I2C(0, sda=Pin(21), scl=Pin(22), freq=400000)   # 400 кГц замість типових 100 000
lcd = I2cLcd(i2c, 0x27, 2, 16)                         # init + backlight — усередині
```
:::

Це безкоштовне прискорення саме для повільного I2C-дисплея. Обережність одна: на довгих дротах чи при багатьох пристроях на шині 400 кГц може «сипати» помилками — тоді поверніться на 100 кГц. Але для короткого шлейфа до одного дисплея fast mode зазвичай працює бездоганно.

## Складність і пастки — п'ять причин «не працює»

Тепер найцінніше: конкретні симптоми й що за ними стоїть. Майже всі скарги на I2C-дисплей зводяться до цих п'яти, і кожну впізнати за виглядом екрана за секунди.

**1. Ряд прямокутників (світлі блоки на кожній клітинці) — код до дисплея не доходить.** Класична картина: підсвітка горить, у верхньому рядку (іноді в обох) — суцільні залиті знайомісця, тексту немає. Це стан «дисплей увімкнувся, але його ніхто не проініціалізував» — контролер HD44780 показує «сирі» комірки. Причини за спаданням частоти:
- **Неправильна адреса** в конструкторі — бібліотека шле байти в нікуди. Лік: запустіть сканер із задачі 1, підставте те, що він знайшов (`0x27` чи `0x3F`).
- **Пропущена або невдала ініціалізація** — забули `lcd.init()`, або на ESP32 шина висить на чужих ніжках (див. правило «`Wire.begin(мої ніжки)` перед `init()`»).
- **Немає контакту по `SDA`/`SCL`** — адреса начебто в коді правильна, але фізично байти не доходять. Сканер це одразу викриє: не знайде взагалі нічого.

**2. Блідий або порожній екран, підсвітка є — контраст.** Текст, найпевніше, **на місці**, ви просто його не бачите: символи майже зливаються з тлом або тло темне до чорноти. Це аналоговий бік, до коду й адреси стосунку не має. Лік: візьміть маленьку викрутку й **крутіть синій потенціометр** на адаптері (`RV1`), спостерігаючи за екраном; десь є вузьке положення, де символи стають чіткими. Якщо крайні положення дають «усе світле» й «усе темне», а виразного тексту немає ніде, — тоді вже підозрюйте адресу (пастка 1) чи занизьке живлення (пастка 3). Порядок дій завжди такий: **спершу контраст, потім код**.

**3. Тиша або сміття саме на 3.3-вольтовій платі — рівні й живлення.** Тут два різні лиха, які легко сплутати.
- **Недостатнє живлення дисплея.** Символьний 1602 хоче **5 В** для читабельного контрасту; від 3.3 В багато екземплярів дають ледь видний текст навіть на максимумі потенціометра. Якщо годуєте адаптер від 3.3 В — не дивуйтесь блідості: це не поломка, це фізика рідких кристалів на заниженій напрузі.
- **Небезпечніше — перевищення рівнів на входах МК.** Це вже не «не працює», а **повільно псується**. Якщо адаптер живиться від 5 В, його лінії `SDA`/`SCL` підтягнуті до 5 В, і ці 5 В приходять на ніжки I2C 3.3-вольтового мікроконтролера (ESP32, STM32, Pico), для яких стеля — 3.3 В. Плата часто «працює», але виводи потроху деградують. Правильно — **не** з'єднувати 5-вольтовий адаптер напряму з 3.3-вольтовим МК: або живіть адаптер від 3.3 В (ціна — тьмяніший екран), або поставте **двонапрямлений перетворювач рівнів** на `SDA`/`SCL`, лишивши дисплею його законні 5 В. У коді цього не полагодити — це залізо; але саме тут ховається найбільше «загадкових» відмов, що приходять через тиждень роботи.

**4. Каша з незрозумілих символів або перекручений текст — не про I2C, а про термінал чи логіку.** Якщо в **терміналі** (`Serial`) каша — це майже завжди неспівпадіння швидкості (термінал на 9600, а плата шле 115200); зведіть швидкості. Якщо каша **на самому дисплеї** — частіше винен ваш код: пишете не-ASCII (кирилицю) у дисплей, що знає лише латину й псевдографіку HD44780; або друкуєте `byte`/сирий покажчик замість форматованого числа. Пам'ятайте: 1602 не знає кирилиці штатно (лише через `createChar` вісім своїх знаків), тож україномовні підписи транслітеруйте або показуйте латиною.

**5. Миготіння й «важкий» показ — зайві перемальовування.** Екран смикається, інтерфейс млявий, реакція із затримкою. Причина — `lcd.clear()` і/або повне перемальовування в циклі: щокадру вся сітка жене крізь повільну шину (див. задачу 3). Лік точковий: статику малювати раз у `setup()`, у циклі оновлювати лише змінені клітинки й лише за зміною значення, `clear()` замінити на `home()` + перезапис, за потреби підняти шину до 400 кГц. Симптом зникає одразу.

## Що варто запам'ятати

Робота з I2C-дисплеєм у коді — це три невеликі звички, що знімають майже всі проблеми. **Спершу сканер** — не гадайте адресу, спитайте шину; `Wire.endTransmission() == 0` означає «пристрій тут», і ви точно знаєте, `0x27` у вас чи `0x3F`. **Тоді мінімальний скетч** — конструктор із адресою й геометрією (`16, 2`), `Wire.begin(мої ніжки)` **перед** `lcd.init()` на ESP32, обов'язково `backlight()`, і `setCursor`/`print`. **Далі — оновлюйте лише змінене**: статику раз у `setup()`, динаміку за зміною значення, без `clear()` у циклі, за потреби 400 кГц.

А коли екран поводиться дивно — читайте його як діагностичний прилад. Ряд прямокутників кричить «неправильна адреса чи немає ініціалізації». Блідість — «крути контраст». Тиша на 3.3-вольтовій платі — «перевір живлення й рівні, поки не спалив входи». Каша — «швидкість термінала або не та мова». Миготіння — «прибери зайві перемальовування». Упізнавши ці п'ять облич, ви заводите будь-який такий дисплей за кілька хвилин — і, головне, не псуєте плату дорогою.
