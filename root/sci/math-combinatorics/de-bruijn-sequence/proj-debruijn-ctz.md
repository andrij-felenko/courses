# ⚙️ Повний код CTZ і таблиця, яку не вгадують, а виводять

Трюк на послідовності де Брейна знаходить позицію наймолодшого встановленого біта трьома діями й одним звертанням до пам'яті — а тут його зібрано в робочий C-код разом із тим єдиним, що в ньому виглядає магією: 32-входовою табличкою `[0, 1, 28, 2, …]`, яку насправді не підбирають руками, а виводять із самої константи кількома рядками циклу.

Нагадаю кістяк, щоб було від чого відштовхнутися. Наймолодший біт ненульового `x` виділяємо як `x & (−x)`: у [доповняльному коді](root:math-number-theory/twos-complement-algebra) число `−x` перевертає всі біти вище наймолодшої одиниці, тож `&` лишає саму цю одиницю — вийшов степінь двійки `2ᵖ`, де `p` — шукана позиція. Множення 32-бітової константи-послідовності `B(2, 5)` на `2ᵖ` зсуває її вліво на `p`, і в старших п'ятьох бітах опиняється п'ятибітове вікно, що починалося з позиції `p`. Оскільки в послідовності де Брейна всі 32 вікна різні, ці п'ять бітів однозначно кажуть `p`. Лишається перекласти вікно на позицію — і саме це робить табличка. Питання, від якого відштовхується весь розбір: звідки та табличка береться?

### Табличка — це обернена перестановка

Ключ у тому, що заготовити табличку означає **прогнати конвеєр наперед** для кожної позиції. Візьмімо відому позицію `p`, ізолюймо `2ᵖ`, помножмо на константу, зсуньмо — дістанемо якесь вікно `w`. Це рівно те вікно, яке конвеєр **побачить**, коли правильна відповідь — `p`. Тому досить записати: «побачив `w` — відповідь `p`», тобто `table[w] = p`. Зробімо так для всіх 32 позицій — і табличка заповниться цілком.

«Цілком» тут не випадкове слово. Мапа `p ↦ w` бере 32 позиції й видає 32 вікна, і всі вони різні — бо це вікна послідовності де Брейна. Отже кожен слот таблички запишеться рівно раз: жоден не перезапишеться двічі й жоден не лишиться порожнім. Мапа `p ↦ w` — це **перестановка** множини `{0, …, 31}`, а табличка — її **обернення**: конвеєр іде `p → w`, а табличка вертає `w → p`.

![Дві стрічки по 32 клітинки: згори — вікно w(p) за позицією p, знизу — обернена табличка table[w]; обидві є перестановками 0…31](img/gen-table.svg)
*Табличка пошуку — це обернена перестановка. Згори: кожна позиція `p` (зліва направо, 0…31) дає своє п'ятибітове вікно `w(p)`. Знизу — та сама відповідність навпаки: за вікном `w` табличка вертає позицію `table[w] = p`. В обох стрічках числа 0…31 стоять рівно раз, бо всі 32 вікна різні. Приклад: позиція 3 дає вікно 7, тож у слот 7 кладемо 3.*

Тому генерація таблички — це буквально «оберни перестановку»:

```c
void build_deBruijn32(uint8_t table[32]) {
    for (uint32_t p = 0; p < 32; p++) {
        uint32_t isolated = 1u << p;                     // рівно те, що дасть x & −x
        uint32_t window   = (isolated * 0x077CB531u) >> 27;
        table[window] = (uint8_t)p;                      // вікно w → позиція p
    }
}
```

Прогнавши цей цикл, дістаємо саме `{0, 1, 28, 2, 29, 14, 24, 3, …}` — ту «магічну» табличку, що в багатьох реалізаціях просто вписана числами. Ніякого підбору: вона однозначно визначена константою.

> 🔧 **Навіщо це.** Вписати табличку готовими числами швидше, але сховати її походження — значить сховати й умову правильності. Згенерований варіант перевіряє себе: якщо константа не та, цикл або перезапише слот, або лишить порожнім, і це видно одразу. А ще той самий цикл переносить трюк на іншу ширину слова чи іншу константу без ручного перерахунку — досить поміняти два-три числа.

### Повний ctz32

Тепер обидві половини разом — заготовлена табличка й три дії над входом:

```c
#include <stdint.h>

static const uint8_t deBruijn32[32] = {
     0,  1, 28,  2, 29, 14, 24,  3, 30, 22, 20, 15, 25, 17,  4,  8,
    31, 27, 13, 23, 21, 19, 16,  7, 26, 12, 18,  6, 11,  5, 10,  9,
};

// Позиція наймолодшого встановленого біта (0…31). Передумова: x ≠ 0.
int ctz32(uint32_t x) {
    uint32_t isolated = x & -x;                  // 2^p: лишити єдину наймолодшу 1
    return deBruijn32[(isolated * 0x077CB531u) >> 27];
}
```

Три дії й одне читання з пам'яті, жодного циклу й жодного розгалуження. Підставте `x`, чий наймолодший біт стоїть на позиції 3: `x & −x` дасть `0x00000008`, множення на константу — `0x3BE5A988`, зсув на 27 — вікно `7`, а `deBruijn32[7]` — рівно `3`. Так само для кожної з 32 позицій, бо табличка для того й обернена.

### Той самий трюк на 64 бітах

Ширшому слову потрібне ширше кільце: `B(2, 6)` з 64 різними шестибітовими вікнами. Вікно тепер завширшки `n = 6`, тож зсув — `64 − 6 = 58`, а константа — 64-бітова послідовність де Брейна `0x03F79D71B4CB0A89`. Табличку на 64 входи виводить той самий цикл — з `1ull << p`, зсувом 58 і `p < 64`:

```c
static const uint8_t deBruijn64[64] = {
     0,  1, 48,  2, 57, 49, 28,  3, 61, 58, 50, 42, 38, 29, 17,  4,
    62, 55, 59, 36, 53, 51, 43, 22, 45, 39, 33, 30, 24, 18, 12,  5,
    63, 47, 56, 27, 60, 41, 37, 16, 54, 35, 52, 21, 44, 32, 23, 11,
    46, 26, 40, 15, 34, 20, 31, 10, 25, 14, 19,  9, 13,  8,  7,  6,
};

// Передумова: x ≠ 0.
int ctz64(uint64_t x) {
    uint64_t isolated = x & -x;
    return deBruijn64[(isolated * 0x03F79D71B4CB0A89ull) >> 58];
}
```

Структура — символ у символ та сама; змінилися лише три числа: ширина типу, константа й зсув. Це і є вигода генерованого підходу — перенести трюк на нову ширину означає поміняти ці три числа й прогнати той самий цикл заново.

### Складність і пастки

Вартість стала: ізоляція біта, множення, зсув і одне звертання до пам'яті — `O(1)`, без розгалужень і без циклу, скільки б нулів не було праворуч. Наївний обхід «зсувай і рахуй, доки біт не з'явиться» коштує в гіршому разі стільки кроків, скільки бітів у слові; трюк де Брейна замінює цей цикл на кілька машинних команд зі сталою латентністю — тому він і живе в менеджерах пам'яті, планувальниках і обході бітових масок. Але його тримають кілька умов, і кожна, якщо її порушити, ламає код **тихо**.

**Вхід мусить бути ненульовий.** Для `x = 0` маємо `−0 = 0`, отже `x & −x = 0`, вікно `0`, і `table[0] = 0`. Функція поверне `0` — наче наймолодший біт на позиції нуль, — хоча одиниць нема зовсім. Це тиха брехня, а не помилка часу виконання. Або гарантуйте `x ≠ 0` з боку виклику, або перевірте окремо, повернувши умовне «немає біта» (скажімо, ширину слова: `if (x == 0) return 32;`).

**Не будь-яке 32-бітове число годиться за константу.** Увесь трюк тримається на тому, що всі 32 п'ятибітові вікна константи різні, — тобто що вона є `B(2, 5)`. Візьміть довільне число — і якісь дві позиції `p ≠ q` дадуть однакове вікно; у генерації один слот перезапише інший, і для однієї з позицій відповідь стане чужою. Комбінаторна властивість «усі вікна різні» тут не прикраса, а умова коректності: `0x077CB531` працює не тому, що особливе, а тому, що це одна з 2048 послідовностей `B(2, 5)`.

**Табличка й константа — нерозлучна пара.** Помножили на іншу константу де Брейна — мусите взяти й табличку, згенеровану саме для неї. Змішати табличку від однієї константи з іншою — дістати сміття, і знову тихо: код скомпілюється й повертатиме правдоподібні, та неправильні числа.

**Множення — беззнакове.** Типи мусять бути `uint32_t`/`uint64_t`. Те, що добуток «лишається в межах слова», — це і є обгортання беззнакового множення за модулем `2ⁿ`, тобто наш зсув. Зі знаковим `int` переповнення — невизначена поведінка (UB) у C, і компілятор має право зробити будь-що; та й `x & −x` покладається на беззнакову семантику заперечення. Тримайте все беззнаковим.

Дзеркальне питання — позиція **найстаршого** біта, тобто [двійковий логарифм](root:math-information/binary-logarithm) `⌊log₂ x⌋` — розв'язується тим самим прийомом, але спершу число «розмазують» униз (`x |= x >> 1; x |= x >> 2; … x |= x >> 16`), обертаючи його на суцільні одиниці від старшого біта; далі — множення на свою константу де Брейна й свою табличку. Той самий комбінаторний факт «усі вікна різні» дає обидві межі — і наймолодший біт, і найстарший.
