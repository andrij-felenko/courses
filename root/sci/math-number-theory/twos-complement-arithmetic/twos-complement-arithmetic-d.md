# Арифметика доповняльного коду

<preknowlist>
- [Доповняльний код](root:math-number-theory/twos-complement-algebra) — як записати від'ємне число: −N = інвертувати всі біти й додати 1; числа лежать на колі; старший біт має від'ємну вагу (−128 для байта).
- [Арифметика в двійковій системі](root:hw-digital/binary-arithmetic) — додавання двійкових чисел стовпчиком і що таке перенос (carry) з розряду в розряд.
- [Модульна арифметика](root:math-number-theory/modular-arithmetic) — числа на колі за модулем 2ⁿ; відкинути «зайвий» біт понад n розрядів — те саме, що звести за модулем 2ⁿ.
</preknowlist>

Доповняльний код прославився однією фразою: «віднімання стає додаванням». Та це лише перша сходинка. За тим самим записом ховається ціла **арифметика** — додати, відняти, змінити знак, розтягнути на ширший тип, зсунути, порівняти, помножити й поділити — і майже все це виходить зі звичайних двійкових дій, тими самими вентилями, що обслуговують і знакові, і беззнакові числа. Ця стаття — про самі операції, їхню реалізацію в кремнії (від швидких префіксних суматорів до компресорних дерев Воллеса й алгоритму Бута) та про їхні гострі краї: де одна схема робить два діла заразом і де вона тихо збреше, якщо не знати правил.

### Кільце лишків: чому одна схема рахує для двох типів

Спершу зрозуміймо, ЧОМУ взагалі можлива одна арифметика на два різні типи чисел. Будь-який n-розрядний двійковий регістр фізично вміщує рівно 2ⁿ комбінацій бітів. Коли до найбільшого значення додають одиницю, виникає перенос за межі n бітів, який схема відкидає. З погляду математики всі обчислення в n-бітному процесорі відбуваються не над нескінченними цілими числами, а в **кільці лишків за модулем 2ⁿ**, яке позначають Z/2ⁿZ.

Візьмімо байт `11001000`. Як **беззнакове** число це 200. Як **знакове** — старший біт важить −128, тож −128 + 64 + 8 = −56. Одні й ті самі біти, а числа різні. Але гляньте на різницю: 200 − (−56) = 256 — рівно повний оберт байта, 2⁸. Це не збіг. Знакове прочитання завжди відрізняється від беззнакового або на нуль (коли старший біт 0), або рівно на 2ⁿ (коли старший біт 1, бо тоді ми відняли 2ⁿ, підмінивши вагу старшого розряду з +2ⁿ⁻¹ на −2ⁿ⁻¹):

```
X_беззнакове − X_знакове = 0       [якщо старший біт = 0]
X_беззнакове − X_знакове = 2ⁿ      [якщо старший біт = 1]
```

Тобто ці два числа **конгруентні за модулем 2ⁿ**:

```
X_беззнакове ≡ X_знакове (mod 2ⁿ)
```

Вони живуть в одній точці кільця Z/2ⁿZ, просто ми чіпляємо їй два різні ярлики. А додавання на колі лишків не питає, яким ярликом ви назвали точку. Додаймо `11001000` і `00000011` (це 3):

```
  11001000    беззнакове 200   |  знакове −56
+ 00000011                3    |          +3
----------
  11001011    беззнакове 203   |  знакове −53
```

Результат `11001011` правильний обома прочитаннями відразу: 203 як беззнакове, −53 як знакове. Схема переклала біти механічно, а тлумачення — уже наша справа. Ось чому в процесора **одна** команда додавання (як `ADD` у x86 або ARM), а не окремі для знакових і беззнакових: біти складаються однаково, різниться лише те, як ми читаємо відповідь. Уся хитрість доповняльного коду в тому, що він розставив від'ємні числа на колі саме так, щоб це збіглося.

### Віднімання: універсальний суматор без окремого віднімача

Тепер зробімо з цього віднімання. У кільці Z/2ⁿZ операція віднімання A − B є додаванням протилежного елемента: A + (−B). Протилежним елементом до B за модулем 2ⁿ є число 2ⁿ − B. Погляньмо, як записати 2ⁿ − B через побітову інверсію.

Число з n одиниць `11...1` дорівнює 2ⁿ − 1. Якщо відняти B від числа з самих одиниць, кожен біт bᵢ просто заміниться на 1 − bᵢ, тобто на побітове заперечення ~B (це побітове NOT або доповнення до одиниці). Тоді протилежний елемент подається так:

```
−B ≡ 2ⁿ − B = (2ⁿ − 1 − B) + 1 = ~B + 1    [у кільці Z/2ⁿZ]
```

Підставивши це у віднімання, маємо:

```
A − B = A + (−B) = A + (~B + 1) = (A + ~B) + 1
```

Гляньте, що вийшло. Щоб відняти B від A, треба виконати рівно дві дії: **побітово інвертувати** B і піднести **одиницю на вхід переносу** наймолодшого розряду (c₀ = 1). Обидва кроки в залізі виконуються без жодного окремого блоку віднімача.

Схема універсального суматора/віднімача будується з n звичайних двійкових повних суматорів (Full Adders) та n двовходових вентилів «виключне АБО» (XOR). На перший вхід кожного i-го суматора заходить біт aᵢ, а на другий — вихід вентиля XOR між bᵢ та єдиним керівним дротом SUB (Add/Subtract):

```
b_модифіковане_і = bᵢ ⊕ SUB
c₀ = SUB
```

Коли SUB = 0 (режим додавання):
- `bᵢ ⊕ 0 = bᵢ` — операнд B проходить без змін;
- `c₀ = 0` — початковий перенос нульовий;
- суматор обчислює `A + B + 0 = A + B`.

Коли SUB = 1 (режим віднімання):
- `bᵢ ⊕ 1 = ~bᵢ` — кожен біт операнда B інвертується;
- `c₀ = 1` — на вхід наймолодшого розряду подається одиниця;
- суматор обчислює `A + ~B + 1 = A − B`.

Порахуймо 3 − 5 на 8-бітному слові:

```
~5 = ~00000101 = 11111010,  c₀ = 1 → 11111010 + 1 = 11111011 = −5

  00000011    (3)
+ 11111011    (−5,  тобто ~5 із перенесеною на вхід одиницею)
----------
  11111110    = −2       (−128+64+32+16+8+4+2 = −2,  а 3 − 5 = −2  ✓)
```

Тут же видно різницю між знаковим і беззнаковим світом. Оскільки 3 менше за 5, у беззнаковій арифметиці сталося **позичання** (borrow): результат не вмістився в невід'ємні числа 0…255. А от знаково вийшло абсолютно законне число −2.

Прапорець переносу (Carry Flag, CF) при відніманні в різних процесорних архітектурах обробляється по-різному:
- У **x86** прапорець CF при відніманні інвертується і позначає позичання: `CF = NOT(cₙ)`. Якщо A < B, позичання сталося і `CF = 1`.
- У **ARM** та **PowerPC** прапорець C зберігає безпосередній вихідний перенос суматора: `C = cₙ`. Якщо позичання не було (тобто A ≥ B), вихідний перенос `cₙ = 1`; якщо позичання було (A < B), `cₙ = 0`.

Сам прийом «віднімати додаванням доповнення» куди старший за комп'ютери. Механічні лічильні машини, чиї шестерні крутилися лише в один бік, віднімали через **доповнення до дев'ятки** ще у XVII столітті. Хто, як і чому докотився від Паскалевої машини до сучасного «інвертуй і додай 1», варто прочитати окремо — [метод доповнень](root:math-number-theory/twos-complement-arithmetic/hist-method-of-complements.md): доповнення до дев'ятки й десятки в десяткових лічильниках, кінцевий перенос, і чому двійкові машини врешті обрали саме доповняльний код, де зайвий перенос просто викидають.

### Два способи зламатися: перенос і переповнення

Ми бачили: операція додавання в кільці лишків однакова для обох прочитань. Але **діапазон** значень різний. Беззнакове число живе в межах від 0 до 2ⁿ − 1, а знакове — від −2ⁿ⁻¹ до 2ⁿ⁻¹ − 1. Тож із однієї-єдиної операції додавання процесор виймає **два незалежні сигнали помилки**:

Перший — **перенос** (carry out, cₙ). Беззнакове ламається, коли справжня сума ≥ 2ⁿ і не влазить у n бітів. Ознака проста: одиниця «вилізла» дев'ятим бітом за старший розряд. Схема зберігає цей біт у прапорці переносу.

Другий — **знакове переповнення** (overflow, V). Знакове ламається, коли **два доданки однакового знаку дають суму протилежного знаку** (додатне + додатне = від'ємне, або від'ємне + від'ємне = додатне). Механічно в схемі переповнення фіксується ще простіше: переповнення сталося тоді й лише тоді, коли **перенос, що зайшов у старший (знаковий) розряд cₙ₋₁, не дорівнює переносу, що вийшов з нього cₙ**:

```
V = cₙ₋₁ ⊕ cₙ
```

Чому саме ця різниця ловить псування знаку — гарно виводиться окремо, у вставці [чому XOR переносів ловить переповнення](root:math-number-theory/twos-complement-arithmetic/math-overflow-detection.md): там і доведення рівності двох ознак (XOR переносів ↔ «однакові знаки дали інший знак»), і пояснення, чому беззнаковий перенос — це просто перенос зі старшого розряду.

Найкраще відчути незалежність цих двох сигналів — на прикладах, де спрацьовує **рівно один** із них.

**Приклад перший: перенос є, переповнення немає.** Додаймо на 8 бітах числа 200 та 100:

```
  11001000    (200 беззнак. |  −56 знак.)
+ 01100100    (100 беззнак. | +100 знак.)
----------
1 00101100    c₈ = 1,  c₇ = 1,  результат = 00101100 = 44
```

Беззнаково 200 + 100 = 300 > 255. Результат не вмістився, виник перенос `c₈ = 1`. **Беззнакове зламалося.** Знаково це −56 + 100 = +44, і біти `00101100` якраз позначають +44. Оскільки перенос у 7-й біт `c₇ = 1` і перенос із нього `c₈ = 1`, прапорець переповнення `V = 1 ⊕ 1 = 0`. **Знакове ціле.**

**Приклад другий: переповнення є, переносу немає.** Додаймо +127 та +1:

```
  01111111    (+127)
+ 00000001    (+1)
----------
0 10000000    c₈ = 0,  c₇ = 1,  результат = 10000000 = −128
```

Знаково обидва доданки додатні, а сума `10000000` читається як −128 — знак перекинувся, `V = 1 ⊕ 0 = 1`. **Знакове зламалося.** Беззнаково 127 + 1 = 128 ≤ 255, вихідного переносу немає (`c₈ = 0`). **Беззнакове ціле.**

> 🔧 **Навіщо це.** Саме звідси ростуть **знаковий і беззнаковий типи** та дві родини умовних переходів у процесорі. Компілятор для обох типів генерує ту саму команду додавання чи віднімання, але для беззнакових порівнянь генерує переходи, що дивляться на перенос (`JB`/`JA` в x86, `B.LO`/`B.HI` в ARM), а для знакових — переходи, що аналізують прапорці знака й переповнення (`JL`/`JG` в x86, `B.LT`/`B.GT` в ARM). Механіку прапорців у залізі розбирає [прапорці АЛП](root:hw-arch/alu-flags), а наслідки переповнення для софту — [переповнення](root:sf-lang/overflow-wraparound).

### Апаратні структури швидких суматорів

Найпростіший n-розрядний суматор — **послідовний суматор із наскрізним переносом** (Ripple-Carry Adder, RCA). У ньому n повних суматорів з'єднані ланцюжком: вихід переносу cᵢ одного каскаду подається на вхід переносу наступного cᵢ₊₁. Перевага RCA — мінімальна площа на кристалі (всього 5 вентилів на розряд). Але його критична вада — час затримки: біт суми старшого розряду sₙ₋₁ не може сформуватися, поки сигнал переносу не пробіжить через усі n каскадів. Час затримки зростає лінійно:

```
T_RCA = O(n)
```

Для 64-розрядного процесора 64 послідовні затримки вентилів зробили б такт нестерпно повільним. Тому сучасні процесори використовують швидкі структури з логарифмічною затримкою `O(log₂ n)`.

#### Carry-Lookahead Adder (CLA)

Ідея суматора з паралельним переносом полягає в тому, щоб вирахувати всі переноси завчасно безпосередньо з вхідних бітів aᵢ та bᵢ. Для кожного розряду i визначають дві проміжні булеві функції:
- **Генерація переносу** (Generate): `Gᵢ = aᵢ · bᵢ`. Якщо обидва біти 1, розряд самостійно породжує перенос незалежно від того, що прийшло знизу.
- **Розповсюдження переносу** (Propagate): `Pᵢ = aᵢ ⊕ bᵢ` (або `Pᵢ = aᵢ + bᵢ`). Якщо хоча б один біт 1, вхідний перенос cᵢ безперешкодно проходить у наступний розряд.

Тоді переноси для перших чотирьох розрядів записуються рекурсивно:

```
c₁ = G₀ + P₀·c₀
c₂ = G₁ + P₁·G₀ + P₁·P₀·c₀
c₃ = G₂ + P₂·G₁ + P₂·P₁·G₀ + P₂·P₁·P₀·c₀
c₄ = G₃ + P₃·G₂ + P₃·P₂·G₁ + P₃·P₂·P₀·G₀ + P₃·P₂·P₁·P₀·c₀
```

Усі ці вирази мають глибину всього 2 рівні логіки (рівень AND та рівень OR). Утім, розширювати прямий CLA на 32 чи 64 біти неможливо: вентилі мають фізичне обмеження на кількість входів (fan-in, у кремнії зазвичай не більше 4–5 входів). Тому на практиці будують **блочні CLA**, де 4-бітні блоки об'єднуються в ієрархічне дерево через групові сигнали генерації та розповсюдження.

#### Паралельно-префіксні суматори (Kogge-Stone та Brent-Kung)

Узагальненням ідеї CLA є представлення переносу через асоціативну бінарну операцію над парами `(G, P)`. Визначимо префіксний оператор «`∘`»:

```
(G_лівий, P_лівий) ∘ (G_правий, P_правий) = (G_лівий + P_лівий · G_правий,  P_лівий · P_правий)
```

Ця операція асоціативна: `(A ∘ B) ∘ C = A ∘ (B ∘ C)`. А це означає, що обчислення префіксних пар для всіх n розрядів зводиться до задачі паралельного префіксного сканування (prefix tree), яке виконується за час:

```
T_Prefix = O(log₂ n)
```

Два класичні дерева демонструють різні інженерні компроміси між площею, затримкою та кількістю з'єднань:
- **Kogge-Stone Adder**: дерево з максимальною кількістю паралельних вузлів. Його логічна глибина мінімально можлива — рівно `log₂ n` рівнів логіки, а розгалуження на виході вузлів (fan-out) не перевищує 2. Це **найшвидший** з відомих суматорів, і його ставлять у критичні за частотою вузли АЛП. Плата за швидкість — величезна кількість вентилів і щільна сітка дротів між рівнями, що збільшує площу та енергоспоживання.
- **Brent-Kung Adder**: дерево з мінімальною кількістю вентилів і з'єднань (`O(n)` замість `O(n log n)`). Воно спершу збирає префікси знизу догори для парних розрядів, а потім розгортає їх згори донизу для непарних. Його логічна глибина більша: `2·log₂ n − 1`, але площа кристала значно менша, а маршрутизація дротів проста. Його обирають для енергоефективних мікроконтролерів.

```
Kogge-Stone (64 біти):  глибина 6 тактів логіки  | висока площа й складна розводка
Brent-Kung (64 біти):   глибина 11 тактів логіки | мала площа й низьке енергоспоживання
```

### Знакове множення: алгоритм Бута (Radix-2)

Множення беззнакових чисел стовпчиком полягає в додаванні зсунутих копій множеного (partial products). Але для знакових чисел у доповняльному коді пряме складання ламається з двох причин:
1. Якщо множене M від'ємне, кожна його зсунута копія вимагає **знакового розширення** одиницями на всю 2n-бітну ширину результуючої сітки.
2. Старший біт множника yₙ₋₁ має від'ємну вагу −2ⁿ⁻¹, тож останній частковий добуток треба не додавати, а віднімати.

1951 року Ендрю Бут (Andrew Donald Booth) запропонував алгоритм, який опрацьовує доповняльний код безпосередньо, а заразом економить операції на довгих ланцюжках одиниць.

#### Ідея згортання одиниць

Візьмімо двійкове число з суцільним ланцюжком одиниць, наприклад `01111000` (це 120):

```
2⁶ + 2⁵ + 2⁴ + 2³ = 64 + 32 + 16 + 8 = 120
```

Замість того щоб виконувати 4 окремі додавання, згадаймо алгебраїчну тотожність:

```
2ᵐ⁺ᵏ − 2ᵐ = 2ᵐ⁺ᵏ⁻¹ + 2ᵐ⁺ᵏ⁻² + ... + 2ᵐ
```

Для нашого ланцюжка одиниць від 3-го до 6-го розряду маємо: `2⁷ − 2³ = 128 − 8 = 120`. Тобто весь блок одиниць замінюється всього **двома операціями**: відніманням на правому краю ланцюжка (перехід з 0 в 1) і додаванням на лівому краю (перехід з 1 в 0).

#### Правила кодування бітових пар

Алгоритм Бута розглядає біти множника Y попарно: поточний біт yᵢ та попередній молодший біт yᵢ₋₁ (на першому кроці для наймолодшого біта беруть фіктивний біт `y₋₁ = 0`):

| yᵢ | yᵢ₋₁ | Подія в ланцюжку бітів | Дія над акумулятором |
|:---|:-----|:-----------------------|:---------------------|
| 0  | 0    | Посередині ланцюжка нулів | Нічого (тільки зсув) |
| 0  | 1    | Кінець ланцюжка одиниць (перехід 1 → 0) | **Додати** множене: A ← A + M |
| 1  | 0    | Початок ланцюжка одиниць (перехід 0 → 1) | **Відняти** множене: A ← A − M |
| 1  | 1    | Посередині ланцюжка одиниць | Нічого (тільки зсув) |

Після кожної операції пара регістрів `[A, Y]` разом із додатковим бітом y₋₁ виконує **арифметичний зсув праворуч на 1 біт** (ASR).

#### Покроковий числовий приклад

Помножмо 4-бітні числа: множене M = 3 (`0011`), множник Y = −5 (`1011`). Очікуваний результат у 8 бітах: 3 × (−5) = −15 (`11110001`).

Початковий стан: A = 0000, Y = 1011, y₋₁ = 0. Множене M = 0011, а −M = 1101.

```
Крок 1:  y₀ = 1, y₋₁ = 0  → пара 10 → A = A − M = 0000 + 1101 = 1101
         Зсув ASR: [A, Y, y₋₁] = [1110, 1101, 1]

Крок 2:  y₁ = 1, y₀ = 1    → пара 11 → операції нема
         Зсув ASR: [A, Y, y₋₁] = [1111, 0110, 1]

Крок 3:  y₂ = 0, y₁ = 1    → пара 01 → A = A + M = 1111 + 0011 = 0010
         Зсув ASR: [A, Y, y₋₁] = [0001, 0011, 0]

Крок 4:  y₃ = 1, y₂ = 0    → пара 10 → A = A − M = 0001 + 1101 = 1110
         Зсув ASR: [A, Y, y₋₁] = [1111, 0001, 1]
```

Результат у регістрах `[A, Y]` після 4 кроків: `11110001`. Перевіримо знакове значення: −128 + 64 + 32 + 16 + 1 = −15. Алгоритм дав точну відповідь для від'ємного множника без жодного спеціального розбиття на знак і модуль.

### Модифікований алгоритм Бута (Radix-4) та дерево Воллеса

Базовий алгоритм Бута має неприємну рису: на чергованих бітах `01010101` він виконує операцію додавання або віднімання на кожному кроці. Крім того, він генерує n часткових добутків, які треба послідовно складати.

**Модифікований алгоритм Бута за основою 4** (Modified Booth / Radix-4 Booth) усуває цей недолік. Він розглядає множник вікном із **трьох сусідніх бітів** `(y₂ᵢ₊₁, y₂ᵢ, y₂ᵢ₋₁)` з перекриттям в 1 біт і кроком у 2 біти. Завдяки цьому кількість часткових добутків скорочується **рівно вдвічі**:

```
Кількість часткових добутків = ⌈n / 2⌉
```

Для 64-розрядного множення замість 64 рядків матриці треба додати лише 32 рядки.

#### Таблиця кодування Radix-4

Кожна трійка бітів перетворюється на коефіцієнт dᵢ ∈ {-2, -1, 0, +1, +2} за формулою ваги розрядів:

```
dᵢ = −2·y₂ᵢ₊₁ + y₂ᵢ + y₂ᵢ₋₁
```

| y₂ᵢ₊₁ | y₂ᵢ | y₂ᵢ₋₁ | Коефіцієнт dᵢ | Частковий добуток | Як реалізується в залізі |
|:---|:---|:---|:---|:---|:---|
| 0 | 0 | 0 | 0 | 0 | Обнулити шину |
| 0 | 0 | 1 | +1 | +M | Пропустити M як є |
| 0 | 1 | 0 | +1 | +M | Пропустити M як є |
| 0 | 1 | 1 | +2 | +2M | Зсунути M ліворуч на 1 біт |
| 1 | 0 | 0 | −2 | −2M | Зсунути M ліворуч на 1 і побітово інвертувати (~2M + 1) |
| 1 | 0 | 1 | −1 | −M | Побітово інвертувати (~M + 1) |
| 1 | 1 | 0 | −1 | −M | Побітово інвертувати (~M + 1) |
| 1 | 1 | 1 | 0 | 0 | Обнулити шину |

Чому саме Radix-4 став стандартом у залізі помножувачів? Бо всі необхідні кратні множимого (±M, ±2M) формуються **миттєво**: зсув на один біт ліворуч дає 2M, а інверсія XOR — заперечення. Якби ми перейшли до Radix-8 (вікно з 4 бітів), виникла б потреба у кратному 3M, для формування якого довелося б ставити додатковий повільний суматор 2M + M.

#### Компресія часткових добутків: дерево Воллеса (Wallace Tree)

Після формування ⌈n/2⌉ часткових добутків їх треба швидко скласти. Складати їх послідовно через суматори означало б знову накопичувати затримку. Тут на допомогу приходить **Carry-Save Adder (CSA)**, який використовують як **компресор 3:2**.

Звичайний повний суматор розглядається як пристрій, що приймає 3 вхідні біти однакової ваги і без будь-якого розповсюдження переносу видає 2 вихідні біти: біт суми S тієї самої ваги і біт переносу C з вагою 2×. Затримка компресора 3:2 — це затримка рівно одного вентиля XOR і одного MUX, незалежно від розрядності!

**Дерево Воллеса (Wallace Tree)** організовує компресори 3:2 у багаторівневу піраміду:
1. На першому рівні кожні 3 рядки часткових добутків згортаються у 2 рядки (коефіцієнт стискання 3 → 2).
2. Отримані рядки знову розбиваються на трійки й згортаються.
3. Процес повторюється, доки не лишиться рівно **2 вектори**: вектор сум Sum і вектор переносів Carry.
4. Затримка згортки становить всього `O(log₁.₅ (n/2))` рівнів.
5. Фінальні два вектори додаються **одним** швидким суматором (CLA або Kogge-Stone) для отримання остаточного 2n-бітного добутку.

Детальний опис апаратного помножувача та його схеми наведено у статті [алгоритм знакового множення](root:hw-digital/booth-hardware-multiplier).

### Знакове ділення: Restoring, Non-Restoring та SRT

Якщо множення — це багаторазове додавання зі зсувом, яке легко розпаралелити за допомогою компресорних дерев, то ділення — принципово **послідовна (ітеративна) операція**. Кожен наступний біт частки залежить від знаку проміжного залишку, обчисленого на попередньому кроці.

Для цілих чисел ділення визначається як:

```
A = B · Q + R,    де |R| < |B|
```

У мовах програмування стандарту C99/C++11 та більшості процесорів закріплено правило **округлення до нуля**: знак частки Q визначається добутком знаків sgn(A) · sgn(B), а знак залишку R **завжди збігається зі знаком діленого A**:

```
 7 /  3 =  2,   7 %  3 =  1       ( 7 =  3 ·  2 +  1)
-7 /  3 = -2,  -7 %  3 = -1       (-7 =  3 · -2 + -1)
 7 / -3 = -2,   7 % -3 =  1       ( 7 = -3 · -2 +  1)
-7 / -3 =  2,  -7 % -3 = -1       (-7 = -3 ·  2 + -1)
```

Апаратне знакове ділення зазвичай зводять до беззнакового (знаходячи |A| та |B|), ділять за одним із базових алгоритмів, а потім коригують знаки Q та R.

#### Restoring Division (ділення з відновленням залишку)

Найпростіший побітовий алгоритм:
1. Зсунути поточний неповний залишок R ліворуч на 1 біт (помножити на 2) і знести наступний біт діленого.
2. Виконати пробне віднімання дільника: R' = 2R − D.
3. Якщо R' ≥ 0, дільник помістився: черговий біт частки qᵢ = 1, а новий залишок R = R'.
4. Якщо R' < 0, дільник не помістився: черговий біт частки qᵢ = 0, і схеми мусить **відновити** попереднє значення залишку зворотним додаванням: R = R' + D.

Недолік очевидний: у найгіршому випадку схема на кожному кроці робить два послідовні додавання (віднімання і відновлення).

#### Non-Restoring Division (ділення без відновлення)

Алгоритм без відновлення позбувається зайвої операції. Якщо на попередньому кроці залишок став від'ємним (R' < 0), ми не відновлюємо його одразу. На наступному кроці після обов'язкового зсуву залишок дорівнює 2R' = 2(2R − D). Якщо до нього тепер **додати** D, вийде:

```
2(R' + D) − D = 2R' + 2D − D = 2R' + D
```

Тобто відновлення і наступне віднімання зливаються в одне додавання +D!

Правило Non-Restoring Division стає симетричним:
- Якщо поточний залишок R ≥ 0: зсунути R ліворуч і **відняти** дільник (2R − D). Якщо результат ≥ 0, то qᵢ = 1, інакше qᵢ = 0.
- Якщо поточний залишок R < 0: зсунути R ліворуч і **додати** дільник (2R + D). Якщо результат ≥ 0, то qᵢ = 1, інакше qᵢ = 0.

На кожній ітерації виконується рівно **одна** операція додавання/віднімання.

#### Алгоритм SRT

Названий за іменами незалежних винахідників (Sweeney, Robertson, Tocher), алгоритм SRT є серцем апаратних блоків ділення в сучасних FPU та ALU.

Головні ідеї SRT:
1. **Надлишкова система числення частки**: цифри частки qᵢ обираються з множини `{-1, 0, +1}` для Radix-2 або `{-2, -1, 0, +1, +2}` для Radix-4.
2. **Передбачення цифри за кількома старшими бітами**: завдяки надлишковості точне значення залишку рахувати не потрібно! Наступну цифру qᵢ обирають через невелику таблицю пошуку (PLA або ROM), дивлячись лише на 3–4 старші біти неповного залишку та дільника.
3. **Робота у форматі Carry-Save**: оскільки точний знак залишку не потрібен, проміжний залишок тримають у вигляді пари векторів Sum і Carry, уникаючи повільного повного суматора на кожній ітерації.

> ⚠️ **Історичний урок: баг Pentium FDIV (1994).** У процесорах Intel Pentium для Radix-4 SRT ділення використовувалася таблиця вибору цифри частки з 2048 комірок. Через помилку в скрипті трансляції масиву в кремній 5 комірок таблиці виявилися порожніми (містили нулі замість +2). Це призводило до помилки в 9–10 знаку після коми при діленні певних пар чисел (наприклад, 4195835 / 3145727) і коштувало компанії Intel відклику процесорів на 475 мільйонів доларів.

### Зміна знака, ділення INT_MIN / -1 та крайові випадки

Змінити знак у доповняльному коді — це взяти протилежне за модулем 2ⁿ:

```
−N = ~N + 1
```

Усе бездоганно й оборотно… крім однієї точки. У n-розрядному слові діапазон чисел асиметричний: від'ємних чисел на одне більше, ніж додатних:

```
[−2ⁿ⁻¹,  2ⁿ⁻¹ − 1]
```

Для 8 бітів це `[-128, +127]`, для 32 бітів — `[-2147483648, +2147483647]`. Число `INT_MIN` (старший біт 1, решта 0) **не має додатної пари**, бо +2ⁿ⁻¹ просто не влазить у розрядну сітку.

Спробуймо змінити знак у байта −128:

```
−128 = 10000000
~   = 01111111
+1  = 10000000    ← знову −128!
```

`INT_MIN` — сам собі протилежний. Звідси випливає найнебезпечніший крайовий випадок цілочислової арифметики — **ділення `INT_MIN / -1`**:

```
INT_MIN / −1 = +2ⁿ⁻¹    [не вміщується у знаковий діапазон]
```

Очікувана математична відповідь +2ⁿ⁻¹ викликає переповнення частки. Як реагує залізо:
- В архітектурі **x86/x86-64** команда `IDIV` при спробі виконати `INT_MIN / -1` генерує апаратний виняток переривання `#DE` (Divide Error Exception) — той самий, що й при діленні на нуль. В операційній системі Linux це призводить до аварійного завершення процесу сигналом `SIGFPE` (Floating point exception).
- В архітектурах **ARM (AArch64)** та **RISC-V** ділення спроєктовано без апаратних винятків: операція `INT_MIN / -1` тихо повертає значення `INT_MIN`, встановлюючи результат без переривання програми.
- У мовах **C і C++** вираз `INT_MIN / -1`, як і ділення на 0, є **невизначеною поведінкою** (Undefined Behavior). Компілятор має право припустити, що такої операції ніколи не відбудеться, і викинути перевірки або переоптимізувати код навколо неї.

### Ширший тип: знакове розширення

Що як перекласти знакове число у ширший тип — байт у 16 чи 32 біти? Наївно долити зверху нулів. Для додатних це правильно, а для від'ємних — катастрофа: −5 на байті це `11111011`, а якщо доповнити нулями, вийде `00000000 11111011` = 251, зовсім не −5. Причина видна на колі: на ширшому колі те саме число −5 має стояти на позиції 2¹⁶ − 5, тобто мати одиниці в усіх нових старших розрядах, а не нулі.

Правило тому таке: розширюючи знакове число, **копіюй старший біт** у всі нові розряди — нулі для додатних, одиниці для від'ємних:

```
−5 у 8 бітах:    11111011
−5 у 16 бітах:   11111111 11111011     (старший біт 1 «розлився» ліворуч)
+5 у 16 бітах:   00000000 00000101     (старший біт 0 → просто нулі)
```

Це **знакове розширення** (sign extension). Процесор має для нього спеціальні команди (наприклад, `MOVSX` в x86 або `SXTW` в ARM), які за один такт заповнюють старшу частину регістра копією знакового біта. Деталі й пастки живуть у [знаковому розширенні](root:sf-lang/sign-extension) — зокрема класична, коли `char` мовчки розширюється зі знаком і байт `0xFF` стає −1 замість 255.

### Зсуви: дешеві ×2 і ÷2 (і пастка округлення)

Зсув бітів — найдешевша арифметика, яку тільки має процесор, і доповняльний код чудово з ним дружить. Зсув **уліво** (`<<`) на k розрядів дописує нулі справа й множить число на 2ᵏ — і для беззнакових, і для знакових однаково, аж поки не станеться переповнення.

А зсув **управо** ділить на 2, але тут дороги розходяться:
- **Логічний зсув праворуч** (`LSR` або `>>>`) — дописує нулі зліва. Це ділення на 2 для **беззнакового** числа.
- **Арифметичний зсув праворуч** (`ASR` або `>>`) — дописує зліва копію **старшого знакового біта** (як у знаковому розширенні). Це ділення на 2 для **знакового** числа.

```
байт −8 = 11111000

логічний >> 1:     01111100 = 124     ← для беззнакового (248 / 2 = 124)
арифметичний >> 1: 11111100 = −4      ← для знакового (−8 / 2 = −4)
```

Логічний зсув для від'ємного зіпсував би знак, тому для знакових обов'язковий саме арифметичний зсув. Але й він ховає фундаментальну пастку.

Арифметичний зсув праворуч ділить із **округленням донизу** (у бік −∞, floor division), тоді як стандартне цілочислове ділення мов C, C++ та Java округлює **до нуля** (truncation towards zero):

:::tabs
```c
int8_t x = -7;
int8_t a = x >> 1;   // 11111001 → 11111100 = -4 (округлення донизу)
int8_t b = x / 2;    // стандарт C99/C11 округляє до нуля → -3
```
```cpp
int8_t x = -7;
int8_t a = x >> 1;   // 11111001 → 11111100 = -4 (округлення донизу)
int8_t b = x / 2;    // стандарт C++11/C++20 округляє до нуля → -3
```
:::

−7 / 2 математично дорівнює −3.5. Арифметичний зсув `x >> 1` дає −4, а ділення `x / 2` дає −3. Вони розходяться на одиницю для всіх непарних від'ємних чисел! Крім того, вираз `−1 >> 1` дає `11111111` = −1 назавжди, тоді як `−1 / 2` дає 0.

Тому оптимізуючий компілятор при заміні знакового `x / 2` на зсув додає апаратну поправку (зміщення): додає 1 до від'ємного числа перед зсувом, якщо старший біт піднятий (`(x + ((x >> 31) & 1)) >> 1`).

> 🔧 **Навіщо це.** Не замінюйте вручну знакове `/ 2` на `>> 1`: для від'ємних значень вони дадуть різні результати, що є класичним багом обчислення середнього значення, фільтрів та координат у графіці. Використовуйте `>> 1` як ділення лише тоді, коли алгоритм свідомо вимагає математичного округлення до меншого цілого (floor).

Підсумок. Доповняльний код відображає числа на **кільце лишків Z/2ⁿZ** так, що знакове й беззнакове прочитання збігаються за модулем 2ⁿ. Завдяки цьому **універсальний суматор** виконує віднімання `A − B` як `A + ~B + 1` через n вентилів XOR та подачу одиниці на вхід переносу, не потребуючи окремого віднімача. Для швидкого складання кремній використовує **префіксні дерева Kogge-Stone та Brent-Kung**, що скорочують затримку переносу до O(log₂ n). **Алгоритм Бута та Radix-4 Modified Booth** перетворюють ланцюжки одиниць на операції ±M, ±2M і скорочують число часткових добутків удвічі, а **дерево Воллеса з компресорами 3:2** сумує їх за логарифмічний час без поширення переносів. **Ділення** реалізується алгоритмами Non-Restoring та **SRT** з надлишковим кодуванням частки. А на краях діапазону асиметрія породжує самотнє **`INT_MIN`**, чиє віднімання й ділення на −1 вимагають пильної уваги через апаратні винятки переповнення.
