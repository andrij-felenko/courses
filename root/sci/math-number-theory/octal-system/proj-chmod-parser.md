# ⚙️ Парсер вісімкових прав Unix (chmod/stat)

Права доступу в системах Unix — це класичний приклад того, де вісімкова система числення є не просто математичною цікавинкою, а щоденним інструментом. Коли ми бачимо команду `chmod 755 script.sh` або читаємо конфігураційний файл, ці цифри прямо відображаються на біти дозволів. Але як правильно прочитати цей рядок у програмі на C++, щоб перетворити його на системні прапорці для виклику `chmod()` чи `open()`?

### 1. Навіщо розробляється реалізація

Під час написання системних утиліт, інсталяторів, демонів або парсерів конфігураційних файлів часто виникає потреба зчитати права доступу з текстового формату в числове подання. Наївний підхід — використання класичних функцій `std::stoi`, `std::stoul` або ж сімейства `scanf` — має кілька архітектурних вад. По-перше, вони можуть ігнорувати зайві символи після валідного числа, що призводить до непомітних помилок конфігурації. По-друге, такі функції вимагають, щоб рядок неодмінно завершувався нульовим символом, що часто призводить до зайвого виділення динамічної пам'яті (копіювання) при розборі великих блоків тексту. Насамкінець, стандартні `std::stoi` генерують винятки при помилках парсингу, що не завжди прийнятно в суворому системному програмуванні, де відсутність винятків (noexcept) є нормою. Тому нам потрібен надійний, оптимізований парсер, який не виділяє пам'яті, чітко розпізнає формат вісімкових чисел та моделює предметну область через сувору типізацію, замість повернення голого цілого числа, яке легко сплутати зі звичайними даними.

### 2. Алгоритмічна та архітектурна ідея

Ідея полягає в тому, щоб обробляти вісімковий рядок як компактну 12-бітну маску. Права доступу Unix логічно поділяються на чотири компоненти, кожен з яких займає по 3 біти (тобто рівно одну цифру від 0 до 7 у вісімковій системі):
- Спеціальні прапорці (SetUID, SetGID, Sticky bit) — старші 3 біти, які часто опускаються, коли дорівнюють нулю.
- Права власника (User: зчитування — 4, запис — 2, виконання — 1).
- Права групи (Group), з аналогічною семантикою.
- Права інших користувачів (Other).

Для розбору цього текстового запису ми застосуємо спеціалізований інструмент стандарту C++17 — функцію `std::from_chars`. Це найнижчорівневіша, але водночас найшвидша та найбезпечніша функція стандартної бібліотеки для конвертації тексту в числа. Її головні переваги: вона взагалі не залежить від поточної локалі системи, не потребує нуль-термінованого рядка, не виділяє пам'яті й повідомляє про помилки через коди повернення, а не винятки. Самі розібрані права ми інкапсулюємо у спеціальну структуру з бітовими полями. Це зробить конфігурацію прозорою, а простий метод `to_mask()` легко збере всі 12 бітів назад у звичайне ціле число для безпосередньої передачі в ядро операційної системи.

### 3. Як працюють ключові фрагменти

Розглянемо практичну реалізацію цього рішення:

```cpp
#include <string_view>
#include <charconv>
#include <system_error>
#include <optional>
#include <cstdint>

// Предметна модель вісімкових прав Unix
struct UnixPermissions {
    uint16_t special : 3;
    uint16_t user    : 3;
    uint16_t group   : 3;
    uint16_t other   : 3;

    // Збираємо 12-бітну маску для системних викликів (наприклад, chmod)
    [[nodiscard]] uint16_t to_mask() const noexcept {
        return (special << 9) | (user << 6) | (group << 3) | other;
    }
};

// Парсер, що не генерує винятків і не виділяє пам'яті
std::optional<UnixPermissions> parse_chmod_octal(std::string_view input) noexcept {
    // 1. Відкидаємо можливий програмістський префікс "0o" або класичний "0"
    if (input.starts_with("0o") || input.starts_with("0O")) {
        input.remove_prefix(2);
    } else if (input.starts_with('0') && input.length() > 1) {
        input.remove_prefix(1);
    }

    // 2. Права не можуть містити більше ніж 4 вісімкові цифри (максимум 7777)
    if (input.empty() || input.length() > 4) {
        return std::nullopt;
    }

    uint16_t raw_val = 0;
    
    // 3. Безпечний парсинг з основою 8 без аллокацій
    auto [ptr, ec] = std::from_chars(input.data(), input.data() + input.size(), raw_val, 8);

    // 4. Перевірка на успіх і відсутність зайвого «сміття» в кінці рядка
    if (ec != std::errc() || ptr != input.data() + input.size()) {
        return std::nullopt;
    }

    // 5. Розпакування зсувами для ініціалізації бітових полів
    return UnixPermissions{
        static_cast<uint16_t>((raw_val >> 9) & 7),
        static_cast<uint16_t>((raw_val >> 6) & 7),
        static_cast<uint16_t>((raw_val >> 3) & 7),
        static_cast<uint16_t>(raw_val & 7)
    };
}
```

Функція приймає `std::string_view`, тому вона вміє працювати зі зрізами рядків прямо з буфера (наприклад, пам'ять, відображена через `mmap`), уникаючи будь-яких копіювань. Сама `std::from_chars` приймає вказівник на початок і кінець фрагмента, чітко задану основу системи числення `8` і записує перетворене значення у змінну `raw_val`. Після цього ми розкладаємо отримане число на чотири логічні складові. Для цього використовується побітовий зсув вправо `>>` та маска `& 7`. Сімка у двійковій системі — це `111`, що ідеально виділяє рівно три молодші біти, відтинаючи все зайве, і ми отримуємо чисте значення кожної вісімкової цифри.

### 4. Інваріанти й граничні випадки

При розробці надійних парсерів найголовніше — правильно і безпечно обробити граничні ситуації та некоректний вхід:
- **Префікси:** Часто конфігурації свідомо передають вісімкові числа з префіксом `0` (класика мови C) або `0o` (поширено в Python, Rust та сучасних інструментах). Ми обережно та безболісно видаляємо їх, застосовуючи метод `remove_prefix`, який лише зсуває внутрішній вказівник об'єкта `string_view` на кілька байтів.
- **Переповнення:** Стандартні права Unix обмежуються суворо 12 бітами (максимальне валідне значення `7777` у вісімковій системі). Наша реалізація жорстко відкидає будь-які рядки, довші за 4 символи, захищаючи логіку ядра програми від безглуздих значень на кшталт `077777`.
- **Зайві символи:** Якщо на вхід подати зловмисний чи помилковий рядок типу `"755x"`, алгоритм парсингу зупиниться на букві `x`. У цьому разі вказівник `ptr`, повернутий структурою з `std::from_chars`, не дорівнюватиме кінцю рядка. Тоді ми надійно відхилимо такий вхід як повністю хибний, повернувши маркер відсутності значення `std::nullopt`.

### 5. Ввід, вивід та складність

З алгоритмічної точки зору, це рішення має часову складність `O(L)`, де `L` — довжина вхідного рядка. Але оскільки ми на самому початку жорстко обмежили допустиму довжину лише 4 символами, часова складність фактично стає абсолютною константою `O(1)`. Просторова складність також становить строге `O(1)`, адже ми взагалі не використовуємо динамічну пам'ять (купку) — уся робота виконується лише завдяки кільком байтам на стеку процесора. 

Вхідним інтерфейсом обрано `std::string_view`, що робить наше API максимально універсальним: воно працює без накладних витрат і з об'єктами `std::string`, і зі статичними масивами `char[]`, і з сирими буферами. На виході функція повертає тип `std::optional<UnixPermissions>`. Таке рішення примушує програміста-користувача явно й усвідомлено обробляти сценарій помилки. Це виключає катастрофічні наслідки в системному коді, коли через помилку парсингу файл міг би випадково отримати хибні права доступу (наприклад, відкрити конфіденційні дані всім користувачам замість надійної заборони).
