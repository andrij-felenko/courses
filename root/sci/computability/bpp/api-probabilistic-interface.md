# 📋 Специфікація інтерфейсу ймовірнісних алгоритмів та генераторів випадкових чисел

Цей довідник визначає уніфікований контракт системного інтерфейсу для обчислювальних модулів класу BPP. Всі ймовірнісні алгоритми з обмеженою хибою вимагають явного керування двома основними ресурсами: параметром допустимого ризику помилки (підсилення) та джерелом випадкової ентропії.

Спроектувати надійний програмний інтерфейс для BPP-обчислень значно складніше, ніж для звичайних детермінованих бібліотек. Головна причина полягає в тому, що BPP-алгоритми за своєю природою приховують двосторонній ризик помилки. Якщо традиційна функція повертає статус успіху або код помилки, то ймовірнісна функція повертає результат разом із математичною оцінкою надійності, яка фундаментально залежить від внутрішнього стану генератора випадкових чисел.

## 1. Контракт налаштування BPP-обчислювача

Кожен BPP-модуль приймає конфігураційну структуру `bpp_config_t`, яка задає граничну ймовірність помилки або фіксовану кількість випробувань, а також покажчик на контекст генератора випадкових чисел.

:::tabs
```c
/* c */
typedef enum {
    BPP_MODE_FIXED_ROUNDS = 0, /* Фіксоване число раундів k */
    BPP_MODE_TARGET_ERROR  = 1  /* Автоматична ампліфікація до заданої хиби epsilon */
} bpp_amplification_mode_t;

typedef struct {
    bpp_amplification_mode_t mode;
    uint32_t                 rounds_k;      /* Кількість повторень (при BPP_MODE_FIXED_ROUNDS) */
    double                   max_error_eps; /* Максимальна допустима хиба (наприклад, 1e-12) */
    void*                    rng_context;   /* Контекст генератора випадкових чисел */
    uint64_t (*rng_next_u64)(void* ctx);    /* Функція вибірки 64 випадкових бітів */
} bpp_config_t;
```
```cpp
// cpp
#include <cstdint>
#include <functional>

namespace bpp {

enum class AmplificationMode : std::uint8_t {
    FixedRounds = 0, // Фіксоване число раундів k
    TargetError = 1  // Автоматична ампліфікація до заданої хиби epsilon
};

struct BppConfig {
    AmplificationMode mode{AmplificationMode::FixedRounds};
    std::uint32_t     rounds_k{30};         // Кількість повторень
    double            max_error_eps{1e-9};  // Максимальна допустима хиба (наприклад, 1e-12)
    void*             rng_context{nullptr}; // Контекст генератора випадкових чисел
    std::function<std::uint64_t(void*)> rng_next_u64{}; // Функція вибірки 64 випадкових бітів
};

} // namespace bpp
```
:::

Структура `bpp_config_t` (або `bpp::BppConfig` у C++) відіграє роль основного контракту між викликаючим кодом та ймовірнісним обчислювачем. Вибір між двома режимами ампліфікації `BPP_MODE_FIXED_ROUNDS` та `BPP_MODE_TARGET_ERROR` визначає обчислювальний бюджет процедури. У режимі фіксованих раундів розробник явно обмежує час виконання, погоджуючись із отриманим рівнем помилки. У режимі цільової помилки бібліотека самостійно розраховує необхідне число запусків `k` за допомогою межі Чернова, виходячи з початкового зазору алгоритму `ε` та бажаного рівня хиби `max_error_eps`.

Поле `rng_context` дає змогу ізолювати стан генератора випадкових чисел між різними потоками виконання. Це є критично важливим для багатопотокових систем, де спільний доступ до одного генератора створює гонки за даними в оперативній пам'яті та руйнує гарантії статистичної незалежності випадкових вибірок.

### Опис полів конфігураційної структури

Режим `mode` визначає семантику інтерпретації параметрів обчислення. Якщо обрано `BPP_MODE_FIXED_ROUNDS`, значення `rounds_k` має бути додатним цілим числом. Замовчуване значення 30 раундів забезпечує зниження помилки до величини, меншої за `2⁻³⁰` для алгоритмів із початковою ймовірністю помилки `1/3`.

Поле `max_error_eps` використовується лише тоді, коли `mode` встановлено у значення `BPP_MODE_TARGET_ERROR`. Це значення визначає верхню межу ймовірності підсумкової алгоритмічної хиби. З міркувань математичної коректності значення `max_error_eps` має лежати строго у відкритому інтервалі `(0.0, 0.33]`. Спроба передати від'ємне значення, нуль або значення, більше за `0.33`, призводить до негайної відмови ініціалізації з кодом помилки `BPP_ERROR_INVALID_PARAM`.

Покажчик `rng_next_u64` повертає 64 випадкові біти за один виклик. Викликаючий код зобов'язаний надати функцію-генератор, яка гарантує рівномірний розподіл та статистичну незалежність.

## 2. Коди відповідей та статусів виконання

Оскільки BPP-алгоритми працюють із двостороннім ризиком помилки, результат обчислення повертається разом із оцінкою досягнутого рівня надійності та детальною статистикою виконання.

:::tabs
```c
/* c */
typedef enum {
    BPP_SUCCESS_ACCEPT     =  1, /* Слово належить мові (прийнято з гарантією 1 - eps) */
    BPP_SUCCESS_REJECT     =  0, /* Слово не належить мові (відхилено з гарантією 1 - eps) */
    BPP_ERROR_INVALID_PARAM = -1, /* Некоректні параметри (наприклад, eps >= 0.5) */
    BPP_ERROR_ENTROPY_FAIL = -2, /* Збій джерела випадкових чисел (виснаження ентропії) */
    BPP_ERROR_TIMEOUT      = -3  /* Перевищено часовий ліміт повторень */
} bpp_status_t;

typedef struct {
    uint32_t total_rounds_executed; /* Загальна кількість виконаних раундів k */
    uint32_t accept_votes;          /* Кількість раундів, що повернули 1 */
    uint32_t reject_votes;          /* Кількість раундів, що повернули 0 */
    double   estimated_error_bound; /* Обчислена верхня межа помилки за межею Чернова */
    uint64_t entropy_bytes_used;    /* Сумарний обсяг зчитаних випадкових байтів */
    uint64_t execution_time_us;     /* Час виконання у мікросекундах */
} bpp_execution_stats_t;
```
```cpp
// cpp
#include <cstdint>
#include <chrono>

namespace bpp {

enum class Status : int32_t {
    SuccessAccept    =  1, // Слово належить мові (прийнято)
    SuccessReject    =  0, // Слово не належить мові (відхилено)
    ErrorInvalidParam = -1, // Некоректні параметри (eps >= 0.5)
    ErrorEntropyFail  = -2, // Збій джерела випадкових чисел
    ErrorTimeout      = -3  // Перевищено часовий ліміт
};

struct ExecutionStats {
    std::uint32_t total_rounds_executed{0}; // Загальна кількість раундів k
    std::uint32_t accept_votes{0};          // Кількість раундів з відповіддю 1
    std::uint32_t reject_votes{0};          // Кількість раундів з відповіддю 0
    double        estimated_error_bound{1.0}; // Межа помилки Чернова
    std::uint64_t entropy_bytes_used{0};    // Обсяг використаної ентропії
    std::chrono::microseconds execution_time{0}; // Час виконання
};

} // namespace bpp
```
:::

Аналіз структури `bpp_execution_stats_t` дозволяє розробнику проводити моніторинг обчислювального процесу в реальному часі. Поля `accept_votes` та `reject_votes` відображають розподіл голосів за результатами `k` випробувань. Якщо співвідношення голосів близьке до 50/50, це свідчить про те, що алгоритм працює поблизу межі порогового зазору відокремлення, або що джерело випадковості має зміщення.

Поле `estimated_error_bound` містить підсумкову точну математичну оцінку ймовірності помилки, обчислену за формулою Чернова на основі реально виконаної кількості раундів. Поле `entropy_bytes_used` показує точний витрат випадкових бітів, що важливо для систем із обмеженим пулом апаратної ентропії (наприклад, в мікроконтролерах без безперервного джерела шуму).

## 3. Функціональний API інтерфейсу BPP-модуля

Системний контракт розробки BPP-обчислювачів передбачає чотири ключові процедури життєвого циклу:

:::tabs
```c
/* c */
bpp_status_t bpp_init(bpp_config_t* config);

bpp_status_t bpp_execute(const bpp_config_t* config, 
                         const uint8_t* data, 
                         size_t len, 
                         bpp_execution_stats_t* stats);

uint32_t bpp_calculate_required_rounds(double max_eps, double delta_gap);

void bpp_cleanup(bpp_config_t* config);
```
```cpp
// cpp
#include <span>
#include <expected>

namespace bpp {

class BppEngine {
public:
    explicit BppEngine(BppConfig config);
    ~BppEngine();

    [[nodiscard]] std::expected<Status, Status> execute(
        std::span<const std::uint8_t> data, 
        ExecutionStats& stats) const noexcept;

    [[nodiscard]] static std::uint32_t calculate_required_rounds(
        double max_eps, 
        double delta_gap) noexcept;

private:
    BppConfig config_;
};

} // namespace bpp
```
:::

Функція `bpp_init` (або конструктор `bpp::BppEngine`) виконує первинну перевірку конфігурації. Вона перевіряє коректність параметрів, тестує доступність джерела випадковості через пробний виклик `rng_next_u64` та виділяє необхідні внутрішні буфери. Якщо покажчик на конфігурацію є довільним або параметри виходять за допустимі межі, функція повертає `BPP_ERROR_INVALID_PARAM`.

Основна обчислювальна робота виконується у функції `bpp_execute` (`BppEngine::execute`). Вона приймає покажчик на вхідні дані `data` довжиною `len` байтів і проганяє `k` незалежних випробувань BPP-алгоритму. У кожному раунді алгоритм зчитує випадкові біти з `rng_context` і підраховує голоси прийняття або відхилення. За результатами голосування повертається відповідний код `BPP_SUCCESS_ACCEPT` або `BPP_SUCCESS_REJECT`, а у структуру `stats` записується повний звіт.

Допоміжна функція `bpp_calculate_required_rounds` реалізує точний розрахунок необхідної кількості раундів `k` за формулою Чернова:

```
k = ⌈ -ln(max_eps) / (2 · delta_gap²) ⌉
```

де `delta_gap` — гарантований пороговий зазор відокремлення даного BPP-алгоритму (наприклад, `1/6` для стандартного алгоритму з помилкою `1/3`). Ця функція є корисною для попереднього оцінювання обчислювальних витрат перед запуском ресурсоємних процедур.

Функція `bpp_cleanup` (або деструктор `BppEngine`) проводити безпечне очищення контексту, обнуляє сесійні ключі та випадкові біти у пам'яті проти атак витоку інформації та звільняє виділені буфери.

## 4. Специфікація алгоритмічних доменів та вимоги до ентропії

Різні практичні BPP-алгоритми мають різну початкову ймовірність помилки за один раунд, що вимагає специфічного розрахунку кількості раундів `k` для досягнення бажаного рівня надійності.

У тестуванні простоти методом Міллера — Рабіна початкова ймовірність помилки для складеного числа не перевищує `1/4`. Це означає, що зазор відокремлення є досить великим (`ε = 1/4`), тому для досягнення криптографічного рівня надійності з імовірністю помилки менше `10⁻⁹` достатньо лише 15 раундів випробувань.

У тесті Соловея — Штрассена ймовірність помилки становить `1/2`, тому зазор є меншим, і для досягнення тієї самої надійності вимагається вже 30 раундів. У алгоритмах перевірки поліноміальних тотожностей (лема Шварца — Зіпсела) ймовірність помилки `p = d / |S|` залежить від розміру скінченної множини `S`. Збільшуючи розмір множини `S`, розробник може зменшити число необхідних раундів до одного запуск при великому `|S|`.

Джерело випадкових чисел (RNG) є найвразливішим елементом BPP-системи. Якщо генератор псевдовипадкових чисел має корельовані біти або короткий період, імовірність підсумкової помилки перестає експоненційно згасати. Для криптографічних застосувань обов'язково використовувати генератори класу CSPRNG (наприклад, системний системний виклик `getrandom` у Linux або `BCryptGenRandom` у Windows), які забезпечують високу ентропію та захист від передбачення наступних бітів.
