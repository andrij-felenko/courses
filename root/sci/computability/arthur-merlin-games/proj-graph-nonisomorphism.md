# ⚙️ Реалізація AM-протоколу неізоморфізму графів: інтерактивний верифікатор та доводжувач

Цей практичний матеріал демонструє повну програмну реалізацію двораундового імовірнісного AM-протоколу для перевірки неізоморфізму графів (Graph Non-Isomorphism, GNI) мовами C та C++, показуючи механіку генерування публічного виклику Артуром, розпізнавання графа Мерліном, аналіз структурних масивів суміжності та алгоритми підсилення надійності доведення.

## Алгоритмічна модель та математична підвалина протоколу GNI

Задача неізоморфізму графів полягає у визначенні того, чи є два задані неорієнтовані графи `G₀ = (V, E₀)` та `G₁ = (V, E₁)` **неізоморфними** (`G₀ ≇ G₁`). Якщо графи ізоморфні (`G₀ ≅ G₁`), існує перестановка вершин `π ∈ Sₙ`, яка повністю зберігає суміжність ребр між усіма парами вершин `(u, v) ∈ E₀ ⇔ (π(u), π(v)) ∈ E₁`.

Для доведення неізоморфізму у класичній моделі детермінованих свідків `NP` потрібен свідок експоненційного розміру або складний алгоритм перевірки всіх `n!` перестановок. Проте у двораундовому імовірнісному протоколі Артура — Мерліна перевірка виконується за поліномний час за допомогою імовірнісного виклику.

Покрокова алгоритмічна послідовність дій одного інтерактивного раунду:
1. **Артур (Верифікатор)** рівномірно і незалежно обирає випадковий біт `b ∈ {0, 1}` та будує випадкову перестановку вершин `π ∈ Sₙ`. Потім він генерує викликовий граф `H = π(G_b)` і публічно передає його Мерліну.
2. **Мерлін (Доводжувач)** обчислює, якому саме з вихідних графів (`G₀` чи `G₁`) ізоморфний отриманий граф `H`. Якщо вихідні графи неізоморфні (`G₀ ≇ G₁`), то викликовий граф `H` може бути ізоморфним лише одному з них, тому Мерлін безпомилково визначає вихідний біт `b'` і надсилає його Артуру. Якщо ж вихідні графи ізоморфні (`G₀ ≅ G₁`), то граф `H` одночасно ізоморфний обом графам `G₀` та `G₁`. У цьому випадку Мерлін позбавлений будь-якої інформації про вибір Артура і змушений вгадувати біт `b'`, тому імовірність його успіху не перевищує `1/2`.
3. **Артур** порівнює відповідь Мерліна `b'` із початковим бітом `b`. Якщо `b' == b`, раунд вважається успішним; інакше Артур миттєво відхиляє доказ і зупиняє роботу.

Повторюючи цей протокол `k` разів послідовно та незалежно, імовірність того, що Мерлін зможе обдурити Артура для двох ізоморфних графів, падає до `(1/2)^k`.

```
                  Схема інтерактивного раунду GNI
   Артур (Поліноміальний імовірнісний)        Мерлін (Обчислювальний оракул)
   ┌──────────────────────────────────┐      ┌─────────────────────────────┐
   │ 1. Обирає монету b ∈ {0, 1}      │      │                             │
   │ 2. Генерує перестановку π ∈ Sₙ   │      │                             │
   │ 3. Будує граф H = π(G_b)         │──H──>│ Перевіряє H ≅ G₀ чи H ≅ G₁  │
   │                                  │      │ Приймає рішення b' ∈ {0, 1} │
   │ 4. Приймає якщо b' == b          │<──b'─│                             │
   └──────────────────────────────────┘      └─────────────────────────────┘
```

## Вибір структур даних та генерація перестановок

Для ефективної програмної симуляції верифікатора Артура та оракула Мерліна критичним є вибір внутрішнього представлення графів та джерела випадкових перестановок.

### Представлення матрицею суміжності
У нашій реалізації графи розглядаються як двовимірні булеві матриці суміжності `adj[n][n]`. Для неорієнтованих графів без петель матриця є симетричною (`adj[i][j] == adj[j][i]`), а діагональні елементи є нульовими (`adj[i][i] == false`).
Перевагою матриці суміжності для малих і середніх графів (`n ≤ 64`) є константний час перевірки суміжності `O(1)` та висока локальність даних у кеші процесора. Застосування перестановки `π` до графа створює новий граф `H`, де елемент `H.adj[π[i]][π[j]] = G.adj[i][j]`.

### Алгоритм Фішера — Йейтса для генерації перестановок
Щоб Артур згенерував рівномірно випадкову перестановку `π ∈ Sₙ`, застосовується класичний алгоритм Фішера — Йейтса (Fisher-Yates shuffle). Починаючи з тотожної перестановки `perm[i] = i`, алгоритм на кожному кроці `i` від `n - 1` до `1` обирає випадковий індекс `j ∈ [0, i]` і міняє місцями елементи `perm[i]` та `perm[j]`. Це гарантує, що кожна з `n!` можливих перестановок генерується з однаковою ймовірністю `1 / n!`.

## Аналіз інженерних пасток та крайових випадків

При практичній розробці імовірнісних інтерактивних систем та верифікаторів Артура — Мерліна виникає низка критичних технологічних пасток, які можуть непомітно повністю зруйнувати коректність протоколу:

1. **Неякісні генератори випадкових чисел (Entropy Collapse).** Використання стандартного `rand()` мови C без криптографічно стійкого посіву призводить до того, що послідовність монет Артура стає передбачуваною. Якщо Мерлін зможе обчислити генератор випадкових чисел Артура, він зможе заздалегідь знати вибір біта `b` та перестановку `π`, що дозволить йому успішно обдурювати Артура навіть для абсолютно ізоморфних графів. Для промислових систем необхідно використовувати криптографічно стійкі джерела псевдовипадкових бітів (CSPRNG, такі як `std::random_device` або системний ентропійний пул `/dev/urandom`).

2. **Обчислювальна складність оракула Мерліна.** У нашій симуляції оракул Мерліна реалізований як простий рекурсивний алгоритм повного перебору перестановок вершини, складність якого становить `O(n!)`. Теоретична модель Артура — Мерліна припускає, що Мерлін має необмежену обчислювальну потужність, однак при локальному запуску програми розмір графів обмежений значеннями `n ≤ 10`. На практиці для більших графів використовуються спеціалізовані солвери ізоморфізму, такі як `Nauty` чи `Traces`.

3. **Аналіз імовірності помилки при ізоморфних графах.** У разі, коли на вхід подано два ізоморфні графи `G₀ ≅ G₁`, Мерлін змушений робити випадкову здогадку про значення біта `b`. Імовірність успішної відповіді Мерліна у кожному раунді становить точно `1/2`. Після `k = 10` раундів імовірність того, що Мерлін випадково вгадає відповіді у всіх 10 раундах поспіль, становить:

```
Pr [ Cheat ] = (1/2)¹⁰ = 1 / 1024 ≈ 0.000976 (менше 0.1%)
```

Для досягнення криптографічної точності (наприклад, ймовірність помилки менше `2⁻⁸⁰`) верифікатор Артур здійснює 80 паралельних або послідовних раундів виклику.

## Оптимізація продуктивності та порівняння складність

Нижче наведено таблицю порівняльного аналізу витрат ресурсів для детермінованого перебору ізоморфізму та імовірнісної AM-верифікації:

```
                 Порівняння підходів верифікації GNI
┌──────────────────────────────┬────────────────────────┬────────────────────────────┐
│ Параметр                     │ Детермінований перебір │ AM-протокол Артура         │
├──────────────────────────────┼────────────────────────┼────────────────────────────┤
│ Часова складність верифікатора│ O(n! · n²)             │ O(k · n²)                  │
│ Потребність у пам'яті        │ O(n²)                  │ O(n²)                      │
│ Тип монет                    │ Немає                  │ Публічні випадкові монети   │
│ Імовірність помилки (Soundness)│ 0.0 (Абсолютна)       │ (1/2)^k (Експоненційна)    │
│ Опорні теоретичні класи      │ coNP                   │ AM (Arthur-Merlin)         │
└──────────────────────────────┴────────────────────────┴────────────────────────────┘
```

Завдяки зниженню складності верифікатора до `O(k · n²)`, AM-протокол робить перевірку складних складнісних тверджень доступною навіть для найбільш обмежених обчислювальних пристроїв.
