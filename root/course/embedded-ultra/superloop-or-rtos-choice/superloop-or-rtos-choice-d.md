Польотний контролер квадрокоптера на базі мікроконтролера STM32 має кожні 125 мікросекунд (на частоті 8 кГц) зчитувати дані гіроскопа через шину SPI, фільтрувати шуми вібрацій рами й розраховувати керівний вплив чотирьох моторів за алгоритмом PID-регулятора. Увесь обчислювальний контур стабілізації мусить укладатися в 60 мікросекунд, залишаючи залишок часу процесора для фонової периферії: розбору пакетів навігації GPS на швидкості 115200 бод, обміну телеметрією MAVLink через UART, опитування барометра по шині I²C на частоті 50 Гц та скидання 512-байтних блоків польотного логу на Flash-пам'ять. Якщо під час запису сектору Flash мікроконтролер затримується на 350 мікросекунд через очікування внутрішньої готовності чипа, контур стабілізації пропускає три цикли поспіль; безперервний зворотний зв'язок розривається, виникає наростаюче фазове запізнення, кутова швидкість апарата виходить з-під контролю, і дрон зривається в некерований штопор.

Ця інженерна проблема вибору між суворим мікросекундним детермінізмом швидкого контуру та обслуговуванням повільних підсистем стоїть перед кожним розробником вбудованих систем. Існує два фундаментально різних шляхи організації архітектури прошивки: суперцикл (Super-loop із кінцевими автоматами в перериваннях) та витісняльна операційна система реального часу (RTOS, Real-Time Operating System).

## Механіка суперциклу: спільний стек і кінцеві автомати

У найпростішому варіанті мікроконтролер виконує одну нескінченну послідовність інструкцій, розміщену всередині функції `main()`. Процесор по черзі викликає функції обробки кожної периферійної підсистеми, після чого повертається на початок циклу.

Така структура називається суперциклом (Super-loop — від латинського *super*, що означає «понад, зверху», та грецького *kyklos* — «коло, оберт»).

У базовому суперциклі без переривань час реакції системи на зовнішню подію повністю визначається сумою тривалостей виконання всіх функцій, що стоять у черзі:

```
T_loop = T_gyro + T_pid + T_motors + T_gps + T_mavlink + T_baro + T_flash
```

Розглянемо часовий бюджет кожного кроку типового польотного циклу на процесорі ARM Cortex-M4 з тактовою частотою 168 МГц:

* **Зчитування гіроскопа (`T_gyro`):** передача 14 байтів по шині SPI на швидкості 10 МГц займає близько 12 мікросекунд при синхронному блокуючому опитуванні.
* **Фільтрація та PID-регулятор (`T_pid`):** обчислення рекурсивних біквадратних фільтрів (Biquad Notch Filter) та пропорційно-інтегрально-диференціального контуру займає близько 28 мікросекунд.
* **Генерація протоколу Dshot (`T_motors`):** формування цифрового пакета для регуляторів швидкості моторів займає 16 мікросекунд.
* **Розбір кадру GPS (`T_gps`):** парсинг рядків NMEA / UBX із кільцевого буфера займає від 15 до 45 мікросекунд.
* **Обробка телеметрії MAVLink (`T_mavlink`):** пакування параметрів стану та підрахунок контрольної суми CRC-16 займає 30 мікросекунд.
* **Зчитування барометра I²C (`T_baro`):** транзакція читання по повільній шині I²C (400 кГц) займає близько 80 мікросекунд.
* **Скидання логів на SPI Flash (`T_flash`):** передача сторінки на 256 байтів та очікування біта зайнятості (WIP, Write In Progress) всередині чипа Flash-пам'яті займає від 200 до 400 мікросекунд.

Якщо функція `T_flash` виконує блокуюче очікування прапорця зайнятості шини, тривалість одного оберту циклу розтягується майже до пів мілісекунди. Часове відхилення фактичного моменту виконання задачі від її розрахункового періоду називають джиттером (Jitter / тремтіння затримки — від середньоанглійського *chiteren*, що означає «дрижати, вібрувати»). У простому суперциклі джиттер найважливішої задачі дорівнює максимальному часу виконання найдовшої фонової операції:

```
Jitter_gyro = max(T_task_exec)
```

Для стабілізації динамічних систем (мультироторних дронів, балансуючих роботів, векторних приводів) джиттер контуру зворотного зв'язку є критичним параметром. Якщо коефіцієнти PID-регулятора розраховані на фіксований крок інтегрування `dt = 125` мкс, а реальний інтервал між викликами через запис Flash коливається від 60 мкс до 450 мкс, інтегральна складова накопичує помилку (Error Accumulation), а диференціальна складова видає потужні помилкові сплески на мотори.

### Розбиття на неблокуючі кінцеві автомати (FSM)

Щоб подолати затримки суперциклу, архітектуру модифікують: швидку первинну обробку переносять в апаратні обробники переривань (ISR, Interrupt Service Routine) та канали прямого доступу до пам'яті (DMA), а тривалі фонові задачі всередині головного циклу розбивають на неблокуючі кінцеві автомати (FSM, Finite State Machine).

```
+-------------------------------------------------------------------+
|                        ГОЛОВНИЙ ЦИКЛ                              |
|                                                                   |
|   1. Перевірити прапорець готовності DMA гіроскопа                |
|   2. Якщо готово -> порахувати PID -> оновити ШІМ моторів         |
|   3. Виконати один мікрокрок автомата запису Flash                |
|   4. Виконати парсинг одного байта з кільцевого буфера UART       |
+-------------------------------------------------------------------+
             ^                                       ^
             | Апаратне переривання                  | DMA завершив прийом
+----------------------------+       +------------------------------+
|  EXTI_IRQHandler (1 кГц)   |       |  DMA1_Channel_IRQHandler     |
|  Встановлює gyro_ready=1   |       |  Перекладає байти GPS у буфер|
+----------------------------+       +------------------------------+
```

Розбиття довгої процедури на стани усуває блокування ядра. Замість очікування завершення запису сторінки Flash-пам'яті функція розділяється на кроки:

1. `FLASH_STATE_IDLE` — очікування наявності повного буфера даних для запису.
2. `FLASH_STATE_SEND_WRITE_ENABLE` — відправка команди розблокування запису по SPI.
3. `FLASH_STATE_START_PAGE_PROGRAM` — передача адреси та корисного навантаження (256 байтів) по каналу DMA.
4. `FLASH_STATE_POLL_WIP` — перевірка біта зайнятості чипа через зчитування регістра статусу.
5. `FLASH_STATE_COMPLETE` — фіксація успішного запису та перехід у стан очікування.

На кожній ітерації суперциклу функція виконує лише один крок або перевіряє статус апаратного регістра без пауз, витрачаючи менш ніж 1–2 мікросекунди процесорного часу.

### Бюджет пам'яті в суперциклі

Головна перевага суперциклу — мінімальне споживання оперативної пам'яті (ОЗП / SRAM). Уся програма працює в єдиному адресному просторі стека, використовуючи головний покажчик стека процесора (MSP, Main Stack Pointer).

Оскільки функції викликаються послідовно, стек не зберігає одночасний стан декількох паралельних завдань. Необхідний розмір стека дорівнює найбільшій глибині викликів серед усіх функціональних гілок плюс розмір контексту одного вкладеного переривання:

```
RAM_stack_superloop = max(Stack_Depth(Task_i)) + Frame_ISR
```

Під час компіляції розробник може точно виміряти максимальне використання стека суперциклу за допомогою прапорця GCC `-fstack-usage` та аналізу графа викликів (Call Graph Analysis). Для більшості вбудованих задач на мікроконтролерах із ядром ARM Cortex-M весь стек суперциклу займає від 512 до 1024 байтів. Уся інша оперативна пам'ять залишається вільною для статичних буферів, масивів калібрувань та корисних структур даних.

*Порівняння часової шкали: поява джиттера в кооперативному суперциклі через блокуючі операції та детерміноване витіснення у витісняльній RTOS.*

## Механіка витісняльної RTOS: багатозадачність і перемикання контексту

Коли кількість підсистем зростає до десятків (додається складна навігація, файлова система FATFS на SD-картці, мережевий стек TCP/IP, моніторинг шини CAN), розбиття кожної операції на неблокуючі стани вимагає створення сотень глобальних змінних і перетворює код на складну для супроводу структуру. Будь-яка помилка сторонньої бібліотеки, яка виконує внутрішній цикл очікування, блокує весь пристрій.

Для вирішення цієї проблеми застосовують операційну систему реального часу (RTOS). Її ключовим механізмом є витіснення (Preemption — від латинського *praeemptio*, утвореного від *prae-* «наперед» та *emere* «захоплювати, купувати»).

Витіснення означає здатність планувальника ядра примусово призупинити виконання поточної низькопріоритетної задачі в довільний момент часу та передати керування високопріоритетній задачі, яка щойно перейшла в стан готовності.

Термін «диспетчер» або «планувальник» (Scheduler) походить від старофранцузького *cedule* та латинського *schedula*, що означає «аркуш паперу, розклад, список дій».

### Анатомія перемикання контексту на ARM Cortex-M

Контекстом задачі називається повний набір значень внутрішніх регістрів процесора, покажчика інструкцій та стану пам'яті, необхідний для відновлення її виконання з точністю до одного такту.

Термін «контекст» походить від латинського *contextus* (від *con-* «разом» та *texere* «ткати, зчіплювати», тобто «зчеплення, тісний зв'язок частин»). Перемикання контексту (Context switch — від давньоанглійського *swician*, «переходити, повертати») на мікроконтролерах архітектури ARM Cortex-M4/M7 реалізовано як двоетапна процедура з апаратною та програмною підтримкою.

Архітектура ARM Cortex-M має два роздільних покажчики стека:
1. **Головний покажчик стека (MSP, Main Stack Pointer):** використовується ядром операційної системи, системними винятками та обробниками переривань ISR.
2. **Процесний покажчик стека (PSP, Process Stack Pointer):** використовується прикладними нитками виконання (задачами RTOS) у непривілейованому або привілейованому режимі нитки (Thread Mode).

Процедура перемикання контексту складається з таких фаз:

1. **Апаратне автозбереження (Hardware Stacking):** Під час виникнення винятку або таймерного переривання SysTick процесор автоматично зберігає у поточному процесному стеку (PSP) 8 базових регістрів:
   `xPSR` (регістр стану), `PC` (адреса повернення), `LR` (регістр зв'язку), `R12`, `R3`, `R2`, `R1`, `R0`.

2. **Програмне дозбереження (Software Stacking):** Спеціальний службовий обробник `PendSV_Handler` (виняток із найнижчим пріоритетом переривань) зберігає решту регістрів ядра (`R4–R11`), зчитує поточне значення покажчика PSP і записує його в структуру дескриптора задачі — блок керування завданням (TCB, Task Control Block).

Термін «блок» походить від французького *bloc* («брила, згусток»), а слово «завдання» (Task) сходить до пізньолатинського *taxare* («оцінювати, призначати обов'язок»).

```
               АПАРАТНИЙ ТА ПРОГРАМНИЙ КАДР СТЕКА ЗАДАЧІ
         
         Високі адреси  +--------------------------------+
                        |  xPSR                          | <-- Автоматично зберігає
                        |  PC (Program Counter)          |     процесор ARM Cortex-M
                        |  LR (Link Register)            |     під час входу в переривання
                        |  R12                           |     (8 слів = 32 байти)
                        |  R3, R2, R1, R0                |
                        +--------------------------------+
                        |  R11, R10, R9, R8              | <-- Зберігає асемблерний
                        |  R7, R6, R5, R4                |     код PendSV_Handler
                        |  (S16-S31 якщо увімкнено FPU)  |     (8 слів = 32 байти)
         Низькі адреси  +--------------------------------+ <-- PSP збережено в TCB->pxTopOfStack
```

Особливу роль відіграє апаратний блок обчислень із плаваючою комою (FPU, Floating Point Unit). Якщо задача використовує інструкції FPU, процесор підтримує механізм ледачого збереження (Lazy Stacking, біт `FPCCR.LSPEN = 1`). Процесор резервує місце на стеку під 16 регістрів `S0–S15` та регістр статусу `FPSCR` (додаткові 68 байтів), проте фізичний запис у пам'ять відкладається доти, доки обробник переривання справді не виконає першу інструкцію з плаваючою комою. Це скорочує час входу в ISR до стандартних 12 тактів.

Повернення з обробника переривання керується спеціальним магічним значенням регістра `LR`, який називається кодом виходу з винятку (`EXC_RETURN`):

* `0xFFFFFFF9` — повернення в режим обробника (Handler Mode), відновлення стека з головного покажчика MSP.
* `0xFFFFFFFD` — повернення в режим нитки (Thread Mode), відновлення базового кадру з процесного покажчика PSP (без блоку FPU).
* `0xFFFFFFED` — повернення в режим нитки (Thread Mode), повне апаратне відновлення регістрів ядра та плаваючої коми FPU з процесного покажчика PSP.

Асемблерний код перемикання контексту у FreeRTOS на Cortex-M демонструє повну послідовність дій:

```
PendSV_Handler:
    mrs r0, psp                 [зчитати покажчик стека поточної задачі]
    isb                         [бар'єр синхронізації інструкцій]
    ldr r3, =pxCurrentTCB       [завантажити адресу покажчика на поточний TCB]
    ldr r2, [r3]
    stmdb r0!, {r4-r11}         [програмно зберегти регістри r4-r11 на стек задачі]
    str r0, [r2]                [зберегти нову вершину стека в перше поле TCB]

    ldr r1, =vTaskSwitchContext [викликати планувальник ядра для вибору нової задачі]
    push {r3, lr}
    blx r1                      [pxCurrentTCB тепер вказує на наступну готову задачу]
    pop {r3, lr}

    ldr r2, [r3]
    ldr r0, [r2]                [отримати вершину стека нової задачі з її TCB]
    ldmia r0!, {r4-r11}         [відновити регістри r4-r11 нової задачі]
    msr psp, r0                 [встановити новий покажчик процесного стека PSP]
    isb
    bx lr                       [повернення з винятку: апарат розгортає r0-r3, r12, lr, pc, xpsr]
```

Завдяки такій апаратній схемі тривалість перемикання контексту на процесорі STM32F4 (168 МГц) становить близько 80–120 тактів ядра, тобто менш ніж 1 мікросекунду. Високопріоритетна задача стабілізації польоту витісняє повільний запис Flash миттєво, отримуючи майже нульовий джиттер запуску.

## Ціна багатозадачності: споживання оперативної пам'яті

Головним компромісом використання RTOS є плата оперативною пам'яттю за ізоляцію потоків виконання.

У витісняльній системі будь-яка задача може бути зупинена в момент, коли вона перебуває на максимальній глибині вкладеності своїх функцій і виділила локальні змінні. Це означає, що кожна задача мусить мати власний повністю виділений і неперекривний масив стека в ОЗП.

Формула розрахунку пам'яті під стеки в RTOS має вигляд:

```
RAM_rtos_stacks = ∑ (Stack_Size_Task[k] + sizeof(TCB)) + Stack_Idle + Stack_Timer
```

Розглянемо типовий розподіл пам'яті для польотного контролера на FreeRTOS:

* **Task_FlightControl (8 кГц):** обчислення PID, матриці орієнтації, робота з плаваючою комою (FPU фрейм вимагає додаткових 136 байтів на контекст) — мінімум 2048 байтів.
* **Task_Telemetry (50 Гц):** пакування структур MAVLink, CRC, буферизація повідомлень — 2048 байтів.
* **Task_FlashLogger (1 кГц):** файловий буфер, кодування Blackbox — 3072 байти.
* **Task_GPS (10 Гц):** розбір рядків NMEA / UBX, математика перетворення координат — 1536 байтів.
* **Task_BaroMag (50 Гц):** інтерполяція таблиць температури, тригонометрія компенсації нахилу — 1536 байтів.
* **Task_Idle + Task_Timer:** системні службові задачі ядра FreeRTOS — 1024 байти.
* **Дескриптори TCB, черги IPC, м'ютекси, лічильники семафорів:** близько 2500 байтів.

Разом під потреби багатозадачності RTOS виділяється близько 13.7 КБ оперативної пам'яті. Якщо мікроконтролер має всього 32 КБ або 48 КБ RAM (наприклад, чипи STM32F303 або STM32F411), виділення 14 КБ лише на каркас операційної системи забирає від 30% до 45% усієї доступної пам'яті кристала.

```
+--------------------------------------------------------------------------+
|  РОЗПОДІЛ ОЗП (SRAM): СУПЕРЦИКЛ ПРОТИ RTOS НА ЧИПІ З 64 КБ ПАМ'ЯТІ        |
|                                                                          |
|  Super-loop:                                                             |
|  [ Стек 1 КБ ][ .data/.bss 4 КБ ][ Вільна ОЗП для буферів: 59 КБ (92%) ] |
|                                                                          |
|  FreeRTOS:                                                               |
|  [ Стеки задач: 12 КБ ][ TCB+ОС: 2.5 КБ ][ .bss: 4 КБ ][ Вільна: 45.5 КБ]|
+--------------------------------------------------------------------------+
```

Якщо інженер помилково виділить задачі `Task_Telemetry` замість 2048 байтів лише 1024 байти, під час передачі довгого пакету на максимальній глибині виклику `sprintf` стек вийде за межі виділеного масиву й затре байти сусіднього дескриптора TCB. Виникне важковловимий збій переповнення стека (Stack Overflow), який призводить до зависання мікроконтролера у винятку `HardFault_Handler`.

Для захисту від таких збоїв RTOS використовує метод канарок стека (Stack Canary / Watermark): під час створення задачі її стек заповнюється магічним шаблоном байтів (наприклад, `0xA5`). Під час кожного перемикання контексту або виклику `uxTaskGetStackHighWaterMark()` ядро перевіряє, скільки байтів шаблону на дні стека залишилися недоторканими.

У системах критичної надійності (авіоніка стандарту DO-178C) динамічне виділення пам'яті через купу (`pvPortMalloc` / `free`) суворо заборонено через ризик непередбачуваної фрагментації пам'яті (Heap Fragmentation). Усі задачі, черги та семафори мусять створюватися виключно статично за допомогою функцій сімейства `xTaskCreateStatic()`, що вимагає виділення фіксованих масивів у секції `.bss` на етапі лінкування.

![Розподіл оперативної пам'яті: Super-loop проти RTOS](/root/course/embedded-ultra/superloop-or-rtos-choice/img/ram-budget-comparison.svg)
*Бюджет оперативної пам'яті: компактний єдиний стек головного циклу проти множини ізольованих стеків під кожну задачу в RTOS.*

## Пастки синхронізації: інверсія пріоритетів і взаємні блокування

У суперциклі гонки за даними можливі лише на межі між основним циклом і перериваннями ISR. В RTOS будь-яка задача може бути витіснена іншою задачею в будь-який момент, що створює критичні секції при доступі до спільних ресурсів (спільна шина SPI, апаратний таймер, пам'ять стану).

Для захисту ресурсів використовують м'ютекси (Mutex, взаємне виключення). Проте м'ютекси породжують специфічну для RTOS небезпеку — інверсію пріоритетів (Priority Inversion — від латинського *prior*, «перший, попереду», та *inversio*, «перевертання, порушення порядку»).

Сценарій класичної інверсії пріоритетів розгортається наступним чином:

1. Низькопріоритетна задача `Task_Flash` захоплює м'ютекс спільної шини SPI для запису сектора логу.
2. Спрацьовує переривання готовності гіроскопа, і високорівнева задача `Task_Gyro_PID` переходить у стан готовності, миттєво витісняючи `Task_Flash`.
3. Задачі `Task_Gyro_PID` необхідно прочитати дані з гіроскопа по тій самій шині SPI. Вона намагається взяти м'ютекс SPI, але він зайнятий. Планувальник блокує задачу `Task_Gyro_PID` і повертає керування задачі `Task_Flash`.
4. У цей момент надходить пакет телеметрії, і прокидається середньопріоритетна задача `Task_MAVLink`. Оскільки її пріоритет вищий за `Task_Flash`, а шина SPI їй не потрібна, вона витісняє `Task_Flash` і починає тривалі обчислення.

У результаті найвищий пріоритет системи (`Task_Gyro_PID`) опиняється заблокованим на невизначений час через виконання середньої задачі `Task_MAVLink`, яка навіть не торкається спільного ресурсу. Якщо час затримки перевищить допустимий дедлайн, літальний апарат втратить керування.

```
Високий (Гіроскоп)  ---\           /----------------[ ЧЕКАЄ М'ЮТЕКС ]--------->
                        \         /
Середній (MAVLink)  -----\-------/------------[ ВИКОНУЄТЬСЯ ТЕЛЕМЕТРІЯ ]------->
                          \     /
Низький (Flash SPI) [ ВЗЯВ М'ЮТЕКС ]---\ (витіснений) ------------------------->
```

Найвідомішим історичним прикладом цієї вади стала місія космічного апарата NASA Mars Pathfinder у 1997 році. Бортовий комп'ютер під керуванням RTOS VxWorks періодично перезавантажувався сторожовим таймером Watchdog через те, що низькопріоритетна задача збору метеорологічних даних блокувала м'ютекс інформаційної шини, задача обміну даними середнього пріоритету витісняла її, а високопріоритетна задача керування орієнтацією марсохода не встигала отримати доступ до шини й пропускала свій дедлайн. Проблему вирішили дистанційно із Землі, передавши команду увімкнення протоколу успадкування пріоритету в ядрі операційної системи.

Для запобігання цій аварійній ситуації застосовують протокол успадкування пріоритету (Priority Inheritance Protocol, PIP). Якщо високопріоритетна задача блокується на м'ютексі, планувальник ядра тимчасово підвищує пріоритет задачі-власника ресурсу (`Task_Flash`) до рівня запитуючої задачі. Середня задача `Task_MAVLink` більше не може її витіснити, `Task_Flash` швидко звільняє шину SPI, її пріоритет повертається до початкового, а `Task_Gyro_PID` негайно отримує доступ до шини.

Реалізація протоколів успадкування вимагає додаткових обчислень усередині ядра при кожному взятті та звільненні м'ютекса, збільшуючи накладні витрати операційної системи.

Друга класична загроза синхронізації — взаємне блокування (Deadlock — від давньоанглійського *dead* та *loc* «замкнений простір»), коли задача 1 захопила шину SPI і чекає м'ютекс DMA, а задача 2 захопила DMA і чекає звільнення SPI. Для запобігання дедлокам у реальному коді застосовують сувору ієрархію захоплення замків (Lock Ordering) або використовують виключно черги повідомлень без спільних блокувань.

![Інверсія пріоритетів на спільній шині SPI](/root/course/embedded-ultra/superloop-or-rtos-choice/img/priority-inversion-mutex.svg)
*Блокування високопріоритетної задачі через захоплення спільного ресурсу низькопріоритетною задачею та її витіснення фоновим процесом.*

## Гібридний підхід: Кооперативний планувальник

Між простим неорганізованим суперциклом та важкою витісняльною RTOS існує проміжне інженерне рішення, яке поєднує переваги обох підходів: кооперативний періодичний планувальник (Cooperative Task Scheduler).

Саме ця архітектура історично використовується в найефективніших прошивках для гоночних квадрокоптерів (таких як Betaflight, Cleanflight та iNav), де критично важливо утримувати частоту оновлення моторів на рівні 8 кГц із нульовими накладними витратами на перемикання стеків.

Принцип роботи кооперативного диспетчера полягає в наступному:

1. Усі задачі виконуються в єдиному контексті головного циклу зі спільним покажчиком стека MSP.
2. Задачі не витісняють одна одну, а викликаються почергово як звичайні функції C/C++.
3. Кожна задача має заздалегідь визначений період виклику та статичний пріоритет.
4. Планувальник використовує апаратний таймер мікросекунд (`micros()`) для визначення точного моменту запуску та вибору найбільш пріоритетної готової задачі.
5. Найшвидший критичний контур (читання гіроскопа через SPI по DMA) запускається апаратним перериванням із найвищим пріоритетом NVIC, повністю оминаючи планувальник.

Узагальнена структура кооперативного диспетчера демонструє простоту й прозорість цього підходу:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

typedef void (*task_callback_t)(uint32_t current_time_us);

typedef struct {
    task_callback_t run;
    uint32_t period_us;
    uint32_t next_run_us;
    uint8_t priority;
} task_entry_t;

#define NUM_TASKS 3

static void task_attitude_pid(uint32_t now) {
    /* Розрахунок стабілізації (тривалість 35 мкс) */
}

static void task_telemetry_mavlink(uint32_t now) {
    /* Передача телеметрії (тривалість 25 мкс) */
}

static void task_battery_monitor(uint32_t now) {
    /* Зчитування АЦП напруги батареї (тривалість 10 мкс) */
}

static task_entry_t task_table[NUM_TASKS] = {
    { task_attitude_pid,      1000, 0, 10 }, /* 1 кГц, пріоритет 10 */
    { task_telemetry_mavlink, 20000, 0, 5 },  /* 50 Гц, пріоритет 5  */
    { task_battery_monitor,  100000, 0, 1 }   /* 10 Гц, пріоритет 1  */
};

void run_cooperative_scheduler(void) {
    uint32_t now = get_system_micros();
    int8_t best_task = -1;
    uint8_t highest_priority = 0;

    /* Вибір найбільш пріоритетної готової задачі */
    for (uint8_t i = 0; i < NUM_TASKS; ++i) {
        if ((int32_t)(now - task_table[i].next_run_us) >= 0) {
            if (best_task == -1 || task_table[i].priority > highest_priority) {
                best_task = i;
                highest_priority = task_table[i].priority;
            }
        }
    }

    if (best_task >= 0) {
        task_entry_t *t = &task_table[best_task];
        t->run(now);
        t->next_run_us += t->period_us;
    }
}
```
```cpp
#include <cstdint>
#include <array>
#include <algorithm>

class FlightTaskScheduler {
public:
    using Callback = void (*)(uint32_t now_us);

    struct TaskDescriptor {
        Callback execute{nullptr};
        uint32_t period_us{0};
        uint32_t next_run_us{0};
        uint8_t priority{0};
    };

    template <size_t N>
    static void dispatch(std::array<TaskDescriptor, N>& tasks) noexcept {
        const uint32_t now = get_system_micros();
        int32_t selected_index = -1;
        uint8_t highest_prio = 0;

        for (size_t i = 0; i < N; ++i) {
            const auto& task = tasks[i];
            if (static_cast<int32_t>(now - task.next_run_us) >= 0) {
                if (selected_index == -1 || task.priority > highest_prio) {
                    selected_index = static_cast<int32_t>(i);
                    highest_prio = task.priority;
                }
            }
        }

        if (selected_index >= 0) {
            auto& ready_task = tasks[static_cast<size_t>(selected_index)];
            ready_task.execute(now);
            ready_task.next_run_us += ready_task.period_us;
        }
    }

private:
    static uint32_t get_system_micros() noexcept;
};
```

## Інженерні критерії вибору: коли що застосовувати

Вибір між архітектурами не є питанням уподобань — це точний розрахунок часових дедлайнів, обсягу пам'яті та складності підсистем пристрою.

### Коли обирати Super-loop або Кооперативний Scheduler:
1. **Жорсткий бюджет ОЗП:** Мікроконтролер має менш ніж 32–64 КБ RAM. Виділення стеків під задачі RTOS призведе до вичерпання пам'яті або ризику переповнення стека.
2. **Екстремальні частоти контуру керування:** Частота оновлення перевищує 2–8 кГц. Накладні витрати на виклики планувальника ядра та перемикання контексту RTOS спалюватимуть занадто великий відсоток корисного часу процесора.
3. **Усі драйвери написані самостійно:** Розробник повністю контролює периферію і може реалізувати роботу з шинами I²C, SPI та UART через неблокуючі апаратні переривання або DMA.
4. **Критична надійність без взаємних блокувань:** Потрібна гарантія відсутності гонок між нитками (Deadlock), інверсії пріоритетів та корупції пам'яті сусідніх стеків.

### Коли обирати витісняльну RTOS (FreeRTOS, NuttX, ChibiOS):
1. **Багатокомпонентні автономні системи:** Проєкт включає десятки різнорідних функцій: картографію, розширений фільтр Калмана (EKF), роботу з файловою системою, протокол MAVLink та оновлення прошивки по повітрю (OTA).
2. **Використання готових блокуючих стеків:** Застосовуються сторонні складні бібліотеки (стек TCP/IP lwIP, USB Host, бібліотека FATFS, драйвери бездротових модулів), які розраховані на блокуючий ввід-вивід і вимагають окремих ниток виконання.
3. **Обчислювальний запас апаратного забезпечення:** Процесор має високу тактову частоту (від 168–480 МГц) і обсяг пам'яті від 128 КБ до 1 МБ RAM (чипи STM32F7, STM32H7, ESP32-S3).
4. **Велика команда розробників:** Окремі інженери пишуть незалежні модулі прошивки. Ізоляція коду в межах власних задач RTOS із чіткими чергами повідомлень (IPC) спрощує паралельну розробку та інтеграцію.

> 🔧 **Навіщо це на практиці:**
> У польотних контролерах поділ викристалізувався практикою: гоночні дрони використовують легкий кооперативний планувальник на базі STM32F405 для отримання 8 кГц циклу PID із нульовим джиттером, тоді як складні автономні дрони на базі Pixhawk і PX4 використовують RTOS NuttX на процесорі STM32H743, де десятки задач навігації, логування та супутникового зв'язку надійно ізольовані власними пріоритетами.
