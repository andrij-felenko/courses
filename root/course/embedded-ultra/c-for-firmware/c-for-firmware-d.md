# Мова C для прошивки

<preknowlist>
* [Flash і RAM](root:hw-arch/flash-vs-ram) — як фізично влаштована пам'ять мікроконтролера і чому Flash є енергонезалежною, а SRAM скидається при перезапуску
* [Memory-mapped IO](root:hw-arch/memory-mapped-io) — як регістри апаратних блоків відображаються в загальний адресний простір і керуються за звичайними адресами
* [Переривання](root:hw-arch/interrupts) та [ISR](root:hw-arch/isr) — як апаратні події асинхронно переривають лінійне виконання коду процесором
</preknowlist>

Настільна програма мовою C працює в комфортному середовищі віртуальної пам'яті та операційної системи: коли покажчик читає значення з комірки, воно гарантовано не змінюється саме по собі, компілятор сміливо кешує змінні в регістрах процесора, а пам'ять під нові структури запитується у ядра через `malloc()`. Але коли той самий C-код компілюється для мікроконтролера без операційної системи, кожен із цих звичних кроків перетворюється на джерело аварій: оптимізатор викидає опитування апаратного прапорця як «непотрібний» порожній цикл, неініціалізована змінна читає випадкове апаратне сміття з оперативної пам'яті, а один-єдиний виклик динамічного виділення пам'яті через кілька десятків годин польоту фрагментує мізерну пам'ять на 32 кілобайти й глухо вішає бортовий вузол телеметрії.

Програмування на «голому залізі» (**bare-metal**, від англійського *bare* — «голий», «відкритий» та *metal* — «метал», «апаратний кремній») вимагає від інженера кардинально іншого мислення. Мова C у прошивках перестає бути високорівневою абстракцією і перетворюється на тонкий синтаксичний шар над конкретними машинними інструкціями процесора, шинами адреси й фізичними секціями кристала. Щоб написати прошивку, яка працюватиме роками без зависань і непередбачуваних перезапусків, необхідно розуміти, як компілятор оптимізує доступ до пам'яті, як розміщуються змінні у фізичних кристалах Flash та SRAM, чому динамічна купа перебуває під суворою забороною в критичних системах і як будуються надійні структури обміну даними між перериваннями та основним циклом.

### Невидимий конфлікт між компілятором C та фізичним кремнієм

Модель виконання мови C створювалася на основі так званої «абстрактної машини C» (*C abstract machine*). За цим стандартом компілятор вважає, що:
1. Значення будь-якої змінної в пам'яті може змінитися **виключно** внаслідок виконання явної інструкції цієї ж самої програми.
2. Читання змінної з пам'яті не має жодних побічних ефектів (*side effects*) для зовнішнього світу.
3. Послідовність операцій, результат яких не впливає на підсумковий спостережуваний стан програми, можна вільно перевпорядковувати, спрощувати або взагалі видаляти.

На персональному комп'ютері чи сервері ця модель чудово працює: пам'ять належить виключно процесору, а доступ до пристроїв схований глибоко в ядрі операційної системи через драйвери. Але в мікроконтролері з архітектурою відображення пам'яті ([Memory-mapped IO](root:hw-arch/memory-mapped-io)) апаратні периферійні блоки підключені до тієї самої внутрішньої шини, що й звичайна пам'ять. Запис за адресою `0x40013804` — це не просто збереження байта в комірці, це передача байта в апаратний передавач UART, який негайно починає модулювати рівень на фізичній ніжці контролера. А читання з адреси `0x40013800` — це не просто вичитування числа, це скидання апаратного прапорця готовності прийому `RXNE` всередині кремнієвого модуля.

Коли компілятор GCC або Clang оптимізує код із прапорцями `-O2` або `-Os` (оптимізація за розміром), він намагається звести до мінімуму звернення до повільної шини пам'яті. Якщо в коді написано наївний цикл очікування надходження байта телеметрії без урахування апаратних особливостей:

:::tabs
```c
#include <stdint.h>

// Помилковий код без розуміння апаратної специфіки
void wait_for_uart_byte_broken(void) {
    uint32_t *uart_status = (uint32_t *)0x40013800UL;
    while (!(*uart_status & (1U << 5))) {
        // Очікування прапорця RXNE
    }
}
```
```cpp
#include <cstdint>

// Помилковий C++ код без урахування апаратного відображення
void wait_for_uart_byte_broken() noexcept {
    auto* uart_status = reinterpret_cast<uint32_t*>(0x40013800UL);
    while (!(*uart_status & (1U << 5))) {
        // Очікування прапорця RXNE
    }
}
```
:::

Компілятор дивиться на цей код крізь призму абстрактної машини C: усередині тіла циклу немає жодного запису за адресою `uart_status`. Отже, за логікою компілятора, значення за цією адресою не може змінитися ніколи. Оптимізатор генерує інструкцію читання з пам'яті в процесорний регістр (наприклад, `R0` в архітектурі ARM Cortex-M) рівно **один раз перед початком циклу**, а далі створює нескінченне зациклення на значенні в регістрі `R0`. Якщо в момент входу в цикл байт ще не прибув, мікроконтролер назавжди зависає в цьому місці, хоча на апаратній ніжці UART уже давно надходять нові дані.

Аналогічна проблема виникає при спробі створити програмну затримку через звичайний порожній лічильник:

:::tabs
```c
#include <stdint.h>

// Наївна затримка, яку оптимізатор повністю видалить
void delay_broken(void) {
    for (uint32_t i = 0; i < 100000U; i++) {
        // Порожній цикл
    }
}
```
```cpp
#include <cstdint>

// Наївна затримка C++, яка зникає при компіляції з -O2
void delay_broken() noexcept {
    for (uint32_t i = 0; i < 100000U; ++i) {
        // Порожній цикл
    }
}
```
:::

Оптимізатор бачить, що змінна `i` після виходу з циклу ніде не використовується, а сам цикл не змінює глобального стану. Такий цикл класифікується як «мертвий код» (*dead code*) і просто викидається з бінарного файлу: затримка перетворюється на нуль тактів процесора.

### Модифікатор `volatile` та керування конвеєром пам'яті

Щоб повідомити компілятору, що за певною адресою розташована фізична пам'ять, яка змінюється незалежно від потоку виконання програми (апаратним блоком, контролером прямого доступу до пам'яті DMA або [обробником переривання ISR](root:hw-arch/isr)), у мові C передбачено спеціальний модифікатор типу.

Термін **volatile** походить від латинського *volatilis* («летючий», «мінливий», від дієслова *volare* — «летіти»). У специфікації C модифікатор `volatile` є обов'язковою директивою компілятору: кожне звернення до змінної (читання чи запис) у вихідному коді повинно транслюватися в **реальну машинну інструкцію доступу до пам'яті** (`LDR` або `STR` в ARM) і не може бути видалене, об'єднане чи винесене за межі циклу.

![Компіляція циклу опитування апаратного регістра: без volatile проти volatile](/root/course/embedded-ultra/c-for-firmware/img/volatile-compiler-loop.svg)
*Зліва: компілятор з оптимізацією -O2 виносить читання регістра за межі циклу в регістр R0 процесора, перетворюючи очікування на вічне зависання. Справа: модифікатор volatile змушує компілятор генерувати інструкцію LDR на кожній ітерації опитування.*

Для коректного доступу до периферії покажчики на апаратні регістри завжди оголошуються як покажчики на `volatile`-дані:

:::tabs
```c
#include <stdint.h>

#define UART_SR_REG  (*(volatile uint32_t *)0x40013800UL)
#define UART_DR_REG  (*(volatile uint32_t *)0x40013804UL)
#define RXNE_FLAG    (1U << 5)

uint8_t uart_receive_byte_direct(void) {
    // Компілятор змушений щоразу читати реальну шину заліза
    while (!(UART_SR_REG & RXNE_FLAG)) {
        // Очікування надходження байта
    }
    // Читання DR скидає прапорець RXNE на рівні кремнію
    return (uint8_t)(UART_DR_REG & 0xFFU);
}
```
```cpp
#include <cstdint>

inline volatile uint32_t& UART_SR_REF = *reinterpret_cast<volatile uint32_t*>(0x40013800UL);
inline volatile uint32_t& UART_DR_REF = *reinterpret_cast<volatile uint32_t*>(0x40013804UL);
inline constexpr uint32_t RXNE_FLAG   = 1U << 5;

uint8_t uart_receive_byte_direct() noexcept {
    while (!(UART_SR_REF & RXNE_FLAG)) {
        // Очікування прапорця
    }
    return static_cast<uint8_t>(UART_DR_REF & 0xFFU);
}
```
:::

У виробничих бібліотеках керування мікроконтролерами (наприклад, CMSIS для мікроконтролерів на базі ядер ARM Cortex-M) апаратні блоки оформлюють у вигляді C-структур, де кожне поле позначене модифікатором `volatile`:

:::tabs
```c
#include <stdint.h>

// Опис апаратного блоку UART через структуру
typedef struct {
    volatile uint32_t SR;    // 0x00: Регістр статусу
    volatile uint32_t DR;    // 0x04: Регістр даних
    volatile uint32_t BRR;   // 0x08: Регістр швидкості (Baud Rate)
    volatile uint32_t CR1;   // 0x0C: Регістр керування 1
    volatile uint32_t CR2;   // 0x10: Регістр керування 2
    volatile uint32_t CR3;   // 0x14: Регістр керування 3
} UART_Regs;

#define UART1_BASE (0x40013800UL)
#define UART1      ((UART_Regs *)UART1_BASE)

void uart_send_byte(UART_Regs *uart, uint8_t byte) {
    // Опитування біта передавача TXE (Transmit Data Register Empty)
    while (!(uart->SR & (1U << 7))) {
        // Очікування звільнення вихідного буфера
    }
    uart->DR = byte;
}
```
```cpp
#include <cstdint>
#include <span>

// Ідіоматичний C++ доступ до апаратної периферії через типізовані структури
struct UartRegs {
    volatile uint32_t sr;
    volatile uint32_t dr;
    volatile uint32_t brr;
    volatile uint32_t cr1;
    volatile uint32_t cr2;
    volatile uint32_t cr3;
};

inline auto uart1 = reinterpret_cast<UartRegs*>(0x40013800UL);

class UartDriver {
public:
    constexpr explicit UartDriver(UartRegs* regs) noexcept : regs_(regs) {}

    void send_byte(uint8_t byte) noexcept {
        constexpr uint32_t txe_bit = 1U << 7;
        while (!(regs_->sr & txe_bit)) {
            // Очікування звільнення вихідного буфера
        }
        regs_->dr = byte;
    }

    void write(std::span<const uint8_t> data) noexcept {
        for (uint8_t byte : data) {
            send_byte(byte);
        }
    }

private:
    UartRegs* regs_;
};
```
:::

Існує критично важлива межа, де `volatile` перестає діяти: **`volatile` не забезпечує атомарності доступу і не є бар'єром конвеєра пам'яті**.
1. Якщо 32-бітне ядро записує 64-бітне значення типу `volatile uint64_t`, цей запис виконується за **дві окремі 32-бітні інструкції** `STR`. Якщо між цими двома інструкціями спрацює переривання і прочитає цю ж змінну, воно отримає наполовину оновлене, повністю спотворене значення.
2. Процесори зі складними конвеєрами або шинними буферами запису можуть фізично змінювати порядок передачі сигналів на зовнішніх шинах. Для гарантування того, що запис у регістр налаштування завершився до виклику наступної інструкції, потрібні спеціальні апаратні бар'єри пам'яті (в ARM — інструкції `__DSB()` — *Data Synchronization Barrier* та `__DMB()` — *Data Memory Barrier*).
3. `volatile` не синхронізує потоки в багатозадачних операційних системах реального часу (RTOS); для взаємовиключення потрібні м'ютекси або атомарні операції з бібліотеки `<stdatomic.h>`.

### Анатомія пам'яті прошивки: секції Flash та SRAM

Пам'ять вбудованого комп'ютера фізично розділена на два абсолютно різні кремнієві типи:
* **Flash (ROM)** — енергонезалежна пам'ять, що зберігає дані при знеструмленні. Її читання швидке, але запис здійснюється повільно, цілими сторінками, і має обмежений ресурс циклів перезапису.
* **SRAM (Static RAM)** — швидка оперативна пам'ять на транзисторних тригерах, стан якої повністю втрачається при вимкненні живлення.

Під час збирання проекту компілятор та компонувальник (*linker*) розподіляють усі функції, константи та змінні на стандартні бінарні секції виконуваного формату ELF (*Executable and Linkable Format*).

![Розподіл пам'яті мікроконтролера між Flash та SRAM](/root/course/embedded-ultra/c-for-firmware/img/memory-layout.svg)
*Фізичне розміщення секцій: Flash містить таблицю векторів, код інструкцій (.text), константи (.rodata) та образ ініціалізації (.data). Під час старту startup-код копіює .data у SRAM і зануляє область .bss.*

Розгляньмо призначення та механізм кожної секції:

#### 1. Секція `.text` (Машинний код)
Містить скомпільовані інструкції процесора та таблицю векторів переривань (`.vector_table`). Ця секція розміщується у Flash-пам'яті (зазвичай починаючи з адреси `0x08000000` на чіпах STM32 або `0x00000000` на інших платформах). Процесор читає інструкції безпосередньо з Flash через апаратний кеш інструкцій або шину I-Code.

#### 2. Секція `.rodata` (Сталі дані тільки для читання)
Назва походить від англійського *Read-Only Data*. Тут зберігаються константи, рядкові літерали (`"Sensors OK\r\n"`), таблиці перерахунку синусів, матриці калібрування давачів та дескриптори протоколів:

:::tabs
```c
#include <stdint.h>

// Змінні потрапляють у Flash-секцію .rodata і НЕ витрачають оперативну пам'ять SRAM
const float ACCEL_SCALE_FACTOR = 0.000061f; 
const uint8_t CRC7_POLY_TABLE[8] = { 0x00, 0x09, 0x12, 0x1B, 0x24, 0x2D, 0x36, 0x3F };
```
```cpp
#include <cstdint>
#include <array>

// Константи constexpr у C++ гарантовано розміщуються у Flash-секції .rodata
inline constexpr float ACCEL_SCALE_FACTOR = 0.000061f;
inline constexpr std::array<uint8_t, 8> CRC7_POLY_TABLE = { 
    0x00, 0x09, 0x12, 0x1B, 0x24, 0x2D, 0x36, 0x3F 
};
```
:::

Уважне використання ключового слова `const` — головний спосіб економії оперативної пам'яті: якщо константу оголосити без `const`, компілятор змушений виділити під неї місце в дефіцитній SRAM.

#### 3. Секція `.data` (Ініціалізовані глобальні змінні)
Містить глобальні та статичні змінні, які мають ненульове початкове значення в коді:

:::tabs
```c
#include <stdint.h>

uint32_t telemetry_baudrate = 115200U; // Початкове значення 115200
static uint8_t active_node_id = 0x01U; // Початкове значення 1
```
```cpp
#include <cstdint>

inline uint32_t telemetry_baudrate = 115200U;
namespace {
    uint8_t active_node_id = 0x01U;
}
```
:::

Оскільки це змінні, під час роботи програми процесор повинен мати можливість їх модифікувати — отже, їхня активна робоча адреса (**VMA**, *Virtual Memory Address*) розташована в **SRAM**. Проте при вимкненні живлення SRAM очищується. Щоб після ввімкнення змінна отримала число `115200`, саме початкове значення має зберігатися у Flash. Тому секція `.data` має дві адреси: адресу завантаження у Flash (**LMA**, *Load Memory Address*) та робочу адресу виконання в SRAM.

#### 4. Секція `.bss` (Неініціалізовані змінні)
Термін **.bss** — це історична абревіатура від назви асемблерної директиви комп'ютера IBM 704 *Block Started by Symbol* («блок, що починається із символу»). У сучасних компіляторах секція `.bss` відведена під глобальні та статичні змінні, які або не мають явної ініціалізації, або ініціалізовані нулем:

:::tabs
```c
#include <stdint.h>

uint8_t rx_packet_buffer[512]; // Автоматично занулюється при старті
static uint32_t packet_counter = 0;
```
```cpp
#include <cstdint>
#include <array>

inline std::array<uint8_t, 512> rx_packet_buffer; // Розміщується у .bss
namespace {
    uint32_t packet_counter = 0;
}
```
:::

Геніальність секції `.bss` полягає в економії Flash-пам'яті: масив на 10 кілобайт не зберігається у Flash як 10 000 нулів. У заголовку бінарного файлу записується лише розмір секції (наприклад, `10240 bytes`). У Flash цей масив займає 0 байтів, а під час завантаження мікроконтролера стартовий код виділяє під нього місце в SRAM і заповнює нулями.

#### 5. Стек (Stack)
Термін **стек** походить від англійського *stack* («стіг», «купа акуратно складених речей»). Це область оперативної пам'яті з дисципліною доступу LIFO (*Last-In, First-Out* — «останнім прийшов, першим пішов»). У стеку зберігаються:
* Локальні змінні функцій.
* Адреси повернення з викликів підпрограм.
* Збережені процесорні регістри під час входу в переривання (ISR).

На архітектурах ARM Cortex-M стек росте **зверху вниз** — від найвищої адреси SRAM до нижчих адрес. Положенням вершини стека керує апаратний регістр процесора `SP` (*Stack Pointer*, або `MSP` — *Main Stack Pointer*).

#### 6. Купа (Heap)
Термін **купа** походить від англійського *heap* («насип», «безладна купа»). Це область динамічної пам'яті, з якої стандартна бібліотека функцій `malloc()` / `free()` або оператор `new` у C++ нарізають блоки довільного розміру під час виконання програми. Купа росте **знизу вгору** — назустріч стеку.

#### Механізм старту: як прошивка оживляє пам'ять
До того, як процесор викличе першу сходинку функції `main()`, апаратне скидання запускає функцію **стартового коду** (`Reset_Handler`). Скрипт лінкувальника (`linker script`, файл із розширенням `.ld`) надає спеціальні мітки-адреси кордонів секцій. Стартовий код виконує три базові кроки:
1. Завантажує вершину стека в регістр `SP` зі значення першого слова таблиці векторів.
2. Копіює блок байтів секції `.data` з адреси у Flash (`_sidata`) в оперативну пам'ять від `_sdata` до `_edata`.
3. Проходить циклом по ділянці пам'яті від `_sbss` до `_ebss` і записує туди нулі.
4. Тільки після очищення `.bss` та ініціалізації `.data` передає керування на функцію `main()`.

Якщо стартовий код пропустить занулення `.bss`, будь-яка неініціалізована змінна міститиме випадкове залишкове значення конденсаторів SRAM, що призведе до хаотичних збоїв логіки.

### Атомарний доступ та апаратний захист від перегонів

У типовій прошивці мікроконтролера періодично виникає необхідність змінити стан однієї ніжки GPIO (наприклад, увімкнути світлодіод індикації телеметрії), не порушуючи стан інших виводів того самого 16-бітного порту.

Наївне рішення мовою C виглядає як класична операція побітового «АБО»:

:::tabs
```c
#include <stdint.h>

#define GPIOA_ODR (*(volatile uint32_t *)0x4001080CUL)

void led_on_naive(void) {
    // Небезпечна операція Read-Modify-Write
    GPIOA_ODR |= (1U << 5);
}
```
```cpp
#include <cstdint>

inline volatile uint32_t& GPIOA_ODR_REF = *reinterpret_cast<volatile uint32_t*>(0x4001080CUL);

void led_on_naive() noexcept {
    // Небезпечна операція Read-Modify-Write
    GPIOA_ODR_REF |= (1U << 5);
}
```
:::

Проблема полягає в тому, що на рівні асемблера процесора інструкція `GPIOA_ODR |= (1 << 5)` перетворюється на послідовність із **трьох окремих інструкцій**:
1. `LDR R0, [R1]` — прочитати весь 32-бітний регістр `ODR` у процесорний регістр `R0`.
2. `ORR R0, R0, #0x20` — модифікувати 5-й біт у регістрі `R0`.
3. `STR R0, [R1]` — записати оновлений 32-бітний стан назад у пам'ять порту.

Ця послідовність називається циклом **Read-Modify-Write (RMW)**. Якщо в проміжку між кроками `LDR` та `STR` спрацює високорівневе апаратне переривання таймера і змінить стан 6-го біта того самого порту, головна програма після повернення з переривання виконає свою інструкцію `STR` зі старим значенням `R0` і **безповоротно затре зміну, зроблену перериванням**.

Для подолання цієї небезпеки архітектура ARM Cortex-M надає два апаратні механізми:
1. **Регістри атомарного встановлення/скидання (BSRR):** Замість читання-модифікації запис одиниці в молодші 16 бітів регістра `BSRR` апаратно встановлює відповідні піни в `1`, а запис у старші 16 бітів — скидає в `0`. Це виконується за **одну інструкцію запису** без читання.
2. **Біт-Бендінг (Bit-Banding):** Механізм апаратного відображення пам'яті в Cortex-M3/M4, де кожен окремий біт пам'яті SRAM або периферії відображається на окреме 32-бітне слово в спеціальній області пам'яті. Звичайний запис `1` або `0` за цією адресою апаратно модифікує рівно один біт на шині без блокування переривань.

:::tabs
```c
#include <stdint.h>

#define GPIOA_BSRR (*(volatile uint32_t *)0x40010810UL)

void led_on_atomic(void) {
    // Атомарне встановлення 5-го піна (1 такт запису, відсутність RMW)
    GPIOA_BSRR = (1U << 5);
}

void led_off_atomic(void) {
    // Атомарне скидання 5-го піна (запис у старшу половину регістра)
    GPIOA_BSRR = (1U << (5 + 16));
}
```
```cpp
#include <cstdint>

inline volatile uint32_t& GPIOA_BSRR_REF = *reinterpret_cast<volatile uint32_t*>(0x40010810UL);

void led_on_atomic() noexcept {
    // Атомарне увімкнення без ризику спотворення стану інших виводів
    GPIOA_BSRR_REF = (1U << 5);
}

void led_off_atomic() noexcept {
    // Атомарне вимкнення
    GPIOA_BSRR_REF = (1U << (5 + 16));
}
```
:::

### Правила MISRA C для безпечного коду прошивки

Стандарт MISRA C (*Motor Industry Software Reliability Association*) виник в автомобільній промисловості й став загальноприйнятим орієнтиром для розробки надійних прошивок. Його правила усувають слабкі місця стандарту C, де поведінка програми залежить від конкретного компілятора чи невизначеної поведінки (*Undefined Behavior*).

Розгляньмо ключові правила, які повинен застосовувати інженер:

#### 1. Заборона неявних приведень типів (MISRA Rule 10.3)
У мові C вираз `uint8_t c = a + b;` спочатку неявно розширює `a` та `b` до типу `int` (*integer promotion*), виконує додавання і лише потім обрізає результат. У прошивках усі приведення типів повинні бути явними, а проміжні типи — строго контрольованими.

#### 2. Побітові операції тільки над беззнаковими типами (MISRA Rule 10.1)
Зсув від'ємного знакового числа вліво `(-5) << 2` є невизначеною поведінкою за стандартом C99/C11. Зсув вправо для знакових чисел реалізує арифметичний зсув (із збереженням знакового біта), що часто ламає бітові маски. Усі змінні для бітових операцій зобов'язані мати тип `uint8_t`, `uint16_t` або `uint32_t` із явним суфіксом `U` у константах (`1U << 5`).

#### 3. Внутрішнє зв'язування через `static` (MISRA Rule 8.4)
Будь-яка глобальна функція або змінна, яка не використовується за межами поточного `.c` файлу, зобов'язана позначатися як `static`. Це запобігає конфліктам імен між модулями та дозволяє оптимізатору компілятора повністю вбудовувати (*inline*) короткі підпрограми без накладних витрат на виклик `BL`.

### Табу на динамічну пам'ять у критичних системах

У прикладних настільних програмах виділення динамічної пам'яті через `malloc()` або `new` є стандартною щоденною практикою. Але у вбудованих системах високої надійності (авіоніка DO-178C, автомобільна електроніка ISO 26262, стандарти безпеки MISRA C:2012) динамічне виділення пам'яті перебуває під **суворою і безумовною забороною** (MISRA Rule 21.3).

Ця заборона викликана чотирма фундаментальними причинами:

#### 1. Недетермінізм часу виконання
Термін **детермінізм** походить від латинського *determinare* («визначати», «ставити межі»). У системах реального часу кожна операція повинна мати строго гарантований максимальний час виконання (*Worst-Case Execution Time*, WCET). Робота функції `malloc()` полягає в пошуку вільного фрагмента пам'яті у зв'язаному списку (*free-list*). Якщо список довгий або фрагментований, пошук підхожого блоку алгоритмами *First-Fit* чи *Best-Fit* може зайняти сотні чи тисячі тактів процесора. Якщо цей виклик трапиться під час аварійного маневру безпілотника, затримка призведе до втрати керування.

#### 2. Фрагментація пам'яті
Термін **фрагментація** походить від латинського *fragmentum* («уламок», «шматочок», від дієслова *frangere* — «ламати»). Коли система постійно виділяє та звільняє блоки різного розміру (наприклад, пакети телеметрії по 32 байти, буфери логів по 128 байтів і службові дескриптори по 64 байти), суцільний простір купи розбивається на дрібні ізольовані «кишені».

Через деякий час виникає фатальна ситуація: сумарний обсяг вільної пам'яті в купі становить 8 кілобайтів, але він розбитий на сотні шматочків по 40 байтів. Коли програма робить запит `malloc(128)`, функція повертає `NULL`, оскільки жодного неперервного шматка пам'яті потрібного розміру більше немає. Якщо код не має бездоганної обробки повернення `NULL`, відбувається розіменування нульового покажчика та апаратне аварійне завершення `HardFault`.

#### 3. Накладні витрати на заголовки блоків
Кожен блок, виділений через `malloc()`, вимагає збереження службових метаданих (розмір блоку, прапорець зайнятості, покажчики зв'язаного списку) — зазвичай від 4 до 16 байтів на виділення. Якщо система виділяє малі структури давачів розміром по 8 байтів, накладні витрати пам'яті перевищують 100%, виснажуючи обмежену SRAM мікроконтролера.

#### 4. Небезпека зіткнення купи і стека (*Heap-Stack Collision*)
Оскільки купа росте вгору, а стек росте вниз, за відсутності апаратного модуля захисту пам'яті ([MPU](root:hw-arch/memory-map)) вони можуть невидимо налізти один на одного. Стек функції затре метадані купи, або черговий `malloc()` виділить пам'ять поверх активного кадру переривання.

**Золоте правило прошивки:** уся необхідна пам'ять — буфери зв'язку, черги подій, структури станів, масиви пакетів — повинна виділятися **статично на етапі компіляції**. Якщо на етапі лінкування звіт показує, що `.data` + `.bss` + максимальний розмір стека вміщуються в SRAM, пам'ять гарантовано ніколи не закінчиться під час роботи.

### Архітектура статичного кільцевого буфера для телеметрії

Найпоширеніша задача у вбудованих пристроях — організація надійного зв'язку між джерелом даних (наприклад, апаратним перериванням UART, яке приймає байти з радіомодема на високій швидкості) та обробником даних (основним циклом `super-loop`, який перевіряє контрольні суми й оновлює стан системи) (детальніше див. [Безблокувальний кільцевий буфер SPSC для систем реального часу](root:sf-tasks/lock-free-spsc-ring-buffer)).

Оскільки переривання не може блокуватися, чекати або виділяти динамічну пам'ять, класичним рішенням є **статичний кільцевий буфер** (*ring buffer*, або циркулярний буфер).

Термін **кільцевий буфер** походить від латинського *circulus* («коло», «кільце»): це звичайний статичний лінійний масив фіксованого розміру, індекси запису та читання якого логічно зациклені від кінця до початку.

![Статичний lock-free кільцевий буфер телеметрії: схема Single-Producer Single-Consumer](/root/course/embedded-ultra/c-for-firmware/img/ring-buffer-telemetry.svg)
*Схема Single-Producer Single-Consumer: ISR оновлює покажчик head при надходженні байта, а основний цикл вичитує дані й зміщує tail. Буфер порожній при head == tail і повний при ((head + 1) & MASK) == tail.*

Буфер будується за архітектурою **один виробник — один споживач** (*Single Producer Single Consumer*, SPSC):
* **Виробник (Producer)** — переривання ISR — записує байт у позицію `head` і зміщує `head` вперед.
* **Споживач (Consumer)** — фоновий цикл — вичитує байт із позиції `tail` і зміщує `tail` вперед.

Щоб структура працювала максимально швидко без дорогих операцій блокування переривань, застосовують ключовий інженерний прийом: **розмір буфера обирають строго рівним ступеню двійки** (`2^N`: 16, 32, 64, 128, 256, 512...). Це дозволяє замінити повільну апаратну операцію взяття залишку від ділення `% CAPACITY` на миттєву побітову маску `& (CAPACITY - 1)`.

На процесорах ARM Cortex-M0 операція ділення не має апаратної підтримки й виконується бібліотечною підпрограмою за 50–120 тактів, тоді як побітове `AND` виконується за **1 такт процесора**.

Для роботи з кільцевим буфером у реальних прошивках використовують модульний інтерфейс, описаний у [довіднику інтерфейсу кільцевого буфера](root:embedded-ultra/c-for-firmware/api-ring-buffer.md). Нижче наведено повну безпечну реалізацію мовами C та C++:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

// Розмір буфера телеметрії — рівно ступінь двійки
#define TELEMETRY_BUF_SIZE 256U
#define TELEMETRY_BUF_MASK (TELEMETRY_BUF_SIZE - 1U)

// Перевірка на етапі компіляції (C11)
_Static_assert((TELEMETRY_BUF_SIZE & TELEMETRY_BUF_MASK) == 0, 
               "Розмір буфера мусить бути ступенем двійки!");

typedef struct {
    uint8_t buffer[TELEMETRY_BUF_SIZE];
    volatile uint16_t head; // Змінюється лише перериванням (Producer)
    volatile uint16_t tail; // Змінюється лише головним циклом (Consumer)
} RingBuffer;

void ring_buffer_init(RingBuffer *rb) {
    rb->head = 0;
    rb->tail = 0;
}

bool ring_buffer_is_empty(const RingBuffer *rb) {
    return rb->head == rb->tail;
}

bool ring_buffer_is_full(const RingBuffer *rb) {
    return ((rb->head + 1U) & TELEMETRY_BUF_MASK) == rb->tail;
}

uint16_t ring_buffer_available(const RingBuffer *rb) {
    return (uint16_t)((rb->head - rb->tail) & TELEMETRY_BUF_MASK);
}

bool ring_buffer_put(RingBuffer *rb, uint8_t byte) {
    uint16_t next_head = (uint16_t)((rb->head + 1U) & TELEMETRY_BUF_MASK);
    if (next_head == rb->tail) {
        return false; // Буфер переповнено, байт відкинуто
    }
    rb->buffer[rb->head] = byte;
    rb->head = next_head; // Атомарне оновлення покажчика
    return true;
}

bool ring_buffer_get(RingBuffer *rb, uint8_t *byte) {
    if (rb->head == rb->tail) {
        return false; // Буфер порожній
    }
    *byte = rb->buffer[rb->tail];
    rb->tail = (uint16_t)((rb->tail + 1U) & TELEMETRY_BUF_MASK);
    return true;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <optional>
#include <array>

// Ідіоматичний безпечний C++20 шаблонний кільцевий буфер без динамічної пам'яті
template <typename T, size_t Capacity>
class StaticRingBuffer {
    static_assert((Capacity > 0) && ((Capacity & (Capacity - 1)) == 0),
                  "Розмір кільцевого буфера має бути ступенем двійки!");
public:
    constexpr StaticRingBuffer() noexcept : head_(0), tail_(0) {}

    [[nodiscard]] bool empty() const noexcept {
        return head_ == tail_;
    }

    [[nodiscard]] bool full() const noexcept {
        return ((head_ + 1U) & mask_) == tail_;
    }

    [[nodiscard]] size_t size() const noexcept {
        return (head_ - tail_) & mask_;
    }

    [[nodiscard]] constexpr size_t capacity() const noexcept {
        return Capacity - 1U; // Одна комірка зарезервована під розрізнення full/empty
    }

    bool push(const T& item) noexcept {
        const size_t next_head = (head_ + 1U) & mask_;
        if (next_head == tail_) {
            return false; // Переповнення
        }
        buffer_[head_] = item;
        head_ = next_head;
        return true;
    }

    std::optional<T> pop() noexcept {
        if (empty()) {
            return std::nullopt;
        }
        T item = buffer_[tail_];
        tail_ = (tail_ + 1U) & mask_;
        return item;
    }

private:
    static constexpr size_t mask_ = Capacity - 1U;
    std::array<T, Capacity> buffer_{};
    volatile size_t head_{0};
    volatile size_t tail_{0};
};

// Екземпляр для прийому байтів телеметрії
inline StaticRingBuffer<uint8_t, 256> telemetry_rb;
```
:::

### Дисципліна типів, вирівнювання та бітові пастки

У коді для мікроконтролерів стандартні типи `int`, `long`, `short` або `char` несуть приховану небезпеку: їхній розмір не фіксований стандартом і залежить від платформи. На 8-бітному контролері AVR `int` має ширину 16 бітів, на 32-бітному ARM Cortex-M — 32 біти, а на 64-бітному комп'ютері моделювання — 64 або 32 біти.

Якщо протокол телеметрії передає 16-бітний покажчик висоти, оголошення його як `int height` призведе до того, що код, протестований на комп'ютері, переповниться на 8-бітному чіпі або займе вдвічі більше пам'яті на 32-бітному.

Тому в прошивках діє залізне правило: **завжди використовувати типи фіксованої ширини зі стандарту `<stdint.h>`** (`<cstdint>` у C++):
* `uint8_t`, `int8_t` — рівно 1 байт (0..255 або -128..127).
* `uint16_t`, `int16_t` — рівно 2 байти (0..65535).
* `uint32_t`, `int32_t` — рівно 4 байти.
* `uintptr_t` — цілочисельний тип, гарантовано рівний ширині адресного покажчика платформи.

#### Вирівнювання пам'яті та пакування структур (*Alignment & Packing*)
Процесори ARM вимагають вирівнювання адрес: 32-бітне число `uint32_t` повинно лежати за адресою, кратною 4 (наприклад, `0x20000000`, `0x20000004`), а 16-бітне — за адресою, кратною 2. Якщо розташувати поля в структурі недбало:

:::tabs
```c
#include <stdint.h>

// Помилкова структура з неконтрольованими байтами вирівнювання
struct BadTelemetryHeader {
    uint8_t  node_id;      // 1 байт (зсув 0)
    // Компілятор додає 3 байти padding!
    uint32_t timestamp_ms; // 4 байти (зсув 4)
    uint16_t payload_len;  // 2 байти (зсув 8)
    // Компілятор додає 2 байти padding наприкінці!
}; // Підсумковий розмір: 12 байтів замість очікуваних 7 байтів!
```
```cpp
#include <cstdint>

// Помилкова C++ структура з прихованими байтами padding
struct BadTelemetryHeaderCpp {
    uint8_t  node_id;      // 1 байт
    uint32_t timestamp_ms; // 4 байти
    uint16_t payload_len;  // 2 байти
}; // Розмір 12 байтів через вирівнювання за 4-байтовою межею
```
:::

Якщо передати таку структуру безпосередньо в радіоефір через `uart_write(&header, sizeof(header))`, у пакет потраплять 5 байтів неініціалізованого сміття пам'яті. Приймач іншої архітектури не зможе розпарсити такий пакет.

Для мережевих протоколів та пакетів телеметрії використовують директиву щільного пакування без вирівнювання:

:::tabs
```c
#include <stdint.h>

// Структура без порожніх байтів вирівнювання
typedef struct __attribute__((packed)) {
    uint8_t  node_id;      // 1 байт
    uint32_t timestamp_ms; // 4 байти
    uint16_t packet_seq;   // 2 байти
    uint16_t crc16;        // 2 байти
} TelemetryPacketHeader;

_Static_assert(sizeof(TelemetryPacketHeader) == 9, "Розмір заголовка має бути рівно 9 байтів!");
```
```cpp
#include <cstdint>
#include <cstddef>

// Щільно упакований C++ заголовок пакета телеметрії
struct [[gnu::packed]] TelemetryPacketHeader {
    uint8_t  node_id;
    uint32_t timestamp_ms;
    uint16_t packet_seq;
    uint16_t crc16;
};

static_assert(sizeof(TelemetryPacketHeader) == 9, "Розмір заголовка має бути рівно 9 байтів!");
```
:::

Утім, треба пам'ятати про ціну пакування: на ядрах ARM Cortex-M0 спроба прочитати 32-бітне поле `timestamp_ms` через розіменування покажчика `uint32_t *` за непарною адресою викличе апаратну аварію `UsageFault` (невирівняний доступ). На таких ядрах доступ до непарних полів виконують побайтово або через копіювання `memcpy()`.

---

Програмування мікроконтролерів мовою C — це точний розрахунок кожного байта й кожного такту. Розуміючи природу модифікатора `volatile`, фізичний поділ Flash та SRAM, правила завантаження секцій `.data` і `.bss` та відмовившись від небезпечної динамічної купи на користь статичних кільцевих буферів, інженер отримує детерміновану систему, готову до безвідмовної роботи в найсуворіших умовах бортового застосування.
