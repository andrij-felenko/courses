# Інтерфейс системного часу: структура timex, виклики adjtimex і стан ядра

Підсистема обліку часу ядра Linux надає інтерфейси не лише для зчитування поточної дати, але й для тонкого керування фазою та частотою внутрішнього генератора. Базовий виклик `settimeofday(2)` або `clock_settime(CLOCK_REALTIME, ...)` виконує грубий стрибок, що розриває неперервність часової шкали. Для плавного підстроювання без розривів призначено системні виклики `adjtime(3)` (історичний BSD-інтерфейс), `adjtimex(2)` (специфічний для Linux низькорівневий інтерфейс) та стандартизований POSIX/NTP-виклик `ntp_adjtime(3)`.

Цей довідник описує внутрішню структуру `timex`, бітові маски режимів конфігурації, прапорці стану фазового автопідстроювання частоти (PLL/FLL), механізм обробки секунд координації, роботу підсистеми апаратного імпульсу точного часу (PPS) та відповідність між ядерними структурами і виводом діагностичних утиліт.

## Системний виклик adjtimex(2) та структура timex

Системний виклик `adjtimex()` зчитує та встановлює параметри алгоритму керування часом ядра Linux, що базується на математичній моделі фазового автопідстроювання Девіда Міллза (David L. Mills, RFC 1305 / RFC 5905).

:::tabs
@tab C
```c
#include <sys/timex.h>

int adjtimex(struct timex *buf);
int ntp_adjtime(struct timex *buf);
```
@tab C++
```cpp
#include <sys/timex.h>

// Системні C-виклики у C++ доступні у глобальному просторі імен або через ::
int ::adjtimex(struct timex *buf);
int ::ntp_adjtime(struct timex *buf);
```
:::

Якщо поле `buf->modes` дорівнює нулю (`0`), виклик виконує суто операцію інспекції: зчитує поточні параметри ядра без внесення будь-яких змін у роботу контуру регулювання. Для модифікації будь-яких параметрів викликаючий процес повинен мати привілей `CAP_SYS_TIME` у своєму просторі імен користувача.

Внутрішня математика підсистеми `timekeeping` оперує значеннями з фіксованою комою. Одиниця виміру частоти у полі `freq` використовує 16-бітну дробову частину: число `65536` (тобто 2¹⁶) відповідає відхиленню частоти в `1 ppm` (одну мільйонну частку, або 10⁻⁶).

### Поля структури timex

Структура `struct timex` визначена в заголовковому файлі `<sys/timex.h>`:

| Поле | Тип | Одиниця виміру | Призначення |
|---|---|---|---|
| `modes` | `unsigned int` | бітова маска | Визначає, які поля структури передаються ядру для запису (`MOD_*`). |
| `offset` | `long` | мкс або нс | Фазове зміщення часу (phase offset). Якщо активний прапорець `STA_NANO`, значення інтерпретується в наносекундах, інакше — у мікросекундах. |
| `freq` | `long` | 2⁻¹⁶ ppm | Частотне зміщення генератора (frequency offset). Значення `65536` відповідає похибці в `1 ppm` (10⁻⁶). |
| `maxerror` | `long` | мкс | Максимальна теоретична похибка (maximum error), що невпинно накопичується ядром через дрейф генератора в періоди між синхронізаціями. |
| `esterror` | `long` | мкс | Оцінена середня похибка (estimated error), розрахована демоном NTP/chrony за результатами серії мережевих вимірювань. |
| `status` | `int` | бітова маска | Стан синхронізації та прапорці конфігурації контуру автопідстроювання (`STA_*`). |
| `constant` | `long` | ціле число | Постійна часу PLL/FLL, що визначає коефіцієнт згладжування та швидкість збіжності контуру регулювання. |
| `precision` | `long` | мкс (тільки читання) | Точність апаратного таймера системи (типово 1 мкс або роздільність системного лічильника). |
| `tolerance` | `long` | 2⁻¹⁶ ppm (тільки читання) | Максимально допустиме відхилення частоти, яке ядро здатне компенсувати (константа `32768000`, що відповідає ±500 ppm). |
| `time` | `struct timeval` | сек + мкс | Поточний системний час (`CLOCK_REALTIME`), зафіксований ядром у момент виконання виклику. |
| `tick` | `long` | мкс | Тривалість часу, що додається до системного годинника за один тик таймера ядра (типово 1000000 / HZ). |
| `ppsfreq` | `long` | 2⁻¹⁶ ppm | Частотне зміщення, отримане від апаратного імпульсу точного часу PPS (Pulse Per Second). |
| `jitter` | `long` | нс/мкс | Джиттер (середньоквадратичне відхилення затримок) сигналу PPS. |
| `shift` | `int` | ціле число | Інтервал усереднення частоти PPS (виражений у степенях двійки). |
| `stabil` | `long` | 2⁻¹⁶ ppm | Стабільність сигналу PPS (блукання частоти / wander). |
| `jitcnt` | `long` | лічильник | Кількість зафіксованих подій перевищення порогу допустимого джиттеру PPS. |
| `calcnt` | `long` | лічильник | Кількість успішно завершених калібрувальних інтервалів PPS. |
| `errcnt` | `long` | лічильник | Кількість помилок калібрування PPS (неприпустима нестабільність або зникнення сигналу). |
| `stbcnt` | `long` | лічильник | Кількість подій перевищення ліміту стабільності генератора PPS. |

## Бітові маски режимів конфігурації (modes)

Поле `modes` повідомляє ядру, які саме поля структури `timex` містять нові дані для запису. Якщо відповідний біт не встановлено, поле ігнорується ядром:

| Константа | Шістнадцяткове значення | Опис дії ядра |
|---|---|---|
| `MOD_OFFSET` | `0x0001` | Застосувати фазове зміщення з поля `offset` для поступової компенсації контуром PLL. |
| `MOD_FREQUENCY` | `0x0002` | Записати нове постійне зміщення базової частоти генератора з поля `freq`. |
| `MOD_MAXERROR` | `0x0004` | Оновити оцінку максимальної теоретичної похибки у полі `maxerror`. |
| `MOD_ESTERROR` | `0x0008` | Оновити розраховану мережеву похибку у полі `esterror`. |
| `MOD_STATUS` | `0x0010` | Змінити активні бітові прапорці стану контуру з поля `status`. |
| `MOD_TIMECONST` | `0x0020` | Встановити постійну часу збіжності контуру PLL з поля `constant`. |
| `MOD_TAI` | `0x0080` | Встановити зсув атомної шкали TAI відносно шкали цивільного часу UTC. |
| `MOD_MICRO` | `0x1000` | Перемкнути інтерпретацію поля фазового зсуву `offset` у мікросекунди. |
| `MOD_NANO` | `0x2000` | Перемкнути інтерпретацію поля фазового зсуву `offset` у високоточні наносекунди. |
| `MOD_TICK` | `0x4000` | Змінити базову тривалість системного тика ядра у полі `tick` (зазвичай 10000 мкс). |

## Бітові прапорці стану ядра (status)

Поле `status` відображає активний режим контуру регулювання часу. Частина прапорців керується простором користувача (службами NTP або chrony), а інша частина виставляється ядром автономно на основі перевірки апаратних сигналів:

| Прапорець | Значення | Керованість | Опис поведінки |
|---|---|---|---|
| `STA_PLL` | `0x0001` | R/W | Увімкнено контур фазового автопідстроювання (Phase-Locked Loop). Ядро автоматично усуває накопичене фазове зміщення `offset`. |
| `STA_FLL` | `0x0002` | R/W | Увімкнено контур частотного автопідстроювання (Frequency-Locked Loop). Використовується при великих інтервалах між вимірюваннями. |
| `STA_PPSTIME` | `0x0004` | R/W | Фазова синхронізація прив'язана до апаратного імпульсу точного часу PPS (Pulse Per Second). |
| `STA_PPSFREQ` | `0x0008` | R/W | Частотна синхронізація генератора дисциплінується сигналами PPS. |
| `STA_PPSSIGNAL`| `0x0010` | Read-only | Фізичний імпульсний сигнал PPS присутній і коректно детектується драйвером ядра. |
| `STA_PPSJITTER`| `0x0020` | Read-only | Рівень шуму (джиттеру) сигналу PPS перевищує допустимий ліміт для стабільної синхронізації. |
| `STA_PPSWANDER`| `0x0040` | Read-only | Блукання частоти імпульсів PPS перевищує встановлені межі стабільності. |
| `STA_PPSERROR` | `0x0080` | Read-only | Критична помилка калібрування або зникнення імпульсів точного часу PPS. |
| `STA_CLOCKERR` | `0x0100` | Read-only | Апаратний збій системного годинника або відмова джерела часу (clocksource). |
| `STA_NANO` | `0x2000` | Read-only | Інтерфейс ядра активовано в режимі наносекундної роздільності передачі зсуву. |
| `STA_MODE` | `0x4000` | R/W | Вибір режиму контуру: `0` — фазовий режим (PLL), `1` — частотний режим (FLL). |
| `STA_CLK` | `0x8000` | R/W | Вибір альтернативного апаратного джерела тактування (A/B). |
| `STA_UNSYNC` | `0x0040` | R/W | **Годинник не синхронізовано.** Системний час вважається недостовірним. |
| `STA_INS` | `0x0010` | R/W | Заплановано додавання позитивної секунди координації (+1 с, Leap Second) наприкінці доби UTC. |
| `STA_DEL` | `0x0020` | R/W | Заплановано видалення секунди координації (-1 с) наприкінці поточної доби UTC. |

### Критичний вплив прапорця STA_UNSYNC на апаратний RTC

Прапорець `STA_UNSYNC` відіграє фундаментальну роль у захисті системного часу комп'ютера від пошкодження:

1. **11-хвилинний режим запису в RTC (11-minute mode):** у ядрі Linux функціонує періодичний таймер, який кожні 11 хвилин записує поточний точний час `CLOCK_REALTIME` в енергонезалежну мікросхему апаратного годинника RTC (`/dev/rtc0`). Це гарантує, що у випадку раптового знеструмлення система збереже точну дату.
2. **Захисне блокування:** якщо в полі `status` встановлено біт `STA_UNSYNC`, ядро повністю зупиняє 11-хвилинний таймер і блокує будь-який автоматичний запис у мікросхему RTC. Ядро не має права записувати розсинхронізований або спотворений час у залізо.
3. **Зняття блокування:** демон синхронізації (`chrony` або `systemd-timesyncd`) скидає біт `STA_UNSYNC` через виклик `adjtimex` лише після того, як отримає стабільні вимірювання від зовнішніх серверів і впевниться, що системний час зійшовся з еталоном.

## Життєвий цикл секунди координації (Leap Second)

Земля обертається навколо своєї осі нерівномірно, тому астрономічний час UT1 поступово розходиться з атомним часом TAI. Міжнародна служба обертання Землі (IERS) періодично оголошує додавання секунди координації наприкінці 30 червня або 31 грудня.

У разі успішного виклику `adjtimex()` повертає поточний стан автомата секунд координації:

| Константа | Код | Стан автомата | Опис поведінки ядра |
|---|---|---|---|
| `TIME_OK` | `0` | Норма | Час синхронізовано, секунд координації не заплановано. |
| `TIME_INS` | `1` | Очікування вставки | Демон встановив біт `STA_INS`. Наприкінці поточної доби UTC ядро вставить секунду координації (послідовність секунд: `23:59:59` → `23:59:60` → `00:00:00`). |
| `TIME_DEL` | `2` | Очікування видалення | Встановлено біт `STA_DEL`. Наприкінці доби буде видалено одну секунду (послідовність `23:59:58` → `00:00:00`). |
| `TIME_OOP` | `3` | Секунда триває | Секунда координації виконується прямо зараз (Leap second in progress). |
| `TIME_WAIT` | `4` | Завершення | Секунда координації щойно завершилася. Автомат очікує скидання прапорців демоном простору користувача. |
| `TIME_ERROR` | `5` | Помилка / Розсинхронізація | Годинник не синхронізовано (встановлено прапорець `STA_UNSYNC`). Історичний синонім у glibc — `TIME_BAD`. |

Під час вставки секунди координації класичні ядра Linux повторювали секунду `23:59:59` двічі, що призводило до порушення монотонності логів та зависання деяких серверних застосунків (зокрема JVM та баз даних через дефекти в обробці таймерів futex). Сучасні сервіси (наприклад, Google та Cloudflare) застосовують техніку **Leap Smearing**, поступово розмазуючи зайву секунду через мікроскопічний зсув частоти впродовж 24 годин до і після події, повністю позбавляючи операційну систему від необхідності обробляти розрив часу.

## Контури автопідстроювання: математична різниця між PLL та FLL

У структурі `timex` прапорці `STA_PLL` та `STA_FLL` перемикають математичну модель реакції ядра на розходження часу:

1. **Фазове автопідстроювання (PLL, Phase-Locked Loop):**
   Використовується за частих оновлень від джерел точного часу (інтервал опитування tau <= 128 секунд). Контур обчислює поправку пропорційно накопиченому фазовому зміщенню `offset`. Швидкість збіжності регулюється параметром `constant` (типово значення 4–6). Чим більше значення константи, тим плавніша реакція на джиттер мережі, але тим повільніше ліквідується систематичне зміщення.

2. **Частотне автопідстроювання (FLL, Frequency-Locked Loop):**
   Активується автоматично або явно (прапорець `STA_FLL`), коли інтервал між оновленнями стає великим (tau > 1024 секунд). У цьому режимі ядро оцінює зміщення частоти як відношення різниці фаз до часу, що минув: Δf = Δoffset / tau. Режим FLL запобігає автоколиванням контуру регулювання за рідкісних вимірювань.

3. **Блокування та паралельний доступ у ядрі (Seqlock):**
   Зчитування часу в ядрі Linux оптимізовано для мінімізації накладних витрат. Запис параметрів часу під час виклику `adjtimex()` захоплює спінлок `timekeeper_lock` та збільшує лічильник послідовного замка `tk_core.seq`. Читачі часу (системні виклики `clock_gettime()`) зчитують лічильник послідовності `read_seqcount_begin(&tk_core.seq)` без блокувань і перевіряють його валідність після зняття знімка через `read_seqcount_retry()`. Це гарантує нульові витрати на міжпроцесорну синхронізацію для читачів при паралельному коригуванні часу.

## Інтроспекція підсистеми через sysfs та ftrace

Стан джерел часу та виклики коригування можна спостерігати безпосередньо через віртуальні інтерфейси ядра:

### 1. Перевірка активного джерела часу (clocksource)

```bash
# Доступні апаратні лічильники в системі
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
# tsc hpet acpi_pm

# Поточне обране ядром джерело
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
# tsc
```

Якщо надійне джерело `tsc` визнано ядром нестабільним через перепади частоти на ядрах процесора, ядро автоматично деградує вибір до повільнішого таймера `hpet` або `acpi_pm`, що різко збільшує вартість системних викликів зчитування часу `clock_gettime()`.

### 2. Трасування системних викликів adjtimex через ftrace

Для фіксації всіх спроб зміни параметрів часу використовують стандартні точки трасування ядра:

```bash
echo 1 > /sys/kernel/tracing/events/syscalls/sys_enter_adjtimex/enable
echo 1 > /sys/kernel/tracing/events/syscalls/sys_exit_adjtimex/enable
cat /sys/kernel/tracing/trace_pipe
```

Вивід фіксує ідентифікатор процесу, який викликає функцію, та значення поверненого стану, що дозволяє миттєво локалізувати конфліктні демони синхронізації або несанкціоновані спроби скидання часу.

## Помилки та права доступу

Системний виклик `adjtimex()` повертає `-1` у разі виникнення помилки та встановлює глобальну змінну `errno`:

* `EFAULT` — покажчик на структуру `buf` вказує на недоступну або невалідну область пам'яті адресного простору процесу.
* `EINVAL` — неприпустиме значення в полях конфігурації (наприклад, передано значення `tick`, що виходить за допустимі межі ±10% від номіналу 1000000 / HZ, або передано некоректну комбінацію прапорців у полі `modes`).
* `EPERM` — процес здійснив спробу запису параметрів (поле `modes != 0`), не маючи системного привілею `CAP_SYS_TIME`. Читання стану (`modes == 0`) дозволено будь-якому непривілейованому користувачеві системи.
