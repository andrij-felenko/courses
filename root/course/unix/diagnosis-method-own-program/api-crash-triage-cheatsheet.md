# 📋 Довідник сигналів аварій, кодів si_code та команд діагностики

Цей довідник надає вичерпну специфікацію системних сигналів ядра Linux, спеціалізованих кодів причин збою `si_code` службової структури `siginfo_t`, архітектурного протоколу доставки фатальних винятків процесора, повного набору команд налагоджувача GDB для посмертного аналізу зліпків пам'яті, конфігураційних змінних компіляторних санітайзерів LLVM/GCC (`ASAN_OPTIONS`, `UBSAN_OPTIONS`) та синтаксису правил придушення помилок утиліти Valgrind Memcheck.

## 1. Системні сигнали аварійного завершення та апаратні винятки

У системному програмуванні POSIX сигнали поділяються на асинхронні (породжені зовнішніми подіями, іншими процесами або таймерами) та синхронні (породжені безпосереднім виконанням поточної інструкції процесора). Синхронні сигнали виникають внаслідок апаратних виключень CPU (Hardware Traps, Faults, Aborts). Їхньою ключовою особливістю є неможливість безпечного ігнорування через `SIG_IGN`: якщо процес замаскує або проігнорує `SIGSEGV` чи `SIGFPE`, процесор після повернення з переривання спробує повторно виконати ту саму несправну інструкцію, що спричинить миттєве зациклення ядра в обробнику винятку.

У таблиці наведено стандартні сигнали POSIX, що генеруються апаратним забезпеченням процесора або бібліотекою C-рантайму glibc при виникненні невиправних помилок виконання, дію за замовчуванням ядра Linux та відповідне апаратне виключення процесора.

| Сигнал | Числовий код (x86_64) | Дія за замовчуванням | Апаратне джерело (CPU Vector) | Типова причина виникнення |
|---|---|---|---|---|
| `SIGSEGV` | `11` | Core Dump | `#PF` (Page Fault, vector 14), `#GP` (General Protection, vector 13) | Розіменування вказівника `NULL`, доступ до невідображеної пам'яті, запис у константний сегмент `.rodata`, виконання коду на стеку без прав `PROT_EXEC` (NX-біт). |
| `SIGBUS` | `7` | Core Dump | `#AC` (Alignment Check, vector 17), помилка драйвера файлової системи | Доступ до відображеної сторінки `mmap()` за межами фізичного розміру усіченого файлу (`ftruncate`), недійсне вирівнювання адреси при виконанні векторних інструкцій SSE/AVX (`movdqa`). |
| `SIGABRT` | `6` | Core Dump | Програмне переривання / виклик `kill(getpid(), SIGABRT)` | Спрацювання макроса `assert()`, необроблений виняток C++ (`std::terminate()`), виявлення пошкодження метаданих купи аллокатором `glibc malloc` (double free). |
| `SIGFPE` | `8` | Core Dump | `#DE` (Divide Error, vector 0), `#MF` (x87 FPU Floating-Point Error, vector 16) | Цілочисельне ділення на нуль (`idiv`), цілочисельне переповнення знакового типу (`INT_MIN / -1`), апаратне виключення операцій рухомої коми при увімкненні `feenableexcept()`. |
| `SIGILL` | `4` | Core Dump | `#UD` (Invalid Opcode, vector 6) | Спроба виконання невідомої або зарезервованої інструкції процесора, використання AVX-512 на старому процесорі, пошкодження стека повернення з переходом на випадкові байти даних. |
| `SIGTRAP` | `5` | Core Dump | `#DB` (Debug, vector 1), `#BP` (Breakpoint, vector 3) | Інструкція точки зупину `INT3` (байт `0xCC`), апаратне трасування по кроках (біт Trap Flag у регістрі `EFLAGS`), спрацювання апаратного регістру спостереження `DR0`–`DR3`. |

## 2. Структура `siginfo_t` та коди причин `si_code`

При виникненні винятку ядро заповнює службову структуру `siginfo_t`, яка передається в обробник сигналу, зареєстрований через виклик `sigaction(sig, &sa, NULL)` з прапорцем `SA_SIGINFO`. Ця структура містить повний контекст аварії, включаючи номер сигналу, код системної помилки, ідентифікатор винного процесу або точну адресу збою пам'яті.

### Анатомія структури `siginfo_t`

У заголовному файлі `<signal.h>` структура `siginfo_t` визначена як об'єднання (union), специфічне для кожного типу сигналу:

```text
siginfo_t {
    int      si_signo;     /* Номер сигналу (наприклад, SIGSEGV або SIGBUS) */
    int      si_errno;     /* Номер системної помилки errno (якщо встановлено ядром) */
    int      si_code;      /* Детальний код причини генерації сигналу */
    pid_t    si_pid;       /* PID процесу-відправника (для асинхронних сигналів) */
    uid_t    si_uid;       /* UID користувача-відправника */
    void    *si_addr;      /* Точна адреса несправності пам'яті (для SIGSEGV, SIGBUS, SIGILL, SIGFPE) */
    short    si_addr_lsb;  /* Найменш значущий біт адреси (для визначення меж пам'яті) */
    void    *si_lower;     /* Нижня межа адреси пам'яті при порушенні меж (Intel MPX) */
    void    *si_upper;     /* Верхня межа адреси пам'яті при порушенні меж (Intel MPX) */
    int      si_pkey;      /* Ключ захисту пам'яті PKU, що викликав порушення доступу */
}
```

Поле `si_addr` є найважливішим елементом під час розслідування крашів пам'яті. Якщо значення `si_addr` лежить у діапазоні від `0x0` до `0xFFFF`, це свідчить про розіменування нульового вказівника зі зміщенням на поле структури. Якщо значення `si_addr` має вигляд `0x55e3a890` або `0x7ffd5a987000`, збій стався під час спроби доступу до реальної області коду, купи чи стека.

### Коди `si_code` для сигналу `SIGSEGV`

Код `si_code` дозволяє миттєво відрізнити спробу доступу до неіснуючої пам'яті від спроби несанкціонованого запису в захищені дані або порушення апаратних ключів пам'яті.

| Значення макросу | Числовий код | Опис архітектурної причини | Стан сторінки віртуальної пам'яті |
|---|---|---|---|
| `SEGV_MAPERR` | `1` | Address not mapped to object | Віртуальна адреса не належить до жодного сегмента `vm_area_struct` у адресному просторі процесу (наприклад, `NULL`, молодші адреси `0x0`–`0xFFFF`, неініціалізовані дикі вказівники). |
| `SEGV_ACCERR` | `2` | Invalid permissions for mapped object | Віртуальна сторінка існує в адресному просторі, але операція порушує встановлені біти прав доступу (спроба запису в сторінку з правами лише на читання `PROT_READ`, спроба виконання інструкцій зі сторінки пам'яті `PROT_READ \| PROT_WRITE`). |
| `SEGV_BNDERR` | `3` | Bounds checking failure | Апаратне порушення меж масиву при використанні розширення Intel MPX (Memory Protection Extensions). |
| `SEGV_PKUERR` | `4` | Protection key violation | Порушення прав доступу на рівні ключів захисту пам'яті ядра (Memory Protection Keys, `PKEY`). |
| `SEGV_ACCADI` | `5` | ADI not enabled | Недійсний маркер доступу до пам'яті (Application Data Integrity на архітектурі SPARC). |
| `SEGV_ADIDERR` | `6` | ADI mismatch | Невідповідність тегу апаратного контролю пам'яті ADI. |
| `SEGV_MTEAERR` | `7` | Asynchronous ARM MTE error | Асинхронна помилка апаратного тегування пам'яті (ARM Memory Tagging Extension). |
| `SEGV_MTESERR` | `8` | Synchronous ARM MTE error | Синхронна помилка розіменування пам'яті з некоректним тегом вказівника (ARM MTE). |

### Коди `si_code` для сигналу `SIGBUS`

Сигнал `SIGBUS` супроводжує помилки апаратної шини пам'яті та збої файлових відображень `mmap()`.

| Значення макросу | Числовий код | Опис архітектурної причини | Стан підсистеми пам'яті / диска |
|---|---|---|---|
| `BUS_ADRALN` | `1` | Invalid address alignment | Недійсне апаратне вирівнювання адреси пам'яті (спроба 64-бітного читання за непарною адресою на строгих архітектурах або виконання векторної інструкції `movdqa` з адресою, не кратною 16 байтам). |
| `BUS_ADRERR` | `2` | Non-existent physical address | Спроба доступу до неіснуючої фізичної пам'яті на апаратній шині. |
| `BUS_OBJERR` | `3` | Object-specific hardware error | Специфічна помилка апаратного об'єкта: виникає при читанні/записі відображеної пам'яті `mmap()` за межами фізичного розміру файлу після виклику `ftruncate()`, або при помилці вводу-виводу накопичувача. |
| `BUS_MCEERR_AR` | `4` | Hardware memory error: action required | Критична апаратна помилка контролю парності оперативної пам'яті ECC (Machine Check Exception, Action Required). |
| `BUS_MCEERR_AO` | `5` | Hardware memory error: action optional | Нефатальна апаратна помилка пам'яті ECC (Machine Check Exception, Action Optional). |

### Коди `si_code` для сигналу `SIGFPE`

Сигнал `SIGFPE` кодує всі види арифметичних помилок ядра та співпроцесора.

| Значення макросу | Числовий код | Опис математичної операції | Процесорний стан |
|---|---|---|---|
| `FPE_INTDIV` | `1` | Integer divide by zero | Цілочисельне ділення на нуль: виконання інструкцій `div` / `idiv` з нульовим дільником. |
| `FPE_INTOVF` | `2` | Integer overflow | Цілочисельне переповнення: виникає на x86 при виконанні ділення `INT_MIN / -1`, коли результат не вміщується в розрядну сітку акумулятора. |
| `FPE_FLTDIV` | `3` | Floating-point divide by zero | Ділення на нуль у блоці рухомої коми (FPU / SSE), якщо прапорець `FE_DIVBYZERO` розмасковано. |
| `FPE_FLTOVF` | `4` | Floating-point overflow | Переповнення діапазону значень рухомої коми (`FE_OVERFLOW`). |
| `FPE_FLTUND` | `5` | Floating-point underflow | Втрата порядку (зникнення порядку) для чисел рухомої коми (`FE_UNDERFLOW`). |
| `FPE_FLTRES` | `6` | Floating-point inexact result | Неточний результат обчислення рухомої коми (`FE_INEXACT`). |
| `FPE_FLTINV` | `7` | Floating-point invalid operation | Недійсна операція рухомої коми: отримання `NaN`, корінь з від'ємного числа (`FE_INVALID`). |
| `FPE_FLTSUB` | `8` | Subscript out of range | Вихід індексу масиву за межі діапазону (деякі мови та архітектури). |

## 3. Команди GDB для посмертного аналізу (Post-Mortem Triage)

Інтерактивний відлагоджувач GNU Debugger (GDB) є головним інструментом інтроспекції файлів дампів пам'яті (`core.dump`). Під час аналізу посмертного зліпка відлагоджувач не може виконувати покрокове виконання інструкцій (`step`, `next`) або змінювати стан пам'яті, оскільки процесу фізично більше не існує. Проте всі команди читання пам'яті, інспекції стеків, декодування регістрів та дизасемблювання коду функціонують у повному обсязі.

### Керування стеком та навігація викликами

Стек викликів організований у вигляді послідовності фреймів (кадрів). Кадр з номером `0` відповідає функції, під час виконання якої стався фатальний збій. Кадр `1` — це функція, яка безпосередньо викликала кадр `0`, і так далі до стартової функції C-рантайму `_start` або `main()`.

| Команда GDB | Скорочення | Опис та призначення |
|---|---|---|
| `backtrace` | `bt` | Вивести повний ланцюг стека викликів поточної нитки від миті падіння до функції `main()`. |
| `backtrace full` | `bt full` | Вивести ланцюг викликів разом зі значеннями всіх локальних змінних у кожному фреймі стека. |
| `frame <номер>` | `f <номер>` | Перемкнути контекст аналізу на фрейм з указаним порядковим номером (0 — вершина стека в момент краху). |
| `up` / `down` | `up` / `do` | Піднятися або опуститися на один кадр стека вгору (до функції, що викликала) або вниз. |
| `info frame` | `i f` | Показати детальний паспорт поточного кадру: адреси вказівника бази стека, вказівника інструкцій та збережених регістрів. |
| `info locals` | `i lo` | Вивести імена та поточні значення всіх локальних змінних активного кадру стека. |
| `info args` | `i ar` | Вивести імена та фактичні значення аргументів, з якими було викликано функцію активного кадру. |

### Інспекція регістрів та апаратного стану процесора

Регістровий контекст містить точний стан процесора в момент генерації переривання. За системною угодою System V AMD64 ABI перші шість цілочисельних аргументів функції передаються через регістри `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`, повертане значення записується в `%rax`, вказівник стека зберігається в `%rsp`, а базовий вказівник кадру — в `%rbp`.

| Команда GDB | Скорочення | Опис та призначення |
|---|---|---|
| `info registers` | `i r` | Показати значення всіх цілочисельних регістрів загального призначення процесора (`$rax`, `$rbx`, `$rcx`, `$rdx`, `$rsi`, `$rdi`, `$rbp`, `$rsp`, `$r8`–`$r15`, `$rip`, `$eflags`). |
| `info all-registers` | `i a-r` | Вивести стан усіх регістрів процесора, включаючи векторні регістри SSE/AVX (`$ymm0`–`$ymm15`), регістри сегментів та системні прапорці. |
| `print /x $rip` | `p /x $rip` | Вивести точну шістнадцяткову адресу інструкції, на якій зупинився процесор при отриманні сигналу. |
| `print /t $eflags` | `p /t $eflags` | Вивести бітову маску прапорців процесора у двійковому форматі (для перевірки бітів нуля ZF, знаку SF, переносу CF, переповнення OF). |

### Команда дослідження сирої пам'яті: синтаксис `x/FMT ADDR`

Формат виклику команди `x` (examine): `x/<кількість><формат><розмір> <адреса>`.

Розміри слів:
- `b` — Byte (1 байт, 8 бітів);
- `h` — Halfword (2 байти, 16 бітів);
- `w` — Word (4 байти, 32 біти);
- `g` — Giant word (8 байтів, 64 біти).

Символи форматів:
- `x` — шістнадцятковий вивід (hexadecimal);
- `d` — десятковий знаковий вивід (signed decimal);
- `u` — десятковий беззнаковий вивід (unsigned decimal);
- `s` — рядок символів ASCII з нульовим завершенням (`null-terminated string`);
- `i` — машинна інструкція процесора (disassembled machine instruction);
- `a` — адреса пам'яті з автоматичним зіставленням із найближчим символом таблиці DWARF.

Приклади практичного застосування:

| Команда GDB | Практичне призначення |
|---|---|
| `x/16gx $rsp` | Прочитати 16 64-бітних слів із вершини апаратного стека (для пошуку адрес повернення та локальних структур). |
| `x/8i $rip - 16` | Дизасемблювати 8 інструкцій машинного коду навколо адреси збою процесора. |
| `x/s $rdi` | Прочитати рядок символів, на який вказує регістр першого аргументу системного виклику або функції. |
| `x/32xb 0x7fffffffd000` | Побайтовий дамп 32 байтів віртуальної пам'яті за вказаною адресою. |
| `x/10a $rsp` | Інтерпретувати значення на стеку як адреси функцій із відображенням символьних імен. |

### Дизасемблювання та робота з багатопотоковими процесами

Якщо аварія сталася у фоновому потоці, важливо дослідити стан усіх потоків одночасно, щоб виявити можливі взаємні блокування (Deadlocks) або конкурентне руйнування пам'яті (Data Races).

| Команда GDB | Опис та призначення |
|---|---|
| `disassemble /s` | Дизасемблювати машинний код поточної функції з накладанням рядків вихідного сирцевого коду C/C++. |
| `disassemble $rip-32, $rip+32` | Дизасемблювати діапазон адрес пам'яті в околиці вказівника інструкцій. |
| `info threads` | Показати список усіх зареєстрованих ниток процесу, їхні числові LWP ID та поточні адреси зупинки. |
| `thread <ID>` | Перемкнутися на нитку з вказаним ідентифікатором GDB. |
| `thread apply all bt` | Вивести короткий стек викликів для кожної нитки процесу одночасно. |
| `thread apply all bt full` | Вивести повний стек викликів з локальними змінними для всіх потоків процесу. |

## 4. Конфігурація AddressSanitizer (`ASAN_OPTIONS`) та UndefinedBehaviorSanitizer (`UBSAN_OPTIONS`)

Параметри середовища `ASAN_OPTIONS` та `UBSAN_OPTIONS` передаються у форматі розділених двокрапкою пар ключ-значення: `export ASAN_OPTIONS="key1=val1:key2=val2"`. Ці параметри контролюють глибину перевірок пам'яті, роботу аллокатора санітайзера та механізми генерації звітів.

### Опції AddressSanitizer

| Параметр | Типове значення | Рекомендоване для діагностики | Призначення |
|---|---|---|---|
| `detect_leaks` | `1` | `1` | Увімкнути автоматичну перевірку витоків пам'яті LeakSanitizer (LSan) під час виходу з програми. |
| `abort_on_error` | `0` | `1` | Замість виходу через `_exit(1)` викликати функцію `abort()` для миттєвої генерації core dump при виявленні помилки ASan. |
| `symbolize` | `1` | `1` | Автоматично декодувати адреси стека викликів у назви файлів та номери рядків через вбудований llvm-symbolizer. |
| `fast_unwind_on_fatal` | `1` | `0` | Використовувати точний розмотувач DWARF замість швидкого розмотування за регістром Frame Pointer (`$rbp`) при формуванні звіту про крах. |
| `allocator_may_return_null` | `0` | `1` | Дозволити функціям `malloc`/`calloc` повертати `NULL` при вичерпанні лімітів пам'яті замість негайної паніки санітайзера. |
| `detect_stack_use_after_return` | `0` | `1` | Виявляти спроби звернення до локальних змінних функції після її завершення (use-after-return) шляхом виділення стекових фреймів на купі. |
| `quarantine_size_mb` | `256` | `512` | Розмір карантинного буфера звільненої пам'яті в мегабайтах для надійного перехоплення застарілих `use-after-free`. |
| `redzone` | `16` | `32` або `64` | Розмір захисної червоної зони навколо блоків пам'яті на купі в байтах (більший розмір ловить ширші виходи за межі). |
| `log_path` | `stderr` | `/var/log/asan.log` | Шлях до файлу для збереження звітів про дефекти пам'яті замість стандартного потоку помилок. |

### Опції UndefinedBehaviorSanitizer (`UBSAN_OPTIONS`)

- `halt_on_error=1` — негайно зупиняти виконання програми при виявленні першого випадку невизначеної поведінки замість простого друку попередження в `stderr`.
- `print_stacktrace=1` — додавати повний стек викликів DWARF до кожного звіту про невизначену поведінку.
- `suppressions=ubsan.supp` — вказати шлях до файлу виключень для ігнорування відомих безпечних переповнень у сторонніх бібліотеках.

## 5. Прапорці та правила придушення Valgrind Memcheck

Команди запуску утиліти Valgrind для динамічної перевірки пам'яті програм без потреби їхньої повторної компіляції. Valgrind транслює машинний код бінарника у внутрішнє проміжне представлення VEX IR, емулюючи роботу процесора і відстежуючи адресність та валідність кожного байта оперативної пам'яті.

| Прапорець Valgrind | Параметри / Значення | Призначення та діагностичний ефект |
|---|---|---|
| `--tool=memcheck` | — | Запустити інструмент детального аналізу пам'яті (активний за замовчуванням). |
| `--leak-check=full` | `no` / `summary` / `full` | Вивести детальний звіт про кожен окремий витік пам'яті з точним стеком виділення блоку. |
| `--show-leak-kinds=all` | `definite,indirect,possible,reachable` / `all` | Відобразити всі категорії витоків, включаючи пам'ять, вказівники на яку зміщені всередину структури (`possible`). |
| `--track-origins=yes` | `no` / `yes` | Відстежувати точне місце створення неініціалізованої пам'яті при виявленні помилки "Use of uninitialised value" (збільшує споживання пам'яті). |
| `--read-var-info=yes` | `no` / `yes` | Зчитувати налагоджувальну інформацію DWARF про типи та імена локальних змінних для деталізації звітів. |
| `--num-callers=30` | Ціле число (дефолт `12`) | Глибина стека викликів, що зберігається та виводиться у звітах про витоки та пошкодження пам'яті. |
| `--gen-suppressions=all` | `no` / `yes` / `all` | Згенерувати готові правила придушення (suppressions) для помилок у системних бібліотеках glibc для збереження у `.supp` файл. |
| `--suppressions=file.supp` | Шлях до файлу | Завантажити файл правил ігнорування відомих безпечних дефектів у сторонньому коді. |
| `--log-file=valgrind.log` | Шлях до файлу | Скерувати повний діагностичний звіт у текстовий файл замість консольного потоку. |

### Формат файлу придушення помилок (`valgrind.supp`)

Якщо стороння бібліотека містить відомі нешкідливі витоки пам'яті під час ініціалізації середовища, їх фільтрують за допомогою структурованих блоків:

```text
{
   ігнорувати_витік_системного_tls
   Memcheck:Leak
   match-leak-kinds: reachable
   fun:malloc
   fun:allocate_dtv
   fun:_dl_allocate_tls
   fun:pthread_create*
}
```

Кожне правило описує тип помилки (`Memcheck:Leak`, `Memcheck:Addr8`, `Memcheck:Value8`, `Memcheck:Cond`) та послідовність символів у стеку викликів (`fun:` для імен функцій, `obj:` для імен бібліотек).
