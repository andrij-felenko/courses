# 🧮 Вартісна модель переміщення даних: розрахунок затримок і пропускної здатності

Цей математичний аналіз встановлює аналітичну залежність між архітектурою вводу-виводу, кількістю проходів даних крізь шину оперативної пам'яті, частотою перемикання кілець захисту процесора та підсумковою пропускною здатністю системи. Без формального розрахунку витрат неможливо обґрунтувати, чому заміна класичного `read`/`write` на `sendfile` або `io_uring` дає не просто процентний приріст швидкості, а змінює асимптотичну межу насичення апаратних ресурсів.

## 1. Загальне рівняння часового бюджету операції вводу-виводу

Повний астрономічний час `T_total`, необхідний для передачі порції даних обсягом `S` байтів між джерелом і приймачем, складається з фіксованих накладних витрат ядра та змінних витрат на фізичне переміщення байтів:

```
T_total = T_syscall + T_context + T_mmu + T_copy + T_dma + T_irq
```

Розгорнемо кожен компонент часового бюджету через параметри системи:

1. **Ціна системних викликів (`T_syscall`):**
   Сумарний час переходів між простором користувача (Ring 3) та простором ядра (Ring 0):
   ```
   T_syscall = N_sys · t_sys
   ```
   де `N_sys` — кількість системних викликів, необхідних для передачі даних, `t_sys` — час виконання пари інструкцій `SYSCALL`/`SYSRET` з урахуванням відновлення таблиць сторінок KPTI (Kernel Page Table Isolation) та бар'єрів безпеки спекулятивного виконання (Speculative Execution Barriers). На сучасних процесорах x86-64 величина `t_sys` становить від 70 до 250 наносекунд.

2. **Ціна перемикання контексту задач (`T_context`):**
   Витрати на зміну активного потоку планувальником при блокуванні на дескрипторі:
   ```
   T_context = N_ctx · t_ctx
   ```
   де `N_ctx` — кількість вимушених перемикань контексту (`voluntary_ctxt_switches`), `t_ctx` — час збереження регістрів, перемикання стека ядра та перезавантаження покажчика `CR3` (від 1.2 до 3.5 мікросекунд).

3. **Ціна трансляції та фіксації пам'яті (`T_mmu`):**
   Витрати ядра на валідацію віртуальних адрес користувача, обхід таблиць сторінок (`get_user_pages` / GUP) та скидання записів буфера асоціативної трансляції (TLB):
   ```
   T_mmu = N_pages · t_gup + N_tlb · t_tlb
   ```
   де `N_pages = ⌈S / 4096⌉` — кількість задіяних фізичних сторінок, `t_gup` — час перевірки прав доступу сторінки (≈ 15–30 нс на сторінку).

4. **Ціна копіювання даних процесором (`T_copy`):**
   Час, витрачений ядрами CPU на фізичне переміщення байтів між буферами через інструкції `rep movsb` або векторні регістри AVX-512:
   ```
   T_copy = k_cpu · (S / BW_l1_copy)
   ```
   де `k_cpu` — кількість операцій копіювання, що виконуються процесором, `BW_l1_copy` — ефективна швидкість копіювання пам'яті процесором з урахуванням читання в регістр та запису назад у RAM. Коли розмір буфера не вирівняний по межі 64-байтових рядків кешу, виникають додаткові апаратні зупинки конвеєра процесора (Store Forwarding Stalls), через які запис за непарною адресою блокує наступне читання того самого рядка пам'яті на 10–18 додаткових тактів процесора на кожні 64 байти.

5. **Ціна апаратного переміщення Direct Memory Access (`T_dma`):**
   Час передачі даних контролером шини PCIe між пам'яттю DRAM та пристроєм:
   ```
   T_dma = k_dma · (S / BW_pcie)
   ```
   де `k_dma` — кількість операцій DMA (зазвичай `k_dma = 2`: 1 читання з диска + 1 запис у мережеву карту), `BW_pcie` — пропускна здатність шини PCIe (наприклад, PCIe 4.0 x8 забезпечує ≈ 15.75 ГБ/с).

6. **Ціна обробки переривань (`T_irq`):**
   Час виконання апаратних обробників переривань контролера та програмних м'яких переривань `NET_RX_SOFTIRQ` / `NET_TX_SOFTIRQ`:
   ```
   T_irq = N_irq · (t_hardirq + t_softirq)
   ```

## 2. Модель насичення шини оперативної пам'яті

Головним фізичним обмежувачем максимальної пропускної здатності сервера є не частота процесора, а сумарний трафік через контролер оперативної пам'яті (DRAM Memory Controller).

Нехай фізична пропускна здатність шини оперативної пам'яті становить `BW_dram` (наприклад, для двоканальної DDR4-3200 це 51.2 ГБ/с, для восьмиканальної DDR5-4800 — 307.2 ГБ/с).

Кожен байт корисних даних, що проходить через сервер, створює певну кількість звернень до шини DRAM залежно від обраної моделі вводу-виводу:

```
N_traversals = k_dma_read + k_cpu_read + k_cpu_write + k_dma_write
```

Для класичної схеми `read()` + `write()`:
1. Контролер диска записує дані в Page Cache ядра через DMA: 1 прохід запису DRAM (`k_dma_read = 1`).
2. Процесор зчитує дані з Page Cache в регістри CPU: 1 прохід читання DRAM (`k_cpu_read1 = 1`).
3. Процесор записує дані з регістрів у буфер користувача: 1 прохід запису DRAM (`k_cpu_write1 = 1`).
4. Процесор зчитує дані з буфера користувача в регістри під час `write()`: 1 прохід читання DRAM (`k_cpu_read2 = 1`).
5. Процесор записує дані в буфер сокета `sk_buff`: 1 прохід запису DRAM (`k_cpu_write2 = 1`).
6. Контролер мережевої карти зчитує дані з `sk_buff` через DMA: 1 прохід читання DRAM (`k_dma_write = 1`).

Сумарна кількість проходів одного байта крізь шину оперативної пам'яті:
```
N_traversals = 1 + 1 + 1 + 1 + 1 + 1   [сума шести операцій звернення до шини]
             = 6                        [підсумок: 6 проходів DRAM на кожен байт]
```

Якщо дані поміщаються в процесорний кеш L3, проміжні проходи 3 і 4 не потрапляють у зовнішню DRAM. Проте при потоковій передачі великих файлів (розмір яких перевищує обсяг кешу L3 процесора) кеш безперервно вимивається, і всі 6 операцій звертаються безпосередньо до DRAM.

Максимальна теоретична корисна пропускна здатність вводу-виводу `BW_effective` обмежена фізичною межею шини:

```
BW_effective = BW_dram / N_traversals
```

### Розрахунок ефективної швидкості для різних архітектур

Обчислимо максимальну швидкість передачі даних для сервера з пропускною здатністю пам'яті `BW_dram = 64 ГБ/с`:

**1. Класичний `read()` + `write()` (6 проходів шини DRAM):**
```
BW_effective = 64 / 6                                     [формула відношення смуги до кількості проходів]
             = 10.67 ГБ/с                                 [обмеження шиною пам'яті: 85.3 Гбіт/с]
```

**2. `sendfile()` без підтримки Scatter-Gather DMA (4 проходи: DMA in + CPU read + CPU write + DMA out):**
```
BW_effective = 64 / 4                                     [ділення на 4 проходи пам'яті]
             = 16.00 ГБ/с                                 [обмеження шиною пам'яті: 128.0 Гбіт/с]
```

**3. `sendfile()` або `splice()` зі Scatter-Gather DMA (2 проходи: DMA in + DMA out):**
```
BW_effective = 64 / 2                                     [ділення на 2 апаратні проходи DMA]
             = 32.00 ГБ/с                                 [обмеження шиною пам'яті: 256.0 Гбіт/с]
```

**4. `io_uring` з попередньо зареєстрованими буферами (`IORING_REGISTER_BUFFERS`):**
```
BW_effective = 64 / 2                                     [прямий доступ DMA без копій ядра]
             = 32.00 ГБ/с                                 [повне усунення процесорного трафіку пам'яті]
```

Висновок: перехід від `read/write` до архітектури Zero-Copy вивільняє 66.7% смуги пропускання шини пам'яті, дозволяючи серверу утилізувати мережеві інтерфейси 100G/200G без збільшення кількості процесорних сокетів.

## 3. Деградація кешу процесора (Cache Pollution Model)

Коли процесор виконує інструкцію `copy_to_user()` або `copy_from_user()`, він завантажує байти потоку в рядки кешу L1D, L2 та L3. Розмір одного рядка кешу на архітектурі x86-64 становить 64 байти.

Якщо обсяг переданого файлу `S` перевищує розмір кешу третього рівня `C_L3` (наприклад, `S = 128 МБ`, а `C_L3 = 32 МБ`), відбувається повне витіснення робочого набору інструкцій та структур даних застосунку (Working Set Eviction). Для сучасного процесора ієрархія затримок доступу до пам'яті виглядає так:
* кеш першого рівня L1D (32–48 КіБ): 4–5 тактів (≈ 1.0–1.2 нс);
* кеш другого рівня L2 (512 КіБ – 1 МБ): 12–14 тактів (≈ 3.0–3.5 нс);
* кеш третього рівня L3 (16–64 МБ, спільний): 40–50 тактів (≈ 10–14 нс);
* системна шина та пам'ять DRAM (головний масив): 200–300 тактів (≈ 60–90 нс).

Коли потік копіювання заповнює всі лінії кешу чужими даними вводу-виводу, кожен наступний крок обробки прикладних об'єктів змушений очікувати завантаження рядків із DRAM. Ймовірність промаху кешу `P_miss` для прикладного коду після завершення системного виклику копіювання наближається до одиниці:

```
P_miss(S) = 1.0   [при умові, що обсяг даних S значно перевищує ємність кешу C_L3]
```

Ціна промаху в кеш L3 дорівнює затримці звернення до головної пам'яті DRAM `t_dram ≈ 60–90 нс`. Якщо застосунок містить активний цикл обробки бізнес-логіки з кількістю звернень до пам'яті `M`, додаткова затримка виконання прикладного коду після виклику `read()` становить:

```
ΔT_app = M · (P_miss · t_dram - t_l3_hit)   [початкова формула різниці затримок]
       = M · (1.0 · 70 нс - 12 нс)          [підстановка значень при повному вимиванні кешу]
       = M · 58 нс                          [підсумкова додаткова затримка на М звернень]
```

При 100 000 звернень до структур даних це додає 5.8 мілісекунди чистої затримки до часу відповіді сервісу виключно через вимивання кешу копіюванням вводу-виводу.

## 4. Амортизація накладних витрат у пакетній моделі io_uring

В асинхронному інтерфейсі `io_uring` передача запитів виконується пачками (батчами) через кільцеві буфери спільної пам'яті.

Нехай розмір пакета операцій становить `B` (наприклад, `B = 64` операції за один системний виклик `io_uring_enter`).

Середня вартість виконання однієї операції вводу-виводу `Cost_op` виражається формулою:

```
Cost_op(B) = (t_enter / B) + t_sqe_submit + t_cqe_reap
```

де:
* `t_enter` — час системного виклику `io_uring_enter` (≈ 150 нс);
* `t_sqe_submit` — час запису структури `io_uring_sqe` у спільну пам'ять (≈ 12 нс, без виходу з Ring 3);
* `t_cqe_reap` — час читання структури `io_uring_cqe` із спільної пам'яті (≈ 8 нс, без виходу з Ring 3).

Порівняємо вартість накладних витрат ядра для різних розмірів пакета `B`:

**1. Одиничний синхронний виклик (`B = 1`):**
```
Cost_op(1) = (150 / 1) + 12 + 8                          [підстановка розміру батчу 1]
           = 170 нс на операцію                          [еквівалент класичного виклику]
```

**2. Пакет із 16 операцій (`B = 16`):**
```
Cost_op(16) = (150 / 16) + 12 + 8                        [підстановка розміру батчу 16]
            = 9.375 + 20                                 [проміжний розрахунок амортизованого виклику]
            = 29.38 нс на операцію                       [прискорення накладних витрат у 5.8 раза]
```

**3. Пакет із 64 операцій (`B = 64`):**
```
Cost_op(64) = (150 / 64) + 12 + 8                        [підстановка розміру батчу 64]
            = 2.34 + 20                                  [проміжний розрахунок амортизованого виклику]
            = 22.34 нс на операцію                       [прискорення накладних витрат у 7.6 раза]
```

**4. Режим ядерного опитування `IORING_SETUP_SQPOLL` (`t_enter = 0`, виклик ядра відсутній):**
```
Cost_op(SQPOLL) = 0 + 12 + 8                             [нульовий час виклику ядра завдяки потоку опитування]
                = 20.00 нс на операцію                   [абсолютний апаратний мінімум]
```

## 5. Векторний ввід-вивід: межа ефективності склеювання буферів

При надсиланні протокольного повідомлення, що складається із службового заголовка (`H` байтів) та корисного навантаження (`P` байтів), розробник обирає між трьома стратегіями:

1. **Два послідовні виклики `write()`:**
   ```
   T_two_writes = 2 · t_sys + (H + P) / BW_copy
   ```

2. **Склеювання в один суміжний буфер у просторі користувача через `memcpy()` перед викликом `write()`:**
   ```
   T_memcpy_write = t_sys + (H + P) / BW_copy_user + (H + P) / BW_copy_kernel
   ```

3. **Один векторний системний виклик `writev()` з масивом `iovec` із 2 елементів:**
   ```
   T_writev = t_sys + t_iovec_walk + (H + P) / BW_copy_kernel
   ```
   де `t_iovec_walk` — час обходу масиву `iovec` у ядрі (≈ 15–25 нс на сегмент).

### Розрахунок точки перетину стратегій

Знайдемо критичний розмір корисного навантаження `P_crit`, за якого векторний виклик `writev()` стає вигіднішим за користувацьке склеювання `memcpy()` + `write()`.

Прирівняємо часові витрати обох стратегій:

```
T_writev < T_memcpy_write
t_sys + t_iovec_walk + (H + P) / BW_k < t_sys + (H + P) / BW_u + (H + P) / BW_k
t_iovec_walk < (H + P) / BW_u
P > (t_iovec_walk · BW_u) - H
```

Підставимо типові апаратні значення:
* час обходу дескриптора ядра `t_iovec_walk = 20 нс`;
* швидкість копіювання пам'яті користувача `BW_u = 16 ГБ/с = 16 байтів/нс`;
* розмір протокольного заголовка `H = 64 байти`.

```
P_crit = (20 нс · 16 байт/нс) - 64 байт                  [підстановка апаратних параметрів]
       = 320 байт - 64 байт                              [розрахунок добутку затримки на смугу]
       = 256 байтів                                      [критичний поріг вигоди векторного вводу-виводу]
```

Висновок: якщо розмір корисного навантаження перевищує лише 256 байтів, векторний системний виклик `writev()` випереджає ручне склеювання через `memcpy()` за рахунок повного усунення зайвого циклу читання-запису в кеші L1 процесора.

## 6. Порівняльний бюджет пропускної здатності на 100-гігабітному каналі

Розглянемо мережевий інтерфейс 100 GbE, який передає `100 · 10⁹ / 8 = 12.5 ГБ/с` сирого трафіку. Оцінимо необхідні ресурси процесора для обслуговування цього потоку за різними технологіями для пакетів розміром 1460 байтів (MTU 1500, стандартний TCP payload):

Кількість пакетів на секунду (PPS):
```
PPS = 12.5 · 10⁹ байт / 1460 байт                         [ділення швидкості каналу на розмір пакета]
    = 8 561 643 пакетів/с                                 [понад 8.56 мільйонів пакетів щосекунди]
```

Часовий бюджет на обробку одного пакета на одному ядрі CPU:
```
T_budget = 1 секунда / 8 561 643                          [розподіл 1 секунди на кількість пакетів]
         = 116.8 наносекунд на пакет                      [жорсткий часовий ліміт одного ядра]
```

### Аналіз здійсненності для різних моделей вводу-виводу

1. **Синхронний `read()` + `write()` (1 виклик на пакет):**
   * Накладні витрати на виклики: `2 · t_sys = 2 · 150 нс = 300 нс`.
   * Час копіювання 1460 байтів (двічі): `2 · (1460 / 16) = 182.5 нс`.
   * Сумарний час на пакет: `300 + 182.5 = 482.5 нс`.
   * Кількість процесорних ядер, необхідних виключно для вводу-виводу:
     ```
     N_cores = 482.5 нс / 116.8 нс                        [відношення витрат до бюджету часу ядра]
             = 4.13 ядра                                  [понад 4 виділених ядра лише на копіювання та syscall]
     ```

2. **Zero-Copy `sendfile()` / `splice()`:**
   * Накладні витрати системного виклику: `t_sys = 150 нс`.
   * Час копіювання CPU: `0 нс` (дані переміщує контролер DMA).
   * Сумарний час на пакет: `150 нс`.
   * Потрібна кількість ядер:
     ```
     N_cores = 150 нс / 116.8 нс                          [відношення витрат системного виклику до бюджету]
             = 1.28 ядра                                  [зниження навантаження на процесор у 3.2 раза]
     ```

3. **`io_uring` з пакетуванням `B = 64` та `IORING_REGISTER_BUFFERS`:**
   * Накладні витрати: `Cost_op(64) = 22.34 нс`.
   * Час копіювання CPU: `0 нс`.
   * Сумарний час на пакет: `22.34 нс`.
   * Потрібна кількість ядер:
     ```
     N_cores = 22.34 нс / 116.8 нс                        [відношення амортизованих витрат до бюджету ядра]
             = 0.19 ядра                                  [одне ядро здатне обслужити повний 100G лінк]
     ```

## 7. Модель вартості сторінкових збоїв та трансляції пам'яті для mmap проти буферизованого читання

При відображенні файлів у пам'ять через виклик `mmap()` виникає компроміс між відсутністю системних викликів `read()` під час доступу та високою ціною обробки сторінкових збоїв (Page Faults) процесорним модулем MMU.

Час доступу до сторінки розміром 4 КіБ через `mmap` розкладається на три взаємовиключні сценарії:

1. **Попадання в TLB (TLB Hit):**
   ```
   T_mmap_hit = t_l1_access
              = 1.2 нс                                   [затримка кешу L1D]
   ```

2. **Промах TLB при наявності сторінки в таблиці сторінок (Page Table Walk):**
   ```
   T_mmap_ptw = t_l1_access + 4 · t_dram_access
              = 1.2 нс + 4 · 65 нс                        [4-рівневий обхід таблиць CR3->PML4->PDPT->PD->PT]
              = 261.2 нс                                 [апаратний обхід MMU]
   ```

3. **Незначний сторінковий збій (Minor Page Fault — сторінка є в Page Cache, але відсутня в таблиці процесу):**
   Подія вимагає переходу в Ring 0, захоплення блокування `mmap_lock`, виділення запису `pte_t` та оновлення TLB:
   ```
   T_minor_fault = t_trap_entry + t_lock_mmap + t_alloc_pte + t_tlb_insert + t_trap_exit
                 = 450 нс + 120 нс + 280 нс + 80 нс + 350 нс   [сума стадій обробника сторінкового збою]
                 = 1280 нс (1.28 мкс)                          [ціна одного Minor Fault]
   ```

4. **Скидання записів TLB між процесорними ядрами (TLB Shootdown):**
   Якщо багатопотоковий застосунок змінює захист або вивантажує сторінку через `munmap()`, ядро надсилає міжпроцесорні переривання (Inter-Processor Interrupts, IPI) усім ядрам, де виконуються потоки процесу:
   ```
   T_shootdown(K) = t_ipi_send + K · t_ipi_ack + t_tlb_flush
                  = 800 нс + K · 150 нс + 60 нс           [модель залежності від кількості активних ядер K]
   ```
   Для 32-ядерного сервера (`K = 32`) затримка операції `munmap()` становить:
   ```
   T_shootdown(32) = 800 нс + 32 · 150 нс + 60 нс         [підстановка кількості ядер]
                   = 800 нс + 4800 нс + 60 нс             [розрахунок часу очікування підтверджень]
                   = 5660 нс (5.66 мкс)                   [катастрофічна затримка міжядерної синхронізації]
   ```

### Точка перетину ефективності `mmap` та `pread`

Порівняємо сумарні витрати на читання блоку пам'яті розміром `N_pages · 4096` байтів:

* Для `pread()`: фіксований системний виклик + копіювання в буфер:
  ```
  T_pread_total = t_sys + N_pages · (4096 / BW_copy)
                = 150 нс + N_pages · (4096 / 16 байт/нс)
                = 150 нс + N_pages · 256 нс
  ```

* Для `mmap()` при першому доступі (послідовні Minor Page Faults):
  ```
  T_mmap_first_access = N_pages · T_minor_fault
                      = N_pages · 1280 нс
  ```

При першому зверненні до сторінок `pread()` виконується в 5 разів швидше за `mmap()`:
```
T_pread_page = 256 нс + (150 нс / N_pages)                [витрати pread на одну сторінку]
T_mmap_page  = 1280 нс                                    [витрати Minor Page Fault на сторінку]
Ratio        = 1280 / 256                                 [співвідношення витрат]
             = 5.0                                        [mmap у 5 разів повільніший на холодних сторінках]
```

## 8. Модель пропускної здатності каналів pipe та системного виклику splice

При передачі даних через анонімний канал `pipe` ядра Linux за допомогою виклику `splice()` дані не копіюються процесором, а переміщуються у вигляді посилань на фізичні сторінки `struct page*` всередині кільцевого масиву `pipe_buffer`.

Стандартна місткість каналу в ядрі Linux становить 16 сторінок (`16 · 4096 = 65 536` байтів, або 64 КіБ).

Швидкість роботи конвеєра `splice(fd_in, NULL, pipefd[1], NULL, len, 0)` та `splice(pipefd[0], NULL, fd_out, NULL, len, 0)` визначається співвідношенням часу запису в канал `T_in` та часу зчитування з каналу `T_out`:

```
T_pipe_stage = max(T_in, T_out) + 2 · t_splice_call + t_page_ref
```

де:
* `t_splice_call` — системний виклик `splice` (≈ 140 нс);
* `t_page_ref` — атомарне збільшення лічильника посилань сторінки `page_ref_inc()` (≈ 15 нс на сторінку).

Для блоку даних розміром `S = 64 КіБ` (`N_pages = 16`):
```
T_splice_total = 2 · 140 нс + 16 · 15 нс                  [два виклики splice на заповнення і спорожнення каналу]
               = 280 нс + 240 нс                          [сума системних викликів та атомарних посилань]
               = 520 нс на 64 КіБ                         [час передачі повного буфера каналу]
```

Розрахуємо граничну пропускну здатність передачі через `splice` на одному процесорному ядрі:
```
BW_splice_max = 65 536 байт / 520 нс                      [ділення обсягу блоку на час передачі]
              = 126.03 ГБ/с                               [гранична швидкість пам'яті ядра]
```

Якщо розмір буфера каналу збільшити через виклик `fcntl(pipefd[0], F_SETPIPE_SZ, 1048576)` до 1 Мегабайта (`256` сторінок), накладні витрати на виклики `splice` амортизуються ще сильніше:
```
T_splice_1M = 2 · 140 нс + 256 · 15 нс                    [два системні виклики на 256 сторінок]
            = 280 нс + 3840 нс                            [атомарні операції над 256 сторінками]
            = 4120 нс на 1 МБ                             [час передачі 1 МБ блоку]
```

Підсумкова пропускна здатність передачі:
```
BW_splice_1M = 1 048 576 байт / 4120 нс                   [ділення 1 МБ на час обробки]
             = 254.5 ГБ/с                                 [практично миттєва передача покажчиків у RAM]
```

## 9. Підсумкова матриця питомих витрат на операцію вводу-виводу

Зведемо отримані аналітичні результати у підсумкову матрицю витрат ресурсів процесора та пам'яті на передачу 1 Гігабайта даних блоками по 64 КіБ (всього `16 384` операції):

| Метод вводу-виводу | Системні виклики | Перемикання контексту | CPU-копіювання | Трафік DRAM | Витрати процесора на 1 ГБ |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `read()` + `write()` | 32 768 | 32 768 | 2.0 ГБ | 6.0 ГБ | ≈ 14.8 мс CPU-часу |
| `writev()` (векторний) | 16 384 | 16 384 | 1.0 ГБ | 5.0 ГБ | ≈ 9.2 мс CPU-часу |
| `sendfile()` (Zero-Copy) | 16 384 | 16 384 | 0 ГБ | 2.0 ГБ | ≈ 2.5 мс CPU-часу |
| `splice()` (Pipe Zero-Copy) | 32 768 | 0 (у межах процесу) | 0 ГБ | 2.0 ГБ | ≈ 4.6 мс CPU-часу |
| `io_uring` (батч 64) | 256 | 0 | 0 ГБ | 2.0 ГБ | ≈ 0.36 мс CPU-часу |
| `io_uring` (SQPOLL + Registered) | 0 | 0 | 0 ГБ | 2.0 ГБ | ≈ 0.08 мс CPU-часу |

Ця модель доводить, що максимальна продуктивність досягається одночасним усуненням двох незалежних факторів гальмування: зайвих проходів шини оперативної пам'яті через прямий апаратний доступ (Scatter-Gather DMA) та витрат на перемикання кілець процесора через асинхронні черги спільної пам'яті.
