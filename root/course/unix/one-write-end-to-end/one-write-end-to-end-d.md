<preknowlist>

- [VFS](root:sys-unix/vfs-layer) — шар віртуальної файлової системи, що уніфікує доступ до різнорідних файлових систем.

- [Кеш сторінок і fsync](root:sys-unix/page-cache-durability) — механізм кешування сторінок у RAM та семантика синхронізації з носієм.

- [NVMe в Linux](root:sys-unix/nvme-in-linux) — контролер, черги Submission/Completion та команди доступу до просторів імен.
</preknowlist>

Високонавантажена служба обробки замовлень записує 4096 байтів журналу транзакцій через системний виклик `write(fd, buffer, 4096)`. Для процесора та прикладного процесу операція завершується майже миттєво: через 700 наносекунд регістри процесора відновлено, функція повернула число `4096`, і потік виконання негайно рушив далі. Проте на фізичному носії — у кремнієвих комірках зарядових пасток NAND Flash чи в намагнічених доменах пластини HDD — цей блок з'явиться лише через десятки секунд, якщо взагалі з'явиться. Протягом цього проміжку 4096 байтів проходять послідовну трансформацію крізь сім рівнів операційної системи та контролера: від буфера стандартної бібліотеки libc до сторінки Page Cache, транзакції журналу JBD2, дескриптора `struct bio`, елемента черги `blk-mq`, команди NVMe Submission Queue і внутрішнього DRAM-кешу твердотільного накопичувача.

![Повний наскрізний шлях запису: від буфера програми у просторі користувача крізь сім рівнів операційної системи та контролера до фізичного сектора](/root/course/unix/one-write-end-to-end/img/full-write-path-pipeline.svg)
*Сім рівнів виконання запису: від моменту повернення виклику write() у просторі користувача до фізичної фіксації на кремнієвих комірках NAND Flash.*

Розуміння того, як один запис долає цей шлях, перетворює абстрактну модель операційної системи на точну інженерну карту. Від взаємодії цих рівнів залежить, чому виклик `fsync()` сповільнює систему на три порядки, як операційна система усуває блокування пам'яті між десятками процесорних ядер, чому журнал файлової системи гарантує цілісність структури каталогів, але не рятує незбережені дані, і як прямий доступ Direct I/O змінює маршрут байтів. Для практичного спостереження за цим маршрутом у реальному ядрі створено [практикум із трасування шляху запису](root:unix/one-write-end-to-end/proj-tracing-write-path.md).

## Рівень 1: Простір користувача, буферизація libc та інструкція syscall

Коли програма викликає функцію виведення на кшталт `fwrite()`, `fprintf()` або метод `std::ostream::write()`, дані спочатку потрапляють у буфер стандартної бібліотеки мови програмування (у середовищі GNU C Library це структура `_IO_FILE`).

```
ПРОСТІР КОРИСТУВАЧА                      ПРОСТІР ЯДРА
┌───────────────────────────┐           ┌───────────────────────────┐
│ Застосунок: fwrite()      │           │ Точка входу: sys_write()  │
│ └── stdio буфер (8 КіБ)   │           │ ├── current->files        │
│     └── POSIX write()     │           │ └── vfs_write()           │
└─────────────┬─────────────┘           └─────────────▲─────────────┘
              │                                       │
              │  x86_64: RAX=1, RDI=fd, RSI=buf, RDX=len
              └───────────────► SYSCALL ──────────────┘
```

Стандартна бібліотека C реалізує три режими буферизації потоку:
1. **Повна буферизація (`_IOFBF`):** Використовується за замовчуванням для всіх регулярних файлів. Бібліотека виділяє в купі процесу проміжний масив (зазвичай розміром 4096 або 8192 байти) і акумулює дрібні порції виведення.
2. **Рядкова буферизація (`_IOLBF`):** Застосовується для інтерактивних терміналів (`stdout`). Буфер скидається щоразу, коли в потоці зустрічається символ нового рядка `\n`.
3. **Небуферизований режим (`_IONBF`):** Усі байти негайно передаються ядру без проміжного накопичення (типовий режим для потоку помилок `stderr`).

Поки буфер `_IO_FILE` не заповнився, жоден системний виклик не генерується: операція додавання символів виконується як звичайне копіювання `memcpy()` у віртуальній пам'яті процесу зі швидкістю понад 10 ГБ/с.

Щойно буфер заповнюється, викликається функція `fflush()`, або коли застосунок викликає низькорівневий інтерфейс POSIX `write()`, починається перехід у простір ядра.

:::tabs
@tab C
```c
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

void demo_write_mechanics(void) {
    /* 1. Рівень stdio: байти осідають у буфері процесу */
    FILE *fp = fopen("app.log", "w");
    if (fp) {
        fputs("Рядок у stdio буфері\n", fp);
        fflush(fp); /* Явний виклик POSIX write() */
        fclose(fp);
    }

    /* 2. Прямий POSIX виклик: оминає stdio, йде в ядро */
    int fd = open("app.log", O_WRONLY | O_APPEND);
    if (fd >= 0) {
        const char msg[] = "Прямий системний виклик\n";
        ssize_t ret = write(fd, msg, sizeof(msg) - 1);
        (void)ret;
        close(fd);
    }
}
```

### Апаратний бар'єр: інструкція syscall та зміна контексту

Системний виклик `write()` — це не виклик звичайної функції, а контрольований перехід процесора з кільця користувача (Ring 3) у захищене кільце ядра (Ring 0).

На архітектурі x86_64 бібліотека libc завантажує параметри операції в апаратні регістри процесора за стандартом System V AMD64 ABI:
* `RAX = 1` (номер системного виклику `__NR_write`);
* `RDI = fd` (перший аргумент: числовий файловий дескриптор);
* `RSI = buf` (другий аргумент: віртуальна адреса буфера з даними);
* `RDX = count` (третій аргумент: кількість байтів для запису).

Після завантаження регістрів виконується машинна інструкція `syscall`. Процесор апаратно реалізує таку послідовність дій:
1. Зберігає адресу наступної інструкції процесу (`RIP`) у регістр `RCX`.
2. Зберігає поточний стан прапорців (`RFLAGS`) у регістр `R11` і маскує переривання відповідно до бітової маски в MSR-регістрі `IA32_FMASK`.
3. Завантажує нову адресу виконання ядра з MSR-регістра `IA32_LSTAR` (де записано адресу функції `entry_SYSCALL_64`).
4. Перемикає сегментні регістри коду й стека (`CS` та `SS`) на дескриптори ядра з рівнем привілеїв Ring 0.
5. За допомогою інструкції `swapgs` ядро підміняє базову адресу регістра `GS` на внутрішню структуру ядра `struct pcpu_hot`, що дає доступ до стека ядра поточного процесора.
6. Вказівник стека `RSP` перемикається з користувацького адресного простору на виділений стек ядра процесу (`task_struct.thread.sp0`).

Процесор опиняється в коді ядра. Функція `do_syscall_64()` зчитує номер `RAX = 1`, звертається до глобальної таблиці системних викликів `sys_call_table` і передає керування функції `sys_write()`.

## Рівень 2: Віртуальна файлова система (VFS) та пошук контексту

Шар VFS (англ. *Virtual Filesystem Switch*) виконує роль уніфікованого диспетчера. Його завдання — транслювати абстрактне число `fd` у конкретні структури даних ядра і перевірити права на виконання операції.

```
                  current (struct task_struct)
                            │
                            ▼
                    struct files_struct
                            │
                            ▼ fdt->fd[fd]
                    struct file
                   ┌───────────────────────────────┐
                   │ f_pos: 4096                   │
                   │ f_flags: O_WRONLY | O_APPEND  │
                   │ f_op: &ext4_file_operations   │
                   │ f_mapping ───────────────┐    │
                   └──────────────┬────────────────┘    │
                                  │                     │
                                  ▼ d_inode             ▼
                           struct inode          struct address_space
                          (метадані файлу)       (сторінковий кеш XArray)
```

Ланцюжок обробки запиту у VFS складається з таких кроків:

1. **Трансляція файлового дескриптора (`ksys_write`):** Ядро звертається до структури поточного процесу `current->files`. У таблиці дескрипторів `fdt->fd[fd]` воно знаходить покажчик на об'єкт відкритого файлу `struct file`. Якщо дескриптор виходить за межі виділеного діапазону або відповідний елемент масиву містить `NULL`, виклик моментально повертає помилку `-EBADF` (Bad File Descriptor).
2. **Перевірка прав доступу:** Ядро перевіряє, чи має файл встановлений прапорець дозволу запису `FMODE_WRITE`. Якщо файл було відкрито в режимі лише для читання (`O_RDONLY`), повертається помилка `-EBADF`.
3. **Контроль позиції та блокувань (`vfs_write`):**
   * Ядро перевіряє діапазон зміщення: операція запису не повинна перевищувати максимальний ліміт розміру файлу процесу `RLIMIT_FSIZE` та апаратні ліміти файлової системи.
   * Якщо дескриптор відкрито з прапорцем `O_APPEND`, ядро бере м'ютекс блокування інода `inode->i_rwsem` і оновлює поточну позицію `file->f_pos`, встановлюючи її рівною актуальному розміру файлу `i_size_read(inode)`. Це гарантує атомарність дописування в кінець файлу навіть за наявності кількох паралельних процесів.
4. **Поліморфна диспетчеризація:** Структура `struct file` містить таблицю віртуальних методів `struct file_operations *f_op`. Ядро викликає файлово-специфічний метод `file->f_op->write_iter(&kiocb, &iov_iter)`. Для файлової системи Ext4 цим методом є функція `ext4_file_write_iter()`, для XFS — `xfs_file_write_iter()`, а для Btrfs — `btrfs_file_write_iter()`.

На цьому етапі VFS завершує абстрактну маршрутизацію і передає керування драйверу конкретної файлової системи.

## Рівень 3: Сторінковий кеш (Page Cache), Folio та копіювання пам'яті

Сучасні файлові системи Linux у буферизованому режимі не взаємодіють із накопичувачем безпосередньо. Вони записують дані в Page Cache — єдину підсистему кешування файлових сторінок в оперативній пам'яті ядра.

Керування вмістом кешу здійснюється через структуру `struct address_space`, покажчик на яку міститься в `file->f_mapping` (або `inode->i_mapping`).

```
struct address_space (inode->i_mapping)
       │
       ▼
   XArray (дерево сторінок RAM)
  ┌─────────────────────────────────────────────────────────────┐
  │ Індекс 0 (0..4095)    ──> struct folio (4 КіБ) [PG_dirty]  │
  │ Індекс 1 (4096..8191) ──> struct folio (4 КіБ) [чиста]      │
  │ Індекс 2 (8192..12287)──> порожньо (не завантажено)        │
  └─────────────────────────────────────────────────────────────┘
```

Виклик `generic_perform_write()` виконує циклічну обробку байтів посторінково (кроками по 4096 байтів):

### Крок 1: Пошук або виділення сторінки в пам'яті

За файловим зміщенням `pos` ядро вираховує логічний індекс сторінки:
```
page_index = pos >> PAGE_SHIFT    [де PAGE_SHIFT = 12 для 4 КіБ сторінок]
```

За цим індексом ядро здійснює пошук у компактній деревоподібній структурі XArray (яка замінила класичне Radix Tree). Якщо сторінки в пам'яті немає:
* Викликається алокатор сторінок ядра (Buddy Allocator) через функцію `folio_alloc()`.
* Ядро виділяє новий фізичний фрейм пам'яті (структуру `struct folio`, що об'єднує одну або декілька суміжних сторінок).
* Новий об'єкт `folio` прив'язується до структури `address_space` і додається у дерево XArray.
* На сторінку накладається блокування блокування сторінки `folio_lock()`, щоб інші потоки не могли читати частково заповнену пам'ять.

Якщо запис змінює лише частину сторінки (наприклад, 100 байтів всередині 4 КіБ блоку), а решта сторінки ще не завантажена з диска, ядро зобов'язане виконати випереджувальне читання (*read-before-write*), зчитавши 4 КіБ з накопичувача, щоб незаписані байти не стали нулями.

### Крок 2: Копіювання байтів з простору користувача

Ядро викликає функцію `copy_page_from_iter_atomic()` (або `copy_from_user()`). Процесор зчитує байти з користувацького буфера `buffer` і записує їх у фізичну пам'ять ядра, виділену під сторінку Page Cache.

Операція виконується виключно на внутрішній шині пам'яті процесора (DDR4/DDR5) зі швидкістю 30–60 ГБ/с. Жодних сигналів на шини введення-виведення (PCIe чи SATA) у цей момент не надсилається.

Якщо віртуальна пам'ять процесу була вивантажена у swap або ще не була виділена фізично, під час `copy_from_user()` виникає сторінковий збій (*page fault*). Ядро тимчасово відпускає блокування, завантажує сторінку процесу і повторює спробу копіювання.

### Крок 3: Позначення сторінки прапорцем PG_dirty

Після завершення копіювання файлова система викликає функцію завершення запису (наприклад, `ext4_da_write_end()` -> `block_write_end()`):
1. **Оновлення розміру:** Якщо запис розширив файл, поле `inode->i_size` збільшується до нового значення.
2. **Маркування брудного стану:** Викликається функція `folio_mark_dirty()`. Вона встановлює бітовий прапорець `PG_dirty` у структурі `page->flags` і виставляє тег `PAGECACHE_TAG_DIRTY` у відповідному вузлі дерева XArray.
3. **Розблокування:** Знімається блокування `folio_unlock()`.

### Крок 4: Перевірка лімітів брудної пам'яті

Перед виходом ядро викликає `balance_dirty_pages_ratelimited(mapping)`. Ця функція перевіряє загальну кількість брудних сторінок у системі:
* Якщо частка модифікованої пам'яті менша за поріг фонового запису (`/proc/sys/vm/dirty_background_ratio`, зазвичай 10 %), ядро нічого не робить.
* Якщо обсяг перевищує жорсткий поріг (`/proc/sys/vm/dirty_ratio`, зазвичай 20 %), поточний процес примусово призупиняється і сам починає скидати сторінки на диск, сповільнюючись до швидкості накопичувача.

### Завершення виклику: повернення в Ring 3

Якщо пороги не перевищено, системний виклик `sys_write()` завершується. Процесор виконує інструкцію `sysretq`, яка відновлює користувацькі регістри `RIP`, `RSP`, `RFLAGS` та повертає виконання в простір користувача.

Програма отримує значення `4096`. Вона вважає операцію виконаною. Але фізично дані існують **лише у вигляді зарядів у конденсаторах оперативної пам'яті RAM**. Якщо прямо зараз висмикнути кабель живлення, ці 4096 байтів зникнуть безповоротно.

## Рівень 4: Журнал файлової системи (ext4 JBD2 / XFS log) та виділення блоків

Поки дані залишаються в пам'яті, файлова система готує зміни метаданих, які знадобляться під час збереження на диск.

Сучасні файлові системи (Ext4, XFS, Btrfs) використовують механізм **відкладеного виділення блоків** (англ. *delayed allocation* або *delalloc*). Під час виклику `write()` файлова система не шукає вільні сектори на диску і не модифікує бітову карту простору. Вона лише резервує квоту в лічильнику `i_reserved_data_blocks`.

Це дає дві колосальні переваги:
1. **Зменшення фрагментації:** Якщо програма записує файл шматками по 4 КіБ, відкладене виділення дозволяє накопичити 100 МБ у пам'яті й потім виділити для них один суцільний неперервний екстент на диску замість тисяч розрізнених кластерів.
2. **Усунення непотрібного вводу-виводу:** Тимчасові файли, які створюються і видаляються за кілька секунд (наприклад, під час компіляції), взагалі ніколи не отримують дискових секторів і не навантажують накопичувач.

```
       ЖУРНАЛ JBD2 (Круговий буфер на диску)
┌─────────────────────────────────────────────────────────────┐
│ Транзакція #4812                                            │
│ ├── Дескрипторний блок: опис змін                           │
│ ├── Блок метаданих 1: Inode #1042 (розмір = 4096 байтів)    │
│ ├── Блок метаданих 2: Бітова карта блоків (блок 512 зайнято)│
│ └── БЛОК ФІКСАЦІЇ (Commit Record + Flush бар'єр)           │
└─────────────────────────────────────────────────────────────┘
```

### Журналювання транзакцій (JBD2)

Коли настає час записати файл на диск, виникає фундаментальна небезпека: запис файлу вимагає модифікації кількох структур — самого інода, бітової карти вільних блоків, дерева екстентів та секторів даних. Якщо аварія живлення станеться посеред цього процесу, файлова система перейде в неузгоджений стан.

Щоб запобігти цьому, файлова система Ext4 використовує підсистему журналювання JBD2 (Journaling Block Device 2). За замовчуванням діє режим **`data=ordered`**:
1. **Збір транзакції:** Усі зміни метаданих об'єднуються у відкриту транзакцію (*running transaction*).
2. **Виштовхування даних:** Перед тим, як зафіксувати транзакцію в журналі, ядро примусово надсилає на диск блоки з новими даними файлу.
3. **Запис метаданих у журнал:** Блоки метаданих записуються у виділений кільцевий файл журналу на диску.
4. **Запис коміт-блоку (Commit Record):** В кінець журналу записується спеціальний маркер завершення транзакції. Перед записом коміт-блоку ядро надсилає дисковому контролеру апаратну команду бар'єра очищення кешу (`FLUSH`), щоб гарантувати: блоки даних та метадані журналу вже лежать на фізичному носії перед записом маркера завершення.

Якщо живлення зникне до запису коміт-блоку, під час наступного завантаження драйвер просто відкине незавершену транзакцію. Якщо після — драйвер виконає процедуру повторення журналу (*journal replay*) і накатить готові зміни на основне дерево файлової системи.

## Рівень 5: Блоковий рівень (Block Layer) та багаточергова підсистема blk-mq

Виштовхування брудних сторінок із пам'яті на диск ініціюється або фоновим потоком ядра `wb_workfn` (видимим у системі як потік `kworker`), або примусово — через системні виклики `fsync()`, `fdatasync()` чи `sync()`.

Файлова система викликає метод зворотного запису `address_space_operations->writepages()` (для Ext4 це `ext4_writepages()`). Файлова система перетворює логічні зміщення сторінок у фізичні номери секторів диска (LBA — *Logical Block Address*) за допомогою дерева екстентів і починає формувати структури блокового рівня.

```
СТОРІНКИ RAM                    ВЕКТОР STRUCT BIO                   АГРЕГОВАНИЙ STRUCT REQUEST
┌──────────────┐               ┌───────────────────────────┐       ┌───────────────────────────┐
│ Folio 0 (4K) │──────────────►│ struct bio                │       │ struct request            │
├──────────────┤               │ ├── bi_sector: 204800     │──────►│ ├── __sector: 204800      │
│ Folio 1 (4K) │──────────────►│ ├── bio_vec[0]: Folio 0   │       │ ├── __data_len: 128 КіБ   │
├──────────────┤               │ ├── bio_vec[1]: Folio 1   │       │ └── bio_list: [bio1, bio2]│
│ Folio 2 (4K) │──────────────►│ └── bi_bdev: /dev/nvme0n1 │       └─────────────┬─────────────┘
└──────────────┘               └───────────────────────────┘                     │
                                                                                 ▼
                                                                     Hardware Dispatch Queue
```

### Формування struct bio

Основною одиницею вводу-виводу блокового рівня є структура `struct bio`. Вона описує атомарну операцію читання або запису для блокового пристрою:
* `bi_iter.bi_sector`: початковий сектор на пристрої (у 512-байтових одиницях);
* `bi_bdev`: покажчик на цільовий блоковий пристрій `struct block_device`;
* `bi_opf`: прапорці операції (`REQ_OP_WRITE`, `REQ_SYNC`, `REQ_FUA`);
* `bi_io_vec`: масив векторів `struct bio_vec`, де кожен елемент містить трійку `(struct page *bv_page, unsigned int bv_len, unsigned int bv_offset)`.

Один `bio` може описувати кілька фізично розрізнених сторінок пам'яті, якщо вони повинні бути записані в суміжний діапазон дискових секторів.

Підготовлена структура передається у блоковий рівень через функцію `submit_bio()`.

![Блоковий рівень: трансформація брудних сторінок у struct bio, обробка в blk-mq та злиття в апаратний запит struct request](/root/course/unix/one-write-end-to-end/img/block-layer-bio-to-request.svg)
*Перетворення сторінок пам'яті у структури блокового рівня: від адресного простору address_space крізь черги blk-mq до DMA-дескрипторів контролера.*

### Архітектура blk-mq (Multi-Queue Block Layer)

У старих версіях ядра Linux блоковий рівень мав одну глобальну чергу запитів під єдиним блокуванням (*request_queue lock*). На швидких SSD-накопичувачах із продуктивністю понад 500 000 IOPS це блокування ставало непереборним вузьким місцем: десятки процесорних ядер витрачали більшість часу на очікування доступу до черги.

Сучасна архітектура `blk-mq` вирішує цю проблему через дворівневу систему черг:

1. **Програмні черги на ядро CPU (`struct blk_mq_ctx` — *Software Staging Queues*):**
   Кожне логічне процесорне ядро має власну чергу підготовки запитів. Коли ядро виконує `submit_bio()`, воно кладе `bio` у чергу поточного CPU взагалі без міжядерних блокувань.
2. **Накопичувальні plug-списки (`struct blk_plug`):**
   Поточний потік виконання утримує локальний список накопичення. Якщо процес виконує послідовний запис багатьох сторінок, блоковий шар не відправляє кожен `bio` окремо, а об'єднує їх у локальному стеку процесу.
3. **Планувальник вводу-виводу (I/O Scheduler / Elevator):**
   Планувальник вирішує, у якому порядку запити надходитимуть до обладнання, та виконує критичну операцію **злиття запитів** (*merging*):
   * **Back Merge / Front Merge:** Якщо новий `bio` починається відразу після сектора, яким завершується вже існуючий у черзі запит `struct request`, вони об'єднуються в єдиний великий запит. Замість 32 окремих операцій по 4 КіБ формується один запит на 128 КіБ.
   * **Типи планувальників:**
     * `none`: Прямий пропуск без черги планування. Застосовується за замовчуванням для швидких NVMe накопичувачів, де апаратна затримка настільки низька, що робота алгоритмів планувальника лише додає накладні витрати CPU.
     * `mq-deadline`: Гарантує максимальний час очікування (дедлайн) для операцій читання й запису, запобігаючи голодуванню повільних запитів.
     * `bfq` (Budget Fair Queueing): Виділяє процесам пропорційні бюджети дискового секторообігу; ідеальний для десктопних систем та інтерактивних середовищ.
     * `kyber`: Легкий планувальник для серверних NVMe-масивів, що динамічно регулює глибину черги для дотримання цільових затримок SLA.
4. **Апаратні черги диспетчеризації (`struct blk_mq_hw_ctx` — *Hardware Dispatch Queues*):**
   Після планування та злиття агреговані об'єкти `struct request` переміщуються в апаратні черги відправки, кількість яких безпосередньо відповідає кількості фізичних черг команд, підтримуваних контролером пристрою.

## Рівень 6: Драйвер пристрою (NVMe/AHCI) та передача DMA

Коли запит `struct request` готовий до відправки на пристрій, шар `blk-mq` викликає функцію диспетчеризації драйвера `q->mq_ops->queue_rq(hctx, &bd)`. Для накопичувачів стандарту NVM Express цією функцією є `nvme_queue_rq()`.

```
ОПЕРАТИВНА ПАМ'ЯТЬ ХОСТА (RAM)                 NVMe КОНТРОЛЕР НАКОПИЧУВАЧА
┌──────────────────────────────────────┐       ┌─────────────────────────────┐
│ NVMe Submission Queue (Кільцевий буфер)│     │ ASIC Процесор контролера    │
│ ┌──────────────────────────────────┐ │       │                             │
│ │ 64-байтний запис команди (SQE)   │ │       │                             │
│ │ • Opcode: 0x01 (Write)           │ │       │                             │
│ │ • SLBA: 204800, NLB: 255 (128 KB)│ │       │                             │
│ │ • PRP1 / SGL: 0x1084A000 (RAM)   │ │       │                             │
│ └──────────────────────────────────┘ │       │                             │
└──────────────────┬───────────────────┘       └──────────────▲──────────────┘
                   │                                          │
                   │     MMIO Запис: Новий хвіст черги        │
                   └──────────────────────────────────────────┘
                        (Doorbell Register на шині PCIe)
```

Драйвер виконує такі низькорівневі операції:

1. **Формування 64-байтової команди SQE (Submission Queue Entry):**
   Драйвер заповнює стандартну структуру команди запису `struct nvme_command`:
   * `cdw0`: код операції запису `nvme_cmd_write` (`opcode = 0x01`);
   * `nsid`: ідентифікатор цільового простору імен накопичувача (*Namespace ID*);
   * `slba`: початковий 64-бітний логічний сектор (*Starting LBA*);
   * `length`: кількість блоків для запису;
   * `prp1` / `prp2` або `sgl`: покажчики фізичних адрес оперативної пам'яті (*Physical Region Page* або *Scatter Gather List*). Драйвер передає контролеру фізичні 64-бітні адреси сторінок пам'яті, звідки контролер повинен забрати дані.
2. **Дзвінок у дзвіночок (Doorbell Ring):**
   Заповнивши команду у виділеному кільцевому буфері пам'яті хоста, драйвер виконує один апаратний запис у регістр контролера через адресний простір пам'яті вводу-виводу (MMIO — *Memory-Mapped I/O*). Драйвер записує новий індекс хвоста черги у регістр `Submission Queue Tail Doorbell` за допомогою функції `writel(sq->tail, sq->q_db)`. Цей єдиний запис на шині PCIe повідомляє ASIC-контролеру накопичувача, що в оперативній пам'яті хоста з'явилася нова робота.
3. **Апаратне зчитування через Bus Master DMA:**
   Отримавши сповіщення від дверного дзвіночка, контролер NVMe бере на себе керування шиною PCIe:
   * DMA-рушій контролера вичитує 64-байтну команду SQE з оперативної пам'яті хоста.
   * Контролер розбирає PRP/SGL адреси та ініціює прямий доступ до оперативної пам'яті хоста (*Bus Master Direct Memory Access*).
   * Дані сторінок кешу (наприклад, 128 КіБ) перекачуються лініями PCIe прямо у внутрішній буфер контролера накопичувача без використання обчислювальних ядер CPU.
4. **Сповіщення про завершення (Completion & MSI-X):**
   * Забравши дані у внутрішній буфер, контролер записує 16-байтну структуру підтвердження CQE (Completion Queue Entry) у кільцевий буфер завершення хоста.
   * Контролер надсилає на шину PCIe повідомлення векторного переривання MSI-X.
   * Ядро процесора перериває поточну роботу і викликає функцію драйвера `nvme_irq()`.
   * Драйвер викликає `blk_mq_complete_request()`, який звільняє дескриптори `struct request` та `struct bio`.
   * Викликається зворотний виклик `end_page_writeback()`, який знімає зі сторінок Page Cache апаратний прапорець `PG_writeback`. Пам'ять знову стає «чистою» (*clean*).

## Рівень 7: Контролер накопичувача, FTL та фізичний сектор

Дані залишили шину процесора, пройшли лінії PCIe і опинилися всередині фізичного пристрою зберігання.

Сучасний твердотільний накопичувач (NVMe/SATA SSD) — це самостійний спеціалізований комп'ютер. Він має власний багатоядерний мікроконтролер (ARM/RISC-V ASIC), швидкісну внутрішню оперативну пам'ять (LPDDR4/DRAM або внутрішню SRAM) та масив мікросхем енергонезалежної Flash-пам'яті (NAND Flash), розведених по 4–16 паралельних фізичних каналах.

```
                  ВНУТРІШНІЙ УСТРІЙ SSD
┌─────────────────────────────────────────────────────────────┐
│ Внутрішня шина контролера                                   │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Внутрішній DRAM-буфер / SLC-кеш (Енергозалежний)       │ │
│ └────────────────────────────┬────────────────────────────┘ │
│                              │ FTL трансляція (LBA ──> PBA) │
│                              ▼                              │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Канали Flash (Канал 0 .. Канал 7)                       │ │
│ │ ┌───────────────┐  ┌───────────────┐  ┌───────────────┐ │ │
│ │ │ Кристал 0     │  │ Кристал 1     │  │ Кристал N     │ │ │
│ │ │ TLC/QLC Блоки │  │ TLC/QLC Блоки │  │ TLC/QLC Блоки │ │ │
│ │ └───────────────┘  └───────────────┘  └───────────────┘ │ │
│ └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

Процес збереження всередині накопичувача відбувається у три етапи:

### 1. Внутрішній кеш запису (Volatile Write Cache)

Отримавши дані через DMA, контролер спочатку поміщає їх у свій внутрішній DRAM-буфер (або швидкий псевдо-SLC кеш) і **негайно надсилає хосту підтвердження успішного завершення CQE**.

Для операційної системи операція блокового запису вважається успішно виконаною. Проте, якщо накопичувач споживчого класу (Consumer SSD) позбавлений апаратного захисту від знеструмлення PLP (Power Loss Protection на базі масиву танталових конденсаторів), аварійне відключення живлення в цю мікросекунду знищить вміст внутрішнього DRAM-кешу контролера.

### 2. Трансляція адрес: робота Flash Translation Layer (FTL)

Фізична природа Flash-пам'яті унеможливлює перезапис даних на тому самому місці:
* Читання і запис здійснюються **сторінками** (розміром 16 КіБ);
* Стирання виконується лише великими **блоками** (розміром від 8 до 32 Мегабайтів).

Тому FTL реалізує парадигму запису в нове місце (*out-of-place write*):
1. FTL приймає логічний сектор (LBA), наприклад `LBA 204800`.
2. FTL знаходить у поточному відкритому блоці стирання чисту фізичну сторінку (PBA — *Physical Block Address*).
3. Дані кодуються алгоритмом корекції помилок (ECC / LDPC — *Low-Density Parity-Check*) для захисту від спотворень бітів.
4. FTL оновлює внутрішню таблицю трансляції адрес `LBA -> PBA`, а стару фізичну сторінку зі старими даними помічає як недійсну (сміття для майбутньої процедури *Garbage Collection*).

### 3. Фізичний запис: програмування комірок пам'яті

На фізичному рівні мікросхеми контролер подає високу напругу (15–20 В) на керуючі затвори транзисторів комірок Flash-пам'яті. Завдяки квантовомеханічному ефекту тунелювання Фаулера — Нордгейма електрони долають діелектричний бар'єр оксиду кремнію і потрапляють у плаваючий затвор або нітридну зарядову пастку (*Charge Trap Flash*).

Залежно від щільності комірки:
* **SLC (1 біт):** програмується 2 рівні заряду;
* **TLC (3 біти):** програмується 8 прецизійних рівнів напруги;
* **QLC (4 біти):** програмується 16 дискретних станів заряду.

Коли електричний заряд стабілізувався в кремнії, дані нарешті стали енергонезалежними. Вони переживуть вимкнення живлення і зберігатимуться роками.

## Примусова синхронізація: механіка fsync, FUA та FLUSH

Оскільки на кожному кроці системи існують буфери та кеші, виникає питання: як гарантувати, що критичні дані справді досягли фізичних комірок пам'яті?

Для цього операційна система та апаратні протоколи надають спеціальні інструменти примусової синхронізації:

```
Застосунок: fsync(fd) / fdatasync(fd)
   │
   ▼
VFS: vfs_fsync() ──> ext4_sync_file()
   │
   ├── 1. Виштовхування всіх брудних сторінок інода (ext4_writepages)
   ├── 2. Завершення поточної транзакції JBD2 (jbd2_journal_commit_transaction)
   └── 3. Відправка блокових запитів із прапорцями синхронізації
          │
          ▼
Блоковий рівень: REQ_OP_WRITE | REQ_PREFLUSH | REQ_FUA
   │
   ▼
NVMe Команди контролеру:
   ├── NVMe Command: Flush (Opcode 0x00) ──> Очищення DRAM-кешу SSD
   └── NVMe Write + біт FUA (Force Unit Access) ──> Прямий запис у NAND Flash
```

### Різниця між fsync() та fdatasync()

* **`fsync(fd)`:** Скидає на диск модифіковані сторінки даних файлу **та всі пов'язані метадані інода** (включно з міткою часу зміни `st_mtime` та `st_ctime`). Це змушує файлову систему відкривати та фіксувати додаткову транзакцію в журналі JBD2.
* **`fdatasync(fd)`:** Скидає сторінки даних і лише ті метадані, які **необхідні для подальшого зчитування даних** (наприклад, зміну розміру файлу `i_size` чи нові адреси екстентів). Якщо змінився лише час модифікації `mtime`, оновлення журналу не виконується. У базах даних це заощаджує до 30–50 % дискових операцій на операцію коміту.

#include <fcntl.h>

### Команди контролера: FLUSH та FUA

На рівні апаратного інтерфейсу накопичувача ядро використовує два механізми:
1. **Команда `FLUSH` (NVMe Opcode `0x00` / ATA `FLUSH CACHE EXT`):**
   Ядро надсилає окрему команду, яка наказує контролеру зупинити обробку черги і скинути весь вміст свого енергозалежного DRAM-кешу в комірки енергонезалежної пам'яті. Контролер не повертає підтвердження CQE, поки останній байт не опиниться в кремнії.
2. **Прапорець `FUA` (Force Unit Access):**
   Прапорець виставляється безпосередньо в 64-байтовій команді запису (біт 30 у полі `cdw12` NVMe). Він вказує контролеру: «запиши ці дані безпосередньо у фізичні комірки пам'яті, минаючи внутрішній DRAM-кеш накопичувача, і звітуй про успіх лише після фіксації в NAND».

## Зведена карта наскрізного шляху запису

Підсумуємо трансформацію одного виклику `write()` крізь усі підсистеми системи у зведеній інженерній таблиці:

| Рівень | Підсистема | Основні структури даних | Типова затримка | Де знаходяться дані? |
|---|---|---|---|---|
| **1. User Space** | Застосунок / libc | `FILE`, `_IO_FILE`, регістри ABI | 10–50 нс | Буфер у віртуальній пам'яті процесу |
| **2. Вхід у ядро** | Перехід Ring 3 ──> Ring 0 | MSR `IA32_LSTAR`, `task_struct` | 50–150 нс | Регістри CPU / стек ядра |
| **3. VFS** | Таблиця дескрипторів | `struct file`, `struct inode` | 100–300 нс | Контекст ядра в RAM |
| **4. Page Cache** | Керування пам'яттю | `address_space`, `struct folio`, XArray | 300–800 нс | **Оперативна пам'ять RAM** (`PG_dirty`) |
| **5. ФС / Журнал** | Ext4 / XFS / JBD2 | Extents tree, JBD2 Journal Transaction | 1–10 мкс | RAM (резервування квот екстентів) |
| **6. Block Layer** | blk-mq / Планувальник | `struct bio`, `struct request`, `blk_mq_ctx` | 2–20 мкс | RAM (пакетні черги блокового шару) |
| **7. Драйвер** | NVMe Driver / PCIe | NVMe SQE/CQE, PRP/SGL DMA списки | 5–15 мкс | RAM / PCIe лінії (DMA передача) |
| **8. Контролер** | SSD Controller FTL | FTL Mapping Table, LPDDR4 Cache | 10–50 мкс | Внутрішній DRAM-буфер SSD |
| **9. Фізичний шар** | Кристали Flash-пам'яті | Плаваючі затвори / зарядові пастки TLC | 100–800 мкс | **Енергонезалежний кремній NAND Flash** |

### Підсумок

Шлях від виклику `write()` до фізичного сектора накопичувача — це багаторівневий компроміс між швидкістю та надійністю. 

Завдяки сторінковому кешу операційна система повертає керування прикладній програмі за частки мікросекунди, даючи змогу процесору виконувати мільярди операцій без простою в очікуванні повільного вводу-виводу. Завдяки відкладеному виділенню блоків та чергам `blk-mq` ядро формує великі неперервні блоки запису та паралелізує потік команд між сотнями черг NVMe.

Водночас платою за цю продуктивність є складна архітектура журналювання та бар'єрів пам'яті: надійне збереження даних вимагає свідомого керування точками синхронізації через `fsync()` або прапорці `O_SYNC`/`O_DIRECT`, щоб перетворити миттєву ілюзію успішного запису в оперативній пам'яті на гарантовану фізичну фіксацію заряду в енергонезалежному носії.
