# 📜 Історія команди which та чому вона розсипається між системами

Команда `which` є одним із найбільш оманливих інструментів в історії Unix: створена для швидкої перевірки розташування двійкових файлів, вона протягом чотирьох десятиліть породжувала несумісні реалізації та приховані аварії в скриптах автоматизації.

---

## Народження у 2BSD: csh-скрипт Білла Джоя

Наприкінці 1970-х років у Каліфорнійському університеті в Берклі Білл Джой (Bill Joy) розробляв оболоку C Shell (`csh`) для дистрибутива 2BSD. На відміну від стандартної оболонки Стівена Борна (Bourne Shell, `sh`), `csh` ввела дві революційні на той час можливості: механізм створення псевдонімів (`alias`) та кешування шляхів до двійкових файлів у внутрішній хеш-таблиці (`hash`).

Користувачам знадобився спосіб з'ясувати, який саме файл або аліас спрацює при введенні команди. Оскільки `csh` не мала вбудованої команди інспекції, Білл Джой написав невеликий зовнішній скрипт `/usr/ucb/which`, призначений виключно для інтерпретатора `csh`:

```csh
#!/bin/csh -f
# Оригінальний підхід 2BSD / 3BSD (1978-1979)
set noglob
foreach arg ($argv)
    # Запуск дочірньої копії csh для зчитування конфігурації .cshrc
    # та пошуку через внутрішню таблицю аліасів
    ...
end
```

Цей перший варіант містив фундаментальну архітектурну ваду, яка переслідувала утиліту всі наступні роки: щоб дізнатися стан поточної сесії користувача, зовнішній скрипт запускав нову підпорядковану оболонку `csh -f` і заново перечитував файл ініціалізації `~/.cshrc`. Якщо користувач перевизначив команду у своїй активній сесії, але не зберіг її у файлі конфігурації, або якщо конфігурація містила умовні конструкції, `which` показував застарілу або зовсім неправдиву інформацію.

## Розкол між гілками: System V проти BSD

Коли на початку 1980-х операційна система Unix розділилася на дві головні комерційні гілки — AT&T System V та BSD, — утиліта `which` опинилася в центрі несумісності:

1. **Гілка AT&T System V:** розробники Bell Labs відмовилися додавати `which` до базової системи. Натомість до стандартної оболонки Bourne Shell було додано вбудовану команду `type`. Команда `type` працювала безпосередньо всередині пам'яті процесу оболонки, знала про всі завантажені функції, зарезервовані ключові слова та внутрішні команди, не потребуючи запуску дочірніх процесів чи парсингу файлів на диску.
2. **Гілка BSD:** продовжувала постачати `which` як зовнішню утиліту. Програмісти, які переходили з BSD на робочі станції під керуванням System V (Solaris, HP-UX, AIX), виявляли відсутність звичної команди `which` і створювали власні наколінні реалізації на базі `sh`, `awk` або мови C.

У результаті в екосистемі з'явилися десятки варіантів `which`, кожен із яких поводився по-своєму: одні повертали код завершення `1`, якщо файл не знайдено, інші завжди завершувалися з кодом `0` і просто виводили повідомлення про помилку у стандартний потік помилок `stderr`, що ламало логічні перевірки `if which cmd; then ...`.

## Спроба стандартизації GNU та надлишкова складність

Проєкт GNU розробив власну версію `which` мовою C під авторством Карло Вуда (Carlo Wood). Намагаючись вирішити проблему невидимості аліасів, утиліта GNU `which` отримала розширені прапорці:
- `--read-alias`: спроба читати псевдоніми зі стандартного вводу;
- `--read-functions`: спроба вичитувати функції оболонки;
- `--skip-alias`, `--skip-functions`, `--show-dot`, `--show-tilde`.

Щоб змусити GNU `which` бачити аліаси Bash, розробники дистрибутивів рекомендували додавати в `~/.bashrc` монструозний псевдонім:

```bash
alias which='alias | which -i'
```

Ця конструкція створювала небезпеку: передача всього списку аліасів через конвеєр зовнішньому процесу під час кожного пошуку команди сповільнювала інтерактивну роботу та призводила до витоку внутрішніх змінних і секретів, випадково збережених у псевдонімах.

## Чому комітет POSIX відкинув `which`

Під час розробки стандарту IEEE Std 1003.1 (POSIX) робоча група з уніфікації оболонок та утиліт проаналізувала поведінку `which` і дійшла категоричного висновку: **зовнішній виконуваний файл принципово не здатний коректно визначити семантику команди в активній оболонці**.

Причини повної відмови POSIX від стандартизації `which`:
- **Сліпота до контексту:** бінарник у `/usr/bin/which` шукає файли виключно у власному масиві змінної `$PATH`. Він нічого не знає про перевизначені користувачем локальні функції `cd()`, тимчасові псевдоніми та спеціальні оператори оболонки (`[[`, `time`, `exec`).
- **Невизначеність коду виходу:** у різних версіях `which` відсутність аргументу або помилка пошуку повертали коди `0`, `1` або `2`.
- **Продуктивність:** виклик зовнішньої програми потребує системних викликів `fork()` та `execve()`, що робить перевірку утиліт у великих циклах надзвичайно повільною.

Замість `which` стандарт POSIX увів обов'язкову вбудовану утиліту `command` із прапорцем `-v`:

```shell
command -v <ім'я_команди>
```

`command -v` стандартизована для всіх сумісних оболонок (sh, dash, bash, ksh, zsh), повертає точний шлях для бінарників, ім'я для вбудованих команд або псевдонімів, і гарантує повернення ненульового статусу при невдачі.

## Сучасний фінал: вилучення `which` із Debian

У 2021 році суперечка навколо `which` досягла логічного завершення. Супроводжувачі дистрибутива Debian оголосили про вилучення пакета `debianutils/which` зі статусу обов'язкових (`Essential: yes`) у релізі Debian 12 (Bookworm). 

Дискусії в розсилці `debian-devel` продемонстрували, що тисячі старих shell-скриптів продовжували небезпечно перевіряти наявність утиліт через `which`:

```bash
# Небезпечний застарілий патерн
if which docker >/dev/null 2>&1; then
    docker run ...
fi
```

Якщо в мінімальному контейнері пакет `which` відсутній, умова повертає помилку `127` («команду which не знайдено»), і скрипт помилково вважає, що Docker не встановлений, навіть якщо `/usr/bin/docker` присутній у системі.

Сучасний надійний системний код утилізує виключно `command -v` для перевірки наявності програми або `type -a` для детальної діагностики середовища.
