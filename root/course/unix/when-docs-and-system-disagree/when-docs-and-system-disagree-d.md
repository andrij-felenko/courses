Ви знаходите в онлайн-документації або на StackOverflow команду для заміни рядків у файлах, копіюєте рядок `sed -i '' 's/old/new/g' config.txt`, запускаєте його на сервері Ubuntu 24.04 і замість тихих змін отримуєте помилку:

```
sed: -e expression #1, char 1: unknown command: `''`
```

На іншій машині з Alpine Linux команда пошуку за регулярними виразами `grep -P '(?<=port=)\d+' server.log` завершується аварійним `grep: unrecognized option '--perl-regexp'`, хоча в офіційному мануалі прапорець `-P` описано першим. Спроба масового видалення тимчасових файлів через `rm *` раптово блокує автоматизований конвеєр, вимагаючи ручного підтвердження `y/n` на кожному кроці, оскільки в середовищі непомітно діє `alias rm='rm -i'`.

Ці ситуації ілюструють системну закономірність: будь-яка зовнішня документація — веб-статті, підручники, онлайн-мануали man7.org чи відповіді генеративних моделей — описує гіпотетичну систему з набором припущень автора. Реальна поведінка програми на конкретному хості формується динамічним нашаруванням оболонки, локальних аліасів, змінних середовища, версії пакета, дистрибутивних патчів та системних викликів ядра.

Щоб знайти точну причину розбіжності та змусити систему працювати передбачувано, необхідно розібрати шлях виконання команди крізь шість рівнів системної трансформації.

## Шість рівнів розриву між описом та виконанням

Коли користувач вводить рядок команди у терміналі, текст проходить шість послідовних етапів перетворення перед тим, як перетворитися на інструкції процесора.

![Шість рівнів трансформації команди: від мануалу до системного виклику](/root/course/unix/when-docs-and-system-disagree/img/docs-vs-reality-layers.svg)
*Шість рівнів трансформації команди: від тексту в мануалі до системного виклику в ядрі.*

Розбіжність виникає на будь-якому з цих кроків:
1. **Зовнішня документація (Documentation Plane):** описує конкретний реліз утиліти на конкретній ОС (найчастіше GNU/Linux або macOS), не враховуючи специфіки вашого дистрибутива чи версії.
2. **Парсинг оболонки (Shell Evaluation):** перевіряє наявність аліасів, функцій та вбудованих у пам'ять команд (built-in), які перехоплюють виклик до звернення до файлової системи.
3. **Пошук виконуваного файлу ($PATH):** порядок каталогів у змінній `$PATH` визначає, який саме бінарник запуститься — наприклад, свіжа збірка з `/usr/local/bin` чи застаріла системна з `/usr/bin`.
4. **Реалізація бінарника (Implementation & Flags):** різна кодова база утиліт з однаковим ім'ям (GNU Coreutils, BSD Userland, BusyBox, Toybox) або зміна поведінки за замовчуванням між мажорними версіями однієї програми.
5. **Оточення процесу та конфігурація (Environment & Libc):** змінні локалі (`LC_COLLATE`, `LANG`), шляхи пошуку спільних бібліотек (`LD_LIBRARY_PATH`), файли налаштувань (`/etc` проти `~/.config`).
6. **Ядро та системні виклики (Kernel Syscall Truth):** єдине об'єктивне джерело істини про те, які файли були фактично відкриті і які операції виконані.

Розгляньмо кожне джерело розбіжностей детально.

## Джерела розбіжностей у кодовій базі утиліт

Найпоширеніша причина, чому команда з документації не працює, полягає в тому, що під одним і тим самим ім'ям у системі встановлено принципово іншу програму або іншу мажорну версію.

### Різні гілки реалізацій: GNU проти BSD проти BusyBox

Історично склалося три головних сімейства базових утиліт простору користувача:

```
                            Базові утиліти Unix
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         ▼                           ▼                           ▼
  GNU Coreutils                 BSD Userland                  BusyBox
(Linux / Ubuntu / RHEL)       (macOS / FreeBSD)          (Alpine / OpenWrt)
   Багаті прапорці,          Консервативний POSIX,       Один спільний бінарник,
   getopt_long (--opt)       відмінності в синтаксисі     мінімальний функціонал
```

#### 1. Модифікація файлів «на місці»: `sed -i`
- **GNU `sed`:** прапорець `-i` приймає необов'язковий суфікс резервної копії безпосередньо разом із прапорцем (`-i.bak`) або працює без створення копії без додаткових аргументів (`sed -i 's/foo/bar/g' file.txt`).
- **BSD `sed` (macOS, FreeBSD):** прапорець `-i` вимагає обов'язкового рядка суфікса розширення. Щоб не створювати резервну копію, передають порожній рядок окремим токеном: `sed -i '' 's/foo/bar/g' file.txt`.
- **Наслідок несумісності:** якщо запустити варіант BSD на машині з GNU `sed`, порожній рядок `''` буде сприйнятий як перший скрипт заміни, а вираз `'s/foo/bar/g'` — як ім'я цільового файлу, що призведе до помилки синтаксису.

#### 2. Регулярні вирази: `grep`
- **GNU `grep`:** підтримує прапорець `-P` (Perl-Compatible Regular Expressions, PCRE) для використання перевірок перегляду вперед/назад (`(?<=...)`), прапорець `-o` (вивід лише збігів) та розширені прапорці кольорів.
- **BusyBox `grep` (Alpine Linux):** підтримує лише базові регулярні вирази (BRE) та розширені (ERE через `-E`). Прапорець `-P` або довгі GNU-опції на кшталт `--line-buffered` відсутні.
- **BSD `grep`:** історично підтримував інші параметри контексту і не завжди компілювався з підтримкою PCRE.

#### 3. Обчислення відносних дат: `date`
- **GNU `date`:** дозволяє довільний парсинг людських дат через прапорець `-d`:
  ```shell
  date -d "yesterday 15:30" +%Y-%m-%d
  ```
- **BSD `date`:** прапорець `-d` слугує для встановлення літнього часу; для зсуву дат використовується прапорець `-v`:
  ```shell
  date -v-1d "+%Y-%m-%d"
  ```
- **BusyBox `date`:** підтримує лише парсинг конкретного числового формату дати через `-d @<seconds>` (Unix epoch timestamp).

#### 4. Синтаксис процесів: `ps`
- **Стиль BSD:** `ps aux` — опції передаються без початкового дефіса. Буква `a` означає всі процеси з терміналом, `u` — користувацький формат виводу, `x` — процеси без терміналу (фонові демони).
- **Стиль System V / POSIX:** `ps -ef` або `ps -u root`. Прапорець із дефісом `-u` означає фільтрацію за іменем користувача, а не зміну формату колонок. Змішування `ps -aux` на багатьох системах виводить попередження або повертає неочікувані списки процесів.

#### 5. Робота з архівами: `tar`
- **GNU `tar`:** автоматично розпізнає алгоритм стиснення (gzip, bzip2, xz, zstd) за заголовками файлу навіть без зазначення прапорця розпакування (`tar -xf archive.tar.xz`).
- **Класичний BSD / POSIX `tar`:** вимагає явного прапорця типу компресії (`-z` для gzip, `-j` для bzip2) або використання зовнішнього конвеєра (`xz -dc archive.tar.xz | tar -xf -`).

### Версійні зсуви та зміна поведінки за замовчуванням

Навіть у межах одного проекту GNU оновлення мажорної версії пакетів здатне зламати усталені скрипти:

#### 1. Зміна лапкування в GNU Coreutils 9.0+ (`ls`)
Починаючи з випуску Coreutils 9.0 (за замовчуванням у Debian 12 та Ubuntu 22.04+), утиліта `ls` змінила стандартне значення стилю лапкування `QUOTING_STYLE` на `shell-escape`. Якщо ім'я файлу містить пропуски, спецсимволи або лапки, `ls` автоматично бере його в одинарні лапки:

```shell
# Поведінка Coreutils 8.x:
ls
my file.txt  archive.tar.gz

# Поведінка Coreutils 9.x:
ls
'my file.txt'  archive.tar.gz
```

Якщо старий скрипт парсив текстовий вивід `ls` (що саме по собі є антипатерном) і розбивав рядки за пробілами або шукав точний збіг імен, додані лапки ламають конвеєр. Щоб повернути старий формат, вимагається явне вказання `ls -N` або `ls --quoting-style=literal`.

#### 2. Безпечне клонування файлів: `cp --reflink=auto`
У GNU Coreutils 9.0 утиліта `cp` за замовчуванням увімкнула спробу швидкого клонування блоків Copy-on-Write (`--reflink=auto`) на файлових системах Btrfs та XFS. Копіювання терабайтного файлу на сучасному дистрибутиві відбувається за мілісекунди без фізичного дублювання даних на диску, тоді як на старих дистрибутивах (Coreutils 8.x) `cp` повністю перечитує та перезаписує байти.

#### 3. Перехід `scp` на протокол SFTP в OpenSSH 9.0+
З випуску OpenSSH 9.0 утиліта `scp` припинила використовувати історичний протокол RCP (Remote Copy Protocol) 1980-х років і перейшла на використання підсистеми `sftp` за замовчуванням. 

У старому протоколі RCP клієнт надсилав рядок шляху на віддалений сервер, де той розкривався через віддалену оболонку (`sh -c "scp -d ..."`). Це дозволяло передавати шаблони автодоповнення:

```shell
scp user@server:/var/log/nginx/*.log .
```

У протоколі SFTP розкриття символів зірочки (`*`) на віддаленому боці більше не відбувається через shell. Якщо на сервері вимкнено підсистему SFTP (`Subsystem sftp` в `sshd_config`), клієнт `scp` від OpenSSH 9.0+ не може скопіювати файл, видаючи помилку `subsystem request failed on channel 0`, хоча підключення через `ssh` працює бездоганно. Для примусового повернення старого протоколу доводиться вказувати прапорець `scp -O`.

#### 4. Заміна `net-tools` на `iproute2`
Команди `ifconfig`, `route`, `netstat` і `arp` оголошені застарілими ще на початку 2000-х років, проте досі часто зустрічаються в онлайн-посібниках. Сучасні дистрибутиви Linux більше не постачають пакет `net-tools` за замовчуванням. Його замінив пакет `iproute2`:
- `ifconfig` → `ip addr` або `ip link`
- `route -n` → `ip route`
- `netstat -tuln` → `ss -tuln`
- `arp -an` → `ip neigh`

### Дистрибутивні патчі та альтернативи (Debian alternatives)

У багатьох дистрибутивах загальне ім'я програми не є прямим двійковим файлом, а веде до системи символьних посилань. Наприклад, у Debian та Ubuntu механізм `update-alternatives` створює ланцюжок:

```
/usr/bin/awk -> /etc/alternatives/awk -> /usr/bin/mawk
```

За замовчуванням у Debian встановлено `mawk` — надзвичайно швидку, але мінімалістичну реалізацію мови AWK, яка не підтримує розширень GNU AWK (`gawk`), таких як масиви масивів, функції часу `strftime()` або регулярні вирази з інтервалами `{n,m}` без прапорця `--posix`. Якщо інженер запускає скрипт, орієнтований на `gawk`, `mawk` завершується синтаксичною помилкою.

Аналогічно, системний редактор за замовчуванням `/usr/bin/editor` може вказувати на `nano`, `vim.basic` або `vim.tiny` (де вимкнено підсвічування синтаксису та плагіни), що кардинально змінює поведінку команд на кшталт `crontab -e` чи `git commit`.

## Пастки оболонки: вбудовані команди, аліаси та функції

Коли ви запускаєте команду, оболонка не поспішає звертатися до диску. Вона перевіряє внутрішні структури даних за суворою ієрархією пріоритетів.

![Ієрархія розв'язання імені команди в Unix-оболонці](/root/course/unix/when-docs-and-system-disagree/img/shell-resolution-hierarchy.svg)
*Ієрархія розв'язання імені команди в оболонці: чому аліас і вбудована функція перекривають двійковий файл у /usr/bin.*

### 1. Конфлікт Builtin проти двійкового файлу в `/usr/bin`

Оболонка містить десятки команд, реалізованих безпосередньо всередині її виконуваного коду, щоб уникнути витрат на виклики `fork()` та `execve()`. Проте поведінка вбудованої команди та однойменного бінарника на диску часто відрізняється:

#### Відмінності команди `echo`
- **Вбудована команда Bash (`builtin echo`):** не розкриває escape-послідовності (`\n`, `\t`) за замовчуванням; для їх інтерпретації потрібен прапорець `-e` (`echo -e "line1\nline2"`).
- **Вбудована команда Dash (`/bin/sh` у Debian/Ubuntu):** суворо слідує POSIX System V: вона **завжди** інтерпретує бекслеш-послідовності, але **не підтримує** прапорець `-e`. Якщо запустити скрипт під `dash`, рядок `echo -e "hello"` надрукує на екран `-e hello`.
- **Зовнішній бінарник `/bin/echo`:** реалізація GNU Coreutils, поведінка якої залежить від змінної оточення `POSIXLY_CORRECT`.

#### Відмінності команди `kill`
- **Вбудована команда Bash (`kill`):** розуміє ідентифікатори завдань фонового керування оболонки (Job Control), наприклад `kill %1` або `kill -STOP %+`.
- **Зовнішній бінарник `/bin/kill`:** системна утиліта, яка взаємодіє виключно з числовими ідентифікаторами процесів ядра (`PID`). Виклик `/bin/kill %1` призведе до помилки `kill: cannot find process "%1"`.

#### Відмінності утиліти `test` та оператора `[`
- Вбудовані `[` та `test` оптимізовані й виконуються за частки мікросекунди всередині процесу оболонки.
- Зовнішній файл `/usr/bin/[` є двійковим файлом ELF. Якщо у скрипті допущено синтаксичну помилку (наприклад, пропущено закриваючу дужку `]`), повідомлення про помилку від вбудованого інтерпретатора відрізнятиметься від помилки зовнішньої програми.

#### Відмінності `pwd`
- Вбудований `pwd` за замовчуванням повертає логічний шлях (`$PWD`), зберігаючи переходи через символьні посилання (`pwd -L`).
- Зовнішній `/bin/pwd` опитує ядро або розгортає фізичний шлях на диску (`pwd -P`), ігноруючи символьні лінки каталогу.

### 2. Приховані аліаси (Aliases)

Аліаси підставляються лексичним аналізатором оболонки на найпершому етапі розбору рядка. Вони діють виключно в інтерактивних сесіях (якщо явно не увімкнено `shopt -s expand_aliases`).

Типові конфігурації дистрибутивів (наприклад, у файлах `~/.bashrc` або `/etc/profile.d/`) містять «зручні» псевдоніми, які спотворюють стандартну поведінку:
- `alias rm='rm -i'` — змушує утиліту видалення запитувати підтвердження.
- `alias grep='grep --color=always'` — автоматично додає керівні escape-послідовності ANSI для розфарбовування тексту. Якщо вивід такого `grep` передати через конвеєр іншій утиліті (`grep pattern file | cut -d: -f1`), утиліта `cut` отримає невидимі байти кольорів (`\033[01;31m`), що поламає подальший парсинг.
- `alias ls='ls -F'` — додає суфікси типу файлу (`/` для каталогів, `*` для виконуваних файлів).

#### Способи гарантованого виклику справжнього бінарника в обхід аліасів:
1. **Бекслеш перед командою:** `\rm file.txt` (вимикає розкриття аліасу для першого слова).
2. **Вбудована утиліта `command`:** `command rm file.txt` (ігнорує аліаси та функції, виконуючи builtin або файл із `$PATH`).
3. **Виклик через утиліту `env`:** `env rm file.txt` (повністю очищає контекст оболонки й шукає файл у `$PATH`).
4. **Абсолютний шлях:** `/bin/rm file.txt`.

### 3. Вплив локалі: сортування та діапазони у регулярних виразах

Змінні середовища `LC_ALL`, `LC_COLLATE` та `LANG` безпосередньо впливають на таблиці сортування символів у стандартній бібліотеці C:

```shell
# Створення тестового списку:
printf "%s\n" a A b B c C > list.txt
```

1. **Сортування за стандартами ASCII (локаль `C` або `POSIX`):**
   ```shell
   LC_ALL=C sort list.txt
   # Результат:
   # A
   # B
   # C
   # a
   # b
   # c
   ```
   Усі великі літери (ASCII 65–90) розташовані перед малими літерами (ASCII 97–122).

2. **Сортування за словниковим порядком (локаль `en_US.UTF-8` або `uk_UA.UTF-8`):**
   ```shell
   LC_ALL=en_US.UTF-8 sort list.txt
   # Результат:
   # a
   # A
   # b
   # B
   # c
   # C
   ```

#### Небезпека діапазонів у `grep` та шаблонах файлів (Globbing)
У локалях UTF-8 вираз `[a-z]` означає не байтовий діапазон ASCII від 97 до 122, а інтерпольовану послідовність символів за алгоритмом Unicode Collation: `a, A, b, B, ..., y, Y, z`. У результаті:

```shell
LC_ALL=en_US.UTF-8 grep '^[a-z]' list.txt
```
Ця команда виведе також і великі літери `B` та `C`! Для суворого зіставлення латинських літер у системних скриптах необхідно завжди встановлювати `LC_ALL=C` або використовувати POSIX-класи `[[:lower:]]`.

### 4. Вплив змінних динамічного лінкера

Змінні середовища `LD_LIBRARY_PATH` та `LD_PRELOAD` здатні підмінити поведінку будь-якого динамічно скомпільованого бінарника без зміни його коду на диску:

- **`LD_LIBRARY_PATH`:** задає каталоги пошуку спільних бібліотек (`.so`), які перевіряються до системних шляхів (`/lib`, `/usr/lib`). Якщо сторонній скрипт встановив `LD_LIBRARY_PATH=/opt/custom/lib`, стандартні утиліти можуть підтягнути нестандартну версію `libc.so` чи `libssl.so`, що призведе до збоїв `undefined symbol`.
- **`LD_PRELOAD`:** примусово завантажує зазначену бібліотеку першою, перехоплюючи будь-які виклики функцій C (`malloc`, `open`, `connect`). Механізм часто використовується для профілювання або емуляції середовищ (fakeroot), але залишена змінна призводить до незбагненних відмінностей у роботі системних команд.

## Методологія локальної верифікації (Допит системи)

Щоб перевірити, яка саме сутність виконується під час введення команди, слід уникати застарілих та ненадійних утиліт.

### Чому не можна довіряти утиліті `which`

Утиліта `which` є зовнішнім бінарником або скриптом, який сканує виключно каталоги у змінній `$PATH`. Вона нічого не знає про поточний контекст процесу оболонки: вона не бачить завантажених у пам'ять аліасів, функцій і built-in команд. 

Історія появи та розпаду сумісності цієї утиліти детально описана у вставці [📜 Історія команди which та чому вона розсипається між системами](root:course/unix/when-docs-and-system-disagree/hist-which-broken-legacy.md).

### Інструменти встановлення істини: `type -a` та `command -v`

Найбільш надійним інструментом інспекції в середовищі Bash/Zsh є команда `type` із прапорцем `-a`:

```shell
type -a echo
```
Вивід:
```
echo is a shell builtin
echo is /usr/bin/echo
echo is /bin/echo
```

Команда показує повний перелік усіх сутностей із цим ім'ям у порядку їх пріоритету виконання.

Для використання у переносимих shell-скриптах стандартом POSIX затверджено утиліту `command -v`:

```shell
command -v grep
```
- Якщо `grep` є аліасом, виведеться `alias grep='grep --color=auto'`.
- Якщо функцією — виведеться назва `grep`.
- Якщо двійковим файлом — виведеться повний абсолютний шлях `/usr/bin/grep`.

Повний звід усіх діагностичних команд, їхніх опцій та кодів виходу наведено у вставці [📋 Довідник команд інспекції та верифікації середовища](root:course/unix/when-docs-and-system-disagree/api-verification-commands.md).

### Ідентифікація версії та збірки бінарника

Якщо встановлено, що команда запускає двійковий файл, необхідно визначити його точну версію:

1. **Опитування прапорців версії:**
   - Для утиліт GNU: `<cmd> --version`
   - Для утиліт BSD та класичного Unix: `<cmd> -V` або `<cmd> -v`
   - Для складних утиліт: `<cmd> version` або `<cmd> -version`

2. **Прямий аналіз рядків двійкового файлу:**
   Якщо бінарник не підтримує вивід версії або зібраний без інтерфейсу CLI, використовують утиліту `strings`:
   ```shell
   strings /usr/bin/custom-app | grep -iE 'version|build|release'
   ```

3. **Опитування бази даних пакетного менеджера:**
   Пакетний менеджер знає, який пакет встановив файл і чи не змінювався бінарник сторонніми процесами:

   - **Debian / Ubuntu:**
     ```shell
     # Визначення пакета:
     dpkg -S $(readlink -f $(command -v grep))
     # Перевірка цілісності контрольних сум встановленого пакета:
     dpkg -V grep
     ```
   - **RHEL / Fedora / CentOS:**
     ```shell
     rpm -qf $(readlink -f $(command -v grep))
     rpm -V grep
     ```
   - **Alpine Linux:**
     ```shell
     apk info -W $(readlink -f $(command -v grep))
     ```
   - **Arch Linux:**
     ```shell
     pacman -Qo $(readlink -f $(command -v grep))
     pacman -Qk grep
     ```

### Читання локального `man` саме цієї машини

Онлайн-документація на сторонніх веб-сайтах описує конфігурацію чужого сервера. Локально встановлений мануал гарантовано відповідає встановленій версії пакета:

```shell
# З'ясувати точне розташування файлу документації:
man -w grep
# Результат: /usr/share/man/man1/grep.1.gz
```

Якщо мануал містить декілька однойменних розділів (наприклад, системний виклик `read(2)` та команда оболонки `read(1)`), вказують номер розділу:

```shell
man 1 read   # Документація на команду користувача
man 2 read   # Документація на системний виклик ядра
man 3 printf # Бібліотечна функція мови C
man 5 crontab # Формат конфігураційного файлу
man 8 mount  # Команда системного адміністрування
```

## Трасування через `strace` як остаточна істина

Коли документація стверджує одне, конфігураційний файл виглядає абсолютно правильним, але програма все одно ігнорує налаштування або завершується з помилкою — єдиним об'єктивним свідком є системні виклики до ядра операційної системи.

Утиліта `strace` перехоплює виконання системних викликів процесу через інтерфейс ядра `ptrace(2)`:

![Перехоплення системних викликів утилітою strace](/root/course/unix/when-docs-and-system-disagree/img/strace-ground-truth-pipeline.svg)
*Перехоплення системних викликів утилітою strace: відстеження реальних шляхів відкриття файлів та виявлення збоїв конфігурації.*

### Практичний шаблон запуску `strace` для аудиту конфігурації

Щоб не перевантажувати журнал викликами роботи з пам'яттю (`mmap`, `brk`), вибирають лише виклики роботи з файловою системою та процесами:

```shell
strace -f -e trace=openat,access,stat,newfstatat,execve -s 512 -o trace.log <command>
```

Розберімо ключові прапорці:
- `-f`: відстежувати всі дочірні процеси та потоки (`fork()`, `clone()`).
- `-e trace=...`: фільтрувати системні виклики за іменами.
- `-s 512`: збільшити ліміт довжини відображення рядків аргументів (за замовчуванням обрізається до 32 байтів).
- `-o trace.log`: записувати вивід у файл.

---

### Три аварійні сценарії з практики системного інженера

#### Сценарій 1. Таємниця шляху конфігураційного файлу
**Симптом:** Ви редагуєте файл `/etc/app/config.json`, перезапускаєте службу `app`, але програма вперто використовує старі параметри або порт за замовчуванням. Документація стверджує, що головний конфіг лежить у `/etc/app/`.

**Діагностика через `strace`:**
```shell
strace -f -e trace=openat /usr/bin/app 2>&1 | grep config
```
Вивід у журналі:
```
openat(AT_FDCWD, "/root/.config/app/config.json", O_RDONLY) = 3
openat(AT_FDCWD, "/etc/app/config.json", O_RDONLY) = -1 ENOENT
```
**Розв'язання:** Трасування миттєво показує, що додаток спочатку перевіряє домашній каталог користувача. Якщо там знайдено файл конфігурації (дескриптор `3`), перевірка системного каталогу `/etc/` просто пропускається. Крім того, виявляється, що шлях до `/etc/app/config.json` повернув помилку `ENOENT` (файл відсутній), оскільки під час компіляції розробники зашили шлях `/usr/local/etc/app/config.json`.

---

#### Сценарій 2. Секретні права доступу та `access()`
**Симптом:** Програма запущена від непривілейованого користувача `www-data` і падає з повідомленням `Configuration file invalid`, не надаючи жодних деталей.

**Діагностика через `strace`:**
```shell
strace -f -e trace=openat,access,read /usr/bin/app 2>&1 | tail -n 20
```
Вивід у журналі:
```
access("/etc/ssl/certs/private.key", R_OK) = -1 EACCES (Permission denied)
write(2, "Configuration file invalid\n", 27) = 27
exit_group(1)                           = ?
```
**Розв'язання:** Програма перевіряє доступність SSL-ключа системним викликом `access(..., R_OK)`. Ядро повертає помилку `EACCES` (Permission denied). Розробники програми перехопили цю помилку всередині коду і замість зрозумілого опису вивели неправдиве повідомлення про некоректність конфігурації. Без `strace` інженер витратив би години на перевірку синтаксису JSON/YAML.

---

#### Сценарій 3. Конфлікт версій динамічних бібліотек
**Симптом:** Сервер падає при старті із загадковим повідомленням `symbol lookup error: /usr/lib/libcustom.so: undefined symbol: SSL_CTX_load_verify_dir`.

**Діагностика через `strace` та `ldd`:**
```shell
strace -f -e trace=openat /usr/bin/app 2>&1 | grep 'libssl'
```
Вивід у журналі:
```
openat(AT_FDCWD, "/opt/thirdparty/lib/libssl.so.1.1", O_RDONLY|O_CLOEXEC) = 3
```
**Розв'язання:** Замість системної бібліотеки `/usr/lib/x86_64-linux-gnu/libssl.so.3` динамічний лінкер підтягнув стару версію `libssl.so.1.1` із каталогу `/opt/thirdparty/lib/`, оскільки у системі було виставлено змінну `LD_LIBRARY_PATH=/opt/thirdparty/lib`. Трасування показало точний файл бібліотеки, який спричинив несумісність двійкових символів ABI.

## Програмна діагностика середовища на C та C++

Для автоматизації перевірки реального оточення та шляхів розв'язання файлів системні інструменти реалізують процедуру повного аудиту:
1. Перевірка локалі та кодування.
2. Розгортання символьних посилань до фізичного двійкового файлу через `realpath`.
3. Пошук файлу за змінною `$PATH` із перевіркою прав доступу на виконання через `access(..., X_OK)`.
4. Безпечний парсинг заголовка ELF без запуску стороннього процесу.

Нижче наведено робочий приклад діагностичної програми двома мовами: на чистому POSIX C та ідіоматичному сучасному C++20.

:::tabs
```c
/* Діагностичний аудит середовища та розв'язання команд на POSIX C */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <limits.h>
#include <sys/stat.h>
#include <locale.h>

void inspect_locale(void)
{
    const char *loc = setlocale(LC_ALL, "");
    printf("[1] Системна локаль: %s\n", loc ? loc : "не визначено");
    const char *collate = getenv("LC_COLLATE");
    printf("    LC_COLLATE: %s\n", collate ? collate : "(за замовчуванням)");
}

void resolve_command(const char *cmd_name)
{
    printf("[2] Дослідження команди: %s\n", cmd_name);
    
    /* Якщо вказано прямий шлях */
    if (strchr(cmd_name, '/')) {
        char resolved[PATH_MAX];
        if (realpath(cmd_name, resolved)) {
            printf("    Прямий шлях знайдено: %s\n", resolved);
        } else {
            perror("    Помилка realpath");
        }
        return;
    }

    const char *path_env = getenv("PATH");
    if (!path_env) {
        fprintf(stderr, "    Змінна PATH відсутня!\n");
        return;
    }

    char *path_copy = strdup(path_env);
    if (!path_copy) {
        perror("strdup");
        return;
    }

    char *dir = strtok(path_copy, ":");
    int found_count = 0;

    while (dir != NULL) {
        char full_path[PATH_MAX];
        snprintf(full_path, sizeof(full_path), "%s/%s", dir, cmd_name);

        if (access(full_path, X_OK) == 0) {
            char real_bin[PATH_MAX];
            if (realpath(full_path, real_bin)) {
                printf("    Знайдено у PATH [%d]: %s -> %s\n", ++found_count, full_path, real_bin);
            } else {
                printf("    Знайдено у PATH [%d]: %s\n", ++found_count, full_path);
            }
        }
        dir = strtok(NULL, ":");
    }

    if (found_count == 0) {
        printf("    Команду '%s' не знайдено у жодному каталозі PATH.\n", cmd_name);
    }

    free(path_copy);
}

int main(int argc, char *argv[])
{
    const char *target = (argc > 1) ? argv[1] : "grep";
    printf("=== Системний аудит середовища виконання ===\n");
    inspect_locale();
    resolve_command(target);
    return 0;
}
```
```cpp
// Ідіоматична реалізація аудиту середовища на C++20
#include <iostream>
#include <string>
#include <string_view>
#include <vector>
#include <filesystem>
#include <cstdlib>
#include <clocale>
#include <ranges>

namespace fs = std::filesystem;

void inspect_locale()
{
    const char* loc = std::setlocale(LC_ALL, "");
    std::cout << "[1] Системна локаль: " << (loc ? loc : "не визначено") << '\n';
    const char* collate = std::getenv("LC_COLLATE");
    std::cout << "    LC_COLLATE: " << (collate ? collate : "(за замовчуванням)") << '\n';
}

void resolve_command(std::string_view cmd_name)
{
    std::cout << "[2] Дослідження команди: " << cmd_name << '\n';

    // Якщо передано прямий шлях
    if (cmd_name.find('/') != std::string_view::npos) {
        std::error_code ec;
        fs::path p(cmd_name);
        fs::path canonical_path = fs::canonical(p, ec);
        if (!ec) {
            std::cout << "    Прямий шлях знайдено: " << canonical_path.string() << '\n';
        } else {
            std::cout << "    Шлях недоступний: " << ec.message() << '\n';
        }
        return;
    }

    const char* path_env = std::getenv("PATH");
    if (!path_env) {
        std::cerr << "    Змінна PATH відсутня в середовищі!\n";
        return;
    }

    std::string_view path_view(path_env);
    int found_count = 0;

    // Розбір PATH через ranges string_view (C++20)
    for (const auto dir_range : std::views::split(path_view, ':')) {
        std::string dir_str(dir_range.begin(), dir_range.end());
        if (dir_str.empty()) continue;

        fs::path candidate = fs::path(dir_str) / cmd_name;
        std::error_code ec;

        // Перевірка існування та прав на виконання
        auto status = fs::status(candidate, ec);
        if (!ec && fs::exists(status) && !fs::is_directory(status)) {
            auto perms = status.permissions();
            bool is_executable = (perms & (fs::perms::owner_exec | fs::perms::group_exec | fs::perms::others_exec)) != fs::perms::none;
            
            if (is_executable) {
                fs::path canonical_target = fs::canonical(candidate, ec);
                std::cout << "    Знайдено у PATH [" << ++found_count << "]: " 
                          << candidate.string() << " -> " 
                          << (ec ? candidate.string() : canonical_target.string()) << '\n';
            }
        }
    }

    if (found_count == 0) {
        std::cout << "    Команду '" << cmd_name << "' не знайдено у каталогах PATH.\n";
    }
}

int main(int argc, char* argv[])
{
    std::string_view target = (argc > 1) ? argv[1] : "grep";
    std::cout << "=== Системний аудит середовища виконання (C++20) ===\n";
    inspect_locale();
    resolve_command(target);
    return 0;
}
```

## Чотирикроковий протокол перевірки істини

Якщо поведінка утиліти на незнайомій машині суперечить очікуванням або інструкціям, застосовуйте стандартний інженерний алгоритм:

```
[Крок 1: Що це?]         type -a <cmd>
                         → Аліас? Функція? Builtin? Шлях у $PATH?
                              │
[Крок 2: Хто зібрав?]     <cmd> --version || <cmd> -V
                         dpkg -S $(readlink -f $(command -v <cmd>))
                         → GNU чи BSD? Яка мажорна версія?
                              │
[Крок 3: Що каже man?]    man -w <cmd>
                         man 1 <cmd>
                         → Читання документації саме цієї системи
                              │
[Крок 4: Що робить ядро?] strace -f -e trace=file,process <cmd>
                         → Які файли насправді відкриваються і чому виникає помилка?
```

1. **Крок 1: Ідентифікуйте тип команди в оболонці.**
   Виконайте `type -a <cmd>`. Переконайтеся, що виклик не перехоплений аліасом (`alias`) або локальною функцією з `~/.bashrc`. За потреби викличте команду через бекслеш `\<cmd>` або `command <cmd>`.
2. **Крок 2: Визначте походження та версію бінарника.**
   Виконайте `<cmd> --version` або `<cmd> -V`. З'ясуйте власника бінарника через пакетний менеджер (`dpkg -S`, `rpm -qf`, `apk info -W`). Перевірте, чи не модифіковано файл (`dpkg -V`, `rpm -V`).
3. **Крок 3: Зверніться до локальної сторінки керівництва.**
   Знайдіть локальний файл мануалу через `man -w <cmd>` і прочитайте секцію `SYNOPSIS` для вашої версії програми замість пошуку в Google.
4. **Крок 4: Увімкніть системне трасування.**
   Якщо налаштування ігноруються, запустіть програму під `strace -f -e trace=openat,access,stat <cmd>`. Журнал системних викликів ядра безпомилково покаже кожен прочитаний файл конфігурації, відсутні права доступу та справжню причину помилки.
