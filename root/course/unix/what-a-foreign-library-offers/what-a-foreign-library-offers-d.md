Розробник створює мережевий сервіс збору телеметрії і додає швидкісне стиснення пакетів за допомогою сторонньої бібліотеки `libzstd`. У системі вже встановлено пакунок середовища виконання `libzstd1`, і файл спільного об'єкта `/usr/lib/x86_64-linux-gnu/libzstd.so.1` фізично присутній на диску. Проте перша ж спроба скомпілювати тестову програму командою `gcc -O2 main.c -lzstd` зазнає аварії: препроцесор видає помилку `fatal error: zstd.h: No such file or directory`. Встановивши пакет для розробників `libzstd-dev`, розробник отримує заголовні файли, але стикається з наступним пластом питань: які саме функції експортує встановлена версія, які структури даних вимагає API, чи потрібні додаткові прапорці компілятора на кшталт `-pthread`, як бібліотека повідомляє про помилки, і що робити, якщо онлайн-документація описує версію 1.5.5, а на цільовому сервері встановлено 1.4.4?

У середовищі Unix бібліотека ніколи не постачається як монолітний «чорний ящик» із вбудованою рефлексією типів, як це прийнято в керованих середовищах Java (JAR-архіви) чи .NET (збірки з метаданими CLI). Двійковий формат ELF (від англ. *Executable and Linkable Format*) зберігає виключно скомпільовані машинні інструкції та плоскі таблиці адрес і імен символів. Інформація про типи аргументів, розміри структур, зміщення полів у пам'яті та семантику викликів повністю винесена за межі двійкового файлу.

Через це інтерфейс чужої бібліотеки в Unix існує одночасно у чотирьох взаємодоповнюючих площинах:
1. **Текстові заголовні файли (`.h` / `.hpp`):** синтаксичний контракт для компілятора (типи, розмітка структур, константи, прототипи);
2. **Декларативні метадані збірки (`pkg-config` / `.pc`):** системний контракт для систем збірки (шляхи до заголовків, бібліотечні прапорці, транзитивні залежності);
3. **Двійкові спільні об'єкти (`.so` / `.a`):** машинний контракт для лінкера та завантажувача (таблиці динамічних символів `.dynsym`, релокації, інструкції коду);
4. **Системна документація (`man 3`):** семантичний контракт для інженера (володіння пам'яттю, потокобезпечність, коди помилок `errno`).

## 1. Подвійна природа бібліотеки: контракт компіляції проти контракту лінкування

Щоб зрозуміти, чому робота з чужою бібліотекою вимагає кількох різних інструментів, необхідно простежити поділ обов'язків між чотирма фазами обробки коду: препроцесором, транслятором у машинний код (`gcc` / `clang`), статичним компонувачем (`ld`) та динамічним завантажувачем ядра (`ld.so`).

Під час трансляції файлу вихідного коду `app.c` у двійковий об'єктний файл `app.o` компілятор не має доступу до скомпільованого коду бібліотеки `libzstd.so`. Компілятору не потрібні машинне тіло функцій чи реальні адреси в пам'яті. Його завдання — побудувати абстрактне синтаксичне дерево (AST), перевірити типи аргументів, обчислити розміри структур для виділення місця на стеку та згенерувати інструкції виклику функцій згідно з угодою про виклики цільової архітектури (System V AMD64 ABI). Усю цю інформацію компілятор бере виключно з текстових заголовних файлів (`.h`).

Коли компілятор зустрічає виклик сторонньої функції `ZSTD_compressCCtx()`, він перевіряє, чи відповідають типи переданих аргументів оголошеному прототипу. Якщо типи коректні, компілятор генерує інструкцію виклику (наприклад, `call 0x0` на архітектурі x86-64) і створює запис у секції релокацій об'єктного файлу `.rela.text` із типом `R_X86_64_PLT32`. В об'єктному файлі `app.o` створюється запис у таблиці символів: символ `ZSTD_compressCCtx` позначається як невизначений (`U`, *Undefined*).

```
       [app.c] ─── (потребує типів і сигнатур) ───> [/usr/include/zstd.h]
          │
      Компілятор (gcc -c)
          │
          ▼
       [app.o] (містить невизначений символ "U ZSTD_compressCCtx")
          │
          ├─────────────────────────────────────────┐
          │                                         │
          ▼                                         ▼
      Компонувальник (ld) <─── (потребує коду) ───> [/usr/lib/libzstd.so]
          │                                        (містить символ "T ZSTD_compressCCtx")
          ▼
    [Виконуваний ELF]
          │
    Динамічний завантажувач (ld.so під час запуску)
          │
          ▼
    Завантаження libzstd.so.1 у пам'ять процесу та виклик коду
```

На наступному етапі статичний компонувальник `ld` збирає докупи всі об'єктні файли програми та зазначені бібліотеки. Заголовні файли `.h` компонувальнику більше не потрібні — він навіть не перевіряє типи аргументів і нічого не знає про мову програмування. Завдання `ld` — переконатися, що кожен невизначений символ `U` з `app.o` має відповідний експортований символ типу `T` (*Text*) у двійковому файлі бібліотеки `libzstd.so`.

Якщо компонування здійснюється динамічно, `ld` не копіює машинний код функції `ZSTD_compressCCtx` у виконуваний файл. Замість цього він записує ім'я потрібної бібліотеки (тег `DT_NEEDED: libzstd.so.1`) у динамічну секцію `.dynamic` результуючого ELF-файлу та формує таблиці непрямих переходів PLT (Procedure Linkage Table) і GOT (Global Offset Table).

Під час запуску програми ядро передає керування динамічному завантажувачу `ld.so`. Завантажувач сканує теги `DT_NEEDED`, знаходить `libzstd.so.1` на диску, відображає її сегменти коду в оперативну пам'ять процесу за допомогою системного виклику `mmap()` із прапорцями `PROT_READ | PROT_EXEC` для секцій коду та `PROT_READ | PROT_WRITE` для секцій даних, після чого заповнює адреси функцій у таблиці GOT.

### Розкол системних пакунків: Runtime проти Development

Саме цей розподіл обов'язків між етапом трансляції та етапом виконання породив стандартний поділ пакунків в операційних системах Linux (Debian/Ubuntu, RHEL/Rocky, Arch, Alpine):

* **Пакунок виконання (Runtime package, наприклад `libzstd1` або `zstd-libs`):** містить виключно спільний двійковий об'єкт із версійним суфіксом (`/usr/lib/x86_64-linux-gnu/libzstd.so.1.5.5`) та символічне посилання SONAME (`libzstd.so.1 -> libzstd.so.1.5.5`). Цього набору достатньо для виконання вже скомпільованих бінарників, але неможливо зібрати жодну нову програму.
* **Пакунок розробника (Development package, наприклад `libzstd-dev` або `libzstd-devel`):** містить текстові C/C++ заголовні файли (`/usr/include/zstd.h`, `/usr/include/zstd_errors.h`), файли метаданих систем збірки (`/usr/lib/pkgconfig/libzstd.pc`), системну документацію (`/usr/share/man/man3/`), статичні архіви (`/usr/lib/libzstd.a`) та спеціальне неверсійне символічне посилання для лінкера (`libzstd.so -> libzstd.so.1`).

Якщо на машині встановлено лише runtime-пакет, лінкер `ld` при спробі виконати `-lzstd` шукає файл `libzstd.so`. Оскільки посилання без номера версії належить dev-пакету, лінкер зупиняється з помилкою `/usr/bin/ld: cannot find -lzstd: No such file or directory`. І навпаки: наявність лише заголовків без двійкового файлу `.so` дозволяє успішно скомпілювати `main.o`, але завершується помилкою компонувальника `undefined reference to 'ZSTD_compressCCtx'`.

## 2. Читання контрактів у заголовках `/usr/include/`

Заголовні файли сторонніх бібліотек за стандартом FHS (Filesystem Hierarchy Standard) встановлюються у системні каталоги `/usr/include/`, `/usr/local/include/` або в архітектурно-специфічні шляхи `/usr/include/x86_64-linux-gnu/` (в архітектурі multiarch).

Заголовок C/C++ — це не просто список оголошень функцій, а формальний контракт сумісності. Промисловий заголовний файл завжди містить п'ять обов'язкових структурних елементів:

### 1. Захист від повторного включення (Include Guards)

Щоб уникнути помилок переозначення типів та макросів при багаторазовому включенні одного й того самого заголовка через складні ланцюжки залежностей, файл захищається директивами препроцесора або компіляторними прагмами:

:::tabs
```c
#ifndef ZSTD_H_23541813
#define ZSTD_H_23541813

/* Тіло заголовного файлу C API */
size_t ZSTD_versionNumber(void);

#endif /* ZSTD_H_23541813 */
```
```cpp
#pragma once

// Сучасний C++ заголовок використовує #pragma once
// або модульні декларації для запобігання дублюванню
namespace compression::zstd {
    unsigned int version_number() noexcept;
}
```
:::

Директива `#pragma once` підтримується всіма основними сучасними компіляторами (GCC, Clang, MSVC) і працює швидше за класичні include guards, оскільки компілятор запам'ятовує ідентифікатор inode файлу на диску і навіть не відкриває його повторно під час трансляції однієї одиниці компіляції.

### 2. Блок зв'язування `extern "C"`

Мова C++ підтримує перевантаження функцій (*function overloading*). Щоб розрізняти функції з однаковими іменами, але різними параметрами, C++ компілятор модифікує імена символів у машинному коді (спотворення імен, або *name mangling*), перетворюючи функцію `compress(const char*, int)` на спаплюжене ім'я `_Z8compressPKci`. Мова C не підтримує перевантаження і зберігає ім'я символу як є: `compress`.

Якщо C++ програма підключає заголовок C-бібліотеки без спеціального блоку, компілятор шукатиме спаплюжене ім'я `_Z8compressPKci` і лінкер видасть `undefined reference`. Щоб бібліотеку можна було прозоро викликати і з C, і з C++, заголовки містять блок:

:::tabs
```c
#if defined (__cplusplus)
extern "C" {
#endif

/* Оголошення функцій C API без викривлення імен */
size_t ZSTD_compress(void* dst, size_t dstCapacity, const void* src, size_t srcSize, int compressionLevel);

#if defined (__cplusplus)
}
#endif
```
```cpp
// У C++ обгортці функції групуються у простори імен,
// захищаючи глобальну область видимості від конфліктів
namespace compression::zstd {
    extern "C" {
        size_t ZSTD_compress(void* dst, size_t dstCapacity, const void* src, size_t srcSize, int compressionLevel);
    }
}
```
:::

Блок `extern "C"` наказує C++ компілятору вимкнути механізм name mangling для всіх функцій усередині блоку і генерувати звичайні неспотворені імена символів за угодою C ABI.

### 3. Непрозорі покажчики (Opaque Pointers / Handles) проти відкритих структур

Те, як бібліотека оголошує свої типи даних, визначає стабільність її двійкового інтерфейсу (ABI):

* **Відкрита структура (Transparent Struct):** оголошує всі внутрішні поля (`struct Point { int x; int y; };`). Компілятор знає точний розмір структури (8 байтів) і може виділяти її на стеку (`struct Point p;`). Проте якщо автори бібліотеки додадуть поле `int z;`, розмір зміниться на 12 байтів. Усі раніше скомпільовані програми, які виділяли 8 байтів на стеку, при виклику нової бібліотеки отримають пошкодження пам'яті (*stack buffer overflow*).
* **Непрозорий покажчик (Opaque Pointer / Handle):** приховує внутрішні поля за неповним типом (*incomplete type*). Клієнтський код не знає внутрішнього розміру структури і працює з нею виключно через покажчик та виділені функції життєвого циклу:

:::tabs
```c
/* C API: Непрозорий вказівник на контекст та функції життєвого циклу */
typedef struct ZSTD_CCtx_s ZSTD_CCtx;

ZSTD_CCtx* ZSTD_createCCtx(void);
size_t ZSTD_freeCCtx(ZSTD_CCtx* cctx);
```
```cpp
// C++ API: Інкапсуляція у клас із патерном Pimpl та розумним покажчиком
#include <memory>

namespace compression {
    class CompressionContext {
    public:
        CompressionContext();
        ~CompressionContext();
        CompressionContext(CompressionContext&&) noexcept;
        CompressionContext& operator=(CompressionContext&&) noexcept;
    private:
        struct Impl;
        std::unique_ptr<Impl> impl_;
    };
}
```
:::

Непрозорі покажчики є фундаментальною інженерною практикою проектування системних бібліотек. Вони дозволяють змінювати, розширювати та перевпорядковувати поля внутрішньої структури без перекомпіляції клієнтських програм і без порушення розміщення даних у пам'яті.

### 4. Константи, переліки та макроси версіонування

Заголовні файли містять макроси, які дозволяють перевірити версію API ще під час препроцесингу:

:::tabs
```c
#define ZSTD_VERSION_MAJOR    1
#define ZSTD_VERSION_MINOR    5
#define ZSTD_VERSION_RELEASE  5
#define ZSTD_VERSION_NUMBER  (ZSTD_VERSION_MAJOR * 10000 + ZSTD_VERSION_MINOR * 100 + ZSTD_VERSION_RELEASE)

#if ZSTD_VERSION_NUMBER >= 10400
    /* Використовуємо нове швидке API контекстів */
#endif
```
```cpp
// У сучасному C++20 версійні константи визначаються як constexpr
namespace compression::version {
    inline constexpr unsigned int major = 1;
    inline constexpr unsigned int minor = 5;
    inline constexpr unsigned int patch = 5;
    inline constexpr unsigned int number = major * 10000 + minor * 100 + patch;
}
```
:::

### 5. Атрибути компілятора та діагностика

Сучасні заголовки активно використовують атрибути компілятора GNU/Clang (`__attribute__`), які керують експортом та перевіркою коректності викликів:

* `__attribute__((visibility("default")))` — позначає символ як публічний експорт спільної бібліотеки (якщо компіляція ведеться з прапорцем `-fvisibility=hidden`);
* `__attribute__((warn_unused_result))` — змушує компілятор генерувати попередження, якщо викликач ігнорує код повернення функції (критично для функцій перевірки помилок);
* `__attribute__((deprecated("Use ZSTD_compressStream2 instead")))` — попереджає про застарілі функції, заплановані до видалення;
* `__attribute__((nonnull(1, 3)))` — підказує компілятору, що перший та третій аргументи не повинні бути нульовими покажчиками (`NULL`), що дозволяє статичному аналізатору ловити потенційні розіменування нульових покажчиків ще під час компіляції.

Нижче наведено практичний приклад роботи з контекстом компресії бібліотеки: ліворуч — класичний підхід мовою C із ручним керуванням пам'яттю, праворуч — ідіоматичний C++20 із застосуванням ідіоми RAII та розумних покажчиків:

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <zstd.h>

int compress_payload(const void* src, size_t src_size, void** out_buf, size_t* out_size) {
    /* Створення непрозорого контексту бібліотеки */
    ZSTD_CCtx* cctx = ZSTD_createCCtx();
    if (!cctx) {
        fprintf(stderr, "Помилка виділення контексту ZSTD\n");
        return -1;
    }

    /* Оцінка максимального розміру буфера стиснення */
    size_t const max_dst_size = ZSTD_compressBound(src_size);
    void* const dst = malloc(max_dst_size);
    if (!dst) {
        ZSTD_freeCCtx(cctx);
        return -1;
    }

    /* Виконання стиснення з рівнем 3 */
    size_t const compressed_size = ZSTD_compressCCtx(cctx, dst, max_dst_size, src, src_size, 3);
    
    /* Перевірка коду повернення на наявність помилки */
    if (ZSTD_isError(compressed_size)) {
        fprintf(stderr, "Помилка стиснення: %s\n", ZSTD_getErrorName(compressed_size));
        free(dst);
        ZSTD_freeCCtx(cctx);
        return -1;
    }

    /* Звільнення ресурсів бібліотеки */
    ZSTD_freeCCtx(cctx);

    *out_buf = dst;
    *out_size = compressed_size;
    return 0;
}
```
```cpp
#include <iostream>
#include <vector>
#include <span>
#include <memory>
#include <expected>
#include <string_view>
#include <zstd.h>

struct ZstdContextDeleter {
    void operator()(ZSTD_CCtx* ctx) const noexcept {
        if (ctx) {
            ZSTD_freeCCtx(ctx);
        }
    }
};

using ScopedZstdCCtx = std::unique_ptr<ZSTD_CCtx, ZstdContextDeleter>;

std::expected<std::vector<uint8_t>, std::string_view> 
compress_payload(std::span<const uint8_t> input_data, int compression_level = 3) {
    // Безпечне керування контекстом через RAII
    ScopedZstdCCtx cctx(ZSTD_createCCtx());
    if (!cctx) {
        return std::unexpected("Не вдалося створити контекст ZSTD");
    }

    size_t const max_dst_size = ZSTD_compressBound(input_data.size());
    std::vector<uint8_t> output_buffer(max_dst_size);

    size_t const compressed_size = ZSTD_compressCCtx(
        cctx.get(),
        output_buffer.data(),
        output_buffer.size(),
        input_data.data(),
        input_data.size(),
        compression_level
    );

    if (ZSTD_isError(compressed_size)) {
        return std::unexpected(ZSTD_getErrorName(compressed_size));
    }

    output_buffer.resize(compressed_size);
    return output_buffer;
}
```

## 3. Автоматизація збірки та пошук залежностей: `pkg-config`

У міру зростання кількості бібліотек у системі виникає проблема узгодження прапорців компіляції (`CFLAGS`) та компонування (`LDFLAGS`). 

Якщо програма використовує три сторонні бібліотеки (наприклад, `libpng`, `libzstd` та `libcrypto`), розробник змушений вручну з'ясовувати:
* У яких саме каталогах лежать їхні заголовки (наприклад, `-I/usr/include/libpng16`);
* Які супутні бібліотеки потрібно передати лінкеру (`-lpng16 -lz -lm -lzstd -lcrypto -pthread -ldl`);
* У якому порядку їх передавати, щоб задовольнити лінкер.

У ранніх версіях Unix кожна бібліотека постачала власний shell-скрипт (наприклад, `libpng-config`, `curl-config`, `sdl-config`). Це породжувало хаос у системах збірки через різні прапорці та несумісні формати виводу.

Для розв'язання цієї проблеми в екосистемі Unix створено єдиний уніфікований механізм `pkg-config`. Кожна бібліотека постачає декларативний файл метаданих із розширенням `.pc`, який встановлюється у стандартний каталог `/usr/lib/pkgconfig/`, `/usr/share/pkgconfig/` або `/usr/lib/x86_64-linux-gnu/pkgconfig/`.

### Анатомія файлу `.pc`

Розглянемо типовий файл опису бібліотеки `libzstd.pc`:

```ini
prefix=/usr
exec_prefix=${prefix}
libdir=${prefix}/lib/x86_64-linux-gnu
includedir=${prefix}/include

Name: zstd
Description: fast lossless compression library
URL: https://facebook.github.io/zstd/
Version: 1.5.5
Libs: -L${libdir} -lzstd
Libs.private: -pthread
Cflags: -I${includedir}
```

Утиліта `pkg-config` читає цей файл і виконує рекурсивну підстановку змінних. Коли користувач або скрипт збірки запитує прапорці:

```sh
$ pkg-config --cflags zstd
-I/usr/include

$ pkg-config --libs zstd
-lzstd
```

### Динамічне проти статичного компонування: `Libs` проти `Libs.private`

Критично важливою можливості `pkg-config` є розділення прямих та транзитивних залежностей через поля `Libs.private` та `Requires.private`:

1. **Динамічна збірка (`pkg-config --libs zstd`):** повертає лише `-lzstd`. Динамічний лінкер `ld.so` під час запуску самостійно зчитає записи `DT_NEEDED` всередині `libzstd.so` і завантажить системну бібліотеку потоків `libpthread.so`. Головній програмі прапорець `-pthread` для лінкування не потрібен.
2. **Статична збірка (`pkg-config --libs --static zstd`):** статичний архів `libzstd.a` є звичайним набором об'єктних файлів і не містить динамічних заголовків `DT_NEEDED`. Лінкер зобов'язаний отримати повний граф залежностей. Прапорець `--static` змушує `pkg-config` розгорнути приватні прапорці:

```sh
$ pkg-config --libs --static zstd
-lzstd -pthread
```

Детальний опис усіх директив, розгортання змінних та роботи з ізольованими sysroot-середовищами наведено у довіднику [специфікація формату .pc та довідник змінних pkg-config](root:course/unix/what-a-foreign-library-offers/api-pkgconfig-pc-format.md).

### Керування пошуком через змінні оточення

* `PKG_CONFIG_PATH` — перелік додаткових каталогів (через двокрапку), де утиліта шукає `.pc` файли перед системними каталогами:
  ```sh
  export PKG_CONFIG_PATH="/opt/custom-libs/lib/pkgconfig:$PKG_CONFIG_PATH"
  ```
* `PKG_CONFIG_LIBDIR` — повністю замінює стандартні шляхи пошуку (використовується при крос-компіляції під іншу архітектуру);
* `PKG_CONFIG_SYSROOT_DIR` — додає шлях до цільового кореня файлової системи при крос-компіляції.

## 4. Інспекція двійкового експорту: `nm -D` та `readelf -s`

Що робити, якщо заголовні файли наявні, але під час лінкування виникає помилка `undefined reference to 'ZSTD_custom_function'`, або коли ви отримали пропрієтарний бінарний файл `.so` без документації?

Для інспекції двійкового вмісту бібліотек в Unix використовується утиліта `nm` (від англ. *names*) та низькорівневий парсер ELF `readelf`.

### Таблиця налагоджувальних символів (`.symtab`) проти динамічних символів (`.dynsym`)

У двійковому файлі ELF існують дві принципово різні таблиці символів:

1. **`.symtab` (Symbol Table):** повна таблиця всіх функцій і змінних, створена під час компіляції. Вона містить як глобальні, так і локальні статичні допоміжні функції. У релізних дистрибутивах цю секцію видаляють утилітою `strip` для зменшення розміру бінарника. Якщо запустити звичайний `nm /usr/lib/x86_64-linux-gnu/libzstd.so.1`, утиліта повідомить: `nm: libzstd.so.1: no symbols`.
2. **`.dynsym` (Dynamic Symbol Table):** спеціальна таблиця експортованих та імпортованих символів, необхідна динамічному завантажувачу `ld.so` під час роботи програми. Цю таблицю **неможливо видалити** утилітою `strip`, оскільки без неї операційна система не зможе зв'язати виклики функцій у пам'яті.

Щоб змусити `nm` зчитувати саме динамічну таблицю `.dynsym`, використовується прапорець `-D` (або `--dynamic`):

```sh
$ nm -D /usr/lib/x86_64-linux-gnu/libzstd.so.1 | grep ZSTD_compress
000000000001a4e0 T ZSTD_compress
000000000001a520 T ZSTD_compressBound
000000000001a610 T ZSTD_compressCCtx
```

![Анатомія запису таблиці динамічних символів nm -D](/root/course/unix/what-a-foreign-library-offers/img/fig-nm-symbol-anatomy.svg)
*Анатомія запису таблиці динамічних символів nm -D, класифікація літер типів та деманглінг C++.*

### Розшифровка літер типів символів у виводі `nm`

Утиліта `nm` виводить три колонки: віртуальну адресу (зміщення відносно початку секції), однолітерний код типу символу та ім'я символу. 

Регістр літери має вирішальне значення: **велика літера** означає глобальний (експортований назовні) символ; **мала літера** означає локальний внутрішній символ.

| Код | Секція ELF | Призначення та семантика | Приклад |
|---|---|---|---|
| **`T`** | `.text` | **Публічний машинний код:** експортована функція, доступна для виклику іншими програмами. | `0001a4e0 T ZSTD_compress` |
| **`t`** | `.text` | **Локальний код:** функція, оголошена як `static` або обмежена видимістю `hidden`. | `00021b40 t frame_header_unpack` |
| **`U`** | — | **Undefined (Імпорт):** символ, який бібліотека викликає, але сама не містить (очікує знайти в libc або іншій `.so`). | `U malloc@@GLIBC_2.2.5` |
| **`D`** | `.data` | **Ініціалізовані глобальні дані:** глобальні змінні, що мають ненульове значення за замовчуванням. | `0003c010 D ZSTD_default_params` |
| **`B`** | `.bss` | **Неініціалізовані дані:** глобальні змінні, які ядро обнуляє під час завантаження в RAM. | `0003d200 B global_error_counter` |
| **`R`** | `.rodata` | **Дані тільки для читання:** строкові літерали, таблиці підстановки, константи `const`. | `0002f100 R ZSTD_version_string` |
| **`W`** | `.text`/`.data` | **Слабкий символ (Weak Symbol):** функція за замовчуванням, яку користувацька програма може перевизначити. | `00014020 W pthread_mutex_lock` |

### Деманглінг C++ імен (`nm -C -D` та `c++filt`)

Якщо спільну бібліотеку скомпільовано з коду C++, прямий вивід `nm -D` міститиме незрозумілі ідентифікатори:

```sh
$ nm -D libengine.so | grep draw
0000000000045a10 T _ZN6Engine8Renderer11draw_spriteERK7Textureii
```

Специфікація Itanium C++ ABI кодує у цьому рядку повний шлях просторів імен та типи аргументів:
* `_Z` — префікс mangled-символу C++;
* `N` — початок ланцюжка вкладених просторів імен та класів;
* `6Engine` — 6 символів назви namespace `Engine`;
* `8Renderer` — 8 символів назви класу `Renderer`;
* `11draw_sprite` — 11 символів назви методу `draw_sprite`;
* `E` — завершення вкладеного простору імен;
* `RK7Texture` — перший аргумент: константна посилання `const Texture&`;
* `ii` — другий та третій аргументи: `int`, `int`.

Щоб перетворити службове ім'я компілятора на зрозумілу сигнатуру C++, додайте прапорець `-C` (demangle) або передайте рядок у фільтр `c++filt`:

```sh
$ nm -C -D libengine.so | grep draw
0000000000045a10 T Engine::Renderer::draw_sprite(Texture const&, int, int)

# Або окремо через утиліту c++filt:
$ c++filt _ZN6Engine8Renderer11draw_spriteERK7Textureii
Engine::Renderer::draw_sprite(Texture const&, int, int)
```

### Перевірка версіонування символів та SONAME через `readelf`

Утиліта `readelf -s --dyn-syms` надає найбільш вичерпний низькорівневий звіт про символи ELF, включно з мітками версій символів:

```sh
$ readelf -s --dyn-syms /usr/lib/x86_64-linux-gnu/libzstd.so.1 | grep ZSTD_compressCCtx
   142: 000000000001a610   284 FUNC    GLOBAL DEFAULT   12 ZSTD_compressCCtx@@ZSTD_1.4.0
```

Позначка `@@ZSTD_1.4.0` вказує на версію двійкового інтерфейсу. Якщо програму скомпільовано проти версії `ZSTD_1.4.0`, динамічний завантажувач перевірить наявність саме цієї версійної мітки у таблиці `.gnu.version_d`.

А логічне ім'я бібліотеки, яке зашивається у всі залежні програми під час збірки, перевіряється в секції `.dynamic`:

```sh
$ readelf -d /usr/lib/x86_64-linux-gnu/libzstd.so.1 | grep SONAME
 0x000000000000000e (SONAME)             Library soname: [libzstd.so.1]
```

Практичну реалізацію автоматизованого аналізу таблиць символів між різними версіями бібліотек викладено у практичній роботі [аудит двійкових символів бібліотеки та перевірка сумісності ABI](root:course/unix/what-a-foreign-library-offers/proj-symbol-table-audit.md).

## 5. Системна документація через man-сторінки секції 3 (`man 3`)

Онлайн-документація на веб-сайтах часто описує останню актуальну версію бібліотеки (наприклад, 1.5.5), тоді як у промислових серверах із дистрибутивами довготривалої підтримки (Debian Stable чи RHEL) встановлено стабільну версію кількорічної давнини (наприклад, 1.4.4). Довіра до сторонніх інтернет-джерел у такому випадку призводить до помилок використання неіснуючих прапорців або змінених сигнатур.

Єдиним джерелом істини для конкретної встановленої версії є системні сторінки довідки (*man-pages*).

### Структура секцій системного довідника man

Довідкова система Unix поділена на стандартні числові секції:

* **Секція 1:** виконувані програми командного рядка (`man 1 ls`, `man 1 gcc`, `man 1 nm`);
* **Секція 2:** системні виклики ядра Linux (`man 2 open`, `man 2 mmap`, `man 2 fork`);
* **Секція 3:** **бібліотечні функції C/POSIX/glibc** (`man 3 fopen`, `man 3 zstd`, `man 3 pthread_create`, `man 3 dlopen`);
* **Секція 4:** спеціальні файли пристроїв (`man 4 null`, `man 4 random`);
* **Секція 5:** формати конфігураційних файлів (`man 5 passwd`, `man 5 elf`).

Якщо ім'я утиліти збігається з ім'ям бібліотечної функції (наприклад, `printf` або `sleep`), виклик `man printf` відкриє утиліту оболонки із секції 1. Щоб відкрити документацію C API, обов'язково вказуйте секцію явно:

```sh
$ man 3 printf
$ man 3 zstd
```

### Пошук функцій за ключовими словами

Якщо точне ім'я функції невідоме, використовується пошук по базі даних коротких описів (*whatis database*):

```sh
# Пошук усіх функцій, пов'язаних зі стисненням zstd у секції 3:
$ man -k -s 3 zstd
# Або еквівалентна утиліта apropos:
$ apropos -s 3 compression
```

### Анатомія сторінки `man 3`: що шукати інженеру

Кожна стандартна сторінка секції 3 побудована за суворо регламентованою структурою:

```
NAME
       zstd - zstandard fast lossless compression library

SYNOPSIS
       #include <zstd.h>

       size_t ZSTD_compress( void* dst, size_t dstCapacity,
                             const void* src, size_t srcSize,
                             int compressionLevel);

       /* Compile with: -lzstd */

DESCRIPTION
       ZSTD_compress() compresses `src` content as a single zstd compressed frame
       into already allocated `dst`.
       ...

RETURN VALUE
       The number of bytes written into `dst` (<= `dstCapacity`),
       or an error code if it fails (which can be tested using ZSTD_isError()).

ERRORS
       When an error occurs, the function returns a code that can be inspected
       using ZSTD_getErrorName(code).
       Standard libc functions set errno to:
       EINVAL Invalid compression parameters.
       ENOMEM Insufficient memory to allocate internal tables.

ATTRIBUTES
       Interface               Attribute       Value
       ZSTD_compress()         Thread safety   MT-Safe

STANDARDS / CONFORMING TO
       BSD-3-Clause / POSIX.1-2008 extension.
```

Критичні розділи, на які звертають увагу в першу чергу:
1. **SYNOPSIS:** показує точний список заголовків, які потрібно включити через `#include`, макроси функціональних тестів (наприклад, `#define _GNU_SOURCE`), які необхідно оголосити до заголовків, та точні типи аргументів;
2. **RETURN VALUE:** чітко визначає межу успіху та помилки. Для системних функцій C успіх зазвичай позначається нулем `0` (або валідним покажчиком/розміром), а помилка — значенням `-1` чи `NULL`;
3. **ERRORS:** перелік кодів глобальної змінної `errno` (`EINVAL`, `EAGAIN`, `ENOMEM`, `EBADF`), які встановлює функція у разі збою;
4. **ATTRIBUTES:** таблиця безпеки середовища виконання. Якщо вказано `MT-Safe` (*Multi-Thread Safe*), функцію можна безпечно викликати паралельно з кількох потоків без додаткових блокувань. Позначка `MT-Unsafe` вимагає зовнішньої синхронізації м'ютексом. Позначка `AS-Safe` (*Async-Signal-Safe*) вказує на безпеку виклику з обробників сигналів.

## 6. Наскрізний інженерний алгоритм: дослідження невідомої бібліотеки

Коли ви стикаєтеся з незнайомою сторонньою бібліотекою або аналізуєте складну систему на сервері клієнта, дослідження здійснюється за єдиним шістьохетапним протоколом:

```
  [Крок 1: pkg-config]  ──>  З'ясувати назву пакета, версію, Cflags та Libs
           │
           ▼
  [Крок 2: readelf -d]  ──>  Перевірити SONAME та список залежностей DT_NEEDED
           │
           ▼
  [Крок 3: nm -D]       ──>  Вилучити реальний перелік експортованих функцій (T)
           │
           ▼
  [Крок 4: /usr/include] ──>  Знайти заголовок, вивчити структури та opaque-типи
           │
           ▼
  [Крок 5: man 3]       ──>  Прочитати контракти помилок, пам'яті та потокобезпечності
           │
           ▼
  [Крок 6: Зонд-тест]   ──>  Скомпілювати мінімальну програму на C/C++
```

### Крок 1. Перевірка метаданих та наявності бібліотеки
Перевіряємо, чи зареєстрована бібліотека в базі `pkg-config`:
```sh
$ pkg-config --list-all | grep -i crypto
libcrypto           OpenSSL-libcrypto - OpenSSL cryptography library
$ pkg-config --modversion libcrypto
3.0.13
$ pkg-config --cflags --libs libcrypto
-I/usr/include -lcrypto
```

### Крок 2. Інспекція двійкового об'єкта та залежностей
Знаходимо двійковий файл `.so` та перевіряємо його системні залежності:
```sh
$ ldconfig -p | grep libcrypto
libcrypto.so.3 (libc6,x86-64) => /lib/x86_64-linux-gnu/libcrypto.so.3

$ readelf -d /lib/x86_64-linux-gnu/libcrypto.so.3 | grep -E 'SONAME|NEEDED'
```

### Крок 6. Написання перевірочного зонду (Probe Program)
Пишемо мінімальний перевірочний виклик, який підтверджує повну працездатність усього ланцюжка:

:::tabs
```c
#include <stdio.h>
#include <string.h>
#include <openssl/evp.h>

int main(void) {
    const char message[] = "Unix library contract verification";
    unsigned char digest[EVP_MAX_MD_SIZE];
    size_t digest_len = 0;

    int ok = EVP_Q_digest(NULL, "SHA256", NULL, message, strlen(message), digest, &digest_len);
    if (!ok) {
        fprintf(stderr, "Помилка обчислення хешу SHA-256\n");
        return 1;
    }

    printf("SHA-256: ");
    for (size_t i = 0; i < digest_len; i++) {
        printf("%02x", digest[i]);
    }
    printf("\n");
    return 0;
}
```
```cpp
#include <iostream>
#include <iomanip>
#include <string_view>
#include <array>
#include <span>
#include <openssl/evp.h>

int main() {
    constexpr std::string_view message = "Unix library contract verification";
    std::array<uint8_t, EVP_MAX_MD_SIZE> digest{};
    size_t digest_len = 0;

    int const ok = EVP_Q_digest(
        nullptr,
        "SHA256",
        nullptr,
        message.data(),
        message.size(),
        digest.data(),
        &digest_len
    );

    if (!ok) {
        std::cerr << "Помилка обчислення хешу SHA-256\n";
        return 1;
    }

    std::cout << "SHA-256: ";
    for (uint8_t byte : std::span(digest.data(), digest_len)) {
        std::cout << std::hex << std::setw(2) << std::setfill('0') << static_cast<int>(byte);
    }
    std::cout << '\n';
    return 0;
}
```

## 7. Синтез: чотири стовпи надійної інтеграції

У середовищі Unix робота з чужим кодом будується не на припущеннях чи пошуку випадкових фрагментів коду, а на злагодженій системі чотирьох взаємопов'язаних інструментів:

* **Заголовки `.h`** захищають ваш код від синтаксичних помилок та невідповідності типів на етапі компіляції;
* **Метадані `pkg-config`** гарантують коректне передавання прапорців та транзитивних бібліотек у систему збірки незалежно від шляхів встановлення;
* **Двійкова інспекція `nm -D` / `readelf`** дає неспростовний доказ того, які саме символи та версії ABI фізично присутні у скомпільованому спільному об'єкті `.so`;
* **Сторінки `man 3`** документують точний контракт життєвого циклу ресурсів, потокобезпечності та обробки помилок через `errno`.

Володіння цією четвіркою перетворює чужу бібліотеку з незрозумілого двійкового файлу на передбачуваний, прозорий та надійний інженерний компонент вашої програмної системи.
