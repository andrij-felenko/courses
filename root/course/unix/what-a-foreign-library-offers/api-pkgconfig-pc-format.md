# 📋 Специфікація формату .pc та довідник змінних pkg-config

Формат файлів опису пакетів `.pc` (від англ. *Package Config*) є загальноприйнятим стандартом в операційних системах сімейства Unix та дистрибутивах Linux для декларативного опису метаданих компіляції, лінкування та версіонування бібліотек. Утиліта `pkg-config` (а також її сучасна сумісна та швидша реалізація `pkgconf`) використовує ці файли, щоб повністю усунути необхідність ручного введення та жорсткого зашивання абсолютних шляхів до заголовних файлів і бібліотечних об'єктів у Makefiles, CMakeLists чи скриптах конфігурації Autotools.

Файл із розширенням `.pc` є звичайним текстовим файлом у кодуванні UTF-8 або ASCII, який складається з двох взаємопов'язаних частин: визначення внутрішніх користувацьких змінних (*variables*) та формальних полів метаданих (*keywords*).

## 1. Синтаксис змінних та механізм рекурсивної інтерполяції

Змінні оголошуються у форматі `ім'я=значення`. Пробіли навколо знака рівності не допускаються або вважаються частиною значення. Утиліта `pkg-config` підтримує рекурсивну підстановку значень інших змінних за допомогою синтаксису `${ім'я_змінної}`. Змінні обчислюються лінійно зверху вниз, тому змінна має бути визначена до моменту її першого використання в інших виразах або полях.

Якщо розробник бібліотеки посилається на неоголошену змінну, утиліта під час розбору підставляє порожній рядок без генерації фатальної помилки, що може призвести до утворення відносних шляхів на кшталт `-I/include` замість `-I/usr/include`.

Типовий початковий блок встановлення системних каталогів має такий вигляд:

```ini
prefix=/usr
exec_prefix=${prefix}
libdir=${exec_prefix}/lib/x86_64-linux-gnu
includedir=${prefix}/include
```

### Стандартні системні змінні

Хоча розробник бібліотеки може створювати довільні власні змінні, в екосистемі Unix існує конвенція щодо обов'язкового набору стандартних змінних:

* `prefix` — базовий каталог встановлення програмного пакета (наприклад, `/usr` для пакетів системного дистрибутива, `/usr/local` для локально скомпільованого софту адміністратора, або `/opt/vendor` для сторонніх ізольованих інсталяцій);
* `exec_prefix` — базовий каталог для файлів, залежних від архітектури процесора (за замовчуванням визначається як `${prefix}`);
* `libdir` — каталог розміщення двійкових файлів спільних та статичних бібліотек (`.so`, `.a`, `.dylib`);
* `includedir` — кореневий каталог розміщення заголовних файлів C/C++ (`.h`, `.hpp`, `.hxx`);
* `bindir` — каталог допоміжних виконуваних утиліт пакета (наприклад, генераторів коду чи компіляторів схем);
* `datarootdir` / `datadir` — каталог архітектурно-незалежних даних та ресурсів (`/usr/share`).

### Спеціальна вбудована змінна `pcfiledir` та переносні пакунки

Особливе місце посідає вбудована змінна `pcfiledir`. Вона автоматично ініціалізується самою утилітою `pkg-config` у момент відкриття файлу та містить абсолютний шлях до каталогу, в якому фізично розміщений цей конкретний `.pc` файл на диску.

Завдяки `pcfiledir` автори бібліотек можуть створювати повністю переносні (*relocatable*) пакунки, які коректно функціонують незалежно від того, куди саме користувач розпакував архів із програмним забезпеченням. Це надзвичайно зручно для розповсюдження SDK у середовищах розробки:

```ini
# Визначення префікса відносно місця розташування .pc файлу:
# Якщо файл лежить у /opt/my-sdk/lib/pkgconfig/libsdk.pc,
# то ${pcfiledir}/../.. розгорнеться в /opt/my-sdk
prefix=${pcfiledir}/../..
exec_prefix=${prefix}
libdir=${exec_prefix}/lib
includedir=${prefix}/include

Name: libsdk
Description: Relocatable Embedded SDK Library
Version: 3.2.0
Libs: -L${libdir} -lsdk
Cflags: -I${includedir}
```

## 2. Нормативні поля метаданих (Keywords)

Поля записуються у форматі `Ключ: Значення`. Назви ключів чутливі до регістру символів. Кожне поле виконує чітко визначену роль у формуванні прапорців збірки.

| Ключове поле | Статус | Призначення та семантичні правила | Приклад запису |
|---|---|---|---|
| `Name` | **Обов'язкове** | Офіційне людиночитне ім'я бібліотеки чи підсистеми. | `Name: libzstd` |
| `Description` | **Обов'язкове** | Короткий опис призначення та функціональності. | `Description: Zstandard compression library` |
| `Version` | **Обов'язкове** | Точний номер версії у форматі SemVer або X.Y.Z. | `Version: 1.5.5` |
| `URL` | Опціональне | Посилання на репозиторій або документацію проєкту. | `URL: https://facebook.github.io/zstd/` |
| `Requires` | Опціональне | Список публічних `.pc` залежностей через кому. | `Requires: libcrypto >= 3.0.0, zlib` |
| `Requires.private` | Опціональне | Список залежностей, потрібних **лише для статичного** лінкування. | `Requires.private: liblzma >= 5.2.0, liblz4` |
| `Conflicts` | Опціональне | Перелік пакетів, несумісних із цією бібліотекою. | `Conflicts: libzstd-legacy < 1.0.0` |
| `Cflags` | Опціональне | Публічні прапорці компілятора (шляхи `-I`, макроси `-D`). | `Cflags: -I${includedir} -DZSTD_MULTITHREAD` |
| `Cflags.private` | Опціональне | Прапорці компілятора тільки для внутрішньої статичної збірки. | `Cflags.private: -DZSTD_STATIC_LINKING_ONLY` |
| `Libs` | Опціональне | Прапорці лінкера для стандартного динамічного зв'язування. | `Libs: -L${libdir} -lzstd` |
| `Libs.private` | Опціональне | Прапорці лінкера, потрібні **виключно для статичного** зв'язування. | `Libs.private: -pthread -lrt -lm` |

### Оператори обмеження версій у полі `Requires`

Поля `Requires` та `Requires.private` підтримують стандартні оператори порівняння версій для забезпечення сумісності:
* `=` — суворе співпадіння версії (`Requires: libfoo = 2.1.0`);
* `>=` — версія не нижче вказаної (`Requires: libssl >= 1.1.1`);
* `<=` — версія не вище вказаної;
* `>` та `<` — строгі нерівності;
* `!=` — версія не повинна дорівнювати вказаній.

Якщо системна версія не задовольняє умові, `pkg-config` повертає ненульовий код завершення та повідомлення про несумісність.

## 3. Механізм ізоляції транзитивних залежностей: `Libs` проти `Libs.private`

Розділення прапорців на публічні та приватні розв'язує фундаментальну проблему керування залежностями у великих проєктах — проблему надлишкового зв'язування (*overlinking*).

1. **Поведінка при динамічному зв'язуванні:**
   Коли прикладний застосунок компонується з динамічною бібліотекою (`gcc main.o $(pkg-config --libs libengine)`), компонувальник `ld` додає спільний об'єкт `libengine.so` до списку прямих залежностей бінарника (запис `DT_NEEDED`). Якщо `libengine.so` всередині викликає функції математичної бібліотеки `libm.so` або криптографічної `libcrypto.so`, але не виставляє їхні типи у своїх публічних заголовках, застосунку ці залежності знати не потрібно. Динамічний завантажувач ядра `ld.so` самостійно завантажить їх під час запуску програми. Тому звичайний виклик `pkg-config --libs` повертає **тільки** вміст поля `Libs` та публічні залежності з `Requires`.

2. **Поведінка при статичному зв'язуванні (`--static`):**
   При статичній компіляції (`gcc -static main.o $(pkg-config --libs --static libengine)`) замість динамічного об'єкта використовується архів об'єктних файлів `libengine.a`. Статичний архів є звичайною колекцією машинних файлів `.o` і взагалі не містить секції `.dynamic` чи записів `DT_NEEDED`. Якщо лінкеру не передати прапорці `-lm` та `-lcrypto`, усі внутрішні виклики математичних і криптографічних функцій залишаться нерозв'язаними, і збірка впаде з помилкою `undefined reference to 'cos'`. Прапорець `--static` змушує `pkg-config` рекурсивно обійти весь граф залежностей і об'єднати:
   `Libs` + `Libs.private` + усі поля `Libs` та `Libs.private` із пакетів, зазначених у `Requires.private`.

### Обробка циклічних залежностей та орієнтованого графа

Утиліта `pkg-config` будує орієнтований ациклічний граф залежностей (DAG). Під час обходу вона відстежує вже відвідані пакети, автоматично розриваючи можливі циклічні посилання. Якщо бібліотека `A` потребує `B`, а `B` посилається назад на `A`, утиліта включає прапорці кожного пакета рівно один раз, розміщуючи залежні бібліотеки після тих, хто їх викликає, що гарантує коректний однопрохідний розв'язок символів у статичному лінкері `ld`.

### Специфіка заголовних бібліотек (Header-Only Libraries)

Для бібліотек, що складаються виключно із заголовних файлів (наприклад, шаблони C++ чи макроси, як у nlohmann/json чи Eigen), поле `Libs` залишається порожнім або взагалі опускається. У файлі `.pc` заповнюється лише поле `Cflags`:

```ini
prefix=/usr
includedir=${prefix}/include

Name: nlohmann_json
Description: JSON for Modern C++
Version: 3.11.2
Cflags: -I${includedir}
```

## 4. Повний довідник командного рядка `pkg-config`

Утиліта `pkg-config` надає багатий інтерфейс для автоматизації збірки в Make-файлах, Shell-скриптах та системах CI/CD:

```sh
# 1. Перевірка наявності пакета та відповідності версійному діапазону
$ pkg-config --exists 'libtelemetry >= 2.0.0' && echo "Пакет знайдено та сумісний"

# 2. Отримання точного номера версії встановленого пакета
$ pkg-config --modversion libtelemetry
2.4.1

# 3. Отримання прапорців компілятора (включення каталогів заголовків та макросів)
$ pkg-config --cflags libtelemetry
-I/usr/local/include/telemetry -DTELEMETRY_API_V2

# 4. Отримання прапорців лінкера для динамічного зв'язування
$ pkg-config --libs libtelemetry
-L/usr/local/lib/x86_64-linux-gnu -ltelemetry -lssl -lcrypto

# 5. Отримання прапорців лінкера для статичного зв'язування (повний граф залежностей)
$ pkg-config --libs --static libtelemetry
-L/usr/local/lib/x86_64-linux-gnu -ltelemetry -lssl -lcrypto -lz -lsodium -pthread -lm -latomic

# 6. Читання довільної стандартної або користувацької змінної
$ pkg-config --variable=schemadir libtelemetry
/usr/local/share/telemetry/schemas

# 7. Тимчасове перевизначення змінної в командному рядку
$ pkg-config --define-variable=prefix=/opt/custom-sdk --cflags libtelemetry
-I/opt/custom-sdk/include/telemetry -DTELEMETRY_API_V2

# 8. Виведення повного списку всіх зареєстрованих у системі пакетів .pc
$ pkg-config --list-all
```

## 5. Змінні середовища та специфіка крос-компіляції

За замовчуванням `pkg-config` перевіряє системні каталоги `/usr/lib/pkgconfig`, `/usr/share/pkgconfig`, `/usr/local/lib/pkgconfig` та архітектурні підкаталоги. Для керування порядком обходу та ізоляції використовуються наступні змінні середовища:

### `PKG_CONFIG_PATH`
Список каталогів через двокрапку, які перевіряються **перед** стандартними системними шляхами. Використовується, коли розробник встановлює власні бібліотеки у домашній каталог або нестандартний префікс:
```sh
export PKG_CONFIG_PATH="/home/developer/.local/lib/pkgconfig:/opt/thirdparty/lib/pkgconfig:$PKG_CONFIG_PATH"
```

### `PKG_CONFIG_LIBDIR`
Повністю **перевизначає** стандартний системний список каталогів пошуку. Це критично важливо під час крос-компіляції (наприклад, збірка під ARM64 на x86-64 хості). Якщо не задати `PKG_CONFIG_LIBDIR`, утиліта випадково зчитає x86-64 пакети хоста, що призведе до передачі неправильних прапорців лінкеру.

```sh
export PKG_CONFIG_LIBDIR="/opt/toolchains/aarch64-linux-gnu/sysroot/usr/lib/pkgconfig:/opt/toolchains/aarch64-linux-gnu/sysroot/usr/share/pkgconfig"
```

### `PKG_CONFIG_SYSROOT_DIR`
Вказує префікс цільової кореневої файлової системи (*sysroot*). Утиліта автоматично додає значення цієї змінної до всіх шляхів `-I` та `-L`, які починаються зі скісної риски `/usr`, запобігаючи небезпечному включенню хостових каталогів:

```sh
export PKG_CONFIG_SYSROOT_DIR="/opt/toolchains/aarch64-linux-gnu/sysroot"
$ pkg-config --cflags libtelemetry
-I/opt/toolchains/aarch64-linux-gnu/sysroot/usr/include/telemetry -DTELEMETRY_API_V2
```

### Інтеграція в сучасні генератори збірки (CMake та Meson)

Сучасні системи автоматизації збірки мають вбудовані модулі для взаємодії з `pkg-config`:

* У системі **CMake** модуль `FindPkgConfig` надає макрос `pkg_check_modules()`, який імпортує цільові змінні та властивості компілятора:
  ```cmake
  find_package(PkgConfig REQUIRED)
  pkg_check_modules(ZSTD REQUIRED IMPORTED_TARGET libzstd)
  target_link_libraries(my_app PRIVATE PkgConfig::ZSTD)
  ```
* У системі **Meson** виклик `dependency('libzstd')` автоматично шукає однойменний `.pc` файл у системних шляхах та застосовує всі необхідні прапорці до цільового виконуваного файлу без ручного розбору параметрів.
