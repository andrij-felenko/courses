# Практичне простеження write() на живому ядрі: від ftrace до bpftrace

- [libc як шлюз до ядра](root:sys-unix/libc-as-gateway) — трансляція викликів мови C у системні виклики ядра.
- [Один виклик наскрізь](root:unix/tracing-one-call) — теоретичний опис наскрізного ланцюжка від рядка коду до драйвера.
</preknowlist>

Коли ми читаємо опис системного виклику у підручнику, ланцюжок викликів виглядає абстрактною схемою: користувацький простір викликає бібліотеку, бібліотека виконує інструкцію пастки, ядро знаходить дескриптор і викликає драйвер. Але операційна система Linux не приховує свого внутрішнього життя. Будь-який розробник або системний інженер може побачити кожен крок цього шляху на власній працюючій машині — з точними мітками часу в наносекундах, аргументами функцій і повними стеками викликів ядра.

Для цього в ядрі існують дві потужні підсистеми спостереження: вбудований трасувальник `ftrace` (зокрема його плагін `function_graph`) та динамічний інструментарій `eBPF` через інтерпретатор `bpftrace`. Розберемо практичний лабораторний практикум: напишемо тестову програму, налаштуємо трасування виклику `write()` і простежимо кожен шар ядра — від моменту входу в `entry_SYSCALL_64` до передачі байтів у драйвер термінала, блоковий шар диска та обробники апаратних переривань.

## Тестова програма: контрольований виклик

Щоб під час трасування не потонути в тисячах сторонніх системних викликів, які постійно генерують фонові служби та графічне середовище, тестова програма має бути максимально ізольованою. Вона має виконувати запис за чіткою командою користувача — після паузи або зчитування символу з клавіатури, — а також демонструвати як запис у термінал (псевдотермінал TTY), так і запис у звичайний файл на диску (ext4 чи XFS).

Створимо програму, яка вміє спрямовувати 6 байтів `"HELLO\n"` як у стандартний вивід (`STDOUT_FILENO`), так і у відкритий на диску файл.

:::tabs
```c
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    const char msg[] = "HELLO\n";
    pid_t pid = getpid();

    printf("PID тестового процесу: %d\n", pid);
    printf("Натисніть Enter для запису в TTY (stdout)...\n");
    getchar();

    /* 1. Запис у термінал (псевдоконсоль) */
    ssize_t ret_tty = write(STDOUT_FILENO, msg, sizeof(msg) - 1);
    if (ret_tty < 0) {
        perror("write tty");
        return 1;
    }

    printf("Натисніть Enter для запису у файл на диску (/tmp/trace_test.txt)...\n");
    getchar();

    /* 2. Запис у звичайний файл на диску */
    int fd_file = open("/tmp/trace_test.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd_file < 0) {
        perror("open file");
        return 1;
    }

    ssize_t ret_file = write(fd_file, msg, sizeof(msg) - 1);
    if (ret_file < 0) {
        perror("write file");
        close(fd_file);
        return 1;
    }

    close(fd_file);
    printf("Запис завершено успішно (TTY: %zd Б, Диск: %zd Б).\n", ret_tty, ret_file);
    return 0;
}
```
```cpp
#include <unistd.h>
#include <fcntl.h>
#include <iostream>
#include <string_view>
#include <system_error>

class FileDescriptor {
    int fd_{-1};
public:
    explicit FileDescriptor(int fd) : fd_(fd) {}
    ~FileDescriptor() { if (fd_ >= 0) ::close(fd_); }
    int get() const noexcept { return fd_; }
    bool valid() const noexcept { return fd_ >= 0; }
};

int main()
{
    constexpr std::string_view msg = "HELLO\n";
    pid_t pid = getpid();

    std::cout << "PID тестового процесу: " << pid << '\n';
    std::cout << "Натисніть Enter для запису в TTY (stdout)...\n";
    std::cin.get();

    /* 1. Запис у термінал (псевдоконсоль) */
    ssize_t ret_tty = ::write(STDOUT_FILENO, msg.data(), msg.size());
    if (ret_tty < 0) {
        auto ec = std::error_code(errno, std::generic_category());
        std::cerr << "Помилка запису в TTY: " << ec.message() << '\n';
        return 1;
    }

    std::cout << "Натисніть Enter для запису у файл на диску (/tmp/trace_test.txt)...\n";
    std::cin.get();

    /* 2. Запис у звичайний файл на диску */
    FileDescriptor file(::open("/tmp/trace_test.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644));
    if (!file.valid()) {
        auto ec = std::error_code(errno, std::generic_category());
        std::cerr << "Помилка відкриття файлу: " << ec.message() << '\n';
        return 1;
    }

    ssize_t ret_file = ::write(file.get(), msg.data(), msg.size());
    if (ret_file < 0) {
        auto ec = std::error_code(errno, std::generic_category());
        std::cerr << "Помилка запису у файл: " << ec.message() << '\n';
        return 1;
    }

    std::cout << "Запис завершено успішно (TTY: " << ret_tty << " Б, Диск: " << ret_file << " Б).\n";
    return 0;
}
```

## Чому класичний strace спотворює картину реального часу

Першим інструментом, про який згадують під час аналізу системних викликів, є `strace`. Проте для дослідження точного наскрізного шляху та вимірювання затримок `strace` принципово не підходить.

Механізм `strace` базується на системному виклику `ptrace` (підсистема відлагодження). Працює це так:
1. `strace` встановлює прапорець `PTRACE_SYSCALL` для досліджуваного процесу.
2. Щоразу, коли процес доходить до інструкції `syscall`, ядро переводить його в стан зупинки (`TASK_TRACED`), генерує сигнал `SIGTRAP` і передає керування процесу `strace`.
3. `strace` прокидається, робить системні виклики для зчитування регістрів процесу через `ptrace(PTRACE_GETREGS)`, форматує аргументи у текстовий вигляд і знову просить ядро відновити процес.
4. Коли системний виклик завершується, ядро вдруге зупиняє процес на точці повернення (`sys_exit`) і знову перемикає контекст на `strace` для зчитування коду результату.

У результаті на кожен системний виклик додається щонайменше чотири повні перемикання контексту між процесами та кілька додаткових системних викликів. Затримка виконання `write()` при цьому штучно зростає від кількох сотень наносекунд до десятків або сотень мікросекунд (у сотні разів). Крім того, `strace` бачить лише дві крайні точки — вхід і вихід, — залишаючи весь внутрішній шлях ядра непрозорою «чорною скринькою».

Саме тому для наскрізного аналізу ми застосовуємо трасувальники всередині ядра — `ftrace` та `bpftrace`, які працюють без зупинки процесу і без перемикання контекстів користувача.

## Спосіб 1. Граф викликів функцій ядра через ftrace

Підсистема `ftrace` вбудована безпосередньо в ядро Linux і доступна через псевдофайлову систему `tracefs` (зазвичай змонтовану за шляхом `/sys/kernel/tracing` або `/sys/kernel/debug/tracing`). Найзручніший спосіб дослідити повну послідовність викликів C-функцій усередині ядра — увімкнути плагін `function_graph`.

### Налаштування фільтрів ftrace

Під час увімкнення `function_graph` ядро перехоплює вхід і вихід із кожної скомпільованої функції за допомогою спеціальних прологів компілятора (`-pg` / `mcount` або `fentry`). Якщо не задати фільтри, буфер трасування за мілісекунду переповниться подіями інших процесорних ядер і фонових потоків. Тому ми відфільтруємо трасування за конкретною точкою входу `ksys_write` і обмежимо запис лише PID нашого процесу.

Виконаємо налаштування від імені суперкористувача (`root`):

```bash
# Переходимо в каталог керування трасуванням
cd /sys/kernel/tracing

# 1. Тимчасово вимикаємо запис для безпечної конфігурації
echo 0 > tracing_on
echo nop > current_tracer
echo > trace

# 2. Встановлюємо плагін графа функцій
echo function_graph > current_tracer

# 3. Вказуємо кореневу функцію, від якої будувати дерево викликів
echo ksys_write > set_graph_function

# 4. Обмежуємо глибину дерева (щоб зосередитися на ключових підсистемах)
echo 6 > max_graph_depth

# 5. Вказуємо PID нашої запущеної програми (наприклад, 4128)
echo 4128 > set_ftrace_pid

# 6. Вмикаємо запис траси
echo 1 > tracing_on
```

Тепер повертаємося у вікно з нашою програмою `trace_target` і натискаємо `Enter` для виконання першого запису (у TTY).

Зупиняємо трасування й копіюємо знятий журнал:

```bash
echo 0 > /sys/kernel/tracing/tracing_on
cat /sys/kernel/tracing/trace > /tmp/ftrace_tty.log
```

### Аналіз журналу function_graph для TTY

Погляньмо на реальний фрагмент отриманого журналу `ftrace` для виклику `write()` у псевдотермінал (`/dev/pts/1`):

```
# tracer: function_graph
#
# CPU  DURATION                  FUNCTION CALLS
# |     |   |                     |   |   |   |
 2)               |  ksys_write() {
 2)   0.120 us    |    __fdget_pos();
 2)               |    vfs_write() {
 2)   0.080 us    |      rw_verify_area();
 2)               |      new_sync_write() {
 2)               |        tty_write() {
 2)               |          file_tty_write.isra.0() {
 2)               |            n_tty_write() {
 2)   0.090 us    |              _copy_from_user();
 2)   0.140 us    |              process_output();
 2)               |              pty_write() {
 2)   0.150 us    |                tty_insert_flip_string_and_push_buffer();
 2)   0.480 us    |              }
 2)   1.240 us    |            }
 2)   1.580 us    |          }
 2)   1.820 us    |        }
 2)   2.110 us    |      }
 2)   0.090 us    |      inc_syscw();
 2)   2.640 us    |    }
 2)   0.110 us    |    __fget_light();
 2)   3.210 us    |  }
```

Цей журнал документально підтверджує кожен крок наскрізного шляху:

1. **`ksys_write()`** — точка входу ядра, розпакована диспетчером викликів `do_syscall_64`.
2. **`__fdget_pos()`** — швидкий пошук структури `struct file` за числовим дескриптором `1` у таблиці `current->files` поточного процесу.
3. **`vfs_write()`** — спільний шар VFS, де виконується перевірка `rw_verify_area()` (чи дозволено запис у вказаний діапазон пам'яті та зміщення).
4. **`new_sync_write()` / `tty_write()`** — диспетчеризація через віртуальну таблицю `file->f_op->write_iter`. Оскільки дескриптор `1` відкритий на псевдотермінал, керування передається підсистемі TTY.
5. **`n_tty_write()`** — дисципліна лінії термінала. Тут викликається `_copy_from_user()`, яка зі зняттям захисту SMAP безпечно копіює 6 байтів із простору користувача в буфер ядра, та `process_output()` для обробки символу переносу рядка `\n`.
6. **`pty_write()`** — драйвер кінцевого пристрою, який поміщає байти у вхідний буфер емулятора термінала.
7. Загальний час виконання операції всередині ядра на цьому процесорі склав **3.21 мікросекунди**.

### Порівняння: граф виклику для дискового файлу (ext4)

Очистимо буфер `trace`, знову ввімкнемо `tracing_on` і натиснемо `Enter` у програмі для виконання другого запису — у файл `/tmp/trace_test.txt` на файловій системі ext4:

```bash
echo > /sys/kernel/tracing/trace
echo 1 > /sys/kernel/tracing/tracing_on
# (виконуємо запис у файл у тестовій програмі)
echo 0 > /sys/kernel/tracing/tracing_on
cat /sys/kernel/tracing/trace > /tmp/ftrace_disk.log
```

Журнал для дискового запису розкриває зовсім іншу гілку VFS:

```
# tracer: function_graph
#
# CPU  DURATION                  FUNCTION CALLS
# |     |   |                     |   |   |   |
 3)               |  ksys_write() {
 3)   0.110 us    |    __fdget_pos();
 3)               |    vfs_write() {
 3)   0.070 us    |      rw_verify_area();
 3)               |      new_sync_write() {
 3)               |        ext4_file_write_iter() {
 3)   0.080 us    |          inode_lock();
 3)               |          ext4_buffered_write_iter() {
 3)               |            generic_perform_write() {
 3)   0.180 us    |              ext4_da_write_begin();
 3)   0.120 us    |              copy_page_from_iter_atomic();
 3)   0.310 us    |              ext4_da_write_end();
 3)   0.850 us    |            }
 3)   1.220 us    |          }
 3)   0.060 us    |          inode_unlock();
 3)   1.640 us    |        }
 3)   1.920 us    |      }
 3)   0.080 us    |      file_update_time();
 3)   2.450 us    |    }
 3)   2.980 us    |  }
```

Порівняння двох журналів унаочнює принцип монолітної архітектури:
- Функції верхнього рівня `ksys_write()` та `vfs_write()` **абсолютно однакові** в обох випадках.
- Розгалуження відбувається всередині `vfs_write()` через виклик покажчика `file->f_op->write_iter`. Для TTY викликається `tty_write()`, а для файлу на диску — `ext4_file_write_iter()`.
- У випадку ext4 дані не летять на диск одразу: `copy_page_from_iter_atomic()` копіює 6 байтів у кеш сторінок (Page Cache), сторінка позначається як «брудна» (`dirty`), і виклик повертає керування за 2.98 мікросекунди, залишаючи реальний запис на диск фоновій підсистемі writeback.

У журналі `ftrace` ліворуч від імен функцій часто можна побачити спеціальні односимвольні позначки — наприклад, `d` (переривання апаратно вимкнено), `N` (потоку потрібне термінове перепланування `TIF_NEED_RESCHED`), `p` (активний контекст `preempt_disable`). Під час аналізу `write()` поява цих позначок вказує на критичні секції ядра, де планувальник не має права перервати поточне ядро процесора, забезпечуючи атомарне оновлення буферів пристрою.

## Спосіб 2. Точне вимірювання затримок і стеків через bpftrace

Інструмент `ftrace` дає чудовий огляд імен функцій, але не дозволяє легко роздрукувати значення аргументів (вміст буфера, кількість байтів, значення дескриптора) або порахувати точні затримки між окремими шарами ядра.

Для цього ідеально підходить `bpftrace` — високорівнева мова трасування на основі eBPF. Вона дозволяє під'єднатися одночасно до точок трасування системних викликів (`tracepoints`), динамічних зондів функцій ядра (`kprobes`) та інструкцій повернення (`kretprobes`).

### Скрипт трасування `trace_write.bt`

Створимо скрипт `trace_write.bt`, який відстежує кожен етап `write()`, вимірює тривалість кожного кроку в наносекундах і знімає повний стек викликів ядра:

```bpftrace
#!/usr/bin/env bpftrace

BEGIN
{
    printf("Трасування системного виклику write() запущено. Очікування подій...\n");
}

/* 1. Точка входу в системний виклик із простору користувача */
tracepoint:syscalls:sys_enter_write
/comm == "trace_target"/
{
    @start_time[tid] = nsecs;
    printf("\n[%u ms] [USER -> KERNEL] sys_enter_write: fd=%d, ubuf=0x%lx, count=%lu\n",
           elapsed / 1000000, args->fd, (uint64)args->buf, args->count);
}

/* 2. Вхід у шар віртуальної файлової системи (VFS) */
kprobe:vfs_write
/@start_time[tid]/
{
    $file = (struct file *)arg0;
    $count = arg2;
    printf("[%u ms]   -> [VFS Layer] vfs_write: file_ptr=0x%lx, count=%lu\n",
           elapsed / 1000000, (uint64)$file, $count);
}

/* 3. Вхід у підсистему TTY (якщо запис іде в термінал) */
kprobe:n_tty_write
/@start_time[tid]/
{
    printf("[%u ms]     -> [Line Discipline] n_tty_write (копіювання через copy_from_user)\n",
           elapsed / 1000000);
}

/* 4. Вхід у драйвер пристрою */
kprobe:pty_write
/@start_time[tid]/
{
    printf("[%u ms]       -> [Device Driver] pty_write: передача байтів у буфер пристрою\n",
           elapsed / 1000000);
    printf("Стек викликів ядра (Kernel Call Stack):\n");
    print(kstack);
}

/* 5. Вхід у файлову систему ext4 (якщо запис іде на диск) */
kprobe:ext4_file_write_iter
/@start_time[tid]/
{
    printf("[%u ms]     -> [Filesystem] ext4_file_write_iter (запис у Page Cache)\n",
           elapsed / 1000000);
    printf("Стек викликів ядра для ext4:\n");
    print(kstack);
}

/* 6. Завершення системного виклику та повернення результату */
tracepoint:syscalls:sys_exit_write
/@start_time[tid]/
{
    $duration_us = (nsecs - @start_time[tid]) / 1000;
    printf("[%u ms] [KERNEL -> USER] sys_exit_write: ret=%ld (записано байтів), час ядра: %u мкс\n",
           elapsed / 1000000, args->ret, $duration_us);
    delete(@start_time[tid]);
}

END
{
    clear(@start_time);
}
```

Запустимо скрипт у першому вікні термінала:

```bash
sudo bpftrace trace_write.bt
```

## Спосіб 3. Трасування за допомогою perf trace

Для швидкої діагностики без написання скриптів на bpftrace або ручного налаштування ftrace у стандартному арсеналі Linux є утиліта `perf trace`. Вона працює подібно до `strace`, але замість дорогого механізму `ptrace` використовує ядерні кільцеві буфери `perf_event`, що зменшує накладні витрати на порядки.

## Як ядро розгортає стек: механізм ORC Unwinder

Під час аналізу виводу `bpftrace` виникає природне запитання: яким чином ядро дізнається точний список функцій від `pty_write` до `entry_SYSCALL_64`?

Історично для побудови стеку викликів компілятор виділяв окремий регістр бази кадру (`%rbp` на x86). На початку кожної функції виконувався пролог:

```asm
push   %rbp
mov    %rsp, %rbp
```

Кожен такий кадр утворював зв'язний список на стеку. Але збереження кадру забирає один цінний регістр загального призначення і додає накладні витрати до кожної функції. Тому сучасні компілятори збирають ядро з оптимізацією `-fomit-frame-pointer`, звільняючи `%rbp` для звичайних обчислень.

Щоб зберегти можливість безпомилково розгортати стек під час аварій і трасування без вказівника кадру, починаючи з ядра Linux 4.14 на x86-64 впроваджено систему **ORC** (Oops Rewind Capability). Під час збирання ядра спеціальна утиліта `objtool` аналізує згенерований асемблерний код кожної функції й створює компактну бінарну таблицю метаданих у спеціальних секціях `.orc_unwind` та `.orc_unwind_ip`.

Для кожної інструкції ядра таблиця ORC містить лише кілька байтів інформації:
- Звідки взяти попередній покажчик стека (зміщення від `%rsp` чи з регістра).
- За яким зміщенням на стеку збережено адресу повернення (`%rip`).
- Де збережено інші збережені регістри (наприклад, стан `pt_regs`).

Коли `bpftrace` викликає внутрішню функцію `print(kstack)`, ядро читає поточний `%rip` і `%rsp`, знаходить відповідний запис у таблиці ORC двійковим пошуком і за кілька десятків тактів процесора піднімається на один кадр угору. Це повторюється, доки розгортач не зустріне маркер межі системного виклику (`entry_SYSCALL_64`). Завдяки цьому зняття повного ядерного стеку не потребує жодних евристик і працює надійно навіть посеред виконання асемблерних інструкцій обробників переривань.

## Простеження конкурентного запису та блокувань файлової позиції

Коли кілька потоків або процесів одночасно викликають `write()` на один і той самий файловий дескриптор, виникає питання узгодженості позиції у файлі (`file->f_pos`). Якщо два потоки пишуть без синхронізації, чи можуть їхні байти перемішатися або перезаписати один одного?

Всередині `ksys_write()` ядро викликає функцію `fdget_pos()`. Якщо дескриптор відкритий на файл, який підтримує позиціонування (звичайний файл на диску), `fdget_pos()` захоплює внутрішній м'ютекс файлу `file->f_pos_lock`:

```c
/* Спрощена логіка fdget_pos у ядрі */
static inline struct fd fdget_pos(int fd)
{
    struct fd f = fdget(fd);
    if (f.file && (f.file->f_mode & FMODE_ATOMIC_POS)) {
        if (file_count(f.file) > 1) {
            mutex_lock(&f.file->f_pos_lock);
            f.flags |= FDPUT_POS_UNLOCK;
        }
    }
    return f;
}
```

Це блокування гарантує, що кожен виклик `write()` повністю завершить оновлення `file->f_pos` перед тим, як наступний потік отримає доступ до запису.

Ми можемо простежити це конкурентне очікування за допомогою `bpftrace`:

```bpftrace
kprobe:mutex_lock
/comm == "trace_target"/
{
    @lock_waits[tid] = nsecs;
}

kretprobe:mutex_lock
/@lock_waits[tid]/
{
    $wait_ns = nsecs - @lock_waits[tid];
    if ($wait_ns > 1000) {
        printf("Конкурентне очікування f_pos_lock потоком %d: %u мкс\n", tid, $wait_ns / 1000);
    }
    delete(@lock_waits[tid]);
}
```

Якщо два потоки одночасно викликають `write()`, ми побачимо, що другий потік проводить у `mutex_lock` рівно стільки часу, скільки перший витрачає на `vfs_write` і оновлення кешу сторінок. Це наочно демонструє, як монолітне ядро забезпечує атомарність файлових операцій на рівні структур даних ядра без участі прикладного коду.

## Перевірка крайових випадків: діагностика помилок на живій системі

Практична цінність наскрізного розуміння виклику стає очевидною, коли щось іде не так. Помилки системних викликів виникають на різних шарах ядра, і спостереження за допомогою eBPF дозволяє точно визначити, де саме обірвався ланцюжок.

### Випадок 1: Недійсний дескриптор (`EBADF`)

Якщо викликати `write(-1, msg, 6)` із завідомо недійсним дескриптором, журнал `bpftrace` фіксує миттєву відмову:

```
[18200 ms] [USER -> KERNEL] sys_enter_write: fd=-1, ubuf=0x7ffdb84a1010, count=6
[18200 ms] [KERNEL -> USER] sys_exit_write: ret=-9 (EBADF), час ядра: 0 мкс
```

Жодна функція `vfs_write`, `tty_write` чи драйвера пристрою навіть не викликалася. Функція `__fdget_pos(-1)` миттєво повернула нульовий покажчик, і ядро повернуло код помилки `-EBADF` (`-9`), витративши менше 80 наносекунд.

### Випадок 2: Помилкова адреса пам'яті (`EFAULT`)

Якщо передати дійсний дескриптор `1`, але вказати недійсну адресу пам'яті користувача (наприклад, `(char*)0x1234`):

:::tabs
```c
write(1, (void *)0x1234, 6);
```
```cpp
::write(1, reinterpret_cast<const void *>(0x1234), 6);
```
:::

Трасування показує іншу поведінку:

```
[19100 ms] [USER -> KERNEL] sys_enter_write: fd=1, ubuf=0x1234, count=6
[19100 ms]   -> [VFS Layer] vfs_write: file_ptr=0xffff888102a3bc00, count=6
[19100 ms]     -> [Line Discipline] n_tty_write (копіювання через copy_from_user)
[19100 ms] [KERNEL -> USER] sys_exit_write: ret=-14 (EFAULT), час ядра: 1 мкс
```

Ядро успішно знайшло дескриптор і дійшло до `n_tty_write()`. Але під час виклику `copy_from_user()` процесор згенерував сторінковий збій на неіснуючій сторінці `0x1234`. Таблиця винятків ядра (`__ex_table`) перехопила збій, відновила нормальний хід ядра й повернула код помилки `-EFAULT` (`-14`). Драйвер термінала не отримав жодного байта, а буфер пристрою залишився недоторканим.

### Випадок 3: Неблокуючий ввід-вивід і переповнення буфера (`EAGAIN`)

Якщо відкрити канал або сокет із прапорцем `O_NONBLOCK` і заповнити його буфер до максимуму, наступний системний виклик `write()` не присипляє процес, а миттєво повертає від'ємне число `-11` (`-EAGAIN` або `-EWOULDBLOCK`):

```
[20500 ms] [USER -> KERNEL] sys_enter_write: fd=4, ubuf=0x7ffdb84a1010, count=4096
[20500 ms]   -> [VFS Layer] vfs_write: file_ptr=0xffff888105c11000, count=4096
[20500 ms]     -> [Pipe Subsystem] pipe_write: буфер каналу повний, O_NONBLOCK активний
[20500 ms] [KERNEL -> USER] sys_exit_write: ret=-11 (EAGAIN), час ядра: 0 мкс
```

Трасування наочно показує, що перевірка блокування виконується безпосередньо у внутрішній підсистемі (`pipe_write`), а не у VFS. VFS передала запит у канальну підсистему, та перевірила прапорець `file->f_flags & O_NONBLOCK`, побачила відсутність вільного місця в кільцевому буфері `struct pipe_inode_info` і миттєво повернула `-EAGAIN`.

## Автоматизація трасування: Python-скрипт для зняття метрик

Для регулярного моніторингу затримок системних викликів або інтеграції у тести продуктивності можна написати скрипт на Python із використанням бібліотеки `bcc` (BPF Compiler Collection). Він компілює eBPF-програму на льоту, завантажує її в ядро та виводить гістограму затримок виклику `write()`:

```python
#!/usr/bin/env python3
"""Автоматизоване вимірювання затримок write() через BCC."""

from bcc import BPF
import time

bpf_code = """
#include <uapi/linux/ptrace.h>

BPF_HASH(start, u32);
BPF_HISTOGRAM(dist);

int trace_sys_enter_write(struct tracepoint__syscalls__sys_enter_write *args) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    u64 ts = bpf_ktime_get_ns();
    start.update(&pid, &ts);
    return 0;
}

int trace_sys_exit_write(struct tracepoint__syscalls__sys_exit_write *args) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    u64 *tsp = start.lookup(&pid);
    if (tsp != 0) {
        u64 delta = bpf_ktime_get_ns() - *tsp;
        dist.increment(bpf_log2l(delta / 1000)); // затримка в мікросекундах (log2)
        start.delete(&pid);
    }
    return 0;
}
"""

b = BPF(text=bpf_code)
b.attach_tracepoint(tp="syscalls:sys_enter_write", fn_name="trace_sys_enter_write")
b.attach_tracepoint(tp="syscalls:sys_exit_write", fn_name="trace_sys_exit_write")

print("Збір статистики затримок write() (натисніть Ctrl+C для виводу)...")
try:
    time.sleep(5)
except KeyboardInterrupt:
    pass

print("\nРозподіл затримок write() (мікросекунди, log2 масштаб):")
b["dist"].print_log2_hist("мкс")
```

Такий скрипт перехоплює всі виклики `write()` у системі з мікроскопічним оверхедом (кілька десятків наносекунд на подію) і виводить наочний розподіл часу виконання, дозволяючи виявити поодинокі «хвости» затримок (tail latency), викликані блокуваннями пам'яті чи дискового вводу-виводу.

## Що дає практичне простеження

Можливість зазирнути всередину системного виклику за допомогою `ftrace`, `bpftrace` та `perf trace` перетворює абстрактні архітектурні концепції на вимірювану реальність:

1. **Вузькість межі**: вся взаємодія процесу з ядром зводиться до номерів викликів і регістрів, які реєструються точками `sys_enter` та `sys_exit`.
2. **Єдиний монолітний адресний простір**: перехід від диспетчера викликів до VFS, а від VFS до TTY чи файлової системи — це звичайні виклики функцій мови C у спільному адресному просторі з нульовими накладними витратами на перемикання контекстів процесора.
3. **Ешелонованість перевірок**: перевірка дескриптора відбувається на самому вході (`ksys_write`), перевірка типу об'єкта — у VFS (`vfs_write`), а копіювання байтів із пам'яті користувача зі зняттям захисту SMAP — лише на рівні кінцевої підсистеми перед безпосереднім записом у буфер.
4. **Прозорість внутрішньої діагностики**: будь-яка затримка чи помилка в системі може бути локалізована до конкретного рядка вихідного коду ядра за лічені хвилини за допомогою вбудованих інструментів трасування.
