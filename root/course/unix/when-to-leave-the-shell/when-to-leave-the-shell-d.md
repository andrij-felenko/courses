Сценарій автоматизації резервного копіювання та моніторингу зазвичай починається з кількох рядків на Bash: створення тимчасового каталогу, виклик утиліти `tar`, перенаправлення архіву в потік стиснення `gzip` та відправка файлу на віддалений сервер через `rsync`. Такий сценарій працює бездоганно, доки вимоги залишаються лінійними. Проте з часом інфраструктура ускладнюється: виникає потреба отримувати конфігурацію з HTTP API у форматі JSON, розраховувати середній час відгуку серверів з дробовою точністю, паралельно опитувати сотні хостів із пулом воркерів та перевіряти цілісність даних хеш-сумами.

Через пів року активної розробки початковий файл на 20 рядків розростається до 800 рядків процедурного коду на Bash. У ньому з'являються ланцюжки `grep | sed | awk` для ручного парсингу вкладених структур даних, виклики зовнішнього калькулятора `bc` всередині циклів на 10 000 ітерацій, фонові процеси `&` без обмеження кількості та десятки глобальних змінних. Перша ж назва файлу з пробілом або неочікуване значення `null` у відповіді API призводить до того, що команда `rm -rf "$BACKUP_DIR/$TARGET"` виконується як `rm -rf /` через порожнє значення змінної `$TARGET`, а прапорець `set -e` аварійно перериває роботу скрипту в середині транзакції без прибирання тимчасових ресурсів.

Цей сценарій є типовим інженерним глухим кутом. Командна оболонка Unix створювалася як інтерактивне середовище та мова макрокомпозиції готових виконуваних файлів, а не як мова програмування загального призначення (*general-purpose programming language*, від лат. *generalis* — загальний). Розуміння фундаментальних фізичних меж оболонки — від моделі пам'яті до вартості створення процесів ядром Linux — дозволяє інженеру вчасно зупинити ускладнення Bash-скриптів і перенести логіку в типізовані, контрольовані мови програмування (Python, Go, Rust або C++).

## Природна ніша командної оболонки

Командна оболонка (Bourne Shell `sh`, Bourne-Again Shell `bash`, Debian Almquist Shell `dash`) володіє синтаксичними властивостями, які роблять її неперевершеною для певного класу завдань. Її головна сила — **оркестрація процесів** (*process orchestration*, від грец. *orchestes* — керівник руху) та потокове перенаправлення дескрипторів вводу-виводу.

Коли інженер виконує команду:

```bash
cat /var/log/nginx/access.log | grep -E 'HTTP/1.1" 5[0-9]{2}' | awk '{print $1}' | sort | uniq -c | sort -nr
```

оболонка виконує винятково диспетчерські функції:
1. Створює шість дочірніх процесів через системні виклики `fork(2)`.
2. Зв'язує їхні стандартні потоки через анонімні односпрямовані канали ядра `pipe(2)`.
3. Замінює образ пам'яті кожного процесу відповідним бінарником через `execve(2)`.
4. Очікує завершення виконання через `waitpid(2)`.

Уся реальна робота з обробки гігабайтів даних відбувається всередині скомпільованих та високоефективних програм (`grep`, `awk`, `sort`), які використовують векторизовані інструкції CPU (AVX/SSE) та оптимізовані алгоритми сортування на диску. Оболонка тут виступає клеєм, витрачаючи менше ніж 0.1% процесорного часу на організацію конвеєра.

```
┌──────────┐ stdout   ┌──────────┐ stdout   ┌──────────┐ stdout   ┌──────────┐
│   cat    │ ───────> │   grep   │ ───────> │   awk    │ ───────> │   sort   │
└──────────┘ pipe(2)  └──────────┘ pipe(2)  └──────────┘ pipe(2)  └──────────┘
```

Оболонка є оптимальним вибором тоді й тільки тоді, коли:
- Завдання є суто лінійним ланцюгом запуску 3–10 готових утиліт.
- Логіка керування потоком виконання зводиться до простих умов «якщо попередня команда завершилась із кодом 0, виконати наступну».
- Дані передаються великими неперервними потоками через системні канали без необхідності їхньої інтерпретації, розбору на вкладені об'єкти чи перевірки типів.
- Загальний обсяг коду сценарію не перевищує 50–100 рядків.

Щойно характер задачі зміщується від зовнішньої координації утиліт до внутрішньої обробки бізнес-логіки (парсинг структур даних, математичні обчислення, керування паралельними воркерами, робота з бінарними протоколами), природні переваги оболонки обертаються фундаментальними обмеженнями.

## Технічні та архітектурні обмеження мови Shell

### 1. Нетипізована рядкова модель (Untyped String Model)

У мовах програмування загального призначення середовище виконання оперує багатим набором фундаментальних і складених типів: цілі 64-бітні числа, числа з плаваючою крапкою, булеві значення, вказівники, структури, списки, словники та інтерфейси. Пам'ять структурується у вигляді компактних стек-фреймів та адресованих купових блоків (*heap*).

В оболонці Shell **усі дані є байтовими рядками** (*byte strings*). Змінна `x=42` не є 32-бітним чи 64-бітним цілим числом у регістрі процесора — це послідовність двох символів ASCII (байти `0x34` та `0x32`), що закінчується нульовим байтом.

```
Bash:
x=42          →  [ '4' (0x34) ] [ '2' (0x32) ] [ '\0' (0x00) ]  (рядок у пам'яті)

C++ / Go:
int64_t x = 42;  →  [ 0x2A 0x00 0x00 0x00 0x00 0x00 0x00 0x00 ]  (машинне слово в регістрі)
```

Це фундаментальне обмеження породжує низку критичних проблем:

- **Відсутність вкладених структур даних**: у стандарті POSIX `sh` немає навіть одновимірних масивів — лише позиційні параметри `$1`, `$2`, `"$@"`. У Bash 4+ з'явилися індексовані та асоціативні масиви (`declare -A map`), проте вони залишаються виключно пласькими таблицями пар «рядок → рядок». Створити масив структур, матрицю, дерево, граф чи список словників `List[Dict[str, Any]]` в оболонці фізично неможливо.
- **Втрата типів при міжфункціональній передачі**: функції в оболонці не можуть повертати значення складених типів. Єдині способи повернути дані з функції — або записати їх у глобальну змінну (руйнуючи інкапсуляцію), або надрукувати їх у стандартний вивід `stdout`, що вимагає підстановки команди `result=$(my_func)` із супутнім викликом `fork()`.
- **Автоматичне відсікання кінцевих переведень рядків**: конструкція підстановки команди `$(...)` за специфікацією POSIX безслідно видаляє всі завершальні символи переведення рядка `\n`. Якщо результат команди містить порожні рядки в кінці або бінарні дані з завершальними нулями чи переведеннями рядків, вони непомітно спотворюються при присвоєнні змінній.
- **Неможливість роботи з довільними бінарними даними**: оскільки змінні оболонки реалізовані як класичні C-рядки (`char*`), вони не можуть містити нульовий байт (`\0`, `NUL`). Спроба зберегти бінарний файл або результат хешування SHA-256 у змінну Bash призводить до обриву рядка на першому ж нульовому байті або помилки `warning: command substitution: ignored null byte in input`.
- **Ліміт обсягу аргументів (`ARG_MAX`)**: передача великих обсягів даних через аргументи командного рядка чи масиви оболонки обмежена константою ядра Linux `ARG_MAX` (зазвичай від 2 до 6 МБ разом зі змінними оточення) та `MAX_ARG_STRLEN` (128 КБ на один аргумент). Спроба передати великий список файлів у команду `cmd "${ARRAY[@]}"` завершується системною помилкою `E2BIG` (*Argument list too long*).

![Порівняння архітектури пам'яті: конвеєр оболонки з байтовими потоками проти єдиного адресного простору з типізованими структурами](/root/course/unix/when-to-leave-the-shell/img/shell-vs-native-architecture.svg)
*Архітектурні відмінності: конвеєр оболонки вимагає постійної текстової серіалізації через IPC-канали, тоді як нативна програма зберігає прямий доступ до типізованих об'єктів у RAM.*

### 2. Небезпека підстановки: поділ на слова, глоб та ін'єкції

Кожна змінна в командному рядку оболонки проходить через багатоетапний конвеєр текстового переписування. Якщо розробник не захистив змінну подвійними лапками `"$var"`, оболонка автоматично застосовує до результату підстановки дві руйнівні фази: **поділ на слова** (*Word Splitting* за змінною `IFS`) та **розгортання імен файлів** (*Globbing / Pathname Expansion*).

Розгляньмо класичну катастрофу видалення тимчасових даних:

```bash
# Небезпечний сценарій очищення робочого каталогу
CLEANUP_DIR="/var/cache/app data"
rm -rf $CLEANUP_DIR/*
```

Якщо змінна `$CLEANUP_DIR` містить пробіл або з якихось причин виявилася порожньою (наприклад, помилка в попередній команді):
1. Вираз `$CLEANUP_DIR` розкривається в порожній рядок.
2. Команда перетворюється на `rm -rf /*`.
3. Операційна система починає рекурсивне знищення всіх файлів у кореневому каталозі `/`.

Навіть якщо змінна містить правильний шлях `/var/cache/app data`, відсутність лапок розриває рядок за пробілом на два незалежні аргументи: `/var/cache/app` та `data/*`. У результаті утиліта `rm` видаляє каталог іншої програми `/var/cache/app`, а потім повідомляє про помилку відсутності шляху `data/*`.

#### Ін'єкція параметрів через імена файлів (Option Injection)

Ще одна витончена небезпека виникає при обробці файлів із масками `*`. Якщо зловмисник або сторонній процес створить у каталозі файл із назвою `-rf` або `--checkpoint-action=exec=sh shell.sh`, звичайний виклик `tar -cf archive.tar *` або `rm *` інтерпретує ім'я файлу як **опцію командного рядка**, а не як позиційний аргумент. У результаті `tar` виконає довільну команду зловмисника з правами поточного користувача. Щоб запобігти цьому, кожен виклик утиліт в оболонці вимагає використання захисного роздільника `--` (наприклад, `rm -- "$file"`), про що розробники часто забувають.

#### Пастки локалей і сортування (`LC_COLLATE`)

Поведінка діапазонів у регулярних виразах та глоб-шаблонах `[a-z]` в оболонці залежить від поточної локалі системи (`LC_COLLATE` / `LC_ALL`). В англомовних локалях (`en_US.UTF-8`) порядок сортування часто є словниковим (`aAbBcCdD...`), через що вираз `[a-z]` неочікувано включає великі літери від `B` до `Z`. Лише встановлення суворого стандарту `LC_ALL=C` повертає очікуване побайтове порівняння за кодами ASCII.

Ще небезпечнішим є використання оператора `eval` або динамічне формування рядків для інтерпретатора. Спроба обробити параметри з неперевірених джерел (користувацький ввід, заголовки HTTP-запитів, назви Git-гілок) перетворює будь-яку оболонку на джерело вразливостей виконання довільного коду (*Command Injection*):

```bash
# Вразливий код динамічного виконання
BRANCH_NAME="main; rm -rf / #"
eval "git checkout $BRANCH_NAME"
```

У мовах зі статичною або строгою типізацією (Python, Go, C++) виклики зовнішніх процесів здійснюються передачею фіксованого вектора рядків `argv[]` безпосередньо системному виклику ядра, де пробіли чи спецсимволи ніколи не інтерпретуються як синтаксичні роздільники:

:::tabs
```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

/* Безпечний запуск процесу в C без участі оболонки */
int safe_exec_c(const char *branch) {
    pid_t pid = fork();
    if (pid == 0) {
        /* Масив argv передається безпосередньо ядру: спецсимволи не інтерпретуються */
        char *const argv[] = {"git", "checkout", (char *)branch, NULL};
        execvp("git", argv);
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);
    return WIFEXITED(status) ? WEXITSTATUS(status) : -1;
}
```
```cpp
#include <unistd.h>
#include <sys/wait.h>
#include <string>
#include <vector>
#include <span>
#include <system_error>

/* Безпечний запуск процесу в ідіоматичному C++20 */
int safe_exec_cpp(const std::string& branch) {
    pid_t pid = fork();
    if (pid == 0) {
        std::vector<const char*> argv = {"git", "checkout", branch.c_str(), nullptr};
        execvp("git", const_cast<char* const*>(argv.data()));
        _exit(127);
    }
    if (pid < 0) {
        throw std::system_error(errno, std::generic_category(), "fork failed");
    }
    int status = 0;
    waitpid(pid, &status, 0);
    return WIFEXITED(status) ? WEXITSTATUS(status) : -1;
}
```

### 3. Продуктивність: ціна створення процесу fork() + exec()

Коли розробник пише цикл мовою загального призначення (Python, Go, Rust, C++), кожна ітерація циклу виконується безпосередньо процесором у просторі користувача: змінюються значення в регістрах або локальному стеку. Час однієї ітерації вимірюється в **наносекундах**.

В оболонці Bash будь-яка операція, що виходить за межі найпростіших вбудованих конструкцій (`builtins`), вимагає запуску окремого зовнішнього процесу через системні виклики `fork(2)` (або `clone(2)`) та `execve(2)`.

```bash
# Катастрофічно повільний цикл на Bash: 10 000 викликів fork/exec
TOTAL=0
for i in $(seq 1 10000); do
    # На кожній ітерації викликається зовнішня утиліта bc
    TOTAL=$(echo "$TOTAL + $i" | bc)
done
```

![Порівняння накладних витрат: системний конвеєр fork/exec проти нативного виконання всередині єдиного процесу](/root/course/unix/when-to-leave-the-shell/img/fork-exec-overhead.svg)
*Накладні витрати: кожна ітерація зовнішньої команди в Bash змушує ядро дублювати пам'ять і викликати динамічний лінкер, тоді як нативний цикл виконується в кеші процесора.*

Розгляньмо, що насправді відбувається всередині ядра Linux під час кожного виконання виразу `$(echo "$TOTAL + $i" | bc)`:
1. **Системний виклик `fork()` / `clone()`**:
   - Ядро виділяє нову структуру дескриптора процесу `task_struct` та виділяє новий ідентифікатор PID.
   - Викликається внутрішня функція ядра `dup_mmap()`, яка проходить по всіх областях віртуальної пам'яті (VMA) батьківського процесу і дублює багаторівневі таблиці сторінок пам'яті (*Page Global Directory*, PGD/P4D/PUD/PMD/PTE).
   - Усі сторінки пам'яті позначаються як спільні лише для читання з механізмом копіювання при записі (*Copy-on-Write*, CoW).
2. **Системний виклик `pipe()`**: ядро виділяє кільцевий буфер розміром 64 КБ у пам'яті ядра та створює два нові файлові дескриптори.
3. **Системний виклик `execve()`**:
   - Ядро повністю звільняє щойно скопійовані структури віртуальної пам'яті дочірнього процесу.
   - Парсить ELF-заголовок бінарника `/usr/bin/bc`, зчитує заголовок програми `PT_INTERP` і знаходить динамічний компонувальник `/lib64/ld-linux-x86-64.so.2`.
   - Динамічний лінкер відображає в адресний простір залежні бібліотеки (`libc.so.6`, `libm.so.6`) через системні виклики `mmap(2)`.
   - Виконується релокація символів у таблицях GOT/PLT та запускаються функції ініціалізації з масиву `.init_array`.
4. **Виконання додавання**: утиліта `bc` зчитує вхідні байти з каналу, виконує додавання за 20 наносекунд і записує результат у `stdout`.
5. **Завершення `exit()`**: процес знищує свій адресний простір, ядро надсилає батьківському процесу сигнал `SIGCHLD` і переводить процес у стан зомбі (*zombie process*).
6. **Батьківський процес `waitpid()`**: оболонка зчитує код завершення з ядра, ядро звільняє `task_struct`, оболонка закриває дескриптори каналу і повертається до парсингу наступного токена.

На сучасному серверному процесорі пара викликів `fork()` + `execve()` займає від **0.5 до 2.5 мілісекунд**. Для 10 000 ітерацій:
- **Bash з викликами `bc`**: `10 000 × 2 мс ≈ 20–30 секунд` суцільного навантаження на ядро Linux, постійного скидання кешу TLB (*Translation Lookaside Buffer*) та перемикання контексту (*context switching*).
- **Python**: `sum(range(1, 10001))` виконується за **0.3 мілісекунди** (у 70 000 разів швидше).
- **C++ / Go / Rust**: цикл виконується за **2–5 мікросекунд** або оптимізується компілятором у формулу `n*(n+1)/2` за 0 наносекунд на етапі компіляції.

Повна зведена таблиця характеристик усіх технологічних стеків представлена в [порівняльній матриці системних мов](root:unix/when-to-leave-the-shell/comp-shell-vs-compiled-languages.md).

### 4. Обробка структурованих форматів (JSON, YAML, XML)

Сучасні середовища Unix глибоко інтегровані з вебсервісами, контейнерами (Docker, Kubernetes) та хмарними платформами, де основним форматом передачі даних є JSON та YAML.

Оболонка не має вбудованих засобів для роботи зі структурованим текстом. Інженери змушені вдаватися до двох підходів:

#### Підхід А: Крихкий парсинг регулярними виразами (`grep`, `sed`, `awk`)

```bash
# Небезпечна спроба витягти IP-адресу з JSON
IP=$(cat response.json | grep '"ip":' | sed 's/.*"ip": *"//;s/".*//')
```

Цей код ламається при найменшій зміні форматування JSON: якщо ключ `"ip"` містить пробіли навколо двокрапки, якщо рядок розбито на кілька рядків, якщо значення містить екрановані лапки `\"` або якщо поле `"ip"` з'явилося всередині вкладеного об'єкта, де воно має інше значення.

#### Підхід Б: Використання зовнішньої утиліти `jq`

Утиліта `jq` є повноцінним процесором JSON, проте її інтеграція в Bash-скрипти супроводжується значними накладними витратами:
- Кожен запит до `jq` у циклі створює новий процес `fork() + exec()`.
- Передача змінних оболонки в `jq` вимагає складного синтаксису екранування через прапорець `--arg var "$val"`.
- Обробка списків об'єктів вимагає серіалізації у формат TSV або Base64, щоб уникнути втрати структури при читанні через цикл `while IFS= read -r line`.

У мовах загального призначення розбір JSON виконується нативними серіалізаторами з перевіркою схеми та миттєвим перетворенням у типізовані структури в пам'яті:

```python
import json
from dataclasses import dataclass

@dataclass
class ServerConfig:
    host: str
    port: int
    enabled: bool

# Надійний парсинг із суворою перевіркою типів
data = json.loads(payload_str)
config = ServerConfig(host=data["host"], port=int(data["port"]), enabled=bool(data["enabled"]))
```

### 5. Обробка помилок, керованість і тестування

Надійність системного сценарію визначається його поведінкою у позаштатних ситуаціях: аварійне завершення зовнішньої програми, переповнення диска, відмова мережі, отримання сигналу `SIGTERM` від системи ініціалізації (systemd/Kubernetes).

В оболонці стандартом «надійного сценарію» вважається режим:

```bash
set -euo pipefail
trap cleanup EXIT INT TERM
```

Проте прапорець `set -e` (*errexit*) у POSIX та Bash містить десятки прихованих винятків, де помилка мовчки ігнорується або призводить до некоректного завершення:
- **Ігнорування в умовах**: помилка всередині умови `if failing_cmd; then ...` не активує `set -e`.
- **Ігнорування у списках або-і**: помилка в лівій частині оператора `failing_cmd || true` не зупиняє скрипт, навіть якщо впав критичний системний виклик створення каталогу чи монтування диска.
- **Арифметичні помилки**: помилка ділення на нуль в арифметичному виразі `$(( 10 / 0 ))` у багатьох версіях Bash не перехоплюється блоком `trap` і може мовчки повертати `0`.
- **Скидання коду завершення командою `local`**: вираз `local result=$(failing_cmd)` **скидає помилку**, оскільки сама вбудована команда `local` успішно виділяє пам'ять під змінну і повертає статус `0`.
- **Сигнали `SIGPIPE` у конвеєрах**: утиліта `head -n 10` закриває вхідний канал після зчитування 10 рядків. Попередня команда в конвеєрі при наступній спробі запису отримує від ядра сигнал `SIGPIPE` і завершується з кодом `141` (`128 + 13`). При увімкненій опції `set -o pipefail` весь конвеєр вважається аварійно завершеним, що змушує писати штучні обгортки.
- **Втрата пасток у підоболонках**: обробники `trap` не успадковуються автоматично підоболонками `(...)` та функціями, якщо не увімкнено специфічні прапорці `set -E` (*errtrace*) та `set -T` (*functrace*).

```bash
# Класична пастка: set -e НЕ спрацьовує через команду local
set -e
my_function() {
    local result=$(false)  # false повертає 1, але local повертає 0!
    echo "Код продовжує виконання попри помилку!"
}
my_function
```

Крім того, оболонка позбавлена структурованих засобів модульного тестування (*Unit Testing*). Спроби використовувати фреймворки на кшталт `bats` або `shunit2` вимагають мокування системних бінарників через підміну каталогу `$PATH`, що є вкрай крихким і повільним підходом. Статичний аналізатор `ShellCheck` є чудовим інструментом для пошуку пропущених лапок, проте він фізично не здатний перевірити типи переданих даних, правильність структури JSON чи наявність взаємних блокувань (*deadlocks*).

У той самий час Python (`pytest`, `unittest.mock`), Go (`testing`), Rust (`cargo test`) та C++ (`GTest`) надають розвинені засоби ізоляції компонентів, вимірювання покриття коду (*code coverage*) та перевірки граничних значень.

Детальний приклад переписування складного сценарію з усуненням усіх перелічених вад наведено в [практиці міграції на Python та Go](root:unix/when-to-leave-the-shell/proj-shell-to-python-migration.md).

## Матриця прийняття рішень: коли виходити зі Shell

Щоб уникнути накопичення технічного боргу, інженерні команди застосовують формалізовані критерії переходу з командної оболонки на мови загального призначення.

![Інженерне дерево прийняття рішень: чіткі критерії виходу з shell до мов Python, Go, Rust та C++](/root/course/unix/when-to-leave-the-shell/img/decision-matrix.svg)
*Дерево прийняття рішень: оцінка складності за обсягом коду, структурами даних, математикою, паралелізмом та вимогами до деплою.*

### Інженерні пороги міграції

1. **Критерій обсягу (100–200 рядків коду)**:
   Якщо сценарій перевищує 150 рядків процедурного коду або містить понад 5 користувацьких функцій, його підтримка мовою Shell стає дорожчою за написання аналога на Python чи Go.

2. **Критерій структур даних**:
   Щойно виникає потреба зберегти зв'язку «об'єкт зі списком вкладених полів», використати багатовимірні масиви або опрацювати JSON/YAML без втрати типів — це однозначний сигнал до виходу зі Shell.

3. **Критерій математичних операцій**:
   Необхідність обчислення дробових чисел (`float`), статистичних перцентилів (p50, p99), середньоквадратичного відхилення чи тригонометрії без виклику зовнішніх утиліт.

4. **Критерій паралелізму та ресурсів**:
   Необхідність організації пулу воркерів (*worker pool*) із чергою завдань, обмеженням споживання пам'яті, м'ютексами (*mutex*) для захисту спільних ресурсів та обробкою сигналів graceful shutdown.

5. **Критерій тестування та критичності (Mission Critical)**:
   Якщо відмова сценарію зупиняє виробничий конвеєр або призводить до втрати фінансових чи клієнтських даних, код зобов'язаний мати 100% покриття модульними тестами, статичний аналіз типів та детерміністичну обробку винятків.

## Вибір мови на заміну

Вибір конкретної мови на заміну Shell залежить від цільового оточення, вимог до дистрибуції та необхідної продуктивності.

### 1. Python: швидкість розробки та багатство бібліотек

Python є найприроднішим наступником для більшості administrative та DevOps-сценаріїв:
- **Швидкість розробки**: код пишеться так само швидко, як і скрипт Bash, але володіє строгою динамічною типізацією та читабельним синтаксисом.
- **Стандартна бібліотека**: модулі `pathlib`, `subprocess`, `concurrent.futures`, `json`, `sqlite3`, `tempfile`, `argparse` покривають 95% системних потреб без встановлення сторонніх пакетів `pip`.
- **Ідеальна ніша**: сервісні інструменти, обробка звітів, інтеграція з REST API, автоматизація хмарної інфраструктури (AWS, GCP, Kubernetes).

### 2. Go: автономні CLI-утиліти та легковажний паралелізм

Go ідеально підходить для створення інструментів, які мають запускатися на сотнях серверів без налаштування оточення:
- **Єдиний статичний двійковий файл**: результат компіляції (`go build`) не має зовнішніх залежностей від бібліотек чи версій інтерпретатора. Достатньо скопіювати один файл у систему.
- **Вбудований паралелізм**: горутини (*goroutines*) займають лише 2–4 КБ пам'яті на старті, що дозволяє легко запускати десятки тисяч паралельних операцій опитування мережі.
- **Ідеальна ніша**: мережеві сканери, демони збору метрик, інструменти розгортання, заміни важких системних скриптів у контейнерах Alpine/Scratch.

### 3. Rust та C++: безкомпромісна продуктивність і низькорівневий контроль

Rust та C++ застосовуються там, де потрібен максимальний контроль над апаратними ресурсами:
- **Відсутність збирача сміття (GC)**: детерміністичне споживання пам'яті та нульові паузи виконання.
- **Пряма взаємодія з ядром**: робота з сокетами `io_uring`, фільтрами `eBPF`, пряме відображення пам'яті `mmap(2)` та обробка гігабайтних потоків даних у реальному часі.
- **Ідеальна ніша**: високонавантажені системні фільтри (аналоги `ripgrep`, `fd`), низькорівневі мережеві утиліти, компоненти вбудованих Linux-систем із жорсткими лімітами пам'яті (8–32 МБ).

## Підсумковий інженерний висновок

Командна оболонка Unix залишається неперевершеним інструментом для швидкого інтерактивного керування сервером і коротких лінійних конвеєрів із готових утиліт. Проте намагання перетворити Bash на мову для реалізації складної бізнес-логіки неминуче впирається у фундаментальні фізичні обмеження: текстову нетипізовану модель пам'яті, дорожнечу системних викликів `fork/exec` та крихкість обробки помилок.

Своєчасний перехід на мови загального призначення (Python для швидкої та гнучкої автоматизації, Go для автономних бінарників та паралелізму, Rust/C++ для максимальної швидкості) забезпечує високу надійність інфраструктури, детерміністичну поведінку у критичних ситуаціях та простоту масштабування коду.
