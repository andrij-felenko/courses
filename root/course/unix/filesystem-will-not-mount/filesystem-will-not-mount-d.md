# ФС не монтується: розбір за моделлю

<preknowlist>
- [VFS](root:sys-unix/vfs-layer) — шар віртуальної файлової системи, роль структур `inode`, `dentry` та `super_block`.
- [Блоковий пристрій](root:sys-unix/block-device-model) — сектори, блоки, черги запитів та операції прямого доступу.
- [Журналювання](root:sys-unix/journaling-consistency) — транзакційний журнал (WAL), фази фіксації та відтворення транзакцій (replay).
- [Device mapper](root:sys-unix/device-mapper) — стек віртуальних блокових пристроїв: LVM, dm-crypt і блокування носіїв.
</preknowlist>

Під час завантаження серверного вузла після аварійного відключення електроживлення системний менеджер systemd ініціалізує монтування дискових розділів. На етапі виконання команди `mount /dev/nvme0n1p2 /data` процес раптово завершується з ненульовим кодом повернення, виводячи в консоль загальне повідомлення: `mount: /data: wrong fs type, bad option, bad superblock on /dev/nvme0n1p2, missing codepage or helper program, or other error`. Завантаження негайно блокується, служба `local-fs.target` переходить у стан аварії, а сервер зупиняється в консолі аварійного відновлення `emergency.target`.

Це консольне повідомлення є узагальненим текстом-парасолькою бібліотеки `libmount`, який простір користувача повертає у відповідь на системну помилку `EINVAL` (код 22). За цим єдиним рядком ховаються понад десять принципово різних апаратних і програмних причин: від спотворення контрольної суми первинного суперблоку диска до несумісних прапорців журналювання JBD2, блокування розділу підсистемою LVM чи помилки в синтаксисі конфігураційного файлу `/etc/fstab`.

Щоб безпечно відновити доступ до файлів без ризику остаточно знищити метадані, інженер повинен розглядати монтування не як разову дію утиліти `mount(8)`, а як детермінований п'ятифазний конвеєр ядра. Будь-який збій на кожній із цих фаз залишає чіткий слід у кодах помилок `errno`, лічильниках блокового рівня та структурах `sysfs`.

![Схема перевірки та реєстрації суперблоку у ядрі під час системного виклику mount](/root/course/unix/filesystem-will-not-mount/img/mount-kernel-pipeline.svg)
*Послідовність операцій системного виклику mount(2) у ядрі: від VFS та пошуку драйвера ФС до валідації магічного числа суперблоку, відтворення журналу транзакцій і реєстрації точки монтування.*

## Анатомія системного виклику `mount(2)` та конвеєр VFS

Коли утиліта монтування виконує системний виклик `mount(source, target, fstype, flags, data)`, процесор перемикається в простір ядра, де керування передається функції `do_mount()`, яка в сучасних версіях ядра транслюється у виклик `path_mount()`. Процес реєстрації нової файлової системи у віртуальній структурі VFS проходить п'ять послідовних стадій:

1. **Валідація прав та шляхів у просторі імен:** Ядро перевіряє, чи володіє викликаючий процес адміністративним привілеєм `CAP_SYS_ADMIN` у поточному просторі імен користувача (*User Namespace*). За допомогою функції `user_path_at()` ядро розбирає шлях `target`, перевіряє існування каталогу точки монтування та виділяє ексклюзивне блокування на рівні структури дерева каталогів `dentry`.
2. **Ексклюзивне захоплення блокового пристрою (`FMODE_EXCL`):** Для файлових систем на базі фізичних або віртуальних дисків ядро викликає функцію `blkdev_get_by_path()` із прапорцем ексклюзивного доступу `FMODE_EXCL`. Підсистема блокового вводу-виводу перевіряє внутрішнє поле `bdev->bd_holder`. Якщо цей блоковий пристрій уже захоплений іншим екземпляром файлової системи, активним RAID-масивом чи томом LVM, ядро відмовляється створювати повторне захоплення й негайно перериває виклик із кодом помилки `EBUSY`.
3. **Пошук драйвера файлової системи:** За текстовим рядком `fstype` функція `get_fs_type()` сканує глобальний зв'язаний список зареєстрованих структур `struct file_system_type`. Якщо потрібний модуль ядра (наприклад, `ext4` або `xfs`) не завантажений в оперативну пам'ять, ядро робить спробу автоматичного завантаження через механізм `request_module()`. Якщо драйвер відсутній серед скомпільованих модулів поточного ядра, виклик повертає код `ENODEV`.
4. **Зчитування та валідація дискового суперблоку:** Драйвер файлової системи виділяє структуру пам'яті `struct super_block` і викликає внутрішню функцію наповнення суперблоку (`fill_super()`, наприклад, `ext4_fill_super()` або `xfs_fs_fill_super()`). Драйвер надсилає команду блокового зчитування `sb_bread()` для отримання початкових секторів пристрою.
5. **Відтворення журналу та підключення до простору імен:** Якщо суперблок містить прапорець нечистого завершення роботи, драйвер запускає процедуру відтворення транзакційного журналу (*Journal Replay*). Після успішної перевірки ядро створює екземпляр `struct vfsmount`, виділяє кореневий `struct dentry` для кореневого індексного дескриптора (inode 2 для Ext4), підв'язує його до цільового каталогу функцією `attach_recursive_mnt()` і оновлює системну таблицю `/proc/self/mountinfo`.

Детальні сигнатури нового компонованого Mount API Linux (`fsopen()`, `fsconfig()`, `fsmount()`) та повну матрицю прапорців `mountflags` наведено в довіднику [api-mount-diagnostics.md](root:unix/filesystem-will-not-mount/api-mount-diagnostics.md).

### Механізм перевірки суперблоку в пам'яті та на диску

Суперблок є кореневим паспортом файлової системи. Він зберігає фундаментальні константи геометрії: розмір блоку даних, загальну кількість блоків та індексних дескрипторів (*inode*), стан узгодженості, бітові маски сумісності розширень та контрольні суми.

Коли функція `fill_super()` зчитує байти з блокового пристрою в буферний кеш ядра, вона виконує сувору поетапну валідацію:

```
Послідовність валідації полів структури super_block:
├── 1. Magic Number Check:   Чи збігається сигнатура (0xEF53 для Ext4, 0x58465342 для XFS)?
├── 2. Block Size Check:     Чи є розмір блоку степенем двійки (1024, 2048, 4096, 65536)?
├── 3. Incompat Flags Check: Чи підтримує поточне ядро всі активні прапорці s_feature_incompat?
├── 4. CRC32C Checksum:      Чи збігається контрольна сума заголовка з дисковим значенням?
└── 5. Journal State Check:   Чи узгоджений журнал і чи дозволено його відтворення (Replay)?
```

Якщо бодай одна з цих перевірок зазнає невдачі, ядро відмовляється створювати об'єкт `struct super_block`, звільняє ексклюзивне захоплення блокового пристрою, вивантажує кешовані сторінки й повертає у простір користувача системну помилку `EINVAL` або `EIO`.

## Діагностична матриця типових збоїв монтування

Усі відмови системного виклику `mount(2)` чітко класифікуються за кодами помилок ядра `errno`. Розуміння внутрішнього механізму кожної помилки дозволяє негайно локалізувати несправність без хаотичного перебору параметрів.

![Діагностичне дерево розбору причин збою монтування файлової системи](/root/course/unix/filesystem-will-not-mount/img/mount-failure-decision-tree.svg)
*Діагностична матриця типових помилок mount(8): класифікація за кодами errno (EINVAL, EBUSY, ENODEV, EIO), джерелами блокування (LVM, процеси) та кроками системного відновлення.*

### 1. Помилка `EINVAL`: пошкодження основного суперблоку та відновлення через резервні копії

Помилка `EINVAL` (код 22, у виводі утиліти `mount` — `wrong fs type, bad option, bad superblock`) виникає в трьох типових ситуаціях:
* Первинний суперблок на початку носія пошкоджено через збій фізичних секторів LBA або випадковий запис нулів/сміття (наприклад, виконання `dd` на початок неправильного диска);
* Таблиця розділів (GPT або MBR) була перестворена зі зміщеним початковим сектором, через що ядро шукає суперблок за неправильною абсолютною адресою LBA;
* У командному рядку або в `/etc/fstab` передано опцію монтування, яку поточна версія драйвера файлової системи не підтримує чи вважає застарілою;
* Файлова система була створена на новішому ядрі з увімкненими прапорцями `s_feature_incompat`, які старіше ядро корпоративного дистрибутива не вміє інтерпретувати (наприклад, прапорець `orphan_file` `0x2000` або `fast_commit` `0x8000`).

#### Геометрія суперблоків Ext4 та механізм `sparse_super`

Файлова система Ext4 розбиває весь дисковий простір на рівні групи блоків (*Block Groups*), стандартний розмір яких при блоці 4 КіБ становить 32 768 блоків (128 МіБ).

Основний суперблок розташований у Групі 0 за фіксованим зміщенням 1024 байти від початку розділу. Перші 1024 байти навмисно зарезервовані для завантажувального сектора x86/MBR. Якби суперблок існував в єдиному екземплярі, пошкодження першого 4-кілобайтного блоку диска призвело б до безповоротної втрати доступу до всіх файлів на томі.

Для захисту від таких аварій Ext4 підтримує механізм розрідженого резервування суперблоків `sparse_super`. Резервні дублікати суперблоку та дескрипторів груп зберігаються лише в тих групах блоків, номери яких є степенями чисел 3, 5 та 7 (а саме в групах 0, 1, 3, 5, 7, 9, 25, 49, 81...).

![Розташування основного та резервних суперблоків у файловій системі Ext4](/root/course/unix/filesystem-will-not-mount/img/ext4-superblock-geometry.svg)
*Геометрія груп блоків Ext4: зміщення первинного суперблоку (1024 байти) та резервних копій у групах 1, 3, 5, 7, 9 за механізмом sparse_super, що використовуються для відновлення через e2fsck -b.*

#### Розрахунок зміщення та відновлення через `e2fsck -b`

Якщо розмір блоку становить 4096 байтів (`s_log_block_size = 2`), номер першого резервного блоку в Групі 1 обчислюється множенням індексу групи на кількість блоків у групі:

```
Номер блоку резервного суперблоку в Групі 1:
Блок = 1 · 32 768 = 32 768

Зміщення у байтах на диску:
Зміщення = 32 768 · 4096 = 134 217 728 байтів (128 МіБ)

Номер блоку в Групі 3:
Блок = 3 · 32 768 = 98 304 (Зміщення = 402 653 184 байтів / 384 МіБ)

Номер блоку в Групі 5:
Блок = 5 · 32 768 = 163 840 (Зміщення = 671 088 640 байтів / 640 МіБ)
```

Якщо первинний суперблок пошкоджено і `mount` повертає `EINVAL`, системний адміністратор визначає точні адреси резервних суперблоків у режимі симуляції створення ФС (без запису на носій):

```bash
# Симуляція розмітки для визначення номерів резервних суперблоків
mke2fs -n -b 4096 /dev/sdb1

# Або прямий перегляд заголовків утилітою dumpe2fs
dumpe2fs /dev/sdb1 | grep -i "superblock"
```

Отримавши номер валідного резервного блоку (наприклад, 32768), запускають процедуру відновлення:

```bash
# Відновлення файлової системи за допомогою резервного суперблоку з Групи 1
e2fsck -b 32768 -y /dev/sdb1
```

Утиліта `e2fsck` зчитує неушкоджені метадані з блоку 32768, валідує таблиці дескрипторів груп, перевіряє цілісність дерева каталогів і записує відновлений суперблок назад у Групу 0 (зміщення 1024 байти). Після цього диск успішно монтується стандартним викликом `mount`.

Практичну реалізацію утиліти, яка перевіряє ексклюзивні блокування та автоматично сканує резервні суперблоки, наведено в проектній вставці [proj-superblock-scanner.md](root:unix/filesystem-will-not-mount/proj-superblock-scanner.md).

### 2. Помилка `EBUSY`: конфлікт дескрипторів, холдери ядра та Device Mapper

Помилка `EBUSY` (код 16, у виводі `mount` — `target is busy` або `device or resource busy`) свідчить про наявність активного блокування в одній із двох незалежних точок:

#### Сценарій А: Блокування точки монтування (Target Busy)
Каталог точки монтування не може бути заміщений новим деревом VFS, якщо:
1. Будь-який процес у системі утримує відкритий файловий дескриптор файлу всередині цього каталогу;
2. Поточний робочий каталог (*Current Working Directory*, `cwd`) процесу перебуває всередині цього піддерева;
3. Усередині цього каталогу вже змонтовано іншу файлову систему.

Діагностика здійснюється утилітами `fuser` та `lsof`:

```bash
# Перегляд процесів, що блокують точку монтування /mnt/data
fuser -vm /mnt/data

# Детальний список відкритих дескрипторів файлів у точці
lsof +f -- /mnt/data

# Примусове завершення процесів-блокувальників (SIGKILL)
fuser -kvm -9 /mnt/data
```

#### Сценарій Б: Блокування блокового пристрою (Device Busy / `bd_open_exclusive`)
Коли ядро монтує файлову систему, воно викликає функцію `blkdev_get_by_path(..., FMODE_EXCL, ...)`. Якщо розділ носія вже утримується іншою підсистемою ядра як складова частина вищого рівня абстракції, ядро повертає `EBUSY`.

Типові джерела блокування блокового пристрою:
* **LVM (Logical Volume Manager):** Розділ `/dev/sdb1` було ініціалізовано як фізичний том (*Physical Volume*, PV) і включено в активну групу томів `vg_data`. Спроба змонтувати сирий розділ `/dev/sdb1` замість логічного тому `/dev/mapper/vg_data-lv_storage` викличе `EBUSY`.
* **dm-crypt / LUKS:** Розділ є зашифрованим томом LUKS. Поки том не відкрито утилітою `cryptsetup open`, або навпаки — коли відкритий мапінг `/dev/mapper/secure_data` вже утримує фізичний носій, пряме монтування фізичного `/dev/sdb1` заборонено.
* **Програмний RAID (`mdadm`):** Розділ є активним дзеркалом у масиві `/dev/md0`.
* **Служба Multipath (`multipathd`):** Якщо демон multipath перехопив блоковий пристрій для побудови надлишкових шляхів Fibre Channel або iSCSI, прямий доступ до сирого `/dev/sdX` блокується на користь агрегованого вузла `/dev/mapper/mpathX`.
* **Ледаче відмонтування (`umount -l`):** Якщо адміністратор виконав «lazy unmount», точка монтування зникає з простору імен VFS, але блоковий пристрій залишається заблокованим у ядрі доти, доки останній процес не закриє свої відкриті дескриптори.

Діагностика холдерів ядра виконується через аналіз віртуальної файлової системи `sysfs`:

```bash
# Перевірка холдерів (драйверів ядра, які утримують цей пристрій)
ls -l /sys/class/block/sdb1/holders/

# Якщо у відповідь виведено dm-0, шукаємо відповідне ім'я Device Mapper:
dmsetup info -c
lsblk -f /dev/sdb1
```

Якщо каталог `holders` містить символьне посилання на віртуальний пристрій `dm-0`, це є прямим доказом того, що розділ зайнятий шаром LVM або dm-crypt, і монтувати необхідно саме відповідний кінцевий пристрій `/dev/mapper/...`.

### 3. Помилка `ENODEV`: відсутність модуля ядра та ізоляція в Initramfs

Помилка `ENODEV` (код 19, `mount: unknown filesystem type`) виникає, коли ядро не має зареєстрованого драйвера для запитаного типу файлової системи.

Діагностичний алгоритм перевірки модулів:

```bash
# 1. Перегляд типів файлових систем, зареєстрованих у поточному ядрі
cat /proc/filesystems

# 2. Перевірка завантаженого модуля ядра
lsmod | grep ext4

# 3. Ручне завантаження модуля драйвера
modprobe ext4
modprobe xfs
```

#### Пастка оновлення ядра без перезавантаження
У робочому середовищі часто виникає ситуація: системний оновлювач оновив пакет ядра (наприклад, з версії `6.8.0-31` на `6.8.0-35`) і видалив старі модулі з каталогу `/lib/modules/6.8.0-31-generic/`. Сервер продовжує працювати на старому завантаженому ядрі `6.8.0-31`.

Коли адміністратор підключає зовнішній накопичувач із файловою системою `xfs` або `btrfs`, утиліта `mount` виконує `modprobe xfs`. Утиліта `modprobe` шукає модуль за шляхом `/lib/modules/$(uname -r)/...`, якого на диску вже немає. `modprobe` повертає помилку, і ядро відхиляє виклик `mount(2)` з кодом `ENODEV`.

#### Відмова кореневого монтування в Initramfs
Якщо збій відбувається під час завантаження системи на етапі переходу від початкового рамдиска (*Initramfs*) до кореневого накопичувача (`rootfs`), причиною `unknown filesystem type` є відсутність драйвера ФС або драйвера контролера сховища (`nvme`, `ahci`, `virtio_blk`) у збірці образу `initramfs`.

Для відновлення коректного складу модулів рамдиск перегенеровують за допомогою утиліт `dracut` або `initramfs-tools`:

```bash
# Для дистрибутивів RHEL / Fedora / CentOS:
dracut --force --add-drivers "ext4 xfs nvme virtio_blk" /boot/initramfs-$(uname -r).img $(uname -r)

# Для дистрибутивів Debian / Ubuntu:
update-initramfs -u -k $(uname -r)
```

## Транзакційний журнал: Journal Replay проти пошкодження метаданих

Сучасні файлові системи (Ext4, XFS) забезпечують стійкість до раптових знеструмлень за допомогою транзакційного журналу (WAL). Коли система завершує роботу нештатно, на диску залишаються зафіксовані в журналі транзакції, які ще не були перенесені в основні структури метаданих.

Під час наступного виклику `mount` драйвер ядра виявляє прапорець нечистого стану:
* В Ext4 встановлюється біт `EXT4_FEATURE_INCOMPAT_RECOVER` у полі `s_feature_incompat` суперблоку;
* В XFS перевіряється заголовок транзакційного журналу `xlog`.

У штатному режимі ядро автоматично запускає процедуру **Journal Replay**: зчитує блоки журналу від останнього збереженого чекпоінту до останнього валідного блоку фіксації (*Commit Block*), накочує зміни на блоки каталогів та екстентів, очищає журнал і скидає прапорець відновлення.

```
Схема поведінки ядра під час виявлення брудного журналу:
[Монтування ФС: Прапорець RECOVER активний]
                │
                ├──> Спроба змонтувати в режимі Read-Write:
                │      └──> Ядро автоматично відтворює журнал (Journal Replay).
                │      └──> Якщо журнал пошкоджено (биті блоки JBD2) -> Помилка EIO / EINVAL!
                │
                ├──> Спроба змонтувати звичайним 'mount -o ro':
                │      └──> Ядро відмовляється монтувати (EROFS / EINVAL):
                │           відтворення журналу вимагає запису на диск, що заборонено -o ro!
                │
                └──> Монтування з прапорцем обходу ('-o ro,noload' / '-o ro,norecovery'):
                       └──> Ядро монтує ФС без відтворення журналу.
                       └──> Дані доступні для читання та аварійного бекапу!
```

### Аварійний обхід журналу: опції `noload` та `norecovery`

Якщо сам журнал транзакцій зазнав фізичного пошкодження секторів, або якщо диск монтується з апаратно заблокованого носія (SD-карта з увімкненим перемикачем Lock, LUN у режимі Read-Only на рівні SAN), стандартна спроба змонтувати файлову систему зазнає краху. Навіть команда `mount -o ro /dev/sdb1 /mnt` завершиться помилкою, оскільки процедура Journal Replay зобов'язана виконувати дисковий запис.

Для виходу з цієї пастки ядро підтримує спеціальні прапорці повного відключення журналу:

```bash
# Для файлових систем Ext3 / Ext4 (опція noload):
mount -o ro,noload /dev/sdb1 /mnt/rescue

# Для файлових систем XFS (опція norecovery):
mount -o ro,norecovery /dev/sdb1 /mnt/rescue

# Для файлових систем Btrfs (опції rescue):
mount -o ro,rescue=usebackuproot,nologreplay /dev/sdb1 /mnt/rescue
```

Ці опції наказують драйверу повністю ігнорувати транзакційний журнал і монтувати поточний стан диска як незмінний зліпок. Це дає змогу негайно врятувати критичні файли (створити архів `tar` або передати корисне навантаження через `rsync`) до початку потенційно небезпечних операцій ремонту.

### Ремонт XFS та небезпека прапорця `xfs_repair -L`

Файлова система XFS принципово відрізняється від Ext4 архітектурою відновлення. Утиліта `fsck.xfs` є порожньою заглушкою, яка під час завантаження системи повертає код 0 і нічого не робить, оскільки розробники XFS поклали всю відповідальність за штатні аварії на вбудований у ядро механізм відновлення журналу.

Якщо ядро не може змонтувати том XFS через фатальне пошкодження лога, єдиним інструментом відновлення стає утиліта `xfs_repair`:

```bash
# 1. Перевірка файлової системи XFS у безпечному режимі без запису на диск
xfs_repair -n /dev/sdb1
```

Якщо утиліта виявляє активний невідтворений журнал, вона зупиняє роботу й виводить категоричну вимогу:
`xfs_repair: The filesystem has valuable metadata changes in a log which needs to be replayed. Mount the filesystem to replay the log, and unmount it before re-running xfs_repair. If you are unable to mount the filesystem, then use the -L option to destroy the log and attempt a repair.`

```bash
# 2. Примусове занулення журналу (Force Log Zeroing)
xfs_repair -L /dev/sdb1
```

> ⚠️ **Критична небезпека прапорця `-L`:** Прапорець `-L` (*Force Log Zeroing*) безповоротно очищає весь транзакційний журнал XFS. Усі метадані, транзакції створення файлів, переміщення каталогів та виділення екстентів, які перебували в журналі на момент аварії, **безповоротно знищуються**. Після занулення лога `xfs_repair` змушений примусово перебудовувати дерева простору B-tree, що неминуче призводить до відриву пошкоджених файлів і скидання їхніх залишків у каталог `/lost+found`. Застосовувати `-L` дозволено виключно як останній засіб після створення посекторного бекапу розділу.

## Помилки конфігурації в `/etc/fstab` та аварійний режим (Emergency Mode)

Під час ініціалізації системи менеджер systemd не викликає утиліту `mount(8)` безпосередньо. Натомість спеціальний вбудований компонент `systemd-fstab-generator` зчитує таблицю конфігурації `/etc/fstab` і транслює кожен рядок у динамічний системний юніт монтування `*.mount` (наприклад, рядок для `/data` перетворюється на юніт `data.mount`).

```
Трансляція рядка /etc/fstab у залежності systemd:
Рядок fstab: UUID=4a2f... /data ext4 defaults 0 2
                 │
                 ▼ (systemd-fstab-generator)
Юніт data.mount:
├── [Unit]
│   ├── Before = local-fs.target
│   └── Requires = dev-disk-by\x2duuid-4a2f....device
└── [Install]
    └── WantedBy = local-fs.target
```

За замовчуванням усі файлові системи, вказані в `/etc/fstab` (крім тих, що мають явну опцію `noauto`), стають **жорсткими блокуючими залежностями** (`Requires=`) цільового стану локальних дисків `local-fs.target`.

Якщо під час завантаження виникає одна з типових несправностей:
1. Дисковий розділ було переформатовано, через що змінився його унікальний ідентифікатор `UUID`, а в `/etc/fstab` залишився старий запис;
2. Додатковий фізичний накопичувач (наприклад, внутрішній HDD або знімний USB-диск) фізично відключено від сервера;
3. Мережевий диск (NFS, iSCSI, CephFS) описано в `/etc/fstab` без спеціальних мережевих параметрів, і система намагається змонтувати його до ініціалізації мережевих адаптерів;

Менеджер systemd очікує появи блокового пристрою від служби udev рівно 90 секунд (дефолтний таймаут `job-timeout`). Після вичерпання таймауту юніт `*.mount` переходить у стан `failed`. Оскільки `local-fs.target` вимагає успіху всіх своїх залежностей, завантаження операційної системи **повністю зупиняється**, а керування скидається в `emergency.target` (Emergency Shell).

### Запобігання аваріям: параметри `nofail`, `_netdev` та таймаути

Щоб відключення вторинного некритичного диска не паралізувало роботу всього сервера, конфігурація `/etc/fstab` повинна використовувати захисні директиви:

```
Зразок відмовостійкої конфігурації /etc/fstab:
# 1. Локальний диск з м'якою залежністю (nofail) та коротким таймаутом (5с):
UUID=a1b2c3d4-e5f6-7890-abcd-112233445566 /data ext4 defaults,nofail,x-systemd.device-timeout=5s 0 2

# 2. Мережевий диск NFS з очікуванням підняття мережі:
192.168.1.50:/srv/nfs /mnt/backup nfs defaults,_netdev,nofail,x-systemd.automount 0 0
```

* **Опція `nofail`:** Перетворює жорстку залежність `Requires=` у м'яку залежність `Wants=` для `local-fs.target`. Якщо пристрій відсутній або виклик `mount(2)` повернув помилку, systemd реєструє повідомлення в системному журналі, ігнорує збій і успішно продовжує завантаження решти служб до стану `multi-user.target`.
* **Опція `_netdev`:** Сигналізує генератору fstab, що файлова система потребує активного мережевого з'єднання. Юніт монтування автоматично отримує залежності `After=network-online.target` та `Wants=network-online.target`, що запобігає передчасній спробі підключення до запуску мережевого стека.
* **Директива `x-systemd.device-timeout=5s`:** Зменшує тривалість блокування завантаження з дефолтних 90 секунд до 5 секунд, якщо фізичний диск не відповідає по шині PCIe/SATA.
* **Директива `x-systemd.automount`:** Створює юніт автомонтування (`*.automount`). Каталог монтується ядром через підсистему autofs лише в момент першого реального звернення процесу до файлів у цій точці.

### Алгоритм діагностики та виходу з Emergency Mode

Якщо сервер зупинився в аварійному режимі `emergency.target`, послідовність дій адміністратора виглядає так:

```bash
# 1. Перегляд повідомлень системного журналу для локалізації збійного юніта
journalctl -xb | grep -iE "mount|failed|timed out"

# 2. Перегляд списку юнітів, що завершилися з помилкою
systemctl --failed

# 3. Визначення реальних UUID наявних блокових пристроїв
blkid

# 4. Перевірка синтаксису /etc/fstab та відповідності UUID
cat /etc/fstab

# 5. Тестовий запуск генератора systemd у тимчасовий каталог
/lib/systemd/system-generators/systemd-fstab-generator /tmp/test-generator/
```

Після виправлення помилкового UUID або додавання параметра `nofail` у файлі `/etc/fstab` виконують перезавантаження конфігурації генераторів:

```bash
# Перечитування конфігурації без перезавантаження ОС
systemctl daemon-reload

# Спроба запуску цільового стану
systemctl default
```

## Методологія безпечного ремонту: захист даних перед викликом `fsck`

Будь-яка спроба програмного відновлення файлової системи за допомогою утиліт `e2fsck`, `fsck` або `xfs_repair` є потенційно деструктивною операцією. Якщо пошкодження спричинені апаратною деградацією комірок Flash чи збоями магнітних поверхонь HDD, запуск ремонту може остаточно спотворити дерева екстентів.

### Залізне правило ремонту: категорична заборона запуску на змонтованій ФС

> ⛔ **Категорично заборонено запускати `fsck` або `e2fsck` на змонтованій файловій системі в режимі читання-запису (Read-Write).**

Коли файлова система змонтована в режимі RW, ядро операційної системи активно кешує дискові структури в оперативній пам'яті (сторінковий кеш, dentry cache, inode cache) і періодично скидає модифіковані блоки на носій через фонові flusher-потоки `wb_workfn`.

Якщо в цей самий момент паралельно запустити утиліту `e2fsck`, яка напряму модифікує ті самі LBA-сектори через сирий блоковий інтерфейс в обхід VFS, виникає катастрофічна гонка даних (*Data Race*):
1. Утиліта `e2fsck` зчитує блок каталогу, виправляє індекс і записує його назад на диск;
2. Через мілісекунду flusher-потік ядра виштовхує зі свого кешу стару версію сторінки метаданих, яка була сформована ядром до виправлення;
3. Виправлені дані `fsck` миттєво перезаписуються застарілими структурами ядра. Результатом стає тотальне руйнування бітових карт виділення блоків (*Block Bitmaps*) та масова поява перехресних посилань на файли (*Cross-linked Inodes*).

Перед виконанням перевірки завжди переконуються, що носій повністю відмонтовано:

```bash
# Перевірка статусу монтування
findmnt /dev/sdb1

# Якщо диск змонтовано — коректне відмонтування
umount /dev/sdb1
```

### Створення віртуального шару COW (Copy-On-Write) через Device Mapper

Якщо дані на диску є критично важливими, ремонт виконують не на фізичному носії, а на віртуальному тимчасовому знімку (*Snapshot Overlay*), створеному за допомогою модуля ядра `dm-snapshot`:

```
Схема безпечного ремонту через COW Snapshot:
[Фізичний диск /dev/sdb1] (Переведено в суворий Read-Only)
           │
           ▼
[Шар Device Mapper: /dev/mapper/repair-snap] (Доступний для запису)
           │
           ├── Читання: йде з оригінального /dev/sdb1
           └── Запис: усі модифікації e2fsck пишуться в тимчасовий RAM-диск /dev/loop0!
```

Покроковий алгоритм безпечного ремонту:

```bash
# 1. Переведення фізичного пристрою в режим Read-Only на рівні блокового шару
blockdev --setro /dev/sdb1

# 2. Отримання точного розміру пристрою в секторах (по 512 байтів)
SIZE=$(blockdev --getsz /dev/sdb1)

# 3. Створення тимчасового файлу для збереження змін (наприклад, у tmpfs RAM-диску)
truncate -s 10G /tmp/overlay.img
LOOP_DEV=$(losetup --find --show /tmp/overlay.img)

# 4. Створення віртуального блокового пристрою COW через dmsetup
# Синтаксис таблиці: 0 <сектори> snapshot <базовий_пристрій> <cow_пристрій> <персистентність> <chunk_size>
echo "0 $SIZE snapshot /dev/sdb1 $LOOP_DEV P 8" | dmsetup create repair-snap

# 5. Тепер /dev/mapper/repair-snap є повною копією диска, відкритою для запису!
# Виконуємо відновлення на віртуальному пристрої:
e2fsck -f -y /dev/mapper/repair-snap

# 6. Перевіряємо результат: чи монтується відновлений образ
mount /dev/mapper/repair-snap /mnt/test
```

Якщо процедура відновлення на віртуальному пристрої `repair-snap` пройшла успішно й дані вдалося прочитати, зміни можна накатити на фізичний носій або зняти копію файлів. Якщо ж утиліта ремонту остаточно зруйнувала структури, віртуальний шар видаляється командою `dmsetup remove repair-snap`, залишаючи оригінальний фізичний диск `/dev/sdb1` у початковому незайманому стані.

## Системний синтез діагностики

Успішна діагностика відмов монтування базується на суворій послідовності дій:

```
Алгоритмічний чекліст інженера при відмові mount(8):
1. Аналіз ядра:       $ dmesg | tail -n 30 -> з'ясувати точний код помилки (EINVAL, EBUSY, ENODEV, EIO).
2. Перевірка модуля:  Чи є драйвер ФС у /proc/filesystems? Якщо ні -> $ modprobe <fs>.
3. Пошук холдерів:    Якщо EBUSY -> перевірити /sys/class/block/*/holders/ та fuser -vm.
4. Ізоляція збою:     Якщо пошкоджено журнал -> аварійне монтування через -o ro,noload / ro,norecovery.
5. Відновлення SB:    Якщо EINVAL (Bad Superblock) -> пошук резервного суперблоку e2fsck -b 32768.
6. Безпечний ремонт:  Заборона fsck на живому диску -> створення COW оверлею через dmsetup snapshot.
```

Такий підхід трансформує хаотичне «відновлення навпомацки» в системний інженерний процес, гарантуючи збереження цілісності дискових метаданих та стійкість інфраструктури.
