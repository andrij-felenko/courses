Користувач запускає скрипт резервного копіювання від імені системної служби `backup-agent` (UID 1042, GID 1042). Скрипт намагається записати архів у файл `/var/data/backups/archive.tar.gz`. Системний адміністратор перевіряє цільовий файл командою `ls -l` і бачить рядок `-rwxrwxrwx 1 backup-agent backup-agent 0`. Повні права на читання, запис та виконання для всіх користувачів системи. Проте системний виклик `open("/var/data/backups/archive.tar.gz", O_WRONLY|O_CREAT, 0666)` негайно повертає значення `-1`, а змінна `errno` містить числовий код 13: `EACCES (Permission denied)`.

В іншій ситуації користувач `developer` (UID 1001) знаходить у спільному каталозі файл іншого колеги `secret.txt` із правами `0000` (`----------`), до якого ніхто не має права запису чи читання. Користувач вводить `rm -f secret.txt` — і файл безперешкодно зникає з диска. Але коли той самий користувач намагається змінити час модифікації цього файлу або виконати `chmod 0644 secret.txt`, система повертає зовсім інший код помилки — `EPERM (Operation not permitted)`.

Ці ситуації здаються взаємно суперечливими лише доти, доки права доступу сприймаються як статичний рядок літер `rwxrwxrwx`, приписаний до файлу. Для ядра Linux відмова в доступі — це результат роботи багатоланкового конвеєра перевірок у підсистемі VFS (Virtual Filesystem, від англ. *Virtual Filesystem* — віртуальна файлова система). Цей механізм спирається на модель дискреційного контролю доступу (DAC, від англ. *Discretionary Access Control* — довільне керування доступом на розсуд власника), де рішення ухвалюється на основі вектора ідентифікаторів процесу, структури каталожного дерева, наявності привілеїв суперкористувача та спеціальних прапорців режимів.

## Паспорт процесу в ядрі: розщеплення ідентичностей у `struct cred`

Коли процес звертається до файлової системи, ядро не перевіряє текстове ім'я користувача в системному файлі `/etc/passwd`. Натомість ядро звертається до службової структури облікових даних `struct cred`, вказівник на яку міститься в дескрипторі кожного завдання `task_struct`.

У цій структурі ідентичність процесу розщеплена на чотири різні числові ідентифікатори користувача (UID, від англ. *User Identifier*) та чотири ідентифікатори групи (GID, від англ. *Group Identifier*):

1. **Реальний ідентифікатор (Real UID / Real GID, `ruid`/`rgid`):** вказує на користувача, який фізично породив цей процес (наприклад, увійшов через SSH або запустив оболонку). Цей ідентифікатор використовується для перевірки прав на надсилання сигналів іншим процесам через системний виклик `kill()` та обліку системних лімітів ресурсів.
2. **Ефективний ідентифікатор (Effective UID / Effective GID, `euid`/`egid`):** визначає поточні привілеї процесу під час виконання більшості системних операцій. Саме `euid` змінюється під час запуску програм із встановленим бітом підвищення прав `setuid`.
3. **Збережений ідентифікатор (Saved Set-UID / Saved Set-GID, `suid`/`sgid`):** зберігає значення ефективного ідентифікатора на момент виконання системного виклику `execve()`. Це дає змогу привілейованим програмам тимчасово скидати привілеї до рівня звичайного користувача і безпечно повертати їх назад.
4. **Ідентифікатор файлової системи (Filesystem UID / Filesystem GID, `fsuid`/`fsgid`):** спеціалізований ідентифікатор ядра Linux, створений спеціально для операцій із файловими системами.

Історична причина появи пари `fsuid`/`fsgid` пов'язана з роботою демона мережевої файлової системи NFS (Network File System) у просторі користувача. Коли сервер NFS обслуговував запити від імені віддаленого не-привілейованого клієнта, демону потрібно було тимчасово прийняти права цього клієнта для перевірки доступу до файлів на локальному диску. Якби сервер просто змінив свій `euid`, він став би вразливим: клієнт із тим самим UID міг би надіслати демону вбивчий сигнал через `kill()`, оскільки перевірка прав на сигнали спирається на `euid` або `ruid`. Ввівши окремий `fsuid`, розробники ядра Linux дозволили змінювати права доступу до файлових операцій без зміни привілеїв на міжпроцесну взаємодію.

За замовчуванням у звичайних програмах `fsuid` завжди автоматично повторює будь-які зміни `euid`. Якщо викликається функція `seteuid(1000)`, ядро одночасно встановлює `fsuid = 1000`. Проте пряма зміна `fsuid` через виклик `setfsuid()` не впливає на `euid`.

Окрім основного `fsgid`, процес несе динамічний масив додаткових груп (Supplementary Groups) у структурі `group_info`. Якщо користувач входить до багатьох різних груп у системі, усі їхні числові GID завантажуються в `cred->group_info`. Коли ядро визначає, чи належить процес до групи файлу, воно перевіряє не лише `fsgid`, але й весь масив додаткових груп.

Повний зліпок активних ідентифікаторів та масок привілеїв процесу можна переглянути через віртуальну файлову систему `procfs`:

```sh
$ grep -E '^(Uid|Gid|Groups)' /proc/$$/status
Uid:    1000    1000    1000    1000
Gid:    1000    1000    1000    1000
Groups: 4 24 27 30 46 100 1000
```

Чотири стовпчики в рядках `Uid` та `Gid` відповідають послідовності `ruid`, `euid`, `suid`, `fsuid`. Саме останнє число — `fsuid` (та відповідні `fsgid` і `Groups`) — передається ядром у функцію перевірки прав VFS.

## Перша лінія оборони: покомпонентний розбір шляху (Path Walk)

Головна помилка інтуїтивного сприйняття файлових прав полягає в тому, що увагу зосереджують виключно на цільовому файлі. Але перш ніж ядро взагалі отримає дескриптор `inode` (від англ. *index node* — індексний вузол) цільового файлу, воно має фізично дійти до нього по дереву каталогів.

Кожен шлях, абсолютний (`/var/data/backups/archive.tar.gz`) чи відносний (`./backups/archive.tar.gz`), підсистема VFS обробляє через внутрішню функцію `link_path_walk()`. Обхід виконується суворо по черзі, компонент за компонентом:

```
[корінь /]  →  [каталог var]  →  [каталог data]  →  [каталог backups]  →  [файл archive.tar.gz]
```

Для кожного проміжного каталогу на цьому шляху процес повинен мати право **перетину / пошуку** (Search / Traverse). У класичній матриці прав це право кодується бітом виконання: `+x` (`0111` у вісімковій системі).

![Покомпонентний розбір шляху та перевірка біта x на каталогах](/root/course/unix/permission-denied-walkthrough/img/path-traversal-resolution.svg)
*Покомпонентний розбір шляху: брак біта виконання на проміжному каталозі блокує доступ до об'єктів усередині.*

Тут виникає фундаментальна різниця між значенням бітів `r` та `x` для каталогів:

* **Біт читання (`r`, read, `0444`):** дозволяє зчитувати список імен файлів, які зберігаються всередині каталогу. Цей біт використовується системним викликом `getdents64()`, на якому базується утиліта `ls`. Якщо каталог має права `r--`, користувач може побачити список файлів, але не зможе дізнатися їхні розміри, власників або відкрити їх (бо для виклику `stat()` на кожен файл потрібен біт `x`).
* **Біт виконання / пошуку (`x`, execute/search, `0111`):** дозволяє підсистемі VFS виконувати операцію `lookup` — транслювати текстове ім'я компонента в номер його `inode` та переходити крізь цей каталог далі вниз по дереву.

Якщо на будь-якому з проміжних каталогів процесу бракує біта `x`, ядро негайно перериває виконання системного виклику і повертає помилку `EACCES`. До перевірки прав самого цільового файлу ядро навіть не доходить.

Саме цим пояснюється загадка з початку статті:

```sh
# Права на каталоги шляху:
drwxr-xr-x  root   root   /
drwxr-xr-x  root   root   /var
drwxr-x---  root   adm    /var/data
drwxrwxrwx  root   root   /var/data/backups
-rwxrwxrwx  backup backup /var/data/backups/archive.tar.gz
```

Коли процес служби `backup-agent` (UID 1042, GID 1042) намагається відкрити файл, ядро успішно проходить каталоги `/` та `/var`. Але на каталозі `/var/data` процес зустрічає права `0750` (`drwxr-x---`), де власником є `root`, а групою — `adm`. Оскільки процес не є `root` і не входить до групи `adm`, ядро застосовує клас «решта» (`others`), де стоять біти `---` (нуль). Процес позбавлений права `+x` на каталозі `/var/data`. Ядро генерує помилку `EACCES`, а права `0777` на каталозі `backups` та самому файлі `archive.tar.gz` не мають жодної сили.

> 🔧 **Навіщо це.**
> Ця властивість дозволяє створювати надійну ізоляцію каталогів: встановивши на домашній каталог права `chmod 0700 /home/alice`, користувач `alice` робить усі свої вкладені файли й каталоги повністю недоступними для інших не-привілейованих користувачів системи, навіть якщо всередині домашнього каталогу якісь файли мають права `0777`.

### Поведінка символьних посилань на шляху

Символьні посилання (symlinks, від англ. *symbolic links*) додають до обходу шляху окремий крок. У класичній моделі Unix права на саме символьне посилання (`lrwxrwxrwx`) є фіктивними: системний виклик `chmod` над символьним посиланням за замовчуванням змінює права на цільовий файл, а не на сам symlink.

Коли функція `link_path_walk()` зустрічає на шляху символьне посилання, ядро виконує такі перевірки:
1. Перевіряє наявність біта `+x` на каталозі, де лежить символьне посилання.
2. Зчитує текстовий шлях із тіла symlink.
3. Перериває поточну траєкторію та починає новий обхід розпакованого шляху.
4. Перевіряє наявність біта `+x` на всіх проміжних каталогах нового шляху.

Якщо символьне посилання веде у каталог, до якого процес не має доступу через брак біта `+x`, операція завершується помилкою `EACCES`. Якщо символьне посилання вказує на неіснуючий об'єкт (висяче посилання, dangling symlink), ядро повертає помилку `ENOENT (No such file or directory)`, навіть якщо сам файл посилання існує на диску.

## Алгоритм перевірки цільового Inode: `generic_permission()`

Якщо всі проміжні каталоги успішно пройдені, VFS досягає дескриптора кінцевого об'єкта і викликає функцію `inode_permission()`, яка звертається до ядра перевірки DAC — функції `generic_permission()`.

Алгоритм `generic_permission()` працює за принципом **першого збігу та взаємного виключення класів**:

1. **Крок 1 (Власник):** Ядро перевіряє, чи збігається `cred->fsuid` процесу з числовим ідентифікатором власника об'єкта `inode->i_uid`. Якщо вони рівні — ядро обирає трійку бітів власника (`User`: `S_IRUSR`, `S_IWUSR`, `S_IXUSR`) і **повністю завершує вибір класу**.
2. **Крок 2 (Група):** Якщо `fsuid` не збігся з власником, ядро перевіряє, чи збігається `cred->fsgid` або будь-який з ідентифікаторів у списку додаткових груп `cred->group_info` з групою об'єкта `inode->i_gid`. Якщо збіг знайдено — ядро обирає трійку бітів групи (`Group`: `S_IRGRP`, `S_IWGRP`, `S_IXGRP`) і **повністю завершує вибір класу**.
3. **Крок 3 (Решта):** Якщо процес не є власником і не входить до групи об'єкта, ядро обирає трійку бітів для інших користувачів (`Others`: `S_IROTH`, `S_IWOTH`, `S_IXOTH`).

![Алгоритм перевірки прав доступу ядра](/root/course/unix/permission-denied-walkthrough/img/dac-decision-tree.svg)
*Алгоритм перевірки прав доступу ядра: покрокове проходження через класи fsuid/fsgid та capabilities.*

Після того як клас обрано, ядро бере лише цю одну трійку бітів і перевіряє, чи дозволяє вона запитувану операцію:

```
[Потрібно читання?]     → чи є біт r?
[Потрібен запис?]       → чи є біт w?
[Потрібне виконання?]   → чи є біт x?
```

Якщо хоча б один потрібний біт у вибраній трійці відсутній, пряма перевірка завершується невдачею.

### Парадокс «прав, що не додаються»

Критично важливо розуміти: **права в Unix ніколи не об'єднуються**. Якщо процес є власником файлу, до нього застосовуються *виключно* біти власника, навіть якщо права групи чи інших користувачів є значно ширшими.

Розглянемо приклад файлу з незвичайною конфігурацією:

```sh
$ ls -l config.db
----rw-r-- 1 alice developers 4096 config.db
```

Користувач `alice` (член групи `developers`) запускає команду `cat config.db`.
* Процес має `fsuid = alice`, `fsgid = developers`.
* Ядро порівнює `fsuid` із власником файлу (`alice`). Збіг є!
* Ядро обирає клас власника: `---` (`0000`).
* Перевірка запиту на читання (`r`): біт відсутній.
* **Результат: `EACCES (Permission denied)`.**

Той факт, що група `developers` має право `rw-`, а всі інші — `r--`, не має жодного значення: оскільки `alice` є власником, перевірка зупинилася на першому кроці, і права групи ядро навіть не аналізувало.

Це не помилка дизайну, а навмисний механізм: завдяки взаємному виключенню класів власник може явно обмежити або заборонити доступ конкретній групі, наприклад, встановивши права `0604` (`rw----r--`), де група позбавлена доступу, тоді як решта користувачів мають право на читання.

### Запасний вихід: Capabilities суперкористувача

Якщо вибрана трійка бітів не дає потрібного дозволу, ядро не повертає помилку миттєво. Воно перевіряє, чи володіє процес спеціальними привілеями ядра — [можливостями (capabilities)](book:unix-linux/capabilities):

1. `CAP_DAC_OVERRIDE` — дозволяє процесу повністю ігнорувати обмеження DAC на читання, запис та виконання.
   * **Виняток для виконання:** навіть якщо процес має `CAP_DAC_OVERRIDE`, ядро дозволить запустити файл на виконання (`x`) лише за умови, що **хоча б один** біт виконання (`x` у класі власника, групи чи інших) встановлений у дескрипторі `inode`. Це запобігає випадковому виконанню суперкористувачем файлів конфігурації, текстових документів чи сирих даних, які не є програмами.
2. `CAP_DAC_READ_SEARCH` — дозволяє процесу читати будь-які файли незалежно від бітів `r` та здійснювати пошук у будь-яких каталогах незалежно від бітів `x`.

Якщо відповідні привілеї у процесу відсутні, ядро остаточно фіксує відмову `EACCES`.

## Парадокс створення та видалення: батьківський каталог і Sticky Bit

Одна з найпоширеніших причин плутанини в системному адмініструванні — це різниця між операціями над *вмістом* файлу та операціями над *іменем* файлу в каталозі.

У моделі Unix каталог — це звичайний файл спеціального типу, вмістом якого є таблиця відображення «текстове ім'я → номер inode» ([каталог як відображення](book:unix-linux/directory-as-mapping)).

Звідси випливає фундаментальний поділ:

* **Зміна даних файлу (`write()`, `truncate()`):** модифікує дискові блоки самого `inode` файлу. Для цього потрібні права `+w` на самому файлі та права `+x` на всіх каталогах шляху до нього. Права батьківського каталогу на операцію запису в існуючий файл **не впливають взагалі**.
* **Створення нового файлу (`creat()`, `open(O_CREAT)`):** це додавання нового запису в таблицю імен батьківського каталогу. Для цього потрібні права `+w` та `+x` на **батьківському каталозі**. Права на інші файли в цьому каталозі не мають значення.
* **Видалення файлу (`unlink()`, `rm`):** це видалення запису з таблиці імен батьківського каталогу та зменшення лічильника посилань `inode->i_nlink` ([жорсткі й символьні посилання](book:unix-linux/hard-and-symbolic-links)). Для цього потрібні права `+w` та `+x` на **батьківському каталозі**.

![Різниця між операціями над файлом і операціями над каталогом](/root/course/unix/permission-denied-walkthrough/img/directory-vs-file-ops.svg)
*Різниця між модифікацією вмісту файлу та зміною записів у каталозі за наявності Sticky Bit.*

Цей механізм пояснює, чому не-привілейований користувач може легко видалити чужий файл із правами `0000`: якщо користувач має право на запис у каталог, він володіє самою таблицею імен цього каталогу і може викреслити з неї будь-який запис. Команда `rm` перед видаленням файлу без прав запису лише запитує інтерактивне підтвердження в терміналі, але сам системний виклик `unlink()` виконується ядром без жодних перешкод.

### Захисний механізм: Sticky Bit на каталогах (`S_ISVTX`)

Якби система цим обмежувалася, спільні каталоги на кшталт `/tmp` або `/var/tmp` були б непридатними для використання: щоб будь-який користувач міг створити тимчасовий файл, каталог `/tmp` повинен мати права на запис для всіх (`0777`). Але тоді будь-який зловмисник міг би видалити або підмінити файли сокетів, блокувань чи тимчасових даних інших користувачів і системних служб.

Для розв'язання цієї проблеми використовується спеціальний прапорець каталогу — **Sticky Bit** (біт захисту від видалення, символьне позначення `t`, числовий біт `S_ISVTX`, `01000` у вісімковій системі).

Коли на каталозі встановлено Sticky Bit (типові права `/tmp` становлять `1777` або `drwxrwxrwt`), ядро активує додаткову перевірку у функції `may_delete()`:

Видалити або перейменувати файл усередині каталогу зі Sticky Bit дозволяється **лише тоді**, коли виконується хоча б одна з трьох умов:

1. `fsuid` процесу збігається з числовим UID **власника файлу** (`victim->i_uid`);
2. `fsuid` процесу збігається з числовим UID **власника каталогу** (`dir->i_uid`);
3. Процес має привілей суперкористувача `CAP_FOWNER`.

Якщо жодна з цих умов не справджується, виклик `unlink()` або `rename()` відхиляється з помилкою `EACCES` (або `EPERM` на деяких старіших Unix-системах), навіть попри наявність біта `+w` на самому каталозі.

### Захист ядра проти гонитви за посиланнями: `fs.protected_*`

Окрім класичного Sticky Bit, сучасне ядро Linux має додатковий вбудований рівень захисту від атак підміни через спільні каталоги. Цей захист налаштовується через параметри `sysctl`:

* `fs.protected_symlinks = 1`: забороняє перехід за символьними посиланнями в каталогах зі Sticky Bit (`/tmp`), якщо власник символьного посилання не збігається з власником каталогу або користувачем, який ініціював відкриття файлу.
* `fs.protected_hardlinks = 1`: забороняє створення жорстких посилань на файли, власником яких процес не є (за винятком файлів, які процес може читати й записувати).
* `fs.protected_fifos = 2` та `fs.protected_regular = 2`: забороняють відкриття іменованих каналів (FIFO) або звичайних файлів у спільних каталогах, якщо вони створені іншим користувачем і відкриваються з прапорцем `O_CREAT`.

Якщо спрацьовує будь-яке з цих правил, системний виклик `open()` негайно повертає помилку `EACCES`, навіть якщо права DAC на файлі формально дозволяють доступ.

## Специфіка виконання скриптів проти двійкових файлів

Окремим джерелом помилок доступу є запуск програм. У системі Unix програми поділяються на два класи: двійкові виконувані файли (ELF-файли) та інтерпретовані скрипти (починаються з рядка shebang `#!/bin/sh` або `#!/usr/bin/env python3`).

Вимоги до прав для цих двох категорій принципово різняться:

1. **Двійкові ELF-файли:** для прямого запуску двійкового файлу потрібен **лише біт виконання (`+x`)** на самому файлі та біти `+x` на проміжних каталогах. Біт читання (`+r`) для двійкового файлу не потрібен, оскільки завантажувач ядра Linux читає сторінки коду безпосередньо у віртуальну пам'ять через внутрішній виклик `do_execveat_common()`.
2. **Інтерпретовані скрипти:** для запуску скрипта як виконуваного файлу (`./script.py`) обов'язково потрібні **і біт `+x`, і біт `+r`**:
   * Біт `+x` перевіряється ядром під час виклику `execve("./script.py")`, щоб переконатися, що файл дозволено запускати.
   * Після того як ядро прочитало перший рядок `#!/usr/bin/python3`, воно завантажує двійковий файл інтерпретатора і передає йому шлях `./script.py` як аргумент.
   * Інтерпретатор Python працює у просторі користувача і намагається відкрити скрипт як текстовий файл викликом `open("./script.py", O_RDONLY)`.
   * Якщо на скрипті стоїть `+x`, але відсутній `+r` (наприклад, `0111`), ядро успішно запустить інтерпретатор, але сам інтерпретатор негайно впаде з помилкою «Permission denied».

```sh
# Демонстрація поведінки скрипта без прав читання:
$ chmod 0111 test.sh
$ ls -l test.sh
---x--x--x 1 developer developer 32 test.sh

$ ./test.sh
/bin/bash: ./test.sh: Permission denied
```

Помилку згенерувала не підсистема запуску ядра, а сам командний інтерпретатор `/bin/bash` під час спроби прочитати текст програми.

## Гонитва перевірки та використання (TOCTOU) і сімейство `*at()`

У програмуванні на C класичною помилкою початківців є перевірка прав файлу перед його відкриттям:

:::tabs
```c
/* Антипатерн: створення вразливості Time-of-Check to Time-of-Use */
if (access("/tmp/data.log", W_OK) == 0) {
    /* Зловмисник може замінити /tmp/data.log на symlink до /etc/shadow прямо тут! */
    int fd = open("/tmp/data.log", O_WRONLY);
    if (fd >= 0) {
        /* Запис даних */
        close(fd);
    }
}
```
```cpp
// Антипатерн у C++: перевірка доступу перед відкриттям
if (access("/tmp/data.log", W_OK) == 0) {
    // Зловмисник може замінити /tmp/data.log на symlink прямо тут!
    std::ofstream file("/tmp/data.log", std::ios::out);
    if (file.is_open()) {
        file << "Дані\n";
    }
}
```
:::

Цей шаблон містить критичну вразливість TOCTOU (Time-of-Check to Time-of-Use — час перевірки проти часу використання). Між виконанням виклику `access()` та відкриттям `open()` операційна система може перемкнути контекст процесу, і паралельний потік або зловмисник встигне підмінити файл чи замінити проміжний каталог символьним посиланням.

Ідіоматичний та безпечний підхід у POSIX-системах полягає у відмові від попередніх перевірок: програма відразу намагається виконати цільову дію (наприклад, `openat()` або `unlinkat()`) і перевіряє код повернення. Якщо ядро повертає `-1` та `errno == EACCES`, програма обробляє відмову.

Сучасний інтерфейс `openat2()` робить крок далі, дозволяючи зафіксувати обхід шляху прапорцем `RESOLVE_BENEATH` (гарантія, що розбір шляху не вийде за межі цільового піддерева каталогу) або `RESOLVE_NO_SYMLINKS` (повна заборона будь-яких символьних посилань на шляху).

## Простір імен користувачів (User Namespaces) та маппінг UID

Під час роботи з контейнерами (Docker, Podman, LXC) виникає додатковий рівень трансляції ідентичностей — простір імен користувачів (User Namespace).

Усередині контейнера процес може бачити себе як користувача з числовим `UID 0` (`root`). Проте підсистема VFS перевіряє права на фізичному диску за відображенням у файлі `/proc/<PID>/uid_map`:

```
# uid_map контейнера: внутрішній UID 0 відповідає хостовому UID 100000
0  100000  65536
```

Якщо всередині такого контейнера процес `root` (внутрішній UID 0) спробує відкрити файл на хості, який належить справжньому `root` хоста (хостовий UID 0) із правами `0700`, ядро співставить внутрішній UID 0 із зовнішнім `100000`. Оскільки `100000 != 0`, ядро застосує клас `others` (`---`) і поверне помилку `EACCES`. Для хостового ядра процес контейнера є звичайним не-привілейованим користувачем.

## Розмежування помилок: `EACCES` проти `EPERM`

У виводах утиліт і журналах ядра можна побачити дві схожі за змістом помилки: `Permission denied` та `Operation not permitted`. У мові C та системних викликах їм відповідають строго різні константи: `EACCES` (errno 13) та `EPERM` (errno 1).

Ядро чітко розмежовує контексти використання цих кодів:

![Розмежування помилок EACCES та EPERM](/root/course/unix/permission-denied-walkthrough/img/eacces-vs-eperm.svg)
*Розмежування помилок EACCES та EPERM: права доступу до даних проти привілеїв адміністрування та метаданих.*

### 1. `EACCES` (код 13, Permission denied — Доступ заборонено)

Ця помилка виникає тоді, коли операція порушує правила доступу до **даних або файлових об'єктів за моделлю DAC**:
* Відсутність необхідного біта `r`, `w` або `x` у відповідному класі прав (власник/група/інші);
* Відсутність біта `+x` на будь-якому з проміжних каталогів при розборі шляху;
* Спроба створити файл у каталозі без біта `+w`;
* Порушення правила Sticky Bit під час спроби видалення чужого файлу в каталозі `1777`;
* Заборона доступу з боку модуля обов'язкового контролю доступу LSM (AppArmor, SELinux);
* Спроба відкрити файл на виконання, коли файлова система змонтована з прапорцем `noexec`.

### 2. `EPERM` (код 1, Operation not permitted — Операція не дозволена)

Ця помилка сигналізує про брак **фундаментальних системних привілеїв суб'єкта або прав власності** на об'єкт:
* Спроба змінити власника файлу викликом `chown()` від імені звичайного користувача. У Linux звичайний користувач не може передати свій файл іншому користувачеві (для цього потрібен привілей `CAP_CHOWN`);
* Спроба змінити права доступу викликом `chmod()` користувачем, який не є власником файлу (і не має `CAP_FOWNER`), навіть якщо цей користувач має повні права `rwx` на файл через групу;
* Спроба змінити або видалити файл, на якому встановлено розширений атрибут незмінності `immutable` (`chattr +i`, що встановлює прапорець `FS_IMMUTABLE_FL` у файловій системі). Зняти цей прапорець може лише процес із привілеєм `CAP_LINUX_IMMUTABLE`;
* Спроба надіслати сигнал через `kill()` процесу, який належить іншому користувачеві, без привілею `CAP_KILL`;
* Спроба виконати привілейовані мережеві чи системні дії (зміна системного годинника, конфігурація мережевих інтерфейсів, завантаження модулів ядра).

### Супутні коди відмов доступу VFS

Крім `EACCES` та `EPERM`, підсистема VFS повертає спеціалізовані коди помилок у разі специфічних системних конфліктів:

* **`EROFS` (код 30, Read-only file system):** повертається при будь-якій спробі модифікації (`MAY_WRITE`), якщо файлова система змонтована з прапорцем `ro` або блоковий пристрій фізично заблокований від запису.
* **`ETXTBSY` (код 26, Text file busy):** повертається, коли процес намагається відкрити на запис двійковий виконуваний файл, який прямо зараз виконується іншим процесом у пам'яті системи. Ядро блокує таку дію для збереження цілісності сторінок коду.

Повна структура функцій ядра, макросів `MAY_*`, декодування бітових масок у `/proc` та сигнатур системних викликів наведена в окремому документі: [довідник інтерфейсів діагностики та кодів помилок](guide:unix/permission-denied-walkthrough/api-dac-diagnostics.md).

## Покрокова методологія діагностики «Permission denied»

Коли прикладний застосунок або системна служба стикається з відмовою в доступі, системний інженер діє за суворим діагностичним алгоритмом із п'яти кроків.

```
[1. Ідентичність]   →   [2. Шлях VFS]   →   [3. Inode & Клас]   →   [4. Каталог/Sticky]   →   [5. Монтування/LSM]
```

### Крок 1. З'ясувати повну ідентичність процесу

Необхідно перевірити, від імені кого саме виконується код. Якщо це запущений демон або контейнер, дивимося його реальний стан у `/proc`:

```sh
$ grep -E '^(Uid|Gid|Groups)' /proc/<PID>/status
```

Якщо перевірка робиться в терміналі, використовується утиліта `id`:

```sh
$ id
uid=1001(developer) gid=1001(developer) groups=1001(developer),27(sudo),1002(docker)
```

Зафіксуйте значення `fsuid`, `fsgid` та список числових ідентифікаторів додаткових груп.

### Крок 2. Просканувати весь шлях утилітою `namei`

Замість ручного перегляду `ls -ld` для кожного каталогу використовуйте утиліту `namei` з ключами `-l` (довгий формат) та `-n` (числові UID/GID):

```sh
$ namei -ln /var/log/app/service.log
f: /var/log/app/service.log
drwxr-xr-x     0     0 /
drwxr-xr-x     0     0 var
drwxr-xr-x     0     0 log
drwxr-x---  1000  1000 app
-rwxrwxrwx  1001  1001 service.log
```

Перевірте кожен рядок із позначкою `d` (каталог) зверху вниз:
* Чи є біт `x` у стовпчику вашого класу?
* Якщо на каталозі `app` стоїть `0750`, а ваш UID дорівнює 1001 (клас others), біт `x` відсутній. Доступ заблоковано на цьому рівні.

### Крок 3. Визначити обраний клас на цільовому Inode

Виведіть точні числові атрибути цільового файлу:

```sh
$ stat -c "Mode: %a (%A), Inode: %i, Owner: %u(%U), Group: %g(%G)" /target/file
Mode: 640 (-rw-r-----), Inode: 284192, Owner: 1000(alice), Group: 1002(devs)
```

Застосуйте правило взаємного виключення:
* Чи дорівнює ваш `fsuid` числу 1000? Якщо так — діють **лише** біти `rw-` (власник).
* Чи дорівнює ваш `fsgid` або будь-яка з ваших додаткових груп числу 1002? Якщо так — діють **лише** біти `r--` (група).
* Якщо ні — діють біти `---` (інші).

### Крок 4. Перевірити батьківський каталог на Sticky Bit та права запису

Якщо дія передбачає створення, видалення або перейменування файлу, перевірте права його безпосереднього батьківського каталогу:

```sh
$ stat -c "Parent Mode: %a, Owner: %u" $(dirname /target/file)
Parent Mode: 1777, Owner: 0
```

Якщо встановлено біт `1000` (Sticky), перевірте, чи є ваш `fsuid` власником файлу, або власником каталогу, або чи володіє процес привілеєм `CAP_FOWNER`.

### Крок 5. Перевірити прапорці монтування та розширені атрибути

Якщо права DAC виглядають бездоганно, але запис чи запуск блокується:

1. Перевірте прапорці файлової системи:
   ```sh
   $ findmnt -T /target/file
   TARGET SOURCE    FSTYPE OPTIONS
   /data  /dev/sdb1 ext4   ro,nosuid,nodev,noexec,relatime
   ```
   * Наявність `ro` блокує будь-який запис із кодом `EROFS`.
   * Наявність `noexec` блокує прямий запуск бінарних файлів із кодом `EACCES`.
   * Наявність `nosuid` блокує дію прапорців `setuid`/`setgid`.

2. Перевірте розширені атрибути файлової системи `ext4`/`xfs`:
   ```sh
   $ lsattr /target/file
   ----i---------e---- /target/file
   ```
   * Прапорець `i` (immutable) блокує будь-яку зміну, перейменування чи видалення файлу навіть для користувача `root` із кодом `EPERM`.
   * Прапорець `a` (append-only) дозволяє лише дописування в кінець файлу, блокуючи перезапис і скорочення.

3. Перевірте стан журналів системного аудиту:
   ```sh
   # Перевірка блокувань AppArmor або SELinux
   $ dmesg | grep -E '(apparmor|selinux|audit)' | tail -n 5
   ```

Для детального практичного моделювання цих перевірок у коді розроблено практичний інструмент діагностики: [симулятор перевірки прав DAC](guide:unix/permission-denied-walkthrough/proj-permission-checker.md), який реалізує повний алгоритм ядра на C та C++ і покроково візуалізує проходження кожного етапу розбору шляху та матриці прав.
