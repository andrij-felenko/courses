Розробник компілює мережеву службу `telemetry-agent` на робочій станції під керуванням Ubuntu 24.04 за допомогою компілятора GCC 13.2 зі стандартною системною бібліотекою glibc 2.38. Зібраний двійковий файл `/opt/bin/telemetry-agent` (формат ELF 64-bit LSB pie executable, архітектура x86-64) бездоганно запускається на машині розробника, проходить модульні тести та демонструє стабільну роботу. Проте коли скомпільований файл копіюють через `scp` на цільовий сервер під керуванням Debian 11 (glibc 2.31) або переносять у легковагий контейнер на базі Alpine Linux 3.19 (musl 1.2.4), спроба запуску `./telemetry-agent` миттєво зазнає аварії ще до того, як процесор виконає бодай одну інструкцію функції `main()`.

На сервері з Debian 11 командна оболонка видає повідомлення:
```
./telemetry-agent: /lib/x86_64-linux-gnu/libc.so.6: version 'GLIBC_2.34' not found (required by ./telemetry-agent)
```
А в контейнері Alpine Linux виникає ще більш оманлива помилка:
```
-sh: ./telemetry-agent: not found
```
Хоча файл фізично лежить у поточному каталозі, має розмір 4.2 мегабайти та прапорець дозволу на виконання `chmod +x` (`-rwxr-xr-x`).

Поширена інженерна фраза «у мене все працює» (англ. *it works on my machine*) у середовищі Unix ніколи не є наслідком містичного збігу обставин. Вона свідчить про розрив контракту двійкового інтерфейсу прикладних програм (ABI, від англ. *Application Binary Interface*) між середовищем компіляції та середовищем виконання. Від моменту, коли системний виклик `execve()` передає шлях до файлу в ядро Linux, і до передачі керування в точку входу користувацького коду, система здійснює п'ятиетапний конвеєр перевірок та зв'язування. Якщо бодай на одному з цих етапів виникає невідповідність шляхів, версій символів, реалізації стандартної бібліотеки або змінних оточення, запуск негайно блокується.

![П'ять бар'єрів виконання: де ламається переносимість бінарника](/root/course/unix/why-it-runs-here-not-there/img/fig-execution-gateways.svg)
*П'ять бар'єрів запуску програми в Linux: від перевірки заголовка ELF у ядрі до ініціалізації локалей у рантаймі.*

## 1. Перший бар'єр: ядро, заголовок ELF і шлях до інтерпретатора (`PT_INTERP`)

Коли користувач або скрипт викликає системний виклик `execve("/opt/bin/telemetry-agent", argv, envp)`, ядро Linux розпочинає обробку всередині функції `do_execveat_common()`. Ядро відкриває вказаний виконуваний файл і зчитує перші 128 байтів у внутрішній буфер для ідентифікації двійкового формату через підсистему двійкових обробників `binfmt_elf`.

Обробник ядра `load_elf_binary()` у вихідному коді ядра `fs/binfmt_elf.c` виконує сувору послідовність низькорівневих дій:

1. **Перевірка заголовка ELF (`Elf64_Ehdr`):** ядро перевіряє магічну сигнатуру `\x7fELF` (байти `0x7F`, `'E'`, `'L'`, `'F'`), розрядність (ELFCLASS64), порядок байтів (ELFDATA2LSB) та цільову архітектуру `e_machine` (наприклад, `EM_X86_64 = 62` або `EM_AARCH64 = 183`). Якщо двійковий файл скомпільовано під іншу архітектуру процесора, системний виклик миттєво повертає помилку `-ENOEXEC (Exec format error)`.
2. **Очищення попереднього контексту:** функція `flush_old_exec()` звільняє віртуальні сторінки пам'яті старого процесу, скидає обробники сигналів на значення за замовчуванням та закриває всі дескриптори файлів, для яких було встановлено прапорець `O_CLOEXEC` / `FD_CLOEXEC`.
3. **Пошук сегмента `PT_INTERP`:** ядро сканує масив програмних заголовків `struct elf_phdr`. Якщо бінарник є повністю статичним, ядро одразу відображає сегменти `PT_LOAD` і готує точку входу `e_entry`. Для динамічного бінарника ядро знаходить сегмент `PT_INTERP`.

Сегмент `PT_INTERP` містить нуль-термінований текстовий рядок із абсолютним шляхом до динамічного завантажувача:

```sh
$ readelf -l /opt/bin/telemetry-agent | grep interpreter
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

Отримавши цей шлях, функція ядра `load_elf_binary()` виконує внутрішній виклик `open_exec("/lib64/ld-linux-x86-64.so.2")`. Якщо за вказаним шляхом у файловій системі хоста немає файлу, системний виклик `execve()` негайно завершується з кодом помилки `-ENOENT (No such file or directory)`.

Саме цим механізмом пояснюється оманлива помилка `-sh: ./telemetry-agent: not found` в Alpine Linux. Командна оболонка передає шлях до бінарника в ядро, ядро зчитує сегмент `PT_INTERP` і намагається відкрити динамічний завантажувач GNU glibc `/lib64/ld-linux-x86-64.so.2`. Оскільки дистрибутив Alpine Linux побудований на базі бібліотеки musl libc, його власний завантажувач розташований за шляхом `/lib/ld-musl-x86_64.so.1`. Ядро не знаходить файлу glibc-завантажувача, виклик `execve()` повертає `ENOENT`, а командна оболонка транслює цей числовий код у повідомлення «файл не знайдено», спантеличуючи користувача, який бачить сам бінарник у каталозі з повними правами на виконання.

Аналогічна ситуація виникає при спробі виконати 32-бітний динамічний бінарник на 64-бітній системі без встановленого пакета багатоархітектурної підтримки (*multilib*). Бінарник шукає 32-бітний інтерпретатор `/lib/ld-linux.so.2`, який відсутній у чистій 64-бітній інсталяції.

Якщо файл інтерпретатора успішно знайдено на диску, ядро здійснює розгортання простору процесу:
* Виділяє віртуальні сторінки пам'яті для сегментів `PT_LOAD` самої програми. Для позиційно-незалежних виконуваних файлів (PIE, тип `ET_DYN`) ядро застосовує рандомізацію адресного простору (ASLR) через `arch_mmap_rnd()`, розміщуючи базу програми за випадковою адресою. Для старих бінарників `ET_EXEC` база зафіксована на `0x400000`.
* Відображає код та дані самого динамічного завантажувача `ld.so` у пам'ять за окремою адресою `AT_BASE`.
* Відображає сторінку віртуального динамічного спільного об'єкта ядра vDSO (*Virtual Dynamic Shared Object*) через `arch_setup_additional_pages()`, яка надає швидкі системні виклики без перемикання контексту (`clock_gettime`, `gettimeofday`).
* Формує початковий стек процесу. На стеку послідовно розміщуються: лічильник аргументів `argc`, масив вказівників `argv[]`, масив вказівників на змінні середовища `envp[]` та термінальний масив допоміжного вектора ядра (*Auxiliary Vector*, `Elf64_auxv_t`).

Допоміжний вектор передає динамічному завантажувачу критично важливі системні параметри:
* `AT_PHDR` — адреса таблиці програмних заголовків виконуваного файлу в пам'яті;
* `AT_PHNUM` — кількість записів у таблиці програмних заголовків;
* `AT_PAGESZ` — апаратний розмір сторінки пам'яті (4096 байтів);
* `AT_BASE` — базова віртуальна адреса відображення завантажувача `ld.so`;
* `AT_ENTRY` — адреса точки входу програми `e_entry`, куди завантажувач передасть керування після лінкування;
* `AT_SECURE` — числовий прапорець (0 або 1), який вмикає захищений режим для програм із бітами `setuid`/`setgid` або правами *capabilities*;
* `AT_RANDOM` — 16 випадкових байтів від ядра для ініціалізації канарок стека (*stack canary*);
* `AT_SYSINFO_EHDR` — адреса заголовка vDSO для виконання надшвидких таймерів.

Після завершення ініціалізації стека ядро передає керування процесором не на адресу `e_entry` програми, а безпосередньо на першу інструкцію точки входу динамічного завантажувача `ld.so`.

Для переносних утиліт цей бар'єр долається модифікацією заголовка ELF за допомогою утиліти `patchelf`:
```sh
$ patchelf --set-interpreter /opt/my-runtime/ld-linux-x86-64.so.2 ./telemetry-agent
```

## 2. Другий бар'єр: динамічний завантажувач та ієрархія пошуку бібліотек

Отримавши керування від ядра, динамічний завантажувач `ld.so` не може одразу викликати звичайні бібліотечні функції, оскільки таблиці релокацій самого завантажувача ще не оброблені. Завантажувач виконує спеціальну процедуру власної саморелокації (bootstrap), після чого зчитує динамічну секцію `.dynamic` головного двійкового файлу. Завантажувач сканує всі записи з тегом `DT_NEEDED`, які містять перелік спільних бібліотек, необхідних для роботи програми:

```sh
$ readelf -d /opt/bin/telemetry-agent | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libssl.so.3]
 0x0000000000000001 (NEEDED)             Shared library: [libcrypto.so.3]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

Для кожного запису `DT_NEEDED` завантажувач зобов'язаний розгорнути коротке логічне ім'я (SONAME, наприклад, `libssl.so.3`) у конкретний файл на диску. Пошук здійснюється за суворою п'ятирівневою ієрархією пріоритетів, де кожний наступний рівень перевіряється лише тоді, коли бібліотеку не було знайдено на попередньому.

![Ієрархія пошуку динамічних бібліотек завантажувачем ld.so](/root/course/unix/why-it-runs-here-not-there/img/fig-library-search-hierarchy.svg)
*Ієрархія пошуку спільних бібліотек: від жорстко зашитих шляхів RPATH до глобального системного кешу.*

Порядок обходу каталогів завантажувачем glibc `ld.so` визначено наступними правилами:

1. **Тег `DT_RPATH`:** якщо у двійковому файлі встановлено застарілий тег `DT_RPATH` і водночас **відсутній** новіший тег `DT_RUNPATH`, завантажувач перевіряє каталоги з `DT_RPATH`. Цей шлях має абсолютний найвищий пріоритет і перекриває навіть змінні середовища користувача.
2. **Змінна середовища `LD_LIBRARY_PATH`:** якщо процес виконується у звичайному режимі (прапорець `AT_SECURE = 0`), завантажувач послідовно сканує каталоги, перелічені в цій змінній через двокрапку. Якщо встановлено біт `setuid` чи `setgid`, ця змінна повністю ігнорується з міркувань безпеки.
3. **Тег `DT_RUNPATH`:** якщо у двійковому файлі встановлено сучасний тег `DT_RUNPATH`, завантажувач перевіряє вказані там каталоги. Оскільки `DT_RUNPATH` має нижчий пріоритет, ніж `LD_LIBRARY_PATH`, адміністратор може тимчасово перевизначити бібліотеку для тестування.
4. **Системний кеш `/etc/ld.so.cache`:** двійковий кеш швидкого пошуку, який генерується утилітою `ldconfig` на основі файлів конфігурації `/etc/ld.so.conf` та `/etc/ld.so.conf.d/*.conf`. Завантажувач виконує пошук у кеші за сталий час `O(1)` за допомогою геш-таблиці.
5. **Стандартні системні шляхи за замовчуванням:** якщо файл не знайдено в кеші, завантажувач звертається до стандартних каталогів `/lib64`, `/usr/lib64`, `/lib`, `/usr/lib` або багатоархітектурних шляхів на кшталт `/lib/x86_64-linux-gnu` та `/usr/lib/x86_64-linux-gnu` у дистрибутивах Debian та Ubuntu.

Якщо на жодному з п'яти рівнів бібліотеку не знайдено, завантажувач перериває запуск із фатальною помилкою:
```
./telemetry-agent: error while loading shared libraries: libssl.so.3: cannot open shared object file: No such file or directory
```

### Відкладене зв'язування проти Full RELRO

Після завантаження всіх об'єктів у пам'ять настає фаза релокації та зв'язування символів. За замовчуванням у класичних системах Unix використовувався механізм відкладеного лінкування (*Lazy Binding*). У цьому режимі завантажувач заповнює таблицю GOT лише для глобальних змінних під час старту. Адреси функцій у секції `.got.plt` ініціалізуються вказівниками на службову процедуру завантажувача `_dl_runtime_resolve()`. Коли програма вперше викликає зовнішню функцію через PLT, процедура розв'язує адресу, записує її в GOT і передає керування коду.

У сучасних дистрибутивах Linux з міркувань безпеки стандартом стало повне негайне зв'язування (*Full RELRO*, прапорці `-Wl,-z,relro,-z,now`):
* Завантажувач розв'язує абсолютно всі символи та функції негайно під час старту процесу;
* Після завершення релокації завантажувач викликає системний виклик `mprotect()`, переводячи секції `.got` та `.got.plt` у режим «лише для читання» (`PROT_READ`).
Це унеможливлює експлуатацію вразливостей через перезапис таблиць GOT, проте вимагає обов'язкової наявності всіх експортованих символів у знайдених бібліотеках під час старту.

### Пастка абсолютних шляхів та динамічний токен `$ORIGIN`

Найпоширеніша помилка розробників полягає у компіляції програми з фіксованими шляхами робочої станції: `-Wl,-rpath,/home/developer/projects/telemetry/lib`. На машині клієнта каталогу `/home/developer` не існує, тому завантажувач пропускає цей крок і намагається завантажити системну бібліотеку хоста, яка може мати зовсім іншу версію або бути відсутньою.

Для створення повністю переносних пакетів стандарт ELF підтримує спеціальний динамічний токен `$ORIGIN`. Під час виконання завантажувач `ld.so` автоматично розгортає рядок `$ORIGIN` в абсолютний шлях до каталогу, де фізично розташований сам виконуваний файл.

Якщо бінарник встановлено у каталог `/opt/telemetry/bin/telemetry-agent`, а його власні бібліотеки розміщено у `/opt/telemetry/lib/`, правильне лінкування здійснюється командою:

```sh
$ gcc main.o -o telemetry-agent -Wl,-rpath,'$ORIGIN/../lib' -Wl,--enable-new-dtags -L../lib -lssl -lcrypto
```

Прапорець `-Wl,--enable-new-dtags` змушує компонувальник `ld` створити тег `DT_RUNPATH` замість застарілого `DT_RPATH`, що зберігає можливість перевизначення шляхів через `LD_LIBRARY_PATH` у процесі налагодження.

### Транзитивні залежності та прапорець DF_1_TRANS

Важливою архітектурною особливістю тегу `DT_RUNPATH` є його не-транзитивність за замовчуванням. Якщо головний двійковий файл `A` має `DT_RUNPATH = '$ORIGIN/../lib'`, він успішно знаходить бібліотеку `B.so` у власному каталозі. Проте якщо бібліотека `B.so` має власну залежність від `C.so`, динамічний завантажувач не використовує `DT_RUNPATH` головного бінарника для пошуку `C.so`, якщо тільки у заголовках не встановлено спеціальний прапорець `DF_1_TRANS`. Для надійного зв'язування розробник зобов'язаний встановлювати `DT_RUNPATH = '$ORIGIN'` на абсолютно кожну спільну бібліотеку, що входить до складу дистрибутивного пакета.

### Пастка затінення бібліотек (Diamond Dependency Trap)

Спроба вирішити проблему нестачі бібліотек глобальним додаванням каталогів до `LD_LIBRARY_PATH` (`export LD_LIBRARY_PATH=/opt/my-app/lib:$LD_LIBRARY_PATH`) часто призводить до затінення системних залежностей. Якщо каталог `/opt/my-app/lib` містить специфічну збірку `libcrypto.so.3`, стандартні системні утиліти (`ssh`, `curl`, `git`), запускаючись у тій самій оболонці, почнуть завантажувати цю версію замість системної. Якщо в кастомній бібліотеці відсутні певні версійні символи, системні команди перестануть працювати з помилками зв'язування.

## 3. Третій бар'єр: версіонування символів у glibc та одностороння сумісність

Навіть якщо всі необхідні файли `.so` присутні на цільовій машині та мають ідентичні назви (наприклад, головна системна бібліотека `/lib/x86_64-linux-gnu/libc.so.6`), запуск може завершитися аварією через механізм **версіонування символів** (*Symbol Versioning*).

Стандартна бібліотека C у Linux (GNU C Library, glibc) використовує версіонування символів для збереження сумісності зі старими бінарниками. Коли розробники glibc змінюють сигнатуру функції або внутрішній формат структур (наприклад, перехід на 64-бітні лічильники часу у `stat()` чи зміна розміру структур блокування у `pthread_create()`), вони не видаляють стару реалізацію. В одній бібліотеці `libc.so.6` одночасно зберігаються кілька варіантів однієї функції, прив'язаних до версійних вузлів: `stat@GLIBC_2.2.5`, `stat@GLIBC_2.33` тощо.

Під час компіляції програми системний компонувальник фіксує у спеціальній секції `.gnu.version_r` бінарника точні версії всіх функцій, які надавала glibc на компіляційній машині:

```sh
$ readelf -V /opt/bin/telemetry-agent

Version needs section '.gnu.version_r' contains 1 entry:
  File: libc.so.6 contains 2 entries:
    0x0d696914: Version: GLIBC_2.34
    0x0963cf85: Version: GLIBC_2.28
```

Коли програма стартує на іншій машині, завантажувач перевіряє секцію `.gnu.version_r` виконуваного файлу і звіряє кожен версійний вузол із секцією `.gnu.version_d` цільової бібліотеки `libc.so.6`.

Звідси випливає фундаментальне правило бінарної сумісності GNU glibc:
**Зворотна сумісність (Backwards Compatibility) гарантована, пряма сумісність (Forwards Compatibility) — відсутня.**

```
Бінарник зібрано на старій glibc (2.28)  ──►  Запуск на новій glibc (2.38)  ──►  УСПІХ  (старі версії присутні)
Бінарник зібрано на новій glibc (2.38)   ──►  Запуск на старій glibc (2.28)  ──►  КРАХ   (GLIBC_2.34 not found)
```

### Велика консолідація glibc 2.34

Найбільш помітний розрив сумісності останніх років стався у випуску glibc 2.34 (серпень 2021 року). Історично функції роботи з потоками (`pthread_create`, `pthread_mutex_lock`), динамічним завантаженням (`dlopen`, `dlsym`) та таймерами реального часу (`clock_gettime`) жили в окремих бібліотеках: `libpthread.so.0`, `libdl.so.2`, `librt.so.1`.

Починаючи з glibc 2.34, усі ці допоміжні бібліотеки було ліквідовано як окремі бінарні сутності та повністю інтегровано в монолітне тіло головної бібліотеки `libc.so.6`. Водночас усі функції потоків та динамічного завантаження дістали версійний суфікс `GLIBC_2.34`.

Як наслідок, будь-яка багатопотокова програма на C або C++, скомпільована на сучасному дистрибутиві (Ubuntu 22.04+, Fedora 35+, Debian 12+), автоматично фіксує залежність від `GLIBC_2.34`. Спроба запустити такий бінарник на стабільних дистрибутивах попередніх релізів (Debian 11 Bullseye з glibc 2.31, Ubuntu 20.04 з glibc 2.31 або RHEL/CentOS 7 з glibc 2.17) миттєво викликає аварійне завершення:
```
libc.so.6: version 'GLIBC_2.34' not found (required by ./telemetry-agent)
```

### Рефакторинг сімейства `stat` у glibc 2.33

Ще один поширений збій виникає через зміну інтерфейсу системних функцій `stat`, `fstat`, `lstat` у випуску glibc 2.33. Усі попередні версії glibc перенаправляли виклики `stat` на внутрішні функції `__xstat` та `__fxstat`, які приймали версійний аргумент (наприклад, `_STAT_VER = 3`). Починаючи з glibc 2.33, внутрішні функції `__xstat` було оголошено застарілими на користь прямих системних викликів ядра `statx()`. Програма, скомпільована на glibc 2.33+, при запуску на старішій glibc шукає прямий експорт `stat@GLIBC_2.33`, якого на старому хості немає, і завершується помилкою `undefined symbol: stat`.

### Директива `.symver` та точковий контроль сумісності

Якщо розробник змушений компілювати код на свіжій системі, але хоче уникнути прив'язки до нових версій символів glibc, використовується директива асемблера `.symver`. Наприклад, функція `memcpy` у glibc 2.14 отримала версію `memcpy@@GLIBC_2.14` з оптимізаціями під AVX-регістри. Щоб змусити компілятор лінкувати старішу сумісну версію `GLIBC_2.2.5`, у вихідний код C/C++ додають директиву `__asm__(".symver memcpy, memcpy@GLIBC_2.2.5");`. Це гарантує, що скомпільований об'єктний файл вимагатиме від цільової системи вузол `GLIBC_2.2.5`, усуваючи збій запуску на старих дистрибутивах.

Повний перелік параметрів діагностики завантажувача та утиліт аналізу ELF структуровано у вставці [Довідник діагностики динамічного завантажувача та утиліт аналізу ELF](guide:unix/why-it-runs-here-not-there/api-runtime-diagnostics.md).

## 4. Четвертий бар'єр: несумісність реалізацій C-Runtime — glibc проти musl

Якщо інтерпретатор та версії символів узгоджені, програма починає взаємодіяти з самою стандартною бібліотекою C. В операційній системі Linux домінують дві фундаментально несумісні реалізації: **GNU C Library (glibc)** та **musl libc**.

Обидві бібліотеки надають інтерфейси стандарту POSIX C і здійснюють однакові системні виклики до ядра Linux. Проте їхні внутрішні двійкові структури, розміщення полів у пам'яті, аллокатори та поведінка потоків кардинально відрізняються:

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                             ДВІЙКОВИЙ РОЗКОЛ RUNTIME                             │
├────────────────────────────────────────┬─────────────────────────────────────────┤
│                glibc                   │                musl libc                │
├────────────────────────────────────────┼─────────────────────────────────────────┤
│ Завантажувач:                          │ Завантажувач:                           │
│   /lib64/ld-linux-x86-64.so.2          │   /lib/ld-musl-x86_64.so.1              │
│ Аллокатор пам'яті:                     │ Аллокатор пам'яті:                      │
│   ptmalloc3 (арени під кожен потік)    │   mallocng (захист від переповнення)    │
│ Розмір стека потоку:                   │ Розмір стека потоку:                    │
│   типово 8 МБ (pthread_create)         │   типово 128 КБ (pthread_create)        │
│ Служба імен (NSS):                     │ Служба імен (NSS):                      │
│   динамічні плагіни /lib/libnss_*.so   │   монолітний статичний DNS/resolv       │
│ Розмір двійкового коду:                │ Розмір двійкового коду:                 │
│   ~2.2 МБ (динамічна libc.so.6)        │   ~650 КБ (монолітне ядро рантайму)     │
└────────────────────────────────────────┴─────────────────────────────────────────┘
```

Головні наслідки цього розколу:

* **Неможливість динамічного змішування:** бібліотеку, скомпільовану під glibc, неможливо завантажити через `dlopen()` у процес під керуванням musl. Структури опису потоків `pthread_t`, дескриптори відкритих потоків `FILE` та блоки локальної пам'яті потоків (Thread-Local Storage, TLS) мають різний внутрішній розмір і зміщення полів, що призводить до миттєвого руйнування пам'яті.
* **Різниця в розмірі стека:** у glibc виклик `pthread_create()` створює потік зі стеком 8 МБ (або 2 МБ на деяких архітектурах). У musl початковий стек становить лише 128 КБ. Програма, яка виділяє великі буфери на стеку (`char buffer[256 * 1024]`), на glibc працює стабільно, а на musl падає через переповнення стека з сигналом `SIGSEGV`.
* **Служба Name Service Switch (NSS):** бібліотека glibc реалізує модульну службу NSS, яка під час викликів `getpwnam()` або `getaddrinfo()` динамічно завантажує плагіни `/lib/x86_64-linux-gnu/libnss_files.so.2` та `/lib/x86_64-linux-gnu/libnss_dns.so.2`. Якщо скомпілювати програму під glibc прапорцем `-static`, функція `getaddrinfo()` все одно намагатиметься завантажити ці спільні бібліотеки під час виконання, і резолвінг імен зламається у середовищі без glibc. Натомість musl містить компактний статичний DNS-клієнт, що робить його статичні бінарники повністю самодостатніми.

### Моделі пам'яті локальних змінних потоків (Thread-Local Storage)

Ще одна прихована пастка криється в реалізації пам'яті TLS (`__thread` або `thread_local`). Компілятори підтримують чотири моделі доступу до TLS:
1. `global-dynamic` — універсальна модель через виклик `__tls_get_addr()`;
2. `local-dynamic` — оптимізація для змінних у межах одного модуля;
3. `initial-exec` — пряме зміщення відносно регістра сегмента (`%fs` на x86-64), що вимагає виділення статичного блоку TLS під час старту;
4. `local-exec` — прямий доступ для головного виконуваного файлу.

Якщо спільну бібліотеку скомпільовано з моделлю `initial-exec` для прискорення доступу, а потім завантажено під час виконання через `dlopen()`, динамічний завантажувач glibc може видати помилку `cannot allocate memory in static TLS block`, якщо статичний резерв TLS процесу вичерпано. Натомість у musl розмір блоку TLS є фіксованим, що вимагає компіляції плагінів виключно з прапорцем `-ftls-model=global-dynamic`.

## 5. П'ятий бар'єр: невидимий контекст оточення — PATH, локалі та дескриптори

Коли всі двійкові залежності завантажено та зв'язано, керування передається на блок ініціалізації середовища процесу. На цьому етапі виконуються функції-конструктори з секції `.init_array`, після чого керування переходить у функцію `main()`. Програма починає взаємодіяти зі змінними середовища `envp`, системними таблицями та спадковими дескрипторами.

### Пастка локалей (`LC_ALL`, `LANG`, `LC_CTYPE`, `LC_NUMERIC`)

Більшість програм під час старту ініціалізують системну локаль за допомогою виклику `setlocale(LC_ALL, "")`. Цей виклик зчитує змінні середовища `LC_ALL`, `LC_CTYPE` або `LANG` і завантажує правила сортування, форматування чисел та таблиці кодувань із системного архіву `/usr/lib/locale/locale-archive`.

Якщо на робочій станції встановлено локаль `uk_UA.UTF-8` або `en_US.UTF-8`, а на мінімальному цільовому сервері чи в контейнері цей мовний пакет не згенеровано утилітою `locale-gen`, виникають три критичні проблеми:

1. **Збій обробки символів UTF-8:** виклик `setlocale()` повертає `NULL`, залишаючи активною стандартну локаль `"C"` (ASCII). Усі функції обробки багатобайтових рядків (`mbrtowc()`, `mbtowc()`) починають вважати байти з кодом вище 127 помилковими, що призводить до обриву парсингу конфігураційних файлів.
2. **Роздільник дробової частини в числах (`LC_NUMERIC`):** у багатьох європейських локалях дробовим роздільником є кома `,` замість крапки `.`. Якщо програма зчитує конфігурації або файли JSON через функції `sscanf()`, `strtod()` чи `atof()`, число `3.14` буде прочитано як `3.0` (оскільки обробка зупиниться на крапці), що спричиняє приховані логічні помилки в розрахунках.
3. **Порядок сортування рядків (`LC_COLLATE`):** функція `strcoll()` повертає різні результати в локалях `"C"` та `"en_US.UTF-8"`, що руйнує очікуваний порядок у відсортованих структурах даних.

Ініціалізація локалі в C та C++:

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <locale.h>

int init_runtime_locale(void) {
    /* Спроба ініціалізувати локаль із середовища */
    if (setlocale(LC_ALL, "") == NULL) {
        /* Fallback на безпечну UTF-8 локаль за замовчуванням */
        if (setlocale(LC_ALL, "C.UTF-8") == NULL) {
            setlocale(LC_ALL, "C");
        }
    }
    /* Примусова фіксація крапки як десяткового роздільника для парсингу даних */
    setlocale(LC_NUMERIC, "C");
    return 0;
}
```
```cpp
#include <iostream>
#include <locale>
#include <clocale>

void init_runtime_locale() {
    // Спроба встановити глобальну локаль C++ з оточення
    try {
        std::locale::global(std::locale(""));
        std::cin.imbue(std::locale());
        std::cout.imbue(std::locale());
    } catch (const std::runtime_error &) {
        // Fallback на безпечну локаль C.UTF-8 або класичну C
        try {
            std::locale::global(std::locale("C.UTF-8"));
        } catch (...) {
            std::locale::global(std::locale::classic());
        }
    }
    // Фіксація числового форматування C для надійного парсингу float/double
    std::setlocale(LC_NUMERIC, "C");
}
```
:::

### Пастка шляху пошуку утиліт (`PATH`), лімітів ресурсів та дескрипторів

Якщо програма породжує дочірні процеси через виклики `popen()`, `system()` або сімейство `execvp()`, вона спирається на змінну середовища `PATH`.

Між різними дистрибутивами Linux існує суттєва різниця у структурі каталогів:
* Сучасні дистрибутиви з підтримкою концепції *UsrMerge* об'єднують каталоги `/bin` та `/sbin` у символьні посилання на `/usr/bin` та `/usr/sbin`.
* У старіших або мінімальних дистрибутивах системні утиліти (наприклад, `ip`, `iptables`, `ifconfig`) розташовані виключно в `/sbin` або `/usr/sbin`. Якщо не-привілейований користувач запускає службу, його змінна `PATH` типово містить лише `/usr/bin:/bin`. Спроба викликати команду `ip route` завершується помилкою `127 (Command not found)`.

Додатково системні збої часто спричиняються різницею в лімітах ресурсів (*Resource Limits*) та успадкуванням відкритих дескрипторів:
1. **Ліміт відкритих файлів (`RLIMIT_NOFILE`):** в інтерактивній оболонці користувача ліміт `ulimit -n` часто налаштований на `1048576`, тоді як системна служба під керуванням systemd за замовчуванням на старих системах отримує ліміт у `1024` файлові дескриптори. Служба, яка ідеально працює під час ручного тестування, зазнає аварії при високому мережевому навантаженні у виробничому середовищі.
2. **Витік спадкових дескрипторів:** якщо батьківський процес відкриває сокети чи файли без прапорця `O_CLOEXEC` / `FD_CLOEXEC`, усі дочірні процеси успадковують відкриті дескриптори. Це призводить до блокування мережевих портів та унеможливлює плавний перезапуск служб.

## 6. Протокол діагностики: як знайти причину відмови за 6 кроків

Коли двійковий файл відмовляється запускатися на цільовій системі, системний інженер застосовує послідовний алгоритм діагностики:

```
                    ДІАГНОСТИЧНИЙ МАРШРУТ
                    
  [ Двійковий файл ]
          │
          ▼
   1. file ./app           ──► Перевірка архітектури (x86-64 vs ARM) та зв'язування
          │
          ▼
   2. readelf -l ./app     ──► Перевірка існування інтерпретатора PT_INTERP
          │
          ▼
   3. readelf -d ./app     ──► Аналіз DT_NEEDED, DT_RPATH та DT_RUNPATH
          │
          ▼
   4. readelf -V ./app     ──► Перевірка версій символів GLIBC_X.Y у .gnu.version_r
          │
          ▼
   5. ldd ./app            ──► Перевірка наявності всіх спільних бібліотек .so
          │
          ▼
   6. LD_DEBUG=libs ./app  ──► Покрокове трасування пошуку та зв'язування ld.so
```

### Крок 1: Перевірка типу файлу та архітектури (`file`)
```sh
$ file ./telemetry-agent
./telemetry-agent: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=..., for GNU/Linux 3.2.0, not stripped
```
Команда `file` дає базову відповідь: чи відповідає архітектура процесору (`x86-64`), чи є файл динамічно зв'язаним (`dynamically linked`) та який інтерпретатор очікується.

### Крок 2: Перевірка наявності інтерпретатора
```sh
$ ls -l /lib64/ld-linux-x86-64.so.2
-rwxr-xr-x 1 root root 212568 Feb 12 14:20 /lib64/ld-linux-x86-64.so.2
```
Якщо файл інтерпретатора відсутній — це пряма причина помилки `No such file or directory`.

### Крок 3: Перевірка залежностей та шляхів пошуку
```sh
$ readelf -d ./telemetry-agent | grep -E '(NEEDED|RPATH|RUNPATH)'
 0x0000000000000001 (NEEDED)             Shared library: [libssl.so.3]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN/../lib]
```

### Крок 4: Перевірка зв'язування бібліотек у системі (`ldd`)
```sh
$ ldd ./telemetry-agent
	linux-vdso.so.1 (0x00007ffd399df000)
	libssl.so.3 => /usr/lib/x86_64-linux-gnu/libssl.so.3 (0x00007f3c14a00000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f3c14800000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f3c14b5a000)
```
Якщо біля якоїсь бібліотеки виведено рядок `not found`, це означає, що завантажувач не зміг знайти відповідний файл у жодному з каталогів пошукової ієрархії.

> [!CAUTION]
> Утиліта `ldd` є скриптом оболонки, який для аналізу бінарника запускає його з встановленою змінною `LD_TRACE_LOADED_OBJECTS=1`. Ніколи не запускайте `ldd` над неперевіреними двійковими файлами від ненадійних джерел, оскільки зловмисний бінарник зі спеціальним інтерпретатором може виконати довільний код. Безпечною альтернативою є виклик:
> ```sh
> $ /lib64/ld-linux-x86-64.so.2 --list ./telemetry-agent
> ```

### Крок 5: Покрокове трасування завантажувача (`LD_DEBUG`)
Якщо програма падає без явних повідомлень або завантажує неправильну версію бібліотеки через перекриття шляхів, вмикають внутрішній трасувальник завантажувача:

```sh
$ LD_DEBUG=libs,files,versions ./telemetry-agent
```
Завантажувач виведе в консоль кожен крок: які каталоги він сканує, які файли відкриває та які версії символів перевіряє.

Практичний алгоритм автоматизованого створення самодостатнього переносного пакета програми разом з усіма залежними бібліотеками та відносними шляхами `$ORIGIN` розглянуто у вставці [Створення герметичного переносного бандла для Linux](guide:unix/why-it-runs-here-not-there/proj-portable-bundle.md).

## 7. Синтез: інженерні стратегії надійного поширення програм

Для забезпечення надійного запуску програм на різноманітних дистрибутивах Linux у сучасній інженерній практиці сформувалися чотири основні стратегії:

```
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│                          МАТРИЦЯ СТРАТЕГІЙ ПОСТАВКИ ПЗ У LINUX                              │

│                   │ (-static)        │ бандл ($ORIGIN) │ (Docker/Podman)  │ (.deb / .rpm)   │
├───────────────────┼──────────────────┼─────────────────┼──────────────────┼─────────────────┤
│ Сумісність glibc  │ Повна (немає     │ Висока (якщо    │ Абсолютна        │ Тільки цільовий │
│                   │ залежності)      │ стара базова)   │ (своя rootfs)    │ дистрибутив     │
│ Розмір файлу      │ Мінімальний      │ Середній        │ Великий          │ Мінімальний     │
```

Розуміння конвеєра запуску перетворює помилку «It works on my machine» з прикрого сюрпризу на чітку інженерну задачу: знайти розірвану ланку між заголовком `PT_INTERP`, пошуком `DT_RUNPATH`, версіями `GLIBC_X.Y`, моделлю C-Runtime та середовищем процесу — і зафіксувати її на рівні збирання чи пакування програми.

### Включення функцій strlcpy та strlcat у glibc 2.38

Останній показовий приклад розриву прямої сумісності відбувся у випуску glibc 2.38 (серпень 2023 року), де функції безпечного копіювання рядків `strlcpy` та `strlcat` (історично запозичені з OpenBSD) було нарешті включено безпосередньо у стандартний простір імен заголовка `<string.h>`. Якщо розробник компілює програму на Ubuntu 24.04 або Fedora 39 з використанням цих функцій, компілятор зв'язує їх із вузлом `GLIBC_2.38`. При спробі запуску такого бінарника на попередніх випусках дистрибутивів (наприклад, Ubuntu 22.04 з glibc 2.35) динамічний завантажувач негайно зупиняє виконання через відсутність версійного вузла `GLIBC_2.38` у хостовій бібліотеці.
