## Архітектура та рівні буферизації введення/виведення (I/O Buffering)

Операційна система Linux та стандартна бібліотека `libc` підтримують три базові режими буферизації для потоків типу `FILE*` (дескриптори `0`, `1`, `2`):

```
_IONBF  [Unbuffered]:     дані скидаються системним викликом write() негайно при кожному виклику fputc/fwrite.
_IOLBF  [Line Buffered]:  дані накопичуються в буфері та скидаються системним викликом write() при появі '\n'.
_IOFBF  [Fully Buffered]: дані скидаються системним викликом write() виключно після повного заповнення (4096 B).
```

### Механізм роботи утиліти stdbuf

Утиліта `stdbuf` не модифікує бінарні файли програм і не змінює системні виклики ядра напряму. Її робота ґрунтується на динамічному завантаженні спеціальної бібліотеки-перехоплювача:

1. `stdbuf` встановлює змінну оточення `LD_PRELOAD=/usr/libexec/coreutils/libstdbuf.so` (або відповідний системний шлях бібліотеки `libstdbuf.so`);
2. Конструктор бібліотеки `libstdbuf.so` викликається динамічним лінкером під час старту процесу ще до передачі керування у точку входу `main()`;
3. Бібліотека зчитує змінні оточення `_STDBUF_I`, `_STDBUF_O`, `_STDBUF_E` та ініціює виклики `setvbuf(stdin, ...)`, `setvbuf(stdout, ...)`, `setvbuf(stderr, ...)` з потрібними прапорцями;
4. Якщо програма скомпільована статично (наприклад, Go-бінарник або Rust без динамічної лінковки libc), механізм `LD_PRELOAD` не спрацьовує, і `stdbuf` не має жодного впливу на її внутрішню буферизацію.

### Таблиця прапорців для ліквідації буферних затримок

| Інструмент | Прапорець / Метод | Принцип дії | Типове використання |
|---|---|---|---|
| `grep` | `--line-buffered` | Викликає `fflush(stdout)` після кожного рядка, що збігся з патерном | `tail -f app.log \| grep --line-buffered ERR` |
| `sed` | `-u` або `--unbuffered` | Читає найменшими доступними порціями та скидає вивід після кожної команди | `tail -f app.log \| sed -u 's/foo/bar/'` |
| `awk` | `fflush()` | Примусово скидає внутрішній буфер поточного каналу виводу | `tail -f app.log \| awk '{print $1; fflush()}'` |
| `tcpdump` | `-l` | Перемикає стандартний вивід у режим `_IOLBF` (Line Buffered) | `tcpdump -l -nn -i eth0 \| grep 'HTTP'` |

## Конфігурація та алгоритмічні особливості утиліти sort

Утиліта `sort` є найважчим компонентом більшості конвеєрів, оскільки вона є **блокуючим бар'єром**: вона не може передати жодного байта споживачу, доки не прочитає весь вхідний потік до кінця.

### Алгоритм зовнішнього сортування злиттям (External Merge Sort)

Коли обсяг вхідного потоку перевищує обсяг виділеної оперативної пам'яті (`sort -S`), утиліта працює за трифазною схемою:

1. **Фаза розбиття на прогони (Runs Generation):** `sort` зчитує порцію даних, яка вміщується в пам'ять (наприклад, 2 ГБ), сортує її за допомогою швидкого сортування (QuickSort / In-Memory Radix Sort) і записує впорядкований прогін у тимчасовий файл у каталозі `/tmp`.
2. **Фаза черги з пріоритетами (K-Way Merge):** Коли вхідний потік вичерпано, утиліта відкриває всі створені тимчасові файли і зливає їх за допомогою мінімальної купи (Min-Heap / Tournament Tree).
3. **Фаза видачі результату:** Відсортований результуючий потік передається у вихідний канал.

### Ключові прапорці оптимізації сортування

```bash
LC_ALL=C sort --parallel=8 --buffer-size=2G --temporary-directory=/mnt/fast_nvme -k1,1 -k2,2n -u
```

- `LC_ALL=C` — вимикає порівняння за правилами локалі `strcoll()`. Перемикає порівняння на пряме побайтове віднімання `strcmp()`, що забезпечує прискорення сортування від 4 до 10 разів;
- `-S 2G` або `--buffer-size=2G` — встановлює максимальний ліміт оперативної пам'яті для фази внутрішнього сортування. Чим більший розмір буфера, тим менше операцій запису на диск виконує `sort`;
- `-T /path/to/dir` — призначає каталог для тимчасових прогонів. Використання файлової системи `tmpfs` у RAM або швидкого NVMe мінімізує затримки дискового введення/виведення;
- `--parallel=N` — кількість паралельних потоків для сортування прогонів у багатоядерних системах;
- `-k POS1[,POS2]` — точне визначення діапазону полів для сортування (наприклад, `-k 1,1` сортує виключно за першим стовпчиком, ігноруючи решту рядка);
- `-u` або `--unique` — видалення дублікатів безпосередньо під час злиття, що усуває потребу в окремому етапі `| uniq`;
- `--compress-program=gzip` — примусове стискання тимчасових файлів на льоту при сортуванні терабайтних масивів, що зменшує навантаження на диск ціною додаткових тактів процесора.

## Контракти статусів виходу та сигнали в конвеєрах

За замовчуванням стандартна оболонка POSIX повертає у спеціальній змінній `$?` статус завершення **виключно останньої команди** у конвеєрі.

### Системні режими обробки статусів

1. **Режим суворої обробки `set -o pipefail`:**
   ```bash
   set -o pipefail
   ```
   *Правило:* Статус конвеєра дорівнює `0`, якщо всі команди повернули `0`. Якщо хоча б одна команда завершилася з помилкою, конвеєр повертає код виходу найбільш правої команди, що завершилася з ненульовим статусом.

2. **Масив `$PIPESTATUS` (Bash) та `$pipestatus` (Zsh):**
   ```bash
   cmd1 | cmd2 | cmd3
   # У Bash:
   echo "${PIPESTATUS[0]} ${PIPESTATUS[1]} ${PIPESTATUS[2]}"
   ```
   *Правило:* Містить масив кодів повернення для кожного окремого процесу конвеєра. Масив оновлюється після кожного виконаного конвеєра.

3. **Коди завершення при доставці сигналів:**
   Якщо процес у конвеєрі завершився через отримання сигналу, оболонка повертає код `128 + Номер_сигналу`.

| Код виходу | Сигнал / Причина | Опис ситуації в конвеєрі |
|---|---|---|
| `0` | `EXIT_SUCCESS` | Успішне завершення процесу |
| `1` | `EXIT_FAILURE` | Загальна помилка виконання або відсутність збігів у `grep` |
| `2` | Синтаксична помилка | Неправильні аргументи командного рядка утиліти |
| `130` | `SIGINT` (128 + 2) | Переривання користувачем через `Ctrl+C` |
| `137` | `SIGKILL` (128 + 9) | Примусове знищення процесу (або OOM Killer ядра) |
| `141` | `SIGPIPE` (128 + 13) | Спроба запису в канал без читачів (норма при роботі з `head`) |
| `143` | `SIGTERM` (128 + 15) | Сигнал штатного завершення процесу |

### Обробка SIGPIPE у виробничих конвеєрах

Коли споживач (наприклад, `head -n 10`) зчитує потрібну кількість рядків і закриває свій дескриптор `stdin`, ядро Linux надсилає сигнал `SIGPIPE` виробнику (`grep` або `cat`).

За замовчуванням більшість утиліт завершуються з кодом `141`. Якщо в сценарії увімкнено `set -e` та `set -o pipefail`, такий код спричинить аварійне завершення скрипту. Для штатного ігнорування `SIGPIPE` використовують перевірку:

```bash
cmd1 | head -n 10 || {
    status=$?
    if [ "$status" -ne 141 ] && [ "$status" -ne 0 ]; then
        echo "Помилка конвеєра з кодом: $status" >&2
        exit "$status"
    fi
}
```

## Діагностика вузьких місць за допомогою Pipe Viewer (pv)

Утиліта `pv` (Pipe Viewer) діє як прозорий посередник між процесами, вимірюючи швидкість передачі даних, відсоток заповнення буферів та локалізуючи вузькі місця:

```bash
cat huge.log | pv -cN raw_in | grep ' 500 ' | pv -cN filtered | awk '{print $1}' | pv -cN projected > /dev/null
```

- Опція `-c` забезпечує вивід кількох смуг прогресу в одному терміналі;
- Опція `-N name` призначає мітку кожній точці вимірювання;
- Опція `-B 4M` вимірює рівень заповненості проміжного буфера: якщо буфер після `grep` постійно заповнений на 100%, це означає, що вузьким місцем конвеєра є наступний споживач (`awk`).

## Підстановка процесів (Process Substitution)

Коли аналітична задача вимагає об'єднання кількох незалежних потоків без використання тимчасових файлів, оболонка надає синтаксис підстановки процесів `<(cmd)` та `>(cmd)`:

```bash
diff -u <(grep '200' today.log | cut -d' ' -f1 | sort -u) \
        <(grep '200' yesterday.log | cut -d' ' -f1 | sort -u)
```

1. Оболонка створює анонімні канали в ядрі або файли дескрипторів `/dev/fd/63`, `/dev/fd/62`;
2. Запускає підкоманди у фонових підоболонках, перенаправляючи їхній `stdout` у створені дескриптори;
3. Передає шляхи `/dev/fd/N` як звичайні файлові аргументи основній програмі `diff`.

## Керування параметрами каналів на рівні ядра Linux

Ядро Linux надає механізми перевірки та зміни місткості кільцевих буферів каналів через інтерфейс `fcntl` та псевдофайлову систему `procfs`:

1. **Глобальний ліміт місткості каналу:**
   Файл `/proc/sys/fs/pipe-max-size` містить максимальний розмір буфера, який непривілейований процес може встановити для каналу (за замовчуванням 1048576 байтів = 1 МБ).

2. **Зміна розміру буфера дескриптора:**
   Програма може збільшити буфер каналу для мінімізації блокувань при нерівномірному навантаженні:
:::tabs
```c
/* Зміна місткості буфера каналу у C */
fcntl(fd, F_SETPIPE_SZ, 1048576); // Збільшення буфера до 1 МБ
int current_size = fcntl(fd, F_GETPIPE_SZ);
```
```cpp
// Зміна місткості буфера каналу у C++
::fcntl(fd, F_SETPIPE_SZ, 1048576);
int current_size = ::fcntl(fd, F_GETPIPE_SZ);
```
