Інженер налаштовує параметри підключення до бази даних перед запуском міграції: вводить у терміналі `DATABASE_URL="postgres://app:secret@db.internal:5432/main"`, запускає бінарний файл `./migrate_db` і натрапляє на аварійну зупинку програми з помилкою `Fatal: database connection string is empty`. В іншому сценарії, під час агрегації системних метрик у конвеєрі `cat metrics.txt | while read -r line; do count=$((count + 1)); done`, команда `echo "Всього: $count"` друкує нуль, хоча цикл щойно успішно опрацював тисячу рядків логу.

В обох випадках інженер зіткнувся з фундаментальною властивістю архітектури Unix: змінні не є магічним загальносистемним реєстром, глобальною пам'яттю чи властивістю термінала. Змінна оболонки існує виключно як внутрішній вузол у приватній структурі даних одного конкретного процесу, а передача стану новому бінарному файлу або сусідній ланці конвеєра підпорядковується суворим апаратним і системним кордонам віртуального адресного простору.

## Анатомія пам'яті: як середовище живе у віртуальному просторі процесу

Щоб простежити, на якому саме етапі губиться змінна, необхідно розібрати внутрішню структуру пам'яті процесу в операційній системі Linux.

Змінні середовища (англ. *environment variables*, від лат. *environare* — «оточувати») — це набір нуль-термінованих байтових рядків формату `КЛЮЧ=ЗНАЧЕННЯ`, які операційна система завантажує у віртуальний адресний простір нової програми під час її запуску. Фізично цей блок даних розташовується на самому верху віртуального простору користувача, безпосередньо в області початкового стека процесу.

![Розташування аргументів та змінних середовища у пам'яті стека Linux](/root/course/unix/variable-did-not-reach-the-program/img/environ-memory-layout.svg)

*Розподіл пам'яті стека процесу під час передачі керування від ядра: рядки середовища зберігаються в найстарших адресах, а покажчики envp формують масив, доступний через глобальний покажчик environ.*

Коли ядро операційної системи виконує системний виклик `execve`, обробник виконуваних файлів ELF у ядрі (`fs/binfmt_elf.c`) виділяє початкові сторінки стека та формує структуру пам'яті в строго визначеному порядку, рухаючись від старших адрес віртуальної пам'яті до молодших:

1. **Блок рядків середовища**: послідовність байтів нуль-термінованих рядків (`"PATH=/usr/bin:/bin\0"`, `"USER=alex\0"`, `"HOME=/home/alex\0"`).
2. **Блок рядків аргументів**: байти аргументів командного рядка (`"argv[0]\0"`, `"argv[1]\0"`).
3. **Допоміжний вектор ядра (Auxiliary Vector, `auxv`)**: масив структур `Elf64_auxv_t`, через які ядро передає динамічному лінкеру низькорівневі системні параметри (розмір апаратної сторінки пам'яті `AT_PAGESZ`, адресу сегмента vDSO `AT_SYSINFO_EHDR`, 16 байтів апаратної ентропії для канарки захисту стека `AT_RANDOM` та точку входу виконуваного файлу `AT_ENTRY`).
4. **Таблиця покажчиків середовища (`char *envp[]`)**: масив 64-бітних адрес, де кожен елемент вказує на початок відповідного рядка в блоці рядків середовища. Масив завершується обов'язковим нульовим покажчиком `NULL`.
5. **Таблиця покажчиків аргументів (`char *argv[]`)**: масив адрес, що вказують на початки рядків аргументів у блоці аргументів, також завершений `NULL`.
6. **Кількість аргументів (`int argc`)**: ціле число на вершині стека, на яке вказує регістр покажчика стека `RSP` у момент передачі керування на точку входу `_start`.

### Ініціалізація в стандартній бібліотеці C (glibc / musl)

Коли керування отримує стартова функція стандартної бібліотеки C (`_start` у glibc), вона зчитує `argc`, `argv` та адресу першого елемента `envp` безпосередньо зі стека і зберігає покажчик на таблицю середовища у глобальній змінній:

:::tabs
```c
/* Глобальний покажчик на таблицю середовища у просторі користувача */
extern char **environ;
```
```cpp
#include <cstdlib>
#include <iostream>

// У C++ доступ до середовища здійснюється через std::getenv або глобальний environ
extern "C" char **environ;
```
:::

Коли програма звертається до функції `getenv("PATH")`, рантайм виконує звичайний лінійний прохід по масиву покажчиків `environ`:

```
environ[0] ──> "PATH=/usr/bin:/bin"   (знайдено збіг до знака '=', повертаємо покажчик на "/usr/bin:/bin")
environ[1] ──> "USER=alex"
environ[2] ──> "HOME=/home/alex"
environ[3] ──> NULL
```

Якщо змінної немає серед покажчиків масиву `environ`, функція `getenv()` повертає `NULL`. Програма не має жодного іншого апаратного чи системного механізму для виявлення внутрішніх змінних командної оболонки, крім цього явно завантаженого масиву.

### Мутації середовища на купі: setenv та putenv

Поки програма лише читає змінні через `getenv()`, масив покажчиків залишається на первинному стеку. Проте щойно процес викликає функцію `setenv("NEW_KEY", "value", 1)` для додавання нової змінної, бібліотека glibc змушена змінити розмір таблиці:

1. Функція `setenv` виділяє блок пам'яті на купі (`malloc`) для розміщення нового рядка `"NEW_KEY=value\0"`.
2. Оскільки початковий масив покажчиків `envp` на стеку затиснутий між іншими структурами даних і не може зростати, glibc виділяє на купі **новий масив покажчиків більшого розміру**.
3. Бібліотека копіює старі покажчики, записує адресу нового рядка, ставить у кінці `NULL` і перенаправляє глобальний покажчик `environ` на цей новий блок у купі.

Усі наступні виклики `setenv` лише реалокують масив у купі. Але цей новий масив існує **тільки в межах віртуальної пам'яті цього процесу**. Жодні зміни через `setenv` чи `putenv` ніколи не поширюються автоматично «вгору» — до батьківського процесу чи оболонки.

## Локальні змінні оболонки проти експортованих: прапорець export

Командна оболонка (Bash, Zsh, Dash) — це звичайна прикладна програма, яка працює в просторі користувача. Для збереження внутрішнього стану, проміжних результатів обчислень та аргументів функцій оболонка підтримує власну внутрішню таблицю символів — хеш-таблицю змінних `var_table`.

Кожен запис у цій таблиці є внутрішньою структурою даних:

:::tabs
```c
/* Концептуальна структура дескриптора змінної у вихідному коді GNU Bash (variables.h) */
typedef struct variable {
    char *name;              /* Ім'я змінної: "DATABASE_URL", "count", "PATH" */
    char *value;             /* Рядкове значення */
    char *exportstr;         /* Кешований рядок "NAME=VALUE" для масиву envp */
    int attributes;          /* Бітова маска прапорців (att_exported, att_readonly тощо) */
    int context;             /* Рівень вкладеності / контекст функції */
} SHELL_VAR;
```
```cpp
#include <string>
#include <cstdint>

namespace shell {
// Концептуальне представлення змінної оболонки на C++
struct ShellVariable {
    enum Flags : uint32_t {
        None = 0,
        Exported = 1 << 0,
        ReadOnly = 1 << 1,
        Integer  = 1 << 2,
        Array    = 1 << 3
    };

    std::string name;
    std::string value;
    uint32_t attributes{None};
};
}
```
:::

Коли користувач вводить у командному рядку просте присвоєння:

```bash
DATABASE_URL="postgres://app:secret@db.internal:5432/main"
```

Оболонка знаходить або створює вузол у своїй внутрішній хеш-таблиці `var_table`. Бітова маска `attributes` ініціалізується нулем (`0x00`). Це означає, що змінна є **локальною змінною оболонки**. Вона доступна для арифметики, умовних переходів та підстановок усередині самої оболонки (наприклад, `echo "$DATABASE_URL"`), але існує виключно у виділених сторінках динамічної пам'яті поточного процесу Bash.

![Життєвий цикл змінної від таблиці символів оболонки через fork до execve](/root/course/unix/variable-did-not-reach-the-program/img/shell-symbol-table-export-fork-exec.svg)

*Еволюція змінної під час запуску програми: неекспортовані змінні відсікаються на етапі підготовки масиву envp перед системним викликом execve.*

Коли користувач виконує зовнішню команду `./migrate_db`, оболонка виконує класичну двоетапну послідовність Unix:

1. **Клонування процесу (`fork`)**: оболонка звертається до ядра через системний виклик `fork()`. Ядро створює точний дублікат процесу оболонки. Завдяки механізму Copy-On-Write дочірній процес у першу мить бачить абсолютно всі внутрішні структури батька, включно з таблицею `var_table` та локальною змінною `DATABASE_URL`.
2. **Підготовка середовища дочірнім процесом**: перед тим як викликати `execve`, дочірній процес оболонки зобов'язаний змонтувати новий масив покажчиків `char **envp`. Оболонка викликає внутрішню функцію `maybe_make_export_env()`, яка обходить усі змінні у своїй таблиці символів і застосовує фільтр:

:::tabs
```c
/* Логіка фільтрації змінних перед системним викликом execve у Bash */
if (var->attributes & att_exported) {
    /* Змінна має прапорець експорту: формуємо рядок і додаємо в масив envp */
    export_env[env_index++] = var->exportstr ? var->exportstr : format_var(var);
} else {
    /* Локальна змінна: повністю ігноруємо! Вона НЕ потрапляє до масиву envp */
}
```
```cpp
#include <vector>
#include <string>
#include <format>

// Фільтрація експортованих змінних на C++
std::vector<std::string> build_export_environment(const std::vector<shell::ShellVariable>& var_table) {
    std::vector<std::string> envp_strings;
    for (const auto& var : var_table) {
        if (var.attributes & shell::ShellVariable::Exported) {
            envp_strings.push_back(std::format("{}={}", var.name, var.value));
        }
    }
    return envp_strings;
}
```
:::

3. Оскільки змінна `DATABASE_URL` не мала встановленого біта `att_exported`, вона **пропускається** і не потрапляє до сформованого масиву `export_env`.
4. **Заміна образу (`execve`)**: дочірній процес викликає системний виклик `execve("/path/to/migrate_db", argv, export_env)`.
5. Ядро операційної системи безповоротно очищає весь адресний простір дочірнього процесу, знищуючи код оболонки, її стек і внутрішню таблицю `var_table`. На новостворений стек програми записуються **лише ті рядки, які були передані в масиві `export_env`**.
6. Бінарний файл `./migrate_db` розпочинає виконання. Його виклик `getenv("DATABASE_URL")` повертає `NULL`, що призводить до аварійної зупинки.

Команда `export DATABASE_URL` (або синтаксичні еквіваленти `declare -x DATABASE_URL`, `typeset -x DATABASE_URL`) робить рівно одну операцію: виставляє бітовий прапорець `att_exported` у дескрипторі змінної. Після цього будь-яка наступна серіалізація масиву `envp` гарантовано включатиме цей рядок.

> 🔧 **Навіщо це.** Якби оболонка автоматично передавала абсолютно всі свої змінні дочірнім процесам, кожен запуск системної утиліти (`ls`, `grep`, `sed`) отримував би на стек масив із сотень внутрішніх лічильників циклів, тимчасових буферів та функціональних масивів скрипту. Це не лише марнувало б пам'ять ядра та процесорний час на копіювання сторінок стека, але й створювало б небезпечні колізії, коли локальна змінна скрипту `TMPDIR` чи `IFS` несподівано зламала б логіку стандартної утиліти.

## Експорт функцій оболонки та уроки вразливості Shellshock

Оболонка GNU Bash має унікальне розширення, якого немає в базовому стандарті POSIX: можливість експортувати не лише рядкові змінні, але й цілі функції оболонки через команду `export -f function_name`.

Оскільки ядро Linux у системному виклику `execve` розуміє виключно рядковий масив `КЛЮЧ=ЗНАЧЕННЯ` і не має концепції «функцій», Bash вимушений кодувати визначення функцій прямо всередині значень звичайних змінних середовища.

Історично Bash формував рядок такого вигляду:

```
my_func=() { echo "Hello from function"; }
```

Коли новий дочірній процес `bash` запускався через `execve`, він обходив усі отримані змінні `environ`. Якщо значення змінної починалося з магічних символів `() {`, оболонка автоматично парсила цей рядок і реєструвала його у своїй таблиці функцій.

Це інженерне рішення призвело до появи знаменитої критичної вразливості **Shellshock** (CVE-2014-6271). Парсер Bash продовжував виконувати будь-які команди, записані після закриваючої фігурної дужки `}`:

```bash
# Приклад атаки Shellshock:
HTTP_USER_AGENT="() { :; }; /bin/cat /etc/passwd"
```

Коли веб-сервер CGI запускав скрипт оболонки, передаючи заголовок клієнта через середовище, дочірній Bash автоматично виконував ін'єктовану команду від імені веб-сервера.

У сучасному Bash цей механізм захищено: експортовані функції отримують спеціальний префікс та суфікс у імені змінної (наприклад, `BASH_FUNC_my_func%%=() { ... }`), а парсер ядра оболонки суворо ізольований від виконання коду поза тілом функції.

## Одноразова передача змінних: синтаксис префікса

Часто змінну потрібно передати конкретному дочірньому процесу одноразово, без зміни глобального стану самої оболонки. Стандарт POSIX визначає для цього спеціальну граматичну форму — префіксне присвоєння:

```bash
DATABASE_URL="postgres://app:secret@db.internal:5432/main" ./migrate_db
```

Внутрішня механіка такого виклику суттєво відрізняється від попереднього виконання `export`:

1. Під час синтаксичного розбору рядка оболонка ідентифікує конструкції `NAME=VALUE`, що стоять перед назвою команди.
2. Вона обчислює значення правої частини у поточному контексті.
3. Оболонка викликає `fork()`.
4. У дочірньому процесі оболонка бере базовий список експортованих змінних і додає до нього тимчасовий елемент `"DATABASE_URL=postgres://..."`, формуючи розширений масив `envp`.
5. Викликається `execve()`. Програма `./migrate_db` успішно отримує значення змінної через `getenv()`.
6. Головний (батьківський) процес оболонки **не змінює власну таблицю `var_table`**. Після завершення команди `./migrate_db` змінна `DATABASE_URL` у поточному сеансі термінала залишається неіснуючою.

### Розбіжності стандарту POSIX та вбудовані команди (Builtins)

Поведінка префіксного присвоєння різниться залежно від того, викликається зовнішня програма чи спеціальна вбудована команда оболонки (Special Builtin: `eval`, `exec`, `set`, `shift`, `trap`, `export`, `readonly`, `.`/`source`):

- **Згідно зі стандартом POSIX**: якщо префіксне присвоєння використовується перед спеціальною вбудованою командою (наприклад, `VAR=value eval 'echo $VAR'`), змінна `VAR` залишається у таблиці символів оболонки **назавжди** навіть після завершення команди!
- **У Bash за замовчуванням**: префіксні змінні перед вбудованими командами залишаються локальними для виклику. Проте якщо увімкнути режим сумісності з POSIX (`set -o posix`), Bash переходить на строгу поведінку стандарту.

### Пастка порядку розкриття параметрів (Expansion Order Trap)

Найпідступніша помилка під час використання префіксного синтаксису виникає через нерозуміння черговості фаз розкриття командного рядка:

```bash
# Класична ілюстрація пастки:
FOO="bar" echo "$FOO"
```

Користувач сподівається побачити на екрані `bar`, але команда виводить порожній рядок (або попереднє значення змінної).

Причина полягає у суворому порядку розбору командного рядка оболонкою:

```
[Початковий рядок]         FOO="bar" echo "$FOO"
                                             │
1. Розкриття параметрів                      ▼
   (Parameter Expansion):  Оболонка читає $FOO зі СВОЄЇ поточної пам'яті (там пусто!)
                           Рядок стає: FOO="bar" echo ""
                                             │
2. Формування команди:     Команда: echo, Аргументи: [""], Тимчасовий envp: [FOO=bar]
                                             │
3. Виконання:              echo друкує свій аргумент "", не заглядаючи в envp!
```

Оскільки розкриття `$FOO` відбувається в батьківській оболонці **до** створення дочірнього процесу та до застосування префікса `FOO="bar"`, команда `echo` отримує як аргумент уже порожній рядок.

Щоб змінна була прочитана з новоствореного середовища, її розкриття має виконувати дочірній процес під час власної роботи:

```bash
FOO="bar" sh -c 'echo "$FOO"'
# Виведе: bar (оскільки дочірній sh розкриє $FOO зі свого масиву environ)
```

## Пастка конвеєрів та Subshell: чому зміни не повертаються

Найбільш масова проблема системного програмування на рівні оболонок — втрата значень змінних, які модифікуються всередині циклів, підключених до конвеєра.

Розглянемо класичний приклад підрахунку записів:

```bash
count=0

cat /var/log/syslog | while read -r line; do
    count=$((count + 1))
done

echo "Всього оброблено рядків: $count"
```

Запустивши цей скрипт, користувач незмінно отримує `Всього оброблено рядків: 0`, попри те що цикл коректно виконав тисячу ітерацій.

![Ізоляція пам'яті підпроцесів у конвеєрі](/root/course/unix/variable-did-not-reach-the-program/img/pipeline-subshell-isolation.svg)

*Конвеєр виконує цикл у дочірньому процесі підоболонки: мутації пам'яті відбуваються у приватних сторінках COW дитини та безслідно зникають після виклику exit(0).*

### Покроковий системний розбір ізоляції конвеєра

Специфікація стандарту POSIX.1 чітко визначає: кожен елемент командного конвеєра (`command1 | command2`) виконується в **окремому середовищі виконання** (subshell). У більшості сучасних оболонок (GNU Bash, Debian Almquist Shell / Dash) це реалізовано через окремі виклики `fork()`:

1. **Стан у батькові (PID 1000)**: Батьківський процес виділяє пам'ять під змінну `count = 0`.
2. **Створення каналу зв'язку**: Батько викликає системний виклик `pipe()`, створюючи пару дескрипторів для передачі байтів.
3. **Запуск генератора (PID 1001)**: Батько викликає `fork()`. Процес PID 1001 дублює дескриптор запису в канал на свій `stdout` (1) та виконує `execve("cat")`.
4. **Запуск споживача (Subshell, PID 1002)**: Батько викликає другий `fork()`. Процес PID 1002 дублює дескриптор читання з каналу на свій `stdin` (0) і починає інтерпретувати тіло циклу `while`.
5. **Робота всередині PID 1002**:
   - На старті PID 1002 має копію пам'яті батька, де `count = 0`.
   - На кожній ітерації процесор виконує інструкцію інкременту. Оскільки сторінка пам'яті позначена ядром як Read-Only для механізму Copy-On-Write, ядро перехоплює сторінкове переривання (Page Fault, функція `do_wp_page` у ядрі Linux), виділяє для PID 1002 **нову фізичну сторінку оперативної пам'яті** та записує змінене значення туди.
   - Значення `count` у фізичній пам'яті PID 1002 послідовно зростає: 1, 2, ..., 1000.
6. **Завершення конвеєра**:
   - Процес `cat` дочитує файл і завершується, закриваючи дескриптор запису каналу.
   - Читання в PID 1002 повертає `EOF` (0 байтів). Цикл `while` завершується.
   - Процес PID 1002 викликає системний вихід `exit(0)`.
   - **Ядро операційної системи повністю знищує таблиці сторінок та адресний простір PID 1002**. Фізична сторінка, де зберігалося число `1000`, повертається в загальний системний пул вільної пам'яті.
7. **Повернення до батька (PID 1000)**:
   - Батьківський процес, який очікував завершення конвеєра через системний виклик `waitpid()`, відновлює виконання.
   - Він переходить до наступного рядка: `echo "Всього оброблено рядків: $count"`.
   - Оболонка зчитує `count` зі **свого власного незмінного адресного простору**. Оскільки дочірній процес PID 1002 фізично не мав доступу до сторінок пам'яті батька, там залишається первинне значення: `0`.

### Чотири способи збереження стану після циклу

#### 1. Підстановка процесу (Process Substitution)

Найбільш надійний та ідіоматичний патерн для Bash та Zsh — винесення джерела даних у фоновий підпроцес, тоді як сам цикл виконується безпосередньо в основному процесі оболонки:

```bash
count=0

# Цикл while виконується у ГОЛОВНОМУ процесі!
while read -r line; do
    count=$((count + 1))
done < <(cat /var/log/syslog)

echo "Всього оброблено: $count" # Друкує реальне значення (наприклад, 1000)
```

Конструкція `< <(...)` створює анонімний канал зв'язку (доступний через віртуальний дескриптор `/dev/fd/63`) і перенаправляє його на стандартний вхід циклу через стандартний оператор перенаправлення `<`. Оскільки для циклу не створюється `subshell`, усі модифікації змінних відбуваються у пам'яті батьківської оболонки.

#### 2. Опція lastpipe у Bash

Починаючи з версії Bash 4.2, оболонка підтримує опцію `lastpipe`, яка змушує останню команду конвеєра виконуватися безпосередньо у поточному процесі оболонки:

```bash
# У неінтерактивних скриптах керування завданнями вимкнено за замовчуванням
shopt -s lastpipe

count=0
cat /var/log/syslog | while read -r line; do
    count=$((count + 1))
done

echo "Всього: $count" # Працює! Остання ланка виконана в поточному процесі.
```

> ⚠️ В інтерактивному сеансі термінала опція `lastpipe` не спрацює, якщо не вимкнути керування завданнями команди через `set +m`, оскільки термінал вимагає створення окремої групи процесів (Process Group) для кожної ланки конвеєра. Утиліти `ksh` (KornShell) та `zsh` історично виконують останню ланку конвеєра в поточному процесі за замовчуванням.

#### 3. Групування логіки у підоболонці

Якщо підсумковий результат потрібен лише для виконання подальших команд і його не обов'язково повертати у глобальний сеанс, можна згрупувати обробку за допомогою фігурних дужок `{ ... }`:

```bash
cat /var/log/syslog | {
    count=0
    while read -r line; do
        count=$((count + 1))
    done
    echo "Всього всередині підоболонки: $count"
    # Подальша робота з $count відбувається тут, до виходу з subshell
}
```

#### 4. Пряме перенаправлення файлу

Якщо вхідні дані зберігаються у файлі на диску, створення конвеєра є надлишковим:

```bash
count=0
while read -r line; do
    count=$((count + 1))
done < /var/log/syslog

echo "Всього: $count" # Працює без жодного додаткового процесу
```

## Системні ліміти ядра на розмір середовища: помилка E2BIG

Змінні середовища не можуть зростати нескінченно. В операційній системі Linux існує жорстке апаратне та програмне обмеження на сумарний обсяг байтів, які можна передати через масиви `argv` та `envp` у виклику `execve`.

Історично це обмеження задавалося константою `NCARGS`, а в сучасному ядрі Linux (починаючи з версії 2.6.23) обчислюється динамічно:

- Сумарний ліміт на всі рядки аргументів і середовища становить **1/4 від поточного ліміту стека процесу** (`RLIMIT_STACK`). При стандартному ліміті стека 8 МБ (`ulimit -s 8192`) максимальний обсяг середовища становить 2 МБ.
- Максимальний розмір одного окремого рядка змінної обмежений константою ядра `MAX_ARG_STRLEN` (32 сторінки пам'яті, що дорівнює 128 КБ на архітектурі x86-64).

Перевірити поточний системний ліміт можна через системну утиліту `getconf`:

```bash
getconf ARG_MAX
# Типове значення: 2097152 (2 мегабайти)
```

Якщо скрипт або програма намагається передати велетенський токен авторизації, бінарний сертифікат або дамп JSON розміром понад 128 КБ в одній змінній, або якщо загальний розмір усіх експортованих змінних перевищує 2 МБ, системний виклик `execve` негайно аварійно завершується з помилкою `E2BIG` («Argument list too long»).

## Діагностика середовища процесу в Linux

Коли сервіс або програма поводиться некоректно і підозрюється втрата конфігурації, системний інженер має набір точних інструментів для інспекції середовища будь-якого процесу.

### 1. Інспекція пам'яті через /proc/[pid]/environ

Віртуальна файлова система `procfs` ядра Linux дозволяє напряму прочитати байти таблиці середовища працюючого процесу.

Для поточної оболонки (PID `$$`):

```bash
# Читання сирого середовища з заміною нульових байтів на перенесення рядків
tr '\0' '\n' < /proc/$$/environ
```

Для будь-якого стороннього сервісу (наприклад, фонового демона з PID 2480):

```bash
# Форматований вивід усіх змінних процесу через xargs
xargs -0 -L1 -a /proc/2480/environ

# Або за допомогою утиліти strings
strings /proc/2480/environ
```

Файл `/proc/[pid]/environ` показує точний початковий стан пам'яті, сформований ядром під час `execve`. Якщо програма після старту викликала `setenv()`, ці зміни не відображатимуться у `/proc/[pid]/environ` на старіших ядрах, проте початковий контракт передачі змінних видно абсолютно прозоро.

### 2. Порівняння set, env, printenv та export -p

| Команда | Тип | Що саме виводить |
|---|---|---|
| `set` | Вбудована команда оболонки (builtin) | **Усі** змінні поточної оболонки: локальні, експортовані, масиви, а також усі оголошені bash-функції. |
| `env` | Зовнішній бінарний файл (`/usr/bin/env`) | Запускається через `fork+exec`. Виводить **виключно експортовані** змінні, які були серіалізовані у масив `environ`. |
| `printenv` | Зовнішня утиліта або builtin | Аналогічно `env`, показує тільки змінні середовища, але підтримує прямий запит одного ключа (`printenv DATABASE_URL`). |
| `export -p` | Вбудована команда оболонки | Виводить список усіх експортованих змінних у форматі POSIX-декларацій (`export NAME="value"`). |

```bash
# Практичний експеримент з різницею видимості:
MY_LOCAL="local_state"
export MY_EXPORTED="shared_state"

set | grep "^MY_"          # Виведе ОБИДВІ змінні: MY_LOCAL та MY_EXPORTED
env | grep "^MY_"          # Виведе ТІЛЬКИ MY_EXPORTED!
printenv MY_LOCAL          # Поверне порожній результат (код виходу 1)
printenv MY_EXPORTED       # Виведе: shared_state (код виходу 0)
```

### 3. Очищення середовища: утиліти env -i та env -u

Для перевірки роботи програми в ізольованому («стерильному») оточенні застосовують прапорці утиліти `env`:

```bash
# Запуск бінарного файлу з повністю порожнім середовищем
env -i ./my_service

# Запуск із суворим білим списком параметрів
env -i PATH=/usr/bin:/bin USER=nobody HOME=/tmp ./my_service

# Запуск з успадкованим середовищем, але з видаленням конкретної небезпечної змінної
env -u LD_PRELOAD ./my_service
```

Це дозволяє усунути вплив випадкових змінних оточення користувача на поведінку сервісів під час налагодження.

### 4. Трасування середовища через strace та gdb

Якщо поведінка програми викликає сумніви, інженер може простежити виклик `execve` за допомогою системного трасувальника `strace`:

```bash
strace -v -e trace=execve ./my_script.sh
```

Прапорець `-v` розгортає повний вміст масиву `envp`, дозволяючи побачити точний перелік рядків, переданих ядру.

У налагоджувачі `gdb` можна інспектувати покажчик `environ` безпосередньо у віртуальній пам'яті процесу:

```text
(gdb) break main
(gdb) run
(gdb) print (char**)environ
$1 = (char **) 0x7fffffffe0c8
(gdb) print (char*)*environ@5
$2 = {"PATH=/usr/bin:/bin", "USER=alex", "HOME=/home/alex", "LANG=uk_UA.UTF-8", 0x0}
```

## Програмне керування середовищем у C та C++

У системному програмуванні для безпечного формування середовища дочірнього процесу використовують пряму побудову масиву покажчиків `envp`.

Нижче наведено порівняння реалізації захищеного запуску мовами C та сучасного C++ (C++23):

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    /* Встановлюємо локальну змінну процесу */
    if (setenv("SERVICE_PORT", "9090", 1) != 0) {
        perror("setenv");
        return EXIT_FAILURE;
    }

    /* Формуємо явний білий список envp для дочірнього процесу */
    char *child_env[] = {
        "PATH=/usr/bin:/bin",
        "SERVICE_PORT=9090",
        "DATABASE_URL=postgres://db.internal:5432/app",
        NULL /* Обов'язковий завершальний нульовий покажчик */
    };

    char *child_argv[] = { "printenv", NULL };

    pid_t pid = fork();
    if (pid == 0) {
        /* Дочірній процес: виконуємо execve з власним масивом envp */
        execve("/usr/bin/printenv", child_argv, child_env);
        perror("execve");
        _exit(127);
    }

    waitpid(pid, NULL, 0);
    return EXIT_SUCCESS;
}
```
```cpp
#include <iostream>
#include <vector>
#include <string>
#include <format>
#include <expected>
#include <unistd.h>
#include <sys/wait.h>
#include <cstring>

namespace sys {

[[nodiscard]] std::expected<int, std::string>
run_with_custom_env(const std::string& path,
                    const std::vector<std::string>& args,
                    const std::vector<std::pair<std::string, std::string>>& env_map) {
    // Формуємо рядки KEY=VALUE
    std::vector<std::string> env_strings;
    env_strings.reserve(env_map.size());
    for (const auto& [k, v] : env_map) {
        env_strings.push_back(std::format("{}={}", k, v));
    }

    // Формуємо масив покажчиків envp
    std::vector<char*> raw_envp;
    raw_envp.reserve(env_strings.size() + 1);
    for (auto& s : env_strings) {
        raw_envp.push_back(s.data());
    }
    raw_envp.push_back(nullptr);

    // Формуємо масив покажчиків argv
    std::vector<char*> raw_argv;
    raw_argv.reserve(args.size() + 2);
    std::string exec_path = path;
    raw_argv.push_back(exec_path.data());
    for (const auto& arg : args) {
        raw_argv.push_back(const_cast<char*>(arg.c_str()));
    }
    raw_argv.push_back(nullptr);

    pid_t pid = ::fork();
    if (pid < 0) {
        return std::unexpected(std::format("fork() failed: {}", std::strerror(errno)));
    }

    if (pid == 0) {
        ::execve(exec_path.c_str(), raw_argv.data(), raw_envp.data());
        std::cerr << std::format("execve failed: {}\n", std::strerror(errno));
        ::_exit(127);
    }

    int status = 0;
    if (::waitpid(pid, &status, 0) < 0) {
        return std::unexpected(std::format("waitpid() failed: {}", std::strerror(errno)));
    }

    if (WIFEXITED(status)) {
        return WEXITSTATUS(status);
    }
    return std::unexpected("Process terminated abnormally");
}

} // namespace sys

int main() {
    auto res = sys::run_with_custom_env("/usr/bin/printenv", {}, {
        {"PATH", "/usr/bin:/bin"},
        {"SERVICE_PORT", "9090"},
        {"DATABASE_URL", "postgres://db.internal:5432/app"}
    });

    if (!res) {
        std::cerr << "Error: " << res.error() << '\n';
        return EXIT_FAILURE;
    }

    return EXIT_SUCCESS;
}
```
:::

Повну інженерну реалізацію системного лаунчера, який інспектує `/proc` у реальному часі та фільтрує небезпечні змінні, наведено у вставці [практичний інспектор середовища та лаунчер процесів](root:unix/variable-did-not-reach-the-program/proj-env-inspector.md).

## Стійкий ментальний каркас

Щоб змінні в Unix-системах ніколи не губилися, достатньо спиратися на прості фізичні правила:

1. **Змінна оболонки — це приватна пам'ять процесу**. Присвоєння `VAR=123` записує байти виключно у внутрішню хеш-таблицю поточного екземпляра оболонки.
2. **export — це прапорець включення у пакет execve**. Тільки змінні з прапорцем `att_exported` потрапляють до масиву `envp`, який ядро завантажує на стек дочірнього процесу.
3. **Конвеєр ділить процеси, а не пам'ять**. Кожна ланка конвеєра `cmd1 | cmd2` виконується в окремому `subshell` (`fork`). Усі мутації змінних у дочірньому процесі безслідно знищуються ядром після завершення підпроцесу (`exit`).
4. **Для збереження мутацій у циклі** використовуйте підстановку процесу `while read ...; done < <(cmd)` або вмикайте опцію `shopt -s lastpipe`.
