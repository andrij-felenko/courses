# ⚙️ Неінвазивний інспектор стану процесу через procfs

Традиційні інструменти динамічного аналізу, такі як `strace` або налагоджувач `gdb`, покладаються на системний виклик `ptrace`. Підключення `ptrace` зупиняє всі нитки процесу на кожній системній події, що генерує колосальні накладні витрати (сповільнення у 10–100 разів) і несе прямий ризик аварійної зупинки високопідсистемних сервісів у продакшені. Якщо високонавантажений веб-сервер або торговий рушій обслуговує десятки тисяч активних з'єднань, навіть секундна пауза під `ptrace` призводить до розриву тайм-аутів TCP-з'єднань, скидання кешів та каскадного колапсу суміжних мікросервісів.

Практична утиліта `proc-spy` демонструє неінвазивний підхід до системної діагностики: вона зчитує діагностичний паспорт процесу безпосередньо з віртуальної файлової системи `procfs` (`/proc/[pid]/status`, `/proc/[pid]/stat`, `/proc/[pid]/wchan`, `/proc/[pid]/stack`, `/proc/[pid]/schedstat`, `/proc/[pid]/io`). Це дозволяє за лічені мікросекунди з'ясувати стан процесу, розподіл часу, баланс контекстних перемикань та точний ланцюг викликів ядра сплячого потоку без зупинки цільової програми та без будь-яких накладних витрат на продуктивність.

## 1. Архітектура та внутрішні механізми ядра в procfs

Коли користувацький процес взаємодіє з віртуальною файловою системою `procfs`, ядро Linux не виконує фізичних операцій читання з блокових накопичувачів. Каталог `/proc/[PID]/` є динамічним вікном ядра у внутрішню пам'ять дескриптора задачі `ttask_struct`, яка живе в адресному просторі ядра.

Під час відкриття та вичитування відповідних файлів обробники VFS звертаються до структур ядра та генерують текстовий звіт «на льоту»:

```
                            Структура ttask_struct у пам'яті ядра
                            ┌───────────────────────────────────────────┐
                            │ • state: TASK_INTERRUPTIBLE (0x0001)      │
                            │ • utime: 14205, stime: 3820               │
                            │ • nvcsw: 120 (примусові перемикання)      │
                            │ • nivcsw: 1849204 (добровільні)           │
                            │ • wchan: &ffutex_wait_queue_me             │
                            │ • sched_info: [cpu_time, runqueue_time]   │
                            │ • mm->rss_stat: [анонімна, файлова RAM]   │
                            └───────────────────────────────────────────┘
                                                  │
                  ┌───────────────────────────────┼───────────────────────────────┐
                  ▼                               ▼                               ▼
        /proc/[pid]/status              /proc/[pid]/wchan               /proc/[pid]/stack
      (Стан, нитки, перемикання)      (Символьна назва сну)          (Ланцюг викликів ядра)
```

### Баланс перемикань контексту: voluntary проти nonvoluntary

Кожен перехід процесора з одного потоку на інший фіксується планувальником ядра у двох лічильниках структури `ttask_struct`:
* **Добровільні перемикання (`vvoluntary_ctxt_switches` / `nvcsw`):** Потік сам ініціював виклик планувальника `schedule()`, тому що не може продовжувати роботу. Це відбувається, коли програма очікує надходження даних із сокета (`read`, `epoll_wait`), читає блок із диска або намагається захопити зайнятий м'ютекс (`futex`).
* **Примусові перемикання (`nonvvoluntary_ctxt_switches` / `nivcsw`):** Потік був готовий виконувати машинний код, але планувальник ядра силоміць зняв його з процесорного ядра через вичерпання виділеного кванта часу або надходження більш пріоритетної задачі.

Співвідношення між цими двома лічильниками миттєво класифікує характер затримки:
* Якщо частка добровільних перемикань наближається до **100%**, проблема лежить у площині **Off-CPU** (блокування на зовнішніх ресурсах або контенція за спільні блокування).
* Якщо частка примусових перемикань висока (тисячі на секунду), процес страждає від **голодування CPU** або жорстких квот cgroups.

### Канал очікування (`wchan`) та стек ядра (`stack`)

Коли потік блокується всередині ядра, адреса точки очікування записується в поле `task->wchan`. Файл `/proc/[pid]/wchan` повертає текстову назву відповідного символу таблиці символів ядра `kallsyms`.

Файл `/proc/[pid]/stack` використовує внутрішній ядерний розгортач стеків (ORC unwinder на архітектурі x86_64) для зчитування адрес повернення з фреймів стека ядра потоку. Це дозволяє без підключення налагоджувача побачити точний шлях: від входу через системний виклик до конкретної функції блокування.

### Облік затримок планувальника: `/proc/[pid]/schedstat`

Файл `/proc/[pid]/schedstat` містить три фундаментальні числа, що відображають взаємодію процесу з планувальником завдань:
1. `cpu_time_ns` — сумарний час у наносекундах, проведений процесом на фізичному ядрі CPU.
2. `runqueue_time_ns` — сумарний час у наносекундах, проведений процесом у черзі планувальника у стані `TASK_RUNNING` в очікуванні звільнення ядра.
3. `pcount` — загальна кількість квантів часу, виділених процесу планувальником.

Якщо під час періодичного зчитування приріст `runqueue_time_ns` становить 400 мілісекунд за 1 секунду астрономічного часу, процес втрачає 40% своєї продуктивності виключно через конкуренцію за процесорні ядра з іншими задачами.

### Розподіл пам'яті: `/proc/[pid]/smaps_rollup`

Традиційна метрика `VmRSS` у файлі `status` часто спотворює уявлення про споживання пам'яті, оскільки вона враховує спільні сторінки бібліотек (Shared Libraries) повністю для кожного процесу. Якщо 50 процесів використовують спільну бібліотеку розміром 20 МіБ, сумарний `RSS` зросте на 1000 МіБ, хоча фізично в RAM знаходиться лише 20 МіБ.

Вузол `/proc/[pid]/smaps_rollup` надає об'єктивну метрику **PSS (Proportional Set Size)**, де пам'ять кожної спільної сторінки ділиться на кількість процесів, які її розділяють:

```
PSS = Private_Clean + Private_Dirty + (Shared_Clean / N) + (Shared_Dirty / N)
```

Також файл відображає:
* `RssAnon` — анонімна пам'ять купи (`heap`) та стеків потоків, виділена через `malloc()` або `mmap(MAP_ANONYMOUS)`.
* `RssFile` — сторінки виконуваного файлу та динамічних бібліотек, які відображені з диска і можуть бути безболісно витіснені ядром у разі дефіциту пам'яті.
* `Swap` — обсяг пам'яті процесу, який ядро витіснило у розділ підкачки.

### Підрахунок дискового вводу-виводу: `/proc/[pid]/io`

Файл `/proc/[pid]/io` дозволяє відрізнити логічний ввід-вивід на рівні VFS від фізичних операцій із накопичувачем:
* `rchar` та `wchar`: кількість байтів, переданих через системні виклики `rread()` та `write()`. Сюди входять операції, що були повністю задоволені сторінковим кешем пам'яті (Page Cache) без звернення до диска.
* `read_bytes` та `write_bytes`: кількість байтів, які ядро фізично змушене було прочитати або записати на блоковий накопичувач.
* `cancelled_write_bytes`: байти, які процес записав у сторінковий кеш, але згодом видалив або обрізав через `ftruncate()`, перш ніж вони були скинуті на диск.

## 3. Анатомічний розбір коду та керування ресурсами

Розроблена утиліта демонструє фундаментальні патерни системного програмування для безпечної роботи з ядром Linux без створення накладних витрат:

### Розбір реалізації мовою C (C99 / POSIX)

1. **Потоковий розбір файлів без динамічної алокації:** Функція 
read_status() використовує статичний буфер char line[256] у стеку викликів. Замість завантаження всього файлу в пам'ять, рядки зчитуються послідовно через fgets().
2. **Захист від переповнення буферів:** При використанні sscanf() для рядкових полів обов'язково вказується максимальна ширина поля (наприклад, %31s для масиву розміром 32 байти), що унеможливлює уразливості класу Buffer Overflow.
3. **Прямий системний виклик 
read() для ядерних стеків:** Читання /proc/[pid]/wchan та /proc/[pid]/stack здійснюється через низькорівневий дескриптор open(O_RDONLY) та системний виклик 
read(). Віртуальні файли стеків ядра генеруються ядром атомарно в межах однієї сторінки пам'яті (4096 байтів). Використання стандартної бібліотеки fopen() тут є зайвим, оскільки ці файли не підтримують позиціонування lseek().

### Розбір реалізації мовою C++ (C++20)

1. **RAII та безпека ресурсів:** Клас ProcSpy повністю інкапсулює життєвий цикл файлових потоків std::ifstream. Будь-які відкриті файлові дескриптори гарантовано закриваються автоматично при виході зі scope або розгортанні стека при винятках.
2. **Безалокаційний парсинг через std::string_view:** Для перевірки префіксів рядків (starts_with()) та відсікання пробілів (trim_leading()) використовуються легковикові зрізи std::string_view. Це усуває виділення пам'яті на купі (heap allocations) під час ітерації рядків.
3. **Семантика відсутності результату:** Повернення std::optional<ProcessStatus> чітко сигналізує про відсутність процесу або відмову в доступі на рівні системи типів, не змушуючи клієнтський код перехоплювати важкі винятки у штатних ситуаціях завершення цільової програми.

## 5. Багатопотокові сервіси: розширення для /proc/[pid]/task/

У сучасних багатопотокових сервісах (пули потоків, асинхронні середовища виконання) стан головного процесу (PID) відображає лише стан первинного потоку (Thread Group Leader). Часто виникає ситуація, коли головний потік мирно спить у системному виклику epoll_wait (стан S), але одна з 32 фонових робочих ниток спалює 100% ядра або застрягла у неперериваному дисковому сні D.

Для виявлення прихованих затримок усередині пулу потоків діагностичний алгоритм розширюється ітерацією каталогу /proc/[PID]/task/:

`
/proc/[PID]/task/
  ├── 14205/  (Головний потік: epoll_wait, стан S)
  ├── 14206/  (Робочий потік 1: ffutex_wait_queue_me, стан S)
  ├── 14207/  (Робочий потік 2: blk_mq_make_request, стан D)  <-- ВУЗЬКЕ МІСЦЕ
  └── 14208/  (Робочий потік 3: ffutex_wait_queue_me, стан S)
`

Кожен підкаталог /proc/[PID]/task/[TID]/ містить незалежні екземпляри файлів status, wchan, stack та schedstat для конкретного легковикового процесу (LWP).

### Порівняльна матриця інструментів діагностики процесу

| Інструмент | Накладні витрати на процес | Безпека для продакшену | Вимагає зупинки ниток | Доступні дані |
| :--- | :--- | :--- | :--- | :--- |
| **proc-spy (procfs)** | 0% (кілька мікросекунд) | Повна безпека (безпечно під 100k RPS) | Ніколи | Стан, пам'ять PSS, wchan, стек ядра, перемикання |
| **perf trace** | 0.5–2% (ring buffer ядра) | Висока (з фільтрацією затримки) | Ні | Системні виклики та аргументи з таймінгами |
| **strace (ptrace)** | 1000–5000% (сповільнення до 50x) | Небезпечно під високим навантаженням | Так (подвійна зупинка на кожен виклик) | Повний текст усіх викликів, буфери, коди помилок |
| **gdb / pstack** | Повна заморозка процесу | Критично небезпечно (розрив сокетів) | Так (повна зупинка всіх ниток) | Стек користувача, змінні пам'яті, регістри |

## 6. Пастки та крайові випадки інтроспекції

1. **Права доступу до `/proc/[pid]/stack`:** З міркувань безпеки (запобігання атакам типу KASLR Bypass через витік адрес ядра) читання файлу `stack` дозволено лише користувачу з привілеями суперкористувача (`root`) або процесам із можливістю `CAP_SYS_ADMIN`. Без належних прав спроба відкриття файлу повертає помилку `EACCES (Permission denied)`.
2. **Гонка завершення процесу (Race Condition):** Якщо цільовий процес завершується під час опитування, спроба відкриття наступного файлу поверне помилку `ENOENT (No such file or directory)`. Код утиліти обробляє цей випадок без аварійного падіння.
3. **Опитування окремих ниток у багатопотокових застосунках:** Файли у корені `/proc/[pid]/` відображають стан головного потоку групи задач (Thread Group Leader). Якщо головний потік спить у виклику `epoll_wait`, але одна з фонових робочих ниток спалює 100% процесора або зависла на диску, її стан необхідно читати з підкаталогу `/proc/[pid]/task/[TID]/`.
4. **Порожній `wchan` для активного процесу:** Якщо потік у момент зчитування виконує машинний код на фізичному ядрі процесора (стан `TASK_RUNNING`), ядро повертає `0` або порожній рядок. Це нормальна поведінка, яка свідчить про те, що потік не заблокований усередині ядра.
5. **Облік пам'яті через `/proc/[pid]/smaps_rollup`:** Для точного аналізу витоків пам'яті значення `VmRSS` у `status` може бути оманливим, оскільки воно включає спільні бібліотеки. Зчитування вузла `smaps_rollup` надає метрику `Pss` (Proportional Set Size), де пам'ять кожної спільної сторінки ділиться на кількість процесів, які її використовують.
6. **Обмеження `yama/ptrace_scope`:** На деяких загартованих (Hardened) дистрибутивах Linux модуль безпеки Yama додатково обмежує доступ до `/proc/[pid]/` для інших процесів користувача через параметр `/proc/sys/kernel/yama/ptrace_scope`. Значення `1` дозволяє інспектувати лише прямих нащадків процесу, тоді як `2` або `3` вимагають обов'язкових прав суперкористувача.

## 7. Практичний регламент (Runbook) розслідування інцидентів

Коли черговий інженер стикається з раптовим зависанням або деградацією латентності критичного процесу, рекомендується дотримуватися наступного покрокового регламенту з використанням утиліти proc-spy:

### Крок 1. Фіксація стану доказів (Snapshot)
Перш ніж вчиняти будь-які дії, зніміть діагностичний паспорт процесу та збережіть його в тимчасовий файл інциденту:

`sh
# Збереження повного паспорта стану та стеків ядра
sudo ./proc_spy_cpp 14205 > /tmp/incident_proc_14205.txt
cat /proc/14205/status >> /tmp/incident_proc_14205.txt
cat /proc/14205/smaps_rollup >> /tmp/incident_proc_14205.txt
`

### Крок 2. Аналіз каналу сну та балансу перемикань
Зверніть увагу на два ключові параметри у виводі:
* Якщо voluntary_ctxt_switches становить понад 95% усіх перемикань, а wchan повертає futex_wait_queue_me або do_epoll_wait — процес спить в очікуванні зовнішніх подій або заблокований на спільних м'ютексах. Не намагайтеся оптимізувати алгоритми або додавати ядра CPU: шукайте блокування або таймаути сокетів.
* Якщо переважають 
onvvoluntary_ctxt_switches, а стан процесу R — процес готовий виконувати інструкції, але йому бракує виділеного процесорного часу. Перевірте ліміти cgroup (cpu.stat) та чергу планувальника (vmstat 1).

### Крок 3. Аудит відкритих сокетів та дескрипторів
Перевірте, чи не вичерпав процес ліміт відкритих дескрипторів або чи не завис на напівзакритих з'єднаннях:

`sh
# Підрахунок кількості відкритих файлів та сокетів
ls -1 /proc/14205/fd | wc -l

# Пошук сокетів у стані CLOSE_WAIT (клієнт закрив з'єднання, але сервер не викликав close)
ss -tpe '( dport = :http or sport = :http )' | grep 14205
`

Якщо сотні сокетів перебувають у стані CLOSE_WAIT, це свідчить про витік дескрипторів у прикладній логіці обробки помилок, через що процес врешті-решт отримає помилку EMFILE (Too many open files) при спробі прийняти нове з'єднання.


### Крок 4. Ідентифікація процесів-зомбі (Defunct / Zombie)
Якщо у виводі status стан процесу позначається як Z (zombie), це означає, що потік уже завершив виконання, звільнив усю пам'ять і файлові дескриптори, але дескриптор task_struct утримується ядром у глобальній таблиці процесів.

* **Чому це небезпечно:** Зомбі-процеси не споживають RAM чи CPU, але займають унікальний номер PID. Накопичення тисяч зомбі призводить до вичерпання ліміту /proc/sys/kernel/pid_max, після чого система не може створити жодного нового процесу (EAGAIN / Resource temporarily unavailable).
* **Пошук винного батьківського процесу:** Знайдіть поле PPid у файлі /proc/[PID]/status та надішліть сигнал SIGCHLD батьківському процесу або перезапустіть батька, щоб процес-ініціалізатор (systemd / PID 1) перехопив і вичистив зомбі через системний виклик waitpid().
