# 📋 Інтерфейси інспекції середовища та віртуалізації

Операційна система Linux надає інженеру структурований набір апаратних та віртуальних інтерфейсів для точного визначення контексту виконання: від фізичного заліза до віртуальних машин, гіпервізорів та ізольованих контейнерів.

Цей довідник описує ключові низькорівневі вузли, сигнатури та конвенції [зондування середовища виконання](root:unix/where-to-get-a-system).

## 1. Апаратний інтерфейс процесора CPUID (x86_64)

На архітектурі x86_64 інструкція `CPUID` повертає апаратні та псевдоапаратні властивості процесора у регістрах `EAX`, `EBX`, `ECX`, `EDX`.

### Листок 0x00000001 (Основні прапорці функцій)
При виклику `CPUID` зі значенням `EAX = 1`:
- **Регістр ECX, біт 31 (Hypervisor Present Bit):**
  - `0`: процесор працює безпосередньо на фізичному залізі (або гіпервізор навмисно приховує свою присутність, маскуючи цей біт);
  - `1`: процесор виконується у віртуалізованому оточенні (гостьова ОС під керуванням Type-1 або Type-2 гіпервізора).

### Листок 0x40000000 (Базовий листок гіпервізора)
Якщо біт `ECX.31` дорівнює `1`, процесор відкриває діапазон листків від `0x40000000` до `0x400000FF`, зарезервований для комунікації з гіпервізором.

При виклику `CPUID` з `EAX = 0x40000000` регістри повертають:
- `EAX`: максимальний номер підтримуваного листка гіпервізора;
- `EBX`, `ECX`, `EDX`: 12-байтовий ASCII-підпис виробника гіпервізора.

| Сигнатура в EBX/ECX/EDX | Виробник / Технологія гіпервізора | Типове середовище |
| :--- | :--- | :--- |
| `"KVMKVMKVM\0\0\0"` | Linux Kernel-based Virtual Machine (KVM) | QEMU, Proxmox, Hetzner, DigitalOcean |
| `"Microsoft Hv"` | Microsoft Hyper-V | Windows Server, Azure VM, WSL2 |
| `"VMwareVMware"` | VMware Workstation / ESXi / Fusion | Корпоративні кластери, локальні VM |
| `"XenVMMXenVMM"` | Xen Hypervisor | AWS EC2 (попередні покоління), Qubes OS |
| `"TCGTCGTCGTCG"` | QEMU Tiny Code Generator | Програмна емуляція без VT-x/AMD-V |
| `"bhyve bhyve "` | FreeBSD Bhyve | FreeBSD віртуалізація |
| `"QNXQVMBSYS\0"` | QNX Hypervisor | Автомобільні та вбудовані RTOS |
| `"ACRNACRNACRN"` | Project ACRN | Індустріальні системи Інтернету речей |

### Додаткові листки гіпервізора

Гіпервізори KVM та Hyper-V надають додаткові діагностичні інтерфейси через послідовні номери листків:
- **Листок `0x40000001` (Інтерфейс KVM):** Регістр `EAX` повертає бітову маску підтримуваних функцій паравиртуалізації KVM:
  - Біт 0 (`KVM_FEATURE_CLOCKSOURCE`): підтримка паравиртуалізованого годинника `kvm-clock`;
  - Біт 3 (`KVM_FEATURE_MMU_OP`): оптимізовані операції з пам'яттю через гіпервиклики;
  - Біт 4 (`KVM_FEATURE_CLOCKSOURCE2`): стабільний годинник реального часу другого покоління;
  - Біт 5 (`KVM_FEATURE_ASYNC_PF`): асинхронна обробка промахів сторінок пам'яті (*Async Page Fault*).
- **Листок `0x40000001` (Інтерфейс Hyper-V / WSL2):** Регістр `EAX` повертає сигнатуру підтримуваного інтерфейсу гіпервикликів (наприклад, ASCII-рядок `"Hv#1"`), що підтверджує наявність рушія віртуалізації Microsoft Hyper-V.

## 2. Апаратні особливості архітектури ARM64

На 64-бітній архітектурі ARM (Apple Silicon, AWS Graviton, Raspberry Pi 4/5) інструкція `CPUID` відсутня. Розмежування привілеїв реалізується через систему рівнів винятків (*Exception Levels*):
- **EL0:** Непривілейований режим виконання користувацьких програм;
- **EL1:** Режим ядра операційної системи (наприклад, ядро Linux або шар BSD ядра XNU);
- **EL2:** Режим апаратного гіпервізора (регістр керування `HCR_EL2` контролює перехоплення інструкцій віртуальної машини та трансляцію пам'яті Stage-2);
- **EL3:** Режим безпечного монітора прошивки (*Secure Monitor* / ARM TrustZone).

Програма простору користувача на ARM64 не має прямого доступу до регістру `CurrentEL`. Виявлення віртуалізації на цій архітектурі здійснюється через аналіз рядка `Features` у файлі `/proc/cpuinfo` (наявність прапорця `vhe` — Virtualization Host Extensions), аналіз пристроїв дерева пристроїв (*Device Tree*, каталог `/sys/firmware/devicetree/base/hypervisor`) або через читання таблиць DMI/SMBIOS у `/sys/class/dmi/id/`.

## 3. Псевдофайлова система /proc

Псевдофайлова система `procfs` генерує структури даних безпосередньо з пам'яті ядра під час виклику `read()`.

### `/proc/version` та `/proc/sys/kernel/osrelease`
Містять рядок збірки ядра Linux, версію компілятора GCC/Clang та маркер дистрибутива.
- **Типовий вигляд на нативному Linux:**
  ```
  Linux version 6.8.0-45-generic (buildd@lcy02-amd64-080) (x86_64-linux-gnu-gcc-13) #45-Ubuntu SMP PREEMPT_DYNAMIC
  ```
- **Типовий вигляд у WSL2:**
  ```
  Linux version 5.15.153.1-microsoft-standard-WSL2 (oe-user@oe-host) (gcc (GCC) 11.2.0) #1 SMP PREEMPT
  ```
- **Типовий вигляд у застарілому WSL1:**
  ```
  Linux version 4.4.0-19041-Microsoft (Microsoft@Microsoft.com) (gcc version 5.4.0) #488-Microsoft Sun Sep 01 13:30:00 PST 2020
  ```

### `/proc/cpuinfo`
Містить докладні прапорці можливостей процесора. У нативному ядрі Linux рядок `flags` містить прапорці апаратної віртуалізації `vmx` (для процесорів Intel) або `svm` (для процесорів AMD). Усередині віртуальної машини ці прапорці зазвичай приховані гіпервізором, якщо тільки адміністратор явно не увімкнув режим вкладеної віртуалізації (*Nested Virtualization*). Наявність прапорця `hypervisor` свідчить про активний біт `ECX.31` в CPUID.

### `/proc/1/environ`
Таблиця змінних середовища процесу ініціалізації (PID 1). Змінні розділені нульовим байтом `\0`.
- **Маркер контейнера:** наявність рядка `container=docker`, `container=podman`, `container=lxc` або `container=systemd-nspawn`.

### `/proc/1/cgroup` та `/proc/self/cgroup`
Ієрархія контрольних груп процесів.
- **У нативній системі без контейнеризації (cgroup v2):**
  ```
  0::/
  ```
- **Усередині контейнера Docker:**
  ```
  0::/docker/4f8b2c1e7a...
  ```
- **Усередині Podman / Kubernetes Pod:**
  ```
  0::/kubepods.slice/kubepods-burstable.slice/...
  ```

### `/proc/self/mountinfo`
Детальна таблиця точок монтування з прапорцями VFS. Кожен рядок містить такі обов'язкові поля:
1. `mount ID`: унікальний ідентифікатор точки монтування;
2. `parent ID`: ідентифікатор батьківського монтування;
3. `major:minor`: номери пристрою файлової системи;
4. `root`: кореневий каталог монтування всередині ФС;
5. `mount point`: шлях монтування відносно кореня процесу;
6. `mount options`: прапорці доступу (`rw`, `relatime`, `nodev`);
7. `filesystem type`: назва типу ФС (`ext4`, `xfs`, `overlay`, `9p`, `virtiofs`).

Присутність типу `overlay` у кореневому монтуванні (`/`) однозначно вказує на виконання всередині контейнера OCI, тоді як типи `9p` та `virtiofs` свідчать про мікро-ВМ або спільні папки гіпервізора.

## 4. Таблиці DMI та шина /sys

Підсистема `sysfs` відображає ієрархію об'єктів ядра `kobject` у каталозі `/sys`.

### Таблиці SMBIOS / DMI (`/sys/class/dmi/id/`)
Доступні для читання непривілейованим користувачам:

| Шлях до файлу | Призначення | Значення на залізі | Значення у віртуальній машині |
| :--- | :--- | :--- | :--- |
| `/sys/class/dmi/id/product_name` | Назва моделі комп'ютера або плати | `ThinkPad T14 Gen 4`, `X670 AORUS ELITE` | `KVM`, `VirtualBox`, `VMware Virtual Platform`, `Standard PC` |
| `/sys/class/dmi/id/sys_vendor` | Виробник материнської плати / системи | `LENOVO`, `ASUSTeK COMPUTER INC.`, `Dell Inc.` | `QEMU`, `innotek GmbH`, `VMware, Inc.`, `Microsoft Corporation` |
| `/sys/class/dmi/id/bios_vendor` | Виробник прошивки UEFI / BIOS | `American Megatrends Inc.`, `Phoenix Technologies` | `SeaBIOS`, `EDK II`, `DigitalOcean`, `Hetzner` |
| `/sys/class/dmi/id/chassis_type` | Форм-фактор корпусу (число SMBIOS) | `9` (Laptop), `3` (Desktop), `23` (Rack Mount) | `1` (Other) або `24` (Sealed-case PC) |

### Числові коди типів шасі (Chassis Type)

Специфікація SMBIOS визначає такі ключові значення у файлі `/sys/class/dmi/id/chassis_type`:
- `1`: Other (невизначений або нестандартний тип, часто встановлюється емуляторами);
- `2`: Unknown (невідомий тип);
- `3`: Desktop (настільний персональний комп'ютер);
- `8` / `9` / `10`: Portable / Laptop / Notebook (ноутбуки та портативні комп'ютери);
- `17` / `23`: Main Server Chassis / Rack Mount Chassis (промислові сервери);
- `24`: Sealed-Case PC (герметичний моноблок або хмарний віртуальний інстанс).

### Шина VirtIO (`/sys/bus/virtio/devices/`)
Присутність каталогів `virtio0`, `virtio1` свідчить про наявність паравиртуалізованих пристроїв KVM/QEMU:
- Пристрій з `device = 0x0001`: мережевий адаптер `virtio_net`;
- Пристрій з `device = 0x0002`: блоковий контролер накопичувача `virtio_blk`;
- Пристрій з `device = 0x0005`: модуль роздування оперативної пам'яті `virtio_balloon`;
- Пристрій з `device = 0x0010`: апаратний графічний адаптер `virtio_gpu`;
- Пристрій з `device = 0x001a`: спільна файлова система `virtio_fs`.

## 5. Консольні утиліти стандартної діагностики

У командному рядку Unix для швидкого аналізу середовища використовуються стандартні утиліти:

### `systemd-detect-virt`
Офіційна утиліта підсистеми ініціалізації `systemd`, що реалізує наведений вище алгоритм перевірки:
```sh
systemd-detect-virt
```
- Прапорець `--vm`: перевіряє лише віртуальні машини (повертає назву: `kvm`, `qemu`, `vmware`, `microsoft`, `oracle`, `xen` або `none`);
- Прапорець `--container`: перевіряє лише контейнери (повертає: `docker`, `podman`, `lxc`, `systemd-nspawn` або `none`);
- **Коди завершення:** `0` — середовище виявлено; `>0` — працює на чистому залізі (`none`).

### `hostnamectl`
Виводить комплексний звіт про хост, ядро, архітектуру та виявлену технологію віртуалізації:
```sh
hostnamectl status
```
Рядок `Virtualization:` автоматично заповнюється на основі DMI та CPUID перевірок.

### `lscpu`
Розбирає апаратні властивості процесора. У віртуальних машинах виводить окремий рядок:
```
Hypervisor vendor:  KVM
Virtualization type: full
```
