# 📋 Системна матриця примітивів міжпроцесної взаємодії

Цей довідник містить точні системні контракти, сигнатури викликів, структури облікових даних, конфігураційні ліміти ядра та семантику обробки збоїв для всіх примітивів міжпроцесної взаємодії в операційних системах сімейства Linux/POSIX. Довідник відкрито для того, щоб отримати вичерпні технічні параметри, точні константи заголовкових файлів, правила мультиплексування в `epoll` та механізми безпечної передачі прав доступу без необхідності шукати розрізнені сторінки керівництва системних викликів.

## Системні виклики створення та життєвий цикл

Кожен примітив міжпроцесної взаємодії визначає власний механізм зустрічі сторін, правила адресації у системних просторах імен та спосіб очищення ресурсів ядра після завершення роботи процесів.

| Примітив IPC | Системні виклики створення | Механізм зустрічі сторін | Простір імен та адресація | Час життя об'єкта в ядрі |
| :--- | :--- | :--- | :--- | :--- |
| **Анонімний канал (Pipe)** | `pipe(int pipefd[2])`, `pipe2(int pipefd[2], int flags)` | Успадкування дескриптора через `fork()` | Немає (анонімний у процесі) | До закриття останнього дескриптора |
| **Іменований канал (FIFO)** | `mkfifo(const char *pathname, mode_t mode)`, `mknod()` | Відкриття шляху через `open()` | Файлова система (VFS) | Файл існує до `unlink()`; буфер — до закриття FD |
| **Парний сокет (Socketpair)** | `socketpair(AF_UNIX, int type, 0, int sv[2])` | Успадкування дескрипторів через `fork()` | Немає (анонімна пара FD) | До закриття обох кінців `sv[0]` та `sv[1]` |
| **Сокет домену Unix (UDS)** | `socket(AF_UNIX, type, 0)`, `bind()`, `connect()` | Шлях у файловій системі або абстрактний простір | Файлова система або `\0` (Linux Abstract Namespace) | Вузол у FS до `unlink()`; абстрактний сокет — до закриття |
| **Спільна пам'ять POSIX** | `shm_open(const char *name, int oflag, mode_t mode)` | Відкриття імені через `shm_open()` + `mmap()` | Віртуальна файлова система `/dev/shm` (tmpfs) | Зберігається в RAM до `shm_unlink()` або перезавантаження |
| **Анонімна спільна пам'ять** | `memfd_create(const char *name, unsigned int flags)` | Передача дескриптора через сокет (`SCM_RIGHTS`) | Немає (анонімний анотований FD) | До закриття останнього дескриптора в системі |
| **Черги повідомлень POSIX** | `mq_open(const char *name, int oflag, ...)` | Відкриття імені через `mq_open()` | Віртуальна файлова система `mqueue` (POSIX IPC) | Зберігається в ядрі до `mq_unlink()` або перезавантаження |

### Прапорці атомарного створення дескрипторів

Сучасні системні виклики створення примітивів підтримують бітові прапорці, які дозволяють уникнути стану гонитви між моментом виклику та наступним налаштуванням атрибутів дескриптора. У багатопотокових програмах виклик `fcntl(fd, F_SETFD, FD_CLOEXEC)` після створення дескриптора створює небезпечне часове вікно: якщо інший потік одночасно виконає `fork()` та `execve()`, дескриптор встигне витекти у дочірній процес. Використання атомарних прапорців створення повністю усуває цю вразливість.

* `O_CLOEXEC` / `SOCK_CLOEXEC`: встановлює прапорець `FD_CLOEXEC` (закриття при виклику `execve()`) безпосередньо під час виділення дескриптора ядром. Запобігає випадковому витоку дескрипторів у сторонні виконувані файли.
* `O_NONBLOCK` / `SOCK_NONBLOCK`: переводить дескриптор у неблокуючий режим вводу-виводу. Операції читання з порожнього буфера та запису в заповнений буфер негайно повертають помилку `EAGAIN` або `EWOULDBLOCK` замість блокування потоку.
* `O_DIRECT` (для каналів у Linux починаючи з версії 3.4): вмикає режим пакетної передачі даних, де кожен виклик `write()` розглядається як окремий неподільний пакет, якщо його розмір не перевищує місткості буфера.

## Характеристики буферизації та системні ліміти ядра

Пропускна здатність та стійкість до перевантажень залежать від розмірів буферів ядра та конфігураційних лімітів операційної системи. Операційна система керує буферами каналів та сокетів через структури ядра, які алокуються в динамічній пам'яті (SLUB/SLAB алокатор).

```
/proc/sys/fs/pipe-max-size        # Максимальний розмір буфера каналу для непривілейованого процесу (типово 1 МБ)
/proc/sys/fs/pipe-user-pages-hard   # Жорсткий ліміт сторінок RAM під усі канали одного користувача
/proc/sys/fs/pipe-user-pages-soft   # М'який ліміт сторінок RAM під канали (при перевищенні заборонено збільшення)
/proc/sys/net/core/rmem_default   # Типовий розмір буфера прийому для сокетів (типово 212 992 байти)
/proc/sys/net/core/wmem_default   # Типовий розмір буфера надсилання для сокетів (типово 212 992 байти)
/proc/sys/fs/mqueue/msg_max       # Максимальна кількість повідомлень у черзі POSIX (типово 10)
/proc/sys/fs/mqueue/msgsize_max   # Максимальний розмір одного повідомлення в байтах (типово 8192)
/proc/sys/fs/mqueue/queues_max    # Максимальна кількість активних черг у системі
```

### Динамічна зміна ємності каналів через fcntl

За замовчуванням канал у Linux має розмір 16 сторінок пам'яті (64 КБ). Якщо програма передає великі обсяги даних і стикається з частими блокуваннями записувача, розмір кільцевого буфера можна динамічно збільшити за допомогою команди `F_SETPIPE_SZ` системного виклику `fcntl()`:

1. Процес викликає `fcntl(pipe_fd, F_SETPIPE_SZ, new_size)`.
2. Ядро округлює запрошений розмір до найближчого степеня двійки, кратного розміру сторінки (4096 байтів).
3. Якщо користувач не має системного привілею `CAP_SYS_RESOURCE`, ядро перевіряє, щоб новий розмір не перевищував ліміт `/proc/sys/fs/pipe-max-size` (зазвичай 1 048 576 байтів).
4. Отримане значення можна перевірити командою `fcntl(pipe_fd, F_GETPIPE_SZ)`.

### Конфігурація буферів сокетів SO_RCVBUF та SO_SNDBUF

Розмір черги прийому та надсилання для сокетів домену Unix регулюється опціями `SO_RCVBUF` та `SO_SNDBUF` виклику `setsockopt()`. Важлива внутрішня особливість ядра Linux: ядро подвоює передане користувачем значення розміру буфера (множник `2x`), резервуючи половину виділеного обсягу під внутрішні службові структури керування пакетами `struct sk_buff`. Якщо процес запитує розмір буфера 65 536 байтів, виклик `getsockopt()` поверне значення 131 072 байти.

### Атомарність та правила кадрування запису

1. **Гарантія `PIPE_BUF` для каналів**:
   * Стандарт POSIX гарантує атомарність запису в канал обсягом до `PIPE_BUF` байтів. У ядрі Linux константа `PIPE_BUF` на всіх апаратних архітектурах становить рівно **4096 байтів** (1 сторінка).
   * Запис обсягом `n <= PIPE_BUF` неподільно потрапляє в буфер ядра. Навіть за умови високої конкуренції десятків паралельних процесів-записувачів, ядро не розриває і не перемішує блоки розміром до 4 КБ.
   * Запис обсягом `n > PIPE_BUF` розбивається ядром на частини й може чергуватися із записами інших процесів.
2. **Гарантія меж для сокетів `SOCK_DGRAM` та `SOCK_SEQPACKET`**:
   * Кожен системний виклик `send()` формує одне неподільне повідомлення із зафіксованими межами.
   * Отримувач вичитує рівно одне повідомлення за виклик `recv()`. Якщо наданий буфер менший за довжину пакета:
     * Для `SOCK_DGRAM`: залишок пакета безповоротно відкидається (встановлюється прапорець `MSG_TRUNC`).
     * Для `SOCK_SEQPACKET`: повертається прочитана частина, а прапорець `MSG_TRUNC` у структурі `msghdr` сигналізує про обрізання даних.
3. **Обмеження та налаштування черг POSIX `mqd_t`**:
   * Параметри черги повідомлень конфігуруються за допомогою структури `struct mq_attr`. Будь-який читач зобов'язаний виділити буфер розміром щонайменше `mq_msgsize`, інакше виклик `mq_receive()` миттєво повертає помилку `EMSGSIZE`.

## Повний життєвий цикл спільної пам'яті POSIX

Управління сегментами спільної пам'яті через виклики `shm_open()` та `mmap()` вимагає суворого дотримання послідовності системних дій. На відміну від анонімних каналів, іменований сегмент у `/dev/shm` існує незалежно від процесів, які його створили.

Послідовність операцій створення та під'єднання:
1. **Створення або відкриття дескриптора**: `int fd = shm_open("/my_shm", O_CREAT | O_RDWR, 0660);`. Сегмент з'являється як файл у віртуальній пам'яті `tmpfs` за шляхом `/dev/shm/my_shm`.
2. **Встановлення розміру пам'яті**: новостворений об'єкт має нульовий розмір. Творець зобов'язаний виділити пам'ять викликом `ftruncate(fd, size)`. Спроба викликати `mmap()` на файл нульового розміру призводить до помилки `EINVAL`.
3. **Відображення в адресний простір**: виклик `void *ptr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);` налаштовує таблицю сторінок процесу.
4. **Закриття дескриптора**: після успішного виклику `mmap()` числовий дескриптор `fd` можна безпечно закрити через `close(fd)` — активне віртуальне відображення утримує сторінки пам'яті в ядрі.
5. **Синхронізація кешу (за потреби)**: виклик `msync(ptr, size, MS_SYNC)` гарантує скидання брудних сторінок пам'яті в підсистему кешу VFS.
6. **Знищення зв'язку імені**: виклик `shm_unlink("/my_shm")` видаляє ім'я з каталогу `/dev/shm`. Сегмент фізично звільняється з оперативної пам'яті ядра лише тоді, коли останній процес виконає `munmap(ptr, size)`.

## Сповіщення у чергах повідомлень через mq_notify

Оскільки дескриптор черги повідомлень `mqd_t` у стандарті POSIX не є звичайним файловим дескриптором, асинхронне сповіщення про надходження нових пакетів реалізується через системний виклик `mq_notify()`.

Структура конфігурації сповіщення `struct sigevent` підтримує два режими доставки:
* `SIGEV_SIGNAL`: ядро надсилає процесу вказаний сигнал (наприклад, сигнал реального часу `SIGRTMIN + 1`) у момент, коли черга переходить зі стану «порожня» у стан «є хоча б одне повідомлення».
* `SIGEV_THREAD`: бібліотека C (`glibc`) автоматично створює новий потік виконання, який викликає вказану функцію зворотного виклику (Callback) для вичитки повідомлення.

Важливе обмеження POSIX: сповіщення через `mq_notify()` спрацьовує рівно один раз (One-Shot Notification). Після отримання сигналу або виконання функції потік зобов'язаний повторно зареєструвати структуру сповіщення через новий виклик `mq_notify()`.

## Порівняння примітивів синхронізації: Семафори проти eventfd та futex

Для синхронізації доступу до спільних ресурсів стандарт POSIX та ядро Linux пропонують кілька механізмів з різними експлуатаційними характеристиками:

1. **Іменовані та безіменні семафори POSIX (`sem_t`)**:
   * Створюються через `sem_open()` або ініціалізуються у спільній пам'яті через `sem_init(sem, 1, initial_value)`.
   * Операції `sem_wait()` та `sem_post()` керують цілочисельним лічильником.
   * Недолік: не мають файлового дескриптора, тому їх неможливо додати до черги очікування `epoll_wait()`.
2. **Лічильники переходів ядра (`eventfd`)**:
   * Створюються системним викликом `eventfd(initval, flags)`.
   * Мають повноцінний файловий дескриптор із підтримкою подій `EPOLLIN` та `EPOLLOUT`.
   * Ідеально підходять для інтеграції асинхронних сповіщень про готовність спільних буферів у цикли подій.
3. **Швидкі користувацькі блокування (`futex`)**:
   * Базуються на 32-бітному цілочисельному слові в оперативній пам'яті.
   * За відсутності конкуренції (Uncontended case) операції захоплення та звільнення виконуються в просторі користувача за 1–2 атомарні інструкції процесора без жодного системного виклику.
   * Лише за наявності конкуренції (Contended case) потік звертається до ядра через `syscall(SYS_futex, ...)`.

## Контракт мультиплексування в epoll

Інтеграція в єдиний реактивний цикл подій процесу визначається наявністю повноцінного файлового дескриптора та правилами генерації подій готовності ядром. Підсистема `epoll` використовує структуру `struct file_operations` у ядрі: якщо драйвер об'єкта реалізує метод `.poll`, дескриптор може бути зареєстрований через `epoll_ctl()`.

| Примітив | Підтримка `epoll_ctl()` | Події готовності до читання | Події готовності до запису | Події закриття та збоїв |
| :--- | :--- | :--- | :--- | :--- |
| **Pipes / FIFO** | Повна (`EPOLL_CTL_ADD`) | `EPOLLIN` (є байти в буфері) | `EPOLLOUT` (є вільне місце в буфері) | `EPOLLHUP` (закрито кінець запису), `EPOLLERR` |
| **Unix Domain Socket** | Повна (`EPOLL_CTL_ADD`) | `EPOLLIN`, `EPOLLPRI` | `EPOLLOUT` | `EPOLLRDHUP` (партнер закрив запис), `EPOLLHUP`, `EPOLLERR` |
| **POSIX Message Queue** | Прямо **не підтримується** у стандартному POSIX (у Linux `mqd_t` є FD, але `mq_notify` надійніший) | Сигнал `SIGEV_SIGNAL` або потік `SIGEV_THREAD` через `mq_notify()` | Немає прямих подій заповнення черги | Немає автоматичного сповіщення про закриття іншою стороною |
| **POSIX Shared Memory** | Прямо **не підтримується** (область пам'яті не має стану готовності) | Потребує зв'язки з `eventfd` (`EPOLLIN`) або `signalfd` | Потребує `eventfd` для сигналізації звільнення слота | Потребує зовнішнього дескрипторного каналу контролю життя |
| **eventfd** | Повна (`EPOLL_CTL_ADD`) | `EPOLLIN` (лічильник `> 0`) | `EPOLLOUT` (лічильник `< 0xfffffffffffffffeULL`) | `EPOLLERR` |

### Реєстрація сокета в epoll із прапорцем EPOLLRDHUP

Для надійного відстеження закриття віддаленої сторони сокета без виконання зайвих викликів `read()` рекомендується завжди вмикати прапорець `EPOLLRDHUP`. Коли віддалений процес закриває свій кінець з'єднання або викликає `shutdown(fd, SHUT_WR)`, ядро встановлює біт `EPOLLRDHUP`. Обробник подій у циклі `epoll` може миттєво звільнити структури сесії клієнта, не очікуючи помилки при наступній спробі передачі.

При використанні крайового спрацьовування (`EPOLLET` — Edge-Triggered) обробник зобов'язаний вичитувати дані у циклі до отримання помилки `EAGAIN` або `EWOULDBLOCK`. Якщо вичитати лише частину даних і вийти з обробника, `epoll_wait()` більше не прокинеться для цього дескриптора, доки в сокет не надійдуть нові байти від партнера, що призведе до зависання обробки запиту.

## Інтерфейси автентифікації та передачі привілеїв

Сокети домену Unix (`AF_UNIX`) мають унікальні механізми верифікації ідентичності партнерів та делегування прав доступу безпосередньо через структури ядра операційної системи.

### 1. Верифікація облікових даних: SO_PEERCRED та SO_PEERPIDFD

Ядро операційної системи зберігає атрибути процесу, який ініціював з'єднання, безпосередньо у внутрішніх структурах сокета `struct unix_sock`. Ці дані неможливо підробити в просторі користувача, оскільки вони зчитуються з дескриптора процесу `task_struct` під час виконання системного виклику `connect()`.

Структура облікових даних `struct ucred` містить:
* `pid_t pid`: ідентифікатор процесу-відправника (у поточному просторі імен PID).
* `uid_t uid`: реальний ідентифікатор користувача.
* `gid_t gid`: реальний ідентифікатор основної групи.

У сучасних версіях Linux (починаючи з ядра 6.5) опція `SO_PEERPIDFD` дозволяє отримати дескриптор `pidfd` віддаленого процесу. Це усуває стан гонитви перепризначення ідентифікаторів (PID Recycling Race): якщо клієнт завершився, а його числовий PID був повторно виданий ядром іншій програмі, дескриптор `pidfd` продовжує надійно вказувати саме на оригінальний екземпляр процесу.

### 2. Передача файлових дескрипторів: SCM_RIGHTS

Механізм передачі прав `SCM_RIGHTS` дозволяє передати відкритий файловий дескриптор через допоміжний блок керування повідомлення `struct msghdr`. Коли ядро Linux передає дескриптор через сокет домену Unix, воно знаходить структуру `struct file` у таблиці відправника, збільшує її лічильник посилань `f_count` та створює новий запис у таблиці дескрипторів процесу-отримувача під час виконання виклику `recvmsg()`.

Складові макросів керування `struct cmsghdr`:
* `CMSG_SPACE(size)`: розраховує повний обсяг пам'яті під заголовок і корисне навантаження з урахуванням вирівнювання.
* `CMSG_LEN(size)`: повертає значення довжини для поля `cmsg_len`.
* `CMSG_FIRSTHDR(msghdr_ptr)`: повертає покажчик на перший блок допоміжних даних.
* `CMSG_NXTHDR(msghdr_ptr, cmsg_ptr)`: повертає покажчик на наступний блок.
* `CMSG_DATA(cmsg_ptr)`: повертає покажчик на масив дескрипторів `(int*)`.

## Безпека та захист спільної пам'яті: запечатування memfd

Для запобігання атакам через несанкціоновану модифікацію або урізання буфера (`ftruncate`) під час читання ненадійним процесом, дескриптор анонімної пам'яті `memfd_create` запечатується через виклики `fcntl(fd, F_ADD_SEALS, ...)`.

Механізм запечатування перетворює анонімний дескриптор пам'яті на незмінний об'єкт (Immutable Buffer). Після накладання печаток навіть процес, який створив дескриптор, втрачає можливість змінити його розмір або виконати несанкціонований запис у захищену ділянку.

| Прапорець запечатування | Числове значення | Семантика обмеження операцій |
| :--- | :--- | :--- |
| `F_SEAL_SEAL` | `0x0001` | Забороняє додавати нові прапорці запечатування до дескриптора в майбутньому |
| `F_SEAL_SHRINK` | `0x0002` | Забороняє зменшувати розмір файлу через `ftruncate()` або `fallocate()` |
| `F_SEAL_GROW` | `0x0004` | Забороняє збільшувати розмір файлу (захист від вичерпання RAM) |
| `F_SEAL_WRITE` | `0x0008` | Повна заборона запису у файл (`write()` повертає `EPERM`, `mmap(PROT_WRITE)` заборонено) |
| `F_SEAL_FUTURE_WRITE` | `0x0010` | Забороняє відкривати нові мапінги на запис, зберігаючи наявні до їх закриття |

### Порядок перевірки печаток на стороні отримувача

Коли процес у пісочниці отримує дескриптор через `SCM_RIGHTS`, він зобов'язаний виконати аудит активних печаток перед тим, як відображати пам'ять у свій адресний простір:

1. Викликається `int seals = fcntl(fd, F_GET_SEALS);`.
2. Перевіряється наявність обов'язкової печатки `F_SEAL_SHRINK`. Якщо ця печатка відсутня, відправник може зменшити файл до нуля байтів, і будь-яка спроба читання пам'яті отримувачем спричинить сигнал `SIGBUS` через відсутність фізичної сторінки.
3. Якщо буфер призначений виключно для читання, перевіряється наявність печатки `F_SEAL_WRITE`. Це гарантує, що дані не будуть перезаписані іншим процесом під час їх парсингу або аналітичної обробки.

## Семантика відмов, сигналів та кодів помилок

При аварійному завершенні (`SIGKILL`, segmentation fault) одного з процесів ядро операційної системи генерує стандартизовані події та коди помилок.

| Стан події | Pipes / FIFO | Unix Domain Sockets | POSIX Shared Memory | POSIX Message Queues |
| :--- | :--- | :--- | :--- | :--- |
| **Читач закрив дескриптор / впав** | Запис генерує сигнал `SIGPIPE`; якщо сигнал заблоковано/ігнорується — виклик повертає `-1`, `errno = EPIPE` | Запис повертає `-1`, `errno = EPIPE` (або генерує `SIGPIPE` без `MSG_NOSIGNAL`) | Запис не відчуває змін; якщо читач тримав м'ютекс — мертве блокування | Черга продовжує приймати повідомлення до вичерпання `mq_maxmsg` |
| **Записувач закрив дескриптор / впав** | Читання вичитує залишок буфера; наступний `read()` повертає `0` (EOF); у `epoll` приходить `EPOLLHUP` | Читання вичитує буфер; наступний `recv()` повертає `0` (EOF); у `epoll` приходить `EPOLLRDHUP` | Структури в пам'яті лишаються незмінними; якщо записувач впав у критичній секції — блокування покинуто | Черга залишається відкритою; читач блокується в очікуванні нових повідомлень |
| **Буфер переповнено (блокуючий режим)** | Процес-записувач засинає в ядрі до появи вільного місця в каналі | Процес-записувач засинає в черзі очікування сокета | Немає поняття переповнення (керується алгоритмом кільцевого буфера в RAM) | Процес-відправник засинає у виклику `mq_send()` |
| **Буфер переповнено (неблокуючий `O_NONBLOCK`)** | `write()` повертає `-1`, `errno = EAGAIN` | `send()` повертає `-1`, `errno = EAGAIN` або `EWOULDBLOCK` | Не стосується пам'яті | `mq_send()` повертає `-1`, `errno = EAGAIN` |

### Обробка аварій у спільній пам'яті: робастні м'ютекси

Якщо процес аварійно завершується всередині критичної секції, утримуючи блокування `pthread_mutex_t`, наступна спроба захоплення м'ютекса іншим процесом повертає код помилки `EOWNERDEAD`. Процес-отримувач зобов'язаний відновити інваріанти структури даних та повідомити систему викликом `pthread_mutex_consistent()`.

Механізм робастних м'ютексів базується на системному виклику ядра Linux `set_robust_list()`. Бібліотека `glibc` під час запуску кожного потоку реєструє у ядрі покажчик на заголовок списку захоплених м'ютексів. Коли процес раптово гине (навіть у разі негайного `SIGKILL` або збою апаратного захисту пам'яті), ядро проходить по зареєстрованому списку, встановлює спеціальний біт `FUTEX_OWNER_DIED` у слові стану м'ютекса та пробуджує наступний процес, який чекає на блокування у виклику `futex()`.

Якщо процес, який отримав код `EOWNERDEAD`, розблокує м'ютекс через `pthread_mutex_unlock()` без попереднього виклику `pthread_mutex_consistent()`, стан м'ютекса назавжди позначається як `ENOTRECOVERABLE`. Будь-які наступні спроби виклику `pthread_mutex_lock()` для цього об'єкта будуть негайно завершуватися помилкою `ENOTRECOVERABLE`, запобігаючи використанню пошкоджених структур пам'яті.
