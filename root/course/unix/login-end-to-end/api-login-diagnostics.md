# 📋 Діагностична матриця відмов входу: помилки, логи та системні команди

Коли користувач стикається з відмовою входу в систему, симптоми можуть виглядати оманливо однаково: екран консолі миттєво повертається до запрошення `login: `, клієнт SSH завершує роботу з діагностикою `Permission denied (publickey,password)` або графічний дисплейний менеджер після введення пароля на секунду гасне і повертає вікно вітання. Проте під капотом ця поведінка може бути викликана збоєм у будь-якій із шести незалежних підсистем операційної системи: у базі хешів `/etc/shadow`, у логіці обчислення контрольних прапорців PAM, в обмеженнях `systemd-logind`, у правах файлової системи на каталог `$HOME`, у вичерпанні дискових квот або у відсутності бінарного файлу оболонки в списку `/etc/shells`.

Нижче наведено вичерпну діагностичну матрицю відмов входу, детальний аналіз внутрішніх кодів помилок, сигнатури системних журналів, методи динамічного трасування та команди відновлення працездатності.

## Зведена матриця точок відмови

| Підсистема | Причина відмови | Сигнатура в логах (`auth.log` / `journalctl`) | Команда інспекції | Команда усунення |
|---|---|---|---|---|
| **Shadow** | Обліковий запис заблоковано (`!`/`*`) | `pam_unix(login:account): account locked` | `passwd -S <user>` | `passwd -u <user>` або `usermod -U <user>` |
| **Shadow** | Термін дії пароля вичерпано | `pam_unix(login:account): password expired` | `chage -l <user>` | `chage -m 0 -M 90 -W 7 -I 14 <user>` |
| **Shadow** | Акаунт прострочено (поле 8 `sp_expire`) | `pam_unix(login:account): account expired` | `chage -l <user>` | `chage -E -1 <user>` (зняти дату ліміту) |
| **PAM Faillock** | Перевищено ліміт невдалих спроб | `pam_faillock(login:auth): Consecutive login failures ...` | `faillock --user <user>` | `faillock --user <user> --reset` |
| **Passwd/NSS** | Відсутня або некоректна оболонка | `login: Cannot execute /bin/zsh: No such file` | `getent passwd <user>` | `chsh -s /bin/bash <user>` |
| **Passwd/NSS** | Оболонка відсутня в `/etc/shells` | `pam_shells(login:auth): /bin/custom not in /etc/shells` | `cat /etc/shells` | `echo "/bin/custom" >> /etc/shells` |
| **SSH Daemon** | Небезпечні права на `~/.ssh` (StrictModes) | `Authentication refused: bad ownership or modes for file ...` | `ls -ld ~ ~/.ssh ~/.ssh/authorized_keys` | `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys` |
| **Квоти / VFS** | Переповнено дискову квоту в `$HOME` | `write: Disk quota exceeded` або збій `.bash_history` | `quota -v <user>` або `repquota -a` | `edquota <user>` або очищення диска |
| **pam_limits** | Вичерпано ліміт дескрипторів або процесів | `pam_limits(login:session): Could not set limit for 'nofile'` | `ulimit -a` (у сеансі) | Редагування `/etc/security/limits.conf` |
| **logind** | Збій виділення cgroup або D-Bus | `pam_systemd(login:session): Failed to create session: Connection timed out` | `systemctl status systemd-logind` | `systemctl restart systemd-logind` |
| **SELinux** | Блокування контексту безпеки SSH/PAM | `SELinux is preventing sshd from read access on authorized_keys` | `ausearch -m avc -ts recent` | `restorecon -R -v ~/.ssh` |

## Коди повернення та поведінка бібліотеки PAM

Кожен модуль PAM після виконання повертає цілочисельний код статусу. Розуміння цих кодів дозволяє системному адміністратору точно локалізувати модуль, який заблокував ланцюг автентифікації:

* `PAM_SUCCESS (0)`: Операція завершилася успішно. Усі умови модуля задоволені.
* `PAM_OPEN_ERR (1)`: Не вдалося динамічно завантажити модуль через виклик `dlopen()` (наприклад відсутня бібліотека `.so` або пошкоджено залежності).
* `PAM_SYMBOL_ERR (2)`: У завантаженому модулі відсутній необхідний символ функції (наприклад `pam_sm_authenticate`).
* `PAM_SERVICE_ERR (3)`: Помилка в конфігураційному файлі служби (синтаксична помилка в `/etc/pam.d/*`).
* `PAM_SYSTEM_ERR (4)`: Системна помилка під час виконання (нестача пам'яті, збій системного виклику ядра).
* `PAM_BUF_ERR (5)`: Помилка виділення буфера пам'яті.
* `PAM_PERM_DENIED (6)`: Доступ заборонено політикою безпеки (наприклад модуль `pam_deny.so`).
* `PAM_AUTH_ERR (7)`: Помилка автентифікації: введений пароль або токен не збігається з еталоном.
* `PAM_AUTHINFO_UNAVAIL (9)`: Неможливо отримати інформацію для автентифікації (недоступний сервер LDAP/Kerberos, пошкоджено базу даних).
* `PAM_USER_UNKNOWN (10)`: Користувач із таким логіном не знайдений у системних базах даних NSS.
* `PAM_MAXTRIES (11)`: Вичерпано максимальну кількість спроб введення автентифікатора.
* `PAM_NEW_AUTHTOK_REQD (12)`: Термін дії пароля вичерпано, вимагається обов'язкова зміна маркера автентифікації.
* `PAM_ACCT_EXPIRED (13)`: Дія самого облікового запису припинена (заблоковано адміністратором або вичерпано дату `sp_expire`).
* `PAM_SESSION_ERR (14)`: Помилка відкриття або закриття сеансу (збій у роботі `pam_systemd.so` або `pam_mkhomedir.so`).
* `PAM_CRED_UNAVAIL (15)`: Неможливо встановити облікові дані користувача (наприклад квитки Kerberos).
* `PAM_CRED_EXPIRED (16)`: Термін дії облікових даних користувача вичерпано.
* `PAM_CRED_ERR (17)`: Помилка встановлення облікових даних.
* `PAM_NO_MODULE_DATA (18)`: Модуль не зміг отримати збережені внутрішні дані попереднього кроку.
* `PAM_CONV_ERR (19)`: Помилка в роботі функції зворотного зв'язку (*conversation function*): збій термінала, закриття потоку введення або відмова користувача.
* `PAM_AUTHTOK_ERR (20)`: Помилка оновлення пароля (новий пароль не відповідає критеріям складності `pam_pwquality.so`).

## Детальний розбір механізмів відмов та їх усунення

### 1. Блокування облікового запису та захист від перебору (Faillock)

Сучасні дистрибутиви Linux на базі PAM використовують модуль `pam_faillock.so` для захисту від атак методом повного перебору паролів (*brute-force*). На відміну від застарілого `pam_tally2.so`, модуль `faillock` веде тимчасові файли невдалих спроб у каталозі оперативної пам'яті `/run/faillock/`.

Коли кількість послідовних невдалих спроб досягає порогу (типово 3 або 5), модуль тимчасово блокує можливість входу для цього облікового запису на заданий інтервал (наприклад 600 або 900 секунд). При цьому навіть якщо користувач вводить абсолютно правильний пароль, модуль негайно повертає `PAM_AUTH_ERR`, не повідомляючи клієнту про факт блокування, щоб ускладнити таймінг-атаки.

Журнал `journalctl -u systemd-logind -u sshd` містить такі записи:
```
pam_faillock(sshd:auth): Consecutive login failures for user devops: 5
pam_faillock(sshd:auth): User devops is locked out for 600 seconds
```

Перевірка статусу та лічильника невдалих спроб користувача:
```
faillock --user devops
```

Ручне скидання лічильника та миттєве розблокування:
```
faillock --user devops --reset
```

Якщо блокування встановлено на рівні файлу `/etc/shadow`, поле хешу матиме префікс `!` або `*`. Це означає, що криптографічна бібліотека `libcrypt` ніколи не зможе згенерувати хеш, що збігається із цим рядком:
```
passwd -S devops
# Вивід: devops LK 2026-08-20 ... (LK = Locked)
```
Зняття адміністративного блокування пароля:
```
passwd -u devops
```

### 2. Часові поля та старіння паролів (Password Aging)

Підсистема контролю старіння паролів у Linux спирається на 9 полів файлу `/etc/shadow`. Кожне числове поле вимірюється в кількості діб від 1 січня 1970 року (Unix Epoch):

```
devops:$y$j9T$vL6K0...$7mX1...:19800:0:90:7:14:19900:
```

* `sp_lstchg` (19800): День останньої зміни пароля.
* `sp_min` (0): Мінімальний інтервал між змінами. Якщо користувач спробує змінити пароль раніше, `passwd` поверне відмову.
* `sp_max` (90): Максимальний термін придатності. Якщо `Поточний_День > sp_lstchg + sp_max`, модуль `pam_unix` повертає `PAM_NEW_AUTHTOK_REQD` і примушує користувача оновити пароль при першому вході.
* `sp_warn` (7): Кількість днів до закінчення `sp_max`, протягом яких при кожному вході виводиться попередження `Warning: your password will expire in X days`.
* `sp_inact` (14): Пільговий період після прострочення. Якщо користувач не увійшов і не змінив пароль протягом цього часу, статус акаунта перемикається на `PAM_ACCT_EXPIRED`, і самостійний вхід стає неможливим без втручання адміністратора.
* `sp_expire` (19900): Абсолютна дата вимкнення облікового запису (наприклад для тимчасових підрядників).

Інспекція параметрів старіння:
```
chage -l devops
```

Встановлення політики (максимальний вік 90 днів, попередження за 7 днів, пільговий період 14 днів):
```
chage -m 0 -M 90 -W 7 -I 14 devops
```

Повне скасування обмежень за термінами:
```
chage -M -1 -E -1 devops
```

### 3. Механізм StrictModes та дозволи файлової системи SSH

Демон OpenSSH містить жорстку внутрішню перевірку безпеки `StrictModes yes` (увімкнено за замовчуванням у `/etc/ssh/sshd_config`). Мета цієї перевірки — унеможливити ситуацію, коли інший локальний користувач може модифікувати відкриті ключі жертви або підмінити шлях до них.

`sshd` перевіряє право власності та права доступу за всім ланцюжком каталогів від кореня файлової системи до цільового файлу ключів:
1. Каталог `/home` — власник `root:root`, права `0755`.
2. Домашній каталог `/home/devops` — власник `devops:devops`, права `0750` або `0755` (група чи інші не повинні мати права `w`).
3. Каталог `/home/devops/.ssh` — власник `devops:devops`, права `0700` (`drwx------`).
4. Файл `/home/devops/.ssh/authorized_keys` — власник `devops:devops`, права `0600` (`-rw-------`).

Якщо хоча б один батьківський каталог у цьому ланцюжку має право на запис для групи (`chmod g+w`) або інших користувачів (`chmod o+w`), `sshd` відкидає автентифікацію за публічним ключем і фіксує помилку:
```
Authentication refused: bad ownership or modes for directory /home/devops/.ssh
```

Відновлення коректних прав доступу:
```
chown -R devops:devops /home/devops
chmod 750 /home/devops
chmod 700 /home/devops/.ssh
chmod 600 /home/devops/.ssh/authorized_keys
```

Якщо в системі активний обов'язковий контроль доступу SELinux, некоректний контекст безпеки файлів (наприклад якщо файл `authorized_keys` було скопійовано з `/tmp`) також заблокує читання демоном `sshd`:
```
# Перевірка контексту безпеки:
ls -lZ ~/.ssh/authorized_keys
# Відновлення стандартного контексту ssh_home_t:
restorecon -R -v ~/.ssh
```

### 4. Динамічне тестування конфігурацій PAM через pamtester

Для безпечної перевірки конфігураційних файлів у `/etc/pam.d/` без ризику втратити доступ до робочого термінала використовується інструмент `pamtester`.

Синтаксис виклику:
```
pamtester [-v] [-I <item>=<value>] <service-name> <username> <pam-function>
```

Типові сценарії діагностики:

1. Перевірка введення пароля та фази `auth`:
```
pamtester -v login devops authenticate
```
Утиліта запитує пароль, виконує конфігураційний стек `/etc/pam.d/login` і друкує точний код повернення бібліотеки (наприклад `pamtester: successfully authenticated`).

2. Перевірка чинності облікового запису (`account`):
```
pamtester -v sshd devops acct_mgmt
```
Дозволяє перевірити, чи не блокують користувача модулі `pam_time.so`, `pam_access.so` або `pam_unix(account)`.

3. Перевірка відкриття та закриття сеансу (`session`):
```
pamtester -v login devops open_session
pamtester -v login devops close_session
```
Тестує створення скоупів у `systemd-logind` та застосування обмежень `pam_limits.so`.

### 5. Трасування системних викликів процесу входу

У складних випадках, коли логи не дають повної відповіді, найкращим інструментом діагностики є пряме трасування системних викликів через `strace`.

Трасування роботи локального демона `login`:
```
strace -f -e trace=openat,read,write,setuid,setgid,initgroups,execve -p $(pgrep -f "agetty.*tty1")
```

Трасування сеансового процесу `sshd`:
```
# Запуск окремого налагоджувального екземпляра sshd на порту 2222:
/usr/sbin/sshd -d -p 2222

# Або підключення strace до головного демона:
strace -f -s 512 -o /tmp/sshd_trace.log -p $(pgrep -o sshd)
```

Аналіз отриманого трасування дозволяє побачити точний системний виклик, який повернув код помилки (наприклад `setuid(1000) = -1 EPERM (Operation not permitted)` або `chdir("/home/devops") = -1 ENOENT (No such file or directory)`).
