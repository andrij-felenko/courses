# ⚙️ Виробничий сценарій резервного копіювання: повний розбір від прапорців до очищення

Створення надійного автоматизованого сценарію для виробничого середовища вимагає розв'язання цілого комплексу інженерних проблем: запобігання паралельним запускам у планувальнику `cron`, ізоляція тимчасових даних у файловій системі, гарантоване прибирання ресурсів при аварійних зупинках, розділення потоків корисних даних та діагностичних повідомлень, а також атомарна фіксація результату.

У цьому проекті розглядається повноцінна утиліта архівації та резервного копіювання `backup-tool.sh`, яка демонструє застосування всіх захисних механізмів оболонки Bash на реальній інженерній задачі.

## Постановка задачі та архітектурні вимоги

Сценарій має приймати на вхід шлях до вихідного каталогу даних, створювати стиснений архів `tar.gz` з унікальною часовою міткою, генерувати контрольну суму SHA-256 для верифікації цілісності, переміщувати результати в каталог сховища та очищати застарілі копії відповідно до встановленого терміну зберігання (*retention policy*).

Сценарій зобов'язаний відповідати таким системним інваріантам:

1. **Захист від накладання процесів (Concurrency Lock)**: якщо попередній запуск резервного копіювання ще триває (наприклад, через великий обсяг нових даних або повільну мережеву файлову систему), новий запуск із `cron` повинен негайно завершитися без пошкодження файлів та блокувань за допомогою механізму `flock`.
2. **Ізольована робоча область**: створення архіву та підрахунок контрольних сум мають відбуватися в унікальному тимчасовому каталозі з правами `0700`, створеному утилітою `mktemp -d`.
3. **Гарантоване прибирання**: будь-яке завершення процесу (включаючи `Ctrl+C`, сигнал `SIGTERM` від менеджера контейнерів або аварійну зупинку `set -e`) має видаляти тимчасові файли без витоку дискового простору.
4. **Атомарний коміт**: цільовий архів стає доступним у сховищі лише після успішного завершення архівації та підрахунку контрольних сум за допомогою системного виклику `rename()` (команда `mv`).
5. **Чистота потоків**: усі логи, попередження та звіти пишуться виключно в потік помилок `stderr`, що дозволяє використовувати `stdout` для передачі структурованих даних або конвеєрів.

## Покроковий розбір системних рішень надійності

Розглянемо, як системні компоненти сценарію забезпечують відмовостійкість у критичних виробничих ситуаціях.

### Неблокуючий замок через flock проти застарілих PID-файлів

Класичний наївний підхід до запобігання повторним запускам полягає у записі поточного ідентифікатора процесу в текстовий файл: `echo $$ > /var/run/script.pid`. Цей метод має фундаментальну ваду: якщо сервер раптово перезавантажується або процес гине від сигналу `SIGKILL`, файл блокування залишається на диску. Наступний запуск бачить наявний файл і помилково відмовляється працювати, доки системний адміністратор не видалить блокування вручну. Гірше того: після перезавантаження операційна система може надати той самий числовий PID іншому, зовсім сторонньому процесу (веб-серверу або базі даних), що остаточно блокує виконання бекапів.

Утиліта `flock` використовує системний виклик ядра Linux `flock(fd, LOCK_EX | LOCK_NB)`. У функції `acquire_lock` ми відкриваємо власний файловий дескриптор `200` на запис у файл блокування `/tmp/backup-tool.sh.lock`:

```bash
exec 200>"${LOCK_FILE}"
if ! flock -n 200; then
    log_warn "Інший екземпляр вже виконується. Завершення роботи."
    exit 0
fi
```

Якщо інший процес уже утримує замок, виклик `flock -n` негайно повертає код `1` без блокування виконання. Скрипт виводить попередження та штатно завершується з кодом `0`. Коли скрипт завершує роботу (штатно чи аварійно), ядро операційної системи автоматично закриває всі відкриті файлові дескриптори таблиці процесу. Це гарантовано звільняє замок на рівні структур ядра VFS навіть при аварійному вимкненні живлення чи виклику `kill -9`.

### Ізоляція каталогу пісочниці та пастка cleanup

Створення робочого простору виконується командою `mktemp -d -t "${SCRIPT_NAME}.XXXXXX"`. Ця функція ядра VFS створює каталог із маскою `0700` (`rwx------`), що робить його недоступним для читання чи запису іншими невідокремленими локальними користувачами системи. Це запобігає атакам класу Symlink Race (стан перегонів символьних посилань), коли зловмисник намагається підсунути символьне посилання на системні файли під час створення тимчасових об'єктів у каталозі `/tmp`.

Пастка реєструється на перелік подій:
```bash
trap cleanup EXIT INT TERM HUP
```

Функція `cleanup` містить три критичні гарантії:
1. Збереження початкового коду помилки `local exit_code=$?` на самому початку функції до виконання будь-яких команд очищення. Якщо цього не зробити, команда `rm -rf` оновить `$?` до 0, і сценарій поверне фальшивий статус успіху, ввівши в оману зовнішній моніторинг.
2. Скасування пастки `trap - EXIT INT TERM HUP`, що запобігає нескінченному зацикленню обробника при збої всередині самої функції `cleanup`.
3. Перевірка наявності каталогу `[[ -n "${TMP_DIR:-}" ]] && [[ -d "${TMP_DIR}" ]]`, що захищає від спроби видалити порожній шлях чи кореневий каталог у разі, якщо помилка виникла ще до створення тимчасової теки.

### Атомарна підміна файлу через системний виклик rename

Якщо записувати архів безпосередньо в цільовий каталог сховища (`DEST_DIR`), процес створення якого займає кілька хвилин, зовнішні сервіси моніторингу або скрипти синхронізації (наприклад, `rsync` чи хмарні агенти бекапу) можуть зчитати напівзаписаний, пошкоджений файл.

Формування архіву та перевірочної контрольної суми відбувається виключно всередині `TMP_DIR`. Лише після того, як архів повністю записано на диск і обчислено його SHA-256 хеш, виконується команда:
```bash
mv "${temp_archive_path}" "${DEST_DIR}/${archive_filename}"
```
На рівні операційної системи команда `mv` в межах однієї файлової системи транслюється в єдиний системний виклик `rename()`, який атомарно підміняє вказівник на іноду в каталозі. Будь-який сторонній процес або бачить попередній стан, або вже повністю сформований та валідний новий архів.

### Ротація з безпечним розбором нульового байта (find -print0)

Для очищення застарілих архівів використовується зв'язка `find ... -print0` та `read -r -d $'\0'`:

```bash
while IFS= read -r -d $'\0' old_file; do
    rm -f "${old_file}"
done < <(find "${DEST_DIR}" -maxdepth 1 -type f -name "${source_name}_*.tar.gz*" -mtime +"${RETENTION_DAYS}" -print0)
```

Символ нового рядка `\n` та пробіли є допустимими символами в іменах файлів у стандарті POSIX. Єдиним символом, який принципово не може зустрічатися в імені файлу, є нульовий байт (`\0`, `NUL`). Передача списку через нульовий роздільник гарантує, що файли з пробілами чи спеціальними символами будуть видалені коректно без ризику випадкового розбиття шляху на частини.

## Тестування та імітація збоїв (Fault Injection)

Для верифікації надійності скрипта проводять серію стрес-тестів:

1. **Імітація браку місця на диску**: створення невеликого tmpfs-розділу та запуск скрипта з файлами, обсяг яких перевищує доступну квоту. Утиліта `tar` завершується з помилкою `No space left on device`, після чого спрацьовує `set -e`. Пастка `cleanup` миттєво видаляє пошкоджений файл з `TMP_DIR`, а в цільовому каталозі `DEST_DIR` не з'являється битих файлів нульового розміру.
2. **Переривання процесу сигналом SIGINT**: натискання `Ctrl+C` під час стиснення багатогігабайтного масиву даних. Сигнал перехоплюється оболонкою, обробник `cleanup` очищає створений тимчасовий каталог і закриває дескриптор блокування `200`, повертаючи код завершення `130`.
3. **Паралельний запуск двох екземплярів**: одночасний старт двох процесів у фоновому режимі (`./backup-tool.sh ... & ./backup-tool.sh ... &`). Перший процес успішно захоплює замок, а другий негайно друкує попередження у `stderr` і виходить з кодом `0`, не створюючи надлишкового навантаження на систему введення-виведення.

## Перевірка статичним аналізатором ShellCheck

Сценарій пройшов повну верифікацію статичним аналізатором коду `shellcheck` без жодного зауваження:

```sh
shellcheck --severity=style backup-tool.sh
```

Лінтер перевіряє правильність лапкування всіх розкриттів змінних, використання вбудованих конструкцій `[[ ... ]]` замість застарілого `[ ... ]`, відсутність небезпечних змінних у `trap`, а також перевіряє сумісність синтаксису з оголошеним шебангом `#!/usr/bin/env bash`.
