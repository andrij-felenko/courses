# 📜 Від рядка в історії до сценарію: як Unix навчився виконувати файли

Коли на початку 1970-х років Кен Томпсон (Ken Thompson) створив першу командну оболонку для Unix (відому як Thompson shell), поняття виконуваного текстового сценарію у сучасному розумінні взагалі не існувало. Оболонка була простим інтерактивним транслятором команд, який зчитував байти з термінала `tty` та викликав системні виклики `fork()` і `exec()`. Якщо системному адміністратору або програмісту потрібно було повторити послідовність із кількох дій, єдиним штатним способом було перенаправити стандартний вхід нового екземпляра оболонки на текстовий файл:

```sh
sh < process_data.txt
```

У такій схемі файл `process_data.txt` не мав жодного системного статусу програми: це був звичайний потік символів, який інтерпретатор зчитував байт за байтом, точно так само, як введення з клавіатури. Ядро операційної системи нічого не знало про зміст файлу і вважало виконуваними лише скомпільовані бінарні об'єктні файли формату a.out.

## Поява мови Bourne Shell та криза різнорідних інтерпретаторів

Із появою у 1979 році в Seventh Edition Unix (V7) оболонки Стівена Борна (Stephen Bourne, `sh`) командна оболонка перетворилася на повноцінну мову програмування зі змінними, циклами, функціями та умовними операторами. Майже одночасно Білл Джой (Bill Joy) в університеті Берклі розробив C Shell (`csh`), синтаксис якої імітував мову C і набув величезної популярності серед академічних користувачів BSD Unix.

Виникла фундаментальна архітектурна проблема. Коли користувач встановлював біт виконання `chmod +x script` на текстовий файл і набирав у терміналі `./script`, ядро Unix робило системний виклик `execve()`. Зустрівши невідомий двійковий заголовок, ядро повертало помилку `ENOEXEC` («Exec format error»). Інтерактивна оболонка перехоплювала цю помилку і на власний розсуд намагалася розібрати файл: Bourne shell запускала для нього копію `sh`, а C shell — копію `csh`.

Якщо файл було написано зі специфічними конструкціями Bourne shell (наприклад, `if [ $? -eq 0 ]; then`), а запускав його користувач, чиєю оболонкою за замовчуванням була `csh`, скрипт аварійно завершувався із синтаксичною помилкою на першому ж рядку. Текстові програми не мали механізму самоідентифікації: файл залежав не від власного синтаксису, а від поточної оболонки того, хто його запускав.

## Двобайтовий магічний порятунок Денніса Рітчі: народження шебангу

Рішення запропонував Денніс Рітчі (Dennis Ritchie) наприкінці 1979 року. Він модифікував реалізацію системного виклику `execve()` безпосередньо всередині ядра Unix, запровадивши розпізнавання магічного двобайтового заголовка `0x23 0x21` — символів ASCII `#!` (англ. *number sign* та *exclamation mark*, що згодом отримали сленгову назву *shebang* або *hashbang*).

Механізм ядра працював напрочуд елегантно:

1. Коли ядро зчитує перші байти файлу під час `execve()`, воно перевіряє сигнатуру.
2. Якщо першими двома байтами є `#!`, ядро припиняє спроби розпізнати файл як двійковий образ ELF або a.out.
3. Ядро зчитує залишок першого рядка (аж до символу нового рядка `\n` або ліміту довжини буфера ядра, зазвичай 127 або 255 байтів).
4. Зчитаний рядок розбивається на шлях до інтерпретатора (наприклад, `/bin/sh` або `/usr/bin/perl`) та рівно один необов'язковий аргумент.
5. Ядро формує новий масив аргументів, де нульовим аргументом стає шлях до інтерпретатора, першим аргументом — ім'я самого скрипта, а далі додаються всі аргументи, передані користувачем.
6. Ядро викликає внутрішню функцію завантажувача для вказаного двійкового інтерпретатора.

Завдяки цій зміні текстовий файл отримав статус повноправного виконуваного образу на рівні інтерфейсу системних викликів ядра. Будь-яка програма, скомпільована на C, могла викликати `execve("./my_script", ...)` без посередництва проміжної командної оболонки.

## Еволюція від ручного буфера історії до детермінованих скриптів

У 1980-х роках із поширенням утиліт інтерактивної історії (`history`, команда `fc` — *fix command*, механізм підстановки подій `!event` у C shell та GNU Bash) склався типовий робочий процес інженера:
1. Виконати експериментальні команди безпосередньо у терміналі;
2. Натиснути стрілку вгору або викликати історію команд;
3. Скопіювати вдалий ланцюжок команд у текстовий файл.

Проте дуже швидко виявилося, що інтерактивне середовище та середовище автономного виконання мають несумісні передумови. Інтерактивна оболонка проєктувалася для зручності людини: вона прощає помилки, очікує підтверджень, завантажує персональні налаштування з `~/.bashrc` і друкує повідомлення негайно на екран.

Коли ж та сама послідовність рядків потрапляла в планувальник завдань `cron` або запускалася під час завантаження системи `init`, скрипт несподівано зависав або руйнував дані. Виявилося, що перетворення рядків з історії в надійну інженерну програму вимагає окремої дисципліни: ізоляції середовища, суворої обробки помилок та явної параметризації.

## Портабельність: бій між /bin/bash, /bin/sh та /usr/bin/env

У 1990-х роках із розвитком стандарту POSIX.2 та поширенням Linux з'явилася нова дилема шляхів. У класичних комерційних системах Unix (Solaris, AIX, HP-UX) оболонка `/bin/sh` була суворим, мінімалістичним інтерпретатором без розширень. У Linux стандартною системною оболонкою став GNU Bash, який у багатьох дистрибутивах симлінком прив'язували до `/bin/sh`.

Це породило небезпечне явище — так звані *башизми* (англ. *bashisms*): конструкції на кшталт `[[ ... ]]`, `source` замість `.`, підстановки масивів та перевірки кодів завершення конвеєрів `PIPESTATUS`. Скрипти із шебангом `#!/bin/sh`, написані на Linux, катастрофічно ламалися на FreeBSD або Solaris, де `/bin/sh` не підтримував розширень Bash.

Водночас у системах сімейства BSD або NixOS двійковий файл Bash часто встановлювався не в `/bin/bash`, а в `/usr/local/bin/bash` або `/run/current-system/sw/bin/bash`. Жорстко закодований шлях `#!/bin/bash` призводив до помилки «No such file or directory».

Це привело індустрію до сучасного стандарту написання шебангу: використання утиліти непрямого пошуку `/usr/bin/env bash`, яка через змінну `PATH` знаходить перший доступний інтерпретатор Bash у системі, гарантуючи водночас доступність мовних розширень та переносність між будь-якими Unix-подібними операційними системами.
