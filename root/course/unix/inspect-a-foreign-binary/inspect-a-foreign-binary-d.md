Системний інженер або фахівець із безпеки отримує невідомий виконуваний файл `sensor-agent`, витягнутий з підозрілого контейнера або застарілого промислового сервера. Документація відсутня, вихідних текстів немає, розробники недоступні. Під час першої інтуїтивної спроби з'ясувати призначення файлу шляхом прямого запуску через термінал операційна система видає загадкову помилку:

```
$ ./sensor-agent --help
bash: ./sensor-agent: No such file or directory
```

Файл фізично існує на диску, має права на виконання (`chmod +x`), проте ядро відмовляється створити процес, повертаючи помилку відсутності файлу. В іншій ситуації запуск невідомого бінарника на сервері може призвести до миттєвого знищення робочої бази даних, запуску прихованого мережевого бекдору або незворотного пошкодження системних файлів. Сліпий запуск чужого коду — найгрубіша помилка експлуатації.

Розкриття чужого бінарника вимагає суворого неінвазивного підходу: дослідження його внутрішніх структур, залежностей та вшитих констант без передачі керування процесору.

*Послідовні фази неінвазивного тріажу виконуваного файлу від базового визначення формату до глибокого аналізу символів і констант.*

### 1. Проблема «чорної скриньки» та принцип статичного тріажу

Кожен скомпільований виконуваний файл у світі Linux є впорядкованим двійковим контейнером стандарту `ELF` (англ. *Executable and Linkable Format*). Навіть якщо автори програми навмисно вичистили всі налагоджувальні імена функцій, сам двійковий формат зобов'язаний містити метадані, необхідні операційній системі для відображення коду в пам'ять, передачі керування на точку входу та динамічного зв'язування з бібліотеками.

Принцип статичного тріажу (англ. *triage* — сортування та первинний огляд) базується на чотирьох послідовних рівнях дослідження:
1. **Паспортизація формату:** встановлення архітектури процесора, розрядності, порядку байтів, типу лінкування (статичне чи динамічне) та шляху до інтерпретатора.
2. **Аудит залежностей:** виявлення зовнішніх динамічних бібліотек (`.so`), вимог до версій системних символів та шляхів їх пошуку без запуску коду.
3. **Анатомія структур та пам'яті:** перевірка сегментів пам'яті (`PT_LOAD`), захисних механізмів стека (`NX`), захисту таблиць релокацій (`RELRO`) та імпортованих функцій системного API (`.dynsym`).
4. **Витягування текстових констант:** пошук мережевих адрес, ключів конфігурації, файлових шляхів, імен модулів та діагностичних повідомлень, зашитих у секціях даних.

Такий покроковий розбір дозволяє сформувати повний профіль програми до того, як вона отримає доступ до ресурсів системи.

### 2. Експрес-ідентифікація через `file`: первинний паспорт бінарника

Першим інструментом аналізу виступає утиліта `file`. Вона не інтерпретує код, а зчитує системну базу сигнатур `magic` (скомпільовану у файл `/usr/share/misc/magic.mgc`) та перевіряє перші байти головного заголовка `Elf64_Ehdr`.

```bash
$ file sensor-agent
sensor-agent: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib/ld-musl-x86_64.so.1, BuildID[sha1]=4a1f8c..., stripped
```

Один рядок виводу дає вичерпну відповідь на те, чому бінарник відмовився запускатися на машині з Ubuntu або Debian.

#### Магічні байти та архітектурний профіль

Кожен коректний файл ELF починається з 16-байтового масиву ідентифікації `e_ident`:
* **Магічні байти (`\x7fELF`):** байти `0x7f 0x45 0x4c 0x46` на початку файлу (`e_ident[EI_MAG0..3]`). Якщо ці байти пошкоджені або змінені, ядро Linux негайно перериває виклик `execve()` із системною помилкою `ENOEXEC` (*Exec format error*).
* **Клас і розрядність (`64-bit` проти `32-bit`):** байт `e_ident[EI_CLASS]` приймає значення `ELFCLASS64` (число `2`) або `ELFCLASS32` (число `1`). Якщо 64-бітне ядро скомпільовано без підтримки 32-бітної сумісності (без опції `CONFIG_COMPAT`), спроба запуску 32-бітного файлу завершиться помилкою.
* **Порядок байтів (`LSB` проти `MSB`):** байт `e_ident[EI_DATA]` вказує на порядок байтів. `ELFDATA2LSB` (число `1`, Little-Endian) характерний для архітектур x86-64 та ARM64 у стандартному режимі, тоді як `ELFDATA2MSB` (число `2`, Big-Endian) зустрічається в мережевих маршрутизаторах (MIPS, PowerPC) або мейнфреймах s390x. Запуск бінарника з невірним порядком байтів апаратно неможливий без емулятора.
* **Архітектура процесора (`x86-64`, `ARM aarch64`, `ARM`, `RISC-V`):** 16-бітне числове поле `e_machine` визначає тип інструкцій. Якщо бінарник зібрано під ARM64 (`EM_AARCH64`, код `0xb7`), звичайний процесор Intel Core або AMD Ryzen (`EM_X86_64`, код `0x3e`) не зможе декодувати жодної його інструкції.

#### Тип об'єкта: `executable` проти `pie executable`

Поле `e_type` головного заголовка визначає режим розміщення коду в пам'яті:
1. `ET_EXEC` (`executable`): класичний бінарник із фіксованою адресою завантаження (наприклад, віртуальна база `0x400000` на x86-64). Компілятор жорстко прив'язує адреси функцій до фіксованих чисел. Такі програми несумісні з повною рандомізацією адресного простору (ASLR), що знижує їхню захищеність від експлуатації вразливостей.
2. `ET_DYN` (`pie executable`): сучасний позиційно-незалежний виконуваний файл (*Position-Independent Executable*, PIE). Технічно він оформлений як спільна бібліотека, але має точку входу `_start`. Під час кожного запуску ядро відображає сегменти програми за новою випадковою базовою адресою, забезпечуючи максимальну стійкість проти атак переповнення буфера.

#### Пастка динамічного інтерпретатора

Фрагмент `dynamically linked, interpreter /lib/ld-musl-x86_64.so.1` розкриває справжню причину помилки `bash: ./sensor-agent: No such file or directory`.

Коли програма лінкується динамічно, статичний компонувальник записує у спеціальний сегмент `PT_INTERP` точний текстовий шлях до системного завантажувача. Під час системного виклику `execve` ядро Linux виконує функцію ядра `load_elf_binary()` (модуль `fs/binfmt_elf.c`):
1. Ядро зчитує заголовок `ELF`, знаходить сегмент `PT_INTERP` і витягує з нього текстовий рядок шляху.
2. Ядро намагається відкрити файл завантажувача за допомогою внутрішнього системного виклику `open_exec()`.
3. Якщо бінарник скомпільовано під дистрибутив Alpine Linux (який використовує стандартну бібліотеку `musl libc`), у ньому прописано шлях `/lib/ld-musl-x86_64.so.1`.
4. Якщо цей файл запустити на стандартній системі Ubuntu чи Debian, де встановлено бібліотеку `glibc` і завантажувач `/lib64/ld-linux-x86-64.so.2`, ядро Linux не знаходить вказаного інтерпретатора і повертає системну помилку `ENOENT` (*No such file or directory*).

Оболонка `bash` отримує цей код помилки від ядра і друкує повідомлення, яке користувач помилково сприймає як відсутність самого файлу `sensor-agent`.

#### Стан налагоджувальної інформації: `stripped` проти `not stripped`

Позначка `stripped` свідчить про те, що з файлу видалено таблицю символів `.symtab` та налагоджувальні секції формату DWARF (`.debug_info`, `.debug_line`). У такому бінарнику відсутні імена внутрішніх статичних функцій та назви локальних змінних. Натомість бінарник зі статусом `not stripped` містить повні імена всіх функцій розробника, що значно полегшує аналіз.

Поле `BuildID[sha1]=...` містить криптографічний хеш відкритого коду та параметрів збірки, згенерований компілятором у секції `.note.gnu.build-id`. За цим хешем системні інженери можуть шукати відокремлені пакети налагодження (`debuginfo` / `dbgsym`) у репозиторіях дистрибутивів або через сервіси `debuginfod`.

### 3. Аналіз динамічних залежностей та смертельна пастка `ldd`

З'ясувавши, що бінарник скомпільовано динамічно, інженер повинен визначити повний перелік спільних бібліотек (`.so`), необхідних для його функціонування. Першим інструментом, до якого традиційно звертаються адміністратори, є утиліта `ldd`. Проте її застосування до невідомих або підозрілих файлів несе пряму загрозу безпеці.

![Небезпека ldd для невідомого коду проти безпечного статичного аналізу](/root/course/unix/inspect-a-foreign-binary/img/ldd-execution-trap-vs-safe-audit.svg)
*Порівняння ризиків виконання неперевіреного бінарника через скрипт ldd та гарантовано безпечного статичного аналізу секцій за допомогою readelf.*

#### Чому `ldd` — це не аналізатор, а оболонка запуску

Утиліта `ldd` (`/usr/bin/ldd`) є звичайним текстовим shell-сценарієм POSIX, а не ізольованим бінарним парсером. Щоб отримати список бібліотек, сценарій `ldd` встановлює діагностичну змінну оточення `LD_TRACE_LOADED_OBJECTS=1` і **безпосередньо викликає досліджуваний бінарник або його динамічний завантажувач**:

```bash
# Спрощена схема того, що реально робить ldd всередині:
LD_TRACE_LOADED_OBJECTS=1 /lib64/ld-linux-x86-64.so.2 ./suspicious-binary
```

За задумом авторів `glibc`, коли завантажувач `ld-linux.so` бачить активну змінну `LD_TRACE_LOADED_OBJECTS`, він завантажує залежні бібліотеки, друкує їхні адреси в термінал і завершує процес через системний виклик `_exit()`, не передаючи керування на точку входу `main()`.

Проте на практиці цей механізм відкриває дві критичні вразливості виконання довільного коду (англ. *Arbitrary Code Execution*):

1. **Фальсифікація заголовка `PT_INTERP`:** Будь-який розробник або зловмисник може записати у заголовок `PT_INTERP` виконуваного файлу шлях до довільної програми в системі — наприклад, `/bin/sh` або власного скомпільованого скрипту. Коли користувач викликає `ldd ./malicious-binary`, сценарій `ldd` виявляє заголовок `PT_INTERP` і запускає вказаний там файл, передаючи йому цільовий бінарник як аргумент. У результаті замість діагностики система виконує довільний код зловмисника з правами поточного користувача.
2. **Конструктори ініціалізації (`.init_array` та `DT_INIT`):** Динамічний завантажувач у деяких версіях Unix-подібних систем та старих релізах Linux може виконувати секції ініціалізації залежних бібліотек ще до завершення фази трасування. Якщо бінарник підтягує локальну шкідливу бібліотеку через відносний `RPATH`, її конструктор `__attribute__((constructor))` отримає керування безпосередньо під час виклику `ldd`.

Офіційна сторінка системного довідника `man 1 ldd` містить пряме попередження: *«ldd ніколи не слід запускати на неперевірених виконуваних файлах, оскільки це може призвести до виконання коду»*.

#### Безпечна альтернатива: статичний аудит через `readelf` та `objdump`

Щоб переглянути залежності гарантовано безпечно, необхідно зчитувати байти динамічної секції `.dynamic` як пасивний масив даних. За це відповідає прапорець `-d` утиліти `readelf`:

```bash
$ readelf -d sensor-agent | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libssl.so.3]
 0x0000000000000001 (NEEDED)             Shared library: [libcrypto.so.3]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

Команда парсить виключно записи типу `DT_NEEDED` усередині бінарника. Процесор не виконує жодної інструкції досліджуваного файлу, а завантажувач не ініціалізується.

Аналогічний результат без ризику виконання забезпечує утиліта `objdump` із прапорцем приватних заголовків:

```bash
$ objdump -p sensor-agent | grep NEEDED
  NEEDED               libssl.so.3
  NEEDED               libcrypto.so.3
  NEEDED               libc.so.6
```

#### Аудит шляхів пошуку бібліотек: `DT_RUNPATH` та `DT_RPATH`

Окрім списку бібліотек, динамічна секція може містити жорстко зашиті шляхи, за якими програма шукає свої залежності в обхід системних каталогів:

```bash
$ readelf -d sensor-agent | grep -E 'RPATH|RUNPATH'
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN/../lib:/opt/custom/lib]
```

* **`DT_RPATH`:** застарілий заголовок. Має найвищий пріоритет і перекриває навіть системну змінну оточення `LD_LIBRARY_PATH`. Якщо в бінарнику прописано відносний `RPATH=.`, програма завантажуватиме бібліотеки з поточного робочого каталогу, що є вектором атаки типу DLL Hijacking.
* **`DT_RUNPATH`:** сучасний заголовок. Має нижчий пріоритет, ніж `LD_LIBRARY_PATH`, що дозволяє адміністратору перевизначити шлях пошуку під час тестування.
* **Спеціальна змінна `$ORIGIN`:** позначає каталог, у якому фізично розташований сам виконуваний файл. Це дозволяє створювати портативні бандли програм, що несуть власні версії бібліотек у сусідній теці `lib/`.

Повний довідник системних команд та їхніх прапорців наведено у довідковій вставці [Довідник команд та прапорців для експрес-аудиту бінарних файлів ELF](root:unix/inspect-a-foreign-binary/api-binary-inspection-cheat-sheet.md).

### 4. Глибока анатомія ELF через `readelf` та `objdump`

Повна реконструкція призначення бінарника вимагає занурення у внутрішню організацію файлу. Формат ELF має двоїсту природу: він містить **сегменти** (для завантажувача ядра під час виконання) та **секції** (для компонувальника, відлагоджувача та аналітика).

![Двоїста архітектура ELF: Program Headers та Section Headers](/root/course/unix/inspect-a-foreign-binary/img/elf-dual-view-segments-sections.svg)
*Двоїста структура ELF: сегменти Program Headers визначають розкладку пам'яті для завантажувача ядра, а Section Headers описують зміст для аналітика та компонувальника.*

#### Головний заголовок ELF (`Elf64_Ehdr`)

Початок файлу містить структуру розміром 64 байти, яку зчитує команда `readelf -h`:

```bash
$ readelf -h sensor-agent
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00 
  Class:                             ELF64
  Data:                              2's complement, little endian
  Version:                           1 (current)
  OS/ABI:                            UNIX - System V
  ABI Version:                       0
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Version:                           0x1
  Entry point address:               0x1080
  Start of program headers:          64 (bytes into file)
  Start of section headers:          14832 (bytes into file)
  Flags:                             0x0
  Size of this header:               64 (bytes)
  Size of program headers:           56 (bytes)
  Number of program headers:         11
  Size of section headers:           64 (bytes)
  Number of section headers:         29
  Section header string table index: 28
```

Ключові поля:
* `Entry point address (0x1080)`: віртуальна адреса точки входу `_start`, на яку процесор стрибає після завантаження програми в пам'ять.
* `Start of program headers (64)`: зміщення таблиці сегментів (починається одразу за головним заголовком).
* `Start of section headers (14832)`: зміщення таблиці секцій (зазвичай розташована наприкінці файлу).

#### Сегменти програми (`Program Headers`) та захист пам'яті

Таблиця заголовків програми зчитується командою `readelf -l`:


Кожен сегмент типу `PT_LOAD` описує неперервний блок байтів, який відображається у пам'ять:
* **Сегмент коду (Прапорці `R E`):** містить машинні інструкції. Доступний для читання та виконання, але закритий для запису (`PROT_READ | PROT_EXEC`). Спроба змінити байти в цьому сегменті під час виконання викличе апаратне переривання процесора `#GP` або `#PF` і сигнал `SIGSEGV`.
* **Сегмент незмінних даних (Прапорці `R`):** містить рядкові літерали та числові константи (`.rodata`).
* **Сегмент змінних даних (Прапорці `RW`):** містить глобальні змінні (`.data`) та буфери неініціалізованих даних (`.bss`). Зверніть увагу: розмір у пам'яті `MemSiz (0x280)` перевищує розмір у файлі `FileSiz (0x240)`. Різниця у 64 байти — це секція `.bss`, під яку ядро виділяє нульові сторінки пам'яті без збереження їх на диску.

#### Аудит маркерів безпеки ядра: `GNU_STACK` та `GNU_RELRO`

1. **Сегмент `PT_GNU_STACK` (Захист стека):**
   Якщо у колонці `Flg` стоїть `RW`, стек процесу захищений бітом `NX` (*No-Execute* / `W^X`). Ядро забороняє виконання коду зі стека. Якщо ж інспектор бачить прапорці `RWE`, це означає, що програма скомпільована з виконуваним стеком (наприклад, через прапорець `gcc -z execstack` або застарілі вкладені функції C). Це критичний маркер небезпеки.
2. **Сегмент `PT_GNU_RELRO` (Захист таблиці релокацій):**
   Описує область даних, яка стає доступною лише для читання після завершення динамічного лінкування. Якщо бінарник зібрано з повним захистом (**Full RELRO**), глобальна таблиця зміщень `GOT` повністю закривається від запису, що унеможливлює атаки типу *GOT Overwrite*.

#### Механізм PLT та GOT: ледаче зв'язування проти Full RELRO

Для розуміння того, як бінарник викликає функції спільних бібліотек, необхідно простежити взаємодію процедурної таблиці зв'язування (PLT, *Procedure Linkage Table*) та глобальної таблиці зміщень (GOT, *Global Offset Table*):

1. **Перший виклик функції:** Коли код програми викликає зовнішню функцію (наприклад, `connect()`), інструкція асемблера виконує перехід `call connect@plt`.
2. **Перехід до PLT:** Секція `.plt` містить короткий трамплін, який виконує непрямий перехід `jmp [GOT_entry]`.
3. **Ледаче розв'язання (*Lazy Binding*):** Під час запуску програми запис `GOT_entry` вказує не на реальну функцію `connect()` у `libc.so`, а назад на наступну інструкцію в PLT-трампліні. Трамплін пушить на стек ідентифікатор релокації та викликає процедуру завантажувача `_dl_runtime_resolve()`.
4. **Оновлення адреси:** Динамічний лінкер знаходить адресу функції `connect()` у завантаженій бібліотеці `libc.so.6` і записує її в `GOT_entry`. Усі наступні виклики `connect@plt` переходитимуть безпосередньо в код бібліотеки в обхід завантажувача.

У режимі **Partial RELRO** секція `.got.plt` лишається доступною для запису протягом усього життя процесу. Це дозволяє зловмиснику при наявності вразливості запису в довільну пам'ять перезаписати адресу в GOT адресою шкідливої функції.

У режимі **Full RELRO** (прапорці збірки `-Wl,-z,relro -Wl,-z,now`):
* Динамічний завантажувач розв'язує адреси абсолютно всіх функцій **ще до передачі керування на `main()`**.
* Після розв'язання завантажувач викликає системний виклик `mprotect()` і переводить усю секцію GOT у режим лише для читання (`PROT_READ`). Будь-яка спроба перезапису GOT негайно завершує процес аварійним сигналом `SIGSEGV`.

#### Таблиця секцій (`Section Headers`): де що лежить

Команда `readelf -S` розкриває внутрішню структуру компонування:

```bash
$ readelf -S -W sensor-agent
  [Nr] Name              Type            Address          Off    Size   ES Flg Lk Inf Al
  [14] .text             PROGBITS        0000000000001080 001080 000382 00  AX  0   0 16
  [16] .rodata           PROGBITS        0000000000002000 002000 000124 00   A  0   0  8
  [24] .data             PROGBITS        0000000000004000 003000 000020 00  WA  0   0  8
  [25] .bss              NOBITS          0000000000004020 003020 000040 00  WA  0   0  8
  [26] .comment          PROGBITS        0000000000000000 003020 00002c 01  MS  0   0  1
```

* **`.text`:** скомпільований машинний код функцій програми.
* **`.rodata`:** дані лише для читання (*Read-Only Data*). Саме сюди компілятор складає всі рядкові літерали, конфігураційні шаблони та повідомлення логів.
* **`.data`:** глобальні та статичні змінні з початковими ненульовими значеннями.
* **`.bss`:** неініціалізовані глобальні змінні (тип `NOBITS` — нуль байтів у файлі).
* **`.comment`:** секція метаданих компілятора. Її дамп через `readelf -p .comment sensor-agent` дозволяє миттєво дізнатися версію компілятора, яким було зібрано файл (наприклад, `GCC: (Ubuntu 13.2.0-23ubuntu4) 13.2.0` або `Clang 17.0.6`).

#### Таблиці символів: `.symtab` проти `.dynsym`

Головна відмінність, яку повинен розуміти аналітик:
* **Секція `.symtab` (Static Symbol Table):** містить імена абсолютно всіх функцій і змінних, створених програмістом. Вона потрібна лише відлагоджувачу `gdb` та статичному лінкеру. Команда `strip --strip-all` повністю вирізає цю секцію з бінарника для зменшення його розміру.
* **Секція `.dynsym` (Dynamic Symbol Table):** містить символи, необхідні динамічному завантажувачу під час роботи програми (імпортовані системні виклики та експортовані API). **Секцію `.dynsym` неможливо видалити утилітою `strip`**, оскільки без неї завантажувач `ld-linux` не зможе знайти адреси функцій у бібліотеках `libc.so` чи `libssl.so`.

#### Читання динамічного імпорту: реконструкція системного API

Команда `readelf -s --dyn-syms` розкриває всі зовнішні функції, які бінарник викликає з системних бібліотек:

```bash
$ readelf -s --dyn-syms -W sensor-agent

Symbol table '.dynsym' contains 18 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND 
     1: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND socket@GLIBC_2.2.5
     2: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND connect@GLIBC_2.2.5
     3: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND sendto@GLIBC_2.2.5
     4: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND EVP_EncryptInit_ex@OPENSSL_3.0.0
     5: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND ptrace@GLIBC_2.2.5
     6: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND unlink@GLIBC_2.2.5
```

Аналіз значень у стовпчику `Ndx`:
* **`UND` (*Undefined*):** символ не реалізований у цьому файлі, а імпортується з зовнішньої бібліотеки.
* **Числовий індекс (наприклад, `14`):** символ визначено всередині бінарника у секції під цим номером (наприклад, у секції `.text`).

Навіть якщо бінарник повністю `stripped`, динамічна таблиця символів чітко розкриває його поведінковий профіль:
* Виклики `socket`, `connect`, `sendto` свідчать про мережеву активність.
* Виклик `EVP_EncryptInit_ex` вказує на шифрування трафіку або файлів алгоритмами OpenSSL.
* Виклик `ptrace` свідчить про спробу анти-відлагодження (*anti-debugging*) або ін'єкції коду в сусідні процеси.
* Виклик `unlink` свідчить про видалення файлів з диска.

Аналогічний компактний список імпортованих функцій можна отримати через утиліту `nm` із прапорцями `-D` (*dynamic*) та `-u` (*undefined*):

```bash
$ nm -D -u sensor-agent
                 U connect@GLIBC_2.2.5
                 U EVP_EncryptInit_ex@OPENSSL_3.0.0
                 U ptrace@GLIBC_2.2.5
                 U sendto@GLIBC_2.2.5
                 U socket@GLIBC_2.2.5
                 U unlink@GLIBC_2.2.5
```

#### Аудит версіонування символів GNU (`.gnu.version_r`)

У системній бібліотеці `glibc` функції мають версійні теги (наприклад, `statx@@GLIBC_2.28` або `memcpy@@GLIBC_2.14`). Команда `readelf -V` дозволяє виявити максимальну необхідну версію `glibc`:

```bash
$ readelf -V sensor-agent | grep -E 'File:|Name:'
  File: libc.so.6
    0x0020: Name: GLIBC_2.34
    0x0030: Name: GLIBC_2.14
    0x0040: Name: GLIBC_2.2.5
```

Якщо на цільовому сервері встановлено версію `glibc 2.31`, бінарник із вимогою `GLIBC_2.34` аварійно завершиться ще на етапі завантаження. Це дозволяє заздалегідь виявити несумісність без спроби тестового запуску.

#### Швидкий асемблерний аудит точки входу через `objdump`

Щоб знайти справжню функцію `main()` у вичищеному (*stripped*) бінарнику, аналітики переглядають код за адресою точки входу `_start`:

```bash
$ objdump -d -M intel --start-address=0x1080 --stop-address=0x10b0 sensor-agent
```

```
0000000000001080 <_start>:
    1080:       f3 0f 1e fa             endbr64 
    1084:       31 ed                   xor    ebp,ebp
    1086:       49 89 d1                mov    r9,rdx
    1089:       5e                      pop    rsi
    108a:       48 89 e2                mov    rdx,rsp
    108d:       48 83 e4 f0             and    rsp,0xfffffffffffffff0
    1091:       50                      push   rax
    1092:       54                      push   rsp
    1093:       4c 8d 05 56 0e 00 00    lea    r8,[rip+0xe56]
    109a:       48 8d 0d df 0d 00 00    lea    rcx,[rip+0xddf]
    10a1:       48 8d 3d 48 01 00 00    lea    rdi,[rip+0x148]        # <main = 0x11f0>
    10a8:       ff 15 32 2f 00 00       call   QWORD PTR [rip+0x2f32] # __libc_start_main
    10ae:       f4                      hlt    
```

Згідно зі стандартною угодою викликів System V AMD64 ABI, функція `_start` C-рантайму (`crt1.o`) передає покажчик на справжню функцію `main` у першому аргументі — через регістр `rdi`. Інструкція `lea rdi, [rip + 0x148]` вказує, що реальна функція `main()` розташована за адресою `0x10a1 + 7 + 0x148 = 0x11f0`. Тепер інженер може дизасемблювати саме цю адресу для розуміння бізнес-логіки.

### 5. Пошук прихованого тексту, адрес і констант через `strings`

Значна частина логіки програми фіксується у вигляді відкритих текстових констант. Компілятори мов C, C++, Go та Rust не шифрують рядкові літерали: вони розміщують їх у секції `.rodata` у вигляді звичайних байтів ASCII або UTF-8, відокремлених нульовими термінаторами `\0`.

Утиліта `strings` послідовно сканує файл і витягує всі послідовності друкованих символів.

#### Правильна параметризація `strings`

За замовчуванням `strings` шукає послідовності довжиною від 4 символів і в деяких версіях Unix сканує лише секції ініціалізованих даних. Для повноцінного аудиту невідомого файлу необхідно застосовувати спеціальні прапорці:

```bash
$ strings -a -n 8 -t x sensor-agent
```

* **`-a` (`--all`):** сканувати весь бінарний файл від нульового до останнього байту, включаючи сегменти коду та заголовочні таблиці.
* **`-n 8` (`--bytes=8`):** збільшити мінімальну довжину рядка до 8 символів. Це відсікає випадковий шум (випадкові збіги 4 байтів машинних інструкцій процесора з діапазоном ASCII) та залишає лише осмислені людські фрази.
* **`-t x` (`--radix=x`):** друкувати точне шістнадцяткове зміщення кожного знайденого рядка від початку файлу. Це дозволяє точно локалізувати, в якій саме секції розташована константа.

#### Пошук артефактів за шаблонами

Комбінація `strings` із регулярними виразами `grep` дозволяє швидко отримати ключові конфігураційні параметри чужого бінарника:

```bash
# 1. Пошук мережевих адрес керуючих серверів (C2 / API endpoints):
$ strings -a -n 8 sensor-agent | grep -Ei 'https?://|tcp://|wss?://|[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}:[0-9]+'
https://telemetry.internal-cloud.net/v2/metrics
https://backup-sink.storage.io/auth
192.168.10.45:8443

# 2. Пошук шляхів файлової системи Linux:
$ strings -a -n 6 sensor-agent | grep -E '^/(etc|var|tmp|proc|sys|dev|usr)/'
/etc/sensor-agent/config.yaml
/var/log/sensor-agent.log
/tmp/.agent-lock
/proc/sys/kernel/random/uuid

# 3. Пошук ключів командного рядка та змінних оточення:
$ strings -a -n 4 sensor-agent | grep -E '^\-\-[a-zA-Z0-9_-]+|^[A-Z0-9_]{4,}='
--config
--daemon
--verbose
--dry-run
AUTH_TOKEN=
LOG_LEVEL=

# 4. Пошук шляхів до вихідного коду розробника (Artifacts of build environment):
$ strings -a -n 8 sensor-agent | grep -Ei '\.(c|cpp|cc|go|rs|h):[0-9]+'
/home/builder/work/sensor-agent/src/network/client.cpp:142
/home/builder/work/sensor-agent/src/crypto/aes_engine.c:58
```

Останній приклад особливо показовий: макроси логування (такі як `__FILE__` та `__LINE__` у C/C++ або механізми паніки в Go/Rust) зберігають повні абсолютні шляхи до файлів вихідного коду машини збірки всередині рядків секції `.rodata`. Це дозволяє відновити структуру модулів програми та імена оригінальних сирцевих файлів навіть у повністю вичищеному (`stripped`) бінарнику.

#### Сканування 16-бітних кодувань UTF-16

Якщо програму написано кросплатформним фреймворком або портовано з Windows, рядки можуть зберігатися у двобайтовому кодуванні UTF-16LE. Утиліта `strings` за замовчуванням їх проігнорує (оскільки кожен другий байт буде нульовим `0x00`). Для їх виявлення використовується прапорець `-e l` (*16-bit little-endian*):

```bash
$ strings -a -n 8 -e l sensor-agent
CommandExecutionEngineInitialized
DatabaseConnectionTimeout
```

#### Виявлення упакованих бінарників (UPX та кастомні протектори)

Якщо у виводі `strings` виявляється вкрай мало друкованих символів (менше кількох десятків рядків для великого файлу), або якщо у виводі з'являються маркери `UPX0`, `UPX1`, `UPX!`, це свідчить про те, що бінарник стиснуто виконуваним пакувальником (*packer*).

Пакувальник шифрує або стискає оригінальний код і секції даних, залишаючи на початку файлу лише невеликий розпаковувач (*stub*). Перевірка структури секцій через `readelf -S` підтверджує пакування: секції з кодом мають нульовий розмір на диску (`FileSiz = 0`), але великий розмір у пам'яті (`MemSiz`), а сегмент `PT_LOAD` має комбіновані права `RWE` для самомодифікації пам'яті під час розпакування. Розпакувати такий бінарник можна утилітою `upx -d sensor-agent`, після чого повторити повний цикл статичного тріажу.
