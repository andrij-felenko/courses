Під час нічного перемикання репліки головної бази даних автоматизований скрипт розгортання раптово падає з помилкою `ssh: connect to host db-master-02.internal port 22: Connection timed out`. Одночасно моніторинг сигналізує про втрату зв'язку з вузлом, а черговий інженер, намагаючись підключитися вручну через термінал, стикається з повідомленням `Permission denied (publickey)`. Не маючи системного алгоритму дій, оператор починає хаотично редагувати локальний файл `/etc/hosts`, скидати правила фаєрволу `iptables -F` на шлюзі, змінювати конфігурацію `sshd_config` та перезавантажувати мережеві демони. У результаті простий збій одного запису DNS перетворюється на каскадне відключення всього сегмента інфраструктури, деактивацію захисних екранів та повну втрату доступу до серверів керування.

Така аварія є класичним наслідком відсутності структурної моделі пошуку несправностей. Спроба вгадати причину недосяжності навмання приречена на поразку, оскільки мережевий зв'язок у середовищі Unix/Linux є суворо ієрархічним конвеєром. Кожен успішний мережевий виклик — це ланцюг із чотирьох незалежних ланок: **Ім'я (DNS/NSS) → Маршрут (Kernel FIB / ARP) → Порт (L4 TCP / Firewall) → Ключ (SSH / Crypto Auth)**. Порушення в будь-якій одній точці робить хост недосяжним, але проявляється принципово різними симптомами та системними кодами помилок ядра.

## 1. Чотириланковий діагностичний ланцюг (4-Step Triage Chain)

Коли клієнтський процес виконує команду `ssh user@host.domain` або відкриває TCP-сокет до віддаленої служби, операційна система виконує сувору послідовність кроків:

1. **Ланка 1: Розв'язання імені (Name Resolution):** Перетворення текстового доменного імені `host.domain` у бінарну IP-адресу (IPv4 або IPv6) через конфігурацію NSS (`/etc/nsswitch.conf`), локальні статичні файли або DNS-сервери.
2. **Ланка 2: Маршрутизація ядра та канальна зв'язність (Routing & L2):** Пошук вихідного мережевого інтерфейсу та шлюзу в таблиці Forwarding Information Base ядра (`ip route get`), а також перевірка наявності апаратного MAC-асоціювання в ARP/NDP-кеші (`ip neigh`).
3. **Ланка 3: Транспортна доступність порту та фаєрволи (Port & L4):** Тристороннє рукостискання TCP SYN/ACK, перевірка стану слухаючого сокета на боці сервера та проходження крізь пакетофільтри (локальні `nftables` або хмарні Security Groups).
4. **Ланка 4: Протокольна автентифікація (Auth & Key Exchange):** Узгодження криптографічних параметрів SSH, перевірка відбитка сервера в `known_hosts`, валідація прав доступу файлової системи (`StrictModes`) та пред'явлення публічного ключа користувача.

![Чотириланковий ланцюг мережевої діагностики](/root/course/unix/cannot-reach-the-host/img/four-step-triage-chain.svg)
*Чотириланковий діагностичний ланцюг: послідовна локалізація недосяжності від розпізнавання імені до перевірки криптографічного ключа.*

Золоте правило системної діагностики: **перевірка завжди виконується строго зліва направо**. Не має жодного сенсу перевіряти SSH-ключі чи налаштування фаєрволу, якщо ім'я не транслюється в IP-адресу; безглуздо звинувачувати демон `sshd`, якщо на транспортному рівні ядро не знає вихідного маршруту або сусідній шлюз не відповідає на ARP-запити.

## 2. Ланка 1: Розв'язання імені (Name Resolution)

Перший бар'єр між програмою та мережею — трансляція текстового доменного імені в бінарну адресу. Якщо розпізнавання зазнає невдачі, застосунок негайно отримує системну помилку `Name or service not known` або код `EAI_NONAME`.

### 2.1. Конвеєр NSS та `/etc/nsswitch.conf`

Більшість стандартних утиліт Linux (включно з `ssh`, `curl`, `nc`) не виконують прямих UDP-запитів до DNS-серверів. Вони викликають бібліотечну функцію glibc `getaddrinfo()`. 

Механізм [шлях розв'язання імені: NSS, resolv.conf, systemd-resolved](root:sys-unix/name-resolution-path) визначає поведінку резолвера через файл конфігурації `/etc/nsswitch.conf`. Знайдемо рядок, що відповідає за базу `hosts`:

```sh
$ grep '^hosts:' /etc/nsswitch.conf
hosts:          files mdns4_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] dns myhostname
```

Порядок плагінів у цьому рядку визначає точну послідовність опитування джерел:
1. `files` — читання локального статичного файлу `/etc/hosts` через бібліотеку `libnss_files.so`. Якщо в ньому знайдено запис, пошук негайно припиняється.
2. `mdns4_minimal [NOTFOUND=return]` — резолвер локальних імен Multicast DNS (доменна зона `.local`). Керуюча конструкція `[NOTFOUND=return]` означає: якщо ім'я закінчується на `.local` і не знайдено, негайно повернути помилку, не опитуючи наступні джерела.
3. `resolve` — звернення до локального сервісу `systemd-resolved` через D-Bus IPC або сокет `/run/systemd/resolve/io.systemd.Resolve`. Прапорець `[!UNAVAIL=return]` гарантує: якщо демон `systemd-resolved` працює, відповідь береться виключно від нього без переходу до класичного плагіна `dns`.
4. `dns` — пряме відправлення UDP/TCP запитів до серверів імен, зазначених у файлі `/etc/resolv.conf`, через модуль `libnss_dns.so`.
5. `myhostname` — автоматичне локальне розпізнавання власного імені хоста системи без звернення до зовнішніх мереж.

Якщо в файлі `/etc/hosts` залишився застарілий статичний запис `192.168.1.50 db-master-02.internal`, система намагатиметься підключитися за старою адресою, навіть якщо авторитативний DNS-сервер давно видає оновлену адресу `10.0.4.12`.

### 2.2. Заглушка `systemd-resolved` (127.0.0.53) та Split-DNS

У сучасних дистрибутивах Linux (Ubuntu, Debian, Fedora, RHEL 9) файл `/etc/resolv.conf` є символічним посиланням на `/run/systemd/resolve/stub-resolv.conf`:

```sh
$ ls -l /etc/resolv.conf
lrwxrwxrwx 1 root root 39 сер 20 10:15 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf

$ cat /etc/resolv.conf
nameserver 127.0.0.53
options edns0 trust-ad
search internal.company.com
```

Адреса `127.0.0.53:53` — це локальний DNS-проксі демона `systemd-resolved`. Він підтримує окремі DNS-конфігурації для кожного мережевого інтерфейсу (Split-DNS). Якщо VPN-тунель або Wi-Fi адаптер піднявся з помилкою, `systemd-resolved` може надсилати внутрішні корпоративні запити у публічний DNS-інтерфейс, отримуючи негативну відповідь `NXDOMAIN`.

Інша прихована пастка криється в директиві `ndots:5`. Якщо конфігурація містить список доменів пошуку `search`, а запитане ім'я містить менше ніж 5 крапок (наприклад, `node-02.internal`), резолвер спершу спробує надіслати запит `node-02.internal.internal.company.com`, отримуючи затримку до 5 секунд перед спробою запитати абсолютне ім'я з крапкою наприкінці.

### 2.3. Внутрішні DNS-проксі в контейнерах (127.0.0.11)

У контейнеризованих середовищах Docker та Kubernetes усередині контейнера файл `/etc/resolv.conf` вказує на адресу `nameserver 127.0.0.11`. Це вбудований DNS-сервер рушія контейнеризації. Якщо контейнер не підключено до спільної користувацької мережі Docker (`bridge network`), вбудований резолвер не може розпізнавати сусідні контейнери за іменами сервісів, повертаючи помилку `SERVFAIL` або `NXDOMAIN`.

### 2.4. Інструменти діагностики першої ланки

Для виявлення точки збою розпізнавання використовують три взаємодоповнюючі утиліти:

```sh
# 1. Перевірка реального шляху glibc NSS (як бачить програма)
getent ahosts db-master-02.internal

# 2. Перевірка стану та кешу демона systemd-resolved
resolvectl query db-master-02.internal
resolvectl status

# 3. Прямий сирий DNS-запит в обхід NSS та systemd-resolved
dig @8.8.8.8 db-master-02.internal +trace
```

Команда `getent ahosts` є еталоном: якщо вона не повертає IP-адресу, жодна стандартна програма в системі не зможе відкрити сокет. Команда `resolvectl status` показує, до якого саме фізичного інтерфейсу прив'язані домени пошуку (`search domains`) та чи активний протокол безпеки DNSSEC.

## 3. Ланка 2: Маршрутизація ядра та канальна зв'язність (L2/L3 Routing)

Отримавши IP-адресу (наприклад, `10.0.4.12`), ядро Linux мусить ухвалити [рішення про маршрут](root:sys-unix/routing-decision): через який саме мережевий інтерфейс відправити пакет і яку адресу вказати як шлюз наступного стрибка (Next-Hop Gateway).

### 3.1. Інтроспекція таблиці FIB: `ip route get`

Для повної симуляції маршрутизації використовують команду `ip route get`. Вона запитує підсистему Forwarding Information Base ядра точно так само, як це робить мережевий стек перед формуванням першого IP-пакета:

```sh
$ ip route get 10.0.4.12
10.0.4.12 via 192.168.1.1 dev eth0 src 192.168.1.105 uid 1000
    cache
```

Аналіз виводу ядра:
* `via 192.168.1.1` — пакет буде направлено на шлюз за замовчуванням `192.168.1.1`.
* `dev eth0` — вихідний фізичний або віртуальний інтерфейс.
* `src 192.168.1.105` — локальна IP-адреса, яку ядро підставить у заголовок як Source IP.

Якщо у системі відсутній маршрут за замовчуванням (`default gateway`), або мережевий інтерфейс перебуває в стані `DOWN`, команда негайно повертає помилку:

```sh
$ ip route get 10.0.4.12
RTNETLINK answers: Network is unreachable
```

Це свідчить про системну помилку `ENETUNREACH` (код 101): пакет не може навіть вийти з локального хоста, оскільки таблиця FIB не містить відповідного префікса підмережі.

### 3.2. Політика маршрутизації (Policy-Based Routing) та метрики

У складних серверах з кількома мережевими інтерфейсами (наприклад, Ethernet та Wi-Fi, або основний канал та резервний LTE) ядро використовує систему правил вибору таблиць маршрутизації:

```sh
$ ip rule show
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
```

Якщо в системі налаштовано дві таблиці з однаковими підмережами або активовано два шлюзи за замовчуванням, вирішальне значення має показник метрики (`metric`). Пакет завжди спрямовується через маршрут з найменшим числовим значенням метрики:

```sh
default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.105 metric 100
default via 192.168.2.1 dev wlan0 proto dhcp src 192.168.2.50 metric 600
```

Якщо шлюз `192.168.1.1` втрачає фізичний зв'язок з інтернетом, але інтерфейс `eth0` залишається увімкненим (`carrier UP`), ядро продовжуватиме штовхати пакети в мертвий шлюз через пріоритет метрики 100, ігноруючи працюючий інтерфейс `wlan0`.

### 3.3. Стан L2-сусідів та протокол ARP: `ip neigh`

Якщо цільовий хост або шлюз перебуває в одній локальній підмережі (L2-сегмент), ядро повинно знати фізичну MAC-адресу мережевої карти отримувача за допомогою протоколу [MAC, IP і ARP](root:com-transport/mac-ip-arp).

Перевіримо таблицю сусідів ядра:

```sh
$ ip neigh show to 192.168.1.1
192.168.1.1 dev eth0 lladdr 52:54:00:12:34:56 REACHABLE

$ ip neigh show to 10.0.4.12
10.0.4.12 dev eth0  FAILED
```

Стани записів у таблиці Neighbor (структура `struct neighbour` у ядрі):
* `REACHABLE` — апаратну MAC-адресу підтверджено; кадри Ethernet передаються штатно.
* `STALE` / `DELAY` / `PROBE` — кеш застаріває, ядро відправляє контрольні ARP-запити для перевірки доступності сусіда.
* `FAILED` / `INCOMPLETE` — ядро надіслало серію широкомовних ARP-запитів (`Who has 10.0.4.12? Tell 192.168.1.105`), але жодної ARP-відповіді не отримало.

Стан `FAILED` свідчить про фізичний або логічний розрив на канальному рівні L2: обрив кабелю, вимкнений комутатор, неправильно налаштований тег VLAN або некоректна маска підмережі CIDR.

### 3.4. Пастка Black Hole MTU та Path MTU Discovery

Окремий підступний клас збоїв зв'язку пов'язаний із розміром максимального блоку передачі (MTU). За замовчуванням у мережах Ethernet встановлено `MTU = 1500` байтів. Якщо на шляху між клієнтом і сервером використовується тунелювання (VPN WireGuard, IPsec, GRE, VXLAN), розмір корисного навантаження кадру зменшується через заголовки інкапсуляції (наприклад, до 1420 або 1380 байтів).

Якщо клієнт надсилає пакети з установленим прапорцем `DF` (Don't Fragment), проміжний маршрутизатор повинен відкинути пакет і повернути клієнту службове повідомлення `ICMP Destination Unreachable, Fragmentation Needed and DF set` (Type 3, Code 4). Проте, якщо проміжний фаєрвол блокує всі ICMP-пакети, клієнт ніколи не дізнається про необхідність зменшити розмір пакета.

Симптом Black Hole MTU:
Тристороннє рукостискання TCP (маленькі пакети SYN/ACK по 60 байтів) проходить миттєво, але щойно починається передача великого блоку даних (наприклад, обмін ключами SSH або передача сертифіката TLS розміром 2 КіБ), сесія наглухо зависає.

Діагностика MTU через команду `ping`:

```sh
# Пошук максимального розміру пакета без фрагментації (1472 + 28 байтів заголовків = 1500)
ping -M do -s 1472 10.0.4.12

# Якщо не проходить, зменшуємо розмір буфера до з'ясування реального MTU шляху
ping -M do -s 1392 10.0.4.12
```

### 3.5. Діагностика втрат на транзитних вузлах: `mtr` та `traceroute -T`

Класична утиліта `ping` використовує протокол ICMP Echo Request. На практиці `ping` часто дає хибні висновки:
1. Багато хмарних провайдерів (AWS, Cloudflare) та корпоративних маршрутизаторів повністю блокують ICMP або застосовують жорсткий полісинг (Control Plane Policing, CoPP), скидаючи ICMP-пакети при нормальному проходженні TCP.
2. `ping` може працювати ідеально, тоді як цільовий TCP-порт заблокований фаєрволом.

Для об'єктивного аналізу транзитного шляху використовують утиліту `mtr` (My Traceroute) та режим TCP-трасування:

```sh
# Збір статистики втрат на кожному проміжному маршрутизаторі (30 пакетів)
mtr -n -c 30 --report 10.0.4.12

# Трасування за допомогою реальних пакетів TCP SYN на порт 22
traceroute -n -T -p 22 10.0.4.12
```

Якщо `traceroute -T` успішно доходить до передостаннього стрибка (шлюзу дата-центру) і зупиняється на вході до сервера, проблема криється у налаштуваннях фаєрволу цільового хоста.

## 4. Ланка 3: Транспортна доступність TCP та фаєрволи (Port & L4)

Коли IP-пакет успішно досягає цільового сервера, в дію вступає транспортний рівень [TCP: життя з'єднання](root:com-transport/tcp-connection-lifecycle). Клієнт надсилає пакет `TCP SYN` і переходить у стан `SYN_SENT`, очікуючи на відповідь `SYN-ACK`.

На цьому етапі можливі два принципово різні діагностичні результати відмови: **Connection refused** та **Connection timed out**. Їхнє розрізнення є ключовим для локалізації несправності.

![Анатомія відмови TCP: активний RST проти мовчазного DROP](/root/course/unix/cannot-reach-the-host/img/tcp-rst-vs-drop.svg)
*Анатомія відмови TCP: отримання активного RST (Connection refused) проти мовчазного скидання DROP (Connection timed out).*

### 4.1. Сценарій А: `Connection refused` (Активне скидання TCP RST)

Якщо клієнт миттєво отримує помилку `Connection refused` (системна помилка `ECONNREFUSED`, код 111), це означає, що **пакет успішно дійшов до хоста, і ядро хоста повернуло у відповідь пакет з прапорцем `TCP RST` (Reset)**.

Фізичні причини отримання `TCP RST`:
1. **Процес не слухає порт:** Демон `sshd` або веб-сервер аварійно завершився і не відкрив сокет.
2. **Неправильна прив'язка інтерфейсу (Bind Address):** Демон слухає сокет на локальній петлі `127.0.0.1:22` замість `0.0.0.0:22` або `:::22`. Коли клієнт звертається до зовнішнього IP `10.0.4.12:22`, ядро перевіряє таблицю `inet_lookup_listener`, не знаходить відповідного сокета і формує `RST`.
3. **Явне правило відхилення у фаєрволі:** Фаєрвол [nftables](root:sys-unix/netfilter-nftables-expression-engine) або `iptables` містить правило з дією `reject with tcp reset`:

```sh
# Правило nftables, що повертає активний RST
nft add rule inet filter input tcp dport 22 reject with tcp reset
```

Також відхилення може повертатися у вигляді ICMP-пакета `Destination Port Unreachable` (ICMP Type 3, Code 3). Клієнтське ядро транслює цей ICMP-пакет у той самий системний код помилки `ECONNREFUSED`.

### 4.2. Сценарій Б: `Connection timed out` (Мовчазне поглинання DROP)

Якщо клієнт висить у паузі 60–120 секунд і завершується помилкою `Connection timed out` (`ETIMEDOUT`, код 110), це свідчить про те, що **пакет SYN було безслідно поглинуто, і жодної відповіді не надійшло**.

Клієнтське ядро надсилає початковий `SYN`, після чого виконує серію повторних відправок з експоненційним зростанням інтервалів (1с, 2с, 4с, 8с, 16с, 32с), кількість яких визначається параметром ядра `/proc/sys/net/ipv4/tcp_syn_retries`. Після вичерпання ліміту сокет закривається за таймаутом.

Фізичні причини `ETIMEDOUT`:
1. **Правило DROP у пакетофільтрі:** Локальний `nftables`, `ufw` або `iptables` скидає вхідні пакети дією `drop`.
2. **Хмарні екрани безпеки:** AWS Security Group, GCP Firewall Rules або Azure NSG не містять правила `Allow Inbound TCP 22` для IP-адреси клієнта.
3. **Асиметрична маршрутизація та rp_filter:** Пакет дійшов до сервера через один інтерфейс, але зворотний маршрут пішов через інший шлюз, і проміжний маршрутизатор скинув його як невалідний стан сесії (Stateful Tracking).
4. **Переповнення таблиці Conntrack:** Якщо підсистема відстеження з'єднань фаєрволу переповнена, у журналі ядра `dmesg` з'являється повідомлення `nf_conntrack: table full, dropping packet`.
5. **Переповнення черги напіввідкритих з'єднань (SYN Backlog):** Якщо сервер зазнає SYN-флуду або бекенд не встигає викликати `accept()`, вхідні пакети SYN скидаються ядром через брак місця в черзі `tcp_max_syn_backlog`.

### 4.3. Інструменти діагностики транспортного рівня

Для швидкої перевірки порту з боку клієнта використовують утиліти `nc` (Netcat) та `curl`:

```sh
# 1. Швидке сканування TCP-порту з жорстким таймаутом 3 секунди
nc -z -v -w 3 10.0.4.12 22

# 2. Зондування порту через curl у режимі Telnet
curl -v --connect-timeout 3 telnet://10.0.4.12:22
```

Якщо є доступ до консолі сервера (через IPMI/KVM або хост-ноду), перевіряють стан сокетів та лічильники фаєрволу за допомогою утиліт [подивитися на мережу: ss, tcpdump, traceroute](root:sys-unix/network-inspection-tools):

```sh
# Перевірка, чи запущено демон і який саме IP він слухає
ss -tlpn 'sport = :22'

# Перевірка правил та лічильників блокування nftables
nft list ruleset | grep -A 5 -B 2 'dport 22'
```

Повний довідник кодів помилок `errno`, прапорців утиліт та параметрів ядра наведено у вставці [матриця інструментів та кодів помилок мережевої діагностики](root:unix/cannot-reach-the-host/api-reachability-diagnostics.md).

## 5. Ланка 4: Протокольна автентифікація SSH (SSH & Auth)

Коли тристороннє рукостискання TCP успішно завершено (порт відкритий, пакети проходять), клієнт переходить до четвертої ланки — встановлення сесії [віддалений сеанс: SSH](root:sys-unix/ssh-remote-session).

Головний інструмент локалізації збоїв на цьому рівні — запуск клієнта з максимальним рівнем трасування:

```sh
ssh -vvv user@10.0.4.12
```

Розглянемо чотири найпоширеніші сценарії аварійних відмов при автентифікації SSH.

![Матриця перевірок автентифікації OpenSSH](/root/course/unix/cannot-reach-the-host/img/ssh-auth-failure-matrix.svg)
*Матриця перевірок безпеки OpenSSH: валідація прав доступу, StrictModes та цикл перебору ключів.*

### 5.1. Зміна відбитка хоста: конфлікт `known_hosts`

Якщо сервер було перевстановлено, йому перевиділено динамічну IP-адресу або трафік перехоплюється зловмисником, клієнт отримує попередження про порушення довіри за моделлю [ключі, known_hosts і довіра до хоста](root:sys-unix/ssh-keys-and-host-trust):

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Host key verification failed.
```

Клієнт SSH негайно розриває з'єднання для запобігання атаці Man-in-the-Middle (MITM). Якщо зміна ключа легітимна (наприклад, після оновлення версії ОС на сервері), старий відбиток видаляють з бази довіри:

```sh
# Очищення старого запису хоста з файлу known_hosts
ssh-keygen -R 10.0.4.12
ssh-keygen -R db-master-02.internal
```

### 5.2. Порушення прав доступу: параноя `StrictModes`

Типова ситуація: публічний ключ `id_ed25519.pub` коректно додано у файл `~/.ssh/authorized_keys` на сервері, але клієнт все одно отримує відмову `Permission denied (publickey)`.

За замовчуванням конфігурація [sshd: конфігурація й загартування](root:sys-unix/sshd-configuration-and-hardening) містить директиву `StrictModes yes`. Перед читанням ключів демон `sshd` виконує строгу перевірку прав володіння та бітів доступу всієї ієрархії каталогів. Якщо будь-який каталог у шляху доступний на запис іншим користувачам або групі, `sshd` відмовляється читати файл authorized_keys, захищаючись від підміни файлу непривілейованим процесом.

Обов'язкові стандарти прав файлової системи на сервері:

| Об'єкт файлової системи | Власник (Owner) | Обов'язкові числові права (Octal) | Символьний запис |
|---|---|---|---|
| Домашній каталог `/home/user` | `user:user` | `0755` або `0750` (Заборонено `0777` чи `0775`) | `drwxr-xr-x` |
| Каталог ключів `/home/user/.ssh` | `user:user` | `0700` (Доступ виключно власнику) | `drwx------` |
| Файл авторизації `~/.ssh/authorized_keys` | `user:user` | `0600` (Читання/запис тільки власнику) | `-rw-------` |
| Приватні ключі `~/.ssh/id_*` | `user:user` | `0600` | `-rw-------` |

Команда відновлення коректних прав на сервері:

```sh
chmod 0750 /home/user
chmod 0700 /home/user/.ssh
chmod 0600 /home/user/.ssh/authorized_keys
chown -R user:user /home/user/.ssh
```

Окремий крайовий випадок — збереження домашніх каталогів на мережевій файловій системі NFS із прапорцем `root_squash`. Коли демон `sshd` працює від імені суперкористувача `root`, операція читання `authorized_keys` на NFS-сервері виконується від імені анонімного користувача `nobody`. Якщо файл мав права `0600`, користувач `nobody` не має до нього доступу, і вхід завершується відмовою. Для таких систем права на `authorized_keys` тимчасово підвищують до `0644`.

Крім того, у системах із SELinux (RHEL, Rocky, Fedora) після ручного копіювання файлу `authorized_keys` з іншого каталогу файл може отримати некоректний контекст безпеки (наприклад, `user_tmp_t` замість `ssh_home_t`). Відновлення контексту:

```sh
restorecon -R -v /home/user/.ssh
```

### 5.3. Переповнення агента автентифікації: пастка `MaxAuthTries`

Якщо інженер використовує утиліту `ssh-agent`, у пам'яті якої завантажено багато приватних ключів (наприклад, 8 різних ключів для GitHub, GitLab, тестових та робочих серверів), виникає прихована помилка:

```
debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: publickey
debug1: Offering public key: /home/user/.ssh/id_rsa_personal RSA ...
debug1: Authentications that can continue: publickey,password
debug1: Offering public key: /home/user/.ssh/id_ed25519_work ED25519 ...
...
Received disconnect from 10.0.4.12 port 22:2: Too many authentication failures
Disconnected from 10.0.4.12 port 22
```

Механізм збою:
Клієнт SSH автоматично по черзі пропонує серверу **всі** ключі з `ssh-agent`. Серверний демон `sshd` має обмеження `MaxAuthTries` (за замовчуванням 6). Після 6 невдалих спроб сервер розриває TCP-з'єднання, навіть якщо 7-й ключ у списку агента був правильним.

Виправлення: примусити клієнт використовувати виключно вказаний ключ, ігноруючи решту ключів агента:

```sh
# Одноразовий виклик з прапорцем IdentitiesOnly
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_target_server user@10.0.4.12
```

Або налаштування блоку хоста у файлі `~/.ssh/config`:

```sshconfig
Host db-master-02
    HostName 10.0.4.12
    User deploy
    IdentityFile ~/.ssh/id_target_server
    IdentitiesOnly yes
    ConnectTimeout 5
```

### 5.4. Застарілі алгоритми підпису: відмова `ssh-rsa`

Починаючи з версії OpenSSH 8.8, криптографічний алгоритм підпису `ssh-rsa` (на базі хешу SHA-1) вимкнено за замовчуванням через його криптографічну вразливість перед колізіями.

Симптом у журналі `ssh -vvv`:

```
debug1: send_pubkey_test: no mutual signature algorithm
debug1: Authentications that can continue: password
```

Хоча старий ключ RSA формально присутній, клієнт і сервер не можуть узгодити алгоритм цифрового підпису. Єдиним надійним рішенням є генерація сучасного ключа на базі еліптичних кривих Ed25519:

```sh
ssh-keygen -t ed25519 -a 100 -C "deploy@cluster"
```

## 6. Зведена матриця діагностики: симптом, локалізація, дія

Для систематизації всього діагностичного алгоритму зведемо типові симптоми, системні команди та точні методи виправлення в єдину таблицю.

| Спостережуваний симптом / помилка | Ланка ланцюга | Точна внутрішня причина | Команда експрес-перевірки | Дія з усунення несправності |
|---|---|---|---|---|
| `Could not resolve hostname` (`EAI_NONAME`) | **Ланка 1 (Ім'я)** | Запис відсутній у DNS або помилка в `/etc/hosts` чи `nsswitch.conf`. | `getent ahosts <name>` | Додати запис у DNS, виправити `/etc/hosts` або налаштувати `systemd-resolved`. |
| `Network is unreachable` (`ENETUNREACH`) | **Ланка 2 (Маршрут)** | У ядрі відсутній шлюз за замовчуванням (Default Gateway) або інтерфейс `DOWN`. | `ip route get <IP>` | Підняти інтерфейс `ip link set up`, додати шлюз `ip route add default via <IP>`. |
| `No route to host` / `ARP FAILED` | **Ланка 2 (Маршрут)** | Шлюз або хост у локальній підмережі не відповідає на ARP-запити. | `ip neigh show to <IP>` | Перевірити фізичний лінк, правильність VLAN, маски підмережі CIDR та комутатор. |
| `Connection refused` (TCP RST) | **Ланка 3 (Порт)** | Служба не запущена, слухає лише `127.0.0.1`, або правило фаєрволу `REJECT`. | `ss -tlpn 'sport = :port'` | Запустити службу `systemctl start sshd`, виправити bind-адресу на `0.0.0.0`, прибрати REJECT. |
| `Connection timed out` (TCP DROP) | **Ланка 3 (Порт)** | Пакети SYN мовчазно скидаються `nftables`, AWS Security Group або провайдером. | `nc -z -v -w 3 <IP> <port>` | Додати правило `allow` у фаєрвол, відкрити Security Group, перевірити `rp_filter`. |
| `Host key verification failed` | **Ланка 4 (Ключ)** | Змінився відбиток публічного ключа сервера у файлі `~/.ssh/known_hosts`. | `ssh-keygen -l -f ~/.ssh/known_hosts` | Видалити застарілий запис через `ssh-keygen -R <host>` після перевірки легітимності. |
| `Permission denied (publickey)` | **Ланка 4 (Ключ)** | Неправильні права на `~/.ssh` (має бути 0700) або `authorized_keys` (0600). | `ls -la ~/.ssh` (на сервері) | Встановити коректні права: `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`. |
| `Too many authentication failures` | **Ланка 4 (Ключ)** | Клієнт вичерпав ліміт `MaxAuthTries`, перебираючи всі сторонні ключі з `ssh-agent`. | `ssh-add -l` | Використовувати `ssh -o IdentitiesOnly=yes -i ~/.ssh/key` або налаштувати `~/.ssh/config`. |

Для автоматизації перевірки всього 4-ланкового конвеєра одним запуском створено спеціалізовану утиліту, реалізацію якої наведено у практичній вставці [автоматизований зонд діагностики 4 ланок на C та C++](root:unix/cannot-reach-the-host/proj-network-triage.md).

## 7. Анатомія розслідування реального інциденту: дедлок перемикання бази даних

Щоб закріпити взаємодію всіх ланок діагностичного ланцюга, простежимо ліквідацію аварії в розподіленому кластері баз даних PostgreSQL.

### Етап 1. Симптом
Клієнтський мікросервіс надсилає алерт `Database connection failed`. Інженер намагається зайти на нову репліку:

```sh
$ ssh deploy@db-node-03.internal
ssh: connect to host db-node-03.internal port 22: Connection timed out
```

### Етап 2. Локалізація за ланцюгом
* **Крок 1 (Ім'я):**
  `getent ahosts db-node-03.internal` повертає `10.0.10.45`. Ланка 1 справна.
* **Крок 2 (Маршрут):**
  `ip route get 10.0.10.45` показує `via 10.0.0.1 dev eth0`. `ip neigh show to 10.0.0.1` повертає `REACHABLE`. Маршрут у ядрі є, шлюз доступний.
* **Крок 3 (Порт):**
  `nc -z -v -w 3 10.0.10.45 22` висить рівно 3 секунди і завершується таймаутом.
  Інженер запускає `traceroute -n -T -p 22 10.0.10.45`: пакети доходять до маршрутизатора підмережі `10.0.0.1` і поглинаються на самому хості `10.0.10.45`.
* **Висновок кроку 3:** Пакети мовчазно скидаються (DROP) на вході до цільового сервера.

### Етап 3. Усунення та відновлення зв'язку
Інженер підключається до хоста через аварійну консоль IPMI/KVM і перевіряє активні правила пакетофільтра:

```sh
$ sudo nft list ruleset | grep -B 2 -A 5 'dport 22'
chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    ip saddr 10.0.0.0/24 tcp dport 22 accept
}
```

Виявлено першопричину: правило фаєрволу дозволяло вхідний SSH лише з підмережі `10.0.0.0/24`, тоді як новий сервер автоматизації мав адресу `10.0.20.15/24`. Інженер додає коректне правило у фаєрвол:

```sh
sudo nft add rule inet filter input ip saddr 10.0.20.0/24 tcp dport 22 accept
```

Після цього виклик `nc -z -v -w 3 10.0.10.45 22` негайно повертає `Connection to 10.0.10.45 22 port [tcp/ssh] succeeded!`, а команда `ssh deploy@db-node-03.internal` успішно відкриває сесію.

## 8. Алгоритм розслідування: покроковий протокол

Підсумуємо методологію у вигляді детермінованого 4-крокового протоколу, який інженер виконує при виникненні будь-якого інциденту мережевої недосяжності:

```
[Початок: Хост не відповідає]
       │
       ▼
[Крок 1: getent ahosts <target>]
  ├─ Збій -> Виправити /etc/hosts, resolv.conf, systemd-resolved -> [КІНЕЦЬ]
  └─ Успіх -> Отримано IP-адресу -> Перехід до Кроку 2
       │
       ▼
[Крок 2: ip route get <IP> && ip neigh show to <IP>]
  ├─ Network unreachable -> Налаштувати шлюз за замовчуванням -> [КІНЕЦЬ]
  ├─ ARP FAILED -> Перевірити L2 кабель, VLAN, статус інтерфейсу -> [КІНЕЦЬ]
  └─ Маршрут є, ARP REACHABLE -> Перехід до Кроку 3
       │
       ▼
[Крок 3: nc -z -v -w 3 <IP> <port>]
  ├─ Connection refused -> Перевірити статус служби (systemctl) та bind 0.0.0.0 -> [КІНЕЦЬ]
  ├─ Connection timed out -> Відкрити порт у nftables / Cloud Security Group -> [КІНЕЦЬ]
  └─ Port OPEN -> З'єднання встановлено -> Перехід до Кроку 4
       │
       ▼
[Крок 4: ssh -vvv user@<IP>]
  ├─ Host key mismatch -> ssh-keygen -R <target> -> [КІНЕЦЬ]
  ├─ Too many auth failures -> ssh -o IdentitiesOnly=yes -i <key> -> [КІНЕЦЬ]
  ├─ Permission denied -> Виправити права chmod 700 ~/.ssh та 600 authorized_keys -> [КІНЕЦЬ]
  └─ Вхід успішний -> Зв'язок відновлено.
```

Дотримання цієї послідовності виключає хаотичні дії та дозволяє локалізувати будь-яку проблему мережевої недосяжності менш ніж за 60 секунд.
