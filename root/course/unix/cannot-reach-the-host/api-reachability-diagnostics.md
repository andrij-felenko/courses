# 📋 Матриця мережевої діагностики: утиліти, коди помилок, сокети та tracepoints

Коли віддалений хост перестає відповідати на запити, системний адміністратор або інженер надійності стикається з десятками спеціалізованих інструментів, системних викликів ядра та кодів помилок `errno`. Без структурованого довідника параметрів командного рядка, бітових масок та трасувальних точок ядра процес локалізації несправності перетворюється на хаотичний перебір команд. Тут зведено повний контракт діагностичних утиліт простору користувача, коди помилок POSIX, структури конфігурації ядра Linux у `/proc/sys/net/` та статичні події `tracefs` для глибокого аналізу мережевих збоїв.

---

## 1. Спеціалізовані прапорці діагностичних утиліт

Стандартні мережеві інструменти часто приховують критичні деталі помилок за умовчанням або занадто довго очікують на таймаути. Наприклад, утиліта `ping` може створювати оманливе враження повної працездатності хоста, коли пакети ICMP вільно проходять через шлюзи, але прикладний порт TCP повністю заблокований фільтрами вхідного трафіку. З іншого боку, запуск команди `ssh` без обмеження ідентифікаторів нерідко призводить до раптового розриву зв'язку ще до початку передачі пароля.

У таблиці наведено спеціалізовані прапорці утиліт простору користувача, оптимізовані саме для детермінованого розслідування мережевої недосяжності.

| Утиліта | Рекомендована команда | Призначення прапорців та діагностичний ефект |
|---|---|---|
| `getent` | `getent -s hosts ahosts <name>` | Використовує конфігурацію `/etc/nsswitch.conf`, повертає всі IP-адреси (IPv4/IPv6) та канонічні імена без локального кешування самої утиліти. |
| `resolvectl` | `resolvectl query --cache=no <name>` | Запитує демон `systemd-resolved` в обхід локального кешу DNS, відображає прив'язку до інтерфейсу (`link`) та статус валідації DNSSEC. |
| `resolvectl` | `resolvectl status <interface>` | Відображає активні DNS-сервери, домени пошуку (`search domains`), протоколи DNS-over-TLS та статус mDNS/LLMNR для конкретного інтерфейсу. |
| `dig` | `dig +trace +all <name>` | Виконує повне рекурсивне трасування від кореневих DNS-серверів (`.`) до авторитативних серверів зони, оминаючи локальний резолвер. |
| `ip route` | `ip route get <IP> fibmatch` | Симулює рішення підсистеми FIB ядра для вказаного IP; прапорець `fibmatch` повертає точний рядок таблиці маршрутизації, що спрацював. |
| `ip neigh` | `ip neigh show to <IP>` | Показує стан ARP/NDP-запису в таблиці сусідів ядра (`REACHABLE`, `STALE`, `DELAY`, `PROBE`, `FAILED`, `INCOMPLETE`, `PERMANENT`). |
| `mtr` | `mtr -n -c 30 --report-wide <IP>` | Одночасне трасування маршруту з відправкою 30 пакетів без розв'язання DNS (`-n`) для виявлення втрат на кожному проміжному маршрутизаторі. |
| `traceroute` | `traceroute -n -T -p 22 <IP>` | Трасування маршруту за допомогою пакетів TCP SYN на конкретний порт замість UDP/ICMP; проходить крізь транзитні фаєрволи. |
| `ss` | `ss -tlpne 'sport = :22'` | Відображає слухаючі TCP-сокети з номерами процесів (`-p`), дескрипторами сокетів (`-e`), числовими портами (`-n`) та таймерами. |
| `nc` (netcat) | `nc -z -v -w 3 <IP> <port>` | Режим сканування порту (`-z`), детальний вивід (`-v`), жорсткий таймаут підключення 3 секунди (`-w 3`). |
| `curl` | `curl -v --connect-timeout 3 telnet://<IP>:<port>` | Виконує сире TCP-підключення до порту з таймаутом з'єднання та детальним журналом стадій сокета. |
| `ssh` | `ssh -vvv -o IdentitiesOnly=yes -o ConnectTimeout=5 user@host` | Максимальний рівень налагодження (`-vvv`), використання лише явно вказаного ключа (`IdentitiesOnly`), обмеження таймауту TCP. |
| `nft` | `nft list ruleset -a` | Відображає всі таблиці, ланцюжки та правила фільтрації `nftables` з їхніми унікальними числовими дескрипторами (`handle`) для трасування лічильників. |

Використання прапорця `-s hosts ahosts` в утиліті `getent` є принциповим: на відміну від команди `host` чи `nslookup`, які відправляють сирі мережеві UDP-пакети безпосередньо на адреси з `/etc/resolv.conf`, `getent` завантажує динамічні бібліотеки NSS (`libnss_files.so`, `libnss_resolve.so`). Це дозволяє побачити доменне ім'я точно так, як його бачать клієнтські процеси `ssh` та `curl`.

## 2. Коди помилок системних викликів (POSIX errno)

Коли прикладний процес викликає системні функції `getaddrinfo()`, `socket()`, `connect()`, `send()` або `read()`, ядро операційної системи сигналізує про характер мережевої відмови через цілочисельний код помилки `errno` (або спеціальні константи `EAI_*` для розпізнавання імен).

Розуміння точного змісту кожного коду дає змогу миттєво визначити рівень мережевого стека, на якому сталася аварія.

### 2.1. Помилки розпізнавання імені (`getaddrinfo` / EAI)

Бібліотечна функція `getaddrinfo()` повертає нуль у разі успішного завершення або ненульовий числовий код відмови. Для перетворення цього коду в людиночитаний рядок використовують функцію `gai_strerror()`:

* **`EAI_NONAME`:** Хост або сервіс не знайдено. Від сервера імен надійшла негативна відповідь `NXDOMAIN`, або запис відсутній у локальному файлі `/etc/hosts`. Вказує на помилку в написанні домену чи відсутність A/AAAA-записів у зоні.
* **`EAI_AGAIN`:** Тимчасовий збій сервера імен. DNS-сервер не відповів протягом встановленого таймауту UDP, або повернув статус `SERVFAIL`. Застосунок повинен повторити запит пізніше.
* **`EAI_FAIL`:** Невиправний збій підсистеми DNS. Сервер імен повідомив про критичну внутрішню помилку, порушення структури зони або збій авторитетності.
* **`EAI_FAMILY`:** Запитане сімейство протоколів (наприклад, тільки IPv6 через `AF_INET6`) не підтримується резолвером хоста або не має налаштованих інтерфейсів.
* **`EAI_SERVICE`:** Запитаний мережевий порт або ім'я сервісу (наприклад, "http", "ssh") не знайдено у системній базі даних `/etc/services`.
* **`EAI_MEMORY`:** Вичерпано оперативну пам'ять процесу для виділення зв'язного списку структур `struct addrinfo`.
* **`EAI_SYSTEM`:** Сталася системна помилка введення-виведення або сокета під час взаємодії з демоном NSS; точний код помилки записано в глобальну змінну `errno`.

### 2.2. Помилки сокетів і транспортного рівня (`errno`)

Нижче наведено коди змінної `errno`, які генеруються ядром під час виконання системних викликів `connect()`, `sendto()` та операцій з дескрипторами сокетів:

* **`ECONNREFUSED` (111 — Connection refused):** 
  Ядро клієнта отримало у відповідь пакет `TCP RST` (Reset) або повідомлення `ICMP Port Unreachable`. Це є строгим доказом того, що мережевий маршрут справний і цільовий хост функціонує, однак на запитаному порті не зареєстровано жодного слухаючого сокета, демон прив'язаний виключно до локальної петлі `127.0.0.1`, або правило фаєрволу виконує дію `REJECT`.
* **`ETIMEDOUT` (110 — Connection timed out):** 
  Вичерпано ліміт часу очікування відповіді на пакет `TCP SYN`. Стек TCP здійснив серію повторних ретрансмітів без отримання жодного байта у відповідь. Це свідчить про мовчазне скидання пакетів дією `DROP` у фаєрволі `nftables`, блокування хмарними екранами Security Group або розрив фізичного каналу зв'язку.
* **`ENETUNREACH` (101 — Network is unreachable):** 
  Локальне ядро не може відправити пакет, оскільки в таблиці Forwarding Information Base (FIB) відсутній відповідний маршрут (немає шлюзу за замовчуванням `default gateway`), або мережевий інтерфейс переведено в стан `DOWN`.
* **`EHOSTUNREACH` (113 — No route to host):** 
  Від проміжного маршрутизатора надійшло службове повідомлення `ICMP Destination Host Unreachable`, або локальне ядро не змогло встановити апаратну MAC-адресу вузла призначення через збій протоколу ARP (стан `FAILED` у таблиці сусідів).
* **`EHOSTDOWN` (112 — Host is down):** 
  Цільовий вузол локальної мережі повністю припинив відповідати на канальні запити або був вимкнений.
* **`EADDRINUSE` (98 — Address already in use):** 
  Спроба виклику `bind()` на локальну IP-адресу та порт, які вже зайняті іншим активним сокетом без прапорця `SO_REUSEPORT` чи `SO_REUSEADDR`.
* **`EADDRNOTAVAIL` (99 — Cannot assign requested address):** 
  Спроба прив'язки сокета до IP-адреси, яка не належить жодному локальному мережевому інтерфейсу системи, або вичерпання пулу динамічних клієнтських портів (`ephemeral ports`).
* **`EACCES` (13 — Permission denied):** 
  Спроба непривілейованого процесу без можливості `CAP_NET_BIND_SERVICE` відкрити привілейований порт нижче 1024, або блокування операції модулями безпеки LSM (SELinux, AppArmor).
* **`EPIPE` (32 — Broken pipe):** 
  Спроба запису даних у сокет, з'єднання якого вже розірвано віддаленою стороною або скинуто через `RST`. За замовчуванням ядро надсилає процесу сигнал `SIGPIPE`.

## 3. Ядерні параметри конфігурації мережі (`/proc/sys/net/`)

Поведінка мережевого стека Linux регулюється файлами віртуальної файлової системи `sysctl`. Значення цих параметрів безпосередньо впливають на швидкість виявлення збоїв, кількість повторних спроб встановлення зв'язку та правила фільтрації асиметричних маршрутів.

Усі параметри можна переглядати через пряме зчитування файлів `/proc/sys/net/` або за допомогою утиліти `sysctl`.

| Шлях параметра sysctl | Замовчування | Опис механізму та діагностичний вплив |
|---|---|---|
| `/proc/sys/net/ipv4/tcp_syn_retries` | `6` | Кількість повторних відправок початкового пакета SYN до розриву з'єднання. Клієнтське ядро подвоює інтервали очікування між спробами: 1с + 2с + 4с + 8с + 16с + 32с. Сумарно це дає близько 63–130 секунд до повернення помилки `ETIMEDOUT`. |
| `/proc/sys/net/ipv4/tcp_retries2` | `15` | Кількість ретрансмітів непотверджених пакетів даних у вже встановленому TCP-з'єднанні до примусового закриття сокета (еквівалентно 13–30 хвилинам залежно від RTT). |
| `/proc/sys/net/ipv4/ip_forward` | `0` | Дозвіл ядру маршрутизувати транзитні IP-пакети між різними мережевими інтерфейсами хоста. Якщо значення дорівнює `0`, хост відкидає всі пакети, адресовані не його власним IP-адресам (критично для VPN-серверів та Docker). |
| `/proc/sys/net/ipv4/conf/all/rp_filter` | `0` / `2` | Режим фільтрації зворотного шляху (Reverse Path Filtering). Значення `1` (строгий режим) змушує ядро скидати вхідні пакети, якщо відповідь на них згідно з таблицею FIB мала б піти через інший інтерфейс. Це часта причина незрозумілих таймаутів при асиметричній маршрутизації. |
| `/proc/sys/net/ipv4/conf/all/arp_ignore` | `0` | Режим відповідей на ARP-запити. Значення `1` дозволяє ядру відповідати на ARP-запит лише в тому разі, якщо запитана IP-адреса налаштована саме на тому інтерфейсі, на який надійшов Ethernet-кадр. |
| `/proc/sys/net/ipv4/tcp_keepalive_time` | `7200` | Час повної бездіяльності відкритого TCP-з'єднання (в секундах) до відправки першого контрольного зонда Keepalive (штатно 2 години). |
| `/proc/sys/net/ipv4/tcp_keepalive_intvl` | `75` | Інтервал між повторними контрольними зондами Keepalive у разі відсутності відповіді від віддаленого сервера. |
| `/proc/sys/net/ipv4/tcp_keepalive_probes` | `9` | Кількість поспіль пропущених зондів Keepalive до оголошення з'єднання мертвим і генерації помилки `ETIMEDOUT` для прикладного процесу. |
| `/proc/sys/net/ipv4/ip_local_port_range` | `32768 60999` | Діапазон динамічних портів для вихідних клієнтських сокетів. При вичерпанні пулу вільних портів виклик `connect()` повертає помилку `EADDRNOTAVAIL`. |

Математичний розрахунок часу очікування таймауту TCP SYN:

```
T_total = \sum_{i=0}^{N-1} (RTO_{base} \cdot 2^i)
```

При початковому таймауті ретрансмісії `RTO = 1` секунда та значенні `tcp_syn_retries = 5` загальний час очікування становить:

```
T = 1 + 2 + 4 + 8 + 16 + 32 = 63 секунди
```

Зменшення цього параметра до `2` чи `3` у високонавантажених мікросервісах дає змогу скоротити час виявлення недосяжних бекендів до 3–7 секунд замість хвилини.

## 4. Ядерні лічильники та файли статистики (`/proc/net/`)

Для виявлення прихованих скидань пакетів на рівні ядра без запуску важкого захоплення трафіку читають спеціальні лічильники підсистем:

### 4.1. `/proc/net/snmp` та `/proc/net/netstat`
Ці файли містять кумулятивні лічильники подій протоколів IP, ICMP, TCP, UDP з моменту завантаження операційної системи.

```sh
# Пошук аномальних скидань та ретрансмітів TCP
grep -E '^(Tcp:|TcpExt:)' /proc/net/netstat /proc/net/snmp
```

Критичні поля для аналізу мережевих збоїв:
* `RetransSegs` — загальна кількість повторно надісланих сегментів TCP. Різке зростання лічильника свідчить про перевантаження каналу або втрату пакетів на маршруті.
* `InErrs` — вхідні пакети IP, відкинуті ядром через пошкоджені заголовки, невірні контрольні суми або невідповідність довжини.
* `OutNoRoutes` — пакети, які локальне ядро не змогло відправити через повну відсутність маршруту в таблиці FIB.
* `ListenOverflows` — кількість вхідних TCP-з'єднань, які були скинуті ядром через переповнення черги `accept()` слухаючого сокета прикладного процесу.
* `ListenDrops` — кількість підключень, відкинутих ядром через брак оперативної пам'яті сокетів або переповнення черги напіввідкритих з'єднань (SYN Backlog).

### 4.2. `/proc/net/dev`
Показує статистику на рівні фізичних та віртуальних мережевих адаптерів хоста:
* `rx_dropped` / `tx_dropped` — пакети, скинуті драйвером мережевої карти або ядром через брак буферної пам'яті чи переповнення кільцевих черг передавача (Ring Buffers).
* `rx_errors` / `tx_errors` — фізичні помилки мережевого контролера, збої контрольних сум кадрів Ethernet (CRC errors) або колізії в напівдуплексних середовищах.

## 5. Статичні трасувальні точки ядра (Kernel Tracepoints)

Коли класичні утиліти не дають відповіді, чому ядро знищує або блокує з'єднання, використовують підсистему `tracefs` (`/sys/kernel/tracing/events/`) або інструменти `perf` та `bpftrace`. Статичні точки трасування мають практично нульові накладні витрати й дозволяють зафіксувати точний момент відкидання пакета.

| Подія трасування (Tracepoint) | Підсистема ядра | Діагностичне значення та аргументи |
|---|---|---|
| `sock:inet_sock_set_state` | Сокети ядра | Фіксує всі переходи станів TCP (`TCP_SYN_SENT` → `TCP_ESTABLISHED`, `TCP_CLOSE` тощо) разом із PID процесу, адресами та портами сокета. |
| `tcp:tcp_destroy_sock` | Протокол TCP | Спрацьовує в момент повного звільнення структури `struct sock` ядром; дає змогу виявити несподівані скидання сесій. |
| `tcp:tcp_retransmit_skb` | Протокол TCP | Викликається на кожній повторній передачі сегмента; вказує на точні IP-адреси та порти сокетів, де виникають втрати. |
| `skb:kfree_skb` | Буфери sk_buff | Спрацьовує кожного разу, коли ядро звільняє (відкидає) мережевий пакет. Поле `location` містить точну адресу функції ядра, що викинула пакет. |
| `net:net_dev_xmit` | Драйвери мережі | Фіксує передачу кадру канального рівня в кільцеву чергу передавача мережевого адаптера. |
| `fib:fib_table_lookup` | Маршрутизація FIB | Показує детальний процес вибору маршруту в ядрі: вхідні параметри, результат пошуку та код помилки. |

Приклад перехоплення причин відкидання пакетів через утиліту `perf`:

```sh
# Збір подій скидання пакетів skb:kfree_skb на 5 секунд
sudo perf record -e skb:kfree_skb -a -g -- sleep 5

# Формування звіту з функціями ядра, що відкинули пакети
sudo perf report --stdio
```

Якщо у виводі `perf report` домінує функція `nf_hook_slow`, це є прямим доказом того, що пакети знищуються правилом фаєрволу `nftables` чи `iptables`. Якщо ж пакети скидаються у функції `tcp_v4_rcv`, причиною є відсутність слухаючого сокета або помилка валідації послідовностей TCP Sequence Number.
