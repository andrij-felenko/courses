# 📋 Інтерфейс системних викликів конвеєра: контракти та керування

Організація міжпроцесного конвеєра в операційних системах сімейства POSIX і Linux спирається на фіксований набір системних викликів ядра. Ці виклики відповідають за створення каналів передачі даних у пам'яті ядра, атомарне перепризначення файлових дескрипторів у таблиці процесу, керування групами процесів та володінням керуючим терміналом, оптимізацію передачі даних без копіювання, асинхронне спостереження за подіями каналів через epoll, низькорівневу синхронізацію між ядрами процесора, а також збирання статусів завершення й обробку сигналів розриву каналу.

Нижче наведено вичерпний довідник системних інтерфейсів, їхніх сигнатур, прапорців, структур даних ядра, правил безпеки та кодів помилок, які використовуються командними оболонками та системними демонами для побудови надійних конвеєрів.

## 1. Створення анонімних каналів: pipe та pipe2

Канал (англ. *pipe*) є односпрямованим байтовим потоком, що буферизується в оперативній пам'яті ядра за принципом черги FIFO (first in, first out). Для його виділення використовуються функції `pipe()` та `pipe2()`.

```c
#include <unistd.h>
#include <fcntl.h>

int pipe(int pipefd[2]);
int pipe2(int pipefd[2], int flags);
```

### Параметри та повертані значення

- `pipefd`: покажчик на масив із двох цілих чисел. У разі успішного виконання ядро виділяє два нові файлові дескриптори в таблиці процесу:
  - `pipefd[0]` — дескриптор для **зчитування** даних (read end);
  - `pipefd[1]` — дескриптор для **запису** даних (write end).
- `flags` (лише для `pipe2`): бітова маска модифікаторів поведінки створених дескрипторів. Якщо `flags == 0`, виклик `pipe2()` повністю еквівалентний базовому `pipe()`.
- **Повертане значення**: `0` у разі успішного виділення; `-1` у разі помилки із записом детального коду причини в глобальну змінну `errno`.

### Прапорці pipe2 (Linux 2.6.27+)

| Прапорець | Числове значення | Призначення та поведінка |
| :--- | :--- | :--- |
| `O_CLOEXEC` | `02000000` | Встановлює прапорець `FD_CLOEXEC` (close-on-exec) на обидва виділені дескриптори. Гарантує атомарне закриття дескрипторів під час виклику `execve()`, усуваючи стан гонитви (race condition) витоку дескрипторів у паралельних потоках. |
| `O_NONBLOCK` | `00004000` | Встановлює неблокуючий режим вводу-виводу для обох кінців каналу. Спроби `read()` з порожнього або `write()` у повний канал негайно повертають помилку `EAGAIN` або `EWOULDBLOCK` замість блокування процесу в ядрі. |
| `O_DIRECT` | `00040000` | Вмикає режим пакетної передачі даних (Linux 3.4+). Кожен окремий виклик `write()` розглядається як дискретний неподільний пакет; `read()` зчитує рівно один пакет за раз. |

### Коди помилок pipe / pipe2

- `EFAULT`: адреса масиву `pipefd` знаходиться поза межами доступного адресного простору процесу.
- `EINVAL`: передано непідтримуване або взаємовиключне значення в аргументі `flags`.
- `EMFILE`: процес вичерпав свій ліміт відкритих файлових дескрипторів (`RLIMIT_NOFILE`).
- `ENFILE`: досягнуто загальносистемне обмеження на кількість одночасно відкритих файлів у системі (`/proc/sys/fs/file-max`).

## 2. Іменовані канали: mkfifo та специфіка відкриття

Іменований канал (FIFO) володіє власною точкою входу у файловій системі, дозволяючи з'єднувати неспоріднені процеси:

```c
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int mkfifo(const char *pathname, mode_t mode);
```

### Специфіка системного виклику open для каналів FIFO

Поведінка `open()` над файлом FIFO суттєво відрізняється від роботи зі звичайними дисковими файлами і залежить від комбінації прапорців доступу та режиму блокування:

- `open(path, O_RDONLY)`: блокує викликаючий процес доти, доки інший процес не відкриє той самий FIFO на запис (`O_WRONLY`).
- `open(path, O_WRONLY)`: блокує викликаючий процес доти, доки інший процес не відкриє той самий FIFO на зчитування (`O_RDONLY`).
- `open(path, O_RDONLY | O_NONBLOCK)`: успішно відкриває дескриптор читання негайно, навіть якщо процесів-записувачів ще немає.
- `open(path, O_WRONLY | O_NONBLOCK)`: якщо читачів немає, виклик **негайно завершується помилкою** із кодом `ENXIO` (No such device or address). Це запобігає зависанню записувача в порожнечу.

## 3. Дублювання та підміна дескрипторів: dup, dup2, dup3

Для підключення стандартних потоків вводу (`stdin`, FD 0) та виводу (`stdout`, FD 1) до створених дескрипторів каналу застосовуються виклики дублювання.

```c
#include <unistd.h>
#include <fcntl.h>

int dup(int oldfd);
int dup2(int oldfd, int newfd);
int dup3(int oldfd, int newfd, int flags);
```

### Порівняльна характеристика викликів

- `dup(oldfd)`: знаходить **найменший вільний** цілочисельний індекс у таблиці дескрипторів процесу й асоціює його з тим самим відкритим описом файлу (`struct file`), на який вказує `oldfd`.
- `dup2(oldfd, newfd)`: атомарно призначає дескриптор `newfd` копією `oldfd`. Якщо дескриптор `newfd` уже був відкритий у процесі, ядро атомарно закриває його перед виконанням операції дублювання, усуваючи необхідність попереднього явного виклику `close(newfd)`. Якщо `oldfd == newfd`, перевіряється валідність дескриптора і повертається `newfd`.
- `dup3(oldfd, newfd, flags)`: розширення `dup2`, що підтримує прапорець `O_CLOEXEC`. На відміну від `dup2`, якщо `oldfd == newfd`, функція не виконує операцію і повертає помилку `EINVAL`.

```
Схема атомарності операції dup2:
+---------------------------------------------------------------+
| 1. Перевірка валідності oldfd (якщо закрито -> EBADF)        |
| 2. Перевірка рівності: if (oldfd == newfd) return newfd;     |
| 3. Атомарне закриття newfd (якщо він відкритий у таблиці)     |
| 4. Запис вказівника на struct file з oldfd у позицію newfd    |
| 5. Очищення прапорця FD_CLOEXEC для цільового newfd          |
+---------------------------------------------------------------+
```

### Коди помилок dup / dup2 / dup3

- `EBADF`: `oldfd` не є дійсним відкритим дескриптором або `newfd` є від'ємним чи перевищує ліміт.
- `EBUSY`: виявлено стан гонитви між одночасними системними викликами `open()` та `dup2()` у багатопотоковому середовищі (специфічно для деяких реалізацій ядра Linux).
- `EINTR`: операцію перепідключення перервано сигналом операційної системи.
- `EINVAL`: передано непідтримуваний прапорець у `dup3` або `oldfd == newfd` для виклику `dup3`.
- `EMFILE`: досягнуто ліміт максимальної кількості відкритих дескрипторів для поточного процесу.

## 4. Керування групами процесів і керуючим терміналом

Щоб конвеєр коректно взаємодіяв із сигналами комбінацій клавіш (наприклад, `Ctrl+C` надсилає `SIGINT`, `Ctrl+Z` надсилає `SIGTSTP`), усі процеси одного конвеєра об'єднуються в єдину **групу процесів** (англ. *process group*), яка призначається активною для керуючого термінала.

```c
#include <unistd.h>
#include <termios.h>

int setpgid(pid_t pid, pid_t pgid);
pid_t getpgid(pid_t pid);
pid_t getpgrp(void);

int tcsetpgrp(int fd, pid_t pgrp);
pid_t tcgetpgrp(int fd);
```

### Системні контракти та правила використання

- `setpgid(pid, pgid)`: призначає ідентифікатор групи процесів `pgid` для процесу `pid`.
  - Якщо `pid == 0`, модифікується група викликаючого процесу.
  - Якщо `pgid == 0`, ідентифікатор групи встановлюється рівним значенню `pid` (процес стає лідером своєї новоствореної групи).
  - **Інваріант надійності конвеєра**: оболонка зобов'язана викликати `setpgid(child_pid, pipeline_pgid)` як у тілі батька, так і в тілі дитини одразу після розгалуження `fork()`. Це гарантує, що дитина опиниться в правильній групі незалежно від того, якому процесу планувальник передасть керування першим.
- `tcsetpgrp(fd, pgrp)`: встановлює групу процесів `pgrp` передньоплановою для термінала `fd` (зазвичай дескриптор `STDIN_FILENO` або відкритий `/dev/tty`). Усі сигнали генерації клавіатури надсилатимуться виключно процесам цієї групи.
- `tcgetpgrp(fd)`: повертає PGID активної передньопланової групи керуючого термінала.

### Коди помилок setpgid та tcsetpgrp

- `EACCES`: процес `pid` уже виконав системний виклик `execve()`. Стандарт POSIX жорстко забороняє змінювати PGID процесу після заміни його коду пам'яті новим бінарним образом.
- `EINVAL`: значення `pgid` менше нуля або не підтримується архітектурою ядра.
- `EPERM`: спроба перемістити процес в іншу сесію або змінити PGID лідера сесії.
- `ESRCH`: процес із переданим ідентифікатором `pid` не знайдено в таблиці процесів ядра.
- `ENOTTY`: файловий дескриптор `fd`, переданий у `tcsetpgrp`, не належить керуючому терміналу поточного сеансу.

## 5. Внутрішня структура ядра: pipe_inode_info та fcntl

У просторі ядра Linux канал описується структурою даних `struct pipe_inode_info`, визначеною в заголовку `include/linux/pipe_fs_i.h`. Вона керує кільцевим масивом сторінок:

```c
struct pipe_inode_info {
    wait_queue_head_t rd_wait;   // черга очікування читачів
    wait_queue_head_t wr_wait;   // черга очікування записувачів
    unsigned int      head;      // індекс наступного запису в кільці
    unsigned int      tail;      // індекс наступного зчитування з кільця
    unsigned int      ring_size; // загальна кількість сторінок у кільці
    unsigned int      readers;   // кількість відкритих дескрипторів читання
    unsigned int      writers;   // кількість відкритих дескрипторів запису
    struct pipe_buffer *bufs;    // масив дескрипторів сторінок пам'яті
};
```

### Керування розміром буфера через fcntl

```c
#include <fcntl.h>

int fcntl(int fd, int cmd, ... /* arg */ );
```

| Команда fcntl | Тип аргументу | Опис операції |
| :--- | :--- | :--- |
| `F_SETPIPE_SZ` | `int` (байти) | Змінює максимальну місткість буфера каналу `fd`. Передане значення автоматично округлюється ядром угору до найближчого степеня двійки, кратного розміру системної сторінки (`PAGE_SIZE`, 4096 байтів). |
| `F_GETPIPE_SZ` | `void` | Повертає поточну виділену місткість буфера каналу в байтах. |

### Системні ліміти ємності каналів у Linux

- **Мінімальний розмір**: одна сторінка пам'яті (4096 байтів).
- **Типовий розмір за замовчуванням**: 16 сторінок пам'яті = 65536 байтів (64 КіБ).
- **Ліміт для непривілейованого процесу**: контролюється файлом `/proc/sys/fs/pipe-max-size` (типово 1048576 байтів = 1 МіБ). Спроба встановити розмір понад цей ліміт без привілею `CAP_SYS_RESOURCE` повертає помилку `EPERM`.
- **Загальний ліміт пам'яті каналів на користувача**: контролюється псевдофайлами `/proc/sys/fs/pipe-user-pages-soft` та `/proc/sys/fs/pipe-user-pages-hard`.

### Атомарність запису: константа PIPE_BUF

Стандарт POSIX визначає константу `PIPE_BUF` як граничний розмір запису, що гарантовано виконується атомарно без розривів:

- **Linux**: `PIPE_BUF = 4096` байтів (визначено в `<limits.h>`).
- **POSIX мінімум**: `_POSIX_PIPE_BUF = 512` байтів.

```
Гарантії атомарності операцій запису:
- Запис розміром N <= PIPE_BUF:
  Ядро гарантує атомарне розміщення всіх N байтів у буфері. Навіть за умови
  одночасного запису кількома незалежними процесами байти ніколи не змішуються.
- Запис розміром N > PIPE_BUF:
  Ядро може розбити потік даних на кілька окремих сторінок. Якщо паралельно
  записує інший процес, дані можуть перемішуватися частинами.
```

## 6. Очікування та аналіз статусів виходу: waitpid та waitid

Оболонка зобов'язана зібрати статуси завершення всіх процесів конвеєра, щоб запобігти утворенню процесів-зомбі (zombies) та визначити підсумковий код повернення конвеєра.

```c
#include <sys/types.h>
#include <sys/wait.h>

pid_t waitpid(pid_t pid, int *wstatus, int options);
int waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options);
```

### Семантика аргументу pid у waitpid

| Значення `pid` | Поведінка очікування |
| :--- | :--- |
| `pid < -1` | Очікувати завершення будь-якого дочірнього процесу, чий PGID дорівнює абсолютному значенню `\|pid\|`. |
| `pid == -1` | Очікувати завершення будь-якого дочірнього процесу (еквівалент класичного `wait()`). |
| `pid == 0` | Очікувати завершення будь-якого дочірнього процесу, чий PGID збігається з PGID викликаючого процесу. |
| `pid > 0` | Очікувати завершення конкретного дочірнього процесу з ідентифікатором `pid`. |

### Прапорці options для waitpid

- `WNOHANG`: повернути керування негайно, якщо жодна дитина ще не змінила свій стан. Якщо процесів у стані очікування немає, повертається `0`.
- `WUNTRACED`: повертати статус також для зупинених дочірніх процесів (сигнали `SIGSTOP`, `SIGTSTP`, `SIGTTIN`, `SIGTTOU`).
- `WCONTINUED`: повертати статус для дочірніх процесів, які відновили виконання після зупинки за сигналом `SIGCONT`.

### Макроси розпакування статусу wstatus

```c
// Перевірка нормального завершення програми через exit() або return із main():
WIFEXITED(wstatus)    // повертає true, якщо процес вийшов штатно
WEXITSTATUS(wstatus)  // повертає молодші 8 бітів коду виходу (діапазон 0..255)

// Перевірка завершення програми внаслідок отримання сигналу:
WIFSIGNALED(wstatus)  // повертає true, якщо процес було вбито необробленим сигналом
WTERMSIG(wstatus)     // номер сигналу, що спричинив загибель (SIGPIPE=13, SIGINT=2)
WCOREDUMP(wstatus)    // повертає true, якщо ядро створило файл дампу пам'яті

// Перевірка зупинки або відновлення процесу (керування завданнями):
WIFSTOPPED(wstatus)   // повертає true, якщо процес зупинено сигналом
WSTOPSIG(wstatus)     // номер сигналу, який спричинив зупинку
WIFCONTINUED(wstatus) // повертає true, якщо процес продовжив роботу
```

## 7. Сигнал розриву каналу: SIGPIPE та помилка EPIPE

Коли процес намагається виконати системний виклик `write()` у канал, для якого **закриті всі дескриптори читання** (у просторі ядра кількість активних читачів `readers == 0`), виникає ситуація зламаної труби (англ. *broken pipe*).

### Алгоритм реакції ядра на спробу запису

1. Ядро перевіряє лічильник читачів у структурі `struct pipe_inode_info`. Якщо `readers == 0`:
2. Процесу-записувачу надсилається сигнал `SIGPIPE` (сигнал № 13).
3. Якщо диспозиція сигналу встановлена в дію за замовчуванням (`SIG_DFL`), процес **негайно знищується** ядром. Код статусу завершення містить прапорець `WIFSIGNALED` із номером сигналу `13` (оболонки транслюють це в код `128 + 13 = 141`).
4. Якщо процес встановив ігнорування сигналу (`signal(SIGPIPE, SIG_IGN)`) або призначив власний обробник через `sigaction`, сигнал не завершує процес, а системний виклик `write()` повертає значення `-1`, встановлюючи `errno = EPIPE`.

```
Логіка генерації SIGPIPE:
[Процес-записувач] ---> write(fd, buf, len)
                               |
                               v
                     [Перевірка в ядрі]
                               |
            +------------------+------------------+
            | readers > 0                         | readers == 0
            v                                     v
   [Запис у кільцевий буфер]            1. Генерація сигналу SIGPIPE
                                        2. Якщо не вбито -> return -1 (errno=EPIPE)
```

## 8. Асинхронний моніторинг конвеєрів: epoll та події каналу

Для одночасного обслуговування кількох каналів в асинхронних серверах дескриптори каналів реєструються в підсистемі `epoll`:

```c
#include <sys/epoll.h>

int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
```

### Події epoll для дескрипторів каналу

- `EPOLLIN`: у буфері каналу з'явилися дані, доступні для зчитування без блокування.
- `EPOLLOUT`: у буфері каналу звільнилося місце (хоча б одна вільна сторінка), можливий запис без блокування.
- `EPOLLHUP`: усі дескриптори запису для цього каналу закриті (для читача це означає настання стану `EOF`). Важливо: `EPOLLHUP` генерується автоматично, його не потрібно вказувати в масці `events`.
- `EPOLLERR`: виникла помилка каналу (наприклад, спроба запису в канал без читачів).

## 9. Декларативний запуск конвеєрів: posix_spawn_file_actions

Сучасний стандарт POSIX надає альтернативу ланцюжку `fork + dup2 + exec` у вигляді декларативного інтерфейсу `posix_spawn()`, що використовує об'єкти дій над дескрипторами:

```c
#include <spawn.h>

int posix_spawn_file_actions_init(posix_spawn_file_actions_t *file_actions);
int posix_spawn_file_actions_destroy(posix_spawn_file_actions_t *file_actions);

int posix_spawn_file_actions_adddup2(posix_spawn_file_actions_t *file_actions,
                                     int oldfd, int newfd);
int posix_spawn_file_actions_addclose(posix_spawn_file_actions_t *file_actions,
                                      int fd);

int posix_spawnattr_setpgroup(posix_spawnattr_t *attr, pid_t pgroup);
int posix_spawnattr_setflags(posix_spawnattr_t *attr, short flags);
```

### Прапорці spawnattr для конвеєрів

- `POSIX_SPAWN_SETPGROUP`: автоматично призначає новостворений процес у групу процесів, задану викликом `posix_spawnattr_setpgroup()`, повністю усуваючи потребу в ручному виклику `setpgid()` у дочірньому процесі.
- `POSIX_SPAWN_SETSIGMASK`: призначає дитині маску блокування сигналів перед заміною образу.
- `POSIX_SPAWN_SETSIGDEF`: скидає обробники сигналів на типові системні дії.

## 10. Передача даних без копіювання: splice та vmsplice

Для побудови надшвидких конвеєрів у просторі ядра Linux надає системні виклики сімейства splice, які передають сторінки пам'яті між дескрипторами файлів і каналів без копіювання даних у простір користувача:

```c
#include <fcntl.h>
#include <sys/uio.h>

ssize_t splice(int fd_in, loff_t *off_in, int fd_out, loff_t *off_out,
               size_t len, unsigned int flags);
ssize_t vmsplice(int fd, const struct iovec *iov, unsigned long nr_segs,
                 unsigned int flags);
```

### Принцип роботи та прапорці splice / vmsplice

Системний виклик `vmsplice()` відображає сторінки пам'яті користувацького буфера безпосередньо у внутрішні структури `struct pipe_buffer` каналу без проміжного копіювання через процесорний кеш (zero-copy memory pinning):

- `SPLICE_F_MOVE`: підказує ядру спробувати перемістити фізичні сторінки пам'яті замість їх дублювання.
- `SPLICE_F_NONBLOCK`: робить виклик неблокуючим.
- `SPLICE_F_MORE`: підказує мережевому стеку або каналу, що незабаром надійдуть додаткові дані.
- `SPLICE_F_GIFT`: передає ядру повне володіння сторінками пам'яті користувача; після цього виклику користувацький процес не повинен змінювати вміст буфера до завершення зчитування.

## 11. Порівняння каналів із socketpair

Для задач, де потрібен повнодуплексний (двосторонній) обмін даними між процесами, альтернативою `pipe()` виступає `socketpair()`:

```c
#include <sys/types.h>
#include <sys/socket.h>

int socketpair(int domain, int type, int protocol, int sv[2]);
```

### Ключові відмінності архітектури

| Характеристика | pipe() / pipe2() | socketpair(AF_UNIX, SOCK_STREAM, ...) |
| :--- | :--- | :--- |
| Напрямок потоку | Строго односпрямований (`sv[0]` для читання, `sv[1]` для запису) | Повнодуплексний (обидва дескриптори підтримують і `read()`, і `write()`) |
| Накладні витрати пам'яті | Мінімальні (простий кільцевий буфер сторінок ядра) | Вищі (повноцінні структури сокетів ядра `struct sock`, черги sk_buff) |
| Передача дескрипторів | Не підтримується | Підтримується через допоміжні повідомлення `SCM_RIGHTS` у `sendmsg()` |
| Передача метаданих | Лише сирий байтовий потік (або пакети в `O_DIRECT`) | Підтримується передача облікових даних процесу `SCM_CREDENTIALS` |

## 12. Низькорівнева когерентність та бар'єри пам'яті

Під час передачі даних через канал на багатоядерних SMP-системах ядро Linux забезпечує сувору послідовність операцій пам'яті без блокування шини процесора:

- **Запис даних**: системний виклик `pipe_write()` копіює дані з простору користувача у виділені фізичні сторінки пам'яті ядра через `copy_page_from_iter()`. Після завершення запису ядра виконує бар'єр пам'яті звільнення (`smp_store_release`) на індексі `pipe->head`.
- **Зчитування даних**: системний виклик `pipe_read()` зчитує індекс `pipe->head` за допомогою бар'єра отримання (`smp_load_acquire`), що гарантує: читаючий процесор гарантовано бачить усі байти в пам'яті сторінки до того, як оновиться індекс доступних даних. Це усуває можливість читання неповної або застарілої інформації з процесорних кешів.

## 13. Трасування подій каналів через ftrace

Для глибокої діагностики затримок і пропускної здатності конвеєра в ядрі Linux передбачені статичні точки трасування (tracepoints) підсистеми `ftrace`:

- `/sys/kernel/debug/tracing/events/pipe/pipe_write/`: фіксує кожен системний виклик запису, обсяг записаних байтів та стан буфера.
- `/sys/kernel/debug/tracing/events/pipe/pipe_read/`: фіксує операції зчитування, час блокування та пробудження процесів на чергах очікування.
- `/sys/kernel/debug/tracing/events/sched/sched_switch/`: дозволяє виміряти точний час перемикання контексту між процесами-учасниками конвеєра.

## 14. Обмеження операцій над каналами

Канали є суто потоковими примітивами і не підтримують позиціонування та відображення в пам'ять:

- `lseek(pipefd, offset, whence)`: завжди повертає `-1` із встановленням `errno = ESPIPE` (Illegal seek).
- `mmap(...)`: повертає `MAP_FAILED` із встановленням `errno = ENODEV` або `EINVAL`, оскільки канал не має асоційованого блокового пристрою чи структури відображення сторінок.

## 15. Діагностика конвеєрів через procfs

Для простеження стану конвеєра в реальній системі використовуються псевдофайли підсистеми procfs:

- `/proc/<PID>/fd/`: каталог символічних посилань на всі відкриті файлові дескриптори процесу. Для каналів посилання мають вигляд `pipe:[123456]`, де число відповідає номеру інода в ядрі.
- `/proc/<PID>/fdinfo/<FD>`: містить інформацію про поточну позицію зміщення (`pos`), прапорці доступу (`flags`) та номер інода каналу (`pipe-ino`).
- `/proc/sys/fs/pipe-max-size`: системна стеля місткості буфера каналу для непривілейованих процесів.

## 16. Безпека дескрипторів каналів при переході привілеїв

Під час створення конвеєрів у багатокористувацькому середовищі критично уникати витоку дескрипторів у привілейовані процеси (наприклад, виконувані файли з встановленим бітом `setuid`):

- **Небезпека витоку FD**: якщо батьківський процес відкриває канал до конфіденційного файлу або IPC-сервера і не встановлює прапорець `FD_CLOEXEC`, дочірній процес після `execve()` привілейованої утиліти збереже доступ до дескриптора.
- **Атака підміни стандартних дескрипторів**: якщо перед запуском програми закрити дескриптори `0`, `1` або `2`, наступний виклик `open()` або `pipe()` займе ці номери. Якщо привілейована програма розраховує, що дескриптор 2 є потоком помилок, запис логів може ненавмисно перезаписати дані в канал іншого користувача. Захисна практика вимагає завжди гарантувати відкритість дескрипторів 0, 1, 2 (наприклад, перенаправленням на `/dev/null`).

## 17. Матриця типових помилок та способів усунення

| Симптом збою | Причина збою в ядрі | Спосіб усунення в коді |
| :--- | :--- | :--- |
| Конвеєр зависає назавжди на читанні | Батьківська оболонка або попередня дитина не закрила кінці запису (`write end`) каналу | Обов'язково викликати `close()` для всіх невикористовуваних дескрипторів каналу в батькові та в кожній дитині одразу після `dup2()`. |
| `setpgid()` повертає `EACCES` | Оболонка спробувала встановити PGID після того, як дитина вже виконала `execve()` | Викликати `setpgid()` двічі: у батьківському процесі та в дочірньому процесі до виклику `execve()`. |
| Процес неочікувано завершується з кодом 141 | Програма записала байти в канал, з якого читач уже вийшов (доставлено `SIGPIPE`) | Встановити ігнорування `SIGPIPE` або коректно обробляти код помилки `EPIPE` системного виклику `write()`. |
| Скрипт успішно завершується попри збій у середині конвеєра | За замовчуванням оболонка повертає статус лише останньої команди | Увімкнути опцію `set -o pipefail` або опитувати масив `$pipestatus` / `$PIPESTATUS`. |
| `open()` на FIFO повертає `ENXIO` | Спроба відкрити FIFO з прапорцем `O_WRONLY \| O_NONBLOCK`, коли немає активних читачів | Забезпечити попереднє відкриття читача або відкривати FIFO без прапорця `O_NONBLOCK`. |
