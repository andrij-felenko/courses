Виробничий кластер баз даних раптово зупиняє приймання нових транзакцій із системною помилкою `No space left on device` (код помилки `ENOSPC`), хоча засоби моніторингу ще годину тому показували понад 150 гігабайтів вільного дискового простору. Черговий інженер підключається до термінала сервера й запускає команду `df -h /var/lib/data`. Утиліта категорично свідчить: розділ місткістю 200 ГБ заповнений на 100%, доступних блоків нуль. Намагаючись локалізувати каталоги, які несподівано розрослися, інженер виконує рекурсивний аналіз дерева через `du -sh /var/lib/data/*`. Результат підрахунку шокує: сумарний обсяг усіх видимих файлів і підкаталогів на цьому розділі становить лише 12 ГБ.

Куди безслідно зникли 188 гігабайтів дискового простору? Дві фундаментальні системні утиліти Unix суперечать одна одній на порядок величин. Інженер намагається поспіхом видалити старі логи командою `rm -f /var/log/app.log`, сподіваючись вивільнити місце, але команда `df -h` продовжує показувати 100% заповнення, а база даних відмовляється стартувати. Ситуація заходить у глухий кут: файлів на диску немає, а місця все одно бракує.

Ця розбіжність не є наслідком помилки в системних програмах чи збою дискового накопичувача. Вона випливає з базової архітектури дискових підсистем Unix, де облік фізичного простору на рівні суперблока файлової системи кардинально відокремлений від обходу видимого дерева назв у просторі користувача.

## 1. Анатомія розбіжності: як рахують `df` та `du`

Щоб зрозуміти причину протиріччя між двома утилітами, необхідно зіставити два принципово різні рівні абстракцій операційної системи, які вони опитують: глобальну статистику суперблока файлової системи проти обходу окремих записів у структурі каталогів.

```
+-----------------------------------------------------------------------------------+
| ДВА ШЛЯХИ ДОСЛІДЖЕННЯ ПРОСТОРУ:                                                  |
|                                                                                   |
|    df (statvfs)                          du (readdir + fstatat)                   |
|         │                                          │                              |
|         ▼                                          ▼                              |
| ┌─────────────────────────┐               ┌─────────────────────────┐             |
| │ Суперблок VFS           │               │ Дерево каталогів VFS    │             |
| │ struct super_block      │               │ struct dentry / dirent  │             |
| │ • Бітова карта блоків   │               │ /var/log/               │             |
| │ • s_free_blocks_count   │               │   ├── app.log (deleted) │ <── НЕ ВИДНО|
| │ • Резерв root (5%)      │               │   └── syslog (12 ГБ)    │ <── du рахує|
| └─────────────────────────┘               └─────────────────────────┘             |
|         │                                          │                              |
|         ▼                                          ▼                              |
| Результат: 200 ГБ ЗАЙНЯТО (100%)          Результат: 12 ГБ ЗАЙНЯТО                |
+-----------------------------------------------------------------------------------+
```

### Як працює утиліта `df`: опитування суперблока

Команда `df` (від англ. *disk free*) не сканує файли й не перевіряє каталоги. Під час запуску вона викликає стандартну системну функцію `statvfs()` (або внутрішній системний виклик ядра `statfs()`), передаючи їй шлях до точки монтування.

На рівні ядра операційної системи підсистема VFS (Virtual File System) транзитом через функцію `vfs_statfs()` викликає метод конкретного драйвера файлової системи — `sb->s_op->statfs()`. Драйвер зчитує поля структури `struct super_block` безпосередньо з оперативної пам'яті ядра.

У суперблоці зберігаються агреговані показники дискового розділу:
1. Загальна кількість блоків геометрії носія (`f_blocks`);
2. Кількість фізично вільних блоків за глобальною бітовою картою розподілу блокових груп (`f_bfree`);
3. Кількість вільних блоків, дозволених для виділення непривілейованим процесам (`f_bavail`);
4. Розмір одиниці фрагментації виділення (`f_frsize`).

Часова складність роботи `df` становить `O(1)`: системний виклик повертає результат за мікросекунди як для флеш-накопичувача на 10 ГБ, так і для дискового масиву ємністю 100 ТБ. Проте `df` має фундаментальну сліпу зону: вона бачить виключно сумарне число зайнятих блоків за глобальними картами виділення, але не володіє жодною інформацією про те, які саме файли, каталоги чи процеси утримують ці блоки.

### Як працює утиліта `du`: рекурсивний обхід дерева назв

Команда `du` (від англ. *disk usage*) працює за абсолютно протилежним принципом. Вона починає рекурсивний обхід файлового дерева від вказаного каталогу, послідовно виконуючи системні виклики `opendir()`, `readdir()` (через низькорівневий системний виклик `getdents64()`) та `lstat()` (через `newfstatat()`) для кожного знайденого елемента.

Для кожного знайденого файлу `du` зчитує поле `st_blocks` зі структури `struct stat`. Це поле містить кількість виділених файлу фізичних 512-байтових секторів. Утиліта веде внутрішню хеш-таблицю пар `(st_dev, st_ino)`, щоб уникнути подвійного підрахунку блоків для файлів, які мають кілька жорстких посилань (*hard links*).

Підсумковий результат `du` є простою арифметичною сумою:

```
Загальний обсяг du = ∑ (st_blocks × 512) для всіх знайдених імен
```

Часова складність `du` становить `O(N)`, де `N` — загальна кількість файлів і каталогів у дереві. На файлових системах із мільйонами файлів сканування може тривати десятки хвилин і створювати колосальне навантаження на підсистему вводу-виводу.

![Анатомія розбіжності між опитуванням суперблока утилітою df та рекурсивним обходом дерева каталогів утилітою du](/root/course/unix/disk-space-illusion/img/df-vs-du-divergence.svg)
*Анатомія розбіжності між опитуванням суперблока утилітою df та рекурсивним обходом дерева каталогів утилітою du.*

Головне обмеження `du`: **вона може порахувати лише ті файли, які мають дійсні записи в таблицях каталогів (*dirent*) і доступні під час обходу дерева**.

| Критерій порівняння | Утиліта `df` | Утиліта `du` |
| :--- | :--- | :--- |
| **Системний виклик** | `statvfs()` / `statfs()` | `readdir()` / `getdents64()` + `fstatat()` |
| **Джерело інформації** | Суперблок файлової системи (`struct super_block`) | Записи каталогів (`dirent`) та іноди (`struct stat`) |
| **Одиниця підрахунку** | Бітова карта вільних блоків розділу | Поле `st_blocks` кожного знайденого файлу |
| **Швидкодія** | `O(1)` — миттєво | `O(N)` — залежить від кількості файлів |
| **Відкриті видалені файли** | **Враховує повністю** (блоки позначені як зайняті) | **Ігнорує** (немає запису в каталозі) |
| **Приховані файли під mount** | **Враховує повністю** (належать батьківській ФС) | **Ігнорує** (перекриті новим монтуванням) |
| **Резерв суперкористувача** | Відображає різницю `f_bfree` та `f_bavail` | Не враховує концепцію резерву |

Повний опис структур та прапорців наведено у вставці [структуру `statvfs` та формати `/proc/pid/fdinfo`](root:unix/disk-space-illusion/api-space-diagnostics.md).

## 2. Відкриті видалені файли: семантика `unlink()` та лічильники посилань

Найпоширенішою причиною гігабайтних розбіжностей між `df` та `du` є утримання дискових блоків процесами через відкриті файлові дескриптори після вилучення імені файлу з каталогу.

### Двофазне видалення файлу в Unix

В операційних системах стандарту POSIX взагалі не існує системного виклику «видалити файл». Команда командного інтерпретатора `rm` насправді викликає системний виклик `unlink()`.

Коли процес створює файл, ядро виділяє два незалежні елементи:
1. **Запис у каталозі (*directory entry, dirent*):** пов'язує текстове ім'я файлу (наприклад, `app.log`) із числовим ідентифікатором інода (`inode number`).
2. **Вузол метаданих (*inode*):** зберігає інформацію про власника, права, атрибути, часові позначки та вказівники на виділені дискові блоки на накопичувачі.

В іноді зберігається службовий лічильник жорстких посилань — `i_nlink`. Він показує, скільки записів у різних або тому самому каталозі посилаються на цей інод. Коли створюється звичайний файл, `i_nlink = 1`.

Коли виконується виклик `unlink("app.log")`, ядро виконує такі кроки:
1. Видаляє запис `app.log` із дискової таблиці каталогу.
2. Декрементує лічильник посилань в іноді: `i_nlink = i_nlink - 1` (тобто `i_nlink` стає рівним `0`).

Проте фізичне звільнення дискових блоків та повернення їх у бітову карту суперблока в цей момент **не відбувається**, якщо файл відкрито хоча б одним процесом!

```
ПРОЦЕС (PID 28411)                    ЯДРО (VFS)                      ДИСК (Ext4)
┌──────────────────────┐          ┌──────────────────────┐        ┌──────────────────────┐
│ FD 3 (app.log)       │─────────>│ struct file          │        │ Блоки даних:         │
│ /proc/28411/fd/3     │          │ • f_count = 1        │        │ #40102 .. #47219030  │
└──────────────────────┘          │ • f_pos = 180 ГБ     │        │ 180 ГБ ЗАЙНЯТО       │
                                  └──────────┬───────────┘        └──────────▲───────────┘
                                             │                               │
                                             ▼                               │
Каталог /var/log/:                ┌──────────────────────┐                   │
┌──────────────────────┐          │ struct inode #88219  │                   │
│ [ЗАПИС ВИЛУЧЕНО]     │          │ • i_nlink = 0        │───────────────────┘
│ du бачить 0 байтів!  │          │ • i_count = 1        │ (карту блоків не очищено!)
└──────────────────────┘          └──────────────────────┘
```

### Роль лічильника `i_count` у VFS

Окрім лічильника імен `i_nlink`, структура `struct inode` у пам'яті ядра містить внутрішній лічильник активних посилань VFS — `i_count`. Кожен системний виклик `open()` або дублювання дескриптора `dup()` створює в ядрі структуру опису відкритого файлу (`struct file`) зі своїм лічильником `f_count` та інкрементує `i_count` відповідного інода.

Фізичне вивільнення блоків підпорядковується залізному логічному правилу:

```
Звільнення блоків = (i_nlink == 0) AND (i_count == 0)
```

Поки хоча б один фоновий процес (сервер застосунків, демон баз даних, ротатор журналів) утримує дескриптор відкритого файлу, `i_count > 0`. Ядро зобов'язане гарантувати процесу цілісність даних: демон продовжує успішно читати й записувати дані в дескриптор, логічний розмір файлу збільшується, а драйвер файлової системи виділяє все нові й нові дискові блоки.

![Анатомія фантомного файлу](/root/course/unix/disk-space-illusion/img/deleted-file-fd-reference.svg)
*Механізм утримання дискових блоків відкритим дескриптором після виклику unlink.*

Утиліта `du`, обходячи каталог `/var/log`, більше не бачить запису `app.log` і рапортує нуль байтів. Утиліта `df`, опитуючи суперблок, бачить, що бітова карта містить 180 ГБ виділених блоків, і чесно сигналізує про вичерпання диска.

### Ланцюжок звільнення в ядрі під час закриття дескриптора

Фізичне повернення дискових секторів відбувається лише тоді, коли процес закриває останній активний дескриптор. У цей момент ядро виконує чітку послідовність викликів:

1. Системний виклик `close(fd)` викликає функцію `filp_close()`, яка зменшує лічильник посилань `f_count` у структурі `struct file`.
2. Коли `f_count` досягає нуля, функція `fput()` викликає `dentry_iput()`, що декрементує лічильник `i_count` у `struct inode`.
3. Оскільки `i_nlink == 0` і тепер `i_count == 0`, ядро запускає функцію виселення інода `iput_final()` -> `evict()`.
4. Драйвер конкретної файлової системи виконує власний обробник звільнення (наприклад, `ext4_evict_inode()` для ext4 або `xfs_inactive()` для XFS).
5. Драйвер проходить по всьому дереву екстентів інода, повертає блоки в глобальні бітові карти розподілу блокових груп, обнуляє біт інода в карті інодів та фіксує транзакцію в журналі файлової системи (JBD2).
6. Лічильник вільних блоків `f_bfree` у суперблоці оновлюється, і `df -h` миттєво показує звільнене місце.

## 3. Виявлення та хірургічне лікування завислих файлів

Коли сервер перебуває в критичному стані аварії `ENOSPC`, інженер не може чекати планового перезапуску системи. Необхідно точно локалізувати процес-винуватець і вивільнити дискові блоки на льоту.

### Локалізація через `lsof` та `/proc`

Найпростіший спосіб знайти всі відкриті файли, які не мають імен у файловій системі, — скористатися утилітою `lsof` із прапорцем `+L1`:

```bash
# Знайти всі відкриті файли з кількістю жорстких посилань менше 1
$ lsof +L1 /var

COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NLINK   NODE NAME
java    28411 app     3w   REG    8,2 193273528320     0  88219 /var/log/app.log (deleted)
```

* Поле `NLINK` показує число `0` — це пряме підтвердження того, що файл було видалено з каталогу.
* Поле `SIZE/OFF` показує розмір у байтах (у цьому прикладі — ~180 ГБ).
* Поле `FD` вказує номер файлового дескриптора (`3w` — дескриптор 3, відкритий на запис).
* Поле `NAME` містить мітку `(deleted)`.

Якщо утиліта `lsof` не встановлена на мінімальному сервері або у врізаному контейнері, аналогічне розслідування виконується безпосередньо через інтерфейс `/proc`:

```bash
# Пошук дескрипторів із міткою deleted по всій системі
$ ls -l /proc/[0-9]*/fd/* 2>/dev/null | grep '(deleted)'

lrwx------ 1 app app 64 Aug 25 14:10 /proc/28411/fd/3 -> /var/log/app.log (deleted)
```

### Чому не можна поспішно перезапускати сервіс

Перший інстинктивний крок багатьох адміністраторів — виконати аварійний перезапуск процесу (`systemctl restart` або `kill -9 28411`). На виробничих серверах це часто неприпустимо:
1. Якщо дескриптор утримується базою даних (PostgreSQL, MySQL), раптовий `kill -9` призведе до тривалого відновлення журналу передзапису (WAL recovery) під час наступного старту, що збільшить час простою (*downtime*) з кількох секунд до десятків хвилин.
2. Процес може утримувати тисячі активних клієнтських з'єднань або виконувати невідновлювану транзакцію обробки платежів.

### Хірургічне звільнення блоків через `/proc/[pid]/fd/[fd]`

Ядро Linux надає унікальну можливість маніпулювати відкритим файлом через псевдопосилання `/proc/[pid]/fd/[fd]`. Навіть якщо файл втратив ім'я в каталозі, доступ до його інода залишається відкритим через віртуальну файлову систему `procfs`.

Найшвидший спосіб скинути розмір файлу до нуля без зупинки процесу — виконати перенаправлення порожнього виводу в командній оболонці:

```bash
# Обнулення відкритого видаленого файлу на льоту
$ : > /proc/28411/fd/3

# Або за допомогою утиліти truncate
$ truncate -s 0 /proc/28411/fd/3
```

Операція перенаправлення викликає системний виклик `truncate()` або `ftruncate()`. Драйвер файлової системи негайно деалокує всі блоки екстентів, повертає їх у глобальний пул суперблока, а показник вільного місця в `df -h` миттєво зростає на 180 ГБ. Процес-демон продовжує безперебійно працювати.

Детальний практичний код емуляції та відновлення наведено у вставці [емулятор витоку відкритого файлу та інструмент відновлення місця](root:unix/disk-space-illusion/proj-space-leak-probe.md).

### Програмування скидання розміру дескриптора на C та C++

Нижче продемонстровано системний підхід до прямого обнулення або вивільнення блоків через дескриптор.

:::tabs
```c
#define _GNU_SOURCE
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
#include <errno.h>

int release_open_file_space(pid_t pid, int target_fd) {
    char proc_path[64];
    snprintf(proc_path, sizeof(proc_path), "/proc/%d/fd/%d", pid, target_fd);

    /* Відкриваємо дескриптор файлу через procfs */
    int fd = open(proc_path, O_WRONLY);
    if (fd < 0) {
        perror("Не вдалося відкрити procfs дескриптор");
        return -1;
    }

    /* Метод 1: Скидання розміру до 0 */
    if (ftruncate(fd, 0) != 0) {
        perror("Помилка ftruncate");
        close(fd);
        return -1;
    }

    /* Метод 2 (альтернатива для сумісних ФС): деалокація блоків через fallocate */
    #ifdef FALLOC_FL_PUNCH_HOLE
    fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, 0, 1024 * 1024 * 1024);
    #endif

    close(fd);
    return 0;
}
```

```cpp
#include <filesystem>
#include <fstream>
#include <string>
#include <system_error>
#include <unistd.h>
#include <fcntl.h>

namespace fs = std::filesystem;

class OpenSpaceRescuer {
public:
    static std::error_code truncate_deleted_fd(pid_t pid, int target_fd) noexcept {
        const std::string proc_path = "/proc/" + std::to_string(pid) + "/fd/" + std::to_string(target_fd);

        int fd = ::open(proc_path.c_str(), O_WRONLY);

            ::close(fd);

        return {};
    }
};
```

## 4. Вичерпання таблиці інодів (`df -i`): невидима катастрофа

Іншою розповсюдженою причиною ілюзії «місце закінчилося, хоча вільні десятки гігабайтів» є вичерпання таблиці дескрипторів інодів.

### Фіксована структура інодів в Ext4

У файлових системах класичної архітектури (ext2, ext3, ext4) простір під вузли метаданих виділяється **один раз на етапі створення файлової системи** (`mkfs.ext4`). За замовчуванням утиліта форматування резервує 1 інод на кожні 16 КіБ дискового простору.

```
СТРУКТУРА РОЗДІЛУ EXT4:
┌─────────────────────┬─────────────────────────────────────────────────┐
│ Таблиця інодів      │ Блоки даних (Data Blocks)                       │
│ (Inode Table)       │                                                 │
│ Фіксована кількість │ Фізичний обсяг у гігабайтах                     │
│ 6 553 600 інодів    │ 100 Гігабайтів                                  │
└─────────────────────┴─────────────────────────────────────────────────┘
```

Якщо на сервері працює сервіс, який генерує мільйони крихітних файлів (наприклад, файли сесій PHP у `/var/lib/php/sessions`, поштова черга Postfix/Maildrop, локальні lock-файли або кеш картинок-тайлів розміром по 50 байтів), кожен такий файл забирає рівно один інод.

Коли 6.5 мільйонів інодів будуть використані:
* Сумарний розмір усіх даних на диску становитиме лише 4 ГБ із 100 ГБ загальної ємності (96 ГБ вільно!).
* Спроба створити будь-який новий файл (`touch new.txt`, `open(..., O_CREAT)`) негайно завершується системною помилкою `ENOSPC` (*No space left on device*).

Команда `df -h` при цьому звітує про 96% вільного місця, вводячи інженера в оману.

![Вичерпання інодів та резерв блоків](/root/course/unix/disk-space-illusion/img/ext4-reserved-blocks-and-inodes.svg)
*Вичерпання таблиці інодів та структура зарезервованого простору суперкористувача.*

### Діагностика через `df -i` та локалізація винуватця

Для перевірки стану інодів використовується спеціальний прапорець `-i`:

```bash
$ df -i /

Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1      6553600 6553600       0  100% /
```

Стовпчик `IFree` дорівнює нулю, а `IUse%` становить 100%.

Щоб знайти каталог, у якому накопичився мільйон дрібних файлів, запускають сканування за кількістю записів:

```bash
# Підрахунок кількості файлів у підкаталогах кореня
$ find /var -xdev -printf '%h\n' | sort | uniq -c | sort -nr | head -n 10

6410291 /var/lib/php/sessions
  12410 /var/spool/postfix/maildrop
   4201 /var/log
```

У наведеному вище лістингу каталог `/var/lib/php/sessions` містить понад 6.4 мільйона файлів, що повністю заблокувало створення нових файлів в усій операційній системі. Очищення цього каталогу через `find /var/lib/php/sessions -type f -delete` повертає іноди в таблицю суперблока й відновлює працездатність серверів.

> 🔧 **Сучасні файлові системи (XFS, Btrfs, ZFS):** На відміну від ext4, файлові системи XFS, Btrfs та ZFS використовують динамічне виділення інодів (B-дерева метаданих). У них іноди створюються динамічно в загальному пулі блоків, тому проблема вичерпання `df -i` окремо від байтів практично відсутня.

## 5. Пастка точок монтування (Over-Mounting): приховані гігабайти

Ще один витончений сценарій виникнення ілюзії браку місця — повторне або перекривальне монтування файлових систем поверх непорожніх каталогів (*over-mounting* або *mount occlusion*).

### Механізм затінення каталогу

Припустімо, на кореневому розділі `/dev/nvme0n1p2` було створено каталог `/mnt/storage`. Системний скрипт або адміністратор записав туди резервну копію бази даних `backup.tar` розміром 60 ГБ.

Після цього було підключено зовнішній диск `/dev/sdb1` і змонтовано його у ту саму точку:

```bash
# Монтування нового накопичувача поверх каталогу з даними
$ mount /dev/sdb1 /mnt/storage
```

Підсистема VFS ядра перемикає розбір шляху: під час розв'язання імені функція `lookup_fast()` виявляє, що об'єкт `struct dentry` для каталогу `/mnt/storage` позначений системним прапорцем `DCACHE_MOUNTED`. Ядро автоматично перемикає контекст обходу на кореневий `dentry` змонтованої структури `struct vfsmount` накопичувача `/dev/sdb1`.

```
КОРЕНЕВИЙ РОЗДІЛ (/dev/nvme0n1p2)          ЗМОНТОВАНИЙ ДИСК (/dev/sdb1)
┌────────────────────────────────┐         ┌────────────────────────────────┐
│ Каталог /mnt/storage/          │         │ Корінь /dev/sdb1               │
│ ├── backup.tar (60 ГБ)         │         │ ├── data.bin (2 МБ)            │
│ [ЗАХОВАНО ПІД ТОЧКОЮ МОНТУВАННЯ]         └───────────────▲────────────────┘
└────────────────────────────────┘                         │
                                                           │ (VFS перенаправляє шлях)
Шлях у системі: /mnt/storage ──────────────────────────────┘
```

Що відбувається з показниками:
1. **Команда `df -h /`:** показує, що кореневий розділ містить 60 ГБ зайнятого місця. Суперблок кореневої ФС знає про виділені блоки і не відпускає їх.
2. **Команда `du -sh /mnt/storage`:** заходить у новий змонтований диск `/dev/sdb1` і бачить там лише кілька мегабайтів.
3. **Команда `du -sh /*`:** сканує всю систему, але оскільки `/mnt/storage` перекрито новим монтуванням, 60 ГБ файлу `backup.tar` стають повністю невидимими для обходу!

Інженер бачить, що корінь переповнений, але рекурсивний `du` по всій системі показує на 60 ГБ менше, ніж `df`.

![Приховування даних під точкою монтування](/root/course/unix/disk-space-illusion/img/mount-point-occlusion.svg)
*Затінення дискового простору при повторному монтуванні поверх непорожнього каталогу.*

### Методика виявлення та доступу через прив'язне монтування

Щоб отримати доступ до прихованих під точкою монтування даних без розмонтування робочого диска (який може прямо зараз використовуватися активними клієнтами), застосовують механізм прив'язного монтування (*bind mount*) самого кореня системи:

```bash
# 1. Створюємо тимчасову точку доступу
# mkdir /mnt/inspect_root

# 2. Виконуємо bind mount кореневої файлової системи
# mount --bind / /mnt/inspect_root

# 3. Скануємо вміст каталогу БЕЗ накладених монтувань
# du -sh /mnt/inspect_root/mnt/storage
60G    /mnt/inspect_root/mnt/storage

# 4. Видаляємо прихований файл
# rm /mnt/inspect_root/mnt/storage/backup.tar

# 5. Прибираємо тимчасове монтування
# umount /mnt/inspect_root
# rmdir /mnt/inspect_root
```

Після видалення прихованого файлу через прив'язне монтування блоки на кореневому розділі негайно вивільняються, і розбіжність між `df` та `du` зникає.

## 6. Зарезервовані блоки суперкористувача: чому 95% означає 100%

Остання фундаментальна причина розбіжності між фізично вільними байтами та реальною доступністю простору для застосунків — механізм резервування блоків суперкористувача (*reserved root blocks*).

### Навіщо потрібен резерв

За замовчуванням під час створення файлових систем ext2/3/4 утиліта `mkfs` резервує **5% від загального обсягу дисків** виключно для використання обліковим записом `root` (UID 0) або спеціальною групою.

Це резервування вирішує дві критичні задачі:
1. **Запобігання фрагментації:** коли файлова система заповнюється понад 90–95%, драйверу розміщення екстентів стає надзвичайно важко знаходити суміжні безперервні ланцюжки вільних блоків. Продуктивність запису деградує, а фрагментація стрімко зростає.
2. **Аварійний запас для системних демонів:** якщо користувацький застосунок (наприклад, веб-сервер або торент-клієнт) повністю заб'є диск логами чи завантаженнями, системні служби (`sshd`, `syslogd`, `cron`) зможуть продовжити роботу, а адміністратор зможе успішно авторизуватися по SSH, щоб ліквідувати аварію.

### Розрив між `f_bfree` та `f_bavail`

У структурі `struct statvfs` поле `f_bfree` відображає абсолютну кількість фізично вільних блоків, тоді як поле `f_bavail` — лише блоки, доступні звичайним користувачам.

```
СТРУКТУРА ЄМНОСТІ EXT4:
┌────────────────────────────────────────────────────────┬─────────────┐
│ Доступно для застосунків (f_bavail)                    │ Резерв root │
│ 95% обсягу диска                                       │ 5% обсягу   │
└────────────────────────────────────────────────────────┴─────────────┘
                                                         ▲
                                                         │
Користувацький процес отримує ENOSPC тут ────────────────┘
```

Коли дисковий розділ заповнюється на 95%, значення `f_bavail` падає до нуля. Будь-який процес, запущений не від користувача `root` (наприклад, `postgres`, `nginx`, `node`), отримує фатальну помилку `ENOSPC`, хоча на диску фізично залишається ще 5% вільного простору.

### Тюнінг резерву на великих дисках через `tune2fs`

У 1990-х роках, коли розмір типового диска становив 2 Гігабайти, резерв у 5% (100 МБ) був цілком розумним і виправданим. Проте на сучасному серверному накопичувачі ємністю 16 Терабайтів резерв 5% марнує **800 Гігабайтів** дорогого простору NVMe або SSD-масиву!

Для окремих розділів даних (особливо тих, де не живуть системні демони) відсоток резерву зменшують за допомогою утиліти `tune2fs`:

```bash
# Зменшити резерв до 1% на розділі даних
# tune2fs -m 1 /dev/sdb1

# Повністю вимкнути резерв (0%) для розділу /var/lib/data
# tune2fs -m 0 /dev/sdb1

# Встановити фіксований резерв у блоках (наприклад, 250 000 блоків по 4 КіБ = 1 ГіБ)
# tune2fs -r 250000 /dev/sdb1
```

Зміна налаштувань набуває чинності миттєво в суперблоці без необхідності розмонтування чи перезавантаження системи.

## 7. Взаємодія з дисковими квотами та розрідженими файлами

Ще два неочевидні механізми ядра здатні викликати хибне враження переповнення диска: підсистема дискових квот (*disk quotas*) та робота з розрідженими файлами (*sparse files*).

### Дискові квоти: локальний ліміт замість фізичного

Якщо на файловій системі ввімкнено облік квот за користувачами або групами (`usrquota`, `grpquota`), ядро обмежує кількість блоків та інодів для кожного UID окремо від глобальної ємності суперблока.

У разі вичерпання персональної квоти системний виклик `write()` або `open(..., O_CREAT)` завершується помилкою `EDQUOT` (*Disk quota exceeded*), яка на рівні багатьох бібліотек користувацького простору транслюється в повідомлення `No space left on device`. Утиліти `df -h` та `df -i` показують десятки гігабайтів вільного місця, оскільки суперблок не заповнений, проте процес не може записати жодного байта. Перевірка здійснюється утилітою `quota -v` або `repquota -a`.

### Розріджені файли та вичерпання відкладеного виділення

У файлових системах із підтримкою відкладеного виділення (*delayed allocation*, `delalloc` в ext4 та XFS) ядро не виділяє фізичні блоки в момент системного виклику `write()`, а лише резервує сторінки в кеші сторінок (*page cache*). Фізичне виділення екстентів відбувається пізніше, під час скидання брудних сторінок фоновим демоном запису (*flusher thread*).

Якщо на диску залишається мало вільного місця, а кілька процесів паралельно створюють великі розріджені файли через `lseek()` та `write()`, виклик `write()` завершується успішно, повертаючи нульовий код помилки. Проте наступний виклик `fsync()` або автоматичне фонове скидання раптово стикається з відсутністю реальних блоків у суперблоці. Процес отримує асинхронну помилку `ENOSPC`, а дані в кеші сторінок можуть бути скинуті з помилкою вводу-виводу.

## 8. Чекліст системного розслідування аварії `ENOSPC`

Коли на виробничому сервері спрацьовує сповіщення про вичерпання дискового простору, розслідування здійснюється за чітким покроковим алгоритмом:

```
                          АВАРІЯ: ENOSPC (No space left on device)
                                             │
                                             ▼
                             ┌───────────────────────────────┐
                             │ Перевірка df -h та df -i      │
                             └───────────────┬───────────────┘
                                             │
                     ┌───────────────────────┴───────────────────────┐
                     ▼                                               ▼
         ┌───────────────────────┐                       ┌───────────────────────┐
         │ df -i показує 100%    │                       │ df -h показує 100%    │
         │ (Вичерпано іноди)     │                       │ (Вичерпано байти)     │
         └───────────┬───────────┘                       └───────────┬───────────┘
                     │                                               │
                     ▼                                               ▼
         ┌───────────────────────┐                       ┌───────────────────────┐
         │ Пошук мільйона файлів │                       │ Порівняння: df vs du  │
         │ find / -type d ...    │                       └───────────┬───────────┘
         └───────────────────────┘                                   │
                                             ┌───────────────────────┴───────────────────────┐
                                             ▼                                               ▼
                                 ┌───────────────────────┐                       ┌───────────────────────┐
                                 │ du ≈ df (файли видно) │                       │ du << df (розбіжність)│
                                 └───────────┬───────────┘                       └───────────┬───────────┘
                                             │                                               │
                                             ▼                       ┌───────────────────────┴───────────────────────┐
                                 ┌───────────────────────┐           ▼                                               ▼
                                 │ Звичайний лог-файл    │ ┌───────────────────┐                         ┌───────────────────┐
                                 │ Очищення / ротація    │ │ lsof +L1          │                         │ Bind-mount кореня │
                                 └───────────────────────┘ │ (Видалені відкриті)│                         │ (Over-mounting)   │
                                                           └─────────┬─────────┘                         └─────────┬─────────┘
                                                                     │                                             │
                                                                     ▼                                             ▼
                                                           ┌───────────────────┐                         ┌───────────────────┐
                                                           │ > /proc/$PID/fd/$FD│                        │ Видалення прихован│
                                                           └───────────────────┘                         └───────────────────┘
```

1. **Крок 1: Оцінка інодів проти байтів.**
   Запустити `df -h` та `df -i`. Якщо `IUse%` становить 100%, локалізувати каталог із мільйоном сесій чи дрібних повідомлень черги через `find . -xdev -printf '%h\n' | sort | uniq -c | sort -nr | head`.
2. **Крок 2: Зіставлення `df` та `du`.**
   Запустити `du -sh -x /*` (прапорець `-x` / `--one-file-system` обов'язковий, щоб не переходити на інші точки монтування). Якщо сума `du` відповідає показникам `df`, знайти великі каталоги та видалити старі логи чи архіви.
3. **Крок 3: Пошук видалених відкритих файлів.**
   Якщо `du` показує значно менше зайнятого місця, ніж `df`, виконати `lsof +L1 /точка_монтування` або `ls -l /proc/*/fd/* 2>/dev/null | grep '(deleted)'`. Звільнити місце на льоту за допомогою `: > /proc/[pid]/fd/[fd]`.
4. **Крок 4: Перевірка прихованих монтувань.**
   Якщо `lsof +L1` не дав результату, виконати тимчасовий прив'язний монтаж `mount --bind / /mnt/inspect_root` і перевірити вміст каталогів, які слугують точками монтування.
5. **Крок 5: Аудит резерву суперкористувача.**
   Перевірити стан резерву суперкористувача через `tune2fs -l /dev/sdX | grep "Reserved"`. За потреби зменшити відсоток резерву на накопичувачах великої ємності через `tune2fs -m 1`.
