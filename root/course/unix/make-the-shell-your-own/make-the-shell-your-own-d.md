Коли інженер уперше відкриває термінальне вікно на свіжовстановленій операційній системі або підключається до віддаленого сервера через SSH, він потрапляє у спартанське середовище: рядок підказки виглядає як монохромний `bash-5.2$ `, автодоповнення по клавіші Tab чутливе до регістру літер і вимагає подвійного натискання, стрілки вгору та вниз безладно перебирають команди без урахування набраного контексту, а історія команд із сусіднього вікна безслідно зникає після закриття сеансу. При спробі самостійно додати кольори до рядка запрошення довгі команди несподівано ламають перенесення тексту, затираючи початок рядка, а створення десятків неструктурованих аліасів у монолітному файлі перетворює конфігурацію на крихку систему, де будь-яка помилка блокує запуск оболонки.

Цей аскетизм — не недогляд розробників, а прямий наслідок вимог зворотного суміщення зі стандартами POSIX сорокарічної давнини. Оболонка за замовчуванням орієнтується на мінімальний спільний знаменник апаратних терміналів кінця 1970-х років. Проте інтерактивна оболонка — це головне робоче місце розробника та системного адміністратора в Unix. Мета професійного налаштування полягає не в декоративному розфарбовуванні інтерфейсу, а в побудові швидкого, передбачуваного та надійного інженерного середовища. Щоб досягти цього, необхідно розуміти кожен системний шар: порядок зчитування файлів конфігурації, дисципліну взаємодії з бібліотекою GNU Readline, фізику буферизації історії команд та правила модульної організації конфігурацій.

## Карта запуску та життєвий цикл конфігураційних файлів

Поведінка командної оболонки під час запуску визначається двома незалежними бінарними осями: чи є оболонка **стартовою для сеансу** (`Login Shell` проти `Non-Login Shell`), та чи працює вона в **інтерактивному режимі** (`Interactive` проти `Non-Interactive`). Комбінація цих станів визначає, які саме конфігураційні файли читатимуться з диска та в якій послідовності.

```
                  ┌───────────────────────────────┐
                  │ Запуск процесу оболонки: bash │
                  └───────────────┬───────────────┘
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
        [ Стартова: Login ]             [ Вторинна: Non-Login ]
        argv[0][0] == '-'               argv[0][0] != '-'
        (Консоль, SSH, macOS)           (Вкладка GUI, tmux)
                  │                               │
                  ├────────────────────────┐      │
                  ▼                        ▼      ▼
            /etc/profile            /etc/bash.bashrc (Debian)
                  │                               │
                  ▼                               ▼
       ~/.bash_profile / ~/.profile            ~/.bashrc
                  │                               │
                  ▼                               │
              ~/.bashrc ◄─────────────────────────┘
```

### Механізм ідентифікації стартової оболонки (Login Shell)

Стартова оболонка створюється при первинній автентифікації користувача в операційній системі. Це відбувається під час входу через текстову віртуальну консоль Linux, віддаленого підключення через демон `sshd`, запуску сеансу через `su - username`, або при відкритті будь-якого нового термінального вікна в macOS (де емулятор Terminal.app за замовчуванням запускає кожну вкладку як login shell).

Ознакою стартової оболонки для ядра та програми є конвенція передачі аргументів системного виклику `execve(2)`. Програма автентифікації (`/bin/login` або `sshd`) формує нульовий аргумент `argv[0]`, додаючи символ дефіса першим байтом імені виконуваного файлу — наприклад, `-bash` або `-zsh`. Побачивши дефіс у позиції `argv[0][0]`, двійковий файл оболонки переходить у режим ініціалізації сеансу. Альтернативно цей режим можна викликати явно, передавши прапорець `-l` або `--login`.

Нижче наведено приклад коду, що демонструє, як процес системної утиліти або власної оболонки перевіряє наявність ознаки login shell та підключення до інтерактивного термінала через системні виклики POSIX.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    // 1. Перевірка наявності дефіса на початку argv[0]
    int is_login = (argc > 0 && argv[0] != NULL && argv[0][0] == '-');

    // 2. Перевірка підключення стандартного потоку вводу до TTY
    int is_interactive = isatty(STDIN_FILENO);

    printf("Ідентифікація оболонки:\n");
    printf("  argv[0]         = %s\n", (argc > 0 && argv[0]) ? argv[0] : "(null)");
    printf("  Login Shell     = %s\n", is_login ? "ТАК (ініціалізація сеансу)" : "НІ (вторинний процес)");
    printf("  Interactive     = %s\n", is_interactive ? "ТАК (підключено до термінала)" : "НІ (виконання скрипта)");

    return 0;
}
```
```cpp

#include <string_view>

    // 2. Перевірка підключення стандартного потоку вводу до TTY
```

### Послідовність зчитування конфігураційних файлів Bash

Поведінка Bash строго регламентована залежно від типу запуску:

1. **Login Interactive Shell (Стартова інтерактивна оболонка):**
   - Спершу зчитується системний файл `/etc/profile`. У ньому задаються загальносистемні обмеження ресурсів, базовий `$PATH` та виконуються допоміжні скрипти з каталогу `/etc/profile.d/*.sh`.
   - Далі оболонка шукає перший наявний користувацький файл із трьох можливих варіантів: `~/.bash_profile`, `~/.bash_login` та `~/.profile`. Пошук зупиняється на **першому знайденому файлі**, решта два повністю ігноруються. Якщо у вашому домашньому каталозі одночасно існують `~/.bash_profile` та `~/.profile`, оболонка виконає лише `~/.bash_profile`.
   - Під час завершення роботи стартової оболонки (виконання команди `exit` або розрив сеансу) зчитуються файли `~/.bash_logout` та загальносистемний `/etc/bash.bash_logout`.

2. **Non-Login Interactive Shell (Вторинна інтерактивна оболонка):**
   - Це найпоширеніший режим: відкриття нової вкладки в емуляторах GNOME Terminal, Alacritty, Kitty або створення нового вікна всередині мультиплексора `tmux`.
   - Оболонка **не читає** `/etc/profile` та файли `profile` користувача.
   - У дистрибутивах родини Debian та Ubuntu зчитується системний файл `/etc/bash.bashrc`.
   - Після цього виконується головний користувацький конфігураційний файл `~/.bashrc`.

3. **Non-Interactive Shell (Неінтерактивний запуск сценаріїв):**
   - Виникає при виконанні bash-скриптів (`#!/bin/bash`) або при запуску команди через `ssh host 'command'`.
   - Оболонка не читає ані `profile`, ані `bashrc`. Вона перевіряє лише значення змінної середовища `$BASH_ENV`: якщо змінна містить шлях до файлу, Bash зчитує його перед початком виконання команд сценарію.

### Порівняння з моделлю завантаження Zsh

Оболонка Zsh, яка стала стандартною в macOS та багатьох сучасних дистрибутивах, використовує іншу, більш розгалужену послідовність завантаження файлів:

1. `/etc/zshenv` та `~/.zshenv` — зчитуються **завжди, для абсолютно всіх типів запусків**, включно з неінтерактивними скриптами.
2. `/etc/zprofile` та `~/.zprofile` — виконуються лише для Login Shell перед запуском інтерактивних компонентів.
3. `/etc/zshrc` та `~/.zshrc` — виконуються для всіх інтерактивних оболонок.
4. `/etc/zlogin` та `~/.zlogin` — виконуються для Login Shell на самомуприкінці ініціалізації.
5. `~/.zlogout` та `/etc/zlogout` — виконуються при завершенні сеансу.

Критична пастка у Zsh пов'язана з файлом `~/.zshenv`: оскільки він виконується навіть для фонових викликів через SSH (`ssh host 'command'`) та протоколів передачі файлів на кшталт `scp` і `rsync`, у ньому категорично заборонено друкувати будь-який текст або ініціалізувати промпти. Будь-який вивід у потік `stdout` всередині `~/.zshenv` миттєво ламає парсер протоколу SFTP/SCP.

### Архітектурний розподіл: чому змінні належать profile, а функції — bashrc

Найпоширеніша помилка початківців — звалювання всіх параметрів у випадковий конфігураційний файл. Це призводить або до дублювання важких операцій під час відкриття кожного вікна, або до ситуації, коли запущена з меню графічна програма не бачить шляхів до встановлених компіляторів.

Розподіл базується на фундаментальній властивості моделі процесів Unix: **успадкуванні пам'яті через системний виклик fork-exec**.

Таблиця змінних середовища процесу (`char **environ`) зберігається в адресному просторі процесу і при виклику `execve(2)` автоматично копіюється ядром у пам'ять нової програми. Якщо змінну оголошено та експортовано через `export VAR="value"` у стартовому файлі `~/.profile`, вона записується в середовище кореневого сеансу користувача. Усі наступні процеси — графічні менеджери, редактори, браузери та дочірні термінали — успадковують цю змінну безкоштовно, без необхідності повторного виконання коду.

На противагу цьому, внутрішні структури самої оболонки — таблиці аліасів (`alias`), визначення функцій, налаштування опцій парсера (`shopt`) та прив'язки клавіш Readline — **не передаються через execve(2)**. Вони існують виключно всередині пам'яті конкретного процесу Bash. Тому кожен новий процес інтерактивної оболонки мусить заново зчитати `~/.bashrc`, щоб ініціалізувати власні внутрішні структури.

> 🔧 **Золоте правило організації конфігурацій:**
> - **У `~/.profile` або `~/.bash_profile`:** розміщуються глобальні змінні середовища (`export PATH`, `export EDITOR`, `export LANG`), налаштування маски створення файлів `umask` та одноразові агенти автентифікації (`ssh-agent`).
> - **У `~/.bashrc`:** розміщуються аліаси, функції оболонки, налаштування рядка підказки `$PS1`, прапорці `shopt`, прив'язки клавіш та налаштування автодоповнення.
> - Щоб стартова оболонка також отримувала аліаси та функції, на початку `~/.bash_profile` обов'язково розміщують блок підключення:
>   ```bash
>   if [ -f "$HOME/.bashrc" ]; then
>       . "$HOME/.bashrc"
>   fi
>   ```

## Керування історією команд: багатосесійний конвеєр без втрат

Історія виконаних команд — це зовнішня пам'ять інженера. Швидкий пошук складної команди компіляції, параметрів `gdb` або конвеєра діагностики рятує години роботи. Проте за замовчуванням підсистема історії Bash налаштована вкрай небезпечно для повсякденної багатозадачності.

### Проблема затирання історії (Last Closed Terminal Wins)

Підсистема історії Bash оперує двома різними сховищами:
1. Кільцевий буфер в оперативній пам'яті поточного процесу оболонки, максимальний розмір якого задається змінною `HISTSIZE`.
2. Дисковий файл `~/.bash_history`, максимальний розмір якого визначається змінною `HISTFILESIZE`.

За замовчуванням, коли користувач відкриває кілька термінальних вікон (наприклад, вікна A, B і C), кожен процес Bash зчитує початковий стан `~/.bash_history` у свій локальний буфер. Під час роботи команди записуються лише в оперативну пам'ять відповідного процесу. Коли користувач закриває вікно, Bash виконує системний виклик `open("~/.bash_history", O_WRONLY | O_CREAT | O_TRUNC)`. Це означає, що процес **повністю очищає та перезаписує дисковий файл** вмістом своєї локальної пам'яті.

Якщо у вікні A ви цілий день налагоджували серверну частину, а у вікні B виконали три команди й закрили його останнім, вікно B безповоротно затре всі результати роботи вікна A.

![Синхронізація історії команд між термінальними вікнами](/root/course/unix/make-the-shell-your-own/img/history-sync-flow.svg)
*Модель атомарного скидання та зчитування історії між паралельними процесами оболонки через системний хук PROMPT_COMMAND*

### Налаштування надійного збереження та дедуплікації

Щоб унеможливити втрату даних, необхідно змінити логіку роботи з дисковим файлом та збільшити ліміти збереження в `~/.bashrc`:

```bash
# 1. Збільшення розміру буфера пам'яті та дискового файлу
export HISTSIZE=50000
export HISTFILESIZE=100000

# 2. Перемикання з режиму перезапису на режим дописування (O_APPEND)
shopt -s histappend

# 3. Багаторядкові команди зберігаються як один запис історії
shopt -s cmdhist

# 4. Фіксація часових міток виконання (РРРР-ММ-ДД ГГ:ХХ:СС)
export HISTTIMEFORMAT="%F %T "

# 5. Керування дублікатами та чутливими даними
export HISTCONTROL="ignoreboth:erasedups"

# 6. Ігнорування тривіальних та навігаційних команд
export HISTIGNORE="ls:ll:la:cd:pwd:exit:history:clear:bg:fg"
```

Розберемо значення ключових прапорців:
- `shopt -s histappend` змушує процес оболонки відкривати файл із прапорцем ядра `O_APPEND`. Нові записи дописуються в кінець файлу, не знищуючи чужі дані.
- `HISTTIMEFORMAT="%F %T "` записує час виконання кожної команди. На диску у файлі `~/.bash_history` це кодується спеціальним рядком-коментарем з Unix Epoch Timestamp перед самою командою:
  ```text
  #1724601240
  make build -j8
  #1724601285
  ./bin/server --config=dev.yaml
  ```
  Бібліотека Readline розпізнає ці рядки як метадані та автоматично фільтрує їх при відображенні історії користувачеві.
- `HISTCONTROL="ignoreboth:erasedups"` об'єднує дві критичні поведінки:
  * `ignorespace`: якщо рядок починається з символу пробілу, він **не потрапляє до історії**. Це стандартний спосіб безпечного введення команд із паролями або токенами (` export SECRET=xyz`).
  * `ignoredups`: ігнорує запис команди, якщо вона ідентична безпосередньо попередній команді.
  * `erasedups`: сканує весь буфер історії і, якщо команда вже виконувалася раніше, видаляє її старі екземпляри, залишаючи лише найсвіжіший запис наприкінці. Це запобігає роздуванню файлу тисячами однакових команд `git status`.

### Миттєва синхронізація в реальному часі

Навіть із `histappend` команди потрапляють на диск лише в момент завершення роботи сеансу. Якщо ви виконали команду у вікні A, вікно B не побачить її, доки вікно A не буде закрите.

Рішення полягає в примусовій синхронізації історії перед кожним відображенням рядка підказки через спеціальну змінну Bash `PROMPT_COMMAND`:

```bash
# Синхронізація історії перед кожним виводом промпта
_sync_history() {
    builtin history -a    # 1. Скинути нові рядки з пам'яті в кінець дискового файлу
    builtin history -c    # 2. Очистити локальний буфер пам'яті
    builtin history -r    # 3. Перечитати весь дисковий файл у свіжий буфер пам'яті
}

PROMPT_COMMAND="_sync_history; ${PROMPT_COMMAND:-}"
```

Як це працює на рівні системних викликів:
1. Коли ви натискаєте Enter і виконуєте команду в терміналі 1, команда завершується.
2. Перед тим як знову показати рядок підказки, Bash викликає функцію з `PROMPT_COMMAND`.
3. Команда `history -a` бере тільки нові команди, додані з моменту останнього скидання, і виконує системний виклик `write(2)` у файл `~/.bash_history`.
4. Коли ви перемикаєтесь у термінал 2 і натискаєте Enter (або виконуєте будь-яку дію), його `PROMPT_COMMAND` очищає старий локальний буфер (`history -c`) і перечитує весь оновлений файл з диска (`history -r`).
5. Натискання стрілки «Вгору» в терміналі 2 миттєво підставляє команду, яку ви щойно набрали в терміналі 1.

Чи створює це суттєве навантаження на диск? Ні. Завдяки сторінковому кешу операційної системи (`Page Cache` у ядрі Linux), файл `~/.bash_history` розміром у кілька мегабайтів постійно перебуває в оперативній пам'яті ядра. Системний виклик `read(2)` для такого файлу виконується за мікросекунди без реальних звернень до фізичного накопичувача SSD.

## Бібліотека GNU Readline: точка контакту клавіатури й оболонки

Усі операції з посимвольним набором тексту, переміщенням курсора, вставкою слів та автодоповненням виконуються не кодом самої оболонки Bash, а підключеною бібліотекою **GNU Readline**. Ця ж бібліотека обслуговує інтерпретатори Python, клієнти баз даних `psql` і `sqlite3`, та зневаджувач `gdb`.

Налаштування Readline виконуються в глобальному файлі конфігурації `~/.inputrc`. Перевага налаштування саме цього файлу полягає в тому, що всі покращення введення починають автоматично діяти в усіх програмах одночасно.

![Архітектура GNU Readline та розрахунок ширини промпта](/root/course/unix/make-the-shell-your-own/img/readline-architecture.svg)
*Обробка вхідного потоку клавіш бібліотекою Readline та вплив маркерів нульової ширини на коректність перенесення рядків*

### Взаємодія з шаром TTY та сирий режим введення

Коли оболонка очікує введення команди, вона переводить керівний псевдотермінал у так званий неканонічний, або «сирий» режим введення (`RAW mode`) за допомогою виклику `tcsetattr(3)` над структурою `termios`.

У стандартному канонічному режимі дисципліна лінії ядра накопичує символи в системному буфері й віддає їх програмі лише після натискання Enter, самостійно обробляючи клавіші Backspace або переривання `Ctrl+C`. У сирому режимі дисципліна лінії вимикає прапорці `ICANON`, `ECHO` та налаштовує параметри `VMIN=1, VTIME=0`. Це означає, що кожен натиснутий байт або керуюча послідовність негайно надходить у процес програми.

Readline перехоплює цей потік байтів, зіставляє його з активним деревом прив'язок клавіш (`keymap`) та перемальовує рядок термінала через команди переміщення курсора ANSI VT100.

Крім того, сучасні версії Readline за замовчуванням вмикають режим безпечної вставки (`Bracketed Paste Mode`). При вставці багаторядкового тексту з буфера обміну емулятор термінала обрамляє вставлені дані спеціальними кодами `\033[200~` на початку та `\033[201~` наприкінці. Readline перехоплює ці маркери й тимчасово блокує виконання символів нового рядка (LF), перетворюючи їх на м'які перенесення рядків усередині буфера редагування. Це повністю нівелює класичну атаку «paste-jacking», коли шкідливий вебсайт підсовує у буфер обміну команду `rm -rf /` із прихованим символом завершення рядка.

### Вибір режиму редагування: Emacs проти Vi

Readline підтримує дві кардинально різні філософії взаємодії з текстом:
1. **Режим Emacs (за замовчуванням):** безмодальне редагування. Кожна комбінація з клавішами `Ctrl` або `Alt` виконує пряму дію:
   - `Ctrl+A` / `Ctrl+E` — стрибок на початок / кінець рядка.
   - `Alt+F` / `Alt+B` — переміщення вперед / назад на одне слово.
   - `Ctrl+K` — видалення (вирізання) тексту від курсора до кінця рядка в кільцевий буфер (`Kill Ring`).
   - `Ctrl+U` — повне очищення рядка.
   - `Ctrl+W` — видалення слова ліворуч від курсора.
   - `Ctrl+Y` — вставка останнього видаленого фрагмента з буфера (`yank`).

2. **Режим Vi (`set editing-mode vi`):** повноцінний модальний автомат, ідентичний текстовому редактору Vim. Оболонка стартує в режимі вставки (`Insert Mode`), а натискання клавіші `Escape` переводить рядок у командний режим (`Command Mode`), де клавіші `h`, `j`, `k`, `l`, `w`, `b`, `d$`, `cw` працюють як стандартні оператори навігації та маніпуляції текстом Vim.

Для повноцінної роботи у режимі Vi у файл `~/.inputrc` додають візуальну зміну форми курсора, щоб наочно бачити поточний стан модального автомата:

```text
# ~/.inputrc
set editing-mode vi
set keyseq-timeout 15
set show-mode-in-prompt on

# \e[2 q — суцільний прямокутний блок для командного режиму
# \e[6 q — тонка вертикальна риска для режиму вставки
set vi-cmd-mode-string "\1\e[2 q\2"
set vi-ins-mode-string "\1\e[6 q\2"
```

### Продуктивне автодоповнення

Стандартна поведінка автодоповнення вимагає подвійного натискання Tab і не вміє зіставляти файли, якщо користувач помилився з великою чи малою літерою. Наступні директиви усувають ці незручності:

```text
# ~/.inputrc — Оптимізація автодоповнення

# Ігнорування регістру символів при пошуку збігів
set completion-ignore-case on

# Виведення списку варіантів при першому натисканні Tab
set show-all-if-ambiguous on

# Кольорове підсвічування типів файлів у списку за $LS_COLORS
set colored-stats on

# Виділення набраного префікса іншим кольором
set colored-completion-prefix on

# Додавання скісної риски до символічних посилань на каталоги
set mark-symlinked-directories on

# Поріг запиту на виведення великої кількості варіантів
set completion-query-items 200

# Циклічний перебір варіантів доповнення у зворотний бік на Shift+Tab
"\e[Z": menu-complete-backward
```

### Префіксний інкрементальний пошук

Найбільш продуктивне покращення навігації — прив'язка функцій `history-search-backward` та `history-search-forward` на стрілки керування курсором «Вгору» та «Вниз».

За замовчуванням стрілка «Вгору» тупо перебирає всі попередні команди підряд. Функція префіксного пошуку працює інакше: вона аналізує текст, який ви вже встигли надрукувати в рядку, і шукає в історії **виключно ті команди, які починаються з цього тексту**.

Наприклад, якщо ви ввели `ssh ` і натиснули стрілку «Вгору», Readline покаже лише попередні виклики `ssh server1`, `ssh root@node5` тощо, пропускаючи сотні інших проміжних команд `ls` чи `git`.

```text
# ~/.inputrc — Префіксний пошук на стрілках
"\e[A": history-search-backward
"\e[B": history-search-forward
```

Повний системний довідник усіх змінних, функцій маніпуляції текстом, синтаксису умовних блоків `$if` та кодів клавіш детально викладено у спеціальній довідковій вставці [довідник директив GNU Readline](root:unix/make-the-shell-your-own/api-readline-config.md).

## Анатомія командного рядка $PS1: колір без графічних артефактів

Змінна `$PS1` (`Prompt String 1`) визначає зовнішній вигляд основного рядка запрошення до вводу. За замовчуванням Bash підтримує набір спеціальних керуючих послідовностей:
- `\u` — ім'я поточного користувача.
- `\h` — коротке ім'я хоста (до першої крапки).
- `\w` — поточний робочий каталог (з заміною домашнього каталогу на `~`).
- `\W` — тільки базова назва поточного каталогу.
- `\$` — символ `#` для суперкористувача root (`UID == 0`) або символ `$` для звичайного користувача.
- `\t` / `\A` — поточний час у 24-годинному форматі.

### Механізм розрахунку ширини та катастрофа відсутності екранування

Головна пастка під час додавання кольорів до `$PS1` полягає в тому, як дисплейний рушій Readline (`rl_redisplay`) розраховує довжину рядка на екрані.

Коли ви фарбуєте текст за допомогою коду ANSI, наприклад зеленого кольору `\033[32m`, ви відправляєте терміналу послідовність із 5 байтів (`ESC`, `[`, `3`, `2`, `m`). Термінал інтерпретує цю команду, змінює колір шрифту і **не займає жодної видимої колонки на екрані**.

Однак бібліотека Readline нічого не знає про графічні можливості термінала: вона підраховує довжину рядка просто як кількість символів у буфері рядка. Якщо ці керуючі байти не екранувати, Readline вважатиме, що промпт займає на 5 колонок більше, ніж він є насправді.

```
Помилковий рядок: PS1="\033[32m\u@\h\033[0m$ "
Видима ширина на екрані:  user@host$  (10 колонок)
Розрахунок Readline:      5 + 9 + 4 + 2 = 20 колонок (помилка на +10 колонок!)
```

Наслідки помилки розрахунку ширини катастрофічні:
1. При наборі довгої команди перенесення тексту на новий рядок відбувається задовго до досягнення правого краю вікна.
2. При редагуванні тексту всередині рядка курсор перескакує на хибну фізичну позицію, затираючи вже надруковані символи або залишаючи графічні артефакти.
3. Клавіші `Home`, `End` та пошук `Ctrl+R` спотворюють вивід рядка.

Щоб виправити це, **кожна керуюча невидима послідовність повинна бути обгорнута в маркери `\[` та `\]`**:
- `\[` (байт `\001` або константа `RL_PROMPT_START_IGNORE`) сигналізує Readline: «Початок невидимих символів нульової ширини».
- `\]` (байт `\002` або константа `RL_PROMPT_END_IGNORE`) сигналізує Readline: «Кінець невидимих символів».

```bash
# ❌ КАТАСТРОФА: Readline ламає перенесення рядків
PS1="\033[32m\u@\h\033[0m:\033[34m\w\033[0m\$ "

# ✓ ПРАВИЛЬНО: Усі ANSI-коди ізольовані маркерами \[ та \]
PS1="\[\033[32m\]\u@\h\[\033[0m\]:\[\033[34m\]\w\[\033[0m\]\$ "
```

### Інтеграція керуючих послідовностей OSC 7 та заголовка вікна

Сучасні емулятори терміналів підтримують спеціальні протоколи зв'язку через послідовності `OSC` (`Operating System Command`).

Зокрема, послідовність `OSC 7` передає терміналу поточний робочий каталог у форматі URL `\033]7;file://hostname/path\033\\`. Це дозволяє графічному терміналу автоматично відкривати нові вкладки в тому самому каталозі, де ви зараз працюєте, навіть якщо сесія запущена всередині SSH або контейнера. Послідовність `OSC 0` (`\033]0;title\007`) динамічно оновлює текст на вкладці вікна термінала.

Оскільки ці послідовності також не займають місця на екрані, вони обов'язково обрамляються в `\[` та `\]`.

### Дворядковий промпт із Git-статусом

Для комфортної щоденної розробки рекомендується використовувати дворядкову структуру промпта. Перший рядок містить повну інформацію про оточення (час, хост, повний шлях та гілку Git), а власне ввід команди починається з нового рядка біля лівого краю. Це залишає максимальний горизонтальний простір для довгих команд.

```bash
# ~/.config/bash/30-prompt.bash

_git_branch() {
    local ref
    ref=$(git symbolic-ref --short HEAD 2>/dev/null || git rev-parse --short HEAD 2>/dev/null)
    if [ -n "$ref" ]; then
        local dirty=""
        # Перевірка наявності не зафіксованих змін
        [ -n "$(git status --porcelain 2>/dev/null)" ] && dirty="*"
        printf " \[\033[35m\](%s%s)\[\033[0m\]" "$ref" "$dirty"
    fi
}

_build_prompt() {
    local exit_code="$?"
    local prompt_color="\[\033[32m\]"
    local exit_str=""

    # Якщо попередня команда завершилась із помилкою — показуємо код
    if [ "$exit_code" -ne 0 ]; then
        exit_str="\[\033[31m\][✘ $exit_code]\[\033[0m\] "
    fi

    # Виділення користувача root червоним кольором
    [ "$EUID" -eq 0 ] && prompt_color="\[\033[31m\]"

    # OSC 0 для оновлення заголовка вікна термінала
    local title_seq="\[\033]0;\u@\h: \w\007\]"

    PS1="${title_seq}${exit_str}${prompt_color}\u@\h\[\033[0m\]:\[\033[34m\]\w\[\033[0m\]$(_git_branch)\n\\$ "
}

PROMPT_COMMAND="_build_prompt; ${PROMPT_COMMAND:-}"
```

### Сучасні скомпільовані генератори промптів (Starship)

Створення складних промптів чистою мовою Bash має суттєвий недолік: для зчитування статусу Git, версії мови Node.js/Python, контексту Kubernetes та заряду батареї bash-скрипт змушений викликати десятки зовнішніх утиліт через підстановку команд `$(...)`. Кожна підстановка породжує системні виклики `fork(2)` та `execve(2)`. На великих репозиторіях або слабких машинах натискання клавіші Enter починає дратувати затримкою в 100–300 мілісекунд.

Сучасним стандартом є використання скомпільованих бінарних рушіїв, таких як **Starship** (написаний на мові Rust) або **Oh-My-Posh** (написаний на Go).

Starship збирає всю метаінформацію паралельно в пулі потоків без викликів зовнішніх підпроцесів (використовуючи прямі звернення до бібліотек `libgit2` та системних API ядра). Час формування навіть найскладнішого рядка підказки не перевищує 5 мілісекунд.

Інтеграція Starship у `~/.bashrc` зводиться до одного рядка:

```bash
if command -v starship >/dev/null 2>&1; then
    eval "$(starship init bash)"
fi
```

## Безпечні аліаси, надійні функції та сучасні утиліти

Аліаси (`alias`) та функції оболонки призначені для автоматизації рутини та запобігання типовим людським помилкам. Проте між ними існує глибока різниця в реалізації.

### Порядок пошуку імен та різниця між аліасом і функцією

Коли користувач вводить команду в рядок, оболонка Bash здійснює пошук виконуваного коду у строгому пріоритетному порядку:
1. **Аліаси (`alias`)** — суто лексична заміна першого слова на етапі синтаксичного розбору. Аліас не підтримує позиційні параметри (`$1`, `$2`), не вміє робити розгалуження через `if` і не має власних змінних.
2. **Зарезервовані ключові слова мови** (`if`, `for`, `while`, `case`).
3. **Функції оболонки (`function`)** — повноцінні блоки коду в пам'яті поточного процесу. Підтримують позиційні параметри, локальні змінні (`local var="val"`) та коди повернення (`return`).
4. **Вбудовані команди оболонки (`builtins`)** (`cd`, `echo`, `read`, `history`).
5. **Зовнішні двійкові файли у файловій системі**, знайдені через послідовний перебір каталогів змінної `$PATH`.

```bash
# ❌ Помилкова спроба використати аргумент в аліасі (аргумент просто допишеться в кінець)
alias mkcd='mkdir -p $1 && cd $1'

# ✓ Правильна реалізація через функцію
mkcd() {
    mkdir -p "$1" && cd "$1"
}
```

### Продуктивність функцій: уникнення зайвих підоболонок

При написанні функцій для щоденного використання критично важливо уникати створення зайвих процесів. Оголошення тіла функції через круглі дужки `fname() ( ... )` змушує Bash викликати `fork(2)` і виконувати код у дочірній підоболонці.

Якщо всередині такої функції ви спробуєте змінити робочий каталог через `cd` або експортувати змінну, зміни відбудуться у пам'яті дочірнього процесу й миттєво зникнуть при виході. Функції навігації завжди оформлюються через фігурні дужки `fname() { ...; }`, які виконують код прямо в контексті батьківської оболонки.

### Пастки захисних аліасів

Часто рекомендують додавати аліас `alias rm='rm -i'`, щоб утиліта запитувала підтвердження перед видаленням кожного файлу. У цьому криється психологічна пастка: інженер звикає, що команда `rm` завжди безпечна, і без вагань натискає `rm file`. Потім, потрапивши на чужий production-сервер без такого аліаса, він за звичкою виконує команду і миттєво знищує важливі дані.

Більш безпечним підходом є використання прапорця `-I` (запитувати підтвердження тільки при видаленні більше трьох файлів або при рекурсивному видаленні) та прапорця `--preserve-root`:

```bash
alias rm='rm -I --preserve-root'
alias cp='cp -iv'
alias mv='mv -iv'
```

Якщо вам необхідно викликати оригінальний бінарний файл в обхід аліаса, Unix надає три рівноцінні механізми:
1. Додати зворотний слеш перед іменем: `\rm file` (слеш запобігає розпізнаванню імені як аліаса).
2. Використати вбудовану команду: `command rm file`.
3. Вказати абсолютний шлях до файлу: `/bin/rm file`.

### Розумні допоміжні функції

Нижче наведено перевірені часом функції для прискорення повсякденної навігації:

```bash
# Швидкий підйом на N рівнів вгору по дереву каталогів: up 3 -> cd ../../..
up() {
    local levels="${1:-1}"
    local target=""
    for (( i=0; i<levels; i++ )); do
        target="../$target"
    done
    cd "$target" || return 1
}

# Універсальний розпакувальник архівів за їхнім магічним розширенням
extract() {
    if [ -f "$1" ]; then
        case "$1" in
            *.tar.bz2)   tar xjf "$1"     ;;
            *.tar.gz)    tar xzf "$1"     ;;
            *.tar.xz)    tar xJf "$1"     ;;
            *.bz2)       bunzip2 "$1"     ;;
            *.rar)       unrar x "$1"     ;;
            *.gz)        gunzip "$1"      ;;
            *.tar)       tar xf "$1"      ;;
            *.tbz2)      tar xjf "$1"     ;;
            *.tgz)       tar xzf "$1"     ;;
            *.zip)       unzip "$1"       ;;
            *.Z)         uncompress "$1"  ;;
            *.7z)        7z x "$1"        ;;
            *)           echo "Невідомий формат архіву '$1'" >&2; return 1 ;;
        esac
    else
        echo "'$1' не є дійсним файлом" >&2
        return 1
    fi
}
```

## Модульна архітектура dotfiles та версіонування через Git

Коли конфігурація оболонки зростає, тримати її в єдиному файлі `~/.bashrc` стає неможливо. Розбиття конфігурації на окремі предметні модулі дозволяє легко ізолювати помилки, вимикати непотрібні компоненти та безпечно переносити робоче середовище між серверами, робочими станціями та контейнерами.

![Модульна архітектура конфігурації оболонки](/root/course/unix/make-the-shell-your-own/img/modular-dotfiles-structure.svg)
*Ієрархія завантаження функціональних модулів у каталозі ~/.config/bash/ та ізоляція локальних налаштувань за допомогою Git Bare Repository*

### Структура каталогу ~/.config/bash/

Відповідно до специфікації XDG Base Directory, конфігурація розбивається на окремі файли в каталозі `~/.config/bash/` з двозначними числовими префіксами, що задають чіткий пріоритет завантаження:

- `00-env.bash` — базові змінні середовища, локаль, шляхи `$PATH` та специфікація XDG.
- `10-history.bash` — налаштування розміру історії, дедуплікації та синхронізація через `PROMPT_COMMAND`.
- `20-readline.bash` — прапорці `shopt`, прив'язки клавіш та параметри введення.
- `30-prompt.bash` — побудова `$PS1` або ініціалізація Starship.
- `40-aliases.bash` — скорочення, кольори утиліт та безпечні прапорці.
- `50-functions.bash` — розширені функції (`mkcd`, `up`, `extract`).
- `99-local.bash` — локальні перевизначення для конкретної машини (додається до `.gitignore`).

Головний файл `~/.bashrc` перетворюється на компактний та надійний завантажувач:

```bash
# ~/.bashrc — Легковага точка входу

# Якщо сеанс не інтерактивний — виходимо
case $- in
    *i*) ;;
      *) return;;
esac

DOTFILES_DIR="${XDG_CONFIG_HOME:-$HOME/.config}/bash"

# Завантаження модулів у числовому порядку
if [ -d "$DOTFILES_DIR" ]; then
    for mod in "$DOTFILES_DIR"/[0-9][0-9]-*.bash; do
        [ -r "$mod" ] && . "$mod"
    done
    unset mod
fi

# Підключення локальних налаштувань за наявності
[ -r "$DOTFILES_DIR/99-local.bash" ] && . "$DOTFILES_DIR/99-local.bash"
```

Повний працюючий стартовий каркас усіх модулів, готовий до розгортання в один клік, розібрано в практичній проєктній вставці [практикум модульної конфігурації dotfiles](root:unix/make-the-shell-your-own/proj-modular-dotfiles.md).

### Керування конфігурацією через Git Bare Repository

Поширений підхід із розміщенням конфігурацій у каталозі `~/dotfiles` та створенням сотень символічних посилань (`symlinks`) за допомогою утиліти `GNU Stow` має суттєві вади: посилання ламаються при оновленнях програм, а графічні застосунки часто перезаписують симлінки звичайними файлами.

Найбільш надійний та елегантний спосіб версіонування — **голий репозиторій Git (`Git Bare Repository`)** безпосередньо в домашньому каталозі.

1. **Ініціалізація сховища на робочій машині:**
   ```bash
   # Створення голого репозиторію в прихованому каталозі
   git init --bare "$HOME/.dotfiles"

   # Створення зручного аліаса для керування
   alias dotfiles='/usr/bin/git --git-dir=$HOME/.dotfiles/ --work-tree=$HOME'

   # Критично: приховування сторонніх невідстежуваних файлів з домашнього каталогу
   dotfiles config --local status.showUntrackedFiles no

   # Додавання конфігурацій і створення першого коміту
   dotfiles add ~/.bashrc ~/.config/bash/ ~/.inputrc
   dotfiles commit -m "feat: модульна структура dotfiles"
   ```

2. **Розгортання на новому сервері за кілька секунд:**
   ```bash
   # Клонування репозиторію
   git clone --bare git@github.com:username/dotfiles.git "$HOME/.dotfiles"
   alias dotfiles='/usr/bin/git --git-dir=$HOME/.dotfiles/ --work-tree=$HOME'

   # Застосування файлів конфігурації у $HOME
   dotfiles checkout
   dotfiles config --local status.showUntrackedFiles no
   ```
