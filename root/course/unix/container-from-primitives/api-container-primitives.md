# 📋 Інтерфейс системних примітивів контейнеризації

Створення ізольованих середовищ у Linux спирається на набір ортогональних системних викликів ядра, віртуальних файлових систем (`cgroupfs`, `procfs`, `sysfs`), мережевих сокетів маршрутизації (`rtnetlink`) та інтерфейсів безпеки (Linux Capabilities, seccomp-BPF). Нижче наведено систематичний опис контрактів, прапорців, структур даних, форматів конфігураційних файлів і кодів помилок, які формують низькорівневу поверхню контейнеризації.

---

### 1. Системні виклики просторів імен

#### 1.1. Створення процесу з новими просторами: `clone` та `clone3`

```c
#define _GNU_SOURCE
#include <sched.h>

int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...
          /* pid_t *parent_tid, void *tls, pid_t *child_tid */);

#include <linux/sched.h>
#include <sys/syscall.h>

long syscall(SYS_clone3, struct clone_args *cl_args, size_t size);
```

| Прапорець | Числове значення | Ізольований ресурс ядра | Вимоги до привілеїв |
| :--- | :--- | :--- | :--- |
| `CLONE_NEWNS` | `0x00020000` | Точки монтування VFS | `CAP_SYS_ADMIN` |
| `CLONE_NEWCGROUP` | `0x02000000` | Корінь cgroup (`/proc/self/cgroup`) | `CAP_SYS_ADMIN` |
| `CLONE_NEWUTS` | `0x04000000` | Ім'я хоста та домену (`nodename`, `domainname`) | `CAP_SYS_ADMIN` |
| `CLONE_NEWIPC` | `0x08000000` | Черги System V / POSIX MQ, спільна пам'ять | `CAP_SYS_ADMIN` |
| `CLONE_NEWUSER` | `0x10000000` | Таблиця UID/GID та набір можливостей (*capabilities*) | Не вимагає `CAP_SYS_ADMIN` |
| `CLONE_NEWPID` | `0x20000000` | Простір ідентифікаторів процесів (PID) | `CAP_SYS_ADMIN` |
| `CLONE_NEWNET` | `0x40000000` | Мережевий стек, інтерфейси, сокети, таблиці IP | `CAP_SYS_ADMIN` |
| `CLONE_NEWTIME` | `0x00000080` | Зсуви годинників `CLOCK_MONOTONIC` і `BOOTTIME` | `CAP_SYS_ADMIN` |

При виклику класичного `clone()` обов'язково передається сигнал завершення дочірнього процесу в молодших 8 бітах (зазвичай `SIGCHLD`). Прапорець `CLONE_VM` **не можна** поєднувати з `CLONE_NEWPID` або `CLONE_NEWUSER`, оскільки дочірній процес вимагає власного адресного простору пам'яті для ініціалізації середовища.

У системному виклику `clone3` конфігурація передається через структуру:

```c
struct clone_args {
    __aligned_u64 flags;        /* Прапорці CLONE_* */
    __aligned_u64 pidfd;        /* Вказівник для повернення файлового дескриптора процесу */
    __aligned_u64 child_tid;    /* Вказівник на TID у дочірній пам'яті */
    __aligned_u64 parent_tid;   /* Вказівник на TID у батьківській пам'яті */
    __aligned_u64 exit_signal;  /* Сигнал завершення (SIGCHLD) */
    __aligned_u64 stack;        /* Початок пам'яті стека */
    __aligned_u64 stack_size;   /* Розмір виділеного стека */
    __aligned_u64 tls;          /* Вказівник на сегмент Thread-Local Storage */
    __aligned_u64 set_tid;      /* Масив бажаних PID у вкладених просторах */
    __aligned_u64 set_tid_size; /* Кількість елементів у set_tid */
    __aligned_u64 cgroup;       /* Файловий дескриптор цільової cgroup v2 */
};
```

Типові коди помилок `clone` / `clone3`:
* `EPERM`: Викликаючий процес не має `CAP_SYS_ADMIN` у поточному просторі користувача для зазначеного прапорця.
* `EINVAL`: Несумісна комбінація прапорців (наприклад, `CLONE_THREAD` разом із `CLONE_NEWPID`).
* `ENOMEM`: Недостатньо пам'яті ядра для виділення структур `task_struct` або `nsproxy`.
* `ENOSPC`: Досягнуто ліміту кількості вкладених просторів імен, заданого у `/proc/sys/user/max_*_namespaces`.

#### 1.2. Від'єднання просторів поточного процесу: `unshare`

```c
#define _GNU_SOURCE
#include <sched.h>

int unshare(int flags);
```

* **Призначення:** Дозволяє процесу без створення дочірнього процесу розірвати спільні зв'язки з батьківським оточенням і отримати новий набір просторів імен.
* **Особливість для простору PID:** Виклик `unshare(CLONE_NEWPID)` не змінює простір імен *поточного* процесу (його PID у системі залишається незмінним), але робить усі *майбутні дочірні процеси* членами нового простору PID. Перший породжений дочірній процес стає PID 1 у цьому новому просторі.

#### 1.3. Приєднання до існуючого простору імен: `setns`

```c
#define _GNU_SOURCE
#include <sched.h>

int setns(int fd, int nstype);
```

* **Параметри:**
  * `fd`: Відкритий файловий дескриптор магічного файлу простору в `/proc/[pid]/ns/<тип>` (наприклад, `/proc/1234/ns/net`) або дескриптор `pidfd`.
  * `nstype`: Очікуваний тип простору імен (`CLONE_NEWNET`, `CLONE_NEWIPC`, `0` для автоматичного визначення).
* **Повертане значення:** `0` при успіху, `-1` при помилці (зі встановленням `errno`: `EINVAL`, `EPERM`, `EBADF`).

### 2. Файлова ізоляція та VFS

#### 2.1. Атомарна зміна кореневого дерева: `pivot_root`

```c
#include <sys/syscall.h>
#include <unistd.h>

int pivot_root(const char *new_root, const char *put_old);
```

Виклик `pivot_root` переставляє поточне кореневе дерево монтування викликаючого процесу у каталог `put_old`, а на його місце як новий корінь `/` встановлює `new_root`.

* **Обов'язкові інваріанти ядра:**
  1. `new_root` мусить бути окремою точкою монтування VFS. Якщо це звичайний каталог, його слід змонтувати до самого себе: `mount(new_root, new_root, NULL, MS_BIND | MS_REC, NULL)`.
  2. `put_old` мусить бути розташований усередині дерева `new_root` (наприклад, `/new_root/.old_root`).
  3. `new_root` і `put_old` не можуть належати до поточної кореневої файлової системи `rootfs` (початковий ramfs/initramfs). Якщо процес працює в `initramfs`, замість `pivot_root` використовується механізм `switch_root`.
  4. Поточний робочий каталог процесу після виклику слід явно змінити через `chdir("/")`.

Типові коди помилок `pivot_root`:
* `EINVAL`: `new_root` не є точкою монтування або `put_old` знаходиться за межами `new_root`.
* `EBUSY`: `new_root` або `put_old` збігаються з поточною точкою монтування кореня або є спільними монтуваннями з іншим простором.
* `EPERM`: Викликаючий процес не має `CAP_SYS_ADMIN`.

#### 2.2. Налаштування розповсюдження монтувань: `mount`

```c
#include <sys/mount.h>

int mount(const char *source, const char *target,
          const char *filesystemtype, unsigned long mountflags,
          const void *data);
```

Критичні прапорці для ізоляції файлових систем:
* `MS_REC | MS_PRIVATE`: Робить усі точки монтування піддерева приватними, блокуючи розповсюдження подій монтування на хостову систему.
* `MS_BIND | MS_REC`: Монтування прив'язки для підготовки кореня або перенесення каталогів хоста.
* `MS_REMOUNT | MS_BIND | MS_RDONLY`: Переведення точки монтування у режим «тільки для читання».
* `MS_NOSUID`: Ігнорування бітів `setuid`/`setgid` на бінарних файлах у змонтованій файловій системі.
* `MS_NODEV`: Заборона доступу до спеціальних файлів пристроїв (блокових і символьних) у цій точці монтування.
* `MS_NOEXEC`: Заборона прямого виконання двійкових програм із цієї точки монтування.

#### 2.3. Монтування об'єднаної файлової системи: OverlayFS

```c
mount("overlay", "/target/merged", "overlay", 0,
      "lowerdir=/layers/base,upperdir=/target/diff,workdir=/target/work");
```

Ключові параметри конфігурації OverlayFS:
* `lowerdir`: Список каталогів базових незмінних шарів образів (розділені двокрапкою `:`, зчитуються зліва направо).
* `upperdir`: Каталог запису для збереження нових і змінених файлів контейнера.
* `workdir`: Службовий каталог на тій самій файловій системі, що й `upperdir`, необхідний ядру для забезпечення атомарності операцій перейменування та видалення файлів (*whiteout*).
* `metacopy=on`: Дозволяє копіювати лише метадані файлу при зміні прав або атрибутів без копіювання самого вмісту файлу в `upperdir`.
* `redirect_dir=on`: Оптимізує операції перейменування каталогів без повного рекурсивного дублювання піддерева.

#### 2.4. Ізоляція псевдотерміналів: devpts

```c
mount("devpts", "/target/dev/pts", "devpts", MS_NOSUID | MS_NOEXEC,
      "newinstance,ptmxmode=0666,mode=0620");
```

* `newinstance`: Створює незалежний примірник пулу псевдотерміналів, повністю відокремлений від хостового пулу `/dev/pts`.
* `ptmxmode=0666`: Задає права доступу до магічного керуючого вузла мультиплексора псевдотерміналів `/dev/pts/ptmx`.

#### 2.5. Ліниве відмонтування старого кореня: `umount2`

```c
#include <sys/mount.h>

int umount2(const char *target, int flags);
```

* `MNT_DETACH` (`0x00000002`): Виконує від'єднання точки монтування від дерева VFS негайно, роблячи її недоступною для нових звернень, тоді як фактичне звільнення структур ядра відбувається після закриття всіх відкритих файлових дескрипторів.
* `MNT_FORCE` (`0x00000001`): Примусове відмонтування (застосовується переважно для завислих мережевих ФС на кшталт NFS).

### 3. Керування ресурсами: Інтерфейс cgroups v2

Усі операції з cgroups v2 здійснюються через запис і читання звичайних текстових файлів у віртуальній файловій системі `cgroupfs`, змонтованій у `/sys/fs/cgroup`.

#### 3.1. Загальне дерево та членство процесів

| Файл у каталозі cgroup | Формат даних | Опис призначення |
| :--- | :--- | :--- |
| `cgroup.procs` | Список PID через `\n` | Перелік процесів у групі. Запис PID переміщує процес у цю cgroup. |
| `cgroup.controllers` | `cpu memory io pids` | Доступні для активації контролери на цьому рівні дерева. |
| `cgroup.subtree_control` | `+cpu +memory +pids` | Контролери, активні для дочірніх підкаталогів. |
| `cgroup.events` | `populated 0/1, frozen 0/1` | Індикатори наявності активних процесів і стану замороження. |
| `cgroup.kill` | Запис `1` | Атомарно надсилає `SIGKILL` усім процесам групи. |
| `cgroup.stat` | `nr_descendants <N>` | Кількість дочірніх cgroup-піддерев. |

#### 3.2. Контролер оперативної пам'яті (`memory.*`)

* `memory.max`: Жорсткий ліміт пам'яті у байтах (або рядок `max`). Перевищення ліміту після безуспішного витіснення сторінок активує OOM-killer для процесів цієї cgroup.
* `memory.high`: М'який ліміт (у байтах). При його перевищенні ядро сповільнює виділення пам'яті процесу та у фоновому режимі витісняє кешовані сторінки.
* `memory.low`: Захищений поріг пам'яті (у байтах). Сторінки нижче цього порогу не витісняються, якщо пам'ять можна звільнити з інших cgroup.
* `memory.min`: Абсолютний захист пам'яті (hard protection). Сторінки нижче цього порогу ніколи не підлягають витісненню ядром під час глобального дефіциту RAM.
* `memory.swap.max`: Ліміт на використання файлу підкачки (swap) процесами групи (значення `0` повністю блокує свопінг).
* `memory.current`: Поточний обсяг використаної пам'яті (анонімна пам'ять + кеш сторінок + структури ядра).
* `memory.events`: Лічильники подій у форматі ключ-значення:
  * `low <count>`: Кількість спроб витіснення нижче захищеного порогу `memory.low`.
  * `high <count>`: Кількість спрацьовувань м'якого обмеження.
  * `max <count>`: Кількість спроб виходу за межі `memory.max`.
  * `oom <count>`: Кількість входів у стан вичерпання пам'яті.
  * `oom_kill <count>`: Кількість процесів, примусово знищених OOM-killer усередині групи.

#### 3.3. Контролер процесорного часу (`cpu.*`)

* `cpu.max`: Два числа через пробіл — квота часу та базовий період у мікросекундах:
  ```
  $MAX_USEC $PERIOD_USEC
  ```
  *Приклад:* `20000 100000` означає виділення не більше 20 мс CPU на кожні 100 мс стінного часу (20% від одного ядра). Для зняття ліміту встановлюється `max 100000`.
* `cpu.weight`: Відносна вага планувальника у діапазоні `[1, 10000]` (значення за замовчуванням: `100`).
* `cpu.stat`: Статистика використання:
  * `usage_usec`: Загальний час виконання у мікросекундах.
  * `user_usec` / `system_usec`: Розподіл між простором користувача та ядром.
  * `nr_periods`: Кількість минулих періодів квотування.
  * `nr_throttled`: Кількість періодів, у яких процеси групи були примусово призупинені через вичерпання квоти.
  * `throttled_usec`: Сумарний час простою у стані обмеження.

#### 3.4. Контролер кількості процесів (`pids.*`)

* `pids.max`: Максимально дозволена кількість задач (процесів і потоків) у групі. Спроби виклику `fork()` або `clone()` понад це значення повертають помилку `EAGAIN` (`Resource temporarily unavailable`).
* `pids.current`: Поточна кількість задач у групі та її підгрупах.
* `pids.events`: Лічильник відмов створення процесів через досягнення ліміту (`max <count>`).

#### 3.5. Контролер дискового вводу-виводу (`io.*`)

* `io.max`: Ліміти швидкості та кількості операцій для конкретних блокових пристроїв:
  ```
  $MAJOR:$MINOR rbps=$BYTES wbps=$BYTES riops=$IOPS wiops=$IOPS
  ```
  *Приклад:* `8:0 rbps=10485760 wbps=10485760` обмежує читання та запис на диск `/dev/sda` рівнем 10 МБ/с.
* `io.stat`: Лічильники переданих байтів та виконаних операцій за категоріями (`rbytes`, `wbytes`, `rios`, `wios`, `dbytes`).

### 4. Інтерфейси безпеки: Linux Capabilities

Linux ділить привілеї всемогутнього користувача `root` (UID 0) на 41 незалежну можливість (*capability*). Керування здійснюється через системні виклики `capget`, `capset` та бібліотеку `libcap`.

```c
#include <sys/capability.h>

int capset(cap_user_header_t hdrp, const cap_user_data_t datap);
int capget(cap_user_header_t hdrp, cap_user_data_t datap);
```

#### 4.1. Набори можливостей процесу

Кожен процес у ядрі містить п'ять наборів бітових масок можливостей:
1. **Permitted (Дозволені):** Граничний набір прав, які процес може перевести в діючі або передати нащадкам.
2. **Effective (Діючі):** Набір бітів, які ядро фактично перевіряє під час виконання системних операцій.
3. **Inheritable (Успадковувані):** Права, які зберігаються через виклик `execve` (вимагають узгодження з файловими можливостями бінарника).
4. **Bounding Set (Обмежувальний набір):** Верхня межа прав, яку процес і всі його нащадки можуть отримати через `execve`. Скидається викликом `prctl(PR_CAPBSET_DROP, cap, 0, 0, 0)`.
5. **Ambient (Амб'єнтні):** Права, які автоматично зберігаються при `execve` для непривілейованих бінарних файлів. Керуються через `prctl(PR_CAP_AMBIENT, ...)` (з'явилися у Linux 4.3).

#### 4.2. Критичні можливості для контейнеризації

| Можливість | Константа | Операції, дозволені ядром | Небезпека для хоста |
| :--- | :--- | :--- | :--- |
| `CAP_SYS_ADMIN` | `21` | Монтування файлових систем, налаштування cgroups, bpf, ptrace | **Критична:** повний контроль над ядром і вихід із контейнера |
| `CAP_SYS_MODULE` | `16` | Завантаження та вивантаження модулів ядра (`init_module`) | **Критична:** виконання довільного коду в просторі ядра |
| `CAP_SYS_RAWIO` | `17` | Прямий доступ до портів вводу-виводу та пам'яті пристроїв (`/dev/mem`) | **Критична:** пряме читання та запис фізичної пам'яті хоста |
| `CAP_SYS_PTRACE` | `19` | Трасування довільних процесів за допомогою `ptrace` | **Висока:** читання та зміна пам'яті процесів поза простором PID |
| `CAP_SYS_BOOT` | `22` | Перезавантаження системи через виклики `reboot` та `kexec_load` | **Висока:** вимикання або перезавантаження всього фізичного вузла |
| `CAP_NET_ADMIN` | `12` | Зміна таблиць маршрутизації, правил firewall, налаштування інтерфейсів | **Середня:** модифікація мережевого стека хоста при спільному netns |
| `CAP_NET_RAW` | `13` | Відкриття сирих сокетів (`SOCK_RAW`, `SOCK_PACKET`) | **Середня:** генерація підроблених IP/ARP пакетів |
| `CAP_NET_BIND_SERVICE` | `10` | Прив'язка сокетів до привілейованих портів (< 1024) | **Безпечна:** потрібна для веб-серверів (порти 80, 443) |
| `CAP_CHOWN` | `0` | Зміна власника та групи файлів | **Безпечна:** у межах ізольованого User Namespace |

### 5. Інтерфейси фільтрації системних викликів: seccomp-BPF

#### 5.1. Заборона підвищення привілеїв: `prctl`

```c
#include <sys/prctl.h>

int prctl(int option, unsigned long arg2, unsigned long arg3,
          unsigned long arg4, unsigned long arg5);
```

* `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`:
  Встановлює для поточного процесу та всіх його нащадків незворотний прапорець `no_new_privs`. Після цього виконання бінарних файлів із бітами `setuid` чи `setgid`, а також виконання файлів із файловими можливостями (*file capabilities*) не призводить до отримання додаткових прав. Цей виклик є обов'язковою передумовою для завантаження seccomp-фільтрів непривілейованим користувачем.

#### 5.2. Системний виклик `seccomp` та структури BPF

```c
#include <linux/seccomp.h>
#include <linux/filter.h>
#include <sys/syscall.h>

int seccomp(unsigned int operation, unsigned int flags, void *args);
```

* `operation`:
  * `SECCOMP_SET_MODE_STRICT` (`0`): Дозволяє лише системні виклики `read`, `write`, `exit`, `sigreturn`. Будь-який інший виклик призводить до негайного знищення процесу сигналом `SIGKILL`.
  * `SECCOMP_SET_MODE_FILTER` (`1`): Встановлює користувацький BPF-фільтр перевірки системних викликів.
* `flags`:
  * `SECCOMP_FILTER_FLAG_TSYNC` (`1`): Синхронізувати та застосувати фільтр до всіх існуючих потоків процесу.
  * `SECCOMP_FILTER_FLAG_LOG` (`2`): Логувати всі заблоковані або зафіксовані виклики в журналі аудиту ядра.

Структури опису BPF-програми:

```c
struct sock_filter {
    __u16 code;   /* Код інструкції cBPF (клас, розмір, режим адресації) */
    __u8  jt;     /* Зсув переходу при істинній умові (jump true) */
    __u8  jf;     /* Зсув переходу при хибній умові (jump false) */
    __u32 k;      /* Багатоцільове поле (константа, зсув або значення для порівняння) */
};

struct sock_fprog {
    unsigned short len;            /* Кількість інструкцій у масиві filter */
    struct sock_filter *filter;    /* Вказівник на масив BPF-інструкцій */
};
```

Дані, що передаються BPF-фільтру ядром під час кожного системного виклику (`struct seccomp_data`):

```c
struct seccomp_data {
    int   nr;                    /* Номер системного виклику (__NR_*) */
    __u32 arch;                  /* Архітектура процесора (AUDIT_ARCH_X86_64, AUDIT_ARCH_AARCH64) */
    __u64 instruction_pointer;   /* Вказівник на інструкцію в пам'яті (RIP/PC) */
    __u64 args[6];               /* Шість 64-бітних аргументів виклику */
};
```

Дії ядра залежно від повертаного значення BPF-фільтра:
* `SECCOMP_RET_ALLOW` (`0x7fff0000`): Дозволити виконання системного виклику без затримок.
* `SECCOMP_RET_ERRNO | (errno & 0xffff)` (`0x00050000`): Заблокувати виклик і повернути процесу зазначений код помилки (наприклад, `EPERM`). Код обробника в ядрі взагалі не виконується.
* `SECCOMP_RET_KILL_PROCESS` (`0x80000000`): Негайно завершити всі потоки процесу сигналом `SIGSYS`.
* `SECCOMP_RET_KILL_THREAD` (`0x00000000`): Завершити лише той потік, що здійснив заборонений системний виклик.
* `SECCOMP_RET_TRAP` (`0x00030000`): Надіслати процесу сигнал `SIGSYS` із заповненою структурою `siginfo_t` для перехоплення налагоджувачем.
* `SECCOMP_RET_TRACE` (`0x7ff00000`): Повідомити процес, що здійснює трасування через `ptrace`, про системний виклик.

### 6. Відображення User Namespaces та конфігурація UID/GID

Для надання процесу прав адміністратора всередині контейнера без надання прав на хостовій машині налаштовуються файли у `/proc/[pid]/`:

```
/proc/[pid]/uid_map
/proc/[pid]/gid_map
```

Формат запису складається з одного або кількох рядків:
```
<ID_усередині_простору> <ID_на_хості> <кількість_ідентифікаторів>
```

*Приклад:* Рядок `0 100000 65536` відображає локальні UID 0–65535 контейнера на діапазон 100000–165535 хоста. Для хостового ядра процес має UID 100000 і не може отримати доступ до системних файлів користувача `root`.

*Вимоги до запису:*
1. Запис у `uid_map` або `gid_map` дозволений лише **один раз** за весь час існування простору імен. Будь-яка наступна спроба запису повертає помилку `EPERM`.
2. Перед записом у `/proc/[pid]/gid_map` непривілейований процес зобов'язаний вимкнути виклик `setgroups`, записавши рядок `deny` у файл `/proc/[pid]/setgroups`:

```bash
echo "deny" > /proc/[pid]/setgroups
echo "0 100000 65536" > /proc/[pid]/gid_map
echo "0 100000 65536" > /proc/[pid]/uid_map
```

### 7. Мережева інтеграція через veth-інтерфейси

Мережева ізоляція нового `netns` вимагає встановлення зв'язку між ізольованим стеком і мережею хоста. Це реалізується через пару віртуальних інтерфейсів (*veth pair*) за допомогою системних сокетів `NETLINK_ROUTE` або утиліти `ip link`:

```bash
# 1. Створення пари віртуальних кабелів
ip link add veth-host type veth peer name veth-guest

# 2. Переміщення кінця кабелю veth-guest у простір імен цільового процесу PID
ip link set veth-guest netns <PID>

# 3. Прив'язка veth-host до хостового мосту br0
ip link set veth-host master br0
ip link set veth-host up

# 4. Налаштування інтерфейсу всередині простору імен контейнера
ip netns exec <ім'я_простору> ip addr add 10.0.0.2/24 dev veth-guest
ip netns exec <ім'я_простору> ip link set veth-guest name eth0
ip netns exec <ім'я_простору> ip link set eth0 up
ip netns exec <ім'я_простору> ip link set lo up
ip netns exec <ім'я_простору> ip route add default via 10.0.0.1
```

### 8. Інспекція стану контейнера через `/proc` та `sysfs`

Ядро Linux надає набір псевдофайлів для аудиту та діагностики активних примітивів ізоляції:

#### 8.1. Ідентифікатори просторів імен: `/proc/[pid]/ns/`

Каталог `/proc/[pid]/ns/` містить магічні символьні посилання на структури просторів імен:

```bash
ls -l /proc/$$/ns/
```
```
cgroup -> 'cgroup:[4026531835]'
ipc    -> 'ipc:[4026531839]'
mnt    -> 'mnt:[4026531840]'
net    -> 'net:[4026531992]'
pid    -> 'pid:[4026531836]'
pid_for_children -> 'pid:[4026531836]'
time   -> 'time:[4026531834]'
time_for_children -> 'time:[4026531834]'
user   -> 'user:[4026531837]'
uts    -> 'uts:[4026531838]'
```

Число у квадратних дужках — це номер `inode` у псевдофайловій системі `nsfs`. Якщо два процеси мають однаковий номер `inode` для певного простору (наприклад, `net:[4026531992]`), вони поділяють один і той самий примірник ресурсу в ядрі.

#### 8.2. Аудит точок монтування: `/proc/[pid]/mountinfo`

Файл `/proc/[pid]/mountinfo` надає повний зріз VFS із типами розповсюдження подій монтування:

```
36 0 8:1 / / rw,relatime shared:1 - ext4 /dev/sda1 rw,data=ordered
```

Поля рядка:
1. `mount ID`: Унікальний числовий ідентифікатор монтування.
2. `parent ID`: ID батьківського монтування.
3. `major:minor`: Старший і молодший номери пристрою файлової системи.
4. `root`: Корінь монтування всередині файлової системи.
5. `mount point`: Шлях точки монтування відносно кореня процесу.
6. `mount options`: Прапорці монтування для VFS (`ro`, `nosuid`, `nodev`, `relatime`).
7. `optional fields`: Теги розповсюдження:
   * `shared:X`: Монтування входить до спільної групи `X` (події дублюються).
   * `master:X`: Монтування є підпорядкованим (*slave*) для групи `X` (отримує події, але не надсилає).
   * `propagate_from:X`: Отримує події монтування від майстра `X`.
   * `unbindable`: Заборонено для використання як джерело монтування прив'язки.
8. `-`: Роздільник необов'язкових полів.
9. `filesystem type`: Назва типу файлової системи (`ext4`, `overlay`, `tmpfs`, `proc`).
10. `mount source`: Джерело файлової системи або назва пристрою.
11. `super options`: Прапорці суперблока.

#### 8.3. Аудит бітових масок можливостей: `/proc/[pid]/status`

Файл `/proc/[pid]/status` містить 64-бітні шістнадцяткові маски для кожного з п'яти наборів можливостей:

```
CapInh: 0000000000000000
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapBnd: 000001ffffffffff
CapAmb: 0000000000000000
```

Значення `000001ffffffffff` відповідає бітовій масці, у якій встановлено перші 41 біт (усі стандартні можливості ядра ввімкнено). У повністю ізольованому контейнері поля `CapEff` та `CapBnd` зазвичай містять лише мінімально необхідні біти (наприклад, `CAP_NET_BIND_SERVICE` та `CAP_SETUID`).

#### 8.4. Зсуви простору часу: `/proc/[pid]/timens_offsets`

Для налаштування віртуального годинника у `CLONE_NEWTIME` використовується файл:

```
/proc/[pid]/timens_offsets
```

Формат запису:
```
<ідентифікатор_годинника> <секунди_зсуву> <наносекунди_зсуву>
```

Підтримуються годинники `monotonic` та `boottime`. Запис дозволений лише до того моменту, поки в новоствореному просторі часу не було запущено жодного процесу (через `fork` чи `clone`).

#### 8.5. Системні ліміти ядра на кількість просторів: `/proc/sys/user/`

Глобальні обмеження ядра на створення просторів імен керуються через параметри `sysctl`:

* `/proc/sys/user/max_user_namespaces`: Максимальна кількість активних User Namespaces.
* `/proc/sys/user/max_pid_namespaces`: Ліміт на вкладені PID-дерева.
* `/proc/sys/user/max_net_namespaces`: Ліміт на окремі мережеві стеки.
* `/proc/sys/user/max_mnt_namespaces`: Ліміт на активні дерева монтувань.

Якщо системний виклик `clone(CLONE_NEW*)` або `unshare(CLONE_NEW*)` перевищує відповідний ліміт, ядро повертає помилку `ENOSPC` (`No space left on device`).
