# 📋 Довідник команд GDB для живої діагностики

Цей довідник містить систематизований опис інтерфейсу, команд, внутрішніх змінних та параметрів GNU Debugger (GDB), призначених для діагностики працюючих процесів у просторі користувача Linux. Кожен розділ розкриває семантику викликів, взаємодію з ядром через системний виклик `ptrace`, поведінку планувальника при перемиканні потоків, роботу з таблицями налагоджувальних символів DWARF та правила безпечної експлуатації на серверах.

## 1. Підключення до процесу та завантаження символів

Підключення до живого процесу вимагає зіставлення простору віртуальних адрес у пам'яті процесу з метаданими налагоджувальних символів, збереженими у бінарних файлах ELF. Якщо цільовий бінарник був зібраний з відокремленими символами або очищений утилітою `strip`, GDB повинен явно отримати шляхи до файлів символів DWARF або звернутися до віддаленого сервера debuginfod.

При підключенні через `gdb -p <PID>` налагоджувач ініціює запит `PTRACE_ATTACH` або `PTRACE_SEIZE`. Якщо бінарний файл на диску було оновлено або видалено після запуску процесу, передача абсолютного шляху до виконуваного файлу першим аргументом гарантує коректне відображення секцій коду `.text` та секцій даних `.rodata`.

| Команда / Параметр | Призначення та поведінка | Вплив на систему |
|---|---|---|
| `gdb -p <PID>` | Підключитися до працюючого процесу за його числовим PID. Викликає системний виклик `ptrace(PTRACE_ATTACH)`. | Надсилає `SIGSTOP` цільовому процесу та переводить його у стан `TASK_TRACED`. |
| `gdb <шлях_до_ELF> <PID>` | Підключитися до процесу з явним завантаженням секцій коду та налагоджувальних таблиць із зазначеного бінарного файлу. | Усуває розбіжності між виконуваним файлом на диску та пам'яттю процесу. |
| `gdb -p <PID> -batch -ex "<cmd>"` | Неінтерактивний пакетний режим: виконує послідовність команд `<cmd>`, скидає результат у стандартний вивід і від'єднується. | Мінімізує час зупинки процесу до мілісекунд; безпечно для автоматизованих скриптів. |
| `file <шлях_до_ELF>` | Завантажити таблицю символів та прив'язати секції адресного простору для поточної активної сесії. | Оновлює внутрішню таблицю типів даних та адрес функцій у пам'яті GDB. |
| `symbol-file <шлях_до_debug>` | Завантажити відокремлені налагоджувальні символи (файл формату `.debug` або не-stripped копію бінарника). | Зіставляє адреси лічильника інструкцій `%rip` з рядками вихідного коду без перезавантаження образу. |
| `set debug-file-directory <шлях>` | Задати список каталогів для автоматичного пошуку символів за хеш-сумою `Build-ID`. | Дозволяє GDB автоматично підтягувати debuginfo-пакунки дистрибутива (наприклад, `/usr/lib/debug`). |
| `set debuginfod enabled on` | Увімкнути клієнт протоколу debuginfod для автоматичного завантаження відсутніх символів та джерел з мережі. | Звертається за HTTP до серверів символів дистрибутива при виявленні невідомих Build-ID. |

## 2. Керування багатопотоковим станом та планувальником

У середовищі Linux кожен потік стандарту POSIX Threads (pthreads) створюється системним викликом `clone` з прапорцем `CLONE_THREAD` і є самостійною одиницею планування ядра (Task Struct) зі своїм власним ідентифікатором потоку (TID або LWP). GDB нумерує потоки власними локальними індексами `1, 2, ... N`, зберігаючи зв'язок із числовим LWP операційної системи.

Коли процес зупиняється на точці зупину або сигналом `SIGSTOP`, планувальник GDB за замовчуванням дозволяє всім потокам продовжити виконання при виклику `continue` або одиночному кроці `step`. Якщо один із потоків зупинився на точці зупину, а інші продовжують виконувати роботу в тлі, це може створити стан гонитви. Для ізольованого дослідження конкретного потоку використовується механізм блокування планувальника `scheduler-locking`.

| Команда | Призначення та поведінка | Особливості застосування |
|---|---|---|
| `info threads` | Вивести таблицю всіх потоків процесу: внутрішній ID GDB, системний LWP (TID ядра), назву потоку та поточний фрейм. | Допомагає виявити потоки, заблоковані у системних викликах `futex`, `epoll_wait` або `read`. |
| `thread <ID>` | Зробити потік з номером `<ID>` активним для наступних команд інспекції та покрокового виконання. | Змінює поточний контекст регістрів процесора на збережений стан `pt_regs` вибраного потоку. |
| `thread apply all <cmd>` | Виконати команду `<cmd>` послідовно у контексті кожного потоку досліджуваного процесу. | Незамінно для отримання знімків стану всієї системи одним викликом. |
| `thread apply all bt` | Зібрати короткий стек викликів (backtrace) для кожного зареєстрованого потоку програми. | Швидкий спосіб локалізації місця зависання або виявлення взаємного блокування між потоками. |
| `thread apply all bt full` | Зібрати повний стек викликів для всіх потоків із дампом усіх локальних змінних кожного кадру. | Дає вичерпну картину стану пам'яті; рекомендовано перенаправляти вивід у файл журналу. |
| `thread apply <ID1> <ID2> <cmd>` | Виконати команду `<cmd>` лише для вибіркового списку потоків процесу. | Дозволяє порівняти стан двох конкретних потоків, задіяних у спільній операції. |
| `thread find <шаблон>` | Знайти потоки, у поточному стеку яких фігурує функція чи адреса, що відповідає регулярному виразу. | Прискорює навігацію у процесах із сотнями робочих потоків у пулі (Worker Pool). |
| `set scheduler-locking on` | Повністю заблокувати планувальник: під час крокування (`step`, `next`, `continue`) виконується лише активний потік. | Запобігає зміні стану глобальних змінних іншими потоками під час аналізу критичної секції. |
| `set scheduler-locking off` | Дозволити всім потокам вільно працювати під час продовження виконання (режим за замовчуванням). | Відновлює природну багатопотокову конкуренцію в процесі. |
| `set scheduler-locking step` | Блокувати інші потоки виключно під час виконання одиночного кроку `step`/`next`, але відпускати при `continue`. | Оптимальний баланс для покрокового трасування складних алгоритмів без несподіваних перемикань. |

## 3. Навігація стеком викликів та фреймами функцій

Стек викликів організований у вигляді послідовності фреймів (кадрів активації), які створюються при кожному виклику функції. Кожен фрейм містить збережену адресу повернення `%rip`, покажчик бази кадру `%rbp` (якщо компіляція велася без оптимізації `-fomit-frame-pointer`), значення вхідних аргументів та локальні змінні функції.

Фрейм `#0` відповідає інструкції, на якій процес зупинився безпосередньо. Фрейми з більшими номерами `#1`, `#2` ведуть угору по ланцюжку викликів до кореневої точки входу. Перемикання фрейму командою `frame <N>` не змінює лічильник інструкцій процесора, але змінює область видимості змінних у сесії GDB, дозволяючи читати змінні викликаючої функції так, ніби ми перебуваємо всередині її тіла.

| Команда | Синтаксис та семантика | Очікуваний результат |
|---|---|---|
| `bt` (або `backtrace`) | Вивести стек викликів для поточного активного потоку від фрейму `#0` до кореня. | Список адрес, імен функцій, вихідних файлів та номерів рядків. |
| `bt <N>` | Обмежити глибину виводу стека першими `<N>` найновішими фреймами. | Зручно при глибокій рекурсії або довгих ланцюжках викликів у фреймворках. |
| `bt -<N>` | Вивести лише `<N>` найстаріших (кореневих) фреймів на дні стека. | Показує контекст запуску потоку та початкову диспетчеризацію завдань. |
| `bt full` | Вивести стек викликів із переліком та значеннями всіх локальних змінних для кожного фрейму. | Дозволяє відстежити зміну параметрів алгоритму на кожному рівні вкладеності. |
| `frame <N>` (або `f <N>`) | Активувати фрейм під номером `<N>` для поточної інспекції. | Перемикає контекст символів і дозволяє командам `print` бачити локальні змінні цього кадру. |
| `up [<N>]` | Піднятися на `<N>` рівнів угору по стеку викликів (у бік викликаючої функції). | Переходить до функції, яка ініціювала поточний виклик. |
| `down [<N>]` | Опуститися на `<N>` рівнів униз по стеку викликів (у бік місця зупинки процесу). | Повертає контекст ближче до місця спрацювання точки зупину або виключення. |
| `info frame` | Надати технічний звіт про активний фрейм: адресу RIP, адресу стека RSP/RBP, збережені регістри. | Допомагає перевірити цілісність стека та виявити пошкодження покажчиків повернення. |
| `info args` | Роздрукувати імена та поточні значення всіх аргументів, переданих у функцію поточного кадру. | Показує вхідні дані, з якими працювала функція перед зупинкою. |
| `info locals` | Роздрукувати імена та значення всіх локальних змінних, розташованих на стеку активного кадру. | Дозволяє оцінити стан обчислень та проміжні результати всередині алгоритму. |

## 4. Точки зупину (Breakpoints) та умовні фільтри

Точки зупину дозволяють перехоплювати потік виконання при досягненні певного рядка коду, функції або адреси пам'яті. Програмна точка зупину тимчасово підміняє перший байт машинної інструкції на опкод `0xCC` (`INT 3` на x86-64), що генерує апаратне переривання `#BP` і переводить процес у стан `TASK_TRACED`.

Для зменшення навантаження на систему при діагностиці високонавантажених циклів застосовуються умовні вирази, які обчислюються в контексті мови C/C++, або одноразові точки зупину, які автоматично демонтуються після першого спрацювання, запобігаючи повторним зупинкам сервісу.

| Команда | Приклад використання | Механізм виконання |
|---|---|---|
| `break <функція>` | `break handle_http_request` | Встановлює опкод `0xCC` на першу дійсну інструкцію прологу зазначеної функції. |
| `break <файл>:<рядок>` | `break worker.cpp:145` | Встановлює точку зупину на адресу коду, що відповідає рядку вихідного тексту в DWARF. |
| `break *0x<адреса>` | `break *0x55aa41208a00` | Встановлює точку зупину на точну віртуальну адресу інструкції без опертя на налагоджувальні символи. |
| `break <місце> if <cond>` | `break send_reply if size > 65535` | Зупиняє процес лише за умови істинності логічного виразу `<cond>`. |
| `tbreak <місце>` | `tbreak initialize_database` | Одноразова точка (Temporary Breakpoint): автоматично видаляється ядром і GDB після першого ж спрацювання. |
| `dprintf <місце>, "<fmt>", args` | `dprintf queue.cpp:80, "Елементів у черзі: %d\n", q_len` | Динамічний друк: друкує повідомлення у вивід без переведення процесу в інтерактивний стан. |
| `condition <N> <умова>` | `condition 2 client_id == 1004` | Призначає або змінює логічну умову для вже існуючої точки зупину з індексом `<N>`. |
| `ignore <N> <лічильник>` | `ignore 1 5000` | Пропускає перші `<лічильник>` спрацювань точки зупину `<N>` перед першою зупинкою. |
| `info breakpoints` | `info breakpoints` (або `i b`) | Виводить повний список встановлених точок зупину, їхній стан (enabled/disabled), адреси та кількість спрацювань. |
| `enable <N>` / `disable <N>` | `disable 1` | Тимчасово вимикає або повертає активність точці зупину `<N>` без її видалення з пам'яті GDB. |
| `delete <N>` | `delete 2` | Повністю демонтує точку зупину з номером `<N>` та відновлює оригінальний байт коду в бінарному образі. |

## 5. Апаратні точки спостереження за пам'яттю (Watchpoints)

Апаратні точки спостереження спираються на спеціалізовані регістри зневадження процесора x86-64 `DR0`–`DR7`. На відміну від програмних точок зупину, вони не змінюють жодного байта в секціях коду чи даних. Процесор апаратно відстежує звернення до шини пам'яті за адресами, записаними в регістрах `DR0`–`DR3`, і генерує виключення `#DB` (Debug Exception, вектор 1) у момент виконання інструкції читання чи запису.

Якщо кількість спостережуваних адрес перевищує 4 або розмір структури даних більший за 8 байтів, GDB перемикається у програмний режим (Software Watchpoint), покроково виконуючи кожну інструкцію програми через `PTRACE_SINGLESTEP`, що сповільнює процес у тисячі разів.

| Команда | Призначення | Апаратна семантика (x86-64 DR7) |
|---|---|---|
| `watch <змінна>` | Зупинити процес при будь-якій модифікації (**записі**) значення вказаної змінної. | Встановлює маску умови `R/W = 01` (Write) для відповідного регістру `DR0`–`DR3`. |
| `watch *(uint64_t*)0x<addr>` | Встановити точку спостереження на запис за конкретною 64-бітною адресою пам'яті. | Прописує лінійну адресу в регістр `DRx` із розміром `LEN = 10` (8 байтів). |
| `rwatch <вираз>` | Зупинити процес при зверненні на **читання** з указаної області пам'яті (Read Watchpoint). | Встановлює маску умови `R/W = 11` (Read/Write) для виявлення операцій читання. |
| `awatch <вираз>` | Зупинити процес при **будь-якому доступі** (читання або запис, Access Watchpoint). | Перехоплює будь-яке звернення до структури даних незалежно від операції. |
| `info watchpoints` | Показати перелік усіх активних точок спостереження та кількість їх спрацювань. | Відображає прив'язку виразів до адрес пам'яті та поточний статус. |
| `set can-use-hw-watchpoints 0` | Примусово вимкнути апаратні регістри CPU та перейти в програмний режим емуляції. | Використовується виключно для налагодження специфічних емуляторів; заборонено на production. |

## 6. Інспекція пам'яті, структур даних та модифікація на льоту

GDB надає потужні засоби форматування даних мовою вихідного коду (C/C++), розіменування складних вказівників, кастингу типів та прямої модифікації оперативної пам'яті. Команда `set` дає змогу оновлювати стан змінних без перезапуску сервісу, що є критично важливим для аварійного розблокування завислих транзакцій.

Команда `x` (Examine Memory) працює безпосередньо з віртуальною пам'яттю за адресою. Її специфікатор формату складається з трьох необов'язкових частин: кількості елементів, символу форматування (`x` — hex, `d` — десяткове зі знаком, `u` — беззнакове, `t` — двійкове, `f` — з рухомою комою, `s` — рядок, `i` — асемблерна інструкція) та розміру одиниці пам'яті (`b` — 1 байт, `h` — 2 байти, `w` — 4 байти, `g` — 8 байтів). Наприклад, `x/4i $rip` виводить чотири наступні інструкції машинного коду від поточної позиції лічильника інструкцій.

| Команда | Формат та приклад | Результат виконання |
|---|---|---|
| `print <вираз>` (або `p`) | `p connection->rx_bytes` | Обчислює значення виразу з урахуванням типів даних поточної мови програмування. |
| `p/x <вираз>` | `p/x flags` | Виводить результат у шістнадцятковому форматі (Hex). |
| `p/t <вираз>` | `p/t mask` | Виводить результат у двійковому форматі у вигляді бітової маски (Binary). |
| `p/s <вираз>` | `p/s buffer_ptr` | Інтерпретує масив байтів як C-рядок із нульовим байтом наприкінці. |
| `p *ptr` | `p *g_config` | Повністю розіменовує вказівник і друкує всі поля відповідної структури даних. |
| `p *(struct T*)0x<addr>` | `p *(struct Session*)0x7fff1020` | Виконує приведення сирої адреси віртуальної пам'яті до конкретного типу структури. |
| `x/<N><fmt><unit> <addr>` | `x/16xw 0x7fff8900` | Досліджує (examine) пам'ять: читає `<N>` елементів формату `<fmt>` (`x`, `d`, `s`, `i`) розміру `<unit>` (`b`, `h`, `w`, `g`). |
| `set var <var> = <val>` | `set var is_healthy = true` | Змінює значення локальної або глобальної змінної безпосередньо у пам'яті процесу. |
| `set {type}0x<addr> = <val>` | `set {int}0x7fff8900 = 0` | Записує нове значення відповідного скалярного типу за абсолютною адресою пам'яті. |
| `call <функція>(<аргументи>)` | `call g_cache.clear()` | Викликає функцію в адресному просторі цільового процесу (Inferior Call) і повертає результат. |

## 7. Перехоплення системних викликів, подій та сигналів

GDB надає спеціальні засоби перехоплення системних подій на рівні ядра (Catchpoints) за допомогою розширень ptrace. На відміну від стандартних точок зупину, catchpoints дозволяють зупиняти процес при генерації системних викликів, сигналів або створенні нових процесів та потоків.

При встановленні `catch syscall` ядро використовує опцію `PTRACE_O_TRACESYSGOOD`, що дозволяє точно розрізняти звичайні сигнали та зупинки на межі системних викликів (`sys_enter` та `sys_exit`).

| Команда | Приклад використання | Семантика перехоплення |
|---|---|---|
| `catch syscall <ім'я_або_номер>` | `catch syscall futex` | Зупиняє процес на вході та виході з вказаного системного виклику. |
| `catch signal <сигнал>` | `catch signal SIGSEGV` | Перехоплює сигнал до того, як його отримає власний обробник процесу. |
| `catch fork` / `catch vfork` | `catch fork` | Зупиняє батьківський процес у момент виклику розгалуження `fork`. |
| `catch exec` | `catch exec` | Перехоплює момент заміни образу процесу викликом `execve`. |
| `catch load [<бібліотека>]` | `catch load libssl.so` | Зупиняє процес у момент динамічного завантаження нової спільної бібліотеки через `dlopen`. |
| `info signals` | `info signals` | Виводить повну таблицю системних сигналів та правила їх обробки налагоджувачем. |

## 8. Протоколювання сесії та автоматизація виводу

Під час екстреного усунення збоїв на віддалених серверах результати діагностики необхідно протоколювати для подальшого командного аналізу (Post-Mortem Review). GDB дозволяє перенаправляти вивід команд у локальні файли або передавати дані через конвеєр (pipe) зовнішнім системним утилітам.

| Команда / Опція | Синтаксис | Призначення |
|---|---|---|
| `set logging file <шлях>` | `set logging file /tmp/gdb_session.log` | Встановлює цільовий файл для збереження виводу сесії. |
| `set logging enabled on` | `set logging enabled on` | Вмикає паралельний запис усіх команд та відповідей у файл журналу. |
| `pipe <cmd> | <shell_cmd>` | `pipe thread apply all bt | grep futex` | Передає вивід внутрішньої команди GDB у довільну оболонку shell для швидкої фільтрації. |
| `set height 0` / `set width 0` | `set height 0` | Вимикає вертикальне та горизонтальне розбиття тексту на сторінки термінала. |

## 9. Безпечне завершення сесії на виробничих серверах

Керування сесією налагодження на живому сервері вимагає суворої дисципліни. Головна мета інженера — отримати діагностичний зріз та від'єднатися без переривання обслуговування клієнтського трафіку.

| Команда / Параметр | Правило використання | Ризики та наслідки |
|---|---|---|
| `detach` | **Обов'язкова команда завершення сесії.** Відновлює оригінальний машинний код, скидає регістри `DR0`–`DR7`, відправляє системний виклик `PTRACE_DETACH` і повертає процес у стан `TASK_RUNNING`. | Безпечно: процес продовжує штатно функціонувати без втрати з'єднань і даних. |
| `quit` (або `q`) | Вихід із середовища GDB. Якщо виконано без попереднього `detach`, GDB запитує дозвіл на вбивство процесу. | **Небезпека:** підтвердження виходу вбиває процес сигналом `SIGKILL`, викликаючи збій сервісу. |
| `set pagination off` | Вимикає очікування натискання клавіші Enter (`---Type <return> to continue---`) при виводі великих списків. | Запобігає зависанню автоматизованих скриптів та конвеєрів діагностики. |
| `set print pretty on` | Вмикає структурне форматування виводу складних об'єктів C/C++ із відступами та розбивкою по полях. | Суттєво спрощує візуальний аналіз розгалужених структур даних у терміналі. |
| `handle <сигнал> nostop noprint pass` | Налаштовує обробку системних сигналів (наприклад, `SIGPIPE` або `SIGUSR1`), дозволяючи їм проходити у програму без паузи у GDB. | Запобігає зупинці налагоджувача на штатних внутрішніх сигналах комунікації процесу. |
