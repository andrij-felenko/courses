Виробничий демон обробки фінансових замовлень із PID `18492` раптово перестає відповідати на мережеві запити. Кількість активних з'єднань у черзі зростає, навантаження на процесор падає до нуля відсотків, а у файлах журналів панує тиша. Простий перезапуск процесу через `systemctl restart` відновить працездатність на кілька годин, але назавжди знищить транзитний стан оперативної пам'яті: незавершені транзакції клієнтів, черги завдань та точне розташування взаємних блокувань у пам'яті, без яких розробники не зможуть знайти першопричину збою. Щоб з'ясувати стан програми без її перезапуску, системний інженер підключає налагоджувач безпосередньо до працюючого процесу в пам'яті сервера, заморожує його виконання, інспектує стек викликів усіх потоків і безпечно від'єднується, не втрачаючи жодного байта даних.

Інструмент `gdb` (GNU Debugger) надає механізм для такої живої діагностики. Проте підключення до працюючого сервісу на виробничому сервері принципово відрізняється від запуску бінарного файлу всередині налагоджувача під час розробки: воно вимагає подолання бар'єрів безпеки ядра Linux, контролю апаратних переривань процесора, розуміння архітектури регістрів зневадження та суворого дотримання правил експлуатації, щоб не перетворити діагностичну паузу на аварійне падіння всієї системи.

## 1. Анатомія підключення GDB до живого процесу

Коли оператор виконує команду `gdb -p 18492` (або `gdb --pid 18492`), налагоджувач не створює новий процес через `fork` та `execve`. Натомість GDB звертається до ядра через системний виклик `ptrace(2)` із запитом `PTRACE_ATTACH` (або новішим `PTRACE_SEIZE`), передаючи цільовий ідентифікатор процесу:

:::tabs
@tab C
```c
ptrace(PTRACE_ATTACH, 18492, NULL, NULL);
```
@tab C++
```cpp
ptrace(PTRACE_ATTACH, 18492, nullptr, nullptr);
```
:::

Системний виклик `ptrace` ініціює складний ланцюг подій у підсистемі керування процесами ядра Linux:

1. **Перевірка прав та ініціалізація зв'язку.** Ядро перевіряє право налагоджувача (англ. *tracer*) керувати цільовим процесом (англ. *tracee*). Якщо перевірка успішна, у структурі `task_struct` цільового процесу встановлюється вказівник на структуру налагоджувача `ptrace`, а в полі `ptrace_flags` активуються прапорці трасування.
2. **Доставка сигналу зупинки.** Ядро надсилає цільовому процесу внутрішній сигнал `SIGSTOP`. На відміну від звичайних сигналів простору користувача, сигнал `SIGSTOP` від ptrace не може бути заблокований, проігнорований або перехоплений власним обробником процесу (навіть якщо програма викликала `sigaction` для інших сигналів).
3. **Перехід у стан зупинки.** Щойно потоки цільового процесу доходять до точки переривання або повернення із системного виклику, планувальник ядра переводить їхній стан зі звичайного `TASK_RUNNING` або `TASK_INTERRUPTIBLE` у спеціальний стан `TASK_TRACED` (позначається літерою `t` або `T` у виводі `ps` та `/proc/<PID>/status`).
4. **Сповіщення налагоджувача.** GDB у цей час перебуває у блокуючому виклику `waitpid(18492, &status, WUNTRACED)`. Щойно цільовий процес переходить у стан `TASK_TRACED`, ядро розблоковує `waitpid`, повертаючи статус із макросом `WIFSTOPPED(status) == true` та номером сигналу `WSTOPSIG(status) == SIGSTOP`.

![Схема системного виклику ptrace(PTRACE_ATTACH): перевірка безпеки Yama LSM, зупинка цільового процесу сигналом SIGSTOP, перехід у TASK_TRACED та безпечне від'єднання](/root/course/unix/live-debug-session/img/ptrace-attach-sequence.svg)

*Системний виклик ptrace заморожує процес через SIGSTOP і переводить його в стан TASK_TRACED, даючи налагоджувачу повний доступ до пам'яті й регістрів.*

У сучасних багатопотокових сервісах процес складається не з однієї нитки виконання, а з групи потоків (англ. *Thread Group*), де кожен потік має власний ідентифікатор потоку (англ. *Task ID / Thread ID*, TID у ядрі або LWP у POSIX), тоді як спільний ідентифікатор групи (TGID) відповідає загальному PID процесу.

Коли GDB підключається через `PTRACE_ATTACH` до основного PID, ядро спочатку зупиняє лише головний потік групи. Далі GDB звертається до псевдофайлової системи `/proc/18492/task/` або використовує бібліотеку `libthread_db.so`, знаходить усі супутні потоки (TID) процесу і по черзі викликає `PTRACE_ATTACH` для кожного з них. Лише після того, як **всі** потоки процесу підтвердили перехід у стан `TASK_TRACED`, GDB завантажує таблиці символів і виводить командний рядок `(gdb)` для оператора.

Якщо в момент підключення потік цільового процесу перебував усередині повільного блокуючого системного виклику (наприклад, `epoll_wait`, `nanosleep` або `read` із сокета), ядро перериває виконання виклику внутрішнім кодом `-ERESTARTSYS`. Коли GDB згодом відпустить процес командою `continue` чи `detach`, ядро прозоро перезапустить перерваний системний виклик, не повертаючи процесу помилку `EINTR`.

## 2. Бар'єри безпеки ядра: Yama LSM, ptrace_scope та CAP_SYS_PTRACE

При спробі виконати `gdb -p <PID>` на сучасних дистрибутивах Linux (Ubuntu, Debian, RHEL) під звичайним непривілейованим користувачем оператор нерідко отримує відмову:

```text
Could not attach to process.  If your debugger is not configured
to allow attaching to processes, you may need to change the
ptrace_scope setting or run as root.
ptrace: Operation not permitted.
```

Навіть якщо користувач запускає GDB від того самого облікового запису (наприклад, `uid=1000`), під яким працює досліджуваний процес, ядро блокує доступ. Причиною є модуль безпеки **Yama LSM** (англ. *Linux Security Module Yama*, реалізований у файлі ядра `security/yama/yama_lsm.c`).

Модуль Yama був створений для блокування поширеного вектору атак: якщо зловмисник зламав один непривілейований процес користувача (наприклад, веб-браузер або мережевий клієнт), без обмежень Yama він міг би виконати `ptrace(PTRACE_ATTACH)` до будь-якого іншого процесу того самого користувача (наприклад, до SSH-агента, GPG-демона чи менеджера паролів) і безперешкодно викрасти криптографічні ключі та токени з оперативної пам'яті.

Рівень обмежень Yama задається через файл конфігурації `/proc/sys/kernel/yama/ptrace_scope`. Доступні чотири режими роботи:

| Рівень (`ptrace_scope`) | Назва режиму | Семантика доступу |
|---|---|---|
| `0` | Класичний (*Classic ptrace*) | Дозволяє процес підключатися до будь-якого іншого процесу з тим самим UID (якщо процес не є setuid/setgid бінарником). |
| `1` | Обмежений (*Restricted ptrace*) | **Значення за замовчуванням у більшості систем.** Процес може викликати `PTRACE_ATTACH` лише до своїх прямих нащадків (процесів, створених через `fork`), або до процесів, які явно дозволили трасування через виклик `prctl`. |
| `2` | Лише адміністратор (*Admin-only*) | Підключення до чужих процесів дозволено виключно процесам із привілеєм ядра `CAP_SYS_PTRACE` (користувач `root` або запуск через `sudo`). |
| `3` | Повне блокування (*Locked-down*) | Виклик `ptrace` повністю заблоковано в усій системі. Жоден процес, включно з `root`, не може підключитися. Режим незворотний до наступного перезавантаження хоста. |

У режимі `ptrace_scope = 1` програма може явно відкрити доступ для стороннього налагоджувача за допомогою системного виклику `prctl(2)` з опцією `PR_SET_PTRACER`. Це дає змогу налагоджувати сервіс без підвищення прав до суперкористувача:

:::tabs
@tab C
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/prctl.h>

void enable_debugging_access(void) {
    // Дозволяємо будь-якому процесу з тим самим UID підключатися через ptrace
    if (prctl(PR_SET_PTRACER, PR_SET_PTRACER_ANY, 0, 0, 0) == -1) {
        perror("Помилка налаштування PR_SET_PTRACER");
    } else {
        printf("Процес (PID: %d) відкритий для підключення GDB\n", getpid());
    }
}
```
@tab C++
```cpp
#include <iostream>
#include <system_error>
#include <unistd.h>
#include <sys/prctl.h>

void enable_debugging_access() {
    // Дозволяємо будь-якому процесу з тим самим UID підключатися через ptrace
    if (prctl(PR_SET_PTRACER, PR_SET_PTRACER_ANY, 0, 0, 0) == -1) {
        throw std::system_error(errno, std::generic_category(), "Помилка налаштування PR_SET_PTRACER");
    }
    std::cout << "Процес (PID: " << getpid() << ") відкритий для підключення GDB\n";
}
```
:::

У виробничих середовищах із контейнеризацією (Docker, Kubernetes) процеси всередині контейнера за замовчуванням позбавлені привілею `CAP_SYS_PTRACE`. Спроба виконати `gdb -p` всередині контейнера завершиться помилкою `Operation not permitted`, навіть під користувачем `root`. Для ввімкнення можливості діагностики контейнер слід запускати з прапорцем `--cap-add=SYS_PTRACE` або підключатися з хостової системи, де адміністратор має повні права над просторами імен.

## 3. Діагностика завислих багатопотокових процесів

Після успішного підключення до процесу першочерговим завданням є з'ясування того, чим зайнятий кожен потік програми. У багатопотокових сервісах 90% зависань спричинені або взаємними блокуваннями м'ютексів (англ. *deadlock*), або нескінченними циклами (англ. *livelock*), або вичерпанням пулу з'єднань із базою даних.

### Список потоків та груповий бектрейс

Команда `info threads` виводить повний перелік ниток виконання процесу:

```text
(gdb) info threads
  Id   Target Id                                   Frame 
* 1    Thread 0x7fa2b9881740 (LWP 18492 "srv-main") 0x00007fa2b99a1976 in __epoll_wait ()
  2    Thread 0x7fa2b9080640 (LWP 18493 "worker-1") 0x00007fa2b99a4238 in __futex_abstimed_wait_common64 ()
  3    Thread 0x7fa2b887f640 (LWP 18494 "worker-2") 0x00007fa2b99a4238 in __futex_abstimed_wait_common64 ()
  4    Thread 0x7fa2b807e640 (LWP 18495 "metrics")  0x00007fa2b99aa102 in clock_nanosleep ()
```

Зірочка `*` вказує на активний потік, чий контекст зараз відкритий у налагоджувачі. Для швидкої діагностики всієї системи незамінна пакетна команда `thread apply all bt` (або `thread apply all bt full`), яка проходить по всіх потоках і розгортає повний стек викликів із значеннями аргументів та локальних змінних:

```text
(gdb) thread apply all bt full
```

Якщо два або більше потоків зупинилися всередині системного виклику `futex` (у функціях glibc `__pthread_mutex_lock_wait` або `__futex_abstimed_wait_common64`), це прямий сигнал про блокування синхронізації.

![Схема діагностики завислого багатопотокового процесу: список потоків, розгортання стека викликів та інспекція фреймів даних](/root/course/unix/live-debug-session/img/live-inspection-thread-frames.svg)

*Інспекція фреймів стека дозволяє виявити взаємне блокування між потоками 2 і 3 за адресами очікуваних м'ютексів.*

### Навігація фреймами стека та інспекція даних

Стек викликів організований у вигляді каскаду фреймів (англ. *stack frames*), пронумерованих від нуля:
- Фрейм `#0` — функція, яка безпосередньо виконується в момент зупинки (наприклад, системний виклик у ядрі або асемблерна інструкція у glibc).
- Фрейм `#1` — функція, яка викликала фрейм `#0`.
- Фрейм `#N` — коренева функція запуску потоку (`main` або точка входу `pthread_create`).

Для переходу між фреймами використовується команда `frame <N>` (або скорочено `f <N>`), а також навігаційні команди `up` (перехід на рівень вище у бік викликача) та `down` (перехід на рівень нижче у бік пастки).

```text
(gdb) thread 2
[Switching to thread 2 (Thread 0x7fa2b9080640 (LWP 18493))]
(gdb) frame 2
#2  0x000055c8f12014c0 in OrderProcessor::process_order (this=0x55c8f280a010, order_id=918429) at order_processor.cpp:114
114         std::lock_guard<std::mutex> lock(account_b->mutex);
```

Перейшовши у фрейм прикладного коду `#2`, інженер отримує доступ до локального простору імен цієї функції:
- `info args` — виводить список і значення всіх вхідних аргументів функції.
- `info locals` — показує стан усіх локальних змінних, виділених на стеку поточного кадру.
- `print <вираз>` (або `p`) — обчислює та виводить значення довільного виразу мовою C/C++, включно з викликом методів та розіменуванням складних структур.

```text
(gdb) info args
this = 0x55c8f280a010
order_id = 918429
(gdb) p *this
$1 = {
  m_gateway_id = 42,
  m_is_active = true,
  m_queue_size = 1480,
  m_primary_account = 0x55c8f280b100
}
(gdb) p *(Account*)0x55c8f280b100
$2 = {
  account_id = 101,
  balance = 450000.0,
  mutex = { ... }
}
```

Для читання сирих ділянок пам'яті використовується команда `x` (англ. *examine*):
- `x/16xg $rsp` — надрукувати 16 восьмибайтних слів у шістнадцятковому форматі, починаючи з вершини стека.
- `x/s 0x7fff89a010` — прочитати нуль-термінований рядок тексту за вказаною адресою.

Повний перелік параметрів та скорочень наведено у [довіднику команд GDB](root:unix/live-debug-session/api-gdb-live-commands.md).

### Проблема відсутності налагоджувальних символів

Якщо бінарний файл утиліти на сервері був очищений від символів командою `strip` (що є стандартом для зменшення розміру дистрибутивів), вивід `bt` замість назв функцій та номерів рядків покаже невизначені адреси:

```text
#0  0x00007fa2b99a4238 in ?? () from /lib/x86_64-linux-gnu/libc.so.6
#1  0x000055c8f12014c0 in ?? ()
```

У такому разі GDB не може розмотати стек викликів без таблиць розмотування DWARF або покажчиків кадру (Frame Pointers). Для відновлення видимості коду не потрібно перезапускати процес — достатньо завантажити окремий файл символів або увімкнути службу `debuginfod`:

```text
(gdb) symbol-file /usr/lib/debug/usr/bin/order_processor.debug
(gdb) set debuginfod enabled on
```

GDB зіставить `Build-ID` працюючого процесу з локальним або віддаленим файлом символів і миттєво відновить імена функцій, типи змінних та рядки коду.

## 4. Розумне керування точками зупину: Breakpoints та апаратні Watchpoints

У живій системі недостатньо просто зафіксувати дедлок — часто необхідно спіймати момент, коли певна змінна набуває помилкового значення або викликається функція з недійсним покажчиком.

### Програмні точки зупину (Software Breakpoints)

Коли інженер вводить команду `break order_processor.cpp:120`, GDB виконує такі дії під капотом:
1. За допомогою запиту `PTRACE_PEEKTEXT` читає оригінальний байт машинної інструкції за цільовою адресою.
2. Зберігає цей оригінальний байт у своїй внутрішній таблиці точок зупину.
3. За допомогою запиту `PTRACE_POKETEXT` (або запису у `/proc/<PID>/mem`) перезаписує цей байт спеціальним однобайтним опкодом `0xCC`.

На архітектурі x86-64 опкод `0xCC` відповідає інструкції `INT 3`. Коли процесор доходить до цієї адреси, він генерує виключення `#BP` (вектор переривання 3). Ядро Linux перехоплює це виключення, визначає, що процес трасується, і надсилає йому сигнал `SIGTRAP`.

GDB перехоплює `SIGTRAP`, відновлює оригінальний байт інструкції в пам'яті, декрементує покажчик інструкцій `%rip` на 1 байт назад і виводить зупинку користувачеві. Коли виконання продовжується, GDB виконує відновлену інструкцію в режимі покрокового виконання (`PTRACE_SINGLESTEP`), повертає опкод `0xCC` на місце і відновлює звичайний біг програми.

### Умовні точки зупину (Conditional Breakpoints)

У високонавантажених сервісах функція може викликатися мільйони разів на секунду. Звичайна точка зупину зупинить сервер на першому ж запиті. Для фільтрації застосовують умовні точки:

```text
(gdb) break process_payment if order_amount > 1000000.0 && client_id == 4812
```

Проте слід враховувати ціну умовних точок зупину: ядро перериває виконання процесу на опкоді `0xCC` **при кожному виклику**, перемикає контекст у GDB, GDB обчислює логічний вираз у просторі користувача, і якщо результат `false`, надсилає `PTRACE_CONT` для продовження. На мільйонах операцій цей цикл перемикання контекстів сповільнює роботу процесу в сотні разів.

Якщо потрібно лише логувати значення без повної інтерактивної зупинки, ефективніше використовувати динамичний друк `dprintf`:

```text
(gdb) dprintf process_payment, "Замовлення ID: %lu, Сума: %.2f\n", order_id, order_amount
```

### Точки спостереження за пам'яттю (Watchpoints) та регістри x86-64 DR0–DR7

Коли пам'ять пошкоджується непомітно (наприклад, гонитва даних або переповнення буфера псує поле стану), точку зупину в коді поставити неможливо, оскільки невідомо, яка саме інструкція здійснює некоректний запис. У таких випадках використовують точки спостереження за пам'яттю (англ. *watchpoints*):

- `watch variable` — зупинити процес при будь-якому **записі** у змінну.
- `rwatch variable` — зупинити процес при **читанні** змінної (Read Watchpoint).
- `awatch variable` — зупинити процес при **будь-якому доступі** (Access Watchpoint: читання або запис).

![Апаратні регістри зневадження x86-64 DR0-DR7 та порівняння апаратного watchpoint із програмним емульованим режимом](/root/course/unix/live-debug-session/img/hardware-watchpoint-dr-registers.svg)

*Апаратні watchpoints використовують регістри DR0-DR7 процесора, забезпечуючи перехоплення доступу до пам'яті з нульовим оверхедом під час виконання.*

На архітектурі x86-64 точки спостереження спираються на спеціальні **апаратні регістри зневадження** (англ. *Debug Registers*):

1. **Регістри адрес `DR0`, `DR1`, `DR2`, `DR3`.** Кожен із цих чотирьох регістрів зберігає 64-бітну лінійну віртуальну адресу комірки пам'яті, за якою ведеться спостереження.
2. **Регістр стану `DR6` (Debug Status Register).** Коли апаратура процесора виявляє збіг адреси на шині пам'яті, відповідні біти `B0`–`B3` у регістрі `DR6` встановлюються в `1`, вказуючи, який саме з регістрів `DR0`–`DR3` викликав спрацювання.
3. **Регістр керування `DR7` (Debug Control Register).** Задає правила спрацювання:
   - Біти `L0`–`L3` та `G0`–`G3` — локальне та глобальне ввімкнення відповідних точок 0–3.
   - Поля `R/W0`–`R/W3` (по 2 біти кожне) визначають тип операції: `00` — виконання інструкції, `01` — лише запис даних, `11` — читання або запис даних.
   - Поля `LEN0`–`LEN3` (по 2 біти кожне) визначають розмір контрольованої області: `00` — 1 байт, `01` — 2 байти, `10` — 8 байтів (на x86-64), `11` — 4 байти.

Коли процес виконує команду запису або читання за адресою, записаною в `DR0`, процесор автоматично генерує виключення `#DB` (вектор 1 — Debug Exception) **без модифікації коду програми**. Байти пам'яті залишаються абсолютно чистими, а програма працює на повній апаратній швидкості процесора.

Якщо інженер встановлює спостереження за об'єктом, розмір якого перевищує 8 байтів, або якщо вичерпано ліміт у 4 апаратні регістри, GDB змушений перейти в режим **програмного спостереження** (англ. *Software Watchpoint*). У цьому режимі GDB переводить процес у покрокове виконання (`single-step`), зупиняючи CPU після **кожної машинної інструкції**, вичитує значення змінної через `ptrace` і порівнює його з попереднім. Це призводить до катастрофічного падіння швидкодії (у 10 000 разів і більше), що є неприпустимим на живих серверах.

## 5. Правила безпеки та втручання на виробничих серверах

Підключення GDB до живого продуктивного вузла — це хірургічна операція з високим рівнем ризику. Необережна команда може призвести до падіння процесу або каскадного збою всієї інфраструктури.

### Модифікація пам'яті на льоту та виклики функцій (Inferior Calls)

GDB дозволяє не лише читати, а й безпосередньо змінювати стан пам'яті процесу:

```text
(gdb) set var is_maintenance_mode = false
(gdb) set {int}0x7fff8900a0 = 1
```

Крім зміни окремих змінних, GDB підтримує виклик прикладних функцій у контексті процесу через команду `call` (англ. *Inferior Function Call*):

```text
(gdb) call g_metrics.dump_to_file("/tmp/metrics_snapshot.json")
```

Під капотом виклику `call` GDB виконує такі складні маніпуляції:
1. Зберігає поточний стан усіх регістрів процесора (`pt_regs`).
2. Виділяє фіктивний фрейм на стеку користувача цільового процесу (зсуваючи `%rsp`).
3. Записує аргументи функції у регістри згідно з ABI (`%rdi`, `%rsi`, `%rdx`).
4. Записує у вершину стека фіктивну адресу повернення, за якою попередньо встановлено опкод `0xCC` (`INT 3`).
5. Встановлює лічильник інструкцій `%rip` на початок викликаної функції та надсилає `PTRACE_CONT`.
6. Після завершення функції процесор потрапляє на `INT 3`, GDB перехоплює зупинку, читає повернене значення з регістра `%rax` і повністю відновлює початкові регістри та стек процесу.

Використання команди `call` на виробництві несе серйозні небезпеки:
- Якщо викликана функція спробує захопити м'ютекс, який вже утримується іншим замороженим потоком цього процесу, виникне внутрішній дедлок, і GDB зависне разом із процесом.
- Якщо всередині функції відбудеться аварійне завершення (наприклад, розіменування нульового покажчика `SIGSEGV`), процес негайно впаде і завершить роботу.

Практичний приклад розблокування завислого багатопотокового вузла розібрано у [практикумі з дедлоку](root:unix/live-debug-session/proj-live-deadlock-inspect.md).

### Безпечне від'єднання: detach проти quit

Найбільш критична помилка інженерів-початківців — спроба вийти з налагоджувача стандартною командою `quit` або комбінацією клавіш `Ctrl+D` / `Ctrl+C`.

```text
(gdb) quit
A debugging session is active.

    Inferior 1 [process 18492] will be killed.

Quit anyway? (y or n) 
```

Якщо підтвердити вихід клавішею `y`, GDB надішле процесу сигнал `SIGKILL` і **повністю знищить продуктивний сервіс**.

Єдиний правильний спосіб завершення діагностичної сесії — явна команда **`detach`**:

```text
(gdb) detach
Detaching from program: /usr/bin/order_processor, process 18492
[Inferior 1 (process 18492) detached]
(gdb) quit
```

Під час виконання `detach`:
- GDB видаляє всі встановлені програмні точки зупину, відновлюючи оригінальні байти інструкцій у секції коду.
- Очищає апаратні регістри зневадження `DR0`–`DR7`.
- Надсилає системний виклик `ptrace(PTRACE_DETACH, pid, NULL, 0)`.
- Ядро скидає прапорці трасування, повертає всі потоки процесу у чергу планувальника (`TASK_RUNNING`), і програма продовжує своє виконання у звичайному режимі без втрати з'єднань.

### Побічні ефекти зупинки живого процесу на сервері

Коли GDB підключається до процесу і тримає його в стані `TASK_TRACED`, весь процес повністю зупинений. Для зовнішнього світу це еквівалентно раптовому зависанню вузла. Необхідно враховувати каскадні реакції інфраструктури:

1. **Вартові таймери (Watchdog).** Якщо служба працює під керуванням `systemd` з увімкненим параметром `WatchdogSec=30s`, демон повинен регулярно надсилати сповіщення `sd_notify("WATCHDOG=1")`. Якщо через зупинку в GDB черговий сигнал не надійде протягом 30 секунд, systemd вважатиме процес мертвим і примусово вб'є його сигналом `SIGABRT` / `SIGKILL`. Перед підключенням до таких служб слід тимчасово вимкнути таймери: `systemctl service-watchdogs no`.
2. **Перевірки стану балансувальників (Health Checks).** Балансувальники навантаження (HAProxy, Nginx, Envoy, Kubernetes Liveness Probes) опитують вузол кожні 2–5 секунд. Зупинка процесу призведе до того, що балансувальник визнає ноду аварійною та виведе її з пулу маршрутизації. Рекомендується заздалегідь зняти трафік із досліджуваного сервера (drain node) перед початком сесії.
3. **Мережеві таймаути клієнтів.** Клієнтські запити, що перебували в обробці в момент зупинки, впадуть за таймаутом читання сокета (`Read Timeout`).

### Швидкий неінтерактивний знімок (Batch Mode)

Щоб мінімізувати час зупинки продуктивного процесу до кількох мілісекунд, діагностику слід виконувати у неінтерактивному пакетному режимі GDB (`batch mode`). Налагоджувач підключається, за частки секунди знімає повний бектрейс усіх потоків у файл і миттєво від'єднується:

```bash
sudo gdb -p 18492 -batch \
    -ex "set pagination off" \
    -ex "set print pretty on" \
    -ex "thread apply all bt full" \
    -ex "detach" > /var/log/debug_dump_$(date +%s).txt
```

Такий підхід скорочує паузу в роботі сервісу до 50–100 мілісекунд, що не викликає спрацювання сторожових таймерів і дозволяє інженерам спокійно аналізувати детальний стан пам'яті та стеків викликів офлайн.
