Інженер розгортає новий бекенд-сервіс у контейнері Docker на сервері під керуванням Linux. У конфігурації контейнера дотримано загальноприйнятих рекомендацій безпеки: усередині образу створено непривілейованого користувача з `UID 1000`, а робочий каталог для збереження стану змонтовано з хостової файлової системи командою `docker run -v /var/data/storage:/app/data my-service:v1`. Одразу після запуску застосунок падає з системною помилкою `EACCES (Permission Denied)` під час першої ж спроби створити файл журналу.

Спроба зв'язатися з сусіднім контейнером бази даних за його іменем `postgres-db` повертає мережеву помилку `NXDOMAIN (Name or service not known)`. Коли ж адміністратор намагається зупинити збійний контейнер командою `docker stop`, термінал блокується рівно на десять секунд, після чого демон примусово знищує процес сигналом `SIGKILL`, залишаючи в системній таблиці хоста десятки незакритих процесів-зомбі.

Кожна з цих трьох несправностей виглядає як загадковий дефект прикладного коду або конфігурації Docker. Проте насправді всі вони мають спільне коріння: розрив між абстракцією контейнера в просторі користувача та суворою логікою монолітного ядра Linux.

### 1. Ілюзія окремої машини та реальність спільного ядра

Широко розповсюджене уявлення про контейнер як про «легковажну віртуальну машину» є головним джерелом помилок під час налагодження виробничих систем. У віртуальній машині гіпервізор емулює фізичне обладнання, а всередині гостьової ОС працює власне повноцінне ядро, власний планувальник завдань, незалежні драйвери пристроїв та власна коренева підсистема ініціалізації.

Контейнер не має власного ядра. Усі процеси, запущені всередині всіх контейнерів на сервері, є звичайними записами `struct task_struct` у глобальній таблиці єдиного монолітного ядра хоста.

Коли процес у контейнері викликає системний виклик `open()`, `fork()`, `socket()` або `kill()`, керування передається в той самий спільний код ядра, що й для звичайного хостового демона `systemd` чи фонового скрипта адміністратора. Ізоляція забезпечується не апаратною віртуалізацією, а системними фільтрами ядра:
* **Простори імен (Namespaces):** підміняють значення, які процес бачить у відповідь на інформаційні виклики (власний список номерів PID, персональний стек інтерфейсів, дерево монтувань VFS).
* **Контрольні групи (cgroups v2):** обмежують кількість ресурсів, які ядро дозволяє виділити групі задач (квота CPU, ліміт сторінок пам'яті, максимальна кількість процесів).

Ця архітектура створює принципову асиметрію. Простір користувача всередині контейнера бачить цілісну, ізольовану операційну систему: власний каталог `/etc/passwd`, де користувач `node` має номер `1000`, свій локальний мережевий інтерфейс `eth0` та свій головний процес із номером `PID 1`.

Проте ядро Linux оперує зовсім іншими категоріями:
1. Ядро не вміє читати текстові файли `/etc/passwd` або `/etc/group` під час перевірки прав доступу VFS. Воно оперує виключно 32-бітними числовими значеннями `uid_t` та `gid_t`.
2. Мережевий стек ядра керується таблицями маршрутизації та правилами `iptables`/`nftables`, де за замовчуванням немає магічного перетворення імен контейнерів на IP-адреси.
3. Модель процесів Unix покладає на процес із номером `PID 1` унікальні системні зобов'язання щодо обробки сигналів та прибирання осиротілих нащадків, яких звичайні веб-застосунки просто не містять у своєму коді.

Розгляньмо кожен із цих трьох конфліктів на рівні структур ядра, системних викликів та інженерних способів їх усунення.

### 2. Конфлікт прав у томах (Bind Mounts): розрив числових UID/GID

Найпоширеніша проблема під час роботи з томами монтування (`docker run -v` або секція `volumes:` у Docker Compose) — це раптова відмова у доступі `EACCES (Permission Denied)` або, навпаки, створення на хості файлів, які неможливо відредагувати без прав суперкористувача.

Щоб зрозуміти механізм цього збою, необхідно простежити, як віртуальна файлова система Linux (VFS) виконує авторизацію системного виклику `open()`.

У ядрі Linux перевірка прав доступу (DAC — Discretionary Access Control) базується на прямому порівнянні бітових масок та числових креденшелів. Нижче наведено алгоритмічний еквівалент цієї перевірки мовами C та C++:

:::tabs
@tab:c
```c
#include <sys/types.h>
#include <sys/stat.h>
#include <errno.h>

/* Імітація алгоритму перевірки прав VFS ядра Linux */
int check_dac_permission(uid_t current_fsuid, gid_t current_fsgid,
                         uid_t inode_uid, gid_t inode_gid,
                         mode_t inode_mode, int requested_mask)
{
    /* 1. Якщо процес є власником інода, перевіряються біти власника (0700) */
    if (current_fsuid == inode_uid) {
        if ((inode_mode & (requested_mask << 6)) == (requested_mask << 6))
            return 0;
        return -EACCES;
    }

    /* 2. Якщо процес входить до групи інода, перевіряються біти групи (0070) */
    if (current_fsgid == inode_gid) {
        if ((inode_mode & (requested_mask << 3)) == (requested_mask << 3))
            return 0;
        return -EACCES;
    }

    /* 3. Для всіх інших користувачів перевіряються біти others (0007) */
    if ((inode_mode & requested_mask) == (mode_t)requested_mask)
        return 0;

    return -EACCES;
}
```
@tab:cpp
```cpp
#include <cstdint>
#include <sys/types.h>
#include <sys/stat.h>
#include <cerrno>

// Ідіоматична C++ реалізація алгоритму перевірки прав VFS
enum class AccessMode : uint32_t {
    Read = 4,
    Write = 2,
    Execute = 1
};

[[nodiscard]] constexpr int check_dac_permission(
    uid_t current_fsuid, gid_t current_fsgid,
    uid_t inode_uid, gid_t inode_gid,
    mode_t inode_mode, AccessMode requested) noexcept
{
    const auto req = static_cast<uint32_t>(requested);

    // 1. Перевірка прав власника
    if (current_fsuid == inode_uid) {
        return ((inode_mode >> 6) & req) == req ? 0 : -EACCES;
    }

    // 2. Перевірка прав групи
    if (current_fsgid == inode_gid) {
        return ((inode_mode >> 3) & req) == req ? 0 : -EACCES;
    }

    // 3. Перевірка прав сторонніх користувачів
    return (inode_mode & req) == req ? 0 : -EACCES;
}
```
:::

Коли процес викликає `open("/app/data/file.txt", O_RDWR)`, VFS витягує з інода файлової системи два поля: `inode->i_uid` (числовий ідентифікатор власника, записаний у структурі інода на Ext4 чи XFS) та `inode->i_mode` (бітова маска прав доступу `rwxrwxrwx`). Потім ядро порівнює `inode->i_uid` з поточним ідентифікатором процесу `current_fsuid()` (файловий UID структури `struct cred`, що належить `task_struct`).

Текстові імена користувачів (`root`, `ubuntu`, `developer`, `app`, `nginx`) є лише абстракцією простору користувача. Стандартна бібліотека C (`glibc` або `musl`) перетворює ім'я в число під час входу в систему за допомогою функції `getpwnam()`, яка парсить текстовий файл `/etc/passwd`. Ядро Linux взагалі нічого не знає про файл `/etc/passwd` усередині контейнера.

*Конфлікт числових ідентифікаторів у VFS Linux: невідповідність між хостовим власником інода та контейнерним процесом, і його розв'язання через User Namespaces та ID-mapped mounts.*

#### 2.1. Анатомія двох протилежних аномалій

Коли хостовий каталог монтується всередину контейнера за допомогою механізму Bind Mount, ядро не копіює файли. Воно монтує ту саму структуру VFS безпосередньо в таблицю простору імен монтувань контейнера. Виникає два типові сценарії відмови:

**Сценарій 1: Контейнер від непривілейованого користувача (UID mismatch).**
1. Розробник на хості створив каталог `/var/data` під своїм користувачем (наприклад, `developer` із `UID 1005`). Права каталогу: `drwxr-x---` (0750, де запис дозволено лише власнику).
2. У Dockerfile вказано директиву `USER node`. Усередині базового образу Alpine/Debian користувач `node` має фіксований числовий `UID 1000`.
3. Контейнер стартує. Процес намагається створити файл у змонтованому томі.
4. Ядро перевіряє `current_fsuid()` (1000) проти `inode->i_uid` каталогу (1005). Вони не збігаються.
5. Процес не є власником, не входить до групи `1005`, а біти для інших (`others`) забороняють запис.
6. Ядро негайно повертає код `-EACCES` (`Permission Denied`).

**Сценарій 2: Запуск під root за замовчуванням (Host pollution).**
1. Контейнер запускається без зміни користувача (за замовчуванням у Docker це `root`, тобто `UID 0`).
2. Процес створює конфігураційні файли або кеш у змонтованому каталозі хоста.
3. Оскільки `current_fsuid()` дорівнює `0`, VFS записує у відповідні іноди на диску `inode->i_uid = 0` та `inode->i_gid = 0`.
4. Коли контейнер зупиняється, звичайний користувач хоста (`UID 1000`) не може відредагувати, перезаписати або видалити створені файли, оскільки вони належать `root` хоста. Спроба видалити такий каталог вимагає виклику `sudo rm -rf`.

#### 2.2. Інженерні методи виправлення

Існує чотири системні способи розв'язання конфлікту прав:

##### Спосіб А: Явне вирівнювання ідентифікаторів при запуску
Найпростіший підхід — передати числовий ідентифікатор поточного користувача хоста безпосередньо демону контейнеризації:

```bash
docker run --rm -u $(id -u):$(id -g) -v $(pwd)/data:/app/data my-app
```

Прапорець `-u` перевизначає структуру `struct cred` новоствореного процесу. Процес у контейнері отримує той самий числовий `UID`, що й користувач хоста, завдяки чому VFS надає повні права на запис у змонтований каталог.

*Де ламається підхід:* якщо застосунку всередині контейнера потрібен доступ до власних системних файлів у `/etc` або `/var/run`, створених під час збірки образу під `root`, непривілейований `UID` хоста може отримати `Permission Denied` вже на внутрішніх шляхах самого образу. Крім того, у файлі `/etc/passwd` контейнера такий UID може бути відсутній, що збиває з пантелику деякі бібліотеки, які вимагають наявності імені облікового запису.

##### Спосіб Б: User Namespaces у Docker (`userns-remap`)
Більш фундаментальне рішення полягає у використанні просторів імен користувачів (User Namespaces, прапорець `CLONE_NEWUSER`).

У файлі `/etc/docker/daemon.json` налаштовується відображення:
```json
{
  "userns-remap": "default"
}
```

Під час старту демон створює на хості користувача `dockremap` і виділяє йому діапазон підпорядкованих ідентифікаторів у файлах `/etc/subuid` та `/etc/subgid` (наприклад, `dockremap:100000:65536`).

Коли контейнер працює під `root` (UID 0 всередині контейнера), ядро транслює всі системні виклики через таблицю `/proc/[pid]/uid_map`. Для хостової файлової системи процес має числовий `KUID 100000`. Якщо такий процес спробує зламати контейнер або модифікувати файли хоста, для хостового ядра він буде повністю непривілейованим стороннім процесом.

##### Спосіб В: Безкореневі контейнери (Rootless Podman)
Утиліта Podman реалізує протилежну схему відображення простору користувачів. Звичайний користувач хоста з `UID 1000` запускає контейнер без прав суперкористувача. За допомогою допоміжних утиліт `newuidmap` та `newgidmap` формується таблиця відображення:

```
[ Простір імен контейнера ]          [ Простір імен хоста ]
UID 0 (root усередині)      <───>   UID 1000 (звичайний користувач)
UID 1..65535                <───>   UID 100000..165534 (/etc/subuid)
```

Завдяки цьому застосунок усередині контейнера впевнений, що він працює як повноправний `root` (може встановлювати пакети менеджером `apk` або `apt`), але будь-які файли, записані на змонтований том хоста, автоматично отримують реальний `UID 1000` хостового розробника.

##### Спосіб Г: ID-mapped mounts у ядрі Linux (5.12+)
У ядрі Linux версії 5.12 з'явився механізм монтування з відображенням ідентифікаторів (*ID-mapped mounts*). Замість того щоб змінювати простір імен усього процесу або рекурсивно переписувати права на диску викликом `chown`, системний виклик `mount_setattr()` дозволяє прив'язати таблицю `struct user_namespace` безпосередньо до конкретної точки монтування VFS.

Ядро здійснює динамічну трансляцію `inode->i_uid` на льоту під час проходження шляху файлової системи, не змінюючи жодного байта на фізичному носії.

Повну специфікацію діагностичних команд для перевірки таблиць відображення та атрибутів файлових систем зібрано у довіднику [📋 Матриця несправностей контейнерного середовища: симптоми, структури ядра та інженерні рішення](root:unix/container-does-not-work/api-container-faults.md).

### 3. Мережева ізоляція та розпізнавання імен: чому ламається DNS

Другий фундаментальний бар'єр виникає під час спроби налагодити мережеву взаємодію між двома контейнерами на одній машині. Розробник запускає контейнер веб-сервісу та контейнер бази даних, але запит `curl http://database:5432` миттєво завершується помилкою розпізнавання імені.

Цей збій безпосередньо пов'язаний із тим, як працює мережевий простір імен (`CLONE_NEWNET`) та яку топологію мережі Docker обирає за замовчуванням.

![Мережева ізоляція та розпізнавання імен у контейнерах](/root/course/unix/container-does-not-work/img/container-dns-network-bridge.svg)
*Мережева ізоляція та розпізнавання імен: відсутність вбудованого DNS у дефолтному мості docker0 проти автоматичного перехоплення запитів iptables у користувацькій мережі.*

#### 3.1. Пастка дефолтної мережі `docker0`

Якщо під час запуску контейнера не вказано прапорець `--network`, Docker автоматично приєднує його до дефолтної мостової мережі `bridge`, яка спирається на віртуальний мережевий міст ядра `docker0` (зазвичай підмережа `172.17.0.0/16`).

У цій конфігурації Docker застосовує особливу поведінку для файлу конфігурації резолвера `/etc/resolv.conf`:
1. Демон Docker генерує файл `/etc/resolv.conf` усередині контейнера, просто копіюючи адреси серверів імен із хостового `/etc/resolv.conf` (наприклад, `nameserver 8.8.8.8` або DNS корпоративного маршрутизатора `192.168.1.1`).
2. У дефолтній мережі `docker0` **повністю відсутній вбудований DNS-сервер**.
3. Коли застосунок викликає стандартну функцію `getaddrinfo("database")`, системна бібліотека надсилає UDP-запит на порт 53 зовнішнього DNS-сервера (наприклад, Google DNS `8.8.8.8`).
4. Зовнішній DNS-сервер в інтернеті нічого не знає про приватні імена контейнерів на вашому локальному сервері й повертає статус `NXDOMAIN`.

Чому Docker так робить? Це свідоме архітектурне рішення для зворотної сумісності зі старими версіями Docker (до версії 1.10), де ізоляція між непов'язаними контейнерами вважалася пріоритетом, а зв'язування вимагало явної передачі змінних оточення через застарілий механізм `--link`.

#### 3.2. Пастка локального DNS-стаба (`127.0.0.53`)

У сучасних дистрибутивах Linux (Ubuntu, Debian, Fedora) системний резолвер хоста обслуговується службою `systemd-resolved`, яка слухає локальну адресу-заглушку `127.0.0.53:53` на хостовому інтерфейсі `lo`.

Коли Docker намагається скопіювати хостовий `/etc/resolv.conf` у новий мережевий простір імен контейнера, він виявляє loopback-адресу `127.0.0.53`. Оскільки всередині мережевого простору контейнера існує власний, повністю ізольований інтерфейс `lo`, на якому ніякий `systemd-resolved` не запущено, пряме копіювання призвело б до мертвого DNS.

Тому Docker застосовує евристику: якщо в хостовому конфігурі виявлено loopback-адресу, Docker видаляє її та підставляє резервний публічний сервер Google DNS (`8.8.8.8`).

*Наслідок:* Якщо ваш сервер знаходиться в закритій корпоративній мережі без прямого виходу в публічний інтернет або якщо вам потрібно резолвити внутрішні хостові домени `.internal`, контейнер у дефолтній мережі повністю втрачає здатність резолвити будь-які доменні імена.

#### 3.3. Користувацькі мережі та магія `127.0.0.11`

Щоб увімкнути автоматичне розпізнавання імен між контейнерами, необхідно створити користувацьку мостову мережу (User-Defined Bridge Network):

```bash
docker network create my-network
docker run -d --name database --network my-network postgres:16
docker run -d --name backend --network my-network my-backend:v1
```

Коли контейнер підключається до користувацької мережі, Docker кардинально змінює конфігурацію:
1. У файлі `/etc/resolv.conf` контейнера прописується єдиний рядок: `nameserver 127.0.0.11`.
2. Адреса `127.0.0.11` — це вбудований DNS-сервер Docker (*Embedded DNS*), який працює всередині демона `dockerd`.
3. Оскільки сам DNS-сервер слухає на випадковому внутрішньому сокеті хоста, ядро використовує механізм Netfilter/iptables безпосередньо всередині мережевого простору контейнера:

```bash
# Правило iptables у ланцюжку NAT контейнера для перехоплення DNS
iptables -t nat -A OUTPUT -d 127.0.0.11 -p udp --dport 53 -j DNAT --to-destination 127.0.0.11:39451
```

Коли застосунок виконує запит `getaddrinfo("database")`:
* UDP-пакет на адресу `127.0.0.11:53` перехоплюється правилом `DNAT` і перенаправляється на внутрішній порт вбудованого резолвера.
* Вбудований DNS-сервер перевіряє внутрішню таблицю активних контейнерів, підключених до мережі `my-network`.
* Якщо ім'я знайдено, резолвер миттєво повертає внутрішню IP-адресу контейнера `database` (наприклад, `172.20.0.2`).
* Якщо запитується зовнішній домен (наприклад, `api.stripe.com`), вбудований DNS проксіює цей запит до апстрім-серверів хоста, визначених у хостовому `/etc/resolv.conf`.

#### 3.4. Блокування міжконтейнерного трафіку (Inter-Container Communication)

Навіть якщо DNS повертає правильну IP-адресу, прямий TCP-трафік між контейнерами може блокуватися хостовим міжмережевим екраном.

Усі мостові інтерфейси Linux комутують кадри на рівні L2, але для проходження пакетів між різними інтерфейсами `veth` ядро викликає ланцюжок `FORWARD` підсистеми `iptables`.

Демон Docker додає власні правила фільтрації:
* **DOCKER-ISOLATION-STAGE-1 / STAGE-2:** спеціальні ланцюжки правил, які гарантують, що пакети з одного моста (наприклад, `br-abc123`) не можуть бути маршрутизовані в інший міст (наприклад, `docker0` або `br-def456`).
* **Параметр `icc=false`:** якщо під час створення мережі вказано `--opt com.docker.network.bridge.enable_icc=false`, ядро додає правило `-j DROP` для будь-яких пакетів, що передаються між портами одного й того самого мосту. Контейнери в одній мережі втрачають можливість зв'язуватися напряму, навіть знаючи точну IP-адресу.

### 4. Фатальна проблема PID 1: накопичення процесів-зомбі (Zombie Reaper Problem)

Третя системна аномалія, яка здатна непомітно паралізувати виробничий вузол, полягає у витоку процесів-зомбі всередині контейнера. З часом на хості вичерпується глобальний ліміт ідентифікаторів процесів або досягається ліміт контрольної групи, і будь-яка команда (включно з `docker exec`) починає повертати фатальну помилку:

```text
fork: Resource temporarily unavailable (errno 11, EAGAIN)
```

Щоб зрозуміти походження цієї проблеми, необхідно звернутися до класичної моделі життєвого циклу процесів у системі Unix.

![Анатомія PID 1 у контейнері: збирач зомбі та обробка сигналів](/root/course/unix/container-does-not-work/img/pid1-zombie-and-signal-lifecycle.svg)
*Життєвий цикл PID 1 у контейнері: накопичення сиріт-зомбі через відсутність waitpid() та ігнорування SIGTERM ядром із подальшим 10-секундним таймаутом.*

#### 4.1. Механізм утворення зомбі та всиновлення сиріт

Коли процес у Linux завершує виконання (через виклик `exit()` або отримання смертельного сигналу), ядро не може миттєво видалити його структуру `struct task_struct` з пам'яті. Ядро зобов'язане зберегти код повернення процесу (*exit code*) та статистику спожитих ресурсів доти, доки його батьківський процес не прочитає ці дані за допомогою системного виклику `wait()` або `waitpid()`.

Стан, коли код і пам'ять процесу вже звільнені, але запис у таблиці процесів і номер PID залишаються зайнятими, називається станом **зомбі** (`EXIT_ZOMBIE`, позначка `Z` у виводі `ps`).

Що відбувається, коли батьківський процес завершує роботу раніше, ніж його дочірній процес? Дочірній процес стає **сиротою** (*orphan*).

У традиційній системі Unix ядро реалізує механізм автоматичного всиновлення: усіх осиротілих нащадків ядро перепідпорядковує найголовнішому процесу системи — системній службі ініціалізації з номером `PID 1` (`systemd`, `init`, `launchd`).

Фундаментальне призначення системного `PID 1` у класичній ОС — це нескінченний цикл прийому сигналу `SIGCHLD` та негайний виклик `waitpid(-1, &status, WNOHANG)` для безперервного видалення записів померлих сиріт із системної таблиці ядра.

#### 4.2. Чому звичайний застосунок ламає цю модель

Коли розробник пише у Dockerfile:
```dockerfile
ENTRYPOINT ["node", "server.js"]
```

Процес Node.js запускається першим у новоствореному просторі ідентифікаторів `pid_namespace` і автоматично отримує номер `PID 1`.

Якщо Node.js під час роботи виконує системні команди (наприклад, `child_process.spawn("git", ...)` або `child_process.exec("imagemagick", ...)`), або якщо всередині контейнера працюють сторонні утиліти, які використовують шаблон подвійного форку (*double fork* для створення фонових демонів):
1. Проміжний процес створює онука і відразу завершується.
2. Процес-онук стає сиротою.
3. Ядро Linux знаходить вершину поточного простору імен і всиновлює цього онука процесу `PID 1` (тобто середовищу виконання Node.js, Python або Java).
4. Коли фоновий процес завершує свою роботу, ядро переводить його в стан зомбі та надсилає сигнал `SIGCHLD` процесу `PID 1`.
5. Середовище виконання Node.js нічого не знає про цього невідомого нащадка! Воно обробляє `waitpid()` виключно для тих процесів, які саме створило через внутрішні дескриптори.

Оскільки `waitpid()` для всиновленого процесу ніколи не викликається, запис про процес назавжди застрягає в таблиці ядра хоста.

#### 4.3. Наслідки накопичення зомбі

Хоча кожен процес-зомбі займає мінімум оперативної пам'яті (лише структуру `task_struct`), він блокує унікальний номер `pid_t`.

У ядрі Linux існує системне обмеження `/proc/sys/kernel/pid_max` (за замовчуванням 32768 або 4194304). Крім того, контрольні групи версії cgroups v2 встановлюють жорсткий ліміт `pids.max` на кожен контейнер (наприклад, 100 або 512 процесів).

Щойно кількість живих процесів разом із накопиченими зомбі досягає значення `pids.max`, будь-який наступний системний виклик `clone()` або `fork()` повертає помилку `EAGAIN`. Контейнер перестає обробляти нові з'єднання, перестає запускати воркери, а системний адміністратор навіть не може підключитися всередину командою `docker exec -it <container> sh`, оскільки створення нової оболонки вимагає породити новий процес.

### 5. Обробка сигналів завершення та 10-секундна пастка SIGKILL

Четверта типова несправність — неможливість штатно зупинити контейнер. Команда `docker stop` блокує термінал на 10 секунд, після чого контейнер «вбивається на смерть».

Цей збій призводить до пошкодження баз даних SQLite, незакритих файлів журналів, розірваних посеред обробки HTTP-транзакцій та відсутності скидання буферів на диск.

Причина полягає у двох взаємопов'язаних факторах: особливому захисті ядра для процесу `PID 1` та пастці оболонки (*Shell Form Trap*).

#### 5.1. Особливий статус `PID 1` у ядрі щодо сигналів

Для будь-якого звичайного процесу в Unix системні сигнали `SIGTERM` (номер 15) та `SIGINT` (номер 2) мають стандартну системну дію за замовчуванням — `SIG_DFL` (завершення процесу). Якщо програма не встановила власний обробник через `sigaction()`, надсилання `SIGTERM` негайно призводить до зупинки процесу.

Проте для процесу, який має номер `PID 1` у своєму просторі імен, ядро Linux реалізує кардинально інше правило:

> **Захист ядра Linux для PID 1:**
> Якщо сигнали надходять ізсередини того самого простору імен або від непривілейованого процесу, ядро **повністю ігнорує будь-які сигнали для PID 1, для яких процес не зареєстрував явний обробник**. Системна дія `SIG_DFL` для `PID 1` інтерпретується ядром як `SIG_IGN` (повне ігнорування).

Це правило створено для того, щоб системний `init` хоста випадково не загинув від несподіваного сигналу, що призвело б до паніки всього ядра (*Kernel Panic*).

Коли виконується команда `docker stop <container>`:
1. Демон контейнеризації надсилає процесу `PID 1` сигнал `SIGTERM`.
2. Якщо застосунок (наприклад, Java, Node.js або скомпільований бінарник на Go/C++) не містить у своєму коді рядка на зразок `process.on('SIGTERM', ...)` або `signal(SIGTERM, handler)`, ядро перевіряє таблицю обробників і бачить там `SIG_DFL`.
3. Оскільки це `PID 1`, ядро просто **відкидає сигнал**.
4. Застосунок навіть не підозрює, що його намагаються зупинити, і продовжує виконувати свій цикл обробки.
5. Демон Docker чекає стандартний період очікування (*Grace Period*, за замовчуванням рівно 10 секунд).
6. Після вичерпання 10 секунд демон надсилає безжальний сигнал `SIGKILL` (номер 9), який неможливо перехопити або проігнорувати.
7. Процес негайно знищується ядром, залишаючи код завершення `137` (що розшифровується за стандартом як `128 + 9`).

#### 5.2. Пастка оболонки (Shell Form Trap)

Ще одна поширена причина ігнорування сигналів — неправильний синтаксис інструкцій `CMD` або `ENTRYPOINT` у файлі `Dockerfile`.

У специфікації Dockerfile існують дві форми запису команд:

```dockerfile
# 1. Shell Form (ФОРМА ОБОЛОНКИ — НЕБЕЗПЕЧНА)
ENTRYPOINT ./start.sh

# 2. Exec / JSON Form (ВИКОНАВЧА ФОРМА — РЕКОМЕНДОВАНА)
ENTRYPOINT ["./start.sh"]
```

Коли використовується форма оболонки (`ENTRYPOINT ./start.sh`), Docker неявно підставляє запуск системної оболонки:
`/bin/sh -c "./start.sh"`.

У результаті дерево процесів усередині контейнера виглядає так:
* `PID 1`: `/bin/sh`
* `PID 2`: `./start.sh` (дочірній процес)
* `PID 3`: `node server.js` (дочірній процес скрипта)

Стандартна оболонка `/bin/sh` (зазвичай це `dash` у Debian/Ubuntu або `busybox ash` в Alpine) не транслює отримані сигнали `SIGTERM` своїм дочірнім процесам. Коли `docker stop` надсилає `SIGTERM` до `PID 1` (`/bin/sh`), оболонка не пересилає його процесу `node`. Застосунок не завершує активні з'єднання, минає 10 секунд, і Docker знищує все дерево через `SIGKILL`.

Щоб виправити це у shell-скриптах, необхідно обов'язково використовувати системну команду `exec`:

```bash
#!/bin/sh
# Підготовчі операції (міграції, перевірка конфігурацій)
echo "Підготовка середовища..."

# Заміна процесу оболонки на цільовий бінарник із збереженням PID 1
exec node server.js
```

Команда `exec` викликає системний виклик `execve()`, який замінює образ пам'яті поточної оболонки `/bin/sh` на виконуваний файл `node`, зберігаючи той самий номер `PID 1`. Завдяки цьому всі наступні сигнали надходитимуть безпосередньо у процес застосунку.

### 6. Системне рішення: ініціалізатори `tini` та `dumb-init`

Щоб одночасно вирішити проблему збирання зомбі та надійної доставки сигналів без необхідності змінювати вихідний код прикладних програм, у контейнерних архітектурах застосовують легковажні спеціалізовані ініціалізатори — **Init Shims** (найвідоміші з них — `tini` та `dumb-init`).

Такий ініціалізатор являє собою компактну бінарну програму розміром у кілька десятків кілобайт, яка виконує дві системні функції:
1. Запускається як справжній `PID 1`, перехоплює всі сигнали ОС (`SIGTERM`, `SIGINT`, `SIGHUP`, `SIGQUIT`) і негайно транслює їх усій дочірній групі процесів.
2. Перехоплює сигнал `SIGCHLD` і в нескінченному циклі викликає `waitpid(-1, &status, WNOHANG)`, миттєво видаляючи з пам'яті ядра всіх осиротілих зомбі.
3. Коли головний дочірній процес завершує роботу, ініціалізатор коректно транслює його код повернення назовні та завершує роботу контейнера.

```bash
# Використання вбудованого tini у Docker через прапорець --init
docker run --init -d --name my-app my-service:v1
```

Повний практичний розбір створення власного легковажного ініціалізатора на C та C++ з використанням системних викликів `signalfd`, `prctl(PR_SET_CHILD_SUBREAPER)` та `poll` наведено у практичному посібнику [⚙️ Реалізація мінімального ініціалізатора-збирача зомбі (Init Shim)](root:unix/container-does-not-work/proj-minimal-init-reaper.md).

### 7. Зведена схема діагностики несправностей

Коли контейнер у виробничому середовищі поводиться некоректно, інженерний аналіз виконується за алгоритмом локалізації точки розриву:

```
[ Проблема з контейнером ]
        │
        ├── 1. Помилка EACCES / неможливість записати файл?
        │      └── Перевірити числові UID/GID хоста та контейнера:
        │          ls -ldn /host/dir vs id -u всередині контейнера.
        │          Виправлення: docker run -u $(id -u):$(id -g) або Rootless Podman.
        │
        ├── 2. Помилка NXDOMAIN / не видно інший контейнер за іменем?
        │      └── Перевірити мережу: cat /etc/resolv.conf.
        │          Якщо немає 127.0.0.11 — контейнер у дефолтному мості docker0!
        │          Виправлення: docker network create custom-net.
        │
        ├── 3. Зависання docker stop на 10 секунд (код 137)?
        │      └── Перевірити ps -ef (чи не запущено команду через /bin/sh -c).
        │          Виправлення: exec node app.js або прапорець docker run --init.
        │
        └── 4. Помилка «fork: Resource temporarily unavailable»?
               └── Перевірити наявність зомбі: ps -eo stat,comm | grep Z.
                   Виправлення: підключити збирач сиріт через docker run --init (tini).
```

Розуміння того, що контейнер — це не ізольована машина, а звичайний процес під контролем просторів імен та монолітного ядра Linux, перетворює хаотичний пошук помилок на послідовний інженерний аналіз структур ядра, системних викликів та конфігурації таблиць віртуалізації.
