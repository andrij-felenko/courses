# 📋 Матриця несправностей контейнерного середовища: симптоми, структури ядра та інженерні рішення

Цей довідник систематизує діагностичні ознаки, низькорівневі механізми ядра Linux, системні структури та практичні способи виправлення збоїв у контейнерних середовищах Docker, Podman та OCI-сумісних рантаймах. Він розроблений для швидкого встановлення першопричини системних збоїв під час експлуатації та налагодження ізольованих середовищ.

### 2. Діагностичні інтерфейси файлових систем та прав доступу

Коли процес усередині контейнера намагається відкрити файл або каталог у змонтованому томі, ядро Linux перевіряє повноваження без участі простору користувача. Для повної діагностики прав доступу інженер має зіставити системні креденшели процесу та бінарні атрибути інодів.

Кожен процес у ядрі описується структурою `task_struct`, яка містить вказівник на структуру `struct cred`. У цій структурі зберігаються чотири пари ідентифікаторів користувача та групи:
* **Реальні (Real UID/GID):** визначають реального власника процесу (хто його запустив у системі).
* **Ефективні (Effective UID/GID):** використовуються для більшості перевірок прав під час виконання загальних системних викликів.
* **Збережені (Saved Set UID/GID):** дозволяють процесу тимчасово змінювати привілеї та безпечно повертатися назад без втрати первинного контексту.
* **Файлові (Filesystem UID/GID — fsuid/fsgid):** використовуються підсистемою VFS для перевірки прав доступу до об'єктів файлових систем. Зазвичай вони синхронізовані з Effective UID/GID, але в системних серверах NFS або Samba можуть змінюватися окремо.

Перевірка фактичних числових значень здійснюється через читання псевдофайлу `/proc/$PID/status`:

```bash
# 1. Перевірка реальних, ефективних та файлових ідентифікаторів процесу
cat /proc/$PID/status | grep -E 'Uid|Gid'
# Вивід:
# Uid:   1000    1000    1000    1000   (real, effective, saved set, fs)
# Gid:   1000    1000    1000    1000

# 2. Перевірка таблиці відображення простору користувача (User Namespace)
cat /proc/$PID/uid_map
# Вивід для rootless podman:
#          0       1000          1      (UID 0 в контейнері -> UID 1000 на хості)
#          1     100000      65536      (UID 1..65536 в контейнері -> UID 100000..165535)

cat /proc/$PID/gid_map
# Вивід:
#          0       1000          1
#          1     100000      65536

# 3. Перевірка системних файлів підпорядкованих діапазонів на хості
cat /etc/subuid
# developer:100000:65536

cat /etc/subgid
# developer:100000:65536
```

Якщо під час виклику `open()` файловий ідентифікатор `current_fsuid()` не збігається з полем `inode->i_uid`, а маска прав `i_mode` забороняє доступ групі або іншим користувачам, ядро миттєво повертає помилку `EACCES`. Текстові записи у файлах `/etc/passwd` контейнера та хоста під час цієї процедури взагалі не зчитуються.

Діагностичний алгоритм розбору прав монтування:
1. Визначити числовий UID процесу всередині контейнера: `docker exec <container> id -u`.
2. Визначити числовий UID власника каталогу на хості: `ls -ldn /path/to/host/dir`.
3. Якщо значення не збігаються, перевірити права на читання, запис та виконання для групи та інших (`others`).
4. Для перевірки наявності активного User Namespace перевірити рядок `uid_map` у каталозі `/proc/<host_pid>/uid_map`.

### 3. Діагностичні інтерфейси мережевого простору та DNS

Усі мережеві інтерфейси, таблиці маршрутів, ланцюжки фільтрації `iptables` та сокети контейнера повністю ізольовані у власному мережевому просторі імен (`struct net`). Прямий виклик мережевих утиліт із хоста не показує стану контейнерної мережі. Для виконання команд безпосередньо в мережевому контексті цільового контейнера застосовується утиліта `nsenter`:

```bash
# Отримання PID головного процесу контейнера на хості
CONTAINER_PID=$(docker inspect --format '{{.State.Pid}}' my-container)

# 1. Перевірка мережевих інтерфейсів та IP-адрес усередині простору контейнера
nsenter -t $CONTAINER_PID -n ip -4 addr show

# 2. Перевірка таблиці маршрутизації контейнера
nsenter -t $CONTAINER_PID -n ip route show

# 3. Перевірка конфігурації резолвера та тестування вбудованого DNS
nsenter -t $CONTAINER_PID -n cat /etc/resolv.conf
nsenter -t $CONTAINER_PID -n dig @127.0.0.11 target-service.my-net +short

# 4. Інспекція правил трансляції адрес DNS (iptables NAT) у просторі контейнера
nsenter -t $CONTAINER_PID -n iptables -t nat -L -n -v
# Типовий ланцюжок перехоплення DNS Docker:
# Chain DOCKER_OUTPUT (1 references)
# pkts bytes target     prot opt in     out     source      destination
#    4   260 DNAT       udp  --  *      *       0.0.0.0/0   127.0.0.11   udp dpt:53 to:127.0.0.11:39451
#    0     0 DNAT       tcp  --  *      *       0.0.0.0/0   127.0.0.11   tcp dpt:53 to:127.0.0.11:41253
```

Особливу увагу слід звертати на трансляцію DNS-запитів. Якщо у виводі `iptables` у мережевому просторі контейнера відсутні правила перенаправлення на порт вбудованого резолвера або якщо сам процес демона `dockerd` зазнав збою, запити на адресу `127.0.0.11` скидатимуться за таймаутом, блокуючи будь-яку мережеву активність застосунку.

Діагностичний чекліст для мережевих несправностей:
1. Перевірити, чи підключений контейнер до користувацької мережі (`docker network inspect <net_name>`).
2. Перевірити наявність запису `nameserver 127.0.0.11` у файлі `/etc/resolv.conf` контейнера.
3. Протестувати резолвінг доменних імен за допомогою команди `nslookup` або `dig`.
4. Перевірити правила міжмережевого екрана в хостовому ланцюжку `FORWARD` на наявність блокувальних правил `DROP` або заборони `com.docker.network.bridge.enable_icc`.

### 4. Діагностичні інтерфейси дерева процесів та сигналів

Виявлення накопичення процесів-зомбі, аналіз ланцюгів успадкування батьківських ідентифікаторів та інспекція масок обробки сигналів виконуються за допомогою системних інструментів аналізу ядра.

Утиліта `ps` дозволяє отримати детальну інформацію про стан кожного процесу в системі:
* **Стан `Z` (Zombie):** процес завершився, звільнив пам'ять і дескриптори, але утримує запис `task_struct` і номер PID, очікуючи виклику `waitpid()` від свого батьківського процесу `PPID`.
* **Батьківський процес `PPID 1`:** вказує, що процес став сиротою і був автоматично перепідпорядкований головному процесу простору імен. Якщо цей головний процес не реалізує збирання сиріт, кількість таких записів невпинно зростає.

```bash
# 1. Виявлення процесів-зомбі та їхніх батьківських ідентифікаторів
ps -eo pid,ppid,pgid,stat,comm | grep -E 'STAT|Z'
# Приклад проблемного дерева:
#   PID  PPID  PGID STAT COMMAND
#     1     0     1 Ss   node
#    45     1     1 Z    python3 <defunct>

# 2. Інспекція маски перехоплення сигналів процесу PID 1 у контейнері
cat /proc/$CONTAINER_PID/status | grep -E 'SigBlk|SigIgn|SigCgt'
# SigBlk: 0000000000000000 (заблоковані сигнали)
# SigIgn: 0000000000000000 (ігноровані сигнали)
# SigCgt: 0000000180004002 (перехоплені сигнали: 16-ткова бітова маска)

# Розшифрування бітової маски за допомогою команди:
# Біт 15 (SIGTERM = 15) повинен бути встановлений у 1 (1 << 14), інакше SIGTERM ігнорується ядром!

# 3. Перевірка споживання ліміту кількості процесів у cgroups v2
cat /sys/fs/cgroup/system.slice/docker-$CONTAINER_ID.scope/pids.current
cat /sys/fs/cgroup/system.slice/docker-$CONTAINER_ID.scope/pids.max
```

Коли лічильник `pids.current` досягає встановленого ліміту `pids.max`, підсистема cgroups блокує будь-яке наступне клонування процесів. Усі виклики `fork()` повертають помилку `EAGAIN` незалежно від обсягу вільної оперативної пам'яті та наявності вільних ядер процесора.

Діагностичний алгоритм для аналізу зависань зупинки:
1. Перевірити, який процес працює під номером `PID 1` усередині контейнера.
2. Якщо це системна оболонка `/bin/sh` або скрипт без виклику `exec`, застосунок не отримує сигналів через пастку оболонки.
3. Якщо це скомпільований бінарник без зареєстрованого обробника `SIGTERM`, ядро ігнорує сигнал через спеціальний захист `PID 1`.
4. Перевірити наявність прапорця `--init` у конфігурації запуску або вбудованого бінарника `tini` в образі.

### 5. Прапорці запуску та конфігураційні параметри

Нижче наведено зведену конфігураційну специфікацію прапорців запуску контейнерів Docker та Podman. Вона демонструє, як на практиці вирівняти права доступу, підключити легковажний ініціалізатор, налаштувати безпечний DNS та захистити середовище від вичерпання ресурсів:

```bash
# Повний безпечний запуск із виправленням прав, ініціалізатором та DNS
docker run -d \
  --name app-production \
  --init \                                # Підключає вбудований tini (PID 1 reaper)
  --user 1000:1000 \                      # Явне вирівнювання UID/GID
  --network custom-bridge \               # Вмикає embedded DNS 127.0.0.11
  --dns 1.1.1.1 \                         # Резервний зовнішній upstream DNS
  --pids-limit 512 \                      # Захист cgroups v2 від fork-бомб та зомбі
  --read-only \                           # Незмінний кореневий шар (захист ФС)
  --tmpfs /tmp:rw,noexec,nosuid \         # Тимчасові файли без прав виконання
  -v /host/data:/app/data:rw \            # Монтування тому з відповідними правами
  my-app:v1.0.0
```

Кожен прапорець у цьому наборі розв'язує конкретну системну вразливість:
* `--init` запобігає витоку процесів-зомбі та усуває 10-секундну затримку при зупинці контейнера.
* `--user` узгоджує числові ідентифікатори процесу з файловою системою хоста без необхідності надання прав root.
* `--network` ізолює трафік у виділеному мості та активує автоматичний розпізнавач імен через вбудований DNS-сервер.
* `--pids-limit` захищає сервер від аварійного вичерпання глобальної таблиці процесів ядра Linux у разі виникнення fork-бомби.

Використання цих параметрів забезпечує стабільну роботу контейнерних застосунків, усуває 10-секундні таймаути при перезапусках та запобігає витокам системних ресурсів ядра хоста.
