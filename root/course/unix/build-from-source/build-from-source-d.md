Системний інженер налаштовує сервер під керуванням Debian 12 або Rocky Linux 9 для обслуговування високонавантаженого вебпроксі. Офіційний системний репозиторій дистрибутива пропонує стабільну, але застарілу версію Nginx, скомпільовану без підтримки сучасного протоколу HTTP/3 (QUIC), або утиліту cURL, зібрану без потрібного криптографічного бекенду. Крім того, стандартні бінарні пакети дистрибутива скомпільовані під узагальнену базову архітектуру x86-64 без урахування векторних інструкцій AVX2 та криптографічних розширень сучасного процесора сервера, через що сервіс втрачає до третини своєї потенційної пропускної спроможності.

Єдиним способом отримати необхідний функціонал та максимальну продуктивність є самостійне складання програмного забезпечення з вихідного коду. Проте цей процес не зводиться до сліпого копіювання трьох команд із README-файлу: він вимагає розуміння повного інженерного циклу — від зондування апаратного середовища операційної системи та розв'язання залежностей заголовків до паралельної компіляції, ізоляції префіксів та створення нативних пакетів, які не руйнують цілісність дистрибутива.

### 1. Чому виникає потреба збірки з вихідного коду

Пакетні менеджери сучасних дистрибутивів (`apt`, `dnf`, `pacman`) оптимізовані під стабільність, передбачуваність та масову сумісність. За це операційна система платить консервативністю: пакети в релізах довгострокової підтримки (LTS) заморожуються на роки, а їхні конфігурації компіляції орієнтовані на найменший спільний знаменник серед усього парку сумісного обладнання.

Виділяють три головні причини, чому системний інженер звертається до складання з вихідних текстів:

1. **Часова затримка релізів та відсутність свіжих можливостей:** Корпоративні дистрибутиви постачають лише виправлення критичних вразливостей безпеки, не оновлюючи мажорні версії програмного забезпечення. Нові мережеві протоколи, алгоритми стиснення даних (наприклад, Zstandard чи Brotli) або нові механізми ядра Linux (наприклад, асинхронний інтерфейс `io_uring`) стають доступними в офіційних пакетах із запізненням у кілька років.
2. **Апаратна оптимізація під конкретний процесор:** Офіційні бінарні пакети більшості дистрибутивів збираються з прапорцями під базовий рівень мікроархітектури `x86-64-v1` (сумісний із процесорами AMD K8 та Intel Core 2 початку 2000-х років). Складання з вихідного коду з прапорцем `-march=native` дозволяє компілятору генерувати спеціалізовані процесорні інструкції (AVX2, AVX-512, FMA, BMI2, AES-NI), що критично для криптографії, обробки медіапотоків, баз даних та математичних обчислень.
3. **Модульність та умовна компіляція:** У мовах C та C++ багато фундаментальних архітектурних рішень ухвалюються на етапі препроцесора (`#ifdef`). Якщо вебсервер чи база даних були скомпільовані без підтримки специфічного стороннього модуля (наприклад, Lua-скриптингу, модуля георозподіленого кешування чи кастомного рушія автентифікації), підключити цей модуль динамічно під час виконання неможливо без повної перезбірки програми.

#### Анатомія релізного архіву: Release Tarball проти Git-репозиторію

Користувачі часто стикаються з вибором: завантажити релізний архів проекту (`tar.gz` або `tar.xz`) чи клонувати його вихідний код через `git clone`. Між цими двома джерелами існує принципова інженерна різниця.

Релізний архів (*Release Tarball*) є самодостатнім артефактом, підготовленим розробниками за допомогою команди `make dist` або спеціалізованих конвеєрів безперервної інтеграції (CI). Він містить не лише вихідні файли мов C/C++, але й готовий до запуску скрипт конфігурації `./configure` та шаблони файлів збірки `Makefile.in`. Щоб зібрати такий архів, на цільовій машині не потрібні інструменти метагенерації (GNU Autoconf, Automake, Libtool, генератори лексичних аналізаторів Flex чи синтаксичних парсерів Bison) — достатньо звичайного POSIX-сумісного командного інтерпретатора `sh` та компілятора C.

Клонований репозиторій Git містить лише «сирий» вихідний код та декларативні файли опису (`configure.ac`, `Makefile.am` або `CMakeLists.txt`). Щоб перетворити такий репозиторій на робочий конвеєр, користувач зобов'язаний виконати етап бутстрапу розробника (наприклад, запустити `autoreconf -fi` для генерації `configure` або ініціалізувати підмодулі `git submodule update --init --recursive`), що вимагає встановлення повного набору утиліт генерації коду.

Понад три десятиліття екосистема вільного та відкритого програмного забезпечення спирається на стандартний трикроковий конвеєр інструментів GNU Autotools.

![Конвеєр конфігурації, компіляції та інсталяції GNU Autotools](/root/course/unix/build-from-source/img/autotools-pipeline.svg)
*Послідовність трансформації вихідних кодів у системні бінарники в конвеєрі GNU Autotools: зондування хоста, паралельна компіляція та інсталяція.*

#### 2.1. Етап конфігурації та зондування системи: `./configure`

Скрипт `./configure` — це автономний скрипт командної оболонки розміром у десятки тисяч рядків. Його головне завдання — розв'язати проблему різнорідності операційних систем сімейства Unix без ручного редагування вихідного коду розробником.

Під час виконання скрипт послідовно виконує такі перевірки:

1. **Зондування інструментального ланцюга (*Toolchain*):** Перевіряє наявність працездатного компілятора C (`CC`) та C++ (`CXX`), переконується, що компілятор здатен створити виконуваний двійковий файл ELF, визначає розрядність цільової платформи та порядок байтів (*Endianness*).
2. **Зондування заголовкових файлів ядра та бібліотек:** Скрипт створює у тимчасовому каталозі крихітні C-файли `conftest.c` із директивами `#include <sys/epoll.h>`, `#include <sys/event.h>` чи `#include <pthread.h>` і намагається їх скомпілювати. Якщо компіляція успішна, заголовок вважається наявним у системі.
3. **Зондування функцій та системних викликів:** Скрипт перевіряє доступність конкретних функцій (наприклад, `epoll_create1`, `statx`, `copy_file_range`, `clock_gettime`), намагаючись скомпілювати та слінкувати тестову програму з викликом цієї функції.
4. **Зондування розмірів базових типів даних:** Визначає розміри типів `off_t`, `time_t`, `size_t` та вмикає підтримку 64-бітних зміщень файлів (*Large File Support*, `_FILE_OFFSET_BITS=64`).

Результатом роботи скрипту `./configure` є створення двох критичних файлів:

- `config.h` (або `include/config.h`): Заголовковий файл C/C++, у якому всі макроси перетворюються на реальні визначення препроцесора. Замість вихідного рядка `/* #undef HAVE_SYS_EPOLL_H */` у файлі з'являється `#define HAVE_SYS_EPOLL_H 1`.
- `Makefile` (у всіх підкаталогах проєкту): Створюється шляхом підстановки значень змінних (`@CC@`, `@CFLAGS@`, `@prefix@`, `@LIBS@`) у шаблони `Makefile.in` за допомогою внутрішнього скрипту `config.status`.

#### Як вихідний код споживає результати зондування

Вихідний код програми використовує `config.h` для адаптації під можливості операційної системи через умовну компіляцію. Розглянемо приклад створення неблокуючого дескриптора файлу: якщо система підтримує сучасний атомарний прапорець `O_NONBLOCK | O_CLOEXEC` у системному виклику `open()`, код використовує його напряму; інакше він робить додатковий виклик `fcntl()`.

:::tabs
```c
/* io_stream.c — C-реалізація з умовною компіляцією на базі config.h */
#ifdef HAVE_CONFIG_H
#include "config.h"
#endif

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>

int open_nonblocking_stream(const char *path) {
#if defined(HAVE_O_NONBLOCK) && defined(O_CLOEXEC)
    /* Сучасне ядро Linux: відкриття з прапорцями за один системний виклик */
    int fd = open(path, O_RDONLY | O_NONBLOCK | O_CLOEXEC);
    if (fd < 0) {
        return -1;
    }
    return fd;
#else
    /* Застарілі POSIX-системи: fallback через два системні виклики */
    int fd = open(path, O_RDONLY);
    if (fd < 0) {
        return -1;
    }
    int flags = fcntl(fd, F_GETFL, 0);
    if (flags == -1 || fcntl(fd, F_SETFL, flags | O_NONBLOCK) == -1) {
        close(fd);
        return -1;
    }
    return fd;
#endif
}
```
```cpp
// io_stream.cpp — Ідіоматична C++ реалізація з RAII та std::expected
#ifdef HAVE_CONFIG_H
#include "config.h"
#endif

#include <string_view>
#include <system_error>
#include <expected>
#include <fcntl.h>
#include <unistd.h>

class UniqueFd {
    int fd_{-1};
public:
    explicit UniqueFd(int fd) noexcept : fd_{fd} {}
    ~UniqueFd() noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }
    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;
    UniqueFd(UniqueFd&& other) noexcept : fd_{other.fd_} {
        other.fd_ = -1;
    }
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) {
                ::close(fd_);
            }
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] bool valid() const noexcept { return fd_ >= 0; }
};

std::expected<UniqueFd, std::error_code> open_nonblocking_stream(std::string_view path) {
#if defined(HAVE_O_NONBLOCK) && defined(O_CLOEXEC)
    int fd = ::open(path.data(), O_RDONLY | O_NONBLOCK | O_CLOEXEC);
    if (fd < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return UniqueFd{fd};
#else
    int fd = ::open(path.data(), O_RDONLY);
    if (fd < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    UniqueFd ufd{fd};
    int flags = ::fcntl(ufd.get(), F_GETFL, 0);
    if (flags == -1 || ::fcntl(ufd.get(), F_SETFL, flags | O_NONBLOCK) == -1) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return ufd;
#endif
}
```

#### Керування опціями конфігурації

Скрипт `configure` приймає стандартизовану множину параметрів для гнучкого налаштування збірки:

```bash
./configure \
    --prefix=/opt/myproxy \
    --enable-http2 \
    --disable-ipv6 \
    --with-ssl=/usr/local/openssl \
    --without-debug \
    CFLAGS="-O3 -march=native" \
    LDFLAGS="-Wl,-z,relro -Wl,-z,now"
```

- `--prefix=КАТАЛОГ` — визначає базовий префікс встановлення (за замовчуванням `/usr/local`).
- `--enable-ОПЦІЯ` / `--disable-ОПЦІЯ` — вмикає або вимикає внутрішні модулі самої програми (наприклад, `--enable-lto` або `--disable-shared`).
- `--with-ПАКУНОК` / `--without-ПАКУНОК` — вказує шляхи до зовнішніх бібліотек або вимикає необов'язкові інтеграції (наприклад, `--with-pcre2` або `--without-zlib`).
- Передача змінних `CFLAGS`, `LDFLAGS`, `LIBS` — дозволяє інжектувати власні прапорці оптимізації та безпеки. Для детального переліку та правил трансляції прапорців зверніться до матеріалу [довідник стандартних змінних середовища збірки](root:course/unix/build-from-source/api-build-variables.md).

#### Діагностика збоїв через `config.log`

Якщо під час роботи `./configure` виникає фатальна помилка (наприклад, `C compiler cannot create executables` або `OpenSSL crypto library not found`), консольний вивід зазвичай показує лише фінальний статус відмови.

Повна причина збою з точністю до рядка фіксується у файлі `config.log`. У ньому записано кожен згенерований тимчасовий C-файл `conftest.c`, повну команду виклику компілятора та точний текст помилки GCC/Clang:

```bash
# Пошук останнього збою у лозі конфігурації:
grep -B 5 -A 15 "error:" config.log
```

Часто виявляється, що «відсутня бібліотека» насправді встановлена в системі, але компілятор відхилив тестову програму через відсутність одного із системних заголовків або помилку лінкування із супутньою бібліотекою `-lpthread`.

#### 2.2. Етап компіляції: `make -j$(nproc)`

Після успішної генерації файлів `Makefile` запускається утиліта збірки `make`. Вона парсить опис графа залежностей і виконує дві послідовні фази:

1. **Фаза трансляції:** Компілює кожен окремий вихідний файл `.c` або `.cpp` у незалежний об'єктний файл машинного коду `.o`:
   ```
   gcc -I. -Iinclude -O3 -march=native -c src/worker.c -o src/worker.o
   ```
2. **Фаза компонування:** Викликає системний лінкер `ld` через драйвер компілятора для злиття всіх `.o` файлів разом із системними бібліотеками у фінальний двійковий файл `ELF`:
   ```
   gcc src/main.o src/worker.o src/network.o -L/usr/lib -lssl -lcrypto -lpthread -o bin/myproxy
   ```

#### Паралелізм збірки та сервер завдань (GNU Make Jobserver)

Складання великого проєкту в один потік на сучасному багатоядерному процесорі призводить до невиправданих затримок. Прапорець `-j` (*jobs*) вказує кількість паралельних процесів компіляції. Системна утиліта `nproc` повертає кількість доступних ядер процесора:

```bash
make -j$(nproc)
```

GNU Make реалізує механізм паралелізму через внутрішній сервер завдань (*Jobserver*). Батьківський процес `make` створює неіменований POSIX-пайп (*pipe*), у який записує `N-1` однобайтних токенів. Кожен дочірній процес перед стартом компіляції нового файлу зчитує один байт із пайпу, резервуючи ядро процесора, а після завершення компіляції повертає байт назад у пайп.

> 🔧 **Запобігання аварійному вичерпанню оперативної пам'яті (OOM):**
> Компіляція великих файлів C++ (особливо з важкими шаблонами або прапорцем LTO) вимагає гігабайти пам'яті на один процес. Якщо запустити `make -j32` на сервері з 16 ГБ RAM, ядро Linux активує OOM Killer і аварійно завершить процес компілятора.
> Для обмеження навантаження використовують комбінацію прапорців із лімітом середнього навантаження системи (*Load Average*):
> ```bash
> make -j$(nproc) -l$(nproc)
> ```
> Прапорець `-l` забороняє створювати нові процеси, якщо поточне завантаження CPU перевищує вказаний поріг.

#### 2.3. Етап інсталяції та розкладка за FHS: `make install`

Правило `make install` виконує копіювання зкомпільованих бінарників, спільних бібліотек, заголовкових файлів та документації у системні каталоги згідно зі стандартом Filesystem Hierarchy Standard (FHS):

```
$PREFIX/bin/           -> виконувані двійкові файли програми
$PREFIX/sbin/          -> системні утиліти адміністратора
$PREFIX/lib/           -> динамічні (.so) та статичні (.a) бібліотеки
$PREFIX/include/       -> C/C++ заголовкові файли (.h, .hpp)
$PREFIX/share/man/     -> довідкові сторінки (man pages)
$PREFIX/etc/           -> файли конфігурації
```

За замовчуванням `$PREFIX` дорівнює `/usr/local`. Для запису в цей каталог потрібні привілеї адміністратора (`sudo make install`).

### 3. Сучасні метасистеми збірки: CMake та Meson + Ninja

Хоча GNU Autotools залишається стандартом для багатьох класичних проєктів GNU, більшість сучасних проєктів мовами C та C++ використовують потужніші метасистеми збірки: **CMake** або зв'язку **Meson + Ninja**.

#### 3.1. Генерація та збірка проєктів у CMake

CMake не компілює файли безпосередньо. Це генератор низькорівневих конфігурацій для інших систем збірки (GNU Make, Ninja або Visual Studio).

Головний принцип роботи з CMake — **суворе відокремлення каталогу збірки від вихідного коду (*Out-of-source build*)**. Збирання проєкту безпосередньо у каталозі з джерельними кодами є застарілою антипрактикою, оскільки призводить до засмічення репозиторію тимчасовими файлами.

```bash
# 1. Конфігурація та генерація дерева збірки у теці build/
cmake -B build -S . \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=/opt/mytool \
    -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# 2. Компіляція проєкту
cmake --build build -j $(nproc)

# 3. Інсталяція зібраних артефактів
cmake --install build
```

- Параметр `-B build` вказує каталог, куди записуватимуться всі артефакти збірки.
- Параметр `-S .` вказує шлях до кореня вихідного коду (де знаходиться файл `CMakeLists.txt`).
- `-DCMAKE_BUILD_TYPE=Release` вмикає рівень оптимізації `-O3 -DNDEBUG`. Для налагодження використовують `-DCMAKE_BUILD_TYPE=Debug` (прапорці `-g -O0`).
- `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` генерує файл `compile_commands.json`, необхідний для роботи мовних серверів (LSP) на кшталт `clangd` або ccls у сучасних редакторах коду.
- Кешовані змінні зберігаються у файлі `build/CMakeCache.txt`. Для їх перегляду або модифікації використовують утиліту `ccmake build` або `cmake -L build`.

#### Керування пошуком пакетів у CMake через `CMAKE_PREFIX_PATH`

Коли CMake виконує директиву `find_package(OpenSSL REQUIRED)`, він шукає або модуль `FindOpenSSL.cmake`, або конфігураційний файл пакета `OpenSSLConfig.cmake`. Якщо бібліотека встановлена у нестандартний каталог (наприклад, `/opt/openssl3`), шлях до неї передається через спеціальну змінну:

```bash
cmake -B build -DCMAKE_PREFIX_PATH="/opt/openssl3;/opt/libuv"
```

#### 3.2. Високопродуктивний тандем Meson та Ninja

Meson створено як відповідь на надмірну складність мови CMake. Він використовує декларативний, строго типізований DSL-синтаксис без тюрінг-повноти, що запобігає написанню заплутаної імперативної логіки у файлах `meson.build`.

Як низькорівневий рушій виконання Meson за замовчуванням використовує **Ninja** — утиліту збірки, спроєктовану розробниками Google Chrome для досягнення максимальної швидкості інкрементальної компіляції. На відміну від `make`, Ninja не займається складними обчисленнями чи перевіркою системних умов під час виконання: вона отримує повністю розгорнутий плоский граф компіляції `build.ninja` і виконує його паралельно з мінімальним споживанням системних ресурсів.

```bash
# 1. Конфігурація середовища збірки
meson setup build \
    --buildtype=release \
    --prefix=/opt/mytool \
    -Dstrip=true

# 2. Компіляція через Ninja (автоматично використовує всі ядра CPU)
ninja -C build

# 3. Запуск автоматичних тестів проєкту
meson test -C build

# 4. Встановлення артефактів
meson install -C build
```

Ninja за замовчуванням задіює всі доступні ядра процесора, тому передавати прапорець `-j` вручну зазвичай не потрібно.

#### Система автозавантаження залежностей: Meson WrapDB

Якщо в системі відсутня необхідна девелоперська бібліотека, Meson підтримує механізм сабпроєктів (*Wrap dependency system*). У каталозі `subprojects/` розміщується текстовий `.wrap`-файл із посиланням на офіційне джерело залежності. Якщо системна бібліотека не знайдена через `pkg-config`, Meson автоматично завантажує вихідний код залежності, компілює її як частину проєкту та статично лінкує з основним бінарником.

### 4. Пошук та резолюція залежностей через `pkg-config`

Найпоширеніша проблема під час збірки ПЗ з джерел — помилка відсутності сторонніх бібліотек на етапі конфігурації або компіляції.

![Механізм розв'язання компіляційних та лінкових залежностей через pkg-config](/root/course/unix/build-from-source/img/dependency-resolution-pkgconfig.svg)
*Схема розв'язання залежностей утилітою pkg-config: читання метаданих .pc, отримання Cflags/Libs та лінкування системних бібліотек.*

#### 4.1. Чому виникає помилка «Missing development headers»

Типова ситуація: користувач встановлює в системі бібліотеку `libssl3` або `libuv1` через пакетний менеджер `apt install libuv1`, однак під час запуску `./configure` чи `cmake` бачить повідомлення про помилку:

```
checking for libuv... no
configure: error: Package 'libuv' not found
```

Або під час компіляції компілятор аварійно зупиняється:

```
src/network.c:12:10: fatal error: uv.h: No such file or directory
   12 | #include <uv.h>
      |          ^~~~~~
compilation terminated.
```

Причина полягає у структурі пакетів дистрибутивів Linux. Усі бібліотеки розділені на дві незалежні частини:

1. **Рантайм-пакунок (`libuv1`, `libssl3`):** Містить виключно динамічні скомпільовані файли спільних бібліотек (`.so`) у каталозі `/usr/lib/x86_64-linux-gnu/`. Цей пакунок дозволяє вже скомпільованим програмам запускатися, але в ньому **немає заголовкових файлів** мов C/C++.
2. **Девелоперський пакунок (`libuv1-dev` у Debian/Ubuntu, `libuv-devel` у RHEL/Fedora):** Містить заголовкові файли C (`uv.h` у `/usr/include/`), статичні архіви (`.a`), документацію та файл метаданих для систем збірки (`libuv.pc`).

**Правило розв'язання:** Для збірки програми з джерел у системі завжди повинні встановлюватися відповідні `-dev` / `-devel` версії всіх бібліотек-залежностей:

```bash
# Debian / Ubuntu:
sudo apt install build-essential libuv1-dev libssl-dev zlib1g-dev

# RHEL / Fedora / Rocky Linux:
sudo dnf install gcc gcc-c++ libuv-devel openssl-devel zlib-ng-devel
```

#### 4.2. Як влаштований механізм `pkg-config` / `pkgconf`

Щоб не прописувати шляхи до заголовків (`-I/usr/include/foo`) та імена бібліотек (`-lfoo`) вручну у `Makefile`, системи збірки звертаються до утиліти `pkg-config` (або її сучасного швидкого аналога `pkgconf`).

Усі параметри кожної встановленої бібліотеки зберігаються у текстовому файлі з розширенням `.pc`, який зазвичай розташований у `/usr/lib/x86_64-linux-gnu/pkgconfig/` або `/usr/share/pkgconfig/`.

Приклад вмісту файлу `openssl.pc`:

```ini
prefix=/usr
exec_prefix=${prefix}
libdir=${exec_prefix}/lib/x86_64-linux-gnu
includedir=${prefix}/include

Name: OpenSSL
Description: Secure Sockets Layer and cryptography libraries and tools
Version: 3.0.13
Requires.private: libssl libcrypto
Cflags: -I${includedir}
Libs: -L${libdir} -lssl -lcrypto
```

Коли система збірки виконує перевірку, вона викликає утиліту `pkg-config` із відповідними запитами:

```bash
# Отримання прапорців препроцесора (шляхи пошуку заголовків):
$ pkg-config --cflags openssl
-I/usr/include

# Отримання прапорців лінкера (шляхи до бібліотек та прапорці зв'язування):
$ pkg-config --libs openssl
-lssl -lcrypto

# Перевірка версії бібліотеки:
$ pkg-config --modversion openssl
3.0.13
```

#### Тонкощі статичного лінкування: `Requires.private` та `Libs.private`

Коли програма лінкується динамічно, їй достатньо знати лише пряму залежність (`-lssl`), оскільки динамічний завантажувач ядра `ld-linux` сам знайде непрямі залежності через заголовок `DT_NEEDED` у файлі `libssl.so`.

Однак під час статичного лінкування (`--static`) компонувальник зобов'язаний отримати повне замикання транзитивних залежностей. Прапорець `pkg-config --static --libs openssl` зчитує поля `Requires.private` та `Libs.private`, повертаючи повний ланцюг бібліотек (наприклад, `-lssl -lcrypto -ldl -pthread`).

#### Робота з нестандартними шляхами через `PKG_CONFIG_PATH`

Якщо залежність була скомпільована вручну та встановлена у нестандартний префікс (наприклад, `/opt/openssl3`), системний `pkg-config` не побачить її файл метаданих.

Для підключення такої бібліотеки системному інструменту вказують змінну середовища `PKG_CONFIG_PATH`:

```bash
export PKG_CONFIG_PATH="/opt/openssl3/lib/pkgconfig:$PKG_CONFIG_PATH"
./configure --prefix=/opt/myproxy
```

Система збірки спочатку перевірить каталоги зі змінної `PKG_CONFIG_PATH`, знайде файл `/opt/openssl3/lib/pkgconfig/openssl.pc` і автоматично використає прапорці нової бібліотеки замість застарілої системної.

### 5. Чисте та безпечне встановлення: як не засмітити операційну систему

Найбільш руйнівною дією початківця є сліпе виконання команди `sudo make install` у системний префікс за замовчуванням `/usr/local`.

![Порівняння стратегій встановлення скомпільованого ПЗ у Linux](/root/course/unix/build-from-source/img/clean-installation-strategies.svg)
*Три підходи до встановлення скомпільованого ПЗ: небезпечний прямий запис, префіксна ізоляція та створення нативних системних пакетів.*

#### 5.1. Чому прямий `sudo make install` є небезпечним

1. **Відсутність обліку файлів:** Пакетний менеджер операційної системи (`dpkg` або `rpm`) веде сувору базу даних усіх встановлених у системі файлів. Команда `make install` копіює файли в обхід менеджера пакетів. ОС «не знає», звідки взялися ці бінарники у `/usr/local/bin` та бібліотеки у `/usr/local/lib`.
2. **Відсутність надійного механізму видалення:** Більшість сторонніх проєктів не мають правила `make uninstall` або реалізують його некоректно. Якщо ви захочете видалити програму через пів року, вам доведеться вручну відшукувати розкидані файли серед сотень інших бібліотек.
3. **Конфлікти версій та підміна системних бібліотек:** Якщо програма встановить у `/usr/local/lib` власну версію `libcrypto.so`, системний динамічний завантажувач може віддати їй пріоритет над системною бібліотекою `/usr/lib/libcrypto.so`, що призведе до порушення працездатності системних утиліт (`ssh`, `curl`, `sudo`).

---

#### 5.2. Стратегія 1: Ізоляція у виділений префікс (`/opt/<app>` або `~/.local`)

Безпечним способом встановлення є повна ізоляція програми всередині окремого підкаталогу:

```bash
./configure --prefix=/opt/myproxy-1.4
make -j$(nproc)
sudo make install
```

Усі файли програми потрапляють в ізольований каталог `/opt/myproxy-1.4/`. Для повного видалення програми достатньо виконати `sudo rm -rf /opt/myproxy-1.4`.

Щоб програма була доступна для запуску в консолі, її бінарник лінкують у системний шлях або додають каталог у змінну `PATH`:

```bash
# Спосіб 1: Створення символічного посилання
sudo ln -s /opt/myproxy-1.4/bin/myproxy /usr/local/bin/myproxy

# Спосіб 2: Додавання шляху в ~/.bashrc
export PATH="/opt/myproxy-1.4/bin:$PATH"
```

Якщо програма встановлює власні спільні бібліотеки, під час компіляції обов'язково вшивають відносний заголовок завантажувача `RUNPATH`:

```bash
LDFLAGS="-Wl,-rpath,'$ORIGIN/../lib'" ./configure --prefix=/opt/myproxy-1.4
```

Тег `$ORIGIN` гарантує, що виконуваний файл завантажить свої бібліотеки з каталогу `/opt/myproxy-1.4/lib` автоматично, не вимагаючи глобальної зміни змінної `LD_LIBRARY_PATH`.

---

#### 5.3. Стратегія 2: Створення нативних системних пакетів (`DESTDIR`, `checkinstall`, `fpm`)

Найбільш зрілим інженерним підходом для серверного розгортання є створення нативного DEB чи RPM пакета.

#### Механізм перехоплення через `checkinstall`

Утиліта `checkinstall` дозволяє автоматизувати створення пакета під час звичайної збірки. Замість команди `sudo make install` виконується:

```bash
sudo checkinstall --pkgname=myproxy --pkgversion=1.4.0 --nodoc
```

`checkinstall` запускає інсталяційне правило під контролем допоміжної динамічної бібліотеки `installwatch` через механізм `LD_PRELOAD`. Бібліотека перехоплює системні виклики файлового запису (`open`, `openat`, `creat`, `unlink`, `mkdir`, `rename`), формує повний список створених файлів, пакує їх у нативний `.deb` або `.rpm` пакунок і реєструє його в системній базі даних пакетного менеджера.

#### Промисловий підхід з проміжним каталогом `DESTDIR` та `fpm`

У промислових конвеєрах CI/CD використання `LD_PRELOAD` часто обмежене безпековими політиками. Замість цього використовують стандартну змінну `DESTDIR` (*Destination Directory*). Вона дозволяє встановити програму у тимчасовий каталог-пісочницю без прав адміністратора:

```bash
# 1. Конфігурація з реальним цільовим префіксом /opt/myproxy
./configure --prefix=/opt/myproxy

# 2. Компіляція
make -j$(nproc)

# 3. Інсталяція у тимчасовий каталог stage
make install DESTDIR=/tmp/pkg-staging
```

Структура `/tmp/pkg-staging/opt/myproxy/` містить усі готові файли. Програма залишається скомпільованою під префікс `/opt/myproxy`, але реальна файлова система хоста не зазнає жодних змін.

Після цього утиліта `fpm` (*Effing Package Manager*) перетворює каталог `stage` на готовий DEB або RPM пакунок:

```bash
fpm -s dir -t deb \
    -n myproxy \
    -v 1.4.0 \
    -C /tmp/pkg-staging \
    --prefix / \
    --description "High-performance custom HTTP/3 proxy" \
    .
```

В результаті створюється файл `myproxy_1.4.0_amd64.deb`. Його можна встановити через стандартний пакетний менеджер:

```bash
sudo dpkg -i myproxy_1.4.0_amd64.deb
```

Тепер програма повністю обліковується операційною системою. Її можна безпечно оновити або чисто видалити командою `sudo apt remove myproxy`.

Детальний практичний розбір процесу збірки ізольованого демона, зв'язування залежностей через `PKG_CONFIG_PATH`, вшивання тегу `$ORIGIN` та створення нативного `.deb` пакета наведено у матеріалі [практичний рецепт повної ізольованої збірки та пакування](root:course/unix/build-from-source/proj-isolated-build.md).

### Підсумковий алгоритм збірки чужого коду

Коли ви стикаєтеся з новим архівом вихідного коду, рекомендований порядок інженерних дій виглядає так:

1. **Ідентифікація системи збірки:**
   - Наявний `./configure` -> GNU Autotools (`./configure && make`).
   - Наявний `CMakeLists.txt` -> CMake (`cmake -B build && cmake --build build`).
   - Наявний `meson.build` -> Meson + Ninja (`meson setup build && ninja -C build`).
2. **Встановлення інструментів та залежностей:**
   - Встановлення компіляторів (`build-essential` або `gcc-c++`).
   - Пошук та встановлення `-dev` / `-devel` пакетів для всіх бібліотек, про які повідомляє конфігуратор.
3. **Конфігурація з ізольованим префіксом:**
   - Завжди вказуйте явний префікс `--prefix=/opt/<app>` або готуйте дерево під `DESTDIR`.
   - Вмикайте необхідні рівні оптимізації через `CFLAGS="-O3 -march=native"`.
4. **Паралельна збірка:**
   - Використовуйте `make -j$(nproc)` або `ninja -C build` для максимального завантаження ядер CPU.
5. **Чисте розгортання:**
   - Використовуйте `make install DESTDIR=...` разом із `fpm` для генерації пакетів або ізолюйте додаток у `/opt/` із вшиванням `$ORIGIN` у `RUNPATH`.
