# 📋 Довідник змінних середовища та прапорців конвеєрів збірки

Складання двійкових виконуваних файлів і спільних бібліотек у середовищі Unix вимагає строго узгодженої взаємодії між системою збірки, препроцесором, компілятором, компонувальником та системним інсталятором. На відміну від інтегрованих середовищ розробки, де налаштування приховані за графічним інтерфейсом, консольні інструменти збірки зчитують конфігурацію через стандартизовані змінні середовища та параметри командного рядка. Ці змінні визначають вибір конкретного компілятора в системі, рівні апаратної оптимізації під цільову мікроархітектуру процесора, шляхи пошуку заголовкових файлів сторонніх бібліотек та кінцеву розкладку артефактів у файловій ієрархії.

Нижче наведено структурований інженерний довідник системних змінних, прапорців компіляції та матрицю їхньої трансляції між основними генераторами збірки: GNU Autotools, CMake та Meson.

---

### 1. Змінні вибору компонентів інструментального ланцюга (Toolchain)

Коли система збірки генерує або виконує команди компіляції, вона не викликає компілятор за жорстко зашитим ім'ям, а звертається до відповідних змінних середовища. Це дозволяє прозоро підміняти стандартний набір GNU Compiler Collection (GCC) на інструменти на базі LLVM/Clang або задіювати кроскомпілятори для інших процесорних архітектур (наприклад, ARM64 або RISC-V).

| Змінна | Призначення | Типове системне значення | Приклад перевизначення |
| :--- | :--- | :--- | :--- |
| `CC` | Компілятор мови C | `gcc` або `cc` | `CC=clang` або `CC=aarch64-linux-gnu-gcc` |
| `CXX` | Компілятор мови C++ | `g++` або `c++` | `CXX=clang++` або `CXX=aarch64-linux-gnu-g++` |
| `CPP` | Автономний препроцесор мови C | `$CC -E` | `CPP="gcc -E"` |
| `LD` | Статичний компонувальник об'єктних файлів | `ld` або `ld.bfd` | `LD=ld.lld` або `LD=ld.gold` |
| `AR` | Архіватор для створення статичних бібліотек (`.a`) | `ar` | `AR=llvm-ar` |
| `RANLIB` | Генератор індексу символів для архівів `ar` | `ranlib` | `RANLIB=llvm-ranlib` |
| `STRIP` | Утиліта видалення таблиці символів та налагоджувальної інформації | `strip` | `STRIP=llvm-strip` |
| `PKG_CONFIG` | Виконуваний файл пошуку метаданих залежностей | `pkg-config` | `PKG_CONFIG=pkgconf` |

#### Механізм вибору компілятора в скриптах конфігурації

Під час старту скрипт `configure` перевіряє змінну `CC`. Якщо вона не задана користувачем, скрипт ітерує список відомих імен компіляторів (`gcc`, `clang`, `cc`) у каталогах змінної `PATH`, створює тимчасовий тестовий файл `conftest.c` і намагається його скомпільувати. Якщо компілятор не підтримує базовий стандарт або не здатен створити двійковий файл, скрипт негайно перериває роботу.

Перевизначення компілятора рекомендується виконувати як явний аргумент конфігуратора, а не через глобальний експорт, щоб уникнути побічних ефектів у поточному терміналі:

```bash
# Рекомендований спосіб для GNU Autotools:
./configure CC=clang CXX=clang++

# Рекомендований спосіб для CMake:
cmake -B build -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++

# Рекомендований спосіб для Meson:
CC=clang CXX=clang++ meson setup build
```

### 2. Прапорці етапів компіляції та компонування

Процес перетворення вихідного тексту на виконуваний бінарник складається з трьох послідовних кроків: препроцесування, трансляції у машинний код та зв'язування об'єктних файлів. Прапорці чітко розмежовані за етапами, на яких вони обробляються.

| Змінна | Фаза обробки | Типові прапорці та призначення | Важливі застереження |
| :--- | :--- | :--- | :--- |
| `CPPFLAGS` | Препроцесор C/C++ | `-I/opt/custom/include`<br>`-DDEBUG=1`<br>`-D_GNU_SOURCE` | Застосовується **і для C, і для C++**. Передає шляхи до заголовків та макровизначення. |
| `CFLAGS` | Компілятор мови C | `-O2`, `-O3`<br>`-march=native`<br>`-Wall -Wextra`<br>`-fPIC` | Впливає **виключно** на компіляцію вихідних файлів мови C (`.c`). |
| `CXXFLAGS` | Компілятор мови C++ | `-std=c++20`<br>`-O3 -march=native`<br>`-fno-exceptions`<br>`-fPIC` | Впливає **виключно** на компіляцію вихідних файлів мови C++ (`.cpp`, `.cc`). |
| `LDFLAGS` | Компонувальник (`ld`) | `-L/opt/custom/lib`<br>`-Wl,-rpath,'$ORIGIN/../lib'`<br>`-Wl,-z,relro,-z,now` | Містить шляхи пошуку бібліотек (`-L`) та спеціальні директиви лінкера (`-Wl,...`). |
| `LIBS` | Підключення бібліотек | `-lssl -lcrypto -lpthread -lm` | Перелік конкретних бібліотек для зв'язування. Передається в кінці команди лінкування. |

#### Детальний розбір впливу прапорців на поведінку інструментів

1. **Керування пошуком заголовків через `CPPFLAGS`:**
   Прапорець `-I/шлях/до/include` додає вказаний каталог на початок списку пошуку для директив препроцесора `#include <...>`. Це дозволяє використовувати новіші або нестандартні версії бібліотечних заголовків замість системних із `/usr/include`.
   Макроси `-DNAME` або `-DNAME=VALUE` еквівалентні директиві `#define NAME VALUE` на початку кожного файлу трансляції.

2. **Оптимізація та кодогенерація через `CFLAGS` / `CXXFLAGS`:**
   - `-O2` — стандартний рівень оптимізації для стабільних релізів, що вмикає векторизацію, інлайнінг невеликих функцій та розгортання циклів без надмірного роздування розміру бінарника.
   - `-O3` — агресивніша оптимізація, що додає глибоке розгортання циклів та автовекторизацію з використанням ширших процесорних регістрів.
   - `-march=native` — вказівка генератору коду використовувати всі інструкції поточного процесора (AVX2, AVX-512, FMA, AES-NI). Бінарник стає максимально швидким, але втрачає переносимість на старіші процесори.
   - `-fPIC` (*Position Independent Code*) — обов'язковий прапорець для коду, що збирається у спільні бібліотеки (`.so`). Він змушує компілятор адресувати дані через таблицю глобальних зміщень (GOT).

3. **Керування лінкером через `LDFLAGS` та `LIBS`:**
   - `-L/шлях/до/lib` — додає каталог до списку пошуку бібліотек під час компонування.
   - `-Wl,опція` — інструктує компілятор передати `опцію` безпосередньо системному компонувальнику `ld`.
   - `-Wl,-rpath,'$ORIGIN/../lib'` — вшиває відносний шлях пошуку бібліотек прямо в ELF-заголовок `DT_RUNPATH`, позбавляючи потреби у змінній `LD_LIBRARY_PATH` під час запуску програми.

### 3. Змінні ієрархії файлової системи (FHS) та інсталяції

Після завершення компіляції скомпільовані двійкові файли, бібліотеки, конфігурації та супутня документація копіюються в системні каталоги. Організація цих шляхів підпорядковується стандарту Filesystem Hierarchy Standard (FHS).

| Змінна / Параметр | Опис призначення за FHS | Значення в Autotools за замовчуванням | Значення в системних пакунках |
| :--- | :--- | :--- | :--- |
| `prefix` (`--prefix`) | Головний кореневий префікс встановлення | `/usr/local` | `/usr` або `/opt/<app>` |
| `exec_prefix` | Префікс для архітектурно-залежних файлів | `${prefix}` | `${prefix}` |
| `bindir` | Виконувані файли загального доступу | `${exec_prefix}/bin` | `/usr/bin` |
| `sbindir` | Двійкові файли системного адміністрування | `${exec_prefix}/sbin` | `/usr/sbin` |
| `libexecdir` | Допоміжні бінарні утиліти внутрішнього виклику | `${exec_prefix}/libexec` | `/usr/lib/<app>` |
| `libdir` | Спільні (`.so`) та статичні (`.a`) бібліотеки | `${exec_prefix}/lib` | `/usr/lib/x86_64-linux-gnu` |
| `includedir` | Заголовкові C/C++ файли (`.h`, `.hpp`) | `${prefix}/include` | `/usr/include` |
| `sysconfdir` | Текстові файли конфігурації програми | `${prefix}/etc` | `/etc` |
| `localstatedir` | Динамічні змінні дані (логи, бази, сокети) | `${prefix}/var` | `/var` |
| `datarootdir` | Архітектурно-незалежні статичні дані | `${prefix}/share` | `/usr/share` |
| `mandir` | Каталог довідкових сторінок системного man | `${datarootdir}/man` | `/usr/share/man` |
| `DESTDIR` | Тимчасовий кореневий каталог підготовки пакетів | *(порожньо)* | `/tmp/staging-area` |

#### Фундаментальна різниця між `PREFIX` та `DESTDIR`

Розробники-початківці часто припускаються критичної помилки, плутаючи призначення параметрів `PREFIX` та `DESTDIR`:

- **Параметр `PREFIX`** задається на етапі конфігурації (`./configure --prefix=/opt/myapp`). Його значення жорстко компілюється в код програми як константа (наприклад, шлях до типового конфігураційного файлу `/opt/myapp/etc/app.conf` або плагінів `/opt/myapp/lib/plugins`). Програма очікує знайти свої ресурси саме за цим шляхом під час звичайного запуску в операційній системі.
- **Змінна `DESTDIR`** діє виключно під час виконання інсталяційного правила (`make install DESTDIR=/tmp/stage`). Вона працює як тимчасовий префікс до абсолютного шляху, перенаправляючи запис файлів: файл, який мав потрапити в `/opt/myapp/bin/app`, записується у `/tmp/stage/opt/myapp/bin/app`. Самі бінарники при цьому не змінюються і продовжують зберігати внутрішні шляхи до `/opt/myapp`. Це основа для створення чистих пакунків `.deb` або `.rpm` без прав суперкористувача.

### 4. Змінні пошуку системних залежностей та бібліотек

Під час складання складного ПЗ виникає необхідність підключати бібліотеки, встановлені в нестандартні префікси або розробницькі каталоги. Для цього використовуються спеціалізовані змінні середовища, що спрямовують інструменти пошуку метаданих та динамічні компонувальники.

| Змінна | Призначення | Формат запису та приклад |
| :--- | :--- | :--- |
| `PKG_CONFIG_PATH` | Додаткові каталоги пошуку `.pc`-файлів перед системними шляхами | `/opt/openssl3/lib/pkgconfig:/home/user/.local/lib/pkgconfig` |
| `PKG_CONFIG_LIBDIR` | Повне перевизначення системного списку пошуку `.pc` (ігнорує системні `/usr/lib/...`) | `/opt/toolchain/sysroot/usr/lib/pkgconfig` |
| `PKG_CONFIG_SYSROOT_DIR` | Кореневий префікс sysroot для корекції абсолютних шляхів у `.pc`-файлах | `/opt/sysroot-arm64` |
| `CMAKE_PREFIX_PATH` | Префікси пошуку пакунків у CMake для `find_package()` | `/opt/qt6;/opt/boost` |
| `LD_LIBRARY_PATH` | Шляхи пошуку динамічних бібліотек завантажувачем `ld-linux.so` під час виконання | `/opt/custom/lib:$LD_LIBRARY_PATH` |
| `LD_RUN_PATH` | Шляхи, які лінкер `ld` автоматично записує в ELF-заголовок `DT_RPATH` під час компіляції | `/opt/custom/lib` |

### 5. Зведена матриця: трансляція прапорців між системами збірки

Різні генератори проєктів використовують різні механізми отримання прапорців: Autotools спирається на змінні оточення та аргументи командного рядка, CMake вимагає явних параметрів з префіксом `-D`, а Meson використовує власну систему типізованих параметрів.

| Дія / Налаштування | GNU Autotools | CMake (версії 3.20+) | Meson + Ninja |
| :--- | :--- | :--- | :--- |
| Встановлення цільового префікса | `./configure --prefix=/opt/app` | `cmake -B build -DCMAKE_INSTALL_PREFIX=/opt/app` | `meson setup build --prefix=/opt/app` |
| Профіль оптимізації (Release) | `./configure CFLAGS="-O3 -DNDEBUG"` | `cmake -B build -DCMAKE_BUILD_TYPE=Release` | `meson setup build --buildtype=release` |
| Профіль відлагодження (Debug) | `./configure CFLAGS="-g -O0"` | `cmake -B build -DCMAKE_BUILD_TYPE=Debug` | `meson setup build --buildtype=debug` |
| Увімкнення адресного санітайзера | `CFLAGS="-fsanitize=address" ./configure` | `cmake -B build -DCMAKE_C_FLAGS="-fsanitize=address"` | `meson setup build -Db_sanitize=address` |
| Генерація `compile_commands.json` | `bear -- make` (зовнішня утиліта) | `cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` | *(створюється автоматично у теці build/)* |
| Запуск паралельної компіляції | `make -j$(nproc)` | `cmake --build build -j$(nproc)` | `ninja -C build` |
| Безпечна інсталяція в тимчасовий каталог | `make install DESTDIR=/tmp/stage` | `DESTDIR=/tmp/stage cmake --install build` | `DESTDIR=/tmp/stage ninja -C build install` |

### 6. Типові інженерні пастки при роботі зі змінними збірки

Практична робота з прапорцями збірки супроводжується низкою типових проблем, викликаних особливостями внутрішнього функціонування компіляторів та компонувальників Linux.

#### Пастка 1: Однопрохідна модель компонувальника GNU ld (Порядок бібліотек у LIBS)

Системний компонувальник `ld` в операційних системах сімейства Linux сканує об'єктні файли та спільні бібліотеки строго зліва направо у тому порядку, в якому вони передані у командному рядку. Коли компонувальник опрацьовує об'єктний файл `main.o`, він формує таблицю нерозв'язаних зовнішніх символів (наприклад, функцію `SSL_new`). Зустрічаючи наступний аргумент `-lssl`, він знаходить реалізацію функції у бібліотеці й витягує її.

Якщо розробник помилково передає бібліотеку `-lssl` усередині змінної `LDFLAGS` (яка підставляється **перед** об'єктними файлами), компонувальник аналізує `libssl.so` в момент, коли список нерозв'язаних символів ще порожній. Бібліотека ігнорується, після чого обробляється `main.o`, і лінкування завершується фатальною помилкою:

```
main.o: in function 'init_tls':
main.c:(.text+0x34): undefined reference to 'SSL_new'
collect2: error: ld returned 1 exit status
```

**Правильне правило:** Прапорці пошуку каталогів (`-L/path`) передаються у `LDFLAGS`, а самі бібліотеки (`-lssl -lcrypto`) — строго у змінну `LIBS` або в кінець списку залежностей цілі `Makefile`.

#### Пастка 2: Забруднення C-компілятора прапорцями C++ через CPPFLAGS

Змінна `CPPFLAGS` (*C PreProcessor Flags*) передається як компілятору C, так і компілятору C++. Якщо помістити туди прапорець вибору стандарту C++ (наприклад, `-std=c++20`), компілятор мови C згенерує помилку `error: invalid argument '-std=c++20' not allowed with 'C'`.

**Правильне правило:** Прапорці конкретних мов програмування ізолюються: стандарти C — у `CFLAGS` (`-std=c11`), стандарти C++ — у `CXXFLAGS` (`-std=c++20`), а в `CPPFLAGS` передаються лише універсальні макроси (`-D_GNU_SOURCE`) та шляхи до заголовків (`-I/path`).

#### Пастка 3: Відсутність прапорця `-fPIC` для проміжних статичних архівів

Якщо проєкт спочатку збирає статичну бібліотеку `libcore.a`, а потім намагається вбудувати її у динамічну спільну бібліотеку `libplugin.so`, усі вихідні файли статичного архіву повинні бути скомпільовані з прапорцем `-fPIC`. На 64-бітних архітектурах x86-64 пряма 32-бітна адресація абсолютних адрес призводить до помилки компонування:

```
/usr/bin/ld: libcore.a(core.o): relocation R_X86_64_32 against '.rodata' can not be used when making a shared object; recompile with -fPIC
```

**Правильне правило:** Якщо статичний код призначений для подальшого лінкування у спільні бібліотеки, у `CFLAGS` та `CXXFLAGS` обов'язково додається прапорець `-fPIC`.
