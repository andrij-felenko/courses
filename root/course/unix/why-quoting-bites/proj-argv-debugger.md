# ⚙️ Інспектор аргументів: перехоплення та трасування argv[]

Командна оболонка передає параметри програмам через системний виклик `execve(2)` у формі масиву покажчиків `argv[]`. Проте на практиці розробники намагаються діагностувати поведінку скриптів за допомогою утиліти `echo $VAR` або `printf "%s\n" $VAR`. Цей підхід створює оманливу ілюзію коректності: сама команда `echo` знову проходить через повний цикл розкриття, зливає аргументи через пробіли і маскує реальні межі токенів, приховані символи переведення рядка (`\n`), табуляції чи нульові байти.

Для точної діагностики поведінки розкриттів необхідний інструмент, який фіксує аргументи безпосередньо в точці їхнього отримання від ядра або перехоплює виклик `execve(2)` до запуску цільового процесу. Нижче розроблено дві взаємодоповнюючі реалізації діагностичного інспектора: пряму тестову утиліту-зонд `argv-dump` та динамічну бібліотеку `libargv_trace.so` для прозорого перехоплення викликів через механізм `LD_PRELOAD`.

## Архітектура перехоплення: як ядро бачить argv[]

У момент виконання системного виклику `execve(const char *pathname, char *const argv[], char *const envp[])` ядро Linux виділяє сторінки пам'яті у верхній частині адресного простору нового процесу (стек ядра й користувача) та копіює туди послідовність рядків із нульовим байтом-термінатором (`\0`). На стек процесу поміщаються:
1. `argc` — 64-бітне ціле число (кількість аргументів).
2. `argv[0] ... argv[argc-1]` — масив покажчиків на початок кожного рядка.
3. `argv[argc]` — обов'язковий покажчик `NULL`.
4. `envp[0] ... envp[N]` — масив покажчиків на змінні середовища.
5. Допоміжний вектор ядра (*auxiliary vector*, `auxv`) — системна інформація про сторінки, розмір кешу та контекст безпеки процесу.

```
Стек пам'яті процесу (високі адреси):
┌─────────────────────────────────────────────────────────────┐
│ Рядки аргументів: "rm\0", "-rf\0", "My Document.txt\0"      │
├─────────────────────────────────────────────────────────────┤
│ Покажчики: argv[0] ──► "rm\0"                               │
│            argv[1] ──► "-rf\0"                              │
│            argv[2] ──► "My Document.txt\0"                  │
│            argv[3] ──► NULL                                 │
├─────────────────────────────────────────────────────────────┤
│ Кількість: argc = 3                                         │
└─────────────────────────────────────────────────────────────┘
```

Якщо під час розгортання в оболонці відбувся помилковий поділ на слова (*Word Splitting*), рядок `My Document.txt` розривається ще до передачі ядру на два незалежні покажчики `argv[2] ──► "My\0"` та `argv[3] ──► "Document.txt\0"`. Наш інспектор роздруковує кожен елемент масиву із зазначенням індексу, точної довжини в байтах та шістнадцяткового дампу недрукованих символів.

## Анатомія пам'яті на стеку процесу

Коли ядро Linux завершує системний виклик `execve`, адресний простір старого процесу повністю знищується, а на його місце завантажуються секції нового бінарного файлу формату ELF (*Executable and Linkable Format*). Вершина стека ініціалізується за домовленістю ABI System V (для архітектур x86_64 та AArch64).

Першим елементом на вершині стека (`%rsp`) розташоване 8-байтне число `argc`. Відразу за ним лежить масив покажчиків `argv[0]`, `argv[1]` ... `argv[argc-1]`, за яким слідує нульовий покажчик `NULL` (8 байтів нулів). Далі розташований масив покажчиків на змінні середовища `envp[]`, який також завершується покажчиком `NULL`. Самі текстові байти рядків розміщуються вище за стеком у неперервному блоці пам'яті.

Ця структура гарантує, що аргументи командного рядка є абсолютно ізольованими рядками мови C. Кожен аргумент починається за адресою свого покажчика і триває до першого байта `0x00`. Пробіли всередині рядка `My Document.txt` є звичайними байтами `0x20` і не мають жодного значення для операційної системи. Якщо ж оболонка помилково розділила рядок під час Word Splitting, вона створила два окремі покажчики, кожен із яких отримав власний нульовий байт-термінатор.

## Прозоре перехоплення через LD_PRELOAD

Якщо потрібно дослідити скрипт або бінарну програму без модифікації її вихідного коду (наприклад, сторонній білд-скрипт чи інсталятор), ми створюємо бібліотеку-обгортку, що підміняє виклик `execve(2)` у просторі користувача.

Динамічний завантажувач Linux (`ld.so`) при виявленні змінної середовища `LD_PRELOAD` завантажує зазначену бібліотеку раніше за системну `libc.so`. Коли будь-який процес у дереві виконання викликає функцію `execve`, керування передається нашому перехоплювачу. Перехоплювач роздруковує параметри у потік діагностики `stderr` і викликає оригінальну функцію ядра через покажчик, отриманий від `dlsym(RTLD_NEXT, "execve")`.

## Механізм динамічного перехоплення символів

Механізм перехоплення спирається на функцію `dlsym` зі спеціальним псевдодескриптором `RTLD_NEXT`. Цей дескриптор наказує динамічному лінкеру шукати наступне входження символу з ім'ям `execve` у списку завантажених спільних бібліотек за порядком їхнього завантаження. Оскільки наша бібліотека стоїть першою в списку завдяки `LD_PRELOAD`, виклик `dlsym(RTLD_NEXT, "execve")` знаходить справжню функцію-обгортку всередині `libc.so`, яка вже здійснює реальний системний виклик переходу в ядро через інструкцію `syscall`.

Зверніть увагу: у випадку помилки перехоплювач викликає функцію `_exit(1)`, а не `exit(1)`. Це критично важливо, оскільки стандартна функція `exit` запускає обробники завершення процесу `atexit` та скидає буфери вводу-виводу, що може призвести до повторного виклику перехоплених функцій або зациклення.

## Компіляція та практичні сценарії налагодження

Зберемо обидва інструменти за допомогою стандартного компілятора GCC або Clang:

```bash
# Компіляція утиліти-зонда
gcc -O2 -Wall -Wextra argv-dump.c -o argv-dump

# Компіляція бібліотеки перехоплення
gcc -O2 -Wall -Wextra -fPIC -shared libargv_trace.c -o libargv_trace.so -ldl
```

### Сценарій 2: Діагностика поведінки "$@" та "$*" у функціях-обгортках

Напишемо тестовий скрипт `wrapper_test.sh`, який делегує аргументи:

:::code proj-argv-debugger/sh/stsenarii-2-diahnostyka.sh

Запуск скрипту виводить вичерпний результат:
- `forward_star_unquoted`: `argc = 4` (`"alpha"`, `"beta"`, `"gamma"`). Початкові межі розбито, аргумент 1 розірвано.

- `forward_at_quoted`: `argc = 3` (`"alpha beta"`, `"gamma"`). Єдина конструкція, яка зберегла початкову структуру вектора `argv[]`.

### Сценарій 3: Трасування недрукованих символів та переведень рядків

Особливо підступними є випадки, коли у вивід команди або значення змінної потрапляють символи нового рядка `\n` або табуляції `\t`:

```bash
$ DATA=$'first line\nsecond line\twith tab'

# Виклик без лапок
$ ./argv-dump $DATA
# Розбивається на 4 окремі аргументи: "first", "line", "second", "line with tab"

# Виклик у подвійних лапках
$ ./argv-dump "$DATA"
# Передається як рівно 1 аргумент із байтами 0x0a (\n) та 0x09 (\t)
```

Інспектор `argv-dump` чітко підсвічує символи `\n` та `\t` у секції `[asc]` та їхні шістнадцяткові коди `0a` і `09` у секції `[hex]`, унеможливлюючи плутанину між пробілом і новим рядком.

### Сценарій 4: Прозорий аудит складного конвеєра через LD_PRELOAD

Підключивши нашу бібліотеку до будь-якої складної оболонки, білд-системи Make або скриптів CMake, ми фіксуємо кожен системний запуск:

```bash
$ LD_PRELOAD=./libargv_trace.so find . -maxdepth 1 -name "*.txt" -exec ls -l "{}" +
```

Утиліта `find` з прапорцем `-exec ... +` накопичує знайдені файли і передає їх утиліті `ls` єдиним великим масивом `argv[]`. Перехоплювач `libargv_trace.so` виведе точний список файлів, які отримав `ls`, дозволяючи перевірити, чи не перевищено системний ліміт `ARG_MAX` і чи коректно оброблено файли зі спецсимволами.

Цей метод незамінний під час налагодження Docker-контейнерів, скриптів CI/CD та системних демонів, де стандартний вивід `stdout` недоступний або перенаправлений у системний журнал `journald`.

## Обмеження механізму перехоплення та безпека

Під час використання `LD_PRELOAD` слід враховувати два системні обмеження ядра Linux:
1. **Бінарні файли із прапорцем setuid / setgid**: ядро Linux з міркувань безпеки автоматично ігнорує змінну `LD_PRELOAD` для програм, у яких біт `setuid` встановлено і власником є інший користувач (наприклад, утиліти `sudo`, `su`, `passwd`). Це блокує можливість виконання довільного коду з правами суперкористувача.
2. **Статично скомпільовані бінарні файли**: програми, скомпільовані статично (наприклад, написані мовою Go без використання CGO або на C з прапорцем `-static`), не використовують динамічний завантажувач `ld.so` і звертаються до ядра безпосередньо через асемблерну інструкцію `syscall`. Для аудиту таких процесів слід застосовувати системний трасувальник `strace` або підсистему ядра `eBPF`.
