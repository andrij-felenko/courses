# ⚙️ Здатності пристроїв DH: від товстого IDevice до вузьких інтерфейсів

Товстий `IDevice` коштував нам винятку о третій ночі. Давач температури, змушений типом обіцяти `turnOff`, `lock` і `startStream`, кидав «не підтримую» рівно тоді, коли хаб уперше проходив по ньому нічною петлею. Ми вже бачили, звідки береться цей біль і яким одним рухом його прибирають — розкроїти товстий тип по здатностях. Тепер зробімо це по-справжньому: візьмімо модель пристроїв Digital Homes і перепишімо її з кінця в кінець — вузькі інтерфейси, чесні пристрої, хаб, що питає «чи вмієш?», і тест, який упіймав би стару пастку, якби та колись повернулася. Код тут не ескіз, а те, що кладеться у файл і запускається.

Головну мову беремо **TypeScript**: його структурна типізація й сторожі типів роблять здатності рідною ідіомою — саме тут вони лягають найприродніше. Поряд, вкладкою, той самий дизайн мовою **Python** на `Protocol` з `runtime_checkable` — щоб побачити, що розкрій по здатностях не тримається на одній мові, це властивість самої думки.

## Задача

Сформулюймо, чого хочемо, точно — трьома вимогами, і кожну можна перевірити:

1. **Жоден пристрій не стоїть за обіцянкою, якої не тримає.** У типі пристрою немає методу, якого він не вміє, — отже, зникають і порожні тіла, і `throw «не підтримую»`. Це бік ISP.
2. **Хаб торкається пристрою лише крізь наявну здатність.** Петля не питає «якого ти класу?» — вона питає «чи вмієш `turnOff`?» і кличе тільки те, що справді є. Це бік LSP: підстановка стає чесною, бо неможливого виклику просто не стається.
3. **Регресію ловить тест.** Якщо колись хтось знову підсуне об'єкт, що бреше поведінкою, автоматичний тест на підстановку має впасти — до продакшену, а не о третій ночі.

Три вимоги — одна нитка: тип каже правду, межа перевіряє здатність, тест стереже, щоб правда не з'їхала.

## Ідея: здатність як одиниця типу

Здатність (англ. *capability*, від лат. *capax* — місткий, спроможний вмістити) — це вузький інтерфейс, що називає **одне реальне вміння** пристрою, і більше нічого. `Readable` — «вмію віддати число». `Switchable` — «вмію вмикатися й вимикатися». Замість одного типу, який перелічує все, що вміє хоч якийсь пристрій, ми маємо жменьку маленьких типів, і кожен пристрій набирає з них рівно ті, що справді тримає.

Що робить цей набір дешевим — **структурна типізація**: пристрій належить до `Switchable` не тому, що десь так написав, а тому, що **має** методи `turnOn`/`turnOff`/`isOn`. У TypeScript ключове слово `implements` — це лише позначка для читача й ранній контроль компілятора; збіг типів рахується за формою, а не за іменем предка. У Python те саме дає `Protocol`: класу не треба нічого успадковувати — досить мати потрібні методи. Це давня ідіома, «качкова типізація» (англ. *duck typing*, від приказки «якщо воно крякає, як качка, і ходить, як качка, то це качка»): не питай, якого воно роду, — дивись, що воно вміє.

Саме тому здатності не заганяють у дерево. `SmartSocket` — водночас `Readable` (розумна розетка міряє спожиту потужність) і `Switchable`, і для цього не треба ні множинного спадкування, ні ромбів у ієрархії: він просто має обидва набори методів. Новий рід пристрою завтра принесе свою комбінацію здатностей — і жодного наявного типу чіпати не доведеться.

Лишається одне питання: коли хаб дістає пристрій, як йому на межі **спитати** — а ти часом не `Switchable`? У TypeScript це **сторож типу** (англ. *type guard*) — булева функція `d is Switchable`, що не лише вертає `true`/`false`, а й **звужує** статичний тип у гілці, де вона істинна. У Python — `isinstance(d, Switchable)` на `Protocol`, позначеному `@runtime_checkable`. Обидва механізми перевіряють **форму** — чи є на об'єкті методи з такими іменами. Затям це слово, «форма»: воно ще вистрелить, коли дійдемо до тесту. Бо сторож каже «метод `turnOff` є» — і не каже нічого про те, чи цей `turnOff` справді вимикає, а чи кидає виняток.

## Робочий код

### Вузькі здатності

Починаємо з розрізу. Кожна здатність — окремий інтерфейс, і жодна не знає про інші:

:::tabs
```ts
// Здатності: по одному вузькому інтерфейсу на кожне реальне вміння.
interface Readable   { read(): number; }
interface Switchable { turnOn(): void; turnOff(): void; isOn(): boolean; }
interface Lockable   { lock(): void; unlock(): void; isLocked(): boolean; }
interface Streamable { startStream(): string; stopStream(): void; }
```
```py
from typing import Protocol, runtime_checkable

# @runtime_checkable дозволяє питати isinstance(d, Switchable) під час роботи.
@runtime_checkable
class Readable(Protocol):
    def read(self) -> float: ...

@runtime_checkable
class Switchable(Protocol):
    def turn_on(self) -> None: ...
    def turn_off(self) -> None: ...
    def is_on(self) -> bool: ...

@runtime_checkable
class Lockable(Protocol):
    def lock(self) -> None: ...
    def unlock(self) -> None: ...
    def is_locked(self) -> bool: ...

@runtime_checkable
class Streamable(Protocol):
    def start_stream(self) -> str: ...
    def stop_stream(self) -> None: ...
```
:::

Зверни увагу, що `turnOn`, `turnOff` і `isOn` лежать **разом** в одному `Switchable`, а не розсипані на три інтерфейси. Це не випадковість, а свідома межа: хто керує розеткою, тому потрібні всі три вкупі — увімкнути, вимкнути й спитати стан — це одна зв'язна робота. Ми ще повернемось до цього, коли розбиратимемо, як легко тут перестаратися.

### Пристрої, що реалізують лише своє

Тепер самі пристрої. Кожен набирає рівно ті здатності, що справді має, — і в його тілі немає жодного зайвого методу:

:::tabs
```ts
class TempSensor implements Readable {
  constructor(private celsius: number) {}
  read(): number { return this.celsius; }          // це все, що він уміє
}

class SmartSocket implements Readable, Switchable {
  private on = false;
  constructor(private watts = 60) {}
  read(): number  { return this.on ? this.watts : 0; }  // спожита потужність, Вт
  turnOn(): void  { this.on = true; }
  turnOff(): void { this.on = false; }
  isOn(): boolean { return this.on; }
}

class DoorLock implements Lockable {
  private locked = false;
  lock(): void        { this.locked = true; }
  unlock(): void      { this.locked = false; }
  isLocked(): boolean { return this.locked; }
}

class Camera implements Streamable {
  private streaming = false;
  startStream(): string { this.streaming = true; return "rtsp://dh/cam/live"; }
  stopStream(): void    { this.streaming = false; }
}
```
```py
class TempSensor:                       # лише Readable — і жодного зайвого методу
    def __init__(self, celsius: float):
        self.celsius = celsius
    def read(self) -> float:
        return self.celsius

class SmartSocket:                      # Readable + Switchable, без спадкування
    def __init__(self, watts: float = 60.0):
        self._on, self._watts = False, watts
    def read(self) -> float:  return self._watts if self._on else 0.0
    def turn_on(self)  -> None: self._on = True
    def turn_off(self) -> None: self._on = False
    def is_on(self) -> bool:  return self._on

class DoorLock:                         # лише Lockable
    def __init__(self):
        self._locked = False
    def lock(self)   -> None: self._locked = True
    def unlock(self) -> None: self._locked = False
    def is_locked(self) -> bool: return self._locked

class Camera:                           # лише Streamable
    def __init__(self):
        self._streaming = False
    def start_stream(self) -> str:
        self._streaming = True
        return "rtsp://dh/cam/live"
    def stop_stream(self) -> None:
        self._streaming = False
```
:::

Придивись до Python-версії окремо: жоден клас **не успадковує** свій `Protocol`. `SmartSocket` ніде не пише «я `Switchable`» — він просто має `turn_on`/`turn_off`/`is_on`, і цього досить, щоб `isinstance(socket, Switchable)` дало `true`. Ось качкова типізація в чистому вигляді: приналежність до здатності випливає з того, що клас **уміє**, а не з того, що він **оголосив**. Порожні тіла зникли не тому, що ми їх акуратно поприбирали, — їх нема звідки взятися: тип більше не вимагає нічого зайвого.

### Проба здатності на межі

Щоб хаб міг спитати пристрій «чи вмієш?», заводимо по одному сторожу на здатність:

:::tabs
```ts
function isReadable(d: unknown): d is Readable {
  return typeof (d as Readable)?.read === "function";
}
function isSwitchable(d: unknown): d is Switchable {
  const s = d as Switchable;
  return typeof s?.turnOn === "function" && typeof s?.turnOff === "function";
}
function isLockable(d: unknown): d is Lockable {
  const l = d as Lockable;
  return typeof l?.lock === "function" && typeof l?.unlock === "function";
}
function isStreamable(d: unknown): d is Streamable {
  return typeof (d as Streamable)?.startStream === "function";
}
```
```py
# У Python окремі функції не потрібні: isinstance по runtime_checkable-Protocol
# і Є пробою здатності. isinstance(d, Switchable) перевіряє наявність методів.
```
:::

У TypeScript тип повернення `d is Switchable` — це не просто `boolean`. Він каже компіляторові: якщо ця функція повернула `true`, то в тій гілці коду `d` **точно** `Switchable`, і всередині можна кликати `d.turnOff()` без зайвих приведень. У Python окремі функції зайві — сам `isinstance(d, Switchable)` на `@runtime_checkable`-протоколі і є та проба; він перевіряє, що на об'єкті присутні всі методи протоколу.

І тут варто одразу назвати межу обох механізмів, поки вона не вкусила пізніше. Вони перевіряють **присутність методів за іменем** — і тільки. `runtime_checkable` за офіційною документацією Python звіряє саму наявність атрибутів, а не їхні підписи, ба навіть не те, чи вони взагалі викличні. TypeScript-сторож так само дивиться лише, що `typeof …turnOff === "function"`. Жоден із них не заглядає всередину `turnOff` і не питає, чи той справді вимикає. Форма — так; поведінка — ні.

### Чесний хаб: питати здатність, а не тип

Тепер серце системи. Нічний режим більше не сліпо кличе `turnOff` на будь-чому — він на межі питає кожен пристрій, що той уміє, і звертається лише крізь наявну здатність:

:::tabs
```ts
function nightMode(devices: unknown[]): void {
  for (const d of devices) {
    if (isSwitchable(d)) d.turnOff();      // світло й розетки — вимкнути
    if (isLockable(d))   d.lock();         // двері — замкнути
    if (isStreamable(d)) d.startStream();  // камери — на нічне чування
  }
}

// Запускається як є: змішаний парк проходить без жодного винятку.
const fleet: unknown[] = [
  new TempSensor(21.5),
  new SmartSocket(),
  new DoorLock(),
  new Camera(),
];
nightMode(fleet);   // давач мовчки пропущено — кинути виняток нема звідки
```
```py
def night_mode(devices: list[object]) -> None:
    for d in devices:
        if isinstance(d, Switchable): d.turn_off()   # світло й розетки
        if isinstance(d, Lockable):   d.lock()       # двері
        if isinstance(d, Streamable): d.start_stream()  # камери — на чування

fleet = [TempSensor(21.5), SmartSocket(), DoorLock(), Camera()]
night_mode(fleet)   # давач мовчки пропущено — кинути виняток нема звідки
```
:::

Простеж, що сталося з давачем температури. Він `Readable` — і тільки. `isSwitchable(sensor)` дає `false`, `isLockable` дає `false`, `isStreamable` дає `false`. Нічна петля тричі його питає й тричі обходить: жодного `turnOff`, жодного `lock`, жодного винятку. Той самий пристрій, що о третій ночі валив стару систему, тепер тихо проминається — не тому, що хтось додав `if (device instanceof TempSensor) continue`, а тому, що петля взагалі не цікавиться, який він на ім'я. Вона питає про вміння — і вмінь, яких треба нічному режимові, у нього просто нема.

Давач t° має тільки Readable; розетка — Readable і Switchable; замок — Lockable; камера — Streamable. Праворуч стовпець «nightMode кличе»: для давача «пропущено», для розетки turnOff, для замка lock, для камери startStream.](img/capability-matrix.svg)

*Хаб не питає «якого ти типу?» — він питає «чи вмієш?». Давач має лише Readable, якої нічний режим не чіпає, тож його мовчки пропускають — а з цього прямо випливає, що виняток о третій ночі кинути нема звідки.*

> 🔧 **Навіщо це.** Помітив, чого в `nightMode` **нема**? Нема жодного `switch` за типом пристрою, жодного `instanceof TempSensor`. А отже, коли завтра приїде новий рід пристрою — скажімо, `Thermostat`, що вміє `Switchable`, — петлю не доведеться чіпати: він пройде через `isSwitchable` сам, бо має потрібні методи. Хаб залежить від **здатностей**, не від переліку класів, — і тому росте прибудовою нових пристроїв, а не редагуванням старого циклу. Це те, чого й хотіли від точки розширення: додавати, не переписуючи.

### Тест на підстановку, що ловить стару пастку

Хаб більше не падає — але звідки нам знати, що не впаде й завтра, коли хтось допише новий пристрій? Потрібен тест, який перевіряє не «чи є метод», а «чи метод чесний». Іншими словами — виконуваний [контракт](root:sf-release/design-by-contract): передумови й постумови, які будь-яка реалізація здатності мусить витримати. Для `Switchable` він короткий: після `turnOn` пристрій увімкнений, після `turnOff` — вимкнений, і жодна з дій не кидає.

:::tabs
```ts
// Крихітний раннер без залежностей — запускається як є.
let failures = 0;
function check(name: string, fn: () => void): void {
  try { fn(); console.log(`ok    ${name}`); }
  catch (e) { failures++; console.log(`FAIL  ${name}: ${(e as Error).message}`); }
}
function assert(cond: boolean, msg: string): void {
  if (!cond) throw new Error(msg);
}

// Контракт Switchable — придатний для БУДЬ-ЯКОЇ реалізації.
function switchableContract(make: () => Switchable): void {
  const d = make();
  d.turnOn();  assert(d.isOn() === true,  "після turnOn має бути ввімкнено");
  d.turnOff(); assert(d.isOn() === false, "після turnOff має бути вимкнено");
}

// Об'єкт, що ВДАЄ Switchable: форма збігається, а поведінка бреше —
// точно та пастка, яку товстий IDevice робив неминучою.
class LyingSwitch implements Switchable {
  turnOn():  void    { throw new Error("не вмикається"); }
  turnOff(): void    { throw new Error("не вимикається"); }
  isOn():    boolean { return false; }
}

check("nightMode не падає на змішаному парку", () =>
  nightMode([new TempSensor(19), new SmartSocket(), new DoorLock(), new Camera()]));

check("SmartSocket чесно виконує контракт Switchable", () =>
  switchableContract(() => new SmartSocket()));

check("сторож ПРОПУСКАЄ брехуна за формою", () =>
  assert(isSwitchable(new LyingSwitch()) === true, "форма Switchable у нього є"));

check("а контракт брехуна ЛОВИТЬ", () => {
  let caught = false;
  try { switchableContract(() => new LyingSwitch()); } catch { caught = true; }
  assert(caught, "контракт мусив упіймати брехню, але пропустив");
});

console.log(failures ? `\n${failures} впало` : "\nусе зелене");
```
```py
def switchable_contract(make) -> None:
    d = make()
    d.turn_on();  assert d.is_on() is True,  "після turn_on має бути ввімкнено"
    d.turn_off(); assert d.is_on() is False, "після turn_off має бути вимкнено"

class LyingSwitch:                        # форма Switchable є, поведінка бреше
    def turn_on(self):  raise RuntimeError("не вмикається")
    def turn_off(self): raise RuntimeError("не вимикається")
    def is_on(self) -> bool: return False

# 1) сторож (isinstance) ПРОПУСКАЄ брехуна — форма ж збігається:
assert isinstance(LyingSwitch(), Switchable)
# 2) чесна реалізація проходить контракт:
switchable_contract(lambda: SmartSocket())
# 3) а контракт брехуна ЛОВИТЬ:
try:
    switchable_contract(lambda: LyingSwitch())
    raise AssertionError("контракт мусив упіймати брехню")
except RuntimeError:
    pass                                  # саме цього й чекали
print("усе зелене")
```
:::

Ось де сходяться дві половини задуму, і це найтонше місце всього кроку. Сторож `isSwitchable` **пропускає** брехуна — повертає `true`, бо метод `turnOff` у нього формально є. Сторож перевіряє форму, а форма в брехуна бездоганна. Але контракт-тест брехуна **валить**: він не дивиться на форму, він кличе `turnOff` і питає `isOn()` — а там виняток. Тобто розкрій по здатностях **прибрав тиск** брехати (давач просто не `Switchable`, тож у нічну петлю не потрапляє й упасти не може), а контракт-тест — це **храповик**, що не дає нікому колись потім протягнути назад об'єкт, який знову вдає вміння, якого не має.

> 🔧 **Навіщо це.** Сторож і тест ловлять різні хвороби, і потрібні обидва. Сторож — фільтр **на межі**: він рятує від «нема методу» (виклик того, чого об'єкт не має). Контракт-тест — сітка **над поведінкою**: він рятує від «метод є, але бреше». Плутати їх — класична помилка: люди пишуть сторож і думають, що захистилися від поганих реалізацій. Ні: `typeof turnOff === "function"` — не обіцянка, що `turnOff` вимикає. Форму стереже сторож, поведінку — тест; прибери одне, і дірка відкриється саме там.

## Складність і пастки

Прийом стрункий, а зіпсувати його легко — і майже завжди на одному з чотирьох місць.

### Перевірка здатності всередині логіки, а не на межі

Найпоширеніша. Сторожі розповзаються по всьому коду: кожна функція, що торкається пристроїв, знову й знову перепитує `isSwitchable`, а `unknown` тече крізь усю систему аж до найглибших закутків.

```ts
// ❌ здатність перевіряють ГЛИБОКО в логіці, знову й знову
function runSchedule(devices: unknown[], plan: Step[]): void {
  for (const step of plan) {
    for (const d of devices) {
      if (step.kind === "off"  && isSwitchable(d)) d.turnOff();
      if (step.kind === "lock" && isLockable(d))   d.lock();
    }
  }
  // …і той самий частокіл if-isXxx у кожній наступній функції
}
```

Це той-таки товстий тип, тільки перевдягнений в `unknown`: замість чесних вузьких типів усередині бігає «щось», і кожен, хто хоче з ним працювати, мусить спершу вгадати, що воно вміє. Лікують це так: пробуємо здатність **один раз**, на межі, де пристрої входять у підсистему, і розкладаємо їх по кошиках уже вузьких типів. Далі логіка не бачить жодного `unknown`:

```ts
// ✓ перевірили ОДИН раз на межі — далі течуть уже вузькі типи
interface Fleet {
  switchable: Switchable[];
  lockable:   Lockable[];
  streamable: Streamable[];
}
function classify(devices: unknown[]): Fleet {
  const f: Fleet = { switchable: [], lockable: [], streamable: [] };
  for (const d of devices) {
    if (isSwitchable(d)) f.switchable.push(d);   // тут d звужено до Switchable
    if (isLockable(d))   f.lockable.push(d);
    if (isStreamable(d)) f.streamable.push(d);
  }
  return f;
}
function nightMode(f: Fleet): void {
  f.switchable.forEach((s) => s.turnOff());       // жодного isXxx — тип уже вузький
  f.lockable.forEach((l) => l.lock());
  f.streamable.forEach((c) => c.startStream());
}
```

> 🔧 **Навіщо це.** Межа — це те місце, де недовірене «щось» уперше зустрічається з типізованим світом. Проба здатності мусить жити **там** і лише там: раз перевірив — далі код говорить вузькими типами й ніколи не перепитує. Коли бачиш `isSwitchable` глибоко в бізнес-логіці — це запах, що межу поставлено не там і товстий тип протік усередину як `unknown`. Заганяй перевірку на край; ядро хай не знає слова «unknown».

### Над-сегрегація: розсікти те, що беруть разом

Протилежна крайність. Захопившись «вужче — краще», інтерфейс дроблять до одного методу — і розтинають те, що клієнт завжди вживає вкупі:

```ts
// ❌ одну зв'язну здатність розсічено на три
interface PowerOn    { turnOn():  void; }
interface PowerOff   { turnOff(): void; }
interface PowerState { isOn():    boolean; }

// клієнт, що керує розеткою, тепер мусить прийняти всі три — і зібрати їх назад:
function toggle(d: PowerOn & PowerOff & PowerState): void {
  if (d.isOn()) d.turnOff(); else d.turnOn();
}
```

Тут сигнал промовистий — оте `PowerOn & PowerOff & PowerState`: клієнт **збирає перетином** назад те, що ти щойно розрізав. ISP велить різати по **клієнтських швах** — там, де окрема група клієнтів вживає окрему підмножину методів, — а не за кількістю методів. Хто керує живленням розетки, тому потрібні `turnOn`, `turnOff` і `isOn` **разом**: увімкнути, вимкнути, спитати стан — це одна робота, одна [зв'язність](root:sf-apps/coupling-cohesion). Справжній шов пролягає між **читанням**, **вмиканням** і **замиканням** — там і різати; всередині вмикання шва немає. Ознака, що ти перестарався, та сама, що видала себе вище: клієнти раз у раз зшивають твої інтерфейси перетином `A & B & C`, або найпростіша операція раптом вимагає трьох типів, щоб її бодай виразити.

### Спокуса повернути товстий фасад

Найпідступніша, бо приходить під маскою зручності. Розкроївши тип, за тиждень хтось стомлюється писати перевірки й заводить «спільний тип, щоб не морочитися»:

```ts
// ❌ товстий фасад чорним ходом — і LSP знову зламано
type Device = Readable & Switchable & Lockable & Streamable;
function getDevice(id: string): Device { /* … */ }   // «зручно ж»
```

Але `Device` як перетин **усіх** здатностей — це достеменно старий `IDevice`, лише записаний іншим синтаксисом. Щойно якийсь код починає вимагати `Device`, кожен пристрій знову мусить уміти все — і давач температури до цього типу не приткнути інакше, як порожніми тілами чи `throw`. Ми повернулися рівно туди, звідки тікали. Те саме з реєстром `Map<string, Device>`: він силою робить парк однорідним, а пристрої однорідними не є.

Чесний «спільний тип», якщо він потрібен, тримає лише те, що в пристроїв **справді** спільне, — їхню **тотожність**, а не суму всіх можливих дій:

```ts
// ✓ спільне — це особа пристрою, не його вміння
interface DeviceId { readonly id: string; readonly name: string; }
function allDevices(): DeviceId[] { /* … */ }
// а вміння з'ясовуємо пробою на межі: isSwitchable(d), isLockable(d), …
for (const d of allDevices()) if (isSwitchable(d)) d.turnOff();
```

Пристрої ділять `id` та `name` — і ганяються одним списком за цією спільною особою; а що кожен **уміє**, лишається питанням, яке ставлять на межі. Спокуса злити здатності назад в один тип — це і є гравітація товстого інтерфейсу; впізнавай її й опирайся.

### Структурний збіг: форма бреше про суть

Остання пастка росте з самої сили структурної типізації. Сторож і `isinstance` звіряють методи **за іменем** — тож будь-що з методом такого імені збіжиться, хай і зовсім не те:

```py
import io
# Текстовий буфер має метод .read — отже, структурно він «Readable»:
assert isinstance(io.StringIO("42"), Readable)       # True (!)
```

Це не хиба реалізації, а задокументована природа `runtime_checkable`: перевіряється присутність імені, не підпис і не сенс. Документація Python наводить власний приклад — рядок має `.encode()`, тож структурно вдовольняє будь-який протокол, що вимагає метод `encode`. Наш `Readable` вимагає `read` — і в нього несподівано «влучає» файл, `io.StringIO`, будь-що з методом `read`, хоч жодне з них не давач температури. Додай сюди, що `isinstance` по протоколу помітно повільніший за звичайний і може навіть **зачепити побічний ефект**, якщо здатність оголошено через `@property` (перевірка форми змусить властивість обчислитися), — і видно, що структурна проба це **евристика**, а не доказ.

Практична межа з цього така. Усередині свого коду, де ти сам пишеш усі реалізації, форма — надійний сигнал: випадкового `SmartSocket` із чужим `read` там не заведеться. Але на **межі недовіри** — де в систему входить щось ззовні — форми замало: там перевіряй не лише «чи є метод», а й що це той самий об'єкт, який ти очікуєш (походження, а не самий обрис). І називай здатності за **сенсом домену**, а не загальним словом: чим конкретніша поведінка стоїть за методом, то менше шансів на випадковий збіг. Сторож зручний рівно доти, доки пам'ятаєш, що він звіряє обрис, а суть — стереже вже тест.

## Що лишається в руках

Ми взяли модель пристроїв, де один товстий `IDevice` змушував давач температури брехати, і розклали її на чотири вузькі здатності — і з того самого руху випливло все інше. Пристрої стали чесними, бо тип більше не вимагає зайвого. Хаб перестав падати, бо питає «чи вмієш `turnOff`?», а не «хто ти?», — і давач, що вміє лише `read`, нічна петля тричі мовчки проминає. Тест на підстановку перетворив LSP із гасла на виконуваний контракт, що ловить брехуна, навіть коли форма в того бездоганна. А чотири граблі показали, де стрункий розкрій обертається на нову халепу: перевірка, розсіяна в глибині замість межі; здатність, розсічена дрібніше, ніж її беруть; товстий фасад, що лізе назад чорним ходом; форма, яку структурний збіг видає за суть.

Уся дисципліна звузилася до однієї звички — питати про пристрій **«чи вмієш?»**, а не **«хто ти?»**. Тип, що каже лише про наявні вміння; межа, що ці вміння перевіряє; тест, що стереже їхню чесність, — і парк пристроїв Digital Homes росте новими родами, жодного разу не змусивши котрийсь із них стати за обіцянку, якої він не тримає.
