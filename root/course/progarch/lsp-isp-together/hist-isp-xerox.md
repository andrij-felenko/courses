# 📜 Як фабрика Xerox породила ISP

Принципи SOLID переказують так, ніби їх видали згори — п'ять карбованих заповідей, які лишається завчити. Насправді кожен виріс із конкретного болю на конкретному проєкті, і принцип розділення інтерфейсів (ISP) — чи не найпрямолінійніший приклад: він народився не за кафедрою, а біля промислової друкарки, яка змушувала інженерів чекати годину після кожної дрібнички. Розберімо, звідки саме він узявся, — бо тут історія пояснює правило краще за будь-яке означення.

## Дядько Боб і друкарка, що думала годину

Людину, яка витягла ISP із живого коду, звати **Роберт Сесіл Мартін** (Robert Cecil Martin, нар. 5 грудня 1952) — американський інженер, якого галузь знає під прізвиськом «дядько Боб» (Uncle Bob). У професії він із 1970 року, а 1991-го заснував консалтингову фірму Object Mentor, з якою й ходив по чужих проєктах, розплутуючи архітектурні вузли. Один із таких проєктів — на початку–середині 1990-х — був у компанії Xerox.

Xerox робила нову систему друку: одна машина мала не лише друкувати, а й зшивати степлером, і слати факси, і сканувати — цілий комбайн офісних задач. Софт до неї ріс органічно, як росте всякий живий код під тиском термінів: коли треба ще одну операцію, її дописували туди, де вже було найзручніше. А найзручніше було в одному класі — його назвали `Job`, «задача». Через `Job` проходила майже кожна дія машини: друк — через `Job`, зшивання — через `Job`, факс — через `Job`.

Так `Job` розбух у те, що Мартін згодом назве **товстим класом** (fat class): у ньому зібралися методи геть усіх підсистем одразу. І тут вилазив бік, який на перший погляд здається дрібницею, а насправді паралізував розробку: клієнт степлера **бачив усі методи друку**, хоч не мав із них жодної користі, — просто тому, що вони жили в тому самому класі. Кожен клієнт залежав від усього `Job` цілком.

Наслідок був фізичний, не естетичний. За свідченням самого Мартіна, система розрослася так, що **найдрібніша зміна тягла за собою цикл перезбирання й розгортання завдовжки близько години**. Пересунув кому в методі факсу — сиди годину, поки все збереться й розкотиться на пристрій. Розробка вповільнилася майже до зупинки.

## Чому товстий клас коштував саме години

Тут варто спитати по-фейнманівськи: **чому** товстий клас коштує години? Адже, здавалося б, клієнт факсу й клієнт друку одне одному не заважають. Відповідь — у тому, як C++ (а система була на C++) в'яже код у мить збирання.

```cpp
// job.h — один товстий клас, який #include-ять УСІ клієнти
class Job {
public:
    void print();     // треба клієнтові друку
    void staple();    // треба клієнтові степлера
    void fax();       // треба клієнтові факсу
    void scan();
    void cancel();
    // …ще десятки методів усіх підсистем
};
```

Коли `Job` — один клас, оголошений в одному заголовку `job.h`, то **кожен** клієнт, якому потрібен бодай один метод `Job`, мусить підключити цей заголовок цілком. А тепер ключове: у C++ зміна заголовка змушує перезбиратися **всі** одиниці трансляції, які його підключають. Додав метод для факсу в `job.h` — і компілятор чесно перезбирає й клієнта друку, і клієнта степлера, і решту, хоч їх той факсовий метод нітрохи не обходить. Клієнти нічого не питали про факс — а платять за нього перезбиранням. Помнож на розмір системи, і ось вона, твоя година.

Тобто зчеплення тут не абстрактне «негарно зв'язано», а цілком матеріальне: **залежність за часом збирання** (compile-time dependency). Клас, у якому лежить усе, робить кожного клієнта заручником змін, що його не стосуються.

> 🔧 **Навіщо це.** Годинний цикл на C++ — крайній, наочний вияв, але хвороба ширша за одну мову. Байт-код Java чи C# перезбирається швидше, тож секундоміра не чути — зате лишається друге: клієнт, прив'язаний до товстого типу, тягне за собою в тестах, у документації, у власній голові дюжину методів, з яких йому потрібен один. Компілятор мовчить, а зчеплення нікуди не поділося. ISP економив Xerox години збирання; та навіть там, де збирання миттєве, він економить те саме по суті — увагу й свободу міняти чуже, не зачепивши свого.

## Діагноз: не залежати від того, чим не користуєшся

Мартінів діагноз був короткий, і його варто знати дослівно. Англійською він звучить так:

> «Clients should not be forced to depend upon interfaces that they do not use.»
>
> *(Robert C. Martin)*

Українською — **клієнтів не можна змушувати залежати від інтерфейсів, яких вони не вживають**. Пізніше те саме перефразовували ще стисліше: жоден код не повинен залежати від методів, яких не використовує. Придивися, як точно це просте правило вказує на хворобу `Job`: клієнт степлера **змушений** залежати — через спільний клас, через спільний заголовок — від методів друку й факсу, яких **не вживає**. Назвати хворобу — уже пів лікування.

## Ліки: інтерфейс на кожного клієнта, зшитий через DIP

Ліки Мартіна елегантні тим, що не чіпають самої машинерії. `Job` лишається одним класом — усю роботу й далі виконує він. Змінюється те, **як клієнти його бачать**. Перед товстим `Job` ставлять шар вузьких інтерфейсів — по одному на тип задачі: `PrintJob` для клієнта друку, `StapleJob` для клієнта степлера, `FaxJob` для факсу. Кожен інтерфейс оголошує рівно ті методи, що потрібні саме цьому клієнтові, — і нічого зайвого.

```cpp
// print_job.h — вузький інтерфейс: лише те, що бачить клієнт друку
class PrintJob {
public:
    virtual void print() = 0;
    virtual ~PrintJob() = default;
};

// staple_job.h — окремий вузький інтерфейс для клієнта степлера
class StapleJob {
public:
    virtual void staple() = 0;
    virtual ~StapleJob() = default;
};

// job.cpp — один клас реалізує ВСІ інтерфейси задач
class Job : public PrintJob, public StapleJob /*, FaxJob, … */ {
public:
    void print()  override;   // та сама реалізація, що й була
    void staple() override;
};
```

Клієнт степлера тепер підключає лише `staple_job.h` і залежить лише від `StapleJob`. Метод факсу може мінятися скільки завгодно — заголовок `StapleJob` при цьому й не ворухнеться, тож клієнта степлера **не перезбирають**. Годинний цикл розсипається на дрібні, бо зміна тепер торкається лише свого інтерфейсу, а не всіх заразом.

Зверни увагу на напрям стрілок — у ньому вся сіль. Клієнт залежить від свого інтерфейсу; а `Job` цей інтерфейс **реалізує**. Залежність, що раніше йшла від клієнта прямо до конкретного товстого класу, тепер перевернута: і клієнт, і `Job` спираються на вузьку абстракцію посередині. Це вже не сам ISP, а сусідній принцип, яким ISP зшивають на практиці, — [інверсія залежностей](book:programming/dependency-inversion) (DIP): залежати не від конкретного класу, а від абстракції, причому абстракцію визначає той, хто нею користується (клієнт), а не той, хто її реалізує. Саме DIP дає інтерфейсам «належати» клієнтам, а не постачальникові, — і без нього розтин `Job` не тримався б.

![Система друку Xerox до і після розтину: ліворуч три клієнти залежать від одного товстого Job, тож будь-яка зміна перезбирає всіх; праворуч перед Job стоять вузькі інтерфейси PrintJob, StapleJob, FaxJob, кожен клієнт залежить лише від свого, а один Job реалізує їх усі через DIP.](/root/course/progarch/lsp-isp-together/img/xerox-job-before-after.svg)

*Той самий клас `Job` до і після. Ліворуч кожен клієнт залежить від усього `Job`, і зміна перезбирає всіх; праворуч перед `Job` стоять вузькі інтерфейси, клієнт бачить лише свій, а `Job` реалізує їх усі — зміна більше не зачіпає сусідів.*

## Де це назвали й закріпили

Проєкт Xerox дав досвід; ім'я й формулювання прийшли трохи згодом і на папері. У середині 1990-х Мартін вів у журналі **C++ Report** авторську колонку «Engineering Notebook», де по черзі викладав принципи, що потім складуться в SOLID (він був і головним редактором цього журналу наприкінці 1990-х). Принцип розділення інтерфейсів вийшов там **1996 року** — це була четверта з тих колонок; саме в ній Xerox-історія й стала правилом із назвою. (Місяць у вторинних джерелах трохи різниться — трапляється і червень, і серпень 1996-го, — але рік усталений.)

Колонки — жанр швидкий і розпорошений. Тривке житло принципи дістали в книжках. 2000 року Мартін звів їх у програмну статтю «Design Principles and Design Patterns», а 2002-го вийшла книжка, яку відтоді цитують як канон, — **«Agile Software Development, Principles, Patterns, and Practices»** (Prentice Hall, 2002). У ній ISP стоїть уже не колонкою на кілька сторінок, а розділом у стрункому ряду поряд зі SRP, OCP, LSP і DIP.

Одну дрібницю варто прояснити, бо її часто плутають. Сам акронім **SOLID** Мартін не вигадував. П'ять принципів він сформулював і назвав кожен окремо; а от зібрати їхні перші літери в слово-пам'ятку «SOLID» додумався інший — **Майкл Фезерс** (Michael Feathers), приблизно 2004 року. Тобто принципи старші за акронім: спершу було п'ять окремих правил, вистражданих на таких проєктах, як Xerox, і лише потім — зручна мнемоніка, яка склала їх в одне вимовне слово.

## Що з цього правда, а що варто винести

Навколо гарних історій легко наростає легенда, тож ось статус кожної ланки — усе перевірене, розкладене за певністю.

- **Xerox-історія**: товстий `Job`, клієнт степлера, що бачить методи друку, годинний цикл перезбирання — **усталений генезис ISP**, який відтворюють і Wikipedia, і незліченні підручники. Важлива чесна поправка: жваві подробиці (та сама «близько години») переказують головно з **власних свідчень Мартіна** — він розповідав це в колонках і книжках; незалежного заводського звіту Xerox тут не наводять. Це не робить історію легендою, але джерело в неї одне, і його варто називати.
- **Формулювання** «Clients should not be forced to depend upon interfaces that they do not use» — **дослівне Мартінове**, канонічне означення ISP.
- **Публікація**: колонка «Engineering Notebook» у C++ Report, **1996** (четверта в серії SOLID-принципів) — усталено; місяць у вторинних джерелах різниться (червень/серпень), рік певний. Книжка **«Agile Software Development, Principles, Patterns, and Practices»**, Prentice Hall, **2002** (ISBN 0-13-597444-5) — усталений факт.
- **Акронім SOLID** склав **Майкл Фезерс** близько **2004** року, з уже готових Мартінових принципів, — усталено (це визнає й сам Мартін). Принципи передували мнемоніці.
- **Біографія**: Роберт Сесіл Мартін нар. 1952, у галузі з 1970-го, Object Mentor заснував 1991-го — усталені факти.
- **C++-механізм**: перезбирання всіх клієнтів від зміни спільного заголовка — **не історичний переказ, а перевірна властивість мови**; саме воно й було технічною мотивацією ISP, а не пізнішою раціоналізацією.

І головне, що пережило і C++, і сам Xerox. Хвороба була не в тому, що `Job` «негарний», а в тому, що він змушував кожного клієнта нести чуже. Ліки — не «менше методів», а **правильні шви**: інтерфейс належить тому, хто ним користується, а не тому, хто його реалізує. Ріж широку абстракцію по клієнтах — і жоден із них більше не платитиме за методи, яких не просив. Друкарка Xerox навчила цього дорого, годинами збирання; нам лишилося взяти урок уже задарма.
