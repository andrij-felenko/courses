О 19:42 у багатоповерховому комплексі з трьохсот квартир спрацювала пожежна тривога третього поверху. Системи Digital Homes мали миттєво відреагувати на подію за трьома незалежними напрямками: надіслати HTTP-вебхуки на сервери п'яти приватних служб охорони, відправити PUSH-сповіщення та SMS-повідомлення восьми сотням мешканців будинку, а також викликати зовнішній API платіжного провайдера для автоматичного поповнення балансу SMS-кредитів платформи.

Розробники першої версії платформи написали цей код напросту: усередині єдиної процедури обробки події запускався цикл, який послідовно робив HTTP `POST`-запити. І того вечора система зазнала повної катастрофи. Сервер однієї з охоронних компаній перебував на регламентному обслуговуванні й не закривав мережеве з'єднання, залишаючи сокет у стані очікування. Потоки робітників Digital Homes застрягли на 30-секундних таймаутах. За п'ятнадцять секунд пул потоків платформи вичерпався повністю. Транзакція в базі даних, яка мала зафіксувати факт спрацювання пожежного датчика, скасувалася за таймаутом (`ROLLBACK`). Проте зовнішній виклик до платіжного провайдера встиг пройти й списати 500 доларів США, але через скасування SQL-транзакції запис про поповнення балансу в базі даних не з'явився. Пуш-сповіщення мешканцям взагалі не вилетіли, а наївний внутрішній цикл повторів (retry) вистрілив п'ять разів поспіль на сервери чотирьох інших охоронних компаній, згенерувавши по п'ять дубльованих тривог у їхніх диспетчерських пультових.

Цей інцидент висвітлив головну ілюзію початківців: уявлення про те, що вихідний мережевий виклик — це звичайна локальна інструкція `http.post()`, розкидана по різних кутках бізнес-логіки. Насправді перетин межі власної системи змінює фізику обчислень. Вихід назовні (англ. *outbound egress*) — це не набір розрізнених викликів бібліотеки, а **єдиний окремий клас архітектурного вузла**, що має власні інваріанти, закони стійкості та анатомію.

## Два адресати, один клас вузла: Машина, Людина та Зовнішнє API

Усі вихідні взаємодії будь-якої розподіленої системи зовні виглядають несхоже, бо адресовані різним споживачам. Проте за фасадами цих вимог ховається ідентична мережева природа.

Розкладімо вихідний потік на три фундаментальні види адресатів:

1. **Вебхуки (виклики «машина-машина»):** Провайдер штовхає JSON-структуру на HTTP-ендпоінт партнерської системи. Тут панують жорсткі контракти схеми, мілісекундні SLA, вимоги до HMAC-підписів тіла та гарантія доставки `at-least-once`. Партнерська система — це програма, яка очікує чітких ключів ідемпотентності, версіонування схем даних (`X-Api-Version`) та унікальних ідентифікаторів подій. Автентифікація реалізується через симетричні HMAC-SHA256 ключі або двосторонній TLS (mTLS).
2. **Сповіщення (виклики «машина-людина»):** Система штовхає сигнал людині через багатоканальний фанаут (PUSH на мобільний пристрій через APNs/FCM, SMS через Twilio, Email через SendGrid, In-App). Тут програма стикається з психологією та обмеженою увагою користувача. У гру вступають тихі години (quiet hours), пріоритети каналів, дедуплікація, злиття подій у дайджести та жорсткі стелі темпу (throttling), щоб не викликати «синдром втоми від тривог». Автентифікація на боці шлюзів ОС або SMS-провайдерів здійснюється через авторизаційні токени й партнерські API-ключі.
3. **Виклики зовнішніх API (взаємодія з чужими сервісами):** Синхронний або асинхронний запит до сторонніх платіжних шлюзів (Stripe), картографічних сервісів (Google Maps), CRM або штучного інтелекту (OpenAI). Тут система виступає клієнтом, що залежить від сторонніх OAuth2-токенів, жорстких лімітів запитів (rate limits) та непередбачуваної латентності чужих серверів.

На перший погляд, між надсиланням SMS-повідомлення мешканцю й відправкою HMAC-підписаного вебхука на сервер Stripe немає нічого спільного. Але якщо прибрати формати заголовочних даних і суто прикладну специфіку адресата, виявиться, що всі три типи вихідних викликів підпорядковуються єдиній формі стійкості. [Історія еволюції вихідних взаємодій показує](root:progarch/outbound-node-recap/hist-outbound-patterns.md), як індустрія пройшла шлях від ручних пакетних файлів EDI до створення єдиного Egress-проксі.

*Адресат визначає формати й політики, але мережеві катастрофи та тактики стійкості ідентичні для всіх виходів: вихід назовні — це єдиний клас вузла.*

> 🔧 **Навіщо це.** Головна помилка архітектури — будувати окремий підхід для відправки SMS, окремий для пушів і окремий для вебхуків. Створивши три різні механізми, ви отримаєте три різні джерела аварій через однакові мережеві затримки. Узагальнення вихідного вузла дозволяє побудувати єдиний стійкий каркас (Outbox + Limiter + Circuit Breaker + DLQ), на який нанизуються будь-які канали відправки.

## Чотири фундаментальні пастки та інваріанти виходу назовні

Чому прямий виклик зовнішнього HTTP-сервера з середини бізнес-коду обов'язково призведе до катастрофи? Оскільки межа системи ділить світ на дві території з принципово різною фізикою: локальну пам'ять/БД (де діє ACID-транзакція) та віддалену мережу (де панує теорема CAP та невідворотність збоїв).

Розкладімо чотири фундаментальні пастки, які визначають обов'язкові інваріанти вихідного вузла.

### 1. Неповоротний side-effect (Non-undoable Side Effect)

Усередині бази даних будь-яку помилку можна скасувати інструкцією `ROLLBACK`. Якщо під час виконання SQL-скрипту стався збій, база повертається до початкового стану, ніби нічого не було.

Мережевий виклик назовні — це неповоротна дія. Ви не можете зробити `ROLLBACK` відправленому SMS-повідомленню, списуванню коштів у Stripe або HTTP `POST`-запиту на сервер партнерові. Як тільки байти залишили мережевий інтерфейс вашого сервера, зовнішній світ змінив свій стан. Звідси випливає перше правило: **мережевий виклик ніколи не повинен виконуватися всередині незафіксованої SQL-транзакції**.

### 2. Транспорт At-Least-Once та невідворотність дублікатів

У розподілених мережах не існує гарантії «фактично один раз» (exactly-once) на рівні транспорту. Якщо ваш вузол відправив HTTP-запит і не отримав відповіді протягом 5 секунд, ви перебуваєте в стані фундаментальної невизначеності:
* Запит міг не дійти до отримувача (впала мережа «туди»).
* Запит дійшов, обробився, але відповідь впала (впала мережа «назад»).
* Запит дійшов, але обробка на боці отримувача затягнулася понад ваш таймаут.

Щоб забезпечити надійність, вихідний вузол змушений виконувати повторні спроби (retry). А отже, доставка на рівні мережі завжди є **at-least-once** («щонайменше один раз»). Звідси випливає друге правило: **будь-який вихідний виклик мусить супроводжуватися дедуп-ключами та ідентифікаторами ідемпотентності**, щоб отримувач міг знешкодити дублікати.

### 3. Порушення порядку та перегони (Out-of-order & Races)

Завдяки наявності декількох паралельних робітників-відправників та мережевих повторів, подія #2 може бути доставлена отримувачу **раніше**, ніж подія #1. Якщо замок надіслав подію «зачинено» о 12:00, а потім «відчинено» о 12:01, мережева затримка чи retry першої події можуть призвести до того, що приймач отримає «відчинено», а через секунду — старе «зачинено».

Звідси третє правило: **вихідні повідомлення повинні нести монотонні позначки часу або послідовні версії (sequence numbers)**, а приймальний вузол має ігнорувати застарілі стани.

### 4. Лавиноподібні збої та отруєння ресурсів (Cascading Failures)

Якщо зовнішній сервіс починає відповідати повільно (наприклад, замість 50 мс віддає відповідь за 10 секунд), локальні робітники відправника застрягають у блокуючих читаннях сокетів. На операційно-системному рівні Linux це призводить до накопичення сокетів у стані `ESTABLISHED` з повними буферами `Send-Q/Recv-Q`. Ядро Linux починає повторно надсилати TCP SYN або ACK пакети згідно з налаштуваннями `sysctl` (`net.ipv4.tcp_syn_retries`, `tcp_retries2`). Пул з'єднань вичерпується, оперативно пам'ять заповнюється чергою невиконаних задач, і весь локальний вузол падає.

Звідси четверте правило: **вихідний вузол мусить ізолювати зовнішні виклики через Circuit Breaker, жорсткі таймаути та обмеження паралелізму (bulkheading)**.

![Зверху — небезпечна пастка подвійного запису (Dual-Write Trap): HTTP POST виконується всередині SQL-транзакції. Падіння HTTP робить ROLLBACK у БД, але мережевий виклик уже відбувся; падіння БД після успішного HTTP створює неузгодженість. *Пастка подвійного запису проти Transactional Outbox: винесення мережевого виклику за межі SQL-транзакції повністю усуває загрозу неузгодженості баз даних та мережі.*

## Анатомія вихідного вузла: шість шарів захисту та стійкості

Щоб гарантувати виконання чотирьох інваріантів, вихідний вузол будується як конвеєр із шістьма послідовними шарами обробки. Жодне повідомлення не потрапляє в мережу напросту — воно проходить крізь усі шість шарів.

```
Подія в системі → [1. Outbox] → [2. Dispatcher] → [3. Policy] → [4. Throttler] → [5. Transport & CB] → [6. DLQ & Audit] → Мережа
```

Розберімо кожен шар та його зону відповідальності.

### Шар 1. Transactional Outbox (Гарантія збереження наміру)

Замість виконання виклику `fetch()` у місці виникнення події, бізнес-код виконує атомарний SQL-запис у таблицю `outbox` в межах тієї ж транзакції, що й основна дія:

```sql
BEGIN TRANSACTION;
  UPDATE smart_locks SET state = 'unlocked' WHERE id = 'lock_42';
  INSERT INTO outbound_outbox (id, destination_type, payload, status, created_at)
  VALUES ('evt_998', 'WEBHOOK', '{"lock_id":"lock_42","state":"unlocked"}', 'PENDING', NOW());
COMMIT;
```

Це повністю вирішує проблему Dual-Write. Якщо транзакція впала — намір відправки не збережеться. Якщо зафіксувалася — намір гарантовано потрапить до вихідного робітника. Альтернативним підходом для високонавантажених систем є використання Change Data Capture (CDC, наприклад Debezium), який вичитає транзакційний лог бази даних (PostgreSQL WAL) і створює події без додаткових `INSERT` у SQL.

### Шар 2. Egress Dispatcher & Deduplication Key (Генерування ключів)

Окремий процес-воркер вичитає записи зі статусом `PENDING` (використовуючи конструкцію `FOR UPDATE SKIP LOCKED` для уникнення блокувань між паралельними воркерами).

Диспетчер генерує для кожного повідомлення детермінований **дедуп-ключ** (`X-Idempotency-Key` або `Message-ID`), який залежить від ідентичності бізнес-події (наприклад, `hash(lock_id + event_type + timestamp_minute)`). Якщо це вебхук — шар додає HMAC-підпис тіла з використанням спільного секрету партнера та поточної позначки часу `t`.

### Шар 3. Subscription, Preferences & Policy Gate (Перевірка прав та бажань)

Перш ніж витрачати мережеві ресурси чи гроші на виклик, шлюз перевіряє політики та преференси отримувача за алгоритмом деревовидного резолюшингу:
1. **Перевірка блокування підписки:** Для вебхуків перевіряється, чи активний партнер і чи підписаний він на цей конкретний тип події.
2. **Перевірка глобального Opt-Out:** Для сповіщень людині перевіряється, чи не натиснув користувач кнопку скасування підписки (`unsubscribe`).
3. **Перевірка тихіх годин (Quiet Hours):** Якщо поточний місцевий час користувача потрапляє в інтервал з 22:00 до 08:00, некритичні сповіщення буферизуються для ранкового дайджесту.
4. **Вибір пріоритетного каналу:** Якщо PUSH-токен відсутній або неактивний, шар переключає маршрут на резервний SMS або Email канал.

### Шар 4. Rate Limiter & Throttler (Захист темпу й бюджету)

Цей шар контролює швидкість вихідного потоку за допомогою алгоритму **Token Bucket** (відро жетонів):
* **Захист чужого API:** Якщо партнер вказав у контракті «не більше 100 запитів на секунду», локальний Rate Limiter притримує вихідний потік, не дозволяючи звалити сервіс партнера.
* **Захист власного бюджету:** Для платних каналів (SMS, voice calls) Throttler встановлює жорсткі ліміти на витрати коштів на одного користувача або на весь будинок на годину, запобігаючи фінансовому виснаженню через баги в сенсорах.

### Шар 5. Transport & Circuit Breaker (Ізоляція падінь та повтори)

Транспортний модуль безпосередньо виконує HTTP/gRPC/SMS виклик. Він захищений двома механізмами:

1. **Circuit Breaker (Автоматичний вимикач):** Перебуває в одному з трьох станів: `CLOSED` (нормальна робота), `OPEN` (сервіс партнеру впав, усі виклики миттєво відхиляються без виходу в мережу), `HALF-OPEN` (пробне зондування поодинокими запитами після таймауту відновлення).
2. **Exponential Backoff з Jitter:** Повторні спроби виконуються не через рівні проміжки часу, а зі зростаючим інтервалом та рандомізацією (зсувом), щоб уникнути ефекту резонансного шторму (Thundering Herd Problem):

```
delay = min(max_delay, base_delay * 2^attempt + random_jitter)
```

[Повну повнофункціональну схему вихідного вузла з Circuit Breaker та backoff реалізовано окремо](root:progarch/outbound-node-recap/proj-outbound-egress-node.md).

### Шар 6. Dead Letter Queue (DLQ) & Audit Trail (Мертва черга й логування)

Якщо після N спроб (наприклад, 5 або 10) повідомлення так і не вдалося доставити через помилки `4xx/5xx` чи невідповідність підпису, воно маркується як «отруйне» (poison message) і переміщується в **Мертву чергу (Dead Letter Queue, DLQ)**.

Запис у DLQ зберігає повний контекст: байти тіла, заголовки, історію всіх спроб з кодами помилок та часовими мітками. Інженери або оператори платформи отримують алерт, мають можливість усунути проблему на боці конфігурації й випустити ручне передоставлення (redeliver) повідомлень із DLQ.

![Конвеєр із шістьма блоками: 1. Outbox БД (атомарний запис наміру), 2. Диспетчер (генерування id та dedup-ключів), 3. Політики (преференси та тихі години), 4. Throttler (Token bucket та бюджети), 5. Транспорт (Circuit Breaker та retry з jitter), 6. DLQ та лог (мертва черга й аудит). Під кожним блоком — стисле курсивне пояснення його функції](img/outbound-node-anatomy.svg)

*Анатомія вихідного вузла: шість шарів захисту та стійкості. Жодна вихідна доставка не торкається мережі напросту: потік іде крізь усі 6 шарів по черзі.*

## Мережева інфраструктура: TLS, Пули сокетів та Егрес-Проксі

Окрім логіки п'яти шарів, вихідний вузол вимагає суворого керування сокетами операційної системи.

### Перевикористання з'єднань (Connection Pooling & Keep-Alive)

Кожен новий вихідний HTTP-запит вимагає створення TCP-з'єднання (TCP 3-way handshake: `SYN` → `SYN-ACK` → `ACK`) та TLS-рукостискання (`ClientHello` → `ServerHello` → обмін ключами). Це додає від 50 до 300 мілісекунд затримки на кожну відправку.

Вихідний вузол повинен використовувати **Connection Pooling** з активним `HTTP Keep-Alive`. Замість закриття сокета після кожної відповіді, пули підтримують відкриті зашифровані TCP-з'єднання до популярних хостів (APNs, FCM, Stripe, партнери). Це зменшує латентність вихідного потоку в 4–5 разів і захищає ядро Linux від вичерпання ефемерних портів (портова виснаженість, `TIME_WAIT` sockets exhaustion).

### Інфраструктурні Egress Proxies (Envoy / Istio vs Application Node)

У великих мікросервісних архітектурах постає вибір: реалізовувати вихідний вузол у коді робітників (In-Process Egress Library) чи винести його в окремий інфраструктурний шар **Egress Proxy** (наприклад, Envoy Egress Gateway):

* **In-Process Egress Library:** Код вихідного вузла компілюється безпосередньо у воркер додатку. Перевага — повний доступ до контексту бази даних, проста відладка, нуль додаткових мережевих хопів.
* **Infrastructure Egress Proxy (Envoy/Istio Sidecar):** Вихідний трафік усіх сервісів перехоплюється й маршрутизується крізь виділений проксі-сервер. Проксі бере на себе TLS-термінацію, ротацію OAuth-токенів, централізований Rate Limiting та виставлення метрик у Prometheus. Це ідеально для поліглотичних середовищ, де сервіси написані різними мовами.

## Стратегія Push + Pull: Ретраї проти періодичної звірки (Reconciliation)

Навіть найдосконаліший вихідний вузол із шістьма шарами захисту не може здолати катастрофи фундаментального характеру. Уявіть, що партнерська хмара вимикається на 48 годин через пожежу в дата-центрі. Черга робітників вихідного вузла вичерпає свої N спроб повторів, відправляє тисячі повідомлень у DLQ і припиняє спроби PUSH-доставки.

Коли хмара партнера повертається до життя через дві доби, її стан та стан Digital Homes розходяться повністю. PUSH-повідомлення про відчинення/зачинення дверей чи зміну статусів охоронних режимів за ці 48 годин втрачені.

Стійка архітектура вихідного вузла розв'язує цю проблему через комбінацію двох протилежних векторів: **Push + Pull Reconciliation**.

1. **Шлях PUSH (реактивний, швидкий):** Забезпечує доставку за мілісекунди або секунди в 99.9% повсякденних випадків. Подія виникає → Outbox → Egress Node → HTTP POST / PUSH.
2. **Шлях PULL (периодична фонова звірка):** Незалежний фоновий процес (Reconciliation Scanner), який за розкладом (наприклад, раз на годину або раз на добу) робить підсумковий запит до API партнера: `GET /v1/devices/status` або `GET /v1/events?since=timestamp`.

Зворотна звірка (Reconciliation) порівнює фактичний стан об'єктів у локальній базі даних зі станом віддаленого сервісу (наприклад, порівнянням хешів станів `state_hash`). Якщо виявлено розбіжність (наприклад, двері фактично відчинені, а в локальному твіні зафіксовано «зачинено»), сканер генерує коригуючу подію й відновлює остаточну узгодженість (eventual consistency).

![Угорі — швидкий шлях PUSH (подія → Egress вузол → HTTP POST до партнера за мілісекунди, але при падінні мережі push згасає в DLQ). Унизу — фоновий шлях PULL (Reconciliation Scanner раз на годину опитує API партнера й порівнює стани, відновлюючи узгодженість). Внизу банер про розподіл ролей](img/push-pull-reconciliation.svg)

*Стратегія Push + Pull: миттєвий пуш забезпечує низьку латентність у повсякденній роботі, а фонова звірка (Pull) гарантує остаточну узгодженість при довготривалих аваріях.*

> 🔧 **Навіщо це.** Ніколи не покладайтеся виключно на PUSH-вебхуки чи PUSH-сповіщення у критичних бізнес-доменах (фінанси, безпека майна, медичні сигнали). Вебхук — це сповіщення про факт, а не сам факт. Фоновий сканер звірки (Reconciliation) — це страхова сітка, яка гарантує, що навіть після повної 3-денної аварії мережі ваша система самостійно відновить правду.

## Матриця прийняття рішень для вихідних вузлів

На завершення зведемо всі інструменти та тактики вихідного вузла у підсумкову матрицю рішень залежно від характеру адресата.

| Критерій / Параметр | Вебхук (Машині) | Сповіщення (Людині) | Зовнішнє API (Партнерові) |
| :--- | :--- | :--- | :--- |
| **Основна мета** | Сповістити іншу систему про факт | Повідомити людину про подію | Отримати послугу / обчислити результат |
| **Семантика виклику** | Asynchronous Push (`at-least-once`) | Asynchronous Push (`fan-out`) | Request-Reply (Синхронно/Асинхронно) |
| **Гарантія збереження** | Transactional Outbox у БД | Transactional Outbox + Event Queue | Direct call або Outbox (залежно від контексту) |
| **Захист від дублів** | HMAC-підпис + `X-Idempotency-Key` | Ключ дедуплікації в Redis / БД | `Idempotency-Key` у HTTP-заголовку |
| **Керування потоком** | Rate Limit на адресата (Token Bucket) | Coalesce (дайджест) + Throttling | Bulkhead + Connection Pooling |
| **Політики обмеження** | Договірний SLA партнера (N req/sec) | Quiet hours + Преференси користувача | Офіційний Rate Limit провайдера |
| **Стратегія відмови** | Retry з jitter → DLQ після N спроб | Fallback каналу (Push → SMS → Email) | Circuit Breaker → Fallback / Degraded state |
| **Механізм звірки** | Pull Reconciliation через API списку | Агрегований лог доставок / Аудит | Reconciliation транзакцій / Re-query |

## Чекліст аудіту вихідного вузла

Перш ніж випускати вихідну систему в продакшен, проведіть аудит архітектури за шістьма пунктами:

1. **Ізоляція транзакцій:** Чи винесено всі мережеві виклики за межі активних SQL-транзакцій бази даних?
2. **Гарантія ідемпотентності:** Чи передається дедуп-ключ (`X-Idempotency-Key`) у кожному вихідному запиті?
3. **Захист від штормів:** Чи реалізовано автоматичний вимикач (Circuit Breaker) та експоненційний відступ із рандомізованим зсувом (Jitter)?
4. **Управління отруйними повідомленнями:** Чи налаштовано Dead Letter Queue (DLQ) із можливістю операторського передоставлення (redeliver)?
5. **Політики споживача:** Чи враховуються тихі години та преференси скасування підписки для людських сповіщень?
6. **Наявність звірки:** Чи існує фоновий процес періодичної звірки (Reconciliation Scanner) для відновлення правди при згасанні PUSH-доставки?

## Компас вихідного вузла

Вихід назовні — це межа, де ваша програма віддає контроль над часом, мережею й виконанням стороннім системам чи людям. Спроба поставитися до цієї межі легкодушно призводить до виснаження потоків, подвійних списань коштів та втрачених сповіщень.

Запам'ятайте чотири орієнтири компасу вихідного вузла:

1. **Не робіть вихідних мережевих викликів усередині SQL-транзакцій.** Завжди використовуйте **Transactional Outbox**, щоб атомарно зберегти намір відправки разом із бізнес-подією.
2. **Приймайте `at-least-once` як невідворотну реальність.** Оснащуйте кожне вихідне повідомлення унікальним дедуп-ключем, монотонною позначкою часу та HMAC-підписом.
3. **Ізолюйте вихідний потік крізь шість шарів захисту.** Не дозволяйте повільному зовнішньому API вбити локальний процес: вирубайте збійні напрямки через **Circuit Breaker**, згладжуйте повтори через **Jitter**, а отруйні повідомлення відкладайте в **DLQ**.
4. **Доповнюйте реактивний Push фоновим Pull.** Використовуйте періодичну звірку (Reconciliation) для відновлення правди після довготривалих мережевих аварій.
