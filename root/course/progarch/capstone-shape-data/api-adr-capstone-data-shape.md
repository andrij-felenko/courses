# 📋 Каталог ADR: Топологія даних та межі консистентності

<preknowlist>
- [Журнал рішений (ADR)](root:progarch/views-and-communication/dh-decision-log) — формат заповнення та збереження наскрізного сліду архітектурних рішень.
</preknowlist>

Цей довідник містить формалізований каталог Записів Архітектурних Рішень (Architectural Decision Records, ADR), у яких зафіксовано обґрунтування, альтернативи, компроміси та наслідки вибору моделей зберігання даних, меж консистентності та транзакційних патернів для глобальної платформи OmniTrade Global.

---

## 1. Методологія та формалізований шаблон ADR

Записи Архітектурних Рішень є головним інструментом боротьби з ерозією архітектури в еволюційних системах. Усі рішення зберігаються у Git-репозиторії поруч із вихідним кодом проєкту, що гарантує їхню актуальність та простежуваність під час зміни поколінь розробників.

Кожне стратегічне рішення фіксується за стандартизованим шаблоном Майкла Найгарда (Michael Nygard):

```text
ADR-XXX: [Коротка та чітка назва прийнятого рішення]
Статус: [Запропоновано | Прийнято | Замінено | Відхилено]
Дата: [YYYY-MM-DD]
Контекст: [Опис бізнес-проблеми, атрибутів якості, технічних обмежень та драйверів]
Розглянуті Альтернативи: [Перелік варіантів із їхніми плюсами й мінусами]
Рішення: [Обґрунтування обраного архітектурного вибору]
Наслідки: [Позитивні наслідки, ризики, компроміси та ціна реалізації]
```

## 2. ADR-001: Застосування Polyglot Persistence для відокремлених контекстів

* **Статус:** Прийнято
* **Дата:** 2026-08-18
* **Автори:** Архітектурна група OmniTrade

### Контекст
Система OmniTrade Global поєднує принципово різнорідні типи навантаження:
1. Фінансові транзакції гаманців (15 000 tps у трьох регіонах, вимога суворого дотримання інваріанту `balance >= 0`).
2. Повнотекстовий пошук товарного каталогу (100 000 rps, повнотекстові фільтри за цінами, категоріями та тегами).
3. Тимчасове резервування товарних позицій під час чекауту (висока конкуренція за обмежені складські залишки).
4. Накопичення телеметрії та аудиторських логів (понад 50 000 подій на секунду).

Первинна архітектура передбачала використання єдиного монолітного кластера PostgreSQL. Проте під час пікових навантажень складні OLAP-запити аналітики та повнотекстовий пошук зжирали оперативну пам'ять і IOPS дискової підсистеми СУБД, блокуючи виконання фінансових транзакцій чекауту.

### Розглянуті Альтернативи

1. **Альтернатива А: Єдиний потужний кластер PostgreSQL з вертикальним масштабуванням.**
   * *Плюси:* Проста обробка запитів; можливість робити прямі SQL-JOIN між усіма таблицями; єдина технологія для експлуатації.
   * *Мінуси:* Висока ціна заліза; жорстке зчеплення контекстів; OLAP-запити блокують OLTP-транзакції; небезпека єдиної точки відмови (Single Point of Failure).

2. **Альтернатива Б: Повний перехід на розподілену NoSQL СУБД (Apache Cassandra).**
   * *Плюси:* Лінійне горизонтальне масштабування; висока доступність при розривах мережі.
   * *Мінуси:* Відсутність суворих ACID-транзакцій та JOIN; ризик подвійних списань у фінансовому модулі; складність підтримки інваріантів.

3. **Альтернатива В: Стратегія Polyglot Persistence (Обрана).**
   * *Плюси:* Ідеальна відповідність бази даних до профілю навантаження контексту; повна ізоляція відмов.
   * *Мінуси:* Зростання операційної складності (Operational Overhead).

### Рішення
Прийняти архітектуру **Polyglot Persistence**. Кожен Bounded Context отримує власне ізольоване сховище даних, підібране строго під його тип навантаження:
* **Ledger & Wallet Context:** CockroachDB (Multi-Region Distributed SQL) зі строгим рівнем ізоляції `SERIALIZABLE`.
* **Catalog & Search Context:** OpenSearch cluster для повнотекстового пошуку + Redis Cluster для кешу Read-Models.
* **Order Context:** PostgreSQL із партиціонуванням за місяцями та регіонами.
* **Analytics Lake Context:** ClickHouse (Columnar Append-Only Store) для аудиту.

### Наслідки
* **Позитивні:** Повна ізоляція відмов і продуктивності (Fault Domain Isolation); можливість незалежного масштабування кожного сховища; можливість оптимізувати вартість інфраструктури.
* **Негативні / Ризики:** Команда повинна підтримувати експертизу в кількох технологіях СУБД; заборона на JOIN-запити між контекстами на рівні SQL; необхідність налаштування додаткових ETL/CDC pipelines.

## 3. ADR-002: Подвійна бухгалтерія (Double-Entry Ledger) та сувора ACID-консистентність

* **Статус:** Прийнято
* **Дата:** 2026-08-18
* **Автори:** Архітектурна група OmniTrade

### Контекст
У попередніх версіях платіжних модулів баланс користувача зберігався як єдине мутабельне поле `balance_cents` у таблиці `accounts`. При кожній транзакції виконувався SQL-запит `UPDATE accounts SET balance_cents = balance_cents - X`. 

Такий підхід спричиняв серйозні проблеми:
* При виникненні race conditions декілька паралельних запитів могли утворити від'ємний баланс.
* У разі збою мережі неможливо було з'ясувати, чи була операція проведена дійсно один раз.
* Відсутність історії змін унеможливлювала проведення незалежного фінансового аудиту.

### Розглянуті Альтернативи

1. **Альтернатива А: Збереження мутабельного балансу з оновленням через Optimistic Locking (`version`).**
   * *Плюси:* Проста схема даних; низький обсяг дискової пам'яті.
   * *Мінуси:* Масові відхилення транзакцій (High Abort Rate) при високій конкуренції запитів; відсутність аудиторського следа.

2. **Альтернатива Б: Повний Event Sourcing для всіх модулів.**
   * *Плюси:* Повна історія подій; можливість відтворити стан на будь-який момент часу.
   * *Мінуси:* Складність побудови поточного стану; високі затримки читання балансу без складних знімків (Snapshots).

3. **Альтернатива В: Класична Подвійна бухгалтерія у реляційній СУБД (Обрана).**
   * *Плюси:* 100% математична точність; суворий балансовий інваріант; легкість аудиту.
   * *Мінуси:* Швидке зростання обсягу дискової пам'яті.

### Рішення
1. Для всіх фінансових маніпуляцій застосовувати патерн **Подвійної бухгалтерії (Double-Entry Bookkeeping)**. Будь-який рух коштів створює мінімум два незмінні (immutable) записи у таблиці `ledger_entries`: дебет одного рахунку та кредит іншого.
2. Сума дебету завжди дорівнює сумі кредиту:

```
∑ Debit - ∑ Credit = 0    [інваріант подвійної бухгалтерії]
```

3. Заборонити `UPDATE` та `DELETE` у таблиці леджера. Будь-яке коригування виконується виключно сторнуючою транзакцією (Reversal Transaction).
4. Зберігати грошові величини суворо в цілих числах найменшої грошової одиниці (`cents`) для уникнення помилок округлення.

### Наслідки
* **Позитивні:** 100% математична аудитовність системи; відсутність втрат історії; гарантія виявлення розсинхрону балансів.
* **Негативні / Ризики:** Швидке зростання обсягу таблиць `ledger_entries` (вимагає періодичного створення знімків балансу).

## 4. ADR-003: Транзакційний Outbox + Saga замість 2PC

* **Статус:** Прийнято
* **Дата:** 2026-08-18
* **Автори:** Архітектурна група OmniTrade

### Контекст
Чекаут замовлення вимагає узгодження дій між трьома незалежними контекстами: `Order Service`, `Wallet Service` (резервування коштів) та `Inventory Service` (резервування товарів). 

Класичний розподілений протокол двох фаз (Two-Phase Commit, 2PC / XA) вимагає утримання блокувань на всіх вузлах протягом всього часу мережевого обміну, що знижує доступність системи до добутку доступностей усіх вузлів (`A = A1 · A2 · A3`) і призводить до частих системних блокувань (Deadlocks) при міжрегіональних затримках.

### Розглянуті Альтернативи

1. **Альтернатива А: Synchronous 2PC / XA Distributed Transactions.**
   * *Плюси:* Строга ACID-консистентність між сервісами.
   * *Мінуси:* Низька доступність; масові Deadlocks; високі затримки.

2. **Альтернатива Б: Dual-Write без Outbox (Пряма відправка у Kafka).**
   * *Плюси:* Проста реалізація без додаткових SQL-таблиць.
   * *Мінуси:* Ризик подвійного запису та розсинхронізації даних при падінні процесу.

3. **Альтернатива В: Transactional Outbox + Saga Orchestration (Обрана).**
   * *Плюси:* Висока доступність; відсутність розподілених блокувань; надійність доставки.
   * *Мінуси:* Поява вікна тимчасової неузгодженості (Eventual Consistency Window).

### Рішення
1. Повністю відмовитися від розподілених 2PC/XA транзакцій між мікросервісами.
2. Застосувати **Transactional Outbox** у кожному мікросервісі для атомарної публікації подій.
3. Координацію чекауту здійснювати через **Saga Orchestrator** у сервісі замовлень із підтримкою компенсаційних дій.

### Наслідки
* **Позитивні:** Висока автономність та доступність сервісів; відсутність розподілених блокувань баз даних.
* **Негативні / Ризики:** Поява тимчасової неузгодженості; необхідність проєктування компенсаційних сценаріїв.
