# 📋 Контракт метаданих пріоритезації та Brownout-відповідей

Щоб розподілена система могла ефективно відкидати другорядне навантаження на вході (Admission Control / Load Shedding) та узгоджено дегрувати свої функції (Brownout), клієнти, шлюзи та внутрішні мікросервіси мусять користуватися **єдиним специфікованим контрактом метаданих**.

Стандартні заголовки HTTP/gRPC, коди відповідей, атрибуція пріоритетів, транспортні протокольні кадри (HTTP/2 та HTTP/3), прокидання контексту W3C Baggage та розширення RFC 9457 Problem Details сигналізують про стан деградації у єдиній специфікації.

---

## 1. Категорії пріоритетів (Priority Classes)

Усі запити в системі класифікуються за рівнем критичності для бізнесу, фізичної безпеки та цілісності даних. Клас пріоритету виражається числом від `0` (найвищий) до `4` (найнижчий) або текстовим кодом.

| Рівень | Текстовий код | Назва класу | Допуск затримки | Опис та приклад у системі | Правило відкидання (Sheddability) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **P0** | `critical` | Critical Emergency | < 100 мс | Засувки, замки, аварійні тривоги, розплачування грошима | **Non-sheddable** (відкидається останнім при фізичному вичерпанні ресурсів) |
| **P1** | `high` | High Operational | < 500 мс | Критична телеметрія опалення, команди систем безпеки | Скидається лише в режимі катастрофічного тиску (Brownout L4) |
| **P2** | `medium` | Status / Presence | < 5–10 с | Статуси пристроїв online/offline, сповіщення про зміну стану | Скидається в першу чергу під помірним тиском (Brownout L3) |
| **P3** | `low` | Analytics / History | Хвилини | Запис історії телеметрії, агрегаційні графіки, фоновий синк | Скидається на ранніх стадіях перевантаження (Brownout L2) |
| **P4** | `background` | Bulk / Media | Доби | Вивантаження відеоархіву, експорт логів, пакетні звіти | **Shed first** (скидається першим при найменшому перевищенні порогу, Brownout L1) |

## 2. Заголовки запиту та транспортні кадри L7

Атрибуція пріоритету передається на трьох рівнях: заголовки HTTP/1.1, транспортні кадри мультиплексування (HTTP/2 та HTTP/3) та бінарні метадані gRPC.

### 2.1. HTTP/1.1 та HTTP/2 Custom Headers

При звичайній взаємодії за протоколами HTTP/1.1 та HTTP/2 Edge Gateway або надійний клієнт передає наступний комплект заголовків:

```http
X-Priority: P0-Critical
X-Client-Class: premium-tenant
X-Origin-Boundary: edge-gateway-01
X-Signature-Priority: sha256-a1b2c3d4...
```

- **`X-Priority`** (string, обов'язковий): Значення `P0-Critical`, `P1-High`, `P2-Medium`, `P3-Low`, `P4-Background`.
- **`X-Client-Class`** (string, опціональний): Рівень клієнта (`free`, `pro`, `enterprise`). Використовується для чесного розподілу всередині одного класу пріоритету.
- **`X-Brownout-Tolerant`** (boolean, опціональний): `true`, якщо клієнтський застосунок підтримує роботу зі спрощеними частковими відповідями (`206 Partial Content`).
- **`X-Signature-Priority`** (string, обов'язковий на внутрішній мережі): HMAC-підпис від Edge Gateway. Захищає від спроб сторонніх клієнтів самовільно встановити собі статус P0 (Anti-Spoofing Guard).

### 2.2. HTTP/3 Extensible Priorities (RFC 9218) та HTTP/2 Stream Dependency

У мультиплексованих протоколах (HTTP/2 та HTTP/3) десятки запитів передаються через єдине TCP або QUIC з'єднання. Щоб роутери й проксі-сервери могли переупорядковувати фрейми в сокетному буфері на канальному рівні, застосовується специфікація RFC 9218 (Extensible Prioritization Scheme for HTTP):

Заголовок запиту RFC 9218:

```http
Priority: u=0, i
```

Де:
- **`u` (urgency)**: Число від `0` (найвищий пріоритет, відповідає P0/P1) до `7` (найнижчий пріоритет, P4).
- **`i` (incremental)**: Прапорець `1` або відсутній. Вказує, чи може відповідь оброблятися частковими блоками (потоково), чи потребує монолітної доставки.

У HTTP/3 пріоритет може динамічно змінюватися під час вже відкритого стриму за допомогою спеціального кадру `PRIORITY_UPDATE` на службовому стримі:

```text
HTTP/3 Control Stream:
[PRIORITY_UPDATE Frame] Stream_ID=124, Urgency=1, Incremental=0
```

Це дозволяє клієнту миттєво підвищити пріоритет стриму (наприклад, коли користувач відкрив екран камери) або понизити його до P4, якщо вікно згорнули.

### 2.3. gRPC Binary Metadata

У gRPC викликах атрибути передаються в метаданих заголовків кадру `HEADERS`:

```text
x-request-priority: 0
x-deadline-ms: 1500
x-allow-degradation: 1
x-tenant-id: home-7782
```

- **`x-request-priority`**: Цілочисельне значення від `0` (P0) до `4` (P4).
- **`x-deadline-ms`**: Абсолютний граничний час виконання у мілісекундах. Якщо затримка в черзі перевищує цей час, виклик скасовується автоматично (`DEADLINE_EXCEEDED`).

## 3. Відповіді при відкиданні: 429 Too Many Requests vs 503 Service Unavailable

Однією з найчастіших архітектурних помилок є плутанина між кодами `429` та `503`. Ця плутанина руйнує логіку повторних спроб (retry policies) на боці клієнтів.

```
+-----------------------------------------------------------------------------------+
|               РІЗНИЦЯ МІЖ RATE LIMITING (429) ТА LOAD SHEDDING (503)               |
+--------------------------+----------------------------------+---------------------+
| Параметр                 | HTTP 429 Too Many Requests       | HTTP 503 Service    |
|                          |                                  | Unavailable         |
+--------------------------+----------------------------------+---------------------+
| Причина збою             | Клієнт перевищив свою персональну| Сервер перевантаже- |
|                          | квоту (Rate Limit / Quota)       | ний (System Load)   |
| Хто винен?               | Проблема на боці КЛІЄНТА (4xx)    | Проблема на боці    |
|                          |                                  | СЕРВЕРА (5xx)       |
| Чи зміниться ситуація при| НІ. Зміна сервера не допоможе.   | ТАК. Інша нода або  |
| повторі на іншу ноду?    | Квота вичерпана всюди.           | чекання допоможе.   |
| Правильна реакція        | Зупинити запити до скидання      | Зачекати Retry-After|
| клієнта                  | вікна квоти.                     | + Exponential Jitter|
+--------------------------+----------------------------------+---------------------+
```

При відкиданні трафіку через Load Shedding сервіс **зобов'язаний повертати 503 Service Unavailable**, а не 429.

## 4. HTTP Headers та розширена специфікація RFC 9457

При відкиданні запиту P2, P3 або P4 сервер повертає відповідь HTTP `503 Service Unavailable` із заголовком `Retry-After` та розширеним JSON-конвертом Problem Details.

### 4.1. HTTP Response Headers

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/problem+json
Retry-After: 45
X-Brownout-Level: L2-Medium
X-Shedding-Reason: queue_delay_threshold_exceeded
X-System-Pressure-Score: 0.89
```

- **`Retry-After`** (integer / seconds): Кількість секунд, яку клієнт повинен зачекати перед повторною спробою. **Клієнтський код зобов'язаний додавати випадковий джитер (±20%) до цього значення, щоб запобігти шторму синхронних повторів (thundering herd).**
- **`X-Brownout-Level`**: Поточний рівень деградації вузла (`L0-Normal`, `L1-Low`, `L2-Medium`, `L3-High`, `L4-Emergency`).
- **`X-System-Pressure-Score`** (float, 0.0 .. 1.0): Векторний показник загального системного тиску на ноді.

### 4.2. Тіло відповіді (RFC 9457 Problem Details Body)

Стандарт RFC 9457 (замінив RFC 7807) визначає машиночитний формат для передачі деталей помилки. Для Load Shedding використовується розширена схема:

```json
{
  "type": "https://api.digitalhomes.io/errors/load-shedding",
  "title": "Service Unavailable Due to Adaptive Load Shedding",
  "status": 503,
  "detail": "Запит категорії P3 (Аналітика) відкинуто через перевищення порогової затримки черги (240 мс > 50 мс). Спробуйте пізніше.",
  "instance": "/devices/dev-9821/telemetry/history",
  "code": "load_shedding_p3_drop",
  "priority_class": "P3-Low",
  "current_brownout_level": "L2-Medium",
  "retry_after_seconds": 45,
  "system_metrics": {
    "queue_delay_ms": 240,
    "active_concurrency": 88,
    "cpu_utilization_pct": 91.4
  }
}
```

Поле `code` є закам'янілим машинним контрактом (`load_shedding_p3_drop`), за яким клієнтський `switch` обирає ветку обробки. Поле `detail` призначене для людських очей та системного журналу.

## 5. Прокидання контексту (Context Propagation) та W3C Baggage

У мікросервісній архітектурі один вхідний запит P0 від користувача спричиняє каскад з десятків внутрішніх RPC-викликів між сервісами. Якщо пріоритет загубиться на першому ж внутрішньому мікросервісі, наступні сервіси почнуть сприймати виклик як дефолтний P2/P3 і можуть відкинути його.

Для прокидання пріоритету крізь розподілений ланцюжок викликів використовуються стандарти **W3C Distributed Tracing & W3C Baggage**.

### W3C Baggage Header Specification

```http
baggage: priority=p0,tenant=home-enterprise,origin=gateway-01,auth_scope=critical_write
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

### Правила трансформації контексту всередині мережі:

1. **Іммутабельність знизу вгору**: Внутрішній сервіс не має права підвищувати пріоритет запиту (наприклад, з P3 до P0), якщо він не має спеціальних привілеїв.
2. **Деградація дочірніх викликів**: Батьківський запит P0 може породжувати дочірні асинхронні виклики нижчого пріоритету (наприклад, запис аудиту в логер — P3). При цьому сам батьківський синхронний потік зберігає статус P0.
3. **gRPC Context Mapping**: У Go (`context.Context`), Java (`ThreadLocal` / `Reactor Context`) та C++ (`grpc::ClientContext`) заголовок `baggage` автоматично парситься middleware й додається до локального контексту потоку.

## 6. Декларативна конфігурація у сервісному шлюзі (Envoy Proxy Config)

На практиці відкидання навантаження та пріоритезація реалізуються декларативно на рівні Edge Gateway. Нижче наведено приклад виробничої конфігурації фільтра `envoy.filters.http.adaptive_concurrency` у проксі Envoy:

```yaml
name: envoy.filters.http.adaptive_concurrency
typed_config:
  "@type": type.googleapis.com/envoy.extensions.filters.http.adaptive_concurrency.v3.AdaptiveConcurrency
  gradient_controller_config:
    sample_aggregate_percentile:
      value: 95.0
    concurrency_limit_params:
      max_concurrency_limit: 1000
      concurrency_update_interval: 0.1s
    min_rtt_calc_params:
      jitter:
        value: 15.0
      interval: 30s
      request_count: 50
  enabled:
    default_value: true
    runtime_key: adaptive_concurrency.enabled
```

Ця конфігурація змушує Envoy динамічно розраховувати мінімальний час відгуку (`RTT_min`) та поточний `RTT`, автоматично відкидаючи запити низьких пріоритетів при зростанні градієнта затримки.
