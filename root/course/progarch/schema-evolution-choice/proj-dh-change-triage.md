# ⚙️ Тріаж змін даних DH: класифікатор рішення

Крок назвав стратегію за двома властивостями даних — і на цьому інтуїція скінчилась. А інтуїція не переживає п'ятниці, коли о 18:40 прилітає квиток «треба поміняти форму `X`», і вирішувати мусить той, хто вже втомився. Тому зведімо ті дві осі в **інструмент**: функцію, що бере описану зміну й повертає стратегію. Не пораду — рішення: механічне, однакове в кожних руках, придатне поставити в код-рев'ю поруч зі змінами схеми.

І найважливіше, що вміє цей інструмент, — не обрати стратегію, а іноді **відмовити**. Бо найдорожчі помилки еволюції даних — не «взяли не ту стратегію», а «взагалі поставили питання про стратегію там, де зміну треба було спершу переформулювати». Класифікатор ловить саме це першим рухом.

Одразу вмовмося, чого тут не буде: переказу двох осей (вони в кроці) і теорії [expand–contract](book:programming/expand-contract) (вона в книзі). Буде рівно машина — `chooseEvolutionStrategy(change)` — і ті скелети SQL та декодерів, у які кожен її вердикт розгортається, плюс три пастки, на яких гарний на вигляд план тихо бреше, що вже безпечно.

## Ідея: класифікуй за фактами про дані, не за смаком

Уся хитрість інструмента в одному: він **ніколи не питає, що тобі хочеться зробити**. Він питає чотири факти про самі дані — і на факти двоє інженерів дають ту саму відповідь, а на «як краще» сваряться до ночі. Факти такі:

1. **Чи ця зміна перепризначає сенс живого ключа?** — ґвардія. Спрацьовує **першою** й може одразу закрити питання вердиктом «заборонено».
2. **Чи це похідні дані?** — якщо так, стратегія випаровується: не мігруй нічого, [перебудуй із джерела](root:progarch/pipeline-consistency).
3. **Який різновид зміни?** — додаєш нове, прибираєш стару форму чи переливаєш існуюче в нову.
4. **Чи переписуване збережене, і чи контролюєш обидва боки?** — дві властивості, що для reshape-змін розводять на різні дороги.

Порядок питань — не косметика. Ґвардія стоїть перша, бо перепризначення сенсу — не поганий вибір стратегії, а зміна, яку не можна проводити **жодною** стратегією: її треба переробити на іншу зміну, перш ніж класифікатор узагалі має право працювати. Похідність — друга, бо вона знімає з дошки половину випадків, не питаючи більше нічого. А переписуваність і контроль над боками — останні, бо вони лише **звужують дорогу**, коли перші три пропустили зміну далі.

## Описати зміну — чотири факти й один різновид

Ось дескриптор зміни й типи, якими класифікатор говорить. Зверни увагу на `kind`: `reshape` (нова форма поруч зі старою) і `redefine` (той **самий** ключ, новий сенс) — розведені навмисне, бо саме на їхній різниці стоїть уся безпека. Мова тут — виразна логіка над записом, тож TypeScript і Python поруч:

:::tabs
```ts
type ChangeKind =
  | "add"       // нове поле/значення; старі дані лишаються валідні
  | "reshape"   // існуюче поле переливають у НОВУ форму (новий ключ/стовпець)
  | "remove"    // прибирають стару форму, якою вже не пишуть
  | "redefine"; // тому САМОМУ ключу дають НОВИЙ сенс ← отрута

interface DataChange {
  what: string;               // людський опис
  derived: boolean;           // дані — чиста функція джерела правди?
  rewritable: boolean;        // збережене можна переписати на місці? (false = незмінна історія)
  controlsBothSides: boolean; // читача й писаря деплоїш РАЗОМ?
  kind: ChangeKind;
}

type Strategy =
  | "REBUILD"           // похідне: перерахуй із джерела, без вікна
  | "ADD"               // адитивне: додай поруч, backfill сенсу нема
  | "MIGRATE_IN_PLACE"  // переписуване джерело: expand → backfill → contract
  | "SCHEMA_ON_READ"    // незмінна історія: версіонуй записи, рости декодер
  | "RETIRE"            // прибрати стару форму, коли читачів уже нема
  | "FORBIDDEN";        // перепризначення сенсу живого ключа — не роби

type Window = "none" | "short" | "long" | "grows-with-decoder" | "may-never-close";
type Compat = "n/a" | "backward" | "forward" | "backward+forward";

interface Decision {
  strategy: Strategy;
  window: Window;
  backfill: boolean;   // чи треба чіпати старі рядки
  compat: Compat;
  note: string;
}
```

## Класифікатор

Тепер сама машина. Кожна гілка — це рядок таблиці, який крок уже вивів словами; тут він стає предикатом, який не можна «відчути інакше»:

:::tabs
```ts
function chooseEvolutionStrategy(c: DataChange): Decision {
  // 0. ҐВАРДІЯ — перш ніж думати про стратегію. Сенс живого ключа не перепризначають.
  if (c.kind === "redefine")
    return { strategy: "FORBIDDEN", window: "none", backfill: false, compat: "n/a",
      note: "новий сенс = новий ключ/версія; старий ключ лишається старим сенсом" };

  // 1. Похідні дані обходять усю матрицю: не мігруй — перерахуй.
  if (c.derived)
    return { strategy: "REBUILD", window: "none", backfill: false, compat: "n/a",
      note: "зміни функцію зведення, перебудуй вікно із сирого" };

  // 2. Адитивне: старі дані лишаються валідні, backfill сенсу нема.
  if (c.kind === "add")
    return { strategy: "ADD",
      window: c.controlsBothSides ? "short" : "long", backfill: false,
      compat: c.controlsBothSides ? "n/a" : "forward",
      note: "старий читач мусить ІГНОРУВАТИ незнайоме, а не падати на ньому" };

  // 3. Прибирання — це фаза contract чиєїсь давнішої expand.
  if (c.kind === "remove")
    return { strategy: "RETIRE",
      window: c.rewritable ? "short" : "may-never-close", backfill: false,
      compat: "backward",
      note: "гейт: ні писаря, ні ДОСЯЖНОГО збереженого запису на старій формі" };

  // 4. reshape справжнього джерела правди — вирішує вісь переписуваності.
  if (!c.rewritable)
    return { strategy: "SCHEMA_ON_READ",
      window: c.controlsBothSides ? "grows-with-decoder" : "may-never-close",
      backfill: false,
      compat: c.controlsBothSides ? "backward" : "backward+forward",
      note: "тегай кожен запис версією, зводь на читанні; історію не переписуй" };

  return { strategy: "MIGRATE_IN_PLACE",
    window: c.controlsBothSides ? "short" : "long", backfill: true,
    compat: c.controlsBothSides ? "backward" : "backward+forward",
    note: "expand → backfill пакетами → contract" };
}
```
```py
def choose_evolution_strategy(c: DataChange) -> Decision:
    # 0. ҐВАРДІЯ: сенс живого ключа не перепризначають — перш за все.
    if c.kind == "redefine":
        return Decision("FORBIDDEN", "none", False, "n/a",
            "новий сенс = новий ключ/версія; старий ключ лишається старим сенсом")

    # 1. Похідні обходять матрицю: не мігруй — перерахуй.
    if c.derived:
        return Decision("REBUILD", "none", False, "n/a",
            "зміни функцію зведення, перебудуй вікно із сирого")

    # 2. Адитивне: старі дані лишаються валідні.
    if c.kind == "add":
        return Decision("ADD",
            "short" if c.controls_both_sides else "long", False,
            "n/a" if c.controls_both_sides else "forward",
            "старий читач мусить ІГНОРУВАТИ незнайоме, а не падати на ньому")

    # 3. Прибирання — фаза contract давнішої expand.
    if c.kind == "remove":
        return Decision("RETIRE",
            "short" if c.rewritable else "may-never-close", False, "backward",
            "гейт: ні писаря, ні ДОСЯЖНОГО збереженого запису на старій формі")

    # 4. reshape джерела правди — вирішує переписуваність.
    if not c.rewritable:
        return Decision("SCHEMA_ON_READ",
            "grows-with-decoder" if c.controls_both_sides else "may-never-close",
            False, "backward" if c.controls_both_sides else "backward+forward",
            "тегай запис версією, зводь на читанні; історію не переписуй")

    return Decision("MIGRATE_IN_PLACE",
        "short" if c.controls_both_sides else "long", True,
        "backward" if c.controls_both_sides else "backward+forward",
        "expand → backfill пакетами → contract")
```
:::

Дві осі кроку сховані у двох останніх поверненнях: `rewritable` розводить `MIGRATE_IN_PLACE` і `SCHEMA_ON_READ`, а `controlsBothSides` **не змінює стратегію**, лише ширину вікна — `short` проти `long`, `backward` проти `backward+forward`. Це і є пуант кроку в коді: контроль над боками диктує не *що* робити, а *як довго* тримати вікно відкритим.

![Класифікатор як низхідна лійка запитань з лівим хребтом і правими листками-стратегіями. Зверху вхід «зміна даних DH». Перше питання-ґвардія «перепризначає сенс живого ключа?»: так веде праворуч до червоного листка FORBIDDEN «заведи нову версію — не чіпай ключ (напр. сенс wh)». Ні веде вниз до «похідні дані?»: так — зелений листок REBUILD «перебудуй із джерела, без вікна (місячне число)». Ні вниз до «додаєш нове поле чи значення?»: так — синій листок ADD «додай поруч, старе валідне (новий тип; nullable-поле)». Ні вниз до «прибираєш стару форму?»: так — листок RETIRE «прибери, коли читачів нема (schema:1)». Ні вниз до останнього питання «переписуване, не незмінна історія?»: так — зелений листок MIGRATE IN-PLACE «expand → backfill → contract (zone→tariff_zone)»; ні — синій листок SCHEMA-ON-READ «версіонуй записи, декодуй на читанні (незмінна історія)». Унизу наскрізний банер: контролюєш обидва боки? визначає лише ширину вікна — так коротке, ні довге плюс forward-сумісність](img/triage-dispatch.svg)
*Той самий вибір, що в кроці, але як виконуваний маршрут. Зміна падає крізь п'ять питань і зупиняється на першому «так»; ґвардія вгорі перехоплює отруйні зміни ще до розмови про стратегію, а нижній банер нагадує, що контроль над боками задає лише ширину вікна, не саму стратегію.*

## Таблиця рішень: п'ять змін DH крізь інструмент

Проженімо крізь машину п'ять реальних квитків Digital Homes і місячне число на додачу. Ось що повертає класифікатор:

| Зміна DH | похідне? | переписуване? | обидва боки? | різновид | → Стратегія | Вікно | Головний ризик |
|---|:--:|:--:|:--:|---|---|---|---|
| Додати тип `ev_charger` | ні | так | **ні** (прошивка/апки читають тип) | add | **ADD** | довге | старий читач падає на невідомому типі |
| `zone` → `tariff_zone` | ні | так | так (один сервіс) | reshape | **MIGRATE IN-PLACE** | коротке | backfill-лок на мільйонах рядків |
| Змінити сенс `wh` | — | — | — | **redefine** | **FORBIDDEN** | — | тихе перепризначення ключа |
| Прибрати `schema:1` | ні | **ні** (історія) | ні | remove | **RETIRE** | може не закритися | contract, що не настає |
| Додати nullable `firmware_channel` | ні | так | ні | add | **ADD** (безкоштовно) | — | `NOT NULL`/дефолт → рерайт + лок + тиха брехня |
| Місячне число `318` | **так** | — | — | (reshape логіки) | **REBUILD** | немає | — |

Таблиця — це вивід; тепер розгорнімо кожен вердикт у скелет, у який він насправді перетворюється, і назвімо ризик поіменно.

### Додати тип пристрою — ADD, і вся гра у forward-сумісності

```ts
chooseEvolutionStrategy({
  what: "додати тип пристрою ev_charger",
  derived: false, rewritable: true, controlsBothSides: false, kind: "add",
});
// → ADD, window "long", backfill false, compat "forward"
```

Backfill нема: жоден старий рядок не міняється, у довіднику просто з'являється нове дозволене значення `type`. Уся вага — в одному слові вердикту: `compat: "forward"`. Старий читач — мобільний застосунок, [прошивка панелі, яку ти не оновиш дистанційно](root:progarch/what-makes-irreversible), — зустріне тип, про який його ніхто не питав. І тут вирішує, як він написаний:

```ts
// ❌ читач, що вибухне на новому значенні:
function render(d: Device) {
  switch (d.type) {
    case "lamp":   return renderLamp(d);
    case "lock":   return renderLock(d);
    case "sensor": return renderSensor(d);
    default: throw new Error(`невідомий тип ${d.type}`);   // ← ev_charger = виняток
  }
}

// ✓ forward-сумісний: незнайоме ДЕГРАДУЄ, а не падає
function render(d: Device) {
  switch (d.type) {
    case "lamp":   return renderLamp(d);
    case "lock":   return renderLock(d);
    case "sensor": return renderSensor(d);
    default: return renderGeneric(d);   // показуємо як загальний пристрій
  }
}
```

Ось прикра асиметрія цієї «найлегшої» зміни: полагодити треба **читача, якого ти вже не контролюєш**. Панель зі `switch`, що кидає на `default`, зламається на `ev_charger` — а виправити її ретроактивно нема як, бо вона в полі на старій прошивці. Тобто forward-сумісність — це не міграція, яку запускаєш; це властивість, яку **купуєш наперед**, ще коли пишеш першу версію читача. Правило «ігноруй незнайоме» — те саме, що [зрілі формати вшивають у резолюцію](book:programming/schema-registry): в Avro поле, якого нема в схемі читача, писар віддає, а читач мовчки відкидає; тут — на рівні значення enum. Додавання дешеве рівно тоді, коли всі читачі вже вміють знизати плечима на невідоме.

### Розкласти zone → tariff_zone — MIGRATE IN-PLACE, і backfill без лока

```ts
chooseEvolutionStrategy({
  what: "розкласти текстове zone у структурований tariff_zone",
  derived: false, rewritable: true, controlsBothSides: true, kind: "reshape",
});
// → MIGRATE_IN_PLACE, window "short", backfill true, compat "backward"
```

Три фази цієї міграції — `ALTER ADD`, backfill, `DROP` — крок уже показав у SQL. Не переказуватиму; візьму те, що там сховалось за одним рядком «`UPDATE ... WHERE id BETWEEN :lo AND :hi` — ганяємо по діапазонах ключа». Саме в цьому рядку живе різниця між тихою міграцією і нічним інцидентом, тож розкриймо його в робочий backfill:

```py
BATCH = 5_000

def backfill_tariff_zone(conn) -> None:
    last_id = 0
    while True:
        cur = conn.execute("""
            WITH batch AS (
                SELECT id FROM home
                WHERE id > %s AND tariff_zone IS NULL
                ORDER BY id
                LIMIT %s
            )
            UPDATE home h
            SET tariff_zone = zone_to_code(h.zone)
            FROM batch
            WHERE h.id = batch.id
            RETURNING h.id
        """, (last_id, BATCH))
        ids = [r[0] for r in cur.fetchall()]
        conn.commit()             # ← лок відпускається ЩОБАТЧУ, не в кінці всього
        if not ids:               # NULL-рядків більше нема — усе
            break
        last_id = max(ids)        # keyset-курсор: наступний батч продовжує з місця
        time.sleep(0.05)          # крапля між батчами: вакуум і реплікація дихають
```

Чому не один `UPDATE home SET tariff_zone = zone_to_code(zone)` на всю таблицю? Порахуймо на реальному масштабі:

**Умова: 4 000 000 рядків реєстру, `zone_to_code` ≈ 25 мкс на рядок.**

```text
один UPDATE:    4 000 000 · 25 мкс = ~100 с в ОДНОМУ транзакті
                → рядкові локи на ВСІ зачеплені рядки тримаються всі 100 с;
                  будь-який живий запис у ці рядки чекає до 100 с;
                  один гігантський WAL-запис, довгий транзакт блокує автовакуум,
                  сплеск лага реплік; впав на рядку 3.9 млн → відкат усього, наново.

батчами 5 000:  800 батчів · ~125 мс = ті самі ~100 с корисної роботи,
                але лок живе ≤125 мс за раз → живий запис чекає щонайбільше 125 мс;
                WAL дрібними порціями, вакуум устигає, репліка не відстає;
                впав на 600-му батчі → 599 уже закомічені, доганяєш решту.
```

Однакова робота, протилежна поведінка. Гігантський `UPDATE` не бере лок на всю таблицю (це `ROW EXCLUSIVE`, паралельний DML він не блокує) — він гірший тонше: тримає **рядкові** локи на кожному зачепленому рядку до самого коміту, роздуває один транзакт до розмірів, за яких прокидаються всі фонові підсистеми бази, і не має де впасти безпечно. Батч із комітом наприкінці кожної ітерації робить лок короткочасним, транзакт дрібним, а падіння — відновним із місця. Keyset-курсор (`id > last_id`) не дає щоразу перечитувати таблицю з початку; частковий індекс `WHERE tariff_zone IS NULL` зробив би пошук наступного батча миттєвим.

> 🔧 **Навіщо це.** «Backfill» звучить як фонова дрібниця, а насправді це найчастіший спосіб покласти живу базу посеред безневинної міграції. Правило одне й тверде: **ніколи не оновлюй мільйони рядків одним транзактом.** Ріж на батчі за ключем, комітай кожен, лишай краплю пауз — і та сама робота з інциденту стає нудним фоном, який можна спинити й продовжити будь-коли.

Коли backfill дійшов кінця, застосунок переводить читання зі `zone` на `tariff_zone` — реліз за релізом, [ховаючи перемикання за прапорцем](book:programming/feature-flags), бо обидва боки тут — один твій деплой, тож вікно коротке. Аж тоді — фаза contract: `DROP COLUMN zone`.

### Змінити сенс `wh` — FORBIDDEN, і чому ґвардія стоїть перша

```ts
chooseEvolutionStrategy({
  what: "wh віднині означає дельту за інтервал замість накопиченого лічильника",
  derived: false, rewritable: false, controlsBothSides: false, kind: "redefine",
});
// → FORBIDDEN, window "none": заведи нову версію, старий wh лишається старим wh
```

Класифікатор навіть не дивиться на решту фактів — ґвардія зачинила двері на `kind: "redefine"`. Це не впертість, це арифметика катастрофи. Уяви, що команда прошивки таки зробила по-своєму: лишила ключ `wh`, але почала слати в нього дельту за інтервал, не піднявши версію. Старий читач ніде про це не дізнається — він досі впевнений, що `wh` накопичувальний, і [далі інтегрує його як лічильник](root:progarch/dh-schema-flow). Дельту, підсунуту замість лічильника, він підсумує в нісенітницю, яка виглядає **правдоподібно** — жодного винятку, жодного червоного, просто повільно гниюче число, аж поки не прийде рахунок. Це і є та сама рана `w` проти `wh`, тільки навмисна.

Правильний хід — не «стратегія», а переформулювання зміни: новий сенс дістає **новий ключ або нову версію**, а старий лишається собою назавжди. І тоді, вже як `redefine`, переписаний на нову версію, він падає в `SCHEMA_ON_READ` — версійний декодер, у якому кожна форма істинна для своїх рядків:

:::tabs
```ts
// Кожен запис несе СВОЮ версію форми; сенс wh читається ЗА ВЕРСІЄЮ, не вгадується.
interface RawRecord { schema: number; [k: string]: unknown; }
interface Reading { wattHours: number; }   // канонічна форма читача

function decode(r: RawRecord): Reading {
  switch (r.schema) {
    case 1: return decodeV1(r);   // wh відсутнє: лише миттєве w — інтегруємо самі
    case 2: return decodeV2(r);   // wh = НАКОПИЧУВАЛЬНИЙ лічильник (Вт·год від старту)
    case 3: return decodeV3(r);   // wh = ДЕЛЬТА за інтервал ← НОВИЙ сенс, НОВА версія
    default: throw new Error(`нема декодера для schema:${r.schema}`);
  }
}
```
```py
_DECODERS = {1: decode_v1, 2: decode_v2, 3: decode_v3}
#   schema:1 — лише миттєве w, інтегруємо самі
#   schema:2 — wh накопичувальний лічильник
#   schema:3 — wh дельта за інтервал ← новий сенс, нова версія

def decode(r: dict) -> Reading:
    try:
        return _DECODERS[r["schema"]](r)     # сенс wh — за версією запису
    except KeyError:
        raise ValueError(f'нема декодера для schema:{r["schema"]}')
```
:::

`decodeV2` і `decodeV3` живуть у коді **одночасно й вічно**, кожен правильний для своїх рядків; жоден рядок не переписано. Саме так чинять зрілі формати, і не випадково: [Protocol Buffers розрізняють поля за номером](book:programming/schema-registry) — тому перейменувати поле безпечно, а повторно вжити вивільнений номер заборонено, бо тоді wire-формат не відрізнить, яким визначенням запис кодували. Ключ (тег, версія) — стабільний, сенс до нього прибитий намертво. Ґвардія в класифікаторі — це те саме правило, піднесене на рівень квитка: перш ніж питати «як провести цю зміну», спитай «а це часом не тихе перепризначення ключа» — і якщо так, зміни не проводь, а переформулюй.

### Прибрати легасі `schema:1` — RETIRE, і два годинники

```ts
chooseEvolutionStrategy({
  what: "викинути гілку декодера для schema:1",
  derived: false, rewritable: false, controlsBothSides: false, kind: "remove",
});
// → RETIRE, window "may-never-close", compat "backward"
```

`RETIRE` — це фаза contract чиєїсь давньої expand: прибрати `case 1` з декодера вище. Вердикт застерігає `window: "may-never-close"`, і за цим — найтонша пастка кроку. Наївний гейт питає: «чи хтось ще **шле** `schema:1`?» Дивиться на живий трафік, бачить нуль уже кілька місяців — і зеленіє. Але `schema:1` — це [незмінна історія](root:progarch/state-inventory): мільйони заморожених рядків, які ніхто не переписує. Живий трафік давно нуль, а **збережені рядки досі лежать** у межах retention — і будь-який [перерахунок історії чи відбудова родоводу](book:programming/data-lineage) занурюється в них саме зараз. Прибереш декодер за живим трафіком — і найближчий reprocess-джоб прочитає трирічний рядок `schema:1`, впаде на `default: throw` (або, гірше, тихо декодує не тим).

Тому гейт мусить слухати **інший годинник** — не «останній живий запис», а «найстаріший **збережений** досяжний рядок»:

```ts
interface RetireGate {
  version: number;
  liveWrites: number;                  // писарі, що ще шлють цю версію (за вікно)
  oldestStoredAgeDays: number | null;  // вік найстарішого збереженого рядка; null = жодного
  retentionDays: number;               // доки взагалі можемо перечитувати історію
}

function canRetireDecoder(g: RetireGate): { green: boolean; why: string } {
  if (g.liveWrites > 0)
    return { green: false, why: `${g.liveWrites} писарів ще шлють schema:${g.version}` };
  if (g.oldestStoredAgeDays !== null && g.oldestStoredAgeDays <= g.retentionDays)
    return { green: false,
      why: `найстаріший schema:${g.version}-рядок ще в retention — перерахунок його прочитає` };
  return { green: true, why: `ні писаря, ні досяжного рядка на schema:${g.version}` };
}
```

Це рідня [харнесу воріт для поля API](root:progarch/api-evolution-dh/proj-dh-field-migration.md), де кнопку `contract` теж чіпляли на метрику, а не на календар, — але з різницею, що й робить незмінну історію окремим звіром. Там ворота слухали живі читання й одного дня чесно зеленіли. Тут другий годинник — вік найстарішого рядка — може лишатися червоним **роками**, доки retention тримає давню історію, і це не поломка гейта, а правда про дані: фаза contract для незмінного журналу настає пізно, а за нескінченного retention — не настає взагалі.

![Два часові годинники один над одним, час тече ліворуч у минуле, праворуч — «зараз» (вертикальна лінія через обидва). Верхній «годинник живого трафіку schema:1»: стовпчики трафіку спадають зліва направо до нуля, вертикальна пунктирна позначка «останній живий schema:1-запит» кілька місяців тому, далі рівна зона нуля; виносний напис праворуч червоним «наївний гейт дивиться сюди → зелено, прибирай декодер». Нижній «годинник збереження історії (retention)»: довга світла смуга покриває минуле аж до зараз із написом «усе це ще можна перечитати», ліворуч у смузі позначені «заморожені schema:1-рядки (роками)» і маркер «найстаріший збережений schema:1-рядок — ще в межах retention»; від «зараз» униз-ліворуч у старі рядки веде стрілка «перерахунок / lineage читає стару історію»; виносний напис зеленим «правильний гейт дивиться сюди → червоно, декодер ще потрібен»](img/retire-two-clocks.svg)
*Два годинники розходяться. Живий трафік `schema:1` занулився місяці тому — і наївний гейт уже зеленіє. Та заморожені рядки `schema:1` досі в межах retention, і перерахунок читає їх зараз, тож правильний гейт, що слухає вік найстарішого збереженого рядка, лишається червоним — можливо, роками. Contract настає за другим годинником, не за першим.*

### Додати nullable-поле — ADD безкоштовно, доки не збрешеш

```ts
chooseEvolutionStrategy({
  what: "додати необов'язкове firmware_channel до реєстру",
  derived: false, rewritable: true, controlsBothSides: false, kind: "add",
});
// → ADD, backfill false: старі рядки лишаються як є
```

Найдешевша зміна з усіх — і рівно тому найпідступніша, бо спокушає зробити «трохи більше» й непомітно перетворити безкоштовне на дороге. Безкоштовний варіант — nullable без дефолта:

```sql
-- ✓ безкоштовно: nullable, без дефолта → лише метадані, жодного рерайту рядків
ALTER TABLE home ADD COLUMN firmware_channel text;   -- старі рядки = NULL = «невідомо»

-- ❌ тиха брехня: NOT NULL з дефолтом насаджує старим рядкам сенс, якого вони не мали
ALTER TABLE home ADD COLUMN firmware_channel text NOT NULL DEFAULT 'stable';
--   PostgreSQL 11+ зробить це теж швидко (сталий дефолт — лише метадані),
--   АЛЕ кожен старий рядок відтепер СТВЕРДЖУЄ, що він 'stable' — хоч канал невідомий;
--   NULL «ми не знали» тихо став 'stable' — і ти вже не відрізниш знаних від незнаних.

-- ❌❌ і зовсім дорого — зробити поле обов'язковим ПІЗНІШЕ:
ALTER TABLE home ALTER COLUMN firmware_channel SET NOT NULL;
--   повний скан таблиці під ACCESS EXCLUSIVE, щоб довести, що NULL-ів нема → лок на весь скан
```

Дві пастки в одному невинному полі. Перша — **семантична**: `NOT NULL DEFAULT 'stable'` не просто заповнює порожнечу, він **переписує сенс** старих рядків, стверджуючи про них те, чого ти не знаєш. `NULL` чесно казав «невідомо»; дефолт замінив його правдоподібною брехнею, і тепер «канал невідомий» не відрізнити від «канал справді stable». Це та сама хвороба, що й перепризначення `wh`, тільки м'якша: ти ретроактивно приписав минулому значення, якого в ньому не було. Друга — **механічна**: зробити поле обов'язковим згодом коштує повного скану під найважчим локом (а нестала за замовчуванням, як-от `now()`, перепише всю таблицю ще на `ADD`). Тому дисципліна проста: нові поля — nullable і без дефолта; «невідомо» лишай як `NULL`, а дефолт [обирай на читанні](book:programming/schema-on-read-write), не запікай у сховище. Не клади в старі рядки припущення, якого потім не забереш.

## Складність і пастки

Кожна з п'яти змін уже принесла свій ризик; звівши їх, бачимо, що всі небезпеки — три, і всі вони про одне: **опубліковані дані не перемикають, і кожна пастка — це спосіб про це забути.**

**Backfill-локи: одним транзактом на мільйон рядків.** Найгрубіша й найчастіша. Гарний план expand-contract провалюється не в фазі `expand` і не в `contract`, а посеред `migrate`, коли інженер пише `UPDATE ... SET ...` без `WHERE`-діапазону й пускає на всю таблицю. Рядкові локи на всіх зачеплених рядках, роздутий транзакт, збуджений автовакуум, лаг реплік, і жодного безпечного місця впасти. Ліки — вище в коді: keyset-батчі по кілька тисяч, коміт після кожного, крапля пауз між ними, частковий індекс по недозаповнених рядках. Правило: робота та сама, лок — короткий.

**Тихе перепризначення ключа: сенс, підмінений під тим самим іменем.** Найтихіша й найдорожча, бо не кидає винятку — вона **отруює числа**. Живий ключ `wh`, якому дали новий сенс без нової версії; `NULL`, який дефолт перетворив на `'stable'`; будь-яке «майже те саме слово, а рахується протилежно». Старий читач декодує за старим правилом, новий писар кодує за новим — і між ними тече правдоподібна нісенітниця, поки хтось не звірить із рахунком. Стіна проти неї одна: **ідентифікуй сенс стабільним ключем — номером, тегом, версією, — і ніколи не віддавай уживаний ключ новому змісту.** Це те, чого ґвардія класифікатора не пускає далі порога, і те, на чому стоять [номери полів protobuf та reader/writer-резолюція Avro](book:programming/schema-registry). Керованих читачів тут ще підстрахують [контрактні тести](book:programming/contract-testing) — їхній CI червоніє на зачеплений сенс; некерованих у полі не рятує ніщо, крім того, що ти ключ не чіпав.

**Contract, що не настає: гейт, який слухає не той годинник.** Найпідступніша для незмінної історії. Прибрати стару форму кортить за живим трафіком: шле хтось `schema:1`? Ні кілька місяців? Викидай. Але заморожені рядки `schema:1` лежать у retention, і перерахунок історії читає їх зараз — а декодера вже нема. Гейт мусить слухати **вік найстарішого збереженого досяжного рядка**, а не останній живий запис; для незмінного журналу в межах retention він законно лишається червоним, часом роками. І це не привід переписати історію, щоб «нарешті закрити вікно», — це нагадування, що для даних, які ти не контролюєш до кінця, фаза contract буває просто **не про тебе**. Найдешевша поведінка тут — прийняти, що декодер `schema:1` — не борг, а сталий податок на відтворюваність.

## Що дає інструмент

Ми взяли шість реальних змін Digital Homes і прогнали крізь одну функцію — і жодного разу не питали «як тобі більше подобається». Питали факти: похідне? переписуване? перетинає межу, яку не оновиш разом? чи це часом не той самий ключ із новим сенсом? На факти відповідь одна в кожних руках, тож і стратегія одна — не смак чергового, а властивість самих даних, виведена на екран.

Найцінніше, що зробив класифікатор, — двічі відмовився щось «мігрувати». `wh` він не пустив далі ґвардії: перепризначення сенсу живого ключа — не стратегія, а зміна, яку треба переробити на нову версію, перш ніж вона взагалі має право на розгляд. А `schema:1` він позначив вердиктом, що чесно каже «вікно може не закритися ніколи», — і врятував від найтихішої поломки, спокуси прибрати декодер за живим трафіком, поки історія ще жива на диску. Обидва рази інструмент не обирав дорогу — він казав, що дороги нема, і саме це вберігало найдорожче.

Тому справжній вихід тріажу — не колонка «стратегія», а звичка описувати зміну її фактами, доки в описі сам собою не проступить хід. Опиши чесно — що це за дані, чи можна їх переписати, кого зламає їхня нова форма, — і половина «як провести міграцію» відповідає на себе, а друга половина виявляється питанням, якого не варто ставити. Класифікатор лише вимовляє вголос те, що вже вписане у форму твоїх даних.
