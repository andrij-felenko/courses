# ⚙️ Читання через межу: наївне зшивання, пастка N+1 і проєкція

Стаття лишила на столі один рядок і одну обіцянку. Рядок — це `deviceCard(id)`: беремо пристрій із `control`, останній вимір із `telemetry`, склеюємо в читачі, жодного `JOIN` через стіну. Обіцянка — що на списку в тисячу пристроїв це наївне склеювання вибухне, і тоді читання доведеться підняти на іншу висоту. Виконаймо обіцянку до дна: пройдемо три сходинки — наївне зшивання, батч на фасаді, окрему read-модель — і на кожній чесно назвемо, що вона коштує й що виграємо.

Наскрізна думка одна. Ми свідомо відмовилися від `JOIN`, який зшив би дві схеми навіки. За цю відмову платимо на боці читача — і весь цей проєкт про те, **як платити дешево**: спершу зайвим запитом, тоді — одним запитом на всіх, а коли й того забагато — свіжістю замість запитів. Ціна росте разом із навантаженням, але жодна її сходинка не повертає нас до зшитих схем.

## Задача

Випишемо сцену точно, бо в дрібницях і ховається пастка. Дашборд малює **список** пристроїв дому, і поряд із кожним — його **останній вимір**: лампа й «увімкнено», термостат і «21.5 °C», замок і «зачинено о 14:03». Пристрій — річ керування: живе в схемі `control`, має ім'я, кімнату, стан. Вимір — річ телеметрії: живе в схемі `telemetry`, ряд чисел у часі. Одна база, але дві схеми, і між ними — стіна: ніякого `JOIN`, ніякого зовнішнього ключа. Дані зшиває **читач**, двома фасадами.

Для одного пристрою це тривіально — той самий `deviceCard(id)` зі статті. Але дашборд показує не один, а всі: тридцять у звичайному домі, тисячу — на екрані оператора, що глядить цілий квартал. І саме на переході від «одного» до «всіх» наївний код тихо перетворюється на генератор сотень запитів у базу. Побачмо, як.

## Крок перший: наївне зшивання — і пастка N+1

Найпряміше узагальнення «одного» на «всіх» — це цикл. Беремо список пристроїв із `control`, і для кожного питаємо телеметрію про останній вимір:

:::tabs
```ts
// НАЇВНО: список пристроїв, а тоді — по виклику телеметрії на КОЖЕН
function deviceCards(homeId: HomeId): DeviceCard[] {
  const devices = control.listDevices(homeId);      // 1 запит: увесь список
  return devices.map(d => ({
    ...d,
    lastReading: telemetry.lastReading(d.id),        // +1 запит НА КОЖНОГО
  }));
}
```
```py
# НАЇВНО: список пристроїв, а тоді — по виклику телеметрії на КОЖЕН
def device_cards(home_id: HomeId) -> list[DeviceCard]:
    devices = control.list_devices(home_id)          # 1 запит: увесь список
    return [
        DeviceCard(**d.__dict__,
                   last_reading=telemetry.last_reading(d.id))  # +1 запит на кожного
        for d in devices
    ]
```
:::

Код читається чисто, і в цьому вся підступність. `telemetry.lastReading(d.id)` виглядає як безкоштовний виклик функції — а в моноліті це він і є, наносекунди. Але **за** цим викликом ховається справжній похід у базу: `SELECT … WHERE device_id = ? ORDER BY at DESC LIMIT 1`. Один пристрій — один похід. Тисяча пристроїв у циклі — тисяча окремих походів, кожен зі своїм плануванням, своїм індексним пошуком, своїм походом туди-назад до сховища.

Порахуймо чесно. Один запит дістає список; далі — по запиту на вимір кожного:

```
запитів = 1 (список)  +  N (по виміру на кожен пристрій)  =  N + 1
N = 1000  →  1001 похід у базу на один показ дашборда
```

Це і є **проблема N+1** (англ. *N+1 queries* — «N плюс один запит»): один запит, щоб дістати список із N елементів, і ще N запитів, щоб дозбирати по шматочку до кожного. Підступність її в тому, що на десятьох пристроях у розробника вона **невидима** — одинадцять запитів пролітають за мілісекунди, тест зелений, демо гладке. Вона прокидається лише в проді, на реальному домі з тисячею пристроїв, коли дашборд раптом вантажиться секунду замість мілісекунди, а база стогне під шквалом однакових дрібних запитів.

![Дві панелі. Ліворуч «наївно»: дашборд, від нього одна зелена стрілка «1 запит» до control.listDevices і червона стрілка «× N» до стосу коробок telemetry.lastReading — унизу червоний підсумок «1 + N = 1001 запит». Праворуч «батч»: той самий дашборд, зелена «1 запит» до control і зелена «1 запит на всіх» до telemetry.lastReadings — унизу зелений підсумок «1 + 1 = 2 запити за будь-якого N»](img/nplus1-vs-batch.svg)

*Та сама композиція на списку з тисячі пристроїв. Наївний цикл питає телеметрію по одному — 1 + N = 1001 похід у базу; батч-виклик `lastReadings(ids)` бере всі виміри одним запитом — 2 походи за будь-якого N. Стіни це не торкається: винен цикл, не кордон.*

І ось де легко зробити хибний висновок: «отже, винна стіна — якби не заборона `JOIN`, одним запитом дістали б усе». Ні. Стіна не вимагає **тисячі** запитів — вона вимагає лише не лізти в чужу схему. Тисячу запитів породив не кордон, а **наївна форма звертання**: ми питаємо по одному там, де можна спитати про всіх разом. Виправлення не чіпає стіни зовсім.

## Крок другий: один запит на всіх — батч на фасаді

Ідея прямо випливає з діагнозу. Якщо боляче саме від того, що питаємо телеметрію **по одному**, — спитаймо про **весь список одразу**. Для цього фасад телеметрії дістає ще одні двері: не «останній вимір цього пристрою», а «останні виміри ось цих пристроїв», списком:

:::tabs
```ts
export interface Telemetry {
  lastReading(id: DeviceId): Reading | null;
  lastReadings(ids: DeviceId[]): Map<DeviceId, Reading>;  // ← батч: усі одним запитом
}
```
```py
class Telemetry(Protocol):
    def last_reading(self, id: DeviceId) -> Reading | None: ...
    def last_readings(self, ids: list[DeviceId]) -> dict[DeviceId, Reading]: ...  # батч
```
:::

Тепер читач бере список пристроїв, одним махом — усі їхні виміри, і склеює вже в пам'яті:

:::tabs
```ts
function deviceCards(homeId: HomeId): DeviceCard[] {
  const devices = control.listDevices(homeId);               // 1 запит
  const last = telemetry.lastReadings(devices.map(d => d.id)); // 1 запит на ВСІХ
  return devices.map(d => ({ ...d, lastReading: last.get(d.id) ?? null }));
}
```
```py
def device_cards(home_id: HomeId) -> list[DeviceCard]:
    devices = control.list_devices(home_id)                  # 1 запит
    last = telemetry.last_readings([d.id for d in devices])  # 1 запит на ВСІХ
    return [DeviceCard(**d.__dict__, last_reading=last.get(d.id))
            for d in devices]
```
:::

Скільки тепер запитів? Один на список, один на всі виміри — і байдуже, тридцять пристроїв чи тисяча:

```
наївно:  1  +  N   =  N + 1     (N = 1000  →  1001)
батч:    1  +  1   =  2          (будь-яке N)
```

Тепер найважливіше — що робить `lastReadings` **усередині** й чому це не порушує стіну. За фасадом телеметрії лежить **один** запит, і весь він — у **власній** схемі телеметрії. Найсвіжіший вимір на кожен пристрій зі списку Postgres дає ідіоматично:

```sql
-- усередині telemetry: тут агрегація по СВОЇХ таблицях — дозволена й правильна
SELECT DISTINCT ON (device_id) device_id, value, unit, at
FROM   telemetry.reading
WHERE  device_id = ANY($1)        -- увесь список ідентифікаторів разом
ORDER  BY device_id, at DESC;     -- на кожен device_id лишиться найсвіжіший рядок
```

Ось тонкість, яку легко проґавити: **заборонений `JOIN` і цей запит — різні речі**. Заборонений був `JOIN` **через стіну** — між `control.device` і `telemetry.reading`, що зшив би дві чужі схеми. А тут телеметрія групує **свою власну** таблицю `reading` по `device_id` — жодного дотику до `control`. Логіка «найсвіжіший на кожен пристрій» — це внутрішня справа телеметрії, схована за фасадом; `control` про неї не знає й знати не повинен. Стіна ціла: список ідентифікаторів увійшов через двері, мапа вимірів вийшла назад, а сира таблиця вимірів так і лишилася невидимою.

> 🔧 **Навіщо це.** Батч — той рідкісний випадок, коли дисципліна меж не коштує майже нічого. Ми прибрали пастку N+1, не проламавши жодної стіни: телеметрія як була господарем своєї схеми, так і лишилась, тільки тепер її фасад уміє відповідати на питання «про багатьох» так само чемно, як «про одного». Правило на все життя: щойно фасад віддає щось у циклі — на нього напрошується батч-двійник, що робить те саме одним запитом. Стіна тут ні до чого; винен цикл.

## Чому два запити дешевші за один JOIN

Хтось справедливо спитає: два запити замість одного `JOIN` — це ж усе одно **зайвий** запит. Один похід у базу проти двох. Навіщо платити, коли `JOIN` дав би все за раз?

Бо ці дві ціни — **різного роду**. Зайвий запит — крихітна, разова, локальна ціна: ще один похід туди-назад, десятки-сотні мікросекунд, які на тлі мережі до браузера й рендеру дашборда просто губляться. А `JOIN` через стіну — ціна **постійна й глобальна**: з дня, коли запит дашборда з'єднав `control.device` і `telemetry.reading`, ці дві схеми **зрослися**. Перейменуй стовпець у `reading` — зламається запит, що живе в геть іншому світі. Захоче телеметрія іншу форму зберігання, партиціювання по даті, окреме масштабування — не зможе, бо за неї тримається чужий `JOIN`. І [винести телеметрію колись у власний сервіс](root:progarch/context-as-service-candidate) стане неможливо без розплутування — а це те, заради чого ми взагалі проводили межі.

Ось і вся арифметика: зайвий запит платиться **раз на показ** і вимірюється мікросекундами; зшиті схеми платяться **вічно** й вимірюються втраченою свободою рухати кожну зі схем окремо. Два дешевих запити купують те, чого не купить жоден `JOIN`, — дві схеми, які й далі можна розвивати нарізно. Курс уже назвав цей важіль: дешеву межу проводимо завжди, дорогу фізичну — лише коли змусять; тут та сама логіка на рівні даних.

## Крок третій: підняти читання до read-моделі

Батч розв'язує N+1, і для переважної більшості дашбордів на цьому історія й закінчується — два запити на показ витримають дуже багато. Але уяви, що дашборд став гарячим: його смикають десятки разів на секунду, композиція зрослася — не два фасади, а чотири-п'ять (пристрій, вимір, статус автоматизацій, тариф білінгу), а обчислення «найсвіжіший на кожен» саме по собі недешеве на мільярді рядків вимірів. Тоді навіть два акуратні запити, помножені на частоту показів, починають муляти. Настав час для наступної сходинки — окремої **read-моделі**.

Ідея радикальніша, ніж здається. Досі читач **щоразу** заново збирав картку з живих джерел. А що, як тримати вже зібраний, готовий до показу зріз — **денормалізовану** таблицю, де кожен рядок і є готова картка дашборда, з ім'ям, кімнатою й останнім виміром в одному місці?

```sql
-- read-модель: денормалізований зріз ПІД дашборд, одна річ на пристрій
CREATE TABLE dashboard.device_card (
  device_id   uuid PRIMARY KEY,
  home_id     uuid NOT NULL,
  name        text NOT NULL,       -- прийшло з control
  room        text,                -- прийшло з control
  last_value  double precision,    -- прийшло з telemetry
  last_unit   text,
  last_at     timestamptz          -- коли зроблено вимір
);
```

Хто ж наповнює цю таблицю й тримає її свіжою? Не читач — читач лише читає. Наповнює її **проєктор** (англ. *projector* — той, що проєктує події в зріз) — ще один [підписник тієї самої шини подій](book:programming/event-driven-architecture), яку ми вже збудували. Він слухає ті самі факти `DeviceEvent`, що й телеметрія, і на кожному оновлює свій рядок:

:::tabs
```ts
// ЄДИНИЙ писар device_card; живиться тією самою шиною, що й усі
class DeviceCardProjector {
  onEvent(e: DeviceEvent): void {
    // 1) голова картки (ім'я, кімната) — раз, коли пристрій уперше побачено:
    //    рядок мусить існувати ДО того, як писати в нього вимір
    if (!db.hasCard(e.deviceId)) {
      const d = control.getDevice(e.deviceId);   // ОДИН виклик на пристрій за життя
      db.insertHead(e.deviceId, e.homeId, d.name, d.room);
    }
    // 2) вимір — просто з події, у вже наявний рядок:
    db.updateReading(e.deviceId, e.value, e.unit, e.at);
  }
}
```
```py
# ЄДИНИЙ писар device_card; живиться тією самою шиною, що й усі
class DeviceCardProjector:
    def on_event(self, e: DeviceEvent) -> None:
        # 1) голова картки — раз, коли пристрій уперше побачено:
        #    рядок мусить існувати ДО того, як писати в нього вимір
        if not db.has_card(e.device_id):
            d = control.get_device(e.device_id)   # ОДИН виклик на пристрій за життя
            db.insert_head(e.device_id, e.home_id, d.name, d.room)
        # 2) вимір — просто з події, у вже наявний рядок:
        db.update_reading(e.device_id, e.value, e.unit, e.at)
```
:::

І тоді дашборд читає **один тривіальний запит** — усе вже склеєно, зшивати нічого:

```sql
-- жодної композиції на читанні: усе вже лежить готовим рядком
SELECT device_id, name, room, last_value, last_unit, last_at
FROM   dashboard.device_card
WHERE  home_id = $1;
```

Придивися, що тут сталося по суті. Склеювання пристрою з виміром **нікуди не зникло** — воно **переїхало в часі**. Замість зшивати картку на **кожному читанні** (а читань — десятки на секунду), ми зшиваємо її **на кожній події** (а події — лише коли пристрій справді змінив стан). Роботи стало менше рівно тому, що змін менше, ніж поглядів на екран. Дорогий виклик `control.getDevice` за ім'ям і кімнатою трапляється **раз на пристрій за все життя**, а не раз на показ, — та сама робота склеювання, тільки заплачена заздалегідь і один раз. Читання ж звелося до вибірки готового рядка за первинним ключем — швидше вже нікуди.

Це і є [CQRS](book:programming/cqrs) у найменшому масштабі: бік **запису** (`control`, `telemetry`) лишається нормалізованим і авторитетним, а бік **читання** отримує власну, [похідну й денормалізовану модель](book:programming/materialized-views), заточену рівно під один екран. Дві моделі однієї реальності, кожна у формі, зручній для свого діла.

![Угорі рамка «бік запису — нормалізований, джерело правди» з коробками control (device, room) і telemetry (reading); від рамки стрілка «потік фактів DeviceEvent» вниз до горизонтальної шини подій. Від шини пунктирна стрілка до коробки «проєктор device_card — єдиний писар», поруч підпис «лаг = кінцева узгодженість: у пам'яті ≈ 0, у брокері мс…с» і нотатки «вимір — прямо з події», «ім'я, кімната — control.getDevice() раз на пристрій». Від проєктора стрілка вниз до коробки «read-модель device_card — денормалізований зріз, 1 рядок на пристрій», а від неї зелена стрілка «1 тривіальний SELECT» до дашборда. Унизу підпис «склеювання переїхало з часу читання на час події»](img/read-projection.svg)

*Читання, підняте до проєкції. Ті самі факти `DeviceEvent` зі спільної шини живлять проєктор — єдиного писаря денормалізованого зрізу `device_card`; дашборд читає готовий рядок одним запитом. Склеювання пристрою з виміром переїхало з часу читання на час події, а ціна — лаг зрізу (кінцева узгодженість), коли шина стане асинхронною.*

## Ціна проєкції: свіжість

Дарма нічого не буває, і проєкція бере плату новою монетою — **свіжістю**. `device_card` — не джерело правди, а лише його **відлуння**. Між миттю, коли пристрій змінив стан, і миттю, коли проєктор обробив подію й оновив рядок, зріз **відстає** від правди.

Сьогодні, поки [шина синхронна й у пам'яті](book:programming/event-driven-architecture), це відставання практично нульове: проєктор відпрацьовує в тій самій транзакції, що й запис, — рядок оновлюється буквально до того, як зміна стане видимою. Але згадаймо, навіщо ми з самого початку вбирали шину в дротовий контракт: щоб у день, коли телеметрія чи читання [поїдуть в окремий сервіс](root:progarch/when-to-split), шина стала справжнім брокером **без переписування**. Того дня проєктор почне обробляти події **асинхронно**, вже після коміту, можливо — на іншій машині. І між подією та оновленням зрізу з'явиться справжній лаг: мілісекунди, іноді секунди. Дашборд покаже вимір, якому кілька секунд.

Це — [кінцева узгодженість](book:programming/consistency-models) (англ. *eventual consistency*): зріз не завжди дорівнює правді **цю мить**, але, якщо події припинити, він її **дожене**. Для дашборда це майже завжди прийнятно: температура, застаріла на дві секунди, для людського ока не відрізняється від миттєвої. Головне — не вдавати, що лагу немає, а **назвати його контрактом**: [«цей екран кінцево узгоджений, свіжість — така-то»](book:programming/read-model-lag). Названий лаг — інженерне рішення; неназваний — прихована брехня інтерфейсу, на яку хтось колись обіпреться.

А спиратися на проєкцію **не можна там, де рішення вимагає правди цю мить**. Питання «чи зачинений замок **зараз**, щоб пустити людину» не йде в зріз — воно йде прямо до `control`, до джерела правди, бо помилка тут коштує безпеки, а не вигляду. Проєкція — для **показу**, не для інваріантів. Це чіткий вододіл: кінцево узгоджене відлуння годиться, коли ним **дивляться**; коли ним **вирішують** щось незворотне — питай першоджерело.

## Яку сходинку коли

Три сходинки — не мода, а відповідь на навантаження, і брати треба найнижчу, що витримує:

- **Один запис або рідкий показ** → наївне зшивання двома фасадами. Найпростіше, найсвіжіше, нуль нових деталей. Для картки одного пристрою — саме воно.
- **Список, N росте** → батч-виклик на фасаді. Так само свіжо й просто, лиш фасад навчився відповідати про багатьох. **Дефолт дашборда в моноліті** — тут зупиняється переважна більшість.
- **Читання гаряче, композиція широка або дорога** → окрема read-модель. Платиш свіжістю (кінцева узгодженість) і новою деталлю, яку треба живити й уміти перебудувати.

> 🔧 **Навіщо це.** Головна помилка — стрибнути на третю сходинку першою. Проєкція виглядає солідно, «по-дорослому», тож рука тягнеться будувати її одразу. Але це найважчий інструмент: нова таблиця, новий підписник, контракт свіжості, історія перебудови (зіпсувався проєктор чи змінилась форма зрізу — треба переграти події наново). Усе це — постійна вага. Батч-виклик прибирає N+1 без жодної з цих турбот. Тому сходинки й беруть по черзі: піднімайся на проєкцію лише тоді, коли батч **справді** перестав витягати, а не тому, що так солідніше.

## Пастки

**N+1, що переліз усередину проєктора.** Прибрали N+1 на читанні — і легко впустити його назад у проєктор, якщо той на пачці подій піде питати джерела по одному. Проєктор має тримати ту саму дисципліну: обробляєш багато подій разом — звертайся до фасадів батчем, не в циклі.

**Перебудова зрізу.** Змінив форму `device_card` чи знайшов баг у проєкторі — старі рядки треба **перебудувати**. Це можливо, лише якщо є з чого переграти: журнал подій або змога наново вивести зріз із боку запису. Проєкція без історії, з якої її відновити, — пастка: одного дня доведеться будувати правду, а нема з чого.

**Два писарі.** У `device_card` пише **лише** проєктор. Щойно в таблицю почне писати ще хтось «напряму» — з'являться два джерела істини для одного рядка, і вони розійдуться. Read-модель має рівно одного господаря пера.

**Переставлені події.** Коли шина стане асинхронною, події можуть прийти не в тому порядку — новіший вимір раніше за старіший. Наївний `updateReading` затре свіже старим. Тому оновлюй **лише якщо подія новіша**: `... WHERE $at > device_card.last_at`. Часова мітка події — сторож проти відкату.

**Свіжість, що протекла в рішення.** Найтихіша пастка: узяти кінцево узгоджений зріз і поставити на ньому рішення, що вимагає правди цю мить, — списати гроші, пустити в дім, зняти блокування. Проєкція для цього не годиться **за побудовою**. Дивишся — бери зріз; вирішуєш незворотне — питай джерело.

Три сходинки, одна нитка: ми ні на мить не повернулися до `JOIN`, що зшив би схеми. Наївне зшивання, батч, проєкція — усе це способи платити за цілу стіну **на боці читача**, від найдешевшого до найсвіжішого. Стіна лишилась цілою, а телеметрія — [кандидатом виїхати у свій сервіс](root:progarch/context-as-service-candidate) того дня, коли це справді знадобиться, і жоден рядок дашборда їй не завадить.
