# Межі всередині моноліта DH

<preknowlist>
- [Модульний моноліт](root:sf-apps/modular-monolith) — модуль = вузький фасад + приховані нутрощі; логічна вісь (де різати) й фізична (по процесах) ортогональні; модулі не лазять у чужу базу.
- [Подієва архітектура всередині застосунку](root:sf-apps/event-driven-architecture) — продюсер публікує факт, а споживачі підписані, не знаючи одне про одного; зчеплення через подію, а не прямий виклик.
- [Фітнес-функція](root:sf-apps/fitness-functions) — виконуваний тест архітектури, що валить збірку на порушенні правила (як-от заборонений імпорт).
- [Мапа контекстів Digital Homes](root:progarch/dh-contexts-map) — дев'ять світів DH і напрямлені стрілки між ними; це та мапа, яку тут кладемо в код.
- [Де провести межі контекстів DH](root:progarch/dh-context-boundaries-choice) — де саме пройшли стіни і чому, та ADR-014: «спершу — модулі в одному процесі, не сервіси».
</preknowlist>

У нас на руках дві готові речі. Є [мапа контекстів](root:progarch/dh-contexts-map) — дев'ять світів дому й стрілки між ними. І є [ухвалений вибір, де саме проходять стіни](root:progarch/dh-context-boundaries-choice), записаний як ADR-014, з коротким і рішучим рядком: «спершу — усе як модулі в одному процесі, не сервіси». А щойно ми [взяли модульний моноліт за дефолт](root:progarch/modular-monolith-first) — форму, у якій межі чесні, а застосунок один.

Але мапа на дошці й рядок в ADR — це ще не структура в коді. «Модулі в одному процесі» звучить ясно, поки не відкриєш репозиторій і не спитаєш буквально: **де лежать теки, хто кого сміє імпортувати, де живуть чиї таблиці — і що фізично не дасть стіні тихо розчинитися за півроку?** Цей крок не малює нову мапу. Він робить стару мапу **реальною в коді**: перетворює намальовані стрілки на правила, які тримає компілятор, а не пильність рев'юера. Дев'ять світів дому стануть дев'ятьма огородженими модулями в одному застосунку — з усіма стінами й без жодного грама мережі.

## Одна коробка, дев'ять кімнат

Почнімо з найбуквальнішого. Digital Homes збирається й котиться як **один застосунок**: один `main`, один процес, одна база. Усередині цієї коробки — не каша, а дев'ять кімнат, по одній на кожен світ мапи: `control` (керування), `twin`, `automations`, `telemetry`, `video`, `notifications`, `identity`, `billing` — плюс крихітне [спільне ядро](root:progarch/dh-contexts-map) `ids` з типами `DeviceId`, `HomeId`, які всі свідомо ділять. (Хаб живе фізично в домі; у хмарі йому відповідає тонкий модуль-адаптер, що [ловить радіо-мову за перекладачем](root:sf-apps/anti-corruption-layer) і віддає всередину чистий факт.)

Кожна кімната — це [модуль у точному сенсі](root:sf-apps/modular-monolith): дві сторони. Назовні — **вузький фасад**, кілька публічних викликів, якими з ним говорять. Усередину — **приватні нутрощі**: класи, SQL, таблиці, які поза модулем не видно й чіпати ззовні заборонено. Мова сама допомагає прибити цю межу — покажу на телеметрії:

:::tabs
```ts
// telemetry/index.ts — ЄДИНІ двері модуля телеметрії
export type { Reading } from "./contract";
export interface Telemetry {            // фасад: усе, що бачать сусіди
  record(e: DeviceEvent): void;         // прийняти вимір із події
  lastReading(id: DeviceId): Reading | null;
}
export { makeTelemetry } from "./service";
// ReadingStore, схема, SQL-запити — НЕ реекспортовано: для сусідів їх не існує
```
```py
# telemetry/__init__.py — фасад через __all__
from ._service import Telemetry, make_telemetry
__all__ = ["Telemetry", "make_telemetry"]      # назовні видно лише це
# _ReadingStore і сирий SQL живуть у _service.py під підкресленням — чужим зась
```
:::

Сусідній модуль може написати рівно `telemetry.lastReading(id)`. Дотягтися до `ReadingStore` чи до таблиці вимірів — не може: їх **не видно за іменем**. Оце й є стіна — не коментар «будь ласка, не чіпайте», а фізична недоступність. Дев'ять таких кімнат в одному домі: перегородки справжні, але, щоб перейти з однієї в іншу, ти просто **викликаєш функцію**, а не стукаєш по мережі.

![Велика зовнішня рамка «Digital Homes — один застосунок, один процес, один деплой», а всередині дев'ять модулів сіткою: ядро (керування, твін, автоматизації) зеленим, служби (телеметрія, відео, сповіщення) синім, загальне (ідентичність, білінг) і спільне ядро ids. Кожен модуль має зелену смугу-фасад уздовж верхнього краю](img/monolith-rooms.svg)

*Одне розгортання, а всередині — дев'ять огороджених модулів. Зелена смуга кожного — його фасад, єдині двері; тіло — приватні класи й таблиці, невидимі сусідам. Стіни ті самі, що були б між сервісами, тільки перетин стіни тут — виклик функції.*

> 🔧 **Навіщо це.** Пригадаймо дешевий і дорогий важіль: логічну межу проводимо завжди, фізичну — лише коли змусять. Тут ми отримуємо **всі** межі мапи (кожна кімната відв'язана, з власним контрактом) і **жодного** мережевого податку: одна збірка, один слід у логах, один профайлер на всю систему, а транзакція бази накриває всю операцію атомарно. Це не «стартова версія, яку перепишемо», — для DH це може бути кінцева, здорова форма на роки.

## Стрілки мапи стали правилами імпорту

Тепер — головне, заради чого крок і затіяно. На мапі кожна стрілка мала напрямок і вид зв'язку. У коді ця сама стрілка означає **дозволене ребро імпорту**: хто кого сміє знати. І весь цей граф мусить лишатися **ациклічним** — жодного «А кличе Б, а Б назад кличе А», інакше дві кімнати злипаються в одну.

Стіну перетинають рівно двома способами, і кожен точно відповідає тому, що казала мапа.

**Перший — прямий виклик фасаду**, коли мапа малювала синхронну залежність «замовник-постачальник». Автоматизаціям щомиті потрібен свіжий стан дому — вони кличуть фасад твіна:

:::tabs
```ts
// automations залежить від фасаду twin — і тільки від нього
class Automations {
  constructor(private twin: Twin) {}          // ← інжектовано, не створено тут
  evaluate(rule: Rule): Command | null {
    const state = this.twin.currentState(rule.homeId);   // виклик у пам'яті: наносекунди
    return rule.matches(state) ? rule.action : null;
  }
}
```
```py
class Automations:
    def __init__(self, twin: Twin):           # ← інжектовано, не створено тут
        self._twin = twin
    def evaluate(self, rule: Rule) -> Command | None:
        state = self._twin.current_state(rule.home_id)    # виклик у пам'яті: наносекунди
        return rule.action if rule.matches(state) else None
```
:::

**Другий — підписка на подію через внутрішньопроцесну шину**, коли мапа малювала «опубліковану мову» з віялом споживачів. Коли пристрій змінив стан, `control` не дзвонить кожному зацікавленому окремо — він **публікує факт** `DeviceEvent` у шину (англ. *bus* — спільна лінія, до якої під'єднані всі учасники), а по той бік сидять підписники: телеметрія кладе вимір у ряд, автоматизації зважують правила, сповіщення вирішують, чи будити власника, білінг лічить «пристрій додано/знято». І ось тонкість, яку легко проґавити: ці підписники **взагалі не імпортують `control`**. Вони знають лише дві речі — контракт події `DeviceEvent` (зі спільного ядра) і саму шину. Продюсер не знає підписників, підписники не знають продюсера — [зчеплення тримає подія, а не пряме ребро](root:sf-apps/event-driven-architecture). Саме так широке віяло не перетворюється на вузол залежностей.

![Граф залежностей DH: угорі горизонтальна шина подій із підписом «DeviceEvent (опублікована мова)»; ліворуч керування публікує у шину; від шини пунктиром униз — телеметрія, сповіщення, білінг (підписані, не імпортують control); автоматизації і підписані на шину, і суцільною стрілкою кличуть фасад твіна; знизу смуга «Ідентичність — authorize()», до якої всі звертаються синхронно вниз, без циклів](img/import-rules.svg)

*Та сама мапа, тільки як граф імпортів. Суцільна стрілка — прямий виклик фасаду там, де зв'язок синхронний; пунктир — підписка на подію через шину там, де мапа мала опубліковану мову. Напрямок усюди вниз за течією — граф ациклічний, і жоден підписник не знає імені продюсера.*

## Одна база, дев'ять комор

Стіни в коді — половина справи. Друга половина — там, де межі гинуть найчастіше й найтихіше: **у базі даних**. DH [давно обрав одне реляційне сховище](root:progarch/dh-v3-storage), і спокуса очевидна: раз база одна, то й таблиці спільні, тягни `SELECT` звідки треба. Саме це, а не спільний процес, і перетворює моноліт на невидимий клубок.

Тому дисципліна тверда: одна база — але **не спільна купа таблиць**, а схема (гр. *schḗma* — обрис, устрій) на кожен модуль. `control` володіє схемою `control` (таблиці `device`, `room`), `telemetry` — схемою `telemetry` (`reading`), `billing` — своєю. І залізне правило поверх цього: **жодного зовнішнього ключа й жодного `JOIN` через стіну**. Сусід дістає чужі дані лише через фасад, ніколи — прямим запитом до чужої таблиці.

Перевіряється це правило на тому самому незручному місці, яке [чесно назвав ADR-014](root:progarch/dh-context-boundaries-choice): дашборд «покажи пристрій і його останній вимір». Дані лежать у двох світах — сам пристрій у `control`, а вимір у `telemetry`, — і рука сама тягнеться до `JOIN`. Але цей `JOIN` намертво зшив би дві схеми: відтепер жодну з них не посунеш, не зачепивши другу. Тому робимо інакше — **зшиваємо на боці читача**, двома викликами фасадів:

:::tabs
```ts
// НЕ РОБИМО так — JOIN через стіну зшиває схеми навіки:
//   SELECT d.*, r.value FROM control.device d
//   JOIN telemetry.reading r ON r.device_id = d.id     ← заборонено

// РОБИМО так — читання-композиція через два фасади:
function deviceCard(id: DeviceId): DeviceCard {
  const device = control.getDevice(id);        // свій фасад control
  const last = telemetry.lastReading(id);       // свій фасад telemetry
  return { ...device, lastReading: last };      // склеюємо вже в читачі
}
```
```py
# НЕ РОБИМО так — JOIN через стіну зшиває схеми навіки (заборонено):
#   SELECT d.*, r.value FROM control.device d
#   JOIN telemetry.reading r ON r.device_id = d.id

# РОБИМО так — читання-композиція через два фасади:
def device_card(id: DeviceId) -> DeviceCard:
    device = control.get_device(id)             # свій фасад control
    last = telemetry.last_reading(id)           # свій фасад telemetry
    return DeviceCard(**device.__dict__, last_reading=last)   # склеюємо в читачі
```
:::

![Угорі читач-дашборд «пристрій + останній вимір»; від нього дві зелені стрілки виклику фасадів униз — до схеми control (device, room) і схеми telemetry (reading). Обидві схеми та схема billing (plan) лежать в одній рамці «Одна база даних». Між control.device і telemetry.reading — червона пунктирна лінія JOIN, перекреслена, з підписом «JOIN / FK через стіну — заборонено»](img/one-db-cellars.svg)

*Одне сховище, але кожен модуль — господар своєї схеми. Прямий `JOIN` між чужими таблицями перекреслено: він зшив би комори намертво. Замість нього читач кличе два фасади й склеює результат сам — стіна лишається цілою й на рівні даних.*

Ця дрібниця має ціну — за неї платимо зайвим запитом і трохи більшим кодом читача; на списку з тисячі пристроїв наївне зшивання ще й перетвориться на [пастку N+1 запитів](root:progarch/dh-monolith-boundaries/proj-dh-read-composition.md), і тоді дашборд варто підвищити до окремої read-моделі. Повний розбір цього перетину — від простого зшивання до проєкції — винесено в [окремий проєкт про читання через межу](root:progarch/dh-monolith-boundaries/proj-dh-read-composition.md).

> 🔧 **Навіщо це.** Межа в коді, яку зраджує база, — фікція. Два модулі, що сидять на спільних таблицях, зчеплені крізь схему, хоч би які чисті були їхні фасади зверху. І навпаки: доки кожен модуль володіє **своєю** схемою, він лишається справжнім [кандидатом стати сервісом](root:progarch/context-as-service-candidate) — його можна колись вийняти разом із його коморою, нічого не розплутуючи. Володіння даними — це те, що робить майбутній розріз узагалі можливим.

## Внутрішньопроцесна шина — контракт, як для мережі

Придивімося ще раз до шини, бо саме в ній ховається чи не найтонше рішення всього кроку. Сьогодні DH — один процес, тож шина — це просто **синхронна диспетчеризація в пам'яті**: `publish` означає «виклич по черзі всіх підписників, тут-таки, у тій самій транзакції». Наносекунди; або всі відпрацювали, або кинувся виняток; жодного «а раптом мережа впала посеред». Публікація події виглядає так:

:::tabs
```ts
// всередині транзакції control, коли команду виконано:
function applyCommand(cmd: Command, tx: Tx): void {
  const device = repo.apply(cmd, tx);              // приватна нутрощі control
  bus.publish({                                    // опублікована мова — лише факт
    kind: "state", deviceId: device.id, homeId: device.homeId,
    at: now(), value: device.state,
  });
}
```
```py
# всередині транзакції control, коли команду виконано:
def apply_command(cmd: Command, tx: Tx) -> None:
    device = repo.apply(cmd, tx)                    # приватна нутрощі control
    bus.publish(DeviceEvent(                        # опублікована мова — лише факт
        kind="state", device_id=device.id, home_id=device.home_id,
        at=now(), value=device.state,
    ))
```
:::

Тепер спитаймо чесно: навіщо чепурити цю подію під нейтральний, «мережевий» контракт, коли по той бік — звичайний виклик функції? Клали б у шину живий об'єкт `Device` цілком — швидше й простіше. Відповідь у слові **кандидат**. Той день, коли телеметрії знадобиться своє масштабування й вона [поїде в окремий сервіс](root:progarch/when-to-split), настане (чи ні) пізніше; але якщо на шині вже їздить нейтральний `DeviceEvent` — лише факт, без вендорських кластерів і без живих агрегатів, — то в цей день шина стає справжнім брокером, а обробник телеметрії **не змінюється жодним рядком**: він завжди говорив дротовою мовою. Контракт, спроєктований «як для мережі», і є той шов, уздовж якого розріз буде дешевим. Поклали б туди живий `Device` — і в день переїзду довелося б переписувати обидва боки.

Одну чесну тонкість тут лишу пунктиром: синхронна диспетчеризація в тій самій транзакції означає, що підписник, який кинув виняток, може відкотити транзакцію продюсера. Тож межу треба свідомо обрати — розсилати після коміту (для некритичного віяла) чи через outbox (коли подія мусить пережити збій). Це вже [матеріал модуля про повідомлення](root:progarch/when-to-split); тут досить знати, що місце для цього рішення **є** і що воно назване.

## Один корінь, що збирає дім

Хто ж вставляє фасад твіна в автоматизації, а шину — в `control`? Модулі цього не роблять самі — інакше вони б знову зналися напряму. Усе зшиває **одне** місце — корінь склеювання (composition root). Ми його вже бачили: [у v1 це був крихітний `run(sensor, heater, cfg)`](root:progarch/dh-v1-modules), де абстрактні порти вперше зустрічали конкретні драйвери. Той диригент просто виріс до розмірів усього застосунку:

:::tabs
```ts
function buildApp(db: Db, bus: Bus) {
  const identity = makeIdentity(db.schema("identity"));
  const twin = makeTwin(db.schema("twin"));
  const telemetry = makeTelemetry(db.schema("telemetry"));
  const control = makeControl(db.schema("control"), bus);   // публікує у шину
  const automations = makeAutomations(twin);                 // кличе фасад твіна
  bus.subscribe(telemetry.record);                           // підписки — теж тут
  bus.subscribe(automations.onEvent);
  return { identity, twin, telemetry, control, automations };
}
```
```py
def build_app(db: Db, bus: Bus):
    identity = make_identity(db.schema("identity"))
    twin = make_twin(db.schema("twin"))
    telemetry = make_telemetry(db.schema("telemetry"))
    control = make_control(db.schema("control"), bus)     # публікує у шину
    automations = make_automations(twin)                  # кличе фасад твіна
    bus.subscribe(telemetry.record)                       # підписки — теж тут
    bus.subscribe(automations.on_event)
    return App(identity, twin, telemetry, control, automations)
```
:::

Уся топологія системи зібрана в одному видимому місці: кожен модуль дістає рівно те, від чого залежить (свою схему, потрібний фасад, шину), і ані краплі більше. Хто кого знає — читається згори вниз за десять секунд. Повний каркас — розкладку всіх дев'яти модулів, робочу шину подій і цей корінь — зібрано в [проєкті-каркасі моноліта DH](root:progarch/dh-monolith-boundaries/proj-dh-monolith-skeleton.md).

## Стіну, яку стереже машина

Лишилася та сама небезпека, що вбиває будь-яку мапу: **вона бреше з часом**. В одному процесі кожен модуль — на відстані одного імпорту. Хтось під дедлайн імпортує приватний `control._DeviceRepo` «на разок», рев'ю це пропускає — і за півроку стіна існує лише на діаграмі, а насправді знову клубок. Добра воля межу не втримає.

Тому в живому DH граф залежностей роблять **машинно вимушеним** — [фітнес-функцією](root:sf-apps/fitness-functions), тестом архітектури, який валить збірку на порушенні. Він тримає перелік дозволених ребер як єдине джерело правди й падає, щойно ребро з'явилося поза списком:

:::tabs
```ts
// arch.test.ts — виконуваний тест графа (dependency-cruiser / eslint-boundaries)
const ALLOWED: Record<string, Set<string>> = {
  automations: new Set(["twin", "ids", "identity"]),
  billing:     new Set(["ids", "identity"]),        // НЕ control!
  telemetry:   new Set(["ids", "identity"]),        // control знають лише через подію
};
test("жоден модуль не проліз повз двері", () => {
  for (const [mod, deps] of actualImports()) {
    for (const d of deps) expect(ALLOWED[mod]).toContain(d);
  }
});
```
```py
# arch_test.py — виконуваний тест графа (import-linter-стиль)
ALLOWED = {
    "automations": {"twin", "ids", "identity"},
    "billing":     {"ids", "identity"},             # НЕ control!
    "telemetry":   {"ids", "identity"},             # control знають лише через подію
}
def test_no_forbidden_import():
    for module, deps in actual_imports().items():
        leaked = deps - ALLOWED[module]
        assert not leaked, f"{module} проліз повз двері: {leaked}"
```
:::

Той самий сторож ловить і цикл у графі, і звертання модуля в чужу схему бази. [ADR-014 накидав таку перевірку на одне ребро](root:progarch/dh-context-boundaries-choice) (`billing` не сміє знати `control`); тут вона розгорнута на **весь** граф. Готові інструменти на кожен стек — `import-linter` для Python, `dependency-cruiser` чи ESLint-правила меж для TypeScript, `ArchUnit` для Java, `Packwerk` для Ruby; повний сторож для DH — у тому ж [каркасі моноліта](root:progarch/dh-monolith-boundaries/proj-dh-monolith-skeleton.md).

> 🔧 **Навіщо це.** Межа, яку не перевіряє машина, — це не межа, а побажання. У сервісів стіну стереже фізика: щоб залізти в чужий модуль, довелося б зробити видимий і дорогий мережевий виклик. В одному процесі цієї природної перепони немає — її роль грає саме тест, що робить порушення **червоною збіркою**, а не темою для дискусії на рев'ю. Тому сторож ставлять поряд із самими модулями з першого дня, а не «колись потім».

## Що тепер у руках

Ми взяли мапу дев'яти світів і зробили її **структурою, яку тримає код, а не добра воля**. Дев'ять огороджених модулів в одному застосунку; стрілки мапи — як правила імпорту в ациклічному графі; одна база, але схема на модуль і жодного `JOIN` через стіну; внутрішньопроцесна шина, що вже говорить дротовим контрактом; один корінь, що збирає весь дім; і машина, яка вартує кожну стіну. DH сьогодні не платить **ані копійки** мережевого податку — будь-який перетин межі лишається викликом функції, — а кожен фасад уже є **наперед прорізаним швом**.

І саме тому наступне питання нарешті можна поставити чесно. Межі проведено, стіни реальні й захищені — тож питання вже не «де різати» (шви розмічені й вартуються), а куди гостріше: **чи різати хмару DH на сервіси взагалі, котрі контексти й коли**. Кандидати вбрані в біле й стоять при дверях; чи буде хтось із них обраний — [окреме рішення](root:progarch/when-to-split), за яке візьмемося далі, вже знаючи, що кожен розріз купується мережею й платити за нього варто лише там, де він щось приносить.
