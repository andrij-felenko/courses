# ⚙️ Нічна агрегація DH: розподілений cron, що не бреше на переведенні стрілок

Крок-власник назвав усі частини машини — лізу, фенсинг-токен, вікно від півночі до півночі, ідемпотентний upsert, весняну дірку й осінню складку — і показав крихітний зародок: дві функції на десять рядків. Але між «назвати» й «зібрати робочим» лежить рівно та відстань, на якій ламаються реальні системи. Тут ми зберемо **весь** нічний вузол DH — планувальник, наздоганяння, задачу — і проженемо його крізь справжні переведення стрілок 2026 року, щоб побачити на виході, а не на віру, що доба буває 23-, 24- і 25-годинна, і що жодна з цих трьох не збиває машину.

Умова конкретна. Дім тримає в кожному регіоні **не один сервер, а кластер** застосункових вузлів. Щоночі, для кожного дому, треба згорнути вчорашню сиру телеметрію — мільйони показань — в один денний рядок: «спожито стільки, пік такий, вимірів стільки». Машина мусить: запуститися **рівно раз** на весь кластер (а не стільки разів, скільки вузлів); порахувати вікно «вчора» **правильно** попри переведення стрілок; **наздогнати** доби, пропущені, поки кластер лежав; і лишитися **ідемпотентною** — щоб дубль ретраю чи осіннє подвоєння не порахували споживання двічі. Мова — TypeScript і Python: той самий бекенд-оркестратор і та сама календарна арифметика, дві ідіоми одного рушія.

## Вікно доби: від півночі до півночі, і чому щілина дістається задарма

Почнімо з серця, бо на ньому все стоїть. «Вчора» — це не «зараз мінус 86400 секунд», а проміжок **від локальної півночі до локальної півночі**, переведений у два UTC-інстанти. Уся хитрість у тому, що дві сусідні локальні півночі самі собою відстоять на 23, 24 чи 25 годин — рівно стільки, скільки тривала та доба, — тож правильне вікно виходить **без жодного окремого коду «а якщо DST»**. Треба лише чесно взяти першу мить доби й першу мить наступної.

І тут TypeScript із новим `Temporal` дає точний інструмент. Метод `startOfDay()` повертає не «00:00», а **першу наявну мить доби** — і це не педантизм: є рідкісні зони, що колись переводили стрілки саме опівночі (історично `America/Sao_Paulo`), і в них 00:00 тієї ночі **не існувало зовсім**, як не існує 02:00 у нашого Києва навесні. `startOfDay()` бере таку щілину до уваги за побудовою; наївне `set hour 0` або кинуло б, або тихо збрехало. У Python стандартної `.startOfDay()` немає, тож першу мить доводиться діставати вручну — і саме тому корисно бачити обидві мови поруч: видно, що́ Temporal робить за тебе.

:::tabs
```ts
// Temporal — стандарт ES2026, у Node 26 доступний без прапорців.
type Window = { fromUtc: Temporal.Instant; toUtc: Temporal.Instant; hours: number };

// Вікно однієї ЛОКАЛЬНОЇ доби `date` у зоні `zone`, у UTC-інстантах.
// startOfDay() дає ПЕРШУ наявну мить доби — тож зона, що колись переводила
// стрілки опівночі (і 00:00 не існувало), врахована сама, без «if DST».
function localDayWindow(zone: string, date: Temporal.PlainDate): Window {
  const start = date.toZonedDateTime(zone).startOfDay();
  const end   = date.add({ days: 1 }).toZonedDateTime(zone).startOfDay();
  const hours = start.until(end, { largestUnit: "hour" }).hours;
  return { fromUtc: start.toInstant(), toUtc: end.toInstant(), hours };
}

// «Вчора» для дому — попередня локальна доба відносно поточної миті в його зоні.
function yesterday(zone: string): Temporal.PlainDate {
  return Temporal.Now.zonedDateTimeISO(zone).toPlainDate().subtract({ days: 1 });
}
```
```py
from datetime import datetime, date, time, timedelta, timezone
from zoneinfo import ZoneInfo          # жива база переведень IANA у stdlib

def local_midnight(d: date, zone: ZoneInfo) -> datetime:
    """Перша наявна мить локальної доби d — ручний аналог Temporal .startOfDay().
    Майже завжди це рівно 00:00; але зона, що колись переводила стрілки опівночі,
    могла НЕ мати 00:00 — тоді беремо мить, куди щілина його виштовхнула."""
    naive = datetime.combine(d, time(0, 0))
    dt = naive.replace(tzinfo=zone)                        # fold=0 → перша, якщо складка
    back = dt.astimezone(timezone.utc).astimezone(zone).replace(tzinfo=None)
    if back != naive:                                      # 00:00 у весняній щілині
        dt = back.replace(tzinfo=zone)                     # мить, куди щілина виштовхнула північ
    return dt

def local_day_window(zone_name: str, d: date) -> tuple[datetime, datetime, float]:
    zone = ZoneInfo(zone_name)
    start = local_midnight(d, zone)
    end   = local_midnight(d + timedelta(days=1), zone)    # наступна локальна північ
    hours = (end - start).total_seconds() / 3600           # 23 / 24 / 25 — саме собою
    return start.astimezone(timezone.utc), end.astimezone(timezone.utc), hours
```
:::

Зверни увагу, де сидить DST і де його **немає**. Крок «наступна доба» — це `date.add({ days: 1 })` (і `d + timedelta(days=1)` у Python): чиста арифметика **дати**, без години, без зони, завжди рівно один календарний день. А переведення в час — `startOfDay().toInstant()` — це вже єдине місце, де база зон питається про зсув, і саме там 23/24/25 годин з'являються самі. Розвести ці дві дії — календарну й часову — і є весь фокус.

Тепер обіцяна перевірка на дотик. Європа переводить стрілки вперед в останню неділю березня (2026-го — 29-го) і назад в останню неділю жовтня (25-го). Проженімо `localDayWindow` для Києва через обидві межі й через звичайний літній день:

```
localDayWindow("Europe/Kyiv", 2026-03-29) → 23 год   [2026-03-28T22:00Z … 2026-03-29T21:00Z)
localDayWindow("Europe/Kyiv", 2026-06-15) → 24 год   [2026-06-14T21:00Z … 2026-06-15T21:00Z)
localDayWindow("Europe/Kyiv", 2026-10-25) → 25 год   [2026-10-24T21:00Z … 2026-10-25T22:00Z)
```

Ось воно, чорним по білому. Локальна доба 29 березня — від півночі за EET (+02:00) до півночі за EEST (+03:00) — триває **23 години**, і вікно це знає, бо його межі — дві правдиві локальні півночі, а не «зараз − 24 год». Доба 25 жовтня — **25 годин**. Звичайна червнева — рівно 24. Жодного розгалуження «якщо сьогодні переводять стрілки» в коді немає й не мусить бути: правило зберігається наміром, а мить розгортається в останню секунду — рівно [вибір зберігання часу з попереднього кроку](root:progarch/time-storage-choice) у дії.

> 🔧 **Навіщо це.** Верхня межа вікна — **напіввідкрита**: `at < toUtc`, а не `<=`. Показання, що впало точно в локальну північ, належить **наступній** добі — і тільки їй, рівно один раз. Замінити `<` на `<=` — і мить межі порахується у двох сусідніх добах: споживання на крихту, але систематично завищене, і найгірше — саме в ніч переведення, коли межа й так стрибає. Напіввідкритий інтервал `[from, to)` — це не стиль, це те, що робить сусідні вікна розбиттям осі, а не покриттям із нахлистом.

А що з тими двома межовими годинами — неіснуючою навесні й подвійною восени, — якщо на них сяде вже не вікно, а сам **час запуску** (скажімо, автоматизація «о 03:30»)? Це окрема розмова про `disambiguation: "reject"` та `fold`, і вона повністю розібрана в [розкладі трьома способами](root:progarch/time-storage-choice/proj-dh-schedule-three-ways.md); тут нам щастить, бо вікно доби спирається на **північ**, а не на межову годину, і `startOfDay()` уже вибрав за нас правильний бік.

## Один запуск на кластер: ліза плюс фенсинг-токен

Вікно готове — але хто його запустить? Якщо cron сидить на кожному вузлі кластера, о другій ночі агрегація стартує **стільки разів, скільки вузлів**, і всі вони кинуться писати той самий підсумок. Наївна відповідь — «хай пише лише один, обраний» — розбивається об те, що обраний вузол може впасти, застрягти в паузі збирача сміття чи від'єднатися від мережі саме тоді, коли настав його час. Потрібне право, яке **саме спливає**, якщо власник замовк.

Це і є **ліза** (англ. *lease* — тимчасове право) — механізм, який Cary Gray і David Cheriton описали ще 1989 року саме проти цієї біди: право з терміном, і що коротший термін, то менше шкодить збій власника. Реалізуймо її одним рядком у базі — рядком, чий строк судить **годинник бази**, а не настінний годинник вузла (це принципово: вузли з розсинхронізованими годинниками все одно погодяться, бо порівнюють з одним `now()`):

```sql
CREATE TABLE cron_lease (
  name       text PRIMARY KEY,            -- 'nightly-rollup'
  holder     text,                        -- ідентифікатор вузла-власника
  fence      bigint NOT NULL DEFAULT 0,   -- фенсинг-токен: монотонно РОСТЕ
  expires_at timestamptz NOT NULL DEFAULT 'epoch'
);
```

Узяти лізу — це один атомарний upsert. Він вдається, лише якщо ліза або нічия, або вже прострочена; і щоразу, коли право переходить у нові руки, він **піднімає фенс на одиницю**. Продовжити свою живу лізу — окрема дія, що фенс не чіпає (те саме право, той самий токен, лише пізніший строк):

:::tabs
```ts
import { Pool } from "pg";

class CronLease {
  constructor(private db: Pool, private name: string,
              private me: string, private ttlSec = 60) {}

  // Взяти лізу (вільну або прострочену). null — хтось інший тримає ЖИВУ.
  async acquire(): Promise<{ fence: number } | null> {
    const { rows } = await this.db.query(
      `INSERT INTO cron_lease (name, holder, fence, expires_at)
       VALUES ($1, $2, 1, now() + make_interval(secs => $3))
       ON CONFLICT (name) DO UPDATE
          SET holder = EXCLUDED.holder,
              fence  = cron_lease.fence + 1,          -- новий власник → новий токен
              expires_at = EXCLUDED.expires_at
          WHERE cron_lease.expires_at < now()         -- лише якщо стара прострочена
       RETURNING fence`,
      [this.name, this.me, this.ttlSec]);
    return rows.length ? { fence: Number(rows[0].fence) } : null;
  }

  // Продовжити СВОЮ живу лізу тим самим токеном. false — лізу втрачено, СТОП.
  async renew(fence: number): Promise<boolean> {
    const { rowCount } = await this.db.query(
      `UPDATE cron_lease SET expires_at = now() + make_interval(secs => $3)
        WHERE name = $1 AND holder = $2 AND fence = $4 AND expires_at >= now()`,
      [this.name, this.me, this.ttlSec, fence]);
    return rowCount === 1;
  }
}
```
```py
class CronLease:
    def __init__(self, pool, name, me, ttl_sec=60):
        self.pool, self.name, self.me, self.ttl = pool, name, me, ttl_sec

    async def acquire(self) -> int | None:
        """Взяти лізу (вільну або прострочену). None — хтось інший тримає ЖИВУ."""
        row = await self.pool.fetchrow(
            """INSERT INTO cron_lease (name, holder, fence, expires_at)
               VALUES ($1, $2, 1, now() + make_interval(secs => $3))
               ON CONFLICT (name) DO UPDATE
                  SET holder = EXCLUDED.holder,
                      fence  = cron_lease.fence + 1,      -- новий власник → новий токен
                      expires_at = EXCLUDED.expires_at
                  WHERE cron_lease.expires_at < now()     -- лише якщо стара прострочена
               RETURNING fence""",
            self.name, self.me, self.ttl)
        return row["fence"] if row else None

    async def renew(self, fence: int) -> bool:
        """Продовжити СВОЮ живу лізу тим самим токеном. False — лізу втрачено, СТОП."""
        tag = await self.pool.execute(
            """UPDATE cron_lease SET expires_at = now() + make_interval(secs => $3)
                WHERE name = $1 AND holder = $2 AND fence = $4 AND expires_at >= now()""",
            self.name, self.me, self.ttl, fence)
        return tag.endswith(" 1")            # 'UPDATE 1'
```
:::

Ліза сама по собі закриває **буденний** випадок: двоє прокинулись, один узяв право, другий бачить живу лізу й мовчить. Але вона має відому діру, і саме про неї — фенсинг-токен. Уяви: власник узяв лізу з токеном 33, почав планувати — і провалився в довгу паузу збирача сміття (кілька секунд, коли процес живий, але заморожений). Ліза за цей час спливла, наступний вузол чесно взяв її з токеном 34 і вже пише. А тоді перший **оживає** — він не знає, що спав, і його наступною дією буде запис, наче він досі власник. Ліза його вже не тримає, але код нічого про це не знає.

Ліки — те, що Martin Kleppmann описав 2016 року, розбираючи, чому наївний розподілений замок небезпечний: **фенсинг-токен** (англ. *fencing token* — «загороджувальний»), монотонно зростаюче число, яке ліза видає при кожному захопленні, і яке **сховище перевіряє на місці запису**. Зомбі-власник приходить із токеном 33; сховище пам'ятає, що вже бачило 34; `33 < 34` — запис відкинуто. Право можна проспати, але старий номер квитка нове сховище не прийме. Це та сама координація «ліза + огорожа», що живе в темі про [розподілені замки](root:sf-distributed/distributed-locks); тут ми прикладаємо її до нічного тику.

## Наздоганяння: high-water mark і три політики пропущеного

Тепер найтонше — і те, що найчастіше пишуть як баг, навіть не помітивши. Питання просте: **які саме доби згортати?** Спокуслива відповідь — «вчорашню, тобто сьогодні мінус один». І вона тихо-катастрофічна, бо ловить рівно одну добу: якщо кластер лежав три доби, ти згорнеш лише останню, а дві попередні зникнуть **назавжди** — їх уже ніхто не перепитає, бо завтра «вчора» буде вже інше.

Правильна відповідь тримає в базі **позначку водолінії** (англ. *high-water mark*) — останню **успішно** згорнуту добу кожного дому. І тоді «які доби due» стає чистою функцією трьох речей: остання зроблена, сьогодні, політика. Наздоганяння з цього **випадає саме собою** — це не окрема функція, яку болтом прикручують, а просто відсутність бага:

:::tabs
```ts
type MissPolicy = "skip" | "catchup" | "coalesce";

// Локальні доби, ще НЕ згорнуті: інтервал (lastDone, сьогодні), обидва кінці виключно.
function dueDays(zone: string, lastDoneIso: string): Temporal.PlainDate[] {
  const today = Temporal.Now.zonedDateTimeISO(zone).toPlainDate();
  const days: Temporal.PlainDate[] = [];
  let cur = Temporal.PlainDate.from(lastDoneIso).add({ days: 1 });  // перша НЕзгорнута
  while (Temporal.PlainDate.compare(cur, today) < 0) {             // строго ДО «сьогодні»
    days.push(cur);
    cur = cur.add({ days: 1 });        // чиста календарна арифметика — DST тут не живе
  }
  return days;
}

// Політика вирішує, ЩО робити з провалом у кілька діб.
function applyPolicy(days: Temporal.PlainDate[], p: MissPolicy): Temporal.PlainDate[] {
  if (days.length <= 1 || p === "catchup") return days;   // усі по черзі
  if (p === "skip") return days.slice(-1);                // лише найсвіжіша, решта — дірки
  return days;                            // coalesce: усі, але далі зіллються в ОДНЕ вікно
}
```
```py
def due_days(zone_name: str, last_done: date) -> list[date]:
    """Локальні доби, ще НЕ згорнуті: (last_done, сьогодні), обидва кінці виключно."""
    today = datetime.now(ZoneInfo(zone_name)).date()
    days, cur = [], last_done + timedelta(days=1)          # перша НЕзгорнута
    while cur < today:                                     # строго ДО «сьогодні»
        days.append(cur)
        cur += timedelta(days=1)                           # чиста дата — DST тут не живе
    return days

def apply_policy(days: list[date], p: str) -> list[date]:
    if len(days) <= 1 or p == "catchup":
        return days                                        # усі по черзі
    if p == "skip":
        return days[-1:]                                   # лише найсвіжіша, решта — дірки
    return days                                            # coalesce: усі → в ОДНЕ вікно
```
:::

Придивися ще раз: `dueDays` крокує **датами** (`add({ days: 1 })`), а вікно кожної дати рахує окрема `localDayWindow`. Тому наздоганяння через переведення стрілок «просто працює»: якщо серед пропущених діб трапилась 23-годинна весняна — вона й порахується 23-годинним вікном, бо кожна дата розгортається в мить незалежно. Провал у три доби, одна з яких переведення, дає три правильні вікна різної тривалості, і жодного окремого коду для цього не треба.

![Локальна вісь діб. Ліворуч 27 бер (24 год, mark тут, згорнуто), далі три пропущені доби під дужкою «кластер лежав»: 28 (24 год), 29 (23 год — весна), 30 (24 год), і 31 «сьогодні». Стрілка catch-up веде mark 27→28→29→30, enumerator видав [28,29,30]. Унизу контр-доріжка: наївне «вчора=сьогодні−1» бачить лише 30, а 28 і 29 позначені ✗ «втрачено назавжди».](img/catchup-mark.svg)

*Позначка водолінії веде наздоганяння сама: доки вона на 27, а сьогодні 31, «due» — це 28, 29, 30, і одна з них 23-годинна. Наївне «вчора = сьогодні − 1» бачить лише 30 — і решта провалу зникає без сліду.*

Тепер про **політику**, бо «наздогнати всі» — не завжди відповідь. Три способи повестися з провалом мають точні імена в дорослих планувальниках, і корисно бачити, що ми не винаходимо, а називаємо давно відоме. У **Quartz** це три misfire-інструкції: `DO_NOTHING` — пропустити прогаяне й чекати наступного (наш **skip**); `IGNORE_MISFIRE` — відпалити всі пропущені (наш **catch-up**); `FIRE_NOW` — злити всі пропущені в **один** негайний запуск (наш **coalesce**). Kubernetes у своєму `CronJob` тримає ту саму логіку інакшими словами — `startingDeadlineSeconds` обмежує, наскільки давнє прогаяне ще варте запуску, а якщо пропущено понад **сто** тиків, контролер узагалі не стартує, щоб не влаштувати лавину.

![Три доріжки на однаковому провалі 28·29·30. SKIP (Quartz DO_NOTHING): 28 ✗, 29 ✗, 30 ✓ — лише найсвіжіша, дірки лишаються. CATCH-UP (Quartz ignore-misfire): 28 ✓, 29 ✓, 30 ✓ — кожна доба свій рядок за ключем (дім, доба). COALESCE (Quartz FIRE_NOW): один широкий блок «28–30 злиті в одне вікно» з попередженням, що ключ (дім, доба) не тримає діапазон.](img/miss-policies.svg)

*Skip дешевий і губить проміжок; catch-up точний і дорогий; coalesce зливає провал в один прогін. Для подобового підсумку годяться перші два — coalesce ламається об ключ (дім, доба).*

І ось де **coalesce** ховає пастку, яку крок-власник лише позначив словом «злити». Наш підсумок ідемпотентний **за ключем `(дім, доба)`** — одна доба, один рядок. А coalesce каже «порахуй провал 28–30 одним вікном» — тобто одним записом, у якого немає єдиної `доби`. Виходить, що coalesce **несумісний** із подобовим підсумком: він годиться там, де тобі байдужі проміжні доби й потрібне лише одне свіже число за діапазон — «перерахуй ковзне середнє за 30 днів», «онови поточний баланс». Для «спожито за кожну добу» coalesce мовчки зіллє три дні в один рядок і зіпсує саме ту гранулярність, заради якої агрегація існує. Тому DH для телеметрії бере **catch-up** (з обмеженням на лавину, про яке нижче), а coalesce лишає перерахункам, чия природа — одне число, а не ряд.

## Ідемпотентний upsert і чому три сітки перекриваються

Лишилося записати підсумок так, щоб **другий** запуск — від осіннього подвоєння, від ретраю черги «щонайменше раз», від наздоганяння, що наклалося, — не додав, а **переписав**. Це і є ідемпотентність за ключем, і в SQL вона виражається прямо первинним ключем плюс `ON CONFLICT`:

```sql
CREATE TABLE daily_summary (
  home_id     text    NOT NULL,
  day         date    NOT NULL,             -- ЛОКАЛЬНА доба дому, НЕ UTC-мить
  kwh         numeric NOT NULL,
  peak_w      numeric NOT NULL,
  samples     integer NOT NULL,
  zone        text    NOT NULL,             -- зона розрахунку (для аудиту)
  computed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (home_id, day)                -- ← сам ключ ідемпотентності
);

INSERT INTO daily_summary (home_id, day, kwh, peak_w, samples, zone)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (home_id, day) DO UPDATE         -- другий запуск ПЕРЕПИШЕ, а не додасть
   SET kwh = EXCLUDED.kwh, peak_w = EXCLUDED.peak_w,
       samples = EXCLUDED.samples, computed_at = now();
```

Зверни увагу на тип `day`: це `date`, **локальна календарна доба**, а не timestamp. Підсумок ключований людською добою; сира телеметрія — інстантами. Дві різні породи часу в одній системі, кожна там, де доречна, — точно як минула подія живе замороженою міттю, а майбутній намір — правилом і зоною. Це відлуння [ключа ідемпотентності DH](root:progarch/dh-bad-network): випадковий рядок казав «один запис на один намір»; тут природний ключ `(дім, доба)` каже «один рядок на одну добу», і повтор наміру сходиться в те саме місце.

Тепер зберемо задачу-робітника цілком. Тонкість, заради якої варто дивитися на весь код, а не на фрагмент, — **порядок і транзакція**: підсумок і просування mark комітяться **разом**, і mark рухається **лише** свіжим фенсом. А сам підсумок фенсом можна й не боронити — і ось чому це не недбалість, а точний розрахунок:

:::tabs
```ts
type AggTask = { homeId: string; zone: string; day: string;
                 fromUtc: string; toUtc: string; fence: number; policy: MissPolicy };

async function aggregate(db: Pool, t: AggTask): Promise<void> {
  const { rows } = await db.query(
    `SELECT value, watts FROM telemetry
      WHERE home_id = $1 AND at >= $2 AND at < $3`,   // напіввідкрите [from, to)
    [t.homeId, t.fromUtc, t.toUtc]);
  const s = rollUp(rows);                             // { kwh, peakW, samples }

  await db.query("BEGIN");
  try {
    // 1) підсумок — ідемпотентний за (дім, доба): дубль перепише той самий рядок
    await db.query(
      `INSERT INTO daily_summary (home_id, day, kwh, peak_w, samples, zone)
       VALUES ($1,$2,$3,$4,$5,$6)
       ON CONFLICT (home_id, day) DO UPDATE
          SET kwh=EXCLUDED.kwh, peak_w=EXCLUDED.peak_w,
              samples=EXCLUDED.samples, computed_at=now()`,
      [t.homeId, t.day, s.kwh, s.peakW, s.samples, t.zone]);
    // 2) mark — після підсумку, свіжим фенсом, і на добу $2 ЛИШЕ якщо вона
    //    БЕЗПОСЕРЕДНЬО наступна (last_done_day = $2 − 1) — АБО політика skip,
    //    якій дозволено навмисне перестрибнути дірку. Тоді доба, що дозріла
    //    поперед сусідів у пулі наздоганяння, mark не зрушить (інакше вона
    //    перестрибнула б ще не зроблену добу — і та зникла б назавжди).
    await db.query(
      `UPDATE home_cron
          SET last_done_day = GREATEST(last_done_day, $2), seen_fence = $3
        WHERE home_id = $1 AND seen_fence <= $3
          AND (last_done_day = $2::date - 1 OR $4 = 'skip')`,
      [t.homeId, t.day, t.fence, t.policy]);
    await db.query("COMMIT");
  } catch (e) {
    await db.query("ROLLBACK");                       // впав до коміту → доба лишилась due
    throw e;
  }
}
```

Тут — уся вага вставки, і вона в одному чесному спостереженні. У цього нічного вузла **три сітки безпеки, і вони перекриваються**. Ліза каже «зазвичай планує один». Фенсинг каже «застарілий писар не зрушить вказівник». Ключ `(дім, доба)` каже «навіть якщо двоє порахують ту саму добу — підсумок той самий, бо вікно є чистою функцією зони й дати». І ось несподіванка, яку більшість статей замовчує: **для самого підсумку фенсинг не обов'язковий** — його вже боронить ідемпотентність за ключем, адже два планувальники, порахувавши `(дім, 29 бер)`, отримають байт у байт те саме число. Фенсинг стає незамінним рівно там, де запис **не** ідемпотентний: рухома позначка mark (яку зомбі міг би зрушити не туди), зовнішній ефект на кшталт відправленого пуша. Не тягни фенсинг як культ у кожен запис — але не викидай його там, де писар може напартачити необоротно.

![Три колонки. СІТКА 1 ЛІЗА: двоє прокинулись о 02:00 → лізу атомарно бере лише один → рівно один планувальник. СІТКА 2 ФЕНСИНГ: власник ліг у GC-паузу, ліза згасла, ожив і пише → наступник узяв токен 34, зомбі пише 33, сховище бачить 33<34 і відмовляє → застарілий запис відкинуто. СІТКА 3 КЛЮЧ (дім,доба): черга доставила задачу двічі → upsert перепише той самий рядок тими самими числами → без подвоєння. Унизу: три сітки перекриваються, ніч стоїть на всіх трьох разом.](img/three-nets.svg)

*Ліза ловить буденний випадок, фенсинг — зомбі після паузи, ключ — дубль від ретраю. Кожна закриває свій клас збою; жодна сама не закриває всі три. Надійність — у перекритті, а не в будь-якій одній сітці.*

> 🔧 **Навіщо це.** Позначку mark рухай **лише після** того, як підсумок durably записано — в одній транзакції з ним. Спокуса зробити навпаки (посунув mark, потім рахуєш) коштує дорого: якщо між ними впасти, mark уже каже «доба зроблена», а рядка немає — і при політиці skip цю добу **ніхто ніколи не перегляне**. Порядок «спочатку факт, потім вказівник на факт» — це те, що робить наздоганяння самовідновним: недороблена доба лишається due, доки її не доведено до коміту.

І тут ховається друга, тонша пастка тієї самої позначки — вже не в порядку «підсумок → mark» усередині однієї задачі, а в порядку між **різними добами**. Наздоганяння ми пустили через окремий пул (щоб не влаштувати лавину), а пул порядку завершення **не гарантує**: задачі за 28-ме, 29-те й 30-те одного дому можуть скомітитись урозбій. Якби mark щоразу стрибав на **максимум** зробленого — наївне `last_done_day = GREATEST(mark, доба)` без жодної умови, — то доба, що дозріла першою, скажімо 30-те, штовхнула б вказівник одразу на 30; а якби 28-ме потім упало, `dueDays` дивилася б уже на порожній проміжок `(30, сьогодні)` і **ніколи** не перепитала б 28-ме. Це рівно та сама «два дні назавжди», від якої вся ця частина й боронить, — тільки прокралася з іншого боку. Тому вказівник рухається **лише на свою безпосередньо наступну добу** (`last_done_day = доба − 1`): доба поза чергою чесно пише свій рядок у `daily_summary`, але mark не чіпає й дочекається, поки черга дійде до неї по порядку — а що її потім перерахують ще раз, байдуже, підсумок ідемпотентний за `(дім, доба)`. Виняток — єдино `skip`: він **навмисне** лишає дірки, тож саме йому дозволено перестрибнути (`OR policy = 'skip'`). Одне й те саме поле `last_done_day` під двома політиками означає різне: під catch-up — «останню суцільно пройдену добу», під skip — «найсвіжішу, повз яку ми свідомо пройшли». `GREATEST` лишається на місці не задля стрибка, а як запобіжник від регресу: дубль зі старою добою чи застарілим фенсом ніколи не потягне вказівник назад.

Планувальник, що зшиває все це докупи, після такого — майже формальність. Він тримає лізу, і поки тримає — обходить доми, для кожного питає `dueDays`, застосовує політику, і кладе задачі в чергу з поточним фенсом:

```ts
async function planner(db: Pool, me: string): Promise<void> {
  const lease = new CronLease(db, "nightly-rollup", me, 60);
  let fence: number | null = null;                         // токен поточної оренди
  for (;;) {
    if (fence === null) {                                  // оренди нема — БЕРЕМО (нове право)
      const held = await lease.acquire();
      if (!held) { await sleep(30_000); continue; }        // живу лізу тримає інший — чекаємо
      fence = held.fence;
    } else if (!(await lease.renew(fence))) {              // не ПРОДОВЖИЛАСЬ → оренду втрачено
      fence = null; continue;                              // на наступному колі спробуємо взяти
    }
    // ми — єдиний планувальник; фенс СТАБІЛЬНИЙ на всю оренду (renew його не міняє)
    for (const h of await loadHomes(db)) {                 // { id, zone, policy, lastDone }
      const days = applyPolicy(dueDays(h.zone, h.lastDone), h.policy);
      for (const day of days) {
        const w = localDayWindow(h.zone, day);
        await enqueue(db, {
          homeId: h.id, zone: h.zone, day: day.toString(),
          fromUtc: w.fromUtc.toString(), toUtc: w.toUtc.toString(),
          fence,                                           // той самий токен їде до писаря
          policy: h.policy,                                // політика їде із задачею — вона вирішує рух mark
        });
      }
    }
    await sleep(30_000);                                   // sleep < TTL, щоб renew устигав
  }
}
```

Планувальник сам **нічого не агрегує** — він лише вирішує, що́ треба зробити, і роздає роботу робітникам, кожен з яких дисциплінований тим самим контрактом, що ми вивели [на прикладі одного довгого кліпа](root:progarch/dh-long-ops): ідемпотентність, чесний статус, оренда з серцебиттям, скінченний строк. Обчислення «які доби» й виконання «згорни добу» розведені — і саме тому одну задачу можна безпечно перезапустити, не чіпаючи решти.

## Складність і пастки

Кожна частина цієї машини має гострий край, і кожен уже стелив комусь нічну зміну.

**Зона дому, а не зона сервера.** `dueDays` і `localDayWindow` беруть зону **дому** (`h.zone`), не зону, у якій крутиться вузол. Два доми в різних поясах мають різне «вчора» й різну довжину доби тієї самої ночі. Порахувати вікно за таймзоною сервера — класична причина, чому «в одних усе добре, в інших графік із діркою», і чому баг видно лише з тих поясів, де сервера немає.

**TTL лізи — між тертям і повільним відновленням.** Короткий строк (кілька секунд) — і випадкова затримка мережі чи пауза збирача змусять лізу без потреби переходити з рук у руки, планувальник смикатиметься. Довгий (хвилини) — і після справжнього падіння власника кластер довго чекатиме, поки право спливе, перш ніж хтось підхопить. Немає «правильного» числа; є усвідомлений компроміс, і **фенсинг** — саме те, що дозволяє тримати TTL коротшим без страху за коректність: навіть якщо помилився й перевів лізу зарано, старий власник упреться в огорожу токена.

**Лавина наздоганяння.** Увімкнули кластер після тижня простою — і catch-up чесно народжує 7 діб × мільйони домів задач за мить. Якщо всі вони поб'ються в один пул робітників, вони виїдять слоти й покладуть свіжу роботу — рівно [пастка спільного пулу](root:progarch/dh-resilient-path), яку ми вже проходили. Тому наздоганяння **обов'язково** через окремий пул із обмеженою пропускністю (саме тому Kubernetes і ставить стелю в сто пропущених тиків) — краще розмазати провал на години, ніж утопити ним живий трафік.

**Позначка, що перестрибує дірку.** Той самий пул наздоганяння завершує доби врозбій — тож рухати mark на максимум зробленого означає дати добі, що дозріла першою, штовхнути вказівник над ще не зробленою сусідкою; та потім упаде, і `dueDays` її вже не побачить. Під catch-up mark сміє йти **лише на наступну по порядку** добу (`last_done_day = доба − 1`); перестрибувати дірку дозволено тільки `skip`, бо в нього дірки — навмисні. Сплутати ці два правила — безумовний `GREATEST` під catch-up — і повертається та сама втрата діб, від якої вся ця частина боронить.

**Coalesce на подобовому ключі.** Ще раз, бо це найтонше: `coalesce` і ключ `(дім, доба)` несумісні за побудовою. Якщо політика дому — подобовий підсумок, coalesce або зіллє тиждень в один рядок (і збреше про гранулярність), або тихо занапастить ідемпотентність. Coalesce — це відповідь для перерахунків «одне число за діапазон», не для рядів. Обирай політику під **природу підсумку**, а не за звичкою.

**Північ, що не існує.** І наостанок — те, з чого почали. У переважній більшості зон локальна північ завжди на місці, і `startOfDay()` виглядає надлишковим. Але саме тому наївний `set hour 0` живе в кодовій базі роками, аж поки дім не з'явиться в зоні, що колись переводила стрілки опівночі, — і тоді вікно тієї однієї ночі порахується від неіснуючої миті. `startOfDay()` (і ручний `local_midnight` у Python) бере цей край задарма; ціна — одна чесна назва методу замість зашитої в код віри, що доба починається о 00:00.

Зібравши все докупи, бачиш, що жоден шматок не був складним поодинці. Складним був **стик**: там, де годинник стає тригером, а кластер — множиною однакових вузлів. Вікно від півночі до півночі знімає DST; ліза з фенсингом зводить кластер до одного планувальника; позначка водолінії, що повзе лише по суцільному пройденому й не перестрибує дірки, робить наздоганяння самовідновним, а не окремою функцією; ключ `(дім, доба)` робить повтор нешкідливим. Чотири прості речі, що перекриваються, — і ніч, яку не збиває ні весняна дірка, ні осіння складка, ні тиждень простою.
