# ⚙️ «Зачинити двері» двома зчепленнями: обидва шляхи від кнопки до замка

Крок лишив на столі два обробники по чотири рядки — і чесно попередив, що це начерк. Синхронний `await hub.send(...)` і асинхронний `enqueue` показали найголовніше: різниця не в тілі, а в тому, що обробник **повертає** — `200` проти `202`. Але між тим начерком і кодом, який справді можна ввімкнути живій родині, лежить усе, про що начерк змовчав. Звідки береться кінцевий стан, коли обробник уже відповів? Що показати на екрані, поки замок іще не клацнув? Що робити, коли брокер підсуне ту саму команду вдруге? І куди подіти команду, яка так і не виконалась?

Зберімо обидва шляхи повністю — так, щоб їх можна було читати як робочий сервіс, а не як ілюстрацію. Теорію зчеплення в часі, арифметику тендітності ланцюга й саму причину, чому `202` — це не `200`, крок уже дав; тут я на них лише спираюся. Буде рівно код: спільна основа, синхронний обробник із чесною поведінкою на таймауті, повний асинхронний конвеєр із дедуплікацією, ендпойнтом статусу й оновленням твіна — і, в кінці, місця, де це вкусить.

Мова тут — TypeScript: команда дому, черга, HTTP-обробники й DTO — це рівно та царина, де він ідіоматичний, а типи-об'єднання станів команди самі документують, що взагалі можливо. Каркас — в стилі Express, але фреймворк тут ні до чого: те, що видно нижче, — форма рішення, а не API бібліотеки.

## Задача: та сама кнопка, дві системи

Ось на що ми домовляємося. Родина тисне «зачинити двері». Обидва шляхи мусять довести команду до фізичного замка через хаб і **чесно** розповісти застосунку, чим усе скінчилося. Але «чесно» означає різне.

**Синхронний** обробник мусить: дочекатися замка, повернути `200` з **реальним** кінцевим станом (`locked`/`unlocked`), а на таймауті — не збрехати. Пам'ятаємо з кроку про [часткову відмову](root:progarch/partial-failure), що мовчання хаба — це «я не знаю», а не «не вийшло»: замок міг клацнути, а відповідь загубитися. Обробник мусить це «не знаю» повернути як окремий стан, а не як фальшиве «помилка».

**Асинхронний** мусить: прийняти команду, одразу відповісти `202` з `commandId`, покласти команду в чергу — і на цьому відпустити застосунок. Окремий споживач витягне команду, коли хаб оживе, виконає її **ідемпотентно за `commandId`** (бо брокер доставляє щонайменше раз — той самий запит прилетить двічі), запише кінцевий стан і оновить твін дому. Застосунок тим часом показує «в обробці» й опитує ендпойнт статусу, доки не побачить кінцевий стан. А команда, що впала N разів поспіль, мусить осісти в мертвій черзі, а не зникнути.

Різниця, яку ми хочемо зробити **видимою в коді**, зводиться до трьох речей: коли й де спливає помилка, хто захищає від дубля, і чи бачить застосунок правду одразу чи згодом. Почнімо зі спільного фундаменту, на якому стоять обидва.

## Спільна основа

Обидва шляхи говорять до того самого хаба й тими самими типами. Виокремимо їх, щоб далі не повторюватись.

```ts
// domain.ts — спільний словник обох шляхів
export type HomeId = string;
export type CommandId = string;
export type LockState = "locked" | "unlocked" | "unknown";

export interface LockCommand {
  commandId: CommandId;
  home: HomeId;
  cmd: "lock";
}

// Дві помилки хаба, які нам ВАЖЛИВО розрізняти нагорі:
export class HubOffline extends Error {}   // хаба нема на зв'язку — команду нема куди подіти
export class HubTimeout extends Error {}   // хаб мовчить — ми не знаємо, клацнув замок чи ні

// Контракт до фізичного хаба. Обидва шляхи кличуть рівно це.
// Може повернути стан, кинути HubOffline — або зависнути (тоді спрацює наш таймаут).
export interface Hub {
  send(home: HomeId, cmd: { cmd: "lock" }): Promise<{ state: LockState }>;
}
```

Одна дрібна, але принципова обгортка — власний дедлайн. Ми ніколи не чекаємо на хаб «скільки треба»: або встигли, або це `HubTimeout`. Написати її треба так, щоб таймер не лишався висіти, коли відповідь усе-таки прийшла, — інакше процес поволі забиває пам'ять мертвими таймерами.

```ts
// util.ts — власний дедлайн поверх будь-якого проміса, без «підвислих» таймерів
export function withTimeout<T>(p: Promise<T>, ms: number): Promise<T> {
  return new Promise((resolve, reject) => {
    const t = setTimeout(() => reject(new HubTimeout(`хаб мовчить ${ms} мс`)), ms);
    p.then(
      (v) => { clearTimeout(t); resolve(v); },
      (e) => { clearTimeout(t); reject(e); },
    );
  });
}
```

> 🔧 **Навіщо це.** Розрізнення `HubOffline` і `HubTimeout` — не педантизм, а серце обох шляхів. `HubTimeout` каже «я не знаю» (може, замок і зачинений) — і синхронний обробник мусить це «не знаю» повернути чесно, а не як «помилка». `HubOffline` каже «до хаба взагалі не достукатися» — і саме тут синхронний шлях безсилий (команду нема куди подіти), а асинхронний виграє (команда спокійно чекає в черзі). Один тип помилки визначає долю команди.

## Синхронний шлях, повністю

Синхронний обробник тримає запит родини відкритим, поки не почує замок, і вертає те, що почув. Уся його чесність — у гілках `catch`.

```ts
// sync-route.ts — await наскрізь; відповідь = РЕАЛЬНИЙ кінцевий стан
app.post("/homes/:id/lock", async (req, res) => {
  try {
    const r = await withTimeout(hub.send(req.params.id, { cmd: "lock" }), 5_000);
    // Дійшли до замка й почули його — вертаємо стан, який він назвав.
    res.status(200).json({ state: r.state });               // 200 «зроблено»
  } catch (e) {
    if (e instanceof HubTimeout) {
      // Таймаут — це «я не знаю», а не «не вийшло»: замок МІГ клацнути.
      res.status(504).json({ state: "unknown", reason: "хаб мовчить" });
    } else if (e instanceof HubOffline) {
      // Хаба нема на зв'язку — покласти команду нема куди. Вона програна ТУТ.
      res.status(502).json({ state: "unknown", reason: "хаб офлайн" });
    } else {
      res.status(500).json({ state: "unknown" });
    }
  }
});
```

Прочитаймо, що цей код обіцяє. За щасливого перебігу застосунок отримує `200` і в тілі — **справжній** стан замка: не «команду відправлено», а `locked`. Родина бачить правду тієї ж миті. Повільний хаб гальмує саму відповідь — і це, як ми бачили, природний зворотний тиск: ніхто не завалює хаб понад силу, бо кожен чекає своєї черги.

А тепер два `catch`, у яких і живе вся драма синхронності. `504` на таймауті — це дослівне втілення уроку про часткову відмову: ми повертаємо `state: "unknown"`, бо чесно не знаємо, чи зачинився замок. Застосунок, отримавши `unknown`, не має права намалювати ані «зачинено», ані «не вийшло» — хіба «стан невідомий, перевірте». І найгостріше — `502` на `HubOffline`: команда, яку нема кому передати, **гине прямо в цьому обробнику**. Немає буфера, який би її притримав. Родина отримає помилку негайно — і це водночас перевага (миттєва правда) і вирок (команда втрачена). Саме цю ваду асинхронний шлях і прийшов лікувати.

## Асинхронний шлях, повністю

Тепер той самий намір — але обробник більше нічого не чекає. Він приймає команду, вкидає її в чергу й одразу відповідає. Робота станеться згодом, окремим шляхом, а результат повернеться третьою дорогою. Розберімо конвеєр по ланці.

### Прийом: `202` і `commandId`

```ts
// async-enqueue.ts — приймаємо команду й ОДРАЗУ відповідаємо 202
app.post("/homes/:id/lock", async (req, res) => {
  // Ключ ідемпотентності. Якщо застосунок ретраїть той самий POST (бо 202 загубився
  // у дорозі), ми НЕ заведемо другу команду — той самий ключ = та сама команда.
  const commandId = req.header("Idempotency-Key") ?? randomUUID();

  // enqueue мусить бути ідемпотентним за commandId (upsert), а не сліпим push.
  await commands.enqueue({ commandId, home: req.params.id, cmd: "lock" });
  await status.put({ commandId, state: "accepted" });

  res.status(202)
     .location(`/commands/${commandId}`)                    // ← ось де опитувати статус
     .json({ accepted: true, commandId });                  // 202 «прийняв, спитай пізніше»
});
```

Код відповіді `202` тут не косметика, а точна назва того, що сталося. RFC 9110 визначає `202 Accepted` як «intentionally noncommittal» — навмисно ні до чого не зобов'язальний: запит **прийнято до обробки, але обробку не завершено**, і команда «може бути виконана, а може й ні». Більше того, специфікація прямо каже: у HTTP **немає** способу згодом надіслати ще одну відповідь із результатом асинхронної операції. Ось чому одного `202` замало — сам протокол відмовляється донести до нас фінал. Тому `Location` веде на окремий ендпойнт статусу, а кінцевий стан ми **самі** доставимо через нього й через твін. `202` — це чесна обіцянка «взяв», а не брехливе «зробив».

Зверніть увагу на `Idempotency-Key`. Це дедуплікація на **найпершому** стику: клієнт → хмара. Якщо відповідь `202` загубилась і застосунок повторив `POST`, той самий ключ означає ту саму команду — і `enqueue`-upsert не заведе дубль. Це той самий прийом, який далі повториться в споживача, тільки одну ланку вище.

### Журнал команд і твін

Обробник відповів, а команда ще й не почалася. Хтось мусить пам'ятати, **де вона зараз** — інакше застосунок не матиме чого опитувати. Це журнал команд: єдине джерело правди про долю кожного `commandId`. Тип запису — об'єднання, і воно саме собою малює весь життєвий цикл.

```ts
// status.ts — журнал команд: де зараз кожна команда
export type CommandRecord =
  | { commandId: CommandId; state: "accepted" }                   // у черзі, ще не взято
  | { commandId: CommandId; state: "processing" }                 // споживач узяв
  | { commandId: CommandId; state: "done"; lock: LockState }      // виконано, ось стан
  | { commandId: CommandId; state: "failed"; reason: string };    // впало остаточно

export interface StatusStore {
  put(r: CommandRecord): Promise<void>;
  get(id: CommandId): Promise<CommandRecord | undefined>;
}

// Твін дому — «остання відома правда» про дім, яку читає весь інтерфейс.
export interface Twin {
  merge(home: HomeId, patch: { lock: LockState }): Promise<void>;
}
```

Журнал і твін — різні речі, і плутати їх не можна. Журнал — про **команду** (ця конкретна спроба зачинити: прийнято → в обробці → зроблено). Твін — про **дім** (двері зараз зачинені, крапка), і його читають усі екрани, а не лише той, хто відправив команду. Споживач наприкінці оновить обидва: журнал скаже «ця команда виконана», твін — «двері зачинені».

У бойовому коді і журнал, і твін, і сховище дедуплікації нижче — це **довговічні** таблиці (Postgres, Redis), а не мапи в пам'яті: якщо процес перезапуститься, пам'ять про команди в польоті мусить пережити рестарт. Тут я лишаю за інтерфейсами саме тому, що конкретна база — деталь, а форма — ні.

### Споживач: ідемпотентний за `commandId`

Осердя всього шляху. Окремий процес тягне команди з черги й виконує їх. Головна його чеснота — переживати те, що **та сама команда прилетить двічі**. Брокер майже завжди дає [гарантію «щонайменше раз» (at-least-once)](book:programming/delivery-guarantees): краще доставити повторно, ніж загубити, — тож [дублі стають нормою, а не збігом](root:progarch/duplicates-and-reorder).

```ts
// consumer.ts — окремий процес: тягне з черги, дедуплікує, виконує ідемпотентно
commands.consume(async (c: LockCommand, ack, nack) => {
  // ── Дедуп-ворота. Той самий commandId міг уже пройти повний цикл.
  if (await processed.has(c.commandId)) {
    return ack();                 // уже виконували — тихо підтверджуємо й виходимо
  }
  await status.put({ commandId: c.commandId, state: "processing" });
  try {
    // Ефект. lock() ідемпотентна НА РІВНІ ПРИСТРОЮ — і це наш головний захист:
    // замкнути вже замкнене — то нічого не сталося (див. пастки нижче).
    const r = await withTimeout(hub.send(c.home, { cmd: "lock" }), 5_000);

    await processed.add(c.commandId);                                  // позначаємо ПІСЛЯ ефекту…
    await status.put({ commandId: c.commandId, state: "done", lock: r.state });
    await twin.merge(c.home, { lock: r.state });                       // кінцевий стан → у твін
    ack();                                                             // …і аж тепер підтверджуємо брокеру
  } catch (e) {
    // НЕ позначили як зроблене → брокер віддасть команду ще раз (повтор).
    await status.put({ commandId: c.commandId, state: "failed", reason: String(e) });
    nack();                       // після N спроб брокер сам зсуне команду в мертву чергу
  }
});

// processed — довговічне сховище вже виконаних commandId (Redis SET, таблиця з TTL…)
interface Processed {
  has(id: CommandId): Promise<boolean>;
  add(id: CommandId): Promise<void>;
}
```

Зупинімося на порядку рядків — він тут не випадковий, а вистражданий. Ми кличемо `ack` (підтвердження брокеру «команду опрацьовано, можеш забути») **найостаннішим**, уже після ефекту, запису статусу й оновлення твіна. Якби ми підтвердили раніше й тут-таки впали, брокер вважав би команду виконаною — а замок так і лишився б відчиненим, і ніхто б не дізнався. Пізній `ack` означає: доки ми не довели справу до кінця, брокер тримає команду й за потреби віддасть її знову. Це і є суть at-least-once з боку споживача: краще двічі зачинити, ніж жодного разу.

А `nack` у `catch` навмисне **не** чіпає `processed`: команда лишається «не виконаною», тож брокер віддасть її ще раз — може, наступного разу хаб оживе. І лише коли спроби вичерпаються, брокер сам відправить команду в мертву чергу, звідки її розбере людина чи фонова служба. Помилка тут не зникає й не б'є в обличчя — вона осідає збоку.

### Ендпойнт статусу і опитування

Застосунок тримає в руках `commandId` і `Location`. Тепер йому треба спосіб спитати «ну як там?». Ось він — простий, як двері.

```ts
// status-route.ts — сюди застосунок опитує, доки не побачить кінцевий стан
app.get("/commands/:commandId", async (req, res) => {
  const rec = await status.get(req.params.commandId);
  if (!rec) return res.status(404).json({ error: "невідомий commandId" });
  res.status(200).json(rec);      // accepted | processing | done{lock} | failed{reason}
});
```

І бік застосунку — те, заради чого все затівалося. Одразу після `202` він чесно каже «в обробці», а тоді опитує статус, поки не побачить `done` чи `failed`.

```ts
// app-client.ts — 202 → «в обробці» → опитуємо → кінцевий стан на екрані
async function lockDoor(homeId: HomeId): Promise<void> {
  const { commandId } = await api.post(`/homes/${homeId}/lock`).json();
  ui.badge("в обробці…");                    // одразу після 202 — чесно, бо ще НЕ зроблено

  const final = await poll<CommandRecord>(`/commands/${commandId}`, {
    ready: (r) => r.state === "done" || r.state === "failed",
    everyMs: 1_000,
    giveUpMs: 30_000,
  });

  if (final.state === "done") {
    ui.badge(final.lock === "locked" ? "зачинено" : "відчинено");
  } else {
    ui.badge("не вдалося — повторити?");      // failed або вичерпали час опитування
  }
}

// поллінг з інтервалом і дедлайном — вертає останнє, що встиг побачити
async function poll<T>(url: string,
  o: { ready: (v: T) => boolean; everyMs: number; giveUpMs: number }): Promise<T> {
  const deadline = Date.now() + o.giveUpMs;
  for (;;) {
    const v = await api.get(url).json<T>();
    if (o.ready(v) || Date.now() > deadline) return v;
    await sleep(o.everyMs);
  }
}
```

Униз від PROCESSING — гілка невдачі: якщо не позначили done, брокер повторює, а після N спроб команда йде в МЕРТВУ ЧЕРГУ, яку розбере людина. Знизу через усю ширину — нагадування: застосунок після 202 показує «в обробці», опитує GET /commands/id (або слухає твін) і міняє на «зачинено» лише коли стан = done, доти дім у кінцевій узгодженості](img/dh-async-lifecycle.svg)
*Одна кнопка — цілий конвеєр. `202` віддає застосунок на волю миттєво; справжній стан приходить згодом, третім шляхом — через журнал і твін. Дедуп-ворота на вході в обробку існують тому, що брокер чесно попереджає: доставлю щонайменше раз.*

### Опитування чи проштовхування

Опитування — найпростіший спосіб, але не єдиний і не завжди найкращий. Твін оновлює **споживач**, а читає його **весь** інтерфейс — тож замість того, щоб застосунок довбав ендпойнт раз на секунду, він може **підписатися** на твін через WebSocket чи SSE. Тоді, щойно споживач викличе `twin.merge`, новий стан замка **сам** дійде до екрана, і «в обробці» перемкнеться на «зачинено» без жодного опитування.

```ts
// app-client.ts — варіант із проштовхуванням: слухаємо твін замість опитування
twin.subscribe(homeId, (state) => {
  if (state.lock === "locked") ui.badge("зачинено");
});
```

Опитування — це «питай, поки не відповість»; підписка на твін — «сиди тихо, тобі скажуть». Обидва несуть **той самий** відкладений результат; вибір між ними — про навантаження й миттєвість, а не про зчеплення. `commandId`, до речі, живе наскрізь усім цим шляхом — від `POST` до твіна, — і саме він дає змогу [зшити розподілений слід](book:programming/distributed-tracing) однієї команди крізь усі служби.

## Поруч: три речі, що змінилися

Тепер, коли обидва шляхи повні, три компроміси видно не на словах, а в самому коді.

**Коли спливає помилка.** У синхронному обробнику збій живе в `catch` тієї самої функції — родина дізнається про нього **в тій самій відповіді**, негайно, поки чекає. В асинхронному `POST` уже повернув `202` й пішов; збій осідає в `failed`-записі та в мертвій черзі, і застосунок дізнається про нього, **лише** якщо опитає статус або слухає твін. Ніхто не заблокований — але й ніхто автоматично не повідомлений.

![Два часові пояси помилки. Угорі, синхронно: App робить POST і застрягає в смузі «заблоковано — чекає на весь ланцюг хмара→хаб→замок», у кінці якої повертається червоне 504 timeout / 502 offline зі state unknown; підпис: помилка негайна і в обличчя викликачеві, але якщо хаб офлайн — команду нема куди подіти, вона втрачена. Унизу, асинхронно: App робить POST і майже одразу отримує зелене 202 з commandId — App вільний; окремим, пізнішим шляхом «черга→споживач→hub.send» команда доходить, а якщо падає N разів — потрапляє в червону МЕРТВУ ЧЕРГУ; App дізнається про failed лише коли сам спитає GET /commands/id; підпис: ніхто не заблокований, але про збій мусить спитати хтось — поллінг, монітор або людина біля мертвої черги](img/dh-error-timing.svg)
*Синхронно помилка — миттєва й у викликача; він за неї платить чеканням, але дізнається одразу. Асинхронно помилка — відкладена й збоку; викликач вільний, але правду про збій треба активно піти й спитати.*

**Хто захищає від дубля.** У синхронному коді слова «дедуплікація» немає — і не треба: один запит, одна відповідь, повтори робить сам застосунок, свідомо. В асинхронному дедуп-ворота (`processed.has`) — обов'язковий вузол, без якого команда виконається стільки разів, скільки брокер її доставить. Захист від дубля перекочував із голови розробника прямо в код споживача.

**Коли застосунок бачить правду.** Синхронний `200` несе кінцевий стан у собі — правда й відповідь приходять разом. Асинхронний `202` не несе стану взагалі; правда доходить згодом, окремим каналом, і весь цей проміжок дім живе в [кінцевій узгодженості](book:programming/eventual-consistency): застосунок показує «в обробці», а справжній стан замка ще в дорозі. Саме тому [черга-посередник](book:programming/message-queue) дає надійність не безкоштовно — платимо відкладеною правдою.

## Складність і пастки

Начерк на чотири рядки цих ям не мав. Повний код — має, і найкраще розуміти їх до того, як на них наступиш.

**«Рівно один раз» — це міф, і `lock()` ідемпотентна недарма.** Гляньмо ще раз на споживача. Ми позначаємо `processed.add` **після** ефекту й **перед** `ack` — найобережніший з можливих порядків. Та навіть він не дає «рівно раз». Уявімо: `hub.send` уже зачинив замок, а процес упав до `processed.add` і `ack`. Брокер, не діставши `ack`, чесно віддасть команду знову — і дедуп-ворота її **не** впіймають, бо `processed` про неї так і не дізналося. Замок зачиниться вдруге. Між «зробити» і «записати, що зробив» лежить розрив, який неможливо закрити повністю: це два різні сховища (пристрій і база), і зробити їх один атомарний запис через мережу не вийде. Ось чому справжній захист — **не** дедуп-сховище, а те, що `lock()` [ідемпотентна](book:programming/idempotency) на рівні пристрою: замкнути замкнене — це нічого. Дедуп-ворота лише **дешево відсіюють** очевидні дублі, щоб не смикати хаб дарма; а гарантує коректність те, що повторний ефект нешкідливий. Якби команда була «переключити» замість «зачинити», жодне дедуп-сховище нас би не врятувало — подвійне переключення лишило б двері відчиненими.

**Дедуп-ворота теж не атомарні.** Пара `has`-потім-`add` має щілину: два повідомлення з тим самим `commandId`, які споживач узяв майже одночасно (два робітники або конкурентна обробка), обидва пройдуть `has` (обидва бачать «нема») й обидва зроблять ефект. У бойовому коді `has`+`add` згортають в **одну атомарну** операцію — `SET NX` у Redis, `INSERT … ON CONFLICT DO NOTHING` у SQL: «встав, якщо ще нема, і скажи, чи вставив». Але навіть атомарні ворота не закривають розрив «ефект стався, а мітка ще ні» з попереднього абзацу — тож ідемпотентність ефекту лишається останнім рубежем, а не розкішшю.

**`commandId` мусить народжуватися в клієнта.** Якщо `commandId` генерує сервер (`randomUUID()` без `Idempotency-Key`), то застосунок, який не дочекався `202` й повторив `POST`, заведе **другу** команду з новим id — і дедуп нижче безсилий, бо id різні. Ось навіщо `Idempotency-Key`: він робить дедуплікацію можливою на найпершому стику. Правило просте — ключ ідемпотентності мусить походити від того, хто **ретраїть**, бо тільки він знає, що це «та сама» спроба.

**Мертва черга — не смітник, а вхідні.** Команду, що впала N разів, брокер зсуває в мертву чергу — і на цьому вона тихо зникне з очей, якщо ніхто туди не дивиться. Мертва черга без моніторингу — це чорна діра для команд родини. Хтось (сповіщення, дашборд, фонова служба) мусить її читати, розбирати причину й вирішувати: повторити, скасувати, покликати людину. І стережіться **отруйних** повідомлень — таких, що падають **завжди** (крива команда, баг у споживачі): без обмеження спроб вони перевідкриваються вічно й крутять споживача вхолосту. Обмеження спроб — не примха, а запобіжник.

**Гонки статусу.** Застосунок опитує й бачить `processing`, а твін іще з попереднім станом — на частку секунди журнал і твін розходяться, бо оновлюються не однією транзакцією. Зазвичай це нешкідливо (наступний опит усе вирівняє), але інтерфейс мусить бути готовим до «команда done, а твін ще старий» і не блимати. І глибше: якщо родина встигла надіслати дві команди — «зачинити», потім «відчинити», — брокер [може переставити їх місцями](root:progarch/duplicates-and-reorder), і останній записаний у твін стан виявиться не тим, якого хотіли останнім. Порядок в асинхронному світі — окрема турбота, і `commandId` тут замало: потрібні версії чи мітки часу на самому твіні.

**`202` — це обіцянка, яку треба дотримати.** Прийняти команду означає взяти на себе відповідальність довести її до кінця **або** зробити провал видимим. `202` без працюючого ендпойнта статусу, без оновлення твіна й без нагляду за мертвою чергою — гірший за чесний синхронний `502`: там родина хоч знає, що не вийшло, а тут думає, що все гаразд, поки двері стоять відчинені. Асинхронність не звільняє від правди — вона лише переносить місце й час, де цю правду доведеться сказати.

## Що з усього цього винести

Одна кнопка, дві системи — і код показав ціну кожної краще за будь-які слова. Синхронний шлях — це одна функція з двома чесними `catch`: мало рухомих частин, миттєва правда, крихкість до всього ланцюга й програна команда, коли хаба нема. Асинхронний шлях — це чергу, журнал команд, твін, дедуп-сховище, ендпойнт статусу, поллінг чи підписка та наглянута мертва черга: система переживає падіння хаба, але тепер ти **власноруч** тримаєш усе те, що синхронний код отримував задарма від одного стека викликів.

`200` проти `202` в обробнику — то лише вершина. Під нею — цілий айсберг: хто пам'ятає стан, хто ловить дублі, хто доносить правду й хто дивиться в мертву чергу. Крок сказав, що зчеплення не зникає, а переноситься. Ось воно, перенесене, — рядок за рядком.
