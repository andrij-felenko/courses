# ⚙️ Порт пристрою: два адаптери й тест без заліза

Три питання дали шву пристрою три «так» — тепер зберімо цей порт руками й отримаймо за нього гроші. Задача вузька й конкретна: узяти зварену лінію v0 і проколоти в ній **рівно один** шов — між правилом «коли гріти» й пристроєм (давачем і розеткою). За портом поставити **два** адаптери: справжній драйвер і підробку в пам'яті. А тоді зробити те, чого [зварений v0](root:progarch/dh-v0-one-sensor) не міг узагалі, — прогнати тест правила без жодного заліза.

Пригадаймо, з чого стартуємо. Серце v0 — це рядок `if t < THRESHOLD: heater_on()`. Рішення («холодно») і дія-драйвер («увімкнути цю розетку») тут злиті в один нероздільний жест. У цьому жесті **немає імені**, яке можна було б покликати окремо, і немає **шва**, куди можна було б всунути підробку замість реального обігрівача. Тому правило й не тестувалося: щоб перевірити «коли гріти», довелося б гріти справжню кімнату. Уся робота цього кроку — дати рішенню ім'я і дати шву щілину.

## Ідея: витягти правило на чистий острів

Увесь фокус в одному русі — **назвати рішення**. Замість того щоб рішення жило безіменним усередині `if`, витягуємо його в чисту функцію: числа входять, вердикт виходить, заліза поруч немає. Це й є ядро, обведене межею, про яке говорив весь модуль, тільки тепер воно не малюнок, а функція, яку можна взяти в руку.

Порт же — це **обітниця про мову**. Ядро розмовляє градусами Цельсія й словом «гріти / не гріти», і більш нічим. Воно не мусить чути ані «мілі-градуси», ані «1-Wire», ані «Wi-Fi-розетка» — усі ці слова заліза лишаються по той бік межі. Порт саме цю обітницю й тримає, а два адаптери її сповняють кожен по-своєму: справжній перекладає мову давача на °C, підробка вдає кімнату в пам'яті.

І ось чому правило варте окремого тесту, а не є «переписуванням поля»: у ньому живе справжня логіка — **гістерезис** (гр. *hystéresis* — відставання). У v0 грілка вмикалася й гасла рівно на порозі, тож коло самого порога, де шум вимірювання гойдає число туди-сюди, реле клацало щотакту — та сама біда, від якої драйвери v0 боронилися прапорцем `if not _heater`. Чесне правило «коли гріти» тримає не крапку, а **смугу**: увімкнутись, коли впало під поріг, і не гасити, доки не перегрілося на пів градуса вище. Оце «пів градуса пам'яті» і є те коштовне ядро, яке хочеться перевірити, не вмикаючи обігрівач на пів години.

## Правило як острів

Ось воно — усе ядро рішення, самими числами:

:::tabs
```py
THRESHOLD = 20.0      # °C — нижче цього холодно (те саме число, що у v0)
HYSTERESIS = 0.5      # °C — наскільки перегріти понад поріг, перш ніж гасити

def should_heat(t: float, heating: bool,
                threshold: float = THRESHOLD, band: float = HYSTERESIS) -> bool:
    if heating:
        return t < threshold + band   # уже гріємо — тримаємо, доки не перескочили верх смуги
    return t < threshold              # ще не гріємо — вмикаємо, тільки-но впало під поріг
```
```ts
const THRESHOLD = 20.0;    // °C — нижче цього холодно (те саме число, що у v0)
const HYSTERESIS = 0.5;    // °C — наскільки перегріти понад поріг, перш ніж гасити

function shouldHeat(t: number, heating: boolean,
                    threshold = THRESHOLD, band = HYSTERESIS): boolean {
  if (heating) return t < threshold + band;  // гріємо — тримаємо, доки не перескочили верх смуги
  return t < threshold;                       // ще ні — вмикаємо, тільки-но впало під поріг
}
```
:::

Придивіться, у чому тут пам'ять. Візьміть температуру рівно 20.3 °C. Якщо ми **вже гріли**, `should_heat` каже «так, гріємо далі» — бо 20.3 ще не перескочило верх смуги 20.5. Якщо ж ми **не гріли**, та сама 20.3 дає «ні» — бо вона вже над порогом 20.0. **Одна температура, дві різні відповіді** — залежно від того, що робили мить тому. Саме ця залежність від попереднього стану і глушить клацання: між «увімкнув» і «вимкнув» лежить ціла смуга в пів градуса, яку треба пройти, а не тонка риска, об яку шум б'ється щосекунди.

І от чому це ядро не перевіриш на живому обігрівачі: щоб дійти до межі смуги, справжня кімната гріється й холоне хвилинами, кожен тест — пів години чекання, а відтворити «рівно 20.5 на спаді» за бажанням ти взагалі не можеш. Логіку, яка вся про поведінку на межах, можна чесно ганяти лише там, де межі підставляєш сам. Отже — потрібен пристрій, якого можна підмінити.

## Порт і два адаптери

Тепер сама межа й обидві її сторони. Порт оголошує, що ядро вміє питати в пристрою, а два класи цю обіцянку тримають — один справжнім залізом, другий пам'яттю:

:::tabs
```py
from typing import Protocol

class Device(Protocol):              # ПОРТ — давач і розетка одним отвором, мовою ядра
    def temperature(self) -> float: ...   # °C, не мілі-градуси й не вольти
    def heat(self, on: bool) -> None: ...

# ── Адаптер 1: СПРАВЖНІЙ. Єдиний в усьому хабі, хто говорить мовою заліза. ──
import urllib.request

class RealDevice:                    # 1-Wire давач + Wi-Fi розетка (напр. Shelly)
    def __init__(self, w1_id: str, plug_url: str):
        self._w1 = f"/sys/bus/w1/devices/{w1_id}/w1_slave"
        self._plug = plug_url

    def temperature(self) -> float:
        text = open(self._w1).read()          # "...crc=.. YES\n.. t=20125"
        milli = int(text.split("t=")[-1])     # DS18B20 віддає мілі-градуси
        return milli / 1000.0                 # → °C ТУТ, на межі; далі ядро °C і не бачить іншого

    def heat(self, on: bool) -> None:
        turn = "on" if on else "off"
        urllib.request.urlopen(f"{self._plug}/relay/0?turn={turn}", timeout=3)

# ── Адаптер 2: ПІДРОБКА. Кімната живе в пам'яті + пише журнал команд. ──
import random

class FakeDevice:
    def __init__(self, start: float = 18.0):
        self._room = start           # прихований «фізичний» стан, як у моку v0
        self._on = False
        self.log: list[bool] = []    # журнал переходів — щоб тест мав що перевірити

    def temperature(self) -> float:
        self._room += (0.4 if self._on else -0.2) + random.uniform(-0.05, 0.05)
        return round(self._room, 1)

    def heat(self, on: bool) -> None:
        if on != self._on:           # записуємо лише реальні перемикання
            self.log.append(on)
        self._on = on
```
```ts
// ПОРТ — давач і розетка одним отвором, мовою ядра
interface Device {
  temperature(): Promise<number>;   // °C, не мілі-градуси й не вольти
  heat(on: boolean): Promise<void>;
}

// ── Адаптер 1: СПРАВЖНІЙ. Єдиний в усьому хабі, хто говорить мовою заліза. ──
import { readFile } from "node:fs/promises";

class RealDevice implements Device {                 // 1-Wire давач + Wi-Fi розетка
  constructor(private w1: string, private plugUrl: string) {}

  async temperature(): Promise<number> {
    const text = await readFile(`/sys/bus/w1/devices/${this.w1}/w1_slave`, "utf8");
    const milli = parseInt(text.split("t=").pop()!, 10);  // DS18B20 → мілі-градуси
    return milli / 1000;                                  // → °C ТУТ, на межі
  }

  async heat(on: boolean): Promise<void> {
    await fetch(`${this.plugUrl}/relay/0?turn=${on ? "on" : "off"}`);
  }
}

// ── Адаптер 2: ПІДРОБКА. Кімната живе в пам'яті + пише журнал. ──
class FakeDevice implements Device {
  private room: number;
  private on = false;
  readonly log: boolean[] = [];       // журнал переходів для тесту

  constructor(start = 18.0) { this.room = start; }

  async temperature(): Promise<number> {
    this.room += (this.on ? 0.4 : -0.2) + (Math.random() - 0.5) * 0.1;
    return Math.round(this.room * 10) / 10;
  }

  async heat(on: boolean): Promise<void> {
    if (on !== this.on) this.log.push(on);   // лише реальні перемикання
    this.on = on;
  }
}
```
:::

Затримаймося на одному рядку `RealDevice`, бо в ньому — увесь сенс порту. Давач DS18B20 віддає температуру не градусами, а **цілим числом мілі-градусів**: `t=20125` означає 20.125 °C (так його показує ядро Linux у файлі `w1_slave`). Це той самий давач, чия «інша мова» тихо зламала v0, коли ми міняли вендора: там `18000` порівнювалося з `20.0`, завжди виходило «не холодно», і вітальня мовчки вистигала. Тепер ділення на 1000 живе **в адаптері, на самій межі** — і жоден мілі-градус за поріг не просочується. Ядро отримує чисті °C і не підозрює, що по той бік хтось рахує тисячними. Підробка ж бере фізику кімнати просто з [моку робочого v0](root:progarch/dh-v0-one-sensor/proj-dh-v0.md) — кімната холоне сама, гріється під струмом, — і додає одне: **журнал** переданих команд, щоб тестові було на що глянути. Обидва класи чесно тримають форму `Device`, і ядро їх не розрізняє — а це і є перевірка на справжній порт, яку ми обговорювали: під нього стає і залізо, і пам'ять.

## Точка збірки

Лишилося зшити це в хаб — і показати місце, де в проді на слот підробки стає реальний давач:

:::tabs
```py
from time import sleep
import os

def tick(device: Device, heating: bool) -> bool:
    t = device.temperature()          # read
    heating = should_heat(t, heating) # decide — чисте правило, байдуже до заліза
    device.heat(heating)              # act
    return heating

def run(device: Device) -> None:      # прод: вічний цикл, точнісінько як серце v0
    heating = False
    while True:
        heating = tick(device, heating)
        sleep(30)

def build_device() -> Device:         # ТОЧКА ЗБІРКИ — єдине місце, що знає, хто за портом
    if os.getenv("DH_ENV") == "prod":
        return RealDevice("28-0119a1b2c3d4", "http://192.168.1.50")
    return FakeDevice()               # усюди, крім проду, — дім у пам'яті

if __name__ == "__main__":
    run(build_device())               # у проді сюди стане RealDevice — і код вище не здригнеться
```
```ts
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function tick(device: Device, heating: boolean): Promise<boolean> {
  const t = await device.temperature();   // read
  heating = shouldHeat(t, heating);        // decide — чисте правило
  await device.heat(heating);              // act
  return heating;
}

async function run(device: Device): Promise<void> {  // прод: вічний цикл, як серце v0
  let heating = false;
  while (true) {
    heating = await tick(device, heating);
    await sleep(30_000);
  }
}

function buildDevice(): Device {          // ТОЧКА ЗБІРКИ — одне місце, що знає, хто за портом
  if (process.env.DH_ENV === "prod")
    return new RealDevice("28-0119a1b2c3d4", "http://192.168.1.50");
  return new FakeDevice();                // усюди, крім проду, — дім у пам'яті
}

run(buildDevice());                       // у проді сюди стане RealDevice — і код вище не здригнеться
```
:::

Серце циклу — ті самі три слова, що й у v0: **прочитати → вирішити → зробити**. Але тепер «вирішити» — це виклик названого правила `should_heat`, а «прочитати» й «зробити» ходять через порт `device`, а не в конкретне залізо. І вся інформація про те, **хто** саме той `device`, стиснута в один-єдиний вузол — `build_device`. Це [точка збірки (composition root)](topic:sf-apps/di-container): місце, де абстрактні порти зустрічають конкретні реалізації, і воно навмисне одне на весь застосунок. У проді змінна оточення каже «prod» — і в слот стає `RealDevice` зі справжнім давачем і справжньою розеткою. Скрізь інде — `FakeDevice`. Рядок `run(build_device())` не міняється ані на символ: хаб дістає щось, що вміє `temperature` і `heat`, а звідки воно взялося — не його клопіт.

## Тест без заліза

Тепер — те, заради чого все й робилося. Два тести, і жодному не потрібні ані давач, ані розетка, ані нагріта кімната:

:::tabs
```py
# test_hub.py — ті самі should_heat і FakeDevice з hub.py; біжить будь-де

def test_rule_holds_the_band():          # ТЕСТ 1: чисте правило, взагалі без пристрою
    assert should_heat(19.9, heating=False)       # холодно — вмикаємо
    assert should_heat(20.3, heating=True)        # у смузі й гріли — тримаємо
    assert not should_heat(20.6, heating=True)    # перескочили верх — гасимо
    assert not should_heat(20.3, heating=False)   # та сама 20.3, та вже вимкнено — НЕ вмикаємо
    # два останні рядки — одна температура, різні відповіді: оце й є пам'ять, що глушить клацання

def test_rule_against_the_fake():        # ТЕСТ 2: правило проти ПІДРОБКИ, без грама заліза
    home = FakeDevice(start=17.0)        # старт нижче за поріг — дім холодний
    heating = False
    for _ in range(80):                  # ~40 хв життя «дому» за частку секунди
        t = home.temperature()           # read  — з пам'яті, не з давача
        heating = should_heat(t, heating) # decide
        home.heat(heating)               # act   — у журнал, не в реле
        # інваріант гістерезису мусить триматися НА КОЖНОМУ такті:
        if t < THRESHOLD:                assert heating       # під порогом — тільки гріти
        if t > THRESHOLD + HYSTERESIS:   assert not heating   # над смугою — тільки гасити
    assert home.log[0] is True           # холодний старт → перша ж дія «ввімкнути»
    assert False in home.log             # кімната прогрілась і таки вимкнулась
```
```ts
// test_hub.ts — ті самі shouldHeat і FakeDevice з hub.ts; біжить будь-де
import assert from "node:assert";

// ТЕСТ 1: чисте правило, взагалі без пристрою
assert(shouldHeat(19.9, false));        // холодно — вмикаємо
assert(shouldHeat(20.3, true));         // у смузі й гріли — тримаємо
assert(!shouldHeat(20.6, true));        // перескочили верх — гасимо
assert(!shouldHeat(20.3, false));       // та сама 20.3, та вже вимкнено — НЕ вмикаємо

// ТЕСТ 2: правило проти ПІДРОБКИ, без грама заліза
async function testAgainstFake() {
  const home = new FakeDevice(17.0);     // старт нижче за поріг — дім холодний
  let heating = false;
  for (let i = 0; i < 80; i++) {         // ~40 хв «дому» за частку секунди
    const t = await home.temperature();  // read  — з пам'яті
    heating = shouldHeat(t, heating);    // decide
    await home.heat(heating);            // act   — у журнал, не в реле
    if (t < THRESHOLD)               assert(heating);   // під порогом — тільки гріти
    if (t > THRESHOLD + HYSTERESIS)  assert(!heating);  // над смугою — тільки гасити
  }
  assert.strictEqual(home.log[0], true); // холодний старт → перша дія «ввімкнути»
  assert(home.log.includes(false));      // кімната прогрілась і таки вимкнулась
}
testAgainstFake();
```
:::

Перший тест бере саме правило й тицяє в його межі — під поріг, у смугу, над смугою — і все це за мілісекунду, без нічого, крім чотирьох чисел. Він сам-один відповідає на друге з трьох питань: «чи є що тестувати в ядрі без інфраструктури?» Ось воно, зелене, у тебе перед очима.

Другий тест ставить підробку на місце пристрою й **проганяє весь цикл** прочитати → вирішити → зробити — вісімдесят тактів, тобто дому десь пів години життя, за частку секунди. Кімната стартує холодною, правило її гріє, вона переходить смугу, правило гасить — і на **кожному** такті тест перевіряє головний інваріант гістерезису: під порогом грілка мусить бути ввімкнена, над смугою — вимкнена. Жодного дроту, жодного очікування, жодної нагрітої кімнати.

> 🔧 **Навіщо це.** Уся цінність цього порту вміщується в один факт: **цей тест існує**. Проти v0 його не можна було навіть почати — не тому, що бракувало вміння, а тому, що не було **за що взятися**. У рядку `if t < THRESHOLD: heater_on()` немає імені `should_heat`, яке можна покликати з тесту, і немає щілини, куди підставити `FakeDevice` замість справжньої розетки. Правило й драйвер зварені, тож ізолювати правило неможливо в принципі. Порт не зробив тест приємнішим — він зробив його **можливим**. За це — і тільки за це — платять непрямотою одного інтерфейсу.

## Складність і пастки

Перша пастка — та сама, що й у v0: підробка **чемніша за залізо**. `FakeDevice` завжди віддає свіже число, ніколи не зволікає, не повертає сміття з поганою контрольною сумою, не відпадає з таймаутом. Реальні `RealDevice.temperature` і `heat` усе це вміють. Але тут порт несподівано грає на нас: коли захочеться перевірити, як хаб тримається під збоями, це буде **третій** адаптер — `FlakyDevice`, що кидає виняток чи зависає, — і він стане в той самий отвір, що й два наші. Шов, який ми проклали заради тесту правила, задарма дає й тестованість збоїв. Це частина того, що купив порт.

Друга пастка — **де саме сидить межа**. Переклад мілі-градусів у °C ми поклали в адаптер, і це не дрібниця стилю: щойно мілі-градус просочиться крізь порт у ядро, шов стає декоративним, а тихий баг v0 повертається — ядро знову порівнює `18000` з `20.0`. Порт справжній рівно доти, доки ядро **ніколи** не бачить одиниць заліза. Межа коштує уваги на кожному адаптері: усе, що пахне вендором, лишається зовні.

Третя ховається в чистоті правила. `should_heat` чисте **лише тому**, що стан `heating` йому передають ззовні. Спокуса сховати цей прапорець у глобальну змінну всередині функції велика — і згубна: правило стане зі станом, а тести — залежними від порядку й крихкими, бо один потягне за собою слід іншого. Чистота тут не косметика, а те, на чому тест стоїть; стан живе на краю, у циклі, а не в ядрі.

І остання, найважливіша поправка — **не перечитати перемогу**. Цей порт купив дві речі й рівно на **одному** шві: тестоване правило й свободу поміняти вендора давача. Він **не** зробив Digital Homes «гексагональним проєктом». Бік драйверів — HTTP чи CLI, хто гукає хаб, — і далі прямий виклик без жодного порту, і так правильно, доки той бік не відростить собі другий годинник. Один справжній шов — один порт. Ні більше.

Отож повернімося до трьох питань, з якими ми до цього шва підійшли, — і побачимо, що кожне «так» тепер не обіцянка, а рядок коду. **Є справжня друга реалізація?** Так — ти щойно ганяв її (`FakeDevice`), а наступний вендор давача стане поруч третім. **Є що тестувати в ядрі без інфраструктури?** Так — гістерезис, доведений зеленим, не нагрівши й кутка кімнати. **Різні годинники?** Так — `should_heat` міняється за продуктовим годинником, `RealDevice` за апаратним, а порт між ними — підшипник, що дає кожному крутитися вільно. Три «так» поспіль, і порт окупився на першому ж шві, що їх заслужив. Цей файл — розписка про сплату.
