# Варіант Б: рішення ухвалює один центр

<preknowlist>
- [Моделі авторизації](book:programming/authorization-models) — як записати правило «кому що можна»: ролями (RBAC), атрибутами (ABAC), зв'язками (ReBAC). Цей крок знову не про те, *як* записати правило, а про те, *де* його тримати й обчислювати.
- [Варіант А: кожен сервіс авторизує сам](root:progarch/authz-inservice-variant) — парна половина розвилки: словник «точка рішення (PDP) / точка застосування (PEP)» і головна ціна вшитого правила — дублювання й дрейф, які Варіант Б і намагається прибрати.
</preknowlist>

У [Варіанті А](root:progarch/authz-inservice-variant) ми боронили найпростіше: хай кожен сервіс вирішує сам, поруч із даними, які він захищає. Він купив найдешевшу у світі об'єктну перевірку — але заплатив одним коренем ціни: **правило живе всередині сервіса, тож копіюється стільки разів, скільки сервісів його потребують**. Копії розповзаються в дрейф; немає одного місця, де відповісти «хто має доступ до камер спальні?»; різномовний флот тримає те саме правило у трьох мовах руками.

Варіант Б — чесний антипод тієї ж розвилки, і ми знову боронимо його в найсильнішій формі, щоб згодом важити чесно. Він бере той самий корінь і перевертає його: **виймає рішення з кожного сервіса й зводить в один центр, який питають усі**. Якщо весь біль А виріс із «правило скопійоване N разів», то весь виграш Б росте з дзеркального «правило одне — і воно одне».

## Один PDP на всіх

Пригадаймо різницю, яку ми вже провели у Варіанті А: **точка рішення** (PDP) — де вердикт *ухвалюють*; **точка застосування** (PEP) — де його *застосовують*: відчинити замок або відмовити. Варіант А звів їх в один процес. Варіант Б розводить їх назад — але не абияк, а до **одного спільного центру**: PEP лишається в кожному сервісі, а PDP стає один на всіх.

Тепер кожен сервіс тримає в себе лише гейт: зупинити запит і спитати центр — «чи можна цьому суб'єктові цю дію над цим об'єктом?». Сам вердикт обчислює окремий **сервіс авторизації**, де й живе правило — одне, для всіх. Виклик `can(...)`, що у Варіанті А був локальною функцією, тут стає походом до сусідньої коробки:

:::tabs
```ts
// Сервіс пристроїв: обробник «відчинити замок». Гейт (PEP) лишився тут,
// але рішення (PDP) — уже не тут: його питають у центрального сервіса.
async function unlockDoor(req: Request, res: Response) {
  const door = await devices.load(req.params.id);   // об'єкт іще під рукою

  const verdict = await authz.check({               // ← стрибок у центр
    subject: req.user.id,                            // хто: Богдан
    action: "unlock",                                // що: відчинити
    resource: `door:${door.id}`,                     // над чим: замок #42
    context: { homeId: door.homeId },                // факти для рішення — з собою
  });

  if (!verdict.allow) return res.status(403).json({ error: "forbidden" });
  await door.unlock();
  res.json({ ok: true });
}
```
```go
// Сервіс пристроїв: гейт (PEP) лишився локальним, а рішення (PDP) — за мережею.
func UnlockDoor(w http.ResponseWriter, r *http.Request) {
    door, _ := devices.Load(r.PathValue("id")) // об'єкт іще під рукою

    verdict, err := authz.Check(r.Context(), Decision{ // ← стрибок у центр
        Subject:  user(r).ID,                          // хто: Богдан
        Action:   "unlock",                            // що: відчинити
        Resource: "door:" + door.ID,                   // над чим: замок #42
        Context:  map[string]any{"homeId": door.HomeID}, // факти — з собою
    })
    if err != nil || !verdict.Allow { // помилка теж означає «ні» (про це нижче)
        http.Error(w, "forbidden", http.StatusForbidden)
        return
    }
    door.Unlock()
    writeJSON(w, ok{true})
}
```
:::

Придивись, що поїхало в центр і що лишилося. Лишилося **застосування**: 403 або відчинити. Поїхало **рішення** — і разом із ним правило. А сам запит до PDP — це маленький, майже беззмістовний на вигляд документ:

```
→ запит рішення           ← відповідь
{ subject:  "Богдан",     { allow: false,
  action:   "unlock",       reason: "не член дому 7" }
  resource: "door:42",
  context:  { homeId: 7 } }
```

![Три сервіси ліворуч тримають лише гейт (PEP) і всі питають один центральний сервіс авторизації праворуч, де правило лежить в одному місці; у Варіанті А рішення жило в кожному процесі — тут воно винесене в спільний центр](/root/course/progarch/authz-central-variant/img/pdp-split.svg)
*Топологію перевернуто: кожен сервіс лишає собі лише застосування (PEP), а рішення (PDP) — одне на всіх. Правило більше не копіюється — воно живе в центрі в одному примірнику.*

## Головний виграш: правило одне — і воно одне

Чому за це беруться? Три виграші сходяться в тому «одне».

**Кінець дрейфу.** Правило «член дому + відповідна роль → можна» більше не вписане в чотири сервіси — воно записане один раз, у центрі. Захотів змінити — «гостям можна відчиняти з 8:00 до 22:00» — правиш **в одному місці**, і всі сервіси одразу бачать нову версію. Немає N копій, які треба вручну зводити до літери; немає тихого шансу, що одну проґавив.

**Єдиний погляд і аудит.** На питання «хто має доступ до камер спальні?» тепер є **одне** місце, де відповісти, — той самий центр. Рев'ю безпеки, аудит, запит про приватність перестають бути розкопками по N кодових базах і стають одним запитом. Ба більше: центр — природне місце для **журналу рішень**: кожен «дозволено/відмовлено» проходить крізь нього, тож маєш повний слід, хто що просив і що відповіли.

**Кінець податку поліглота.** Правило тепер записане один раз — [політикою як кодом](book:programming/policy-as-code): у власній мові рушія (Rego в OPA, мова Cedar) або як граф зв'язків. Python-сервіс, Go-сервіс і TypeScript-сервіс усі питають **той самий** PDP і дістають **ідентичний** вердикт. Правило більше не існує у трьох мовах, які треба тримати однаковими руками, — воно існує в одній.

> 🔧 **Навіщо це.** Найдорожчий момент авторизації в дорослій системі — не «написати правило», а **довести, що воно однакове скрізь**. Коли аудитор питає «покажіть, що *усі* шляхи до медичних даних однаково перевіряють згоду», у Варіанті А ти йдеш читати кожен сервіс; у Варіанті Б ти показуєш **одну** політику й один журнал рішень. Ти платиш стрибком і новою залежністю (нижче), щоб купити цю єдину відповідь. Для системи під аудитом чи відповідність це часто вирішальний виграш.

## Хто возить це в проді

Це не теорія — це ціла індустрія. Загальні рушії політик виносять **правило**: Open Policy Agent (OPA) — проєкт, що народився 2016-го в Styra й [2021 року першим у CNCF випустився саме як інструмент авторизації](root:progarch/authz-central-variant/hist-zanzibar-lineage.md), з власною мовою політик Rego; AWS Cedar (відкритий 2023-го) живить Amazon Verified Permissions. Інша гілка виносить не правило, а **дані відносин**: її задала стаття Google *Zanzibar* (2019) — система, що тримає авторизацію для Docs, Drive, Calendar, YouTube в одному місці. За нею пішла хвиля відкритих реалізацій — SpiceDB від AuthZed, OpenFGA (Auth0/Okta, у CNCF із 2022-го), Ory Keto. [Історію того, як потреба Google в одній узгодженій авторизації на всі продукти народила Zanzibar, а за ним — цілий клас систем](root:progarch/authz-central-variant/hist-zanzibar-lineage.md), варто знати окремо: вона пояснює, чому «центр» буває про політику, а буває про дані — і чому це дві дуже різні ціни.

## Чим платиш

Тепер — найважливіший рядок. І вся ціна Варіанта Б росте з одного кореня, дзеркального до А: **рішення тепер живе по той бік межі — далі від даних і за окремим викликом (часто за мережею).**

**Мережевий стрибок і хвіст затримки.** Вердикт більше не виклик функції, а запит до іншої коробки. Кожен запит користувача тепер чекає ще й на PDP — і [цілий клас відмов, який Варіант А знімав](book:programming/distributed-fallacies), повертається: мережа не миттєва, не завжди надійна, має свій хвіст. До твоєї затримки додається кругова дорога в центр і назад — стільки, скільки коштує **найповільніший** похід, бо на хвіст дивляться за найгіршими, а не середніми.

**Нова залежність, що може впасти.** Найгостріша операційна ціна. Якщо PDP недосяжний — що робить сервіс? Дві відповіді, обидві погані. **Fail-open** (пропустити) — і твоя авторизація відмикається саме тоді, коли найпотрібніша: дірка. **Fail-closed** (відмовити) — безпечно, але тепер **весь** застосунок падає разом із PDP: один сервіс став точкою, від живості якої залежить усе. Синхронна залежність ще й множить відмову:

```
A_разом = A_сервіс × A_PDP
99.9% × 99.9% ≈ 99.8%     ← удвічі більше простою, ніж було
```

Тому центр майже ніколи не буває голим: його реплікують, ставлять перед ним [запобіжник із розумним fallback](book:programming/circuit-breaker-pattern), а вердикти [кешують](book:programming/caching-strategies) — щоб пережити і хвіст, і коротку недосяжність. А кеш тягне за собою власну, найтоншу ціну (нижче).

**Проблема даних для рішення.** Найглибша ціна — і точне дзеркало виграшу Варіанта А. Згадай, чому А так легко закривав [IDOR](root:progarch/idor-horizontal-escalation): об'єкт був **у руках**, тож перевірка бачила і Богдана, і сам замок #42 з його `homeId`. Центральний PDP бачить лише сухий запит: «Богдан, unlock, door:42». Він **не знає**, чий це замок 42 і чи Богдан — член дому 7, бо ці факти живуть не в ньому, а в сервісі пристроїв і сервісі домогосподарств. Щоб вирішити, PDP мусить ці факти **звідкись узяти** — і тут лише два виходи, обидва з ціною.

![Центральний PDP отримав запит «Богдан · unlock · door:42», але для вердикту йому бракує двох фактів — чий це замок і чи Богдан член дому 7; ці факти живуть у сервісі пристроїв і сервісі домогосподарств, тож PDP мусить або дотягтися по них, або отримати їх у контексті запиту](/root/course/progarch/authz-central-variant/img/decision-data-gap.svg)
*Центр знає запит, але не знає фактів — вони живуть у сервісах. Або PEP везе факти в контексті запиту (як `homeId` у коді вище), або центр тримає власну копію графа зв'язків — і тоді централізувати авторизацію означає централізувати ще й дані.*

Або **PEP везе факти з собою** в контексті запиту — так робив код вище, підклавши `homeId`. Дешево, поки фактів мало; але хто гарантує, що клієнт не збрехав про `homeId`, і що робити, коли правило спирається на дані з трьох різних сервісів воднораз? Або **центр тримає власну копію** потрібних зв'язків — членства, власності, ролей — і тоді централізувати авторизацію означає ще й **зливати в центр дані з усіх сервісів**, з усією застарілістю, яку такий злив тягне. Саме цю другу дорогу й проклав Zanzibar: він робить центр сховищем **кортежів зв'язку** (relation tuple) виду `door:42#owner@home:7` — і сам стає джерелом правди про «хто з чим пов'язаний».

**Консистентність кешу — і «новий ворог».** Ми кешуємо вердикти, щоб пережити стрибок. Але застарілий вердикт авторизації — це не просто несвіжість, це **діра або хибна відмова**. Найнебезпечніший бік — **відкликання**: вигнали мешканця з дому, а кеш ще хвилину віддає старе «дозволено» — і виключений усе ще відчиняє двері. Є й тонший різновид, який у Zanzibar назвали **проблемою нового ворога** (new enemy problem): відкликаєш комусь доступ, потім додаєш у ту саму теку новий документ — а застаріла перевірка застосує стару, ще щедру ACL до нового вмісту. Це вже не про TTL, а про **порядок** подій. Zanzibar розв'язав це через zookie — непрозорий токен-знімок причинності, який змушує наступну перевірку поважати порядок, у якому міняли доступ і вміст. Мораль проста: щойно центр кешує, він мусить думати не лише «наскільки свіжо», а й [«у якому порядку»](book:programming/consistency-models) — інакше центр, що мав дати *суворіший* контроль, тихо дає *слабший*.

## Три способи «винести в центр»

Тут ховається головна тонкість, без якої вибір несправедливий: **«централізувати» — це не одне рішення, а три різні**, залежно від того, *що саме* ти зводиш у центр. Плутати їх — значить приписувати одному варіанту ціну іншого.

**Центр вирішує (мережевий PDP).** Найпряміша модель — та, що в коді вище: PEP на кожен вердикт ходить у центральний сервіс рішень. Найясніша в голові, але й з повним рахунком — стрибок на кожен запит і залежність від живості центру.

**Центр — політику, оцінка локальна.** Хитріша й дуже популярна модель: у центрі живе й редагується **правило**, але роздається воно на місця (OPA як sidecar поруч із кожним сервісом отримує «бандл» політики), і кожен сервіс **оцінює локально** — без походу по мережі на кожне рішення. Так знімається і стрибок, і залежність від центру в гарячому шляху; лишається проблема даних — локальній оцінці потрібні локальні факти. Це «і вовки ситі» середина: політика одна, дрейфу немає, а рішення знову швидке.

**Центр — дані відносин.** Zanzibar-гілка виносить не правило, а **граф зв'язків**: усі кортежі «хто з чим пов'язаний» мають один дім, сервіси туди пишуть, а перевірки — читають. Це єдина модель, що по-справжньому закриває «правило тягнеться через ресурси різних сервісів» і «єдиний погляд на доступ». Ціна — злити дані в центр і тримати ту саму машинерію причинності (zookie), щоб кеш не збрехав.

![Три вертикальні панелі: ліворуч центр ухвалює рішення (PEP ходить по мережі до центрального PDP), посередині центр тримає політику й роздає її бандлами в sidecar-и, де оцінка локальна, праворуч центр тримає граф кортежів зв'язку, куди сервіси пишуть і звідки перевірки читають](/root/course/progarch/authz-central-variant/img/three-ways-central.svg)
*Один заголовок «Варіант Б» — три різні архітектури з різними цінами. Питання не «централізувати чи ні», а «централізувати рішення, політику чи дані».*

## Де виграє, а де стіна

Зведімо в одне чесне речення. Варіант Б **сяє**, коли сервісів багато, флот поліглотний, правила тягнуться через ресурси різних сервісів, а аудит і відповідність вимагають **одного** місця, де відповісти «кому що можна» й показати повний журнал рішень. Він **упирається в стіну**, коли сервіс один чи їх кілька (стрибок і зайва критична залежність нічого не купують), коли бюджет затримки не має місця ні на похід, ні на вікно застарілості кешу, або коли команда замала, щоб надійно тримати ще один сервіс рівня «впав — упало все».

Чутлива точка, що перемикає вибір, — дзеркальна до А: **чи спирається рішення на дані більш ніж одного сервіса, і чи потрібен один погляд на «хто що може»?** Так — центр окупається. Ні — центр лишається накладними витратами поверх того, що А робив дешевше й ближче.

## Зворотність: наскільки це двері в один бік

Остання лінза — та сама, що в А. На рівні **коду** перехід у центр напрочуд зворотний, якщо ти послухався Варіанта А й сховав перевірку за [швом](root:progarch/seams-and-boundaries) — єдиним `Authorizer.can(user, action, resource)`, крізь який ходять усі обробники. Тоді замінити локальне рішення на виклик центру — це одна нова реалізація того самого інтерфейсу, не чіпаючи жодного хендлера. Саме тому ми будували А за швом із першого дня.

Але не сплутай зворотність коду зі зворотністю **рішення**. Код за швом перемкнути легко; важко відкотити операційну ставку. Піднявши центр, ти завів сервіс рівня «tier-0» — впав він, лягла авторизація всюди; завів (у Zanzibar-гілці) конвеєри зливу даних, які тепер треба живити й звіряти. Це вже не однорядкова зміна, а інфраструктура, яку тримають командою. Тож формула чесна: **код Варіанта Б — зворотний за швом; операції Варіанта Б — важка й радше однобічна ставка**. Перше робить експеримент дешевим; друге вимагає, щоб драйвери справді того просили.

І саме це важить наступний крок. Ані А, ані Б не виграє в порожнечі — [підсумковий вибір](root:progarch/authz-choice) прожене обидва крізь [спільні сценарії якості](book:programming/attribute-scenarios) DH і, найпевніше, складе з них **гібрид**: об'єктну перевірку лишить у сервісі (де А непереможний), а політику й граф доступу винесе в центр (де сяє Б). А тоді ми проведемо один живий запит Богдана [крізь усю дорогу авторизації DH](root:progarch/dh-auth-path) — від гейта до вердикту — і побачимо обидва варіанти на роботі в одному ланцюжку. Щоб той гібрид не був схемою на папері, [збери центральний шлях DH руками](root:progarch/authz-central-variant/proj-dh-central-authz.md): виклик до PDP, кеш вердиктів із чесним вікном застарілості й fail-closed, коли центр мовчить.
