# 🧮 Математична модель атрибуції юніт-косту та маржинальних витрат

Ця вставка формалізує математичний апарат обчислення юніт-вартості (англ. *unit cost*), маржинальних витрат на транзакцію, статистичної значущості фінансових регресій та побудови матриці чутливості під час аналізу змін у CI/CD. Вона дає кількісне підґрунтя для налаштування порогових значень у фітнес-функціях вартості та оцінки фінансового ризику архітектурних рішень.

## 1. Загальна функція витрат інфраструктури

Сукупна вартість обчислювальної інфраструктури `C_total` за фіксований часовий інтервал `T` (наприклад, один календарний місяць або одну годину) складається з постійної базової частини `C_fixed` та динамічної частини, залежної від обсягу споживаних ресурсів:

```
C_total(T) = C_fixed + ∑ [ c_i · R_i(N) ]
```

де:
- `C_fixed` — фіксовані витрати на інфраструктуру, що не залежать від поточного навантаження (наприклад, зарезервовані базові екземпляри баз даних, накладні витрати на контрольну площину Kubernetes, базові плати за сертифікати чи NAT-шлюзи);
- `R_i(N)` — обсяг споживання ресурсу `i`-го типу (процесорні ядра CPU, оперативна пам'ять RAM, дискові операції IOPS, мережевий вихідний трафік Egress) при обробці `N` бізнес-транзакцій;
- `c_i` — одинична ціна `i`-го ресурсу згідно з каталогом хмарного провайдера (наприклад, `\$0.0416` за vCPU-годину або `\$0.09` за 1 ГБ вихідного трафіку).

Фіксована складова `C_fixed` забезпечує готовність системи до роботи, але створює високу початкову вартість при малих обсягах трафіку. Динамічна складова `∑ [ c_i · R_i(N) ]` масштабується разом із зростанням кількості користувачів та транзакцій.

## 2. Юніт-вартість та маржинальна вартість транзакції

Середня юніт-вартість однієї бізнес-транзакції `U_cost` обчислюється як відношення загальних витрат інфраструктури до кількості оброблених транзакцій `N`:

```
U_cost(N) = C_total(N) / N
          = (C_fixed / N) + (1 / N) · ∑ [ c_i · R_i(N) ]
```

При малих обсягах навантаження `N → 0` значення `U_cost` прямує до нескінченності через домінування фіксованої складової `C_fixed / N`. При зростанні навантаження `N → ∞` фіксовані витрати розмиваються по великій кількості запитів, і юніт-вартість асимптотично наближається до маржинальної вартості.

**Маржинальна вартість** (англ. *marginal cost*) `MC(N)` характеризує приріст витрат інфраструктури при додаванні однієї додаткової бізнес-транзакції. Математично вона є першою похідною загальної функції витрат за кількістю транзакцій:

```
MC(N) = dC_total / dN = ∑ [ c_i · (dR_i / dN) ]
```

Аналіз функції маржинальної вартості дозволяє розділити системи на три категорії за типом ресурсомісткості:

1. **Лінійна модель споживання (`dR_i / dN = α_i`):** Споживання ресурсів зростає строго пропорційно кількості запитів (`R_i(N) = α_i · N`). У цьому разі маржинальна вартість є константою: `MC = ∑ [ c_i · α_i ]`.
2. **Сублінійна модель споживання (`d²R_i / dN² < 0`):** Виникає при ефективному кешуванні та агрегації запитів. Кожна наступна транзакція коштує дешевше за попередню.
3. **Надлінійна / Нелінійна модель споживання (`d²R_i / dN² > 0`):** Виникає через ефекти конкуренції за ресурси (контеншн баз даних, блокування таблиць, неоптимальні алгоритми `O(N²)`). При квадратичній залежності споживання `R_i(N) = α_i · N + β_i · N²` маржинальна вартість зростає лінійно разом із навантаженням:

```
MC(N) = ∑ [ c_i · (α_i + 2 · β_i · N) ]
```

Це пояснює, чому архітектурні дефекти (наприклад, відсутність індексу у БД) проявляються в юніт-економіці не одразу на staging, а призводять до вибухового зростання рахунку під піковим навантаженням у продакшені.

## 3. Математика оцінки відхилення у CI (Delta Cost Shift)

Під час виконання навантажувального тесту у CI-конвеєрі для базової версії коду `base` та нової версії з пул-реквесту `PR` вимірюються вектори споживання ресурсів на один запит:

```
V_base = [ CPU_base, RAM_base, IOPS_base, Egress_base ]
V_PR   = [ CPU_PR, RAM_PR, IOPS_PR, Egress_PR ]
```

Очікувана зміна юніт-вартості `Δ U_cost` визначається як скалярний добуток вектора різниці ресурсів на вектор ціни продуктів `C_price`:

```
Δ U_cost = (V_PR - V_base) · C_price
         = ∑ [ c_i · (R_{i, PR} - R_{i, base}) ]
```

Для оцінки річного фінансового ефекту `Δ Cost_annual` зміна юніт-вартості екстраполюється на прогнозований річний обсяг транзакцій `N_annual`:

```
Δ Cost_annual = Δ U_cost · N_annual
```

## 4. Статистична оцінка значущості відхилень (t-тест Стьюдента)

Вимірювання юніт-вартості у середовищі CI піддається впливу випадкового шуму (коливання навантаження на тестовому хості, затримки мережі). Щоб відрізнити реальну фінансову регресію від випадкового шуму, використовується двовибірковий t-критерій Стьюдента для вибірок розміром `k` вимірювань.

Формульовується нульова гіпотеза `H_0: μ_PR = μ_base` (зміна коду не вплинула на середню вартість).

Обчислюється t-статистика:

```
t_stat = (X̄_PR - X̄_base) / √[ (s²_PR / k_PR) + (s²_base / k_base) ]
```

де `X̄` — вибіркове середнє значення юніт-вартості, а `s²` — вибіркова дисперсія.

Якщо `t_stat > t_critical` для заданого рівня значущості (α = 0.05), нульова гіпотеза відхиляється, і фітнес-функція фіксує **статистично значуще зростання юніт-вартості**.

## 5. Матриця чутливості витрат (Cost Sensitivity Matrix)

Матриця чутливості показує, які саме ресурси справляють найбільший вплив на підсумкову вартість системи. Вона обчислюється як вектор частинних похідних загальних витрат по кожному ресурсному параметру:

```
S_i = ∂ C_total / ∂ R_i = c_i
```

Для виявлення "гарячих точок" витрат обчислюється нормалізований коефіцієнт чутливості `E_i` (еластичність витрат):

```
E_i = (∂ C_total / ∂ R_i) · (R_i / C_total)
```

Значення `E_i = 0.65` для ресурсу процесора означає, що зростання споживання CPU на 10% призводить до зростання загального рахунку інфраструктури на 6.5%. Це дозволяє автоматизовано підказувати розробнику у коментарях PR, який саме ресурс потребує першочергової оптимізації.

## 6. Покроковий розрахунок статистичної значущості (Приклад)

**Початкові умови:**
Команда сервісу авторизації проводить навантажувальне профільування 1000 запитів на базовій гілці та на гілці з PR, який замінив локальний кеш JWT-токенів на виклики до Redis.

Вектор цін ресурсів `C_price`:
- `c_cpu` = `\$0.00000001` за 1 мс CPU
- `c_redis_op` = `\$0.0000005` за 1 операцію Redis
- `c_ram` = `\$0.000000002` за 1 МБ-сек RAM

Результати вимірювань середнього споживання на запит:
- Базова гілка `base`: CPU = 12.0 мс, Redis_ops = 0, RAM = 45 МБ (час життя запиту 50 мс)
- Пул-реквест `PR`: CPU = 8.0 мс, Redis_ops = 2, RAM = 20 МБ (час життя запиту 30 мс)

**Крок 1. Обчислення юніт-вартості базової версії (`U_cost_base`):**

```
U_cost_base
= (12.0 · 10⁻⁸) + (0 · 5 · 10⁻⁷) + (45 · 0.050 · 2 · 10⁻⁹)
= 1.20 · 10⁻⁷ + 0 + 0.045 · 10⁻⁷
= 1.245 · 10⁻⁷ USD (або $0.1245 на 1 млн запитів)
```

**Крок 2. Обчислення юніт-вартості версії з PR (`U_cost_PR`):**

```
U_cost_PR
= (8.0 · 10⁻⁸) + (2 · 5 · 10⁻⁷) + (20 · 0.030 · 2 · 10⁻⁹)
= 0.80 · 10⁻⁷ + 10.0 · 10⁻⁷ + 0.012 · 10⁻⁷
= 10.812 · 10⁻⁷ USD (або $1.0812 на 1 млн запитів)
```

**Крок 3. Обчислення абсолютного та відносного зсуву вартості:**

```
Δ U_cost = U_cost_PR - U_cost_base
         = 10.812 · 10⁻⁷ - 1.245 · 10⁻⁷
         = +9.567 · 10⁻⁷ USD на запит

Ratio = U_cost_PR / U_cost_base
      = 10.812 / 1.245
      = 8.68 (зростання вартості у 8.68 рази)
```

**Крок 4. Фінансовий висновок для CI:**
Попри те, що використання CPU зменшилося на 33%, додавання двох викликів Redis на кожен запит збільшило юніт-вартість транзакції на 768%. При обсязі 500 мільйонів запитів на місяць цей PR збільшить щомісячний рахунок за інфраструктуру на:

```
Δ Cost_monthly = 9.567 · 10⁻⁷ · 500,000,000 = $478.35 / місяць
```

Математичний аналіз показує, що оптимізація CPU виявилася хибною ціллю: фітнес-функція вартості у CI автоматично ловить таке викривлення і блокує PR, вимагаючи повернення до локального кешування або оптимізації викликів Redis.
