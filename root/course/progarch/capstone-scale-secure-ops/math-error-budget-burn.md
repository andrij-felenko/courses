# 🧮 Математика швидкості вигорання бюджету помилок (Burn Rate)

Служба вважається надійною не тоді, коли вона досягає абстрактного 100% аптайму, а коли її фактична кількість помилок вкладається у визначений цільовий рівень обслуговування (Service Level Objective, SLO). Прагнення до абсолютного 100% аптайму є економічно недоцільним і технічно згубним: воно блокує швидкість розробки нових фіч та вимагає експоненційного зростання витрат на інфраструктуру.

Проте традиційний моніторинг статичних порогів (наприклад, тривога при `Error Rate > 1%` за останні 5 хвилин) має фундаментальні недоліки. На високому трафіку сплеск у 1% протягом 5 хвилин може спалити левову частку місячного запасу надійності, а на низькому нічному трафіку поодинокий збій дасть штучний стрибок `Error Rate = 10%`, викликавши хибне нічне сповіщення чергового інженера. Математичною основою сучасного аналізу канареєчних деплоїв та автоматичного сповіщення є **швидкість вигорання бюджету помилок (Burn Rate)**.

## 1. Розрахунок бюджету помилок (Error Budget)

Бюджет помилок (Error Budget) — це математичний міст між продуктовими вимогами та операційною надійністю. Він визначає максимально припустиму кількість невдалих операцій чи часу відмови, яку система може собі дозволити без погіршення користувацького досвіду.

Нехай `SLO` — це цільовий коефіцієнт успішних запитів за фіксоване часове вікно `T` (зазвичай 30 днів або 720 годин). Нормативна частка припустимих помилок `E_slo` обчислюється як доповнення до `SLO`:

```text
E_slo = 1 - SLO

Приклад для SLO = 99.99%:
E_slo = 1 - 0.9999
      = 0.0001 (або 0.01% усіх запитів)

Приклад для SLO = 99.9%:
E_slo = 1 - 0.999
      = 0.001 (або 0.1% усіх запитів)
```

Обчислимо максимально припустимий сумарний час простою `T_down` за 30-денний період (`T = 30 днів · 24 год · 3600 сек = 2 592 000 сек`):

```text
T_down = T · E_slo
       = 2 592 000 · 0.0001     [застосовано визначення E_slo]
       = 259.2 секунди
       ≈ 4.32 хвилини на місяць
```

Отже, для досягнення рівня надійності 99.99% за місяць система може накопичити не більше ніж 259.2 секунди загальної відмови або не більше 1 невдалого запиту на кожні 10,000 виконаних операцій. Усі 100% бюджету помилок належать команді розробки: цей бюджет можна витрачати на канареєчні деплої, експерименти та оновлення архітектури.

## 2. Формальне визначення швидкості вигорання (Burn Rate)

Швидкість вигорання `B` — це безрозмірна величина, яка описує відношення поточної швидкості виникнення помилок `e(w)` за вікно спостереження `w` до максимально припустимої нормативної швидкості `E_slo`:

```text
B(w) = e(w) / E_slo
```

Де `e(w)` — це частка невдалих запитів за вікно `w`:

```text
e(w) = N_errors(w) / N_total(w)
```

Значення швидкості вигорання `B` показує, за який час система повністю вичерпає весь свій 30-денний бюджет помилок, якщо поточний рівень помилок `e(w)` залишатиметься незмінним. Час повного вичерпання бюджету `T_exhaust` обчислюється за формулою:

```text
T_exhaust = T / B(w)

Шкала вигорання (для T = 30 днів / 720 годин):
B = 1.0  → Бюджет 100% вигорить рівно за 30 днів (720 годин). Ідеальний нормальний стан.
B = 2.0  → Бюджет вигорить за 15 днів (360 годин).
B = 14.4 → 2% бюджету вигоряє за 1 годину (повне вичерпання за 50 годин).
B = 36.0 → 5% бюджету вигоряє за 1 годину (повне вичерпання за 20 годин).
B = 100  → 100% бюджету вигоряє за 7.2 години. Критична катастрофа продакшну.
```

## 3. Виведення коефіцієнтів для оптимізації сповіщень (Multi-Window Multi-Burn-Rate)

Для побудови надійного контролера канареєчного розгортання та системи сповіщень чергових інженерів застосовують математичну модель Google SRE. Головний принцип цієї моделі: сповіщення має спрацьовувати не тоді, коли стається випадковий поодинокий баг, а коли швидкість вигорання загрожує вичерпати фіксований відсоток `P` бюджету помилок за проміжок часу `h`.

Виведемо загальну формулу для розрахунку необхідного коефіцієнта Burn Rate `B`:

```text
P_consumed = (B · h) / T

Розв'яжемо відносно B:
B = (P_consumed · T) / h
```

Розглянемо два стандартні операційні сценарії розрахунку коефіцієнтів:

### Сценарій 1. Термінова сторінка (Emergency Page / Canary Rollback)

Мета: негайно зупинити канареєчний деплой або розбудити чергового інженера, якщо система втрачає `P = 2%` (0.02) від усього 30-денного бюджету помилок за проміжок часу `h = 1 година`:

```text
B = (0.02 · 720 годин) / 1 година     [підстановка T = 720, P = 0.02, h = 1]
  = 14.4 / 1
  = 14.4
```

Коефіцієнт **`B = 14.4`** є фундаментальною константою SRE-інженерії. Якщо виміряна похибка канареєчного деплою перевищує допустиму норму `E_slo` в 14.4 раза, контролер розгортання примусово зупиняє просування нової версії та здійснює автоматизоване відкочування (Rollback) за < 30 секунд.

### Сценарій 2. Квиткове сповіщення (Ticket Alert)

Мета: створити нетермінове завдання (Ticket / Email) для інженерної команди, якщо система повільно втрачає `P = 5%` (0.05) бюджету помилок за проміжок часу `h = 6 годин`:

```text
B = (0.05 · 720 годин) / 6 годин     [підстановка T = 720, P = 0.05, h = 6]
  = 36 / 6
  = 6.0
```

Коефіцієнт **`B = 6.0`** вказує на помірний некритичний витік надійності, який вимагає уваги розробників протягом робочого дня.

## 4. Двовіконний алгоритм оцінки (Multi-Window Guard)

Використання лише одного часового вікна вимірювання створює операційні пастки:
- Якщо контролер оцінює лише одне довге вікно `w_long = 1 година`, то після усунення аварії чи відкочування канарейки середнє значення `B` за годину залишатиметься високим, і тривога горітиме ще 55 хвилин після ліквідації проблеми.
- Якщо контролер оцінює лише одне коротке вікно `w_short = 5 хвилин`, випадковий мережевий таймаут кількох пакетів дасть короткий сплеск `B > 14.4`, викликавши хибне відкочування працюючого деплою.

Для розв'язання цього фундаментального протиріччя канареєчний контролер використовує **алгоритм подвійного вікна (Multi-Window Multi-Burn-Rate)**. Контролер обчислює Burn Rate за двома вікнами одночасно:

```text
Умова спрацювання канареєчного відкочування (Canary Rollback Trigger):

[ B(w_long = 1 год) ≥ 14.4 ]   ТАКИЙ ЩО   [ B(w_short = 5 хв) ≥ 14.4 ]
```

```text
+---------------------------------------------------------------------------------------------------+
|  Швидкість B    |  Довге вікно (w_long) | Коротке вікно (w_short) | Дія контролера / Сповіщення     |
+---------------------------------------------------------------------------------------------------+
|  B ≥ 14.4       |  1 година             | 5 хвилин                | Automated Rollback / PagerDuty  |
|  B ≥ 6.0        |  6 годин              | 30 хвилин               | Create Jira Ticket / Slack      |
|  B ≥ 1.0        |  3 дні                | 6 годин                 | Low priority warning email      |
+---------------------------------------------------------------------------------------------------+
```

Математично двовіконна умова гарантує два інваріанти:
1. **Значущість:** Помилка є достатньо важкою, щоб спалити понад 2% місячного бюджету за годину (`w_long`).
2. **Актуальність:** Помилка продовжує відбуватися просто зараз у момент вимірювання (`w_short`), а не є залишковим ефектом минулого сплеску.

## 5. Граничні випадки: мала вибірка та холодний старт

При практичній імплементації математичної моделі необхідно враховувати два граничні випадки:

1. **Проблема низької частоти (Small N Problem):** На малій кількості запитів (наприклад, `N = 20` запитів за 5 хвилин) 1 помилка дає `e(w) = 0.05` (5%). Для `SLO = 99.99%` це дає `B = 0.05 / 0.0001 = 500`. Щоб уникнути хибного відкочування, контролер вимагає виконання умови мінімального статистичного порогу: `N_total(w) ≥ 1000`.
2. **Пастка стартів (Cold Start Shift):** Перші 30 секунд після запуску канареєчний Pod може мати підвищені затримки через JIT-компіляцію чи розігрів пулів сокетів. Математична оцінка `B(w_short)` повинна починатися строго після успішного проходження проби готовності (Readiness Probe).
