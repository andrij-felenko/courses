# ⚙️ Три дози DDD в одній системі: ядро, реєстр, пошта

Digital Homes — одна система, але не однорідний моноліт: три її частини живуть із геть різною густотою правил, і тому кожна заслуговує на **свою** дозу DDD. Досі ми міряли цю дозу на словах — повна ядру, легка реєстру, ніяка загальному. Слова легко кивнути й забути. Тож зберімо всі три частини руками, кожну своєю дозою, і зробімо те, чого проза не вміє: **запустімо** правило ядра без жодного заліза й **відтворімо** дві крайні помилки — недобір дози в ядрі та надмір у реєстрі. Розмитий регулятор гучності обертається трьома конкретними файлами, і кожен на дотик інший.

Одне обмеження, щоб порівняння було чесним: усі три частини — **однією мовою**, ідіоматичним TypeScript. Якби ядро я написав багатою мовою, а реєстр — бідною, ти б не розібрав, звідки різниця: від дози чи від мови. Прибиваємо мову цвяхом — і все, що побачимо далі, належить **дозі**, а не синтаксису. А доза, нагадаю, дорівнює одному: **густоті правил**, які тримає в голові знавець справи і які легко наплутати. Де їх густо — лізь високо; де порожньо — не лізь узагалі.

## Ядро: багатий агрегат, що сам себе стереже

Почнімо з частини, заради якої DH узагалі існує, — з автоматики сценаріїв. Тут живе справжня складність предмета. Господар складає **сценарії** («Ніч», «Прихід додому», «Провітрити»), кожен велить кімнаті кліматом і світлом; а поверх усіх сценаріїв стоїть залізне **блокування безпеки**: в одній кімнаті обігрівач і кондиціонер не працюють разом ніколи. Це не забаганка стилю — це правило, яке знавець тримає в голові й яке, порушене, псує залізо й рахунок за електрику. Саме такому правилу належить повна доза.

Дивись, як кожна сходинка DDD лягає рядком коду. Спершу — **мова предмета** й **значеннєвий об'єкт**: сценарій, незмінний рецепт, названий так, як його зве господар.

```ts
class DomainError extends Error {
  constructor(message: string) { super(message); this.name = "DomainError"; }
}

// Незмінний рецепт, названий по-людськи. Рівність — за вмістом, не за посиланням.
type ClimateIntent =
  | { readonly want: "heat"; readonly targetC: number }
  | { readonly want: "cool"; readonly targetC: number }
  | { readonly want: "off" };

interface Scenario {
  readonly name: string;            // "Ніч", "Прихід додому", "Провітрити"
  readonly climate: ClimateIntent;
  readonly lightsOn: boolean;
}
```

А тепер — **корінь агрегату**, кімната. Її внутрішній стан клімату захований; назовні стирчать лише команди, названі дією предмета, а не «встанови поле 3»:

```ts
class Room {
  private heating = false;
  private cooling = false;
  private lightsOn = false;
  private targetC = 21;

  constructor(readonly name: string) {}

  // Сценарій — цілісний стан, а не приріст до старого. Лише через корінь.
  apply(scenario: Scenario): void {
    this.stopClimate();                                   // новий сценарій починає з чистого
    const c = scenario.climate;
    if (c.want === "heat")      this.startHeating(c.targetC);
    else if (c.want === "cool") this.startCooling(c.targetC);
    this.lightsOn = scenario.lightsOn;
  }

  startHeating(targetC: number): void {
    this.changeClimate(true, this.cooling);               // хочу гріти, кулер лишаю як є
    this.targetC = targetC;
  }
  startCooling(targetC: number): void {
    this.changeClimate(this.heating, true);
    this.targetC = targetC;
  }
  stopClimate(): void {
    this.changeClimate(false, false);
  }

  // Інваріант безпеки живе ТУТ — в одному захищеному місці, і ніде більше.
  // Перевірка ПЕРЕД зміною: відмова не лишає кімнату в напівстані.
  private changeClimate(heating: boolean, cooling: boolean): void {
    if (heating && cooling)
      throw new DomainError(
        `${this.name}: обігрівач і кондиціонер не працюють у кімнаті разом`);
    this.heating = heating;
    this.cooling = cooling;
  }

  get climate(): "heating" | "cooling" | "idle" {
    if (this.heating) return "heating";
    if (this.cooling) return "cooling";
    return "idle";
  }
}
```

Затримаймося, бо в цих тридцяти рядках — уся повна доза, кожна сходинка на своєму місці. **Мова предмета:** метод зветься `startHeating`, а не `setMode(1)`; вхід — `Scenario` з іменем, а не мапа полів. Знавець, глянувши, упізнає свій предмет і скаже «так, воно працює так» — а це, як ми знаємо, і є та розмова, задля якої DDD затівають. **Усе через корінь:** поля `heating`/`cooling` приватні, і назовні немає жодного важеля, щоб їх смикнути напряму — `room.heating = true` просто не скомпілюється. Єдині двері всередину — названі команди, і двері **під охороною**. **Інваріант в одному місці:** правило «не разом» живе рівно в `changeClimate`, і перевірка стоїть **перед** зміною стану — тому навіть відмовлена команда не лишає кімнату з увімкненими обома. Один захищений вузол стереже цілу групу полів як одне ціле — це і є [агрегат із коренем](book:programming/aggregates-consistency), не метафора, а тридцять рядків.

Тепер тонкість, через яку тут аж два способи керувати кліматом. `apply` бере **цілісний сценарій** — авторський задум, уже несуперечливий, — і тому чесно скидає клімат перед тим, як покласти новий: сценарії перемикаються вільно, «Ніч» після «Ранку» просто гасить гріння й вмикає холод. А `startHeating`/`startCooling` — це **сирі команди** для незалежних автоматичних правил. Уяви два таких правила: «надворі нижче 5 °C → грій» і «вологість понад 70 % → холоди, бо кондиціонер сушить». Холодного вологого ранку **спрацюють обидва** — і кожне гукне свою сиру команду. Фізично гріти й холодити одну кімнату не можна, тож корінь мусить **відмовити** другому й підняти галас. Ось справжня робота інваріанта, і ось звідки береться `DomainError`: не з авторського сценарію, а зі збігу незалежних правил.

> 🔧 **Навіщо це.** Уся ціна багатої моделі окупається одним фактом: **правило можна перевірити, не вмикаючи обігрівача**. Воно живе в чистому об'єкті — ні бази, ні мережі, ні розетки, — тож тест ганяє його за мілісекунди й на межах, куди справжня кімната повзла б хвилинами. Багата модель — не «краса ООП», а те, що робить найважче правило системи **дешевим у перевірці**.

Ось цей тест — і йому не потрібні ані давач, ані реле, ані нагріта кімната:

```ts
import assert from "node:assert/strict";

// 1) Сценарії перемикаються вільно й лишають РІВНО ОДНЕ, не обидва.
const bedroom = new Room("спальня");
bedroom.apply({ name: "Ніч",   climate: { want: "cool", targetC: 18 }, lightsOn: false });
assert.equal(bedroom.climate, "cooling");
bedroom.apply({ name: "Ранок", climate: { want: "heat", targetC: 22 }, lightsOn: true });
assert.equal(bedroom.climate, "heating");        // холод сам згас, коли прийшло гріння

// 2) Два незалежні правила конфліктують — корінь відмовляє, а не мовчить.
const hall = new Room("вітальня");
hall.startHeating(21);                            // правило «надворі холодно»
assert.throws(() => hall.startCooling(24), DomainError);   // правило «волого» — конфлікт!

// 3) На шляху відмови стан НЕ спотворився: досі гріємо, кулер не прокрався.
assert.equal(hall.climate, "heating");
```

Третій `assert` — найтихіший і найважливіший. Він доводить, що інваріант не тільки **ловить** заборонену комбінацію, а й ловить її **безпечно**: після відмови кімната лишилася рівно там, де була, а не завмерла з обома ввімкненими. Це подарунок від «перевірки перед зміною» в `changeClimate` — і саме такі гарантії на межах виправдовують багату модель. Правило доведене зеленим, а жодного вата тепла не витрачено.

## Недобір: те саме ядро як грудка багна

А тепер подивись, на що перетворюється **той самий** інваріант, коли ядру не додали дози. Правило нікуди не поділося — просто ніхто не дав йому дому, і воно розтеклося краплями по сервісах:

```ts
interface DB {
  query(sql: string, id: string): { heater: number; cooler: number };
  exec(sql: string, id: string): void;
}

// ❌ Недобір: правило безпеки розмазане по коду магічними числами.
function runScenario(roomId: string, scenarioId: number, db: DB): void {
  const room = db.query(`SELECT heater, cooler FROM rooms WHERE id = ?`, roomId);

  if (scenarioId === 3) {                          // 3 — це «ніч»? «ранок»? хто вже згадає
    db.exec(`UPDATE rooms SET heater = 1 WHERE id = ?`, roomId);
    // ...а чи не працює ще кулер — перевірити ТУТ забули
  } else if (scenarioId === 7) {
    if (room.cooler === 0)                         // тут перевірку згадали...
      db.exec(`UPDATE rooms SET heater = 1 WHERE id = ?`, roomId);
  }
  // ...те саме правило живе ще у notifyService і в scheduleService,
  //    і в одному з них перевірку теж загубили
}
```

Проглянь очима знавця — і побачиш **баг**. Гілка `scenarioId === 3` вмикає обігрівач **не спитавши про кулер**. Спрацюй цей сценарій, поки кондиціонер сушить кімнату, — і маєш обидва разом, рівно те, що інваріант мав не пустити ніколи. У багатій моделі такого коду просто не існує: єдина брама `changeClimate` не дала б навіть записати заборонений стан. А тут правило продубльоване в трьох файлах трьома різними руками, «стан» захований у магічну сімку й трійку, яких ніхто вже не пам'ятає, і досить одному з-поміж переписувачів позіхнути — щоб перевірка зникла в одній гілці, а система тихо стала небезпечною. Це і є [велика грудка багна](root:progarch/what-is-architecture/hist-big-ball-of-mud.md): не буря, а болото, і виростає воно рівно там, де правил найгустіше, — у частині, що найдужче заслуговувала на модель. Недобір карає точно в ядро.

## Допоміжне: реєстр як DTO і тонкий сервіс

Переходимо на сусідню поличку — і регулятор клацає донизу. Реєстр пристроїв: додати пристрій, перейменувати, прибрати, вибрати ті, що в кімнаті. Постав над ним головний тест здорового глузду — **чи є тут знавець, що тримає правило, яке можна наплутати?** І відповідь чесна: нема. «Правило» реєстру вичерпується словом «збережи». Це не предмет, це сантехніка — і доза їй належить легка.

Легка, але не нульова: **трохи мови** реєстр таки заслужив. Хай пристрій зветься пристроєм, кімната — кімнатою, а ідентифікатор пристрою не можна ненароком підставити туди, де чекають назву кімнати. Ось уся доза — **названі типи** й чесний DTO, і ні на йоту більше:

```ts
// Названі типи: щоб id пристрою й назва кімнати не переплуталися мовчки.
type DeviceId = string & { readonly __brand: "DeviceId" };
type RoomName = string & { readonly __brand: "RoomName" };
type DeviceKind = "heater" | "cooler" | "light" | "sensor" | "lock";

const deviceId = (s: string) => s as DeviceId;    // «розумний» конструктор бренду
const roomName = (s: string) => s as RoomName;

// DTO: названі поля, жодного правила. Знекровлено — і це ПРАВИЛЬНО.
interface Device {
  readonly id: DeviceId;
  readonly room: RoomName;
  readonly kind: DeviceKind;
  readonly name: string;            // як його зве господар: «торшер біля дивана»
}

// Тонкий сервіс: додати, перейменувати, прибрати, вибрати. І все.
class DeviceRegistry {
  constructor(private store: Map<DeviceId, Device>) {}

  register(device: Device): void {
    this.store.set(device.id, device);
  }
  rename(id: DeviceId, name: string): Device {
    const found = this.store.get(id);
    if (!found) throw new Error(`пристрою ${id} немає`);   // не інваріант, а перевірка існування
    const renamed: Device = { ...found, name };           // DTO незмінний — робимо новий
    this.store.set(id, renamed);
    return renamed;
  }
  remove(id: DeviceId): void {
    this.store.delete(id);
  }
  inRoom(room: RoomName): Device[] {
    return [...this.store.values()].filter(d => d.room === room);
  }
}
```

Придивись до `Device` — це чистий [DTO](book:programming/dto), торба названих полів без поведінки. У ядрі така анемія була б смертю; тут вона — **норма**, бо DTO й не належить нести правил: йому належить переносити дані. А `rename`, хоч і кидає виняток, кидає його не через доменний інваріант, а через звичайну перевірку «а чи є такий рядок» — це сантехніка, не мова предмета. Бренди на типах — то весь виторг від «єдиної мови», найдешевшої сходинки: імена, що не переплутаються, і жодного `changeClimate` понад те.

> 🔧 **Навіщо це.** Спокуса тут — «облагородити» реєстр до рівня ядра, бо DDD відчувається як знак якості. Не піддавайся. Знекровлений об'єкт — гріх лише там, де **є що інкапсулювати**; де правил нема, багатити нема чого, і тонкий DTO чесніший за будь-який «агрегат». Доза міряється потребою частини, а не твоїм бажанням писати грамотно.

## Надмір: реєстр в анемічній церемонії

Що ж буває, коли спокусі таки піддатися? Виростає дзеркальний до багна монстр — **анемічна** (гр. *an-* «без» + *haîma* «кров») церемонія: усі шати багатого домену, накинуті на те, у чому нема ані краплі правил.

```ts
interface DeviceRepo { save(agg: DeviceAggregate): void; }
interface EventBus  { publish(event: { type: string; id: string }): void; }

// ❌ Надмір: обряд багатого домену над тим, у чому інваріантів НЕМА.
class DeviceAggregate {
  private constructor(private device: Device) {}

  static register(id: DeviceId, room: RoomName,
                  kind: DeviceKind, name: string): DeviceAggregate {
    return new DeviceAggregate({ id, room, kind, name });   // фабрика, що нічого не стереже
  }
  rename(name: string): void {
    this.device = { ...this.device, name };                 // сетер, перевдягнений у «поведінку»
  }
  get snapshot(): Device { return this.device; }
}

interface RegisterDeviceCommand { id: string; room: string; kind: DeviceKind; name: string; }

class RegisterDeviceHandler {
  constructor(private repo: DeviceRepo, private bus: EventBus) {}
  handle(cmd: RegisterDeviceCommand): void {
    const agg = DeviceAggregate.register(
      deviceId(cmd.id), roomName(cmd.room), cmd.kind, cmd.name);
    this.repo.save(agg);
    this.bus.publish({ type: "DeviceRegistered", id: cmd.id });  // подія, на яку ніхто не підписаний
  }
}
```

Полічи шари, які тут з'явилися заради «вставити рядок»: агрегат-обгортка, приватний конструктор із фабрикою, команда, її хендлер, шина подій. П'ять конструкцій — і **жодна нічого не стереже**, бо стерегти нема чого. `rename` виглядає як поведінка, а насправді це сетер під мантією. Подія `DeviceRegistered` летить у шину, де на неї ніхто не чекає. Це рівно та [передчасна складність, від якої застерігає YAGNI](book:programming/dry-kiss-yagni), тільки вбрана в доменні шати, — і, за влучним висновком [давньої суперечки про анемічну модель](root:progarch/data-access-choice/hist-anemic-domain-debate.md), вона несе всі витрати доменної моделі, не даючи жодної з її переваг. Клас, названий мовою предмета, але порожній усередині, — найпідступніша з помилок: він **виглядає** грамотно, тож проходить рев'ю, а платиш за нього щодня, читаючи п'ять шарів там, де чесний був би один рядок `store.set`.

## Загальне: пошта як тонкий перехідник

Лишилася третя частина — сповіщення, аудит, пошта. Постав той самий тест — і навіть питати ніяково: ні знавця, ні правила, ні свого предмета. Розсилати листи вміє півсвіту, це зроблено тисячу разів; тут нема чого **приборкувати** і нема чого **винаходити** — таке [беруть готовим, а не пишуть](root:progarch/dh-not-building). Доза DDD — нульова. Уся «архітектура» — одне слово нашою мовою на вході й тонкий перехідник до чужої бібліотеки на виході:

```ts
type UserId = string & { readonly __brand: "UserId" };

// Порт: одне слово нашою мовою — щоб ядро не знало ні пошти, ні пушів, ні SMS.
interface Notifier {
  notify(userId: UserId, text: string): Promise<void>;
}

// Готові речі, яких ми не писали: бібліотека розсилання й довідник людей.
interface Mailer        { send(msg: { to: string; subject: string; body: string }): Promise<void>; }
interface UserDirectory { emailOf(userId: UserId): Promise<string>; }

// Адаптер: уся «логіка» — перекласти НАШ виклик у виклик бібліотеки.
class EmailNotifier implements Notifier {
  constructor(private mailer: Mailer, private users: UserDirectory) {}

  async notify(userId: UserId, text: string): Promise<void> {
    const email = await this.users.emailOf(userId);
    await this.mailer.send({ to: email, subject: "Digital Homes", body: text });
  }
}
```

Ось де межа доречного DDD стоншується до нитки — і це правильно. Єдиний доменний слід тут — назва порту `Notifier` та його метод `notify`, щоб ядро говорило «сповісти господаря» своєю мовою, а не викликало `nodemailer.sendMail` посеред логіки сценаріїв. Жодного агрегата, жодного інваріанта, жодного значеннєвого об'єкта — сам перехідник, що перекладає наш виклик у чужий. Захотілося б завтра слати не листа, а пуш — з'явиться `PushNotifier` за тим самим портом, і ядро не здригнеться. Це вся доза, яку заслужило загальне: тонкий шов до готового, і ні кроку вглиб.

## Складність і пастки

Постав три частини поряд — і побачиш одну систему в трьох дозах, а між ними два способи схибити.

![Таблиця з трьох рядків (ядро, реєстр, пошта) на дві колонки — помилкова доза проти правильної. Ядро: помилка — недобір, грудка багна з if status==3 по сервісах; правильно — багатий агрегат з інваріантом в одному місці. Реєстр: помилка — надмір, анемічна церемонія з порожніми агрегатами й хендлерами; правильно — DTO плюс тонкий сервіс. Пошта: помилка — надмір, моделювати те, що береться готовим; правильно — тонкий адаптер до бібліотеки](/root/course/progarch/ddd-when-overkill/img/dose-wrong-right.svg)

*Та сама система, три дози — і два дзеркальні способи їх схибити. Ядро карає за недобір (грудка багна), реєстр і пошта — за надмір (порожня церемонія). Правильна доза щоразу випливає з густоти правил у частині, а не з бажання писати грамотно.*

Тепер пастки, які чигають на цьому шляху.

**Найпідступніша — середина: імена DDD без його суті.** Це не недобір і не надмір, а їхній гібрид: багаті назви, порожній зміст. `DeviceAggregate` з нашого прикладу надто грамотний на вигляд, щоб хтось на рев'ю спитав «а що він, власне, стереже?». Обряд без судження — це культ вантажу, [принцип, перетворений на догму](root:progarch/principles-as-tools-not-dogma); лік один — щоразу питати не «чи грамотно я назвав клас», а «який інваріант він захищає». Нема відповіді — нема агрегата, хоч як його назви.

**Друга — розростання агрегату.** Спокуса, зробивши `Room` багатою, підтягнути під її корінь і реєстр, і розклади, і історію команд — «щоб усе доменне було разом». Не роби цього: агрегат тримають **тісним навколо інваріанта**. `Room` стереже одне-єдине правило клімату; щойно ти всунув у неї список пристроїв кімнати, вона почала стерегти те, що стерегти не треба, і легка частина заразилася вагою важкої. Межа агрегата — це межа інваріанта, не межа теми.

**Третя — м'якість `private` у TypeScript.** Слово `private` живе лише під час компіляції; у зібраному JS поле доступне, тож дисципліновану інкапсуляцію ядра варто прибити твердим `#`-полем (`#heating`), яке недосяжне ззовні й у рантаймі. Але не переплутай інструмент із суттю: інваріант тримає не ключове слово, а те, що **єдиний** шлях до стану — крізь захищену команду. `#` робить цю обіцянку залізною, проте саму обіцянку дає дизайн, не синтаксис.

І звідси — головне, що лишається в руках. Ми зібрали одну систему тричі, і кожна частина спинилася на своїй висоті: ядро вилізло на самий верх, до багатого агрегата з інваріантом, реєстр зупинився на іменах і CRUD, а пошта не полізла взагалі. Жодна доза не «правильніша» за інші — правильна та, що дорівнює густоті правил у частині. Недобір робить болото там, де правил густо; надмір робить порожню церемонію там, де їх нема; і обидві помилки ростуть з одного кореня — з рішення рефлексом замість погляду на конкретну частину. Тому дозу рахують не на проєкт, а **частина за частиною**: більшість твоєї системи — CRUD і труби, де DDD лежить мертвою вагою, але та одна частина, що є твоїм ядром, покарає за кожен день, поки ти тримаєш її грудкою багна. Регулятор один, поділок багато — і читаєш його там, де густо правил, а не там, де хочеться виглядати грамотно.
