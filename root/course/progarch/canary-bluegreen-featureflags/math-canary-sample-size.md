# 🧮 Математика аналізу канарки: вибірка, значущість та мінімальний bake time

Ця математична вставка розкриває статистичний апарат автоматичного аналізу канарейкових випусків — як обчислити необхідний розмір вибірки запитів, визначити мінімальний час спостереження (bake time) та розрізнити випадковий шум від реальної деградації системи.

## 1. Постановка проблеми: шум проти сигналу

Коли 1% трафіку спрямовується на канарейкову версію, кількість запитів, що потрапляють на новий код, може бути відносно малою. Якщо загальний потік становить `100 RPS` (запитів за секунду), канарейка отримує лише `1 RPS` (86 400 запитів за добу або 60 запитів за хвилину).

Якщо з 60 запитів за хвилину один аварійно завершився помилкою HTTP 500, частота помилок становить:

```
p_canary = 1 / 60 ≈ 0.0167 (1.67%)
```

Якщо на контрольному середовищі (Baseline) частота помилок становить `0.1%` (0.001), виникає запитання: чи є сплеск до `1.67%` доказом зламаного коду, чи це випадкова девіація на малій вибірці?

Сліпий відкат на кожен дрібний сплеск створює хибні спрацьовування (англ. *false positives*), зупиняючи конвеєр. І навпаки: ігнорування сплеску пропускає баг на 100% користувачів (англ. *false negatives*).

---

## 2. Статистичні гіпотези та двовибірковий Z-тест пропорцій

Для оцінки частоти дискретних помилок (наприклад, помилок HTTP 5xx чи відхилених з'єднань) генеральна сукупність описується біноміальним розподілом. Ми перевіряємо дві статистичні гіпотези:
- **Нульова гіпотеза `H0`:** частота помилок у канарці та базлайні однакова (`p1 = p2`). Будь-яке відхилення є випадковим шумом.
- **Альтернативна гіпотеза `H1`:** нова версія збільшила частоту помилок (`p2 > p1`).

Під час прийняття рішення можливі два типи помилок:
- **Помилка I роду (`α`):** система оголошує канарку несправною, коли насправді новий код ідеальний (хибне тривожне сповіщення). Типово встановлюють `α = 0.05` (5%).
- **Помилка II роду (`β`):** система пропускає деградовану канарку на 100% проду (пропущений баг). Потужність тесту становить `1 - β`. Типово обирають `β = 0.20` (потужність 80%).

Для перевірки застосовується двовибірковий Z-тест пропорцій із нормальним наближенням біноміального розподілу.

Формула мінімальної кількості запитів `n` для кожної групи (Baseline та Canary):

```
p_bar = (p1 + p2) / 2

n = (z_alpha * sqrt(2 * p_bar * (1 - p_bar)) + z_beta * sqrt(p1 * (1 - p1) + p2 * (1 - p2)))² / (p1 - p2)²
```

### Покроковий розрахунок прикладу

Припустимо, базова система має `p1 = 0.001` (0.1% помилок). Ми хочемо гарантовано виявити зростання помилок у канарці до `p2 = 0.005` (0.5% помилок), тобто `Δp = 0.004`.

```
p_bar
= (0.001 + 0.005) / 2     [середня пропорція частоти помилок]
= 0.003                  [значення p_bar]

z_alpha = 1.96           [квантиль для alpha = 0.05]
z_beta  = 0.84           [квантиль для beta = 0.20, power = 80%]

Chislitel
= 1.96 * sqrt(2 * 0.003 * 0.997) + 0.84 * sqrt(0.001 * 0.999 + 0.005 * 0.995)   [підстановка параметрів]
= 1.96 * sqrt(0.005982) + 0.84 * sqrt(0.000999 + 0.004975)                      [обчислення під коренями]
= 1.96 * 0.07734 + 0.84 * 0.07729                                                [вилучення квадратних коренів]
= 0.15159 + 0.06492                                                              [множення додатків]
= 0.21651                                                                        [сума чисельника]

Znamenatel
= (0.005 - 0.001)²       [різниця частот помилок у квадраті]
= (0.004)²               [обчислення різниці]
= 0.000016               [значення знаменника]

n
= (0.21651)² / 0.000016  [ділення квадрата чисельника на знаменник]
= 0.046877 / 0.000016    [квадрат чисельника]
≈ 2930 запитів           [округлення необхідного розміру вибірки]
```

**Висновок:** щоб статистично обґрунтовано (із довірчою ймовірністю 95% та потужністю 80%) стверджувати, що канарка збільшила частоту помилок з 0.1% до 0.5%, канарейковий вузол мусить обробити як мінімум **2930 запитів**.

## 3. Обчислення мінімального часу витримки (Bake Time)

Час витримки канарки (англ. *bake time*) — це тривалість перебування нового коду під канарейковим трафіком до моменту прийняття рішення про розширення чи відкат.

Формула bake time через загальний навантажувальний потік `RPS_total` та частку канарки `c` (де `c = 0.01` для 1%):

```
RPS_canary = RPS_total * c                       [частка канарейкового трафіку]

T_bake = n / RPS_canary                          [тривалість збору вибірки]
```

Розглянемо два сценарії навантаження системи:

### Сценарій А: Високе навантаження (`RPS_total = 1000`, канарка `c = 1%`)

```
RPS_canary = 1000 * 0.01                         [трафік канарки: 1% від 1000 RPS]
= 10 RPS                                         [отриманий потік запитів]

T_bake = 2930 / 10                               [ділення розміру вибірки n=2930 на 10 RPS]
= 293 секунди                                    [час у секундах]
≈ 4.9 хвилини                                    [переведення у хвилини]
```

При високому трафіку канарейковий аналіз накопичує необхідну статистичну вибірку за **~5 хвилин**.

### Сценарій Б: Низький трафік (`RPS_total = 10`, канарка `c = 1%`)

```
RPS_canary = 10 * 0.01                           [трафік канарки: 1% від 10 RPS]
= 0.1 RPS                                        [еквівалентно 6 запитів за хвилину]

T_bake = 2930 / 0.1                              [ділення розміру вибірки n=2930 на 0.1 RPS]
= 29300 секунд                                   [час у секундах]
≈ 8.1 години                                     [переведення у години]
```

При низькому трафіку спроба розкатувати канарку на `1%` вимагає понад **8 годин** лише для збору мінімальної вибірки!

## 4. Аналіз безперервних метрик продуктивності: Непараметричний тест Манна — Уітні

Параметричний Z-тест чудово працює для дискретних частот помилок (0 або 1), але він **абсолютно непридатний для аналізу латентності (p95, p99)**. Латентність мережевих запитів має важкі хвости (heavy-tailed, логнормальний або Парето-розподіл). Середнє значення та дисперсія для таких розподілів суттєво викривляються окремими викидами (outliers).

Для порівняння метрик затримки (latency) автоматизовані системи (наприклад, Kayenta у Spinnaker) застосовують **непараметричний критерій Манна — Уітні (U-тест)**.

### Алгоритм тесту Манна — Уітні:

1. Збираються дві вибірки латентності однакового розміру: `X = {x1, ..., xk}` для Baseline та `Y = {y1, ..., yk}` для Canary.
2. Усі елементи обидвох вибірок об'єднуються у єдиний варіаційний ряд та рангуються від найменшого значення до найбільшого (ранги від 1 до `2k`).
3. Обчислюється сума рангів `R_canary` для канарейкової вибірки.
4. Обчислюється статистика `U`:

```
U = k * k + (k * (k + 1)) / 2 - R_canary
```

5. Отримане значення `U` порівнюється з критичним значенням для заданого рівню значущості `α`. Якщо `U` менше критичного, це математично доводить, що розподіл латентності канарки зсунутий у бік більших значень (продуктивність погіршилася), і конвеєр генерує автоматичний відкат.

## 5. Обчислення підсумкового балу канарки (Canary Score Algorithm)

В автоматизованих релізних платформах аналізатор агрегує результати багатьох метрик у єдину інтегральну оцінку — **Canary Score (від 0 до 100 балів)**.

Кожній групі метрик присвоюється ваговий коефіцієнт залежно від її критичності для бізнесу:

```
Score_total = w_errors * Score_errors + w_latency * Score_latency + w_resources * Score_resources
```

Типові вагові коефіцієнти у високонавантажених системах:
- **Частота помилок HTTP 5xx (`w_errors = 0.50`):** найвища вага. Будь-яке статистично значуще зростання помилок моментально обвалює підсумковий бал нижче порогу відкату (`Score < 75`).
- **Латентність p99 (`w_latency = 0.30`):** середня вага. Деградація затримки на 15% знижує бал канарки, сповільнюючи розкочування.
- **Споживання системних ресурсів CPU/RAM (`w_resources = 0.20`):** нижча вага. Дозволяє виявити витоки пам'яті до того, як вони спричинять аварію.

Якщо підсумковий `Score_total >= 90`, канарка вважається успішною і автоматично переходить на наступний рівень розкочування. Якщо `75 <= Score_total < 90`, розкочування призупиняється на додатковий час спостереження. При `Score_total < 75` конвеєр негайно запускає процедуру автоматичного відкату (Auto-Rollback).

## 6. Інженерний компроміс: адаптивне геометричне розширення фаз

Математичний аналіз задає залізне обмеження: **чим менший радіус ураження (нижча частка `c`), тим довшим має бути bake time**.

Щоб не чекати 8 годин на низькому трафіку, автоматизовані конвеєри використовують адаптивне геометричне розширення фаз:

```
Фаза 1:  1% трафіку  →  bake time = 10 хв  (перевірка катастрофічних крашів p > 5%)
Фаза 2:  5% трафіку  →  bake time = 15 хв  (накопичення статистики для Δp = 0.4%)
Фаза 3: 25% трафіку  →  bake time = 20 хв  (фінальна перевірка p99 latency)
Фаза 4: 100% трафіку →  реліз завершено
```

Така комбінація дозволяє відсікти очевидні аварії на першій хвилині (де `Δp` велике, тому необхідне `n` є малим), а точні статистичні відхилення виявити на фазі 5–25% за розумний час.
