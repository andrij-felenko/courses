# ⚙️ Тривкий DeviceRepository: код, який стаття лише пообіцяла

Стаття зупинилася на межі обіцянки. Вона показала наївний файл, перелічила чотири камені, об які він спотикається, і сказала: річ, що вирішує всі чотири, зветься базою даних, а повний тривкий репозиторій — з атомарним записом, версією на SQLite за тим самим портом і тестом на переживання рестарту — зібрано окремо. Ось це «окремо». Тут ми напишемо той код цілком: не ескіз, не псевдокод, а дві робочі реалізації одного порту, кожну доведену до стану, у якому їй можна довірити правду дому.

І одразу задамо тон, бо в ньому весь сенс вправи. Реалізацій буде **дві** — своя, зроблена руками з файлу, і чужа, узята з полиці разом із SQLite, — а порт над ними **один і той самий**. Доказом, що ми не зшахраювали, стане не наше слово, а те, що `HubService`, `decide` і сценарії дверей не зміняться **ні на літеру**, коли ми підмінимо одну реалізацію іншою. Порт — це контракт; дві геть різні його виконавиці мусять бути взаємозамінні до останнього байта поведінки. Якщо це справдиться, форма, яку [ми заклали у v2](root:progarch/dh-v2-hexagon), відпрацювала свій хліб.

## Задача: той самий порт, але цього разу по-справжньому тривкий

Випишімо ціль точно, бо неясна ціль дає ласий на виправдання код. Реєстр пристроїв ще у v2 сховано за портом `DeviceRepository`, і [зібраний DH v2 ставив за ним `InMemoryDeviceRepository`](root:progarch/dh-v2-hexagon/proj-dh-v2.md) — чесну тимчасову затичку, що тримала пристрої в оперативній памʼяті й гинула разом із процесом. Наше завдання — дати за той **самий** порт реалізацію, яка процес переживає.

Порт трохи підріс проти кістяка: реєстру тепер потрібен не лише «поклади» і «дай усе», а й **точковий доступ за ключем** — тож у контракті три обіцянки, `save` · `get` · `all`, а кожен пристрій носить стабільний `id`, за яким його впізнають і в памʼяті, і на диску:

:::tabs
```py
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Device:                         # доменний пристрій із реєстру — тепер з ключем
    id: str                           # стабільний ідентифікатор, напр. "lock-1"
    kind: str                         # "lock", "plug", "thermostat"…
    room: str
    state: str = "unknown"

    def to_dict(self) -> dict:        # плаский рядок для серіалізації у файл
        return {"id": self.id, "kind": self.kind, "room": self.room, "state": self.state}

    @staticmethod
    def from_dict(r: dict) -> "Device":
        return Device(r["id"], r["kind"], r["room"], r.get("state", "unknown"))

class DeviceRepository(Protocol):     # ПОРТ: три обіцянки, і жодного слова про носій
    def save(self, d: Device) -> None: ...          # поклади (або онови за id)
    def get(self, id: str) -> Device | None: ...    # дай один за ключем, або нічого
    def all(self) -> list[Device]: ...              # дай усіх
```
```ts
interface Device {                    // доменний пристрій із реєстру — тепер з ключем
  id: string;                         // стабільний ідентифікатор, напр. "lock-1"
  kind: string;                       // "lock", "plug", "thermostat"…
  room: string;
  state: string;
}

interface DeviceRepository {          // ПОРТ: три обіцянки, і жодного слова про носій
  save(d: Device): void;              // поклади (або онови за id)
  get(id: string): Device | undefined;// дай один за ключем, або нічого
  all(): Device[];                    // дай усіх
}
```
:::

Зверніть увагу, чого в порті **немає**: ні слова «файл», ні слова «SQL», ні натяку, де саме житимуть байти. Порт описує, що застосунок уміє **питати** в сховища, і мовчить про те, хто відповідає. Саме ця мовчанка й дозволить нам поставити за нього то файл, то базу, не зачепивши нікого вище. А «чесно тривка» реалізація — це та, що закриває всі [чотири камені зі статті](root:progarch/dh-data-model): атомарний запис, що не рветься на краху; впускання писарів по черзі; швидкий пошук за частиною; групування змін «усе або нічого». Файлова версія доб'є руками перший камінь і чесно оголить решту; SQLite забере всі чотири за так. Почнімо з файлу — бо на ньому найкраще видно, **чому** запис на диск складніший, ніж здається.

## Файлова версія: запис, що не рветься на краху

Наївний запис зі статті — `open(path, "w")`, тоді `json.dump` — падає на першому ж камені, і варто розібрати падіння кадр за кадром, бо в ньому вся суть. Річ у режимі `"w"`: він відкриває файл із прапорцем зрізання (`O_TRUNC`), а зрізання стається **в мить відкриття**, ще до того, як твій код напише бодай байт. Тобто старий вміст гине **першим**, а новий наповнює порожнечу **потім** — і між цими двома митями на диску немає жодної цілої версії:

**Умова: на диску цілий реєстр із трьох пристроїв, іде звичайний нічний деплой.**
```
до:     dh-devices.json = [{"id":"lock-1",…},{…},{…}]   (214 байтів, цілий)
t0:     open("dh-devices.json", "w")   ← O_TRUNC: файл МИТТЄВО обрізано до 0 байтів
t1:     ⚡ процес убито (деплой) — до json.dump(...) виконання не дійшло
після:  dh-devices.json = ""            (0 байтів — порожньо)
старт:  json.load(open("dh-devices.json"))  → JSONDecodeError → реєстр зник НАЗАВЖДИ
```

Ось де жало: втрачено не останню зміну, а **весь реєстр**. Наївний запис зробив сховище **менш** живучим за памʼять — бо тепер краху боїться навіть те, що вже було надійно збережене вчора. Це нестерпно: сховище, яке псує старі дані, гірше за відсутність сховища.

Ліки — не писати поверх живого файлу взагалі. Пишемо новий вміст **збоку**, у тимчасовий файл, доводимо його до диска через `fsync`, і лише тоді одним рухом **перейменовуємо** тимчасовий поверх справжнього. Ось повний `FileDeviceRepository` за нашим портом — з атомарним записом усередині:

:::tabs
```py
import json, os, threading

class FileDeviceRepository:                        # за портом DeviceRepository з v2
    def __init__(self, path: str = "dh-devices.json"):
        self._path = path
        self._lock = threading.Lock()              # черга писарів — про неї нижче
        self._devices: dict[str, Device] = self._load()

    def _load(self) -> dict[str, Device]:
        try:
            with open(self._path, encoding="utf-8") as f:
                rows = json.load(f)
        except FileNotFoundError:
            return {}                              # перший запуск — дім порожній
        return {r["id"]: Device.from_dict(r) for r in rows}

    def save(self, d: Device) -> None:
        with self._lock:                           # один писар за раз
            self._devices[d.id] = d                # онови памʼять…
            self._flush()                          # …і відразу поклади ВЕСЬ реєстр на диск

    def get(self, id: str) -> Device | None:
        return self._devices.get(id)

    def all(self) -> list[Device]:
        return list(self._devices.values())

    def _flush(self) -> None:                      # атомарний тривкий запис — серце класу
        tmp = self._path + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump([d.to_dict() for d in self._devices.values()], f, ensure_ascii=False)
            f.flush()                              # з буфера мови → в кеш ОС (ще летюче!)
            os.fsync(f.fileno())                   # кеш ОС → на носій, з підтвердженням
        os.replace(tmp, self._path)                # атомарна заміна: старий XOR новий
```
```ts
import * as fs from "node:fs";

class FileDeviceRepository {                        // за портом DeviceRepository з v2
  private devices: Map<string, Device>;
  constructor(private path = "dh-devices.json") {
    this.devices = this.load();
  }

  private load(): Map<string, Device> {
    try {
      const rows: Device[] = JSON.parse(fs.readFileSync(this.path, "utf8"));
      return new Map(rows.map((d) => [d.id, d]));
    } catch (e: any) {
      if (e.code === "ENOENT") return new Map();    // перший запуск — дім порожній
      throw e;
    }
  }

  save(d: Device): void {
    this.devices.set(d.id, d);                      // онови памʼять…
    this.flush();                                   // …і відразу поклади ВЕСЬ реєстр на диск
  }
  get(id: string): Device | undefined { return this.devices.get(id); }
  all(): Device[] { return [...this.devices.values()]; }

  private flush(): void {                           // атомарний тривкий запис — серце класу
    const tmp = this.path + ".tmp";
    const fd = fs.openSync(tmp, "w");
    fs.writeSync(fd, JSON.stringify([...this.devices.values()]));
    fs.fsyncSync(fd);                               // кеш ОС → на носій, з підтвердженням
    fs.closeSync(fd);
    fs.renameSync(tmp, this.path);                  // атомарна заміна: старий XOR новий
  }
}
```
:::

Чому саме перейменування **лікує** розірваний запис — і не абияк, а конструктивно, тобто вбиває поганий стан на корені, а не робить його рідшим? Бо `rename` (він же `os.replace`, він же системний виклик `rename(2)`) на одній файловій системі — **атомарна** операція. Стандарт POSIX вимагає буквально: доки перейменування триває, імʼя цілі лишається видимим іншим процесам і вказує **або** на старий файл, **або** на новий — ніколи на щось проміжне. Технічно це не копіювання байтів, а перемикання одного вказівника в каталозі: запис у теці, що донедавна показував на старий inode, миттю починає показувати на новий. Немає моменту, коли imʼя показує «нікуди» чи «на половину».

![Дві стратегії запису реєстру на диск, одна над одною. Угорі «наївно open('w')»: цілий старий файл, стрілка «open('w') → 0 байтів» веде у червону рамку «порожній / рваний файл», далі «write + fsync» до цілого нового файлу; під червоною рамкою напис, що краш у цьому вікні втрачає і старе, і нове. Унизу «атомарно tmp+rename»: цілий старий файл лишається недоторканим, збоку пишемо tmp і робимо fsync, тоді один атомарний rename дає новий файл; підпис знизу — у будь-яку мить path дорівнює або старому, або новому, третього стану нема](img/atomic-write.svg)
*Наївний `open('w')` спершу знищує старе (обрізає до нуля), а тоді наповнює порожнечу — і між цими митями цілого файлу на диску немає; краш у цьому вікні губить усе. Атомарний запис натомість будує новий файл збоку, не чіпаючи старого, і `rename` одним атомарним клацом перемикає імʼя зі старого inode на новий. Третього стану, у якому дані рвані, просто не існує.*

Порівняйте два світи. У наївному запису була **одна** ціль — живий файл, — і ми руйнували її на місці: спершу «обнулити», потім «наповнити», з фатальним провалом між кроками. В атомарному є **дві** цілі: недоторканий старий файл і повністю готовий новий, — і момент правди стиснуто в один неподільний перемикач між ними. Краш до `rename` лишає старий файл цілим (втратимо останню зміну, але не весь реєстр); краш після `rename` лишає цілим новий. Хоч куди впади — на диску завжди повна, справна версія. Оце й означає «прибрати проблему конструктивно»: ми не зменшили шанс розірваного файлу, ми зробили розірваний файл **неможливим**.

> 🔧 **Навіщо це.** Пʼять рядків замість одного — це не педантизм, це різниця між сховищем, якому можна довірити правду дому, і сховищем, що зраджує на першому ж деплої. Наївний варіант «працює» на кожному ручному прогоні й на кожній демонстрації — і саме тому підступний: він відкладає свою поразку до найгіршої миті, до збою живлення посеред запису на бойовому хабі. Атомарний запис коштує наперед — тимчасовий файл, `fsync`, перейменування, — але цю ціну платять раз, у коді, а не потім, у втрачених даних клієнта.

## Та сама задача мовою SQLite — і жодного рядка ядра не змінилось

Тепер найголовніше доведення модуля. Ми беремо ту саму трійцю обіцянок — `save` · `get` · `all` — і виконуємо її геть інакше: не файлом, а базою. Якщо порт справжній, застосунок різниці не помітить.

:::tabs
```py
import sqlite3

class SqliteDeviceRepository:                      # ТОЙ САМИЙ порт DeviceRepository
    def __init__(self, path: str = "dh.db"):
        self._db = sqlite3.connect(path)
        self._db.execute("PRAGMA journal_mode=WAL")   # читачі не блокують писаря
        self._db.execute("""
            CREATE TABLE IF NOT EXISTS devices (
                id    TEXT PRIMARY KEY,             # ключ реєстру — на рівні схеми
                kind  TEXT NOT NULL,
                room  TEXT NOT NULL,
                state TEXT NOT NULL
            )""")
        self._db.commit()

    def save(self, d: Device) -> None:
        self._db.execute(
            "INSERT INTO devices (id, kind, room, state) VALUES (?, ?, ?, ?) "
            "ON CONFLICT(id) DO UPDATE SET "        # поклади АБО онови за id — одним рухом
            "  kind=excluded.kind, room=excluded.room, state=excluded.state",
            (d.id, d.kind, d.room, d.state))
        self._db.commit()                          # ← межа тривкості: тут база робить fsync

    def get(self, id: str) -> Device | None:
        row = self._db.execute(
            "SELECT id, kind, room, state FROM devices WHERE id = ?", (id,)
        ).fetchone()                               # частковий пошук: один рядок за ключем
        return Device(*row) if row else None

    def all(self) -> list[Device]:
        rows = self._db.execute(
            "SELECT id, kind, room, state FROM devices").fetchall()
        return [Device(*r) for r in rows]
```
```ts
import { DatabaseSync } from "node:sqlite";         // вбудований у Node ≥ 22.5

class SqliteDeviceRepository {                      // ТОЙ САМИЙ порт DeviceRepository
  private db: DatabaseSync;
  constructor(path = "dh.db") {
    this.db = new DatabaseSync(path);
    this.db.exec("PRAGMA journal_mode=WAL");        // читачі не блокують писаря
    this.db.exec(`CREATE TABLE IF NOT EXISTS devices (
      id    TEXT PRIMARY KEY,                        -- ключ реєстру — на рівні схеми
      kind  TEXT NOT NULL,
      room  TEXT NOT NULL,
      state TEXT NOT NULL)`);
  }

  save(d: Device): void {
    this.db.prepare(
      `INSERT INTO devices (id, kind, room, state) VALUES (?, ?, ?, ?)
       ON CONFLICT(id) DO UPDATE SET               -- поклади АБО онови за id
         kind=excluded.kind, room=excluded.room, state=excluded.state`
    ).run(d.id, d.kind, d.room, d.state);           // run() автокомітить → тривко
  }
  get(id: string): Device | undefined {
    return this.db.prepare(
      "SELECT id, kind, room, state FROM devices WHERE id = ?"
    ).get(id) as Device | undefined;                // частковий пошук за ключем
  }
  all(): Device[] {
    return this.db.prepare(
      "SELECT id, kind, room, state FROM devices").all() as Device[];
  }
}
```
:::

І тепер — уся розписка за форму, в одному рядку. Щоб дім почав памʼятати себе через базу замість файлу, у **точці збірки** правиться рівно одне присвоєння, а `HubService` навіть не прокидається:

:::tabs
```py
def build(env: str) -> HubService:
    ...
    # було:   devices = InMemoryDeviceRepository()
    devices = SqliteDeviceRepository("dh.db")       # або FileDeviceRepository("dh-devices.json")
    return HubService(sensor, heater, devices, cfg) # ← сервіс не змінився ні на літеру
```
```ts

  // було:   const devices = new InMemoryDeviceRepository();
  const devices = new SqliteDeviceRepository("dh.db");   // або new FileDeviceRepository(...)
  return new HubService(sensor, heater, devices, cfg);   // ← сервіс не змінився ні на літеру
```

:::

Три реалізації — памʼять, файл, база — стоять за одним інтерфейсом і взаємозамінні в одному вузлі. Це і є доказ, що порт не декорація: `decide` чисте, `HubService` диригує обіцянками, а хто їх сповнить — вирішує єдиний рядок збірки. Форма купила нам право поміняти носій, не торкнувшись мозку.

А тепер погляньмо, що база дала **задарма** — усі чотири камені, об які розбився файл. **Атомарний тривкий запис**: `commit` (у Python його кличемо явно; `node:sqlite` автокомітить кожен запит окремою транзакцією) — це і є межа тривкості, у ній база злизує журнал на носій через `fsync`, а «підтверджений запис переживе будь-що» — це рівно та [літера D в ACID](root:sf-data/transactions-acid), заради якої весь клопіт. **Не втратити даних навіть на краху посеред запису** база вміє тим самим прийомом, що й ми з тимчасовим файлом, тільки дорослішим — [журналом попереднього запису](root:sf-data/write-ahead-log): спершу намір лягає в окремий журнал, і тільки цілий намір застосовується. **Писарі по черзі** — база впускає лише **одного** писаря за раз (навіть у режимі WAL): другий чекає, а не змішує свій запис із чужим. **Частковий пошук** — `get(id)` торкає рівно потрібний рядок за первинним ключем, не піднімаючи й не розбираючи весь реєстр. І **«усе або нічого»** — коли зміна зачепить кілька рядків, їх обгортають в одну транзакцію, і [агрегат ляже неподільно](root:progarch/dh-data-model), як ми й домовлялися.

Різницю в ціні найкраще видно на масштабі, і вона не про смак, а про порядок складності:

```
файл  · один save    = перепис УСЬОГО реєстру         → O(n) байтів на кожен запис
      · n записів поспіль                              → O(n²) сукупної роботи
      · «які пристрої в кухні?»                         → підняти й розібрати ВЕСЬ файл
sqlite· один save    = один рядок + оновлення індексу   → ~O(log n) на запис
      · get(id) / where room=?                          → торкає лише потрібні рядки
```

Поки пристроїв дюжина на один дім, обидва стовпці невідчутні — і файл був би чесною відповіддю. Коли їх сотні тисяч на багато домів у хмарі, ліва колонка вбиває систему, а права ледь помічає навантаження. Ось чому база — не забаганка, а [та сама відповідь на ті самі чотири задачі](root:progarch/dh-v2-hexagon), роками виточена й вивірена так, як ми самотужки не виточимо.

## Двоє писарів і чому запис серіалізують

Один камінь я сховав у код без пояснення — `threading.Lock` у файловій версії. Час пояснити, бо він тримає цілий клас чесним. Згадаймо, що в дім v2 ведуть [двоє дверей](root:progarch/dh-v2-hexagon): автономний цикл у фоновому потоці й CLI у головному. Обидві можуть захотіти записати реєстр — і якщо пустити їх у файл одночасно, стається тиха катастрофа, від якої атомарний `rename` **не** рятує.

![Гонка двох писарів у той самий файл. Вісь часу вниз, дві колонки — автономний цикл і CLI. Крок 1: цикл читає файл і бачить {замок}. Крок 2: CLI читає той самий файл і теж бачить {замок}. Крок 3: цикл робить rename і пише {замок, темп.=21}. Крок 4: CLI робить rename і пише {замок, лампа}, і червона стрілка «затирає» веде від кроку 3 до кроку 4. Підсумок унизу: крок 4 перезаписав крок 3, тож оновлення температури зникло; ліки — серіалізувати запис, і SQLite тримає цю чергу сам](img/two-writers.svg)
*Обидва писарі читають ту саму базу — реєстр із одним замком, — кожен додає своє в памʼяті й пише повний знімок назад. Оскільки читали вони однакове, останній `rename` затирає передостанній: у файлі лишається `{замок, лампа}`, а оновлення температури від циклу зникло безслідно. Атомарний запис захистив кожен файл від рваності, але не захистив реєстр від загубленої зміни.*

Ця біда зветься **загубленим оновленням** (lost update), і росте вона з того, що кожен наш `save` — це насправді «прочитати весь реєстр → змінити свою частинку → записати весь назад». Два таких цикли, що переплелися, читають однакову основу й пишуть, не бачачи змін одне одного; хто перейменував останнім — той і виграв, а праця іншого щезла. Атомарний `rename` тут безсилий: він гарантує, що кожен **окремий** запис цілий, але нічого не каже про **двох** писарів, що женуться навперейми.

Ліки одне слово — **серіалізувати**: впустити писарів у критичну ділянку «читай-зміни-запиши» по одному. Найпростіше — замок, як у коді вище: `with self._lock` навколо `save` робить так, що доки один потік не дописав і не перейменував, другий чекає на порозі. Чистіший, але дорожчий за перебудову шлях — **єдиний власник**: хай реєстром володіє лише цикл, а CLI не пише сам, а **кладе команду в чергу**, яку цикл вибирає між тіками; тоді пишучий потік один-єдиний, і гонки нема з чого початися. А найдешевший шлях — не писати черги руками взагалі, бо [SQLite вже тримає її всередині](root:sf-data/write-ahead-log): другий писар отримає «зайнято» й дочекається свого, база сама впорядкує. Це ще одна причина, чому чесне сховище тяжіє до бази: черга писарів у ній — не наш клопіт.

Одне чесне уточнення про мови. У Node з його однопотоковим циклом подій **синхронний** `flush` не переплітається сам із собою — доки `renameSync` не повернувся, інший обробник не виконається, тож наведений TypeScript від цієї конкретної гонки застрахований самою моделлю. Але щойно запис стане асинхронним (`fs.promises`), вікно для переплетення відчиниться знову — і замок або черга знадобляться так само, як у потоковому Python. Форма проблеми від стека не залежить; лише мить, коли вона кусає, різна.

## Тест: реєстр переживає смерть процесу

Тепер притиснемо головну обіцянку до стіни — і зробимо це так, щоб доказ не можна було підробити. Уся хитрість тесту в одному русі: ми **викидаємо** обʼєкт репозиторію дощенту й відкриваємо **новий** над тим самим шляхом. Це і є вбивство процесу в мініатюрі: між «до» і «після» не лишається жодного спільного байта в памʼяті — єдиний канал, яким правда може просочитися крізь «рестарт», це тривкий носій. Якщо новий обʼєкт побачив пристрої — значить, вони справді на диску, а не в чиємусь полі.

І ще один зиск: той самий тест ганяємо **над обома** реалізаціями, файлом і базою. Так він заразом стає крихітним контрактним тестом — доводить, що дві різні виконавиці порту поводяться однаково там, де це найважливіше:

:::tabs
```py
import pytest

@pytest.fixture(params=["file", "sqlite"])
def open_repo(request, tmp_path):
    """Повертає функцію, що ВІДКРИВАЄ репозиторій над тим самим шляхом.
    Покликати її двічі = два різні обʼєкти над одним сховищем."""
    def _open():
        if request.param == "file":
            return FileDeviceRepository(str(tmp_path / "dh-devices.json"))
        return SqliteDeviceRepository(str(tmp_path / "dh.db"))
    return _open

def test_registry_survives_restart(open_repo):
    repo = open_repo()
    repo.save(Device("lock-1", "lock", "вхідні двері"))
    repo.save(Device("plug-2", "plug", "кухня"))

    del repo                                    # ← «смерть процесу»: обʼєкт і вся його RAM зникли

    reborn = open_repo()                         # новий процес відкриває те саме сховище
    ids = {d.id for d in reborn.all()}
    assert ids == {"lock-1", "plug-2"}           # реєстр уцілів попід «рестартом»
    assert reborn.get("plug-2").room == "кухня"  # і поля на місці, не лише ключі
```

```ts
import { test } from "node:test";
import assert from "node:assert";
import { mkdtempSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";

for (const kind of ["file", "sqlite"] as const) {
  test(`реєстр переживає рестарт (${kind})`, () => {
    const dir = mkdtempSync(join(tmpdir(), "dh-"));
    const open = () =>                            // відкрити репозиторій над тим самим шляхом
      kind === "file"
        ? new FileDeviceRepository(join(dir, "dh-devices.json"))
        : new SqliteDeviceRepository(join(dir, "dh.db"));

    let repo = open();
    repo.save({ id: "lock-1", kind: "lock", room: "вхідні двері", state: "unknown" });
    repo.save({ id: "plug-2", kind: "plug", room: "кухня", state: "unknown" });

    repo = open();                               // ← «смерть процесу»: новий обʼєкт, стара RAM стерта

    const ids = new Set(repo.all().map((d) => d.id));
    assert.deepStrictEqual(ids, new Set(["lock-1", "plug-2"]));   // реєстр уцілів
    assert.strictEqual(repo.get("plug-2")!.room, "кухня");        // і поля на місці
  });
```

Сила цього тесту — у контрасті, який він мовчки ставить. Прожени рівно ті самі рядки над `InMemoryDeviceRepository` — і `reborn.all()` поверне порожньо, бо новий обʼєкт починає з порожнього словника, а старий помер і забрав усе. Той самий сценарій, зелений для файлу й бази й **червоний** для памʼяті, і є вимірювання тривкості: він точно окреслює, що ми купили, замінивши затичку на справжнє сховище. Жодного `sleep`, жодного справжнього перезапуску ОС — досить викинути обʼєкт і відкрити носій наново, бо саме через носій, і лише через нього, дані течуть попід розривом.

## Складність і пастки

**`fsync` коштує — і тому тривкість дозують.** Кожен `save` тут чесно жде підтвердження з носія, а `fsync` — операція повільна: на звичайному диску це одиниці мілісекунд, тобто сотні записів на секунду, не більше. Для дому з його дюжиною пристроїв це невидимо; для гарячого шляху, що пише тисячі разів на секунду, «`fsync` на кожен ключ» стане стіною. Дорослі бази тому дають **вибір**: групувати багато змін в одну транзакцію й платити одним `fsync` за всі, або (як `PRAGMA synchronous=NORMAL` у WAL) свідомо послабити гарантію заради швидкості. Тривкість — не тумблер «увімк/вимк», а повзунок між «швидко» і «нічого не втрачу»; знати, де його поставити, — окреме рішення на кожен клас даних.

**Перейменування атомарне лише в межах однієї файлової системи.** Тимчасовий файл ми навмисне кладемо **поряд** із цільовим (`path + ".tmp"`), а не в умовний `/tmp`. Якби `tmp` опинився на іншому томі, `rename` не зміг би просто перемкнути вказівник у каталозі — довелося б копіювати байти через межу (`EXDEV`), а копіювання вже **не** атомарне, і все жало повернулося б. Правило просте: тимчасовий файл — у тій самій теці, що й цільовий.

**`rename` віддав дані, але каталог теж треба злити.** Найтонша пастка: після `os.replace` сам факт перейменування якийсь час живе в кеші ОС — той самий летючий кеш. Щоб перейменування пережило раптовий збій живлення напевно, бездоганний рецепт додає ще один крок — `fsync` **батьківської теки** після заміни. Ми його опустили заради ясності, і ціна цього мʼяка: без нього краш може відкотити нас до **старого цілого файлу** (втратимо останню зміну), але **ніколи** — до рваного. Тобто пропуск directory-`fsync` коштує підтвердженого запису, а не цілості; знати цю різницю важливо, бо перше — прикрість, друге — катастрофа.

**Фейк і справжнє мовчки розходяться.** У нас тепер три виконавиці порту, і `InMemoryDeviceRepository` [лишається фейком за тим самим контрактом](root:progarch/dh-v2-hexagon/proj-dh-v2.md). Ніщо, крім нашої пильності, не змушує памʼятну підробку поводитися точно як `SqliteDeviceRepository` — день у день вони розійдуться (фейк стерпить дублікат `id`, база — ні), і зелений тест на фейку почне брехати про прод. Привʼязь від цього одна — [ганяти всі реалізації спільним контрактним набором](root:progarch/test-doubles-when/proj-verified-fake.md); наш параметризований тест на рестарт — перша ниточка такого набору, і його варто доростити рештою обіцянок порту.

**Схема — теж стан, і вона змінюється.** Сьогодні `Device` має чотири поля; завтра додасться `installed_at`, і старі рядки в базі та старі записи у файлі його не матимуть. `from_dict` уже підстелив соломки (`r.get("state", "unknown")`), але це латка, не стратегія. Чесна відповідь — **версія схеми** й міграції: колонка `version` у файлі чи `PRAGMA user_version` у SQLite, і код, що піднімає старі дані до нового вигляду. Тривке сховище живе довше за будь-яку одну форму даних — і ця довговічність сама стає задачею, щойно дім переживе перше своє оновлення.

Отут і замикається вся вправа. Ми написали не «збереження в базу», а дві чесні відповіді на одне питання — як відчепити життя фактів від життя процесу, — і довели зеленим, що обидві тримають реєстр попід рестартом, а порт над ними не здригнувся. Файл виявився чесним ескізом із стелею на масштабі; SQLite — дорослою відповіддю, що бере всі чотири камені за так. А головне лишилося тим самим, з чого ми почали: коли сховище сховане за портом, вибір носія стає одним рядком у точці збірки, а не операцією на серці системи.
