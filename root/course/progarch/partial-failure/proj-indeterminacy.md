# ⚙️ Три світи за однією тишею: робочий прогін невідання

Ми вже знаємо на словах: за однією тишею таймауту ховаються три несумісні правди, і зсередини їх не розрізнити. Але «знати на словах» — крихка річ. Варто сісти й дописати повтор, як рука сама тягнеться зробити те, що на папері здавалося очевидно небезпечним. Тому зробімо невідання **відчутним** — таким, що його можна запустити й поміряти на лічильнику.

Задача проста до сміховинності. Застосунок шле хабові одну команду — «відчини замок №7» — поганим каналом. Ми змусимо канал зламатися трьома способами по черзі й подивимось **дві речі поряд**: що бачить клієнт і що насправді сталося з реле по той бік. Ідея всього прогону — вставити на хабі **лічильник спрацювань**, якого клієнт не бачить. Цей лічильник — детектор правди: він покаже те, що таймаут приховує, і на ньому ми впіймаємо, як наївний повтор задвоює ефект — а тоді як мінімальна пара заходів це лікує.

Мова тут — Go: канал, що ковтає пакети, робота, яку хаб виконує «десь там», і клієнт, що чекає з таймаутом, — усе це рідні для Go `select`, `time.After` і буферований канал. Наприкінці побачимо, що в однопотоковому рантаймі (Node, `asyncio`) зникає одна деталь, а логіка часткової відмови лишається та сама.

## Стенд: хаб із лічильником, канал зі збоями, клієнт із терпінням

Три деталі, і кожна — рівно те, чим була б у житті. **Хаб** виконує команду й лічить кожне фізичне смикання реле; цей `fires` і є наш інструмент. **Канал** уміє не доставити роботу трьома різними способами. **Клієнт** чекає підтвердження не довше за своє терпіння, а на таймауті повертає помилку — не знаючи про той бік нічого.

Почнімо з хаба. Замок №7 має стан (відчинено чи ні), а `fires` рахує, скільки разів реле реально смикнулось — не «скільки команд надіслав клієнт», а скільки разів двері фізично клацнули:

```go
// Hub — «хаб у передпокої». Виконує команди й лічить КОЖНЕ спрацювання реле.
// fires — не про наміри клієнта, а про фізику: скільки разів двері клацнули.
type Hub struct {
	mu    sync.Mutex
	open  bool // стан замка №7
	fires int  // ← слід кожного смикання реле; це наш детектор правди
}

func (h *Hub) unlock() {
	h.mu.Lock()
	defer h.mu.Unlock()
	h.open = true
	h.fires++
}

func (h *Hub) state() string { // «замок №7 зараз який?»
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.open {
		return "відчинено"
	}
	return "замкнено"
}

func (h *Hub) firesCount() int {
	h.mu.Lock()
	defer h.mu.Unlock()
	return h.fires
}
```

Тепер канал. Він не знає, *що* за робота, — знає лише, як її (не) донести. Три збої — це рівно три світи з попереднього кроку: пакет зник туди, робота сталася а підтвердження зникло назад, робота повзе й дійде вже після того, як клієнт здався:

```go
type Fault int

const (
	None    Fault = iota
	DropReq       // (1) запит зник дорогою ТУДИ — хаб команди не бачив
	DropAck       // (2) хаб виконав, підтвердження зникло НАЗАД
	SlowReq       // (3) запит повзе — дійде, та вже після терпіння клієнта
)

// Link — ненадійний канал. faults[i] — який збій станеться на i-ту спробу
// (далі канал чистий). work() виконує ефект на боці хаба й повертає підтвердження.
type Link struct {
	faults  []Fault
	slow    time.Duration
	attempt int
}

func (l *Link) send(work func() string) <-chan string {
	fault := None
	if l.attempt < len(l.faults) {
		fault = l.faults[l.attempt]
	}
	l.attempt++

	reply := make(chan string, 1) // буфер 1: горутина не зависне, коли клієнт уже пішов
	go func() {
		switch fault {
		case DropReq:
			return // хаб work() не викликав — ні ефекту, ні відповіді
		case DropAck:
			work() // ефект СТАВСЯ…
			return // …а підтвердження зникло: клієнту тиша
		case SlowReq:
			time.Sleep(l.slow) // повзе довше за терпіння клієнта
			work()             // зрештою виконає — але клієнт уже не слухає
			reply <- "пізно"   // відповідь прийде в порожнечу
		default:
			reply <- work() // ідеальний прохід: виконали й підтвердили
		}
	}()
	return reply
}
```

І клієнт. Уся його драма — в одному `select`: гонка між підтвердженням і власним терпінням. Хто перший, той і визначає результат:

```go
// clientUnlock шле «відчини замок №7» і чекає НЕ довше patience.
// На таймауті повертає помилку — не знаючи, ЩО там сталося.
func clientUnlock(l *Link, h *Hub, patience time.Duration) error {
	reply := l.send(func() string { h.unlock(); return "ok" })
	select {
	case <-reply:
		return nil // почули «ok» — успіх
	case <-time.After(patience):
		return errors.New("таймаут") // тиша. Котрий зі світів — невідомо.
	}
}
```

Ось де ховається все жало. `DropReq` і `DropAck` різняться однією-єдиною лінією — чи викликано `work()`. Але для клієнта обидва однакові: у жодному з них у `reply` нічого не приходить, тож `select` щоразу випадає в гілку `time.After` і повертає **ту саму** помилку. Клієнт фізично не має слова, щоб розрізнити «не сталося» і «сталося, та я не почув».

> 🔧 **Навіщо це.** `fires` на хабі — не прикраса для тесту, а єдина точка, з якої видно правду. У проді її роль грає журнал спрацювань чи метрика лічильника: коли клієнт бачить лише таймаут, спитати «скільки разів реле реально смикнулось» можна тільки з боку того, хто смикав. Будуватимеш повтори наосліп, не маючи такого лічильника, — двоїтимеш ефект і навіть не знатимеш про це.

## Прогін перший: три світи, один таймаут

Проженімо всі три збої з терпінням у сто мілісекунд, а «повільному» дамо триста — тобто втричі більше, ніж клієнт готовий чекати. Після кожного випадку трохи почекаємо, щоб `SlowReq` встиг доповзти, і аж тоді спитаємо лічильник:

```go
func runWorlds() {
	patience := 100 * time.Millisecond
	cases := []struct {
		name  string
		fault Fault
	}{
		{"(1) запит зник туди", DropReq},
		{"(2) підтвердження зникло", DropAck},
		{"(3) запит повзе", SlowReq},
	}
	for _, c := range cases {
		hub := &Hub{}
		link := &Link{faults: []Fault{c.fault}, slow: 300 * time.Millisecond}

		err := clientUnlock(link, hub, patience)
		time.Sleep(350 * time.Millisecond) // дати «повільному» доповзти — щоб побачити правду

		fmt.Printf("%-24s клієнт: %-8s реле: %d\n", c.name, label(err), hub.firesCount())
	}
}

func label(err error) string {
	if err == nil {
		return "успіх"
	}
	return err.Error()
}
```

Друкує таке:

```
(1) запит зник туди      клієнт: таймаут  реле: 0
(2) підтвердження зникло  клієнт: таймаут  реле: 1
(3) запит повзе          клієнт: таймаут  реле: 1
```

Ось воно, чорним по білому. Ліва колонка — те, що бачить клієнт, — **однакова в усіх трьох рядках**: таймаут, таймаут, таймаут. Права колонка — правда з хаба — **різна**: нуль, один, один. Один спостережний факт на екрані клієнта, три різні стани світу за ним. Це вже не метафора з попереднього кроку, а вихід програми, який можна перезапустити.

Три рядки: (1) запит зник туди — хаб не бачив команди — таймаут — 0 — повтор безпечний; (2) підтвердження зникло назад — хаб виконав ефект — таймаут — 1 — повтор ЗАДВОЇТЬ; (3) запит повзе, не дочекались — виконає, але вже пізно — таймаут — 1 — повтор дасть гонку. *Один прогін виводить три світи в один стовпчик таймаутів — а лічильник на хабі розводить їх назад. Саме цей розрив між «що бачив клієнт» і «що сталось насправді» і є невідання, тепер уже вимірне.*

## Лічильник ловить те, чого клієнт не бачить — і наївний повтор двоїть

Тепер зробімо те, до чого рука тягнеться сама: раз таймаут — повторімо. Здається безпечним: підтвердження не прийшло, отже, спробуймо ще. Пастка в тому, що канал у житті глючить **минуще** — перший раз підтвердження зникло, а на повторі вже пройшло. Змоделюймо саме це: `faults: []Fault{DropAck}` — збій один раз, далі канал чистий. Ось наївний повтор — і в Go, і мовою стеку поряд, бо урок тут той самий:

:::tabs
```go
// Наївний повтор: таймаут → ще раз. Небезпечно — таймаут ≠ «не виконалось».
func naiveRetry(l *Link, h *Hub, patience time.Duration, tries int) error {
	for i := 0; i < tries; i++ {
		if err := clientUnlock(l, h, patience); err == nil {
			return nil // почули «ok» — виходимо
		}
		// таймаут. Замок не чіпали — чи вже відчинили, а підтвердження зникло? Невідомо.
		// Якщо відчинили — цей повтор смикне реле ВДРУГЕ.
	}
	return errors.New("вичерпано спроби")
}

func runNaive() {
	hub := &Hub{}
	link := &Link{faults: []Fault{DropAck}} // збій раз, тоді канал чистий
	err := naiveRetry(link, hub, 100*time.Millisecond, 3)
	fmt.Printf("наївний повтор: клієнт: %s | реле смикнулось: %d\n", label(err), hub.firesCount())
	// → наївний повтор: клієнт: успіх | реле смикнулось: 2
}
```
```ts
// Стенд (Hub, Link, clientUnlock) — прямий переклад Go (в однопотоковому рантаймі — без мьютекса).
// Наївний повтор: таймаут → ще раз. Небезпечно — таймаут ≠ «не виконалось».
async function naiveRetry(link: Link, hub: Hub, patienceMs: number, tries: number) {
  for (let i = 0; i < tries; i++) {
    try {
      await clientUnlock(link, hub, patienceMs); // чекаємо ack або таймаут
      return;                                    // почули «ok» — виходимо
    } catch {
      // таймаут. Не чіпали — чи вже відчинили, а ack зник? Невідомо.
      // Якщо відчинили — цей повтор смикне реле ВДРУГЕ.
    }
  }
  throw new Error("вичерпано спроби");
}

const hub = new Hub();
const link = new Link(["dropAck"]);              // збій раз, тоді канал чистий
await naiveRetry(link, hub, 100, 3);
console.log(`клієнт: успіх | реле смикнулось: ${hub.fires}`); // → 2
```
:::

**Умова: підтвердження зникає на першій спробі, канал відпускає на другій; терпіння 100 мс.**

Проженімо в голові по лічильнику. Спроба перша йде через `DropAck`: `work()` смикає реле (`fires` стає **1**), але підтвердження зникає — клієнт ловить таймаут і повторює. Спроба друга йде вже чистим каналом: `work()` смикає реле **вдруге** (`fires` стає **2**) і повертає «ok» — клієнт бачить успіх. **Клієнт задоволений, а реле смикнулось двічі.** Двері, які вже були відчинені, відчинилися ще раз: зайвий запис у журналі, зайве клацання — а якщо між спробами хтось підійшов і замкнув їх рукою, повтор мовчки відчинив назад те, що людина щойно зачинила. Для команди «додай 10 до балансу» те саме задвоєння коштувало б грошей.

Причина рівно та, що ми бачили в стенді: `catch` і `err != nil` виглядають як «не вийшло», але за мережею вони означають лише «я не почув відповіді». Побудувати повтор на цій хибі — значить прийняти тишу за доказ бездіяльності, якого в ній немає.

![Дві доріжки-порівняння того самого збою «підтвердження зникло, тоді канал чистий». Ліва «Наївний повтор — без ключа»: спроба 1 → хаб реле +1, лічильник = 1 → ack загубився, клієнт таймаут → спроба 2 → хаб реле +1 ЗНОВУ, лічильник = 2 → ack ok, клієнт успіх; банер «лічильник = 2 — ефект ЗАДВОЄНО». Права «З ключем на команді»: спроба 1 → реле +1, лічильник = 1, запам'ятав K → ack загубився, таймаут → спроба 2 з тим самим K → хаб бачить дубль, реле не чіпає, = 1 → ack ok, успіх; банер «лічильник = 1 — ключ відсік дубль».](img/retry-double-vs-key.svg)
*Той самий збій каналу й той самий повтор — але зліва хаб виконує ефект двічі, а справа ключ на команді дає йому впізнати дубль і смикнути реле рівно раз. Уся різниця — чи несе повтор те саме посвідчення, що й перша спроба.*

## Чесна відповідь: ключ на команді робить повтор безпечним

Розрізнити три світи зсередини не можна — це ми довели лічильником. Тож ціль зміщується: не «вгадати, що сталося», а зробити так, щоб **повтор не двоїв ефект, навіть якщо перша спроба таки дійшла**. Найпряміший спосіб — приколоти до команди **ключ ідемпотентності**: унікальне посвідчення, згенероване **раз** на логічну команду й незмінне на всіх повторах. Хаб запам'ятовує кожен виконаний ключ і на дубль віддає збережену відповідь, **не чіпаючи реле вдруге**:

```go
// KeyedHub — той самий хаб, але команда несе КЛЮЧ. Уже бачений ключ повертає
// збережений результат, не виконуючи ефекту повторно.
type KeyedHub struct {
	mu    sync.Mutex
	open  bool
	fires int
	seen  map[string]string // ключ команди → збережений результат
}

func NewKeyedHub() *KeyedHub { return &KeyedHub{seen: map[string]string{}} }

func (h *KeyedHub) unlock(key string) string {
	h.mu.Lock()
	defer h.mu.Unlock()
	if res, dup := h.seen[key]; dup {
		return res // ДУБЛЬ: віддаємо збережене, реле не чіпаємо
	}
	h.open = true
	h.fires++                     // виконуємо РІВНО раз на ключ
	h.seen[key] = "ok: відчинено" // перевірка → ефект → запис ключа: усе під ОДНИМ замком
	return h.seen[key]
}

func (h *KeyedHub) firesCount() int { h.mu.Lock(); defer h.mu.Unlock(); return h.fires }
```

Клієнт генерує ключ **один раз, ще до першої спроби**, і носить його незмінним крізь усі повтори:

```go
// safeRetry: ОДИН ключ на всю логічну команду (у житті — UUID v4), той самий
// на кожній спробі. Дубль по дорозі хаб відсіє сам.
func safeRetry(l *Link, h *KeyedHub, patience time.Duration, tries int) error {
	key := "unlock-7:9f2c1a" // згенеровано РАЗ; той самий на всіх спробах
	for i := 0; i < tries; i++ {
		reply := l.send(func() string { return h.unlock(key) })
		select {
		case <-reply:
			return nil
		case <-time.After(patience):
			// таймаут → повтор із ТИМ САМИМ ключем
		}
	}
	return errors.New("вичерпано спроби")
}

func runSafe() {
	hub := NewKeyedHub()
	link := &Link{faults: []Fault{DropAck}} // той самий збій, що й у наївному прогоні
	err := safeRetry(link, hub, 100*time.Millisecond, 3)
	fmt.Printf("повтор із ключем: клієнт: %s | реле смикнулось: %d\n", label(err), hub.firesCount())
	// → повтор із ключем: клієнт: успіх | реле смикнулось: 1
}
```

**Умова та сама, що й у наївному прогоні — тільки команда тепер несе ключ.** Спроба перша (`DropAck`): `unlock(key)` не бачить ключа в `seen`, тож смикає реле (`fires` = **1**), кладе `seen[key]` — і підтвердження зникає, клієнт ловить таймаут. Спроба друга йде чистим каналом із **тим самим** ключем: `unlock(key)` знаходить ключ у `seen`, повертає збережене «ok» і реле **не чіпає** — `fires` лишається **1**. Клієнт бачить успіх, реле смикнулось рівно раз. Задвоєння зникло, і зникло не тому, що ми вгадали правильний світ, а тому, що зробили світи **нерозрізненними для результату**: хоч дійшла перша спроба, хоч ні — підсумок один.

Це не наша вигадка, а щоденна практика платіжних API: Stripe приймає заголовок `Idempotency-Key` на кожному POST, зберігає відповідь першого запиту під цим ключем і на будь-який повтор із тим самим ключем повертає той самий результат (радять брати UUID v4, ключ живе близько доби). Повний розбір самого поняття — [ідемпотентність](book:programming/idempotency); нам тут важило одне: ключ перетворив небезпечний повтор на безкарний. Він же перетворює доставку [«щонайменше раз»](book:programming/delivery-guarantees) на **ефект «рівно раз»** — саме те, чого ми й хотіли, не вміючи гарантувати саму доставку.

## І коли ключа мало: звірка через справжній стан

Ключ рятує повтор, але буває, що його ніде поставити — команду шле стороння система, яка про ключі не чула, або ти просто хочеш **пересвідчитися**, а не покладатися на пам'ять хаба. Тоді працює друга чесна відповідь: не гадати, а піти й **прочитати справжній стан** — «замок №7 зараз який?» — і діяти вже з правди. Читання — операція без побічного ефекту, тож саме читання повторювати завжди безпечно:

```go
// reconcile: на таймауті не повторюємо наосліп, а питаємо ПРАВДУ й діємо з неї.
func reconcile(l *Link, h *Hub, patience time.Duration) error {
	if err := clientUnlock(l, h, patience); err == nil {
		return nil // почули «ok» — усе гаразд
	}
	// таймаут: не гадаємо, котрий зі світів справдився. Читаємо стан замка.
	reply := l.send(h.state) // h.state має тип func() string — рівно те, що чекає канал
	select {
	case st := <-reply:
		if st == "відчинено" {
			return nil // замок таки відчинений → команда спрацювала, повтор НЕ потрібен
		}
		return clientUnlock(l, h, patience) // напевно замкнено → повторити тепер безпечно
	case <-time.After(patience):
		return errors.New("стан невідомий: і команда, і звірка не дійшли")
	}
}
```

На тому самому збої `DropAck` це відпрацьовує чисто: перша команда відчинила замок (`fires` = 1), підтвердження зникло, клієнт дістав таймаут — і замість сліпого повтору читає стан, бачить «відчинено» й **зупиняється**, не смикнувши реле вдруге. Правда з першого джерела замінила здогад.

Але звірка — не срібна куля, і чесно назвати її межі. По-перше, читання йде **тим самим ненадійним каналом** — воно теж може не дійти, і тоді ми падаємо в останню гілку, «стан невідомий»: невідання не зникло, лише посунулось із запису на читання. По-друге, «відчинено» каже, що замок відкритий, але **не каже, чия саме команда його відкрила**. Для замка це байдуже — ти хотів «відчинено», воно «відчинено», по всьому. А для «додай 10 до балансу» прочитати баланс **не** скаже, чи вплинули туди саме твої десять, — тому там єдиний надійний інструмент лишається ключ. Звірка сильна рівно там, де стан можна **повністю спостерегти**; ключ працює й там, де ні.

## Складність і пастки

Уся ця конструкція тримається на дрібницях, і кожна дрібниця вже комусь коштувала інциденту.

**Побічний ефект ПЕРЕД фіксацією ключа.** Ключ рятує лише тоді, коли перевірка «чи бачив я його», сам ефект і запис ключа стаються **неподільно** — під одним замком, в одній транзакції. Розірви їх — і між ними відкривається вікно, у якому падіння все ламає. Смикнув реле, а ключ записати не встиг і впав — повтор не побачить ключа й смикне реле вдруге, тобто ти повернувся до наївного задвоєння. Записав ключ, а реле смикнути не встиг і впав — повтор побачить ключ, вирішить «уже зроблено» й піде, а замок так і лишиться замкненим. Саме тому в `KeyedHub` перевірка, `h.fires++` і `h.seen[key] = …` сидять під одним `h.mu.Lock()`: не задля швидкості, а щоб між ними не влізло падіння.

![Дві доріжки обробки одного ключа. Верхня «Небезпечно: ефект ПЕРЕД записом ключа»: ① прийняв unlock [K] → ② смикнув реле (ЕФЕКТ стався) → червоне «вікно падіння» → ③ записав ключ K; підпис «Падіння у вікні: реле вже смикнуло, а ключ K ще не записано — повтор не бачить K і смикає реле ВДРУГЕ». Нижня «Безпечно: перевірка + запис ключа + ефект — ОДНЕ ціле»: ① прийняв unlock [K] → ② ключ новий? → запис K → реле (одна транзакція, неподільно) → ③ готово; підпис «Падіння — або до транзакції, або після; проміжного стану нема. Повтор бачить K → реле спрацьовує рівно раз».](/root/course/progarch/partial-failure/img/commit-window.svg)
*Зверху ефект і запис ключа розірвані, і в шпарину між ними влазить падіння, що воскрешає задвоєння. Знизу вони — одна неподільна дія: хоч би де впало, проміжного стану, у якому ефект уже є а ключа ще нема, просто не існує.*

**Повтор без ключа — або з новим ключем на кожну спробу.** Перше ми щойно бачили на лічильнику: `fires` = 2. Друге підступніше й виглядає «правильним»: клієнт генерує ключ, але **всередині циклу повтору**, тож кожна спроба несе свіжий ключ. Для хаба це не повтори, а різні команди — жодна не збігається з попередньою, `seen` не спрацьовує, реле двоїться так само, як без ключа. Ключ мусить народитися **раз на логічну команду** й пережити всі повтори (а щоб пережити ще й перезапуск клієнта — зберегтись на диску до підтвердження). Ключ у циклі — це той самий баг, лише вдягнений у посвідчення.

**Таймаут, коротший за реальну обробку.** Згадай третій світ, `SlowReq`: терпіння 100 мс, а робота чесно триває 300. Клієнт не дочекався не тому, що канал зламався, а тому, що йому забракло терпіння на **справну, лише повільну** операцію. І щойно він на це відповість повтором — почнеться справжня біда: він шле другу команду, поки перша ще виконується, потім третю — і сам, власноруч, ліпить дублі й гонки з порожнього місця, забиваючи й без того захлинутий хаб. Тому таймаут кладуть не «на око», а від виміряного часу обробки (з запасом на хвіст повільних запитів); [таймаути й бюджет часу](book:programming/timeouts-deadlines) — окрема дисципліна саме тому, що надто короткий таймаут перетворює здорову повільність на шторм. І повтор, навіть безпечний завдяки ключу, все одно має бути **стриманим** — з наростанням паузи, [повтори з відступом](book:programming/retries-backoff), — щоб не добивати того, хто просто не встигає.

**Мьютекс на хабі — не всесвітня константа.** У Go горутини бігають по-справжньому паралельно, тож без `h.mu` два одночасні `h.fires++` могли б затерти одне одного — це вже [гонка даних](book:programming/data-races-locks). В однопотоковому рантаймі — Node з його циклом подій, Python з `asyncio` — синхронне тіло обробника відпрацьовує **до кінця без витіснення**, тож окремий замок там не потрібен, а перевірка-й-запис ключа неподільні самі собою. Але не переплутай: це прибирає лише **мьютекс**, а не часткову відмову. Загублене підтвердження, повільний запит, задвоєння від наївного повтору — усе, що ми міряли лічильником, лишається дослівно тим самим, якою мовою стеку хаб не пиши. Однопотоковість рятує від однієї гонки в пам'яті, а не від мережі, що ковтає пакети.
