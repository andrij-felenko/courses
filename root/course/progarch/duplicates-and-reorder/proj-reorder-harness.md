# ⚙️ Стенд, що доводить вартового: перемішай, задублюй, переконайся

Ми склали вартового версії й розважили, чому він сходиться до правди. Розважили — це обіцянка. Стенд — це доказ, який можна **запустити** й побачити, як вартовий або встоює, або падає з конкретним номером спроби на руках. Різниця між «я вірю, що воно сходиться» і «я прогнав десять тисяч ворожих порядків, і в кожному воно зійшлося» — це та сама різниця, що між гарним наміром і робочою системою.

Тільки довести стійкість одним прогоном не вийде, і варто зрозуміти, чому, бо саме це визначає весь устрій стенда. Пошлемо B, тоді A — вартовий утримав свіже, зелено. Що ми довели? Що він переживає **рівно цей один** порядок прибуття. А порядків у навіть коротенького потоку — жахлива безліч:

```
40 оновлень → 40! ≈ 8·10⁴⁷ можливих порядків прибуття
```

І це ще без дублів, які множать кожен варіант ще й ще. Один сценарій, що пройшов, розповідає про одну піщинку з цього пляжу — і мовчить про решту. Щоб довіряти вартовому, потрібен не сценарій, а **машина, яка сама грає ворога**: породжує потік, тасує й дублює його так само зловісно, як зробила б мережа, згодовує у випадковому порядку — і перевіряє, що вартовий однаково осів на правді. І так тисячі разів, щоразу з новим перемішуванням.

У цієї форми є ім'я — **тестування властивостей** (англ. *property-based testing*). Замість «вхід X → чекаю Y» ти формулюєш **властивість**, що мусить триматися для *всіх* входів цілої родини, а самі входи хай породжує машина. Прийом народила пара — Коен Клессен (Koen Claessen) і Джон Г'юз (John Hughes) — у бібліотеці QuickCheck для Haskell, доповіддю на конференції ICFP 2000; відтоді його перенесли в десятки мов (fast-check для TypeScript, Hypothesis для Python). Наша властивість одна-єдина: **за будь-якого перемішування й дублювання поміченого версіями потоку кінцеве значення кожного пристрою у вартового дорівнює оновленню з найбільшою версією.** Це близький родич [фаззингу — сипати в код згенеровані входи й дивитися, що зламається](root:sf-release/fuzzing); різниця тільки в питанні: фаззер шукає вхід, який *завалить* програму (аварія, зависання), а ми годуємо цілком коректні, лише переставлені входи й стережемо **інваріант**.

## Ідея стенда: годуй хаос, а ціль знай наперед

Стенд складається з трьох частин, і хитрість — у третій.

**Джерело.** Те саме, що на боці хаба: штампує кожне оновлення пристрою його **власним** монотонним лічильником. Перше оновлення вітальні — v1, друге — v2; перше оновлення передпокою — теж v1, окремим лічильником. Ця дрібниця — «лічильник на пристрій, а не один на всіх» — виявиться пасткою №2, тож затямимо її вже тут.

**Вартовий.** `applyUpdate`, який ми випробовуємо, — незмінний, слово в слово зі статті. Стенд його не чіпає; він об'єкт досліду, а не учасник.

**Сам стенд.** І ось де народжується доказ. Ми будуємо *істинний* потік, тоді з нього напряму рахуємо **оракул** — найбільшу версію на кожен пристрій, тобто ту саму ціль, до якої вартовий *мусить* прийти. Далі кожне оновлення дублюємо 1–3 рази й усе перемішуємо, згодовуємо вартовому в цьому переставленому вигляді — і стверджуємо, що його підсумок збігся з оракулом для кожного пристрою.

Чому це працює й чому дешево? Бо **ціль ми знаємо, не проходячи через хаос.** Оракул — це просто максимум версій; нам не треба передбачати, що там намішається в дорозі, бо весь сенс правила версій у тому, що кінцева точка *не залежить від шляху*. Ми не моделюємо каламутну середину — ми знаємо, куди річка **зобов'язана** впасти, і перевіряємо, що вона впала туди попри всі коліна. А щоб будь-яке падіння відтворити точно, стенд крутить не «справжню» випадковість, а генератор псевдовипадкових чисел із **зерном** (seed): спроба №4137 щоразу дає той самий потік, те саме перемішування, ту саму невдачу — є за що вхопитися, коли червоне.

![Ліворуч джерело штампує «істинний потік» (living: v1 v2 v3; hall: v1 v2). З нього одна стрілка «істина» веде вгору до ОРАКУЛА (max версія на пристрій: living→v3, hall→v2), друга — вниз до червоної «ЗЛОВОРОЖОЇ МЕРЕЖІ» (× 1..3 копії + перемішати), далі до ВАРТОВОГО (applyUpdate, межа на пристрій) і до «кінцевого стану». *Оракул рахує ціль напряму, не проходячи крізь мережу. Хоч як мережа перемішає й задублює потік, підсумок вартового мусить збігтися з тим, що оракул знав із самого початку.*

## Робочий код

Ось увесь стенд — джерело, вартовий і одне випробування, замкнене в цикл на десять тисяч зерен. Запусти — і якщо жодне не впало, вартовий пережив десять тисяч різних ворожих світів.

:::tabs
```ts
type DeviceId = string;
type State = number;
type Update = { deviceId: DeviceId; version: number; value: State };

// (1) ДЖЕРЕЛО — свій монотонний лічильник НА КОЖЕН пристрій
class Source {
  private version = new Map<DeviceId, number>();
  stamp(deviceId: DeviceId, value: State): Update {
    const next = (this.version.get(deviceId) ?? 0) + 1;   // 1, 2, 3 … окремо на пристрій
    this.version.set(deviceId, next);
    return { deviceId, version: next, value };
  }
}

// (2) ВАРТОВИЙ — те, що випробовуємо; одне число межі на пристрій
class Store {
  private value = new Map<DeviceId, State>();
  private applied = new Map<DeviceId, number>();
  versionOf(id: DeviceId): number {
    return this.applied.get(id) ?? -1;                    // −1 = пристрій ще не знайомий
  }
  applyUpdate(u: Update): "applied" | "dropped" {
    if (u.version <= this.versionOf(u.deviceId)) return "dropped";
    this.value.set(u.deviceId, u.value);
    this.applied.set(u.deviceId, u.version);              // рухаємо межу ЦЬОГО пристрою
    return "applied";
  }
  snapshot(): Map<DeviceId, State> { return new Map(this.value); }
}

// маленький ГПВЧ із зерном — щоб будь-яке падіння відтворити точно
function mulberry32(seed: number): () => number {
  let s = seed >>> 0;
  return () => {
    s = (s + 0x6d2b79f5) >>> 0;
    let t = Math.imul(s ^ (s >>> 15), 1 | s);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function shuffle<T>(a: T[], rnd: () => number): void {     // Фішер–Єйтс
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(rnd() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
}

// (3) СТЕНД — одне випробування з фіксованим зерном
function runTrial(seed: number): void {
  const rnd = mulberry32(seed);
  const source = new Source();
  const store = new Store();
  const devices = ["living", "bedroom", "hall", "kitchen"];

  // 3a. істинний потік: кожен пристрій дістає серію оновлень зі зростальними версіями
  const stream: Update[] = [];
  for (const d of devices) {
    const n = 1 + Math.floor(rnd() * 12);                 // 1..12 оновлень на пристрій
    for (let i = 0; i < n; i++) {
      stream.push(source.stamp(d, Math.round(rnd() * 100)));
    }
  }

  // 3b. ОРАКУЛ: ціль знаємо напряму — найбільша версія на пристрій
  const oracle = new Map<DeviceId, { version: number; value: State }>();
  for (const u of stream) {
    const cur = oracle.get(u.deviceId);
    if (cur === undefined || u.version > cur.version) {
      oracle.set(u.deviceId, { version: u.version, value: u.value });
    }
  }

  // 3c. ЗЛОВОРОЖА МЕРЕЖА: задублювати ×1..3 і перемішати
  const scrambled: Update[] = [];
  for (const u of stream) {
    const copies = 1 + Math.floor(rnd() * 3);             // 1..3 копії кожного оновлення
    for (let c = 0; c < copies; c++) scrambled.push(u);
  }
  shuffle(scrambled, rnd);

  // 3d. згодувати вартовому у переставленому, задубльованому порядку
  for (const u of scrambled) store.applyUpdate(u);

  // 3e. ствердити: кінець кожного пристрою = оновлення з найбільшою версією
  const final = store.snapshot();
  for (const d of devices) {
    const want = oracle.get(d)!.value;
    const got = final.get(d);
    if (got !== want) {
      throw new Error(`seed=${seed} ${d}: чекали ${want} (max версія), маємо ${got}`);
    }
  }
  if (final.size !== oracle.size) {                       // жодних привидів — див. пастку 1
    throw new Error(`seed=${seed}: привид-пристрій у підсумку`);
  }
}

for (let seed = 1; seed <= 10_000; seed++) runTrial(seed);
console.log("10000 випробувань пройдено: копія щоразу зійшлася до правди");
```

```py
from __future__ import annotations
import random
from dataclasses import dataclass


@dataclass(frozen=True)
class Update:
    device_id: str
    version: int
    value: int


# (1) ДЖЕРЕЛО — монотонний лічильник на кожен пристрій
class Source:
    def __init__(self) -> None:
        self._version: dict[str, int] = {}

    def stamp(self, device_id: str, value: int) -> Update:
        nxt = self._version.get(device_id, 0) + 1          # 1, 2, 3 … окремо на пристрій
        self._version[device_id] = nxt
        return Update(device_id, nxt, value)


# (2) ВАРТОВИЙ — те, що випробовуємо
class Store:
    def __init__(self) -> None:
        self._value: dict[str, int] = {}
        self._applied: dict[str, int] = {}

    def version_of(self, device_id: str) -> int:
        return self._applied.get(device_id, -1)            # −1 = пристрій ще не знайомий

    def apply_update(self, u: Update) -> str:
        if u.version <= self.version_of(u.device_id):
            return "dropped"
        self._value[u.device_id] = u.value
        self._applied[u.device_id] = u.version             # рухаємо межу ЦЬОГО пристрою
        return "applied"

    def snapshot(self) -> dict[str, int]:
        return dict(self._value)


# (3) СТЕНД — одне випробування з фіксованим зерном
def run_trial(seed: int) -> None:
    rnd = random.Random(seed)                              # ГПВЧ на зерні: падіння відтворюване
    source, store = Source(), Store()
    devices = ["living", "bedroom", "hall", "kitchen"]

    # 3a. істинний потік зі зростальними версіями на пристрій
    stream: list[Update] = []
    for d in devices:
        for _ in range(rnd.randint(1, 12)):               # 1..12 оновлень на пристрій
            stream.append(source.stamp(d, rnd.randint(0, 100)))

    # 3b. оракул — найбільша версія на пристрій, незалежно від порядку
    oracle: dict[str, Update] = {}
    for u in stream:
        cur = oracle.get(u.device_id)
        if cur is None or u.version > cur.version:
            oracle[u.device_id] = u

    # 3c. задублювати ×1..3 і перемішати
    scrambled: list[Update] = []
    for u in stream:
        scrambled += [u] * rnd.randint(1, 3)              # 1..3 копії кожного оновлення
    rnd.shuffle(scrambled)

    # 3d. згодувати вартовому у переставленому, задубльованому порядку
    for u in scrambled:
        store.apply_update(u)

    # 3e. ствердити збіг із оракулом + жодних привидів (див. пастку 1)
    final = store.snapshot()
    for d in oracle:
        assert final.get(d) == oracle[d].value, \
            f"seed={seed} {d}: чекали {oracle[d].value} (max версія), маємо {final.get(d)}"
    assert len(final) == len(oracle), f"seed={seed}: привид-пристрій у підсумку"


if __name__ == "__main__":
    for seed in range(1, 10_001):
        run_trial(seed)
    print("10000 випробувань пройдено: копія щоразу зійшлася до правди")
```

Одна дрібна, але промовиста різниця між мовами вже тут. Python дає відтворюваний генератор задарма — `random.Random(seed)` зі стандартної бібліотеки; у JavaScript вбудований `Math.random()` **не** приймає зерна, тож стенд несе власний крихітний `mulberry32`. Дрібниця, але саме така дрібниця відрізняє стенд, чиє падіння можна відтворити, від стенда, чиє «іноді червоніє» ганяєш півдня.

## Складність і пастки

Стенд простий. Пастки — ні, і що цінно, майже кожну з них видно **тільки** тоді, коли стенд достатньо злий. Слабкий стенд не просто менше ловить — він **завіряє** зламаного вартового зеленою галочкою, а це гірше за жодного стенда.

### Пастка 1: невідомий пристрій

Перше оновлення пристрою мусить пройти завжди. Отже, `versionOf` для незнайомця має вертати щось **строго менше за будь-яку справжню версію** — інакше найперше оновлення осяде на порозі, і пристрій навік лишиться порожнім. Наш вартовий вертає −1, і це працює лише тому, що версії в джерела починаються з 1. Спокуслива дрібна помилка — ініціалізувати межу нулем: якщо десь версії теж рахуються від 0, умова `0 ≤ 0` тихо ковтне перше справжнє оновлення. Куленепробивна форма перевіряє не магічне число, а **наявність** ключа:

```py
def version_of(self, device_id: str) -> int:
    return self._applied[device_id] if device_id in self._applied else -1
    # немає ключа → «нижче за все» без припущень, з якого числа починаються версії
```

І є ще одне обличчя цієї ж пастки — **привид**. Якщо вартовий на невідомому пристрої лінькувато заводить запис `(значення=0, версія=0)`, то в підсумку зринає пристрій, який **жодного разу не озивався**. Значення 0 виглядає як справжнє показання, хоч насправді це слід ініціалізації. Тому стенд перевіряє не лише значення, а й **склад**: у підсумку мають бути рівно ті пристрої, що слали оновлення, — ні на один більше. Саме це робить рядок `final.size !== oracle.size` наприкінці випробування; без нього привид проскочив би непоміченим.

### Пастка 2: межа на пристрій, а не глобальна

Найпідступніша з усіх, бо помилка дає **зелений** стенд, якщо стенд наївний. Межу версій треба тримати **на кожен пристрій окремо**. Спокуслива спрощенка — одне число `maxSeen` на весь вартовий: «відкидай усе, чия версія ≤ найбільшої, що я бачив». На одному пристрої це не відрізнити від правильного — глобальна межа й межа на пристрій там **збігаються**. Помилка оживає лише тоді, коли версії двох пристроїв **накладаються**.

І ось тут — головне рішення в усьому стенді. Лічильник кожного пристрою починається з 1, тож у **кожного** є своя v1, своя v2… — номери різних пристроїв **навмисно збігаються**. Згодуй їх упереміш — і глобальна межа відкине законну v2 передпокою лише тому, що вітальня вже підняла спільне число вище двійки. Простеж по кроках:

![Три колонки. Ліва «ГЛОБАЛЬНА межа — БАГ», центральна «ПРИБУЛО (те саме)», права «МЕЖА НА ПРИСТРІЙ». Прибуття по черзі: living·v2→22°, hall·v1→70%, living·v1→21°, hall·v2→72%. Глобальна межа бере living v2 (−1→2), тоді ВІДКИДАЄ hall v1 (1≤2), відкидає living v1 (1≤2, слушно), і ВІДКИДАЄ hall v2 (2≤2) — hall лишається порожній. Межа на пристрій веде окремі лічильники: living −1→2, hall −1→1, living 1≤2 відкинуто, hall 1→2 — обидва праві](img/perkey-vs-global.svg)
*Прибуття однакові. Глобальна межа зараховує версії вітальні проти передпокою й лишає передпокій порожнім; окрема межа на кожен пристрій тримає їх нарізно. Помилку видно лише з кількома пристроями, чиї номери збігаються.*

Помітьмо тонкість, від якої залежить, чи стенд узагалі здатний це впіймати. Якби джерело роздавало **один наскрізний** номер на всі пристрої (кожне оновлення в світі дістає унікальне зростальне число), баг глобальної межі був би **замаскований** — двох однакових номерів просто не бувало б, і глобальна межа поводилася б як правильна. Отже, вибір «лічильник на пристрій, що рестартує з 1» — не косметика, а **пастколовка**: саме він змушує номери збігатися й виводить помилку на світло. Стенд з одним пристроєм, або з наскрізними унікальними номерами, спокійно завірить зламаного вартового.

> 🔧 **Навіщо це.** На рев'ю, коли показують зелений тест на дедуплікацію, спитай не «скільки асертів», а **скільки різних ключів він ганяє і чи збігаються їхні номери версій**. Зелений тест на одному ключі — це рівно той тест, який переживає баг глобальної межі. Вага фаз-стенда не в кількості перевірок, а в **злобі вхідних даних**: кілька ключів зі спільними номерами, дублі, випадковий порядок. Стенд, який цього не робить, не доводить нічого — він лише заспокоює.

### Пастка 3: скільки пам'ятати

Вартовий версії тримає **одне число** на пристрій — і край. Хоч мільйон дублів прилетить, хоч потік тягнеться годинами, пам'ять на пристрій стала: O(1), незалежно від довжини потоку й кількості повторів. Це варто відчути на контрасті з дедуплікацією **за ідентифікатором** — тим самим ключем ідемпотентності, яким ми колись [знешкодили повтор команди на поганому Wi-Fi](root:progarch/dh-bad-network). Щоб відсіювати за унікальним [ідентифікатором](root:sf-distributed/idempotency), треба пам'ятати **множину всіх бачених** — а вона росте без упину, тож доводиться навішувати TTL, ковзне вікно чи фільтр Блума, і дубль, старший за вікно, прослизне. Номерові версії таке вікно не потрібне: одне монотонне число вже означає «я бачив усе, що ≤ цього». Дедуплікація за версією **обмежена самою своєю природою**, і це тиха, велика її перевага.

Але не дай собі збрехати, ніби пам'ять зовсім стала. **Мапа пристроїв** усе одно росте — по запису на кожен пристрій, що бодай раз озвався. Пристрій, який замовк назавжди, однаково займає комірку. Тож питання «скільки пам'ятати» не зникає — воно **переїжджає** з «на кожне повідомлення» на «на кожен пристрій», і відповідь тут — виселяти давно мовчазних. З однією гострою засторогою, яку стенд уміє показати як **падіння**. Забудеш межу мовчазного пристрою — а тоді прилетить застарілий дубль його старого оновлення, що доти блукав мережею, — і без межі він знову зійде за свіжий:

```py
# межа living доти = 7; виселяємо його як «давно мовчазного»
del store._applied["living"]                       # ← еквівалент виселення за TTL
store.apply_update(Update("living", 5, 21))        # межі нема → −1 → 5 «свіже» → ЗАСТОСОВАНО
assert store.snapshot()["living"] == 23            # ✗ впаде: старий 21° затер свіжий 23°
```

Цей мінівипробунок падає **навмисно** — і в його падінні весь урок: виселяти межу безпечно лише для пристроїв, які мовчать **довше за найбільший можливий вік повідомлення** в мережі (або взагалі не забувати межу, а зберігати її в тривкому сховищі). Виселиш ранiше — впустиш регресію, тихцем, без жодної помилки в коді самого вартового.

### Пастка 4: одночасні повтори

Досі ми годували вартового по одному оновленню. Але хмара на те й хмара, що обробляє потік **кількома робітниками заразом** — і тут ховається остання, найтонша пастка. `applyUpdate` — це **читання-порівняння-запис**: спершу дізнайся межу, тоді виріши, тоді запиши. Три кроки. Якщо два робітники обробляють оновлення **того самого** пристрою одночасно, ці кроки переплітаються:

![Два робітники W1 і W2 над тим самим пристроєм, межа спершу 5. Верхня панель «без замка»: у t1 W1 читає межу 5 (бачить v7), у t2 W2 читає межу 5 (бачить v6), у t3 W1 пише значення=v7, межа=7, у t4 W2 пише значення=v6, межа=6 — межа відкотилася 7→6, свіже v7 затерто старим v6. Нижня панель «із замком на пристрій»: W1 бере замок, читає 5, ставить межу 7, віддає; W2 бере замок, читає 7, бачить v6≤7 і відкидає — значення=v7, межа=7, правду збережено](img/race-check-then-act.svg)
*Читання-порівняння-запис без захисту не є неподільним: обидва робітники читають стару межу 5, обидва вважають своє оновлення свіжим, і той, хто пише останнім, відкочує межу назад. Замок на пристрій робить трійку неподільною.*

Наголосімо на найгіршому наслідку: відкотилася не лише картинка — **сама межа** впала з 7 на 6. А це значить, що наступний відсталий дубль v7, який доти чесно відсіювався, тепер `7 > 6` — і застосується вдруге. Одна гонка не просто затерла значення, вона **зламала охоронця на майбутнє**. Ліки — зробити трійку «читай-порівняй-пиши» на один пристрій **неподільною**, і мови дають це по-різному:

:::tabs
```ts
// TypeScript: один потік, цикл подій. Синхронний applyUpdate неподільний САМ ПО СОБІ —
// але щойно між читанням і записом з'явиться await, гонка вертається:
async applyUpdate(u: Update): Promise<"applied" | "dropped"> {
  const seen = await this.load(u.deviceId);        // ← цикл подій може віддати керування ТУТ
  if (u.version <= seen) return "dropped";
  await this.save(u.deviceId, u.value, u.version); // інший обробник міг уже посунути межу
  return "applied";
}
// Лік: серіалізувати за ключем (черга/мьютекс на пристрій) або — краще — атомарний
// умовний запис у сховищі (див. нижче), щоб між читанням і записом не було зазору.
```
```py
# Python: GIL НЕ рятує — між dict.get і dict.set багато байткодів, і перемикання
# потоків може влучити всередину. Потрібен явний замок НА КОЖЕН пристрій:
import threading


class SafeStore(Store):
    def __init__(self) -> None:
        super().__init__()
        self._locks: dict[str, threading.Lock] = {}
        self._guard = threading.Lock()

    def apply_update(self, u: Update) -> str:
        with self._guard:                                  # захистити саму мапу замків
            lock = self._locks.setdefault(u.device_id, threading.Lock())
        with lock:                                         # неподільно НА ЦЕЙ пристрій
            return super().apply_update(u)
```
:::

Замок на пристрій розв'язує задачу, але має ціну — робітники, що б'ються за той самий пристрій, шикуються в чергу. Тому в справжньому сховищі трійку зазвичай не замикають, а **зливають в одну атомарну операцію** — умовний запис, який рухає межу лише коли нове більше:

```sql
-- одним неподільним рядком: межа поповзе вгору лише як нове більше за старе
UPDATE devices SET value = :val, version = :ver
WHERE device_id = :id AND version < :ver;
```

Немає окремого читання, нема зазору, нема чого замикати: база сама порівнює й пише за один захід. А найдешевший спосіб узагалі уникнути гонки — **розкласти за ключем**: спрямуй усі оновлення одного пристрою до одного робітника, і одночасності на ньому просто не стане. Це не хитрість заради стенда, а те, як живуть промислові черги: розділ (partition) у Kafka, ключований пристроєм, дає рівно таку одноосібну обробку одного ключа.

## Що доводить стенд, а що — його устрій

Прогнати десять тисяч зерен зеленими — приємно, але справжня цінність стенда не в зеленому числі, а в тому, що **його ворожі рішення і є специфікація вартового**, записана виконуваним кодом. Кілька пристроїв зі збіжними лічильниками кажуть «межа на кожен пристрій, не глобальна». Дублі кажуть «повтор нічого не міняє». Випадковий порядок каже «переставленість — норма». Одночасні робітники кажуть «порівняння-запис атомарне». Прибери бодай одну з цих рис — і стенд однаково зазеленіє, а вартовий однаково брехатиме; зелений слабкий стенд гірший за жодного, бо підписується під багом.

Тож коли писатимеш такий стенд для власного вартового, пиши його **злим**: хай тасує жорсткіше, дублює щедріше, крутить кілька ключів із номерами, що налазять один на один, і б'є в один пристрій кількома робітниками. Легкий стенд ловить легкі помилки, яких у тебе й так немає. А правду про те, чи справді копія сходиться, розповість лише той стенд, який щиро старається змусити її збрехати — і не зміг.
