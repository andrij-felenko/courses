# Протікання шару

## Паперові стіни: аварія на межі шарів у Digital Homes

О шостій вечора в п'ятницю сервер моніторингу платформи Digital Homes почав масово скидати з'єднання мобільних застосунків через вичерпання таймауту. База даних PostgreSQL захлиналася від навантаження: утилізація процесора сягнула 100%, пул підключень спорожнів за кілька секунд, а мобільні клієнти замість показників температури показували користувачам білі екрани або повідомлення про внутрішню помилку сервера.

При цьому репозиторій проєкту виглядав зразково. Код суворо відповідав канонам тришарової архітектури:
- папка `Controllers/` містила лише класи веб-обробників;
- папка `Domain/` містила сервіси з бізнес-правилами;
- папка `Infrastructure/` інкапсулювала доступ до бази через репозиторії.

Кожен файл лежав у своєму каталозі, компілятор не видавав жодних попереджень, а юніт-тести завершувалися із зеленим статусом за частки секунди. Архітектурна катастрофа виникла не в структурі файлової системи, а в тому, що саме подорожувало між цими каталогами під час виконання програми.

За два тижні до аварії команді знадобилося додати новий ендпойнт для отримання поточного стану термостата. Щоб вкластися у дедлайн і позбутися написання однотипного перенесення полів, розробники вирішили заощадити на [ціні мапінгу між шарами](root:progarch/cost-of-layer-mapping). Замість створення окремого об'єкта передавання даних (@@en|DTO@@, від англійського *Data Transfer Object*) та його заповнення з доменної моделі, сутність ORM прокинули наскрізь: із репозиторію в доменний сервіс, а з сервісу — безпосередньо у контролер, який передав її механізму серіалізації в JSON.

```csharp
// Infrastructure/Persistence/ThermostatEntity.cs
[Table("thermostats")]
public class ThermostatEntity
{
    [Key]
    public Guid Id { get; set; }

    [Column("serial_number")]
    public string SerialNumber { get; set; } = string.Empty;

    [Column("target_temperature")]
    public double TargetTemperature { get; set; }

    [Column("current_temperature")]
    public double CurrentTemperature { get; set; }

    // Навігаційна властивість зв'язку один-до-багатьох
    public virtual ICollection<ThermostatAuditLog> Audits { get; set; } 
        = new List<ThermostatAuditLog>();
}

// Presentation/Controllers/ThermostatController.cs
[ApiController]
[Route("api/thermostats")]
public class ThermostatController : ControllerBase
{
    private readonly IThermostatService _service;

    public ThermostatController(IThermostatService service)
    {
        _service = service;
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> GetById(Guid id)
    {
        // Сутність бази даних безпосередньо повертається у веб-відповідь
        ThermostatEntity? thermostat = await _service.GetThermostatAsync(id);
        if (thermostat is null)
        {
            return NotFound();
        }

        return Ok(thermostat);
    }
}
```

На тестових стендах такий підхід працював бездоганно. Для тестового термостата з порожньою історією запит виконувався за три мілісекунди, повертаючи очікуваний компактний JSON. Пастка спрацювала після двох цілком стандартних змін у наступному релізі:

1. До сутності термостата додали колекцію аудиту `Audits`, щоб відстежувати, хто й коли змінював цільову температуру. Навігаційну властивість налаштували зі стандартним для багатьох ORM відкладеним завантаженням (@@en|lazy loading@@).
2. Адміністратори бази даних стандартизували іменування стовпчиків: поле `target_temperature` перейменували на `target_temp_celsius`. Розробники відповідно оновили назву властивості в `ThermostatEntity`.

Жоден із цих кроків не торкався контролера чи сервісу. Проте у робочому середовищі система зазнала потрійного удару, який паралізував сервіс.

Першим ударом стала лавина прихованих запитів. Коли метод контролера завершив роботу й повернув `Ok(thermostat)`, керування перейшло до вбудованого у веб-фреймворк механізму серіалізації (від латинського *series* — ряд, зв'язка). Серіалізатор обходить публічні властивості об'єкта за допомогою рефлексії. Дійшовши до властивості `Audits`, він звернувся до геттера. Оскільки ORM підмінила сутність динамічним проксі-об'єктом, це звернення непомітно ініціювало SQL-запит до таблиці журналів аудиту.

Для термостата, що працював пів року, накопичилося дві тисячі записів аудиту. Кожен такий запис містив посилання на користувача, який змінив температуру. Серіалізатор заглибився в кожен запис журналу й для кожного з них надіслав окремий запит на отримання даних користувача. Замість одного легкого запиту отримання термостата перетворилося на 2001 звернення до бази даних — класичну проблему вибуху запитів N+1. Коли одночасно надійшло сто таких HTTP-запитів від мобільних клієнтів, база даних отримала двісті тисяч запитів за кілька секунд і повністю вичерпала пул підключень.

Другим ударом стало миттєве руйнування клієнтських контрактів. Мобільний застосунок очікував у відповіді поле `targetTemperature`. Перейменування властивості в сутності бази даних автоматично змінило ключ у вихідному документі JSON на `targetTempCelsius`. Контролер не знав про цю зміну, але клієнти втратили сумісність: мобільні застосунки не змогли розпізнати нове поле, скинули значення температури до нуля або завершилися з критичною помилкою десеріалізації. Звичайна оптимізація схеми таблиці несподівано зламала публічний інтерфейс системи.

Третім ударом став витік технічних нутрощів назовні. Коли пул підключень вичерпався, черговий запит від серіалізатора до бази впав із таймаутом. Драйвер бази згенерував виняток `Npgsql.NpgsqlException: 53300: remaining connection slots are reserved`. Оскільки помилка сталася не всередині репозиторію чи сервісу, а вже на етапі запису тіла HTTP-відповіді, жоден доменний блок обробки винятків не міг її перехопити. Низькорівневий виняток драйвера пробив усі рівні застосунку й потрапив у стандартний веб-перехоплювач, який повернув клієнту відповідь з кодом 500 і повним текстом трасування стека: назвами внутрішніх таблиць, структурою запиту та IP-адресою сервера бази даних.

![що показано і що з неї видно](img/formal-vs-runtime-layer-leakage.svg)
*Зліва — формальний поділ за каталогами (контролери, домен, інфраструктура), де кожен файл лежить на своєму місці. Справа — реальні рантайм-зв'язки: JSON-серіалізатор неявно смикає базу даних через ліниві зв'язки сутності, а винятки драйвера пробивають усі рівні назовні.*

Ця аварія демонструє різницю між двома станами системи: тим, як код розкладено по папках у сховищі, і тим, як об'єкти взаємодіють у пам'яті під час виконання. Папки у проєкті — це лише паперові стіни. Вони створюють ілюзію порядку для розробника, але для середовища виконання не існує ані «папки контролерів», ані «папки інфраструктури». Єдине, що має значення в рантаймі — це графі об'єктів, межі володіння ресурсами та потоки керування.

Ситуація, коли внутрішні деталі, технічні винятки, життєвий цикл з'єднань або структури даних одного рівня проникають крізь кордони в інші частини системи, називається **протіканням шару** (@@en|layer leakage@@, від праслов'янського *tekti* — литися, текти, та латинського *stratum* — шар, настил).

Протікання виникає тому, що програмісти часто плутають синтаксичну ізоляцію з поведінковою. Ще у 2002 році Джоел Спольські у своєму класичному есе сформулював **закон протікаючих абстракцій** (@@en|Law of Leaky Abstractions@@; від латинського *abstractio* — відокремлення, відволікання): будь-яка нетривіальна абстракція містить шпарини, крізь які пробиваються деталі базової реалізації ([hist-law-of-leaky-abstractions](root:progarch/layer-leakage/hist-law-of-leaky-abstractions.md)). Що потужнішим є інструмент, що більше зусиль він докладає, аби сховати від нас мережу чи реляційні таблиці, то катастрофічнішим стає витік, коли ця ілюзія руйнується.

Спроба вважати сутність ORM звичайним об'єктом пам'яті отримала в інженерії назву **краху «прозорого збереження»** (@@en|transparent persistence fallacy@@; [hist-transparent-persistence-fallacy](root:progarch/layer-leakage/hist-transparent-persistence-fallacy.md)). На зламі 1990-х і 2000-х років технології на зразок EJB Entity Beans намагалися переконати розробників, що звернення до бази даних можна звести до виклику звичайних геттерів і сеттерів. Практика довела зворотне: реляційна база живе за законами реляційної алгебри, транзакцій і фізичного вводу-виводу. Ця прірва між графом об'єктів у пам'яті та двовимірними таблицями відома як [об'єктно-реляційний розрив](root:sf-data/object-relational-mismatch). Навішування магічних проксі-об'єктів поверх таблиць не знищує цю прірву, а лише маскує її до першого навантаження.

У випадку Digital Homes команда спробувала змусити один клас виконувати три несумісні ролі одночасно:
1. **Схема збереження.** Клас описує реляційні таблиці, зовнішні ключі, індекси та типи колонок. Ця структура змінюється під тиском адміністраторів бази даних, оптимізації індексів і міграцій.
2. **Бізнес-поведінка.** Клас містить логіку термостата: допустимі діапазони температур, перевірку прав доступу, правила безпеки проти замерзання труб. Ця частина змінюється відповідно до вимог замовника та предметної області.
3. **Публічний контракт API.** Клас визначає форму JSON, яку очікують клієнти: веб-панелі та мобільні пристрої. Ця частина змінюється дуже повільно і вимагає суворої зворотної сумісності.

Коли всі три ролі склеєні в одному об'єкті, система втрачає незалежність розвитку. Будь-який рух на рівні бази даних негайно б'є по публічному API. Будь-яке розширення бізнес-правил тягне за собою зміну таблиць. А будь-яка спроба відобразити дані назовні перетворюється на неконтрольоване [керування транзакційними межами](root:progarch/transaction-boundary-management), коли підключення до бази залишається відкритим аж до моменту запису останнього байта в мережевий сокет.

> 🔧 **Навіщо це.**
> Здатність розрізняти формальну структуру папок і реальну ізоляцію в пам'яті рятує від найдорожчих аварій у промислових системах. Коли розробник бачить, що заради «економії на мапінгу» сутність бази даних передається у представлення, він розуміє справжню ціну цього рішення: приховані запити N+1, жорстке зчеплення клієнтів зі схемою таблиць та витік системних винятків у відповіді користувачам. Справжня архітектурна межа визначається не тим, у яких каталогах лежать файли, а тим, де зупиняється поширення змін і де обривається життєвий цикл низькорівневих ресурсів.

## Явний витік моделей даних: як структури бази руйнують домен

Під час створення нової функціональності написання трьох майже ідентичних класів для однієї сутності викликає сильний інженерний спротив. Клас `ApartmentEntity` зберігає стан у реляційній таблиці, клас `Apartment` у доменному шарі інкапсулює правила поведінки, а `ApartmentResponseDto` передає ці самі дані клієнту через мережу. Усі три класи містять однакові поля: ідентифікатор, адресу, площу, ціну та статус. Кожне нове поле змушує редагувати три різні файли, дублювати код або налаштовувати бібліотеки автоматичного перетворення даних.

У цей момент виникає спокуса позбутися зайвої роботи: оголосити один клас ORM-сутності, провести його крізь усі шари й повернути безпосередньо у відповіді HTTP-контролера. Таке рішення здається прагматичною оптимізацією розробки, але платою за нього стає знищення архітектурної межі: [ціна мапінгу між шарами](root:progarch/cost-of-layer-mapping) оманливо видається марнотратством, доки система не стикається з першими змінами вимог.

Причина криється у фундаментальній несумісності: вимоги реляційного рушія прямо суперечать вимогам бізнес-моделі. Бібліотеки об'єктно-реляційного відображення (ORM) створювалися для механічного перенесення рядків реляційних таблиць у пам'ять процесу. Щоб інфраструктурний рушій міг автоматично відновити об'єкт із результатів SQL-запиту, він висуває до класу суворі технічні обмеження:

По-перше, вимога безпараметричного конструктора. Механізм рефлексії (від лат. @@en|reflectere@@ — повертати назад, відображати) під час читання записів із бази створює порожній екземпляр класу без передавання обов'язкових аргументів, а потім по черзі записує значення у поля. Для бізнес-моделі це катастрофа. Жодна квартира в реальному світі не може існувати без обов'язкової адреси, площі та призначеного власника. Наявність відкритого конструктора без параметрів дозволяє будь-якій частині системи створити об'єкт у напівпорожньому, невалідному стані. Обов'язкові бізнес-правила, які ніколи не повинні порушуватися протягом усього життєвого циклу об'єкта, називаються інваріантами (від лат. @@en|invariabilis@@ — незмінний). Безпараметричний конструктор позбавляє об'єкт можливості захищати власні інваріанти під час народження.

По-друге, відкриті сетери для кожної властивості. Щоб ORM могла вільно записувати зчитані стовпчики у властивості об'єкта, розробники відкривають публічні модифікатори запису: `public decimal Price { get; set; }`. У цю ж мить руйнується інкапсуляція. Якщо будь-який зовнішній сервіс чи контролер може напряму змінити ціну на від'ємну або виставити статус «Продано» без реєстрації банківського платежу, доменний об'єкт перетворюється на звичайну пасивну торбинку з даними. Бізнес-правила вимиваються з сутностей і розпорошуються по випадкових службах та обробниках інтерфейсу. Такий стан архітектури називають анемічною моделлю предметної області (від грец. @@en|anaimia@@ — безкровність, @@en|anemic domain model@@).

По-третє, скалярні зовнішні ключі замість багатих доменних зв'язків. Реляційна база оперує числовими первинними та зовнішніми ключами (`OwnerId: long`), тоді як бізнес-логіка мислить цілісними об'єктами: правилами реєстрації власника, його лімітами на придбання та історією операцій. Зведення зв'язків до числових ідентифікаторів змушує бізнес-код вручну координувати численні запити до сховищ замість виконання операцій над повноцінними агрегатами. Ця прірва між виразною об'єктною моделлю та пласкими таблицями відома як [об'єктно-реляційний розрив](root:sf-data/object-relational-mismatch).

По-четверте, засмічення бізнес-коду інфраструктурними анотаціями. Щоб пояснити базі зв'язок колонок, обмеження унікальності чи типи індексів, над полями доменного класу з'являються атрибути: `[Table("apartments")]`, `[Column("sq_meters")]`, `[ForeignKey("OwnerId")]` або `@Entity` та `@Column`. Доменний модуль втрачає автономність і дістає пряму залежність від сторонніх бібліотек доступу до бази (`Microsoft.EntityFrameworkCore` або `jakarta.persistence`). Зміна імені колонки в базі даних чи налаштування індексу змушує перекомпілювати модуль, що відповідає за розрахунок вартості угод.

```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

namespace RealEstate.Domain.Entities;

// Приклад витоку: ORM-сутність намагається водночас бути структурою таблиці,
// доменною моделлю та форматом відповіді веб-контролера
[Table("apartments")]
public class Apartment
{
    // Технічна вимога ORM для рефлексії: дозволяє створити пустий об'єкт в обхід перевірок
    public Apartment() { }

    [Key]
    [Column("id")]
    public long Id { get; set; }

    [Column("sq_meters")]
    public double Area { get; set; }

    // Відкритий сетер руйнує інкапсуляцію: ціну можна змінити без перевірки бізнес-правил
    [Column("price_usd")]
    public decimal Price { get; set; }

    [Column("status")]
    public string Status { get; set; } = "Draft";

    // Числовий зовнішній ключ замість об'єктного зв'язку з власником
    [Column("owner_id")]
    public long OwnerId { get; set; }
}
```

Коли такий клас використовується в ролі бізнес-моделі, захистити цілісність системи стає неможливо:

```csharp
// Будь-який компонент системи може спотворити стан сутності:
var apartment = new Apartment(); // Створено об'єкт із нульовими значеннями без адреси та власника
apartment.Price = -50000m;       // Від'ємна ціна успішно записана, інваріант вартості зламано
apartment.Status = "Sold";       // Квартиру позначено як продану без оформлення договору та оплати
```

Справжні руйнівні наслідки такого підходу виявляються під час еволюції системи. Коли одна й та сама сутність служить структурою бази даних, моделлю бізнес-правил і тілом JSON-відповіді в API, між трьома частинами виникає наджорстке зчеплення.

Причина конфлікту криється в тому, що різні шари системи живуть за різними внутрішніми годинниками:
- Шар представлення змінюється найшвидше. Інтерфейси мобільних додатків і веб-сторінок оновлюються щотижня або щодва тижні: змінюються формати екранів, додаються нові візуальні блоки, перейменовуються поля відображення.
- Доменний шар розвивається помірно. Правила розрахунку вартості, умови бронювання та вимоги верифікації клієнтів еволюціонують у горизонті місяців слідом за змінами в бізнес-стратегії чи законодавстві.
- Шар збереження даних змінюється найповільніше. Реляційні таблиці несуть тягар терабайтів історичних даних. Будь-яка міграція схеми вимагає планування періодів зупинки, створення резервних копій та узгодження з адміністраторами баз даних, що розтягується на квартали.

![Шестерні трьох шарів із різними власними швидкостями обертання та жорстким штифтом витоку](img/layer-clocks-and-coupling-drag.svg)
*Три шари системи мають різні власні темпи змін: швидкий інтерфейс оновлюється щотижня, доменні правила — щомісяця, а схема бази даних — щокварталу. Без проміжних моделей спільна ORM-сутність утворює жорсткий штифт між шестернями: перейменування стовпчика в базі змушує ламати контракт клієнтського API, позбавляючи систему гнучкості.*

Якщо між шарами немає проміжних контрактів, спільна ORM-сутність діє як сталевий штифт, забитий між шестернями з різними швидкостями. Будь-яка зміна на повільному рівні бази даних негайно б'є по найшвидшому рівню клієнтських інтерфейсів.

Якщо адміністратор бази вирішує перейменувати стовпчик `price_usd` на `price_cents` або розбити одне поле на два, розробник змінює ім'я властивості в класі `Apartment`. Оскільки цей же об'єкт повертається контролером, механізм JSON-серіалізації змінює назву ключа у вихідній відповіді. Тисячі мобільних телефонів користувачів, де встановлено попередню версію додатка, перестають розуміти відповідь сервера й аварійно завершують роботу. Команда опиняється перед вибором: або ніколи не покращувати схему бази даних, або щоразу ламати робочі клієнти.

Історія програмування вже проходила цю пастку наприкінці 1990-х років, коли технологія EJB Entity Beans намагалася зробити доступ до бази повністю невидимим. Крах ілюзії прозорого збереження (від лат. @@en|persistere@@ — залишатися, витримувати, @@en|transparent persistence@@) детально розібрано у [вставці про помилку прозорого збереження](root:progarch/layer-leakage/hist-transparent-persistence-fallacy.md). Фундаментальну причину цього провалу сформулював Джоел Спольські у [вставці про закон дірявих абстракцій](root:progarch/layer-leakage/hist-law-of-leaky-abstractions.md): будь-яка спроба сховати фізичні властивості складного механізму за спрощеною абстракцією протікає деталями реалізації. У формальних моделях зчеплення ця залежність проявляється як архітектурний дрейф у заборонені сектори матриці структури проєктування ([вставка про аналіз зчеплення через DSM](root:progarch/layer-leakage/math-dsm-layer-coupling.md)).

Щоб розірвати це зчеплення, доменний об'єкт позбавляють технічних анотацій і захищають від прямого втручання ззовні:

```csharp
namespace RealEstate.Domain.Model;

// Чиста доменна модель: жодних атрибутів СКБД, повний захист інваріантів
public class Apartment
{
    public ApartmentId Id { get; }
    public Area Area { get; }
    public Money Price { get; private set; }
    public ApartmentStatus Status { get; private set; }
    public OwnerId OwnerId { get; }

    // Конструктор гарантує, що невалідний стан створити неможливо
    public Apartment(ApartmentId id, Area area, Money initialPrice, OwnerId ownerId)
    {
        Id = id ?? throw new ArgumentNullException(nameof(id));
        Area = area ?? throw new ArgumentNullException(nameof(area));
        Price = initialPrice ?? throw new ArgumentNullException(nameof(initialPrice));
        OwnerId = ownerId ?? throw new ArgumentNullException(nameof(ownerId));
        Status = ApartmentStatus.Draft;
    }

    // Зміна стану відбувається виключно через доменні методи з валідацією
    public void ChangePrice(Money newPrice)
    {
        if (Status == ApartmentStatus.Sold)
            throw new InvalidOperationException("Неможливо змінити ціну вже проданої квартири.");

        Price = newPrice ?? throw new ArgumentNullException(nameof(newPrice));
    }
}
```

> 🔧 **Навіщо це.**
> Розділення реляційних сутностей, доменних агрегатів та об'єктів передавання даних (DTO) створює між шарами демпфер: схема бази даних може вільно оптимізуватися індексами й денормалізацією, доменний код зосереджується на перевірці бізнес-правил, а зовнішній API зберігає стабільність контрактів для мобільних і веб-клієнтів.

## Прихований поведінковий витік: пастки IQueryable та лінивого завантаження

Навіть коли моделі даних суворо розділені, а доменний шар позбавлений реляційних анотацій, межа між шарами залишається вразливою. Наступний витік відбувається не на рівні статичних структур, а на рівні динамічної поведінки коду під час виконання запитів.

Під час побудови шару доступу до даних розробники неминуче стикаються з розростанням інтерфейсів сховищ. Для вибірки квартир спочатку потрібен метод `GetByCity(string city)`. Згодом з'являється потреба шукати за ціною: `GetByCityAndPriceRange(...)`. Далі бізнес просить сортувати за датою публікації, фільтрувати за поверхом чи наявністю ліфта. Інтерфейс сховища розбухає від десятків однотипних сигнатур, кожна з яких відрізняється лише парою умов у блоці `WHERE`.

Прагнення скоротити рутинний код підштовхує до спокусливого рішення: навіщо створювати окремі методи, якщо можна повернути з репозиторію універсальний інтерфейс `IQueryable<T>`? Тоді викликач у контролері чи прикладному сервісі зможе самостійно дописувати будь-які фільтри за допомогою виразів LINQ:

```csharp
// Здається ідеальним рішенням: один метод на всі випадки життя
IQueryable<Apartment> GetAll();
```

Цей підхід виглядає верхом гнучкості, проте він закладає в систему приховану часову міну.

Справа в тому, що інтерфейс `IQueryable` не є колекцією завантажених у пам'ять об'єктів. Він представляє дерево синтаксису виразу (від грец. @@en|syntaxis@@ — побудова, поєднання, @@en|abstract syntax tree@@), нерозривно пов'язане з постачальником запитів (`IQueryProvider`) і відкритим контекстом сесії конкретної СКБД.

Прокидання цього інтерфейсу крізь архітектурну межу спричиняє три критичні збої:

Перший збій — падіння під час трансляції виразу в рантаймі.
Коли розробник пише запит над колекцією об'єктів у пам'яті (`IEnumerable`), компілятор мови гарантує, що будь-який коректний вираз буде обчислено. Але для `IQueryable` компілятор перевіряє лише синтаксис C#, а не здатність конкретного провайдера перекласти цей код на діалект SQL.

Якщо у веб-контролері викликати власний допоміжний метод чи функцію форматування:

```csharp
var results = repository.GetAll()
    .Where(a => StringHelper.MatchesMask(a.PostalCode, mask))
    .ToList();
```

код успішно скомпілюється. Проте під час виконання користувач отримає аварійне завершення запиту: ORM викине `System.InvalidOperationException` із повідомленням про те, що даний вираз неможливо транслювати в SQL. Типізований інтерфейс обдурив клієнта: він створив ілюзію повної свободи запитів, але реально підтримує лише ту підмножину операцій, яку розуміє драйвер конкретної бази даних.

Другий збій — часовий розрив і збій закритої сесії.
Механізм відкладеного виконання (від лат. @@en|differre@@ — відкладати, переносити, @@en|deferred execution@@) означає, що SQL-запит надсилається до бази не в момент створення `IQueryable`, а лише тоді, коли програма починає читати записи: під час виклику `.ToList()`, у циклі `foreach` або під час передавання результату в потік серіалізації.

Якщо метод сервісу чи сховища самостійно керує підключенням до бази і закриває сесію перед поверненням результату, контролер отримує синтаксичне дерево, чий життєвий контекст уже мертвий. Коли веб-сервер починає генерувати HTTP-відповідь і перебирати колекцію, ORM намагається виконати запит через уже звільнене з'єднання. У середовищі .NET це викликає збій через спробу доступу до закритого контексту (`Cannot access a disposed context`), а в середовищі Java/Hibernate призводить до аварії `LazyInitializationException: could not initialize proxy - no Session`. Детальніше про контроль життєвого циклу підключень див. [керування транзакційними межами](root:progarch/transaction-boundary-management).

Третій збій — лавина запитів N+1 та втрата контролю над навантаженням.
Намагаючись обійти помилку закритої сесії, розробники часто залишають сесію бази даних відкритою протягом усього часу обробки HTTP-запиту (антипатерн @@en|Open Session in View@@). Це відкриває дорогу найпідступнішій проблемі — лінивому завантаженню (@@en|lazy loading@@).

Коли сутність має зв'язані дані (наприклад, фотографії квартири чи історію платежів), ORM не завантажує їх одразу, а підставляє об'єкт-замінник (проксі). Коли JSON-серіалізатор у контролері звертається до поля `apartment.Photos`, проксі-об'єкт непомітно для розробника надсилає окремий SQL-запит до бази:

```sql
SELECT * FROM photos WHERE apartment_id = 101;
```

Для списку зі 100 квартир серіалізатор спочатку виконає 1 запит на завантаження списку квартир, а потім ще 100 окремих запитів на завантаження фотографій для кожної квартири окремо. Замість одного швидкого запиту база даних отримує лавину зі 101 запиту — хрестоматійну проблему N+1 запиту (@@en|N+1 query problem@@).

![Часова діаграма відкладеного виконання IQueryable зі зсувом точки запиту у веб-контролер](img/deferred-iqueryable-boundary-leak.svg)
*Часова діаграма взаємодії: сховище повертає синтаксичне дерево виразу IQueryable замість виконаних даних і закриває з'єднання, через що спроба серіалізації у веб-контролері ініціює нові SQL-запити поза контекстом сесії та спричиняє лавину N+1 запитів або аварійний збій.*

Найнебезпечнішим наслідком цієї поведінки стає зсув архітектурної відповідальності: керування навантаженням на базу даних вислизає з інфраструктурного шару та опиняється всередині веб-контролерів і механізмів серіалізації. Інженери, які оптимізують базу даних, більше не бачать точок входу SQL-запитів: додавання одного поля в JSON-відповідь на рівні представлення здатне миттєво вичерпати пул з'єднань і паралізувати роботу всієї платформи.

Практичну покрокову ліквідацію таких витоків та заміну дірявих сигнатур на безпечні інтерфейси наведено у [вставці про рефакторинг дірявої межі ORM](root:progarch/layer-leakage/proj-refactoring-leaky-orm-boundary.md).

```csharp
using Microsoft.AspNetCore.Mvc;

namespace RealEstate.Presentation.Controllers;

// Небезпечний контракт: сховище випускає за межі шару дерево запиту IQueryable
public interface IApartmentRepository
{
    IQueryable<Apartment> GetAll();
}

[ApiController]
[Route("api/apartments")]
public class ApartmentController : ControllerBase
{
    private readonly IApartmentRepository _repository;

    public ApartmentController(IApartmentRepository repository)
    {
        _repository = repository;
    }

    [HttpGet("by-region")]
    public IActionResult GetByRegion([FromQuery] string regionCode)
    {
        // Пастка: виклик методу C#, невідомого для SQL-провайдера.
        // Код компілюється без помилок, але під час виконання викидає InvalidOperationException
        var apartments = _repository.GetAll()
            .Where(a => CustomRegionFilter.IsValid(a.PostalCode, regionCode))
            .ToList();

        return Ok(apartments);
    }
}
```

Щоб ліквідувати поведінкове протікання, сховище проектує дані безпосередньо у незмінні DTO та негайно матеріалізує вибірку в межах власного адаптера:

```csharp
namespace RealEstate.Application.Boundaries;

// Незмінна проекція даних, повністю відрізана від контексту бази
public record ApartmentSummaryDto(
    long Id,
    string Address,
    decimal Price,
    IReadOnlyList<string> PhotoUrls);

// Контракт сховища замкнений на завдання системи, а не на інфраструктурні запити
public interface IApartmentReadRepository
{
    Task<IReadOnlyList<ApartmentSummaryDto>> GetSummariesByCityAsync(
        string city,
        CancellationToken cancellationToken = default);
}
```

```csharp
using Microsoft.EntityFrameworkCore;

namespace RealEstate.Infrastructure.Persistence;

public class ApartmentSqlRepository : IApartmentReadRepository
{
    private readonly ApplicationDbContext _context;

    public ApartmentSqlRepository(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<IReadOnlyList<ApartmentSummaryDto>> GetSummariesByCityAsync(
        string city,
        CancellationToken cancellationToken = default)
    {
        // Запит проектується безпосередньо в DTO і матеріалізується всередині сховища:
        // з'єднання з базою закривається, назовні повертаються виключно готові дані
        return await _context.Apartments
            .AsNoTracking()
            .Where(a => a.City == city && a.Status == "Active")
            .Select(a => new ApartmentSummaryDto(
                a.Id,
                a.Address,
                a.Price,
                a.Photos.Select(p => p.Url).ToList()))
            .ToListAsync(cancellationToken);
    }
}
```

> 🔧 **Навіщо це.**
> Замикання запитів усередині сховища за допомогою явної проекції в DTO та негайної матеріалізації гарантує детермінізм виконання: адаптер інфраструктури повністю контролює оптимізацію SQL, ізолює життєвий цикл з'єднання та запобігає прихованим аваріям закритої сесії чи лавинам N+1 запитів.

## Протікання винятків і деталей транспорту: як технічні збої захоплюють домен

Користувач системи керування мікрокліматом Digital Homes реєструє в мобільному додатку новий розумний термостат для спальні. Сервіс реєстрації приймає серійний номер пристрою, створює сутність і викликає збереження через інтерфейс репозиторію. Якщо цей термостат уже був зареєстрований для іншої квартири, користувач очікує зрозуміле пояснення: «Пристрій із таким серійним номером уже додано до системи». Натомість застосунок раптово повертає помилку сервера з кодом 500, а журнал логів заповнюється аварійним дампом:

```text
Npgsql.PostgresException (0x80004005): 23505: duplicate key value violates unique constraint "devices_serial_number_key"
   at Npgsql.Internal.NpgsqlConnector.ReadMessageLong(...)
   at Npgsql.NpgsqlDataReader.NextResult(...)
   at DigitalHomes.Infrastructure.Repositories.DeviceRepository.AddAsync(...)
```

Низькорівневий виняток (від лат. *exceptio* — вилучення, непередбачена обставина) драйвера СКБД безперешкодно прошив репозиторій, доменний сервіс і веб-контролер, вибухнувши на межі системи.

Першою реакцією на такий збій часто стає спроба перехопити помилку безпосередньо в бізнес-сервісі чи контролері:

```csharp
// Антипатерн: доменний сервіс аналізує технічні деталі конкретної СКБД
public class DeviceRegistrationService
{
    private readonly IDeviceRepository _repository;

    public DeviceRegistrationService(IDeviceRepository repository)
    {
        _repository = repository;
    }

    public async Task RegisterDeviceAsync(RegisterDeviceCommand command)
    {
        try
        {
            var device = new Thermostat(command.DeviceId, command.SerialNumber);
            await _repository.AddAsync(device);
        }
        catch (NpgsqlException ex) when (ex.SqlState == "23505")
        {
            // Бізнес-код аналізує вендорний код PostgreSQL
            throw new DeviceAlreadyExistsException(command.SerialNumber, ex);
        }
    }
}
```

Такий код створює оманливе враження розв'язаної проблеми: виняток перехоплено, доменну помилку згенеровано. Проте ціною стає руйнування архітектурної межі:

1. **Пряма залежність від постачальника технології.** Бізнес-шар змушений підключати клієнтську бібліотеку `Npgsql`. Чисте ядро системи тепер знає, яка саме база даних працює на сервері.
2. **Прив'язка до вендорних магічних констант.** Рядок `"23505"` — це стандартний код стану SQLSTATE для порушення унікальності в PostgreSQL. Якщо для тестування або через зміну вимог проєкт перейде на Microsoft SQL Server, помилка порушення унікальності прийде з числовим кодом `2627` або `2601`. У SQLite це буде код `19 (SQLITE_CONSTRAINT)`, а в MySQL — `1062`. Бізнес-сервіс, налаштований на рядок `"23505"`, пропустить новий виняток повз фільтр `when`, і система знову впаде з аварією.
3. **Параліч модульного тестування.** Справжній об'єкт `NpgsqlException` неможливо створити через звичайний виклик `new` у швидкому юніт-тесті: його внутрішня структура закрита або вимагає реальних мережевих буферів драйвера. Щоб перевірити просте бізнес-правило («повідомити про дублікат пристрою»), інженер змушений підіймати реальний екземпляр PostgreSQL у Docker-контейнері, витрачаючи секунди замість мікросекунд.

Аналогічний прорив трапляється на стику з мережевим транспортом. Якщо шлюз пристроїв Digital Homes надсилає команду на терморегулятор через HTTP або сокети, розрив з'єднання породжує системний `SocketException` з кодом `10060 (WSAETIMEDOUT)` чи `HttpRequestException` зі статусом `504 Gateway Timeout`. Коли доменний шар починає аналізувати `HttpStatusCode.GatewayTimeout`, концепції веб-транспорту стають частиною бізнес-логіки. Якщо протокол зв'язку змінять на бінарний MQTT чи CoAP, де статусів HTTP взагалі не існує, доведеться переписувати бізнес-правила системи.

Ще одна прихована загроза полягає в дрейфі версій драйверів. Оновлення мінорної версії бібліотеки доступу до даних може змінити внутрішню ієрархію класів — наприклад, обернути виняток сокета у власний `NpgsqlConnectionException`. Оскільки бізнес-сервіс очікував базовий `SocketException`, фільтр перехоплення не спрацює, перетворивши звичайне оновлення стороннього пакета на виробничу аварію.

Архітектурний захист від таких проривів забезпечує рубіж трансляції винятків (@@en|exception translation boundary@@). Трансляція (від лат. *translatio* — перенесення, переведення) означає, що жодна технічна помилка інфраструктури не має права перетнути межу шару в сирому вигляді.

Адаптер сховища чи шлюзу зобов'язаний перехоплювати помилки драйверів і сокетів безпосередньо в місці їхнього виникнення й перетворювати їх на зрозумілі домену типи:

![Рубіж трансляції винятків на стику інфраструктурного адаптера й бізнес-домену: перехоплення таймаутів сокетів і реляційних кодів помилок із перетворенням їх на типізовані доменні результати](img/exception-translation-boundary.svg)
*Схема рубежу трансляції винятків: низькорівневі помилки сокетів і специфічні коди бази даних ізолюються всередині адаптера, повертаючи в бізнес-шар чисті типізовані помилки.*

Трансляція може виконуватися у типізовані доменні винятки або у функціональний тип результату Result. Подробиці реалізації такого механізму розкрито у вставці [Побудова механізму трансляції технічних помилок на межі шарів](root:progarch/layer-leakage/proj-exception-translation-pipeline.md), а концептуальні засади взаємодії з чужими підсистемами описує [Антикорупційний шар](root:progarch/anti-corruption-layer).

Реалізація репозиторію з рубежем трансляції ізолює драйвер усередині адаптера:

```csharp
// Інфраструктурний адаптер інкапсулює вендорні помилки та коди СКБД
public class PostgresDeviceRepository : IDeviceRepository
{
    private readonly NpgsqlConnection _connection;

    public PostgresDeviceRepository(NpgsqlConnection connection)
    {
        _connection = connection;
    }

    public async Task<Result<Unit, DeviceSaveError>> AddAsync(Thermostat device)
    {
        const string sql = "INSERT INTO devices (id, serial_number) VALUES (@Id, @Serial)";

        try
        {
            await _connection.ExecuteAsync(sql, new { Id = device.Id, Serial = device.SerialNumber });
            return Result.Success<Unit, DeviceSaveError>(Unit.Value);
        }
        catch (PostgresException ex) when (ex.SqlState == PostgresErrorCodes.UniqueViolation)
        {
            // Вендорний код 23505 локалізовано в інфраструктурі
            return Result.Failure<Unit, DeviceSaveError>(
                DeviceSaveError.DuplicateSerialNumber(device.SerialNumber));
        }
        catch (NpgsqlException ex)
        {
            // Технічний розрив зв'язку не показує нутрощі бази назовні
            return Result.Failure<Unit, DeviceSaveError>(
                DeviceSaveError.InfrastructureUnavailable(ex.Message));
        }
    }
}
```

Тепер доменний сервіс оперує виключно власними категоріями:

```csharp
// Доменний сервіс не має жодного імпорту Npgsql чи реляційних понять
public class DeviceRegistrationService
{
    private readonly IDeviceRepository _repository;

    public DeviceRegistrationService(IDeviceRepository repository)
    {
        _repository = repository;
    }

    public async Task<Result<Unit, RegistrationError>> RegisterDeviceAsync(RegisterDeviceCommand command)
    {
        var device = new Thermostat(command.DeviceId, command.SerialNumber);
        var saveResult = await _repository.AddAsync(device);

        return saveResult.Match(
            onSuccess: _ => Result.Success<Unit, RegistrationError>(Unit.Value),
            onFailure: error => error switch
            {
                DeviceSaveError.DuplicateSerialNumber => 
                    Result.Failure<Unit, RegistrationError>(RegistrationError.AlreadyRegistered),
                DeviceSaveError.InfrastructureUnavailable => 
                    Result.Failure<Unit, RegistrationError>(RegistrationError.ServiceTemporarilyBusy)
            });
    }
}
```

Бізнес-ядро позбулося залежності від бібліотек СКБД, зберегло інкапсуляцію та легко перевіряється в тестах підставними реалізаціями інтерфейсу `IDeviceRepository`.

> 🔧 **Навіщо це.**
> Рубіж трансляції помилок перетворює непередбачувані аварії драйверів на строгі контракти системи. Завдяки цьому заміна реляційної СКБД, міграція шлюзу на інший транспортний протокол або оновлення драйверів не торкаються бізнес-правил і не вимагають регресійного переписування доменного ядра.

## Чому шари протікають: закон Спольські та крах прозорого збереження

Три форми архітектурного витоку — витік реляційних структур через відкриті сетери, поведінковий витік відкладеного виконання `IQueryable` та прорив драйверних винятків — не є випадковими помилками недосвідчених розробників. Вони виникають навіть у проєктах досвідчених інженерів. Причина полягає у двох фундаментальних факторах: природі абстракцій у програмуванні та економічній спокусі уникнути мапінгу між шарами.

У 2002 році програміст Джоел Спольські сформулював принцип, що став канонічним в інженерії програмного забезпечення: @@en|Law of Leaky Abstractions@@ (закон протікання абстракцій). Він стверджує:

> «Усі нетривіальні абстракції певною мірою протікають».

Саме слово «абстракція» (від лат. *abstractio* — відволікання, відокремлення загального від конкретних деталей) визначає її роль: сховати складність базового механізму за спрощеною моделлю. Класичним прикладом є мережевий протокол TCP. Він пропонує розробникові ілюзію надійного й неперервного потоку байтів: програма відкриває сокет і читає або пише дані так, ніби працює з локальним файлом.

Проте фізична реальність TCP — це ненадійна пакетна мережа IP. Коли мережевий кабель зазнає перешкод або маршрутизатор переповнює буфер, пакети губляться. Протокол TCP змушений повторно надсилати фрагменти, що призводить до падіння пропускної здатності й різкого зростання затримок. Якщо мережа зникає повністю, запис у сокет зависає на таймауті. У цей момент абстракція надійного файлового потоку протікає: інженер більше не може вдавати, що мережі немає, і змушений враховувати розмір вікна передавання, значення MTU та алгоритми керування перевантаженням. Детальніший аналіз цієї закономірності наведено у вставці [Історія формування закону протікання абстракцій Джоела Спольські](root:progarch/layer-leakage/hist-law-of-leaky-abstractions.md).

Те саме явище виникає в шаровій архітектурі. Шари намагаються створити абстракцію, у якій робота з базою даних, файловою системою чи зовнішнім шлюзом виглядає як звичайні виклики методів об'єктів. Проте фізичні властивості збереження — затримки мережі, блокування рядків у реляційних таблицях, транзакційні рівні ізоляції — пробивають створену ілюзію.

На зламі 1990-х і 2000-х років індустрія захопилася концепцією «прозорого збереження» (@@en|transparent persistence@@; персистентність від лат. *persistere* — залишатися, тривати). Архітектурні специфікації того часу, передусім Enterprise JavaBeans (EJB 1.x та 2.x Entity Beans), стверджували, що програміст повинен проєктувати бізнес-модель так, ніби всі сутності постійно перебувають у нескінченній оперативній пам'яті. Механізм збереження мав невидимо синхронізувати стан цих об'єктів із дисковими таблицями реляційної СКБД.

Ця концепція зазнала промислового краху через фундаментальну різницю фізичних характеристик пам'яті й диска:

1. **Прірва у швидкодії.** Звернення до комірки оперативної пам'яті займає одиниці або десятки наносекунд. Мережевий запит до віддаленої дискової бази даних триває одиниці мілісекунд — на п'ять-шість порядків довше.
2. **Пастка обходу зв'язків.** Звичайна ітерація циклом по зв'язаній колекції об'єктів у пам'яті виконується миттєво. У моделі прозорого збереження те саме звернення непомітно генерує лавину окремих SQL-запитів (катастрофа N+1), блокуючи пул з'єднань і перевантажуючи сервер бази даних.
3. **Руйнування узгодженості.** Спроба сховати межі транзакцій призводить до того, що розробник не контролює моменти блокування даних, спричиняючи взаємні блокування (дедлоки) потоків у продуктивному середовищі.

Спроба замаскувати реляційну природу бази даних під звичайні об'єкти викрила [Об'єктно-реляційний розрив](root:sf-data/object-relational-mismatch): реляційна алгебра оперує множинами, кортежами й транзакційними межами, тоді як об'єктна модель спирається на ідентичність екземплярів, посилання та стан у пам'яті. Крах спроб приховати цю прірву докладно розглянуто у вставці [Історія краху концепції прозорого збереження в епоху EJB Entity Beans](root:progarch/layer-leakage/hist-transparent-persistence-fallacy.md).

Якщо протікання шарів неминуче призводять до збоїв, чому розробники знову й знову повторюють ці патерни?

Причина — тактична економія на мапінгу. Створення ізольованих об'єктів для передавання даних (DTO) в інтерфейсі користувача, чистих доменних моделей без анотацій СКБД і спеціалізованих структур зберігання для репозиторію вимагає написання коду перекладання даних. Для простого сценарію читання чи запису це здається зайвою бюрократичною витратою: класи мають майже однакові поля `Id`, `Name`, `Status`. Розробник вирішує прибрати проміжну трансляцію й використати клас ORM-сутності безпосередньо у відповіді веб-контролера.

Ця локальна економія зусиль викликає системний колапс темпів змін. У статті [Ціна мапінгу між шарами](root:progarch/cost-of-layer-mapping) показано, що різні шари системи мають різні годинники:

- **Шар інтерфейсу користувача та API** має швидкий годинник: він змінюється щотижня під вимоги клієнтських додатків, нових екранів мобільного застосунку Digital Homes чи змін у форматуванні дат.
- **Доменний шар** має помірний годинник: правила розрахунку тарифів опалення чи безпеки житла змінюються в ритмі розвитку бізнесу (раз на місяць або квартал).
- **Шар бази даних** має повільний годинник: реляційна схема змінюється обережно й рідко (раз на пів року чи рік), адже кожна міграція таблиць із мільйонами рядів вимагає блокувань, ретельного тестування індексів та узгодження вікон простою.

Коли ORM-сутність прокидається наскрізно від таблиці до JSON-відповіді, ці три годинники виявляються жорстко зчепленими між собою:

| Шар | Природний темп змін | Що стається при наскрізній ORM-сутності |
| :--- | :--- | :--- |
| **Інтерфейс (UI/API)** | Щотижня (спринти, правки клієнтів) | Змушений пристосовуватися до структури таблиць СКБД |
| **Домен** | Щомісяця (зміна бізнес-правил) | Втрачає інкапсуляцію через вимоги ORM до відкритих сетерів |
| **База даних** | Щокварталу (міграції схеми, індекси) | Не може змінити імена колонок без руйнування клієнтського API |

Спроба перейменувати колонку в таблиці бази заради оптимізації реляційного індексу негайно ламає публічний контракт мобільного додатку, оскільки серіалізатор віддає поле під новою назвою. І навпаки: потреба мобільного інтерфейсу отримувати нове агреговане поле змушує додавати колонку в базу або захаращувати доменний клас неперсистентними властивостями. Будь-яка локальна правка втрачає локальність, вимагаючи наскрізного регресійного тестування всієї системи.

Для математичного аналізу таких небажаних залежностей застосовують [Матрицю структури проєктування DSM](root:progarch/layer-leakage/math-dsm-layer-coupling.md): протікання шарів створює щільні паразитні зв'язки у заборонених секторах матриці, руйнуючи її строгу трикутну форму й перетворюючи спрямований потік залежностей на хаотичну мережу.

Закон Спольські не закликає відмовитися від шарів і абстракцій. Він нагадує, що герметичність шару — це не подарунок середовища виконання, а результат інженерної дисципліни. Межа шару працює лише тоді, коли за неї сплачено ціну: явний мапінг даних, трансляцію технічних помилок і контроль напрямку залежностей.

> 🔧 **Навіщо це.**
> Усвідомлення закону протікання абстракцій позбавляє інженера ілюзій щодо «магічних» можливостей фреймворків. Відмова від наскрізного використання моделей бази даних захищає незалежність різних годинників системи, дозволяючи інтерфейсу розвиватися з високою швидкістю, не ставлячи під загрозу стабільність реляційного сховища.

## Герметичні контракти сховища: матеріалізовані проєкції замість витоку запитів

Коли розробник проєктує шар доступу до даних, найсильнішою спокусою стає узагальнена гнучкість. Навіщо створювати окремий метод на кожен сценарій вибірки, якщо можна оголосити один універсальний інтерфейс репозиторію й повернути з нього типізований запит `IQueryable`? Здається, що система отримує ідеальну свободу: зовнішній сервіс чи навіть веб-контролер може самостійно вирішувати, які поля відфільтрувати, за якими критеріями відсортувати записи та де саме розбити результат на сторінки.

Проте за цією позірною зручністю криється повне руйнування архітектурної межі. Повертаючи відкладений вираз запиту, адаптер бази даних не виконує операцію самостійно, а лише передає клієнтському коду будівельний важіль для формування стороннього SQL-запиту. Межа шару стає паперовою: сервіси вищих рівнів починають диктувати структуру реляційних об'єднань (@@en|join@@), вимагають відкритого мережевого з'єднання з базою і відкладають момент завантаження даних аж до серіалізації відповіді. Прихована сесія СКБД розтікається всією програмою, спричиняючи лавину запитів N+1 та аварійні падіння через звернення до закритого контексту сесії.

Щоб зупинити це розмивання, шарова архітектура вимагає першої лінії оборони: заміни узагальнених механізмів вибірки на строгі, орієнтовані на сценарії використання @@en|межові контракти@@ (від лат. *contractus* — угода, договір). Замість надання клієнту права довільно формувати запити, інтерфейс сховища декларує вузькі операції, кожна з яких точно відповідає конкретному бізнес-завданню споживача.

Усередині такого контракту принципово розмежовують два типи операцій: читання даних для відображення та отримання стану для зміни. Коли системі потрібно показати перелік сенсорів на панелі приладів, витягувати з бази повні ORM-сутності з усіма внутрішніми зв'язками — надлишково й небезпечно. Мапінг завантажених сутностей у пам'яті все одно змушує ORM вичитувати з таблиць десятки непотрібних колонок і створює ризик випадкового спрацьовування лінивих навігаційних властивостей.

Розв'язком стає техніка, відома як @@en|проєкція запиту@@ (англ. @@en|query projection@@, від лат. *projectio* — викидання вперед, винесення форми на площину). За цієї техніки форма кінцевих даних конструюється безпосередньо в реляційному виразі сховища. Інфраструктурний адаптер транслює лише потрібні для сценарію стовпчики в інструкцію вибірки СКБД (`SELECT id, serial_number, status FROM ...`), поміщаючи результат відразу в незмінний @@en|об'єкт передавання даних@@ (англ. @@en|Data Transfer Object@@, DTO; від лат. *transferre* — переносити).

Матеріалізація (від лат. *materialis* — речовинний, набуття фізичної форми) цього DTO відбувається виключно **до** того, як дані перетнуть архітектурну межу сховища. Адаптер ініціює негайне виконання SQL-запиту (наприклад, через виклик `.ToListAsync()`) і повністю завершує взаємодію з базою.

![що показано і що з неї видно](img/encapsulated-query-projections.svg)
*Ізоляція виконання запитів і сесії всередині інфраструктурного адаптера: фільтрація, з'єднання та проекція в незмінний DTO відбуваються до перетину межі, тому клієнт отримує чистий знімок даних без проксі-об'єктів і відкладеного доступу.*

Головний інженерний наслідок такої ізоляції — фізичне унеможливлення лінивого завантаження (англ. @@en|lazy loading@@) за межами сховища. Повернутий DTO є простим об'єктом у пам'яті (record або незмінною структурою), повністю відрізаним від сесії СКБД. Він не містить динамічних проксі-обгорток чи невидимих перехоплювачів властивостей. Навіть якщо розробник у контролері спробує звернутися до даних, які не були включені в контракт, компілятор повідомить про помилку ще на етапі збирання, а рантайм гарантовано не робитиме несанкціонованих мережевих запитів.

Сесія бази даних (наприклад, `DbContext` чи `EntityManager`) має жити рівно стільки, скільки виконується метод адаптера. Будь-які спроби протягнути сесію у веб-шар (патерн @@en|Open Session in View@@) є порушенням межі. Якщо бізнес-сценарію потрібні додаткові відомості з інших таблиць, зв'язок має бути явно описаний у межовому проєктованому запиті й матеріалізований всередині адаптера.

> 🔧 **Навіщо це.**
> Заборона повернення `IQueryable` та примусова матеріалізація проєкцій у незмінні DTO знімає з веб-контролерів і доменних сервісів тягар керування підключеннями до бази даних. Це захищає систему від прихованих збоїв закритої сесії, гарантує передбачуваний час виконання запитів і дає змогу оптимізувати схему зберігання чи індекси без ризику зламати бізнес-код через непередбачувані сторонні ефекти ORM.

Подібна ізоляція не є безкоштовною: вона вимагає створення явних структур під кожен сценарій. Проте, як розкрито в темі [Ціна мапінгу між шарами](root:progarch/cost-of-layer-mapping), ці витрати окупаються незалежністю життєвих циклів компонентів. Коли ж операція вимагає зміни стану домену, репозиторій повертає не DTO, а повноцінний доменний агрегат із перевіреними інваріантами, виконання якого підпорядковане правилам [Керування транзакційними межами](root:progarch/transaction-boundary-management). Ігнорування цього розділення знову повертає систему до хронічної проблеми [Об'єктно-реляційний розрив](root:sf-data/object-relational-mismatch), де реляційні таблиці намагаються видати за сутності реального світу.

Практичний покроковий перехід від протікаючого `IQueryable` до замкнених проєкцій розібрано у вставці [Практичний рефакторинг сервісу з витоками ORM](root:progarch/layer-leakage/proj-refactoring-leaky-orm-boundary.md).

Розглянемо реалізацію герметичного контракту на прикладі сервісу моніторингу розумних будинків:

```csharp
// Контракт межі: чіткі сценарії замість абстрактного IQueryable
public interface IDeviceReadRepository
{
    // Повертає матеріалізований знімок пристроїв для моніторингу
    Task<IReadOnlyList<DeviceSummaryDto>> GetActiveDevicesSummaryAsync(
        HomeId homeId, 
        CancellationToken cancellationToken = default);
}

// Незмінний DTO: чистий знімок без прихованих зв'язків чи проксі
public sealed record DeviceSummaryDto(
    Guid DeviceId,
    string SerialNumber,
    string ModelName,
    string RoomName,
    DateTimeOffset LastHeartbeat);

// Інфраструктурний адаптер: замкнене виконання та проєкція в SQL
public sealed class SqlDeviceReadRepository : IDeviceReadRepository
{
    private readonly HomeAutomationDbContext _dbContext;

    public SqlDeviceReadRepository(HomeAutomationDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public async Task<IReadOnlyList<DeviceSummaryDto>> GetActiveDevicesSummaryAsync(
        HomeId homeId, 
        CancellationToken cancellationToken = default)
    {
        var targetHomeId = homeId.Value;

        // Явна проєкція: формує точний SQL SELECT лише з потрібними полями
        // AsNoTracking запобігає підключенню сутностей до трекера змін сесії
        return await _dbContext.Devices
            .AsNoTracking()
            .Where(d => d.HomeId == targetHomeId && d.IsActive)
            .Select(d => new DeviceSummaryDto(
                d.Id,
                d.SerialNumber,
                d.Model.Name,
                d.Room.Title,
                d.LastHeartbeat))
            .ToListAsync(cancellationToken); 
            // Точка матеріалізації: SQL-запит відправлено й завершено,
            // назовні виходить автономний список незмінних записів
    }
}
```

У цьому коді виклик `.Select(...)` транслюється бібліотекою доступу до бази даних у безпосереднє об'єднання таблиць `Devices`, `Models` та `Rooms` на рівні SQL-сервера. Виклик `.ToListAsync()` фіксує матеріалізацію: дані вичитуються з мережевого потоку, інстанціюються у формі списку `DeviceSummaryDto`, а з'єднання із сесією вичерпується. Зовнішній клієнт отримує самодостатній масив значень. Жодна дія у веб-шарі не здатна змусити цей об'єкт генерувати нові SQL-запити.

## Рубіж трансляції помилок: технічні збої мовою бізнес-наслідків

Навіть якщо контракти даних стали повністю непроникними, архітектурні шари можуть зазнати протікання у зворотному напрямку — знизу вгору через стек викликів, коли інфраструктурний механізм дає збій.

Розглянемо штатну бізнес-ситуацію: мешканець додає новий датчик до системи розумного дому, але вказує серійний номер, який уже закріплений за іншим пристроєм. Реляційна таблиця захищена обмеженням унікальності (@@en|unique constraint@@) за полем `serial_number`. Адаптер сховища намагається виконати команду додавання запису. Що відбувається на рівні драйвера? База даних відхиляє команду й генерує низькорівневий код помилки: наприклад, PostgreSQL повертає стан `23505` (`unique_violation`), а бібліотека Npgsql генерує виняток `PostgresException`.

Якщо інфраструктурний шар не містить рубежу захисту, цей виняток безперешкодно летить крізь шар доменної логіки й досягає веб-контролера. У цей момент розробник опиняється перед вибором із двох руйнівних компромісів:

1. Дозволити веб-шару або глобальному фільтру винятків самостійно аналізувати `PostgresException`. Це означає, що веб-шар мусить володіти знаннями про коди помилок реляційної СКБД і залежати від драйвера бази. Зміна типу бази чи перехід на хмарне сховище миттєво зламає клієнтське розпізнавання конфліктів.
2. Перехопити `PostgresException` всередині сервісу реєстрації пристроїв у домені. Але тоді сам домен мусить додати пряму залежність від бібліотеки `Npgsql`! Бізнес-правила, покликані виражати правила поведінки розумного дому, стають заручниками конкретного виробника бази даних.

Виходом із цієї пастки є друга стратегія захисту: побудова конвеєра трансляції помилок на інфраструктурній межі. Трансляція винятків (від лат. *translatio* — перенесення, переведення) — це архітектурний патерн, за якого технічні винятки драйверів, сокетів і транспортних клієнтів перехоплюються безпосередньо всередині інфраструктурного адаптера й конвертуються в поняття, що належать мові бізнес-домену.

Інфраструктурний адаптер (репозиторій, клієнт брокера черг чи шлюз зовнішнього сервісу) є єдиним компонентом системи, який має законне право залежати від бібліотек драйвера. Саме він аналізує вендорні статуси та перетворює їх на зрозумілі для домену структури.

У сучасній архітектурі застосовують два підходи до оформлення трансляції:

1. **Типізовані доменні винятки** (англ. @@en|typed domain exceptions@@): наприклад, створення класу `DeviceAlreadyRegisteredException(serialNumber)`. Доменний сервіс чи контролер реагує на конкретний тип помилки, не знаючи про SQL. Проте винятки в більшості мов не відбиваються в сигнатурі методу, залишаючи потік керування неявним, а побудова трасування стека (@@en|stack trace@@) створює помітні накладні витрати на швидкодію.
2. **Функціональний тип результату** (англ. @@en|Result type@@, або варіант вибору @@en|Either@@; від староанглійського *ǣgðer* — кожен із двох). Метод репозиторію відмовляється від генерації винятків для передбачуваних збоїв і повертає контейнер `Result<TValue, TError>`, який явно декларує в сигнатурі всі можливі варіанти завершення операції.

Окрему увагу на межі інфраструктури приділяють розмежуванню характеру помилок. Порушення унікальності або відсутність зовнішнього ключа — це семантичні наслідки бізнес-операцій; вони підлягають трансляції у доменні типи результату. Натомість тимчасові збої (англ. @@en|transient fault@@, від лат. *transiens* — той, що минає) — таймаути з'єднання, обриви мережевих сокетів або взаємні блокування (@@en|deadlock@@) — не мають бізнес-аналогів у домені. Їх опрацьовують політиками повторних спроб (@@en|retry policy@@) безпосередньо всередині адаптера, або піднімають як узагальнений системний збій доступності сховища.

> 🔧 **Навіщо це.**
> Трансляція технічних винятків на межі інфраструктури перетворює незрозумілі SQL-коди помилок або мережеві розриви на чіткі доменні наслідки. Доменні сервіси та контролери отримують змогу реагувати на бізнес-відмови (наприклад, повідомити користувача про зайнятий серійний номер) без жодного імпорту бібліотек СКБД чи зашивання вендорних кодів у бізнес-правила.

Побудований рубіж діє як класичний [Антикорупційний шар](root:progarch/anti-corruption-layer), не дозволяючи деталям зовнішніх підсистем забруднювати модель предметної області. Для глибшого вивчення механік безпечного повернення результатів рекомендуємо звернутися до теми [Шаблон Result для доменних помилок](root:progarch/result-pattern-domain-errors).

Повний цикл побудови такого рубежу — від перехоплення драйверного коду до мапінгу в HTTP-статуси — описано у вставці [Механізм трансляції технічних помилок на межі шарів](root:progarch/layer-leakage/proj-exception-translation-pipeline.md).

Проілюструємо реалізацію конвеєра трансляції на прикладі реєстрації пристрою:

```csharp
// Доменний контракт помилок: лише бізнес-значення, жодних винятків СКБД
public abstract record DeviceRegistrationError
{
    public sealed record DuplicateSerialNumber(string SerialNumber) : DeviceRegistrationError;
    public sealed record StorageUnavailable(string Reason) : DeviceRegistrationError;
}

// Контракт сховища повертає типізований результат замість неконтрольованих збоїв
public interface IDeviceWriteRepository
{
    Task<Result<Device, DeviceRegistrationError>> RegisterAsync(
        Device device, 
        CancellationToken ct = default);
}

// Інфраструктурний адаптер: перехоплює помилки драйвера й транслює їх
public sealed class SqlDeviceWriteRepository : IDeviceWriteRepository
{
    private readonly HomeAutomationDbContext _context;
    private const string PostgresUniqueViolation = "23505";

    public SqlDeviceWriteRepository(HomeAutomationDbContext context)
    {
        _context = context;
    }

    public async Task<Result<Device, DeviceRegistrationError>> RegisterAsync(
        Device device, 
        CancellationToken ct = default)
    {
        try
        {
            await _context.Devices.AddAsync(device, ct);
            await _context.SaveChangesAsync(ct);
            return Result<Device, DeviceRegistrationError>.Success(device);
        }
        catch (DbUpdateException ex) when (ex.InnerException is PostgresException pgEx)
        {
            // Перевірка низькорівневого вендорного коду всередині адаптера
            if (pgEx.SqlState == PostgresUniqueViolation)
            {
                // Трансляція в чисте доменне поняття
                return Result<Device, DeviceRegistrationError>.Failure(
                    new DeviceRegistrationError.DuplicateSerialNumber(device.SerialNumber.Value));
            }

            // Інші збої СКБД транслюються в помилку доступності інфраструктури
            return Result<Device, DeviceRegistrationError>.Failure(
                new DeviceRegistrationError.StorageUnavailable(pgEx.MessageText));
        }
        catch (SocketException)
        {
            // Мережевий збій ізолюється на межі інфраструктури
            return Result<Device, DeviceRegistrationError>.Failure(
                new DeviceRegistrationError.StorageUnavailable("З'єднання зі сховищем втрачено."));
        }
    }
}
```

Тепер клієнтський код у сервісі або контролері опрацьовує результат через виразне зіставлення зі зразком, не маючи жодного посилання на пакунки бази даних:

```csharp
// Доменний сервіс: працює виключно з виразними бізнес-наслідками
public sealed class DeviceRegistrationService
{
    private readonly IDeviceWriteRepository _repository;

    public DeviceRegistrationService(IDeviceWriteRepository repository)
    {
        _repository = repository;
    }

    public async Task<RegistrationOutcome> RegisterDeviceAsync(RegisterDeviceCommand command)
    {
        var device = Device.Create(command.SerialNumber, command.ModelName);

        var registrationResult = await _repository.RegisterAsync(device);

        return registrationResult.Match(
            onSuccess: createdDevice => 
                RegistrationOutcome.Success(createdDevice.Id),
            onFailure: error => error switch
            {
                DeviceRegistrationError.DuplicateSerialNumber dup => 
                    RegistrationOutcome.Conflict($"Пристрій із серійним номером {dup.SerialNumber} вже зареєстровано."),
                DeviceRegistrationError.StorageUnavailable => 
                    RegistrationOutcome.Unavailable("Сховище тимчасово недоступне. Спробуйте пізніше."),
                _ => RegistrationOutcome.Unexpected("Непередбачена помилка реєстрації.")
            });
    }
}
```

У результаті доменний сервіс стає цілковито ізольованим від технічного середовища. Якщо команда вирішить замінити PostgreSQL на DocumentDB чи мікросервісний шлюз, зміни торкнуться виключно класу `SqlDeviceWriteRepository`: сигнатура методу та логіка опрацювання помилок у `DeviceRegistrationService` залишаться непорушними.

## Автоматизовані вартові меж: архітектурні фітнес-тести проти дрейфу шарів

На початку проєкту межі між шарами здаються непорушними. Команда узгоджує діаграму взаємодії, описує обов'язки кожного модуля в документації та фіксує правила чистоти коду на стартових зборах. Проте за кілька місяців система виростає, до розробки долучаються нові інженери, а бізнес вимагає термінового випуску функціональності. Під тиском дедлайну розробникові потрібно перевірити стан датчика розумного будинку перед зміною режиму обігріву. Створювати окрему матеріалізовану проєкцію, описувати метод у контракті сховища й прокидати його крізь прикладний сервіс здається задовгим шляхом задля одного поля. Інженер додає прямий імпорт `Microsoft.EntityFrameworkCore` чи `jakarta.persistence` безпосередньо у доменну сутність або викликає контекст бази даних із веб-контролера, заспокоюючи себе тим, що це лише тимчасовий компроміс.

На ручному код-рев'ю серед сотень змінених рядків один рядок імпорту інфраструктурного пакета виглядає як незначна технічна деталь. Рев'юер зосереджений на бізнес-сценарії: чи вимикається котел, чи коректно надсилається сповіщення, чи немає явних логічних помилок. Оцінити, як один додатковий зв'язок змінює топологію всієї системи, людина під час перегляду коду не здатна. Так виникає @@en|architectural drift@@ (архітектурний дрейф; від грец. *architekton* — будівничий, зодчий та англ. *drift* / нід. *drijven* — повільне зміщення за течією) — поступова, непомітна ерозія ізоляції між модулями. Докладніше про природу цього явища розповідає [Архітектурний дрейф](root:progarch/architectural-drift). Жоден компроміс окремо не ламає систему, але накопичення сотень таких зв'язків зводить шарову архітектуру до формальності. Домовленості в документації забуваються, а усна дисципліна випаровується під першим виробничим тиском. Захист меж не може спиратися на людську пильність — він має стати механічним бар'єром у процесі збирання системи.

### Автоматизовані фітнес-функції у конвеєрі перевірки

Щоб перевести архітектурні правила з площини побажань у площину невідворотного контролю, застосовують @@en|fitness function@@ (архітектурна фітнес-функція; термін запозичено з еволюційних обчислень, від англ. *fit* — придатний, належний). Її концептуальні засади розкриває матеріал [Архітектурні фітнес-функції](root:progarch/architectural-fitness-functions). Архітектурний фітнес-тест — це звичайний програмний тест, який перевіряє не поведінку бізнес-логіки системи, а структуру самої кодової бази: напрямки залежностей між модулями, правила доступу між просторами імен та склад публічних інтерфейсів.

Такі тести стають обов'язковим етапом конвеєра неперервної інтеграції (@@en|Continuous Integration@@, CI/CD). Тест компілюється разом із проєктом і виконується під час кожної перевірки гілки або пул-реквесту. Якщо інженер додає заборонену залежність, тест завершується аварією, збірка стає червоною, а автоматика блокує злиття коду в основну гілку. Важлива властивість фітнес-тестів — їхня надзвичайна швидкість. Вони не запускають веб-сервер, не відкривають мережевих сокетів і не звертаються до реальної СКБД. Тестовий рушій зчитує скомпільовані метадані (байткод класів JVM або проміжний IL-код збірок .NET) і виконує статичний аналіз графа типів. Сотні архітектурних правил перевіряються за кількасот мілісекунд, що унеможливлює аргумент про «заповільнення збірки». Практичний процес створення такого набору перевірок розібрано у [вставці proj-arch-fitness-tests](root:progarch/layer-leakage/proj-arch-fitness-tests.md).

### Три рубежі декларативного захисту шарів

Ефективний захист вимагає чітких правил щодо того, які саме зв'язки вважаються порушенням. У тришаровій системі виділяють три критичні контури перевірки:

1. **Повна ізоляція домену від інфраструктури та транспорту.** Доменний шар містить сутності та чисті бізнес-правила системи. Він не повинен мати жодного уявлення про таблиці СКБД, мережеві сокети чи протоколи передавання даних. Забороняється імпортувати пакети ORM (`Microsoft.EntityFrameworkCore`, `NHibernate`, `jakarta.persistence`, `org.hibernate`), веб-фреймворків (`Microsoft.AspNetCore`, `org.springframework.web`) та бібліотек серіалізації в простори імен домену. Якщо цей рубіж проривається, виникає [Об'єктно-реляційний розрив](root:sf-data/object-relational-mismatch), через який технічні вимоги бази починають спотворювати чисті інваріанти домену.

2. **Заборона обходу проміжних шарів (патерн bypass).** Зовнішній шар представлення (контролери, обробники API-запитів) зобов'язаний взаємодіяти з системою виключно через шар застосунку (сценарії використання чи команди). Пряме звернення з контролера до репозиторію або контексту бази даних у шарі інфраструктури суворо забороняється. Зрізання кутів руйнує [Керування транзакційними межами](root:progarch/transaction-boundary-management) і перетворює шар застосунку на [Шар, що лише передає далі](root:progarch/pass-through-layer), позбавляючи систему єдиної точки валідації, авторизації та аудиту.

3. **Герметичність публічних контрактів.** Навіть якщо інфраструктурний клас сховано за інтерфейсом, його сигнатура може протікати, якщо методи приймають чи повертають специфічні структури даних драйвера або бібліотек доступу до даних. Публічні контракти портів повинні оперувати лише доменними типами або незмінними структурами передавання даних (DTO). Будь-який технічний виняток має транслюватися всередині адаптера, щоб зберегти прийнятною [Ціну мапінгу між шарами](root:progarch/cost-of-layer-mapping) та вберегти домен від спотворення, спираючись на [Антикорупційний шар](root:progarch/anti-corruption-layer).

Для формулювання цих обмежень використовують декларативні бібліотеки перевірки архітектури: ArchUnit для екосистеми Java/Kotlin та NetArchTest для платформи .NET. Повний опис доступних методів конструювання правил наведено у [вставці api-archunit-layer-dsl](root:progarch/layer-leakage/api-archunit-layer-dsl.md).

### Матриця структури проєктування: виявлення прихованих зв'язків

Коли система налічує тисячі класів, точкових правил для окремих просторів імен може виявитися недостатньо. Складні витоки часто маскуються за непрямими або транзитивними залежностями: модуль `A` посилається на `B`, `B` на `C`, а `C` несподівано звертається назад до `A`, утворюючи прихований цикл.

Для глобального аудиту та топологічного контролю системи використовують інструмент системної інженерії — @@en|Design Structure Matrix@@ (матриця структури проєктування, DSM; від лат. *matrix* — джерело, таблиця та *structura* — будова, розташування частин). Матриця DSM представляє граф залежностей у вигляді квадратної таблиці розміром `N × N`, де рядки й стовпці відповідають підсистемам або модулям у порядку їхнього ієрархічного розташування згори вниз:

1. Представлення (Presentation)
2. Застосунок (Application)
3. Домен (Domain)
4. Інфраструктура (Infrastructure)

Елемент матриці на перетині рядка `i` та стовпця `j` показує, чи залежить модуль `i` від модуля `j`. Якщо прийняти домовленість, що рядок позначає споживача залежності, а стовпець — постачальника, то за ідеальної пошарової архітектури зв'язки спрямовані строго в один бік. Це означає, що всі дозволені ненульові комірки розташовуються виключно по один бік від головної діагоналі, формуючи строго блочно-трикутну матрицю.

Будь-яка ненульова комірка у протилежному трикутнику — це математична фіксація витоку знань: виклик із домену в інфраструктуру або пряме звернення з представлення до бази даних. Наявність симетричних ненульових елементів з обох боків діагоналі сигналізує про наявність взаємного циклічного зчеплення.

Алгоритми топологічного сортування та знаходження компонент сильної зв'язності (алгоритми Тар'яна або Косараджу) автоматично переставляють рядки й стовпці матриці, виявляючи циклічні ядра та обчислюючи коефіцієнт архітектурного дрейфу — частку зв'язків, що порушують трикутну канонічну форму. Повний математичний апарат таких матриць і алгоритми аналізу наведено у [вставці math-dsm-layer-coupling](root:progarch/layer-leakage/math-dsm-layer-coupling.md).

> 🔧 **Навіщо це.**
> Архітектурні фітнес-тести та автоматизований аналіз матриць DSM кардинально змінюють роботу інженерної команди. Вони звільняють технічних лідерів від невдячної ролі ручних наглядачів на код-рев'ю, перетворюючи суб'єктивні суперечки про стиль на об'єктивний результат проходження тестів. Новий розробник отримує миттєвий зворотний зв'язок у терміналі ще до відкриття пул-реквесту, а архітектура системи зберігає свою герметичність і темп розвитку роками, незалежно від плинності кадрів чи напруженості релізних графіків.

Архітектурна межа існує лише тоді, коли спроба її перетнути призводить до аварії збірки. Якщо межа тримається виключно на пам'яті розробників і записах у внутрішній вікі, вона приречена на протікання під першим же виробничим викликом. Фітнес-тести в конвеєрі перевірки роблять правила герметичності реальними інженерними законами системи.
