# 🧮 Математична модель TCO та unit-економіки Digital Homes

Ця математична вставка виводить повний калькуляційний розрахунок сукупної вартості володіння (TCO) та unit-економіки телеметрії й відеопотоків платформою Digital Homes при масштабуванні до 5 мільйонів активних домівок. Без цих формул і математичного апарату неможливо осягнути, чому конкретні архітектурні межі — дельта-фільтрація, WebRTC P2P-транзит та перехід на власні брокери — є фінансово неминучими.

При проєктуванні високонавантажених IoT-систем інженери часто припускаються помилки, рахуючи лише обсяг корисного навантаження (payload) та ігноруючи транспортні заголовки мережевих протоколів, накладні витрати TLS-рукостискань, тарифікаційну дискретність хмарних провайдерів та нелінійне зростання трафіку при вихідних з'єднаннях (Cloud Egress). Цей документ детально розбирає кожен математичний фактор, який формує підсумковий хмарний рахунок.

## 1. Математична модель наївного телеметричного потоку

Розглянемо вихідні параметри масштабу системи Digital Homes. Флот складається з `N_h` підключених будинків. У кожному будинку розміщено `N_s` фізичних давачів різного типу (температура, вологість, давачі руху, розмикання дверей, лічильники споживання електроенергії, давачі витоку газу та води).

Кожен давач опитується локальним контролером з частотою `f_s` (вимірів на секунду). Кожне окреме вимірювання формує корисне навантаження у форматі JSON або MessagePack розміром `S_payload` байтів.

### Аналіз накладних витрат мережевого стека (Protocol Overhead)

При безпосередній відправці кожного виміру в хмару через протокол MQTT поверх захищеного транспортного з'єднання TLS 1.3 корисні дані загортаються в багаторівневий стек протоколів. Кожен рівень додає власний службовий заголовок:

1. **Ethernet II / Wi-Fi кадр:** додає 14 байтів службових даних канального рівня.
2. **IP заголовок (IPv4):** додає 20 байтів (без додаткових опцій).
3. **TCP заголовок:** додає 20 байтів транспортного рівня при встановленому з'єднанні.
4. **TLS 1.3 заголовок і кодування (Record Protocol & MAC):** додає 29 байтів для шифрування та автентифікації пакета.
5. **MQTT 5.0 FIXED/VARIABLE заголовок:** додає 5 байтів (заголовок PUBLISH, ідентифікатор топіка, QoS level).

Розрахуємо підсумковий розмір одного мережевого пакета телеметрії:

```
S_packet
= S_payload + S_mqtt + S_tls + S_tcp + S_ip   [базовий склад пакету]
= 100 + 5 + 29 + 20 + 20                      [підстановка розмірів заголовків]
= 174 байти                                   [загальний розмір пакета телеметрії]
```

Звернувши увагу на співвідношення `S_payload / S_packet = 100 / 174 = 0.574`, ми бачимо, що 42.6% переданого мережевого трафіку становить не корисна інформація, а службові заголовки протоколів.

### Добовий та секундний потік вимірів

При наївній передачі кожної точки (без локального буферування та дельта-фільтрації) добовий обсяг повідомлень від одного будинку обчислюється так:

```
M_daily_home
= N_s · f_s · 86400                           [визначення добової кількості вимірів]
= 20 · (1 / 5) · 86400                        [підстановка: 20 давачів по 1 виміру в 5 сек]
= 4 · 86400                                   [множення частоти на кількість давачів]
= 345,600 повідомлень/день                    [добовий обсяг для одного будинку]
```

Для всієї системи з `N_h = 5,000,000` будинків загальний добовий потік повідомлень дорівнює:

```
M_daily_total
= N_h · M_daily_home                          [множення на кількість будинків у флоті]
= 5,000,000 · 345,600                         [підстановка 5 млн будинків]
= 1,728,000,000,000 повідомлень/день          [сумарний добовий потік 1.728 трлн пакетів]
```

Обчислимо секундний потік інгестії (Ingestion Throughput):

```
R_ingest
= M_daily_total / 86400                       [ділення добового обсягу на секунди доби]
= 1,728,000,000,000 / 86400                   [підстановка 1.728 трлн пакетів]
= 20,000,000 повідомлень/секунду              [інтенсивність вхідного потоку]
```

### Вартість наївної хмарної інгестії (Managed Cloud Ingestion)

Використовуючи тарифну сітку класичного керованого хмарного брокера (AWS IoT Core — $1.00 за 1 мільйон повідомлень інгестії) та тариф гарячої NoSQL бази даних (AWS DynamoDB — $1.25 за 1 мільйон операцій запису WCU):

```
C_ingest_daily
= (M_daily_total / 1000000) · (Price_broker + Price_wcu)  [формула добової вартості]
= 1728000 · ($1.00 + $1.25)                               [підстановка тарифних ставок]
= 1728000 · $2.25                                         [сумування тарифів брокера та бази]
= $3,888,000 / день                                       [добовий рахунок інгестії]
```

```
C_ingest_monthly
= C_ingest_daily · 30                         [множення добових витрат на 30 днів]
= $3,888,000 · 30                             [підстановка добового рахунку]
= $116,640,000 / місяць                       [місячний рахунок інгестії]
```

Ціна обслуговування одного будинку лише за обробку телеметрії складає `$116,640,000 / 5,000,000 = $23.328 / дім / місяць`. Це математичний вирок наївній архітектурі, який доводить абсолютну неможливість побудови бізнесу без попереднього стиснення та обробки потоку.

## 2. Формули Edge-агрегації та коефіцієнт стиснення потоку

Щоб звести unit-cost до цільового показника ($0.01 / дім / місяць), хаб застосовує три етапи зменшення трафіку:

1. **Дельта-фільтрація (Delta-Filtering):** Значення давача відправляється негайно лише тоді, коли абсолютна зміна перевищує поріг `Δ_threshold`. Для 80% давачів (температура, вологість, RSSI) коефіцієнт дублювання значень становить `R_delta = 0.95`.
2. **Локальне батчування (Batching Window):** Незакриті дельти зберігаються в локальній SQLite і відправляються ущільненим батчем кожні `T_batch = 900` секунд (15 хвилин). Коефіцієнт об'єднання `R_batch = 180` вимірів на один MQTT-пакет.
3. **Пріоритетне проходження (Emergency Bypass):** Події безпеки (рух, датчик диму, розмикання дверей) оминають батч і передаються за `0.05` секунди.

Обчислимо новий обсяг повідомлень після Edge-оптимізації:

```
M_optimized_home_daily
= N_s · ( (86400 / T_batch) + N_events_urgent )   [формула батчованого трафіку]
= 20 · ( (86400 / 900) + 10 )                     [підстановка 15-хвилинного вікна]
= 20 · ( 96 + 10 )                                [сума батчів та невідкладних подій]
= 20 · 106                                        [множення на кількість давачів]
= 2,120 повідомлень/день                          [оптимізований обсяг на один дім]
```

Для всієї системи з 5 мільйонів будинків:

```
M_optimized_total_daily
= 5,000,000 · 2,120                           [множення на флот із 5 млн будинків]
= 10,600,000,000 повідомлень/день             [10.6 млрд замість 1.728 трлн пакетів]
```

Обчислимо місячну вартість інгестії для self-hosted кластера EMQX та аналітичного сховища ClickHouse на власних екземплярах EC2 / Bare-Metal:

```
C_infrastructure_monthly
= (N_nodes · Cost_node) + (Bandwidth_GB · Cost_GB)  [формула витрат інфраструктури]
= (48 · $420) + (137000 · $0.01)                    [підстановка 48 нод та трафіку]
= $20,160 + $1,370                                  [сумування compute та мережі]
= $21,530 / місяць                                  [місячна вартість інфраструктури]
```

```
Unit_Cost_telemetry
= C_infrastructure_monthly / N_h              [ділення витрат на флот будинків]
= $21,530 / 5,000,000                         [підстановка 5 млн будинків]
= $0.0043 / дім / місяць                      [unit-cost телеметрії]
```

Завдяки дельта-фільтрації та батчуванню на рівні хаба підсумкові витрати на телеметрію впали з $23.328 до $0.0043 за дім на місяць (скорочення в 5425 разів!).

## 3. Математична модель Cloud Egress для відеопотоків

Відео є найважчим елементом за смугою пропускання. Припустимо, кожна IP-камера генерує потік H.265 із бітрейтом `B_video = 2.0 Mbps` (0.25 MB/s).

Для 5,000,000 будинків із 1 камерою на будинок при наївній хмарній трансляції (Camera -> Cloud Gateway -> User App):

```
V_video_second
= N_h · B_video                               [сумарна секунда смуга відеопотоку]
= 5,000,000 · 2.0 Mbps                        [підстановка 5 млн камери по 2 Mbps]
= 10,000,000 Mbps                             [вхідний потік]
= 10 Tbps                                     [переведення в Терабіти на секунду]
```

Припустимо, користувачі сумарно переглядають live-відео протягом `T_view = 600` секунд на будинок на добу. Добовий хмарний вихідний трафік (Cloud Egress) становить:

```
Egress_daily_GB
= N_h · (B_video / 8) · T_view / 1000000      [формула обсягу вихідного трафіку]
= 5,000,000 · 0.25 · 600 / 1000000            [переведення бітів у мегабайти]
= 750,000,000 / 1000000                       [обчислення загального обсягу в МБ]
= 750,000 GB / день                           [добовий egress в гігабайтах]
```

```
Egress_monthly_PB
= (Egress_daily_GB · 30) / 1000000            [переведення добового egress в петабайти]
= (750,000 · 30) / 1000000                    [підстановка 30 днів місяця]
= 22.5 PB / місяць                            [місячний вихідний трафік]
```

При хмарній ціні Egress `$0.05` за gigabyte (AWS Direct Connect / CloudFront volume tier):

```
C_egress_monthly_naive
= 22500000 · $0.05                            [множення гігабайтів на тариф egress]
= $1,125,000 / місяць                         [місячний рахунок за трафік відео]
```

### Формула WebRTC P2P Direct Offloading

Впровадження WebRTC direct streaming із NAT Traversal (STUN/TURN) змінює напрямок руху байтів:

```
V_clip_size
= 10 · 0.25                                   [множення 10 секунд на 0.25 МБ/с]
= 2.5 MB                                      [розмір одного подієвого кліпу]
```

```
V_clips_monthly_total
= (5000000 · 5 · 2.5 · 30) / 1000             [обчислення обсягу всіх тривожних кліпів]
= 1,875,000 GB / місяць                       [обсяг у гігабайтах на місяць]
```

```
C_video_hybrid_monthly
= (22500000 · 0.04 · $0.05) + (1875000 · $0.007) [сума 4% TURN relay та S3 cold storage]
= $45,000 + $13,125                           [обчислення складових витрат відео]
= $58,125 / місяць                            [підсумкові витрати на відео]
```

```
Unit_Cost_video
= C_video_hybrid_monthly / N_h                [ділення витрат відео на флот]
= $58,125 / 5,000,000                         [підстановка 5 млн будинків]
= $0.0116 / дім / місяць                      [unit-cost відеообслуговування]
```

## 4. Математичний розрахунок перезапуску флоту (Reconnection Storm)

Окремим макроекономічним ризиком є явище блек-ауту, коли після відновлення електропостачання в регіоні 1,000,000 хабів одночасно намагаються відновити TLS-з'єднання з брокером.

Обчислимо обсяг обчислювальних ресурсів, необхідний для обробки рукостискань TLS 1.3:

```
S_handshake
= 1.5 KB                                      [середній розмір даних TLS 1.3 рукостискання]

Data_storm_total
= 1000000 · 1.5 KB                            [підстановка 1 млн хабів]
= 1,500,000 KB                                [сумарний обсяг даних рукостискань]
= 1.5 GB                                      [обсяг трафіку за 30 секунд]
```

Потужність CPU для виконання асиметричної криптографії (Elliptic Curve Diffie-Hellman):

```
CPU_crypto_ops
= 1000000 / 30                                [ділення 1 млн з'єднань на 30-секундне вікно]
= 33,333 handshakes/sec                       [необхідна швидкодія криптографії]
```

Для витримування цієї швидкості без збою брокер повинен підтримувати TLS Session Tickets (RFC 8446), що скорочує CPU-навантаження на рукостискання у 10 разів і захищає хмару від фінансового штрафу за перевищення Compute Quota.

## 5. Підсумкова матриця TCO Digital Homes

Об'єднавши всі розраховані математичні модулі, сформуємо підсумковий баланс витрат платформового сервісу Digital Homes:

```
TCO_total_monthly
= C_ingest + C_storage + C_video_egress + C_video_store + C_ops  [сума всіх статей витрат]
= $21,530 + $8,400 + $45,000 + $13,125 + $15,000                 [підстановка складових]
= $103,055 / місяць                                             [сумарні місячні витрати]
```

```
Unit_TCO
= TCO_total_monthly / N_h                     [ділення сумарних витрат на флот]
= $103,055 / 5,000,000                        [підстановка 5 млн будинків]
= $0.0206 / дім / місяць                      [підсумковий unit-cost платформи]
```

Завдяки математично обґрунтованому зміщенню обчислень на край (Edge NVR + SQLite + WebRTC) вартість обслуговування одного смарт-будинку знизилась із **$24.25/місяць** до **$0.02/місяць**, що гарантує високу маржинальність бізнесу Digital Homes.
