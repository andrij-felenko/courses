# ⚙️ Полювання на IDOR у DH: перебрати, закрити, довести

Ми звели горизонтальну ескалацію до одного пропущеного рядка: сервер підіймає дім за `homeId` із запиту й не питає, чи цей дім належить тому, хто питає. Латка теж на рядок — дописати `belongsTo`. Але рядок, який ти можеш **дописати**, а не **показати в дії**, — це поки що припущення, не факт. «Здається, тепер безпечно» і «доведено, що сусід більше не тече» — різні стани, і відстань між ними закриває не редактор, а **робочий інструмент**.

Тож ця майстерня — окремий шар над інлайн-латкою, і в ній рівно три артефакти, кожен зі своєю роллю. **Харнес** (англ. *harness* — упряж, оснастка) — короткий скрипт, що перебирає чужі доми під нашою сесією й показує витік чорним по білому: доводить, що загроза реальна й **тривіально автоматизується**. **Чек** — той самий рядок авторизації об'єкта, але тепер розібраний по трьох несучих властивостях, кожну з яких легко загубити. **Тест** — той самий перебір, обернений на вартового: він щодня перепитує сервер «а сусід досі закритий?» і **не дає дірці тихо відкритися знову**. Червоне, зелене, і замок, що тримає зелене замкненим.

## Крок 1. Харнес: цікавість стає циклом

Історію про мешканця, що «змінив одну цифру в адресі», легко почути як анекдот про допитливого сусіда. Це самозаспокоєння. Одна змінена цифра — не подія, а **тіло циклу `for`**. Те, що людина робить руками раз, машина робить тисячу разів на секунду, і саме цей перехід від одиничної цікавості до автоматичного перебору перетворює «дрібний баг у списку» на **витік даних цілого кварталу**.

> 🔧 **Навіщо це.** Написати експлойт власноруч — не хизування, а єдиний чесний спосіб дізнатися, наскільки ти вразливий. Абзац у звіті «ендпоінт може віддавати чужі дані» нічого не важить, поки над ним можна відмахнутися: «теоретично». Двадцять рядків, що під сесією тестового акаунта витягують реєстр сусідських пристроїв, знімають слово «теоретично» — і перетворюють дискусію «чи варто цим займатися» на «коли викочуємо латку». Той, хто прийде по цю діру ззовні, напише той самий скрипт; краще, щоб він у вас уже був.

Ідея харнеса гранично проста, і в цій простоті вся суть. Ми беремо **свою власну** сесію — акаунт мешканця #4021, залогінений чесно, без жодного злому автентифікації, — і посилаємо той самий запит `GET /api/homes/{id}/devices` по черзі для `id = 4022, 4023, 4024, …`, тобто для домів, яких ми ніколи не бачили в інтерфейсі. Сесія на кожному запиті **та сама, наша**. Змінюється лише число в адресі. І дивимося, що відповість сервер.

:::tabs
```ts
// idor-sweep.ts — перебір чужих домів під ВЛАСНОЮ сесією мешканця #4021
const BASE = "https://api.dh.example";
const cookie = process.env.DH_SESSION!;      // сесія залогіненого #4021 — його ЧЕСНИЙ вхід

async function probe(homeId: number) {
  const res = await fetch(`${BASE}/api/homes/${homeId}/devices`, {
    headers: { cookie },                      // та сама сесія на КОЖЕН id
  });
  if (res.status !== 200) return { homeId, status: res.status, count: 0 };
  const devices = (await res.json()) as unknown[];
  return { homeId, status: 200, count: devices.length };
}

const mine = 4021;
for (let id = mine + 1; id <= mine + 8; id++) {   // сусіди, яких ми не маємо бачити
  const r = await probe(id);
  const leak = r.status === 200 ? "  ← ВИТІК" : "";
  console.log(`home ${id}: ${r.status}  devices=${r.count}${leak}`);
}
```
```py
# idor_sweep.py — перебір чужих домів під ВЛАСНОЮ сесією мешканця #4021
import os, httpx

BASE = "https://api.dh.example"
cookies = {"session": os.environ["DH_SESSION"]}   # чесний вхід #4021

def probe(client, home_id):
    r = client.get(f"{BASE}/api/homes/{home_id}/devices", cookies=cookies)
    if r.status_code != 200:
        return home_id, r.status_code, 0
    return home_id, 200, len(r.json())            # та сама сесія на КОЖЕН id

with httpx.Client() as client:
    mine = 4021
    for home_id in range(mine + 1, mine + 9):     # сусіди, яких ми не маємо бачити
        hid, status, n = probe(client, home_id)
        leak = "  ← ВИТІК" if status == 200 else ""
        print(f"home {hid}: {status}  devices={n}{leak}")
```
:::

Проти вразливого сервера вивід нещадний:

```
home 4022: 200  devices=7    ← ВИТІК
home 4023: 200  devices=4    ← ВИТІК
home 4024: 404  devices=0
home 4025: 200  devices=12   ← ВИТІК
home 4026: 200  devices=5    ← ВИТІК
home 4027: 404  devices=0
```

Кожен рядок зі `200` — чужий дім, розкритий нам повністю: скільки в ньому пристроїв, а за наступним запитом — які саме, з їхніми іменами, станами замків та історією. `404` тут — не захист, а просто діри в нумерації: домів #4024 і #4027 не існує, тому сервер каже «нема». Він відмовляє нам не тому, що дім чужий, а тому, що дому **немає взагалі** — і ця деталь стане важливою, коли дійдемо до вибору коду відповіді.

![Ліворуч власна сесія мешканця #4021 живить цикл, що перебирає homeId 4022…4030 тим самим запитом; праворуч реєстр відповідей вразливого сервера, де майже кожен рядок — 200 із витоком чужих пристроїв, а поодинокі 404 — лише прогалини нумерації](/root/course/progarch/idor-horizontal-escalation/img/idor-harness-sweep.svg)
*Одна чесно здобута сесія плюс цикл `for` — і реєстр пристроїв цілого кварталу в тебе на екрані. Жодного «злому»: сервер зробив рівно те, що йому сказали, для кожного підставленого id.*

Порахуймо, чому це саме витік, а не курйоз. Вартість такої атаки складається з двох доданків, і обидва мізерні:

```
вартість ≈ 1 сесія (свій-таки акаунт)  +  N запитів
N        = розмір діапазону homeId       (напр. 10 000 сусідів)
за ~50 запитів/с (тихо, не привертаючи уваги)
         → увесь квартал вичитано за ≈ 200 с
```

Три з половиною хвилини, один безкоштовний акаунт, двадцять рядків коду — і зловмисник тримає в руках приватний інвентар десятків тисяч домів. Тут корисно перестати думати про «хакера» як про людину з цікавістю й почати думати про [зловмисника як про силу](root:progarch/attacker-as-force), що автоматично пробує все дешеве: питання вже не «кому спаде на думку перебирати сусідські id?», а «що взагалі дешево спробувати?» — і якщо перебір дешевий, його спробують гарантовано, лишень система стане цікавою. Проєктувати треба проти сили, не проти окремого допитливця.

Варто чесно сказати: цей скрипт — навчальна, зменшена версія того, що в індустрії давно роблять готові інструменти. Розширення **Autorize** для Burp Suite (його написав дослідник безпеки Барак Тавілі) робить рівно наш цикл, тільки автоматично: воно бере трафік залогіненого користувача, **переграє** кожен запит під сесією іншого (менш привілейованого чи взагалі анонімного) акаунта й порівнює відповіді — якщо переграний запит теж вертає `200`, доступ не перевіряється, і це IDOR. Наш харнес — та сама логіка, вручну й на один ендпоінт, щоб було видно **механізм**, а не лише червоний рядок у звіті інструмента.

## Крок 2. Чек: три властивості, кожну легко загубити

Тепер закриваємо. Латка вже відома — запитати модель дому, чи належить він тому, хто прийшов, — але цінність цього кроку не в тому, **що** дописати, а в тому, щоб побачити, з **чого саме** складається правильний чек. Бо він виглядає як один рядок, а насправді тримається на трьох властивостях, і варто впустити будь-яку — діра лишається відчиненою, хоч рядок начебто на місці.

:::tabs
```ts
app.get("/api/homes/:homeId/devices", requireSession, async (req, res) => {
  const home = await homes.byId(req.params.homeId);   // id — з запиту, тобто від КЛІЄНТА
  // Три несучі властивості чека:
  //  1) НА СЕРВЕРІ  — тут, а не в застосунку (саме клієнт і підставляє чужий id);
  //  2) НА КОЖНОМУ доступі — у цьому обробнику, не «десь раніше по дорозі»;
  //  3) ЗА ОСОБОЮ запитувача — ключ = req.session.userId, НЕ id, надісланий клієнтом.
  if (!home || !home.belongsTo(req.session.userId))
    return res.status(404).end();                      // 404, не 403 — про це нижче
  res.json(await devices.ofHome(home.id));
});
```
```py
@app.get("/api/homes/{home_id}/devices")
def list_devices(home_id: str, user: User = Depends(current_user)):
    home = homes.by_id(home_id)                         # id — з URL, тобто від клієнта
    # 1) на сервері; 2) на кожному доступі; 3) ключ = user.id (хто увійшов),
    #    а не home_id (що надіслав клієнт)
    if home is None or not home.belongs_to(user.id):
        raise HTTPException(404)                         # 404, не 403
    return devices.of_home(home.id)
```
:::

Пройдімо ці три властивості не як гасла, а як три **різні способи** написати рядок так, що він виглядатиме правильним і не працюватиме. Це важливо, бо помиляються тут не через лінь, а через правдоподібні напівкроки.

**На сервері, а не в інтерфейсі.** Спокуса «полагодити» на клієнті майже нездоланна: не показуй мешканцю кнопки до чужого дому — і по всьому. Але наш харнес взагалі не відкриває застосунок. Він б'є в API напряму, і будь-яка перевірка, що живе у фронтенді, для нього просто не існує — її код виконується на **його** машині, під **його** контролем, і викидається одним рядком `fetch`. Клієнту не можна вірити з простої причини: клієнт — це і є той, хто підставляє чужий id. Перевірка мусить стояти там, куди зловмисник дотягнутися не може, тобто на сервері.

**На кожному доступі, а не «десь раніше».** Друга правдоподібна помилка — винести чек «нагору», у якийсь спільний шар, що спрацьовує «на вході», і заспокоїтися. Проблема в тому, що об'єкт піднімається **тут**, у цьому обробнику, за id, що прийшов **у цей запит**. Перевірка, зроблена деінде над іншим id чи над самим фактом «сесія дійсна», не звіряє **той** об'єкт, який ми зараз збираємося віддати. Право на об'єкт живе поряд із підняттям об'єкта — між `byId` і `res.json` не має бути щілини, крізь яку проліз би непитаний дім.

**За особою запитувача, а не за id із запиту.** Це найтонше, і найлегше зіпсувати так, що тести на щасливому шляху лишаться зеленими. Уявіть чек, що звіряє власника дому з… `homeId` із запиту, або бере `userId` теж із параметрів. Тоді зловмисник, підставляючи чужий `homeId`, підставить і «правильного» для нього власника — і сам собі видасть дозвіл. Єдиний ключ, якому тут можна вірити, — той, що його встановила автентифікація й клієнт підмінити не може: `req.session.userId`. Питання завжди «чи має право **ТОЙ, ХТО УВІЙШОВ**?», ніколи — «чи збігається те, що клієнт про себе написав, із тим, що клієнт просить».

Саме `belongsTo` перекладає ці три властивості на мову домену. Воно питає модель дому те, що вона й так знає з [нашого доменного розкрою DH](root:progarch/dh-data-model): дім має одного власника й набір **упущених** ним членів родини, і `belongsTo(userId)` істинне, якщо цей `userId` — власник **або** будь-хто з упущених у цей дім. Тобто латка не рубає спільний доступ під корінь: чоловік, дружина, доросла дитина, яких власник свідомо додав, лишаються з доступом; чужий з вулиці — ні. Ця гілка «упущеного члена родини» ще нагадає про себе в тестах — забути її означає полагодити безпеку ціною зламаного сімейного доступу.

## Крок 3. 404 проти 403: не зізнаватися, що об'єкт існує

Один рядок латки ховає рішення, повз яке легко проскочити: **яким кодом** відмовити? Інтуїція підказує `403 Forbidden` — «заборонено», чесна назва для «дім є, але не твій». І саме ця чесність тут шкодить.

Згадаймо, що `403` буквально означає: «ресурс існує, доступ заборонено». Тобто відповідь `403` на `homes/4088/devices` **підтверджує**, що дім #4088 існує — просто він не наш. А `404` не зізнається ні в чому: «нема такого, і крапка». Різниця здається косметичною, поки не згадати наш харнес. Для перебирача відповідь сервера — це **сигнал**, і `403` перетворює сервер на **оракула існування**: пройдися перебором, і всі `403` складуться в точну карту того, які доми реальні, а `404` покажуть прогалини. Зловмисник не прочитав вмісту — але вже знає межі й щільність забудови, а це половина розвідки. `404` цю карту стирає: чужий-але-існує й чужого-нема-зовсім дають **однакову** відповідь, і відрізнити їх зовні неможливо.

![Таблиця відповідей на чотири класи проб. У стовпці «403 наївно» рядок «чужий, існує» світиться червоним маяком — 403 підтверджує, що дім є; у стовпці «404 правильно» той самий рядок дає 404, зливаючись із «чужого нема зовсім». Власний дім в обох стовпцях 200, власного-нема — 404](/root/course/progarch/idor-horizontal-escalation/img/idor-404-oracle.svg)
*403 на «чужий, існує» — маяк, що видає реальні доми. 404 зливає «чужий існує» і «чужого нема» в одну відповідь, і оракул згасає. Власнику ж, як і раніше, 200.*

Тут ховається пастка, суворіша за сам вибір коду: **послідовність**. Якщо неіснуючий дім дає `404`, а чужий-але-існуючий — `403`, то ти повернувся туди, звідки тікав: **сама різниця** між `403` і `404` знову стала оракулом. Тому правило не «вертай 404 замість 403», а «вертай **одне й те саме** на «нема» і на «не твоє»» — щоб ці два стани були зовні нерозрізненні. У коді це природно: та сама гілка `if (!home || !home.belongsTo(userId)) return 404` навмисне склеює «дому нема» й «дім не твій» в одну відповідь.

І оракул тече не лише кодом статусу. Якщо тіло `404` для чужого дому важче, ніж для неіснуючого; якщо відповідь на реальний-але-чужий приходить на 30 мілісекунд повільніше (бо сервер устиг сходити в базу, підняти дім і аж тоді відмовити); якщо той самий id зринає у якомусь іншому, менш пильному ендпоінті — існування протече цими щілинами. Ідеал недосяжний дешево, але напрям ясний: **дві заборони мають бути схожі як близнюки** — однаковий код, однакове за формою тіло, по змозі близький час. Інакше нерозрізненність, заради якої ми обрали `404`, розчиниться в дрібних відмінностях.

Чесно скажемо і про ціну: `404` замість `403` — це **оборона в глибину**, не сама латка. Він піднімає поріг розвідки, ускладнює життя перебирачу — але дім тримає закритим не він, а `belongsTo` перед ним. Якби чек було впущено, найввічливіший `404` не завадив би віддати чужі пристрої: сервер сказав би «нема» тим, кому не можна, і `200` з повним вмістом — усім підряд. Спершу чек, і лише **тоді** — акуратний код відмови поверх нього.

## Крок 4. Тест: перебір, обернений на вартового

Лишився третій артефакт, і він найважливіший, бо перетворює разову перемогу на тривалу. Латка, яку ніхто не стереже, живе рівно до наступного рефакторингу: хтось перепише обробник, згорне `belongsTo` у ширший метод, «спростить» — і діра тихо відкриється знову, а щасливий шлях лишиться зеленим, бо його ніхто й не думав ламати. Тому останній крок — обернути наш харнес на **автоматичний тест**, який щоразу перепитує сервер те саме, що перебирач питав зі зла: «а сусід досі закритий?».

:::tabs
```ts
// idor.access.test.ts — той самий перебір, тепер як регресійний вартовий
import { describe, it, expect, beforeAll } from "vitest";
import request from "supertest";
import { app } from "../app";

let cookie4021: string;      // сесія мешканця #4021
const OWN      = 4021;       // дім, що НАЛЕЖИТЬ #4021
const NEIGHBOR = 4022;       // дім сусіда — ІСНУЄ, але чужий
```

Проти полагодженого сервера все зелене; поверни стару латку — і три негативні перевірки спалахнуть червоним, назвавши поіменно кожен id, що знову потік.

Тепер — головне спостереження цієї майстерні, заради якого варто було писати всі три артефакти. Придивіться, який тест **ловить** діру, а який — ні. Перевірка «власний дім → 200» **зелена й на вразливому сервері, і на полагодженому** — вона не бачить дірки в принципі, бо ходить лише щасливим шляхом. Спіймати IDOR може **тільки негативна** проба: «чужий-але-існуючий → 404». І ось збіг, який насправді не збіг: **пропущений тест має точнісінько ту саму форму, що пропущений чек**. Обидва зелені на щасливому шляху, обидва мовчать про сусіда, обидва впускають діру в продакшен. Дірка народжується з пропущеного питання «а дім твій?» — і доживає до продакшену через пропущене питання «а що буде з **чужим** домом?».

*Пропущений тест — дзеркало пропущеного чека: обидва зелені на щасливому шляху, обидва лишають двері прочиненими. Латка й вартовий закривають діру в парі: чек не пускає сусіда, тест стереже, що чек не зникне.*

Звідси й вимога до тесту, а не лише до коду: він мусить перевіряти **поведінку під особою запитувача**, і саме в негативі. «Ендпоінт вертає 200 власнику» — необхідно, але дірку не ловить; несуча перевірка — «ендпоінт вертає **404 не-власнику на реальний чужий дім**». Тому в тесті стоїть окремий `NEIGHBOR`, і це не будь-який id: він має бути **чужим, але справді існуючим**. Тест на 404 для `999999` доводить лише, що сервер уміє казати «нема такого». А ось `404` для #4022, який реально належить сусідові, доводить те, що нам потрібно: систему не можна змусити **відрізнити** «не твоє» від «не існує». Забудеш посадити в базу справжній чужий дім — і твій зелений тест насправді нічого не стереже.

## Складність і пастки: одна латка — ще не квартал

Три артефакти закрили **один** обробник. Спокуса поставити крапку велика — і хибна, бо справжня складність IDOR не в тому, як залатати ендпоінт, а в тому, що обробників, які торкаються об'єктів із власником, у зрілій DH **сотні**: пристрої, кімнати, сцени, записи камер, запрошення, рахунки. Один забутий серед них — і квартал знову тече. Полагоджений device-API — це доказ концепції латки, не кінець роботи; далі йдуть пастки, на яких ця латка ламається або тихо не спрацьовує.

**Вкладеність об'єктів — авторизуй лист, а не предка.** Візьмімо ендпоінт на один рівень глибше: `GET /api/homes/:homeId/devices/:deviceId`. Природно перевірити, що `homeId` наш, і на цьому заспокоїтися. Пастка в тому, що `deviceId` теж прийшов від клієнта — і ніщо не заважає попросити `/homes/<мій>/devices/<чужий>`. Якщо чек звіряє лише дім, зловмисник підставляє свій дім у шлях і чужий пристрій у хвіст — і читає його:

:::tabs
```ts
app.get("/api/homes/:homeId/devices/:deviceId", requireSession, async (req, res) => {
  const home = await homes.byId(req.params.homeId);
  if (!home || !home.belongsTo(req.session.userId))
    return res.status(404).end();
  const device = await devices.byId(req.params.deviceId);
  // Мало, що дім наш: пристрій має належати САМЕ цьому дому. Інакше
  // /homes/<мій>/devices/<чужий> пройде — власність перевірено не на тому об'єкті.
  if (!device || device.homeId !== home.id)
    return res.status(404).end();
  res.json(device);
});
```
```py
@app.get("/api/homes/{home_id}/devices/{device_id}")
def get_device(home_id: str, device_id: str, user: User = Depends(current_user)):
    home = homes.by_id(home_id)
    if home is None or not home.belongs_to(user.id):
        raise HTTPException(404)
    device = devices.by_id(device_id)
    # пристрій мусить належати саме цьому дому, а не будь-якому нашому
    if device is None or device.home_id != home.id:
        raise HTTPException(404)
    return device
```
:::

Правило під цією пасткою: перевіряй право на **той самий об'єкт**, який зрештою віддаєш, — на лист дерева, а не на його зручного предка. Кожен клієнтський id у шляху — окремий вхід, який хтось спробує підставити.

**Списки й фільтри — звужуй запит, а не фільтруй після.** Друга форма тієї самої діри носить іншу одежу: `GET /api/devices?homeId=4088`. Тут спокуса — дістати все й відфільтрувати в застосунку. Це погано двічі: обробник усе одно **підняв** чужі дані (а отже, міг їх десь випадково лишити — у логах, у метриках, у наступному рядку коду), і фільтр легко забути. Правильна форма — **звузити сам запит особою** запитувача, щоб чужого просто не існувало в результаті:

:::tabs
```ts
// Погано: дістати все, тоді відсіяти — сервер уже «бачив» чуже, і фільтр легко впустити
const all = await devices.all();
return res.json(all.filter(d => d.ownerId === req.session.userId));

// Добре: одразу звузити запит особою — чужого немає в наборі за побудовою
return res.json(await devices.ofOwner(req.session.userId));
```
```py
# Погано: дістати все, тоді відсіяти
all_devices = devices.all()
return [d for d in all_devices if d.owner_id == user.id]

# Добре: звузити запит особою — чужого немає в наборі за побудовою
return devices.of_owner(user.id)
```
:::

Це різниця між «пустити всіх у сховище й попросити брати лише своє» і «видавати кожному лише його полицю». Друге не покладається на дисципліну — воно **структурно** не має чужого на виході.

**Не вір ownerId на запис.** Дзеркало IDOR на боці записування — клієнт, що сам присилає `ownerId` чи `homeId` у тілі `POST`/`PATCH`, розраховуючи приписати об'єкт собі або підмінити власника. Власника нового об'єкта завжди бери з `req.session.userId`, а не з тіла запиту; поле власника в тілі — ігноруй або відхиляй. Та сама несуча властивість — **ключ від того, хто увійшов, не від того, що клієнт написав**, — тільки на іншому дієслові.

**Тестові дані — це половина тесту.** Вартовий надійний рівно настільки, наскільки чесна база під ним. Йому потрібні щонайменше **два справжні орендарі** (щоб #4021 володів одними домами, а хтось — сусідніми, реально існуючими), і окремо — **упущений член родини** #4021 у дім `SHARED`. Пропустиш гілку «упущеного» — і одного дня хтось «посилить» `belongsTo` до самого лише власника, зламає сімейний доступ, а тест цього не помітить, бо такого випадку в ньому немає. Негативні проби мусять бити в **реальні чужі** доми, позитивні — покривати **обидві** законні гілки (власник і впущений). Тест перевіряє не абстрактну ідею, а конкретну поведінку на конкретних даних — і прогалина в даних стає прогалиною в охороні.

І остання, найбільша пастка — думати, що всі ці чеки можна щоразу **пам'ятати** дописувати. Не можна; люди забувають надійно, надто коли щасливий шлях і без чека сяє зеленим. Тому справжня відповідь лежить не в старанності, а в архітектурі: конвеєр запиту має бути влаштований так, щоб доступ **не надавався**, доки щось явно його не дозволило, а забута перевірка **падала в замкнене**, не тихо пропускала. Це принцип [найменших привілеїв і відмови за замовчуванням](book:programming/least-privilege): типова відповідь системи — «ні», доступ відкриває лише явний дозвіл, і пропуск означає заборону, а не діру. Наш харнес, чек і тест — інструменти, якими ловлять і закривають **окремий** пролом; але щоб проломів не було **конструктивно**, чек мусить жити там, де його неможливо забути. Куди саме його покласти — у кожен обробник, у спільний бар'єр чи в поєднання обох — це вже не полювання, а вибір форми авторизації, і його ця майстерня передає далі, вклавши в руки головне: перевірка на сервері, на кожному доступі, за особою запитувача, з відмовою за замовчуванням, і вартовий-тест, що не дає цій перевірці зникнути.
