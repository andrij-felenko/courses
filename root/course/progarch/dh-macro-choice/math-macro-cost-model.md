# 🧮 Математична модель операційних витрат та затримок: Моноліт проти Мікросервісів для DH

Цей математичний аналіз виводить квантитативні моделі мережевих затримок, обчислювального податку серіалізації даних, витрат на хмарну інфраструктуру та когнітивного навантаження інженерної команди. Модель створено для точного кількісного порівняння Модульного моноліту та Мікросервісної архітектури на конкретних параметрах системи Digital Homes.

Математичне моделювання дозволяє усунути суб'єктивні спори про «кращу архітектуру» та перевести вибір у площину об'єктивних розрахунків часу виконання, використання системних ресурсів процесора та фінансових витрат.

---

## 1. Вхідні параметри та масштаби системи Digital Homes (v3)

Для проведення точних обчислень зафіксуємо реальні фізичні та продуктові параметри системи Digital Homes на поточній стадії еволюції:

- **Кількість активних хабів у домогосподарствах (`N_hubs`):** `50 000` одиниць.
- **Загальна кількість підключених пристроїв (`N_devices`):** `500 000` одиниць (давачі, актуатори, камери).
- **Пікова інтенсивність користувацьких API-запитів (`R_api`):** `1 500 req/sec`.
- **Потік інжесту телеметрії та оновлення станів (`R_telem`):** `10 000 events/sec`.
- **Розмір інженерної backend-команди (`Team`):** `6 осіб`.

## 2. Математична модель накопичення затримок та ампліфікації tails (p99)

Порівняємо фізичну затримку виконання міжмодульної взаємодії у двох макроархітектурних варіантах.

### 2.1. Фізичні часові константи виклику

У **Модульному моноліті** виклик методу іншого модуля зводиться до передачі покажчика в пам'яті одного процесу:
```
t_in_memory = 20..50 ns  (0.00002..0.00005 ms)
```

У **Мікросервісній архітектурі** аналогічний виклик здійснюється по мережі (gRPC / HTTP/2 + TLS) через системні виклики ядра, TCP/IP-стек та мережевий комутатор:
```
t_network = 3.5 ms  (за умови розміщення сервісів у межах однієї хмарної зони AZ)
```

Отже, один мережевий виклик між сервісами коштує у **70 000 — 100 000 разів дорожче** за часом виконання, ніж виклик функції у пам'яті.

### 2.2. Модель ампліфікації хвостових затримок (Tail Latency Amplification)

Розглянемо типовий сквозний сценарій реагування на спрацювання давача протікання води у Digital Homes:
`SensorIngest` → `DeviceRegistry` (перевірка стану) → `AutomationEngine` (обчислення правил) → `UserIdentity` (перевірка прав) → `NotificationService` (відправка пуш-сповіщення).

Ланцюжок викликів має глибину `k = 5` послідовних викликів.

Припустимо, кожен поодинокий мікросервіс працює з високою надійністю і має ймовірність поодинокого мережевого занепаду чи затримки `p = 0.02` (тобто 98% запитів виконуються за норму, але 2% зазнають хвостової затримки `t_tail = 150 ms` через GC, переповтори або затримки сокетів).

Ймовірність `P_ok`, що підсумковий сценарій з `k` викликів пройдуть **БЕЗ жодної затримки** на всьому шляху, обчислюється як добуток ймовірностей успіху на кожному кроці:

```
P_ok = (1 - p)ᵏ
P_ok = (1 - 0.02)⁵ = (0.98)⁵ ≈ 0.9039  (90.39%)
```

Відповідно, ймовірність `P_tail_total`, що користувач відчує важку хвостову затримку всього сценарію:

```
P_tail_total = 1 - P_ok
P_tail_total = 1 - 0.9039 = 0.0961  (9.61%)
```

```
Ймовірність хвостової затримки (P_tail_total) залежно від глибини ланцюжка k:
k = 1  (Моноліт):      P_tail = 1 - (0.98)¹ = 2.00%
k = 3  мікросервіси:   P_tail = 1 - (0.98)³ = 5.88%
k = 5  мікросервісів:  P_tail = 1 - (0.98)⁵ = 9.61%
k = 10 мікросервісів: P_tail = 1 - (0.98)¹⁰ = 18.29%
```

**Висновок за затримками:** У мікросервісній системі з глибиною у 5 викликів майже **кожен десятий запит** користувача зазнає важкої затримки (>200 мс). У Модульному моноліті `k` викликів відбуваються у пам'яті за сумарні `< 1 мкс`, тому мережева ампліфікація затримок дорівнює нулю.

## 3. Процесорний податок серіалізації (CPU Serialization Tax)

При кожному міжмережевому виклику об'єкти мови програмування повинні перетворюватися у байтовий потік (JSON або Protobuf) для передачі сокетом, а на стороні отримувача — десеріалізуватися назад.

Нехай середній розмір об'єкта стану пристрою складає `S = 2 KB`.
Витрати CPU на серіалізацію, десеріалізацію та TLS-шифрування на 1 KB даних складають приблизно `C_ser = 1.2 мкс` процесорного часу сучасного ядра.

Для навантаження інжесту телеметрії `R_telem = 10 000 events/sec`, де кожна подія у мікросервісах проходить крізь 3 сервіси (Інжест → Правила → Сховище):

```
Кількість операцій серіалізації/десеріалізації на секунду:
N_op = 10 000 events/sec × 3 сервіси × 2 (пари encode/decode) = 60 000 op/sec

Сумарний витрачений процесорний час CPU на секунду:
T_cpu = 60 000 op/sec × (2 KB × 1.2 мкс) = 144 000 мкс/sec = 0.144 CPU cores
```

При використанні текстового JSON (де витрати в 4–5 разів вищі за бінарний Protobuf), податок серіалізації з'їдає **понад 1.5 повних ядер CPU** виключно на марні обчислення перекладання байтів. У Модульному моноліті ці об'єкти передаються за zero-copy посиланнями у пам'яті з нульовим витрачанням CPU.

## 4. Фінансова модель витрат на хмару (AWS Egress & Infrastructure Tax)

Обчислимо щомісячні фінансові витрати на інфраструктуру у хмарі AWS для двох макроархітектурних моделей при обслуговуванні 50 000 хабів.

### 4.1. Варіант А: Модульний моноліт (`cloud-core`)

- **Обчислювальні вузли:** 3 екземпляри `c6i.xlarge` (4 vCPU, 8 GB RAM) для забезпечення відмовостійкості (HA):  
  `3 × $122.64/міс = $367.92`
- **База даних:** Primary + Standby Managed PostgreSQL (`db.m6g.xlarge`):  
  `$450.00/міс`
- **Міжмодульний мережевий трафік:** Здійснюється в пам'яті одного процесу:  
  `$0.00`
- **Всього за місяць:** **`$817.92 / місяць`**

### 4.2. Варіант Б: 12 Мікросервісів у кластері Kubernetes (EKS)

- **Плата за плагін EKS Control Plane:**  
  `$73.00/міс`
- **Обчислювальні вузли:** 12 мікросервісів × 2 репліки = 24 контейнери. Через оверхед системних процесів кожної ноди (Kubelet, proxy, Istio sidecars) потрібно 6 вузлів `c6i.xlarge`:  
  `6 × $122.64 = $735.84/міс`
- **Бази даних:** 12 логічних RDS-екземплярів або розгалужений кластер під концепцію Database per Service:  
  `$1 250.00/міс`
- **Cross-AZ Network Egress (Міжзонний трафік):**  
  При 10 000 events/sec і розмірі об'єкта 2 KB міжсервісний трафік у кластері створює:  
  `10 000 events/sec × 2 KB × 3 сервіси = 60 MB/sec = 155.5 TB / місяць`.  
  У хмарі AWS міжзонний трафік (Cross-Availability Zone Egress) коштує `$0.01 / GB` в один бік (`$0.02 / GB` round-trip).  
  З урахуванням того, що приблизно 66% трафіку перетинає межі зон:  
  `Egress_Cost = 155 500 GB × 0.66 × $0.02 = $2 052.60 / місяць`
- **Всього за місяць:** **`$4 111.44 / місяць`**

**Підсумкове фінансове порівняння:**  
Модульний моноліт забезпечує **понад 5-разову економію ($817.92 проти $4 111.44 на місяць)** на хмарній інфраструктурі при абсолютно однаковому корисному обсязі виконаної бізнес-логіки.

## 5. Модель інженерного когнітивного навантаження (Cognitive Load Index)

Сформулюємо інтегральний показник когнітивного навантаження `CLI` (Cognitive Load Index) для команди з `Team = 6` backend-розробників як функцію від кількості репозиторіїв `R`, CI/CD-пайплайнів `P` та міжсервісних мережевих меж `B`:

```
CLI = R × 1.5 + P × 2.0 + B × 3.5
```

- **Значення для Модульного моноліту (1 репо, 1 CI/CD-пайплайн, 0 міжмережевих меж):**
  ```
  CLI_mono = 1 × 1.5 + 1 × 2.0 + 0 × 3.5 = 3.5
  ```

- **Значення для 12 Мікросервісів (12 репо, 12 CI/CD-пайплайнів, 15 меж між сервісами):**
  ```
  CLI_micro = 12 × 1.5 + 12 × 2.0 + 15 × 3.5 = 18.0 + 24.0 + 52.5 = 94.5
  ```

Показник `CLI = 94.5` для команди з 6 осіб сигналізує про те, що кожен інженер змушений витрачати понад **40% свого робочого часу** на супровід міжсервісної інфраструктури (синхронізація PR між репозиторіями, налаштування таймаутів, зведення трасувань у Jaeger) замість написання функціональності продукту Digital Homes.
