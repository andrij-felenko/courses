# 🔌 Специфікація бізнес-контексту та матриці корисності OmniPay

Ця вставка містить формалізовану специфікацію бізнес-контексту, тарифних планів, системних обмежень та повне дерево корисності (Utility Tree) мультирегіональної платіжної платформи OmniPay Global, на яку спирається наскрізний капстон-проєкт. Ознайомлення з цією специфікацією необхідне для розуміння математичних та організаційних межових умов, у яких ухвалюються всі подальші архітектурні рішення.

## 1. Специфікація продуктів та тарифних рівнів (Tenant Tiers)

Платформа OmniPay обробляє платежі та транзакційні розрахунки для B2B-клієнтів (торговців, платіжних агрегаторів та глобальних маркетплейсів). Усі клієнти платформи розділені на три тарифні рівні (Tenant Tiers). Кожен рівень накладає суворі обмеження на час доступності, затримки, гарантії консистентності даних та рівень ізоляції обчислювальних ресурсів:

| Параметр | Enterprise Tier | Standard Tier | Self-Service Tier |
| :--- | :--- | :--- | :--- |
| **Частка транзакційного обсягу** | 40% загального обсягу | 45% загального обсягу | 15% загального обсягу |
| **Гарантія SLA (Uptime)** | 99.99% (≤ 52.56 хв/рік) | 99.9% (≤ 8.76 год/рік) | 99.0% (Best Effort) |
| **Бюджет затримки (p99)** | ≤ 150 мс у межах регіону | ≤ 300 мс у межах регіону | ≤ 1000 мс у межах регіону |
| **Гарантія консистентності** | Strong (RPO = 0, RTO < 30с) | Strong (RPO = 0, RTO < 5хв) | Eventual (RPO < 60с) |
| **Ізоляція обчислювальних ресурсів** | Dedicated Cell / DB Schema | Shared Cluster (Pool) | Multi-tenant Shared |
| **Особливості білінгу та обмежень** | Індивідуальні ліміти & SLAs | Стандартні квоти | Жорсткий Rate Limit |

### Детальний опис тарифних моделей та механізмів ізоляції

1. **Enterprise Tier (Преміальний рівень):** Призначений для великих міжнародних маркетплейсів та авіакомпаній, які генерують мільйонні транзакції щодня. Для цих клієнтів простій системи вимірюється сотнями тисяч доларів втрат за хвилину. Архітектура вимагає виділених комірок (Dedicated Cells) або ізольованих схем у базах даних, гарантуючи, що сплеск навантаження у сусіда ніколи не вплине на обробку платежів Enterprise-клієнта. Затримка обробки (p99) не повинна перевищувати 150 мс у межах одного хмарного регіону.
2. **Standard Tier (Стандартний рівень):** Обслуговує середній B2B-бізнес та регіональні інтернет-магазини. Клієнти ділять між собою спільні пули мікросервісів та кластери баз даних (Shared Pool), але ізолюються на рівні ідентифікаторів орендаря (`Tenant-ID`). Гарантія доступності становить 99.9%, а бюджет затримки обмежений 300 мс.
3. **Self-Service Tier (Базовий рівень):** Призначений для малого бізнесу та стартапів з безкоштовним або дешевим входом. Обслуговується за принципом Best Effort у спільній багатоорендній інфраструктурі. Під час екстремальних піків навантаження (наприклад, Black Friday) трафік Self-Service клієнтів першим підпадає під адаптивне скидання (Load Shedding) для збереження доступності вищих рівнів.

## 2. Нормативні обмеження та суверенітет даних (Data Sovereignty)

Платформа працює у трьох міжнародних регуляторних юрисдикціях. Первинні обмеження вимагають категоричного поділу даних та заборони неконтрольованого крос-регіонального трафіку:

```text
[Зона EU (Frankfurt)] ── (GDPR) ──> Заборона експорту необроблених PII за межі ЄС
[Зона US (Virginia)]  ── (CCPA / PCI-DSS L1) ──> Ізольований Token Vault для карток
[Зона APAC (Singapore)] ── (PDPA) ──> Локальне зберігання журналу транзакцій
```

### Деталізація правових режимів та архітектурні наслідки

1. **Персональні дані (PII та GDPR у ЄС):** Відповідно до Загального регламенту про захист даних (GDPR, Статті 44–49), персональні дані громадян ЄС (імена, поштові адреси, номери телефонів, IP-адреси) не можуть передаватися до серверів у США чи Азії без спеціальних правових угод або незворотної псевдонімізації. Архітектурне наслідок: сервіси профілів клієнтів та БД персональних даних розгортаються строго у регіоні EU-Central (Франкфурт). Крос-регіональна реплікація дозволена лише у вигляді криптографічних анонімних хешів.
2. **Карткові дані та стандарт PCI-DSS Level 1 (США):** Обробка номерів платіжних карток (PAN) та CVV-кодів вимагає щорічного аудиту безпеки PCI-DSS Level 1. Щоб зменшити контур аудиту (PCI Scope) та уникнути сертифікації сотень мікросервісів, створюється єдине ізольоване сховище токенів (Token Vault) у зоні US-Virginia. Усі інші мікросервіси платформи працюють виключно з знеособленими токенами (`tok_live_99a8f...`), які не є платіжними даними.
3. **Азіатсько-Тихоокеанський суверенітет (PDPA у Сінгапурі):** Закон про захист персональних даних Сінгапуру (PDPA) та вимоги місцевих регуляторів вимагають зберігання первинного фінансового журналу локальних транзакцій у межах національних дата-центрів. Спроба централізувати всі проводки у єдиному дата-центрі США призводить до відкликання ліцензії еквайрингу в Азії.
4. **Фінансовий журнал (Ledger) та гарантія RPO = 0:** Кожна проводка грошей є транзакцією append-only з подвійним записом (Double-Entry Bookkeeping). Кожен запис містить дебет, кредит, валюту та криптографічний підпис попереднього стану. Втрата навіть одного запису журналу є неприпустимою (`RPO = 0`), що вимагає використання синхронного запису у транзакційний лог (Write-Ahead Log, WAL) до повернення відповіді клієнту.

## 3. Повне дерево корисності (Utility Tree)

Дерево корисності агрегує бізнес-цілі платформи, розгортаючи їх у конкретні вимірювані сценарії якості, зважені за шкалою `(Важливість для бізнесу, Архітектурний ризик)`:

### Розділ 1. Доступність та Стійкість (Availability & Resilience)

- **[H, H] Сценарій А1: Повне виведення з ладу хмарного регіону (Region Outage).**
  - *Джерело:* Аварія у дата-центрі хмарного провайдера (наприклад, вимкнення живлення в US-East).
  - *Стимул:* Втрата зв'язку з 100% вузлів у регіоні US-East під час активної торгівлі.
  - *Середовище:* Продакшн під нормальним навантаженням (10 000 RPS).
  - *Артефакт:* Edge-маршрутизатор, DNS-перемикач, міжрегіональний синхронізатор стану.
  - *Відповідь:* Автоматичне перенаправлення трафіку на резервний регіон EU-Central за ≤ 30 секунд.
  - *Міра відповіді:* Для Enterprise Tier втрата транзакцій RPO = 0, час відновлення послуги RTO < 30 секунд. Для Standard Tier RTO < 5 хвилин.

- **[H, M] Сценарій А2: Збій банку-еквайєра під час авторизації платежу.**
  - *Джерело:* Зовнішній банк-партнер відмовляє у прийомі запитів (HTTP 500 / Timeout).
  - *Стимул:* Таймаут відповіді > 2000 мс від первинного еквайєра.
  - *Середовище:* Онлайн-чекаут покупця.
  - *Артефакт:* Сервіс каскадного роутингу (Smart Routing Adapter).
  - *Відповідь:* Автоматичний переключення запиту на вторинний банк-еквайєр у межах того ж регіону.
  - *Міра відповіді:* Загальний час успішного проведення транзакції не перевищує 2.5 секунди, покупець не бачить помилки.

### Розділ 2. Продуктивність та Масштабованість (Performance & Scale)

- **[H, H] Сценарій П1: Пікова Чорна П'ятниця (сплеск навантаження 50,000 RPS).**
  - *Джерело:* Одночасний початок промо-акцій у 10 000 маркетплейсів.
  - *Стимул:* Вхідний трафік зростає з 2 000 до 50 000 RPS за 30 секунд.
  - *Середовище:* Продакшн під час пікового навантаження.
  - *Артефакт:* Ingress Gateway, дроселі навантаження (Rate Limiters), пули обробки.
  - *Відповідь:* Система зберігає латентність p99 < 250 мс для Enterprise та Standard клієнтів. При перевищенні абсолютного ліміту обчислень вмикається пропорційне скидання навантаження (Load Shedding) для Self-Service Tier.
  - *Міра відповіді:* 0% помилок для Enterprise Tier, деградація затримки не перевищує 20%.

- **[M, H] Сценарій П2: Генерація щомісячного звіту балансу для клієнта з 10 млн транзакцій.**
  - *Джерело:* Бухгалтерія Enterprise-орендаря запитує виписку за місяць.
  - *Стимул:* Важкий аналітичний SQL-запит із агрегацією мільйонів рядків.
  - *Середовище:* Онлайн-система під час робочого дня.
  - *Артефакт:* Аналітичне сховище (Read-Model / Data Lake).
  - *Відповідь:* Запит спрямовується на неблокуючу матеріалізовану репліку, не чіпаючи OLTP-базу авторизацій.
  - *Міра відповіді:* Час виконання виписки ≤ 1.5 секунди, 0 мс впливу на затримку транзакцій онлайн-чекауту.

### Розділ 3. Змінюваність та Екосистема (Modifiability & Ecosystem)

- **[M, M] Сценарій З1: Підключення нового локального платіжного методу (наприклад, Pix або iDEAL).**
  - *Джерело:* Продукт розширюється на ринок Латинської Америки.
  - *Стимул:* Вимога додати специфічний API-протокол еквайрингу Pix.
  - *Середовище:* Процес розробки нового релізу.
  - *Артефакт:* Шар адаптерів еквайрингу (Payment Adapters).
  - *Відповідь:* Нова інтеграція реалізується як ізольований плагін за інтерфейсом `PaymentGatewayPort` без внесення змін у транзакційне ядро Ledger.
  - *Міра відповіді:* Трудомісткість реалізації ≤ 3 людино-днів, 0 змін у коді леджера.

- **[H, M] Сценарій З2: Міграція схем баз даних без зупинки платформи (Zero-Downtime Schema Evolution).**
  - *Джерело:* Команда розробників додає нові поля у структуру транзакційного журналу.
  - *Стимул:* Викатка нової версії сервісу білінгу.
  - *Середовище:* Цілодобовий продакшн-потік.
  - *Артефакт:* Схема PostgreSQL / Cassandra та DTO контракти.
  - *Відповідь:* Застосування трьохфазного патерну Expand-Contract (додавання поля -> подвійний запис -> видалення старого поля).
  - *Міра відповіді:* 0 секунд простою платформи, 100% зворотної сумісності для старих версій сервісів.

### Розділ 4. Безпека та Аудит (Security & Compliance)

- **[H, H] Сценарій Б1: Спроба витоку бази даних PII або карткових даних атакувальником.**
  - *Джерело:* Зловмисник отримує доступ до дампа дискового накопичувача в хмарі.
  - *Стимул:* Читання сирих блоків даних бази даних.
  - *Середовище:* Компрометація дискового сховища.
  - *Артефакт:* Шар шифрування (Envelope Encryption / HSM).
  - *Відповідь:* Усі дані на диску зашифровані ключами AES-256-GCM. Ключі шифрування зберігаються у криптографічному модулі HSM.
  - *Міра відповіді:* Атакувальник отримує лише нечитабельний зашифрований текст (ciphertext), 0 деанонімізованих карт чи PII.

- **[H, M] Сценарій Б2: Незалежний аудиторський аналіз фінансових проводок (Financial Auditability).**
  - *Джерело:* Фінансовий регулятор або зовнішній аудитор перевіряє баланси.
  - *Стимул:* Запит на підтвердження відсутності несанкціонованих ручних правок балансу.
  - *Середовище:* Аудиторська перевірка.
  - *Артефакт:* Транзакційний журнал (Append-only Ledger).
  - *Відповідь:* Кожен запис у журналі підписується хеш-ланцюжком (Cryptographic Ledger Chain). Спроба змінити минулий запис робить весь наступний ланцюжок невалідним.
  - *Міра відповіді:* 100% математична доведеність цілісності журналу, 0 можливостей непомітного коригування.

Ця формалізована специфікація виступає нормативним стандартом для ухвалення всіх подальших архітектурних рішень та формування записів ADR у межах капстону.
