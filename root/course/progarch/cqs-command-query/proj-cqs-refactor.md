# ⚙️ Проєкт: рефакторинг до CQS і три чесні винятки

У Digital Homes є сервіс рахунків, що приймає показники лічильників. Кожен розумний лічильник раз на хвилину шле споживання, застосунок кличе `record(...)`, а на дашборді поруч світиться поточний рахунок за місяць. Хтось колись написав `record` так, щоб він одразу й повертав цей рахунок — «зручно, усе за один виклик»:

```ts
// ЗАПАХ: І дописує показник, І повертає свіжий рахунок
record(deviceId: string, kWh: number): Money {
  const list = this.readings.get(deviceId) ?? [];
  list.push(kWh);
  this.readings.set(deviceId, list);
  const total = list.reduce((a, b) => a + b, 0);
  return Math.round(total * this.tariff) + this.standing;   // похідне від НОВОГО стану
}
```

Метод зветься `record` — це наказ, — а `: Money` наприкінці робить його ще й запитом. Наслідки не косметичні, а конкретні. Хочеш просто записати показник фонового лічильника, який ніхто не дивиться, — усе одно щоразу перераховуєш рахунок і викидаєш його. Хочеш показати рахунок на дашборді, не додаючи показника, — не можеш, бо єдина дорога до суми лежить через запис у стан. А коли треба перевірити, що арифметика рахунку правильна, тест мусить дописати показник — тобто **зіпсувати журнал**, щоб дізнатися відповідь. Три різні болі з одного кореня: метод змішав дію й відповідь.

Задача цього розбору вузька й практична: узяти цей метод, розсікти його на команду й запит, показати тести до і після — а тоді чесно пройти три місця, де такий різ робити **не треба**, і кожне розібрати робочим кодом.

## Ідея різу: команда пише, запит рахує

Похідне значення тут — рахунок — це **чиста функція від збереженого стану**: маєш перелік показників пристрою, помножив суму на тариф, додав абонплату, дістав рахунок. Раз воно виводиться зі стану, його не треба повертати з команди — його будь-коли перерахує окремий запит. Тому різ прямий: `record` лишає по собі тільки зміну стану, а рахунок стає власним методом-запитом.

:::tabs
```ts
type Money = number;                 // у копійках, щоб не губити точність на дробах

class EnergyService {
  private readings = new Map<string, number[]>();
  constructor(
    private readonly tariff: Money,        // копійок за 1 кВт·год
    private readonly standing: Money = 0,  // фіксована абонплата
  ) {}

  // КОМАНДА: дописала показник — і мовчить
  record(deviceId: string, kWh: number): void {
    const list = this.readings.get(deviceId) ?? [];
    list.push(kWh);
    this.readings.set(deviceId, list);
  }

  // ЗАПИТ: рахунок — чиста функція від збережених показників
  projectedBill(deviceId: string): Money {
    const kWh = (this.readings.get(deviceId) ?? []).reduce((a, b) => a + b, 0);
    return Math.round(kWh * this.tariff) + this.standing;
  }

  // ЗАПИТ: скільки показників лежить — знадобиться в тестах
  readingCount(deviceId: string): number {
    return this.readings.get(deviceId)?.length ?? 0;
  }
}
```
```py
class EnergyService:
    def __init__(self, tariff: int, standing: int = 0) -> None:
        self._readings: dict[str, list[float]] = {}
        self._tariff = tariff          # копійок за 1 кВт·год
        self._standing = standing      # фіксована абонплата

    def record(self, device_id: str, kwh: float) -> None:      # КОМАНДА
        self._readings.setdefault(device_id, []).append(kwh)

    def projected_bill(self, device_id: str) -> int:           # ЗАПИТ
        kwh = sum(self._readings.get(device_id, ()))
        return round(kwh * self._tariff) + self._standing

    def reading_count(self, device_id: str) -> int:            # ЗАПИТ
        return len(self._readings.get(device_id, ()))
```
:::

Зверни увагу на дрібницю в запиті: у ньому ми читаємо `self._readings.get(device_id, ())` — з дефолтом, а не `self._readings[device_id]`. Якби запит писався через `defaultdict` чи через `[...]`, він **створював би** порожній запис у мапі для невідомого пристрою — тобто нишком міняв би стан. У статті про CQS про таке говорилося як про запит, що потай діє; тут ми його не пускаємо навіть у дрібниці, бо запит, який чіпає стан, — це вже не запит.

Тепер той, хто хоче і записати, і побачити рахунок, робить два наміри двома рядками — і це навіть чесніше, бо обидва видно:

```ts
svc.record(deviceId, kWh);
const bill = svc.projectedBill(deviceId);
```

Ціна різу — один зайвий виклик на дашборді. Виграш побачимо аж у тестах.

## Тести: чому змішаний метод боляче перевіряти — і як стає легко

Візьмімо той самий сервіс рахунків і спробуймо покрити його тестами **до** різу. Ми хочемо дві прості речі: пересвідчитися, що рахунок рахується правильно, і що показник справді лягає в журнал. На змішаному методі обидва тести виходять кривими:

```ts
// ДО різу: єдиний метод — тому перевірка арифметики МУСИТЬ мутувати журнал
test("рахунок правильний (?)", () => {
  const svc = new EnergyService(250);
  const bill = svc.record("boiler", 8);   // щоб дізнатися рахунок, довелося ЗАПИСАТИ
  expect(bill).toBe(2000);                // 8·250; але журнал уже брудний
});
```

Перевірити арифметику, не змінюючи стану, тут неможливо — відповідь віддає лише той метод, що пише. А тест «чи показник додався» ще гірший: у змішаного методу нема окремого способу спитати стан, тож доводиться **вірити поверненому рахунку** як доказу запису («рахунок зріс на 8·тариф — отже, показник ліг»). Тест на дію спирається на побічну відповідь дії — рівно та плутанина, від якої CQS застерігає.

Після різу обидва тести розпадаються на дві чисті половини. **Запит тестується тривіально** — підготував стан, спитав, порівняв; а що запит не лишає слідів, видно з того, що двічі поспіль він дає те саме:

:::tabs
```ts
// ЗАПИТ: підготуй стан → спитай → порівняй. Двічі — те саме число.
test("projectedBill — чиста функція показників", () => {
  const svc = new EnergyService(250);       // 2.50 грн/кВт·год у копійках
  svc.record("boiler", 3);
  svc.record("boiler", 5);

  expect(svc.projectedBill("boiler")).toBe(2000);  // (3+5)·250
  expect(svc.projectedBill("boiler")).toBe(2000);  // спитали вдруге — стан не зрушив
});
```
```py
def test_projected_bill_is_pure_query():
    svc = EnergyService(tariff=250)               # 2.50 грн/кВт·год у копійках
    svc.record("boiler", 3)
    svc.record("boiler", 5)

    assert svc.projected_bill("boiler") == 2000   # (3+5)·250
    assert svc.projected_bill("boiler") == 2000   # вдруге — те саме, стан не зрушив
```
:::

**Команда тестується через стан.** Вона повертає `void` — перевіряти в неї нема чого, тож ми дивимося не на повернене, а на **слід**, який вона лишила, і читаємо цей слід окремим запитом:

:::tabs
```ts
// КОМАНДА: перевіряємо НЕ повернене (його нема), а зміну стану — через запит
test("record — дописує показник у стан", () => {
  const svc = new EnergyService(250);
  expect(svc.readingCount("boiler")).toBe(0);

  const result = svc.record("boiler", 3);
  expect(result).toBeUndefined();               // команді нема чого повертати

  expect(svc.readingCount("boiler")).toBe(1);   // ефект видно лише запитом
  expect(svc.projectedBill("boiler")).toBe(750);
});
```
```py
def test_record_changes_state_only():
    svc = EnergyService(tariff=250)
    assert svc.reading_count("boiler") == 0

    assert svc.record("boiler", 3) is None         # команда нічого не повертає

    assert svc.reading_count("boiler") == 1        # ефект видно лише запитом
    assert svc.projected_bill("boiler") == 750     # 3·250
```
:::

Ось у цій парі й лежить уся вигода різу, названа руками. Арифметику рахунку тепер видно **в ізоляції** — жодного запису, щоб її перевірити; можна прогнати сотню тарифів і крайових випадків, не торкнувшись журналу. А факт запису перевіряється **через незалежний запит**, а не через довіру до побічної відповіді. Дві половини, кожна чесна, замість одного тесту, що плутав дію з відповіддю.

> 🔧 **Навіщо це.** Форма тесту — це рентген дизайну. Якщо перевірити результат методу можна лише викликом, що псує стан, — метод змішав дві речі, і тест кричить про це першим. Коли ловиш себе на тому, що готуєш складне оточення тільки щоб дістати відповідь, або перевіряєш дію через повернене нею значення, — це майже завжди прихований змішаний метод, який проситься на різ.

Досі різ був беззаперечним. Тепер — три місця, де він шкідливий, і де команда **свідомо** повертає значення.

## Виняток перший: дістати-й-вилучити

У Digital Homes є черга вихідних наказів пристроям: оновлення прошивок, зміни розкладів, сповіщення. Кілька воркерів розбирають її паралельно, і кожен бере наступний наказ методом, що **повертає елемент і одразу його прибирає** — класичний `dequeue`:

:::tabs
```ts
class CommandQueue<T> {
  private items: T[] = [];

  enqueue(job: T): void { this.items.push(job); }      // КОМАНДА — чиста

  // ВИНЯТОК: дістати-й-вилучити ОДНИМ кроком
  dequeue(): T | undefined {
    return this.items.shift();   // повертає перший і тут-таки прибирає його
  }

  get size(): number { return this.items.length; }     // ЗАПИТ
}
```
```py
from collections import deque

class CommandQueue:
    def __init__(self) -> None:
        self._items: deque = deque()

    def enqueue(self, job) -> None:        # КОМАНДА
        self._items.append(job)

    def dequeue(self):                     # ВИНЯТОК: дістати-й-вилучити
        return self._items.popleft() if self._items else None

    def size(self) -> int:                 # ЗАПИТ
        return len(self._items)
```
:::

За буквою CQS це порушення: `dequeue` і міняє стан, і повертає значення. Спокуса «виправити» — розділити на запит `peek` (подивись перший) і команду `removeFirst` (прибери перший):

```ts
peek(): T | undefined { return this.items[0]; }   // «запит»
removeFirst(): void { this.items.shift(); }        // «команда»

// воркер:
const job = queue.peek();
if (job) { process(job); queue.removeFirst(); }
```

І ось тут різ народжує баг, якого в змішаному методі не було. Між `peek` і `removeFirst` є **вікно**, у яке встигає вклинитися інший воркер. Воркер A подивився й побачив наказ #7. Перш ніж A встиг його прибрати, воркер B теж подивився — і побачив **той самий** #7, бо стан іще не змінився. Обидва беруться його виконувати. Наказ #7 виконано двічі; хтось отримав подвійне оновлення прошивки.

![Часова стрічка двох воркерів: A робить peek і бачить наказ #7, у вікні до його remove воркер B теж робить peek і бачить той самий #7; обидва виконують один наказ двічі.](/root/course/progarch/cqs-command-query/img/race-window.svg)
*Вікно між роздільними `peek` і `removeFirst`: поки A не прибрав елемент, стан не змінився, тож B бачить той самий наказ. Атомарний `dequeue` цього вікна не лишає — «подивись» і «прибери» злиті в один неподільний крок.*

Змішаний `dequeue` цього вікна не має за побудовою: «дістати» і «прибрати» — один крок, який неможливо перервати посередині, тож двом воркерам фізично не дістанеться один елемент. Тут CQS програє коректності, і програє свідомо. У самій мові це часом видно: у CPython `deque.popleft()` — одна атомарна операція під глобальним замком, тож безпечна між потоками, тоді як пара `peek` + `popleft` — уже ні. А коли черга не в пам'яті, а справжня, атомарність «дістати-й-вилучити» тобі й так уже подарували: Redis `LPOP`, `RPOPLPUSH`/`LMOVE`, `ReceiveMessage` в SQS із таймаутом видимості — усе це віддає повідомлення й водночас ховає його від інших споживачів одним неподільним кроком, саме щоб те вікно не відкрилося.

> 🔧 **Навіщо це.** Справжні черги — те, на чому тримається фонова робота цілого сервісу, — існують саме тому, що «дістати-й-вилучити» мусить бути атомарним. Розділиш заради чистоти — і дістанеш подвійну обробку під навантаженням: [брокер повідомлень](book:programming/message-queue) віддає роботу так, щоб двоє споживачів не вхопили одне завдання.

## Виняток другий: атомарний лічильник під конкурентністю

Кожній вихідній події Digital Homes присвоює зростаючий номер — щоб події можна було впорядкувати й не сплутати. Багато потоків просять номер водночас, і кожному має дістатися **свій**, унікальний. Метод «віддай поточний номер і зсунь лічильник на одиницю» — це знову команда, що повертає значення, і розділяти її не можна вже не через зручність, а через фізику паралельності.

Спершу подивімось, ЧОМУ розділення тут ламає все, — на голому лічильнику без атоміків:

```
Лічильник = 42.

Потік T1: прочитав 42  ─┐
Потік T2: прочитав 42  ─┤ обидва бачать 42 (запит нічого не змінив)
Потік T1: записав 43   ─┤
Потік T2: записав 43   ─┘ номер 42 видано ДВІЧІ, а 43 узагалі проґавлено
```

Це той самий [стан гонитви](book:programming/atomicity-races), що й у черзі, тільки над числом: роздільні «прочитай» і «збільш» лишають вікно, у якому два потоки читають одне значення. Ліки — злити читання й запис у один неподільний крок, який процесор гарантує апаратно. У системних мовах це `fetch_add` / `getAndIncrement`:

:::tabs
```cpp
#include <atomic>
#include <cstdint>

class EventIds {
  std::atomic<std::uint64_t> next_{1};
public:
  // ВИНЯТОК: віддати поточний номер І зсунути лічильник — одним атомарним кроком
  std::uint64_t allocate() {
    return next_.fetch_add(1, std::memory_order_relaxed);  // повертає значення ДО +1
  }
};
```
```java
import java.util.concurrent.atomic.AtomicLong;

class EventIds {
    private final AtomicLong next = new AtomicLong(1);

    long allocate() {
        return next.getAndIncrement();   // повертає попереднє значення, атомарно +1
    }
}
```
```go
import "sync/atomic"

type EventIds struct{ next atomic.Uint64 }   // нульове значення = 0

func (e *EventIds) Allocate() uint64 {
    return e.next.Add(1)   // Add повертає НОВЕ значення: 1, 2, 3, … — кожне унікальне
}
```
:::

Три реалізації дають ту саму послідовність `1, 2, 3, …`, у якій жоден номер не повторюється й не губиться, — але тут ховається пастка, на якій легко наламати дров, тож назвімо її вголос. `fetch_add` у C++ і `getAndIncrement` у Java повертають значення **до** додавання, тому лічильник сіють одиницею, і перший виклик віддає `1`. А Go-шний `Add` повертає значення **після** додавання, тому лічильник лишають на нулі, і перший `Add(1)` теж віддає `1`. Різна домовленість — «старе» проти «нового», — однакова гарантія: кожному потоку свій номер. Сплутаєш конвенції (сієш Go-лічильник одиницею й повертаєш `Add`) — і перший номер вискочить `2`, а нуль чи одиниця десь загубляться.

`fetch_add` — окремий випадок ширшого прийому. Коли над значенням треба зробити не просто `+1`, а будь-яке перетворення, що залежить від поточного значення, роблять **цикл порівняй-і-заміни** (compare-and-swap): прочитай старе, порахуй нове, і заміни лише **якщо між читанням і заміною ніхто не втрутився**; втрутився — почни спочатку.

```go
// загальна форма: атомарно застосувати f до значення через compare-and-swap
func (e *EventIds) Update(f func(uint64) uint64) uint64 {
    for {
        old := e.next.Load()
        neu := f(old)
        if e.next.CompareAndSwap(old, neu) {  // вдалося лише якщо ніхто не змінив old
            return neu
        }
        // хтось випередив між Load і CompareAndSwap → пробуємо ще раз
    }
}
```

Придивись, що робить цей цикл: він бере той самий небезпечний різ — «прочитай, тоді запиши» — і **робить його безпечним**, перевіряючи на записі, що прочитане ще чинне. `CompareAndSwap` повертає `false`, коли значення встигло змінитися, і тоді ми не затираємо чужу зміну, а перечитуємо й лічимо наново. Тобто навіть якщо дуже хочеться розділити читання й запис, під конкурентністю доводиться склеїти їх назад — цим циклом. Той самий compare-and-swap лежить в основі [оптимістичного блокування](book:programming/optimistic-locking) у базах: `UPDATE … SET версія = версія+1 WHERE версія = ?` оновлює рядок лише тоді, коли версія не змінилася відколи ти її прочитав, — та сама «заміна за умовою», тільки над рядком таблиці. А сам інструментарій атомарних цілих — від `fetch_add` до `compare_exchange` — розібрано в [std::atomic](book:programming/std-atomic).

## Виняток третій: створити-й-повернути ідентифікатор

Останній виняток відрізняється від перших двох на самому корені. Там розділити було **можна**, тільки шкідливо — відкривалося вікно. Тут розділити **фізично нема як**: значення, яке команда повертає, вона ж і **народжує**.

Пристрій у Digital Homes отримує ідентифікатор не від застосунку, а від бази — з послідовності, атомарно, у мить вставки. Доки рядок не вставлено, ідентифікатора **не існує**; тож повернути його окремим запитом нема звідки — питати нічого. Створення й повернення id зливаються не заради швидкодії, а тому, що інакше не буває:

```sql
-- id не існує, доки рядок не вставлено; БД присвоює його з послідовності в мить INSERT
INSERT INTO devices (room, kind, name)
VALUES ('kitchen', 'thermostat', 'Кухня')
RETURNING id;
```

`RETURNING` віддає щойно присвоєний id тим самим кроком, що й вставляє рядок. У коді бекенду це один виклик:

:::tabs
```ts
async function createDevice(db: Pool, d: NewDevice): Promise<number> {
  const { rows } = await db.query<{ id: number }>(
    `INSERT INTO devices (room, kind, name)
     VALUES ($1, $2, $3)
     RETURNING id`,
    [d.room, d.kind, d.name],
  );
  return rows[0].id;   // свіжий id — прямий продукт вставки
}
```
```py
def create_device(conn, d: NewDevice) -> int:
    with conn.cursor() as cur:
        cur.execute(
            "INSERT INTO devices (room, kind, name) "
            "VALUES (%s, %s, %s) RETURNING id",
            (d.room, d.kind, d.name),
        )
        return cur.fetchone()[0]   # id, якого до цього рядка не існувало
```
:::

Синтаксис різниться по базах, а суть — та сама скрізь. `RETURNING` підтримують PostgreSQL (від версії 8.2, 2006), SQLite (від 3.35.0, 2021) і MariaDB. MySQL його не має — там після вставки питають `LAST_INSERT_ID()`; SQL Server віддає ключ клаузою `OUTPUT inserted.id` або через `SCOPE_IDENTITY()`. Але зверни увагу: навіть де синтаксис окремий, «дістати щойно створений ключ» усе одно склеєне зі вставкою — `LAST_INSERT_ID()` повертає ключ **останнього** твого `INSERT` у межах з'єднання саме тому, що інакше два паралельні з'єднання не розрізнили б, чий це ключ. Спроба зробити «по-CQS» — спершу запитом узяти наступний id, тоді вставити рядок із ним — не рятує, а гірша: це той самий різ читання-й-запису з винятку другого, тільки тепер ти ще й перевинаходиш послідовність, яку база вже роздає атомарно. Тож команда повертає id — і це правильно.

## Правило чесного винятку

Три випадки різні на вигляд — черга, лічильник, база, — але тримає їх один шов. Розділення або **впускає між кроки чужий виклик** (черга, лічильник), або **фізично неможливе**, бо значення створює сама дія (id). І в кожному повернене з команди — не побічний звіт «до купи», а **прямий продукт самої дії**: вилучений елемент, номер, який дістався саме цьому викликачу, свіжий ідентифікатор.

![Дві зони. Ліворуч «розділити можна, але відкриється вікно»: dequeue повертає вилучений елемент, allocate повертає унікальний номер. Праворуч «розділити неможливо, значення створює сама дія»: createDevice повертає свіжий id. Спільне внизу: повернене — прямий продукт дії, не побічний звіт.](/root/course/progarch/cqs-command-query/img/honest-return.svg)
*Таксономія трьох винятків за причиною злиття: ліворуч — розділити можна, та між кроками відкриється вікно; праворуч — розділити нема як, бо значення народжує сама дія. У всіх трьох повернене — прямий продукт команди.*

Звідси й практичний припис для винятку: **ламай CQS свідомо, назви причину й зроби повернене чесним.** «Свідомо» означає, що виняток видно — з імені (`dequeue`, `allocate`, `createDevice` самі кажуть, що беруть-і-змінюють), з коментаря, що називає гонитву чи неможливість, з типу. «Чесне повернене» означає, що команда віддає **прямий наслідок своєї дії** — те, чого без цієї дії не було б і що жоден запит не дістав би окремо, — а не якесь похідне, що його спокійно порахував би окремий метод. Наш вихідний `record` провалює обидві перевірки: рахунок — не продукт запису, а чиста функція стану, яку залюбки поверне `projectedBill`; отже, різ.

## Складність і пастки

**Фальшивий виняток — побічний звіт під маскою «це ж як pop()».** Найчастіша помилка — прикрити звичайний змішаний метод авторитетом законного винятку. `saveOrder()`, що повертає список попереджень валідації; `updateProfile()`, що віддає оновлений об'єкт; наш `record()`, що віддавав рахунок, — усі вони кивають на `dequeue` як на виправдання. Перевірка одна й гостра: **чи повернене — прямий продукт дії, якого не дістати окремим запитом?** Вилучений елемент, номер, id — так, їх породжує сама дія. Попередження валідації, оновлений об'єкт, рахунок — ні, це похідне від стану, яке порахує чистий запит. Похідне від стану → різ; продукт дії → законний виняток.

**Виняток невидимий наївному тесту.** Ось чому переплутати різ із винятком так небезпечно. Розділений `peek` + `removeFirst` проходить **кожен** однопотоковий тест: викликав по черзі — елемент дістався, чергу спорожнено, зелено. Баг живе тільки у вікні між двома викликами, а вікно відкривається лише коли хтось вклинюється — під навантаженням, у проді, раз на тисячу разів. Зелений тест тут нічого не доводить: коректність атомарного винятку — це обов'язок **міркування**, а не те, що витягне асерт. Тому винятки й треба вміти впізнавати оком: тест на них сліпий.

**Виняток без конкуренції — зайва плутанина.** Дзеркальна пастка: тягти атомарний лічильник чи злиті методи туди, де все однопотокове. Якщо номери роздає один потік, `fetch_add` не потрібен — простий `count++` ясніший і швидший, а атомік лише збиває з пантелику читача, змушуючи його шукати конкурентність, якої нема. Виняток заробляє свій хліб **лише під суперництвом за стан**; без нього це просто змішаний метод, що втратив виправдання. Спершу спитай, чи руки справді тягнуться до об'єкта водночас, — а тоді вже злучай.

**Перебір із поверненим у створенні.** Спокуса роздути `createDevice` до повернення цілого свіжозчитаного об'єкта пристрою «щоб клієнтові було зручно». Прямий продукт вставки — це **id**, а не весь рядок; повний об'єкт — це вже окремий запит `getDevice(id)`, який чудово живе сам. Повертай мінімальний чесний продукт дії; де клієнтові треба більше — то окреме питання, яке має право бути окремим. Виняток дозволяє команді повернути **наслідок дії**, а не перетворює її на комбайн «зроби і заразом усе розкажи».

Отже, CQS лишається компасом і тут. Три винятки — не діри в правилі й не дозвіл махнути на нього рукою, а рівно ті місця, де світ **сам** склеїв читання й зміну — у черзі, у процесорному лічильнику, у послідовності бази, — і мудрість не в тому, щоб героїчно розсікти склеєне, а в тому, щоб упізнати шов, свідомо піти в обхід і лишити по собі коментар, чому саме тут компас показав повз північ.
