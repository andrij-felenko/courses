# 📋 API-контракт ідепотентості та дедуплікації на межі

Ця довідкова вставка регламентує мережевий API-контракт між клієнтом та шлюзом (API Gateway / Ingest Boundary) для дедуплікації повторних запитів. Вона описує стандартизовані HTTP-заголовки, коди відповідей, формати payload, механізми канонізації тіла запиту, трасування та часові правила TTL.

## Стандартизовані HTTP-заголовки

Для передачі ідентифікаторів дедуплікації використовуються стандартизовані заголовки відповідно до специфікації IETF Draft *The Idempotency-Key HTTP Header Field*.

Використання єдиного стандарту заголовків є критичним для забезпечення сумісності між різними мобільними клієнтами, сторонніми партнерами та внутрішньою інфраструктурою API Gateway. При відсутності такого стандарту кожен сервіс починає вигадувати власні заголовки на кшталт `X-Idempotency-Token` чи `Client-Transaction-ID`, що призводить до деградації архітектурної цілісності контракту.

Приклад вхідного HTTP-запиту:

```http
POST /api/v1/payments HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 7b9e021e-1284-4d89-a212-0738e4a9e5b8
X-Request-ID: req-c891a-9921
Content-Type: application/json

{
  "amount": 1500,
  "currency": "UAH",
  "account_id": "ACC-90412"
}
```

### Вичерпна специфікація заголовків

| Заголовок | Передає хто | Призначення | Тривалість життя (TTL) |
|---|---|---|---|
| `Idempotency-Key` | Клієнт | Детермінований унікальний ключ бізнес-наміру клієнта для мутувальних запитів (`POST`, `PATCH`). | 24–72 години (залежно від SLA) |
| `X-Request-ID` | Клієнт / Gateway | Унікальний ідентифікатор конкретної мережевої спроби (спроба №1, спроба №2). Потрібен для сквозного трасування логів. | Тільки під час запиту (Log Trace) |
| `Original-Request-Date` | Gateway (відповідь) | ISO-8601 штамп часу, коли вперше було прийнято й оброблено оригінальний запит. | Присутній у повторній відповіді |
| `Idempotency-Replayed` | Gateway (відповідь) | Булевий прапорець (`true`), що інформує клієнта про те, що відповідь повернено з дедуп-кешу. | Присутній у повторній відповіді |

## Спектр кодів відповідей на межі (Response Matrix)

При отриманні запиту із заголовком `Idempotency-Key` Edge Gateway реалізує таку конечну автоматну матрицю (FSM):

```
                        ┌──────────────────────────────┐
                        │ Вхідний запит з Key: K123    │
                        └──────────────┬───────────────┘
                                       │
                    ┌──────────────────┴──────────────────┐
                    ▼                                     ▼
        [Key K123 НЕМАЄ в кеші]                 [Key K123 Є в кеші]
                    │                                     │
                    ▼                                     ▼
        Пропускаємо до бекенду              ┌─────────────┴─────────────┐
                                            ▼                           ▼
                                    [Хеш Payload збігається]  [Хеш Payload РІЗНИЙ]
                                            │                           │
                                            ▼                           ▼
                                    Повертаємо збережену      Повертаємо 409 Conflict
                                    відповідь (200/201)        (Mismatched Payload)
```

### Опис HTTP статус-кодів та бізнес-семантики

#### 1. Успішне відтворення (`200 OK` / `201 Created` + `Idempotency-Replayed: true`)
Повертається, якщо запит із тим самим `Idempotency-Key` та **ідентичним хешем тіла запиту (Payload Hash)** вже був успішно оброблений. Шлюз віддає збережений у кеші тіло відповіді та заголовки без повторного виклику бізнес-логіки. Це створює для клієнта повну ілюзію того, що його запит було оброблено саме зараз, хоча насправді відповідь зчитано з оперативної пам'яті.

#### 2. Колізія повторного використання (`409 Conflict` - Mismatched Payload)
Повертається, якщо клієнт повторно використав той самий `Idempotency-Key`, але надіслав **інше тіло запиту (Payload)** або інші критичні параметри. Це свідчить про колізію ключів або помилку в програмуванні клієнтського SDK. Заборонити зміну payload при тому самому ключі є критично важливим для захисту від фроду та викривлення бізнес-наміру.
```json
{
  "code": "idempotency_key_reused_with_different_payload",
  "detail": "Заголовок Idempotency-Key '7b9e021e' вже використано для іншого запиту з відмінним тілом.",
  "status": 409
}
```

#### 3. Блокування запиту в процесі (`429 Too Many Requests` / `425 Too Early` - In-Progress Lock)
Повертається, якщо перший запит з таким `Idempotency-Key` ще знаходиться у процесі обробки бекендом (In-Flight), а клієнт уже надіслав паралельний дублікат. Замість того щоб пропускати другий запит до бази даних чи змушувати його чекати відкритим HTTP-з'єднанням, шлюз повертає чітку інструкцію сповільнитися.
```json
{
  "code": "request_in_progress",
  "detail": "Оригінальний запит із цим ключем ще обробляється. Спробуйте пізніше.",
  "status": 429
}
```

## Канонізація тіла запиту та розрахунок Payload Hash

Шлюз межі не просто перевіряє факт наявності `Idempotency-Key`, але й верифікує цілісність бізнес-наміру клієнта через обчислення хешу від канонізованого тіла запиту (Canonical Request Hashing).

### Алгоритм канонізації

Якщо два клієнтські запити містять однаковий JSON за змістом, але відрізняються форматуванням (наприклад, різний порядок полів або додаткові пробіли), пряме хешування байтів поверне різні значення. Щоб запобігти цьому, Edge Gateway виконує канонізацію:

1. **Сортування ключів JSON (Canonical JSON):** Всі поля JSON-об'єкта сортуються в алфавітному порядку за кодами символів UTF-8.
2. **Нормалізація пробілів:** Видаляються всі незначущі пробіли, символи табуляції та переходи рядків поза межами текстових значень.
3. **Нормалізація чисел та кодування:** Усі числа приводяться до канонічного десяткового вигляду (без зайвих нулів наприкінці), а рядки кодуються в UTF-8.

Формула обчислення Payload Hash:

```
Payload_Hash = SHA256( HTTP_Method + "\n" + Canonical_Path + "\n" + Canonical_JSON_Body )
```

Якщо при повторному запиті з тим самим `Idempotency-Key` обчислений `Payload_Hash` відрізняється від збереженого у кеші, шлюз миттєво повертає `409 Conflict`.

## Формат збереження стану на межі (Cache Record Schema)

Для зберігання стану ідемпотентності у швидкому зсувному кеші (Redis / Key-Value Store) використовується така структура даних:

```json
{
  "key": "idem:tenant_102:7b9e021e-1284-4d89-a212-0738e4a9e5b8",
  "status": "COMPLETED",
  "request_hash": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "created_at": "2026-08-18T09:30:00Z",
  "response": {
    "status_code": 201,
    "headers": {
      "Content-Type": "application/json",
      "Location": "/api/v1/payments/pay_991823"
    },
    "body_base64": "ewogICJpZCI6ICJwYXlfOTkxODIzIiwKICAic3RhdHVzIjogInN1Y2Nlc3MiCn0="
  }
}
```

### Політики та розрахунок TTL

- **Мінімальний TTL:** Значення TTL мусить перевищувати максимальне вікно повторів клієнтського SDK (`Max Client Retry Window`). У корпоративних API (наприклад, Stripe, PayPal) стандартом є **24 години**.
- **Очищення (Eviction Policy):** У Redis для ключів ідемпотентності налаштовується алгоритм `volatile-lru` або автоматичне видалення через `EXPIRE`.
- **Безпека та мультиарендність:** Ключ дедуплікації у кеші **обов'язково** повинен містити префікс `Tenant_ID` або `User_ID` (наприклад, `idem:tenant_102:<key>`), щоб унеможливити атаки між орендарями (Cross-Tenant Key Collisions), коли один користувач підгадує `Idempotency-Key` іншого.

## Специфікація обробки помилок мережевого з'єднання

Окремим розділом контракту є поведінка шлюзу при проміжних збоях під час передачі відповіді:

1. **Втрата з'єднання при відправці відповіді (Client Disconnect):**
   Якщо доменна транзакція виконана успішно і відповідь збережена в Redis, але клієнт розірвав TCP-з'єднання до отримання останнього байта — стан ідемпотентності вважається **успішно зафіксованим**. При наступному повторі клієнт отримає збережену відповідь із кешу.

2. **Запізнення відповіді бекенду (Gateway Timeout 504):**
   Якщо доменний сервіс не відповів протягом ліміту Gateway (наприклад, 5 секунд), шлюз видаляє тимчасовий блок `In-Progress` або маркує його статусом `FAILED_TIMEOUT`. Це дозволяє клієнту повторити запит без блокування колізією 429.

## Простеження та метрики ідемпотентності (Observability)

Для моніторингу роботи дедуплікації на межі API Gateway мусить експортувати такі метрики в форматі Prometheus / OpenTelemetry:

- `http_idempotency_requests_total{status="hit"}` — лічильник унікальних запитів, успішно відсіяних на межі з поверненням збереженої відповіді з кешу.
- `http_idempotency_requests_total{status="miss"}` — лічильник первинних унікальних запитів, що пройшли далі у доменний шар.
- `http_idempotency_requests_total{status="conflict"}` — лічильник спроб повторного використання ключа з відмінним тілом payload (потенційний фрод або баг).
- `http_idempotency_requests_total{status="in_progress_lock"}` — лічильник запитів, що впали за блокуванням 429 під час виконання первинної транзакції.

Аналіз співвідношення `hit / (hit + miss)` дозволяє оцінити ефективність кешування дедуплікатора на межі під час відновлення після мережевих аварій.

## Підтримка gRPC та GraphQL протоколів

Хоча класичний контракт орієнтований на HTTP REST, специфікація поширюється й на інші транспортні протоколи:

1. **gRPC Protocol:** Заголовок ідемпотентності передається в gRPC Metadata: `idempotency-key: 7b9e021e...`. При відтворенні дубля шлюз повертає збережений gRPC Protobuf Payload зі статусом `OK` та метаданими `idempotency-replayed: true`.
2. **GraphQL Protocol:** Оскільки GraphQL використовує єдину кінцеву точку `POST /graphql`, ключ ідемпотентності передається або в HTTP-заголовку, або в директиві запиту: `mutation CreatePayment @idempotencyKey(key: "7b9e021e...")`.
