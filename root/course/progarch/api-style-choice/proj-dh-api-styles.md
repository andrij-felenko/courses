# ⚙️ Панель Digital Homes чотирма стилями — і поміряти різницю

**Задача.** Намалювати один буденний екран застосунку DH — панель дому: дім, його кімнати, у кожній кімнаті пристрої, у кожного пристрою останнє показання. Форма даних та сама щоразу. Реалізуймо цю панель чотирма стилями — REST-водоспадом, gRPC, GraphQL і чергою — і не сперечаймося гаслами, а виміряймо три числа на кожному: скільки виходить обертів до сервера (round-trip), скільки байтів проходить по дроту й яке зчеплення лишається на межі. Числа сперечатися не вміють.

**Ідея.** Форма графа одна, а от **хто визначає цю форму** і **де вона збирається** — різне в кожному стилі, і саме тут ховається вся ціна. Зафіксуймо однакову фікстуру для всіх чотирьох, щоб порівняння було чесним:

```text
Дім 42 → 5 кімнат → 15 пристроїв (по 3 на кімнату)
RTT телефона в мобільній мережі ≈ 150 мс
RTT сервіс-до-сервіса всередині датацентру ≈ 1 мс
```

Двадцять із гаком дрібних читань, з яких треба скласти один екран. Погляньмо, у що це виливається кожним стилем.

## Стиль 1 — REST-водоспад: платиш за глибину графа

Наївний ресурсний REST дає рівно те, що обіцяє одиниця розмови: ти називаєш річ і дістаєш її представлення. Проблема в тому, що представлення дому містить не самі кімнати, а **посилання** на них; кімната — посилання на пристрої. Щоб дійти до листка графа, доводиться спускатися рівень за рівнем:

```http
GET /homes/42            → { "id":42, "roomIds":["r1", … "r5"] }
GET /rooms/r1            → { "id":"r1", "name":"кухня", "deviceIds":["d1","d2","d3"] }
GET /devices/d1          → { …повне представлення пристрою з lastReading… }
```

Клієнт мусить сам оркеструвати цей спуск. Ось чесний код мобільної панелі — той, який хочеться написати, бо він «простий»:

```typescript
const API = "https://api.digitalhomes.io";
const get = (p: string) => fetch(API + p).then(r => r.json());

// найгірший, але найчастіший варіант — послідовно, «бо так читається зверху вниз»
async function loadPanelNaive(homeId: number) {
  const home = await get(`/homes/${homeId}`);          // 1
  for (const rid of home.roomIds) {
    const room = await get(`/rooms/${rid}`);            // ×5
    for (const did of room.deviceIds) {
      const dev = await get(`/devices/${did}`);         // ×15
      paint(room, dev);                                 // 21 оберт ПІДРЯД
    }
  }
}
```

Це двадцять один синхронний оберт один за одним. Порахуймо:

```text
1 (дім) + 5 (кімнати) + 15 (пристрої) = 21 запит
21 × 150 мс = 3150 мс ≈ 3.2 с білого екрана
```

Перша й очевидна поправка — розпаралелити запити в межах одного рівня: усі кімнати можна тягти водночас, усі пристрої — водночас. `Promise.all` замість циклу:

```typescript
async function loadPanelParallel(homeId: number) {
  const home  = await get(`/homes/${homeId}`);                           // хвиля 1
  const rooms = await Promise.all(home.roomIds.map((id: string) => get(`/rooms/${id}`)));   // хвиля 2
  const ids   = rooms.flatMap(r => r.deviceIds);
  const devs  = await Promise.all(ids.map((id: string) => get(`/devices/${id}`)));          // хвиля 3
  return assemble(home, rooms, devs);
}
```

І ось тут вилазить головний, неочевидний урок, якого не видно, поки не поміряєш:

```text
хвиля 1: дім              → 1 × 150 мс
хвиля 2: 5 кімнат ∥       → 1 × 150 мс
хвиля 3: 15 пристроїв ∥   → 1 × 150 мс
разом: 3 × 150 = 450 мс
```

Паралелізм прибрав 21 запит до **трьох хвиль**, але не до однієї. Чому? Бо URL-и третього рівня (`/devices/d1`) ти дізнаєшся **лише з відповіді** другого рівня, а другого — лише з першого. Кожна хвиля залежить від попередньої, і жоден паралелізм цього ланцюга не розірве. **REST-водоспад платить не за кількість запитів, а за глибину графа** — за число рівнів, які треба пройти послідовно. Три рівні — три RTT, і крапка. Це структурна ціна ресурсної одиниці розмови, а не недбалість реалізації.

Друга ціна — **перебір** (over-fetch). Представлення пристрою чесно віддає *весь* пристрій, а панелі з нього треба п'ять полів:

```text
GET /devices/d1 віддає:
  { id, kind, room, firmwareVersion, mac, ip, battery,
    calibration{…}, config{…}, lastReading{ value, at } }   ≈ 780 Б
панелі потрібно:
  { id, kind, room, lastReading.value, lastReading.at }     ≈ 60 Б
перебір: 15 × 780 ≈ 11.7 КБ по дроту, корисних ≈ 0.9 КБ  (≈ 13× зайвого)
```

Дзеркальна вада — **недобір** (under-fetch): щоб узнати пристрої, спершу тягнеш кімнати; щоб кімнати — спершу дім. Кожен рівень недодає граф і змушує йти ще раз. Перебір і недобір — це два боки однієї монети: контракт REST зафіксовано на боці **сервера**, і він ніколи не збігається точно з тим, що треба **цьому** екрану.

Чесно додати й другий бік балансу, бо REST тут не «поганий»: усі 21 запит — це прості кешовані `GET`, які їдуть на будь-якому HTTP-залізі, лягають у CDN і проксі, дебажаться в `curl` і відкриваються з чого завгодно. Водоспад коштує обертів — але дає задарма всю інфраструктуру Вебу. І варто пам'ятати: «21 проти 1» — це не REST проти решти, а **наївний ресурсний водоспад проти зібраної форми**. Той самий REST може віддати панель за один оберт, якщо зробити під неї компаунд-ендпойнт (`GET /homes/42/panel`) або BFF — ціною окремого рукотворного ендпойнта під кожен екран.

## Стиль 2 — gRPC: один типізований виклик свій-до-свого

Тепер інша межа — не телефон, а нутрощі хмари: реєстр пристроїв віддає панель рушієві автоматизацій. Тут можна дозволити собі щільний типізований контракт. Обидві сторони діляться одним файлом опису, з якого генератор робить код:

```proto
syntax = "proto3";
package dh.registry.v1;

service DeviceRegistry {
  rpc GetHomePanel(HomePanelRequest) returns (HomePanel);
}

message HomePanelRequest { uint64 home_id = 1; }

message HomePanel {
  uint64 home_id      = 1;
  repeated Room rooms = 2;
}
message Room {
  string id              = 1;
  string name            = 2;
  repeated Device devices = 3;
}
message Device {
  string  id   = 1;
  string  kind = 2;
  Reading last = 3;
}
message Reading {
  double value      = 1;
  int64  at_unix_ms = 2;
}
```

Зверни увагу на числа `= 1, = 2, = 3` — це **не порядок полів, а їхня вічна ідентичність на дроті**. Бінарний формат не пише назви полів, лише ці теги, тож поміняти чи перевикористати номер видаленого поля — тихо зіпсувати розбір усіх старих повідомлень; правило залізне: номер, що колись жив, більше нікому не віддають (для викинутого поля пишуть `reserved`). Це і є та тіснота, яку ти купуєш разом зі швидкодією.

Серверна реалізація на Go — вся форма вже типізована, збираєш одним запитом до сховища:

```go
func (s *server) GetHomePanel(ctx context.Context, req *pb.HomePanelRequest) (*pb.HomePanel, error) {
    rooms, err := s.store.RoomsWithDevices(ctx, req.HomeId) // один запит, граф уже зібрано в БД
    if err != nil {
        return nil, status.Errorf(codes.Internal, "load panel %d: %v", req.HomeId, err)
    }
    return &pb.HomePanel{HomeId: req.HomeId, Rooms: toProto(rooms)}, nil
}
```

А виклик з боку рушія виглядає майже як локальний виклик функції — у цьому вся суть RPC:

```go
conn, _ := grpc.NewClient("registry:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()))
client := pb.NewDeviceRegistryClient(conn)

panel, err := client.GetHomePanel(ctx, &pb.HomePanelRequest{HomeId: 42})
// panel.Rooms[0].Devices[0].Last.Value — усе типізовано, компілятор перевірив форму
```

Виміри:

```text
1 типізований оберт, RTT датацентру ≈ 1 мс         → ≈ 1 мс
бінарний protobuf, увесь граф уже вкладено         → ≈ 1.6 КБ по дроту
```

Один оберт — і він у сто разів дешевший за телефонний, бо межа коротка. Але є жирна зірочка: **цю межу телефон напряму не дістане**. Браузер не вміє читати HTTP/2-трейлери й керувати кадрами, тож gRPC у веб живе лише через проксі-перекладач (типово Envoy), що конвертує gRPC-Web поверх HTTP/1.1 у справжній gRPC. Тобто «один оберт» gRPC реальний, але на **внутрішній** межі; до публічного клієнта його доводиться виводити через шлюз чи BFF. gRPC — інструмент для свого проти свого, і в цьому його сила, а не хиба.

## Стиль 3 — GraphQL: форму малює клієнт, а N+1 переїжджає на сервер

Повертаємось на мобільну межу — але тепер форму відповіді диктує не сервер, а сам клієнт. Спершу схема, спільний словник графа:

```graphql
type Query { home(id: ID!): Home }
type Home    { id: ID!  name: String!  rooms: [Room!]! }
type Room    { id: ID!  name: String!  devices: [Device!]! }
type Device  { id: ID!  kind: String!  last: Reading }
type Reading { value: Float!  at: String! }
```

Клієнт панелі надсилає один запит рівно тієї форми, що потрібна екрану — три рівні графа за один захід, і жодного зайвого поля:

```graphql
query Panel($id: ID!) {
  home(id: $id) {
    name
    rooms { name devices { id kind last { value at } } }
  }
}
```

```text
1 оберт потрібної форми, RTT телефона ≈ 150 мс     → 150 мс
у відповіді рівно замовлені поля                    → ≈ 0.8 КБ по дроту
```

З боку клієнта — мрія: один оберт, нуль перебору. Але подивімося, у що це обходиться серверу. Резолвери — це функції, що добувають кожен вузол графа, і наївно вони роблять так:

```typescript
const resolvers = {
  Query:  { home:    (_p, { id }) => db.home(id) },       // 1 виклик
  Home:   { rooms:   (home)       => db.roomsOf(home.id) }, // 1 виклик
  Room:   { devices: (room)       => db.devicesOf(room.id) }, // ← по 1 на КОЖНУ кімнату
  Device: { last:    (dev)        => db.lastReading(dev.id) }, // ← по 1 на КОЖЕН пристрій
};
```

Порахуймо звернення до сховища на нашій фікстурі:

```text
home            → 1
Home.rooms      → 1
Room.devices    → ×5  (по кімнаті)
Device.last     → ×15 (по пристрою)
разом: 1 + 1 + 5 + 15 = 22 запити до БД на ОДИН клієнтський оберт
```

Ось воно — класичне **N+1 резолверів**. Водоспад нікуди не зник; він **переїхав** із мережі між телефоном і хмарою всередину сервера, у фан-аут запитів до бази. Клієнт бачить один гарний оберт, а база тим часом гарує 22 рази. Якщо цього не помітити, GraphQL перетворює зручність клієнта на самопобиття сервера.

Лік — **DataLoader**: він збирає всі виклики `.load(id)`, зроблені в один такт циклу подій, і б'є їх одним пакетним запитом:

```typescript
const devicesByRoom = new DataLoader((roomIds: string[]) => db.devicesOfMany(roomIds));
const lastByDevice  = new DataLoader((devIds: string[])  => db.lastReadingsOf(devIds));

const resolvers = {
  Query:  { home:    (_p, { id }) => db.home(id) },
  Home:   { rooms:   (home)       => db.roomsOf(home.id) },
  Room:   { devices: (room)       => devicesByRoom.load(room.id) }, // 5 load → 1 пакет
  Device: { last:    (dev)        => lastByDevice.load(dev.id) },   // 15 load → 1 пакет
};
```

```text
з DataLoader: home(1) + rooms(1) + devices(1 пакет) + readings(1 пакет) = 4 запити до БД
було 22 → стало 4
```

Урок GraphQL точний: **один оберт клієнта — це обіцянка, яку сервер мусить дотримати пакетуванням**. Гнучкість форми, що є подарунком клієнтові, на сервері обертається зарядженою рушницею — N+1 і необмежена складність довільного запиту (глибокий вкладений запит може коштувати дорого). І платиш ще однією валютою: єдиний `POST`-ендпойнт з непрозорим тілом **важко кешувати** — ти проміняв безкоштовний HTTP-кеш REST на свободу форми (частково відкупляються персистовані запити).

## Стиль 4 — черга: телеметрії відповідь не потрібна

Четверта межа зовсім іншої природи. Пригадаймо найпершу DH v0 — хаб раз на дві секунди читає температуру, і показання має долітати до хмари. Тут немає «панелі» й немає запиту: є **факт, який треба віддати й забути**. Якщо хаб на кожне показання робитиме синхронний виклик і чекатиме відповіді, то на кволому домашньому Wi-Fi він зависатиме на кожному вимірі, а щойно мережа моргне — губитиме дані.

Правильна форма — не питати, а покласти повідомлення в брокер і йти. Продюсер на хабі:

```python
import json, time
import paho.mqtt.client as mqtt

hub = mqtt.Client(client_id="hub-42")
hub.connect("broker.digitalhomes.io", 1883)
hub.loop_start()   # мережа крутиться у фоновому потоці; publish НЕ блокує

def on_reading(dev_id: str, value: float) -> None:
    topic = f"dh/home/42/{dev_id}/reading"
    payload = json.dumps({"v": value, "at": int(time.time() * 1000)})
    hub.publish(topic, payload, qos=1)   # поклав у буфер і повернувся — відповіді не чекаємо
```

Споживач у хмарі забирає, коли готовий, зовсім окремим життям:

```python
def on_message(_client, _userdata, msg) -> None:
    r = json.loads(msg.payload)
    dev = msg.topic.split("/")[3]
    store_reading(dev, r["v"], r["at"])   # МУСИТЬ бути ідемпотентним — див. нижче

ingest = mqtt.Client(client_id="ingest-1")
ingest.on_message = on_message
ingest.connect("broker.digitalhomes.io", 1883)
ingest.subscribe("dh/home/+/+/reading", qos=1)   # + — універсал на один рівень теми
ingest.loop_forever()
```

Виміри тут іншого роду — не round-trip панелі, а **час блокування продюсера**:

```text
publish() повертається за мікросекунди (лише кладе в out-буфер клієнта)
хаб не блокується й не чекає, чи хмара взагалі жива
синхронний POST натомість блокував би ≈ 150 мс на показання й падав би на розриві мережі
```

Але безплатного тут немає, ціна лише інша. Відповіді немає — отже, **ти ніколи не дізнаєшся синхронно, що показання опрацьоване**. Надійність купуєш не кодом статусу, а рівнем QoS плюс ідемпотентністю. `qos=1` MQTT — це *at least once*: доставку гарантовано, але за втраченим підтвердженням те саме повідомлення може прийти **двічі**. Тому споживач мусить бути ідемпотентним — дедуплікувати за парою «пристрій + мітка часу», щоб дубль не зіпсував історію. (Є ще `qos=0` — *at most once*, справжнє «кинув і забув» без гарантій, і `qos=2` — *exactly once* через чотирикроковий рукостискальний обмін, найдорожчий.) Це та сама межа зчеплення, лише в часі: черга роз'єднує сторони, а платою стають дублі, можливе переупорядкування й брокер як окрема критична інфраструктура.

## Підсумкова таблиця рішення

Усі чотири на одній фікстурі, поруч — і видно, що це чотири різні відповіді на чотири різні межі, а не змагання за один трон:

| Стиль | Round-trip на панель | По дроту | Зчеплення | Чия це межа |
|---|---|---|---|---|
| **REST-водоспад** | 21 запит / **3 хвилі глибини** (≈ 450 мс ∥) | ≈ 11.7 КБ (перебір) | вільне, ціною суворості | публічна: чужі некеровані клієнти, кеш задарма |
| **gRPC** (компаунд RPC) | **1** типізований (≈ 1 мс у ДЦ) | ≈ 1.6 КБ бінарно | тісне: спільний `.proto` | свій↔свій, гарячий шлях усередині |
| **GraphQL** | **1** (форма клієнта) | ≈ 0.8 КБ (рівно поля) | схема-моноліт; N+1 на сервері | багато різних екранів, один граф |
| **Черга / MQTT** | **—** (відповіді немає) | ≈ 40 Б на показання | роз'єднане в часі | телеметрія fire-and-forget |

Число round-trip і число байтів — не питання смаку, їх видно. І щойно вони на столі, суперечка «REST чи gRPC взагалі» просто зникає: у кожного рядка своя межа, і сили на ній самі диктують стовпчик. Зчеплення в цій таблиці — не абстракція; це прямо те [зчеплення](book:programming/coupling-cohesion), яке робить майбутню зміну дешевою або дорогою, тільки взяте на конкретну межу розмови.

## Типові пастки кожного стилю

Кожен стиль має вбудований спосіб зробити боляче — той самий, з якого його впередженість і росте. Знати їх наперед дешевше, ніж наступити.

**REST-водоспад.** Головна пастка — **балакучість**: наївний ресурсний спуск платить за глибину графа, і три-чотири рівні перетворюють екран на секунди очікування. Лік — компаунд-ендпойнт чи BFF під конкретний екран, вкладення (`?expand=devices`) або розріджені поля (`?fields=…`), але кожен такий лік фрагментує колись-єдиний контракт. Друга пастка — перебір жирних представлень; третя, підступніша, — спокуса «просто ще один ендпойнт під цей екран», від якого API розповзається в сотню вузькоспеціальних маршрутів.

**gRPC.** Найгостріша пастка — **браузер його не говорить**: без проксі-перекладача (Envoy) gRPC-Web у веб не працює, тож на публічну межу його тягти марно. Друга — **тіснота через спільний `.proto`**: обидві сторони мусять регенеруватися разом, а перевикористаний номер поля тихо трощить дані на дроті (номери — навічно). Третя, суто експлуатаційна: HTTP/2-з'єднання довгі й мультиплексовані, тож наївний L4-балансувальник приліплює всі потоки до одного бекенда — потрібне gRPC-свідоме балансування.

**GraphQL.** Пастка номер один — **N+1 резолверів**: без DataLoader-пакетування один гарний клієнтський запит кладе твою власну базу. Друга — **важко кешувати**: єдиний `POST` з непрозорим тілом вибиває безплатний крайовий кеш, тож потрібні персистовані запити. Третя — **необмежена складність запиту як поверхня атаки**: глибокий вкладений запит може бути навмисне дорогим, тому ставлять ліміти глибини й вартості. І четверта — одна велика схема стає точкою зчеплення, яку правлять усі команди водночас.

**Черга / MQTT.** Найковзкіша пастка — **немає відповіді, отже, немає синхронного «готово»**: надійність доводиться будувати з *at-least-once* плюс ідемпотентного споживача, а не з коду статусу. Звідси друга — **дублі й переупорядкування як норма** (`qos=1` доставляє принаймні раз), які споживач мусить терпіти. Третя — **брокер стає критичною інфраструктурою** з власною доступністю, утриманням і політикою тиску (back-pressure). Четверта — **діагностика непряма**: немає наскрізного стек-трейсу через розрив, тож рятують лише простежувані ідентифікатори повідомлень.

![Порівняння обертів до сервера, щоб намалювати ту саму панель: угорі REST-водоспад — три послідовні хвилі (дім, потім 5 кімнат паралельно, потім 15 пристроїв паралельно), кожна хвиля 150 мс, разом близько 450 мс, бо клієнт платить за глибину графа; унизу GraphQL і компаунд-gRPC — один оберт близько 150 мс, бо форма приходить за один захід.](/root/course/progarch/api-style-choice/img/roundtrip-cascade.svg)

*Той самий граф, та сама фікстура — а число обертів різне не через «швидкість» стилю, а через те, хто визначає форму відповіді: REST-водоспад долає граф рівень за рівнем і платить за глибину, зібрана форма забирає його за один захід.*

Ось що дає ця практика поверх будь-якої суперечки: перш ніж воювати за стиль, виміряй **свій** граф — його глибину й розмір відповіді — на **своїй** межі. Глибина графа кличе зібрану форму (GraphQL чи компаунд-ендпойнт); гарячий внутрішній шлях кличе типізований gRPC; факт без потреби у відповіді кличе чергу; публічна некерована юрба кличе звичайний REST з його безплатним кешем. Стиль обереться майже сам — щойно на столі опиняться числа, а не гасла.
