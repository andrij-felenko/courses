# ⚙️ Дві брами в одному обробнику

Крок розвів дві межі словами: автентифікація питає «хто ти?», авторизація — «що саме тобі можна з оцим?». Слова — добра опора для думки, але діру в безпеці відкриває не слово, а рядок коду, якого немає. Тож візьмімо звичайний обробник запиту Digital Homes, спершу зліпимо його так, як він народжується в поспіху — з однією брамою, — і на власні очі побачимо, як Оля читає термостат Марти. А тоді розділимо брами, доростимо другу від грубого порівняння власника до ролей дому й пройдемося пастками, на яких вона тихо зникає знову.

Мова тут не про регістри й гарячий шлях, а про форму серверного маршруту — тож беремо дві мови, якими веб-бекенд і пишуть: TypeScript на Express (брама як мідлвар) і Python на FastAPI (брама як залежність). Обидві — ідіоматично; форма однакова, і саме тому корисно бачити її двічі: те, що лишається спільним, і є суть, а не примха фреймворка.

## Задача

Випишімо фікстуру точно, бо на неточному сценарії й висновок був би неточний. Ендпойнт — `GET /homes/:id/thermostat`: віддати показ термостата дому за його `id`. У хмарі два доми:

```
H-olya    власник: Оля
H-marta   власник: Марта
```

І членство — хто в якому домі та з якою роллю:

```
Оля    — у H-olya,  роль founder (засновниця)
Гриць  — у H-olya,  роль guest   (запрошений гість)
Оля    — у H-marta: НЕМАЄ ЗАПИСУ
```

Ролі несуть різне право на дію. Дій рівно три, і вони ростуть за силою: `read` (читати показ), `write` (керувати — крутити уставку), `manage` (врядувати — заводити й виганяти членів, знести дім). Чого ми хочемо від правильної системи, розписано наперед, і кожен рядок цієї таблиці ми потім проженемо крізь код:

```
Оля   GET  H-olya/thermostat   → 200   (засновниця читає свій дім)
Оля   PUT  H-olya/thermostat   → 204   (засновниця керує)
Гриць GET  H-olya/thermostat   → 200   (гість читати може)
Гриць PUT  H-olya/thermostat   → 403   (гість керувати НЕ може)
Оля   GET  H-marta/thermostat  → 403   (у домі Марти вона ніхто)
```

Зверни увагу: три різні відповіді на **той самий** ендпойнт від **тієї самої** автентифікованої Олі. Це і є те, чого автентифікація сама дати не вміє: вона знає, що це Оля, — і мовчить про те, чи можна **їй** зробити **це** над **цим**. Уся робота нижче — навчити обробник ставити друге питання й відповідати на нього по-різному залежно від дому, ролі та дії.

## Баговий обробник: сама лише перша брама

Ось як маршрут народжується, коли про друге питання ще ніхто не думає. Автентифікацію ставлять на краю — раз, мідлваром чи залежністю, — вона перетворює токен на суб'єкта. А далі обробник бере `id` з адреси, піднімає дім і віддає. Виглядає завершено. Насправді — ні.

:::tabs
```ts
// ── Домен ────────────────────────────────────────────────
type Subject = { id: string };
type Role    = "guest" | "family" | "founder";
type Action  = "read"  | "write"  | "manage";
type Home    = { id: string; ownerId: string };

// Express.Request доповнюємо полем subject (його ставить автентифікація)
declare global {
  namespace Express { interface Request { subject?: Subject } }
}

// Автентифікація — на краю, раз на запит: токен → суб'єкт
function authenticate(req: Request, res: Response, next: NextFunction) {
  const subject = verifyToken(req.header("authorization"));
  if (!subject) {                                    // немає / хибний / протух
    res.set("WWW-Authenticate", "Bearer").status(401).end();
    return;
  }
  req.subject = subject;
  next();
}

// ⛔ БАГ: перевірено лише «хто», не «що саме йому можна»
app.get("/homes/:id/thermostat", authenticate, (req, res) => {
  const home = homes.get(req.params.id);             // :id — рядок від клієнта
  if (!home) return res.status(404).end();
  res.json(readThermostat(home));                    // ← другої брами немає
});
```
```py
from dataclasses import dataclass
from fastapi import FastAPI, Depends, HTTPException, Request

app = FastAPI()

# ── Домен ────────────────────────────────────────────────
@dataclass(frozen=True)
class Subject:
    id: str

@dataclass(frozen=True)
class Home:
    id: str
    owner_id: str

Role   = str   # "guest" | "family" | "founder"
Action = str   # "read"  | "write"  | "manage"

# Автентифікація — на краю, залежністю: токен → суб'єкт
def current_subject(request: Request) -> Subject:
    subject = verify_token(request.headers.get("authorization"))
    if subject is None:                              # немає / хибний / протух
        raise HTTPException(401, headers={"WWW-Authenticate": "Bearer"})
    return subject

# ⛔ БАГ: спитано лише «хто», не «що саме йому можна»
@app.get("/homes/{home_id}/thermostat")
def get_thermostat(home_id: str, subject: Subject = Depends(current_subject)):
    home = homes.get(home_id)                        # home_id — рядок від клієнта
    if home is None:
        raise HTTPException(404)
    return read_thermostat(home)                     # ← другої брами немає
```
:::

Пройдімо цим кодом Олю, що просить `GET /homes/H-marta/thermostat`. `authenticate` перевіряє токен — суб'єкт Оля, справжня, `next()`. Обробник бере `req.params.id` — рядок `"H-marta"` — і піднімає за ним дім. Дім є, `404` не спрацював. `readThermostat` віддає показ. Двісті. Оля щойно прочитала термостат Марти, і жоден рядок не збрехав: токен дійсний, `id` правильно сформований, сервер зробив рівно те, що написано.

Уся біда — в одному слові з двох, якими названо `id`. Клієнт **сам** називає об'єкт (`H-marta`), а сервер вживає це ім'я **прямо**, щоб дістати річ, — не переклавши його на питання «а цьому запитувачеві вона належить?». Це і є [горизонтальна ескалація через пряме посилання на об'єкт (IDOR)](root:progarch/idor-horizontal-escalation): крок убік, до сусіда на тому самому рівні влади, крізь перевірку, якої не написали. І це не рідкісна екзотика: у зведенні OWASP Top 10 2021 категорія «зламане керування доступом» (Broken Access Control) стоїть **першою**, і саме забута перевірка права на об'єкт дає в ній найбільше випадків — категорія з найбільшою кількістю знахідок у всьому наборі даних. *(Статус: усталений факт за даними OWASP; A01:2021 піднялася туди з п'ятого місця редакції 2017 року.)*

## Друга брама: окремо, пообʼєктно, після завантаження

Полагодити це — дописати другу браму. Але спершу відповімо на питання, яке вирішує все інше: **де** їй стояти? Спокуса — почепити її туди ж, де автентифікацію: при дверях, глобальним мідлваром перед маршрутом. І тут криється пастка, варта окремого малюнка.

![Конвеєр запиту: запит із :id у URL → автентифікація при дверях (знає лише «хто») → завантажити дім за id (аж тепер відомі власник і члени) → брама авторизації can(суб., дія, дім) → обробник, що дістає вже авторизований дім. Червона пунктирна гілка вниз від дверей до червоної рамки «брама ТУТ — сліпа: є лише рядок id, власник ще невідомий» з хрестиком](/root/course/progarch/auth-vs-authz-boundary/img/gate-placement.svg)

*При дверях у нас на руках лише рядок `id` — ім'я об'єкта, а не сам об'єкт. Хто ним володіє, хто в ньому член і з якою роллю — усе це живе в базі й з'являється аж після завантаження. Тож брама сидить не при вході, а на крок далі: спершу підняти об'єкт, і вже тоді, тримаючи в одній руці суб'єкта, а в другій — обʼєкт, питати про право.*

Ось той самий обробник із дописаною другою брамою. `canRead` починаємо якнайпростіше — грубим порівнянням власника; воно ще неправильне для дому з кількома мешканцями, зате гранично ясно показує **місце** брами:

:::tabs
```ts
function canRead(subject: Subject, home: Home): boolean {
  return home.ownerId === subject.id;                // поки що — тільки власник
}

app.get("/homes/:id/thermostat", authenticate, (req, res) => {
  const home = homes.get(req.params.id);
  if (!home) return res.status(404).end();
  if (!canRead(req.subject!, home))                  // ← друга брама, ПІСЛЯ завантаження
    return res.status(403).end();
  res.json(readThermostat(home));
});
```
```py
def can_read(subject: Subject, home: Home) -> bool:
    return home.owner_id == subject.id               # поки що — тільки власник

@app.get("/homes/{home_id}/thermostat")
def get_thermostat(home_id: str, subject: Subject = Depends(current_subject)):
    home = homes.get(home_id)
    if home is None:
        raise HTTPException(404)
    if not can_read(subject, home):                  # ← друга брама, ПІСЛЯ завантаження
        raise HTTPException(403)
    return read_thermostat(home)
```
:::

Тепер Оля з `H-marta` натикається на `canRead`: `home.ownerId` — це `"Марта"`, `subject.id` — `"Оля"`, не рівні, `403`. Дім Марти в безпеці, і полагодив його рівно один рядок. Помітне й головне: цій брамі потрібне те, чого автентифікації не треба, — **об'єкт**. Автентифікації досить самого доказу; авторизації потрібна трійця «суб'єкт, дія, обʼєкт», а обʼєкт з'являється тільки після завантаження. Тому вона й не може жити при дверях — двері ще не знають, який дім ти зараз попросиш.

## Як росте `can`: від власника до ролей дому

Грубе порівняння власника рятує від витоку, але робить дім однолюдним: у ньому може щось робити лише той, чий `id` збігся з `ownerId`. А дім Digital Homes живий — у ньому є родина, є запрошений гість, згодом буде орендар. Усі вони не власники за полем `ownerId`, і всіх їх грубе порівняння викидає геть. Значить, `canRead` мусить вирости: від питання «це власник?» до питання «яка в цього суб'єкта **роль** у цьому домі й що ця роль дозволяє?».

![Таблиця ролей дому DH проти дій. Рядки: гість, сім'я/орендар, засновник. Стовпці: читати, керувати, врядувати. Гість — читати так, решта ні. Сім'я — читати й керувати так, врядувати ні. Засновник — усі три так. Згори стрілка еволюції: було «дім = один власник, subject.id == home.ownerId» → стало «членство + роль (ця таблиця)». Знизу: не член дому → жодного рядка → відмова fail-closed](/root/course/progarch/auth-vs-authz-boundary/img/role-matrix.svg)

*Одне грубе порівняння власника було однією клітиною в кутку цієї таблиці. Ролі розгортають її повністю: кожна роль відмикає свій набір дій, а хто не член дому — того в таблиці немає взагалі, і за замовчуванням він дістає відмову.*

У коді ця таблиця — маленьке відображення «роль → множина дозволених дій», а `can` стає трьома рядками: дістати роль суб'єкта в цьому домі, а тоді спитати, чи є задана дія в наборі цієї ролі. Немає ролі — немає й членства — відмова:

:::tabs
```ts
// роль → дозволені дії (гість лише читає, сім'я керує, засновник — усе)
const GRANTS: Record<Role, ReadonlySet<Action>> = {
  guest:   new Set(["read"]),
  family:  new Set(["read", "write"]),
  founder: new Set(["read", "write", "manage"]),
};

function can(subject: Subject, action: Action, home: Home): boolean {
  const role = memberships.roleOf(subject.id, home.id);   // Role | undefined
  if (!role) return false;                                // не член → відмова
  return GRANTS[role].has(action);
}
```
```py
# роль → дозволені дії (гість лише читає, сім'я керує, засновник — усе)
GRANTS: dict[Role, set[Action]] = {
    "guest":   {"read"},
    "family":  {"read", "write"},
    "founder": {"read", "write", "manage"},
}

def can(subject: Subject, action: Action, home: Home) -> bool:
    role = memberships.role_of(subject.id, home.id)   # Role | None
    if role is None:
        return False                                  # не член → відмова
    return action in GRANTS[role]
```
:::

Тепер той самий `can` відповідає по-різному на всі рядки нашої таблиці задачі. Гриць у `H-olya` має роль `guest`; `can(Гриць, "read", H-olya)` — `read` є в наборі гостя, `true`; `can(Гриць, "write", H-olya)` — `write` у наборі гостя немає, `false`, а обробник обертає це на `403`. Оля в `H-olya` — `founder`, їй усі три дії дозволені. Оля в `H-marta` — `roleOf` не знаходить членства, повертає нічого, `can` одразу `false`. Одна функція, дом'єнна таблиця з трьох рядків — і всі п'ять очікуваних відповідей сходяться. Що важливо: коли завтра з'явиться роль `tenant` (орендар) з якимось своїм набором, змінюється **один рядок** таблиці `GRANTS`, а не десяток розкиданих `if`. Саме заради цього рішення тримають в одній функції — це вже поріг [моделей авторизації](book:programming/authorization-models), куди веде наступний крок; тут нам досить бачити, що `can` — одне ясне місце, а не звичка копіювати перевірку.

## Брама, яку не можна забути

У версії вище є прихована слабина, і вона не в `can`, а в тому, що браму **треба не забути покликати** в кожному обробнику. Ми написали `canRead` на `GET`. Завтра колега додає `PUT /homes/:id/thermostat`, щоб міняти уставку, — і в поспіху копіює лише щасливий шлях, без виклику `can(..., "write", ...)`. Ендпойнт працює, демо блищить, а Гриць-гість тим часом крутить термостат у чужому домі. Брама є в системі — просто на цьому маршруті її забули.

Ліки — зробити виклик брами **структурним**, а не доброю волею того, хто писав маршрут. В Express це фабрика мідлвару: вона вантажить дім, перевіряє право на задану дію й кладе вже авторизований дім далі за потоком — у `res.locals`. У FastAPI ще чистіше: [залежність](book:programming/dependency-injection), що вантажить і авторизує, **повертає сам обʼєкт** — і обробник дістає його параметром. А отже, без проходу крізь браму об'єкта в обробнику просто **немає** з чого почати:

:::tabs
```ts
// Фабрика брами: мідлвар, що вантажить дім і пускає лише з правом на дію.
// Обробник дістає вже авторизований дім у res.locals — забути перевірку ніде.
function requireHome(action: Action): RequestHandler {
  return (req, res, next) => {
    const home = homes.get(req.params.id);
    if (!home) return res.status(404).end();
    if (!can(req.subject!, action, home)) return res.status(403).end();
    res.locals.home = home;                          // далі — вже авторизований обʼєкт
    next();
  };
}

app.get("/homes/:id/thermostat", authenticate, requireHome("read"), (req, res) => {
  res.json(readThermostat(res.locals.home));         // право вже перевірено вище
});
app.put("/homes/:id/thermostat", authenticate, requireHome("write"), (req, res) => {
  setThermostat(res.locals.home, req.body.target);
  res.status(204).end();                             // сюди Гриць-гість не дійде
});
```
```py
# Фабрика брами: залежність, що вантажить дім і пускає лише з правом.
# Обробник ОДЕРЖУЄ вже авторизований дім параметром — інакше його просто нема.
def authorized_home(action: Action):
    def dep(home_id: str, subject: Subject = Depends(current_subject)) -> Home:
        home = homes.get(home_id)
        if home is None:
            raise HTTPException(404)
        if not can(subject, action, home):
            raise HTTPException(403)
        return home
    return dep

@app.get("/homes/{home_id}/thermostat")
def get_thermostat(home: Home = Depends(authorized_home("read"))):
    return read_thermostat(home)                     # дім тут ⇒ право вже перевірено

@app.put("/homes/{home_id}/thermostat")
def put_thermostat(target: float, home: Home = Depends(authorized_home("write"))):
    set_thermostat(home, target)
    return {"ok": True}                              # сюди Гриць-гість не дійде
```
:::

Зверни увагу на зсув, який тут стався. У першій версії безпека трималася на **пам'яті** програміста: не забудь дописати `if (!can(...))`. У цій — на **типі й потоці**: обробник `put_thermostat` фізично не може виконатися, поки залежність `authorized_home("write")` не поверне дім, а вона не поверне його без успішного `can`. Забути перевірку стало **важче, ніж її зробити**, — і це головна різниця між кодом, що «зазвичай безпечний», і кодом, безпечним за побудовою. Політику ми лишили в одному місці (`can` і таблиця `GRANTS`), а от її **застосування** притягли до кожного маршрута так, що обійти його треба свідомо.

## Складність і пастки

Дві брами в коді — це не дві перевірки поспіль, а рішення про **шари, місця й час**. Ось де воно найчастіше ламається.

### Перевірка не в тому шарі

Ми вже бачили верхній край цієї пастки: авторизацію об'єкта тягне при двері, у глобальний мідлвар, де на руках лише `id`, а не сам дім. Такий мідлвар або не може вирішити (власник ще невідомий), або мусить сам піти в базу — і тоді ти вантажиш дім двічі. Є й дзеркальна крайність: заштовхати перевірку **вглиб**, у шар доступу до бази, де зручно тримати запити, але незручно дістати суб'єкта з HTTP-контексту, — і тоді суб'єкта протягують крізь п'ять шарів параметром або, що гірше, беруть з глобальної змінної. Правильний шар — **межа обробника, одразу після завантаження**: це єдине місце, де суб'єкт (з краю) і обʼєкт (зі сховища) природно лежать поруч в одній руці. Не вище — бо вище немає обʼєкта; не нижче — бо нижче немає суб'єкта.

І тонкість, яку легко переплутати з «не повторюйся»: **рішення** тримай в одному місці (функція `can`), але **застосовувати** його однаково мусиш на кожній межі. DRY стосується політики, не її викликів. Зекономити на самих викликах — це і є забута брама з попереднього розділу.

### Забута брама на сусідньому маршруті

Це продовження тієї ж думки, але варте окремого імені, бо трапляється найчастіше. Перевірка живе **на маршруті**, а маршрути ростуть. Написав `GET` з `read` — потім хтось додає `PUT` з `write`, `DELETE` з `manage`, `GET /homes/:id/history`, `GET /homes/:id/members` — і на котромусь новому забуває покликати `can`. Фабрика-мідлвар і залежність-обгортка з попереднього розділу і є структурна відповідь: коли єдиний спосіб дістати дім в обробнику — це попросити його в брами, забути перевірку вже не виходить непомітно. Додатковий страхувальник — **fail-closed**: типовий шлях у роутері хай **відмовляє**, а прохід відкриває лише свідомо повішена брама. Тоді новий маршрут без брами дає чесну відмову, а не тихий витік.

### TOCTOU: вікно між «перевірили» і «зробили»

Є підступніший розрив — у **часі**. Абревіатура TOCTOU, від англ. *time of check to time of use*, «від миті перевірки до миті вжитку», називає вікно між тим, як ти спитав право, і тим, як ним скористався. Якщо у цьому вікні світ змінився — рішення застаріло.

![Вісь часу одного запиту. t0 — завантажили дім, Оля тут роль сім'я. t1 — ПЕРЕВІРКА can(Оля, write) дала так. Далі червона смуга «вікно TOCTOU», у якій Марта відкликає Олю. t2 — ДІЯ apply write виконується, хоча рішення вже застаріле. Знизу дві оборони: не перечитувати обʼєкт за id після перевірки; злити перевірку в саму дію через UPDATE WHERE EXISTS](/root/course/progarch/auth-vs-authz-boundary/img/toctou-window.svg)

*Перевірка сказала «так» о t1, коли Оля ще була в домі. У вікні між перевіркою й дією її членство відкликали — а команда все одно застосувалася о t2, спираючись на протухле «так».*

У наших обробниках вікно вузьке, але не нульове, і воно ширшає, щойно між перевіркою й дією з'являється повільна робота — мережевий виклик, черга, друге читання. Дві оборони. Перша дешева: **перевіряй і дій на тому самому завантаженому обʼєкті**, не перечитуй його за `id` після перевірки — повторне читання може повернути вже інший, змінений рядок, і твоє «так» стосуватиметься не того, що ти зрештою чіпаєш. Друга надійніша для запису: **злий перевірку в саму дію**, щоб «перевірити» й «зробити» стали одним неподільним висловом. У базі це природно — умову права вкладають прямо в `UPDATE`:

```sql
-- перевірка й дія — одним висловом; вікна між ними немає
UPDATE thermostat SET target = :target
WHERE home_id = :home
  AND EXISTS (SELECT 1 FROM membership
              WHERE subject_id = :subject AND home_id = :home
                AND role IN ('family', 'founder'));
-- 0 змінених рядків ⇒ права немає (або вже відкликано) ⇒ 403
```

Тут немає двох митей — є одна. Якщо о цій миті членство Олі вже зникло, `EXISTS` не справджується, оновлюється нуль рядків, і обробник чесно віддає `403`. Той самий лічильник версій, що ловить конфлікти при [оптимістичному блокуванні](book:programming/optimistic-locking), закриває і це вікно: перевіряй право під тією ж умовою версії, під якою й пишеш.

### Масовий ендпойнт: фільтр у запиті, не в памʼяті

Останнє місце, де брама зраджує, — це список. `GET /homes` має віддати доми, до яких у суб'єкта є доступ. Наївний хід — підняти **всі** доми й відсіяти зайві в пам'яті тим самим `can`:

:::tabs
```ts
// ✗ підняти все, відсіяти в памʼяті — повільно й крихко
app.get("/homes", authenticate, (req, res) => {
  const mine = homes.all().filter(h => can(req.subject!, "read", h));
  res.json(mine);
});

// ✓ авторизація як умова запиту — чужі рядки не залишають БД
app.get("/homes", authenticate, (req, res) => {
  res.json(homes.listForMember(req.subject!.id));    // JOIN membership …
});
```
```py
# ✗ підняти все, відсіяти в памʼяті — повільно й крихко
@app.get("/homes")
def list_homes(subject: Subject = Depends(current_subject)):
    return [h for h in homes.all() if can(subject, "read", h)]

# ✓ авторизація як умова запиту — чужі рядки не залишають БД
@app.get("/homes")
def list_homes(subject: Subject = Depends(current_subject)):
    return homes.list_for_member(subject.id)         # SELECT … JOIN membership
```
:::

Фільтр у пам'яті хибний одразу з трьох боків. Він **повільний**: тягне з бази чужі доми, щоб їх викинути, — на мільйоні домів це мільйон дарма піднятих рядків. Він **протікає**: чужі дані вже вилетіли зі сховища в застосунок, і досить одного `console.log`, помилки з дампом чи лічильника, порахованого до фільтра («X домів усього»), щоб вони просочилися назовні. І він **крихкий**: пагінація, `count`, сортування рахуються по всьому набору, а не по твоєму, — і зраджують саме там, де ти певен, що вже відсіяв. Правильно — зробити авторизацію **умовою самого запиту**: `WHERE home.id IN (SELECT home_id FROM membership WHERE subject_id = :subject)`. Предикат права стає частиною `SELECT`, і чужий рядок узагалі не залишає бази. Для масштабу це та сама ізоляція сусідів, що й [мультиарендність](book:programming/tenant-isolation): не «підняти й відсіяти», а «з самого початку не піднімати чуже».

## Що лишається в руках

Дві межі в коді — це не дві перевірки одна за одною, а одна брама, поставлена свідомо: **пообʼєктно**, **після завантаження**, на **трійці** «суб'єкт, дія, обʼєкт», за замовчуванням **зачинена**. Прибери її — і дістанеш баговий обробник із однією брамою, де Оля читає дім Марти не тому, що зламали автентифікацію, а тому, що другої перевірки немає. Постав грубо — і дім стане однолюдним; доростити `can` від порівняння власника до ролей дому — це змінити одну функцію й одну таблицю, а не розсипати `if`. А далі починаються пастки не про «чи перевіряти», а про «де, коли і як»: не в тому шарі, забута на сусідньому маршруті, протухла у вікні TOCTOU, розмита на масовому списку. Спосіб їх пережити один і той самий — зробити виклик брами структурним, а не покладеним на пам'ять: хай обробник не має обʼєкта, поки не пройде крізь неї. Чим саме відповідати на `can` — порівнянням, ролями, політиками над атрибутами — це вже наступний крок; тут ми довели, що друге питання не тільки існує, а й має в коді своє точне місце, час і форму.
