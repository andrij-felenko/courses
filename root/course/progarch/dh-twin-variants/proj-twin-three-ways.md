# ⚙️ Той самий твін — трьома формами правди, крізь один сценарій

Три твіни ми вже звели до трьох дієслів: актор кладе команду в пошту (`tell`), база читає-міняє-пише рядок (`put`), журнал дописує факт (`append`). Дієслово — це обіцянка; тут ми беремо кожну обіцянку й доводимо до робочого коду, що лягає на диск і запускається. А тоді робимо єдине, що чесно розрізняє три форми правди: женемо всі три крізь **один і той самий сценарій** і дивимося, де вони розходяться.

Сценарій навмисне жорстокий і короткий, бо саме на злам він і зроблений. На дім #42 прилітають **дві команди «замкни» майже водночас** — від двох сесій, що не знають одна про одну. І щойно вони лягли, **вузол, який тримав цей дім, гине**. Дві прості події — і кожна б'є в окреме місце. Дві команди водночас питають: хто не дасть їм злитися й затерти одна одну? Смерть вузла питає: а де після воскресіння правда про дім?

Ось дві осі, на яких ми поміряємо всіх трьох, і більше ні на яких: **серіалізація** (хто боронить від гонки) і **відновлення** (хто переживе крах). Той самий вхід, ті самі два питання — три різні відповіді. І головний висновок, який ми намацаємо руками: різниця у відповідях тече не з бібліотеки, не з «TS проти Python», а з того, **де в кожному варіанті лежить правда**.

## Задача

Випишемо фікстуру точно, бо неточний сценарій дав би неточний висновок. У домі #42 є замок `entrance`. Стан замка у твіні — не просто «замкнено/відчинено», а трійка `{ bolt, version, lastCmd }`. `version` тут не прикраса: він рахує, **скільки команд уже застосовано**, і саме він робить видимою гонку. Такий лічильник у справжніх системах потрібен для [ідемпотентності й виявлення конфліктів](book:programming/optimistic-locking) — щоб відкинути дубль чи спізнілу команду й не застосувати її двічі. Домовмося, що замок уже прожив трохи життя: на старті сценарію `version = 5`.

Тепер сам сценарій, крок за кроком:

1. Сесія A шле `{ kind: "lock", seq: 6, by: "A" }`.
2. Сесія B майже тієї самої миті шле `{ kind: "lock", seq: 7, by: "B" }`.
3. Обидві мають бути застосовані — після них чесний твін мусить показувати `version = 7`, `bolt = locked`, а `lastCmd` — котрусь із двох (порядок хай вирішить сама конструкція, аби він був **якийсь один** і не загубив жодної команди).
4. Одразу по тому вузол із домом #42 падає. Ми його піднімаємо й перечитуємо твін.

![Ліворуч твін дому #42 із замком entrance; згори й знизу дві сесії шлють «замкни» (seq 6 і seq 7) майже одночасно, стрілки збігаються на твіні; далі стрілка часу впирається в символ краху «вузол гине»; праворуч дві питання-осі: ① гонка — обидві команди враховано (version = 7)? ② крах — правда вціліла після воскресіння?](img/scenario-fixture.svg)
*Один вхід для всіх трьох варіантів. Дві «замкни» майже водночас ставлять питання про серіалізацію; смерть вузла — питання про відновлення. Ми не хвалитимемо кожен варіант його мірками, а проженемо всіх трьох крізь ці самі дві події й порівняємо, що вони покажуть на виході.*

Зверни увагу на підступність вибору «дві **однакові** команди». Обидві кажуть «замкни», тож фінальний `bolt` вийде `locked` за будь-якого порядку — двері фізично опиняться там, де треба, навіть якщо одна команда згубиться. Саме тому `version` тут неоціненний: він викриє загублену команду там, де стан замка її милосердно приховав. А досить одній із двох бути «відчини» — і та сама гонка, що зараз лише зіпсує лічильник, лишить двері у стані, якого користувач **не** просив. Ми міряємо на нешкідливій парі те, що на різних командах стає небезпекою.

## Варіант А — актор: пошта і є черга

Актор тримає стан дому [живим об'єктом у пам'яті](book:programming/actor-model), а єдиний спосіб з ним заговорити — покласти команду в пошту. З цього однієї властивості серіалізація випадає задарма: пошта і є черга, а актор бере з неї по одному повідомленню й доводить кожне до кінця, перш ніж узяти наступне.

:::tabs
```ts
type LockState = { bolt: "locked" | "unlocked"; version: number; lastCmd: string };
type Cmd = { kind: "lock" | "unlock"; seq: number; by: string };

const SNAP_EVERY = 100;   // знімок на диск — раз на сотню команд

class HomeActor {
  private box: Cmd[] = [];          // ← пошта: єдина черга дому
  private sinceSnapshot = 0;

  constructor(private homeId: string,
              private lock: LockState = { bolt: "unlocked", version: 5, lastCmd: "" }) {}

  // ЄДИНИЙ вхід ззовні: покласти команду в пошту й піти. Стан ніхто не чіпає напряму.
  tell(cmd: Cmd): void { this.box.push(cmd); }

  // ЄДИНИЙ виконавець дому: бере по одному, доводить до кінця, і лише тоді наступне.
  // (у справжньому рантаймі цей цикл крутиться безперервно, сам собою.)
  drain(): void {
    for (let cmd = this.box.shift(); cmd; cmd = this.box.shift()) this.apply(cmd);
  }

  private apply(cmd: Cmd): void {
    // жодного read-modify-write: стан ось тут, у полі, і виконавець його один
    this.lock = {
      bolt: cmd.kind === "lock" ? "locked" : "unlocked",
      version: this.lock.version + 1,
      lastCmd: `${cmd.by}#${cmd.seq}`,
    };
    if (++this.sinceSnapshot >= SNAP_EVERY) {
      saveSnapshot(this.homeId, this.lock);   // періодичний знімок на диск
      this.sinceSnapshot = 0;
    }
  }

  snapshot(): LockState { return this.lock; }
}

// сценарій: дві «замкни» майже водночас — обидві лягають у ту саму пошту
const a = new HomeActor("home42");
a.tell({ kind: "lock", seq: 6, by: "A" });
a.tell({ kind: "lock", seq: 7, by: "B" });   // у скриньці тепер ДВІ
a.drain();                                    // виконавець бере по одній: version 5 → 6 → 7
```
```py
from collections import deque
from dataclasses import dataclass

SNAP_EVERY = 100                     # знімок на диск — раз на сотню команд

@dataclass
class LockState:
    bolt: str = "unlocked"
    version: int = 5
    last_cmd: str = ""

class HomeActor:
    def __init__(self, home_id, lock=None):
        self.home_id = home_id
        self.lock = lock or LockState()
        self._box = deque()          # ← пошта: єдина черга дому
        self._since_snapshot = 0

    # ЄДИНИЙ вхід ззовні: покласти команду в пошту й піти. Стан ніхто не чіпає напряму.
    def tell(self, cmd):
        self._box.append(cmd)

    # ЄДИНИЙ виконавець дому: бере по одній, доводить до кінця, і лише тоді наступну.
    # (у справжньому рантаймі цей цикл крутиться безперервно, сам собою.)
    def drain(self):
        while self._box:
            self._apply(self._box.popleft())

    def _apply(self, cmd):
        # жодного read-modify-write: стан ось тут, і виконавець його один
        self.lock = LockState(
            bolt="locked" if cmd["kind"] == "lock" else "unlocked",
            version=self.lock.version + 1,
            last_cmd=f"{cmd['by']}#{cmd['seq']}",
        )
        self._since_snapshot += 1
        if self._since_snapshot >= SNAP_EVERY:
            save_snapshot(self.home_id, self.lock)     # періодичний знімок на диск
            self._since_snapshot = 0

# сценарій: дві «замкни» майже водночас — обидві лягають у ту саму пошту
a = HomeActor("home42")
a.tell({"kind": "lock", "seq": 6, "by": "A"})
a.tell({"kind": "lock", "seq": 7, "by": "B"})   # у скриньці тепер ДВІ
a.drain()                                        # виконавець бере по одній: version 5 → 6 → 7
```
:::

Придивися, де тут поділася гонка. Її **нема куди вставити**. Стан `lock` — приватне поле, і торкається його рівно один виконавець — цикл `drain`. Обидві команди лягають у ту саму пошту, а виконавець бере їх по одній і доводить кожну до кінця, перш ніж узяти наступну, тож тіла двох `apply` ніколи не переплітаються. Тому `version` чесно росте 5 → 6 → 7, і замок не потрібен: замикати нема від кого, бо спільного стану, за який змагатися, просто не існує. Це не наша хитрість, а рідна властивість моделі: у Microsoft Orleans, наприклад, кожен ґрейн виконує свої виклики строго по одному від початку до кінця, і документація каже про це прямо — немає потреби в замках чи іншій синхронізації проти станів гонки. Серіалізацію купуєш не кодом, а **формою**.

А тепер друга вісь — крах. Стан живе в пам'яті, отже, зі смертю вузла він зникає весь. Піднімаємо актора зі знімка:

:::tabs
```ts
// воскресіння: RAM зникла разом із вузлом. Що є на диску — останній знімок.
async function reviveActor(homeId: string): Promise<HomeActor> {
  const snap = await loadSnapshot(homeId);      // { bolt, version } — стан на мить знімка
  return new HomeActor(homeId, snap ?? INITIAL);
}
```
```py
# воскресіння: RAM зникла разом із вузлом. Що є на диску — останній знімок.
def revive_actor(home_id):
    snap = load_snapshot(home_id)               # стан на мить знімка
    return HomeActor(home_id, snap or LockState())
```
:::

І ось де актор показує свою ціну без прикрас. Знімок ми робимо раз на сотню команд, тож на диску лежить `version = 5` — стан **до** наших двох «замкни». Крах між знімком і наступним знімком означає просте й неприємне: воскреслий актор знає лише `version = 5`, а обидві команди **втрачено**. Періодичний знімок — це вікно втрати завширшки в період знімка.

Лікують це тим, що актор рідко стоїть сам: під ним тримають довговічну підкладку — журнал, куди кожну команду дописують **перед** застосуванням, і тоді воскресіння стає «знімок плюс перегравання хвоста». Це рівно те, що робить, приміром, Akka Persistence: актор відновлюється, переграваючи журнальовані події, а знімки лише скорочують перегравання. Але зверни увагу, що сталося: щоб зробити падіння дешевим, актор **позичив журнал у Варіанта В**. Чиста пам'ять швидка й серіалізує задарма, та за тривкість вона доплачує — або вікном втрати на знімках, або тим самим логом, що є серцем третього варіанта. [Робочий актор із обмеженою скринькою, наглядачем і доказом ізоляції на штучно отруєному пристрої](root:progarch/runtime-actors-variant/proj-dh-device-actor.md) ми вже збирали окремо — там видно, що надійність актора постачає рантайм, а не слово в назві бібліотеки.

## Варіант Б — рядок: правда на диску, гонку треба заборонити

Тут правда лежить рядком у [шардованій базі](root:progarch/dh-replicas), і кожна команда — це читання-зміна-запис того рядка. Тривкість дістається задарма: щойно транзакція зафіксована, рядок на диску. А от серіалізацію, яку актор мав із конструкції, тут доводиться **добудовувати руками** — бо наївний read-modify-write ховає в собі точнісінько ту гонку, від якої актор застрахований.

Спершу напишімо наївно — так, як пише кожен, доки його не вкусило:

:::tabs
```ts
// НАЇВНО: прочитали рядок, змінили, записали назад. Гонка ховається саме тут.
async function applyNaive(db: Db, homeId: string, cmd: Cmd): Promise<void> {
  const row = await db.get("device_state", homeId);          // read  (version = 5)
  row.bolt = cmd.kind === "lock" ? "locked" : "unlocked";    // modify
  row.version += 1;                                          //        (5 → 6)
  row.lastCmd = `${cmd.by}#${cmd.seq}`;
  await db.put("device_state", homeId, row);                 // write (version = 6)
}
// дві такі команди водночас: ОБИДВІ прочитали version=5, ОБИДВІ пишуть version=6.
// друга затерла першу — «загублене оновлення». version=6, а команд було дві.
```
```py
# НАЇВНО: прочитали рядок, змінили, записали назад. Гонка ховається саме тут.
def apply_naive(db, home_id, cmd):
    row = db.get("device_state", home_id)                    # read  (version = 5)
    row["bolt"] = "locked" if cmd["kind"] == "lock" else "unlocked"   # modify
    row["version"] += 1                                      #        (5 → 6)
    row["last_cmd"] = f"{cmd['by']}#{cmd['seq']}"
    db.put("device_state", home_id, row)                     # write (version = 6)
# дві такі команди водночас: ОБИДВІ прочитали version=5, ОБИДВІ пишуть version=6.
# друга затерла першу — «загублене оновлення». version=6, а команд було дві.
```
:::

Код бездоганний на око й **проходить кожен однопотоковий тест**: пусти команди одну за одною — версія чесно росте. Гонка прокидається лише коли дві команди справді накладаються в часі: сесія A читає `version = 5`, сесія B читає теж `version = 5` (перша ще не записала), обидві рахують `6`, обидві пишуть `6`. Друга команда затерла першу — це класичне **загублене оновлення** (lost update), і твін тепер каже, що бачив одну команду, хоч їх було дві. На двох «замкни» двері вціліли випадково; на «замкни» плюс «відчини» твін застряг би у стані, якого ніхто не просив.

Ліки — не «бути обережним», а зробити гонку структурно неможливою. Найдешевший спосіб — [версія рядка](book:programming/optimistic-locking): пиши лише тоді, коли `version` не змінилася з-під тебе, тобто порівняй-і-заміни (compare-and-swap) по стовпцю версії.

:::tabs
```ts
// ВЕРСІЯ РЯДКА (оптимістично): запис проходить, лише якщо version та сама, що прочитали
async function applyCas(db: Db, homeId: string, cmd: Cmd): Promise<void> {
  for (;;) {
    const row = await db.get("device_state", homeId);
    const changed = await db.update("device_state", {
      where: { homeId, version: row.version },               // ← умова CAS
      set: {
        bolt: cmd.kind === "lock" ? "locked" : "unlocked",
        version: row.version + 1,
        lastCmd: `${cmd.by}#${cmd.seq}`,
      },
    });
    if (changed === 1) return;        // ми виграли — рівно ми бумкнули version
    // changed === 0: хтось інший бумкнув version між нашим read і write → повторити
  }
}
```
```py
# ВЕРСІЯ РЯДКА (оптимістично): запис проходить, лише якщо version та сама, що прочитали
def apply_cas(db, home_id, cmd):
    while True:
        row = db.get("device_state", home_id)
        changed = db.update(
            "device_state",
            where={"home_id": home_id, "version": row["version"]},   # ← умова CAS
            set={
                "bolt": "locked" if cmd["kind"] == "lock" else "unlocked",
                "version": row["version"] + 1,
                "last_cmd": f"{cmd['by']}#{cmd['seq']}",
            },
        )
        if changed == 1:            # ми виграли — рівно ми бумкнули version
            return
        # changed == 0: хтось бумкнув version між read і write → повторити
```
:::

По суті це один рядок SQL, який робить читання-перевірку-запис атомарними в базі:

```sql
UPDATE device_state
   SET bolt = ?, version = version + 1, last_cmd = ?
 WHERE home_id = ? AND version = ?;        -- застосуй, лише якщо version не зрушила
-- вплинуло 0 рядків → хтось випередив → перечитай і спробуй знову
```

Тепер дві команди не можуть обидві виграти на `version = 5`: перша, чий `UPDATE` доходить, ставить `6`, друга бачить, що умова `version = 5` більше не збігається (вплинуло 0 рядків), перечитує `6` і робить `7`. Версія росте 5 → 6 → 7 — те саме, що актор дав безплатно, лише тут ми за це заплатили циклом-повтором. Альтернатива — песимістичний замок: `SELECT … FOR UPDATE` бере рядок під блокування на весь час транзакції, і друга команда чекає, поки перша відпустить. Оптимістично (версія) чи песимістично (замок) — але **без одного з двох рядок у базі до серіалізації команд глухий**.

Крах тут — найнудніша частина, і в цьому вся сила. Зафіксована транзакція вже на диску: база провела її крізь [журнал попереднього запису](book:programming/write-ahead-log) із fsync, тож `version = 7` пережило смерть вузла без жодного окремого «воскресіння». А якщо вузол упав **посеред** транзакції, вона відкотиться атомарно — жодної пів-команди, жодного напівзамкненого замка. Відновлення Варіанта Б — це відсутність відновлення: правда й так на диску.

## Варіант В — журнал: порядок дає лог

Третій варіант робить істиною не поточний стан, а [журнал подій](book:programming/event-sourcing): кожна команда — це дописаний у лог факт, а «як зараз» рахують згорткою (проєкцією) над логом. Серіалізацію тут дає сам лог: він присвоює кожному запису позицію, і ця позиція **і є** порядок.

:::tabs
```ts
type Event = { type: "Locked" | "Unlocked"; seq: number; by: string };

// ЗАПИС: дописати факт. Лог сам присвоює позицію — вона й є порядок.
async function record(log: Log, homeId: string, cmd: Cmd): Promise<void> {
  await log.append(homeId, {
    type: cmd.kind === "lock" ? "Locked" : "Unlocked",
    seq: cmd.seq, by: cmd.by,
  });                                  // durable: fsync до підтвердження
}

// ЧИТАННЯ: поточний стан = згортка журналу. «Як зараз» рахуємо, а не зберігаємо.
function apply(s: LockState, e: Event): LockState {
  return {
    bolt: e.type === "Locked" ? "locked" : "unlocked",
    version: s.version + 1,
    lastCmd: `${e.by}#${e.seq}`,
  };
}
function project(events: Event[]): LockState {
  return events.reduce(apply, INITIAL);
}
```

```py
# ЗАПИС: дописати факт. Лог сам присвоює позицію — вона й є порядок.
def record(log, home_id, cmd):
    log.append(home_id, {

        "seq": cmd["seq"], "by": cmd["by"],
    })                                 # durable: fsync до підтвердження

# ЧИТАННЯ: поточний стан = згортка журналу. «Як зараз» рахуємо, а не зберігаємо.
def apply(s, e):
    return LockState(
        bolt="locked" if e["type"] == "Locked" else "unlocked",
        version=s.version + 1,
        last_cmd=f"{e['by']}#{e['seq']}",
    )
def project(events):
    return reduce(apply, events, LockState())
```

Гонки на втрату тут нема з іншої причини, ніж в актора. Актор **не пускав** двох одночасно; лог пускає обидві, але `append` лише **дописує** — він фізично не може затерти чужий запис, як це робив наївний `put`. Дві «замкни» лягають у лог двома сусідніми позиціями, у якомусь одному порядку, і згортка над ними чесно дає `version = 7`. Порядок вирішує не наш код, а те, у якій послідовності лог прийняв дописи (єдиний писар на дім дає йому повний порядок — той самий єдиний писар, на якому [тримався твін на репліках](root:progarch/dh-replicas)).

Крах Варіанта В — його рідна стихія. Лог тривкий (кожен `append` доходить до диска перед підтвердженням), тож після смерті вузла проєкцію просто відбудовують переграванням:

:::tabs
```ts
// воскресіння: лог тривкий. Проєкцію відбудовуємо переграванням від знімка.
async function reviveProjection(log: Log, homeId: string): Promise<LockState> {
  const snap = (await loadSnapshot(homeId)) ?? INITIAL;    // знімок проєкції — прискорити
  const tail = await log.readFrom(homeId, snap.version);   // події ПІСЛЯ знімка
  return tail.reduce(apply, snap);                         // згорнути хвіст на знімок
}
```
```py
# воскресіння: лог тривкий. Проєкцію відбудовуємо переграванням від знімка.
def revive_projection(log, home_id):

    tail = log.read_from(home_id, snap.version)            # події ПІСЛЯ знімка
```

Знімок тут — той самий трюк, що в актора, і рівно з тим самим призначенням: щоб перегравання не починалося щоразу від початку часів. Але різниця принципова: у актора знімок був **єдиною** тривкою правдою, і хвіст між знімками можна було втратити; у журналі знімок — лише кеш, а справжня правда — це весь лог, і хвіст `e6, e7` дочекався нас на диску. Тому тут `version = 7` після краху — не щастя, а гарантія.

## Один сценарій, три поведінки

Тепер поставмо три виходи поряд — на той самий вхід, крізь ті самі дві осі. Ось де три філософії правди перестають бути словами.

![Три горизонтальні доріжки — Актор (синій), Рядок (бурштиновий), Журнал (зелений) — показують, як кожен обробляє дві одночасні «замкни». Актор: пошта FIFO з seq6, seq7 → актор бере по одному → version 5→6→7, галочка, «гонки нема за побудовою». Рядок: дві транзакції обидві читають v5 і пишуть v6 → червоне «v6, одна команда зникла», хрестик; лік — CAS «WHERE version=5», друга ретраїть → v7, галочка, «версія рядка або замок». Журнал: слоти e5, e6, e7 дописані по порядку → згортка apply → version 7, галочка, «дописи не перетирають одне одного»](img/race-serialization.svg)
*Перша вісь — серіалізація. Актор не пускає двох одночасно (пошта). Рядок пускає — і наївний read-modify-write губить оновлення, доки не приб'єш гонку версією рядка чи замком. Журнал пускає обох, але `append` не вміє перетирати, тож порядок дає позиція в лозі. Три способи не дати двом «замкни» злитися — і лише в одного це задарма.*

![Три горизонтальні доріжки показують відновлення після смерті вузла. Актор: «RAM version 7» перекреслено (стерто) → снапшот v5 на диску → плюс переграти хвіст e6, e7 → v7, галочка; збоку червоне «без журналу хвоста → лише v5: дві команди втрачено». Рядок: рядок v7 на диску (зафіксовано, fsync) → вцілів як є, галочка, «нема окремого воскресіння; незавершена txn — атомарний відкат». Журнал: лог e6, e7 на диску (fsync до ack) → переграти зі снапшота → проєкція v7, галочка, «порядок беруть із позицій у лозі»](img/crash-recovery.svg)
*Друга вісь — відновлення. Актор воскресає зі знімка, і хвіст після знімка або втрачено, або треба журналювати окремо. Рядок нічого не воскрешає: зафіксоване вже тривке. Журнал переграє себе зі знімка й відновлює порядок із позицій. Той самий крах — три різні ціни, бо правда лежить у трьох різних місцях.*

Звівши обидві осі в одну табличку, дістаємо портрет кожного варіанта на нашому сценарії:

```
                  гонка (дві «замкни» на version 5)      крах вузла
──────────────────────────────────────────────────────────────────────────────────
А  актор          v7 — пошта серіалізує, замок зайвий     v5 — лише зі знімка (хвіст втрачено);
                                                          v7 — тільки з журналом хвоста
Б  рядок наївно   v6 — ЗАГУБЛЕНЕ оновлення                v_зафікс — що зафіксовано, те на диску
Б  рядок + CAS    v7 — версія рядка / замок боронять      (те саме: тривке даром)
В  журнал         v7 — порядок = позиція в лозі           v7 — переграти лог зі знімка
```

Прочитай її як три характери. **Актор** бере серіалізацію задарма (пошта), але за тривкість доплачує: чиста пам'ять забуває все, і воскресіння тримається на знімках плюс, зрештою, тому самому журналі. **Рядок** бере тривкість задарма (диск), але за серіалізацію доплачує: без версії чи замка наївний RMW тихо губить команди. **Журнал** бере обидві осі — і порядок, і воскресіння, — але доплачує деінде: читання відстає від логу, а сам лог росте й потребує знімків та компакції. Жоден не дістав обидві осі безкоштовно; кожен узяв одну даром і виставив рахунок за другу.

> 🔧 **Навіщо це.** Коли на дошці сперечаються «актор чи Postgres чи Kafka», суперечка майже завжди не про те. Ти обираєш не бібліотеку — ти обираєш, **де живе правда**, а серіалізація й відновлення вже випливають із цього вибору, хочеш ти того чи ні. Поклав правду в пам'ять живого об'єкта — серіалізацію дістав даром, тривкість мусиш дозбирати. Поклав у рядок на диску — тривкість даром, гонку мусиш заборонити. Поклав у лог — порядок і перегравання даром, свіжість читань і ріст сховища мусиш терпіти. Тому перше питання рев'ю не «яка технологія?», а «якої форми правда — об'єкт, рядок чи стрічка фактів?»; відповідь на нього вже наполовину назвала і твої гонки, і твоє воскресіння.

## Складність і пастки

Кожен варіант несе свій набір граблів, і майже всі вони — тіні тих самих переваг.

**Актор: знімок — це вікно втрати, а «актор» у назві — не гарантія.** Головна ціна вже випливла в сценарії: періодичний знімок означає, що крах може з'їсти все, що сталося після нього. Зменшуєш період — частішаєш дорогі записи на диск; збільшуєш — ширшаєш вікно втрати; хочеш нуль втрати — журналюєш кожну команду наперед і фактично стаєш Варіантом В під іншим ім'ям. Поряд чигають знайомі болячки акторної моделі: [гарячий дім](root:progarch/dh-replicas), чий актор перевантажено й якого не розкидати; наглядання й розміщення акторів по вузлах; і найпідступніше — ілюзія, що ізоляцію постачає слово «актор». Акторна бібліотека поверх звичайних потоків дає модель обміну повідомленнями, але не рантаймові гарантії: досить передати назовні вказівник на свій стан — і [перегони даних](book:programming/data-races-locks), від яких актор нібито втік, повертаються. Що саме купує рантайм, а що лише позичає назва пакета, ми розібрали на [робочому акторі з наглядачем і доказом ізоляції](root:progarch/runtime-actors-variant/proj-dh-device-actor.md).

**Рядок: гонка невидима, поки не стане одночасності; а лік має свою ціну.** Найнебезпечніше в наївному RMW те, що він **зелений на всіх тестах**, які не влаштовують справжнього накладання в часі: один потік — версія росте бездоганно, і баг спить до першого дня, коли дві сесії клацнуть замок в одну мілісекунду. Оптимістичний лік (версія рядка) під високим контеншеном вироджується в **шторм повторів**: що гарячіший рядок, то частіше CAS не збігається й крутить цикл, палячи такти на перечитуваннях. Песимістичний лік (`SELECT … FOR UPDATE`) прибирає повтори, але купує натомість блокування, черги очікування й ризик [взаємного клину](book:programming/data-races-locks) двох транзакцій, що взяли рядки в різному порядку. І з усім тим кожна команда — це похід у базу з fsync, тобто латентність на кожен клац; ефемерне на кшталт присутності писати сюди щосекунди — марнотратство.

**Журнал: читання відстають, схема — назавжди, а перегравання росте.** Проєкцію треба тримати свіжою, і вона завжди трохи позаду логу — це [кінцева узгодженість](book:programming/eventual-consistency): «замкни» вже в лозі, а панель ще показує старе, доки проєкція не наздожене. Схема подій стає [однобічними дверима](root:progarch/what-makes-irreversible): на кожен старий тип події вже спираються проєкції, тож переписати його начисто не можна — лише додавати нові й версіонувати. Перегравання без знімків і компакції з часом розтягується на хвилини; навіть просте «дай поточний стан замка» перестає бути пошуком за ключем і стає зверненням до проєкції, яку хтось мусить оновлювати. Найдорожчі журнальні системи — ті, де лог завели «бо модно», а історією так ніхто й не скористався: узяли всю вагу незворотності, не взявши її вигоди.

## Що лишається в руках

Ми написали один твін тричі й прогнали крізь один сценарій — дві «замкни» та смерть вузла, — і різницю щоразу видали не бібліотеки, а **місце, де лежить правда**. Актор поклав її в пам'ять живого об'єкта: пошта серіалізувала команди задарма, зате RAM забула все й воскресала зі знімка. Рядок поклав її на диск: тривкість дісталася даром, зате наївний RMW губив команду, доки ми не заборонили гонку версією рядка чи замком. Журнал зробив правдою саму стрічку фактів: `append` не вміє перетирати, тож порядок дала позиція, а воскресіння — перегравання.

Помітили головне? Ми жодного разу не обирали між «швидким» і «повільним» чи між «модним» і «нудним». Ми обирали **форму правди** — об'єкт, рядок чи журнал, — і рівно з цієї форми вже випливали і те, як бореться гонка, і те, як переживається крах. `tell`, `put`, `append` — це не три способи зробити те саме; це три різні відповіді на питання «що я вважаю істиною про дім». Ось чому суперечка «яку взяти технологію?» майже завжди недороблена: спершу назви форму правди, і половина відповідей про серіалізацію та відновлення напишеться сама.
