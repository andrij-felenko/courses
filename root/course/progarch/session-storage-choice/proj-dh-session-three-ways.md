# ⚙️ Одна сесія DH трьома сховищами — і як швидко вона вмирає на команду

Про три способи зберігати сесію легко сперечатися словами: «стор надійніший», «токен масштабніший», «гібрид найкращий». Слова нічого не важать. Візьмімо **одну-єдину** перевірку «хто це» — ту, крізь яку в Digital Homes проходить кожен запит, — і зберімо її **тричі**: непрозорим ідентифікатором у сторі, підписаним токеном без стану, гібридом із коротким access і наглянутим refresh. Та сама сесія, той самий шов перевірки, той самий сценарій. Різнитися буде одне число, і саме воно нас цікавить: **скільки сесія живе після команди «відклич її негайно»** — бо для дверей це буквально час, поки чужий іще всередині.

І одразу пуант, щоб тримати його весь розбір: три реалізації майже однакові за обсягом коду, а вікно відкликання в них — **нуль, дві хвилини й цілу добу**. Не на відсотки різні. На порядки в часі. Це число і є ціною, яку матриця вибору показувала словами, а тут воно проступить на дотик — таймлайном, який ми надрукуємо.

## Задача — прибити все, крім сховища

Щоб контраст був чесний, лишаємо змінним рівно **одне** — де живе правда про сесію. Усе інше прибиваємо цвяхами. Особа одна й та сама. Сценарій один: увійшли, попрацювали, **відкликали**, спробували ще раз. І — головне — перевірку «хто це» ховаємо за **один-єдиний шов**, крізь який ходить кожен викликач. Це той [шов](root:progarch/seams-and-boundaries), навколо якого й крутиться зворотність вибору: якщо перевірка сидить в одній точці, то яку начинку ти поклав усередину — стор чи токен — справа заміни, а не переписування системи.

Оголосимо цей шов першим, бо саме він робить порівняння можливим. Кожен варіант мусить реалізувати той самий інтерфейс: узяти **пред'явлене** клієнтом і сказати, **хто це** (або `null`), плюс уміти **погасити** сесію.

```ts
// Хто перед нами, коли перевірка пройшла. Далі бізнес-код бачить ЛИШЕ це.
type Principal = { sub: string; home: string; scopes: string[] };

// ЄДИНИЙ шов гарячого шляху. Що всередині — стор чи токен — викликач не знає.
interface SessionSeam {
  validate(presented: string): Promise<Principal | null>; // гарячий шлях: хто це?
  revoke(handle: string): Promise<void>;                   // орган відкликання: погаси
}
```

Одна проміжна ланка Express кличе цей шов — і вона **байдужа** до того, який варіант під нею. Прочитала пред'явлене, спитала шов, поклала `Principal` у запит — далі жоден обробник маршруту не знає й не хоче знати, звідки взялася відповідь.

```ts
import type { Request, Response, NextFunction, RequestHandler } from "express";

function readCredential(req: Request): string {
  const bearer = req.header("authorization")?.replace(/^Bearer /, "");
  return bearer ?? (req as any).cookies?.sid ?? ""; // Bearer (Б/В) або кукі sid (А)
}

// Та сама middleware для ВСІХ трьох варіантів. Міняється лише seam при збірці.
function authenticate(seam: SessionSeam): RequestHandler {
  return async (req: Request, res: Response, next: NextFunction) => {
    const who = await seam.validate(readCredential(req));
    if (!who) return res.status(401).json({ error: "unauthorized" });
    (req as any).principal = who; // далі — лише Principal, походження невидиме
    next();
  };
}

// Викликач — і гадки не має, стор під ним чи підпис. Бачить готового principal.
app.post("/device/:id/unlock", authenticate(seam), (req, res) => {
  const who = (req as any).principal as Principal;
  if (!who.scopes.includes("door:unlock")) return res.status(403).end();
  lock.open(req.params.id, who.home); // ← ось той самий замок вхідних дверей
  res.json({ ok: true });
});
```

Тепер уся розвилка стиснута в **один рядок** — той, де при збірці програми ми пишемо `const seam = new …()`. Поміняли цей рядок — і `authenticate`, і кожен обробник маршруту лишаються байт-у-байт тими самими. Ось що означає «сховати вибір за швом»: три геть різні сховища сесії відрізняються лише вибором конструктора.

![Ліворуч три викликачі (GET /home, POST /device/:id/unlock, GET /telemetry), що бачать лише req.principal; від них стрілка в центральну зелену рамку «authenticate() — єдиний шов перевірки: validate(presented) → Principal or null»; від рамки стрілка в гніздо-рейку, а в неї вставляються три взаємозамінні картки-начинки: А server-side store (вставлена суцільним), Б stateless JWT і В гібрид access+refresh (пунктиром, «на полиці»)](img/one-seam.svg)

*Гарячий шлях знає лише одну точку — `authenticate()`. Сховище сесії (А / Б / В) вставляється в неї, як змінна начинка в гніздо; викликачі його не бачать. Уся розвилка — це який конструктор написати при збірці.*

> 🔧 **Навіщо це.** Без цього шва «поміняти сховище сесії» означає обійти весь код, що десь смикає Redis руками, а десь розбирає JWT просто в контролері, — і кожне таке місце переписати. Зі швом та сама зміна коштує один рядок при збірці. Тому в реальному проєкті першим кладуть **не** «правильний» варіант зберігання, а чисту межу перевірки; сам вибір А/Б/В із незворотного стає зворотним рівно тому, що обгороджений.

## Ідея — одне питання й один годинник

За трьома варіантами стоїть одне питання: на кожен запит **іти по правду в стор** чи **вірити пред'явленому**? Варіант А йде в стор завжди. Варіант Б не йде нікуди — вірить підпису. Варіант В вірить підпису на гарячому шляху, але право сказати «ні» лишає в сторі, куди зазирає лише зрідка. Три відповіді — три вікна відкликання.

Щоб побачити ці вікна **на дотик**, а не на словах, нам треба керований годинник — інакше довелося б чекати реальну добу, поки протухне токен варіанта Б. На щастя, тут допомагає одна деталь бібліотеки: при перевірці підпису `jsonwebtoken` бере «поточний час» не жорстко з системного годинника, а з опції `clockTimestamp` — «час у секундах, проти якого робити всі порівняння», і лише **за замовчуванням** підставляє `Math.floor(Date.now()/1000)`. Тобто ми можемо **впорснути власний час** і промотати добу за наносекунди, нічого не підробляючи в самій криптографії.

```ts
let NOW = 0;                 // «зараз» у секундах від старту сценарію
const clock = () => NOW;     // впорскуємо цей годинник у варіанти Б і В
```

Тепер сценарій усюди буде однаковий: увійти, перевірити (жива), **відкликати**, перевіряти знову, промотуючи `NOW` уперед, і дивитися, **на якій секунді** сесія нарешті поверне `null`. Ця секунда і є вікно відкликання.

## Варіант А — server-side store: правда в сторі

У кукі клієнта — лише короткий непрозорий `sid`, випадковий рядок, що сам собою нічого не значить. Уся правда сесії — у сторі Redis-класу, куди дотягуються всі інстанси. Логін кладе правду туди й віддає клієнтові лише ключ; перевірка на кожен запит іде в стор за цим ключем; відкликання — видалення рядка.

```ts
import { randomBytes } from "node:crypto";

interface Store {                                   // рівно те, що дає Redis
  get(k: string): Promise<string | null>;
  set(k: string, v: string, ttlSec: number): Promise<void>;
  del(k: string): Promise<void>;
}

class ServerStoreSeam implements SessionSeam {
  constructor(private store: Store) {}

  // холодний шлях: логін кладе правду в стор, клієнтові дає лише непрозорий sid
  async login(p: Principal): Promise<string> {
    const sid = randomBytes(32).toString("base64url"); // сам собою нічого не значить
    await this.store.set(`sess:${sid}`, JSON.stringify(p), 30 * 24 * 3600);
    return sid;
  }

  // гарячий шлях: правду шукаємо в сторі на КОЖЕН запит
  async validate(sid: string): Promise<Principal | null> {
    if (!sid) return null;
    const raw = await this.store.get(`sess:${sid}`);   // ← похід у Redis
    return raw ? (JSON.parse(raw) as Principal) : null; // нема запису — нема сесії
  }

  // орган відкликання: видалив рядок — сесія мертва в ту ж мить, на всіх інстансах
  async revoke(sid: string): Promise<void> {
    await this.store.del(`sess:${sid}`);
  }
}
```

У живому Node цей клас майже дослівно — це `express-session` поверх `connect-redis`: та сама кукі з непрозорим `sid`, той самий похід у стор на кожен запит, а `req.session.destroy()` — це рівно наш `revoke`. Я переписую його тонко власноруч лише щоб усі три варіанти сиділи за **однаковим** інтерфейсом і порівняння лишалося чистим.

Тепер сценарій «відклич, потім спробуй ще раз». Стор — проста мапа в пам'яті замість Redis; API той самий.

```ts
class MemoryStore implements Store {                 // у проді — Redis, API ідентичний
  private m = new Map<string, string>();
  async get(k: string) { return this.m.get(k) ?? null; }
  async set(k: string, v: string) { this.m.set(k, v); }
  async del(k: string) { this.m.delete(k); }
}

const alice: Principal = { sub: "u-42", home: "home-7", scopes: ["door:unlock"] };
const seamA = new ServerStoreSeam(new MemoryStore());

const sid = await seamA.login(alice);
console.log(await seamA.validate(sid)); // → { sub: 'u-42', … }  ЖИВА
await seamA.revoke(sid);                //   ← «викинули телефон»: видалили запис
console.log(await seamA.validate(sid)); // → null                МЕРТВА В ТУ Ж МИТЬ
```

```
t=0s   validate → Principal   (жива)
t=0s   revoke               (видалили рядок sess:…)
t=0s   validate → null      ← вікно відкликання = 0: мертва миттєво
```

Наступний запит уже не знаходить рядка — і `validate` повертає `null` на всіх інстансах одразу, бо всі дивляться в один стор. Ключ, який ти контролюєш, і відібрати можна миттєво. Ціна цієї миттєвості — той самий похід у стор **на кожному** запиті: латентність плюс спільна залежність на критичному шляху. Але для дверей вікно нуль коштує саме стільки, скільки треба.

## Варіант Б — stateless JWT: правда в токені

Протилежна філософія: сервер не тримає жодної сесії. Усе — «це користувач такий-то, ось права, чинний до такої-то хвилини» — лежить у самому токені, а зверху криптографічна печатка. Підписуємо приватним ключем при вході; перевіряємо публічним локально на кожен запит, [як і належить підписаному токену без стану](topic:sf-web/jwt-tokens); нікуди не ходимо.

```ts
import jwt from "jsonwebtoken";

class StatelessJwtSeam implements SessionSeam {
  constructor(
    private priv: string,                    // приватний ключ — лише в емітента
    private pub: string,                     // публічний — у кожного, хто перевіряє
    private clock: () => number = () => Math.floor(Date.now() / 1000),
  ) {}

  login(p: Principal): string {
    const now = this.clock();
    return jwt.sign(
      { sub: p.sub, home: p.home, scopes: p.scopes, iat: now, exp: now + 24 * 3600 },
      this.priv,
      { algorithm: "RS256" },   // підпис приватним; expiresIn НЕ передаємо — exp уже в тілі
    );
  }

  async validate(token: string): Promise<Principal | null> {
    try {
      const c = jwt.verify(token, this.pub, {
        algorithms: ["RS256"],
        clockTimestamp: this.clock(), // порівняння exp — проти НАШОГО годинника
      }) as jwt.JwtPayload;
      return { sub: c.sub as string, home: c.home, scopes: c.scopes };
    } catch {
      return null; // прострочений або підроблений — і БІЛЬШЕ дивитися нема куди
    }
  }

  async revoke(_handle: string): Promise<void> {
    // НІКУДИ писати. Сервер не тримає сесій — отже, нема місця сказати «ця вже ні».
    // Єдиний спосіб — завести денилист… але це вже похід у стор на гарячому шляху,
    // тобто вже НЕ stateless. Тож тут — чесний no-op, і в ньому вся рана.
  }
}
```

Зверни увагу на тіло `revoke`. Воно **порожнє** — і не тому, що я полінувався. Порожнє воно **за побудовою**: у варіанті, де сервер лише перевіряє підпис, немає жодного місця, куди записати факт «цю сесію відкликано». Токен чинний, доки ціла печатка й не настав `exp`; сервер, який тільки читає печатку, не має де тримати список винятків. Проженемо той самий сценарій — і побачимо порожнечу в дії.

```ts
const seamB = new StatelessJwtSeam(privateKey, publicKey, clock); // exp = вхід + 24 год
const token = seamB.login(alice);

NOW = 60;         console.log(await seamB.validate(token)); // → Principal   ЖИВА
                  await seamB.revoke("u-42-sess");           //   ← «викинули телефон»
NOW = 61;         console.log(await seamB.validate(token)); // → Principal   ВСЕ ЩЕ ЖИВА
NOW = 3600;       console.log(await seamB.validate(token)); // → Principal   і за годину жива
NOW = 24 * 3600 + 1; console.log(await seamB.validate(token)); // → null     аж ТЕПЕР
```

```
t=60s     validate → Principal   (жива, хвилина по вході)
t=60s     revoke   → (no-op: писати нікуди)
t=61s     validate → Principal   ← «відкликали», а вона жива
t=1h      validate → Principal   ← досі жива
t=24h+1s  validate → null        ← мертва лише коли exp настав САМ
```

Ось воно, на дотик. Ми викликали `revoke` на шістдесятій секунді — і нічого не сталося. Токен пережив команду відкликати й лишався чинним ще майже цілу добу, аж поки не протух власним терміном. Вікно відкликання тут — **~24 години**, і його задає не наша воля, а `exp`, вписаний при вході. Для віджета погоди байдуже. Для дверей це доба, протягом якої злодій із украденим телефоном заходить у дім.

І сама спокуса «а полагодьмо це денилистом» веде по колу назад: щойно ти на гарячому шляху перевіряєш токен **проти списку відкликаних**, ти знову ходиш у стор на кожен запит — тобто платиш ту саму ціну, що й варіант А, але вже без його простоти. Stateless, який уміє миттєво відкликати, — це просто server-side store, що ходить манівцями.

## Варіант В — гібрид: гарячий шлях локальний, відкликання на рефреші

Третій шлях бере локальну перевірку з Б, а орган відкликання — з А, і чесно платить складністю. Токенів два. Короткий **access** — той самий stateless-JWT, але з терміном у хвилини; ним ходять на гарячому шляху, перевіряючи локально. І довгий **refresh** — непрозорий ідентифікатор, який сервер **тримає в сторі**; ним клієнт раз на кілька хвилин виміняє свіжий access. На цьому обміні й живе право сказати «ні».

```ts
class HybridSeam implements SessionSeam {
  constructor(
    private priv: string,
    private pub: string,
    private store: Store,             // тримає лише РЕФРЕШІ, а не гарячий шлях
    private accessTtlSec = 120,       // короткий повідок: 2 хвилини
    private clock: () => number = () => Math.floor(Date.now() / 1000),
  ) {}

  // холодний шлях: логін дає короткий access + непрозорий refreshId (у сторі)
  async login(p: Principal): Promise<{ access: string; refreshId: string }> {
    const refreshId = randomBytes(32).toString("base64url");
    await this.store.set(`refresh:${refreshId}`, JSON.stringify(p), 30 * 24 * 3600);
    return { access: this.issueAccess(p), refreshId };
  }

  private issueAccess(p: Principal): string {
    const now = this.clock();
    return jwt.sign(
      { sub: p.sub, home: p.home, scopes: p.scopes, iat: now, exp: now + this.accessTtlSec },
      this.priv, { algorithm: "RS256" },
    );
  }

  // ГАРЯЧИЙ шлях — суто локальний, як у Б: жодного стору
  async validate(access: string): Promise<Principal | null> {
    try {
      const c = jwt.verify(access, this.pub, {
        algorithms: ["RS256"], clockTimestamp: this.clock(),
      }) as jwt.JwtPayload;
      return { sub: c.sub as string, home: c.home, scopes: c.scopes };
    } catch { return null; }
  }

  // ХОЛОДНИЙ шлях, раз на кілька хвилин: обмін refresh на свіжий access — ТУТ можна відмовити
  async refresh(refreshId: string): Promise<string | null> {
    const raw = await this.store.get(`refresh:${refreshId}`);
    if (!raw) return null;                     // відкликали — нового access не дамо
    return this.issueAccess(JSON.parse(raw) as Principal);
  }

  // орган відкликання: викидаємо refresh зі стору (або в денилист)
  async revoke(refreshId: string): Promise<void> {
    await this.store.del(`refresh:${refreshId}`);
  }
}
```

`validate` тут — копія варіанта Б: локальна арифметика підпису, жодного стору. А `revoke` — копія варіанта А: видалення рядка. Хитрість у тому, що вони діють на **різні** токени. Відкликання рве refresh, але живий короткий access цього ще не знає — він протухне сам за свої дві хвилини. Проженемо сценарій і побачимо, як ці дві хвилини й стають вікном.

```ts
const seamV = new HybridSeam(privateKey, publicKey, new MemoryStore(), 120, clock);
NOW = 0;                                              // назад на старт: логін від t=0 → exp = 0 + 120
let { access, refreshId } = await seamV.login(alice); // access живе 2 хв

NOW = 10;   console.log(await seamV.validate(access));  // → Principal   ЖИВА
            await seamV.revoke(refreshId);              //   ← «викинули телефон»: рвемо refresh
NOW = 11;   console.log(await seamV.validate(access));  // → Principal   access ще НЕ протух
NOW = 60;   console.log(await seamV.validate(access));  // → Principal   у межах 2-хв повідка
NOW = 121;  console.log(await seamV.validate(access));  // → null        access протух САМ
            console.log(await seamV.refresh(refreshId)); // → null       а нового не дадуть
```

```
t=10s     validate → Principal   (жива)
t=10s     revoke(refreshId)     → refresh викинуто зі стору
t=11s     validate → Principal   ← гарячий шлях локальний, access живий
t=60s     validate → Principal   ← ще в межах повідка
t=121s    validate → null        ← access протух сам
t=121s    refresh  → null        ← нового access НЕ дадуть → доступ обірвано
```

Ось де видно всю ідею гібрида. Ми відкликали на десятій секунді, і секунду по тому сесія ще жива — гарячий шлях чесно вірить короткому токену. Але за дві хвилини access протухає, клієнт іде по новий — і **тут** натикається на стіну: refresh уже викинуто, нового access не буде, доступ обривається. Вікно відкликання — **термін життя access**, тут дві хвилини. Не нуль, як у А, і не доба, як у Б, а рівно стільки, скільки ти дозволив короткому токену жити без нагляду. Довжину цього повідка задаєш ти: що дорожче те, що відмикає сесія, то коротший робиш access — і то ближче вікно відкликання до нуля, ціною частіших рефрешів.

## Три вікна поруч — ось де слова стають числом

Покладімо три таймлайни один під одним. Код `authenticate` і код обробника `unlock` при цьому **не змінювався жодного разу** — мінявся лише конструктор `seam` при збірці.

```
                    команда відкликати → фактична смерть   вікно відкликання
А server-side store        t=0s      →     t=0s                 0 (миттєво)
Б stateless JWT (24 год)   t=60s     →     t=24h                ~24 години
В гібрид (access 2 хв)     t=10s     →     t=121s               ~2 хвилини (TTL access)
```

Жодна реалізація не «зламана» — усі три роблять рівно те, що обіцяли їхні конструктори. Різниця не в правильності, а в тому, **де лежить право сказати „ні“**: у варіанті А воно в сторі, тому спрацьовує в ту ж мить; у Б його нема ніде, тому команда відкликати провалюється в порожнечу й чекає `exp`; у В воно в сторі, але дотягується до гарячого шляху не одразу, а через термін життя access. Той самий шов, той самий сценарій, той самий обсяг коду — а «як швидко сесія вмирає на команду» стрибає від секунд до доби.

І помітьмо ще одне, менш очевидне. Варіанти А і В обидва тримають стор — але **на різних шляхах**. У А стор на гарячому: кожен запит платить похід у нього. У В стор на холодному: гарячий шлях локальний, а в стор зазираємо лише на рефреші, раз на дві хвилини. Ось чому В масштабується там, де А починає задихатися: він зняв стан із гарячого шляху й лишив його на холодному, не втративши органа відкликання.

## Складність і пастки

Три реалізації — три різні набори граблів, і кожні ростуть із того самого кореня, що й перевага.

**А — стор на гарячому шляху.** Миттєве відкликання куплене тим, що **кожен** запит залежить від стору: він ліг — залогінитися не може ніхто, бо перевірити сесію нема де. Це серце, яке страшно спинити, і його доводиться реплікувати й берегти. Друга грабля тонша: непрозорий `sid` мусить бути справді непередбачуваним — 32 байти з `randomBytes`, а не лічильник і не щось, виведене з даних користувача; вгаданий `sid` — це вкрадена сесія без жодного зламу підпису. І третя: не забудь `ttlSec` при `set`, інакше мертві сесії осідатимуть у сторі назавжди — стор не гумовий.

**Б — відкликання неможливе за побудовою.** Ми це вже бачили: `revoke` нема куди писати. Але рана глибша за один вихід із системи. По-перше, **ротація ключа підпису**: поки ти крутиш `pub`/`priv`, на старому ключі підписані живі токени, і викинути старий ключ, не дочекавшись їхнього протухання, не можна — незворотність рівно тому, що [токени переживають ключ](root:progarch/what-makes-irreversible). По-друге, **не можна вкоротити вже виданий токен**: якщо поставив 24 години, то це 24 години для кожного, хто вже увійшов, — зменшення `exp` подіє лише на майбутні входи. По-третє, кожен зайвий клейм роздуває **кожен** запит на ті самі байти. Stateless прекрасний там, де відкликання не потрібне зовсім; щойно воно потрібне швидко — Б випадає першим.

**В — найбільше рухомих частин.** Ти не втік від стану, ти пересунув його на холодний шлях — і разом із ним прийшли його клопоти. Refresh довгоживучий, тож украдений refresh цінний; звідси **ротація рефрешів** (кожен обмін видає новий, старий гасне) і **виявлення повторного використання**: якщо той самий `refreshId` пред'явили двічі, це сигнал крадіжки — рвемо всю родину рефрешів. Далі — **годинниковий дрейф**: коли інстанси мають трохи різний час, короткий access на межі `exp` то живий, то ні; на цей випадок є `clockTolerance` у `jwt.verify` — кілька секунд поблажки. І головна пастка гібрида — **вибір довжини повідка**: постав access задовго — і вікно відкликання розповзається до небезпечного; закоротко — і клієнт задихається від рефрешів. Дві хвилини для дверей розумні; дві години — уже майже Б із зайвою механікою.

Ось де пуант, з якого ми починали, лягає доказом у руки. Сесія була **одна**, шов перевірки — **один**, обсяг коду — майже той самий. А відповідь на єдине запитання «що станеться в перші п'ять хвилин після команди відкликати?» вийшла не схожа навіть віддалено: нуль, дві хвилини, доба. Вибираючи, де живе сесія, ти вибираєш не «яку технологію любиш» — ти вибираєш **довжину цього вікна**. І для системи, чия сесія відмикає фізичний замок, довжина вікна — це не рядок у таблиці порівнянь, а час, який ти даруєш тому, хто вкрав ключ.
