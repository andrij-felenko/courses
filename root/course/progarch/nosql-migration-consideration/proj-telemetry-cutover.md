# ⚙️ Плейбук: перевезти живу телеметрію без простою й без утрати рядка

Рішення вже ухвалене: телеметрія DH відчіпляється від реляційного ядра й переселяється в супутник — сховище часових рядів. Але між «ухвалили» й «зроблено» лежить робота, від якої холонуть руки: таблицю треба перевезти, **поки вона жива**. Два мільйони давачів щохвилини дописують у неї нове показання, дашборди щосекунди її читають, а позаду лежить чверть трильйона рядків історії. Спинити цей потік не можна — «технічне вікно на пів доби» для розумного дому означає, що чиясь автоматика не спрацює, чийсь графік обірветься, а хтось саме тепер дивиться, чи не протікає в нього труба.

Отже задача точна: **перевезти рухому річку, не спинивши течії, не загубивши краплі — і на кожному кроці мати двері назад.** Ворогів рівно два. Простій (англ. *downtime*) — коли система не відповідає. І втрата даних — коли рядок, який давач надіслав, ніде не осів. До них додається третій, найпідступніший: **мить, з якої немає легкого шляху назад.** Наївний план — «вимкнути застосунок, зняти dump старого, залити restore у нове, перемкнути й помолитися» — програє за всіма трьома одразу: десятки терабайтів копіюються годинами, весь цей час система лежить, а якщо на середині щось піде не так, відкат — це відновлення з резервної копії, тобто ще години простою й невідомо який стан на виході. Так возять мертве. Живе возять інакше.

## Ідея: старе й нове якийсь час живуть поруч

Уся хитрість — не переставляти дані одним ривком, а зробити так, щоб старе й нове сховища якийсь час **працювали пліч-о-пліч**, і не рухати нічого важливого, доки нове не доведе, що дослівно повторює старе. Це розкладає страшний ривок на шість дрібних фаз, і кожна з них — оборотні ворота:

1. **Подвійний запис.** Застосунок починає з певної миті T₀ писати кожне показання в **обидва** сховища. Нове ловить живий потік.
2. **Беквіл історії.** Усе, що старіше за T₀, пачками переливаємо зі старого в нове — ідемпотентно.
3. **Звірка паритету.** Рахуємо рядки й порівнюємо вибіркові читання старе-проти-нового.
4. **Перемикання читань.** Поступово, часткою трафіку, переводимо читання на нове; старе лишається запасним.
5. **Стоп запису в старе.** Коли нове довело себе на читаннях — перестаємо його дублювати.
6. **Скидання партицій старого.** Повертаємо десятки терабайтів реляційній базі.

Несуча ідея, яку варто вкарбувати одразу: **читання рушає останнім, і лише після того, як паритет доведено.** Поки читання сидять на старому, будь-яка розбіжність нового — **невидима користувачу**, а отже відкат нічого не коштує: ти просто не робиш наступного кроку. Саме цей порядок перетворює міграцію з азартної гри на низку дрібних, тверезих рішень.

Далі — по фазі, з механікою й кодом. Мова прикладів тут загальнобекендна: показання пише сервіс, беквіл жене окремий воркер, звірку рахує скрипт — це світ Python, Go й TypeScript, не регістрів.

## Фаза 1. Подвійний запис — годуємо нове живим потоком

Найперший крок нічого не переносить — він лише робить так, щоб **з певної миті** кожне нове показання лягало в обидва сховища. Ця мить T₀ — не просто час на годиннику, а межа відповідальності: усе, що прийшло від T₀ і далі, бере на себе подвійний запис; усе, що раніше, дожене беквіл. Тому T₀ фіксуємо один раз і за **часом самого показання** (event-ts), а не за миттю, коли рядок долетів до сервера.

Обгортка запису проста, і вся сіль — у порядку та в тому, що робити, коли одне зі сховищ спіткнеться. Старе поки лишається **джерелом правди**, тож у нього пишемо першим і його помилку віддаємо користувачу чесно. Нове пишемо другим і **«як вийде»**: якщо воно не прийняло рядок, ми не валимо запис користувача — прогалину однаково залатає беквіл або звірка, поки правда живе в старому. Єдине, чого не можна, — це проковтнути збій **мовчки**: кожну невдачу нового рахуємо лічильником розбіжності й дивимось на нього безперервно, а не лише під час звірки.

:::tabs
```python
async def write_reading(self, r: Reading) -> None:
    # Старе — джерело правди: якщо воно не прийняло рядок, це справжня
    # помилка, і вона летить користувачу.
    await self.old.insert(r)
    try:
        await self.new.upsert(r)          # нове — «як вийде»
    except Exception as e:
        self.divergence.inc()             # лічильник розбіжності — стежимо БЕЗПЕРЕРВНО
        log.warning("new-store write failed: device=%s ts=%s err=%s",
                    r.device_id, r.ts, e)
        # навмисно ковтаємо: нове ще не джерело правди, прогалину залатає звірка
```
```go
// WriteReading пише спершу в старе (джерело правди), потім «як вийде» в нове.
// Збій нового НЕ валить запис користувача — прогалину дожене беквіл/звірка.
func (w *TelemetryWriter) WriteReading(ctx context.Context, r Reading) error {
    if err := w.old.Insert(ctx, r); err != nil {
        return err // старе не прийняло — це справжня помилка, повертаємо як є
    }
    if err := w.new.Upsert(ctx, r); err != nil {
        w.divergence.Inc() // лічильник розбіжності — під безперервним оком
        log.Warn("new-store write failed", "device", r.DeviceID, "ts", r.TS, "err", err)
        // навмисно НЕ повертаємо: нове ще не джерело правди
    }
    return nil
}
```
```ts
async writeReading(r: Reading): Promise<void> {
  // Старе — джерело правди: помилка тут справжня, летить далі.
  await this.old.insert(r);
  try {
    await this.new.upsert(r);            // нове — «як вийде»
  } catch (err) {
    this.divergence.inc();               // безперервний лічильник розбіжності
    log.warn(`new-store write failed: device=${r.deviceId} ts=${r.ts} err=${err}`);
    // навмисно не кидаємо далі: нове ще не джерело правди
  }
}
```
:::

> 🔧 **Навіщо це.** Порядок «старе першим, нове другим» — не косметика. Він означає, що збій ще-не-довіреного сховища ніколи не стане збоєм користувача, і що в кожну мить є рівно одне джерело правди, до якого можна відкотитися. Переставиш місцями — і перший же тайм-аут нового сховища почне ронити живі записи заради даних, які тобі ще навіть не потрібні.

Тут-таки чесно назвемо ваду застосункового подвійного запису: це **два окремі записи, і другий може не статися**, а застосунок про це лише дізнається постфактум. Ми свідомо з цим живемо, бо маємо запобіжну сітку — правда в старому, а беквіл і звірка залатають пропуски. Але сітки може й не бути, і тоді дублювати потік варто надійніше. Дорога перша — [транзакційний outbox](book:programming/outbox-pattern): застосунок в одній транзакції зі старим пише «завдання переслати» в допоміжну таблицю, а окремий відправник дочитує її й доставляє в нове, доки не підтвердить. Дорога друга, і часто чистіша, — узагалі **не** просити застосунок писати двічі, а читати журнал реплікації самої бази й струмом переливати кожну зміну в супутник; це [захоплення змін даних](book:programming/change-data-capture) (англ. *change data capture*, CDC): джерелом істини стає **сам журнал**, тож коли нове сховище лежить, зміни просто чекають у журналі й доганяють його потім, без утрати. Ціна CDC — окрема інфраструктура (конектор на кшталт Debezium) і невелике відставання; ціна застосункового подвійного запису — оцей ризик розсинхрону, який ми гасимо звіркою. Обирай за зрілістю експлуатації, а не за модою.

## Фаза 2. Беквіл історії — марафон, який ти перезапустиш

Тепер, коли живий край надійно тече в обидва сховища, беремося за минуле: усе з `ts < T₀` треба переписати зі старого в нове. І перше, що варто зробити, — прикинути на серветці, **скільки це триватиме**, бо від цього залежить уся конструкція беквілу:

```
260 000 000 000 рядків / 500 000 рядків за секунду ≈ 520 000 с ≈ 6 діб
```

Півтижня-тиждень безперервного переливання — і це ще оптимістично, бо жену його ти **під живим навантаженням**, а отже мусиш притлумлювати темп, щоб не задушити старе сховище, з якого водночас годуєшся сам. Висновок звідси один і жорсткий: беквіл, який іде шість діб, **обов'язково** колись урветься — рестарт сервісу, вичерпаний диск, задушене читанням старе. Тому він мусить бути **відновлюваним** (продовжити з місця, де впав) і **ідемпотентним** (перезапуск не наробить дублів). Не «бажано» — інакше він просто не дійде до кінця.

Ідемпотентність тут дістається майже задарма, і саме через те сховище, яке обрала стаття. У ширококолонковому сховищі часових рядів первинний ключ показання — це `(device_id, ts)`, а вставка за наявним ключем не додає новий рядок, а **перезаписує ту саму комірку**. Тобто повтор пачки фізично не може наплодити дублів: другий запис лягає поверх першого тим самим значенням. Це і є [ідемпотентність](book:programming/idempotency) — властивість, за якої повторити операцію байдуже, чи не робив ти її взагалі. Нам не треба вигадувати дедуплікацію; вона вбудована у форму ключа.

Сам цикл ходить партиціями від найстарішої до T₀, читає старе пачками за курсором, ідемпотентно пише в нове й **рухає чекпойнт лише після успішного запису** — щоб після падіння перезайти рівно з тієї пачки, яку не встиг підтвердити (а повторити її безпечно):

:::tabs
```python
# Беквіл однієї партиції: читаємо старе пачками за курсором (краще з РЕПЛІКИ,
# щоб не душити головний вузол), ідемпотентно пишемо в нове, чекпойнт рухаємо
# ПІСЛЯ запису. Повтор пачки безпечний: upsert за (device_id, ts) перезаписує комірку.
def backfill_partition(part, checkpoint, batch=10_000):
    last_key = checkpoint.load(part.id)                 # де спинилися минулого разу
    while True:
        rows = old_replica.read_batch(part, after=last_key, limit=batch, ts_lt=T0)
        if not rows:
            break
        new.upsert_many(rows)                           # ідемпотентно за первинним ключем
        last_key = rows[-1].key                         # (device_id, ts) останнього рядка
        checkpoint.save(part.id, last_key)              # рухаємо чекпойнт лише ТЕПЕР
    checkpoint.mark_done(part.id)
```
```go
// Партиції беквілимо кількома робітниками: серійний темп 260 млрд рядків не витягне,
// але старе сховище не можна затопити — ширина пулу = скільки паралельного читання
// воно стерпить, лишивши смугу живому трафіку.
func runBackfill(ctx context.Context, parts []Partition, workers int) {
    sem := make(chan struct{}, workers)
    var wg sync.WaitGroup
    for _, p := range parts {
        if checkpoint.Done(p.ID) {   // партицію вже добито — пропускаємо (ідемпотентність і тут)
            continue
        }
        wg.Add(1)
        sem <- struct{}{}
        go func(p Partition) {
            defer wg.Done()
            defer func() { <-sem }()
            if err := backfillPartition(ctx, p); err != nil {
                log.Error("backfill failed", "part", p.ID, "err", err) // впав — просто перезапустять
            }
        }(p)
    }
    wg.Wait()
}

// Одна партиція: курсор із чекпойнта, читаємо з репліки, пишемо ідемпотентно,
// чекпойнт рухаємо ПІСЛЯ успішного запису.
func backfillPartition(ctx context.Context, p Partition) error {
    last := checkpoint.Load(p.ID)
    for {
        rows, err := oldReplica.ReadBatch(ctx, p, last, batchSize, ltTS(T0))
        if err != nil {
            return err
        }
        if len(rows) == 0 {
            break
        }
        if err := newStore.UpsertMany(ctx, rows); err != nil {
            return err // впали до чекпойнта — повтор пачки безпечний
        }
        last = rows[len(rows)-1].Key      // (device_id, ts)
        checkpoint.Save(p.ID, last)       // рухаємо курсор лише після запису
    }
    return checkpoint.MarkDone(ctx, p.ID)
}
```
:::

Лишається слизьке місце — **записи в польоті на самому шві**. Що з показанням, чиє `ts` менше за T₀, але яке долетіло до сервера **пізніше**, ніж беквіл уже пройшов його партицію? Давачі буферизують офлайн і скидають накопичене з запізненням — таке трапляється щохвилини. Відповідь падає з того, що подвійний запис розкладає показання за **event-ts**, а не за часом прибуття: запізніле показання з `ts < T₀` подвійний запис однаково покладе в нове сховище, у правильну (за часом) комірку. Якщо беквіл уже проходив цю комірку — новий запис просто ляже поверх тим самим значенням (знову ідемпотентність рятує), якщо ще не проходив — беквіл згодом ляже поверх нього. Хоч так, хоч так у комірці опиняється правильне значення. А зовсім останніх відставальців, що прилетіли геть пізно, підмете фінальний прогін звірки по недавніх партиціях.

![Горизонтальна вісь часу події зліва (минуле) направо. Пунктирна червона вертикаль T₀ — мить, коли ввімкнули подвійний запис. Ліворуч T₀ — ряд блоків «історичні партиції (ts < T₀)» з підписами місяців. Під ними зелена стрілка «беквіл: від найстарішої партиції до T₀, пачками». Праворуч T₀ — зелений блок «живий край: подвійний запис, ts ≥ T₀». Угорі бурштиновий виносок «запізніле показання (ts < T₀) прилітає ПІСЛЯ беквілу → подвійний запис кладе його за event-ts; повтор упсертом безпечний», зі стрілкою вниз до шва біля T₀.](/root/course/progarch/nosql-migration-consideration/img/backfill-overlap.svg)
*Дві сили наповнюють нове сховище й не б'ються між собою: беквіл суне історію зліва до T₀, подвійний запис тримає живий край справа. Шов між ними тримає ідемпотентність — де беквіл і запис накладаються (зокрема на запізнілих показаннях), повторний upsert за (device_id, ts) просто кладе те саме значення в ту саму комірку. Тому перекриття безпечне, а прогалина — ні; уся дисципліна беквілу в тому, щоб не лишити прогалини.*

## Фаза 3. Звірка паритету — рахунок і вибірка

Беквіл добіг — але «добіг» ще не «переніс усе правильно». Перш ніж бодай думати про читання з нового, треба **довести** паритет двома перевірками, що ловлять різні хвороби.

Перша, груба й дешева, — **лічильник рядків** за кожною партицією-місяцем, з обох боків. Розбіжність у числі означає буквальну втрату або зайвину:

```sql
-- Скільки рядків у старому за кожен місяць історії (до межі T₀).
SELECT date_trunc('month', ts) AS month, count(*) AS n
FROM   telemetry
WHERE  ts < :t0
GROUP  BY 1 ORDER BY 1;
```

Той самий підрахунок жену по новому сховищу за ті самі місяці й порівнюю помісячно. Але рахунок бачить лише **кількість**, не **зміст**: партиції можуть збігтися рядок-у-рядок, а значення в них — розійтися (зсунувся часовий пояс, обрізалося дробове число, переплутались одиниці). Тому друга перевірка — **вибіркове читання**: беру багато випадкових пар «пристрій + вікно часу» й порівнюю фактично прочитане старе-проти-нового.

```python
# Вибіркова звірка: N випадкових (пристрій, вікно) — рівняємо реальні значення.
# Лічильник ловить грубу втрату рядків; вибірка — тиху псарію в самих значеннях.
def sample_parity(n=2000, window=timedelta(hours=1)):
    bad = []
    for _ in range(n):
        dev = random_device()
        lo  = random_ts(before=T0)
        old_rows = old.read(dev, lo, lo + window)         # [(ts, value), ...]
        new_rows = new.read(dev, lo, lo + window)
        if old_rows != new_rows:
            bad.append((dev, lo, len(old_rows), len(new_rows)))
    return bad          # порожньо → вибірка збіглася; є рядки → копати саме ці партиції
```

І ось де окупається весь наш порядок фаз. Якщо звірка показала розбіжність — **нічого страшного не сталося**, бо читання досі йдуть зі старого, і жоден користувач розбіжності не бачив. Відкат тут — це не аврал, а звичайна дія: знаходиш винні партиції за виводом звірки, перезапускаєш по них беквіл (він **ідемпотентний**, тож повтор безпечний навіть по вже наполовину перенесеному) і звіряєш ще раз. Крутиш цей цикл «звірка → долив → звірка», доки і рахунок, і вибірка не зійдуться. Правда весь цей час не рухалася зі старого — тому й ціна помилки нульова.

> 🔧 **Навіщо це.** Дві перевірки замість однієї — не перестраховка, а різні сита. Хто звіряє лише рахунок, той пропустить мовчазну псарію значень і дізнається про неї з кривого графіка через місяць після перемикання. Хто звіряє лише вибірку, той на чверті трильйона рядків легко промахнеться повз цілу загублену партицію. Рахунок бачить дірки, вибірка — брехню; докупи вони покривають обидва способи, якими копія розходиться з оригіналом.

## Фаза 4. Перемикання читань — поетапно, не стрибком

Аж тепер, коли нове сховище доведено дорівнює старому, рушаємо читання — і рушаємо їх **часткою**, а не рубильником. Маршрутизатор читань дивиться на керований ззовні `rollout` і шле в нове лише його частку трафіку; решта йде в старе. Частку повземо вгору сходинками — 1% → 10% → 50% → 100%, — на кожній сходинці спостерігаючи за латентністю, помилками й тим самим лічильником розбіжності. Будь-якої миті `rollout = 0` вертає весь трафік на старе **миттєво й без відновлення з бекапа** — бо старе нікуди не поділося й далі приймає подвійний запис.

```python
# Перемикач читання: частка rollout іде в нове, решта — у старе.
# Частку повземо 1% → 10% → 50% → 100%; будь-якої миті rollout=0 = миттєвий відкат.
def read_telemetry(dev, lo, hi):
    if hash_frac(dev) < config.rollout:      # стабільно за пристроєм, не мигтить від запиту до запиту
        try:
            return new.read(dev, lo, hi)
        except Exception:
            return old.read(dev, lo, hi)     # нове спіткнулось — тихий відкат на старе
    return old.read(dev, lo, hi)
```

Дрібниця, що варта уваги: частку рахуємо від **сталого хешу пристрою**, а не від випадку на кожен запит. Інакше той самий дашборд стрибав би між старим і новим від оновлення до оновлення, і будь-яка розбіжність блимала б у користувача перед очима. Стабільний хеш означає, що конкретний пристрій або вже цілком на новому, або цілком на старому, — і канаркова група росте передбачувано.

Чому взагалі поетапно, а не «раз — і все»? Бо великий стрибок збирає **весь ризик в одну незворотну мить**, а поетапність розсипає його на дрібні оборотні кроки. Ось ця різниця, поставлена поруч:

![Два способи перевезення поруч. Угорі «Big-bang»: одна широка червона рамка «ВІКНО ПРОСТОЮ: зупинити запис → dump → restore → перемкнути» і збоку червоний блок «крок назад = відновлення з бекапа (години, усе або нічого)»; підпис «простій вимірюється годинами-добою, відкату на крок немає». Унизу «Поетапно»: шість дрібних зелених воріт у ряд — 1 подв.запис, 2 беквіл, 3 звірка, 4 читання %-трафіку, 5 стоп старого, 6 DROP; під кожними з перших п'яти підпис «↩ оборотно», під шостими червоне «незворотно»; підпис «ризик розсипано на дрібні кроки, кожен, крім останнього, вертається флагом».](/root/course/progarch/nosql-migration-consideration/img/bigbang-vs-phased.svg)
*Big-bang концентрує всю небезпеку в один момент, де єдиний крок назад — багатогодинне відновлення з копії, а система весь цей час лежить. Поетапний шлях не має простою взагалі й до фази 6 не має жодного незворотного кроку: кожні ворота вертаються — беквіл перезапуском, читання прапорцем rollout. Та сама робота, але ризик роздрібнено на порції, кожну з яких можна відкотити окремо.*

## Фаза 5. Стоп запису в старе — перша майже-незворотна межа

Коли нове тримає 100% читань достатньо довго — не годину, а **soak-вікно** на кілька днів під повним живим навантаженням, без сплесків розбіжності й латентності, — можна перестати дублювати запис у старе. Прибираємо гілку `new` з обгортки подвійного запису (тепер вона єдина), і нове стає **одноосібним джерелом правди**.

Це перший крок, який не відкотиш прапорцем: щойно старе перестало отримувати свіжі показання, воно почало відставати, і повернути читання на нього вже не можна без нового беквілу у зворотний бік. Саме тому перед ним — найдовша витримка з усіх фаз: усе, що йшло не так, тут мало вже проявитися. Але й це ще не точка неповернення — **дані в старому цілі**, воно просто застигло. Якщо за день-два нове раптом покаже щось геть погане, у тебе досі є повна історія до моменту зупинки, з якої можна відбудуватися. Незворотним крок стане аж на наступній фазі.

## Фаза 6. Скидання партицій — повертаємо диск

Останнє — власне те, заради чого все затівалося: звільнити реляційну базу від чверті трильйона рядків, що душили ядро. І тут окупається те, що телеметрія від початку лежала **посекційно, по місяцях**: скинути відпрацьований місяць — це не мільярд повільних `DELETE`, що ще й роздують журнал транзакцій, а миттєва операція над метаданими. Робимо її у два такти, лишаючи собі вікно безпеки:

```sql
-- Такт 1: від'єднати партицію. Дані ще на диску, крок назад можливий —
-- партицію можна вернути на місце.
ALTER TABLE telemetry DETACH PARTITION telemetry_2026_01;

--  ... витримка кілька днів: нове сховище обслуговує ці дати без нарікань ...

-- Такт 2: аж тепер знищити й повернути диск. ОЦЕ — незворотно.
DROP TABLE telemetry_2026_01;
```

`DETACH` оборотний — від'єднана партиція лежить осторонь і за потреби вертається; `DROP` — ні, він і є та єдина точка неповернення, до якої вів увесь плейбук. Тому між ними — вікно, а самі партиції скидаємо від найстаріших до найновіших, лишаючи найсвіжіші наостанок. Коли впав останній `DROP`, робота скінчена: ядро дихає, телеметрія живе у своєму супутнику, простою не було, жодного рядка не згублено — а кожен крок аж до передостаннього можна було відкотити без слова «бекап».

## Складність і пастки

**Межу T₀ рахуй за часом події, не за прибуттям.** Уся конструкція тримається на тому, що беквіл бере `ts < T₀`, а подвійний запис — `ts ≥ T₀`, і ці дві множини стуляються без шва. Візьмеш межу за часом прибуття рядка на сервер — і запізніле показання з давнім `ts` провалиться між фазами: беквіл його вже проминув, а подвійний запис за прибуттям порахував «майбутнім» і не поклав куди слід. Перекриття лікує ідемпотентність, а от прогалину — ніщо; вона стає тихою втратою, яку помітиш нескоро.

**Не ідемпотентний приймач — і повтор плодить дублі.** Уся безпека перезапуску беквілу спирається на те, що нове сховище перезаписує за первинним ключем `(device_id, ts)`. Якщо ти надумаєш класти телеметрію в приймач із сурогатним автоключем або в суто дозаписне сховище без ключа-перезапису, то будь-який рестарт беквілу — а за шість діб він неминучий — наплодить копії тих самих показань. Форма ключа приймача — не деталь, це передумова всього плейбуку.

**Беквіл на повній швидкості задушить живий трафік.** Читати старе сховище на максимум, поки те саме сховище обслуговує живі дашборди, — певний спосіб покласти живе заради мертвого. Читай історію з **репліки**, а не з головного вузла; тримай ширину пулу воркерів і розмір пачки такими, щоб лишалася смуга живому; жени найважче вночі. Беквіл — марафон на кілька днів, а не спринт; він може дозволити собі бути повільним, а от живий трафік — ні.

**Звірка лише рахунком проґавить зіпсовані значення.** Однакове число рядків заколисує, але воно не бачить, що всередині: години, зсунуті на часовий пояс, обрізані дроби, переплутані одиниці дадуть той самий `count(*)` і зовсім інші графіки. Рахунок — лише перше сито; без вибіркового порівняння самих значень паритет не доведено.

**Скинеш старе зарано — зостанешся без сітки.** Спокуса дропнути партиції одразу по перемиканні читань велика — диск кличе. Але `DROP` незворотний, і якщо нове проявить хворобу на третій день, відкотитися вже нема куди. Найдовша витримка належить саме останнім двом фазам; диск почекає тиждень, а от загублену історію не вернеш.

**Розсинхрон подвійного запису тихо накопичується.** Кожен проковтнутий збій запису в нове — це майбутня розбіжність, і якщо не дивитися на лічильник **безперервно**, а лише під час звірки, то дізнаєшся про хронічну проблему (нове регулярно відкидає якийсь клас показань) аж наприкінці, коли перезаливати доведеться багато. Лічильник розбіжності — не звіт для фінальної фази, а сигнал тривоги, що має горіти від фази 1.

Спільна нитка всіх пасток одна: **не рухай правди, доки копію не доведено, і не роби незворотного, доки лишається дешевший крок назад.** Плейбук довший за big-bang рівно на стільки, скільки коштує ця обережність, — і саме цим купує «без простою й без утрати рядка».
