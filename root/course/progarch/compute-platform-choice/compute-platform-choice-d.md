Коли масштабна IoT-платформа Digital Homes розростається до 500 000 активних розумних будинків і понад 10 мільйонів підключених пристроїв, обчислювальне навантаження системи втрачає однорідність. Усередині backend-інфраструктури одночасно виникають чотири кардинально різні типи процесів: утримування 5 мільйонів довгоживучих gRPC-стримів телеметрії з постійним потоком 500 000 повідомлень на секунду, короткі сплески HTTP/REST-запитів від мобільних додатків на рівні 50 000 rps, ефемерні асинхронні виклики вебхуків при спрацюванні тривог (від нульового трафіку вночі до 20 000 rps під час негоди), а також важка аналітика відеопотоків із камер спостереження на базі алгоритмів машинного навчання, що вимагає прямого доступу до апаратних графічних прискорювачів (GPU).

Перша спроба спростити інфраструктуру шляхом вибору однієї «універсальної» обчислювальної платформи (англ. *Compute Platform*) для всіх чотирьох сервісів неодмінно закінчується інфраструктурною катастрофою. Якщо перевести всі сервіси виключно на безсерверні функції (Serverless), щомісячний рахунок від хмарного провайдера за утримування мільйонів idle-сокетів сягає сотень тисяч доларів, а затримка холодного старту (Cold Start) в 500 мілісекунд руйнує критичні сценарії відчинення замків та сповіщень про пожежу. Якщо ж побудувати власну інфраструктуру на фізичних серверах (Bare Metal), команда опиняється під завалом операційного обслуговування ОС, оновлень кворуму Kubernetes та нічних аварійних заміною дисків, витрачаючи до 40% інженерного часу на підтримку заліза замість розвитку продукту.

Ефективна архітектура обчислювальної платформи не шукає єдиний «найкращий» інструмент. Вона розкладає всі робочі навантаження системи на чотири фундаментальні вектори — чутливість до затримки, профіль утилізації, загальну вартість володіння (TCO) та операційний бюджет команди — і підбирає для кожного підсервісу оптимальне середовище виконання: Serverless, Managed Kubernetes чи Bare Metal.

Детально про те, як індустрія пройшла шлях від монолітних фізичних серверів до сучасного різноманіття обчислювальних середовищ, викладено в 📜 [Історії еволюції обчислювальних парадигм](root:progarch/scale-and-load/compute-platform-choice/hist-compute-paradigm-shifts.md).

> 🔧 **Навіщо це.** Прагнення до інфраструктурної монокультури — це поширений антишаблон у Highload-архітектурі. Намагання запхати тривалий стрімінг у Serverless або, навпаки, тримати цілодобовий кластер Kubernetes ради двох фонових cron-задач однаково спалює ресурси компанії. Розуміння меж ефективності кожної платформи дозволяє побудувати гібридне середовище виконання, де кожен долар, витрачений на compute, дає максимальну продуктивність і стабільність.

## Чотири стовпи вибору: Затримка, Утилізація, Економіка та Операції

Щоб прийняти обґрунтоване рішення про вибір обчислювальної платформи, кожен мікросервіс системи Digital Homes оцінюється за чотирма незалежними вимірами.

```
                      +-----------------------------------+
                      |   Вектори оцінки Compute-платформ |
                      +-----------------------------------+
                                        |
        +------------------+------------+------------+------------------+
        |                  |                         |                  |
        v                  v                         v                  v
+---------------+  +---------------+         +---------------+  +---------------+
| 1. Затримка   |  | 2. Утилізація |         | 3. Фінанси    |  | 4. Операції   |
| - Cold Start  |  | - Baseline    |         | - TCO & Capex |  | - Control Pl. |
| - Jitter (p99)|  | - Burstiness  |         | - Pay-per-use |  | - Ops Footprint|
| - Isolation   |  | - Bin-packing |         | - Reserved    |  | - Hardware/Kernel|
+---------------+  +---------------+         +---------------+  +---------------+
```

### 1. Чутливість до затримки та ізоляція виконання (Latency & Execution Isolation)

Латентність обробки запиту розпадається на дві складові: базовий час виконання коду та затримку ініціалізації середовища (Cold Start).

- **Бессерверні середовища (Serverless / Fargate):** При надходженні запиту до неактивної функції провайдер повинен виділити мікровіртуальну машину (MicroVM), змонтувати образ, ініціалізувати рантайм (Node.js, JVM, Python) та виконати глобальний код ініціалізації. Це спричиняє затримку холодного старту від 50 мілісекунд для C++/Go до 2–5 секунд для Java чи важких Python-контейнерів. Крім того, в Multi-Tenant середовищі присутній ризик «галасливого сусіда» (Noisy Neighbor), коли сусідній процес на тому ж фізичному хості тимчасово забирає L3-кеш CPU або мережеву пропускну здатність.
- **Оркестровані контейнери (Kubernetes):** Поди Kubernetes уже запущені й тримають у пам'яті відкриті басейни з'єднань із базами даних. Затримка p99 є стабільною і визначається лише мережевим RTT усередині кластера (0.5–2 ms). Завдяки механізмам `cgroups` можна жорстко зафіксувати ресурси CPU (`limits = requests`), мінімізувавши переключення контексту.
- **Пряме залізо (Bare Metal / VM):** Забезпечує абсолютний контроль над затримками. Інженери можуть ізолювати конкретні ядра CPU (`CPUAffinity`, `numactl`), вимкнути гіперпотоковість (Hyper-Threading), налаштувати переривання мережевих карт (IRQ pinning) та використовувати розширити eBPF/DPDK для прямої обробки мережевих пакетів у просторі користувача. Це гарантує ультра-низьку затримку p99 < 1 ms із нульовим джиттером (Jitter).

### 2. Профіль утилізації та коефіцієнт спалаховості (Utilization Profile & Elasticity)

Профіль навантаження сервісу вимірюється співвідношенням середнього споживання ресурсів до пікового значення (`U = CPU_avg / CPU_peak`):

1. **Плаский цілодобовий фоновий потік (`U ≥ 70%`):** Сервіс постійно споживає значний обсяг CPU та RAM (наприклад, сервіси прийому телеметрії чи брокери повідомлень).
2. **Прогнозовані добові цикли (`30% ≤ U ≤ 60%`):** Активність зростає у робочі години й падає вночі (наприклад, мобільний REST API для мешканців).
3. **Спалахове пилкоподібне навантаження (`U < 15%`):** Запити надходять хаотичними спалахами, між якими система годинами простоює (наприклад, обробники подій відкриття дверей, верифікаційні електронні листи, нічні cron-задачі).

Для спалахового навантаження традиційні виділені сервери є економічно збитковими, оскільки 85–90% часу залізо спалює електрику без користі. І навпаки, для плаского 24/7 потоку бессерверна оплата за кожну мілісекунду перетворюється на величезну переплату.

### 3. Фінансова модель та TCO (Total Cost of Ownership)

Економіка обчислювальної платформи спирається на три моделі тарифікації:

- **Pay-per-use (Serverless):** Плата нараховується суворо за обсяг виділеної оперативної пам'яті, помножений на тривалість виконання запиту у мілісекундах (`GB·sec`). Поріг входження дорівнює нулю, але вартість однієї процесорної секунди містить 400–600% маржі провайдера.
- **Hourly Allocated Capacity (Kubernetes / IaaS VM):** Плата нараховується за оренду віртуальних або фізичних вузлів за годину, незалежно від того, чи завантажений процесор на 1% чи на 99%. Економічна ефективність досягається за рахунок щільного пакування контейнерів (Bin-packing) та використання знижок за довгострокове зарезервування (Reserved Instances, Savings Plans) або переривані ноди (Spot Instances).
- **Physical Capex / Fixed Opex (Bare Metal):** Купівля заліза або довгострокова оренда стійок у дата-центрі. Найнижча вартість 1 vCPU/sec на ринку, але високий початковий капітальний бар'єр (Capex) та наявність плати за нехолостий простій.

### 4. Операційне навантаження та когнітивна складність (Ops Footprint)

Операційна вартість вимірюється обсягом інженерних зусиль, необхідних для підтримки працездатності платформи (Platform Engineering Tax):

- **NoOps (Serverless):** Провайдер бере на себе патчинг ядра ОС, масштабування заліза, балансування навантаження та ізоляцію безпеки. Розробник оперує виключно бізнес-кодом.
- **Managed Kubernetes (EKS / GKE):** Провайдер управляє кворумом Control Plane (etcd, API Server), але команда зобов'язана самостійно налаштовувати ingress-контролери, CNI-мережі, сервісні сітки (Service Mesh), політики безпеки PodSecurity, моніторинг Prometheus та оновлювати версії Kubernetes кожні 4 місяці.
- **Self-Hosted Infrastructure (Bare Metal / OpenStack):** Повний спектр операційної відповідальності: заміна збійного обладнання, побудова фізичних мереж BGP/Leaf-Spine, оновлення BIOS/IPMI, управління системними демонами, резервне копіювання та захист від фізичних аварій у дата-центрі.

## Глибинна анатомія ізоляції та механізмів ядра Linux

Переваги та обмеження кожної обчислювальної платформи прямо випливають з того, яким чином ядро Linux або гіпервізор ділить фізичні ресурси обладнання між процесами.

### 1. Механізми cgroups v2 та пастка CFS Throttling у Kubernetes

У середовищі Kubernetes обмеження використання CPU реалізується за допомогою підсистеми ядра Linux `cgroups v2` та планувальника Completely Fair Scheduler (CFS). Параметр `resources.limits.cpu: "2000m"` конвертується в два конфігураційні файли ядра у директорії `/sys/fs/cgroup/`:

- `cpu.max`: Містить два числа — квоту (`quota`) у мікросекундах та період (`period`). Для 2 vCPU (`2000m`) ядро встановлює `quota = 200000` мікросекунд при `period = 100000` мікросекунд (100 ms).
- **Пастка CFS Throttling:** Якщо багатопотоковий застосунок усередині поду випускає 8 паралельних потоків обчислень, вони сукупно вичерпують квоту в 200 000 мікросекунд усього за 25 мілісекунд від початку 100-мілісекундного періоду. Протягом наступних 75 мілісекунд ядро Linux повністю примусово зупиняє (throttles) виконання поду. На моніторингу завантаження CPU ноди може становити лише 20%, але p99 латентність застосунку стрибає до 100 мілісекунд через очікування наступного кванта часу CFS.

Щоб уникнути CFS Throttling у Kubernetes для latency-sensitive сервісів, застосовують клас якості обслуговування `Guaranteed QoS` із задіянням статичного плагіна `kubelet --cpu-manager-policy=static`, який виділяє подійні процеси на ексклюзивні фізичні ядра без обмежень CFS quota.

### 2. Санбоксинг MicroVM та холодний старт у Serverless

У бессерверних платформах (AWS Lambda, Fargate) ізоляція досягається через технологію мікровіртуалізації Firecracker. Замість використання спільних іменних просторів ядра хоста (`namespaces`), Firecracker запускає мінімалістичний екземпляр ядра Linux у режимі KVM:

1. **Етапи запуск MicroVM:**
   - Створення пристроїв vCPU та vRAM через `ioctl(/dev/kvm)`.
   - Ініціалізація спрощеного BIOS/bootloader та завантаження ядра Linux (2–5 ms).
   - Монтування ефемерного дискового образу та ініціалізація рантайму (Node.js/Python/Go) (15–100 ms).
   - Виконання глобального коду ініціалізації файлу (до кількох секунд при підключенні до БД).

2. **Переваги та ціна:** MicroVM забезпечує 100% захист від уразливостей типу Container Escape, але створює неминучу затримку холодного старту при першому запиті після періоду простою.

### 3. Архітектура NUMA та direct hardware access у Bare Metal

На фізичному сервері (Bare Metal) із двома процесорними сокетами (наприклад, Intel Xeon або AMD EPYC) оперативна пам'ять розділена на декілька локальних вузлів NUMA (Non-Uniform Memory Access). Якщо процес, запущений на сокеті 0, звертається до оперативної пам'яті, підключеної до сокета 1, затримка доступу зростає у 2.5 рази через шину міжпроцесорного з'єднання (UPI/Infinity Fabric).

На Bare Metal архітектор може вручну прив'язати мережеву карту та процес обробки телеметрії до одного NUMA-вузла за допомогою утиліти `numactl --membind=0 --cpubind=0`, повністю усунувши затримки міжсокетового обміну та досягаючи продуктивності до 10 мільйонів пакетів на секунду на один сервер.

## Простеження та діагностика обчислювального середовища через sysfs та procfs

Діагностика поведінки обчислювальної платформи під Highload-навантаженням вимагає низькорівневого аналізу метрик ядра Linux. Архітектор повинен уміти орієнтуватися у файлових системах `procfs` (`/proc`) та `sysfs` (`/sys`), де ядро експонує реальний стан підсистем `cgroups` та `CFS scheduler`.

### 1. Простеження тротлінгу CPU у cgroups v2

Для перевірки наявності тротлінгу поду у Kubernetes або контейнера Docker інженер аналізує файл `/sys/fs/cgroup/cpu.stat` усередині файлової системи контейнера:

```
$ cat /sys/fs/cgroup/cpu.stat
usage_usec 482910492
user_usec 391029401
system_usec 91881091
nr_periods 120400
nr_throttled 15420
throttled_usec 891048102
```

Значення `nr_throttled / nr_periods > 0.05` свідчить про те, що у понад 5% часових квантів процес примусово призупинявся ядром Linux через вичерпання CFS quota. Рішенням є підвищення `limits.cpu` або перехід на static cpu policy.

### 2. Діагностика переповнення сокетів та дефіциту дескрипторів

У високонавантажених вхідних шлюзах (IoT Ingest) часто виникають таємничі відмови підключень при низькому споживанні CPU. Аналіз файлу `/proc/net/softnet_stat` дає змогу виявити скидання мережевих пакетів через переповнення черги мережевої карти:

```
$ cat /proc/net/softnet_stat
00482910 00000000 00001402 ...
```

Третя колонка (`00001402` в 16-іншій системі) вказує на кількість пакетів, скинутих через перевищення параметра `net.core.netdev_max_backlog`. На Serverless інженер позбавлений доступу до цих файлів і не може діагностувати причину розривів сокетів, тоді як на Bare Metal це виправляється однією командою `sysctl -w net.core.netdev_max_backlog=100000`.

## Математика утилізації та точка рівноваги (Breakeven Analysis)

Економічний вибір між Serverless, Managed Kubernetes та Bare Metal зводиться до знаходження критичної точки утилізації `U_crit`, у якій криві загальних витрат платформ перетинаються.

Детально формальний математичний вивід та числові рівняння TCO наведено в 🧮 [Математичній моделі TCO та утилізації compute](root:progarch/scale-and-load/compute-platform-choice/math-compute-unit-economics.md).

Загальне рівняння щомісячних витрат для трьох моделей визначається так:

```
TCO_serverless = N_req · P_req + (N_req · T_sec) · M_gb · P_gbsec
TCO_k8s        = P_control_plane + N_nodes(U) · P_node_month + C_ops_k8s
TCO_baremetal  = N_servers · P_server_month + C_datacenter + C_ops_hw
```

Залежність сукупних витрат TCO від рівня середньої утилізації ресурсів висвітлено на діаграмі нижче.

![Порівняння кривих TCO обчислювальних платформ](/root/course/progarch/compute-platform-choice/img/compute-cost-curves.svg)
*Залежність щомісячних витрат TCO від середньої утилізації системи виявляє три чіткі економічні зони: Serverless домінує при утилізації < 18%, Managed Kubernetes є оптимальним у діапазоні 18–68%, а Bare Metal стає найдешевшим при цілодобовому завантаженні > 68%.*

Графік виокремлює три ключові економічні зони:

1. **Зона 1: Serverless Dominance (`0 ≤ U < 18%`):**
   При низькому або сильно спалаховому трафіку витрати на Serverless є мінімальними, оскільки оплата за простій дорівнює точно нулю. Спроба розгорнути для такого навантаження кластер Kubernetes вимагає сплати фіксованої вартості Control Plane та мінімального кворуму з трьох нод для високої доступності (High Availability), що створює високий початковий поріг витрат.

2. **Зона 2: Kubernetes Optimum (`18% ≤ U ≤ 68%`):**
   При зростанні середньої утилізації крива витрат Serverless стрімко піднімається вгору через високу вартість 1 GB-sec. У цій зоні Managed Kubernetes демонструє найкращу економіку: механізми Horizontal Pod Autoscaler (HPA) та Cluster Autoscaler динамічно додають та видаляють ноди, підтримуючи утилізацію кластера на рівні 70%, а щільне пакування контейнерів (Bin-packing) витискає максимум із виділеного заліза.

3. **Зона 3: Bare Metal Efficiency (`U > 68%`):**
   Коли навантаження стає монотонним і цілодобовим (наприклад, прийом 500 000 повідомлень телеметрії на секунду), накладні витрати на хмарну націнку провайдера у формі On-Demand нод переважають вартість оренди фізичного заліза. Пряма оренда або купівля серверів (Bare Metal) дає від 3-кратного до 5-кратного виграшу у підсумковому TCO, зорюючи витрати на одиницю обчислень до фізичного мінімуму.

## Порівняльна анатомія трьох обчислювальних моделей

Для систематизації архітектурного вибору розберемо технологічну анатомію кожної обчислювальної платформи.

```
+-----------------------------------------------------------------------------------+
|                        Платформи виконання (Compute Models)                        |
+-----------------------------------------------------------------------------------+
| 1. Serverless / Fargate   | 2. Managed Kubernetes       | 3. Bare Metal / Direct VM|
| - Sandbox / MicroVM       | - Linux Containers (Docker) | - Physical CPU / KVM     |
| - Pay-per-ms              | - Bin-packing & HPA         | - CPU Affinity & eBPF    |
| - Cold start risk         | - Managed Control Plane     | - Full Kernel Control    |
| - Low Ops                 | - Medium/High Ops           | - Max Ops                |
+-----------------------------------------------------------------------------------+
```

### 1. Serverless / Container Fargate (AWS Lambda, Cloud Run, AWS Fargate)

В основі сучасного бессерверного обчислення лежить технологія легковагової мікровіртуалізації (наприклад, AWS Firecracker). Замість того щоб ділити спільно ядро хостової ОС між чужими контейнерами, провайдер запускає кожен запуск функції у власному мінімалістичному KVM-контейнері з виділеним ядром Linux.

- **Переваги:** Абсолютна еластичність (масштабування від 0 до 10 000 паралельних виконань за секунди), відсутність плати за простій, нульові витрати на патчинг ОС та безпеку ядра.
- **Недоліки:** Наявність холодного старту, жорсткі ліміти на час виконання (максимум 15 хвилин для AWS Lambda), відсутність підтримки довгоживучих TCP/gRPC сокетів, обмежений обсяг тимчасового диска (/tmp до 10 GB) та відсутність прямого доступу до апаратних прискорювачів чи низькорівневих мережевих сокетів.

### 2. Managed Kubernetes (AWS EKS, Google GKE, Azure AKS)

Kubernetes оперує контейнерами Linux (OCI), об'єднаними в Поди (Pods), які розміщуються на пулі віртуальних або фізичних вузлів. Наданий хмарою Managed Control Plane бере на себе розгортання etcd та API-сервера, позбавляючи команду найважчої частини роботи з підтримки консенсусу.

- **Переваги:** Повний контроль над конфігурацією середовища, підтримка будь-яких мережевих протоколів (HTTP/1.1, HTTP/2, gRPC, WebSockets, QUIC), відсутність холодних стартів для запущених подів, багата екосистема відкритих інструментів (Helm, Prometheus, Istio, ArgoCD) та можливість прозорого автомасштабування за будь-якими призначеними для користувача метриками через KEDA (Kubernetes Event-driven Autoscaling).
- **Недоліки:** Високий поріг входу та операційна складність. Команда змушена управляти конфігураціями ресурсів, вирішувати проблеми сіткового інгресу, стежити за лімітами пам'яті (`OOMKilled`) та регулярними оновленнями версій кластера.

### 3. Bare Metal / Direct VM Fleet (Physical Racks, IaaS Dedicated EC2)

Модель прямого розгортання передбачає запуск застосунків безпосередньо на операційній системі фізичного сервера або виділеної віртуальної машини верхнього рівня без проміжних шарів оркестрації.

- **Переваги:** Максимально можлива продуктивність заліза. Доступ до інструкцій AVX-512, прямого зчитування даних із GPU через RDMA (Remote Direct Memory Access), налаштування системних параметрів ядра (`sysctl`, `net.core.somaxconn`, `tcp_rmem`), прив'язка потоків виконання до конкретних фізичних ядер (CPU Pinning) та використання eBPF для високошвидкісної фільтрації мережевих пакетів.
- **Недоліки:** Відсутність автоматичної еластичності. Масштабування вимагає ручного або скриптового розгортання нових машин (Ansible, Terraform), а будь-яка збійна планка RAM або дисковий масив вимагають фізичного втручання та налаштованої системи самовідновлення на рівні програми.

Порівняння декларативних конфігурацій та параметрів розгортання для кожної з платформ наведено в 📋 [Декларативних специфікаціях та контрактах розгортання compute-платформ](root:progarch/scale-and-load/compute-platform-choice/api-compute-platform-contract.md).

Загальну матрицю компромісів та рекомендованих сфер застосування підсумовано на діаграмі нижче.

## Практична матриця прийняття рішень для Digital Homes

Застосуємо розроблену методологію до чотирьох ключових компонентів системи Digital Homes і визначимо для кожного оптимальне середовище виконання.

```
                                  +---------------------------------------+
                                  |   Компоненти платформи Digital Homes  |
                                  +---------------------------------------+
                                                      |
        +--------------------------+------------------+-------------------+--------------------------+
        |                          |                                      |                          |
        v                          v                                      v                          v
+-----------------------+  +-----------------------+              +-----------------------+  +-----------------------+
| 1. Ingest Gateway     |  | 2. Core Mobile API    |              | 3. Event Webhooks     |  | 4. Video AI Analytics |
| - 5M gRPC streams     |  | - REST / GraphQL      |              | - Spiky / Intermittent|  | - Real-time GPU       |
| - 500k msg/s          |  | - Latency < 30ms      |              | - Alarm notifications |  | - High RAM & PCIe     |
| - Latency < 2ms       |  | - 50k rps peak        |              | - Latency < 200ms     |  | - Latency < 15ms      |
|                       |  |                       |              |                       |  |                       |
| 🎯 BARE METAL / VM    |  | 🎯 MANAGED KUBERNETES |              | 🎯 SERVERLESS FARGATE |  | 🎯 BARE METAL / GPU   |
+-----------------------+  +-----------------------+              +-----------------------+  +-----------------------+
```

### 1. Вхідний шлюз телеметрії хабів (IoT Ingest Gateway)

- **Профіль навантаження:** 5 мільйонів постійно відкритих gRPC/HTTP2 з'єднань від домашніх хабів. Цілодобовий потік телеметрії в 500 000 msg/s. Вкрай висока утилізація CPU та мережевих карт (`U > 80%`).
- **Вимоги до затримки:** p99 < 2 ms. Будь-які затримки призводять до розриву TCP-сокетів і перезапуску мільйонів з'єднань (з'єднувальний шторм, Connection Storm).
- **Вибір платформи:** **Bare Metal або виділені IaaS VM у пулі.**
- **Обґрунтування:** Serverless категорично дискваліфікується через неможливість утримувати довгоживучі TCP-сокети та астрономічну ціну 24/7 виконання. Kubernetes на звичайних нодах створює накладні витрати на проксування сокетів у kube-proxy. Прямі сервери з тюнінгом мережевого стека ядра (`net.ipv4.tcp_rmem`, `SO_REUSEPORT`) та eBPF-маршрутизацією забезпечують найвищу щільність сокетів на один сервер (до 500 000 сокетів на ноду) при найнижчому TCO.

### 2. Основний мобільний та веб-API (Core Mobile API)

- **Профіль навантаження:** Денний цикл активності користувачів. Пікові 50 000 rps о 18:00–21:00, падіння до 3 000 rps вночі. Середня утилізація `U ≈ 40%`. Безплатформовий stateless-код.
- **Вимоги до затримки:** p99 < 30 ms. Холодний старт небажаний, оскільки користувач очікує миттєвого відкриття додатка.
- **Вибір платформи:** **Managed Kubernetes (AWS EKS / GKE).**
- **Обґрунтування:** Ідеальний баланс між ціною та операційною гнучкістю. HPA масштабує кількість подів від 20 уночі до 200 під час вечірнього піку. Використання Spot-нод для 70% покриття пікової потужності зменшує витрати на інфраструктуру на 60% порівняно з On-Demand нодами, а запущені Поди повністю виключають холодні старти для клієнтів.

### 3. Обробник тривог та асинхронних подій (Event Webhooks & Async Workers)

- **Профіль навантаження:** Асинхронна обробка подій спрацювання датчиків (відчинення дверей, протікання води, пожежна тривога). Протягом 95% часу трафік близький до нуля. При проходженні грозового фронту над містом виникає миттєвий спалах до 20 000 подій на секунду (`U < 5%`).
- **Вимоги до затримки:** p99 < 200 ms (допустима затримка в межах 100–200 мілісекунд для формування push-сповіщення чи SMS).
- **Вибір платформи:** **Serverless (AWS Lambda / AWS Fargate / Cloud Run).**
- **Обґрунтування:** Споживання ресурсів у цій зоні є суворо пилкоподібним. Тримати постійний кворум серверів для обробки пожежних тривог означає платити за 95% простою. Serverless забезпечує миттєве масштабування від 0 до 10 000 паралельних обробників під час спалаху, а вночі вартість утримання системи дорівнює точно нуль доларів.

### 4. Модуль аналітики відеопотоків та штучного інтелекту (Video AI Analytics)

- **Профіль навантаження:** Постійний аналіз відеопотоків із 50 000 зовнішніх камер для розпізнавання облич та автономерів. Обчислення вимагають інтенсивних матричних множень на GPU.
- **Вимоги до затримки:** p99 < 15 ms для реального часу розпізнавання руху. Потрібен прямий доступ до пам'яті GPU через CUDA/TensorRT та PCIe шину.
- **Вибір платформи:** **Bare Metal / Dedicated GPU VM Fleet.**
- **Обґрунтування:** Контейнерні бессерверні середовища не надають виділеного прямого доступу до тензорних ядер GPU без значної націнки провайдера. Запуск відеоаналітики на фізичних серверах із графічними прискорювачами (наприклад, NVIDIA A10G / T4) та налаштованими драйверами CUDA забезпечує 100% утилізацію коштовних GPU-чипів без накладних витрат віртуалізації.

Інтерактивний двигун обчислення інтегрального балу для будь-якого довільного робочого навантаження з кодом на C++ та Python реалізовано в ⚙️ [Матриці прийняття рішень вибору compute-платформи](root:progarch/scale-and-load/compute-platform-choice/proj-platform-decision-matrix.md).

У підсумку, сучасна архітектура обчислень високонавантаженої системи — це не вибір «однотипної платформи на всі випадки життя», а прагматичний розподіл сервісів за їхнім фізичним та економічним профілем. Комбінуючи Bare Metal на вхідних стрімах, Kubernetes на основному API та Serverless на ефемерних подійних функціях, архітектор досягає максимальної надійності та найнижчого TCO інфраструктури.
