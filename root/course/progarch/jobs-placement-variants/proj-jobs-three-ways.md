# ⚙️ Одна задача, три черги — і тест, що ловить сироту

Мапу ми вже накреслили: «черга задач» — це роль, а не продукт, і одне питання про транзакцію розтинає всі варіанти надвоє. Мапа показує напрямки. Але напрямок — це не дорога; дорогу дає лише код, що лягає на диск і запускається. Тож візьмімо **одну** конкретну задачу — «користувач залив кліп, перекодувати його треба у фоні» — і напишімо її **тричі**, кожен раз на своєму субстраті.

Головний приз тут — не три способи покласти задачу. Це вміє будь-хто. Приз — **тест наприкінці**, який відтворює осиротілий кліп на подвійному записі (база зафіксувалась, а постановка задачі — ні) і на очах гоїть його транзакційним outbox'ом; плюс воркер, якому ту саму задачу можна вручити двічі, і він не перекодує кліп двічі. Тобто ми зараз зробимо те абстрактне питання — «чи ділить постановка задачі транзакцію із записом?» — **виконуваним**: перетворимо його на код, що падає червоним рівно тоді, коли відповідь «ні», і зеленіє, коли «так».

## Задача

Випишемо точно, що будуємо. Користувач шле кліп; ми записуємо факт у базу й хочемо, щоб окремий воркер згодом його перекодував. Одна таблиця фактів, одна таблиця задач, одна таблиця результатів — і, для третього варіанта, таблиця-outbox:

```sql
CREATE TABLE clips (
  id         BIGSERIAL PRIMARY KEY,
  home_id    BIGINT      NOT NULL,
  url        TEXT        NOT NULL,          -- сирий файл у сховищі
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE jobs (
  id         BIGSERIAL PRIMARY KEY,
  type       TEXT        NOT NULL,
  payload    JSONB       NOT NULL,
  status     TEXT        NOT NULL DEFAULT 'ready',   -- ready | running | done
  locked_by  TEXT,                                   -- який воркер узяв
  locked_at  TIMESTAMPTZ,                            -- коли взяв (для оренди)
  attempts   INT         NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX jobs_ready_idx ON jobs (id) WHERE status = 'ready';

CREATE TABLE renditions (              -- РЕЗУЛЬТАТ перекодування
  clip_id BIGINT NOT NULL,
  profile TEXT   NOT NULL,             -- напр. 'h264-720p'
  path    TEXT   NOT NULL,
  PRIMARY KEY (clip_id, profile)       -- один вихід на (кліп, профіль) — ключ ідемпотентності
);

CREATE TABLE outbox (
  id           BIGSERIAL PRIMARY KEY,
  topic        TEXT        NOT NULL,
  payload      JSONB       NOT NULL,
  delivered_at TIMESTAMPTZ,            -- NULL, поки relay не доправив у брокер
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Від кожного способу хочемо дві речі: **поставити** задачу під факт кліпа й **забрати** її воркером. І один інваріант, який ми будемо захищати кодом, а не обіцянкою: *кожен зафіксований кліп рано чи пізно отримує рівно одне перекодування, і виконати задачу двічі лишає один результат, а не два*. Перше — про те, щоб задача не загубилась; друге — про те, щоб дубль її не задвоїв. Тримаймо обидва в голові весь розбір: майже все, що ми напишемо, служить одному з них.

Мова — TypeScript для застосунку й воркера (це рідний дім вебобробника «залив кліп») і Python поряд, де другий погляд щось додає; запити — SQL. Домен тут загальний, серверний, тож перформанс-мови в тіло не тягнемо — вузьке місце перекодування не в мові обробника, а в самому кодеку.

## Спосіб А: черга в памʼяті — і тест, що дивиться, як задача випаровується

Найдешевша черга — структура даних просто в процесі. Опишемо її чесним маленьким класом, щоб було що тестувати, а не ховаймо за незачеканою обіцянкою:

:::tabs
```ts
type Job = { type: string; payload: unknown };

class InMemoryQueue {
  private items: Job[] = [];
  enqueue(type: string, payload: unknown) { this.items.push({ type, payload }); }
  take(): Job | undefined { return this.items.shift(); }
  depth(): number { return this.items.length; }
}
```
```py
from collections import deque

class InMemoryQueue:
    def __init__(self):
        self._items = deque()
    def enqueue(self, type_, payload):
        self._items.append({"type": type_, "payload": payload})
    def take(self):
        return self._items.popleft() if self._items else None
    def depth(self):
        return len(self._items)
```
:::

Обробник кладе задачу в цю чергу й одразу відповідає; окремий цикл її розбирає. Затримка субмілісекундна, серіалізації нема, нової коробки в інфраструктурі — теж. І рівно тут чигає пастка, яку найкраще не описати, а **показати тестом**. Питання одне: що станеться з відкладеною роботою, якщо процес перезапуститься саме зараз? Рестарт процесу — це не магія; це просто новий екземпляр із порожніми полями. Напишімо це буквально:

```ts
test("черга в памʼяті губить роботу на рестарті", () => {
  let q = new InMemoryQueue();
  q.enqueue("transcode", { clipId: 42 });     // кліп 42 залито, задача стоїть
  expect(q.depth()).toBe(1);

  // Деплой, падіння, рестарт = НОВИЙ процес = НОВА, порожня черга:
  q = new InMemoryQueue();

  expect(q.depth()).toBe(0);   // задача зникла. Кліп у базі є, борг — випарувався.
});
```

Оцей `q = new InMemoryQueue()` — і є весь механізм катастрофи. Черга жила в полях одного об'єкта одного процесу; не стало процесу — не стало полів. Кліп, якщо ми встигли його записати, лишився в базі; задача на перекодування зникла **без сліду в жодному лозі**. Ніхто навіть не дізнається, що є кліп без відео, — бо запису про борг ніде нема. Тест зеленіє на `depth() === 0`, і саме ця зелень — доказ провалу: ми хотіли, щоб робота пережила рестарт, а вона його не пережила.

До цього додається дві менші біди. Черга **не виходить за процес**: три репліки застосунку — три приватні черги, які не бачать одна одну. І якщо задачі надходять швидше, ніж розбираються, `items` росте, доки не зжере памʼять, — бо тут навіть нема кому вести [протитиск](book:programming/backpressure-local), тобто пригальмувати того, хто кладе, коли той, хто бере, не встигає. Тому місце цього способу — рівно робота, яку не шкода втратити: прогріти кеш, згорнути метрику. Кліп, за який заплатили, сюди класти не можна, і тест щойно пояснив чому.

## Спосіб Б: черга в базі — атомарна постановка й чесний забір

Крок правіше — і черга переїжджає в базу, яку застосунок і так тримає. Тут зʼявляється властивість, заради якої все й затівалось: **постановка задачі неподільна із записом факту**. Кладемо кліп і задачу під нього **в одну транзакцію**:

:::tabs
```ts
import { Pool } from "pg";

async function uploadClip(pool: Pool, homeId: number, url: string): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(
      "INSERT INTO clips (home_id, url) VALUES ($1, $2) RETURNING id",
      [homeId, url]);
    const clipId = rows[0].id;
    await client.query(
      "INSERT INTO jobs (type, payload) VALUES ('transcode', $1::jsonb)",
      [JSON.stringify({ clipId })]);
    await client.query("COMMIT");     // кліп І задача лягають разом — або жоден
    return clipId;
  } catch (e) {
    await client.query("ROLLBACK");   // відкотилось — задачі теж нема, ніби й не було
    throw e;
  } finally {
    client.release();
  }
}
```
```py
from psycopg_pool import AsyncConnectionPool
from psycopg.types.json import Jsonb

async def upload_clip(pool: AsyncConnectionPool, home_id: int, url: str) -> int:
    async with pool.connection() as conn:          # транзакція — контекст
        async with conn.transaction():             # вихід без винятку → COMMIT
            row = await (await conn.execute(
                "INSERT INTO clips (home_id, url) VALUES (%s, %s) RETURNING id",
                (home_id, url))).fetchone()
            clip_id = row[0]
            await conn.execute(
                "INSERT INTO jobs (type, payload) VALUES ('transcode', %s)",
                (Jsonb({"clipId": clip_id}),))     # виняток усередині → ROLLBACK усього
        return clip_id
```
:::

Немає жодної шпарини, крізь яку кліп міг би існувати без своєї задачі: обидва INSERT-и — усередині однієї межі, тож фіксуються разом або відкочуються разом. Клас багів «записали факт, а задача загубилась» тут **не існує як можливість** — не бо ми акуратні, а бо база фізично не дає цим двом записам розійтися. Цю неподільність дає [транзакційність (ACID)](book:programming/transactions-acid): атомарність означає, що набір записів у транзакції — неподільне ціле.

Тепер забір. Пул воркерів має розбирати таблицю так, щоб двоє не вхопили одну задачу й ніхто не чекав на чужий зайнятий рядок. Це і є [конкурентні споживачі](book:programming/competing-consumers) — взаємозамінні воркери над спільною чергою; ключ до них у Postgres — `FOR UPDATE SKIP LOCKED`: воркер бере рядок під замок, а зайняті іншими **перескакує**, замість ставати в чергу за ними.

Наївний хід — «взяти рядок під замок, перекодувати, поставити `done`, закомітити» — має тиху ваду **саме для нашої задачі**. Перекодування триває хвилини. Тримати транзакцію (а з нею й замок на рядку, і зайняте зʼєднання) відкритою всі ці хвилини — отруйно: довгі транзакції розпухають, зʼєднання не вертаються в пул, `VACUUM` не може прибрати старі версії рядків. Тож для довгих задач забір роблять **у два такти**: спершу коротка транзакція, що лише *claim'ить* задачу — перемикає `ready → running` і ставить оренду (хто взяв і коли), — а сама важка робота йде **поза** будь-яким тримання замка:

```sql
-- КОРОТКИЙ claim: атомарно вихопити одну готову задачу й позначити своєю.
-- SKIP LOCKED усередині підзапиту → двоє воркерів беруть РІЗНІ рядки, ніхто не чекає.
UPDATE jobs
   SET status = 'running', locked_by = $1, locked_at = now()
 WHERE id = (
   SELECT id FROM jobs
    WHERE status = 'ready'
    ORDER BY id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
 )
RETURNING id, type, payload;
```

```ts
async function claim(pool: Pool, workerId: string): Promise<Job | null> {
  const { rows } = await pool.query(claimSql, [workerId]);   // SQL вище
  return rows[0] ?? null;      // pg сам розбирає jsonb payload в обʼєкт
}

async function runOnce(pool: Pool, workerId: string,
                       handle: (job: Job) => Promise<void>): Promise<boolean> {
  const job = await claim(pool, workerId);   // короткий такт: вихопили
  if (!job) return false;
  await handle(job);                          // довгий такт: кодуємо, БЕЗ відкритої транзакції
  await pool.query("UPDATE jobs SET status = 'done' WHERE id = $1", [job.id]);
  return true;
}
```

Тепер найважливіше в цьому такті — те, що робить забір **чесним** попри падіння. Уяви, що воркер вихопив задачу (`running`), перекодував, але впав **до** `UPDATE ... done`. Задача застрягла в `running` навіки? Ні — для цього й стоїть оренда. Окремий «жнець» (reaper) вертає в чергу все, що висить у `running` довше за розумний строк:

```sql
-- Задачу взяли, але воркер не встиг закрити її за 5 хвилин → він, певно, помер.
-- Повертаємо в чергу — хай візьме інший. Це і є доставка «щонайменше раз».
UPDATE jobs
   SET status = 'ready', attempts = attempts + 1
 WHERE status = 'running' AND locked_at < now() - interval '5 minutes';
```

І ось де все звʼязується. Жнець може повернути в чергу задачу, яку перший воркер **насправді вже виконав** (перекодував кліп), але не встиг позначити `done`. Її візьме інший воркер — і перекодує **вдруге**. Це не баг реалізації, а неминучий наслідок будь-якої надійної черги: гарантія — [«щонайменше раз»](book:programming/delivery-guarantees), і дубль треба не боятися, а знешкодити. Що ми й зробимо наступним розділом.

А поки — обіцяна інтроспекція. Задача в базі видна як звичайні дані, тож глибину черги дебажиш одним SELECT, без окремої панелі:

```sql
-- Скільки задач у кожному стані + як довго чекає найстаріша готова.
SELECT status, count(*) AS n,
       now() - min(created_at) FILTER (WHERE status = 'ready') AS oldest_ready
  FROM jobs
 GROUP BY status;
```

Якщо `oldest_ready` поповз у хвилини — воркери не встигають, і ти бачиш це раніше, ніж поскаржаться користувачі. Оце «чергу видно як таблицю» — тиха, але щоденна перевага бази: борг, що застряг, читаєш тим самим SQL, що й решту даних.

## Ідемпотентний воркер: щонайменше раз, а результат — один

Отже, воркер **зобовʼязаний** стерпіти повторну доставку тієї самої задачі. Властивість, яка це дає, зветься [ідемпотентністю](book:programming/idempotency): операцію можна застосувати раз чи багато разів — а видимий результат однаковий. Секрет майже завжди один — **природний ключ результату**, за яким «зробити ще раз» стає «нічого не міняти». У нас цей ключ уже є в схемі: `renditions (clip_id, profile)` — первинний ключ, тобто один результат на пару «кліп + профіль».

:::tabs
```ts
type Encode = (clipId: number, profile: string) => Promise<string>;

async function transcode(pool: Pool, clipId: number, encode: Encode,
                         profile = "h264-720p"): Promise<void> {
  // Ключ ідемпотентності: якщо результат уже є — ця доставка дубль, виходимо.
  const done = await pool.query(
    "SELECT 1 FROM renditions WHERE clip_id = $1 AND profile = $2", [clipId, profile]);
  if (done.rowCount) return;                       // уже перекодовано — no-op, дорогого кодека не чіпаємо

  const path = await encode(clipId, profile);      // ← єдине дороге місце

  await pool.query(
    `INSERT INTO renditions (clip_id, profile, path) VALUES ($1, $2, $3)
       ON CONFLICT (clip_id, profile) DO NOTHING`, // ← навіть гонка двох воркерів згортається в 1 рядок
    [clipId, profile, path]);
}
```
```py
async def transcode(pool, clip_id, encode, profile="h264-720p"):
    async with pool.connection() as conn:
        row = await (await conn.execute(
            "SELECT 1 FROM renditions WHERE clip_id=%s AND profile=%s",
            (clip_id, profile))).fetchone()
        if row:
            return                                  # дубль доставки — нічого не робимо
        path = await encode(clip_id, profile)       # дорогий кодек — лише коли справді треба
        await conn.execute(
            "INSERT INTO renditions (clip_id, profile, path) VALUES (%s,%s,%s) "
            "ON CONFLICT (clip_id, profile) DO NOTHING",
            (clip_id, profile, path))
```
:::

Тут два рубежі, і вони різні. Попередній `SELECT` — рубіж **економії**: коли дубль очевидний, ми не запускаємо дорогий кодек удруге. А `ON CONFLICT DO NOTHING` — рубіж **коректності**: він ловить навіть те, що перевірка проґавить, — гонку, де два воркери одночасно пройшли `SELECT` (обидва побачили «порожньо»), обидва закодували й обидва пишуть результат; конфлікт первинного ключа лишить **один** рядок, а не два. Перевірка одна без одної недостатня: без `SELECT` ми марно палили б кодек, без `ON CONFLICT` — падали б на гонці.

Доведемо це тестом. Вручаємо ту саму задачу двічі поспіль і рахуємо, скільки разів реально смикнувся кодек:

```ts
test("воркер ідемпотентний: та сама задача двічі — перекодування одне", async () => {
  const clipId = await insertClip(pool, "s3://clips/raw/42.mov");
  let encodes = 0;
  const encode: Encode = async () => { encodes++; return `s3://clips/out/${clipId}.mp4`; };

  await transcode(pool, clipId, encode);   // перша доставка
  await transcode(pool, clipId, encode);   // ДУБЛЬ (жнець повернув, relay доправив двічі — байдуже)

  expect(encodes).toBe(1);                 // кодек смикнувся РІВНО раз
  const r = await pool.query(
    "SELECT count(*) FROM renditions WHERE clip_id = $1", [clipId]);
  expect(Number(r.rows[0].count)).toBe(1); // один результат, не два
});
```

`encodes === 1` при двох доставках — оце й є ідемпотентність на дотик: доставок скільки завгодно, ефект один. Тепер «щонайменше раз» уже не страшне — ми його **знешкодили ключем**, а не намагаємось (марно) досягти «рівно раз» на доставці.

Доставка 1 веде в лаву воркера: «перевір renditions(42) → порожньо» → «encode() — дорогий кодек» (зелена рамка) → «INSERT rendition(42, h264-720p)». Доставка 2 веде в другу лаву: «перевір renditions(42) → вже є» → «encode ПРОПУЩЕНО» (сіра, перекреслена) → «INSERT … ON CONFLICT DO NOTHING → 0 рядків». Унизу спільна таблиця renditions з ОДНИМ рядком (clip_id 42, profile h264-720p). Підпис-стрічка внизу: «щонайменше раз × ключ ідемпотентності = ефект рівно раз».](img/at-least-once.svg)
*Дві доставки тієї самої задачі входять зверху; перша проходить крізь дорогий кодек, друга впирається в наявний результат і згасає. Природний ключ `(clip_id, profile)` перетворює «щонайменше раз» на видимий «ефект рівно раз» — не на рівні доставки, а на рівні результату.*

## Спосіб В: окремий брокер — подвійний запис, сирота і лік outbox'ом

Ще крок правіше — і черга виїжджає в окрему систему під чергування: Redis, RabbitMQ, SQS. Пропускна здатність, доставка штовханням, повна коробка фіч. Але тепер бізнес-факт (у базі) і постановка задачі (у брокері) — **дві різні системи без спільної транзакції**, і подвійний запис вертається на поріг. Щоб це не лишилось словами, змоделюймо брокер тестовим дублером, у якого можна навмисно «зламати» наступний виклик:

```ts
class FakeBroker {
  delivered: Array<{ topic: string; payload: unknown }> = [];
  private fail = false;
  failNext() { this.fail = true; }                 // «брокер на мить недоступний»
  async enqueue(topic: string, payload: unknown) {
    if (this.fail) { this.fail = false; throw new Error("broker unavailable"); }
    this.delivered.push({ topic, payload });
  }
}
```

Такий дублер — зручний, але й підступний: ніщо не змушує його поводитись, як справжній Redis, і день у день вони тихо розходяться. Це окрема пастка тестових дублерів; лік — [прогнати фейк і бій спільним контрактним набором](root:progarch/test-doubles-when/proj-verified-fake.md), щоб підробка не брехала. Тут же він служить одному: детермінованому відтворенню збою.

Наївний подвійний запис виглядає невинно — записали кліп, поставили задачу:

```ts
async function uploadClipNaive(pool: Pool, broker: FakeBroker,
                               homeId: number, url: string): Promise<number> {
  const { rows } = await pool.query(
    "INSERT INTO clips (home_id, url) VALUES ($1, $2) RETURNING id", [homeId, url]);
  const clipId = rows[0].id;                        // 1) факт зафіксовано в базі
  // ── а якщо процес упав / брокер ліг ОТУТ? ──
  await broker.enqueue("transcode", { clipId });    // 2) постановка в ІНШІЙ системі
  return clipId;
}
```

Між рядком 1 і рядком 2 немає спільної транзакції — це шов між двома світами. Впаде застосунок або брокер саме тут — і кліп у базі є, а задачі нема. Відтворімо цю сироту тестом:

```ts
test("наївний подвійний запис сиротить кліп, коли enqueue падає", async () => {
  const broker = new FakeBroker();
  broker.failNext();                               // брокер на мить ліг — рівно на нашому enqueue
  const url = "s3://clips/raw/7.mov";

  await expect(uploadClipNaive(pool, broker, 7, url)).rejects.toThrow();

  // Кліп ЗАфіксувався (перший запит пройшов і закомітився сам собою)...
  const clip = await pool.query("SELECT id FROM clips WHERE url = $1", [url]);
  expect(clip.rowCount).toBe(1);                   // кліп ІСНУЄ
  // ...а задача НЕ доправлена. Осиротілий кліп, нуль сліду.
  expect(broker.delivered).toHaveLength(0);        // борг зник — і ніхто не знає
});
```

Тест зелений — і ця зелень болюча: вона стверджує, що система **штатно** лишає кліпи без відео щоразу, коли брокер моргне між двома записами. Оце і є [проблема подвійного запису](book:programming/outbox-pattern) на дотик.

Лік — **транзакційний outbox**. Ідея точна: раз ми не можемо втягнути брокер у транзакцію бази, покладімо в ту транзакцію *намір* — рядок у таблицю `outbox` **тією ж транзакцією, що й кліп**. А окремий relay вже несе намір із таблиці в брокер. Постановка знову стала неподільною з фактом — бо `outbox` живе в тій самій базі:

```ts
async function uploadClipOutbox(pool: Pool, homeId: number, url: string): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(
      "INSERT INTO clips (home_id, url) VALUES ($1, $2) RETURNING id", [homeId, url]);
    const clipId = rows[0].id;
    await client.query(
      "INSERT INTO outbox (topic, payload) VALUES ('transcode', $1::jsonb)",
      [JSON.stringify({ clipId })]);               // ← НАМІР у ТІЙ САМІЙ транзакції
    await client.query("COMMIT");                  // кліп + намір лягають атомарно
    return clipId;
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}

// Relay: злити недоправлене з outbox у брокер. Ганяється циклічно, окремо від застосунку.
async function relayOnce(pool: Pool, broker: FakeBroker): Promise<void> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(`
      SELECT id, topic, payload FROM outbox
       WHERE delivered_at IS NULL
       ORDER BY id
       LIMIT 100
       FOR UPDATE SKIP LOCKED`);                   // кілька relay-інстансів не переступлять одне одному
    for (const row of rows) {
      await broker.enqueue(row.topic, row.payload);// може доправити двічі → воркер ідемпотентний, дубль ок
      await client.query(
        "UPDATE outbox SET delivered_at = now() WHERE id = $1", [row.id]);
    }
    await client.query("COMMIT");
  } catch (e) {
    await client.query("ROLLBACK");                // не встигли позначити → на наступному колі перешлемо
    throw e;
  } finally {
    client.release();
  }
}
```

І ось доказ, заради якого весь розділ. Зламаймо relay **рівно в тій точці**, де наївна версія сиротила кліп, — на першому `enqueue`. Наївний варіант там втратив задачу назавжди. Подивімось, що станеться з outbox'ом:

```ts
test("outbox доправляє задачу, навіть коли relay спершу падає", async () => {
  const broker = new FakeBroker();
  const url = "s3://clips/raw/8.mov";
  await uploadClipOutbox(pool, 7, url);            // кліп + рядок outbox — одна транзакція

  broker.failNext();                               // перша спроба relay падає — ТА САМА мить збою
  await expect(relayOnce(pool, broker)).rejects.toThrow();
  expect(broker.delivered).toHaveLength(0);        // ще нічого не доправлено...

  // ...але намір ЦІЛИЙ в outbox, тож повторний прогін relay доводить справу:
  await relayOnce(pool, broker);                   // брокер ожив
  expect(broker.delivered).toEqual([
    { topic: "transcode", payload: { clipId: expect.any(Number) } },
  ]);
  const stuck = await pool.query(
    "SELECT count(*) FROM outbox WHERE delivered_at IS NULL");
  expect(Number(stuck.rows[0].count)).toBe(0);     // жодної сироти не лишилось
});
```

Порівняй два тести рядок у рядок. Той самий збій, та сама мить — «база зафіксувалась, доставка впала». У наївній версії задача **зникла**, і другого шансу не було. З outbox'ом намір пережив збій у базі (він же там і лежав, атомарно з кліпом), тож relay просто спробував ще раз — і доправив. Різниця не в тому, що outbox «надійніший брокер». Різниця в тому, що постановку задачі знову втягнуто в транзакцію факту — а **брокер винесено за неї, у крок relay, який можна безпечно повторювати**.

![Дві горизонтальні доріжки-таймлайни, і посередині — вертикальна червона пунктирна лінія «тут падає процес: після COMMIT, до enqueue», спільна для обох. Верхня доріжка «наївний подвійний запис»: злива «INSERT clip» → «COMMIT ✓» (обидва ЛІВОРУЧ від лінії падіння), а ПРАВОРУЧ від лінії — бліда пунктирна коробка «enqueue transcode — не сталося», далі червона рамка-результат «кліп ✓, задача ✗ = ОСИРОТІЛИЙ КЛІП». Нижня доріжка «транзакційний outbox»: ЛІВОРУЧ від лінії «INSERT clip + рядок outbox (одна транзакція)» → «COMMIT ✓»; ПРАВОРУЧ від лінії «relay: 1-ша спроба ✗ → retry → enqueue ✓» → «UPDATE outbox delivered», далі зелена рамка-результат «0 сиріт — намір був у базі». Підпис-стрічка: наївний губить задачу в точці падіння; outbox переживає ту саму точку, бо намір закомічено ліворуч від неї.](img/orphan-vs-outbox.svg)
*Та сама точка падіння — праворуч від COMMIT, ліворуч від доставки в брокер. Наївний запис у цій точці втрачає задачу назавжди (права частина доріжки — привид). Outbox переживає ту саму точку, бо намір закомічено ЛІВОРУЧ від неї, у транзакції з кліпом, і relay лишається безпечно повторюваним кроком.*

Придивись тепер до `relayOnce` уважніше — і побачиш тиху іронію. Він читає таблицю `outbox` через `FOR UPDATE SKIP LOCKED` і позначає доправлене. Це **буквально черга в базі з другого варіанта**, приставлена спереду до брокера. Тобто зроблений правильно, третій варіант відрощує всередині себе шматочок другого — щоб відкупити назад ту саму атомарність, яку сам щойно й втратив. А ще зверни увагу: relay може доправити задачу в брокер, але впасти **до** `UPDATE ... delivered_at`; наступне коло перешле її знову. Виходить те саме «щонайменше раз» — і саме тому воркер із попереднього розділу **мусить** бути ідемпотентним. Усе замикається: outbox дає «щонайменше раз», ідемпотентний ключ згортає дублі в один результат.

> 🔧 **Навіщо це.** Побачив у коді два записи в різні системи підряд — `db.save(); broker.enqueue()`, `db.commit(); http.post()`, `save(); email.send()` — спинися й спитай: «а якщо процес упаде між ними?». Якщо відповідь «один бік є, другого нема, і ми не помітимо» — ти щойно знайшов подвійний запис, найтихіше джерело осиротілих фактів у розподілених системах. Лік майже завжди той самий: не намагайся зробити два записи атомарними через мережу (це [двофазний коміт](book:programming/outbox-pattern), і він крихкий), а зведи їх до **одного** запису в свою базу — outbox — і винеси другий бік у повторюваний relay. Один надійний запис плюс повтор завжди дешевший за два ненадійні.

## Складність і пастки

Три способи — три різні набори граблів, і майже всі ростуть із того самого кореня, що й переваги.

**А — памʼять: тиша на втраті.** Найгірша риса — не те, що робота гине, а те, що гине **безшумно**: ні винятку, ні рядка в лозі, кліп просто лишається без відео. Плюс безмежний масив, що пухне без [протитиску](book:programming/backpressure-local), і три репліки — три сліпі одна до одної черги. Правило просте: якщо на питання «переживе рестарт?» відповідь має бути «так» — цей варіант уже не твій.

**Б — база: замки, опитування й отруйна задача.** Головна грабля вже показана — тримати транзакцію відкритою через усе перекодування; ліки — короткий claim плюс оренда й жнець, як вище. Друга: воркери **опитують** таблицю, а це або зайві порожні запити, або затримка; помʼякшує `LISTEN/NOTIFY`, що будить воркерів, коли робота є. Третя: на дуже високому потоці гарячий обіг `jobs` починає заважати тому ж Postgres, що обслуговує бізнес. І четверта, про яку легко забути: задача, що **завжди падає** (битий файл, вічний виняток), під жнецем крутитиметься по колу вічно — це [отруйна задача](book:programming/poison-message); тому ми й лічимо `attempts`, а вичерпавши ліміт, відкладаємо її в [мертву чергу](book:programming/dead-letter-queue) на розгляд людини, а не даємо їй забивати воркерів безкінечно.

**В — брокер: outbox сам по собі «щонайменше раз».** Найтонше: relay доправляє **щонайменше раз** (може переслати після падіння між `enqueue` і `delivered_at`), тож без ідемпотентного воркера outbox лише міняє «загублену задачу» на «задвоєну» — виправляє один баг, заводячи інший. Обидва треба разом. Далі — сам relay: його опитування можна замінити штовханням через [захоплення змін даних (CDC)](book:programming/change-data-capture) — читати виправлення прямо з журналу реплікації Postgres, і тоді намір летить у брокер майже без затримки. І пам'ятай, що «окрема черга» не означає «довговічніша»: брокер у памʼяті на падінні може втратити секунди-хвилини записів, тож твій «нудний» Postgres часто надійніший за спеціальний субстрат.

## Що лишається в руках

Ми взяли одну задачу — «залив кліп, перекодуй у фоні» — і написали її тричі, але справжнім героєм щоразу був **тест**, а не постановка. У памʼяті тест подивився, як задача випаровується на рестарті, — і зелень на `depth() === 0` стала доказом провалу. У базі атомарна постановка зробила осиротілий кліп **структурно неможливим**: немає шпарини, крізь яку факт розійдеться із задачею. А брокер повернув сироту на поріг — і той самий outbox, що є переодягнена черга з другого варіанта, відкупив атомарність назад, лишивши relay безпечно повторюваним.

Під усіма трьома лежало одне виконуване питання — чи ділить постановка задачі транзакцію із записом, що її породив. Тепер це не афоризм, а два тести: один відтворює сироту, другий доводить, що outbox її прибирає. І поряд — другий інваріант, теж у коді: та сама задача, вручена двічі, лишає один результат, бо «щонайменше раз» помножене на природний ключ дає ефект рівно раз. Три субстрати, одне питання про транзакцію — і набір тестів, що спалахне червоним тієї ж миті, коли ти відповіси на нього неправильно. Куди саме з цих трьох ляже фонова робота дому — зважимо, обираючи чергу під її справжні класи задач: [яку чергу взяти для Digital Homes](root:progarch/jobs-choice).
