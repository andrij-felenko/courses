# ⚙️ Прийняти телеметрію DH на однім циклі — і не отруїти смугу

Картка лишила обіцянку: покласти на стіл найсильнішу версію Варіанта Б — не гаслом, а кодом, який можна запустити. Виконаймо її. Зберемо той край хмари DH, що приймає телеметрію від хабів: багато одночасних з'єднань, дрібні показання, пересилання у сховище — і все це на **однім потоці**, який ніколи не спить на очікуванні. А тоді свідомо його зламаємо: вкинемо в обробник важкий місячний рахунок і подивимося, як застигає весь прийом. І полагодимо — винесенням рахунку за межу циклу.

Нитка тут одна, і варто тримати її перед очима від першого рядка: **що лишається на циклі, а що мусить його покинути.** Приймати, парсити, пересилати — це майже суцільне чекання на мережу, рідна земля циклу подій. Молоти числа за місяць — це чистий процесор, найгірше, що можна покласти на єдину смугу. Весь приклад малює саме цю лінію поділу.

## Задача

Випишемо сцену точно. Кожен хаб у домі тримає **живе TCP-з'єднання** до хмари й раз на хвилину шле рядок телеметрії — JSON із показанням, завершений `\n`. Хабів — тисячі, і майже всі мовчать: одне коротке повідомлення на хвилину, решту часу з'єднання просто відкрите. Хмара має прийняти рядок, розібрати його, доліпити мітку хаба й **пересунути у сховище** — чергу чи базу, до якої вона ходить своїм асинхронним клієнтом (тобто теж по мережі, теж із чеканням).

Поверх цього потоку є другий, рідкісний і важкий: інколи приходить команда «звести показання цього дому за місяць» — перцентилі, ковзні середні, пошук аномалій по десятках тисяч рядків. Це вже не чекання, а **рахунок**: секунда роботи процесора на одне зведення.

Отже, дві геть різні задачі течуть крізь один сервер. Перша — обмежена вводом-виводом, її має бути видно тисячами. Друга — обмежена обчисленням, її одиниці, але кожна ненажерлива. Мета: щоб друга **ніколи** не заморозила першу.

> 🔧 **Навіщо це.** Це не вигаданий приклад — це форма половини бекендів світу: шлюз, брокер, приймач подій, вебхук-ендпоінт. Скрізь та сама суміш — тонкий струмок важкої роботи в широкій річці дешевого вводу-виводу. Хто змішає їх на одній смузі, той дізнається про «отруєння смуги» не з книжки, а з пейджера о третій ночі.

## Крок 1 — приймати, не тримаючи смугу

Почнемо з чистого прийому. Кожне з'єднання обслуговує **один обробник-корутина**; коли він доходить до читання з мережі чи запису у сховище, він каже `await` — і цикл на цей час бере наступного, хто дозрів. Жодного потоку на з'єднання: тисячі напіврозмов жонглює одна нитка.

:::tabs
```py
import asyncio, json

storage = ...  # асинхронний клієнт черги/БД: await storage.put(...) — теж по мережі

async def handle_hub(reader, writer):
    hub = writer.get_extra_info("peername")[0]
    async for raw in reader:                 # рядок за рядком; readline під капотом
        line = raw.strip()
        if not line:
            continue
        try:
            reading = json.loads(line)        # дрібний JSON — швидко, лишаємо в циклі
        except ValueError:
            continue                          # биту телеметрію мовчки кидаємо
        reading["hub"] = hub
        await storage.put(reading)            # await → поки сховище пише, смуга вільна
    writer.close()

async def main():
    srv = await asyncio.start_server(handle_hub, "0.0.0.0", 9099)
    async with srv:
        await srv.serve_forever()

asyncio.run(main())
```
```ts
import { createServer, Socket } from "node:net";
import { createInterface } from "node:readline";

// асинхронний клієнт черги/БД: await storage.put(...) — теж по мережі
declare const storage: { put(r: unknown): Promise<void> };

createServer((sock: Socket) => {
  const hub = sock.remoteAddress;
  const lines = createInterface({ input: sock });   // рядок за рядком
  lines.on("line", async (raw) => {
    const line = raw.trim();
    if (!line) return;
    let reading: Record<string, unknown>;
    try { reading = JSON.parse(line); }             // дрібний JSON — швидко
    catch { return; }                                // биту телеметрію кидаємо
    reading.hub = hub;
    await storage.put(reading);                      // await → смуга вільна, поки пише
  });
  sock.on("error", () => sock.destroy());
}).listen(9099);
```
:::

Прочитаймо, де саме тут відбувається магія дешевої одночасності. Обидва `await` — на читанні рядка й на записі у сховище — це точки, де обробник **поступається**: він не тримає потік, поки ловить наступне показання чи чекає підтвердження від бази. Тим часом цикл проганяє інші з'єднання, яким уже прийшли дані. Сокет, що мовчить, не коштує жодного такту процесора — про його готовність цикл дізнається від [неблокуючого вводу-виводу](book:programming/blocking-vs-nonblocking-io), який замість «спати на `read()`» одразу каже «ще не готово», а ОС розбудить, коли буде.

Одна тонкість, яку варто помітити одразу, бо вона повернеться в пастках. У версії Python `async for` **сам собою** тримає порядок у межах одного з'єднання: наступний рядок читається лише після того, як `await storage.put(...)` для попереднього завершився. Тобто на кожне з'єднання роботи не більше, ніж воно встигає протовкти, — вбудований зворотний тиск. У версії Node обробник `line` — асинхронний, але `readline` його **не чекає**: рядки можуть сипатися швидше, ніж сховище їх ковтає. Поки що заплющмо на це око — ми зумисне пишемо наївну версію, щоб побачити межу; полагодимо в пастках.

## Крок 2 — отрута: місячний рахунок просто в циклі

Тепер додаймо другий, важкий шлях — і зробімо це найприроднішим, найгіршим способом: покличемо агрегацію **прямо в обробнику**, синхронно, так само, як покликали б будь-яку функцію.

:::tabs
```py
def aggregate_month(hub_id, rows):            # чистий CPU: перемолоти місяць показань
    # десятки тисяч рядків → перцентилі, ковзні середні, детект аномалій
    total = sum(r["value"] for r in rows)     # (насправді роботи на ~900 мс)
    return {"hub": hub_id, "avg": total / len(rows)}

async def handle_control(reader, writer):
    cmd = (await reader.readline()).split()
    if len(cmd) >= 2 and cmd[0] == b"aggregate":
        hub_id = cmd[1].decode()
        rows = await storage.month(hub_id)             # неблокуюче читання — ок
        summary = aggregate_month(hub_id, rows)        # ОТРУТА: ~900 мс CPU В ЦИКЛІ
        writer.write(json.dumps(summary).encode() + b"\n")
        await writer.drain()
```
```ts
function aggregateMonth(hubId: string, rows: Reading[]): Summary {
  // десятки тисяч рядків → перцентилі, ковзні середні, детект аномалій
  const total = rows.reduce((s, r) => s + r.value, 0);  // (роботи на ~900 мс)
  return { hub: hubId, avg: total / rows.length };
}

async function handleControl(cmd: string[], sock: Socket) {
  if (cmd[0] === "aggregate") {
    const hubId = cmd[1];
    const rows = await storage.month(hubId);            // неблокуюче читання — ок
    const summary = aggregateMonth(hubId, rows);        // ОТРУТА: ~900 мс CPU В ЦИКЛІ
    sock.write(JSON.stringify(summary) + "\n");
  }
}
```
:::

Читання `storage.month(...)` чемно чекає через `await` — з ним усе гаразд. А от наступний рядок — катастрофа, і то тиха, бо в коді вона виглядає невинно. `aggregate_month(...)` не має жодного `await`: це просто виклик функції, що **дев'ятсот мілісекунд** крутить процесор, нікому не поступаючись. І поки вона крутиться, смуга зайнята. Тисяча хабів, що саме цієї миті надіслали показання, стоять у черзі готових; `/health` від балансувальника не отримує відповіді; нові з'єднання не приймаються. Не «повільніше» — **застигло на 900 мс**, як і обіцяла картка: один синхронний важкий виклик не віддає єдину смугу, і мерзнуть усі невинні сусіди.

Найпідступніше — що це той самий баг, хоч би якою мовою: у Python його не рятує ані `async`, ані GIL; у Node — ані проміси, ані `await` деінде. Кооперативне планування карає буквально: задача біжить, доки **сама** не поступиться, а `aggregate_month` поступатися не вміє.

Верхня, підписана «ДО — важкий рахунок просто в циклі»: ліворуч у ній стоять готові задачі /reading і /health, середину-праворуч займає червоний блок «агрегація · 900 мс — тримає смугу», з боку напис «усі мерзнуть», під смугою — «готові, але стоять». Нижня половина, підписана «ПІСЛЯ — агрегацію винесено з циклу»: смуга циклу заповнена короткими зеленими обробниками з написом «цикл вільний — приймає далі», під нею — «короткий обробник → await → звільнив смугу», а окремим блоком нижче стоїть «робітник (окреме ядро): агрегація · 900 мс», з'єднаний із циклом стрілками «віддав» униз і «зведення (await)» угору](/root/course/progarch/runtime-eventloop-variant/img/offload-before-after.svg)

*Той самий рахунок, дві долі. Угорі він сидить у смузі й морозить усіх; унизу цикл віддав його робітникові й одразу звільнив смугу, а результат забрав назад через `await`. Змінилося одне: де саме крутиться процесор.*

## Крок 3 — лік: винести рахунок за межу циклу

Лік випливає прямо з діагнозу. Цикл подій не тягне процесорної роботи — отже, процесорну роботу треба забрати з циклу й віддати туди, де є вільні ядра: у [пул робітників](book:programming/thread-pool) або окремий процес. Обробник лишається на смузі рівно настільки, щоб **віддати** завдання й `await`-нути результат; поки робітник меле числа на іншому ядрі, смуга вільна й приймає телеметрію далі.

Тут між рантаймами проходить чесна, повчальна різниця. У Python нитки не рятують від процесорного навантаження: глобальний замок інтерпретатора (GIL) не дає двом потокам виконувати байткод водночас, тож `aggregate_month` на сусідньому **потоці** все одно крастиме такти в циклу. Справжнє винесення дає **окремий процес** — власний інтерпретатор, власний GIL. У Node такого замка нема: `worker_threads` — це справжні паралельні ізоляти V8, тож окремого потоку досить.

:::tabs
```py
from concurrent.futures import ProcessPoolExecutor

POOL = ProcessPoolExecutor()                  # окремі процеси — оминають GIL

async def handle_control(reader, writer):
    cmd = (await reader.readline()).split()
    if len(cmd) >= 2 and cmd[0] == b"aggregate":
        hub_id = cmd[1].decode()
        rows = await storage.month(hub_id)
        loop = asyncio.get_running_loop()
        summary = await loop.run_in_executor(      # смуга ВІЛЬНА, поки процес рахує
            POOL, aggregate_month, hub_id, rows)
        writer.write(json.dumps(summary).encode() + b"\n")
        await writer.drain()
```
```ts
// aggregate.worker.ts — окремий потік V8, справжня паралельність
import { parentPort, workerData } from "node:worker_threads";
import { aggregateMonth } from "./aggregate";
parentPort!.postMessage(aggregateMonth(workerData.hubId, workerData.rows));

// ── server.ts — віддаємо завдання потокові й чекаємо результат ──
import { Worker } from "node:worker_threads";

function aggregateOffloaded(hubId: string, rows: Reading[]): Promise<Summary> {
  return new Promise((resolve, reject) => {
    const w = new Worker(new URL("./aggregate.worker.js", import.meta.url),
                         { workerData: { hubId, rows } });
    w.once("message", (m) => { resolve(m as Summary); w.terminate(); });
    w.once("error", reject);
  });
}

async function handleControl(cmd: string[]) {
  if (cmd[0] === "aggregate") {
    const rows = await storage.month(cmd[1]);
    return await aggregateOffloaded(cmd[1], rows);   // смуга вільна, поки потік меле
  }
}
```
:::

Різниця мікроскопічна в коді й тектонічна за наслідком. Було: `summary = aggregate_month(...)` — виклик у смузі. Стало: `summary = await run_in_executor(POOL, ...)` — завдання йде за межу, а `await` звільняє смугу до повернення. Верхня й нижня смуги на фігурі — це буквально ці два рядки.

Тут і проступає парадокс, який картка назвала суттю Варіанта Б: рантайм, що ми обрали «щоб не мати потоків», під капотом **усе одно тримає пул потоків чи процесів** — рівно для тієї роботи, якої цикл не тягне. Цикл не скасував потоки; він **вигнав їх на край**, до процесорних сплесків, і лишив собі чисте чекання.

![Ліворуч велика рамка «Цикл подій · один потік»: сітка сокетів під написом «epoll стежить за всіма», рамка «await I/O — потік нікого не тримає» і підпис «дрібна робота (парсинг JSON, пересилання) лишається тут». Праворуч, за пунктирною межею «межа процесу / потоку», — стос із чотирьох рамок «робітник · окреме ядро — CPU» під заголовком «Пул робітників (окремі процеси / потоки)» і підписом «місячна агрегація рахується тут». *Межа offload — головна лінія всього прикладу. Ліворуч живе ввід-вивід і дрібнота, яку смуга протовкує миттю; праворуч, за кордоном процесу, — важкий рахунок. Через кордон їздить лише те, що варте переходу, бо сам перехід не безкоштовний.*

## Крок 4 — маленький замір: 10 000 сплячих з'єднань

Картка обіцяла ще й показати ціну пам'яті наживо, на невеликому числі. Зробімо крихітний замір: підняти два сервери, що тримають **10 000 мовчазних з'єднань**, і порівняти їхній слід у пам'яті. Один тримає з'єднання циклом подій (одна призупинена задача на кожне), другий — за моделлю [Варіанта А, потік на з'єднання](root:progarch/runtime-threads-variant) (один OS-потік на кожне, заблокований на `recv`).

Спершу — тримач на циклі подій: кожне з'єднання стає призупиненою задачею, а замір читає власний `VmRSS` без жодних залежностей.

```py
# ЦИКЛ ПОДІЙ: одне з'єднання = одна призупинена задача. Стек не зайнятий.
import asyncio

def rss_mb():                                  # VmRSS із /proc — без залежностей
    for ln in open("/proc/self/status"):
        if ln.startswith("VmRSS:"):
            return int(ln.split()[1]) / 1024

async def hold(reader, writer):
    await asyncio.Event().wait()               # спить вічно; смуги не тримає

async def main():
    srv = await asyncio.start_server(hold, "127.0.0.1", 9100)
    async with srv:
        await srv.serve_forever()

asyncio.run(main())
# 10 000 клієнтів під'єдналися → VmRSS ≈ кілька КБ × 10⁴ + база інтерпретатора
```

А тепер той самий приймач за моделлю Варіанта А — по OS-потоку на з'єднання, кожен заблокований на `recv`:

```py
# ПОТІК НА З'ЄДНАННЯ: одне з'єднання = один OS-потік, заблокований на recv.
import socket, threading

def hold(conn):
    conn.recv(1)                               # блокується — увесь стек СТОЇТЬ

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 9101)); srv.listen(10_000)
while True:
    conn, _ = srv.accept()
    threading.Thread(target=hold, args=(conn,), daemon=True).start()
# 10 000 потоків × 8 МБ стек = 80 ГБ віртуальних — система відмовить,
# доки стек не вріжеш; навіть врізаний — RSS на сотні МБ + тасування 10⁴ потоків
```

Числа з прогону на 64-бітному Linux — порядок величини, не константа (точні залежать від ОС і налаштувань), але форма ціни видна без сумніву:

```
10 000 сплячих з'єднань      слід у пам'яті             на 1 з'єднання
── цикл подій (asyncio) ──    VmRSS ≈ 50–90 МБ           ~кілька КБ user-space
── потік на з'єднання ────    80 ГБ віртуальних заброн.  8 МБ стек (типово)
                             RSS сотні МБ + планувальник тасує 10⁴ потоків
```

І тут — чесна тонкість, без якої замір збрехав би на свою користь. Виграш циклу подій — це **не** економія пам'яті ядра: сам сокет ОС коштує однаково обом моделям (структура `tcp_sock` — кілька кілобайтів на кожне відкрите з'єднання, плюс буфери, якщо в них лежать дані). Різниця вся в **user-space**: потоку потрібен цілий стек — типово 8 МБ зарезервованого адресного простору на Linux (значення `RLIMIT_STACK`), — тоді як призупиненій задачі циклу вистачає дрібного об'єкта-стану на кілька кілобайтів. На десяти тисячах сонних з'єднань це різниця між «влазить у сервіс без роздумів» і «система відмовляється дати стільки потоків». Помнож на мільйон — і отримаєш той самий терабайт проти гігабайтів, що картка порахувала на серветці; наш замір лише мацає ту саму криву руками, на числі, яке видно.

## Складність і пастки

Один цикл — модель дисципліни. Слабне вона на п'яти окремих граблях, і кожна б'є по-своєму.

### Забутий `await`: тиха втрата роботи

Найдешевша помилка й найгидкіша. Напиши `storage.put(reading)` **без** `await` — і в Python лишиться нестворена корутина (`RuntimeWarning: coroutine was never awaited`), а в Node — проміс, що полетів сам по собі. Запис може не статися; а якщо всередині вибухне помилка, вона не спливе в обробник, а осяде «необробленою відмовою» десь у логах. Правило просте: кожен виклик, що повертає корутину чи проміс, або **чекають**, або свідомо кладуть у відстежуваний список задач — третього «просто покликати» тут нема.

### Зворотний тиск до сховища

Пам'ятаєте наївний Node-обробник із Кроку 1? `readline` не чекає на асинхронний `line`-слухач, тож рядки з хаба можуть надходити швидше, ніж `storage.put` встигає їх ковтати. Незавершені записи громадяться в пам'яті — і сервер, що мав бути ощадливим, роздувається, поки не впаде. У Python `async for` дає зворотний тиск **на одне з'єднання** задарма (наступний рядок чекає на попередній `put`), але через **тисячу** з'єднань водночас можна так само затопити сховище. Лік — обмежити кількість записів у польоті: у Node — паузити сокет на час запису; всюди — пропускати весь трафік крізь семафор чи обмежену чергу. Це та сама тема [зворотного тиску (backpressure)](book:programming/backpressure-local), лише в мініатюрі одного сервера: швидкість входу не сміє довго перевищувати швидкість виходу, бо різницю оплачує пам'ять.

:::tabs
```py
SEM = asyncio.Semaphore(500)                  # не більше 500 записів у польоті

async def store(reading):
    async with SEM:                           # 501-й чекає, поки звільниться місце
        await storage.put(reading)
```
```ts
// паузимо сокет, поки запис не завершиться — природний зворотний тиск
lines.on("line", async (raw) => {
  const reading = parse(raw); if (!reading) return;
  sock.pause();                               // хаб зачекає
  try { await storage.put(reading); }
  finally { sock.resume(); }
});
```
:::

### Ціна переходу через межу

Offload не безкоштовний. Аргументи й результат, що їдуть у робітника й назад, **серіалізуються**: для окремого процесу — через `pickle`, для `worker_threads` — через структурне клонування ([серіалізація як така](book:programming/data-serialization)). Віддати за межу дрібну роботу — програш: перехід коштуватиме дорожче, ніж сам рахунок. Тому дрібний JSON парситься **в циклі**, а межу перетинає лише те, що велике настільки, щоб покрити переїзд, — місячна агрегація на 900 мс. Правило межі з фігури — буквальне: через кордон їде **тільки** робота, більша за вартість переходу.

Звідси й практичне уточнення до Node-коду: створювати `Worker` **на кожен запит** марнотратно — старт потоку теж коштує. У проді тримають **сталий пул** робітників (готова бібліотека Piscina чи власний набір, що перевикористовує потоки), а завдання роздають у нього — рівно як `ProcessPoolExecutor` перевикористовує процеси, а не плодить новий на кожне зведення.

### Що НЕ виносити — і чому GIL тут головний свідок

Провести межу занадто рано — теж помилка, дзеркальна отруєнню. Якби ми винесли в пул кожну дрібницю, сервер потонув би в серіалізації. Виносять лише **гаряче ядро** — ту функцію, що справді молотить процесор секундами. У Python цю межу підказує сам GIL: пул **потоків** (`asyncio.to_thread` чи `ThreadPoolExecutor`) звільнить смугу від *блокування* вводу-виводу, але для чистого пайтонівського рахунку **не дасть паралельності** — GIL однаково серіалізує байткод. Тому для CPU у CPython правильна відповідь — пул **процесів**; потоковий пул лишають для блокуючих бібліотек, що самі відпускають GIL на час системного виклику. Node вільний від цього замка, тож там `worker_threads` дають справжню паралельність без окремих процесів — але й там дрібне завдання не варте переходу.

### Один цикл — одне ядро

І остання, найширша межа. Навіть ідеально написаний цикл використовує **одне ядро**: пул рятує від процесорних сплесків, але сам приймальний цикл не масштабується вшир. Щоб зайняти вісім ядер приймання, запускають **вісім циклів** — по одному на ядро, за спільним портом (`SO_REUSEPORT`) чи через кластер. Це вже [thread-per-core / shared-nothing](book:programming/thread-per-core), і з ним повертається питання, якого один цикл щасливо не знав: як ці вісім копій ділять стан, коли дешевої спільної пам'яті між ними нема. Цикл подій масштабується **назовні**, копіями, а не вглиб одного процесу.

А щоб узагалі помітити отруту раніше за клієнтів, смугу **вимірюють**. І Node, і asyncio дають затримку планування циклу (event-loop lag): якщо між тим, як задача стала готовою, і тим, як цикл до неї дійшов, зачасту зяють десятки мілісекунд — значить, хтось тримає смугу надто довго. Це найдешевший датчик здоров'я такого сервера: рівна низька затримка — смуга дихає; стрибки — десь у коді сидить синхронний важкий виклик, який пора виносити за межу.

## Що лишається в руках

Ми зібрали приймальний край DH так, як його справді будують. Прийом телеметрії ліг на один цикл: тисячі мовчазних з'єднань, кожне — призупинена задача на кілька кілобайтів, а не потік зі стеком; `await` на читанні й записі робить чекання майже безкоштовним, і одна нитка жонглює всіма. Це виграш, що його замір на десяти тисячах з'єднань підтвердив руками — з чесною поправкою, що економимо ми стек, а не пам'ять ядра.

А тоді ми зламали й полагодили модель на її ж головному правилі. Синхронний місячний рахунок у обробнику заморозив увесь прийом на 900 мс — рівно те «отруєння смуги», яким платить кожен цикл подій. Лік — не переписати рантайм, а **провести межу**: дрібнота лишається на смузі, важкий рахунок їде в пул процесів (у CPython — щоб оминути GIL) чи в робочий потік (у Node), а `await` тримає обробник рівно доти, доки чекає результат. Пастки окреслили ту саму межу з п'яти боків: забутий `await` губить роботу тихо; зворотний тиск боронить пам'ять від затоплення; серіалізація робить дрібний offload збитковим; GIL підказує, що саме процеси, а не потоки, виносять CPU у Python; а одне ядро на цикл жене нас до копій на кожне ядро. Під усім — один рядок, який картка винесла в назву моделі й який цей код тепер довів: **на циклі подій смугу не тримають — ані блокуючим викликом, ані важким рахунком; усе, що не вміє поступитися, живе за межею.**
