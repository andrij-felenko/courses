# 📋 Специфікація конверта даних та атрибутів шифрування

<preknowlist>
- [Наскрізне шифрування](root:progarch/end-to-end-encryption) — обмін ключами між кінцевими пристроями та осліплення сервера.
- [Шифрування у спокої й ключі](root:progarch/encryption-at-rest) — прозоре проти прикладного шифрування, ієрархія DEK/KEK і сховища ключів (KMS).
</preknowlist>

Ця довідка визначає повний двобічний контракт криптографічного конверта (*Payload Envelope*), заголовків класифікації даних та схему обміну метаданими шифрування між сервісами платформи Digital Homes (DH) та кінцевими пристроями (настінні панелі, мобільний застосунок, домашні Edge-хаби, IoT-камери).

Контракт є обов'язковим для всіх мікросервісів прийому даних (Ingestion Gateways), шин повідомлень (Kafka/RabbitMQ) та сховищ (PostgreSQL, Cassandra, S3). Він забезпечує єдиний протокол обробки зашифрованого вмісту та гарантує, що жоден сервіс не обійде криптографічну політику.

## 1. Призначення та фундаментальні принципи контракту

Головна мета цієї специфікації — відокремити метадані транспорту та класифікації від зашифрованого корисного навантаження. Це дозволяє проміжним серверним вузлам (маршрутизаторам, балансувальникам навантаження, чергам повідомлень) виконувати інспекцію та маршрутизацію пакетів за відкритими заголовками, не вимагаючи розшифрування вмісту.

При розробці контракту закладено три фундаментальні принципи:
1. **Явна класифікація на межі**: кожен пакет маркується заголовком `X-DH-Data-Class` на момент створення на пристрої відправника. Сервер не має права змінювати клас даних у напрямку послаблення криптографічних вимог.
2. **Абсолютна самодостатність конверта**: зашифрований конверт містить усі метадані, необхідні для розшифрування (ідентифікатор ключа, вектор ініціалізації, алгоритм, auth tag), але не містить самого ключа у відкритому вигляді.
3. **Строгий детермінізм помилок**: будь-які порушення структури конверта або невдалі спроби верифікації тегу автентичності призводять до виклику чітко визначених кодів помилок з категоричною відмовою в обробці (fail-closed).

## 2. Заголовок класифікації та криптографічні атрибути запиту

Кожен HTTP-запит, gRPC-виклик або подія шини даних, що містить прикладні дані користувачів або пристроїв, мусить бути маркована єдиним набором криптографічних заголовків транспорту.

Заголовки дозволяють шлюзу маршрутизації (API Gateway) ухвалювати рішення про обробку або відхилення пакета без розпакування корисного навантаження.

```http
X-DH-Data-Class: CLASS_A_E2E
X-DH-Crypto-Mode: E2EE_SIGNAL_V2
X-DH-Key-ID: e2e:device_hub_9921:session_881
X-DH-Payload-Format: application/octet-stream
X-DH-Nonce: 9f8a1b2c3d4e5f6a
```

### Детальна специфікація класифікаторів (`X-DH-Data-Class`)

Класифікація визначає межу довіри, тип шифрування та доступність серверних обчислень для кожного запиту:

1. **`CLASS_A_E2E` (End-to-End Encrypted Payload)**:
   - **Межа розшифрування**: виключно кінцевий пристрій отримувача (смартфон, настінна панель). Серверні процеси хмари не мають доступних ключів.
   - **Дозволені серверні операції**: маршрутизація байтів, тимчасова буферизація за зашифрованою чергою, генерація пуш-сповіщень без вмісту.
   - **Заборонені серверні операції**: повнотекстовий пошук, OCR, декодування відеокадрів, серверний AI-аналіз, OLAP-агрегація, трансформація полів.

2. **`CLASS_A_SIGNED` (E2E Integrity & Non-Repudiation)**:
   - **Межа розшифрування**: корисне навантаження може бути відкритим або шифрованим TLS, але містить асиметричний цифровий підпис пристрою (ECDSA на кривій secp256r1 або Ed25519).
   - **Призначення**: критичні команди керування (відчинення замка, вимкнення сигналізації). Сервер перевіряє підпис відкритим ключем пристрою, але не може самостійно згенерувати валідну команду.

3. **`CLASS_B_EDGE` (Edge Hybrid & Local Analytics)**:
   - **Межа розшифрування**: локальний домашній сервер (Edge Hub) або серверний GPU-вузол із короткоживучим DEK у пам'яті.
   - **Призначення**: відеопотоки для локального AI-аналізу руху, розпізнавання облич на хабі без передачі відкритого відео в публічну хмару.

4. **`CLASS_C_SSE` (Server-Side KMS Envelope Encryption)**:
   - **Межа розшифрування**: продуктовий мікросервіс усередині захищеного контуру хмари (VPC).
   - **Призначення**: системна телеметрія, метрики розряду батарей, білінгові трансакції, системні логи. Забезпечує захист від витоку дисків та дампів БД при збереженні повного повнотекстового пошуку й агрегації.

## 3. Формат конверта зашифрованого корисного навантаження

Залежно від шини транспорту використовується JSON-версія конверта (для REST/HTTP API) або Protobuf-версія (для gRPC та високонавантаженої шини Kafka).

### Схема JSON-конверта для `CLASS_A_E2E`

Структура конверта `CLASS_A_E2E` оптимізована для передачі зашифрованих медіафрагментів та приватних повідомлень. Усі криптографічні параметри (ефемерний відкритий ключ, крок ратчета) містяться у блоці `keyRef`.

```json
{
  "$schema": "https://api.dh.io/schemas/v2/crypto-envelope-e2e.json",
  "version": 2,
  "dataClass": "CLASS_A_E2E",
  "cryptoMode": "AES_256_GCM_E2E",
  "keyRef": {
    "senderDeviceId": "cam_living_room_01",
    "recipientDeviceId": "app_mobile_usr_44",
    "ratchetStep": 142,
    "ephemeralPublicKey": "MCowBQYDK2VwAyEA9b4bJ8k2m9xL1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV="
  },
  "iv": "d3F8a1b2c3d4e5f6",
  "ciphertext": "K8n2m9xL1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV==",
  "authTag": "xY9zA1b2C3d4E5f6",
  "meta": {
    "timestampMs": 1724001122000,
    "clientNonce": "992184",
    "contentType": "video/h265-fragment"
  }
}
```

### Схема JSON-конверта для `CLASS_C_SSE` (Envelope Encryption)

Конверт `CLASS_C_SSE` розроблено для зберігання шифрованих даних у базах даних та об'єктних сховищах S3. Поле `encryptedDek` містить симетричний ключ даних (DEK), зашифрований за допомогою ключа KEK у хмарному KMS. Поле `indexedFields` зберігає лише ті атрибути, по яких дозволено відкриту індексацію.

```json
{
  "$schema": "https://api.dh.io/schemas/v2/crypto-envelope-sse.json",
  "version": 2,
  "dataClass": "CLASS_C_SSE",
  "cryptoMode": "KMS_ENVELOPE_AES_256_GCM",
  "keyRef": {
    "kmsKeyArn": "arn:aws:kms:eu-central-1:123456789012:key/dh-telemetry-kek",
    "encryptedDek": "AQEDAHg1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV=="
  },
  "iv": "e5f6a1b2c3d4f8a1",
  "ciphertext": "M7vR4sT7uVK8n2m9xL1vP0qR4sT7uV8n2m9xL1vP0qR4sT7uV8n2m9xL1v==",
  "authTag": "C3d4E5f6xY9zA1b2",
  "meta": {
    "tenantId": "tenant_home_441",
    "indexedFields": {
      "deviceId": "sensor_temp_04",
      "eventType": "telemetry_read",
      "firmwareVersion": "v3.4.1"
    }
  }
}
```

### Двійкове представлення Protobuf (для gRPC та Kafka)

Для високонавантажених сервісів обробки телеметрії текстове представлення JSON створює значний накладний витратний коефіцієнт парсингу. У внутрішній шині даних Kafka використовується двійкова схема Protobuf, яка скорочує розмір заголовків конверта з 450 байт до 48 байт.

Двійкова структура гарантує збереження однакових імен полів та типів даних між мовами C++, Go, Java та Python без ризику помилок кодування UTF-8 чи текстового екранування.

### Вимоги до вектора ініціалізації (IV) та катастрофічні наслідки повтору

Для алгоритму AES-256-GCM застосовуються суворі криптографічні обмеження відповідно до рекомендацій NIST SP 800-38D:
- Довжина вектора ініціалізації (`iv`) становить чітко **96 біт (12 байт)**.
- **Вимога унікальності**: повторне використання одного й того самого `iv` з одним симетричним ключем для двох різних повідомлень призводить до катастрофічної втрати автентичності AES-GCM (відновлення ключа автентифікації GHASH та можливості підробки шифротекстів).
- Для `CLASS_A_E2E` `iv` генерується мобільним пристроєм за допомогою стійкого генератора випадкових чисел (CSPRNG).
- Для `CLASS_C_SSE` `iv` генерується сервісом шифрування на основі монотонного лічильника та ідентифікатора процесу.

Повторне використання `iv` для одного симетричного ключа в режимі Galois/Counter Mode (GCM) вважається критичною криптографічною вразливістю першого рівня severity. При такому повторі операція XOR між двома шифротекстами розкриває XOR двох відкритих текстів (`C1 ⊕ C2 = P1 ⊕ P2`), що дозволяє нападнику легко відновити відкриті повідомлення. Більше того, це дозволяє обчислити ключ автентифікації GHASH і підробляти `authTag` для нових повідомлень.

## 4. Протокол узгодження ключів HKDF та алгоритми шифрування

При генерації сесійних ключів з базового секрету (Master Secret) відправник та приймач мусять дотримуватися стандартизованої функції виведення ключів **HKDF (HMAC-based Extract-and-Expand Key Derivation Function, RFC 5869)** на основі SHA-256.

Процедура виведення симетричного ключа DEK складається з двох послідовних етапів:

1. **HKDF-Extract**: обчислює псевдовипадковий ключ `PRK = HMAC-Hash(salt, IKM)`, де `IKM` — спільний секрет Ель-Ґамаля/Diffie-Hellman, отриманий після виконання асиметричного обміну X25519.
2. **HKDF-Expand**: розгортає `PRK` до необхідної довжини 256 біт для ключа AES-256-GCM з використанням контекстного рядка `info`:

```http
info = "DH-V2-E2E-AES-256-GCM-Payload-Key"
```

Використання строго визначеного контекстного рядка `info` гарантує, що навіть при використанні одного й того самого базового секрету для шифрування корисного навантаження та підпису автентичності, виведені симетричні ключі будуть криптографічно незалежними.

## 5. Протокол ротації ключів та перешифрування

Ротація ключів — обов'язкова процедура у системі забезпечення безпеки даних. Контракт розрізняє два типи ротації:

### 1. Ротація KEK у сховищі KMS (Server-Side Encryption)
При ротації майстер-ключа KEK у хмарному KMS самі зашифровані терабайти даних у базі даних чи S3 **не перешифровуються**.
Замість цього виконується процедура Re-encrypt метаданих:
- Зчитується зашифрований DEK (`encryptedDek`).
- KMS розшифровує `encryptedDek` старим KEK і негайно зашифровує той самий DEK новим KEK.
- Оновлений `encryptedDek` перезаписується у конверт.

Це дозволяє виконати ротацію ключів для мільярдів записів за лічені хвилини без читання й перезапису гігабайтів корисного навантаження.

### 2. Ротація ратчетом у E2E (Signal Double Ratchet)
В E2E-режимі кожне нове повідомлення шифрується новим симетричним ключем, який виводиться з поточного стану ратчета.
Якщо пристрій втрачає синхронізацію лічильника `ratchetStep`, сервер відхиляє конверт з кодом `e2e_key_expired` і примушує клієнти виконати новий Diffie-Hellman крок для ініціалізації свіжого ланцюжка ключів.

## 6. Машинний контракт помилок та обробка криптографічних збоїв

При отриманні пошкодженого, неетичного або некоректно шифрованого пакета API Gateway або мікросервіс прийому повертає стандартизований JSON Problem Details (RFC 7807) та відповідний статус-код HTTP.

Цей контракт гарантує, що клієнтський застосунок чітко розуміє, чи варто повторювати запит, чи потрібно ініціювати нову сесію узгодження ключів, чи негайно повідомити користувача про помилку доступу.

### Таблиця реакції системи на криптографічні збої

| Код помилки (`code`) | HTTP статус | Причина збою | Технічна реакція та дії клієнта |
| :--- | :--- | :--- | :--- |
| `crypto_class_mismatch` | `400 Bad Request` | Запит містить `CLASS_A_E2E`, але вказаний маршрут вимагає серверного пошуку | Перевірити класифікацію. Змінити маршрут або виконати локальну індексацію на пристрої. |
| `e2e_key_expired` | `409 Conflict` | Лічильник кроків ратчета (`ratchetStep`) застарів або розсинхронізувався | Пристрій повинен ініціювати новий сеанс узгодження ключів (Ratchet Handshake). |
| `kms_dek_unwrap_failed` | `502 Bad Gateway` | Серверний KMS не зміг розшифрувати `encryptedDek` (відкликано IAM доступ або KEK) | Алерт у систему спостережуваності (Prometheus/Grafana). Перевірити IAM ролі мікросервісу. |
| `auth_tag_mismatch` | `422 Unprocessable` | Спроба розшифрування AES-GCM завершилася збоєм перевірки `authTag` | Пакет відкинуто. Зафіксовано спробу підробки або пошкодження даних у мережі. |
| `iv_reuse_detected` | `403 Forbidden` | Шлюз виявив повторне використання `iv` для одного й того самого `keyRef` | Негайно блокувати сесію пристрою. Вимагати повної повторної автентифікації. |

## 7. Специфікація узгодження можливостей (Capabilities Negotiation)

При підключенні нового пристрою або оновленні мобільного застосунку клієнт і сервер виконують процедуру узгодження криптографічних можливостей.

Це дозволяє уникнути ситуацій, коли пристрій надсилає `CLASS_A_E2E` потік, який сервер не спроможний розшифрувати для хмарного запису, або коли застарілий мобільний клієнт намагається використати непідтримуваний шифр.

Процедура узгодження відбувається перед відкриттям WebSocket-з'єднання або WebRTC-відеопотоку.

### Запит узгодження клієнта (`POST /api/v2/crypto/negotiate`)

```json
{
  "deviceId": "cam_living_room_01",
  "deviceClass": "camera_v2",
  "supportedDataClasses": ["CLASS_A_E2E", "CLASS_B_EDGE", "CLASS_C_SSE"],
  "supportedCiphers": ["AES_256_GCM_E2E", "CHACHA20_POLY1305_E2E"],
  "edgeHubConnected": true,
  "edgeHubId": "hub_local_8841"
}
```

### Відповідь сервера про вибір режиму (`200 OK`)

```json
{
  "status": "configured",
  "selectedDataClass": "CLASS_A_E2E",
  "selectedCipher": "AES_256_GCM_E2E",
  "activeCapabilities": {
    "cloudAiAnalytics": false,
    "serverFulltextSearch": false,
    "localEdgeAnalytics": true,
    "directWebRtcStream": true
  },
  "warnings": [
    "Cloud motion detection disabled due to E2E classification."
  ]
}
```

## 8. Еволюція схеми та зворотна сумісність (Schema Evolution)

Криптографічний контракт розрахований на тривалий цикл життя пристроїв (до 10 років для настінних панелей та камери спостереження). Зміна структури конверта мусить дотримуватися правил зворотної сумісності:

1. **Додавання нових полів у метадані**: нові атрибути містяться лише у розділі `meta` або `keyRef` та позначаються як опціональні. Старі пристрої ігнорують невідомі поля JSON або Protobuf без генерації винятків.
2. **Зміна версії алгоритму (`cryptoMode`)**: при запровадженні пост-квантових шифрів (ML-KEM / Kyber) додається нове значення алгоритму в заголовок. Пристрої, що не підтримують новий режим, повертають статус `400 Bad Request` з кодом `unsupported_crypto_mode`, що змушує шлюз перемкнути з'єднання на резервний AES-256-GCM.
3. **Заборона видалення обов'язкових полів**: поля `version`, `dataClass`, `iv`, `ciphertext` та `authTag` є фіксованими надавачами структури і не можуть виключатися в майбутніх версіях специфікації.

## 9. Спостережуваність, скрізна кореляція та маскування в логах

Для забезпечення можливості відлагодження розподілених транзакцій без витоку відкритого тексту, специфікація вимагає дотримання суворих правил маскування (*Log Redaction*):

- **Скрізний ідентифікатор запиту (`X-DH-Nonce`)**: передається у заголовках усіх мікросервісів та записується в логи підсистеми спостережуваності (Prometheus, Grafana, Datadog). Це дозволяє відстежити шлях зашифрованого пакета крізь 20 мікросервісів без читання його вмісту.
- **Маскування шифротексту в логах**: сервіси логування зобов'язані відтинати значення полів `ciphertext` та `encryptedDek` до перших 8 символів у лог-виводах. Запис повного шифротексту в журналі логів вважається порушенням політики безпеки другого рівня (Medium severity).
- **Заборона логування ключів**: будь-яка спроба записати відкритий DEK чи ефемерний ключ у журнал логів блокується на рівні статичного аналізатора коду у CI/CD.

## 10. Вимоги до апаратних сховищ ключів (HSM / Secure Enclave)

Безпека криптографічного конверта фундаментально спирається на захищеність ключів шифрування на кінцевих вузлах. Специфікація визначає апаратні вимоги до рівнів зберігання ключів:

1. **Клієнтські пристрої (iOS / Android / Edge Hub)**:
   - Приватні ключі E2E та майстер-секрети підпису мусять зберігатися у захищеному криптопроцесорі (Apple Secure Enclave, Android StrongBox / KeyStore, TPM 2.0 на Edge Hub).
   - Експорт приватного ключа у відкритому вигляді за межі захищеного чипа заборонений на рівні прошивки.
   - Усі криптографічні операції підписання та генерації ключів виконуються всередині апаратного модуля.

2. **Серверна інфраструктура хмари (KMS / HSM)**:
   - Ключі шифрування ключів (KEK) зберігаються у хмарних HSM, сертифікованих за стандартом FIPS 140-3 Level 3 (або FIPS 140-2 Level 3).
   - Жоден системний адміністратор хмари або інженер розробки не має технічного доступу до вивантаження приватного KEK з апаратного модуля.
   - Операція `kms:Decrypt` фіксується у підсистемі аудиту AWS CloudTrail / GCP Cloud Audit Logs із зазначенням сервісного акаунта та часової позначки.

## 11. Аварійна процедура розшифрування (Break-Glass Protocol)

Для випадків масштабних інцидентів безпеки або втрати зв'язку з хмарним KMS, специфікація визначає аварійну процедуру Break-Glass для даних `CLASS_C_SSE`:

- **Резервний HSM-модуль**: у фізично ізольованому резервному дата-центрі зберігається зашифрована копія майстер-ключа KEK під охороною двофакторної схеми розкріплення (Threshold Secret Sharing 3-of-5).
- **Схема авторизації**: розшифрування резервного KEK вимагає одночасного підтвердження криптографічними ключами щонайменше трьох офіцерів з безпеки компанії (Chief Security Officer, Infrastructure Lead, Legal Counsel).
- **Автоматичний аудит**: виклик аварійної процедури генерує невідкличне сповіщення в незалежний зовнішній сервіс моніторингу та реєструє подію в аудит-лозі WORM.

Для даних `CLASS_A_E2E` аварійна процедура Break-Glass не існує за дизайном: оскільки хмара не володіє ключами користувачів, жодні дії адміністраторів чи офіцерів безпеки не дозволяють розшифрувати приватний E2E-контент.

Такий детальний контракт гарантує однозначність розуміння меж довіри між розробниками мобільних застосунків, фахівцями з безпеки та інженерами хмарної інфраструктури, виключаючи випадкові витоки або розходження у трактуванні безпекових вимог.
