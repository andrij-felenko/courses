# 🔌 Модель оцінки вартості евакуаційного бюджету та вектори прив'язки

Ця вставка містить узагальнену модель чотирьох векторів залежності від постачальника (Vendor Lock-in) та детальний математичний розрахунок сумарного бюджету евакуації (Exit Cost) для оцінки фінансових і технічних ризиків при виборі хмарних сервісів.

Прив'язка до постачальника виникає не раптово: це кумулятивний результат інженерних рішень, прийнятих на різних рівнях технологічного стеку. Щоб оцінити справжню вартість виходу з хмари чи SaaS-платформи, архітектор має проаналізувати чотири вектори залежності, кожен із яких створює свій тип опору (friction) при спробі міграції.

---

## Чотири вектори залежності від постачальника

Залежність розподіляється по чотирьох архітектурних шарах. Спроба евакуації з системи, де всі чотири вектори заблоковані proprietary-рішеннями, коштує в середньому від 50% до 200% річного бюджету розробки всієї системи.

```
+-----------------------------------------------------------------------+
| 1. Вектор API та коду (API & Code Vector)                             |
| Виклики proprietary SDK, специфічні анотації, асинхронні події vendor |
+-----------------------------------------------------------------------+
| 2. Вектор даних та формату (Data Gravity Vector)                      |
| Proprietary типи, бінарні формати, індекси, ціна мережевого egress     |
+-----------------------------------------------------------------------+
| 3. Вектор операцій та IaC (Operations Vector)                         |
| Terraform-провайдери, спец-моніторинг, права IAM, скрипти CI/CD      |
+-----------------------------------------------------------------------+
| 4. Вектор компетенцій та екосистеми (Ecosystem & Skill Vector)        |
| Знання команди, сертифікації, інтеграція з суміжними SaaS-платформами|
+-----------------------------------------------------------------------+
```

### 1. Вектор API та коду (API & Code Vector)

Вектор коду проникає безпосередньо у вихідний код застосунку через прямий імпорт хмарних SDK та заголовочних файлів провайдера. Використання специфічних бібліотек (наприклад, AWS SDK для DynamoDB, GCP BigQuery Client або Azure Cosmos SDK) прив'язує точки виклику, обробку помилок і структури даних до конкретного інтерфейсу. Евакуація вимагає рефакторингу кожної точки виклику або створення шару адаптерів.

Опір цього вектора зростає пропорційно кількості мікросервісів та ступеню їхнього прямого імпорту хмарних заголовочних файлів чи пакунків. Якщо SDK вендора просочився у доменні сутності, зміна СУБД вимагає перегляду модульних тестів та бізнес-правил системи. Коли доменний код оперує proprietary-типами даних провайдера, навіть просте оновлення версії SDK перетворюється на ризикований інженерний захід.

### 2. Вектор даних та гравітації (Data Gravity Vector)

Найважчий і найдорожчий вектор. Що більший обсяг накопичених даних, то важче їх перемістити через мережеві обмеження та тарифну політику постачальника на вихідний трафік (egress cost). Хмарні провайдери свідомо будують асиметричні тарифи: вхідний трафік (ingress) є безкоштовним, тоді як виведення даних на власні сервери або до конкурента коштує від 50 до 90 євро за один терабайт.

До додаткового блокування призводить використання закритих форматів даних або відсутність знімків (snapshots) у стандартних відкритих форматах. Якщо вендор зберігає дані у власному бінарному форматі і надає доступ до них лише через платне API з обмеженням швидкості (Rate Limiting), процес експорту може розтягнутися на місяці, паралізуючи роботу аналітичних систем та завдаючи прямих збитків бізнесу.

### 3. Вектор операцій та інфраструктури (Operations Vector)

Інфраструктура як код (IaC), налаштування авторизації (IAM), пайплайни CI/CD, правила моніторингу та алертингу, заточені під конкретний сервіс (наприклад, AWS CloudWatch, GCP Stackdriver або Azure Monitor). 

Міграція вимагає повного переписання інфраструктурних маніфестів та перезапуску процесів забезпечення стійкості. Команда змушена створювати нові інструменти автоматичного розгортання та перевірки конфігурацій, що потребує значних інженерних ресурсів. Операційне блокування часто стає непомітним під час розробки, але проявляється у вигляді тривалих затримок під час спроби перенести розгорнуту систему в новий регіон чи приватну хмару.

### 4. Вектор компетенцій та екосистеми (Ecosystem Vector)

Людський чинник та накопичений контекст. Інженери, які звикли до інструментів одного вендора, витрачають значний час на опанування альтернативних технологій, що знижує продуктивність розробки під час міграційного періоду. Команда відчуває природний психологічний опір, оскільки звичні методи налагодження та розгортання замінюються новими інструментами.

Окрім цього, системні інтеграції між різними SaaS-платформами (наприклад, між CRM, платіжними gateways та службами нотифікацій) створюють мережу залежностей, де заміна одного компонента вимагає оновлення суміжних договорів та інтерфейсів авторизації. Зміна одного вендора викликає каскадну реакцію переналаштування суміжних підсистем.

## Математична модель розрахунку евакуаційного бюджету (Total Exit Cost)

Сумарна вартість виходу складається з п'яти незалежних параметрів витрат. Підсумковий бюджет розраховується за формулою:

```
Total_Exit_Cost = C_egress + C_rewrite + C_ops + C_dual_run + C_opportunity
```

Розберемо детальний покроковий розрахунок кожної складової для системи обсягом `D` терабайт даних та `N` мікросервісів:

### 1. Вартість виведення даних (Egress Cost)

Витрати на мережевий трафік та обчислювальні ресурси для конвертації proprietary-формату у відкритий:

```
C_egress = D · T_egress + D · C_transform
```

- `D` — загальний обсяг даних для евакуації (у ТБ).
- `T_egress` — тариф провайдера за 1 ТБ вихідного мережевого трафіку.
- `C_transform` — обчислювальна вартість розпакування proprietary-формату у відкритий (наприклад, вивантаження з DynamoDB в S3 у формат Parquet).

```
Приклад розрахунку (D = 200 ТБ, T_egress = 80 €/ТБ, C_transform = 15 €/ТБ):
C_egress
= 200 · 80 € + 200 · 15 €      [застосували тариф трафіку 80 €/ТБ та конвертацію 15 €/ТБ]
= 16 000 € + 3 000 €           [помножили обсяги на відповідні цінові ставки]
= 19 000 €                     [підсумували витрати на виведення та конвертацію даних]
```

### 2. Вартість переписування коду (Code Refactoring Cost)

Витрати на адаптацію вихідного коду та заміну SDK вендора на нейтральні порти:

```
C_rewrite = N_loc · C_loc_refactor
```

- `N_loc` — кількість рядків коду, які мають безпосередню залежність від SDK вендора.
- `C_loc_refactor` — середня вартість рефакторингу одного рядка коду (з урахуванням тестування та рецензування).

```
Приклад розрахунку (N_loc = 45 000 рядків коду у 12 сервісах при ставці 6 €/LOC):
C_rewrite
= 45 000 · 6 €                 [середня ціна переписання та тестування 6 €/LOC]
= 270 000 €                    [отримали загальну вартість трудових витрат розробників]
```

### 3. Вартість операційної адаптації (Operations Migration Cost)

Витрати на оновлення маніфестів інфраструктури, конвеєрів CI/CD та навчання SRE-інженерів:

```
C_ops = (H_iac + H_train) · Rate_ops
```

- `H_iac` — години на переписування маніфестів Terraform/Kubernetes та пайплайнів CI/CD.
- `H_train` — години на перенавчання команди інфраструктури та експлуатації.
- `Rate_ops` — погодинна ставка DevOps/SRE інженера.

```
Приклад розрахунку (H_iac = 320 год, H_train = 160 год, Rate_ops = 75 €/год):
C_ops
= (320 + 160) · 75 €           [підсумували інженерні години на інфраструктуру та навчання]
= 480 · 75 €                   [отримали загальний обсяг трудовитрат SRE]
= 36 000 €                     [помножили години на погодинну ставку]
```

### 4. Вартість паралельної експлуатації (Dual-Running Cost)

Під час міграції (яка триває `M` місяців) обидві інфраструктури працюють паралельно для забезпечення подвійного запису та валідації даних.

```
C_dual_run = M · (Infra_old + Infra_new) · K_sync
```

- `Infra_old` — щомісячний рахунок старої хмари.
- `Infra_new` — щомісячний рахунок нової хмари.
- `K_sync` — коефіцієнт додаткового навантаження на синхронізацію та проміжне реплікування (зазвичай 1.2–1.4).

```
Приклад розрахунку (M = 4 місяці, Infra_old = 25 000 €, Infra_new = 18 000 €, K_sync = 1.25):
C_dual_run
= 4 · (25 000 + 18 000) · 1.25 [записали базову суму щомісячної оренди двох хмар]
= 4 · 43 000 · 1.25            [додали рахунки старої та нової інфраструктури]
= 172 000 · 1.25               [помножили на тривалість міграційного вікна у 4 місяці]
= 215 000 €                    [врахували накладні витрати на подвійну синхронізацію]
```

### 5. Альтернативна вартість замороженого випуску (Opportunity Cost)

Поки команда розробників зайнята міграцією інфраструктури, вона не створює нових продуктових фіч, що призводить до недоотримання прибутку на ринку:

```
C_opportunity = Dev_FTE · M · Monthly_Salary · K_velocity_loss
```

```
Приклад розрахунку (8 інженерів на 4 місяці при зарплаті 6 000 €/міс та втраті швидкості 50%):
C_opportunity
= 8 · 4 · 6 000 € · 0.50       [записали параметри заморожених інженерних ресурсів]
= 192 000 € · 0.50             [підсумували фонди оплати праці команди за 4 місяці]
= 96 000 €                     [обрахували чисто втрачену цінність нестворених фіч]
```

### Підсумковий розрахунок евакуаційного бюджету

```
Total_Exit_Cost
= 19 000 € + 270 000 € + 36 000 € + 215 000 € + 96 000 €
= 636 000 €                    [підсумували всі 5 складових евакуаційного бюджету]
```

## Зведена матриця стратегій пом'якшення залежності

Залежно від етапу розвитку продукту та бізнес-пріоритетів архітектор обирає один із чотирьох підходів до управління ризиками прив'язки:

| Стратегія | Початкові витрати (Upfront Cost) | Операційна складність | Вартість виходу (Exit Cost) | Швидкість розробки (TTFV) |
|---|---|---|---|---|
| **Прямий Lock-in (Direct Binding)** | Дуже низька | Низька | Надзвичайно висока | Дуже висока |
| **Порт і Адаптер (Thin Abstraction)** | Низька–Середня | Низька | Низька | Висока |
| **Повна ізоляція (Over-engineered Abstraction)** | Висока | Висока | Дуже низька | Низька |
| **Подвійний постачальник (Active-Active Multi-Cloud)** | Надзвичайно висока | Надзвичайно висока | Близька до нуля | Дуже низька |

## Критерій доцільності евакуації (Evacuation Break-Even Criterion)

Проведення евакуації вважається економічно виправданим лише тоді, коли підсумкова економія від переходу на новий сервіс або власне залізо за 3 роки (`Total_Savings_3Y`) перевищує сумарний бюджет виходу з урахуванням ризикового коефіцієнта:

```
Total_Savings_3Y > Total_Exit_Cost · 1.35
```

Коефіцієнт `1.35` закладає 35% страховий буфер на непередбачувані затримки під час проведення міграційних робіт. Якщо прогнозована економія нижча за цей поріг, проведення міграції позбавлене економічного сенсу, а поточний Lock-in є раціональним боргом, який дешевше обслуговувати, ніж ліквідовувати.
