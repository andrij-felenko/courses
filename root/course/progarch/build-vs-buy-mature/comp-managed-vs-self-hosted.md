# 🔌 Класи інфраструктури: Managed SaaS vs Self-Hosted Open Source vs Custom Build

Порівняльний розбір трьох фундаментальних класів виконання інфраструктури розкриває їхні реальні операційні характеристики, межі застосування та ціну супроводу. Ця вставка надає системну матрицю для оцінки чотирьох критичних підсистем сучасної архітектури: автентифікації та ідентичності, брокерів повідомлень і черг, реляційних та документних баз даних, а також систем спостережливості й телеметрії.

## 1. Три класи виконання: операційні межі та розподіл відповідальності

Кожне інфраструктурне рішення в сучасній архітектурі реалізується в одному з трьох класів виконання. Межа між ними проходить не за функціональними можливостями коду, а за **розподілом операційної відповідальності** між вашою командою та зовнішнім постачальником.

1. **Managed SaaS / PaaS (Хмарний керований сервіс):**
   Ви повністю відчужуєте операційну відповідальність (управління фізичними та віртуальними серверами, патчі безпеки операційної системи, автоматичний failover, реплікацію, моніторинг заліза та відновлення після збоїв) на зовнішнього вендора (Auth0, Confluent Cloud, Datadog, AWS Aurora). Споживання оцінюється за тарифікатором підписки (за кількість користувачів, обсяг логів чи кількість викликів API).
2. **Self-Hosted Open Source (Власне розгортання відкритого ПЗ):**
   Ви розгортаєте перевірене відкрите рішення (Keycloak, Apache Kafka, PostgreSQL, LGTM-стек) на власних або орендованих обчислювальних потужностях (AWS EC2, Kubernetes, Bare-metal у дата-центрі). Команда має 100% доступ до конфігурацій, але несе повну відповідальність за Day-2 операції: процедури ребалансування дисків, оновлення версій без простою (zero-downtime upgrades) та реагування на нічні інциденти.
3. **In-House Custom Build (Власна індивідуальна розробка):**
   Команда пише власну проприєтарну систему з нуля (наприклад, власний сервер автентифікації, власний черговик повідомлень поверх сокетів). Ви отримуєте абсолютний контроль над функціоналом та синтаксисом контракту, але берете на себе 100% витрат на R&D, написання документації, тестування крайових випадків та нескінченний супровід власного коду.

```
Спектр класів виконання та операційна відповідальність:

[ Managed SaaS / PaaS ]  ─────►  [ Self-Hosted Open Source ]  ─────►  [ In-House Custom Build ]
 • Нуль операцій з залізом         • Контроль над даними й конфігом     • 100% контроль над кодом
 • Найвищий річний рахунок         • Потрібна SRE/DevOps експертиза     • Найвищий R&D борг і ризики
 • Низька гнучкість адаптації       • Фіксовані витрати на обчислення    • Повна ізоляція від вендорів
```

## 2. Зведена порівняльна матриця атрибутів

Нижче наведено зводний системний порівняльний аналіз трьох класів за основними інженерними та бізнес-критеріями:

| Атрибут | Managed SaaS / PaaS | Self-Hosted Open Source | In-House Custom Build |
| :--- | :--- | :--- | :--- |
| **Time-to-Market (Day 1)** | **1–3 дні** (виклики API / SDK) | **2–4 тижні** (IaC, Helm, налаштування) | **3–12 місяців** (R&D, тестування, v1) |
| **Day-2 Ops (Чергування/Патчі)**| **0%** (відповідальність вендора) | **Високе** (ротація дисків, оновлення) | **Критичне** (виправлення власних багів) |
| **Динаміка витрат на масштабі**| **Нелінійна / Стрімка** ($/GB, $/user) | **Лінійна** (ціна заліза/vCPU) | **Низька** (лише чисте залізо) |
| **Мережевий трафік (Egress)** | **Високий** (міжхмарний перетин) | **Мінімальний** (все всередині VPC) | **Нульовий** (локальний процес/VPC) |
| **Рівень прив'язки (Lock-in)** | **Критичний** (проприєтарні API) | **Низький** (відкриті стандарти/SQL) | **Відсутній** (код повністю ваш) |
| **Суверенітет даних / GDPR** | **Ускладнений** (третя сторона) | **Повний** (дані не покидають контур) | **Повний** (абсолютний контроль) |
| **Гнучкість кастомізації** | **Низька** (лише конфіг/вебхуки) | **Середня** (плагіни/конфігурація) | **Абсолютна** (зміна будь-якого рядка) |

## 3. Детальний розбір 4 інфраструктурних підсистем

### 1. Автентифікація та ідентичність (Auth / IDP)

Автентифікація є найбільш чутливою підсистемою з точки зору безпеки та криптографічних ризиків.

- **Managed SaaS (Auth0, Okta, Clerk, AWS Cognito):**
  - *Механізм:* Використання готового Hosted UI або SDK для обміну креденшалів на підписані JWT/OIDC токени.
  - *Плюси:* Автоматична підтримка WebAuthn, Passkeys, двофакторної автентифікації (MFA), відповідність стандартам SOC 2, ISO 27001 та вбудований захист від штормів підбору паролів (англ. *credential stuffing*).
  - *Пастка Day-2:* Різкий стрибок ціни при переході на B2B Enterprise план. Базові тарифи включають лише простий вхід за поштою. Поява вимоги корпоративного входу (SAML/SSO, Active Directory/LDAP) переводить акаунт у категорію Enterprise ($1,500–$5,000+ на місяць за замовчуванням).
- **Self-Hosted Open Source (Keycloak, Ory Hydra, Authentik):**
  - *Механізм:* Розгортання відкритого сервера ідентичності у власному Kubernetes-кластері з підключенням до власної бази PostgreSQL.
  - *Плюси:* Повна відповідність суворим вимогам GDPR / HIPAA (хеші паролів та персональні дані не залишають контур компанії), відсутність націнки за кількість активних користувачів (MAU).
  - *Пастка Day-2:* Складність налаштування високодоступного кластера. Потрібно власноруч будувати кешування сесій (Redis/Infinispan), налаштовувати реплікацію та оновлювати схеми бази даних при виході нових версій.
- **In-House Custom Build (Власний JWT/Session Server):**
  - *Оцінка:* Написання власного повноцінного сервера OAuth2/OIDC з нуля є небезпечною помилкою. Інженери систематично припускаються криптографічних помилок (неправильна перевірка підпису JWT, вразливість до алгоритму `none`, помилки у генерації випадкових сольей чи зберігання рефреш-токенів у бекапах). Дозволено лише написання найпростішого виклику підпису токена поверх готових перевірених бібліотек.

### 2. Брокер повідомлень і черги (Message Queue / Broker)

- **Managed SaaS (AWS SQS, Confluent Cloud, AWS MSK Managed Kafka):**
  - *Механізм:* Керований кластер із автоматичним виявленням та заміною збійних вузлів, автоматичним розширенням дискового простору та підтримкою REST/gRPC API.
  - *Плюси:* Нуль часу на управління ZooKeeper/KRaft, автоматичне ребалансування розділів (partitions), готова інтеграція з хмарними службами моніторингу.
  - *Пастка Day-2:* Приховані витрати на Cross-AZ мережевий трафік. У хмарах типу AWS реплікація даних між трьома зонами доступності (Multi-AZ) стягує плату за кожен гігабайт трафіку в обох напрямках. При навантаженні 50,000 подій/сек плата за трафік реплікації може втричі перевищувати ціну залізо-вузлів.
- **Self-Hosted Open Source (Apache Kafka, RabbitMQ, Redpanda на K8s/EC2):**
  - *Механізм:* Розгортання кластера на обчислювальних вузлах із локальними високошвидкісними NVMe-дисками.
  - *Плюси:* Фантастична пропускна здатність на фіксованому бюджеті, відсутність націнки за мільярди дрібних подій.
  - *Пастка Day-2:* Необхідність утримання досвідченого Kafka/SRE-інженера. Очищення заповнених дисків (retention policies), усунення деградації OS page cache під навантаженням та ручне виправлення розбалансованих розділів потребують глибокої експертизи.
- **In-House Custom Build:**
  - *Оцінка:* Виправдано виключно у системах наднизької затримки (англ. *Ultra-Low Latency* — наприклад, високочастотний трейдинг HFT або ядро LMAX Disruptor), де мережевий стекинг стандартних брокерів створює неприпустимі затримки у мікросекундах.

### 3. Реляційні та документні бази даних (Database)

- **Managed Cloud DB (AWS Aurora, Cloud SQL, MongoDB Atlas):**
  - *Механізм:* Розподілена керована база даних із відокремленим шаром зберігання та обчислень.
  - *Плюси:* Автоматичні знімки (snapshots), Point-in-Time Recovery (PITR), авто-failover за 30 секунд без втрати даних, автоматичне розширення дискового простору без зупинки роботи.
  - *Пастка Day-2:* Нелінійна ціна за IOPS (запити читання/запису до диска) та висока націнка за оперативну пам'ять.
- **Self-Hosted DB (PostgreSQL / MySQL на EC2 чи Bare-Metal):**
  - *Механізм:* Пряме розгортання DBMS на обчислювальних екземплярах або фізичному залізі.
  - *Плюси:* Повна свобода від лімітів хмарного гіпервізора, можливість тонкого налаштування параметрів ядра Linux (`sysctl`), HugePages, WAL-архівування під унікальний профіль навантаження.
  - *Пастка Day-2:* Високий ризик раптової втрати даних при збої реплікації (англ. *split-brain scenario*). Команда змушена власноруч будувати, документувати та регулярне тестувати сценарії катастрофічного відновлення (DR / Disaster Recovery).

### 4. Спостережність та телеметрія (Observability / Logs / Traces)

- **Managed SaaS (Datadog, Honeycomb, New Relic):**
  - *Механізм:* Збір логів, метрик та трасувань через агента з відправкою у хмару вендора.
  - *Плюси:* Фантастичний UX, автоматична кореляція логів з APM-трасуваннями, готові дашборди.
  - *Пастка Day-2:* Експоненційне зростання рахунку при каскадних аваріях («bill shock»). Випадково залишений лог рівня `DEBUG` у циклі обробки подій може згенерувати рахунок у $20,000 за один день.
- **Self-Hosted LGTM Stack (Loki, Grafana, Tempo, Mimir / Prometheus):**
  - *Механізм:* Використання OpenTelemetry Collector для збору та відправки логів у локальний кластер Loki, який зберігає стиснуті блоки даних у cheap Object Storage (AWS S3 / MinIO).
  - *Плюси:* Фіксований кошторис, відсутність плати за обсяг прийнятих логів, повна відповідність стандартам OpenTelemetry.
  - *Пастка Day-2:* Складність підтримки індексувальників Loki та зберігання довготривалих метрик у Mimir при обсягах понад 10 ТБ логів на добу.

## 4. Підсумкові інженерні орієнтири вибору

```
               [ Оцінка обсягу та масштабу ]
                            │
         ┌──────────────────┴──────────────────┐
         ▼                                     ▼
 [ Малий/Середній ]                    [ Гігантський ]
 (Time-to-market вирішує)              (Трафік / Ноди > N*)
         │                                     │
 ┌───────┴───────┐                     ┌───────┴───────┐
 ▼               ▼                     ▼               ▼
[Generic]      [Core]                 [Generic]      [Core]
 │               │                     │               │
 ▼               ▼                     ▼               ▼
Managed SaaS   Build In-House      Self-Hosted OS  Build In-House
(через Шов)    (Ядро продукту)     (Репатріація)   (Оптимізація)
```

1. **Якщо підсистема є Generic (Auth, Logs, Broker) і масштаб малий/середній** ──► обирайте **Managed SaaS**, але *обов'язково ховайте його за інтерфейсним швом* (Port-Adapter).
2. **Якщо підсистема є Generic, але масштаб перетнув точку N* або є вимоги суверенітету даних** ──► здійснюйте міграцію на **Self-Hosted Open Source**.
3. **Якщо підсистема є Core (ваша унікальна бізнес-логіка)** ──► обирайте **In-House Custom Build**, оскільки саме сюди варто інвестувати 100% інженерного ресурсу.
