# 🔌 Класифікація соціотехнічних антипатернів та моделей деградації

Нехтування соціотехнічним дизайном призводить до неминучої деградації як кодової бази, так і продуктивності організацій. У цій вставці наведено розширену класифікацію типових соціотехнічних антипатернів, які виникають при невідповідності між комунікаційною структурою команд та архітектурною формою систем, а також інженерні тактики їх діагностики та ліквідації.

---

## Анатомія соціотехнічного незбігу (Sociotechnical Misalignment)

Соціотехнічний незбіг виникає тоді, коли топологічна межа кодового артефакту (сервісу, модуля, репозиторію) не збігається з топологічною межею соціуму (команди, яка має повну автономність та контекст для його підтримки). 

У результаті закон Конвея починає діяти як руйнівна сила: невидимі комунікаційні зв'язки, неформальні домовленості та суперечливі пріоритети менеджменту пробивають ізоляцію модулів, породжуючи неочищену зв'язаність коду (*leaky abstractions*).

```
Матриця незбігу соціо- та техно-структур:

┌────────────────────────────┬───────────────────────────────────────────┬───────────────────────────────────────────┐
│ Організаційна структура    │ Архітектура: Моноліт                      │ Архітектура: Розподілені сервіси          │
├────────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ Функціональні колодязі     │ Класичний моноліт з очікуваннями в Jira   │ Антипатерн 1: Розподілений моноліт        │
│ (UI / Backend / DBA / QA)  │ (Lead Time > 30 днів, низький потік)      │ (Катастрофічне тертя, синхронні PR)       │
├────────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ Компонентні команди        │ Бійка за єдиний монолітний репозиторій    │ Антипатерн 3: Сервісні колодязі           │
│ (Core / Web / Infra)       │ (Merge-conflicts, розмивання відповідальн.)│ (Вузькі місця у володінні, черги прохань) │
├────────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ Stream-Aligned команди    │ Оптимум для старт-етапу (Модульний моноліт)│ Соціотехнічний оптимум (Автономний потік) │
│ (Повне доменне володіння)  │ (Високий потік, низький overhead)        │ (Lead Time < 1 день, Self-service IDP)    │
└────────────────────────────┴───────────────────────────────────────────┴───────────────────────────────────────────┘
```

## Антипатерн 1: Розподілений моноліт крізь функціональні колодязі (Distributed Monolith via Siloed Teams)

**Симптоми та механізм виникнення.** Організація ухвалює архітектурне рішення перейти з моноліту на мікросервісну архітектуру, сподіваючись прискорити релізи. Проте структура організаційного дерева залишається незмінною: існують окремий відділ Frontend-розробників, відділ Backend-інженерів, централізована група DBA та відділ QA.

Оскільки жодна з команд не володіє сервісом повністю end-to-end, будь-яка бізнес-фіча розпадається на 3–5 тикетів у Jira. Команда бекенду створює новий REST API у своєму мікросервісі, надсилає тикет DBA для додавання нової колонки в PostgreSQL, чекає 4 дні, після чого надсилає тикет Frontend-команді для оновлення UI.

```
Команда Frontend ─── (Тикет Jira) ───► Сервіс UI
                                           │ (Синхронний REST)
Команда Backend  ─── (Тикет Jira) ───► Сервіс Бізнесу
                                           │ (Синхронні заклики DB)
Команда DBA      ─── (Тикет Jira) ───► Центральна База Даних
```

**Архітектурні наслідки:**
1. Сервіси вимушені зв'язуватися жорсткими синхронними викликами, дзеркалячи міжвідділкові наради.
2. Неможливо розгорнути один мікросервіс у продакшн без одночасного сумісного розгортання (*Lockstep Deployment*) трьох інших сервісів та бази даних.
3. Lead Time зростає у 2–3 рази порівняно з початковим монолітом через нелінійне накопичення затримок у міжкомандних чергах.

**Ліквідація:** Перехід до Stream-Aligned команд. Переформувати команди так, щоб у кожній були фронтендер, бекендер, QA та інженер з навичками роботи з даними, прикріплені до одного обмеженого контексту (Bounded Context).

## Антипатерн 2: Шаруватий моноліт шаруватих команд (Layered Monolith via Layered Teams)

**Симптоми та механізм виникнення.** Структура коду розрізана на традиційні класичні шари (*UI Layer*, *Domain Business Logic*, *Data Access Layer*), і кожним шаром володіє окремий підрозділ компанії. Команда UI відповідає за подання, команда Core — за бізнес-правила, а команда бази даних — за збереження.

**Архітектурні наслідки:**
- Жодна зміна бізнес-логіки не може відбутися всередині одного шару.
- Будь-яка нова вимога пронизує всі шари згори донизу.
- Виникає явище **«шаруватого тертя»**: зміна в моделі даних вимагає послідовного рефакторингу в трьох репозиторіях із координацією трьох лідів.

**Ліквідація:** Застосування вертикального нарізання кодової бази (*Vertical Slice Architecture*). Код та команди групуються за доменними фічами, а не за технічними шарами.

## Антипатерн 3: Платформена команда як інфраструктурне вузьке місце (Platform Team as Silo Bottleneck)

**Симптоми та механізм виникнення.** Керівництво оголошує про створення «Платформеної команди» (*Platform Team*). Проте замість розробки внутрішньої продуктової платформи self-service (IDP) ця команда функціонує як старий відділ системного адміністрування (Ops) або безпеки (Sec), схований під новою модною вивіскою.

Продуктові Stream-Aligned команди не мають доступів до створення Kubernetes-просторів, баз даних чи черг повідомлень. Вони вимушені створювати квитки у Jira проханням *«створіть нам топік Kafka»* або *«надайте доступ до S3-бакету»*.

```
[Stream Team A] ──┐
[Stream Team B] ──┼──► (Ручні тикети Jira) ──► [«Платформена» команда] ──► Створення баз/S3
[Stream Team C] ──┘                             (Вузьке місце)
```

**Архітектурні наслідки:**
1. Платформена команда стає головним системним затором для всієї організації.
2. Продуктові команди втрачають автономію і тривалий час очікують на банальні конфігураційні зміни.
3. Починають виникати «тіньові IT» (*Shadow IT*): продуктивні команди купують власні хмарні акаунти в обхід платформи.

**Ліквідація:** Запровадження концепцій **Golden Path / Paved Road** та принципу **Platform-as-a-Product**. Платформена команда не виконує ручних задач, а надає програмований API, CLI-інструменти та шаблони (*Self-Service Infrastructure*), що дозволяють продуктовим командам самостійно розгортати ресурси за секунди без чекання.

## Антипатерн 4: Карго-культ реорганізацій та організаційна турбулентність (Inverse Conway Cargo-Cult)

**Симптоми та механізм виникнення.** Менеджмент дізнається про зворотний маневр Конвея і починає кожні 6 місяців перетасовувати інженерів та змінювати оргструктуру компанії. Проте саму кодову базу та архітектуру моноліту ніхто не рефакторить — код залишається спагеті з тісним зчепленням модулів (*Tight Coupling*).

**Архітектурні наслідки:**
- Соціотехнічний розрив досягає максимуму. Нові Stream-Aligned команди намагаються працювати автономно, але їхній код жорстко прив'язаний до модулів, якими володіють інші нові команди.
- Виникають постійні конфлікти злиття (*Merge Conflicts*) та руйнування контрактів у продакшн.
- Інженери втрачають психологічну безпеку та розуміння меж відповідальності.

**Ліквідація:** Організаційна перебудова повинна синхронізуватися з архітектурним рефакторингом. Зміна меж команд має супроводжуватися чітким проведенням модульних меж у коді (наприклад, через *Branch-by-Abstraction* або створення *Anti-Corruption Layer*).

## Антипатерн 5: Трагедія спільного володіння кодом (Tragedy of the Commons)

**Симптоми та механізм виникнення.** У гонитві за нульовим міжкомандним тертям оголошується модель абсолютно безегового колективного володіння (*Collective Ownership*) на масштабі сотень розробників. Будь-яка команда має право коммітити у будь-який сервіс чи спільну бібліотеку.

**Архітектурні наслідки:**
1. Жодна команда не почувається господарем кодової бази.
2. Зникають єдині інженерні стандарти, розмивається архітектурна цілісність, накопичується неконтрольований технічний борг.
3. Спільна бібліотека утиліт деградує у смітник дубльованого коду.

**Ліквідація:** Перехід до моделі **InnerSource / Weak Ownership**. Кожен модуль має чітких хранителів (*Stewards / Maintainers*). Інші команди можуть подавати Pull Requests, але хранителі контролюють архітектурні інваріанти та злиття коду.

## Антипатерн 6: Сервісні колодязі компонентних команд (Component-Silo Services)

**Симптоми та механізм виникнення.** Організація розбиває розробників на команди за технічними компонентами: *Команда Kafka*, *Команда Redis-кешу*, *Команда Auth*. Будь-яка продуктова фіча вимагає від кожної з цих компонентних команд внести локальні зміни у свій компонент.

**Архітектурні наслідки:**
- Кожна компонентна команда має свій власну чергу пріоритетів і свій беклог.
- Випуск продуктової фічі блокується найповільнішою компонентною командою.
- Когнітивне навантаження продуктового менеджера зростає до катастрофічного рівня через необхідність тримати у голові залежності між п'ятьма компонентами.

**Ліквідація:** Переформатування компонентних команд у платформені (Platform) або спеціалізовані субсистемні (Complicated-Subsystem) команди, які надають сервіси продуктовим Stream-командам за схемою **X-as-a-Service**.
