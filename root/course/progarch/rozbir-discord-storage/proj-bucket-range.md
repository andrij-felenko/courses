# ⚙️ Проєкт: з message_id — у відро й у діапазон для «останніх N»

У розборі ми звели все розміщення до однієї фрази: «один зсув і одне ділення — і з ID народжується адреса партиції». Тепер проженемо цю фразу до кінця — від сирого 64-бітного числа до точного списку партицій, які треба прочитати, у правильному порядку й **не скануючи назад аж до дня, коли Discord народився**. Саме тут ховаються справжні пастки, яких не видно з красивої формули.

## Задача

За кадром у «показати останні повідомлення каналу» сидять три під-задачі:

1. **З `message_id` дістати час і відро.** Взяти Snowflake, витягти мілісекунди, поділити на ширину відра — дістати номер 10-денного вікна, де лежить повідомлення.
2. **Згенерувати спадний ряд відер і піти партиціями назад.** Від курсора «before» (повідомлення, старіше за яке гортаємо) породити номери відер від новішого до старішого й ходити партиціями `(channel_id, bucket)`, доки не набереться N повідомлень **або** доки не впремося в створення каналу.
3. **Не ходити дарма.** Розріджений канал — це дірки: відра без жодного повідомлення. Discord запам'ятовує порожні відра, щоб наступного разу їх проминути, не турбуючи сховище.

Вхід: `channel_id`, курсор `before` (message_id), число N. Вихід: до N повідомлень, найновіші згори, і курсор наступної сторінки.

## Ідея: Snowflake сам собі годинник — і сам собі дно

Уся арифметика тримається на тому, що [Snowflake несе годинник у старших бітах](book:programming/sequences-counters): верхні 42 біти — мілісекунди від власної епохи Discord (1 січня 2015). Отже `id >> 22` викидає 22 молодші біти (воркер, процес, лічильник) і лишає чистий час у мілісекундах. Поділи цей час на ширину відра (10 діб) — отримаєш номер вікна. Дві операції, обидві цілочислові, жодного звернення до бази.

Тепер найтонше, і саме воно рятує систему від нескінченного скану. **`channel_id` — це теж Snowflake.** Канал теж колись створили, і його ID так само несе мітку часу. Значить `bucket_of(channel_id)` — це відро, у якому канал народився, тобто **дно**: раніше за нього повідомлень не було й бути не могло. Скільки б порожніх відер не тягнулося в минуле, ми маємо жорсткий нижній край — і ніколи не питаємо базу про час, коли каналу ще не існувало.

Звідси весь план другого кроку: ідемо відрами **згори вниз** (від новішого до старішого, бо всередині партиції повідомлення теж лежать спадним `message_id`), беремо з кожного скільки треба, і спиняємось на першій із двох умов — набрали N або дійшли до дна. А щоб розріджені канали не змушували марно стукати в порожні відра, запам'ятовуємо ті, що виявились пустими.

## Крок 1. З ідентифікатора — у відро

Три короткі функції. Основна мова тут — Rust (нею Discord і писав свої сервіси даних та мігратор): бітовий зсув і цілочислове ділення лягають ідіоматично. Поруч — Python, де та сама арифметика читається як псевдокод, бо цілі там необмежені.

:::tabs
```rust
/// Епоха Discord — 1 січня 2015, 00:00 UTC, у мілісекундах від епохи Unix.
const DISCORD_EPOCH: u64 = 1_420_070_400_000;
/// Ширина відра — 10 діб у мілісекундах (10·24·60·60·1000).
const BUCKET_MS: u64 = 10 * 24 * 60 * 60 * 1000; // = 864_000_000

/// Мілісекунди від епохи Discord: старші 42 біти Snowflake — це показ годинника.
fn ms_since_epoch(id: u64) -> u64 {
    id >> 22
}

/// Номер відра: у яке 10-денне вікно потрапляє повідомлення.
fn bucket_of(id: u64) -> u64 {
    ms_since_epoch(id) / BUCKET_MS
}

/// Календарний час (мс від епохи Unix) — лише щоб показати людині дату.
fn unix_ms(id: u64) -> u64 {
    ms_since_epoch(id) + DISCORD_EPOCH
}

fn main() {
    // Наскрізний приклад із розбору:
    let id: u64 = 181_193_932_800_000_000;
    assert_eq!(ms_since_epoch(id), 43_200_000_000);  // id >> 22
    assert_eq!(bucket_of(id), 50);                    // 43_200_000_000 / 864_000_000
    assert_eq!(unix_ms(id), 1_463_270_400_000);       // + епоха → десь травень 2016
}
```

Зверни увагу, що **відро рахують від мілісекунд-від-епохи (`id >> 22`), а не від календарного часу**. Додавання `DISCORD_EPOCH` потрібне лише, щоб показати людині дату; для номера вікна воно зайве — і якби ми його вплели у `bucket_of`, приклад дав би не 50, а близько 1693. Дрібниця, від якої розсипається все розміщення: одна й та сама мітка мусить лягати в те саме відро і на записі, і на читанні.

## Крок 2. Спадний ряд і хода партиціями

Тепер сама вибірка. Абстрагуємо сховище за вузьким інтерфейсом: одне звернення — одна партиція `(channel_id, bucket)`, рядки вже впорядковані спадним `message_id` (це задає `CLUSTERING ORDER BY message_id DESC` у схемі), відфільтровані `message_id < before` і не більші за ліміт. Так код лишається чесним щодо форми запиту до Cassandra чи ScyllaDB, не прив'язуючись до конкретного драйвера.

```rust
/// Одне повідомлення (лишили тільки те, що треба сторінці).
struct Message { id: u64 /* Snowflake */ }

/// Абстракція над сховищем: одне звернення = одна партиція (channel_id, bucket).
/// Рядки повертаються спадним message_id, з фільтром message_id < before, ≤ limit.
trait Store {
    fn query_partition(&self, channel_id: u64, bucket: u64, before: u64, limit: usize)
        -> Vec<Message>;
}

/// Номери відер від курсора `before` (включно) НАЗАД до відра створення каналу
/// (теж включно). channel_id — теж Snowflake, тож його відро і є дном.
fn buckets_desc(channel_id: u64, before: u64) -> impl DoubleEndedIterator<Item = u64> {
    let floor = bucket_of(channel_id); // раніше каналу не існувало — глибше не йдемо
    let start = bucket_of(before);     // з якого відра починаємо
    // Якщо курсор старіший за сам канал (start < floor) — діапазон порожній,
    // .rev() дає порожній ітератор, і жодного скану не буде.
    (floor..=start).rev()
}

struct Page { messages: Vec<Message>, next_before: Option<u64> }

fn fetch_before(store: &impl Store, channel_id: u64, before: u64, limit: usize) -> Page {
    let mut out: Vec<Message> = Vec::with_capacity(limit);

    for bucket in buckets_desc(channel_id, before) {
        let need = limit - out.len();
        let rows = store.query_partition(channel_id, bucket, before, need);
        out.extend(rows);
        if out.len() >= limit {
            break; // набрали повний екран — глибше в минуле не лізьмо
        }
    }

    let next_before = out.last().map(|m| m.id); // курсор наступної сторінки
    Page { messages: out, next_before }
}
```

Уся сила — у `(floor..=start).rev()`. Включний діапазон (`..=`) гарантує, що ми не загубимо крайні відра, а `.rev()` розвертає його спадно — новіші вікна першими. Коли канал щільний, цикл спиниться на першому-другому відрі: екран набереться миттю. Коли курсор старіший за сам канал — діапазон порожній, і ми взагалі не турбуємо базу.

Від відра-старту 53 хода йде ліворуч: 53 і 52 віддають повідомлення, порожнє 51 пропущено з кешу, на відрі 50 набрано N — і скан спинився, не дійшовши ні до відер 49-48, ні до дна. *Хода спиняється на першій із двох умов: набрано N або досягнуто дна. Дно — це відро створення каналу; воно існує задарма, бо channel_id теж Snowflake.*

> 🔧 **Навіщо це.** Різниця між системою, що відповідає за 15 мс, і тією, що зависає на розрідженому каналі, — це не швидкість бази, а **де стоїть нижній край скану**. Поставиш його від структури («йдемо, доки не набралось») — і одного дня хтось відкриє тихий канал трирічної давнини, а сервіс піде перебирати сотні порожніх відер поспіль. Поставиш його від даних (`bucket_of(channel_id)` — канал не міг писати до свого народження) — і скан обмежений завжди, за побудовою. Дно тут не оптимізація, а інваріант: воно є в кожному Snowflake, треба лише його прочитати.

## Крок 3. Пам'ятати порожні відра

Дно рятує від нескінченності, але не від марноти: канал, створений п'ять років тому з десятком старих повідомлень, усе одно змусить перебрати ~180 порожніх відер, поки набереться екран. Discord описав рівно цю латку словами «ми **навчили запити відстежувати порожні відра й надалі їх оминати**» — і тоді, за їхніми ж словами, повторний такий запит у гіршому разі сканує лише найновіше відро. Додаємо пам'ять про дірки:

```rust
use std::collections::HashSet;

fn fetch_before_cached(
    store: &impl Store,
    empty: &mut HashSet<(u64, u64)>, // відомо-порожні партиції (channel_id, bucket)
    channel_id: u64,
    before: u64,
    limit: usize,
) -> Page {
    let mut out = Vec::with_capacity(limit);
    let start = bucket_of(before); // крайнє (найновіше) відро цього запиту

    for bucket in buckets_desc(channel_id, before) {
        if empty.contains(&(channel_id, bucket)) {
            continue; // уже знаємо: тут порожньо — навіть не турбуємо сховище
        }
        let need = limit - out.len();
        let rows = store.query_partition(channel_id, bucket, before, need);
        if rows.is_empty() {
            // Кешувати «порожнє» можна ЛИШЕ там, де фільтр `before` не міг сховати рядки.
            // У крайньому відрі нуль означає «усі повідомлення >= before», а не «відро
            // пусте» — його позначати не можна, інакше наступний запит із більшим
            // before хибно проскочить відро, у якому насправді є що читати.
            if bucket < start {
                empty.insert((channel_id, bucket));
            }
            continue;
        }
        out.extend(rows);
        if out.len() >= limit { break; }
    }

    let next_before = out.last().map(|m| m.id);
    Page { messages: out, next_before }
}
```

Умова `bucket < start` — не косметика, а коректність. У найстарішому напрямку кожне відро повністю лежить під курсором: усі його `message_id` менші за `before` (бо його верхня межа часу строго нижча за час курсора), тож нуль рядків там означає справжню порожнечу — таку кешувати безпечно. А от **крайнє** відро `start` містить і саме `before`, і сусідів; нуль рядків у ньому означає лише «нижче за before тут уже нічого немає», але вище — є. Позначиш його порожнім — і наступна сторінка з іншим курсором помилково проскочить живе відро. Один рядок захисту `if bucket < start` тримає кеш чесним.

## Складність і пастки

**Скільки це коштує.** Кількість відер між дном і курсором — це `(час_before − час_каналу) / 864_000_000`. Рік — це лише ~36.5 відра, п'ятирічний канал — ~180. Тобто навіть уся історія найстарішого каналу — це кілька сотень партицій, а щільний канал віддає екран за одну-дві. Небезпека завжди одна — **розрідженість**: діри між рідкими повідомленнями. Дно обмежує їхнє число згори, а кеш порожніх відер робить повторний запит амортизовано O(порушених непорожніх відер + 1) — рівно та обіцянка «у гіршому разі скануємо тільки найновіше відро».

**Пастка 1: необмежений зворотний скан.** Без дна й без кешу «останні N» на тихому каналі перетворюються на перебір усіх відер аж до нуля — сотні мережевих походів у базу на кожне гортання. У Discord це вистрелило найболючіше на каналах, засипаних **надгробками** (tombstones): хтось зайшов, написав, стер, пішов — лишивши відра, повні маркерів видалення й жодного живого рядка. Cassandra перечитувала надгробки на кожному читанні, тиск на збирача сміття зростав, паузи довшали. Латка була подвійна: відстежувати порожні відра (алгоритм вище) і скоротити строк життя надгробків. Обидва боки — про те саме: **не платити знову за дірку, про яку вже знаєш**.

**Пастка 2: off-by-one на межі відра.** Три обличчя однієї помилки. Перше — **включність краю**: Discord у `make_buckets` пише `range(make_bucket(start), make_bucket(end) + 1)`, і цей `+ 1` включає останнє відро; у Rust те саме дає `..=`. Забудеш його (звичайний `..`) — і тихо втратиш ціле 10-денне вікно повідомлень: діапазон обірветься на відро раніше, а користувач просто не побачить частини історії. Друге — **межове повідомлення**: те, чий час націло ділиться на `BUCKET_MS`, за цілочисловим діленням належить **вищому** відру; поки один і той самий `bucket_of` рахує і запис, і читання, край узгоджений — але дозволь запису й читанню округляти по-різному, і межове повідомлення запишеться в одне відро, а шукатиметься в сусідньому, ставши невидимим. Третє обличчя — та сама умова `bucket < start` з кроку 3.

**Пастка 3: переповнення 64 біт.** Сам `id >> 22` лише зменшує число — безпечний. `ms_since_epoch` не перевищує `2⁴² − 1 ≈ 4.4·10¹²` (бо годинник — це рівно 42 біти), плюс `DISCORD_EPOCH` (1.42·10¹²) дає ~5.8·10¹² — далеко під стелею `u64`. Справжня пастка — **типи**. У Python кожне ціле необмежене, тож блоговий код не може переповнитись — саме тому він і читається так чисто. Перенеси ту саму арифметику в мову з фіксованими цілими — і мусиш свідомо взяти 64 біти: `int timestamp = id >> 22` у C з 32-бітним `int` переповниться катастрофічно, бо `ms_since_epoch` (~4·10¹⁰) не вміщається у ~2.1·10⁹. Схема Discord кодує це прямо: `channel_id` і `message_id` — `bigint` (64 біти), а `bucket` — звичайний `int` (32 біти). Чому відру вистачає 32? Бо воно крихітне: найбільше можливе відро за будь-який Snowflake — це ~5090 (сам 42-бітний годинник вичерпається аж близько 2154 року), тож 32 біти покривають усе життя схеми з колосальним запасом. А от якщо колись помножиш `bucket · BUCKET_MS` назад, щоб дістати час початку відра, — тримай і цей добуток 64-бітним: 5090 · 8.64·10⁸ ≈ 4.4·10¹² вже давно за 32-бітною межею.
