# 🧮 Арифметика fan-out: аналіз витрат, мультиплікація та точка зламу

Вибір між моделлю розсилки On-Write та On-Read — це не стилістична перевага, а суто математичне розв'язання рівняння ресурсоємності. Будь-яка система сповіщень платить за доставку сигналів двома ресурсами: операціями введення-виведення (I/O) під час запису та операціями I/O під час читання. Мета цього аналізу — точно обчислити критичний розмір аудиторії, за якого модель On-Write стає руйнівною, та визначити точку переходу на On-Read або гібрид.

## Показники та змінні моделі

Визначимо базові параметри системи:

- `N` — кількість отримувачів події (розмір аудиторії);
- `f_event` — частота генерації подій даного типу (подій за секунду);
- `f_read` — частота відкриття застосунку / зчитування стрічки підписниками (запитів за секунду);
- `C_write` — обчислювальна вартість збереження 1 запису в чергу або БД (процесорний час + мережевий RTT + дисковий I/O);
- `C_read` — обчислювальна вартість зчитування 1 запису зі стрічки / вхідних;
- `M` — середнє число джерел/топіків, які зчитує один користувач під час On-Read вибірки.

## Формалізація витрат On-Write (Push / Materialized)

При On-Write моделі кожна подія миттєво розмножується на `N` підписників у момент виникнення. Процесор і мережева картка сервера витрачають ресурси пропорційно до кількості отримувачів `N`.

```
Cost_write_per_sec = f_event · N · C_write      [витрати запису на секунду]

Cost_read_per_sec = f_read · C_read             [витрати читання на секунду]

Total_OnWrite
= Cost_write_per_sec + Cost_read_per_sec       [сума витрат]
= (f_event · N · C_write) + (f_read · C_read)  [підстановка компонентів]
```

Звідси видно головну властивість On-Write: витрати читання мінімальні й стали `O(1)`, але витрати запису зростають лінійно від розміру аудиторії `N`. Якщо `N` сягає 10 000 користувачів, одна подія вимагає 10 000 дискових/мережевих операцій.

## Формалізація витрат On-Read (Pull / Query-Time Join)

При On-Read моделі подія зберігається рівно в одному екземплярі у журналі джерела, а розмноження відбувається під час зчитування.

```
Cost_write_per_sec = f_event · 1 · C_write      [витрати запису на секунду]

Cost_read_per_sec = f_read · M · C_read         [витрати читання на секунду]

Total_OnRead
= Cost_write_per_sec + Cost_read_per_sec       [сума витрат]
= (f_event · C_write) + (f_read · M · C_read)  [підстановка компонентів]
```

Властивість On-Read: витрати запису є сталими `O(1)` незалежно від того, скільком людям призначена подія. Проте витрати читання зростають залежно від кількості активних читачів `f_read` та кількості джерел `M`.

## Обчислення точки зламу (Critical Threshold N_crit)

Шукаємо точку рівноваги `N_crit`, у якій сукупна вартість On-Write дорівнює сукупній вартості On-Read:

```
(f_event · N_crit · C_write) + (f_read · C_read)
= (f_event · C_write) + (f_read · M · C_read)           [рівність витрат On-Write = Total_OnRead]

f_event · C_write · (N_crit - 1)
= f_read · C_read · (M - 1)                            [перенос подібних доданків]

N_crit - 1
= (f_read / f_event) · (C_read / C_write) · (M - 1)     [ділення на f_event · C_write]

N_crit
≈ (f_read / f_event) · (C_read / C_write) · M          [наближення для N >> 1, M >> 1]
```

Отримана формула дає інженерний орієнтир:

1. Якщо розмір аудиторії події `N < N_crit`, ефективнішою є модель **On-Write** (швидке читання переважає витрати на невеликий розсип записів).
2. Якщо розмір аудиторії події `N > N_crit`, ефективнішою є модель **On-Read** (дешевий запис захищає від вибуху навантаження).

## Числовий розрахунок для платформи Digital Homes

Розгляньмо конкретні числа для ЖК на 5 000 квартир (12 500 мешканців):

- `f_event` = 0.001 подій/с (одне загальне оголошення ОСББ на день);
- `f_read` = 0.5 запитів/с (мешканці відкривають застосунок періодично протягом дня);
- `C_read / C_write` ≈ 0.2 (читання з кешу в 5 разів дешевше за транзакційний запис у БД);
- `M` = 10 (мешканець підписаний на 10 топіків: дім, під'їзд, паркінг, ліфт, ОСББ тощо).

```
N_crit
= (f_read / f_event) · (C_read / C_write) · M    [формула точки зламу]
= (0.5 / 0.001) · 0.2 · 10                       [підстановка конкретних чисел]
= 500 · 0.2 · 10                                 [проміжне множення]
= 1 000 отримувачів                              [кінцевий критичний поріг]
```

**Висновок аналізу:** Для будь-якої події з аудиторією понад 1 000 мешканців наївна розсилка On-Write стає економічно збитковою та створює ризик перезавантаження I/O системи.

## Множник мультиплікації (Amplification Factor) та ємність черги

Множник мультиплікації (англ. *Fan-Out Amplification Factor*, `A_f`) показує, у скільки разів вихідний потік асинхронних задач перевищує вхідний потік подій:

```
A_f = N_avg                                      [середня аудиторія події]

Throughput_req = f_event_total · A_f             [визначення необхідної пропускної спроможності]
```

Якщо в Digital Homes стається 10 аварійних локальних подій на секунду (у кожній `N` = 3 мешканці) і 1 масова подія `N` = 12 000, то:

```
Throughput_req
= (10 · 3) + (1 · 12 000)                        [підстановка локальних та масових подій]
= 30 + 12 000                                    [проміжний розрахунок]
= 12 030 задач / секунду                         [підсумкове навантаження на чергу]
```

Масова подія формує **99.75%** всього навантаження на чергу задач. Саме тому ізоляція масових подій у гібридну або On-Read траєкторію є єдиним способом гарантувати, що локальні аварійні 30 задач на секунду виконуватимуться із затримкою під 100 мілісекунд, а не годинами.

## Теорія масового обслуговування та затримка черги (M/M/c Model)

Щоб оцінити затримку доставки сповіщень у проді під час сплеску On-Write, застосуємо модель теорії масового обслуговування `M/M/c` (де `c` — кількість паралельних воркерів у пулі, `lambda` — темп надходження задач, `mu` — пропускна спроможність одного воркера):

```
Util = lambda / (c · mu)                        [коефіцієнт завантаження пулу воркерів]
```

Якщо завантаження `Util` наближається до 1.0 (наприклад, 0.98 під час масової розсилки), затримка очікування в черзі `W_q` зростає за гіперболою:

```
W_q ≈ (Util / (1 - Util)) · (1 / mu)            [оцінка середнього часу очікування в черзі]
```

Якщо один воркер робить push-запит за `10 мс` (`mu = 100` задач/с), а завантаження пулу через сплеск On-Write зросло до `0.99`, то час очікування в черзі складе:

```
W_q
≈ (0.99 / (1 - 0.99)) · 0.010                   [підстановка завантаження 0.99]
= (0.99 / 0.01) · 0.010                         [проміжне ділення]
= 99 · 0.010                                    [множення на час обробки]
= 0.99 секунди                                  [затримка лише в черзі]
```

При завантаженні `0.999` затримка очікування зростає до 10 секунд! Це прямо доводить, чому сплески On-Write розсилок руйнують SLA затримки критичних аварійних сповіщень, якщо вони живуть у спільній черзі.

## Визначення розміру пулу воркерів (Worker Pool Sizing)

Для забезпечення гарантованої затримки аварійного каналу `SLA_target < 0.5` секунди під час пікового навантаження `lambda_max` обчислимо мінімально необхідну кількість воркерів `c_min`:

```
c_min
= (lambda_max / mu) · (1 + (1 / (mu · SLA_target)))  [розрахунок мінімальної кількості потоків]
```

Якщо для аварійного каналу `lambda_max = 50` задач/с, `mu = 100` задач/с, а `SLA_target = 0.5` с:

```
c_min
= (50 / 100) · (1 + (1 / (100 · 0.5)))          [підстановка параметрів emergency каналу]
= 0.5 · (1 + (1 / 50))                          [проміжне множення]
= 0.5 · 1.02                                    [додавання константи]
= 0.51 воркера                                  [теоретична межа]
```

Для гарантії відсутності затримок виділений emergency-пул налаштовується на `c = 4` воркери, що гарантує p99 затримку очікування `W_q < 5 мс` за будь-яких умов.

## Моделювання потреби в оперативній пам'яті (RAM Allocation)

Розплануємо обсяг оперативної пам'яті, необхідний для утримання черги задач у Redis під час сплеску On-Write розсипки:

```
RAM_req = N_recipients · S_payload · M_safety  [формула розрахунку пам'яті]
```

Де `S_payload` — розмір середовища задачі (включаючи ключі дедуплікації, payload, заголовочки та токени пристроїв, типово 2 кілобайти), а `M_safety = 1.5` — коефіцієнт запасного буфера на службові структури даних Redis:

```
RAM_req
= 30 000 · 2048 · 1.5                           [підстановка для масової розсилки]
= 61 440 000 · 1.5                              [проміжне множення]
= 92 160 000 байт                               [байтовий обсяг]
≈ 92.16 мегабайт                                [підсумковий обсяг RAM на 1 подію]
```

Якщо протягом п'яти хвилин стається 20 подібних масових оголошень, потреба у RAM перевищує 1.8 гігабайта. При перевищенні ліміту пам'яті Redis запускає алгоритм витіснення ключів (maxmemory-policy), знищуючи гарячі ключі дедуплікації або викликаючи OOM-killer процесу.

## Вплив згортання (Coalescing Ratio) на оптимізацію витрат

Якщо до розсилки застосувати попереднє злиття подій у часовому вікні `W`, коефіцієнт стиснення подій `K_coalesce` визначається як:

```
K_coalesce = 1 / (1 + (Rate_events · W))        [коефіцієнт зменшення кількості подій]
```

При високій частоті повідомлень про відключення пристроїв (`Rate_events = 10` подій/сек) та вікні згортання `W = 60` секунд:

```
K_coalesce
= 1 / (1 + (10 · 60))                           [підстановка параметрів злиття]
= 1 / (1 + 600)                                 [множення частоти на вікно]
= 1 / 601                                       [проміжне ділення]
≈ 0.00166                                       [підсумковий коефіцієнт]
```

Завдяки згортанню вихідне навантаження на роутер розсилки зменшується у **601 раз**, повністю нейтралізуючи загрозу вибуху On-Write мультиплікації.
