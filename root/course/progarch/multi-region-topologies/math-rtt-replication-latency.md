# 🧮 Фізика RTT та математика міжрегіональної реплікації

Математична та фізична модель затримок поширення сигналу в оптоволокні визначає фундаментальні межі продуктивності, латентності та втрат даних при передачі стану між міжрегіональними центрами обробки даних. Без розрахунку швидкості світла, коефіцієнтів заломлення скла, накладних витрат мережевих протоколів та вікон TCP неможливо обґрунтувати вибір між синхронною та асинхронною реплікацією даних, оцінити граничну пропускну здатність міжконтинентальних каналів та вирахувати потенційну обсяг втраченої інформації (RPO) у момент кабельного розриву.

## Фізика світла у склі та мінімальний RTT

Поширення електромагнітної хвилі у вакуумі відбувається зі швидкістю `c ≈ 299 792 458 м/с` (приблизно `300 000 км/с`). Проте у середовищі оптичного волокна (кварцеве скло з домішками германію) світло зазнає гальмування за рахунок взаємодії з електронними оболонками атомів. Швидкість світла в оптоволокні `v_fiber` визначається відношенням `c` до абсолютного показника заломлення ядра волокна `n`:

```
v_fiber = c / n
```

Для стандартного одномодового оптичного волокна марки SMF-28 (стандарт ITU-T G.652), що є основою міжконтинентальних підводних та наземних ліній зв'язку, показник заломлення на робочій довжині хвилі 1550 нм становить `n ≈ 1.4682`.

Підставивши значення, отримуємо фазову швидкість поширення світлового імпульсу у волокні:

```
v_fiber = 299 792.458 / 1.4682
= 204 190.47 км/с               [ділення c на показник заломлення n=1.4682]
```

Це означає, що світло у прозорому склі долає відстань у `1000 км` за `4.897 мс`.

Проте реальний шлях оптичного кабелю між центрами обробки даних ніколи не йде найкоротшою геодезичною лінією (великим колом Землі). Кабелі прокладають уздовж залізниць, автошляхів, оминаючи рельєф дна океанів та тектонічні розломи. Для розрахунку реальної довжини оптичної траси `L_optical` застосовують коефіцієнт трасування `k_route` (традиційно `k_route ≈ 1.30 – 1.45` для наземних ліній та `k_route ≈ 1.15 – 1.25` для підводних кабелів):

```
L_optical = d_geo · k_route     [де d_geo — геодезична відстань між ДЦ]
```

Окрім геометричної довжини волокна, у підсумковий час кругового запізнення (Round-Trip Time, RTT) додається затримка у активному обладнанні: оптичних підсилювачах (EDFA/DRA), міжпроміжних повторювачах, мультиплексорах DWDM та кордових маршрутизаторах. У середньому комутаційні вузли додають від `0.003` до `0.008 мс` на кожен кілометр траси.

Підсумкова формула фізичного мінімального RTT між двома географічними регіонами має вигляд:

```
RTT_phys = 2 · (L_optical / v_fiber + t_equip)
= 2 · (d_geo · k_route / v_fiber + t_equip)   [підстановка L_optical = d_geo · k_route]
```

## Матриця затримок між глобальними хмарними регіонами

Застосуємо фізичну модель до реальних магістралей, якими з'єднані центри обробки даних (Frankfurt `eu-central-1`, N. Virginia `us-east-1`, Tokyo `ap-northeast-1`, Kyiv `local-dc`):

1. **Франкфурт ↔ Київ:**
   Геодезична відстань `d_geo ≈ 1 850 км`. Наземний кабель `k_route = 1.35` дає `L_optical ≈ 2 497 км`.
   
```
RTT_phys = 2 · (2 497 / 204 190.47)
= 2 · 0.012228 c                [час поширення світла в один бік]
= 24.45 мс                       [чистий RTT в обох напрямках]
```
   З урахуванням комутації реальний мережевий RTT становить `25 – 28 мс`.

2. **Франкфурт ↔ Північна Вірджинія (Трансатлантичний підводний кабель):**
   Геодезична відстань `d_geo ≈ 6 330 км`. Підводний кабель `k_route = 1.20` дає `L_optical ≈ 7 596 км`.

```
RTT_phys = 2 · (7 596 / 204 190.47)
= 2 · 0.037200 c                [час поширення світла крізь Атлантику]
= 74.40 мс                       [чистий RTT в обох напрямках]
```
   З урахуванням підводних оптичних підсилювачів та прибережних гейтвеїв реальний RTT становить `78 – 85 мс`.

3. **Франкфурт ↔ Токіо (Транссибірський / Транстихоокеанський маршрут):**
   Геодезична відстань `d_geo ≈ 9 350 км`. Комбінований тракт `k_route = 1.35` дає `L_optical ≈ 12 622 км`.

```
RTT_phys = 2 · (12 622 / 204 190.47)
= 2 · 0.061814 c                [час поширення світла до Азії]
= 123.63 мс                      [чиста латентність оптичного шляху]
```
   З урахуванням багатьох транзитних автономних систем (AS) та міжконтинентальних стиків реальний мережевий RTT становить `210 – 235 мс`.

## Ціна синхронної реплікації у міжрегіональних транзакціях

Уявімо розподілену транзакцію запису між регіоном Франкфурт (Primary) та Токіо (Replica).

Якщо застосовується **строго синхронна реплікація** (Synchronous Replication), транзакція вважається завершеною лише тоді, коли запис зафіксовано на обох вузлах. Використання двохфазного фіксування (Two-Phase Commit, 2PC) вимагає двох послідовних сетевих раундів спілкування між координатором та учасником:

1. Раунд 1: Фаза підготовки (`Prepare` → `Ready`).
2. Раунд 2: Фаза коміту (`Commit` → `Acknowledged`).

Розрахуємо мінімальний час виконання синхронної 2PC-транзакції `T_2pc` з урахуванням локального I/O диска `T_disk ≈ 2 мс`:

```
T_2pc = 2 · RTT_WAN + T_disk
= 2 · 220 мс + 2 мс              [підстановка RTT Франкфурт-Токіо = 220 мс]
= 442 мс                         [загальна латентність одного запису!]
```

Для порівняння, якщо реплікація виконується усередині одного дата-центру (`RTT_local ≈ 0.5 мс`), той самий 2PC завершується за:

```
T_2pc_local = 2 · 0.5 мс + 2 мс  [підстановка RTT_local = 0.5 мс]
= 3.0 мс                         [затримка усередині одного ДЦ]
```

Отже, винесення другого вузла синхронної 2PC-транзакції через океан **збільшує затримку у 147 разів** (`442 / 3.0 ≈ 147.3`).

Якщо замість 2PC використовується міжрегіональний консенсус Raft або Paxos (де потрібна згода більшості вузлів, тобто `(N/2) + 1`), для підтвердження коміту достатньо **одного раунду RTT** до найближчого кворуму. При розташуванні 3 вузлів у Франкфурті, Ірландії та Вірджинії, Франкфурт отримує кворум від Ірландії (`RTT ≈ 15 мс`), не чекаючи на Вірджинію (`RTT ≈ 80 мс`):

```
T_consensus = RTT_closest_quorum + T_disk
= 15 мс + 2 мс                   [підстановка RTT_closest_quorum = 15 мс]
= 17 мс                          [латентність за наявності локального кворуму]
```

Саме тому сучасні розподілені бази даних розміщують 2 з 3 реплік кворуму в близьких географічних зонах, залишаючи третю дальню репліку лише для катастрофічного виживання.

## Добуток пропускної здатності та затримки (BDP)

Окрім латентності одиночного запиту, фізика RTT обмежує граничну пропускну здатність каналу передачі даних між регіонами при використанні протоколу TCP.

Добуток пропускної здатності на затримку (Bandwidth-Delay Product, BDP) визначає обсяг даних, який мусить перебувати «у польоті» (in-flight data) в оптичній жилі, щоб повністю заповнити мережевий канал:

```
BDP = Bandwidth · RTT
```

Для 10-гігабітного міжрегіонального каналу (`Bandwidth = 10 Gbit/s = 1.25 GB/s`) між Франкфуртом та Вірджинією (`RTT = 80 мс`):

```
BDP = 1.25 GB/s · 0.080 c
= 0.100 GB                       [множення швидкості на час затримки]
= 100 MB                         [обсяг даних у польоті через океан]
```

Якщо розмір буфера вікна прийому TCP (TCP Window Size `W_tcp`) менший за `BDP`, відправник змушений зупиняти передачу нових пакетів і чекати на надходження підтвердження `ACK` з іншого боку океану. Максимальна досяжна швидкість передачі `Th_max` описується формулою:

```
Th_max = min(Bandwidth, W_tcp / RTT)
```

При стандартному неоптимізованому системному буфері TCP `W_tcp = 64 KB` на каналі з `RTT = 80 мс` гранична швидкість реплікації даних становитиме:

```
Th_max = 65 536 bytes / 0.080 c
= 819 200 bytes/s                [ділення розміру вікна на RTT]
= 0.819 MB/s                     [конвертація у мегабайти за секунду (6.55 Mbps)]
```

Щоб вичерпати 10 Gbps канал реплікації між регіонами, операційна система мусить налаштувати динамічне масштабування буферів TCP (TCP Window Scaling, RFC 7323) до величини не менше ніж `100 MB`.

## Математична модель втрати даних при асинхронній реплікації (RPO)

При асинхронній реплікації Primary-вузол відповідає клієнту про успіх одразу після фіксування запису у локальний журнал WAL, а передача зміщень у дальній регіон відбувається фоновим потоком з асинхронним лагом `Δt_lag`.

Обсяг втрачених даних `Data_loss` у байтах при раптовому виході з ладу Primary-регіону (аварія живлення, кабельний розрив) виражається через інтенсивність потоку запису `R_write` (байтів/сек):

```
RPO_bytes = ∫_{t_fail - Δt_lag}^{t_fail} R_write(t) dt
```

При постійному навантаженні запису `R_write = const` вираз спрощується до:

```
RPO_bytes = R_write · Δt_lag
```

Якщо платформа згенеровує `5 000` операцій запису на секунду, а середній розмір транзакції становить `2 KB` (`R_write = 10 MB/s`), то при міжконтинентальному лагу реплікації `Δt_lag = 2.5 c` втрата даних під час автоматичного переключення (Failover) становитиме:

```
RPO_bytes = 10 MB/s · 2.5 c
= 25 MB                          [неповоротно втрачені транзакції!]
```

Кількість втрачених бізнес-операцій `N_lost` визначається як:

```
N_lost = TPS_write · Δt_lag
= 5 000 ops/s · 2.5 c            [підстановка TPS_write = 5000 та lag = 2.5s]
= 12 500 операцій                 [підсумкова кількість втрачених транзакцій]
```

Саме цей математичний факт вимагає від архітектора свідомого вибору: або погодитися на потенційну втрату 12 500 записів ради 20-мілісекундного відгуку користувачам, або платити 220 мілісекунд латентності на кожен запис ради гарантії `RPO = 0`.
