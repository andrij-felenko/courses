# 🧮 Математична модель пропускної здатності та оцінки часу очікування у віртуальній черзі

Проєктування архітектури Virtual Waiting Room вимагає сувого математичного опису процесів накопичення та вимивання трафіку, оскільки помилка в розрахунку пропускної здатності призводить або до каскадного перевантаження джерела правди (Origin), або до невиправданого простою товарних запасів. В основі управління віртуальною чергою лежать алгоритми теорії масового обслуговування (Queueing Theory), балансу потоків та детермінованого допуску за допомогою шаблону Token Bucket.

## Динаміка накопичення черги та закон збереження потоків

Розглянемо систему продажу квитків як замкнений контур обробки запитів. Позначимо через `λ_in(t)` інтенсивність надходження вхідних запитів користувачів у момент часу `t` (вимірюється в користувачах на секунду, req/s). Позначимо через `r(t)` інтенсивність допуску користувачів із віртуальної кімнати очікування до захищеного Origin-сервісу checkout.

У момент початку продажів `t = 0` виникає імпульсна хвиля трафіку, де `λ_in(t) >> r(t)`. Загальна кількість користувачів у черзі `Q(t)` у довільний момент часу `t >= 0` описується рівнянням балансу:

```
Q(t) = Q(0) + ∫ [λ_in(τ) - r(τ) - γ(τ)] dτ   [баланс накопичення черги у часі]
```

Де:
- `Q(0)` — початкова кількість користувачів, які перебували у Pre-queue до моменту старту `t = 0`.
- `λ_in(τ)` — миттєвий вхідний потік нових користувачів.
- `r(τ)` — швидкість вибуття користувачів із черги до сервісу купівлі (Admission Rate).
- `γ(τ)` — швидкість добровільного залишення черги користувачами через втрату терпіння або закриття вкладки браузера (Abandonment Rate).

Якщо ми знехтуємо відтоком `γ(τ)` для отримання найгіршого сценарію (Worst-case Capacity Planning), накопичення черги досягає свого піка `Q_max` у момент часу `t_peak`, коли вхідний потік спадає дорівнює швидкості допуску `λ_in(t_peak) = r(t_peak)`.

## Адаптація закону Літтла та обчислення миттєвої позиції й ETA

Для кожного користувача, який перебуває у черзі на позиції `Pos(t)` у момент часу `t`, головним показником є прогноз часу очікування `W_hat(t)` (Estimated Time of Arrival, ETA).

Відповідно до фундаментального закону Літтла (Little's Law) для стаціонарних систем масового обслуговування, середня кількість покупців у системі `L` дорівнює добутку середньої інтенсивності допуску `λ` на середній час перебування покупця в системі `W`:

```
L = λ · W   [закон Літтла для стаціонарної черги]
```

У дискретній кімнаті очікування позиція користувача `Pos(t)` зменшується з кожним крон-інтервалом випуску пакету токенів. Динаміка зміни позиції описується виразом:

```
Pos(t) = max(0, Pos(0) - ∫ r(τ) dτ)   [зменшення порядкового номера у черзі]
```

Якщо швидкість допуску є константою або плавно коригується контролером `r(τ) ≈ r_bar`, миттєва оцінка часу очікування `W_hat(t)` обчислюється як:

```
W_hat(t) = Pos(t) / r_bar + T_processing   [оцінка часу очікування в секундах]
```

Де `T_processing` — затримка виконання одного кроку видачі токену та ініціалізації сесії в Origin.

### Модель згладжування оцінки часу (Moving Average ETA)

Оскільки реальна швидкість покупки `r(t)` коливається залежно від часу, який користувачі витрачають на вибір місця в залі та введення даних банківської картки, використання прямого ділення `Pos(t) / r(t)` створює високу осциляцію (стрибки) значення ETA у браузері користувача.

Щоб запобігти паніці користувачів через резкі стрибки лічильника, застосовують експоненційно зважене ковзне середнє (EWMA) для розрахунку ефективної швидкості допуску `r_bar_k` на кроці `k`:

```
r_bar_k = α · r_measured_k + (1 - α) · r_bar_k_minus_1   [згладжування швидкості EWMA]
```

Де:
- `r_measured_k` — фактична кількість викуплених сесій або знятих блокувань за останнє вікно вимірювання (наприклад, за останні 10 секунд).
- `α ∈ (0, 1]` — коефіцієнт згладжування (типово `α = 0.15 ... 0.20`).

## Розрахунок граничної спроможності Origin та бакету токенів

Головним обмеженням, яке визначає максимально припустиму швидкість `r_max`, є ємність критичного ресурсу в Origin-базі даних.

Розглянемо параметри системи:
- `K_active` — максимальна кількість одночасних активних сесій оформлення квитків (Checkout Sessions), яку здатна витримати база даних без виникнення дедлоків та деградації latency понад 500 ms.
- `T_checkout` — середній час, який користувач проводить на екрані оплати (зазвичай `T_checkout = 300 ... 600` секунд).
- `C_db_iops` — гранична кількість транзакцій запису в секунду, яку витримує накопичувач БД.

Для підтримки стабільного стану системи кількість активних сесій в Origin `N_active(t)` не повинна перевищувати `K_active`. Динаміка активних сесій описується рівнянням:

```
d N_active(t) / dt = r(t) - μ_checkout · N_active(t)   [баланс активних сесій checkout]
```

Де `μ_checkout = 1 / T_checkout` — інтенсивність завершення сесій купівлі.

У сталому режимі (`d N_active / dt = 0`) маємо максимальну безпечну швидкість входу `r_safe`:

```
r_safe = μ_checkout · K_active = K_active / T_checkout   [безпечна швидкість допуску]
```

### Алгоритм Token Bucket для допуску

Для реалізації швидкості `r_safe` на рівні Edge Gatekeeper використовується алгоритм бакету токенів (Token Bucket). Бакет має ємність `B` токенів і поповнюється зі швидкістю `R = r_safe` токенів на секунду.

Кількість доступних токенів `b(t)` у момент часу `t` обчислюється як:

```
b(t) = min(B, b(t_last) + R · (t - t_last))   [поповнення бакету токенів]
```

При надходженні запиту з перевіреним статусом черги:
- Якщо `b(t) >= 1`: видається токен доступу Pass Token, `b(t) = b(t) - 1`, запит пропускається до Origin.
- Якщо `b(t) < 1`: запит затримується в черзі або повертається статус очікування HTTP 202 / 302.

## Модель добровільного залишення черги (Abandonment Rate)

Психологічна поведінка користувачів у віртуальній черзі описується ймовірнісним розподілом терпіння. Нехай `T_patience` — випадкова величина терпіння користувача з функцією розподілу `F(t) = P(T_patience <= t)`.

У практичних архітектурних розрахунках функцію залишення черги часто моделюють за допомогою лог-нормального розподілу або експоненційного згасання з параметром інтенсивності відтоку `β`:

```
P(abandon | W) = 1 - exp(-β · W)   [ймовірність добровільного залишення черги]
```

Якщо очікуваний час `W_hat` перевищує 15 хвилин (900 секунд), коефіцієнт залишення сягає ~40%. Це означає, що реальне навантаження на сервіс оформлення зменшується природним чином, але збільшується кількість «покинутих слотів» (Abandoned Slots), які вимагають швидкого повернення в загальний пул доступних токенів.

## Аналіз моделей черг Пуассона та Маркова (M/M/c vs M/D/c)

При моделюванні віртуальної кімнати очікування системи класифікують за нотацією Кендалла (Kendall's Notation). 

Вхідний потік нових користувачів після первинного спалаху описується Пуассонівським процесом з інтенсивністю `λ`. Час обробки сесії купівлі `T_checkout` моделюється або експоненційним розподілом `M` (модель M/M/c), або детермінованим суворим таймером `D` (модель M/D/c), де `c = K_active` — кількість паралельних обслуговуючих каналів (слотів в Origin).

У моделі M/D/c з фіксованим таймером викупу `T_checkout = 600` секунд ймовірність того, що всі `c` каналів зайняті (формула Ерланга B), обчислюється як:

```
P_block = ( (λ / μ)^c / c! ) / Σ_{k=0}^{c} ( (λ / μ)^k / k! )   [формула блокування Ерланга]
```

Використання детермінованого таймера викупу в Origin знижує дисперсію часу очікування у 2 рази порівняно з експоненційним розподілом, що суттєво підвищує точність прогнозування ETA для покупців у черзі.

## Числовий приклад розрахунку для топ-концерту

Проведемо повний розрахунок параметрів Virtual Waiting Room для реального сценарію продажу квитків на стадіонний концерт.

### Вхідні дані:
1. Загальна кількість квитків у продажу: `N_tickets = 60,000`.
2. Вхідний спалах трафіку на `t = 0`: `Q(0) = 300,000` користувачів у Pre-queue, додатковий потік `λ_in = 2,000 req/s` протягом перших 5 хвилин.
3. Продуктивність Origin БД: максимум `K_active = 3,000` паралельних сесій checkout.
4. Середній час вибору місця та оплати: `T_checkout = 360` секунд (6 хвилин).

### Крок 1. Обчислення допустимої швидкості входу `r_safe`:

```
r_safe = K_active / T_checkout = 3000 / 360 = 8.33 сесій/сек = 500 сесій/хвилину
```

### Крок 2. Обчислення максимального часу очікування `W_max` у найгіршій позиції:

Для 300 000-го користувача в черзі:

```
W_max = Q(0) / r_safe = 300,000 / 8.33 = 36,014 секунд ≈ 10 годин
```

Оскільки `W_max` є неприпустимо великим, система після розпродажу всіх 60 000 квитків (що станеться за `N_tickets / середня кількість квитків на чек`) повинна автоматично закрити чергу й сповістити решту користувачів про статус Sold Out.

Якщо кожен покупець купує в середньому 2.5 квитки, загалом буде допущено:

```
N_admitted = 60,000 / 2.5 = 24,000 покупців
```

Час повного розпродажу події `T_sold_out` складе:

```
T_sold_out = N_admitted / r_safe = 24,000 / 8.33 = 2,881 секунд ≈ 48 хвилин
```

Усі користувачі з позицією в черзі понад 24 000 бачитимуть повідомлення: «Незважаючи на високу позицію у черзі, кількість доступних квитків обмежена. Можливий повний розпродаж до настання вашої черги».

Цей математичний апарат дозволяє точно запрограмувати ліміти Token Bucket та забігти виникненню критичних перевантажень захищеного Origin-сервера.
