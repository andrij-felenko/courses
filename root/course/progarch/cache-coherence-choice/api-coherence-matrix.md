# 📋 Матриця та контракт стратегій свіжості даних між сервісами

Ця довідкова матриця систематизує архітектурні параметри, гарантії свіжості даних, ціну інфраструктури та ризики для п'яти основних патернів когерентності кешу між розподіленими сервісами, а також визначає стандартний контракт повідомлень та REST/gRPC-інтерфейсів інвалідації.

## 1. Сводна матриця порівняння стратегій когерентності

У таблиці нижче наведено систематичне порівняння стратегій за ключовими інженерними критеріями.

| Стратегія когерентності | Максимальне вікно несвіжості (`W`) | Зчеплення розгортання та часу | Ризик подвійного запису (Dual-Write) | Складність інфраструктури | Гарантія консистентності | Основний сценарій застосування |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Direct Read (Без кешу)** | `0 мс` (Строга свіжість) | Високе часове (1:1 HTTP/gRPC) | Вручну відсутній | Мінімальна (тільки DB) | Strong / Linearizable | Фінансові транзакції, списання коштів, блокування залишків |
| **Cache-Aside + Eviction** | `[0, TTL]` (залежить від гонок) | Низьке часове | **Високий** (при збої після `DB.commit`) | Низька (Redis/Memcached) | Eventual (з можливими зомбі-ключами) | Некритичні читання з високим навантаженням (профілі, каталоги) |
| **Write-Through / Write-Behind** | Write-Through: `0 мс`<br>Write-Behind: `[0, T_flush]` | Write-Through: високе<br>Write-Behind: асинхронне | Низький (кеш керує DB) | Середня (Inline caching layer) | Write-Through: Strong<br>Write-Behind: Eventual | Локальні модулі в межах одного сервісу (не для міжсервісних меж) |
| **TTL / Soft TTL (Stale-While)** | `[0, TTL_hard]` (прогнозоване) | Нульове (автономні сервіси) | **Відсутній** (немає викликів інвалідації) | Низька (локальний LRU / In-memory) | Bounded Staleness (Обмежена несвіжість) | Медіа-тайли, конфігурації, високонавантажений довідковий трафік |
| **Event-Driven Invalidation** | `[T_transport, T_consumer]` | Низьке (розв'язка через брокер) | **Високий** без Transactional Outbox | Середня (Kafka / RabbitMQ + Outbox worker) | Eventual (з ризиком порушення порядку) | Міжсервісне сповіщення про зміну бізнес-сутностей |
| **Change Data Capture (CDC)** | `[T_wal_lag, T_transport]` (зазвичай < 100 мс) | Нульове (читання журналів WAL) | **Нульовий** (атомарність на рівні БД) | **Висока** (Debezium + Kafka + Schema Registry) | Monotonic Eventual (Гарантована хронологія WAL) | Критична свіжість між автономними розподіленими сервісами |

## 2. Докладний деталізований аналіз стратегій

### 2.1. Пряме читання з джерела (Direct Read / No-Cache)
Стратегія відмови від кешування перекладає все навантаження на первинну транзакційну базу даних.
- **Накладні витрати**: Висока затримка (Network Roundtrip до БД + час виконання SQL-запиту). Високі вимоги до вертикального масштабування сховища (CPU/RAM).
- **Переваги**: Гарантія лінійованості (Linearizability). Нульовий ризик читання застарілого стану. Відсутність складності інвалідації ключів.
- **Обмеження**: Створює єдину точку відмови (Single Point of Failure). При спалахах трафіку (Flash Crowd) пули з'єднань БД швидко вичерпуються.

### 2.2. Cache-Aside з інвалідацією через видалення (Eviction)
Прикладна програма явно опитує кеш, а при miss звертається до бази даних. Записувач оновлює БД й надсилає команду вилучення ключа з кешу.
- **Накладні витрати**: Одне додаткове мережеве звернення до кешу при hit. При miss — два звернення (кеш + БД) плюс операція запису в кеш.
- **Переваги**: Кешуються лише ті дані, які реально запитуються клієнтами (Lazy Loading). Пам'ять кешу використовується максимально ефективно.
- **Критичний ризик**: Проблема подвійного запису. Збій застосунку між оновленням БД та видаленням з кешу залишає зомбі-ключ назавжди. Спроба оновити значення у кеші замість видалення спричиняє race conditions між паралельними читачами й записувачами.

### 2.3. Write-Through та Write-Behind (Inline Caching)
Кеш слугує єдиною точкою входу для читання й запису.
- **Write-Through**: Синхронний запис у кеш та підлегле сховище. Гарантує консистентність, але збільшує затримку запису до суми затримок обох сховищ.
- **Write-Behind**: Асинхронний скид змін у БД пачками (Batch Flushes). Забезпечує надзвичайно високу швидкість запису, але створює ризик втрати даних (Data Loss) при раптовому падінні вузла кешу до скидання на диск.
- **Обмеження між сервісами**: Не застосовується на межах сервісів, оскільки вимагає передачі права керування транзакціями бази даних сторонньому кеш-шару.

### 2.4. Пасивна когерентність (TTL та Soft TTL / Stale-While-Revalidate)
Сервіси-споживачі зберігають локальні копії даних із встановленим часом життя, не реагуючи на мережеві події інвалідації.
- **Hard TTL**: Дані автоматично тухнуть після закінчення інтервалу. Створює ризик Cache Stampede (масовий пробіг до БД) при закінченні терміну дії гарячого ключа.
- **Soft TTL (Stale-While-Revalidate)**: Розділення TTL на м'який (фонове оновлення) та твердий (витіснення). Дозволяє повертати застаріле значення миттєво, показово знижуючи p99 затримку та ізолюючи сервіси від збоїв первинного джерела.

### 2.5. Подійно-орієнтована інвалідація (Event-Driven + Outbox)
Сервіс-власник генерує події змін стану в шину подій (Kafka / RabbitMQ), а сервіси-споживачі слухають топіки й очищають свої кеші.
- **Гарантія доставки**: Без використання патерну Transactional Outbox пряма публікація в брокер піддається ризику подвійного запису. Outbox забезпечує гарантію `at-least-once`.
- **Проблема впорядкованості**: Мережеві затримки або повторні спроби обробки (Retries) у брокері можуть призвести до доставки запізнілої події `v1` після події `v2`. Вимагає обов'язкової наявності версійних числових штампів у конверті подій.

### 2.6. Change Data Capture (CDC via Transactional Log Mining)
Спеціалізований процес (Debezium) зчитує бінарний журнал транзакцій (PostgreSQL WAL) і транслює зміну в Kafka.
- **Переваги**: Повна відсутність коду інвалідації у прикладному сервісі. Абсолютна гарантія атомарності на рівні бази даних. Сувора монотонна послідовність подій інвалідації.
- **Складність**: Вимагає високої інфраструктурної зрілості (Kafka Connect, Debezium, Schema Registry, моніторинг WAL Lag).

## 3. Контракт повідомлення інвалідації кешу

При використанні подійно-орієнтованої інвалідації (Event-Driven або CDC) сервіси-споживачі мусять отримувати стандартизований конверт повідомлення. Неоднозначність у контракті інвалідації призводить до помилкового стирання чужих ключів або пропущення інвалідації через невідому версію схеми.

### 3.1. Схема конверта інвалідації (JSON Schema)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "CacheInvalidationEvent",
  "type": "object",
  "required": [
    "eventId",
    "eventType",
    "aggregateType",
    "aggregateId",
    "sequenceNumber",
    "timestampEpochMs",
    "invalidationScope"
  ],
  "properties": {
    "eventId": {
      "type": "string",
      "format": "uuid",
      "description": "Унікальний ідентифікатор події для ідемпотентної обробки"
    },
    "eventType": {
      "type": "string",
      "enum": ["ENTITY_UPDATED", "ENTITY_DELETED", "SCOPED_EVICTION_REQUESTED"],
      "description": "Тип події інвалідації"
    },
    "aggregateType": {
      "type": "string",
      "description": "Назва доменної сутності (наприклад, 'user-profile', 'product-inventory')"
    },
    "aggregateId": {
      "type": "string",
      "description": "Первинний ключ сутності, що змінила стан"
    },
    "sequenceNumber": {
      "type": "integer",
      "minimum": 1,
      "description": "Монотонний номер версії сутності або LSN у WAL для захисту від out-of-order подій"
    },
    "timestampEpochMs": {
      "type": "integer",
      "description": "Час створення зміни на джерелі (в мілісекундах Epoch)"
    },
    "invalidationScope": {
      "type": "object",
      "required": ["strategy", "targetKeys"],
      "properties": {
        "strategy": {
          "type": "string",
          "enum": ["EXACT_KEY", "PATTERN_PREFIX", "TAG_BASED"]
        },
        "targetKeys": {
          "type": "array",
          "items": { "type": "string" },
          "description": "Список конкретних ключів або паттернів для видалення з кешу"
        }
      }
    }
  }
}
```

### 3.2. Правила семантичної обробки контракту

1. **Захист від запізнілих подій (Out-of-Order Guard)**:
   Споживач кешу зобов'язаний перевіряти `sequenceNumber` або `timestampEpochMs`. Якщо у локальному записі кешу вже збережено версію `N = 10`, а з брокера прийшла подія інвалідації з `sequenceNumber = 8`, ця подія **ігнорується**, оскільки вона відтворює застарілий стан.
2. **Семантика видалення замість перезапису (Eviction Over Update)**:
   Повідомлення інвалідації **не повинно містити нове тіло сутності** (Full Entity Payload) для прямих записів у кеш споживача, якщо між ними немає суворої впорядкованості. Повідомлення містить виключно команду на **видалення ключів** (`EXACT_KEY` / `PATTERN_PREFIX`).
3. **Ідемпотентність споживача**:
   Повторна доставка однієї й тієї самої події (`eventId`) не повинна викликати побічних ефектів окрім повторного виклику `Cache.delete(key)`, який у більшості сховищ є ідемпотентною операцією `O(1)`.

## 4. Специфікація Protobuf (gRPC) для подійної інвалідації

У високопродуктивних внутрішніх мережах замість JSON використовують типізовані контракти Protobuf v3.

```protobuf
syntax = "proto3";

package domain.cache.v1;

option go_package = "domain/cache/v1;cachev1";

enum InvalidationStrategy {
  INVALIDATION_STRATEGY_UNSPECIFIED = 0;
  INVALIDATION_STRATEGY_EXACT_KEY = 1;
  INVALIDATION_STRATEGY_PATTERN_PREFIX = 2;
  INVALIDATION_STRATEGY_TAG_BASED = 3;
}

message CacheInvalidationEvent {
  string event_id = 1;
  string aggregate_type = 2;
  string aggregate_id = 3;
  uint64 sequence_number = 4;
  int64 timestamp_epoch_ms = 5;
  InvalidationStrategy strategy = 6;
  repeated string target_keys = 7;
}

message InvalidationBatch {
  repeated CacheInvalidationEvent events = 1;
  string publisher_service_id = 2;
}

service CacheCoherenceService {
  rpc EvictKeys (InvalidationBatch) returns (EvictKeysResponse);
}

message EvictKeysResponse {
  uint32 evicted_count = 1;
  bool success = 2;
}
```

## 5. REST/gRPC API специфікація примусової інвалідації

Окрім асинхронних подій, сервіс-управління кешем повинен надавати адміністративний контракт примусового очищення кешу (Administrative Management Boundary).

### 5.1. Ендпойнти управління (REST OpenAPI)

#### POST `/api/v1/internal/cache/evict`
Примусове видалення конкретного ключа чи маски ключів.

- **Headers**:
  - `Content-Type: application/json`
  - `X-Correlation-ID: 9f8b7c6a-5e4d-3c2b-1a0f-9e8d7c6b5a4f`
  - `Authorization: Bearer <internal-service-token>`

- **Request Payload**:
```json
{
  "scope": "EXACT_KEY",
  "keys": ["user:profile:usr_42", "user:permissions:usr_42"],
  "reason": "ADMIN_PRIVILEGE_REVOCATION"
}
```

- **Response (200 OK)**:
```json
{
  "status": "SUCCESS",
  "evictedCount": 2,
  "executionTimeMs": 1.4
}
```

- **Response Error (400 Bad Request / 401 Unauthorized)**:
```json
{
  "type": "https://api.domain.internal/errors/invalid-cache-scope",
  "title": "Invalid Cache Eviction Scope",
  "status": 400,
  "detail": "Pattern prefix wildcard 'user:*' is forbidden for production evictions without tag scope.",
  "instance": "/api/v1/internal/cache/evict"
}
```

## 6. Заголовки трасування та скрізний контекст (Tracing Headers)

Для забезпечення спостережуваності інвалідації між розподіленими вузлами кожне мережеве повідомлення мусить містити заголовки стандарту W3C Trace Context:

- `traceparent`: `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01` — з'єднує транзакцію запису в БД з інвалідацією в Redis;
- `tracestate`: `vendor=invalidation-engine` — додаткові інфраструктурні мітки;
- `x-invalidation-origin`: `service-user-profile-prod-az1` — ідентифікатор пода або ноди, яка згенеструвала запит на очищення;
- `x-wal-lsn`: `0/16B3748` — позиція у журналі транзакцій (Log Sequence Number) для CDC-подій.

## 7. Реєстр крайових випадків та сценаріїв аварій

Нижче наведено каталог критичних збоїв при управлінні когерентністю кешу між сервісами та інженерні засоби їх нейтралізації.

| Сценарій збою | Механізм виникнення | Наслідок для системи | Інженерне рішення / Захист |
| :--- | :--- | :--- | :--- |
| **Зомбі-ключ після crash** | Сервіс виконав `DB.commit()`, але впав під час виклику `Redis.del(key)` | Кеш назавжди зберігає старе значення до вичерпання TTL | Використання Change Data Capture (Debezium) або Transactional Outbox |
| **Гонка Read-Miss / Write** | Читач при miss отримує `v1` з БД. Записувач оновлює БД до `v2` й робить `del()`. Читач пише `Set(v1)` | Кеш переписується застарілим значенням `v1` | Обов'язкове встановлення TTL на кожен ключ або перевірка CAS / Version guard |
| **Cache Stampede (Thundering Herd)** | Гарячий ключ інвалідується або тухне за TTL під високим RPS | Тисячі паралельних запитів пробивають кеш й валять первинну БД | Single-flight coalescing (Mutex lock на ключі) або Soft TTL (Stale-While-Revalidate) |
| **Out-of-Order Invalidation** | Подія інвалідації `v2` запізнилася в мережі й прийшла *після* події `v3` | Кеш інвалідує свіжий стан `v3` або відновлює застарілий `v2` | Монотонні номери версій (`sequenceNumber`) у ключах або порівняння LSN |
| **Розбухання паттернів (Pattern Eviction Load)** | Запитувач виконує `KEYS user:*` або `DEL` за маскою у великому Redis | Блокування єдиного потоку Redis на секунди, відмова сервісів | Використання індексації за тегами (Redis Sets / Hashes) або безблокового `SCAN` + `UNLINK` |
