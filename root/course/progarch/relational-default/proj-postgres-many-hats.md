# ⚙️ Один Postgres у пʼятьох капелюхах: живий SQL для Digital Homes

Інстинкт розкидати пʼять форм даних по пʼятьох сховищах звучить переконливо рівно доти, доки не спробуєш зробити навпаки — покласти всі пʼять в **одну** нудну базу й подивитися, де саме вона тріщить. Не на пальцях, не «Postgres же універсальний», а живим SQL: ось таблиця, ось індекс, ось запит, ось число. Візьмімо Digital Homes — систему, що керує тисячами домів і десятками тисяч пристроїв, — і вдягнімо на один PostgreSQL усі пʼять капелюхів, які інстинкт роздав би окремим двигунам. А наприкінці намалюймо чесну межу: не «Postgres усе може», а точно ті профілі й масштаби, за якими він справді перестає бути достатнім.

## Задача: пʼять форм даних під одним дахом

Випишемо потреби DH так, як їх принесли б на дизайн-ревʼю, — і поряд той рефлекс, що під кожну хапає окреме сховище.

- **Реєстр домів і пристроїв.** Хто де стоїть, який пристрій якому дому належить, хто власник. Класична реляція зі звʼязками. *Рефлекс: та це ж очевидно Postgres.*
- **Конфіг пристрою різної форми.** Термостат зберігає цільову температуру й розклад; замок — затримку автоблокування й слоти пін-кодів; камера — роздільність і зони руху. Форми несумісні. *Рефлекс: гнучкі документи — берімо MongoDB.*
- **Пошук по журналу подій людською мовою.** Господар хоче спитати «коли востаннє відчиняли гараж» і дістати відповідь із тисяч записів активності. *Рефлекс: повнотекстовий пошук — це Elasticsearch.*
- **Черга команд до пристроїв.** Хмара кладе в чергу «замкни двері», «постав 21°», а пул воркерів розбирає й відправляє. Кілька воркерів мусять тягти паралельно, не наступаючи одне одному на пʼяти. *Рефлекс: черга — це RabbitMQ чи Kafka.*
- **Телеметрія.** Кожен пристрій шле показники раз на кілька хвилин; це часоряд, що росте вічно. *Рефлекс: часоряд — це InfluxDB чи Cassandra.*

Пʼять рефлексів — пʼять сховищ, кожне «найкраще у своєму класі». Наша задача — зробити ту саму роботу **одним** Postgres, кожен капелюх окремим шматком робочого SQL, і чесно позначити, де ця економія вичерпується.

## Ідея: виграш операційний, а не магічний

Перш ніж писати схему, домовмося, у чому саме виграш, — бо легко пообіцяти забагато. Один Postgres **не** робить SQL магічним ключем до будь-якої форми даних. Кожен капелюх усе одно потребує свого індексу, свого оператора, свого профілю доступу; дисципліна нікуди не зникає. Виграш деінде — він **операційний**. Пʼять сховищ — це пʼять бекапів, пʼять моделей відмови, пʼять наборів знань у голові чергового о третій ночі, пʼять місць, де щось піде не так. Один — це одне з усього цього. А ще це **безкоштовні звʼязки між капелюхами**: команда посилається на пристрій, пристрій — на дім, подія — на пристрій, і все це в одній транзакції, під одним зовнішнім ключем, без жодного двофазного танцю між системами. Дані, що лежать поряд, зшиваються `JOIN`-ом; дані, розкидані по пʼятьох двигунах, зшиваються кодом застосунку, який ти пишеш і супроводжуєш сам.

Ось уся схема з висоти пташиного лету — пʼять капелюхів на одному рушії, кожен зі своїм механізмом.

*Пʼять форм даних, один рушій. Кожен капелюх — своя таблиця чи колонка й свій механізм доступу; спільне — одна межа відмови, один бекап, один `JOIN` через усі пʼять.*

Тепер по капелюхах, кожен — робочим SQL на PostgreSQL 17.

## Капелюх 1 — реляційне ядро із зовнішніми ключами

Почнімо з того, де реляційне вдома, — реєстр. Два звʼязані [відношення](topic:sf-data/relational-model): доми й пристрої, і **зовнішній ключ**, що тримає їхній звʼязок.

```sql
CREATE TABLE homes (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text        NOT NULL,
    tz         text        NOT NULL DEFAULT 'Europe/Kyiv',
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE devices (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    home_id      bigint NOT NULL REFERENCES homes(id) ON DELETE CASCADE,
    kind         text   NOT NULL CHECK (kind IN ('thermostat','lock','camera','sensor')),
    serial       text   NOT NULL UNIQUE,
    installed_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ON devices (home_id);   -- під запит «усі пристрої цього дому»
```

Один рядок, `home_id bigint NOT NULL REFERENCES homes(id)`, робить те, чого твій код не мусить робити сам: жоден пристрій не може вказувати на неіснуючий дім — база просто відмовить у вставці. А `ON DELETE CASCADE` каже, що зі знесенням дому підуть і його пристрої, без осиротілих рядків. Це **інваріант, який боронить сховище на найнижчому шарі**, куди не дотягнеться жоден баг застосунку. Запит через звʼязок — звична річ:

```sql
-- усі замки дому 42
SELECT d.serial
  FROM devices d
  JOIN homes h ON h.id = d.home_id
 WHERE h.id = 42 AND d.kind = 'lock';
```

Це найнудніший капелюх, і тому найнадійніший. Усе цікаве починається, коли форма даних перестає бути прямокутною.

## Капелюх 2 — колонка jsonb як документ

Конфіг пристрою — саме така форма. Термостат, замок і камера зберігають геть різні поля, і майбутні пристрої принесуть іще нові. Три звичні виходи тут погані. **Таблиця на кожен вид** — це `JOIN`-пекло й жорсткість: новий вид пристрою = зміна схеми. **Широка розріджена таблиця** — пʼятдесят колонок, з яких на кожен рядок заповнено пʼять, решта `NULL`. **EAV** (сутність-атрибут-значення) — класичний антипатерн, де одна таблиця з парами «ключ-значення» ховає структуру від бази й від тебе. PostgreSQL дає четвертий вихід: колонка `jsonb` — один стовпець, будь-яка форма.

```sql
ALTER TABLE devices ADD COLUMN config jsonb NOT NULL DEFAULT '{}';

UPDATE devices SET config = '{"target_c": 21.5, "mode": "auto", "fw": "2.3.1"}'
 WHERE id = 1;   -- термостат
UPDATE devices SET config = '{"auto_lock": true, "delay_s": 30, "fw": "1.9.0"}'
 WHERE id = 2;   -- замок

-- GIN — інвертований індекс: розкладає документ на ключі й значення
CREATE INDEX devices_config_gin ON devices USING gin (config);
```

`jsonb` (на відміну від текстового `json`) зберігає розібране двійкове дерево, тож база може дивитися **всередину** документа й індексувати його вміст. Тип зʼявився у PostgreSQL 9.4 (2014) саме для цього — гнучкість документа при індексованій швидкості доступу. Запит «усі пристрої з увімкненим автоблоком» — оператор **вкладення** `@>` («документ містить оцей фрагмент»), який GIN пришвидшує:

```sql
SELECT id, serial
  FROM devices
 WHERE config @> '{"auto_lock": true}';   -- йде через GIN
```

Дістати конкретне поле — оператори шляху `->` (повертає `jsonb`) і `->>` (повертає `text`):

```sql
-- замки з автоблоком, де затримка довша за 20 секунд
SELECT id, config->>'fw' AS firmware
  FROM devices
 WHERE kind = 'lock'
   AND config @> '{"auto_lock": true}'          -- індексований відбір
   AND (config->>'delay_s')::int > 20;          -- добірка вже на кандидатах
```

Тут варто знати одну розвилку індексу. Стандартний клас операторів `jsonb_ops` кладе в GIN і ключі, і значення, тож тримає широкий набір операторів (`@>`, `?`, `?|`, `?&`). Менший `jsonb_path_ops` індексує лише значення (як хеш шляху до них) — індекс виходить помітно компактніший і на запитах-вкладеннях точніший, але вміє тільки `@>`. Обираєш за тим, чи потрібні тобі перевірки наявності ключа, чи самі лише вкладення.

> 🔧 **Навіщо це.** `jsonb` спокушає скласти в нього **все** — і ось тут ховається пастка. Щойно якесь поле стає **гарячим**: за ним постійно фільтрують, сортують, зʼєднують, — воно проситься назад у справжню колонку. `fw` у прикладі — саме такий кандидат: якщо звіти щодня рахують пристрої за версією прошивки, розумніше винести його в окрему колонку (звичайну або **згенеровану**) з `btree`-індексом, а в `jsonb` лишити те, що справді довільне. Документ — для форми, якої ти не знаєш наперед; не для полів, за якими живеш щодня.

## Капелюх 3 — повнотекстовий пошук через tsvector

Господар DH не пише SQL — він хоче спитати «гараж» і дістати все про гараж із журналу подій. Це третій капелюх: повнотекстовий пошук, вбудований у ядро Postgres ще з версії 8.3 (2008), коли машинерію `tsvector`/`tsquery` — а разом і самі GIN-індекси — принесли в базу розробники Олег Бартунов і Теодор Сигаєв.

Ідея пошуку — не шукати підрядок (`LIKE '%гараж%'` повільний і дурний), а звести і документ, і запит до **лексем** — нормалізованих слів — і звіряти вже їх. Документ стає значенням типу `tsvector`; від Postgres 12 його можна тримати **згенерованою колонкою**, яку база рахує сама при кожному записі:

```sql
CREATE TABLE events (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    home_id   bigint NOT NULL REFERENCES homes(id) ON DELETE CASCADE,
    device_id bigint REFERENCES devices(id) ON DELETE SET NULL,
    at        timestamptz NOT NULL DEFAULT now(),
    message   text NOT NULL,
    -- база сама рахує tsvector при вставці/оновленні (Postgres 12+)
    tsv tsvector GENERATED ALWAYS AS (to_tsvector('simple', message)) STORED
);

CREATE INDEX events_tsv_gin ON events USING gin (tsv);
```

```sql
INSERT INTO events (home_id, device_id, message) VALUES
  (42, 2, 'Гараж відчинено гостьовим кодом'),
  (42, 1, 'Термостат перейшов у нічний режим'),
  (42, 2, 'Двері гаража замкнено вручну');
```

Тепер запит господаря. `websearch_to_tsquery` (від Postgres 11) розбирає людський рядок у `tsquery`, а оператор `@@` звіряє його з `tsvector`:

```sql
SELECT at, message
  FROM events
 WHERE tsv @@ websearch_to_tsquery('simple', 'гараж')
 ORDER BY at DESC
 LIMIT 20;
```

Знайдуться обидва записи про гараж, повз термостат. А якщо результатів багато, їх ранжирують за релевантністю — `ts_rank` дає вагу збігу:

```sql
SELECT message, ts_rank(tsv, q) AS rank
  FROM events, websearch_to_tsquery('simple', 'гараж двері') q
 WHERE tsv @@ q
 ORDER BY rank DESC
 LIMIT 10;
```

Одне зауваження чесності. Ми взяли конфігурацію `'simple'` — вона лише ріже текст на токени й опускає регістр, без мовного морфологічного згортання (стемінгу). Для української це свідомий безпечний вибір: у стандартній поставці Postgres роками не було українського стемера, тож `'simple'` не «розумний», зате й не бреше несподіваним згортанням. Хочеш, щоб «відчинено» й «відчиняли» злипались в одну лексему, — треба підключати відповідний словник і, як правило, `unaccent`. Але навіть «наївний» повнотекстовий на GIN — це вже не `LIKE '%...%'`, а індексований пошук по лексемах, і для журналу подій DH його вистачає з головою.

## Капелюх 4 — черга задач: FOR UPDATE SKIP LOCKED

Четвертий капелюх — той, що найбільше дивує людей, певних, ніби черга конче потребує брокера. Хмара кладе команди в таблицю; пул воркерів їх розбирає. Уся хитрість — щоб **кілька воркерів тягли паралельно**, кожен свою задачу, і жоден не блокувався на чужій.

```sql
CREATE TABLE commands (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_id  bigint NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    kind       text   NOT NULL,                 -- 'lock','unlock','set_temp'…
    payload    jsonb  NOT NULL DEFAULT '{}',
    status     text   NOT NULL DEFAULT 'ready'
                      CHECK (status IN ('ready','done','failed')),
    created_at timestamptz NOT NULL DEFAULT now()
);

-- ЧАСТКОВИЙ індекс: тільки готові рядки, тож скан лишається дешевим,
-- скільки б «done» не накопичилось у хвості
CREATE INDEX commands_ready ON commands (created_at) WHERE status = 'ready';
```

Серце черги — один запит, який кожен воркер виконує у **своїй** транзакції:

```sql
BEGIN;
  SELECT id, device_id, kind, payload
    FROM commands
   WHERE status = 'ready'
   ORDER BY created_at            -- FIFO: найстаріша готова першою
   FOR UPDATE SKIP LOCKED         -- зайняті рядки ПРОПУСКАЄМО, а не чекаємо
   LIMIT 1;
  -- ...відправити команду пристрою (швидко)...
  UPDATE commands SET status = 'done' WHERE id = :id;
COMMIT;
```

Розберімо чотири слова, у яких уся суть. `FOR UPDATE` бере **рядковий замок** на вибраний рядок — поки транзакція жива, ніхто інший його не змінить. Саме собою це дало б чергу, але повільну: другий воркер, наткнувшись на замкнений рядок, **став би й чекав**. `SKIP LOCKED` (додане у PostgreSQL 9.5, 2016, Томасом Манро саме для черг) міняє це докорінно: замість чекати, воркер **перескакує** замкнений рядок і бере наступний готовий. `ORDER BY created_at` тримає порядок FIFO, `LIMIT 1` — по одній задачі за раз. І ось десять воркерів, запустивши цей самий запит в одну мить, розберуть десять **різних** задач без жодної домовленості між собою й без єдиної секунди блокування. Частковий індекс `WHERE status = 'ready'` тримає скан миттєвим, навіть коли «done» назбираються мільйонами в хвості.

![Ліворуч три коробки-воркери (A, B, C), кожен зі своїм зʼєднанням. Праворуч вертикальний стос із шести рядків таблиці commands: #1..#6 зі статусами. Від воркера A суцільна зелена стрілка до рядка #1 (позначено «🔒 взято A»); від воркера B пунктирна червона стрілочка спершу тицяється в #1 із підписом «зайнято → пропускаю», а тоді суцільна зелена до #2 («🔒 взято B»); від воркера C суцільна зелена до #3 («🔒 взято C»). Рядки #4, #5, #6 світлі, з підписом «готові — наступним воркерам». Унизу банер: «три воркери · три різні задачі · нуль блокувань»](img/skip-locked-workers.svg)
*`SKIP LOCKED` перетворює звичайний рядковий замок на чергу без черги на замках: кожен воркер пропускає зайняте й бере наступне готове. Десять воркерів — десять різних задач, нуль блокувань.*

> 🔧 **Навіщо це.** Замок живе до `COMMIT` — і в цьому головна пастка черги на базі. Якщо тримати рядок замкненим **упродовж повільної відправки** команди пристрою (мережа, таймаути, ретраї), один застряглий воркер підвісить рядок надовго, а впав він — рядок висітиме до кінця його транзакції. Тому дисципліна така: **взяв — познач і швидко закоміть**, а повільну роботу роби вже поза замком. Практичний патерн — `UPDATE ... SET status = 'processing'`, `COMMIT`, тоді відправка, тоді фінальний `done`; а щоб підняти задачі загиблих воркерів, додають колонку часу-початку й «час видимості», за яким «зависле» повертається в `ready`. Ідея та сама, що в сусідньому кроці про [перегони на останній квиток](root:progarch/last-ticket-race): рішення про рядок ухвалює [транзакція сховища](topic:sf-data/transactions-acid), а не сподівання застосунку.

## Капелюх 5 — часоряд телеметрії

Пʼятий капелюх — той, задля якого найчастіше заводять окрему базу. Телеметрія росте вічно, і саме тому її треба вміти не лише **писати** й **читати за пристроєм і часом**, а й **викидати старе** дешево. PostgreSQL складає це трьома звичними деталями: секціювання за діапазоном часу, складений індекс під головний запит і політика зберігання через відкидання цілих секцій.

```sql
CREATE TABLE telemetry (
    device_id bigint      NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    ts        timestamptz NOT NULL,
    metric    text        NOT NULL,          -- 'temp_c','motion','lock_state'
    value     double precision NOT NULL
) PARTITION BY RANGE (ts);                   -- секціювання за часом (Postgres 10+)

-- місячні секції: свіже окремо, старе — цілим шматком під відкидання
CREATE TABLE telemetry_2026_07 PARTITION OF telemetry
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
CREATE TABLE telemetry_2026_08 PARTITION OF telemetry
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

-- індекс під головний запит «цей пристрій за цей проміжок»;
-- створений на батьківській таблиці, він лягає на кожну секцію
CREATE INDEX ON telemetry (device_id, ts DESC);
```

**Декларативне секціювання** (PostgreSQL 10, 2017) розбиває одну логічну таблицю на фізичні шматки за діапазоном `ts`. Головний запит DH — «покажи цей пристрій за цю добу» — бʼє рівно в один місяць і йде складеним індексом `(device_id, ts)`:

```sql
SELECT ts, metric, value
  FROM telemetry
 WHERE device_id = 42
   AND ts >= '2026-07-11' AND ts < '2026-07-12'
 ORDER BY ts;
```

Планувальник відсікає (pruning) усі секції, крім липневої, а всередині неї йде індексом просто до потрібного пристрою й діапазону. А ось де секціювання окупається двічі — **політика зберігання**. Тримати сире 90 днів, старше — геть. Наївно це `DELETE ... WHERE ts < ...` — а він роздуває таблицю мертвими рядками й вантажить `autovacuum`. Із секціями старе відкидається **однією миттєвою операцією**, що одразу повертає диск:

```sql
-- зберігаємо 90 днів: квітнева секція застара — геть, миттєво й без роздування
DROP TABLE telemetry_2026_04;
```

І тут-таки — [прикидка на серветці](topic:sf-apps/back-of-envelope), яка й вирішує, чи це взагалі задача для окремої бази. Пілот DH: 40 000 пристроїв, запис раз на 5 хвилин — це ≈133 рядки/с, ≈11.5 млн рядків/добу, ≈17 ГБ/місяць сирих. 133 рядки на секунду — кілька відсотків того, що спокійно тримає один вузол Postgres. Часоряд DH живе в тій самій базі, що й реєстр, — під одним бекапом, з можливістю `JOIN`-нути телеметрію на `devices` і `homes` однією фразою.

## Складність і пастки

Кожен капелюх сидить добре рівно доти, доки памʼятаєш його гострі краї. Ось найгостріші.

**`jsonb` не безкоштовний.** Оновлення одного поля переписує **весь** документ — Postgres не міняє `jsonb` частково на місці; для великих документів із частими дрібними правками це помітна ціна. GIN-індекс пришвидшує читання, але додає роботи на кожен запис і сам може роздуватися. І база не вміє легко тримати інваріанти **між** документами так, як тримає зовнішній ключ між таблицями. Висновок той самий: у `jsonb` — довільне, у колонки — гаряче.

**Черга живе на дисципліні транзакції.** Крім «взяв — швидко закоміть» (вище), стеж за роздуванням: черга — це стіл, де рядки народжуються й помирають лавинами, тож `autovacuum` мусить встигати прибирати за `done`, інакше таблиця розпухне, а частковий індекс — за нею. Без `ORDER BY` порядок вибірки не визначений (не FIFO); без `LIMIT` воркер спробує замкнути забагато. І памʼятай стелю `max_connections`: кожен воркер — це зʼєднання.

**Повнотекстовий — не Google.** `ts_rank` — проста вагова функція, не BM25; вбудований пошук не має вродженої стійкості до друкарських помилок і нечіткого збігу; вибір конфігурації (`'simple'` проти мовного словника) міняє результат докорінно. Згенерована колонка проти тригера, GIN проти GiST, `unaccent` для нечутливості до наголосів — усе це рішення, які треба ухвалити свідомо, а не за замовчуванням.

**Часоряд вимагає догляду за секціями.** Найпідступніше: вставка в діапазон, для якого секції **немає**, **падає** помилкою. Отже, майбутні секції треба створювати наперед — розширенням `pg_partman`, плановим завданням або секцією `DEFAULT` як запобіжником. На величезних, тільки-на-додавання таблицях розглянь `BRIN`-індекс замість `btree` — він крихітний і чудово лягає на дані, впорядковані за часом самим порядком вставки.

**Пʼять капелюхів — це не одна таблиця й не відсутність дисципліни.** Найбільша пастка — концептуальна: вирішити, що «все в Postgres» означає «все в одну таблицю» або «схема сама якось складеться». Ні. Кожен капелюх — це своя таблиця, свій індекс, свій оператор, свій профіль доступу. Виграш — не в тому, що SQL чарівно вмістив усе, а в тому, що ти тримаєш **одну** систему, а не пʼять. Дисципліну проєктування ніхто не скасовував — її просто не треба множити на пʼять.

## Чесна межа: де Postgres перестає бути достатнім

А тепер обіцяна чесність. Кожен капелюх має масштаб і профіль, за яким нудна база справді програє спеціалістові, — і межу цю креслять **виміром**, а не страхом.

![Таблиця з пʼяти рядків, кожен — один капелюх і його межа. Три колонки: капелюх · «поки достатньо Postgres» (зелена клітина з порогом) · стрілка · «далі — спеціаліст» (червона клітина). Рядки: часоряд — до ~10⁴–10⁵ рядків/с сталого запису або TB гарячих — TimescaleDB / колонкове; черга — до тисяч задач/с, короткі транзакції — Kafka / RabbitMQ (величезний backlog, строгий порядок, фан-аут); пошук — базова релевантність — Elasticsearch (BM25, друкарські помилки, фасети); документ — помірні документи — документна БД (величезні документи, горизонтальний шардинг); кеш/сесії — епізодично — Redis (суб-мс, ефемерне, гарячий ключ). Унизу банер: «спершу — розширення того самого Postgres: Citus · TimescaleDB · pgvector · pg_partman»](img/where-postgres-ends.svg)
*Кожен капелюх має свій поріг. Зелене — де один Postgres достатній; червоне — профіль, за яким спеціаліст справді виграє. Порогом слугує виміряне число, а першим кроком за ним — часто розширення того самого Postgres, а не ще одне сховище на окреме чергування.*

- **Часоряд.** Один вузол тягне десятки тисяч вставок на секунду; коли сталий потік телеметрії підповзає до сотень тисяч рядків/с або гарячі дані перестають уміщатися в памʼять, час на розширення на кшталт TimescaleDB, а для важкої аналітики — на колонкове сховище (ClickHouse, DuckDB): рядковий рушій із `btree` — не та форма для сканів по мільярдах рядків.
- **Черга.** `SKIP LOCKED` чудова до тисяч задач на секунду за коротких транзакцій. Величезний backlog, строгий наскрізний порядок, широкий фан-аут на багато незалежних споживачів, потокова обробка — це вже територія Kafka чи RabbitMQ, де ці властивості вроджені.
- **Пошук.** Вбудований повнотекстовий добрий для базової релевантності на помірному корпусі. Потрібні BM25-ранжирування, стійкість до помилок, фасети, підказки на льоту, мільйони документів під складні запити — Elasticsearch чи OpenSearch зроблені саме для цього.
- **Документ.** `jsonb` покриває гнучкі конфіги досконало. Але якщо документи стають величезними, а модель вимагає горизонтального шардингу «документ як одиниця масштабу» — спеціалізована документна база на своєму місці.
- **Кеш і сесії.** Навіть з `UNLOGGED`-таблицями Postgres несе накладні витрати транзакцій і зʼєднань. Суб-мілісекундний, ефемерний, гарячий доступ ключ-значення — робота для Redis.

Спільна нитка проста і її варто вимовити вголос. По-перше, кожен із цих переходів — [свідоме відхилення від дефолту](topic:sf-data/polyglot-persistence), яке ухвалюють за [виміряним сценарієм із числом](topic:sf-apps/attribute-scenarios), а не за слоганом. По-друге — і це найчастіше проґавлюють — **першим** кроком за межу часто буде розширення **того самого** Postgres: `Citus` шардить його на кластер, `TimescaleDB` дотягує часоряд, `pgvector` додає векторний пошук схожості, `pg_partman` автоматизує секції. Шосте окреме сховище з власним чергуванням заводять аж тоді, коли й розширення вперлося в стіну.

## Що лишається в руках

Ми вдягли на один PostgreSQL пʼять капелюхів, які інстинкт роздав би пʼятьом двигунам, — і кожен виявився не натяжкою, а робочим SQL: зовнішній ключ тримає реєстр, `jsonb` із GIN тримає документи, `tsvector` — пошук, `FOR UPDATE SKIP LOCKED` — чергу воркерів без блокувань, секційований часоряд — телеметрію з миттєвим відкиданням старого. Жоден капелюх не магія: кожен потребує свого індексу й своєї дисципліни. Магія в іншому — в **одній** межі відмови замість пʼятьох, в одному бекапі, в `JOIN`-і, що зшиває всі пʼять форм однією фразою.

І межа, де це вичерпується, тепер не здогад, а карта: пʼять порогів, кожен — виміряне число, за яким спеціаліст справді виграє, і за яким першим кроком стоїть радше розширення того самого Postgres, ніж нове сховище. Це і є практичний зміст «нудного за замовчуванням»: не «Postgres усе», а «Postgres, поки виміряний сценарій не покаже інакше, — і навіть тоді спершу глянь, чи не закриває цей випадок розширення тієї самої нудної бази».
