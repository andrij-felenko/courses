- [Еволюція API](root:progarch/api-evolution-dh) — поблажливий читач та адитивність контракту.
</preknowlist>

Команда сервісу білінгу оновлює схему рахунка-фактури: додає поле податкового ідентифікатора покупця й робить його обов'язковим для нових квитанцій. Якщо сервіс замовлень викликає білінг через синхронний gRPC, викатка нового білінгу миттєво блокує реліз сервісу замовлень: будь-який запит зі старою формою DTO повертає `400 Bad Request` або `INVALID_ARGUMENT`, зупиняючи оформлення покупок доти, доки обидва сервіси не синхронізують свої деплої. Одне обов'язкове поле в синхронному контракті перетворює дві незалежні команди на одну повільну зграю.

Ця проблема виникає не через недбалість розробників і не через погану мову програмування. Вона народжується в мить, коли архітектор обирає **тип зв'язку між сервісами**, не враховуючи його впливу на **незалежність розгортання змін** (release coupling). Прямий мережевий виклик прокладає не лише канал для байтів — він прокладає часову й структурну нитку, яка зв'язує долі двох сервісів під час кожного деплою, відкату чи аварії.

У цьому кроці ми розберемо, як вибір між синхронним REST/gRPC та асинхронними подіями визначає автономію продуктових команд, що відбувається зі схемами даних при викачуванні нових фіч та як побудувати компактну матрицю прийняття рішень для вибору типу зв'язку під час релізів.

## 1. Анатомія зчеплення при зміні: чому релізи втрачають незалежність

У програмуванні поняття «зчеплення» (coupling) часто вживають як загальну лайку. Проте для розгортання змін важить критичне розрізнення між двома принципово різними видами зчеплення: **зчепленням виконання** (runtime execution coupling) та **зчепленням розгортання** (deployment / release coupling).

Зчеплення виконання показує, чи потрібна сервісу B працездатність сервісу A в ту саму мілісекунду, коли сервіс A обробляє запит користувача. Зчеплення розгортання показує дещо глибше: чи може команда сервісу A розгорнути нову версію свого коду у середу о 14:00, якщо команда сервісу B перебуває у відпустці й не планує жодних оновлень до наступного місяця.

```
                  +-------------------------------------------------+
                  |            Типи зчеплення при змінах            |
                  +-------------------------------------------------+
                                    /             \
                                   /               \
         +-------------------------------+   +-------------------------------+
         |     Часове зчеплення (Time)   |   |   Схематичне зчеплення (Data) |
         |   Замовник чекає відповіді    |   |   Поля та типи мають бути    |
         |   в одну й ту саму секунду    |   |    сумісними в мить виклику   |
         +-------------------------------+   +-------------------------------+
                                   \               /
                                    \             /
                  +-------------------------------------------------+
                  |      ЗЧЕПЛЕННЯ РЕЛІЗІВ (Lockstep Deployment)    |
                  |     Команди не можуть розгортатися окремо       |
                  +-------------------------------------------------+
```

Коли сервіс A викликає сервіс B через синхронний HTTP REST або gRPC, між ними миттєво виникають три фундаментальні зв'язкові лінії:

1. **Часова прив'язка (Temporal Binding)**: Запит блокує виконання A до завершення обробки в B. Якщо B перезапускається після деплою нових контейнерів, A отримує мережеві помилки `503 Service Unavailable` або `Connection Refused`.
2. **Структурна прив'язка (Structural Binding)**: Байти, відправлені A, мусять точно збігатися зі схемою, на яку очікує B у момент розкочування. (наприклад, `int32` → `string`) або додавання обов'язкового поля вимагають дзеркальних змін з обох боків.
3. **Операційна прив'язка (Operational Binding)**: Помилка у новій версії коду B миттєво просочується в A у вигляді зростання затримки (latency spikes) або вичерпання пулу потоків.

### Радіус вибуху та каскадне навантаження
При синхронній взаємодії затримки обчислюються сумарно. Якщо клієнтський запит викликає Сервіс A, який синхронно опитує B, C та D, загальний час відповіді T_total становить:

```
T_total = T_A + T_B + T_C + T_D + T_network_sum
```

Якщо під час розгортання оновлення у Сервісі C його затримка зростає з 10 мс до 2000 мс через перезбірку кешу, потоки виконання у Сервісах A та B виявляються заблокованими в очікуванні відповіді. Пул з'єднань (Connection Pool) вичерпується за лічені секунди. Результатом є каскадна відмова системи, де невелике оновлення одного допоміжного сервісу паралізує весь фронтальний трафік.

### Ілюзія захисту за допомогою Запобіжників (Circuit Breakers)
Поширеною оманою є віра в те, що додавання інструментів Resilience4j, Hystrix або Envoy Circuit Breaking повністю вирішує проблему синхронного зчеплення при розгортанні змін.

Запобіжник справді рятує систему від повного вичерпання потоків: коли Сервіс B починає повертати 500-ті помилки або тупити, запобіжник розмикає ланцюг (Open State) і миттєво відхиляє наступні виклики без очікування тайм-ауту. Однак запобіжник **не поповнює втрачену бізнес-функціональність**. Якщо Сервіс A вимагає даних від Сервісу B для завершення транзакції замовлення, відкритий запобіжник означає, що замовлення не буде створене. Запобіжник перетворює повільне каскадне падіння на швидке відхилення, але він **не відновлює незалежність релізів**.

Якщо для виконання зміни в сервісі A ви змушені одночасно розгортати сервіс B, ви побудували **розподілений моноліт** (Distributed Monolith). Ви вже платите мережевим накладним часом, складністю розподіленого трейсингу та ризиками каскадних відмов, але втратили головну обіцянку мікросервісної архітектури — автономію незалежних команд.

Детальний аналіз того, як корпоративна індустрія 2000-х років зіштовхнулася з цією пасткою під час переходу від монолітів до перших веб-сервісів, описано в [історичному екскурсі про lockstep-релізи](root:progarch/change-coupling-choice/hist-lockstep-deployments.md).

## 2. Синхронний зв'язок (REST / gRPC): ціна й сили синхронної зміни

Синхронний зв'язок — це стандарт за замовчуванням для більшості веб-розробників. HTTP REST із JSON або gRPC із Protobuf пропонують надзвичайно просту ментальну модель: ви викликаєте віддалену функцію так само, як викликали б локальний метод класу, і негайно отримуєте результат або виняток.

### 2.1. Чому синхронний зв'язок залишається привабливим
Причиною популярності REST та gRPC є не неуважність до релізів, а суворі бізнес-вимоги, які важко або дорого реалізувати інакше:

- **Миттєве підтвердження команд (Read-Your-Writes)**: Користувач тисне кнопку «Сплатити замовлення». Застосунок має негайно повідомити: транзакцію прийнято, банк підтвердив списання, ID чек-ауту — `PAY-123`.
- **Строгі гарантії консистентності**: Перевірка залишків дорогоцінного товару на складі під час спалах-розпродажу (Flash Sale). Сервіс складського обліку має атомарно заблокувати одиницю товару в мить запиту.
- **Простота відлагодження**: Наскрізний HTTP-запит проходить крізь системи з єдиним заголовком `X-Request-ID`. Стек викликів зрозумілий, а трасування в інструментах на зразок Jaeger чи Zipkin малюється суцільним деревоподібним графом.

### 2.2. Як синхронний зв'язок ламає незалежність релізів
Ціною цих зручностей є вразливість до змін. Припустимо, сервіс авторизації оновлює формат токена доступу. Якщо він робить це через синхронний gRPC-контракт, будь-яка з наступних трьох змін у схемі розриває релізну незалежність:

- **Видалення чи перейменування поля**: Поле `user_name` перейменовано на `full_name`. Старі клієнти перестають бачити ім'я.
- **Зміна обов'язковості поля**: Необов'язкове поле `phone_number` стало обов'язковим у новій версії валідатора. Запити від старих клієнтів відхиляються з кодом `400`.
- **Зміна семантики відповіді**: Код помилки `404 Not Found` (користувача не знайдено) замінено на `404` (акаунт заблоковано). Клієнти, які мали `switch(code)`, починають обробляти відмову за хибною гілкою.

```
       Версія 1 (Початковий стан)                  Версія 2 (Ламаюча зміна в Б)
       
   +----------+          +----------+         +----------+          +----------+
   | Сервіс А | --REST-> | Сервіс Б |         | Сервіс А | --REST-> | Сервіс Б |
   |   (v1)   |  JSON v1 |   (v1)   |         |   (v1)   |  JSON v1 |   (v2)   |
   +----------+          +----------+         +----------+          +----------+
        |                     |                    |                     |
        +-- Успіх (200 OK) ---+                    +-- ❌ 400 Bad Request-+
                                                       (Обов'язкове поле!)
```

### 2.3. Повна деталізація тактики Expand-Contract у синхронному контурі
Щоб реалізувати несумісну зміну в синхронному API без зупинки продакшену, команда змушена проводити тривалу 4-фазну міграційну кампанію:

1. **Фаза 0 (Базовий стан)**: Продюсер віддає лише старе поле `user_name`.
2. **Фаза 1 (Expand — Розширення)**: Продюсер викочує версію коду, яка приймає та повертає **обидва поля** (`user_name` та `full_name`). Нове поле робиться optional. Продюсер виконує внутрішній подвійний запис.
3. **Фаза 2 (Migrate — Перехід споживачів)**: Споживачі у власному темпі протягом днів чи тижнів оновлюються, переходячи на читання `full_name`. За допомогою систем спостережності фіксується лічильник звернень до застарілого поля `user_name`.
4. **Фаза 3 (Contract — Звуження)**: Лише коли лічильник звернень до `user_name` досягає нульової позначки в усіх когортах трафіку, продюсер випускає реліз, який остаточно видаляє старе поле з коду.

Ця процедура гарантує безпеку релізів, проте її ціна висока: код змушений місяцями нести застарілі атрибути та містити подвійну логіку трансформації.

### 2.4. Версіонування REST/gRPC за допомогою Media Types (Header Versioning)
Замість внесення номерів версій у шлях URL (наприклад, `/api/v1/orders` → `/api/v2/orders`), що розмножує нові ендпойнти у коді контролерів та змушує клієнтів змінювати базові URI, застосовують версіонування через **Media Types (Content Negotiation)**.

Клієнт передає заголовок HTTP:
`Accept: application/vnd.company.order.v2+json`

Серверний API Gateway розпізнає версію контракту на рівні заголовків і перераховує об'єкт через відповідний трансформатор DTO. Це дозволяє зберігати єдину адресну структуру ресурсів URL, реалізуючи підтримку старих клієнтів ізольованими адаптерами на краю системи.

### 2.5. Канаркові релізи (Canary Deployments) та ротація подів
При здійсненні розгортання нових версій синхронних сервісів часто використовують **канарковий деплой** (Canary Deployment), коли лише 5% трафіку перенаправляється на під `v2` за допомогою Service Mesh (Envoy, Istio, Linkerd).

Проте якщо зміна API між v1 та v2 є ламаючою (non-backward compatible), канарковий деплой перетворюється на пастку: 5% користувачів починають бачити регулярні помилки `400 Bad Request` або `500 Internal Server Error`, у той час як решта 95% трафіку працює справно. Це ускладнює автоматичне визначення збоїв метриками загальної доступності (Error Rate Thresholds) і вимагає розділення моніторингу за тегами версій подов у Prometheus.

### 2.6. Контрактне тестування (Consumer-Driven Contract Testing)
Для зниження ризиків синхронних змін у CI/CD застосовують **Consumer-Driven Contract Testing** (наприклад, фреймворк Pact або Spring Cloud Contract).

Замість того щоб під час деплою сподіватися, що Сервіс B зрозуміє новий REST-запит від Сервісу A, команда Сервісу A створює файли контракту (Pact Files), які описують очікувані структури запитів та відповідей. Ці контракти публікуються у центральний реєстр (Pact Broker).

Під час збірки Сервісу B у його CI-конвеєрі автоматично проганяються мок-тести проти всіх зареєстрованих контрактів усіх споживачів. Якщо Сервіс B намагається викачати несумісну зміну, CI-пайплайн Сервісу B виявляє це ще до деплою в тестове середовище. Це дозволяє вчасно зупинити шкідливу зміну, хоча й не знімає потреби в Expand-Contract.

## 3. Асинхронний подійний зв'язок (Pub/Sub / CDC / Outbox): розрив часової нитки

Якщо синхронний виклик — це прохання «Зроби це зараз і дай відповідь», то асинхронна подія — це оголошення факту: «Це вже сталося в моєму домені, робіть із цим що хочете».

### 3.1. Чому Події розривають часову залежність
Головний архітектурний секрет асинхронних систем полягає в різниці між **асинхронними командами** та **доменними подіями**. 

Якщо сервіс замовлень відправляє в чергу повідомлення `ProcessPaymentCommand`, він усе ще тісно зв'язаний із білінгом: він чекає конкретної дії від конкретного виконавця. Якщо ж він публікує подію `OrderPlaced`, він взагалі не знає, хто її прочитає. Можливо, її прочитає лише білінг. Можливо — білінг, аналітика, служба доставки та сервіс лояльності. А можливо — взагалі ніхто, якщо зараз система перебуває в режимі обслуговування.

```
       Синхронний виклик (REST/gRPC)               Асинхронна подія (Pub/Sub)
       
   +----------+          +----------+         +----------+          +---------------+
   | Сервіс А | --REST-> | Сервіс Б |         | Сервіс А | ------>  | Outbox / Log  |
   +----------+          +----------+         +----------+          +---------------+
        |                     |                    |                        |
        | [Чекає відповіді]   |                    | [Повернув контроль]    | (Kafka / Queue)
        v                     v                    v                        v
   [Залежність виконання в реальному часі]   [Повна часова розв'язка]  +---------------+
                                                                    |   Сервіс Б    |
                                                                    +---------------+
```

Під час розгортання оновлень асинхронні події надають три масивні переваги для автономії релізів:

- **Буферизація в черзі (Queue Buffering)**: Під час деплою нової версії Сервісу B його контейнери зупиняються. Сервіс A продовжує працювати у звичайному режимі, публікуючи сотні подій за секунду у топік Kafka. Черга накопичує байти. Коли Сервіс B піднімається з новим кодом, він вичитує накопичений буфер із тією швидкістю, яку здатен витримати.
- **Ізоляція відкату (Rollback Isolation)**: Якщо у новій версії Сервісу B виявлено критичний баг, його розгортання відкочують назад до попередньої версії. Споживач може зупинити свій зсув (offset) або скинути непорозбирані повідомлення у Dead Letter Queue (DLQ). Сервіс A навіть не помітить аварії в сусідів.
- **Відтворення історії (Replay Capability)**: При випуску нового сервісу аналітики вам не потрібно міняти код Сервісу A. Новий сервіс просто скидає свій читацький вказівник на початок логу подій і перечитує історію за останній рік.

### 3.2. Надійність публікації: Пастка подвійного запису та Outbox
Асинхронний зв'язок дає автономію лише тоді, коли публікація події є **надійною**. Поширеною помилкою є спроба записати бізнес-сутність у базу даних і одразу після цього викликати метод `kafkaProducer.send()`.

Якщо мережа моргне між першою та другою операцією, база даних матиме замовлення, але решта системи ніколи про нього не дізнається. Для розв'язання цієї проблеми застосовують **Transactional Outbox**: зміна стану сутності та запис події в таблицю `outbox` виконуються в єдиній транзакції БД. Окремий демон (CDC / Debezium) зчитує outbox і гарантує доставку в брокер за принципом *at-least-once*.

### 3.3. Передача стану у подіях: Event Notification проти ECST
При розробці подійних систем виникає вибір між двома стилями вмісту подій:

1. **Event Notification (Коротке сповіщення)**: Подія містить лише ID сутності: `{"event": "OrderPlaced", "id": 9901}`. Споживач, отримавши подію, змушений робити зворотний синхронний HTTP-запит до Сервісу A, щоб зчитати деталі замовлення. Це повертає часове та релізне зчеплення через чорний хід!
2. **Event-Carried State Transfer (ECST — Подія з повним станом)**: Подія несе в собі всі атрибути, необхідні споживачу: ID, суму, перелік товарів, дані покупця. Споживач зберігає ці дані у власному локальному read model і більше ніколи не робить синхронних запитів до відправника. Подібне розчеплення повністю вивільняє незалежність релізів.

### 3.4. Спостережність та трасування в асинхронних мережах
Асинхронні події розривають суцільний HTTP-потік, тому звичайні заголовки трасування губляться. Для збереження спостережності (Observability) використовують стандарт **W3C Trace Context** або OpenTelemetry headers, що запікаються безпосередньо в метадані (Kafka Headers або AMQP Properties).

Продюсер додає у заголовок повідомлення `traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`. Коли споживач вичитує повідомлення з черги через 15 хвилин після публікації, він створює новий child span із цим самим `trace_id`. Це дозволяє інженерам бачити суцільний шлях замовлення у дашбордах спостережності, незважаючи на часову розв'язку між деплоями продюсера та споживача.

### 3.5. Стратегії партиціонування та порядку подій
У розподілених логах (Apache Kafka, AWS Kinesis) важливим критерієм розчеплення є збереження порядку обробки подій для конкретної сутності.

За це відповідає **ключ партиціонування (Partition Key)**. Якщо продюсер відправляє події про зміну стану смарт-замка з ключем `device_id: "lock-44"`, усі події цього замка потрапляють в одну й ту саму партицію і обробляються строго послідовно. При зміні коду продюсера важливо гарантувати, що ключ партиціонування не змінюється (наприклад, з `device_id` на `home_id`), адже це змішає порядок обробки у споживачів і зламає послідовність релізів.

### 3.6. CQRS та Управління лагом проєкції (Read Model Lag)
Перехід на асинхронний подійний зв'язок неминуче приводить систему до архітектурного патерну **CQRS (Command Query Responsibility Segregation)**. Модель запису (Command Model) обробляє зміни та генерує події, а модель читання (Read Model) вичитує події й будує матеріалізовані представлення для швидкого пошуку.

Між моментом виконання команди й оновленням моделі читання існує **лаг проєкції (Read Model Lag)**. Для того щоб розгортання нових версій споживачів не псувало досвід користувача (UX), застосовують три тактики управління лагом:
- *Optimistic UI Update*: Клієнтський застосунок додає створений об'єкт у локальний список ще до отримання підтвердження від брокера.
- *Явний індикатор свіжості*: Інтерфейс чесно показує користувачу повідомлення «Дані оновлено 3 секунди тому».
- *Версійні ключі інвалідації*: Клієнт запитує дані з заголовком `If-Match: "v1.0.4"`, змушуючи кеш віддати відповідь лише після досягнення споживачем відповідного зсуву.

### 3.7. Еволюція схем у Protobuf та Avro
Для збереження релізної незалежності в асинхронних подійних архітектурах бінарні формати Protobuf та Avro використовують математичні гарантії числових тегів та реєстрів схем:

- **Protobuf Field Tags**: У Protobuf нові поля додаються з унікальними тегами (`string tax_id = 4;`). Якщо старий споживач вичитує подію з тегом `4`, якого немає в його бінарному декодері, він зберігає його у спеціальному полі `unknownFields` і продовжує обробку. Забороняється змінювати теги існуючих полів.
- **Avro Schema Registry Default Values**: В Avro кожне нове optional-поле повинно мати дефолтне значення (`"default": null`). При зчитуванні нової події старий споживач підставляє значення за замовчуванням для невідомих атрибутів, досягаючи повної `FULL` двосторонньої сумісності.

## 4. Порівняльний аналіз для тактики розгортання змін

Для того щоб обрати тип зв'язку під конкретну зміну, архітектор має зіставити їх за спектром зчеплення, поведінкою під час деплою та динамікою відкату.

![Спектр зчеплення релізів при змінах](/root/course/progarch/change-coupling-choice/img/release-coupling-spectrum.svg)
*Спектр зчеплення релізів: від жорсткої синхронної залежності до повної автономії з логом подій.*

Як видно зі спектра, синхронний REST/gRPC розташований на полюсі максимального зчеплення. Кожна зміна вимагає координації між командами або застосування складного трифазного Expand-Contract. Асинхронний Outbox та подійний лог розташовані на полюсі максимальної автономії.

Порівняймо, що відбувається з трафіком під час розгортання несумісної зміни в обох підходах.

![Синхронний каскад проти асинхронного буфера](/root/course/progarch/change-coupling-choice/img/lockstep-vs-independent.svg)
*Каскадна відмова при синхронному розгортанні проти буферизації змін в асинхронній черзі.*

При синхронному зв'язку викатка нового поля у Сервісі A зустрічає жорстку відмову `400 Bad Request` від Сервісу B, який ще не оновився. Система падає в стан проплаченого простою. При асинхронному зв'язку подія v2 потрапляє в чергу. Старий Сервіс B v1 ігнорує нове поле завдяки поблажливому читачеві (Tolerant Reader) або накопичує події у буфері до моменту власного релізу.

Ще гостріше різниця виявляється під час **аварійного відкату (Rollback)**.

![Поведінка системи при відкаті: REST проти подій](/root/course/progarch/change-coupling-choice/img/schema-evolution-coupling.svg)
*Поведінка системи під час відкату (Rollback): синхронний злам проти збереження даних у логу.*

При синхронному відкаті Сервісу B назад до v1, вимушено відкочуватися має й Сервіс A, оскільки його нові HTTP-запити відхиляються. Це створює доміно-ефект відкатів по всій компанії. При подійному зв'язку відкат Сервісу B зводиться до зупинки зсуву споживача або переведення неопрацьованих повідомлень у Dead Letter Queue. Продюсер A продовжує приймати трафік користувачів без жодної секунди простою.

## 5. Матриця компакт-вибору: критерії й алгоритм прийняття рішень

Вибір між REST/gRPC та Подіями не повинен здійснюватися за принципом «ми суто подійні» або «ми пишемо лише REST». Це інженерний компроміс між **затримкою (latency)** та **автономією (autonomy)**.

Ось дерево прийняття рішень для вибору типу зв'язку при проєктуванні нової зміни:

```
                                    Чи потрібна ВІДПОВІДЬ
                                  у мить виконання запиту?
                                         /        \
                                       ТАК        НІ
                                       /            \
                       Чи потрібна сувора          Скільки існує
                      транзакційна консистентність?    споживачів цієї зміни?
                             /        \                   /       \
                           ТАК        НІ                1:1       1:N
                           /            \               /           \
                     Синхронний      Синхронний     Асинхронний    Pub/Sub /
                       gRPC            REST           Command      Event Log
                    (з Expand-      (з Tolerant        Queue        (Outbox +
                    Contract)        Reader)        (RabbitMQ)     Kafka)
```

Для швидкого огляду критеріїв використовують компактну підсумкову таблицю.

| Критерій | Синхронний REST / gRPC | Асинхронний Pub/Sub (Events) |
| :--- | :--- | :--- |
| **Затримка (Latency)** | Мінімальна (прямий сокет) | Вища (накладний час черги) |
| **Автономія релізів** | Низька (ризик lockstep) | Максимальна (буферизація в логу) |
| **Обробка відкатів** | Складна (каскад відкатів) | Проста (DLQ / скидання offset) |
| **Консистентність** | Строга (ACID / synchronous) | Узгодженість у кінцевому підсумку |
| **Топологія споживачів** | Point-to-point (1:1) | Fan-out (1:N) |
| **Складність відлагодження** | Низька (суцільний TraceID) | Вища (асинхронна кореляція) |

Вичерпну довідкову таблицю з усіма сімома вимірами зчеплення, режимами сумісності Schema Registry (BACKWARD, FORWARD, FULL) та чек-листом для Architecture Review зібрано в [матриці оцінки зчеплення](root:progarch/change-coupling-choice/api-coupling-matrix.md).

А практичну реалізацію обох підходів у коді — від прямого REST-запиту, що валить реліз, до робочого Transactional Outbox з поблажливим читачем мовами C, C++, Go та TypeScript — розібрано в [практичному прикладі міграції зчеплення](root:progarch/change-coupling-choice/proj-decoupled-migration.md).

## 6. Архітектурна тактика: гібридні контури та захисні бар'єри у реальних системах

У реальних масштабних системах — таких як платформа розумного дому Digital Homes — ви ніколи не знайдете чистих монокультів. Дорослі системи будуються як **гібридні контури**, де стиль зв'язку обирають під сили конкретної межі.

```
+-----------------------------------------------------------------------------------+
|                              ВНУТРІШНІЙ СИНХРОННИЙ КОНТУР                         |
|                                                                                   |
|  +-------------------+       gRPC (Protobuf)      +----------------------------+  |
|  | DeviceRegistryHub | -------------------------> | AutomationEngine           |  |
|  | (Реєстр пристроїв)|  [Низька затримка < 2мс]   | (Рушій локальних сценаріїв)|  |
|  +-------------------+                            +----------------------------+  |
+-----------------------------------------------------------------------------------+
                                          |
                                          | (Transactional Outbox)
                                          v
+-----------------------------------------------------------------------------------+
|                             ЗОВНІШНІЙ АСИНХРОННИЙ КОНТУР                          |
|                                                                                   |
|                           +---------------------------+                           |
|                           |   Kafka Event Broker      |                           |
|                           +---------------------------+                           |
|                             /           |           \                             |
|                            /            |            \                            |
|                           v             v             v                           |
|                    +------------+ +------------+ +-----------------+              |
|                    | Analytics  | | Billing    | | Cloud Telemetry |              |
|                    | Service    | | Service    | | Sync Service    |              |
|                    +------------+ +------------+ +-----------------+              |
+-----------------------------------------------------------------------------------+
```

Усередині локального хаба розумного дому між реєстром пристроїв та рушієм автоматизації використовується **синхронний gRPC**. Чому? Бо вимикач світла має спрацьовувати за 15 мілісекунд, обидва модулі пишуться однією командою, живуть в одному репозиторії й розгортаються єдиною прошивкою. Тимчасове зчеплення тут виправдане вимогами продукту.

Але коли той самий хаб публікує факти зміни стану пристроїв назовні — у хмару для аналітики, телеметрії та білінгу — використовується **Transactional Outbox та асинхронні події**. Хмара може проводити технічні роботи, білінг може бути недоступний через планові міграції баз даних, а аналітики можуть викачувати нові версії моделей тричі на день. Асинхронний лог подій стверджує: **існування хаба й затишок у домі не залежать від релізів хмарних білінгів.**

### 6.1. Аналіз сукупної вартості володіння (Total Cost of Ownership — TCO)
Вибір типу зв'язку визначає структуру витрат компанії:

- **Синхронний REST/gRPC**: Низькі інфраструктурні витрати (не потрібно тримати кластери Kafka, Zookeeper/KRaft чи Schema Registry). Однак високі людські витрати на релізні комітети, нічні чергування, узгодження релізів між командами та виправлення каскадних падінь на продакшені.
- **Асинхронні події**: Вищі інфраструктурні витрати (кластери брокерів, CDC-демони Debezium, дискові масиви для retention). Проте значно нижчі людські витрати: команди розгортаються незалежно у будь-який день, а помилки споживачів усуваються за секунди шляхом перепроведення подій із DLQ.

### 6.2. Чек-лист готовності контракту до релізу (Production Release Gate)
Перед тим як відправити нову версію контракту в продакшен, команда зобов'язана провести перевірку готовності за наступним алгоритмом:

1. **Перевірка на адитивність**: Жодне існуюче поле не видалено й не перейменовано без проходження фаз Expand-Contract.
2. **Перевірка поблажливості споживачів**: Запущено контрактні тести проти старих версій читачів.
3. **Перевірка ідемпотентності**: Споживачі мають таблицю ідемпотентності для усунення дублікатів при ретраях.
4. **Наявність контуру DLQ**: Забезпечено ізоляцію непорозбираних повідомлень без зупинки основного потоку обробки.
5. **Валідація W3C Trace Context**: Заголовки трасування коректно прокидаються крізь черги.
6. **Оцінка пропускної здатності черги**: Проведено розрахунок навантаження та перевірено конфігурацію алгоритмів стиснення (snappy, zstd) для великих ECST-пакетів.
7. **Оцінка часу витримки буфера (Retention Sizing)**: Перевірено, що дисковий ліміт брокера витримає накопичення повідомлень за 48 годин у разі вимушеної зупинки споживача.
8. **Наявність резервного плану відкату (Rollback Strategy)**: Складено покрокову інструкцію скидання зсуву (Offset Reset) для споживачів у разі виявлення критичних помилок.
9. **Моніторинг затримки споживача (Consumer Lag Alerting)**: Налаштовано порогові сповіщення у Prometheus Alertmanager для виявлення накопичення затриманих подій у топіках Kafka.

### Висновок
Вибір типу зв'язку для зміни — це не суперечка релігійних догм. Це чіткий розрахунок: там, де потрібна низька затримка й строга атомарність в межах однієї команди — ми беремо синхронний REST/gRPC і інвестуємо в дисципліну Expand-Contract. Там, де потрібна автономія релізів багатьох команд та ізоляція відкатів — ми беремо асинхронні Події та Transactional Outbox.
