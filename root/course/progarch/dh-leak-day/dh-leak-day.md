Коли приватний ключ або секрет доступу потрапляє у відкритий репозиторій, автоматизовані боти нападників виявляють його за лічені секунди. Інцидент безпеки принципово відрізняється від звичайного збою інфраструктури: системний код не є поламаним, але довіра до криптографічних ключів повністю знищена. Нападник вже знаходиться всередині периметра й може володіти згенерованими маркерами доступу. 

Метою реагування на День витоку є не виправлення коду, а негайне вигнання супротивника з системи, розрив активних сесій та проведення каскадної ротації секретів.

---

## 1. Оцінка радіуса вибуху та локалізація (Containment)

Першим кроком реагування є визначення **радіуса вибуху** (англ. *blast radius*) — меж інфраструктури, до яких нападник здобув доступ. Якщо викрадений ключ мав привілеї деплою (управління кластером), під загрозою опиняються всі внутрішні секрети: ключі підпису сесій, паролі баз даних та сертифікати пристроїв.

![Граф каскадного поширення компрометації](img/blast-radius-cascade.svg)
*Декомпозиція каскадного ураження інфраструктури при витоку ключа.*

Аналіз витоку вимагає від інженерів оцінити не лише безпосередньо викрадений файл, а й усі похідні секрети, до яких нападник міг дотягнутися через Kubernetes Secrets або змінні оточення. Зкомпрометований ключ деплою дозволяє атакувальнику читати майстер-ключі шифрування, підробляти сесії користувачів та відправляти шкідливі команди розумним пристроям.

Для негайної зупинки атаки застосовується трирівневий розрив сесій:
1. **Глобальний відсікач (`leak_timestamp`)**: В оперативну пам'ять API Gateway записується час витоку. Усі маркери JWT, випущені до цього моменту, негайно відхиляються на межі шлюзу без звернення до бази даних.
2. **Фільтр відкликаних токенів (`jti_blacklist`)**: Унікальні ідентифікатори компрометованих токенів додаються в швидкий ін-меморі фільтр Bloom Filter у Redis-кластері з нульовою затримкою для обробки гарячого трафіку.
3. **Анулювання Refresh-токенів**: Інкремент лічильника сесій у базі даних унеможливлює повторне отримання маркерів доступу без повторного проходження автентифікації.

## 2. Послідовність каскадної ротації секретів

Ротація секретів виконується у суворо визначеному порядку залежностей — від баз даних до зовнішніх пристроїв:

![Послідовність каскадного реагування](img/revocation-sequence.svg)
*Чотири фази інженерного плейбука ротації секретів.*

* **Бази даних (Dual-Auth)**: Впровадження другого тимчасового пароля для сервісу, оновлення конфігурацій додатків через Vault, плановий перезапуск подив Kubernetes й видалення старого пароля після успішного переключення трафіку.
* **Маркери JWT (JWKS Rollover)**: Випуск нового ключа підпису `kid_v2`. Старий ключ `kid_v1` залишається у списку довірених лише для читання протягом 24 годин для завершення активних сесій.
* **Майстер-ключі KMS (KEK)**: Ротація Master Key з автоматичним перешифруванням 256-бітних заголовків ключів даних (DEK) без фізичного перешифрування петабайтів збережених файлів у сховищі S3.

---

## 3. Ротація сертифікатів флоту пристроїв та юридичні дедлайни

Ротація mTLS-сертифікатів 1.2 мільйона периферійних хабів не може бути виконана миттєво. Негайне анулювання сертифіката сервера перетворить пристрої на «цеглини» (Bricking), позбавивши їх можливості отримати нову конфігурацію.

![Часова шкала зрізу ротації](img/fleet-rotation-timeline.svg)
*Порівняння часових горизонтів ротації секретів у хмарі та на пристроях.*

Для безпечного оновлення флоту задіюється двофазова міграція (Dual-CA Setup):
1. Додавання нового Центру Сертифікації (`Fleet_CA_v2`) у список довірених на серверних TLS-термінаторах.
2. Поступова перевидача сертифікатів хабам за протоколом EST (RFC 7030) протягом 14 днів для запобігання перевантаженню серверів (Thundering Herd Problem).
3. Остаточне видалення старого CA після оновлення 99.8% пристроїв.

Паралельно з технічними кроками інженерна команда зобов'язана дотримуватися дедлайнів розкриття інформації: **24 години** для початкового повідомлення про інцидент критичної інфраструктури (NIS2 Directive) та **72 години** для офіційного розкриття регуляторам захисту даних (GDPR Article 33).

Фіксація доказів здійснюється за стандартом RFC 3227 (Order of Volatility): перед перезапуском серверів фіксуються RAM-дампи та мережеві сокети eBPF, а Merkle Tree хеш-ланцюжок логів аудиту заморожується та підписується апаратним HSM-модулем.

За результатами усунення наслідків витоку розробляється детальний постмортем інциденту безпеки. До конвеєрів CI/CD впроваджуються автоматичні перевірки захисту від витоку секретів у вихідний код (gitleaks у Git pre-commit hooks) та перехід на короткоживучі OIDC-токени (Workload Identity Federation), що повністю унеможливлює зберігання статичних секретів у кодовій базі.

Кожен крок реагування регламентується суворими інженерними правилами та практичними сценаріями, щоб мінімізувати можливий вплив витоку на кінцевих користувачів розумного будинку та відновити повний контроль над цифровою платформою.

День витоку доводить, що стійкість системи вимірюється не відсутністю інцидентів, а швидкістю та детермінованістю каскадного відновлення довіри.
