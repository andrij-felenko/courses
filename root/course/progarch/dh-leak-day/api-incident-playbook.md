# 📋 Специфікація плейбука реагування та ротації секретів Digital Homes

Цей документ визначає нормативну специфікацію, таксономію секретів, матрицю реагування на інциденти витоку (Incident Response Matrix) та параметри ротації ключів для інфраструктури платформи Digital Homes. Специфікація слугує інженерним контрактом для чергових інженерів (On-Call Engineers), команди безпеки (SecOps) та автоматизованих скриптів каскадної ротації.

Головною метою специфікації є перетворення хаотичного інженерного гасіння пожежі під час кризового інциденту на детерміновану послідовність кроків із чітко визначеними межами відповідальності, часовими нормативами (SLA) та юридичними дедлайнами розкриття.

## 1. Таксономія секретів та радіус вибуху (Blast Radius Matrix)

Усі секрети, криптографічні ключі та маркери доступу платформи Digital Homes класифікуються за чотирма рівнями критичності. Рівень визначається на основі потенційного радіуса вибуху (Blast Radius) — тобто максимально можливого обсягу системних ресурсів, персональних даних та фізичних пристроїв, до яких нападник може здобути доступ при компрометації конкретного секрету.

```
┌────────┬────────────────────────────────┬───────────────────────────────┬───────────────────────────────┬──────────────────────────────┐
│ Рівень │ Тип секрету                    │ Приклади компрометації        │ Радіус вибуху (Blast Radius)  │ Допустимий SLA ротації       │
├────────┼────────────────────────────────┼───────────────────────────────┼───────────────────────────────┼──────────────────────────────┤
│ L0     │ Infrastructure Root Secrets    │ CI/CD Deployer Private Key,   │ Повний контроль над Prod K8s, │ Негайно                      │
│ (P0)   │ & Cloud Credentials            │ AWS Root/Admin Credentials    │ KMS Master Keys, 1.2M хабів   │ (< 15 хвилин)                │
├────────┼────────────────────────────────┼───────────────────────────────┼───────────────────────────────┼──────────────────────────────┤
│ L1     │ Token Signing & Master Encryption│ JWT Ed25519 Private Key,     │ Підробка сесій будь-якого     │ До 60 хвилин                 │
│ (P1)   │ Keys (KEK)                     │ KMS Envelope KEK Key          │ користувача, розшифровка DB   │                              │
├────────┼────────────────────────────────┼───────────────────────────────┼───────────────────────────────┼──────────────────────────────┤
│ L2     │ Subsystem & DB Credentials     │ PostgreSQL Auth Passwords,    │ Читання/запис конкретної БД,  │ До 4 годин                   │
│ (P2)   │                                │ Redis Token Store Password    │ доступ до черги RabbitMQ      │                              │
├────────┼────────────────────────────────┼───────────────────────────────┼───────────────────────────────┼──────────────────────────────┤
│ L3     │ Fleet & Edge Identity Keys     │ Fleet mTLS Intermediate CA,   │ Компрометація підключення     │ 1 – 14 днів                  │
│ (P3)   │ (mTLS / Device Tokens)         │ Hub Client Identity Certificate│ конкретного хаба чи пристрою │ (Staggered Fleet Migration)  │
└────────┴────────────────────────────────┴───────────────────────────────┴───────────────────────────────┴──────────────────────────────┘
```

Рівень L0 є найвищим ступенем небезпеки. Зкомпрометований секрет цього рівня дає нападнику привілеї адміністратора інфраструктури, дозволяючи зчитувати майстер-секрети інших рівнів, підробляти прошивки та виконувати довільний код.

## 2. Алгоритм дій та послідовність виконання плейбука (Execution Protocol)

При виявленні витоку (алерт від автоматизованої системи GitHub Secret Scanning, сповіщення від Bug Bounty дослідників або виявлення аномальної активності в логах аудиту) чергова інцидент-команда діє за суворим протоколом із чотирьох послідовних етапів.

### Етап 1: Зупинка кровотечі (Containment Phase) — SLA < 15 хвилин

Головна мета першого етапу — позбавити нападника можливості продовжувати атаку та створювати нові точки закріплення в інфраструктурі.

1. **Анулювання джерела витоку**:
   * Для облікових даних AWS: виконання команди `aws iam update-access-key --access-key-id <AKIA...> --status Inactive`.
   * Для GitHub CI/CD: Деактивація персональних токенів доступу `PAT` або негайна ротація ролей `OIDC Workload Identity Federation`.
2. **Ввімкнення екстреного фільтра сесій (Emergency Session Kill)**:
   * Встановлення значення `leak_timestamp = now()` в конфігурації Edge Gateway (Envoy / BFF).
   * Опублікування події про витік у каналі Redis Pub/Sub для оновлення локальних ін-меморі фільтрів на всіх розгорнутих екземплярах API Gateway.
3. **Замороження форензик-зрізу**:
   * Збереження логів аудиту до моменту ротації: створення Read-Only Snapshot бакету логів.
   * Виконання `docker pause` або `crictl pause` для компрометованого контейнера (якщо присутня активна сесія нападника) для подальшого зняття RAM-дампу оперативної пам'яті.

### Етап 2: Каскадна ротація секретів хмари (Cloud Rotation Phase) — SLA < 60 хвилин

Після локалізації джерела витоку здійснюється підготовка та ротація внутрішньохмарних секретів.

1. **Ротація секретів баз даних та брокерів**:
   * Переведення конфігурації баз даних PostgreSQL у режим Dual-Auth (підтримка одночасно старого та нового пароля користувача сервісу).
   * Виконання перезапуску подив Kubernetes за допомогою `kubectl rollout restart deployment/<service-name>`.
   * Деактивація старого пароля після успішного завершення ротації всіх залежних подив.
2. **Ротація токенів підпису (JWKS Rollover)**:
   * Збірка нової пари ключів підпису Ed25519: `kid_v2`.
   * Публікація еліптичного публічного ключа `kid_v2` в JWKS ендпоінт `https://auth.digitalhomes.io/.well-known/jwks.json`.
   * Переключення прапорця `active_for_signing = kid_v2`.

### Етап 3: Ротація KMS та конвертного шифрування (Storage Rotation Phase) — SLA < 4 години

Ротація ключів шифрування баз даних та об'єктного сховища здійснюється без зупинки доступу до сервісу.

1. **Ротація Master Key (KEK)**:
   * Створення нового Master Key `KEK_v2` у хмарному KMS (AWS KMS або HashiCorp Vault).
   * Запуск фонового демона ре-враппінгу (Re-wrapping Worker): демон послідовно читає зашифровані заголовки таблиць DEK (Data Encryption Keys), розшифровує їх за допомогою `KEK_v1` та зашифровує за допомогою `KEK_v2`.
   * Використання конвертного шифрування гарантує, що терабайти зашифрованих відеозаписів та телеметрії **не перешифровуються**, змінюються лише криптографічні заголовки DEK.

### Етап 4: Ротація TLS-сертифікатів флоту пристроїв (Fleet Rollout Phase) — SLA 1–14 днів

Ротація ідентичності периферійних пристроїв та хабів є найдовшим етапом інженерного реагування.

1. **Розгортання подвійного CA (Dual-CA Setup)**:
   * Випуск нового Intermediate CA `Fleet_CA_2026_v2`.
   * Додавання публічного сертифіката `Fleet_CA_2026_v2` в список довірених Root CA на хмарних термінаторах mTLS.
2. **Поступова перевидача сертифікатів хабів (Staggered Issue)**:
   * Запуск EST/SCEP демона перевидачі з випадковим часовим розкидом (jitter) для запобігання атаці Thundering Herd на сервери видачі сертифікатів.
   * Розподіл 1.2M пристроїв на 14 добових квантів (~85 000 хабів на добу).
3. **Відкликання старого CA**:
   * Після досягнення 99.8% оновлених пристроїв старий сертифікат `Fleet_CA_2026_v1` викреслюється з конфігурації TLS-термінатора.

## 3. Специфікація юридичного розкриття та дедлайни регуляторів

У разі компрометації персональних даних (PII) або систем управління смарт-будинками компанія підпадає під дію міжнародних регуляторних норм. Недотримання часових рамок розкриття тягне за собою важкі юридичні та фінансові санкції.

```
┌────────────────────────┬────────────────────────────────┬───────────────────────────────┬────────────────────────────────┐
│ Регуляторна норма      │ Поріг застосування             │ Дедлайн першого повідомлення  │ Вимоги до змісту звіту         │
├────────────────────────┼────────────────────────────────┼───────────────────────────────┼────────────────────────────────┤
│ GDPR Article 33        │ Витік PII користувачів ЄС      │ 72 години з моменту виявлення │ Причина, обсяг PII, вжиті      │
│ (Data Protection)      │ (імена, геопозиція, відео)     │ (Supervisory Authority)       │ заходи, контакти DPO           │
├────────────────────────┼────────────────────────────────┼───────────────────────────────┼────────────────────────────────┤
│ NIS2 Directive         │ Аварія чи витік у критичних    │ 24 години (Early Warning),    │ Початкова оцінка чутливості,   │
│ (Critical Infra)       │ смарт-системах життєзабезпечення│ 72 години (Full Notification) │ вектор компрометації, суміжні  │
├────────────────────────┼────────────────────────────────┼───────────────────────────────┼────────────────────────────────┤
│ SEC Cybersecurity      │ Суттєвий інцидент публічної    │ 4 робочі дні (Form 8-K)       │ Вплив на фінансовий стан,      │
│ Disclosure (US)        │ компанії                       │                               │ операційну спроможність        │
└────────────────────────┴────────────────────────────────┴───────────────────────────────┴────────────────────────────────┘
```

Розслідування інциденту зобов'язане формувати первинне повідомлення (Early Warning Notification) протягом перших 24 годин. Звіт повинен описувати характер компрометації, попередню кількість постраждалих облікових записів та перелік вжитих інженерних заходів з локалізації.

## 4. Метрики ефективності (Postmortem Fitness Functions)

Для автоматизованої перевірки готовності платформи Digital Homes до дня витоку в CI/CD конвеєри розробки впроваджуються такі інженерні фітнес-функції:

* **Secret Leak SLA Check**: Автоматичні навчання (Chaos Security Drill) — імітація витоку тестового ключа у контрольованому середовищі та вимір часу до повного анулювання сесій (цільове значення: `< 120 секунд`).
* **Staggered Fleet Capacity Test**: Тестування пропускної спроможності EST-сервера перевидачі mTLS сертифікатів (цільове значення: `> 500 certs/sec`).
* **Audit Chain Integrity Verification**: Щоденне математичне вирахування та перевірка цілісності Merkle Tree хеш-ланцюжка логів аудиту.
