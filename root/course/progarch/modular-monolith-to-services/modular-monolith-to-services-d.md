# Від модульного моноліта до сервісів без розриву

<preknowlist>
- [Модульний моноліт як дефолт](book:progarch/modular-monolith-first) — чому система починається в одному деплої і як чисті межі коду готують ґрунт під розкол.
- [Branch by Abstraction](book:programming/branch-by-abstraction) — патерн виділення абстракції над старою реалізацією для безболісної підміни компонента в живій системі.
- [Острови даних і транзакційні межі](book:progarch/aggregates-consistency) — чому база даних у моноліті має природні зони ізоляції і як транзакція зв'язує сутності.
</preknowlist>

У момент, коли навантаження на один із модулів моноліта перетинає розраховану розтяжку продуктивності, або коли команда розробників конкретного домену виростає до кількох автономних продуктових трибів, архітектор ухвалює рішення про виділення першого мікросервісу. На слайдах презентацій та в маркетингових статтях цей крок виглядає оманливо простим: виділити теку з кодом модуля в окремий репозиторій, загорнути у Docker-контейнер, поставити перед ним HTTP-шлюз та вимкнути старий код у моноліті.

У реальних промислових системах спроба виконати такий розкол «в лоб» у 90% випадків призводить до катастрофи: тривалої зупинки продакшну, ручного відновлення збочених даних у базі, каскадних відмов та появу найгіршого з можливих архітектурних антипатернів — **розподіленого моноліта**. Код, який роками працював в одному процесі, просочений сотнями неявних зв'язків: прямими викликами методів суміжних класів через синглтони, спільними транзакціями бази даних `BEGIN ... COMMIT`, що охоплюють кілька бізнес-доменів, складними SQL-запитами з `JOIN` через шість таблиць різних модулів та спільним пам'ятковим кешем.

Справжній розпил моноліта — це не інфраструктурне перемикання прапорців, а керована бізнес-хірургія на працюючій системі під повним користувацьким навантаженням. Вона виконується за покроковою стратегією без зупинки обслуговування (Zero Downtime) через чотири системні етапи: створення швів у коді, логічну й фізичну ізоляцію даних, патерн Strangler Fig та автоматизоване контрактне тестування у CI/CD.

## 1. Перший крок розколу робиться в коді, а не на мережі

Головна пастка, у яку потрапляють інженерні команди при виділенні сервісу — це початок з інфраструктури: розгортання нових контейнерів у Kubernetes, конфігурування Service Mesh та налаштування мережевих маршрутів Nginx. Доки межі модуля всередині моноліта є розмитими та мають приховані зчеплення (coupling), витягування його на мережу лише перетворить швидкі й надійні виклики методів у пам'яті на повільні, крихкі й ненадійні мережеві стрибки, зберігаючи при цьому всю вихідну складність.

Розпил завжди починається **всередині монолітного коду** — із виділення швів (Code Seams). Шов — це точка у кодовій базі, де монолітну поведінку можна розірвати й вставити нову реалізацію без жодної зміни клієнтських модулів.

```
Фаза 0: Крихкий моноліт                  Фаза 1: Виділений шов (Branch by Abstraction)
┌───────────────────────────────┐        ┌───────────────────────────────┐
│ [ Модуль А ] ──(прямий)──►    │        │ [ Модуль А ]                  │
│                [ Модуль Б ]   │        │      │                        │
│ (Спільні JOIN / Singletons)   │        │      ▼                        │
└───────────────────────────────┘        │ [ Інтерфейс-Фасад Б ]         │
                                         │      │                        │
                                         │      ├──► [ Модуль Б (Legacy) ]
                                         │      └──► [ HTTP/gRPC Клієнт ]│
                                         └───────────────────────────────┘
```

### Анатомія виділення шва в коді за патерном Branch by Abstraction

Процес створення шва здійснюється за патерном **Branch by Abstraction** («галуження через абстракцію») і складається з п'яти послідовних кроків:

1. **Ізоляція публічної поверхні модуля:** Для модуля, який готується до винесення (наприклад, `TelemetryModule`), чітко окреслюється мінімально необхідна поверхня методів. Усі внутрішні класи модуля (сервіси, ORM-сутності, утиліти) оголошуються приватними для модуля (`package-private` або закриваються правилами оптимізатора видимості).
2. **Створення абстрактного інтерфейсу та DTO:** Запроваджується явний інтерфейс (наприклад `ITelemetryRepository`), який описує контракти методів у термінах чистого DTO (Data Transfer Object). З полів цього DTO повністю видаляються будь-які посилання на сутності ORM, внутрішні ідентифікатори або таблиці бази даних.
3. **Побудова шару запобігання пошкодженню (Anti-Corruption Layer, ACL):** Навколо старої реалізації модуля будується шар ACL. Його задача — конвертувати старі внутрішні структури даних моноліта у нові чисті DTO інтерфейсу і навпаки. Це захищає майбутній мікросервіс від успадкування концептуального боргу старого моноліта.
4. **Переведення споживачів на абстракцію:** Усі клієнтські модулі моноліта рефакторяться так, щоб посилатися виключно на інтерфейс `ITelemetryRepository`. Прямий доступ до внутрішніх класів модуля Б блокується автоматичними тестами архітектури (наприклад, фитнес-функціями на ArchUnit або статичними аналізаторами коду в CI).
5. **Впровадження проксі-роутера (Branch Router):** Створюється реалізація інтерфейсу, яка на основі конфігурації здатна перенаправляти виклик або старій локальній реалізації в пам'яті, або новому мережевому RPC-клієнту.

```
[ Модуль-Споживач ] ──► [ ITelemetryRepository ] ──► [ Strangler Branch Router ]
                                                           │
                                   ┌───────────────────────┴───────────────────────┐
                                   ▼                                               ▼
                     [ ACL -> Legacy Module ]                        [ HTTP / gRPC Client ]
```

На цьому етапі вся система продовжує виконуватися в одному процесі, але шов у коді вже повністю сформовано. Компілятор та контейнер впровадження залежностей (Dependency Injection) тепер строго охороняють межу модуля. Жоден розробник більше не зможе випадково додати прямий виклик внутрішнього класу вбік, адже лінтер CI блокуватиме такий PR.

### Захист швів за допомогою фітнес-функцій CI

Щоб виділений шов у коді не розмивався під час паралельної розробки іншими членами команди, у CI/CD конвеєр додається автоматична фітнес-функція (Fitness Function). Вона аналізує граф імпортів та AST (Abstract Syntax Tree) проєкту при кожному pull request:

```java
// Приклад архітектурного тесту (ArchUnit) для захисту шва модуля Telemetry
@ArchTest
public static final ArchRule telemetry_seam_protection = noClasses()
    .that().resideInAPackage("com.digitalhomes.monolith.automations..")
    .should().dependOnClassesThat()
    .resideInAPackage("com.digitalhomes.monolith.telemetry.internal..")
    .because("Модуль Automations мусить звертатися до Telemetry ЛИШЕ через ITelemetryRepository!");
```

Якщо хтось із розробників спробує заізолювати новий метод напряму зі старої пакети `internal`, тест провалиться у CI й блокуватиме злиття коду.

> 🔧 **Навіщо це.** Створення шва в коді — це зворотна дія з нульовим ризиком для продакшну. Якщо під час побудови фасаду з'ясується, що модуль `Telemetry` має 80 неявних взаємних залежностей від модуля `Users`, це означає, що доменні межі накреслені хибно. Виправлення цих залежностей у коді моноліта коштує кілька днів роботи; виправлення тих самих залежностей після винесення на мережу коштує місяців важкого рефакторингу розподіленого моноліта.

## 2. Ізоляція даних: найважчий і найнебезпечніший крок розколу

Якщо рефакторинг коду є відносно безпечним завдяки підтримці компілятора та автоматизованих unit-тестів, то **ізоляція даних є найскладнішою фазою розпилу**. Код не має власного стану (stateless), тоді як база даних зберігає бізнес-історію та фінансовий стан компанії за всі роки її існування.

У моноліті база даних майже завжди являє собою спільне реляційне сховище, де таблиці різних доменів зв'язані зовнішніми ключами (Foreign Keys), а складні бізнес-операції виконуються через SQL-запити з `JOIN` та спільні ACID-транзакції. Спроба винести код сервісу в окремий процес, лишивши його ходити в спільну базу моноліта, утворює руйнівний антипатерн **Database-as-an-IPC** (база даних як засіб міжпроцесної комунікації). Це призводить до блокувань рядків, дедлоків та неможливості змінити структуру таблиці без зупинки всіх сервісів одразу.

Ізоляція даних виконується суворо поетапно, без спроб розділити фізичні сервери БД на першому ж кроці.

![Етапи безпечної ізоляції даних під час розпилу моноліта](/root/course/progarch/modular-monolith-to-services/img/data-decoupling-stages.svg)
*Стратегія покрокового розчеплення даних: від спільних таблиць із зовнішніми ключами до повністю автономних фізичних баз даних для кожного сервісу.*

### Етап А: Ліквідація cross-domain JOINs та Foreign Keys

Першою дією у базі даних є видалення всіх зовнішніх ключів (Foreign Keys), що перетинають межу виділюваного домену. Наприклад, якщо таблиця `telemetry_readings` має обмеження `CONSTRAINT fk_device FOREIGN KEY (device_id) REFERENCES devices(id)`, це обмеження видаляється прямою міграцією БД:

```sql
-- Видалення зовнішнього ключа між доменами Telemetry та Devices
ALTER TABLE telemetry_schema.telemetry_readings 
DROP CONSTRAINT fk_device_id;
```

Після цього валідація існування пристрою переноситься на прикладний рівень коду (Application Level Integrity). Код сервісу телеметрії більше не розраховує на те, що база даних відхилить запис із неіснуючим `device_id`, а перевіряє це через кеш або API домену `Devices`.

Далі з коду моноліта вилучаються всі SQL-запити, які виконують `JOIN` між таблицями моноліта та таблицями виділюваного модуля. Складний запит вида:

```sql
-- ЗАБОРОНЕНО: SQL JOIN через межу домену
SELECT d.name, d.model, t.temperature, t.timestamp 
FROM schema_monolith.devices d 
JOIN schema_telemetry.telemetry_readings t ON d.id = t.device_id 
WHERE d.owner_id = 42 AND t.timestamp > 1700000000;
```

замінюється на двокрокову композицію на прикладному рівні:

```sql
-- Крок 1: Отримати ID пристроїв з домену Devices
SELECT id, name, model FROM schema_monolith.devices WHERE owner_id = 42;

-- Крок 2: Отримати телеметрію через фасад TelemetryModule (у пам'яті або через RPC)
SELECT temperature, timestamp FROM schema_telemetry.telemetry_readings 
WHERE device_id IN (101, 105, 120) AND timestamp > 1700000000;
```

### Етап Б: Логічні схеми баз даних (Logical Schemas)

Замість негайного придбання та налаштування нового фізичного сервера БД, у поточній реляційній базі даних (наприклад, PostgreSQL) створюються окремі логічні схеми: `schema_monolith` та `schema_telemetry`.

Таблиці модуля телеметрії переносяться у `schema_telemetry`. Для коду моноліта створюється окремий користувач БД (`monolith_user`), якому **забороняється доступ** (`REVOKE ALL`) до таблиць `schema_telemetry`. Аналогічно, користувач `telemetry_user` отримує доступ лише до своєї схеми.

```sql
-- Ізоляція прав на рівні користувачів PostgreSQL
CREATE SCHEMA schema_telemetry;
ALTER TABLE telemetry_readings SET SCHEMA schema_telemetry;

-- Створення ізольованого користувача для нового мікросервісу
CREATE USER telemetry_service_user WITH PASSWORD 'secure_pass';
GRANT ALL PRIVILEGES ON SCHEMA schema_telemetry TO telemetry_service_user;
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA schema_telemetry TO telemetry_service_user;

-- Відкликання прав у користувача моноліта на таблиці телеметрії
REVOKE ALL ON SCHEMA schema_telemetry FROM monolith_user;
```

Цей крок миттєво виявляє всі замасковані SQL-запити, які намагалися прочитати «чужі» таблиці вхідними шляхами, й примушує розробників виконувати будь-яку взаємодію лише через виділений фасад.

### Етап В: Синхронізація даних (Dual Write / CDC)

Коли логічні схеми повністю ізольовані, виникає задача перенесення даних на окремий фізичний сервер БД нового мікросервісу. Оскільки зупиняти систему на багато годин для експорту/імпорту дампу заборонено бізнесом, застосовують один із двох механізмів синхронізації:

1. **Прикладне подвійне оновлення (Dual Write):** Модуль-шлюз у коді моноліта при надходженні нового запису пише дані спочатку в стару базу, а потім синхронно або асинхронно у базу нового сервісу. Головний ризик Dual Write — половинчасті відмови (Partial Failures), коли запис у першу БД пройшов, а в другу впав через мережеву помилку. Для мітигації цього ризику обов'язково запускається фоновий процес звірки (Reconciler Job), який шукає розходження й дозаписує дані.
2. **Change Data Capture (CDC):** Найбільш надійний інфраструктурний підхід без зміни коду запису. Спеціальний процес (наприклад, Debezium) зчитує транзакційний лог WAL (Write-Ahead Log) бази моноліта у режимі реального часу, ставить події зміни таблиць у Kafka, а консюмер нового мікросервісу матеріалізує ці дані у своїй базі.

```
[ Клієнт ] ──► [ Моноліт БД ] ──(WAL Log)──► [ Debezium / CDC ] ──► [ Kafka ]
                                                                       │
                                                                       ▼
[ Нова БД Сервісу ] ◄────── (Матеріалізація) ────────── [ New Service Consumer ]
```

Після того, як CDC-потік наздоганяє поточний час (реплікаційний лаг наблизився до кількох мілісекунд), обидві бази даних стають повністю синхронізованими, і новий сервіс готовий перебрати на себе навантаження.

## 3. Патерн Strangler Fig: поступове витіснення без Big Bang

Після підготовки шва в коді та логічної ізоляції даних настає фаза безпосереднього перенаправлення користувацького трафіку. Для цього застосовується патерн **Strangler Fig** («фікус-удушувач»). [Детальний історичний екскурс виникнення цього патерна від спостережень Мартіна Фаулера в австралійських лісах до сучасної інженерної практики](book:guide/progarch/monolith-vs-microservices/modular-monolith-to-services/hist-strangler-origin.md) показує, що головна ідея патерна — поступове обростання старого коду новим, поки старий не всохне й не буде вилучений.

![Чотири фази покрокової міграції від моноліта до мікросервісу](/root/course/progarch/modular-monolith-to-services/img/migration-phases.svg)
*Чотири фази трансформації: від моноліта в одному деплої до повністю автономного мікросервісу із власною БД.*

### Механіка роботи Strangler Fig на мережевій межі

Перед монолітом встановлюється розумний маршрутизатор (API Gateway, Nginx, Envoy або AWS API Gateway). 

```
                               ┌── (5% трафіку / Canary) ──► [ Новий Мікросервіс ]
[ Клієнт ] ──► [ API Gateway ] ┤
                               └── (95% трафіку) ──────────► [ Моноліт (Legacy) ]
```

Міграція здійснюється за п'ятьма фазами із використанням канарейкового розгортання (Canary Deployment):

1. **Фаза 0 (Темний запуск / Dark Launch):** Новий мікросервіс розгорнуто в продакшн-середовищі, але API Gateway спрямовує 100% трафіку на моноліт. Новий сервіс перевіряється синтетичними запитами healthcheck.
2. **Фаза 1 (Shadow Reads / Тіньові читання):** API Gateway або внутрішній фасад моноліта дублює 100% запитів на читання до нового мікросервісу асинхронно у фоні. Відповідь нового сервісу не повертається користувачу, але порівнюється з відповіддю моноліта спеціальним модулем-реконсилятором (Reconciler). Це дозволяє виявити розходження в логіці під повним навантаженням без жодного ризику для користувачів.
3. **Фаза 2 (Канарейкове перемикання 1% -> 5% -> 25%):** API Gateway починає спрямовувати малу частку реальних запитів (наприклад, за заголовком `X-Canary: true` або за хедшем `device_id % 100 < 5`) на новий мікросервіс. Відповідь нового сервісу стає офіційною для цієї групи користувачів. Детермінований роутинг за `device_id` гарантує, що той самий пристрій не стрибає між сервісом та монолітом при повторних запитах.
4. **Фаза 3 (Повне перемикання 100%):** Після підтвердження стабільності, відсутності помилок 5xx та сплесків p99 латентності, API Gateway переводиться у режим 100% роутингу на новий мікросервіс.
5. **Фаза 4 (Удушення та демонтаж):** Старий модуль всередині моноліта вимикається, його код видаляється з репозиторію, а логічна схема в базі даних моноліта видаляється (`DROP SCHEMA`).

### Механізм реконсиляції та анти-ентропії (Anti-Entropy Reconciler)

Під час тіньових читань та подвійного запису неминуче виникають розходження (Discrepancies) через мережеві затримки, плаваючі години або різні версії алгоритмів. Для обробки цих відхилень будується модуль **Anti-Entropy Reconciler**:

- **Порівняння відповідей:** Реконсилятор зрівнює JSON-дерева відповідей моноліта та нового сервісу, ігноруючи динамічні поля (UUID, `created_at`).
- **Логування невідповідностей:** Будь-яке розходження у бізнес-полях записується в лог з тегом `DISCREPANCY_DETECTED` та вимірюється лічильником Prometheus.
- **Автоматичне згладжування:** Якщо відсоток розходжень перетинає 0.1%, канарейка автоматично відкочується до 0%, а розробники отримують сповіщення з дампами обох відповідей.

[Повна практична реалізація конвеєра Strangler Fig із підтримкою Branch by Abstraction, канарейкового роутера та тіньового запису на мовах C та C++](book:guide/progarch/monolith-vs-microservices/modular-monolith-to-services/proj-strangler-migration.md) показує, як ця механіка втілюється у робочому коді без використання сторонніх важких фреймворків.

## 4. Контрактні тести: гарантія того, що дріт не зламає API

Коли виклик між модулями пересувається з пам'яті в мережу, виникає новий клас відмов — **розрив сумісності API (API Schema Breakage)**. Розробник нового мікросервісу може перейменувати поле `device_id` на `deviceId` або змінити формат дати з Unix Timestamp на ISO-8601, вважаючи це покращенням. Якщо монолітний код чекає на старий формат, десеріалізація впаде з помилкою в продакшні.

Традиційне unit-тестування не ловить ці помилки, бо моноліт використовує моки (Mocks) нового сервісу, які самі розробники забули оновити. Для вирішення цієї проблеми застосовують **контрактні тести на основі вимог споживача (Consumer-Driven Contracts, CDC)** та інструментарій **Pact**.

![Петля перевірки контрактних тестів у CI/CD](/root/course/progarch/modular-monolith-to-services/img/contract-test-gate.svg)
*Конвеєр контрактного тестування: Споживач генерує файл контракту в unit-тестах, а Провайдер підтверджує його сумісність у своєму CI/CD до виходу на прод.*

### Як працює контрактний CI/CD Gate

1. **Споживач (Моноліт) створює контракт:** Під час запуску unit-тестів моноліта спеціальний тест-клієнт робить запит до локального Pact-сервера й описує вимоги: *"Коли я роблю GET /api/v1/devices/105/telemetry, я очікую статус 200 та JSON, у якому поле `temperature` є числом з плаваючою крапкою"*. Фреймворк зберігає цей опис у файл контракту `monolith-telemetry-pact.json`.
2. **Публікація в Pact Broker:** Файл контракту надсилається в центральний реєстр — **Pact Broker**.
3. **Верифікація Провайдером (Новим сервісом):** Під час збірки нового мікросервісу у CI автоматично запускається інструмент `pact-provider-verifier`. Він зчитує контракт із Broker, піднімає локальний інстанс мікросервісу, відтворює записані запити й перевіряє, чи реальні відповіді відповідають очікувальним правилам (Matching Rules).
4. **Блокування деплою через `can-i-deploy`:** Перед виходом будь-якого із сервісів у продакшн у CI виконується команда:

```bash
pact-broker can-i-deploy \
  --pacticipant Telemetry-Microservice \
  --version $GIT_COMMIT \
  --to-environment production
```

Якщо новий мікросервіс містить несумісні зміни в API (Breaking Changes), команда повертає код `1`, і CI/CD конвеєр **автоматично заблокує деплой**, застерігши систему від аварії на продакшні.

[Повна технічна специфікація JSON-схеми Pact v3/v4, мапа сумісності API-змін, шаблони верифікації станів та CLI-інструкції](book:guide/progarch/monolith-vs-microservices/modular-monolith-to-services/api-contract-testing.md) винесені в окремий довідник.

## 5. Спостережуваність під час міграції (Observability & Traceability)

Поширеною небезпекою під час розпилу моноліта є втрата простежуваності (Traceability). У моноліті весь запит виконувався у межах одного потоку (Thread) з єдиним лог-контекстом. Щойно виклик перетинає мережу через API Gateway та проксі-шов, запит розпадається на кілька незалежних HTTP-викликів у різних сервісах. Якщо в цей момент станеться помилка, без наскрізної простежуваності знайти її причину буде практично неможливо.

Для збереження простежуваності під час використання патерна Strangler Fig впроваджуються три обов'язкових інструменти:

1. **Контекстний Correlation ID (OpenTelemetry Trace Parent):** API Gateway або шов у моноліті генерує унікальний ідентифікатор `traceparent` за стандартом W3C Trace Context (наприклад, `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`) і передає його у заголовках усіх HTTP/gRPC викликів.
2. **Метрики розподілу канарейки (Canary Metrics Dashboard):** У Prometheus / Grafana будується єдиний дашборд, який у реальному часі порівнює чотири золотих сигнали (Golden Signals) для монолітного модуля та нового мікросервісу:
   - Частота запитів (RPS).
   - Частка помилок (Error Rate 5xx).
   - Перцентилі затримки (p50, p95, p99).
   - Насиченість ресурсів (CPU, Memory, DB Connection Pool).
3. **Алерт на розходження порогових значень:** Якщо p99 латентності нового мікросервісу перевищує p99 моноліта на 20%, або помилки 5xx зростають вище 0.05%, канарейка автоматично скидається на 0% без участі людини (Automated Rollback).

## 6. Наскрізна розбір-хірургія на прикладі Digital Homes

Застосуємо всю сформовану покрокову стратегію до системи розумного дому **Digital Homes**.

На початковому етапі хмарний бекенд DH являє собою [модульний моноліт з дев'ятьма контекстами в одному деплої](book:progarch/modular-monolith-first): ідентичність, твін, керування, автоматизації, телеметрія, відео, сповіщення, білінг та хаб. Система обробляє телеметрію від 2 000 домів та 40 000 пристроїв.

Зі зростанням популярності платформи кількість датчиків у кожному домі виросла вдесятеро, а сталий потік запису телеметрії досяг 12 000 подій на секунду. Метрики моніторингу показали, що гарячий потік запису телеметрії починає вичерпувати пули з'єднань БД моноліта й негативно впливати на латентність читання реєстру пристроїв. **Спрацювала сигнальна розтяжка продуктивності**: контекст `Telemetry` визрів для винесення в окремий сервіс.

```
Digital Homes Моноліт (Початковий стан):
 1 Деплой ──► [ PostgreSQL ] (Спільні таблиці: devices, telemetry_events, users)

Digital Homes Після розпилу (Кінцевий стан):
 1 Моноліт (8 модулів) ──► [ PostgreSQL Monolith ] (devices, users, billing...)
            │
 (gRPC / HTTP API Gateway)
            │
            ▼
 1 Telemetry Service ────► [ TimescaleDB / ScyllaDB ] (telemetry_events)
```

### Хронологічна послідовність розпилу модуля Telemetry у Digital Homes

1. **Крок 1 (Шов у коді):** Розробники DH виділяють модуль `TelemetryModule` за інтерфейсом `ITelemetryRepository`. Всі прямі SQL-запити до таблиці `telemetry_events` з модуля `Automations` закриваються фасадом. Контролер перевірки залежностей в CI (ArchUnit) гарантує відсутність прямих імпортів.
2. **Крок 2 (Ізоляція логічної схеми):** У базі PostgreSQL створюється схема `schema_telemetry`. Видаляється зовнішній ключ `telemetry_events.device_id REFERENCES devices(id)`. Перевірка існування пристрою здійснюється в коді через кеш твінів у пам'яті. Права користувача моноліта обмежені (`REVOKE ALL ON SCHEMA schema_telemetry FROM monolith_user`).
3. **Крок 3 (Інфраструктурна реплікація CDC):** На базу моноліта підключається Debezium. Зміни з таблиці `telemetry_events` через Kafka реплікуються у нове спеціалізоване сховище часових рядів TimescaleDB нового сервісу телеметрії.
4. **Крок 4 (Написання контрактних тестів):** Для моноліта створюються Pact-тести, які описують контракти запиту телеметрії. Контракт `monolith-telemetry-service.json` публікується в Pact Broker.
5. **Крок 5 (Запуск канарейки Strangler Fig):** Новий контейнер `telemetry-service` розгортається в Kubernetes. AWS API Gateway переводить 5% трафіку телеметрії від хабів на новий сервіс за детермінованим хешем `device_id % 100 < 5`. Моноліт виконує тіньове читання (Shadow Read) для 95% решти трафіку та перевіряє збіг агрегованих графіків температур.
6. **Крок 6 (Повний Cutover та демонтаж):** Після 48 годин стабільної роботи канарейка розширюється до 100%. Прямі виклики старого модуля в моноліті вимикаються. Код модуля `Telemetry` та застаріла схема в монолітній БД видаляються (`DROP SCHEMA schema_telemetry CASCADE`).

В результаті сервіс `Telemetry` отримав власний інфраструктурний стек, здатний масштабуватися незалежно, а моноліт Digital Homes позбувся гарячого потоку запису, зберігши при цьому цілісність решти 8 контекстів.

## 7. Фінал: розпил як керована дисципліна

Виділення мікросервісу з модульного моноліта — це не порив емоцій і не відданина моді, а сувора, вимірювана інженерна дисципліна. Спроба розрізати систему поспіхом без підготовки швів та ізоляції даних неминуче приносить усю складність мережі, позбавляючи переваг автономності.

Ключові правила розпилу без розриву:
- **Спочатку шов у коді, потім мережа:** Ніколи не винось модуль на мережу, поки його інтерфейси не очищені всередині моноліта за патерном Branch by Abstraction.
- **Ізоляція даних передує ізоляції коду:** Приберіть cross-domain JOINs та зовнішні ключі до того, як розрізати процеси.
- **Невеликі оборотні кроки замість Big Bang:** Застосовуйте Strangler Fig та канарейкове перемикання трафіку з тіньовими читаннями та реконсиляцією.
- **Автоматизований контроль контрактів:** Використовуйте Consumer-Driven Contracts в CI/CD для унеможливлення поломки API під час міграції.
- **Наскрізна спостережуваність:** Проводьте Correlation ID крізь усі межі та відкочуйте канарейку автоматично при зростанні помилок.

Дотримуючись цієї покрокової стратегії, архітектор перетворює небезпечний розпил моноліта на серію передбачуваних, повністю оборотних кроків, гарантуючи безперервний розвиток продукту та спокій команди.
