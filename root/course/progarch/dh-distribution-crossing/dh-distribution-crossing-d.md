# DH перетинає межу машини

<preknowlist>
- [DH як порти й адаптери](root:progarch/dh-v2-hexagon) — усередині хаба логіка спілкується зі світом через **порти** (інтерфейси), а конкретне «як саме» ховає **адаптер**; зв'язок «хаб → хмара» уже був таким портом.
- [Шов як точка зміни](root:progarch/seams-and-boundaries) — **шов** — це місце, де один бік можна підмінити, не чіпаючи іншого; саме по швах систему й розрізають на частини.
</preknowlist>

Наприкінці минулого кроку ми дали собі обіцянку: пустити **весь** хаб через межу машини по-справжньому. Досі ми зробили чесним [один замок](root:progarch/dh-bad-network) — одну команду, обв'язану таймаутом, повтором і ключем ідемпотентності. Це була латка на конкретну болячку. Але Digital Homes — не один замок. Це хаб, повний пристроїв і правил; хмара в дата-центрі; застосунок у кишені; чужі хмари вендорів. І питання засновника, з якого все почалося, тепер росте разом із системою: уже не «чи зачинився цей замок?», а «чи хмара взагалі знає правду про цей дім?».

Тут криється пастка, у яку легко впасти. Здається, що «перейти межу машини» — це технічна дрібниця: підняти сервер, відкрити порт, і хай собі шлють запити. Насправді це не рядок мережевого коду, а **пучок архітектурних рішень**: де саме прокласти межу, куди зібрати всю мережеву чесність, як по-різному повестися з різними течіями трафіку і що робити з тим, що правда про дім тепер живе у двох місцях одночасно. Цей крок — про те, як усі окремі прийоми модуля складаються в одну **поставу** системи, що чесно живе з мережею. Почнімо з несподіванки: більшу частину роботи ми вже зробили, самі того не помітивши.

## Межа вже була швом — ми лише не бачили її фізики

Пригадаймо, що [хаб зібрано як гексагон](root:progarch/dh-v2-hexagon): його логіка не викликає хмару напряму, а звертається до **порту** — інтерфейсу на кшталт «надішли звіт», «забери команди». У версії v2 за цим портом стояв простенький адаптер, що жив у тому ж процесі. І ось головне усвідомлення: «перейти межу машини» для цього порту — це **не переписати логіку**, а написати для нього **новий адаптер**, який кладе байти в мережу замість того, щоб гукнути сусідній об'єкт. Шов лишається там, де був. Змінюється **фізика за швом**.

![Ліворуч — один процес: логіка хаба через порт кличе хмару-порт, це виклик функції, все-або-нічого, дешево. Праворуч — та сама логіка й той самий порт, але за портом лягла межа машини й хмара стала іншою машиною; за портом тепер висять таймаут, повтор, ключ, часткова відмова](/root/course/progarch/dh-distribution-crossing/img/seam-boundary.svg)
*Форма порту не змінюється — логіка й далі кличе «надішли звіт». Змінюється те, що стоїть за ним: був сусідній об'єкт у спільній пам'яті, стала інша машина через мережу з усіма її податками.*

Оце і є винагорода за всю ту роботу з межами, яку ми робили сторінками раніше. Ми різали систему по швах не заради краси діаграм, а рівно заради цієї миті: коли один зі швів мусить стати мережею, код над ним майже нічого не помічає, бо взаємодіє з портом тієї самої форми. Порт готовий; треба лише інший адаптер.

Але «тієї самої форми» — це водночас і найбільша брехня, яка тут можлива. Той самий підпис методу приховує **зовсім іншу тварину**: локальний виклик або повертає, або кидає — а виклик крізь мережу додає третю долю, [тишу, яку ми вже назвали часткою відмови](root:progarch/partial-failure). Спокуса вдати, що віддалений виклик — це просто трохи повільніший локальний, і є [першою з оман розподілених обчислень](book:programming/distributed-fallacies); за неї платять негайно. Тому форма порту лишається невинною, а вся правда про мережу мусить оселитися **за** ним — у новому адаптері. Подивімось, як він виглядає:

:::tabs
```ts
// Порт — та сама форма, що й у гексагоні v2. Логіка хаба знає лише його.
interface CloudLink {
  send(cmd: Command): Promise<Result>;
}

// Адаптер v2: сусід у тому ж процесі. Дві долі — повернув або кинув.
class InProcessCloud implements CloudLink {
  send(cmd: Command) { return this.cloud.handle(cmd); }   // все-або-нічого
}

// Адаптер за межею машини: та сама форма, але за нею — мережа.
// Уся чесність зібрана ТУТ, логіка над портом її не бачить.
class NetworkCloud implements CloudLink {
  async send(cmd: Command): Promise<Result> {
    const key = cmd.id;                    // один ключ на команду — крізь усі повтори
    const deadline = monotonic() + 10_000; // бюджет часу: чекання зі стелею
    return withRetries(deadline, () =>     // повтор із відступом + розкидом
      this.http.post("/cmd", cmd, key, deadline));   // а дублі впізнає бік хмари
  }
}
```
```go
// Порт — та сама форма, що й у гексагоні v2. Логіка хаба знає лише його.
type CloudLink interface {
	Send(ctx context.Context, cmd Command) (Result, error)
}

// Адаптер v2: сусід у тому ж процесі. Дві долі — значення або помилка.
type InProcessCloud struct{ cloud *Cloud }
func (c InProcessCloud) Send(ctx context.Context, cmd Command) (Result, error) {
	return c.cloud.Handle(cmd) // все-або-нічого
}

// Адаптер за межею машини: та сама форма, але за нею — мережа.
// Уся чесність зібрана ТУТ, логіка над портом її не бачить.
type NetworkCloud struct{ http *Client }
func (c NetworkCloud) Send(ctx context.Context, cmd Command) (Result, error) {
	ctx, cancel := context.WithTimeout(ctx, 10*time.Second) // бюджет часу
	defer cancel()
	return withRetries(ctx, func() (Result, error) {         // повтор з відступом
		return c.http.Post(ctx, "/cmd", cmd, cmd.ID)         // ключ = cmd.ID
	})
}
```
:::

> 🔧 **Навіщо це.** Коли постає питання «а що з нашого монолітного хаба першим піде за мережу?» — відповідь не «те, що технічно легше винести», а **той шов, який уже прорізаний чисто**, тобто оформлений портом. Якщо частина спілкується з рештою через вузький інтерфейс — її можна віддати за межу машини, підмінивши адаптер, і код над портом не здригнеться. Якщо ж виклики до неї розсипані по всій логіці голими зверненнями — спершу зроби з них порт, а вже потім став межу. Порядок саме такий: спочатку шов, потім мережа.

## Чесність — не латка на виклик, а постава адаптера

У кроці про поганий Wi-Fi ми обв'язали таймаутом, повтором і ключем **одну** команду, вручну. Уяви тепер, що так треба зробити з кожним викликом, який перетинає межу: у кожному місці коду згадати про бюджет, згенерувати ключ, накрутити цикл повторів. Це не лише марудно — це **розповзається**: десь забули розкид, десь поставили таймаут, довший за бюджет того, хто нас кличе, десь згенерували новий ключ на кожну спробу й тим зламали дедуплікацію. Розсипаний по call-site прийом рано чи пізно розсинхронізується сам із собою.

Вихід ми вже, по суті, намалювали на схемі: зібрати всю мережеву чесність **в одному місці** — в адаптері за портом. Логіка над портом і далі пише простодушне `cloud.send(cmd)`, ніби виклик локальний; а `NetworkCloud` бере на себе [бюджет часу](book:programming/timeouts-deadlines), [повтор із відступом](book:programming/retries-backoff) та [ключ ідемпотентності](book:programming/idempotency) — так, що жоден виклик крізь межу не проходить без цієї трійці. Три рухи, які в минулому кроці були латкою на замок, стають **звичною поставою всього, що йде за межу**. Це і називають політикою на межі: не «кожен пам'ятає», а «межа знає».

> 🔧 **Навіщо це.** Якщо в код-рев'ю ти бачиш ретрай-цикли й таймаути, розкидані по десятку сервісів і хендлерів, — це запах. Мережева політика хоче жити не в кожному виклику, а в **одному адаптері** (чи вузькому шарі — sidecar, клієнт-обгортка), який володіє нею на весь напрям. Тоді змінити відступ чи час-стелю — це одна правка, а не полювання по всій кодовій базі; і новий виклик через межу отримує чесність задарма, бо вона вбудована в дорогу, а не дописується щоразу.

## Одна межа — дві течії з протилежною поставою

Досі ми говорили про межу так, ніби весь трафік крізь неї однаковий. Але придивись до того, що насправді тече між домом і хмарою, — і побачиш **дві різні течії**, яким потрібне протилежне.

Перша — **команда**: «зачини», «відчини для гостя», «додай яскравості». Її пускає людина й тут-таки дивиться на крутилку в застосунку. Отже, тут важить бюджет часу (хтось чекає), важить [доставка «фактично раз»](book:programming/delivery-guarantees) — ключ плюс дедуп на боці виконавця, щоб повтори не задвоїли дію, — і чесний таймаут, коли відповіді нема. Команда за своєю природою тягнеться до **синхронності**: спитав — чекаю відповідь.

Друга течія — **звіт**: температура 21°, замок зачинено, датчик живий. Цього — потоком, десятки разів на хвилину, і **ніхто на нього не чекає**, живій людині байдуже до кожного окремого відліку; хмарі потрібна лише **остання правда**. Звідси зовсім інша постава. Тут доречна доставка [«щонайменше раз»](book:programming/delivery-guarantees) з дедупом за ключем; тут [порядок не гарантований](root:progarch/duplicates-and-reorder) — пізніший замір може дійти раніше за ранній, — тож «яка правда свіжіша» вирішує **власна мітка часу відліку**, а не порядок прибуття пакетів. І найважливіше: коли хмара мовчить, хаб не має ані падати, ані блокуватися — він **складає звіти в локальний буфер і досилає потім**. Тобто звіт тяжіє до **асинхронності**: віддав у чергу — і живи далі.

![Одна пунктирна межа машини між домом і хмарою. Згори червона стрілка від хмари до хаба — КОМАНДА «зачини/відчини», під нею плашка: бюджет часу, ключ ідемпотентності, доставка «фактично раз». Знизу синя стрілка від хаба до хмари — ЗВІТ «температура, стан замка», під нею плашка: «щонайменше раз», дедуп за ключем, терпить переупорядкування, буфер, поки хмара мовчить](/root/course/progarch/dh-distribution-crossing/img/two-paths.svg)
*Та сама межа, дві протилежні постави. Команда синхронна, з бюджетом і «фактично раз», бо на неї чекають. Звіт асинхронний, «щонайменше раз» і терпить безлад, бо потрібна лише остання правда, а не кожен окремий пакет.*

Отут абстрактний [вибір «синхронно проти асинхронно»](root:progarch/sync-vs-async-fundamental) перестає бути теорією й стає двома конкретними доріжками через один і той самий кордон. Не буває «система синхронна» чи «система асинхронна» — буває, що **команда лягла синхронно, а звіт асинхронно**, і межа спокійно тримає обидві течії, бо для кожної обрано свою гарантію.

## Межу проводять там, де важливе лишається на одному боці

Ми обрали, що виносити (шов-порт) і як обв'язати кожну течію. Лишилося рішення, яке важить чи не найбільше, — **де саме** прокласти лінію відносно того, без чого дім не дім.

Придивись до найпростішого й найважливішого сценарію: людина тисне кнопку на стіні, і замок відчиняється. Якщо ця дія піде в подорож — кнопка → хаб → **хмара** → назад до хаба → замок, — то поганий Wi-Fi чи впала хмара залишать людину під власними дверима. Виходить, лінію не можна вести так, щоб **життєвий контур** перетинав ненадійний канал. Її ведуть навпаки: кнопка → хаб → замок замикається **цілком удома**, ні разу не торкнувшись межі; а хмара сидить по той бік кордону й лише **збагачує** — статистика, віддалений доступ, історія, — але контур від неї не залежить.

![Велика рамка «ДІМ»: кнопка на стіні → хаб → замок, зв'язані зеленими стрілками в пунктирному контурі з підписом «контур замикається без мережі». Праворуч за пунктирною межею машини — хмара з підписом «збагачення, не залежність», з'єднана з хабом тонкою лінією, яку перетинає хрестик на межі. Унизу: «Хмара впала? Контур удома все одно замикається»](/root/course/progarch/dh-distribution-crossing/img/vital-loop.svg)
*Життєвий контур кнопка → хаб → замок лежить цілком на домашньому боці й не перетинає межу. Хмара — по той бік, як збагачення; розрив зв'язку (хрестик) її відрізає, але контур удома замикається однаково.*

Помічаєш, що сталося з [деградацією з гідністю](book:programming/graceful-degradation)? Раніше вона звучала як окремий прийом — «на випадок відмови припни запасну гілку». А тут вона перестала бути гілкою `catch` і стала **структурою**: дім переживає смерть хмари не тому, що ми дописали обробник, а тому, що провели межу так, аби вітальне ніколи не залежало від її перетину. Найкраща обробка часткової відмови — та, якої не треба писати, бо важливий шлях просто не ходить через частину, що падає.

> 🔧 **Навіщо це.** Про кожну функцію, яку кладеш у систему з мережею, спитай одне: **по який бік межі** живе її критичний шлях? Якщо вітальна дія потребує кругового рейсу через канал, що може впасти, — межу проведено не там. Іноді ліки — перенести трохи логіки чи стану на «домашній» бік, щоб контур замикався локально, а хмара лишалася приємним, але необов'язковим доважком. Це рішення про **розміщення**, і воно набагато потужніше за будь-який ретрай.

## Один стан на одній машині — три стани на двох

І ось найглибший наслідок переходу межі, який змінює саме мислення про систему. Поки все жило на одній машині, «стан замка» був **одним** значенням в одній пам'яті: подивився — і знаєш. Тепер правда про замок роздвоюється, ба навіть **розтроюється**. Удома живе **справжній** стан — те, як реле стоїть насправді. У хмарі живуть два здогади: **бажаний** стан — те, яким хмара хоче бачити замок, — і **востаннє почутий** — те, що вона востаннє про нього чула. І в будь-яку мить ці троє можуть не збігатися: звіт іще летить, команда ще не долетіла, канал упав посеред обміну.

![Ліворуч, у домі, — джерело правди: справжній стан ЗАЧИНЕНО (зелене). Праворуч, у хмарі, — два здогади: бажаний ЗАЧИНЕНО і востаннє почутий ВІДЧИНЕНО о 10:02 (застаріле, бурштинове). Через межу машини — дві фонові стрілки звірки: униз «надсилай бажаний, доки не збіжеться», угору «перечитуй справжній»; підпис «зерно твіна дому»](/root/course/progarch/dh-distribution-crossing/img/desired-reported.svg)
*Одне значення на одній машині стало трьома на двох. Хмара не бачить справжнього стану — лише бажане й востаннє почуте; вони розходяться з домом і сходяться назад не миттєво, а фоновою звіркою.*

**Приклад: як розходяться і сходяться три стани.** Простежмо один замок у часі, коли на секунду просів Wi-Fi:
```
момент   справжній(дім)   бажаний(хмара)   востаннє почутий(хмара)
t0       зачинено         зачинено         зачинено          ← усі згодні
t1       —                відчинено        зачинено          застосунок хоче «відчинити»
t2       відчинено        відчинено        зачинено          хаб виконав; звіт іще не дійшов
t3       відчинено        відчинено        зачинено          Wi-Fi просів — звіт у буфері
t4       відчинено        відчинено        відчинено         зв'язок вернувся, буфер долетів → сходяться
```
Між t2 і t4 хмара **помиляється** про дім — і це не баг, а норма життя за межею. Питання не в тому, щоб помилки не було (її не уникнути, канал ненадійний), а в тому, щоб система **сходилася** щоразу, коли зв'язок дозволяє.

Тому хмара кидає марну спробу тримати «правду» й натомість тримає лише бажане й востаннє почуте, а збіг доганяє **у фоні**: доти, доки почуте не дорівнює бажаному, тихенько дошли команду; час від часу перепитай справжній стан. Не миттєва обіцянка — а рефлекс звірки:

:::tabs
```ts
// Фоновий рефлекс звірки: не гарантія, а наполегливість.
async function reconcile(link: CloudLink, twin: Twin) {
  if (twin.reported !== twin.desired) {           // хмара й дім розійшлися
    await link.send(setState(twin.id, twin.desired));  // дошли бажане (ідемпотентно!)
  }
  twin.reported = await link.read(twin.id);       // перечитай справжній стан
}
```
```go
// Фоновий рефлекс звірки: не гарантія, а наполегливість.
func Reconcile(ctx context.Context, link CloudLink, twin *Twin) error {
	if twin.Reported != twin.Desired {                    // хмара й дім розійшлися
		if _, err := link.Send(ctx, SetState(twin.ID, twin.Desired)); err != nil {
			return err                                    // дошли бажане (ідемпотентно!)
		}
	}
	twin.Reported = link.Read(ctx, twin.ID)               // перечитай справжній стан
	return nil
}
```
:::

Цей об'єкт, що тримає «бажане» й «востаннє почуте» замість справжнього стану, — зерно [цифрового близнюка](root:progarch/dh-replicas) (англ. *twin* — близнюк): копії дому в хмарі, яка ганяється за оригіналом і ніколи не збігається з ним точно. А те, що дві копії одних даних розходяться, а тоді доганяють одна одну у фоні, — це і є [кінцева узгодженість](book:programming/eventual-consistency); ми щойно вивели її потребу власними руками з одного замка на поганому Wi-Fi, і далі курс візьме її вже як окрему велику тему. Повний робочий межовий адаптер — з обома течіями, локальним буфером звітів, дедупом і циклом звірки, а ще з тестом, що глушить хмару посеред потоку й показує, як контур удома не здригнувся, а звіти долетіли фактично раз, коли зв'язок вернувся, — зібрано в [проєкті межового адаптера](root:progarch/dh-distribution-crossing/proj-boundary-adapter.md).

## Що тепер у руках

Оглянься на весь модуль — і побачиш, що омани розподілених обчислень, часткова відмова, таймаути, повтори, ідемпотентність, гарантії доставки, дублі й переупорядкування ніколи не були сімома окремими трюками. Це одна **постава** межі, яка чесна щодо того, що вона — мережа, а не пам'ять.

А остання річ, яку ми взяли в руки, — що стан тепер живе у копіях, які розходяться, — це вже не кінець, а двері. Бо щойно даних стало **дві копії, що дрейфують**, постає ціле нове коло питань: хто з них головний, як їх мирити, коли вони конфліктують, і що взагалі означає «узгоджено», коли машин багато. Саме з цих дверей починається наступний модуль — про реплікацію й моделі консистентності.
