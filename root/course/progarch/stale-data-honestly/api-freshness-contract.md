# 📋 Контракт та специфікація метаданих свіжості API

Ця інструктивна специфікація визначає стандартний контракт передачі метаданих свіжості (*freshness metadata*) між сервером, проксі-шаром та клієнтськими застосунками. Вона забезпечує єдину мову опису часового лагу, джерел даних та стану деградації як на рівні HTTP-заголовків, так і всередині обгортки (конверта) тіла відповіді JSON.

У розподілених архітектурах, де дані проходять через ланцюжки реплікації, кешуючі проксі, реляційні БД та нозоподібні проєкції, клієнт не може здогадатися про реальний вік об'єкта лише з факту отримання HTTP 200 OK. Специфікація стандартизує передачу міток часу, обчислення лагу та класифікацію стану застарілості.

## 1. HTTP-заголовки для управління свіжістю та деградацією

Для стандартних кешуючих проксі (CDN, Edge Gateway, NGINX, Varnish) та протокольних HTTP-клієнтів передача стану свіжості здійснюється через заголовок `Cache-Control` з розширеннями специфікації RFC 5861, а також супутні мета-заголовки часових міток:

- `Cache-Control: max-age=60, stale-while-revalidate=300, stale-if-error=86400`:
  Вказує проксі та браузеру, що відповідь вважається абсолютно свіжою 60 секунд. Протягом наступних 300 секунд (вікно `stale-while-revalidate`) кеш має право миттєво віддати застарілу копію клієнту, паралельно ініціювавши асинхронний запит оновлення до джерела. Якщо джерело повертає помилку `5xx` або недоступне по мережі, заголовок `stale-if-error` дозволяє віддавати застарілий об'єкт до 24 годин (86400 секунд).

- `Age: 142`:
  Стандартний заголовок HTTP/1.1, що показує тривалість перебування відповіді у проміжних кешах у секундах від миті згенерованого сервером origin відповіді.

- `Warning: 110 response-cache "Response is Stale"`:
  Попереджувальний заголовок HTTP/1.1 (код 110), що сигналізує клієнтському застосунку та інспекційним утилітам про те, що отримана відповідь була згенерована з застарілого кешу або резервної копії.

- `X-Data-Timestamp: 2026-08-18T09:30:00.000Z`:
  Точна монотонна UTC ISO-8601 часова мітка створення або останнього вимірювання даних у первинному сховищі правди (наприклад, час фізичного зняття показу давача чи виконання транзакції у БД-майстер).

- `X-Replication-Lag-Ms: 4500`:
  Поточний обчислений лаг реплікації або затримка між первинним записом та зчитуванням з читацької проєкції у мілісекундах на момент формування відповіді.

Механіка роботи цих заголовків спирається на прозору каскадну передачу: Edge-шлюз перевіряє заголовок `X-Data-Timestamp`, обчислює різницю з поточним часом сервера origin та формує заголовок `Warning: 110`, якщо лаг перевищує поріг свіжості.

## 2. Специфікація обгортки (конверта) свіжості у JSON-відповіді

Для REST, GraphQL та gRPC-over-HTTP сервісів, які повертають складні DTO, метадані свіжості інтегруються безпосередньо у обгортку JSON-структури на верхньому рівні відповіді. Це дозволяє передавати доменну інформацію разом із часовим контекстом навіть крізь не-HTTP проксі або WebSocket-канали.

### 2.1. Формат об'єкта метаданих `freshness`

Об'єкт `freshness` містить повний набір полів, необхідних клієнтському кеш-менеджеру для вибору режиму візуалізації:

```json
{
  "data": {
    "device_id": "dh-sensor-042",
    "temperature": 21.8,
    "humidity": 45.2
  },
  "freshness": {
    "data_timestamp": "2026-08-18T09:40:00.000Z",
    "fetched_at": "2026-08-18T09:40:45.000Z",
    "lag_ms": 45000,
    "ttl_seconds": 60,
    "state": "STALE_ACCEPTABLE",
    "is_degraded": false,
    "staleness_reason": "REVALIDATING_IN_BACKGROUND",
    "source": "READ_PROJECTION_REPLICA_2"
  }
}
```

### 2.2. Семантика станів свіжості (`freshness.state`)

Класифікація стану свіжості здійснюється API-шлюзом або клієнтським кеш-менеджером на основі порівняння лагу `lag_ms` із налаштованим SLA ресурсу:

- `FRESH`: Дані повністю актуальні. Лаг знаходиться у межах строгого SLA свіжості, значення `lag_ms` не перевищує допустимий поріг `ttl_seconds`. Клієнт відображає дані у стандартному режимі без додаткових підказок чи зауважень.
- `STALE_ACCEPTABLE`: Дані застаріли, але знаходяться у допустимому вікні грації (`stale-while-revalidate`). Клієнтський застосунок відображає дані зі стандартним UI, проте фоновий процес кешу ініціює перезавантаження об'єкта по мережі.
- `STALE_DEGRADED`: Дані застаріли понад стандартний SLA, фонова реплікація зупинилася або сервер джерела перебуває під високим навантаженням. Клієнт зобов'язаний перейти у режим деградації: відобразити приглушені кольори (muted opacity) та додати візуальний бейдж «Дані застаріли».
- `EXPIRED_FALLBACK`: Дані повністю протухли, проте повертаються з резервного локального snapshot-сховища через абсолютну недоступність джерела. Клієнт переходить у режим «Офлайн-архів» та блокує небезпечні управляючі дії.

## 3. Гранулярні (per-field) метадані свіжості для композитних DTO

У складних дашбордах або агрегованих проєкціях (наприклад, загальний стан розумного дому чи зведений аналітичний звіт) різні поля одного JSON-об'єкта можуть надходити з різних сервісів та давачів із радикально відмінним лагом. Наприклад, статус охоронної сигналізації надходить із радіохаба з лагом 200 мілісекунд, тоді як показник кімнатної температури передається батарейним сенсором раз на 10 хвилин.

Злиття цих даних в один голий JSON-об'єкт створює невизначеність: якщо позначити весь об'єкт як застарілий, користувач вирішить, що й охорона не працює. Якщо позначити весь об'єкт як свіжий, користувач повірить застарілій температурі.

Для розв'язання цієї проблеми використовується мета-покажчик `_field_freshness`, який описує індивідуальні мітки часу для кожного критичного поля DTO:

```json
{
  "home_id": "dh-home-88",
  "security_mode": "ARMED",
  "climate": {
    "target_temp": 22.0,
    "current_temp": 24.1
  },
  "_field_freshness": {
    "security_mode": {
      "data_timestamp": "2026-08-18T09:40:50Z",
      "lag_ms": 400,
      "state": "FRESH"
    },
    "climate.current_temp": {
      "data_timestamp": "2026-08-18T09:35:00Z",
      "lag_ms": 350000,
      "state": "STALE_DEGRADED",
      "reason": "SENSOR_OFFLINE_BATTERY"
    }
  }
}
```

Клієнтський UI використовує `_field_freshness` для точкового приглушення окремих віджетів на екрані: статус охорони залишається яскраво-зеленим, тоді як індикатор температури набуває приглушеного сірого кольору з підказкою «Оновлено 5 хвилин тому».

## 4. Контракт деградованого режиму та специфікація помилок

При виникненні аварій на боці upstream-сервісів або бази даних API-шлюз ухвалює одне з двох рішень щодо контракту відповіді:

1. **Відповідь із застарілим кешем (HTTP 200 OK або HTTP 203 Non-Authoritative Information):**
   - Додається HTTP-заголовок `Warning: 110 "Response is Stale"`.
   - В обгортці `freshness` прапорець `is_degraded` встановлюється в `true`.
   - Поле `staleness_reason` містить машинозчитуваний код причини (`UPSTREAM_TIMEOUT`, `DB_REPLICA_LAG_EXCEEDED`).

2. **Відмова у викачці з підказкою про наявність локального знімка (HTTP 503 Service Unavailable):**
   - Використовується формат RFC 9457 (*Problem Details*). Сервер явно каже, що читацька проєкція не здатна забезпечити потрібний SLA, але підказує клієнту про наявність застарілого знімка:

```json
{
  "type": "https://api.digitalhomes.io/errors/read-model-unavailable",
  "title": "Read Model Projection Unavailable",
  "status": 503,
  "detail": "The primary read projection is lagging by 600s. Cached snapshot is available.",
  "instance": "/homes/88/telemetry",
  "stale_fallback_available": true,
  "max_available_snapshot_age_s": 1200
}
```

При отриманні такої відповіді 503 клієнтський кеш-менеджер не демонструє фатальний факел помилки, а витягає з локального IndexedDB/SQLite останній збережений snapshot і переводить екран у режим «Офлайн-архів».

## 5. Обробка зсуву годинників (Clock Skew Mitigation)

При обчисленні `lag_ms` на клієнті принциповою проблемою є розходження системного часу смартфона й сервера origin. Якщо годинник користувача поспішає на 3 хвилини, обчислене значення `lag_ms` стане від'ємним чи неадекватно великим.

Специфікація вимагає від клієнтського кеш-менеджера виконувати вирівнювання годинників:

```
Server_Date_Header = ParseHTTPHeader("Date")
Client_Receive_Time = Now()
Clock_Offset = Client_Receive_Time - Server_Date_Header
Adjusted_Now = Current_Client_Time() - Clock_Offset
Lag_Ms = Adjusted_Now - Envelope.DataTimestamp
```

Це гарантує, що оцінка свіжості залишається коректною незалежно від налаштувань часового поясу чи раптового зсуву годинника на пристрої користувача.
