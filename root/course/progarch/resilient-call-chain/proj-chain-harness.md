# ⚙️ Стенд: полічити шторм і загасити його

Ми не раз сказали: наївний ланцюг перетворює один клік на двадцять сім ударів по дну, а дисципліна кладе і кількість викликів, і хвіст затримки додолу. Це легко проголосити — і важко відчути, поки числа лишаються словами. Тож зберімо маленький стенд, який ці числа **друкує**, і в який можна тицьнути пальцем: покрутити кволість C, увімкнути один охоронець за одним і побачити, як два лічильники їдуть униз.

Стенд навмисне крихітний і **без справжньої мережі**. C — це ручка, яку ми самі робимо кволою (частина викликів падає) і повільною (частина залипає надовго). З іншого кінця виходять рівно два числа, ті самі, за якими судять живий сервіс: **скільки викликів дісталось до C** і **p99 наскрізної затримки** — тобто затримка, гірша за яку лишається одному запиту зі ста. Спершу проженемо наївний ланцюг і побачимо шторм; тоді ввімкнемо охоронців і побачимо, як він гасне.

## Ідея: час — це число

Головна хитрість стенда — **не спати по-справжньому**. Якби кожна модельна затримка була справжнім `setTimeout` чи `time.Sleep`, прогін десяти тисяч запитів тривав би хвилини, залежав би від планувальника й давав щоразу інший p99. Тому час у стенді — це просто **число**: віртуальний годинник `now`, який кожен охоронець посуває вперед рівно на стільки, скільки «коштувала» його робота. Так мільйон запитів проганяється за мить, а p99 виходить той самий від запуску до запуску.

> 🔧 **Навіщо це.** Модельний час дає дві речі, яких немає в реальному прогоні: **відтворюваність** (те саме насіння — ті самі числа, тож «до» і «після» справді порівнянні) і **швидкість** (можна прогнати стільки запитів, щоб p99 був статистично чесний, а не «на око по десятьох»). Ціна — стенд не ловить справжніх гонок за потоки; але штука, яку ми міряємо — множення викликів і роздування хвоста — це властивість **лічби**, і вона видно й на модельному годиннику.

Той самий віртуальний годинник — **монотонний** за побудовою: лічильник тільки росте. Це не дрібниця, а натяк на реальність. У бою «зараз» беруть **не** зі стінного годинника: `Date.now()` у JS чи стінне значення `time.Now()` у Go можуть смикнутися назад, коли NTP підправить час, — і тоді `дедлайн − зараз` раптом стане від'ємним на цілком живому запиті. Для вимірювання тривалості беруть монотонне джерело: `performance.now()` у JS, а в Go — те, що `time.Now()` носить усередині монотонний відлік, і `time.Since`/`time.Until` та віднімання часів користуються **саме ним**. Наш лічильник моделює цей монотонний годинник напряму.

І ще одне, що закладаємо з першого рядка: результат кожної спроби несе прапорець **«чи варто мене повторювати»**. Це той самий сигнал, що [на одному чесному виклику](root:progarch/dh-bad-network) відрізняє минущий збій (таймаут, «сервіс перевантажений») від відповіді по суті («поганий запит», «не знайдено»). Далі побачимо, що саме цей прапорець, який тече **вгору** по ланцюгу, і не дає повторам бити в стіну.

Ось кістяк моделі: годинник, детермінований генератор, лічильник викликів на C і сама квола залежність.

:::tabs
```ts
// ── Стенд: усе детерміноване, час — це число, а не реальний сон ──
// Віртуальний МОНОТОННИЙ годинник. now і deadline — модельні мілісекунди.
type Ctx = { now: number; deadline: number };

// Детермінований генератор — щоб «27» і p99 повторювались від прогону до прогону.
let seed = 1;
const rnd = () => (seed = (seed * 1103515245 + 12345) & 0x7fffffff) / 0x7fffffff;

let cCalls = 0;          // ЄДИНА метрика навантаження на дно ланцюга
let sick = false;        // драйвер вмикає «інцидент» на частину запитів

// Результат несе сигнал «чи варто мене повторювати» — він потече ВГОРУ по ланцюгу.
type Ok  = { ok: true;  value: string; latency: number };
type Err = { ok: false; kind: string; retryable: boolean; latency: number };
type Res = Ok | Err;
type Call = (ctx: Ctx) => Promise<Res>;

// ── C — квола й подеколи повільна залежність ──
// Здоровий: 5% помилок, зрідка залипає. Хворий: 90% помилок, залипає часто.
const rawCallC: Call = async (_ctx) => {
  cCalls++;
  const pFail = sick ? 0.90 : 0.05;
  const pSlow = sick ? 0.70 : 0.01;
  const latency = rnd() < pSlow ? 600 : 20;      // модель, НЕ реальний сон
  if (rnd() < pFail) return { ok: false, kind: "overloaded", retryable: true, latency };
  return { ok: true, value: "camera-frame", latency };
};
```
```go
// ── Стенд: усе детерміноване, час — це число, а не реальний сон ──
// Віртуальний МОНОТОННИЙ годинник. Now, Deadline — модельні мілісекунди.
type Clock struct{ Now, Deadline int }

// Спроба повертає значення + скільки коштувала (для таймаута й p99).
type Result struct {
	Value   string
	Latency int
}

// Помилка несе сигнал «чи варто повторювати» — він тече ВГОРУ по ланцюгу.
type Failure struct {
	Kind      string
	Retryable bool
}

func (f *Failure) Error() string { return f.Kind }

func retryable(err error) bool {
	var f *Failure
	if errors.As(err, &f) {
		return f.Retryable
	}
	return err != nil // невідому помилку вважаємо минущою
}

type Call func(cl *Clock) (Result, error)

// Детермінований генератор — щоб «27» і p99 повторювались.
var seed int64 = 1

func rnd() float64 {
	seed = (seed*1103515245 + 12345) & 0x7fffffff
	return float64(seed) / float64(0x7fffffff)
}

var cCalls int  // ЄДИНА метрика навантаження на дно ланцюга
var sick bool   // драйвер вмикає «інцидент» на частину запитів

// ── C — квола й подеколи повільна залежність ──
func rawCallC(_ *Clock) (Result, error) {
	cCalls++
	pFail, pSlow := 0.05, 0.01
	if sick {
		pFail, pSlow = 0.90, 0.70
	}
	latency := 20
	if rnd() < pSlow {
		latency = 600
	}
	if rnd() < pFail {
		return Result{Latency: latency}, &Failure{Kind: "overloaded", Retryable: true}
	}
	return Result{Value: "camera-frame", Latency: latency}, nil
}
```
:::

Зверніть увагу на дрібницю, що визначає все далі: `rawCallC` **не** посуває годинник сам — він лише повідомляє свою латентність. Посуне годинник той, хто зверху вирішить, чи ми дочекались: таймаут. Так само помилка носить свою латентність — бо збій теж коштує часу (ми ж чекали, перш ніж зрозуміти, що не вийшло).

## Наївний ланцюг: звідки береться 27

Наївна дисципліна проста: кожен, кого вчили повторювати невдалий виклик, повторює його — **на своєму рівні**, ні з ким не змовляючись. A повторює виклик до B тричі; всередині кожної спроби B повторює виклик до C тричі; всередині кожної з тих — C-клієнт повторює свою спробу тричі. Три незалежні цикли по три, вкладені один в одного.

:::tabs
```ts
// Наївний повтор: до n спроб, поки помилка «варта повтору». Без бюджету, без змови.
async function retryNaive(fn: () => Promise<Res>, n: number): Promise<Res> {
  let r = await fn();
  for (let i = 1; i < n && !r.ok && r.retryable; i++) r = await fn();
  return r;
}

// Одна спроба до C, обгорнута лише таймаутом (стеля 300 мс).
const attemptC: Call = (ctx) => withTimeout(rawCallC, 300)(ctx);

// A повторює B (×3), B повторює C (×3), C-клієнт повторює спробу (×3).
const naiveChain: Call = (ctx) =>
  retryNaive(() =>                         // A→B  ×3
    retryNaive(() =>                       //   B→C  ×3
      retryNaive(() => attemptC(ctx),      //     C-клієнт  ×3
      3), 3), 3);
```
```go
// Наївний повтор: до n спроб, поки помилка «варта повтору». Без бюджету, без змови.
func retryNaive(fn func() (Result, error), n int) (Result, error) {
	res, err := fn()
	for i := 1; i < n && err != nil && retryable(err); i++ {
		res, err = fn()
	}
	return res, err
}

// A повторює B (×3), B повторює C (×3), C-клієнт повторює спробу (×3).
func naiveChain(cl *Clock) (Result, error) {
	attemptC := WithTimeout(rawCallC, 300) // одна спроба до C зі стелею 300 мс
	return retryNaive(func() (Result, error) { //     A→B  ×3
		return retryNaive(func() (Result, error) { //   B→C  ×3
			return retryNaive(func() (Result, error) { // C-клієнт  ×3
				return attemptC(cl)
			}, 3)
		}, 3)
	}, 3)
}
```
:::

Тепер порахуймо буквально. Візьмімо найгірший, але цілком звичайний випадок: C зовсім не тягне й на кожну спробу відповідає минущою помилкою. Тоді жоден цикл не спиниться достроково, і кожен доходить до трьох. Проженемо це через лічильник:

:::tabs
```ts
async function runStorm() {
  cCalls = 0;
  // C, що завжди відповідає минущою помилкою — кожна спроба «варта повтору».
  const alwaysFail: Call = async () => {
    cCalls++;
    return { ok: false, kind: "overloaded", retryable: true, latency: 300 };
  };
  const chain: Call = (ctx) =>
    retryNaive(() => retryNaive(() => retryNaive(() => alwaysFail(ctx), 3), 3), 3);
  await chain({ now: 0, deadline: 1e9 });
  console.log(`шторм: C дістав ${cCalls} викликів`);   // → 27
}
```
```go
func runStorm() {
	cCalls = 0
	// C, що завжди відповідає минущою помилкою — кожна спроба «варта повтору».
	alwaysFail := func(cl *Clock) (Result, error) {
		cCalls++
		return Result{Latency: 300}, &Failure{Kind: "overloaded", Retryable: true}
	}
	cl := &Clock{Now: 0, Deadline: 1 << 30}
	retryNaive(func() (Result, error) {
		return retryNaive(func() (Result, error) {
			return retryNaive(func() (Result, error) { return alwaysFail(cl) }, 3)
		}, 3)
	}, 3)
	fmt.Printf("шторм: C дістав %d викликів\n", cCalls) // → 27
}
```
:::

```
шторм: C дістав 27 викликів
```

Двадцять сім — не оцінка й не метафора, а `3·3·3`, яке лічильник підтвердив штука за штукою. І тут криється найгидкіше: C відповів минущою помилкою майже напевно тому, що йому **вже** було важко, — а ми у відповідь вдарили по ньому в двадцять сім разів сильніше. Що більше він давиться, то більше повторів; що більше повторів, то гірше йому. Петля [годує сама себе](book:programming/metastable-failures) — і, розкрутившись, не відпускає навіть після того, як початковий поштовх минув: система застрягає в поганій рівновазі. Стенд дає це помацати руками: зроби `alwaysFail` просто повільним замість того, щоб падати, — і побачиш, як ті самі 27 спроб перетворюються на 27 таймаутів по 300 мс, тобто вісім секунд змарнованого часу на **один** клік.

## Охоронці: таймаут, запобіжник, дедлайн, повтор під бюджетом

Тепер зберімо чотирьох охоронців, кожен з яких ми вже знаємо поодинці, і подивімося на них як на **код**, а не як на ідею. Порядок, у якому вони обгортають виклик, той самий, що ми вивели: таймаут усередині запобіжника, запобіжник усередині повтору.

**Таймаут** перетворює «повільно» на «швидко-і-ясно». Він не спить — він дивиться на латентність, яку повернула спроба, і якщо та перевищила стелю, оголошує таймаут, **списавши з годинника рівно стелю** (ми ж прочекали саме її, а не всю довжину залипання).

**Запобіжник** — серце стенда, і саме його стани найлегше наплутати. Тож промалюймо їх окремо.

![Три стани запобіжника — ЗАМКНЕНО (пропускаю виклики), РОЗІМКНЕНО (корочу одразу) і НАПІВВІДКРИТО (пропускаю одну пробу) — і чотири переходи між ними: k невдач поспіль замикають коло; минув кулдаун — пробуємо один виклик; проба вдала — знову замкнено; проба провалилась — знову розімкнено. Збоку — нагадування, що розімкнене коло не чіпає C, віддає швидку відмову й сигнал «не повторюй»](/root/course/progarch/resilient-call-chain/img/breaker-states.svg)
*Запобіжник — це маленький автомат на три стани. Розімкнене коло робить два подарунки водночас: віддає **швидку** відмову замість повільної й **не пускає** викликів до C зовсім — тому воно й гасить шторм у корені.*

Читається так. У стані **ЗАМКНЕНО** виклики йдуть до C, а лічильник невдач росте від кожного збою й обнуляється від кожного успіху. Набралось `k` невдач поспіль — коло **РОЗІМКНЕНО**: тепер ми C не чіпаємо взагалі, а одразу віддаємо швидку відмову. Минув кулдаун — коло стає **НАПІВВІДКРИТО** й пропускає **рівно одну** пробу: вдала — вертаємось у ЗАМКНЕНО, невдала — знову РОЗІМКНЕНО на новий кулдаун. Уся суть [запобіжника](book:programming/circuit-breaker-pattern) — у цій петлі.

**Дедлайн** тече крізь ланцюг залишком, і кожен охоронець перед роботою питає: чи лишилось часу бодай на мінімум? Якщо ні — це приречена робота, і чесна відповідь — не братися.

Ось усі четверо в коді. Придивіться до **прапорця `retryable`**, який повертають запобіжник (коли розімкнено) і дедлайн (коли часу нема): обидва кажуть «`false` — не повторюй». Це і є сигнал, що тече вгору.

:::tabs
```ts
// ТАЙМАУТ: спрацьовує на витраченому ЧАСІ, байдуже, ok спроба чи ні.
function withTimeout(inner: Call, limit: number): Call {
  return async (ctx) => {
    const r = await inner(ctx);
    if (r.latency > limit) {
      ctx.now += limit;                                    // прочекали рівно стелю
      return { ok: false, kind: "timeout", retryable: true, latency: limit };
    }
    ctx.now += r.latency;                                  // встигли — платимо реальну ціну
    return r;
  };
}

// ЗАПОБІЖНИК: автомат closed → open → half. Стан живе в замиканні.
type BState = "closed" | "open" | "half";
function withBreaker(inner: Call, o: { failsToOpen: number; cooldown: number }): Call {
  let state: BState = "closed", fails = 0, openedAt = 0;
  return async (ctx) => {
    if (state === "open") {
      if (ctx.now - openedAt < o.cooldown)                 // ще кулдаун — КОРОТИМО
        return { ok: false, kind: "circuit-open", retryable: false, latency: 0 };
      state = "half";                                      // час на одну пробу
    }
    const r = await inner(ctx);                            // (це withTimeout(rawCallC))
    if (r.ok) { state = "closed"; fails = 0; return r; }   // одужав
    fails++;
    if (state === "half" || fails >= o.failsToOpen) {      // проба впала / досить невдач
      state = "open"; openedAt = ctx.now; fails = 0;
    }
    return r;
  };
}

// ПОВТОР ПІД БЮДЖЕТОМ, свідомий дедлайну й сигналу «не повторюй».
class Budget {
  private calls = 0; private retries = 0;
  constructor(private ratio = 0.10) {}
  allow(): boolean { return this.retries < this.ratio * this.calls; } // ≤10% трафіку
  record(isRetry: boolean) { this.calls++; if (isRetry) this.retries++; }
}
const doomed = (): Res => ({ ok: false, kind: "deadline", retryable: false, latency: 0 });

function withRetry(inner: Call, o: { tries: number; minWork: number }, b: Budget): Call {
  return async (ctx) => {
    if (ctx.deadline - ctx.now < o.minWork) return doomed();   // приречена робота
    let r = await inner(ctx); b.record(false);
    let attempt = 1;
    while (!r.ok && r.retryable && attempt < o.tries          // помилка ВАРТА повтору
           && ctx.deadline - ctx.now >= o.minWork             // ще є час
           && b.allow()) {                                    // бюджет дозволяє
      b.record(true); r = await inner(ctx); attempt++;
    }
    return r;
  };
}
```
```go
// ТАЙМАУТ: спрацьовує на витраченому ЧАСІ, байдуже, ok спроба чи ні.
func WithTimeout(inner Call, limit int) Call {
	return func(cl *Clock) (Result, error) {
		res, err := inner(cl)
		if res.Latency > limit {
			cl.Now += limit // прочекали рівно стелю
			return Result{Latency: limit}, &Failure{Kind: "timeout", Retryable: true}
		}
		cl.Now += res.Latency // встигли — платимо реальну ціну
		return res, err
	}
}

// ЗАПОБІЖНИК: автомат closed → open → half. Мьютекс — бо в бою кличуть з багатьох горутин.
type Breaker struct {
	mu                    sync.Mutex
	state                 string // "closed" | "open" | "half"
	fails, openedAt       int
	failsToOpen, cooldown int
}

func (b *Breaker) Wrap(inner Call) Call {
	return func(cl *Clock) (Result, error) {
		b.mu.Lock()
		if b.state == "open" {
			if cl.Now-b.openedAt < b.cooldown { // ще кулдаун — КОРОТИМО
				b.mu.Unlock()
				return Result{}, &Failure{Kind: "circuit-open", Retryable: false}
			}
			b.state = "half" // час на одну пробу
		}
		b.mu.Unlock()

		res, err := inner(cl) // лок НЕ тримаємо під час виклику

		b.mu.Lock()
		defer b.mu.Unlock()
		if err == nil {
			b.state, b.fails = "closed", 0 // одужав
			return res, nil
		}
		b.fails++
		if b.state == "half" || b.fails >= b.failsToOpen {
			b.state, b.openedAt, b.fails = "open", cl.Now, 0
		}
		return res, err
	}
}

// ПОВТОР ПІД БЮДЖЕТОМ, свідомий дедлайну й сигналу «не повторюй».
type Budget struct {
	mu             sync.Mutex
	ratio          float64
	calls, retries int
}

func (b *Budget) allow() bool {
	b.mu.Lock(); defer b.mu.Unlock()
	return float64(b.retries) < b.ratio*float64(b.calls) // ≤10% трафіку
}
func (b *Budget) record(isRetry bool) {
	b.mu.Lock(); defer b.mu.Unlock()
	b.calls++
	if isRetry {
		b.retries++
	}
}

func WithRetry(inner Call, tries, minWork int, b *Budget) Call {
	return func(cl *Clock) (Result, error) {
		if cl.Deadline-cl.Now < minWork { // приречена робота
			return Result{}, &Failure{Kind: "deadline", Retryable: false}
		}
		res, err := inner(cl)
		b.record(false)
		for a := 1; a < tries && err != nil && retryable(err) &&
			cl.Deadline-cl.Now >= minWork && b.allow(); a++ {
			b.record(true)
			res, err = inner(cl)
		}
		return res, err
	}
}
```
:::

## Складаємо дисципліну й міряємо

Тепер найважливіше: **повтор живе лише на одному рівні** — там, де ми ближче до користувача, тобто на A. B кличе C **один раз** і чесно віддає відмову вгору, не крутячи власних спроб. Запобіжник стоїть на самій залежності C (де він і потрібен), а дедлайн течe крізь усі стрибки. Отак `3·3·3` розсипається на просте `3` — і навіть ці три впираються в бюджет і в розімкнений запобіжник.

:::tabs
```ts
const MIN_WORK = 25;

function makeDisciplined(): Call {
  const budget = new Budget(0.10);
  // C-клієнт: таймаут ВСЕРЕДИНІ запобіжника. БЕЗ повтору.
  const cClient = withBreaker(withTimeout(rawCallC, 300), { failsToOpen: 5, cooldown: 200 });
  // B: трохи власної роботи й ОДИН виклик до C. Відмову віддає вгору.
  const bHop: Call = async (ctx) => {
    if (ctx.deadline - ctx.now < MIN_WORK) return doomed();
    ctx.now += 5;
    return cClient(ctx);
  };
  // A: ПОВТОР ЛИШЕ ТУТ — під бюджетом і поки є час.
  const aRetry = withRetry(bHop, { tries: 3, minWork: MIN_WORK }, budget);
  return async (ctx) => { ctx.now += 5; return aRetry(ctx); };
}

// Драйвер: жене n запитів, вмикає «інцидент» на середину прогону, рахує p99.
async function benchmark(chain: Call, n: number): Promise<{ cCalls: number; p99: number }> {
  cCalls = 0; seed = 1;                                     // однакові умови «до» і «після»

    await chain(ctx);
    lat.push(ctx.now);                                      // наскрізна затримка = витрачений час
  }
  lat.sort((a, b) => a - b);
  return { cCalls, p99: lat[Math.ceil(0.99 * n) - 1] };
}
```

Прочитаймо, звідки взялося кожне число. **Викликів на C менше** тому, що під час інцидентного вікна запобіжник за п'ять невдач розмикається й далі **не пускає** викликів до C зовсім — а не тому, що ми повторюємо втричі менше. **p99 упав** із двох причин разом: розімкнений запобіжник обертає повільну відмову (300 мс таймауту) на миттєву (0 мс), а дедлайн відкидає роботу, на яку часу вже не лишилось, замість чекати намарно. І найтонше: дисциплінований p99 **у межах дедлайну 1000 мс** не випадково — його там тримає конструкція, тоді як наївний ланцюг, що ігнорує дедлайн і стосує спроби, спокійно набирає вісім секунд на один клік.

## Складність і пастки

Стенд навмисне маленький, і кожне його спрощення — це місце, де в бою легко забитись. Перелічимо чесно.

**Сигнал «не повторюй» — це не деталь, а те, що тримає всю конструкцію.** Придивіться: коли запобіжник розімкнений, він повертає `retryable: false`, і зовнішній повтор на A, побачивши цей прапорець, **не повторює**. Заберіть його — і повтор почне гамселити розімкнене коло, зводячи нанівець сам сенс запобіжника. Той самий прапорець несе й приречена робота (`kind: "deadline"`), і відповідь по суті («поганий запит», «не знайдено»). Класична помилка — трактувати **будь-яку** помилку як минущу й повторювати наосліп: так повтор перетворюється з страховки на важіль, що обертає вашу систему на того, хто вас кладе.

**Монотонний годинник — не педантизм.** У стенді час це число, що тільки росте, тож `deadline − now` завжди чесне. У бою, якщо взяти «зараз» зі стінного годинника (`Date.now()`, стінне значення `time.Now()`), то під час підстроювання NTP годинник може смикнутись **назад** — і `deadline − now` раптом стане від'ємним на живому запиті, який ви через це відкинете як приречений; або смикнутись уперед — і ви прогавите вже перейдений дедлайн. Тому тривалість і бюджет міряють монотонним джерелом: `performance.now()`, а в Go — тим монотонним відліком, який `time.Since`/`time.Until` беруть автоматично. Наш лічильник — модель саме цього.

**Стани запобіжника легко наплутати на переходах.** Три пастки поспіль. Перша: **що вважати невдачею** запобіжника. Таймаут — мусить рахуватись (тому таймаут і стоїть *усередині* запобіжника); а от приречену роботу чи «поганий запит» рахувати **не** можна — це не C захворів, і від цих «невдач» коло розмикати не варто. У стенді запобіжник бачить лише те, що повертає таймаут навколо самого C, — і це правильна межа. Друга: **напіввідкритий стан мусить пропустити рівно одну пробу**. У нашому послідовному стенді це виходить само; у справжньому конкурентному коді кілька викликів можуть проскочити, поки стан ще `half`, — і на ледь оживлений C ринеться натовп проб. Тому в бою напіввідкритість стереже прапорець «проба в польоті» або лічильник дозволених проб. Третя: **кулдаун теж міряється тим самим монотонним годинником** — на стінному він поплив би разом з усіма бідами вище.

**Стенд послідовний, а шторм — про конкурентність.** Ми женемо запити один за одним, щоб p99 був відтворюваний. Тому мьютекси в `Breaker` і `Budget` тут наче зайві — але вони там навмисне: у бою цих охоронців кличуть з багатьох горутин (чи з багатьох `Promise` водночас), і саме спільний стан робить їх спільними. Що стенд **не** ловить через послідовність — це справжні гонки за той стан; зате головне, що він ловить — множення викликів і роздування хвоста — від конкурентності не залежить.

**Шторм живе на корельованій відмові.** Якби C падав незалежно й рідко, наївний ланцюг був би лише трохи гірший. Двадцять сім і восьмисекундний хвіст народжуються тоді, коли C хворіє **вікном** — цілим шматком часу, коли падає майже все. Тому в стенді є `sick`-вікно: без нього справжнього шторму не побачити, бо шторм — це не «іноді помилка», а «всім погано водночас».

**Бюджет повторів на холодну поводиться обережно.** Умова `retries < 0.10 · calls` на перших запитах майже завжди хибна (`calls` ще мале), тож попервах повтори притиснуті. На популяції в тисячі запитів частка сходиться до стелі; це та сама форма, що радить досвід великих служб — не «завжди три спроби», а стеля на **частку** трафіку, яка сама пригасає під навантаженням.

**Порівняння чесне лише при однакових умовах.** Драйвер щоразу скидає `seed` і будує дисциплінований ланцюг **наново** (свіжий запобіжник, свіжий бюджет) — інакше «до» і «після» побачили б різну послідовність поведінки C, і різниця в числах була б через насіння, а не через дисципліну.

І останнє, чого стенд **не** вирішує: коли всі охоронці спрацювали, а C таки недосяжний — що саме віддати користувачеві? Швидка ясна відмова — це вже краще за восьмисекундне зависання, але часто можна більше: віддати часткову, кешовану чи типову відповідь. Куди подіти цю швидку відмову й як зробити деградацію непомітною — окрема розмова про [запасний хід і деградацію](root:progarch/fallback-and-degradation).
