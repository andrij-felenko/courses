# 🧮 Математика швидкості спалювання бюджету помилок та багатовіконні алерти

Ця математична вставка містить формальне виведення рівнянь бюджету помилок (Error Budget), математичне визначення швидкості вигорання (Burn Rate), обчислення часу вичерпання ресурсу надійності, аналіз проблеми малого обсягу вибірки (Low-Traffic Problem) та доведення ефективності багатовіконних алгоритмів генерації сповіщень.

## 1. Фундаментальні визначення: SLI, SLO та Бюджет помилок

Індикатор рівня сервісу (SLI) вимірюється як відношення кількості вдалих подій `Good` до загальної кількості валідних подій `Total` протягом визначеного часового вікна `W`:

```
SLI = Good / Total
```

Ціль рівня сервісу (SLO) задається як мінімально допустима частка `S` вдалих подій протягом скользячого вікна `W` (наприклад, 30 днів):

```
SLI ≥ S
```

Звідси частка дозволених помилкових або повільних запитів `E` (Error Budget) становить:

```
E = 1 − S
```

Якщо сервіс отримує загальну кількість запитів `N_total` за період `W`, то абсолютна кількість дозволених невдалих запитів `N_bad` обчислюється так:

```
N_bad
= N_total · E      [множення загальної кількості на частку помилок]
= N_total · (1 − S) [заміна E на (1 − S)]
```

Для часового вікна тривалістю `T_window` секунд при постійній інтенсивності запитів `R` (запитів на секунду, RPS) абсолютний бюджет помилок у секундах простою `T_downtime` або у кількості невдалих запитів `N_bad` дорівнює:

```
N_bad = R · T_window · (1 − S)
T_downtime = T_window · (1 − S)
```

Розглянемо приклад обчислення для доступності 99.9% за 30 днів. 30 днів містять 2 592 000 секунд. Бюджет помилок становить `E = 1 - 0.999 = 0.001` або 0.1%. Множення 2 592 000 на 0.001 дає рівно 2 592 секунди допустимого простою, що дорівнює 43.2 хвилини на місяць.

```
T_window = 30 діб · 24 години · 3600 секунд = 2 592 000 секунд
S = 0.999
E = 1 − 0.999 = 0.001 (0.1%)

T_downtime
= 2 592 000 · 0.001   [застосування формули простою]
= 2 592 секунди       [обчислення у секундах]
= 43.2 хвилини        [переведення у хвилини: 2592 / 60]
```

При оцінці паралельних або послідовних систем підсумкова надійність розраховується за правилами комбінаторики й теорії ймовірностей. Для двох послідовних залежностей із доступностями `S1` та `S2` підсумковий SLO становить `S_total = S1 · S2`. Якщо `S1 = 0.999` та `S2 = 0.999`, то підсумкова доступність впаде до `0.998001` (99.8%), а бюджет помилок подвоїться до 0.2%.

Для двох паралельних дубльованих залежностей із доступностями `S1` та `S2`, де для успіху достатньо працездатності хоча б одного вузла, підсумковий SLO розраховується через імовірність одночасного збою: `S_total = 1 - ((1 - S1) · (1 - S2))`. Якщо `S1 = 0.99` та `S2 = 0.99`, підсумкова доступність становитиме `1 - (0.01 · 0.01) = 0.9999` (99.99%).

## 2. Математичне визначення Burn Rate (Швидкості спалювання)

Номінальна швидкість витрати бюджету вважається рівною `1.0` (Burn Rate = `1.0`), якщо бюджет помилок вигорає рівномірно і вичерпується точно за всю тривалість вікна `T_window` (наприклад, точно за 30 днів).

Швидкість спалювання `B` (Burn Rate) визначається як відношення фактичної частки вигореного бюджету за проміжок часу `Δt` до номінальної частки, яка мала б згоріти за цей самий час:

```
B = (ΔE / E) / (Δt / T_window)
```

де:
- `ΔE` — частка помилок, зафіксована за короткий інтервал `Δt` (тобто `1 − SLI_Δt`);
- `E` — повний бюджет помилок (`1 − S`);
- `Δt` — тривалість інтервалу спостереження (наприклад, 1 година);
- `T_window` — повне вікно SLO (наприклад, 30 днів = 720 годин).

Розкриємо цю формулу для обчислення часу `T_exhaustion`, за який бюджет згорить повністю (на 100%) при збереженні поточного Burn Rate `B`:

```
T_exhaustion
= T_window / B       [поділ тривалості вікна на швидкість вигорання]
```

Якщо `B = 1.0`, бюджет згорить за `720 / 1.0 = 720` годин (30 днів).
Якщо `B = 2.0`, бюджет згорить удвічі швидше — за `720 / 2.0 = 360` годин (15 днів).
Якщо `B = 14.4`, бюджет вичерпається вщент всього за `720 / 14.4 = 50` годин (2.08 доби).

Звідси видно математичну залежність: швидкість вигорання показує, у скільки разів швидше система втрачає надійність порівняно із запланованим темпом.

## 3. Таблиця швидкостей спалювання та критичність сповіщень

Для вибору порогів сповіщень у SRE-інженерії застосовується розбиття за відсотком витраченого бюджету за фіксовані часові інтервали.

Обчислимо, яке значення `B` відповідає спалюванню конкретного відсотка бюджету `P_budget` за час `t_lookback`:

```
B = (P_budget · T_window) / t_lookback
```

Обчислимо значення `B` для стандартних ситуацій реагування при `T_window = 30 днів = 720 годин`:

**Сценарій 1: Критичний алерт (PagerDuty, невідкладна чергова тривога вночі)**
Ціль: спіймати збій, який випалює 2% бюджету помилок за 1 годину.

```
P_budget = 0.02 (2%)
t_lookback = 1 година
T_window = 720 годин

B
= (0.02 · 720) / 1    [застосування формули розрахунку B]
= 14.4                [результат: Burn Rate 14.4x]
```

При `B = 14.4` увесь бюджет (100%) буде вичерпано за `720 / 14.4 = 50` годин (2 доби). Це означає, що інженер має лише кілька годин на реакцію, перш ніж система вийде з ладу на весь місяць.

**Сценарій 2: Високопріоритетний алерт (Ticket / Slack у робочий час)**
Ціль: спіймати збій, який випалює 5% бюджету помилок за 6 годин.

```
P_budget = 0.05 (5%)
t_lookback = 6 годин
T_window = 720 годин

B
= (0.05 · 720) / 6    [застосування формули]
= 36 / 6              [обчислення чисельника]
= 6.0                 [результат: Burn Rate 6.0x]
```

При `B = 6.0` бюджет буде вичерпано за `720 / 6.0 = 120` годин (5 діб). Це вимагає створення тикету високого пріоритету та вирішення протягом поточного робочого дня.

**Сценарій 3: Повільний витік (Slow Burn Ticket)**
Ціль: спіймати збій, який випалює 10% бюджету помилок за 3 дні (72 години).

```
P_budget = 0.10 (10%)
t_lookback = 72 години
T_window = 720 годин

B
= (0.10 · 720) / 72   [застосування формули]
= 72 / 72             [обчислення чисельника]
= 2.0                 [результат: Burn Rate 2.0x]
```

При `B = 2.0` бюджет вичерпається за `720 / 2.0 = 360` годин (15 діб).

## 4. Проблема низького трафіку (Low-Traffic Problem) та статистична значущість

Формули Burn Rate чудово працюють для високонавантажених сервісів (RPS > 100). Однак для низьконавантажених сервісів (наприклад, внутрішній сервіс адміністрування, який отримує лише 100 запитів на день) виникає статистична аномалія малого обсягу вибірки (Small-N Problem).

Якщо сервіс отримує 10 запитів на годину при SLO 99.9% (дозволено 0.001 помилок), то один єдиний виняток (1 помилка з 10) дає локльний SLI = 90%. Формула вигорання покаже катастрофічний `Burn Rate = (0.10 / 0.001) / (1 / 720) = 100 / (1 / 720) = 72000x`! Одне сповіщення негайно розбудить інженера вночі, хоча у кількосному вимірі згоріла лише дрібна частка абсолютного бюджету.

Для вирішення проблеми низького трафіку застосовують дві математичні модифікації:

1. **Мінімальний поріг абсолютної кількості запитів (Minimum Event Threshold)**:
   Алерт на основі Burn Rate активовується тільки у разі, якщо загальна кількість запитів `N_total` за вікно `t_lookback` перевищує мінімальний поріг:
   ```
   N_total ≥ N_min
   ```
   де `N_min = 10 / (1 - S)`. Для SLO = 99.9% мінімальна вибірка `N_min` становить 10 000 запитів.

2. **Інтервали довіри Вілсона (Wilson Score Interval)**:
   Замість точкової оцінки `SLI = Good / Total` обчислюють нижню межу двостороннього 95% довірчого інтервалу для біноміального розподілу. Сповіщення викликається тільки тоді, коли нижня межа довірчого інтервалу опускається нижче порогу SLO. Це гарантує, що поодинокі збої на малому трафіку не викликають хибних тривог.

## 5. Математичне обґрунтування багатовіконної детекції (Multi-Window Multi-Burn-Rate)

Просте сповіщення за одним довгим вікном `t_long` (наприклад, 1 година) має фундаментальну ваду — інерційність згасання (Alert Reset Lag).

Якщо на системі стався короткий сплеск помилок (наприклад, 100% помилок протягом 2 хвилин), який випалив 3% бюджету, а потім система повністю відновилася, сповіщення за 1-годинним вікном продовжуватиме горіти ще 58 хвилин після того, як проблема повністю зникла. Це розбудить інженера, який о 3-й ночі побачить абсолютно здорову систему.

Натомість перевірка лише за коротким вікном `t_short` (наприклад, 5 хвилин) має низьку точність (low precision) через дрібні статистичні флуктуації та поодинокі таймаути.

Щоб розв'язати цю проблему, застосовують математичний кон'юнктивний фільтр (логіка `AND`), який вимагає одночасного виконання двох умов:

```
Alert_Triggered = (BurnRate(t_long) ≥ Threshold) AND (BurnRate(t_short) ≥ Threshold)
```

де `t_short` вибирається як `1/12` від `t_long`.

**Стандартна співвідносна матриця вікон Google SRE:**

1. **Критичне сповіщення (Page):**
   - Довге вікно `t_long = 1 година`, поріг `BurnRate ≥ 14.4` (витрачено ≥ 2% бюджету).
   - Коротке вікно `t_short = 5 хвилин`, поріг `BurnRate ≥ 14.4`.
   - *Математичний сенс:* Довге вікно підтверджує, що важкість збою достатня (втрачено 2% бюджету), а коротке вікно підтверджує, що збій триває просто зараз (не згас 2 хвилини тому).

2. **Попереджувальне сповіщення (Ticket):**
   - Довге вікно `t_long = 6 годин`, поріг `BurnRate ≥ 6.0` (витрачено ≥ 5% бюджету).
   - Коротке вікно `t_short = 30 хвилин`, поріг `BurnRate ≥ 6.0`.

Доведемо математичне скидання алерту після згасання збою. Нехай сплеск помилок тривав 3 хвилини й припинився. Через 5 хвилин після початку сплеску показник `BurnRate(t_short = 5m)` розраховується лише за останні 5 хвилин, де перші 2 хвилини були чистими. `BurnRate(t_short)` падає нижче порогу `14.4`. Отже, умова `(BurnRate(t_long) ≥ 14.4) AND (BurnRate(t_short) ≥ 14.4)` перетворюється на `True AND False = False`. Алерт автоматически деактивується (auto-resolve) вже через 5 хвилин після завершення збою, замість 60 хвилин при однодетекційній схемі.

Це математично гарантує максимізацію повноти детекції (recall = 99.9%) при зведенні хибних спрацьовувань (false positives) практично до нуля.
