# 📋 Формалізований масив прийняття рішень та специфікація вибору стратегій міграції

У цій довідковій вставці подано формалізовану матрицю вибору стратегій міграції (Expand-Contract, Parallel Run, Strangler Fig, Dark Launch), деталізовану аналітичну модель розрахунку інфраструктурних накладних витрат, критерії допустимості простою (SLA/RTO/RPO) та деревний алгоритм прийняття рішень для архітекторів високонавантажених програмних систем.

---

## 1. Специфікація параметрів та критеріїв оцінки міграційного ризику

Прийняття рішення про вибір архітектурного патерну зміни живої системи спирається на попередню кількісну оцінку системи. Архітектор не може керуватися лише суб'єктивними вподобаннями чи модними тенденціями; вибір повинен обґрунтовуватися аналізом вимог до неперервності бізнесу та складності даних.

Перед вибором стратегії кожна зміна у живій системі оцінюється за шістьма фундаментальними параметрами:

| Параметр | Позначення | Діапазон значень | Опис та системний вплив |
| :--- | :--- | :--- | :--- |
| **Допустимий час простою** | `RTO` (Recovery Time Objective) | `0` (Zero Downtime) … `N` годин | Максимально дозволена тривалість вікна обслуговування (Maintenance Window). |
| **Допустима втрата даних** | `RPO` (Recovery Point Objective) | `0` (Zero Data Loss) … `N` записів | Максимальний обсяг даних, який дозволено втратити при некоректному відкаті. |
| **Вимоги до SLA доступності** | `SLA_target` | `99.9%` … `99.999%` | Загальний бюджет помилок (Error Budget), доступний для даного сервісу під час релізу. |
| **Складність стану та мутацій** | `State_complexity` | `Stateless`, `Append-Only`, `In-Place Mutable` | Наявність транзакційного стану, ACID-гарантій та зовнішніх побічних ефектів. |
| **Коефіцієнт витрат ресурсу** | `Cost_mult` | `1.1x` … `2.5x` | Перевищення витрат на обчислювальні потужності та бази даних під час міграції. |
| **Тривалість релізу** | `Duration` | `Хвилини`, `Дні`, `Місяці` | Фізичний час проведення процедури заміни від першого деплою до декомісії. |

### 1.1. Математична формалізація бюджету помилок (Error Budget)

Сучасний SLA визначає максимальну сумарну тривалість простою сервісу протягом 30-денного розрахункового періоду:

- **SLA 99.0% (Дві дев'ятки):** Допустимий простій до `7.2 годин` на місяць. Дозволяє проводити короткі планові вікна обслуговування з зупинкою сервісу.
- **SLA 99.9% (Три дев'ятки):** Допустимий простій до `43.2 хвилин` на місяць. Виключає ручні міграції баз даних, але дозволяє короткі канарейкові переключення.
- **SLA 99.99% (Чотири дев'ятки):** Допустимий простій до `4.32 хвилин` на місяць. Вимагає стратегій з нульовим RTO (Expand-Contract, Strangler Fig).
- **SLA 99.999% (П'ять дев'яток):** Допустимий простій не більше `25.9 секунд` на місяць. Будь-яке неконтрольоване блокування таблиці чи простій сервісу негайно перевищує бюджет помилок, що зобов'язує використовувати Parallel Run або Dark Launch.

Аналіз цих метрик визначає так зване «вікно безпечної зміни». Якщо система має цільовий SLA на рівні 99.999%, будь-яка стратегія, що вимагає зупинки сервісу хоча б на 1 хвилину, дискваліфікується негайно. Натомість для некритичних аналітичних дашбордів із вимогами 99.0% планова зупинка на вихідних може бути фінансово доцільнішою за складні паралельні прогони.

## 2. Зведена порівняльна матриця стратегій

У таблиці нижче підсумовано інженерні характеристики чотирьох головних стратегій зміни живої системи. Кожен патерн оптимізовано під свій клас архітектурних задач та ризикових профілів:

| Стратегія міграції | Основний фокус та придатність | RTO / RPO | Складність стану | Інфраструктурна ціна (`Cost_mult`) | Ризик релізу та радіус ураження |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Expand-Contract** | Зміна схем БД, еволюція API-контрактів, додавання DTO-полів | RTO = 0<br>RPO = 0 | `Stateless` або `Append-Only` | `1.1x` (Тимчасовий обсяг колонок у БД) | **Низький:** Зворотно-сумісні кроки, легкий локальний відкат. |
| **Parallel Run (Dual Run)** | Фінансовий білінг, ризик-моделі, бухгалтерський облік, розрахунок податків | RTO = 0<br>RPO = 0 | `In-Place Mutable` (ACID state) | `2.0x – 2.5x` (Подвійна інфраструктура + Reconciler) | **Мінімальний:** 100% звіряння виходів до відключення старого коду. |
| **Strangler Fig** | Заміна монолітів, виділення мікросервісів, реархітектура legacy | RTO = 0<br>RPO = 0 | `Mixed` (Покрокове розщеплення моноліту) | `1.2x – 1.5x` (API Gateway + Нові сервіси) | **Керований:** Покрокове витіснення маршрутів, відсутній Big Bang. |
| **Dark Launch (Shadow)** | Перевірка продуктивності, навантажувальне тестування, валідація latency | RTO = 0<br>RPO = N/A (без ефектів) | `Stateless` або `Muted Mutations` | `1.5x – 2.0x` (Тіньові інстанси + Shadow Proxy) | **Zero-Risk:** Клієнти не бачать відповідей тіньової системи. |

### 2.1. Покриття стратегіями за доменами застосування

- **Фінансові рахунки та Ledger:** Застосовується виключно **Parallel Run**. Помилка у 1 цент при порівнянні балансу `v1` та `v2` є блокуючим дефектом релізу.
- **Еволюція моноліту e-Commerce:** Застосовується **Strangler Fig**. Домени Корзини, Каталогу та Профілю виділяються у мікросервіси послідовно протягом 6–12 місяців.
- **Оновлення SQL-схеми таблиці замовлень:** Застосовується **Expand-Contract**. Схема збагачується новими полями через подвійний запис без виходу сервісу з ладу.
- **Запуск нового рушія пошукового ранжування:** Застосовується **Dark Launch**. Новий сервіс обробляє 100% пошукових запитів у тіньовому режимі для вимірювання latency p99 та навантаження на пам'ять.

## 3. Формалізоване дерево рішень (Decision Tree Algorithm)

Для автоматизації та стандартизації процедури вибору стратегії в інженерних командах застосовується формалізований деревний алгоритм. Він гарантує, що розробники обирають найпростіший інструмент, який задовольняє обмеженням безпеки:

```
[Початок оцінки міграції]
       |
       v
Чи є міграція зміною структури БД чи API-контракту в межах одного сервісу?
       ├── ТАК ──> Чи дозволено розбити деплой на 3 фази (Expand -> DualWrite -> Contract)?
       │              ├── ТАК ──> 🏆 Використовуй EXPAND-CONTRACT
       │              └── НІ  ──> ⚠️ Зупинка: потрібне рефакторинг-вікно (Maintenance Window)
       │
       └── НІ  ──> Чи вимагає зміна повної заміни монолітного застосунку або цілої підсистеми?
                      ├── ТАК ──> Чи дозволяє API-периметр перехоплювати окремі URL-маршрути?
                      │              ├── ТАК ──> 🏆 Використовуй STRANGLER FIG
                      │              └── НІ  ──> ⚠️ Створіть Facade / API Gateway шари на периметрі
                      │
                      └── НІ  ──> Чи є головним ризиком фінансова точність та ACID-консистентність?
                                     ├── ТАК ──> 🏆 Використовуй PARALLEL RUN (DUAL RUN)
                                     │
                                     └── НІ  ──> Чи є головним ризиком навантаження, TPS та Latency?
                                                    ├── ТАК ──> 🏆 Використовуй DARK LAUNCH (SHADOW)
                                                    └── НІ  ──> Використовуй Canary / Blue-Green
```

### 3.1. Деталізація гілок та практичні приклади

#### Гілка 1: Expand-Contract
Застосовується у випадках, коли зміна обмежена межами одного сервісу та його автономного сховища даних. Приклади: розділення поля `full_name` на `first_name` та `last_name`, зміна типу колонки з `INT` на `BIGINT`, додавання поля `tax_id` у JSON-контракт API.

Якщо розбити деплой на три фази неможливо (наприклад, сторонній клієнт не підтримує подвійний запис), команда зобов'язана погодити з бізнесом вікно обслуговування (Maintenance Window) і проводити міграцію в оффлайн-режимі.

#### Гілка 2: Strangler Fig
Застосовується під час рефакторингу монолітних систем. Головною передумовою є наявність API-шлюзу або проксі-шару, здатного розбирати URL-па шляхи та заголовки. Якщо моноліт приймає трафік прямо на сокет без проксі, першим кроком міграції є введення Reverse Proxy (Envoy, Nginx) без зміни самого монолітного коду.

#### Гілка 3: Parallel Run
Застосовується для критичних бізнес-операцій із високим рівнем фінансового ризику. Обов'язковою умовою є розробка Reconciler-модуля, здатного порівнювати виходи старої та нової систем і генерувати метрики відхилень у реальному часі.

#### Гілка 4: Dark Launch
Застосовується, коли новий сервіс написано на іншій мові програмування або з використанням нової бази даних (наприклад, заміна Python REST API на Rust gRPC сервіс). Головний ризик полягає у невідомості профілю затримок під високим навантаженням.

## 4. Конфігураційна специфікація та порогові метрики

### 4.1. Декларативний контракт Expand-Contract для міграцій БД

Під час проведення міграцій Expand-Contract фази повинні бути чітко розмежовані у конфігураціях CI/CD конвеєра, щоб запобігти випадковому виконанню ламаючих SQL-команд:

```yaml
migration_contract:
  strategy: expand_contract
  target_table: "orders"
  phases:
    - phase_1_expand:
        sql: "ALTER TABLE orders ADD COLUMN customer_tax_id_v2 VARCHAR(64) NULL;"
        backward_compatible: true
        deploy_app_version: "v1.10.0" # Код пише у v1 і v2, читає з v1

    - phase_2_backfill:
        job: "background_tax_id_migrator"
        batch_size: 1000
        throttle_ms: 50
        verification: "SELECT COUNT(*) FROM orders WHERE customer_tax_id_v2 IS NULL;"

    - phase_3_read_switch:
        deploy_app_version: "v1.11.0" # Код читає з v2 з фолбеком на v1

    - phase_4_contract:
        sql: "ALTER TABLE orders DROP COLUMN legacy_tax_code_v1;"
        deploy_app_version: "v1.12.0" # Код працює виключно з v2
```

### 4.2. Конфігурація дзеркалювання трафіку у Envoy (Dark Launch Spec)

Декларативне конфігурування L7-проксі Envoy для реалізації тіньового дублювання трафіку на тестовий кластер:

```yaml
static_resources:
  listeners:
    - name: ingress_http
      address:
        socket_address: { address: 0.0.0.0, port_value: 8080 }
      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                stat_prefix: ingress_http
                route_config:
                  name: local_route
                  virtual_hosts:
                    - name: backend
                      domains: ["*"]
                      routes:
                        - match: { prefix: "/api/v2/orders" }
                          route:
                            cluster: primary_service_v1
                            request_mirror_policies:
                              - cluster: shadow_service_v2
                                runtime_fraction:
                                  default_value:
                                    numerator: 100
                                    denominator: HUNDRED
```

### 4.3. Порогові показники припинення міграції (Circuit Breaker Limits)

Для кожної стратегії встановлюються суворі порогові значення автоматичного скасування (Rollback Criteria). Перевищення будь-якого порогу негайно блокує просування релізу:

| Стратегія | Метрика спостереження | Порогове значення алерту | Дія при перевищенні порогу |
| :--- | :--- | :--- | :--- |
| **Expand-Contract** | Lag бекфіллу даних | `Lag > 10,000` записів протягом 15 хв | Пауза бекфілл-воркера, відкат прочитання на v1 |
| **Parallel Run** | Частка розбіжностей Reconciler | `Diff > 0.001%` від загального трафіку | Блокування перемикання трафіку, збереження логів |
| **Strangler Fig** | 5xx Error Rate на нових маршрутах | `5xx > 0.1%` або `p99 latency > 500ms` | Перенаправлення маршруту Gateway назад у моноліт |
| **Dark Launch** | Тіньова затримка & CPU Proxy | `CPU > 80%` або `Drop rate > 5%` | Зменшення `mirrorPercentage` з 100% до 10% |

Автоматична обробка цих порогів у моніторингу (Prometheus / Grafana Alertmanager) захищає команду від людського чинника.

## 5. Формула оцінки інфраструктурних витрат (Cost Estimation Model)

Сумарна вартість проведення міграції `Total_Cost` обчислюється за економічною формулою:

```
Total_Cost = Base_Infra_Cost × (1 + Cost_mult × (Duration_days / 365)) + Dev_Ops_Hours × Rate
```

Де:
- `Base_Infra_Cost` — базова річна вартість утримання даної системи у продакшн-середовищі.
- `Cost_mult` — коефіцієнт подвоєння ресурсів (1.1 для Expand-Contract, 2.0 для Parallel Run / Dark Launch).
- `Duration_days` — тривалість утримання двох паралельних систем у днях.
- `Dev_Ops_Hours` — трудомісткість розробки роутерів, міграторів даних та Reconciler-рушіїв у годинах.
- `Rate` — погодинна ставка інженерної команди.

### 5.1. Приклад математичного розрахунку для білінгової системи

Припустимо, базова інфраструктура білінгового сервісу коштує `100 000 USD` на рік. Команда розглядає можливість проведення Parallel Run протягом `90 днів`. Трудомісткість створення Reconciler та тіньових воркерів оцінюється у `200 інженерних годин` за ставкою `75 USD/годину`.

```
Base_Infra_Cost = 100 000 USD
Cost_mult = 2.0 (100% подвоєння серверів і баз даних)
Duration_days = 90 днів
Dev_Ops_Hours = 200 годин
Rate = 75 USD/год

Додаткові витрати на інфраструктуру:
Infra_Add = 100 000 × (2.0 × (90 / 365)) = 100 000 × (2.0 × 0.2465) = 49 300 USD

Витрати на інженерні розробки:
Dev_Cost = 200 × 75 = 15 000 USD

Загальна вартість проведення Parallel Run:
Total_Cost = 49 300 + 15 000 = 64 300 USD
```

### 5.2. Інструкція з ліквідації аварійних інцидентів (Incident Runbook)

Під час проведення міграцій за кожною із чотирьох стратегій інженерна чергова служба дотримується регламенту реагування на аварії:

1. **Інцидент при Expand-Contract (Блокування БД / Deadlock):**
   - Крок 1: Негайно зупинити фоновий процес бекфіллу (`KILL BACKFILL_JOB_ID`).
   - Крок 2: Відновити фолбек прочитання на `v1_field` шляхом перемикання конфігураційного прапорця без деплою коду.
   - Крок 3: Перевірити наявність блокувань у СУБД (`SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';`).

2. **Інцидент при Strangler Fig (Перевантаження нового мікросервісу):**
   - Крок 1: Змінити вагу маршруту на API Gateway, повернувши 100% трафіку на моноліт (`weight: 100` до Monolith).
   - Крок 2: Перевірити залишковий стан кешів у новому мікросервісі.
   - Крок 3: Збільшити кількість реплік нового сервісу у Kubernetes (`kubectl scale deployment`).

3. **Інцидент при Dark Launch (Деградація проксі-балансувальника):**
   - Крок 1: Скинути параметри тіньового дзеркалювання в Envoy до 0% (`mirrorPercentage: 0%`).
   - Крок 2: Перевірити споживання CPU та пам'яті на L7-балансувальниках.
   - Крок 3: Перезапустити вузли проксі з підвищеними лімітами дескрипторів сокетів.

### 5.3. Чек-лист готовності до початку міграції (Pre-Migration Readiness Checklist)

Перед запуском фази Expand або увімкненням дзеркалювання трафіку команда зобов'язана підтвердити проходження 10 контрольних пунктів:

1. [ ] Схема бази даних підтримує Nullable колонки для нових полів (`v2`).
2. [ ] Налаштовано оптимістичне блокування (Optimistic Locks) у бекфілл-воркерах.
3. [ ] Розгорнуто L7-балансувальник із підтримкою динамічного перемикання маршрутів без перезапуску.
4. [ ] Реалізовано прокидання наскрізного заголовку трасування (`traceparent`) крізь усі межі.
5. [ ] Модуль Reconciler підключено до метрик Prometheus та Alertmanager.
6. [ ] Для режиму Dark Launch вимкнено всі мутуючі зовнішні HTTP-виклики та SMS-сповіщення.
7. [ ] Резервна копія бази даних створена та перевірена на відновлення протягом останніх 24 годин.
8. [ ] Затверджено порогові рівні скасування релізу (Circuit Breakers).
9. [ ] Оцінено витрати на утримання подвійної інфраструктури та погоджено бюджет із бізнесом.
10. [ ] Оформити архітектурне рішення у вигляді документації (ADR - Architecture Decision Record).
