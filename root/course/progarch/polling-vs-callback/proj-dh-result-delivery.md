# ⚙️ Доставка результату DH: обидва боки, загартовано

Розвилку ми вже пройшли: телефон **тягне** статус, партнерська хмара дістає **штовхнутий** вебхук, а поверх обох лежить **звірка** як страхувальна сітка. Код у тій розмові був навмисне голий — статус у три рядки, поллінг у цикл, доставка одним `deliver(...)`, під яким чесно ховалося «див. проєкт». Ось той проєкт. Тут ми збираємо доставку результату оновлення прошивки **цілком**, на два боки, і не в лабораторних умовах, а так, щоб трималося, коли мережа робить те, що вона робить завжди: губить, дублює, затримує й підсовує підробки.

Домовмося одразу, де тут складність. Щасливий шлях — оновлення пройшло, телефон спитав і почув «готово», партнер дістав POST і оновив запис — справді десяток рядків. Але за ці рядки ніхто не платить нічними інцидентами. Платять за **інші дев'яносто відсотків**: за повтор, що прилетів удруге; за POST, який надіслав не DH; за вебхук, що не дійшов узагалі; за паралельний застосунок, що затер свіжий результат старим. Кожна з п'яти частин нижче закриває один конкретний спосіб втратити чи зіпсувати результат.

У центрі DH: дешева статус-точка та відправник, що по завершенні задачі підписує результат і штовхає POST; вичерпані повтори падають у мертву чергу. *Ліворуч телефон тягне статус вихідним GET; у центрі DH підписує результат і штовхає його партнерові, а невдалі доставки складає в мертву чергу; праворуч партнер звіряє підпис, дедупить за event-id і застосовує раз; звірка-сітка внизу добирає те, що вебхук проґавив. Уся конструкція тримається на одному: один результат — один event-id.*

Наскрізна деталь, на якій усе тримається, видно вже з карти: **один результат оновлення — один стабільний `event-id`** (скажімо, `evt_<jobId>`, виведений з номера задачі). І вебхук, і звірка несуть **той самий** ключ, тож приймач дедупить їх разом — байдуже, котрий канал приніс подію першим. Тримай цю думку в голові; вона зшиває частини (в), (г) і (ґ) в одне ціле.

## 1. Статус-точка `GET /jobs/{id}` — дешевий бік pull

Почнімо з найпростішого — точки, яку **опитує** телефон. Її єдиний обов'язок: віддати поточний стан задачі, і віддати **дешево**. Чому дешево — арифметика з попереднього кроку: десять тисяч застосунків на п'ятисекундному інтервалі — це дві тисячі запитів на секунду, кожен із яких лише питає «готово?». Якщо на кожен такий запит сервер робить важку роботу — джойнить таблиці, будить сусідній сервіс, — поллінг-шторм помножить цю вагу на дві тисячі. Тому статус — це **одне читання за ключем** і нічого більше.

Друга тонкість — кешування. Проміжний стан (`running`) кешувати **не можна**: він ще зміниться, а закешована відповідь примусить телефон опитувати застарілу «правду». А от **термінальний** стан (`done`/`failed`) незмінний назавжди — його кешувати не лише можна, а й варто, щоб зняти зайві звертання.

:::tabs
```ts
// СЕРВЕР DH — статус для тих, хто ОПИТУЄ. Має бути ДЕШЕВОЮ: її б'ють N/T разів на секунду.
app.get("/jobs/:id", async (req, res) => {
  const job = await jobs.get(req.params.id);        // одне читання за ключем — і по всьому
  if (!job) return res.status(404).json({ error: "unknown job" });

  const terminal = job.status === "done" || job.status === "failed";
  res.set("Cache-Control", terminal ? "public, max-age=3600" : "no-store"); // done — можна; running — ні

  res.json({
    jobId: job.id,
    status: job.status,                             // queued | running | done | failed
    result: terminal ? job.result : null,           // {version, ok} на done; {code, message} на failed
    updatedAt: job.updatedAt,                       // точка відліку для клієнта Й для звірки
  });
});
```
```py

@app.get("/jobs/{job_id}")
async def job_status(job_id: str, response: Response):

    if job is None:
        raise HTTPException(404, "unknown job")

    terminal = job.status in ("done", "failed")
    # термінальний стан кешувати можна; проміжний — ні, він ще зміниться
    response.headers["Cache-Control"] = "public, max-age=3600" if terminal else "no-store"
    return {
        "jobId": job.id,
        "status": job.status,                        # queued | running | done | failed
        "result": job.result if terminal else None,  # {version, ok} на done; {code, message} на failed

```
:::

Зверни увагу на `updatedAt` у відповіді — це не косметика. Він дає і телефону, і майбутній звірці **точку відліку**: «покажи все, що змінилося після цієї миті». Без нього звірка мусила б щоразу перечитувати всі задачі поспіль.

**Пастка тут одна, зате дорога: зробити статус важким.** Кожен зайвий джойн, кожен виклик у сусідній сервіс на цьому шляху множиться на частоту поллінга. Статус мусить бути настільки дешевим, щоб дві тисячі його викликів на секунду було не помітно.

## 2. Мобільний поллінг — обмежений, з відступом і джитером

Тепер бік телефону. У попередньому кроці поллінг-клієнт виглядав так: цикл, `fetch`, `sleep` із подвоєнням паузи. Цього **замало** для проду, і бракує там рівно трьох речей.

Перше — **межа**. Той цикл крутиться `for (;;)` — вічно. Якщо задача чомусь ніколи не стане термінальною (застрягла, загубилась), телефон опитуватиме її до кінця світу, гріючи батарею й сервер. Поллінг мусить мати **бюджет**: пів години крутити спінер немає сенсу — за кілька хвилин здаємось і кажемо користувачеві «щось пішло не так».

Друге — **джитер**. Подвоєння паузи (`1 → 2 → 4`) рятує сервер від частоти, але не від **синхронності**: якщо тисяча телефонів почала опитувати одночасно (а так і буває — після масової розсилки «оновіть хаб»), то й повторюють вони синхронно, б'ючи сервер пульсуючою стіною в ті самі миті. Це «стадо, що гримить». Ліки — **повний джитер**: брати паузу рівномірно випадковою в усьому вікні `[0, вікно]`, щоб телефони розповзлися в часі.

Третє — **термінальна невдача теж вихід**. Наївний цикл чекав лише на `done`. Але `failed` — теж кінець: оновлення могло не вдатися, і телефон мусить це показати, а не опитувати далі в надії, що «раптом полагодиться».

:::tabs
```ts
// ТЕЛЕФОН — поллінг ОБМЕЖЕНИЙ: бюджет часу + експоненційний відступ + ПОВНИЙ джитер.
// Виходимо, коли: термінальний стан АБО вичерпано бюджет АБО згорнули екран (abort).
async function pollJob(id: string, budgetMs: number, signal: AbortSignal): Promise<Job> {
  const deadline = Date.now() + budgetMs;           // напр. 5 хв — далі спінер не має сенсу
  const base = 1000, cap = 15_000;                  // 1 → 2 → 4 → 8 → стеля 15 с
  for (let attempt = 0; ; attempt++) {
    const job = await (await fetch(`/jobs/${id}`, { signal })).json();
    if (job.status === "done" || job.status === "failed") return job; // ← єдиний нормальний вихід

    const window = Math.min(cap, base * 2 ** attempt);
    const wait = Math.random() * window;            // повний джитер: рівномірно в [0, вікно]
    if (Date.now() + wait > deadline) throw new Error("poll budget exhausted"); // не спати за бюджет
    await sleep(wait, signal);                      // прокидається на abort → екран згорнули
  }
}
```
```py
# ТЕЛЕФОН — поллінг ОБМЕЖЕНИЙ бюджетом часу + експоненційний відступ + ПОВНИЙ джитер.
async def poll_job(job_id: str, budget_s: float = 300.0) -> dict:
    deadline = time.monotonic() + budget_s           # 5 хв — далі спінер не має сенсу
    base, cap, attempt = 1.0, 15.0, 0
    while True:
        job = await http_get_json(f"/jobs/{job_id}")
        if job["status"] in ("done", "failed"):
            return job                               # ← єдиний нормальний вихід

        wait = random.uniform(0, min(cap, base * 2 ** attempt))  # повний джитер
        if time.monotonic() + wait > deadline:       # не спати за бюджет — здаємось
            raise TimeoutError("poll budget exhausted")
        await asyncio.sleep(wait)
        attempt += 1
```
:::

> 🔧 **Навіщо це.** Необмежений поллінг — не «трохи неощадливо», а відкритий кран на батарею користувача й на твій сервер. Три запобіжники роблять його свійським: **бюджет** обриває безнадійне очікування, **повний джитер** розганяє синхронне стадо, а вихід на **обох** термінальних станах (`done` і `failed`) не дає циклу крутитися після того, як усе вже вирішилось. Забереш джитер — дістанеш пульсуючу стіну; забереш бюджет — дістанеш телефони, що опитують мертві задачі годинами.

## 3. Відправник вебхука — підписати й повторювати в мертву чергу

Бік DH, дзеркальний до телефону. Щойно оновлення завершилось, сервер **сам** стукає до партнера. І тут з'являється те, чого поллінг не знав зовсім: доставку тепер несе **відправник крізь мережу**, а мережа ненадійна в обидва боки — партнер може лежати, проксі може відкинути, з'єднання може обірватися по дорозі. Тому «надіслати POST» — це насправді три обов'язки.

Перший — **підпис**. Вхідний POST «нібито від DH» міг зліпити будь-хто, хто знає адресу партнера. Щоб партнер міг **довести** собі, що подія справді від DH і по дорозі її не підмінили, DH підписує тіло. Схему беремо не з голови, а перевірену: так роблять [підпис вебхука](topic:programming/webhook-security) — щоб приймач міг звірити, що тіло справді від нас і не змінене — Stripe і GitHub, обидва через HMAC-SHA256 над корисним навантаженням, ключований на спільному секреті. Stripe до підписуваного рядка додає ще й **мітку часу** (підписує `timestamp.body`), і ми беремо саме цей варіант: підпис тоді прикриває не лише вміст, а й **час**, а сама мітка дає приймачеві захист від переграння старого перехопленого POST. Заголовок несе і час, і підпис: `t=<unix>,v1=<hex>`.

Другий — **повтор із відступом**. Якщо партнер відповів `5xx` або не відповів зовсім, це, найпевніше, минуще — повторюємо, але **розумно**: з експоненційним відступом і — знову — повним джитером, щоб тисяча відправників не гатила синхронно. А `4xx` (крім `429`) повторювати **не** можна: це відповідь «ти надіслав щось не те», і повторення тієї самої дурниці нічого не полагодить.

Третій — **мертва черга**. Повтори не можуть тривати вічно. Вичерпав N спроб — подія не має права просто зникнути; вона падає в [мертву чергу](topic:programming/dead-letter-queue) — окреме сховище для того, що не вдалося доставити, — звідки її дістане тривога й ручний (чи автоматичний) повторний прогін.

![Відправник вебхука в часі. Ліворуч: задача done породжує подію зі стабільним id, яку підписують HMAC(t·тіло). Далі над віссю часу — серія невдалих POST (спроби 0,1,2,3, кожна з хрестиком «✗»), а між ними ростуть удвічі вікна джитера w₀, w₁, w₂. Після серії спроб розвилка: будь-яка відповідь 2xx завершує доставку вгору «готово», а вичерпані N спроб ведуть праворуч у мертву чергу «на розбір, не загублено». Унизу: 4xx крім 429 обриває повтори одразу; id той самий на кожен POST](img/sender-retry-dlq.svg)
*Подію підписують раз і повторюють доставку з експоненційним відступом і повним джитером; `2xx` завершує, `4xx` (крім `429`) обриває одразу, а вичерпані спроби падають у мертву чергу — на розбір, не в нікуди.*

І тут уперше проступає той самий `event-id`. Подію будують **раз**, з ідентифікатором, стабільним **на всі повтори**: згенеруєш новий id на кожен POST — і приймач не впізнає дубль, застосує подію двічі. Один результат — один id, скільки б разів його не повторювали.

:::tabs
```ts
import { createHmac } from "node:crypto";

// Подія будується РАЗ, з id, стабільним на ВСІ повтори (id — ключ дедупу в приймача).
async function onFirmwareDone(job: Job) {
  const event = {
    id: `evt_${job.id}`,               // детермінований з задачі → той самий на кожен повтор і на звірку
    type: "firmware.updated",
    home: job.home, version: job.version, ok: job.ok,
    occurredAt: job.finishedAt,
  };
  for (const url of await hooks.for(job.home)) await deliver(url, event);
}

// Підпис Stripe-стилю: HMAC-SHA256 над `t.body` — підпис прикриває й тіло, й час.
function sign(body: string, secret: string, ts: number): string {
  const mac = createHmac("sha256", secret).update(`${ts}.${body}`).digest("hex");
  return `t=${ts},v1=${mac}`;
}

async function deliver(url: string, event: object) {
  const body = JSON.stringify(event);              // рівно ці байти й підписуємо, й шлемо
  const ts = Math.floor(Date.now() / 1000);
  const sig = sign(body, HOOK_SECRET, ts);
  const base = 1000, cap = 60_000, maxAttempts = 8;

  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      const r = await fetch(url, {
        method: "POST",
        headers: { "content-type": "application/json", "dh-signature": sig },
        body,                                      // тіло НЕ перебудовуємо — байти мусять збігтися з підписом
        signal: AbortSignal.timeout(5000),
      });
      if (r.status >= 200 && r.status < 300) return;                  // прийнято — по завершенню
      if (r.status >= 400 && r.status < 500 && r.status !== 429) break; // 4xx (крім 429) — не полагодиться повтором
    } catch { /* таймаут/обрив — падаємо у відступ нижче */ }

    const window = Math.min(cap, base * 2 ** attempt);
    await sleep(Math.random() * window);           // експонента + повний джитер
  }
  await deadLetters.put({ url, body, sig, failedAt: Date.now() });    // на розбір, не в нікуди
}
```
```py
import hmac, hashlib, json, time, random, asyncio

async def on_firmware_done(job):
    event = {                                       # будуємо РАЗ; id детермінований з задачі
        "id": f"evt_{job['id']}",                   # той самий на кожен повтор і на звірку
        "type": "firmware.updated",
        "home": job["home"], "version": job["version"], "ok": job["ok"],
        "occurred_at": job["finished_at"],
    }
    for url in await hooks.for_home(job["home"]):
        await deliver(url, event)

def sign(body: str, secret: str, ts: int) -> str:
    mac = hmac.new(secret.encode(), f"{ts}.{body}".encode(), hashlib.sha256).hexdigest()
    return f"t={ts},v1={mac}"                        # Stripe-стиль: підпис прикриває й тіло, й час

async def deliver(url: str, event: dict):
    body = json.dumps(event, separators=(",", ":"))  # канонічні байти: й підписуємо, й шлемо саме їх
    ts = int(time.time())
    sig = sign(body, HOOK_SECRET, ts)
    base, cap, max_attempts = 1.0, 60.0, 8

    for attempt in range(max_attempts):
        try:
            r = await http_post(url, data=body, timeout=5.0,
                                headers={"content-type": "application/json", "dh-signature": sig})
            if 200 <= r.status < 300:
                return                               # прийнято
            if 400 <= r.status < 500 and r.status != 429:
                break                                # 4xx (крім 429) — не полагодиться повтором
        except (TimeoutError, ConnectionError):
            pass                                     # мережа — у відступ

        window = min(cap, base * 2 ** attempt)
        await asyncio.sleep(random.uniform(0, window))  # експонента + повний джитер
    await dead_letters.put({"url": url, "body": body, "sig": sig, "failed_at": time.time()})
```
:::

> 🔧 **Навіщо це.** Відправник — не `fetch` у циклі, а маленький протокол надійності. **Підпис** дає приймачеві право вірити; **мітка часу під підписом** закриває переграння; **відступ із джитером** лікує, а не добиває того, хто впав; **розрізнення 4xx/5xx** не марнує спроби на невиправне; **мертва черга** перетворює «не доставили» на «відклали на розбір», а не на «втратили тихо». Прибери будь-що одне — і знайдеться ніч, коли саме воно тебе розбудить.

## 4. Приймач партнера — довіра, дедуп, застосування раз

Найважча частина — бік партнера, що **приймає** POST. Тут порядок дій не випадковий, і переставити його не можна: спершу вирішуємо, чи **вірити** повідомленню взагалі, тоді — чи не **бачили** ми його вже, і лише тоді — **застосовуємо**.

![Порядок перевірок у приймачі, згори вниз. POST надійшов (сирі байти й заголовок). Перевірка 1 — підпис збігся? HMAC у сталий час; ні → 401, це не від DH. Перевірка 2 — час свіжий, |тепер − t| ≤ 5 хв? ні → 400, застарілий, захист від переграння. Перевірка 3 — event-id уже в inbox? так → ACK 200, нічого не робимо, повтор проковтнули тихо. Якщо ні — свіжа подія — вставити event-id і застосувати ефект в одній транзакції, тоді ACK 200 після коміту. Збоку: порядок незмінний — довіра, свіжість, дедуп, раз](img/receiver-flow.svg)
*Три брами в незмінному порядку: спершу підпис (чи вірити), тоді свіжість (чи не переграно), тоді inbox за event-id (чи не бачили вже) — і лише тоді застосування, разом із записом ключа в одній транзакції.*

**Крок довіри — звірити підпис, і звірити правильно.** Партнер сам обраховує HMAC над тим самим `timestamp.body` своїм примірником секрету й порівнює з тим, що прийшов у заголовку. Дві пастки чигають саме тут. Перша: порівнювати треба **сирі байти** тіла — ті самі, що підписав DH. Якщо десь у конвеєрі middleware розпарсив і **перезібрав** JSON (переставив ключі, прибрав пробіли), байти зміняться, і підпис чесної події не зійдеться. Тому тіло для звірки беруть **до** парсингу, сирим. Друга: порівняння підписів мусить бути **сталим у часі** — звичайне `===` на рядках виходить із циклу на першому розбіжному байті, і за часом відповіді зловмисник **вгадує секрет побайтно**. Тому — `timingSafeEqual` у Node, `hmac.compare_digest` у Python, ніколи не `===`.

**Крок свіжості — відкинути старе.** Навіть із правильним підписом подія може бути **перехопленою й переграною** пізніше. Мітка часу під підписом це ловить: якщо `t` старіша за кілька хвилин (Stripe бере вікно 5 хв), подію відкидаємо. Це той рідкісний випадок, коли трохи вільне вікно — навмисне: годинники DH і партнера трохи розходяться, і надто вузьке вікно рубало б чесні події.

**Крок дедупу й застосування — і це серце частини.** Мережа доставляє [щонайменше раз (at-least-once)](topic:programming/delivery-guarantees) — гарантія «дійде, можливо, не раз», через що повтори неминучі: той самий підписаний, свіжий POST цілком законно прилетить двічі, бо DH повторив, коли перша `2xx` загубилась по дорозі. Тому приймач **зобов'язаний** бути [ідемпотентним](topic:programming/idempotency): застосувати подію рівно раз, хоч скільки разів вона прийшла. Механізм — [вхідна скринька (inbox)](topic:programming/inbox-pattern): таблиця, де `event_id` — первинний ключ; приймач **в одній транзакції** вставляє `event_id` і застосовує ефект. Прийшов дубль — `INSERT … ON CONFLICT DO NOTHING` нічого не вставить, ми побачимо нуль торкнутих рядків і **тихо проковтнемо** повтор, не застосувавши його вдруге.

:::tabs
```ts
import { createHmac, timingSafeEqual } from "node:crypto";

const parseSig = (h: string): Record<string, string> =>
  Object.fromEntries(h.split(",").map((kv) => kv.split("=", 2)));  // "t=..,v1=.." → {t, v1}

// Сирі байти на ЦЬОМУ маршруті — express.raw, не express.json: парсинг зсунув би байти й зламав підпис.
app.post("/dh/webhook", express.raw({ type: "application/json" }), async (req, res) => {
  const raw = req.body as Buffer;
  const { t, v1 } = parseSig(req.get("dh-signature") ?? "");

  // 1 · ДОВІРА: HMAC над тими самими `t.body`, звірка у СТАЛИЙ час.
  const expected = createHmac("sha256", HOOK_SECRET).update(`${t}.`).update(raw).digest();
  const got = Buffer.from(v1 ?? "", "hex");
  if (got.length !== expected.length || !timingSafeEqual(got, expected))
    return res.status(401).end();                  // підпис не зійшовся — це не від DH

  // 2 · СВІЖІСТЬ: старий підпис міг би переграти зловмисник. Вікно 5 хв, як у Stripe.
  if (Math.abs(Date.now() / 1000 - Number(t)) > 300) return res.status(400).end();

  const event = JSON.parse(raw.toString());        // тепер тілу можна вірити

  // 3 · ДЕДУП + ЗАСТОСУВАННЯ РАЗ — в ОДНІЙ транзакції: ключ і ефект або разом, або ніяк.
  await db.tx(async (tx) => {
    const ins = await tx.query(
      "INSERT INTO inbox(event_id) VALUES ($1) ON CONFLICT DO NOTHING", [event.id]);
    if (ins.rowCount === 0) return;                // подію вже застосовували — тихо проковтнули повтор
    await applyFirmwareResult(tx, event);          // ефект застосовано РІВНО раз
  });

  res.status(200).end();                           // ACK після коміту — DH може забути про доставку
});
```

import hmac, hashlib, time, json

def parse_sig(h: str) -> dict:
    return dict(p.split("=", 1) for p in h.split(",") if "=" in p)  # "t=..,v1=.." → {t, v1}

@app.post("/dh/webhook")
async def receive(request: Request):
    raw = await request.body()                      # сирі байти ДО .json() — інакше підпис не зійдеться
    sig = parse_sig(request.headers.get("dh-signature", ""))
    t, v1 = sig.get("t", "0"), sig.get("v1", "")

    # 1 · ДОВІРА: HMAC над тими самими `t.body`, звірка у СТАЛИЙ час.
    expected = hmac.new(HOOK_SECRET.encode(), f"{t}.".encode() + raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(v1, expected):
        raise HTTPException(401, "bad signature")   # не від DH

    # 2 · СВІЖІСТЬ: вікно 5 хв проти переграння, як у Stripe.
    if abs(time.time() - int(t)) > 300:
        raise HTTPException(400, "stale timestamp")

    event = json.loads(raw)                         # тепер тілу можна вірити

    # 3 · ДЕДУП + ЗАСТОСУВАННЯ РАЗ — в ОДНІЙ транзакції.
    async with db.transaction() as tx:
        ins = await tx.execute(
            "INSERT INTO inbox(event_id) VALUES ($1) ON CONFLICT DO NOTHING", event["id"])
        if ins.rowcount == 0:
            return {"ok": True}                     # вже застосовано — проковтнули повтор
        await apply_firmware_result(tx, event)      # ефект застосовано рівно раз
    return {"ok": True}                             # ACK після коміту

Найтонше тут — **одна транзакція** на дедуп-ключ і ефект. Якби ми спершу застосували ефект, а окремо потім записали `event_id`, то збій між цими двома кроками або застосував би подію без сліду (і наступний повтор застосував би її знову), або записав би ключ без ефекту (і подію б утратили). Разом — або обидва, або жоден — робить застосування атомарно-однократним. І `ACK 200` **після** коміту: доки ми не записали результат, DH не має вважати доставку успішною.

> 🔧 **Навіщо це.** Приймач вебхука — не «обробник POST», а фортеця з трьома брамами в незмінному порядку. **Підпис** (сталим часом, по сирих байтах) вирішує, чи вірити; **свіжість** відкидає перегране; **inbox у спільній транзакції** гарантує, що навіть законний дубль застосується рівно раз. Пропустиш першу браму — приймеш фальшиве «оновлення успішне» від чужака; пропустиш третю — подвоїш дію на першому ж повторі, а повтори при at-least-once **будуть**.

## 5. Звірка-сітка — добрати те, що вебхук проґавив

Лишилася п'ята частина, і вона пояснює, навіщо ми взагалі тримаємо **обидва** канали. Вебхуки **губляться** — не «в теорії», а буденно: приймач полежав тридцять секунд на деплої, проксі відкинув сплеск, спрацював якийсь фільтр. Якщо DH вичерпав повтори, подія лежить у нього в мертвій черзі — а партнерів запис так і лишився з застарілою прошивкою, і **ніхто про це не знає**. Push сам по собі не дає гарантії; гарантію дає pull.

Тому партнер періодично — рідко, це ж страхувальна сітка, а не гарячий шлях — **сам тягне** з DH те, що міг проґавити: `GET /jobs?status=done&updatedSince=<чекпойнт>`. І — ось краса задуму — женемо здобуте крізь **той самий** ідемпотентний шлях, що й вебхуки. Звірка будує подію з **тим самим** `evt_<jobId>`, вставляє в **той самий** inbox. Що вебхук уже приніс — дедупиться геть; що проґавив — застосується тут. Подвійне застосування **неможливе за побудовою**, бо ключ спільний.

:::tabs
```ts
// ЗВІРКА (partner). Рідко — це страхувальна сітка. Женемо здобуте крізь ТОЙ САМИЙ inbox.
async function reconcile() {
  const since = await checkpoint.get("firmware");        // де спинились минулого разу
  const done = await dhApi.listJobs({ status: "done", updatedSince: since });

  for (const job of done) {
    const event = {
      id: `evt_${job.id}`,                 // ТОЙ САМИЙ ключ, що й у вебхука → inbox дедупне
      type: "firmware.updated",
      home: job.home, version: job.version, ok: job.ok,
    };
    await db.tx(async (tx) => {
      const ins = await tx.query(
        "INSERT INTO inbox(event_id) VALUES ($1) ON CONFLICT DO NOTHING", [event.id]);
      if (ins.rowCount === 0) return;      // вебхук уже приніс — нічого не робимо
      await applyFirmwareResult(tx, event); // вебхук проґавив — застосовуємо тут
    });
  }
  await checkpoint.set("firmware", nowIso()); // чекпойнт — лише після успішного проходу
}
setInterval(reconcile, 5 * 60_000);          // раз на кілька хвилин

Ключ до того, щоб сітка не наробила шкоди, — **спільний event-id**: звірка не має власного способу застосувати результат, вона користується тим самим inbox, тож у найгіршому разі просто нічого не робить (усе вже застосовано). Прибери звірку — і кожен проґавлений вебхук стає **тихою вічною втратою**; лишиш її без спільного ключа — і вона задублить усе, що вебхук уже доставив.

## Складність і пастки

П'ять частин зібрано; лишилося пройтися по краях, де все це ламається на дрібниці.

**Сире тіло — святе.** Підпис прикриває **байти**, а не «сенс». Будь-який проксі, будь-який middleware, що розпарсив і перезібрав JSON перед твоєю перевіркою, змінює байти — і підпис чесної події не зійдеться. У Express це означає `express.raw()` саме на цьому маршруті (а не глобальний `express.json()`); у FastAPI — `await request.body()` до будь-якого доступу до `.json()`. Підписуй і звіряй рівно ті байти, що йдуть дротом.

**Стале порівняння — не педантизм.** `crypto.timingSafeEqual` (Node) і `hmac.compare_digest` (Python) виходять не на першому розбіжному байті, а завжди за однаковий час; звичайне `===`/`==` — виходить, і час відповіді витікає підпис побайтно. І перед `timingSafeEqual` звір **довжину** буферів: на різній довжині він кидає виняток, тож спершу порівняй довжини (це не витікає нічого корисного), а тоді вміст.

**event-id мусить бути стабільним і детермінованим.** Уся ідемпотентність тримається на тому, що дубль несе **той самий** ключ. Згенеруєш `randomUUID()` на кожен POST — і кожен повтор виглядатиме як нова подія, дедуп осліпне, застосування задвоїться. Виводь id **із задачі** (`evt_<jobId>`), а не з моменту відправлення: тоді і третій повтор вебхука, і звірка через годину несуть один ключ.

**Порядок і latest-wins.** Дедуп ловить точні повтори **однієї** події, але не рятує від **різних** подій, що прийшли не по черзі: прошивку оновили до v3, потім до v4, а вебхук v3 через повтор прилетів **після** v4. Наївний `apply` затре свіжий v4 старим v3. Тому сам ефект має бути **монотонним за версією** — `UPDATE … WHERE version < :new`, застосовуй, лише якщо подія новіша за вже записане. Inbox прибирає дублі; версійний запис прибирає **інверсії порядку**.

**Мертва черга — не могила.** Скинути подію в DLQ — половина справи; хтось мусить її звідти **діставати**. DLQ без тривоги й дренажу — це тихе накопичення втрачених подій, яке помітять, коли клієнт поскаржиться. На кожну мертву чергу — сигнал «тут щось є» і механізм повторного прогону.

**ACK рано проти ACK надійно.** Ми повертаємо `200` **після** коміту — найпростіший коректний варіант: доки результат не записано, доставка не вважається вдалою. Спокуса відповісти `200` одразу, а застосувати «потім, асинхронно», реальна (менша затримка для відправника), але вона повертає всі проблеми: упаде процес між `ACK` і застосуванням — подію втрачено, бо DH уже почув «прийнято» й не повторить. Асинхронне застосування вимагає спершу **надійно** записати подію (той самий inbox як журнал), і навіть тоді твоєю справжньою страхувальною сіткою лишається звірка з частини 5. Ось навіщо вона є.

**Годинник під підписом теж бреше.** Вікно свіжості (5 хв) припускає, що годинники DH і партнера приблизно збігаються. Якщо партнерів сервер поплив на десять хвилин, він відкидатиме **чесні** свіжі події як «застарілі». Тримай час синхронізованим (NTP) і не роби вікно надто тісним — воно захищає від переграння, а не від хвилини розходження.

Під усіма п'ятьма частинами — одна думка. Доставити результат надійно означає не «надіслати вдало», а **зробити кожен крок таким, що переживе повтор, підробку, затримку й пропажу**: дешевий статус, обмежений поллінг, підписаний вебхук у мертву чергу, ідемпотентний приймач і звірка, що добере втрачене. Жоден із каналів не буває певним поодинці — певність дає лише їхнє поєднання, зшите одним спільним ключем.
