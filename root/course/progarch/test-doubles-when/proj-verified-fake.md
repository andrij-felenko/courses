# ⚙️ Перевірений фейк у коді: один контракт, дві реалізації, спіймана брехня

Крок про дублери закінчився правилом, яке легко проказати й важко відчути на дотик: кожен фейк, що лишається жити в тестах, **винен тобі контрактний тест**. Поки ти не побачив, як цей контракт червоніє саме тоді, коли фейк почав брехати, правило лишається гаслом. Тож зробімо його руками — на коді, який кладеться на диск і запускається, — і доведімо чорним по білому: та сама зміна, від якої звичайні юніт-тести й бровою не поведуть, спалахне червоним у спільному наборі й спіймає розбіжність **до бою**, а не в бою.

Візьмемо те саме сховище показників, у яке контролер охолодження зазирав викликом `store.recent()`. Досі контролеру вистачало одного боку обіцянки — прочитати останні показники. Тепер, щоб поставити поруч справжнє сховище й фейк і зіштовхнути їх, додамо й другий бік: `save`. Виходить крихітний, але повний інтерфейс — покласти показник і дістати найсвіжіші. Рівно на ньому й розіграється вся драма.

## Задача: фейк, якого нема чим спіймати

Придивімося до небезпеки впритул. У тестах контролера ми годували йому фейк-сховище в пам'яті — швидке, без диска й мережі. У бою під тим самим інтерфейсом стоятиме справжнє: база чи файл. Отже, **одну обіцянку** («поклав — дістав найсвіжіші») втілюють **дві** реалізації. І тут пастка, яку легко проґавити: ніщо не змушує ці дві реалізації **погоджуватися між собою**.

Звідки взятися розбіжності? Фейк — це справжній код, який хтось написав нашвидку й більше не чіпав. Справжній адаптер живе своїм життям: змінюється схема, додається сортування, база квантує числа по-своєму. Кожна така дрібниця тихенько розводить фейк і бій. А зелений юніт-тест цього не побачить **ніколи** — бо він ганяється **тільки на фейку**. Він доводить, що код працює з нашою підробкою; про те, чи підробка досі схожа на реальність, він не знає й не питає. Це і є непiдв'язаний фейк: міна, яку видно лише коли рвоне.

Потрібна прив'язь, яка змусить обидві реалізації тримати **ту саму** обіцянку — і закричить, щойно одна відступила.

## Ідея: один набір перевірок, прогнаний по обох

Хід простий і саме тому потужний. Замість того щоб писати окремі тести на фейк і окремі на базу, ми записуємо **обіцянку один раз** — як набір перевірок, що нічого не знає про конкретну реалізацію, а лише годує їй входи й звіряє виходи з контрактом. Тоді той самий набір **параметризуємо** реалізацією й ганяємо двічі: на фейку й на справжньому. Обидва **мусять** пройти. Щойно фейк розійшовся з боєм — набір червоніє на фейку, і брехня випливає в тесті.

Це та сама ідея [контрактних тестів](topic:sf-release/contract-testing) — перевірок, що описують обіцянку межі й ганяються проти **будь-якої** реалізації тієї межі, — тільки повернута всередину, на власний дублер. Мартін Фаулер назвав цей прийом «контрактним тестом» ще 2011 року: набір, який звіряє, що виклики до твого дублера дають те саме, що дав би справжній сервіс, і який ловить розходження, коли реальність змінює контракт (усталена, добре задокументована практика — не фольклор). Ми лише застосуємо його до найближчого дублера — фейка сховища у власному репозиторії.

> 🔧 **Навіщо це.** Різниця між «тест на фейк» і «контракт на обидва» — це різниця між дзеркалом і терезами. Окремий тест на фейк лише віддзеркалює те, що фейк і так робить: він зелений за визначенням, бо перевіряє підробку проти себе самої. Спільний набір **важить** — кладе фейк і бій на одну шальку й показує розбіжність вагою. Тому правило «кожен фейк винен контрактний тест» на практиці означає рівно одне: **та сама функція перевірок, два входи-реалізації, обидва зобов'язані пройти.**

## Крок 1 — контракт сховища як інтерфейс save/recent

Спершу випишемо обіцянку словами — бо саме її, а не код, кодуватиме набір. Сховище показників обіцяє чотири речі. Що `save` **запам'ятовує** покладене. Що `recent(n)` віддає **до n** показників. Що це саме **найсвіжіші** — з найбільшим часом `at`, і **найсвіжіше — перше**. І що показник **повертається таким, яким сховище його тримає** — зокрема час `at` живе цілими мілісекундами, бо epoch-мілісекунда — ціле число. Це та сама [межа-як-обіцянка](topic:sf-release/design-by-contract): тонка домовленість, за яку тримаються обидві сторони, не знаючи одна одної в обличчя.

А тепер — той самий контракт формою, яку компілятор і читач бачать однаково:

:::tabs
```ts
export type Reading = { at: number; celsius: number };   // at — epoch, мс

// Контракт сховища. Дві реалізації нижче обіцяють РІВНО це — й нічого понад.
export interface ReadingStore {
  save(r: Reading): void;
  recent(limit: number): Reading[];   // до limit найсвіжіших; найсвіжіше — перше
}
```
```py
from dataclasses import dataclass
from typing import Protocol

@dataclass
class Reading:
    at: int          # epoch, мс
    celsius: float

# Контракт сховища. Дві реалізації нижче обіцяють РІВНО це — й нічого понад.
class ReadingStore(Protocol):
    def save(self, r: Reading) -> None: ...
    def recent(self, limit: int) -> list[Reading]: ...   # до limit найсвіжіших; найсвіжіше — перше
```
:::

Інтерфейс мовчить про те, **як** обіцянку дотримати — сортуванням у пам'яті чи `ORDER BY` у базі. Це навмисне: контракт описує поведінку, яку видно ззовні, а не начинку. Саме тому одна обіцянка й може мати дві геть різні реалізації — і саме тому їх треба щось звірити.

## Крок 2 — дві реалізації однієї обіцянки

Перша — **фейк у пам'яті**. Тримає показники списком, на `recent` сортує за часом і відрізає верхівку. Швидкий, без диска, для тестів:

:::tabs
```ts
export class InMemoryStore implements ReadingStore {
  private items: Reading[] = [];
  save(r: Reading): void { this.items.push({ ...r }); }
  recent(limit: number): Reading[] {
    return [...this.items].sort((a, b) => b.at - a.at).slice(0, limit);  // найсвіжіше — перше
  }
}
```
```py
class InMemoryStore:
    def __init__(self) -> None:
        self._items: list[Reading] = []
    def save(self, r: Reading) -> None:
        self._items.append(Reading(r.at, r.celsius))
    def recent(self, limit: int) -> list[Reading]:
        return sorted(self._items, key=lambda r: r.at, reverse=True)[:limit]  # найсвіжіше — перше
```
:::

Друга — **справжній адаптер** на SQLite. Тут доречно взяти вбудований у платформу двигун без сторонніх залежностей: Python має `sqlite3` у стандартній бібліотеці, а Node з версії 22.5 — модуль `node:sqlite` (`DatabaseSync`; запуск `node --experimental-sqlite`, а з v22.13/v23.4 прапорець уже не потрібен). База в пам'яті (`:memory:`) лишає адаптер справжнім по механіці — той самий SQL, ті самі типи стовпців, — але без файлів на диску:

:::tabs
```ts
import { DatabaseSync } from "node:sqlite";

export class SqliteStore implements ReadingStore {
  private db = new DatabaseSync(":memory:");
  constructor() {
    // стовпець at — INTEGER: сховище тримає ЦІЛІ мілісекунди
    this.db.exec("CREATE TABLE readings (at INTEGER NOT NULL, celsius REAL NOT NULL)");
  }
  save(r: Reading): void {
    this.db.prepare("INSERT INTO readings (at, celsius) VALUES (?, ?)")
      .run(Math.round(r.at), r.celsius);          // округлюємо на вході — стовпець цілий
  }
  recent(limit: number): Reading[] {
    const rows = this.db
      .prepare("SELECT at, celsius FROM readings ORDER BY at DESC LIMIT ?")
      .all(limit) as Array<{ at: number; celsius: number }>;
    return rows.map(r => ({ at: r.at, celsius: r.celsius }));
  }
}
```
```py
import sqlite3

class SqliteStore:
    def __init__(self) -> None:
        self._db = sqlite3.connect(":memory:")
        # стовпець at — INTEGER: сховище тримає ЦІЛІ мілісекунди
        self._db.execute("CREATE TABLE readings (at INTEGER NOT NULL, celsius REAL NOT NULL)")
    def save(self, r: Reading) -> None:
        self._db.execute("INSERT INTO readings (at, celsius) VALUES (?, ?)",
                         (round(r.at), r.celsius))   # округлюємо на вході — стовпець цілий
    def recent(self, limit: int) -> list[Reading]:
        rows = self._db.execute(
            "SELECT at, celsius FROM readings ORDER BY at DESC LIMIT ?", (limit,)
        ).fetchall()
        return [Reading(at, celsius) for at, celsius in rows]
```
:::

Зверни увагу на два місця, де реалізації **чесно розходяться в начинці**, лишаючись при цьому вірними контракту. Порядок фейк тримає сортуванням списку, а база — `ORDER BY at DESC`. Цілість часу фейк не чіпає взагалі, а адаптер округлює на вході, бо стовпець `at` — `INTEGER`. Обидві розбіжності контракт дозволяє — його обходить лише **видима поведінка**. Але тримай їх в оці: рівно тут за мить проб'ється дрейф.

## Крок 3 — параметризований набір, спільний на обидва

Тепер серце всієї затії. Пишемо перевірки **один раз** і параметризуємо їх реалізацією. У кожній перевірці — свіже сховище з фабрики (чому свіже, а не спільне, розберемо в пастках), кілька `save`, тоді звірка `recent` із контрактом:

:::tabs
```ts
import { test } from "node:test";
import assert from "node:assert/strict";

// фабрика на кожну реалізацію — набір нижче про них нічого більше не знає
const impls: { name: string; make: () => ReadingStore }[] = [
  { name: "InMemoryStore", make: () => new InMemoryStore() },
  { name: "SqliteStore",   make: () => new SqliteStore() },
];

for (const { name, make } of impls) {
  test(`[${name}] save-then-recent повертає покладене`, () => {
    const s = make();
    s.save({ at: 1000, celsius: 20 });
    assert.deepEqual(s.recent(10), [{ at: 1000, celsius: 20 }]);
  });

  test(`[${name}] recent(n) — n найсвіжіших, найсвіжіше перше`, () => {
    const s = make();
    for (const at of [3000, 1000, 2000]) s.save({ at, celsius: at / 100 });  // БЕЗЛАДНО
    assert.deepEqual(s.recent(2).map(r => r.at), [3000, 2000]);
  });
}
```
```py
import pytest

# фабрика на кожну реалізацію — набір нижче про них нічого більше не знає
@pytest.fixture(params=[InMemoryStore, SqliteStore])
def store(request):
    return request.param()          # свіже сховище на КОЖНУ перевірку

def test_save_then_recent(store):
    store.save(Reading(1000, 20.0))
    assert store.recent(10) == [Reading(1000, 20.0)]

def test_recent_newest_first(store):
    for at in (3000, 1000, 2000):   # БЕЗЛАДНО
        store.save(Reading(at, at / 100))
    assert [r.at for r in store.recent(2)] == [3000, 2000]
```
:::

Запусти — `node --experimental-sqlite --test` або `pytest` — і побачиш **чотири** зелені галочки: дві перевірки, кожна на двох реалізаціях. Спинися на цьому. Той самий рядок `assert` щойно виконано і над списком у пам'яті, і над SQL-запитом до бази — і обидва світи заприсяглися однаково. Оце і є перевірений фейк: не «фейк, який ми вважаємо правильним», а «фейк, прибитий до бою тим самим цвяхом».

І придивися до другої перевірки — вона вже зараз хитра. Ми годуємо показники **не в часовому порядку** (`3000, 1000, 2000`), а вимагаємо назад двох найсвіжіших `[3000, 2000]`. Фейк проходить, бо чесно сортує; база проходить, бо `ORDER BY`. Тримай цю перевірку в голові: за хвилину вона стане тим детектором, що спіймає брехню.

## Крок 4 — уводимо дрейф: «нешкідливе спрощення» фейка

Тепер розіграймо звичайнісіньку сцену з життя. Приходить рев'ю, хтось дивиться на `recent` фейка й каже: «навіщо повне сортування щоразу? Ми ж усе одно кладемо показники в часовому порядку — візьмемо просто останні `n` і розвернемо, буде швидше». Правка виглядає безневинно й навіть слушно:

:::tabs
```ts
recent(limit: number): Reading[] {
  return this.items.slice(-limit).reverse();   // «спрощення»: останні n, розвернуті
}
```
```py
def recent(self, limit: int) -> list[Reading]:
    return list(reversed(self._items[-limit:]))   # «спрощення»: останні n, розвернуті
```
:::

Тепер найважливіше — послухаймо, що на це скажуть різні тести. Спершу **звичайний юніт-тест сховища**, той, що його написали б нашвидку, годуючи показники в часовому порядку:

**Умова.** Кладемо `1000`, потім `2000` — у порядку часу. Питаємо двох найсвіжіших.
```
items = [ {at:1000}, {at:2000} ]
slice(-2)        →  [ {at:1000}, {at:2000} ]
.reverse()       →  [ {at:2000}, {at:1000} ]     ← рівно чого й чекали
```
**Висновок.** Зелено. Спрощений фейк на впорядкованому вході віддає точно те саме, що й раніше. Юніт-тест контролера, який годував фейку заготовлений відсортований список, — теж лишається зелений, бо ніколи й не клав показники безладно. З погляду цих тестів нічого не сталося.

А тепер той самий фейк ставимо під **спільний контрактний набір** — під другу перевірку з безладним входом:

**Умова.** Кладемо `3000, 1000, 2000` — не в часовому порядку. Контракт вимагає двох найсвіжіших: `[3000, 2000]`.
```
items = [ {at:3000}, {at:1000}, {at:2000} ]     ← у порядку ВСТАВКИ
slice(-2)        →  [ {at:1000}, {at:2000} ]     ← останні двоє вставлених
.reverse()       →  [ {at:2000}, {at:1000} ]
очікувано контрактом:  [ 3000, 2000 ]
```
**Висновок.** Червоно — і саме на фейку. `3000`, найсвіжіший показник, **випав узагалі**, бо його вставили першим, а «останні `n`» його не захопили. Ось як це виглядає в прогоні:
```
✔ [SqliteStore]   recent(n) — n найсвіжіших, найсвіжіше перше
✖ [InMemoryStore] recent(n) — n найсвіжіших, найсвіжіше перше
    очікувано: [ 3000, 2000 ]
    одержано:  [ 2000, 1000 ]        ← 3000 (найсвіже!) загубилося
```

Спіймали. «Спрощення» мовчки підмінило контракт `recent` — «найсвіжіші за часом» на «останні за вставкою» — і поки дані лягали впорядковано, різниці не було видно **ніде**. Справжня база з `ORDER BY` цієї підміни не робила й лишилася зелена. Спільний набір поклав фейк і базу на одну шальку — і фейк переважив брехнею. У бою цей баг чекав би на перший показник, що прийшов із запізненням чи пакетним синхроном не в порядку, — і контролер порахував би середнє не по тих числах. Замість аварії в домі — червоний рядок у тесті.

![Один фейк під двома тестами: угорі звичайний юніт-тест годує показники в часовому порядку — фейк повертає очікуване, зелено, їде в бій; унизу спільний контрактний набір годує безладно — той самий фейк губить найсвіжіший показник, червоно, спіймано до бою; справжній адаптер проходить обидві доріжки](img/drift-catch.svg)
*Різницю робить не суворість перевірки, а її вхід. Юніт-тест на впорядкованих даних не має чим побачити брехню; спільний набір навмисне годує безладне — те, що бій робить сам собою, — і дрейф спливає. Справжній адаптер тримає контракт на обох доріжках, тож розбіжність — цілком на совісті фейка.*

## Крок 5 — другий дрейф: фейк, чесніший за реальність

Перший дрейф фейк робив **менше**, ніж обіцяв, — не сортував. Але є підступніший рід брехні: фейк робить **більше**, ніж уміє бій. Пригадай наші дві реалізації: адаптер округлює `at` на вході, бо стовпець `INTEGER`, а фейк не чіпає час зовсім. Отже, фейк тримає час так, як йому дали, — хоч цілим, хоч дробовим `float`-мілісекундом. Поки всі тести підсовували цілі epoch-мілісекунди (а `Date.now()` саме такі й дає), різниця спала. Додаймо в набір перевірку, яка її розбудить:

:::tabs
```ts
test(`[${name}] at зберігається цілими мілісекундами`, () => {
  const s = make();
  s.save({ at: 1000.7, celsius: 21 });               // дробове — навмисне
  assert.ok(Number.isInteger(s.recent(1)[0].at),
            `at мусить бути цілим, а не ${s.recent(1)[0].at}`);
});
```
```py
def test_at_is_whole_ms(store):
    store.save(Reading(1000.7, 21.0))                 # дробове — навмисне
    top = store.recent(1)[0]
    assert isinstance(top.at, int), f"at мусить бути цілим, а не {top.at!r}"
```
:::

**Умова.** Кладемо показник із дробовим `at = 1000.7`. Контракт: сховище тримає цілі мілісекунди.
```
справжній адаптер:  round(1000.7) = 1001   → Number.isInteger(1001) = true   ✔
фейк у пам'яті:     1000.7 (як дали)        → Number.isInteger(1000.7) = false ✖
```
**Висновок.** Знову червоно на фейку — і то повчальніше за перший раз. Фейк не помилився; він виявився **точнішим за бій**. Тримаючи дробовий час, який справжнє сховище округлило б і викинуло, він дозволяє тестам покладатися на точність, якої в продакшені **не існує**. Тест міг би, скажімо, розрізняти дві події за `0.3` мілісекунди — і бути зеленим на фейку, тоді як база звела б їх в одну мить. Зауваж і те, що в Python-версії анотація `at: int` не рятує: вона нічого не перевіряє під час виконання, і `Reading(at=1000.7)` тихо тримає `float`. Обіцянку стереже **контракт**, а не підказка типу.

Це той самий рід пастки, що вихолоджував наш дім, коли [фейк давача віддавав охайне `19.0`, а живий DS18B20 — цілі мілі-градуси `19000`](root:progarch/seams-and-boundaries/proj-dh-sensor-seam.md): підробка дотримала контракту, який ми на неї повісили, а справжнє — іншого. Найдорожче ця розбіжність коштує там, де числа мають дискретну одиницю реальності: гроші (округлення до копійки), час (квант годинника), одиниці вимірювання. Фейк, який тримає `10.005` гривні або `1000.7` мілісекунди, зеленить тести, що в бою неминуче зіткнуться з копійкою й цілим мілісекундом. Спільний набір змушує фейк **збіднитися до реальності** — і саме тому він винен кожному фейкові.

> 🔧 **Навіщо це.** Коли пишеш фейк, тебе тягне зробити його «кращим» за бій — точнішим, поблажливішим, без прикрих обмежень справжнього сховища. Це і є отрута. Контракт мусить кодувати не лише те, що бій **вміє**, а й те, чого він **не вміє**: квантує час, обрізає точність, має межу довжини, не терпить `NaN`. Перевіряй фейк на **обмеженнях** бою так само пильно, як на можливостях, — інакше зелений тест означає тільки «на ідеальному, неіснуючому сховищі працює».

## Складність і пастки

Прийом дає силу — і має гострі краї. Кожна пастка нижче — це спосіб, яким спільний набір може тихо перестати ловити те, заради чого й затіявся.

**Свіже сховище на кожну перевірку — фабрика, не спільний примірник.** Ми не дарма беремо `make()` / фікстуру з `params`, а не один об'єкт на всі тести. Спільний примірник тече станом: показники, покладені однією перевіркою, лишаються бачити наступній, і порядок тестів починає нишком впливати на їхній результат. Для фейка-списку це особливо підступно; SQLite у пам'ті рятує сам собою, бо кожне `new SqliteStore()` — окреме з'єднання з новою базою, — але покладатися на це не варто. Фабрика робить кожну перевірку самодостатньою: чистий стан, жодної залежності від сусідів.

**Справжній бій зазвичай асинхронний — інтерфейс і набір мусять це визнати.** Ми взяли синхронний SQLite задля чистоти показу, але справжня база чи мережеве сховище повертає `Promise` / `Future`. Якщо бойовий інтерфейс асинхронний, а фейк лишити синхронним, контракт бреше про **час**: тести проходять там, де в бою між `save` й `recent` вклинюється очікування, чужий запис, перевпорядкування. Правило просте: **фейк повторює форму бою до кінця** — асинхронний бій, асинхронний фейк, той самий набір з `await` на обох. Дублер, легший за оригінал бодай у сигнатурі, — це вже маленька брехня.

**Контракт звіряє поведінку, а не начинку — не пришпилюй реалізацію.** Спокуса дописати в набір перевірку на кшталт «`recent` виконує `ORDER BY`» або «дані лежать відсортовані в масиві». Щойно так зробив — контракт перестав бути спільним: він тепер вимагає **однакової начинки**, і фейк уже не має права бути простішим за базу. Набір має право звіряти лише те, що видно ззовні через `save`/`recent`; **як** саме кожна сторона дотримує обіцянку — її приватна справа. Занадто тісний контракт зчеплює фейк із бойовою реалізацією й краде в тебе свободу, заради якої фейк і заводили.

**Набір ловить не все — знай його межу.** Спільний контракт пришпилює **поведінкову** обіцянку: що зберігається, у якому порядку, якими одиницями. Він за визначенням **не** побачить того, чим фейк і бій різняться найдужче: затримки (база на диску повільна, пам'ять миттєва), поведінки під навантаженням і гонок (два записи водночас), витривалості до збою (переживе показник раптове вимкнення живлення?), вичерпання місця. Це не вада прийому, а його чесна межа: перевірений фейк гарантує, що підробка **поводиться** як бій, а не що вона так само **витримує** бій. Ті властивості ловлять іншим інструментом — інтеграційними й навантажувальними тестами проти справжньої бази.

**Справжня нога набору повільніша — але її таки треба ганяти.** Прогін контракту по SQLite (а тим паче по мережевій базі) коштує дорожче за прогін по пам'яті: підняти базу, накотити схему, прибрати за собою. Спокуса — лишити в наборі тільки фейк, «бо швидко». Це вихолощує весь прийом: набір без бойової ноги знову звіряє фейк проти себе. Розумний компроміс — тримати обидві ноги в наборі, але ганяти справжню рідше: на кожному коміті — фейк, у CI перед злиттям — і фейк, і бій. Головне — не **ніколи**: фейк, чию бойову ногу вимкнули «на потім», старіє точно так само, як фейк без набору.

Зведімо докупи. Перевірений фейк — це не окремий вид фейка, а фейк **із прив'яззю**: один набір перевірок, що описує обіцянку сховища словами поведінки, параметризований реалізацією й прогнаний по обох ногах — підробці й бою. Прив'язь коштує кілька рядків фабрики й спільного тіла перевірок тоді, коли фейк народжується. Без неї фейк тихо дрейфує — менше, ніж обіцяв, як зі згубленим сортуванням, чи більше, ніж уміє бій, як із зайвим дробом часу, — і одного дня зелена збірка обертається падінням у домі. Саме тому кожен фейк, який ти лишаєш жити в тестах, винен тобі цей набір: дешевий цвях сьогодні проти дорогої аварії завтра.
