# 📋 Соціотехнічний контракт, аудит когнітивного навантаження та матриця TCO/Lock-in

Цей довідник містить нормативні шаблони соціотехнічних контрактів взаємодії команд, методику аудиту когнітивного навантаження, специфікацію HTTP-заголовків деприкації та формулу розрахунку вартості виходу з хмарного вендора (Vendor Lock-in Exit Cost).

## 1. Шаблон соціотехнічного контракту взаємодії команд (Team Interaction Contract)

Кожна команда в соціотехнічній топології висуває чіткий контракт взаємодії (Team Interaction Contract), який фіксує її межі, доступні сервіси, режими співпраці та гарантії підтримки.

### 1.1. Назначення та принципи використання соціотехнічного контракту

Соціотехнічний контракт — це декларативний документ у форматі YAML чи Markdown, який зберігається в корені головного репозиторію команди (`/docs/team-contract.yaml`). Він є єдиним джерелом правди про те, які бізнес-контексти належать даній команді, за які репозиторії та топіки повідомлень вона відповідає, які показники SLO підтримує та в якому режимі готова взаємодіяти із сусідніми командами.

Завдяки існуванню соціотехнічного контракту інші інженери в компанії не витрачають час на пошуки відповідальних у Slack чи проведення усних узгоджень. Якщо команді `Devices` потрібен новий ендпоінт від команди `Payments`, вона відкриває її контракт і бачить офіційні канали зв'язку, припустимі режими співпраці та терміни виконання SLA.

### 1.2. Детальна YAML-структура документа контракту

```yaml
# socio-technical-contract.yaml
schema_version: "1.0"
team_name: "Payments & Ledger Team"
team_type: "stream-aligned"  # stream-aligned | platform | enabling | complicated-subdomain
bounded_contexts:
  - name: "Payment Processing"
    domain_type: "core"
    description: "Обробка транзакцій, інтеграція з платіжними шлюзами Stripe/LiqPay"
  - name: "Billing Ledger"
    domain_type: "core"
    description: "Незмінна бухгалтерська книга обліку підписок та балансів користувачів"

interaction_modes:
  - target_team: "Platform Team"
    mode: "X-as-a-Service"
    provided_by_target: "Kubernetes Cluster, PostgreSQL Operator, Vault IDP"
  - target_team: "Device Telemetry Team"
    mode: "Collaboration"
    duration: "2 weeks (Q3)"
    purpose: "Design async event schema for usage-based billing"

owned_artifacts:
  services:
    - name: "payment-gateway-service"
      repo: "github.com/dh/payment-gateway"
      primary_language: "Go"
      maintainers_slack: "#team-payments-dev"
    - name: "ledger-immutable-service"
      repo: "github.com/dh/ledger-service"
      primary_language: "C++"
      maintainers_slack: "#team-payments-core"
  event_topics:
    publishes:
      - topic: "dh.payments.v1.payment-settled"
        schema: "schemas/events/payment-settled.proto"
      - topic: "dh.payments.v1.invoice-generated"
        schema: "schemas/events/invoice-generated.proto"
    subscribes:
      - topic: "dh.telemetry.v1.usage-aggregated"
        consumer_group: "payments-usage-calculator"

slo_commitments:
  api_availability: "99.95%"
  latency_p99_ms: 150
  deprecation_notice_days: 90
  on_call_support: "24/7 Severity-1, Business Hours Severity-2/3"

code_ownership_policy:
  mode: "strict-ownership" # strict-ownership | open-internal-source
  external_prs_allowed: true
  pr_review_sla_hours: 24
  required_approvers_count: 2
```

### 1.3. Регламент трьох режимів взаємодії за Team Topologies

Соціотехнічний дизайн категорично забороняє «безсистемну співпрацю», коли команди безкінечно сидять на спільних мітингах або редагують код одна одної без чітких правил. Взаємодія виділяється строго у три регламентованих режими:

| Режим взаємодії | Опис та сценарії застосування | Правила й обмеження |
| :--- | :--- | :--- |
| **X-as-a-Service** | Одна команда надає продукт або сервіс іншій команді безпосередньо через API чи самообслуговування. | Ніхто не очікує ручних дій; повна автоматизація; чітке SLO; відсутність спільних онлайн-мітингів для щоденної роботи. |
| **Collaboration** | Дві команди тимчасово працюють разом над спільним відкритим питанням чи створенням нового API-інтерфейсу. | Суворо обмежений термін (від 2 днів до 4 тижнів); спільна мета; запобігає тривалому виникненню подвійного володіння (Co-ownership). |
| **Facilitating** | Одна команда (зазвичай Enabling) допомагає іншій команді опанувати нову технологію чи архітектурний патерн. | Команда-фасилітатор НЕ пише код за основну команду; фокус на навчанні, фасилітації та проведення архітектурних воркшопів. |

### 1.4. Регламент управління SLO, Error Budget та чергуванням On-Call

Управління надійністю сервісів у соціотехнічному контракті спирається на концепцію **Error Budget (Бюджет помилок)**:

1. **Цільовий показник доступності (SLO):** Для платіжного домену встановлюється `SLO = 99.95%` (допустимий час простою не більше 21.6 хвилин на місяць).
2. **Бюджет помилок:** `ErrorBudget = 100% - SLO = 0.05%`. Якщо сумарні помилки за місяць вичерпують цей бюджет, усі релізи нових бізнес-фіч автоматично заморожуються. Команда витрачає 100% часу на рефакторинг та підвищення надійності.
3. **Чергування On-Call:** Кожна Stream-aligned команда організовує власне первинне чергування On-Call за своїми сервісами. Автоматичний роутер PagerDuty надсилає сповіщення черговому інженеру відповідної команди за інцидентом Severity-1.

## 2. Опитувальник та аудит когнітивного навантаження (Cognitive Load Assessment)

Обмеження когнітивного навантаження є головним критерієм розкроювання кодової бази та виділення команд. Аудит здійснюється за трикомпонентною моделлю робочої пам'яті інженера.

### 2.1. Класифікація компонентів навантаження

1. **Внутрішня складність (Intrinsic Load):** Складність самого бізнес-домену (наприклад, правила розрахунку податків, алгоритми контролю синхронізації часу, математика обробки відео). Це корисна складність, задля якої компанія наймає фахівців. Вона знижується чистим доменним моделюванням (DDD) та розділенням контекстів.
2. **Стороннє навантаження (Extraneous Load):** Рутинна робота, необхідна для збірки й розгортання проєкту (написання YAML для Kubernetes, налаштування CI/CD конвеєрів, ручний менеджмент SSL-сертифікатів, біганина за доступами). **Має бути мінімізоване до майже нульового рівня за допомогою Внутрішньої платформи розробника (IDP).**
3. **Доречне навантаження (Germane Load):** Корисне когнітивне зусилля, що витрачається на створення бізнес-цінності, проєктування інваріантів домену та покращення якості коду. **Мусить складати 50–60% від загального ресурсу команди.**

### 2.2. Математична формула аудиту когнітивної ємності команди

Загальне когнітивне навантаження команди `L_total` обчислюється за виваженою формулою на основі оцінки за 5-бальною шкалою (де 1 — мінімальне, 5 — критичне перевантаження):

```
L_total = (Intrinsic_Score × 1.2) + (Extraneous_Score × 2.0) + (Germane_Score × 0.8)
```

**Обґрунтування вагових коефіцієнтів:**
- Коефіцієнт `2.0` для `Extraneous_Score` показує руйнівну силу сторонньої рутини: кожна бальна одиниця інфраструктурного хаосу подвоює вигорання розробників.
- Коефіцієнт `1.2` для `Intrinsic_Score` враховує природну складність бізнесу, яку неможливо усунути повністю.
- Коефіцієнт `0.8` для `Germane_Score` зменшує підсумкову тривожність, оскільки корисна доменна робота дає відчуття продуктивності.

**Шкала інтерпретації результату `L_total`:**
- `L_total < 8.0`: **Низьке навантаження.** Команда має вільну ємність. Можна додати новий субдомен або розширити межі контексту.
- `8.0 ≤ L_total ≤ 14.0`: **Оптимальна зона.** Команда працює у стабільному плановому ритмі без вигорання.
- `L_total > 14.0`: **Критичне перевантаження.** Потрібно негайно передати частину Extraneous-навантаження до Platform Team або виділити один із контекстів в окрему Stream-aligned команду.

### 2.3. Листок перевірки аудиту (Checklist для архітектурного квадро-аудиту)

Для проведення щоквартального аудиту когнітивного навантаження команда заповнює наступну матрицю самооцінки:

- [ ] **Критерій 1 (Кількість контекстів):** Чи відповідає команда більше ніж за 2 складні бізнес-контексти (Bounded Contexts)?
- [ ] **Критерій 2 (Кількість артефактів):** Чи перевищує кількість репозиторіїв під опікою однієї команди (розміром 5–8 осіб) 4 оновлюваних сервіси?
- [ ] **Критерій 3 (Інфраструктурна рутина):** Чи витрачають розробники понад 20% робочого часу на підтримку скриптів розгортання, Kubernetes-маніфестів та налаштування середовищ розробки?
- [ ] **Критерій 4 (Локальний запуск):** Чи вимагає запуск локального оточення для розробки понад 30 хвилин або виконання більше ніж 3 команд у терміналі?
- [ ] **Критерій 5 (Автономність знань):** Чи є у кодовій базі мови програмування чи фреймворки, якими у команді володіє лише одна людина (Single Point of Failure)?

### 2.4. План дій при виявленні критичного перевантаження (`L_total > 14.0`)

При зафіксованому критичному перевантаженні архітектор вживає наступних невідкладних заходів:
1. **Інвентаризація Extraneous-рутини:** Platform Team переводить сервіси команди на Золотий шлях (Golden Path) — авто-генерування маніфестів розгортання та централізоване керування секретами.
2. **Відокремлення складних субдоменів:** Якщо Intrinsic Load залишається високим через важку математику обробки відеопотоків, цей модуль передається новоствореній Complicated-Subdomain команді.
3. **Брунькування команди:** Якщо в кодовій базі є два незалежних контексти (наприклад, `Devices` та `Firmware Updates`), команда ділиться на дві Stream-aligned групи по 5 осіб.

### 2.5. Стратегії зниження когнітивного навантаження при розплетенні монолітів

При розплетенні успадкованого моноліту команда потрапляє в пастку тимчасового подвоєння когнітивного навантаження: розробники вимушені одночасно підтримувати старий монолітний код і будувати нові мікросервіси.

Для розвантаження команди застосовуються три соціотехнічні стратегії:
1. **Замороження монолітної сфери (Freeze Boundary):** Розробникам забороняється додавати нові класи чи таблиці у старий моноліт. Будь-яка нова функціональність створюється виключно у новому сервісі поруч.
2. **Тимчасова залучення Enabling Team:** Експертна команда з розгортання microservice chassis підключається на 3 тижні, щоб налаштувати CI/CD, трейсинг та метрики для нового сервісу, не відволікаючи розробників від доменного коду.
3. **Ізоляція БД через CDC (Change Data Capture):** Замість написання складного коду подвійного запису в моноліті вмикається Debezium / Kafka Connect, який асинхронно транслює зміни з таблиць моноліту в нові сервіси.

## 3. Специфікація RFC/W3C HTTP-заголовків деприкації API

При виведенні з експлуатації старого API або сервісу в межах еволюційної архітектури використання одних лише листівок електронною поштою є неефективним. Система повинна транслювати свій стан безпосередньо у HTTP-протоколі.

### 3.1. Специфікація заголовків `Deprecation` та `Sunset`

Згідно із стандартами RFC 8594 (`Sunset` header) та IETF Draft (`Deprecation` header), сервер повертає наступні метадані у відповідь на будь-який запит до старого ендпоінту:

```http
HTTP/1.1 200 OK
Date: Tue, 18 Aug 2026 10:00:00 GMT
Content-Type: application/json
Deprecation: @1785000000
Sunset: Sun, 15 Nov 2026 23:59:59 GMT
Link: <https://developer.dh.io/docs/migrations/v1-to-v2>; rel="deprecation"; type="text/html"
Link: <https://api.dh.io/api/v2/telemetry>; rel="successor-version"

{
  "status": "success",
  "data": { ... }
}
```

### 3.2. Значення та семантика полів

- **`Deprecation`:** Вказує момент часу (у форматі Unix Timestamp з символом `@` або HTTP-Date), коли ендпоінт офіційно оголошено застарілим. Сигналізує інструментарію споживача про необхідність спланувати міграцію.
- **`Sunset`:** Вказує точну дату й час у майбутньому, коли ендпоінт буде **остаточно вимкнено**. Після настання цієї дати сервер почне повертати `HTTP 410 Gone` або `HTTP 404 Not Found`.
- **`Link; rel="deprecation"`:** Посилання на документацію з детальною інструкцією щодо міграції на нову версію.
- **`Link; rel="successor-version"`:** Пряме посилання на новий URI API-ендпоінту, який замінює поточний.

### 3.3. HTTP Статус-коди та стратегія обробки на шлюзі

1. **Фаза Notice (До дати Sunset):** Шлюз повертає статус `HTTP 200 OK` або `HTTP 201 Created`, але додає заголовки `Deprecation`, `Sunset` та `Link`.
2. **Фаза Sunset Expired (Після дати Sunset):** Шлюз відхиляє обробку і повертає `HTTP 410 Gone`. Тіло відповіді містить JSON із поясненням та посиланням на новий ендпоінт.
3. **Обробка застарілих вебхуків:** Для асинхронних вебхуків заголовок `Deprecation` передається в метаданих події (`cloud_events_headers`).

### 3.4. Окремі специфікації заголовків для gRPC та Protobuf

Для внутрішніх gRPC міжсервісних викликів метадані деприкації передаються через gRPC Metadata Headers (`metadata` / `context.Context`):

```protobuf
// telemetry_v1.proto — Позначення застарілих полів у Protobuf
message TelemetryRequest {
  string device_id = 1;
  double temperature = 2 [deprecated = true]; // Застаріле поле
  double ambient_temp_celsius = 3;             // Нове замінне поле
}
```

Вхідні gRPC-запити до методів із позначкою `deprecated = true` супроводжуються метаданими відповіді:
- `x-deprecation-date: 2026-08-18T10:00:00Z`
- `x-sunset-date: 2026-11-15T23:59:59Z`
- `x-successor-method: /dh.telemetry.v2.TelemetryService/Ingest`

## 4. Формула розрахунку TCO та оцінки Vendor Lock-in Exit Cost

Вибір між власними абстракціями (Self-hosted) та хмарними закритими сервісами (Proprietary Cloud Services) вимагає суворого математичного підрахунку Повної вартості володіння (TCO) та Ціни виходу (Exit Cost).

### 4.1. Формула Повної вартості володіння (TCO)

Повна вартість володіння інфраструктурним вузлом за період `T` (наприклад, 12 місяців) обчислюється як:

```
TCO = C_infra + C_ops + C_cognitive
```

Де:
- `C_infra`: Прямі рахунки за хмару або обладнання (сервери, диски, трафік, ліцензії).
- `C_ops`: Заробітна плата інженерів, витрачена на обслуговування, оновлення, патчі безпеки та ліквідацію аварій (`Hours_ops × Rate`).
- `C_cognitive`: Вартість затримки виходу нових фіч через складність інфраструктури (оцінюється як втрачена бізнес-вигода від прострочених релізів).

### 4.2. Формула розрахунку Lock-in Exit Cost (Ціни виходу)

Ціна виходу (Exit Cost) — це фінансові та часові витрати, необхідні для повної міграції системи з одного вендора чи технології на іншу:

```
ExitCost = (H_rewrite × Rate) + C_migration_data + C_downtime_risk
```

Де:
- `H_rewrite`: Кількість людино-годин, необхідних для переписування коду, що прямо залежить від закритих SDK вендора.
- `C_migration_data`: Вартість мережевого вигрузу даних (Egress Fees) та написання скриптів трансформації даних.
- `C_downtime_risk`: Потенційні збитки бізнесу від ризику простою під час перемикання.

### 4.3. Оціночна матриця коефіцієнта заціплення (Lock-in Index)

| Шар технологічного стека | Рівень заціплення (Lock-in Index) | Приклад технологій | Оцінка H_rewrite та Exit Cost |
| :--- | :--- | :--- | :--- |
| **Layer 1: Bare Compute / OS** | **Дуже низький (1/5)** | Linux, Docker, Standard POSIX, x86/ARM | Низька. Перенесення контейнера вимагає 2–4 годин. |
| **Layer 2: Open Standard Managed** | **Низький (2/5)** | AWS RDS (PostgreSQL), Managed Kafka (MSK) | Низька–Середня. Перемикання connection string; міграція даних стандартним `pg_dump` чи CDC. |
| **Layer 3: Cloud Frameworks** | **Середній (3/5)** | Kubernetes (EKS/GKE), Terraform, OpenTelemetry | Середня. Шаблони сумісні, але відрізняються провайдери IAM та Storage Classes. |
| **Layer 4: Proprietary Data Stores** | **Високий (4/5)** | AWS DynamoDB, Google BigTable, CosmosDB | Висока. Потрібне повне переписування шардингу, індексів та запитів у коді. |
| **Layer 5: Serverless Ecosystem** | **Критичний (5/5)** | AWS Lambda + AppSync + Step Functions + EventBridge | Екстремальна. Код сервісу повністю переплетений з провайдерськими подіями та SDK. |

### 4.4. Числові приклади розрахунку Exit Cost

#### Приклад 1. Вихід з AWS DynamoDB на PostgreSQL

Розглянемо практичний розрахунок виходу з AWS DynamoDB на Self-hosted PostgreSQL для сервісу телеметрії з 100 мільйонами записів:

1. **Витрати на переписування коду (`H_rewrite × Rate`):** Команда з 3 Go-розробників витрачає 6 тижнів (720 людино-годин) на видалення DynamoDB SDK, написання нових SQL-запитів у PostgreSQL, налаштування індексів та переписування Unit-тестів. При ставці `$50/годину`:
   ```
   Cost_code = 720 × 50 = $36,000
   ```
2. **Витрати на міграцію даних (`C_migration_data`):** Вигруз 2 ТБ даних із DynamoDB через Egress Traffic (`$0.09/ГБ`) плюс оновлення AWS DynamoDB Streams експорту:
   ```
   Cost_data = 2000 × 0.09 + $1,500 (CloudWatch/DynamoRead) = $1,680
   ```
3. **Оцінка ризиків простою (`C_downtime_risk`):** 2 години планованого технічного вікна з потенційною втратою 0.01% вхідного трафіку:
   ```
   Cost_risk = $5,000
   ```
4. **Підсумковий Exit Cost:**
   ```
   ExitCost = $36,000 + $1,680 + $5,000 = $42,680
   ```

#### Приклад 2. Вихід з AWS Kinesis на Apache Kafka (MSK)

Розглянемо розрахунок міграції потокової обробки подій з пропрієтарного AWS Kinesis на Managed Kafka (MSK):

1. **Витрати на переписування коду:** Заміна Kinesis Client Library (KCL) на стандартну бібліотеку `franz-go` або `confluent-kafka-go` у 4 мікросервісах вимагає 160 людино-годин:
   ```
   Cost_code = 160 × 50 = $8,000
   ```
2. **Витрати на міграцію даних:** Оскільки потокові дані є ефемерними (time-to-live 24 години), старі події не вигружаються. Новий потік запускається паралельно. Витрати на дублювання трафіку протягом 24 годин:
   ```
   Cost_data = $300
   ```
3. **Підсумковий Exit Cost:**
   ```
   ExitCost = $8,000 + $300 = $8,300
   ```

Оскільки `$8,300` є відносно невеликою сумою, міграція з Kinesis на Kafka має низький поріг завад і повністю виправдовує себе при підвищенні обсягу трафіку понад 50 000 повідомлень на секунду.

### 4.5. Чеклист FinOps-оптимізації та принципи екологічної хмарної архітектури

Для підтримки оптимального TCO та контролю за хмарними витратами компанія впроваджує наступний FinOps-регламент:

- [ ] **Обов'язкове тегування:** Кожен інфраструктурний ресурс має прикріплені теги `Environment` (prod/staging), `OwnerTeam` та `CostCenter`. Resources без тегів автоматично зупиняються нічним платформеним скриптом.
- [ ] **Правомірність розмірів (Right-Sizing Audit):** Щомісячний аналіз використання vCPU та RAM у Kubernetes-кластерах. Сервіси із середнім завантаженням CPU < 15% утилізуються або об'єднуються.
- [ ] **Запобігання пасткам зарезервованої ємності (Reserved Instances vs Spot):** Непродуктивні оточення (Dev/Staging) розгортаються виключно на спотових інстансах (AWS Spot Instances), що знижує інфраструктурні витрати на 70%.
- [ ] **Контроль Egress-трафіку:** Всі міжсервісні виклики всередині одного регіону маршрутизуються через приватні VPC Endpoints, запобігаючи виходу трафіку у публічний інтернет.

Завдяки дотриманню цих нормативних вимог компанія отримує повну фінансову прозорість інфраструктурних витрат, тримаючи Повну вартість володіння (TCO) та Ціну виходу (Exit Cost) під постійним контрольним контролем.

> 💡 **Правило архітектора:** Якщо планована економічна вигода від переходу на власну інфраструктуру за 2 роки менша ніж `ExitCost ($42,680)`, міграція є економічно недоцільною, і системі слід залишитися на managed-сервісі.
