# 📋 Специфікація W3C Trace Context та атрибути OpenTelemetry

Цей довідник описує повний технічний контракт поширення контексту трасування у розподілених мікросервісних системах: кодування та правила обробки заголовків W3C Trace Context (`traceparent` і `tracestate`), бінарний формат gRPC, модель даних спанів OpenTelemetry, специфікацію екземплярів Prometheus Exemplars та правила структурування JSON-логів для наскрізної кореляції телеметрії.

---

## 1. Специфікація W3C Trace Context

Коли один мікросервіс звертається до іншого через протоколи HTTP/1.1, HTTP/2 або gRPC, він зобов'язаний передати ідентифікатор поточного трасування. Специфікація **W3C Trace Context** регламентує два HTTP-заголовки: `traceparent` (обов'язковий стандартний заголовок) та `tracestate` (необов'язковий заголовок для вендорних даних).

### 1.1. Структура заголовка `traceparent`

Заголовок `traceparent` — це кодований ASCII-рядок строго фіксованої довжини (55 символів), що складається з чотирьох полів, розділених дефісами:

```
version - trace_id - parent_id - trace_flags
```

Приклад реального заголовка на дроті:
`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`

```
 00 - 4bf92f3577b34da6a3ce929d0e0e4736 - 00f067aa0ba902b7 - 01
 ──   ────────────────────────────────   ────────────────   ──
 │                   │                           │           │
 │                   │                           │           └─ TraceFlags (8 бітів / 2 hex)
 │                   │                           └─ ParentSpanID (64 біти / 16 hex)
 │                   └─ TraceID (128 бітів / 32 hex)
 └─ Версія заголовка (8 бітів / 2 hex)
```

| Поле | Розмір | Формат | Опис та правила валідації |
| :--- | :--- | :--- | :--- |
| `version` | 1 байт (2 hex) | `00` | Поточна версія специфікації W3C. Значення `ff` вважається недійсним і призводить до відкидання всього заголовка. Якщо сервіс бачить невідому йому версію (наприклад, `01`), він повинен спробувати розпарсити заголовок за правилами версії `00`. |
| `trace_id` | 16 байтів (32 hex) | `4bf92f3577b34da6a3ce929d0e0e4736` | Унікальний 128-бітний ідентифікатор усього розподіленого трасування. Генерується на крайовому шлюзі (Edge Proxy) й залишається абсолютно незмінним уздовж усього ланцюга мікросервісних викликів. Значення `00000000000000000000000000000000` заборонено стандартом і вважається недійсним. |
| `parent_id` / `span_id` | 8 байтів (16 hex) | `00f067aa0ba902b7` | 64-бітний ідентифікатор батьківського спану (конкретного виклику, який зробив даний запит). Кожен новий мікросервіс при створенні власного спану генерує новий `span_id`, але передає його нижче за течією як `parent_id`. Значення `0000000000000000` недійсне. |
| `trace_flags` | 1 байт (2 hex) | `01` | 8 бінарних прапорців керування трасуванням. Наразі стандартизовано 0-й біт (`01` — `Sampled`). |

#### Бітова маска полів `trace_flags`

```
+---+---+---+---+---+---+---+---+
| 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
+---+---+---+---+---+---+---+---+
                              │
                              └─ Bit 0: Recorded / Sampled (1 = так, 0 = ні)
```

* **Bit 0 (`Sampled`)**: Якщо біт дорівнює `1`, це означає, що цей запит вибрано системою вибірки (sampling) і відправлено до зберігача трейсів. Якщо біт дорівнює `0`, запит не зберігається у базі трейсів, проте заголовок `traceparent` все одно **зобов'язаний прокидатися далі** по ланцюгу мікросервісів для збереження цілісності `trace_id` у логах.
* **Bits 1–7**: Зарезервовані для майбутніх розширень стандарту W3C (мусять дорівнювати `0`).

### 1.2. Структура заголовка `tracestate`

Заголовок `tracestate` слугує для передачі вендор-специфічних метаданих у вигляді списку пар ключ-значення, розділених комами. Це дозволяє декільком системам спостережуваності (наприклад, OpenTelemetry, Datadog, Dynatrace, New Relic) співіснувати в одній інфраструктурі без конфліктів.

Синтаксис заголовка:

```http
tracestate: rojo=123,congo=456,dh_tenant=building_84,dd=s:1;p:00f067aa
```

#### Правила мутації та обробки `tracestate`

1. **Порядок ключів**: Новий або оновлений ключ завжди додається на **початок (ліворуч)** рядка `tracestate`.
2. **Максимальний розмір**: Заголовок не може перевищувати 512 символів або містити більше 32 елементів. Якщо розмір перевищено, найстаріші елементи з правої частини списку відкидаються.
3. **Формат ключів**: Простий ключ складається з ASCII-символів (наприклад, `rojo`). Вендорний ключ може містити префікс із символом `@` (наприклад, `fw@system=12`).
4. **Прокидання**: Сервіс зобов'язаний зберегти всі незнайомі йому пари ключ-значення й передати їх downstream-запиту без змін.

---

### 1.3. Бінарний формат gRPC Trace Context (`grpc-trace-bin`)

Під час використання gRPC замість HTTP-заголовків використовується бінарне метаполе `grpc-trace-bin`. Воно упаковує `trace_id`, `parent_id` та `trace_flags` у компактну послідовність байтів з префіксами полів (Protobuf-style tags):

```
+-----------+-----------------------------------+-----------+-------------------+-----------+-------------+
| Field 0   | TraceID Value                     | Field 1   | ParentID Value    | Field 2   | Flags Value |
| 1 byte    | 16 bytes                          | 1 byte    | 8 bytes           | 1 byte    | 1 byte      |
| (0x00)    | (128-bit hex representation)      | (0x01)    | (64-bit hex)      | (0x02)    | (8-bit)     |
+-----------+-----------------------------------+-----------+-------------------+-----------+-------------+
```

Загальний розмір бінарного кадру становить 29 байтів. Це зменшує накладні витрати на серіалізацію метаданих у високонавантажених gRPC-з'єднаннях між внутрішніми мікросервісами.

## 2. Модель даних спану OpenTelemetry (Span Data Model)

Спан (Span) — це фундаментальна одиниця роботи в розподіленому трейсингу. Він представляє одну дискретну операцію з чітко визначеним часом початку та завершення.

### 2.1. Обов'язкова структура полів OpenTelemetry Span

JSON-схема спану, що відправляється до OpenTelemetry Collector:

```json
{
  "name": "SELECT device_telemetry_events",
  "context": {
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "5c067aa0ba902b71",
    "trace_flags": "01"
  },
  "parent_span_id": "00f067aa0ba902b7",
  "kind": "SPAN_KIND_CLIENT",
  "start_time_unix_nano": 1771402500100000000,
  "end_time_unix_nano": 1771402514280000000,
  "attributes": {
    "db.system": "postgresql",
    "db.name": "digital_homes_prod",
    "db.statement": "SELECT * FROM device_telemetry_events WHERE payload->>'status' = 'offline'",
    "db.user": "telemetry_writer",
    "net.peer.name": "pg-cluster-primary.internal",
    "net.peer.port": 5432
  },
  "events": [
    {
      "time_unix_nano": 1771402500150000000,
      "name": "db.lock_wait_start",
      "attributes": {
        "lock.type": "ExclusiveLock",
        "lock.target": "relation:device_telemetry_events"
      }
    },
    {
      "time_unix_nano": 1771402514250000000,
      "name": "db.lock_acquired",
      "attributes": {
        "lock.wait_duration_ms": 14100
      }
    }
  ],
  "status": {
    "code": "STATUS_CODE_ERROR",
    "message": "Query execution time exceeded statement_timeout threshold"
  }
}
```

---

### 2.2. Категорії типів спанів (`SpanKind`)

Тип спану вказує на його роль у мережевому або процесному графіку викликів:

| `SpanKind` | Опис ролі в архітектурі | Приклад у Digital Homes |
| :--- | :--- | :--- |
| `SERVER` | Вхідний синхронний запит від зовнішнього або внутрішнього клієнта (HTTP/gRPC server). | Envoy прийняв `POST /api/v2/devices/unlock`. |
| `CLIENT` | Вихідний синхронний виклик до зовнішнього сервісу або бази даних (HTTP/gRPC/DB client). | Node.js надсилає SQL-запит до PostgreSQL. |
| `PRODUCER` | Асинхронне відправлення повідомлення у брокер черг. | Запис події тривоги у тему Apache Kafka / RabbitMQ. |
| `CONSUMER` | Асинхронна вибірка та обробка повідомлення з черги. | Фоновий воркер обробляє подію з Kafka. |
| `INTERNAL` | Внутрішньопроцесна обробка без мережевих меж. | Обчислення хелс-індексу квартири за формулою. |

---

### 2.3. Коди статусів спану (`SpanStatus`)

Кожен спан завершується з одним із трьох стандартних статусів:

1. `STATUS_CODE_UNSET` (дефолтний): Операція завершилася без явних помилок. Статус інтерпретується як успіх, якщо немає винятків.
2. `STATUS_CODE_OK`: Сервіс явно підтвердив успішне виконання бізнес-операції.
3. `STATUS_CODE_ERROR`: Запит завершився збоєм (системна помилка, таймаут, необроблений виняток, код HTTP 5xx). При встановленні `STATUS_CODE_ERROR` обов'язково заповнюється поле `message`.

---

### 2.4. Модель подій всередині спану (Span Events)

Подія спану (Span Event) — це внутрішньочасовий маркер (timestamped annotation), який фіксує точний момент виникнення певної внутрішньої ситуації без створення окремого дочірнього спану. Події ідеально підходять для логування проміжних етапів: `db.lock_wait_start`, `cache_miss`, `retry_attempt_1`.

## 3. Prometheus Exemplars: Специфікація з'єднання метрик і трейсів

**Exemplar** (екземпляр) — це конкретний запис вимірювання, який прив'язується до значення гістограми або лічильника в Prometheus. Вона містить унікальний `trace_id`, значення виміряної величини та точну часову мітку.

### 3.1. Текстовий формат Prometheus OpenMetrics з Exemplars

Під час опитування ендпоінту `/metrics` через Prometheus OpenMetrics parser, сервіс повертає рядок гістограми з розширенням Exemplar:

```http
# TYPE http_request_duration_seconds histogram
# HELP http_request_duration_seconds Тривалість HTTP запитів у секундах.
http_request_duration_seconds_bucket{le="0.05",service="telemetry-svc"} 142050
http_request_duration_seconds_bucket{le="0.5",service="telemetry-svc"} 148900
http_request_duration_seconds_bucket{le="10.0",service="telemetry-svc"} 149110 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 8.42 1771402508.420
http_request_duration_seconds_bucket{le="+Inf",service="telemetry-svc"} 149200 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 14.21 1771402514.280
```

Синтаксичний аналіз рядка Exemplar:

`# { trace_id = "HEX32" } VALUE TIMESTAMP`

* `{trace_id="..."}`: Набір атрибутів екземпляра (сумарно не більше 128 символів).
* `VALUE`: Точне виміряне значення часу відповіді чи розміру кадру (наприклад, `14.21` секунди).
* `TIMESTAMP`: Час події у форматі UNIX timestamp (секунди з плаваючою крапкою).

---

### 3.2. Обмеження та збереження Exemplars у Prometheus TSDB

1. **In-Memory Ring Buffer**: Prometheus зберігає Exemplars у тимчасовому кільцевому буфері пам'яті (за замовчуванням протягом 24 годин).
2. **Низькі накладні витрати**: Зберігається лише один останній Exemplar на кожне вимірювання бакета, що запобігає роздуванню бази даних метрик.
3. **Інтеграція з Grafana**: При наведенні курсора на точку графіка перцентиля p99 у Grafana, інтерфейс витягає `trace_id` з Exemplar і відображає пряме посилання для переходу в Jaeger/Tempo.

## 4. Контракт структурованих JSON-логів для кореляції

Для того щоб інструменти агрегації логів (Grafana Loki, Elasticsearch, OpenSearch, ClickHouse) могли миттєво згрупувати всі записи логів, згенеровані під час виконання конкретного трейсу, логер сервісу зобов'язаний ін'єктувати поля `trace_id` та `span_id` у кожен JSON-рядок.

### 4.1. Стандартна схема полів логу Digital Homes

```json
{
  "timestamp": "2026-08-18T14:15:14.280Z",
  "level": "ERROR",
  "service": "device-telemetry-service",
  "environment": "production",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "5c067aa0ba902b71",
  "trace_flags": "01",
  "home_id": "dh-home-ua-kyiv-0841",
  "device_id": "lock-front-door-991",
  "message": "Database query execution failed due to lock wait timeout",
  "error": {
    "type": "QueryFailedError",
    "code": "55P03",
    "detail": "canceling statement due to lock timeout",
    "stack": "QueryFailedError: canceling statement due to lock timeout\n  at PostgresQueryRunner.query (/app/node_modules/typeorm/driver/postgres/PostgresQueryRunner.js:211:19)"
  },
  "db": {
    "query_duration_ms": 14180,
    "lock_wait_ms": 14100,
    "table": "device_telemetry_events"
  }
}
```

### 4.2. Семантичні стандарти йменування полів (OpenTelemetry Semantic Conventions)

Для забезпечення однакового парсингу в усіх мікросервісах бекенду використовуються єдині назви полів:

| Назва поля | Тип | Формат / Значення | Призначення |
| :--- | :--- | :--- | :--- |
| `timestamp` | Rядок | ISO-8601 UTC (`2026-08-18T14:15:14.280Z`) | Точний астрономічний час фіксації події. |
| `level` | Рядок | `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` | Рівень важливості повідомлення. |
| `service` | Рядок | Lowercase k8s app label (`device-telemetry-service`) | Ідентифікатор мікросервісу. |
| `trace_id` | Рядок | 32 hex символи нижнього регістру | Ідентифікатор трасування W3C. |
| `span_id` | Рядок | 16 hex символів нижнього регістру | Ідентифікатор поточного спану. |
| `error.type` | Рядок | Клас помилки (`QueryFailedError`, `TimeoutError`) | Назва типу винятку для групування. |
| `db.statement` | Рядок | Очищений SQL-рядок (без паролів та персональних даних) | Текст запиту до бази даних. |

Завдяки трибічній узгодженості специфікацій (W3C `traceparent` ↔ OpenTelemetry Span ↔ Prometheus Exemplars ↔ Structured JSON Logs) оператор отримує суцільну видимість виконання системи від зовнішнього HTTP-запиту до найнижчого рядка блокування в базі даних.
